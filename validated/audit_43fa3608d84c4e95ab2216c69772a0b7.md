### Title
Direct transfer of `stakingToken` to `operator` inflates `totalStaked()` and permanently dilutes `rewardPerTokenStored`, freezing yield for honest stakers - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BaseRewardPoolV2.totalStaked()` computes the pool's total stake purely from `IERC20(stakingToken).balanceOf(operator)`, which is fully decoupled from the per-user accounting kept in `MasterMagpie.userInfo` (exposed via `stakingInfo`). Any holder of the raw `stakingToken` who transfers it directly to `operator` (MasterMagpie) instead of calling `deposit`/`depositFor` inflates the denominator used in `_provisionReward`, permanently diluting `rewardPerTokenStored` for every legitimate staker without ever crediting a `balanceOf(_account)` increase.

### Finding Description
`totalStaked()` reads the raw ERC20 balance of the operator: [1](#0-0) 
while `balanceOf(_account)` is derived independently from `MasterMagpie.stakingInfo`, which is backed by the `userInfo[_stakingToken][_account].amount` mapping updated only inside `_deposit`/`_withdraw`: [2](#0-1) [3](#0-2) [4](#0-3) 

`_provisionReward` divides the incoming reward amount by `totalStaked()` to update `rewardPerTokenStored`: [5](#0-4) 

Because `totalStaked()` and the sum of tracked `userInfo.amount` are two independent state sources, any raw ERC20 transfer of `stakingToken` straight to the `operator` address (bypassing `deposit`/`depositFor`) increases the divisor without crediting any account, permanently shrinking the `rewardPerTokenStored` increment computed on the next `queueNewRewards`/`donateRewards` call. Legitimate stakers' `earned()` is computed from `balanceOf(_account) * rewardPerTokenStored`, so they receive less than the amount of reward token actually deposited into the contract; the shortfall has no other exit path and remains stuck in the reward pool contract.

Feasibility caveat: for pools that use `WombatPoolHelperV2` (`depositLP`/`deposit`), the `stakingToken` (Wombat receipt token) is minted directly to the pool-helper contract inside `WombatStaking.depositLP`/`deposit` (`msg.sender` = the helper, gated by `_onlyActivePoolHelper`), and is auto-staked into MasterMagpie in the same transaction: [6](#0-5) [7](#0-6) 
An ordinary EOA never actually holds a raw balance of this receipt token in this flow, so the exact "depositLP then direct transfer" sequence described in the question is not directly reachable by an unprivileged attacker for helper-managed pools; becoming a pool helper requires a privileged/authorized role, which is out of scope. However, for pools registered directly against `MasterMagpie.deposit(_stakingToken, _amount)` where users hold a plain, freely transferable ERC20 in their own wallet before calling `deposit` (e.g. any pool where `pool.stakingToken` is a standard transferable token the depositor already owns), the attacker legitimately holds the raw token and can simply send it to `operator` instead of calling `deposit`, triggering the dilution described.

### Impact Explanation
This is a permanent-freezing-of-unclaimed-yield issue: once `rewardPerTokenStored` is computed with an inflated `totalStaked()`, the affected reward epoch's diluted portion can never be recovered by legitimate stakers because there is no reconciliation between raw token balance and per-user share accounting. The griefing degrades yield accrual for every staker in that pool for as long as the excess balance remains at the operator address (indefinitely, since nothing burns/withdraws it back out via normal flows).

### Likelihood Explanation
Likelihood is low-to-moderate and pool-dependent. It requires the attacker to hold a raw, freely transferable balance of the specific `stakingToken` used by a given `BaseRewardPoolV2` instance outside of an auto-stake wrapper flow. This is not achievable for `WombatPoolHelperV2`-wrapped pools (receipt token never reaches attacker's wallet, and becoming a pool helper is privileged). It is achievable for pools where users deposit a plain token they already control directly via `MasterMagpie.deposit`. The attack requires no special privileges, only capital equal to however much stake dilution the attacker wants to cause, and it is a pure griefing action (the attacker's tokens are sent for no return, so it is not directly profitable to them).

### Recommendation
Track `totalStaked()` as an internal accounting variable incremented/decremented only inside `_deposit`/`_withdraw` (mirroring `BribeRewardPool.totalSupply`), rather than reading `IERC20(stakingToken).balanceOf(operator)`, so direct/donation transfers cannot influence reward-per-token calculations. Alternatively, add a `sync()`/skim mechanism that only credits balances increased through the tracked deposit path, and sweep any un-attributed token balance rather than letting it silently distort `totalStaked()`.

### Proof of Concept
Foundry test plan (for a directly-deposited pool, e.g. an MGP-based `BaseRewardPoolV2`/`vlMGPBaseRewarder` pool where `stakingToken` is a plain transferable ERC20 the user controls before depositing):
1. Deploy `MasterMagpie`, register a pool with a mock ERC20 `stakingToken`, deploy `BaseRewardPoolV2` as its rewarder, add a rewardManager.
2. Mint `stakingToken` to `staker1` and `attacker`. `staker1` calls `MasterMagpie.deposit(stakingToken, 100e18)`.
3. Manager calls `queueNewRewards(100e18, rewardToken)`; record `rewardPerTokenStored_before` (should equal `100e18 * 1e18 / 100e18`).
4. `attacker` calls `stakingToken.transfer(address(masterMagpie), 900e18)` directly (bypassing `deposit`), inflating `IERC20(stakingToken).balanceOf(masterMagpie)` to 1000e18 without any `userInfo` update.
5. Manager calls `queueNewRewards(100e18, rewardToken)` again; assert `rewardPerTokenStored` increment is `100e18 * 1e18 / 1000e18`, i.e., 10x smaller than it would have been absent the direct transfer (`100e18 * 1e18 / 100e18`).
6. Assert `staker1.earned(rewardToken)` reflects the diluted amount, and total reward tokens claimable by all stakers sums to less than the 200e18 total deposited via `queueNewRewards`, with the remainder permanently stuck in the rewarder contract.
