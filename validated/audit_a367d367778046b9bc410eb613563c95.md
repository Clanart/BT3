### Title
DataLayer SSRF via unauthenticated on-chain mirror URLs fetched by `http_download` - (File: `chia/data_layer/download_data.py`)

### Summary
Any wallet holder can publish an arbitrary URL as a "mirror" for **any** DataLayer store (not just their own) by spending a small amount of XCH to create a mirror coin with `create_new_mirror`, memo-tagging it with the target `launcher_id` and attacker-chosen URLs. Any DataLayer node that is tracking/subscribed to that store will treat the URL as a valid file-server and issue an unauthenticated HTTP GET to it in `http_download`, with no validation that the target host isn't loopback, link-local, or an RFC 1918 private address, and no re-validation of redirect targets.

### Finding Description
`DataLayerWallet.create_new_mirror` builds a spend that creates a "mirror" coin whose memo encodes `[launcher_id, *urls]`, with no check that the sender owns or controls the `launcher_id`/singleton being mirrored: [1](#0-0) 

When any peer sees this coin spent, `DataLayerWallet.coin_added` decodes the mirror and, as long as the referenced `launcher_id` is a store the node is tracking (i.e. a store the node has subscribed to, which any user/Data Layer client can do for any public store), it stores the attacker-supplied URL as a legitimate mirror for that store: [2](#0-1) 

`DataLayer.add_mirror` also exposes this over RPC and enforces only that the URL list is non-empty — no scheme/host restriction: [3](#0-2) 

During sync, `DataLayer.fetch_and_validate` pulls `servers_info` (populated from tracked mirrors) for the store and, for each, calls `insert_from_delta_file` → `download_file` → `http_download`, using `server_info.url` directly: [4](#0-3) [5](#0-4) 

`http_download` performs an `aiohttp` GET to `server_info.url + "/" + filename` with no validation that the resolved/target host is not a loopback, link-local, or private-range address, and `aiohttp` follows redirects by default with no revalidation of the redirect target. This mirrors the reported bug class in `@steipete/summarize` (GHSA-3vx2-vqx8-jxfg / CVE-2026-53782), where an attacker-controlled feed entry (here: an attacker-controlled on-chain mirror URL) causes the host application to make outbound requests to internal/reserved network destinations without hostname/redirect revalidation.

### Impact Explanation
A DataLayer client tracking any public store is coerced into issuing HTTP requests to arbitrary attacker-chosen destinations (internal services, cloud metadata endpoints, loopback ports, other RFC1918 hosts), and — because the request body/response is fed into `insert_from_delta_file`/DB insertion logic — this can be used to probe internal services, trigger internal side effects on reachable HTTP endpoints, or, combined with DNS rebinding/redirects, exfiltrate response data indirectly via error/timing/behavior of the DataLayer sync process. This is reachable by any unprivileged wallet user who can afford the mirror-coin fee, targeting any DataLayer client that subscribes to the affected store — no special network position or privilege is required.

### Likelihood Explanation
High reachability: creating a mirror coin costs only a small transaction fee/amount and requires no ownership of the target store's singleton; any node that syncs/tracks the store will automatically pick up and fetch from the malicious mirror URL during normal `fetch_and_validate` operation.

### Recommendation
Before dispatching `http_download`/plugin download requests, validate that `server_info.url`'s resolved host is not loopback, link-local, or within private/reserved IP ranges (and re-validate after DNS resolution and on every redirect hop, disabling automatic redirect following or manually revalidating each `Location`). Additionally, consider requiring mirror publishers to prove ownership/authorization for the `launcher_id` they are mirroring, or allow store owners/operators to explicitly allow-list trusted mirror URLs rather than trusting any on-chain mirror coin.

### Proof of Concept
1. Attacker creates a DataLayer mirror coin for a victim's `launcher_id` (a store the victim's node is known to track) pointing to `http://127.0.0.1:<victim-internal-port>` or a cloud metadata IP, via `dl_new_mirror`/`create_new_mirror` — no ownership check is enforced: [1](#0-0) 
2. Once confirmed, the victim's `DataLayerWallet.coin_added` records this as a legitimate mirror for the tracked launcher_id.
3. On the victim's next `fetch_and_validate` cycle for that store, `http_download` issues a GET to the attacker-controlled internal URL: [5](#0-4) 
4. The request succeeds or fails depending on the internal target, revealing information about internal network topology/service availability to the attacker (who can infer results from mirror "miss" tracking/log timing), and can be used to hit unauthenticated internal HTTP endpoints.

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
