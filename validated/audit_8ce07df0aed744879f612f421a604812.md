### Title
`incentiveDeposit` reward double-counting via `mWomSV.startUnlock` manipulating `getUserTotalLocked` - ([File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.getRewardAmount` and `calDoubledCounted` both derive the "already rewarded" baseline from a live, user-controllable read of `mWomSV.getUserTotalLocked(_account)` instead of a monotonically-stored record. Because `mWomSV.startUnlock` instantly lowers `getUserTotalLocked` (it only moves accounting from "locked" to "cooldown" inside `mWomSV`, with no penalty, no token movement, and no delay for the call itself), an attacker can shrink this baseline between deposits and get the same MGP reward tier paid out again for tokens that were already rewarded.

### Finding Description
`getRewardAmount` computes, for the lock path (`_lock == true`):
```
accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account)
rewardAmount = tieredSum(accumulated)
mgpReward = rewardAmount/DENOMINATOR - calDoubledCounted(_account)
``` [1](#0-0) 

and `calDoubledCounted` recomputes the "already paid" tiered reward purely from the current `mWomSV.getUserTotalLocked(_account)`: [2](#0-1) 

`getUserTotalLocked` is defined in `mWomSV.sol` as the amount staked in MasterMagpie minus the amount currently in cooldown: [3](#0-2) 

`startUnlock` is a permissionless, no-cost, instantaneous call that moves an arbitrary chosen amount from "locked" into a cooldown slot, decrementing `getUserTotalLocked` immediately — it does **not** withdraw tokens from MasterMagpie or apply any penalty; only the later `unlock()` call (after the cooldown period) actually removes tokens via `_unlock`/`withdrawMWomSVFor`: [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker calls `incentiveDeposit(A, ratio, false, 2)` — this locks mWom into `mWomSV`, `getUserTotalLocked` becomes `L0`, and the attacker is rewarded MGP for the full tiered bracket up to `L0` (reward = `f(L0) - calDoubledCounted(0) = f(L0)`).
2. Attacker immediately calls `mWomSV.startUnlock(D)` for some `D < L0`, dropping `getUserTotalLocked` to `L0 - D` (tokens are still fully backing the attacker's position — nothing was withdrawn or penalized).
3. Attacker calls `incentiveDeposit(B, ratio, false, 2)` again. Now:
   - `accumulated = B + (L0 - D)`
   - `calDoubledCounted = f(L0 - D)`
   - `reward = f(B + L0 - D) - f(L0 - D)`

Because the baseline used to subtract "already rewarded" amount is `L0 - D` instead of the true previously-rewarded `L0`, the reward function re-pays the bracket spanned by `D` a second time (it was already paid for in step 1's `f(L0)`). The contract even has a leftover state variable `bracketRewarded` explicitly commented `// not in use` [6](#0-5) , confirming the intended design was a monotonic, persisted ledger of rewarded brackets that was replaced by this live-balance recomputation — exactly the flaw described.

No modifier (`nonReentrant`, `whenNotPaused`) prevents this because it is not a reentrancy attack; it is two entirely separate, legitimate top-level transactions (`incentiveDeposit`, then `mWomSV.startUnlock`, then `incentiveDeposit` again) executed by an ordinary, unprivileged user.

### Impact Explanation
The attacker mints excess MGP that gets locked via `vlMGP.lockFor(rewardToSend, msg.sender)` for amounts they were not entitled to, draining the finite MGP reward pool held by `ArbWomUp3` (checked only against `IERC20(mgp).balanceOf(address(this))`, which just caps a single call, not the cumulative over-reward). This is a direct theft of protocol-held reward funds, matching "Critical - Direct theft of user funds" (in effect, direct theft of protocol/reward funds paid to the attacker).

### Likelihood Explanation
This requires no privileged role, no capital beyond funds the attacker already deposits, and no waiting period (the profitable manipulation is calling `startUnlock`, not `unlock`, which is instantaneous and cost-free). It is fully repeatable: attacker can repeat lock → startUnlock → deposit cycles, each time re-claiming a previously rewarded bracket, subject only to depleting the MGP balance held by the contract.

### Recommendation
Replace the live-balance-derived "already rewarded" computation with a monotonically increasing per-account ledger (e.g., actually use the existing `bracketRewarded` mapping) that records the highest tiered-reward amount ever paid to `_account`, and only pay the incremental difference between the new cumulative deposit total and that stored high-water mark — never derive it by re-reading `mWomSV.getUserTotalLocked`, which the user can lower via `startUnlock` without penalty.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie` mocks/forked instances with a tier table (e.g., tier0: [0, 1000] multiplier 100%, tier1: [1000, 5000] multiplier 50%).
2. Fund `ArbWomUp3` with MGP.
3. Attacker calls `incentiveDeposit(1000e18, ratio, false, 2)`. Record MGP locked for attacker (`reward1`), and confirm `mWomSV.getUserTotalLocked(attacker) == L0` (~500e18 after 50/50 split logic in `_deposit`).
4. Attacker calls `mWomSV.startUnlock(L0 * 9 / 10)` directly, confirm `getUserTotalLocked(attacker)` drops sharply while `balanceOf(attacker)` (locked + cooldown) is unchanged.
5. Attacker calls `incentiveDeposit(1000e18, ratio, false, 2)` again. Record MGP locked for attacker (`reward2`).
6. Assert `reward1 + reward2` exceeds `f(total real accumulated deposits)` computed independently from the tier table — i.e., exceeds what a single deposit of the same cumulative size would have paid, proving double-counted reward, and assert the MGP balance of `ArbWomUp3` decreased by more than the legitimate single-shot entitlement.

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
