Audit Report

## Title
Unprivileged `DepositDelegatorRewards` griefing permanently blocks vote-account withdrawal/closure - (File: `programs/vote/src/vote_state/mod.rs`)

## Summary
`deposit_delegator_rewards` allows any signing account (the "source" of a lamport transfer) to unconditionally increase a V4 vote account's `pending_delegator_rewards` counter, with no check that the depositor is related to the vote account's authorities [1](#0-0) . Because `withdraw` blocks full account closure whenever `pending_delegator_rewards > 0` and inflates the minimum retained balance for partial withdrawals by that same value, an attacker can keep the counter above zero indefinitely by re-depositing trivial amounts, permanently denying the account's legitimate `authorized_withdrawer` the ability to close or fully withdraw funds [2](#0-1) .

## Finding Description
`deposit_delegator_rewards` only requires `verify_authorized_signer(&source_address, signers)` on the sender — there is no check binding `source_address` to the target vote account's authorized voter/withdrawer [3](#0-2) . It then performs a CPI transfer from that arbitrary signer to the vote account and unconditionally calls `add_pending_delegator_rewards(deposit)` [4](#0-3) , which simply adds the deposit with a checked_add and no cap, cooldown, or caller-identity restriction [5](#0-4) .

`withdraw` reads this same field via `vote_state.pending_delegator_rewards()` and uses it to gate both full closure (`InstructionError::InsufficientFunds` if `pending_delegator_rewards > 0` when `remaining_balance == 0`) and the minimum retained balance for partial withdrawals (`min_rent_exempt_balance + pending_delegator_rewards`) [2](#0-1) . No other code path in `vote_processor.rs` or `handler.rs` decrements `pending_delegator_rewards`; it is only reduced by the epoch-boundary reward distribution in `calculate_block_reward` (runtime side), which the attacker can outpace by re-depositing.

The instruction is reachable only when `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` (SIMD-0291/0232/0123-dependent features) are all active, as gated in the processor's dispatch [6](#0-5) ; when active, no further account-relationship checks apply.

## Impact Explanation
This is a fund-lock/denial-of-access griefing vector: any funded, unprivileged account can prevent a targeted V4 vote account's rightful `authorized_withdrawer` from closing the account or withdrawing below `pending_delegator_rewards + rent_exempt_minimum`, corrupting the effective withdrawable-lamports state of the vote account against the owner's will. No malicious validator, leaked key, or trusted role is required — only an ordinary signer capable of submitting a `DepositDelegatorRewards` transaction with a minimal `deposit` value.

## Likelihood Explanation
Attack cost is a single lamport transfer per repetition, replayable indefinitely with no rate limit or authorization check in `deposit_delegator_rewards`, so the attacker can maintain `pending_delegator_rewards > 0` faster/cheaper than any single epoch-boundary drain can offset it. The only precondition is that the three named features are active network-wide, which is a network configuration state rather than an attacker capability requirement, and doesn't change the underlying design flaw in the code.

## Recommendation
Tie increases of `pending_delegator_rewards` exclusively to the runtime's own reward-distribution logic rather than an externally callable, unauthenticated instruction, or decouple the `withdraw` gating check from an attacker-controllable counter — e.g., snapshot the amount owed at the last distribution and only block withdrawal up to that fixed value instead of the live, externally-inflatable `pending_delegator_rewards`.

## Proof of Concept
1. Enable features `commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing` and create a V4 vote account `V` with authorized withdrawer `W`.
2. From an unrelated funded keypair `A`, submit `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` targeting `V`, signed only by `A` — see `programs/vote/src/vote_state/mod.rs:936-951` for the lack of authority binding.
3. Confirm `V`'s `pending_delegator_rewards` is now `>= 1` via `add_pending_delegator_rewards` at `programs/vote/src/vote_state/handler.rs:196-209`.
4. `W` submits `Withdraw` to fully close `V` (amount == full balance); observe `InstructionError::InsufficientFunds` from `programs/vote/src/vote_state/mod.rs:1087-1092`.
5. Repeat step 2 periodically (or before each withdrawal attempt) to keep `pending_delegator_rewards > 0` and demonstrate `V` can never be closed by `W`.
