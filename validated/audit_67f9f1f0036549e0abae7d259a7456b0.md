### Title
`associateAddresses` only checks the Sei-address side of the EVM↔Sei mapping, allowing an already-associated EVM address to be re-pointed and creating an inconsistent bidirectional mapping - ([File: precompiles/addr/addr.go])

### Summary
The `associate`/`associatePublicKey` precompile methods (and the equivalent EVM ante-handler auto-association path) validate only that the **Sei address** side of an EVM↔Sei association is unused before writing a new mapping. They never check whether the **EVM address** side is already bound to a different Sei address. Since `SetAddressMapping` unconditionally overwrites the `EVMAddressToSeiAddressKey` entry without touching the stale `SeiAddressToEVMAddressKey` entry for the previous owner, the store can end up with two different Sei addresses that both believe they "own" the same EVM address — one via a fresh (correct) forward mapping and one via a stale reverse mapping. This is structurally the same bug class as the reported `ProtectionPool.movePoolPhase()` issue: a two-sided invariant ("neither side may already be bound") is enforced by checking only one side, letting the system transition into a state (a duplicated/inconsistent association) that the design assumes cannot occur.

### Finding Description
`associateAddresses` in `precompiles/addr/addr.go`: [1](#0-0) 
only calls `p.evmKeeper.GetEVMAddress(ctx, seiAddr)` to check the `seiAddr → evmAddr` direction. It never calls `GetSeiAddress(ctx, evmAddr)` to check whether `evmAddr` is already bound to a *different* `seiAddr`.

The write path, `AssociationHelper.AssociateAddresses` → `Keeper.SetAddressMapping`, unconditionally overwrites both KV entries for the *new* pair without invalidating the old reverse entry for the *previous* owner of `evmAddr`: [2](#0-1) 

Concretely, if `evmAddr` was already mapped as `seiAddr1 ↔ evmAddr`, and an account controlling `seiAddr2` (unassociated) later proves ownership of the same EVM private key for `evmAddr` (via `associate`'s ECDSA-signature-over-custom-message flow, or via `associatePublicKey`), the check in `associateAddresses` only looks at `seiAddr2` (not yet associated → passes) and never notices `evmAddr` is already claimed by `seiAddr1`. `SetAddressMapping` then sets:
- `EVMAddressToSeiAddressKey(evmAddr) = seiAddr2` (new, "correct")
- `SeiAddressToEVMAddressKey(seiAddr2) = evmAddr` (new)

but leaves the pre-existing `SeiAddressToEVMAddressKey(seiAddr1) = evmAddr` entry untouched, because `DeleteAddressMapping` is never invoked for `seiAddr1`'s stale entry.

The identical asymmetric check exists in the ante-handler auto-association path used for ordinary EVM transactions: [3](#0-2) 
which only guards `isAssociateTx && isAssociated` (the seiAddr side) before calling `associateHelper.AssociateAddresses`, with no corresponding check on the EVM-address side.

The result is a bidirectional mapping the rest of the EVM/bank bridge code assumes is unique and consistent: `GetEVMAddress(seiAddr1)` still returns `evmAddr`, while `GetSeiAddress(evmAddr)` now returns `seiAddr2`. Both `x/evm/keeper/balance.go`'s `GetBalance` and the `usei`/`wei` StateDB bridge (`x/evm/state/balance.go`) resolve `sdk.AccAddress` from `evmAddr` via `GetSeiAddressOrDefault`, so any EVM-side balance operations on `evmAddr` are now routed to `seiAddr2`, while any code path that looks up `seiAddr1`'s EVM address (e.g. `getEvmAddr` precompile call, `GetEVMAddressOrDefault` used in event emission/tracing/precompile calls) still reports `evmAddr` as belonging to `seiAddr1`. `CanAddressReceive`'s invariant, which explicitly depends on the association being one-to-one, is likewise violated: [4](#0-3) 

### Impact Explanation
This breaks the assumed bijective invariant between Sei and EVM addresses that the `usei`/`wei` StateDB bridge, balance queries, and downstream tooling rely on. Concretely:
- Balance/lookup APIs and precompile methods (`getEvmAddr`, `getSeiAddr`) return inconsistent, stale information about which Sei address owns which EVM address, creating address-confusion that can misdirect balance displays/queries and any external system (wallets, bridges, exchanges) that trusts the forward mapping for `seiAddr1` while EVM execution actually credits/debits `seiAddr2`.
- Because `MigrateBalance` is re-triggered on the second association, it can move any residual funds sitting under `sdk.AccAddress(evmAddr[:])` (the direct-cast account) to `seiAddr2` instead of `seiAddr1`, even though `seiAddr1` still displays itself as "associated" with `evmAddr`.
- This qualifies as unauthorized fund-routing/address-confusion within the Sei<->EVM address association and bridge component explicitly listed as in-scope.

### Likelihood Explanation
Reachable by any two unprivileged Cosmos/EVM transactions from an attacker who controls (or can obtain a valid custom-message signature for) an EVM private key already associated with another Sei address — e.g., an attacker's own second account, or any EVM key that a victim has associated but whose private key material has also been reused/shared. No special privilege is required: `associate`/`associatePublicKey` are public precompile methods, and the EIP-7702/normal-tx auto-association path in the ante handler applies to every ordinary transaction sender.

### Recommendation
In `associateAddresses` (`precompiles/addr/addr.go`) and in the ante-handler association path (`x/evm/ante/preprocess.go`), check both directions before writing a new mapping: reject if `p.evmKeeper.GetSeiAddress(ctx, evmAddr)` already returns a *different* Sei address (not just check the seiAddr side), mirroring the recommended fix pattern of validating both bounds of a two-sided condition rather than only one. Alternatively, have `SetAddressMapping`/`AssociateAddresses` explicitly delete any pre-existing reverse mapping for the old owner (`DeleteAddressMapping(ctx, oldSeiAddr, evmAddr)`) before establishing the new pair, so the store can never hold two Sei addresses simultaneously claiming the same EVM address.

### Proof of Concept
1. Account A (`seiAddr1`) calls the `associate` precompile with a signature proving control of EVM key `K`, deriving `evmAddr`. `associateAddresses` finds `seiAddr1` unassociated, so it stores `seiAddr1 ↔ evmAddr`.
2. Account B (`seiAddr2`, unassociated) later submits a signature over a custom message using the *same* EVM private key `K` (attacker controls both `seiAddr1` and `seiAddr2`, or otherwise obtains a valid signature under `K`). `associateAddresses` only checks `GetEVMAddress(ctx, seiAddr2)` → not found → passes, and calls `SetAddressMapping(ctx, seiAddr2, evmAddr)`.
3. After step 2: `GetSeiAddress(evmAddr) == seiAddr2` but `GetEVMAddress(seiAddr1) == evmAddr` (unchanged, stale). The association is no longer one-to-one, and any code depending on that invariant (balance bridge, `CanAddressReceive`, precompile lookups) now behaves inconsistently for `seiAddr1` versus `evmAddr`.

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}

	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
