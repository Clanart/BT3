### Title
Copilot conflict-resolution hunk boundaries can desync between context-extraction and reassembly, letting an attacker-controlled merge/rebase branch silently corrupt the committed file - (File: app/src/lib/copilot-conflict-context.ts, app/src/lib/copilot-conflict-resolution.ts)

### Summary
The Copilot merge-conflict feature parses conflict markers twice with two independently-implemented, non-identical algorithms: once in `extractConflictHunks` (used to build the AI prompt and validate the AI's response), and once in `reassembleResolvedFile` (used to splice the AI's per-hunk answers back into the on-disk file that is then `git add`ed and committed/pushed). Only the *count* of hunks is validated between the two representations (`validateResolutionPaths`), not their identity or position. If a conflicting file — whose "theirs" side content is attacker-controlled (e.g. a malicious fork/PR branch the victim merges or rebases onto) — is crafted so the two marker-parsers agree on hunk count but disagree on hunk boundaries/ordering, the model's per-hunk resolution for one conflict block gets spliced into a different block of the file. This is written to disk and staged with no further check, silently corrupting what the user commits and pushes.

### Finding Description
`extractConflictHunks` in [1](#0-0)  walks the raw file distinguishing an explicit diff3 base section: after the `<<<<<<<` marker it scans for either a `|||||||` base marker or a `=======` separator, and if a base marker is found it then scans specifically for the *next* separator to close the base section before collecting "theirs" content up to `>>>>>>>`.

`reassembleResolvedFile`, however, uses a much simpler lookahead that has no concept of the base marker at all — it just records whether *any* `=======`-shaped line was seen and whether a `>>>>>>>`-shaped line follows it, before treating the whole span as one hunk: [2](#0-1) 

These two independent parsers are not guaranteed to agree on where each hunk starts/ends or how many well-formed hunks exist for the same input when the conflicting content itself contains marker-like lines (e.g. a divider `=======` embedded inside base/"theirs" text, or malformed/adjacent marker sequences). The only cross-check performed before trusting the AI's response is a *count* comparison: [3](#0-2) 

This mirrors the root cause of the audited smart-contract bug: the code reads/derives a size or position from one entity (`extractConflictHunks`'s boundary detection) but a *different* entity is later mutated using that same index (`reassembleResolvedFile`'s own, independently-detected boundaries) — an implicit invariant ("both functions identify the same N hunks in the same order") that is never actually verified, only the total count is.

The result is fed straight into the write path: `_applyCopilotConflictResolutions` writes `resolution.resolvedContent` to disk and runs `git add` with no diff/preview validation against the original hunk-by-hunk mapping: [4](#0-3) 

### Impact Explanation
If hunk boundaries desync while the count stays equal, the reassembled file silently contains the wrong resolution spliced into the wrong conflict location — e.g. code intended to resolve hunk #2 lands in hunk #1's position, or base/"theirs" fragments bleed into content that ends up staged. Since the app only diffs this against the working-tree file (which still has markers) for the *preview*, and the final commit path never re-validates hunk-by-hunk correctness, a maintainer can end up committing and pushing code they never actually reviewed/approved (mis-merged logic, reintroduced attacker-controlled code, or dropped fixes) without any warning dialog.

### Likelihood Explanation
This requires no local access, malware, or leaked credentials — it only requires the victim to merge, rebase, or cherry-pick a branch/PR whose content includes crafted conflict-adjacent text (e.g. a documentation divider, a string literal, or template content containing 7-character marker-like sequences) and then to accept Copilot's suggested resolution via "Continue Merge." This is a realistic contributor-controlled input path (attacker supplies the "theirs" branch content in a normal PR/merge workflow), making the trigger condition plausible without unnatural steps, though crafting content that reliably desynchronizes the two specific parsers requires some precision.

### Recommendation
Replace the two independent marker-walking implementations with a single shared parser that produces one canonical hunk-boundary representation, used both to build the AI context and to splice resolutions back in (e.g., have `reassembleResolvedFile` consume the same `IConflictHunk` boundaries produced by `extractConflictHunks`, rather than re-deriving them). At minimum, `validateResolutionPaths` should verify structural identity (e.g. hash/marker-position fingerprint) of each hunk between context-build time and reassembly time, not just the count, and abort with a validation error on mismatch instead of silently writing the file.

### Proof of Concept
1. Set up a merge/rebase where the incoming ("theirs") side of a conflicting file contains a base-only three-way conflict block whose base or theirs content itself contains a line consisting of exactly `=======` (e.g. a markdown horizontal rule) between the true `|||||||` and the true closing `>>>>>>>` marker.
2. Trigger "Resolve with Copilot." `buildConflictContext` → `extractConflictHunks` parses this as hunk N with `hasBase` handling that treats the *first* `=======` after the base marker as the base/theirs boundary, per [5](#0-4) .
3. The model returns a resolution for hunk N based on that (possibly already-skewed) content.
4. On "Continue Merge," `reassembleResolvedFile` independently re-scans the same raw file and locates its own `hasSeparator`/`closingIndex` pair via [6](#0-5) , which can select different marker lines than the ones `extractConflictHunks` used, especially once more than one hunk with such embedded marker-like content exists in the file (increasing the chance that hunk ordering/boundaries diverge while `hunks.length` still matches).
5. The mismatched resolved content is written via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staged with `git add`, per [7](#0-6) , with no further check that the spliced content matches what was actually reviewed/intended for that location.

  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>

  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )

      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
