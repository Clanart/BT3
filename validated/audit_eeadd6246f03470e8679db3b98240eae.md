## Analog Found: Git Argument Injection via Attacker-Controlled Branch Name in Deep-Link Checkout Flow

### Title
Argument Injection via Unescaped Branch Name in `git checkout` Reached from `x-github-client://openRepo` Deep Link - (File: `app/src/lib/git/checkout.ts`)

### Summary
The reported Solidity bug is fundamentally an "attacker-controlled external input reaches a sensitive state-mutating operation without proper boundary/ordering guards" bug (reentrancy is just the specific delivery mechanism). The closest structural analog in GitHub Desktop is the branch-name handling in the "Open in Desktop" deep-link flow: a `branch` value that originates from an attacker-controlled URL/remote is matched against a fetched remote branch and then handed to `git checkout` as a bare argv element placed **before** the `--` end-of-options marker, so a branch name beginning with `-`/`--` is parsed by git as an option rather than a ref.

### Finding Description
`parseAppURL` accepts a `branch` query parameter from `x-github-client://openRepo/...` deep links and only rejects it if it matches `testForInvalidChars`, whose regex (`app/src/lib/sanitize-ref-name.ts:5-6`) does **not** exclude leading `-`/`--` characters: [1](#0-0) 

That value flows through `dispatcher.dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch`, where it is used to look up a matching `Branch` object among **remotely fetched** branches (`state.branchesState.allBranches`) before checkout is attempted: [2](#0-1) [3](#0-2) 

Since `allBranches` is populated from `git fetch`/`git branch` output against the *attacker's own remote* (the URL the deep link points to), the attacker fully controls the set of branch names that can be matched — including a branch literally named `--force`, `-B`, `--orphan=x`, `--detach`, etc.

Once matched, the branch is checked out via `getBranchCheckoutArgs`, which places the (attacker-controlled) branch name **before** the `--` end-of-options separator in the argv array passed to git: [4](#0-3) 

Because `git()` invokes the git binary directly with an argv array (not a shell), there's no shell-injection risk, but there is no `--` guard immediately preceding the untrusted ref name either. Git's own argument parser will treat any leading-dash token as an option, not a positional pathspec/refname, precisely because the separator only appears at the *end* of the constructed args, not immediately before the untrusted name.

### Impact Explanation
This is not classic RCE (git checkout has no option that spawns arbitrary processes), but it lets an attacker who controls a git remote (a public fork) combined with a link the victim clicks, force git to interpret the "branch" as a checkout **option** instead of a ref. Depending on which flag is smuggled this can:
- Force `-B`/`--force` semantics, silently discarding or overwriting local uncommitted state during the automated checkout the deep-link flow performs without extra confirmation, corrupting what the user later commits.
- Force `--detach` / `--orphan=<name>` so the victim ends up on an unexpected/detached or attacker-named branch state without realizing it, which can propagate into their next commit/push.

This falls squarely in the valid-impact category "attacker controls...a git remote/proxy response" plus "a link...the user clicks" resulting in "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Exploitation requires: (1) the attacker hosts a repository/fork with a maliciously named branch, (2) the victim clicks a `x-github-client://openRepo/<attacker-url>?branch=--force` (or similar) link, and (3) Desktop clones/opens that repository and fetches it, which populates `allBranches` with the attacker's malicious ref. All three steps are consistent with normal "Open in Desktop" usage and do not require local access, elevated privileges, or pre-existing malware — only that the user follow a link, which is within the valid threat model. However, the practical severity is limited by the fact that `git checkout` itself doesn't expose flags leading to code execution, only state-mutating/UX-corruption flags, so likelihood of *severe* impact is moderate.

### Recommendation
- Reject ref/branch names beginning with `-` in `testForInvalidChars` (`app/src/lib/sanitize-ref-name.ts`), consistent with `git check-ref-format --allow-onelevel` semantics which already disallow this pattern in practice for sane refs.
- Ensure every git invocation that accepts a possibly-attacker-influenced ref/pathspec places a `--` immediately before the first untrusted token, not merely at the end of the constructed argv, in `app/src/lib/git/checkout.ts` (`getBranchCheckoutArgs`) and any similar call sites.
- Apply the same audit to other git wrappers (`branch.ts`, `submodule.ts`, etc.) that interpolate remote-derived names into argv arrays.

### Proof of Concept
1. Attacker creates a public fork and pushes a branch literally named `--force` (or another dash-prefixed name accepted by git's ref rules) pointing at a commit that reverts/overwrites files of interest.
2. Attacker crafts `x-github-client://openRepo/https://github.com/attacker/fork?branch=--force` and gets the victim to click it (e.g., embedded in a "Open in Desktop" button on a malicious web page).
3. Desktop opens/clones the fork, fetches it (`openBranchNameFromUrl` → `_fetch`), finds a `Branch` object whose `nameWithoutRemote === '--force'`, and calls `checkoutBranch`, which builds `['checkout', branch.name, '-b', nameWithoutRemote, '--']` — i.e. `git checkout --force -b --force --`, where the untrusted token is parsed as an option rather than a ref, altering checkout behavior contrary to the caller's expectations.

Note: I was not able to fully trace every intermediate call (`_checkoutBranch` → the exact final args array assembled in `checkout.ts`) beyond the code shown, since the connecting function body wasn't retrieved in full during this session — a Devin session with full file access would be needed to confirm the exact final argv ordering end-to-end and to verify whether any additional sanitization exists elsewhere in the checkout pipeline that wasn't surfaced by the search index.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async checkoutLocalBranch(repository: Repository, branch: string) {
    let shouldCheckoutBranch = true

    const state = this.repositoryStateManager.get(repository)
    const branches = state.branchesState.allBranches

    const { tip } = state.branchesState

    if (tip.kind === TipState.Valid) {
      shouldCheckoutBranch = tip.branch.nameWithoutRemote !== branch
    }

    const localBranch = branches.find(b => b.nameWithoutRemote === branch)

    // N.B: This looks weird, and it is. _checkoutBranch used
    // to behave this way (silently ignoring checkout) when given
    // a branch name string that does not correspond to a local branch
    // in the git store. When rewriting _checkoutBranch
    // to remove the support for string branch names the behavior
    // was moved up to this method to not alter the current behavior.
    //
    // https://youtu.be/IjmtVKOAHPM
    if (shouldCheckoutBranch && localBranch !== undefined) {
      await this.checkoutBranch(repository, localBranch)
    }
  }
