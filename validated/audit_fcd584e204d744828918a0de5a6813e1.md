### Title
Unbounded recursive decoding of nested `AccountKeyRoleBased` in account-update transactions allows stack-overflow DoS - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
CVE-2023-2789 describes a stack-overflow / DoS caused by unbounded recursion in `parser.c`'s variable-declaration parsing when handling deeply nested input. The analogous bug class — unbounded recursive decoding of attacker-controlled nested structures without a depth check — exists in Kaia's `AccountKeyRoleBased.DecodeRLP`, which recursively decodes account keys embedded inside account-update transactions submitted by any unprivileged transaction sender.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of RLP-encoded sub-keys and, for each entry, invokes `rlp.DecodeBytes` on a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` in turn resolves the key type and calls `s.Decode(serializer.key)`: [2](#0-1) 

If the decoded `keyType` is itself `AccountKeyTypeRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`, creating unbounded mutual recursion for every level of nesting present in the RLP bytes. Nothing in the decode path enforces a nesting limit — the "no nested composite key" rule is only enforced afterwards, in business-logic checks such as `CheckInstallable`/`CheckUpdatable`, and in the JSON-only helper `checkAccountKeyZeroValues` (which explicitly rejects a `roleBasedKey` containing another `roleBasedKey`, but is called only from the `EncodeAccountKey` RPC JSON path, not from the RLP decode path used for real transactions): [3](#0-2) [4](#0-3) 

Because the underlying `rlp` package itself performs no recursion-depth limiting during decoding (`decodeInterface`/`decodeListSlice`/struct decoders call back into the decoder tree with no depth counter): [5](#0-4) 

an attacker can construct a `TxTypeAccountUpdate` transaction whose `Key` field is an `AccountKeyRoleBased` value nested inside itself thousands of times. Decoding this transaction (via `TxInternalDataAccountUpdate.UnmarshalJSON`/RLP decode, reached through `eth_sendRawTransaction`, p2p transaction propagation, or block/tx-pool validation) drives the Go call stack to grow unboundedly through repeated `DecodeRLP` → `rlp.DecodeBytes` → `DecodeRLP` cycles, one stack frame per nesting level, eventually triggering a Go runtime stack-overflow fatal error. Unlike a panic, a Go stack-overflow is a fatal, unrecoverable runtime error that immediately crashes the process — `recover()` cannot catch it — so it crashes every node (validator, full node, RPC node) that attempts to decode the malicious transaction, rather than being contained to the submitting connection.

### Impact Explanation
Any unprivileged transaction sender can submit a single crafted `TxTypeAccountUpdate` transaction (as raw bytes to `eth_sendRawTransaction`/`klay_sendRawTransaction`, or via p2p tx gossip) that, once decoded by a node's tx pool or block validation logic, crashes the receiving process due to a Go stack overflow. Because propagation is automatic in a blockchain network, this can cascade to every node in the network that decodes the transaction (pool admission, block execution, or re-broadcast), producing a network-wide denial of service.

### Likelihood Explanation
The path is fully reachable from a single external transaction — no special privileges, validator status, or peer trust is required. Constructing nested `AccountKeyRoleBased` RLP bytes only requires standard RLP encoding tooling; no cryptographic material is validated before the recursive decode occurs (decode happens before signature/role checks). This makes the likelihood high, matching the "exploit disclosed publicly" character of the reference CVE.

### Recommendation
Add an explicit recursion/nesting-depth counter to `AccountKeyRoleBased.DecodeRLP` (and generally to the RLP decoding of `AccountKey`/`AccountKeySerializer`), rejecting decode as soon as a `RoleBased` key is found to contain another `RoleBased` (or any composite) key, before recursing — i.e., move the check currently done in `CheckInstallable`/`checkAccountKeyZeroValues` into the decode path itself, or pass down a depth/composite-flag through `DecodeRLP`. Consider also adding a general depth limit to the `rlp` decoder for defense in depth.

### Proof of Concept
1. Construct `AccountKeyWeightedMultiSig` or `AccountKeyPublic` as an innermost leaf key.
2. Wrap it in `AccountKeyRoleBased` (`NewAccountKeyRoleBasedWithValues`), RLP-encode via `AccountKeySerializer`.
3. Repeat step 2 thousands of times, each time wrapping the previous `AccountKeySerializer`-encoded bytes as the sole role-key inside a new `AccountKeyRoleBased`, per the pattern used (once) in [6](#0-5)  but iterated recursively many times instead of once.
4. Embed the final deeply-nested encoded key as the `Key` field of a `TxTypeAccountUpdate` transaction and RLP-encode the transaction.
5. Submit the raw transaction bytes via `eth_sendRawTransaction`/`klay_sendRawTransaction` or broadcast over p2p; decoding via `TxInternalDataAccountUpdate` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurses proportional to nesting depth, exhausting the goroutine stack and crashing the receiving node process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
