### Title
Interested-puzzle-hash store overwrites the wallet-id mapping for a shared puzzle hash, allowing incoming coin state to be attributed to the wrong wallet - (File: chia/wallet/wallet_interested_store.py)

### Summary
`WalletInterestedStore` persists at most one `wallet_id` per `puzzle_hash` via `INSERT OR REPLACE`, while `WalletStateManager.interested_coin_cache` tracks *all* interested `wallet_id`s per key in memory. When two different wallets register interest in the same puzzle hash (a legitimate scenario, e.g., a reused puzzle hash or a hinted/interest-only coin later re-attributed to a different wallet type such as `RemoteWallet`), the on-disk mapping used by `get_interested_puzzle_hash_wallet_id` / `get_wallet_identifier_for_puzzle_hash` silently keeps only the *last* registrant, discarding the earlier one. This mirrors the HashiCorp Vault bug class (CVE-2022-40186): a shared "alias name" (here, puzzle hash) is used as the lookup key for per-entity metadata (here, wallet identity), and the last writer overwrites the association intended for a different entity, causing state (coin ownership/attribution) to be delivered to the wrong "alias" (wallet).

### Finding Description
`WalletInterestedStore.add_interested_puzzle_hash` stores a single row keyed by `puzzle_hash`: [1](#0-0) 
and `get_interested_puzzle_hash_wallet_id` returns just the one stored `wallet_id`: [2](#0-1) 

In contrast, `WalletStateManager.add_interested_puzzle_hashes` explicitly acknowledges (in its own comment) that the in-memory cache keeps *all* wallet_ids for a puzzle hash, while the persistent store keeps only one: [3](#0-2) 

`get_wallet_identifier_for_puzzle_hash` falls back to the interested store's single-wallet mapping whenever the puzzle store has no direct derivation record for that puzzle hash: [4](#0-3) 

This wallet identifier feeds directly into `_add_coin_state`, which decides which wallet a newly seen coin belongs to: [5](#0-4) 

Because the `interested_puzzle_hashes` table is `PRIMARY KEY(puzzle_hash)` with `INSERT OR REPLACE`, if wallet A first registers interest in puzzle hash `P` (e.g., a DID/NFT/DL/PlotNFT/Pool wallet or a remote wallet performing `register_remote_coins`) and wallet B later registers interest in the same `P`, the persisted mapping flips entirely to wallet B. Any subsequent restart or resync that must consult the durable store (rather than the in-memory cache, which can also be lost/rebuilt) will resolve coin state for `P` to wallet B only, causing wallet A to lose visibility of that coin's state changes (spend confirmations, coin removal, subscription rehydration), while wallet B may gain owner-like attribution over money/state it does not actually control.

This is analogous to the Vault flaw where an entity with multiple mount accessors sharing an alias name had its identity metadata routed to the wrong alias because the accessor→metadata mapping was not scoped per-unique accessor, only per shared name.

### Impact Explanation
Chia's `WalletStateManager` uses `wallet_identifier` resolution to route on-chain coin state to the correct wallet's coin store and balance/transaction bookkeeping. A puzzle-hash collision in the durable `interested_puzzle_hashes` table means:
- The wallet that legitimately should track a coin (e.g., its DID/NFT/DL/PlotNFT/Pool coin, or a coin it is watching via `RemoteWallet.register_remote_coins`) can silently stop being informed of that coin's spend/creation once a second wallet later claims interest in the same puzzle hash, because after a restart the durable store — not the transient in-memory cache — is authoritative.
- Conversely the second wallet can end up being treated as the interested party for coin-state updates that were never meant for it, since `get_wallet_identifier_for_puzzle_hash` will hand back its `wallet_id` for that puzzle hash.

This can result in coin-set divergence between what an honest node's wallet believes it owns/tracks versus reality (misattributed ownership/metadata), a state confusion class explicitly in scope (coin-set divergence / unintended coin attribution) though bounded to wallet-side bookkeeping rather than a direct on-chain double-spend.

### Likelihood Explanation
Multiple, unprivileged wallet-side flows call `add_interested_puzzle_hash(es)` for puzzle hashes that are not guaranteed globally unique to one wallet: `RemoteWallet.register_remote_coins`, DID/NFT/PlotNFT/Pool wallet identify flows, and Data Layer wallet flows all add interest via this shared, non-scoped keyspace. Any user/local RPC caller that can create/register wallets (e.g., `RemoteWallet`) or reuse puzzle hashes (e.g., via `reuse_puzhash` transaction config, which is exercised in the test suite) can trigger two different wallet_ids to be registered for the same puzzle hash, triggering the overwrite. No malicious peer/farmer/node cooperation is required — a single local wallet user driving normal reuse/watch-registration flows suffices to hit the collision.

### Recommendation
Change `interested_puzzle_hashes` to a many-to-many table (composite primary key of `puzzle_hash, wallet_id`) instead of `puzzle_hash PRIMARY KEY`, and update `get_interested_puzzle_hash_wallet_id`/`get_wallet_identifier_for_puzzle_hash` to return (or properly select among) all interested wallet_ids per puzzle hash, consistent with how `interested_coin_cache` already tracks a list of wallet_ids per key. This removes the last-writer-wins overwrite and keeps durable state and in-memory cache semantics aligned.

### Proof of Concept
1. Create two wallets in the same `WalletStateManager` (e.g., a `RemoteWallet` #1 and any other wallet type, or two flows that legitimately call `add_interested_puzzle_hashes` for the same reused puzzle hash `P`).
2. Call `wallet_state_manager.add_interested_puzzle_hashes([P], [wallet_id_A])`, then later `wallet_state_manager.add_interested_puzzle_hashes([P], [wallet_id_B])`. Both are accepted; `interested_coin_cache[P]` now (transiently) holds both, but `WalletInterestedStore.add_interested_puzzle_hash` (`INSERT OR REPLACE`) leaves only `wallet_id_B` persisted, as shown directly by the unit test that only asserts a single winning `wallet_id` survives repeated registration: [6](#0-5) .
3. Restart/reload the wallet (simulating loss of the in-memory `interested_coin_cache`, e.g., process restart) so that `get_wallet_identifier_for_puzzle_hash` must resolve via the durable store: [4](#0-3) .
4. Any coin created at puzzle hash `P` will now resolve exclusively to `wallet_id_B` in `_add_coin_state`, even though `wallet_id_A` originally registered interest and should also have been notified/attributed.

        async with self.db_wrapper.reader_no_transaction() as conn:
            cursor = await conn.execute(

            )
            row = await cursor.fetchone()
        if row is None:
            return None
        return int(row[0])

        async with self.db_wrapper.writer_maybe_transaction() as conn:
            cursor = await conn.execute(
                "INSERT OR REPLACE INTO interested_puzzle_hashes VALUES (?, ?)", (puzzle_hash.hex(), wallet_id)

    async def get_wallet_identifier_for_puzzle_hash(self, puzzle_hash: bytes32) -> WalletIdentifier | None:
        wallet_identifier = await self.puzzle_store.get_wallet_identifier_for_puzzle_hash(puzzle_hash)
        if wallet_identifier is not None:
            return wallet_identifier

        interested_wallet_id = await self.interested_store.get_interested_puzzle_hash_wallet_id(puzzle_hash=puzzle_hash)
        if interested_wallet_id is not None:
            wallet_id = uint32(interested_wallet_id)
            if wallet_id not in self.wallets.keys():
                self.log.warning(f"Do not have wallet {wallet_id} for puzzle_hash {puzzle_hash}")
                return None
            return WalletIdentifier(uint32(wallet_id), self.wallets[uint32(wallet_id)].type())
        return None
```

    async def add_interested_puzzle_hashes(self, puzzle_hashes: list[bytes32], wallet_ids: list[int]) -> None:
        # TODO: It's unclear if the intended use for this is that each puzzle hash should store all
        # the elements of wallet_ids. It only stores one wallet_id per puzzle hash in the interested_store
        # but the coin_cache keeps all wallet_ids for each puzzle hash
        for puzzle_hash in puzzle_hashes:
            if puzzle_hash in self.interested_coin_cache:
                wallet_ids_to_add = list({w for w in wallet_ids if w not in self.interested_coin_cache[puzzle_hash]})
                self.interested_coin_cache[puzzle_hash].extend(wallet_ids_to_add)
            else:
                self.interested_coin_cache[puzzle_hash] = list(set(wallet_ids))
        for puzzle_hash, wallet_id in zip(puzzle_hashes, wallet_ids):
            await self.interested_store.add_interested_puzzle_hash(puzzle_hash, wallet_id)
```
