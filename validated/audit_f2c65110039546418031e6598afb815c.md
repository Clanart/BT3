## Title
Partial-Commit Line Selections Are Applied Against a Freshly Re-fetched Diff Instead of the One the User Reviewed — Silent Corruption of Selective Commits - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only *some* lines/hunks of a file ("partial commit"), GitHub Desktop records the selection as a set of absolute line indices against the diff that was rendered in the Changes view. At commit time, however, `applyPatchToIndex` does not reuse that diff — it independently re-runs `git diff` against the current working tree and blindly re-applies the old index-based selection to the *new* diff's hunks. If the two `git diff` invocations produce differently-shaped hunks (e.g. because attacker-controlled repository content such as `.gitattributes` line-ending normalization or a clean/smudge filter causes the working-tree comparison to shift between the two calls), the user's selection silently maps onto different lines than what they reviewed, corrupting the resulting commit without any warning.

### Finding Description
The UI computes a `DiffSelection` (a bitset of absolute line indices) against a diff object fetched once, when the file is selected: [1](#0-0) 

That same file explicitly documents that the diff underlying an existing selection can go stale, and that Desktop only prunes indices that fall completely out of range — it does not verify the selected lines still correspond to the same logical content: [2](#0-1) 

When the commit is actually created, `stageFiles` routes any file with a partial selection to `applyPatchToIndex`: [3](#0-2) 

`applyPatchToIndex` does **not** take the diff the renderer used — it calls `getWorkingDirectoryDiff` again from scratch, right before formatting the patch: [4](#0-3) 

`formatPatch` then walks the hunks of this brand-new diff and decides which raw diff lines to keep purely by looking up `file.selection.isSelected(absoluteIndex)` — i.e. it trusts that hunk/line index `N` in the new diff means the same thing it meant in the diff the user actually looked at: [5](#0-4) 

This is structurally the same flaw as the reported Solidity issue: a decision (the user's line selection, analogous to a completed vote) is evaluated/enforced using freshly recomputed state (a brand-new `git diff`, analogous to a freshly recomputed `quorumNumerator`) instead of the state that was in effect when the decision was made. Nothing in `applyPatchToIndex`/`formatPatch` checks that the new diff's hunk structure still matches the one the selection indices were computed against.

`getWorkingDirectoryDiff` invokes plain `git diff`, whose output is shaped by the repository's own `.gitattributes` (line-ending normalization, clean/smudge filters) — content that is fully attacker-controlled in a cloned/fetched repository. If attribute-driven normalization (or a configured filter driver) causes the working-tree comparison to differ between the moment the UI diff was fetched and the moment `applyPatchToIndex` re-fetches it (e.g. due to a filter with non-deterministic or environment-dependent output, or ordinary git normalization edge cases with mixed line endings), the hunk boundaries/line counts shift and the previously-computed absolute indices silently point at different lines.

### Impact Explanation
The direct consequence is silent corruption of what the user actually commits: lines the user explicitly excluded can be included, and lines they wanted included can be silently dropped, without any error or warning surfaced by the UI. This falls squarely under the accepted impact category "silent corruption of what the user commits or pushes." Because commits are often pushed to shared/remote branches, a corrupted partial commit can propagate secrets, unreviewed code, or unintended reverts into a shared history.

### Likelihood Explanation
Exploitation requires an attacker-controlled repository (fully in scope: "attacker controls a cloned/fetched repository") whose tracked `.gitattributes`/filter configuration can cause `git diff` to yield inconsistent hunk shaping across two independent invocations of the same working tree state. This is a narrow but real window — the existing in-code comment in `app-store.ts` (lines 3480-3486) already acknowledges the underlying diff-goes-stale problem as an unresolved concern for exactly this code path, indicating maintainers are aware the invariant is fragile even without an active attacker.

### Recommendation
Do not recompute the diff inside `applyPatchToIndex`. Instead, pass the exact `IDiff`/hunks object that the selection (`file.selection`) was computed against down into `stageFiles`/`applyPatchToIndex`, so the patch is built from the same hunk structure the user reviewed. If a fresh diff must be fetched (e.g. because the caller only has a stale reference), verify hunk-for-hunk structural equivalence (line counts, headers, content) before reusing old selection indices, and refuse to stage / prompt the user to re-review if the diff has changed.

### Proof of Concept
1. Clone an attacker-crafted repository containing a tracked file plus a `.gitattributes` rule (e.g. `text=auto`/`eol=` or a `filter=<driver>` entry) engineered so that two consecutive `git diff` invocations against the same working-tree file can yield differently shaped hunks (e.g. by having the filter driver's output vary based on timing/environment, or by exploiting Git's binary/text auto-detection near the heuristic boundary).
2. In GitHub Desktop, modify the file, open the Changes view so `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3404`) fetches diff #1, and select only specific lines/hunks for the commit.
3. Trigger the condition that makes the second `git diff` (invoked internally by `applyPatchToIndex`, `app/src/lib/git/apply.ts:60`) differ in hunk layout from diff #1 (e.g., normalization/filter behavior change).
4. Commit. `formatPatch` (`app/src/lib/patch-formatter.ts:143`) applies the old absolute-index selection to the new hunks, producing a commit whose actual included/excluded lines differ from what was shown and selected in the UI, with no warning to the user.
