### Title
`SignableTransaction` under-calculates the fee when an OP_RETURN `data` output is present - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends a caller-supplied OP_RETURN output to `tx_outs` before computing the transaction weight, but `calculate_weight_vbytes` is invoked with `payments` — the payment list only — so the extra output is never counted in the weight/vbytes used to derive `needed_fee`. The resulting transaction is larger than measured yet pays only the fee computed for the smaller transaction, so the actual fee rate is lower than the caller-requested `fee_per_vbyte`.

### Finding Description
The bug class from the external report is "a total is snapshotted once and then not updated when the set of items it must cover changes." Here the analog is the transaction's output set:

1. `data` pushes an additional `TxOut` onto `tx_outs` (networks/bitcoin/src/wallet/send.rs:194-202).
2. The weight/vbytes are then computed from `payments`, which does *not* include that OP_RETURN output (send.rs:204 and the change variant at send.rs:226).
3. `needed_fee = fee_per_vbyte * vbytes` is therefore computed for a smaller transaction than the one that will actually be signed and broadcast.

The final `Transaction` built at send.rs:245-251 includes the OP_RETURN output, so `fee()` (send.rs:138-141) equals `input_sat - sum(tx_outs)` = the stale `needed_fee`, while the real vbytes are larger. The minimum-relay check at send.rs:211 is also evaluated against the understated `vbytes`, so a transaction can pass the `TooLowFee` guard while its true fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`.

### Impact Explanation
The multisig will produce a validly signed transaction whose effective fee rate is lower than requested — potentially below the minimum relay fee, so it may never confirm and the spent `ReceivedOutput` inputs are effectively stuck until the plan is rebuilt. This is reachable by any caller supplying `data` to `SignableTransaction::new` (the machine path feeds it via `Plan`/`payments` construction in the processor). OP_RETURN adds ~9-90+ bytes, so the understatement is proportional to the data length.

### Likelihood Explanation
Any plan that attaches `data` triggers it deterministically; the fee error scales with data size and with how close `fee_per_vbyte` is to the minimum relay rate.

### Recommendation
Include the OP_RETURN output in the weight computation — e.g., pass the actual `tx_outs` (or `payments` plus the data script) into `calculate_weight_vbytes` for both the no-change and with-change calculations, and evaluate the minimum-relay check against the true vbytes.

### Proof of Concept
```rust
// Conceptual: two transactions, identical inputs/payments/fee rate,
// one with data, one without.
let inputs = vec![received_output_with_100_000_sats];
let payments = [(script_pubkey, 50_000)];

let no_data = SignableTransaction::new(inputs.clone(), &payments, None, None, 10).unwrap();
let with_data =
  SignableTransaction::new(inputs, &payments, None, Some(vec![0xAA; 80]), 10).unwrap();

// Both report the same needed_fee and actual fee...
assert_eq!(no_data.needed_fee(), with_data.needed_fee());
// ...but with_data's serialized transaction is ~90 bytes larger,
// so its true sat/vbyte rate is strictly lower than requested.
assert!(with_data.transaction().weight() > no_data.transaction().weight());
```

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
