### Title
Cached FROST nonces are committed and `sign` re-executed before the final signer set/message is fixed, enabling nonce reuse and validator key-share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
Analogous to the Telcoin delayed-withdrawal bypass (a timestamp recorded *before* the precondition — a deposit — existed, letting stale state bypass the guard), `SigningProtocol::preprocess_internal` commits and caches FROST nonces keyed only by `(b"DkgConfirmer", attempt)` *before* the signing set and message are fixed, and `share_internal` then re-runs `sign` on the same cached nonces whenever `share` or `complete` is invoked. If the preprocess set (and hence `included`, binding factors, and challenge) or the `key_pair` message differs between those invocations, the same nonce pair `(d, e)` produces two distinct signature-share equations — the exact nonce-reuse condition the code itself documents as enabling third-party recovery of the private key share.

### Finding Description
`preprocess_internal` stores an XOR-encrypted `CachedPreprocess` under `CachedPreprocesses::get(self.txn, &self.context)` where `context = (b"DkgConfirmer", self.attempt)`, and deterministically rebuilds the identical `AlgorithmSignMachine` (same nonces) on every call via `AlgorithmSignMachine::from_cache` → `seeded_preprocess`. [1](#0-0) 

`DkgConfirmer::share` and `DkgConfirmer::complete` each invoke `share_internal`, which calls `preprocess_internal` and then `machine.sign(preprocesses, msg)` — i.e., `sign` runs at least twice under the same nonces. [2](#0-1) 

Inside `sign`, the `included` set is derived from the *keys of the `preprocesses` map passed in*, and each participant's binding factor `rho` is a function of the full preprocess transcript and `msg` (`set_keys_message(...)`). [3](#0-2) [4](#0-3) 

The `share` call operates on the preprocesses known at share time, while `complete` re-executes `sign` on the preprocesses/shares finalized later. The preprocess map passed to `complete` can be a superset or otherwise different set than the one used at `share` time (preprocesses are collected from chain transactions at different points, and there is no check that the set used in `complete` equals the set used in `share`). Any difference in `included` changes `rho_i`, `R = D + sum(rho_i * E_i)`, and the challenge, yielding `s = d + e*rho + lam*share*c` for two different `rho`/`c` values under identical `d` and `e`. Solving the two-share linear system recovers the nonce `d`, `e` and then the MuSig secret key share — exactly what `spec/cryptography/FROST.md` warns: "Reusing preprocesses would enable a third-party to recover your private key share." [5](#0-4) 

The file itself flags the analogous precondition gap: "TODO: We also need to review how we're handling Processor preprocesses and likely implement the same on-chain-preprocess-matches-presumed-preprocess check before publishing shares." [6](#0-5) 

### Impact Explanation
Recovery of a validator's MuSig secret share — the root-of-trust key used for `set_keys` confirmation signatures. Two shares over the same nonces with distinct effective challenges is textbook deterministic-nonce reuse; the long-lived key share falls out algebraically. Severity: High (key compromise of a consensus validator, enabling forgery of future `DkgConfirmer` signatures once combined with threshold-compatible cooperation).

### Likelihood Explanation
Divergence requires only that the preprocess set or `key_pair` seen at `complete` differ from that at `share`. No malicious threshold is needed: an honest validator's `CosignPreprocess` transaction landing between the two calls (or a `removed` set change altering `threshold_i_map_to_keys_and_musig_i_map` remapping) changes `included`. The comment at lines 37–48 explicitly relies on "received messages" never differing between re-executions, an assumption the code does not enforce for the preprocess map — unlike `AttemptDb` gating for processor signing, nothing here verifies set equality. [7](#0-6) 

*Uncertainty:* I could not fully trace `handle.rs` call sites to confirm exactly which preprocess/shares maps are passed to `share` vs `complete`; if the finalized maps are guaranteed identical, both `sign` calls produce the same share and no leakage occurs. The finding stands on the missing equality check and the documented TODO.

### Recommendation
- Pin the signer set: record the `included` participant list (or the serialized preprocess map hash) when the share is first produced, and have `complete` verify the map it re-signs over matches exactly before calling `share_internal`; abort rather than re-sign on mismatch.
- Alternatively, key `CachedPreprocesses` by a commitment to the preprocess set and message (`context = (b"DkgConfirmer", attempt, H(preprocesses || msg))`), so a distinct set deterministically derives distinct nonces instead of reusing them.
- Implement the flagged on-chain-preprocess-matches-presumed-preprocess check before any share publication.

### Proof of Concept
1. Attempt `n` of DKG confirmation: `preprocess_internal` caches seed `s`, publishes commitments `D, E` derived from `ChaCha20Rng::from_seed(s)`. [8](#0-7) 
2. `share(preprocesses_A, key_pair)` signs with `included = A ∪ {i}` producing `s_1 = d + e·rho_1 + λ·x·c_1`.
3. One additional validator's `CosignPreprocess` is included on chain, then `complete(preprocesses_A ∪ {p}, key_pair, shares)` re-executes `share_internal` → `from_cache` restores the same `(d, e)`; `included` now contains `p`, so `rho_i` and `c` change, producing `s_2 = d + e·rho_2 + λ·x·c_2`.
4. With both shares public (`Share`/`BatchShare` transactions are published), solve the 2×2 linear system for `d`, `e`, then recover `λ·x` and hence the secret share `x`.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,

      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },

**File:** spec/cryptography/FROST.md (L45-55)
```markdown
# Caching

modular-frost supports caching a preprocess. This is done by having all
preprocesses use a seeded RNG. Accordingly, the entire preprocess can be derived
from the RNG seed, making the cache just the seed.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.
```
