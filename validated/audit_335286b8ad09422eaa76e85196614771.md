### Title
App proxy signature verification lacks timestamp freshness/expiry check, enabling indefinite replay - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#verify_proxy_request` only checks that the HMAC signature matches the query string; it never validates the `timestamp` parameter against a bounded validity window. Any previously captured valid `query_string` + `signature` pair therefore remains valid forever and can be replayed by an unprivileged attacker.

### Finding Description
`verify_proxy_request` calls `query_string_valid?(request.query_string)`, which parses the raw query string, extracts `signature`, recomputes the HMAC over the remaining sorted params (including `timestamp` if present), and compares it with `ActiveSupport::SecurityUtils.secure_compare`: [1](#0-0) 

`timestamp` is treated exactly like any other opaque query parameter folded into `calculated_signature`: [2](#0-1) 

There is no code anywhere in this concern (or the calling controller's `before_action` chain, since the only hook added is `verify_proxy_request` itself) that parses `timestamp`, compares it to `Time.now`, or rejects requests older than some threshold. A confirmed grep across the repo shows the only `timestamp`-related logic exists in unrelated areas (callback controller OAuth flow, login protection, generator templates) — none of it applies to app-proxy verification. Consequently, as long as the HMAC matches (which it always will for a previously valid signed URL, since the signature is a deterministic function of the exact same query params), the request is accepted regardless of how much time has elapsed. An attacker who observes one valid signed app-proxy URL (via browser history, shared links, logs, or a public storefront page making a proxy request) can resend that exact URL indefinitely and it will continue to authenticate as coming from Shopify for that shop.

### Impact Explanation
This is an unauthenticated replay of a forged/valid signed app-proxy request, matching Shopify's "forged app-proxy request" impact class. Because the app proxy controller trusts `verify_proxy_request` as its authentication boundary (shop identity is normally derived from the `shop` query param once the signature is accepted), an attacker replaying a captured signed URL can invoke app-proxy actions as that shop indefinitely, even long after the original request's context (and legitimate purpose) has expired.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to have observed one valid signed app-proxy `query_string` (no secret, no session, no HMAC key needed — this is a pure precondition of prior request exposure, e.g., via logs, Referer headers, browser history, or a link containing the proxy URL). The attack itself is trivially repeatable — a simple repeated GET with the identical `query_string` — with no rate limiting or freshness check to stop it.

### Recommendation
Parse the `timestamp` parameter in `query_string_valid?` (or a new check invoked from `verify_proxy_request`), convert it to an integer/time, and reject the request (`head(:forbidden)`) if it falls outside an acceptable window (e.g., a few minutes) relative to `Time.now.to_i`, in addition to the existing HMAC comparison.

### Proof of Concept
```ruby
class AppProxyVerificationTest < ActionController::TestCase
  test "accepts a previously valid signed query string indefinitely" do
    Timecop.freeze(Time.now) do
      query_hash = { "shop" => "test-shop.myshopify.com", "timestamp" => Time.now.to_i.to_s, "path_prefix" => "/apps/test" }
      signature = OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        query_hash.collect { |k, v| "#{k}=#{v}" }.sort.join,
      )
      query_string = query_hash.merge("signature" => signature).to_query
      @request.env["QUERY_STRING"] = query_string
      get :index
      assert_response :success
    end

    # Replay the exact same query_string long after the original timestamp
    Timecop.freeze(Time.now + 3600) do # 1 hour later
      @request.env["QUERY_STRING"] = query_string
      get :index
      # Expected (secure) behavior: 403 forbidden due to expired timestamp
      # Actual behavior: still 200, because timestamp is never checked for freshness
      assert_response :success
    end
  end
end
```
The controller under test only mixes in `ShopifyApp::AppProxyVerification`; no additional freshness check exists in the concern to reject the stale replay.

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
