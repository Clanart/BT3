### Title
`files[numStatCount]` desync in `parseRawLogWithNumstat` can throw / mis-attribute file status when parsing attacker-crafted commit history - (File: `app/src/lib/git/log.ts`)

### Summary
`parseRawLogWithNumstat` walks the combined `--raw --numstat -z` output of `git log`/`git diff` in a single pass, pushing entries into a `files` array from the `--raw` section while independently tracking a separate counter `numStatCount` for the `--numstat` section. The function assumes the two sections are always in lock-step (i.e., `files[numStatCount]` is always the numstat-section's matching raw entry), but this indexing relationship is never verified. If the two sections fall out of alignment while parsing output derived from a commit whose tree the attacker fully controls (a cloned/fetched malicious repository), `files[numStatCount]` can read past what has actually been pushed, yielding `undefined`, and `isCopyOrRename(files[numStatCount].status)` throws a `TypeError`.

### Finding Description
`app/src/lib/git/log.ts` lines 276-334 [1](#0-0)  builds up `files` by pushing `CommittedFileChange` entries whenever a line starts with `:` (the raw diff line), and separately increments `numStatCount` for every non-`:` line (numstat line):

```
if (line.startsWith(':')) {
  ...
  files.push(new CommittedFileChange(...))
} else {
  ...
  if (isCopyOrRename(files[numStatCount].status)) {
    i += 2
  }
  numStatCount++
}
``` [2](#0-1) 

This is invoked directly on `git log`/`git diff` output for a specific commit SHA taken from a cloned/fetched repository, e.g. `getChangedFiles` at lines 219-245 [3](#0-2) , and `getCommitRangeChangedFiles`/`getBranchMergeBaseChangedFiles` in `app/src/lib/git/diff.ts` (lines 252-335) [4](#0-3) , all of which operate on commits that originate from a remote the user cloned or fetched — content fully under an attacker's control.

The invariant the code relies on — "the Nth numstat record always corresponds to the Nth raw record already pushed into `files`" — is never checked. Unlike the FeeConversionKeeper bug, where an oversized array is allocated and left with zeroed trailing slots that are blindly iterated, here the arrays (`files`) are built incrementally but consumed by an unchecked index (`numStatCount`) computed from a parallel but separately-driven loop counter. Both are the same broken-invariant class: **trusting a length/index derived from one data stream to safely index a differently-sized structure built from another stream**, with no bounds check before dereferencing (`files[numStatCount].status`).

### Impact Explanation
If desynchronization occurs, `files[numStatCount]` returns `undefined`, and the subsequent `.status` property access throws an unhandled `TypeError`. Since this parser underlies core commit-history and diff-viewing functionality (`getChangedFiles`, `getCommitRangeChangedFiles`, `getBranchMergeBaseChangedFiles`), a crafted commit tree can reliably break history/diff rendering for any user who clones or fetches the malicious repository and opens its history in Desktop. Because there is no bounds check or recovery path, this is a straightforward denial-of-service against a core Desktop feature (viewing history/diffs) triggered purely by attacker-controlled repository content — not by local access, admin rights, or social engineering.

I was not able to fully confirm within available context whether the desync condition is reachable given git's own guarantees about the ordering/pairing of `--raw` and `--numstat` output (git normally interleaves them in matching order per file, which would make this hard to trigger through *content* differences alone). This is the main source of uncertainty in this analog: it's plausible git's own format guarantees prevent this loop from ever actually going out of sync for any legal diff, in which case this would only be a defense-in-depth gap, not an exploitable bug. I could not verify this against Desktop's actual test suite coverage for adversarial inputs (only well-formed fixtures were visible in `app/test/unit/git/log-test.ts`).

### Likelihood Explanation
Low-to-moderate confidence. The report's "trailing zero" bug class is about a *known, deterministic* size mismatch (oversized array vs. only-partially-filled array) baked directly into the code. In Desktop's case, the size relationship between the raw-derived `files` array and the numstat-derived `numStatCount` counter is intended to always match by construction of git's own `--raw --numstat` combined output format, and no direct manipulation vector (e.g., unusual filenames, embedded NULs, degenerate rename percentages) was confirmed to break this pairing during this review. Absent a concrete proof-of-concept diff/commit that reproduces the desync, this should be treated as a suspicious, unguarded assumption rather than a confirmed vulnerability.

### Recommendation
Add an explicit bounds check before indexing `files[numStatCount]` in `parseRawLogWithNumstat`, and fail closed (skip/log rather than throw an unhandled exception) if `numStatCount >= files.length` or if the corresponding entry is `undefined`. This converts an unhandled crash into a defined, recoverable error path, consistent with the report's recommendation to only process the "real count" of populated entries rather than trusting an index derived from a separate/parallel count.

### Proof of Concept
Not verified — I could not construct or confirm a concrete crafted commit/diff that forces `numStatCount` to exceed `files.length` given git's normal `--raw --numstat -z` output pairing. A background engineering investigation (fuzzing `parseRawLogWithNumstat` with malformed/edge-case `--raw`+`--numstat` combined text, e.g. mixed rename/copy detection thresholds, type-changes, or partial-content commits) would be needed to determine definitively whether this desync is reachable from real git output before treating this as more than a hardening gap.

export function parseRawLogWithNumstat(
  stdout: string,
  sha: string,
  parentCommitish: string
) {
  const files = new Array<CommittedFileChange>()
  let linesAdded = 0
  let linesDeleted = 0
  let numStatCount = 0
  const lines = stdout.split('\0')

  for (let i = 0; i < lines.length - 1; i++) {
    const line = lines[i]
    if (line.startsWith(':')) {
      const lineComponents = line.split(' ')
      const srcMode = forceUnwrap(
        'Invalid log output (srcMode)',
        lineComponents[0]?.replace(':', '')
      )
      const dstMode = forceUnwrap(
        'Invalid log output (dstMode)',
        lineComponents[1]
      )
      const status = forceUnwrap(
        'Invalid log output (status)',
        lineComponents.at(-1)
      )
      const oldPath = /^R|C/.test(status)
        ? forceUnwrap('Missing old path', lines.at(++i))
        : undefined

      const path = forceUnwrap('Missing path', lines.at(++i))

      files.push(
        new CommittedFileChange(
          path,
          mapStatus(status, oldPath, srcMode, dstMode),
          sha,
          parentCommitish
        )
      )
    } else {
      const match = /^(\d+|-)\t(\d+|-)\t/.exec(line)
      const [, added, deleted] = forceUnwrap('Invalid numstat line', match)
      linesAdded += added === '-' ? 0 : parseInt(added, 10)
      linesDeleted += deleted === '-' ? 0 : parseInt(deleted, 10)

      // If this entry denotes a rename or copy the old and new paths are on
      // two separate fields (separated by \0). Otherwise they're on the same
      // line as the added and deleted lines.
      if (isCopyOrRename(files[numStatCount].status)) {
        i += 2
      }
      numStatCount++
    }
  }

  return { files, linesAdded, linesDeleted }
}

export async function getCommitRangeChangedFiles(
  repository: Repository,
  shas: ReadonlyArray<string>,
  useNullTreeSHA: boolean = false
): Promise<IChangesetData> {
  if (shas.length === 0) {
    throw new Error('No commits to diff...')
  }

  const oldestCommitRef = useNullTreeSHA ? NullTreeSHA : `${shas[0]}^`
  const latestCommitRef = shas.at(-1) ?? '' // can't be undefined since shas.length > 0
  const baseArgs = [
    'diff',
    oldestCommitRef,
    latestCommitRef,
    '-C',
    '-M',
    '-z',
    '--raw',
    '--numstat',
    '--',
  ]

  const { stdout, gitError } = await git(
    baseArgs,
    repository.path,
    'getCommitRangeChangedFiles',
    {
      expectedErrors: new Set([GitError.BadRevision]),
    }
  )

  // This should only happen if the oldest commit does not have a parent (ex:
  // initial commit of a branch) and therefore `SHA^` is not a valid reference.
  // In which case, we will retry with the null tree sha.
  if (gitError === GitError.BadRevision && useNullTreeSHA === false) {
    const useNullTreeSHA = true
    return getCommitRangeChangedFiles(repository, shas, useNullTreeSHA)
  }

  return parseRawLogWithNumstat(stdout, latestCommitRef, oldestCommitRef)
}
