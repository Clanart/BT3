### Title
Unbounded `Rs` vector allocation in `SchnorrAggregate::read` enables remote memory-exhaustion DoS via a 4-byte length prefix - ([File: crypto/schnorr/src/aggregate.rs])

### Summary
`SchnorrAggregate::<C>::read` trusts an attacker-controlled `u32` count and then performs one `C::read_G` per declared element, pushing each decoded point into a `Vec<C::G>` with no upper bound. Analogous to CVE-2023-34969 (an unprivileged party crashing a daemon with a crafted message), any code path that feeds untrusted bytes into `SchnorrAggregate::read` (signature payloads, gossiped/batched proof material, stored data re-read on boot) can be driven into multi-gigabyte allocation or abort on OOM, crashing the host process.

### Finding Description
In `crypto/schnorr/src/aggregate.rs:77-88`, deserialization is:

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;

  #[allow(non_snake_case)]
  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }

  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
```

The `len` field is a fully attacker-controlled `u32` (up to 4,294,967,295). Two distinct DoS primitives result:

1. **Memory exhaustion:** for curves with permissive decodings (e.g., Ristretto/ed25519 compressed points where roughly half of all 32-byte strings decode), the attacker supplies `len = u32::MAX` followed by a long stream of 32-byte elements. Each successful `read_G` pushes a group element into `Rs`, growing the heap allocation proportional to bytes supplied, with no cap. A modest input (e.g., a stream that keeps producing valid encodings) can force an allocation far exceeding available memory — the process aborts on allocation failure.

2. **CPU burn even on failure:** even if the stream eventually produces an invalid encoding, the victim performs up to `len` point decompression operations (decompression + validity checks per element) purely under attacker control, before the error is returned. Per-byte work is high (full point decompression per 32 bytes), making this an amplification DoS.

Notably, `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`) rejects identity but does nothing to bound count, and no caller-side length contract exists in the library. Other `read` functions in scope use fixed-size or `u16`-bounded fields (e.g., `SecretShare::read`, `ThresholdKeys::read` reading `n` items where `n` is a `u16` — itself a ~2 MB worst case), but `SchnorrAggregate::read` uses a `u32`, making it the outlier.

### Impact Explanation
Any Serai component (or integrator) that calls `SchnorrAggregate::read` on bytes an unprivileged peer can supply — aggregate-signature messages, DLEq/batch verification artifacts, or bytes replayed from storage — can be crashed by an unauthenticated party. This matches the CVE's denial-of-service class: a low-privilege network attacker kills the daemon. Since `std::io::Read` streams until error, the attacker can sustain the byte stream to keep the allocation loop growing. Denial of service of a threshold-signing validator halts signing/withdrawal availability for the whole set.

### Likelihood Explanation
The trigger requires only control over the input byte stream to `read` — a `u32::MAX` prefix plus a sustained stream of bytes that decode as valid points. No key material, collusion, or protocol position is needed. The only mitigating factor is whether the specific deployment exposes `SchnorrAggregate::read` to unauthenticated input before authentication; the API itself is `pub` and documented for external use, so integrators are reasonably expected to call it on peer-supplied bytes.

### Recommendation
- Impose a sane upper bound on `len` inside `SchnorrAggregate::read` (e.g., a `u16`, or an explicit `max` parameter matching the number of signatures actually aggregated, consistent with `write` which documents `u32` only for completeness).
- Alternatively, read lazily / cap total bytes consumed (e.g., wrap the reader in `reader.take(max_bytes)`) so declared length cannot exceed supplied bytes for buffered inputs.
- Audit sibling deserializers for the same pattern (`EncryptedMessage::read`, `ThresholdKeys::read`'s `n`-sized `Vec::with_capacity`, `SignData`/`Output` readers in calling crates) and enforce bounded counts everywhere attacker-controlled lengths are honored.

### Proof of Concept
```rust
use std::io::Cursor;
use schnorr::SchnorrAggregate;
use dalek_ff_group::Ristretto;
use ciphersuite::group::GroupEncoding;

fn main() {
  // Attacker-controlled buffer: u32::MAX element count followed by a stream of
  // canonically valid compressed Ristretto points (e.g., the generator encoding
  // repeated indefinitely — the attacker streams from a socket).
  let mut data = u32::MAX.to_le_bytes().to_vec();
  let gen = <Ristretto as ciphersuite::Ciphersuite>::generator().to_bytes();
  // A realistic attacker streams these; even a bounded test buffer shows each
  // 32 bytes consumed produces one heap-allocated point in `Rs`.
  for _ in 0 .. 1_000_000 {
    data.extend_from_slice(gen.as_ref());
  }

  // Each iteration allocates and stores a point. With a u32::MAX prefix and a
  // persistent stream, the Vec grows to ~137+ GB of group elements -> OOM abort.
  // Even on error, up to ~4.3 billion decompressions are performed.
  let _ = SchnorrAggregate::<Ristretto>::read(&mut Cursor::new(&data));
}
```
