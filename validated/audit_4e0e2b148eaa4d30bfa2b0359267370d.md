### Title
Value sent to the distribution precompile's `rewards()` view method is permanently stranded with no recovery mechanism - (File: precompiles/distribution/distribution.go)

### Summary
The distribution precompile at `0x0000000000000000000000000000000000001007` exposes a `rewards(address)` view method that, unlike every other query/view method on the same precompile, never validates that the call is non-payable. An EVM caller can invoke `rewards()` with a non-zero `msg.value`, and that value is accepted and never refunded to the caller, unlike the mutating (`IsTransaction`) methods, which correctly refund payment via `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei`.

### Finding Description
`Execute` dispatches `RewardsMethod` directly to `p.rewards(ctx, method, args)` without a `pcommon.ValidateNonPayable(value)` check, and unlike `withdrawValidatorCommission` (guarded at line 177) or the other query methods that route through `p.validateInput(value, args, n)` (which internally calls `ValidateNonPayable`, e.g., `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`, `params`), `rewards()` only checks argument length: [1](#0-0) [2](#0-1) 

Compare with the sibling view `validatorOutstandingRewards`, which correctly rejects payment via `p.validateInput`: [3](#0-2) 

This gap is explicitly called out in the repo's own integration test comment, which documents that a value-bearing call to `rewards()` will succeed and strand funds: [4](#0-3) 

The mutating methods on this same precompile (e.g. `setWithdrawAddress`, `withdrawDelegationRewards`) explicitly refund any `value` sent along by the caller through `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` (seen consistently across `precompiles/common/*/precompiles.go`), because the underlying dynamic-gas precompile dispatch mechanism transfers the `usei`/`wei` portion of `msg.value` into the precompile's associated Sei account before `Execute` runs, and it is each executor's responsibility to refund it back to the payer: [5](#0-4) 

Because `rewards()` performs no such refund and no such rejection, any `usei`/`wei` value attached to a `rewards()` call is transferred into the precompile's account and never returned - it is not tracked by any withdrawal path and there is no rescue/refund mechanism analogous to the missing `ethRescue` function described in the reference report.

### Impact Explanation
Any EVM caller who mistakenly (or via a wallet/dApp bug) attaches non-zero `value` to a `rewards(address)` call against the distribution precompile permanently loses those funds. There is no way to recover them: the precompile executor has no refund logic for this method, and there is no owner/admin rescue function reachable by a normal transaction. This is a direct, unrecoverable loss of user funds triggered purely by a single externally-submitted EVM transaction, which is a concrete permanent-fund-loss condition.

### Likelihood Explanation
Likelihood is non-trivial: `rewards()` is a commonly called read-style method (fetching delegation rewards), and nothing in the ABI or contract semantics signals to callers/tooling that it must be called with `value = 0`. Any integrator, script, or wallet that (incorrectly) attaches value to what looks like a "view" call, or that reuses a payment-attaching call pattern (e.g., copy-pasting from `withdrawDelegationRewards`), will trigger permanent loss. The precompile-tests file explicitly flags this as a known quirk ("no 'view rejects value' test" since it would actually succeed and strand funds), confirming the maintainers are aware but have not implemented a fix.

### Recommendation
Add the same non-payable guard used by all other view methods on this precompile. Either:
1. Call `pcommon.ValidateNonPayable(value)` at the top of `rewards()` in `precompiles/distribution/distribution.go` (mirroring `p.validateInput`'s behavior used by `validatorOutstandingRewards`, `validatorCommission`, etc.), rejecting the call if `value != 0`; or
2. If `rewards()` must remain payable for backward compatibility, explicitly refund any attached `usei`/`wei` back to `caller` via `pcommon.HandlePaymentUseiWei` before returning, consistent with the mutating methods on the same precompile.

### Proof of Concept
1. Caller associates their EVM address with a Sei address and delegates to a validator so that `DelegationTotalRewards` returns a non-error response.
2. Caller calls the distribution precompile at `0x0000000000000000000000000000000000001007`, method `rewards(address)`, passing their own address, but attaches `msg.value = X wei/usei` to the call (e.g., via `ethers.Contract.rewards(addr, { value: X })`).
3. The call succeeds (per `Execute`/`rewards` in `precompiles/distribution/distribution.go:204-205,543-579`, which never checks `value`), the EVM debits `X` from the caller's account and credits it to the precompile's associated account, and the ABI-encoded reward data is returned normally.
4. No refund event or subsequent path ever returns `X` to the caller — the funds are permanently stuck in the precompile's account, with no owner/admin rescue function available to recover them (unlike a normal contract that could implement an `ethRescue`-style function, this precompile's account is not spendable by any externally reachable native-transaction path).

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}

func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return coin, nil
}

func HandlePaymentUseiWei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Int, sdk.Int, error) {
