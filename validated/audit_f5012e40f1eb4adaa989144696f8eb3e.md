Audit Report

## Title
Custom commission collector address is not epoch-delayed, letting the withdraw authority redirect already-earned inflation-reward commissions to a new collector - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

## Summary
Agave's vote program allows the authorized withdrawer to redesignate the inflation-rewards commission collector pubkey via `update_commission_collector` at any time with only a signer check, while the reward-calculation code fetches the commission *rate* from a delayed snapshot but reads the commission *collector pubkey* from the live vote-account state at distribution time. This asymmetry lets a withdraw authority front-run the partitioned reward distribution for an already-completed epoch and divert that epoch's inflation-reward commission lamports to a new address they control.

## Finding Description
`update_commission_collector` in `programs/vote/src/vote_state/mod.rs` (lines 907-933) performs only `verify_authorized_signer` before overwriting `inflation_rewards_collector`/`block_revenue_collector` — there is no slot/epoch-based timing restriction analogous to `is_commission_update_allowed`. By contrast, `update_commission_bps` (lines 828-859) explicitly documents "No commission update rule, per SIMD-0249 and SIMD-0291," relying entirely on the reward-calculation code to neutralize late rate changes by reading from a delayed snapshot.

In `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`, the reward calculation function reads `vote_state` from `distribution_epoch_vote_accounts` (line 651/701), the current/live view at distribution time. When `delay_commission_updates` is enabled, `commission_bps` is instead resolved from `vote_state_for_commission`, sourced from `snapshot_epoch_vote_accounts` or `rewarded_epoch_vote_accounts` — i.e., an earlier, "delayed" snapshot (lines 709-724). However, `commission_pubkey` is unconditionally derived from the live `vote_state.inflation_rewards_collector()` (lines 750-757), with no equivalent snapshot fallback. This means the collector-delay protection that exists for the rate does not exist for the recipient address, even though both are "who gets paid for epoch N" fields that should be resolved consistently.

## Impact Explanation
An authorized withdrawer can call `UpdateCommissionCollector` after an epoch's stake/vote credits are fixed but before the bank executes `calculate_stake_rewards_and_commissions`/`redeem_delegation_rewards` for that epoch, redirecting that epoch's entire inflation-reward commission payout — which is computed and distributed later against the live `inflation_rewards_collector` value — to an address that was not the designated collector during the epoch the rewards were earned in. This constitutes fund misdirection of validator commission lamports, matching the "fund theft/loss" impact category, with the exact corrupted value being the `commission_pubkey` field used in `InflationRewardWithCommission` and ultimately in `store_commission_accounts_partitioned`/`distribute_reward_commissions`.

## Likelihood Explanation
The attack requires only an authorized withdrawer (an "unprivileged w.r.t. other stakeholders" actor, e.g. relative to delegators or stake-pool participants relying on the custom-collector arrangement) to submit a single `UpdateCommissionCollector` transaction within the window between epoch-N credit accrual finishing and the bank running reward calculation/distribution for epoch N — a window that reliably exists because partitioned rewards are computed and distributed across blocks early in epoch N+1. Since the rate-delay mechanism demonstrates that this exact "front-run distribution" attack class was anticipated and defended against for `commission_bps`, but the parallel protection was omitted for `inflation_rewards_collector`, this is a genuine, currently-reachable code path rather than a theoretical gap.

## Recommendation
Apply the same delayed-snapshot resolution used for `commission_bps` to the commission collector: when `delay_commission_updates` (or the SIMD-0232 custom-collector equivalent) is active, resolve `commission_pubkey` from `vote_state_for_commission` (the same delayed view already computed at lines 710-714) rather than from the live `vote_state`, in the block at lines 750-757 of `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`.

## Proof of Concept
1. Vote account `V` has `authorized_withdrawer = W` and `inflation_rewards_collector = A` during epoch `N`; delegated stake earns inflation rewards throughout epoch `N` with `A` as the entitled collector.
2. Before the bank runs reward calculation for epoch `N` (early in epoch `N+1`), `W` submits `VoteInstruction::UpdateCommissionCollector { new_collector: B, kind: InflationRewards }`, processed by `update_commission_collector` (`programs/vote/src/vote_state/mod.rs:907-933`), which succeeds immediately since there is no timing check.
3. When `calculate_stake_vote_rewards_and_credits_from_delegation` executes for rewarded epoch `N`, `commission_bps` correctly reflects the delayed/historical rate, but `commission_pubkey` at lines 750-757 reads `vote_state.inflation_rewards_collector()` from the live (post-update) state, yielding `B`.
4. All of epoch `N`'s commission lamports are paid to `B` via `store_commission_accounts_partitioned`/`distribute_reward_commissions` instead of `A`. This can be reproduced as an integration test analogous to `test_calculate_stake_vote_rewards`, inserting an `UpdateCommissionCollector` transaction between credit accrual and the bank's reward-calculation call, then asserting the resulting `commission_pubkey`/`reward_commissions` key equals `B` rather than `A`.

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
