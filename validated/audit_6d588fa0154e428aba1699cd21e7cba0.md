## Analysis

The Aave flash-loan bug in the report is a case of a contract trusting an insufficient access check on a callback function (`executeOperation`) that any unprivileged caller can trigger with attacker-chosen parameters by simply invoking a permissionless external protocol call (`flashLoan`) and naming the victim contract as `receiver`.

The Cosmos EVM analog is the **IBC Callbacks module**'s source-side `onPacketAcknowledgement`/`onPacketTimeout` dispatch in `x/ibc/callbacks/keeper/keeper.go`. This module lets an EVM contract register itself (via the ICS-20 transfer `memo.src_callback.address` field) to receive a call when a packet it allegedly sent is acknowledged or times out.

### Title
Attacker-controlled `msg.sender` and target-contract selection in IBC source callbacks allow permissionless invocation of `onPacketAcknowledgement`/`onPacketTimeout` on arbitrary contracts - (`File: x/ibc/callbacks/keeper/keeper.go`)

### Finding Description
`IBCOnAcknowledgementPacketCallback` and `IBCOnTimeoutPacketCallback` invoke the target contract's callback using the *packet sender's own address* as the caller identity, not a fixed, trusted module address: [1](#0-0) 

and equivalently for timeout: [2](#0-1) 

The `contractAddress` invoked is taken directly from the `src_callback.address` field of the memo that the packet sender itself supplies when creating the `MsgTransfer`, and is not required to be a contract the sender owns, deployed, or has any relationship with: [3](#0-2) 

The module's own documentation states the security assumption that "**Implementing contracts must ensure that only the IBC module can invoke these callback methods**": [4](#0-3) 

However, the implementation makes that assumption impossible to enforce: `msg.sender`, as observed inside the target contract, is set to the attacker's own transaction-signing address (`packetSenderAddress`), not to any fixed "IBC callbacks module" address. Any unprivileged account can:
1. Send a trivial-value `MsgTransfer` from their own account, with `memo.src_callback.address` pointing at any victim contract that implements `ICallbacks`.
2. Force the packet to time out (simply withholding relay before the timeout, which is entirely within the sender's control) or let it be acknowledged.
3. Have `IBCOnTimeoutPacketCallback`/`IBCOnAcknowledgementPacketCallback` call `victim.onPacketTimeout(sourceChannel, sourcePort, sequence, data)` (or `onPacketAcknowledgement`) with `msg.sender` = attacker's own address, and `sourceChannel`, `sourcePort`, `sequence`, `data` all derived from the attacker's own crafted packet.

This is structurally identical to the H-02 pattern: a "callback" surface reachable by any unprivileged party via a legitimate protocol primitive (here, `MsgTransfer`/`MsgTimeout`/`MsgAcknowledgement` instead of Aave's `flashLoan`), where the receiving contract cannot rely on `msg.sender` or the call parameters to establish that the invocation corresponds to a packet the contract itself actually sent, because there is no dedicated trusted-caller identity — the caller identity is always attacker-controlled.

### Impact Explanation
Any contract built on top of the documented `ICallbacks` interface that gates privileged accounting logic (e.g., unlocking escrowed funds, minting/mirroring tokens, rolling back internal ledger state) on the assumption that `onPacketAcknowledgement`/`onPacketTimeout` is only invoked for packets the contract itself sent is vulnerable to unauthorized triggering of that logic by any external, unprivileged account, at attacker-chosen times, with attacker-chosen `sourceChannel`/`sourcePort`/`sequence`/`data` values. Depending on the victim contract's logic, this enables unauthorized minting/duplication, double-refund/unlock of previously-moved value, or state corruption — a critical accounting-integrity violation of exactly the class targeted by this review (unauthorized minting/duplication/unauthorized extraction of spendable value).

### Likelihood Explanation
The trigger requires no privileged access: it only needs the ability to submit an `MsgTransfer` with a crafted memo (any account with a small balance can do this) and to let/force the packet to time out, both fully within an ordinary user's control. The core module code itself provides no mitigation for this — it is entirely up to third-party contract authors to defend against it, and the module's own documentation gives them incorrect assurance ("only the IBC module can invoke") that is not actually enforceable given the current caller-identity design.

### Recommendation
Use a fixed, dedicated module/precompile address as the `from`/caller identity for `CallEVM` invocations of `onPacketAcknowledgement`/`onPacketTimeout`/`onRecvPacket`-style callbacks, rather than the packet sender's address, so receiving contracts can reliably gate access with `require(msg.sender == IBC_CALLBACKS_MODULE)`. Additionally, consider passing the invoking contract's own previously-recorded packet-send record (channel/port/sequence) so contracts can cross-check that the callback corresponds to a packet they actually sent, rather than trusting attacker-supplied parameters alone.

### Proof of Concept
1. Deploy or identify a target contract `V` on the EVM chain that implements `ICallbacks` and gates sensitive logic (e.g., `unlock()`/`mintRefund()`) inside `onPacketTimeout`, relying on the documented invariant that only the IBC module can call it.
2. As an unprivileged attacker with a small token balance, submit `MsgTransfer` with `memo = {"src_callback": {"address": "<V address>", "gas_limit": "1000000"}}` and a short/likely-to-timeout `timeoutTimestamp`.
3. Do not relay the packet to the counterparty chain before timeout expiry.
4. Submit `MsgTimeout` (permissionless, provable via light-client proof of non-receipt) for the packet.
5. This triggers `IBCOnTimeoutPacketCallback`, which calls `V.onPacketTimeout(sourceChannel, sourcePort, sequence, data)` with `msg.sender` equal to the attacker's own address, entirely outside `V`'s control or intent — demonstrated in the code path at [2](#0-1) .

### Design

The sender of an IBC transfer packet may specify a contract to be called when the packet lifecycle completes.
This contract **must** implement the expected entrypoints for `onAcknowledgePacket` and `onTimeoutPacket`.

Crucially, **only the IBC packet sender can set the callback**.

### Use case

The cross-chain swaps implementation sends an IBC transfer. If the transfer were to fail, the sender should
be able to retrieve their funds which would otherwise be stuck in the contract. A contract may also wish to
retry sending the packet. In order to do either, the contract must receive the acknowledgement and timeout
callback to understand what occured in the packet lifecyle.
