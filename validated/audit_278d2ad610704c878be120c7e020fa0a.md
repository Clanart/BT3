### Title
Unvalidated remote mirror URLs let any spend bundle trigger SSRF from the DataLayer service - ([File: chia/data_layer/download_data.py])

### Summary
The DataLayer subscription/mirror system fetches attacker-controlled URLs without validating the URL scheme or resolved network destination, allowing any unprivileged party to force a victim's DataLayer node to make HTTP requests to arbitrary hosts, including loopback/private/link-local addresses.

### Finding Description
DataLayer stores tracked by a wallet advertise "mirror" URLs on-chain. A mirror is simply a coin sent to the mirror puzzle hash (`create_mirror_puzzle()`, a `P2_PARENT` puzzle curried with `1`) carrying a `CREATE_COIN` condition whose memo list is `[launcher_id, *urls]`, as parsed by `get_mirror_info()` in [1](#0-0) . Any wallet holder can submit a standard spend bundle creating such a coin — `DataLayerWallet.create_new_mirror()` builds this with a plain `generate_signed_transaction()` call with **no check that the caller owns or controls `launcher_id`** [2](#0-1) .

When any node's wallet observes this coin and already tracks that `launcher_id` (e.g., because a user or a DataLayer service subscribed to that store), it unconditionally records the attacker-supplied URLs as a mirror with no ownership or URL-content validation: [3](#0-2) .

`DataLayer.update_subscriptions_from_wallet()` pulls these mirror URLs from the wallet and inserts them into local subscriptions [4](#0-3) , which the periodic sync loop then dereferences via `fetch_and_validate()` [5](#0-4) , ultimately calling `http_download()`: [6](#0-5) 

There is no scheme allow-list, no hostname/IP validation, and no blocking of loopback/private/link-local ranges anywhere in this fetch path (confirmed absent via search of `chia/data_layer/`), unlike the CVE-2026-44363 fix in misp-modules which added exactly these checks. The same permissionless URL injection also applies via the RPC/CLI `subscribe`/`add_mirror` commands (`chia data subscribe -u <url>`, `dl_new_mirror`), which likewise accept arbitrary strings with no validation [7](#0-6) [8](#0-7) .

### Impact Explanation
A local DataLayer service can be coerced into issuing outbound HTTP GET requests to attacker-chosen destinations, including `127.0.0.1`/internal RFC1918 addresses, potentially reaching other local services (e.g., unauthenticated local HTTP endpoints, cloud metadata endpoints if run in a cloud VM) that the operator did not intend to expose to remote-influenced requests. Because the trigger (mirror coin creation) requires only a normal, permissionless on-chain spend for an arbitrary `launcher_id` already tracked by the victim, this is reachable by any spend-bundle submitter without requiring the victim's cooperation beyond having previously subscribed to/tracked that store. This is a Server-Side Request Forgery class issue (CWE-918) matching the reported bug class, scoped to Data Layer's remote-resource fetching.

### Likelihood Explanation
Moderate: exploitation requires the victim's DataLayer node to already be tracking the targeted `launcher_id` (via subscription or ownership) so the mirror coin gets picked up, but creating the mirror coin itself requires no special privilege — just a standard signed spend to the mirror puzzle hash with an arbitrary memo, which any wallet holder can construct.

### Recommendation
Validate mirror/subscription URLs before use: enforce an `http(s)` scheme allow-list, resolve the hostname, and reject loopback, private, and link-local address ranges before calling `http_download()`/`download_file()` in `chia/data_layer/download_data.py`, mirroring the validation added upstream for the referenced advisory. Consider also requiring launcher-id ownership (or at least surfacing mirror provenance) before auto-trusting mirror URLs pulled into local subscriptions in `data_layer.py`.

### Proof of Concept
1. Attacker identifies a `store_id`/`launcher_id` that the victim's DataLayer node tracks (subscribed store or owned store visible via public chain data).
2. Attacker submits a standard signed spend bundle creating a coin with puzzle hash `create_mirror_puzzle().get_tree_hash()` and a `CREATE_COIN` condition whose memo is `[launcher_id, b"http://127.0.0.1:<internal-port>/"]` (equivalent to what `DataLayerWallet.create_new_mirror()` produces, but crafted for a `launcher_id` the attacker does not own).
3. Once confirmed, the victim's `DataLayerWallet.coin_added()` records this as a tracked mirror since it already tracks `launcher_id`.
4. On the next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` imports the URL into local subscriptions, and `fetch_and_validate()` → `insert_from_delta_file()` → `download_file()` → `http_download()` issues `GET http://127.0.0.1:<internal-port>/<filename>` from the victim's machine, demonstrating SSRF against an internal target chosen entirely by the attacker.

def create_mirror_puzzle() -> Program:
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
