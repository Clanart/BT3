## Analog Found

### Title
Denial of Service via Unbounded Bech32 Offer String Length Check Bypass in `Offer.from_bech32` - (File: `chia/wallet/trading/offer.py`)

### Summary
`chia/util/bech32m.py`'s `bech32_decode()` enforces an intentional anti-DoS length cap (`max_length: int = 90`) on any bech32-encoded string before it is character-by-character validated and checksummed. `Offer.from_bech32()` in `chia/wallet/trading/offer.py` calls this function while explicitly disabling that cap: `bech32_decode(offer_bech32, max_length=len(offer_bech32))`. This mirrors the LiteLLM DoS pattern where a boundary/length check that should terminate processing early is instead defeated, letting the server churn through an attacker-controlled amount of input.

### Finding Description
`bech32_decode()` is written to bound input size defensively: [1](#0-0) 

Every other production caller (`decode_puzzle_hash()`) uses the default 90-character cap: [2](#0-1) 

But `Offer.from_bech32()` passes `max_length=len(offer_bech32)`, which makes the length check a no-op — the string is accepted at whatever size the caller supplies and is then fully scanned multiple times (`ord()` sweep, `.lower()`, `.rfind()`, an `all(x in CHARSET ...)` scan, a `CHARSET.find(x)` per character list build, and a `bech32_polymod` checksum walk over the whole data array): [3](#0-2) 

This method is reached directly from wallet-facing, attacker/counterparty-controlled input:
- `TakeOffer.parsed_offer` (used by the `take_offer` RPC endpoint) calls `Offer.from_bech32(self.offer)` on the raw request string. [4](#0-3) 
- `check_offer_validity()` also calls `Offer.from_bech32(request.offer)` directly on RPC input. [5](#0-4) 

Because `bech32_decode`'s length guard is disabled, a wallet user or an "offer counterparty" who hands a wallet a crafted offer string (e.g., pasted into `take_offer`, or sent through any flow that eventually calls `Offer.from_bech32`) can force full linear-but-unbounded character-level processing (multiple full-length passes, each doing per-character `CHARSET.find`/`in` membership checks) before validation fails, rather than being rejected almost immediately by the intended 90-character cap.

### Impact Explanation
Any code path accepting an offer string (RPC `take_offer`, `check_offer_validity`, and CLI wrappers that pass user/counterparty-supplied text straight to `Offer.from_bech32`) will spend CPU proportional to the attacker-chosen string length instead of being bounded to ~90 characters as the underlying primitive was designed to enforce. This is a resource-consumption/availability issue against the wallet RPC service — the exact bug class in the report (a boundary/limit check defeated by attacker-controlled length, causing disproportionate processing of a single crafted request).

### Likelihood Explanation
The bypass is deterministic and requires no privileges: any string handed to `take_offer`/`check_offer_validity` (or any offer-consuming CLI/GUI path) goes straight to `Offer.from_bech32` with the disabled cap. An attacker (a would-be offer counterparty, or anyone able to submit strings to the wallet RPC) can trivially construct an arbitrarily long non-conforming bech32-looking string, bounded only by the RPC's `max_request_body_size` (documented as configurable, with a Data Layer example default of ~25MB).

### Recommendation
Do not override `bech32_decode`'s length cap with the caller-supplied string's own length. Either keep the default 90-character bound for offers (bech32 offers are compressed/binary payloads that don't need to exceed a small bound before their own internal validation runs) or introduce an explicit, small, fixed maximum (e.g., a documented `MAX_OFFER_BECH32_LENGTH`) instead of `len(offer_bech32)`, so oversized/malformed input is rejected before the character-by-character scan and checksum walk run.

### Proof of Concept
1. Construct a string starting with any prefix, a separator `1`, and millions of characters drawn only from `CHARSET = "qpzry9x8gf2tvdw0s3jn54khce6mua7l"` (so the `all(x in CHARSET ...)` fast-reject doesn't short-circuit), sized up to the RPC's configured `max_request_body_size`.
2. Send it as the `offer` field to the wallet RPC `check_offer_validity` or `take_offer` endpoint (or pass it to `Offer.from_bech32()` directly).
3. Observe that `bech32_decode(offer_bech32, max_length=len(offer_bech32))` processes the entire string (multiple linear passes plus a full-length `bech32_polymod` checksum computation) before ultimately failing checksum verification — work that the 90-character design limit was meant to prevent for any single request.

```python
def bech32_decode(bech: str, max_length: int = 90) -> tuple[str | None, list[int] | None]:
    """Validate a Bech32 string, and determine HRP and data."""
    bech = bech.strip()
    if (any(ord(x) < 33 or ord(x) > 126 for x in bech)) or (bech.lower() != bech and bech.upper() != bech):
        return (None, None)
    bech = bech.lower()
    pos = bech.rfind("1")
    if pos < 1 or pos + 7 > len(bech) or len(bech) > max_length:
        return (None, None)
    if not all(x in CHARSET for x in bech[pos + 1 :]):
        return (None, None)
    hrp = bech[:pos]
    data = [CHARSET.find(x) for x in bech[pos + 1 :]]
    if not bech32_verify_checksum(hrp, data):
        return (None, None)
    return hrp, data[:-6]
```
