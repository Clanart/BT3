### Title
`CLEMENTINE_EIP712_DOMAIN` omits `chain_id`, enabling cross-network replay of withdrawal authorization signatures — (`File: core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is defined with only `name` and `version`, omitting `chain_id`. Because neither the domain nor the signed message structs (`OptimisticPayoutMessage` / `OperatorWithdrawalMessage`) bind to a Citrea chain ID, a valid aggregator verification signature produced for one Citrea deployment can be replayed verbatim against a second Citrea deployment that shares the same aggregator key, bypassing the authorization gate that guards optimistic-payout and operator-withdrawal flows.

---

### Finding Description

`core/src/rpc/ecdsa_verification_sig.rs` defines the single global EIP-712 domain used to authenticate every withdrawal authorization signature in the bridge:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The `chain_id` field is absent. The two signed message structs contain no network identifier either:

```rust
struct OptimisticPayoutMessage {
    uint32 withdrawal_id;
    bytes  input_signature;
    bytes32 input_outpoint_txid;
    uint32 input_outpoint_vout;
    bytes  output_script_pubkey;
    uint64 output_amount;
}
struct OperatorWithdrawalMessage { /* identical fields */ }
``` [2](#0-1) 

The EIP-712 signing hash fed to `recover_address_from_prehash` is therefore identical for the same withdrawal parameters regardless of which Citrea chain the verifier or operator is running on:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)…;
``` [3](#0-2) 

The recovered address is then compared to `aggregator_verification_address` in config. Because `citrea_chain_id` is a known, distinct value per deployment (e.g. `5655` for testnet4) and is already stored in `BridgeConfig`: [4](#0-3) 

…it is never injected into the domain, leaving the domain separator network-agnostic.

The same domain is consumed in both the verifier's `sign_optimistic_payout` path: [5](#0-4) 

…and the operator's `withdraw` RPC handler: [6](#0-5) 

---

### Impact Explanation

If the same aggregator ECDSA key is used across two Citrea deployments that share the same underlying Bitcoin network (e.g., two Citrea testnets both anchored to Bitcoin testnet4), an authorization signature produced for a withdrawal on deployment A is cryptographically valid on deployment B. An attacker who captures such a signature can submit it to deployment B's verifiers or operators. Verifiers would pass the `address_from_sig == address_in_config` check and proceed to sign an optimistic-payout MuSig2 partial signature; operators would proceed to broadcast a payout transaction — both without the aggregator having authorized the action on that chain.

The downstream database checks (`get_move_to_vault_txid_from_citrea_deposit`, `get_withdrawal_utxo_from_citrea_withdrawal`) provide partial mitigation: they require the same `withdrawal_id` and `input_outpoint` to be present in the target deployment's DB. This limits exploitability to scenarios where the same Bitcoin UTXO and deposit index exist on both deployments, which is possible but not guaranteed. [7](#0-6) 

---

### Likelihood Explanation

**Low-to-medium.** Preconditions are:
1. The same aggregator ECDSA key is configured on two distinct Citrea deployments (common during staging/migration).
2. Both deployments are anchored to the same Bitcoin network (e.g., both use Bitcoin testnet4).
3. A matching `withdrawal_id` and Bitcoin UTXO exist on the target deployment.

Conditions 1 and 2 are operationally plausible; condition 3 is the binding constraint that reduces likelihood. The `aggregator_verification_address` guard is also optional — if not configured, the domain issue is moot for that deployment.

---

### Recommendation

Include `chain_id` in the domain, sourced from `BridgeConfig::citrea_chain_id` at startup rather than as a compile-time constant:

```rust
// At initialization time, build the domain with the runtime chain ID:
pub fn make_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass `config.citrea_chain_id as u64` when constructing the domain, and thread it through `recover_address_from_ecdsa_signature` instead of using the global static. This mirrors the fix applied to `Karma.sol` (`__ERC20Permit_init(NAME)`) — supplying the missing binding parameter that scopes signatures to a specific network.

---

### Proof of Concept

1. Deploy two Clementine instances (A and B) both connected to Bitcoin testnet4, with different Citrea chain IDs but the **same** `aggregator_verification_address` / signing key.
2. On instance A, have the aggregator sign an `OptimisticPayoutMessage` for `withdrawal_id=0`, `input_outpoint=TXID:0`, `output_amount=X`.
3. Capture the hex-encoded `verification_signature`.
4. On instance B, submit an `optimistic_payout` RPC call with the same parameters and the captured signature.
5. Because `CLEMENTINE_EIP712_DOMAIN` contains no `chain_id`, `eip712_signing_hash` produces the same digest on both instances; `recover_address_from_prehash` returns the same aggregator address; the check at line 1616 passes; verifiers on instance B sign the optimistic payout without the aggregator having authorized it on chain B.
