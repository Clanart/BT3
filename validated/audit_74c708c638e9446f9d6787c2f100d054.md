### Title
BIP-340 signing normalizes nonce parity but not group-key parity, making funds sent to odd output keys unspendable - (File: networks/bitcoin/src/crypto.rs)

### Summary
Bitcoin Taproot signatures are generated with a raw FROST group key while BIP-340 verification interprets the serialized x-only key as its even-Y representative. The implementation adjusts the nonce when `R` is odd but never negates or otherwise normalizes an odd group key. Consequently, validly completed threshold signatures are rejected by Bitcoin whenever the effective Taproot output key is odd, leaving received outputs unspendable through the normal signing path. [1](#0-0) [2](#0-1) 

### Finding Description
`x_only` serializes only the x coordinate of a point, discarding whether the point has even or odd Y, while `needs_negation` identifies odd-Y points. [3](#0-2)  During BIP-340 challenge generation, `Hram::hram` hashes `x(R)`, `x(A)`, and the message, then negates the challenge when `R` is odd; it performs no equivalent parity handling for the public key `A`. [1](#0-0) 

The transaction signer applies each input’s offset, verifies that `p2tr_script_buf(offset.group_key())` matches the previous output, and signs the Taproot sighash with that offset key. [4](#0-3) [5](#0-4)  However, `Schnorr::sign_share` delegates directly to the generic FROST Schnorr implementation, which signs `r + c * secret_share` without negating `secret_share` when the group key is odd. [6](#0-5) [7](#0-6) 

The generic verifier checks `R + cA - sG == 0` against the full projective point `A`, including its odd-Y form. [8](#0-7)  Bitcoin instead verifies the signature against the even-Y lift of the same x-only key, which is `-A` when `A` is odd. The Bitcoin wrapper preserves that internal verification result, conditionally negates `s` based only on `R`, and emits the x-only `R || s` encoding. [2](#0-1) 

Thus, the internal success check and the external Bitcoin verifier evaluate different signing equations whenever the effective output key is odd. The signature can satisfy Serai’s `sG = R + cA` equation while failing Bitcoin’s required equation against `-A`. [9](#0-8) [8](#0-7) 

### Impact Explanation
A P2TR output constructed for an odd effective group key can be detected and reported as received, but `SignableTransaction::multisig` will generate signatures that Bitcoin consensus rejects. [4](#0-3)  Since the output commits only to the x coordinate, the mismatch is not visible in the script public key and cannot be corrected by choosing a different signature nonce. [3](#0-2)  This creates a loss-of-funds condition for outputs controlled by odd effective keys and can halt transaction signing after threshold participants successfully produce internally consistent shares. [9](#0-8) 

### Likelihood Explanation
An unrestricted uniformly distributed group or tweaked output key has approximately a one-in-two probability of having odd Y. The reachable path only requires a Bitcoin payment to such a P2TR output followed by a normal spend attempt; no malicious validator, malformed signature share, or invalid curve encoding is needed. [10](#0-9) [4](#0-3)  The signing and completion paths shown do not enforce even output keys or normalize the distributed secret to the even representative before signing. [11](#0-10) 

### Recommendation
Normalize the signing key parity before producing shares. If the effective Taproot group key `A` is odd, sign with the negated threshold secret corresponding to `-A`, and use the same even-lifted key in `sign_share`, `verify`, and `verify_share`. Alternatively, constrain output-key derivation or offsets so the committed effective key is always even, and reject any stored offset that produces an odd `offset.group_key()` before funds are accepted. Apply the nonce parity normalization alongside—not instead of—the key parity normalization, and add deterministic tests covering all four combinations of odd/even `R` and `A`. [1](#0-0) [4](#0-3) 

### Proof of Concept
Let `q` be the distributed secret and `A = qG` be an odd-Y effective output key. Bitcoin interprets the x-only public key as `A' = -A`, whose corresponding secret is `-q`, not `q`. [3](#0-2) 

For aggregate nonce `r` with `R = rG`, define `h = H_BIP340(x(R) || x(A) || m)`. The implementation computes `h` from `x(R)` and `x(A)` and negates it only when `R` is odd. [1](#0-0) 

- If `R` is even, Serai emits `s = r + hq`. Bitcoin expects `s' = r + h(-q) = r - hq`.
- If `R` is odd, Serai internally forms `r - hq`, then emits `s = -(r - hq) = -r + hq`. Bitcoin expects `s' = -r + h(-q) = -r - hq`.

In both cases the emitted `s` differs by `2hq`, so BIP-340 verification fails except in negligible degenerate cases. The internal FROST completion can still accept the shares because it verifies against the raw odd point `A`, while Bitcoin verifies against `-A`. [9](#0-8) [2](#0-1)

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
