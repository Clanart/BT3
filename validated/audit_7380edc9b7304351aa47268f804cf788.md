### Title
Transaction-level `data`/`presumed_origin` applied to every accumulated output, letting a later transaction rewrite earlier deposits' instructions - (File: processor/src/networks/bitcoin.rs)

### Summary
In `Bitcoin::get_outputs`, the `outputs` vector is declared **outside** the per-transaction loop over `block.txdata[1 ..]` [1](#0-0) . After scanning each transaction, the code iterates `for output in &mut outputs` and overwrites `output.data` and `output.presumed_origin` for **all outputs collected so far**, not just the ones found in the current transaction [2](#0-1) . This is the direct Serai analog of CVE-2019-20884 ("a file partially attachable to more than one post"): one transaction's InInstruction payload and origin address are attached to every previously scanned output in the same block.

### Finding Description
`scan_transaction` pushes freshly found `Output`s into the block-scoped `outputs` vec (lines 689-700). Then, per transaction, `presumed_origin` is computed from `tx.input[0]`'s spent output script (lines 707-729) and `data` from `Self::extract_serai_data(tx)` (line 730), and both are cloned into every element of `outputs` (lines 731-736). Two consequences:

1. If transaction A (victim deposit to the multisig's `External` address) precedes transaction B (attacker transaction, which needs no Serai output at all), then when B is processed the cumulative `outputs` is non-empty, the `if outputs.is_empty() { continue }` guard does not fire (it checks the cumulative vec, not per-tx results), and B's `data`/`presumed_origin` overwrite the ones already assigned to A's outputs.
2. `presumed_origin` is fed into `instruction_from_output` as the fallback refund origin (`instruction.origin.or(presumed_origin)`) [3](#0-2) . If the overwritten `data` fails `Shorthand::decode`/`RefundableInInstruction::try_from` (e.g., the attacker's tx has no `OP_RETURN`, leaving `data` empty or malformed), the code takes the refund path and builds `PlanFromScanning::Refund(output, refund_to)` with `refund_to` = the attacker's address [4](#0-3) .

The spec states origin is "the transaction's first input's address" [5](#0-4)  — but this implementation silently substitutes the *attacker's* transaction's first input for the *victim's* deposit.

### Impact Explanation
An unprivileged attacker can steal deposited funds or hijack deposit instructions. By getting any transaction (even one paying no Serai address) ordered after a victim's deposit in the same block, the attacker overwrites the victim output's `presumed_origin` with their own address and/or its `data` with garbage or an attacker-crafted InInstruction (e.g., `Dex(Data)` executing attacker-chosen calls against the victim's balance). The cleanest exploit: attacker tx with no OP_RETURN wipes `data`, causing `instruction_from_output` to produce no instruction, and the victim's UTXO is scheduled as a `Refund` paying the attacker's presumed_origin address. This is "funds reported received that are not spendable [by their rightful owner]" — redirected to the attacker.

### Likelihood Explanation
Requires only that the attacker's transaction appears in the same block after the victim's — achievable by watching the mempool for deposits to a known Serai multisig address and broadcasting a competing transaction, or via miner/co-located bundles. The overwrite is deterministic once ordering holds. This does assume refund scheduling to an attacker-controlled `presumed_origin` isn't caught downstream; the code path itself applies no check that `data`/`presumed_origin` came from the output's own transaction.

### Recommendation
Scope `data` and `presumed_origin` assignment to the outputs found in the current transaction only — e.g., scan into a per-tx `Vec`, decorate those outputs, then extend the block-level accumulator:

```rust
let mut tx_outputs = vec![];
for output in scanner.scan_transaction(tx) { ... tx_outputs.push(output); }
if tx_outputs.is_empty() { continue; }
// compute presumed_origin/data from this tx, apply to tx_outputs only
outputs.extend(tx_outputs);
```

Also make the `is_empty` guard check the per-tx vector so unrelated transactions never trigger origin/data computation.

### Proof of Concept
Block contains, in order:
1. `tx_v`: victim sends X BTC to the multisig's `p2tr_script_buf(key)` (External kind), with `OP_RETURN` encoding `RefundableInInstruction { origin: None, instruction: Transfer }`.
2. `tx_a`: attacker's arbitrary transaction (input owned by attacker, no Serai output, no OP_RETURN).

During `get_outputs`, `tx_v` pushes the victim `Output` into `outputs` and initially sets its `data`/`presumed_origin` correctly. On `tx_a`, `scan_transaction` adds nothing but `outputs.is_empty()` is false, so `presumed_origin` is recomputed as `Address::new(attacker_prevout_script)` and `data = extract_serai_data(tx_a)` (empty). Both are cloned onto the victim's output. In `scanner_event_to_multisig_event`/`instruction_from_output`, empty `data` decodes to no instruction while `refund_to = Some(attacker_address)`, producing `PlanFromScanning::Refund(victim_output, attacker_address)` — the victim's deposit is refunded to the attacker.
