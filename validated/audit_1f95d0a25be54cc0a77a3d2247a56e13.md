### Title
`ReceivedOutput::read` deserializes an unchecked scalar offset/output pair, reporting funds received that are not spendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report concerns an unchecked return value: `CurveAMO_V3.giveCollatBack` updates `returned_collat_historical` and returns success even when the token transfer silently failed. The analog in Serai is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs` (lines 122–134), which deserializes an attacker-supplied `offset` scalar, `TxOut`, and `OutPoint` and returns `Ok(ReceivedOutput)` without ever validating that `offset` actually maps the group's key to `output.script_pubkey`. The "transfer failed but success reported" pattern is replicated as "the output cannot be spent with this offset, yet a spendable-looking `ReceivedOutput` is returned successfully".

### Finding Description
`Scanner::scan_transaction` (lines 199–214) only produces `ReceivedOutput`s whose `offset` was pulled from the internally-maintained `scripts` map, guaranteeing `p2tr_script_buf(key + offset·G) == output.script_pubkey`. However, `ReceivedOutput` is also constructible purely from untrusted bytes via `ReceivedOutput::read` (lines 122–134), listed as a public untrusted-bytes entry point. That function performs three independent decodes and returns `Ok` unconditionally:

```rust
// networks/bitcoin/src/wallet/mod.rs
let offset = Secp256k1::read_F(r)?;
output  = TxOut::consensus_decode(&mut buf_r)...?;
outpoint = OutPoint::consensus_decode(&mut buf_r)...?;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no cross-check analogous to what `SignableTransaction::multisig` later performs at line 277 (`p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey`). A `ReceivedOutput` read from untrusted bytes can therefore carry an offset that does not derive the output's script — i.e., an output whose value is credited (`value()`, line 116) as spendable wallet funds while the spend key is wrong. The failure is only detected much later (and only because `multisig` happens to re-check), exactly like the report's scenario where the failed transfer is only detected after state was already committed.

### Impact Explanation
Funds are reported as received (`ReceivedOutput::value`) that are not spendable: the deserialized offset does not correspond to any key able to satisfy `output.script_pubkey`. Any accounting/deposit flow that trusts a serialized `ReceivedOutput` credits value that cannot be signed for — a direct analog of collateral "returned" that never moved. If the downstream consumer treats the deserialization success as validation (as `giveCollatBack` treated the transfer call's success), the discrepancy is silent.

### Likelihood Explanation
Reachable by any unprivileged party able to feed bytes to `ReceivedOutput::read`: the scalar is fully attacker-controlled (`Secp256k1::read_F` only enforces canonicality), and the `TxOut`/`OutPoint` are arbitrary consensus-decodable data. Crafting a mismatched offset requires no work — any random scalar mismatches with overwhelming probability. Exploitation depends on an integrator persisting/relaying serialized `ReceivedOutput`s across a trust boundary, which is the function's evident purpose (it is `std`-gated serialization for transport/storage).

### Recommendation
Bind the offset to the output at read time. Either (a) change `ReceivedOutput::read` to take the group's `ProjectivePoint` and verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)` before returning `Ok`, mirroring the check in `SignableTransaction::multisig` (send.rs line 277); or (b) document loudly that `read` performs no consistency validation and consumers MUST re-verify via `Scanner`/`multisig` before crediting `value()`. Treating deserialization success as correctness is the same class of error as treating a `transfer` call's return as a successful transfer.

### Proof of Concept
```rust
// Attacker-controlled bytes: valid canonical scalar + valid TxOut + valid OutPoint,
// where offset does NOT derive the script_pubkey.
let mut bytes = Vec::new();
bytes.extend(Scalar::ONE.to_bytes());            // arbitrary, wrong offset
bytes.extend(serialize(&victim_txout));          // pays to scanner's script
bytes.extend(serialize(&outpoint));

let received = ReceivedOutput::read(&mut &bytes[..]).unwrap(); // succeeds
assert!(received.value() > 0); // credited as spendable
// SignableTransaction::new(...).multisig(&keys) later returns None:
// the offset does not produce the output's script_pubkey.
```

Caveat: the exploit requires a consumer that trusts serialized `ReceivedOutput`s without re-scanning; if all consumers go through `Scanner::scan_transaction`/`scan_block`, the mismatched offset is never accepted. This is a missing-validation / fail-open boundary issue rather than a directly exploitable cryptographic flaw.
