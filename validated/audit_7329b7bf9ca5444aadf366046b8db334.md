## Analog Found

### Title
Wrapped-SEI (`WSEI`) `withdraw()` uses `.transfer()` and can permanently strand funds for contract-based holders - (File: `contracts/src/WSEI.sol`)

### Summary
The `WSEI` contract, whose bytecode is packaged in the chain's own artifacts and deployable/used as the canonical Wrapped-SEI ERC-20 (an exact WETH9-style wrapper), sends native SEI to the withdrawing account using Solidity's `.transfer()`, which forwards only a fixed 2300-gas stipend. This is the same anti-pattern flagged in the external report (`Borrower.sol`'s `withdrawAnte`).

### Finding Description
`WSEI.withdraw()` burns the caller's wrapped balance and then unwraps it by calling `payable(msg.sender).transfer(wad)`: [1](#0-0) 

`.transfer()` hard-codes a 2300 gas stipend for the receive/fallback execution of the recipient. Any `msg.sender` that is a smart contract (multisig wallet, proxy, DeFi vault, another contract that wraps/holds WSEI, an account-abstraction/EIP-7702 delegated account, etc.) whose `receive`/`fallback` function consumes more than 2300 gas, or that is called through an intermediate proxy, will have this call revert with out-of-gas. This contract is shipped as first-class chain tooling — its bytecode/ABI live under `x/evm/artifacts/wsei` and can be deployed by any user via the `evm tx deploy-wsei` CLI command, which then becomes a canonical wrapped-native-token contract that other contracts and integrators are expected to hold and interact with: [2](#0-1) 

Because Sei is fully EVM-equivalent (arbitrary bytecode can be deployed by any unprivileged sender), any contract that legitimately accumulates WSEI balance (e.g., an AMM pool, vault, or router contract) and later tries to `withdraw()` its underlying SEI can be permanently blocked if its own fallback logic (or gas overhead from a proxy/delegatecall pattern) exceeds 2300 gas — irrespective of the amount of gas supplied to the outer transaction.

### Impact Explanation
This can result in permanent freezing of native SEI funds inside the `WSEI` contract for any contract-based holder whose receive/fallback exceeds the 2300 gas stipend, since `withdraw()` will unconditionally revert for that caller with no alternative unwrap path. This matches the "permanent freezing of funds" acceptance criterion, reachable purely through normal EVM contract deployment and interaction (no privileged/validator access required).

### Likelihood Explanation
Likelihood is proportional to adoption of `WSEI` by other smart contracts (routers, vaults, multisigs) as the standard wrapped-native token, which is the intended use case since the chain ships and documents its deployment. Any contract wallet or proxy-based contract with non-trivial fallback logic holding WSEI would trigger this deterministically on withdrawal.

### Recommendation
Replace `payable(msg.sender).transfer(wad)` in `WSEI.withdraw()` with a low-level `call` and explicit success check, consistent with modern WETH9-style implementations:
```solidity
(bool success, ) = msg.sender.call{value: wad}("");
require(success, "SEI_TRANSFER_FAILED");
```

### Proof of Concept
1. Deploy a contract `Recipient` whose `receive()` function performs a state-changing operation costing more than 2300 gas (e.g., an `SSTORE` to a non-zero slot).
2. `Recipient` calls `WSEI.deposit{value: 1 ether}()`, receiving 1 WSEI.
3. `Recipient` calls `WSEI.withdraw(1 ether)`.
4. The internal `payable(msg.sender).transfer(wad)` call reverts because the 2300-gas stipend is insufficient for `Recipient`'s `receive()` logic, even though `Recipient`'s WSEI balance was already decremented in a code path guarded by `require`, causing the whole `withdraw` transaction (and thus the unwrap) to always fail — the 1 ether of underlying SEI is permanently stuck in the `WSEI` contract with no other recovery function.
