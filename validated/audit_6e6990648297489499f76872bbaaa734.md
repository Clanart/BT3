## Analysis

The report's core primitive is: an operation **pulls** trusted state, hands control to an **external, attacker-influenceable call**, and a component that shares state with that call can be abused to **exfiltrate value that was never meant for it**, because nothing binds the reentrant call to the specific operation/asset it should be scoped to.

The GitHub Desktop analog is in the trampoline credential mechanism.

### Broken invariant

`withTrampolineEnv` sets `GIT_CONFIG_PARAMETERS` to force `credential.helper=desktop` and exports `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` for **every** Git invocation, explicitly so that child processes spawned by Git (hooks, filters, Git LFS, etc.) also pick up the credential helper configuration: [1](#0-0) 

When the trampoline server receives a `credential get` request, `getCredential` first tries `getGitHubCredential`, which resolves purely by matching the request's `host`/`url` against a signed-in account's origin — with no check that the host corresponds to the repository/remote that the currently-running git operation actually targets: [2](#0-1) [3](#0-2) 

If it matches, the real account token is returned unconditionally: [4](#0-3) 

The trampoline token is only checked for validity (i.e. "some Desktop-initiated operation is in flight"), not for which repository/remote it was issued to: [5](#0-4) [6](#0-5) 

## Title
Any subprocess spawned by a Git operation (hooks/filters) can impersonate a `host=github.com` credential request and exfiltrate the signed-in user's GitHub token via the trampoline credential helper - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
Desktop configures `credential.helper=desktop` and exposes `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` to every process spawned during a Git operation, including filters and hooks that run untrusted repository content (this is called out explicitly in code comments as intentional, for Git LFS). Any such child process can speak the trampoline protocol (or simply invoke `git credential fill`) with a forged `host=github.com`/`host=<ghe-host>` request. The trampoline's `getGitHubCredential` resolves credentials purely by host with no binding to the repository/remote the outer operation is actually working with, so it returns the user's real GitHub username/PAT to that untrusted process.

### Finding Description
`withTrampolineEnv` is the single choke point used by every `git`/`spawnGit` invocation, and it deliberately exports the credential trampoline configuration in environment variables (rather than CLI args) "because we want commands invoked by filters (i.e. Git LFS) to be able to pick up our configuration": [7](#0-6) 

Those env vars are consequently inherited by any child process the outer `git` process spawns while acting on repository-controlled configuration/content (clean/smudge filters, custom LFS transfer agents, hooks, etc.).

When a `credential get` request arrives, `createCredentialHelperTrampolineHandler` parses the request's `stdin` verbatim (`protocol=`, `host=`, `url=` — attacker-controlled if the caller is a repo-driven subprocess) and passes it into `getCredential`: [8](#0-7) 

`getCredential` checks `getGitHubCredential` **first, unconditionally**, before any check of what the enclosing git operation/repository actually is: [9](#0-8) 

`findGitHubTrampolineAccount` only compares URL origins, and `credWithAccount` attaches the account's real token: [3](#0-2) [4](#0-3) 

The trampoline token is validated only for existence (`isValidTrampolineToken`), not for association with a specific repository path or remote: [5](#0-4) 

So the only thing separating "a legitimate Git subprocess asking for the credentials it needs for the current remote" from "an attacker-influenced subprocess asking for `github.com` credentials it has no business requesting" is the *content* of the credential request — which is fully controlled by whatever process makes the request. There is no guard analogous to a reentrancy lock that ties a `get` request to the specific host/remote the outer operation launched with `path`/`isBackgroundTask` for.

### Impact Explanation
A successful request yields the victim's real GitHub username and personal access/OAuth token (`a.token`) formatted and handed back over the local TCP trampoline socket to the requesting process: [10](#0-9) 

That token grants the same scopes as the user's Desktop session, so an attacker who can get any code to run as a child of a Desktop-initiated `git` call can silently exfiltrate the user's GitHub credentials — well beyond the intended blast radius of "authenticate to the requested remote." This matches the "credential/token exfiltration" impact category.

### Likelihood Explanation
Exploitation requires the attacker to get *some* process spawned as part of a Desktop `git` invocation to speak the credential-helper protocol with a forged host — e.g. via a Git filter/clean-smudge driver or an LFS custom transfer agent declared in repository-tracked configuration (`.gitattributes` / `.lfsconfig`) that the code comment in `trampoline-environment.ts` explicitly acknowledges as an intended recipient of the credential helper env vars. Because this design intentionally propagates the trampoline credentials to filter subprocesses without scoping the resulting `get` requests to the operation's actual remote, the security boundary that should exist between "the remote Desktop is talking to" and "the remote a subprocess can request creds for" does not exist. This is a design-level absence of a scoping guard rather than a rare race, so once any repo-driven subprocess execution path is available, exploitation is deterministic and requires no user interaction beyond the normal clone/fetch/checkout that already triggers the filter/hook.

### Recommendation
Bind each trampoline token to the specific remote/host (and repository path) the enclosing operation was started for, and reject `get` requests whose `host`/`url` doesn't match that binding (or fall through to the non-GitHub generic-credential path instead of returning GitHub Desktop's own signed-in credential). Equivalently, scope `getGitHubCredential` lookups to the actual remote URL of the running operation (available via `getTrampolineEnvironmentPath`/associated repository) rather than trusting the attacker-suppliable `host` field verbatim, closing the "reentrant" path that lets filters/hooks harvest credentials meant for a different host.

### Proof of Concept
1. User is signed in to GitHub Desktop with a GitHub.com account.
2. Attacker gets the victim to clone/fetch a malicious repository that ships a Git filter/clean-smudge command or custom LFS transfer agent (repository-tracked `.gitattributes`/`.lfsconfig`) which Desktop will spawn as a child of the `git` process for that operation.
3. That child process inherits `DESKTOP_PORT` and `DESKTOP_TRAMPOLINE_TOKEN` (per `withTrampolineEnv`) and simply runs:
   `git credential fill` with stdin `protocol=https\nhost=github.com\n\n` (routed by the inherited `credential.helper=desktop` config to the trampoline).
4. `trampoline-server.ts` validates the token as "in use" only, dispatches to `createCredentialHelperTrampolineHandler`, which calls `getCredential` → `getGitHubCredential`, matches the signed-in account by origin, and returns `username=<login>` and `password=<PAT>` to the malicious subprocess.
5. The subprocess exfiltrates the returned token to an attacker-controlled endpoint.

export const createCredentialHelperTrampolineHandler: (
  store: AccountsStore
) => TrampolineCommandHandler = (store: Store) => async command => {
  const firstParameter = command.parameters.at(0)
  if (!firstParameter) {
    return undefined
  }

  const { trampolineToken: token } = command
  const input = parseCredential(command.stdin)

  if (__DEV__) {
    debug(
      `${firstParameter}\n${command.stdin
        .replaceAll(/^password=.*$/gm, 'password=***')
        .replaceAll(/^(.*)$/gm, '  $1')
        .trimEnd()}`
    )
  }

  try {
    if (firstParameter === 'get') {
      const cred = await getCredential(input, store, token)
      if (!cred) {
        const endpoint = `${getCredentialUrl(input)}`
        info(`could not find credential for ${endpoint}`)
        setHasRejectedCredentialsForEndpoint(token, endpoint)
      }
      return cred ? formatCredential(cred) : undefined

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
