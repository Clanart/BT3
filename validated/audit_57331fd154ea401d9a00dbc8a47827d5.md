### Title
Unauthenticated `operator_xonly_pk` in `payout_tx` OP_RETURN allows the attributed "payer" to diverge from the party that actually funded the withdrawal - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` writes the operator's x-only public key into a plain, unsigned `OP_RETURN` output that the protocol later trusts as cryptographic proof of "who fronted this withdrawal." Because the value moved to the user comes almost entirely from freely-addable funding inputs (the withdrawal's own presigned input is a 550-sat dust UTXO), and because that dust input is signed with `SIGHASH_SINGLE|ANYONECANPAY`, anyone who observes the user's Citrea-committed withdrawal signature can construct and broadcast their own fully valid `payout_tx` that fronts the withdrawal with their own BTC while stamping a different (real, publicly-known) operator's `xonly_pk` into the OP_RETURN. The chain of verifier code that decides who is credited as "the payer" (`update_finalized_payouts`, `is_kickoff_malicious`, `validate_payer_is_operator`) relies solely on this OP_RETURN value, breaking the binding "the operator credited == the party that paid."

### Finding Description
`create_payout_txhandler` embeds `operator_xonly_pk` as raw OP_RETURN data with no signature over it beyond the ordinary wallet-signed tx (see below): [1](#0-0) 

The withdrawal's dedicated input is a tiny dust UTXO (550 sats), not the actual bridge funds: [2](#0-1) 

and its signature is `SinglePlusAnyoneCanPay`: [3](#0-2) 

`SIGHASH_SINGLE|ANYONECANPAY` only commits input 0 to output 0 (the user payout). It does **not** commit to any other input or output, so it can legally be reused inside a completely different transaction built by any third party, together with that party's own funding inputs and an arbitrary OP_RETURN payload. The operator's real `withdraw()` flow illustrates exactly how the "extra" funding is added and only then wallet-signed with a normal (SIGHASH_ALL) signature that is specific to *that* operator's own transaction: [4](#0-3) 

Critically, this same construction is not gated to registered operators - it only requires: (1) the user's presigned dust-input signature, which is exposed publicly the moment the user submits it to Citrea's `safeWithdraw` contract call (an on-chain, publicly observable EVM transaction), and (2) the target operator's `xonly_pk`, which is public (`GetXOnlyPublicKey` RPC / on-chain reimbursement history). Both prerequisites are attacker-obtainable without any protocol role.

Once such a transaction confirms, the verifier's block-sync logic parses the OP_RETURN blindly and stores it as the payer of record with no check that the embedded key's owner actually supplied the funding inputs: [5](#0-4) 

This record is later trusted as ground truth by both the anti-fraud check that validates an operator's own kickoff: [6](#0-5) 

and by the operator's own automation, which decides whether to submit a `kickoff` (and thus claim `reimburse_tx`) purely by comparing the DB's stored payer key to its own signer key, with no verification of the actual transaction's funding inputs: [7](#0-6) 

The `reimburse_tx` pays the operator the deposited bridge amount from the `MoveToVaultTx` output as the reward for having fronted the withdrawal: [8](#0-7) 

### Impact Explanation
If an unprivileged party constructs and confirms a `payout_tx` that fronts the withdrawal using their own BTC but embeds a different, real operator's `xonly_pk` in the OP_RETURN (griefing, or race-condition front-running of the intended operator's own broadcast), the DB records that named operator as the payer of record. If that operator's automation later issues a `kickoff`/`reimburse_tx` for the corresponding deposit (as it is designed to do whenever it detects itself as payer), it receives the full bridge-amount reimbursement from the `MoveToVaultTx` UTXO despite never having spent any of its own funds on this withdrawal. This is BTC leaving a move-to-vault UTXO without a matching fronted withdrawal by the credited operator - a Critical-severity custody-binding break ("operator reimbursed for a payout it never funded").

### Likelihood Explanation
Reachability requires no privileged role: the user's presigned dust-input signature is exposed publicly via Citrea's `safeWithdraw` transaction before any operator broadcasts a matching Bitcoin payout, and target operator public keys are openly available. Building a competing `payout_tx` with `SIGHASH_SINGLE|ANYONECANPAY` reuse is standard Bitcoin script tooling. The only non-trivial requirement is winning the race to get the transaction confirmed before the legitimate operator's own broadcast and having the targeted operator's automation act on the (unverified) DB record without independent corroboration.

### Recommendation
Do not trust the OP_RETURN `operator_xonly_pk` as proof of payment provenance. Bind the payer attribution cryptographically to the actual funding, e.g., by requiring the payout transaction's non-dust funding input(s) to be spendable only by (or otherwise provably controlled by) the same `xonly_pk` embedded in the OP_RETURN, or by having the operator's automation independently verify (via wallet UTXO history / signature verification) that it, not merely the OP_RETURN text, actually supplied the funding inputs before submitting a kickoff for a given deposit.

### Proof of Concept
1. Wait for a user withdrawal request to be submitted to Citrea's `safeWithdraw` (publicly visible on-chain), extracting the dust-UTXO outpoint, output script/amount, and the `SinglePlusAnyoneCanPay` signature from the call data (see `get_citrea_safe_withdraw_params`, `core/src/test/common/citrea/parameters.rs:182-272`).
2. Build a new `payout_tx`: input 0 = the same dust UTXO + reused signature; output 0 = the required user payout (must match exactly per SIGHASH_SINGLE); additional input(s) = attacker's own BTC wallet UTXOs to cover the payout value; OP_RETURN = a real, targeted registered operator's `xonly_pk` (obtained via `GetXOnlyPublicKey`).
3. Sign the additional inputs with the attacker's own key (SIGHASH_ALL over the whole tx is fine, since the attacker constructed the whole tx) and broadcast it before the targeted operator (or any operator) broadcasts a competing payout for the same withdrawal.
4. Once confirmed, the verifier's `update_finalized_payouts` (`core/src/verifier.rs:2283-2352`) records the targeted operator as `payout_payer_operator_xonly_pk` for this deposit.
5. If/when the targeted operator's automation checks `validate_payer_is_operator` (`core/src/operator.rs:1686-1740`) and proceeds to kickoff, it is reimbursed the full bridge amount from the `MoveToVaultTx` output via `reimburse_tx` despite never funding the payout.

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}

        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };
