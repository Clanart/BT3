### Title
Unrestricted URI scheme passed to `shell.openExternal` from attacker-influenced links enables OS URI-handler abuse - (File: app/src/main-process/main.ts)

### Summary
The report's bug class is "a numeric/threshold guard exists but is not strict enough to stop the attacker-controlled input from causing damage" (`significantCollateralDrop` allows up to 90% pass-through). The closest verifiable Desktop analog is a similar under-strict guard at a trust boundary: the `open-external` IPC handler in the main process accepts *any* string as a destination for `shell.openExternal`, and only performs a cosmetic check (logging) for `http`/`https` — it does not reject or otherwise validate other URI schemes before handing the string to the OS shell.

### Finding Description
The main-process IPC handler for opening external links does this: [1](#0-0) 

The handler lower-cases the path only to decide whether to *log* it as "opening in browser" — it does not gate execution on the scheme. Any string reaching this handler, regardless of protocol (`file:`, `ms-msdt:`, `search-ms:`, `shell:`, vendor-specific handlers, or UNC-style `file://\\host\share` paths), is forwarded directly to Electron's `shell.openExternal`.

Renderer-side callers are inconsistent about pre-filtering the scheme before invoking this IPC path:
- `LinkButton` forwards `this.props.uri` straight to `shell.openExternal(uri)` with no protocol check: [2](#0-1) 
- Only one call site I could confirm — the sandboxed markdown renderer's click interceptor — restricts navigation to `http(s)` before calling out to `openExternal`: [3](#0-2) 

This means the http(s)-only restriction is opt-in per call site rather than enforced at the trust boundary (the IPC handler itself, which is the last line of defense before untrusted data reaches the OS shell). Any `LinkButton` or other component that renders a URL sourced from attacker-controlled data (e.g., a GitHub API object's homepage/URL field, a PR/issue link, or a repository-provided string) without itself re-validating the scheme will pass an arbitrary URI straight through to `shell.openExternal`.

This mirrors the reported bug-class exactly: a guard exists ("only log for http/https"), it looks like validation, but it doesn't actually block anything — just like `significantCollateralDrop` looks like a safety check but still lets 90% of value through.

### Impact Explanation
`shell.openExternal` with an attacker-chosen scheme is a well-documented Electron/desktop-app risk: URIs such as `ms-msdt:` (Follina, CVE-2022-30190), `search-ms:`, or crafted `file://\\attacker-host\share` UNC paths can trigger OS-registered handlers or NTLM credential leakage/relay without any additional user action beyond a single click that the user believes just opens a normal link. This can lead to remote code execution or credential exfiltration on the victim's machine — squarely within the requested impact categories (code execution / credential exfiltration via a link the user clicks).

### Likelihood Explanation
The path-traversal protections found elsewhere in the codebase (`resolveWithin`, `sanitizeCloneName`, `isClonePathSensitive` in `app/src/lib/git/clone.ts` and `app/src/lib/path.ts`) do not address this class of issue at all — they only prevent filesystem path escape during clone/file access, not URI-scheme validation for `shell.openExternal`. Because the scheme check is duplicated ad hoc per UI component (confirmed only in `sandboxed-markdown.tsx`) rather than centralized at the IPC boundary, any current or future call site that renders an attacker/API-sourced URL through `LinkButton` (or directly through `openExternal`) without its own scheme allowlist reintroduces the vulnerability. I was not able to fully enumerate every renderer call site that feeds untrusted data into `LinkButton`/`openExternal` before running out of iterations, so I cannot confirm a specific reachable attacker-controlled data source (e.g., which GitHub API field ends up in a `LinkButton`) — this is the main open uncertainty.

### Recommendation
- Enforce the `http:`/`https:` (and any other explicitly required, e.g. `mailto:`) allowlist inside the `open-external` IPC handler itself in `app/src/main-process/main.ts`, rejecting/refusing any other scheme unconditionally, rather than only logging.
- Audit every renderer call site that passes external, attacker/API-derived strings into `shell.openExternal`/`LinkButton` to confirm a scheme allowlist is applied before the IPC call, not after.

### Proof of Concept
Conceptual (not fully verified against a live attacker-controlled data source due to tool-call exhaustion):
1. An attacker crafts a GitHub object (e.g., a repository/PR field) whose URL value is `ms-msdt:...` or `file://\\attacker\share\x` instead of a normal `https://` URL.
2. If that value is rendered through a `LinkButton` (or any other component calling `shell.openExternal` directly) without a scheme check, clicking it invokes:
   `app/src/ui/lib/link-button.tsx:85` → IPC `open-external` → `app/src/main-process/main.ts:591` `shell.openExternal(path)`.
3. Because `main.ts`'s handler only *logs* for `http`/`https` and does not reject other schemes, the OS shell processes the malicious URI (e.g., triggering `ms-msdt.exe` or leaking NTLM credentials via SMB), all from a single click the user believed opened a normal link.

Because I could not confirm within the remaining iterations a concrete GitHub API field that reaches `LinkButton` unsanitized, treat the "Likelihood" section's caveat as the key remaining verification step for a background agent.

    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
