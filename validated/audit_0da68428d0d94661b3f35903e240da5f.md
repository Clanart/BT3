### Title
`Staking` post-condition coverage can be bypassed for `delegate-stack-stx` locks in PoX-4 — ([File: pox-locking/src/pox_4.rs])

### Summary
The `handle_stack_lockup_pox_v4` function only calls `global_context.log_stacking(&stacker, locked_amount)` — the call that records a lock into the Clarity `AssetMap`'s `stacking_map` — when `function_name == "stack-stx"`. For any other lock-causing function routed through the same handler (most notably `delegate-stack-stx`), the STX lock is applied via `pox_lock_v4` but the amount is never recorded into the asset map's stacking bookkeeping. [1](#0-0) 

### Finding Description
`check_transaction_postconditions` enforces `Staking` post-conditions by reading `asset_map.get_stacking(&principal)` for any explicit `TransactionPostCondition::Staking` clause, and separately enforces *coverage* (in `Deny`/`Originator` mode) by iterating `asset_map.get_all_stacking()` and requiring every principal that appears there to have been covered by an explicit `Staking` condition. [2](#0-1) [3](#0-2) 

This is the direct on-chain analog of `StakerVault.strategiesTotalStaked`/`_poolTotalStaked`: a side bookkeeping map that a protective check (post-conditions / reward eligibility) relies on, which is only updated on *some* of the code paths that actually move/lock the asset.

`handle_stack_lockup_pox_v4` is the special-case handler invoked whenever a PoX-4 contract call returns a stacking-lock result; it locks the STX via `pox_lock_v4` unconditionally, but only records the lock into the asset map's `stacking_map` when the triggering function name is literally `"stack-stx"`:

```
Ok(_) => {
    // For direct stacking, we log the locked amount in the asset map.
    if function_name == "stack-stx" {
        global_context.log_stacking(&stacker, locked_amount)?;
    }
    ...
``` [4](#0-3) 

Because the STX balance lock (`pox_lock_v4`) happens regardless of `function_name`, but the `AssetMap` entry used by the post-condition machinery is gated on `function_name == "stack-stx"`, any other function dispatched through this same handler (i.e., `delegate-stack-stx`, which also locks STX on behalf of `stacker` and is expected to hit this same `handle_stack_lockup_pox_v4` path per the PoX-4 dispatch logic) locks real STX for `stacker` without that lock ever appearing in `asset_map.get_stacking(stacker)` or `asset_map.get_all_stacking()`.

### Impact Explanation
This breaks the equality the `Staking` post-condition system is supposed to guarantee: "every STX amount actually locked by a principal in this transaction is checked against (or at minimum accounted for by) that principal's `Staking` post-conditions." Concretely:

- If `stacker` sets `TransactionPostConditionMode::Deny` (or `Originator`) expecting the coverage-enforcement loop to abort any uncovered staking action, a `delegate-stack-stx` call from a delegate that locks `stacker`'s STX will not populate `stacking_map`, so the coverage loop at lines 393‑407 of `crates/stacks-transactions/src/lib.rs` never sees the amount and never aborts the transaction — the lock silently commits even though it was supposed to be blocked/covered.
- Conversely, if the delegate constructs a transaction with an explicit `TransactionPostCondition::Staking(stacker, ...)` post-condition to satisfy some wallet UX check, `asset_map.get_stacking(&stacker)` returns 0 (not the locked amount), so the condition check at line 300 trivially passes with `amount_staked = 0` regardless of the actual amount locked — an asset (STX, now locked) moves in a way the post-condition was supposed to gate but does not actually verify.

This is an "asset moving past its post-conditions" class defect — the same class as the StakerVault report, where a bookkeeping variable relied on by a protective accounting mechanism was updated on one code path but not a sibling path that moves the same asset.

### Likelihood Explanation
Reachable by any unprivileged account acting as a PoX delegate: a delegate who has been authorized via `delegate-stx`/`stack-aggregation-commit` (or equivalent PoX-4 flow) can call `delegate-stack-stx` on behalf of a stacker who has authorized delegation, and this call path locks the stacker's STX through the same special-case handler as `stack-stx`, but is gated out of `log_stacking`. No miner, signer, or admin privilege is required — only a legitimate delegate role that is a normal, permissionless PoX mechanism.

### Recommendation
Update `handle_stack_lockup_pox_v4` (and check the parallel `pox_5.rs`/`pox_3.rs` implementations for the same pattern) to call `global_context.log_stacking(&stacker, locked_amount)` unconditionally whenever `pox_lock_v4` succeeds, regardless of `function_name`, so that every STX-locking path is reflected in the `AssetMap`'s stacking bookkeeping and therefore correctly enforced (or correctly reported) by `Staking` post-conditions.

### Proof of Concept
Conceptual PoC (exact test harness would need to be validated in a full checkout, since only the referenced snippet was inspected — see caveat below):
1. Stacker `A` delegates stacking rights to delegate `D` via the normal PoX-4 delegation flow.
2. `D` submits a contract-call transaction invoking `delegate-stack-stx` for `A`, with `post_condition_mode = Deny` and **no** `Staking` post-condition (or an explicit `Staking(A, SentEq, 0)` post-condition).
3. Expected behavior (per the intent of `TransactionPostCondition::Staking` coverage enforcement, as tested for `stack-stx` in `pox_5_integrations.rs`) is that the transaction aborts with `abort_by_post_condition` because the stake is uncovered.
4. Actual behavior: because `handle_stack_lockup_pox_v4` only calls `log_stacking` for `function_name == "stack-stx"`, the `delegate-stack-stx` lock never appears in `asset_map`'s stacking map, so the coverage-enforcement loop never flags it, and the transaction succeeds, locking `A`'s STX with the post-condition silently bypassed.

**Caveat**: I was not able to load the full `pox-locking/src/pox_5.rs` or the dispatcher that maps `delegate-stack-stx` to `handle_stack_lockup_pox_v4` in this session (tool calls to read those files failed to return content before the iteration limit). The finding is based on the confirmed snippet at `pox-locking/src/pox_4.rs:178-241`, the confirmed post-condition-enforcement code, and the fact that PoX-4's `delegate-stack-stx` and `stack-stx` both return the same `(stacker, locked-amount, unlock-height)` tuple shape consumed by `handle_stack_lockup_pox_v4`. A full confirmation that `delegate-stack-stx` is dispatched through this exact handler (rather than a separate one that already calls `log_stacking`) should be done by inspecting the dispatch table in `pox-locking/src/pox_4.rs` / `clarity/src/vm/contexts.rs` before treating this as fully proven.
