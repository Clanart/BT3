## Analysis

The `_debt_interest_since_last_update` bug is a precision-scaling defect: dividing by a base constant with insufficient decimal precision silently drops orders of magnitude, amplifying (or deflating) a financial quantity by a large power-of-ten factor while all guards remain silent. The closest local analog to this "silent decimal-mismatch amplification" pattern is in the `hyper-fungible-token` pallet's ERC20 ↔ local-balance decimal conversion helpers. [1](#0-0) 

### Title
Wrong-direction `saturating_sub` in `convert_to_erc20`/`convert_to_balance` silently skips decimal rescaling when local decimals exceed remote ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`. This expression is only correct when `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals` (a token registered with a lower ERC20 decimals count than the local asset's decimals, which is common — e.g. a 6-decimal ERC20 like USDC bridged against an 18-decimal local asset), `saturating_sub` clamps to `0`, making the scale factor `10^0 = 1`. The function then performs **no rescaling at all** in the direction that actually needs it, exactly mirroring the H-8 pattern of "dividing/multiplying by the wrong constant loses the actual precision delta."

### Finding Description
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
``` [2](#0-1) 

Both functions use the *same* one-directional exponent `erc_decimals.saturating_sub(local_decimals)`:
- `convert_to_balance` is documented as "Divides by 10^(erc_decimals - local_decimals) to scale down" — this is only valid for `erc_decimals >= local_decimals`.
- `convert_to_erc20` is documented as "Multiplies by 10^(erc_decimals - local_decimals) to scale up" — again only valid for the same direction.

Neither function handles the inverse case (`local_decimals > erc_decimals`) by dividing/multiplying by `10^(local_decimals - erc_decimals)`. `saturating_sub` returns `0` in that case, so the "scale factor" collapses to `1` and the raw numeric value crosses the decimal boundary completely unconverted — identical in nature to the Sherlock report dividing by `PERCENTAGE_BASE` (precision 2) instead of `PERCENTAGE_BASE_HIGH` (precision 5), silently dropping a factor of `10^n`.

### Impact Explanation
If a registered token pair has `local_decimals > erc_decimals` (e.g. local asset 18 decimals vs. a bridged ERC20 with 6 decimals — a very ordinary configuration, since USDC/USDT are 6-decimal), then:
- On the mint path (`convert_to_balance`), an inbound ERC20 amount is credited into the local balance with **no upscaling**, minting `10^(local_decimals - erc_decimals)` times **less** than the correct amount — locking/losing value for the depositor.
- On the redemption/withdrawal path (`convert_to_erc20`), a local balance debit is converted to an outbound ERC20 amount with **no downscaling**, sending out `10^(local_decimals - erc_decimals)` times **more** raw ERC20 units than backing exists — this is a direct, unauthorized over-payment that can drain the pallet's custodial reserve of the bridged asset on the EVM side (theft/loss of funds), matching the bug bounty's "unauthorized transaction... false state acceptance... direct loss of funds" criteria.

### Likelihood Explanation
Exploitability depends entirely on whether any token pair is (or can be) configured with `local_decimals > erc_decimals`. I could not fully confirm within this session whether `lib.rs`/`module.rs` enforce `erc_decimals >= local_decimals` at registration time — grep confirmed additional references to `erc_decimals`/`local_decimals` in `modules/pallets/hyper-fungible-token/src/lib.rs` and `module.rs` and in the pallet's test suite, but I did not have remaining iterations to read those files and verify whether a decimals-ordering invariant is enforced. **This is the key open question**: if registration permits `local_decimals > erc_decimals` for any token (which is the natural configuration when bridging a 6-decimal stablecoin against an 18-decimal local representation), this is directly and permissionlessly triggerable by any user who deposits/withdraws through that token pair — no malicious relayer, prover, or governance actor required.

### Recommendation
Replace the one-directional `saturating_sub` exponent with an explicit two-branch scale, and reduce duplication by sharing one directional helper:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
Apply the symmetric fix to `convert_to_erc20`, and add a regression test asserting round-trip correctness for `local_decimals > erc_decimals` configurations (e.g. 18 vs 6). Additionally, verify (and if absent, add) an explicit invariant check at token-pair registration time so this class of misconfiguration cannot silently exist.

### Proof of Concept
Given a registered pair with `erc_decimals = 6`, `local_decimals = 18`:
1. `convert_to_balance(U256::from(1_000_000u128), 6, 18)`: exponent = `6u8.saturating_sub(18) = 0` → divisor `10^0 = 1` → mints `1_000_000` local (18-decimal) units instead of the correct `1_000_000 * 10^12` units — depositor receives `10^-12` of deposited value.
2. `convert_to_erc20(1_000_000_000_000_000_000u128 /* 1.0 local token, 18dp */, 6, 18)`: exponent = `0` → multiplier `1` → returns raw ERC20 amount `1_000_000_000_000_000_000`, which on a 6-decimal ERC20 is `10^12` whole tokens instead of `1`, letting the withdrawer drain the pallet's ERC20 reserve by a factor of `10^12`.

Because I could not verify the decimals-registration invariant in the remaining time, I present this with an explicit caveat: **the vulnerability is real and provable from the helper functions' code as written; whether it is reachable in production depends on token-pair registration constraints in `lib.rs`/`module.rs` that I was unable to fully inspect before this session ended.** A Devin session with full repository access should verify `RegisterToken`/pair-setup logic in `modules/pallets/hyper-fungible-token/src/lib.rs` and `module.rs` to confirm whether `local_decimals > erc_decimals` is permitted for any live or governance-addable token pair.
