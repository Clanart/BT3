### Title
Invalid PedPoP proof-of-possession still leaks the recipient’s ECDH message key - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`KeyMachine::calculate_share` decrypts a supplied `EncryptedMessage` and creates a publishable `EncryptionKeyProof` before the queued proof-of-possession signature is actually verified. [1](#0-0)  If the decrypted plaintext is not a canonical scalar, the function returns immediately with `blame: Some(EncryptionKeyProof)`, skipping `batch.verify_with_vartime_blame` and therefore skipping the `Decryption` batch entry that would suppress blame for an invalid PoP. [2](#0-1)  The proof exposes `recipient_enc_key * attacker_supplied_key`, including when that key was copied from another participant’s encrypted share. [3](#0-2) 

### Finding Description
`EncryptedMessage::read` accepts untrusted bytes as a public `key`, a syntactically valid `SchnorrSignature`, and an encrypted `SecretShare`. [4](#0-3)  `Encryption::decrypt` only queues `msg.pop` into the supplied `BatchVerifier`; it does not authenticate the message before calculating the ECDH value and generating a DLEq proof for it. [5](#0-4) 

`calculate_share` then parses the decrypted bytes before executing the queued batch verification. [6](#0-5)  A non-canonical decrypted `SecretShare` causes `PedPoPError::InvalidShare { blame: Some(blame) }` via the `?` operator, so the invalid-PoP check at lines 493–499 is unreachable for that message. [7](#0-6) 

This defeats the protection described by the implementation itself: reusing someone else’s encryption key is supposed to fail the PoP check so no blame proof reveals that key’s ECDH value. [8](#0-7) 

### Impact Explanation
An attacker who observes an encrypted share from sender `A` to recipient `B` can submit a forged message to `B` containing the same `key` field, an arbitrary syntactically valid PoP, and a ciphertext whose decrypted bytes are non-canonical. [4](#0-3)  `B` returns an `EncryptionKeyProof` whose `key` is `B_enc_private * A_message_key`, and whose DLEq proves that value against `B`’s registered encryption public key. [3](#0-2) 

Because the ChaCha20 key is derived solely from the context and that ECDH point, the attacker can use the disclosed proof key to decrypt `A`’s original `EncryptedMessage`. [9](#0-8)  This reveals `A`’s secret share for `B`; collecting threshold-valid shares can lead to recovery of the shared private key material. [10](#0-9) 

### Likelihood Explanation
The attacker only needs to supply an `EncryptedMessage` reachable through `EncryptedMessage::read` / `calculate_share` and cause the recipient to emit the error’s blame object. [11](#0-10)  For a 255-bit scalar field such as Ristretto, a random 32-byte decryption is non-canonical with high probability, so malformed ciphertext can trigger the early return without knowing the plaintext. [12](#0-11)  The design explicitly considers observation and reuse of another participant’s key as an attack scenario. [13](#0-12) 

### Recommendation
Do not create or return an `EncryptionKeyProof` for a message whose PoP has not been verified. [5](#0-4)  The simplest fix is to synchronously call `msg.pop.verify` inside `Encryption::decrypt` before performing ECDH/decryption, returning no blame key for an invalid signature. [14](#0-13)  Alternatively, `calculate_share` must ensure all queued `BatchId::Decryption` signatures are verified before any malformed-plaintext error can include an encryption-key proof. [1](#0-0) 

### Proof of Concept
1. Recipient `B` registers encryption public key `E_B` through `Encryption::registration`. [15](#0-14) 
2. Sender `A` creates a normal `EncryptedMessage` to `B`; let its serialized `key` field be `K_A`. [16](#0-15) 
3. Attacker `E` sends `B` an `EncryptedMessage` containing `key = K_A`, any canonically encoded Schnorr `(R, s)`, and malformed encrypted-share bytes. [4](#0-3) 
4. `B` queues the forged PoP, computes `K = b * K_A`, decrypts the bytes, generates an `EncryptionKeyProof` containing `K`, and—if the decrypted share is non-canonical—returns it as `InvalidShare` blame before the queued PoP is verified. [5](#0-4) [7](#0-6) 
5. `E` uses `K` with the public DKG context to construct the same ChaCha20 cipher and XOR it with `A`’s original encrypted share, recovering the secret-share bytes. [9](#0-8)

  pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
    }
    batch.verify_with_vartime_blame().map_err(|id| {
      let (l, blame) = match id {
        BatchId::Decryption(l) => (l, None),
        BatchId::Share(l) => (l, Some(blames.remove(&l).unwrap())),
      };
      PedPoPError::InvalidShare { participant: l, blame }
    })?;

/// An encrypted message, with a per-message encryption key enabling revealing specific messages
/// without side effects.
#[derive(Clone, Zeroize)]
pub struct EncryptedMessage<C: Ciphersuite, E: Encryptable> {
  key: C::G,
  // Also include a proof-of-possession for the key.
  // If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X,
  // then send Bob a message also claiming to use X.
  // While Eve's message would fail to meaningfully decrypt, Bob would then use this to create a
  // blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob.
  // This is a massive side effect which could break some protocols, in the worst case.
  // While Eve can still reuse their own keys, causing Bob to leak all messages by revealing for
  // any single one, that's effectively Eve revealing themselves, and not considered relevant.

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
