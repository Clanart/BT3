### Title
Attacker-controlled bytes passed to `ThresholdKeys::read` instantiate a fully attacker-chosen key set (arbitrary group key with no binding between `secret_share` and `verification_shares`), enabling theft of funds sent to the resulting `group_key` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes `t`, `n`, `i`, the interpolation method (including attacker-supplied `Constant` coefficients), the `secret_share`, and all `n` verification shares entirely from the input byte stream. `ThresholdKeys::new` (which `read` calls) never verifies that `verification_shares[i] == C::generator() * secret_share`, never checks verification shares for identity/non-canonical points beyond `read_G`, and requires no proof of possession. The `group_key` is then computed purely from the attacker-supplied verification shares (`sum over participants 1..=t` of `verification_shares[i] * interpolation_factor`). This is the direct analog of the LFI bug class: just as `/reinstall_extension` concatenated an attacker string into a path and loaded whatever it pointed at, `ThresholdKeys::read` loads whatever keys the attacker bytes describe, with no authenticity check on which key material is loaded.

### Finding Description
In `ThresholdKeys::read` ( [1](#0-0) ), every field defining the multisig is taken verbatim from the reader:

- `t`, `n`, `i` are read as raw `u16`s (only `i != 0` is checked at parse time; `ThresholdParams::new` later checks `i <= n` and `t <= n`, but nothing else).
- The interpolation selector byte picks `Constant(Vec<F>)` — `n` attacker-chosen coefficients — or `Lagrange`.
- `secret_share` is a bare `read_F`.
- `verification_shares` are `n` bare `read_G` points.

`ThresholdKeys::new` ( [2](#0-1) ) then computes `group_key` by interpolating participants `1..=t` over those supplied verification shares. Critically:

1. There is no check that `C::generator() * secret_share == verification_shares[&i]`. The loaded object's claimed identity (`i`) and its secret are unbound from the public key material.
2. There is no PoP/proof that the loader knows the discrete log of any verification share, so an attacker can encode a polynomial/key whose **group secret it fully knows** while presenting it as the victim's threshold key.
3. `Interpolation::Constant` requires `t == n`, but `Interpolation::Lagrange` accepts any `t`, so the attacker controls the threshold semantics too.

The consumed result (`group_key()`) is what integrators (e.g. bitcoin-serai via `register_offset`/TapTweak, or any deposit-address derivation) use as the receive address.

### Impact Explanation
If an integrator loads `ThresholdKeys` from bytes an unprivileged party can influence (the rules expressly list `ThresholdKeys::read` as an accepted untrusted-bytes sink), the attacker supplies a serialization where:

- `verification_shares[1..=n]` are `G * s_j` for attacker-generated Shamir shares `s_j` of a secret `x` the attacker knows, with `secret_share = s_i` embedded so the object is self-consistent and even produces valid signature shares.

The victim then derives `group_key() = G*x` as its deposit/treasury address. **The attacker already knows `x`** — they can spend every coin sent to that key unilaterally, without any threshold signing at all. This is "funds reported received that are not spendable [by Serai]" — the strongest accepted impact — achieved purely through deserialization of untrusted bytes, exactly mirroring the LFI primitive (attacker-chosen input → loads attacker-chosen executable/key material).

A secondary impact: the attacker can instead make `verification_shares[i]` inconsistent with `secret_share`, so the victim signs shares that fail `verify_share`, or set `group_key` to a point unrelated to the embedded shares — a denial-of-service / confused-deputy on the signing pipeline.

### Likelihood Explanation
Reachability requires an integrator to pass untrusted bytes into `ThresholdKeys::read`. Within the audit's threat model this sink is explicitly in scope (it is listed among the accepted `read_*` sinks). The format embeds a curve `ID` check, which prevents cross-curve confusion but does nothing against same-curve malicious payloads. No malicious validator, colluding threshold, or leaked key is required — the attacker only needs to control the serialized bytes. Exploitation is deterministic once the bytes are loaded.

### Recommendation
- In `ThresholdKeys::new` (or at the end of `read`), enforce `verification_shares[&params.i()] == C::generator() * secret_share`. This binds the claimed participant index and secret to the public material, rejecting keys where the loader's share doesn't match its verification share.
- Document that `ThresholdKeys::read` must only be used on trusted/authenticated storage, and preferably gate it behind an explicit `unsafe`/authenticated-reader API — a serialized blob alone cannot prove the loader legitimately participated in a DKG for the encoded `group_key`.
- Reject identity verification shares (`share.is_identity()`) for all `n` shares during deserialization.
- For `Interpolation::Constant`, note the current `t == n` check is correct but the coefficients themselves remain attacker-chosen; the `secret_share`-to-verification-share binding is what makes them harmless.

### Proof of Concept
```rust
// Attacker crafts serialized ThresholdKeys for a group secret it knows
// (conceptual; uses frost/dkg public APIs)

// 1) Attacker generates a polynomial of degree t-1 with constant term x
//    (the group secret the attacker will keep).
//    s_i = poly(i) for i in 1..=n; verification_shares[i] = G * s_i.

// 2) Attacker serializes per ThresholdKeys::write layout:
//      u32 len of C::ID || C::ID || t || n || i || interpolation byte (1) ||
//      s_i.to_repr() || verification_shares[1..=n] points
let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(t.to_le_bytes());
buf.extend(n.to_le_bytes());
buf.extend(i.to_le_bytes());        // victim's participant index
buf.push(1u8);                      // Interpolation::Lagrange
buf.extend(s_i.to_repr().as_ref()); // consistent share for index i
for j in 1..=n {
    buf.extend((G * s[j]).to_bytes().as_ref());
}

// 3) Victim integrator loads it
let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();

// keys.group_key() == G * x  -> used as the deposit/taproot address
// Attacker knows x and sweeps all deposits without any FROST round.
```

Note: `read` succeeds because `ThresholdParams::new` passes (`t <= n`, `i <= n`), verification share count matches `n`, and no share-to-secret consistency check exists ( [3](#0-2) ).

*Uncertainty caveat:* the finding's severity hinges on an integrator feeding untrusted bytes to `ThresholdKeys::read`; within Serai itself, processors load keys from their local DB, so real-world exploitability depends on deployment-specific input paths to this sink. The missing consistency check in `ThresholdKeys::new`/`read` is confirmed by the code above.

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }

    {
      let different = || io::Error::other("deserializing ThresholdKeys for another curve");

      let mut id_len = [0; 4];
      reader.read_exact(&mut id_len)?;
      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }
