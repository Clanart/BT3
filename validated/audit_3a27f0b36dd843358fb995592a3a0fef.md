## Analysis

The Gravity bug is a class of "recorded/trusted value diverges from ground truth" issue: the contract records `_amount` (a value it computed itself) as fact instead of verifying it against what actually happened (`balanceOf` diff), and that unverified record becomes what downstream logic (Cosmos minting) permanently trusts.

The closest concrete analog in this Desktop codebase is in the Copilot-assisted merge-conflict resolution feature, where Desktop reconstructs "ours"/"theirs" hunk boundaries by naive regex line-matching against file content instead of verifying those matches are actually git-inserted conflict markers, and then blindly splices the model's output back into the file it writes to disk and stages for commit.

### Title
Naive conflict-marker line matching in Copilot conflict resolution lets attacker-controlled branch content desynchronize hunk boundaries, causing Desktop to silently write and stage corrupted merge results — (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
When resolving conflicts with Copilot, Desktop extracts "ours"/"base"/"theirs" content by scanning the raw conflicted file for lines matching `^<{7}`, `^\|{7}`, `^={7}$`, `^>{7}` [1](#0-0)  in `extractConflictHunks` [2](#0-1) . After the model responds, `reassembleResolvedFile` independently re-scans the same raw content with a second, separately-defined set of marker regexes to find where to splice the model's resolved content back in [3](#0-2) . Neither pass verifies that a matched line is an actual git-inserted conflict marker (which always carries a branch/ref label, e.g. `<<<<<<< HEAD`) — the regexes accept any bare 7-character line of `<`, `=`, or `>` as a boundary. If a file's real "ours" or "theirs" content (e.g. code, docs, or test fixtures that legitimately contain a 7-character `=======`/`<<<<<<<`/`>>>>>>>` line, such as ASCII dividers, RST underlines, or literal example conflict markers in documentation/test files) collides with this pattern, the hunk boundaries computed by the two independent scanners no longer correspond to the real git conflict boundaries. The two counts still agree with each other (since both scanners use the same flawed heuristic), so `validateResolutionPaths`'s hunk-count check [4](#0-3)  passes even though the semantic boundaries are wrong.

### Finding Description
- `extractConflictHunks` builds the "ours"/"theirs" content that is sent to the LLM by scanning line-by-line and terminating "ours" content on the first line matching `separatorMarker` or `baseMarker`, without verifying the line is a genuine git marker with a following label [5](#0-4) .
- `reassembleResolvedFile` performs a second, independently coded scan over the same raw file to find `<<<<<<<` / `=======` / `>>>>>>>` boundaries to splice the model's `resolvedContent` back in, again accepting any bare matching line [6](#0-5) .
- The only integrity check between the model's output and the on-disk file is a count comparison (`resolution.hunks.length !== expectedCount`) [7](#0-6) . There is no verification that the *content* boundaries used for extraction match the boundaries used for reassembly against git's actual conflict-region semantics — analogous to Gravity trusting `_amount` without checking the actual balance delta.
- The reassembled result is written directly to disk and staged with `git add` with no diff review or further validation: `await writeFile(absolutePath, resolution.resolvedContent, 'utf8')` followed immediately by `git(['add', ...])` [8](#0-7) .
- The only pre-write guard is a check that the file still has unresolved conflict markers (skips if the user already resolved it manually) [9](#0-8)  — this does not detect boundary-desynchronization corruption, since the file will still show conflict-marker-like content either way.

### Impact Explanation
A malicious branch/PR that a victim merges, rebases onto, or cherry-picks from can shape the surrounding conflicted content so that a spurious boundary line is present inside the real "ours" or "theirs" region. Because both the extraction pass (what gets shown to the LLM) and the reassembly pass (what gets spliced into the committed file) misparse the same way, the check in `validateResolutionPaths` cannot catch the mismatch — it only compares counts, not semantic correctness. The user, believing the AI correctly merged the code, clicks "Continue Merge", and Desktop silently writes and `git add`s a file whose content differs from a correct three-way merge (dropped code, duplicated code, or code moved across the ours/theirs boundary) without any diff being shown for review at that point. This is "silent corruption of what the user commits/pushes" — the same failure class as Gravity minting vouchers based on an unverified `_amount` rather than the actual delivered balance.

### Likelihood Explanation
Exploitation requires only that the attacker control content on one side of a merge (a PR branch, a fork the user pulls from, or a file introduced upstream) — no local access, no credentials, and no unusual user action beyond the normal "Resolve with Copilot" flow that Desktop already offers on conflicts. The trigger condition (a bare 7-character `<`/`=`/`>` line inside real content) is a narrow but realistic occurrence in real-world files (ASCII dividers, RST/Markdown headers, or files about git tooling/tests containing literal example markers). This is a design gap (no real marker validation) rather than a probabilistic race, so once the crafted content exists in the merge, corruption is deterministic on every "Resolve with Copilot" run.

### Recommendation
- Validate that matched marker lines are genuine git-inserted markers (require the trailing label that git always appends, e.g. `<<<<<<< <ref>` / `>>>>>>> <ref>`), rather than accepting any bare 7-character run.
- Cross-check the extraction result against `git`'s own understanding of the conflict (e.g., derive hunk boundaries from `git merge-file`/`git diff3` output or count markers using the same authoritative parser used elsewhere in Desktop for status, rather than a bespoke ad hoc scanner duplicated in two files).
- Before staging, diff the reassembled file against the two side-versions to confirm no non-conflicted lines were altered, and surface the resulting diff to the user for review prior to `git add`.

### Proof of Concept
1. Create a file `notes.md` whose content — identical on both branches outside the conflicting hunk — includes a horizontal rule line consisting of exactly `=======` (a common Markdown/RST divider), positioned within the region that will end up inside a real conflicting hunk.
2. On branch `feature`, modify a nearby line to create a genuine conflict with `main` at that same hunk.
3. In Desktop, start a merge of `feature` into `main`, triggering a conflict, and click "Resolve with Copilot".
4. `extractConflictHunks` and `reassembleResolvedFile` will each independently, but consistently, treat the divider line as a marker boundary, causing the model to receive and later splice content into the wrong region.
5. Click "Continue Merge" — Desktop writes the corrupted result via `writeFile` and stages it via `git add` [8](#0-7)  with no further diff shown, and the user commits/pushes content that silently differs from a correct merge.

Note: I could not execute the app to empirically confirm the exact malformed-marker line will always desynchronize in every git conflict-style configuration (e.g. `merge.conflictStyle=diff3` vs default), since I only have static code access (no filesystem/terminal execution here). The code-level absence of marker-authenticity validation and the shared, duplicated ad hoc parsing logic across the two files is confirmed directly from source.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }

// Conflict markers used by reassembleResolvedFile to locate marker blocks.
const reassemblyOursMarker = /^<{7}(?:\s|$)/
const reassemblySeparatorMarker = /^={7}$/
const reassemblyTheirsMarker = /^>{7}(?:\s|$)/

/**
 * Reassemble a fully resolved file by splicing per-hunk resolutions into
 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
 */
export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }
