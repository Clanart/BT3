### Title
`DLEqProof::verify` accepts a proof bound to attacker-controlled identity points — the challenge does not bind the witness, enabling a universal forgery - (File: crypto/dleq/src/lib.rs)

### Summary
The external report describes a "verification bypass": a callback reports authentication success while no cryptographic object actually binds the check to a secret. The Serai analog is `DLEqProof::verify`. The Schnorr-style verification recomputes each nonce as `R_i = s·G_i − c·P_i` and transcripts `R_i` before comparing `self.c` to the resulting challenge. Because the challenge is a pure function of `(generators, R_i(s), points)` — and not of anything the verifier independently commits to — a prover who can cause the checked `points` to be the identity element reduces each statement to `R_i = s·G_i`, computes the exact challenge the verifier will derive, and returns `Ok(())` with a fully forged proof. No discrete logarithm is ever proven.

### Finding Description
In `DLEqProof::verify` the verifier loops over `(generator, point)` pairs calling `verify_statement`, which recomputes the nonce point as `(generator * s) - (point * c)` and transcripts it, then checks `self.c == challenge(transcript)`. [1](#0-0)  The recomputed nonce is `s·G − c·A`; when `A` (the attacker-supplied `point`) is the identity, this collapses to `s·G` — a value the attacker computes offline for a freely chosen `s`. [2](#0-1)  The attacker then replays the transcript (generators, `s·G_i`, identity points are all known/predictable) to obtain `c`, and outputs `DLEqProof { c, s }`. Verification re-derives the identical `R_i` values, hence the identical challenge, and returns `Ok(())` — a forged proof that the points share a discrete logarithm when no such relationship was established. The same forgery works trivially when `generators.is_empty()` (challenge is over an empty, fully predictable transcript). The canonical-encoding `read` path (`DLEqProof::read`) imposes no additional constraint. [3](#0-2)  This proof type is consumed by the DKG generator-promotion path, which calls `DLEqProof::verify` on points derived from deserialized key material (`crypto/dkg/promote/src/lib.rs`), and `ThresholdKeys::read`/`read_G` accept the identity encoding for `PrimeGroup` ciphersuites, making the identity point reachable from untrusted bytes.

### Impact Explanation
An unprivileged party supplying a `DLEqProof` together with a malicious point set (identity points obtained via `read_G`/`ThresholdKeys::read` in the generator-promotion flow) produces a proof that verifies without knowledge of any discrete logarithm. This is a forged proof: the verifier's "success" signal (`Ok(())`) carries no cryptographic binding to a witness, exactly mirroring the HAL-18 class where `onAuthenticationSucceeded` grants access without the `CryptoObject` ever being validated.

### Likelihood Explanation
Requires the verifier to evaluate `verify` over attacker-influenced `points`/`generators` and for the point encodings to permit the identity element (canonical for `PrimeGroup` implementations such as the kp256/dalek-ff-group ciphersuites). In the generator-promotion use of `DLEqProof`, the points are derived from supplied key material, which an untrusted counterparty controls. Medium likelihood.

### Recommendation
Mirror the report's fix: require the "CryptoObject" equivalent — an explicit, verifier-committed binding — before accepting success.
1. Reject the identity element in `verify` for both `generators` and `points` (and in `read`/deserialization paths feeding verification), since an identity `point` removes `c·A` from the statement entirely.
2. Reject empty `generators`/`points` lists.
3. Optionally transcript `self.c` and `self.s` (or a prover nonce commitment) inside the domain-separated transcript so the challenge is bound to the proof bytes themselves, not only to values the prover can predict.

### Proof of Concept
For any generator set `G_1..G_k` where the verifier will check points `P_i` supplied (directly or via deserialization) by the prover:

1. Set every `P_i = identity` (identity encodes canonically for prime-order groups, so `read_G` accepts it).
2. Choose arbitrary `s ∈ F`. Compute `R_i = s·G_i` locally.
3. Clone the verifier's transcript, apply `domain_separate(b"dleq")`, append `generator`, `R_i`, `point` for each `i` exactly as `verify_statement` does, and read `c = challenge(transcript)`. [4](#0-3) 
4. Output `DLEqProof { c, s }` via `write`/`serialize`.

During `verify`, each statement recomputes `s·G_i − c·identity = s·G_i = R_i`, reproducing the identical transcript, so `self.c == challenge(transcript)` and `verify` returns `Ok(())` — a valid-looking DLEq proof over garbage points with no witness. The analogous empty-statement variant (k = 0) yields the domain-separator-only challenge, which is likewise fully predictable.

```rust
  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[G],
    points: &[G],
  ) -> Result<(), DLEqError> {
    if generators.len() != points.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"dleq");
    for (generator, point) in generators.iter().zip(points) {
      Self::verify_statement(transcript, *generator, *point, self.c, self.s);
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }

    Ok(())
  }
```
