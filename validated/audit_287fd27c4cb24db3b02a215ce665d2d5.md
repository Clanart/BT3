## Analysis

The external report's core invariant: **a protocol computes a value in "USD" terms and converts it into a base/fee token using only decimal scaling, silently assuming 1 token unit = $1 USD, with no price reference to the token's actual market value.**

The closest local analog in Hyperbridge is `BandwidthManager.purchase()`.### Title
`BandwidthManager.purchase()` assumes the host's fee token is worth exactly $1 USD when scaling 18-decimal tier prices - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.purchase()` converts a governance-set 18-decimal "USD" tier price into the local fee token amount using pure decimal arithmetic, with no reference to the fee token's actual market value. This is the same broken invariant as the `OperationalTreasury` report: a USD-denominated amount is transferred in a base/fee token while assuming 1 unit of that token == $1, with no oracle or peg check.

`tierPrice[tier]` is an 18-decimal value that governance intends to represent a USD price (docs explicitly describe tiers as "$50", "$100", etc., and instruct governance to "keep prices in sync" across every chain since "the same SKU costs different amounts depending on which chain a buyer is on" if not). The contract's only adjustment for cross-chain/cross-token differences is `10 ** (18 - dec)` — a pure decimal-precision rescale. There is no Chainlink feed, no peg assertion, and no check that `IDispatcher(_host).feeToken()` is in fact a $1-pegged stablecoin, unlike `SimplexPaymaster`, which explicitly reads a Chainlink oracle for both the native asset and the accepted ERC-20 before pricing: [2](#0-1) 

Because `feeToken()` is a per-chain configuration value (any ERC-20 the host is configured with), and `BandwidthManager` performs no validation that this token holds a $1 value, any depeg of the configured fee token, or any deployment where the fee token is not actually a USD stablecoin, causes every buyer to pay an amount whose real USD value diverges from the tier price governance intended. Because tier prices are pushed identically (in 18-decimal "USD" units) to every chain's manager via `SetTiers`: [3](#0-2) 

the protocol's tier economics are silently wrong on any chain whose fee token is mispriced relative to $1 — exactly the class of bug the source report describes (`_takeFeesLockLiquidity` transferring `premium + fees` computed in USD terms directly in a token assumed to be worth $1).

### Impact Explanation
If the configured `feeToken` for a chain is not tightly pegged to $1 (e.g., it depegs, or is a non-stable ERC-20 the host happens to use as its fee token), buyers on that chain receive the exact same bandwidth allowance (bytes × duration) for a real USD cost far below (or above) what governance intended. This is a direct, unprivileged, protocol-level fund-value loss: the treasury systematically under-collects real value relative to the byte allowance it grants, and any user can repeatedly exploit the mispriced chain to acquire disproportionately large bandwidth credits for the same nominal fee-token spend. No malicious relayer, prover, or governance action is required — only a normal `purchase()` call against a chain whose fee token is not exactly $1.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires either (a) a depeg event in the deployed fee token, or (b) a chain where governance/deployment configures a non-$1 ERC-20 as the fee token — both plausible given `feeToken()` is fully configurable per-chain and the contract enforces no invariant on its value.

### Recommendation
Do not treat `IDispatcher(_host).feeToken()` implicitly as a $1 stablecoin. Either (a) restrict `feeToken()` to audited, tightly-pegged stablecoins with an on-chain enforcement/allowlist, or (b) introduce a price oracle (as `SimplexPaymaster` already does for gas pricing) to convert the 18-decimal USD tier price into the correct fee-token amount at purchase time, reverting or reflecting the real price if the oracle reports significant deviation from $1.

### Proof of Concept
1. Governance calls `dispatch_set_tiers` pushing `TierOne = 50e18` ("$50") to `BandwidthManager` on Chain X, where Chain X's host `feeToken()` returns a token `T` that is *not* pegged to $1 (e.g., it trades at $0.10, or later depegs from an intended $1 peg).
2. Any user calls `purchase(app, TierOne, 1, chain)`. The contract computes `amount = 50e18 / 10**(18-dec)`, i.e., exactly 50 units of token `T` (scaled to its decimals) — with no adjustment for `T`'s real market value.
3. The user pays 50 `T` (worth $5 at $0.10/T) and receives the full `TierOne` byte allowance that governance intended to cost $50, a 10x underpayment relative to the intended USD price, while identical tier allowances issued on chains with correctly pegged fee tokens cost the full $50. [4](#0-3)

        external
        returns (bytes32 commitment)

        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();

        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
