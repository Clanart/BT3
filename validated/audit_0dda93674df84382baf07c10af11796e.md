### Title
Staleness gate is bypassed for future-timestamped price feeds, permanently locking out fresh price updates - (File: `local-testing/contracts/market/market.clar` / `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The oracle freshness check in `market.clar` treats any price whose reported timestamp is ahead of the current Stacks block time as automatically "fresh" (`delta = u0`), regardless of how far in the future that timestamp is. Combined with the strict monotonic-timestamp requirement `(>= ts prev)` and the fact that `last-update` is only ever advanced, never corrected, a single future-dated (or clock-skewed) publish can permanently poison the per-feed `last-update` state, after which all subsequent legitimate, correctly-timestamped price updates for that feed are rejected forever — mirroring the Taiko bug class where a state value can never be "re-proven"/corrected once written.

### Finding Description
`oracle-timestamp-fresh` is defined identically in both `local-testing/contracts/market/market.clar:387-393` and `mainnet/contracts/market/v0-4-market.clar:365-371`: [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

If the reported price timestamp `ts` is greater than the current `stacks-block-time`, `delta` is forced to `u0`, which always satisfies `(<= delta max-staleness)`. This means *any* future-dated timestamp — whether from ordinary clock drift between Pythnet and the Stacks chain, or an inflated/incorrect timestamp — is unconditionally treated as maximally fresh, defeating the entire purpose of the `max-staleness` gate for that update.

This check feeds directly into `price-resolve`, used by every price lookup in the protocol: [2](#0-1) 

```clarity
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        ...
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)
    (ok final-price)))
```

Two compounding problems create the "cannot re-prove/correct" condition:
1. `last-update` (`local-testing/contracts/market/market.clar:394-396` doc reference) is a per-feed monotonic high-water-mark; it is only ever advanced (`if (> timestamp last-update-time) (map-set last-update key timestamp) false)`), never rolled back.
2. Once a future-dated timestamp is accepted and stored as `last-update`, every subsequent — correctly, honestly timestamped — publish will have `ts < prev` (the poisoned high value), failing `(>= ts prev)` and reverting with `ERR-ORACLE-INVARIANT` on every future call, with no admin/DAO function found in the codebase to reset or override `last-update` for a feed. The only equivalent of the Taiko report's "upgrade before the cooling window expires" workaround here would be a full contract upgrade.

Unlike the Taiko bug (guardian tier `contestBond == 0` vs `== 1`), the flaw here is not a strict-equality bug but a bypass condition (`> ts stacks-block-time → delta = 0`) that produces the same category of outcome: an unrecoverable, self-inflicted staleness/monotonicity lock that neither users nor the DAO can undo on-chain.

### Impact Explanation
Two related but distinct impacts:
- **Wrong price / wrong health verdict while poisoned**: Any price update whose `ts` exceeds `stacks-block-time` is accepted as "fresh" no matter how old the actual data is meant to represent, since the staleness distance is zeroed out rather than bounded. A price that should have failed the `max-staleness` check for its asset can be used to compute collateral/debt USD values in `get-notional-evaluation`/`liquidate` paths, leading to incorrect LTV and liquidation determinations (`local-testing/contracts/market/market.clar:1444-1458` / `mainnet/contracts/market/v0-4-market.clar:1422-1435`), which can allow under-collateralized borrows or block/allow liquidations incorrectly.
- **Permanent freezing of the feed**: once a future timestamp is stored in `last-update`, all later genuine updates for that asset's feed are rejected forever (`(>= ts prev)` fails), causing `price-resolve`/`price-multi-resolve` to permanently revert for any operation that needs that asset's price (borrow, withdraw, liquidate). This is a temporary/permanent freezing-of-funds condition for all positions holding that asset, since no user or liquidation action involving it can proceed without a contract upgrade to reset state.

This lands in the in-scope **High** (temporary freezing of funds) to **Critical** (protocol insolvency via bad debt from wrong health verdicts, or permanent freezing) impact bands depending on which asset feed is affected and how the wrong valuation is exploited before or after the lock occurs.

### Likelihood Explanation
Reaching the initial "poisoning" state does not require a malicious third party controlling Pyth/DIA signing keys — it can occur from ordinary, expected clock skew between the Pythnet network's `publish-time` and the Stacks chain's `stacks-block-time` (independent clocks/block cadences), which is a routine and foreseeable operating condition rather than a third-party data-integrity failure. Because the vulnerable logic lives entirely in Zest's own `oracle-timestamp-fresh`/`price-resolve` code (not in the Pyth/DIA oracle contracts), this is squarely an in-scope, first-party logic bug reachable under normal operation, not "bad third-party oracle data."

### Recommendation
- Do not zero out the staleness delta when `ts > stacks-block-time`. Either reject/clamp such timestamps with a small tolerance bound (e.g., a max allowed clock-skew constant) instead of `u0`, or compute `delta` as `(if (> ts stacks-block-time) (- ts stacks-block-time) (- stacks-block-time ts))` and bound the absolute skew by `max-staleness` (or a dedicated future-skew constant) in both directions.
- Add a DAO-guarded recovery function to reset/override a poisoned `last-update` entry per feed, analogous to fixing the Taiko `contestBond == 1` re-prove check, so an erroneous high timestamp does not permanently brick a feed.
- Add a unit test asserting that a future-dated (or manipulated) timestamp cannot be used to bypass `max-staleness`, and that once accepted, an update with a normal, correct timestamp can still be applied afterward (i.e., the feed is recoverable).

### Proof of Concept
1. A price update arrives via Pyth (or DIA/mock) with `publish-time = T_future`, where `T_future > stacks-block-time` at the time of the Stacks transaction (plausible under normal Pythnet/Stacks clock drift, or if a relayer/mock resubmits with an inflated timestamp).
2. `price-resolve` calls `oracle-timestamp-fresh(T_future, prev, max-staleness)`; because `T_future > stacks-block-time`, `delta = u0`, so `(<= delta max-staleness)` is trivially true, and `(>= T_future prev)` also holds (assuming `T_future` is the largest timestamp seen so far).
3. The update is accepted, and `last-update` for that feed is set to `T_future` via `(map-set last-update key timestamp)`.
4. Any subsequent legitimate publish with a normal (lower) timestamp `ts_next < T_future` now fails `(>= ts_next prev)` inside `oracle-timestamp-fresh`, causing `price-resolve` to hit `(asserts! ... ERR-ORACLE-INVARIANT)` and abort every borrow/withdraw/liquidate call that needs this asset's price, with no on-chain function available to reset `last-update`.
