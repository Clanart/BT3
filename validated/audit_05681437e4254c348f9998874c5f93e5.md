## Title
Division by zero in `consolidatedNode.Split()` when both CN and CL staking amounts truncate to zero, causing consensus-critical panic during block reward distribution - (File: kaiax/staking/staking_info.go)

### Summary
The `RGBtoXYZ()` divide-by-zero pattern in the OSV report (unchecked divisor in a fee/ratio-style calculation) has a structural analog in Kaia's reward-splitting code. `consolidatedNode.Split()` divides by `totalAmount = CNStakingAmount + CLStakingAmount` without verifying it is non-zero, and this function is invoked unconditionally on the block proposer's node during every deferred-reward computation.

### Finding Description
`consolidatedNode.Split()` computes the proportional split of a reward amount between a validator's CN staking and its consensus-liquidity (CL) staking pool: [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}
	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)
	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)   // <-- unchecked divisor
	...
}
```

`totalAmount` is only guarded by the `c.CLStakingInfo == nil` branch; there is no check that `c.StakingAmount + c.CLStakingInfo.CLStakingAmount > 0`. Both quantities are derived via lossy integer truncation to whole KAIA units: [2](#0-1) 

Any staking amount less than 1 KAIA (10^18 kei) truncates to `0` in `StakingAmount`/`CLStakingAmount`. This function is called unconditionally for the block proposer's consolidated node in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex`, which is executed on **every block's** deferred reward computation (`FinalizeState`), with no minimum-stake filter applied to the proposer's own node lookup: [3](#0-2) 

```go
cns := si.ConsolidatedNodes()
for _, cn := range cns {
    if cn.RewardAddr != config.Rewardbase {
        continue
    }
    if cn.CLStakingInfo == nil {
        break
    }
    cnAmount, clAmount := cn.Split(proposer)   // divide-by-zero if both amounts truncate to 0
    ...
}
```

Note this path does **not** check `cn.StakingAmount >= minStake` before calling `Split`, unlike the eligibility filters used elsewhere (`assignStakingRewards`/`assignStakingRewardsFlex`) which only call `Split` for CNs whose staking amount already exceeds `minStake`: [4](#0-3) 

### Impact Explanation
`big.Int.Div` by a zero divisor panics in Go. If this panic occurs inside `FinalizeState()`/deferred reward processing — which runs identically on every full node processing a block — it would crash all nodes processing that block simultaneously, halting the chain (denial of availability), matching the "Availability: High" impact of the reference CVE. This maps to the "state transition and gas/burn accounting" / "reward redirection" category in scope.

### Likelihood Explanation
Reaching this requires the elected block proposer's consolidated node to have `CLStakingInfo != nil` while both its CN `StakingAmount` and CL `CLStakingAmount` truncate to `0` KAIA. This is only possible if proposer/validator eligibility (enforced in `kaiax/valset`) does **not** require the CN's own `StakingAmount` to be above 0 independent of CL stake — I was unable to fully confirm within the available tool budget whether `kaiax/valset`'s qualification logic (e.g., `getter_context.go`) enforces `StakingAmount >= minStake` strictly on the CN-only amount before allowing a node to become proposer, since typical `minStake` defaults (e.g., 5,000,000 KAIA) would normally prevent CN amount from truncating to zero. This is the main open uncertainty limiting confidence to Medium likelihood.

### Recommendation
Add an explicit zero-check in `consolidatedNode.Split()` before dividing:
```go
if totalAmount.Sign() == 0 {
    return amount, big.NewInt(0) // or big.NewInt(0), amount, depending on desired fallback
}
```
Additionally, apply the same `StakingAmount >= minStake` eligibility check used in `assignStakingRewards`/`assignStakingRewardsFlex` before invoking `Split()` on the proposer's node in `specWithProposerAndFunds`/`specWithProposerAndFundsFlex`.

### Proof of Concept
Conceptual (not verified end-to-end due to tool budget limits on confirming proposer-eligibility constraints):
1. Register a CN in `AddressBook` whose `CNStakingAmount` is below `1 KAIA` (truncates to `StakingAmount = 0` after `Div(a, params.KAIA)`).
2. Register the same node's `CLNodeId` in `CLRegistry` with a CL staking amount also below `1 KAIA` (truncates to `CLStakingAmount = 0`).
3. If validator/proposer selection in `kaiax/valset` permits this node to become the block proposer (unconfirmed constraint), then at block finalization, `specWithProposerAndFunds` calls `cn.Split(proposer)` with `totalAmount = 0 + 0 = 0`, causing a `big.Int` divide-by-zero panic in `FinalizeState()`, crashing the node.

**Uncertainty flag:** Whether the proposer/validator selection process (`kaiax/valset`) permits a proposer with `StakingAmount` truncating to 0 was not confirmed within the available search iterations. If valset strictly enforces `StakingAmount >= minStake` (with typical non-trivial `minStake` values), this specific PoC path may not be reachable, though the missing zero-check in `Split()` remains a latent defect that could be triggered through other/future call sites.
