## Title
`SyscallAllocFree` (`sol_alloc_free_`) charges zero compute units, allowing unmetered repeated heap-allocator calls - (File: `syscalls/src/lib.rs`)

### Summary
The Stylus `MemoryGrow` report describes an opcode whose real cost was assumed to be "handled elsewhere," but for a code path where that other handler doesn't run, the opcode ends up priced far below its actual cost. Agave's SBF runtime has a structurally similar pattern in the heap-allocation syscall `SyscallAllocFree` (`sol_alloc_free_`), used whenever a BPF program's Rust/C allocator needs heap memory (e.g. via `Vec`, `Box`, `String`). Unlike essentially every other syscall in the codebase, this handler never calls `invoke_context.compute_meter.consume_checked(..)`, so it consumes zero compute units of its own, regardless of the number of times it is invoked.

### Finding Description
Every metered operation in the SBF program runtime charges compute units through `invoke_context.compute_meter.consume_checked(cost)`, either a syscall-specific cost (e.g. `create_program_address_units`, `mem_op_base_cost`) or at minimum `syscall_base_cost` for syscalls that otherwise "do no work" (see `SyscallGetStackHeight`, `SyscallRemainingComputeUnits`, `SyscallGetProcessedSiblingInstruction` at [1](#0-0) , [2](#0-1) , and [3](#0-2) ). Memory-touching syscalls such as `memcpy`/`memmove`/`memset` charge a size-scaled cost via `mem_op_consume` [4](#0-3) .

`SyscallAllocFree`, however, contains no call to `consume_checked` at all: [5](#0-4) 

It only computes a `Layout`, locks the per-instruction `BpfAllocator`, and calls `allocator.alloc(layout)`, which is a bump-pointer allocation defined at [6](#0-5) . The heap itself is sized via `ComputeBudget::heap_size` and its *setup* cost is charged once per invocation through `calculate_heap_cost` in the `create_vm!` macro [7](#0-6) [8](#0-7) . That one-time heap-size charge is analogous to the WASM "memory pricer" in the report: it prices the *total heap footprint requested for the call*, but — exactly like the report's fixed-memory MemoryGrow case — it does not account for the cost of the operation actually invoked to use that memory (each `alloc()` call itself), which the per-opcode/per-syscall pricing table is supposed to cover but doesn't here.

This means a BPF program can invoke `sol_alloc_free_` (indirectly, via any Rust heap allocation like `Vec::push`, `Box::new`, `format!`, etc., or directly via inline assembly / raw syscall invocation) an arbitrary number of times within its heap budget, and the runtime charges nothing beyond the fixed per-instruction "call" cost that the sBPF instruction meter already counts for executing the `call` opcode itself. There is no guard that re-derives a cost from `size`, from allocation count, or from `syscall_base_cost` for this syscall.

### Impact Explanation
This causes the same class of impact as the report: a program can drive real CPU work (layout computation, bounds-checked pointer arithmetic, borrow-checked access to `MemoryContext`) at a price of zero CU per call, while every comparable "no-op" syscall elsewhere in the same file is metered with at least `syscall_base_cost`. In the worst case this could allow a single instruction to perform far more allocator work than its `compute_unit_limit` should permit, which is a resource-exhaustion vector against validators executing that transaction (non-RPC remote exhaustion), and it distorts the fee/compute-accounting invariant that "1 CU of budget corresponds to a bounded amount of validator work," similar in spirit to the MemoryGrow underpricing exploit scenario.

The severity is bounded by the fact that `BpfAllocator::alloc` is O(1) (a bump-pointer check, not a real "grow" with copying), and the number of syscall invocations any single instruction can make is still gated by the interpreter's own per-BPF-instruction CU accounting for the surrounding `call` opcode and loop instructions used to invoke it repeatedly. So while the *specific opcode* is unmetered, the overall achievable amplification per compute-unit-limit is limited relative to the WASM `MemoryGrow` case, where growing/resizing linear memory is a comparatively more expensive operation than a bump-pointer allocation.

### Likelihood Explanation
Any signed transaction can deploy or invoke an ordinary program whose loop repeatedly triggers heap allocation (a common, unprivileged, natural usage pattern), so no special validator/peer/admin trust is required — this is exactly the "unprivileged Agave issue in program runtime/accounts" class the scope calls out. The gap (missing `consume_checked` call) is directly visible in the source and requires no race condition or timing dependency to trigger.

### Recommendation
- **Short term:** Add an explicit `invoke_context.compute_meter.consume_checked(execution_cost.syscall_base_cost)` (or a size-scaled cost analogous to `mem_op_consume`) at the top of `SyscallAllocFree` in `syscalls/src/lib.rs`, matching the metering pattern used by every other syscall in the file.
- **Long term:** Add an automated invariant/lint (or unit test coverage in `syscalls/src/lib.rs`) asserting that every `declare_builtin_function!`-registered syscall calls `compute_meter.consume_checked` at least once, so future syscalls cannot silently regress to zero-cost execution the way `SyscallAllocFree` currently does.

### Proof of Concept
1. Deploy a BPF program (via `bpf_loader`/`bpf_loader_upgradeable`) whose entrypoint performs a tight loop invoking heap allocation through the standard runtime (e.g. repeatedly `Box::new`/`Vec::push` small elements) sized to stay within the program's fixed heap frame (`request_heap_frame`), causing many `sol_alloc_free_` syscall invocations without exceeding the transaction's `compute_unit_limit`.
2. Instrument/compare compute-unit consumption logged via `SyscallLogBpfComputeUnits`/`sol_log_compute_units_` before and after the allocation loop, and observe that each `sol_alloc_free_` call subtracts effectively 0 CU from the compute meter beyond what is already attributed to the surrounding sBPF `call` instruction(s), unlike an equivalent loop invoking, e.g., `sol_get_stack_height` (which charges `syscall_base_cost` per call) as a control comparison at [1](#0-0) .
3. This demonstrates that `SyscallAllocFree` at [5](#0-4)  is effectively free relative to every metered counterpart, confirming the underpriced-opcode analog to the MemoryGrow report.

**Note on confidence:** I was unable to execute this PoC against a live validator/test harness (no filesystem/terminal access in this environment); the analysis is based on static reading of `syscalls/src/lib.rs`, `syscalls/src/mem_ops.rs`, `program-runtime/src/vm.rs`, and `program-runtime/src/invoke_context.rs`. The actual amplification factor achievable within a real `compute_unit_limit` would need to be measured empirically (e.g. via `solana-program-test` or `svm` unit tests) to size the practical severity, since the sBPF interpreter's own per-instruction CU accounting for the calling loop already imposes some cost ceiling that a WASM interpreter in the original report may not have in the same way.

```rust
fn mem_op_consume(invoke_context: &mut InvokeContext, n: u64) -> Result<(), Error> {
    let compute_cost = invoke_context.get_execution_cost();
    let cost = compute_cost.mem_op_base_cost.max(
        n.checked_div(compute_cost.cpi_bytes_per_unit)
            .unwrap_or(u64::MAX),
    );
    invoke_context.compute_meter.consume_checked(cost)
}
```

```rust
pub struct BpfAllocator {
    len: u64,
    pos: u64,
}

impl BpfAllocator {
    pub fn new(len: u64) -> Self {
        Self { len, pos: 0 }
    }

    pub fn alloc(&mut self, layout: Layout) -> Result<u64, AllocErr> {
        let bytes_to_align = (self.pos as *const u8).align_offset(layout.align()) as u64;
        if self
            .pos
            .saturating_add(bytes_to_align)
            .saturating_add(layout.size() as u64)
            <= self.len
        {
            self.pos = self.pos.saturating_add(bytes_to_align);
            let addr = MM_HEAP_START.saturating_add(self.pos);
            self.pos = self.pos.saturating_add(layout.size() as u64);
            Ok(addr)
        } else {
            Err(AllocErr)
        }
    }
}
```

```rust
/// Only used in macro, do not use directly!
pub fn calculate_heap_cost(heap_size: u32, heap_cost: u64) -> u64 {
    const KIBIBYTE: u64 = 1024;
    const PAGE_SIZE_KB: u64 = 32;
    let mut rounded_heap_size = u64::from(heap_size);
    rounded_heap_size =
        rounded_heap_size.saturating_add(PAGE_SIZE_KB.saturating_mul(KIBIBYTE).saturating_sub(1));
    rounded_heap_size
        .checked_div(PAGE_SIZE_KB.saturating_mul(KIBIBYTE))
        .expect("PAGE_SIZE_KB * KIBIBYTE > 0")
        .saturating_sub(1)
        .saturating_mul(heap_cost)
}
```

```rust
/// Create the SBF virtual machine
#[macro_export]
macro_rules! create_vm {
    ($vm:ident, $program:expr, $invoke_context:expr $(,)?) => {
        let invoke_context = &*$invoke_context;
        let stack_size = $program.get_config().stack_size();
        let heap_size = invoke_context.get_compute_budget().heap_size;
        let heap_cost_result =
            invoke_context
                .compute_meter
                .consume_checked($crate::__private::calculate_heap_cost(
                    heap_size,
                    invoke_context.get_execution_cost().heap_cost,
                ));
        let $vm = heap_cost_result.and_then(|_| {
            let (mut stack, mut heap) = $crate::__private::MEMORY_POOL
                .with_borrow_mut(|pool| (pool.get_stack(stack_size), pool.get_heap(heap_size)));
            let vm = $crate::__private::create_vm(
                $program,
                $invoke_context,
                stack
                    .as_slice_mut()
                    .get_mut(..stack_size)
                    .expect("invalid stack size"),
                heap.as_slice_mut()
                    .get_mut(..heap_size as usize)
                    .expect("invalid heap size"),
            );
            vm.map(|vm| (vm, stack, heap))
        });
    };
}
```
