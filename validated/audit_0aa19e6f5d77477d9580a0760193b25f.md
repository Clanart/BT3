### Title
`ThresholdKeys::read` trusts attacker-supplied security parameters without any consistency check — crafted key bytes cause false blame of honest signers (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to `validateToken()` trusting the spoofable `auth-user`/`Host` headers to bypass authentication, `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) deserializes every security-critical field — `t`, `n`, the participant index `i`, interpolation coefficients, `secret_share`, and all `verification_shares` — directly from untrusted bytes and passes them to `ThresholdKeys::new`, which never verifies that the claimed `secret_share` actually corresponds to `verification_shares[i]`. The group key itself is derived solely from attacker-chosen verification shares (`verification_shares[i] * interpolation_factor(i)` for `i in 1..=t`, crypto/dkg/src/lib.rs:376-378). The downstream FROST code explicitly acknowledges the consequence: "The only known way to cause this ... is to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494).

### Finding Description
`ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) performs only structural checks:

- `verification_shares.len() == n` (lines 355-360)
- every participant index `<= n` (lines 361-365)
- `Constant` interpolation only when `t == n` (lines 367-374)

There is no check that `C::generator() * secret_share == verification_shares[&params.i()]`, and no check that the interpolated `group_key` matches any expected value. All bytes are read via `C::read_F`/`C::read_G` and the `t`/`n`/`i` header fields (lines 591-623), so an attacker who controls the serialized blob fully controls the participant index the key claims to be, the secret share, the interpolation, and the group key.

### Impact Explanation
When such a key is used in `AlgorithmMachine`/`AlgorithmSignMachine::sign`, the victim computes shares under `view` built from the injected `secret_share`, while `group_key` and `verification_shares` come from the attacker's chosen points. In `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:447-494), aggregate verification fails, and the blame path queues `verify_share` statements against the attacker-chosen `self.view.verification_share(*l)`. Shares produced by honest co-signers (using their own honest keys) will fail verification against the injected verification shares, yielding `FrostError::InvalidShare(l)` that blames an honest participant — i.e., spoofed key material defeats the accountability/blame mechanism and deterministically aborts signing (liveness loss). The attacker can also make the victim adopt an arbitrary group key, so any address/script derived from `keys.group_key()` (e.g., `p2tr_script_buf`, networks/bitcoin/src/wallet/mod.rs:80-86) is attacker-defined.

### Likelihood Explanation
Reachability requires attacker-supplied bytes into `ThresholdKeys::read` — the prompt's rules explicitly accept untrusted bytes fed to `ThresholdKeys::read` as an in-scope input. This corresponds to environments where key blobs are loaded from shared storage/messages rather than exclusively from self-generated state. No cryptographic assumption is broken; the bypass exists purely because authenticity/consistency of the fields is assumed rather than verified — the same defect class as trusting `auth-user: service-brother` plus a client-controlled `Host`.

### Recommendation
- In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise.
- Consider authenticating serialized `ThresholdKeys` (MAC/version tag) or documenting that `read` must only consume self-generated bytes.
- Optionally recompute/bound-check `group_key` non-identity and canonical.

### Proof of Concept
```rust
// Crypto/dkg test sketch
use frost::curve::{Ciphersuite, Ristretto, Curve};
use frost::dkg::{Participant, ThresholdParams, ThresholdKeys};

// Craft a serialized ThresholdKeys blob where secret_share does NOT match
// verification_shares[i], and verification_shares[1..=t] interpolate to an
// attacker-chosen group key.
let mut blob = vec![];
blob.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
blob.extend(Ristretto::ID);
blob.extend(1u16.to_le_bytes());            // t = 1
blob.extend(2u16.to_le_bytes());            // n = 2
blob.extend(1u16.to_le_bytes());            // i = 1 (we claim participant 1)
blob.push(1);                               // Interpolation::Lagrange
// arbitrary secret_share — never checked against verification_shares[1]
blob.extend(<Ristretto as Ciphersuite>::F::ONE.to_repr().as_ref());
// attacker-chosen verification shares -> attacker-chosen group_key
let attacker_point = <Ristretto as Ciphersuite>::generator() * <Ristretto as Ciphersuite>::F::from(42u64);
blob.extend(attacker_point.to_bytes().as_ref());
blob.extend(<Ristretto as Ciphersuite>::generator().to_bytes().as_ref());

let keys = ThresholdKeys::<Ristretto>::read::<&[u8]>(&mut blob.as_ref()).unwrap();
// group_key is entirely attacker-defined; secret_share is inconsistent.
// Using `keys` in AlgorithmSignMachine::sign -> complete() deterministically
// hits the InvalidShare blame path, attributing fault to honest signers.
assert_eq!(keys.group_key(), attacker_point);
```

Note: within the indexed snapshot I verified `ThresholdKeys::read`/`new` perform no share↔verification-share binding; I could not fully trace every in-repo caller of `ThresholdKeys::read` to confirm a concrete untrusted-byte flow beyond the documented `KeysDb`/`GeneratedKeysDb` usage (processor/src/key_gen.rs:51-62), so the severity hinges on deployments exposing that deserialization path to attacker-controlled data.
