### Title
Unverified PoP share decryption leaks the victim's static ECDH result, enabling secret share recovery - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
In `KeyMachine::calculate_share`, each incoming `EncryptedMessage` is passed to `Encryption::decrypt`, which computes `ecdh(self.enc_key, msg.key)` — the victim's static encryption secret multiplied by an attacker-supplied point — and returns an `EncryptionKeyProof` containing that ECDH result as "blame" material. The Schnorr proof-of-possession (`pop`) that would prove the sender knows the discrete log of `msg.key` is only *queued* into the `BatchVerifier` (`msg.pop.batch_verify`), but the decrypted share is checked synchronously with `C::F::from_repr` immediately afterwards. If the decrypted share fails to parse, `calculate_share` returns `PedPoPError::InvalidShare { blame: Some(blame) }` early, without ever running `batch.verify_with_vartime_blame()`. The attacker therefore receives a blame proof revealing `e · P` for an arbitrary point `P` they chose, with no requirement that they know `P`'s discrete log.

### Finding Description
- `Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs) queues the PoP verification and unconditionally computes `let key = ecdh::<C>(&self.enc_key, msg.key)` then decrypts the message and returns `(msg.msg, EncryptionKeyProof { key, dleq })` — where `dleq` proves `log(msg.key) = key` relative to `enc_key`, making the leaked `key` self-authenticating.
- `EncryptedMessage::read` accepts any canonical point for `msg.key` via `C::read_G` — no identity rejection, and the PoP is not verified at parse time.
- In `calculate_share` (crypto/dkg/pedpop/src/lib.rs), the decrypted `SecretShare` bytes are checked with `C::F::from_repr(share_bytes.0)`. A failure returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` *before* `batch.verify_with_vartime_blame()` is reached, so the PoP on `msg.key` is never verified on this error path.
- Blame proofs are designed to be published to third parties, which re-verify them via `Decryption::decrypt_with_proof` — which does check `msg.pop` — but by then the attacker already holds the leaked ECDH output. The attacker's goal isn't to convince others; it's the leaked value itself.

This mirrors the CVE bug class: a function expects input of one "type" (a key whose discrete log is proven), the caller supplies a chosen input of another "type" (an arbitrary point), and receives a computation over secret memory (the victim's static `enc_key`) that they could not compute themselves.

### Impact Explanation
The attacker selects `msg.key = K_j`, the ephemeral public key inside an *honest* participant `j`'s `EncryptedMessage` addressed to the victim (DkgShares payloads are broadcast/published in Serai's DKG flow). The returned blame leaks `key = e_victim · K_j`, which is exactly the shared secret `cipher(context, ecdh)` uses to encrypt `j`'s share to the victim. The attacker feeds `key` into `cipher()` and decrypts `j`'s ciphertext, recovering the share `j` sent to the victim. Repeating per honest sender yields every share addressed to the victim; summing them yields the victim's aggregated secret share (`*self.secret += share` in `calculate_share`). This is key share recovery: confidentiality of a threshold participant's `secret_share` is broken, enabling an attacker who later obtains the remaining shares (or already holds `t-1` shares across collusion) to reconstruct the group private key, and immediately enabling forgery of that participant's signature share.

### Likelihood Explanation
Any DKG participant can trigger this deterministically: craft an `EncryptedMessage` with `key` set to a target point and any ciphertext, submit it as their share message, and the victim's `calculate_share` returns the blame containing the ECDH result before the PoP batch check runs. No collusion, no malformed-curve trickery, and no timing assumptions are needed; the only requirement is that the victim processes the message, which is the normal protocol path.

### Recommendation
Verify the PoP synchronously inside `decrypt` (or restructure `calculate_share` so no blame/decryption output is produced until the batch PoP check succeeds), and only emit `EncryptionKeyProof` for messages whose `pop` is known-valid. Additionally, reject the identity point for `msg.key`/`enc_key` (e.g., use the `Curve::read_G` identity check semantics) so `ecdh` can never produce a known constant output.

### Proof of Concept
1. Victim registers `enc_pub_key = e·G` and runs `KeyMachine::calculate_share` over received shares.
2. Honest participant `j` publishes `EncryptedMessage { key: K_j, pop, msg: C_j }` addressed to the victim.
3. Attacker sends `EncryptedMessage { key: K_j, pop: <arbitrary bytes parsed as SchnorrSignature>, msg: <garbage same length> }` (via `EncryptedMessage::read`, which performs no PoP check and no identity check on `key`).
4. `calculate_share` calls `self.encryption.decrypt(...)`, which computes `key = e·K_j`, decrypts the garbage, and returns `(garbage_share, EncryptionKeyProof { key, dleq })`.
5. `C::F::from_repr(garbage_share)` fails (attacker ensures this by construction, e.g., bytes that remain non-canonical after the keystream — or simply rely on the overwhelmingly likely random failure), so `calculate_share` returns `PedPoPError::InvalidShare { blame: Some(proof) }` before `batch.verify_with_vartime_blame()` ever validates the attacker's PoP.
6. Attacker recovers `key = e·K_j` from the blame, runs `cipher::<C>(context, &Zeroizing::new(key)).apply_keystream(&mut C_j)`, and reads `j`'s secret share to the victim.
7. Repeating for each sender `j` recovers all shares; summing them (as `calculate_share` does) yields the victim's `secret_share` — key share recovery.
