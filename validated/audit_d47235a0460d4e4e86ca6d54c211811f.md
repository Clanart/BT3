### Title
Unbounded per-transaction batching in `PlotNFT2Wallet.claim_rewards` can make accumulated pool rewards unclaimable due to CLVM cost limits - ([File: chia/wallet/plotnft_wallet/plotnft_wallet.py])

### Summary
The external OTLM report describes a bug class where a reward-claim function loops over every unclaimed accounting unit (epoch) without any batching/limit, so once enough units accumulate, the single required transaction exceeds gas/cost limits and reverts, permanently locking a user out of claiming (or forcing them into extremely expensive claims). The Chia analog is `PlotNFT2Wallet.claim_rewards()` in `chia/wallet/plotnft_wallet/plotnft_wallet.py`, which builds one `CoinSpend` per unclaimed pool reward coin for **all** `rewards_to_claim` returned by `plotnft2_store.get_pool_rewards()` and pushes them as a single `WalletSpendBundle`, with no batching/limit parameter analogous to `PoolWallet.claim_pool_rewards()`'s `max_spends_in_tx`/`DEFAULT_MAX_CLAIM_SPENDS`.

### Finding Description
`PlotNFT2Wallet.claim_rewards()` fetches all unclaimed pool rewards for the plotNFT and constructs one coin spend per reward plus the singleton claim spend, all combined into a single `WalletSpendBundle`: [1](#0-0) 

This mirrors the CLVM-side `PlotNFT.claim_pool_rewards()`, which iterates `rewards_to_claim` and `reward_delegated_puzzles_and_solutions` and emits a `CoinSpend` for every reward with no cap: [2](#0-1) 

By contrast, the older `PoolWallet.claim_pool_rewards()` explicitly caps the number of reward coins absorbed per transaction via `max_spends_in_tx`/`DEFAULT_MAX_CLAIM_SPENDS`, truncating and logging when the limit is exceeded so the resulting `SpendBundle` fits into a block: [3](#0-2) 

`PlotNFT2Wallet.claim_rewards()` has no equivalent batching parameter or truncation logic, and the RPC entry point `pw_absorb_rewards` in `chia/wallet/wallet_rpc_api.py` calls `wallet.claim_rewards(...)` for `PlotNFT2Wallet` without any batch-size argument, unlike the `PoolWallet` branch which forwards `request.max_spends_in_tx`: [4](#0-3) 

If a plot NFT accrues a large number of unclaimed pool reward coins (e.g., a farmer who does not claim frequently, or is unable to claim due to fee errors, low balance, or being offline for a long period), the next `claim_rewards()` call must bundle every one of those reward coins plus the singleton spend into one spend bundle. Each reward coin spend and the growing `SendMessage`/announcement list in the delegated puzzle adds CLVM execution cost. Once total cost (or serialized size) exceeds the max block cost / mempool limits, the resulting transaction can never be included, and there is no way to claim a subset — the function has no partial-claim mechanism, so the entire batch of unclaimed rewards becomes stuck.

### Impact Explanation
This is a spend-triggered transaction-processing halt for the affected wallet: legitimate reward coins already farmed to the plot NFT become permanently unclaimable once the accumulated reward count grows large enough to blow the per-transaction cost budget, since there is no partial/batched claim path. This can cause a denial of service on the user's own funds (locked rewards) triggered purely by normal usage patterns (infrequent claiming), matching the "excessively expensive computation exceeds gas limit" impact pattern from the source report, adapted to Chia's CLVM cost-limited transaction model.

### Likelihood Explanation
Likelihood is moderate: it requires a user (or an automated system) to let pool rewards accumulate substantially before calling `claim_rewards()` — plausible for infrequent-claim workflows, disabled auto-claim, or fee-based abandonment of earlier claim attempts. No malicious peer or privileged actor is needed; it is entirely reachable by a normal wallet user through the standard `pw_absorb_rewards`/`claim_rewards` RPC/CLI path.

### Recommendation
Add a batching/limit mechanism to `PlotNFT2Wallet.claim_rewards()` analogous to `PoolWallet.claim_pool_rewards()`'s `max_spends_in_tx` (e.g., accept an optional `max_rewards_in_tx` parameter, truncate `rewards_to_claim` to a safe count per transaction, and allow repeated calls to drain the remainder), and update `pw_absorb_rewards` in `chia/wallet/wallet_rpc_api.py` to forward such a parameter for `PlotNFT2Wallet` the same way it does for `PoolWallet`.

### Proof of Concept
1. Farm many blocks with a Plot NFT in `FARMING_TO_POOL` mode via `PlotNFT2Wallet` so a large number of pool reward coins accrue without ever calling `claim_rewards()` (or with claim calls failing for other reasons, e.g., fee errors as tested in `test_plotnft_wallet.py` lines 167-171).
2. Call `claim_rewards()` (or RPC `pw_absorb_rewards`) once the number of accrued rewards is large.
3. Observe that `plotnft.claim_pool_rewards()` builds one `CoinSpend` per reward plus the singleton spend into a single `WalletSpendBundle` with no cap, per `chia/pools/plotnft_drivers.py` lines 590-642 and `chia/wallet/plotnft_wallet/plotnft_wallet.py` lines 149-198.
4. Unlike `PoolWallet.claim_pool_rewards()` (`chia/pools/pool_wallet.py` lines 722-762), there is no mechanism to cap/batch the spends, so once the combined CLVM execution cost of the singleton/message chain and reward-coin spends exceeds the max block cost, the spend bundle can never be pushed, permanently stranding those reward coins for that plot NFT.

    def claim_pool_rewards(
        self,
        rewards_to_claim: list[PoolReward],
        reward_delegated_puzzles_and_solutions: list[DelegatedPuzzleAndSolution],
    ) -> list[CoinSpend]:
        if self.pooling:
            raise ValueError("Cannot claim rewards while pooling. If you're a pool, try `forward_pool_rewards`")
        if len(rewards_to_claim) != len(reward_delegated_puzzles_and_solutions):
            raise ValueError("Number of rewards and delegated puzzles and solutions must match")
        dpuz_and_solution = DelegatedPuzzleAndSolution(
            puzzle=Program.to(
                (
                    1,
                    [
                        CreateCoin(
                            puzzle_hash=self.inner_puzzle_hash(),
                            amount=self.coin.amount,
                            memos=[self.singleton_struct.struct_hash()],
                        ).to_program(),
                        *(
                            SendMessage(
                                msg=dpuz_and_sol.puzzle.get_tree_hash(),
                                sender=MessageParticipant(puzzle_hash_committed=self.puzzle_hash(nonce=0)),
                                receiver=MessageParticipant(coin_id_committed=reward.coin.name()),
                            ).to_program()
                            for reward, dpuz_and_sol in zip(rewards_to_claim, reward_delegated_puzzles_and_solutions)
                        ),
                    ],
                )
            ),
            solution=Program.to([]),
        )
        return [
            self.singleton_action_spend(
                inner_solution=self.puzzle_with_restrictions().solve(
                    member_validator_solutions=[],
                    dpuz_validator_solutions=[],
                    member_solution=self.bls_member.solve(),
                    delegated_puzzle_and_solution=dpuz_and_solution,
                )
            ),
            *(
                make_spend(
                    coin=reward.coin,
                    puzzle_reveal=reward.puzzle(),
                    solution=reward.solve(
                        self.inner_puzzle_hash(),
                        delegated_puzzle_and_solution=dpuz_and_sol,
                    ),
                )
                for reward, dpuz_and_sol in zip(rewards_to_claim, reward_delegated_puzzles_and_solutions)
            ),
        ]
