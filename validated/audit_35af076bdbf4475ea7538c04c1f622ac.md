## Title
Automatic remote-URL migration on GitHub repo refresh doesn't verify the new URL's host, silently redirecting `origin` to an attacker-controlled server - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` mirrors the `SingleStrategyController.migrate()` flaw: it swaps the trusted "destination" (the local `origin` remote) for a new one supplied by an external, less-trusted source without validating that the new destination is actually compatible/consistent with the old one. The controller checked strategy addresses but never the *base token*; here Desktop checks the URL's *protocol* but never the *hostname*, which is the actual authority boundary for git credentials and content.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app-store.ts` during routine repository refresh: it fetches the repo's metadata from the GitHub API (`api.fetchRepository(owner, name)`) using the account bound to that repo's `endpoint`, and if the API's `clone_url` differs from the local remote, it calls `gitStore.setRemoteURL(...)` to rewrite the local `origin` remote — with no user prompt. [1](#0-0) 

The guard logic in `updateRemoteUrl` is: [2](#0-1) 

The only equality check performed before rewriting is **protocol** equality (`https` vs `https`/`ssh` vs `ssh`), derived from Node's `URL.parse().protocol`. Nothing compares the **hostname** of the new `clone_url` against the hostname of the current remote or the account's configured endpoint. `urlsMatch`/`urlMatchesRemote` are only used to detect whether the URL has *changed* (`!urlsMatch`) and whether the remote was previously unmodified (`remoteUrlUnchanged`) — never to reject a change whose host differs from the trusted authority. [3](#0-2) 

Contrast this with `urlMatchesRemote`, which does properly compare `hostname`, `owner`, and `name` — proving the codebase already has the primitive needed to perform a real check, it's just never applied to the *new* URL against the *trusted host*.

### Impact Explanation
If the value returned for `clone_url` by the account's configured GitHub API endpoint is attacker-influenced (a compromised/malicious GitHub Enterprise Server the user has already added an account for, or a MITM/proxy that tampers with the API response for `fetchRepository`), Desktop will silently rewrite the local `origin` remote to point at an attacker-controlled `https://` host — satisfying `protocolsMatch` trivially and `remoteUrlUnchanged` as long as the user hasn't manually edited the remote. From that point on:
- Any subsequent `git push` from Desktop (or the underlying credential helper keyed by host) sends the user's repository contents/credentials to the attacker's host.
- Any subsequent `git fetch`/pull brings in attacker-supplied refs/commits that the user may merge and later push upstream, silently corrupting what they commit/push.

This maps directly to the report's core failure class — a privileged "migration" step trusts an externally supplied replacement resource without validating it is consistent with the resource being replaced — and to the allowed impact bucket "attacker controls ... a GitHub API object ... and the result is ... credential/token exfiltration ... or silent corruption of what the user commits or pushes."

### Likelihood Explanation
This path requires no unusual user action: refreshing GitHub repository info happens as part of normal background repository refresh, not an explicit user-initiated "migrate" action. The precondition is that the account's API endpoint (typically a GitHub Enterprise Server the user already trusts, or a proxy in front of GitHub) returns a manipulated `clone_url` — this is within the "attacker controls ... a GitHub API object" category explicitly allowed by the task's valid-impact list, and does not require local/physical access, admin rights, or prior malware.

### Recommendation
In `updateRemoteUrl`, add an explicit hostname check comparing the new `apiRepo.clone_url`'s host against the host of the *existing trusted* remote (or the account's configured endpoint) using the already-available `parseRemote`/`urlMatchesRemote` machinery, and refuse to auto-update (or require explicit user confirmation, as already done in `UpstreamAlreadyExists`) whenever the hostname changes: [4](#0-3) 

i.e., require something equivalent to `require(parseRemote(remoteUrl).hostname === parseRemote(updatedRemoteUrl).hostname)` before calling `gitStore.setRemoteURL`.

### Proof of Concept
1. User has a GitHub Enterprise Server (or GitHub.com behind a compromised/incorrect proxy) account added in Desktop, with a repository whose `origin` remote is `https://ghe.company.com/org/repo.git`.
2. The GHES instance (or MITM proxy) is compromised and, in response to `GET /repos/org/repo` (`api.fetchRepository`), returns `clone_url: "https://ghe-evil.attacker.tld/org/repo.git"`.
3. On the next repository refresh, `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` runs:
   - `protocolsMatch` → true (`https` === `https`)
   - `remoteUrlUnchanged` → true (user never manually edited the remote)
   - `urlsMatch` → false (hostname differs)
   - Result: `gitStore.setRemoteURL('origin', 'https://ghe-evil.attacker.tld/org/repo.git')` executes with no dialog and no host check.
4. The user's next `git push`/`git fetch` operations, and their credential helper interactions, now target `ghe-evil.attacker.tld`.

I was not able to fully trace every call-site of `repositoryWithRefreshedGitHubRepository` (grep only confirmed it lives in `app-store.ts` with 7 references) to enumerate all trigger conditions (e.g., exact refresh cadence/background timers); a Devin session with full repo access could confirm the precise trigger frequency if needed.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
