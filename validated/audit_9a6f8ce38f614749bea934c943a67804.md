## Finding

The Wagmi bug is a specific instance of a broader pattern: **an unconditional, non-recoverable push-transfer to a caller-selected beneficiary blocks settlement forever when the beneficiary cannot receive the token.** Hyperbridge's `IntentGatewayV2` (EVM) has the same pattern in its cross-chain escrow settlement path, compounded by `EvmHost.dispatchIncoming` silently swallowing the resulting revert instead of surfacing it, and by the settlement messages being dispatched with `timeout: 0` (no timeout path).

### Title
Blacklisted solver or user beneficiary permanently locks IntentGateway escrow with no recovery path - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`'s cross-chain settlement handler (`ExtrinsicIntents.onAccept`) unconditionally calls `_withdraw`, which pushes escrowed ERC-20 tokens directly to the ISMP-decoded `beneficiary` via `IERC20.safeTransfer` (or a raw ETH `.call`). If that beneficiary is blacklisted for the token (e.g. a sanctioned/frozen USDC/USDT address), the transfer reverts, the whole `onAccept` reverts, and `EvmHost.dispatchIncoming` swallows the revert by deleting the request receipt and returning — with no escrow fallback and `timeout: 0` on the dispatched message, the escrow can never be released.

### Finding Description
`_fillCrossChain` in `ExtrinsicIntents.sol` dispatches a `RedeemEscrow` `DispatchPost` back to the source chain naming the solver (`msg.sender`) as beneficiary, and `_cancelFromDest`/`onGetResponse` dispatch `RefundEscrow` naming `order.user` as beneficiary: [1](#0-0) [2](#0-1) 

Both `timeout: 0` on the `DispatchPost` means these settlement messages never expire and can only be resolved by successful delivery.

On the source chain, `onAccept` routes both message kinds straight into `_withdraw`: [3](#0-2) 

`_withdraw` performs an unconditional push transfer to `beneficiary`: [4](#0-3) 

If `beneficiary` is blacklisted for `token` (or, for native ETH, is a contract that rejects the call), `IERC20.safeTransfer`/the low-level `.call` reverts, and that revert propagates all the way up through `_withdraw` → `onAccept`.

`EvmHost.dispatchIncoming` — the host function that invokes `IApp.onAccept` — catches this failure but does not surface it as a permanent error; it deletes the just-written request receipt "so that it can be retried" and returns without emitting `PostRequestHandled`: [5](#0-4) 

Because the receipt is deleted, a relayer (or the beneficiary itself, since delivery is generally permissionless) can resubmit the same message indefinitely, but it will revert every single time the beneficiary remains blacklisted — there is no branch anywhere in `_withdraw`/`onAccept`/`dispatchIncoming` that reroutes funds to an escrow account, and since the dispatch used `timeout: 0` there is no timeout-triggered refund path either (unlike `HyperFungibleToken`/`HyperbridgeLzEndpoint`, which explicitly wrap their beneficiary-facing transfer in `try`/`catch` or a native-ETH-then-WETH fallback to avoid exactly this class of lock, e.g. `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol` and `sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`'s isolated inbound-delivery `try`/`catch`).

The Tron fork of `IntentGatewayV2.sol` has the identical unconditional-transfer pattern in its own `withdraw`: [6](#0-5) 

### Impact Explanation
For a cross-chain fill (`RedeemEscrow`): the solver has already delivered output tokens to the user on the destination chain *before* the settlement message is dispatched. If the solver's own address later becomes blacklisted for the escrowed input token (or was already blacklisted and this is only discovered at settlement time), the solver has irreversibly given up their output tokens and can never redeem the escrowed input — a direct, permanent loss of funds with no recovery mechanism, exactly mirroring the Wagmi report's "creditor forced to default" but without even a fallback like Wagmi's "emergency closure."

For a cross-chain cancellation (`RefundEscrow`): if `order.user` is blacklisted for the escrowed input token, the user's escrow is permanently locked in the `IntentGatewayV2` contract — it can never be marked filled/refunded, and since it is neither refundable (blacklist blocks `_withdraw`) nor timeoutable (`timeout: 0`), the funds are stuck indefinitely.

### Likelihood Explanation
This does not require a malicious relayer, prover, or governance actor — it triggers under ordinary conditions whenever the beneficiary address (solver or user, both unprivileged, ordinary actors) is or becomes blacklisted by the escrowed token's issuer (USDC/USDT-style blacklists, or OFAC-driven freezes are common in production). Any solver or user who transacts in a blacklistable stablecoin is exposed, and delivery is retried automatically by relayers, so the failure is discovered organically rather than requiring special attacker action.

### Recommendation
Wrap the beneficiary-facing transfer in `_withdraw` (and the Tron `withdraw` equivalent) in a `try`/`catch` (or low-level `call` + fallback check as done elsewhere in the codebase, e.g. `HyperbridgeLzEndpoint.onAccept`'s isolated `try`/`catch`), and on failure route the funds to a per-beneficiary escrow/claim mapping that the beneficiary (or a designated recovery address) can withdraw from later once unblocked, rather than letting the entire settlement message revert forever.

### Proof of Concept
1. A user places a cross-chain order on chain A with `inputs = [USDC]`.
2. A solver fills the order on chain B, delivering output tokens to the user, then chain B dispatches `RedeemEscrow{commitment, tokens: inputs, beneficiary: solver}` to chain A with `timeout: 0`. [7](#0-6) 
3. Before the message is delivered, the solver's address is added to USDC's blacklist (issuer-driven, no attacker action needed).
4. A relayer delivers the message on chain A; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw` → `IERC20(USDC).safeTransfer(solver, amount)`, which reverts because USDC blocks transfers to/from blacklisted addresses. [8](#0-7) 
5. `EvmHost.dispatchIncoming` swallows the revert, deletes the request receipt, and returns silently — no funds move, no error is surfaced on-chain beyond a failed retry. [9](#0-8) 
6. Any future relayer resubmission of the same message reverts identically for as long as the solver remains blacklisted; since `timeout: 0`, there is no timeout path either — the escrowed USDC is permanently stuck in `IntentGatewayV2` with no code path to recover it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
