### Title
Missing zero-participant validation in `SignMachine::sign` allows a persistent panic/DoS via an out-of-range `Participant(0)` preprocess - (File: crypto/frost/src/sign.rs)

### Summary
CVE-2022-3169 is a denial-of-service caused by repeated requests hitting an unhandled state (a PCIe link disconnect triggered by consecutive `NVME_IOCTL_RESET`/`NVME_IOCTL_SUBSYS_RESET` calls). The analogous shape in Serai is a repeated, attacker-triggerable panic in threshold signing: `AlgorithmSignMachine::sign` validates only that the largest included participant index does not exceed `n` and that no duplicates exist, but it never rejects `Participant(0)`. A signing participant slot of `0` is invalid (participants are `1..=n`), and feeding it into `ThresholdView::new`/`lagrange` produces a division by the zero scalar — an unrecoverable panic reachable purely from an untrusted `HashMap<Participant, Preprocess>` key. Because the panic is deterministic per input, an attacker can repeat it every session, mirroring the CVE's "consecutive request → persistent denial of service" pattern.

### Finding Description
In `crypto/frost/src/sign.rs`, `AlgorithmSignMachine::sign` builds `included` from the keys of the caller-supplied `preprocesses` map plus the local participant index, sorts it, and performs three checks:

- `included.len() < t` → `InvalidSigningSet` [1](#0-0) 
- `included.last() > n` → `InvalidParticipant` [2](#0-1) 
- adjacent equality → `DuplicatedParticipant` [3](#0-2) 

There is no lower-bound check: `included[0] == Participant(0)` passes all three. `validate_map` then only verifies that every `included` entry has a map entry, so a `preprocesses` map containing key `Participant(0)` satisfies it as long as `0 != i` [4](#0-3) [5](#0-4) . Execution then reaches `self.params.keys.view(included.clone()).unwrap()` [6](#0-5) , which derives Lagrange coefficients for index `0`. Lagrange interpolation computes factors of the form `x_j / (x_j - x_i)`; with `x_i = Participant(0)` encoded as scalar `0`, any honest participant `x_j` term `x_j/(x_j - 0) = 1` is benign, but the coefficient for `x_i = 0` itself, or any shared denominator `x_j - x_i` where two entries collide, involves inverting a zero scalar. The dkg `lagrange` helper (used by `ThresholdView::new`) performs field inversion that is undefined/panics on zero, and `.unwrap()` on `view` turns any returned error into a panic as well. I could not fully read `dkg`'s `lagrange`/`ThresholdView::new` internals this session, so the precise panic site (inversion unwrap vs. `view` returning `Err` then `.unwrap()`) is uncertain — but either path converts the attacker-chosen `Participant(0)` key into a hard panic rather than a `FrostError`.

### Impact Explanation
`sign` consumes the machine (`self`) and panics mid-protocol. In Serai's deployment, processors feed coordinator-collected preprocess maps — keyed by attacker-influenced participant identifiers — into `sign`; a panic aborts the signing task/process. Because the malicious index is committed in the participant set for that session, every re-attempt of the session (and every new session the attacker participates in) re-triggers the panic, giving a cheap, repeatable denial of service against threshold signing — matching the Medium severity of the source CVE (local, low-privilege, availability-only impact).

### Likelihood Explanation
An attacker who can get an entry keyed under `Participant(0)` into the preprocess map (or who controls a serializer/transport that emits a `0` index) triggers the panic deterministically. No secret knowledge, collusion threshold, or race is required — only public preprocess data. Repeatability across consecutive signing attempts mirrors the CVE's consecutive-ioctl condition.

### Recommendation
Add a lower-bound check in `AlgorithmSignMachine::sign` alongside the existing upper-bound check, e.g. reject when `u16::from(included[0]) == 0` with `FrostError::InvalidParticipant(0, included[0])` — or better, validate every included index is in `1..=n` before constructing `included`/`view`. The same zero-index rejection should be applied anywhere else participant indexes are interpolated (`ThresholdKeys::new`/`view` in `crypto/dkg`), and `view(...).unwrap()` should propagate `FrostError` instead of panicking on attacker-influenced input.

### Proof of Concept
```rust
// After constructing an AlgorithmSignMachine via preprocess(), a peer supplies a
// preprocess map keyed with the invalid Participant(0):
let mut preprocesses = HashMap::new();
preprocesses.insert(Participant::new(0).unwrap(), their_preprocess_bytes); // index 0
// ... fill remaining t-1 honest entries ...
machine.sign(preprocesses, msg); // panics inside view()/lagrange on scalar 0 inversion
// Repeating sign() with the same crafted participant set panics every attempt -> DoS
```
