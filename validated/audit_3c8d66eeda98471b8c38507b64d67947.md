### Title
Unauthenticated `internal_send_tx` reachable via `Interceptors::Noop` when `client_verification=false` - ([File: core/src/servers.rs], [File: core/src/rpc/interceptors.rs])

### Summary
When `config.client_verification` is `false`, `create_grpc_server` installs `Interceptors::Noop`, which unconditionally returns `Ok(req)` for every request with no certificate check at all [1](#0-0) . This means the `is_internal`/`only_aggregator_and_self` authorization logic, which is the only code that ties a caller's identity to `aggregator_cert`/`our_cert`, is never invoked, so any TCP client reaching the aggregator's port can call `internal_send_tx` and any other RPC without holding any certificate.

### Finding Description
The binding claimed to hold is: `caller reaching ClementineAggregator::internal_send_tx == holder of config.aggregator_cert_path/our_cert`. Tracing the code shows this binding is enforced only inside `only_aggregator_and_self`, which compares the TLS leaf certificate against `aggregator_cert`/`our_cert` [2](#0-1) . That function is only reached when the interceptor variant is `Interceptors::OnlyAggregatorAndSelf`, which is only constructed when `config.client_verification == true` [3](#0-2) . When `client_verification` is `false`, `Interceptors::Noop` is installed instead, and its `call` implementation is `Interceptors::Noop => Ok(req)` — no certificate is inspected, no `is_internal` check happens, and no comparison to any cert occurs [4](#0-3) . The server still presents a TLS server identity (`ServerTlsConfig::new().identity(server_identity)`) but does not request or validate a client certificate in this branch [5](#0-4) . `create_aggregator_grpc_server` only emits a `tracing::warn!` when verification IS enabled, and takes no compensating action when it is disabled [6](#0-5) . Consequently, on a port configured this way, an attacker with a bare TLS client (no client certificate, no CA-issued identity) can open a channel and invoke `ClementineAggregator::internal_send_tx` (confirmed present in `core/src/rpc/aggregator.rs`) with an arbitrary `SendTxRequest.raw_tx`, and this can flow into the tx-sender queue (`insert_try_to_send`, referenced from `core/src/rpc/aggregator.rs` and implemented in `core/src/tx_sender_queue.rs`).

### Impact Explanation
Because no caller identity is verified in the `Noop` path, the aggregator's fee-paying infrastructure can be induced to enqueue and attempt to broadcast a transaction chosen entirely by an unprivileged internet party, without spending any bridge UTXO logic in between. This matches the High-severity category "an unauthenticated state-changing or broadcasting call" — the aggregator's operational funds/fee-bumping wallet could be driven to pay fees for or broadcast attacker-selected transactions, and other exposed methods (`Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`) become equally reachable, since the same `Noop` interceptor gates the entire service, not just this one RPC. This is repeatable on every call while the misconfiguration persists and applies uniformly regardless of deposit/operator identity, since the gate is service-wide rather than per-deposit.

### Likelihood Explanation
The only precondition is deployment configuration: `config.client_verification = false` on the aggregator's `BridgeConfig`. The question notes this is described as "the documented state for the aggregator" in at least one reference config (`core/src/test/data/bridge_config.toml`, `scripts/docker/configs/testnet4/bridge_config.toml` both reference `client_verification`, confirming this flag exists and is toggled in shipped configs). No BTC cost, no key material, and no prior interaction with the bridge is required by the attacker beyond network reachability to the aggregator's gRPC port — this is a pure configuration/authorization gap in `core/src/servers.rs` and `core/src/rpc/interceptors.rs`, fully reachable through this repository's own server bootstrap code path.

### Recommendation
Do not allow `Interceptors::Noop` to be used on any externally reachable production listener for the aggregator (or any node). At minimum, `only_aggregator_and_self`-style method gating (including the `is_internal` check) should be enforced independently of `client_verification`, or `client_verification=false` should be rejected/disallowed for non-loopback/non-test bind addresses. Consider making `Noop` a test-only variant (`#[cfg(test)]`) so it cannot be selected in a real deployment build, forcing all production aggregator/operator/verifier servers to require mTLS with `OnlyAggregatorAndSelf`.

// added purely to demonstrate the reachable gap in servers.rs/interceptors.rs)
#[tokio::test]
async fn noop_interceptor_allows_unauthenticated_internal_send_tx() {
    let mut config = BridgeConfig::default(); // or test config
    config.client_verification = false; // documented aggregator state
    let (addr, _shutdown) = create_aggregator_grpc_server(config.clone()).await.unwrap();

    // Bare, non-mTLS client: only trusts server cert (or skips verification), presents NO client certificate.
    let channel = tonic::transport::Channel::from_shared(format!("https://{addr}"))
        .unwrap()
        .tls_config(ClientTlsConfig::new().with_native_roots()) // no .identity(..) => no client cert
        .unwrap()
        .connect()
        .await
        .unwrap();

    let mut client = ClementineAggregatorClient::new(channel);

    let raw_tx = /* attacker-chosen arbitrary valid Bitcoin tx bytes */ vec![/* ... */];
    let resp = client
        .internal_send_tx(SendTxRequest { raw_tx, /* other fields */ })
        .await;

    // Binding under test:
    // LHS: "caller reached internal_send_tx"      -> resp.is_ok() == true
    // RHS: "caller holds aggregator_cert/our_cert" -> false (no client cert configured on this channel)
    assert!(resp.is_ok(), "unauthenticated caller reached internal_send_tx");
    // Then assert the tx landed in tx_sender's outbox/queue, e.g. via a test hook into
    // AggregatorServer's TxSender state or DB row for the inserted try-to-send tx.
}
```
This demonstrates the LHS/RHS equality diverges: an unauthenticated caller (no cert) successfully reaches `internal_send_tx`, whereas the intended binding requires it to equal a caller holding `aggregator_cert_path`/`our_cert`.

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
```
