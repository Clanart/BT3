### Title
Nil Pointer Dereference via Ineffective Nil-Check on `CallArgs.Value` in `ToMessage` - ([File: api/api_kaia_blockchain.go])

### Summary
`CallArgs.ToMessage` contains a broken nil-check, `if &args.Value != nil`, which always evaluates to `true` because `&args.Value` is the address of a struct field and can never be `nil`, regardless of whether the `*hexutil.Big` pointer `args.Value` itself is `nil`. This defeats the intended guard and unconditionally calls `args.Value.ToInt()` on every request, including those where the RPC caller omitted the `"value"` field. [1](#0-0) 

### Finding Description
`ToMessage` builds the `types.Message` used by public read-only RPC methods (`eth_call`, `eth_estimateGas`, `kaia_call`, tracing APIs, etc.). It first initializes a safe default:
```go
value := new(big.Int)
if &args.Value != nil {
    value = args.Value.ToInt()
}
``` [1](#0-0) 

The correct check should be `if args.Value != nil`. As written, the branch is always taken because `&args.Value` (the address of the field on the `*CallArgs` struct) is never `nil`. Consequently, whenever a caller submits a call/estimate-gas request without a `"value"` field (a very common, entirely valid case), `args.Value` remains a `nil *hexutil.Big`, and the code still executes `args.Value.ToInt()`. In go-ethereum-style `hexutil.Big`, `ToInt()` is a pointer type conversion (`(*big.Int)(b)`), so calling it on a nil receiver does not itself panic — but it silently overwrites the safe `value := new(big.Int)` default with a `nil *big.Int`. That nil `*big.Int` is then propagated into `types.NewMessage(...)` as the message's `value` field. [2](#0-1) 

Downstream, the transaction-processing / EVM-transfer code path treats `Value()` as a normal `*big.Int` and performs arithmetic on it (e.g., sign checks, balance subtraction/addition via `big.Int.Sub`/`Add`/`Cmp`/`Sign`). Any of these standard library `big.Int` methods dereference internal fields of the receiver/argument and will panic with a nil pointer dereference when given a `nil *big.Int`. This mirrors the reported TensorFlow class of bug (CWE-476): a missing/ineffective nil check on an operand that is later used in a numeric computation routine, leading to a crash.

This is reachable purely through public RPC methods reachable by any unprivileged caller — `ToMessage` is invoked from `api/api_eth.go`, `api/api_kaia_blockchain.go`, and `node/cn/tracers/api.go`, all of which are standard `eth_call`/`eth_estimateGas`/debug-trace RPC entry points that any external client can invoke without authentication. [3](#0-2) 

### Impact Explanation
A node process crash caused by an unhandled nil pointer dereference is a Denial-of-Service condition reachable by any public, unauthenticated RPC caller sending a normal `eth_call`/`eth_estimateGas`/trace request that simply omits the `value` field. This matches the availability-only impact profile of the referenced CVE (CVSS `C:N/I:N/A:H`) and could crash or destabilize public RPC nodes, degrading availability of the network's RPC-serving infrastructure.

### Likelihood Explanation
High likelihood of reachability: omitting `value` in a JSON-RPC call object is an ordinary, common client pattern (not malformed input), so the vulnerable path is trivially triggered without any special privileges, and the guard intended to prevent it is provably non-functional due to the `&args.Value != nil` idiom bug.

### Recommendation
Fix the nil check to test the pointer itself instead of its address:
```go
value := new(big.Int)
if args.Value != nil {
    value = args.Value.ToInt()
}
```
Additionally, audit the codebase for similar `&x != nil` patterns on struct fields, since this idiom is a common but always-incorrect nil-check mistake that silently defeats guard logic.

### Proof of Concept
Submit a standard `eth_call` (or `kaia_call`/`eth_estimateGas`) JSON-RPC request that omits the `value` key in the call object, e.g.:
```json
{
  "jsonrpc": "2.0",
  "method": "eth_call",
  "params": [{"from": "0x...", "to": "0x...", "data": "0x"}, "latest"],
  "id": 1
}
```
Because `args.Value` deserializes to `nil` when omitted, and the guard `if &args.Value != nil` always passes, `value` becomes a `nil *big.Int` and is passed into `types.NewMessage`. Downstream arithmetic on this value (balance transfer/sign checks in the state-transition/EVM path) invoked while processing the resulting message can trigger a nil pointer dereference panic in the serving node.

**Uncertainty note:** I was not able to fully trace, within the available tool budget, the exact downstream call site inside `blockchain/state_transition.go` or the EVM transfer function that first dereferences the nil `*big.Int` `value` (e.g., which specific `big.Int.Sub/Add/Sign/Cmp` call triggers the panic), nor confirm the exact `hexutil.Big.ToInt()` implementation in this repo. The finding is based on the ineffective nil-check pattern being provably always-true (a compile-time-verifiable Go semantics fact) combined with standard `big.Int`/`hexutil.Big` semantics; a Devin session with full file access would be needed to pinpoint the exact panic call site for a complete PoC trace.
