### Title
Fee-on-transfer reward tokens cause reward-accounting overstatement and permanent freezing of user rewards in `BaseRewardPool`/`BaseRewardPoolV2`/`mWOMSVBaseRewarder` via `donateRewards` - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`, `rewards/mWOMSVBaseRewarder.sol`)

### Summary
`donateRewards()` is a public, unprivileged, permissionless function that lets any wallet inject additional reward tokens into a reward pool for any token already registered as a reward token. It calls `_provisionReward()`, which credits the pool's reward accounting (`historicalRewards`, `rewardPerTokenStored`, `queuedRewards`) using the caller-supplied `_amountReward` parameter, but only actually pulls tokens via `safeTransferFrom(msg.sender, address(this), _amountReward)`. If the reward token charges a transfer fee (fee-on-transfer token), the pool receives fewer tokens than the amount credited to reward accounting, permanently inflating claimable rewards beyond the pool's real token balance.

### Finding Description
`_provisionReward()` in `rewards/BaseRewardPoolV2.sol` (also duplicated in `rewards/BaseRewardPool.sol` and `rewards/mWOMSVBaseRewarder.sol`) performs: [1](#0-0) 

It transfers `_amountReward` via `safeTransferFrom`, then unconditionally adds the full nominal `_amountReward` to `historicalRewards` and uses it to compute `rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked()`. There is no check of the actual token balance delta received by the contract.

This function is reachable by `donateRewards`, which is `external` with no access control beyond requiring the token already be a registered reward token: [2](#0-1) 

Any unprivileged wallet holding a small amount of a registered fee-on-transfer reward token can call `donateRewards(_amountReward, _rewardToken)`. If the actual transferred amount is less than `_amountReward` (due to the token's transfer fee), `rewardPerTokenStored` for that token is inflated relative to the tokens actually held by the pool. As more users claim rewards via `getReward`/`_sendReward` (which uses `safeTransfer` for the full accrued `userRewards[...]` amount), the pool's real token balance will eventually be insufficient to pay out all accrued/earned rewards for that token, since the recorded `rewardPerTokenStored` overstates what was actually deposited.

The identical pattern (crediting accounting with the requested amount rather than the amount actually received) exists in: [3](#0-2) [4](#0-3) 

This directly mirrors the reported Velodrome `Bribe.sol` bug class: `notifyRewardAmount()`/`_provisionReward()` credits the nominal transferred amount into reward accounting while `_safeTransferFrom`/actual balance received is lower for fee-on-transfer tokens, and later payout (`deliverReward()`/`_sendReward()`) attempts to pay out the inflated amount, resulting in insufficient contract balance and reverts/frozen funds for later claimants.

### Impact Explanation
Once accounting is inflated beyond actual token holdings, some subset of stakers with legitimately earned rewards for that token will be permanently unable to claim them — `_sendReward`'s `safeTransfer` will revert once the pool's real balance of the fee-on-transfer token is exhausted before all `userRewards` are paid out. This is a permanent freezing of unclaimed yield for a subset of users, without any privileged action.

### Likelihood Explanation
Likelihood requires that a fee-on-transfer token be listed as a reward token for a given `BaseRewardPool`/`BaseRewardPoolV2`/`mWOMSVBaseRewarder` instance (via `queueNewRewards`, called by an authorized `manager`, e.g. `WombatStaking.vote()` when forwarding bribe/reward tokens to rewarders). Given such a token is registered, exploitation via `donateRewards` requires no special privilege — any wallet holding the token can trigger the broken accounting, and the resulting insolvency arises even from legitimate/unintentional use of `donateRewards` with such a token, not just adversarial action.

### Recommendation
In `_provisionReward()`, measure the actual amount received by comparing the contract's token balance before and after `safeTransferFrom`, and use that delta (instead of the nominal `_amountReward` parameter) for all reward accounting updates (`historicalRewards`, `queuedRewards`, `rewardPerTokenStored`).

### Proof of Concept
1. A fee-on-transfer token `FOT` (2% fee) is registered as a reward token for a `BribeRewardPool`/`BaseRewardPoolV2` instance via `queueNewRewards`.
2. An unprivileged user calls `donateRewards(100, FOT)`.
3. `_provisionReward` calls `safeTransferFrom(user, pool, 100)`; due to the 2% fee, the pool only receives 98 `FOT`.
4. `_provisionReward` nonetheless adds `100` to `historicalRewards` and computes `rewardPerTokenStored += (100 * 10**decimals) / totalStaked()`, i.e., based on 100 tokens instead of the 98 actually received. [1](#0-0) 
5. Over time, as stakers call `getReward`, cumulative `userRewards[FOT][...]` claims will exceed the pool's actual `FOT` balance, causing `_sendReward`'s `safeTransfer` to fail for the last claimant(s), permanently freezing their earned `FOT` rewards.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
```
