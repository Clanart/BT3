## Analysis

The Apache bug class is: an attacker-controlled value that is only ever expected to be set by a trusted party is written into a field that later drives an outbound network request, causing SSRF when the attacker-controlled value is actually attacker-reachable.

The closest reachable analog in this codebase is Chia DataLayer's **mirror mechanism**. A "mirror" coin is a plain, unauthenticated on-chain construct: anyone can spend any coin to create a coin with puzzle hash `create_mirror_puzzle().get_tree_hash()` (`P2_PARENT.curry(1)`), whose memos encode an arbitrary `launcher_id` plus an arbitrary list of URL strings [1](#0-0) . There is no signature or ownership check tying the mirror coin's creator to the DataLayer store owner — `get_mirror_info()` simply decodes whatever `launcher_id`/URLs were memo'd by whoever spent the parent coin.

On the receiving side, `DataLayerWallet.coin_added()` watches for any coin with that mirror puzzle hash, decodes the memos, and — as long as the wallet is already tracking that `launcher_id` (i.e., the victim subscribed to that store) — persists the attacker-supplied URLs into the local `dl_store` as a `Mirror` record, without validating the submitter's authority over the store: [2](#0-1) 

These stored URLs subsequently flow, unfiltered, into outbound HTTP requests made by the DataLayer service itself. `DataLayer.fetch_and_validate()` reads `servers_info` (populated from these URLs) and issues outbound requests to `server_info.url` via `insert_from_delta_file()` → `download_file()` → `http_download()`: [3](#0-2) [4](#0-3) 

No restriction is applied to the URL's scheme, host, or address (no blocking of loopback, link-local, RFC1918, or cloud-metadata addresses such as `169.254.169.254`), and the same URL is also forwarded, still attacker-controlled, to any configured downloader plugin's HTTP endpoint (`get_downloader()`), meaning the victim's DataLayer process (and any configured plugin) will make a network request to a destination chosen entirely by an unrelated third party's on-chain spend: [5](#0-4) 

This matches the Apache report's bug class precisely: a value provided by an unprivileged party (there: an HTTP request header value fed into mod_headers; here: a memo/URL fed into a mirror-coin spend) that should never influence outbound-request destinations ends up doing exactly that, enabling SSRF from a locally running, trusted service (mod_proxy / DataLayer) against attacker-chosen internal or external targets.

### Title
SSRF via unauthenticated DataLayer mirror coins injecting attacker-controlled URLs into outbound fetch/plugin requests - (File: `chia/data_layer/data_layer_wallet.py`, `chia/data_layer/data_layer.py`, `chia/data_layer/download_data.py`)

### Summary
Any unprivileged spend-bundle submitter can create a "mirror" coin (`create_mirror_puzzle()`) whose memos encode an arbitrary target `launcher_id` and an arbitrary list of URLs. If the victim's wallet already tracks that `launcher_id` (i.e., subscribes to that DataLayer store), the wallet unconditionally records these attacker-chosen URLs as a legitimate `Mirror`. The DataLayer service then uses these URLs as fetch targets for `http_download()` and as the destination for downloader-plugin POST requests, with no validation restricting the target host/IP/scheme.

### Finding Description
- `create_mirror_puzzle()` / `get_mirror_info()` place no requirement that the mirror-coin creator own or control the referenced `launcher_id`; the puzzle (`P2_PARENT.curry(1)`) simply lets whoever spends the parent coin choose the memoed `launcher_id` and URL list [1](#0-0) .
- `DataLayerWallet.coin_added()` accepts and persists these attacker-chosen URLs into `dl_store` as long as the wallet already tracks the target `launcher_id`, with only an empty-URL-list check, no source authentication [2](#0-1) .
- `DataLayer.fetch_and_validate()` shuffles and iterates `servers_info` (populated from mirror/subscription URLs) and passes `server_info.url` straight into `insert_from_delta_file()`/`download_file()`/`http_download()`, which performs an unrestricted `aiohttp` GET to `server_info.url + "/" + filename` [3](#0-2) [4](#0-3) .
- The same untrusted URL is also sent to configured downloader plugins via `get_downloader()`, causing the plugin process to also issue a request keyed off the attacker-chosen value [5](#0-4) .
- The codebase's own module documentation explicitly flags "mirror URLs" as an "external trust input" that "must continue to be verified," acknowledging the trust boundary but the verification only covers the *downloaded content* (against wallet-advertised roots), not the *destination* of the outbound request itself [6](#0-5) .

### Impact Explanation
Because DataLayer periodically and automatically fetches from these URLs in the background sync loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`), a passive victim who merely subscribes to a store (a normal DataLayer client action) is exposed to arbitrary outbound network requests from their own node/process, chosen by a completely unrelated on-chain party. Depending on the deployment (cloud VM, internal network), this permits SSRF-style probing/interaction with internal services (e.g., localhost admin ports, cloud metadata endpoints, internal LAN hosts) that the DataLayer host can reach but that should not be attacker-directed. It can also be used to trigger unwanted outbound connections to arbitrary external hosts for reconnaissance, DoS amplification (repeated automatic retries against a target), or to a downloader-plugin's `/handle_download` and `/download` endpoints with attacker-chosen URL values that are trusted at face value there too.

### Likelihood Explanation
Reachable by any unprivileged chain participant who can submit a spend bundle that creates a coin with the mirror puzzle hash and appropriate memos — no privileged keys, no interaction with the victim beyond the victim having previously subscribed to (tracked) the target store, which is a normal DataLayer usage pattern. The victim's background sync loop runs automatically without any manual action, making exploitation largely passive from the attacker's perspective once the mirror coin is confirmed on-chain.

### Recommendation
Require mirror coins to be authorized by the store owner (e.g., verify a signature/lineage tie to the DataLayer singleton owner, or restrict which coin sources can be treated as trusted mirrors) before persisting mirror URLs. Additionally, apply outbound-request destination validation (block loopback/link-local/private ranges and cloud metadata addresses, or provide an explicit allow-list/opt-in) before issuing `http_download()` requests or downloader-plugin POSTs derived from on-chain-sourced URLs.

### Proof of Concept
1. Attacker identifies a `launcher_id` known to be tracked/subscribed by a victim DataLayer node (store ids are public).
2. Attacker spends any owned coin to create a new coin with puzzle hash `create_mirror_puzzle().get_tree_hash()`, with a `CREATE_COIN` condition whose memo list is `[launcher_id, b"http://169.254.169.254/latest/meta-data/", ...]` — following exactly the format produced by `get_mirror_info()`'s expected decode (`memos[0]` = launcher_id, `memos[1:]` = URLs) [7](#0-6) .
3. Attacker submits and gets this spend confirmed on chain.
4. Victim's `DataLayerWallet.coin_added()` sees the mirror coin, decodes it, and since `launcher_id` is tracked, stores the attacker's URL as a legitimate mirror [2](#0-1) .
5. On the victim's next `periodically_manage_data()` cycle, `fetch_and_validate()`/`update_subscription()` picks up the malicious URL from `get_available_servers_for_store()` and issues an outbound HTTP GET to it via `http_download()` [8](#0-7) [9](#0-8) , completing the SSRF from the victim's DataLayer process to the attacker-chosen destination.

```python
def create_mirror_puzzle() -> Program:
    return P2_PARENT.curry(Program.to(1))


MIRROR_PUZZLE_HASH = create_mirror_puzzle().get_tree_hash()


def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
```

```python
async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```

```markdown
## Fragility Hotspots

- High-risk edits move work across DB writer transactions, `_update_confirmation_status()`, pending-root status changes, or wallet RPC calls. These boundaries encode publication and rollback assumptions.
- File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking. Concurrent service/plugin/server access should be treated as a real consistency concern.
- Empty-root normalization is subtle and historically uneven. Audit any change touching `bytes32.zeros`, `None`, `Root.node_hash`, or proof roots with both empty and non-empty stores.
- Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots, and file path/name validation must stay strict.
- DataLayer wallet code depends on singleton CLVM structure, odd singleton amounts, lineage proofs, and offer solver field names. Changes in wallet puzzle drivers or offer summaries can break this module without direct edits here.
- Tests for this module should cover lifecycle/order effects: pending batch to publish, confirmation promotion, wallet-unreachable sync retry, delta-file validation failure, grouped vs ungrouped filenames, unsubscribe retention, historical proof verification, and offer-created local mutations.
```
