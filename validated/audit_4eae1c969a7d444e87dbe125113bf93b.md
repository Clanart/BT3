## Analysis

The report's core broken invariant: **a single actor is trusted to self-certify facts about a transaction it also benefits from, with no cross-check binding "who did the work" to "who gets paid" per unit of work claimed.**

`pallet-consensus-incentives::on_executed` (`FeeHandler` implementation, called by `pallet-ismp` after a batch of messages executes) reproduces this exact pattern: [1](#0-0) 

It recovers a single `relayer_account` from **only the first message in the batch** (`messages.get(0)`), decoding its embedded signature over that one message's `consensus_proof`: [2](#0-1) 

It then pays that *one* recovered relayer for **every** `StateMachineUpdated` event that occurred anywhere in the whole batch, regardless of which relayer's consensus message actually produced each state-machine advance: [3](#0-2) 

### Title
Consensus-incentive reward misattribution lets a relayer steal other relayers' rewards by batch-ordering - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`on_executed` attributes **all** state-machine-update rewards in a processed message batch to whichever relayer's signature is recovered from the **first** message only, instead of matching each `StateMachineUpdated` event to the specific consensus message (and specific relayer) that produced it.

### Finding Description
`pallet-ismp` batches messages for execution and calls `FeeHandler::on_executed(messages, events)` once per batch with the full list of processed `MessageWithWeight` and the resulting `IsmpEvent`s. The consensus-incentives pallet:

1. Looks only at `messages[0]`. If it is a `Message::Consensus`, it recovers a single relayer account from the embedded `signer`/`consensus_proof` hash.
2. Collapses **all** `StateMachineUpdated` events across the entire batch into a `state_machine_id -> highest_latest_height` map.
3. Pays `relayer_account` (from step 1) the full block-span reward for **every** state machine in that map — including chains whose consensus advance was actually delivered by a *different* relayer's message elsewhere in the same batch.

Since `pallet-ismp` batches messages from potentially many relayers/transactions into one executed batch (a normal, permissionless operation — anyone can submit a consensus message), an attacker relayer can:
- Submit their own (even minimal/cheap) consensus message first in a batch alongside consensus messages from other honest relayers that update multiple other state machines, or
- Race to have their message land as `messages[0]` in a batch that also contains legitimate, unrelated consensus updates for other chains submitted by other relayers.

Because attribution is per-batch and keyed only to the first message, the attacker's account collects the treasury-funded reward (`T::Currency::transfer` from `TreasuryAccount`) for state-machine advances they did not deliver, and also mints reputation tokens (`T::ReputationAsset::mint_into`) for work performed by others.

### Impact Explanation
This is a direct "wrong beneficiary" fund-diversion bug in a reward-claim path: treasury BRIDGE/native funds and reputation-token mints intended for the relayer who actually delivered a given chain's consensus proof are instead paid to an unrelated party purely due to batch/message ordering. This falls squarely under the bounty's "reward claims ... must move exactly once and only to the rightful beneficiary and amount" pivot — no admin, governance, or malicious-peer assumption is required; any permissionless relayer submitting consensus messages can trigger it.

### Likelihood Explanation
Message batching in `pallet-ismp` is a normal execution path (not adversarial infrastructure), and multiple relayers submitting consensus proofs for different state machines in overlapping timeframes is expected behavior of the "relay race" model documented in the protocol (`docs/content/protocol/ismp/relayers.mdx`). An attacker only needs to get their own signed consensus message positioned first in a batch that also contains other relayers' consensus messages — achievable by normal transaction-pool ordering/priority manipulation, not by compromising any relayer or admin key.

### Recommendation
Attribute each `StateMachineUpdated` event to the relayer recovered from the specific `Message::Consensus` entry that produced it (matching by `state_machine_id`/height range or by carrying the relayer identity through the event), rather than defaulting the whole batch's rewards to `messages[0]`'s signer.

### Proof of Concept
1. Relayer A submits a valid consensus message updating `StateMachine::Evm(X)` late in a batch.
2. Attacker submits a trivial/self-signed consensus message (updating any state machine, or even a minimal valid one) that lands as `messages[0]` in the same executed batch — feasible since block-batch composition/ordering is not tied 1:1 to a single relayer's submission.
3. `on_executed` recovers `relayer_account` = attacker from `messages[0]`.
4. It iterates `events`, finds the `StateMachineUpdated` for `Evm(X)` (produced by Relayer A's message), and calls `process_message` crediting the **attacker** with the treasury reward and reputation mint for Relayer A's delivered work.
5. Repeat/scale across batches containing multiple state-machine updates to redirect the bulk of consensus-incentive rewards to the attacker while contributing minimal real work.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
