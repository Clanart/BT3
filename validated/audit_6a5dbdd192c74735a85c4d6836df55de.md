### Title
Unauthenticated operator attribution in payout OP_RETURN allows crediting an arbitrary operator for a withdrawal it never fronted - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The payout transaction, which anyone can construct once a withdrawal's Schnorr signature is public (posted on Citrea for any party to fulfill), embeds the "fronting" operator's x-only pubkey in a plain, unsigned OP_RETURN output. The bridge later derives who is credited as having funded the withdrawal (and therefore who is entitled to kickoff-based reimbursement) solely from this OP_RETURN byte string, with no proof that the named operator's own funds paid the output.

### Finding Description
`create_payout_txhandler` builds the payout tx with the user's `SIGHASH_SINGLE|ANYONECANPAY`-style key-spend witness for input 0/output 0 only, and appends an OP_RETURN output containing an arbitrary `operator_xonly_pk` value chosen by whoever constructs the transaction: [1](#0-0) 

The user's signature verified in `Operator::withdraw` only binds the withdrawal input/output pair (via `payout_txhandler.calculate_sighash_txin`), it does not bind or authenticate the OP_RETURN operator-pubkey output: [2](#0-1) 

Once the payout transaction is mined, the verifier scans it and trusts the OP_RETURN bytes verbatim as "the payer" with no signature check binding it to whoever actually supplied the funding inputs: [3](#0-2)  This is persisted as `payout_payer_operator_xonly_pk`: [4](#0-3) 

That value then autonomously drives the named operator's own reimbursement automation: `PayoutCheckerTask` looks up "unhandled payouts" filtered by the operator's own `xonly_public_key` matching the DB column, and if found, immediately consumes one of that operator's kickoff connectors via `handle_finalized_payout`: [5](#0-4) [6](#0-5)  The same unauthenticated attribution is later used to authorize `get_reimbursement_txs` via `validate_payer_is_operator`, which only compares the DB-stored (attacker-controlled) `payer_xonly_pk` against the local operator's key — it never re-derives payer identity from the actual Bitcoin inputs that funded the payout: [7](#0-6) 

The broken equality is: **`payout_payer_operator_xonly_pk` (OP_RETURN bytes, unauthenticated) == operator who actually funded the payout (holder of the spent Bitcoin inputs)**. Nothing in the protocol enforces this equality; it is purely self-declared plaintext data any transaction constructor can set, since the withdrawal's Schnorr signature (the only real authorization check) is scoped to input/output 0 alone and says nothing about additional funding inputs, change outputs, or the OP_RETURN payload.

### Impact Explanation
Because the withdrawal signature (`in_signature`/`in_outpoint`/`out_script_pubkey`/`out_amount`) is registered on Citrea for any operator to race to fulfill, any unprivileged party who observes it can construct and broadcast a valid payout transaction that fronts the withdrawal with their own BTC while stamping an **arbitrary operator's** x-only pubkey in the OP_RETURN instead of their own. That named operator's node will autonomously treat itself as the payer (`get_first_unhandled_payout_by_operator_xonly_pk` + `handle_finalized_payout`), consuming one of its limited kickoff connectors and round-collateral slots for a withdrawal it never funded, and proceeding through the kickoff/reimbursement flow to claim `bridge_amount` back from the bridge for a payout paid by someone else. This is precisely the Critical-class impact "an operator reimbursed for a payout it never funded," and can additionally grief a targeted honest operator by forcibly burning through its finite kickoff/round slots for withdrawals it did not choose to front, degrading its ability to service legitimate withdrawals.

### Likelihood Explanation
The withdrawal parameters (signature, input outpoint, destination, amount) are, by protocol design, meant to be picked up and raced on by any operator — they are not secret to a single privileged party, and constructing the payout transaction requires no special credential, no gRPC access, and no key beyond the constructor's own Bitcoin wallet for the funding inputs. The OP_RETURN pubkey field is entirely free-form and unchecked at signing time, so exploitation only requires broadcasting a self-crafted Bitcoin transaction — no verifier/operator/aggregator role is needed to trigger it. `verifier.rs`'s own comments acknowledge the field can be arbitrary/absent ("operator constructed the payout tx wrong"), showing the code already anticipates untrusted OP_RETURN content but never rejects or independently re-derives it from the funding side of the transaction.

### Recommendation
Do not trust the OP_RETURN operator-pubkey as sole proof of payer identity. Require the credited operator to cryptographically prove they funded the payout — e.g., require the OP_RETURN commitment (or a separate signature) to be signed/verifiable against the operator's registered key, or bind attribution to the transaction's actual funding inputs (verifiable ownership of the extra inputs beyond the withdrawal UTXO) rather than an unauthenticated data push. At minimum, `handle_finalized_payout`/`PayoutCheckerTask` should require operator opt-in/confirmation before automatically consuming kickoff connectors based on chain-observed OP_RETURN data.

### Proof of Concept
1. Watcher observes a pending Citrea withdrawal request with public fields `(withdrawal_id, in_signature, in_outpoint, out_script_pubkey, out_amount)`.
2. Attacker builds a payout transaction identical in structure to `create_payout_txhandler` (input = `in_outpoint` spent with `in_signature`; output 0 = `out_script_pubkey`/`out_amount`; anchor output; OP_RETURN = `move_txid || honest_operator_xonly_pk` where `honest_operator_xonly_pk` belongs to a targeted operator, not the attacker), funding any shortfall/fee with the attacker's own BTC.
3. Attacker broadcasts this transaction directly to Bitcoin (bypassing any operator gRPC entirely).
4. Once mined, the targeted honest operator's `PayoutCheckerTask` observes its own pubkey in the OP_RETURN via `update_finalized_payouts`/`get_first_unhandled_payout_by_operator_xonly_pk` and automatically calls `handle_finalized_payout`, consuming its kickoff connector and proceeding to claim `bridge_amount` reimbursement for a payout it never funded — breaking `payer_xonly_pk == actual funder` and matching the Critical impact "an operator reimbursed for a payout it never funded."

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
