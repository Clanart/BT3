### Title
Webhook `shop_domain` Header Is Trusted Without Being Covered by HMAC Verification, Enabling Cross-Shop Webhook Forgery - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
The Halborn finding describes a root cause pattern: an unverified input (the NFT token used in `craft()`) is trusted and acted upon without confirming it is actually bound to/owned by the authenticated caller. The same root-cause pattern exists in `shopify_app`'s webhook handling: the HMAC signature only authenticates the raw request body, while the `shop_domain` value — used by generated jobs to select *which shop's data to act on* — is read from a separate, unsigned header and never cross-checked against the verified payload's shop context.

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` computes `hmac_valid?` over `request.raw_post` only: [1](#0-0) 

The HMAC secret used is the app's shared client secret (`ShopifyApp.configuration.secret`/`old_secret`), which is identical for *every* shop that has installed the app — it is not shop-specific: [2](#0-1) 

Immediately after verifying only the body, the same module exposes a `shop_domain` helper that simply echoes an attacker-controlled request header, with no linkage to the HMAC-covered content: [3](#0-2) 

This `shop_domain` value is exactly what the gem's own documentation tells developers to trust and forward to background jobs: [4](#0-3) 

The generated job templates then use that untrusted `shop_domain`/`shop` value to look up a `Shop` record and perform privileged, destructive actions on it (e.g., permanently destroying the shop record on `app/uninstalled`, or running redaction on `customers/redact` / `shop/redact`): [5](#0-4) [6](#0-5) 

Because any merchant can legitimately install the app on their own shop and thereby obtain a valid `(body, HMAC)` pair signed with the app's single shared secret, that merchant can replay the request while substituting the `X-Shopify-Shop-Domain` header (or the `shop_domain` parameter in a custom controller built per the documented pattern) to point at a victim shop. `hmac_valid?` still returns true because the signature check never examined the shop header — mirroring the report's root cause: the code assumes the ERC721 `input`/NFT is legitimately controlled by the caller because a *related* check (the earlier lock/HMAC event) succeeded once, without re-verifying ownership/binding on every use.

### Impact Explanation
An attacker (any merchant with their own install of the vulnerable app) can forge webhook deliveries that are accepted as authentic and cause the app to act on a different, victim shop's stored record — e.g. `shop.destroy` in the uninstall job or redaction flows against `shop_domain` values the attacker chooses, none of which are constrained by the HMAC signature. This is a cross-shop data-integrity/destruction issue reachable purely over HTTP without any app-side vulnerability beyond following the gem's documented pattern.

### Likelihood Explanation
Exploitation only requires the attacker to be an unrelated, unprivileged merchant with a legitimate install of the same public app (a very low bar — comparable to the "any user can install the app" precondition in the original report where the attacker did not need to own the NFT initially, only needed the target resource to already be in a state reachable via a shared, unauthenticated-for-ownership code path).

### Recommendation
Do not use the raw `X-Shopify-Shop-Domain` header (or an unauthenticated `shop_domain` parameter) as the sole means of selecting which shop record to act upon. Bind the shop identity to the HMAC-verified payload itself (Shopify webhook bodies include the shop's domain/id in the JSON body) and compare it against the header before trusting it, or derive shop context exclusively from the verified payload content, matching the same pattern that `TokenExchange#reject_mismatched_requested_shopify_domain` already applies for session-based requests: [7](#0-6) 

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggers an `app/uninstalled` (or `customers/redact`) webhook, and captures the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair — a fully valid signature since the shared secret is identical across all shop installs.
2. Attacker replays the exact same body/HMAC to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds because only the body (not the shop header) is checked: [1](#0-0) 
4. The generated job (e.g. `AppUninstalledJob`) is invoked with `shop_domain: "victim.myshopify.com"`, looks up and destroys/redacts the victim's `Shop` record: [8](#0-7)

      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )

class AppUninstalledJob < ActiveJob::Base

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
