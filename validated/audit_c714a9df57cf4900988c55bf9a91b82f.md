### Title
Quadratic Lagrange interpolation in `ThresholdKeys::view`/`ThresholdKeys::new` enables CPU DoS via attacker-controlled `included`/`n` - (File: crypto/dkg/src/lib.rs)

### Summary
`Interpolation::interpolation_factor` performs a linear scan over the `included` signing set for every participant whose factor is computed. `ThresholdKeys::view` calls it once per included signer and `ThresholdKeys::new` calls it once per participant `1..=t`, producing O(k²) field operations where `k` (the signing set size, resp. `n`/`t`) is attacker-controllable up to `u16::MAX` via untrusted bytes parsed by `ThresholdKeys::read` or via the `included` vector passed to `ThresholdKeys::view`. This mirrors the reported quadratic-complexity DoS (linear search inside a loop over all participants).

### Finding Description
The analog of the Revolver `uniquePlayers` linear search is `Interpolation::Lagrange`'s interpolation factor, which iterates the full `included` list per evaluation, accumulating `num`/`denom` products:

- `interpolation_factor` loops over every `l in included`, performing field multiplications per element — O(k) per call [1](#0-0) .
- `ThresholdKeys::view` invokes `interpolation_factor` inside `for i in &included` — O(k²) over a caller-supplied, only-sorted `Vec<Participant>` bounded solely by `n` [2](#0-1) .
- `ThresholdKeys::new` invokes it inside `t.iter().map(...)` for `1..=t` — O(t²) during key construction [3](#0-2) .
- `ThresholdKeys::read` reaches `ThresholdKeys::new` with `t`/`n` parsed directly from the untrusted byte stream, each up to `u16::MAX` (65535), with no cost bound [4](#0-3) .

Additionally, `ThresholdView::interpolation_factor` layers a second O(k) linear search (`self.included.contains(&participant)`) on top of the O(k) Lagrange evaluation, and FROST calls this per signer when computing `binding`/`verify_share` inputs, compounding the quadratic factor on the signing path [5](#0-4) [6](#0-5) .

### Impact Explanation
A single maliciously crafted `ThresholdKeys` blob declaring `n = t = 65535` forces `read` → `ThresholdKeys::new` to perform ~4.3×10⁹ field multiplications (65535 factors × ~65535 loop iterations each, plus an inversion each) in `interpolation_factor` before any validation can fail. Any node calling `view` with a large `included` set — reachable from deserialized participant lists — pays O(k²) per call, and FROST's `complete` pays it again per signer via `ThresholdView::interpolation_factor`. This stalls the signing/verification thread, enabling resource-exhaustion DoS of the affected component without any secret knowledge.

### Likelihood Explanation
Reachability depends on whether untrusted parties can feed `ThresholdKeys::read` or a large `included` set to `view`/`ThresholdView::interpolation_factor`. Where these APIs parse externally supplied bytes (key recovery, protocol messages carrying participant lists), a single unauthenticated message triggers quadratic work; the u16 bound caps but does not eliminate the blowup (~4e9 ops is already minutes of CPU). No collusion or secret material is required.

### Recommendation
- Precompute Lagrange numerators/denominators once per signing set: compute the full numerator product `Π l` once (O(k)) and derive each factor via one inversion of `(share - i_f)` denominators, reducing `view`/`new` to O(k log k) or O(k) total.
- Alternatively, batch-invert all denominators with Montgomery's trick: O(k) multiplications + one inversion total.
- Bound `n`/`t` and `included.len()` at parse time in `ThresholdKeys::read` to a sane maximum before entering `ThresholdKeys::new`.
- Replace the `included.contains` linear search in `ThresholdView::interpolation_factor` with a `HashSet` built once in `view`.

blob.extend((C::ID.len() as u32).to_le_bytes());
blob.extend(C::ID);

blob.extend(u16::MAX.to_le_bytes());      // n
blob.extend(1u16.to_le_bytes());          // i
blob.push(1);                             // Interpolation::Lagrange
blob.extend(<C as Ciphersuite>::F::ZERO.to_repr()); // secret share
for _ in 0 .. u16::MAX {                  // verification shares
  blob.extend(<C as Ciphersuite>::G::generator().to_bytes());
}

Root cause: per-participant O(k) scans inside `interpolation_factor` invoked per participant by `view` and `new`, with sizes drawn from untrusted input.

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
