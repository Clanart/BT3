### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers a large up-front heap allocation from a handful of bytes - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes `t`, `n`, and `i` directly from the input stream, then immediately executes `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` branch before validating `ThresholdParams` or confirming that the corresponding data is actually present. `n` is an attacker-controlled `u16`, so a ~12-byte input forces an allocation of up to 65,535 field elements (~2–4 MB depending on the curve). This is the same bug class as CVE-2025-59375 (a small document causing disproportionate dynamic memory allocation in libexpat). [1](#0-0) 

### Finding Description
The deserializer reads `n` as a raw `u16` from the untrusted byte stream at `crypto/dkg/src/lib.rs:591-602`. For interpolation variant `0` (`Constant`), it performs `Vec::with_capacity(usize::from(n))` at line 608 before reading any of the `n` scalars and before `ThresholdParams::new(t, n, i)` is called at line 626 — meaning the size check happens only *after* the oversized allocation is made. An attacker supplies `interpolation = 0` and `n = 0xFFFF`; the allocator immediately reserves `65535 * size_of::<C::F>()` (~2 MB for Ristretto `Scalar`, ~4 MB for ed448 `Scalar`) even if the stream ends after the header. The subsequent `read_F` loop fails at the first missing element, but the allocation was already performed. The same unvalidated `n` then drives `for l in (1 ..= n)` for verification shares at lines 621-623, though that path is bounded by actual input bytes. [2](#0-1) 

By contrast, the sibling `Commitments::<C>::read` in `crypto/dkg/pedpop/src/lib.rs:110-128` sizes its allocation from `params.t()` supplied by the caller's own `ThresholdParams`, not from the byte stream, so it does not exhibit this amplification. [3](#0-2) 

### Impact Explanation
Any component that feeds untrusted bytes to `ThresholdKeys::read` (e.g., keys material supplied by a remote party or read from attacker-influenced storage) lets an unprivileged attacker amplify a handful of bytes into multi-megabyte allocations — roughly a 10^5× size amplification. Issued repeatedly, this exhausts heap memory and crashes the node. Beyond the allocation, the early `with_capacity` commit means the failure occurs before `ThresholdParams::new` can reject semantically invalid `(t, n)` pairs, so even parameters that would fail validation still cost the allocation. Availability impact without authentication: maps to Medium/High severity.

### Likelihood Explanation
Reachability requires a caller to deserialize `ThresholdKeys` from bytes an attacker controls. `ThresholdKeys::read` is a public API explicitly listed among untrusted-byte sinks, and `n` is a single `u16` field trivially set to `0xFFFF`. Each malicious blob is only ~12 bytes: `id_len(4) || C::ID || t(2) || n(2) || i(2) || interpolation(1) = 0`. No valid points, scalars, or proofs are needed — the allocation precedes all content parsing. The cap is bounded by `u16::MAX` (unlike the unbounded `u32` case in `coordinator/tributary/src/block.rs:92`, which is out of scope), so a single message is survivable; exploitation requires repeated submissions, which is realistic for any exposed deserialization endpoint.

### Recommendation
- Validate `t`, `n`, `i` via `ThresholdParams::new` *before* any allocation, and reject `n` exceeding a sane bound.
- Replace `Vec::with_capacity(n)` with `Vec::new()` and `push`, or chunk reads (as `networks/ethereum/src/machine.rs:51-60` already does for attacker-controlled lengths) so memory grows only with bytes actually consumed.
- Cap `n` against a protocol maximum (e.g., the tributary validator-set limit) prior to reading the interpolation variant.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
use dalek_ff_group::Ristretto;

// Build a minimal blob: id_len || C::ID || t || n=0xFFFF || i || interpolation=0
let mut blob = vec![];
blob.extend((Ristretto::ID.len() as u32).to_le_bytes());
blob.extend(Ristretto::ID);
blob.extend(1u16.to_le_bytes());        // t
blob.extend(u16::MAX.to_le_bytes());    // n = 65535 -> Vec::with_capacity(65535)
blob.extend(1u16.to_le_bytes());        // i
blob.push(0u8);                         // Interpolation::Constant

// ~20 bytes of input; forces allocation of 65535 * size_of::<Scalar>() (~2 MB)
// before read_F fails on the empty tail.
let res = ThresholdKeys::<Ristretto>::read(&mut Cursor::new(&blob));
assert!(res.is_err()); // errors only after the oversized allocation
```

Repeat the call in a loop against any endpoint that accepts serialized `ThresholdKeys` to drive memory exhaustion. The amplification factor is ~10^5× per request.
