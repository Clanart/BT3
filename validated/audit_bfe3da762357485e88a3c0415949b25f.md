### Title
Unverified-PoP blame proofs leak the ECDH shared key, decrypting the victim's secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The DKG's blame mechanism is designed so a recipient can reveal the ECDH shared key for an invalid message, enabling everyone to adjudicate fault. To prevent an attacker from co-opting another participant's per-message encryption key (`msg.key`) and thereby tricking a victim into publishing a blame proof that decrypts the *victim's* message, each `EncryptedMessage` carries a Schnorr proof-of-possession (`pop`). However, in `KeyMachine::calculate_share`, the decryption PoP is only *queued* into a `BatchVerifier` — if the decrypted share bytes fail to deserialize as a canonical scalar, the function returns early with `blame: Some(EncryptionKeyProof)` **before `batch.verify_with_vartime_blame()` is ever called**. The PoP is therefore never verified, and a blame proof revealing `recipient_enc_key * msg.key` is emitted for an unauthenticated message — the exact key-disclosure scenario XSA-403-style "shared region exposes unrelated data" class, mapped onto PedPoP's blame-disclosure channel.

### Finding Description
In `crypto/dkg/pedpop/src/lib.rs` `calculate_share` (lines 476–499):

```rust
for (l, share_bytes) in shares.drain() {
  let (mut share_bytes, blame) =
    self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
  let share =
    Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
      PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
    })?);   // <-- early return: batch.verify_* never runs, PoP never checked
  ...
}
batch.verify_with_vartime_blame().map_err(...)  // only reached if all shares deserialize
```

`Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:469–501) merely *queues* `msg.pop.batch_verify(...)` and unconditionally computes `key = ecdh(enc_key, msg.key)` and wraps it in an `EncryptionKeyProof` (a DLEq proof that this is the correct ECDH key for the recipient's registered `enc_pub_key` and `msg.key`). So `blame` contains the live ECDH shared key whether or not the PoP is valid.

The spec (spec/cryptography/Distributed Key Generation.md:28-35) and the code comment (encryption.rs:83-90) explicitly state the PoP exists so that an attacker reusing someone else's key X cannot cause a blame statement that reveals `bX` and hence the victim's message. Because the canonical-scalar check at line 480 returns *before* the batch verifier validates the queued PoP, that mitigation is bypassed: the attacker submits `msg.key` copied from victim Alice's `EncryptedMessage`, a garbage `pop`, and a garbage ciphertext. Decryption yields pseudorandom bytes that are almost never a canonical scalar, triggering the early `InvalidShare` error with `blame = Some(proof)`.

### Impact Explanation
The `EncryptionKeyProof` is a blame artifact distributed to validators (processor `VerifyBlame` path, processor/src/key_gen.rs:504-549, reads `EncryptedMessage` + `EncryptionKeyProof` and calls `AdditionalBlameMachine::blame`). Since the proof certifies the ECDH key for `(recipient.enc_pub_key, msg.key)`, and `msg.key` is the same ephemeral public key Alice used in her real `EncryptedMessage` to this recipient, the revealed key decrypts Alice's actual secret share via `cipher(context, ecdh)` (encryption.rs:101-133). A single malicious DKG participant thus publicly exposes an honest participant's Pedersen secret share destined for themselves — secret-share recovery material, defeating the confidentiality the per-message keys and PoP were added to protect. This is a High: an unprivileged protocol participant causes disclosure of another party's secret share bytes with only public inputs (a crafted `EncryptedMessage` fed to `EncryptedMessage::read` → `calculate_share`).

### Likelihood Explanation
Fully deterministic and trivially reachable: the attacker controls all bytes of their share message. They copy Alice's `msg.key` (visible in her broadcast `EncryptedMessage`), attach any `pop`/`msg` bytes, and send it as their share. The PoP is never evaluated because the deserialized "share" fails `from_repr` first. The only requirement is participation in the same DKG session as the victim and recipient.

### Recommendation
Verify the queued PoP (and the batch) before returning a blame proof, or restructure `calculate_share` so `blame` is only attached after `batch.verify_with_vartime_blame()` confirms the `BatchId::Decryption(l)` PoP — e.g., on `from_repr` failure, still run the batch check and emit `blame: Some(...)` only if the PoP verified (mapping a failed PoP to `blame: None`, consistent with the `BatchId::Decryption` arm at line 495). Alternatively, make `decrypt` itself return the proof only upon confirmed PoP validity.

### Proof of Concept
1. DKG with n ≥ 2; Alice (`a`) and attacker (`e`) send shares to recipient Bob (`b`).
2. `e` observes Alice's `EncryptedMessage` `M_a = (key=X, pop_a, msg_a)` addressed to `b`.
3. `e` constructs `M_e = EncryptedMessage { key: X, pop: <arbitrary 64 bytes parsed as SchnorrSignature>, msg: <arbitrary 32 bytes> }` and submits it as `e`'s share to `b`.
4. Bob calls `calculate_share`: `decrypt` queues `M_e.pop` verification (which would fail — it's bound to `from=e` and `e` doesn't know `x`) but returns `blame = EncryptionKeyProof { key: enc_key_b * X, dleq }`. `ChaCha20` decryption of the garbage `msg` yields non-canonical bytes, so `from_repr` fails and the function returns `Err(InvalidShare { participant: e, blame: Some(proof) })` before `batch.verify_with_vartime_blame()` runs.
5. Bob publishes the blame. Any observer applies `cipher(context, enc_key_b * X)` to Alice's `msg_a`, recovering her secret share plaintext — a share disclosure the PoP was specifically introduced to prevent.
