## Title
EvmHost.dispatch()/fundRequest() strand overpaid native ETH as protocol-controlled dust instead of refunding the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH via `msg.value` and swap it through Uniswap V2 for the exact `feeToken` amount needed (`post.fee`/`get.fee`/`amount`) using `swapETHForExactTokens`. This is the same bug class as H-01 (`SpeedBumpPriceGate.passThruGate`): any ETH sent in excess of the amount actually required is never returned to the caller.

### Finding Description
In all three entrypoints: [1](#0-0) [2](#0-1) [3](#0-2) 

`msg.value` is forwarded wholesale into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard UniswapV2 router logic computes the exact input required (`amounts[0] <= msg.value`) and refunds the difference (`msg.value - amounts[0]`) via `TransferHelper.safeTransferETH(msg.sender, ...)`. From the router's perspective, `msg.sender` of that inner call is `EvmHost` itself (since `EvmHost` is the one invoking the router), not the original caller of `dispatch()`/`fundRequest()`. The refunded dust therefore lands back on `EvmHost`, which is exactly what the code comment confirms: [4](#0-3) 

`receive() external payable {}` — described explicitly as "receive function for UniswapV2Router02, collects all dust native tokens." There is no logic anywhere in `dispatch()` or `fundRequest()` that computes `amounts[0]` and forwards the leftover back to `_msgSender()`/`post.payer`. The only way that trapped ETH can ever leave the contract is via the governance-gated `withdraw()`: [5](#0-4) 

which is `restrict(_hostParams.hostManager)` and sends to whatever `beneficiary` cross-chain governance selects — not necessarily (or ever, in practice) the original overpaying caller.

This contrasts directly with the pattern the same codebase already uses correctly elsewhere: `IntentGatewayV2`/`IntentGatewayV2SameChainTest`/`ExtrinsicIntents`/`IntrinsicIntents` explicitly compute `msgValue -= amounts[0]` after the identical `swapETHForExactTokens` call and refund the remainder to `msg.sender`: [6](#0-5) 

`EvmHost` itself — the lower-level primitive any `HyperApp` or a user routes native-fee dispatches through — has no equivalent refund step.

### Impact Explanation
Any caller (a `HyperApp` contract or an EOA) that invokes `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, or `EvmHost.fundRequest()` with `msg.value` greater than the exact ETH input the Uniswap swap consumes for the requested fee permanently loses the difference. That ETH becomes indistinguishable protocol-owned balance recoverable only through cross-chain governance withdrawal to an address of governance's choosing — unauthorized loss of user funds through a fully public, unprivileged entrypoint, matching the "stealing or loss of funds" impact category.

Because exact swap pricing (`getAmountsIn`) can shift between the moment a caller estimates `msg.value` off-chain and the moment the transaction executes (due to reserve changes from other swaps/dispatches), any caller who pads `msg.value` for safety margin — the same defensive habit the original H-01 report describes — loses that margin unrecoverably per call.

### Likelihood Explanation
High likelihood of occurrence in normal operation: `dispatch()`/`fundRequest()` are the base primitives documented for native-token fee payment (see `docs/content/developers/evm/messaging/post-requests.mdx`), and callers must estimate the ETH amount off-chain before the AMM price is finalized on-chain, so slight overpayment is a common/expected pattern rather than an edge case. No malicious relayer, prover, or governance actor is needed — a single unprivileged caller triggering the normal dispatch path is sufficient.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the returned `amounts` array and refund `msg.value - amounts[0]` back to `_msgSender()` (or `post.payer`), mirroring the pattern already implemented in `IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    (bool sent,) = _msgSender().call{value: msg.value - amounts[0]}("");
    if (!sent) revert WithdrawalFailed();
}
```

### Proof of Concept
1. Attacker (any EOA) calls `EvmHost.dispatch(DispatchPost{ dest, to, body, timeout, fee: X, payer: attacker })` with `msg.value = X_native_estimate` where `X_native_estimate` intentionally exceeds the ETH actually required to purchase `X` fee tokens via the configured Uniswap V2 pool (e.g., due to natural price slippage buffer, or because reserves shift favorably between quote and execution).
2. `EvmHost.dispatch` forwards the entire `msg.value` to `swapETHForExactTokens{value: msg.value}(X, path, address(this), block.timestamp)`. [7](#0-6) 
3. The router computes `amounts[0] < msg.value`, performs the swap, and refunds `msg.value - amounts[0]` — but to `EvmHost`'s own address (the router's caller), landing in `EvmHost.receive()`. [4](#0-3) 
4. `dispatch()` returns normally with `commitment` computed and event emitted; the attacker's transaction succeeds but the overpaid ETH balance now sits in `EvmHost`, with no code path returning it to the attacker.
5. The only recovery path is `EvmHost.withdraw()`, restricted to `_hostParams.hostManager` and payable to a beneficiary chosen through cross-chain governance — the original caller has no means to reclaim their excess ETH. [8](#0-7)

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
