## Title
Webhook `shop_domain` header is not covered by HMAC verification, allowing cross-shop webhook data spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` validates the authenticity of an incoming webhook solely by checking an HMAC over the raw request body, but the shop identity used by consumers of the module (`shop_domain`) is read directly from an unauthenticated HTTP header and is never cross-checked against anything the HMAC actually covers. This mirrors the reported bug class: a value ("receivingAssetId"/here "shop_domain") that has no cryptographic tie to the value that was actually verified/swapped is nonetheless used as the authoritative identifier for a security-sensitive downstream action (attributing webhook data to a tenant).

### Finding Description
`verify_request` computes HMAC only over `request.raw_post`: [1](#0-0) 

`shop_domain` is a completely separate accessor that simply echoes the `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, with no participation in the HMAC computation: [2](#0-1) 

`hmac_valid?` in `PayloadVerification` only ever hashes the raw `data` (body) with the app secret; the shop domain header is never included in the digest input: [3](#0-2) 

Because the webhook secret is the app's single client secret shared across *all* shops that installed the app (not a per-shop secret), any merchant that has installed the app can capture a genuine, validly-signed webhook (body + `X-Shopify-Hmac-Sha256`) for their own shop, then replay that exact body/signature to the app's webhook endpoint while substituting an arbitrary value (e.g. a different, unrelated merchant's domain) in the `X-Shopify-Shop-Domain` header. `verify_request` will still pass because it only re-computes the HMAC over the untouched body. The gem's own documentation instructs developers to build custom webhook controllers around exactly this trust model, using the unauthenticated `shop_domain` to route/attribute the payload to a shop-scoped job: [4](#0-3) 

The same disconnect exists in the generator-produced webhook controller template, which forwards `webhook_request.shop` (parsed by the underlying API gem, itself dependent on the header, not an HMAC-bound value) to a job: [5](#0-4) 

### Impact Explanation
An attacker who is a legitimate (but hostile) merchant of the app can forge the shop attribution of an authentic webhook body, causing the app to process/store data (e.g. product/order/customer payloads, or privacy webhooks such as `customers/data_request`, `customers/redact`, `shop/redact`) under a different, unrelated shop's tenant context. Depending on how the consuming job trusts `shop_domain` (e.g. looking up that shop's session/access token to act on the data, or writing/deleting records keyed by shop), this enables cross-shop data corruption, incorrect redaction/deletion for the wrong shop, or information leakage between tenants — a cross-shop access/integrity violation reachable from an unrelated-merchant HTTP request without any secret leak or privileged access.

### Likelihood Explanation
Exploitation requires only that the attacker's own shop have the app installed (a normal, unprivileged action any merchant can do) and the ability to capture and replay one legitimate webhook HTTP request with a modified header — no bypass of cryptography or access to the app secret is needed, since the header is entirely outside the signed data. This is a realistic, low-effort attack path built directly on the documented/intended usage pattern of the gem.

### Recommendation
Do not trust `HTTP_X_SHOPIFY_SHOP_DOMAIN` as an authenticated tenant identifier. Either:
- Bind the shop domain into the HMAC verification (e.g., require it to be included in the signed payload/verification context and reject if it disagrees with any shop identity embedded in the verified body), or
- Derive the shop identity exclusively from a source that is itself part of the authenticated payload (e.g., a per-shop signing secret so the HMAC is bound to a specific shop, or the shop domain embedded in the JSON body if present and validated), rather than an independent header.
At minimum, document prominently that `shop_domain` is unauthenticated and must not be used alone to select which shop's session/access token or records a webhook job acts upon.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event that causes Shopify to send a real webhook (e.g. `orders/create`) to the app's endpoint, capturing the raw body and its valid `X-Shopify-Hmac-Sha256` header.
2. Attacker resends the exact same body and HMAC header to the same endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `verify_request` recomputes the HMAC only from `request.raw_post`; since the body is untouched, `hmac_valid?` returns true and the request passes verification: [1](#0-0) .
4. The downstream controller/job reads `shop_domain` (now `victim-shop.myshopify.com`) and processes/attributes the attacker's own webhook payload as though it belongs to the victim shop, per the documented pattern: [6](#0-5) .

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
