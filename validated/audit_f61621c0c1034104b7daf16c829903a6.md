### Title
Tokenfactory Denom AllowList Bypass via EVM `bank` Precompile `send` - (File: `precompiles/bank/legacy/v630/bank.go` / `sei-cosmos/x/bank/keeper/send.go`)

### Summary
The bank precompile's `send` method (reachable by any EVM caller, specifically the ERC20-native-pointer contract) transfers tokenfactory-restricted denoms by calling `bankKeeper.SendCoins` directly, bypassing the `IsInDenomAllowList` authorization check that the Cosmos `MsgSend`/`MsgMultiSend` handlers enforce.

### Finding Description
`x/tokenfactory` denoms can be configured with a bank-level `AllowList`, restricting which addresses may send or receive the denom (`sei-cosmos/x/bank/keeper/send.go` `IsInDenomAllowList`, lines 501-524). This restriction is only checked in the msg-server layer: [1](#0-0)  for `MsgSend` and similarly for `MsgMultiSend`.

However, the EVM `bank` precompile's `send` method — reachable from any deployed ERC20-native pointer contract on behalf of an arbitrary EVM caller — calls `p.bankKeeper.SendCoins` directly without ever invoking `IsInDenomAllowList`: [2](#0-1)  (the current precompile version follows the same pattern, only checking that the caller is the registered ERC20-native pointer for the denom, not whether sender/receiver are allow-listed) [3](#0-2) .

`SendCoins` itself, the low-level keeper primitive, contains no allow-list enforcement — that logic lives only in `IsInDenomAllowList`, a separate helper that must be explicitly called by callers of `SendCoins`: [4](#0-3) . The bank precompile's `send` method is one such caller that omits this check, unlike the Cosmos-native `MsgSend`/`MsgMultiSend` paths which explicitly call it.

### Impact Explanation
An admin who creates a tokenfactory denom and configures an `AllowList` (e.g., to whitelist a permissioned distribution mechanism or restrict a security-token to KYC'd addresses) has a false sense of enforcement: any holder can register/use the ERC20-native pointer for that denom and transfer it to or from non-allow-listed addresses purely through the EVM `bank` precompile's `send` function, completely sidestepping the restriction that is otherwise enforced for native Cosmos `MsgSend` transactions. This is an unauthorized-transfer / access-control-bypass condition on a fund-transfer primitive.

### Likelihood Explanation
Any user who holds the restricted tokenfactory denom and can interact with its ERC20 pointer contract (which anyone can create via the `pointer` precompile, since pointer creation itself has no admin restriction) can trigger this bypass with a single `send`/`transfer` call on the pointer contract. No special privileges are required beyond holding or being sent the restricted asset via the pointer, making exploitation straightforward.

### Recommendation
Add an `IsInDenomAllowList` (and `BlockedAddr`) check for both sender and receiver inside the bank precompile's `send` (and any other code path such as `sendNative`/wasm bindings that ultimately call `bankKeeper.SendCoins`/`SendCoinsAndWei` for tokenfactory-restricted denoms), mirroring the checks already present in `sei-cosmos/x/bank/keeper/msg_server.go`'s `Send`/`MultiSend` handlers, or move the allow-list check into `SendCoins` itself so all callers are protected uniformly.

### Proof of Concept
1. Admin creates tokenfactory denom `factory/{admin}/restricted` and sets an `AllowList` containing only address `A` via `MsgUpdateDenom`.
2. Attacker `B` (not on the allow list) somehow receives/holds the denom through a non-checked path, or the token is routed through the ERC20-native pointer prior to allow-list configuration.
3. Attacker `B` registers/uses the ERC20 native pointer for `factory/{admin}/restricted` via the `pointer` precompile (`AddNativePointer`).
4. Attacker calls `bank.send(fromB, toC, "factory/{admin}/restricted", amount)` on the bank precompile (address `0x...1001`) from the pointer contract context.
5. The transfer to arbitrary address `C` (also not allow-listed) succeeds because `precompiles/bank/*/bank.go`'s `send` never calls `IsInDenomAllowList`, whereas the equivalent native `MsgSend` would have reverted with `"... is not allowed to send/receive funds"`.

**Note on uncertainty**: I verified the allow-list check is present only in `msg_server.go` and absent in the precompile's `send`/`SendCoins` call chain across multiple precompile versions inspected in the index. I was not able to fully trace every downstream caller of `SendCoins` (e.g., IBC transfer hooks, wasm bindings) within the available index to confirm whether other paths have the same gap; a full audit of all `SendCoins` call sites would be needed to scope the complete blast radius. If the user needs exhaustive verification of every call site, a Devin session with full repository access would be required to grep and confirm all invocations.

		return nil, err
	}

		return nil, err
