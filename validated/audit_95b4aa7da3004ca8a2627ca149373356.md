## Analysis

The Arrakis bug's broken invariant is: *"a security check (price-deviation) is validated once, but a later step trusts attacker-controlled data/callback without re-validating, silently invalidating the earlier check."* The closest structural analog I could verify in this codebase is in the git-credential trampoline, where the "is this really a GitHub host" check can be short-circuited by data the remote server itself controls.

### Title
Git credential-helper trusts an attacker-controlled `WWW-Authenticate` header to classify a remote as "GitHub Enterprise" and launches the enterprise sign-in flow against that host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git needs credentials for any remote (triggered by a `clone`/`fetch`/`pull`/`push`/submodule update against a URL the user opened, including one embedded in a cloned repo's `.gitmodules` or a link the user pasted into "Clone repository"), Desktop's credential-helper trampoline decides how to treat the host via `getEndpointKind`. This function has a real, network-based verification path (`isGitHubHost(endpoint)`), but before reaching it, it first honors any `wwwauth[...]` credential field that Git forwarded from the server's HTTP 401 response. [1](#0-0) 

### Finding Description
`getEndpointKind` classifies a credential request as `'enterprise'` purely because the remote server's response contained a `WWW-Authenticate` header whose value matches `realm="GitHub"` — no cryptographic or API-based confirmation is performed for this branch: [2](#0-1) 

The only path that actually calls out to verify the host (`isGitHubHost(endpoint)`) is reached exclusively via the `else` branch below, i.e. **only if** the attacker did not supply the spoofed header: [3](#0-2) 

`getCredential` then uses that unverified classification directly to decide whether to launch a GitHub sign-in flow for a host the user has no account for: [4](#0-3) 

`ui.promptForGitHubSignIn` takes the raw `endpoint` (derived straight from the attacker's server URL) and, since the hostname isn't `github.com`, calls `beginEnterpriseSignIn` and sets the sign-in endpoint to the attacker's own origin before showing the sign-in dialog: [5](#0-4) 

This mirrors the Arrakis pattern precisely: a legitimate validation exists (`isGitHubHost`, the network-verified "real" check), but a value entirely controlled by the untrusted counterparty (the HTTP response header from a git remote/proxy) is consumed *before* that check and is sufficient by itself to flip the trust decision — bypassing the intended verification exactly like the malicious router call in `SimpleManager.rebalance` bypassed the price-deviation check.

### Impact Explanation
An attacker who controls a git server, a MITM-capable proxy on the clone/fetch path, or a submodule/remote URL embedded in a cloned repository can respond to Git's authentication probe with `WWW-Authenticate: realm="GitHub"`. Desktop will then treat that arbitrary host as a GitHub Enterprise instance and drive the user into the "Continue with Browser"/enterprise sign-in flow scoped to the attacker's origin (`setSignInEndpoint(origin)`), which can be used to solicit and exfiltrate the user's GitHub Enterprise credentials/PAT, or bind an OAuth session to an attacker-controlled endpoint — matching the "unauthorized OAuth or account binding" / "credential exfiltration" impact classes.

### Likelihood Explanation
Any unprivileged action that causes Git to talk to an attacker-controlled endpoint is sufficient: adding/using a malicious remote, cloning a link a user clicked, or a submodule URL inside a cloned repository (submodule updates route through the same trampoline credential helper). No local access, admin rights, or prior malware is needed — only a normal git operation against a server the attacker controls.

### Recommendation
Never let an unauthenticated, remote-supplied `WWW-Authenticate` header alone determine that a host is a trusted GitHub/GitHub Enterprise instance. Either always perform the `isGitHubHost` network verification (fetch `/api/v3/meta` or equivalent, checking a signed/expected response) before honoring the header-based classification, or restrict the header-based fast path to hosts that are already present in the user's known-accounts list (so it can only ever *confirm*, never *establish*, GitHub-host status).

### Proof of Concept
1. Attacker stands up an HTTP git server (or a MITM proxy) at `https://evil.example.com/repo.git`.
2. Victim clones/fetches this URL in GitHub Desktop (e.g., via "Clone repository" using a link, or as a submodule referenced from an otherwise legitimate repo).
3. Git requests credentials over HTTPS; the attacker's server returns `401` with header `WWW-Authenticate: realm="GitHub"`.
4. Git forwards this as a `wwwauth[0]=...` field via the credential-helper protocol to Desktop's trampoline.
5. `getEndpointKind` matches the realm string and returns `'enterprise'` without calling `isGitHubHost`. [6](#0-5) 
6. `getCredential` sees no stored account for `evil.example.com` and calls `ui.promptForGitHubSignIn('https://evil.example.com')`. [7](#0-6) 
7. Desktop shows the sign-in dialog with `beginEnterpriseSignIn` scoped to the attacker's origin, prompting the victim to authenticate against what looks like a GitHub Enterprise sign-in. [8](#0-7) 

*Note*: I was not able to trace the full downstream enterprise sign-in UI code (`beginEnterpriseSignIn`/`setSignInEndpoint` implementation) within the indexed context to confirm exactly which credential-entry mode (browser OAuth vs. basic-auth form) is triggered by default for an arbitrary origin; that final confirmation would require a Devin session with full repository access to read `app/src/lib/stores/app-store.ts`'s sign-in store logic in full.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
