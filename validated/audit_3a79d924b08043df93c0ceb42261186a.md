## Confirmed: `MempoolManager` caches `SpendBundleConditions` without invalidating them on soft/hard-fork height crossings

This is a real analog of the OtterSec "executor cache inconsistency" report: the mempool caches a validated result (`SpendBundleConditions`, computed once with the CLVM/AGG_SIG flags active *at admission time*) and later reuses that cached result — including on the "full reinit" path that is supposed to be the authoritative re-validation path — without recomputing it under the flags that apply *now*.

### Finding Description
Each `MempoolItem` stores a `conds: SpendBundleConditions` field, computed once by `MempoolManager.pre_validate_spendbundle()` using `flags = get_flags_for_height_and_constants(self.peak.height, self.constants)` at the moment the transaction is admitted [1](#0-0) . These flags gate stricter ELF/CLVM parsing-style rules exactly like the report describes (e.g. `HARD_FORK_HEIGHT`, `SOFT_FORK9_HEIGHT`, `HARD_FORK2_HEIGHT` gates) [2](#0-1) .

Once admitted, `conds` is never recomputed for an item still sitting in the mempool. In `MempoolManager.new_peak()`, the "full reinit" path — which runs specifically when the simple chain-extension optimization does not apply (e.g., after a reorg, exactly the case where the flags for the new peak height could differ from the flags in effect when the item was first validated) — reuses the stale `item.conds` directly instead of recomputing it: [3](#0-2) 

`add_spend_bundle()` → `validate_spend_bundle()` accepts this pre-computed `conds` as an input parameter and never re-executes CLVM against it [4](#0-3) ; it only checks puzzle-hash/coin-record/fee/timelock consistency, not condition-parsing validity under current flags.

Downstream, `Mempool.create_bundle_from_mempool_items()` (legacy `create_block_generator`) uses `item.conds.cost` directly for budgeting [5](#0-4) , and even though the legacy path re-runs the final assembled generator once at the end with current flags [6](#0-5) , that re-run treats any single stale/now-invalid item as an unexpected assertion failure ("This should not happen") rather than pruning the offending item — the whole candidate block generation fails and returns `None`.

### Impact Explanation
If a stricter CLVM/condition-parsing rule is gated by height (analogous to `reject_callx_r10` in the report), a spend admitted to the mempool just before the gate activates keeps its pre-gate `SpendBundleConditions` cached. After the gate activates (especially via the "full reinit" `new_peak()` path after a reorg, which explicitly reuses `item.conds` unchanged), this now-invalid item remains in the mempool as if still valid, and is fed into block-generator construction using cost/condition data computed under obsolete rules. This can:
- Cause block-candidate generation to abort (`create_block_generator` returns `None`, logged as an unexpected error) whenever such a stale item is selected, creating a spend-triggered halt in transaction/block-generation processing for that farming attempt.
- Cause divergence between nodes: a node that never reorgs across the boundary keeps admitting/using post-gate-consistent conds, while a node whose mempool went through the "full reinit" reorg path keeps stale pre-gate conditions for previously-admitted items, producing different accept/reject decisions for the same spend bundle across otherwise-honest nodes.

This matches the report's core claim — a validity cache invalidated by a feature/fork-gate activation, but not flushed — reachable purely by submitting an ordinary spend bundle around the gate-activation boundary combined with a reorg (a scenario an unprivileged submitter can trigger simply by timing normal transaction submission around a known fork height and a normal fork/reorg event).

### Likelihood Explanation
Medium. It requires a natural chain reorg that straddles a height at which CLVM/condition-parsing flags change (fork heights are public/known, e.g. `HARD_FORK2_HEIGHT`, `SOFT_FORK9_HEIGHT`), plus an in-flight mempool item admitted on the pre-fork side. Reorgs across fork-activation heights are a realistic, if not routine, occurrence, and the "full reinit" path is explicitly the one invoked by such reorgs.

### Recommendation
On the `new_peak()` "full reinit" path (and any other path that migrates existing `MempoolItem`s across a peak-height change), recompute `SpendBundleConditions` via `pre_validate_spendbundle()`/`validate_clvm_and_signature` with the flags for the *new* peak height rather than reusing the previously cached `item.conds`. More generally, whenever `get_flags_for_height_and_constants()` would return a different flag set for the new peak than for the height the item was originally validated at, the cached `conds` for that item should be invalidated and recomputed (or the item dropped) before it can be used for cost accounting or block generation.

### Proof of Concept
Conceptual reproduction (not run, since this is a design/logic analysis, not an executed exploit):
1. Node peak height is just below a fork-height gate (e.g. `SOFT_FORK9_HEIGHT - 1`) that will newly reject a certain condition/opcode pattern.
2. Submit a spend bundle exploiting the soon-to-be-rejected pattern; it is admitted via `pre_validate_spendbundle()` using pre-gate flags, and `MempoolItem.conds` is cached as valid.
3. Trigger (or wait for) a short reorg that crosses the gate height, forcing `MempoolManager.new_peak()` down the "full reinit" branch.
4. Observe that `add_spend_bundle(item.to_spend_bundle(), item.conds, ...)` re-admits the item using the stale, pre-gate `conds` [3](#0-2)  without re-running CLVM under the new, stricter post-gate flags.
5. When this item is later selected for block-generator construction, either the generator-build step aborts unexpectedly (logged as "this should not happen") [7](#0-6) , or — on nodes whose mempool never underwent the reinit path — the item is simply treated as still-valid, producing a state/behavior mismatch between nodes for the same spend bundle around the fork boundary.
