This confirms `Operator::withdraw` broadcasts the payout tx directly via `self.rpc.send_raw_transaction(&signed_tx)` (`core/src/operator.rs:686-689`), with `replaceable: None` passed to `fund_raw_transaction` (`core/src/operator.rs:656-669`), meaning the RBF flag is left to node/wallet defaults (Bitcoin Core's `-walletrbf` defaults to enabled), so the operator's payout broadcast is typically opt-in-RBF-signaled and visible in the public mempool prior to confirmation.

### Title
Unsigned outputs in `create_payout_txhandler`'s `SinglePlusAnyoneCanPay` payout tx let anyone strip the operator OP_RETURN and permanently orphan a withdrawal's reimbursement attribution - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the payout transaction with the user's `SinglePlusAnyoneCanPay` signature covering only input 0 and output 0 (the user payout output); the anchor output and the operator-identifying OP_RETURN output are completely unsigned. Anyone who observes the operator's broadcasted-but-unconfirmed payout transaction in the mempool can extract the witness and construct a conflicting, fee-bumped replacement that keeps output 0 (so the withdrawal still gets paid and Citrea marks it fulfilled) but funds the transaction with their own BTC and omits the OP_RETURN entirely, so `Verifier::update_finalized_payouts` records `operator_xonly_pk = None` for that withdrawal forever.

### Finding Description
The binding claimed to hold is: `attributed_operator_xonly_pk (in withdrawals.payout_payer_operator_xonly_pk) == operator who actually funded the payout that fulfills the withdrawal`. This binding is broken because the signature scheme used to authorize the payout tx does not cover the OP_RETURN output at all.

- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a 3-output tx: user output (index 0), anchor (index 1), OP_RETURN with the operator's xonly pk (index 2). The witness is set via `set_p2tr_key_spend_witness(&user_sig, 0)` where `user_sig.sighash_type == SinglePlusAnyoneCanPay`, which under BIP-341/342 covers only input 0 and its corresponding output (index 0). Outputs 1 and 2, and any additional inputs, are unconstrained by the signature.
- `Operator::withdraw` (`core/src/operator.rs:560-691`) verifies the user's signature only over input0/output0 (`core/src/operator.rs:630-637`), funds the tx via `fund_raw_transaction` with `replaceable: None` (defaulting to the node's `-walletrbf` setting, commonly enabled) (`core/src/operator.rs:652-673`), signs, and calls `self.rpc.send_raw_transaction(&signed_tx)` directly (`core/src/operator.rs:686-689`) — broadcasting to the public mempool before confirmation.
- Because `SinglePlusAnyoneCanPay` explicitly permits third parties to add/replace inputs and outputs beyond index 0, any attacker who observes this unconfirmed transaction can extract the operator's public witness and construct a competing transaction: same input0 (withdrawal UTXO) and witness, same output0 (unchanged, satisfying BIP-125/consensus), but funded by the attacker's own inputs, with the anchor and OP_RETURN outputs dropped, at a higher fee rate — a standard BIP-125 RBF replacement, requiring no keys, no majority hashrate, and no verifier/operator privileges.
- Once the attacker's variant confirms instead, `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2354`) calls `get_first_op_return_output` (returns `None`), so `operator_xonly_pk` is set to `None` and persisted via `db.update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`) — irreversibly, since this is the one time this withdrawal's row is populated.
- `get_payout_info_from_move_txid` (`core/src/database/verifier.rs:253-280`) will now always return `(None, blockhash, txid, idx)` for this withdrawal's move-to-vault txid. Two downstream guards then permanently prevent any legitimate reimbursement: `Verifier::is_kickoff_malicious` treats `operator_xonly_pk_opt == None` as "assuming malicious" (`core/src/verifier.rs:1882-1885`), and `Operator::send_asserts` errors out entirely when `payout_op_xonly_pk_opt` is `None` (`core/src/operator.rs:1284-1286`). No existing guard (deposit validity, `SECP.verify_schnorr`, storage proof checks, or the presigned tx graph) restores attribution once the OP_RETURN-less transaction confirms, because the signature never protected that output in the first place.

### Impact Explanation
The withdrawal's underlying deposit's move-to-vault UTXO becomes permanently unreimbursable to any operator: `is_kickoff_malicious` will flag any operator's kickoff for this deposit as malicious (triggering challenge/collateral loss for that operator if attempted), and `send_asserts` hard-errors before an operator can even complete the reimbursement flow. This matches the Critical category "a move-to-vault UTXO permanently frozen" and "an honest operator permanently unable to be reimbursed" — the operator that intended to front this specific withdrawal can never be credited for it, since the L1 side is already fulfilled by the attacker's substitute funding. The attack is repeatable per-withdrawal and requires no privileged role, only mempool visibility and enough BTC to outbid the operator's fee.

### Likelihood Explanation
The precondition is simply that the operator's payout transaction is broadcast to a public/observable mempool before confirmation and is RBF-signalable (the default `fund_raw_transaction` call in `core/src/operator.rs` leaves `replaceable: None`, deferring to node policy, which is commonly RBF-enabled). No verifier/operator keys, TLS, or Citrea access are required — only the ability to see the mempool and pay a marginally higher fee than the operator's payout tx, both squarely inside the stated unprivileged attacker capabilities ("broadcast Bitcoin transactions and pay fees"). This is feasible on every operator payout attempt and is repeatable across withdrawals/operators.

### Recommendation
Bind the OP_RETURN (and any output the protocol depends on for attribution) into the signed sighash — e.g. have the user sign with `AllPlusAnyoneCanPay` covering all current outputs, or require the operator's own signature/commitment (rather than the withdrawing user's) to authorize which outputs exist, or restructure so operator attribution is committed on Citrea (e.g., embedded in the withdrawal request itself) instead of being inferred post-hoc from an unauthenticated OP_RETURN in the confirmed L1 tx.
