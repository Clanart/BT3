### Title
Stash-pop heuristic silently drops the user's stash and destroys uncommitted work on unrecognized conflict output - (`File: app/src/lib/git/stash.ts`)

### Summary
`popStashEntry` decides whether a `git stash pop` actually succeeded by inspecting only the process exit code and whether `stderr` is empty, rather than verifying that the stash contents were actually merged into the working directory. When the heuristic misfires, Desktop calls `dropDesktopStashEntry`, permanently deleting the only copy of the user's stashed (uncommitted) changes, exactly mirroring the report's root cause: a fallback/error path that omits validating a value it should account for before finalizing an irreversible action.

### Finding Description
`popStashEntry` in [1](#0-0)  runs `git stash pop --quiet <name>` and only pre-registers `DugiteError.MergeConflicts` as an "expected" error. In the `.catch` handler, any other exit-code-1 failure whose `stderr` happens to be empty is treated as "stash was actually applied successfully but git reported oddly," and the code proceeds to call `dropDesktopStashEntry(repository, stashSha)` — permanently removing the stash from the reflog.

The comment above this logic, written by the Desktop maintainers themselves, admits the fragility of this assumption:
```
// popping a stashes that create conflicts in the working directory
// report an exit code of `1` and are not dropped after being applied.
// so, we check for this case and drop them manually unless there's
// anything in stderr as that could have prevented the stash from being
// popped. Not the greatest approach but stash isn't very communicative
```
and further up, the same pattern/uncertainty is documented for `createDesktopStashEntry` in [2](#0-1) : "Here be dragons... I got curious about the assumptions made in the following logic."

The broken invariant: **"exit code 1 + empty stderr" is treated as proof the stash was fully applied**, when in reality git can exit with code 1 for reasons unrelated to a successful-but-noisy merge (e.g. conflicts on binary files, conflicts whose message format isn't matched by dugite's `MergeConflicts` classifier, filesystem write failures reported only via stdout/warnings, or case-insensitive/path-collision issues on the target platform). None of these cases are guaranteed to leave stderr empty-but-safe; they are simply *not classified* as `MergeConflicts` by the upstream error parser, so they fall through to the "assume success, drop the stash" branch.

Since the target branch content is fully attacker-controlled (a cloned/fetched malicious repository, or a branch/PR the user checks out), an attacker can craft file content that:
1. Conflicts with the user's stashed changes when popped (deliberately, e.g. via a repository that a victim clones and immediately starts working on), and
2. Produces a git failure mode that isn't recognized by dugite's conflict-detection regex (e.g., binary-file merge conflicts, which git often reports differently from textual `CONFLICT (content)` lines) while `stderr` stays empty.

When this happens, `popStashEntry` silently deletes the stash entry via `dropDesktopStashEntry` in [3](#0-2) , even though the user's changes were never actually restored to the working directory. This code path is reachable both from the explicit "Restore stash" UI action in [4](#0-3)  and from the automatic "bring my changes" branch-switch flow in [5](#0-4) , which stashes changes, checks out the (attacker-influenced) target branch, and immediately calls `popStashEntry` without any post-hoc verification that the working directory actually contains the expected content.

### Impact Explanation
The user's uncommitted work — which may represent significant unsaved local changes — is irrecoverably deleted with no warning and no error surfaced to the UI (the failure path swallows the anomaly and proceeds as if successful). This is a silent, permanent loss of the user's own changes, and if the working directory is left in a partially/incorrectly merged state, any subsequent commit the user makes will silently omit or corrupt the changes they believed were restored — matching the "silent corruption of what the user commits" impact category.

### Likelihood Explanation
Exploitation requires only that a victim clone/fetch and check out an attacker-authored branch (a completely ordinary Desktop workflow) while having local stashed/uncommitted changes that collide with attacker-crafted file content in a way git reports outside the recognized `MergeConflicts` error signature (e.g., binary conflicts). No elevated privileges, social engineering beyond "open this repo/branch," or local/physical access are required, but it does depend on hitting one of the non-standard git failure formats not covered by dugite's classifier, which the maintainers' own comments acknowledge as an unreliable heuristic ("not the greatest approach").

### Recommendation
Do not infer stash-pop success from exit code and stderr length. After a `git stash pop` failure not classified as `MergeConflicts`, re-run `getStatus`/`getWorkingDirectoryConflictDetails` to positively confirm the stash contents are present (e.g., verify the stash's tree diff is reflected in the working directory or index) before calling `dropDesktopStashEntry`. If verification is inconclusive, surface an error to the user and leave the stash entry intact rather than deleting it.

### Proof of Concept
1. Attacker publishes a repository/branch containing a binary file (or another change) engineered to produce a merge conflict when `git stash pop` is applied, in a form that dugite's `MergeConflicts` pattern does not recognize (verifiable by testing `git stash pop` locally against dugite's regex list), while emitting no output to `stderr`.
2. Victim opens the repository in Desktop, makes local uncommitted edits, and either:
   - Uses "Bring my changes" while switching to the attacker's branch (`checkoutAndBringChanges` in `app-store.ts`), or
   - Manually creates a stash and clicks "Restore" (`StashDiffHeader.onRestoreClick`).
3. `git stash pop` exits 1 with empty stderr and no `MergeConflicts` classification.
4. `popStashEntry`'s catch handler treats this as "popped successfully but noisy" and calls `dropDesktopStashEntry`, permanently deleting the stash.
5. The victim's working directory does not actually contain their restored changes (or contains an unresolved/incorrect merge), and there is no stash left to recover from — the changes are gone with no error shown.

export async function popStashEntry(
  repository: Repository,
  stashSha: string
): Promise<void> {
  // ignoring these git errors for now, this will change when we start
  // implementing the stash conflict flow
  const expectedErrors = new Set<DugiteError>([DugiteError.MergeConflicts])
  const stashToPop = await getStashEntryMatchingSha(repository, stashSha)

  if (stashToPop !== null) {
    const args = ['stash', 'pop', '--quiet', `${stashToPop.name}`]
    await git(args, repository.path, 'popStashEntry', {
      expectedErrors,
    }).catch(e => {
      // popping a stashes that create conflicts in the working directory
      // report an exit code of `1` and are not dropped after being applied.
      // so, we check for this case and drop them manually unless there's
      // anything in stderr as that could have prevented the stash from being
      // popped. Not the greatest approach but stash isn't very communicative
      if (
        e instanceof GitError &&
        e.result.exitCode === 1 &&
        e.result.stderr.length === 0
      ) {
        log.info(
          `[popStashEntry] a stash was popped successfully but exit code ${e.result.exitCode} reported.`
        )
        // bye bye
        return dropDesktopStashEntry(repository, stashSha)
      }
      return Promise.reject(e)
    })
  }
}
