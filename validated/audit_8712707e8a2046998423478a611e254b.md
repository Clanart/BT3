### Title
Race Condition in Gasless TxPool Admission Control via Shared-Lock Read-Modify-Write on `knownTxs` Map - (File: kaiax/gasless/impl/tx_pool.go)

### Summary
`GaslessModule.PreAddTx` acquires only a **read lock** (`g.knownTxsMu.RLock()`) while performing a check-then-act sequence (`numQueue()` read followed by `knownTxs.add()` write) on the shared `knownTxs` map, a plain unsynchronized Go `map[common.Hash]*knownTx`. Because `RLock` permits multiple concurrent callers, two or more goroutines can execute `PreAddTx` at the same time, both observe the same pre-mutation `numQueue()` count, and both proceed to write into the map — an unsynchronized concurrent map write. This mirrors the underlying bug class in CVE-2020-10575: insufficient locking around shared, reference-counted per-session state permitting premature/duplicate mutation, only here the "session" object is the gasless bundle-tx admission map used for KIP-247 gasless swaps.

### Finding Description
`PreAddTx` is the sole point at which incoming gasless bundle transactions (approve/swap txs, KIP-247) are admitted into the queue-side tracking structure `knownTxs`, subject to the `GetMaxBundleTxsInQueue()` limit: [1](#0-0) 

Note the lock discipline mismatch across the module's other mutators of the same map — `IsReady`, `PreReset`, and `PostReset` all take the **exclusive** write lock `g.knownTxsMu.Lock()`: [2](#0-1) [3](#0-2) [4](#0-3) 

But `PreAddTx` — invoked directly from the transaction-pool insertion path for every submitted transaction — only takes `RLock()`, while itself calling `g.knownTxs.add(...)`, a plain map write: [5](#0-4) 

Since `knownTxs` is a bare Go map (not `sync.Map`, no internal locking), two concurrent `RLock`-held goroutines calling `add()` simultaneously constitute a data race on the map's internal buckets. Go's runtime detects concurrent unsynchronized map writes and will trigger a `fatal error: concurrent map writes` process crash (unrecoverable, not a panic that can be caught) whenever two callers hit this path close enough in time. Additionally, even absent an outright crash, the TOCTOU pattern (`numQueue()` check, then `add()`) is not atomic with respect to other `PreAddTx` callers under `RLock`, so the intended admission limit `GetMaxBundleTxsInQueue()` can be exceeded by concurrent submissions, since multiple goroutines read the same pre-increment count before any of their writes land.

### Impact Explanation
An unprivileged party submitting transactions to the public RPC (`eth_sendRawTransaction` / bundle submission) can trigger this race merely by sending multiple gasless bundle transactions (KIP-247 approve/swap transactions) concurrently, which is exactly the kind of untrusted, externally-reachable input this module exists to process (`kaiax/gasless/README.md`). The consequences are either:
1. A node crash via Go's `fatal error: concurrent map writes` when the transaction pool's parallel/insertion pipeline calls `PreAddTx` for two gasless bundle txs at once, and
2. Bypass of the `GetMaxBundleTxsInQueue` admission control, allowing the queue-tracking accounting used elsewhere (e.g., `numExecutable()` limits enforced in `IsReady`, which gate how many bundle txs can enter `pending`) to be inconsistent with the real txpool state, undermining the pool's designed rate-limiting for gasless bundle transactions.

### Likelihood Explanation
The transaction pool processes multiple incoming transactions concurrently (e.g., via `AddRemotes`/batch insertion and RPC handling goroutines), so two gasless bundle transactions arriving close together from the same or different senders is a normal, easily reproducible scenario for anyone submitting transactions to a public Kaia RPC endpoint — no special privileges are required.

### Recommendation
Change `PreAddTx` to acquire the exclusive write lock (`g.knownTxsMu.Lock()`) rather than `RLock()`, matching the locking discipline already used in `IsReady`, `PreReset`, and `PostReset`, so that the check (`numQueue()`) and mutation (`add()`) on `knownTxs` are atomic with respect to all other paths that read or write the same map.

### Proof of Concept
Not independently executed; the race is evident from the code paths cited above. Conceptually:
1. Submit two distinct valid GaslessApproveTx/GaslessSwapTx (or bundle) transactions from two different sender keys concurrently to the RPC endpoint (e.g., two parallel `eth_sendRawTransaction` calls) such that the tx pool's insertion logic invokes `GaslessModule.PreAddTx` for both nearly simultaneously.
2. Under Go's race detector or under load, both goroutines pass `g.knownTxsMu.RLock()` concurrently and both execute `g.knownTxs.add(tx, TxStatusQueue)` on the shared map, producing a data race; running with `-race` or under sufficient concurrency reliably surfaces `fatal error: concurrent map writes`, crashing the node process. Absent a crash, the two `numQueue()` reads observed before either write commits can each pass the `< GetMaxBundleTxsInQueue()` check, allowing the queue to exceed its configured cap.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
