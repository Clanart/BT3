## Analysis

The C4 report's core broken invariant: a **permissionless, incentivized function performs an on-chain swap using caller-influenced parameters with no protection over the leftover/output value**, letting execution economics leak value away from the rightful party. I looked for the same shape — public entrypoint → uniswap swap → unprotected balance handling — inside Hyperbridge's EVM contracts.

`EvmHost.sol` contains three public, unprivileged, native-token-accepting entrypoints that each perform an *exact-output* Uniswap V2 swap to buy `feeToken` with `msg.value`: [1](#0-0) [2](#0-1) [3](#0-2) 

All three call `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(amount, path, address(this), block.timestamp)` and **never capture the returned `amounts` array, and never refund any unspent native token back to `_msgSender()`**.

This is directly contradicted by the sibling implementation in `IntentGatewayV2.placeOrder`, which performs the identical swap pattern but correctly captures the swap cost and refunds the difference to the caller: [4](#0-3) 

and by the project's own UniswapV2-compatible wrapper contracts (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`), which explicitly compute and return unspent ETH to `msg.sender`: [5](#0-4) [6](#0-5) 

Since `swapETHForExactTokens` is exact-output, the standard UniswapV2Router02 implementation refunds unspent ETH to *its caller*, and the caller here is `EvmHost` itself (it calls the router directly with `address(this)` as token recipient). Because `EvmHost` doesn't forward that refund onward, every native-funded call to `dispatch()`/`fundRequest()` that sends more ETH than the exact swap cost silently donates the difference to the Host contract instead of returning it to the user who paid it.

### Title
Native-token fee payment in `EvmHost.dispatch()`/`fundRequest()` permanently strands unspent ETH instead of refunding the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in `EvmHost.sol` let any caller pay for cross-chain message/relayer fees with native ETH by triggering an internal `swapETHForExactTokens` call. Because callers must send `msg.value` as an upper bound on an unknown, live AMM price, they must always overestimate the ETH they send. Unlike `IntentGatewayV2.placeOrder`, which correctly refunds the swap's leftover ETH, `EvmHost` never captures the swap's return value nor forwards a refund — the excess is silently absorbed into the Host contract's balance.

### Finding Description
`swapETHForExactTokens` is an exact-output swap: the caller supplies `msg.value` as `amountInMax`, and the router refunds unused ETH to whoever called it. In `EvmHost.dispatch()`/`fundRequest()`, that caller is `EvmHost` itself, since the Host directly invokes the router with `address(this)` as token recipient [7](#0-6) . The Host discards the swap's return data and takes no further action with any leftover native balance — there is no `msgValue -= amounts[0]; refund(...)` step as is present in `IntentGatewayV2.placeOrder` [8](#0-7) .

Because `amount`/`post.fee`/`get.fee` is a caller/user-specified target output and AMM prices move between quote and execution (normal drift, MEV, or an attacker deliberately front-running the transaction to worsen the price), a caller who does not send an exact-to-the-wei `msg.value` will always overpay, and that overpayment is not recoverable through the Host's public interface. Existing guards (`notFrozen` modifier) do nothing to prevent this — they only check the freeze state, not value accounting.

### Impact Explanation
Every native-token-funded call to `dispatch()` or `fundRequest()` results in unrecoverable loss of the caller's excess ETH once the swap executes favorably (which is the common case, since callers must pad `msg.value` for slippage/price uncertainty). This is a direct, protocol-level loss of user funds triggered through an ordinary, unprivileged, documented usage path (native-token fee payment is explicitly advertised in the docs), not a peripheral griefing vector.

### Likelihood Explanation
High. Any user who pays request/relayer fees in native token (the documented, recommended flow per `docs/content/developers/evm/messaging/post-requests.mdx`) is affected on essentially every call, since exact-priced `msg.value` is not practically achievable against a live pool. An attacker can also amplify the loss deterministically by front-running to push the swap's actual cost down relative to the padded `msg.value`, maximizing the amount left stranded in the Host contract.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost)` with `post.fee = 100 feeToken` and sends `msg.value = 1 ether` (padded for slippage since the exact ETH cost of 100 feeToken via the pool cannot be known precisely at submission time) — see the pattern exercised in `evm/tests/foundry/IntentGatewayV2Test.sol:3461-3499`'s analogous fee-swap test for `IntentGatewayV2` (which *does* assert a refund happens) [9](#0-8) .
2. `EvmHost.dispatch()` calls `IUniswapV2Router02.swapETHForExactTokens{value: 1 ether}(100e18, [WETH, feeToken], address(this), block.timestamp)` [1](#0-0) .
3. Suppose the swap only needs 0.3 ETH to buy 100 feeToken; UniswapV2Router02 refunds the remaining 0.7 ETH to its caller, `EvmHost`.
4. `EvmHost.dispatch()` never checks the returned `amounts` and never sends any ETH back to the user; the 0.7 ETH remains stuck in the Host contract's balance with no public function to reclaim it on the user's behalf.
5. Repeating for every native-funded `dispatch`/`fundRequest` call accumulates unrecovered ETH loss across all such users.

Note: I was unable to fully confirm within the available tool budget whether the Host contract exposes any privileged sweep/withdraw function for its native balance (which would determine whether the stranded ETH is merely inaccessible to the user or also drainable by governance/an admin) — the `receive()`/withdrawal grep returned matches in `EvmHost.sol` that I did not get to inspect in detail before running out of iterations. This does not change the core finding (loss of the *user's* funds through a public, unprivileged entrypoint), but it's a gap in the picture the user should be aware of.
