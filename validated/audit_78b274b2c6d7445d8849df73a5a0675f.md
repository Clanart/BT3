# Finding: Intent escrow ledger is amount-tracked, not balance-tracked — same invariant break as Axelar’s rebasing-token exploit

## Title
Intent escrow settlement trusts a fixed ledger amount instead of actual token balance, causing fund lock/loss for tokens whose balance changes outside of transfers - (File: evm/src/apps/intentsv2/IntentsBase.sol)

## Summary
`IntentGatewayV2`/`IntentsBase` correctly defends the *deposit* side against non-standard ERC20 behavior (fee-on-transfer) by measuring `balanceOf` before/after the pull, but the *release* side (`_withdraw`) still trusts the previously recorded escrow number and blindly calls `safeTransfer(beneficiary, amount)`. This is exactly the broken invariant from the Axelar report: a ledger balance (`_orders[commitment][token]`) that is assumed to always equal the real token balance, but for tokens whose balance changes outside of transfers (rebasing, deflationary-on-hold, etc.) it will not.

## Finding Description
On `placeOrder`, the contract is careful to measure actual received tokens rather than trust the caller-supplied amount, explicitly to handle fee-on-transfer tokens: [1](#0-0) 

and stores that measured amount as the escrow ledger: [2](#0-1) 

However, on release (`_withdraw`, used for fills, refunds, and cancellations), the contract does not re-measure the actual token balance held by the contract. It simply decrements the stored ledger value and transfers that fixed amount: [3](#0-2) 

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
...
IERC20(token).safeTransfer(beneficiary, amount);
```

The comment/tests in the repo (`FEE-ON-TRANSFER TOKEN TESTS`) show the team is fully aware ERC20s can behave non-standardly and deliberately built the *deposit*-side balance-diff guard for it: [4](#0-3) 

But no equivalent balance-diff (or "release everything the contract actually holds") logic exists for withdrawal. This is precisely the pattern the Axelar report attacked: `TOKEN_BALANCES` (`Tracked`) is decremented by a fixed `amount` via `checked_sub`, and if the real balance has drifted from the tracked ledger (rebase), the withdrawal either reverts (negative drift) or leaves unaccounted surplus stuck (positive drift).

## Impact Explanation
If any input token registered for an order rebases downward (or otherwise loses balance outside of transfers) between `placeOrder` escrow and the eventual `_withdraw` call (fill/refund/cancel), the escrow accounting (`_orders[commitment][token]`) still records the pre-rebase amount, but `IERC20(token).balanceOf(address(this))` is now lower. `safeTransfer(beneficiary, amount)` will revert once the requested `amount` exceeds the real balance — permanently locking the legitimate beneficiary's (solver's or refunding user's) funds for that commitment, since the escrow bookkeeping never adjusts and the order can never be finalized. Conversely, on a positive rebase the contract holds more tokens than the ledger tracks, and that surplus is unrecoverable by any legitimate party (no sweep path exists for `_orders[commitment][token]` beyond the stored `amount`). This falls squarely under the bounty's "stealing or loss of funds" / fund-lock category, since it affects live order escrow custody.

## Likelihood Explanation
Reachable through the fully permissionless, public `placeOrder` entrypoint — any user can select any ERC20 as `order.inputs[i].token`, including a rebasing token; no relayer, prover, or admin cooperation is required. The rebase itself is normal token behavior, not an attack requiring a malicious peer. The only requirement is that the order remain outstanding across a rebase event, which is a normal window for intent settlement (fill/refund/cancel are not instantaneous with placement).

## Recommendation
At withdrawal time, do not trust the static ledger value as the literal amount to transfer for tokens that can rebase. Either (a) explicitly disallow such tokens by requiring a token-type declaration analogous to `LOCK_UNLOCK_FEE`/`MINT_BURN` and reject "vanilla ERC20" custody for tokens with balance changes outside transfers, or (b) redesign `_withdraw` to cap the transferred amount to `min(escrowed, IERC20(token).balanceOf(address(this)))` per commitment/token and reconcile the ledger from the real balance, similar to the balance-diff pattern already used in `placeOrder`.

## Proof of Concept
1. User calls `placeOrder` with `order.inputs[0].token = REBASE_TOKEN`, `amount = 1000e18`. The contract measures actual received (`balBefore`/`balAfter`) and stores `_orders[commitment][REBASE_TOKEN] = 1000e18` (evm/src/apps/IntentGatewayV2.sol:282-298, 333-343).
2. Before the order is filled/refunded, `REBASE_TOKEN` undergoes a negative rebase (e.g., -5%), so the gateway's real balance of `REBASE_TOKEN` drops to `950e18`, while `_orders[commitment][REBASE_TOKEN]` still reads `1000e18`.
3. Solver fills the order or the deadline passes and a refund is triggered; `_withdraw` is invoked with `body.tokens[i].amount = 1000e18` (evm/src/apps/intentsv2/IntentsBase.sol:390-410).
4. `escrowed - amount` succeeds (ledger bookkeeping is self-consistent), but `IERC20(token).safeTransfer(beneficiary, 1000e18)` reverts because the contract only holds `950e18` — the entire withdrawal transaction reverts, and because the ledger only decrements on a successful call, the position is now permanently unwithdrawable (fund lock) for as long as the token's real balance stays below the ledger value.

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({

            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),

        assertEq(

            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
