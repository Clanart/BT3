### Title
Distribution rewards accrued under the pre-association direct-cast Sei address become permanently frozen when the EVM address is later associated to a different Sei address - ([File: utils/helpers/associate.go])

### Summary
Before an EVM address explicitly calls the `addr` precompile's `Associate`/`associatePublicKey` methods, Sei precompiles resolve an unassociated `caller`'s Sei identity to the *direct-cast* address (`sdk.AccAddress(evmAddr[:])`), the same pattern used throughout the codebase via `GetSeiAddressOrDefault`. A user can therefore delegate stake and accrue distribution rewards under this direct-cast identity through the distribution/staking precompiles. When the user later associates their EVM address with a *different*, "true" (pubkey-derived) Sei address, `AssociationHelper.AssociateAddresses`/`MigrateBalance` migrates only bank and wei balances from the direct-cast address to the new Sei address, then unconditionally deletes the direct-cast account if it has no locked (vesting) coins — without checking for, withdrawing, or migrating any outstanding staking delegations or distribution rewards. This is directly analogous to the ALCX report: an entity ("from" token / direct-cast address) is destroyed while its accrued, claimable rewards are left behind and become permanently unreachable.

### Finding Description
`AssociationHelper.MigrateBalance` moves spendable/wei balances from the direct-cast address (`castAddr := sdk.AccAddress(evmAddr[:])`) to the newly associated `seiAddr`, and then removes the `castAddr` account entirely as long as it has no `LockedCoins` (a vesting-only check, not a staking/rewards check): [1](#0-0) 

Bonded/staked tokens held via the staking module are not reflected in `LockedCoins`, so an account with active delegations and unclaimed distribution rewards will still pass this check and be removed via `accountKeeper.RemoveAccount`.

The `castAddr` identity is the default resolution used across precompiles for unassociated EVM callers (the same `GetSeiAddressOrDefault` pattern used elsewhere, e.g. in the solo precompile): [2](#0-1) [3](#0-2) 

The distribution precompile resolves the delegator for reward operations from the caller's address in the same way before invoking `withdraw`: [4](#0-3) 

Once a user delegates/stakes through the distribution or staking precompile while unassociated (delegator = direct-cast address), and later associates their EVM address to a distinct, real Sei address via the `addr` precompile: [5](#0-4) 

`AssociateAddresses` runs `MigrateBalance`, which deletes the direct-cast account without settling `DelegatorStartingInfo`/outstanding rewards owed to it. Because `GetEVMAddress`/`GetSeiAddress` are re-pointed to the new Sei address, all future precompile or native calls made by this EVM address (or its real Sei address) resolve to the new identity — the old direct-cast address can never again be reached to withdraw the stranded rewards, since no private key can natively sign transactions as that address (its bytes come from `keccak256`-based EVM derivation, not the ripemd160/sha256 derivation used for native secp256k1 signature verification).

This is architecturally the same root cause as the ALCX report: state (rewards) tied to an identity is left behind when that identity is destroyed/retired, with no code path forcing settlement first.

### Impact Explanation
This results in **permanent freezing of unclaimed staking rewards** (and, more severely, of the underlying delegated principal, since the delegation record itself is also orphaned under the deleted `castAddr`) for any user who interacts with staking/distribution precompiles before formally associating their EVM address with a distinct Sei address. Because association is common (any user with a custom bech32 Sei address linking it to a MetaMask-style EVM key will go through this flow), and staking-before-association is a directly reachable, unprivileged action, this can cause real, permanent loss of value to legitimate users — matching the "Permanent freezing of unclaimed yield" / "fails to deliver promised returns" impact class validated in the rules.

### Likelihood Explanation
Reachable by any ordinary user in three straightforward steps: (1) call the distribution or staking precompile from an EVM address before ever calling `Associate`, thereby delegating/staking under the direct-cast identity; (2) let rewards accrue; (3) call `Associate`/`associatePublicKey` to bind that EVM address to a separate, real Sei address. No special privileges, governance, or validator control are required — this is a normal onboarding pattern for users who use EVM tooling first and later want their assets under a native Sei bech32 identity.

### Recommendation
Before removing the direct-cast account in `AssociationHelper.MigrateBalance` (and more generally before any association re-points a `castAddr`'s identity), the protocol should:
- Check for and reject/settle any existing staking delegations (`stakingKeeper.GetDelegatorDelegations`) under `castAddr`, either by migrating them to the new `seiAddr` or by withdrawing rewards and returning the delegation to the caller before finalizing association.
- Explicitly withdraw any outstanding distribution rewards (`distrKeeper.WithdrawDelegationRewards`) for `castAddr` and forward them to `seiAddr` prior to `RemoveAccount`.
- Only call `RemoveAccount` once it is confirmed `castAddr` holds no unclaimed rewards, delegations, or other module-keyed state referencing it as an owner.

### Proof of Concept
Conceptual PoC (illustrating the reachable path; the actual precompile addresses/ABIs would need to be exercised via the EVM JSON-RPC or a Solidity test harness consistent with the repo's `integration_test/precompile_tests`):
1. From a fresh EVM address `E` (not yet associated), call the staking precompile's delegate function; internally this delegates using `sdk.AccAddress(E[:])` (the direct-cast address) as the delegator.
2. Wait for rewards to accrue and confirm via the distribution precompile's `rewards`/`delegationRewards` query that `sdk.AccAddress(E[:])` has non-zero pending rewards.
3. Call the `addr` precompile's `associatePublicKey`/`Associate` for `E` with a distinct target Sei address `S` (native, pubkey-derived, `S != sdk.AccAddress(E[:])`).
4. Observe: `sdk.AccAddress(E[:])`'s account is removed [6](#0-5) ; querying rewards/delegations for `sdk.AccAddress(E[:])` still show the stake/rewards existing in the staking/distribution stores, but no transaction can be signed as that address to withdraw them, and neither `E` nor `S` can reach that state through the precompiles anymore (their identity now points to `S`).

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
