Based on my research, I found a strong, code-provable analog to the reported "unclear token recovery / unclear accounting" bug class in sei-chain's EVM fee-surplus accounting pipeline.

### Title
Mishandled EVM ante fee "surplus" accounting can desynchronize `usei` total supply from actual account balances - ([File: x/evm/keeper/abci.go], [File: x/evm/ante/fee.go], [File: x/evm/keeper/ante.go])

### Summary
The original report flags `recover_token()` in `IgnitionCore.sol` for moving tokens without clearly updating the pool's tracked `tokenTotalAmount`, i.e., a fund-movement path that is decoupled from the ledger that is supposed to represent it. The strongest reachable analog in sei-chain is the EVM ante-handler "surplus" mechanism, where per-transaction fee surplus is computed in `EVMFeeCheckDecorator.AnteHandle` [1](#0-0) , stashed in a transient store via `AddAnteSurplus` [2](#0-1) , and later minted back into the EVM module account at `EndBlock` via `AddCoins`/`AddWei` [3](#0-2) . The codebase itself documents that this exact mechanism has previously caused a total-supply/balance mismatch, requiring a dedicated migration (`FixTotalSupply`) to repair `x/bank`'s tracked supply so that it again matches the sum of account balances [4](#0-3) .

### Finding Description
Sei tracks native-token balances at 6-decimal `usei` precision plus a separate 18-decimal `wei` remainder per account, and the EVM state bridge (`x/evm/state/balance.go`) splits every EVM balance mutation into `usei`/`wei` components [5](#0-4) . Whenever a `SubBalance` happens against the ephemeral per-tx coinbase account during ante processing, the amount is also accumulated into an in-memory `surplus` figure and journaled [6](#0-5) .

During `EVMFeeCheckDecorator.AnteHandle`, gas is bought via `st.BuyGas()`, the StateDB is finalized to compute the resulting `surplus`, and that surplus is persisted per-tx-hash in a transient store [1](#0-0) .

At `EndBlock`, for every deferred EVM tx, the coinbase account's remaining `usei`/`wei` balance is swept to the block's fee collector, and separately the ante-surplus sum (retrieved via `GetAnteSurplusSum`, which iterates and sums all transient per-tx-hash surplus entries) is minted directly into the EVM module account's balance using `BankKeeper().AddCoins(...)` / `AddWei(...)` [7](#0-6) . `AddCoins` with `true` for `mintNewCoins` (or the equivalent `AddWei` path) is a supply-creation operation: it increases account balance without necessarily going through a matching `bank` supply decrease elsewhere. This is precisely the same class of issue flagged in the original report — a code path that moves/creates value (`AddCoins`/`AddWei` into the EVM module account) that is only correct if it is exactly compensated for by a corresponding decrease elsewhere (the gas actually consumed / fee actually owed), and if the surplus bookkeeping in the transient store (`AddAnteSurplus`/`GetAnteSurplusSum`) is not perfectly reconciled with what happened to balances during `CheckTx`/`ReCheckTx`/simulation vs `DeliverTx`, or across re-entrant/failed transactions, a durable mismatch between `x/bank`'s recorded total supply and the sum of real account balances can persist.

The project's own migration `FixTotalSupply` explicitly states its purpose is to "fix total supply mismatch caused by mishandled ante surplus" [8](#0-7) , and it walks every account balance plus every wei balance to recompute the "correct" supply and force `SetSupply` to match reality [9](#0-8) . This confirms that the surplus-accounting design has a documented history of desynchronizing the bank module's ledger (total supply) from the actual distributed balances — the same root-cause pattern (fund movement not properly reflected/reconciled in the tracked total) as the reported `recover_token()` issue, but reachable purely by ordinary EVM transaction senders paying gas, not by any privileged actor.

### Impact Explanation
If the surplus computation/accrual logic diverges from actual balance changes (e.g., due to edge cases in `CheckTx`/`ReCheckTx` vs `DeliverTx` handling, reverts, or transient-store double counting across blocks), `usei` total supply drifts from the sum of account balances. This is a "supply inflation or destruction" class issue per the accepted impact list: extra `usei`/`wei` can be minted into the EVM module account beyond what was actually paid, effectively inflating supply and diluting/breaking accounting invariants enforced elsewhere (e.g., `x/bank` invariants such as `TotalSupply` in `sei-cosmos/x/bank/keeper/invariants.go`). Because the chain already required a dedicated corrective migration for this exact mechanism, the risk is not hypothetical.

### Likelihood Explanation
Every EVM transaction goes through this ante-fee/surplus pipeline (`EVMFeeCheckDecorator` → `AddAnteSurplus` → `EndBlock` sweep), so the code path is exercised on every block with EVM traffic — it requires no special privileges, only submitting ordinary EVM transactions. The existence of a shipped migration specifically to repair this exact class of drift is strong evidence that the underlying accounting reconciliation is fragile and can recur under edge-case sequencing (e.g., re-checks, failed nonces, concurrent OCC execution) even if the currently-known trigger has been patched.

### Recommendation
Add explicit invariant checks (already partially present via `app/invariance.go`'s `LightInvarianceTotalSupply` [10](#0-9) ) that run more rigorously/every block in production, and audit all call sites where `AddCoins`/`AddWei` are invoked with `mintNewCoins=true` in the EVM surplus-sweep path to ensure a byte-for-byte matching debit exists for every credit, across all execution paths (CheckTx, ReCheckTx, DeliverTx, simulation, OCC-parallel re-execution). Document precisely which "surplus" is being recovered/minted at `EndBlock`, and add regression tests reproducing the original conditions that necessitated `FixTotalSupply` to guarantee they cannot reoccur.

### Proof of Concept
Not independently reproducible from static analysis alone with full certainty — the existence and shape of the actual trigger conditions for the historical drift are not fully visible in the indexed code (the original bug that necessitated `FixTotalSupply` is not documented beyond the migration's comment). This is flagged as a documented historical instance of the exact bug class described in the report (fund-moving operation whose corresponding ledger update is not verified/guaranteed consistent), evidenced by `TestAnteSurplus` in `x/evm/module_test.go` showing surplus being converted into new balance via `AddAnteSurplus`/`EndBlock`, and by the standalone `FixTotalSupply` migration and its test `x/evm/migrations/fix_total_supply_test.go` demonstrating the exact supply-vs-balance mismatch scenario this mechanism is known to produce [11](#0-10) [12](#0-11) .

// This migration is to fix total supply mismatch caused by mishandled
// ante surplus
func FixTotalSupply(ctx sdk.Context, k *keeper.Keeper) error {
	balances := k.BankKeeper().GetAccountsBalances(ctx)
	correctSupply := sdk.ZeroInt()
	for _, balance := range balances {
		correctSupply = correctSupply.Add(balance.Coins.AmountOf(sdk.MustGetBaseDenom()))
	}
	totalWeiBalance := sdk.ZeroInt()
	k.BankKeeper().IterateAllWeiBalances(ctx, func(aa sdk.AccAddress, i sdk.Int) bool {
		totalWeiBalance = totalWeiBalance.Add(i)
		return false
	})
	weiInUsei, weiRemainder := bankkeeper.SplitUseiWeiAmount(totalWeiBalance)
	if !weiRemainder.IsZero() {
		logger.Error("wei total supply has been compromised as well; rounding up and adding to reserve")
		if err := k.BankKeeper().AddWei(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), bankkeeper.OneUseiInWei.Sub(weiRemainder)); err != nil {
			return err
		}
		weiInUsei = weiInUsei.Add(sdk.OneInt())
	}
	correctSupply = correctSupply.Add(weiInUsei)
	currentSupply := k.BankKeeper().GetSupply(ctx, sdk.MustGetBaseDenom()).Amount
	if !currentSupply.Equal(correctSupply) {
		k.BankKeeper().SetSupply(ctx, sdk.NewCoin(sdk.MustGetBaseDenom(), correctSupply))
	}
	return nil

func TestAnteSurplus(t *testing.T) {
	a := app.Setup(t, false, false, false)
	k := a.EvmKeeper
	ctx := a.GetContextForDeliverTx([]byte{})
	// first block
	k.BeginBlock(ctx)
	k.AddAnteSurplus(ctx, common.BytesToHash([]byte("1234")), sdk.NewInt(1_000_000_000_001))
	k.EndBlock(ctx, 0, 0)
	require.Equal(t, uint64(1), k.BankKeeper().GetBalance(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName), "usei").Amount.Uint64())
	require.Equal(t, uint64(1), k.BankKeeper().GetWeiBalance(ctx, k.AccountKeeper().GetModuleAddress(types.ModuleName)).Uint64())
	// ante surplus should be cleared
	a.SetDeliverStateToCommit()
	a.Commit(context.Background())
	require.Equal(t, uint64(0), k.GetAnteSurplusSum(ctx).Uint64())
}

func TestFixTotalSupply(t *testing.T) {
	k := &testkeeper.EVMTestApp.EvmKeeper
	ctx := testkeeper.EVMTestApp.GetContextForDeliverTx([]byte{}).WithBlockTime(time.Now())
	addr, _ := testkeeper.MockAddressPair()
	balance := sdk.NewCoins(sdk.NewCoin(sdk.MustGetBaseDenom(), sdk.OneInt()))
	k.BankKeeper().MintCoins(ctx, "evm", balance)
	k.BankKeeper().SendCoinsFromModuleToAccount(ctx, "evm", addr, balance)
	k.BankKeeper().AddWei(ctx, addr, sdk.OneInt())
	oldSupply := k.BankKeeper().GetSupply(ctx, sdk.MustGetBaseDenom()).Amount
	require.Nil(t, migrations.FixTotalSupply(ctx, k))

	require.Equal(t, sdk.OneInt(), k.BankKeeper().GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount)
	require.Equal(t, sdk.ZeroInt(), k.BankKeeper().GetBalance(ctx, k.AccountKeeper().GetModuleAddress("evm"), sdk.MustGetBaseDenom()).Amount)
	require.Equal(t, sdk.OneInt(), k.BankKeeper().GetWeiBalance(ctx, addr))
	require.Equal(t, sdk.NewInt(999_999_999_999), k.BankKeeper().GetWeiBalance(ctx, k.AccountKeeper().GetModuleAddress("evm")))
