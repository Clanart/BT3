## Title
`buildStatusMap()` silently drops staged-then-deleted entries from the working directory list, causing unstaged content to be silently reset before commit - (File: `app/src/lib/git/status.ts`)

## Summary
The external report's broken invariant is: a value feeding into a critical aggregate/commit computation silently omits a category of underlying state (`OmoAgent.getPositionValue()` ignoring deposited assets), causing the aggregate consumer (`totalAssets()`) to act on incomplete data. The closest verifiable Desktop analog is in `buildStatusMap()` in `app/src/lib/git/status.ts`, which unconditionally drops any index entry whose index status is `Added` and working-tree status is `Deleted` from the `workingDirectory.files` collection that later drives what Desktop stages and commits.

## Finding Description
`getStatus()` parses `git status --porcelain=2` output and folds every entry into a `Map<string, WorkingDirectoryFileChange>` via `buildStatusMap()`: [1](#0-0) 

When an entry is `Added` in the index but `Deleted` in the working tree, the function returns the map unchanged - the file is entirely omitted from `workingDirectory.files`, with only a one-line comment asserting "the file won't be part of the commit."

That omitted list (`status.workingDirectory.files`) is exactly the data structure the rest of the app treats as the full, authoritative "total assets" of pending changes:

- `createCommit()` always does `unstageAll(repository)` and then `stageFiles(repository, files)` using **only** the files present in `workingDirectory` [2](#0-1) 
- `_commitIncludedChanges()` derives the files to commit purely from `state.changesState.workingDirectory.files` [3](#0-2) 

Because `unstageAll` clears the *entire* index first, and only files enumerated by `getStatus()`/`buildStatusMap()` get re-staged, any index entry that was silently excluded by the `Added`+`Deleted` skip is never re-added to the index on the next commit. This means: if an attacker-controlled repository/checkout state (e.g., a crafted `.git` index left by a malicious clone script, a completed merge/rebase, or a build step run against a fetched repo) leaves the index holding an "Added" blob for a path that is not present on disk, Desktop's status/commit total silently treats that path as if it doesn't exist at all - the equivalent of `getPositionValue()` ignoring `depositAssets()`. The user is shown nothing in the Changes list for that path, "Select All" and commit totals do not account for it, and the very next commit action unstages it without ever telling the user.

There is an existing regression test that documents (and thus locks in) *part* of this behavior as intentional for the ordinary same-session case: [4](#0-3) 

but that test only exercises a benign, same-user scenario. It does not evaluate what happens when this exact index state is inherited from an untrusted source (a fetched/cloned repository, a completed operation from a remote/hook, or any process outside Desktop) - i.e., the state simply is presumed "safe to drop" without any diffing against what the index actually contains versus what will be committed on the next commit.

## Impact Explanation
This corrupts what the user believes they are about to commit or push: content staged in the Git index (which could include sensitive or unwanted blobs introduced by an untrusted repository/operation) is silently discarded from Desktop's UI/accounting layer, and the next legitimate commit action unstages it without any user-visible diff, warning, or accounting. This falls squarely under "silent corruption of what the user commits or pushes," listed as a valid Desktop impact class, because the working-directory/staging total (the Desktop analog of `totalAssets()`) is computed from an incomplete view of the index/working-tree state.

## Likelihood Explanation
Likelihood is Medium: the `Added`+`Deleted` index combination is a real, reachable git status state (it can arise from external `git rm`, third-party tools, hooks, or manipulated fixture/cloned repositories that ship an index with staged-but-missing blobs) without requiring any local/physical access beyond opening or interacting with such a repository/checkout in Desktop. It does not require elevated privileges, malware already resident, or leaked credentials — only an attacker-supplied repository state.

## Recommendation
Do not silently drop `Added`+`Deleted` entries from `workingDirectory.files`. Instead, surface them to the user (e.g., as a "staged file missing from disk" state) so `stageFiles`/`createCommit` cannot unstage index content without the user seeing and approving that change, and so the changed-files total accurately reflects everything present in the index/working tree before any commit action clears and rebuilds the index.

## Proof of Concept
1. Attacker or an external process leaves the git index for a checked-out repository in a state where `path/to/file` is staged as `Added` (`git add`) while the file itself has since been removed from the working tree (`rm path/to/file` without `git rm`), producing porcelain-2 status code `AD` for that path.
2. Open this repository in Desktop. `getStatus()` → `buildStatusMap()` parses the `AD` entry and, per [5](#0-4) , drops it entirely — it never appears in the Changes list, and the "files changed" total/badge does not count it.
3. The user makes an unrelated commit through Desktop's normal flow. `_commitIncludedChanges()` → `createCommit()` runs `unstageAll(repository)` then `stageFiles(repository, files)` with `files` limited to what was shown in the UI [2](#0-1) .
4. Result: the previously staged-but-missing `path/to/file` addition is unstaged and effectively discarded from the index without ever being shown to the user, silently altering the repository state relative to what the index actually held.
