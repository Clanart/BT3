### Title
Post-`await` re-read of `this.state.oauthState` in `resolveOAuthRequest` allows cross-wiring of concurrent OAuth flows - (File: `app/src/lib/stores/sign-in-store.ts`)

### Summary
The literal proof-of-concept in the question ("second deep link resolves the *first* promise") does not work exactly as described, because `resolveOAuthRequest` gates on `this.state.oauthState.state !== action.state` [1](#0-0)  before doing any work, so a deep link whose `state` doesn't match the *currently stored* `oauthState` is rejected outright. However, the same root cause the question identifies — `this.state`/`oauthState` being a single mutable field shared across concurrent in-flight `authenticateWithBrowser()` calls — does produce a real, symmetric bug: the function re-reads `this.state.oauthState.onAuthCompleted` **after** two `await`s, so if a second (or third) `authenticateWithBrowser()` invocation overwrites `this.state.oauthState` while the first request's token exchange is still in flight, the account fetched with the *first* request's `code`/`endpoint` ends up completing the *second* (currently active) request's promise instead.

### Finding Description
`resolveOAuthRequest` captures nothing about "which flow it belongs to" beyond a one-time comparison at the top of the function:

```ts
public async resolveOAuthRequest(action: IOAuthAction) {
  if (!this.state || this.state.kind !== SignInStep.Authentication) return
  if (!this.state.oauthState) return
  if (this.state.oauthState.state !== action.state) { ...; return }

  const { endpoint } = this.state
  const token = await requestOAuthToken(endpoint, action.code)   // <-- async gap #1

  if (token) {
    const account = await fetchUser(endpoint, token)             // <-- async gap #2
    this.state.oauthState.onAuthCompleted(account)                // <-- re-reads live this.state!
  } else {
    this.state.oauthState.onAuthError(new Error(...))
  }
}
``` [2](#0-1) 

The CSRF `state` check at line 341 is only performed once, before the two network `await`s. `this.state.oauthState` is dereferenced again at line 353 (and 355), *after* those awaits, instead of using a value captured before the async work started. Since `this.state` is a single shared field [3](#0-2) , any subsequent call to `authenticateWithBrowser()` that occurs while a `resolveOAuthRequest` call is awaiting the network overwrites `oauthState` (a new `csrfToken`, a new `onAuthCompleted`/`onAuthError` pair) via `setState` [4](#0-3) .

Concretely:
1. Flow A starts: `oauthState = { state: tokenA, onAuthCompleted: resolveA, ... }`.
2. A deep link with `state=tokenA` arrives; `resolveOAuthRequest` passes the check and begins `await requestOAuthToken(...)`/`await fetchUser(...)` for flow A.
3. Before that resolves, `authenticateWithBrowser()` is invoked again (e.g. user re-clicks "Sign in with your browser", or the UI re-triggers the flow), overwriting `this.state.oauthState` to flow B's `{ state: tokenB, onAuthCompleted: resolveB, ... }`.
4. Flow A's token exchange finishes; the code executes `this.state.oauthState.onAuthCompleted(accountA)` — but `this.state.oauthState` is now flow B's object, so `resolveB(accountA)` is invoked: flow B's promise resolves with an `Account` obtained from flow A's authorization `code`/`endpoint`.
5. In `authenticateWithBrowser().then(...)`, the success handler only checks `this.state.kind !== SignInStep.Authentication` [5](#0-4)  — unlike the `.catch` handler, which additionally checks `this.state.oauthState?.state === csrfToken` [6](#0-5) . This missing check means the success path cannot detect that the resolved account did not originate from "its own" CSRF token/flow, so it happily calls `emitAuthenticate(accountA)` and transitions to `Success` using whatever `resultCallback` is on `this.state` at that moment (flow B's), i.e. the wrong callback/UI receives the wrong account.

This is a genuine TOCTOU-style shared-mutable-state race, but it is the reverse pairing from the one the question hypothesized (an *earlier* request's result completing a *later* request's promise, not a later deep link stealing an earlier promise). Exploiting it requires the attacker to be able to fire two (or more) OAuth deep links whose `state` values are each valid for a genuinely active `oauthState` — the `state` is a `crypto.randomUUID()` [7](#0-6)  that is never exposed to a remote attacker in this code path (it only travels through the OS browser → GitHub → protocol-handler redirect for the current user's own device). Without access to the victim's browser/redirect (which is out of scope per the "local access" exclusion), an external attacker cannot supply a `state` value that would pass the check for either flow, so they cannot control which `code`/`endpoint` gets substituted.

### Impact Explanation
If triggerable, the impact would be legitimate but silent account/session cross-wiring — one OAuth flow's UI/result callback completing with an account fetched via a different flow's authorization code. This matches "unauthorized OAuth or account binding" in the valid-impact list. However, exploitability depends on the attacker being able to deliver two deep links with correct, unguessable per-session CSRF `state` values, which are never disclosed to a network/content attacker in this code path.

### Likelihood Explanation
Low, for an unprivileged remote/content attacker. The `state` value is a per-flow random UUID that only exists on the victim's machine as part of the browser round-trip; an attacker who does not already control the victim's browser/OS (local access, which is excluded) has no way to learn or predict it, so they cannot craft a matching deep link for either concurrent flow. The condition is more readily reproduced as a self-inflicted race (e.g., the user double-triggering "Sign in with browser") than as an externally-attacker-triggered exploit, and the question's specific proof idea (second, attacker-controlled deep link resolving the *first* promise) is not supported by the code as written, since the initial `state` equality check blocks any deep link that doesn't match the currently-active `oauthState`.

### Recommendation
Capture the specific `oauthState` object (or at minimum its `onAuthCompleted`/`onAuthError`/`endpoint` and the `csrfToken`) into a local variable at the top of `resolveOAuthRequest` before the `await`s, and use that captured reference (not a fresh `this.state` read) after the awaits. Add the same `this.state.oauthState?.state === csrfToken` guard to the success `.then` handler in `authenticateWithBrowser` that already exists in the `.catch` handler, so a stale/overwritten flow can never call `emitAuthenticate`/transition to `Success` on behalf of a different in-flight flow. Additionally, consider rejecting/cancelling any pre-existing `oauthState` (calling its `onAuthError`) when `authenticateWithBrowser` is invoked again while one is already pending, instead of silently overwriting it.

### Proof of Concept
Not independently reproducible against an external/unprivileged attacker as described in the question, because the CSRF `state` values are per-flow random UUIDs never exposed outside the victim's own browser round-trip. A unit-test-level reproduction (without any attacker involvement) would be:
1. Call `signInStore.authenticateWithBrowser()` (flow A), capture `tokenA` from the emitted `oauthState`.
2. Await/simulate `resolveOAuthRequest({name:'oauth', code:'codeA', state: tokenA})` but stall `requestOAuthToken`/`fetchUser` (e.g., mock with a delayed promise) before it resolves.
3. While still pending, call `signInStore.authenticateWithBrowser()` again (flow B) without calling `reset()`, capturing `tokenB`.
4. Let flow A's mocked network calls resolve with `accountA`.
5. Observe that `emitAuthenticate`/the `Success` transition fires with `resultCallback` belonging to flow B, using `accountA` (fetched via flow A's code), demonstrating the cross-wiring caused by re-reading `this.state.oauthState` after the `await`s in `resolveOAuthRequest`. [2](#0-1)

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
