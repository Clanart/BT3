### Title
Unsynchronized read/write race between `handle_finalized_payout`'s WOTS commit and `update_payout_txs_and_payer_operator_xonly_pk`'s row update can make an honest kickoff's committed `payout_tx_blockhash` diverge from the persisted DB value used later by `is_kickoff_malicious` - ([File: core/src/database/verifier.rs])

### Summary
`PayoutCheckerTask::run_once` reads `withdrawals.payout_tx_blockhash` once via `get_first_unhandled_payout_by_operator_xonly_pk` and burns it immutably into the kickoff transaction's Winternitz commitment through `handle_finalized_payout`, but the read is a plain `SELECT` with no row lock and the later `mark_payout_handled` call is keyed only by `citrea_idx`/`kickoff_txid`. If `update_payout_txs_and_payer_operator_xonly_pk` (invoked from `update_finalized_payouts` when the state-manager's block-fetcher observes a new/re-organized spend of the same withdrawal outpoint) rewrites `payout_tx_blockhash` for the same `idx` in that window, the value baked into the on-chain kickoff witness and the value the verifier later reads via `get_payout_info_from_move_txid`/`is_kickoff_malicious` can permanently diverge.

### Finding Description
The binding this code relies on is: `truncated(payout_tx_blockhash read at handle_finalized_payout time)` == `truncated(withdrawals.payout_tx_blockhash read later by is_kickoff_malicious)`.

- `get_first_unhandled_payout_by_operator_xonly_pk` (core/src/database/verifier.rs:282-313) does a bare `SELECT ... WHERE payout_txid IS NOT NULL AND is_payout_handled = FALSE AND payout_payer_operator_xonly_pk = $1` with no `FOR UPDATE`, so it takes no lock on the row.
- `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39-111) captures the returned `payout_tx_blockhash` (H1) at line 53 and passes it unchanged into `Operator::handle_finalized_payout` (core/src/operator.rs:839-915), which truncates it to 20 bytes and embeds it in the kickoff transaction's Winternitz commitment via `create_and_sign_txs` (operator.rs:893-915). Once this kickoff is broadcast, this commitment is immutable.
- Concurrently, `update_finalized_payouts` (core/src/verifier.rs:2283-2354), driven by the state-manager's block-fetcher for a newly processed block, calls `update_payout_txs_and_payer_operator_xonly_pk` (core/src/database/verifier.rs:199-251), which performs an unconditional `UPDATE withdrawals SET ... payout_tx_blockhash = c.payout_tx_blockhash ... WHERE w.idx = c.idx` — no `WHERE payout_tx_blockhash = <old value>` guard, no version/optimistic-lock check.
- `mark_payout_handled(dbtx, citrea_idx, kickoff_txid)` (called at payout_checker.rs:104-106) finalizes the row by `citrea_idx`/`kickoff_txid` only; it never re-verifies that `payout_tx_blockhash` is still H1.
- Later, `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1859-1915) re-derives the expected commitment by reading the **current** row via `get_payout_info_from_move_txid` (core/src/database/verifier.rs:253-280) and compares `payout_blockhash[12..]` against the bytes extracted from the kickoff witness. If the row was rewritten to H2 in the race window, `committed_blockhash != truncated_blockhash` and `is_kickoff_malicious` returns `true` even though the operator signed honestly with H1.

Existing guards do not close this gap: `SECP.verify_schnorr` only validates the user's payout signature, not the blockhash-commit consistency; `is_deposit_valid`/`SPV::verify`/`verify_storage_proofs` operate on unrelated data; there is no DB uniqueness constraint or trigger preventing `payout_tx_blockhash` from being overwritten for an `idx` that already has `is_payout_handled = FALSE` but a kickoff already broadcast in-flight.

### Impact Explanation
When the divergence occurs, an honest operator that correctly signed and broadcast its kickoff with H1 will later be flagged as malicious by `is_kickoff_malicious` because the persisted row now shows H2. This leads verifiers to challenge a legitimate kickoff, resulting in the honest operator's collateral being burned — matching the Critical category "an honest operator's collateral burned." The bug is repeatable for any deposit/operator pair where the payout UTXO's confirming transaction changes identity for the same `idx` between the read in `get_first_unhandled_payout_by_operator_xonly_pk` and the commit of `mark_payout_handled`.

### Likelihood Explanation
The DB-level race (missing row lock in the `SELECT`, missing optimistic-lock/version check in the `UPDATE`, and `mark_payout_handled` not re-checking the blockhash) is a structural defect independent of any external event, and is directly reproducible with two concurrent `dbtx`s as the question's proof idea describes — no live Citrea, no mainnet, and no actual Bitcoin reorg is required to demonstrate it. The real-world trigger described (RBF via reused `SINGLE|ANYONECANPAY` signature landing in a different, still-canonical block due to a shallow reorg) is a secondary avenue that would additionally require the block-fetcher to reprocess/rewrite `bitcoin_syncer_spent_utxos` for the same outpoint across the reorg boundary, which is plausible for a reorg-aware syncer but is not fully confirmed from the code inspected. The core race window itself, however, is confirmed directly from the cited SQL and call sites.

### Recommendation
Take a row-level lock (`SELECT ... FOR UPDATE`) in `get_first_unhandled_payout_by_operator_xonly_pk` for the row being processed, and make `mark_payout_handled` (and/or `update_payout_txs_and_payer_operator_xonly_pk`) conditional on `payout_tx_blockhash` still matching the value that was used to build the kickoff commitment (e.g., `WHERE idx = $1 AND payout_tx_blockhash = $2`), failing/retrying the `PayoutCheckerTask` iteration if the value changed underneath it. Alternatively, persist the exact blockhash actually committed to the kickoff witness in a separate immutable column and have `is_kickoff_malicious` compare against that column instead of the mutable `payout_tx_blockhash`.
