### Title
Publicly derivable internal output offsets let any sender force funds into protocol-internal classifications (Branch/Change/Forwarded) — ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
The bug class in CVE-2022-25336 is *exposure of a resource to the wrong sphere*: resources made reachable under names an unprivileged party can deduce or guess, with no access control distinguishing legitimate from attacker-initiated use. Serai's Bitcoin integration exhibits the same shape: the internal `Branch`, `Change`, and `Forwarded` output offsets are deterministic `hash_to_F` values under a fixed public domain separator, so anyone can compute the corresponding P2TR addresses and send a transaction that the processor will classify as an internal-protocol output rather than an external deposit.

### Finding Description
`scanner()` in `processor/src/networks/bitcoin.rs` registers three internal offsets derived via `Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")` where `KEY_DST = b"Serai Bitcoin Output Offset"` is a hardcoded public constant [1](#0-0) . The offset scalars are not secret: `hash_to_F` over public inputs plus the public group key `key` fully determines `key + G*offset`, and `p2tr_script_buf` converts that into a standard P2TR script [2](#0-1) . `Scanner::scan_transaction` then classifies any output whose `script_pubkey` matches a registered script — with no other check — by looking up only the script in `self.scripts` [3](#0-2) . In `get_outputs`, the matched offset is mapped back through `kinds[offset_repr_ref]` to `OutputType::{External, Branch, Change, Forwarded}`, and the deposit's attached `InInstruction` data (`extract_serai_data(tx)`) is only copied onto outputs classified `External` [4](#0-3) .

`register_offset` even documents that "arbitrary offsets may introduce a script path into the output," i.e. the scheme assumes offsets are securely generated — yet the protocol's own internal offsets are computed from a fixed public DST, so they are exactly reproducible by an outside party [5](#0-4) . There is no tag, proof, or on-chain marker distinguishing "output the protocol created" from "output an attacker created to an address the protocol happens to scan."

### Impact Explanation
An unprivileged Bitcoin user can send funds directly to the Branch, Change, or Forwarded P2TR addresses. The processor reports these as `OutputType::Branch`/`Change`/`Forwarded` outputs with `data` left empty and `presumed_origin` populated — indistinguishable from outputs the multisig itself created during internal operations. Depending on downstream handling in `processor/src/multisigs`, this can cause funds to be miscategorized as protocol-internal liquidity/change, deposits to lose their attached instruction data (silently non-crediting a deposit while appearing as a valid internal output), or an attacker deposit to be swept/handled as a forwarded output. This is an instance of the reported "resource accessible in the wrong sphere" — internal-purpose resources reachable by guessable public identifiers — with concrete impact: outputs are reported received under a classification they do not legitimately hold, which the validation criteria accept as "funds reported received that are not spendable" under the intended semantics.

### Likelihood Explanation
Reachable by any party who can broadcast a Bitcoin transaction — no validator status, no collusion, no leaked keys. Computing the target address requires only the public group key and the published constants `KEY_DST`, `b"branch"`, `b"change"`, `b"forward"`, all of which appear verbatim in the source. The cost is one ordinary P2TR payment. Exploitation does require the attacker to intentionally pay to the internal addresses (which costs them funds unless the miscategorization yields a benefit such as credit, forwarding, or griefing of accounting), which tempers severity to Medium, matching the reported advisory.

### Recommendation
Bind internal-purpose outputs to protocol intent rather than address shape alone. Options: (a) derive Branch/Change/Forwarded offsets with a per-multisig secret or key-dependent input so outsiders cannot compute them (while still allowing the documented "securely generated offsets" invariant), (b) require internal outputs to carry a verifiable marker — e.g., only treat a Change/Branch output as internal if it appears in a transaction the multisig itself signed/scheduled — and classify any unsolicited payment to those scripts as `External` or reject it, and (c) at minimum, attach `extract_serai_data` results to all output kinds so attacker deposits to internal addresses cannot silently lose their instruction payload.

// Always construct the full scanner in order to ensure there's no collisions
fn scanner(
  key: ProjectivePoint,
) -> (Scanner, HashMap<OutputType, Scalar>, HashMap<Vec<u8>, OutputType>) {
  let mut scanner = Scanner::new(key).unwrap();
  let mut offsets = HashMap::from([(OutputType::External, Scalar::ZERO)]);

  let zero = Scalar::ZERO.to_repr();
  let zero_ref: &[u8] = zero.as_ref();
  let mut kinds = HashMap::from([(zero_ref.to_vec(), OutputType::External)]);

  let mut register = |kind, offset| {
    let offset = scanner.register_offset(offset).expect("offset collision");
    offsets.insert(kind, offset);

    let offset = offset.to_repr();
    let offset_ref: &[u8] = offset.as_ref();
    kinds.insert(offset_ref.to_vec(), kind);
  };

  register(
    OutputType::Branch,
    *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")),
  );
  register(
    OutputType::Change,
    *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")),
  );
  register(
    OutputType::Forwarded,
    *FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")),
