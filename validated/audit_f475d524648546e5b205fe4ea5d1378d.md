### Title
Tron `IntentGatewayV2.withdraw()` treats a raw `.call` success as ERC-20 transfer success, ignoring the ABI-decoded return value - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary

### Finding Description
The main EVM implementation of the Intent Gateway (`evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`) uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the ERC-20 boolean return value (or lack thereof) and reverts on failure. [1](#0-0) 

The Tron variant of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`) instead performs a raw low-level `.call` with the `transfer` selector and only checks that the call itself did not revert (`success`), never decoding or checking the boolean return value that ERC-20's `transfer()` is supposed to return: [2](#0-1) 

This mirrors the exact broken invariant in the external report: a call's top-level completion (`success` / `txStatus`) is treated as proof of full logical success, while a secondary status field that actually reflects whether the intended effect occurred (ERC-20's returned `bool`, analogous to `receiverContractExecutionStatus`) is discarded. Any ERC-20-like token that returns `false` on failure instead of reverting (a well-known non-standard-but-common pattern, e.g. old USDT-style tokens or a token deliberately built to do this) will make `success == true` even though no tokens moved.

`withdraw()` is reached from two unauthenticated-by-the-caller-of-record paths:
- `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages arriving from a verified peer instance [3](#0-2) 
- `onGetResponse()` for cross-chain cancellation refunds [4](#0-3) 

In both cases, once `withdraw()` is invoked, it unconditionally: marks the order `_filled[commitment] = beneficiary`, decrements the escrow accounting (`_orders[commitment][token] -= amount`), and emits `EscrowReleased`/`EscrowRefunded` — regardless of whether the underlying token transfer actually delivered value: [5](#0-4) 

### Impact Explanation
Because the order/token whose type is chosen by the **user at order-placement time** (an unprivileged actor), a user can construct or select an escrow input token contract whose `transfer()` returns `false` instead of reverting on failure. When the settlement message eventually triggers `withdraw()` to pay the solver (or refund the user), `success` from the raw `.call` is `true` (the call executed without reverting), so the function proceeds to:
- mark the order as finalized/filled (blocking any legitimate retry or alternative recovery path), and
- decrement `_orders[commitment][token]` as if the tokens were paid out,

while the tokens never actually leave the contract's balance. This is a direct "loss/lock of funds" and "false success acceptance" outcome matching the bounty's accepted impact classes: the solver who delivered real output tokens is defrauded of the escrowed input, and/or the escrowed funds become permanently stuck in the gateway with no state left to trigger a legitimate re-delivery, since `_filled`/`_orders` have already been mutated to reflect a "completed" settlement that never happened.

### Likelihood Explanation
The path requires no relayer, prover, or admin compromise — only a user placing an order with an ERC-20-style token they control that returns `false` (rather than reverting) on `transfer()` failure, a widely known and easily reproducible token pattern. All the other steps (fill, settlement message dispatch, `onAccept`/`onGetResponse` delivery) are the normal, expected protocol flow. The existing guard (`if (!success) revert`) only catches a reverting call, not a call that returns `false` gracefully, so it does not stop this path.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw` (and the identical pattern in `onAccept`'s `SweepDust` handling) with OpenZeppelin's `SafeERC20.safeTransfer`, exactly as already done in the canonical EVM implementation (`IntentsBase.sol::_withdraw`). `SafeERC20` decodes the return data and reverts if it is present and `false`, or if the call reverts — closing the gap between "call succeeded" and "transfer actually succeeded," analogous to checking `receiverContractExecutionStatus`/`errorMessage` in addition to `txStatus`.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20-compatible token whose `transfer()` function performs no state change and simply `return false;` (never reverts).
2. Attacker calls `placeOrder()` on the Tron `IntentGatewayV2`, escrowing `EvilToken` as the input asset with a legitimate-looking output requirement (e.g., real USDC) to attract a solver.
3. A solver fills the order via `fillOrder()`, delivering real output tokens to the attacker's beneficiary address, and the cross-chain `RedeemEscrow` settlement message is dispatched back to the source chain.
4. When the settlement message is delivered via `onAccept()` → `withdraw()`, the contract calls `EvilToken.transfer(solver, amount)` via raw `.call`; the call returns normally with `success = true` and encoded `false` payload, which is never decoded/checked. [6](#0-5) 
5. `withdraw()` proceeds to mark `_filled[commitment] = solver`, decrement `_orders[commitment][EvilToken] -= amount`, and emit `EscrowReleased` — even though the solver's `EvilToken` balance never increased.
6. Net result: the solver paid out real output tokens and received nothing in return; the escrowed `EvilToken` amount is now unrecoverable (accounting says it was paid, but the funds/tokens are effectively lost/misaccounted), fully mirroring the external report's "silent false-success" failure mode.

```text
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
```
