### Title
Unspendable dust outputs reported as received funds via `Scanner::scan_transaction` - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The ERC-4626 "donation inflation" bug class maps onto Serai as an attacker donating dust-value outputs to a watched script. `Scanner` indexes only `script_pubkey → offset` and `scan_transaction` returns every matching output as a `ReceivedOutput` regardless of its value. There is no minimum-value check anywhere in the wallet layer, so outputs whose value is below the fee required to spend them are reported to consumers as received funds. These UTXOs are economically unspendable: including one as an input in `SignableTransaction::new` costs more in added fee weight (~57 vbytes per Taproot input) than the output contributes, and any attempt to spend it either burns value or is rejected by the scheduler's dust logic, permanently locking accounting.

### Finding Description
`Scanner::new`/`register_offset` build a `scripts: HashMap<ScriptBuf, Scalar>` map keyed solely on the P2TR script. `scan_transaction` pushes a `ReceivedOutput` for any output whose `script_pubkey` matches, with no value filter (networks/bitcoin/src/wallet/mod.rs:199-214). `ReceivedOutput` is then the sole unit consumed by `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256), which computes `needed_fee = fee_per_vbyte * vbytes` and checks only the aggregate `input_sat >= payment_sat + needed_fee`. An attacker who knows a registered script_pubkey (it is the public deposit address, or any offset-derived address announced via `register_offset`) can craft transactions paying dust (e.g. 330–1000 sat) to it. Each such output is returned by `scan_block`/`scan_transaction` as a confirmed received output, yet spending it adds ~57 vbytes of weight — at any non-trivial feerate its contribution is net-negative, and it can never be consolidated profitably.

The analogy to fxSAVE: the attacker's "10 wei mint + donation" becomes "dust donation to a watched script"; the victim's "deposit yielding 0 shares" becomes the treasury/scheduler crediting funds that can never be economically spent or that force fee-subsidized spends of the attacker's dust, and — since `register_offset` is surjective and keyed by script — repeated dust to the same script also permanently occupies that outpoint set with no cleanup path.

### Impact Explanation
Funds are reported received that are not economically spendable: the accounting layer sees a `ReceivedOutput` with positive value, but any transaction including it pays more in fees than the input contributes, so the value is stranded (or must be subsidized by other inputs, leaking treasury funds to miners). Repeated donations accumulate unspendable UTXOs. Impact is a bounded but griefing-permanent loss of reported funds per dust output, at a cost to the attacker of only the dust amount plus one transaction fee.

### Likelihood Explanation
Requires no privilege: anyone can send a Bitcoin transaction to a public P2TR script_pubkey. Cost per dust UTXO is a few hundred satoshis plus share of a transaction's fee. There is no rate limit — `scripts` grows with `register_offset` and every matching output is accepted. Constraints: the attacker cannot escalate to stealing existing funds (the offset keys are still required to sign), so this is value-stranding/griefing rather than theft, bounding severity to Medium/Low.

### Recommendation
Enforce a minimum relay-spendable value (the crate already defines `DUST = 10_000` in `networks/bitcoin` processor constants / `send.rs`) inside `Scanner::scan_transaction` or at `ReceivedOutput` construction, dropping sub-dust outputs before they reach consumers. Alternatively, have `SignableTransaction::new` reject or optionally skip inputs below the dust threshold so dust can be excluded rather than subsidized. This is the analog of "seed shares to a dead address": never let a zero-marginal-cost donation inflate the set of reported, unspendable holdings.

### Proof of Concept
1. Register a `Scanner` for group key `K` (or observe any announced offset-derived script from `register_offset`).
2. Attacker broadcasts a transaction with an output `{ value: 546 sat, script_pubkey: p2tr_script_buf(K) }`.
3. `scanner.scan_block(block)` returns `ReceivedOutput { offset: 0, output: 546 sat, outpoint }` — indistinguishable from a legitimate deposit.
4. Consumers cannot spend it: at `fee_per_vbyte = 5`, adding this input costs `5 * 57 = 285 sat` of fee while contributing `546` — before the existing `needed_fee`/`NotEnoughFunds` check passes only by draining other inputs; at `fee_per_vbyte ≥ 10` the input is strictly net-negative, and at any rate it sits below `DUST`, so it can never appear as change or be consolidated. The 546 sat is reported as received yet is permanently stranded — matching the report's "attacker locks user funds at a fraction of the cost" shape.
