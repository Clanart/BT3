### Title
Unverified PoP lets attacker elicit a blame proof that leaks an honest participant's ECDH key and secret share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns an `EncryptionKeyProof` (which reveals the ECDH shared key for a message) on the non-canonical-share error path **before** the batch-verified Schnorr proof-of-possession for that message has been checked. A malicious DKG participant can replay an honest sender's `EncryptedMessage` (publicly transmitted `key`, `pop`, `msg` fields) with mutated ciphertext bytes; the victim's node decrypts, produces a blame proof containing `proof.key = enc_key_victim * msg.key`, and returns it as `PedPoPError::InvalidShare { blame: Some(..) }`, which the processor serializes and broadcasts. Anyone can then decrypt the honest party's original secret-share ciphertext, recovering a valid Pedersen share — exactly the co-opted-key attack the per-message PoP was added to prevent.

### Finding Description
The bug class in the external report is "sensitive material exposed because access to it was not restricted to authorized parties." In PedPoP, the sensitive material is the per-message ECDH shared key, and the authorization check is the Schnorr PoP on `EncryptedMessage::pop` (see the explicit rationale in `encryption.rs` comments and `spec/cryptography/Distributed Key Generation.md`: without the PoP, an attacker reusing Alice's per-message key X causes Bob's blame proof `bX` to reveal Alice's message to Bob).

The enforcement fails because verification is deferred. `Encryption::decrypt` only *queues* the PoP into the `BatchVerifier` and immediately computes `key = ecdh(&self.enc_key, msg.key)` and returns `EncryptionKeyProof { key, dleq }` (encryption.rs:469-501). In `calculate_share`, the loop then does `C::F::from_repr(share_bytes.0)` and returns `Err(PedPoPError::InvalidShare { participant: l, blame: Some(blame) })` early (lib.rs:479-482) — the `batch.verify_with_vartime_blame()` call at lib.rs:493 is never reached, and the batch verifier (which would have flagged `BatchId::Decryption(l)` and produced `blame: None`) is dropped. The processor then emits `ProcessorMessage::InvalidShare { blame: Some(blame.serialize()) }` (processor/src/key_gen.rs:419-425), publishing the shared key. `Decryption::decrypt_with_proof`/`BlameMachine::blame` verify the DLEq against `enc_keys[decryptor]`, so the leaked `proof.key` is accepted network-wide as the correct decryption key for `msg.key` under the victim's encryption key.

### Impact Explanation
Unauthenticated/unprivileged secret exposure: a single malicious DKG participant (public inputs only — a mutated copy of a transmitted `EncryptedMessage`) causes an honest victim node to broadcast `EncryptionKeyProof.key`, the ECDH shared key between the victim's `enc_pub_key` and the *honest sender's* per-message key. Applying `cipher(context, key)` to the original honest ciphertext recovers the sender's secret share destined for the victim. Shares from a malicious sender combined with a leaked honest share reduce the work needed to reconstruct the group secret; at minimum it leaks an honest dealer's share to a party it was never addressed to, breaking the DKG confidentiality guarantee the encryption layer exists for. This is key-material (share) recovery reachable purely from public protocol messages.

### Likelihood Explanation
The trigger requires only that `C::F::from_repr` on the malleated plaintext fails — i.e., the decrypted 32 bytes are ≥ the field modulus, which occurs for ~50% of random 32-byte ciphertext mutations on 255-bit fields (ed25519/Ristretto, secp256k1), so the attacker retries mutations offline-bytes until the victim errors with `blame: Some`. No PoP valid for the mutated message is ever needed, since the early-return path skips `batch.verify_with_vartime_blame`. The attacker needs only a copy of any honest `EncryptedMessage` addressed to the victim (sent over the DKG broadcast/authenticated channel), making this reliably exploitable by any protocol participant or anyone who can feed messages to a victim's `calculate_share`.

### Recommendation
Verify the per-message PoP *before* producing or returning the `EncryptionKeyProof`, or withhold the blame proof until PoP validity is established. Concretely: in `KeyMachine::calculate_share`, do not attach `blame` on the `from_repr` early-return unless the PoP for that message has already been verified (e.g., verify `msg.pop` inline inside `Encryption::decrypt` prior to computing/returning the `EncryptionKeyProof`, or only release `blame` after `batch.verify_with_vartime_blame()` succeeds / maps the failure to `BatchId::Share`). Ensure no code path returns `blame: Some(..)` for a message whose `pop` was never checked.

### Proof of Concept
1. Honest Alice runs `generate_secret_shares`, producing `EncryptedMessage { key: X, pop, msg }` addressed to victim Bob (`to = enc_pub_key_bob`), sent to Bob.
2. Malicious Eve obtains that message (it transits the authenticated channel visible to participants) and sends Bob a copy with `from = Eve` and `msg.msg` bytes XOR-mutated so `C::F::from_repr` of the keystream-XORed plaintext fails.
3. Bob's `KeyMachine::calculate_share` calls `encryption.decrypt` (queues PoP under `BatchId::Decryption(Eve)` — never verified), computes `key = ecdh(bob_enc_key, X)`, builds `EncryptionKeyProof { key, dleq }`, then hits the `from_repr` error and returns `PedPoPError::InvalidShare { participant: Eve, blame: Some(proof) }` without running `batch.verify_with_vartime_blame`.
4. Processor serializes `blame` into `ProcessorMessage::InvalidShare` and broadcasts it.
5. Any observer runs `cipher(context, proof.key).apply_keystream` on Alice's *original* ciphertext and recovers Alice's secret share to Bob — a share Bob himself can validate via `share_verification_statements`. Confidentiality of an honest dealer's share is broken by a party who never possessed it.
