### Title
Deserialized `ThresholdKeys` with attacker-chosen `Constant` interpolation coefficients collapses the threshold to a single signer - (File: crypto/dkg/src/lib.rs)

### Summary
The Munchables exploiter's primitive was writing contract state to grant themselves a balance they never earned. The Serai analog lives in `ThresholdKeys::read`/`ThresholdKeys::new`: an attacker who supplies the serialized key material can choose `Interpolation::Constant(c)` with arbitrary coefficients, plus arbitrary `secret_share` and `verification_shares`, and thereby assign themselves unilateral signing power over the resulting "group key" — with zero validation that the coefficients encode a real threshold sharing.

### Finding Description
`ThresholdKeys::read` accepts untrusted bytes and reads, in order, `t`, `n`, `i`, an interpolation tag, `n` scalars for `Constant`, the `secret_share`, and `n` `verification_shares`, then calls `ThresholdKeys::new` [1](#0-0) . For `Interpolation::Constant`, `interpolation_factor` simply returns `c[i - 1]` with no constraint on the values [2](#0-1) . `ThresholdKeys::new` only enforces `t == n` for Constant interpolation and then computes `group_key = Σ verification_shares[i] * c[i-1]` over participants `1..=t` [3](#0-2) .

An attacker sets `c = [0, 0, ..., 1, ..., 0]` with the sole `1` at their own index, sets their `verification_shares[i] = G * x` and `secret_share = x` for a known `x`. The resulting `group_key` is exactly `G * x` — a key the attacker alone controls. During FROST signing, `ThresholdView::secret_share` multiplies each participant's share by its interpolation factor, so every other "signer's" contribution is multiplied by zero [4](#0-3) ; partial-share verification uses the attacker-supplied `verification_shares` from the same crafted view [5](#0-4) , so everything is internally consistent. This is the storage-slot manipulation mapped onto Serai: the attacker writes the coefficients (the "balance mapping") and the protocol dutifully credits them the entire key.

### Impact Explanation
What is presented as an `n`-of-`n` threshold key is in fact a 1-of-1 key fully known to the attacker. Any funds/operations authorized by signatures under the reported `group_key` can be signed unilaterally — the same end state as Munchables (one insider-controlled account draining a pool that appeared jointly controlled). `recover_key`'s consistency checks do not help because it operates on already-parsed `ThresholdKeys` [6](#0-5) .

### Likelihood Explanation
Requires an attacker to control the serialized `ThresholdKeys` bytes fed to `ThresholdKeys::read` (listed in-scope as untrusted input). Where serialized keys transit a coordinator, backup service, or recovery flow rather than being locally generated, this is reachable by an unprivileged party supplying bytes. The Constant-interpolation path exists precisely for hand-constructed sharings, so no exotic preconditions are needed.

### Recommendation
In `ThresholdKeys::new`, validate `Interpolation::Constant` beyond `t == n`: reject zero coefficients where a nonzero share is expected, and ideally verify the reconstruction (e.g., that `Σ c[i]·verification_shares[i]` equals a group key consistent with an independently committed value, or require Constant interpolations to be supplied via a fixed, non-deserializable construction). Alternatively, disallow `Constant` in `ThresholdKeys::read` for untrusted input, or authenticate serialized key material.

### Proof of Concept
1. Attacker picks scalar `x`, sets `n = t = 2`, own index `i = 1`.
2. Serializes a `ThresholdKeys` blob: interpolation tag `0`, coefficients `c = [1, 0]`, `secret_share = x`, `verification_shares = [G·x, G·y]` for arbitrary `y`.
3. `ThresholdKeys::read` succeeds; `group_key() == G·x` since participant 2's factor is `0` [7](#0-6) .
4. In `view([1,2])`, participant 2's secret share contribution is `0 · share`, and participant 2's interpolated verification share is `0 · V2` — verification accepts it [8](#0-7) .
5. Attacker alone produces valid FROST signatures under `group_key = G·x`, while the system reports a 2-of-2 multisig.

impl<F: Zeroize + PrimeField> Interpolation<F> {
  /// The interpolation factor for this participant, within this signing set.
  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
