### Title
Cached FROST preprocess seed is never deleted after use — an error-path retry reuses the same nonce seed, enabling secret share recovery — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The CVE describes an incorrect `free()` reached through incorrect error-handling code: a resource is released (or not released) on an error path such that later code operates on stale/freed state. The Serai analog is the inverse shape of the same class: `preprocess_internal` decrypts a cached FROST preprocess seed from the database but never deletes it, and `share_internal` reconstructs a fresh `AlgorithmSignMachine` from that same seed on every call. The FROST `SignMachine` contract explicitly requires the cached preprocess to be deleted after a single use — any reuse leaks the private key share. Because `share_internal` returns `Err(Participant)` on an attacker-controlled `read_preprocess` failure *before* `sign` consumes the machine, an unprivileged participant can force the honest node down an error path and induce a second `share_internal` execution under the same context, deterministically regenerating the identical nonces for a different signing set or message.

### Finding Description
`preprocess_internal` loads the seed via `CachedPreprocesses::get(self.txn, &self.context)` and decrypts it, but there is no corresponding `CachedPreprocesses` delete anywhere in the codebase — grep confirms only `get`/`set` usages. Each invocation therefore calls `AlgorithmSignMachine::from_cache` with the identical `CachedPreprocess(cached)` seed.

The FROST trait documents the hazard explicitly: "This cached preprocess MUST only be used once. Reuse of it enables recovery of your private key share" and "After this, the preprocess must be deleted so it's never reused" (`crypto/frost/src/sign.rs:209-224`).

`share_internal` then iterates the attacker-supplied `serialized_preprocesses` map and calls `machine.read_preprocess(...)` per participant, returning `.map_err(|_| participant)?` on failure (lines 161-168). At that point the machine is dropped without consuming the nonces — but critically, the *seed still lives in the DB*. A subsequent call to `share_internal` for the same `context` (e.g., a retry after blaming the faulty participant, a re-executed tributary transaction, or any re-run of the signing state machine) calls `preprocess_internal` again, `seeded_preprocess` derives the same `(d, e)` nonce pair from the same seed (`crypto/frost/src/nonce.rs:53-72`), and `sign` produces a second share `s' = d + rho'·e + lam·x` over different `rho'/lam'` values. Two shares under the same `(d, e)` with different binding factors and Lagrange coefficients yield a linear system that recovers the secret share `x`.

This mirrors the CVE's "incorrect free on an error path" class: the seed should be consumed/erased on first use, and the error-handling path (`read_preprocess` failing) leaves it alive for reuse.

### Impact Explanation
**High — key share recovery.** An unprivileged participant (any validator-set member submitting preprocess bytes) can send a malformed preprocess to force `read_preprocess` to error, then participate in a subsequent signing attempt under the same context. The honest node reuses its deterministic nonce pair; the two resulting `SignatureShare` values are public (broadcast per protocol), and solving the two equations reveals the victim's FROST secret share — equivalent to the private key compromise the `SignMachine::from_cache` docs warn about.

### Likelihood Explanation
Reachable with public inputs: the trigger is a malformed preprocess byte string fed to `read_preprocess` (explicitly in scope). Whether a second `share_internal` execution occurs depends on the calling code in `tributary/transaction.rs` re-executing after an `Err(Participant)` return (e.g., via re-execution after rebuild, which the file's own comments acknowledge is part of the design — "Instead of maintaining state in memory, a combination of the DB and re-execution are used"). The nonce-safety argument in the header comment relies on BFT ordering of messages and re-deciding nonces "upon any complete rebuild" — but the cached seed mechanism undermines that assumption for partial re-execution within the same context, since the same seed is read again rather than deleted. I could not fully trace every `share_internal` call site to confirm a second invocation with *distinct* messages occurs in practice; the finding assumes re-execution or retry under the same context is possible, which the design comments indicate is intended behavior.

### Recommendation
Delete the `CachedPreprocesses` entry atomically when it is read in `preprocess_internal` (read-and-clear), so any error path before or during `sign` permanently retires the seed. Alternatively, key the cache by a one-shot attempt identifier rather than `context` alone, and treat a missing entry after a failed sign as a hard failure rather than regenerating.

### Proof of Concept
1. Honest coordinator runs `share_internal(ctx, participants, map_A, msg)`; a malicious participant `p` supplies preprocess bytes that fail `Commitments::read` / `read_addendum`, causing `Err(p)` at `signing_protocol.rs:165-166`. The machine is dropped; the seed in `CachedPreprocesses[ctx]` is untouched.
2. The protocol retries (excluding `p` or with corrected bytes): `share_internal(ctx, participants', map_B, msg)` re-decrypts the same seed; `from_cache` → `seeded_preprocess` regenerates identical nonces `(d, e)`; `sign` emits share `s₂` with new binding factor `rho₂` and Lagrange `lam₂`.
3. From the two public shares `s₁ = d + rho₁·e + lam₁·x` and `s₂ = d + rho₂·e + lam₂·x`, subtract to eliminate `d`: `s₁ - s₂ = (rho₁ - rho₂)·e + (lam₁ - lam₂)·x`. Combined with the public nonce commitments `D = d·G`, `E = e·G` (which reveal the relation), or a third share, `x` is recovered — equivalently, standard FROST nonce-reuse algebra recovers `e` from the commitment-consistent equations and then `x` directly.
