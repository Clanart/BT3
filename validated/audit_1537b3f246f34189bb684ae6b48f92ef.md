Confirmed: `Kip71GasTarget` uses `noopFormatChecker`, meaning governance can set `GasTarget = 0` with no validation, unlike `Kip71BaseFeeDenominator` which explicitly rejects zero. [1](#0-0) 

### Title
Division by zero in `NextMagmaBlockBaseFee` via unvalidated `GasTarget` governance parameter causes node panic / consensus halt - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee`, the KIP-71/Magma base fee update function used every block, performs an unguarded division by `gasTarget` when the parent block's gas usage exceeds the target. The governance parameter that supplies `gasTarget` (`Kip71GasTarget`) is validated with a `noopFormatChecker`, allowing it to be set to `0` through the governance voting mechanism, which will cause a division-by-zero panic identical in nature to the reported ImageMagick CVE-2021-20241 (undefined division-by-zero behavior from unsanitized numeric input).

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee based on `parentGasUsed` vs `gasTarget`: [2](#0-1) 

When `parentGasUsed > gasTarget` (true for any nonzero gas usage if `gasTarget == 0`, since `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` and `upperGasLimit` is normally nonzero), the code executes:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget))   // gasTarget == 0 → panic
```
`big.Int.Div` panics on division by zero (`"division by zero"`), which is unrecovered here.

Unlike `BaseFeeDenominator`, which has an explicit zero-guard both in the format checker and defensively inside `NextMagmaBlockBaseFee` itself ("To avoid panic, set the fluctuation range small"), `GasTarget` has no such protection anywhere: [3](#0-2) [1](#0-0) 

The `Kip71GasTarget` parameter uses `FormatChecker: noopFormatChecker`, so the governance module accepts and applies `GasTarget = 0` without rejection.

This function is invoked in consensus-critical paths, e.g. header verification (`VerifyMagmaHeader`) and RPC fee estimation (`processBlock` in `node/cn/gasprice/feehistory.go`), meaning a zero `GasTarget` would crash header validation on every node processing a block after the parameter takes effect, not just a single RPC caller. [4](#0-3) [5](#0-4) 

### Impact Explanation
Setting `GasTarget = 0` via governance is analogous to the ImageMagick flaw — an attacker-influenced numeric parameter leads to an unguarded division by zero. In Kaia's case, since `NextMagmaBlockBaseFee` is called during block header verification and RPC gas-price/fee-history computation, a zero `GasTarget` would cause a runtime panic in every node validating a block, or in any public RPC node computing `eth_feeHistory`/gas suggestions once the malicious parameter is active — a chain-wide denial of service (availability impact), matching the CVSS vector `C:N/I:N/A:H` of the referenced CVE.

### Likelihood Explanation
This requires a governance parameter change to take effect (`Kip71GasTarget = 0`), which under most governance modes requires majority/single-governing-node authority rather than being reachable by an arbitrary unprivileged transaction sender. This significantly limits likelihood compared to a purely user-reachable bug, but the total absence of a format check (in contrast to the sibling `BaseFeeDenominator` parameter, which is explicitly protected) indicates an inconsistency/oversight in input validation that governance-instance operators, contract migrations, or governance parameter injection bugs could trigger unintentionally.

### Recommendation
Add a zero-check to the `Kip71GasTarget` `FormatChecker` in `kaiax/gov/param.go` (reject `v == 0`), and additionally add a defensive zero-guard inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` (mirroring the existing `BaseFeeDenominator` protection) so that a zero `gasTarget` cannot reach the `big.Int.Div` call under any circumstance.

### Proof of Concept
1. Through governance voting, set parameter `kip71.gastarget = 0` (accepted because `noopFormatChecker` performs no validation, per `kaiax/gov/param.go:324-334`).
2. Once the vote takes effect at the target block, any block with `GasUsed > 0` will trigger `NextMagmaBlockBaseFee` to compute `parentGasUsed > gasTarget` (since `gasTarget=0`), executing `x.Div(x, new(big.Int).SetUint64(0))`.
3. `big.Int.Div` panics with `"division by zero"`, crashing block processing (`VerifyMagmaHeader`) and any RPC calls that call `processBlock`/`NextMagmaBlockBaseFee` (e.g., `eth_feeHistory`), halting the affected node(s).

		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.

	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
