## Finding

The GitHub Desktop analog of this bug is in `app/src/lib/stores/app-store.ts`, in `repositoryWithRefreshedGitHubRepository()`, which explicitly documents that stale `GitHubRepository` associations (the local analog of the smart contract's `collectionIdToAllowList` mapping tied to an old contract address) are never invalidated when the underlying remote/"address" for a repository changes.

### Title
Stale `GitHubRepository` association (permissions & branch-protection cache) is never invalidated when a repository's remote changes - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`FantiumMinterV1` kept `collectionIdToAllowList` bound to collection IDs even after `fantiumNFTContractAddress` was migrated, so stale allow-list data leaked into the new contract context. Desktop has the same broken-invariant shape: a local `Repository`'s association with a `GitHubRepository` (owner/name/endpoint, permissions, branch-protection state) is cached and keyed independently of the actual git remote, and Desktop's own code acknowledges it is never cleared when that remote changes.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` re-resolves the `GitHubRepository` for a local `Repository` by calling `matchGitHubRepository()`, which inspects the current default remote URL [1](#0-0) . If the remote no longer matches any signed-in account's host (e.g. the remote was changed to point elsewhere), the function bails out and keeps the repository's old, now-incorrect `gitHubRepository` association, with the comment explicitly stating this is a known, unresolved gap: [2](#0-1) 

That stale `gitHubRepository` value drives:
- Write-permission checks via `hasWritePermission(gitHubRepo)` used to decide whether to even query branch protection [3](#0-2) .
- Branch protection / repo-rules fetches keyed by the stale `owner`/`name` [4](#0-3) .
- Per-`dbID` in-memory caches in `RepositoriesStore` (`branchProtectionSettingsFoundCache`, `protectionEnabledForBranchCache`) that persist across the lifetime of the app process [5](#0-4) .

Because the remote-to-account match in `matchGitHubRepository()` is purely a hostname comparison against `IRemote.url` read straight from the working copy's git config [6](#0-5) , anything that rewrites the remote URL on disk (a malicious `post-checkout`/`post-merge` hook shipped inside a cloned/fetched repository, or a compromised `.git/config`) can silently repoint `origin` without Desktop ever re-evaluating - or clearing - the previously cached GitHub identity, permissions, and protection state for that `Repository`.

### Impact Explanation
The corrupted value is the `Repository.gitHubRepository` association (owner/name/endpoint/permissions) together with the dependent `currentBranchProtected` / `currentRepoRulesInfo` state kept in `RepositoryStateCache` and `RepositoriesStore`'s per-`dbID` caches. When a repository's remote is changed underneath Desktop (attacker-controlled hook/config inside a cloned or fetched repo), the UI continues to reason about write access and branch protection using information for a repository that is no longer the one being pushed to/from. This can mislead the user's push/commit decisions (e.g. suppressing a "branch is protected" warning, or showing a write-access state) for what is now effectively a different, attacker-influenced remote - matching the report's core impact category of state that should have been invalidated on migration but wasn't.

### Likelihood Explanation
This requires an attacker-controlled cloned/fetched repository (e.g. a hostile git hook committed to the repo) that rewrites the remote URL - satisfying the "attacker controls a cloned/fetched repository" impact class. `matchGitHubRepository`/`repositoryWithRefreshedGitHubRepository` are only invoked opportunistically (after publish, after account change, after fork conversion, etc.), so the stale association can persist across many normal user actions in between, which is explicitly flagged as a known, un-remediated gap by the code's own TODO reference to desktop/desktop#1144.

### Recommendation
When the resolved remote no longer matches the cached `GitHubRepository` (or matches a different owner/name/endpoint), proactively clear or replace the association and its dependent caches (`branchProtectionSettingsFoundCache`, `protectionEnabledForBranchCache`, `currentBranchProtected`, `currentRepoRulesInfo`) rather than silently retaining the old data, closing the gap referenced by desktop/desktop#1144.

### Proof of Concept
1. Clone/open a legitimate GitHub repository `A` in Desktop; Desktop caches `gitHubRepository` (owner/name/permissions) and branch-protection state for `A`.
2. A malicious commit/hook inside the repository (e.g. `post-checkout`) runs `git remote set-url origin <non-github-or-different-repo-url>`.
3. Trigger any flow that calls `repositoryWithRefreshedGitHubRepository` (e.g. switching accounts). Since `matchGitHubRepository` fails to resolve an account for the new remote, the function bails out at the early-return path shown in `app-store.ts:4880-4885`, leaving `repository.gitHubRepository` and the branch-protection caches pointed at the original repository `A`.
4. The user continues to see permission/branch-protection status for `A` while actually committing/pushing against the rewritten remote.

  private async matchGitHubRepository(
    repository: Repository
  ): Promise<IMatchedGitHubRepository | null> {
    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)
      : null
  }

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
