### Title
Wallet coins remain locked after an offer's on-chain expiration because pending trades are never transitioned to `EXPIRED` - (File: `chia/wallet/trade_manager.py`)

### Summary
`TradeManager.get_locked_coins()` locks a maker's coins as long as the associated `TradeRecord` has status `PENDING_ACCEPT`, `PENDING_CONFIRM`, or `PENDING_CANCEL`. An offer created with a time-limited validity (`valid_times`/`expires_at`) becomes unenforceable on-chain once its expiration condition passes, but nothing in the wallet automatically transitions the trade's status to `EXPIRED` (or otherwise clears it) at that point. The coins therefore stay excluded from `get_spendable_coins_for_wallet` and remain locked indefinitely until the user manually cancels the offer, mirroring the reported bug class of stale "active" state that is not automatically cleared.

### Finding Description
`TradeManager.get_locked_coins()` collects coins of interest from every trade whose status is `PENDING_ACCEPT`, `PENDING_CONFIRM`, or `PENDING_CANCEL`: [1](#0-0) 

These locked coin IDs are then subtracted from a wallet's spendable coin set in `WalletStateManager.get_spendable_coins_for_wallet()`: [2](#0-1) 

`TradeRecord` supports an expiration via `valid_times`, populated from `parse_timelock_info(extra_conditions)` when the offer is created: [3](#0-2) 

`TradeStatus` defines an `EXPIRED` state: [4](#0-3) 

However, a repo-wide search shows `EXPIRED` is never assigned anywhere in the wallet code — there is no background task, `new_peak` hook, or periodic check in `TradeManager` that compares a `PENDING_ACCEPT` trade's `valid_times`/expiration to the current chain time/height and transitions it to `EXPIRED` (or otherwise removes it from consideration). The only transitions found are to `CANCELLED`/`PENDING_CANCEL` (via `cancel_pending_offers`) and `FAILED` (via `fail_pending_offer`, triggered only on transaction-send failure in `remove_from_queue`): [5](#0-4) 

Because no automated mechanism clears a trade once its `valid_times` expiration has passed, an offer that is expired on-chain (and thus can no longer be accepted/settled by a counterparty) still counts as `PENDING_ACCEPT` in `get_locked_coins()`. This is the same bug class as the report: a durability list ("active" trades) used to gate resource availability (coin spendability) is not automatically pruned when the underlying condition (offer validity) has lapsed, so the resource (the coin) stays locked longer than intended until a manual, user-initiated action (`cancel_pending_offers`) clears it.

### Impact Explanation
A wallet user who creates a time-limited offer (via `expires_at`/`valid_times`) has the coins offered rendered unspendable by their own wallet beyond the offer's actual expiration, even though the offer itself can no longer be accepted on-chain. The user must notice this and manually issue a cancellation transaction (paying a fee if `secure=True`) to regain access to their own funds. This is a medium-severity availability/usability issue affecting fund liquidity — not a direct loss of funds, but an unintended and unbounded locking of a user's own coins beyond their expectation, consistent with the "tokens locked slightly [or indefinitely] longer than expected" bug class.

### Likelihood Explanation
This is highly likely to be triggered whenever a maker creates an offer with `expires_at`/`valid_times` and the counterparty does not take the offer before expiration (a common real-world scenario for time-limited offers). No malicious actor is required — this is a standard wallet-user workflow gap.

### Recommendation
Add a mechanism in `TradeManager` (e.g., invoked from a `new_peak`/periodic wallet sync hook) that inspects `PENDING_ACCEPT` trades' `valid_times` against the current peak height/timestamp and transitions expired trades to `TradeStatus.EXPIRED`, excluding them from `get_locked_coins()`. Alternatively, have `get_locked_coins()` itself filter out trades whose `valid_times` expiration has already passed before including their coins in the locked set.

### Proof of Concept
1. Maker creates an offer with `expires_at` set to a near-future timestamp via `TradeManager.create_offer_for_ids` / `MakeOfferCMD`, e.g. `expires_at=<now+60s>` — this populates `TradeRecord.valid_times` and sets status `PENDING_ACCEPT`: [6](#0-5) 
2. Wait for the expiration time/height to pass without anyone taking the offer.
3. Call `get_spendable_coins_for_wallet` (or attempt to spend the offered coin via `send_transaction`) — the coin is still excluded because `get_locked_coins()` still returns it, since the trade status is still `PENDING_ACCEPT`: [1](#0-0) 
4. Confirm no wallet-internal process changes the trade status to `EXPIRED` — grep of the codebase shows `TradeStatus.EXPIRED` is defined but never set anywhere in `chia/wallet/`.
5. Manually cancel the offer via `cancel_pending_offers`, which is the only way to release the coin, confirming the coin was locked strictly longer than the offer's designed validity window.

    async def get_locked_coins(self) -> dict[bytes32, WalletCoinRecord]:
        """Returns a dictionary of confirmed coins that are locked by a trade."""
        all_pending = []
        pending_accept = await self.get_offers_with_status(TradeStatus.PENDING_ACCEPT)
        pending_confirm = await self.get_offers_with_status(TradeStatus.PENDING_CONFIRM)
        pending_cancel = await self.get_offers_with_status(TradeStatus.PENDING_CANCEL)
        all_pending.extend(pending_accept)
        all_pending.extend(pending_confirm)
        all_pending.extend(pending_cancel)

        coins_of_interest = []
        for trade_offer in all_pending:
            coins_of_interest.extend([c.name() for c in trade_offer.coins_of_interest])

        # TODO:
        #  - No need to get the coin records here, we are only interested in the coin_id on the call site.
        return (
            await self.wallet_state_manager.coin_store.get_coin_records(
                coin_id_filter=HashFilter.include(coins_of_interest)
            )
        ).coin_id_to_record
