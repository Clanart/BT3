### Title
`ReceivedOutput::read` deserializes an unvalidated scalar offset/output pair, letting untrusted bytes declare an output spendable under an offset that does not derive its `script_pubkey` - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The Gitea advisory (CVE-2020-28991) is an improper-input-validation flaw: `ParseRemoteAddr` accepted a host field containing a port and URL-encoded newlines, letting smuggled protocol content flow downstream. The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`, which reconstructs a "spendable output" object from untrusted bytes — a scalar `offset`, a `TxOut`, and an `OutPoint` — without validating that the claimed `offset` actually derives the output's `script_pubkey` from the scanner's group key. The structural invariant that makes a `ReceivedOutput` meaningful (`p2tr_script_buf(key + G*offset) == output.script_pubkey`) is enforced only at construction time inside `Scanner::scan_transaction`, never at deserialization.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` and only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` returns the registered offset, so a legitimately-produced `ReceivedOutput` is guaranteed spendable by the threshold key shifted by `offset` [1](#0-0) . However, `ReceivedOutput::read` performs only three independent field parses — `Secp256k1::read_F`, `TxOut::consensus_decode`, `OutPoint::consensus_decode` — and returns `Ok` unconditionally [2](#0-1) . There is no `key` field and no cross-field consistency check, so any caller that consumes deserialized `ReceivedOutput`s (rather than scanner-produced ones) trusts an attacker-asserted binding between `offset` and `output.script_pubkey`. Consumers then use `offset()` to re-key the spend (per-input commitment re-keying) and `output()`/`outpoint()` to build the transaction [3](#0-2) , meaning the mismatched pair propagates into signing just as the smuggled port/newline propagated into Gitea's git protocol stream.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` can craft a `ReceivedOutput` whose `output` pays to an arbitrary `script_pubkey` while `offset` is a scalar of their choosing. A downstream signer that applies `offset` to the threshold secret share and signs a spend of `outpoint` produces signatures that are invalid on-chain (the derived key does not match the output's key path), yielding outputs reported/treated as received and spendable that are not actually spendable, and causing the signing session to construct a transaction that cannot be confirmed. Depending on how the consumer aggregates inputs, a single forged entry can poison a batch spend of otherwise-valid outputs.

### Likelihood Explanation
Reachability is limited to contexts where `ReceivedOutput` values are deserialized from attacker-influenced storage or messages rather than produced directly by `Scanner::scan_transaction`/`scan_block`. Where outputs come straight from `scan_transaction`, the offset/script binding is guaranteed by the `scripts` map and the bug is unreachable. The finding therefore hinges on consumers trusting `read` output, and the impact is integrity/availability of spends rather than key disclosure, since an attacker cannot pick an offset for which they know the discrete log of `key + offset*G`.

### Recommendation
Bind the offset to the output at deserialization: either store/verify the scanner's group key in `ReceivedOutput` and assert `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)` in `read`, or make `read` private to the `Scanner`/`Wallet` context that owns `key` so the check can be performed. At minimum, re-validate every deserialized `ReceivedOutput` against the scanner's `scripts` map before scheduling it for signing.

### Proof of Concept
Conceptual: serialize a `ReceivedOutput` via `write` with `offset = Scalar::ONE` and `output = TxOut { script_pubkey: <attacker-controlled P2TR script>, .. }`, `outpoint` referencing any real UTXO. `ReceivedOutput::read` returns `Ok` [2](#0-1)  even though `p2tr_script_buf(group_key + G)` does not equal the supplied `script_pubkey`, so a consumer keying the spend by `offset()` signs under a key that cannot satisfy the output's script — a signed-but-invalid spend, mirroring the unvalidated field injection of the Gitea flaw.

Caveat: I was unable to trace the consumer(s) of `ReceivedOutput::read` within the in-scope files (usage appears to live in `processor/`, which is out of scope), so the exact reachable impact depends on how deserialized outputs are used downstream.

```rust
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
```

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
