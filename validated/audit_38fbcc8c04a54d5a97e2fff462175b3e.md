## Title
Stale line-level commit selections are silently reapplied to a freshly-fetched diff, allowing attacker-controlled remote content to corrupt what gets staged and committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
The reported `VAIVault` flaw is a stale-accounting bug: a value computed at one point in time (`xvsBalance`) is blindly overwritten/consumed at a later point without reconciling it against state changes that happened in between, letting an attacker exploit the timing gap. GitHub Desktop has the same class of bug in its partial-commit ("stage some lines of a file") pipeline: the bitmap of *which diff lines the user selected* is recorded against one diff snapshot, but is later blindly reapplied to a **different, freshly re-fetched diff** at staging time, without validating that the line positions still mean the same thing.

### Finding Description
When the working directory status is refreshed, `updateChangedFiles` merges the new file list with the previous state and carries the old selection object forward purely by file ID/path, with no comparison to the file's actual content or diff: [1](#0-0) 

The only place that attempts to reconcile a selection against a freshly-loaded diff, `updateChangesWorkingDirectoryDiff`, does so **only for the single file that is currently being viewed** in the Changes pane: [2](#0-1) [3](#0-2) 

Any other file that already has a `Partial` selection (line-index bitmap) sitting in `IChangesState.workingDirectory` is never revalidated against changes to its on-disk content.

At commit time, `stageFiles` routes partially-selected files through `applyPatchToIndex`, which fetches a **brand new diff from disk** (not the diff the selection was originally computed against): [4](#0-3) [5](#0-4) 

`formatPatch` then builds the patch by checking `file.selection.isSelected(absoluteIndex)` against that new diff's line positions, with no validation that the indices still correspond to the same logical content the user reviewed: [6](#0-5) 

The corrupted value is `WorkingDirectoryFileChange.selection` (the `DiffSelection` line-index bitmap): it is treated as durable "accounting" of user intent, but it is never invalidated or re-derived when the underlying diff it was computed against changes. `git pull` on the current branch (fully driven by an attacker-controlled remote) rewrites tracked file content on disk as an ordinary fast-forward/merge; this is exactly the kind of external event that can happen in the gap between a user selecting lines in file A and clicking "Commit," if the user has since switched their diff view to another file (so file A's selection is never re-validated per the bug above).

### Impact Explanation
This results in silent corruption of what the user commits and, subsequently, pushes: the staged patch generated by `formatPatch`/`applyPatchToIndex` no longer matches the content the user actually reviewed and approved by clicking specific lines in the diff viewer. Because the mismatch happens transparently inside the "Commit" action, the user has no visual indication that their approved selection is being applied to different underlying content — this can cause unintended lines (potentially attacker-influenced, since the divergent content originates from a pull against an attacker-controlled remote) to be committed and pushed, or intended changes to be silently dropped.

### Likelihood Explanation
This requires no local/admin access, no leaked credentials, and no unnatural user steps beyond normal Desktop usage: select partial lines in file A, switch the Changes view to another file (a completely ordinary action), pull from a remote that legitimately updates file A (fully attacker-controlled, e.g. a fork/PR branch or malicious/compromised remote), then commit. All of the guard logic that exists (`updateChangesWorkingDirectoryDiff`'s selectable-line pruning) explicitly only protects the single currently-displayed file, as the code comment itself acknowledges "the diff might have changed dramatically since last we loaded it" — but that comment's mitigation is scoped to the wrong set of files.

### Recommendation
Before staging a `Partial` file in `stageFiles`/`applyPatchToIndex`, or at minimum before `_commitIncludedChanges` proceeds, re-fetch the diff for every file with a `Partial` selection (not just the currently displayed one) and revalidate/rebuild the selection's selectable lines against it, clearing or renormalizing any selection whose backing diff has changed since it was captured — mirroring the report's recommendation to reconcile pending/external state *before* allowing the sensitive operation (`updatePendingRewards()` before `updateVault()`) rather than trusting a stale snapshot.

### Proof of Concept
1. In Desktop, open a repository tracking `origin/main`, modify `file.txt`, and in the Changes diff viewer select only some of the added/removed lines (creating a `Partial` `DiffSelection`) — do not commit yet.
2. Click another file in the Changes list so `file.txt` is no longer the actively-displayed diff (per `ChangesSelectionKind.WorkingDirectory`, only one file's diff is tracked/revalidated at a time).
3. Have the attacker-controlled `origin` push a new commit to `main` that also modifies `file.txt` (different lines/hunks); the user runs "Pull origin" in Desktop, which fast-forwards/merges `main` and rewrites `file.txt` on disk.
4. `_refreshRepository` → `_loadStatus` → `updateChangedFiles` reuses the pre-pull `Partial` selection bitmap verbatim for `file.txt` (`changes-state.ts:56`) since it's not the displayed file, so no selectable-line revalidation occurs.
5. User clicks "Commit" (`_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex`), which calls `getWorkingDirectoryDiff` again on `file.txt`, obtaining the **post-pull** diff, and `formatPatch` applies the stale line-index bitmap to it — staging different lines/content than what the user selected/reviewed prior to the pull.

    if (
      changesStateBeforeLoad.selection.kind !==
      ChangesSelectionKind.WorkingDirectory

      return
    }

    const selectionBeforeLoad = changesStateBeforeLoad.selection
    const selectedFileIDsBeforeLoad = selectionBeforeLoad.selectedFileIDs

    // We only render diffs when a single file is selected.

            diff: null,

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
