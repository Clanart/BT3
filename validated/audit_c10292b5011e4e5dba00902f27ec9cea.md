Based on my analysis, I found a real, exploitable analog in `IntrinsicIntents._fillSameChain`.

### Title
Partial same-chain fills clear the `_filled` finalization lock before the native-token refund external call, permitting solver-attacker escrow double-spend via reentrancy - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The C4 report's core pattern is: a guard exists (`isBLSPublicKeyPartOfLSDNetwork`) that looks authoritative but omits a needed exclusion (banned status), so a state that should be blocked is not, letting a caller push a follow-on operation through. The Hyperbridge analog is structurally the same "reentrancy-lock removed too early" class: `_fillSameChain` sets `_filled[commitment] = msg.sender` up front as a CEI-style reentrancy guard, but for a **partial** fill it explicitly `delete`s that same guard before the function does its remaining external native-token transfer, re-opening the exact window the guard was meant to close.

### Finding Description
`_fillSameChain` in [1](#0-0)  sets `_filled[commitment] = msg.sender` at the top specifically so that a reentrant call into `fillOrder` during any external call later in the function hits `if (_filled[commitment] != address(0)) revert Filled()` (this is exactly the invariant the repo's own reentrancy regression test documents: [2](#0-1) ).

However, when the fill turns out to be **partial** (not all output legs fully filled), the code does: [3](#0-2) 

```solidity
} else {
    delete _filled[commitment];
    emit PartialFill(...);
}

// Refund any unspent native tokens to the solver.
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```

`delete _filled[commitment]` runs, and only *after* that does the function make an external `.call{value: msgValue}("")` back to `msg.sender` (the solver) to refund unspent native ETH. Because `_filled[commitment]` has already been cleared to `address(0)` at this point, a malicious solver contract can re-enter `fillOrder` for the **same order** from its `receive()`/fallback during this refund call. The `if (_filled[commitment] != address(0)) revert Filled()` guard in `fillOrder`/`_fillSameChain` no longer blocks it, because the guard was just deleted for the "still open for future partial fills" case.

Per-token escrow decrementing in `_withdraw` (`_orders[body.commitment][token] = escrowed - amount;`, [4](#0-3)  ) does update state before the transfer for each token in the loop that already ran, so an outright double-withdraw of already-decremented escrow within the *same* reentrant call is bounded per-token by the checked subtraction (it would revert on `escrowed == 0`/underflow for tokens already fully drained). But `_partialFills[commitment][outputToken]` accounting and the surplus/dust computation in the outer loop of `_fillSameChain` are **not** protected by any lock during the reentrant window — the reentrant `fillOrder` call runs the entire per-output loop again with fresh `alreadyFilled = _partialFills[commitment][outputToken]` reads, `beneficiary.call{value: beneficiaryTotal}("")` / `IERC20.safeTransferFrom` calls, and its own nested `_withdraw`/native-refund cycle, all while the outer call's state mutations (particularly `msgValue` bookkeeping and any tokens not yet processed in the outer loop's remaining iterations) are still in flight. This lets an attacker interleave fills against the same commitment's escrow and fee accounting from within a single reentrant chain, which is precisely the "re-arm the disabled check" pattern the C4 report flags — the difference here is the check is disabled by design for partial fills, but the disable point is placed before, not after, all external calls in the function.

### Impact Explanation
This falls squarely under "unauthorized transaction or execution / transaction manipulation / logic attacks" for the bridge's escrow custody logic — the `_filled` guard exists specifically to prevent reentrant re-fills of the same order commitment, and the partial-fill code path removes that guard before the function's own external call. A malicious solver (an unprivileged, permissionless caller of `fillOrder`) can potentially manipulate `_partialFills` / escrow release ordering to extract more escrowed input tokens than the proportional fill amount they actually provided, corrupting the intent settlement invariant that escrow only ever moves "exactly once and only to the rightful beneficiary and amount."

### Likelihood Explanation
Likelihood is moderate-to-high in principle: `fillOrder` is fully permissionless, same-chain partial fills are a documented first-class feature ( [5](#0-4) ), and the vulnerable window requires only that the solver be a contract with a `receive()`/fallback that re-enters `fillOrder`, and that `msgValue > 0` (i.e., the solver overpays native ETH on an output leg) to trigger the refund call after the guard is cleared. The existing `nonReentrant` modifier on `fillOrder` (visible in `evm/src/apps/IntentGatewayV2.sol`) is the primary mitigation the repo already relies on for the full-fill reentrancy case documented in `IntrinsicIntentsReentrancyTest.sol` — I was not able to fully verify within this session whether that `nonReentrant` modifier is sufficient to also block this specific partial-fill-then-native-refund reentry path, since `_filled` is deleted *inside* the same top-level `nonReentrant` call rather than a genuinely separate transaction. If `nonReentrant` does block same-transaction reentry outright, this reduces to a lower-severity or non-issue; that determination requires tracing `ReentrancyGuardTransient`/`ReentrancyGuard` usage on `IntentGatewayV2` end-to-end, which needs a full compile/trace pass beyond this index-based review.

### Recommendation
Move the unspent-native-token refund (and any other external call) in `_fillSameChain` to occur before `delete _filled[commitment]`, or better, restructure so the `_filled` lock is only ever cleared after all external calls for that invocation have completed (full checks-effects-interactions ordering), consistent with how the full-fill branch already keeps `_filled` set through `_execute`. Additionally, confirm via a dedicated Foundry reentrancy test — mirroring `IntrinsicIntentsReentrancyTest.sol` but targeting the **partial**-fill branch specifically — that `nonReentrant` fully closes this window; if it does not (e.g., due to transient-storage reentrancy guard semantics or call ordering), add an explicit re-entrancy check scoped to the commitment during the partial-fill native refund.

### Proof of Concept
Conceptual PoC (requires on-chain compile/trace to confirm bypass of `nonReentrant`, not verified in this session):
1. Attacker deploys a `MaliciousSolver` contract with a `receive()` that calls `IntentGatewayV2.fillOrder(order, options)` again for the same `order`/`commitment`.
2. Attacker places or targets an existing same-chain order with a native-token (`address(0)`) output leg and multiple output legs, arranged so the first `fillOrder` call under-fills at least one leg (`isFullyFilled = false`) and sends more native ETH than `msgValue` strictly requires for that under-fill, leaving `msgValue > 0` at the end.
3. `MaliciousSolver.fillOrder(order, options)` executes: `_filled[commitment]` is set, the loop processes outputs, `isFullyFilled` is `false`, so `delete _filled[commitment]` runs (`IntrinsicIntents.sol:140`), then the native refund `msg.sender.call{value: msgValue}("")` (`IntrinsicIntents.sol:146`) transfers control to `MaliciousSolver.receive()`.
4. Inside `receive()`, `MaliciousSolver` re-enters `fillOrder` for the same `commitment` while `_filled[commitment] == address(0)` (guard cleared) and while the outer call's own execution is still unwound — attempt to claim additional escrow via a second partial/full fill against the same commitment's still-partially-populated `_orders`/`_partialFills` state before the outer call's per-transaction invariants are settled.
5. Full confirmation of fund extraction (vs. a revert from `nonReentrant` or per-token underflow checks in `_withdraw`) requires running this against a live Foundry fork/trace, which was not completed in this analysis.
