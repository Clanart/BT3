### Title
Shallow `Bid.Copy()` allows attacker-controlled `*big.Int` aliasing to corrupt bid-pool auction state - (File: kaiax/auction/bid.go)

### Summary
`Bid.Copy()` performs a struct-level copy of `BidData` but does not deep-copy the pointer fields it contains (`Bid *big.Int`, `MaxGasPrice *big.Int`, and the `Data`/`SearcherSig`/`AuctioneerSig` byte slices). This mirrors the reported `EscrowManager.sol` bug class: an intended "independent copy" of a struct is actually a shallow copy that shares mutable underlying state with the original.

### Finding Description
`Bid.Copy()` is defined as:
```go
func (b *Bid) Copy() *Bid {
	return &Bid{
		BidData: b.BidData,
	}
}
``` [1](#0-0) 

`BidData` embeds pointer and slice fields:
```go
type BidData struct {
	...
	Bid           *big.Int       `json:"bid"`
	MaxGasPrice   *big.Int       `json:"maxGasPrice,omitempty"`
	...
	Data          []byte         `json:"data"`
	SearcherSig   []byte         `json:"searcherSig"`
	AuctioneerSig []byte         `json:"auctioneerSig"`
}
``` [2](#0-1) 

Because `Bid` and `MaxGasPrice` are `*big.Int` and the byte slices reference the same backing arrays, assigning `BidData: b.BidData` copies the pointers/slice headers, not the underlying values. Any in-place mutation of `original.Bid` (e.g. via `.Add`, `.Sub`, `.SetUint64`) after `Copy()` is called will also change `copy.Bid`, and vice versa — the two `Bid` structs are not truly independent, exactly the aliasing pattern described in the external report about `VotingPowerPointCopy`.

`Copy()` is used directly in the bid-pool admission path to compare and store bids, e.g. in tests exercising `AddBid`:
```go
zeroBid := testBids[0].Copy()
zeroBid.Bid = big.NewInt(0)
...
higherBid := testBids[3].Copy()
``` [3](#0-2) 

showing that callers rely on `Copy()` returning an object that can be freely rewritten (`zeroBid.Bid = big.NewInt(0)`) without affecting the pooled original — which happens to work only because those call sites *replace* the pointer rather than mutate it in place. If any code path instead mutates `Bid`/`MaxGasPrice` in place (a common `*big.Int` idiom, e.g. `.Add(x, y)` writing into the receiver) on a copy obtained from `BidPool.bidMap`/`bidTargetMap`/`bidWinnerMap`, it would silently corrupt the pooled bid that other goroutines/paths read via `GetTargetTxMap` and winner-selection logic.

### Impact Explanation
The auction module's bid pool (`kaiax/auction/impl/bid_pool.go`) stores `*auction.Bid` values keyed by block number/target tx hash and by sender, and exposes them via getters such as `GetTargetTxMap` [4](#0-3) . If a shallow `Copy()` is used anywhere on a hot path that then in-place-mutates the numeric `Bid`/`MaxGasPrice` fields (e.g., fee/refund adjustment before re-comparing against the winning bid), the mutation propagates back into the stored winning bid, potentially causing the auction to settle with an incorrect/inflated bid amount or gas price relative to what the searcher actually signed — a state-divergence and settlement-integrity risk in the auction/MEV module reachable purely from submitted bids (an unprivileged auction bidder’s RPC call).

### Likelihood Explanation
Medium: the existing test call-sites happen to use pointer-replacement (`copy.Bid = big.NewInt(0)`) rather than in-place mutation, so the bug is currently latent rather than actively triggered by known code paths I could locate. However, `*big.Int` in-place mutation (`.Add`, `.Sub`, `.Mul` on the receiver) is an idiomatic and easy mistake in Go, and `Copy()` is exported/public API of the `auction.Bid` type intended to produce an "independent" bid object for exactly this kind of manipulation. Any future or existing helper that mutates a "copied" bid in place — reachable from bid submission (an auction bidder's transaction/bid) — would trigger real state corruption without additional privilege.

### Recommendation
Make `Bid.Copy()` a true deep copy of all mutable reference fields in `BidData`:
```go
func (b *Bid) Copy() *Bid {
	cp := b.BidData
	if b.Bid != nil {
		cp.Bid = new(big.Int).Set(b.Bid)
	}
	if b.MaxGasPrice != nil {
		cp.MaxGasPrice = new(big.Int).Set(b.MaxGasPrice)
	}
	cp.Data = append([]byte(nil), b.Data...)
	cp.SearcherSig = append([]byte(nil), b.SearcherSig...)
	cp.AuctioneerSig = append([]byte(nil), b.AuctioneerSig...)
	return &Bid{BidData: cp}
}
```
This ensures mutation of a copy (or the original) can never leak into the other, matching the "deep copy" recommendation from the analogous `VotingPowerPointCopy` bug.

### Proof of Concept
1. Submit a bid `B` with `B.Bid = 100` KAIA; it gets stored in `BidPool.bidWinnerMap`/`bidTargetMap` as the current winner.
2. Any code path (present or future) calls `winner := storedBid.Copy()` intending an independent working copy, then performs an in-place adjustment such as `winner.Bid.Sub(winner.Bid, penalty)` instead of reassigning the pointer.
3. Because `Copy()` only copied the `*big.Int` pointer, `storedBid.Bid` (still referenced by the pool) is mutated too — the pooled winning bid's amount silently changes to `100 - penalty` without going through bid-validation/signature-checking logic, since `SearcherSig`/`AuctioneerSig` were signed over the original `100` value. This lets the auction settle at a value the searcher never signed for, or causes divergent state between nodes that call `Copy()`-then-mutate at different times. [5](#0-4) [4](#0-3)

func (bp *BidPool) GetTargetTxMap(num uint64) map[common.Hash]*auction.Bid {
	bp.bidMu.RLock()
	defer bp.bidMu.RUnlock()

	maps.Copy(targetTxMap, bp.bidTargetMap[num])

}
