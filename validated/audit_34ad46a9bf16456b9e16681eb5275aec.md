### Title
Windows trailing-dot/ADS filename bypass of `isSafeFileExtension` allows disguised `.exe` execution via "Open with default program" - (File: `app/src/ui/lib/context-menu.ts`)

### Summary
`isSafeFileExtension` relies on Node's `path.extname()` producing an exact match against a hardcoded blocklist (`.cmd`, `.exe`, `.bat`, `.sh`). Node's `extname` does not perform Windows path normalization, so a repository-controlled filename such as `payload.exe.` (trailing dot) yields `extname === '.'` rather than `.exe`, and a filename such as `payload.exe:evil` yields `extname === '.exe:evil'`. Neither matches `.exe` exactly, so the file is classified as "safe" and the "Open with default program" context menu entry is offered without a warning/confirmation gate.

### Finding Description
`isSafeFileExtension` performs a naive `indexOf` string-equality check on the raw output of `Path.extname(file.path)` lowercased. [3](#0-2) 
It does not attempt to normalize the filename the way the Windows shell/filesystem does before extension comparison. Windows historically strips trailing dots and spaces from filenames in many Win32 APIs (`CreateFileW`, `ShellExecuteW`) for legacy FAT compatibility, but NTFS itself can store filenames containing trailing dots/spaces when written through APIs that bypass this normalization (e.g., extended-length `\\?\` paths, which Git for Windows' checkout path uses). This means a file physically named `payload.exe.` can be created on disk during `git clone`/`git checkout` of an attacker-controlled repository, while `Path.extname('payload.exe.')` returns `'.'` (not `.exe`), causing `isSafeFileExtension` to return `true`.

### Impact Explanation
If Desktop's UI (e.g. `app/src/ui/changes/filter-changes-list.tsx`, `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`) uses `isSafeFileExtension` to decide whether to show a warning or gate the "Open with default program" action, the mismatch means a user could be invited to open what appears to be a "safe" file, but the underlying file, once resolved by the Windows shell, launches as an executable — potentially achieving code execution from a maliciously crafted, attacker-controlled repository the victim cloned.

### Likelihood Explanation
Exploitation requires: (1) the attacker commits a file with a trailing-dot/space-suffixed `.exe` name to a repo the victim clones/fetches, (2) Git for Windows preserves that literal trailing dot on checkout (this depends on Git's own path-writing behavior on Windows, which needs empirical verification since some tooling also normalizes such names on write), and (3) the victim manually right-clicks and selects "Open with default program" in Desktop. This is a plausible but non-trivial chain: it depends on Git for Windows actually persisting a trailing-dot filename to NTFS (not guaranteed — Git may itself sanitize/reject such names on checkout), and requires a real user action, but no admin rights, local access, or pre-existing malware.

### Recommendation
Do not rely on raw string matching against `path.extname()` output. Normalize the filename first (strip trailing dots/spaces, resolve any embedded `:` as an NTFS ADS separator) before extracting/comparing the extension, or compare against the extension after passing the path through the same normalization the OS/shell performs, to ensure `isSafeFileExtension` cannot be bypassed by such suffixes.

### Proof of Concept
1. On a Windows machine, create a test repository containing a file physically named `payload.exe.` (with a trailing dot) or `payload.exe ` (trailing space) — verify persistence to disk via `git status`/`dir` after checkout with Git for Windows.
2. Clone/open this repository in GitHub Desktop.
3. Right-click the file in the Changes/History list and confirm the "Open with default program" option is presented without any restricted-extension warning, since `isSafeFileExtension(Path.extname('payload.exe.'))` evaluates `'.'` against the blocklist and returns `true`.
4. Select "Open with default program" and observe whether Windows shell execution (`shell.openPath`/`ShellExecuteW`) normalizes the trailing dot and launches the file as an executable.
