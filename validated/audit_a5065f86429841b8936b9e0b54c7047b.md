### Title
Silent origin remote URL rewrite from stale/attacker-influenced GitHub API data enables repo-jacking of pushes/pulls - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The bug-class seed is "an overwrite-style update function silently replaces authoritative state based on data that can be manipulated by an untrusted party, causing the victim to unknowingly act against attacker-controlled data." In Teller this was `updateCommitment` clobbering `maxPrincipal`. The Desktop analog is `updateRemoteUrl()` in `app/src/lib/stores/updates/update-remote-url.ts`, which silently rewrites the local Git `origin` remote URL to whatever `clone_url` the GitHub API currently reports for the repository the user is tracking — with no user confirmation and no verification that the repository identity (owner/name) presently returned by the API is still the same logical repository the user originally added.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` in `app-store.ts` matches the local repository to a GitHub API repository by hostname/owner/name via `matchGitHubRepository`, then calls `api.fetchRepository(owner, name)` and passes the response into `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

`updateRemoteUrl` then compares the API's `clone_url` against the current remote and, if the protocol matches and the remote hadn't been manually changed from the previously cached `cloneURL`, silently rewrites the `origin` remote with `gitStore.setRemoteURL`: [2](#0-1) 

The check only verifies hostname/owner/name string equality via `urlMatchesRemote`/`urlsMatch` in `repository-matching.ts` — it does not verify that the GitHub repository ID (`dbID`) or any immutable identifier is unchanged: [3](#0-2) 

This is the same broken invariant as the Teller bug: an "update" operation that unconditionally overwrites a security-relevant field (here, the trusted push/pull destination) using freshly fetched data, without confirming that the underlying identity backing that data hasn't changed out from under the user. On GitHub, `owner/name` is not a stable identity — a user can rename or delete their account/repo, freeing up the `owner/name` slug for another party to claim (a well-known "repo/account-jacking" pattern). If that happens between refreshes, the next call to `_refreshRepository`/`repositoryWithRefreshedGitHubRepository` (which runs routinely, e.g. after fetch: see `performFetch` calling `_refreshRepository`) fetches a *different* repository that now occupies the same `owner/name`, and Desktop silently repoints the user's local `origin` remote to the new (attacker-controlled) `clone_url`.

### Impact Explanation
Once `origin` is silently rewritten, all subsequent user-initiated pushes/pulls/fetches transparently target the attacker's repository instead of the one the user intended, even though the UI still shows the same repository name/path. Because there is no confirmation dialog, the user's next `git push` can leak private commits/branches (potentially containing secrets) to the attacker's remote, and the next `git pull`/fetch can silently merge attacker-supplied history/content into the user's working repository. This maps directly to the listed valid-impact category "silent corruption of what the user commits or pushes," since the destination of a push is corrupted without any signal to the user, and the attacker fully controls that destination by reclaiming a vacated `owner/name`.

### Likelihood Explanation
This requires no local access, no credential leakage, and no unnatural user action — it is triggered by GitHub Desktop's own routine background behavior (`repositoryWithRefreshedGitHubRepository` runs as part of normal repository refresh/fetch flows). The precondition is that the original repository's `owner/name` becomes reclaimable (e.g., original owner renames their account/repo, or repo is deleted) and an attacker claims it before the victim's next refresh — a scenario documented broadly as "repojacking" in the wider ecosystem. Existing guards (`protocolsMatch`, `remoteUrlUnchanged`) only prevent overwriting a manually customized remote; they do nothing to verify that the *matched* GitHub repository is still the same logical entity, so they do not stop this path.

### Recommendation
Do not silently rewrite `origin`'s URL from freshly fetched API data. At minimum:
1. Verify the immutable GitHub repository ID (`apiRepo.id`) matches the previously cached `gitHubRepository.dbID`/API id before considering the fetched repository "the same" one, rather than relying solely on owner/name string matching.
2. If the ID differs (indicating the owner/name slug has been reclaimed), do not auto-update the remote — instead surface a prompt so the user can confirm/reject before `setRemoteURL` is invoked.
3. Never silently retarget `origin` as part of a background/automatic refresh; require explicit user consent for any remote URL change tied to repository identity changes.

### Proof of Concept
1. Victim clones and tracks `https://github.com/alice/project` in GitHub Desktop; `gitHubRepository.cloneURL` is cached.
2. Alice renames her GitHub account (or deletes/transfers `project`), freeing the `alice/project` slug.
3. Attacker immediately registers the `alice` username (or creates a repo at the same slug) and creates a repository named `project` with a malicious `clone_url`.
4. Victim performs a routine fetch; `performFetch` → `_refreshRepository` (indirectly via account/selection refresh paths) triggers `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository('alice', 'project')` and now receives the attacker's repository data: [1](#0-0) 
5. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (since the local origin still matches the old cached `cloneURL`), and `urlsMatch === false` (new clone_url differs), so it calls `gitStore.setRemoteURL('origin', <attacker clone_url>)` without any prompt: [4](#0-3) 
6. The victim's next `git push`/`git pull` in Desktop silently targets the attacker-controlled repository.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
