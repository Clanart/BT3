### Title
Unauthenticated OP_RETURN operator attribution in `payout_tx` allows a mismatched/impersonated operator identity to be bound into `deposit_constant` and auto-claimed for reimbursement - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`deposit_constant`/`host_deposit_constant` derive `operator_xonlypk` solely from the first OP_RETURN push of `payout_spv.transaction`, a field that is never signed by, or otherwise cryptographically tied to, the operator it names. Downstream automation (`PayoutCheckerTask`) and the malicious-kickoff check (`is_kickoff_malicious`) both trust this same unauthenticated field, so anyone who can broadcast a valid spend of the withdrawal-input UTXO (i.e. the party who actually authorizes/funds the payout) can attribute the payout to an arbitrary real operator's `xonly_pk` instead of their own, causing that other operator's automation to claim reimbursement for a front it never performed.

### Finding Description
The claimed binding is: `operator_xonlypk` (used inside `deposit_constant`) == `xonly_pk` of the operator whose BTC actually funded `payout_tx.input[payout_input_index]`.

In `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:206-229`) and the host-side equivalent `host_deposit_constant` (`bridge-circuit-host/src/structs.rs:482-516`), `operator_xonlypk` is extracted purely from `get_first_op_return_output`/`parse_op_return_data` on the payout transaction: [1](#0-0) [2](#0-1) 

`create_payout_txhandler` shows the payout tx's only signature (`user_sig`, key-spend) authenticates the *withdrawer's* spend of the input UTXO; the OP_RETURN push of `operator_xonly_pk` is populated as plain data with no signature binding it to that operator's identity: [3](#0-2) 

On the verifier side, `update_finalized_payouts` re-extracts this same unauthenticated OP_RETURN value from the on-chain payout tx and stores it as `payout_payer_operator_xonly_pk`: [4](#0-3) 

`is_kickoff_malicious` only cross-checks that the operator who sent a kickoff matches this same DB-stored (attacker-controllable) value — it never checks it against the actual signer/funder of the withdrawal input: [5](#0-4) 

Crucially, an operator's own automation (`PayoutCheckerTask::run_once`) decides to start a kickoff/reimbursement flow purely by querying "unhandled payouts" keyed by this OP_RETURN-derived `operator_xonly_pk`, with no verification that the operator itself broadcast/funded that specific payout: [6](#0-5) 

Exploit flow: An attacker who is an ordinary bridge user (owns the private key of the withdrawal-input UTXO, since that UTXO's taproot key is `user_xonly_pk` checked against the withdrawer's own signature) constructs and directly broadcasts the `payout_tx` on Bitcoin themselves (bypassing any operator's gRPC entirely), correctly satisfying the required withdrawal output/amount, but pushing a *real, different* operator's (`operator B`) `xonly_pk` into the OP_RETURN instead of their own. Because nothing checks that operator B actually authored/funded this transaction, operator B's `PayoutCheckerTask` (matching by `operator_xonly_pk` alone) will pick it up as an "unhandled payout attributed to me" and automatically initiate `handle_finalized_payout` → kickoff. The subsequent `bridge_circuit`/`host_deposit_constant` computation binds `operator_xonlypk = operator B` together with operator B's own `round_txid`/`kickoff_round_vout` (since operator B's own kickoff tx is used), producing a valid proof and `journal_hash` that `is_kickoff_malicious` will not flag (the DB value and `kickoff_data.operator_xonly_pk` match, because both are derived from/equal to operator B).

### Impact Explanation
Operator B is reimbursed (bridge value released from the vault via the round/kickoff/reimburse transaction graph) for a payout it never actually fronted — the attacker (the withdrawer) is the one who authorized/broadcast the spend of the withdrawal UTXO. This is a direct instance of the Critical category "an operator reimbursed for a payout it never funded," and by extension can also manifest as BTC leaving the bridge without a genuine corresponding front by the credited operator. The attack is repeatable per withdrawal and can target any operator whose `xonly_pk` is public (all operators' pubkeys are public protocol parameters), so the blast radius spans every operator and every withdrawal processed by an automated `PayoutCheckerTask`.

### Likelihood Explanation
Preconditions: automation feature enabled for the target operator's `PayoutCheckerTask` (default deployment configuration for operators per the repo's automation feature). The attacker only needs to be a legitimate withdrawer of their own funds (own key on the withdrawal-input UTXO) and the ability to broadcast a raw Bitcoin transaction with a custom OP_RETURN, both of which are within the unprivileged attacker's granted capabilities. No signature, key compromise, or operator/verifier cooperation is required. Cost is limited to normal Bitcoin transaction fees.

### Recommendation
Do not treat the OP_RETURN operator pubkey as authoritative attribution. Require operators to persist/sign their own record of payout txs they actually broadcast (e.g., via a presigned commitment or a signature covering the OP_RETURN payload) before `PayoutCheckerTask` acts on it, and have `is_kickoff_malicious` (and `deposit_constant`'s consumers) verify that attribution against that operator-authenticated record rather than solely against the unauthenticated on-chain OP_RETURN bytes.

fn host_deposit_constant(
    input: &BridgeCircuitInput,
) -> Result<DepositConstant, BridgeCircuitHostParamsError> {
    let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&input.sp.storage_proof_deposit_txid).map_err(|e| {
            BridgeCircuitHostParamsError::StorageProofDeserializationError(e.to_string())
        })?;

    let round_txid = input.kickoff_tx.input[0]
        .previous_output
        .txid
        .to_byte_array();

    let kickoff_round_vout = input.kickoff_tx.input[0].previous_output.vout;

    let operator_xonlypk: [u8; 32] = parse_op_return_data(&first_op_return_output.script_pubkey)
        .ok_or(BridgeCircuitHostParamsError::InvalidOperatorPubkey)?
        .try_into()
        .map_err(|_| BridgeCircuitHostParamsError::InvalidOperatorPubkey)?;

    let deposit_value_bytes: [u8; 32] = deposit_storage_proof.value.to_be_bytes::<32>();

    Ok(deposit_constant(
        operator_xonlypk,
        input.watchtower_challenge_connector_start_idx,
        &input.all_tweaked_watchtower_pubkeys,
        deposit_value_bytes,
        round_txid,
        kickoff_round_vout,
        input.hcp.genesis_state_hash,
    ))
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }
