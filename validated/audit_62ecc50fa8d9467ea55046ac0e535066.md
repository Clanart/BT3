### Title
`depositFor` hardcodes `_minimumLiquidity = 0`, enabling sandwich/MEV theft from victims relying on relay deposits - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor()` forwards `0` as `_minimumLiquidity` to `_deposit`, unlike `deposit()` which lets the caller specify slippage protection. Any depositor (or relay) that uses `depositFor` on behalf of a beneficiary (`_for`) removes the beneficiary's ability to protect against unfavorable Wombat coverage-ratio pricing, letting an attacker sandwich the transaction with flash-loan-driven pool skewing to extract value from the victim's deposit.

### Finding Description
`deposit()` passes through the caller-supplied slippage parameter: [1](#0-0) 

`depositFor()` instead hardcodes zero slippage protection regardless of amount or market conditions, while still routing the deposit through the same underlying pool call: [2](#0-1) 

Both are funneled into `_deposit`, which calls `IWombatStaking(wombatStaking).deposit(lpToken, _amount, _minimumLiquidity, _for, _from)` — the LP-mint amount returned by Wombat's underlying pool is governed by the pool's coverage-ratio-dependent slippage/haircut formula, so a `_minimumLiquidity` of `0` means the call will succeed no matter how unfavorable the exchange rate is at execution time: [3](#0-2) 

Because `depositFor` is a public, unauthenticated entry point (anyone can call it for any `_for` address, e.g., a relay/bot batching deposits for users who approved it), an attacker who observes a pending `depositFor` transaction in the mempool can:
1. Flash-loan-skew the underlying Wombat pool's coverage ratio to make new deposits mint fewer LP shares than fair value.
2. Let/force the victim's `depositFor` transaction execute at the skewed price (no revert possible since `_minimumLiquidity = 0`).
3. Restore the pool ratio and capture the value differential (e.g., via arbitrage/swap or `SmartWomConvert`).

No modifier, `nonReentrant` guard, or accounting check in `WombatPoolHelperV2` or `_deposit` prevents this, since the vulnerability is purely a missing slippage check, not a reentrancy or authorization bug.

### Impact Explanation
The victim (`_for`) receives fewer receipt/LP tokens than the fair-value backing of their deposited stablecoins, a direct and quantifiable loss of principal for that user — matching the Immunefi "theft of user funds" / "backing" impact class, since the receipt token now represents less collateral than deposited.

### Likelihood Explanation
Exploitability requires: (1) a `depositFor` call in-flight (only possible if some contract/bot legitimately uses this function on behalf of users — the codebase includes callers such as relays), and (2) the attacker's ability to flash-loan-skew the Wombat pool's coverage ratio around that transaction, which is capital-intensive but feasible via flash loans and requires no privileged role. This is a MEV/sandwich-style attack, repeatable against every `depositFor` call as long as `_minimumLiquidity` remains hardcoded to `0`.

### Recommendation
Add a `_minimumLiquidity` (or equivalent minimum-output) parameter to `depositFor`, sourced from the actual caller/relay's intended slippage tolerance, and validate it exactly as `deposit()` does — never hardcode zero slippage protection for calls that deposit value on behalf of a third party.

### Proof of Concept
Foundry/Hardhat test plan:
1. Fork BNB chain (or relevant network) at a block with a live Wombat pool used by `WombatPoolHelperV2`.
2. Deploy/attach to `WombatPoolHelperV2`, `WombatStaking`, and the underlying Wombat pool.
3. Simulate a victim/relay flow: victim approves a "relay" contract, relay calls `depositFor(amount, victim)`.
4. Before the relay's tx, have an attacker contract flash-loan a large amount of one of the pool's assets and swap it into the pool to skew the coverage ratio unfavorably for deposits.
5. Execute the victim's `depositFor` call at the skewed ratio; record `lpReceived` (via `stakingToken` balance change for `victim`).
6. Attacker repays flash loan by reversing the swap, capturing profit.
7. Compare `lpReceived` against a baseline run of `deposit()` with a proper `_minimumLiquidity` computed off pre-skew pricing — assert the victim received measurably fewer LP/receipt tokens than fair value, quantifying the loss.
