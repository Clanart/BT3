### Title
Partial-commit line selection is applied against a re-fetched working-directory diff, allowing silent corruption of committed content on external file changes - (`File: app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop lets a user select individual diff lines/hunks to commit ("partial commit"). The line selection is stored as absolute line indices (`DiffSelection`) computed against a specific diff snapshot rendered in the UI. At commit time, `applyPatchToIndex` re-fetches a *fresh* working-directory diff and reuses the old index-based selection against it, with no check that the diff structure still matches what the user actually saw and selected.

### Finding Description
When a user partially stages/commits a file, the renderer keeps a `WorkingDirectoryFileChange.selection` object whose `isSelected(absoluteIndex)` checks are keyed to line offsets (`hunk.unifiedDiffStart + lineIndex`) from the diff that was displayed to the user at selection time.

At commit time, `createCommit` → `stageFiles` → `applyPatchToIndex` does not reuse that already-rendered diff. Instead it independently calls `getWorkingDirectoryDiff(repository, file)` again: [1](#0-0) 

and then builds the patch to `git apply --cached` from that newly fetched diff, applying the user's *old* line-index selection to the *new* hunk structure: [2](#0-1) 

`formatPatch` walks the hunks of this new diff and decides which lines to include using `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is recomputed relative to the *new* hunk layout, not the one the user saw: [3](#0-2) 

If the working tree file is modified between the moment the UI computed/rendered the diff (and the user made a line selection) and the moment `createCommit` runs — e.g. an editor autosave, a build tool, a git hook, or another process writing to the file — hunk boundaries and `unifiedDiffStart` offsets shift. The old selection indices, blindly reapplied to the new hunk geometry, can now correspond to entirely different lines (different content, different hunks, or lines that no longer exist), and `git apply --cached` will happily stage whatever those lines resolve to.

This is the structural analog of the Float Capital bug: a value (the confirmed-but-unsettled balance / here, the "selected" diff lines) is computed against one state snapshot (`userNextPrice_currentUpdateIndex` pointing at price index x+1 / here, the diff shown to the user) but is evaluated against a *different*, later snapshot (`currentMarketUpdateIndex` = x+2 / here, the diff re-fetched at `applyPatchToIndex` time) with no equality/version check between the two, silently corrupting the derived result.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes" — a Desktop-specific security-relevant impact. The user believes they are committing only the lines they explicitly reviewed and checked in the diff viewer, but the actual staged/committed content can differ if the file changed underneath the app between diff rendering and the physical `git apply --cached` call. Because commit content is exactly what gets pushed to the remote and reviewed by teammates, a mismatch here means unintended code (potentially including hunks the user deliberately excluded, e.g. secrets, debug code, or malicious modifications introduced by a compromised build tool/editor plugin/pre-commit process) can end up in the commit without the user's knowledge or consent.

### Likelihood Explanation
The window between diff display and commit execution is typically short but not atomic, and multiple normal workflows can modify tracked files during that window: autosave in an external editor, a formatter/linter running in a file watcher, a build system regenerating a tracked file, or another git operation (stash pop, checkout in another tool) touching the same path. Unlike several other async flows in this codebase (`_changeFileSelection`, `updateChangesWorkingDirectoryDiff`, `updateChangesStashDiff`) which explicitly re-check state before/after the async diff load and bail out on mismatch, `applyPatchToIndex`/`stageFiles`/`createCommit` perform no such before/after consistency check between the diff the selection was computed against and the diff used to build the patch.

### Recommendation
Before calling `git apply --cached`, verify that the diff fetched inside `applyPatchToIndex` matches the diff the user's selection was computed against (e.g. by comparing a hash/fingerprint of the diff or the underlying blob/mtime used when the selection was created). If they differ, abort the partial-stage operation for that file and force the UI to re-diff and require the user to reselect lines, rather than silently applying a stale selection to new hunk geometry.

### Proof of Concept
1. Modify a tracked file with several hunks; open it in Desktop's Changes view so the working-directory diff is fetched and rendered.
2. In the diff viewer, select only specific lines within hunk 2 for partial commit (this creates a `DiffSelection` keyed to absolute indices of the currently-rendered diff).
3. Before clicking "Commit", externally modify the same file (e.g. run a formatter, or have an editor autosave) such that line counts/hunk boundaries shift (add/remove a blank line above the selected hunk).
4. Click "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff (now with shifted hunk offsets) via `getWorkingDirectoryDiff` and reuses the stale `DiffSelection` indices against it in `formatPatch`.
5. Inspect the resulting commit: the staged/committed hunk content does not correspond to the lines the user visually selected in step 2 — some unintended lines are included/excluded, demonstrating silent corruption of committed content that never went through user re-review.

Note: I was unable to fully trace the dispatcher-level call path (`_commitIncludedChanges` or equivalent in `app-store.ts`/`dispatcher.ts`) that invokes `createCommit`, since the specific commit-orchestration function contents weren't retrieved within the available search scope; there may be a re-diff/staleness guard performed higher up in `app-store.ts` before invoking `createCommit` that I could not confirm was present or absent. If such a guard exists, it would mitigate this issue, and I recommend explicitly verifying `app-store.ts`'s commit-initiating method for any diff-staleness check before treating this as confirmed-exploitable in the current build.
