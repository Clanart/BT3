### Title
DataLayer SSRF via unvalidated mirror/subscription URLs causes outbound requests to attacker-chosen hosts - (File: chia/data_layer/download_data.py)

### Summary
Chia's DataLayer service fetches delta files from server URLs that originate from two untrusted sources: URLs supplied directly to the local `subscribe` RPC, and URLs published on-chain by any DataLayer store owner via `add_mirror`/`dl_new_mirror`, which are later pulled into local subscription state by `update_subscriptions_from_wallet()`. Neither path validates the URL's scheme, host, or port before the DataLayer service uses it in an outbound `aiohttp` request. This mirrors the CWE-918 pattern in the reported Apache Ambari advisory: a REST-exposed parameter (there, `api/v1/proxy`; here, a DataLayer mirror URL or subscription URL) is used unchecked as the target of a server-initiated HTTP request, letting a remote/on-chain party direct the victim node's outbound connections at internal-only hosts and ports.

### Finding Description
`DataLayerRpcApi.subscribe()` takes `urls` straight from the RPC request and forwards them to `DataLayer.subscribe()`, which stores them as `ServerInfo` records with no host/scheme allow-listing: [1](#0-0) [2](#0-1) 

Separately, `add_mirror()` publishes an arbitrary URL list on-chain via wallet RPC with only an empty-list check — no host/scheme validation: [3](#0-2) 

Any DataLayer node that is or becomes a subscriber to that store (including via DataLayer offer interactions, since `process_offered_stores()` operates on `store_id`s supplied by the offer/counterparty) periodically calls `update_subscriptions_from_wallet()` to import that store's on-chain mirror URLs into its local subscription list, then unconditionally proceeds to `fetch_and_validate()` for every subscription in the background loop: [4](#0-3) [5](#0-4) 

`fetch_and_validate()` shuffles the resulting `servers_info` and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs `session.get(server_info.url + "/" + filename, ...)` with no restriction on scheme, host, or port (including loopback, RFC1918, or cloud metadata addresses): [6](#0-5) [7](#0-6) 

The behavior differs observably by outcome: a reachable target with valid-looking headers proceeds into `insert_into_data_store_from_file()` parsing (and success/failure is recorded per-server in `server_misses_file()`/`received_correct_file()`, and reflected in the periodic ban/backoff state), while an unreachable target raises `ClientConnectorError`/timeout. This differential is enough to fingerprint open ports/services on hosts that are otherwise unreachable to the attacker, and it forces the victim's own DataLayer process to originate connections into internal network segments the attacker cannot otherwise reach — the same SSRF/port-scan primitive described in the Ambari advisory.

### Impact Explanation
This is not an operator/self-inflicted-only issue: a counterparty in a DataLayer offer, or any DataLayer store publisher whose store another node subscribes to, can plant on-chain mirror URLs pointing at arbitrary internal hosts/ports. This is reachable purely by publishing on-chain data and inducing a victim node to track/subscribe (a normal DataLayer interaction flow), matching the "Medium" severity of the source advisory: it enables port scanning and probing of otherwise-unreachable internal services from the perspective of the victim's node, without requiring any code execution or credential compromise.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: mirror URLs are a normal, unauthenticated (from the perspective of URL content) piece of on-chain state that any store owner controls, and `periodically_manage_data()` automatically imports and fetches from them for every tracked/owned/subscribed store without user review or URL sanitization, so no additional user interaction beyond normal DataLayer subscription/offer flows is required.

### Recommendation
Validate and restrict mirror/subscription URLs before they are persisted or dereferenced: enforce an allow-listed scheme (e.g., `https`), reject loopback/link-local/private-network/metadata-service addresses unless explicitly opted in via config, and consider resolving+checking the destination IP at request time (not just the hostname) to prevent DNS-rebinding bypasses. This validation should be applied both at `DataLayerRpcApi.subscribe()`/`DataLayer.add_mirror()` (input boundary) and again at `http_download()` (request boundary) as defense in depth.

### Proof of Concept
1. Attacker creates a DataLayer store and, as its owner, calls `add_mirror` with `urls=["http://169.254.169.254", "http://127.0.0.1:8555"]` (or any internal target), publishing the mirror coin on-chain.
2. Attacker gets a victim node to track this store — e.g., by proposing/completing a DataLayer offer referencing this `store_id`, or by having the victim manually subscribe (`chia data subscribe -d <store_id>`), which is a normal, expected DataLayer usage flow.
3. On the victim's next `periodically_manage_data()` cycle, `update_subscriptions_from_wallet()` imports the attacker's mirror URLs into the local subscription's `servers_info`, and `fetch_and_validate()`/`http_download()` issues `GET <url>/<delta-filename>` from the victim's DataLayer process directly to the attacker-chosen internal host/port.
4. By observing subsequent subscription/mirror ban-state (`num_consecutive_failures`/`ignore_till` behavior visible via `get_subscriptions`/log timing) across repeated cycles with different candidate internal URLs, the attacker can infer which internal hosts/ports the victim's node was able to reach, achieving the SSRF/port-scan primitive described in the source advisory.

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
