### Title
Forged `ReceivedOutput` accepted without validating that the declared `TxOut`/`OutPoint` exist on-chain, inflating reported received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an attacker-controlled `offset` scalar, `TxOut`, and `OutPoint` from raw bytes with no consistency checks beyond point/scalar decoding. Downstream, `SignableTransaction::new` trusts the embedded `output.value` as real input funds for balance and fee accounting, and the only integrity check in `multisig` compares `p2tr_script_buf(offset.group_key())` against the *claimed* `script_pubkey` — a value the attacker also supplies. A forged `ReceivedOutput` therefore reports funds as received that are not spendable.

### Finding Description
CVE-2018-20332's class is "read of a resource at an attacker-specified location/identity, with no authorization that the caller is entitled to that object." In `bitcoin-serai`, the reachable analog is `ReceivedOutput::read` at `networks/bitcoin/src/wallet/mod.rs:122-134`: it reads `offset` via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns the composite object as authoritative spendable state. Nothing binds the claimed `output`/`outpoint` to a real UTXO, and nothing binds `output.script_pubkey` to `offset` at read time.

When this object is consumed by `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-256`), `input.output.value.to_sat()` is summed into `input_sat` (line 175), which is the sole authority for `NotEnoughFunds`, the change computation (lines 224-235), and `fee()`/`needed_fee`. The only cryptographic check, in `multisig` at `send.rs:273-285`, verifies `p2tr_script_buf(offset.group_key()) == self.prevouts[i].script_pubkey` — but `prevouts[i].script_pubkey` is taken from the same attacker-controlled `TxOut`, so an attacker satisfies it trivially by declaring `script_pubkey = p2tr(group_key + offset*G)` for any `offset` they choose, and any `value` and `outpoint` they choose. Because the real prevout's amount and script are committed in the BIP-341 sighash (`Prevouts::All`, `send.rs:373-390`), the resulting signature is invalid on-chain: the output is reported received but is permanently unspendable.

### Impact Explanation
Any unprivileged party able to feed bytes to `ReceivedOutput::read` (or to a path that constructs `ReceivedOutput` without going through `Scanner::scan_transaction`/`scan_block`) can cause Serai to account for a deposit of arbitrary value — e.g., a claimed 100 BTC input backed by a 546-sat or nonexistent `OutPoint`. The protocol then constructs and threshold-signs a `SignableTransaction` treating those phantom funds as real, corrupting fee/change math (change is computed from the inflated `input_sat`) and producing a transaction that can never confirm. This maps directly to the accepted impact "funds reported received that are not spendable," with additional accounting corruption since the fabricated value flows into `fee()` and change outputs.

### Likelihood Explanation
The deserialization performs zero validation relating the three fields to each other or to chain state; `read` is a trusted-boundary function by design yet the struct is passed through signing plumbing where `output` is trusted as a real prevout. Exploitation requires only control of the serialized bytes reaching `ReceivedOutput::read`; the attacker needs no key material since the script check is self-consistent by construction. The forged input reliably passes `multisig`'s check and produces a deterministic invalid-signature outcome.

### Recommendation
Do not treat `ReceivedOutput` as self-authenticating. Either (a) make `multisig`/`SignableTransaction::new` verify each prevout against the actual chain (fetch the `OutPoint` and compare the full `TxOut`), or (b) at minimum, in `ReceivedOutput::read` or a validation method, require proof that `output.script_pubkey == p2tr_script_buf(key + offset*G)` for the scanner's `key` — i.e., carry the base `key` so the offset-to-script binding is checked against a trusted value rather than the attacker-supplied `script_pubkey` — and treat the value/outpoint as unverified until confirmed against a block.

### Proof of Concept
1. Attacker learns the multisig's base key `K` (public) and picks an arbitrary scalar `o`. Compute `S = p2tr(K + o·G)` — an even-Y tweaked key they cannot spend but can encode.
2. Craft bytes: `offset = o` (32-byte scalar), `TxOut { value: 100 BTC, script_pubkey: S }`, `OutPoint` pointing to a real 546-sat UTXO or a nonexistent one. Feed to `ReceivedOutput::read` — it succeeds.
3. `SignableTransaction::new` sees `input_sat = 100 BTC`, builds payments/change against it; `multisig` passes because the check compares `p2tr_script_buf(offset.group_key())` to the attacker-declared `script_pubkey`.
4. Threshold signing produces a transaction whose BIP-341 sighash commits the false prevout amount/script — invalid on-chain; the "received" 100 BTC is unspendable and the accounting/fee computation is corrupted.
