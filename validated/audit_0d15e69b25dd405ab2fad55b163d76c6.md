### Title
Cross-transaction overwrite of `presumed_origin`/`data` for scanned outputs in `get_outputs` - (File: processor/src/networks/bitcoin.rs)

### Summary
The SSS exploit's bug class is value mis-accounting when an operation expected to act on a distinct counterparty instead acts on the same entity twice. In `Bitcoin::get_outputs`, the `outputs` accumulator is declared **outside** the per-transaction loop, so when more than one transaction in a block pays the multisig key, the `for output in &mut outputs` pass rewrites `presumed_origin` and `data` for every previously collected output with the *later* transaction's origin and `InInstruction` data. An unprivileged sender who causes two payments to the Serai multisig to land in one block can therefore mis-attribute the instruction data and refund origin of the earlier deposit.

### Finding Description
`get_outputs` builds a `Scanner` for the group key, then iterates `block.txdata[1 ..]` (skipping the coinbase). For each transaction it pushes newly scanned outputs into a single `outputs` Vec declared before the loop [1](#0-0) . After pushing, it computes `presumed_origin` from `tx.input[0]`'s spent output address and `data` from `Self::extract_serai_data(tx)`, then assigns them to **`&mut outputs`** — the entire accumulated Vec, not just the outputs from the current `tx` [2](#0-1) .

So for block `[txA (pays key), txB (pays key)]`:
- txA iteration: `outputs = [a]`; `a.presumed_origin = originA`, `a.data = dataA`.
- txB iteration: `outputs = [a, b]`; the loop overwrites `a.presumed_origin = originB` and `a.data = dataB` as well as setting `b`'s.

The only guard is `if outputs.is_empty() { continue; }`, which does not prevent the overwrite when a later paying tx exists [3](#0-2) . These `Output`s are then filtered and returned upstream as the block's received outputs, where `kind == External` outputs carry `data` into instruction handling and `presumed_origin` into refund logic [4](#0-3) , [5](#0-4) .

### Impact Explanation
`presumed_origin` and `data` drive how an external deposit is credited and where refunds are sent. An attacker can:

1. Send txB in the same block as a victim's deposit txA (or send both themselves), each paying the multisig.
2. txA's scanned output is reported with txB's `presumed_origin` and txB's embedded `InInstruction` data.

Consequences: a deposit is processed under an attacker-chosen instruction (routing the credited funds per the attacker's `data` rather than the depositor's), and/or the refund origin recorded for the deposit points to the attacker's address — enabling misdirection of bridged funds or theft of refunds. This is "funds reported received" with corrupted metadata, reachable purely with public Bitcoin transactions the attacker broadcasts.

### Likelihood Explanation
Bitcoin blocks routinely contain multiple transactions paying the same address; the attacker controls ordering and can also be the sender of both transactions, making triggering fully within an unprivileged party's reach. The flaw triggers deterministically whenever ≥2 transactions in one scanned block contain outputs to the multisig's scripts — no validator misbehavior, reorg, or race is required. Severity is bounded by what control over `data`/`presumed_origin` grants in instruction/refund handling rather than by direct signature forgery, so Medium-to-High depending on downstream trust in `presumed_origin`.

### Recommendation
Scope the post-processing to only the outputs scanned from the current transaction:

```rust
for tx in &block.txdata[1 ..] {
    let scanned: Vec<Output> = scanner.scan_transaction(tx)
        .into_iter()
        .map(|output| { /* build Output with kind */ })
        .collect();
    if scanned.is_empty() { continue; }
    // compute presumed_origin and data, apply to `scanned` only
    outputs.extend(scanned);
}
```

Equivalently, track the start index (`let start = outputs.len();` before pushing) and iterate `&mut outputs[start ..]`, so prior transactions' outputs are never re-touched. This mirrors the fix pattern for the SSS class: ensure each state mutation applies to exactly the entity (transaction) it corresponds to.

### Proof of Concept
```rust
// Conceptual PoC against Bitcoin::get_outputs
// Block contains:
//   txA: input from ALICE, output -> p2tr(key + external_offset), OP_RETURN dataA
//   txB: input from ATTACKER, output -> p2tr(key + external_offset), OP_RETURN dataB
//
// get_outputs(block, key):
//   txA iteration: outputs=[oA]; oA.presumed_origin=ALICE, oA.data=dataA
//   txB iteration: outputs=[oA,oB];
//     for output in &mut outputs {           // iterates BOTH
//       output.data = dataB;                  // oA.data now dataB  <-- BUG
//       output.presumed_origin = ATTACKER;   // oA.origin now ATTACKER
//     }
//
// Result: the deposit from txA is reported with ATTACKER's origin and dataB
// instruction, even though txA actually carried dataA and was funded by ALICE.
```

The fix is a one-line scope change; the bug exists because the accumulator declared at [6](#0-5)  outlives the per-transaction iteration at [7](#0-6) .
