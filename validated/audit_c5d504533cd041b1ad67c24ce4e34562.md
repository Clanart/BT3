## Title
NUL-byte field desynchronization in `createLogParser` can cause an attacker-controlled string to be assigned to `Commit.sha`, which is then passed unvalidated to `git revert` — ([File: app/src/lib/git/git-delimiter-parser.ts])

## Summary
`getCommits` in `app/src/lib/git/log.ts` builds a `git log` format string by joining requested fields with the literal separator `%x00` and appends the `-z` flag, then parses the resulting buffer with `createLogParser`. [1](#0-0) 
The parser's `parse` function naively chunks the NUL-split records array into fixed-size groups of `keys.length` with no re-synchronization logic: [2](#0-1) 
This design implicitly assumes that no field's *content* (e.g. `%s`/`%b` summary/body, or `%(trailers:unfold,only)`) ever contains a literal NUL byte, because NUL is being (ab)used simultaneously as both the intra-record field separator and (via `-z`) the inter-record terminator.

## Finding Description
Git's on-disk commit object format stores the commit message as a length-prefixed byte blob, not a NUL-terminated string, so a commit message *can* contain an embedded NUL byte if the object is constructed directly (e.g. via low-level plumbing/fast-import) rather than through the `git commit` porcelain, which normally strips such bytes. Git's `fsck` check for this condition (`nulInCommit`) is a warn-level, non-fatal check, and `fetch.fsckObjects`/`transfer.fsckObjects` are **off by default**, so such an object is accepted silently during a normal `clone`/`fetch` from an attacker-controlled remote.

If a commit's message field contains an embedded NUL, `splitBuffer`/`String.split('\0')` in `createLogParser.parse` will produce one extra record for that commit than expected. Because the loop advances strictly by `keys.length` with no anchor, this extra record shifts the alignment for that commit **and every subsequent commit** in the same `git log` invocation — field values from one logical position bleed into a different named field (e.g., a `body`/`trailers` fragment ends up assigned to `sha`). [3](#0-2) 

This misaligned value flows straight into the `Commit` model: [4](#0-3) 

and from there into `revertCommit`, which pushes it directly as an argv element to `git revert`: [5](#0-4) 

## Impact Explanation
Because `commit.sha` is used directly as a git revision argument, an attacker who controls repository content served over a crafted git remote can cause the wrong (attacker-influenced) revision string to be passed to `git revert`. `git` is invoked via `dugite`'s `exec` with an argv array (not a shell string), so this is not classic shell injection, but it does allow: (a) silent corruption of what the user reverts/commits (a core "Valid Impact" category — silent corruption of what the user commits or pushes), and (b) potential git option/argument injection if the misaligned value begins with `-`, since `git revert` accepts option-like arguments (e.g. `--gpg-sign=...`, `--strategy=...`, `-X<option>`) that could alter revert behavior in unexpected ways.

## Likelihood Explanation
Exploitation requires the attacker to construct a git object with an embedded NUL in the commit message (achievable via low-level object crafting, not the normal CLI) and have the victim clone/fetch from that attacker-controlled remote — this is squarely in scope ("a git remote/proxy response"). It does not require local access, admin rights, or social engineering beyond adding/cloning a repository, which is a normal, expected user action in GitHub Desktop.

## Recommendation
- Reject or sanitize commit message fields that contain literal NUL bytes before or during parsing (e.g., replace embedded `\0` with a safe placeholder), or
- Make `createLogParser.parse` resilient to unexpected NUL counts by validating that the total record count is an exact multiple of `keys.length` and rejecting/logging otherwise instead of silently misaligning, and
- Validate that `commit.sha` matches an expected SHA-1/SHA-256 hex format before using it as a git revision argument in `revert.ts` (and other similar consumers), rejecting anything that doesn't match `^[0-9a-f]{7,64}$`.

## Proof of Concept
1. Using low-level plumbing (e.g., `git hash-object -w -t commit --stdin` or `git fast-import`) construct a commit object whose message body contains a literal `\0` byte (e.g. `git fast-import` with an inline `data <n>` blob length that includes an embedded NUL), and set that commit as a repository ref (`refs/heads/main`).
2. Serve this repository via a git server/proxy the attacker controls (default `fetch.fsckObjects=false` means the embedded NUL will not be rejected).
3. Have the victim clone/fetch this repository in GitHub Desktop, then open History (invokes `getCommits`, `app/src/lib/git/log.ts:120-205`).
4. Instrument/log the parsed `entries` from `createLogParser.parse` (`app/src/lib/git/git-delimiter-parser.ts:23-36`) to confirm that `commit.sha` for a commit following the corrupted one is not a valid 40/64-hex SHA but a fragment of another field's content.
5. Trigger "Revert this commit" for the corrupted entry and observe that `args.push(commit.sha)` (`app/src/lib/git/revert.ts:33`) passes the corrupted, non-SHA string to `git revert`.

**Note on verification limits:** I was unable to fully verify within this session (a) whether GitHub Desktop's dugite/git build enables `transfer.fsckObjects`/`fetch.fsckObjects` by default in its bundled git config, and (b) whether any upstream sanitization strips NUL bytes from commit messages elsewhere in the fetch/clone pipeline before `getCommits` is called. These would need to be confirmed with a live PoC to fully validate exploitability; the code-level parsing flaw itself (`createLogParser`'s lack of re-synchronization) is confirmed in the source shown above.

```typescript
export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }
```
