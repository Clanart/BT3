### Title
Stop-hook review set silently drops dangerous changes committed via `git commit --amend` (or any non-fast-forward HEAD move) - (File: `plugins/security-guidance/hooks/diffstate.py`)

### Summary
`compute_v2_review_set` in `diffstate.py` computes the Stop-hook's LLM-review file set as `dirty_now & changed_since`, where `dirty_now` is populated with committed-but-clean changes only when the ancestry check `_is_ancestor(head_at_capture, current_head)` succeeds. `git commit --amend` (and any other non-fast-forward HEAD move such as `reset`+recommit or interactive rebase) replaces `HEAD` with a sibling commit rather than a descendant, so the ancestry check fails, `dirty_now` stays empty for a clean working tree, and the intersection with `changed_since` becomes empty even though `changed_since` correctly shows the dangerous file changed. The result is that a dangerous change committed via amend is never sent to the LLM security reviewer.

### Finding Description
`capture_git_baseline` (`plugins/security-guidance/hooks/diffstate.py:163-204`) snapshots the working tree at `UserPromptSubmit` via `git stash create`, and `head_at_capture` is recorded alongside it [1](#0-0) .

At Stop, `compute_v2_review_set` builds the review set: [2](#0-1) 

The head-advance branch only adds committed files to `dirty_now` when `_is_ancestor(head_at_capture, current_head)` is true, i.e., only for a fast-forward/linear sequence of new commits: [3](#0-2) 

`git commit --amend` replaces `HEAD` with a new commit whose parent is the *same* parent as the pre-amend commit — the old `head_at_capture` is not an ancestor of the new amended `HEAD`, it is a sibling. Consequently:
- `tracked_dirty` and `untracked` are both empty (working tree is clean after a normal amend), so `dirty_now == ∅`.
- The ancestry check fails, so `dirty_now` is never populated with the amended commit's files.
- `changed_since = _git_name_only(repo, baseline_sha)` (a `git diff --name-only <baseline_sha> HEAD`) *does* correctly list the dangerous file, since it directly diffs the stash-baseline SHA against the amended HEAD [4](#0-3) .
- `review_set = dirty_now(∅) & changed_since({dangerous_file, ...}) = ∅`.

The dangerous file is silently dropped from `review_paths` even though it demonstrably changed relative to the baseline. This breaks the stated invariant that the review set must stay bound to the correct repo/baseline/touched paths, because a normal, unprivileged git operation (`commit` then `amend`) shifts what the ancestry check treats as "linear progress," causing a real diff to be treated as if nothing happened.

No approval prompt, allowlist, or workspace guard intercepts this — the flaw is purely in the set-intersection logic of `compute_v2_review_set`, and it applies to the Stop-hook's LLM security review path specifically (`ENABLE_STOP_REVIEW`/`ENABLE_CODE_SECURITY_REVIEW`), which is documented as the "final review" gate [5](#0-4) .

### Impact Explanation
An unprivileged party who can influence Claude Code's Bash tool usage (e.g., via prompt injection in repository content) can have Claude introduce a dangerous change, commit it, then amend it (a completely ordinary, unprivileged git sequence), causing the Stop-hook's git-diff-derived LLM security review to compute an empty review set for that file. This means the dangerous change is never scanned by the vulnerability/areas-of-concern LLM passes and no `exit(2)` guidance is emitted — effectively bypassing the plugin's only automated safety net for that turn, matching "Unauthorized local command execution that bypasses Claude Code approval or deny controls" in spirit: the plugin's review/deny signal is suppressed for an actually-dangerous commit.

### Likelihood Explanation
Highly feasible and fully repeatable: it requires only two ordinary git commands (`git commit`, `git commit --amend`) executed in the current turn, no special privileges, no race conditions, and no reliance on interrupted turns or timing. Any turn where Claude amends a commit after making a dangerous edit reproduces the bug deterministically.

### Recommendation
In `compute_v2_review_set`, do not gate committed-file inclusion solely on `_is_ancestor(head_at_capture, current_head)`. When HEAD changed but is not a linear descendant of `head_at_capture` (amend, rebase, reset+recommit), fall back to including `_git_name_only(repo, baseline_sha)` (i.e., treat `changed_since` as `dirty_now` directly, or union it in) rather than intersecting with a `dirty_now` that structurally cannot reflect non-fast-forward commits. Alternatively, always union `changed_since` files that are also reachable from current `HEAD` (via `git diff --name-only baseline_sha HEAD`) into `dirty_now` regardless of the ancestry relationship, since `changed_since` already only reflects real content diffs against the trusted baseline SHA.

### Proof of Concept
Integration test plan for `compute_v2_review_set`:
1. Init a repo, create an initial commit (`README`), capture `baseline_sha = capture_git_baseline(cwd)` and `head_at_capture = git rev-parse HEAD`.
2. Write a dangerous file (`eval(user_input)`), `git add`, `git commit -m "wip"`.
3. `git commit --amend -m "final"` with no further working-tree changes (tree ends clean).
4. Call `compute_v2_review_set(cwd, baseline_sha, head_at_capture, {})`.
5. Assert: `dangerous_file` path IS present in the returned `review_paths` (expected/desired) — current behavior: `review_paths == []`, demonstrating the dangerous file is dropped from review despite differing from `baseline_sha`.
