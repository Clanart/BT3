### Title
Scanner reports zero-value/dust outputs as received funds, enabling griefing and fee drain - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` accepts any transaction output whose `script_pubkey` matches a registered script, with no minimum-value or dust check. An unprivileged party can send zero-value or sub-dust outputs to the threshold wallet's address; each is returned as a `ReceivedOutput` indistinguishable from a real deposit. These outputs are economically unspendable (their value cannot cover the marginal fee to include them as inputs), yet `SignableTransaction::new` will happily consume them — inflating transaction weight, the fee, and the number of FROST signatures required — or force the wallet to leave reported "funds" stranded forever.

### Finding Description
`scan_transaction` iterates all outputs of an arbitrary on-chain transaction and pushes a `ReceivedOutput` for every `script_pubkey` match, without inspecting `output.value`:

```rust
// networks/bitcoin/src/wallet/mod.rs
pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for (vout, output) in tx.output.iter().enumerate() {
    let Ok(vout) = u32::try_from(vout) else { break };
    if let Some(offset) = self.scripts.get(&output.script_pubkey) {
      res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
    }
  }
  res
}
``` [1](#0-0) 

Bitcoin consensus permits outputs of value 0 (only standardness/relay policy enforces the ~546 sat dust limit), so an attacker cooperating with — or being — a miner, or simply waiting for policy-lax relay, can create arbitrarily many dust/zero outputs to the wallet's key. Note that `DUST = 546` is defined in `send.rs` and enforced on *payments* (`TransactionError::DustPayment`) and on *change*, but never on *inputs* — the symmetric receive-side check is missing. [2](#0-1) [3](#0-2) 

The downstream consumer mirrors this asymmetry: `SignableTransaction::new` sums all input values and builds one `TxIn` per `ReceivedOutput`, requiring one full FROST signature per input (`self.sigs.len() == tx.input.len()`), each adding ~66 vbytes of weight to be paid for. [4](#0-3) [5](#0-4) 

### Impact Explanation
- Funds reported received that are not economically spendable: a 0- or 1-sat `ReceivedOutput` is spendable in the consensus sense but costs more in fees than its value; the wallet's accounting overstates its balance.
- Griefing/fee drain: if these outputs are swept into a `SignableTransaction` (e.g., consolidation/spend of "all" received outputs), each dust input adds signature weight the honest inputs must pay for — directly analogous to the reported "drain the node's funds" impact.
- DoS amplification: each spammed output adds a `TxIn`, a Schnorr/FROST signing round per input, and witness data; enough dust pushes the transaction over `MAX_STANDARD_TX_WEIGHT` (rejected with `TooLargeTransaction`), blocking legitimate spends entirely.
- This matches the bug class precisely: a deposit path with no minimum-amount/fee check, reachable by any unprivileged party via an on-chain transaction they send.

### Likelihood Explanation
Sending a dust/zero-value output requires only a crafted transaction — cheap for a miner or via direct submission. Once created, the output permanently sits in `Scanner`'s results; there is no filtering or expiry, so repeated dust sends accumulate and the griefing compounds over time. No privileged position, collusion, or key material is needed.

### Recommendation
Enforce a minimum value on received outputs: in `Scanner::scan_transaction` (or at `ReceivedOutput` construction), skip outputs with `output.value.to_sat() < DUST` (546), mirroring the `DustPayment` check already applied to payments in `SignableTransaction::new`. Alternatively/additionally, reject inputs below `DUST` in `SignableTransaction::new` so a dust `ReceivedOutput` can never be consumed.

### Proof of Concept
Conceptual, against `Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs`:

```rust
// key = wallet group key; scanner = Scanner::new(key).unwrap()
let dust_tx = Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: vec![/* any valid input funding the tx */],
  output: vec![
    TxOut {
      value: Amount::from_sat(0),          // or 1..=545 sats
      script_pubkey: p2tr_script_buf(key).unwrap(),
    };
    100                                     // spam 100 zero-value outputs
  ],
};

let received = scanner.scan_transaction(&dust_tx);
assert_eq!(received.len(), 100);            // all reported as received funds
assert_eq!(received[0].value(), 0);         // each worthless

// Consuming them:
let res = SignableTransaction::new(received, &payments, None, None, fee_rate);
// Either succeeds (burning real funds as fees for worthless inputs and
// requiring 100 FROST signature rounds), or fails with TooLargeTransaction /
// NotEnoughFunds, leaving the wallet unable to spend cleanly.
```

Each asserted `ReceivedOutput` carries the wallet's spendable offset and a valid outpoint, yet its value is zero — reported received, not spendable.
