### Title
Zero-slippage WOM→mWom swap driven by manipulable spot pool ratio permanently steals staker yield during permissionless `harvest()` - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking._sendRewards` automatically converts a portion of harvested WOM reward fees into mWom via `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` whenever pool rewards are harvested [1](#0-0) . `smartConvert` in turn computes a conversion ratio from `currentRatio()` and `maxSwapAmount()`, both of which read the wom/mWom pool's *current* spot state (`Asset.cash()`/`liability()` and `IWombatRouter.getAmountOut` against the live pool) rather than any time-weighted or manipulation-resistant price source [2](#0-1) . This is the same bug class as the reported `slot0` issue: using the most recent, trivially manipulable on-chain price/liquidity state to drive value-affecting logic.

### Finding Description
`_convertFor` then executes the actual on-chain swap of the buyback portion with **zero slippage protection**:
```solidity
amountRec = IWombatRouter(router).swapExactTokensForTokens(
    tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp
);
``` [3](#0-2) 

The only downstream guard is `if (convertAmount + amountRec < _minRec) revert MinRecNotMatch();`, but when invoked via `smartConvert` from `WombatStaking._sendRewards`, `_minRec` is hardcoded to `0` [4](#0-3) , so the guard provides no protection in the automatic harvest path.

`WombatStaking.harvest(_lpToken)` is an external function gated only by `whenNotPaused` and `_onlyActivePool(_lpToken)` [5](#0-4) ; it internally calls `_toMasterWomAndSendReward` → `_sendRewards` → `smartConvert` → the unprotected swap. This chain is reachable from an ordinary, unprivileged wallet (any address can call `harvest`), so any MEV actor can:
1. Front-run `harvest()` by swapping in the wom/mWom pool to skew `cash()`/`liability()` (and thus `currentRatio()`/`maxSwapAmount()`), and/or simply sandwich the zero-slippage `swapExactTokensForTokens` call itself.
2. Extract the difference between fair value and the executed price on the WOM fee amount that was destined for stakers' reward pool (`IBaseRewardPool(_rewarder).queueNewRewards`).
3. Back-run to restore the pool, pocketing the loss extracted from protocol reward flow.

I was not able to fully confirm within the available tool budget whether `_onlyActivePool` imposes any caller restriction beyond validating that `_lpToken` is registered/active (I could only locate the modifier's usage sites, not its full body), so there is residual uncertainty about whether `harvest()` is truly open to any wallet or restricted to specific callers.

### Impact Explanation
The WOM portion of harvested rewards is fee income destined for stakers via `IBaseRewardPool(feeInfo.to).queueNewRewards` / `IBaseRewardPool(_rewarder).queueNewRewards` [6](#0-5) . Because the WOM→mWom leg of that fee execute with `0` minimum output and a ratio computed from live, unprotected pool state, value is siphoned out of the reward stream before it ever reaches users — this is a direct, repeatable theft of unclaimed yield belonging to all stakers of the affected pool, not just the caller.

### Likelihood Explanation
Every call to `harvest()` (or any of the deposit/withdraw paths that route through `_toMasterWomAndSendReward`/`_sendRewards` when the WOM fee is non-zero and `smartWomConverter` is set) triggers this unprotected swap. Since `harvest` appears externally callable and MEV bots routinely watch mempools for arbitrage/sandwich opportunities on AMM swaps, exploitation is straightforward and requires no special privilege — only capital to front-run/back-run the swap.

### Recommendation
- Do not hardcode `_minRec = 0` when `WombatStaking` calls `smartConvert`; instead pass a slippage-bound minimum derived off-chain or from a TWAP-based quote.
- In `SmartWomConvert._convertFor`, never pass `0` as the router's minimum-out parameter for the internal buyback swap; propagate a real minimum computed from a manipulation-resistant reference price.
- Replace `currentRatio()`/`maxSwapAmount()`'s reliance on the pool's instantaneous `cash()`/`liability()` state with a time-weighted or otherwise deviation-checked reference, mirroring the `_checkPriceDeviation` fix referenced in the original report.

### Proof of Concept
1. Attacker monitors mempool for any `WombatStaking.harvest(_lpToken)` (or deposit/withdraw) call that will trigger `_sendRewards` with a non-zero WOM fee and `smartWomConverter` configured.
2. Attacker front-runs with a large swap in the wom/mWom pool to depress the mWom-out price and/or simply sandwiches the internal `swapExactTokensForTokens(..., 0, ...)` call inside `_convertFor` [7](#0-6) .
3. The victim transaction executes the zero-slippage swap at the manipulated price, converting the protocol's WOM fee into fewer mWom tokens than fair value.
4. Attacker back-runs to restore the pool and realize the extracted value, which is permanently lost from the amount that would have been queued to `IBaseRewardPool` for stakers.
