## Analysis

The external report's broken invariant is: **a price oracle can lag a real, sudden price change long enough that an attacker exploits the stale value before it updates, extracting more value than the corrected price would allow — in a single unprivileged transaction.**

The Hyperbridge repo does not run a lending protocol, but it ships `SimplexPaymaster`, an ERC-4337 paymaster that also derives an exchange rate from Chainlink price feeds and only guards against staleness via a fixed **age** window (`maxOracleAge`), not against a price-jump/deviation. This is the same failure mode: the guard checks "is the timestamp recent enough" rather than "is the price still economically sound," so a hard depeg inside the age window is silently trusted.

### Title
Stale Chainlink price acceptance in `SimplexPaymaster` allows draining paymaster ETH during a stablecoin depeg - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` only rejects a Chainlink answer if `block.timestamp - updatedAt > maxOracleAge`; it performs no price-deviation or "answer freshness relative to true market" check [1](#0-0) . `_tokenPrice`/`_fetchDetails` use this stale-but-"fresh-enough" value to compute how many stablecoin units the paymaster charges per wei of gas [2](#0-1) . Exactly as in the swETH TWAP report, a sudden step-function price move (e.g. a stablecoin depeg) is not reflected until the feed updates, and up to that point any unprivileged user can submit `UserOperation`s through the public ERC-4337 `EntryPoint` and pay with the devalued token at the old (higher) peg price, draining real native-asset value from the paymaster's `EntryPoint` deposit.

### Finding Description
`_getOraclePrice` is the only defense against a bad Chainlink reading:
```solidity
function _getOraclePrice(...) internal view returns (uint256) {
    (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(...);
    if (block.timestamp - updatedAt > maxOracleAge) revert StaleOraclePrice(...);
    ...
}
```
`maxOracleAge` is governance-configurable up to `MAX_ORACLE_AGE = 7 days`, and the contract's own comment acknowledges wide, intentional staleness windows: *"Base/Ethereum stablecoins up to 24h"* [3](#0-2) . There is no check that the answer reflects a recent price *level* (e.g., deviation bound, `answeredInRound >= roundId`, or comparison against a secondary source) — it only checks the answer's age.

`_tokenPrice` computes the amount of token charged per wei of native gas directly from `tokenUsd`:
```solidity
return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
``` [2](#0-1) 

If `tokenUsd` used here is stale-high (the feed hasn't yet caught up to a depeg down, e.g. the token is really worth $0.90 but the feed still reports ~$1.00 within the allowed age window), `tokenPrice` computes as *lower* than it should be — meaning the paymaster charges fewer token units for the same amount of native gas than the token is actually worth. `_fetchDetails` (invoked by the base `PaymasterERC20` during standard, permissionless `_validatePaymasterUserOp`/`_postOp` flow) uses this under-priced rate to pull `erc20Cost` from the user and have the `EntryPoint` release real native-asset gas/refund from the paymaster's deposit [4](#0-3) .

Because `_validatePaymasterUserOp`/`_fetchDetails` are reachable by anyone bundling a `UserOperation` through the public `EntryPoint` (no relayer, prover, admin, or governance actor is involved), an attacker who is holding (or cheaply acquires) the depegging token can flood the mempool with `UserOperation`s that consume the paymaster's `EntryPoint` deposit — paying in a token now worth materially less than the price the paymaster still assumes — until the feed updates or `maxOracleAge` forces a revert.

### Impact Explanation
This is a direct, unauthorized extraction of funds held by the paymaster (native asset deposited at the `EntryPoint`, funded by the treasury/governance) using an economically-invalid price. It matches the bounty's "stealing or loss of funds" / "transaction manipulation" categories: an unprivileged caller manipulates the effective exchange rate accepted by the protocol to obtain gas subsidization worth more than the tokens surrendered, draining the paymaster's `EntryPoint` balance.

### Likelihood Explanation
Requires only a real-world stablecoin depeg event of sufficient magnitude and duration to exceed `maxOracleAge` before the feed catches up (a scenario Chainlink feeds have historically exhibited, e.g. during USDC's March 2023 depeg) — no relayer, prover, or privileged role compromise is needed, and the exploit is a single, self-contained sequence of `UserOperation`s submitted by any account holding the depegging token and its allowance/permit to the paymaster.

### Recommendation
- Add a price-deviation/sanity bound (e.g., reject or require re-verification if `answer` deviates more than X bps from a stored reference or a secondary oracle) in addition to the timestamp-age check.
- Tighten `MAX_ORACLE_AGE`/`maxOracleAge` for stablecoin feeds and/or add a governance-triggerable pause (already present via `DeactivateToken`) that can be invoked quickly on detecting depeg events, and consider rate-limiting/per-block caps on paymaster-subsidized value per token to bound worst-case drain during the staleness window.

### Proof of Concept
1. Token `T` (e.g. USDC) is registered in `SimplexPaymaster` with `maxOracleAge` set to, say, 24h per the code's documented rationale [3](#0-2) .
2. `T` depegs sharply (true price drops materially below the last reported Chainlink answer) but the Chainlink feed's `updatedAt` is still within `maxOracleAge`, so `_getOraclePrice` accepts it [1](#0-0) .
3. Attacker (any address holding depegged `T` with allowance/permit to the paymaster) submits many `UserOperation`s through the public `EntryPoint` using mode `0x01`/`0x00`; `_fetchDetails`/`_tokenPrice` compute `tokenPrice` from the stale `tokenUsd`, undercharging `T` relative to its real value [5](#0-4) .
4. Each UserOp causes the `EntryPoint` to release real native-asset value from the paymaster's deposit for an under-priced amount of devalued `T`, repeated across many ops/blocks until the oracle updates or `StaleOraclePrice` finally reverts — net draining the paymaster.

    /// @dev Returns the token to charge and its price relative to native gas.
    ///
    ///      PaymasterERC20 computes `erc20Cost = weiCost * tokenPrice / 1e18`,
    ///      so tokenPrice must be token base units per wei, scaled by 1e18:
    ///        tokenPrice = (nativeUsd * 10^tokenDecimals) / tokenUsd
    ///      e.g. BNB at $600, USDC at $1 with 6 decimals: 0.001 BNB (1e15 wei)
    ///      should cost 0.60 USDC (600000 units), giving tokenPrice = 6e8, which
    ///      is exactly (600e8 * 1e6) / 1e8. Markup is applied on top.
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }
```
