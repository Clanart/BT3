Confirmed: `Nonce<T>` in `modules/pallets/relayer/src/lib.rs` is a single `StorageDoubleMap<address, StateMachine, u64>` shared by two independent signature-authorization flows — `accumulate()`'s beneficiary redirect and `withdraw()`'s beneficiary specification — and both flows hash the exact same tuple shape into the signed digest.

### Title
Cross-domain signature replay via shared `Nonce` storage between `withdraw()` and `accumulate()` beneficiary authorizations - ([File: modules/pallets/relayer/src/lib.rs])

### Summary
`pallet-ismp-relayer` uses one `Nonce<T>` double-map keyed by `(address, StateMachine)` to authorize two functionally distinct signed actions: redirecting accumulated-fee credit to a beneficiary in `accumulate()`, and dispatching an on-chain payout to a beneficiary in `withdraw()`. Both actions hash an identical `(nonce, StateMachine, beneficiary)` tuple with no domain-separation tag, so a signature produced for one action is byte-identical to (and accepted as) a valid signature for the other.

### Finding Description
`withdrawal.rs::message()` computes the signed digest as: [1](#0-0) 

`accumulate.rs::beneficiary_message()` computes: [2](#0-1) 

These are the same SCALE-encoded `(u64, StateMachine, Vec<u8>)` tuple hashed with `keccak_256` — there is no discriminator (e.g. a purpose tag) separating "authorize a redirect during accumulate" from "authorize a withdrawal payout." Both consumers read and increment the nonce from the identical storage item: [3](#0-2) 

`withdraw()` fetches/increments the nonce and verifies against `message()`: [4](#0-3) 

`accumulate()` fetches/increments the *same* nonce map and verifies against `beneficiary_message()`: [5](#0-4) 

Because the report's core broken invariant is "no domain separation / no way to invalidate a signed authorization before it is consumed for an unintended purpose," this is a direct local analog: a relayer who signs a beneficiary-redirect message for `accumulate()` at nonce `N` on chain `X` produces a signature that is also a syntactically valid `withdraw_fees` authorization for the same `(N, X, beneficiary)` — and vice versa. Whichever call is submitted first to the (unsigned, `validate_unsigned`-gated) extrinsic pool consumes the nonce and executes with the beneficiary embedded in the shared payload, regardless of which action the relayer actually intended.

### Impact Explanation
If an attacker (or a rogue relayer's counterparty) observes a `beneficiary_details` signature broadcast for `accumulate_fees` (these are public unsigned extrinsics gossiped in the transaction pool per `validate_unsigned`), they can resubmit the identical `(signature, beneficiary)` pair as `withdraw_fees` input before the relayer's intended `accumulate_fees` call lands — dispatching an actual on-chain fee payout (`DispatchPost` to the host manager) to that beneficiary immediately, and zeroing the relayer's `Fees` entry, even though the relayer only meant to redirect *future* accumulation credit, not trigger an immediate transfer. Conversely, a `withdraw_fees` signature can be replayed as an `accumulate_fees` beneficiary redirect. Either direction moves the effect of one signed authorization into an unintended pallet function, matching "logic attack / transaction manipulation" and "wrong beneficiary or amount" in the bounty's impact list, without requiring a malicious relayer, prover, or admin — any third party who observes the gossiped extrinsic can act.

### Likelihood Explanation
Both `accumulate_fees` and `withdraw_fees` are `ensure_none` (unsigned) extrinsics validated via `validate_unsigned`, meaning submitted payloads (including the beneficiary signature) are visible in the public transaction pool before inclusion: [6](#0-5) 
Exploitation requires only observing a pending extrinsic and resubmitting its signature bytes wrapped in the other call's input struct — no cryptographic break, no privileged role, and no reliance on a malicious relayer/prover.

### Recommendation
Add a distinct domain-separation tag (e.g. a pallet/purpose-specific prefix or the call name) into both `message()` and `beneficiary_message()` before hashing, so a signature valid for `withdraw_fees` can never decode as valid input for `accumulate_fees`'s beneficiary redirect (and vice versa). Alternatively, split the nonce into two independent storage maps, one per action, so consuming one namespace cannot be triggered by a signature intended for the other.

### Proof of Concept
1. Relayer `R` (address `A`) has accrued fees on chain `X`, current `Nonce::<T>::get(A, X) == n`.
2. `R` signs `beneficiary_message(n, X, B)` intending to submit `accumulate_fees` with `beneficiary_details = (B, sig)` to redirect future accumulation credit to `B`.
3. Attacker observes this pending unsigned extrinsic in the mempool and extracts `(B, sig)`.
4. Attacker immediately submits `withdraw_fees` with `WithdrawalInputData { signature: sig, dest_chain: X, beneficiary: Some(B) }`. Since `message(n, X, B) == beneficiary_message(n, X, B)` (identical encoding) and `Nonce::<T>::get(A, X)` is still `n`, `withdraw()`'s signature check at [7](#0-6)  passes.
5. `withdraw()` dispatches an immediate on-chain payout of `R`'s entire `Fees` balance to `B`, zeroes `Fees`, and increments the nonce — consuming it before `R`'s originally intended `accumulate_fees` call can land, causing `R`'s subsequent `accumulate_fees` submission to fail nonce/signature verification and the payout to occur at a time and via a mechanism `R` never authorized.

	impl<T: Config> ValidateUnsigned for Pallet<T>

		T::Balance: Into<u128>,

		// empty pre-dispatch so we don't modify storage
		fn pre_dispatch(_call: &Self::Call) -> Result<(), TransactionValidityError> {

		fn validate_unsigned(_source: TransactionSource, call: &Self::Call) -> TransactionValidity {
			let res = match call {
				Call::accumulate_fees { withdrawal_proof } =>
					Self::accumulate(withdrawal_proof.clone()),
				Call::withdraw_fees { withdrawal_data } => Self::withdraw(withdrawal_data.clone()),
				Call::claim_outbound_consensus_delivery_reward { claim } =>
					Self::process_outbound_consensus_delivery_claim(claim.clone()),
				Call::claim_outbound_request_delivery_reward { claim } =>
					Self::process_outbound_request_delivery_claim(claim.clone()),
				_ => Err(TransactionValidityError::Invalid(InvalidTransaction::Call))?,
			};

			if let Err(err) = res {
				log::error!(target: "ismp", "Pallet Relayer Fees error {err:?}");
				Err(TransactionValidityError::Invalid(InvalidTransaction::Call))?
			}

			let encoding = match call {
				Call::accumulate_fees { withdrawal_proof } => withdrawal_proof.encode(),
				Call::withdraw_fees { withdrawal_data } => withdrawal_data.encode(),
				Call::claim_outbound_consensus_delivery_reward { claim } => claim.encode(),
				Call::claim_outbound_request_delivery_reward { claim } => claim.encode(),
				_ => unreachable!(),
			};

			let msg_hash = sp_io::hashing::keccak_256(&encoding).to_vec();

			Ok(ValidTransaction {
				priority: 100,
				requires: vec![],
				provides: vec![msg_hash],
				longevity: TransactionLongevity::MAX,
				propagate: true,
			})
		}
