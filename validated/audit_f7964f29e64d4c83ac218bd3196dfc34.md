### Title
Unchecked payment arithmetic allows an oversized Bitcoin transaction to be signed - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
Medium-severity integer overflow: `SignableTransaction::new` sums attacker-controlled payment amounts and adds the calculated fee using unchecked `u64` arithmetic, allowing the funding check to wrap and pass while embedding the original oversized amount in the transaction. [1](#0-0) [2](#0-1) 

### Finding Description
`SignableTransaction::new` accepts payment amounts as `u64`, checks only that each amount is at least `DUST`, and serializes each amount directly into a `TxOut`. [3](#0-2) [4](#0-3)  It then calculates `payment_sat` with `sum::<u64>()` and evaluates `input_sat < (payment_sat + needed_fee)` without checked addition. [5](#0-4) [6](#0-5)  For a single payment of `u64::MAX`, `payment_sat + needed_fee` wraps to approximately `needed_fee - 1`, so a small input satisfies the check despite the transaction containing a `u64::MAX` output. [7](#0-6)  The malformed transaction is subsequently used to calculate Taproot sighashes and generate threshold signature shares. [8](#0-7) [9](#0-8) 

### Impact Explanation
An unprivileged party who can supply a payment amount can cause the threshold wallet to produce signatures for a transaction the funding check should have rejected. [10](#0-9) [9](#0-8)  The resulting signatures are bound to a serialized transaction whose output value and total output do not correspond to the checked `payment_sat` value, which constitutes signing unintended transaction data. [11](#0-10) [12](#0-11)  While the oversized transaction should be rejected by Bitcoin consensus, the threshold key has still authorized bytes outside the validated economic constraints. [8](#0-7) [7](#0-6) 

### Likelihood Explanation
The attack requires only a single payment amount of `u64::MAX`; no malformed curve encoding, invalid participant index, forged proof, or blockchain-level cooperation is needed. [13](#0-12) [3](#0-2)  The wrapped check can be satisfied by a modest input because `u64::MAX + needed_fee` reduces to a small value in wrapping release arithmetic. [14](#0-13) [6](#0-5)  Likelihood is therefore bounded by whether the caller accepts attacker-controlled `payments`, but the vulnerable path itself is direct and deterministic. [13](#0-12) 

### Recommendation
Use `checked_add` or `try_fold` for `input_sat`, `payment_sat`, and every `payment_sat + needed_fee` or `payment_sat + fee_with_change` calculation, and use `checked_mul` for `fee_per_vbyte * vbytes`. [15](#0-14) [16](#0-15) [17](#0-16)  Also reject any payment or output amount exceeding Bitcoin's maximum-money bound before constructing `TxOut`s, and return a new `TransactionError` for arithmetic overflow rather than allowing a wrap or panic. [4](#0-3)

```rust
// A syntactically constructed funding transaction gives Scanner a ReceivedOutput
// worth only 2_000 sats.
let funding_tx = Transaction {
  version: Version(2),
  lock_time: LockTime::ZERO,
  input: vec![],
  output: vec![TxOut {
    value: Amount::from_sat(2_000),
    script_pubkey: script.clone(),
  }],
};

let input = Scanner::new(group_key)
  .unwrap()
  .scan_transaction(&funding_tx)
  .remove(0);

// payment_sat is u64::MAX. The checked expression
// payment_sat + needed_fee wraps to approximately needed_fee - 1.
let payments = [(script, u64::MAX)];
let crafted =
  SignableTransaction::new(vec![input], &payments, None, None, 1).unwrap();

assert_eq!(crafted.transaction().output[0].value.to_sat(), u64::MAX);

// multisig(...) then signs the malformed transaction's Taproot sighash.
let machine = crafted.multisig(&threshold_keys).unwrap();
let (sign_machine, _) = machine.preprocess(&mut rng);
```

[7](#0-6)  `multisig` creates per-input signing machines only after confirming the supplied prevout script, so the subsequent `sign` operation commits threshold signature shares to that malformed transaction.
