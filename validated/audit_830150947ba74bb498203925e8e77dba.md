## Finding

### Title
CR-CAT and R-CAT wallets are identified/deduplicated by tail hash alone instead of by the full (tail hash, CR/revocation parameters) pair - (File: `chia/wallet/cat_wallet/cr_cat_wallet.py`, `chia/wallet/cat_wallet/r_cat_wallet.py`, `chia/wallet/cat_wallet/cat_wallet.py`)

### Summary
`CRCATWallet.get_or_create_wallet_for_cat` and `RCATWallet.get_or_create_wallet_for_cat` (and the coin-identification path in `CATWallet.identify`) key wallet lookup/deduplication solely on the CAT tail hash (`limitations_program_hash`). For CR-CATs and R-CATs, however, the actual on-chain asset identity is not just the tail hash - it also depends on `authorized_providers`/`proofs_checker` (for CR-CATs) or `hidden_puzzle_hash` (for R-CATs). Because these extra parameters are ignored during lookup, a second CR-CAT/R-CAT "pair" sharing the same tail hash but different providers/proofs-checker/hidden-puzzle-hash silently reuses the first wallet's stored parameters, exactly mirroring the reported class of bug where an oracle/asset mapping keyed by a single token collapses two logically distinct pairs into one.

### Finding Description
`CRCATWallet.get_or_create_wallet_for_cat` only compares `w.get_asset_id() == limitations_program_hash` to decide whether an existing wallet already represents the requested CR-CAT, then returns that wallet unconditionally, discarding the newly supplied `authorized_providers`/`proofs_checker`: [1](#0-0) 

The same pattern exists for `RCATWallet.get_or_create_wallet_for_cat`, which ignores a mismatched `hidden_puzzle_hash` for an existing tail-hash match: [2](#0-1) 

Worse, the earlier coin-identification step in `CATWallet.identify` (used during coin sync when a new CR-CAT coin arrives) performs the same tail-hash-only comparison to decide whether an incoming coin belongs to an already-known CR-CAT wallet, again ignoring `authorized_providers`/`proofs_checker`: [3](#0-2) 

In all three call sites, the "pair" that actually determines the on-chain puzzle/asset identity is `(tail_hash, authorized_providers, proofs_checker)` for CR-CATs or `(tail_hash, hidden_puzzle_hash)` for R-CATs - analogous to the Y2K Finance `tokenToOracle[_token]` bug where the mapping key should have been the pair, not the single token. Just as that bug silently kept the stale oracle for a new pair, this code silently keeps the stale CR/revocation parameters for a new pair sharing the same tail hash, because the check `if tokenToOracle[_token] == address(0)` / `if w.get_asset_id() == limitations_program_hash` only inspects one component of the true identity.

### Impact Explanation
When a wallet later syncs a genuinely distinct CR-CAT coin that happens to share a tail hash with an already-tracked CR-CAT wallet but has different `authorized_providers`/`proofs_checker` (fully attacker-controlled by whoever mints or sends the coin, e.g. an offer counterparty), the coin gets silently attributed to the wrong `CRCATWallet` instance, which stores the old, mismatched provider list/proofs checker in `CRCATInfo`. Any subsequent spend attempt constructed from this stale info will curry the wrong CR parameters, producing spends that do not match the coin's real on-chain puzzle. This is a coin-identity/spend-construction correctness bug that can manifest as: incorrect enforcement of credential restrictions as understood by the wallet (the wallet may believe a coin is restricted to providers/proofs different from what is actually curried on-chain), and failed/invalid spend construction for the affected coin. This falls under the "invalid spend acceptance" / coin-identity confusion category the same way the reported oracle bug produced silently wrong pricing for a new pair.

### Likelihood Explanation
Reaching this requires only that an unprivileged party (offer counterparty, or anyone who can send a CAT/CR-CAT coin to the victim's hinted puzzle hash) mint or forward a CR-CAT/R-CAT coin whose tail hash collides with one the victim wallet already tracks but whose `authorized_providers`/`proofs_checker`/`hidden_puzzle_hash` differ. No special network position, timing, or privileged role is needed - this is purely a client-side wallet bookkeeping defect triggered by ordinary coin receipt/sync, which is the normal, expected way CR-CAT/R-CAT wallets are created (`CATWallet.identify` -> `get_or_create_wallet_for_cat`).

### Recommendation
Key CR-CAT/R-CAT wallet lookup and deduplication on the full asset-identity tuple rather than the tail hash alone:
- For `CRCATWallet.get_or_create_wallet_for_cat` and the `identify` matching logic, compare `(limitations_program_hash, authorized_providers, proofs_checker)` (or a hash of the full outer puzzle driver) before reusing an existing wallet.
- For `RCATWallet.get_or_create_wallet_for_cat`, compare `(limitations_program_hash, hidden_puzzle_hash)`.
- If a genuine tail-hash collision with differing CR/revocation parameters is detected, create a new, distinct wallet instead of silently reusing the existing one.

### Proof of Concept
1. Victim wallet already has a `CRCATWallet` for tail hash `T` with `authorized_providers=[A]`, `proofs_checker=PC1` (created via `CRCATWallet.get_or_create_wallet_for_cat`).
2. An unprivileged counterparty mints/sends a CR-CAT coin also using tail hash `T` but with `authorized_providers=[B]`, `proofs_checker=PC2` (a legitimately different CR-CAT "pair" sharing the tail hash), to a puzzle hash owned by the victim.
3. During wallet sync, `CATWallet.identify` iterates `get_all_wallet_info_entries(wallet_type=WalletType.CRCAT)` and matches solely on `crcat_info.limitations_program_hash == asset_id`, returning the existing wallet id for tail hash `T` regardless of the new coin's actual `[B]`/`PC2` parameters [3](#0-2) .
4. The coin is now tracked under a `CRCATWallet` whose stored `CRCATInfo.authorized_providers`/`proofs_checker` do not match the coin's real curried puzzle parameters, so any spend the wallet constructs for it will use stale/incorrect CR data, diverging from the actual on-chain puzzle for that coin.
