### Title
Permanent escrow lock when the beneficiary's token blocks transfer during `RedeemEscrow`/`RefundEscrow` settlement - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The external report's core broken invariant: a bridge-message handler performs a single, un-guarded external call (`deposit()`) to move custody of bridged funds to a beneficiary, with no fallback path if that call permanently fails, so escrowed value becomes permanently unrecoverable. The same pattern exists in Hyperbridge's `IntentGatewayV2` settlement path: `_withdraw()` in `IntentsBase.sol` unconditionally calls `IERC20(token).safeTransfer(beneficiary, amount)` (or a raw `.call` in the `evm/tron/contracts/apps/IntentGatewayV2.sol` variant) to release escrowed input tokens to a beneficiary named inside a signed cross-chain message, with no catch/fallback and no alternate redemption path.

### Finding Description
`_withdraw()` is the single code path that releases escrowed order inputs, invoked from `onAccept()` for both `RedeemEscrow` (pay the solver who filled the order) and `RefundEscrow` (refund the user on cancellation): [1](#0-0) 

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        _authenticate(incoming.request);
        WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
        return _withdraw(body, kind == RequestKind.RefundEscrow, true);
    }
``` [2](#0-1) 

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    if (finalize) _filled[body.commitment] = beneficiary;
    ...
    uint256 escrowed = _orders[body.commitment][token];
    if (escrowed == 0) revert UnknownOrder();
    _orders[body.commitment][token] = escrowed - amount;
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        IERC20(token).safeTransfer(beneficiary, amount);
    }
}
```

`beneficiary` here is not chosen by the party that will eventually receive it and cannot be changed after the fact: for `RedeemEscrow` it is the solver address selected at fill time on the destination chain; for `RefundEscrow` it is fixed to `order.user`. If the escrowed `token` is an ERC20 with issuer-controlled transfer restrictions (e.g. a centrally blacklistable stablecoin) and the beneficiary address becomes blocked by the token issuer at any point between order placement and settlement delivery, `safeTransfer` reverts every time this message is (re)processed. Because the whole `onAccept` call reverts, the identical scenario recurs on every retry (the host's low-level `.call` retry mechanism in `EvmHost.dispatchIncoming` — see `evm/src/core/EvmHost.sol:794-818` — only helps when the failure is transient; it cannot help when the failure is permanent). There is no code path in `IntentsBase`/`ExtrinsicIntents`/`IntentGatewayV2` that lets governance, the beneficiary, or the original order owner redirect or reclaim escrow once a `WithdrawalRequest` targeting a permanently-blocked beneficiary has been dispatched — the only recovery primitive available (`SweepDust`) sweeps *unescrowed* protocol dust, not tokens still tracked in `_orders[commitment][token]`.

This mirrors the reported bug class exactly: an unguarded external call whose failure mode can be permanent, with no fallback transfer target and no alternate settlement path, leading to funds that are indefinitely stuck in the contract.

### Impact Explanation
Escrowed input tokens for the affected order become permanently locked in the `IntentGatewayV2`/`ExtrinsicIntents` contract: no cancellation route exists once a `RedeemEscrow`/`RefundEscrow` message referencing a permanently-non-transferable beneficiary is in flight, because `_filled[commitment]` is only set on a *successful* `_withdraw` and every retry hits the same beneficiary. This is a loss-of-funds condition for the affected user/solver and, at scale, for any order that happens to name a beneficiary the escrowed token's issuer later restricts — a condition entirely outside Hyperbridge's control but with no defensive fallback in the contract, unlike the WETH-unwrap fallback pattern already implemented for native-token beneficiaries in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` (compare `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:309-324`, which re-wraps and retries via ERC20 transfer if the native push fails).

### Likelihood Explanation
This requires no malicious peer, relayer, prover, or governance actor — only that an order escrows a token with issuer-side transfer restrictions (e.g. USDC-style blacklisting) and that the eventual beneficiary (solver or user) is later restricted by that issuer, which is realistic given intent-gateway inputs are open to arbitrary ERC20 tokens chosen at order placement time. The failure is deterministic and reproducible on every retry attempt once it occurs.

### Recommendation
Add a fallback path in `_withdraw()` (and its `IntentGatewayV2.sol`/tron equivalent) analogous to the native-token WETH re-wrap pattern already used elsewhere in the codebase: wrap the `safeTransfer` in a try/catch (or low-level call check), and on failure route the amount to a recoverable escrow/claim mechanism (e.g. credit a per-beneficiary claimable balance withdrawable to an alternate address, or allow governance/`SweepDust`-style recovery of specifically the stuck `_orders[commitment][token]` entry) rather than leaving the order permanently un-settleable.

### Proof of Concept
1. User places a cross-chain order escrowing `TokenX` (an ERC20 with issuer-controlled blacklist, e.g. USDC-like) as input, per `IntentGatewayV2.placeOrder`.
2. Solver fills the order on the destination chain; destination gateway dispatches a `RedeemEscrow` `WithdrawalRequest` naming the solver as `beneficiary` back to the source chain (`evm/tron/contracts/apps/IntentGatewayV2.sol:620-626`).
3. Before the message is delivered/settled on the source chain, `TokenX`'s issuer blacklists the solver's address (external, out of Hyperbridge's control — analogous to "exchange deposits disabled" in the original report).
4. Host delivers the message; `IntentsBase._withdraw()`/`IntentGatewayV2.withdraw()` calls `IERC20(TokenX).safeTransfer(solver, amount)`, which reverts because the recipient is blacklisted.
5. `onAccept` reverts; `EvmHost.dispatchIncoming` deletes the request receipt to allow retry, but every subsequent retry hits the same reverting transfer — `_orders[commitment][TokenX]` remains non-zero forever, and no other function can move it out, permanently locking the escrowed funds.
