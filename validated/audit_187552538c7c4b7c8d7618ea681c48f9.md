### Title
Cached DKG-confirmation nonces are keyed only by `(b"DkgConfirmer", attempt)` and are not invalidated across sessions/specs, causing Schnorr nonce reuse and validator key-share recovery — (`coordinator/src/tributary/signing_protocol.rs`)

### Summary
`SigningProtocol::preprocess_internal` stores a deterministic preprocess seed in `CachedPreprocesses`, indexed solely by `context = (b"DkgConfirmer", self.attempt)`. The key does not include the tributary genesis, session, validator set, or participant list. When a validator participates in a later DKG confirmation that reuses the same attempt number (attempts restart at low values for every new DKG/session), the stale seed from the prior session is loaded and `AlgorithmMachine::seeded_preprocess` deterministically re-derives the same nonces via `ChaCha20Rng::from_seed`. The validator then produces a Schnorrkel/MuSig signature share over a different `set_keys_message` with an identical nonce — classic nonce reuse that reveals the secret key.

This is the direct Serai analog of the reported bug class: a value cached under an old configuration (`tickLowerLasts` under old tick-spacing; the preprocess seed under the old session/set) is not reset when the surrounding parameters change, so new operations are computed against a mismatched base.

### Finding Description
In `SigningProtocol::preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:100-148), the flow is:

1. `CachedPreprocesses::get(self.txn, &self.context)` — the DB key is only `context.encode()` where `context = (b"DkgConfirmer", self.attempt)` (line 275). No genesis, session index, `spec.set()`, or participants are mixed in.
2. If a cache entry exists, it is decrypted and passed to `AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached))` (line 144-145).
3. `from_cache` → `seeded_preprocess` (crypto/frost/src/sign.rs:121-144) derives all nonces/commitments deterministically: `ChaCha20Rng::from_seed(*seed.0)` then `Commitments::new(&mut rng, ...)` and `preprocess_addendum(&mut rng, ...)`. Same seed → same nonce scalar(s) → same commitment R values.

`DkgConfirmer` is instantiated once per DKG confirmation attempt. `dkg_confirmation_nonces`/`generated_key_pair`/`DkgConfirmed` handling all funnel through `DkgConfirmer::new(key, spec, txn, attempt)` with `attempt` supplied externally (`handle.rs:42`, `handle.rs:57`, `handle.rs:533`). The `attempt` counter is per-(genesis, topic) in `AttemptDb`, but `CachedPreprocesses` has no genesis/namespace in its key (`create_db!` at line 86-90). On the next tributary spec (new session, new genesis, new validator set, new `key_pair`, new `removed` list → different `set_keys_message`), the same `attempt` value hits the stale DB entry and reuses the old nonce seed.

Note that `keys` are rebuilt fresh per call with the current `spec`/`participants` via `musig(musig_context(self.spec.set().into()), ...)` (line 118-121), so the signing set/aggregated key is correct for the new session — only the nonce is stale. The share equation is `s = d_i + b_i·e_i·ρ + c·(aggregated secret share)` with `d_i, e_i` fully seed-derived, so an identical nonce is committed to two different challenges.

### Impact Explanation
An observer (anyone reading public tributary data — the preprocesses and `DkgConfirmed` shares are published on-chain) who sees two confirmation shares from the same validator that reuse the same nonce commitment under different challenges can solve `x = (s1 − s2)/(c1 − c2)` (after accounting for the binding factors, which are themselves deterministic and publicly reconstructible) to recover the validator's MuSig secret share — i.e., its validator signing key contribution. Recovery of a validator's tributary signing key lets an attacker forge that validator's signed tributary transactions (votes, shares, slash reports), compromising the coordinator's root-of-trust MuSig confirmations. The documentation itself states the consequence: "It is explicitly unsafe to reuse nonces across signing sessions" (signing_protocol.rs:25) and "Reuse will enable third-party recovery of your private key share" (crypto/frost/src/sign.rs:85-86). This is secret-key recovery reachable entirely from published data — Critical/High severity.

### Likelihood Explanation
Trigger requires the same coordinator DB to process two DKG confirmations whose `(b"DkgConfirmer", attempt)` contexts collide, i.e., a new session/spec running DKG attempt *n* after a prior session also ran attempt *n*. DKG attempts routinely start at 0/1 and increment on re-attempts (`ReattemptDb::schedule_reattempt`, `AttemptDb::attempt`), so the very first confirmation attempt of every new validator set reuses context attempt 0/1. Whenever validator sets rotate and a new DKG is executed — a normal, governance-driven parameter change, exactly analogous to the tick-spacing change in the report — the stale seed is silently reused. No malicious validator or broken BFT is needed; the re-execution-on-rebuild design (which intentionally regenerates state) combined with a DB-key that omits session identity makes the collision deterministic on every subsequent session.

### Recommendation
Namespace the preprocess cache by everything the nonce must be unique with respect to. Concretely:

- Include `spec.genesis()` (or `spec.set().session` / the full `musig_context`) and the participant list in `context`, e.g. `context = (b"DkgConfirmer", spec.genesis(), attempt, participants_hash)`, so a seed can never be replayed under a different session or set.
- Additionally, delete the cache entry (`CachedPreprocesses::del`) after `share`/`complete` consumes it, enforcing the documented "MUST only be used once" invariant rather than relying on callers never reusing a context.
- Keep the seeded-determinism safety property (needed for re-execution) but bind determinism to the full session identity, not just the attempt counter.

### Proof of Concept
1. Session S: coordinator runs `DkgConfirmer::new(key, spec_S, txn, attempt=1)`. `preprocess()` → `preprocess_internal` → no cache → generates seed `k` via `machine.cache()`, stores `CachedPreprocesses[("DkgConfirmer", 1)] = k XOR enc_key` (line 123-134). Publishes commitments derived from `ChaCha20Rng::from_seed(k)`. Later `share`/`complete` publishes share `s1` over `set_keys_message(set_S, removed_S, key_pair_S)` with challenge `c1`.
2. Session S′ (validator set rotation → new DKG, same DB): `DkgConfirmer::new(key, spec_S′, txn, attempt=1)`. `CachedPreprocesses::get(("DkgConfirmer", 1))` returns `k` → `from_cache` → `seeded_preprocess` regenerates identical nonces `d, e` and identical commitments (line 127-132 of sign.rs). `share_internal` produces share `s2` over the different message `set_keys_message(set_S′, removed_S′, key_pair_S′)` with challenge `c2 ≠ c1` but the same effective nonce `k_nonce = d + b·e`.
3. Attacker solves the linear system: `s1 − s2 = (c1 − c2)·share_secret` (interpolation/MuSig coefficients are public and identical structure), recovering the validator's secret share, hence its tributary signing key.

One caveat I could not fully verify within tool limits: whether `Commitments::new` mixes `original_secret_share` into nonce derivation in a way that would alter the nonce when the secret changes — the coordinator `key` is the same across sessions, so this does not affect the attack; the nonce is still identical across the two sessions because seed and key are unchanged while the message/challenge changes.
