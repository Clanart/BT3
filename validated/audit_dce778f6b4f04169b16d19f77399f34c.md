### Title
Unvalidated backward/forward line-range scan in `findInteractiveDiffRange` can select the wrong diff lines to stage or discard - ([File: app/src/ui/diff/diff-explorer.ts])

### Summary
`findInteractiveDiffRange` (used by the diff view to decide which lines belong to the "interactive" add/delete block a user clicked) scans backward and forward from a clicked line index using `hunk.lines[i]`, relying on the assumption that `hunk.lines` and `hunk.unifiedDiffStart`/`unifiedDiffEnd` are internally consistent with the hunk header produced by `DiffParser`/`expandTextDiffHunk`. That range is then fed into `withRangeSelection`/`formatPatch` (`app/src/lib/patch-formatter.ts`) to build the actual patch applied with `git apply` when staging or discarding changes. Unlike the Solidity report where an unguarded subtraction reverts and locks funds, here the equivalent broken invariant (index consistency between hunk boundaries and line arrays) does not throw — it silently returns a wrong `from`/`to` range, which is then used to build a patch that stages/discards different lines than what is visually presented to the user.

### Finding Description
`diffHunkForIndex` [1](#0-0)  locates a hunk purely by comparing an absolute `index` against `unifiedDiffStart`/`unifiedDiffEnd`, values which are computed by the diff parser and diff-expansion code (`app/src/lib/diff-parser.ts` and `app/src/ui/diff/text-diff-expansion.ts`) from hunk header numbers such as `oldStartLine`/`newLineCount` that originate from `git diff` output of a **fetched/cloned repository's working tree or blob content**. `findInteractiveDiffRange` then does: [2](#0-1) 

The `relativeIndex = index - hunk.unifiedDiffStart` and the subsequent backward/forward loops assume `hunk.lines` is exactly `unifiedDiffEnd - unifiedDiffStart + 1` long and that `hunk.lines[relativeIndex]` exists. This mirrors the `payOff()` bug's core flaw: an arithmetic relationship (`feesUSD <= pnl` in the original; here, `hunk.lines.length === unifiedDiffEnd - unifiedDiffStart + 1`) is assumed but never asserted at the point of use. If a hunk is produced through the hunk-merging path in `mergeDiffHunks`/`expandTextDiffHunk` [3](#0-2)  with any accounting drift between `numberOfNewDiffLines` and the actual concatenated `lines` array (e.g. a crafted diff/file whose expansion path hits the "merge with adjacent" branch with unusual hunk-header line counts), `hunk.lines[relativeIndex]` in `diffLineInfoForIndex` [4](#0-3)  can return `undefined` or a line belonging to a different logical position than the one the user clicked, and `findInteractiveOriginalDiffRange` [5](#0-4)  can map to an unrelated `from`/`to` in the original diff.

Unlike the Solidity report, where the broken invariant causes a `revert` (a *loud* failure that locks funds), this JS/TS path fails *silently*: there is no bounds check or exception — `hunk.lines[i]` for an out-of-range `i` returns `undefined` and `isIncludeableLine()` would throw on `undefined`, OR, if indices merely drift instead of going fully out of range, the wrong `DiffLine` is picked up without any error at all. The resulting range is passed to `DiffSelection.withRangeSelection` and eventually to `formatPatch`/`formatPatchToDiscardChanges` [6](#0-5)  which builds the literal patch text applied via `git apply --cached`.

### Impact Explanation
If the interactive range computation silently drifts, the checkbox/line-selection UI can stage (or discard) a different set of lines than what the user visually selected — i.e., **silent corruption of what the user commits**, which is explicitly a valid impact class for this task. This does not require any local/physical access: it is triggered purely by the content of a diff generated from a cloned/fetched repository's files, which is attacker-controlled content.

### Likelihood Explanation
Likelihood is speculative/medium at best. I could not find a concrete crafted-file/diff proof that forces `hunk.lines.length` to diverge from `unifiedDiffEnd - unifiedDiffStart + 1` — the diff-expansion and diff-parser code appears to keep these values consistent along the paths I reviewed (`getDiffTextFromHunks`, `mergeDiffHunks`, `parseHunk`), and I was not able to fully trace every hunk-expansion edge case (e.g., repeated expansion + merge cycles, dummy-hunk boundary interactions) within the available tool budget. I am not fully confident this is exploitable without deeper testing/fuzzing of `expandTextDiffHunk`'s merge branches.

### Recommendation
- Add explicit bounds/consistency assertions in `diffLineInfoForIndex` (verify `hunk.lines.length === hunk.unifiedDiffEnd - hunk.unifiedDiffStart + 1` and that `relativeIndex` is within `[0, hunk.lines.length)`) and fail closed (return `null`, disabling the interactive selection for that row) rather than silently proceeding.
- Add the same invariant assertion immediately after any hunk mutation in `text-diff-expansion.ts` (`expandTextDiffHunk`, `mergeDiffHunks`) so any drift is caught at the point of construction rather than at the point of use in `diff-explorer.ts`.
- Add a defensive check in `formatPatch`/`formatPatchToDiscardChanges` that the total selected/context line count reconstructed matches the hunk header's `oldLineCount`/`newLineCount` before emitting the patch, throwing rather than silently emitting a patch that doesn't match the hunk header.

### Proof of Concept
I was unable to construct a concrete end-to-end repro (crafted repo/diff) within the available investigation budget that forces the `hunk.lines`/`unifiedDiffStart`/`unifiedDiffEnd` invariant to drift — this would require exercising `expandTextDiffHunk`'s hunk-merge branches with a live diff and stepping through `DiffSelection`/`formatPatch` to confirm a real mismatch between the UI-displayed selection and the emitted patch. Given this, treat this finding as a **plausible but unverified** structural analog rather than a confirmed exploit; a Devin session with full repo/test access would be needed to fuzz `expandTextDiffHunk`/`mergeDiffHunks` and attempt to produce a concrete mismatched patch.

export function diffHunkForIndex(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): DiffHunk | null {
  const hunk = hunks.find(h => {

  })
  return hunk || null
}
