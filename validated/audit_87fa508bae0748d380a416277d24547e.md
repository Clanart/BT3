### Title
Attacker-controlled `ThresholdKeys` bytes count an identity/zero contribution as a real participant, and never bind `secret_share` to `verification_shares` — yielding a fully attacker-chosen `group_key` - (File: crypto/dkg/src/lib.rs)

### Summary
The LooksRare bug is a "zero-value deposit counted as a real entry" flaw: `depositETHIntoMultipleRounds()` increments a slot counter without checking the contributed amount, letting an attacker occupy capacity or force resolution with no stake. The Serai analog lives in `ThresholdKeys::new` / `ThresholdKeys::read` (crypto/dkg/src/lib.rs:349-391, 574-632): the participant set is constructed entirely from attacker-supplied `verification_shares`, with no check that any share is non-identity and no check that `C::generator() * secret_share == verification_shares[params.i()]`. An identity verification share is the literal analog of a 0-ETH deposit — a participant slot that contributes nothing — and because `group_key` is computed by interpolating only the supplied shares, the attacker fully dictates the reported group key.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) deserializes `t`, `n`, `i`, the interpolation method, `secret_share`, and `n` verification shares from untrusted bytes, then calls `ThresholdKeys::new`. `new` enforces only:

- `verification_shares.len() == n` (line 355)
- every participant index `<= n` (line 362)
- `Interpolation::Constant` requires `t == n` (line 369)

It then computes the group key as `sum_{i in 1..=t} verification_shares[i] * interpolation_factor(i, {1..=t})` (lines 376-378). Nothing rejects identity points in `verification_shares` (a 0-contribution participant, directly mirroring the 0-ETH deposit that still occupies a round slot), and nothing verifies the internal consistency of the structure — in particular that `G * secret_share` equals `verification_shares[i]`, or that the shares actually lie on a common degree-`t-1` polynomial.

The same gap exists on the trusted path: `dkg::dealer::key_gen` never lets this happen because it constructs consistent shares, but `musig()` (crypto/dkg/musig/src/lib.rs:116-162) and `GeneratorPromotion::complete` (crypto/dkg/promote/src/lib.rs:120-167) both call `ThresholdKeys::new` with externally-derived verification share maps; `check_keys` in musig dedups by encoding but never rejects the identity point either (musig/src/lib.rs:54-60). A "participant" registering `identity` contributes `binding_factor * identity = identity` — a 0-value slot, exactly the report's bug class.

The code itself acknowledges the danger implicitly: `AlgorithmSignatureMachine::complete` comments "The only known way to cause this ... is to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:492-494) — i.e., the invariant that shares and group key are consistent is assumed but never enforced at the deserialization boundary.

### Impact Explanation
- **Attacker-chosen group key:** since `group_key` is derived purely from attacker-controlled `verification_shares` in the byte stream, an attacker who can get a victim (or downstream consumer of `ThresholdKeys::read`, e.g. via `signing_protocol.rs`'s `musig(...).into()` / keys flowing through coordinator data) to deserialize crafted bytes obtains a `ThresholdKeys` whose `group_key()`/`original_group_key()` is a key whose discrete log the attacker knows (they choose scalars `s_i` and set `verification_shares[i] = G*s_i`). Any funds or trust anchored to `group_key()` — e.g. the Bitcoin `Scanner` built from that key (networks/bitcoin/src/wallet/mod.rs:162-166) — are spendable by the attacker, not the victim. This is strictly worse than the source report's fee-loss/DoS impact.
- **DoS by zero-contribution slot:** an identity verification share makes a participant count toward `n` while contributing nothing; views built over `included` sets containing that participant produce inconsistent secret/verification share pairs, so signing sessions stall or fail blame attribution (the `InternalError("everyone had a valid share yet the signature was still invalid")` path), analogously to the report's "fill rounds with 0 deposits to DoS".
- **Reachability:** `ThresholdKeys::read` and `Commitments::read`/`read_share` are explicitly untrusted-input surfaces; bytes can also reach `musig()`/`GeneratorPromotion::complete` via peer-supplied key maps. No secret or privileged position is required — only control of serialized bytes or of one participant slot.

### Likelihood Explanation
Exploitation requires the attacker to feed crafted bytes to `ThresholdKeys::read` (or to occupy a participant index with an identity public key in a `musig`/promotion flow). The Serai coordinator legitimately transports serialized keys and maps of participant material over its data layer, so the input surface is real; whether any given deployment reads attacker-serialized `ThresholdKeys` determines whether this is High (key theft) or Medium (DoS-only via identity slots). The missing validation is unconditional — no race or environmental condition is needed.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), enforce the missing invariants that the LooksRare fix's "check entries are non-zero" maps onto:

```rust
// Reject zero-contribution participants
for (i, share) in &verification_shares {
  if bool::from(share.is_identity()) {
    Err(DkgError::ZeroParameter { t: params.t(), n: params.n() })?;
  }
}
// Bind the secret share to its claimed verification share
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::InvalidParticipant { n: params.n(), participant: params.i() })?;
}
```

and verify the `n` shares lie on a common degree-`t-1` polynomial (equivalently, that the `1..=t` reconstruction is consistent with every other share under Lagrange interpolation). Apply the same non-identity rejection in `check_keys` in crypto/dkg/musig/src/lib.rs:46-63 so an identity public key cannot occupy a MuSig slot.

### Proof of Concept
```rust
use std::collections::HashMap;
use zeroize::Zeroizing;
use ciphersuite::{Ciphersuite, group::GroupEncoding};
use frost::curve::Ristretto;
use dkg::{Participant, ThresholdParams, ThresholdKeys, Interpolation};

// Crafted "deposit": t = n = 1, but the single verification share is IDENTITY
// (a 0-ETH deposit occupying the only participant slot)
let mut bytes = vec![];
bytes.extend(u32::try_from(<Ristretto as Ciphersuite>::ID.len()).unwrap().to_le_bytes());
bytes.extend(<Ristretto as Ciphersuite>::ID);
bytes.extend(1u16.to_le_bytes()); // t
bytes.extend(1u16.to_le_bytes()); // n
bytes.extend(1u16.to_le_bytes()); // i
bytes.push(1);                    // Interpolation::Lagrange
bytes.extend(<Ristretto as Ciphersuite>::F::ZERO.to_repr().as_ref());        // secret_share = 0
bytes.extend(<Ristretto as Ciphersuite>::G::identity().to_bytes().as_ref()); // verification share = identity

let keys = ThresholdKeys::<Ristretto>::read(&mut bytes.as_slice()).unwrap();
// Accepted: group_key == identity, a 0-value participant counted as real.
assert_eq!(keys.group_key(), <Ristretto as Ciphersuite>::G::identity());

// Stronger variant: choose scalars s_1..=s_n, set verification_shares[i] = G*s_i.
// keys.group_key() is then a key whose discrete log the attacker knows — any
// Scanner / deposit address derived from group_key() credits the attacker.
```

This mirrors the source report exactly: a zero contribution is counted as a genuine entry, and the accounting derived from it (here, `group_key`) becomes attacker-controlled.
