### Title
Security-review bypass via unconditional "reviewed" marking of commits regardless of review outcome - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`, `plugins/security-guidance/hooks/diffstate.py`)

### Summary
The `security-guidance` plugin's commit-review hook records a commit SHA as "reviewed" in `.git/sg-reviewed-shas` unconditionally after attempting the review, regardless of whether the review actually completed or found anything. The push-sweep mechanism then trusts this file to skip re-reviewing commits on `git push`, so any review failure (API error, timeout, LLM error) silently and permanently marks a vulnerable commit as safe, bypassing the plugin's own security guard.

### Finding Description
`handle_commit_review_posttooluse` resolves the commit SHAs from the just-run `git commit` and unconditionally calls `_append_reviewed_shas`, explicitly "regardless of whether findings were emitted": [1](#0-0) 

`_append_reviewed_shas`/`_load_reviewed_shas` persist this append-only log under `.git/sg-reviewed-shas`, and this set is later consulted by the push-sweep to advance the "already reviewed" diff base and skip re-review on push: [2](#0-1) 

Separately, `handle_stop_hook` shows the analogous pattern for the Stop-hook review path: on an API error it calls `restore_unreviewed_stop_state` to correctly re-queue the review, but the commit-review path (above) has no equivalent restoration — a failed or errored LLM call at commit-time (`vulns` being `None`/empty due to exception, timeout, or truncated/malformed response) still results in `_append_reviewed_shas(repo_root, full_shas, vulns_found=len(vulns or []))` being called with `vulns_found=0`, indistinguishable from a genuinely clean review: [3](#0-2) 

This mirrors the Gondi `confirmCollectionFactors` root cause: a caller-influenceable event (a transient failure condition, analogous to submitting zero/already-confirmed values) is accepted into a persistent "confirmed/reviewed" state store without validating that the confirmation actually corresponds to a completed, successful check. Once recorded, the state is never invalidated, so the record permanently short-circuits the intended two-stage validation flow (commit-time review, then push-time sweep).

### Impact Explanation
An attacker who can influence timing or network conditions during a commit (e.g., causing the security-guidance LLM call to time out, hit a rate limit, get an HTTP error, or return a response that fails schema parsing) gets their commit's SHA permanently whitelisted in `.git/sg-reviewed-shas`. The push-sweep — the plugin's last line of defense before code reaches a shared branch — will then skip reviewing that commit on push, silently bypassing the security-guidance plugin's automated vulnerability detection for that code. This is a direct compromise of the project's automated security control (a "tool authorization"/git-automation trust boundary), allowing genuinely vulnerable or malicious code to be committed and pushed without triggering the intended review/warning, with no attacker privilege beyond normal repository write access.

### Likelihood Explanation
No special privileges are required — any user of Claude Code with the security-guidance plugin enabled can trigger this by committing during a period of API unavailability/rate-limiting (which the CHANGELOG confirms happens organically, e.g. "Transient server rate-limit errors ... retried automatically") or by any condition that causes `llm._last_call_claude_http_error` to be set or the agentic/single-shot review to error out before producing `vulns`. Because the marking is unconditional and irreversible (append-only log, no re-review trigger), the bypass is easy to reproduce and persists across sessions and clones that share the same `.git` directory.

### Recommendation
Only append to the reviewed-SHA log when the review provably completed successfully (no API error, no exception, no truncation/parse failure) and returned a definitive result. On any error path, either omit the SHA from `_append_reviewed_shas` entirely or record it with an explicit `unreviewed`/`error` marker that the push-sweep treats as "must re-review," mirroring the `restore_unreviewed_stop_state` pattern already used for the Stop-hook path. Additionally, consider tracking failure reasons in the log format so intermittent failures don't accumulate into permanent false "reviewed" entries.

### Proof of Concept
1. Enable the `security-guidance` plugin with `ENABLE_COMMIT_REVIEW`/`ENABLE_CODE_SECURITY_REVIEW` active.
2. Introduce an obviously vulnerable pattern in a file (e.g., hardcoded secret or `eval` of user input) and stage it.
3. Force the LLM review call to fail during commit — e.g., temporarily block network access to `api.anthropic.com`, or trigger a rate-limit/HTTP error during the commit window — then run `git commit`.
4. Observe that `handle_commit_review_posttooluse` still resolves the commit SHA and calls `_append_reviewed_shas(repo_root, full_shas, vulns_found=0)` per [4](#0-3) , adding the vulnerable commit's SHA to `.git/sg-reviewed-shas`.
5. Restore network access and run `git push`. Confirm via debug logs / `.git/sg-reviewed-shas` contents that the push-sweep (`handle_push_sweep_posttooluse`) treats the vulnerable commit as already covered and does not re-flag it, i.e., the vulnerable code is pushed without any security-guidance warning ever being surfaced.

Note: I was not able to inspect `handle_push_sweep_posttooluse` or `atomic_check_and_mark_warning`/`record_pending_warnings` bodies directly (not returned by the index), so the exact push-sweep skip logic and pattern-warning dedup internals are inferred from the surrounding comments and the `_load_reviewed_shas`/`_append_reviewed_shas` contract; a full session with file access would be needed to confirm push-sweep's exact consumption of this log line-by-line.

def _append_reviewed_shas(repo_root, shas, vulns_found=0):
    """Record that `shas` were reviewed. Best-effort; never raises.

    Uses fcntl.flock for the read-gc-write; appends are O_APPEND-atomic but
    GC needs the lock so concurrent CC sessions in the same clone don't race
    each other's truncation.
    """
    p = _reviewed_shas_path(repo_root)
    if not p or not shas:
        return
    import time as _time
    ts = int(_time.time())
    pv = _PV or 0
    lines = [f"{s}\t{ts}\t{pv}\t{int(vulns_found)}\n" for s in shas]
    try:
        import fcntl
        with open(p, "a+") as f:
            fcntl.flock(f.fileno(), fcntl.LOCK_EX)
            try:
                f.seek(0)
                existing = f.read().splitlines(keepends=True)
                # Dedup by sha (first column) — keep newest, then cap.
                seen = set()
                merged = []
                for ln in (existing + lines)[::-1]:
                    sha = ln.split("\t", 1)[0].strip()
                    if sha and sha not in seen:
                        seen.add(sha)
                        merged.append(ln if ln.endswith("\n") else ln + "\n")
                merged = merged[:_REVIEWED_SHAS_CAP][::-1]
                f.seek(0)
                f.truncate()
                f.writelines(merged)
            finally:
                fcntl.flock(f.fileno(), fcntl.LOCK_UN)
    except (OSError, ImportError):
        # fcntl unavailable (Windows) or write failed — degrade to plain
        # append; cap enforcement happens on the next locked write.
        try:
            with open(p, "a") as f:
                f.writelines(lines)
        except OSError:
            pass
