### Title
`SignableTransaction` omits the `OP_RETURN` data output when calculating weight, vbytes, and fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to `StableOracleDAI` assuming the wrong scale for an oracle value, `SignableTransaction::new` computes the transaction's weight, virtual size, and required fee from a transaction template that **excludes the `OP_RETURN` data output**, even though that output is included in the final transaction. The recorded `needed_fee` and the minimum-relay-fee check therefore both assume a smaller transaction than the one actually produced.

### Finding Description
In `SignableTransaction::new`, when `data` is specified the `OP_RETURN` output is pushed onto `tx_outs` first (`send.rs:194-202`). Immediately afterwards, the fee computation builds a *separate* weight-estimation transaction via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (`send.rs:204`), which reconstructs outputs **only from `payments`** (`send.rs:85-93`) and never includes the data output. The same omission occurs in the change-output path (`send.rs:225-226`).

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is computed for a transaction that is up to ~90+ vbytes smaller than the real one (80 bytes of data plus output/opcode overhead).
- The `TooLowFee` check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (`send.rs:211`) is evaluated against the under-counted `vbytes`. A caller passing `fee_per_vbyte = 1` passes the check, yet the final transaction's effective rate is `needed_fee / real_vbytes < 1 sat/vB` — below the 1000 sat/kilo-vbyte minimum relay fee — so the signed transaction may be rejected by the network.
- The `MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) is likewise applied to a weight that excludes the data output.

### Impact Explanation
Any transaction built with `data != None` pays a strictly lower fee rate than the caller requested — a direct parallel to the oracle's mis-scaled price producing a mis-scaled result. In the worst case the signed transaction's actual fee rate falls below the default minimum relay fee and cannot propagate, stalling the threshold spend after the FROST ceremony has already run. The miscalculation is silent: `needed_fee()` reports a value inconsistent with the transaction that `complete()` produces.

### Likelihood Explanation
The bug triggers deterministically whenever `SignableTransaction::new` is called with `Some(data)`. Reachability by an unprivileged on-chain party is limited — the `data` parameter is caller-supplied, and Serai's own processor (`processor/src/networks/bitcoin.rs`) passes `None` — so the practical exposure is integrators who attach `OP_RETURN` data. Within `bitcoin-serai` itself, the miscalculation is unconditional for that input path.

### Recommendation
Include the data output in the weight/vbyte estimation. Either build the estimation transaction from the final `tx_outs` (payments + OP_RETURN + optional change), or pass `data` into `calculate_weight_vbytes` and append the `OP_RETURN` output there before calling `tx.weight()`.

### Proof of Concept
```rust
// In SignableTransaction::new (send.rs:194-211):
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: op_return(data) }); // in final tx
}
let (_, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None); // data omitted
let needed_fee = fee_per_vbyte * vbytes;
// needed_fee / actual_vbytes(signed tx) < fee_per_vbyte, and can be < 1 sat/vB
// while still passing the DEFAULT_MIN_RELAY_TX_FEE check computed on `vbytes`
```
