`GnosisUniswapV2Interface.swapETHForExactTokens` reports `amounts[0] = msg.value` instead of actual amount needed, causing `IntentGatewayV2.placeOrder` to skip native-token refunds and trap surplus WXDAI - (File: `evm/src/utils/uniswapv2/GnosisUniswapV2Wrapper.sol`)

### Summary
On Gnosis, `IntentGatewayV2.placeOrder` swaps native token for `order.fees` worth of `feeToken` through the configured `uniswapV2Router`, which is `GnosisUniswapV2Interface` (deployed and wired into `HostParams.uniswapV2`/`UNISWAP_V2` config by `evm/script/DeployGnosisWrapper.s.sol`). Unlike the real `IUniswapV2Router02.swapETHForExactTokens` contract, `GnosisUniswapV2Interface.swapETHForExactTokens` wraps the *entire* `msg.value` into WXDAI, sends the full amount to the caller, and returns `out[0] = msg.value` — not the amount actually needed to cover `amountOut` (`order.fees`). This breaks `IntentGatewayV2`'s bookkeeping invariant that `amounts[0]` represents the native value consumed by the swap.

### Finding Description
`GnosisUniswapV2Interface.swapETHForExactTokens`: [1](#0-0) 

only rejects the call if `amountOut > msg.value`; otherwise it wraps 100% of `msg.value` and reports `out[0] = msg.value`, regardless of `amountOut`.

`IntentGatewayV2.placeOrder` treats the router's return value as the actual amount spent and derives the native-token refund from it: [2](#0-1) 

Here `msgValue` at the swap-call site is the *entire remaining* native value the caller sent (after any native `order.inputs` legs are deducted), not bounded to `order.fees`. On real Uniswap V2 routers (and the `UniV3`/`UniV4` wrappers used on other chains), the router internally refunds unused ETH back to the caller and returns only the actually-spent amount in `amounts[0]`, so `msgValue -= amounts[0]` correctly reflects the leftover that still needs to be refunded to the end user. The Gnosis wrapper does neither: it consumes all of `msgValue`, gives the *full* amount back as WXDAI (not just `order.fees` worth), and reports `amounts[0] == msgValue`, so the subtraction always yields `0`. The refund branch `if (msgValue > 0)` never fires, even though only `order.fees` was actually needed and credited to `_orders[commitment][TRANSACTION_FEES]`.

The result: any surplus between `msgValue` sent for the fee swap and `order.fees` is converted into WXDAI held by `IntentGatewayV2` but never credited to `_orders[commitment][...]` for any token, and never refunded to the caller as native token. This exactly matches the scenario the SDK itself relies on for slippage buffers, as shown by the existing test that sends 5 ether expecting a large refund of unused ETH: [3](#0-2) 

That refund behavior works correctly against a real router (which internally refunds unused ETH), but is silently broken specifically when `uniswapV2Router` resolves to `GnosisUniswapV2Interface`, i.e. in the production Gnosis deployment path: [4](#0-3) 

### Impact Explanation
Any unprivileged user calling `placeOrder` on the Gnosis-configured `IntentGatewayV2` with `msgValue` (the residual native value after input-token legs) greater than `order.fees` will have the entire surplus wrapped into WXDAI and stranded inside `IntentGatewayV2`, uncredited to any `_orders[commitment][...]` slot and not refunded in native token. This is a real, unaccounted asset-movement/escrow-accounting break: funds leave the caller's control with no path back to them and no recorded ownership inside the gateway's accounting, i.e. the "only `order.fees` worth of native token is escrowed" invariant is violated and native-refund accounting is corrupted. Because the SDK/relayer flow for other chains legitimately sends a slippage buffer above the exact fee (as codified in the gateway's own refund tests), this is not a purely user-error edge case but a realistic operational path on Gnosis specifically, caused by the wrapper's non-conformance to the `IUniswapV2Router02` semantics the gateway assumes.

### Likelihood Explanation
High on Gnosis deployments whenever a caller (user or relayer/SDK acting on the user's behalf) sends `msg.value` above the minimum required for `order.fees` — which is the expected/standard usage pattern elsewhere in the codebase (buffer + auto-refund). No privileged access, malicious relayer, or forged proof is required; it is triggered purely by normal `placeOrder` calls with any excess in `msgValue` earmarked for the fee swap.

### Recommendation
Make `GnosisUniswapV2Interface.swapETHForExactTokens` behave like a real V2 router with respect to the caller-facing contract: only consume `amountOut` worth of `msg.value`, refund the excess `msg.value` back to `msg.sender` in native token, and return `out[0] = amountOut` (the amount actually spent), not `msg.value`. Alternatively, if the Gnosis wrapper is intentionally "wrap-only" and expects exact-value calls, `IntentGatewayV2.placeOrder` must not pass the entire remaining `msgValue` to `swapETHForExactTokens` on chains using this wrapper — it should cap the value sent to `order.fees` (since 1 xDAI == 1 WXDAI, no slippage buffer is needed) and treat any additional `msgValue` as refundable before the swap call, rather than relying on `amounts[0]` for correctness.

2. User calls `placeOrder{value: 5 ether}(order, graffiti)` where `order.fees = 1 ether` (or any amount `< msgValue`) and no native `order.inputs`.

4. `GnosisUniswapV2Interface.swapETHForExactTokens` wraps the full 5 ether into WXDAI, sends 5 WXDAI to `IntentGatewayV2`, and returns `amounts[0] = 5 ether`.
5. `msgValue -= amounts[0]` → `0`; `_orders[commitment][TRANSACTION_FEES] = 1 ether` (only); no native refund is issued.
