### Title
Stale line-selection indices re-applied against a freshly re-fetched diff can silently corrupt partial commits - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex` re-fetches the working directory diff at staging time and blindly re-applies the user's previously-computed `DiffSelection` line indices against it, then applies the resulting patch with `git apply --unidiff-zero`, which disables the context-line matching that would normally catch a mismatched/shifted diff. This mirrors the bug class in the report: a security/intent decision ("these are the exact lines the user approved for commit") is validated against one snapshot of state, but the operation that actually executes is performed against a different, later snapshot of the same externally-mutable resource (the working tree file), with no invariant enforced that the two match.

### Finding Description
The commit flow captures a `DiffSelection` (line-index bitmap) from a diff rendered earlier in the UI (via `getWorkingDirectoryDiff`, `app/src/lib/git/diff.ts:342-401`) when the user picks which lines to stage. When the commit is actually executed, `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) calls `applyPatchToIndex` for every partially-selected file, which does: [1](#0-0) 

Note that `diff` is re-fetched fresh from disk right here, not the diff object that was originally shown to the user and against which `file.selection` was built. `formatPatch` then walks the *new* diff's hunks and asks the *old* selection object whether each line's absolute index is selected: [2](#0-1) 

`DiffSelection.isSelected` only knows about integer line indices — it has no way to detect that the hunk layout, line count, or line offsets it was computed against have changed. If the on-disk file content changes between the moment the user's selection was captured and the moment `applyPatchToIndex` runs (any window during which the user reviews the diff, types a commit message, then clicks "Commit"), the newly-fetched diff can have a different hunk structure (shifted line numbers, merged/split hunks, altered context) than the one the selection indices were derived from. The stale indices are then applied to the wrong lines of the new diff.

Compounding this, the patch is applied with `--unidiff-zero`: [3](#0-2) 

`--unidiff-zero` tells `git apply` to accept hunks with zero lines of context, which is precisely the setting that removes `git apply`'s built-in safety net of verifying that the surrounding context still matches the target file. In other words, the code has explicitly disabled the one mechanism that would normally catch a diff/selection mismatch and reject the patch — so a shifted selection is more likely to *apply successfully* (and be committed) rather than fail loudly.

### Impact Explanation
This produces "silent corruption of what the user commits," which is explicitly in-scope per the task's valid-impact list. If a malicious/attacker-influenced repository ships tooling that runs during the window between diff display and commit — e.g. an npm/husky/pre-commit-style hook, a build watcher, a devcontainer task, or an editor/format-on-save integration triggered by files inside the cloned repository — it can rewrite tracked file content on disk. The user, having reviewed and selected specific lines in the Desktop UI, ends up committing (and potentially pushing) different content than what they approved, without any error being surfaced, because the stale index / no-context-check combination allows the mismatched patch to apply cleanly.

### Likelihood Explanation
The window between selection and staging is normally short but real (composing a commit message, waiting on hooks, etc.), and Desktop already accounts for a similar race in the codebase's own comments (`update-index.ts:131-149` explicitly discusses races between staged renames and recreated files), showing the team is aware such races exist for this exact commit path. The precondition — the diff shown to the user differing from the diff fetched at staging time — does not require local/physical access, admin rights, or social engineering; it only requires a git-tracked automation surface controlled by the cloned repository (or any concurrent tool operating on the working tree) to fire in that window.

### Recommendation
Do not re-fetch the diff inside `applyPatchToIndex`; instead, thread through and reuse the exact diff object the `DiffSelection` was computed against (or re-validate that the freshly fetched diff is structurally identical to the one used to build the selection before applying it). Additionally, avoid `--unidiff-zero` for partial-commit patch application (or supplement it with an explicit content/hash check of the file before/after diff generation) so that a stale-selection/diff mismatch causes `git apply` to fail rather than silently apply against unintended lines.

### Proof of Concept
1. Open a repository in Desktop, modify a tracked file so it has multiple hunks, and open the Changes view so `getWorkingDirectoryDiff` is loaded and rendered.
2. Select only specific lines for the commit (creating a `DiffSelection` keyed to absolute line indices of the currently displayed diff): [4](#0-3) 
3. Before clicking "Commit," have any repo-driven process (e.g., a task runner, formatter, or file watcher started when the repository was opened/checked out) modify the same file so the hunk boundaries/line offsets shift.
4. Click "Commit." `stageFiles` → `applyPatchToIndex` re-fetches the diff (now different) and calls `formatPatch(file, diff)` using the stale `file.selection` indices: [5](#0-4)  The resulting patch, applied with `--unidiff-zero` (no context validation), stages/commits content different from what was reviewed and explicitly selected in the UI, with no error shown to the user.
