### Title
`rewards()` view method on the Distribution precompile accepts msg.value without a non-payable guard, permanently stranding attacker-sent funds - ([File: precompiles/distribution/distribution.go])

### Summary
The Distribution precompile (`0x0000000000000000000000000000000000001007`) validates that most state-mutating methods reject non-zero `value` via `pcommon.ValidateNonPayable(value)` before proceeding, but the `RewardsMethod` view call is dispatched without any such check. [1](#0-0)  A test-suite comment explicitly documents this as a known guard quirk: `rewards()` is "the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)". [2](#0-1) 

### Finding Description
Every other transaction method on the Distribution precompile (`SetWithdrawAddressMethod`, `WithdrawDelegationRewardsMethod`, `WithdrawValidatorCommissionMethod`, etc.) either calls `pcommon.ValidateNonPayable(value)` to reject any attached ETH/usei value, or explicitly consumes the value via `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` and refunds it back to the payer. [3](#0-2) [4](#0-3) 

`RewardsMethod`, however, is dispatched directly to `p.rewards(ctx, method, args)` with no value validation and no refund path. [5](#0-4)  This is analogous to the reported `StaticAttester.sol` bug class: the contract has no enforcement that `value == 0`, and no mechanism exists to reclaim any value that is sent along with the call. Because the low-level EVM `CALL` semantics transfer the `value` from the caller's balance into the precompile's associated account balance before the precompile logic executes (the same mechanism used by `HandlePaymentUsei` to explicitly refund value in every other method), any usei/wei sent alongside a `rewards()` call is credited to the precompile's module account and never returned, since the view path performs no `SendCoins`/`SendCoinsAndWei` refund back to the caller.

### Impact Explanation
Funds sent with a `rewards()` call become permanently stuck in the distribution module account with no code path to reclaim them — this is a permanent freezing of the sender's funds, matching the "permanent freezing" impact criterion. Unlike the original `StaticAttester` report (informational/low severity because it required a payable resolver), this is directly reachable by any unprivileged EVM caller/contract that calls the precompile's `rewards()` view function with non-zero `msg.value`, with no privileged actor or unusual configuration required.

### Likelihood Explanation
Likelihood is high: this requires only a single EVM transaction/contract call to the well-known precompile address `0x1007` invoking `rewards(...)` with `value > 0`. No special permissions, delegation state, or validator cooperation is needed. The bug is a straightforward omission (missing `pcommon.ValidateNonPayable` check) that is already acknowledged internally by the test comment as a known quirk, but the test suite explicitly skips validating it, leaving the path unguarded in production code.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check (or a value-refund step matching the pattern used elsewhere in the same file) at the top of the `RewardsMethod` case in `Execute`, consistent with `ValidatorOutstandingRewardsMethod`, `ValidatorCommissionMethod`, and other view methods, so that any non-zero value sent to `rewards()` is rejected before precompile logic runs.

### Proof of Concept
1. From an EVM account, call the Distribution precompile at `0x0000000000000000000000000000000000001007` via `rewards(address delegator)` (or the equivalent view selector), attaching a nonzero `value` (e.g. `value: 1e18`).
2. Observe the call succeeds and returns normally (no `ValidateNonPayable` revert), unlike calls to `withdrawValidatorCommission` or other guarded methods with the same nonzero value, which revert with `"sending funds to a non-payable function"`. [6](#0-5) 
3. Check the caller's EVM/bank balance after the call: the attached value has been deducted and is not present in the caller's balance, nor is there any subsequent transaction able to recover it, since `rewards()` never issues a refund `SendCoins` call as the payable transaction methods do.

func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
	if hooks != nil {
		newCtx := ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
		if hooks.OnEnter != nil {
			hooks.OnEnter(depth+1, byte(vm.CALL), evmKeeper.GetEVMAddressOrDefault(newCtx, precompileAddr), evmKeeper.GetEVMAddressOrDefault(newCtx, payer), []byte{}, GetRemainingGas(newCtx, evmKeeper), value)
		}
		if hooks.OnExit != nil {
			hooks.OnExit(depth+1, []byte{}, 0, nil, false)
		}
	}
	return coin, nil
}
