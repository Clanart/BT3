## Title
Conflict-hunk boundary misdetection in Copilot merge-conflict resolution lets a crafted file silently corrupt what the AI merges into the user's commit — ([File: app/src/lib/copilot-conflict-context.ts])

## Summary
Reducing the external report to its core: a value is computed by one code path (`truncatedAmount` sent to L1) while accounting is recorded against a *different* value (the original, un-truncated amount), and the mismatch is never detected or reconciled, silently corrupting protocol state. The closest deterministic analog in this Desktop codebase is in the AI merge-conflict resolution feature, where the parser that extracts "ours"/"theirs" conflict content (`extractConflictHunks`) can misidentify hunk boundaries when file content coincidentally matches the conflict-separator pattern, feeding the AI model incorrect data that is then trusted verbatim and spliced back into the user's file without any cross-check.

## Finding Description
`extractConflictHunks` (app/src/lib/copilot-conflict-context.ts:179-279) parses a conflicted file to build the `oursContent`/`theirsContent`/`baseContent` sent to Copilot:

```
199|    i = oursStart
200|    // Collect ours content
201|    while (i < lines.length) {
202|      if (baseMarker.test(lines[i])) { hasBase = true; i++; break }
203|      if (separatorMarker.test(lines[i])) { i++; break }
204|      oursLines.push(lines[i]); i++
205|    }
``` [1](#0-0) 

`separatorMarker` is `/^={7}$/` — any line that is *exactly* seven `=` characters. This regex is applied blindly while collecting "ours" content: it does not verify that this candidate separator is actually followed later by a well-formed `>>>>>>>` closer before treating it as authoritative, and it does not distinguish a genuine git-inserted separator from a coincidental line of exactly seven equals signs that already existed in the user's file (e.g. reStructuredText section underlines, ASCII banners, or changelog dividers that conventionally use a run of `=`). If such a line appears inside the true "ours" region of a real conflict block, `extractConflictHunks` truncates `oursContent` early and misclassifies the remaining genuine "ours" lines as `theirsContent`.

This corrupted content is what gets rendered into the prompt sent to the model:
```
571|      parts.push('Ours (current branch):')
572|      parts.push(makeFencedBlock(hunk.oursContent, lang))
...
581|      parts.push('Theirs (incoming branch):')
582|      parts.push(makeFencedBlock(hunk.theirsContent, lang))
``` [2](#0-1) 

Meanwhile, the actual splice performed by `reassembleResolvedFile` operates only on the outer `<<<<<<<` … `>>>>>>>` boundary and replaces that whole span with the model's `resolvedContent`, trusting it verbatim:
```
584|      // Splice in the resolved content for this hunk
585|      if (hunkIndex < hunkResolutions.length) {
586|        const resolved = hunkResolutions[hunkIndex].resolvedContent
587|        if (resolved.length > 0) {
588|          resultLines.push(...resolved.split(/\r?\n/))
589|        }
590|      }
``` [3](#0-2) 

The existing guard in `reassembleResolvedFile` only protects against a missing `=======`/`>>>>>>>` pair (`if (!hasSeparator || closingIndex === -1)`), which does not catch this case — a well-formed closing marker still exists, so the block is treated as legitimate; the corruption is entirely in what content was *labeled* as "ours" vs "theirs" before ever reaching the model. Nothing in `validateResolutionPaths` (app/src/lib/copilot-conflict-resolution.ts:473-521) re-derives or cross-checks the semantic content of a hunk — it only checks hunk *counts* per file, which remain unaffected since the outer `<<<<<<<`/`>>>>>>>` span is still found once.

## Impact Explanation
An attacker who controls a fetched/cloned branch (a pull request, or any remote a user merges/rebases against) can craft a file whose current-branch content includes a line of exactly seven `=` characters positioned inside what will become the "ours" region of a conflict. When the user runs Copilot conflict resolution, the model is shown swapped/truncated "ours" and "theirs" content and produces a resolution based on that false premise. The dialog's "reasoning" text will describe an incorrect narrative ("kept ours, dropped theirs" when the reverse actually happened), giving the user no visible signal that context was corrupted, and the wrong merge is spliced into the file and can be committed/pushed — a silent corruption of what the user actually commits, matching the report's "silent corruption of what the user commits or pushes" impact class.

## Likelihood Explanation
This requires: (1) a real conflict to occur against attacker-influenced content, and (2) the user invoking the Copilot conflict-resolution feature. Unlike the original financial-truncation bug, which is 100% deterministic, this is a parsing flaw that produces bad *input* to a probabilistic model — the model may still produce a correct merge despite corrupted labels, so actual downstream corruption is not guaranteed on every trigger. The trigger condition (a line of exactly seven `=` characters inside a real conflict's "ours" region) is a real and unforced pattern (RST headers, banners, changelog dividers) rather than a contrived one, but it is narrower than a universally-reachable path.

## Recommendation
- In `extractConflictHunks`, require that a candidate `=======` (or `|||||||`) line be validated by first confirming a subsequent `>>>>>>>` line exists as the block's true closer (i.e. parse ours/base/theirs sections using the same "look ahead for closing marker" strategy already used defensively in `reassembleResolvedFile`, rather than breaking eagerly on the first regex match).
- Make `reassembleResolvedFile` and `extractConflictHunks` share a single boundary-detection routine so the two independently-implemented parsers cannot disagree on what constitutes "ours"/"separator"/"theirs" for the same block.
- Optionally, surface a warning in the resolution dialog when a hunk's "ours"/"theirs" content itself contains lines matching the conflict-marker regexes, since this is inherently ambiguous input.

## Proof of Concept
1. Attacker submits a branch/PR that modifies a `.rst` (or similarly formatted) file such that the current branch's changed region contains a standalone line of exactly `=======` (7 characters) — e.g., a section underline whose title is 7 characters long, sitting inside the hunk that will conflict.
2. User attempts to merge/rebase this branch, hits a conflict on that file, and invokes Copilot conflict resolution.
3. `extractConflictHunks` (app/src/lib/copilot-conflict-context.ts:199-214) stops collecting `oursContent` at the coincidental `=======` line and starts collecting the remaining true "ours" lines into `theirsContent` instead.
4. The prompt sent to the model (via `formatConflictContextForPrompt`) shows the model factually swapped "ours"/"theirs" content for this hunk.
5. The model's `resolvedContent` for that hunk — generated from the wrong premise — is spliced verbatim into the file by `reassembleResolvedFile` (app/src/lib/copilot-conflict-resolution.ts:584-590), with no check that reconciles the mismatch, and can be committed/pushed by the user believing the reasoning text (which itself echoes the false ours/theirs framing).
