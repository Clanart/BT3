### Title
Wildcard `with-ft` allowance grants the full allowance amount independently to every fungible token instead of one shared budget - ([File: clarity/src/vm/functions/post_conditions.rs])

### Summary
The Clarity `restrict-assets?`/`as-contract?` allowance mechanism lets a contract author bound how much of an asset a nested expression may move with a `with-ft` allowance. When the special token name `"*"` is used, the documentation states the allowance "applies to **all** FTs defined in `contract-id`" — i.e., a single shared budget across every fungible token of that contract. The implementation in `check_allowances` instead re-checks each distinct fungible token's moved amount against the *same* wildcard allowance value independently, without ever decrementing/sharing the budget across tokens, so the effective outflow permitted is `allowance.amount × (number of distinct FTs moved)` rather than `allowance.amount` total.

### Finding Description
`check_allowances` in `clarity/src/vm/functions/post_conditions.rs` builds, for every fungible-token asset moved, a `merged` list combining exact-match `Ft` allowance entries and wildcard (`asset_name == "*"`) entries for the same contract: [1](#0-0) 

For each entry in `merged` it does `if *amount_moved > allowance { record_violation(...) }` — a per-asset, per-allowance comparison. There is no bookkeeping that sums the amounts moved for multiple *distinct* fungible tokens that are all covered by the same wildcard allowance entry. The docs describe the wildcard semantics as a combined cap across all FTs in the contract: [2](#0-1) 

Existing tests only ever exercise a single fungible-token asset (`stackaroo`) with wildcard allowances, e.g.: [3](#0-2) [4](#0-3) 

None of them cover a contract that defines two or more fungible tokens and moves more than one of them under a single wildcard allowance, which is exactly the scenario where the shared-budget semantic breaks: each token's outflow is validated against the full allowance amount in isolation, so the combined outflow can be an arbitrary multiple of the stated cap.

This mirrors the structural class of bug in the external report — a mismatch between the amount actually permitted/needed and the amount the code enforces/reserves, caused by treating a single declared budget as if it applied per-item rather than in aggregate. Here it results in the post-condition/allowance guarantee being escaped rather than a revert.

### Impact Explanation
This breaks the guarantee `restrict-assets?`/`as-contract?` is meant to provide: "no more than the declared allowance amount of an asset moves out of the protected principal." A contract author (or a wallet enforcing tx-level post-conditions/allowances) relying on `(with-ft contract "*" amount)` to bound total fungible-token exposure to `amount` can, in practice, have `amount * N` moved out, where `N` is the number of distinct FTs defined by `contract-id` that get transferred inside the protected scope. This is an asset moving past its declared post-conditions/allowance, which is explicitly a Critical/High-impact class.

### Likelihood Explanation
This is reachable by any unprivileged caller who invokes a contract-call guarded with a wildcard `with-ft` allowance against a contract (which may itself be attacker-authored, e.g. a token pool exposing multiple `define-fungible-token`s) that transfers more than one distinct fungible token within the `restrict-assets?`/`as-contract?` scope. No miner, signer, or admin privilege is required — only a transaction whose Clarity code exercises this pattern, which is a normal usage of the allowance feature as documented.

### Recommendation
In `check_allowances`, when checking FT movements, wildcard allowance entries must track a running consumed total across every distinct fungible-token asset they cover (per allowance index), and each additional asset's `amount_moved` should be checked against the *remaining* budget of that wildcard entry, not the full original amount. Concretely, replace the independent `if *amount_moved > allowance` check with a per-allowance-index running total keyed by `index`, decrementing available allowance as each qualifying asset's movement is accounted for, mirroring how exact-match allowances are intended to behave when reused (see existing "multiple allowances" tests) but extended across the distinct assets a single wildcard entry covers.

### Proof of Concept
```clarity
(define-fungible-token stackaroo)
(define-fungible-token sidekick)
(ft-mint? stackaroo u200 tx-sender)
(ft-mint? sidekick u200 tx-sender)
(let ((recipient 'SP000000000000000000002Q6VF78))
  (restrict-assets? tx-sender ((with-ft current-contract "*" u100))
    (begin
      (try! (ft-transfer? stackaroo u100 tx-sender recipient))
      (try! (ft-transfer? sidekick u100 tx-sender recipient))
    )
  )
)
```
Per the documented semantics ("the allowance applies to all FTs defined in contract-id"), the declared budget of `u100` should cap the *combined* outflow of `stackaroo` + `sidekick`, so this should fail after the first transfer already exhausts the shared allowance. With the current implementation, both `ft-transfer?` calls are checked independently against the same `u100` ceiling in `check_allowances` (`clarity/src/vm/functions/post_conditions.rs:621-624`), so both pass and the code returns `(ok true)`, having moved `u200` total fungible tokens under a `u100` allowance — double the declared cap.
