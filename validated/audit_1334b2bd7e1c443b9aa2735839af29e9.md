## Finding: Diff-selection line indices are not consistently mapped back to the original (unexpanded) diff before being persisted, allowing partial commits/discards to apply to the wrong lines [1](#0-0) 

### Title
Silent corruption of partially-committed/discarded content via unmapped diff-line indices after hunk expansion — (File: `app/src/ui/diff/side-by-side-diff.tsx`)

### Summary
GitHub Desktop lets users expand collapsed diff context ("Show more lines") which re-numbers every subsequent hunk's line indices (`unifiedDiffStart`/`unifiedDiffEnd`), and lets users select individual lines for partial staging or discarding by dragging the mouse over the gutter. The line indices recorded by mouse-drag selection are taken directly from the (possibly expanded) on-screen diff, but the `DiffSelection` object that is later consulted to build the actual `git apply` patch is evaluated against a **freshly re-fetched, unexpanded** diff. Nothing constrains these two coordinate spaces to match, so a selection made after expanding a hunk can be interpreted against different lines than the ones the user actually selected — exactly the "missing constraint linking what was read (displayed/selected) to what is written (committed/discarded)" pattern from the report.

### Finding Description
When a hunk is expanded, `expandTextDiffHunk` rewrites the hunk list and shifts every downstream hunk's `unifiedDiffStart`/`unifiedDiffEnd` by the number of newly inserted context lines: [2](#0-1) 

To compensate, the codebase provides `getLineInOriginalDiff`/`findInteractiveOriginalDiffRange`, which translate a line index in the *current* (possibly expanded) diff back to the index it had in the *original* diff, using each `DiffLine.originalLineNumber`: [3](#0-2) 

The hunk-click ("stage whole hunk") handler correctly uses this remapping before updating the selection: [4](#0-3) 

However, the mouse-drag line-selection path does **not** go through this remapping. `onStartSelection`/`onUpdateSelection` record `diffLineNumber` values taken straight from the currently rendered (possibly expanded) rows, and `onEndSelection` applies them directly to the `DiffSelection` with no translation back to the original diff's coordinate space: [5](#0-4) 

That `DiffSelection` is later consulted purely by numeric line index in `formatPatch`, which is run against a diff obtained by a brand-new, unexpanded `git diff` call at commit time (not the expanded diff the user was looking at): [6](#0-5) [7](#0-6) 

The same unmapped index is also used for discarding lines via `formatPatchToDiscardChanges` → `discardChangesFromSelection`, which runs `git apply` against the working tree: [8](#0-7) 

There is no assertion anywhere that `DiffSelection`'s line indices are always expressed in "original diff" coordinates; `onClickHunk` enforces that invariant by convention, but `onEndSelection` breaks it silently.

### Impact Explanation
If a user expands a hunk (to see more context, which is a normal and encouraged workflow shown in the diff view) and then drag-selects a set of lines to stage or discard, the stored `DiffSelection` indices are offset from what `applyPatchToIndex`/`discardChangesFromSelection` expect, because those functions rebuild the diff from scratch (unexpanded) at commit time. Depending on the offset, the generated patch can:
- Stage lines the user never selected (including unrelated content from a malicious or unexpected diff into the commit), or
- Discard/revert lines the user never chose to discard, silently destroying working-tree changes, or
- Simply desync the "hunk"/context boundary so a partial commit contains a different subset of changes than what was shown as selected on screen.

This is a silent corruption of what the user commits or discards — a valid impact category per the task's scope — because the UI shows one thing selected while a materially different set of lines is written to the index/tree, and there is no server or git-level check that would catch the mismatch (the generated patch is syntactically valid, `git apply` will happily apply it).

### Likelihood Explanation
Hunk expansion ("Show N more lines") is a common, prominently exposed UI affordance in the diff viewer, and mouse-drag multi-line selection is the default way most users select more than one line for partial commits (as opposed to clicking a single line or the whole-hunk checkbox, which goes through the correct/original-diff path). Any file with more than one hunk and a user who expands context before selecting several lines is at risk, requiring no adversarial repository content — it is triggered purely by ordinary UI interaction sequencing, which increases the likelihood relative to attack-requiring bugs, though it is a logic bug rather than an attacker-controlled data corruption per se.

### Recommendation
Route `onStartSelection`/`onUpdateSelection`/`onEndSelection` through the same original-diff mapping used by `onClickHunk` (`getLineInOriginalDiff`/`findInteractiveOriginalDiffRange`) before calling `DiffSelection.withLineSelection`/`withRangeSelection`, so that all paths which mutate `DiffSelection` are guaranteed to operate in the same "original diff" coordinate space that `formatPatch`/`formatPatchToDiscardChanges` assume. Alternatively, add an invariant/assertion at the `DiffSelection` boundary (or in `formatPatch`) that verifies the selection was computed against the same hunk layout being patched, similar to how the OpenVM fix collapsed `cols.data_read`/`cols.data_write` into the same columns to make the two values impossible to diverge.

### Proof of Concept
Conceptual reproduction (not executed, based on static code review):
1. Open a file with two or more hunks in Desktop's diff view, with side-by-side or unified diff.
2. Click "Expand" on the first hunk to pull in additional context lines (shifts `unifiedDiffStart`/`unifiedDiffEnd` of the second hunk downward per `expandTextDiffHunk`).
3. Using mouse drag, select a run of lines that fall inside the second hunk in the now-expanded view.
4. `onEndSelection` stores these lines' *expanded* diff-line indices directly into the file's `DiffSelection` (no call to `getLineInOriginalDiff`).
5. Commit with only this file's partial selection; `applyPatchToIndex` re-fetches a fresh, unexpanded diff via `getWorkingDirectoryDiff` and calls `formatPatch`, which checks `file.selection.isSelected(absoluteIndex)` using the *original* (unexpanded) hunk's `unifiedDiffStart`.
6. Because the selection indices were recorded against the expanded numbering while `formatPatch` evaluates them against unexpanded numbering, the resulting patch stages/discards a different set of lines than what was visually selected by the user.

I was not able to execute this against a running Desktop instance or inspect the definition of `getDiffLineNumber`/`getDiffRowLineNumber` (only its call sites were found in the index), so the exact numeric offset and whether some other unseen guard neutralizes it could not be fully confirmed from static analysis alone — a Desktop session with full file access and a debugger would be needed to conclusively verify the offset in practice.

export function findInteractiveOriginalDiffRange(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): IDiffRange | null {
  const range = findInteractiveDiffRange(hunks, index)

  if (range === null) {
    return null
  }

  const from = getLineInOriginalDiff(hunks, range.from)
  const to = getLineInOriginalDiff(hunks, range.to)

  if (from === null || to === null) {
    return null
  }

  return {
    ...range,
    from,
    to,
  }
}

/**
 * Utility function to get the line number in the original line from a given
 * line number in the current text diff (which might be expanded).
 */
export function getLineInOriginalDiff(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
) {
  const diffLine = diffLineForIndex(hunks, index)
  if (diffLine === null) {
    return null
  }

  return diffLine.originalLineNumber
}

  private onUpdateSelection = (ev: MouseEvent) => {
    const { temporarySelection } = this.state
    const list = this.virtualListRef.current
    if (!temporarySelection || !list) {
      return
    }

    const listNode = ReactDOM.findDOMNode(list)
    if (!(listNode instanceof Element)) {
      return
    }

    const rect = listNode.getBoundingClientRect()
    const offsetInList = ev.clientY - rect.top
    const offsetInListScroll = offsetInList + listNode.scrollTop

    const rows = this.getCurrentDiffRows()
    const totalRows = rows.length

    let rowOffset = 0

    // I haven't found an easy way to calculate which row the mouse is over,
    // especially since react-virtualized's `getOffsetForRow` is buggy (see
    // https://github.com/bvaughn/react-virtualized/issues/1422).
    // Instead, the approach here is to iterate over all rows and sum their
    // heights to calculate the offset of each row. Once we find the row that
    // contains the mouse, we scroll to it and update the temporary selection.
    for (let index = 0; index < totalRows; index++) {
      // Use row height cache in order to do the math faster
      let height = listRowsHeightCache.getHeight(index, 0)
      if (height === undefined) {
        list.recomputeRowHeights(index)
        height = listRowsHeightCache.getHeight(index, 0) ?? DefaultRowHeight
      }

      if (
        offsetInListScroll >= rowOffset &&
        offsetInListScroll < rowOffset + height
      ) {
        const row = rows[index]
        let column = DiffColumn.Before

        if (this.props.showSideBySideDiff) {
          column =
            ev.clientX <= rect.left + rect.width / 2
              ? DiffColumn.Before
              : DiffColumn.After
        } else {
          // `column` is irrelevant in unified diff because there aren't rows of
          // type Modified (see `getModifiedRows`)
        }
        const diffLineNumber = this.getDiffRowLineNumber(row, column)

        // Always scroll to the row that contains the mouse, to ease range-based
        // selection with it
        list.scrollToRow(index)

        if (diffLineNumber !== null) {
          this.setState({
            temporarySelection: {
              ...temporarySelection,
              to: diffLineNumber,
            },
          })
        }

        return
      }

      rowOffset += height
    }
  }

  private onEndSelection = () => {
    let selection = this.getSelection()
    const { temporarySelection } = this.state

    if (selection === undefined || temporarySelection === undefined) {
      return
    }

    const { from: tmpFrom, to: tmpTo, isSelected } = temporarySelection

    const fromLine = Math.min(tmpFrom, tmpTo)
    const toLine = Math.max(tmpFrom, tmpTo)

    for (let line = fromLine; line <= toLine; line++) {
      selection = selection.withLineSelection(line, isSelected)
    }

    this.props.onIncludeChanged?.(selection)

/**
 * Discards the local changes for the specified file based on the passed diff
 * and a selection of lines from it.
 *
 * When passed an empty selection, this method won't do anything. When passed a
 * full selection, all changes from the file will be discarded.
 *
 * @param repository The repository in which to update the working directory
 *                   with information from the index
 *
 * @param filePath   The relative path in the working directory of the file to use
 *
 * @param diff       The diff containing the file local changes
 *
 * @param selection  The selection of changes from the diff to discard
 */
export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
