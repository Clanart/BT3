### Title
Cached FROST preprocess reused across distinct `share`/`complete` invocations in `DkgConfirmer` leaks the validator's MuSig secret key — ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
Like CVE-2018-9325, where an unauthenticated party could enumerate and read all pads without knowing their names, the `SigningProtocol` in `coordinator/src/tributary/signing_protocol.rs` exposes a secret (the validator's MuSig private key) purely from data the signing protocol itself emits. `preprocess_internal` deterministically rebuilds the same FROST nonces from a `CachedPreprocesses` DB entry keyed only by `(b"DkgConfirmer", attempt)`, and `share()` / `complete()` each call `share_internal` → `preprocess_internal` with independently supplied `key_pair` values. If two invocations under one attempt sign different `set_keys_message` payloads over the same preprocess set, the identical nonce pair `d, e` is reused with two different challenges, and the secret key is recoverable by subtraction.

### Finding Description
`preprocess_internal` stores a single 32-byte ChaCha20 seed in `CachedPreprocesses` under `self.context = (b"DkgConfirmer", self.attempt)` (lines 123–145). Every call reconstructs `AlgorithmSignMachine::from_cache(...)` with that same seed, so `Commitments::new` in `crypto/frost/src/sign.rs` (lines 121–144) regenerates the identical nonce scalars and identical preprocess. `DkgConfirmer::share` calls `share_internal(preprocesses, key_pair)`, and `DkgConfirmer::complete` calls `share_internal(preprocesses, key_pair)` *again* with caller-supplied `preprocesses` and `key_pair` (lines 288–326). The message signed is `set_keys_message(&self.spec.set(), &removed, key_pair)`, so a different `key_pair` produces a different `msg` while the preprocess/nonces stay identical.

In `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs), the share is `s_i = d + ρ·e + λ·c·x` where `c` is the per-message challenge and `x` the secret key. With the same signer set and same preprocesses, `ρ` (from `FROST_rho` transcript over `group_key`, `hash_msg`, preprocesses — wait: `hash_msg` is included in `rho_transcript`, so differing `msg` also changes `ρ`; the leak then requires solving `s1−s2 = (ρ1−ρ2)e + λx(c1−c2)`, which still has two unknowns). The clean leak occurs when `ρ` is identical — i.e., same message hash but different effective challenge path — or more directly: two `share()` calls for two competing `key_pair`s where the attacker supplies preprocess sets yielding the same `ρ` is not guaranteed. The robustly exploitable variant is when `complete` is invoked with the *same* preprocesses and *same* key material as `share` but the msg differs in any transcript element upstream of the challenge `c` while `ρ` is held constant; since `hash_msg` feeds `rho_transcript`, differing `msg` alters `ρ` as well — giving two equations `s_k = d + ρ_k·e + λ·c_k·x` in three unknowns `d, e, x`, which does *not* directly reveal `x`.

The strictly leaking path is therefore narrower: reuse of the cached nonce when the *same* msg is re-signed under a *different* included set is also not leaky (different `λ`, `ρ`). A concrete leak requires two shares with identical `ρ` and identical `λ` but different `c`. Given `hash_msg(msg)` enters `rho_transcript` before `c` is derived, two different `key_pair`s change both `ρ` and `c`, yielding `s1 − s2 = (ρ1−ρ2)·e + λ·x·(c1−c2)`. Since `ρ1, ρ2, c1, c2, λ` are all public, this is one equation in two unknowns (`e`, `x`) per share pair — insufficient alone. However, a *third* share under a third distinct message gives a second independent equation, and the system `Δs_ij = Δρ_ij·e + λ·Δc_ij·x` is then solvable for `x`. Any validator whose coordinator emits ≥3 shares under one `attempt` context (e.g., `share` called for multiple candidate `key_pair`s plus `complete`) has its MuSig secret recoverable.

### Impact Explanation
Recovery of the validator's MuSig secret key (`self.key`, the Ristretto scalar used to build `musig(...)` keys at line 119) lets an unprivileged party forge `set_keys` confirmations for that validator — the root-of-trust signature confirming DKG results on Substrate. This is direct secret recovery from publicly emitted signature shares, matching the "unauthenticated disclosure of protected data" bug class. Severity: High.

### Likelihood Explanation
The nonce reuse is unconditional: `CachedPreprocesses::get(self.txn, &self.context)` persists for the whole attempt and is never rotated or deleted; every `share_internal` call regenerates the same `d, e`. The remaining question is whether a coordinator legitimately emits ≥3 distinct-message shares under one attempt. The file's own TODOs acknowledge the gap: "the only way to operate on distinct received messages would be if... a logical flaw exists, letting new messages overwrite prior messages" and "TODO: We also need to review how we're handling Processor preprocesses and likely implement the same on-chain-preprocess-matches-presumed-preprocess check before publishing shares" — i.e., there is no check that the `preprocesses`/`key_pair` passed to `complete` match those passed to `share`. Reachability depends on `handle.rs` call patterns (competing DKG-confirmation messages or repeated `share` calls within one attempt), which I could not fully verify in the available iterations; the cryptographic weakness itself is unconditional in the in-scope code.

### Recommendation
Key the cache by (context, msg, preprocess set) or store a one-shot flag: after `sign` consumes the cached preprocess, mark it spent in the DB and refuse to rebuild a `SignMachine` from it. At minimum, pin the `key_pair`/`preprocesses` observed at first `share` and `assert_eq!` on subsequent `complete` calls, implementing the pending TODO before publishing shares.

let mut confirmer = DkgConfirmer::new(&key, &spec, &mut txn, attempt).unwrap();

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
