### Title
Uncaught exception when parsing a malformed commit author/committer identity from a malicious repository - ([File: app/src/lib/git/log.ts])

### Summary
The Rosetta bug is a case of untrusted external input (an unsupported key type) reaching a code path that assumes valid, well-formed data and throws/panics instead of returning a graceful error. The closest Desktop analog is `CommitIdentity.parseIdentity`, which throws a hard `Error` when a commit's author/committer identity string doesn't match an expected regex, and this function is called unguarded inside `getCommits` while processing commit data from a cloned/fetched repository — data fully controlled by whoever authored the commits.

### Finding Description
`CommitIdentity.parseIdentity` parses the raw `%an <%ae> %ad` / `%cn <%ce> %cd` identity strings emitted by `git log`, matching them against `/^(.*?) <(.*?)> (\d+) (\+|-)?(\d{2})(\d{2})/`. If the string doesn't match (no `<...>` block, malformed/garbage date, etc.) it throws `new Error("Couldn't parse identity ...")`, and if the parsed timestamp is `NaN` it throws a second `Error`. [1](#0-0) 

`getCommits` in `app/src/lib/git/log.ts` calls this directly on every commit returned by `git log`, with no try/catch around the call: [2](#0-1) 

Git itself does not strictly enforce the `Name <email> timestamp tz` shape of author/committer lines at the object level — a crafted commit object (e.g., built with `git hash-object`/`git commit-tree` and a raw commit body, or via `git commit --author` with unusual content, or a corrupted/rewritten history published to a remote) can contain an author or committer line that fails this regex, or a numeric timestamp field that isn't a valid date. When a Desktop user clones or fetches such a repository and Desktop calls `getCommits` (e.g., to populate History, Compare, or Copilot conflict-resolution context), the parse throws synchronously.

Notably, the codebase already recognizes this exact function is unsafe to call unguarded: the sibling helper `getAuthorIdentity` in `app/src/lib/git/var.ts` wraps the identical `CommitIdentity.parseIdentity` call in a `try/catch` and falls back to `null`: [3](#0-2) 
`getCommits` has no equivalent guard, so the "existing check" that stops this exact panic elsewhere in the codebase is missing on the attacker-reachable path.

### Impact Explanation
Depending on how far up the call chain the exception propagates, this can surface as an uncaught rejection in the renderer, breaking the History/Changes UI for the affected repository, or degrading callers that build on `getCommits` (e.g., `getAuthors`, `copilot-conflict-context.ts`) without their own try/catch. This matches the report's bug class: attacker-controlled, malformed input reaching a parser that throws instead of validating and reporting a controlled error.

### Likelihood Explanation
I was not able to fully confirm, within the available tool budget, whether every call site of `getCommits` (particularly in `app/src/lib/stores/git-store.ts`) wraps it in a `performFailableOperation`-style catch that would downgrade the crash to a swallowed error. That uncertainty affects whether the ultimate severity is "silent feature breakage" vs. a more disruptive unhandled rejection; I was unable to verify this in the remaining time. What is confirmed is that `getCommits` itself performs no defensive parsing of identity strings, unlike the analogous `getAuthorIdentity` function, which shows the maintainers are aware this parse can fail on untrusted input.

### Recommendation
Wrap the `CommitIdentity.parseIdentity` calls inside `getCommits` (and any other unguarded direct callers) in the same defensive `try/catch` pattern used by `getAuthorIdentity`, and produce a safe placeholder identity (or skip the malformed commit) rather than throwing, mirroring the Rosetta fix's shift from a panic to a controlled error response.

### Proof of Concept
1. Create a repository and craft a commit whose author line cannot match `NAME <EMAIL> TIMESTAMP TZ`, e.g. via `git commit-tree` with a hand-built commit object containing `author Attacker-No-Angle-Brackets 12345`.
2. Push/host this repository and have the victim clone or fetch it in GitHub Desktop.
3. Desktop calls `getCommits` to render history; `CommitIdentity.parseIdentity` throws on the malformed line, propagating out of the unguarded call site in `app/src/lib/git/log.ts`.

  public static parseIdentity(identity: string): CommitIdentity {
    // See fmt_ident in ident.c:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L346
    //
    // Format is "NAME <EMAIL> DATE"
    //  Markus Olsson <j.markus.olsson@gmail.com> 1475670580 +0200
    //
    // Note that `git var` will strip any < and > from the name and email, see:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L396
    //
    // Note also that this expects a date formatted with the RAW option in git see:
    //  https://github.com/git/git/blob/35f6318d4/date.c#L191
    //
    const m = identity.match(/^(.*?) <(.*?)> (\d+) (\+|-)?(\d{2})(\d{2})/)
    if (!m) {
      throw new Error(`Couldn't parse identity ${identity}`)
    }

    const name = m[1]
    const email = m[2]
    // The date is specified as seconds from the epoch,
    // Date() expects milliseconds since the epoch.
    const date = new Date(parseInt(m[3], 10) * 1000)

    if (isNaN(date.valueOf())) {
      throw new Error(`Couldn't parse identity ${identity}, invalid date`)
    }
