### Title
Unchecked payment-amount arithmetic allows `u64` overflow producing an invalid/unspendable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` performs the exact bug class of the external report: it accepts arbitrary `u64` payment amounts and fee rates from untrusted input and performs unchecked `sum`, addition, and multiplication over them. There is no upper-bound check on `payment.1` beyond the `DUST` floor, no `Amount::MAX_MONEY` check, and no checked arithmetic anywhere in the funding math. As a result, amounts "can become very large and cause unintended behavior" — precisely the reported pattern.

### Finding Description
In `SignableTransaction::new`, the only validation applied to each payment amount is a lower-bound dust check:

```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
``` [1](#0-0) 

The amounts then flow into unchecked arithmetic:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
...
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
...
let mut needed_fee = fee_per_vbyte * vbytes;
...
if input_sat < (payment_sat + needed_fee) { ... NotEnoughFunds ... }
``` [2](#0-1) 

and the change calculation uses `checked_sub` on the *difference* while the inner addition `payment_sat + fee_with_change` is itself unchecked:

```rust
if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
``` [3](#0-2) 

The same class exists in `fee()`, which subtracts the sum of outputs from the sum of prevouts with no checked arithmetic:

```rust
self.prevouts.iter().map(|prevout| prevout.value.to_sat()).sum::<u64>() -
  self.tx.output.iter().map(|prevout| prevout.value.to_sat()).sum::<u64>()
``` [4](#0-3) 

Payment amounts are attacker-influenced data: they are derived from user-supplied burn/payout instructions which the processor turns into `payments` entries, and `ReceivedOutput` values are deserialized from untrusted bytes via `ReceivedOutput::read` → `TxOut::consensus_decode`, which accepts any `u64` value without a `MAX_MONEY` bound. [5](#0-4) 

### Impact Explanation
Two concrete failure modes, neither caught by any check:

1. **Silent wraparound (release builds).** If `payments` contains amounts whose `sum::<u64>()` overflows (or `payment_sat + needed_fee` / `payment_sat + fee_with_change` overflows), the totals wrap to a small value. The `NotEnoughFunds` check then passes, and `tx_outs` is populated with `TxOut { value: Amount::from_sat(attacker_amount), ... }` values far above Bitcoin's 21M-coin `MAX_MONEY` limit. The resulting `SignableTransaction` is passed to the FROST `TransactionSignMachine`, which produces valid BIP-340 threshold signatures over `Prevouts::All` sighashes — i.e., the threshold group signs a transaction that is consensus-invalid and can never confirm. Funds burned/locked on the Serai side are lost while no spendable Bitcoin output is produced. [6](#0-5) 

2. **Panic / crash (debug or overflow-checks builds).** `sum::<u64>()`, `payment_sat + needed_fee`, `fee_per_vbyte * vbytes`, and the subtraction in `fee()` panic on overflow, giving an unprivileged party who can influence payment values a crash-DOS against the signing path.

### Likelihood Explanation
Triggering requires only that attacker-controlled amounts reach `payments` (or `ReceivedOutput::read`-deserialized values reach `inputs`) with values summing past `u64::MAX`, or a single payment ≥ `u64::MAX - needed_fee`. Whether upstream layers cap individual burn amounts to the real supply does not remove the defect: `networks/bitcoin` is a standalone wallet library and its only guard is `*amount < DUST`. Under `validate_map`-style assumptions the FROST layer will happily sign whatever `SignableTransaction` is constructed, since the invalidity is a consensus-level property the signing code never checks.

### Recommendation
Mirror the report's fix: add explicit upper-bound checks and checked arithmetic.

- Reject any `payment.1` exceeding `bitcoin::Amount::MAX_MONEY.to_sat()` (and consider a protocol-level sanity cap) inside `SignableTransaction::new`, alongside the existing `DUST` check.
- Replace `sum::<u64>()` for `input_sat`/`payment_sat` with `try_fold`/`checked_add`, and use `checked_add`/`checked_mul` for `payment_sat + needed_fee`, `payment_sat + fee_with_change`, and `fee_per_vbyte * vbytes`, returning a new `TransactionError::AmountOverflow` on failure.
- Make `fee()` use `checked_sub` so a malformed `SignableTransaction` cannot wrap or panic.

### Proof of Concept
Conceptual Rust against the wallet library:

```rust
// payments whose total overflows u64
let huge = u64::MAX - 1_000;
let payments = vec![
  (p2tr_script_buf(attacker_key).unwrap(), huge / 2 + 1),
  (p2tr_script_buf(attacker_key).unwrap(), huge / 2 + 1),
];
// payment_sat wraps to ~998; the NotEnoughFunds check passes,
// tx_outs embeds Amount::from_sat(huge/2+1) > MAX_MONEY
let tx = SignableTransaction::new(real_inputs, &payments, None, None, fee).unwrap();
// tx.fee() / signing proceeds; the broadcast TX is consensus-invalid
```

Additionally, `SignableTransaction::new(inputs, &[(addr, u64::MAX)], None, None, fee)` reaches `Amount::from_sat(u64::MAX)` for the output while `payment_sat + needed_fee` overflows — wrapping in release, panicking under overflow checks. Both behaviors stem directly from the missing `fundingGoal`-style upper-bound check identified in the report.
