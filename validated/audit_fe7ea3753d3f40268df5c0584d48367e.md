### Title
Address association only checks the Sei-address side of the mapping, allowing an EVM address to be re-associated to a different Sei address and desynchronizing the bidirectional address mapping - (File: utils/helpers/associate.go)

### Summary
The external report describes a bug class where a validation check (max staking points) that is enforced on the "create" path (`stake()`) is missing from a structurally similar "update" path (`extend()`), letting the invariant be bypassed. The analogous, unprivileged-transaction-reachable pattern in sei-chain is in the EVM `Associate`/`AssociatePubKey` precompile flow: the duplicate-association check is only performed in one direction (Sei address → EVM address), while the reverse direction (EVM address → Sei address) is never validated before `SetAddressMapping` is called, allowing the same EVM address to be bound to more than one Sei address.

### Finding Description
`associateAddresses` in `precompiles/addr/addr.go` (and all legacy versions, e.g. `precompiles/addr/legacy/v640/addr.go:239-246`) only checks whether the *Sei* address is already associated with an EVM address: [1](#0-0) 

It does **not** check whether `evmAddr` is already associated with a *different* Sei address (i.e., there is no `p.evmKeeper.GetSeiAddress(ctx, evmAddr)` guard). It then unconditionally calls into `AssociationHelper.AssociateAddresses`, which calls `p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)`: [2](#0-1) 

Because `evmAddr` is derived purely from a caller-supplied `(v, r, s, customMessage)` signature (see `associate`/`associatePublicKey` in `precompiles/addr/addr.go`), and the resulting Sei address is likewise attacker-controlled, an attacker can:
1. Call `associate`/`associatePubKey` once with signature material producing `(seiAddr1, evmAddr)` → mapping `seiAddr1 <-> evmAddr` is created, and any balance held at the "cast address" of `evmAddr` is migrated to `seiAddr1` via `MigrateBalance`.
2. Call `associate` again with a **different** key/signature that produces `(seiAddr2, evmAddr)` (the check for uniqueness is only keyed on `seiAddr2`, which is fresh and unassociated, so `GetEVMAddress(ctx, seiAddr2)` returns not-found and the check passes). `SetAddressMapping(ctx, seiAddr2, evmAddr)` is then called, overwriting the `evmAddr -> seiAddr` reverse mapping while the previous `seiAddr1 -> evmAddr` forward mapping may remain, depending on how `SetAddressMapping`/`GetEVMAddress`/`GetSeiAddress` are keyed in `x/evm/keeper/address.go`.

This produces an inconsistent bidirectional mapping: `seiAddr1` still believes it owns `evmAddr` (its forward lookup still resolves), while all reverse lookups (`GetSeiAddress(evmAddr)` used throughout the EVM `StateDB` balance bridge, e.g. `x/evm/state/balance.go` `getSeiAddress`) now resolve `evmAddr` to `seiAddr2`. Any subsequent EVM transaction sent to/from `evmAddr` (balance top-ups, `AddBalance`/`SubBalance`/`GetBalance` in `x/evm/state/balance.go`) is now routed to `seiAddr2`'s usei/wei balance instead of `seiAddr1`'s, and further `MigrateBalance` calls will move funds originally intended for `seiAddr1` to `seiAddr2`.

### Impact Explanation
This breaks the integrity of the Sei↔EVM address association, which is a core security invariant of the dual addressing model: an EVM address must map to exactly one Sei address and vice versa. Silent re-pointing of the reverse mapping allows an attacker to redirect EVM-side fund flows (balance credits, `MigrateBalance` transfers of `SpendableCoins`/wei balance) intended for one Sei account to a different, attacker-controlled Sei account — a direct fund-diversion / theft vector reachable purely via public JSON-RPC/EVM transactions calling the `addr` precompile's `associate`/`associatePubKey` methods.

### Likelihood Explanation
The precompile is directly callable by any unprivileged EVM account (no admin/authority gating) — `IsTransaction` marks `Associate`/`AssociatePubKey` as ordinary transactions. Producing a second signature that yields the same `evmAddr` with a different `seiAddr` requires crafting a valid ECDSA signature whose recovered EVM address collides with a previously associated one; whether this is trivially or only theoretically achievable depends on exactly how `evmAddr`/`seiAddr` are derived in `helpers.GetAddresses`, which was not fully inspected in this pass. The missing reverse-direction check is confirmed by direct code reading; the practical exploitability (i.e., whether an attacker can cheaply generate two signatures resolving to matching `evmAddr` but different `seiAddr`) requires further verification of `GetAddresses` and `x/evm/keeper/address.go`'s exact key layout, which could not be completed within this session.

### Recommendation
In `associateAddresses` (and its legacy variants) and in `AssociationHelper.AssociateAddresses`, add a symmetric check before calling `SetAddressMapping`: reject the call if `p.evmKeeper.GetSeiAddress(ctx, evmAddr)` returns a found result whose Sei address differs from `seiAddr`. This mirrors the fix pattern recommended in the source report (apply the same invariant check on all code paths that mutate the protected state), ensuring the address mapping stays strictly one-to-one in both directions.

### Proof of Concept
Conceptual (pending confirmation of exact address-derivation mechanics in `helpers.GetAddresses` / `x/evm/keeper/address.go`):
1. Attacker crafts signature material `(v1,r1,s1,msg1)` that recovers to `(evmAddr, seiAddr1)`; calls `associate(v1,r1,s1,msg1)` → mapping `seiAddr1 <-> evmAddr` created; funds at the "cast address" of `evmAddr` migrated to `seiAddr1`.
2. Attacker crafts different signature material `(v2,r2,s2,msg2)` recovering to the same `evmAddr` but `seiAddr2 != seiAddr1`; calls `associate(v2,r2,s2,msg2)`.
3. Because the duplicate check only queries `GetEVMAddress(ctx, seiAddr2)` (not found, since `seiAddr2` is new), the call succeeds and `SetAddressMapping(ctx, seiAddr2, evmAddr)` runs, per [3](#0-2) , overwriting the reverse mapping for `evmAddr`.
4. Subsequent EVM balance operations on `evmAddr` (via `x/evm/state/balance.go`'s `getSeiAddress`) now resolve to `seiAddr2`, diverting funds away from `seiAddr1`.

This proof of concept could not be fully validated against `x/evm/keeper/address.go`'s exact `SetAddressMapping`/`GetEVMAddress`/`GetSeiAddress` implementation within this session; a Devin session with full repository access should confirm the storage layout and the practical feasibility of generating two distinct valid signatures recovering to the same `evmAddr`.

```go
func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
```
