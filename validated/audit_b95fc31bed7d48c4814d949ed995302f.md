### Title
`distribution` precompile's `rewards()` view lacks a non-payable check, permanently stranding native funds sent with the call - (File: precompiles/distribution/distribution.go)

### Summary
The `distribution` precompile at `0x0000000000000000000000000000000000001007` implements every state-changing and view method with a `pcommon.ValidateNonPayable(value)` (directly or via `p.validateInput`) guard that rejects any call carrying non-zero `msg.value` — except `rewards()`. A caller can invoke `rewards(address)` with a non-zero `value`, and the call succeeds instead of reverting, moving native funds into the EVM value-transfer path with no way for the precompile to route them back to the caller, unlike `bank.sendNative`/`HandlePaymentUseiWei`, which explicitly refunds the payer.

### Finding Description
The `Execute` dispatcher in `precompiles/distribution/distribution.go` routes every method except `RewardsMethod` through validation that checks `value`: [1](#0-0) 

Compare this to the sibling view methods (`params`, `validatorOutstandingRewards`, `validatorCommission`, etc.), which all call `p.validateInput(value, args, n)`, itself wrapping `pcommon.ValidateNonPayable(value)`: [2](#0-1) 

But `rewards()` only validates argument length and never checks `value` at all: [3](#0-2) 

The test suite already documents this discrepancy as an intentional quirk rather than a fixed bug: [4](#0-3) 

Other precompiles that intentionally accept value (`bank`, `staking`, `gov`, `wasmd`) are registered in `payablePrecompiles` and their executor functions explicitly forward the received value back out (e.g., `bank.sendNative` calls `pcommon.HandlePaymentUseiWei`, which refunds the payer before executing the transfer): [5](#0-4) [6](#0-5) 

The `distribution` precompile is **not** in `payablePrecompiles`, and `rewards()` has no logic that forwards, refunds, or otherwise makes use of any value received. This mirrors the `Reservoir` bug class from the external report: a contract/precompile that is unintentionally exposed to receiving a native asset but has no design to handle, forward, or return it — so any value sent in is effectively stuck.

### Impact Explanation
Any unassociated or associated EVM account can call `rewards(address)` on `0x...1007` with a non-zero `value`. Because the EVM's native value-transfer semantics move `wei`/`usei` balance from the caller into the precompile's account as part of the CALL, and the `rewards` handler never refunds or forwards that value (unlike every payable precompile method), the sent funds become permanently unrecoverable by the sender — there is no withdrawal path for value accidentally or maliciously routed to the distribution precompile's account via this specific method. This is a concrete, permanent loss of user funds, reachable by any transaction sender with no special privilege.

### Likelihood Explanation
Likelihood is moderate: this requires the caller to explicitly attach `value` to a `rewards()` call, which is not the "happy path" a typical dApp/wallet integration would do, and view calls do not usually carry value. However, nothing in the ABI or EVM tooling prevents a wallet, contract integrator, or attacker from constructing such a transaction; the bug is a simple missing-guard defect (the same guard exists in every other method in the same file), so it is exploitable in a single, straightforward transaction with no preconditions besides having spendable native balance.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check to `rewards()` in `precompiles/distribution/distribution.go`, consistent with every other view/query method in the file (e.g., mirror `p.validateInput` used by `params`, `communityPool`, `delegationRewards`, etc.), so a value-bearing call to `rewards()` reverts before any native value transfer is finalized.

### Proof of Concept
1. From an EVM-associated Sei account, construct a raw `eth_call`/transaction to `0x0000000000000000000000000000000000001007` (distribution precompile) calling `rewards(address)` with `value` set to a non-zero amount (e.g. `1_000_000_000_000_000_000` wei / 1 usei-equivalent).
2. Unlike calls to `params()`, `communityPool()`, or `validatorCommission()` (which all revert with "sending funds to a non-payable function" per `precompiles/staking/staking_test.go` and `precompiles/distribution/distribution_test.go` patterns for other methods), the `rewards()` call succeeds and returns normal reward data.
3. Inspect the caller's post-tx bank/wei balance: it is reduced by the attached `value`, while the distribution precompile module account balance is increased by the same amount, with no mechanism in `precompiles/distribution/distribution.go` ever debiting that balance back out — confirmed by the absence of any `HandlePaymentUseiWei`/refund call in the `rewards` function body (`precompiles/distribution/distribution.go:543-579`) and explicitly called out as a known gap in `integration_test/precompile_tests/precompiles/distribution.spec.ts:1-12`.

	if err := pcommon.ValidateNonPayable(value); err != nil {
