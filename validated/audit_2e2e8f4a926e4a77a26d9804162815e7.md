### Title
SSRF in DataLayer mirror-URL fetch flow lets any wallet user force a peer's node to make arbitrary outbound HTTP requests - ([File: chia/data_layer/data_layer.py])

### Summary
DataLayer mirror URLs are attacker-supplied, on-chain data with no ownership binding: any wallet user can spend a tiny amount to publish a mirror coin for *any* `launcher_id` (including a store they do not own) with arbitrary URLs via `DataLayerWallet.create_new_mirror()`. Any node that syncs/subscribes to that store will later feed those attacker-chosen URLs directly into `http_download()`/`aiohttp.ClientSession().get(...)`, causing the victim node to issue outbound HTTP requests to attacker-controlled destinations. This mirrors the WonderCMS SSRF bug class (CVE-2024-27561), where a user-controlled URL parameter is passed unchecked into a server-side HTTP fetch.

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a mirror coin whose memos encode `launcher_id` and an arbitrary list of `urls`, with no check that the caller owns or controls that `launcher_id`: [1](#0-0) 

This is directly reachable from the wallet RPC `dl_new_mirror`, which simply forwards the caller-supplied `launcher_id`, `amount`, and `urls` to `create_new_mirror` with no ownership validation of the target store: [2](#0-1) 

The mirror puzzle/solution round-trips the `launcher_id` and raw URL bytes via memos, and any node can decode them back out with `get_mirror_info()`: [3](#0-2) 

On the consumer side, `DataLayer.update_subscriptions_from_wallet()` pulls **all** mirrors registered for a `store_id` (regardless of who created them) and stores their URLs as subscription servers: [4](#0-3) 

`DataLayer.fetch_and_validate()` then iterates those server URLs and calls `insert_from_delta_file()` → `download_file()` → `http_download()`, which performs an `aiohttp` GET directly against `server_info.url + "/" + filename` with no allow-list, scheme restriction, or private-network filtering: [5](#0-4) [6](#0-5) 

Because subscribing to and syncing a store are normal, low-privilege DataLayer client operations (any local DataLayer user can `subscribe` to a store id they discover, and owned stores are also auto-synced), an attacker only needs to (a) know or guess a `store_id` a victim tracks/owns, and (b) publish a mirror coin (cheap, unprivileged spend) with a malicious URL such as `http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:<internal-port>/...`, or an internal-network host. The victim's DataLayer service will then issue outbound requests to that destination during its normal `periodically_manage_data()` / `fetch_and_validate()` loop.

### Impact Explanation
This is a genuine SSRF: an unprivileged actor (any wallet holder capable of submitting a spend bundle) can force another user's node to make arbitrary outbound HTTP(S) requests chosen by the attacker, with no validation of scheme/host/port. This can be used to probe/attack internal network services or cloud metadata endpoints reachable from the victim's host, and to trigger unwanted side effects on any HTTP endpoint the victim's node can reach — classic SSRF impact, consistent with the CVSS 9.1 rating pattern of the referenced CVE (confidentiality/integrity impact via server-forced requests), though full data exfiltration back to the attacker is limited unless the response affects observable node behavior (e.g., delta-file parsing errors, timing, or bans) or the target endpoint has request-based side effects.

### Likelihood Explanation
Likelihood is high: creating a mirror coin is a normal, cheap, unprivileged wallet operation exposed via public RPC (`dl_new_mirror`) with no ownership check on `launcher_id`, and mirror-driven fetches (`update_subscriptions_from_wallet` → `fetch_and_validate` → `http_download`) are part of the routine DataLayer sync loop that runs automatically for owned/subscribed stores.

### Recommendation
- Validate/sanitize mirror URLs before they are ever used as fetch targets: enforce an allow-list of schemes (`http`/`https` only), reject loopback/link-local/private/metadata IP ranges (e.g. 127.0.0.0/8, 169.254.0.0/16, RFC1918 ranges) unless explicitly permitted by local config, and consider DNS-rebinding-safe resolution checks at fetch time.
- Restrict who can register mirrors for a given `launcher_id`, e.g. require store ownership or an explicit user opt-in/allow-list before a mirror's URLs are used as active subscription/sync sources.
- Apply the same URL validation in `get_downloader()`'s plugin dispatch and any plugin `handle_download`/`download` HTTP calls that consume externally supplied URLs.

### Proof of Concept
1. Attacker wallet calls RPC `dl_new_mirror` with a victim-tracked `launcher_id` and `urls=["http://169.254.169.254/latest/meta-data/", "http://<internal-host>:<port>/admin"]`, paying a minimal fee — accepted because there is no ownership check in `create_new_mirror`/`dl_new_mirror`.
2. The mirror coin confirms on-chain.
3. Victim's DataLayer service, tracking/subscribed to the same `store_id`, runs its periodic sync loop; `update_subscriptions_from_wallet()` reads the new mirror's URLs into its subscription server list.
4. On the next `fetch_and_validate()` pass, `http_download()` issues `GET http://169.254.169.254/latest/meta-data/<delta-filename>` (or the internal host URL) from the victim's node — an outbound SSRF request fully controlled by the attacker.

def get_mirror_info(
    parent_puzzle: Program | SerializedProgram, parent_solution: Program | SerializedProgram
) -> tuple[bytes32, list[bytes]]:
    assert type(parent_puzzle) is type(parent_solution)
    _, conditions = run_with_cost(parent_puzzle, INFINITE_COST, parent_solution)
    for condition in conditions.as_iter():
        if (
            condition.first().as_python() == ConditionOpcode.CREATE_COIN
            and condition.at("rf").as_python() == create_mirror_puzzle().get_tree_hash()
        ):
            memos: list[bytes] = condition.at("rrrf").as_python()
            launcher_id = bytes32(memos[0])
            return launcher_id, [url for url in memos[1:]]
    raise ValueError("The provided puzzle and solution do not create a mirror coin")
