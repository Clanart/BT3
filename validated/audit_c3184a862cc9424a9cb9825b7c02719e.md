### Title
Unbounded attacker-controlled allocation in `ReceivedOutput::read` via `TxOut::consensus_decode` enables remote denial of service - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` feeds untrusted bytes directly into `TxOut::consensus_decode`, which trusts a `CompactSize` length field for the `script_pubkey` and allocates a `Vec` of that size before reading. A single malicious serialization with a ~4 GiB length prefix (encoded in a handful of bytes) forces an allocation failure/abort or OOM, crashing any process that deserializes untrusted `ReceivedOutput` data — the same untrusted-length → crash class as CVE-2023-47016's OOB read in `r_bin_object_set_items`.

### Finding Description
`ReceivedOutput::read` reads a scalar offset and then consensus-decodes a `TxOut` and `OutPoint` from the stream with no size bound [1](#0-0) . `TxOut`'s consensus encoding is `value (8 bytes) || script_pubkey_length (CompactSize u64) || script_pubkey`. `rust-bitcoin`'s decoder allocates a `Vec` sized by that length field before attempting to fill it, so the attacker controls the allocation size independent of the actual number of bytes provided.

The `BufReader::with_capacity(0, r)` wrapper used to bound the consensus decode does not bound anything — capacity 0 just prevents buffering; the length prefix inside the stream is still fully attacker-controlled [2](#0-1) .

The same untrusted stream reaches this path through `Output::read` (which chains `ReceivedOutput::read` on attacker bytes) and through the scanner DB replay loop `while !bytes.is_empty() { res.push(N::Output::read(&mut bytes).unwrap()) }`, which additionally `.unwrap()`s on any parse error rather than returning an `io::Error` [3](#0-2) . `read_F`/`read_G`/`SchnorrSignature::read`/`DLEqProof::read` are all fixed-width and safe; this is the one in-scope read path whose length is adversary-controlled [4](#0-3) .

### Impact Explanation
An unprivileged party who can cause their bytes to be passed to `ReceivedOutput::read` — e.g., serialized outputs relayed through processor messages, scanner/DB output serialization, or any integration reading `ReceivedOutput`/`Output` blobs — can crash the node with a ~15-byte payload requesting a multi-GB allocation, or a panic via the `.unwrap()` in the output-replay loop. This is availability loss equivalent to the CVE (CVSS A:H): the signer/scanner process aborts mid-operation, halting signing and output processing until restart.

### Likelihood Explanation
`ReceivedOutput` is designed to be serialized (`serialize()`/`write`) and read back from streams, and scanner output persistence round-trips it verbatim [5](#0-4) . Any channel feeding externally produced serialized outputs (tributary/processor messages, stored blobs re-read after tampering, or third-party integrations of `bitcoin-serai`) reaches the vulnerable decode. Triggering requires only a length prefix; no valid output structure is needed before the allocation occurs.

### Recommendation
Do not consensus-decode `TxOut`/`OutPoint` directly from an unbounded reader. Take the stream by a fixed maximum size (`reader.take(MAX_OUTPUT_LEN)`), and either:
- validate the `CompactSize` length against a bound consistent with Bitcoin consensus/standardness (scripts far exceedable) before allocation, or
- hand-roll the decode: 8-byte value + length-prefixed script with an explicit cap, e.g. `u32` length ≤ `MAX_TX_SIZE`, plus `OutPoint` (fixed 36 bytes).
Also replace `.unwrap()` on decode paths in `processor/src/multisigs/scanner.rs` output replay with `io::Result` error propagation so malformed data cannot panic the loop.

### Proof of Concept
```rust
// networks/bitcoin: crashes/aborts the process on allocation of ~4 GiB
use bitcoin_serai::wallet::ReceivedOutput;
use k256::Scalar;
use ciphersuite::group::ff::PrimeField;

let mut bytes = Vec::new();
// offset: canonical secp256k1 scalar
bytes.extend_from_slice(Scalar::ZERO.to_repr().as_ref());
// TxOut::value = 0 sats
bytes.extend_from_slice(&0u64.to_le_bytes());
// TxOut::script_pubkey length as CompactSize = 0xffffffff (4 GiB)
bytes.extend_from_slice(&[0xfe, 0xff, 0xff, 0xff, 0xff]);
// No script bytes follow; allocation happens before the read fails.
// ReceivedOutput::read(&mut bytes.as_slice()) aborts/OOMs on the Vec allocation.
let _ = ReceivedOutput::read(&mut bytes.as_slice());
```
A panic-only variant targets the DB replay loop: truncate any stored `Output` blob so `Output::read` returns `Err` (or `Option::<Vec<u8>>::decode(..).unwrap()` panics on malformed SCALE in `processor/src/networks/bitcoin.rs:150`), causing `N::Output::read(&mut bytes).unwrap()` to panic the scanner task.
