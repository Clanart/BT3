### Title
Stale `manualResolutions` map carries across conflict-type transitions, silently re-applying an old ours/theirs choice to an unrelated merge/rebase/cherry-pick - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`updateConflictState` derives the new `ConflictState` by feeding the *previous* conflict state's `manualResolutions` map straight into `getConflictState()`, keyed only by file path, with no check that the new conflict is actually the same operation, or even the same operation *kind*, as the one that produced those resolutions.

### Finding Description
`updateConflictState` (`app/src/lib/stores/updates/changes-state.ts:263-311`) computes:

```
const manualResolutions =
  prevConflictState !== null
    ? prevConflictState.manualResolutions
    : new Map<string, ManualConflictResolution>()

const newConflictState = getConflictState(status, manualResolutions)
``` [1](#0-0) 

`manualResolutions` is carried over unconditionally, without checking whether `prevConflictState.kind` matches the kind (`merge` / `rebase` / `cherryPick`) of the operation that produced the new status. The function only special-cases same-kind transitions (merge→merge, rebase→rebase) for telemetry side effects; any transition between *different* kinds falls into the final branch:

```
// Otherwise we transitioned from a merge conflict to a rebase conflict or
// vice versa, and we should avoid any side effects here
return newConflictState
``` [2](#0-1) 

`newConflictState` was already built with the *old* `manualResolutions` map before this check runs — the "avoid side effects" comment only refers to skipping the stats-store telemetry calls, not to resetting the resolutions map. So if the user manually resolved a conflicted path (e.g. `src/foo.ts` → "theirs") during a rebase, and — without an intervening state where `conflictState` becomes `null` — the app's next status refresh instead reports a merge (or cherry-pick) conflict that touches a file at the same path, that file will be treated as already resolved with the stale rebase-time choice. `getConflictState()` (`app/src/lib/stores/updates/changes-state.ts:121-176`) has no per-operation identity (no tip/branch check tying `manualResolutions` entries to the specific in-progress operation), so nothing invalidates the map when the underlying operation actually changes.

This is a structural analog of the reported invariant: a state field (`rebalancingRewardActive` in the report, `manualResolutions` here) that is only reset in the code paths the author anticipated (matching-kind transitions), but silently persists across a different, unanticipated path (kind-changing transition), causing the wrong decision to be reused later.

### Impact Explanation
If the stale "theirs"/"ours" choice from a prior, unrelated operation is silently re-applied to a same-path file in a new merge/rebase/cherry-pick, `stageManualConflictResolution` (`app/src/lib/git/stage.ts`) will `git checkout --ours/--theirs` that file without ever surfacing a fresh decision UI for it, and it will be included in the final commit as already-resolved. This is a silent corruption of what the user commits: the committed content for that file is chosen by a decision the user made for a different source branch/commit, not the one actually being merged/rebased now.

### Likelihood Explanation
This requires a specific interleaving — conflict-kind transitioning directly from one kind to another without the app observing an intermediate "no conflict" status, and a manual resolution having been recorded on a path that recurs in the next operation. This can plausibly occur via rapid successive operations (e.g., scripted/automated git usage outside Desktop while Desktop's periodic status refresh coalesces multiple git state changes into one), or a background status poll landing exactly between an abort and a new operation start. I was not able to fully verify from static reading alone whether Desktop's UI/dispatcher guarantees an intermediate null-conflict refresh in all normal user flows (e.g., every abort/finish action explicitly triggers `_loadStatus` before a new operation can begin) — this would need dynamic testing to confirm reachability with certainty.

### Recommendation
In `getConflictState`/`updateConflictState`, only preserve `manualResolutions` when the new conflict is the same operation (same `kind`, and ideally same operation identity, e.g. matching `currentTip`/target branch as recorded in `prevConflictState`). On any kind change (or any change that doesn't conclusively continue the same operation), reset `manualResolutions` to a fresh empty map before calling `getConflictState`.

### Proof of Concept
Not independently reproduced against a running app; based on static code review only (no dynamic execution tool available). The following is a static walk-through of the code paths that will trigger the bug:
1. Start a rebase; a conflict occurs on `src/foo.ts`. User picks "theirs" via `updateManualConflictResolution`, which calls `_updateManualConflictResolution` → `conflictState.manualResolutions.set('src/foo.ts', theirs)` (`app/src/lib/stores/app-store.ts:8796-8828`).
2. Before the app observes a status refresh in which `conflictState` becomes `null`, the working copy is put into a different conflict kind (e.g., a merge is started, e.g. via external git usage or a race in status polling) that also produces a conflict on `src/foo.ts`.
3. `updateConflictState` is called with `prevConflictState.kind === 'rebase'` and the freshly computed `newConflictState.kind === 'merge'`; since kinds differ, it falls to the final branch and returns `newConflictState`, which was built using the still-attached `manualResolutions` Map containing `src/foo.ts → theirs` from the earlier rebase (`app/src/lib/stores/updates/changes-state.ts:263-311`, `121-176`).
4. The merge conflicts dialog shows `src/foo.ts` as already resolved (`theirs`) even though the user never made that choice for this merge; committing the merge silently applies the stale resolution.
