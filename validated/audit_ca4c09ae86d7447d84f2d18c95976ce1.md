### Title
Copilot conflict resolution silently splices unverified LLM-generated content into merged files based on attacker-controlled conflict input - (File: app/src/lib/copilot-conflict-resolution.ts)

### Summary
GitHub Desktop's "Resolve with Copilot" feature builds a prompt from the conflicting hunks of a merge/rebase/cherry-pick — hunks that can originate entirely from an attacker-authored branch/PR — sends it to an LLM, and then mechanically splices whatever `resolvedContent` the model returns into the working file via `reassembleResolvedFile`. Validation (`parseCopilotConflictResolution`, `validateResolutionPaths`) only checks JSON shape, file-path membership, and hunk *count*; it never checks that the returned content is semantically consistent with, or bounded by, the original "ours"/"theirs" hunk content. This mirrors the core flaw in the Chainlink report: data returned by an untrusted/attacker-influenced source is accepted and used to determine a critical output (there: a price; here: committed file content) with only superficial, not substantive, validation.

### Finding Description
`reassembleResolvedFile` walks the raw on-disk file (which still contains conflict markers) and, for every well-formed `<<<<<<< / ======= / >>>>>>>` block, blindly replaces it with `hunkResolutions[hunkIndex].resolvedContent` from the model — matched purely by order, with no comparison to the original "ours"/"theirs" text: [1](#0-0) 

The only gates before this splice are:
- JSON shape/field-type checks and a check that `resolvedContent` doesn't literally contain a `<<<<<<<`/`=======` marker line [2](#0-1) 
- That the returned file paths match the expected conflicted files and that the *hunk count* matches [3](#0-2) 

None of these checks constrain the actual *content* of `resolvedContent` to anything derived from the real conflict. The conflicting hunk content itself — which forms the bulk of the prompt sent to the model — comes directly from a fetched/merged branch that an attacker fully controls (e.g., a malicious PR/branch the victim merges or rebases onto). This is a classic prompt-injection surface: crafted comment text, string literals, or "helpful" instructions embedded in the conflicting code can steer the model into emitting attacker-chosen code as the "resolution," and the pipeline has no independent check that would reject it.

The write path then takes this content largely on faith: `_applyCopilotConflictResolutions` performs a repo-boundary check on the *path* (`resolveWithin`) [4](#0-3)  but performs no verification of the *content* before writing and staging it: [5](#0-4) 

The user is shown a "Continue Merge" dialog with Summary/Changes tabs, and the flow can also be auto-routed straight into Copilot resolution when the feature is enabled and the AI-disclaimer is "fresh" [6](#0-5) , meaning the review step is a UI affordance, not a content-integrity control — nothing in code guarantees the diff view highlights subtly malicious insertions (e.g., a changed dependency version, an added script, or an altered URL) buried in a large multi-hunk file.

### Impact Explanation
If a victim merges/rebases/cherry-picks a branch containing crafted conflict content, an attacker can cause GitHub Desktop's AI-assisted conflict resolution to silently inject attacker-chosen code into the resolved file that the user then commits (and likely pushes). This is a direct analogue of "silent corruption of what the user commits or pushes" — the corrupted value is the `resolvedContent` string that gets written via `writeFile(absolutePath, resolution.resolvedContent, ...)` and immediately `git add`-ed [7](#0-6) , without any check that ties the output back to the legitimate contents of either side of the conflict.

### Likelihood Explanation
Requires no privileged access: the attacker only needs the victim to merge/rebase/cherry-pick a branch/PR they control (an ordinary, expected Desktop workflow), have Copilot conflict resolution enabled, and click "Continue" without spotting the injected change in a (potentially large, multi-file) diff review. Auto-routing to Copilot resolution when the disclaimer is "fresh" further reduces the number of deliberate choices the user makes before the write occurs. The existing validations (`validateResolutionPaths`, marker-string check) do not address content fidelity at all, so they provide no protection against this path.

### Recommendation
- Constrain `resolvedContent` for standard (non-`action`) hunks: require that it be composed only from lines that actually appear in the original "ours"/"theirs"/"base" hunk content (or diff against them and flag/reject resolutions introducing net-new lines beyond a reviewed allowlist).
- Surface an explicit, line-level diff of Copilot's proposed change versus both original sides for every hunk in the "Changes" tab, and require per-hunk (not just per-file) confirmation for hunks that introduce content not present on either side.
- Treat conflict hunk text as untrusted input to the LLM prompt; consider sanitizing/flagging embedded instruction-like text before sending it to the model.

### Proof of Concept
1. Attacker crafts a branch that will conflict with the victim's branch on a sensitive file (e.g., a build script or dependency manifest), embedding text in a comment/string inside the conflicting region designed to instruct the model to "helpfully" add extra code/dependency when resolving the conflict.
2. Victim opens the branch and performs a merge/rebase/cherry-pick in Desktop; a conflict is detected and Copilot resolution is invoked (`_startCopilotConflictResolution` → `resolveConflictsWithCopilot` in `copilot-store.ts`).
3. The model's JSON response passes `parseCopilotConflictResolution`/`validateResolutionPaths` (correct path, correct hunk count, no literal marker strings) despite containing attacker-steered content.
4. `reassembleResolutions`/`reassembleResolvedFile` splices this content into the file verbatim [8](#0-7) .
5. Victim clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes the file to disk and `git add`s it [7](#0-6) , after which the victim commits and pushes the attacker-influenced content.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
