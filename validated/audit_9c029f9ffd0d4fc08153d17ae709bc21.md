### Title
Ankr-recovery lock bypass via self-inflating collateral in `AnkrBNBPoolHelper.withdraw` - (File: wombat/AnkrBNBPoolHelper.sol)

### Summary
`AnkrBNBPoolHelper.withdraw()` gates early withdrawal of locked ankr-recovery funds by comparing `lockedAmount[msg.sender]` against `rest`, the caller's *aggregate* remaining stake in the shared rewarder/stakingToken [1](#0-0) . Because `rest` is computed via `IBaseRewardPool(rewarder).balanceOf(msg.sender)`, which reads `MasterMagpie.stakingInfo(stakingToken, account)` [2](#0-1) , any unlocked stake the attacker adds to that same `stakingToken`/`rewarder` (either via `AnkrBNBPoolHelper.deposit()`/`depositLP()` itself, or per the stated precondition via a sibling `WombatPoolHelper`/`WombatPoolHelperV2` sharing the same `stakingToken`/`rewarder`) inflates `rest` and lets the attacker withdraw the physically locked liquidity before `unlockTime`.

### Finding Description
`withdraw(_liquidity, _minAmount)` performs, in order: (1) `IWombatStaking.withdraw` which physically sends underlying tokens for `_liquidity` to `msg.sender` [3](#0-2) ; (2) `_unstake(_liquidity, msg.sender)` which reduces the caller's stake in `MasterMagpie` for `stakingToken` [4](#0-3) ; (3) computes `rest = this.balance(msg.sender)` (i.e., the caller's *remaining* aggregate stake for `stakingToken`) and only reverts if `unlockTime > block.timestamp && lockedAmount[msg.sender] > rest` [1](#0-0) .

The check treats "remaining aggregate balance ≥ lockedAmount" as a proxy for "the locked portion was not withdrawn," but it does not track which specific tokens were withdrawn versus retained. If the attacker first stakes additional, unlocked collateral `E` into the same `stakingToken` (e.g. via `AnkrBNBPoolHelper.deposit()`, which stakes into `stakingToken` without touching `lockedAmount` — a gap the code's own comment flags: `"should be corrected as amount so if user extra deposit, can withdraw extra"` [5](#0-4) ), the attacker's aggregate stake becomes `L + E` where `L = lockedAmount[msg.sender]`. Calling `withdraw(L, minAmount)` physically withdraws the locked `L` tokens, drops the aggregate stake to `E`, and the guard `L > E` is false whenever `E >= L`, so the withdrawal of the locked capital succeeds early.

Per the question's stated precondition, the same effect is achievable cross-contract: if `stakingToken`/`rewarder` is shared with a separate `WombatPoolHelper`/`WombatPoolHelperV2` front-end (both of which call the identical `balanceOf`/`stakingInfo` accounting path [6](#0-5) ), depositing `E` there has the exact same inflating effect on `rest`, since `balanceOf` is keyed purely by `stakingToken` and account, not by which helper originated the stake.

No other modifier (no `nonReentrant`, no per-source accounting) protects this specific comparison; `IWombatStaking.withdraw`/`deposit` themselves are protected by `nonReentrant`/`whenNotPaused` but that does not prevent the sequential deposit-then-withdraw pattern.

### Impact Explanation
This allows an unprivileged holder of ankr-recovery locked funds to force physical release of their `lockedAmount` before `unlockTime`, defeating the explicit purpose of the one-year lock mechanism (`unlockTime`/`lockedAmount`) implemented for ankr-exploit-affected users [7](#0-6) . This matches the "funds frozen ≥24h early release" / premature unlock of funds meant to remain frozen impact class.

### Likelihood Explanation
Feasible and fully self-contained: the attacker only needs to be an ankr-recovery user with `lockedAmount[msg.sender] = L` and temporary capital `E >= L` (their own funds, immediately recoverable back since `E` is unlocked and unrestricted). No special privileges, oracle manipulation, or third-party cooperation is required — a simple `deposit()` followed by `withdraw(L, minAmount)` in either the same or a subsequent transaction achieves the bypass, and it is repeatable for any locked user.

### Recommendation
Track locked/unlocked stake explicitly rather than inferring it from aggregate `balanceOf`. E.g., maintain a separate `unlockedExtra[msg.sender]` counter incremented only by voluntary extra deposits and decremented on withdrawal, and require `_liquidity <= unlockedExtra[msg.sender]` (or `balanceBeforeWithdraw - lockedAmount[msg.sender]`) whenever `unlockTime > block.timestamp`, instead of comparing against the post-withdrawal aggregate `rest`.

### Proof of Concept
Foundry test plan:
1. Deploy `AnkrBNBPoolHelper` with `unlockTime = block.timestamp + 365 days`, and set `lockedAmount[attacker] = L` via `batchDepositLPFor` (mint/lock `L` LP for attacker).
2. Attacker calls `AnkrBNBPoolHelper.deposit(E, minLiquidity)` with `E >= L` of their own capital, staking into the shared `stakingToken`/`rewarder`.
3. Assert `IBaseRewardPool(rewarder).balanceOf(attacker) == L + E`.
4. Attacker calls `AnkrBNBPoolHelper.withdraw(L, minAmount)` before `unlockTime`.
5. Assert the call does **not** revert, attacker receives `L` worth of underlying tokens, and `IBaseRewardPool(rewarder).balanceOf(attacker) == E` (i.e., `L >= E`... actually assert `E >= L` holds so guard passes), demonstrating early release of the locked `L` funds prior to `unlockTime`.
6. (Optional extension per precondition) Repeat using a separate `WombatPoolHelper` instance configured with the same `stakingToken`/`rewarder` to deposit `E`, and show identical bypass of `AnkrBNBPoolHelper.withdraw`.
