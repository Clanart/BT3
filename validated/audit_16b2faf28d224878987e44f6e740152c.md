### Title
Silent, unconfirmed rewrite of the `origin` remote URL from an untrusted GitHub API response - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`update-remote-url.ts` silently rewrites the local `origin` remote URL whenever the GitHub API's reported `clone_url` differs from what's currently configured, based solely on stale-value equality checks — with no user confirmation. This mirrors the underlying flaw in the ThunderNFT report: a security-relevant action (updating an order's payment target / here, updating the git push target) is gated by comparing an old cached value to a new value supplied by an external/untrusted source, and the comparison logic silently drives a state mutation instead of requiring explicit re-validation or user consent.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` every time Desktop refreshes GitHub repository metadata (e.g. on repository selection, account change, fetch): [1](#0-0) 

The `apiRepo` object comes straight from `api.fetchRepository(owner, name)` — an object entirely controlled by the GitHub API endpoint (or GHE instance) associated with the account, i.e. the "GitHub API object" attacker surface called out in the Valid Impact section: [2](#0-1) 

Inside `updateRemoteUrl`, the decision to call `gitStore.setRemoteURL` — which runs `git remote set-url` against the real git remote used for `push`/`fetch`/`pull` — is based purely on comparing the previously **cached** `gitHubRepository.cloneURL` to the current git remote, and the new `apiRepo.clone_url` to the current git remote: [3](#0-2) 

If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, the origin URL is overwritten with whatever `apiRepo.clone_url` says — no dialog, no diff shown to the user, no cryptographic or ownership verification of the new URL. This differs sharply from the `upstream` remote update flow, which explicitly prompts the user via a confirmation dialog before changing the upstream remote: [4](#0-3) 

There is no equivalent prompt for the `origin` remote change in `updateRemoteUrl`; the mutation of the push/fetch target is fully automatic and silent.

### Impact Explanation
`origin` is the remote most commonly used for `git push`. Once rewritten, `push()` uses `remote.url` both as the git push target and to compute credential-helper environment via `envForRemoteOperation(remote.url)`: [5](#0-4) 

If the value returned in `clone_url` by the API response points to a host under attacker control (e.g. because the tracked owner/name was repojacked/recreated, or the endpoint's API response was tampered with by a compromised/malicious GHE server), Desktop will silently redirect the user's next push (and the credential material resolved for that host) to the attacker-controlled remote — corrupting where the user's commits go and creating a path to credential/token exfiltration, matching the "silent corruption of what the user commits or pushes" and "credential/token exfiltration" impact categories in the Valid Impact section.

### Likelihood Explanation
The trigger path (`_selectRepository` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`) runs automatically and frequently (repository selection, account refresh, fetch), requiring no unusual user action. The only precondition is that the API response for the tracked `owner/name` differs from the currently configured remote URL while superficially satisfying `remoteUrlUnchanged` (i.e., the user hasn't manually customized their remote) — a state that is the common/default case for most users, making the attacker-controlled-response path realistically reachable without local access, admin rights, or social engineering.

### Recommendation
- Do not silently call `gitStore.setRemoteURL` from `updateRemoteUrl`; surface a confirmation dialog to the user analogous to `UpstreamAlreadyExists`, showing the current and proposed URL before changing `origin`.
- Validate the new `clone_url` against the repository's immutable GitHub `id` (already available from the API response) rather than trusting owner/name string continuity, to detect renamed/deleted/re-created (repojacked) repositories.
- Consider pinning/verifying the hostname against the account's known endpoint before allowing any automatic remote URL rewrite.

### Proof of Concept
1. User has Desktop tracking a `RepositoryWithGitHubRepository` whose `gitHubRepository.cloneURL` matches the configured `origin` remote (`remoteUrlUnchanged === true`), and origin uses `https`.
2. On next repository refresh, `api.fetchRepository(owner, name)` (backed by an untrusted/compromised GHE instance, or a repo whose ownership at that owner/name has changed) returns an `IAPIRepository` with `clone_url` set to `https://attacker-host/owner/name`.
3. `updateRemoteUrl` computes `protocolsMatch = true`, `remoteUrlUnchanged = true`, `urlsMatch = false` → condition holds → `gitStore.setRemoteURL('origin', 'https://attacker-host/owner/name')` executes silently. [6](#0-5) 
4. Any subsequent `git push`/`fetch` for that repository now targets `attacker-host`, using `envForRemoteOperation` credential resolution scoped to that new URL. [5](#0-4) 

Note: I was not able to trace the exact matching logic of `matchGitHubRepository` (used to resolve `owner`/`name` for the API call) within the available index; whether it matches strictly by stored GitHub repository `id` or by owner/name text could affect exact exploitability preconditions and should be verified directly in a full checkout.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
