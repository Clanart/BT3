## #VulnerabilityFound

### Title
Clone-time symlink/hooks protection deliberately disabled via `GIT_CLONE_PROTECTION_ACTIVE=false`, re-opening CVE-2024-32002 RCE - (`app/src/lib/git/clone.ts`)

### Summary
`clone()` in [1](#0-0)  builds the environment for every `git clone --recursive` invocation and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. This environment variable is the actual Git-core kill switch that upstream Git added as the fix/mitigation for CVE-2024-32002 (the "clone with recursive submodules leads to RCE via crafted `.git/hooks` path collision on case-insensitive/case-normalizing filesystems" bug). Git's protection is normally *active by default* in patched Git versions; forcing this variable to `'false'` disables that protection unconditionally for every Desktop-initiated clone, regardless of the Git binary's version or default configuration.

### Finding Description
The relevant code:
```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
...
await git(args, __dirname, 'clone', opts)
``` [2](#0-1) 

`--recursive` causes Git to immediately clone all submodules as part of the top-level clone. CVE-2024-32002 exploited the fact that a submodule whose name/path is engineered to collide with `.git`, `.git/hooks`, or similar paths (particularly on case-insensitive filesystems like default macOS/Windows) could cause Git to write files into the parent repository's `.git/hooks` directory during the recursive submodule clone. Upstream Git shipped a fix that performs additional path-collision checks during clone, gated by this exact protection mechanism (surfaced to users/embedders via `GIT_CLONE_PROTECTION_ACTIVE`). By setting the variable to the literal string `'false'` on every clone, Desktop is not merely failing to enable a mitigation — it is actively force-disabling a security check that a properly patched Git binary would otherwise perform by default.

The path traversal guard `isClonePathSensitive()` at [3](#0-2)  only validates the top-level destination directory chosen by the user; it does nothing to prevent a malicious nested submodule inside the cloned repository from writing into `<clone-path>/.git/hooks` once the protection is turned off.

### Impact Explanation
An attacker who controls a remote repository (fully within the stated threat model: "repository content ... attacker controls a cloned/fetched repository") can craft a submodule whose declared path collides with `.git/hooks` (or a path that normalizes to it on case-insensitive filesystems). With protection disabled, cloning that repository with GitHub Desktop can result in a hook script (e.g., `post-checkout`, `pre-commit`) being written into the victim's real `.git/hooks` directory. Because Desktop and subsequent Git operations (checkout, commit, etc.) will execute repository hooks, this leads directly to arbitrary code execution on the victim's machine outside the intended repository content scope — satisfying "code execution ... outside the repo" in the Valid Impact criteria.

### Likelihood Explanation
Likelihood is high: the only prerequisite is that the victim clones an attacker-supplied repository URL in GitHub Desktop, which is squarely within Desktop's core, expected user workflow (no unnatural steps, no local access, no malware pre-required). `--recursive` is unconditionally passed for all clones, so every clone performed through this function is affected, and the disabling environment variable is applied unconditionally as well — there is no code path where the protection remains active.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Either omit the variable entirely (allowing Git's built-in default, which is protection-enabled on patched versions) or explicitly set it to `'true'`/leave unset, and ensure the bundled/embedded Git dependency is a version that contains the CVE-2024-32002 fix. If there is a legitimate reason certain trusted internal clone flows need protection relaxed, that decision must never apply to arbitrary user-supplied/attacker-controlled remote URLs.

### Proof of Concept
1. Prepare a malicious remote repository containing a submodule entry (in `.gitmodules`) whose `path` is crafted to case-fold/normalize to `.git/hooks` on the target filesystem (the same technique used in public CVE-2024-32002 PoCs), with the submodule's payload being a script named after a hook Git will execute (e.g. `post-checkout`).
2. Have the victim clone this repository's URL via GitHub Desktop (`clone()` in `app/src/lib/git/clone.ts`), which runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment.
3. Because the protection check is disabled, Git writes the submodule content into the real `.git/hooks` directory of the cloned repository instead of rejecting/aborting the clone.
4. Any subsequent Git operation that triggers the corresponding hook (performed automatically by Desktop, e.g. on checkout) executes the attacker's script, achieving code execution on the victim's machine.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
```
