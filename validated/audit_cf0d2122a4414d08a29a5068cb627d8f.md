### Title
Empty DLEq statement allows forged proof acceptance - (File: crypto/dleq/src/lib.rs)

### Summary
`DLEqProof::verify` accepts an empty `generators`/`points` pair because it only checks that their lengths are equal. An attacker can calculate the transcript challenge for the empty statement, serialize it as `c`, provide any canonical `s`, and have the forged proof accepted.

### Finding Description
`verify` rejects mismatched input lengths, but does not reject the zero-length case. When both slices are empty, the loop at `crypto/dleq/src/lib.rs:171-173` adds no generator, nonce, or point commitments to the transcript. Verification therefore only requires `self.c == challenge(transcript)` after the `dleq` domain separator. [1](#0-0) 

`DLEqProof::read` accepts attacker-controlled canonical encodings for both `c` and `s` without semantic validation. [2](#0-1)  The challenge is deterministically derived from the transcript, so an unprivileged party can compute the required `c` for an empty statement offline. [3](#0-2) 

### Impact Explanation
This permits a forged DLEq proof for an empty statement to be accepted by any reachable verifier path that does not independently enforce a non-empty relation. In a protocol that treats proof acceptance as authorization to continue a key-linkage or recovery operation, the attacker can pass proof verification without demonstrating knowledge of any shared discrete logarithm.

### Likelihood Explanation
The attack requires only public proof bytes and empty public input vectors. No private key, malformed encoding, malicious validator, or collision is needed. The serialized proof is fully controlled through `DLEqProof::read`, while the missing non-empty check makes acceptance deterministic.

### Recommendation
Reject empty statements in `DLEqProof::verify` before comparing lengths or before transcripting:

```rust
if generators.is_empty() || generators.len() != points.len() {
  return Err(DLEqError::InvalidProof);
}
```

Consider the same explicit validation for every public verifier API that iterates over a caller-provided statement list.

### Proof of Concept
Conceptually:

```rust
// Build the same transcript used by the verifier.
let mut transcript = verifier_transcript();

// Since generators/points are empty, the transcript contains only
// domain_separate(b"dleq") before challenge generation.
// Calculate that challenge and encode it as `proof_c`.
let proof_bytes = proof_c_encoding || arbitrary_canonical_s_encoding;

let proof = DLEqProof::<G>::read(&mut proof_bytes.as_slice()).unwrap();
assert!(proof.verify(&mut transcript, &[], &[]).is_ok());
```

Because no per-generator statement is appended, every `s` is equivalent and only the publicly computable `c` must match.
