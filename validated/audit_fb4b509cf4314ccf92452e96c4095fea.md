## Title
Silent auto-rewrite of a repository's `origin` remote to an attacker-influenced GitHub API `clone_url`, without host-identity verification — ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The upstream report's broken invariant is: an address (`CURVE_POOL`) can be changed by a privileged action, but the invariant that dependent state (`token.approve()`) tracks that address is not maintained, so the system silently operates on stale/incorrect trust assumptions. The Desktop analog is `updateRemoteUrl()`, which silently rewrites a repository's local git remote URL to whatever `clone_url` the GitHub API returns for the matched repository, verifying only that the URL's *protocol* stayed the same — never that the *host* or repository identity chain is trustworthy beyond what the API happened to report.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` in `app/src/lib/stores/app-store.ts` periodically re-associates a local repository with its GitHub counterpart by calling `api.fetchRepository(owner, name)` and, if the repository already has a `gitHubRepository`, invoking `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

`updateRemoteUrl` then compares the *previously stored* `gitHubRepository.cloneURL` against the *current* local remote to decide if the remote was "manually changed", and if not, force-updates it to the freshly fetched `apiRepo.clone_url` — gated only by a same-protocol check, not a same-host check: [2](#0-1) 

This mirrors the "no way to set approval after setting new address" defect class: the trusted "address" (the local `origin` remote used for every subsequent `push`/`fetch`) is silently swapped out to match a value the app fetched from a network API object, with no independent verification that the new host is the one the user actually intends to keep pushing their code to. `urlMatchesRemote()` only checks scheme/host/owner/name structurally, it does not pin to the account/host that originally authenticated the repository: [3](#0-2) 

Once the remote is rewritten, the credential lookup path (`findGitHubTrampolineAccount` / `findGenericTrampolineAccount` in `app/src/lib/trampoline/find-account.ts`) determines what account/token to hand to Git purely by matching the *new* remote's origin: [4](#0-3) 

so a rewritten remote pointing at a different, API-controlled host can cause the next `git push`/`git fetch` to silently target that host instead of the one the user configured, and depending on account matching, either send code to the wrong destination or prompt for/leak credentials tied to the new host.

### Impact Explanation
This falls into "silent corruption of what the user commits or pushes": the user believes they are pushing to the remote they configured, but Desktop's background refresh logic (`repositoryWithRefreshedGitHubRepository`, invoked opportunistically e.g. from `withRefreshedGitHubRepository`) can rewrite `origin` based on API data without any user confirmation or diff/host-change warning shown in the UI. There is no dialog equivalent to `RepositorySettings`'s manual remote-URL change flow — the automatic path bypasses user review entirely.

### Likelihood Explanation
Exploitation requires the attacker to control the `clone_url` value returned by `api.fetchRepository(owner, name)` for the specific `owner/name` matched to the user's local remote (e.g., via a malicious/compromised GitHub Enterprise Server the user has signed into, or a MITM'd API response on an unencrypted/misconfigured enterprise endpoint). This is a real, network/API-object-controlled surface as called out in scope, but it is narrower than a fully unauthenticated attack since it depends on the user's own account/enterprise endpoint serving a manipulated repository object; for github.com itself the host in `clone_url` cannot be attacker-chosen. Likelihood is therefore moderate and scoped mainly to GHE/self-hosted or MITM scenarios, not a universal github.com issue.

### Recommendation
Before silently rewriting `origin`, verify that the new `clone_url`'s hostname matches the hostname of the account/endpoint used to fetch it (i.e., pin to `account.endpoint`'s host, not just protocol), and/or surface a confirmation prompt to the user when the remote's host would change as a result of an automatic refresh, mirroring the manual `RepositorySettings` flow which requires explicit user action.

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop and clone a repo `org/repo` from it, creating `origin` = `https://ghe.example.com/org/repo`.
2. Have the (malicious or compromised) GHE instance's `GET /api/v3/repos/org/repo` response return `clone_url: "https://ghe.example.com/org/repo-attacker"` (same host/protocol, different path — well within the current checks) — or, in a MITM scenario against a non-TLS-pinned enterprise deployment, an entirely different but protocol-matching URL.
3. Desktop's periodic `repositoryWithRefreshedGitHubRepository` refresh calls `updateRemoteUrl`, which sees `protocolsMatch && remoteUrlUnchanged && !urlsMatch` and silently runs `git remote set-url origin <new-url>` via `gitStore.setRemoteURL` — [5](#0-4)  — with no user-visible confirmation.
4. The next `git push` from the user goes to the attacker-designated destination/path instead of the one the user originally set up.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
