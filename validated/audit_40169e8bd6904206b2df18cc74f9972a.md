### Title
SchnorrAggregate verification weights do not bind public keys or nonces, enabling signature forgery - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the AWS CLI advisory (verification of the counterparty identity omitted, enabling impersonation/MITM), `SchnorrAggregate::verify` computes each per-signature scalar weight `z_i` from a transcript that commits **only to the challenges**, never to the public keys or the nonces `R_i`. The aggregation weight is therefore not bound to the statement being proven, so a forged aggregate signature can be constructed that verifies under an arbitrary public key, given a single valid Schnorr signature under any key sharing the same challenge.

### Finding Description
In `SchnorrAggregate::verify`, the digest is initialized with `dst` and `domain_separate(b"signatures")`, then only each `challenge` is appended:

- `crypto/schnorr/src/aggregate.rs:132-136` — `digest.append_message(b"challenge", challenge.to_repr())` is the only per-statement input; the keys `C::G` and nonces `self.Rs[i]` are never transcripted.
- `crypto/schnorr/src/aggregate.rs:138-145` — the check is `multiexp_vartime` over `(z_i, R_i)`, `(z_i * c_i, A_i)`, `(-s, G)`, requiring `Σ z_i·R_i + z_i·c_i·A_i − s·G == 0`.

Because `z_i = weight(dst, domain, c_1..c_n)` depends only on the challenges (attacker-observable verifier inputs), the attacker can compute every `z_i` locally and then choose `Rs` and `s` adaptively to satisfy the linear relation under any key.

The sibling `SchnorrAggregator::complete` has the identical flaw (aggregate.rs:169-185): it appends only `challenge` per signature, so honest aggregation and verification share the same broken weights, meaning the forgery works end-to-end against the real verifier path.

### Impact Explanation
Given any valid Schnorr signature `(R, s)` verifying `s·G = R + c·A` under some key `A` and challenge `c`, an unprivileged attacker can produce a `SchnorrAggregate` that `verify` accepts for `(key = B, challenge = c)` for an arbitrary `B` of the attacker's choosing:

- `z = weight(dst, c)` (computable by the attacker since it depends only on public values),
- `R' = R + c·(A − B)`,
- `s' = z·s`.

Then `z·R' + z·c·B = z·(R + c·A − c·B) + z·c·B = z·(R + c·A) = z·s·G = s'·G`. The forged aggregate verifies under a key the attacker does not control — a forged signature on an unintended key, the exact analog of skipping host-key/identity verification. This scales to re-targeting signatures across keys and enables cross-key malleability between statements within a batch, since `Rs` and keys are interchangeable under unchanged weights.

### Likelihood Explanation
An attacker needs only one observed valid signature `(R, s)` and its challenge `c` for some key — all public data. The weight function is deterministic over public inputs, so no secret knowledge or privileged position is required. Any consumer calling `SchnorrAggregate::verify` / `SchnorrAggregator::complete` on attacker-supplied aggregate bytes (`SchnorrAggregate::read`, aggregate.rs:77-88) reaches the vulnerable formula.

### Recommendation
Transcript the full statement per signature — the public key, the nonce `R_i`, and the challenge (e.g., `append_message(b"key", key.to_bytes())`, `append_message(b"nonce", R.to_bytes())`, `append_message(b"challenge", ...)` inside the same loop) — in both `SchnorrAggregate::verify` and `SchnorrAggregator::aggregate`, so `z_i` binds `(R_i, A_i, c_i)` as required by half-aggregation (eprint 2021/350 §3.2, which hashes `(pk_i, m_i, R_i, i)` into each coefficient).

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {

      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }
