## Analysis

The external report's broken invariant is: **a security‑sensitive value (an approval/permission) is overwritten based on a new input without confirming/resetting the trust state first**, allowing an attacker-influenced value to be silently accepted on the second write.

The closest real analog in GitHub Desktop is in `updateRemoteUrl()`, which silently rewrites the local `origin` git remote URL using the `clone_url` field returned from the GitHub API — with no user confirmation — whenever the app decides the "trust" heuristic passes.### Title
Silent, unconfirmed rewrite of the `origin` remote URL from an untrusted GitHub API field - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl()` rewrites a repository's `origin` remote URL to whatever `clone_url` value the GitHub API returns for the matched repository, and it does so silently — no user prompt, no confirmation dialog — as long as a small set of loose heuristics pass. This mirrors the report's broken invariant: a security‑relevant value (here, the destination of all future `git push`/`git fetch` traffic) is overwritten based on externally supplied data without the equivalent of the "reset/confirm before commit" step that the codebase itself uses elsewhere for the conceptually identical upstream-remote case.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches repository metadata from the GitHub API keyed off the owner/name parsed from the existing `origin` remote, and unconditionally feeds the response into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then calls `gitStore.setRemoteURL(...)`, which directly executes `git remote set-url` with no user-facing confirmation of any kind: [2](#0-1) [3](#0-2) [4](#0-3) 

The only gates before this silent rewrite are:
- `protocolsMatch` — only checks that `http(s)`/`ssh` protocol strings are equal, not that the host/owner is trustworthy.
- `remoteUrlUnchanged` — checks the *current* remote still structurally matches the previously cached `cloneURL` (host+owner+name), via `urlMatchesRemote`, which itself only compares parsed hostname/owner/name strings, not any cryptographic identity of the repository: [5](#0-4) 
- `!urlsMatch` — skip if nothing changed.

None of these guards verify that the *new* `clone_url` still refers to the same underlying repository object (e.g., a stable repo ID) — they only check string-level host/owner/name equality against the old cached value, which is exactly the value being replaced. Once these string-only heuristics pass, the new attacker-influenced `clone_url` is written to disk via `git remote set-url` with **zero user confirmation**.

This is inconsistent with how Desktop treats the analogous *upstream* remote: when the fork's upstream remote diverges from the parent's expected clone URL, Desktop explicitly shows a confirmation dialog (`UpstreamAlreadyExists`) and lets the user choose "Update" or "Ignore": [6](#0-5) [7](#0-6) 

No equivalent confirmation exists for the `origin` remote path — the write happens automatically inside a background refresh (`repositoryWithRefreshedGitHubRepository`), which is invoked from routine operations such as fetch/pull/push flows.

### Impact Explanation
`origin`'s URL is the destination for every subsequent `git push` and the source for every `git fetch`/`git pull`. Silently repointing it means:
- Future pushes can be silently redirected to a different remote, exfiltrating the user's (possibly private) source code to a location the user never approved.
- Future fetches/pulls can silently pull content from a different remote than the one the user originally cloned, corrupting the working tree/history the user believes they are working with — this is "silent corruption of what the user commits or pushes," an explicitly listed valid impact category.
- Because the credential helper resolves credentials per-host (`app/src/lib/trampoline/trampoline-credential-helper.ts`), a changed host also changes which stored credential/token gets sent, which can leak a token/credential to a different, attacker-influenced host if the new `clone_url` points at a different domain accepted by the loose `urlMatchesRemote` string comparison.

### Likelihood Explanation
The trigger condition (a matched GitHub API response whose `clone_url` differs from the current remote while the remote otherwise looks "unchanged" from the last cached value) is reachable any time Desktop revalidates GitHub repository metadata — which happens routinely during normal fetch/push/pull cycles via `repositoryWithRefreshedGitHubRepository`. This function runs automatically and unconditionally on background refreshes, requiring no unusual user action. The report's required attacker primitive — control over a GitHub API object returned to the client (e.g., a compromised/malicious GitHub Enterprise Server, a repository-transfer/rename scenario, or a MITM'd/altered API response on an environment where the API endpoint is not the hardened dotcom endpoint) — is exactly the kind of primitive the task explicitly allows ("attacker controls...a GitHub API object").

### Recommendation
Treat a change to `origin`'s resolved clone URL the same way the upstream-remote case is already treated: never call `gitStore.setRemoteURL` automatically from `updateRemoteUrl`. Instead, surface a confirmation dialog (reusing the pattern in `upstream-already-exists.tsx`) showing the current vs. proposed URL and only rewrite the remote after explicit user approval. Additionally, strengthen `urlMatchesRemote`/`urlsMatch` to require a stable repository identifier (e.g., API repository `id`) match rather than relying solely on string comparison of hostname/owner/name, since those are exactly the fields an attacker-controlled API response can manipulate.

### Proof of Concept
1. User has `origin` set to `https://ghe.example.com/acme/app.git`, tracked in Desktop as a GitHub repository with cached `cloneURL = https://ghe.example.com/acme/app.git`.
2. Attacker with control of the GHE server's API responses (or any environment where `repos/{owner}/{name}` can be influenced) returns an `IAPIFullRepository` object for the same owner/name whose `clone_url` is `https://ghe.example.com/acme-mirror/app.git` (or any URL that still parses to a matching hostname/owner/name under `urlMatchesRemote`'s loose comparison, but is actually attacker-controlled infrastructure).
3. On the next background refresh (e.g., triggered by `_fetch`, `_pull`, or `_push` calling `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository`), `updateRemoteUrl` is invoked with this API object.
4. Because `protocolsMatch` is true and `remoteUrlUnchanged` is true (remote still matches the old cached value) and `urlsMatch` is false (new URL differs), `gitStore.setRemoteURL` is called and `git remote set-url origin <attacker-url>` executes with **no dialog, no confirmation, no log visible to the user**.
5. The next `git push`/`git fetch` from Desktop silently talks to the attacker's endpoint instead of the user's real remote. [8](#0-7)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
