### Title
Overfill loss-bound clamp is disabled in the Simplex filler's pricing path, letting a single order drain the solver's full balance instead of the documented 5% cap - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The external report describes a protective threshold (a liquidation/health check meant to bound loss) being effectively neutralized so that losses accumulate far beyond the intended bound before any corrective action fires. The same pattern exists in Hyperbridge's reference Intent Gateway solver ("Simplex"): the documented `maxOverfillBps` per-leg loss bound is explicitly disabled in code, turning what should be a hard cap into a log-only warning.

### Finding Description
The `HyperFX` strategy's `calculateProfitability` computes a `rawPolicyMaxOutput` per order leg from pair/venue pricing, then is documented and configured to clamp it to `(1 + maxOverfillBps) × user-requested amount` (default 5%) as a bound against "a bug, stale cache, or manipulated venue" price [1](#0-0) .

In the actual implementation, this clamp is commented out and intentionally disabled: [2](#0-1) 

`policyMaxOutput` is set equal to the unclamped `rawPolicyMaxOutput`, and only a warning is logged when the overfill ceiling would have been exceeded. The only remaining limiter on `finalOutputAmount` is the filler's own wallet + funding-venue balance: [3](#0-2) 

Because pricing for at least one leg type is sourced from an on-chain venue (Uniswap V4, per the docs: "including venue-priced legs (e.g. Uniswap V4)"), a stale cache, an oracle/pool-price manipulation, or a pricing bug directly inflates `rawPolicyMaxOutput` with no ceiling. Previously the 5% cap bounded the blast radius of any single bad price to 5% of the user-requested amount per leg; with the clamp removed, the only bound is "however much balance the filler happens to be holding," which the code explicitly funds via wallet balance plus vault withdrawals up to `policyMaxOutput` [3](#0-2) .

### Impact Explanation
This mirrors the report's core broken invariant: a safety check that used to gate the magnitude of loss during abnormal pricing conditions has been disabled, so the protocol/operator absorbs losses that scale with available liquidity rather than with a designed small percentage. For the Simplex filler, this converts a bounded ("5% per leg, self-halting after 3 consecutive clamp events") loss surface into an unbounded one gated only by wallet+vault balance — i.e., a single adversarial or degraded-price order can drain the filler's fillable balance in one fill instead of being capped and triggering the `HyperFX` self-halt safety mechanism (which only fires when the clamp itself activates, and cannot activate because the clamp is disabled).

### Likelihood Explanation
The trigger conditions are exactly those the original safeguard was designed for and that the report also flags: stale cache, pricing bug, or a manipulated pricing venue. An order requesting a token pair priced off a manipulable/thin-liquidity venue (e.g., a low-liquidity Uniswap V4 pool) is sufficient to inflate `rawPolicyMaxOutput`; no privileged actor, relayer collusion, or front-running is required — an ordinary order placed by any user against a mispriced/manipulated venue triggers the unclamped fill path.

### Recommendation
Re-enable the `maxOverfillBps` clamp so `policyMaxOutput` is hard-capped at `(1 + maxOverfillBps) × output.amount` rather than only logging a warning, and ensure the `maxConsecutiveClamps` self-halt logic in `HyperFX` can still observe and react to clamp events. If unclamped filling is intentionally desired for competitiveness on some venues, gate it behind an explicit, narrowly-scoped opt-in per pair/venue rather than a blanket global disablement, and add a hard per-order/per-block absolute loss ceiling independent of wallet balance.

### Proof of Concept
1. Configure a `HyperFX` pair leg priced from a Uniswap V4 venue with thin liquidity.
2. An attacker (any unprivileged Intent Gateway user) manipulates the pool price momentarily (or exploits a stale price cache) so that the venue-derived rate makes `rawPolicyMaxOutput` for the requested leg far exceed `output.amount` (the user's requested amount).
3. `calculateProfitability` computes `overfillCeiling = output.amount × (1 + maxOverfillBps) / 10000` but does not apply it — `policyMaxOutput = rawPolicyMaxOutput` per [4](#0-3) .
4. The filler proceeds to source `policyMaxOutput` from wallet balance and configured funding venues (vault withdrawals) up to that amount [3](#0-2) , and fills the order with `finalOutputAmount`, releasing far more value than the 5%-bounded design intended — up to the filler's full available liquidity for that token — for a single manipulated order.

Note: this analog lives in the off-chain reference solver (`sdk/packages/simplex`), not in an on-chain pallet/contract; I flag this uncertainty explicitly since the impact falls on solver/filler funds rather than protocol-custodied escrow, though the `IntentGatewayV2`/`ExtrinsicIntents` escrow-release paths that the filler interacts with were reviewed and did not show an equivalent disabled threshold.

### Overfill Protection

Bounds per-leg loss if the filler's internal pricing is wrong (bug, stale cache, manipulated venue). For every order, the filler clamps its computed output to at most `(1 + maxOverfillBps) × user-requested amount` — this ceiling applies to every strategy. After `maxConsecutiveClamps` consecutive orders where the clamp activated, the **HyperFX** strategy halts itself — a pattern that strongly suggests a systemic pricing error — and requires an operator restart. HyperFX additionally rejects any order where the total output USD value ≥ total input USD value.

Defaults are sensible (`maxOverfillBps = 500` ≈ 5% ceiling, `maxConsecutiveClamps = 3`). Override under `[simplex.overfillProtection]`:

```toml lineNumbers
[simplex.overfillProtection]
maxOverfillBps       = 500   # 5% ceiling above user-requested output
maxConsecutiveClamps = 3     # halt threshold (HyperFX)
