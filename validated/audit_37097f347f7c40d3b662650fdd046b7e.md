### Title
Copilot conflict resolution splices AI hunk output by position, not by content match, allowing prompt-injected/attacker-crafted repo content to silently corrupt the merged file that gets committed and pushed - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The external report's broken invariant is: a value that determines how untrusted data maps onto a fixed structure (`l2MerkleTreesDepth`) is checked for a superficial property (existence/type) but never checked for *structural correctness* against the real proof, so mismatches are silently accepted. The same class of bug exists in GitHub Desktop's Copilot-assisted merge-conflict resolution: the number of AI-returned "hunks" is validated to *match a count*, but nothing validates that hunk *i* in the model's response actually corresponds to conflict block *i* in the real on-disk file. Reassembly is purely positional.

### Finding Description
`reassembleResolvedFile` walks the raw file content, finds each well-formed `<<<<<<< / ======= / >>>>>>>` block, and splices in `hunkResolutions[hunkIndex]` purely by incrementing counter `hunkIndex` — there is no check that the resolved content it is inserting was actually generated for *that* conflict block: [1](#0-0) 

The only integrity check performed before this splice is `validateResolutionPaths`, which enforces that the *count* of returned hunks equals the *count* of hunks that were originally sent to the model — nothing about content or order: [2](#0-1) 

This is structurally identical to the LineaRollup bug: the "depth" (here, hunk count) is checked against an expected value, but is never bound to the actual proof (here, the real byte-for-byte identity/order of each conflict block). A count match gives false confidence that positions line up.

The conflict-marker sanity check on the model's returned content is also weak — it only rejects a hunk if it contains *both* a `<<<<<<< ` opener AND a `=======` separator; a stray or reordered partial marker slips through: [3](#0-2) 

The content fed to the model — file conflict hunks, commit messages, and PR titles/descriptions — is attacker-influenceable: any contributor who can get their branch merged/rebased/cherry-picked against, or who opens a PR/commit with a crafted description, controls text that ends up in the prompt via `formatConflictContextForPrompt` and is referenced by `extractPullRequestNumberFromCommitSummary`/`selectReferencedContext`. A prompt-injection payload embedded in a comment or commit message can attempt to make the model emit the *same number* of hunks (so `validateResolutionPaths` passes) but with hunk content shuffled, malformed, or containing attacker-chosen substitutions — with no mechanism downstream to detect that hunk *N* no longer corresponds to conflict block *N*.

Once resolutions pass validation, the user (via the "Continue Merge" button) writes the reassembled content straight to disk and stages it: [4](#0-3) [5](#0-4) 

### Impact Explanation
If hunk-to-block correspondence breaks (whether through prompt injection, model confusion on ordering, or a race where `ctx.rawContent` used for reassembly has drifted from the file state the hunk count was computed against), `reassembleResolvedFile` will silently splice the wrong resolved content into a wrong conflict location. Because `resolvedContent` is written to disk and `git add`-ed automatically, this results in silent corruption of what the user commits and pushes — the exact "silent corruption of what the user commits or pushes" impact class called out as valid. Given this runs during merge/rebase/cherry-pick conflict resolution, the corrupted region could reintroduce vulnerable code, drop a security fix from one side, or inject attacker-influenced code that a cursory diff review in the result dialog may not catch, especially across many files/hunks.

### Likelihood Explanation
Exploitation requires only that an attacker's branch, commit messages, or PR text (all attacker-controlled, ordinary GitHub objects) get pulled into a merge/rebase/cherry-pick that the victim resolves using "Resolve with Copilot." No local access, admin rights, or pre-existing malware is needed — just the ability to contribute content that eventually conflicts with the victim's branch, which is a normal collaborative workflow. The likelihood of a *successful, controlled* injection depends on the underlying LLM's susceptibility to the crafted payload, which introduces some non-determinism, but the count-only validation guarantees that a resulting mismatch is not caught by any Desktop-side guard.

### Recommendation
Bind each returned hunk resolution to the specific conflict block it was generated for, not just to an ordinal position:
- Have the model (or a wrapper) tag/reference each hunk with a stable identifier (e.g. hash or index tied to conflict marker content) sent in the prompt, and verify that identifier during reassembly, not just the total count.
- In `reassembleResolvedFile`, additionally verify that the resolved content doesn't merely omit markers but is plausible for the region being replaced (e.g., diffing sizes/content fingerprints against what was sent to the model for that specific block).
- Re-derive `expectedHunkCounts` from the same `rawContent` that `reassembleResolvedFile` will actually use, immediately before reassembly, to close the TOCTOU window between context-gathering and file writing.
- Tighten the conflict-marker leftover check in `parseCopilotConflictResolution` to catch any stray `<<<<<<<`, `=======`, or `>>>>>>>` marker independently, not only when both an opener and separator co-occur.

### Proof of Concept
1. Attacker opens a PR/branch whose commit message or file content (visible to the merge-conflict prompt builder) contains an injection payload instructing the model to "reorder hunk resolutions" or "always return N hunks regardless of true content match, filling extra slots with `<payload>`."
2. Victim merges/rebases/cherry-picks this branch, hits conflicts, and clicks "Resolve with Copilot."
3. `parseCopilotConflictResolution` accepts the response as long as JSON shape is valid; `validateResolutionPaths` accepts it as long as `hunks.length` per file matches the original count — it does not check that hunk order/content matches conflict block order/content. [2](#0-1) 
4. `reassembleResolvedFile` splices `hunkResolutions[0], [1], [2]...` into conflict blocks strictly by scan order, so if the model (successfully manipulated) returns them out of correspondence, the wrong content lands in the wrong block. [6](#0-5) 
5. The victim clicks "Continue Merge"; the corrupted file is written to disk and staged automatically, with no re-verification against the true conflict content. [7](#0-6)
