### Title
Group key "priced" from only the first `t` verification shares — shares for participants `t+1..=n` are never checked for consistency with it - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::new` derives the group key by interpolating only the verification shares of participants `1..=t`, while accepting arbitrary, unvalidated verification shares for participants `t+1..=n`. `ThresholdKeys::read` feeds attacker-controlled bytes straight into this constructor. This mirrors the Indexed Finance bug class: an aggregate "value" (here the group key / verification-share map, there the pool valuation) is computed from a subset of inputs while the remaining inputs are trusted without being proven to back that value. A crafted serialized `ThresholdKeys` therefore encodes verification shares that are unbacked by the group key — a participant index `> t` can be assigned `G*y` for any `y`, decoupled from the secret polynomial that produced the group key.

### Finding Description
In `ThresholdKeys::new`, the group key is computed as the Lagrange-interpolated sum over only participants `1..=t`: [1](#0-0) 

The only other checks are that `verification_shares.len() == n` and every index is `<= n` — there is no check that shares for indexes `t+1..=n` lie on the same polynomial that produced `group_key`. [2](#0-1) 

`ThresholdKeys::read` builds that map from raw untrusted bytes (one `read_G` per index `1..=n`) and calls `ThresholdKeys::new`, so a malicious or corrupted key blob is accepted with an inconsistent share map. [3](#0-2) 

When such keys are later used, `view()` takes `self.core.verification_shares[i]` for each `i` in `included` and interpolates it, so a participant index `> t` carries a verification share that was never anchored to the group key. [4](#0-3) 

Inside an honest PedPoP run this cannot happen, because `calculate_share` derives every verification share from the summed commitment stripes. [5](#0-4) 

The inconsistency exists only for `ThresholdKeys` materialized from bytes (`read`/`BorshDeserialize`/`ThresholdKeys::new` on integrator-supplied data) — exactly the "trusted-but-unbacked input" shape of the Indexed mint.

### Impact Explanation
An attacker who can influence the bytes a validator loads as `ThresholdKeys` (restored state, coordinator-supplied key material, imported shares) can craft a key set whose group key `A` is well-formed, while participant `j > t` has secret share `s` and verification share `j*G` chosen so `s` passes per-share verification in any signing session — yet `s` has no relation to `A`. The result is a key that *appears* valid (deserialization succeeds, group key looks normal) but whose shares for indexes `> t` are worthless or, conversely, whose secret share silently belongs to a different key than the public group key. Funds received at `group_key()` are unspendable by the holder of the manipulated share, and a signature produced in a set including such a participant fails only at aggregation time — a state the code itself acknowledges is reachable via "a semantically invalid FrostKeys" deserialization. [6](#0-5) 

Because the key blob is accepted wholesale before any signing, the corruption is detected only after value has been attributed to the group key — analogous to Indexed minting index tokens against balances that were never actually backed.

### Likelihood Explanation
Reachability requires untrusted bytes reaching `ThresholdKeys::read` or `ThresholdKeys::new` — listed as an in-scope public input. Many integrators persist and reload `ThresholdKeys` (the `serialize`/`read` pair exists for exactly this), and any path where those bytes are attacker-influenced (compromised backup, replicated state, coordinator-distributed material) triggers it. No threshold collusion or malicious participant in the DKG is needed — the DKG itself produces consistent shares; the flaw is purely that deserialization does not re-derive consistency for indexes `> t`. Severity is bounded by requiring influence over stored key material rather than a pure network message, hence Medium rather than Critical.

### Recommendation
In `ThresholdKeys::new` (or in `read` for the Lagrange case), re-derive the group key using a *different* `t`-sized subset (or verify that the interpolation over all `n` shares is consistent — e.g., check `group_key` equals interpolation of shares `n-t+1..=n`, or evaluate each remaining share against the polynomial implied by the first `t`). This forces every verification share in the map to be backed by the same secret that `group_key` commits to, closing the unbacked-share gap.

### Proof of Concept
For a `(t=2, n=3, i=3)` key over any `C`:

1. Choose scalars `a, s` and a group key `A`. Construct `verification_shares` where indexes 1 and 2 are arbitrary points whose Lagrange interpolation yields `A` (e.g., `V1 = A` via index-1/2 factors, `V2 = 0` adjusted accordingly — concretely set `V1 = 2A`, `V2 = A` so `2*V1 - V2... ` solve the two-equation system for target `A`), and set `V3 = s*G` where `s` is unrelated to `A`.
2. Serialize: curve ID header, `t=2`, `n=3`, `i=3`, interpolation byte `1` (Lagrange), `secret_share = s`, then `V1, V2, V3` via `write`/`read_G` format.
3. `ThresholdKeys::<C>::read` accepts it: length is `n`, all indexes `<= n`, `group_key = A`.
4. `keys.view(vec![1,3])` (or any set containing 3) builds verification shares using the bogus `V3`; a signing session completed with this participant yields a signature that fails `algorithm.verify`, or — if the attacker also picked `s` to satisfy their own verification share — produces a share validating against `V3` while contributing nothing toward a signature under `A`. The key holder believes they co-own `A` while holding a share of an unrelated secret.

The root cause is the one-sided valuation in `ThresholdKeys::new`: `group_key` is "priced" exclusively by indexes `1..=t`, leaving `t+1..=n` unbacked — the same structural mistake as Indexed Finance computing mint price from a balance that was never reconciled against actual backing.
