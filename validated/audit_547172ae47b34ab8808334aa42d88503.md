### Title
`ThresholdKeys::read` accepts attacker-chosen interpolation coefficients and an inconsistent secret share, allowing key substitution - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2013-0156 is a parser that trusts attacker-declared type metadata (YAML/Symbol tags in XML), letting input coerce objects into unintended representations. The analog in Serai is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`: a single tag byte switches the `Interpolation` representation between `Constant(Vec<F>)` and `Lagrange`, and in the `Constant` case the deserializer reads `n` fully attacker-controlled field elements that become the per-participant combination weights. Neither `read` nor `ThresholdKeys::new` verifies that `secret_share` corresponds to `verification_shares[params.i()]`, and there is no check that the verification shares arise from any polynomial — so an attacker supplying serialized keys fully dictates both the resulting `group_key` and every participant's interpolation factor.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, then a tag byte: `0` reads `n` scalars into `Interpolation::Constant`, `1` yields `Interpolation::Lagrange` (`crypto/dkg/src/lib.rs`, lines 604-616). It then reads `secret_share` and `n` verification shares and calls `ThresholdKeys::new` (lines 618-631).

`ThresholdKeys::new` only checks:
- `verification_shares.len() == n` and all indices `<= n` (lines 355-365),
- `Constant` requires `t == n` (lines 367-374).

It then computes `group_key` as `sum_{i in 1..=t} verification_shares[i] * interpolation_factor(i, [1..=t])` (lines 376-378), where for `Constant`, `interpolation_factor` is just `c[i - 1]` — the attacker-supplied coefficients (lines 226-229).

What is missing:
1. **No share consistency check.** `generator * secret_share == verification_shares[i]` is never verified. A crafted blob stores any secret share alongside unrelated verification shares.
2. **Attacker-controlled weights.** `Interpolation::Constant` coefficients come straight off the wire, so `interpolation_factor` for every participant is attacker-chosen. This re-interprets the exact bytes an honest Lagrange-serialized key would occupy into a different algebra (coefficient list vs. Lagrange basis) — the same "the parser trusts the embedded type tag to pick a representation" shape as CVE-2013-0156.
3. **Resulting `group_key` is unconstrained.** Since verification shares and coefficients are all attacker input, `group_key` can be set to any point, including a key whose discrete log the attacker knows.

### Impact Explanation
`ThresholdKeys` is the root object driving FROST signing (`view()` derives `ThresholdView` using `interpolation_factor` and `group_key`, lines 463-533) and Bitcoin scanning (`Scanner::new(key)` / `register_offset` derive the deposit `script_pubkey` from `group_key`, `networks/bitcoin/src/wallet/mod.rs` lines 162-196). If untrusted bytes reach `ThresholdKeys::read` — e.g., key recovery/import paths or any storage an attacker can influence — the attacker supplies a blob whose `group_key()` is a key they control outright. Deposits scanned against that group key are reported to the protocol as multisig-controlled while being spendable solely by the attacker: funds reported received that the threshold group cannot spend. Additionally, inconsistent `secret_share`/verification data causes every signing session under the loaded keys to attribute blame to honest participants or abort, and crafted `Constant` coefficients let a single share dominate the combined signature weight.

### Likelihood Explanation
Severity is bounded by reachability: this requires attacker control over bytes fed to `ThresholdKeys::read` (a persistence/import boundary). Where that boundary is trusted local storage, impact is limited; where serialized keys cross a trust boundary (recovery, migration, backup restore), a malformed blob is silently accepted because all length, participant-index, and canonical-encoding checks pass — nothing in the format binds keys to the PedPoP/MuSig transcript that produced them. Severity: Medium (High only if the serialization is network/import-reachable in the deployment).

### Recommendation
- In `ThresholdKeys::new`, verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise.
- For `Interpolation::Constant`, either reject it in `read` when the key didn't originate from a MuSig-style flow, or bind the coefficients to an expected derivation (e.g., recompute binding factors from the verification shares and compare) instead of trusting wire-supplied weights.
- Consider committing the expected `group_key` into the serialized form and verifying it matches the recomputed interpolation.

### Proof of Concept
1. Attacker chooses scalar `k`, computes `A = G * k` (a key they fully control).
2. Craft serialized `ThresholdKeys<Secp256k1>`: `t = n = 2`, `i = 1`, interpolation tag `0`, coefficients `[1, 1]`, `secret_share = 1` (arbitrary), verification shares `[A, X]` for any `X` — so `group_key = A*1 + X*1`; choose `X = 0`-adjusted values or simply set shares so the sum equals `A` (e.g., `verification_shares = [A, identity]` is rejected for identity on FROST curves, so use `c = [1, 0]` and shares `[A, any]`).
3. `ThresholdKeys::read` accepts the blob; `keys.group_key() == A`.
4. A scanner built on `keys.group_key()` reports deposits to `p2tr(A)` as received multisig outputs — spendable only by the attacker holding `k`.
