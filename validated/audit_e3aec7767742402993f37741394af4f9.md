The Tron deployment of `IntentGatewayV2.sol` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not carry over the fee-on-transfer accounting fix that exists in the main EVM version, making it the direct local analog of the USDT `transferFrom` fee bug.

### Title
Escrow bookkeeping in Tron `IntentGatewayV2.placeOrder` is not corrected for fee-on-transfer tokens, allowing insolvency and cross-order fund theft - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`placeOrder()` computes the order commitment and the escrow credit (`reducedInputs`/`_orders[commitment][token]`) from the caller-supplied `order.inputs[i].amount` *before* any token transfer happens, and then pulls tokens with a plain `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`. For any token that charges a fee on transfer (USDT-style deflationary/fee tokens), the contract actually receives less than `order.inputs[i].amount`, but still credits the full (fee-reduced-only-by-protocol-fee) amount to `_orders[commitment][token]`. This inflates the gateway's internal escrow ledger beyond its real token balance.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

the commitment/`reducedInputs` were already computed earlier from the raw requested amount: [2](#0-1) 

Unlike this, the primary EVM `IntentGatewayV2.sol` explicitly measures the *actual* balance received before crediting escrow or hashing the commitment, exactly to defend against this class of bug: [3](#0-2) [4](#0-3) 

This fix is verified by dedicated tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, etc.): [5](#0-4) 

The Tron contract has no equivalent balance-before/after check anywhere in its escrow path, so for a fee-on-transfer ERC-20 the ledger entry `_orders[commitment][token]` will be larger than what the contract actually holds for that order.

### Impact Explanation
`withdraw()` pays out strictly from the requested `body.tokens[i].amount` against the ledger, and simply decrements `_orders[body.commitment][token]` — it never checks the contract's real token balance: [6](#0-5) 

Because every order placed with a fee-on-transfer token books more escrow than it actually funded, the aggregate liability recorded across all orders' `_orders[...]` entries exceeds the token balance actually held by the contract. Any solver/beneficiary who is paid out for such an order is, in effect, paid using tokens that belong to the escrow of other, unrelated orders — a direct loss/theft of other users' bridged/escrowed funds once the shortfall is drawn down. This is the same broken invariant as the reported USDT bug ("contract can have less than the recorded/expected amount because of transfer fees"), just relocated to intent escrow bookkeeping instead of a credit account.

### Likelihood Explanation
Exploitation requires only an unprivileged user calling the public `placeOrder()` with any ERC-20 that deducts a fee on `transferFrom`/`transfer` (fee-on-transfer tokens are common and can also be introduced by tokens that change fee parameters after listing, or via non-standard tokens accepted permissionlessly since `placeOrder` does not restrict input tokens). No relayer, prover, or admin collusion is needed — a normal order flow with a normal (if non-standard) ERC-20 triggers the shortfall automatically on every such order.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom` in `placeOrder`, use the actual delta (not the requested amount) to compute `reducedInputs`/protocol fee and to build the commitment hash, and only credit `_orders[commitment][token]` with that actually-received, fee-adjusted amount.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a 1% fee-on-transfer token (e.g., the `FeeOnTransferToken` mock used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. User A calls `placeOrder` requesting `inputs[0].amount = 1000e18` of the FOT token; the gateway actually receives only `990e18`, yet `_orders[commitmentA][token]` is credited with `~1000e18` (minus only the protocol fee), i.e. it books 10e18 more than it holds.
3. Repeat with User B's order — the ledger keeps overstating held balance by ~1% per order.
4. Once enough orders accumulate this deficit, a beneficiary/solver settling any one order via `withdraw()` (called from `onAccept`/`cancelOrder`/`onGetResponse`) is paid the full booked amount even though the contract's real FOT balance is insufficient to cover all outstanding `_orders[...]` entries — later legitimate withdrawals for other orders will fail or be shorted, i.e. funds are effectively drained from other users' escrow.
