### Title
Unbounded DID metadata accepted and persisted to the wallet database without size limits - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
The `did_update_metadata` wallet RPC endpoint accepts an arbitrary-size `dict[str, str]` and writes it directly to the local wallet SQLite database via `DIDWallet.update_metadata()`, with no length validation on keys or values, unlike other similar wallet features (e.g. notification messages, keyring labels) that impose explicit size caps.

### Finding Description
`DIDUpdateMetadata.metadata` is declared as an unconstrained `dict[str, str]` in the wallet request type [1](#0-0) , and the RPC handler passes it straight through to the wallet layer without any bound checks: [2](#0-1) 

`DIDWallet.update_metadata()` only validates that values are strings — it performs no length/size check on the dict, its keys, or its values — then immediately serializes it with `json.dumps()` and persists it to the wallet database via `save_info()`, independent of whether the corresponding on-chain spend ever succeeds or is even pushed: [3](#0-2) 

This is directly analogous to the Synapse CVE-2021-21394 bug class: an authenticated-caller-facing endpoint accepts attacker/user-controlled string parameters with no maximum length enforcement, and those values are persisted to local storage, enabling repeated calls to grow local storage/memory usage without bound. In this codebase, other similar surfaces (e.g. `NotificationManager.potentially_add_new_notification`) explicitly cap message size at 10 KB [4](#0-3) , and keychain labels are bounded by `MAX_LABEL_LENGTH` per the util context notes . `did_update_metadata` has no equivalent bound.

### Impact Explanation
A wallet RPC caller can repeatedly invoke `did_update_metadata` with very large metadata dictionaries (e.g. megabyte-scale JSON strings). Each call:
1. Immediately serializes and persists the oversized metadata blob into the wallet's SQLite database via `save_info()`, regardless of whether the follow-on `create_update_spend()` transaction is ever pushed or accepted by the mempool/full node.
2. Can be repeated arbitrarily, growing wallet database size and increasing memory pressure whenever that DID's info is loaded/read from disk (e.g. via `did_get_metadata`, `puzzle_for_pk`, `puzzle_hash_for_pk`, which `json.loads()` the stored metadata on every puzzle derivation).

This does not directly enable coin theft or forged assets, but it can degrade the local wallet node's availability (excessive disk usage, slower puzzle-hash derivation, increased memory use per DID access) — a resource-exhaustion condition matching the CVE's bug class and impact category.

### Likelihood Explanation
High likelihood of triggering: the RPC endpoint is reachable by any authenticated wallet RPC caller (a "local RPC caller" per the described threat model) with no special privileges beyond normal wallet RPC access, no cost/CLVM validation gates the initial persistence step (only the on-chain spend step, which is a separate call), and there is no dict-size, key-count, or string-length check anywhere in the call chain from RPC request to `save_info()`.

### Recommendation
Add explicit bounds in `DIDWallet.update_metadata()` (and/or at the RPC request-parsing layer) analogous to the `NotificationManager`'s 10 KB cap and `Keychain`'s `MAX_LABEL_LENGTH`: enforce a maximum serialized metadata size, a maximum number of keys, and a maximum length per key/value before calling `json.dumps()`/`save_info()`. Reject oversized requests with a clear `ValueError` before any database write occurs.

### Proof of Concept
1. Connect to a running wallet RPC (in-scope local RPC caller) with valid wallet RPC credentials.
2. Create a DID wallet.
3. Call `did_update_metadata` repeatedly with a large payload, e.g.:
```python
huge_value = "A" * (50 * 1024 * 1024)  # 50 MB string
await wallet_rpc_client.update_did_metadata(
    DIDUpdateMetadata(wallet_id=did_wallet_id, metadata={"k": huge_value}, push=False),
    tx_config,
)
```
4. Observe that `wallet.update_metadata()` immediately persists the 50 MB JSON blob to the wallet database via `save_info()` (visible as growth in the wallet SQLite file), with no exception raised for the oversized value, and that this can be repeated to continuously grow local storage usage.

Note: I was unable to fully trace `save_info()`'s exact table/column update path within the available context (only its call sites were located, not its full body), so the precise on-disk representation (e.g., whether it hits `WalletUserStore.data` or a separate DID-info table) is inferred from `WalletUserStore.update_wallet()`'s unbounded `data text` column [5](#0-4)  rather than directly confirmed; a Devin session with full repo access could verify this exact storage path.

```python
        request: DIDUpdateMetadata,
        action_scope: WalletActionScope,
```

```python
    async def update_metadata(self, metadata: dict[str, str]) -> bool:
        # validate metadata
        if not all(isinstance(v, str) for v in metadata.values()):
            raise ValueError("Metadata key value pairs must be strings.")
        did_info = DIDInfo(
            origin_coin=self.did_info.origin_coin,
            backup_ids=self.did_info.backup_ids,
            num_of_backup_ids_needed=self.did_info.num_of_backup_ids_needed,
            parent_info=self.did_info.parent_info,
            current_inner=self.did_info.current_inner,
            temp_coin=self.did_info.temp_coin,
            temp_puzhash=self.did_info.temp_puzhash,
            temp_pubkey=self.did_info.temp_pubkey,
            sent_recovery_transaction=self.did_info.sent_recovery_transaction,
            metadata=json.dumps(metadata),
        )
        await self.save_info(did_info)
        await self.wallet_state_manager.update_wallet_puzzle_hashes(self.wallet_info.id)
        return True
```
