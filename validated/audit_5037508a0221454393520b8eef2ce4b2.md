### Title
Partial-commit line selection is applied against a freshly re-fetched diff instead of the diff the user reviewed, allowing silent inclusion of unreviewed content in a commit - ([File: app/src/lib/git/apply.ts])

### Summary
`DiffSelection` tracks which lines a user has (de)selected purely by numeric line index, with no binding to the content or version of the diff it was computed against. When a partial commit is created, `applyPatchToIndex` re-fetches the working directory diff from disk at staging time and replays the user's index-based selection against that *new* diff, rather than against the diff the UI actually rendered when the user made their selections.

### Finding Description
The commit flow works as follows:
1. The UI computes a diff and lets the user select/deselect individual lines via `DiffSelection`, which stores only integer line indices (`divergingLines`) with no hash/version tie back to the diff content (`app/src/models/diff/diff-selection.ts:78-136`).
2. When the user clicks Commit, `_commitIncludedChanges` in `app/src/lib/stores/app-store.ts:3681-3714` takes the `WorkingDirectoryFileChange[]` (each carrying its `DiffSelection`) straight from `state.changesState.workingDirectory.files` and passes them into `createCommit`.
3. `createCommit` (`app/src/lib/git/commit.ts:15-31`) calls `stageFiles`, which for any file with `DiffSelectionType.Partial` calls `applyPatchToIndex` (`app/src/lib/git/update-index.ts:109-168`).
4. `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-83`) does **not** use the diff that produced the selection indices; it independently calls `getWorkingDirectoryDiff(repository, file)` again at that moment, and `formatPatch` (`app/src/lib/patch-formatter.ts:129-221`) applies `file.selection.isSelected(absoluteIndex)` against the hunks of this newly fetched diff.

There is a documented awareness of this exact class of problem elsewhere in the codebase — `updateChangesWorkingDirectoryDiff` in `app/src/lib/stores/app-store.ts:3466-3513` explicitly recomputes `selectableLines` because "the diff might have changed dramatically since last we loaded it" — but that reconciliation only happens for the *UI's* cached diff object; it is never invoked/enforced immediately before `applyPatchToIndex` re-fetches the diff for staging. Nothing revalidates that the diff used to build `DiffSelection` is the same diff `applyPatchToIndex` uses to build the patch. If the on-disk content of a tracked file changes between the moment the diff is displayed/selected and the moment Commit is pressed (e.g. due to a build step, formatter, linter, git hook, or any other background process touching the working tree — all of which are common in real repositories and can be embedded by a malicious/compromised clone via `post-checkout`/`post-merge` hooks or file-watcher tooling), the line indices no longer correspond to the same hunks/content. `formatPatch` will happily apply "line 5 is selected" semantics to whatever is now at absolute index 5 in the new diff, silently staging and committing different content than what the user actually reviewed and approved.

This is structurally the same defect pattern as the report: a decision (which lines to commit) is made using data (line indices bound to a diff) that is not guaranteed fresh/consistent at the time it is consumed (a newly fetched diff), and there is no re-validation step to guard against staleness before the value is "spent."

### Impact Explanation
This can cause **silent corruption of what the user commits**: a user could believe they reviewed and selected specific lines (e.g., excluding a sensitive change, or only including a small fix) but end up committing/pushing unintended content because the underlying diff shifted between review and commit. Because the commit succeeds without error or warning, the user has no visibility into the mismatch — directly matching the "silent corruption of what the user commits or pushes" category of valid impact.

### Likelihood Explanation
Likelihood is Medium: it requires the working tree to change between diff-review and commit-click, which is not attacker-triggerable purely from a remote/clone without some local mechanism (e.g., a git hook, editor auto-format-on-save, or build watcher active in the opened repository) already running. Desktop does execute repository-configured git hooks during git operations, and a cloned/fetched attacker-controlled repository can ship hooks or expect common developer tooling (linters/formatters/watchers) to be active, making the race practically reachable without any social engineering beyond "open this repo and commit normally."

### Recommendation
Bind `DiffSelection` (or the `WorkingDirectoryFileChange`) to an identifier/hash of the diff it was computed from, and have `applyPatchToIndex`/`stageFiles` re-validate that the freshly fetched diff matches that identifier before applying the patch. If it doesn't match, refuse to stage the file (or recompute `selectableLines` and force a re-render/re-confirmation) instead of silently applying stale line-index selections to new diff content.

  private constructor(
    private readonly defaultSelectionType:
      | DiffSelectionType.All
      | DiffSelectionType.None,
    private readonly divergingLines: Set<number> | null = null,
    private readonly selectableLines: Set<number> | null = null
  ) {}

  /** Returns a value indicating the computed overall state of the selection */
  public getSelectionType(): DiffSelectionType {
    const divergingLines = this.divergingLines
    const selectableLines = this.selectableLines

    // No diverging lines, happy path. Either all lines are selected or none are.
    if (!divergingLines) {
      return this.defaultSelectionType
    }
    if (divergingLines.size === 0) {
      return this.defaultSelectionType
    }

    // If we know which lines are selectable we need to check that
    // all lines are divergent and return the inverse of default selection.
    // To avoid looping through the set that often our happy path is
    // if there's a size mismatch.
    if (selectableLines && selectableLines.size === divergingLines.size) {
      const allSelectableLinesAreDivergent = [...selectableLines].every(i =>
        divergingLines.has(i)
      )

      if (allSelectableLinesAreDivergent) {
        return this.defaultSelectionType === DiffSelectionType.All
          ? DiffSelectionType.None
          : DiffSelectionType.All
      }
    }

    // Note that without any selectable lines we'll report partial selection
    // as long as we have any diverging lines since we have no way of knowing
    // if _all_ lines are divergent or not
    return DiffSelectionType.Partial
  }

  /** Returns a value indicating wether the given line number is selected or not */
  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
