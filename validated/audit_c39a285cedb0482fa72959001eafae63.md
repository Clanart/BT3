### Title
Excess native ETH sent to `placeOrder` is permanently trapped, never refunded to the user - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder()` in the Tron variant of the Intent Gateway takes `msg.value`, consumes it for native-token order inputs and for a `swapETHForExactTokens` fee swap, but — unlike the canonical EVM `IntentGatewayV2.sol` — never returns any leftover `msgValue` to the caller at the end of the function. This is the direct local analog of the ARCH over-supply bug: a user (or solver) input amount that exceeds what the protocol actually needs is silently absorbed by the contract instead of being refunded to the rightful owner.

### Finding Description
In the mainline EVM contract, `placeOrder()` explicitly tracks unspent `msgValue` through the fee-swap branch and refunds it at the end: [1](#0-0) 

The Tron-targeted copy of the same function implements the identical fee-swap logic — calling `swapETHForExactTokens{value: msgValue}(order.fees, ...)` — but drops both the `msgValue -= amounts[0]` bookkeeping and the final "refund any unspent native tokens to the user" step: [2](#0-1) 

Two independent sources of leftover native ETH accumulate in this function and are never returned to `msg.sender`:
1. When native-token inputs are used, `msgValue` is decremented by `order.inputs[i].amount` for each native input, but any amount sent beyond the sum of native inputs plus `order.fees` remains unaccounted: [3](#0-2) 
2. `swapETHForExactTokens` only consumes the exact ETH needed to buy `order.fees` worth of fee token and returns the remainder to the caller (this contract) — in the mainline contract that returned remainder is captured via `amounts[0]` and forwarded back to the user; here it is not tracked or forwarded at all: [4](#0-3) 

There is no `receive()`/sweep/withdraw mechanism elsewhere in the contract that would let a user reclaim this stranded ETH, so any overpayment of native currency into `placeOrder` is permanently lost to the contract (effectively locked, unrecoverable by anyone, including governance, since this path has no dedicated withdrawal instruction for stray native balance).

This mirrors the reported bug exactly: the function checks that at least enough was supplied (`InsufficientNativeToken` reverts guard the "not enough" side) but has no corresponding check/refund for "too much," so all excess is taken and never returned.

### Impact Explanation
Any user or integrator who overestimates gas/fee costs when calling `placeOrder` with a native-token fee payment or native-token input on the Tron deployment permanently loses the excess ETH — a direct, unconditional loss of user funds with no recovery path, matching the bounty's "stealing or loss of funds" criterion. Because `swapETHForExactTokens` virtually always returns some dust (exact-output swaps rarely consume 100% of an approximate input), this triggers on essentially every fee-token swap that uses native payment, not just extreme overpayment cases.

### Likelihood Explanation
High: this is a public, unprivileged entry point (`placeOrder`) that ordinary users call to open orders, requires no malicious actor, relayer, or prover, and is triggered by completely normal usage patterns (paying fees in native token, or slightly overestimating the exact `order.fees` swap cost). The bug requires no adversarial conditions — it fires deterministically whenever `msgValue` isn't consumed exactly by input transfers and the fee swap.

### Recommendation
Track cumulative `msgValue` consumption through both the native-input loop and the fee-swap branch (capturing `amounts[0]` from `swapETHForExactTokens`), then refund any remaining `msgValue` to `msg.sender` at the end of `placeOrder`, mirroring the logic already present in `evm/src/apps/IntentGatewayV2.sol` lines 364-368.

### Proof of Concept
1. User calls `placeOrder{value: X}(order, graffiti)` on the Tron `IntentGatewayV2` where `order.fees > 0` and payment is in native token (the `msgValue > 0` branch at line 468).
2. `X` exceeds the exact ETH needed to obtain `order.fees` units of fee token via `swapETHForExactTokens`.
3. `swapETHForExactTokens{value: msgValue}(order.fees, ...)` sends the entire `msgValue` but internally only pulls the ETH needed for the exact output, refunding the rest to `address(this)` (the gateway contract), not to the user.
4. Function returns; no code path forwards the refunded ETH (or any of `msgValue` unspent by native inputs) back to `msg.sender`.
5. The excess ETH sits in the contract's balance with no `receive()`/withdraw path to reclaim it — permanently lost to the user who supplied it. [2](#0-1)
