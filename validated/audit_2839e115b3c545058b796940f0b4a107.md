### Title
Clone explicitly disables Git's built-in clone-time protection against malicious repository content - (File: `app/src/lib/git/clone.ts`)

### Summary
When GitHub Desktop clones a repository, `clone()` hard-codes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into the environment used to invoke `git clone --recursive`. This deliberately turns off a Git-level safety check that exists specifically to protect users from maliciously crafted repositories (and their submodules) during clone.

### Finding Description
`clone()` builds the process environment for the clone invocation like this: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

The broken invariant, mirroring the PoolTogether report's pattern of "an unprivileged/attacker-influenced party can silently change a safety parameter the user relies on," is: Desktop unconditionally opts the user out of Git's own defense-in-depth protection for every clone, regardless of whether the URL/repository is trusted. The attacker here is the remote repository owner (the thing being cloned) — fully analogous to the report's "external, potentially malicious party changing state the user is relying on for safety guarantees" — except instead of a liquidity cap, the value being silently subverted is a Git security control that specifically exists to stop malicious repository content from executing during clone/`--recursive` submodule checkout.

Because the clone always uses `--recursive`, an attacker can craft a repository with a submodule whose configuration/hooks/symlinked `.git` layout would normally be caught and aborted by Git's clone-time protections. With `GIT_CLONE_PROTECTION_ACTIVE=false`, that check is bypassed uniformly for every clone Desktop performs, whether the user is cloning their own trusted repo or an arbitrary URL/organization repo shared by someone else (Desktop's own `clone-path-safety` tests show Desktop already treats clone targets as adversarial input, e.g. the traversal-payload tests in `app/test/unit/clone-path-safety-test.ts`, confirming the threat model includes hostile remotes). [2](#0-1) 

Existing guards do not stop this path: `isClonePathSensitive()` only validates the destination directory on disk, not the content of the repository being cloned, so it provides no protection against the class of attack that `GIT_CLONE_PROTECTION_ACTIVE` exists to prevent. [3](#0-2) 

### Impact Explanation
If the disabled protection is the one that guards against malicious submodule/`.git` layouts during `--recursive` clone (the class of issue Git's clone-protection environment variable was introduced for), a crafted repository cloned through Desktop could execute unintended code or write files outside the intended repository boundary during the clone itself, before the user has any chance to review content — matching the "code execution / file write outside the repo" impact category for an attacker who only controls a cloned repository.

### Likelihood Explanation
Likelihood is high for any user who clones a repository they do not fully control (a very common workflow — cloning collaborators' forks, open-source projects, or repositories linked from GitHub search/PRs) because the protection is disabled unconditionally for all clones (`clone()` has no trusted/untrusted branch), and `--recursive` is always passed, maximizing exposure to submodule-based attack payloads.

### Recommendation
Do not disable `GIT_CLONE_PROTECTION_ACTIVE` unconditionally. Only opt out of Git's clone-time protections when there is a demonstrated compatibility need on a specific, narrowly-scoped code path, log/telemetry the reason, and prefer leaving Git's default protection active for all remote clones initiated from arbitrary user-supplied URLs. If the protection variable is being disabled to work around a Dugite/Git version compatibility issue, gate it behind a version check rather than applying it globally, and add regression tests (mirroring `clone-path-safety-test.ts`) that assert clone-time protections remain active for `--recursive` clones of untrusted URLs.

### Proof of Concept
1. Attacker publishes a public repository containing a submodule entry crafted to trigger the condition that Git's clone-time protection (`GIT_CLONE_PROTECTION_ACTIVE`) is designed to detect and abort on (e.g. a submodule/`.git` path collision on the target filesystem).
2. Victim uses GitHub Desktop's "Clone repository" feature to clone the attacker's URL.
3. `clone()` invokes `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment. [4](#0-3) 
4. Because the protection is disabled, Git proceeds with the clone/submodule checkout instead of aborting, allowing the malicious repository layout to be processed on disk.

Note: I could not find in this codebase the specific Git/Dugite version pinned, nor any comment explaining why `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'`, nor a test asserting the intended behavior of that flag — these would need to be checked in a full Devin session (e.g. `package.json`/`dugite` version, and any linked upstream Desktop PR/changelog entry) to confirm the exact underlying Git protection being disabled and whether it is exploitable in the pinned Git version.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
