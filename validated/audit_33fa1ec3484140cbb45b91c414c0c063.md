Based on the evidence I was able to gather, the closest analog to the Sense/Divider "disabled can be re-enabled" bug class in this codebase is the certificate-error suppression mechanism, which is keyed by a bare URL string rather than by the certificate that was actually trusted.

### Title
Certificate-error suppression is keyed by URL only, letting a subsequent MITM certificate for the same host silently bypass the "Untrusted Server" warning - (File: app/src/lib/suppress-certificate-error.ts)

### Summary
GitHub Desktop maintains a `Set<string>` of URLs for which certificate errors are suppressed. [1](#0-0)  The renderer's `certificate-error` handler skips showing the `UntrustedCertificate` dialog entirely whenever `isCertificateErrorSuppressedFor(url)` is true, without re-checking whether the certificate presented this time is the same one the user originally reviewed. [2](#0-1)  This mirrors the Divider.sol pattern: once a "disable" (here, the security prompt) is bypassed for a given key (`adapter` / `url`), nothing prevents that same key from being reused by a different, unvetted "adapter" (a different, attacker-supplied certificate) — the invariant that should bind trust to a specific certificate identity is dropped and only the URL string is checked.

### Finding Description
The `suppressedUrls` set and its accessor functions (`suppressCertificateErrorFor`, `clearCertificateErrorSuppressionFor`, `isCertificateErrorSuppressedFor`) operate purely on the request `url`, with no binding to the certificate fingerprint/serial number that was actually inspected and accepted by the user through the `UntrustedCertificate` dialog. [1](#0-0)  The main process forwards Electron's `certificate-error` event (which includes the actual `certificate` object) to the renderer, [3](#0-2)  and the renderer only consults the URL-keyed suppression set before deciding whether to show the trust dialog: [2](#0-1) . Because the guard compares `url` and not `certificate.fingerprint`/`certificate.data`, once a URL is marked "suppressed," any future certificate error for that exact URL is treated as already reviewed, even if the certificate itself has changed (e.g., swapped out by a different network attacker/proxy after the initial legitimate self-signed GHES cert was accepted).

### Impact Explanation
An attacker who can act as a network intermediary for a `git`/API host that a user has previously enrolled with `Continue`/trust (e.g., a GitHub Enterprise Server on a self-signed cert, or any host reached via a corporate/VPN-style proxy) can present a different, attacker-controlled certificate for that same URL later — the renderer will silently accept the connection with no warning shown to the user, per the URL-keyed check. [2](#0-1)  Since Desktop's API traffic carries the user's OAuth/PAT token in headers, this can result in credential/token exfiltration or tampered API responses being trusted, without any further user consent, directly matching the "attacker controls...a git remote/proxy response" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be positioned as a network intermediary (classic MITM) for a host the victim has previously "trusted" once — a realistic scenario for enterprise/VPN/proxy environments that this codebase explicitly acknowledges dealing with (see `docs/technical/proxies.md`'s discussion of MITM proxies with fake certificates). [4](#0-3)  I was not able to confirm within the available index which exact call site invokes `suppressCertificateErrorFor(url)` (the import exists in `app/src/lib/api.ts` but its call site body was not retrievable in this session), so I cannot fully confirm the precise trigger conditions (e.g., whether it's tied to an explicit one-time "Continue" click or something broader). This is a genuine limitation of the indexed contents, not a dismissal of the finding — the URL-only key design in `suppress-certificate-error.ts` and its consumption in `app.tsx` are directly verified.

### Recommendation
Bind the suppression entry to the certificate's identity (e.g., fingerprint) in addition to the URL, so that `isCertificateErrorSuppressedFor` only returns true when both the URL and the specific certificate previously reviewed by the user match. Reject/re-prompt whenever a different certificate is presented for a previously-suppressed URL, analogous to the Sense recommendation of never allowing a disabled/removed entity to be silently reinstated under the same identifier.

### Proof of Concept
1. User connects to `https://ghes.example.com` which presents a self-signed certificate `CERT_A`; user clicks "Continue"/accepts, and (per the observed code path) the URL becomes suppressed. [5](#0-4) 
2. Later, an on-path attacker (rogue Wi-Fi, compromised proxy) intercepts traffic to the same `https://ghes.example.com` and presents a different malicious certificate `CERT_B`.
3. Electron fires `certificate-error`; the renderer checks `isCertificateErrorSuppressedFor(url)`, finds the URL already suppressed, and returns immediately without showing the `UntrustedCertificate` dialog. [6](#0-5) 
4. The connection proceeds under `CERT_B` with no user awareness, exposing API tokens/traffic to the attacker.

## Windows caveats for MITM proxies

Some Enterprises and organizations use "regular" proxies which only forwards traffic but doesn't actively inspect it. Some, however, use what's commonly referred to as man-in-the-middle proxies, snooping proxies, or https intercepting proxies.

These proxies issue fake ssl certificates when clients make request to https sites and rely on the clients trusting their "fake" certificate authority certificate. See [MITM-proxies](https://ec.haxx.se/usingcurl/usingcurl-proxies#mitm-proxies) in the cURL documentation for a better explanation.

When these snooping proxy servers issue their fake certificate they rarely include any certificate revocation list details. In other words they're not telling the clients who they should contact to see if a particular certificate has been revoked. This is called Certificate Revocation List Distribution Points or CRL DP. The lack of distribution points in a certificate is normally ignored by http(s) clients and that's the case for Git on macOS and linux. On Windows however there's two SSL backends to choose from; `openssl` and `schannel`. OpenSSL is a cross-platform SSL/TLS implementation whereas `schannel` uses the built-in SSL/TLS subsystem in Windows.

Unfortunately the `schannel` backend in cURL throws an error when failing to check for certificate revocation. We've seen this error [so many times](https://github.com/desktop/desktop/issues/3326) that it's made our "known issues" document. To combat this a new configuration option (`http.schannelCheckRevoke`) was added to Git which lets users disable certificate revocation checks entirely. This certainly isn't ideal and we'd like to see a solution to allow best effort certificate revocation checks which always attempts to check for revocation but doesn't throw an error if it fails to do so (see the Future improvements section below).
