### Title
Blame proof leaks ECDH shared key before proof-of-possession verification, enabling DKG secret share recovery - (File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to the XXE class (untrusted input processed in a way that discloses secret data), PedPoP's `Encryption::decrypt` computes the ECDH shared key and constructs a publishable `EncryptionKeyProof` **unconditionally**: it only *queues* the message's proof-of-possession (PoP) Schnorr signature into a `BatchVerifier` for later checking. In `KeyMachine::calculate_share`, if the decrypted bytes fail scalar deserialization, the function returns early with `blame: Some(blame)` — revealing the shared key `b·msg.key` — *before* `batch.verify_with_vartime_blame()` ever runs and could attribute the failure to `BatchId::Decryption` (which would return `blame: None`). An attacker who replays another party's encryption key `X` (which they do not know the discrete log of) obtains a DLEq-certified revelation of `bX`, decrypting the victim's encrypted secret share — exactly the side effect the code comments explicitly try to prevent.

### Finding Description
`EncryptedMessage` includes a PoP specifically to prevent key reuse: the comment at crypto/dkg/pedpop/src/encryption.rs:83-90 explains that if Eve copies Alice's encryption key `X` into a message to Bob, Bob's blame argument would reveal `bX`, decrypting Alice's message. The PoP is meant to make such a forgery impossible. However, `Encryption::decrypt` (encryption.rs:469-501) does not verify the PoP inline — it calls `msg.pop.batch_verify(...)` which merely queues the statement, then immediately computes `key = ecdh(&self.enc_key, msg.key)` and returns `(decrypted_msg, EncryptionKeyProof { key, dleq })`. The returned `EncryptionKeyProof` is a publicly verifiable DLEq proof that `key` is the true shared ECDH key.

In `KeyMachine::calculate_share` (lib.rs:476-499), the batch is only checked at line 493 via `batch.verify_with_vartime_blame()`. But the early return at lines 480-482 — `from_repr` failing on the decrypted share — fires first and propagates `PedPoPError::InvalidShare { participant: l, blame: Some(blame) }`, where `blame` is the already-generated `EncryptionKeyProof`. The batched PoP failure (which would map to `BatchId::Decryption(l)` and yield `blame: None`, correctly withholding the key) is never evaluated. Additionally, even when the batch does run, `decrypt` has already output the proof to the caller; the design relies on the caller discarding it, but the early-return path hands it out inside the error itself.

### Impact Explanation
Eve observes Alice's `EncryptedMessage` to Bob (key `X = aG` for Alice's per-message key `a`), then sends Bob `EncryptedMessage { key: X, pop: <arbitrary validly-encoded signature>, msg: <garbage ciphertext> }`. Bob's `decrypt` computes `k = bX` (Bob's static encryption key `b` times `X`), decrypts garbage, and produces a valid `EncryptionKeyProof` proving `k` is the ECDH key for `(G, X, enc_pub_key_bob, k)`. With probability ~15/16 (for ristretto255/secp256k1-order fields where the group order is much less than 2^256) the garbage fails `from_repr`, triggering the early return that exposes the proof. Publishing `k` lets Eve decrypt Alice's original ciphertext and recover Alice's secret share for Bob. Combined across messages or used against threshold participants, this is secret share / key material disclosure — a Critical/High impact under the stated criteria (key share recovery from public inputs via `EncryptedMessage::read` + `calculate_share`).

### Likelihood Explanation
Requires an unprivileged DKG participant (or anyone able to send shares to a participant) to submit a crafted `EncryptedMessage` and to have observed a prior `EncryptedMessage` from any sender to the same recipient — all within the attacker's normal protocol reach, no validator collusion needed. The forged message needs no valid PoP because the PoP check is deferred and bypassed by the early error return. The only probabilistic element is the decrypted garbage failing scalar canonicality, which succeeds with high probability per attempt and is trivially repeatable.

### Recommendation
Verify `msg.pop` inline (synchronously, via `SchnorrSignature::verify`) inside `Encryption::decrypt` before computing the ECDH and constructing `EncryptionKeyProof`, or restructure `calculate_share` so the `EncryptionKeyProof` is only produced after `batch.verify_with_vartime_blame()` confirms the PoP. Alternatively, have `decrypt` return a lazy handle that only materializes the proof once the caller confirms the batch outcome. In `decrypt_with_proof`/`blame_internal` this ordering already exists; the hot path must match it.

### Proof of Concept

```rust
// Eve observed msg_alice: EncryptedMessage<C, SecretShare> with key X, sent to Bob.
// Eve constructs a forgery reusing X:
let forged = EncryptedMessage {
  key: msg_alice.key,                    // replayed per-message pubkey X = aG
  pop: SchnorrSignature { R: random_G, s: random_F }, // invalid PoP
  msg: SecretShare(<garbage bytes>),     // e.g. all-0xFF repr (non-canonical)
};

// Bob calls calculate_share with shares map containing Eve's forged message.
// In Encryption::decrypt:
//   - pop is only queued into the BatchVerifier (encryption.rs:479-485)
//   - key = b*X is computed (encryption.rs:487)
//   - EncryptionKeyProof { key: bX, dleq } is built (encryption.rs:491-499)
// In calculate_share, decrypted garbage fails from_repr -> early return:
//   Err(InvalidShare { participant: Eve, blame: Some(proof_of_bX) })  (lib.rs:480-482)
// batch.verify_with_vartime_blame() at lib.rs:493 never runs, so the bad PoP
// is never detected and blame is not suppressed.

// Eve now holds a DLEq-verified revelation of k = bX, derives the ChaCha20
// cipher via `cipher(context, k)`, and decrypts Alice's original ciphertext,
// recovering Alice's secret share for Bob.
```
