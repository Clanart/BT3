### Title
Disabled overfill clamp in `FXFiller.calculateProfitability` lets a manipulated/stale venue price force unbounded solver overpayment - ([File: sdk/packages/simplex/src/strategies/fx.ts])

### Summary
The Simplex intent filler's FX pricing strategy computes a per-leg `policyMaxOutput` from a venue price feed (including Uniswap V4 quotes) and previously clamped that output to `(1 + maxOverfillBps) × order.output.assets[i].amount` before committing to fill an order. That clamp has been intentionally disabled: the code now only logs a warning when the computed output exceeds the ceiling and always fills the full unclamped amount, exactly reproducing the bug class described in the external report — a stale/incorrect quoted amount is used for settlement instead of the amount actually agreed/requested, with no bound to protect the party funding the settlement.

### Finding Description
`FXFiller.calculateProfitability` in `sdk/packages/simplex/src/strategies/fx.ts` derives `rawPolicyMaxOutput` from `computeLegPolicyOutput`, which prices the leg using `rates.rate` sourced from `resolveLegRates` (including on-chain venue quotes such as Uniswap V4). [1](#0-0) 

Immediately after, the code computes an `overfillCeiling` based on the user's originally requested `output.amount` and `maxOverfillBps`, but — per the comment — the clamp that used to bound `policyMaxOutput` to this ceiling has been removed; only a warning is emitted, and `policyMaxOutput` is left equal to the raw, unclamped, venue-priced value: [2](#0-1) 

This `policyMaxOutput` then directly drives how much the filler actually withdraws/sends as `finalOutputAmount`, capped only by available wallet/vault liquidity, not by any bound tied to the order's requested amount: [3](#0-2) 

The on-chain `IntentGatewayV2` fill functions do not protect against this because they only enforce a **floor** on solver-provided output (`solverAmount >= totalRequired`), never a ceiling — surplus is explicitly a valid, expected code path (`surplusShareBps` split): [4](#0-3) 

Because the on-chain contract cannot distinguish "legitimate solver surplus" from "solver output size corrupted by a stale/manipulated price feed," the only protection against a bad or manipulated venue price was this off-chain clamp — and it has been disabled.

### Impact Explanation
An attacker who can influence the venue price used by `resolveLegRates` (e.g., manipulating a thin/flash-loanable Uniswap V4 pool used for cross-chain pair pricing, or exploiting a stale cache) can inflate `rawPolicyMaxOutput` far beyond the order's requested amount. With the clamp disabled, the filler will unconditionally transfer that inflated amount to the order's beneficiary and dispatch the `RedeemEscrow`/settlement message, moving funds far in excess of the rightful amount to the beneficiary at the filler's expense. This directly violates the required invariant that bridged assets/order escrow must move "exactly once and only to the rightful beneficiary and amount," and constitutes a logic/transaction-manipulation attack that causes fund loss through the intent-settlement path.

### Likelihood Explanation
This requires only price manipulation of a venue quote (e.g., a flash-loan-based price move on a shallow Uniswap V4 pool) by an unprivileged attacker who places or benefits from an order — no compromised relayer, prover, or admin key is needed. The guard that existed specifically to protect against this scenario ("a bug / stale cache / manipulated venue price") has been explicitly removed per the code's own comment, making exploitation straightforward once a suitable low-liquidity pair/pool is targeted.

### Recommendation
Re-enable the overfill clamp: cap `policyMaxOutput` to `overfillCeiling` (or reject the leg) instead of only logging a warning when `rawPolicyMaxOutput > overfillCeiling`. If intentional overfill for competitiveness is desired, bound it to a small, explicitly configured `maxOverfillBps` rather than leaving output entirely uncapped, and add sanity checks (e.g., TWAP or multi-source price cross-checks) before trusting a single venue quote for sizing settlement amounts.

### Proof of Concept
1. Configure/target an FX pair whose venue price source resolves through a low-liquidity Uniswap V4 pool.
2. Attacker takes a flash loan and swaps to sharply move the pool's tick/price just before (or during) order placement, inflating the rate returned by `resolveLegRates`.
3. Place (or have an accomplice place) an intent order for that pair; `FXFiller.calculateProfitability` computes `rawPolicyMaxOutput` from the manipulated rate, which now exceeds `overfillCeiling`.
4. Because the clamp is disabled (only a `logger.warn` is emitted, per [5](#0-4) ), the filler proceeds to fund `finalOutputAmount` at the unclamped, inflated size and calls `fillOrder` with it.
5. `IntentGatewayV2`'s on-chain check only requires `solverAmount >= totalRequired` ( [6](#0-5) ), so the inflated fill succeeds, and the beneficiary receives far more than the order's requested amount, funded by the filler's escrowed liquidity.
