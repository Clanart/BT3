### Title
Re-registration in `MGPRelease.register()` resets `claimed` to zero, enabling double-claim of previously withdrawn tokens - (File: rewards/MGPRelease.sol)

### Summary
`MGPRelease.register()` (`onlyOwner`) unconditionally overwrites a beneficiary's entire `Vesting` struct, including resetting `claimed` to `0`, whenever the owner re-registers an existing address. An unprivileged beneficiary can front-run a pending re-registration transaction with `claim()` to drain their current entitlement, then call `claim()` again after the re-registration lands to receive a fresh payout computed from `claimed = 0`, resulting in cumulative payouts that exceed the beneficiary's final, intended `totalAlloced`.

### Finding Description
`register()` writes a brand-new `Vesting` struct for each address without checking or preserving any existing `claimed` value: [1](#0-0) 

`claim()` computes `claimable` purely from current storage state (`totalAlloced`, `claimed`) via `getClaimable()`, and then increments `claimed`: [2](#0-1) 

Exploit flow:
1. Beneficiary already has `Vesting{totalAlloced: A_old, claimed: C_old}`.
2. Owner submits a (legitimate, non-malicious) `register()` transaction to update this beneficiary's allocation to `A_new` — e.g. to correct an error or top up/adjust the amount. This is a routine admin action, not an abuse of privilege.
3. The attacker, an unprivileged existing beneficiary, observes this pending transaction in the mempool and front-runs it with `claim()`. Because `claim()` reads current on-chain state, it correctly computes and pays out `claimable_1` based on `A_old`, and sets `vesting.claimed = C_old + claimable_1`.
4. The owner's `register()` transaction then lands, and because it does a full struct overwrite, it resets `claimed` back to `0` regardless of the amount just paid out in step 3, while setting `totalAlloced = A_new`.
5. The attacker calls `claim()` again. `getClaimable()` now computes `claimable_2` from `A_new` and `claimed = 0`, as if nothing had ever been paid.

Total tokens received by the attacker = `claimable_1 + claimable_2`, while contract state now only shows `claimed = claimable_2` against `totalAlloced = A_new`. If `A_new` is intended to reflect the beneficiary's true remaining entitlement (e.g., a correction downward, or simply a top-up where the owner assumed prior claims would carry over), the beneficiary receives up to the entirety of `claimable_1` as pure excess — tokens paid but never subtracted from any final balance. No existing modifier (`onlyOwner`, `nonReentrant`) prevents this, because both `claim()` calls are individually valid and the attacker never needs privileged access — they only race their own `claim()` transactions around an honest admin transaction.

### Impact Explanation
This is a direct theft of protocol/vesting funds (conservation violation): the beneficiary can extract more `tokenToRelease` than the final `totalAlloced` set for them supports, at the expense of the contract's remaining token balance intended for other beneficiaries or the dust-withdrawal at the end of vesting. This matches the Immunefi "direct theft of user funds" / protocol insolvency impact class, since the released token supply backing all vestings becomes under-collateralized by the excess amount claimed.

### Likelihood Explanation
Preconditions: attacker must already be a registered beneficiary (no special capital needed — no staking/whitelisting beyond having been previously registered by the owner), and the owner must at some point call `register()` again for that same address (a plausible, non-malicious operational event, e.g., correcting an allocation amount or adding more allocation instead of using a differential/append pattern). The exploit only requires the attacker to watch the mempool and submit two ordinary `claim()` transactions, which is trivial and fully repeatable each time re-registration occurs for an address with unclaimed history.

### Recommendation
`register()` should not blindly reset `claimed` to `0` on re-registration. Instead:
- Preserve `claimed` across re-registration (e.g., only update `totalAlloced` while leaving `claimed` untouched), or
- Force a mandatory `claim()`-and-settle (or explicit accounting adjustment) as part of the same transaction/flow before allowing `totalAlloced` to be changed, or
- Track allocations as monotonically increasing deltas rather than full overwrites, ensuring `claimed` semantics remain consistent with the token amounts actually transferred out.

### Proof of Concept
Foundry test plan:
1. Deploy `MGPRelease` with a short vesting window and `initialUnlockPercentage` set so that some tokens are immediately claimable at `startTimestamp`.
2. Owner calls `register([attacker], [A_old])`.
3. Warp time so `getClaimable(attacker)` returns a non-zero `claimable_1` (e.g., past `endTimestamp` so `claimable_1 = A_old`).
4. Simulate mempool ordering: call `attacker.claim()` (mined first) — assert `IERC20(tokenToRelease).balanceOf(attacker) == claimable_1` and `beneficiaries[attacker].claimed == claimable_1`.
5. Then execute the owner's pending `register([attacker], [A_new])` transaction (e.g., `A_new = A_old / 2`) — assert `beneficiaries[attacker].claimed == 0` after this call (the reset).
6. Call `attacker.claim()` again — assert it succeeds and pays out `claimable_2 = A_new` (since still past `endTimestamp` with `claimed = 0`).
7. Final assertion: `IERC20(tokenToRelease).balanceOf(attacker) == claimable_1 + claimable_2 > A_new`, proving cumulative payout exceeds the latest `totalAlloced` alone, violating the conservation invariant.

    function getClaimable(address _account) public view returns (uint256 claimable) {
        Vesting storage vesting = beneficiaries[_account];
        uint256 initialUnlockedAmount = vesting.totalAlloced * initialUnlockPercentage / denominator;

        if (block.timestamp <= startTimestamp)
            return  initialUnlockedAmount - vesting.claimed;

        if (block.timestamp >= endTimestamp)
            return vesting.totalAlloced - vesting.claimed;

        uint256 needVesting = vesting.totalAlloced - initialUnlockedAmount;
        uint256 vested = (((block.timestamp - startTimestamp) * needVesting) / (endTimestamp - startTimestamp));

        claimable = (initialUnlockedAmount + vested - vesting.claimed);
    }    

    /* ============ External Functions ============ */

    function claim() nonReentrant external {
        Vesting storage vesting = beneficiaries[msg.sender];
        if (vesting.revoked)
            revert AccountRevoked();
        
        uint256 claimable = getClaimable(msg.sender);
        IERC20(tokenToRelease).safeTransfer(msg.sender, claimable);
        vesting.claimed += claimable;

        emit Claimed(msg.sender, claimable);
    }
