Confirmed vulnerability: `addRemote` (`app/src/lib/git/remote.ts:29-37`) builds the `git remote add` argument vector as `['remote', 'add', name, url]` with no `--` end-of-options separator before `url`, and this function is fed a `url` value (`headCloneUrl`) that comes straight from a PR object obtained through the GitHub API, with no scheme/character validation performed anywhere in the call chain.

### Title
Argument-injection via unsanitized PR fork `clone_url` in `addRemote` - (File: app/src/lib/git/remote.ts)

### Summary
`Dispatcher.checkoutPullRequest` / `AppStore._findPullRequestBranch` take `pullRequest.head.repo.clone_url` (or `pullRequest.head.gitHubRepository.cloneURL`) — a string returned verbatim by a GitHub/GHE API response for a pull request — and, if no existing remote matches it, pass it directly into `addRemote(repository, forkRemoteName, headCloneUrl)`, which runs `git(['remote', 'add', name, url], ...)`. [1](#0-0) [2](#0-1) 

### Finding Description
Compare this to `clone()`, which explicitly guards against a hostile URL/path by inserting a `--` separator before the positional `url`/`path` args (`args.push('--', url, path)`), precisely to stop a crafted string from being parsed as a git option instead of a value. [3](#0-2) 

`addRemote` has no equivalent protection: `git(['remote', 'add', name, url], ...)` passes `url` (and `name`) as bare positional arguments with no `--` terminator. `git remote add` accepts option flags such as `-f` (fetch immediately after adding), `-t <branch>`, `-m <master>`, `--mirror=fetch|push`, and reads further values from subsequent arguments. Because the value driving this call — `headCloneUrl` — is not a locally-typed URL but data taken from a remote GitHub API response object (`pullRequest.head.repo.clone_url`), it satisfies the report's threat model of "attacker controls a GitHub API object." A hostile or compromised GitHub Enterprise Server (or a man-in-the-middle on that connection) can shape the PR API response so `clone_url` (or `owner.login`, which becomes the remote *name* via `forkPullRequestRemoteName`) begins with `-`, causing `git remote add` to interpret it as a flag rather than a literal repository URL.

`urlMatchesRemote`/`repository-matching.ts` only compares the *value* structurally against existing remotes for matching purposes; it does not sanitize or reject strings that look like git options before they reach `addRemote`. [4](#0-3) 

The corrupted value is the `url` argument silently reinterpreted as a git CLI flag by `git remote add` inside `addRemote`, which the app trusts as "just a remote URL" but which is actually attacker-influenced API data with no allowlist of scheme (`https://`/`ssh://`) or leading-dash rejection anywhere along `AppStore._findPullRequestBranch` → `addRemote` → `git.ts`.

### Impact Explanation
`git remote add -f <name> <flags...>` will trigger an immediate fetch using whatever comes after, and combined with `--mirror` or crafted `-t`/`-m` arguments this can corrupt the on-disk remote configuration (`.git/config`), redirect subsequent fetch/push operations to attacker infrastructure, or otherwise silently alter what the local repo considers its remotes — falling squarely under "silent corruption of what the user commits or pushes." Because `addRemote` is reused by `_findPullRequestBranch` for automatic fork-remote creation with no user prompt, this is an unprivileged path triggered purely by opening/checking out a PR whose head repo/API data is attacker-influenced.

### Likelihood Explanation
This requires the PR API response's `head.repo.clone_url` (or `head.repo.owner.login`) to be attacker-controlled, i.e., a malicious/compromised GitHub Enterprise host or an API MITM — consistent with the allowed "attacker controls a GitHub API object" primitive in the report's valid-impact list. The flow is fully automatic: viewing/checking out a PR from the PR list (`pull-request-list.tsx` → `dispatcher.checkoutPullRequest` → `_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote`) requires no unusual user action beyond the normal "checkout PR" click. [5](#0-4) [6](#0-5) 

### Recommendation
Add a `--` separator before the positional `name`/`url` arguments in `addRemote` (and audit `setRemoteURL`, which has the same pattern), mirroring the fix already applied in `clone.ts`. Additionally validate that `headCloneUrl` parses as an `https://`/`ssh://` URL via `parseRemote`/`sanitizeCloneName`-style checks before it is ever passed to `addRemote`, rejecting values that don't match a well-formed git remote URL.

### Proof of Concept
1. Point Desktop at a malicious/compromised GitHub Enterprise Server account.
2. Have that server return a pull request API payload where `head.repo.clone_url` is set to a value such as `-oProxyCommand=touch pwned;` is not directly applicable to `remote add`, but a value like `--mirror=fetch` or `-f` as the "URL", and `head.repo.owner.login` used to build the remote name.
3. In Desktop, open the Pull Requests list for a repository tracked against that account and click the malicious PR to trigger "checkout pull request."
4. This calls `dispatcher.checkoutPullRequest` → `AppStore._checkoutPullRequest` → `_findPullRequestBranch`, which finds no matching existing remote and calls `addRemote(repository, forkRemoteName, headCloneUrl)`.
5. `addRemote` executes `git(['remote', 'add', forkRemoteName, headCloneUrl], ...)` with no `--` separator, so `headCloneUrl` is parsed by git as an option rather than a URL, an immediate unauthenticated fetch/mirror action is initiated, and `.git/config` gains an unexpected remote configuration — without any prior confirmation dialog to the user.

Note: I was unable to execute this against a live GHE instance to confirm the exact git option-parsing behavior for every crafted `clone_url` value (i.e., whether `git remote add` errors out vs. silently succeeds for each specific flag combination); this is based on static analysis of the missing `--` separator relative to the guarded `clone.ts` pattern and would benefit from dynamic verification in a full Devin session.

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
