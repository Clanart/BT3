## Analysis

The test suite `evmd/tests/ibc/ibc_middleware_test.go:2038-2087` (`TestOnTimeoutPacketWithCallback`) confirms the invariant IBC-Go's callbacks middleware is designed to preserve: *"the timeout refund should still happen [even if callback fails]"* — the escrow refund and the callback are meant to be independent, isolated operations, with the callback's context and gas usage sandboxed away from the packet-processing context. ### Title
Wrong-context gas metering in `IBCOnTimeoutPacketCallback` bypasses isolated gas sandbox, breaking timeout-refund atomicity guarantee - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCOnTimeoutPacketCallback` builds an isolated `cachedCtx` with an infinite gas meter capped at `cbData.CommitGasLimit` specifically to run the EVM callback without touching the real Cosmos SDK gas meter of the enclosing packet-timeout transaction (as documented in the function's own comments, and consistently implemented in the two sibling functions `IBCReceivePacketCallback` and `IBCOnAcknowledgementPacketCallback`). However, `IBCOnTimeoutPacketCallback` calls `k.evmKeeper.CallEVM(ctx, ...)` with the **original** `ctx` instead of `cachedCtx` — the exact anti-pattern the surrounding comment warns against.

### Finding Description
Compare the three sibling callback handlers in `x/ibc/callbacks/keeper/keeper.go`:

- `IBCReceivePacketCallback` (line 192, 215): `k.evmKeeper.CallEVM(cachedCtx, ...)` / `CallEVMWithData(cachedCtx, ...)` [3](#0-2) 
- `IBCOnAcknowledgementPacketCallback` (line 326): `k.evmKeeper.CallEVM(cachedCtx, ...)` [4](#0-3) 
- `IBCOnTimeoutPacketCallback` (line 424): `k.evmKeeper.CallEVM(ctx, ...)` — uses the **raw** `ctx`, not `cachedCtx` [5](#0-4) 

All three functions carry the identical comment explaining why `cachedCtx`/the infinite gas meter must be used:
> "`ProcessCallback` in IBC-Go overrides the infinite gas meter with a basic gas meter, so we need to generate a new infinite gas meter to run the EVM executions on. Skipping this causes the EVM gas estimation function to deplete all Cosmos gas." [6](#0-5) 

In `IBCOnTimeoutPacketCallback`, `cachedCtx` is still constructed (and `cachedCtx.GasMeter().GasRemaining()` is even used to compute the gas cap passed as `gasCap` to `CallEVM`), but the EVM execution itself runs against `ctx` — the packet-processing context whose gas meter is the basic (non-infinite) meter from IBC-Go's `ProcessCallback`. This reintroduces precisely the "deplete all Cosmos gas" failure mode the comment describes: the EVM/state-DB machinery underlying `CallEVM` consumes SDK gas from `ctx.GasMeter()` (via KV-store gas costs on `ctx`, not the isolated infinite meter), so it can panic with an out-of-gas condition that is not scoped to `cbData.CommitGasLimit` but to whatever gas remains in the real transaction-wide meter.

### Impact Explanation
This is functionally identical in class to the LayerZero bug: the destination-side (here, callback-execution) gas parameters used for a cross-domain-triggered call are taken from the wrong gas domain (real tx meter vs. isolated infinite meter), which can either waste/underprice gas or cause the call to blow the wrong budget and fail. IBC-Go's callbacks middleware is architected so that a `src_callback` failure must **not** prevent or roll back the underlying ICS-20 timeout refund (this invariant is explicitly asserted by the project's own test at `ibc_middleware_test.go:2075-2084`, "the timeout refund should still happen" even on callback failure). [7](#0-6) 

Because the timeout-callback path bypasses the sandbox and runs the EVM call directly against `ctx`, an out-of-gas panic here occurs on the same context/gas meter used by the surrounding packet-timeout message processing (rather than being contained to `cachedCtx`, which is discarded — not written back — on error, exactly as designed in the other two handlers). If `ProcessCallback`'s recovery in IBC-Go does not fully insulate `ctx`'s own gas meter state from this panic (which is the very scenario the code comment says must be avoided), the escrow refund tied to the same message execution can be jeopardized or repeatedly fail in a way that is not visible to, or curable by, the packet sender or relayer, since the escrowed ICS-20 tokens can only be recovered via a successful `OnTimeoutPacket`/`MsgTimeout` execution. This matches the required Critical impact category: permanent freezing/loss of escrowed IBC value via a normal, unprivileged user-triggerable flow (any sender specifying a `src_callback` in their transfer memo).

### Likelihood Explanation
Likelihood is unprivileged and directly reachable: any IBC transfer sender can attach a `src_callback` memo (documented, user-facing feature) pointing to a contract; whenever that packet times out, `IBCOnTimeoutPacketCallback` is executed with the buggy `ctx` usage. No relayer or validator collusion is required — a legitimate timeout is sufficient to reach the vulnerable code path.

### Recommendation
Change line 424 to run the EVM call against `cachedCtx` instead of `ctx`, matching `IBCOnAcknowledgementPacketCallback` and `IBCReceivePacketCallback`:
```go
res, err := k.evmKeeper.CallEVM(cachedCtx, *abi, sender, contractAddr, true,
    math.NewIntFromUint64(cachedCtx.GasMeter().GasRemaining()).BigInt(), "onPacketTimeout",
    packet.GetSourceChannel(), packet.GetSourcePort(), packet.GetSequence(), packet.GetData())
```
This restores the isolation that prevents the callback's EVM/state-DB gas usage from being charged against (and potentially exhausting) the real packet-timeout transaction's gas meter, consistent with the documented rationale already present in the same function and its siblings.

### Proof of Concept
Full verification requires a background Devin session with terminal access to build a reproduction (construct a timeout-callback contract whose execution consumes state/storage operations sufficient to exceed the outer `ctx`'s remaining gas while staying within `cbData.CommitGasLimit`, then trigger `MsgTimeout` and observe whether the escrow refund transaction fails/panics due to `ctx`'s gas meter being exhausted by the miswired `CallEVM(ctx, ...)` call, as opposed to being safely contained to `cachedCtx`). This is not achievable through static code reading alone since it depends on IBC-Go's exact `ProcessCallback` panic-recovery behavior (external dependency, not present in this repo's indexed sources) — this cannot be confirmed with certainty from the available codebase index alone.
