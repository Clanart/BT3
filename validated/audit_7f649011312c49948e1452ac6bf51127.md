### Title
Hardcoded zero slippage in `WombatPoolHelperV2.depositFor` exposes depositors to sandwich/frontrunning losses - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor` deposits stable tokens into the underlying Wombat pool via `WombatStaking.deposit`, but unlike the public `deposit()` function (which lets the caller specify `_minimumLiquidity`), `depositFor` hardcodes the minimum-liquidity slippage parameter to `0`, exposing the depositor to loss of value from adverse pool-state changes between transaction submission and execution.

### Finding Description
The public `deposit` function allows the caller to pass a custom `_minimumLiquidity` value that is forwarded through `_deposit` → `WombatStaking.deposit` → `IWombatPool.deposit`: [1](#0-0) 

However `depositFor`, an unauthenticated `external` function callable by any wallet, hardcodes the minimum liquidity to `0` regardless of the actual deposited amount: [2](#0-1) 

This `0` is passed all the way to `_deposit`, then to `WombatStaking.deposit`, and finally to the Wombat pool's `deposit`, whose returned LP amount (`liabilityToMint`/`lpTokenToMint`) is a function of the pool's current `cash`/`liability` equilibrium — a value that can shift significantly between transaction submission and mining, or be manipulated in the same block by a preceding large deposit/withdraw (sandwich): [3](#0-2) 

Because there is no minimum-liquidity check, `WombatStaking.deposit` will mint receipt/staking tokens 1:1 with whatever (possibly much smaller) LP amount was actually received, without ever reverting: [4](#0-3) 

This is the same root cause as the referenced report: a slippage parameter that should be attacker/market-configurable is instead hardcoded to zero on a path that any unprivileged wallet can trigger (`depositFor` has no access control, unlike `SimplePoolHelper.depositFor` which requires `onlyAuthorized`) — so the deposit executes at whatever (possibly manipulated) pool price exists at execution time.

### Impact Explanation
A user (or integrator calling on a user's behalf) invoking `depositFor` can be sandwiched: an attacker skews the target Wombat pool's cash/liability ratio just before the victim's deposit executes, causing the victim to receive materially fewer LP/receipt/staking tokens than the fair-value amount for their deposited tokens, then reverts the skew afterward and profits from the mispriced mint. Because the receipt tokens minted directly represent claimable value in the pool, this results in a permanent, non-reversible loss of user funds with no reliance on any admin/oracle misbehavior — the attack is executable purely through ordinary transactions by any wallet.

### Likelihood Explanation
`depositFor` is `external` with no `onlyAuthorized`/access-control modifier (unlike the analogous function in `SimplePoolHelper.sol`), so it is directly reachable by any wallet or by any contract that calls it on behalf of a user. Sandwiching a pending public-mempool transaction with deposit/withdraw pairs against an AMM-like liquidity pool is a well-established, low-cost MEV technique, making exploitation practical whenever `depositFor` is used with a non-trivial deposit amount during periods of pool volatility or low liquidity.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` (mirroring `deposit`) and forward the caller-supplied value instead of hardcoding `0`:
```solidity
function depositFor(uint256 _amount, address _for, uint256 _minimumLiquidity) external {
    IERC20(depositToken).safeTransferFrom(msg.sender, address(this), _amount);
    IERC20(depositToken).safeApprove(wombatStaking, _amount);
    _deposit(_amount, _minimumLiquidity, _for, address(this));
}
```

### Proof of Concept
1. Attacker monitors mempool for a pending `depositFor(amount, victim)` call on `WombatPoolHelperV2`.
2. Attacker front-runs with a large deposit/withdraw (or swap) against the same Wombat pool's `depositToken`/`lpToken`, skewing `cash`/`liability` so that `getRsETH`-style mint calculation (here, `exactDepositLiquidityInEquilImpl`) yields far less LP per deposited token: [3](#0-2) 
3. Victim's `depositFor` executes with `_minimumLiquidity = 0`, so `WombatStaking.deposit` never reverts and mints `poolInfo.receiptToken` 1:1 with the reduced `lpReceived`: [5](#0-4) 
4. Attacker back-runs to restore the pool ratio and unwind their position, capturing the value the victim lost.
