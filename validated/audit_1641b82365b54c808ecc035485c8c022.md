### Title
Heuristic-based Git error suppression in stash handling can silently discard a user's stashed changes - ([File: app/src/lib/git/stash.ts])

### Summary
GitHub Desktop's stash handling code (`createDesktopStashEntry` and `popStashEntry`) mirrors the exact anti-pattern described in the external report: instead of trusting `git`'s exit code, the code applies a heuristic ("exit code 1 + no `error:` prefix in stderr" or "exit code 1 + empty stderr") to *guess* whether the underlying git operation actually succeeded, and defaults to treating it as success. Because the guess is based on parsing free-form, repository/locale-dependent text rather than a reliable signal, a repository or environment that produces atypical `git stash` output can cause Desktop to believe a stash was created/applied when it wasn't (or vice versa), leading to silent loss of the user's uncommitted work.

### Finding Description
In `createDesktopStashEntry`: [1](#0-0) 
the code catches a `GitError` for exit code 1 and searches stderr with the regex `/^error: /m`. If no line begins with the literal ASCII string `error: `, it assumes the stash succeeded anyway and returns the underlying result instead of re-throwing. This assumption is documented by the author themselves as unverified ("Here be dragons... That didn't hold up to a quick read of the stash code").

In `popStashEntry`: [2](#0-1) 
a similar heuristic is used: if `git stash pop` exits with code 1 and stderr is empty, Desktop assumes the pop succeeded (just didn't auto-drop the stash) and calls `dropDesktopStashEntry` to delete the stash entry from the reflog — permanently discarding it — without having actually verified that the working directory now contains the popped changes.

Both heuristics rely on the exact byte-for-byte format of git's stderr output. This format is not a stable, versioned API: it can vary based on the Git version bundled with dugite, localization (`LC_ALL`/`LANG` in the environment), or custom `core.editor`/hook output mixed into the stream, and it can be influenced by repository state that an attacker controls (e.g., a crafted repository history/working tree that puts `git stash` into an edge-case failure mode not covered by the original heuristic — the same "does not cover every case, leading to inconsistencies" flaw called out in the source report). When the heuristic misfires in the "assume success" direction, Desktop will either (a) proceed as though changes are safely stashed and continue with destructive operations (e.g., branch switching) that assume the working directory is clean, or (b) delete (`dropDesktopStashEntry`) a stash entry that was never actually applied, causing irrecoverable loss of the user's uncommitted changes.

### Impact Explanation
This breaks the invariant that a stash is only dropped/discarded after Desktop has confirmed the corresponding changes are safely restored. The corrupted value is the boolean/void success status returned by `createDesktopStashEntry`/`popStashEntry`, which downstream code (checkout flows) treats as ground truth. A misfire can result in silent loss of the user's local, non-committed work — a stronger form of "silent corruption of what the user commits" since the user's pending changes are destroyed with no explicit error surfaced. There is no `revert`-equivalent trap; like the audited contracts, the default assumption on ambiguous exit codes is success, not failure.

### Likelihood Explanation
Exploitation does not require local/admin access or leaked credentials — only a specially-crafted repository or working tree state, or a non-default environment (locale), that pushes `git stash` into one of the untested edge cases the code comment itself acknowledges (e.g., unborn HEAD, index corruption, etc., all of which are attacker-shaped repository states affecting a cloned/fetched repo). However, actually forcing the *exact* exit-code/stderr combination that flips the heuristic to "false success" is nontrivial and version/locale dependent, so likelihood is moderate rather than trivially reproducible from local static analysis alone — this is the main area of uncertainty in this finding.

### Recommendation
Do not infer success/failure of `git stash` operations from free-text heuristics on stderr. Use explicit, versioned mechanisms instead — e.g., check `git stash list` before and after the operation to confirm the actual stash state, or rely solely on documented exit codes without pattern-matching human-readable error text. Any git operation whose result heuristic is not 100% certain should fail loudly (throw / surface an error to the user) rather than silently assume success and perform destructive follow-up actions like `dropDesktopStashEntry`.

### Proof of Concept
Not independently reproduced in this analysis — reproduction would require constructing a repository/working-tree state or locale configuration that causes bundled `git stash push`/`git stash pop` to exit with code 1 while emitting stderr that lacks the literal `error: ` prefix (for the push case) or emitting no stderr at all (for the pop case), then observing Desktop treat the operation as successful and call `dropDesktopStashEntry`, discarding un-applied changes. Confirming this would require running the actual git binary version bundled with dugite in Desktop against various malformed/edge-case repository states, which is outside the scope of static code review.
