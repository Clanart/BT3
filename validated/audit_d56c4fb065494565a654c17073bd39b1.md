### Title
Nested/recursive precompile calls cause the `BalanceHandler` to double-apply (or leak) bank events into the EVM `StateDB`, corrupting balances - (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
This is the Cosmos EVM analog of the Perennial "timestamp checkpoint mismatch" bug class: a value is recorded relative to one checkpoint (`prevEventsLen`, analogous to the oracle's recorded request timestamp) but later consumed/interpreted against a different, shifted state (the full, ever-growing `ctx.EventManager().Events()` list, analogous to the pending position's rounded-forward timestamp). When precompile calls are nested/recursive (a very realistic and unprivileged pattern — an EVM contract calling one stateful precompile from inside another, or a token with `_beforeTokenTransfer`/`_afterTokenTransfer` hooks that call a precompile, or `try/catch`-wrapped precompile calls that revert), events emitted by an inner precompile call are read and applied to `StateDB` by an outer precompile's `BalanceHandler` too, because the underlying `sdk.Context` event manager and its growing event slice are shared across the nested calls while each nested call's `BalanceHandler` only knows its own "start index" checkpoint.

### Finding Description
Every stateful precompile call goes through `Precompile.runNativeAction` in [1](#0-0) , which:
1. Creates a fresh `BalanceHandler` via `p.BalanceHandlerFactory.NewBalanceHandler()`.
2. Calls `balanceHandler.BeforeBalanceChange(ctx)`, which records `prevEventsLen = len(ctx.EventManager().Events())` — a "checkpoint" into the shared event log [2](#0-1) .
3. Executes the precompile method (`action(ctx)`), which may itself trigger further EVM execution, which may in turn call the same or another stateful precompile (nested/recursive call).
4. After the action returns, calls `balanceHandler.AfterBalanceChange(ctx, stateDB)`, which iterates `events[bh.prevEventsLen:]` — i.e., every event appended to the manager since the checkpoint, unconditionally — and applies `CoinSpent`/`CoinReceived`/fractional-balance events to the EVM `StateDB` via `AddBalance`/`SubBalance` [3](#0-2) .

Because `ctx.EventManager().Events()` is a single, monotonically-growing slice shared by the whole call context, and `AfterBalanceChange` never truncates/marks the events it has consumed, the following composes incorrectly:
- Outer precompile call A starts, checkpoint `prevEventsLen_A = N`.
- Inside A's execution, a nested precompile call B starts, checkpoint `prevEventsLen_B = N+k` (after A's own bank events, if any, have already been appended).
- B emits bank events, then calls its own `AfterBalanceChange`, applying `events[N+k:]` to `StateDB` — correct for B in isolation.
- Control returns to A. A finishes and calls `AfterBalanceChange`, which processes `events[N:]` — this **includes the same events already consumed and applied by B**, because the event manager was never scoped or truncated between nested calls.
- Result: the balance deltas from B's bank operations get applied to `StateDB` a second time by A, corrupting the EVM-visible balance relative to the actual `x/bank` ledger — a direct violation of the "Asset-representation path" invariant (1:1 accounting between native coins, ERC20/precompile views, and stateDB balances).

The repository's own test suite documents this exact defect class:
- `evmd/tests/integration/balance_handler/balance_handler_test.go` is explicitly titled to test "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" [4](#0-3) .
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` states it "Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" [5](#0-4) , and uses a contract (`ERC20RecursiveRevertingPrecompileCall.sol`) whose `_beforeTokenTransfer` hook loops 5 times calling a distribution-precompile method wrapped in `try/catch` that always reverts [6](#0-5) , an entirely unprivileged, user-triggerable pattern (any ERC20/token contract with transfer hooks that call precompiles).
- The `DebugPrecompileCaller.sol` / debug precompile used to reproduce the bug is a minimal recursive precompile-call harness, confirming the mechanism is generic to any stateful precompile (ERC20, staking, distribution, gov, slashing, ICS20 — all of which use `BalanceHandlerFactory`, see `precompiles/erc20/erc20.go`, `precompiles/staking/staking.go`, `precompiles/distribution/distribution.go`, `precompiles/gov/gov.go`, `precompiles/ics20/ics20.go`, `precompiles/slashing/slashing.go`).

I was not able to fully confirm from the available static context whether the current `NewBalanceHandler()`-per-call factory pattern in `precompiles/common/precompile.go` fully eliminates the double-application across *nested* (not just sequential) calls, or whether it only fixed the earlier "singleton BalanceHandler stored on the precompile struct" variant still present in `testutil/testdata/debug/debug.go` (`p.GetBalanceHandler()` pattern). The event-manager sharing/non-truncation issue described above appears to persist independent of whether the handler instance itself is shared, because the vulnerability is in the *event log*, not the handler struct. This would require dynamic testing (e.g., running the existing `ICS20RecursivePrecompileCallsTestSuite`/`BalanceHandlerTestSuite` tests and asserting on `StateDB` vs bank-keeper balances) to conclusively confirm whether current mitigations (if any) fully prevent double-application in genuinely nested (not just revert-and-retry) scenarios.

### Impact Explanation
If confirmed exploitable, this allows an unprivileged user to deploy a contract that recursively calls a bank-affecting precompile (ERC20 precompile transfer, staking delegate/undelegate, distribution claim rewards, ICS20 transfer) from within a token hook or nested call, causing the EVM `StateDB` balance to be credited/debited more than the actual `x/bank`/`x/precisebank` state reflects. This is a direct **critical accounting-corruption / unauthorized duplication of spendable value** across native and EVM-visible balances, matching the explicitly allowed impact: "unauthorized minting, burning, duplication ... of spendable user value across native balances, EVM balances ... or precompile-mediated assets."

### Likelihood Explanation
The trigger requires only deploying and calling a normal smart contract with a transfer hook or nested call into a stateful precompile — no privileged role, validator, or relayer involvement is needed. The repository's own test suite already constructs exactly this scenario (recursive/nested precompile calls, including via `try/catch`-wrapped reverting calls), indicating the maintainers are aware of and actively testing this exact bug class, which increases confidence that the underlying event-log-sharing defect is real, though its current exploitability in the latest code state (post any partial fix) could not be conclusively verified without running the tests.

### Recommendation
Ensure `BalanceHandler.AfterBalanceChange` cannot re-process events that were already consumed by a nested/inner `BalanceHandler`. Options: (1) truncate or mark-consumed the portion of `ctx.EventManager().Events()` that has been applied to `StateDB` (e.g., by resetting to a fresh `EventManager` scoped per precompile call and merging results back explicitly), or (2) track a global/shared "high-water mark" across the whole nested call stack (via the `StateDB`/journal, not a per-call local `BalanceHandler`) so that each event is applied to `StateDB` exactly once regardless of nesting depth. Add explicit invariant tests asserting `StateDB` balances equal `x/bank`/`x/precisebank` balances after arbitrary nested/recursive precompile call sequences, including revert paths.

	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
