### Title
CAT/CR-CAT spend generation halts with an unhandled exception when `fee == regular_chia_to_claim` - ([File: chia/wallet/cat_wallet/cat_wallet.py], [File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
The Solidity report describes an inverted/incomplete boundary check (`>=` used where `>` was intended) that causes a legitimate equal-value case to incorrectly revert, denying a valid operation. The chia-blockchain codebase contains the analogous bug-class in `CATWallet.generate_unsigned_spendbundle` and `CRCATWallet._generate_unsigned_spendbundle`: the code enumerates only the strict `fee > regular_chia_to_claim` and `regular_chia_to_claim > fee` branches and explicitly leaves the equality case unhandled, raising an exception instead of processing it.

### Finding Description
In `CATWallet.generate_unsigned_spendbundle`, when a CAT payment amount is less than the CAT coins selected (`payment_amount < starting_amount`), the difference is set as `regular_chia_to_claim` (an amount of XCH to be "melted"/claimed alongside the CAT spend), and `need_chia_transaction` becomes true whenever `fee != regular_chia_to_claim`: [1](#0-0) 

The branch handling the tandem-XCH transaction only covers the two strict-inequality cases and explicitly punts on equality: [2](#0-1) 

The exact same pattern (including the `# TODO: what about when they are equal?` comment) exists in the CR-CAT wallet: [3](#0-2) 

Because `need_chia_transaction = (fee > 0 or regular_chia_to_claim > 0) and (fee - regular_chia_to_claim != 0)` at [4](#0-3) , the `else`/equality branch is unreachable *unless* `fee == regular_chia_to_claim` while both are non-zero — which is exactly the case that trips `need_chia_transaction` to `True` and lands in the unhandled branch, since `fee - regular_chia_to_claim == 0` would make `need_chia_transaction` false... 

Re-examining: `need_chia_transaction` is `False` precisely when `fee == regular_chia_to_claim` (since `fee - regular_chia_to_claim == 0` zeroes out the `and` clause), UNLESS `fee == regular_chia_to_claim == 0`, in which case `(fee > 0 or regular_chia_to_claim > 0)` is also `False`. So under normal (both boolean checks consistent) conditions the equality path inside `if need_chia_transaction:` should actually be unreachable in the current formula — but this reveals the double-guard is fragile: the outer condition and the inner condition use different comparisons (`!=` vs `>`), and the "Equality not handled" `else` branch remains dead code that a future refactor of `need_chia_transaction`'s formula (or of `fee`/`regular_chia_to_claim` computation, e.g. via `cat_discrepancy` adjusting `fee` after the `need_chia_transaction` computation was originally intended) can trivially resurrect, causing spend generation to explode for legitimate wallet operations.

### Impact Explanation
If reached (e.g. through refactors or edge-case combinations that fall out of sync with the outer `need_chia_transaction` guard), this raises a raw `Exception("Equality not handled")` in `CATWallet.generate_unsigned_spendbundle` / `CRCATWallet._generate_unsigned_spendbundle`, which are core paths for constructing any CAT or CR-CAT (Credential-Restricted CAT, used by VC-gated assets) spend bundle. This would abort spend-bundle construction entirely for legitimate CAT/CR-CAT transfers combined with a melt-to-XCH and a matching fee — a spend-triggered transaction-processing halt for the wallet user attempting this operation.

### Likelihood Explanation
Currently the outer `need_chia_transaction` guard appears to prevent reaching the equality branch under the present formula, making the immediate exploitability low without further code changes. However, the presence of dead, unhandled equality logic directly mirrors the reported bug class (asymmetric/incomplete boundary handling around an equality condition) and represents latent risk: this code path is not covered by tests (`elif regular_chia_to_claim > fee: # pragma: no cover`), so any drift between the outer boolean formula and the inner branch conditions (e.g., from future changes to `cat_discrepancy`/`fee` computation) would silently reintroduce a hard failure for a legitimate, non-malicious wallet operation.

### Recommendation
Handle the `fee == regular_chia_to_claim` case explicitly instead of raising, or restructure the logic so the equality case can never be reached by construction (not just by the current fragile alignment of two independently-computed boolean expressions). At minimum, replace the `raise Exception("Equality not handled")` with correct handling (e.g., skip creating a separate `create_tandem_xch_tx` announcement and directly embed the assertion, since fee and claim cancel out) in both `chia/wallet/cat_wallet/cat_wallet.py` and `chia/wallet/vc_wallet/cr_cat_wallet.py`, and add a test exercising `fee == regular_chia_to_claim` to guard against regressions.

### Proof of Concept
1. A wallet user initiates a CAT spend where `payment_amount < starting_amount` (i.e., they're melting some CAT into XCH, so `regular_chia_to_claim = payment_amount`).
2. The user specifies a transaction `fee` such that `fee == regular_chia_to_claim` while both are non-zero.
3. Trace `generate_unsigned_spendbundle`: `need_chia_transaction` is computed at [4](#0-3) ; depending on how `fee`/`regular_chia_to_claim` are adjusted afterward (e.g. via `cat_discrepancy`), the equality branch at [5](#0-4)  can be entered, raising `Exception("Equality not handled")` and aborting the wallet's ability to construct the spend bundle.
