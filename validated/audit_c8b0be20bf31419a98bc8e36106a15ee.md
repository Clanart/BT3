### Title
Uneconomical dust outputs trigger FROST signing of unspendable/unprofitable transactions - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to `GetRestorationProof` issuing a proof for a target that `Restore` will always reject, Serai's Bitcoin pipeline accepts any scanned output whose value is at least `N::DUST` and unconditionally schedules `Plan`s and FROST signing rounds for it — including plans that cannot possibly pay their own fee. `Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214` admits any output whose `script_pubkey` matches a registered offset, and the processor-side filter in `processor/src/multisigs/scanner.rs:562-566` only checks `output.balance().amount.0 >= N::DUST` (the relay dust limit, ~546 sat), not whether the output can be profitably spent. `Scheduler::schedule` (`processor/src/multisigs/scheduler/utxo.rs:303-451`), `refund_plan` (`utxo.rs:587-605`), and `shim_forward_plan`/`forward_plan` (`utxo.rs:607-630`) then build `Plan`s spending these inputs with `change: None` and the full balance as the payment, triggering coordinator `Transaction::Sign` rounds and signature-share computation for transactions that `SignableTransaction::new` either rejects outright or that relay at a net loss.

### Finding Description
- `scan_transaction` matches solely on `output.script_pubkey` against the `scripts` map; any unprivileged party can craft a P2TR output to `key + offset*G` of arbitrary value.
- The only value gate is `N::DUST` in `processor/src/multisigs/scanner.rs:564`. At feerates above ~9–10 sat/vB, spending a single 546-sat P2TR input costs more than its value.
- `add_outputs` pushes every non-Branch output into `self.utxos` unconditionally (`utxo.rs:295`); `schedule` aggregates and generates signing `Plan`s for all of them (`utxo.rs:376-385`, `423-431`).
- `refund_plan`/`shim_forward_plan` emit `Plan`s where the payment equals `output.balance()` with `change: None` (`utxo.rs:593-601`, `608-618`), so the entire input must cover both payment and fee — a construction that fails for any output at or near dust.
- No analogous "will this plan survive downstream" check exists before the coordinator broadcasts `CoordinatorMessage::Preprocesses`/`Shares` and validators burn signing work, mirroring how `GetRestorationProof` emits a proof the EVM will always reject.

### Impact Explanation
An unprivileged attacker repeatedly sends dust-value deposits to Serai's external/forward/branch addresses. Each deposit is scanned, emitted as a `ScannerEvent::Block`, scheduled, and put through threshold FROST signing (preprocess + share rounds across the validator set) and batch submission, causing validators to burn coordination bandwidth, signing computation, and — where the transaction is broadcastable — network fees on provably uneconomical inputs. Like the report's gas-burn scenario, the requester bears no cost beyond the dust output itself, while the honest multisig operators bear recurring cost. Severity: Medium (resource/fee burn, no secret leakage or forged signatures).

### Likelihood Explanation
Deposit addresses are public and outputs are matched only by `script_pubkey`, so any external party can trigger the path with a single on-chain transaction per attempt. No validator privileges, leaked keys, or collusion are required; the only prerequisite is Bitcoin feerate conditions under which a dust-adjacent input is unprofitable, which is common.

### Recommendation
Add an economic-viability check before scheduling/signing — the analog of "reject a contract `Target` before generating the proof." Concretely, in `processor/src/networks/bitcoin.rs::get_outputs` (or in `Scheduler::add_outputs`), estimate the marginal spend cost of the input via the transaction's `needed_fee` accounting and drop outputs whose value cannot cover it; also refuse `Plan` construction in `refund_plan`/`shim_forward_plan` when `output.balance()` is below the estimated fee, rather than emitting a plan guaranteed to fail at `SignableTransaction::new` or be relayed at a loss.

### Proof of Concept
1. Obtain the multisig's forward/external address (`forward_address`/`external_address` in `processor/src/networks/bitcoin.rs:671-673`).
2. Broadcast a transaction paying exactly `N::DUST` satoshis to that script while mempool feerate is high.
3. `Scanner::scan_transaction` returns a `ReceivedOutput` (`wallet/mod.rs:205-211`); `get_outputs` keeps it (`scanner.rs:564`); `Scheduler::schedule`/`forward_plan` emits a `Plan` and `BatchSigner::sign`/`attempt` initiates FROST signing (`processor/src/batch_signer.rs:192-202`).
4. The resulting `SignableTransaction` either fails construction (wasted signing round, retried per attempt logic) or spends more in fees than the input is worth — repeatable at the attacker's discretion.

Note: `networks/bitcoin/src/wallet/mod.rs` contents beyond line ~229 (including `SignableTransaction::new`'s exact fee/change handling) were not retrievable from the index due to coverage limits, so the precise failure-vs-net-loss branch at signing time is inferred from the scheduler's `change: None` plans and the test's `needed_fee` assertions rather than verified line-by-line.
