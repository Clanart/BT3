### Title
Missing zero-amount guard before `SmartWomConvert.smartConvert` call in `WombatStaking._sendRewards` causes deposit/withdraw DoS — (File: wombat/WombatStaking.sol)

### Summary
`WombatPoolHelper.withdraw` (and `deposit`/`depositLP`/`harvest`) unconditionally routes through `WombatStaking._toMasterWomAndSendReward` → `_sendRewards`, which, for any active fee entry flagged `isMWOM` with `smartWomConverter` set, calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)` without checking that `feeAmount > 0`. `SmartWomConvert.smartConvert` explicitly reverts with `MustNoBeZero()` when its input is zero, so any harvested WOM amount small enough that `feeAmount = originalRewardAmount * feeInfo.value / DENOMINATOR` rounds down to zero causes the entire `withdraw`/`deposit`/`harvest` transaction to revert.

### Finding Description
`WombatPoolHelper.withdraw` (wombat/WombatPoolHelper.sol) calls `IWombatStaking(wombatStaking).withdraw(...)` on every single principal withdrawal: [1](#0-0) 

`WombatStaking.withdraw` unconditionally invokes `_toMasterWomAndSendReward`, which triggers the master-wombat harvest and then routes all accrued WOM through `_sendRewards`: [2](#0-1) [3](#0-2) 

Inside `_sendRewards`, for each active fee entry, `feeAmount` is computed by integer division and, when the fee is `isMWOM` and a `smartWomConverter` is configured, `smartConvert(feeAmount, 0)` is called **unconditionally**, with no check that `feeAmount > 0`: [4](#0-3) 

`SmartWomConvert.smartConvert` reverts immediately if its input is zero: [5](#0-4) 

Because `feeAmount = originalRewardAmount * feeInfo.value / DENOMINATOR` (DENOMINATOR = 10000), any time the harvested `womRewards` (i.e. `originalRewardAmount`) is nonzero but small enough that this multiplication rounds down to 0 (e.g., `womRewards < 10000/feeInfo.value`), the call reverts with `MustNoBeZero()`. Since `_toMasterWomAndSendReward` is invoked on **every** `deposit`, `depositLP`, `withdraw`, and `harvest`, this reverts the entire outer transaction — blocking principal withdrawal for `msg.sender` and, because the pool state (accrued rewards in `masterWombat`) is not the attacker's individual balance but a pool-wide accrual, any other user's withdraw/deposit call in the same pool during that window fails identically. This directly ties principal movement to the success of an unrelated, optional reward-conversion leg, exactly matching the mechanism described in the question. No owner/poolManager/rewardManager privilege is needed to trigger this — any unprivileged withdraw call while the pending WOM is in the "rounds-to-zero" band reverts.

The existing `nonReentrant`/`whenNotPaused`/`_onlyPoolHelper` modifiers on `WombatStaking.withdraw` do not protect against this: they don't validate reward-fee rounding conditions, so they do not prevent the revert.

### Impact Explanation
When the described precondition holds (an active `isMWOM` fee entry with `smartWomConverter != address(0)`), a pool whose harvested WOM rewards intermittently fall into the "rounds-to-zero" band (small fee value combined with low or newly-registered pool emission) becomes unable to process `deposit`, `depositLP`, `withdraw`, or `harvest` calls. Because the failure mode is a hard revert rather than a partial/graceful path, users cannot withdraw principal, satisfying Immunefi's "Temporary freezing of funds" class. The duration of the freeze is bounded by however long it takes the pool's per-block WOM harvest to exceed the rounding threshold (`DENOMINATOR / feeInfo.value` wei) — for low-fee-value/low-emission pools this can exceed 24 hours.

### Likelihood Explanation
No privileged role is required to trigger the revert — it happens automatically to whichever user (attacker or victim) is the first to call `deposit`/`withdraw`/`harvest` while the accrued WOM is in the "rounds-to-zero" band; an attacker can even actively keep triggering (and reverting) `harvest()`/`withdraw()` attempts to observe/confirm the state without needing any tokens beyond gas. It does require the specific fee configuration precondition given in the question (active `isMWOM` fee + `smartWomConverter` set), which is a plausible, non-misconfigured production state (this is literally the intended flow for buying back mWOM with harvested WOM), and a pool/fee-value combination where per-harvest WOM is small relative to `DENOMINATOR/feeInfo.value`. This is most likely immediately after pool registration or for pools with low allocation, but does not require any external price manipulation.

### Recommendation
Guard the `smartConvert` (and the plain `mWom.deposit`) calls in `WombatStaking._sendRewards` with `if (feeAmount > 0) { ... }`, mirroring the top-level `if (_amount == 0) return;` check, so that a zero (or rounded-to-zero) fee amount never reaches an external call that unconditionally reverts on zero input. More broadly, consider decoupling the harvest/fee-distribution logic from the principal `deposit`/`withdraw` critical path (e.g., making harvest best-effort/try-catch) so that a revert in an optional reward leg cannot block principal movement.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `WombatStaking`, register a pool via `registerPool`, deploy `SmartWomConvert` and call `setSmartConvert`.
2. Call `addFee(value=1, to=<rewarder>, isMWOM=true, isAddress=false)` (a realistic small fee, e.g., 0.01%) and set `isActive=true`.
3. Have a user deposit into the pool so there is a nonzero stake, and let masterWombat/mock accrue a tiny amount of pending WOM (e.g., 1–50 wei) — achievable right after pool registration when accrual is minimal, or by using `MasterWombatMock` to set `pendingTokens` to a small deterministic value.
4. As an unprivileged EOA, call `WombatPoolHelper.withdraw(_liquidity, _minAmount)`.
5. Assert the transaction reverts with `MustNoBeZero()` (bubbled from `SmartWomConvert.smartConvert`), and that `IERC20(stakingToken).balanceOf(address(this))` and `IMasterMagpie(masterMagpie).stakingInfo(stakingToken, _for).staked` remain unchanged (no withdrawal succeeded), demonstrating principal is stuck as long as the pending WOM stays under `DENOMINATOR/feeInfo.value` wei.
