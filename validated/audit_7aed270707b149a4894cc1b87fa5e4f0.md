### Title
Deposit Liveness Failure: `collateral_check` Returns `false` for Operators Whose Round Tx Is In Mempool, Permanently Blocking In-Flight Deposits - (File: `core/src/extended_bitcoin_rpc.rs`)

---

### Summary

`collateral_check` uses `is_tx_on_chain` (confirmed-only) to advance the collateral chain but uses `is_utxo_spent` (mempool-aware) to decide if the final collateral UTXO is consumed. When an operator's round transaction is in mempool but not yet confirmed, the function sees the original collateral as spent but the round tx as absent, concludes the operator has exited the protocol, and returns `false`. Because the aggregator builds deposit data from all registered operators without any collateral check, and verifiers call `is_deposit_valid` (which calls `collateral_check`) during both `deposit_sign` and `deposit_finalize`, any deposit that includes this operator is rejected mid-flight. The user's BTC is locked in the deposit address until the `user_takes_after` timelock expires.

---

### Finding Description

**Aggregator builds deposit data without collateral validation.**

In `core/src/rpc/aggregator.rs` `new_deposit` (lines 1464–1473), the aggregator constructs `deposit_data` by calling `self.fetch_operator_keys()`, which returns the public keys of every registered operator with no collateral check:

```rust
let deposit_data = DepositData {
    deposit: deposit_info.clone(),
    nofn_xonly_pk: None,
    actors: Actors {
        verifiers: self.fetch_verifier_keys().await?,
        watchtowers: vec![],
        operators: self.fetch_operator_keys().await?,   // ← all operators, no collateral check
    },
    security_council: self.config.security_council.clone(),
};
``` [1](#0-0) 

**Verifiers enforce collateral validity during signing.**

Both `deposit_sign` (line 876) and `deposit_finalize` (line 994) in `core/src/verifier.rs` call `is_deposit_valid`, which calls `collateral_check` for every operator in the deposit data: [2](#0-1) [3](#0-2) 

If `collateral_check` returns `false` for any operator that is present in the deposit data, the deposit is rejected:

```rust
if operators_in_deposit_data.contains(xonly_pk) && !is_collateral_usable {
    return Err(BridgeError::InvalidDeposit(reason));
}
``` [4](#0-3) 

**`collateral_check` mixes confirmed-only and mempool-aware queries.**

The function iterates the round-tx chain using `is_tx_on_chain` (confirmed blocks only). When a round tx is in mempool, the loop breaks and `current_collateral_outpoint` stays at the previous (original) collateral outpoint. The final check uses `is_utxo_spent`, which is mempool-aware:

```rust
for round_idx in RoundIndex::iter_rounds(paramset.num_round_txs) {
    ...
    let is_round_tx_on_chain = self.is_tx_on_chain(&round_txid).await?;
    if !is_round_tx_on_chain {
        break;   // ← loop exits; current_collateral_outpoint stays at original
    }
    current_collateral_outpoint = OutPoint { txid: round_txid, vout: ... };
    ...
}
// mempool-aware check on the stale outpoint
Ok(!self.is_utxo_spent(&current_collateral_outpoint).await?)
``` [5](#0-4) 

**The inconsistency produces a false negative.** When the operator's automation sends a round tx (spending the original collateral UTXO) and that tx is in mempool but not yet confirmed:

| Query | Result | Reason |
|---|---|---|
| `is_tx_on_chain(round_txid)` | `false` | not in a block yet |
| `is_utxo_spent(original_collateral)` | `true` | spent by mempool round tx |

`collateral_check` therefore returns `false`, signalling "operator exited protocol", even though the operator is legitimately advancing to the next round.

---

### Impact Explanation

The deposit signing pipeline has an `OVERALL_DEPOSIT_TIMEOUT` of 2 hours. During this window, any operator's automation may broadcast a round tx. Because the aggregator includes all registered operators unconditionally, and verifiers re-run `is_deposit_valid` at both `deposit_sign` and `deposit_finalize`, a round tx entering mempool at any point during the pipeline causes the deposit to fail with `BridgeError::InvalidDeposit`.

The user's BTC is already locked in the deposit address (the deposit UTXO is on-chain). A failed deposit leaves it locked until the `user_takes_after` timelock script path becomes spendable. Depending on configuration, this can be weeks. This is a liveness failure with material fund impact on bridged BTC. [6](#0-5) 

---

### Likelihood Explanation

- The aggregator always includes every registered operator; there is no pre-flight collateral check.
- The deposit pipeline can run for up to 2 hours (`OVERALL_DEPOSIT_TIMEOUT`).
- Operator automation sends round txs as part of normal reimbursement flow; this is not an adversarial action.
- The window is wide enough that any active operator cycling through rounds will trigger this condition during a busy bridge.
- No special privileges or external conditions are required; the trigger is normal protocol operation. [7](#0-6) 

---

### Recommendation

**Option A (preferred):** In `collateral_check`, use a mempool-aware tx lookup (e.g., `get_tx_of_txid` which already queries both mempool and chain) to advance the collateral chain, not just `is_tx_on_chain`. If the round tx is found in mempool, treat the collateral as still in-protocol (the round tx is a deterministic pre-signed tx whose txid cannot change via RBF because it uses CPFP anchor outputs).

**Option B:** In the aggregator's `new_deposit`, call `collateral_check` for each operator before including it in `deposit_data`. Operators whose collateral is in transition are excluded from this deposit. This eliminates the race condition at the source.

**Option C:** In `is_deposit_valid`, treat a `false` result from `collateral_check` for an operator that is in the deposit data as a transient condition (retry or exclude) rather than a hard rejection, provided the operator's collateral UTXO was spent by a known protocol transaction.

---

### Proof of Concept

1. Operator `O` is registered; collateral UTXO `C0` is confirmed on-chain.
2. User calls `new_deposit` on the aggregator. Aggregator builds `deposit_data` with `O` included (no collateral check). Deposit signing pipeline starts.
3. Operator `O`'s automation broadcasts a round tx `R0` that spends `C0`. `R0` enters mempool but is not yet confirmed (e.g., fee market spike).
4. Verifier calls `deposit_sign` → `is_deposit_valid` → `collateral_check(O)`:
   - `is_tx_on_chain(R0.txid)` → `false` → loop breaks, `current_collateral_outpoint = C0`
   - `is_utxo_spent(C0)` → `true` (spent by `R0` in mempool)
   - Returns `false`
5. `is_deposit_valid` hits line 638–644: operator `O` is in deposit data but `is_collateral_usable = false` → returns `BridgeError::InvalidDeposit("Operator ... collateral is spent")`.
6. `deposit_sign` / `deposit_finalize` fails; the aggregator's `new_deposit` returns an error.
7. User's BTC remains locked in the deposit address. Recovery requires waiting for the `user_takes_after` timelock (e.g., `paramset.user_takes_after` blocks). [8](#0-7) [4](#0-3) [1](#0-0)
