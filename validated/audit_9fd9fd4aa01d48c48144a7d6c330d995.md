### Title
FROST threshold secret share serialized to disk in plaintext - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::write` / `ThresholdKeys::serialize` in `crypto/dkg/src/lib.rs` persist a validator's FROST secret share — the threshold signing credential equivalent to the SSH key passphrases in CVE-2017-1000245 — as raw unencrypted field-element bytes, with no encryption, no integrity protection, and no documentation warning the caller that the output must be protected.

### Finding Description
The Jenkins SSH plugin bug class is: a long-lived secret granting signing/authentication capability is written to persistent storage in plaintext, so anyone who can read the storage (backup, DB snapshot, log shipping, co-tenant process, path traversal in another component) recovers the credential without attacking the cryptography at all.

In `crypto/dkg/src/lib.rs`, `ThresholdKeys<C>::write` serializes the credential fields and then writes the secret share verbatim:

```rust
// crypto/dkg/src/lib.rs:553-555
let mut share_bytes = self.core.secret_share.to_repr();
writer.write_all(share_bytes.as_ref())?;
share_bytes.as_mut().zeroize();
```

`serialize()` (`crypto/dkg/src/lib.rs:567-571`) returns the same plaintext encoding. The only mitigation is zeroizing the temporary buffer *after* the bytes have already been emitted to the caller's `Write` sink, which is typically a file or database row.

This stands out against Serai's own security posture: `coordinator/src/tributary/signing_protocol.rs:104-114` explicitly encrypts `CachedPreprocesses` before writing them to the DB, with the comment that "the DB isn't expected to be arbitrarily readable... shouldn't be trusted as one" — yet the far more sensitive `ThresholdKeys` secret share (a permanent credential, not a single-session nonce) is serialized with no such protection at the library layer that all consumers share.

### Impact Explanation
Any party that obtains read access to wherever the serialized `ThresholdKeys` blob is stored (DB dump, disk image, misconfigured backup, another on-path component) recovers the validator's FROST secret share directly — no signature forgery or protocol attack needed. Combined with `t` shares, or combined with a single additional compromised share, the attacker can sign arbitrary messages/Bitcoin transactions as the validator set. This is the same impact as the Jenkins bug: plaintext-at-rest credentials convert any storage-read primitive into full credential compromise.

### Likelihood Explanation
This is the library's designated persistence path — any node that restarts must call `serialize`/`write` and `read`, so the plaintext secret share necessarily exists at rest on every validator. Exploitation requires a storage-read capability, which is a weaker precondition than exploiting a cryptographic flaw; the codebase itself acknowledges DB reads are a realistic threat model for the less-sensitive cached preprocess. Severity Medium-High: requires an adjacent read primitive, but the exposed secret is maximal and permanent.

### Recommendation
Encrypt the secret share portion at rest inside `ThresholdKeys::write`/`serialize` (e.g., keyed AEAD derived from a node secret, as done for `CachedPreprocesses` in `signing_protocol.rs`), and document that the plaintext form must never touch untrusted storage. At minimum, add an explicit doc warning that the serialized blob contains the raw secret share.

### Proof of Concept
```rust
// Any holder of a ThresholdKeys<C> writes its secret share in plaintext:
let keys: ThresholdKeys<C> = ...;           // from a completed DKG
let blob = keys.serialize();                 // Zeroizing<Vec<u8>>

// blob layout (crypto/dkg/src/lib.rs:538-561):
//   id_len || C::ID || t || n || i || interpolation || SECRET_SHARE || shares...
// The field element `secret_share` is recoverable by reading the bytes at the
// documented offset — no decryption key exists because none is used.
// ThresholdKeys::read (line 574) will happily reconstruct the credential from
// a stolen blob, yielding a working signer for that Participant index.
```
Contrast with `coordinator/src/tributary/signing_protocol.rs:107-131`, where the preprocess seed is XOR-masked with `Blake2s256("Cached Preprocess Encryption Key" || context || secret_key)` before hitting the DB — demonstrating both that plaintext-at-rest secrets are a recognized threat in this codebase and that the `ThresholdKeys` path lacks the protection.
