### Title
Partial-commit line selection is applied against a freshly re-read diff, letting concurrent working-directory writes silently smuggle unreviewed content into a commit - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex` re-derives the diff from disk at commit time instead of using the diff the user actually reviewed and selected lines against, then applies the user's `DiffSelection` (a set of line *indices*) to that newly-fetched diff. If the working-directory file changes between the moment the user makes a partial line selection (in the UI) and the moment `commitIncludedChanges`/`stageFiles` runs, the line indices in the stale selection no longer correspond to the same content, and `git apply --cached` will stage whatever lines now occupy those positions - not what the user saw and checked in the diff viewer.

### Finding Description
The partial-commit flow works as follows:
1. The renderer loads a diff for the currently selected file via `getWorkingDirectoryDiff` and displays it (`app/src/lib/stores/app-store.ts` `_selectWorkingDirectoryFiles` / `updateChangesWorkingDirectoryDiff`, `app/src/ui/changes/changes.tsx`).
2. The user toggles individual lines/hunks; this produces a `DiffSelection` keyed by **absolute line index** in that specific diff (`onDiffLineIncludeChanged` → `dispatcher.changeFileLineSelection`).
3. When the user commits, `createCommit` → `stageFiles` (`app/src/lib/git/update-index.ts:109-168`) is invoked, and for any file with a partial selection it calls `applyPatchToIndex(repository, file)`.
4. Critically, `applyPatchToIndex` does **not** reuse the diff that produced the selection. It calls `getWorkingDirectoryDiff(repository, file)` again, live, at commit time: [1](#0-0) 
5. `formatPatch(file, diff)` then walks this brand-new diff's hunks/lines and asks `file.selection.isSelected(absoluteIndex)` for each line, using the index positions from the *old* diff against the *new* diff's line layout: [2](#0-1) 

There is no check anywhere in this path that the diff used to build the patch is the same diff (same content/hash) that the `DiffSelection` was computed against. Contrast this with the read paths in the same codebase, which are careful about this exact problem: `_selectWorkingDirectoryFiles`'s diff-loading routine explicitly re-validates that "a different file (or files) could have been selected while we were loading the diff" and recomputes `selectableLines` before applying an old selection to a new diff: [3](#0-2) 
That defensive re-validation exists for *display* purposes only. It is never invoked or consulted by the commit-time code path (`apply.ts` / `update-index.ts` / `commit.ts`), which is the code path that actually determines what bytes get written into the repository's history.

This is structurally identical to the `Staker.shiftTokens` bug: a value (`amountStakedSyntheticToken` there, `DiffSelection` line indices here) is computed/validated against one state snapshot, but consumed against a different, later state snapshot, with no invariant check tying the two together. In `shiftTokens` this let a user shift more tokens than they had staked; here it lets whatever is on disk at commit time bypass the user's actual line-by-line review.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." If a file is modified between diff display and commit — e.g., by a build tool, an IDE, a Git hook, a background formatter/linter, an npm postinstall script from a package the user just installed, or literally any other process writing into the working tree while GitHub Desktop's UI is idle waiting for the user to click "Commit" — the lines actually staged and committed can differ from the lines the user reviewed and explicitly selected in the diff viewer. An attacker who can trigger a file write in the repository during this window (a very small window is not even required; only that the file changes before the user hits commit) can cause code the user never approved to be silently included in a commit that is then pushed, with the user believing they only committed the specific lines they checked.

### Likelihood Explanation
Partial (line/hunk-level) commit selection is a heavily used, core GitHub Desktop feature (`app/test/unit/git/commit-test.ts` exercises exactly this "commit only some lines" scenario extensively). There is no synchronization, hashing, or generation check between the diff used for selection and the diff used for patch generation — `getWorkingDirectoryDiff` is called a second time from scratch in `applyPatchToIndex` with no guard. Any legitimate background process that touches the file (auto-formatters, linters, watchers, git hooks, other tooling) during the (however brief) interval between "user finishes selecting lines" and "user clicks commit" is sufficient to trigger the mismatch; no privileged access or unusual user action is required beyond normal development workflows.

### Recommendation
`applyPatchToIndex` (and `stageFiles`) should not silently re-fetch a fresh diff at commit time. Instead:
- Pass the exact diff (or a content hash/generation token of it) that was used to build the `DiffSelection` through to `stageFiles`/`applyPatchToIndex`, and fail (or re-prompt the user) if the working-directory file's current diff differs from the one the selection was made against.
- Alternatively, re-validate — as `_selectWorkingDirectoryFiles`'s display path already does — that all previously-selected line positions still correspond to the same line content before generating the patch, and abort/require re-review of the commit if they don't.

### Proof of Concept
1. Open a repository with a large modified file in GitHub Desktop; select the "Changes" view for that file.
2. In the diff viewer, uncheck all lines except a few benign ones near the top of the file (a partial `DiffSelection`), but do not commit yet.
3. Concurrently (background formatter, `git hook`, IDE auto-save, or any other process with write access to the working directory) insert/remove lines earlier in the file so that line offsets shift, or directly rewrite content at the positions the user's selection indices reference.
4. Click "Commit." `stageFiles` → `applyPatchToIndex` calls `getWorkingDirectoryDiff` fresh (`app/src/lib/git/apply.ts:60`), and `formatPatch` (`app/src/lib/patch-formatter.ts:143-172`) applies the stale `file.selection.isSelected(absoluteIndex)` bitmap against this new diff.
5. Inspect the resulting commit: the staged content corresponds to whatever now occupies the selected index positions in the new diff, not the lines the user actually reviewed and checked in step 2 — demonstrating silent corruption of the commit contents.
