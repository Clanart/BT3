### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new` enables CPU-exhaustion DoS via attacker-supplied `ThresholdKeys` bytes - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a fully attacker-controlled `(t, n, i)` triple (each a `u16`, up to 65535), then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` once per participant in `1 ..= t`. For `Interpolation::Lagrange`, each `interpolation_factor` call is itself O(t) field multiplications plus one field inversion, making group-key derivation O(t²) in attacker-chosen parameters — a quadratic-work analog of the league/commonmark super-linear parsing DoS.

### Finding Description
`ThresholdKeys::read` deserializes `t` and `n` directly from the input stream with no bound other than `ThresholdParams::new`'s checks (`t <= n`, `i <= n`, non-zero) (`crypto/dkg/src/lib.rs:591-602`, `crypto/dkg/src/lib.rs:166-178`). It then reads `n` verification shares and invokes `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:620-631`).

`ThresholdKeys::new` derives the group key as `sum(verification_shares[i] * interpolation_factor(i, &t))` over `i in 1..=t` (`crypto/dkg/src/lib.rs:376-378`). `interpolation_factor` for Lagrange iterates over every element of `included` performing a field multiply on the numerator and denominator, then performs a field inversion (`crypto/dkg/src/lib.rs:229-246`). With `t = n = 65535`, that is 65535 outer iterations × 65535 inner field multiplications ≈ 4.3×10⁹ multiplications plus 65535 inversions and 65535 variable-base point multiplications — triggered by a serialized payload of only ~`n * 32` ≈ 2–4 MB (the verification-share encodings are the dominant input cost; each `read_G` reads a fixed-size `GroupEncoding::Repr`).

The same quadratic shape recurs in `ThresholdKeys::view`, which calls `interpolation_factor` once per element of `included` (`crypto/dkg/src/lib.rs:500-507`), so the cost is repeated on every `view`/`sign` call against a deserialized key.

### Impact Explanation
An unauthenticated party who can cause a victim to run `ThresholdKeys::read` (or borsh-deserialize `ThresholdKeys`) on untrusted bytes — a path explicitly reachable per the in-scope surface — burns minutes of CPU per ~2 MB request. Because the work happens inside the constructor before any validity of the shares is established, no cryptographic check gates the amplification. Repeated submissions exhaust CPU on validators/processors, stalling signing and DKG rounds. This is availability-only impact, matching the advisory class.

### Likelihood Explanation
Reachability depends on the integrator feeding untrusted bytes to `ThresholdKeys::read`; the rules explicitly include `ThresholdKeys::read` in the untrusted-input surface. The trigger is a single short header (`t`/`n`/`i` fields) plus a linear amount of point encodings; no crafted structure, valid proofs, or honest shares are needed — the quadratic work precedes any verification that would reject the keys.

### Recommendation
Enforce a sane upper bound on `n`/`t` in `ThresholdParams::new` or at the `ThresholdKeys::read` boundary before allocating/interpolating (e.g., reject `n` above a protocol maximum such as the largest supported validator set). Additionally, `ThresholdKeys::new` could compute Lagrange group keys via the O(t) prefix/suffix product trick (batch inversion with a single `invert` over the product), and `view` could cache interpolation factors.

### Proof of Concept
```rust
// PoC: quadratic CPU in ThresholdKeys::read via attacker-chosen t = n = u16::MAX
use std::io;
use ciphersuite::{Ciphersuite, group::GroupEncoding, Secp256k1};
use dkg::{ThresholdKeys, Participant, ThresholdParams};

fn main() -> io::Result<()> {
  let mut buf = vec![];

  // Curve ID
  buf.extend((Secp256k1::ID.len() as u32).to_le_bytes());
  buf.extend(Secp256k1::ID);

  // t = n = u16::MAX, i = 1 — all pass ThresholdParams::new (t <= n, i <= n)
  buf.extend(u16::MAX.to_le_bytes()); // t
  buf.extend(u16::MAX.to_le_bytes()); // n
  buf.extend(1u16.to_le_bytes());     // i (Participant)

  // Interpolation::Lagrange (tag 1)
  buf.push(1);

  // secret_share: scalar 1
  buf.extend(<Secp256k1 as Ciphersuite>::F::ONE.to_repr());

  // n verification shares: generator encoding repeated
  let g = <Secp256k1 as Ciphersuite>::generator().to_bytes();
  for _ in 0 .. u16::MAX {
    buf.extend(g.as_ref());
  }

  // ~2.1 MB input triggers ~4.3e9 field muls + 65535 inversions + 65535 point muls
  // inside ThresholdKeys::new's group-key derivation (interpolation_factor per i).
  let _keys = ThresholdKeys::<Secp256k1>::read(&mut buf.as_slice())?;
  Ok(())
}
```
Note `ThresholdKeys::read` reads exactly `n` F/G encodings, so input size is linear in `n` while CPU is quadratic — the amplification factor itself grows with input size, matching the advisory's profile.
