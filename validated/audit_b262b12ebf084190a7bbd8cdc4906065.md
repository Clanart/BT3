## Confirmed: stale line-selection applied against a freshly re-diffed file at commit time

### Title
Stale line-index `DiffSelection` applied against a freshly re-fetched diff silently commits attacker-influenced content — (File: `app/src/lib/git/apply.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
The Blend report's broken invariant is: a mutated value (`d_supply` updated in memory) is not carried forward; a later step re-reads the *original* stale value from a different source of truth (storage) and persists it, silently corrupting global state. GitHub Desktop has a structurally identical pattern for commits: the user's partial-line selection (`DiffSelection`, an index-based bitmap) is computed against one diff snapshot but applied, at staging time, against a *different, freshly re-fetched* diff of the same file — with no check that the two diffs still agree on line positions.

### Finding Description
`_commitIncludedChanges` in `app/src/lib/stores/app-store.ts` reads the currently cached working-directory files straight out of `repositoryStateCache` and passes their `selection` objects, unmodified, into `createCommit`: [1](#0-0) 

`createCommit` (`app/src/lib/git/commit.ts`) unstages everything and calls `stageFiles`, which for any file with a `Partial` selection calls `applyPatchToIndex`: [2](#0-1) 

Crucially, `applyPatchToIndex` does **not** reuse the diff object the UI showed the user when they picked which lines to include — it re-fetches the diff live from the working directory at apply time: [3](#0-2) 

That freshly fetched diff is then combined with the (potentially stale) `file.selection`, whose `isSelected(absoluteIndex)` calls are purely positional (hunk/line offsets), with no correlation to actual line content: [4](#0-3) 

The only place that re-validates a `DiffSelection` against a new diff is `updateChangesWorkingDirectoryDiff`, and it only runs when the UI explicitly reloads the diff for display (e.g. re-selecting the file), recomputing `selectableLines` from the new diff: [5](#0-4) 

This reconciliation is never invoked as part of the commit path. It is also insufficient even when it does run: `updateChangedFiles` in `changes-state.ts` explicitly *preserves* the old `Partial` selection object across a background status refresh (unless `clearPartialState` is requested), it does not invalidate or remap it to the new diff's line numbers: [6](#0-5) 

So the sequence an attacker can exploit is:
1. User opens a diff for a tracked file in a cloned/checked-out attacker-controlled repository and selects specific lines/hunks for a partial commit (`DiffSelection` positions computed against diff D1).
2. Before the user clicks "Commit", the file's on-disk content changes without the UI reloading the diff — e.g. a Git clean/smudge filter, a `.gitattributes`-driven text conversion, a background `post-checkout`/`post-merge` hook (any of which the repo owner controls and Desktop will execute once the user trusted the directory), or simply another background `_loadStatus`/`refreshChangesSection` call that updates file content metadata but preserves the stale selection per `updateChangedFiles`.
3. The user clicks Commit. `applyPatchToIndex` re-diffs the file (diff D2, different hunk layout/line offsets) and applies the old D1-based `DiffSelection` bit positions to D2's lines via `formatPatch`.
4. Because `DiffSelection.isSelected` is purely a positional/index lookup with no diff-identity check, lines that the user never reviewed or intended to include can be silently staged and committed (or vice versa, lines the user wanted included get dropped) — while the UI told the user a different, safe set of lines was chosen.

### Impact Explanation
This breaks the fundamental invariant that "what the user visually selected is what gets committed." A crafted repository (via commit hooks, smudge filters, or any mechanism that mutates working-tree content between the user's diff review and their commit action) can cause Desktop to silently commit and push content the user never reviewed or approved — e.g. exfiltrating secrets accidentally left in the working tree, injecting malicious code into a legitimate-looking partial commit, or dropping a security fix line the user believed was included. This falls squarely under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Moderate-to-low, but concrete: it requires (a) the user to be doing a partial/line-level commit (a common, encouraged Desktop workflow) and (b) the tracked file's content to change between diff-review and commit without an intervening diff reload. Git clean/smudge filters and checkout/merge hooks are a normal, repo-controlled mechanism (once a user has trusted the directory to run repo-defined executables, per the existing "unsafe repository" warning in `add-existing-repository.tsx`), and Desktop performs many background status refreshes (`_refreshRepository`, `refreshChangesSection`) that do not force a diff reload for the currently displayed file unless the file selection changes — meaning the stale-diff window is realistically hit without any unnatural user action.

### Recommendation
Before staging a partially selected file, re-fetch the working-directory diff and validate it is structurally identical (e.g. compare hunk headers/line counts, or a content hash) to the diff the `DiffSelection` was computed against; if it differs, force the file back to `DiffSelectionType.None`/prompt the user to re-review rather than silently applying stale line indices to new content. Equivalently, thread the diff object (not just the selection) end-to-end from the UI into `applyPatchToIndex`/`formatPatch`, and fail loudly if the on-disk diff has changed since it was captured — mirroring the recommended fix in the Blend report of re-synchronizing cached/mutated state before it is persisted.

### Proof of Concept
Conceptual repro (not run, since Desktop requires a live app/session to exercise the UI path):
1. Clone a repository containing a tracked file `secret.txt` with existing content, and a `.git/hooks/pre-commit` (or a clean filter defined in `.gitattributes`) that rewrites `secret.txt` on invocation, or simply simulate a background file mutation between steps.
2. In Desktop, open `secret.txt`'s diff, deselect the lines you don't want committed (partial `DiffSelection`), leaving the file `Partial`-selected.
3. Modify `secret.txt` on disk (simulating the hook/filter effect) without triggering Desktop to reload the diff for that file (e.g. via a script running concurrently, or rely on a background non-selecting status refresh).
4. Click Commit. Inspect `app/src/lib/git/apply.ts:60` (`getWorkingDirectoryDiff` called fresh) combined with the old `file.selection` and observe via `git show` that the committed content does not match what was visually selected in the diff viewer before the mutation, confirming the stale-selection application described above.
