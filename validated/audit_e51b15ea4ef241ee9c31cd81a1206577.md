### Title
Field-extraction tool-representation gap in `RuleEngine._extract_field` lets `MultiEdit` bypass block rules targeting `old_text`/`old_string` - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` hard-codes per-tool field mappings, and the branch that maps `old_text`/`old_string` to `tool_input['old_string']` only exists for `tool_name in ['Write', 'Edit']`, not for `tool_name == 'MultiEdit'`. A block rule authored against the `old_text`/`old_string` field to detect dangerous content being removed/replaced (e.g., stripping a safety check, deleting a credential guard, matching a sensitive pattern in the pre-edit content) silently fails to match whenever the same file mutation is performed with the `MultiEdit` tool instead of `Edit`, because the extracted field value is `None` and `_check_condition` treats a missing field as non-matching.

### Finding Description
`evaluate_rules` calls `_rule_matches` → `_check_condition` → `_extract_field` for each rule condition [1](#0-0) . `_check_condition` short-circuits to `False` (no match) whenever `_extract_field` returns `None` [2](#0-1) .

`_extract_field`'s tool-specific fallback logic explicitly handles `old_text`/`old_string` only for `Write`/`Edit`: [3](#0-2) 

For `MultiEdit`, only `file_path` and `new_text`/`content` (concatenation of `new_string` across edits) are handled — there is no equivalent extraction of the pre-edit (`old_string`) content: [4](#0-3) 

Both `Edit`, `Write`, and `MultiEdit` are dispatched to the same `event='file'` rule set by the `PreToolUse` hook entrypoint [5](#0-4) , so a `.claude/hookify.*.local.md` rule with `event: file` and a condition on `old_text`/`old_string` is expected by the rule author to apply uniformly across all file-editing tool representations. Because `MultiEdit` and `Edit` are functionally equivalent from Claude's perspective (both let the model replace `old_string` with `new_string` in a file), an attacker who can influence which tool Claude picks (e.g., via prompt injection from untrusted repository content, issue text, or tool output that Claude is instructed to act on) can steer the edit to go through `MultiEdit` specifically to evade any block rule that inspects the removed/pre-existing content via `old_text`/`old_string`. The engine returns `{}` (allow) for this rule since the condition never matches [6](#0-5) , so `PreToolUse` enforcement grants the edit that would otherwise have been denied.

### Impact Explanation
A `block`-action hookify rule intended to protect file contents (e.g., "deny any edit that removes `verify_signature(...)`" or "deny any edit whose old content contains a secret marker") is bypassed whenever the file edit is issued via `MultiEdit` rather than `Edit`/`Write`. This defeats the local `PreToolUse` enforcement mechanism the user configured, allowing an attacker-influenced agent session to perform an unauthorized file mutation that the deny rule was supposed to block — i.e., a Claude Code approval/deny control bypass for file write operations.

### Likelihood Explanation
No special privileges are required beyond the ability to influence Claude's tool choice for a file edit (e.g., via prompt injection in repository content the agent reads). `MultiEdit` is a standard, commonly-used tool, so an attacker does not need to invent an unusual invocation — simply causing/preferring a `MultiEdit` call over `Edit` for the same file change is sufficient. The gap is deterministic and always reproducible for any rule keyed on `old_text`/`old_string`.

### Recommendation
In `RuleEngine._extract_field`, add `old_text`/`old_string` handling for `tool_name == 'MultiEdit'` by concatenating `old_string` across `tool_input.get('edits', [])`, mirroring the existing `new_text`/`content` handling, so that field extraction is consistent across all tool representations of the same logical operation (`Edit`, `Write`, `MultiEdit`).

### Proof of Concept
Unit test against `RuleEngine.evaluate_rules`:
1. Define a `block` rule with `event: file`, condition `field: old_text, operator: contains, pattern: "SECRET_TOKEN"`.
2. Case A — `tool_name: "Edit"`, `tool_input: {"file_path": "x", "old_string": "SECRET_TOKEN=abc", "new_string": ""}`. Assert `evaluate_rules` returns a deny/`permissionDecision: "deny"` response.
3. Case B — `tool_name: "MultiEdit"`, `tool_input: {"file_path": "x", "edits": [{"old_string": "SECRET_TOKEN=abc", "new_string": ""}]}`. Assert current behavior incorrectly returns `{}` (allow) instead of the same deny response as Case A, demonstrating the bypass.
