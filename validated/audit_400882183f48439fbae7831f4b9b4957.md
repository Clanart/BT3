### Title
Out-of-bounds read in `is_atom_canonical` when validating CLVM atom length prefixes for DEDUP/FF-eligible mempool spends - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical` (and its caller `is_clvm_canonical`) in `chia/full_node/mempool_manager.py` parses attacker-supplied `puzzle_reveal`/`solution` bytes to determine canonical CLVM atom encoding for dedup/fast-forward eligibility, but the multi-byte length-prefix-reading loop advances `offset` and indexes `clvm_buffer[offset]` without ever checking that `offset` stays within the buffer bounds.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads a length-prefix byte, determines `prefix_len` (0–5 extra bytes based on the CLVM length-prefix encoding), then loops `prefix_len` times doing: [1](#0-0) 
each iteration increments `offset` and dereferences `clvm_buffer[offset]` with no bounds check against `len(clvm_buffer)`. This mirrors the HDF5 `H5VM_memcpyvv` bug class from CVE-2024-32605: a length/count value taken from untrusted input is used to drive a read loop over a buffer without validating that the computed read region stays inside the underlying allocation.

The caller, `is_clvm_canonical`, walks a full CLVM serialization tree and calls `is_atom_canonical` at each atom boundary found while scanning: [2](#0-1) 
Because the outer loop trusts `atom_len`/`offset` advancement returned from `is_atom_canonical`, a crafted trailing byte sequence (e.g., a length-prefix marker such as `0xFC`/`0xF8`/etc. placed at or near the very end of `clvm_buffer`) causes the inner loop to index past the end of the buffer. In CPython, indexing a `bytes` object past its end normally raises `IndexError` rather than reading adjacent heap memory (unlike the C-level HDF5 case), so the practical effect here is a Python exception, not a silent memory disclosure/heap over-read.

### Impact Explanation
The function is only invoked on `puzzle_reveal`/`solution` bytes belonging to spends attempting to qualify for `ELIGIBLE_FOR_DEDUP` semantics (per the referenced test coverage), i.e. bytes a wallet/spend-bundle submitter fully controls. If `is_clvm_canonical` raises an unhandled `IndexError` instead of returning `False`/being caught, a single crafted spend bundle sent to `add_spend_bundle()`/mempool admission could throw an unexpected exception during canonical-form checking. Depending on how far up the call stack this exception propagates and whether it is caught, this ranges from a per-spend-bundle rejection (benign) to an unhandled exception disrupting spend-bundle processing for that request path (localized denial-of-service against the canonicalization check, not an OOB memory disclosure/corruption in the HDF5 sense).

### Likelihood Explanation
Reachable directly from a single externally-submitted spend bundle: any peer/wallet can submit a `puzzle_reveal` or `solution` ending in a truncated multi-byte atom length-prefix marker. No privileged access, signature validity, or coordination is required, only that the code path invoking `is_clvm_canonical` is reached (dedup/fast-forward eligibility evaluation during mempool admission).

### Recommendation
Add explicit bounds checks in `is_atom_canonical` before each `clvm_buffer[offset]` access (raise/return non-canonical, or a bounds-checked error) instead of relying on the caller-controlled `offset` staying within `len(clvm_buffer)`. Also verify the outer `is_clvm_canonical` loop's `clvm_buffer[offset]` accesses are similarly guarded, and ensure any `IndexError` raised here is caught and translated into a controlled validation failure (e.g. `False` / `INVALID_COIN_SOLUTION`) rather than propagating as an unhandled exception through the mempool-admission path.

```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0xFC = 1+8+8+8+8+8-bit length prefix marker (prefix_len = 5), but buffer

# is_atom_canonical will index clvm_buffer[1], [2], ... past the end.
clvm_buf = bytes([0xFC])

is_clvm_canonical(clvm_buf)  # raises IndexError instead of returning False
```

```python
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
