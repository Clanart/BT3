### Title
PedPoP `EncryptionKeyMessage` encryption key is not bound by the sender's proof‑of‑knowledge, allowing theft of a victim's secret shares - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
In the PedPoP DKG, each participant broadcasts an `EncryptionKeyMessage<Commitments>` containing (a) their polynomial commitments, (b) a Schnorr proof‑of‑knowledge over `coefficients[0]`, and (c) `enc_key`, the ECDH public key all other participants will encrypt secret shares to. The Schnorr PoK's challenge (`challenge()` / `cached_msg`) authenticates only the commitment bytes — `enc_key` is appended to the wire message *outside* the signed region and is never bound to the participant. An attacker who can substitute untrusted bytes into another participant's commitment message (e.g., a relaying participant, since the map is attacker‑supplied `HashMap<Participant, EncryptionKeyMessage>`) can replace `enc_key` with a key they control while the original PoK still verifies. All shares destined for the victim are then encrypted to the attacker's key, yielding recovery of the victim's full secret share.

### Finding Description
`Commitments::read` builds `cached_msg` exclusively from the serialized `commitments` points (crypto/dkg/pedpop/src/lib.rs, `Commitments::read` lines 109–128). The PoK challenge is computed over `context, participant, R, cached_msg` (lines 86–94) and verified in `verify_r1` at lines 323–329. Separately, `EncryptionKeyMessage::read` reads `msg` then `enc_key` (crypto/dkg/pedpop/src/encryption.rs, lines 57–59), and `Encryption::registration` wraps the message with an unsigned `enc_pub_key` (lines 448–450). `Decryption::register` stores whatever `enc_key` arrived under the claimed `participant` index with no authentication (encryption.rs lines 351–362).

Because `enc_key` is not covered by the Schnorr signature, an attacker observing Alice's broadcast `EncryptionKeyMessage` can forward `EncryptionKeyMessage { msg: alice.msg, enc_key: X_m }` where `X_m = G*x_m` is a key the attacker generated. `verify_r1` still accepts it: the batch verification only checks the PoK over `cached_msg` (lib.rs lines 323–334). Every other participant then calls `self.encryption.encrypt(rng, alice_index, share)` which encrypts `f_j(alice)` under `X_m` via `ecdh(key, enc_keys[alice])` (encryption.rs lines 460–467, 154). The attacker computes the same ECDH key with `x_m` and decrypts each `EncryptedMessage<C, SecretShare>` addressed to Alice, recovering `Σ f_j(alice) = s_alice` — Alice's complete `ThresholdKeys` secret share.

### Impact Explanation
Recovery of a victim participant's full secret share. With `t` colluding/compromised key shares (or by repeating across victims), the attacker can sign on behalf of the group key without authorization — i.e., concrete signing capability obtained purely from substituting an unauthenticated field in an otherwise‑valid message. Alice herself cannot decrypt (she holds neither `x_m` nor a valid share stream), so she aborts, but the damage to share confidentiality is already done. The code's own comments acknowledge this channel is *not* authenticated by the DKG (encryption.rs lines 299–301) and that key substitution attacks on message keys were a real concern (lines 84–90), yet the *registration* key — the root of trust for all per‑message keys — received no such protection.

### Likelihood Explanation
Requires the ability to tamper with the forwarded commitment bytes for a target participant before they reach the other participants. In deployments where commitment messages are gossiped/relayed through other participants or a coordinator (the library explicitly does not provide the authenticated channel; lib.rs lines 98–101, 154–155), any participant or relay performing this substitution goes undetected because the signature check passes. Detection only occurs when Alice fails decryption — at which point the attacker already holds her share.

### Recommendation
Include `enc_key` in the authenticated region: extend `cached_msg` (or `challenge()`) to cover `enc_key.to_bytes()` so the PoK binds the encryption key to the participant, and/or add a Schnorr proof‑of‑possession over `enc_key` keyed to `participant` and `context` (mirroring the per‑message PoP in `pop_challenge`, encryption.rs lines 302–324). Alternatively sign `(commitments || enc_key)` once with a participant identity key.

### Proof of Concept
1. Honest Alice runs `KeyGenMachine::generate_coefficients`, producing `EncryptionKeyMessage { msg: Commitments{c.., sig}, enc_key: X_a }`.
2. Attacker Mallory (a relaying participant) generates `x_m`, `X_m = G*x_m`, and forwards to all participants the map entry `alice → EncryptionKeyMessage { msg: alice.msg.clone(), enc_key: X_m }`.
3. In `SecretShareMachine::verify_r1`, Alice's PoK verifies against `challenge(context, alice, R, cached_msg)` — `cached_msg` never contained `X_a`, so verification succeeds and `Decryption::register(alice, msg)` stores `X_m` (encryption.rs lines 356–360).
4. Every honest participant `j` computes `encrypt(rng, alice, SecretShare(f_j(alice)))` → `cipher(context, ecdh(key_j, X_m))` (encryption.rs lines 154, 466).
5. Mallory computes `ecdh = key_j_pub * x_m` for each message's public `key`, derives the same ChaCha20 keystream, and decrypts each `SecretShare`, summing them to obtain Alice's secret share `s_alice`.
