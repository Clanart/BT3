### Title
Gasless module `PreAddTx` mutates `knownTxs` map while holding only a read lock, causing a data race that can crash or corrupt gasless tx-pool state - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`(g *GaslessModule) PreAddTx()` acquires `g.knownTxsMu.RLock()` (a shared read lock) but then calls `g.knownTxs.add(tx, TxStatusQueue)`, which mutates the shared `knownTxs` map. Every other call site that mutates `knownTxs` (`IsReady`, `PreReset`, `PostReset`) correctly takes the exclusive `g.knownTxsMu.Lock()`. `PreAddTx` is the outlier that mutates state under a non-exclusive lock, matching exactly the bug class described in the report (`RLock()` held over a location that is also written/deleted).

### Finding Description
`PreAddTx` is defined as: [1](#0-0) 

It takes `g.knownTxsMu.RLock()` and, if the incoming transaction is a bundle transaction and under the queue limit, calls `g.knownTxs.add(tx, TxStatusQueue)` — a write to the shared `knownTxs` map — while still holding only the read lock.

By contrast, every other mutator of `knownTxs` (`IsReady`, `PreReset`, `PostReset`) takes the **exclusive** write lock before calling `add`/`delete`: [2](#0-1) [3](#0-2) [4](#0-3) 

Because `sync.RWMutex.RLock()` allows multiple concurrent readers, two or more transactions arriving concurrently (e.g. from multiple RPC clients submitting gasless approve/swap transactions simultaneously, or from concurrent local+remote submission paths) can both enter `PreAddTx` at the same time, both pass the `RLock()`, and both call `g.knownTxs.add(...)` concurrently on the same underlying map with no mutual exclusion between them. This is a classic concurrent-map-write race in Go, which can panic the process (`fatal error: concurrent map writes`) or silently corrupt the `knownTxs` bookkeeping structure.

### Impact Explanation
`PreAddTx` is invoked in the transaction-pool admission path for every transaction entering the pool (this is the standard `kaiax.TxPoolModule` hook), so it is reachable by any unprivileged transaction sender who can submit transactions concurrently via the public RPC or p2p. A concurrent-map-write panic in this hot path threatens the liveness of the node (crash), and in the non-panicking case can corrupt `knownTxs`, which gates gasless bundle admission/promotion logic (`numQueue`, `numExecutable`, dedup via `get`). Corruption here can let a duplicate/known gasless bundle transaction be treated as unrecognized (bypassing `ErrUnableToAddKnownBundleTx`) or cause incorrect queue/pending accounting, both of which touch the gasless settlement flow that is explicitly in scope (gasless module).

### Likelihood Explanation
The race requires only ordinary concurrent transaction submission — no privileged access, no malicious peer/validator behavior, just multiple senders (or a single sender flooding) submitting gasless-eligible transactions at the same time, which is a normal and easily triggerable client pattern. Given `RWMutex` semantics, any two concurrent `PreAddTx` calls that both satisfy `g.IsBundleTx(tx)` will race.

### Recommendation
Change `PreAddTx`'s `g.knownTxsMu.RLock()`/`RUnlock()` to `g.knownTxsMu.Lock()`/`Unlock()`, since the function conditionally mutates `g.knownTxs` via `add()`. Alternatively, split the function into a read-only check followed by a separate write-locked mutation section, ensuring the write path is always exclusive.

### Proof of Concept
1. Configure a node with the gasless module enabled and `GaslessConfig.MaxBundleTxsInQueue` set to a normal value.
2. From two or more separate RPC connections, concurrently submit distinct valid gasless bundle transactions (`approve`/`swapForGas` pairs) so that `g.IsBundleTx(tx)` is true for each.
3. Both goroutines in `TxPool.AddTx`/`PreAddTx` (kaiax module hook) acquire `g.knownTxsMu.RLock()` concurrently and both execute `g.knownTxs.add(tx, TxStatusQueue)` on the same map without mutual exclusion.
4. Running with Go's race detector (`-race`) reproducibly flags this as a data race; under sufficient concurrency in production this manifests as `fatal error: concurrent map writes`, crashing the node process.

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}
