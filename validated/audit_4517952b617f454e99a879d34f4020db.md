### Title
Malicious plot-NFT owner can bypass the wallet-side `relative_lock_height` bound to defeat the pool anti-cheat wait period - ([File: chia/pools/pool_wallet.py])

### Summary
The Dutch-auction report shows that letting the contract owner freely choose critical timing parameters (`endTime`, `stepSize`) with no bound enforced by the contract itself lets the owner defeat the mechanism the contract is supposed to guarantee. In Chia's pooling protocol, the equivalent trust boundary is `relative_lock_height`: the value that is supposed to force a pool member to wait before leaving a pool (so they cannot "quickly leave a pool and claim a block that was pledged to the pool," as documented directly in `PoolWallet`'s own docstring). That minimum is enforced only in Python wallet code (`PoolWallet.MINIMUM_RELATIVE_LOCK_HEIGHT` / `MAXIMUM_RELATIVE_LOCK_HEIGHT`, checked in `_verify_initial_target_state`, called from `create_new_pool_wallet_transaction`/`join_pool`), not by the on-chain CLVM puzzle that actually enforces the wait.

### Finding Description
`PoolWallet` declares the intended bound: [1](#0-0) 

and documents the exact protection this is supposed to provide: [2](#0-1) 

This bound is checked only through `PoolWallet._verify_initial_target_state()`, invoked from the official `join_pool()` / `create_new_pool_wallet_transaction()` wallet flows: [3](#0-2) [4](#0-3) 

However, the value that is actually enforced on-chain is whatever `relative_lock_height` is curried directly into `POOL_WAITINGROOM_INNERPUZ` by `create_waiting_room_inner_puzzle()`: [5](#0-4) 

The CLVM puzzle itself never re-validates that this curried value falls within `[MINIMUM_RELATIVE_LOCK_HEIGHT, MAXIMUM_RELATIVE_LOCK_HEIGHT]` — that check lives entirely in the Python `PoolWallet` class, which is bypassable by any party who can submit their own spend bundle to transition their own singleton (e.g., a custom wallet, a hand-crafted `create_travel_spend`, or direct RPC/CLI use with a crafted `PoolState`). `create_travel_spend()` builds the travel spend directly from an arbitrary `target: PoolState` supplied by the caller with no bound check performed at this layer either: [6](#0-5) 

Because pools are joined "anonymously, without an account or prior signup" (per `PoolWallet`'s own design docstring) and the pool never gets to approve or reject the specific `relative_lock_height` a member curries into their own puzzle before farming begins, a member can transition to `FARMING_TO_POOL` with `relative_lock_height = 0` (or any value below the documented minimum of 5), entirely bypassing the wallet-level guard rail — exactly analogous to the Dutch-auction owner setting `stepSize`/`endTime` to defeat the price-decay guarantee that the contract's users rely on.

### Impact Explanation
The anti-cheat design explicitly states the wait period exists to prevent a member from "quickly leaving a pool, and claiming a block that was pledged to the pool." With `relative_lock_height` set to `0` (or any attacker-chosen minimal value) directly in the curried puzzle, the member can escape the `LEAVING_POOL` waiting-room state immediately (the on-chain `ASSERT_HEIGHT_RELATIVE` gate is satisfied trivially), undermining the wait-time guarantee that pools rely on to prevent members farming a pool-pledged block and immediately reclaiming it for themselves before the pool's accounting/payout process can react. This is a self-serving manipulation of an on-chain protocol invariant (reward-redirection/anti-cheat bypass) that defeats a documented consensus-adjacent protection, not merely a UX validation gap — matching the reachable, high-severity impact classes in scope (reward redirection via a spend-triggered path).

### Likelihood Explanation
Likelihood is high for any user willing to bypass the official Chia wallet UI/RPC path: no signature from the pool or any third party is required to set `relative_lock_height`, since the value is chosen unilaterally by the pool member's own wallet code and only ever checked client-side. Any actor capable of building a raw `CoinSpend`/`SpendBundle` (a normal, unprivileged mempool submitter) can curry an out-of-bounds value into `POOL_WAITINGROOM_INNERPUZ` and have it accepted by any honest full node, since node/consensus-level validation never inspects or bounds this application-level parameter.

### Recommendation
Move the `relative_lock_height` bound check (`MINIMUM_RELATIVE_LOCK_HEIGHT` / `MAXIMUM_RELATIVE_LOCK_HEIGHT`) into the CLVM puzzle itself (`POOL_WAITINGROOM_INNERPUZ` / the corresponding member puzzle) so it is enforced as a consensus-level invariant, not merely as a wallet-side courtesy check in `PoolWallet._verify_initial_target_state`. At minimum, pool operators should independently validate the `relative_lock_height` a member commits to before accepting partials, rather than assuming the official wallet's client-side guard applies universally.

### Proof of Concept
1. Craft a `PoolState` with `state=FARMING_TO_POOL`, `relative_lock_height=uint32(0)`, and an arbitrary `owner_pubkey`/`target_puzzle_hash`, bypassing `PoolWallet.join_pool()`/`_verify_initial_target_state()` entirely (e.g., call `create_waiting_room_inner_puzzle()` and `create_travel_spend()` directly, as shown in `chia/_tests/pools/test_pool_puzzles_lifecycle.py`, but substituting `relative_lock_height=0`).
2. Submit the resulting `CoinSpend`/`SpendBundle` to the mempool as a normal, unprivileged spend-bundle submitter; no additional signature or approval from the pool is required for a member to change their own singleton's puzzle parameters.
3. Farm a block whose reward is committed to the pool's `p2_singleton` address while the state is `FARMING_TO_POOL`.
4. Immediately submit a travel spend transitioning `LEAVING_POOL → SELF_POOLING`; because `relative_lock_height = 0`, the `ASSERT_HEIGHT_RELATIVE` condition inside `POOL_WAITINGROOM_INNERPUZ` is trivially satisfied at the very next block, defeating the intended multi-block wait that is supposed to prevent this exact "farm-then-flee" abuse documented in `PoolWallet`'s own comments.

Note: I was unable to fully verify from the indexed CLVM sources within this session whether the reward-forwarding puzzle path (`create_absorb_spend`) has any independent secondary check that would mitigate the actual fund redirection once the wait is bypassed; a full Devin session with access to the complete `chia-puzzles-py` CLVM sources (`pool_waiting_room_innerpuz.clsp`, `pool_member_innerpuz.clsp`) would be needed to confirm the exact on-chain enforcement/absence of enforcement of the minimum lock height and finalize exploit mechanics for absorbed rewards.
