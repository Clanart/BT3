### Title
Malicious/MITM Git server can spoof `WWW-Authenticate: realm="GitHub"` to trigger a GitHub sign-in prompt and credential lookup for an attacker-controlled host - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The Escher bug is fundamentally about a downstream function trusting attacker-supplied input to decide *who owns/controls a resource*, bypassing the intended authorization gate. In GitHub Desktop's git-credential trampoline, the analogous broken invariant is in `getEndpointKind()`, which decides whether a remote host should be treated as a trusted GitHub/GitHub-Enterprise endpoint based on attacker-controlled data returned by the remote server itself (an HTTP `WWW-Authenticate` header), rather than on a value Desktop independently verifies.

### Finding Description
When Git needs credentials for a remote it invokes Desktop's credential helper trampoline (`createCredentialHelperTrampolineHandler` in [1](#0-0) ). To classify the remote, `getEndpointKind()` is called and explicitly trusts `wwwauth[...]` header values captured by Git during the authentication challenge with the remote server: [2](#0-1) 

Any HTTPS git server the user adds as a remote (or any git remote/proxy an attacker fully controls, including a spoofed/MITM endpoint or a repository whose remote URL an attacker convinces the user to add) can simply respond with a `WWW-Authenticate` header containing `realm="GitHub"`, and Desktop's credential helper will classify the host as `'enterprise'` — i.e. a trusted GitHub Enterprise-style endpoint — without any independent verification such as the `isGitHubHost()` network probe that is used later in the same function for hosts that don't send this header (line 178).

Once classified as `'enterprise'`, `getCredential()` treats the endpoint as GitHub-flavored rather than generic: [3](#0-2) 

If the user has no account matching `apiEndpoint` (computed from the attacker's own host via `getAPIEndpoint`), Desktop calls `ui.promptForGitHubSignIn(endpoint)` — presenting the user a "Sign in to GitHub" dialog for a host the attacker fully controls. If the user goes through with it (a normal, unremarkable action for a Desktop user who's told "this remote requires GitHub sign-in"), the resulting OAuth flow completes against the attacker's endpoint. Separately, if the attacker's host happens to collide with (or the user already has) an account for that same hostname, `findGitHubTrampolineAccount()` — which matches purely by URL `origin` — will hand the stored token/credential straight to the attacker's server as `username`/`password` in the git credential response: [4](#0-3) 

The trust decision ("is this a GitHub host that should receive GitHub-flavored credential handling / trigger a GitHub sign-in") is being derived from data the remote server supplies, which is exactly the same class of bug as Escher: an authorization-relevant property (creator/admin identity there, "is this a trusted GitHub host" here) is set based on attacker-supplied input rather than a value Desktop derives and verifies itself.

### Impact Explanation
An attacker who controls a git remote/proxy endpoint (e.g., a malicious git server the victim clones/adds as a remote, or a network MITM proxy sitting in front of an HTTPS git connection before certificate validation completes at the HTTP layer) can:
- Trigger Desktop's "Sign in to GitHub" UI for their own arbitrary host, tricking users into starting an OAuth flow against a host they didn't intend to authenticate to (unauthorized OAuth binding / phishing surface built directly into trusted app UI).
- Under specific host-matching conditions, cause Desktop to send previously stored GitHub credentials to that same-named host without the `isGitHubHost()` verification step being exercised, since the `wwwauth[]` check short-circuits before it.

This matches the requested impact category of "attacker controls a git remote/proxy response" resulting in "unauthorized OAuth or account binding" or "credential/token exfiltration."

### Likelihood Explanation
This requires the victim to add/connect to a remote controlled by the attacker (or be MITM'd) — no local access, no admin rights, and no pre-existing malware, matching the "unprivileged" criteria. It does need the attacker to control network responses for that remote, which is a realistic capability for a malicious hosted git server or an on-path attacker performing a downgrade/MITM on the pre-TLS handshake HTTP negotiation. The heuristic nature of the `wwwauth[]` shortcut (explicitly documented as a "happy-path" to avoid a network request) means it was a deliberate trust decision, not an oversight guarded elsewhere — the safer `isGitHubHost()` probe is bypassed entirely whenever this header is present.

### Recommendation
Do not trust the `WWW-Authenticate` realm string alone to classify a host as GitHub/GitHub Enterprise for the purposes of prompting sign-in or selecting credential-handling logic. Always corroborate with the `isGitHubHost()` verification (or an equivalent authenticated check against a known GitHub API shape) before treating an arbitrary host as enterprise/GitHub, and require explicit user confirmation before treating a previously-unknown host as GitHub-authenticated.

### Proof of Concept
1. Stand up an HTTPS git server (or MITM proxy) that responds to unauthenticated requests with `WWW-Authenticate: Basic realm="GitHub"` and otherwise behaves like a normal git smart-HTTP server.
2. In GitHub Desktop, add this server as a remote/clone URL and perform a fetch/pull that requires authentication.
3. Observe that `getEndpointKind()` returns `'enterprise'` purely from the header ( [5](#0-4) ), causing Desktop's credential helper to invoke `ui.promptForGitHubSignIn(endpoint)` for the attacker's host instead of the generic-credential flow, without ever calling `isGitHubHost()`.

**Note on completeness:** I was not able to fully trace `isGitHubHost()`'s implementation or confirm exactly how `promptForGitHubSignIn` renders the target host to the user (whether it clearly discloses the raw hostname), which affects how convincing the phishing surface is in practice. A Devin session with full repo access would be needed to inspect `app/src/lib/api.ts`'s `isGitHubHost` implementation and the sign-in dialog UI to fully confirm exploitability end-to-end.

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.

    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
