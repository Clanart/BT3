## Finding Confirmed

### Title
Unsanitized GitHub API `email` field allows commit-trailer injection via `Co-Authored-By` - (File: `app/src/ui/lib/author-input/author-input.tsx`)

### Summary
`getEmailAddressForUser` returns the `email` field from a `KnownUserHit` (sourced from a GitHub API mentionables/search-users response) with no validation, and this value is later embedded verbatim into a `Co-Authored-By` git trailer that crosses into the main-process git invocation.

### Finding Description
`getEmailAddressForUser` takes `user.email` straight from the API-derived `KnownUserHit` object and returns it unmodified whenever it's non-empty, falling back to a stealth email only when it's empty: [1](#0-0) 

This value is stored as `KnownAuthor.email` via `authorFromUserHit`: [2](#0-1) 

The `email` originates from `IMentionableUser`/API data with no format constraint enforced client-side: [3](#0-2) [4](#0-3) [5](#0-4) 

When the commit is created, `commit-message.tsx` builds the trailer value directly by string interpolation with no newline stripping: [6](#0-5) 

That `ICommitContext.trailers` array (typed as `ReadonlyArray<ITrailer>`, with `ITrailer.value: string` unconstrained) is passed to `onCreateCommit` which dispatches across the renderer→main IPC boundary to the git layer: [7](#0-6) [8](#0-7) 

On the git-invocation side, `mergeTrailers` places the raw trailer value into a single `--trailer token=value` argv element passed to `git interpret-trailers`: [9](#0-8) 

Because the value is passed via argv (not a shell string), embedded `\n` cannot be used for OS/shell command injection, but git's own trailer serialization does not strip or fold embedded newlines that lack RFC822-style leading whitespace — they are written out as literal extra lines in the commit message body. This means a value like `"attacker@example.com\nEvil-Trailer: forged"` becomes two distinct lines in the final commit message once merged, rather than a single `Co-Authored-By` value, corrupting the intended single-value trailer semantics.

### Impact Explanation
If an attacker controls the `email` field returned by a GitHub API object for a mentionable user (e.g., a malicious/compromised GitHub Enterprise server response, or any crafted API object reaching `IMentionableUser`), and the victim adds that user as a co-author (a normal, intended workflow action), the resulting commit's trailers section can contain attacker-injected lines beyond the intended `Co-Authored-By: Name <email>` value. This is a silent corruption of commit metadata that the user commits and pushes — matching the "silent corruption of what the user commits or pushes" impact category. It does not achieve shell/argv injection (git receives the value as one argv token, not concatenated into a shell command) and does not by itself achieve code execution or credential exfiltration.

### Likelihood Explanation
Requires: (1) an attacker-controlled GitHub API response supplying a crafted `email` value containing newlines — normal github.com profile-email validation would likely reject non-email strings, so the most realistic vector is a malicious/compromised GHE server or a MITM'd/altered API response; and (2) the victim voluntarily selecting that user as a co-author, which is standard use of the feature, not an unnatural step. Likelihood is therefore moderate-to-low, gated primarily by whether the trusted endpoint's email field can actually be forced to contain such a payload.

### Recommendation
Sanitize/validate `user.email` in `getEmailAddressForUser` (and generally any value destined for a git trailer) by rejecting or stripping control characters (`\n`, `\r`) before it is used to construct `KnownAuthor.email`/`ITrailer.value`, and/or add a guard in `mergeTrailers`/`formatCommitMessage` that rejects trailer values containing newlines before invoking `git interpret-trailers`.

### Proof of Concept
Unit test sketch:
```ts

  kind: 'known-user',
  username: 'evil',
  name: 'Evil',
  email: 'a@b.com\nEvil-Trailer: forged',
  endpoint: 'https://github.com',
}
const author = authorFromUserHit(hit)
// author.email === 'a@b.com\nEvil-Trailer: forged' -- not sanitized
const trailers = [{ token: 'Co-Authored-By', value: `${author.name} <${author.email}>` }]
// formatCommitMessage(repo, { summary, description, trailers }) merges this via
// `git interpret-trailers --trailer Co-Authored-By=<value-with-embedded-newline>`
// producing a commit body with an extra unintended line/trailer.
```

Note: I could not execute `git interpret-trailers` in this environment to empirically confirm the exact output formatting (whether git folds/escapes the embedded newline in some git versions), so this last step is based on code-path analysis and general `git-interpret-trailers` semantics rather than direct execution.
```typescript
export async function mergeTrailers(
  repository: Repository,
  commitMessage: string,
  trailers: ReadonlyArray<ITrailer>,
  unfold: boolean = false
) {
  const args = ['interpret-trailers']

  // See https://github.com/git/git/blob/ebf3c04b262aa/Documentation/git-interpret-trailers.txt#L129-L132
  args.push('--no-divider')

  if (unfold) {
    args.push('--unfold')
  }

  for (const trailer of trailers) {
    args.push('--trailer', `${trailer.token}=${trailer.value}`)
  }

  const result = await git(args, repository.path, 'mergeTrailers', {
    stdin: commitMessage,
  })

  return result.stdout
}
```
