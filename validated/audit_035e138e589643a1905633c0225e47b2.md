## Title
Permissionless bandwidth-purchase flooding lets an attacker evict a victim's unexpired, unconsumed subscription via the FIFO `SubscriptionList` cap - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`Pallet::push_subscription` enforces a hard 1024-entry cap per `(app_chain, app)` key and evicts index `0` (the oldest entry) whenever a new subscription is pushed onto a full list. Because purchases are sponsorship-permissible — any payer on any source chain can credit bandwidth for any `(app_chain, app)` pair, not just their own — an attacker can drive a targeted victim app's subscription queue to the cap with cheap, minimal-tier purchases and force-evict the victim's large, unexpired, still-unconsumed subscription.

### Finding Description
`push_subscription` appends every purchase to `Allowance<T>` keyed by `(app_chain, app)` taken from the purchase message body, independent of `request.source`/payer: [1](#0-0) 

When the list is already at `MAX_SUBSCRIPTIONS` (1024), the oldest entry (`list.remove(0)`) is unconditionally evicted regardless of its `remaining_bytes` or `expires_at`, and `SubscriptionEvicted { lost_bytes, .. }` is emitted: [2](#0-1) 

Sponsorship is explicitly by-design cross-payer: the pallet keys `Allowance` by `app_chain`/`app` from the message body, not by who paid, so "a treasury on a single chain can sponsor bandwidth for an app deployed across many chains" — but this same mechanism means *any* address can push subscriptions onto *any* app's queue, including apps they don't control and have no relationship to, as confirmed in the pallet docs: [3](#0-2) 

The purchase→credit path (`on_accept` → `push_subscription`) only checks that the message came from the *registered manager* for the source chain — it does not check any relationship between the payer and the `app` being credited: [4](#0-3) 

Consequently, an attacker who repeatedly calls `purchase()` against the cheapest configured `TierIndex`, targeting the victim's `(app_chain, app)` key, can push 1024 minimal-tier subscriptions onto that queue. Since the list is FIFO and capped, the 1025th push (the attacker's own purchase, or even the victim's later top-up) evicts index `0`. If the attacker first waits for/targets a state where the victim's large paid subscription sits at the front (e.g., it's the oldest live entry, or the attacker floods immediately after the victim's credit lands), the victim's subscription — however large and however far from expiry — is evicted and its `remaining_bytes` are lost permanently, with only a `SubscriptionEvicted` event as evidence.

The existing test `subscription_cap_evicts_oldest` only exercises this mechanism via admin-only `force_credit` calls from a single actor, confirming the eviction mechanics but not testing (or guarding against) a hostile third-party payer deliberately targeting another app's queue: [5](#0-4) 

There is no per-payer isolation, no minimum-value protection ordering (e.g., evicting cheapest/soonest-to-expire rather than strictly oldest), and no cap on how many entries a single non-owning payer may inject into another app's queue.

### Impact Explanation
This breaks the invariant (stated in the pallet's own doc comments) that "what you paid for is yours only until it expires" — i.e., that a paid-for allowance is drained only by the gate consuming bytes on behalf of its own app, not by an unrelated third party's cheap purchases. A victim who paid for a large, long-duration tier can have that allowance destroyed by an attacker spending comparatively little on 1024 minimal purchases, resulting in real loss of prepaid bandwidth funds/allowance that the victim is contractually owed under the tier's `(bytes, duration_secs)` SKU. This matches the required impact category of broken accounting invariants around bridged/bandwidth balances not moving/being consumed exactly as intended.

### Likelihood Explanation
The attack is fully unprivileged: it only requires calling `BandwidthManager.purchase()` repeatedly (a permissionless entry point) targeting a known `(app_chain, app)` key, which is public information (emitted in `BandwidthCredited`/`BandwidthPurchased` events and derivable from the app's own on-chain address). The cost is bounded by `1024 × cheapest_tier_price` plus gas for 1024 dispatches — a griefing cost that is governance-tier-price-dependent but has no protocol-level floor preventing it; if any tier is priced low relative to the victim's tier, the attack is economically favorable. No malicious relayer, prover, or infrastructure compromise is required — this is a pure logic/permission gap in `push_subscription`'s eviction policy combined with the permissionless cross-payer sponsorship model.

### Recommendation
- Scope the FIFO/eviction cap per payer (or per payer+app) rather than purely per `(app_chain, app)`, so a third party cannot inject entries into a queue whose eviction harms an unrelated payer's subscription; or
- Change eviction policy to never evict a live subscription with `remaining_bytes > 0` in favor of a subscription that is closer to expiry/already fully drained; alternatively bound the number of subscriptions a single non-owner payer may push before requiring the app itself (or an allowlisted relationship) to consolidate/claim; or
- Increase `MAX_SUBSCRIPTIONS` significantly and/or add a minimum-value/first-protect-N-largest heuristic, and emit a governance-actionable alert path once eviction of a non-trivial `remaining_bytes` subscription is imminent.

### Proof of Concept
1. Victim (or a legitimate sponsor) credits `(app_chain=APP_CHAIN, app=APP)` with one large subscription, e.g. `bytes = 10_000_000`, `duration_secs = MONTH_SECS`, via a normal purchase/`force_credit` (see `force_credit` call pattern used in `subscription_cap_evicts_oldest`, `modules/pallets/testsuite/src/tests/pallet_bandwidth.rs:523-546`).
2. Attacker calls `BandwidthManager.purchase()` (or, in the pallet test harness, repeats `Bandwidth::force_credit`/simulated purchase messages) 1024 times against the same `(APP_CHAIN, APP)` key, using the cheapest configured `TierIndex` and minimal `bytes`/`months`.
3. After the 1024th attacker purchase lands, assert (mirroring `subscription_cap_evicts_oldest`'s structure) that:
   - `Allowance::<T>::get(APP_CHAIN, app_key())` no longer contains the victim's original large subscription (it was `list.remove(0)`'d in `push_subscription`, `modules/pallets/bandwidth/src/lib.rs:416-425`).
   - `Event::SubscriptionEvicted { lost_bytes: 10_000_000, .. }` was emitted, well before the victim's `expires_at` and before any gate consumption drained it.
4. This demonstrates the victim's paid allowance was destroyed purely by an unrelated attacker's cheap, permissionless purchases against the same public `(app_chain, app)` key.

```rust
		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});
```

```text
## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```

```rust
/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
```
