### Title
SSRF via unvalidated on-chain DataLayer mirror URLs consumed by `http_download`/plugin uploader-downloader HTTP requests - (File: `chia/data_layer/download_data.py`)

### Summary
Any wallet user can create a DataLayer mirror coin with arbitrary attacker-controlled URL strings (no scheme/host validation), and every peer that subscribes to that store id will have their local DataLayer service issue outbound HTTP(S) requests to those URLs, mirroring the "insufficient URL validation" SSRF bug class described in the Linkwarden `fetchTitleAndHeaders` advisory.

### Finding Description
`DataLayerWallet.create_new_mirror()` builds a mirror coin whose puzzle memos simply hold the launcher id followed by raw `urls: list[bytes]` supplied by the caller, with no validation of scheme, host, or target (e.g., no rejection of `http://127.0.0.1/...`, `http://169.254.169.254/...`, internal hostnames, etc.): [1](#0-0) 

The `DataLayerRpcApi.add_mirror` / `DataLayer.add_mirror` path only checks that the URL list is non-empty; it performs no URL validation before pushing the mirror coin on-chain: [2](#0-1) [3](#0-2) 

Once the mirror coin is confirmed on-chain, `DataLayerWallet.coin_added()` decodes the memo URLs and any tracked wallet stores them as `Mirror` records with no filtering: [4](#0-3) 

Any node's DataLayer service that subscribes to (or owns/mirrors) this store id pulls these mirror URLs via `update_subscriptions_from_wallet()` and stores them as candidate download servers: [5](#0-4) 

`fetch_and_validate()` then randomly selects one of these attacker-supplied server URLs and issues an HTTP GET (or, for the plugin downloader path, an HTTP POST) directly against it: [6](#0-5) 

The actual outbound network request is made in `http_download()`, which concatenates the attacker-controlled `server_info.url` with a filename and performs `aiohttp.ClientSession().get(...)` with no restriction on target host/IP (no blocking of loopback, link-local, or private ranges): [7](#0-6) 

This is the same class of bug reported for Linkwarden: URL input from an authenticated/unprivileged party is passed directly into a server-side HTTP client without validating that the destination is not an internal/private resource — except here the "server" doing the fetch is any peer's local `chia_data_layer` process, and reachability is via a normal on-chain spend (mirror coin), not a privileged admin action.

### Impact Explanation
An attacker who can create/own a DataLayer store and spend a small mirror coin (any wallet user, no special privilege) can force any peer that subscribes to (or auto-tracks/pseudo-subscribes) that store to issue arbitrary outbound HTTP requests from the victim's DataLayer service — e.g., against `127.0.0.1`, cloud metadata endpoints, or other internal-only services reachable from the victim node. Depending on the internal service reached, this can be used for internal network reconnaissance, triggering unauthenticated internal actions, or (combined with the plugin path, which POSTs a JSON body including `url`, `filename`, and headers derived from `PluginRemote`) probing/attacking local plugin services. This satisfies "concrete... spend-triggered" exposure reachable from a single on-chain action; per the review rules this is Medium/High severity SSRF rather than a coin-set-divergence or fund-theft bug, but it is a genuine, reachable server-side request forgery triggered purely by an unprivileged coin spend.

### Likelihood Explanation
Likelihood is High for any peer that has DataLayer enabled and subscribes to a store controlled by an untrusted party (this is the designed usage pattern — DataLayer stores are commonly shared/subscribed to across independent parties). No additional privilege beyond normal wallet spend capability and DataLayer usage is required; the mirror-coin creation flow is a standard, publicly documented feature (`chia data add_mirror` CLI / `dl_new_mirror` RPC), and the `.cursor/context/data-layer.md` design notes explicitly acknowledge "mirror URLs... are external trust inputs" for data integrity but do not address SSRF/network-egress risk from acting on those URLs. [8](#0-7) 

### Recommendation
Validate mirror URLs at creation time (`DataLayerWallet.create_new_mirror` / `DataLayer.add_mirror`) and again at consumption time (`http_download`, plugin upload/download request builders) to enforce an allow-list of schemes (e.g., only `http`/`https`), reject loopback/link-local/private/multicast/metadata address ranges (after DNS resolution, not just literal string checks), and consider requiring explicit user opt-in/allow-listing of subscription mirror hosts before the DataLayer service will issue outbound requests to them.

### Proof of Concept
1. Attacker creates a DataLayer store (`create_data_store`) and publishes a mirror coin with `urls=["http://127.0.0.1:8555/some_admin_endpoint"]` (or an internal service IP/hostname) via `add_mirror` RPC / `chia data add_mirror`. [2](#0-1) 
2. Victim node subscribes to attacker's store id (a normal DataLayer usage flow) or otherwise tracks it; `update_subscriptions_from_wallet()` pulls the mirror URL into the victim's subscription server list. [5](#0-4) 
3. On the victim's next sync cycle, `fetch_and_validate()` picks the attacker URL and `http_download()` issues an outbound `GET http://127.0.0.1:8555/some_admin_endpoint/<delta-filename>` from the victim's DataLayer process, hitting whatever internal service is listening there. [7](#0-6)

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()

## Fragility Hotspots

- High-risk edits move work across DB writer transactions, `_update_confirmation_status()`, pending-root status changes, or wallet RPC calls. These boundaries encode publication and rollback assumptions.
- File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking. Concurrent service/plugin/server access should be treated as a real consistency concern.
- Empty-root normalization is subtle and historically uneven. Audit any change touching `bytes32.zeros`, `None`, `Root.node_hash`, or proof roots with both empty and non-empty stores.
- Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots, and file path/name validation must stay strict.
- DataLayer wallet code depends on singleton CLVM structure, odd singleton amounts, lineage proofs, and offer solver field names. Changes in wallet puzzle drivers or offer summaries can break this module without direct edits here.
