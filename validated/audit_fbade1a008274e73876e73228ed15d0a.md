## Finding: Stale, position-based `DiffSelection` is silently re-applied to a freshly re-computed diff during partial commits — "what you see is not what you commit"

### Title
Partial-commit line selection is applied against a re-fetched (potentially different) diff, silently committing content the user never reviewed - (`app/src/lib/git/apply.ts`)

### Summary
The AllBridge bug is fundamentally a **quote/execution mismatch**: the amount of shares minted is computed against pool state that can change between the moment the user is shown an expected result and the moment the transaction actually executes, with no check that the executed result matches what was reviewed. GitHub Desktop has a structurally identical class of bug in its partial-commit ("select specific lines/hunks to commit") feature: the line selection the user makes is stored as *raw line-index numbers* against one snapshot of a file's diff, but is later blindly re-applied to a **second, independently-fetched diff** of the same file when the commit is actually built - with no verification that the two diffs still agree on what those indices mean.

### Finding Description
When a user makes a partial selection of lines/hunks to commit, that selection is stored as a `DiffSelection` object which is purely index-based (a set of "diverging" line numbers), see [1](#0-0) . It carries no reference to the diff content it was derived from - only line numbers.

At commit time, `_commitIncludedChanges` simply filters the working-directory files by selection state and forwards them straight to `createCommit`: [2](#0-1) 

`createCommit` resets the index and calls `stageFiles`: [3](#0-2) 

For any file with a partial selection, `stageFiles` calls `applyPatchToIndex`: [4](#0-3) 

Critically, `applyPatchToIndex` does **not** use the diff the user actually looked at in the Changes view. It re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff`, and then formats a patch from that *new* diff using the *old* `DiffSelection`'s line indices: [5](#0-4) 

`formatPatch` walks the newly-fetched diff's hunks and decides whether each line is included purely by asking `file.selection.isSelected(absoluteIndex)` - i.e., "was line index N selected in the old diff?" - with no check that line N in the new diff is the same logical line the user selected in the old diff: [6](#0-5) 

The app is aware this exact class of problem exists: the *live* Changes-view diff refresh path explicitly reconciles a stale selection against a freshly loaded diff by pruning selectable lines that no longer exist: [7](#0-6) 

but that reconciliation only runs on the UI's periodic re-render path (`updateChangesWorkingDirectoryDiff`); it is never invoked on the commit path. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` never goes through it, so the exact TOCTOU gap that the UI code acknowledges and partially guards against in the *display* layer is left completely unguarded in the *commit* layer.

### Impact Explanation
If the on-disk content of a file changes between when the diff was rendered/selected in the Changes pane and when the user clicks "Commit" (window during which Desktop's own background repository refresh, `RepositoryIndicatorUpdater`, LFS smudge/download completion, or any file-watcher-triggered tool can touch the file), the hunk/line boundaries in the freshly re-fetched diff can shift. The stale index-based selection is then reinterpreted against different lines, meaning `git apply --cached` builds a patch containing lines the user never selected/reviewed, or omits lines the user did select. This is silent corruption of what actually gets committed and later pushed - functionally identical to the AllBridge bug where the pool state used to mint shares differed from the state the user believed they were depositing into.

### Likelihood Explanation
This requires no admin rights, no local malware, and no unnatural user steps: any legitimate partial-commit workflow (select some lines, leave others for later) combined with an external, timing-sensitive modification to the working tree file during the review-to-commit window is sufficient to trigger the divergence. The code path has zero staleness detection, unlike the sibling UI-refresh code that already demonstrates the team is aware line-index-based selection can go stale.

### Recommendation
Before building the commit patch, `applyPatchToIndex`/`stageFiles` should verify the diff used to build the patch is unchanged from the diff the `DiffSelection` was derived from (e.g., by comparing a hash/blob OID of the working-tree file content, or by re-deriving selectable lines the same way `updateChangesWorkingDirectoryDiff` does and refusing to proceed - surfacing an error/refresh prompt to the user - if the file changed underneath the selection).

### Proof of Concept
1. Modify a tracked file with two separate hunks; open it in the Changes pane and select only the second hunk for commit (leaving `DiffSelection` line indices referencing the *current* diff).
2. Before pressing "Commit", have an external process (editor autosave, formatter, background script, or a slow LFS smudge completing) alter the file so that the first hunk shrinks or grows, shifting line numbers.
3. Click "Commit". `applyPatchToIndex` re-fetches the diff (now with shifted line numbers) and applies the old index-based selection to it via `formatPatch`, producing a patch that includes/excludes different logical lines than what was visually selected.
4. Inspect the resulting commit with `git show`: it contains lines the user did not select (or omits lines they did), with no warning shown by Desktop.
