## Title
Unrefunded native token overpayment permanently locked in `EvmHost` on `dispatch()`/`fundRequest()` — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and forward the **entire** amount into `swapETHForExactTokens{value: msg.value}(fee, ...)`, but never compute or refund the leftover native token after the swap completes. Any user who overestimates the amount of native currency needed to cover `post.fee`/`get.fee`/`amount` loses the difference — it lands in `EvmHost`'s own balance and can only ever be moved by cross-chain governance via `withdraw()`, never by the original payer. This is the exact bug class from the external report (`WRAP_CODE`-style overpayment stuck on the router), reproduced locally in the core dispatch path rather than at the app layer.

### Finding Description
`EvmHost.dispatch(DispatchPost memory post)` swaps the full `msg.value` for exactly `post.fee` fee-tokens and stops: [1](#0-0) 

The same unconditional-full-value-forward pattern repeats in `dispatch(DispatchGet)` and `fundRequest()`: [2](#0-1) [3](#0-2) 

The underlying swap wrapper (`swapETHForExactTokens`) refunds any unspent ETH to `msg.sender` — but in this call chain `msg.sender` of the swap is `EvmHost` itself, not the original caller of `dispatch`/`fundRequest`: [4](#0-3) 

So the refund is captured by `EvmHost`'s own balance rather than returned to the user. There is no code path in `EvmHost` that sends this delta back to `_msgSender()`. The only function that can move native ETH out of `EvmHost` afterward is `withdraw()`, restricted to `_hostParams.hostManager` (cross-chain governance only): [5](#0-4) 

This contrasts directly with the rest of the codebase, which treats "refund unspent native to the caller" as a required invariant for every other entry point that swaps native for fee tokens — e.g. `IntentGatewayV2.placeOrder` explicitly tracks `msgValue -= amounts[0]` and refunds the remainder to `msg.sender`: [6](#0-5) 

and `ExtrinsicIntents` / `IntrinsicIntents` do the same for solver overpayment: [7](#0-6) 

`EvmHost.dispatch`/`fundRequest` are the lowest-level, most-used native-payment entry points in the protocol (invoked directly by end-user apps such as `sendMessageWithNative`, and indirectly by `WrappedHyperFungibleToken.send` whenever `msgValue > 0` after wrapping), yet they are the ones missing this refund guard.

### Impact Explanation
Any unprivileged user or app calling `IDispatcher(host()).dispatch{value: msg.value}(post)` (or `dispatch(DispatchGet)`, or `fundRequest`) with `msg.value` even slightly greater than what the on-chain swap actually needs to acquire `post.fee`/`get.fee`/`amount` fee tokens permanently loses the excess. The lost native token is not burned or refunded — it becomes indistinguishable protocol-owned balance, withdrawable only through cross-chain governance (`withdraw()`), never by the payer. This is a direct "loss of funds" impact matching the bounty's required impact set: unprivileged, no relayer/prover/admin collusion needed, and reachable through the primary, documented, public dispatch interface used by every `HyperApp`.

### Likelihood Explanation
Likelihood is high because:
- `dispatch{value: msg.value}` with native-token payment is a documented, encouraged usage pattern (see `docs/content/developers/evm/messaging/post-requests.mdx`), and fee/price fluctuation between quote-time and execution makes exact `msg.value` sizing unreliable in practice.
- Every other native-value-consuming function in the same codebase (`IntentGatewayV2`, `ExtrinsicIntents`, `IntrinsicIntents`) was specifically hardened with a refund step, strongly suggesting the omission in `EvmHost` itself is an oversight rather than an intentional design choice.
- No `require` or slippage/exact-value check exists in `EvmHost.dispatch`/`fundRequest` to prevent or bound overpayment.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the actual amount spent by the swap (e.g. `amounts[0]` returned by `swapETHForExactTokens`) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder` and `ExtrinsicIntents`/`IntrinsicIntents`.

### Proof of Concept
1. User calls `MyApp.sendMessageWithNative` (per `docs/content/developers/evm/messaging/post-requests.mdx`), which does `IDispatcher(host()).dispatch{value: msg.value}(post)` with `post.fee = X` fee-tokens required.
2. User sends `msg.value = 2 * nativeFeeEstimate` (e.g., due to price movement or client-side over-estimation).
3. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` swaps only enough ETH (`amounts[0] < msg.value`) to obtain `post.fee` fee tokens; the router refunds `msg.value - amounts[0]` to `msg.sender` of the swap call, which is `EvmHost`.
4. `EvmHost.dispatch` returns without ever moving that refunded delta back to the user; `address(EvmHost).balance` increases by `msg.value - amounts[0]`.
5. The user has no function to reclaim this amount; only `withdraw()`, restricted to `_hostParams.hostManager` (cross-chain governance), can move it, and it is indistinguishable from legitimate protocol revenue once received.

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
