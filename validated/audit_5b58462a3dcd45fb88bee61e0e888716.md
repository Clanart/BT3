Based on my investigation, I found a submodule-related issue in this codebase that maps to the same broken-invariant pattern as the GiantPool bug: **an object controlled by an untrusted source (the repository's own `.gitmodules`) is trusted and consumed without validating that it corresponds to a value the user actually intends to fetch**, and the code deliberately disables a Git safety control that exists specifically to prevent that abuse.

### Title
Unconditional `protocol.file.allow=always` override lets a malicious `.gitmodules` submodule URL read local files outside the repo during checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  accepts an `allowFileProtocol` boolean and, when `true`, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation, with no inspection of the actual submodule URLs declared in the cloned repository's `.gitmodules`. This flag is threaded through from `checkoutBranch`/`checkoutCommit` in [2](#0-1)  and [3](#0-2) .

### Finding Description
Since Git 2.38 (CVE-2022-39253), Git restricts submodule URLs using the `file://` scheme by default (`protocol.file.allow=user`), precisely because a hostile repository could otherwise declare a submodule pointing at an arbitrary local path/URL and have Git copy that content into the victim's working tree during `submodule update --init --recursive`. Desktop's `updateSubmodulesAfterOperation` re-enables the unrestricted mode (`protocol.file.allow=always`) whenever it is invoked with `allowFileProtocol=true`: [4](#0-3) 

This override is applied globally to *all* submodules processed by that `submodule update` invocation — there is no per-submodule check that the URL is one the user expects (e.g., matching a known relative path, a previously-approved local mapping, or requiring explicit per-submodule confirmation). The function never reads or validates the `.gitmodules` file contents; it simply trusts whatever URLs are present, the same way `GiantPoolBase.withdrawLPTokens` trusted whatever LP token the caller specified without checking it was the one actually issued for staked ETH.

The attacker's primitive: craft a repository with a `.gitmodules` entry such as
```
[submodule "x"]
  path = payload
  url = file:///Users/victim/.ssh
```
When the victim clones/fetches this repository in Desktop and performs a checkout that Desktop happens to run with `allowFileProtocol=true`, Git will read from the local filesystem path instead of a remote and materialize its contents into the `payload` directory inside the working tree, because the safety check that would normally reject `file://` submodule URLs has been disabled by Desktop's `-c protocol.file.allow=always` argument.

### Impact Explanation
This falls squarely under the report's accepted impact class of "file write or read outside the repo": local files/directories the user never intended to expose (e.g., `~/.ssh`, another private local repository, credential caches) can be copied into the checked-out working tree of an untrusted, attacker-authored repository. If the victim subsequently stages/commits/pushes (a very natural next Desktop action after checkout), that local content is exfiltrated to the attacker's remote — a case of "silent corruption of what the user commits or pushes" as well, since the resulting commit contains data the user never knowingly added.

### Likelihood Explanation
The attacker only needs the victim to clone/fetch a hostile repository and check out a branch or commit within it — an ordinary Desktop workflow requiring no elevated privileges, local access, or unnatural steps, matching the report's valid-attacker profile ("attacker controls a cloned/fetched repository"). The remaining open question — which I was unable to fully verify before running out of tool budget — is the exact condition under which Desktop's higher-level callers (in `app-store.ts`/`dispatcher.ts`) pass `allowFileProtocol=true` into `checkoutBranch`/`checkoutCommit`. I confirmed the sink (`submodule.ts`) performs no validation regardless of that flag's origin, but I could not trace every call site that supplies `true` in the time available, so I cannot state with certainty how frequently this code path is exercised in normal usage versus a narrower/gated scenario.

### Recommendation
Do not globally re-enable `protocol.file.allow=always` for submodule updates during ordinary checkout operations. If local-path submodules must be supported, validate each URL in `.gitmodules` individually (e.g., only allow `file://` when it resolves to a path the user has explicitly trusted, mirroring how `getRepositoryType`/`addSafeDirectory` gate untrusted directories elsewhere in this codebase, see [5](#0-4) ), and prompt the user before fetching a submodule that resolves outside the expected remote origin.

### Proof of Concept
1. Attacker publishes a repository containing a `.gitmodules` file:
   ```
   [submodule "leak"]
     path = leak
     url = file:///Users/victim/.ssh
   ```
2. Victim clones this repository in GitHub Desktop and checks out a branch/commit that triggers `checkoutBranch`/`checkoutCommit` → `updateSubmodulesAfterOperation(..., allowFileProtocol=true)` ( [6](#0-5) ).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive` ( [7](#0-6) ), and Git copies the contents of `/Users/victim/.ssh` into `leak/` in the working tree, bypassing Git's own `file://` submodule protection.
4. Victim's private key material now exists inside the tracked working directory of an attacker-controlled repository; if committed and pushed, it is exfiltrated to the attacker's remote.

**Note on confidence:** I was not able to confirm, within the available tool budget, the precise higher-level conditions that set `allowFileProtocol=true` for a given checkout — this should be verified against `app-store.ts`/`dispatcher.ts` call sites before treating this as fully confirmed end-to-end exploitable in the default UI flow.
