Confirmed: `is_clvm_canonical()` / `is_atom_canonical()` in `chia/full_node/mempool_manager.py` is called directly on every submitted spend bundle's puzzle reveal and solution bytes in `MempoolManager.validate_spend_bundle()`, before any length re-validation against the atom's declared length prefix.

### Title
Out-of-bounds read in `is_atom_canonical()` / `is_clvm_canonical()` on attacker-controlled CLVM buffers - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` decodes a CLVM atom's length-prefix header by indexing `clvm_buffer[offset]` in a loop keyed off the prefix length bits, without ever checking that `offset` stays within `len(clvm_buffer)` [1](#0-0) . `is_clvm_canonical()`, which walks the whole buffer atom-by-atom and calls `is_atom_canonical()`, has the same unchecked-index pattern for `b = clvm_buffer[offset]` [2](#0-1) . This is analogous to the LibRaw `adobe_copy_pixel()` OOB-read bug class: a length/prefix field taken from untrusted input is used to index into a buffer with no upper-bound check against the buffer's actual size.

### Finding Description
Both functions are invoked directly on raw bytes coming from an untrusted, attacker-submitted `SpendBundle`:

```python
if not is_clvm_canonical(bytes(coin_spend.puzzle_reveal)) or not is_clvm_canonical(
    bytes(coin_spend.solution)
):
    return Err.INVALID_COIN_SOLUTION, None, []
``` [3](#0-2) 

Inside `is_atom_canonical()`, once the first byte's high bits select a `prefix_len` of up to 5, the loop `for i in range(prefix_len): ... offset += 1; atom_len |= clvm_buffer[offset]` reads subsequent bytes with no check that `offset < len(clvm_buffer)` [4](#0-3) . Likewise `is_clvm_canonical()`'s outer loop does `b = clvm_buffer[offset]` and, after processing a pair/atom token, continues without bounds-checking `offset` against the buffer length except at the very end of the whole walk [5](#0-4) . A truncated buffer whose last byte declares a multi-byte length prefix (e.g. `0xFC`, `0xF8`, `0xE0`, `0xC0` as the final byte with fewer bytes remaining than the prefix requires) causes Python to raise `IndexError` rather than a controlled `ValueError`/`Err`.

### Impact Explanation
In Python, `bytes[offset]` past the end raises `IndexError` instead of silently reading adjacent memory, so this is not a raw memory-corruption bug like the LibRaw C++ original. However, it is still a reachable unhandled-exception path: `validate_spend_bundle()` is called from `add_spend_bundle()` / `pre_validate_spendbundle()` in the mempool admission path, and an uncaught `IndexError` bubbling out of `is_clvm_canonical()` is not one of the `Err` results the mempool manager's callers expect to catch here — unlike other malformed-input cases in this same file which are deliberately converted to `Err.INVALID_COIN_SOLUTION`. This can produce a crash/exception in the full node's mempool-item processing path for a single submitted spend bundle, i.e., a spend-triggered transaction-processing disruption, rather than any coin-set divergence, forged asset identity, or theft.

### Likelihood Explanation
High from a reachability standpoint: any unprivileged party who can submit a spend bundle (wallet RPC, mempool gossip acceptance path) controls `coin_spend.puzzle_reveal` and `coin_spend.solution` bytes fed straight into `is_clvm_canonical()` [3](#0-2) . Constructing a buffer whose final byte is a multi-byte-prefix marker with no following bytes is trivial and requires no signature validity (this check happens as part of general coin-solution shape checking, independent of `AGG_SIG` verification).

### Recommendation
Add explicit bounds checks in both `is_atom_canonical()` and `is_clvm_canonical()` before indexing `clvm_buffer[offset]`, raising/returning a handled error (mirroring the existing `Err.INVALID_COIN_SOLUTION` path) instead of letting an `IndexError` propagate. Specifically, verify `offset < len(clvm_buffer)` on every loop iteration in `is_atom_canonical()`'s prefix-byte loop [4](#0-3)  and in `is_clvm_canonical()`'s main walk before each `clvm_buffer[offset]` read [6](#0-5) .

### Proof of Concept
Submit a `CoinSpend` whose `solution` (or `puzzle_reveal`) serializes to a truncated CLVM buffer ending in a multi-byte atom-length prefix marker with insufficient trailing bytes, e.g. `bytes.fromhex("fc")` (a `0xFC` marker requires 5 more prefix bytes but none follow). When `MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))` on this buffer, `is_atom_canonical()` executes `atom_len |= clvm_buffer[offset]` with `offset >= len(clvm_buffer)`, raising an unhandled `IndexError` instead of returning a mempool `Err` [4](#0-3) [3](#0-2) .

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
