### Title
Scanner::scan_block reports immature coinbase outputs as received funds that are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to consuming `latestRoundData` without checking `updatedAt` for staleness, `Scanner::scan_block` consumes block transaction data without checking whether each transaction's outputs are actually spendable. It iterates `block.txdata` including `txdata[0]` (the coinbase transaction), whose outputs are locked by Bitcoin's 100-block maturity rule. Any output paid to a watched script in the coinbase is returned as a `ReceivedOutput` indistinguishable from a normally spendable output.

### Finding Description
`scan_block` at networks/bitcoin/src/wallet/mod.rs:221-227 scans every transaction in `block.txdata`, including the coinbase at index 0:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

`scan_transaction` (lines 199-214) matches only on `output.script_pubkey` and pushes a `ReceivedOutput` carrying just `offset`, `output`, and `outpoint`. There is no maturity flag, no coinbase marker, and no spendability field — the returned `ReceivedOutput` is structurally identical to a confirmed, spendable UTXO. The doc comment on lines 216-220 acknowledges the issue ("This will also scan the coinbase transaction which is bound by maturity") but imposes it as a caller burden rather than enforcing it; `scan_block` is the natural API for block scanning and nothing in the type system or API prevents the immature output from flowing into scheduling/signing.

The attacker path requires only public inputs: the watched script pubkeys are derived from the public group key (`Scanner::new` / `register_offset`). Any miner — an unprivileged party — can construct a coinbase transaction paying to one of these scripts, exactly as they would pay any address.

### Impact Explanation
An output discovered this way is recorded as received funds, yet spending it via `sign_transaction` produces a transaction that Bitcoin consensus rejects (`bad-txns-premature-spend-of-coinbase`) for 100 blocks. Funds are reported received that are not spendable. Depending on the consumer, this can wedge a scheduler on an unbroadcastable plan or cause fee/change accounting to include value that cannot move, and a miner can repeat this every block they win.

### Likelihood Explanation
Low-to-moderate frequency, zero cost to the attacker: miners already produce coinbases and can point the payout at any public script. The 100-block delay is the only mitigator, and the impact is a scheduling failure rather than permanent loss, matching Medium severity — consistent with the acknowledged-caveat status of the upstream stale-data report.

### Recommendation
In `scan_block`, skip `block.txdata[0]` when it is a coinbase (`tx.is_coinbase()`), or record maturity on `ReceivedOutput` (e.g., an `is_coinbase` flag set in `scan_transaction`) so downstream consumers can defer scheduling until maturity. Documented caller-side post-processing is not a sufficient check since `scan_block` itself returns no signal distinguishing the output.

let mut scanner = Scanner::new(group_key).unwrap();
let watched_script = p2tr_script_buf(group_key).unwrap();

let coinbase = Transaction {
  // txdata[0]: coinbase paying `watched_script`
  input: vec![coinbase_txin],
  output: vec![TxOut { value: Amount::from_sat(50_0000_0000), script_pubkey: watched_script }],
  ..Default::default()
};
let block = Block { header, txdata: vec![coinbase] };

// scan_block returns the immature coinbase output as an ordinary ReceivedOutput
let outputs = scanner.scan_block(&block);
assert_eq!(outputs.len(), 1);
// outputs[0] is indistinguishable from a spendable output, yet any spend of
