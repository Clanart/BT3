### Title
Missing zero-check on governance parameter `GasTarget` causes division-by-zero panic in `NextMagmaBlockBaseFee` (KIP-71 base fee calc) - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` when computing the base fee delta, but unlike `BaseFeeDenominator` (which has an explicit `== 0` fallback), `GasTarget` has no such safeguard, and the governance parameter registry (`Kip71GasTarget`) uses a `noopFormatChecker` that accepts `0` as a valid value.

### Finding Description
In `NextMagmaBlockBaseFee`, when `parentGasUsed != gasTarget`, the code computes `x.Div(x, new(big.Int).SetUint64(gasTarget))` for both the "used more than target" and "used less than target" branches. [2](#0-1)  There is an explicit fallback for `BaseFeeDenominator == 0` ("To avoid panic, set the fluctuation range small"), but no equivalent guard exists for `gasTarget == 0`. [3](#0-2) 

`math/big.Int.Div` panics on division by zero. If `gasTarget` is `0` and `parentGasUsed` (`min(parentHeaderGasUsed, upperGasLimit)`) is not equal to `0` (i.e., any block actually uses gas), the code takes the `parentGasUsed > gasTarget` branch and panics inside `x.Div(x, new(big.Int).SetUint64(gasTarget))`. [4](#0-3) 

The governance parameter registry defines `Kip71GasTarget` with `FormatChecker: noopFormatChecker`, meaning any `uint64` value including `0` is accepted as a valid governance vote/parameter value — unlike `Kip71BaseFeeDenominator`, which explicitly rejects `0` via `return ok && v != 0`. [1](#0-0)  This is directly analogous to the reported Perennial bug: an edge case (`gasTarget == 0`, i.e., denominator degenerating) that the NatSpec/design intends to be handled (as evidenced by the sibling `BaseFeeDenominator` guard) is left unhandled for `GasTarget`.

### Impact Explanation
`NextMagmaBlockBaseFee` is called both when producing/verifying every block's `BaseFee` (`VerifyMagmaHeader`) and when computing `FeeHistory` results for the JSON-RPC API. [5](#0-4) [6](#0-5)  If `GasTarget` is set to `0` via governance vote, every node that processes a block whose parent used any gas will panic while computing the expected base fee — a state-transition/block-assembly path reachable by any block containing at least one transaction. This causes all honest nodes to crash/halt when processing that block, i.e., a chain-wide denial of service, not merely a resource-only bug.

### Likelihood Explanation
This requires a governance vote to set `kip71.gastarget` to `0`, which passes the (missing) format check since `noopFormatChecker` always returns `true`. [7](#0-6)  Once such a vote is finalized and the corresponding block/epoch activates it, any subsequent block with nonzero gas usage inevitably triggers the panic — the condition is deterministic and unavoidable once the parameter is `0`, unlike a probabilistic exploit.

### Recommendation
Add a zero-check for `gasTarget` in `NextMagmaBlockBaseFee`, mirroring the existing `BaseFeeDenominator == 0` fallback, e.g., treat `gasTarget == 0` as a special case (return `lowerBoundBaseFee`/`upperBoundBaseFee` or skip the block-based adjustment). Additionally, update `Kip71GasTarget`'s `FormatChecker` in `kaiax/gov/param.go` to reject `0`, consistent with `Kip71BaseFeeDenominator`'s `v != 0` check.

### Proof of Concept
1. Submit and finalize a governance vote setting `kip71.gastarget = 0` (accepted because `Kip71GasTarget.FormatChecker` is `noopFormatChecker`). [7](#0-6) 
2. Once the parameter activates, any block whose parent has `GasUsed > 0` causes `parentGasUsed := min(parentHeaderGasUsed, upperGasLimit)` to be `> 0 = gasTarget`, entering the `parentGasUsed > gasTarget` branch. [4](#0-3) 
3. `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` executes `big.Int.Div(x, 0)`, which panics, crashing every node computing/verifying the next block's `BaseFee` via `VerifyMagmaHeader`/`NextMagmaBlockBaseFee`. [8](#0-7)
