### Title
Frontmatter parsing divergence between `parse-frontmatter.sh` and `config_loader.py` causes inconsistent enforcement decisions on the same `.claude/*.local.md`/`hookify.*.local.md` file - ([File: plugins/plugin-dev/skills/plugin-settings/scripts/parse-frontmatter.sh])

### Summary
`parse-frontmatter.sh` extracts YAML frontmatter with a *stateful* sed range address (`/^---$/,/^---$/`) that reactivates every time a `---` line is encountered anywhere in the file, while `config_loader.extract_frontmatter` uses `content.split('---', 2)`, which only ever treats the first two `---` lines as delimiters and freezes everything after as opaque message text. An attacker who contributes a rule/settings file containing an extra `---`-delimited block inside the markdown body (a very common markdown idiom for horizontal rules) can make the two parsers disagree on the value of `enabled`/`action` for the identical file.

### Finding Description
`parse-frontmatter.sh` extracts frontmatter with:
```
FRONTMATTER=$(sed -n '/^---$/,/^---$/{ /^---$/d; p; }' "$FILE")
``` [1](#0-0) 
This range address is stateful across the whole file: once the first `---`…`---` range closes, any *subsequent* `---` line reopens a new range. Field extraction then does:
```
VALUE=$(echo "$FRONTMATTER" | grep "^${FIELD}:" | sed ...)
``` [2](#0-1) 
`grep` returns **every** matching line, so if the reactivated "second block" also contains a line starting with the same field name, `VALUE` becomes a multi-line string (e.g. `"true\nfalse"`).

By contrast, `config_loader.extract_frontmatter` in the hookify enforcement path does:
```python
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
``` [3](#0-2) 
Only the first two `---` lines are ever treated as delimiters; everything after is opaque `message` text and is never re-parsed as YAML, regardless of how many more `---` lines it contains. This feeds `Rule.from_dict`, which is used by `load_rule_file`/`load_rules` and consumed by `pretooluse.py`, `posttooluse.py`, and `stop.py` to make the actual PreToolUse/PostToolUse/Stop enforcement decision. [4](#0-3) [5](#0-4) 

`parse-frontmatter.sh` and the identical shell pattern is the officially documented way for plugin-dev agents/commands/hooks to read `.claude/*.local.md`/`hookify.*.local.md` settings files, including explicit `enabled`/`action`-style boolean checks:
```bash
ENABLED=$(echo "$FRONTMATTER" | grep '^enabled:' | sed 's/enabled: *//')
if [[ "$ENABLED" != "true" ]]; then exit 0; fi
``` [6](#0-5) 
This same source-of-truth file (e.g. `.claude/hookify.rule.local.md`) is readable both by hookify's Python enforcement path and by any agent/skill/command using this shell pattern, since both consume the identical file with no cross-checking.

**Exploit flow:** Attacker adds a file such as:
```
---
name: block-secrets
enabled: true
event: file
action: block
pattern: API_KEY
---

This rule blocks edits containing API_KEY.

---
enabled: false
---

Footer text.
```
- `config_loader` (hookify's real enforcement, `load_rule_file`) sees only the first two `---` lines as frontmatter: `enabled=True, action="block"` — a strict rule.
- `parse-frontmatter.sh file.md enabled` sees the sed range reopen at the third `---` line, appends `enabled: false` to `FRONTMATTER`, and `grep '^enabled:'` returns two lines, producing `VALUE="true\nfalse"`. Any shell consumer doing `[ "$ENABLED" = "true" ]` (the exact pattern documented in `SKILL.md`) evaluates false, treating the rule as disabled and skipping its own enforcement, contradicting hookify's authoritative `enabled=True`.

No allowlist, workspace guard, or parser-agreement check exists between the two code paths; the file is not schema-validated against a single canonical parser before either consumer reads it.

### Impact Explanation
This breaks the invariant that a single `.claude/*.local.md`/`hookify.*.local.md` file yields one consistent enforcement decision. Any agent-facing workflow, hook, or command built per the plugin-dev `SKILL.md` guidance (or using `parse-frontmatter.sh` directly) that trusts the shell-parsed `enabled`/`action` value can take a materially weaker action (skip enforcement, treat a `block` rule as `warn`, etc.) on a file that hookify's own enforcement path treats as strictly enabled/blocking — a trust-boundary bypass caused entirely by attacker-controlled repository content, with no elevated privilege required.

### Likelihood Explanation
Trivial and fully repeatable: an unprivileged contributor only needs to add one `.local.md`-style file containing a markdown horizontal rule (`---`) in the body followed by a re-used key (`enabled`/`action`) and a closing `---` — an extremely natural markdown construct, not an obscure edge case. Any project pairing hookify's enforcement hooks with a shell-based settings/agent workflow built from the documented pattern is affected deterministically every time such a file is loaded.

### Recommendation
Rewrite `parse-frontmatter.sh`'s extraction to match `config_loader.py`'s semantics exactly: stop after the second literal `---` line (e.g., using an `awk`/counter-based single-pass extraction like the `BODY=$(awk '/^---$/{i++; next} i>=2' "$FILE")` pattern already present elsewhere in the same skill), and change field extraction to take only the first match (`grep -m1`). More robust: replace shell YAML parsing with a call into `config_loader.py`/a shared canonical parser so all consumers of `.claude/*.local.md` files agree by construction.

### Proof of Concept
Invariant/differential test:
1. Generate randomized frontmatter documents of the form: `--- <k:v pairs> --- <body text possibly containing one or more extra "---"-delimited pseudo-blocks with reused keys> ---` (including the "clean" no-extra-delimiter case).
2. For each document, write it to a temp file and run:
   - `bash parse-frontmatter.sh tmpfile.md enabled` → `shell_enabled`
   - `config_loader.Rule.from_dict(*config_loader.extract_frontmatter(open(tmpfile.md).read())[:1], "")` wait: `frontmatter, message = extract_frontmatter(content); rule = Rule.from_dict(frontmatter, message)` → `python_enabled = str(rule.enabled).lower()`
3. Assert `shell_enabled == python_enabled` (and similarly for `action`).
4. Expected result: assertion fails whenever the generated document contains an extra `---`-delimited block in the body reusing the `enabled` (or `action`) key — `shell_enabled` becomes a multi-line/garbled value (`"true\nfalse"`) while `python_enabled` remains the value from the first frontmatter block only, demonstrating the divergence and its impact on any `[ "$ENABLED" = "true" ]`-style shell comparison.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
