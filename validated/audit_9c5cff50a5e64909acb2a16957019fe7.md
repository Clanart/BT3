### Title
Unlimited, unthrottled master-passphrase brute force via daemon RPC `unlock_keyring`/`validate_keyring_passphrase` - ([File: chia/daemon/server.py])

### Summary
The Nextcloud CVE-2021-41177 bug class is "rate limiting exists in code but is silently absent for a code path because it depends on an optional backend / is not consistently applied." In this repo, the analogous gap is that keyring master-passphrase brute-force protection (retry cap + delay) is implemented only in the interactive CLI helper `obtain_current_passphrase()`, but the daemon's RPC handlers that perform the exact same passphrase check have no such protection at all.

### Finding Description
`chia/util/keyring_wrapper.py` defines the intended anti-brute-force control: [1](#0-0) 
This is enforced only inside `obtain_current_passphrase()`, which loops `MAX_RETRIES` times with a `FAILED_ATTEMPT_DELAY` sleep between failed attempts and then raises `KeychainMaxUnlockAttempts`: [2](#0-1) 

However, the daemon exposes the identical underlying check — `Keychain.master_passphrase_is_valid()` / `KeyringWrapper.master_passphrase_is_valid()` — directly over the local RPC/websocket surface via `unlock_keyring` and `validate_keyring_passphrase`, with no retry counter, no delay, and no lockout: [3](#0-2) [4](#0-3) 

Both handlers are registered in the daemon's command map and reachable by any client permitted to open a websocket connection to the daemon: [5](#0-4) 

The underlying validation itself performs no internal throttling either — `master_passphrase_is_valid` maps straight to `FileKeyring.check_passphrase()`, which just attempts a decryption and returns a boolean: [6](#0-5) [7](#0-6) 

As documented in the module context, the daemon's only gate is mutual TLS plus local config, with no request-level rate limiter of any kind — this is explicitly called out as distinct from the P2P rate-limit machinery in `chia/server/`: [8](#0-7) 

The v1/v2/v3 rate limiters described in `chia/server/rate_limits.py`, `rate_limit_numbers.py`, and `rate_limits_v3.py` are peer-wire-protocol-only and are never wired into the daemon's local RPC dispatch (`get_command_mapping()`), confirming the daemon RPC surface has zero request throttling for any command, including passphrase validation.

### Impact Explanation
Any local client capable of completing the daemon's mutual-TLS handshake (any process holding/derivable from the daemon private certs, which is the same access class used by `KeychainProxy`, CLI, and GUI) can send unlimited `unlock_keyring` or `validate_keyring_passphrase` requests to brute-force the master passphrase protecting the wallet keyring, with no lockout, exponential backoff, or attempt cap — unlike the CLI path which caps attempts at `MAX_RETRIES = 3`. A successful guess unlocks the keyring and yields access to all private keys managed by `Keychain`, enabling unauthorized signing/spending of all coins controlled by those keys — a full custody compromise. This satisfies the "unauthorized coin movement" acceptance criterion via unauthorized private key recovery.

### Likelihood Explanation
Exploitability depends on the passphrase's strength and the KDF cost per attempt (`FileKeyring.check_passphrase` performs an authenticated decryption per call), so this is not a trivial online attack against a strong passphrase, but it is a definite regression relative to the CLI's explicit `MAX_RETRIES`/delay design intent, and the attack requires no privilege escalation beyond the level already needed to talk to the daemon (i.e., any local RPC caller in the defined threat model). Given the daemon RPC access is explicitly in-scope ("daemon/keychain RPC authorization, wallet state and key derivation") and no other layer compensates, likelihood is Medium.

### Recommendation
Apply the same anti-brute-force policy used in `obtain_current_passphrase()` (attempt counting, inter-attempt delay, and lockout raising `KeychainMaxUnlockAttempts`) inside `WebSocketServer.unlock_keyring()` and `WebSocketServer.validate_keyring_passphrase()` in `chia/daemon/server.py`, tracked per-connection or per-daemon-instance, and independent of any optional external cache/backend so the protection is always active regardless of deployment configuration.

### Proof of Concept
1. Obtain a local websocket connection to the daemon using the daemon certs (the same access any `KeychainProxy`/CLI/GUI client uses).
2. Send repeated `validate_keyring_passphrase` (or `unlock_keyring`) command payloads with different `key` guesses, as done in `chia/_tests/core/daemon/test_daemon.py::test_validate_keyring_passphrase_rpc`: [9](#0-8) 
3. Observe that the daemon returns `{"success": False, "error": None}` for each wrong guess with no increasing delay, no error indicating lockout, and no connection termination — confirming requests can be repeated indefinitely, unlike the CLI path (`obtain_current_passphrase`) which raises `KeychainMaxUnlockAttempts` after 3 tries.

```python
    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"
```

```python
    async def validate_keyring_passphrase(
        self,
        websocket: WebSocketResponse,
        request: dict[str, Any],
    ) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            success = Keychain.master_passphrase_is_valid(key, force_reload=True)
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"

        response: dict[str, Any] = {"success": success, "error": error}
        return response
```

```python
    def check_passphrase(self, passphrase: str, force_reload: bool = False) -> bool:
        """
        Attempts to validate the passphrase by decrypting keyring.data
        contents and checking the checkbytes value
        """
        if force_reload:
            self.cached_file_content = FileKeyringContent.create_from_path(self.keyring_path)

        try:
            self.cached_file_content.get_decrypted_data_dict(passphrase)
            return True
        except Exception:
            return False
```
