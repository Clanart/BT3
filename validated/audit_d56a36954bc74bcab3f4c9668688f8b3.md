### Title
`Treasury.payRent`‑style pause bypass analog: `BaseSendKeeper.SendCoinsAndWei` (wei-denominated transfers used by the EVM bank precompile) skips the `BlockedAddr`/module-blocklist enforcement that `SendCoins` performs - ([File: sei-cosmos/x/bank/keeper/send.go])

### Summary
The realitycards bug is a classic "one transfer entrypoint enforces a safety check, a sibling entrypoint doing the same fund movement does not" pattern. In `sei-cosmos/x/bank/keeper/send.go` the usei coin transfer path (`SendCoins` → `SendCoinsWithoutAccCreation` → `sendCoinsWithoutAccCreation`) is guarded by `AddCoins`, which calls `k.CanSendTo(ctx, addr)` [1](#0-0) , and the higher-level `MsgSend` handler in `msg_server.go` additionally checks `BlockedAddr` before invoking the keeper. The sibling wei-denominated transfer function `SendCoinsAndWei`, used by the EVM bank precompile to move the sub-usei ("wei") remainder of native token balances, only calls `SubWei`/`AddWei` [2](#0-1) . `AddWei` itself only checks `CanSendTo` [3](#0-2)  — the same recipient-checker hook used by `AddCoins` — but the actual `BlockedAddr` denylist check (which restricts sending to module/system accounts) is defined separately as a keeper interface method [4](#0-3)  and is not invoked anywhere inside `SendCoinsAndWei`/`AddWei`/`SubWei`.

### Finding Description
`BlockedAddr` is meant to prevent transfers of funds into restricted module accounts (e.g. fee collector, mint, distribution, or the `evm_coinbase` prefix address it explicitly special-cases) [4](#0-3) . For ordinary `usei` coin sends via `MsgSend`, this check is enforced before the keeper's `SendCoins` is invoked. However, `SendCoinsAndWei`, which is the function used to move the wei-denominated remainder for EVM-native transfers (reached via the EVM bank precompile and any code path that settles usei/wei balances for EVM accounts), never calls `BlockedAddr`. It only routes through `CanSendTo`, which is driven by a distinct, pluggable `recipientCheckers` mechanism [3](#0-2) , not the blocklist. This is functionally identical to the reported bug class: a security check (`marketPaused`/`BlockedAddr`) exists and is enforced on one code path (`Market.newRental`/`SendCoins`) but is silently absent on a sibling code path that performs the same fundamental operation (`payRent`/`SendCoinsAndWei`).

### Impact Explanation
If `BlockedAddr` is relied upon to prevent funds from landing in module accounts that should never directly receive user-initiated transfers (which would corrupt module accounting invariants, e.g. the fee collector or mint module balance being manipulated outside of its expected flow), an EVM transaction sender can use the wei-transfer path to move wei into those restricted addresses, bypassing the safeguard that `usei` sends observe. This is reachable directly from a submitted EVM transaction (any address-to-address transfer with a non-zero wei remainder) and could allow unauthorized crediting of a blocked/module address, undermining bank module invariants that the rest of the system assumes are protected by `BlockedAddr`.

### Likelihood Explanation
The precompile/EVM path for native token transfers routinely uses `SendCoinsAndWei` to reconcile usei/wei balances since Sei represents EVM 18-decimal native value as usei + wei. Any EVM transaction sender can trigger a transfer to an arbitrary address, including addresses that map to blocked/module accounts, so the divergent code path is trivially reachable without special privileges.

### Recommendation
Add an explicit `BlockedAddr` (and, for parity, `IsSendEnabledCoins`/`IsInDenomAllowList` where applicable) check on the recipient inside `SendCoinsAndWei` (or in `AddWei`), mirroring the checks performed for the `usei` coin transfer path, so that wei-denominated transfers cannot land in restricted module/system addresses that ordinary bank sends are barred from crediting.

### Proof of Concept
Could not be fully constructed within the available tool budget — I was unable to inspect `precompiles/bank/bank.go` and `sei-cosmos/x/bank/keeper/msg_server.go` in enough detail to confirm the exact call sites and whether an outer layer (e.g., the precompile itself) redundantly re-checks `BlockedAddr` before calling `SendCoinsAndWei`. The code shown above conclusively demonstrates that `SendCoinsAndWei`/`AddWei`/`SubWei` in `sei-cosmos/x/bank/keeper/send.go` do not call `BlockedAddr`, unlike the `usei` `SendCoins` path which is gated by it at the `MsgSend` handler level; verifying end-to-end exploitability requires confirming that no other layer (precompile-level check) re-enforces `BlockedAddr` before invoking `SendCoinsAndWei`.

func (k BaseSendKeeper) BlockedAddr(addr sdk.AccAddress) bool {
	if len(addr) == len(CoinbaseAddressPrefix)+8 {
		if bytes.Equal(CoinbaseAddressPrefix, addr[:len(CoinbaseAddressPrefix)]) {
			return true
		}
	}
	return k.blockedAddrs[addr.String()]
}
