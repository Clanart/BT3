## Title
BEEFY ECDSA consensus client accepts state updates without checking for duplicate `authorityIndex` votes, allowing sub-quorum sets of colluding validators to pass the supermajority check - (File: `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` derives its supermajority decision purely from the *count* of submitted votes (`sigLen = relayProof.signedCommitment.votes.length`), never checking that each vote comes from a distinct `authorityIndex`. This is the same bug class as the external report: a length/count-derived value taken directly from attacker-controlled input is trusted for a security-critical decision without validating the uniqueness/structure of the underlying data.

### Finding Description
In `verifyMmrUpdateProof`: [1](#0-0) 

```solidity
uint256 sigLen = relayProof.signedCommitment.votes.length;
...
if (!checkParticipationThreshold(sigLen, authoritySet.len)) revert SuperMajorityRequired();
...
MerkleMultiProof.Leaf[] memory authorities = new MerkleMultiProof.Leaf[](sigLen);
for (uint256 i = 0; i < sigLen; i++) {
    Vote memory vote = relayProof.signedCommitment.votes[i];
    address authority = ECDSA.recover(commitmentHash, vote.signature);
    authorities[i] = MerkleMultiProof.Leaf({index: vote.authorityIndex, hash: keccak256(abi.encodePacked(authority))});
}
bool valid = MerkleMultiProof.VerifyProof(authoritySet.root, relayProof.proof, authorities, authoritySet.len);
```

`checkParticipationThreshold(len, total)` only compares raw counts: [2](#0-1) 

Nowhere in this function — nor in `MerkleMultiProof.VerifyProof` as called here — is there a check that the `authorityIndex` values inside `relayProof.signedCommitment.votes` are unique. The `votes` array is fully attacker/relayer-supplied calldata (it is decoded straight from `proof` in `verify()`), so an attacker (or a relayer colluding with a minority of validators) can submit the *same* valid `(authorityIndex, signature)` pair multiple times, or the same signature under artificially repeated entries, inflating `sigLen` far past the true number of distinct signing authorities while the actual number of unique, verifiable validator signatures is below the real 2/3+1 threshold.

Compare this with the Rust BEEFY verifier (`modules/consensus/beefy/verifier/src/lib.rs`), which also counts `signatures_length` directly from `mmr.signed_commitment.signatures.len()` for the threshold check before doing per-index Merkle verification — the same missing-uniqueness pattern exists there too, but it is the Solidity `EcdsaBeefy` path (used directly on EVM destination/consensus clients, is documented as "no off-chain proving infrastructure" i.e. a production, permissionless-message verification path) that is most exposed since anyone can submit a BEEFY consensus proof to advance trusted state (`IConsensusV2.verify`).

Whether this duplicate-index inflation ultimately succeeds also depends on whether `MerkleMultiProof.VerifyProof` internally tolerates or de-duplicates repeated indices in its 2-D k-index reconstruction (that library lives outside this repo, in `@polytope-labs/solidity-merkle-trees`, so its exact duplicate-handling behavior could not be confirmed from this codebase). The vulnerability described here is precisely the missing local guard: `EcdsaBeefy.sol` has zero uniqueness enforcement on `authorityIndex` before trusting `sigLen` for the supermajority decision, unlike the length/format checks hardened elsewhere in this same file (e.g., the `mmr.mmr_proof.leaf_indices.len() != 1` guard added in the Rust BEEFY verifier, `modules/consensus/beefy/verifier/src/lib.rs:234`, which exists specifically because unchecked lengths from proof data were previously exploitable).

### Impact Explanation
If duplicate `authorityIndex` entries are not rejected by the multi-proof library (or if any other combination of `votes` lets `sigLen` diverge from the true distinct-signer count), an attacker controlling fewer than 2/3+1 real BEEFY validator keys can forge a `BeefyConsensusProof` that `EcdsaBeefy.verify()` accepts as legitimate. This directly causes **false state acceptance**: a fabricated MMR root / parachain state commitment gets stored via `EvmHost.storeConsensusState` and `storeStateMachineCommitment` (see `HandlerV2.sol` lines 151-164), which is then used to authorize `handlePostRequests`, `handleGetResponses`, and timeout paths — i.e., unauthorized cross-chain message execution and fund transfers (escrow release, relayer fee payout) driven from an unauthenticated consensus proof.

### Likelihood Explanation
This requires an attacker to hold real signatures from some subset of validators (not a wholly unprivileged attacker, and not simply "malicious peer" since the vote signatures still must ECDSA-recover to real authority-set members) — but it does **not** require colluding with 2/3+1 of the validator set, which is the entire security assumption of BEEFY light clients. Any minority coalition (or a single compromised/rented key reused across duplicated leaf entries, if the underlying multi-proof accepts repeated `k_index` positions) could exploit it. The complexity is that exploitability hinges on unverified behavior of the external `MerkleMultiProof.VerifyProof` implementation, which this review could not fully confirm was safe or unsafe against duplicate indices from within this repository alone.

### Recommendation
In `verifyMmrUpdateProof`, before computing `sigLen`/the threshold check, deduplicate and validate `vote.authorityIndex` values (e.g., require strictly increasing indices, or track a bitmap/`seen` set and revert on repeats) so `checkParticipationThreshold` is computed against the count of *distinct* authorities, not the raw array length. Apply the equivalent fix to `verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs` for consistency between the Solidity and Rust BEEFY light clients.

### Proof of Concept
Conceptual (could not be fully executed without the `solidity-merkle-trees` library source to confirm duplicate-index handling):
1. Attacker/relayer obtains one or a minority of validator ECDSA signatures over a forged `Commitment` (e.g. a fabricated MMR root pointing at attacker-controlled parachain state).
2. Attacker builds `relayProof.signedCommitment.votes` with the same `(authorityIndex, signature)` pair repeated `N` times such that `sigLen = N >= (2*authoritySet.len)/3 + 1`, satisfying `checkParticipationThreshold`.
3. Calls `EvmHost`/`HandlerV2` consensus-update entrypoint with this proof.
4. If `MerkleMultiProof.VerifyProof` does not reject repeated leaf indices, the forged commitment is accepted, `newState` is stored, and the attacker's fabricated `IntermediateState` (state root) becomes trusted — enabling subsequent forged `PostRequest`/`GetResponse` proofs against that fake root to drain escrowed funds via `handlePostRequests`/`dispatchIncoming`.
