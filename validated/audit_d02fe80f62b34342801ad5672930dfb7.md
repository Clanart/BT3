### Title
Escrow marked filled/refunded and decremented even when ERC20 transfer silently fails, permanently locking user funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` contract releases escrowed order tokens to a beneficiary using a raw low-level `.call()` to the token's `transfer` selector, and only checks that the *call itself* did not revert (`success`), never decoding the ERC20 boolean return value. For a "no-revert-on-failure" ERC20 token (returns `false` instead of reverting), `success` is `true` even though no tokens actually moved, yet the function unconditionally marks the order as settled and decrements the escrow accounting — an exact structural analog of the Footium `claimERC20Prize()` bug.

### Finding Description
`withdraw()` is the single internal function that releases input-token escrow for both order refunds (`cancelOrder`, same-chain and cross-chain via `onGetResponse`) and successful fills (`RedeemEscrow` via `onAccept`): [1](#0-0) 

```
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    if (token == address(0)) {
        (bool sent,) = beneficiary.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
```

`success` here reflects only whether the external call reverted, not the decoded ERC20 return value. Standard-noncompliant, "no-revert-on-failure" ERC20 tokens (historically USDT, BNB, ZRX, and others) return `false` on a failed transfer instead of reverting. In that case `success == true`, the `if (!success) revert TransferFailed();` guard never fires, and execution proceeds to:
- `_filled[body.commitment] = beneficiary;` (set unconditionally at function entry, before the transfer even executes)
- `_orders[body.commitment][token] -= amount;` (escrow accounting decremented as if the release succeeded)

Once `_filled[commitment]` is non-zero, the same commitment can never be retried: `cancelOrder()` checks `if (_filled[commitment] != address(0)) revert Filled();` [2](#0-1) , and `onGetResponse` checks `if (incoming.response.values[0].value.length != 0) revert Filled();` before calling `withdraw` [3](#0-2) . There is no retry or recovery path once the commitment is marked filled/refunded.

This is precisely the class of bug from the seed report: an unchecked `transfer()` (here, an unchecked low-level `.call()` whose returndata boolean is ignored) lets accounting state advance as if the transfer succeeded, while the token itself silently drops the transfer. The other transfer sites in the same file that use a similar `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern (`SweepDust` handling and the tx-fee redemption at the end of `withdraw`) have the identical flaw [4](#0-3) . By contrast, the token *deposit* paths in `placeOrder` correctly use OpenZeppelin `safeTransferFrom` [5](#0-4) , and the predispatch/call-dispatcher sweep paths measure actual balance deltas rather than trusting the call result [6](#0-5)  — but `withdraw()`'s output-side release does neither.

### Impact Explanation
This directly matches the required impact class "stealing or loss of funds." Escrowed order-input tokens become permanently unrecoverable:
- On refund (`cancelOrder`), the order owner's own escrowed tokens are marked refunded/filled without ever moving, so the user loses access to them with no way to retry.
- On a legitimate fill settlement (`RedeemEscrow` triggered by `onAccept`), the solver's earned input-token payout can silently fail to transfer while the protocol still records the order as filled — the solver never receives payment and the tokens are stuck in the contract, unreachable by any other code path (no sweep/rescue function guards against this exact residual-balance scenario tied to a specific commitment).

Both cases are outright loss of user/solver funds, not merely griefing, matching the bounty's accepted impact ("stealing or loss of funds ... false proof/state acceptance" analog — here it is false *settlement-state* acceptance for a token-transfer outcome).

### Likelihood Explanation
The intent system is explicitly multi-chain and permissionless about which ERC20 the order creator selects as `order.inputs[i].token` — there is no allowlist enforced in `placeOrder`/`withdraw`. No malicious relayer, prover, admin, or governance actor is required: the order creator (an ordinary unprivileged user) simply escrows a token that is known to return `false` on failed transfers (a well-documented, still-in-production category of ERC20 implementations) under conditions the transfer can fail (e.g., blacklist status, paused token, insufficient allowance/balance edge state introduced by the token's own logic). This is a realistic production scenario, not a testnet-only or hypothetical corner case, and it is fully reachable through the normal `cancelOrder` / cross-chain `RedeemEscrow` flow that every order goes through.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` release path in `withdraw()` (and the identical pattern in the `SweepDust` handler and fee redemption) with OpenZeppelin's `SafeERC20.safeTransfer()`, which both propagates reverts and validates the decoded boolean return value for tokens that return `false` instead of reverting. Alternatively, follow the same "measure the balance delta" pattern already used in the deposit-side sweep logic — record `balanceOf(beneficiary)` before and after the transfer and require the delta equals `amount`, reverting otherwise — before mutating `_filled` and `_orders`.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer()` returns `false` (no revert) whenever a configurable "fail" flag is set (mirrors real no-revert-on-failure tokens like legacy USDT).
2. `placeOrder()` an intent using this mock token as `order.inputs[0].token`, escrowing `amount` tokens into `IntentGatewayV2`.
3. Set the mock token's fail flag to `true` (simulating e.g. the beneficiary being blacklisted, or the token being paused).
4. Call `cancelOrder()` for a same-chain order (or trigger `onGetResponse`/`onAccept` RedeemEscrow/RefundEscrow for cross-chain), which invokes `withdraw(body, isRefund)`.
5. Observe: `token.call(...)` returns `success = true` (the mock's `transfer` executes without reverting) even though it returns `false`; the `if (!success) revert TransferFailed();` guard does not fire.
6. `_filled[commitment]` is now set to the beneficiary and `_orders[commitment][token]` is decremented, while `token.balanceOf(beneficiary)` is unchanged (transfer never actually happened).
7. Any further attempt to cancel or redeem this commitment reverts with `Filled()`, and the tokens remain stuck in the `IntentGatewayV2` contract with no recovery path — permanent fund loss.
