Audit Report

## Title
Calculated stake rewards are permanently burned instead of retried if a stake account is closed before its partition's distribution block - ([File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`])

## Summary
Agave computes each stake account's epoch reward once at the reward-calculation boundary but defers the actual lamport credit across many subsequent blocks via `distribute_partitioned_epoch_rewards`. If a stake account is fully withdrawn/closed (removed from the live `stakes_cache`) after calculation but before its specific partition's distribution block, `build_updated_stake_reward` returns `DistributionError::AccountNotFound`, and `store_stake_accounts_in_partition` responds by logging an error and permanently discarding the calculated reward into `stake_reward_lamports_burned`, with no retry or recovery path.

## Finding Description
Reward calculation happens once at the epoch boundary in `begin_partitioned_rewards`, which stores the computed `all_stake_rewards` and sets `EpochRewardStatus::Active(EpochRewardPhase::Calculation(...))` [1](#0-0) . Distribution is then spread over many subsequent blocks by `distribute_partitioned_epoch_rewards`, which on each block height within `[distribution_starting_block_height, distribution_end_exclusive)` calls `distribute_epoch_rewards_in_partition` for that block's `partition_index` [2](#0-1) .

Critically, in normal (non-snapshot-restore) block processing, this distribution path uses the `all_stake_rewards` computed once at calculation time — it is not recalculated against the current `stakes_cache` each block. The only place recalculation happens is `recalculate_partitioned_rewards_if_active`, which is called solely from `initialize_after_snapshot_restore` [3](#0-2) , not on every ordinary block during the distribution window.

When a given stake account's partition block arrives, `store_stake_accounts_in_partition` looks the account up in the live `stakes_cache_accounts` via `build_updated_stake_reward`: [4](#0-3) . If the account is not found (e.g., it was withdrawn/closed in the intervening blocks), this returns `Err(DistributionError::AccountNotFound)` [5](#0-4) .

`store_stake_accounts_in_partition` handles this failure by logging an `error!` and adding the reward amount to `stake_reward_lamports_burned`, permanently discarding the payment with no retry: [6](#0-5) . The doc comment directly above explicitly (and incorrectly, in the general case) asserts this should never happen: [7](#0-6) .

I searched for the "stake-program restrictions" referenced in that comment that would supposedly prevent a stake account with a pending calculated reward from being withdrawn/closed before its distribution block, and found no such check tying stake `Withdraw` processing to the bank's `EpochRewardStatus`/pending reward state. The existing guard is only aspirational commentary, not an enforced invariant — the `AccountNotFound` branch exists precisely because this assumption can be violated.

## Impact Explanation
Any staker can trigger the loss of their own already-computed reward by fully withdrawing/closing their stake account during the multi-block reward-distribution window, before their specific partition's block height is reached. The exact corrupted/lost value is the calculated `stake_reward_amount` (and associated `block_reward_amount`) for that stake account, which is added to `stake_reward_lamports_burned`/`block_reward_lamports_burned` in `DistributionResults` [8](#0-7)  instead of being credited to the account. This is a genuine, unrecoverable loss of lamports legitimately owed per the epoch's `point_value.rewards` accounting, falling under the runtime/accounts fund-loss impact category. The loss is self-inflicted (affects only the acting staker's own reward) rather than a cross-account theft, which limits blast radius but does not eliminate the fund-loss classification.

## Likelihood Explanation
This requires no privileged access — any holder of a stake account can trigger it via a normal deactivate-then-`Withdraw` sequence timed to land within the reward-distribution block window, which can span many blocks depending on `num_partitions` (computed via `get_reward_distribution_num_blocks`) [9](#0-8) . It is a low-effort, self-serviceable, deterministic action once the attacker knows (or estimates) their partition's block height.

## Recommendation
Rather than unconditionally burning the reward on `AccountNotFound` in `store_stake_accounts_in_partition`, either detect stake-account closures at reward-calculation time and exclude/adjust affected entries before finalizing the point-value-based budget, or add an explicit enforced restriction (not just a comment) in the stake program preventing full withdrawal/closure of a stake account that has a pending, not-yet-distributed calculated reward, or redirect the un-deliverable reward lamports to a reconciled fallback rather than silently classifying them as burned.

## Proof of Concept
1. At an epoch boundary, `begin_partitioned_rewards` computes a positive `stake_reward` for stake account `S` and stores it in `all_stake_rewards`/`partition_indices`.
2. Before the block height corresponding to `S`'s partition index (`distribution_starting_block_height + partition_index`) is reached, submit a `Deactivate` + `Withdraw` transaction pair that fully withdraws `S`, removing it from `stakes_cache`.
3. When `S`'s partition block arrives, `store_stake_accounts_in_partition` calls `build_updated_stake_reward`, which returns `Err(DistributionError::AccountNotFound)` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:249-252`).
4. The `match` in `store_stake_accounts_in_partition` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:393-407`) logs the failure and adds `stake_reward_amount` to `stake_reward_lamports_burned` — the reward computed for `S` is never paid and cannot be retried. This can be reproduced as a Rust unit test analogous to `test_distribute_partitioned_epoch_rewards`, but removing the target stake account from `stakes_cache` between calculation and its partition's distribution block, then asserting `stake_reward_lamports_burned > 0` in the returned `DistributionResults`.

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
