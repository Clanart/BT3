### Title
`OnRecvPacket` returns an error acknowledgement after the underlying ICS20 transfer has already unescrowed/minted funds, causing double-crediting of value across chains - (File: x/erc20/keeper/ibc_callbacks.go)

### Summary
`x/erc20`'s ICS20 middleware auto-converts received IBC coins into their ERC20 representation inside `Keeper.OnRecvPacket`. In "Case 2" (receiving a coin that is a registered native-ERC20 token pair), if `MintingEnabled` or `ConvertCoinNativeERC20` fails, the function returns `channeltypes.NewErrorAcknowledgement(err)` — but this callback runs *after* the wrapped ICS20 transfer app has already unescrowed/credited the coin to the recipient's bank balance. Converting a packet that already had a successful, committed state transition into an "error acknowledgement" causes the source chain to interpret the packet as failed and refund/re-mint the sender's funds there, while the destination chain keeps the funds it already credited — duplicating spendable value across the two chains. This is the ICS20/erc20 analog of the referenced `getNextValidator()` report: a downstream failure in an auxiliary step (validator/ERC20 registration or minting) is allowed to corrupt/abort a flow whose primary effects (fund movement) were already irreversibly committed.

### Finding Description
`OnRecvPacket` in `x/erc20/ibc_middleware.go` first invokes the wrapped ICS20 transfer module's `OnRecvPacket`, which performs the actual escrow/mint/unescrow of coins and returns a success acknowledgement if that step succeeded: [1](#0-0) 

Only if that succeeds does control pass to `k.OnRecvPacket` (the erc20 keeper), which performs an *additional*, non-essential step: converting the already-received Cosmos coin into its ERC20 representation: [2](#0-1) 

For "Case 2" (`found && pair.IsNativeERC20()`), if the additional ERC20 minting step fails, the code discards the previously-returned success acknowledgement and substitutes an error acknowledgement: [3](#0-2) 

By the time this code runs, `im.Module.OnRecvPacket` has already unescrowed the native ERC20's backing coin from the escrow account to the recipient's bank balance (this is the state mutation that IBC's ack-based refund protocol assumes did NOT happen for an error ack). Returning `NewErrorAcknowledgement` here does not roll back that already-committed state change — it only affects what acknowledgement bytes get written and relayed back over IBC.

The counterparty chain, upon receiving this error acknowledgement, will execute its own `OnAcknowledgementPacket`/refund logic, re-crediting (un-escrowing or re-minting) the amount to the original sender on that chain — exactly as demonstrated by this repo's own test suite, which verifies that error acks reliably trigger `checkRefund()` / escrowed-balance-zero-and-sender-refunded behavior: [4](#0-3) [5](#0-4) 

The result: the recipient on the destination chain already holds the unescrowed coin (from the underlying transfer module's already-committed mutation), while the sender on the source chain is refunded/re-minted the same amount due to the (incorrectly) downgraded acknowledgement — a duplication of the same value on both sides of the channel.

Notably, the code path handling the mirror-image scenario (`OnAcknowledgementPacket` / `OnTimeoutPacket` → `ConvertCoinToERC20FromPacket`) intentionally avoids this exact class of bug: when the same `ConvertCoinNativeERC20` call fails there, the error is deliberately swallowed and `nil` (success) is returned instead of propagating the failure, with an explicit code comment explaining that the user should just keep the bank token and manually retry conversion: [6](#0-5) [7](#0-6) 

This inconsistency confirms the intended safe pattern (swallow post-commit conversion failures, never turn a committed receive into an error ack) was correctly applied in the Ack/Timeout paths but was not applied in the `OnRecvPacket` Case 2 path, where the bug lives.

Case 1 (registering a brand-new IBC denom as an ERC20 extension) has the identical structural flaw — `RegisterERC20Extension` failure also returns an error ack after the underlying transfer already minted the voucher coin — but Case 1 registration failures are comparatively harder for an unprivileged attacker to force deterministically (they generally require internal collisions such as EVM account/codehash conflicts). Case 2, by contrast, is reachable any time `MintingEnabled` or the ERC20 `transfer` call inside `ConvertCoinNativeERC20` fails for a token pair that is otherwise valid and enabled — e.g. `IsSendEnabledCoin` being false for the denom, the receiver being blocked, or (in `ConvertCoinNativeERC20`) the module's escrowed ERC20 token balance being insufficient/exhausted due to a race with other in-flight conversions, or the ERC20 contract call reverting for any reason (self-destructed contract, transfer hook, non-standard return value, etc., as literally documented in the code's own comments about failure modes).

### Impact Explanation
This matches the Critical impact gate: "unauthorized minting, burning, duplication, ... of spendable user value across native balances, ... IBC escrows." When the erroneous error-ack path is hit, funds already credited on the destination chain are not clawed back, while the source chain independently re-credits the sender the same amount — creating spendable value out of thin air across the two connected chains, corrupting the global escrow/circulating-supply invariant that IBC's ack semantics are designed to guarantee.

### Likelihood Explanation
The trigger conditions for Case 2 (temporarily disabled send for a denom, a blocked/module receiver, a paused/failing ERC20 `transfer`, or an under-collateralized module ERC20 balance during high transfer volume) are plausible without any privileged access, and the repo's own test suite explicitly demonstrates that error acknowledgements from this exact middleware reliably trigger sender-side refunds while assuming (incorrectly, for this callback) that no destination-side state changes occurred. The main uncertainty is how easily an attacker can force `MintingEnabled`/`ConvertCoinNativeERC20` to fail on demand versus opportunistically (e.g., racing to drain the module's escrowed ERC20 balance) — this would need to be validated with a live reproduction to establish full reliability, but the code path itself is a real design flaw independent of the exact failure trigger.

### Recommendation
In `x/erc20/keeper/ibc_callbacks.go`'s `OnRecvPacket`, never downgrade an already-successful acknowledgement to an error acknowledgement after the wrapped ICS20 transfer app's state changes have committed. Instead, mirror the pattern already used in `OnAcknowledgementPacket`/`ConvertCoinToERC20FromPacket`: catch `MintingEnabled`/`ConvertCoinNativeERC20` failures, emit a failure event, and return the original success `ack` unmodified, leaving the user with the Cosmos-coin representation instead of the ERC20 (to be converted manually later). Apply the same fix to Case 1's `RegisterERC20Extension` failure path.

### Proof of Concept
1. Governance registers/enables a native ERC20 token pair `X` on chain A, and a user converts ERC20 `X` to coin `X` and sends it via IBC to chain B, then back to chain A (or use any scenario producing an ICS20 receive of coin `X` on chain A where `pair.IsNativeERC20()` is true).
2. Before the return packet is received, cause `MintingEnabled` to fail deterministically for the recipient/denom — e.g., have governance (or a race condition) set `IsSendEnabledCoin` to false for denom `X`'s bank send-enabled flag, or ensure the recipient address is on the bank blocked-address list, or drain/starve the module's escrowed ERC20 `X` balance so `ConvertCoinNativeERC20`'s `transfer` call inside `CallEVM` fails.
3. Relay the packet: `im.Module.OnRecvPacket` executes first and successfully un-escrows coin `X` to the recipient's bank balance on chain A (confirmable via `BankKeeper.GetBalance`).
4. `k.OnRecvPacket`'s Case 2 branch then fails at `MintingEnabled`/`ConvertCoinNativeERC20` and returns `channeltypes.NewErrorAcknowledgement(err)`.
5. The relayer delivers this error acknowledgement to chain B, whose `OnAcknowledgementPacket` refunds/re-mints the amount to the original sender there — reproducible by the repo's own `checkRefund`/`TestOnAcknowledgementPacketNativeErc20` assertions of escrowed-balance-zero-and-sender-refunded on error acks: [8](#0-7) 
6. Result: chain A recipient retains the coin `X` credited in step 3, and chain B sender is separately refunded/re-minted the same amount in step 5 — the same value now exists twice across the two chains.

// OnAcknowledgementPacket responds to the success or failure of a packet
// acknowledgement written on the receiving chain. If the acknowledgement was a
// success then nothing occurs. If the acknowledgement failed, then the sender
// is refunded and then the IBC Coins are converted to ERC20.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnAcknowledgementPacket
// still succeeds, but the user receives the corresponding bank token from the
// TokenPair instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}
