### Title
Aggregate Schnorr signature forgery via unbound nonce and public key - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` derives each aggregation weight from only the ordered Schnorr challenges. It never commits the weight for an entry to that entry’s nonce `R` or public key. The first entry is implicitly assigned weight `1`, while later weights come from `weight(&mut digest)`. Because the aggregate prover controls `Rs`, `s`, and the supplied `(key, challenge)` list, an attacker can algebraically cancel a victim’s weighted verification statement into their own nonce commitment and produce a valid aggregate for a signature the victim never made. The weight derivation appends only challenges, and verification applies each weight only after all challenges have been committed. [1](#0-0) 

### Finding Description
For each index `i`, verification checks the aggregate statement

```text
Σ z_i * (R_i + c_i * A_i) - s * G == 0
```

where `A_i` is the public key and `c_i` its challenge. `z_0` is `1` because the first call to `weight` derives the first nonzero pseudorandom weight after the digest contains all challenges; the important flaw is not the first weight specifically, but that no `z_i` binds `R_i` or `A_i`. The digest is initialized with `dst`, domain-separated, and then receives only `challenge` values before weights are generated. [2](#0-1) 

An attacker can therefore choose an aggregate nonce commitment after seeing the public key, challenge, and deterministic weight of every entry. They can place a victim entry in the aggregate and move its entire weighted statement into their own `R` value, without knowing the victim’s private key.

`SchnorrAggregate::read` is directly reachable with attacker-controlled bytes: it reads an attacker-chosen list of canonical group elements and a canonical scalar, with no requirement that the aggregate was produced by `SchnorrAggregator`. [3](#0-2) 

### Impact Explanation
Any verifier accepting a `SchnorrAggregate` as evidence that every listed public key signed its associated challenge can be presented with a forged aggregate containing a victim public key and victim challenge. The victim never produces a signature and does not need to participate.

The forged statement can claim arbitrary signed statements, depending on how the caller computes the supplied challenges. If challenges commit to messages in the normal Schnorr manner, the aggregate can falsely attest that the victim signed a chosen message in an aggregated set. This is signature forgery, not merely aggregate malleability.

### Likelihood Explanation
Exploitation is deterministic whenever the attacker can include an aggregate entry for a key they control alongside a victim entry. The attacker needs:

- their own private/public key pair;
- the victim public key;
- the victim challenge, which is normally public;
- control over the aggregate’s `Rs` and `s`, which is inherent to submitting an aggregate.

No collision, discrete-logarithm solution, malformed encoding, or malicious local signer is required. The attacker controls the relevant boundary values in the same way the archive bug allows an archive entry to escape the destination boundary: here, unbound aggregate components escape the statement they were supposed to prove.

### Recommendation
Bind each aggregation weight to the complete statement being aggregated:

- the public key `A_i`;
- the nonce commitment `R_i`;
- the challenge `c_i`;
- the entry index and/or total entry count.

The aggregator should collect all signatures, append `(index, key, R, challenge)` tuples in a fixed order to the aggregation transcript, and only then derive all weights. Verification must reconstruct that same transcript from the submitted aggregate. A construction equivalent to

```text
z_i = H(dst || "signatures" || count || i || A_i || R_i || c_i)
```

with a single transcript commitment to the full ordered statement list would prevent moving one entry’s statement into another entry’s nonce commitment.

### Proof of Concept
Let the attacker control private key `a`, public key `A_a = aG`, and challenge `c_a`. Let the victim have public key `A_v` and challenge `c_v`. Place the attacker first and the victim second.

The first entry has weight `z_a`; the victim has deterministic weight `z_v`, derived from the challenges. The attacker chooses scalar `r_a` and arbitrary point `R_v`, then computes:

```text
R_a = r_a * G - z_v * (R_v + c_v * A_v)
s   = r_a + c_a * a
```

They submit:

```text
Rs = [R_a, R_v]
s  = r_a + c_a * a
keys_and_challenges = [(A_a, c_a), (A_v, c_v)]
```

The verifier computes:

```text
z_a * (R_a + c_a * A_a)
  + z_v * (R_v + c_v * A_v)
  - s * G
```

If `z_a` is the first weight and equals `1`, substitution gives:

```text
R_a + c_a * A_a
= r_a * G - z_v * (R_v + c_v * A_v) + c_a * a * G
```

Adding the victim’s weighted statement cancels the forged compensation:

```text
z_v * (R_v + c_v * A_v)
- z_v * (R_v + c_v * A_v)
= 0
```

leaving:

```text
r_a * G + c_a * a * G - (r_a + c_a * a) * G = 0
```

Thus `verify` returns true for an aggregate containing the victim’s public key and challenge even though the victim supplied no signature. If the first weight is not literally `1`, the attacker can still choose

```text
R_a = r_a * G - (z_v / z_a) * (R_v + c_v * A_v)
s   = r_a + c_a * a
```

because every weight is known before the attacker chooses `R_a`.
