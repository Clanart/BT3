### Title
Working-directory image diff sink follows attacker-planted symlinks, allowing arbitrary file read outside the repository - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryImage` builds the path to read with a plain `Path.join(repository.path, file.path)` and passes it straight to `fs/promises` `readFile`, without any containment/symlink check. Because Node's `readFile` follows symbolic links by default, a symlink committed inside the repository (git blob mode `120000`) whose target points outside the working tree will be transparently dereferenced, and the target file's bytes are read, base64-encoded, and handed to the renderer for display in `TwoUp`'s `ImageContainer`.

### Finding Description
`getWorkingDirectoryImage` resolves the on-disk path via a simple join and reads it directly: [1](#0-0) 

There is no call to the containment helper `resolveWithin`/`resolveWithinPosix` that the codebase already defines specifically to guard against paths escaping a root via traversal or symlinks (it compares `realpath` of the root vs. the resolved target): [2](#0-1) 

That helper is used elsewhere (e.g. `app/src/ui/dispatcher/dispatcher.ts`, `app/src/lib/stores/app-store.ts`, `app/src/lib/copilot-conflict-context.ts`) for exactly this class of untrusted-path problem, but is not used in `diff.ts`'s image/blob-reading paths.

The sink is reachable from `getImageDiff`, which is invoked from `convertDiff` whenever `git diff` reports a binary change whose extension matches one of the recognized image extensions (`.png`, `.jpg`, `.gif`, etc.): [3](#0-2) [4](#0-3) 

An attacker who controls repository content (a cloned/fetched repo) can commit a symlink blob named e.g. `logo.png` whose link target is an absolute or relative path outside the repo root (e.g. `/etc/passwd`, or a path traversal like `../../../.ssh/id_rsa`). When git checks this out, the OS creates a real symlink on disk. When the victim views this file's diff, `git diff` reports it as a changed/binary path, the `.png` extension routes it into `getImageDiff` → `getWorkingDirectoryImage`, and `fs.readFile` follows the symlink, reading the external target's bytes into the process and rendering them (as base64) for `TwoUp`'s `ImageContainer`.

### Impact Explanation
This allows an attacker-controlled repository to cause GitHub Desktop to read and expose the contents of arbitrary files outside the repository's working tree that are readable by the current OS user (e.g. SSH keys, other project files, config with secrets), satisfying the "file read outside the repo" impact category. The content ends up base64-encoded in application state/props and passed toward rendering, which is a stronger exposure than merely opening a file descriptor.

### Likelihood Explanation
Requires the victim to clone/fetch a repository containing a malicious symlink and then open the diff view for that path (a normal, expected user action when reviewing changes) — no unusual steps beyond viewing a diff of a file with an image extension. Symlinks are a first-class git object type and are trivially committed by any contributor/attacker with push/PR access to a repo the victim will clone.

### Recommendation
Before reading, resolve `file.path` against `repository.path` using the existing `resolveWithinPosix`/`resolveWithin` helper (which performs a `realpath`-based containment check) and reject (or treat as `Unrenderable`/`Binary`) if the resolved real path is not within the repository root. Additionally, consider `lstat`-checking the path and refusing to treat symlinked entries as displayable images. The same fix should be applied to any other direct `Path.join(repository.path, file.path)` + `readFile` calls in `diff.ts` (e.g. `getResolutionDiff`).

### Proof of Concept
1. Create a git repository; add `ln -s /etc/passwd logo.png` (or on the target OS, a symlink named with an image extension pointing to a file outside the repo root, e.g. `../../secret.png`).
2. Commit and have the victim clone the repository in GitHub Desktop.
3. Modify the symlink target file's content externally, or simply have the file show as a change/untracked file so it appears in Changes.
4. Open the diff for `logo.png` in Desktop; `getWorkingDirectoryImage` is invoked with `file.path = "logo.png"`.
5. Observe that `readFile(Path.join(repository.path, "logo.png"))` follows the symlink and returns the contents of the external target file, which get base64-encoded and passed into `TwoUp`'s image container — i.e. content outside the working tree is read and surfaced, rather than the read failing due to containment enforcement.

```typescript
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
```

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
