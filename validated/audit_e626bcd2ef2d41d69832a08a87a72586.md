### Title
Front-runnable instantaneous reward dilution in `vlMGPBaseRewarder._queueNewRewardsWithoutTransfer` allows theft of forfeited yield by newly-locked, non-time-weighted stakers - ([File: rewards/vlMGPBaseRewarder.sol])

### Summary
`vlMGPBaseRewarder` distributes rewards (including forfeited MGP from early-unlock penalties) using a Synthetix-style `rewardPerTokenStored` accumulator that is bumped in a single atomic step and shared pro-rata across the *current* `totalStaked()` balance, with no linear vesting or minimum holding period. An attacker can front-run a known high-forfeiture `unlock()`/`getReward()` transaction by locking MGP (`VLMGP.lock`/`lockFor`, which calls `MasterMagpie.depositVlMGPFor`) immediately before it, thereby diluting the forfeited reward across their own freshly-added balance and claiming a share of yield they did not accrue over time.

### Finding Description
`_queueNewRewardsWithoutTransfer` (called from `_sendReward` and `queueMGP` whenever a forfeiture occurs) updates the global index unconditionally on the current `totalStaked()`: [1](#0-0) 

`totalStaked()` and `balanceOf()` read live values from `VLMGP`/`MasterMagpie`, not time-weighted stake: [2](#0-1) 

A user's earned amount is purely `balance * (rewardPerToken - userRewardPerTokenPaid)`, checkpointed only at the last interaction (`_updateFor`), with no notion of "how long" the balance was held: [3](#0-2) [4](#0-3) 

Exploit flow:
1. Attacker observes a pending high-forfeiture `unlock()`/`getReward()` transaction from a victim in the mempool (forfeiture is computed via `_calExpireForfeit`/`getRewardablePercentWAD` in `VLMGP.sol`, based on early unlock percentage) [5](#0-4) .
2. Attacker front-runs with `VLMGP.lock(amount)`, which calls `_lock` → `MasterMagpie.depositVlMGPFor` and increases `totalAmount` (hence `totalStaked()`), and updates the attacker's `userRewardPerTokenPaid` checkpoint to the *pre-forfeit* `rewardPerTokenStored` value [6](#0-5) .
3. Victim's transaction executes, triggering `_sendReward` → `_queueNewRewardsWithoutTransfer`, which folds the entire forfeited amount into `rewardPerTokenStored` in one atomic step, spread across `totalStaked()` — which now includes the attacker's just-added balance.
4. Attacker immediately calls `getReward`, whose `updateReward` modifier computes `_earned` using the attacker's *current* balance against the stale (pre-bump) checkpoint, yielding a nonzero claimable share despite zero elapsed staking duration [7](#0-6) .

No modifier, cooldown, or vesting schedule prevents this: `lock`/`lockFor` only carry `whenNotPaused`/`nonReentrant`, and there is no minimum stake duration or linear reward streaming to prevent instantaneous, disproportionate reward capture by same-block depositors.

### Impact Explanation
This allows unprivileged attackers to systematically skim a share of every large forfeiture (or any lump-sum `queueNewRewards`/`queueMGP` call) intended for pre-existing long-term lockers, by depositing capital for a single block/transaction. This matches the Immunefi impact class "theft of unclaimed yield" — value that should have accrued to long-term stakers is redirected to a front-runner with zero time-weighted contribution.

### Likelihood Explanation
Feasibility is high on Arbitrum/BNB, where mempool visibility for pending `unlock()`/forfeiture transactions is straightforward, and the required capital is only the MGP amount to lock (which the attacker keeps as `vlMGP`, merely subject to the normal unlock/cooldown mechanics — no burn or transfer of that principal is required to execute the theft). The attack is repeatable against every sizable forfeiture event or admin/manager reward queuing (`queueNewRewards`, `queueMGP`), making it a systemic, recurring drain rather than a one-off edge case.

### Recommendation
Replace the instantaneous lump-sum reward injection with a time-weighted/streaming distribution (e.g., `rewardRate` over a fixed `duration`, as used elsewhere in the codebase for continuous emissions) so that a snapshot of balance at a single block cannot capture a disproportionate share of freshly forfeited rewards. Alternatively, checkpoint eligibility based on a minimum stake duration before a deposit is eligible to share in newly queued rewards, or exclude reward accrual for balance added within the same block as the reward-queuing transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `VLMGP`, `vlMGPBaseRewarder` with a registered reward token (or MGP itself via `queueMGP`).
2. Set up a long-term "victim" locker who locks MGP and lets time pass, accruing standard rewards.
3. Set up victim's pending `startUnlock`/`unlock` (or `getReward` path) that will trigger a large forfeiture via `_calExpireForfeit`.
4. In the same block/transaction ordering: have "attacker" call `VLMGP.lock(amount)` immediately before the victim's forfeiting call executes.
5. Execute victim's forfeiting transaction (bumps `rewardPerTokenStored` via `_queueNewRewardsWithoutTransfer`).
6. Have attacker immediately call `getReward`/`getRewards` via `MasterMagpie`.
7. Assert: `earned(attacker, rewardToken) > 0` and that this amount is proportional to `attacker.balance / totalStaked()` of the forfeited delta, despite attacker having zero elapsed staking time before the forfeiture event — demonstrating a quantifiable, unearned reward claim at the expense of long-term lockers.

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }

    function _updateFor(address _account) internal {
        uint256 length = rewardTokens.length;
        uint256 userVlMGPAmount = balanceOf(_account);

        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;

            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userVlMGPAmount);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
