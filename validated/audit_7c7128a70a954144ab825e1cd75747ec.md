### Title
Unauthenticated `ReceivedOutput` deserialization permits inflated non-spendable Bitcoin deposits - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an independently encoded scalar offset, `TxOut`, and outpoint without proving that the outpoint actually resolves to that `TxOut`. Because `value()` and transaction construction use the supplied `TxOut` while the Bitcoin input spends only the supplied outpoint, an attacker can encode a real Serai outpoint alongside an inflated or mismatched output and have the wallet report funds that cannot actually be spent.

### Finding Description
`ReceivedOutput` is documented as “a spendable output” and stores its spending `offset`, claimed `TxOut`, and claimed `OutPoint` as independent fields. [1](#0-0)  Its public deserializer reads those three values and immediately returns a `ReceivedOutput`, without checking that the outpoint exists or resolves to the encoded value and script. [2](#0-1)  The reported received amount is derived exclusively from the unauthenticated `TxOut`. [3](#0-2) 

`SignableTransaction::new` similarly uses `input.output.value` to calculate available funds, but places only `input.outpoint` in the Bitcoin transaction input. [4](#0-3)  The multisig path verifies that the supplied previous-output script corresponds to the offset key, but it does not verify that this supplied `TxOut` is the output committed by the referenced outpoint. [5](#0-4)  Signing then commits to all supplied `prevouts`, so a mismatch with the real UTXO produces signatures over incorrect input data and a transaction rejected by Bitcoin consensus. [6](#0-5) 

This is analogous to sending one amount through the portal while encoding a different amount in the bridge message: Serai’s accounting and signature preimage use the serialized `TxOut`, while the transaction actually spends only the serialized outpoint.

### Impact Explanation
An attacker who can supply untrusted bytes to `ReceivedOutput::read` can create an object reporting an arbitrary balance for an outpoint that is absent, already spent, controlled by another script, or has a lower value. If the claimed script is Serai-controlled and a real lower-value Serai outpoint is supplied, the object can pass the wallet’s script/key check and proceed through transaction construction and threshold signing, but the resulting Bitcoin transaction is not spendable because Taproot commits to the actual previous-output amount and script. This can cause incorrect received-funds accounting and failed or repeatedly attempted spends.

### Likelihood Explanation
The vulnerability requires an attacker-controlled serialized `ReceivedOutput`, not merely an ordinary Bitcoin transaction. The attack does not require threshold-key compromise, validator collusion, malformed elliptic-curve encodings, or an invalid transaction accepted by Bitcoin; it requires the caller to treat the public deserializer as evidence that the encoded outpoint and `TxOut` are a real spendable pair.

### Recommendation
Do not expose `ReceivedOutput::read` as an authenticated claim of spendability. Require `ReceivedOutput` construction through `Scanner::scan_transaction`, or resolve each outpoint against the Bitcoin chain and require the retrieved `TxOut` to equal the serialized `TxOut` before calling `SignableTransaction::new`. If deserialization is retained for trusted storage, restrict or explicitly name it as unchecked and perform outpoint-to-output validation at the trust boundary.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs
// Conceptual PoC against the public deserializer.

let real_outpoint = OutPoint::new(real_serai_txid, 0);

// This script can correspond to the real outpoint, while the value is inflated.
let fake_txout = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: real_serai_script_pubkey,
};

let mut bytes = Vec::new();
bytes.extend(Scalar::ZERO.to_bytes());
bytes.extend(bitcoin::consensus::encode::serialize(&fake_txout));
bytes.extend(bitcoin::consensus::encode::serialize(&real_outpoint));

let claimed = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// The object reports 100_000 sats even if real_outpoint references 10_000 sats.
assert_eq!(claimed.value(), 100_000);

// Construction and signing use the fake TxOut as the Taproot prevout.
// The resulting transaction spends real_outpoint, whose actual TxOut differs,
// so Bitcoin validation rejects the threshold-signed transaction.
```

  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
