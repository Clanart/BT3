### Title
Forwarded outputs are matched to saved `InInstruction`s by amount alone, letting an unrelated output hijack/strand another depositor's instruction - (File: processor/src/multisigs/mod.rs)

### Summary
The Merit Circle bug is a cross-identity lookup confusion: `increaseLock()` reads deposit parameters under one identity (`msg.sender`) while writing the computed value under a different identity (`_receiver`), because the lookup key and the credit key are not bound together. Serai's multisig scanner exhibits the same shape: when a `Forwarded` output is observed on-chain, the processor associates it with a pending `InInstruction` via `ForwardedOutputDb::take_forwarded_output(txn, output.balance())` — a lookup keyed **only by the output's balance**, not by the outpoint, the originating deposit, or any identity-binding data [1](#0-0) .

### Finding Description
During rotation, external outputs sent to the retiring multisig are forwarded to the new multisig. Because some networks cannot embed arbitrary data in the forwarding transaction, the processor saves the depositor's `InInstruction` locally, keyed by the post-fee amount, and later "re-attaches" it when a `Forwarded`-kind output is scanned [2](#0-1) .

Two consequences follow from keying on `balance` alone:

1. **Attacker-injected output steals the instruction association.** `Forwarded`-kind scripts are just `key + G*FORWARD_OFFSET` P2TR addresses [3](#0-2) . Anyone can compute `forward_address(key)` and send BTC to it — the `Scanner` matches on `script_pubkey` alone and will classify the attacker-controlled UTXO as `OutputType::Forwarded` [4](#0-3) . If the attacker's amount equals (or collides with) the amount stored for a pending forwarded instruction, `take_forwarded_output` consumes that instruction and attributes it to the attacker's output. The instruction's destination/minimums were authored for a different deposit, so attacker funds execute a victim's instruction — and, more importantly, the victim's real forwarded output later arrives to an empty DB entry, is pushed no instruction, and is silently dropped by the `retain(kind == External)` filter [5](#0-4) . The depositor's funds sit in the multisig with no credited instruction — effectively frozen/unaccounted.

2. **Honest collisions.** Two legitimate deposits forwarded in the same rotation with equal post-fee amounts are indistinguishable; `take_forwarded_output` can return instruction A for output B. Since the saved balance was already fee-adjusted [6](#0-5) , equal-amount deposits are plausible, causing instruction/output swaps — each depositor's funds executed under the *other's* parameters (destination addresses, refund origins, swap minimums).

### Impact Explanation
An unprivileged external party (anyone who can send a Bitcoin transaction to a publicly derivable address) can cause a pending depositor's forwarded output to be permanently disassociated from its `InInstruction`, stranding those funds in the multisig, and/or cause instructions to be applied to the wrong output so funds are credited/swapped/refunded according to another user's parameters. This is the same outcome class as the source finding: computation/lookup performed under one entity's record applied to another entity's balance.

### Likelihood Explanation
The forwarding path is exercised on every key rotation for networks without data-carrying forwarding transactions, and the attacker needs only a standard on-chain send — no validator status, no collusion. The amount-keyed DB makes collisions deterministic to engineer (attacker observes the pending forwarding plan amount and matches it). Caveat: I could not fully verify `ForwardedOutputDb`'s key layout (whether it stores a queue keyed purely by amount or includes additional fields), nor whether downstream execution re-validates instruction↔output binding; the read of `take_forwarded_output(txn, output.balance())` strongly indicates amount is the sole key, but the exact storage schema in `db.rs` was not fully reviewed.

### Recommendation
Bind the forwarded instruction to the output's unique identity rather than its amount: key `ForwardedOutputDb` by the expected `OutPoint`/derived forwarding address of the new multisig (or by a one-time nonce offset registered per forward), so only the exact UTXO produced by the forwarding transaction can claim the instruction. At minimum, include the source outpoint or a per-forward index in the key and assert uniqueness on save.

### Proof of Concept
1. Observe rotation: the processor computes `forward_address(new_key) = key + G*FORWARD_OFFSET` [7](#0-6) .
2. Victim's external output is forwarded; processor saves `InInstruction` under `balance = amount - fee` via `save_forwarded_output` [8](#0-7) .
3. Attacker sends `amount - fee` satoshis to the same `forward_address` so it confirms in a block scanned before (or alongside) the real forwarding tx.
4. `scanner_event_to_multisig_event` sees a `Forwarded` output, calls `take_forwarded_output(txn, output.balance())`, gets the victim's instruction, and pushes it to `instructions` bound to the attacker's output [9](#0-8) .
5. The victim's genuine forwarded UTXO arrives later; the DB entry was consumed, no instruction is emitted, and the output is filtered out of `outputs` — its funds are never credited to any instruction.
