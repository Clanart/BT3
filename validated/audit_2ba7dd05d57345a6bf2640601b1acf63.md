### Title
Attacker-controlled `n` drives multi-megabyte preallocation in `ThresholdKeys::read`, enabling memory-exhaustion DoS - (File: crypto/dkg/src/lib.rs)

### Summary
The albatross bug class is "unbounded/unchecked attacker-driven allocation while deserializing untrusted bytes." Serai's analog is in `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`: two attacker-supplied `u16` fields (`t`, `n`) are read from the byte stream, and `n` is immediately used to size `Vec::with_capacity` and a `HashMap` fill loop *before* any semantic validation of the parameters occurs. [1](#0-0) 

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the reader (lines 591-602). It then:

1. If the `interpolation` byte is `0` (`Interpolation::Constant`), executes `Vec::with_capacity(usize::from(n))` for `n` scalars (lines 607-613) — up to 65,535 `C::F` elements (~2-4 MB depending on curve) allocated purely from a 2-byte attacker field.
2. Loops `for l in (1 ..= n)` inserting into a `HashMap` verification-shares map (lines 620-623), each entry requiring a group element read.

Only *after* these allocations does it call `ThresholdParams::new(t, n, i)` (line 626) to validate that `t <= n`, `i <= n`, and `n > 0`. So malformed messages (e.g., `t=0`, `i>n`, duplicate/nonsense params) still cause the full allocation before being rejected.

Unlike `SchnorrAggregate::read` (crypto/schnorr/src/aggregate.rs:77-88), which grows proportionally to bytes actually sent, `ThresholdKeys::read` gives a ~100-200x amplification: ~15 bytes of input (`id_len` + `C::ID` + `t` + `n` + `i` + interpolation tag) triggers ~2-4 MB of committed allocation (the `with_capacity` alone), and the `1..=n` `read_G` loop then consumes attacker-controlled streaming bytes with no total bound, growing the `HashMap` to 65,535 entries. [2](#0-1) 

### Impact Explanation
An unprivileged party who can submit `ThresholdKeys` bytes (e.g., key material payloads routed through processor/coordinator deserialization of `ThresholdKeys::read`) can force repeated ~2-4 MB speculative allocations plus up to 65,535 `HashMap` entries per message, all before any rejection. Sustained submissions exhaust host memory — the same impact class as the albatross advisory (host-level OOM/DoS of the signing component), CVSS-consistent Medium.

### Likelihood Explanation
The path is reachable wherever serialized `ThresholdKeys` are consumed from untrusted input (the audit scope explicitly lists `ThresholdKeys::read` as a public-input entry point). No key knowledge or validator status is needed to trigger the allocation — just bytes claiming a large `n`. The u16 bound caps each message at a few MB, so the attack requires volume rather than a single message, keeping it Medium rather than High.

### Recommendation
Validate parameters before allocating:
- Reorder `ThresholdKeys::read` to construct `ThresholdParams::new(t, n, i)` immediately after reading `t`, `n`, `i`, and reject before any `with_capacity`/loop.
- Cap `n` at a protocol-meaningful bound (e.g., `MAX_KEY_SHARES_PER_SET`) before sizing containers.
- Avoid `Vec::with_capacity(n)`/`HashMap` pre-sizing based on unvalidated input; grow incrementally as bytes are actually consumed.

### Proof of Concept
Construct a serialized `ThresholdKeys` buffer: `C::ID.len()` as u32-LE, `C::ID` bytes, `t = 0xFFFF`, `n = 0xFFFF`, `i = 0xFFFF`, interpolation byte `0`, followed by a stream of canonical scalars/points. `ThresholdKeys::read` allocates `Vec::with_capacity(65535)` for scalars and begins filling a 65,535-entry `HashMap` — only failing `ThresholdParams::new` (t cannot exceed n's valid range / i=0xFFFF is invalid) at the end. Each ~dozen-byte prefix yields megabytes of allocation; looping this exhausts memory.
