### Title
Shared `BalanceHandler` instance across recursive/nested precompile calls corrupts EVM StateDB balance vs. x/bank ground truth — ([File: precompiles/common/balance_handler.go])

### Summary
The ENS finding hinges on a state-tracking invariant ("is this node currently wrapped?") that is checked once and then silently invalidated by a second, overlapping code path (the legacy `.eth` registrar) operating on the same underlying resource, letting an attacker desynchronize the "wrapped" bookkeeping from the true ownership state. The Cosmos EVM analog is the `BalanceHandler` used by native precompiles (staking, distribution, gov, ics20, erc20, slashing): it tracks a single mutable index (`prevEventsLen`) into `ctx.EventManager().Events()` to know which bank events to translate into `StateDB.AddBalance`/`SubBalance` calls. When precompile calls nest or recurse within the same EVM call frame, the shared handler's `prevEventsLen` is overwritten by the inner call before the outer call's `AfterBalanceChange` runs, causing the wrong slice of bank events to be replayed into the StateDB — the same mismatch-between-two-parallel-accounting-systems pattern as the ENS bug.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records the current length of the SDK event log: [1](#0-0) 

`AfterBalanceChange` then replays every bank event emitted since that recorded index, translating `EventTypeCoinSpent`/`EventTypeCoinReceived`/`EventTypeFractionalBalanceChange` into `StateDB.SubBalance`/`AddBalance` calls so that the EVM's balance view matches the true `x/bank` balance changes performed by the precompile's Cosmos-side logic: [2](#0-1) 

Crucially, `prevEventsLen` is a single mutable field on the `BalanceHandler` struct, and each precompile (`staking`, `distribution`, `gov`, `ics20`, `erc20`, `slashing`) obtains and reuses this handler via `GetBalanceHandler()` on the shared `Precompile` struct: [3](#0-2) 

The precompile `Run` flow (illustrated in the debug precompile, which mirrors the real precompile implementations) calls `BeforeBalanceChange` right before executing the method and `AfterBalanceChange` right after: [4](#0-3) 

If, during `p.Execute(...)`, the precompile call recursively triggers another call into the *same* precompile instance (e.g., a contract callback invoked mid-execution that re-enters the precompile, or a nested precompile-to-precompile call as exercised by the ICS-20 recursive-call test), the inner invocation's `BeforeBalanceChange` overwrites `prevEventsLen` with a later index. When the outer call's `AfterBalanceChange` subsequently runs, it uses this now-stale/incorrect index, so it either:
- re-processes events that the inner call already applied to the StateDB (double-counting a balance credit — i.e., duplicating spendable EVM-side value without a matching increase in the actual bank balance), or
- skips events that should have been applied to the StateDB for the outer call (silently losing a balance credit/debit, desynchronizing StateDB from x/bank).

This exact mechanism and its consequence — "balance desync between native bank keeper and EVM stateDB" from "recursive precompile calls shar[ing] the same BalanceHandler instance, causing prevEventsLen to be overwritten" — is explicitly documented by the project's own test suite: [5](#0-4) [6](#0-5) 

This is structurally the same bug class as [H-02]: two systems that are supposed to stay 1:1 (NameWrapper state vs. ENS registry ownership; x/bank ledger vs. EVM StateDB balance) are kept in sync by an implicit "diff since last checkpoint" mechanism, and a reachable, unprivileged code path (registrar re-registration in ENS; nested/recursive precompile invocation here) can cause that checkpoint to be silently invalidated, producing a permanent accounting divergence that an attacker can exploit for value extraction rather than a benign one-off inconsistency.

### Impact Explanation
If an attacker can construct a contract/precompile call sequence that triggers nested execution through the same `BalanceHandler` (e.g. a contract that calls a precompile, which during its execution causes reentry into a precompile method — such as ICS-20 send/receive triggering a callback that itself invokes a precompile, or staking/distribution/gov precompiles invoked recursively from a malicious contract), the resulting StateDB balance can be inflated relative to the true bank balance. Since the EVM StateDB balance is what is read/spent by subsequent `CALL`/`transfer`/`SELFDESTRUCT` operations within the same or later transactions, an inflated StateDB balance is directly spendable EVM value that is not backed by real bank coins — this is a duplication of spendable user value, matching the Critical "unauthorized minting/duplication/irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets" impact category. Conversely, an attacker (or ordinary user) could also trigger the "skipped event" variant, permanently locking funds whose bank-side debit is not reflected as a StateDB credit for the receiver, matching the "permanent freezing/locking of user funds" impact category.

### Likelihood Explanation
The bug is triggered purely through the ordinary EVM call semantics available to any unprivileged user — no validator, relayer, or governance privilege is required. The project's own test suite (`evmd/tests/integration/balance_handler/balance_handler_test.go`, `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go`) was written specifically to reproduce and demonstrate this scenario using a debug precompile and recursive ICS-20 precompile calls, indicating the recursion/nesting path is reachable in production precompiles (staking, distribution, gov, ics20, erc20, slashing all share the same `GetBalanceHandler()` mechanism). Whether this has already been fully remediated in the current tree could not be confirmed with certainty — I was unable to retrieve `precompiles/common/precompile.go` in full (tool call failed on the final iteration) to verify whether `GetBalanceHandler()` now creates a fresh handler per call (via the `BalanceHandlerFactory.NewBalanceHandler()` seen in the code) rather than reusing a single shared instance across nested calls. This is the key open question for confirming exploitability in the current state of the code.

### Recommendation
Verify (and if not already so, enforce) that every precompile call — including nested/recursive ones — obtains a **fresh** `BalanceHandler` instance from `BalanceHandlerFactory.NewBalanceHandler()` rather than reusing one attached to the precompile object across the call stack, so `prevEventsLen` cannot be clobbered by an inner call. Alternatively, make the handler reentrancy-safe by using a stack (push/pop) of checkpoints instead of a single scalar, and add an invariant check that total `StateDB` balance deltas applied via `AfterBalanceChange` always equal the sum of the underlying `x/bank`/`x/precisebank` events for that call's exact event range, failing loudly (reverting the call) rather than silently mis-processing events on any detected overlap or gap.

### Proof of Concept
The repository already contains a reproducing test that is the direct analog of the ENS PoC (a scripted sequence exploiting the shared/implicit state-tracking mechanism): [7](#0-6) 
which deploys a caller contract that recursively invokes the debug precompile (`callback`) and asserts on the resulting event/balance counts to demonstrate the `prevEventsLen`-overwrite condition; and the ICS-20 recursive-precompile-call suite reproduces the same class of issue against real production precompiles: [8](#0-7)

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
