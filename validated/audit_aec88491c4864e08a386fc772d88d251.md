### Title
Permissionless ERC20 registration lets an attacker mint unbacked native coins via a self-referential balance check - (File: `x/erc20/keeper/msg_server.go`, `x/erc20/keeper/proposals.go`)

### Summary
`x/erc20` allows **any account, without any privileged check, to register an arbitrary contract as an ERC20 token pair** (`MsgRegisterERC20` → `Keeper.registerERC20`), exactly like the SAM `create()` bug allowed anyone to register an untrusted contract as a trusted "edition." Once registered, `ConvertERC20` mints real Cosmos-SDK bank coins based on a balance-invariance check that queries `balanceOf()` **on the very same attacker-controlled contract that performed the "transfer."** Because the contract fully controls both `transfer()` and `balanceOf()`, it can implement a fabricated internal ledger that always satisfies the module's own invariant, letting the attacker mint unlimited native coins of the token-pair denom with zero real backing.

### Finding Description
`RegisterERC20` explicitly documents that "Any account can permissionlessly register a native ERC20 contract to map to a Cosmos Coin": [1](#0-0) 

The actual pair creation performs no validation of contract behavior beyond reading its self-reported name/symbol/decimals via `QueryERC20`: [2](#0-1) [3](#0-2) 

When a user later calls `ConvertERC20` for a native ERC20 pair, the keeper:
1. Reads `balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)` (before),
2. Calls `contract.transfer(ModuleAddress, amount)`,
3. Re-reads `balanceTokenAfter := k.BalanceOf(...)` (after),
4. Requires `balanceTokenAfter == balanceToken + amount`,
5. If satisfied, **mints real bank coins** (`k.bankKeeper.MintCoins`) and sends them to the receiver. [4](#0-3) 

The entire "invariant" is self-referential: `balanceOf` and `transfer` are both functions on the attacker's own contract. The test suite only exercises contracts that (a) skim value away via real internal transfers (`ERC20DirectBalanceManipulation`, which correctly fails the invariant because it uses real inherited OZ storage) or (b) plant a hidden allowance as a side effect (`ERC20MaliciousDelayed`, which passes because balances are otherwise correct): [5](#0-4) [6](#0-5) 

Neither test contract overrides `balanceOf()` itself. A genuinely malicious contract does not need to inherit any real ERC20 ledger at all — it can implement `transfer()` to simply increment an internal counter and `balanceOf()` to return that same counter, with no real value ever moving. This makes the check in step 4 trivially satisfiable for any `amount`, since the "before/after" values are entirely fabricated by the contract the attacker deployed and registered themselves.

This is the direct structural analog of the SAM bug: `create()`'s `onlyEditionOwnerOrAdmin`/`onlyBeforeMintConcluded` checks derived their truth from calling into the attacker's own contract; here, the mint-authorization check (`balanceTokenAfter == balanceToken + amount`) derives its truth from calling `balanceOf`/`transfer` on the attacker's own contract. In both cases, a value that is supposed to represent an independently verifiable state is instead supplied by the untrusted party itself.

### Impact Explanation
Successful exploitation lets the attacker mint arbitrary amounts of a real bank-module coin (`erc20:0x<attackerContract>`) with zero backing ERC20 tokens ever escrowed. Because this is an ordinary native Cosmos coin once minted, it is indistinguishable from any other coin to the rest of the chain: it can be transferred via `x/ibc-transfer`, escrowed and sent out over IBC (`x/ibc/transfer/keeper/msg_server.go`), causing the counterparty chain to mint corresponding IBC vouchers that are redeemable/tradeable as if backed by real value. This is unauthorized minting / irreversible accounting corruption of spendable value, matching the Critical impact gate ("unauthorized minting… of spendable user value across native balances… IBC escrows"). [7](#0-6) 

### Likelihood Explanation
- `RegisterERC20` is designed to be permissionless (`params.PermissionlessRegistration`), and the keeper code path and integration tests both exercise a non-governance signer succeeding when this flag is true, indicating the feature is meant to be usable without any privileged approval in typical deployments.
- Deploying and registering a malicious contract, then calling `MsgConvertERC20`, requires only ordinary, unprivileged transactions — no validator, relayer, or governance collusion needed.
- The only barrier is chain operators explicitly disabling `PermissionlessRegistration` via governance; I could not fully confirm the default value of this parameter from the available index (uncertain), so likelihood is contingent on this configuration remaining enabled, which appears to be the module's intended default use case based on the code comments and permissionless test cases.

### Recommendation
Do not treat a self-registered, arbitrary contract's own `balanceOf`/`transfer` return values as a sufficient authorization for minting native coins. Options:
- Require the escrow balance check to be validated against an independently trusted source (e.g., verify via `Transfer` event emitted correctly by codehash-verified, allow-listed bytecode, similar to `RegisterERC20CodeHash`/`Erc20Bytecode` used for dynamic IBC precompiles), rather than trusting the registered contract's self-reported balance.
- Alternatively, gate `ConvertERC20`/minting so that it only applies to contracts registered through a trusted path (governance-approved list or the canonical `ERC20MinterBurnerDecimalsContract` bytecode deployed by the module itself), removing reliance on permissionless third-party bytecode for value-creating operations.
- Add fuzzing/audit-style test contracts with a fully fabricated `balanceOf` (no OZ inheritance) to the existing malicious-contract test suite, since current coverage (`ERC20DirectBalanceManipulation`, `ERC20MaliciousDelayed`) does not exercise this exact pattern.

### Proof of Concept
Conceptual Solidity contract and flow (concrete PoC could not be executed against a live node from the index, but the logic is directly traceable in the cited keeper code):
```solidity
contract FakeLedgerERC20 {
    mapping(address => uint256) public balanceOf;
    string public name = "Fake"; string public symbol = "FAKE"; uint8 public decimals = 18;
    event Transfer(address indexed from, address indexed to, uint256 value);

    function transfer(address to, uint256 amount) external returns (bool) {
        balanceOf[to] += amount; // no real value moved, no `from` balance check
        emit Transfer(msg.sender, to, amount);
        return true;
    }
}
```
1. Attacker deploys `FakeLedgerERC20` and calls `MsgRegisterERC20` (permissionless) to create a token pair for it — analogous to SAM's `create()` with an untrusted contract.
2. Attacker calls `MsgConvertERC20{ContractAddress: FakeLedgerERC20, Amount: 1_000_000, ...}`.
3. `convertERC20IntoCoinsForNativeToken` calls `FakeLedgerERC20.transfer(ModuleAddress, 1_000_000)`, which just sets `balanceOf[ModuleAddress] += 1_000_000` and emits a matching `Transfer` event.
4. The invariant check `balanceTokenAfter == balanceToken + amount` passes trivially because `balanceOf` reads the same fabricated storage that `transfer` just wrote.
5. `k.bankKeeper.MintCoins` mints `1_000_000 erc20:0x<FakeLedgerERC20>` real bank coins to the attacker, with no real ERC20 value ever backing them.
6. Attacker can then move these coins over IBC (`MsgTransfer`) to mint corresponding vouchers on another chain. [8](#0-7) [9](#0-8)

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
