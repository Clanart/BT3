### Title
Spoofable GitHub-host fingerprint (`x-github-request-id` header check) lets an attacker-controlled git remote get classified and trusted as a GitHub Enterprise endpoint, triggering unauthorized sign-in/account binding - ([File: app/src/lib/api.ts])

### Summary
`isGitHubHost()` in `app/src/lib/api.ts` decides whether an arbitrary, previously-unknown git remote is a "GitHub" host purely by sending an HTTP `HEAD` request to `${endpoint}/meta` and checking for the presence of the `x-github-request-id` response header [1](#0-0) . This header is entirely attacker-controlled since it is just an arbitrary HTTP response header that any server (including a malicious git remote's web/proxy endpoint) can emit. This mirrors the root cause pattern in the source report: code assumes a specific "interface" contract (here, "only real GitHub servers send this header") without verifying it against the actual, potentially adversarial, implementation it is talking to.

### Finding Description
The credential trampoline (`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts`) calls `isGitHubHost(endpoint)` as the last-resort check when Git asks Desktop for credentials for an unrecognized HTTPS remote [2](#0-1) . If `isGitHubHost` returns `true`, the endpoint is classified as `'enterprise'` rather than `'generic'`.

That classification feeds directly into `getCredential()`: when the endpoint is not `'generic'` and no existing account matches, Desktop automatically pops the GitHub sign-in UI for that endpoint via `ui.promptForGitHubSignIn(endpoint)` [3](#0-2) . This is triggered purely by Git needing credentials for a remote — i.e., simply adding/cloning/fetching a repository whose remote points at the attacker's server is enough to reach this code path; no unnatural user action beyond a normal clone/fetch is required.

Because `isGitHubHost`'s only network-observable signal is a spoofable header, an attacker who controls the git remote/proxy target can trivially set `x-github-request-id` on the `/meta` response to make their arbitrary host masquerade as a GitHub Enterprise server, even though it is not one. Existing guards do not stop this:
- The check explicitly `omit`s credentials and aborts on redirect [4](#0-3) , which prevents a *different* class of leak, but does nothing to validate the authenticity of the header itself.
- There is no cryptographic or well-known-endpoint verification (e.g. checking a real GitHub API shape, TLS certificate chain to a known provider, or GraphQL schema) — the check is a single free-form header string.
- `knownThirdPartyHosts`/hostname heuristics only reject some well-known non-GitHub SaaS domains; any other hostname (e.g. attacker's own domain) falls through to the spoofable network check [5](#0-4) .

### Impact Explanation
Once misclassified, Desktop's own trusted "Sign in" UI is presented to the user for an endpoint that is not actually GitHub/GHE. This directly satisfies "unauthorized OAuth or account binding": the user is invited, in-band, during normal Desktop workflows, to authenticate against an attacker-controlled endpoint. Any credentials/PAT entered are sent straight to the attacker's server as part of Desktop's own sign-in/validation flow, and (in the OAuth case) the bundled `login/oauth/access_token` exchange (`requestOAuthToken` in `app/src/lib/api.ts`) is directed at the attacker-supplied `getHTMLURL(endpoint)` base, since that endpoint is derived entirely from the attacker's own host string. This is a credential-exfiltration / unauthorized-account-binding primitive reachable purely by having the victim clone or fetch from an attacker-hosted repository.

### Likelihood Explanation
Any repository with a remote pointing at attacker infrastructure (a proxy, self-hosted git server, or malicious "self-hosted CI mirror") reaches this code the moment Git needs credentials for a fetch/push/clone, which is a very common and expected trigger — no special user behavior beyond normal repository use is needed to reach the misclassification. The remaining step (user completing the sign-in prompt) is the same trusted UI flow Desktop shows for legitimate GHE onboarding, making it plausible users will proceed.

### Recommendation
Do not use a spoofable response header as the sole signal that a remote is a genuine GitHub/GHE instance. Require verification of an authenticated, hard-to-forge signal (e.g., validated TLS certificate transparency/pinning to known GitHub infrastructure is not feasible for GHE, but at minimum corroborate with multiple independent GitHub-specific API behaviors, e.g., a full `/meta` JSON payload with expected schema plus `x-github-enterprise-version`, rather than a single arbitrary header), and/or require explicit user confirmation with the literal hostname displayed before treating an unknown host as an enterprise GitHub endpoint and before allowing that endpoint to receive OAuth `client_id`/`client_secret` or PAT validation requests.

### Proof of Concept
1. Stand up an HTTP server at `https://attacker.example.com` that responds to `HEAD /meta?ghd=*` with status 200 and header `x-github-request-id: spoofed`.
2. Create/host a git repository with a remote `https://attacker.example.com/foo/bar.git` and have the victim clone/fetch it in GitHub Desktop.
3. Git invokes Desktop's credential trampoline; `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts` finds no matching account/wwwauth realm and falls through to `isGitHubHost('https://attacker.example.com')` in `app/src/lib/api.ts`, which returns `true` due to the spoofed header.
4. Desktop classifies the endpoint as `'enterprise'` and, finding no existing account, automatically shows the GitHub Enterprise sign-in prompt for `attacker.example.com`.
5. If the user proceeds with sign-in (PAT or OAuth), their credentials/token or the OAuth code-exchange request is sent to the attacker-controlled server.
