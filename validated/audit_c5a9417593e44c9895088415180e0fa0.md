### Title
Funds sent to a multisig address before its activation block are permanently ignored by the Scanner and become unspendable - (File: processor/src/multisigs/scanner.rs)

### Summary
Analogous to the Morpho "isolation mode" report — where an unprivileged party can force a shared contract position into a permanently restricted state by being the first/unsolicited sender — Serai's UTXO scanner has a permanent dead-zone: outputs paying to a multisig key's addresses in blocks before that key's `activation_number` are never reported, never enter the `Scheduler`'s UTXO set, and can never be signed for, despite sitting at an address whose key Serai controls.

### Finding Description
`Scanner::run` iterates blocks strictly forward from `ram_scanned + 1` (`processor/src/multisigs/scanner.rs:492`). For each block it iterates `scanner.keys` — a `Vec<(usize, G)>` of `(activation_number, key)` pairs — and skips any key whose activation block hasn't been reached yet:

```rust
for (activation_number, key) in scanner.keys.clone() {
  if activation_number > block_being_scanned {
    continue;
  }
  ...
  for output in network.get_outputs(&block, key).await { ... }
}
```
(`processor/src/multisigs/scanner.rs:550-567`)

Once `block_being_scanned` advances past a block, that block is never re-scanned (`ram_scanned` only moves forward, `scanner.rs:722`). Therefore a Bitcoin transaction paying to `p2tr_script_buf(key)` (or the branch/change/forward scripts — all deterministically derived from `key` via fixed `hash_to_F` offsets, `processor/src/networks/bitcoin.rs:308-346`) in any block `< activation_number` produces an output that:

- is matched by `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`), but is filtered out by the activation gate,
- is never emitted as a `ScannerEvent::Block` output, never passed to `Scheduler::add_outputs` (`processor/src/multisigs/scheduler/utxo.rs:266-300`), and never enters `self.utxos`,
- remains forever spendable only by Serai's threshold key, which has no record of it — no code path ever re-derives it.

The next key's group key (hence its external P2TR address) is publicly knowable before activation: multisig sets are decided on-chain in advance of their activation block, and rotation plans (`forward_plan`, `utxo.rs:621-630`) reference the incoming key. An attacker (or an unknowing early depositor — the same "unknowing user" vector as in the Morpho report) can broadcast a deposit in the window between key publication and activation.

### Impact Explanation
Permanent loss of funds: BTC is confirmed on-chain to an address only the Serai multisig can spend, yet the scheduler has no knowledge of the output. No refund, no recovery path, no event emitted. The depositor is never credited. This is the same shape as the report's accepted impact ("funds reported received that are not spendable") inverted: funds actually received that can never be spent by the system. It also applies to Change/Branch/Forward outputs sent early to a not-yet-active key.

### Likelihood Explanation
Medium. Requires only a normal public Bitcoin transaction — no validator collusion, no malformed bytes, no timing race. The pre-activation window is a protocol-observable period (rotation is scheduled on-chain ahead of the activation block), so any unprivileged observer of Serai's chain state can compute `external_address(key)` from the group key and front-run activation. An unknowing user with a stale/cached address can trigger it accidentally.

### Recommendation
When a key is registered, scan from `min(activation_number, earliest relevant block)` — i.e., scan the key across all already-scanned blocks back to when the key could first have been publicly derived, or emit outputs found before activation rather than gating `get_outputs` on `activation_number > block_being_scanned`. Alternatively, document and enforce that the network's reported outputs must cover pre-activation blocks (e.g., pass a per-key start block into `get_outputs`/`scan_transaction`).

### Proof of Concept
1. Multisig set rotation is decided on-chain; the new group key `K` and its activation block `A` are public.
2. Attacker computes `addr = p2tr_script_buf(K)` (external address) and sends a transaction paying `addr`, confirmed in block `A-1` (or any block `< A` that the scanner already passed or will skip).
3. In `Scanner::run`, for blocks `< A`, the loop hits `if activation_number > block_being_scanned { continue; }` and never calls `network.get_outputs(&block, K)` for that key (`processor/src/multisigs/scanner.rs:550-556`).
4. When `block_being_scanned` reaches `A`, only block `A` onward is scanned for `K`; block `A-1` is never revisited (`ram_scanned` is monotonic, `scanner.rs:722`).
5. The attacker's UTXO never appears in any `ScannerEvent::Block` outputs, never reaches `Scheduler::utxos`, and is permanently unspendable despite being controlled by Serai's threshold key.

Note: scope limitations — `processor/` is not in the listed in-scope crates (`networks/bitcoin/src` is); the root cause spans `processor/src/multisigs/scanner.rs` and the `Scanner`/`register_offset` semantics in `networks/bitcoin/src/wallet/mod.rs`. If the audit scope strictly excludes `processor/`, this analog should be downgraded or re-evaluated; the in-scope `Scanner::scan_block`/`scan_transaction` primitives themselves behave as documented and merely enable the gap.
