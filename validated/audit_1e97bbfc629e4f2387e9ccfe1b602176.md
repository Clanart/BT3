### Title
Unauthenticated payout OP_RETURN lets an attacker misattribute a payout to an operator who never funded it, triggering false self-reimbursement - (File: core/src/verifier.rs, core/src/task/payout_checker.rs)

### Summary
The payout tx's OP_RETURN (`operator_xonly_pk`) is not covered by the withdrawer's `TapSighashType::SinglePlusAnyoneCanPay` signature, so anyone who can construct or race a payout transaction for a given withdrawal UTXO can freely set the OP_RETURN to any operator's pubkey while keeping the (unchanged) signed input/output valid. `update_finalized_payouts` blindly records whatever pubkey is parsed from the confirmed tx's OP_RETURN as the "payer", and `PayoutCheckerTask`/`get_first_unhandled_payout_by_operator_xonly_pk` blindly trusts this DB column to automatically trigger `handle_finalized_payout`, causing an operator to claim reimbursement for a payout it never actually funded.

### Finding Description
The broken binding is: `withdrawals.payout_payer_operator_xonly_pk == the xonly_pk of the operator whose own funds paid the withdrawal output`. In reality the equality only checks `withdrawals.payout_payer_operator_xonly_pk == whatever bytes appear in the confirmed payout tx's OP_RETURN output`, which is unauthenticated.

- `create_payout_txhandler` places the "fronting operator" pubkey in an OP_RETURN output (index 2) that is separate from the signed input/output [3](#0-2) .
- The withdrawer's signature is checked with `calculate_sighash_txin(0, in_signature.sighash_type)` and enforced to be `SinglePlusAnyoneCanPay` [2](#0-1) [4](#0-3) . This sighash type commits only to input 0 and the single output at index 0 (the user payout) — the anchor output and OP_RETURN are excluded from the signed message.
- Consequently, anyone who obtains a validly signed payout tx (e.g., the raw tx returned by `Withdraw`/`InternalWithdraw` RPCs, or observed in mempool) can rebuild an alternate transaction with the same input/output[0] and a different OP_RETURN (any operator's xonly_pk) and a different/attacker-funded anchor input, and race it onto the chain (it double-spends the same withdrawal UTXO, so only one version confirms).
- `update_finalized_payouts` parses whichever version confirms and writes its OP_RETURN pubkey into `withdrawals.payout_payer_operator_xonly_pk` with no check that this pubkey corresponds to the actual funder [5](#0-4) .
- `PayoutCheckerTask::run_once` and `get_first_unhandled_payout_by_operator_xonly_pk` then automatically pick up this row for the victim operator, purely by pubkey match, with zero verification that the victim operator itself broadcast or funded this specific payout txid [6](#0-5) [7](#0-6) .
- `handle_finalized_payout` then automatically builds and submits a kickoff for that deposit under the victim's own key [8](#0-7) , and because `is_kickoff_malicious` only compares `operator_xonly_pk` (from the manipulated OP_RETURN) to `kickoff_data.operator_xonly_pk` (also the victim, since the victim signed its own kickoff), the check "matches" and verifiers do not challenge it [9](#0-8) .
- The lookup key for both `is_kickoff_malicious` and the automatic payout-checker path is `move_to_vault_txid`, which is deterministic per deposit [10](#0-9)  and stored 1:1 with the withdrawal's Citrea index [11](#0-10) . This means the misattribution can only affect the specific deposit/withdrawal whose UTXO the attacker races, not an unrelated "different deposit" as hypothesized in the question — that specific premise (cross-deposit attribution) does not hold, because `get_payout_info_from_move_txid`/`get_first_unhandled_payout_by_operator_xonly_pk` are scoped strictly per move_txid/deposit row.

### Impact Explanation
Within the same deposit/withdrawal, an attacker can cause the deposit's move-to-vault BTC to reimburse an operator ("V") who never actually funded the withdrawal, while the real economic funder was the attacker (who paid the user output via the raced transaction) or nobody (if the honest operator's own transaction was pre-empted before it confirmed). This matches the Critical category "an operator reimbursed for a payout it never funded." It does not, however, make an honest operator's own **correctly-attributed** kickoff for a different, unrelated deposit challengeable — that specific cross-deposit escalation asserted in the question is not supported by the code, since attribution and challenge-checking are both scoped per move_txid/deposit. The attack is repeatable per withdrawal that the attacker can race (requires winning a double-spend race against the legitimate funder's broadcast/confirmation), and its practical value to the attacker is limited: it does not let the attacker steal funds for themselves (they cannot forge a kickoff for the victim without the victim's private key), and it primarily forces victim operator V to unknowingly consume one of its round/kickoff slots and receive a windfall reimbursement rather than lose funds. It can be used to grief an operator by forcing them into unintended reimbursement claims that consume limited per-round kickoff capacity, potentially denying that operator's ability to service a real withdrawal in the same round.

### Likelihood Explanation
Exploitation requires the attacker to win a mempool race (or RBF/fee-bump) against the legitimate funder's broadcast of the same withdrawal UTXO before it confirms, and to have their own funds available to bear the fee/anchor cost of the alternate transaction. This is feasible for a technically capable attacker but non-trivial to time reliably, and does not by itself yield direct profit to the attacker — it is primarily a griefing/misattribution vector rather than a fund-theft vector, which affects the assessed severity of real-world likelihood.

### Recommendation
Bind the attribution to an authenticated source instead of an unauthenticated OP_RETURN: either (a) have the withdrawer's signature use `All`/cover the full output set (including OP_RETURN) so it cannot be altered post-signature, or (b) have each operator record its own outgoing payout txid locally at withdrawal-broadcast time and require `PayoutCheckerTask`/`handle_finalized_payout` to match the confirmed payout txid against that local record before treating it as "its own" payout, rather than trusting the OP_RETURN pubkey alone.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
