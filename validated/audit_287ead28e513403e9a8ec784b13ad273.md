### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` keys enables stack-overflow DoS via a crafted `TxTypeAccountUpdate`/`TxTypeAccountCreation` transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each of its member keys as a full `AccountKeySerializer`, and `AccountKeySerializer.DecodeRLP` dispatches back into `NewAccountKey`/`s.Decode` based on an attacker-controlled type byte [1](#0-0) . Because a member key can itself be `AccountKeyTypeRoleBased`, this decode path recurses into itself with no depth limit, and the composite-type rejection (`ErrNestedCompositeType`) is only enforced later during `CheckInstallable`/`CheckUpdatable`, after decoding has already completed [2](#0-1) . This mirrors the CVE-2020-36375 bug class: a recursive-descent decoder/parser with attacker-controlled nesting depth and no recursion guard, leading to native stack overflow (process crash / DoS), except here the "input" is the RLP-encoded `key` field of a standard Kaia transaction, which is reachable by any unprivileged transaction sender.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` reads a list of byte strings and, for each element, calls `rlp.DecodeBytes(b, &serializer)` into a fresh `AccountKeySerializer`: [3](#0-2) 

`AccountKeySerializer.DecodeRLP` reads a `keyType` byte, calls `NewAccountKey(keyType)` to construct the correct key implementation, and then decodes into it: [1](#0-0) 

`NewAccountKey` allows `AccountKeyTypeRoleBased` to be constructed again for any nested key entry: [4](#0-3) 

If the decoded key type is again `AccountKeyTypeRoleBased`, decoding recurses back into `AccountKeyRoleBased.DecodeRLP`. This chain (`AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `NewAccountKey` → `AccountKeyRoleBased.DecodeRLP` → ...) has **no depth counter or limit**. The only safeguard against nested composite keys — `IsCompositeType()` check producing `kerrors.ErrNestedCompositeType` — runs in `CheckInstallable`/`CheckUpdatable`, which execute *after* the entire nested structure has already been fully decoded via reflection/recursive calls [2](#0-1) .

This decode path is invoked for any transaction that carries an account key field, e.g. `TxInternalDataAccountUpdate.UnmarshalJSON`/`DecodeRLP` and `TxInternalDataAccountCreation.UnmarshalJSON`, both of which call `rlp.DecodeBytes(js.Key, ser)` on attacker-supplied key bytes before any semantic validation occurs [5](#0-4) [6](#0-5) . The same RLP-based path is also reachable directly from a public RPC endpoint, `KaiaAPI.DecodeAccountKey`, which decodes arbitrary attacker-supplied bytes with no depth restriction: [7](#0-6) .

An attacker can craft a `key` byte-string that nests `AccountKeyRoleBased` inside `AccountKeyRoleBased` inside `AccountKeyRoleBased`... many thousands of times. Decoding this structure (either during tx-pool ingestion of an `AccountUpdate`/`AccountCreation`/fee-delegated variant transaction, or via the public `kaia_decodeAccountKey` RPC call) drives unbounded Go-runtime stack growth through recursive function calls, which can exhaust the goroutine stack and crash the node process (Go runtime `fatal error: stack overflow`, which is unrecoverable via panic/recover).

### Impact Explanation
A successful attack causes denial of service: the node process handling the malicious transaction or RPC call crashes with a fatal, unrecoverable Go runtime stack-overflow error. If triggered during transaction-pool validation/block-processing (via a submitted `AccountUpdate`/`AccountCreation`/fee-delegated-account-update transaction), it can crash any full node or validator that processes/validates the transaction, which is a network-wide availability impact and can also cause honest nodes to diverge if only some nodes crash while processing the same block/tx. This satisfies the "Medium and above" bar (matches CVSS AV:L/AC:L/PR:N/UI:R/... /A:H in the underlying CVE, translated to a network-reachable transaction/RPC context here).

### Likelihood Explanation
Likelihood is high for the RPC-triggered path (`KaiaAPI.DecodeAccountKey`) since it requires only a single crafted byte string sent to a public JSON-RPC endpoint, no fee, no special privilege, and no valid signature. For the transaction path, the attacker must construct a valid RLP-encoded transaction with a maliciously nested `key` field; while the resulting transaction would ultimately fail `CheckInstallable`/signature validation, the stack overflow occurs during the RLP decode step, which happens before those checks, so the crash occurs regardless of whether the transaction is otherwise valid. Achievable nesting depth is bounded by transaction/RPC payload size limits, but Go's default stack overflow threshold (up to the 1GB max stack per goroutine before the runtime aborts) is reachable with a nesting depth on the order of tens of thousands of levels; whether the maximum permitted RLP/transaction size is sufficient to encode that many levels was not fully confirmed in this review (see below) and would need to be validated experimentally.

### Recommendation
- Add and enforce a strict maximum nesting/recursion depth for `AccountKeySerializer`/`AccountKeyRoleBased` decoding (both `DecodeRLP` and `UnmarshalJSON` paths), rejecting any input where nested `AccountKeyTypeRoleBased` values appear (composite-in-composite), by checking `IsCompositeType()` *during* decode rather than only in the later `CheckInstallable`/`CheckUpdatable` calls.
- Apply the same depth/size guard to the public `KaiaAPI.DecodeAccountKey`/`EncodeAccountKey` RPC handlers before invoking `rlp.DecodeBytes`.
- Consider adding a generic recursion-depth counter to `rlp.Stream`/`Decoder` invocations for custom `Decoder` types that can recursively construct other `Decoder`s, to close this class of bug generally rather than only for `AccountKey`.

### Proof of Concept
Conceptual PoC (not executed against a live node):
1. Construct an `AccountKeySerializer` payload of type `AccountKeyTypeRoleBased` whose single list element is itself an RLP-encoded `AccountKeySerializer` of type `AccountKeyTypeRoleBased`, and repeat this nesting N times (e.g., N = 50,000), each level wrapped as `rlp.EncodeToBytes` per `AccountKeyRoleBased.EncodeRLP`/`AccountKeySerializer.EncodeRLP` [8](#0-7) [9](#0-8) .
2. Submit this byte string to the public `kaia_decodeAccountKey` RPC method: `KaiaAPI.DecodeAccountKey(encodedAccKey)` [7](#0-6) , or embed it as the `key` field of an `AccountUpdate`/`AccountCreation` transaction sent to the node's tx-pool, which triggers `rlp.DecodeBytes(js.Key, ser)` in `UnmarshalJSON` before any semantic validation [10](#0-9) .
3. The recursive chain `AccountKeyRoleBased.DecodeRLP → AccountKeySerializer.DecodeRLP → NewAccountKey → AccountKeyRoleBased.DecodeRLP → ...` executes N times with no depth check, exhausting the goroutine's stack and crashing the node process.

Note: The exact nesting depth required to overflow Go's stack, and whether it fits within the node's maximum accepted transaction/RPC payload size, was not empirically verified in this review and should be confirmed by a background engineer with test-execution access before treating this as fully proven end-to-end.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
