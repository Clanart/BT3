### Title
Gasless `ApproveTx` can be permanently purged from the pool (and its lender fee wasted) whenever the bundled `SwapTx` fails due to unrelated, later on-chain state changes - (File: `work/worker.go`, `kaiax/gasless/impl/builder.go`, `blockchain/tx_list.go`)

### Summary
The Fenix `_poke`/`_vote` bug shows a pattern where an already-accepted, previously-valid set of actions is blindly "replayed" as a unit, and if any single element of that unit becomes invalid due to an unrelated later state change, the whole replay reverts and blocks a legitimate, unrelated user action. Kaia's gasless-transaction bundling (`kaiax/gasless`) exhibits the same "batch atomicity vs. stale validity" pattern: a `GaslessApproveTx` that was valid and admitted into the pool can be permanently discarded because the paired `GaslessSwapTx` fails inside the EVM for reasons unrelated to the approve step itself.

### Finding Description
Gasless transactions are built as `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` bundles by `GaslessModule.ExtractTxBundles`: [1](#0-0) 

The bundle is executed atomically in `commitBundleTransaction`. If *any* transaction in the bundle fails (`err != nil || receipt.Status != types.ReceiptStatusSuccessful`), the entire bundle's state changes are rolled back with `restoreEnv()`, and **all concrete transactions in the bundle — including the earlier `ApproveTx` that already executed successfully — are marked unexecutable**: [2](#0-1) 

The `SwapTx`'s admissibility (`isSwapTx`) depends on `g.swapRouter`/`g.allowedTokens`, which are refreshed only once per block via `updateAddresses`, reading fresh on-chain `GaslessSwapRouter` state: [3](#0-2) 

Because this cache is block-granular while `checkBalanceForSwap` also queries the live router contract for `GetAmountIn` and allowance/balance at commit-time, the router or token state can change between when the `ApproveTx`/`SwapTx` pair was validated as `Ready` (admitted to the pool) and when it is actually committed in a bundle (e.g., router liquidity shifts, token temporarily de-listed, or another transaction earlier in the same block changes allowance/balance). When this happens, `SwapTx` reverts inside the EVM, and per the atomic-bundle logic above, the entire bundle — including the already-successful `ApproveTx` — is rolled back and `ApproveTx` is flagged `MarkUnexecutable(true)`.

Once flagged, `blockchain/tx_list.go`'s `Filter` unconditionally drops the transaction from the pool on the next filtering pass, regardless of whether it is otherwise perfectly valid: [4](#0-3) 

This mirrors the external report's root cause exactly: a previously-accepted, valid action (`ApproveTx` / the vote on `gaugeA`+`gaugeB`) is force-replayed/re-evaluated as an atomic unit together with a companion element whose validity depends on volatile external state (`SwapTx` / vote on `gaugeB`), and the unit's failure destroys the previously-valid element rather than gracefully separating them.

### Impact Explanation
A gasless user's `ApproveTx` — for which the proposer already lent gas via `LendTxGenerator` and which had already been accepted into the pool as `Ready` — is silently and permanently purged whenever the paired `SwapTx` fails for reasons the user does not control (router/token state drift, front-running of the router's liquidity, or nonce-adjacent transactions altering allowance/balance). The user must detect this and manually resubmit both the approve and swap transactions, repeating the entire lending/approval dance and losing their pool "slot"/nonce continuity in the interim — a genuine denial-of-service against the gasless transaction flow that KIP-247 defines. Because it can be repeatedly triggered by conditions outside the user's control (e.g., a router operator toggling a token, or normal price/liquidity movement), affected users can be made unable to complete gasless swaps for extended periods, analogous to the "temporarily undetachable veNFT" DoS in the source report.

### Likelihood Explanation
This does not require any privileged access. Any two natural events are sufficient: (1) router/token allow-list state (`GaslessSwapRouter`) or on-chain liquidity/allowance shifts between pool admission and block building — something normal DEX activity or a router operator's `TokenRemoved`/allowance change can trigger; or (2) transaction reordering within the same block window changes the `allowance`/`balanceOf` values checked in `checkBalanceForSwap`. Because `updateAddresses` only refreshes once per block while a bundle can be attempted repeatedly across proposer retries, the window for this race is non-trivial and does not require an attacker at all, only ordinary market activity or a benign admin action.

### Recommendation
Avoid permanently marking `ApproveTx` unexecutable when it is only the `SwapTx` portion of the bundle that fails. Options:
- Separate the failure handling so `markAllTxUnexecutable` only marks the specific transaction that caused the revert (the `SwapTx`), keeping the `ApproveTx` in the pool (its ERC20 state effects are still rolled back, but its validity as a pending transaction is unaffected).
- Re-check `SwapTx` viability (via `VerifyExecutable`) using the exact state right before committing the bundle rather than relying on a block-refreshed cache, and skip/exclude the bundle without touching `ApproveTx`'s pool status if the swap is no longer viable.
- On bundle failure, requeue `ApproveTx` for potential re-bundling with a fresh `SwapTx` rather than dropping it via `MarkUnexecutable`.

### Proof of Concept
1. User signs and submits `ApproveTx` (nonce N) and `GaslessSwapTx` (nonce N+1) for token X via router R. Both pass `VerifyExecutable`/`checkBalanceForSwap` and are promoted to `pending` (see `kaiax/gasless/impl/tx_pool.go` `checkBalanceForSwap`, lines 107-182).
2. `GaslessModule.ExtractTxBundles` forms `[LendTxGenerator, ApproveTx, SwapTx]` (`kaiax/gasless/impl/builder.go`, lines 28-72).
3. Before this bundle is committed, on-chain conditions change such that the swap becomes non-viable at commit time (e.g., router `GetAmountIn` price moves, or allowance/balance drifts, or token is removed) — the `SwapTx`'s EVM execution now reverts.
4. `Task.commitBundleTransaction` (`work/worker.go`, lines 906-936) executes `LendTxGenerator` then `ApproveTx` (both succeed), then `SwapTx` (fails). Because `err != nil`, `markAllTxUnexecutable()` marks **all three bundle transactions**, including the successful `ApproveTx`, as `Unexecutable`, and `restoreEnv()` rolls back all state changes including the approval.
5. On the pool's next `Filter` pass (`blockchain/tx_list.go`, lines 376-387), `ApproveTx.IsMarkedUnexecutable()` returns true and the transaction is dropped from the pool entirely, even though it was independently valid and unrelated to why the swap failed.
6. The user must resubmit both `ApproveTx` and `SwapTx` from scratch to proceed with their gasless swap.

func (g *GaslessModule) updateAddresses(header *types.Header) error {
	g.gaslessInfoMu.Lock()
	defer g.gaslessInfoMu.Unlock()

	swapRouter, tokens, err := getGaslessInfo(g.Chain, header)
	// proceed even if there is something wrong with multicall contract
	if err != nil {
		g.swapRouter = common.Address{}
		g.allowedTokens = map[common.Address]bool{}
		logger.Warn("there is something wrong with multicall contract", "err", err.Error())
		return nil
	}

	g.swapRouter = swapRouter

	g.allowedTokens = map[common.Address]bool{}
	for _, addr := range tokens {
		// all tokens are allowed if nil
		if g.GaslessConfig.AllowedTokens == nil {
			g.allowedTokens[addr] = true
		}
		for _, allowed := range g.GaslessConfig.AllowedTokens {
			if addr == allowed {
				g.allowedTokens[addr] = true
			}
		}
	}

	return nil
}
