## Analog Found

The UNCX bug is: a *privileged pointer* (`collector`/`additionalCollector`) is bound to a `lock` by identity (`tokenId`), but when the underlying ownership of that identity changes, the pointer is never invalidated — so old, now-unauthorized state continues to be trusted for the same identity.

The GitHub Desktop analog is in how Desktop tracks a local repository's association with a "GitHub repository" and automatically keeps the git remote URL in sync with that identity, using **owner login + repo name as the durable identity key** instead of the GitHub-stable numeric repo id — and using that identity to *silently* rewrite the trust anchor (the remote URL) that all future pushes/fetches use.

### Title
Silent remote URL rewrite trusts owner/name identity instead of repository ID, enabling repo-hijack redirection of pushes - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically calls `git remote set-url` on the user's `origin` remote whenever the GitHub API's `clone_url` for the previously-matched `owner/name` differs from the current remote, as long as the current remote still matches the last-cached `clone_url` and protocols match. The identity used to look up "the same GitHub repository" is `owner.login` + `name` strings (see `putOwner`/`_upsertGitHubRepository` keyed by `[ownerID+name]`), not GitHub's immutable numeric repository id. This mirrors the reported bug: an identity (lock id / owner-name pair) can change hands, but the associated privileged state (collector address / trusted remote URL) is neither reset nor re-validated against the new true owner.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` (around line 4874) resolves the local repository to a GitHub repo via `matchGitHubRepository`, which only parses `owner`/`name` out of the current remote URL [1](#0-0) . It then fetches `api.fetchRepository(owner, name)` and, if the repo exists, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)` [2](#0-1) .

`updateRemoteUrl` then compares the *previously cached* `gitHubRepository.cloneURL` against the current git remote, and if they still match (`remoteUrlUnchanged`) but the freshly-fetched `apiRepo.clone_url` differs and protocols match, it silently rewrites the remote: [3](#0-2) 

The local database keys `GitHubRepository` records by `[ownerID+name]`, where `ownerID` itself is derived from `endpoint+login` (`getOwnerKey`), not from GitHub's numeric account/repo id [4](#0-3) . The `GitHubRepository` model explicitly notes its `dbID` "is no relation to the API ID" and never stores/compares the GitHub API's actual repository id [5](#0-4) .

Because identity is anchored purely to the `owner/name` string pair, if the real-world entity behind that pair changes — e.g., the account is renamed/released and re-registered by a different (attacker-controlled) account, or the repository is deleted and an identically-named repo is recreated under the same still-controlled login by an attacker who has taken over the account/name — Desktop's periodic refresh (`repositoryWithRefreshedGitHubRepository`, invoked from repository indicator refresh / account-change refresh flows) will fetch the "new" repository's `clone_url` and automatically retarget the user's `origin` remote to it, with no user confirmation, as long as the user never manually touched the remote URL.

### Impact Explanation
Once the remote is silently rewritten, all subsequent `git push`/`git fetch` operations the user performs through Desktop's UI operate against the attacker-controlled repository/identity instead of the one the user originally added. This can result in:
- Silent corruption of what the user pushes (private code/commits sent to a repository the user does not control or trust).
- Exposure of code/history the user believes is going to their original private repo.

This matches the accepted impact class: "a git remote/proxy response... result is... silent corruption of what the user commits or pushes."

### Likelihood Explanation
The precondition (the user never manually edited the `origin` URL since it was last synced, i.e. `remoteUrlUnchanged`) is the default state for the vast majority of repositories cloned via Desktop. The attacker precondition — regaining control of an `owner/name` pair that a victim's Desktop client has previously associated with a specific repository (via GitHub username release/re-registration, a deleted-and-recreated repo, or an org repo transfer to a new owner reusing the name) — is a known, previously-exploited class of "repo-jacking"/"repository confusion" issue on GitHub, and requires no special access to the victim's machine. The rewrite happens automatically during routine background refreshes with no user prompt, and existing guards (`protocolsMatch`, `remoteUrlUnchanged`, `urlMatchesRemote`) only check URL string shape, not any stable repository identity, so they do not stop this path.

### Recommendation
Anchor the "is this the same GitHub repository" decision to GitHub's immutable numeric repository id (obtainable from the API response) rather than solely `owner/name` strings, and treat a mismatch in id as a *new* repository requiring the user to explicitly confirm/re-associate (and possibly re-authorize) rather than silently rewriting `origin`. At minimum, `updateRemoteUrl` should require explicit user confirmation before changing the remote URL, and any cached `GitHubRepository` record should store and validate against the API's repository id, invalidating/resetting cached trust (and prompting reassociation) when the id no longer matches for a given `owner/name`.

### Proof of Concept
1. Victim adds/clones `https://github.com/alice/project` in Desktop; Desktop stores a `GitHubRepository` keyed by owner login `alice` + name `project`, with `cloneURL` cached.
2. `alice` renames her GitHub account (or the account is later released and re-registered) and an attacker registers the `alice` login, then creates a new repository named `project`.
3. On the next background refresh (repository indicator update / account refresh), `repositoryWithRefreshedGitHubRepository` calls `matchGitHubRepository`/`api.fetchRepository('alice','project')`, which now resolves to the attacker's repository, returning its `clone_url`.
4. Since the victim never manually edited `origin` (`remoteUrlUnchanged` is true) and protocols match, `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', <attacker clone_url>)` with no prompt [6](#0-5) .
5. The victim's next push/fetch in Desktop now silently targets the attacker's repository.

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

  private async putOwner(
    endpoint: string,
    login: string,
    ownerType?: GitHubAccountType
  ): Promise<Owner> {
    const key = getOwnerKey(endpoint, login)
    const existingOwner = await this.db.owners.get({ key })
    let id

    // Since we look up the owner based on a key which is the product of the
    // lowercased endpoint and login we know that we've found our match but it's
    // possible that the case differs (i.e we found `usera` but the actual login
    // is `userA`). In that case we want to update our database to persist the
    // login with the proper case.
    if (
      existingOwner === undefined ||
      existingOwner.login !== login ||
      // This is added so that we update existing owners with an undefined type.
      (ownerType !== undefined && existingOwner.type !== ownerType)
    ) {
      id = existingOwner?.id
      const existingId = id !== undefined ? { id } : {}
      id = await this.db.owners.put({
        ...existingId,
        key,
        endpoint,
        login,
        type: ownerType,
      })
    } else {
      id = forceUnwrap('Missing owner id', existingOwner.id)
    }

    return new Owner(login, endpoint, id, ownerType ?? existingOwner?.type)
