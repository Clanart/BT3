## Finding

**Binding claimed to hold:** `kickoff_data.operator_xonly_pk` used to authorize a Reimburse spend `==` the operator who actually broadcast/funded the payout to the Citrea withdrawer.

**What the code actually checks:** `Verifier::is_kickoff_malicious` only checks `kickoff_data.operator_xonly_pk == operator_xonly_pk_opt` where `operator_xonly_pk_opt` is whatever x-only pubkey was parsed out of the *confirmed* payout transaction's OP_RETURN output by `update_finalized_payouts`, with no independent re-derivation of who funded the payout.

### Title
Reimburse tx is authorized based on an unsigned, forgeable payout OP_RETURN operator field, not on proof the operator funded the payout - (File: `core/src/verifier.rs`, `core/src/task/payout_checker.rs`)

### Summary
The payout transaction's user signature is enforced to use `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) , which only commits to the spent input and the output at the same index (index 0, the user's payout output). The OP_RETURN output containing the "operator that fronted" attribution [2](#0-1)  is outside the signed message, so it is not authenticated by the operator's key at all. Verifiers' malicious-kickoff check and the operator's own reimbursement-claim automation both trust this unauthenticated field as ground truth for "who fronted this withdrawal."

### Finding Description
`Verifier::is_kickoff_malicious` derives the "authorized operator" for a deposit purely from the DB-cached OP_RETURN parse of the confirmed payout tx and compares it only to the kickoff sender's own key, never to any signed proof of funding: [3](#0-2) 

That DB value is populated by `update_finalized_payouts`, which simply parses whatever OP_RETURN happens to be in the block-confirmed payout transaction, and explicitly documents that a missing/invalid pubkey is tolerated ("assuming malicious" only if absent, not if wrong-but-plausible): [4](#0-3) 

Since the user's payout signature (`SinglePlusAnyoneCanPay`) never covers the OP_RETURN output, an unprivileged attacker who observes any broadcast/mempool payout tx (or the RBF-fundable, non-finalized tx before confirmation) can rebuild an equivalent payout transaction with the same signed input/output-0 but an OP_RETURN naming an arbitrary honest operator X who never touched this withdrawal, and get that version confirmed instead (per the prior RBF/replacement questions, out of scope to reprove here).

Once that forged attribution is confirmed on-chain:
1. `update_finalized_payouts` records operator X as payer for that withdrawal.
2. Operator X's own `PayoutCheckerTask` autonomously picks up this "unhandled payout" keyed by X's own xonly pubkey and calls `handle_finalized_payout`, assigning the deposit to X's round/kickoff slot for reimbursement — no wrongdoing by X is required: [5](#0-4) 
3. When X's kickoff for that deposit is broadcast, `is_kickoff_malicious` compares `kickoff_data.operator_xonly_pk` (X) to the DB-recorded payer (X, due to the forgery) — they trivially match, so `handle_kickoff` treats it as non-malicious and never queues a Challenge: [6](#0-5) 
4. The Reimburse transaction for X's round/kickoff slot was already pre-signed N-of-N by verifiers generically at deposit time — during `deposit_sign`, before any payout even exists, and independent of who eventually pays out — via `create_nofn_sighash_stream` covering `TransactionType::Reimburse` among "AllNeededForDeposit": [7](#0-6) 
5. With no challenge raised, `create_reimburse_txhandler`'s already-existing N-of-N signature lets the Reimburse output pay X's `operator_reimbursement_address` from the move-to-vault funds: [8](#0-7) 

No code path re-derives "X funded this payout" from a signature made with X's operator key; the entire chain of custody rests on unauthenticated OP_RETURN bytes.

### Impact Explanation
BTC from a move-to-vault UTXO is paid out via a legitimately-signed (N-of-N) Reimburse transaction to an operator who never fronted the corresponding Citrea withdrawal — directly matching "an operator reimbursed for a payout it never funded" (Critical). This is repeatable per withdrawal/deposit and can target any registered operator, since the only precondition is that the payout tx's OP_RETURN naming can be swapped in favor of any operator's known x-only pubkey (a public value). The blast radius covers every deposit that goes through the fronted-payout (non-optimistic) path.

### Likelihood Explanation
Preconditions: the attacker must be able to substitute the OP_RETURN content of a not-yet-confirmed payout transaction while preserving the `SinglePlusAnyoneCanPay`-signed input/output-0 (established feasible per the prior RBF/sighash questions in this series). No verifier, operator, or aggregator credential is needed; the attacker only needs to observe a broadcast/mempool payout tx and any registered operator's known public x-only key, then get their replacement mined with normal fee-bumping. Cost is limited to Bitcoin transaction fees for the replacement transaction.

### Recommendation
Do not derive operator payout attribution solely from an unauthenticated OP_RETURN. Either (a) require the operator to sign a commitment to the OP_RETURN content with their own key when submitting the kickoff/payout claim and verify that signature independently of the confirmed OP_RETURN bytes, or (b) extend the payout signature's sighash coverage (or add a separate covenant/commitment) so the OP_RETURN output is bound by the user's or operator's signature and cannot be altered without invalidating it. `is_kickoff_malicious` should independently verify that the operator claiming reimbursement is cryptographically tied to the funding of the payout output, not merely that unauthenticated on-chain bytes name them.

### Proof of Concept
`cargo test` plan (new test, not reusing existing fixtures beyond standard e2e helpers):
1. Run a standard deposit + withdrawal setup so operator A legitimately builds and broadcasts a payout tx (via `Operator::withdraw`) for withdrawal `W`, with OP_RETURN naming A.
2. Before confirmation, construct a second transaction spending the same input, reusing the same `SinglePlusAnyoneCanPay` witness, identical output 0, but an OP_RETURN naming operator B's xonly pubkey instead of A's; broadcast/mine this version instead.
3. Let verifier/operator B's automation run `update_finalized_payouts` and `PayoutCheckerTask`; assert the DB now records B as payer for `W` (`get_payout_info_from_move_txid` returns B).
4. Have operator B send its Kickoff for this deposit; assert `Verifier::is_kickoff_malicious` returns `false` and no `Challenge` tx is queued, even though B never called `withdraw`/broadcast the original payout.
5. Assert the Reimburse tx for B's kickoff slot (already N-of-N signed at deposit time) is accepted and confirms, paying B's `operator_reimbursement_address` — proving `kickoff_data.operator_xonly_pk (B) == payout_info.operator_xonly_pk (forged B)` while `B != actual funder of W`, i.e., the binding "Reimburse signed == payout actually fronted by that operator" is broken.

    /// Checks if the kickoff is malicious and sends the appropriate txs if it is.
    /// Returns true if the kickoff is malicious.
    /// Sends a challenge tx if the kickoff is first malicious one in the current round, and the network is not mainnet or testnet4.
    pub async fn handle_kickoff<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        kickoff_witness: Witness,
        mut deposit_data: DepositData,
        kickoff_data: KickoffData,
        challenged_before: bool,
    ) -> Result<bool, BridgeError> {
        let is_malicious = self
            .is_kickoff_malicious(kickoff_witness, &mut deposit_data, kickoff_data, dbtx)
            .await?;

        let deposit_outpoint = deposit_data.get_deposit_outpoint();

        let (_signed_txs, tx_metadata, challenge_tx) = self
            .get_signed_txs_for_kickoff(dbtx, kickoff_data, deposit_data)
            .await?;

        if is_malicious {
            tracing::warn!(
                "Malicious {} detected. {} Challenge tx: {} for deposit {}",
                kickoff_data,
                match challenged_before {
                    false => "This is the first malicious kickoff in the current round.",
                    true => "This is not the first malicious kickoff in the current round.",
                },
                bitcoin::consensus::encode::serialize_hex(&challenge_tx),
                deposit_outpoint
            );
            // do not automatically send challenge txs on mainnet or testnet4
            if !challenged_before
                && !matches!(
                    self.config.protocol_paramset().network,
                    bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
                )
            {
                #[cfg(feature = "automation")]
                self.tx_sender
                    .add_tx_to_queue(
                        dbtx,
                        TransactionType::Challenge,
                        &challenge_tx,
                        &[],
                        Some(tx_metadata),
                        self.config.protocol_paramset(),
                        None,
                    )
                    .await?;
            }
        } else {
            tracing::debug!(
                "Non-malicious {} detected, challenge tx: {}",
                kickoff_data,
                bitcoin::consensus::encode::serialize_hex(&challenge_tx)
            );
        }
