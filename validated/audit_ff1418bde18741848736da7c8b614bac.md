### Title
Pointer precompile's `AddCW20`/`AddCW721`/`AddCW1155` blindly type-asserts an untrusted CosmWasm contract's query response, causing an unrecovered panic that aborts block processing - ([File: precompiles/pointer/pointer.go])

### Summary
The `pointer` precompile lets any EVM caller create an ERC20/ERC721/ERC1155 "pointer" wrapper around an arbitrary CosmWasm contract by supplying only its bech32 address, mirroring the audited bug pattern of accepting an "asset" without verifying it actually conforms to the expected interface. `AddCW20`/`AddCW721`/`AddCW1155` query the target contract for `token_info`/`contract_info` and directly assert the returned `"name"`/`"symbol"` JSON fields as Go strings with no schema or type validation.

### Finding Description
`PrecompileExecutor.AddCW20`, `AddCW721`, and `AddCW1155` call `p.wasmdKeeper.QuerySmartSafe` against the caller-supplied `cwAddr` and then do:
```go
name := formattedRes["name"].(string)
symbol := formattedRes["symbol"].(string)
``` [1](#0-0) [2](#0-1) [3](#0-2) 

There is no check that the target is a genuine CW20/CW721/CW1155 contract beyond "the query succeeded and returned some JSON". Any wasm contract — including a trivial contract deployed by the attacker themselves that implements a `token_info`/`contract_info` query handler — can return JSON that omits `"name"`/`"symbol"` or returns them as a non-string type (number, object, null). In Go, `interface{}(nil).(string)` or a type mismatch causes a runtime panic (`interface conversion: interface {} is ..., not string`), not a recoverable error.

This precompile method is executed via `DynamicGasPrecompile.RunAndCalculateGas`, whose only panic-recovery scope is the calldata-decode charging step; the executor's own panic is explicitly **not** caught, as verified by the regression test: [4](#0-3) 

The panic then propagates through EVM execution into `msgServer.EVMTransaction`, whose deferred recover only logs and metrics-increments before **re-panicking**: [5](#0-4) 

That re-panic is finally caught by `App.ProcessBlock`'s top-level recover, which discards the *entire block's* results (`txResults = nil`, `events = nil`) and returns an error: [6](#0-5) 

Because this panic is fully deterministic given the same malicious transaction and contract state, every validator executing that block hits the same code path and the same recovery outcome — the whole block's processing fails identically everywhere it's attempted, which can prevent block finalization/halt progress rather than just reverting the single offending transaction.

### Impact Explanation
This differs from the audited `whitelistAsset` bug (which only risked "unexpected behaviour"): here the missing interface validation produces an unrecovered Go panic reachable from a single, unprivileged EVM transaction (`addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer`), and the panic is not safely converted to an EVM revert. The only two "safety nets" in the call chain (`RunAndCalculateGas`'s decode-gas recover, and `msgServer.EVMTransaction`'s recover) both explicitly re-panic non-gas-meter panics rather than swallow them, letting the panic bubble to `ProcessBlock`, which fails the entire block rather than just the transaction. This is a validator/chain-halt risk (block delay/processing failure), matching the "validator halt / block delay" impact bar.

### Likelihood Explanation
High. No special privileges are required: any account can (1) deploy a trivial CosmWasm contract that answers `token_info`/`contract_info` queries with a response missing/mistyping `"name"`/`"symbol"`, and (2) call `addCW20Pointer`/`addCW721Pointer`/`addCW1155Pointer` (precompile at `0x000000000000000000000000000000000000100b`) with that contract's address in a normal EVM transaction. This requires no governance, no validator collusion, and no malformed p2p/consensus messages — purely an application-level transaction.

### Recommendation
In `AddCW20`/`AddCW721`/`AddCW1155` (and their legacy/versioned copies under `precompiles/pointer/legacy/...`), validate the decoded response before type-asserting, e.g.:
```go
nameVal, ok := formattedRes["name"]
if !ok {
    return nil, 0, errors.New("cw contract token_info missing name")
}
name, ok := nameVal.(string)
if !ok {
    return nil, 0, errors.New("cw contract token_info name is not a string")
}
```
(same for `symbol`), returning a normal `error` instead of allowing a panic. Additionally, wrap the pointer precompile's executor `Execute`/`AddCW*` functions with the same `recover()`-to-`error` pattern already used in `precompiles/addr`, `precompiles/oracle`, and `precompiles/solo` (see `defer func(){ if r := recover(); r != nil { err = fmt.Errorf("execution reverted: %v", r) } }()`), so that any unexpected panic from untrusted contract responses degrades to a reverted transaction rather than an unrecovered panic that unwinds through `msgServer.EVMTransaction`'s re-panicking recover into `ProcessBlock`.

### Proof of Concept
1. Deploy a CosmWasm contract `C` whose `ExecuteMsg`/`QueryMsg` handles `{"token_info":{}}` (for the CW20 case) by returning valid JSON that is missing the `"name"` key (or sets it to `null`/a number), e.g. `{"symbol": "X", "decimals": 6, "total_supply": "0"}`.
2. From any EOA, call the pointer precompile at `0x...100b` method `addCW20Pointer(C_bech32_address)`.
3. `p.wasmdKeeper.QuerySmartSafe` succeeds and returns the malformed JSON; `formattedRes["name"].(string)` panics with an interface-conversion panic.
4. The panic is not caught by `RunAndCalculateGas`'s decode-only recover (confirmed by `TestDynamicGasPrecompileRepanicsNonGas`), propagates through EVM execution, is re-panicked by `msgServer.EVMTransaction`'s recover, and is only caught (with block-wide `err` returned and results discarded) by `App.ProcessBlock`'s recover — failing the whole block that included the transaction.

Note: I was unable to fully trace how `ProcessBlock`'s returned error is ultimately handled at the ABCI `FinalizeBlock` boundary (e.g., whether it crashes the process outright or is retried), since the final tool iteration budget was exhausted before locating that caller. This should be verified in a Devin session with full repository access to confirm whether the failure mode is a full node crash, a stuck/halted chain, or a recoverable retry.
