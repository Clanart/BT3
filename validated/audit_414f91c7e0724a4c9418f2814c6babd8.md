### Title
Cached FROST preprocess seed keyed only by `(label, attempt)` is reused across differing signing sets/messages, enabling nonce-reuse recovery of the MuSig secret share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class in the external report is "stale cached state used in place of freshly computed state when computing a security-critical parameter." The Serai analog lives in `SigningProtocol::preprocess_internal`: the FROST preprocess seed is cached in `CachedPreprocesses` keyed solely by `self.context`, while the participant set, the `removed` list, and the signed message are all fresh per call. Because `AlgorithmSignMachine::from_cache` regenerates identical nonces from the identical seed, any second `share`/`complete` invocation under the same context but with a different preprocess set or different `key_pair` produces two signature shares over the same nonce with different binding factors/challenges — a classic nonce-reuse leak of the secret share.

### Finding Description
In `preprocess_internal`, the seed cache lookup uses only `self.context`: [1](#0-0) 

`from_cache` rebuilds nonces deterministically via `seeded_preprocess` (`ChaCha20Rng::from_seed(*seed.0)`): [2](#0-1) 

For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` — it does **not** bind the `removed` set, the preprocess set, or `key_pair`/`msg`: [3](#0-2) 

`share()` is invoked with attacker-influenced `preprocesses` and `key_pair`; `complete()` calls `share_internal` a second time under the same context: [4](#0-3) 

The actual signed nonce is `base + rho * actual` where `rho` is the per-participant binding factor derived from the transcript over the included preprocess set (`B.calculate_binding_factors(&rho_transcript)`): [5](#0-4) 

Because the seed — hence the base/actual nonces — is stale across calls while `included` and `msg` may change, two shares satisfy `s₁ = d + ρ₁·c·x` and `s₂ = d + ρ₂·c'·x` (or differing `msg` ⇒ differing challenge), yielding `x` by subtraction/division. This exactly mirrors the report's pattern: a stored value (`CachedPreprocesses` seed vs. `signerCount`) that should have been recomputed (`countValidSigners`/fresh RNG) is reused while the surrounding inputs changed.

### Impact Explanation
Any observer of the two differing shares (all participants see shares over the authenticated channel) can solve for the victim's MuSig secret share. Combined with the threshold structure this enables recovery of signing capability for the set key — i.e., signing of unintended messages (substrate `set_keys` messages for `DkgConfirmer`), equivalent to key-share recovery, a Critical-adjacent primitive.

### Likelihood Explanation
Reachability requires two `share`-producing calls under one `(label, attempt)` context with differing effective transcripts. This occurs if `share`/`complete` is re-driven with a different accumulated preprocess subset (the accumulation path in `handle.rs` collects per-validator data keyed by `DataSpecification`, and `threshold_i_map_to_keys_and_musig_i_map` remaps to a different included set when `removed` or the contributing signer subset changes), or if `key_pair` differs between calls. The seed is never cleared after use — `CachedPreprocesses::get` is read repeatedly without deletion — so any repeat within the same attempt deterministically reuses the nonce. Likelihood is moderate: it needs a distinct second signing instance under the same attempt, which the retry/complete paths make plausible but not guaranteed on every run.

### Recommendation
Include the full signing context in the cache key — e.g., hash of `participants`, `removed`, `msg`/`key_pair`, and the committed preprocess set — or, preferably, delete the cached seed on first consumption (`CachedPreprocesses::kill` after `get`) and generate a fresh seed per `share` invocation rather than per `(label, attempt)`. At minimum, document and enforce that `preprocess_internal` may be called only once per context with identical inputs.

### Proof of Concept
1. Attempt `a` of `DkgConfirmer`: seed `s` stored under context `(b"DkgConfirmer", a)`.
2. Call `share(preprocesses_A, key_pair)` — machine derives nonces `d, e` from `s`, binding factor `ρ_A` from transcript over set `A`; emits share `s₁`.
3. A second invocation `share(preprocesses_B, key_pair)` where `B ≠ A` (e.g., a different validator contributed, altering `included` after `threshold_i_map_to_keys_and_musig_i_map`), or a differing `key_pair` altering `msg`, regenerates the same `d, e` from `s` but computes `ρ_B ≠ ρ_A` and/or a different challenge; emits `s₂`.
4. Solve `s₁ - s₂ = (ρ_A·c_A - ρ_B·c_B)·x` for the secret share `x`.

Uncertainty: I did not fully trace `handle.rs`'s `Topic::DkgConfirmation` dispatch to confirm a second `share` call with differing inputs is reachable in a single attempt; the vulnerability's existence stands on the seeded-nonce reuse (`sign.rs:121-144`, `signing_protocol.rs:123-147`), while reachability determines final severity (Medium if a second distinct invocation is not reachable, High/Critical if it is).
