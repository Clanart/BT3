### Title
Ed448 accepts low-order points because its torsion check is always true - (`crypto/ed448/src/point.rs`)

### Summary
`Ed448::read_G` relies on `Point::from_bytes` to reject non-prime-order points, but `Point::is_torsion_free` evaluates `(-1 * P) + P`, which is always the identity, instead of multiplying by the prime-order scalar. As a result, canonical encodings of low-order Ed448 points are accepted as `PrimeGroup` elements and can be used in Schnorr verification. This permits signatures for malformed public keys that do not possess a discrete logarithm relative to the generator. [1](#0-0) [2](#0-1) 

### Finding Description
`Point::from_bytes` reconstructs an Ed448 point from `y`, rejects negative zero, and then requires `point.is_torsion_free()`. The latter is implemented as:

```rust
((*self * (Scalar::ZERO - Scalar::ONE)) + self).is_identity()
```

`Scalar::ZERO - Scalar::ONE` is `-1`, not the prime subgroup order, so this expression is mathematically `(-P) + P = identity` for every curve point. The intended subgroup bound is therefore never enforced. [1](#0-0) 

`Ciphersuite::read_G` accepts any `G::from_bytes` result and only additionally checks that reserializing the point produces the same bytes. Consequently, a validly encoded low-order point supplied as public input passes the canonical parser. [2](#0-1) 

The Schnorr verifier computes `R + cA - sG` and accepts it when the result is the identity. Since the parser no longer guarantees that `A` and `R` are in the prime-order subgroup, an attacker can use the order-2 Ed448 point `T = (0, -1)` and choose `R = rG + T`, `A = T`, and `s = r`. The verification equation becomes `(1 + c)T`, which is identity whenever the challenge scalar `c` is odd. Iterating `r` until the message-bound challenge is odd yields an accepted signature for a public key that is not a scalar multiple of the generator. [3](#0-2) 

### Impact Explanation
The `PrimeGroup` contract is violated for attacker-controlled Ed448 encodings: `read_G`, `SchnorrSignature::read`, and higher-level `verify` APIs can operate on points outside the subgroup despite declaring the signature format strict and prime-order. An unprivileged party can therefore construct a canonical key encoding that has no corresponding secret scalar and still produce an accepted Schnorr signature with approximately one retry per candidate challenge parity. [4](#0-3) [5](#0-4) 

This is a verifier-formula flaw rather than merely accepting unusual encodings: the accepted group element changes the algebraic statement being verified from “the key is `aG`” to “the key is `aG + T`”, where the unbound torsion component can be canceled through challenge parity. Any protocol that authenticates actions using parsed Ed448 keys and Schnorr signatures can accept a proof for a mathematically invalid key. [6](#0-5) 

### Likelihood Explanation
The attack requires only public bytes: a canonical 57-byte Ed448 point encoding supplied to `Ed448::read_G`, plus a normally encoded Schnorr signature. No validator compromise, secret access, malformed-length input, or noncanonical encoding is needed. [2](#0-1) 

The order-2 point is directly encodable as `y = -1 mod (2^448 - 2^224 - 1)` with a zero sign bit. Its `(x, y)` coordinates are `(0, -1)`, so doubling it produces the identity, while `x == 0` and `sign == 0` bypass the negative-zero rejection. [7](#0-6) 

For a Fiat-Shamir challenge bound to `R`, the forged signature succeeds when `c` is odd. Trying different `r` values changes `R = rG + T` and therefore the challenge, giving roughly a one-in-two success rate per candidate. [8](#0-7) 

### Recommendation
Replace the current check with an actual cofactor/subgroup check. For Ed448, multiply the candidate by the prime subgroup order `q` and require the result to be identity, or equivalently verify `h * P` has order at most the cofactor while ensuring `P` itself lies in the prime-order subgroup according to the intended API contract.

For example, expose the scalar-field modulus/order constant and implement:

```rust
fn is_torsion_free(&self) -> Choice {
  (*self * Scalar::ORDER).is_identity()
}
```

The exact implementation should avoid introducing a second representation of `q`; use the scalar implementation’s canonical modulus constant if available. Add a regression test asserting that the canonical encoding of `(0, -1)` is rejected by both `Point::from_bytes` and `Ed448::read_G`, while the generator and ordinary generated points remain accepted. Also test all canonical low-order Ed448 encodings. [1](#0-0) 

### Proof of Concept
1. Let `p = 2^448 - 2^224 - 1`.
2. Encode `y = p - 1` in the first 56 bytes of a 57-byte Ed448 compressed encoding, little-endian, and set byte 56 to `0`.
3. The decoded point is `(x, y) = (0, -1)`, an order-2 point.
4. Pass those bytes to `Ed448::read_G`; `Point::from_bytes` accepts it because `is_torsion_free` computes `-P + P`, which is always identity. [1](#0-0) 
5. Treat that decoded point as public key `A`.
6. For candidate scalar `r`, construct `R = rG + T` and signature `(R, s = r)`.
7. The verifier computes:

   ```text
   R + cA - sG
   = (rG + T) + cT - rG
   = (1 + c)T
   ```

   This is identity whenever `c` is odd. Repeating candidates until the challenge is odd produces a `true` result from `SchnorrSignature::verify`, even though `A = T` has no discrete logarithm with respect to `G`. [9](#0-8)
