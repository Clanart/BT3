### Title
Permissionless `RegisterERC20` lets an attacker mint unbacked native bank coins backed by a self-controlled, sham ERC20 contract - ([File: x/erc20/keeper/msg_server.go], [File: x/erc20/keeper/proposals.go])

### Summary
The Timeswap report describes a factory (`TimeswapV2PoolFactory.create()`) that created "official" pools referencing arbitrary, unvalidated underlying contracts, letting an attacker supply a malicious contract that the factory's official status made users trust. The Cosmos EVM analog is `x/erc20`'s `RegisterERC20` message handler, which — under the module's `DefaultParams()` — permissionlessly registers *any* attacker-supplied ERC20 contract address as an "official" `TokenPair` with a bank-module-recognized denom, without validating that the contract behaves like a real, honest ERC20. Because the subsequent `ConvertERC20`/`MintCoins` flow trusts values returned by that same attacker-controlled contract to decide how many *real* native bank coins to mint, an attacker can mint arbitrary amounts of spendable native coins while presenting a fake balance to the invariant check.

### Finding Description
`MsgRegisterERC20` is handled by `Keeper.RegisterERC20`: [1](#0-0) 

When `params.PermissionlessRegistration` is `true` — which is the module's default value — [2](#0-1) 

any unprivileged account can call `MsgRegisterERC20` with an arbitrary `Erc20Addresses` list and skip the `validateAuthority` (governance) check entirely. The handler then calls `k.registerERC20`, which only checks the address isn't already registered and pulls `name`/`symbol`/`decimals` straight from the untrusted contract via `QueryERC20`/`CreateCoinMetadata` — there is no validation that the contract is bytecode-verified, non-malicious, or behaves like a standards-compliant ERC20: [3](#0-2) 

Once registered, the pair is treated as `OWNER_EXTERNAL`/native-ERC20 and becomes eligible for the official `ConvertERC20` conversion path, which escrows the "ERC20" token and mints real bank coins 1:1: [4](#0-3) 

The critical flaw is that the only "proof" the module has that tokens were actually escrowed is the return value of `balanceOf(moduleAddress)` called on the same attacker-authored contract, both before and after the `transfer` call: [5](#0-4) 

Because the attacker fully controls the contract's bytecode, they can implement `transfer()` to always report success (or emit a matching `Transfer` event) and make `balanceOf()` return whatever value is needed to satisfy `balanceTokenAfter == balanceToken + amount`, without any real value ever changing hands (e.g., simply incrementing an internal counter unconditionally). The keeper then proceeds to `MintCoins` and `SendCoinsFromModuleToAccount`, minting genuine, spendable native bank coins of denom `types.CreateDenom(contract.String())` and sending them to the attacker-controlled receiver: [6](#0-5) 

This is a direct structural analog to TRST-M-2: an "official" factory/registry (`TimeswapV2PoolFactory` / `x/erc20` token-pair registry) creates trusted objects referencing attacker-supplied contracts without verifying their legitimacy, and the resulting "officially sanctioned" objects are then used to extract/create real value (pool funds / native coins) based on data the attacker controls.

### Impact Explanation
This breaks the core `x/erc20` invariant that a native bank coin issued via `ConvertERC20` is always 1:1 backed by a genuinely escrowed ERC20 token. An unprivileged attacker can deploy a sham ERC20 contract, permissionlessly register it as a token pair (default `PermissionlessRegistration=true` requires no governance approval), and repeatedly call `MsgConvertERC20` to mint arbitrary amounts of new, fully spendable native bank coins backed by nothing. These coins are ordinary bank-module coins — they can be transferred, used with other bank/precompile flows, or bridged out via IBC — constituting unauthorized minting and irreversible accounting corruption of spendable user value, matching the repository's Critical impact gate ("Critical unauthorized minting ... of spendable user value across native balances ... ERC20 representations").

### Likelihood Explanation
High under default configuration: `DefaultParams()` sets `PermissionlessRegistration: true`, so no governance step is required — an unprivileged EOA can (1) deploy a malicious ERC20 contract with any desired `transfer`/`balanceOf` logic, (2) submit `MsgRegisterERC20` directly, and (3) call `MsgConvertERC20` to mint coins. All steps use ordinary, permissionless transaction flows with no special privileges. The only mitigating factor would be if a deployment explicitly sets `PermissionlessRegistration=false` via governance, restoring the `validateAuthority` gate — but this is not the shipped default.

### Recommendation
Do not rely solely on values returned by the registered/converted contract itself to validate escrow accounting. Consider: (1) defaulting `PermissionlessRegistration` to `false` and requiring governance/allow-listing for native ERC20 token pairs; (2) validating that a registered ERC20 contract's bytecode matches a known-safe/audited implementation set (similar to the Timeswap fix of deriving the trusted contract address deterministically from a factory rather than accepting an arbitrary address); and (3) cross-checking escrow accounting against independently tracked module-side state rather than solely the token contract's self-reported `balanceOf`.

### Proof of Concept
1. Attacker deploys a malicious ERC20-like contract `Evil` where `transfer(to, amount)` always returns `true`/emits a `Transfer` event and unconditionally increases the value returned by `balanceOf(moduleAddress)` by `amount`, regardless of any real balance movement.
2. Attacker (any unprivileged account) submits `MsgRegisterERC20{Signer: attacker, Erc20Addresses: [Evil]}`. Since `PermissionlessRegistration=true` by default, `RegisterERC20` ( [7](#0-6) ) skips authority validation and calls `registerERC20`, creating a `TokenPair` and bank denom metadata for `Evil`.
3. Attacker submits `MsgConvertERC20{ContractAddress: Evil, Amount: <huge>, Receiver: attacker, Sender: attacker}`.
4. `convertERC20IntoCoinsForNativeToken` calls `Evil.transfer(moduleAddress, amount)`, which succeeds and satisfies the balance invariant check by design of the malicious contract ( [8](#0-7) ).
5. The keeper then executes `k.bankKeeper.MintCoins` and `SendCoinsFromModuleToAccount`, crediting the attacker with newly minted, fully spendable native coins of the `Evil`-derived denom ( [6](#0-5) ) with no real underlying value ever escrowed.

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}
