### Title
`rewards()` view method in the distribution precompile omits the non-payable value check, permanently stranding attached ETH/usei - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards` handler in the distribution precompile (`0x0000000000000000000000000000000000001007`) is the only query/view method in that file that does not call `pcommon.ValidateNonPayable(value)` before executing. Every other view method (`params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) routes through `p.validateInput(value, args, N)`, which internally rejects any nonzero `msg.value` [1](#0-0) . `rewards` instead validates only argument length and never inspects `value` at all [2](#0-1) , and the dispatcher calls it without any payability check either [3](#0-2) .

### Finding Description
`ValidateNonPayable` is the guard used throughout the precompile suite to reject any call carrying `msg.value` unless the function is explicitly designed to accept and account for it [4](#0-3) . The distribution precompile address (`0x1007`) is not present in the `payablePrecompiles` allow-list that suppresses/handles transfer accounting for precompiles meant to receive value — only `bank`, `staking`, `gov`, and `wasmd` are registered there [5](#0-4) . This means the distribution precompile as a whole is expected to be non-payable, and indeed every other method in `distribution.go` enforces that via `ValidateNonPayable`. `rewards`, however, is missing this call, so a transaction that invokes `rewards(address)` with a nonzero `value` field is not rejected. This is confirmed independently by the integration test suite comment: "Guard quirk worth knowing: rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds)" [6](#0-5) .

Because the EVM's native value-transfer mechanics move the wei to the precompile's account balance as part of executing the `CALL`, and there is no code path in `rewards()` (or anywhere else in the distribution precompile) to forward, refund, or otherwise account for that value, the sent funds become permanently inaccessible.

### Impact Explanation
Any unprivileged EVM caller (any address, no special permission required) can send usei/wei value alongside a call to `rewards(address)` on precompile `0x1007`. Since the value is silently accepted rather than rejected, those funds are transferred into the precompile's balance with no mechanism to recover them — a direct, attacker/user-triggerable, permanent loss of funds for whoever sends the value. This matches the "permanent freezing of funds" impact class.

### Likelihood Explanation
Likelihood is high: `rewards` is a public, unauthenticated view function reachable by any EVM transaction sender or contract that interacts with the distribution precompile; no special state, timing, or race condition is required — a single call with `value > 0` triggers the loss. The only mitigating factor is that most legitimate callers use tooling/ABIs that would not normally attach value to a "view" function, but nothing on-chain enforces this, and malformed/malicious transactions or a mis-integrated contract can trivially set `value`.

### Recommendation
Add the same `pcommon.ValidateNonPayable(value)` guard used by the other view methods (`params`, `validatorOutstandingRewards`, etc.) to `rewards`, e.g. by validating `value` before or via `p.validateInput` similar to sibling methods at [1](#0-0) , so a nonzero `msg.value` causes the call to revert instead of stranding funds.

### Proof of Concept
1. Associate an EVM address with a Sei address.
2. Call the distribution precompile at `0x0000000000000000000000000000000000001007` invoking `rewards(delegatorAddress)` (selector for `RewardsMethod`) while attaching a nonzero `value` in the transaction/call, e.g. via `distribution.rewards(delegatorAddr, { value: ethers.parseEther("1") })` as illustrated in the test harness pattern [7](#0-6) .
3. Observe that the call succeeds (returns reward data) rather than reverting with "sending funds to a non-payable function," unlike calls to any other view method (e.g. `params`, `communityPool`) with attached value, which do revert via `ValidateNonPayable` [4](#0-3) .
4. The attached value is now held at the precompile's balance with no code path in `distribution.go` to withdraw or refund it, permanently freezing those funds.
