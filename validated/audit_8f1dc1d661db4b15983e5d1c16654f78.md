### Title
Front-runnable point-in-time reward snapshot allows dilution/theft of queued yield - (File: rewards/vlMGPBaseRewarder.sol)

### Summary
`queueNewRewards` and `_queueNewRewardsWithoutTransfer` compute the reward increment as `_amountReward * 1e18 / totalStaked()`, where `totalStaked()` is a live read of `vlMGP.totalSupply()` at the moment the reward is queued [1](#0-0) . Because `VLMGP.lock`/`lockFor` credit a locker's balance to `totalStaked()` synchronously and with no minimum holding period [2](#0-1) [3](#0-2) , any unprivileged actor can inflate `totalStaked()` immediately before a `rewardManager`'s `queueNewRewards` call lands, diluting the per-token increment for existing stakers while entitling themselves to a proportional share of that specific reward event based purely on point-in-time balance rather than staking duration.

### Finding Description
`rewardPerTokenStored` is only updated in discrete lump sums inside `queueNewRewards`/`_queueNewRewardsWithoutTransfer`, using `totalStaked()` sampled at call time [4](#0-3) . `totalStaked()` returns `IERC20(address(vlMGP)).totalSupply()`, which is `VLMGP.totalAmount`, updated immediately inside `_lock` when `lockFor` is called [5](#0-4) [6](#0-5) [3](#0-2) .

`lockFor` is a fully public, unprivileged function with no cooldown or vesting delay: `MGP.safeTransferFrom` then `IMasterMagpie(masterMagpie).depositVlMGPFor` then `totalAmount += _amount` all happen in one transaction [2](#0-1) . Therefore an attacker can, in the same block or immediately preceding a pending `queueNewRewards(_amountReward, _rewardToken)` transaction in the mempool, call `lockFor(largeAmount, self)` to inflate `totalStaked()`. When `queueNewRewards` executes, the per-token increment `(_amountReward * 1e18) / totalStaked()` is computed against the now-inflated denominator, but the attacker's balance participates fully in the numerator share once `earned()`/`_earned()` is evaluated for them: `_earned` computes `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid) / 1e18 + userRewards` [7](#0-6) . Since the attacker's large balance is counted at the exact block the increment is applied, they receive a share of that reward event proportional to their balance/totalStaked ratio at that instant — with zero staking duration — while all pre-existing long-term stakers' share of that specific distribution is diluted by the enlarged denominator.

Crucially, unlike the literal "lock → unlock" sequence in the question, the attacker does not need to unlock afterward at all: `VLMGP.unlock` requires first calling `startUnlock` and then waiting `coolDownInSecs` before `unlock` succeeds (`if (slot.endTime > block.timestamp) revert StillInCoolDown();`) [8](#0-7) , so instant lock-then-unlock in adjacent transactions is not possible. However, this does not stop the exploit — the attacker can simply leave the MGP locked and later call the normal claim path (`getReward`/`getRewards`, routed through `masterMagpie`) to harvest the disproportionate `userRewards` balance that was already credited by the diluting `queueNewRewards` call, with no requirement to ever unlock.

No existing check mitigates this: `onlyManager` only gates who can call `queueNewRewards` (the reward depositor), not who can be staked when it executes; there is no minimum lock duration, no time-weighted average balance, and no per-second/streaming reward accrual mechanism (contrast with a linear vesting drip) that would make reward entitlement proportional to duration held.

### Impact Explanation
This is a theft/dilution of unclaimed yield: a large, adjacent-block flash-locker captures a share of a `queueNewRewards` distribution proportional to capital deployed for a single block, at the expense of stakers who held their position for the entire accrual period between distributions. This matches the "theft of unclaimed yield" impact class — genuine long-term lockers receive a smaller share of a specific reward drop than they otherwise would, and the attacker extracts value with negligible holding-duration risk (only requiring the capital to briefly lock, not to actually participate in governance/lock risk long-term).

### Likelihood Explanation
- Requires only unprivileged `lockFor` access and MGP token capital (no special roles) — the ATTACKER_ACTION preconditions are met.
- Requires visibility into the mempool for the `rewardManager`'s `queueNewRewards` transaction and standard front-running/priority-fee tooling to guarantee ordering ahead of it — routine on most EVM chains without private mempools.
- Capital efficiency depends on the ratio of attacker's lockable capital to existing `totalStaked()`; the larger the reward event relative to pool size, the more attractive the attack. This is repeatable for every `queueNewRewards` call the attacker can front-run, and capital is not locked away permanently (attacker can eventually unlock after the mandatory cooldown, or simply leave it locked and repeat the strategy on subsequent distributions).

### Recommendation
Replace the discrete, point-in-time `rewardPerTokenStored` bump with a duration-weighted/streaming accrual model (e.g., reward-rate-per-second drip similar to Synthetix `StakingRewards`, or snapshotting/ checkpointing balances with a minimum eligibility delay before a newly deposited balance can participate in a distribution). At minimum, introduce a lock-duration requirement (e.g., balance must have been staked prior to the block in which `queueNewRewards` is called, using a checkpointed balance rather than live `totalSupply()`/`balanceOf()`) so that reward shares reflect actual time staked rather than instantaneous balance at the exact block of distribution.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder` with a reward token, set `rewardManager`.
2. Have a long-term staker ("Alice") call `lockFor(100e18, alice)` and let time pass (no claims).
3. Simulate the reward manager preparing a `queueNewRewards(amountReward, rewardToken)` transaction (do not execute yet).
4. Have attacker ("Bob") call `lockFor(900e18, bob)` in the preceding transaction/block.
5. Execute `queueNewRewards(amountReward, rewardToken)`.
6. Assert: `rewardPerTokenStored` increment = `amountReward * 1e18 / 1000e18` (diluted by Bob's stake) rather than `amountReward * 1e18 / 100e18` (undiluted, what Alice would have earned alone).
7. Call `earned(bob, rewardToken)` and `earned(alice, rewardToken)`; assert Bob receives ~90% of `amountReward` (proportional to his 900/1000 balance) despite zero prior staking duration, while Alice's absolute reward from this event is reduced ~10x compared to the no-front-run baseline computed in step 3's hypothetical undiluted scenario.
8. Optionally show Bob can call `getReward`/harvest via `masterMagpie` immediately, without ever calling `startUnlock`/`unlock`, confirming yield extraction does not require completing the cooldown-gated unlock sequence.

    function queueNewRewards(uint256 _amountReward, address _rewardToken)
        override
        external
        onlyManager
        returns (bool)
    {
        if (!isRewardToken[_rewardToken]) {
            rewardTokens.push(_rewardToken);
            isRewardToken[_rewardToken] = true;
        }
        IERC20Metadata(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
        return true;
    }
