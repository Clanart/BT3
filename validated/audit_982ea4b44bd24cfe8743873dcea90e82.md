### Title
Value sent to the `distribution` precompile's `rewards()` view method is permanently stranded due to a missing non-payable check - ([File: precompiles/distribution/distribution.go])

### Summary
The `rewards()` method of the `distribution` Cosmos precompile (address `0x...1007`) is a read-only query but, unlike every other payable-guarded method in the same precompile, it never validates that `msg.value` is zero. A caller who mistakenly (or intentionally) attaches native value to a `rewards()` call has that value moved to the precompile's EVM address via the normal EVM value-transfer path, but the `rewards()` executor never touches, refunds, or forwards `value`, so the funds become permanently unrecoverable — mirroring the reported "ETH stuck due to missing non-payable/no-recovery function" bug class.

### Finding Description
In `precompiles/distribution/distribution.go`, `Execute()` dispatches state-changing methods with an explicit `pcommon.ValidateNonPayable(value)` guard (e.g. `WithdrawValidatorCommissionMethod`) [1](#0-0) . However, the `RewardsMethod` case dispatches directly to `p.rewards(ctx, method, args)` without any such check and without even passing `value` into the function: [2](#0-1) .

The `rewards()` implementation itself only performs a keeper query and packs the result — it never inspects, refunds, or forwards `value`: [3](#0-2) .

Other view methods in the same file (e.g. `validatorOutstandingRewards`, `params`, `validatorCommission`) explicitly receive `value` and call `p.validateInput(value, args, N)`, which enforces non-payable semantics — `rewards()` is the sole exception, confirmed by the precompile test-suite documentation itself: [4](#0-3)  and [5](#0-4) .

The `distribution` precompile address is not registered in the `payablePrecompiles` allowlist (only `bank`, `staking`, `gov`, `wasmd` are listed there) [6](#0-5) . That allowlist only controls suppression of ERC20-style transfer events; it does not gate whether the EVM's native value transfer occurs. Regardless of this list, the EVM's generic `CALL`-with-`value` semantics still move the wei/usei balance to the callee address via the StateDB balance primitives used elsewhere in the EVM/state layer for value transfers (e.g. `TransferWithoutEvents` in `x/evm/state/transfer.go`) [7](#0-6) . Because `rewards()` performs no `HandlePaymentUsei`/`HandlePaymentUseiWei` refund (unlike payable precompile methods such as `bank.sendNative`, which explicitly refunds the payer before debiting) [8](#0-7) , any value attached to a `rewards()` call is credited to the precompile's address balance and never returned to the caller nor consumed by chain logic — there is no admin/keeper function to sweep balances accidentally held at precompile addresses.

### Impact Explanation
Any EVM caller (an unprivileged transaction sender or a contract) who calls `rewards(address)` on the distribution precompile with a non-zero `msg.value` will have that usei/wei balance permanently and irrecoverably credited to the precompile's address, since:
- the precompile logic ignores `value` entirely for this method,
- no non-payable check reverts the call,
- there is no admin/sweep function to recover balances stranded at a precompile address.

This is a permanent freezing of user funds, matching the "Accept only concrete fund loss or permanent freezing" validation criterion.

### Likelihood Explanation
Likelihood is moderate: this requires a caller to mistakenly (or via a buggy integration/wallet) attach `msg.value` to what is documented and expected to be a free view/query call. Since `rewards()` is a commonly-used query (checking a delegator's accrued rewards) that developers might naively wrap in generic "payable" call boilerplate (many wallets/SDKs default to attaching value fields), accidental fund loss is plausible, and it is trivially reproducible by any EVM public RPC client.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` (or equivalent) check to the `RewardsMethod` case in `Execute()` in `precompiles/distribution/distribution.go`, consistent with how `params`, `validatorOutstandingRewards`, `validatorCommission`, and other view methods already enforce non-payability via `validateInput`/`ValidateNonPayable`. As defense in depth, consider adding a generic module/keeper-level sweep mechanism to reclaim any usei/wei balance that inadvertently accumulates at any precompile address.

### Proof of Concept
1. Deploy or use any EVM contract/EOA that can call the distribution precompile at `0x0000000000000000000000000000000000001007`.
2. Call `rewards(delegatorAddress)` and attach non-zero `msg.value` (e.g., `{ value: ethers.parseEther("1") }`), as noted explicitly in the precompile test suite comment that such a call "would succeed" [4](#0-3) .
3. The call succeeds and returns the rewards data; the attached value is transferred to the precompile address's balance.
4. There is no way to withdraw or recover this balance — repeated calls with value will keep accumulating funds at the precompile address, permanently locked.

```go
func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
```
