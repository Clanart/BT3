### Title
Blame proof leaks the ECDH decryption key before the message PoP is verified, enabling share decryption via key reuse - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` returns an `EncryptionKeyProof` (the ECDH shared key plus a DLEq proof of correctness) on the "non-canonical scalar" error path *before* the batch verification that validates the message's proof-of-possession ever runs. An attacker who reuses an honest participant's per-message public key can therefore force the victim to publish the ECDH key that decrypts the honest participant's original message — the exact attack the per-message PoP was added to prevent.

### Finding Description
In `Encryption::decrypt` the PoP is only *queued* into the `BatchVerifier` (`msg.pop.batch_verify(...)`, crypto/dkg/pedpop/src/encryption.rs:479-485), while the ECDH key is computed and the `EncryptionKeyProof` is constructed and returned unconditionally (encryption.rs:487-499).

In `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-499) the loop does:

1. `self.encryption.decrypt(...)` → returns `(share_bytes, blame)` where `blame` is the `EncryptionKeyProof`.
2. `C::F::from_repr(share_bytes.0)` fails → early `?` returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` at lib.rs:480-482.

Because this is an early return inside the loop, `batch.verify_with_vartime_blame()` at lib.rs:493 — the only place where a failed PoP is detected and where `BatchId::Decryption(l)` would correctly map to `blame: None` — is never reached. A message with an *invalid PoP* but a non-canonical plaintext scalar is therefore reported with `blame: Some(...)` instead of `blame: None`.

The PoP exists precisely to stop this: encryption.rs:84-91 documents that if Eve reuses Alice's per-message key X toward Bob, Bob's blame would reveal `bX`, decrypting Alice's real message. In the processor, `PedPoPError::InvalidShare` is converted to `ProcessorMessage::InvalidShare` with `blame: Some(blame.map(|b| b.serialize()))` and broadcast for public `VerifyBlame` adjudication (processor/src/key_gen.rs:419-425, 504-541). `decrypt_with_proof` does check the PoP first (encryption.rs:374-379), so Eve is correctly blamed — but the ECDH key `bX` has already been published, which is the secret-leaking side effect the PoP was meant to prevent.

### Impact Explanation
An attacker publishes a blame proof containing the ECDH shared key for a per-message key they do not own. Anyone observing the (authenticated/broadcast) channel can now decrypt the honest sender's encrypted secret share to the victim, disclosing a DKG secret share that was supposed to remain confidential between the two parties. Disclosure of secret shares undermines the confidentiality of the generated threshold key and is precisely the "massive side effect" the code comments warn about (encryption.rs:88).

### Likelihood Explanation
Requires the attacker to be a DKG participant (or able to submit shares to one) and to observe a victim's per-message public key on the share channel — both explicitly within the documented threat model (encryption.rs:84-91, spec Distributed Key Generation.md "Blame" section). The malicious message is trivially constructible: copy the victim's `key` field, attach any invalid Schnorr PoP, and supply ciphertext that decrypts under the known-key construction to a non-canonical scalar (e.g., all-`0xFF` repr, as in `invalidate_share_serialization`). No collusion or protocol-level access is needed beyond sending one crafted `EncryptedMessage`.

### Recommendation
Do not emit the `EncryptionKeyProof` until the PoP has been verified. Concretely, in `calculate_share` either:

- verify each `msg.pop` immediately (non-batched) before producing/returning `blame`, or
- defer the `from_repr` early-return until after `batch.verify_with_vartime_blame()` has run, so that a `BatchId::Decryption(l)` failure (invalid PoP) is mapped to `blame: None` before any scalar-validity error can surface `Some(blame)`.

The same ordering must hold for any future caller that publishes `Encryption::decrypt`'s second return value before batch verification completes; ideally `decrypt` should not hand out the `EncryptionKeyProof` optimistically at all.

### Proof of Concept
1. Alice (`Participant 1`) runs `generate_secret_shares`, producing `EncryptedMessage { key: X, pop, msg }` to Bob (`Participant 2`) over the share channel, where `X = G*x`.
2. Eve (`Participant 3`) observes `X`. She builds `EncryptedMessage { key: X, pop: invalid_sig, msg: ct }` to Bob where `ct` is a ciphertext under the `cipher(context, ecdh)` keystream for an arbitrary key — since PoP verification is deferred, the plaintext only needs to deserialize-fail; simplest is `ct` that decrypts to all-`0xFF` bytes (non-canonical `C::F::Repr`).
3. Bob's `KeyMachine::calculate_share` calls `self.encryption.decrypt(...)`: Eve's garbage PoP is queued in `batch`, and `blame = EncryptionKeyProof { key: bX, dleq }` is produced (encryption.rs:487-499).
4. `from_repr` fails → lib.rs:480-482 returns `PedPoPError::InvalidShare { participant: 3, blame: Some(blame) }` before `batch.verify_with_vartime_blame()` runs → Eve's invalid PoP is never checked.
5. Processor serializes `blame` into `ProcessorMessage::InvalidShare` (key_gen.rs:419-425). `bX` is now public.
6. Anyone computes `cipher(context, bX)` and XORs it against Alice's original `msg` ciphertext → recovers Alice's secret share `f_alice(bob)`. Eve is later blamed in `VerifyBlame` (PoP check fails, `decrypt_with_proof` → `InvalidSignature` → sender at fault), but the share is already leaked.

Analogous to CVE-2020-15219: an error-handling path (invalid share) exposes internal sensitive material (the ECDH decryption key) to parties who should only learn "the sender is faulty".
