### Title
Unhandled `IndexError` in `is_clvm_canonical()`/`is_atom_canonical()` from a crafted `coin_spend` puzzle/solution can crash spend-bundle validation - ([File: chia/full_node/mempool_manager.py])

### Summary
`MempoolManager.validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))` and `is_clvm_canonical(bytes(coin_spend.solution))` directly on attacker-supplied bytes from every coin spend in a submitted spend bundle, with no length/bounds validation before indexing into the buffer, analogous to the GIMP DDS bug class (insufficient length validation of user-supplied data before it is consumed by a parser).

### Finding Description
`is_clvm_canonical()` and its helper `is_atom_canonical()` walk a raw CLVM byte buffer using a manually incremented `offset`, reading `clvm_buffer[offset]` and, inside `is_atom_canonical`, further advancing `offset` by `prefix_len` bytes to read length-prefix bytes: [1](#0-0) 

```
def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    ...
    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]
        ...
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            ...
            offset += atom_len
        if tokens_left == 0:
            break
    return offset == len(clvm_buffer)
``` [2](#0-1) 

`is_atom_canonical()` reads `clvm_buffer[offset]` and then loops `prefix_len` times doing `offset += 1; atom_len |= clvm_buffer[offset]` with **no check that `offset` stays within the bounds of `clvm_buffer`** before each index access. If a caller supplies a multi-token or pair opcode (`0xFF`/atom-with-length-prefix) at (or near) the very end of the buffer, indicating a length prefix or pair body that runs past the end of the buffer, `clvm_buffer[offset]` (or `[offset]` in the prefix loop) will raise a plain Python `IndexError` instead of returning `False`/being caught by any length check — there is no `try/except` and no explicit bounds test analogous to the parity checks used elsewhere in this codebase (e.g. `full_block_utils.py`'s `skip_bytes`/`skip_list`, which explicitly raise a descriptive `ValueError` when `n > len(buf)`).

This function is invoked unconditionally, per coin spend, directly on attacker-controlled bytes coming from a submitted `SpendBundle`: [3](#0-2) 

```
for coin_spend in new_spend.coin_spends:
    ...
    if not is_clvm_canonical(bytes(coin_spend.puzzle_reveal)) or not is_clvm_canonical(
        bytes(coin_spend.solution)
    ):
        return Err.INVALID_COIN_SOLUTION, None, []
```

`validate_spend_bundle()` is called from `add_spend_bundle()`, which is the RPC/network path used to admit any spend bundle a wallet, offer counterparty, or unprivileged submitter provides to the mempool: [4](#0-3) 

There is no `try/except` around the `is_clvm_canonical` calls in `validate_spend_bundle`, nor in `add_spend_bundle`, so an `IndexError` raised here propagates as an unhandled exception rather than the intended, structured `Err.INVALID_COIN_SOLUTION` rejection.

### Impact Explanation
This is directly analogous to the CVE-2023-44441 bug class: a length/offset value taken from user-controlled input is trusted to index/copy from a buffer without validating that the resulting index stays within bounds. In the GIMP case that produced a heap overflow (native memory corruption); in this Python codebase the equivalent lack of bounds checking produces an unhandled `IndexError` instead of a `ValueError`/graceful rejection. Because `is_clvm_canonical` is reached for every coin spend before any other CLVM cost/signature validation, a single unprivileged spend-bundle submission with a crafted puzzle_reveal or solution (an atom-encoding or pair token placed such that its declared prefix/length runs past the actual buffer length) can throw an uncaught exception out of `validate_spend_bundle()`/`add_spend_bundle()`. Depending on how the calling code (full-node RPC/mempool admission task) handles unexpected exceptions, this can manifest as a spend-triggered processing halt/crash of the validation path for that bundle (denial of transaction processing), rather than the intended `INVALID_COIN_SOLUTION` rejection — this matches the "spend-triggered transaction-processing halt" impact category explicitly in scope.

### Likelihood Explanation
High reachability: this code executes for every coin spend in every spend bundle submitted to a full node's mempool (via the standard wallet/offer/RPC submission path), requiring no privilege beyond being able to submit a spend bundle. Constructing the malformed puzzle_reveal/solution bytes only requires crafting a CLVM buffer with a valid opcode byte but a truncated/absent length-prefix tail (e.g., ending the buffer right after an atom-length-prefix opcode byte such as `0xC0`–`0xFC`), which is trivial to produce.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()`/`is_clvm_canonical()` before every `clvm_buffer[offset]` access (both the initial byte read and the `prefix_len` loop), mirroring the pattern already used in `chia/full_node/full_block_utils.py` (`skip_bytes`/`skip_list`), and return `False`/raise a `ValueError` that is caught and translated into `Err.INVALID_COIN_SOLUTION` rather than allowing an `IndexError` to propagate. Additionally wrap the `is_clvm_canonical` calls in `validate_spend_bundle()` in a narrow `try/except (IndexError, ValueError)` as defense-in-depth so malformed input cannot escape as an unhandled exception.

### Proof of Concept
A `coin_spend.puzzle_reveal` (or `.solution`) whose serialized bytes end immediately after a multi-byte atom length-prefix opcode, e.g. `bytes.fromhex("f0")` (an `0xF0` opcode indicating a 3-byte length-prefix atom, `min_value` bracket needing `offset+1..offset+3` more bytes that don't exist) submitted as `puzzle_reveal` in a `CoinSpend`, causes `is_atom_canonical()`'s prefix loop to execute `offset += 1; ... clvm_buffer[offset]` with `offset >= len(clvm_buffer)`, raising `IndexError: index out of range`, which propagates unhandled out of `MempoolManager.validate_spend_bundle()` since no exception handling wraps the `is_clvm_canonical` checks at lines 723-726.

Note: I was unable to directly trace what happens to this unhandled `IndexError` further up the call stack (e.g., in the full-node RPC handler or the mempool-admission task loop) within the available index, so I cannot confirm with certainty whether it crashes the whole node process, only the single validation task, or is silently swallowed at a higher layer — this would need to be confirmed by reading the caller of `add_spend_bundle` (e.g. in `full_node.py`/`full_node_api.py`) in a full checkout of the repository.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
