Found a concrete analog. `Pallet::decode_receipt_relayer` in `modules/pallets/relayer/src/accumulate.rs` is used to attribute a delivery to a relayer for **both** the fee-accumulation path and the `outbound_request` delivery-claim path, but the two callers use it with different trust assumptions and only one of them cross-checks the result against a signature.

### Title
Unauthenticated `decode_receipt_relayer` output is trusted directly by `accumulate_fees`, letting anyone redirect a relayer's accrued fee payout - (`modules/pallets/relayer/src/accumulate.rs`)

### Summary
`decode_receipt_relayer` (`modules/pallets/relayer/src/accumulate.rs:322-351`) decodes the raw `RequestReceipts[commitment]` state-proof value into "the delivering relayer's bytes." For substrate destinations it accepts either a raw 32-byte public key **or** a SCALE-encoded `Signature` wrapper, from which it extracts `.signer()` — an unauthenticated field read (`modules/utils/crypto/src/verification.rs:109-115`), not a cryptographically recovered value. `signer()` simply returns whatever `public_key`/`address` bytes are embedded in the enum, with no proof that the embedded key actually produced any signature over anything.

In `process_outbound_request_delivery_claim` (`modules/pallets/relayer/src/outbound_request.rs`), this weakness is compensated for: `delivered_by` from `decode_receipt_relayer` is then checked against the *cryptographic recovery* of `signature.verify(&msg, None)`, so the claimant must actually control the private key.

But in `validate_results`/`accumulate_fee_and_deposit_event` (`modules/pallets/relayer/src/accumulate.rs:238-302, 353-368`), the exact same `decode_receipt_relayer` output is used as the final beneficiary key with **no subsequent signature verification** — `entry = result.entry(address)... *entry += fee;` directly credits `Fees::<T>::get(state_machine, address)` to whatever bytes were embedded in the substrate receipt.

### Finding Description
The relayer identity written into a substrate destination's `RequestReceipts[commitment]` during message delivery is whatever the destination chain's dispatch logic puts there. If that identity is ever recorded as a `Signature::Sr25519`/`Ed25519`/`Evm` wrapper containing an attacker-chosen `public_key`/`address` field alongside arbitrary (even all-zero, as shown in the pallet's own test `decodes_substrate_signature_wrapper`, `modules/pallets/testsuite/src/tests/pallet_ismp_relayer.rs:1731-1749`) signature bytes, `decode_receipt_relayer` will happily extract that embedded public key via `.signer()` with zero cryptographic verification, and `accumulate_fees` will credit the relayer-fee balance to that arbitrary key.

Contrast this with the outbound-request claim path, which was explicitly hardened to require `signature.verify(...)` to cryptographically match `delivered_by` before payout (`modules/pallets/relayer/src/outbound_request.rs:169-173`). The fee-accumulation path never received the equivalent binding — it treats the unauthenticated `.signer()` field as ground truth for whom to pay.

### Impact Explanation
If a delivery receipt on any substrate destination chain can end up storing a `Signature`-wrapper blob rather than a bare AccountId (e.g., through a module that writes signature metadata into its own receipt-equivalent storage, or any decode path that is fed attacker-influenced bytes), `accumulate_fees` will silently redirect the relayer fee for that delivered request to an address of the attacker's choosing — a false-beneficiary fund diversion with no signature check gating the actual payout, unlike the parallel `outbound_request` claim path that was hardened against exactly this.

### Likelihood Explanation
Exploitability is contingent on being able to influence the bytes committed at the receipt storage key that `accumulate_fees`'s state proof reads (`receipts_state_trie_key`) for a substrate destination — this is dependent on destination-chain-specific write paths that were not fully enumerated in this review, so the concrete injection vector could not be conclusively confirmed here. The structural issue (using `.signer()` with no matching `.verify()`) is nonetheless a real gap relative to the sibling `outbound_request` code that does bind payout to a verified signature.

### Recommendation
In `validate_results`/`accumulate_fee_and_deposit_event`, do not trust `decode_receipt_relayer`'s substrate `Signature`-wrapper branch as an authenticated beneficiary. Either: (a) restrict substrate receipts to bare AccountId bytes only (reject the `Signature` wrapper entirely at this call site), or (b) require the same cryptographic `signature.verify()` binding that `process_outbound_request_delivery_claim` enforces before crediting `Fees`.

### Proof of Concept
Conceptual, based on the pallet's own unit test fixture (`modules/pallets/testsuite/src/tests/pallet_ismp_relayer.rs:1731-1749`):
```rust
// decode_receipt_relayer accepts an unverified Signature wrapper and returns
// its embedded public key with no check that `signature` bytes are valid.
let forged = Signature::Sr25519 {
    public_key: ATTACKER_PUBKEY.to_vec(),
    signature: vec![0u8; 64], // never checked
};
let raw = forged.encode().encode();
let decoded = Pallet::<T>::decode_receipt_relayer(SUBSTRATE_DEST, &raw).unwrap();
assert_eq!(decoded, ATTACKER_PUBKEY.to_vec()); // accepted with no signature check
```
If this `raw` blob is what ends up proven at the destination's receipt slot for a delivered request, `validate_results` -> `accumulate_fee_and_deposit_event` will credit `Fees::<T>::get(dest_chain, ATTACKER_PUBKEY)` with the fee owed to the real delivering relayer, with no signature verification step analogous to `outbound_request.rs`'s `OutboundRequestSignerMismatch` check.
