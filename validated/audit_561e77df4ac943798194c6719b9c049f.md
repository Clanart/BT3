## Title
Division-before-multiplication in NFT royalty computation causes systematic underpayment to royalty recipients during offer settlement - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()` in `chia/wallet/nft_wallet/nft_wallet.py` performs an integer division (`// royalty_split`) *before* multiplying by `percentage`, and only divides by `MAX_ROYALTY_BASIS_POINTS` last. Because Solidity-style integer truncation compounds each time a division is applied before a subsequent multiplication, this ordering discards more precision than necessary and produces a smaller royalty amount than the mathematically correct multiply-first calculation. This directly parallels the reported Pool.sol issue: performing division before multiplication is equivalent to dividing twice, amplifying truncation loss.

### Finding Description
The vulnerable code is: [1](#0-0) 

```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```

The correct order to minimize truncation loss is multiply-first, divide-last:
`abs(offered_amount) * percentage // MAX_ROYALTY_BASIS_POINTS // royalty_split`.

With the current (buggy) order, `abs(offered_amount) // royalty_split` truncates first, discarding up to `royalty_split - 1` units of the offered amount before the percentage is even applied. This lost precision is then further compounded by the second `// MAX_ROYALTY_BASIS_POINTS` truncation. For example, with `offered_amount=10`, `royalty_split=3`, `percentage=3333` (33.33%):
- Current buggy order: `10 // 3 = 3`, `3 * 3333 = 9999`, `9999 // 10000 = 0`
- Correct order: `10 * 3333 = 33330`, `33330 // 10000 = 3`, `3 // 3 = 1`

The buggy calculation returns `0` while the correct one returns `1` — royalty recipients are shorted.

The same pattern also appears in the display-only `royalty_calculation()` helper: [2](#0-1) 

`compute_royalty_amount()` is called from `NFTWallet.make_nft1_offer()`, the code path used whenever a wallet user constructs an offer that includes royalty-enabled NFTs split across multiple parties: [3](#0-2) 

This is directly reachable by any offer counterparty (an unprivileged wallet user creating an NFT offer with `royalty_split > 1`, i.e., multiple NFTs traded together against one fungible payment), matching the allowed "offers and trades" attack surface.

### Impact Explanation
Because the royalty payment amount is computed once and baked into the settlement `CreateCoin` output for the royalty address, the systematic under-truncation causes the NFT creator/royalty holder to receive strictly less than their entitled percentage whenever `royalty_split > 1`. The shorted mojos remain with the offering party instead of being paid out — this is a concrete value-diversion ("offer settlement theft") from the royalty recipient to the offer counterparty, not merely a display/estimation inaccuracy. The magnitude grows with `royalty_split` and can fully zero out small royalty payments that should have been non-zero (as shown in the `10`-mojo example above), and scales proportionally for larger trades.

### Likelihood Explanation
Any user constructing a multi-NFT offer that splits royalty payments (`royalty_split > 1`) with `royalty_calculation`/`compute_royalty_amount` in the code path triggers this every time; no privileged access or malicious peer behavior is required — it is a pure computation defect exercised by normal offer-construction usage.

### Recommendation
Reorder the arithmetic to multiply before dividing, dividing by the largest divisor last:
```python
amount = abs(offered_amount) * percentage // MAX_ROYALTY_BASIS_POINTS // royalty_split
```
Apply the same fix to the `royalty_calculation()` display helper at `chia/wallet/nft_wallet/nft_wallet.py:853` for consistency between quoted and actually paid royalty amounts.

### Proof of Concept
```python
from chia.wallet.nft_wallet.nft_wallet import compute_royalty_amount

# royalty_split = 3, percentage = 33.33%
result = compute_royalty_amount(offered_amount=-10, royalty_split=3, percentage=3333)
print(result)  # returns 0 due to early truncation from // royalty_split

# Multiply-first order would yield 1:
correct = (abs(-10) * 3333 // 10000) // 3
print(correct)  # 1
```

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
