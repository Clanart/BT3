### Title
`ThresholdKeys::read` accepts semantically inconsistent shares, producing a group key no coalition can sign for - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation coefficients, the secret share, and the `n` verification shares entirely from attacker-supplied bytes, then calls `ThresholdKeys::new`, which validates only counts and index bounds — never that `secret_share * G == verification_shares[i]` nor that the verification shares/constant-interpolation coefficients are mutually consistent. The group key is then derived as `sum_{i=1..=t} verification_shares[i] * l_i`. An untrusted blob therefore materializes keys whose reported `group_key()` is unanchored from any actual secret sharing, so funds sent to the reported key are permanently unspendable.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` (lines 574-632) reads all parameters and all curve/scalar material from the reader. `ThresholdKeys::new` (lines 349-391) checks only `verification_shares.len() == n` and `participant <= n`, computes `group_key` from `verification_shares[1..=t]`, and returns the keys without verifying:

1. The loaded `secret_share` actually corresponds to `verification_shares[i]` (i.e., `C::generator() * secret_share == verification_shares[i]`).
2. For `Interpolation::Constant`, that the `n` coefficients read from the stream are the genuine polynomial coefficients for the sharing (any vector of `n` scalars is accepted).
3. Any MAC/commitment binding the blob to a previously established sharing.

The codebase itself acknowledges the consequence: `AlgorithmSignatureMachine::complete` in `crypto/frost/src/sign.rs` (lines 491-494) returns `FrostError::InternalError("everyone had a valid share yet the signature was still invalid")` with the comment that "the only known way to cause this ... is to deserialize a semantically invalid FrostKeys" — confirming the invariant exists but is never enforced at deserialization.

This is the analog of the Flowise injection bug (untrusted input silently interpreted as meaningful state): crafted bytes are loaded as authoritative key material and drive downstream protocol execution (address generation, scanning, signing) without integrity checks.

### Impact Explanation
A node that loads a crafted `ThresholdKeys` blob computes and reports `group_key()` derived from attacker-chosen verification shares and interpolation coefficients. That key does not correspond to the discrete log of any `t`-of-`n` combination of the secret shares held by the (honest) participants. Outputs addressed to the reported key are detected as received yet no signing set can ever produce a valid signature for them — the "funds reported received that are not spendable" impact. Because `sign_share`/`complete` only detects the inconsistency after a full threshold signing round fails (and even then mis-attributes it to an internal error or blame search), the funds are bricked rather than merely delayed. Severity: Medium–High (loss of funds' spendability for the validator set; no direct key extraction).

### Likelihood Explanation
Reachability requires an untrusted party to supply the serialized key blob read via `ThresholdKeys::read` — exactly the byte-driven path the in-scope rules allow for `read_*` APIs. There is no cryptographic check anywhere in the read path that would reject an inconsistent blob, so the attack succeeds deterministically whenever such input is accepted (key import/recovery/migration paths). It is not exploitable by a mere signing-session peer (preprocesses and shares are checked), which keeps likelihood moderate rather than high.

### Recommendation
In `ThresholdKeys::new` (or at the end of `read`), enforce:

- `C::generator() * secret_share == verification_shares[&params.i()]` (reject otherwise).
- For `Interpolation::Constant`, verify the coefficients are consistent with the verification shares (e.g., that each share's verification point matches evaluation of the committed polynomial), or drop constant coefficients from the wire format if they are recomputable.
- Optionally bind serialized keys to an authenticated commitment (hash of the DKG transcript) so blobs cannot be swapped across sessions.

### Proof of Concept
Construct a blob for a `t=2, n=2, i=1` key set:

```text
id_len || C::ID || t=2 || n=2 || i=1 || interp=1 (Lagrange)
|| secret_share = a (any scalar)
|| verification_shares[1] = G*b1  (with b1 != a)
|| verification_shares[2] = G*b2
```

`ThresholdKeys::read` accepts it: `ThresholdParams::new` passes, share count matches, indices valid. `group_key()` returns `b1*l1*G + b2*l2*G` = `G*(b1*l1 + b2*l2)`. The holder's share `a` does not satisfy `a*G == verification_shares[1]`, so even a full `2-of-2` signing set yields shares that verify individually against their stated verification shares but cannot reconstruct a signature under a consistent secret — `complete` hits the `InternalError` branch at `crypto/frost/src/sign.rs:491-494`. Any funds sent to `group_key()` derived from these shares while a sibling node loaded a divergent blob (different `b1`, `b2`) are unspendable.
