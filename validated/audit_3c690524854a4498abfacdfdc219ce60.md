### Title
Attacker-controlled pull-request `clone_url` is passed unvalidated into `git remote add` / `git fetch`, allowing protocol/argument-smuggling via a malicious fork - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user opens a pull request from a fork (either via the in-app PR list or via the `x-github-client://openRepo/...?pr=NNN` deep link), Desktop takes the `head.repo.clone_url` field returned by the GitHub API for that PR and feeds it directly into `git remote add` and subsequently `git fetch`, without validating that the value is a well-formed `https://`/`git@` URL. Because a PR's head repository can belong to any attacker-controlled account, the attacker fully controls the string that ends up as an argument to Desktop's `git` invocations.

### Finding Description
The flow is:
1. `dispatcher.ts`'s `openPullRequestFromUrl` fetches the PR via the API and forwards `pullRequest.head.repo.clone_url` straight to `appStore._checkoutPullRequest` [1](#0-0) .
2. `_checkoutPullRequest`/`_findPullRequestBranch` take that `headCloneUrl` and, if no existing remote matches it, call `addRemote(repository, forkRemoteName, headCloneUrl)` [2](#0-1) .
3. `addRemote` shells out with `git(['remote', 'add', name, url], ...)` — the `url` argument is taken verbatim, with no scheme allow-list, no rejection of `ext::`/`fd::`/leading-dash values, etc. [3](#0-2) .
4. The remote is then fetched via `_fetchRemote` → `performFetch` → `gitStore.fetchRemote` → `fetch()` in `app/src/lib/git/fetch.ts`, again just forwarding `remote.name` to `git fetch` [4](#0-3) .
5. `envForRemoteOperation`, which builds the environment for these git invocations, only sets authentication and (for `http(s)://`) proxy variables; it never sets `GIT_ALLOW_PROTOCOL` or otherwise restricts which git transport helpers may run [5](#0-4) .

The origin-side entry point (deep link `openrepo`) is validated only for `pr`/`branch`/`filepath` shape — the repository `url` itself is passed through unmodified as `parsedPath` with no scheme/format check [6](#0-5) . Combined with `openPullRequestFromUrl` calling `fetchPullRequest(url, pr)` against whatever host is embedded in the link and then trusting the API's own `clone_url` field for the head repo, this is a case where a value fully controlled by an attacker-served/forked GitHub API object (analogous to the omnichain "srcChainSender" — a value assumed trustworthy because it came from a "protocol" round trip, but actually attacker-supplied) flows unguarded into a local, security-relevant git operation.

This differs from the generic clone-destination-path hardening already present (`isClonePathSensitive` in `app/src/lib/git/clone.ts`), which defends only the *local path*, not the *remote URL* used for `remote add`/`fetch` in the PR-checkout path.

### Impact Explanation
If Git (as bundled/dugite-shipped or the user's system git) has any transport helper enabled that can be reached from a crafted `clone_url` (e.g. an `ext::` helper, or a URL that resolves through a locally configured credential/protocol helper in unusual ways), an attacker who merely opens a pull request against a public repo (or crafts a `github-mac://openRepo/...?pr=NNN` link with a malicious PR) could get Desktop to run `git remote add`/`git fetch` against a value they fully control, potentially achieving command execution outside the sandboxed renderer or reading/writing files outside the intended repository, without the victim doing anything more than opening the PR link/dialog inside Desktop. This lands squarely in the "attacker controls a GitHub API object or a link the user clicks, resulting in code execution or file access outside the repo" impact category.

### Likelihood Explanation
Exploitability depends on whether the specific dugite/git binary bundled with the analyzed Desktop build treats `ext::`/similarly dangerous URL schemes as enabled by default (recent upstream Git disabled `ext`/`fd` by default unless `GIT_ALLOW_PROTOCOL` explicitly allows them). I was not able to verify from the codebase which git version dugite bundles or whether it compiles in a stricter protocol allow-list, and there is no local guard (`GIT_ALLOW_PROTOCOL` or a `clone_url` scheme check) that would make this Desktop-side mitigation independent of the bundled Git version. This is the primary uncertainty limiting a definitive confirmation of exploitability; the missing application-level validation itself is confirmed and directly traceable in the code.

### Recommendation
Validate `headCloneUrl`/`clone_url` (and the `openrepo` deep-link `url` parameter) against a strict allow-list of expected schemes (`https://`, `git://`, `ssh://`, or `user@host:path` SCP-like syntax) before it is ever passed to `addRemote`/`git fetch`/`git clone`, and additionally set `GIT_ALLOW_PROTOCOL=http:https:ssh:git` in `envForRemoteOperation` so that even if an unexpected value reaches Git, transport helpers like `ext::`/`fd::` cannot be invoked regardless of the bundled Git's compiled-in defaults.

### Proof of Concept
Not independently reproducible from the indexed code alone — reproduction requires confirming which dugite/git binary version and its `protocol.*.allow` compile-time defaults are bundled, which was not available via the code index. Conceptually: create a pull request (or craft a `github-mac://openRepo/<encoded-attacker-url>?pr=1` link) whose head repository's `clone_url` (or the deep link's own url) is set to a git transport-helper URI (e.g. `ext::sh -c "id>/tmp/pwned"`); have the victim open it from Desktop's "Open in Desktop" flow, triggering `openPullRequestFromUrl` → `_checkoutPullRequest` → `addRemote`/`fetch` with the attacker-controlled string, since no scheme validation exists at any step in this path.
