I'll check the FROST signing path for the closest in-scope analog (value/inputs accepted but not bound/consumed), plus the Bitcoin send path.### Title
`SignableTransaction::new` accepts an OP_RETURN `data` output but excludes it from fee and weight accounting, producing underpriced/potentially nonstandard transactions - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The external report describes a payable function accepting value through two channels (ETH via `msg.value` and WETH via `pullToken`) while only crediting one, leaving the excess stranded and sweepable by anyone. The analog in Serai is in `SignableTransaction::new`: a transaction output channel (the OP_RETURN `data` output) is accepted and committed into the signed transaction, yet is entirely omitted from the weight/vbyte/fee computation and the maximum-standard-weight check. The signed artifact therefore carries unaccounted-for output weight, so the multisig signs a transaction whose actual fee rate is lower than the `fee_per_vbyte` the caller specified and which can exceed `MAX_STANDARD_TX_WEIGHT` while passing the size check.

### Finding Description
`SignableTransaction::new` builds `tx_outs` from `payments`, then pushes an additional OP_RETURN output when `data` is `Some` (`send.rs:194-202`). However, both calls to `calculate_weight_vbytes` pass only `payments` — never the data output: [1](#0-0) [2](#0-1) 

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` is computed on a transaction image that lacks the OP_RETURN output (`send.rs:204-206`). The actual serialized transaction is larger than what the fee covers.
2. The change computation `input_sat - (payment_sat + fee_with_change)` uses the underestimated `fee_with_change`, so the change output silently absorbs the missing fee; the realized fee rate is strictly below `fee_per_vbyte`.
3. The `MAX_STANDARD_TX_WEIGHT` check at `send.rs:241` runs against the underestimated `weight`, so a transaction whose real weight exceeds the standardness limit can be constructed and signed.
4. The `TooLowFee` minimum-relay check (`send.rs:211`) is likewise evaluated against understated vbytes, so a transaction can pass the check while its true fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE`.

The `data` bytes are caller-supplied (up to 80 bytes, `send.rs:171`), i.e., exactly the "transaction data they cause to be signed" channel. Because `TransactionSignMachine::sign` commits all prevouts (`Prevouts::All`, `send.rs:375`) into each input's taproot sighash, the threshold group produces a signature over this malformed transaction. [3](#0-2) 

### Impact Explanation
The multisig signs a transaction that (a) pays less fee per actual vbyte than requested — potentially below the mempool minimum relay fee, making it unbroadcastable — or (b) exceeds the standardness weight limit while the constructor claimed it was valid. In either case the signed transaction cannot confirm, and the FROST signing session (which cannot reuse its preprocesses across messages) has committed threshold signature shares to an unusable transaction. This mirrors the report's "the contract accepted resources it never credited" shape: the OP_RETURN output's cost is accepted but never accounted, and the discrepancy is silently dumped into change/fee rather than rejected.

### Likelihood Explanation
Any path that passes `Some(data)` to `SignableTransaction::new` triggers it deterministically (no race or adversarial timing needed); the underestimation is proportional to the data length, and the weight-check bypass requires the payment/change footprint to already be near the limit. The processor currently calls `SignableTransaction::new` with `data: None`, so realized impact in the shipped configuration is limited, keeping this at Medium rather than High.

### Recommendation
Include the OP_RETURN output (and the change output) in the transaction image used by `calculate_weight_vbytes` — e.g., compute weight over the final `tx_outs` plus the prospective change — so `needed_fee`, the `TooLowFee` check, the change amount, and the `TooLargeTransaction` check all reflect the transaction actually signed. Alternatively, pass the fully-constructed `Transaction` to the weight helper instead of reconstructing it from `payments`.

### Proof of Concept
```rust
// networks/bitcoin: given inputs, payments, change, and data
let data = vec![0u8; 80];
let st = SignableTransaction::new(inputs, &payments, change.clone(), Some(data.clone()), fee)
  .unwrap();
// st.needed_fee() == fee * vbytes(inputs, payments[, change])
// but st.transaction().output contains an extra OP_RETURN output (~90 bytes),
// so st.fee() covers a strictly smaller transaction than st.transaction().
// With weight near MAX_STANDARD_TX_WEIGHT, `new` returns Ok while the
// resulting Transaction exceeds the standardness limit.
```
The fix verification: `st.transaction().weight()` and `st.vsize()` must equal the values used internally for `needed_fee` and the weight check, including the OP_RETURN output.
