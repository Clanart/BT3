### Title
Attacker-supplied proof map with a missing participant index panics `GeneratorPromotion::complete` via `unwrap()` - (File: crypto/dkg/promote/src/lib.rs)

### Summary
The referenced CVE (panic in Go's `crypto/elliptic` on malformed input) is a remotely-triggerable panic/DoS class. The same class exists in Serai's DKG promotion path: `GeneratorPromotion::complete` validates only the *count* and the *upper bound* of the `proofs` map it receives, then unconditionally calls `proofs.get(&i).unwrap()` for every expected participant index. A map that passes both checks but omits a required participant index (e.g., by additionally containing `params.i()` — the local participant — which is never rejected) causes a panic, crashing the process during a key-rotation/promotion session driven by untrusted peer messages.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs these checks on the peer-supplied `proofs: &HashMap<Participant, GeneratorProof<C1>>`: [1](#0-0) 

It verifies `proofs.len() == n - 1` and that every key satisfies `key <= n`. It does **not** verify that the key set equals exactly `{1..=n} \ {params.i()}`. In particular, a key equal to `params.i()` (the local participant, who never submits a proof) is accepted by the bound check.

The loop then does: [2](#0-1) 

For each `i in 1..=n` with `i != params.i()`, it calls `proofs.get(&i).unwrap()`. If the supplied map has length `n - 1`, all keys `<= n`, but contains `params.i()` and therefore omits some `j != params.i()`, `proofs.get(&j)` returns `None` and `.unwrap()` panics.

Concrete example: `n = 3`, `params.i() = 1`. A `proofs` map keyed `{Participant(1), Participant(2)}` passes `proofs.len() == 2` and the `key <= 3` bound check. The loop reaches `i = 3`, calls `proofs.get(&Participant(3))`, gets `None`, and panics.

### Impact Explanation
A panic during `GeneratorPromotion::complete` aborts the promotion procedure by unwinding (or aborting under `panic = abort`). Promotion is used to migrate existing threshold keys to a new generator — a routine invoked when networks re-key. Crashing honest nodes mid-promotion denies service and can leave validators unable to participate in the migrated key set, stalling signing for the affected network. This mirrors the CVE class exactly: a panic reachable during processing of inputs supplied by other protocol participants.

### Likelihood Explanation
Reachability depends on how the caller constructs the `proofs` map. If the integrator keys proofs by a claimed/parsed participant index rather than strictly by authenticated sender identity, an unprivileged participant can submit a malformed bundle (e.g., a promotion payload tagged with the victim's own index, or a duplicated index that displaces a legitimate entry) that produces a map passing both checks while missing a required index. Even absent a malicious peer, deserialization/aggregation errors that produce the same key set cause the crash. The function's own validation is provably incomplete: it never checks `i != params.i()` for map keys, and the subsequent `unwrap()` is documented by its own panic.

Note: if the integrator guarantees keys are strictly `sender_id` and the transport enforces unique senders in `{1..=n} \ {i}`, the panic is unreachable — that assumption is undocumented and unenforced in this crate.

### Recommendation
Replace the `unwrap()` with an explicit validation pass before consuming proofs:

- Reject any `proofs` key equal to `params.i()` or `> n` (add `InvalidParticipant` for `params.i()`), or
- For each `i in 1..=n` with `i != params.i()`, use `proofs.get(&i).ok_or(PromotionError::MissingProof(i))?` instead of `.unwrap()`.

Validating the exact expected key set (`proofs.keys().collect::<HashSet<_>>() == (1..=n).filter(|i| *i != params.i())`) closes the gap completely.
