### Title
Unauthenticated cross-shop session access via unauthenticated `shop` param trust in `EnsureInstalled` (legacy, non-token-exchange path) - (File: `app/controllers/concerns/shopify_app/ensure_installed.rb`)

### Summary
When `ShopifyApp.configuration.use_new_embedded_auth_strategy?` is `false`, `EnsureInstalled` derives `current_shopify_domain` purely from the sanitized `shop` query/POST parameter and uses it to fetch that shop's stored offline session via `installed_shop_session`, without any cryptographic proof (JWT/id_token, HMAC) that the requester actually represents that shop. `validate_non_embedded_session` only checks whether the shop's stored token is still valid against Shopify's API — it does not verify caller identity — so an unauthenticated attacker who simply knows or guesses a victim's `*.myshopify.com` domain can cause any `EnsureInstalled`-protected controller action to run with the victim's offline session loaded into `@shop`/`installed_shop_session`.

### Finding Description
`current_shopify_domain` only sanitizes the raw `shop` param format via `ShopifyApp::Utils.sanitize_shop_domain(params[:shop])`; it performs no verification that the caller controls that shop: [1](#0-0) 

`installed_shop_session` then loads that shop's real, server-stored offline session purely from this attacker-suppliable domain string: [2](#0-1) 

In the legacy (non-token-exchange) branch, the before_actions are `check_shop_domain` → `check_shop_known` → `validate_non_embedded_session`: [3](#0-2) 

`check_shop_known` merely checks whether *some* session exists for that domain — again keyed only by the untrusted `shop` param: [4](#0-3) 

`validate_non_embedded_session` is the only remaining gate, but it validates the *token's* liveness against Shopify, not the *caller's* identity — it makes an Admin API call using the victim's own stored (real) offline token and only redirects if that token itself is stale (HTTP 401). If the victim's app installation is healthy (the normal case), this call succeeds and the action proceeds with the victim's session loaded: [5](#0-4) 

This is confirmed by the existing test fixture, which shows a request with only `shop: "shop1.myshopify.com"` (no proof of ownership — no id_token, no HMAC, no embedded session) being treated as a legitimate, authorized "installed" request and returning `:ok`: [6](#0-5) 

By contrast, the newer `TokenExchange`-based path (used when `use_new_embedded_auth_strategy?` is `true`) explicitly guards against exactly this class of attack by comparing the *requested* shop domain (from `params[:shop]`) against the *authenticated* shop domain derived from a verified Shopify ID token, rejecting mismatches with `head(:unauthorized)`: [7](#0-6) 

The legacy `EnsureInstalled` flow has no equivalent check — there is no code path in `ensure_installed.rb` that ties `current_shopify_domain`/`installed_shop_session` to any authenticated proof of the requester's identity (no `id_token` verification, no HMAC verification of the `shop`/`host` params, and `loaded_directly_from_admin?` merely checks `params[:embedded] == "1"`, itself attacker-controlled).

### Impact Explanation
Any application using `ShopifyApp::EnsureInstalled` with `use_new_embedded_auth_strategy?` disabled (the pre-token-exchange / classic OAuth mode, still supported and default-able in this gem) is exposed to cross-shop access: an unauthenticated attacker who supplies any real merchant's `.myshopify.com` domain in the `shop` param on any `EnsureInstalled`-protected GET route causes that merchant's offline session (and the real stored access token) to be loaded and used server-side for the request, and any shop-specific data the controller action renders is returned to the attacker's browser. This matches the "cross-shop access: loading/acting with another store's offline session" impact class.

### Likelihood Explanation
Exploitability requires only: (1) the app be configured with the legacy strategy (`use_new_embedded_auth_strategy?` false, historically the default/most common integration path for this gem), (2) knowledge of a target `myshopify.com` shop domain (often discoverable/public via storefront URLs, app listings, etc.), and (3) that target shop currently has a valid installed offline session (the normal, common state for an active merchant). No secrets, tokens, or victim interaction are required — a single unauthenticated GET request suffices. This is highly feasible and repeatable.

### Recommendation
In `EnsureInstalled` (legacy branch), do not trust `params[:shop]` alone to select/load a session. Require and verify an authenticated proof of shop identity (e.g., a Shopify session/ID token or HMAC-signed request) before calling `installed_shop_session`, and reject requests where the requested `shop` param does not match an authenticated domain — mirroring the `reject_mismatched_requested_shopify_domain` pattern already implemented in `ShopifyApp::TokenExchange`.

### Proof of Concept
Existing repo fixture demonstrating the trust boundary violation (attacker supplies only `shop`, no proof of ownership, and the request is treated as authorized):

```ruby
# test/controllers/concerns/ensure_installed_test.rb:54-67
test "returns :ok if the shop is installed" do
  session = mock
  ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain).returns(session)

  client = mock
  ShopifyAPI::Clients::Rest::Admin.expects(:new).with(session: session).returns(client)
  client.expects(:get)

  shopify_domain = "shop1.myshopify.com"

  get :index, params: { shop: shopify_domain }

  assert_response :ok
end
```

A regression fixture pinning the invariant ("loaded session must correspond to a proven caller, not a raw param") should instead assert this scenario is **rejected** absent any authentication proof — e.g., add:

```ruby
test "regression: unauthenticated shop param must not load another store's session" do
  victim_session = mock
  ShopifyApp::SessionRepository.stubs(:retrieve_shop_session_by_shopify_domain)
    .with("victim-shop.myshopify.com").returns(victim_session)

  get :index, params: { shop: "victim-shop.myshopify.com" }

  # Expected (fixed) behavior: reject/redirect because no proof the caller
  # controls victim-shop.myshopify.com was supplied.
  assert_response :redirect
  refute_equal victim_session, @controller.send(:installed_shop_session)
end
```
Currently this assertion fails, confirming the vulnerability.

    def current_shopify_domain
      authenticated_shopify_domain_from_token
    rescue *INVALID_SHOPIFY_ID_TOKEN_ERRORS => e
      respond_to_invalid_shopify_id_token(e)
    end

    private

    def authenticated_shopify_domain_from_token
      current_shopify_session&.shop || jwt_shopify_domain
    end

    def reject_mismatched_requested_shopify_domain
      requested_domain = requested_shopify_domain
      return false if requested_domain.blank?

      authenticated_domain = authenticated_shopify_domain_from_token
      return false if authenticated_domain.blank? || authenticated_domain == requested_domain

      ShopifyApp::Logger.debug("Shop context validation failed")
      head(:unauthorized)
      true
    end
