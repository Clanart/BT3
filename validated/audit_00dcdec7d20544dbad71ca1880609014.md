## Analysis

The core broken invariant in the external report is: **a caller-supplied optional field toggles off a security check that should be mandatory**, letting the corresponding action proceed as if the check passed. The closest local analog in Hyperbridge is in `pallet-hyper-fungible-token`'s `on_accept` handler, where the optional `SubstrateCalldata::signature` field controls whether the pallet actually verifies who authorized an arbitrary runtime-call dispatch.

### Title
Unsigned cross-chain calldata dispatch trusts unauthenticated `message.from` as the call origin - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`HyperFungibleToken::on_accept` allows an incoming cross-chain transfer to carry an optional ABI-encoded `SubstrateCalldata { signature, runtime_call }` payload that is dispatched as a runtime call. When `signature` is `Some`, the code cryptographically verifies the signer against the transfer `beneficiary` before using it as the dispatch origin. When `signature` is `None`, the pallet skips all verification and instead derives the dispatch origin directly from the unauthenticated `message.from` bytes carried in the cross-chain message body, then dispatches an arbitrary `runtime_call` as that origin.

### Finding Description
In `on_accept` [1](#0-0) , the calldata-execution branch computes an `origin`:

```rust
let origin = if let Some(signature) = substrate_data.signature {
    // ... verify Ed25519/Sr25519/Ecdsa signature against `beneficiary` ...
    beneficiary.clone()
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
...
runtime_call.dispatch(RawOrigin::Signed(origin.clone()).into())...
``` [2](#0-1) 

The signed branch is the only place any cryptographic proof of authorization is checked. The unsigned (`None`) branch performs **no** verification of ownership — it simply converts the wire-format `message.from` bytes into a substrate `AccountId` via `T::EvmToSubstrate::convert` and dispatches the runtime call as if that account had signed it. Whether this is exploitable depends entirely on whether the EVM-side sender contract enforces `message.from == msg.sender` when constructing the ABI-encoded body; nothing in this pallet enforces or re-validates that binding. Since the dispatched call only passes through `T::BaseCallFilter` [3](#0-2) , any allowed extrinsic (e.g. `Balances::transfer_allow_death`, as exercised in the pallet's own test) can be executed as the derived origin.

This is structurally the same bug class as the report: an attacker/dapp-controlled optional flag (`signature: None`) removes a security control (authenticated proof of the acting party) that the "signed" code path treats as mandatory, and the fallback path substitutes a weaker, unauthenticated identity source (`message.from`) for the thing that should have been verified.

### Impact Explanation
If the EVM-side `from` field is not strictly bound to `msg.sender` (or if it can otherwise diverge from the actual authorizing account, e.g. via a proxy/relay contract crafting the payload), an attacker could dispatch arbitrary permitted runtime calls (transfers, governance-permitted extrinsics, etc.) as a victim account, without ever presenting a valid signature — this is unauthorized execution / potential fund loss, matching the bounty's "unauthorized transaction or execution" and "stealing or loss of funds" categories.

### Likelihood Explanation
Exploitability is contingent on the EVM sender contract's guarantee about the `from` field, which I could not fully confirm from the retrieved snippets (the encoding side of `HyperFungibleToken.sol`'s `send` was not fully inspected in this pass). If `from` is always forced to `msg.sender` on the EVM side, the unsigned path only lets an attacker dispatch calls as their own EVM-mapped substrate identity — a self-inflicted, non-exploitable case. This uncertainty should be resolved by inspecting `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`'s `send`/message-construction logic to confirm whether `from` is caller-supplied or hard-bound to `msg.sender`, and whether any relayed/aggregated path could let `from` diverge from the true initiator.

### Recommendation
Require a valid signature (or an equivalent cryptographic proof binding the dispatch origin to the actual initiator) for **every** calldata-execution path, removing the unsigned fallback entirely — mirroring the report's recommendation to eliminate optional toggles that bypass verification. If the unsigned path must be kept for UX reasons, it should only be usable when the pallet can independently prove (not merely assume) that `message.from` equals the cryptographically authenticated sender on the source chain (i.e., enforced invariantly by the source contract and cross-checked here), and that guarantee should be documented and tested explicitly for both EVM and substrate sources.

### Proof of Concept
Conceptual PoC based on the pallet's own test harness [4](#0-3) :
1. Craft a `PostRequest` whose ABI-encoded `Message.data` contains a `SubstrateCalldata { signature: None, runtime_call: Balances::transfer_allow_death { dest: attacker, value: victim_balance }.encode() }`.
2. Set `Message.from` to the victim's 20-byte EVM address (if the source contract does not enforce `from == msg.sender`, or via any code path that lets the message body diverge from the authenticated sender).
3. Deliver the request through the normal ISMP path so `on_accept` is invoked; the pallet derives `origin = T::EvmToSubstrate::convert(victim_evm_address)` with **no signature check**, and dispatches the transfer as the victim, moving funds to the attacker.

This should be validated by inspecting the EVM-side `send()`/message construction to confirm whether `from` can be decoupled from `msg.sender` before treating it as a fully proven finding.
