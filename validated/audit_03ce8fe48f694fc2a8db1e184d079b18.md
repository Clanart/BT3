### Title
`cancelUnlock()` skips `updateTotalFactor`, permanently desynchronizing `totalBoostFactor` from real vlMGP locks - (File: `VLMGP.sol` / `rewards/ReferralStorage.sol`)

### Summary
`VLMGP.startUnlock()` calls `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` after moving tokens into cooldown, but `VLMGP.cancelUnlock()` — which reverses that exact state change and immediately raises `getUserTotalLocked()` — never calls it. This means `ReferralStorage.totalBoostFactor` and every affected `userInfo.factor` become permanently stale relative to the real, currently-locked vlMGP amounts, unless the user later triggers another `lock`/`lockFor`/`startUnlock` event.

### Finding Description
In `VLMGP.sol`, `startUnlock()` updates `userUnlockings[...].amountInCoolDown` and then explicitly reconciles the referral factor: [1](#0-0) 

`cancelUnlock()` performs the exact inverse of that state transition (`slot.amountInCoolDown = 0`, `totalAmountInCoolDown -= ...`), which increases `getUserTotalLocked()` immediately (since `getUserTotalLocked = amountInMasterMagpie - amountInCoolDown`), but it has no corresponding call into `ReferralStorage`: [2](#0-1) 

`ReferralStorage.updateTotalFactor()` is the only place that reconciles `totalBoostFactor` with per-user `factor = sqrt(getUserTotalLocked(account))`: [3](#0-2) 

Because `cancelUnlock` never invokes this function, a user (or referrer) who calls `startUnlock` (lowering their locked amount and correspondingly lowering `factor`/`totalBoostFactor`) and then calls `cancelUnlock` (restoring their real locked balance) leaves `userInfo.factor` and `totalBoostFactor` stuck at the lowered value indefinitely — until another `lock`/`lockFor`/`startUnlock` call happens to re-sync it. `totalBoostFactor` is a shared denominator used in `_calBoosted`: [4](#0-3) 

Since `totalBoostFactor` is understated relative to the true sum of live `sqrt(lock)` factors, `_calBoosted()` returns an inflated `boostesd` value for every account that still has a non-zero cached `factor`, which is used in `trigger()` to split each referee's reward between referer and referee: [5](#0-4) 

This breaks the stated invariant that `totalBoostFactor` must equal the sum of current per-user factors at all times.

### Impact Explanation
Because `_calBoosted` inflates `basic + boostesd` for referral reward splits, `trigger()` will consistently over-allocate `rewardAmount` to referrers/referees relative to the intended tiered/boosted percentage. Over repeated `trigger()` calls this can push cumulative `userInfos[*].rewardAmount` balances above what `MGP.balanceOf(address(this))` was actually funded to cover, since the token inflow backing `_amount` is external to this miscalculation. If the contract becomes under-collateralized, the earliest claimers via `claimReward()` succeed while later claimers experience reverting transfers, an effective freezing/loss of their unclaimed referral yield. This matches "Theft of unclaimed yield" in scope, though the magnitude depends on how frequently `trigger()` fires and how large the reward-splitting gap becomes, which in turn depends on `sharePercent`/tier configuration and usage patterns of `startUnlock`/`cancelUnlock`.

### Likelihood Explanation
`lockFor`, `startUnlock`, and `cancelUnlock` are all fully permissionless external functions reachable by any EOA/contract holding MGP and having registered a referral code (`registerCode`). No privileged role is required. The sequence `startUnlock()` → `cancelUnlock()` is trivially repeatable and costs only gas (cooldown does not need to complete since `cancelUnlock` can be called any time before `endTime`, per `_checkInCoolDown`). This makes the desync easy and cheap to trigger and to repeat indefinitely, growing the accounting drift over time.

### Recommendation
Call `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` inside `cancelUnlock()` (and any other state-changing function in `VLMGP.sol` that alters `getUserTotalLocked`, such as `forceUnLock`/`unlock`), mirroring the call already present in `startUnlock()`, so that `totalBoostFactor` and per-user `factor` are always resynchronized whenever the user's live locked balance changes.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `VLMGP`, `ReferralStorage`, mock `MasterMagpie`/MGP token; set `referralStorage` on `VLMGP` and `vlMGP` on `ReferralStorage`.
2. Have user A `registerCode()` on `ReferralStorage`, then `lock()`/`lockFor()` MGP into `VLMGP` so `userInfo.factor` and `totalBoostFactor` are initialized to `sqrt(lockedAmount)`.
3. Call `startUnlock(amount)` for user A; assert `totalBoostFactor` decreases to `sqrt(lockedAmount - amount)`.
4. Call `cancelUnlock(slotIndex)`; assert `getUserTotalLocked(A)` returns to the original `lockedAmount`, but `totalBoostFactor`/`userInfos[A].factor` in `ReferralStorage` remain at the post-`startUnlock` (lower) value — confirming the desync.
5. Simulate `trigger(referee, amount)` calls from a mock `masterMagpie` before and after the cancel-unlock sequence with identical `_amount`; compare `refererAmount`/`refereeAmount` computed in each run and show the post-cancel run yields a higher payout for the same underlying `_amount`, without any corresponding increase in `MGP.balanceOf(address(this))`.
6. Assert the invariant violation: `totalBoostFactor != sqrt(getUserTotalLocked(A)) + sum(other users' live factors)`.

    function updateTotalFactor(address _account) external override _onlyVlMGP {
        UserInfo storage userInfo = userInfos[_account];
        if (userInfo.myCode == bytes32(0)) return; // user did not activate referral feature
        
        totalBoostFactor -= userInfo.factor;
        uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
        userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);

        totalBoostFactor += userInfo.factor;
    }
