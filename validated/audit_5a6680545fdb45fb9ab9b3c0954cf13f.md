The refinance bug pattern — verifying one identity attribute (NFT address/tokenId) while omitting a second, security-relevant attribute (amount) that is not cryptographically bound to the first — has a direct structural analog in `shopify_app`'s webhook trust model: the shared-secret HMAC covers only the raw request body, while the shop attribution (`X-Shopify-Shop-Domain` header) used to route/attribute the webhook is never covered by that signature.

### Title
Webhook `shop_domain` is not bound to the HMAC signature, allowing cross-shop webhook attribution - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only that the HMAC over `request.raw_post` matches the shared app secret; it never binds or checks the `X-Shopify-Shop-Domain` header against that signature. [1](#0-0) 

### Finding Description
`hmac_valid?` computes the digest solely over the POST body (`data = request.raw_post`), using the app-wide shared secret configured in `ShopifyApp.configuration.secret`/`old_secret`. [2](#0-1) 
The `shop_domain` helper simply reads an unauthenticated header, and this same header (or the shop value parsed by `ShopifyAPI::Webhooks::Request`) is what apps are told to use to route webhook processing to the correct shop. [3](#0-2) 
The official documentation and generator templates both instruct apps to trust this header/value directly for dispatching per-shop background jobs: [4](#0-3) [5](#0-4) 

Because the app secret is shared across every shop that has the app installed (it is the app's client secret, not a per-shop key), any merchant with the app installed can obtain a validly-HMAC'd webhook body/signature pair for their own shop, then resend that same signed body to the webhooks endpoint while substituting the `X-Shopify-Shop-Domain` header (or equivalent shop value) for a *different, unrelated* shop's domain. `verify_request` still validates the HMAC successfully — because it never checked the domain at all — and the app proceeds to queue/execute the shop-specific job (e.g. `CartsUpdateJob`, or the mandatory privacy jobs like `ShopRedactJob`/`CustomersRedactJob`) using the attacker-supplied `shop_domain`, which is exactly the same class of bug as the Kettle.sol report: one field (NFT id / HMAC) is checked, a second, independently-attacker-controllable field (amount / shop domain) that should have been bound to the first is not. [6](#0-5) 

### Impact Explanation
An attacker who is a legitimate but unrelated merchant of the same app can cause the app to process attacker-controlled webhook payloads under a victim shop's identity — e.g. triggering redact/data-request handling, or any custom job built per the documented pattern (`SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`) — for a shop they have no relationship to. This is a cross-shop attribution/spoofing issue: the app will accept a validly-signed webhook and misattribute its (attacker-chosen) body to whichever `shop_domain` value the attacker supplies.

### Likelihood Explanation
Exploitation requires only that the attacker be an installed, unrelated merchant of the target app (no secret leak needed — everyone with the app installed receives real HMACs signed with the same app secret over bodies they fully control from Shopify's real triggers, and headers are trivially replayable/forgeable in a replay/relay attack since they are outside the signed data).

### Recommendation
Bind the shop domain to the signed payload before trusting it: either verify that the shop referenced in the header matches a shop value embedded/signed within the verified body (where Shopify includes one), or otherwise incorporate the shop domain into the HMAC verification step in `PayloadVerification`/`WebhookVerification`, rejecting requests where the header-derived shop cannot be cryptographically tied to the verified payload.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`.
2. Capture a real webhook delivery: valid `X-Shopify-Hmac-Sha256` header + raw body, both generated by Shopify using the app's shared secret.
3. Replay this exact HMAC + body to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `verify_request` in `lib/shopify_app/controller_concerns/webhook_verification.rb` validates the HMAC successfully (it only checks the body), and the controller/job dispatch uses `shop_domain` (now `victim.myshopify.com`) to route processing — e.g. into `victim`'s privacy job, order job, or any custom job — even though the body content and event originated from the attacker's own shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
