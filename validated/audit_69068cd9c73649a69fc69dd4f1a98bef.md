This confirms the point-at-infinity encoding (`0xc0` + zero bytes) is explicitly the spec-defined `PointAtInfinity`/`G1_POINT_AT_INFINITY` constant [1](#0-0) , and the official consensus-spec test vectors for `verify_kzg_proof` include multiple cases with `proof` or `commitment` set to this exact infinity encoding, expecting `output: true` for genuinely valid openings (e.g. zero polynomial, or the "twos poly" cases) and `output: false` when the opening is not true [2](#0-1) [3](#0-2) . This is exactly aligned with the consensus-specs `validate_kzg_g1` semantics, which explicitly special-cases and accepts `G1_POINT_AT_INFINITY` as valid before running `KeyValidate` on any other bytes.

`deserializeG1Point` delegates directly to `bls12381.G1Affine.SetBytes` [4](#0-3) , which is gnark-crypto's standard canonical compressed-point deserialization. In the ZCash/IETF BLS12-381 compressed serialization format that this library and the spec both use, the byte pattern `0xc0` followed by all-zero remaining bytes is the unique canonical encoding of the identity element (compression flag + infinity flag set, no coordinate data). `SetBytes` accepts this single canonical infinity pattern and rejects any other combination of the infinity flag with non-zero remaining bytes as non-canonical, so `Serialize(Deserialize(b)) == b` holds for this input and no second, non-canonical encoding of infinity is accepted.

Because the identity element trivially belongs to the prime-order subgroup, accepting it as a "valid" deserialization is not a deviation from `validate_kzg_g1`—it is required by it. Whether the resulting `VerifyKZGProof` call returns `true` or `false` is then decided purely by the actual pairing equation in `kzg.Verify` [5](#0-4) , which the official test vectors show correctly returns `true` only for genuine openings and `false` for forged ones, even when one of the points involved is the point at infinity. There is no forged proof being accepted here—only mathematically true openings involving the identity element pass.
