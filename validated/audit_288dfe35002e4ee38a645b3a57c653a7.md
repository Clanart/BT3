This is a strong, confirmed finding: the `commits` list computed by a stale/name-matched rebase preview is passed directly into `dispatcher.startRebase` and used by `appStore._rebase` to drive the actual rebase (cherry-pick) operation, not merely displayed as UI text — so a stale preview does translate into a corrupted git operation.

### Title
Rebase preview computed against a stale branch tip is used to drive the actual rebase operation - (File: `app/src/ui/lib/update-branch.ts`)

### Summary
`updateRebasePreview` guards against races only by comparing the **branch name** captured at call time (`computingRebaseForBranch !== baseBranch.name`), not the branch's `tip.sha` [1](#0-0) . If a branch's tip moves (e.g., after a `fetch`/pull from a remote that force-updates a ref) while a preview computation for that same branch name is in flight, or while a stale computation is still pending after the user re-selects the same branch, the resulting `commitsAhead`/`commitsBehind` list — computed from the earlier, now-obsolete `baseBranch.tip.sha` — is accepted and stored in state as if it reflected the branch's current tip.

### Finding Description
`updateRebasePreview` snapshots `baseBranch.tip.sha` and `targetBranch.tip.sha` up front, computes `commitsBehind`/`commitsAhead` from those two shas via `getCommitsBetweenCommits`, and only rejects the result if `computingRebaseForBranch !== baseBranch.name` [2](#0-1) . This check only detects that the *user switched to a different branch name*; it never detects that the *same-named branch's tip changed* between the start of the async `git` calls and their resolution — unlike the sibling `MergeChooseBranchDialog.updateStatus`, which explicitly re-validates `this.state.selectedBranch.tip.sha !== branch.tip.sha` before committing the result to state [3](#0-2) .

The resulting `RebasePreview.commitsAhead` is not just cosmetic — it is the authoritative list of commits handed to the real rebase operation: `RebaseChooseBranchDialog.start` passes `rebasePreview.commitsAhead` straight into `dispatcher.startRebase` [4](#0-3) , and the equivalent compare-view flow does the same [5](#0-4) . `startRebase` stores that exact `commits` array as `operationDetail.commits` for the multi-commit-operation state [6](#0-5) , and it is later replayed by `appStore._rebase` as the concrete set of commits to cherry-pick onto the (now current) target tip. There is no re-fetch of `baseBranch.tip.sha` or re-diff against the live ref before rebase begins — the operation trusts the cached, potentially stale `commits` list.

### Impact Explanation
Because the actual rebase is driven by a **stale commit list** rather than a fresh diff against the base branch's current tip, an attacker who controls a remote/fetch response that rewrites a branch (force-push) between the moment Desktop computed the preview and the moment the user clicks "Start rebase" can cause Desktop to rebase using a commit set that no longer corresponds to the real branch history. This can silently drop, duplicate, or include unintended commits in the resulting rebase — i.e., silent corruption of what the user ultimately commits, matching the impact class called out in the task (silent corruption of what the user commits or pushes). This is the same "used stale data as if fresh, with no invalidation on the underlying value changing" root cause as the Chainlink `getPrice` bug, just applied to a branch tip instead of a price feed timestamp.

### Likelihood Explanation
The race window is real but narrow: it requires (a) the rebase choose-branch dialog or compare-view rebase preview to be open/in-flight, and (b) the selected base branch's underlying ref to change (via background fetch or an explicit fetch triggered by the user) while the `git`-shelling-out preview computation (`getCommitsBetweenCommits`, wrapped in `promiseWithMinimumTimeout` with a 500ms floor) is still pending [7](#0-6) . Desktop's periodic/background fetch and the fact the preview always waits at least 500ms make this a plausible, not merely theoretical, window, especially for remote-tracking branches. It requires no local access, admin rights, or social engineering — only a hostile or compromised remote server response landing during normal Desktop usage.

### Recommendation
Apply the same sha-based staleness guard used in `MergeChooseBranchDialog.updateStatus` to `updateRebasePreview`: capture `baseBranch.tip.sha` (and `targetBranch.tip.sha`) at call time and re-verify, immediately before invoking `onUpdate`, that the branch's live tip sha still matches what was used for the computation (rather than only comparing branch names). Additionally, `RebaseChooseBranchDialog.start`/`dispatcher.startRebase` should re-validate that the `commits` list still matches a fresh `baseBranch.tip.sha` at operation start, rather than trusting a UI-cached array computed at an earlier point in time.

### Proof of Concept
1. Open a repository in Desktop and start a rebase, selecting a base branch `origin/feature` whose current tip is `A`.
2. `updateRebasePreview` begins: `computingRebaseForBranch = 'origin/feature'`, and issues two `git log` calls diffing `targetBranch.tip.sha` against `A`.
3. Before these calls resolve, trigger (or simulate an attacker-controlled remote causing) a background fetch that force-updates `origin/feature` to a new tip `B` with a completely different commit history (same branch name, different sha) — Desktop updates the in-memory `Branch` object's `tip.sha` to `B` but the in-flight preview computation still refers to `A`.
4. The async calls resolve; `computingRebaseForBranch === baseBranch.name` still holds (`'origin/feature' === 'origin/feature'`), so the check at `update-branch.ts:68` passes and the preview (commits computed against stale tip `A`) is committed to state via `onUpdate`.
5. User clicks "Start rebase" in `RebaseChooseBranchDialog.start`; `rebasePreview.commitsAhead` (computed from stale tip `A`) is passed to `dispatcher.startRebase`, which uses it as the authoritative commit set for the rebase operation against the actual (now `B`-based) target — producing a rebase result that does not reflect the real, current state of `origin/feature`. export async function updateRebasePreview(
  baseBranch: Branch,
  targetBranch: Branch,
  repository: Repository,
  onUpdate: (rebasePreview: RebasePreview | null) => void
) {
  const computingRebaseForBranch = baseBranch.name

  onUpdate({
    kind: ComputedAction.Loading,
  })

  const commitsBehind = await promiseWithMinimumTimeout(
    () =>
      getCommitsBetweenCommits(
        repository,
        targetBranch.tip.sha,
        baseBranch.tip.sha
      ),
    500
  )

  const commitsAhead = await promiseWithMinimumTimeout(
    () =>
      getCommitsBetweenCommits(
        repository,
        baseBranch.tip.sha,
        targetBranch.tip.sha
      ),
    500
  )

  // if the branch being track has changed since we started this work, abandon
  // any further state updates (this function is re-entrant if the user is
  // using the keyboard to quickly switch branches)
  if (computingRebaseForBranch !== baseBranch.name) {
    onUpdate(null)
    return
  }

  // if we are unable to find any commits to rebase, indicate that we're
  // unable to proceed with the rebase
  if (commitsBehind === null) {
    onUpdate({
      kind: ComputedAction.Invalid,
    })
    return
  }

  onUpdate({
    kind: ComputedAction.Clean,
    commitsAhead: commitsAhead ?? [],
    commitsBehind: commitsBehind,
  })
}
