### Title
Unbounded operator-approval query in the CW721→ERC721 pointer allows griefing DoS via out-of-gas on `isApprovedForAll` - (File: contracts/src/CW721ERC721Pointer.sol)

### Summary
`CW721ERC721Pointer.isApprovedForAll` fetches the *entire* `all_operators` list for an NFT owner from the underlying CW721 contract and then iterates it with a Solidity `for` loop to find a match, with no cap on the number of items returned/iterated.

### Finding Description
`isApprovedForAll` queries the CosmWasm CW721 contract for `all_operators` for a given owner and then loops over every returned operator entry, calling `JsonPrecompile.extractAsBytes` and `AddrPrecompile.getEvmAddr` per entry, to check whether the given `operator` is present: [1](#0-0) 

The number of operators an owner can approve is controlled entirely by the NFT owner themselves via `setApprovalForAll`, which is unbounded and simply calls the CW721 `approve_all` message with no limit on distinct operators: [2](#0-1) 

Nothing in the pointer contract, the underlying `example/cosmwasm/cw721` contract, or the query path caps the size of the `all_operators` result set, so a token owner can call `setApprovalForAll` with a large number of distinct operator addresses, growing the stored operator list without bound. Because `isApprovedForAll` is a `view` function invoked both directly by external callers (e.g., marketplaces, `SafeTransferFrom`-style approval checks in third-party integrations) and can be invoked as part of composite flows relying on ERC721 approval semantics, every call pays for decoding and iterating the full, attacker-grown list. This mirrors the reported bug class exactly: a privileged party (the NFT/collection owner) sets an arbitrarily large list that is later fully iterated inside a *different* call, and that iteration cost is paid by whoever triggers it, not by the owner who grew the list.

### Impact Explanation
Any unprivileged EVM caller (a marketplace contract, dApp, or the pointer's own logic if it starts using `isApprovedForAll` for authorization) that queries approval status for an owner with an inflated operator list will burn increasing amounts of gas linearly with the operator-list size, and can be forced to run out of gas / revert if the owner grows the list large enough relative to the caller's supplied gas or the block/call gas cap. This is a griefing/DoS vector against anyone who needs to check approval-for-all status for that owner (which can block legitimate transfers/marketplace interactions relying on this check), analogous to the report's out-of-gas cancellation-blocking scenario, though here it targets read/approval-check reachability rather than fund-locking directly.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the CW721 collection owner to intentionally (or via bulk delegated actions) approve a very large number of distinct operator addresses through repeated `setApprovalForAll`/`approve_all` calls — each such call costs the owner gas too, so building a sufficiently large list to grief callers requires sustained, deliberate effort, similar to the acknowledged unlikelihood in the original report ("nobody sets... such a big list").

### Recommendation
- Cap the number of operators an owner can approve via `approve_all` in the underlying CW721 contract, or
- Change `isApprovedForAll` in `CW721ERC721Pointer.sol` to use a paginated/limited query (similar to the pattern already used in `balanceOf`, which pages through `tokens` with `limit`/`start_after`) instead of fetching and iterating the unbounded `all_operators` list in one call, and/or
- Add an explicit upper bound / early-exit paging mechanism so a single `isApprovedForAll` call cannot be forced to process an unbounded operator set.

### Proof of Concept
1. Attacker (owner of a CW721 token pointed to by `CW721ERC721Pointer`) repeatedly calls `setApprovalForAll(operatorN, true)` for N distinct addresses, e.g., several thousand, growing the CW721 contract's stored `all_operators` list for that owner.
2. Any third party (e.g., a marketplace contract or another user) calls `pointer.isApprovedForAll(owner, someOperator)`.
3. The call in `contracts/src/CW721ERC721Pointer.sol` lines 101-113 queries `all_operators` and loops over all N entries, decoding each with the JSON precompile; with N large enough, the gas cost of this single view call exceeds the caller's provided/available gas, causing the call to fail, denying the ability to verify or rely on approval status for that owner.     function isApprovedForAll(address owner_, address operator) public view override returns (bool) {
        string memory o = _formatPayload("owner", _doubleQuotes(AddrPrecompile.getSeiAddr(owner_)));
        string memory req = _curlyBrace(_formatPayload("all_operators", _curlyBrace(o)));
        bytes memory response = WasmdPrecompile.query(Cw721Address, bytes(req));
        bytes[] memory approvals = JsonPrecompile.extractAsBytesList(response, "operators");
        for (uint i=0; i<approvals.length; i++) {
            bytes memory op = JsonPrecompile.extractAsBytes(approvals[i], "spender");
            if (AddrPrecompile.getEvmAddr(string(op)) == operator) {
                return true;
            }
        }
        return false;
    }

    function setApprovalForAll(address operator, bool approved) public override {
        string memory op = _curlyBrace(_formatPayload("operator", _doubleQuotes(AddrPrecompile.getSeiAddr(operator))));
        if (approved) {
            _execute(bytes(_curlyBrace(_formatPayload("approve_all", op))));
        } else {
            _execute(bytes(_curlyBrace(_formatPayload("revoke_all", op))));
        }
    }
