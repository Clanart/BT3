### Title
Invalid proof-of-possession can expose the ECDH key for another participant’s encrypted DKG share - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
`KeyMachine::calculate_share` decrypts every submitted `EncryptedMessage` and immediately creates an `EncryptionKeyProof` before the batched proof-of-possession verification completes. If the decrypted share is not a canonical scalar, it returns `InvalidShare` with `Some(proof)` before checking whether the message’s PoP was valid [1](#0-0) [2](#0-1) .

This bypasses the protection described by `EncryptedMessage`: without a PoP, an observer can reuse another party’s per-message encryption key and induce the recipient to reveal that ECDH result, thereby decrypting the original message [3](#0-2) .

### Finding Description
An `EncryptedMessage` consists of a public ephemeral key `key`, a Schnorr PoP over that key, sender, and ciphertext, and fixed-length encrypted message bytes [4](#0-3) . Its public deserializer accepts all three fields independently and does not verify semantic relationships [5](#0-4) .

During `calculate_share`, `Encryption::decrypt` queues the PoP for later batch verification, computes `key = self.enc_key * msg.key`, decrypts the ciphertext, and constructs a DLEQ proof revealing that shared ECDH point [6](#0-5) . `calculate_share` then attempts to decode the plaintext scalar; on a non-canonical encoding it immediately returns `InvalidShare` with that proof attached [1](#0-0) . The queued PoP result is only consulted by `batch.verify_with_vartime_blame()` afterward [7](#0-6) .

An attacker who observes an honest `EncryptedMessage` can therefore reuse its `key` while changing the encrypted payload and using any canonically encoded but invalid Schnorr PoP. With approximately one-half probability for a 32-byte Ristretto scalar representation, blind mutation makes the ChaCha20 plaintext decode as a non-canonical scalar. The recipient then emits the ECDH proof before discovering the invalid PoP. That proof verifies the same `msg.key * recipient_enc_key` used by the observed honest message, so the attacker can decrypt that original share.

### Impact Explanation
This can recover another participant’s encrypted DKG secret share. The code comments explicitly identify revealing an ECDH key for a reused message key as a “massive side effect” capable of revealing the original message [8](#0-7) . The exposed `EncryptionKeyProof` contains the shared point and a DLEQ proving it corresponds to `msg.key` and the recipient’s registered encryption key [9](#0-8) . Anyone can use that point with `cipher` to decrypt the observed ciphertext [10](#0-9) .

### Likelihood Explanation
The attacker needs a canonical `key` and Schnorr-signature-shaped input plus mutated fixed-size ciphertext; `EncryptedMessage::read` accepts these as untrusted bytes [5](#0-4) . The attacker does not need to know the reused ephemeral private key or calculate a valid PoP. Each independently mutated ciphertext has a substantial probability of decrypting to a non-canonical scalar, and attempts can be repeated across DKG attempts even if a protocol only accepts one share per attempt.

### Recommendation
Do not create or expose `EncryptionKeyProof` until the PoP has been verified. In `Encryption::decrypt`, perform PoP verification before calculating the ECDH proof and plaintext, or return a provisional result that `calculate_share` cannot convert into `Some(blame)` until batch verification succeeds. At minimum, the non-canonical-scalar branch in `calculate_share` must not return the ECDH proof before the PoP batch has verified [11](#0-10) .

A regression test should submit an `EncryptedMessage` with a reused honest `key`, mutated ciphertext that decrypts to a non-canonical scalar, and an invalid PoP. `calculate_share` must return `InvalidShare { blame: None }` and must not produce an `EncryptionKeyProof`.

### Proof of Concept
1. Run PedPoP round 1 so sender `A` and victim recipient `B` register encryption keys.
2. Observe `A`’s serialized `EncryptedMessage` to `B`, containing `X = aG`, PoP `(R, s)`, and ciphertext `C = share_encoding XOR ChaCha20(bX)`.
3. Construct another `EncryptedMessage` with the same `X`, a canonically encoded invalid Schnorr signature, and `C' = C XOR delta` for attacker-chosen `delta`.
4. Submit it to `B`’s `calculate_share`.
5. `Encryption::decrypt` queues the invalid PoP but still derives `bX`, decrypts `C'`, and constructs a DLEQ proof for `bX` [6](#0-5) .
6. If `C' XOR ChaCha20(bX)` is non-canonical—which occurs with high probability for random `delta`—`calculate_share` returns `InvalidShare { blame: Some(proof) }` before batch verification reports the invalid PoP [11](#0-10) .
7. Verify the returned DLEQ against `[G, X]` and `[B_enc_key, proof.key]`, then initialize the same ChaCha20 cipher with `proof.key` and decrypt the originally observed `C`, recovering `A`’s scalar share encoding [12](#0-11) .

pub struct EncryptedMessage<C: Ciphersuite, E: Encryptable> {

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
