### Title
Cross-context signature replay in the `addr` precompile's `associate()` forces unwanted EVM↔Sei address association and balance migration - ([File: precompiles/addr/addr.go])

### Summary
The `associate` method of the `addr` precompile (`0x0000000000000000000000000000000000001004`) authenticates the caller's intent to link a Sei address to an EVM address purely by recovering an ECDSA public key from a `(v, r, s)` signature over `keccak256(customMessage)`, where `customMessage` is an arbitrary, attacker-supplied string with no chain ID, precompile-address, or purpose tag baked into the signed payload on-chain.

### Finding Description
`precompiles/addr/addr.go` `associate()` computes:
```go
customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
``` [1](#0-0) 
and then unconditionally calls `associateAddresses`, which — if the recovered `seiAddr` is not already associated — performs a full state mutation: it sets the EVM↔Sei mapping, assigns the pubkey to the account, and migrates *all* spendable balances and wei balances from the "direct-cast" address (`sdk.AccAddress(evmAddr[:])`) to the newly bound Sei address, then removes the cast account: [2](#0-1) [3](#0-2) 

The signed digest contains no domain separator: no chain ID, no contract/method identifier, and no nonce. The frontend convention embeds a fixed literal message (`ASSOCIATE_MESSAGE` in the test suite) inside an EIP-191 envelope that is then passed as `customMessage`, but nothing on-chain enforces that content: [4](#0-3) 

Because the same signature format (raw `keccak256` of an unstructured string, without chain binding) is valid on every Sei network and chain instantiation that runs this precompile, any signature a user has ever produced over that literal association string — e.g., captured from a testnet, a fork, a different `sei-chain` deployment, or a previous broadcast that a public RPC/mempool observer intercepts — can be captured and replayed by an unrelated third party against a *different* target chain (or a chain that has since been re-genesised) to force association and balance migration for the victim's address there, without the victim's participation. This is the "authentication bypass by capture-replay" pattern: the recovered signature genuinely proves possession of the private key at signing time, but the protocol never binds that proof to the specific chain/session it is meant to authorize, so a legitimately-produced signature is fully reusable across unrelated authorization contexts (CWE-294 pattern), directly analogous to the Spark handshake reuse issue GHSA-9rr6-jpg7-9jg6.

Notably, the codebase's own developers have already identified and fixed exactly this bug class in the sibling EIP‑7702 authorization path, with explicit comments warning that a "publicly-visible authorization a user signed for another chain... could be replayed... to force-associate them — migrating their direct-cast balance and orphaning staking/distribution state": [5](#0-4) 
`AuthorityToPreAssociate` enforces `auth.ChainID` must be zero or match the local chain before pre-association is allowed: [6](#0-5) 
No equivalent chain-ID check exists in the `addr` precompile's `associate()`/`GetAddresses()` path — the `customMessageHash` is just `keccak256(customMessage)` with no chain ID mixed in.

### Impact Explanation
A successful replay forces `AssociateAddresses`/`MigrateBalance` to run for the victim's account on the target chain: all spendable coin balances and wei balance held at the direct-cast address are moved to the newly-bound Sei address, and the cast account is removed. Because association is a one-time, irreversible action (an already-associated address rejects further calls), a maliciously-triggered forced association at an unexpected time (e.g., mid-migration, before a user has intentionally opted in on a given deployment, or on a forked/testnet chain that shares key material with mainnet) can permanently rewire which Sei address owns a user's EVM-side funds and identity, satisfying the "unauthorized transfer via precompile" and "permanent freezing/loss of expected fund location" impact classes named in scope.

### Likelihood Explanation
Exploitation requires only a captured `(v, r, s, customMessage)` tuple that a victim produced for the association flow in any context (any Sei chain ID, any historical broadcast, or any fork/testnet sharing the fixed message string) — no privileged position, no validator/node compromise, and no on-chain secret is needed. `associate()` is a normal, permissionless EVM precompile call reachable by any unprivileged transaction sender or contract, so the barrier to replay is purely "has the attacker ever observed this specific signature," which is realistic given the message is a fixed, publicly documented string and is transmitted in plaintext transaction/calldata that is visible to any mempool watcher, block explorer, or full-node operator on any chain running the same precompile logic.

### Recommendation
Bind the signed payload to the specific target chain and precompile invocation before hashing, e.g. include the EVM `ChainID`, the precompile address, and a purpose tag (mirroring the `0x05 || rlp([chainId, address, nonce])` domain separation already used for EIP-7702 authorizations in `RecoverAddressesFromAuthorization`) inside the digest that `GetAddresses` verifies, and reject association if the encoded chain ID does not match `ek.ChainID(ctx)`, following the same pattern already implemented in `AuthorityToPreAssociate`.

### Proof of Concept
1. On Sei chain A (e.g. a testnet or a chain that shares genesis/derivation with a target), a user signs the standard association message with their private key and calls `associate(v, r, s, customMessage)` on the `addr` precompile — or simply produces the signature off-chain for legitimate use and it is observed by a third party before broadcast.
2. An attacker copies the identical `(v, r, s, customMessage)` tuple and submits it as calldata to the `addr` precompile's `associate` method on a different Sei chain instance B (or the same chain at a different point after account/state changes) where the victim's derived `seiAddr` is not yet associated.
3. `GetAddresses` recovers the same `evmAddr`/`seiAddr`/`pubkey` because the hash `keccak256(customMessage)` contains no chain-binding data, so signature validation succeeds on chain B exactly as it did (or would have) on chain A.
4. `associateAddresses` → `AssociateAddresses` → `MigrateBalance` executes, moving the victim's direct-cast balance to the newly bound Sei address and permanently registering the association on chain B — without any transaction ever being authorized by the victim for chain B.

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
