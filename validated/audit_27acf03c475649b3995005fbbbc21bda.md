Based on the code, this is silently applied — there's no confirmation dialog gating the actual `gitStore.setRemoteURL` call in `updateRemoteUrl`; it's invoked automatically from `repositoryWithRefreshedGitHubRepository` on account/repository refresh.

## Analysis

`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` is called with an `apiRepo: IAPIRepository` obtained by `API.fetchRepository(owner, name)` in `repositoryWithRefreshedGitHubRepository` [1](#0-0) . The gating conditions before it calls `gitStore.setRemoteURL(...)` are: [2](#0-1) 

- `protocolsMatch` — only compares the URL **scheme** (`https:` vs `ssh:`/`git+ssh:` etc.), not the host.
- `remoteUrlUnchanged` — compares the *previously stored* `gitHubRepository.cloneURL` against the *current* local git remote (`gitStore.defaultRemote`) via `urlMatchesRemote`, which checks hostname+owner+name equality [3](#0-2) . This only verifies the user hasn't manually edited the remote away from what Desktop last recorded — it says nothing about the **new** `apiRepo.clone_url`.
- `!urlsMatch` — true precisely when `apiRepo.clone_url` (hostname/owner/name) **differs** from the current remote.

Critically, there is no check anywhere in this function that the new `apiRepo.clone_url`'s hostname matches the original remote's hostname, the previously known `gitHubRepository.cloneURL`'s hostname, or the account's endpoint host. As soon as `protocolsMatch && remoteUrlUnchanged && !urlsMatch` holds, `gitStore.setRemoteURL` is invoked with whatever host is embedded in `apiRepo.clone_url` [4](#0-3) , with no user confirmation step in between (verified by the callers in `app-store.ts`, which invoke `updateRemoteUrl` directly and unconditionally as part of the periodic/account-triggered `repositoryWithRefreshedGitHubRepository` refresh flow).

The test suite confirms this behavior is intentional for the "repository renamed on GitHub" use case (same host, new owner/name) [5](#0-4) , but the guard as written does not restrict the change to same-host renames — any `clone_url` value returned by the `IAPIRepository` object for that owner/name lookup will pass, provided the user hasn't already hand-edited the local remote away from what Desktop expects.

Where this becomes attacker-relevant: the `apiRepo` object is the parsed JSON body of a GitHub API response `repos/{owner}/{name}` for the account's `endpoint` [6](#0-5) . For a GitHub Enterprise Server endpoint (or any server compromise/response-tampering scenario), the `clone_url` field is attacker-influenced content coming back from that server — nothing in `updateRemoteUrl` pins the new URL's host to a trusted value. This matches "GitHub API object" attacker control called out in the bounty scope.

## Verdict

This is a real gap (missing hostname-pinning) in `updateRemoteUrl`, but whether it rises to a valid, in-scope finding depends on how the `apiRepo` object can practically become attacker-controlled without requiring the excluded categories (network MITM against a legitimate github.com endpoint, or the user themselves configuring a malicious GHES account, which borders on "unprompted unnatural user steps"/self-inflicted trust). I could not find, within the indexed code, any additional layer (e.g., in `dispatcher.ts` or elsewhere) that gates this update behind a user-facing confirmation dialog or an endpoint/host allow-list before `setRemoteURL` is called — only the checks shown above. I was not able to fully trace whether `IAPIRepository` responses are scoped/validated against the requested endpoint's TLS-pinned host anywhere else in the HTTP layer (`ghRequest`), which would be needed to fully rule out a legitimate github.com response ever containing an attacker-chosen `clone_url`.

### Title
Missing hostname validation in `updateRemoteUrl` allows repo's git remote to be silently repointed to a different host - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` updates the local `origin` remote URL based on the GitHub API's `clone_url` field without ever validating that the new URL's hostname matches the original/trusted host, gated only by a URL-scheme match and a "has the user manually changed the remote" check.

### Finding Description
`protocolsMatch` only compares `URL.parse().protocol` (e.g. `https:`), and `remoteUrlUnchanged` only asserts the *current* remote still matches the *previously cached* `gitHubRepository.cloneURL` — neither compares the *new* `apiRepo.clone_url`'s host against anything trusted. If `apiRepo.clone_url` names a different host but the same protocol, `!urlsMatch` becomes true and `gitStore.setRemoteURL` is called unconditionally with the new host [7](#0-6) .

### Impact Explanation
If exploitable, this silently changes where the user's Desktop client fetches from and pushes to, which is a "silent corruption of what the user commits or pushes" class impact — future pushes would go to an unintended remote and future pulls/fetches would come from it.

### Likelihood Explanation
Low/uncertain — exploitation requires the `IAPIRepository` JSON returned for the trusted account's endpoint (`repos/{owner}/{name}`) to actually contain an attacker-chosen `clone_url` with a different host, which normally requires either compromising github.com's API/TLS (out of scope) or the user having connected to an attacker-operated GitHub Enterprise-style endpoint (borderline in/out of scope depending on how "GitHub API object" attacker control is interpreted).

### Recommendation
In `updateRemoteUrl`, additionally require that `URL.parse(updatedRemoteUrl).hostname` equals `URL.parse(remoteUrl).hostname` (or matches `gitHubRepository.endpoint`'s host) before calling `gitStore.setRemoteURL`, so only owner/name changes on the same host are auto-applied; cross-host changes should require explicit user confirmation.

### Proof of Concept
Given a repository whose local `origin` and `gitHubRepository.cloneURL` are both `https://ghes.example.com/acme/widget`, if the next `api.fetchRepository('acme','widget')` call against `ghes.example.com` returns `clone_url: "https://evil.example.com/acme/widget"`, `remoteUrlUnchanged` is true (matches cached value), `protocolsMatch` is true (both `https:`), and `!urlsMatch` is true (different host) — `updateRemoteUrl` will call `gitStore.setRemoteURL('origin', 'https://evil.example.com/acme/widget')`, repointing the local remote with no host validation and no user prompt, as shown in the guard logic at [8](#0-7) .

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
