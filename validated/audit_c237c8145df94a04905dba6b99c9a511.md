### Title
Path Traversal via Symlinked Working-Directory Entries in "Open File" / "Reveal in File Manager" — Path.join Used Instead of resolveWithin - (File: app/src/lib/app-shell.ts, app/src/ui/changes/sidebar.tsx, app/src/ui/app.tsx)

### Summary
GitHub Desktop already recognizes that a naive `Path.join(repository.path, untrustedPath)` is unsafe against directory-traversal/symlink-escape attacks originating from attacker-controlled repository data: it built `resolveWithin()` (which uses `realpath` to defeat symlink escapes) specifically to guard the "Open Repository from URL" deep-link flow. However, several other sinks that also build a filesystem path by joining `repository.path` with a path string taken from the working directory / conflict UI (data that is ultimately derived from the contents of a cloned/fetched, attacker-controlled repository) do **not** use `resolveWithin` and instead use plain `Path.join`, which does not resolve symlinks.

### Finding Description
`resolveWithin()` in `app/src/lib/path.ts` explicitly resolves both the root and the candidate path with `fs/promises`' `realpath()` and only returns a path when the real, symlink-resolved result still starts with the real root: [1](#0-0) 

This is precisely because a relative "path within the repo" can, via a symlink placed inside the working tree, resolve to a location entirely outside the repository root — the project's own test suite explicitly documents and validates this attack: [2](#0-1) 

This guard is applied for the `x-github-client://openRepo` deep-link `filepath` parameter: [3](#0-2) 

But the *same class* of untrusted, repository-controlled relative path (`WorkingDirectoryFileChange.path`, or a conflicted-file path, both sourced from `git status`/`git diff` output on a cloned/fetched repository) reaches `Path.join` in at least three other sinks without any `resolveWithin`/`realpath` check:

- `revealInFileManager()`, which is called from the changes sidebar and the conflict-resolution overflow menu: [4](#0-3) 

- "Open with default program" from the Changes sidebar: [5](#0-4) 

- "Open in external editor" for a working-directory path: [6](#0-5) 

- The Copilot conflict-resolution overflow menu, which builds `absolutePath` the same unsafe way and feeds it to `openFile`, `openFileInExternalEditor`, and `revealInFileManager`: [7](#0-6) 

`openFile()` itself performs no path validation — it simply hands the joined path to `shell.openExternal`: [8](#0-7) 

The `IAppShell` interface's own doc-comments acknowledge the danger ("Do not use this method with non-validated paths"), confirming the developers know these sinks require validated input, yet the working-directory-derived call sites do not perform that validation: [9](#0-8) 

**Corrupted value:** the fully-qualified path passed to `shell.showItemInFolder` / `shell.openExternal` / the external editor launcher. It is computed as `Path.join(repository.path, path)` where `path` is a filename/relative path taken from a working-tree entry of a cloned/fetched repository. Because `Path.join` is purely lexical, it never detects that a path component inside the working tree is a symlink pointing outside the repository, so the invariant "this file lives inside the repository" — the same invariant `resolveWithin` was created to enforce — is silently violated here.

### Impact Explanation
An attacker who controls a repository the victim clones or fetches (matching the report's "attacker controls a cloned/fetched repository" primitive) can place a symlink inside the working tree that points to a sensitive location outside the repo (e.g., the user's SSH keys, another local repository, or an arbitrary file). If the victim's Changes list, diff view, or conflict-resolution UI shows an entry whose relative path traverses through that symlink, clicking "Open with default program", "Open in external editor", or "Show in Explorer/Finder" resolves and opens/executes a file outside the intended repository boundary. Depending on the target file type and the OS's file-association handling, this can result in disclosure of file contents outside the repo, or execution of an unintended program/document handler — i.e., "file... read outside the repo" as called out in the Valid Impact criteria.

### Likelihood Explanation
Symlinks are a normal, low-friction feature of Git working trees (a repository can commit a symlink object, and it will be materialized on checkout on macOS/Linux, and on Windows when developer mode/symlink support is enabled). No special git server behavior, admin rights, or prior host compromise is required — only that the victim clones the malicious repository and interacts with a file entry in the normal UI (Changes list, conflict list). Because the app already had to build and test `resolveWithin`'s symlink defenses for one flow, the missing coverage in the other, more commonly used flows (opening/revealing working-directory files) represents a realistic gap rather than a purely theoretical one.

### Recommendation
Route every path derived from repository working-directory/diff/conflict data through `resolveWithin(repository.path, path)` (or `resolveWithinPosix`/`resolveWithinWin32` as appropriate) before calling `shell.showItemInFolder`, `shell.openExternal`, or launching an external editor, mirroring the pattern already used in `dispatcher.ts`'s `openRepositoryFromUrl`. Specifically harden:
- `revealInFileManager()` in `app/src/lib/app-shell.ts`
- `onOpenItem` in `app/src/ui/changes/sidebar.tsx`
- `onOpenInExternalEditor` in `app/src/ui/app.tsx`
- `onOverflowMenuClick` in `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`

Reject and log (as the deep-link handler does) any path that fails to resolve within the repository root.

### Proof of Concept
1. Attacker creates a public repository containing a symlink `evil -> ../../../../` (or an absolute-target symlink to `~/.ssh` on macOS/Linux) and commits it along with a tracked/untracked file path that traverses through it, e.g. `evil/.ssh/id_rsa` appearing as an untracked/modified entry in the working tree once cloned (the symlink target need only exist on the victim's filesystem, e.g. `~/.ssh`).
2. Victim clones this repository with GitHub Desktop.
3. In the Changes sidebar, the victim right-clicks the entry corresponding to `evil/.ssh/id_rsa` and selects "Show in Explorer/Finder" (or "Open with default program").
4. `revealInFileManager(repository, 'evil/.ssh/id_rsa')` computes `Path.join(repository.path, 'evil/.ssh/id_rsa')`, which the OS resolves (following the `evil` symlink) to `~/.ssh/id_rsa`, revealing/opening a file entirely outside the cloned repository — the same class of escape that `resolveWithin`'s symlink test in `app/test/unit/path-test.ts` was written to prevent, but which is not applied on this code path.

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
