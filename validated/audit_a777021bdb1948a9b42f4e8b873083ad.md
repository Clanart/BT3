### Title
Copilot merge-conflict resolutions are applied from a stale content snapshot without re-validating the on-disk state at finalize time - (File: `app/src/lib/stores/app-store.ts`)

### Summary
The reported smart-contract bug is a classic two-phase "request → finalize" race: a user commits to a stake/unstake request, and is later allowed to *finalize* it using information (game outcome, share price) that may have changed since the request was made, with no re-check that the finalize input still matches what was true at request time. GitHub Desktop's Copilot conflict-resolution feature has the same structural flaw: it computes a resolution ("request") from a **snapshot of file content read from disk**, and later ("finalize") writes that same stale content back to disk, validating only a coarse status flag rather than the actual content the resolution was generated from.

### Finding Description
The two-phase flow:

1. **Request/generate phase** – `buildConflictContext` reads each conflicted file from disk and stores the full `rawContent` snapshot used to build the AI prompt: [1](#0-0) . This context is sent to the Copilot SDK, and the response's per-hunk resolutions are spliced back into that captured `rawContent` snapshot in `reassembleResolutions`/`reassembleResolvedFile`, producing a `resolvedContent` string that is only ever consistent with the *original* snapshot, not with whatever is currently on disk: [2](#0-1) .
2. This generation step can run for a long time — the app's own instrumentation buckets runs over 15s, 30s, 60s, and 120s: [3](#0-2) . During this window the user (or any other process/tool operating on the same working directory) can keep working, and the result is deferred: "Files are NOT written to disk yet — that happens when the user clicks 'Continue Merge'" [4](#0-3) .
3. **Finalize phase** – `_applyCopilotConflictResolutions` writes the stored `resolution.resolvedContent` straight to disk. The *only* re-validation performed against current state is a coarse status check: it skips a file solely when it is no longer reported as conflicted (i.e., someone fully resolved it externally), but performs no comparison between the current on-disk content/conflict markers and the `rawContent` snapshot the resolution was actually generated from: [5](#0-4) .

Because the "finalize" step trusts stale generation-time data and only checks a shallow status flag, any change to the conflicted file's content between generation and confirmation (as long as it still looks "conflicted" to git status) is silently discarded when the stale resolution is written over it via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and then staged with `git add`: [6](#0-5) . This mirrors the report's core defect: a value captured at request time (share price / game state ⇔ file content) is used unconditionally at finalize time, with only a superficial guard that doesn't verify the value hasn't moved.

### Impact Explanation
This can result in silent corruption of what the user actually commits/pushes: content the user (or an external tool/editor) wrote into the conflicted file after the AI resolution was generated — but before "Continue Merge" was clicked — is overwritten without warning by the stale AI-generated content, and then staged and committed as if it were current. Since the result dialog shows a diff computed from the same stale snapshot, the UI gives the user no indication that what's about to be written no longer matches the working directory's real state. This falls squarely into the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Likelihood is bounded by the fact that AI conflict resolution runs can legitimately take from tens of seconds to multiple minutes (as evidenced by the app's own >60s/>120s telemetry buckets), giving a realistic window for the working tree to change — whether from the user manually touching the file in an external editor while waiting, or from another tool/process (build scripts, formatters, git hooks) acting on the fetched/merged repository. No special privileges are required; it can occur during ordinary use of the feature on a repository merging/rebasing against an untrusted branch.

### Recommendation
Before writing `resolution.resolvedContent` in `_applyCopilotConflictResolutions`, re-read the current on-disk content (or retain a hash/snapshot alongside each `IFileResolution`) and compare it to the content the resolution was generated from. If it has changed, treat the file the same way as a manually-resolved file: skip the AI resolution and surface the discrepancy to the user instead of silently overwriting.

### Proof of Concept
1. Start a merge/rebase/cherry-pick against a branch that produces conflicts, and trigger "Resolve with Copilot" (`_startCopilotConflictResolution`).
2. While the resolution is in flight (can take well over a minute per the app's own `copilotConflictResolutionOver120sCount` telemetry), open one of the conflicted files in an external editor and make an edit that leaves conflict markers intact (e.g., edit content inside the `<<<<<<<`/`>>>>>>>` block without fully removing the markers).
3. Wait for the Copilot result dialog and click "Continue Merge" (`onContinue` → `applyCopilotConflictResolutions` → `_applyCopilotConflictResolutions`).
4. Observe that `_applyCopilotConflictResolutions` only checks `isConflictedFileStatus(...) && !hasUnresolvedConflicts(...)` (still true here) and proceeds to `writeFile` with the stale `resolvedContent`, discarding the edit made in step 2 without any warning, then stages it via `git add`.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
