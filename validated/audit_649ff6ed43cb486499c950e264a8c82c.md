## Analog Confirmed

### Title
Attacker-controlled `WWW-Authenticate` header can redirect the trusted "Sign in to GitHub Enterprise" flow to the attacker's own server, exfiltrating credentials - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Sherlock report's broken invariant is: *a privileged action (returning funds / handing over an asset) is triggered based on the wrong identity source, because the code trusts an attacker-influenced field instead of verifying the actual authorized party.* The Desktop analog is structurally identical: the credential-helper trampoline decides whether a host is "GitHub" (and therefore worthy of Desktop's trusted sign-in UI and stored tokens) based on an HTTP `WWW-Authenticate` response header that is fully controlled by the remote Git server the request was made to — i.e. by an attacker who controls a cloned/fetched remote or a man-in-the-middle proxy.

### Finding Description
When Git needs credentials for an HTTPS remote, Desktop's credential helper is invoked via `createCredentialHelperTrampolineHandler` → `getCredential` in [1](#0-0) .

`getCredential` calls `getEndpointKind`, which classifies the remote host as `github.com`, `ghe.com`, `enterprise`, or `generic`. Crucially, this classification is derived from `wwwauth[...]` entries that Git forwards verbatim from the server's HTTP response: [2](#0-1) 

If the value contains `realm="GitHub"`, the endpoint is unconditionally classified as `'enterprise'` — there is no verification that the host is an actual GitHub/GHE instance (no TLS cert check, no API probe, no allow-list). Since this header is set by the server the git operation is talking to, an attacker-controlled remote (or a proxy sitting on the network path, e.g. via a `.gitmodules` submodule URL, a hostile `insteadOf` rewrite, or simply a repository the user adds as a remote and fetches from) can trivially set this header on its 401 challenge response.

Once classified as `'enterprise'` and no matching account exists, `getCredential` calls the UI helper to start a sign-in flow: [3](#0-2) 

`ui.promptForGitHubSignIn` then does: [4](#0-3) 

Since the attacker's hostname is (by construction) not `github.com`, the branch `this.dispatcher.beginEnterpriseSignIn(cb)` + `await this.dispatcher.setSignInEndpoint(origin)` executes, pointing Desktop's built-in **GitHub Enterprise** sign-in flow directly at the attacker's origin. `setSignInEndpoint` → `SignInStore.setEndpoint` only rejects the URL if it's non-HTTPS or if it matches `github.com`; any other HTTPS host is accepted as a legitimate "GitHub Enterprise instance": [5](#0-4) 

The resulting popup is the same trusted "Sign in to GitHub" dialog (`PopupType.SignIn`, `isCredentialHelperSignIn: true`), which the user is conditioned to trust and fill in their username and Personal Access Token, or click "Sign in with your browser" (`authenticateWithBrowser`), which opens an OAuth authorization URL built from the attacker-controlled endpoint via `getOAuthAuthorizationURL(endpoint, csrfToken)` [6](#0-5) .

This exactly mirrors the original bug's shape: the code uses an attacker/adversary-influenced field (`FeePayer()` vs. `FeeGranter()` in the original; here, a server-supplied `WWW-Authenticate` header vs. an actually-verified GitHub host) to decide who receives a sensitive asset (refunded fee vs. a user's GitHub credential / trusted sign-in target), with no independent check of the "real" authorized party.

### Impact Explanation
If the user enters a PAT/password on the resulting Authentication form, it is submitted for basic-auth verification against the attacker's endpoint — direct credential exfiltration. If the user instead uses "sign in with browser," the OAuth authorization request is issued against the attacker's endpoint, which can be leveraged for OAuth/account-binding confusion (the attacker's server can return an arbitrary "account" object which `fetchUser`/`onAuthCompleted` will treat as authenticated, potentially binding an attacker-controlled identity into the user's Desktop account list, or capturing whatever token the user believes they're handing to GitHub). Either path constitutes credential/token exfiltration or unauthorized account binding triggered purely by fetching from/cloning a hostile repository — no local access, malware, or social engineering beyond normal git operations required.

### Likelihood Explanation
Likelihood is moderate-to-high for exploitation but requires user interaction (entering credentials in the resulting dialog, or clicking through the "sign in with browser" flow) once the popup appears. The trigger condition itself (control over the HTTP response to a `git credential` challenge for an added remote) is trivially achievable by anyone who can offer a remote URL the user fetches/clones/pushes to, which fits the required "attacker controls a cloned/fetched repository / git remote or proxy response" primitive precisely. The `WWW-Authenticate` heuristic is a "happy-path" optimization documented in the code comment itself as skipping a real verification step, which is exactly the missing check called out in the original report ("check for the correct recipient" before acting).

### Recommendation
Do not trust the `WWW-Authenticate: realm="GitHub"` header alone to classify a host as an "enterprise" GitHub instance eligible for the trusted sign-in flow. Before invoking `promptForGitHubSignIn`/`beginEnterpriseSignIn`, perform (or require) the existing `isGitHubHost(endpoint)` API probe (already used later in `getEndpointKind` as a fallback) as a mandatory verification step, or otherwise cryptographically/API-verify the endpoint is a genuine GitHub/GHE instance before offering the "Sign in to GitHub" trust-elevated UI and before opening any OAuth authorization URL derived from it.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a proxy achieving MITM on an insecure network) and hosts a repository.
2. Victim adds this server as a remote (or clones it) in GitHub Desktop and performs a fetch/push that requires authentication.
3. Git issues an HTTP request; the attacker's server responds with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
4. Desktop's credential helper (`trampoline-credential-helper.ts`) parses this via `command.stdin`'s `wwwauth[...]` entries, `getEndpointKind` returns `'enterprise'` [7](#0-6) .
5. No account exists for the attacker's host, so `ui.promptForGitHubSignIn(endpoint)` is invoked, calling `beginEnterpriseSignIn` + `setSignInEndpoint(<attacker origin>)` [8](#0-7) .
6. Desktop shows its normal "Sign in to GitHub" popup; the victim, believing it's a legitimate GHE sign-in, enters credentials or authorizes via browser, and those credentials/tokens are sent to (or authorized against) the attacker's endpoint.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

  public async setEndpoint(url: string): Promise<void> {
    const currentState = this.state

    if (
      currentState?.kind !== SignInStep.EndpointEntry &&
      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with endpoint entry`
      )
    }

    /**
     * If the user enters a github.com url in the GitHub Enterprise sign-in
     * flow we'll redirect them to the GitHub.com sign-in flow.
     */
    if (/^(?:https:\/\/)?(?:api\.)?github\.com($|\/)/.test(url)) {
      this.beginDotComSignIn(currentState.resultCallback)
      return
    }

    this.setState({ ...currentState, loading: true })

    let validUrl: string
    try {
      validUrl = validateURL(url)
    } catch (e) {
      let error = e
      if (e.name === InvalidURLErrorName) {
        error = new Error(
          `The GitHub Enterprise instance address doesn't appear to be a valid URL. We're expecting something like https://example.ghe.com.`
        )
      } else if (e.name === InvalidProtocolErrorName) {
        error = new Error(
          'Unsupported protocol. Only https is supported when authenticating with GitHub Enterprise instances.'
        )
      }

      this.setState({ ...currentState, loading: false, error })
      return
    }

    const endpoint = getEnterpriseAPIURL(validUrl)

    const existingAccount = this.accounts.find(x => x.endpoint === endpoint)

    if (existingAccount) {
      this.setState({
        kind: SignInStep.ExistingAccountWarning,
        endpoint,
        existingAccount,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    } else {
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    }
