### Title
Unbounded Sequential RPC Loop in `collect_deposit_move_txids` / `collect_withdrawal_utxos` Blocks Verifier Block Processing, Risking Missed Challenge Windows — (`core/src/citrea.rs`)

---

### Summary

`CitreaClient::collect_deposit_move_txids` and `CitreaClient::collect_withdrawal_utxos` iterate through every deposit/withdrawal index one-by-one via sequential, synchronous RPC calls to the Citrea bridge contract, with no batching, no upper-bound cap, and no way to resume mid-range. The loop is driven by `get_last_deposit_idx` / `get_last_withdrawal_idx` from the DB. After a long offline period or on first sync against a mature bridge, the verifier must drain the entire backlog in a single blocking pass before it can process any Bitcoin block. This can delay or permanently stall the verifier's challenge-window monitoring, allowing an operator to escape a valid watchtower challenge.

---

Both are called from `update_citrea_deposit_and_withdrawals` in `verifier.rs`, which is the verifier's per-Bitcoin-block Citrea sync step: [3](#0-2) 

The starting index is read from the DB via `get_last_deposit_idx` / `get_last_withdrawal_idx`: [4](#0-3) 

The `withdrawals` table (schema line 269) has no removal mechanism — rows are only ever inserted or updated, never deleted. The deposit/withdrawal count on Citrea grows monotonically and unboundedly. [5](#0-4) 

The `CitreaClient` provider is constructed without an explicit per-call timeout on the `contract` handle (only the JSON-RPC `client` gets a timeout), so each `depositTxIds(N)` call can block for an arbitrary duration: [6](#0-5) 

---

### Impact Explanation

`update_citrea_deposit_and_withdrawals` is called inside the verifier's Bitcoin block handler while holding an open `DatabaseTransaction`. If the loop must drain a large backlog (e.g., thousands of deposits after a restart), the verifier is blocked from processing any subsequent Bitcoin block until the loop completes. The verifier is responsible for detecting invalid operator assertions and issuing watchtower challenges within a fixed Bitcoin timelock window. If the verifier cannot advance its block-processing loop in time, it misses the challenge window, the operator's fraudulent assertion goes unchallenged, and the operator can claim the bridged BTC collateral — a direct theft of bridge-controlled funds.

---

### Likelihood Explanation

The condition is reachable without any privileged action:

1. A verifier node restarts after being offline for an extended period (routine operational event).
2. The Citrea bridge has accumulated N deposits since the last DB-recorded index.
3. The verifier must make N sequential RPC calls before it can process any Bitcoin block.
4. For N in the thousands (plausible on a live bridge), and with each call taking even 1–2 seconds, the total delay easily exceeds the Bitcoin-timelock challenge window (measured in blocks/hours).

No attacker action is required; normal bridge growth is sufficient.

---

### Recommendation

1. **Add a batch-size cap**: Accept a `max_batch` parameter and return after fetching at most `max_batch` entries per call, allowing the caller to commit progress and resume on the next tick.
2. **Commit progress incrementally**: Write each fetched deposit/withdrawal to the DB and update `last_deposit_idx` / `last_withdrawal_idx` inside the same loop iteration (or in small sub-transactions), so a restart resumes from the last committed index rather than re-scanning from scratch.
3. **Separate the sync loop from the block-processing critical path**: Run the Citrea backlog drain in a dedicated background task that does not block the verifier's challenge-monitoring loop.

---

### Proof of Concept

**Setup**: Bridge has 5 000 deposits on Citrea. Verifier DB has `last_deposit_idx = 0` (fresh restart).

**Trigger** (no special privileges needed): Verifier receives a new Bitcoin block and calls `update_citrea_deposit_and_withdrawals`.

**Execution**:
- `get_last_deposit_idx` returns `None` → `start_idx = 0`.
- `collect_deposit_move_txids` enters the loop and calls `depositTxIds(0)`, `depositTxIds(1)`, …, `depositTxIds(4999)` — 5 000 sequential awaited RPC calls.
- At 1 second per call, the loop takes ~83 minutes before returning.
- During this time, the verifier's block-processing task is blocked; no Bitcoin block is processed.
- An operator whose fraudulent kickoff has a 6-block (~60-minute) challenge window goes unchallenged.
- The operator's assert transaction becomes final; the operator claims the bridged BTC.

**Root cause**: `collect_deposit_move_txids` at `core/src/citrea.rs:432–454` has no batch cap and no incremental progress commit, making the total work proportional to the unbounded, ever-growing Citrea deposit count. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)

    async fn collect_deposit_move_txids(
        &self,
        last_deposit_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, Txid)>, BridgeError> {
        let mut move_txids = vec![];

        let mut start_idx = match last_deposit_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let deposit_txid = self
                .contract
                .depositTxIds(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match deposit_txid {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Deposit txid not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            tracing::info!("Deposit txid found for index: {:?}", deposit_txid);

            let deposit_txid = deposit_txid.expect("Failed to get deposit txid");
            let move_txid = Txid::from_slice(deposit_txid._0.as_ref())
                .wrap_err("Failed to convert move txid to Txid")?;
            move_txids.push((start_idx as u64, move_txid));
            start_idx += 1;
        }
        Ok(move_txids)
    }

    async fn collect_withdrawal_utxos(
        &self,
        last_withdrawal_idx: Option<u32>,
        to_height: u64,
    ) -> Result<Vec<(u64, OutPoint)>, BridgeError> {
        let mut utxos = vec![];

        let mut start_idx = match last_withdrawal_idx {
            Some(idx) => idx + 1,
            None => 0,
        };

        loop {
            let withdrawal_utxo = self
                .contract
                .withdrawalUTXOs(U256::from(start_idx))
                .block(BlockId::Number(BlockNumberOrTag::Number(to_height)))
                .call()
                .await;
            match withdrawal_utxo {
                Err(e) if e.to_string().contains("execution reverted") => {
                    tracing::trace!("Withdrawal utxo not found for index, error: {:?}", e);
                    break;
                }
                Err(e) => return Err(e.into()),
                Ok(_) => {}
            }
            let withdrawal_utxo = withdrawal_utxo.expect("Failed to get withdrawal UTXO");
            let txid = withdrawal_utxo.txId.0;
            let txid =
                Txid::from_slice(txid.as_ref()).wrap_err("Failed to convert txid to Txid")?;
            let vout = withdrawal_utxo.outputId.0;
            let vout = u32::from_le_bytes(vout);
            let utxo = OutPoint { txid, vout };
            utxos.push((start_idx as u64, utxo));
            start_idx += 1;
        }
        Ok(utxos)
    }

    pub async fn get_last_deposit_idx(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
    ) -> Result<Option<u32>, BridgeError> {
        let query = sqlx::query_as::<_, (i32,)>("SELECT COALESCE(MAX(idx), -1) FROM withdrawals");
        let result = execute_query_with_tx!(self.connection, tx, query, fetch_one)?;
        if result.0 == -1 {
            Ok(None)
        } else {
            Ok(Some(result.0 as u32))
        }
    }

    /// Returns the last withdrawal index where withdrawal_utxo_txid exists.

            Ok(None)
