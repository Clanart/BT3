### Title
Citrea Light Client Prover Unavailability Permanently Blocks Operator Kickoff Initiation, Causing Permanent Loss of Fronted BTC — (File: `core/src/task/payout_checker.rs`)

---

### Summary

`PayoutCheckerTask::run_once()` places a proactive call to `fetch_validate_and_store_lcp` — which contacts the external Citrea light client prover — inside the same database transaction that assigns the kickoff connector and marks the payout as handled. The call propagates its error with `?`. If the Citrea light client prover is permanently unavailable for the specific payout block height, the entire transaction is rolled back on every retry, the payout is never marked as handled, the kickoff is never initiated, and the operator permanently loses the BTC they fronted for the withdrawal.

---

### Finding Description

`PayoutCheckerTask::run_once()` executes the following sequence inside a single `dbtx`:

1. `handle_finalized_payout` — assigns an unused kickoff connector to the deposit.
2. `fetch_validate_and_store_lcp(payout_block_height, citrea_idx, ...)` — contacts the Citrea light client prover RPC to retrieve and store the LCP receipt.
3. `end_round` (automation feature).
4. `mark_payout_handled` — records the kickoff txid and marks the payout complete.
5. `dbtx.commit()`. [1](#0-0) 

The `?` on step 2 means any error from `fetch_validate_and_store_lcp` propagates out of `run_once`, dropping `dbtx` without committing. Steps 1–4 are rolled back atomically. The payout row remains in the "unhandled" state, so the next poll (60 s in production) re-enters the same code path and fails again.

`fetch_validate_and_store_lcp` calls `get_light_client_proof(payout_block_height, ...)`. If the prover returns `None` for that height, the function converts it to a hard error: [2](#0-1) 

There is no retry loop or grace period inside `fetch_validate_and_store_lcp` itself — a single `None` response is immediately fatal to the entire task iteration.

The same blocking pattern exists in the manual reimbursement path `get_next_txs_to_send`, called by the `GetReimbursementTxs` gRPC endpoint: [3](#0-2) 

Both the automated and manual kickoff-initiation paths are gated behind the same external LCP call, leaving no alternative route for the operator to proceed.

The LCP is only strictly required later, during `send_asserts`, when the operator must prove the payout to a challenger: [4](#0-3) 

Fetching it proactively in `PayoutCheckerTask` is an optimisation, but placing it inside the same atomic transaction as kickoff assignment and `mark_payout_handled` turns an optional prefetch into a hard protocol gate.

---

### Impact Explanation

The operator has already broadcast the payout transaction and transferred BTC to the user. To recover that BTC they must complete the kickoff → challenge-timeout → ReadyToReimburse → Reimburse chain. That chain cannot start until `mark_payout_handled` is committed and a kickoff connector is assigned. Because both are inside the same transaction as the failing LCP fetch, neither is ever persisted. The operator's fronted `bridge_amount` (1 BTC in production config) is permanently unrecoverable. This satisfies the allowed-impact gate: **permanent loss of operator collateral / reimbursement output**. [5](#0-4) 

---

### Likelihood Explanation

The Citrea light client prover is an external HTTP service (`light_client_prover_url`). It can be unavailable for a specific L1 block height if:

- The prover service is down or restarted and loses state for that height.
- A prover bug causes it to skip or permanently omit a proof for a particular height.
- The prover is intentionally shut down or migrated.

The prover is queried by L1 block height, not by a rolling window, so a gap at exactly `payout_block_height` is sufficient to trigger the lock. The operator has no in-protocol escape hatch once the payout is recorded as unhandled. [6](#0-5) 

---

### Recommendation

1. **Decouple the LCP prefetch from kickoff initiation.** Commit `handle_finalized_payout` and `mark_payout_handled` in one transaction, then attempt the LCP fetch in a separate, non-blocking step. A failure to prefetch the LCP should only log a warning; the LCP can be fetched on demand inside `send_asserts` when a challenge actually arrives.

2. **Replace `?` with graceful error handling in `PayoutCheckerTask`.** If `fetch_validate_and_store_lcp` returns an error, log it and continue to `mark_payout_handled` and `dbtx.commit()`. The LCP can be retried independently.

3. **Apply the same fix to `get_next_txs_to_send`.** The manual reimbursement path has the identical blocking `?` and must also be decoupled.

---

### Proof of Concept

1. Operator calls `Withdraw` and broadcasts a payout transaction at Bitcoin block height **H**. The verifier's `update_finalized_payouts` records the payout as unhandled in the DB.
2. The Citrea light client prover is permanently unavailable for height **H** (e.g., prover bug, service outage, or state loss).
3. `PayoutCheckerTask::run_once()` fires. It calls `handle_finalized_payout` (assigns kickoff connector inside `dbtx`), then calls `fetch_validate_and_store_lcp(H, citrea_idx, ...)`.
4. `get_light_client_proof(H, ...)` returns `None`. `fetch_validate_and_store_lcp` returns `Err("Light client proof could not be fetched found for block height H")`.
5. The `?` propagates the error; `dbtx` is dropped and rolled back. The kickoff connector assignment and `mark_payout_handled` are both undone.
6. The task sleeps 60 s and retries. Steps 3–5 repeat indefinitely.
7. The operator calls `GetReimbursementTxs` manually. `get_next_txs_to_send` also calls `fetch_validate_and_store_lcp` with `?` and fails identically.
8. No kickoff transaction is ever sent. The operator's fronted `bridge_amount` is permanently unrecoverable. [7](#0-6) [8](#0-7)

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;

        dbtx.commit().await?;

        Ok(true)
    }
