## Assessment: Valid finding (bounded impact)

I verified the actual sink in the current codebase. Note: the symbols named in the question (`getImageDiff`/`buildDiff` in `app/src/ui/diff/image-diffs/index.ts`) do not exist there — that file only re-exports React components: [1](#0-0) 

The real sink is `getWorkingDirectoryImage` in `app/src/lib/git/diff.ts`, which is the function that actually loads image bytes for the working-directory side of an image diff: [2](#0-1) 

`file.path` is a repo-relative path taken from git status entries (`IStatusEntry` / `AppFileStatusKind`), and `Path.join(repository.path, file.path)` is then passed straight to `readFile` with no `fs.realpath`/containment check and no `fs.lstat` check for a symlink. Node's `fs.promises.readFile` follows symlinks by default, so if the working-directory entry at that repo-relative path is a symlink whose target resolves outside `repository.path`, the bytes read and turned into the base64 `Image` come from the symlink target, not from a file confined to the repo.

This same unguarded `Path.join(repository.path, file.path)` → `readFile`/`fs` pattern recurs elsewhere in the codebase (e.g. syntax highlighting, discard-changes, trash), which indicates this is a systemic trust assumption in Desktop — the working directory itself is trusted once checked out — rather than a defect isolated to the image-diff feature specifically: [3](#0-2) [4](#0-3) 

### Title
Symlink dereference in `getWorkingDirectoryImage` allows working-directory image diff to read file contents outside the repository - (File: `app/src/lib/git/diff.ts`)

### Summary
`getWorkingDirectoryImage` builds the path to read purely with `Path.join(repository.path, file.path)` and calls `readFile` without checking whether the resolved path is a symlink or whether its target stays within `repository.path`.

### Finding Description
A malicious repository can include a tracked symlink (mode `120000`) named e.g. `image.png` pointing to an absolute path outside the working directory. When the user modifies that path locally (or the attacker's repo already reflects it as changed vs. HEAD) and opens the "Changes" view, Desktop's diff machinery ends up calling `getWorkingDirectoryImage(repository, file)`, which does:
```
const contents = await readFile(Path.join(repository.path, file.path))
```
Because `fs.promises.readFile` transparently follows symlinks, `contents` will be the bytes of whatever file the symlink target resolves to on disk — including files outside `repository.path` — and these bytes are base64-encoded into an `Image` and rendered in the diff UI.

### Impact Explanation
This satisfies the "read outside the repo" impact category: the working-directory-scoped read is not actually confined to `repository.path`. However, the practical exposure is limited to local disclosure inside the Desktop renderer (the image preview panel); there is no code path here that automatically transmits the read bytes to a remote attacker, Copilot, or an error report — the attacker only gains information if the local victim subsequently acts on it (e.g., re-commits/pushes the file back, or the content is exposed via other renderer-accessible surfaces). Severity should be assessed as local file-read/disclosure, not remote exfiltration by itself.

### Likelihood Explanation
Moderate. Requires the victim to clone/fetch an attacker-controlled repo containing a symlinked "image" file, and to open the Changes/History image diff for that path after it is committed as changed. `core.symlinks` must be enabled (the Git/Desktop default on macOS/Linux; on Windows, symlink checkout support depends on developer mode/privileges, which reduces likelihood there).

### Recommendation
Before calling `readFile` in `getWorkingDirectoryImage` (and the analogous pattern in `getNewFileContent`/other working-directory readers), verify the target is a regular file within the repository: use `fs.lstat`/`fs.realpath` on the resolved path and reject (or special-case) entries that are symlinks resolving outside `repository.path`.

### Proof of Concept
1. Attacker creates a repo with a symlink `image.png -> /etc/passwd` (or any file outside the repo), commits it, and pushes.
2. Victim clones the repo in Desktop, then modifies the symlink target file's content out-of-band (or the repo already shows it as changed relative to HEAD).
3. Victim opens the file in the Changes list; Desktop invokes `getWorkingDirectoryImage`, which follows the symlink via `readFile(Path.join(repository.path, 'image.png'))`.
4. The rendered "image" diff actually reflects the contents of `/etc/passwd` (or whichever external file), confirming the containment bypass. [2](#0-1) 

**Caveat:** I could not verify the exact call chain that dispatches to `getWorkingDirectoryImage` (the `getImageDiff`/`buildDiff` naming in the question does not match current source, and I was unable to trace the caller before the iteration budget ran out) — I recommend confirming with a full-index Devin session that this function is indeed reached specifically for symlinked files classified as images by extension, and that no upstream `AppFileStatusKind`/status-parser logic already filters out symlink entries before this point.

```typescript
export async function getWorkingDirectoryImage(
  repository: Repository,
  file: FileChange
): Promise<Image> {
  const contents = await readFile(Path.join(repository.path, file.path))
  return new Image(
    contents.buffer,
    contents.toString('base64'),
    getMediaType(Path.extname(file.path)),
    contents.length
  )
}
```
