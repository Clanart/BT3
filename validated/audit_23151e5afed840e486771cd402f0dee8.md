### Title
Cached FROST preprocess seed is never consumed/invalidated, deterministically re-deriving identical signing nonces on every signing attempt for the same context — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

The PyCrypto bug class is "PRNG output reused because it was never reseeded before a second consumer accessed it." Serai's FROST signing path contains the same structural flaw: `SigningProtocol::preprocess_internal` stores the `CachedPreprocess` seed in the database keyed only by `context`, and **never deletes or rotates it**. Every subsequent call re-seeds a `ChaCha20Rng` from that identical seed, deterministically re-deriving the same FROST nonce pair `(d, e)` — so any two signing invocations that share the context but differ in message or participant set reuse the same nonces, enabling private key share recovery.

### Finding Description

In `preprocess_internal`, the seed is written once (`if CachedPreprocesses::get(...).is_none() { ... CachedPreprocesses::set(...) }`) and then read back on **every** call, including all future calls, with no removal: [1](#0-0) 

`from_cache` routes to `seeded_preprocess`, which feeds the stored seed into `ChaCha20Rng::from_seed` and derives nonces via `Commitments::new` → `Curve::random_nonce(secret_share, rng)` — the nonce is a pure function of `seed || secret_share`; the message and session are **not** mixed in: [2](#0-1) [3](#0-2) 

`share_internal` calls `preprocess_internal` again to rebuild the machine, and `DkgConfirmer::complete` calls `share_internal` a second time. `share`/`complete` take attacker-supplied `preprocesses` and a `key_pair` that feeds `set_keys_message` as `msg`, while `removed` can change which participants map in: [4](#0-3) [5](#0-4) 

In `AlgorithmSignMachine::sign`, the effective nonce is `d + rho·e` where `rho` is bound to `hash_msg(msg)`, the group key, and the committed preprocess set. Two sign calls under the same context with different `msg`/`preprocesses` reuse `(d, e)` but produce shares `s_i = d + rho_i·e + λ·x·c_i` with distinct `(rho_i, c_i)` — each additional reused-nonce share is another linear equation in `(d, e, λx)`, and three such shares recover the secret share `x`. [6](#0-5) 

The FROST spec itself concedes the consequence: "Reusing preprocesses would enable a third-party to recover your private key share" — the library-level contract (delete after one use) is not enforced here because the DB entry is never deleted: [7](#0-6) 

### Impact Explanation

Recovery of the validator's Ristretto secret key share. The share signs `set_keys_message` confirming validator-set key pairs via `dkg_musig`/`Schnorrkel`; compromise of the FROST secret share for that MuSig instance undermines the threshold confirmation signature on substrate key-set updates. This is secret-key material leakage caused purely by deterministic nonce reuse — the exact outcome the caching design documentation warns about, made systematic rather than accidental because the seed persists and is re-used automatically by `share` → `complete` and any retry/reboot path.

### Likelihood Explanation

The reuse is deterministic, not probabilistic: *every* call to `preprocess_internal` for a given `context` returns the identical nonces. Whether a validator can be induced to produce multiple shares under one context with differing `msg`/`rho` depends on the surrounding tributary protocol (retries after reboot, varying `removed` sets, or differing `preprocesses` maps supplied by other validators — which are untrusted inputs). Peer validators control the `preprocesses` HashMap fed to `share`/`complete`, and `msg` varies with `key_pair` and `removed`, so divergence in `rho`/`c` across calls is reachable without any misbehavior by the victim beyond normal operation. The missing `CachedPreprocesses::remove` (or equivalent single-use guard) means there is no code path that prevents it.

Caveat: this analysis is based on the indexed code; the precise set of upstream callers that can drive `share`/`complete` with divergent messages under one context (e.g., whether `attempt`/context uniqueness is guaranteed per distinct `msg`) could not be fully traced within the available context.

### Recommendation

Delete the cached seed upon first consumption — e.g., `CachedPreprocesses::remove(txn, &context)` inside `share_internal` after rebuilding the machine — so a seed can never seed a second signing session. Alternatively/and additionally, bind the nonce derivation to the session: mix `msg` and the committed preprocess set into the `random_nonce` seed, or store a monotonically incremented counter alongside the seed in `CachedPreprocesses` and mix it into the `ChaCha20Rng` seed, guaranteeing distinct `(d, e)` even if the record is reused.

### Proof of Concept

1. For a fixed context `(b"DkgConfirmer", attempt)`, `preprocess_internal` stores seed `S` once; all later calls recompute `nonces = (d, e) = f(ChaCha20Rng(S), secret_share)` — identical every time (`signing_protocol.rs:123-147`, `frost/src/sign.rs:127-132`, `frost/src/curve/mod.rs:98-117`).
2. Invoke `share(preprocesses_A, key_pair_A)` → emits `s1 = d + rho_1·e + λ·x·c_1`.
3. Invoke `share`/`complete` again with different peer `preprocesses_B` or a differing `key_pair_B`/`removed` set → `rho_2 ≠ rho_1`, `c_2 ≠ c_1`, but the same `(d, e)` → emits `s2 = d + rho_2·e + λ·x·c_2`.
4. A third divergent call yields `s3`. Solve the 3×3 linear system over the scalar field for `(d, e, λx)`; divide out the known Lagrange coefficient `λ` to recover the validator's secret share `x`.

  fn random_nonce<R: RngCore + CryptoRng>(
    secret: &Zeroizing<Self::F>,
    rng: &mut R,
  ) -> Zeroizing<Self::F> {
    let mut seed = Zeroizing::new(vec![0; 32]);
    rng.fill_bytes(seed.as_mut());

    let mut repr = secret.to_repr();

    // Perform rejection sampling until we reach a non-zero nonce
    // While the IETF spec doesn't explicitly require this, generating a zero nonce will produce
    // commitments which will be rejected for being zero (and if they were used, leak the secret
    // share)
    // Rejection sampling here will prevent an honest participant from ever generating 'malicious'
    // values and ensure safety
    let mut res;
    while {
      seed.extend(repr.as_ref());
      res = Zeroizing::new(<Self as Curve>::hash_to_F(b"nonce", seed.deref()));
      res.ct_eq(&Self::F::ZERO).into()
    } {
      seed = Zeroizing::new(vec![0; 32]);
      rng.fill_bytes(&mut seed);
    }
    repr.as_mut().zeroize();

    res
  }

# Caching

modular-frost supports caching a preprocess. This is done by having all
preprocesses use a seeded RNG. Accordingly, the entire preprocess can be derived
from the RNG seed, making the cache just the seed.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
