### Title
OAuth session-confusion in `resolveOAuthRequest` allows a stale/attacker-timed callback response to complete a *different* sign-in session with the wrong account - (File: app/src/lib/stores/sign-in-store.ts)

### Summary
`SignInStore.resolveOAuthRequest` validates the OAuth `state` (CSRF token) against `this.state.oauthState` *before* awaiting the network calls, but re-reads `this.state.oauthState` *after* the awaits complete to invoke `onAuthCompleted`/`onAuthError`. Because `this.state` is a mutable field (not a captured local), it can be replaced in the interim by `reset()` followed by a new `beginDotComSignIn`/`authenticateWithBrowser()` call, causing the callback of the *new* session to be invoked with the account resolved by the *old* session's network round trip.

### Finding Description
In `resolveOAuthRequest`: [1](#0-0) 

- The function captures `endpoint` from `this.state` and checks `this.state.oauthState.state !== action.state` before the `await requestOAuthToken(...)` / `await fetchUser(...)` calls.
- After both awaits resolve, it calls `this.state.oauthState.onAuthCompleted(account)` — but this expression re-reads the **current** `this.state`, not the state that was validated at function entry. TypeScript's control-flow narrowing makes this look safe at compile time, but at runtime `this.state` is a plain mutable class field that can be swapped out during the `await` suspension.
- `reset()` does not cancel or track in-flight `requestOAuthToken`/`fetchUser` promises; it only calls the *old* state's `oauthState.onAuthError` and nulls out `this.state`: [2](#0-1) 
- If, while `resolveOAuthRequest` for session A is awaiting the network, the app calls `reset()` and then starts a brand-new session B via `beginDotComSignIn` → `authenticateWithBrowser`, a fresh `oauthState` (with a new CSRF token and a new `onAuthCompleted`/`onAuthError` resolve/reject pair) is installed on `this.state`: [3](#0-2) 
- When session A's `resolveOAuthRequest` promise chain finally resolves, line 353 (`this.state.oauthState.onAuthCompleted(account)`) fires the **new session B's** `resolve` function with the account that was fetched using **session A's** endpoint/token. Session B's `.then()` handler in `authenticateWithBrowser` only checks that `this.state.kind === SignInStep.Authentication` — which is true because it *is* session B's state — so it accepts the account and calls `emitAuthenticate(account)`, then transitions to `SignInStep.Success` using session B's `resultCallback`: [4](#0-3) 

The net effect: the UI/flow that the user believes is session B (e.g., a GitHub.com sign-in) is silently completed with an `Account` object that was actually produced by session A's endpoint (e.g., a GitHub Enterprise URL the user previously typed in, or one reached via a redirect/deep-link-triggered flow). Since `fetchUser`'s response for session A's endpoint is attacker-influenced if that endpoint is attacker-controlled (e.g., a malicious/compromised Enterprise host reached earlier in the flow), this allows an attacker-influenced `Account` (arbitrary login/name/token/endpoint fields as returned by the enterprise API) to be bound into the app as if it were the result of the legitimate session B flow — a session-confusion / account-binding issue, not merely a stale-response no-op.

Unlike the analogous `.catch()` handler in `authenticateWithBrowser`, which re-validates `this.state.oauthState?.state === csrfToken` before touching state, there is no equivalent re-validation guard on the success path inside `resolveOAuthRequest`, nor is the originally-checked `oauthState` object captured into a local variable before the awaits.

### Impact Explanation
This allows unauthorized OAuth/account binding: an account resolved from one sign-in session's network exchange can be delivered into a completely different, unrelated sign-in session, silently substituting the account the user believes they're signing into. Combined with the fact that `endpoint`/account data for the "old" session may originate from a source not fully trusted by the user in the new context, this can result in the wrong (or attacker-supplied) account being added to the local `AccountsStore` and used for subsequent Git/API operations.

### Likelihood Explanation
Exploitation requires a specific timing window: a first sign-in flow (session A) must be in the state where `resolveOAuthRequest` has been called and is awaiting `requestOAuthToken`/`fetchUser`, and during that window `reset()` + a new sign-in (session B) must be initiated before session A's promise settles. This requires either attacker control over response timing/delay of the OAuth token/user-fetch endpoint (e.g., a slow/malicious Enterprise server) combined with normal user actions (cancel and re-attempt sign-in), or some other trigger that calls `reset()` mid-flight (e.g., app-level `beginDotComSignIn`/`beginEnterpriseSignIn` invoked again). It is a genuine logic bug but requires a race window, so likelihood is moderate rather than trivially always exploitable.

### Recommendation
- Capture the validated `oauthState` (and CSRF token) into a local variable at the top of `resolveOAuthRequest`, before the `await` calls, and use that captured reference (not `this.state.oauthState`) to invoke `onAuthCompleted`/`onAuthError`.
- Additionally re-validate that `this.state?.kind === SignInStep.Authentication && this.state.oauthState?.state === <captured csrfToken>` immediately before calling `onAuthCompleted`, mirroring the guard already used in the `.catch()` block of `authenticateWithBrowser`.
- Consider having `reset()` also invalidate any in-flight `resolveOAuthRequest` (e.g., via an `AbortController` or a per-session generation counter) so stale responses are dropped rather than acted upon.

### Proof of Concept
1. Start Enterprise sign-in flow (session A) pointing at an endpoint the attacker can delay/control the response from; trigger `authenticateWithBrowser()` → `resolveOAuthRequest(actionA)` is invoked and is awaiting `requestOAuthToken`/`fetchUser`.
2. While that await is pending, call `signInStore.reset()`.
3. Immediately call `beginDotComSignIn()` then `authenticateWithBrowser()` to start session B; this installs a new `oauthState` (new CSRF token, new `onAuthCompleted`) on `this.state`.
4. Let session A's delayed `fetchUser` response resolve. Observe that `this.state.oauthState.onAuthCompleted(account)` (session B's resolve function) is invoked with the account fetched from session A's endpoint.
5. Confirm via `onDidAuthenticate` listener / resulting `SignInStep.Success` state that session B's flow completed and emitted the account originating from session A, despite `action.state`/CSRF for session A never matching session B's token. [1](#0-0) [2](#0-1)

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
