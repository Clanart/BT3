## Title
`getWorkingDirectoryDiff` diffs renamed files against the index instead of HEAD, letting attacker-staged index content be silently committed without appearing in the reviewed diff - (File: `app/src/lib/git/diff.ts`)

### Summary
The seed report's broken invariant is: *the value used for a calculation/decision (`sqrtPriceX96`) is not the current authoritative value, but a stale/alternate source, so the computed result (token amounts) silently diverges from what the user actually gets.* The Desktop analog with the same broken invariant is `getWorkingDirectoryDiff` in `app/src/lib/git/diff.ts`, which for `Renamed` files diffs the working tree against the **index**, not against **HEAD** — while every other file status (`New`, `Untracked`, `Modified`, etc.) is diffed against `HEAD`. This means the diff a user reviews before committing a rename can silently omit content that is *already staged* in the index, exactly mirroring "using the wrong reference value produces a wrong/incomplete result the user relies on."

### Finding Description
`getWorkingDirectoryDiff` builds the `git diff` arguments differently depending on file status: [1](#0-0) 

For `AppFileStatusKind.Renamed`, the code intentionally diffs the on-disk file against the index (default `git diff <path>` behavior with no revision arg), rather than against `HEAD` like every other status branch. The comment in the source explicitly documents this as a known incorrectness:

> "NB: Technically this is incorrect, the best kind of incorrect. In order to show exactly what will end up in the commit we should perform a diff between the new file and the old file as it appears in HEAD. By diffing against the index we won't show any changes already staged to the renamed file which differs from our other diffs."

This is functionally the same class of bug as the seed report: the diff engine consults a **non-authoritative reference point** (the index, which can already contain attacker-influenced staged content) instead of the value that actually determines what change set the app is about to build (`HEAD`, the true baseline for `createCommit`). `createCommit` itself always resets the index (`unstageAll`) and re-stages exactly the files/selections the user approved via `stageFiles`: [2](#0-1) 

So if the index already contains staged content for a renamed file *before* Desktop calls `unstageAll`/`stageFiles`, and the user has that file's `DiffSelectionType.All` selection, `stageFiles` re-adds the working-tree content for that path (`updateIndex(repository, normal)`), meaning whatever is on disk — not what the diff view showed — ends up in the commit: [3](#0-2) 

The result: a rename whose diff was reviewed against a stale/attacker-influenced index baseline can hide additional changes from the reviewer, yet those changes are still what gets committed (since the true commit is built from the working tree via `stageFiles`, and the diff review is the only gate a user has).

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": a user could review what looks like a clean, small rename diff and approve a commit that actually contains attacker-influenced content that was never surfaced in the UI. This is most reachable when a repository ships a pre-checkout/merge workflow (or any process that manipulates the index for a renamed path) that leaves stray staged content in the index prior to Desktop computing the diff (e.g., during merge/rebase/cherry-pick continuation flows or externally-run git commands the user triggers from a linked terminal) — Desktop then shows an incomplete diff for that rename while the eventual commit/push includes the full on-disk content.

### Likelihood Explanation
Likelihood is limited by the precondition that the index must already contain staged content for the renamed path before Desktop's diff is computed, and it only affects the specific `Renamed` code path. Desktop's git-hook interception (`app/src/lib/hooks/with-hooks-env.ts`, `hooks-proxy.ts`) does not appear to auto-run hooks like `post-checkout`/`post-merge` for arbitrary git operations invoked outside `interceptHooks`-enabled calls, so a hook-based automatic exploitation chain could not be fully confirmed within available context — this is a caveat on likelihood rather than on the underlying defect, which is self-documented in the source as a correctness bug independent of any specific trigger.

### Recommendation
Change the `Renamed` branch of `getWorkingDirectoryDiff` to diff against `HEAD` (consistent with all other status kinds), matching what will actually be produced by `createCommit`/`stageFiles`, rather than against the index.

### Proof of Concept
Conceptual reproduction (not fully verified against a live index-staging trigger within available tooling):
1. Rename `foo` to `bar` and commit (`bar` now tracked, clean).
2. Stage extra content into the index for `bar` directly (e.g., via a script/hook run outside Desktop's controlled `stageFiles` sequence) without changing the working tree copy shown by Desktop yet, or vice versa — such that index and HEAD diverge for `bar`.
3. Modify `bar` further on disk.
4. Open Desktop's Changes view: `getWorkingDirectoryDiff` for the `Renamed` file diffs working tree vs. index, so any content difference between index and HEAD is invisible to the reviewer.
5. Commit via `_commitIncludedChanges` → `createCommit` → `stageFiles`, which re-stages the full on-disk content of `bar`, producing a commit whose actual diff against HEAD includes the hidden content that was never shown in step 4. [1](#0-0) [4](#0-3) [5](#0-4)

```typescript
export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }
```
