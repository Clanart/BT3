## Title
Pooled per-token escrow accounting in Tron `IntentGatewayV2::placeOrder`/`withdraw` allows one order leg to drain escrow reserved for another leg sharing the same token — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Sherlock report's root cause was that `Launch.sol` updated a per-user token-accounting variable using the wrong quantity (a total/pooled value instead of the delta owed to that specific action), causing later legitimate operations to underflow or be shortchanged. The Tron variant of Hyperbridge's `IntentGatewayV2` has the same accounting shape: escrow is tracked as a single pooled value per `(commitment, token)` pair, `_orders[commitment][token]`, and `withdraw()` releases whatever amount the caller-supplied `WithdrawalRequest` specifies out of that pool while only checking `_orders[commitment][token] == 0` — never that `amount` is bounded by that leg's rightful share of the pool.

### Finding Description
In the mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`), `placeOrder` explicitly guards against this class of bug: [1](#0-0) 
this rejects duplicate input token addresses in the same order (`revert InvalidInput()` if `_orders[commitment][token] != 0`), guaranteeing a 1:1 mapping between an order's input index and its escrow slot.

The Tron contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) removed this guard. Its `placeOrder` instead **accumulates** into the pooled slot with `+=`, with no check for a pre-existing balance: [2](#0-1) [3](#0-2) 

This means a user can place a single order whose `inputs[]` array references the same token address at two different indices (e.g., legs intended to correspond to two different output assets/beneficiaries or two different partial redemption events). Both amounts land in the *same* `_orders[commitment][token]` bucket instead of being tracked separately per leg — exactly analogous to `Launch.sol` tracking `userTokens` as one aggregate number instead of per-participation deltas.

`withdraw()` then releases funds against this pooled bucket using only a non-zero check, not a sufficiency check against the specific `amount` being paid out: [4](#0-3) 

Compare this to the sibling same-chain fill logic in `IntrinsicIntents.sol`, which demonstrates the exact hazard this pooling creates: on completion of any single output leg, the contract releases the **entire remaining pooled escrow for that token address**, not the amount proportional to that specific leg: [5](#0-4) 

Because the Tron contract shares the identical `mapping(bytes32 => mapping(address => uint256)) public _orders` pooling model and the identical withdraw-by-token-address pattern, but has *removed* the duplicate-input-token guard that the mainline contract relies on to make that pooling safe, a `WithdrawalRequest` (built either locally for same-chain cancel/fill or dispatched cross-chain via `RedeemEscrow`/`RefundEscrow`) that targets one leg's amount is checked only against "is the bucket non-empty," not "does the bucket contain enough to cover exactly this leg without touching the other leg's reserved funds."

### Impact Explanation
This falls squarely within the bounty's "loss of funds" and "logic attacks / broken invariant" categories. An order with two legs sharing a token address lets the first-settled leg (fill, cancel, or cross-chain redeem/refund) drain a pooled balance that includes funds contractually reserved for the second, not-yet-settled leg. The second leg's rightful beneficiary is later denied funds (locked/lost) or the transaction reverts once the pool has been exhausted (`_orders[body.commitment][token] == 0` check reverting `UnknownOrder`), permanently stranding whatever remained committed to that leg. This is the same failure mode as the `Launch.sol` report: an aggregate/pooled accounting variable is decremented/read using the wrong granularity, producing DOS on cancellation/redemption and stuck/lost user funds, without requiring any malicious relayer, prover, or admin — only an unprivileged user placing a structured order and an unprivileged solver/counterparty triggering settlement of one leg before the other.

### Likelihood Explanation
No documented validation elsewhere in the Tron contract enforces uniqueness of `order.inputs[].token`; the removal of the check present in the mainline EVM sibling appears to be an unintentional divergence between the two implementations of the same protocol rather than a deliberate design difference (the doc comments for both are otherwise identical). Placing an order with a repeated input token is a normal, permissionless action requiring no special privileges, and settlement of individual legs (fill, cancel, cross-chain redeem) is likewise permissionless once the order exists, making this readily triggerable by any user/solver pair on the Tron deployment.

### Recommendation
Port the mainline EVM guard into the Tron contract's `placeOrder`: reject orders whose `inputs[]` contains a token address already recorded for that commitment (`if (_orders[commitment][token] != 0) revert InvalidInput();`) before crediting escrow, restoring the 1:1 invariant between an input index/leg and its escrow slot. Additionally, harden `withdraw()` to check `amount <= _orders[body.commitment][token]` (not just `!= 0`) before transferring and decrementing, so any future pooling regression fails safely with a clear revert rather than silently over-releasing funds belonging to another leg.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: 500}, {token: USDC, amount: 300} ]`, intended to back two separate output legs (e.g., two different beneficiaries/destinations via separate order legs or repeated cross-chain redemptions). Because there is no duplicate-token check, `_orders[commitment][USDC]` becomes `500 + 300 = 800` (`evm/tron/contracts/apps/IntentGatewayV2.sol:435,457`).
2. The first leg is settled (e.g., a solver fills/cancels/redeems leg 1). The `WithdrawalRequest` built for that settlement, following the same pattern as `IntrinsicIntents.sol:116-123`, resolves the released amount against the pooled `_orders[commitment][USDC]` balance rather than the leg-specific 500. `withdraw()` transfers out an amount up to the full 800 pool and only checks `_orders[commitment][USDC] == 0` before doing so (`evm/tron/contracts/apps/IntentGatewayV2.sol:691-701`).
3. When leg 2's settlement is attempted afterward, `_orders[commitment][USDC]` is already 0 (or insufficient), so `withdraw()` reverts with `UnknownOrder`, permanently denying the rightful beneficiary of leg 2 their escrowed 300 USDC — a direct loss/lock of user funds caused purely by pooled-accounting logic, requiring no malicious relayer or admin.
