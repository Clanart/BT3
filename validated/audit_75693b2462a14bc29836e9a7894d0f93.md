### Title
Corrupted `CodedInputStream` limit stack on unrecognized packed-enum extension value causes silent mis-parsing of subsequent fields - (File: `java/core/src/main/java/com/google/protobuf/GeneratedMessageLite.java`)

### Summary
`ExtendableMessage.parseExtension` in the Lite runtime parses packed repeated extension enum values inside a length-delimited region established via `input.pushLimit(length)`. When an unrecognized enum value is encountered mid-loop, the code executes `return true;` directly out of `parseExtension` (`GeneratedMessageLite.java:717-721`) without ever calling the matching `input.popLimit(limit)` at line 733. This is structurally the same bug class as the Debita report: a `return` used where only the *inner iteration/scope* should be aborted, silently skipping mandatory bookkeeping (there, updating incentive mappings for later array elements; here, restoring the parser's limit stack) and leaving state corrupted for everything that follows.

### Finding Description
The relevant flow, all attacker-reachable through any public `parseFrom`/`mergeFrom` API on a `GeneratedMessageLite.ExtendableMessage` subtype (Lite runtime, used pervasively on Android and in performance-sensitive server code) that has a registered enum extension: [1](#0-0)

`pushLimit`/`popLimit` on `CodedInputStream` form a stack that bounds how many bytes the current length-delimited region is allowed to consume; `popLimit` restores the previous limit and updates `bufferSizeAfterLimit` bookkeeping so subsequent reads outside this sub-message see the correct remaining byte count. When the attacker supplies a packed enum extension payload containing **any single unrecognized enum value that is not the last element**, the loop hits `return true;` and exits `parseExtension` entirely — skipping:
1. The remaining bytes of the packed array (never consumed, never validated), and
2. The `input.popLimit(limit)` call that must run to restore the outer limit.

Because `popLimit` is never invoked, the `CodedInputStream`'s internal limit/`bufferSizeAfterLimit` state remains set to the (now stale) inner packed-field limit while the enclosing message-parsing loop (`parseUnknownField` caller in the generated `mergeFrom`) continues reading the *next* tag/field from the stream as if the previous limit had been correctly popped. This is the direct analog of the Debita `return` bug: a control-flow shortcut intended to only affect the current element ("drop this one enum value") instead unwinds an entire enclosing scope, silently corrupting bookkeeping state that subsequent, otherwise-valid processing depends on (there: `lentAmountPerUserPerEpoch`/`totalUsedTokenPerEpoch`/`borrowAmountPerEpoch` for later array elements; here: the limit stack governing how many more bytes the parser believes remain in the current sub-region).

The non-packed enum-extension sibling path (`GeneratedMessageLite.java:757-765`) has the identical `return true;` shortcut, but there is no `pushLimit`/`popLimit` pair to corrupt for a singular field, so only the packed-array code path is structurally hazardous.

### Impact Explanation
This breaks the wire-format invariant that a length-delimited region's byte-accounting must be exactly balanced (`pushLimit` always paired with `popLimit` before the surrounding parse loop proceeds). Once the limit stack is left in an inconsistent state, parsing of the remainder of the outer message becomes undefined relative to the true byte layout: depending on stream buffering internals, subsequent fields can be misread (wrong tag/length interpreted), the parser can throw an unexpected `InvalidProtocolBufferException` (denial of parsing for otherwise well-formed messages), or, in the best case, the remaining packed enum entries are silently dropped without error even though the wire data was well-formed. All three are integrity/availability failures directly reachable from ordinary bounded-size attacker input through the public `parseFrom` API, with no privileged access required — squarely inside the stated exposure assumption for a public Protobuf parse API. This is comparable in class (not in financial magnitude) to the original report's "later valid elements are silently dropped due to premature `return`", but the Protobuf analog additionally corrupts shared parser cursor state rather than only a local map/array's remaining slice.

### Likelihood Explanation
Reachable whenever: (1) the target message is a `GeneratedMessageLite.ExtendableMessage`, (2) it declares (and the parsing extension registry recognizes) a repeated, packed `enum` extension field, and (3) the attacker sends a packed field whose bytes decode to at least one enum-number value not present in the enum's generated value set, followed by at least one more encoded varint value or any subsequent field in the outer message. All of these are ordinary, schema-compliant conditions requiring no malformed varints, oversized allocations, or resource exhaustion — only a value outside the enum's known number range, which is trivial for any attacker-controlled binary payload to produce. Likelihood is High for any application using Lite-runtime packed enum extensions with attacker-supplied binary Protobuf.

### Recommendation
Replace the early `return true;` inside the packed-enum loop with logic that only skips the current unrecognized value (`continue;`) while still recording it via `mergeVarintField` (matching the non-packed enum branch's behavior) or via the packed-field unknown-value fallback, and unconditionally execute `input.popLimit(limit)` before leaving the `packed` block, e.g. wrap the loop in a `try/finally` that guarantees `popLimit` runs regardless of the early exit. The general fix pattern mirrors the audited Debita fix: change control flow so an invalid element is skipped rather than aborting the entire bounded region, and ensure any push/acquire operation (`pushLimit`, mapping entry, etc.) has a matching pop/release performed on every exit path.

### Proof of Concept
Reasoning-level PoC (exact runtime `CodedInputStream` internal-state assertions were not executed in this environment; the code path itself is confirmed present and reachable):
1. Define a proto2 Lite extension `repeated MyEnum ext = N [packed = true];` on some extendable message `M`, where `MyEnum` has only value `A = 0`.
2. Craft raw bytes for `M`: a packed field with tag/wiretype length-delimited for `ext`, `length = 2`, payload bytes `[1, 0]` (varint `1` = unrecognized enum number, varint `0` = `A`), followed immediately by bytes encoding a second, unrelated known field of `M` (e.g., an `int32` field with a small value).
3. Call `M.parseFrom(bytes)` through the generated Lite parser.
4. Expected (if the code were correct): either the malformed `1` is skipped/recorded as unknown and the following int32 field is parsed correctly, or a clean `InvalidProtocolBufferException` is thrown.
5. Actual code path: at `GeneratedMessageLite.java:714-721`, `rawValue = 1` yields `value == null`, so `return true;` fires before consuming the remaining packed byte `0` and before `input.popLimit(limit)` at line 733 runs. The outer parsing loop then continues to read the next tag from a stream whose limit bookkeeping was never restored, so parsing of the subsequent int32 field is performed against a corrupted byte-boundary. Full dynamic confirmation (e.g., asserting the parsed value of the trailing field, or observing an unexpected exception) requires running this scenario in a build environment, which was not available in this session — this should be verified with an actual `forge`-equivalent Java unit test (`ExtendableMessage` + a packed enum extension + the byte sequence above) before treating the impact assessment as fully proven.
