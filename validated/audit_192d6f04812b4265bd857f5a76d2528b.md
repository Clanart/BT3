### Title
Message-boundary desync across sequential delimited-message parses on a shared `InputStream` due to missing post-parse consumption check - (File: `java/core/src/main/java/com/google/protobuf/AbstractMessageLite.java`)

### Summary
The Traffic Server CVE-2024-38311 is a request-smuggling bug: after Traffic Server parses a chunked message body, it fails to guarantee that the parser's notion of "end of body" is perfectly synchronized with the number of bytes it has actually consumed from the connection, so pipelined bytes belonging to the *next* request get misattributed to a prior boundary decision. The transferable invariant is: **when a framing layer declares an explicit length for a sub-unit of a shared stream, the consumer of that sub-unit must be verified to have consumed exactly that many bytes before the stream is handed back for parsing the next sub-unit; if the inner parser can terminate "successfully" early, the leftover bytes must be resynchronized (skipped) rather than silently left for the next read.**

Protobuf's Java delimited-stream API (`mergeDelimitedFrom(InputStream, ...)`, used to frame multiple protobuf messages back-to-back on one persistent `InputStream`, e.g. length-prefixed streaming/IPC protocols) implements exactly this length-prefixed-framing-over-shared-stream pattern, and does not enforce that the inner parse consumed the declared `size` before returning success.

### Finding Description
`AbstractMessageLite.mergeDelimitedFrom` reads a varint `size`, wraps the underlying stream in a `LimitedInputStream` capped to `size` bytes, and merges the message from that limited view: [1](#0-0) 

Protobuf's wire format treats a `readTag()` result of `0` as the legitimate "end of message" sentinel — this is the same signal used both for genuine stream EOF and for an in-band `0x00` byte encountered at a field boundary. `mergeFrom` loops read tags until this sentinel is hit, then trust `checkLastTagWas(0)` as the sole framing-completion check: [2](#0-1) 

Nothing in `mergeDelimitedFrom` (nor in `GeneratedMessageLite`'s parallel implementation) verifies that the `LimitedInputStream`'s remaining `limit` is `0` — i.e., that all `size` declared bytes were actually consumed — before returning success: [3](#0-2) 

`LimitedInputStream` itself is a thin pass-through proxy (it does not buffer or discard the unread remainder on its own): [4](#0-3) 

Consequently, if an attacker-controlled message body (bounded, within the declared `size`) contains an embedded `0x00` byte positioned so it is read as a tag rather than as data (e.g. crafted padding/trailing bytes after the legitimate encoded fields but still inside the declared `size`), the parser can hit the `tag==0` sentinel and terminate "successfully" *before* consuming all `size` bytes. `checkLastTagWas(0)` passes because that is exactly the condition it checks. The leftover, unread bytes of the current logical message remain unread on the underlying, shared `InputStream`. If the caller — a normal, documented usage pattern for streaming multiple length-prefixed protobuf messages over one connection — then calls `mergeDelimitedFrom` again to parse the "next" message, it will start reading from the stale, un-skipped tail of the previous message rather than from the true start of the next frame. The parser's idea of where message *N* ends (the `tag==0` sentinel) has desynchronized from the framing layer's declared length for message *N*, and that desync bleeds attacker-controlled bytes into the parse of message *N+1* — the direct analog of request smuggling via chunked-body/pipelining desync.

C++'s equivalent utility explicitly documents and mitigates this exact hazard class by requiring callers to reuse the *same* buffered `ZeroCopyInputStream` object across calls (so any bytes read ahead of the true boundary remain in that object's buffer and are correctly consumed by the next parse): [5](#0-4) 

and additionally performs an explicit post-parse consumed-length check that Java's implementation lacks: [6](#0-5) 

Java's plain `InputStream`-based API offers no equivalent object to "keep reusing" (an `InputStream` is not seekable/re-buffered the same way), and it has no analogous length-consumed assertion, so the mitigating discipline documented for the C++ API is both inapplicable and unenforced on the Java path.

### Impact Explanation
This is a message-boundary confusion / framing desync, not a memory-safety bug: an attacker who controls the content of one bounded, length-prefixed message in a stream of sequential protobuf messages (a legitimate consuming-application pattern — persistent IPC/log/streaming connections that call `parseDelimitedFrom`/`mergeDelimitedFrom` in a loop) can cause the parser to silently under-consume the declared frame, corrupting how the *next* message on the same stream is parsed. Depending on the consuming application, this can let an attacker inject or splice bytes into a message nominally authored/framed by someone else on the same connection (integrity impact), analogous to how HTTP request smuggling lets one client's request tail be interpreted as another request's start. Severity is bounded by the fact that it requires two conditions the consuming application must already satisfy: (1) multiple delimited messages shared on one persistent stream, and (2) no independent authentication/authorization boundary between successive frames.

### Likelihood Explanation
Likelihood is moderate: the trigger only requires an attacker to control the byte content of one bounded delimited message (matching the stated threat model of a client sending bounded protobuf through a public parse API) and to embed a `0x00` byte at a field-boundary-aligned position within the declared `size`, which is straightforward to construct deterministically. It does not require malformed schemas, huge inputs, or privileged access. It does require the specific "multiple delimited messages over one persistent stream" usage pattern, which is a common but not universal way applications use `parseDelimitedFrom`.

### Recommendation
In `AbstractMessageLite.mergeDelimitedFrom` (and the analogous `GeneratedMessageLite.parsePartialDelimitedFrom`/`Parser`/`AbstractParser` delimited paths), after merging from the `LimitedInputStream`, verify that the limit was fully drained (e.g., expose and check `LimitedInputStream`'s remaining `limit == 0`, or explicitly skip any remainder) before returning success, and throw `InvalidProtocolBufferException` (truncated/unconsumed message) otherwise — mirroring the explicit consumed-length check already performed in `ParseDelimitedFromCodedStream` for C++.

### Proof of Concept
Conceptual reproduction (not executed, per index limitations — a background Devin session would be needed to run this against the actual Java runtime):
1. Build a byte buffer: `varint(size=100)` + `<valid encoded field(s) totaling 5 bytes>` + `0x00` + `<95 bytes of arbitrary "smuggled" content>`.
2. Call `SomeMessage.parseDelimitedFrom(sharedInputStream)` on this buffer. The parse succeeds (tag `0` at byte 6 is read as end-of-message; `checkLastTagWas(0)` passes) after consuming only 6 of the declared 100 bytes.
3. Immediately call `SomeMessage.parseDelimitedFrom(sharedInputStream)` again on the *same* stream to read the "next" frame. Instead of reading the intended next frame's varint length, it reads from the 95 bytes of attacker-controlled leftover content from step 1 — demonstrating the boundary desync and cross-message content bleed.

    static final class LimitedInputStream extends FilterInputStream {
      private int limit;

      LimitedInputStream(InputStream in, int limit) {
        super(in);
        this.limit = limit;
      }

      @Override
      public int available() throws IOException {
        return Math.min(super.available(), limit);
      }

      @Override
      public int read() throws IOException {
        if (limit <= 0) {
          return -1;
        }
        final int result = super.read();
        if (result >= 0) {
          --limit;
        }
        return result;
      }

      @Override
      public int read(final byte[] b, final int off, int len) throws IOException {
        if (limit <= 0) {
          return -1;
        }
        len = Math.min(len, limit);
        final int result = super.read(b, off, len);
        if (result >= 0) {
          limit -= result;
        }
        return result;
      }

      @Override
      public long skip(final long n) throws IOException {
        // because we take the minimum of an int and a long, result is guaranteed to be
        // less than or equal to Integer.MAX_INT so this cast is safe
        int result = (int) super.skip(Math.min(n, limit));
        if (result >= 0) {
          // if the superclass adheres to the contract for skip, this condition is always true
          limit -= result;
        }
        return result;
      }
    }

bool ParseDelimitedFromCodedStream(MessageLite* message,
                                   io::CodedInputStream* input,
                                   bool* clean_eof) {
  if (clean_eof != nullptr) *clean_eof = false;
  int start = input->CurrentPosition();

  // Read the size.
  uint32_t size;
  if (!input->ReadVarint32(&size)) {
    if (clean_eof != nullptr) *clean_eof = input->CurrentPosition() == start;
    return false;
  }

  // Get the position after any size bytes have been read (and only the message
  // itself remains).
  int position_after_size = input->CurrentPosition();

  // Tell the stream not to read beyond that size.
  io::CodedInputStream::Limit limit = input->PushLimit(static_cast<int>(size));

  // Parse the message.
  if (!message->MergeFromCodedStream(input)) return false;
  if (!input->ConsumedEntireMessage()) return false;
  if (input->CurrentPosition() - position_after_size != static_cast<int>(size))
    return false;

  // Release the limit.
  input->PopLimit(limit);

  return true;
}
