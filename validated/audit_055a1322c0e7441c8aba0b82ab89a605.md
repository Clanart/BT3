## Title
Attacker-controlled `token` address collides with the reserved `TRANSACTION_FEES` escrow slot in `IntentGatewayV2.placeOrder`, corrupting order escrow accounting — ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
The `remove_timestamp_cache` bug's core broken invariant is: an attacker-controlled value from an untrusted payload is used directly as a *key* into a shared accounting structure that also stores privileged/reserved entries, letting the attacker's data silently overwrite protocol-owned bookkeeping. `IntentGatewayV2` reproduces this exact pattern in Solidity: the `_orders[commitment][token]` mapping uses a `token` key that is taken directly, unchecked, from the user-supplied `Order.inputs[i].token` field — and the same mapping namespace is also used to store a reserved, non-token accounting entry, `TRANSACTION_FEES`, computed as `address(uint160(uint256(keccak256("txFees"))))`.

### Finding Description
`_orders` is declared as `mapping(bytes32 => mapping(address => uint256)) public _orders;` [1](#0-0) , and the reserved fee slot is a compile-time constant address within that very address-keyed map: `address private constant TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))));` [2](#0-1) .

In `placeOrder`, for every user-supplied input the contract derives `token` straight from `order.inputs[i].token` (a caller-controlled `bytes32`, truncated to an address) with no check that it differs from `TRANSACTION_FEES`:
```
address token = address(uint160(uint256(order.inputs[i].token)));
...
if (_orders[commitment][token] != 0) revert InvalidInput();
_orders[commitment][token] = reducedInputs[i].amount;
``` [3](#0-2) 

Later in the same call, if the order carries a solver fee, the contract unconditionally overwrites the *same* mapping slot keyed by the reserved constant with `=` (not `+=`):
```
_orders[commitment][TRANSACTION_FEES] = order.fees;
``` [4](#0-3) 

Because `TRANSACTION_FEES` is just another `address` value in the same keyspace that `order.inputs[i].token` populates, an attacker can craft an input whose `token` field equals the `TRANSACTION_FEES` constant. Since that constant has no deployed contract code, `IERC20(token).safeTransferFrom(...)` against it succeeds trivially (a call to an address with no code returns success with empty returndata, which OpenZeppelin's `SafeERC20`/low-level call check accepts) — so the attacker escrows a phantom "token" entry at `_orders[commitment][TRANSACTION_FEES] = amount` without transferring any real value. The duplicate-token guard (`if (_orders[commitment][token] != 0) revert InvalidInput();`) only protects against reusing the same key twice among the `inputs` array itself; it does not protect the reserved `TRANSACTION_FEES` slot from being pre-seeded by a spoofed input, nor does the fee-write step check whether that slot is already occupied before clobbering it with `=`.

This mirrors the reported bug class precisely: `remove_timestamp_cache` let attacker payload fields (`cycleCounter`, `txId`) act as raw property keys into a cache object that also held sensitive prototype internals (`__proto__`, `hasOwnProperty`), letting attacker data collide with and corrupt protocol-managed state. Here, the attacker payload field `order.inputs[i].token` acts as a raw mapping key into `_orders[commitment]`, which also holds the protocol-reserved `TRANSACTION_FEES` slot — the same class of "attacker key aliases a privileged key in a shared keyspace" defect.

### Impact Explanation
This corrupts the on-chain escrow accounting for the order: the input-token escrow entry the attacker just wrote gets silently overwritten by `order.fees` the moment the fee branch executes, and vice versa depending on ordering, meaning `_orders[commitment][TRANSACTION_FEES]` no longer reliably reflects either the true fee amount or a real token escrow. Downstream consumers of `_orders` (fill/refund/cancel paths, and off-chain checks such as `OrderStatusChecker.isOrderRefunded`, which zero-checks every input's `_orders[commitment][token]` entry to decide refund completeness [5](#0-4) ) can be misled: a solver/filler client (`verifyOrderOnSource` in the Simplex filler) also treats a non-zero `_orders[commitment][token]` value as proof of real backing escrow [6](#0-5) , so a phantom, unbacked entry at the `TRANSACTION_FEES` key can pass this check even though no real tokens were escrowed, and the legitimate fee accounting for that same order is destroyed. This can cause fee under-collection/over-refund, false confirmation of escrow presence, or loss of the protocol's fee bookkeeping for that order — a logic/accounting-integrity defect in the fund-custody path of `IntentGatewayV2`, reachable by any unprivileged user calling `placeOrder`.

### Likelihood Explanation
High feasibility for reaching the collision: any caller of the public, unprivileged `placeOrder` function fully controls `order.inputs[i].token` and `order.fees`; no relayer, prover, or admin cooperation is required. The only requirement is knowing the constant `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))`, which is derivable by anyone from the public source code/bytecode. The `safeTransferFrom` against a no-code "token" succeeding without moving funds is a well-known Solidity/OpenZeppelin quirk, not a novel primitive.

### Recommendation
Reject any `order.inputs[i].token` (and `order.output.assets[i].token`, `order.predispatch.assets[i].token`) equal to `TRANSACTION_FEES` in `placeOrder`, or move the fee accounting out of the shared `_orders[commitment][address]` keyspace entirely (e.g., a dedicated `mapping(bytes32 => uint256) _orderFees`) so user-controlled token addresses can never alias a protocol-reserved slot. Additionally, prefer `+=`/existence checks over `=` for the `TRANSACTION_FEES` write so an unexpected pre-existing value is not silently discarded.

### Proof of Concept
1. Compute `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))` (public constant, same value as in the contract).
2. Craft `Order.inputs[0] = TokenInfo({ token: bytes32(uint256(uint160(TRANSACTION_FEES))), amount: X })`, plus `order.fees = Y > 0` and other required fields, sending along `msg.value`/no approvals since the "token" has no code (its `safeTransferFrom` call succeeds trivially with no state change).
3. Call `intentGateway.placeOrder(order, 0)`.
   - Phase 3 sets `_orders[commitment][TRANSACTION_FEES] = X` (phantom escrow, no funds moved).
   - The fees branch then executes `_orders[commitment][TRANSACTION_FEES] = Y`, clobbering the phantom entry (or vice-versa depending on which write executes last), corrupting whichever bookkeeping value is expected to persist at that reserved slot for the remainder of the order's lifecycle (fill, cancel, refund, off-chain status checks).
4. Read `intentGateway._orders(commitment, TRANSACTION_FEES)` to confirm it reflects only one of the two intended values, demonstrating the collision (analogous to reading the polluted `hasOwnProperty` after the `__proto__`/`hasOwnProperty` payload collision in the original report). [7](#0-6)
