## Title
Argument Injection via Unsanitized Deep-Link `branch` Parameter in Git Clone - (File: `app/src/lib/git/clone.ts`)

### Summary
The bug report describes a filter (`recv_internal`'s opcode check) that fails to include one dangerous value (`0xF`), letting a crafted message reach unintended logic. The same "incomplete denylist" pattern exists in GitHub Desktop's deep-link branch validation: `testForInvalidChars()` is used as the gatekeeper for the `branch` query parameter coming from an `x-github-client://openRepo/...` URL, but its regex does not reject a leading `-`/`--`. That value is later concatenated directly as a `-b <branch>` argument to `git clone`, allowing an attacker-controlled hyperlink to inject arbitrary `git clone` command-line options.

### Finding Description
`parseAppURL()` extracts the `branch` parameter from an untrusted deep-link URL and validates it only with `testForInvalidChars`: [1](#0-0) 

`testForInvalidChars` is backed by `invalidCharacterRegex`, which blocks control characters, `~^:?*[\|""<>`, `@{`, consecutive/leading/trailing dots, and `.lock`/trailing `/` — but **not a leading `-`**: [2](#0-1) 

Note that `sanitizedRefName()` (the sibling function) does strip a leading `-`/`+` via a *second*, separate regex (`.replace(/^[-\+]*/g, '')`), but `parseAppURL` only calls `testForInvalidChars`, never `sanitizedRefName`, so a branch value such as `--upload-pack=/tmp/evil.sh` or `--upload-pack=touch$IFS/tmp/pwned` passes validation untouched and is placed into the returned `IOpenRepositoryFromURLAction.branch` field.

That action is dispatched to the renderer via `sendURLAction`/`dispatchURLAction` and ultimately drives a clone flow whose `branch` option is passed straight through to `git`: [3](#0-2) 

Because the value is inserted as a bare token (`args.push('-b', options.branch)`) rather than after a `--` end-of-options marker, a string beginning with `-` is interpreted by `git clone` as a command-line flag instead of a branch name. `git clone`'s well-known `--upload-pack=<command>` option lets the *local* git client invoke an arbitrary command in place of the remote's `git-upload-pack` when it locally executes the transport step, giving straightforward local process execution driven entirely by a link the user clicked.

### Impact Explanation
An attacker who gets a user to click a crafted `x-github-client://openRepo/<url>?branch=--upload-pack=<command>` link (e.g., embedded in a webpage, README, or chat message) can achieve arbitrary command execution on the victim's machine when Desktop performs the resulting clone, without any local access, admin rights, or pre-existing malware — matching the "attacker controls a git remote/deep link the user clicks → code execution" impact class.

### Likelihood Explanation
The `openrepo` deep-link handler is a documented, user-facing feature (`"Open in Desktop"` buttons on github.com and third parties), so the URL scheme is reachable by any web page or clickable link, and no additional confirmation step blocks a malicious `branch` value from reaching `clone()`'s `-b` argument. The only requirement is a user click, which is within the accepted threat model.

### Recommendation
- In `parse-app-url.ts`, reject (or strip) `branch` values that start with `-` in addition to the existing `testForInvalidChars` check (align it with `sanitizedRefName`'s leading `-`/`+` stripping), e.g. add `/^-/` to the rejection checks before returning `open-repository-from-url`.
- Defense in depth: in `app/src/lib/git/clone.ts`, insert a `--` separator before positional arguments, or validate/prefix `options.branch` (e.g., disallow leading `-`) immediately before pushing `-b`/branch value onto `args`, so no caller can smuggle a git option through this path.

### Proof of Concept
1. Attacker publishes a link: `x-github-client://openrepo/https://github.com/some/repo?branch=--upload-pack=touch%20/tmp/pwned;`
2. Victim clicks the link; the OS invokes GitHub Desktop's registered protocol handler, which calls `handleAppURL` → `parseAppURL`. [4](#0-3) 
3. `parseAppURL` validates only via `testForInvalidChars(branch)`, which does not flag the leading `-`, so the action `{ name: 'open-repository-from-url', url, branch: '--upload-pack=touch /tmp/pwned;', ... }` is returned and forwarded to the renderer.
4. The renderer's clone flow eventually calls `clone(url, path, { branch })`, which builds `['clone', '--recursive', ..., '-b', '--upload-pack=touch /tmp/pwned;', '--', url, path]`. [3](#0-2) 
5. `git clone` parses `--upload-pack=...` as a real option and executes the attacker-supplied command as the "upload-pack" program during the clone, resulting in code execution under the victim's user account.

**Uncertainty**: I was not able to fully trace the exact intermediate call chain from `Dispatcher.openRepositoryFromUrl` in `app/src/ui/dispatcher/dispatcher.ts` through to the `CloneOptions.branch` field consumed by `clone()`, because tool access ended before I could read that function's body — the index may not have surfaced its full contents. The vulnerable primitives (unsanitized `branch` extraction in `parse-app-url.ts` and unguarded `-b` argument injection in `clone.ts`) are confirmed directly from source, but I recommend a Devin session review that call path to confirm there is no intermediate sanitization step before recommending a fix.

```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
```
