### Title
`_has_redos_structure` ReDoS heuristic ignores `{m,n}` bounded-repetition syntax, letting malicious `security-patterns.yaml`/`.json` regexes pass `_validate_pattern` and hang the PostToolUse pattern-scan hook - (File: `plugins/security-guidance/hooks/extensibility.py`)

### Summary
`_has_redos_structure` in `extensibility.py` only recognizes catastrophic-backtracking shapes that use the literal `+`/`*`/`?` quantifier characters, both for the nested-quantifier check and for `_ALT_UNDER_REP`. It never inspects `{m,n}`/`{m,}` curly-brace repetition, even though that syntax is semantically identical to `+`/`*` for backtracking purposes. A repo-committed `.claude/security-patterns.yaml` can therefore embed a classic `(a+)+`-style catastrophic regex written as `(a{1,}){1,}` (or any `{...}` equivalent) and sail through `_validate_pattern`'s gate straight into the compiled rule set used by the file-content pattern scanner.

### Finding Description
`_validate_pattern` (extensibility.py:199-244) calls `_has_redos_structure(regex)` before accepting a user-supplied rule regex, and only rejects the rule if that heuristic returns `True`: [1](#0-0) 

The heuristic itself is defined purely in terms of literal `+`/`*`/`?` characters: [2](#0-1) 
`_REDOS_SHAPES[0]` requires a literal `+`/`*` *inside* the parens and a literal `[+*?]` immediately after the closing paren; `_ALT_UNDER_REP` requires a literal `[+*]` after the closing paren. Neither pattern, nor `_has_redos_structure`'s branch-overlap loop, has any awareness of `{m,n}` / `{m,}` repetition: [3](#0-2) 

Since Python's `re` engine treats `a{1,}` identically to `a+` for matching/backtracking semantics, a rule regex such as `(a{1,}){1,}b` (or `(a{1,40}|aa{0,40}){1,40}` for the alternation-overlap case) is the exact catastrophic-backtracking shape the heuristic is meant to catch, but is invisible to both `_REDOS_SHAPES` and `_ALT_UNDER_REP` because they only pattern-match on `+`/`*`/`?`, never on `{`. The regex passes the gate, `re.compile()` succeeds (curly-brace quantifiers are syntactically valid), and the rule is stored in `_user_patterns` and merged with the built-in `SECURITY_PATTERNS` used by the PostToolUse pattern scanner (`patterns.py`) that runs against real file content on every Edit/Write tool call. Because these config files are discovered from `<cwd>/.claude/security-patterns.{yaml,json}` — ordinary, committable repo content per the module's own discovery-precedence docs — an attacker only needs to get such a file merged into a victim's checkout (e.g. via a PR) for it to be loaded by `load_for_session()` on the next Claude Code session in that directory. [4](#0-3) 

### Impact Explanation
Once loaded, the malicious rule's regex is evaluated against arbitrary edited/written file content inside the security-guidance PostToolUse hook. Feeding it a string shaped like many repeated `a` characters followed by a non-matching terminator (a shape that is not unusual in real source files — long identifier runs, repeated whitespace/indentation, comment banners, base64 blobs, etc.) triggers exponential-time backtracking in Python's backtracking `re` engine, hanging the hook process. This is a resource-exhaustion / denial-of-service condition against the security-guidance plugin's PostToolUse enforcement path: it can stall or time out the hook on every subsequent Edit/Write matching the rule's `path_filter`, which either blocks the tool-response pipeline while the regex runs or, if externally killed on a hook timeout, silently drops the intended security warnings for that edit — degrading a security control via attacker-supplied repo content, without requiring any elevated privilege.

### Likelihood Explanation
Preconditions are low-effort and match the ordinary attacker model: no admin/maintainer privilege, no leaked keys, no social engineering beyond getting a `.claude/security-patterns.yaml` file into a repo the victim opens with Claude Code (e.g., via a PR that later gets merged, or a repo the victim clones directly). The bypass regex itself is trivial to construct once the `+`/`*`-only detection gap is known, and is fully deterministic — `re.compile()` accepts it, `_has_redos_structure` returns `False` for it every time, and Python's `re` engine's backtracking behavior on `(a{1,}){1,}`-style patterns is a well-documented, reliably reproducible catastrophic-backtracking case.

### Recommendation
Extend `_has_redos_structure` to normalize `{m,}` / `{m,n}` (with `n` large or absent) repetition to the same quantifier class as `+`/`*` before running the existing shape checks — e.g., pre-process the regex text to rewrite `{0,}`→`*`, `{1,}`→`+`, and treat any `{n,}` or large-range `{n,m}` as an unbounded quantifier for detection purposes — rather than matching only literal `+`/`*`/`?` characters. Alternatively (and more robustly), stop relying solely on a static structural heuristic and enforce a hard runtime timeout (e.g., via a worker process/thread with `signal.alarm`, `regex` module's timeout support, or bounding input length before matching) around every user-supplied regex evaluation in the pattern scanner, so that even structurally-undetected ReDoS patterns cannot hang the hook.

import re
import time
from plugins.security_guidance.hooks.extensibility import _has_redos_structure, _validate_pattern

def test_curly_brace_redos_bypasses_heuristic():
    evil_regex = r"(a{1,}){1,}b"  # semantically identical to (a+)+b
    assert _has_redos_structure(evil_regex) is False  # heuristic misses it

    entry = {
        "rule_name": "evil",
        "reminder": "x",
        "regex": evil_regex,
    }
    rule = _validate_pattern(entry, source="Project")
    assert rule is not None  # rule is accepted and would be merged into SECURITY_PATTERNS

def test_curly_brace_redos_actually_hangs():
    evil_regex = re.compile(r"(a{1,}){1,}b")
    payload = "a" * 35 + "!"  # does not end in 'b' -> forces exponential backtracking
    start = time.time()
    evil_regex.search(payload)
    elapsed = time.time() - start
    assert elapsed > 5  # demonstrates catastrophic backtracking (would grow exponentially with length)
```
Expected result: both assertions pass, demonstrating (1) `_has_redos_structure` fails to flag a `{}`-based catastrophic pattern that is structurally equivalent to the `+`/`*` shapes it is designed to block, and (2) the same pattern, once merged into the live rule set, causes multi-second-to-unbounded hang time on ordinary file content during the PostToolUse pattern scan.

def _has_redos_structure(regex: str) -> bool:
    """Heuristic catastrophic-backtracking check. Not a proof. Catches:
      - nested quantifiers ((a+)*, (a*b)+)
      - wildcard groups under repetition ((.*)*)
      - alternation under repetition where one branch is a prefix of another
        ((a|aa)*, (ab|a)*) — these overlap and explode on non-matching input.
    Does NOT flag non-overlapping alternation ((a|b)*) which is safe."""
    if any(p.search(regex) for p in _REDOS_SHAPES):
        return True
    for m in _ALT_UNDER_REP.finditer(regex):
        branches = [b for b in m.group(0).strip("()*+").split("|") if b]
        for i, a in enumerate(branches):
            for b in branches[i + 1:]:
                # If one branch is a literal prefix of another, the alternation
                # overlaps and the engine backtracks combinatorially.
                if a.startswith(b) or b.startswith(a):
                    return True
    return False
```
