### Title
Use-after-free of a Python map-value wrapper when `MergeFromString`/`MergeFrom` overwrites a message-valued map entry with a duplicate key - (File: `python/google/protobuf/pyext/message.cc`)

### Summary
The Alpine CVE is a UAF/double-free caused by an anchor-name table freeing a YAML node (`syck_hdlr_add_anchor`/`syck_hdlr_remove_anchor`) while a second structure (the parser's value stack) still holds a live pointer to that same node, so a later `syck_hdlr_add_node` frees it again. The transferable invariant is: **a redefinition of a keyed reference must not free memory that is still reachable through another live handle to it.**

The CPython C-extension implementation of `protobuf` has the exact analog for message-valued map fields. `CMessage::MaybeReleaseOneofBeforeMerge` in `python/google/protobuf/pyext/message.cc` was added specifically to fix this class of bug for oneof fields (see the comment at lines 2087–2090: “release the wrappers for switching oneof fields in the target message before they are deleted by C++ during the merge, preventing use-after-free bugs”), but the same function **explicitly excludes repeated/map fields** from the release step via the `!descriptor->is_repeated()` guard, even though its own comment acknowledges “For message map with same keys, it is overwrite” [1](#0-0) .

### Finding Description
`MergeFromStringImpl` (bound to the public `MergeFromString`/`ParseFromString` APIs) parses untrusted bytes into a temporary C++ message and then, before doing the real C++-level `MergeFrom`, calls `MaybeReleaseOneofBeforeMerge` to detach any live Python wrapper objects (`CMessage`s cached in `self->composite_fields`) that the underlying C++ merge is about to free/replace [2](#0-1) .

That release logic walks `composite_fields` and only handles a field if `!descriptor->is_repeated()`, i.e. only singular (oneof) message fields [3](#0-2) . Map fields (which are represented as `is_repeated()==true` entry-message fields in the C++ reflection model) are skipped entirely by this pass.

On the C++ side, when the underlying `MergeFrom` merges a message-valued map with a duplicate key, `UntypedMapBase::UntypedMergeFrom` allocates a new node for the incoming value and calls `InsertOrReplaceNode`, which — for a colliding key — must dispose of the previously-stored node/value and splice in the new one [4](#0-3) . This “second one wins” / overwrite semantics is confirmed by the generated/C++ map test showing duplicate map keys collapsing to the newest value [5](#0-4)  and by the Python-level regression test `testMapMergeFrom`, whose final block (“Test overwrite message value map”) exercises exactly `msg.MergeFromString(msg2.SerializeToString())` with a duplicate map key and message value [6](#0-5) .

The failed invariant: any live Python `CMessage` object that a caller obtained for `msg.some_message_map[key]` (which is backed directly by the C++ node's memory, not a copy) is not invalidated/released before the map merge frees/replaces that node — unlike the oneof case, where this exact hazard was already recognized and mitigated. If the C++ node backing that key is freed and replaced during `MergeFrom`/`MergeFromString`, the previously obtained Python wrapper becomes a dangling pointer into freed memory.

### Impact Explanation
If the stale Python wrapper is later accessed (attribute read/write) or garbage-collected in a way that touches the freed C++ object, this is a use-after-free from the process's own heap, reachable purely by calling the public `MergeFromString`/`MergeFrom` API with two attacker-influenced (or attacker-supplied-then-merged) messages sharing a map key with message values. Depending on allocator state this can crash the interpreter (denial of service) or corrupt heap state, mirroring the "crash/abort" impact described for the YAML::Syck CVE. This does not require malicious schemas, hostile plugins, or privileged access — only ordinary use of the public parse/merge API by a consuming application that retains a reference to a map-valued submessage across a subsequent merge, which is a normal application pattern.

### Likelihood Explanation
Medium. Reaching the vulnerable state requires: (1) obtaining a `CMessage` reference to a message-valued map entry (`msg.field[key]`), which is a common, supported operation that lazily creates and caches a wrapper in `composite_fields`, and (2) calling `MergeFrom`/`MergeFromString` on the containing message with a second message that has the same map key. Both are ordinary, well within the documented public API surface, and no crafted schema or generator changes are needed — only two bounded, attacker-influenced protobuf payloads sharing a map key. This is comparable in reachability to the anchor-redefinition trigger in the report (a 7-byte document).

### Recommendation
Extend `MaybeReleaseOneofBeforeMerge` (or add a sibling routine invoked from `MergeFromStringImpl`/`CMessage`'s `MergeFrom`) to also walk message-valued map fields present in `composite_fields`, and for every map key that exists in both `self` and `other`, release/detach the cached Python wrapper for that entry (mirroring `InternalReleaseFieldByDescriptor`) before invoking the native `MergeFrom`, then re-fixup the wrapper afterward (as `FixupMessageAfterMerge` already does for oneof fields). Alternatively, ensure `FixupMessageAfterMerge`-style repair also revisits cached map-entry wrappers so their raw pointer/state cannot outlive the freed backing node.

### Proof of Concept
This is not confirmed with an executed trace (no sandbox access here) but is a minimal, concrete reproduction that a background engineer should run to confirm/quantify the corruption:

```python
from google.protobuf import map_unittest_pb2

msg = map_unittest_pb2.TestMap()
msg.map_int32_foreign_message[222].c = 123

# Obtain a live wrapper backed directly by the C++ map node.
ref = msg.map_int32_foreign_message[222]
assert ref.c == 123

msg2 = map_unittest_pb2.TestMap()
msg2.map_int32_foreign_message[222].d = 20

# Public parse/merge API call with duplicate map key + message value.
msg.MergeFromString(msg2.SerializeToString())

# `ref` may now be a dangling wrapper over memory freed/replaced by
# UntypedMapBase::InsertOrReplaceNode during the C++-level MergeFrom,
# unlike the oneof case which is explicitly protected by
# MaybeReleaseOneofBeforeMerge.
print(ref.c)  # potential use-after-free access
```

Note: I was unable to inspect `python/google/protobuf/pyext/map_container.cc` (the Python message-map wrapper implementation) within the available tool budget to confirm whether it independently invalidates/re-binds cached per-key `CMessage` wrappers through some other fixup path not visible in `message.cc`. That file should be reviewed to determine whether an additional, map-specific safety net already neutralizes this hazard; if not, the gap described above is real and exploitable via the public API as shown.

void UntypedMapBase::UntypedMergeFrom(Arena* arena,
                                      const UntypedMapBase& other) {
  ABSL_DCHECK_EQ(arena, this->arena());
  if (other.empty()) return;

  // Do the merging in steps to avoid Key*Value number of instantiations and
  // reduce code duplication per instantation.
  NodeBase* nodes = nullptr;

  // First, allocate all the nodes without types.
  for (size_t i = 0; i < other.num_elements_; ++i) {
    NodeBase* new_node = AllocNode(arena);
    new_node->next = nodes;
    nodes = new_node;
  }

  // Then, copy the values.
  VisitValueType([&](auto value_type) {
    using Value = typename decltype(value_type)::type;
    NodeBase* out_node = nodes;

    // Get the ClassData once to avoid redundant virtual function calls.
    const internal::ClassData* class_data =
        std::is_same_v<MessageLite, Value>
            ? GetClassData(*other.GetValue<MessageLite>(other.begin().node_))
            : nullptr;

    for (auto it = other.begin(); !it.Equals(EndIterator()); it.PlusPlus()) {
      Value* out = GetValue<Value>(out_node);
      out_node = out_node->next;
      auto& in = *other.GetValue<Value>(it.node_);
      if constexpr (std::is_same_v<MessageLite, Value>) {
        class_data->PlacementNew(out, arena)->CheckTypeAndMergeFrom(in);
      } else {
        Arena::CreateInArenaStorage(out, arena, in);
      }
    }
  });

  // Finally, copy the keys and insert the nodes.
  VisitKeyType([&](auto key_type) {
    using Key = typename decltype(key_type)::type;
    for (auto it = other.begin(); !it.Equals(EndIterator()); it.PlusPlus()) {
      NodeBase* node = nodes;
      nodes = nodes->next;
      const Key& in = *other.GetKey<Key>(it.node_);
      Key* out = GetKey<Key>(node);
      if (!internal::InitializeMapKey(out, in, arena)) {
        Arena::CreateInArenaStorage(out, arena, in);
      }

      static_cast<KeyMapBase<Key>*>(this)->InsertOrReplaceNode(
          arena, static_cast<typename KeyMapBase<Key>::KeyNode*>(node));
    }
  });
}
