## Finding: Valid — Commit-blind `FileChange.id` breaks the stale-response guard in `SeamlessDiffSwitcher`

### Summary
`FileChange.id` is derived only from `status.kind` and `path` (plus `oldPath` for renames/copies) — it never incorporates `commitish`/`parentCommitish`. As a result, two distinct `CommittedFileChange` objects for the *same path with the same status kind but different commits* are indistinguishable by `id`. `isSameFile()` in `seamless-diff-switcher.tsx`, which is used both to decide whether to keep cached `fileContents` and — critically — to guard against stale async responses, relies solely on this commit-blind `id`. This lets a late-arriving `getFileContents()` response for an *earlier* commit overwrite the diff/file contents that are currently being shown for a *different* commit, misrepresenting the reviewed content.

### Finding Description
`FileChange.id` is constructed purely from `path`/`status.kind` (and `oldPath` for renames): [1](#0-0) 

`CommittedFileChange` adds `commitish`/`parentCommitish` as separate fields but does **not** fold them into `id`: [2](#0-1) 

So `new CommittedFileChange('foo.txt', {kind: Modified}, 'commitB', 'commitB^')` and `new CommittedFileChange('foo.txt', {kind: Modified}, 'commitA', 'commitA^')` have identical `.id` values. This is the normal case whenever the same path is modified in two different commits — no exotic "renamed-then-restored" crafting is even required, though that scenario also collides via the `Renamed+path+oldPath` id form.

`SeamlessDiffSwitcher.isSameFile()` compares only `.id`: [3](#0-2) 

This helper is used in two places:
1. `getDerivedStateFromProps`, to decide whether to retain `state.fileContents` across a prop update: [4](#0-3) 
2. `loadFileContentsIfNeeded`, as the race-condition guard after an async `getFileContents()` fetch completes — verifying the fetch is still relevant before applying it: [5](#0-4) 

`getFileContents` (and its helpers) use `file.commitish` / `file.parentCommitish` to read the actual blob content for that specific commit: [6](#0-5) 

Attack/race scenario: the user (reviewer) is viewing commit A's diff for `foo.txt`. They click to view commit B, which also modifies `foo.txt` (same `AppFileStatusKind`, hence same `id`). If the async blob fetch for commit A (e.g., delayed due to a large object, slow filesystem/network-backed clone, or a git process artificially delayed by repository content the attacker controls — e.g., huge blobs, packfile layout, or many refs forcing git to take longer) resolves *after* the fetch for commit B has already completed and rendered, the guard `isSameFile(fileToLoad, this.props.file)` at line 321 wrongly evaluates to `true` (because `id` doesn't encode commit identity), so `applyFileContents()` is called and overwrites the already-correct commit-B content with stale commit-A content. The component ends up in a stable, "not loading" state (`isLoadingDiff: false`), silently showing the wrong commit's file contents/diff for review, with no further trigger to self-correct.

### Impact Explanation
This can be leveraged by an attacker who controls the content of a repository/commit history (e.g., a malicious contributor whose commits get reviewed via GitHub Desktop's History view) to cause a reviewer to see stale/incorrect diff content for a commit while believing they are looking at that commit's actual changes — a diff/content-review spoofing condition. This does not achieve code execution or credential exfiltration, but it does misrepresent what content a reviewer is seeing during commit review, which is explicitly listed in scope as a valid impact category ("misrepresenting which commit's content is shown for review").

### Likelihood Explanation
Requires the specific ordering where an older commit's async content fetch resolves after a newer commit's, while both commits touch a path with the same `AppFileStatusKind`. This is plausible in real usage (fast repeated commit navigation, slower git object reads for one commit vs another) but is a race condition, not deterministically reproducible on demand; the identity collision itself (same `id` for different commits) is trivially true and requires no crafting.

### Recommendation
Include `commitish`/`parentCommitish` in the identity used to compare `CommittedFileChange` instances — either by incorporating them into `FileChange.id` for `CommittedFileChange` (in `app/src/models/status.ts`) or by making `isSameFile()` in `seamless-diff-switcher.tsx` additionally compare `commitish`/`parentCommitish` when both files are `CommittedFileChange` instances, so a stale fetch for a different commit can never pass the "same file" check.

### Proof of Concept
1. Mount `SeamlessDiffSwitcher` with `file = new CommittedFileChange('foo.txt', {kind: AppFileStatusKind.Modified}, 'commitA', 'commitA^')` and let it load `fileContents`/`diff` for commit A.
2. Update props to `file = new CommittedFileChange('foo.txt', {kind: AppFileStatusKind.Modified}, 'commitB', 'commitB^')` with a new `diff` for commit B, and let its `getFileContents()` fetch resolve and render correctly.
3. Manually resolve a previously-pending (mocked/delayed) `getFileContents()` promise for commit A's file after step 2 completes — this simulates the race. Because `isSameFile(fileA, currentPropsFile=fileB)` returns `true` (identical `id`), the check at `app/src/ui/diff/seamless-diff-switcher.tsx` line 321 fails to reject the stale response, and `applyFileContents` overwrites the state with commit A's content.
4. Assert the rendered diff/fileContents now reflect commit A's stale content while `state.propSnapshot.file` (and the UI's commit context) indicates commit B. [7](#0-6)

    props: ISeamlessDiffSwitcherProps,
    state: ISeamlessDiffSwitcherState
  ): Partial<ISeamlessDiffSwitcherState> {
    const sameFile =
      state.fileContents !== null &&
      isSameFile(state.fileContents.file, props.file)
    const fileContents = sameFile ? state.fileContents : null
    // If it's a text diff, we'll consider it loaded once the contents of the old
    // and new files have been loaded.
    const isLoadingDiff =
      props.diff === null || (isTextDiff(props.diff) && fileContents === null)
    const beganOrFinishedLoadingDiff = isLoadingDiff !== state.isLoadingDiff
    // If the props diff is not a text diff, just pass it along to the state.
    const diff =
      props.diff !== null && !isTextDiff(props.diff) ? props.diff : state.diff

    return {
      isLoadingDiff,
      ...(!isLoadingDiff ? { propSnapshot: props } : undefined),
      // If we've just begun loading the diff or just finished loading it we
      // can't say that it's slow in all other cases we leave the
      // isLoadingSlow state as-is
      ...(beganOrFinishedLoadingDiff ? { isLoadingSlow: false } : undefined),
      diff,
      fileContents,
    }
  }

async function getNewFileContent(
  repository: Repository,
  file: ChangedFile
): Promise<Buffer | null> {
  if (file.status.kind === AppFileStatusKind.Deleted) {
    return null
  }

  if (file instanceof WorkingDirectoryFileChange) {
    return readPartialFile(
      Path.join(repository.path, file.path),
      0,
      MaxHighlightContentLength - 1
    )
  } else if (file instanceof CommittedFileChange) {
    return getPartialBlobContents(
      repository,
      file.commitish,
      file.path,
      MaxHighlightContentLength
    )
  }

  return assertNever(file, 'Unknown file change type')
