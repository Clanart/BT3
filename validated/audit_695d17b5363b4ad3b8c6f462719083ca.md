## Analysis Summary

The CVE describes a stack-overflow DoS caused by unbounded/uncapped recursive parsing of a crafted file format (GPAC's SAF demuxer). The reachable analog in this codebase is the recursive RLP decoding of the `AccountKeyRoleBased` account-key type, which allows a single unprivileged transaction sender to submit a crafted `TxTypeAccountUpdate`/`TxTypeAccountCreation` transaction whose account key contains deeply/self-nested `AccountKeyRoleBased` structures. The nesting-depth/composite-type check (`ErrNestedCompositeType`) is only enforced **after** decoding completes (in state transition / tx pool validation), not during the recursive `DecodeRLP` calls themselves, allowing unbounded recursion before any validation occurs.

### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` account keys allows stack-overflow DoS via a single crafted transaction - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each element of a role-based key list through `AccountKeySerializer`, and if any nested key is itself of type `AccountKeyTypeRoleBased`, the process recurses into `AccountKeyRoleBased.DecodeRLP` again with no depth limit. Because the "nested composite type" rejection is only checked later (during tx-pool admission / state transition), an attacker can submit a crafted transaction whose account key is nested arbitrarily deep, causing unbounded recursive decoding before any validation rejects it.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of byte blobs and, for each one, constructs a fresh `AccountKeySerializer` and calls `rlp.DecodeBytes` on it: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type, instantiates the corresponding `AccountKey` via `NewAccountKey`, and then decodes into it with `s.Decode(serializer.key)`: [2](#0-1) 

If the decoded `keyType` is again `AccountKeyTypeRoleBased`, `NewAccountKey` returns a new `*AccountKeyRoleBased`: [3](#0-2) 

...and `s.Decode` on it re-enters `AccountKeyRoleBased.DecodeRLP`, recursing with no depth check. The check that is meant to prevent nested composite types (`ErrNestedCompositeType`) exists elsewhere in the codebase, and is exercised through `txpool.AddRemote`/`applyTransaction` — i.e., it fires only *after* a Go-level `AccountKey` value already exists, meaning it applies to the post-decode/validation phase, not during the recursive `DecodeRLP` walk itself: [4](#0-3) 

This account-key field is reachable directly from attacker-controlled transaction bytes: `TxInternalDataAccountUpdate.DecodeRLP` and `TxInternalDataAccountCreation.DecodeRLP` decode the serializable struct (which embeds the RLP-encoded key bytes) as part of ordinary transaction decoding: [5](#0-4) [6](#0-5) 

This is triggered on every incoming transaction via the top-level `Transaction.DecodeRLP` / `UnmarshalBinary` path used for pool admission and RPC/`sendRawTransaction`: [7](#0-6) 

### Impact Explanation
Go's growable goroutine stacks tolerate significant recursion, but they are still bounded (default max ~1 GB, controlled by `debug.SetMaxStack`). A sufficiently deep chain of nested `AccountKeyRoleBased` blobs (each level only requires a small RLP list wrapper) can drive the decode recursion deep enough to exceed the maximum stack size, triggering an unrecoverable Go runtime fatal error (`goroutine stack exceeds ... -bound`) that crashes the process — not merely a panic that can be recovered. Since this triggers during ordinary transaction decoding/admission, it affects any node (validator, RPC/full node) that processes the crafted transaction, i.e. a public-RPC/tx-pool reachable Denial of Service, matching CVSS `AC:L/PR:N/UI:R/... A:H` (availability impact only).

### Likelihood Explanation
An unprivileged transaction sender constructs the malicious RLP bytes directly (no valid signatures/state needed to trigger the crash — the crash occurs inside `DecodeRLP`, before signature or nested-type checks run) and submits it via `sendRawTransaction`/p2p tx propagation/tx-pool `AddRemote`. Because `rlp.DecodeBytes` is called for each nesting level, an attacker can construct extremely deep nesting with only linear growth in encoded size, making the attack cheap and reliable to trigger with a single crafted transaction.

### Recommendation
Add an explicit recursion/nesting-depth check inside `AccountKeyRoleBased.DecodeRLP` (and/or `AccountKeySerializer.DecodeRLP`) that rejects `AccountKeyTypeRoleBased` values nested inside another `AccountKeyRoleBased` *during decode*, rather than only after decoding completes and a full `AccountKey` Go object graph already exists. This mirrors the intended invariant already enforced later in `state_transition.go`/`checkAccountKeyZeroValues`, but must be enforced before recursive decoding is allowed to proceed unbounded.

### Proof of Concept
Construct a `TxTypeAccountUpdate` (or `TxTypeAccountCreation`) transaction whose account key field is an `AccountKeySerializer`-encoded `AccountKeyRoleBased` list containing a single element that is itself an `AccountKeySerializer`-encoded `AccountKeyRoleBased`, and repeat this nesting N times (e.g., tens/hundreds of thousands of levels, each adding only a few bytes of RLP list overhead). Submit the resulting raw transaction bytes via `sendRawTransaction`/tx propagation. When the receiving node calls `Transaction.DecodeRLP` → `TxInternalDataAccountUpdate.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recursively N times, the recursive decode chain grows the goroutine stack until it exceeds Go's maximum stack size, crashing the node process before any `ErrNestedCompositeType` validation is reached.

**Note on verification limits:** I was not able to fully trace every intermediate validation path (e.g., whether `s.Decode` on `RawValue`/size limits inside `rlp.Stream` impose an indirect ceiling on nesting depth before the recursion could grow large enough to overflow, given Go's large default max stack). This assessment is based on static code reading of the decode chain; a Devin session with full build/test tooling would be needed to empirically confirm the crash by running the RLP decode against a deeply nested crafted payload.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

// DecodeRLP implements rlp.Decoder
func (tx *Transaction) DecodeRLP(s *rlp.Stream) error {
	serializer := newTxInternalDataSerializer()
	if err := s.Decode(serializer); err != nil {
		return err
	}

	if !SanityCheckSignatures(serializer.tx.RawSignatureValues(), serializer.tx.Type()) {
		return ErrInvalidSig
	}

	size := calculateTxSize(serializer.tx)
	tx.setDecoded(serializer.tx, int(size))

	return nil
}

// UnmarshalBinary decodes the canonical encoding of transactions.
// It supports legacy RLP transactions and EIP2718 typed transactions.
func (tx *Transaction) UnmarshalBinary(b []byte) error {
	newTx := &Transaction{}
	if err := rlp.DecodeBytes(b, newTx); err != nil {
		return err
	}

	tx.setDecoded(newTx.data, len(b))
	return nil
}
