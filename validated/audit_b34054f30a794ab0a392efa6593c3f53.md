### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary

Medium severity. `Scanner::scan_block` scans every transaction in a block, including the coinbase transaction, and returns matching outputs as `ReceivedOutput`s without tracking whether they satisfy Bitcoin’s coinbase-maturity rule. [1](#0-0) 

### Finding Description

`scan_transaction` treats an output as received solely when its `script_pubkey` matches a registered scanner script, then constructs a `ReceivedOutput` containing the value, outpoint, and spending-key offset. [2](#0-1) 

`scan_block` applies that logic to every transaction in `block.txdata`, including `block.txdata[0]`, which is the coinbase transaction in a valid Bitcoin block. [3](#0-2) 

The returned `ReceivedOutput` is explicitly modeled as a spendable output, but it contains no transaction type, block height, confirmation count, or maturity flag. [4](#0-3) 

`SignableTransaction::new` subsequently accepts these objects and converts their outpoints directly into transaction inputs without checking coinbase maturity. [5](#0-4) 

This is analogous to validating only the initial URL before following a redirect: the scanner validates that an output pays a recognized script, but does not revalidate the spendability of the resolved outpoint in its block context. [2](#0-1) 

### Impact Explanation

A block producer can direct the coinbase reward to a scanner-registered Taproot script. Serai will report that output as received even though Bitcoin consensus makes coinbase outputs unspendable until they have sufficient maturity. [3](#0-2) 

A caller that feeds the result into `SignableTransaction::new` can construct and threshold-sign a transaction spending an immature coinbase outpoint; Bitcoin nodes will reject the resulting transaction until maturity. [5](#0-4) 

The concrete impact is funds reported as available when they are not currently spendable, potentially causing incorrect wallet accounting and generation of invalid spends. [6](#0-5) 

### Likelihood Explanation

Triggering the issue requires a valid Bitcoin block whose coinbase pays one of the scanner’s registered scripts. This requires block-production capability, but does not require validator privileges or access to Serai key shares. [7](#0-6) 

The code documentation acknowledges that `scan_block` includes coinbase outputs and recommends either post-processing or scanning `block.txdata[1 ..]`, but the API still returns an object represented as spendable and downstream spending code performs no maturity check. [1](#0-0) 

### Recommendation

Make `scan_block` exclude `block.txdata[0]` by default, or preserve maturity information in `ReceivedOutput` and reject immature coinbase inputs in `SignableTransaction::new`. [8](#0-7) 

If historical or accounting visibility is required, expose a separate `scan_block_including_immature` API whose results cannot be passed directly to transaction construction. [1](#0-0) 

### Proof of Concept

```rust
// `block` is a valid Bitcoin block supplied by the network.
// `scanner` was constructed for the wallet's Taproot group key.
let outputs = scanner.scan_block(&block);

// The first transaction is the coinbase. If it pays a registered script,
// scan_transaction returns it as an ordinary ReceivedOutput.
assert!(block.txdata[0].is_coinbase());
assert_eq!(outputs.len(), 1);
assert_eq!(
  outputs[0].outpoint(),
  &OutPoint::new(block.txdata[0].compute_txid(), 0),
);

// The result is accepted as a spendable input even though the coinbase
// output is not yet mature under Bitcoin consensus rules.
let spend = SignableTransaction::new(
  outputs,
  &[(destination_script, payment_amount)],
  None,
  None,
  fee_per_vbyte,
);

assert!(spend.is_ok());
```

This succeeds because `scan_block` forwards the coinbase transaction to the same script-only matching path used for ordinary transactions, and `SignableTransaction::new` consumes the returned outpoint without a maturity check. [3](#0-2) [5](#0-4)
