Found a genuine TOCTOU (time-of-check-to-time-of-use) analog: `_applyCopilotConflictResolutions` in `app-store.ts` snapshots `state.changesState.workingDirectory.files` once at the top of the function, but the write loop runs Copilot's AI-generated resolutions (asynchronously assembled over network calls that can take tens of seconds — the code even tracks 15s/30s/60s/120s buckets) against that stale snapshot.

### Title
Stale working-directory snapshot lets Copilot conflict resolution overwrite conflict markers a concurrent git operation has already changed - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` reads `state.changesState.workingDirectory.files` (captured before the write loop starts) once, then iterates `copilotResolutions` and, for each file, checks that single stale `onDiskFile` snapshot to decide whether the file is "still conflicted" before calling `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`. [1](#0-0) [2](#0-1) 

### Finding Description
The comment directly above the check explains the intended guard: "If the user resolved this file externally … while the result dialog was open, git status will report it with no remaining conflict markers. Overwriting it with Copilot's stored content would silently clobber their work, so skip it." [3](#0-2) 

The broken invariant: the guard's freshness depends on `state` being current, but `state` is a single `repositoryStateCache.get(repository)` call taken at function entry — it is never re-fetched inside the `for` loop, and this whole flow runs after an unbounded, multi-file, potentially multi-minute Copilot resolution round-trip (the exact scenario the seed report describes: a mutable parameter checked once and then relied upon across a long-running operation). The status check therefore reflects the working directory as it was *before* the "Continue Merge" click was even processed, not as it is at write time.

Between `_startCopilotConflictResolution` finishing and the user clicking "Continue Merge" (`onContinue` in `copilot-conflicts-dialog.tsx`), and again during the file-write loop itself, `git` background/foreground operations (fetch, `refreshRepository`, or another checkout/rebase triggered from a different UI surface) can re-run and change the on-disk conflict state, add new hunks, or resolve markers differently — none of that invalidates the already-fetched `state` object used inside `_applyCopilotConflictResolutions`. [4](#0-3) 

Path traversal itself is guarded by `resolveWithin` [5](#0-4)  — that specific defense is solid — but the *content-integrity* guard (the "don't clobber the user's own resolution" check) is not: it's a point-in-time read used to authorize a write that happens after the state could have drifted. This is the same class of bug as the Loot.sol report: a governance/config value (`vestingDuration` there, working-directory-file-status here) is read once and trusted for a decision that is executed later, after the value may have legitimately changed, causing an outcome (slashing there; silent overwrite of the user's/attacker-influenced conflict resolution here) the actor did not consent to at write time.

### Impact Explanation
If the merge/rebase conflict is against an attacker-controlled fetched branch (a fork PR, or any remote a victim merges/rebases against), Copilot's resolution is generated from AI-processed content of that attacker-authored side of the conflict. The stale-snapshot check that's supposed to prevent overwriting a user's independent resolution can pass even though the user (or a concurrent background refresh) has since updated the file, causing GitHub Desktop to silently re-write file content that no longer matches what the UI displayed, and stage it (`git add`) without further confirmation. [6](#0-5)  This is a silent-corruption-of-what-the-user-commits class impact: the user believes they are committing what they saw/approved in the result dialog, but the actually-staged content can be Copilot's stale resolution clobbering a newer on-disk state, or vice versa a stale check letting a mismatched write proceed.

### Likelihood Explanation
Requires no special privileges beyond a normal merge/rebase/cherry-pick against an untrusted branch and use of the (opt-in) Copilot conflict resolution feature — the resolution call itself is documented to commonly take 15–120+ seconds [7](#0-6) , widening the race window between the state snapshot and the eventual write. It does require the user to trigger another repository-mutating action (e.g., a background fetch-triggered refresh, or manually editing/checking the file) during that window, so likelihood is moderate, not trivial — consistent with the "Medium" severity of the seed report which also required a narrow, but real, ordering condition.

### Recommendation
Re-fetch `state.changesState.workingDirectory.files` (or at minimum re-run `git status`/re-check conflict markers on the specific `absolutePath`) immediately before each `writeFile` call inside the loop in `_applyCopilotConflictResolutions`, rather than relying on the single snapshot taken before the loop begins. Consider also re-validating that the file's on-disk conflict markers still match what was fed to Copilot (e.g., hash the pre-image) before splicing in the AI-resolved content, so any external mutation aborts that specific file's write instead of silently proceeding.

### Proof of Concept
1. Start a merge/rebase against a branch from an untrusted remote/fork so several files conflict.
2. Trigger "Resolve with Copilot"; while `_startCopilotConflictResolution` is awaiting the (slow, 15s+) API round trip, use another Desktop surface (or `git` directly) to modify one of the conflicted files, e.g., resolve it manually or trigger a background fetch/refresh that updates `changesState.workingDirectory.files`.
3. When the result dialog appears, click "Continue Merge" (`onContinue` → `applyCopilotConflictResolutions`).
4. Observe that `_applyCopilotConflictResolutions` uses the `state` object captured at function entry — which does not reflect the mutation from step 2 — to decide whether to write Copilot's (possibly stale) resolution over the file, per the check at [8](#0-7) , then `git add`s the result unconditionally per [6](#0-5) .
