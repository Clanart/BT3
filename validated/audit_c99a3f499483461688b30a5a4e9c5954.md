### Title
`SchnorrAggregate::verify` accepts a trivially-forged signature over an empty signer/challenge set - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The LiquidJS bug class is "a guard that lives inside a loop body and is skipped entirely when the iterated collection is empty." `SchnorrAggregate::verify` exhibits the same shape: the per-signature binding (transcripting each `challenge`, deriving each `weight`, and queuing each `(R, key)` pair) only executes inside `for (i, (key, challenge)) in keys_and_challenges.iter().enumerate()`. When `keys_and_challenges` is empty, no statement is bound into the digest and the batch equation reduces to the single term `(-s)·G == identity`, which is satisfied by `s = 0`. Combined with `SchnorrAggregate::read`, which happily deserializes `Rs` with a zero length prefix, an attacker can submit `len=0 || s=0` and pass `verify` — a forged aggregate signature accepted against zero public keys. ### Finding Description
`SchnorrAggregate<C>` implements the half-aggregation scheme of eprint 2021/350. `verify(dst, keys_and_challenges)`:

1. Checks `self.Rs.len() != keys_and_challenges.len()` and returns false on mismatch (line 128-130). With both empty, this check passes.
2. Transcripts each challenge into `digest` — inside the loop at lines 134-136, so it runs zero times.
3. Queues the verification pairs `(z·R_i, z·c_i·key_i)` — again only inside the loop at lines 139-143.
4. Pushes `(-s, generator)` and checks `multiexp_vartime(&pairs).is_identity()` (lines 144-145).

For an empty `keys_and_challenges`, `pairs` is exactly `[(-s, G)]`, so `verify` returns `s·G == identity`, i.e. true whenever `s = 0`. `read` imposes no lower bound on the `u32` length prefix, so the bytes `00 00 00 00 || 0x00…00` (32-byte zero scalar) deserialize and verify. The "security" the loop was meant to enforce — that `s` equals `Σ z_i·s_i` for real signatures under real keys — is never consulted, exactly like `renderLimit.check()` never running for an empty `{% for %}` body.

### Impact Explanation
Any caller that invokes `verify` with a `keys_and_challenges` slice derived from attacker-influenced data (e.g., a signature batch whose membership can be reduced to zero — filtered-out keys, an empty plan, an empty validator set edge case) will accept `len=0, s=0` as a valid aggregate signature. The verifier's soundness claim "the signature attests that every listed key signed" degenerates to a vacuous truth the attacker controls, yielding a forged-signature acceptance on the empty-statement boundary. Concrete downstream impact depends on the caller not separately enforcing `keys_and_challenges.len() > 0`; the primitive itself does not.

### Likelihood Explanation
Exploitation requires reaching `verify` with an empty statement list. `SchnorrAggregator::complete` refuses to produce an empty aggregate (lines 175-178), so honest aggregation never creates this object — but `SchnorrAggregate::read` creates it directly from untrusted bytes, which is the documented untrusted-input path. The forgery is deterministic, costless, and works on every ciphersuite.

### Recommendation
Reject empty aggregates in `verify` (and/or in `read`): `if self.Rs.is_empty() || keys_and_challenges.is_empty() { return false; }`, matching the producer-side guard already present in `SchnorrAggregator::complete` (lines 175-178). Alternatively, mix a count into the digest and a nonzero constant term so the empty case cannot collapse to `s·G == 0`.

### Proof of Concept
```rust
use ciphersuite::Ciphersuite;
use schnorr::SchnorrAggregate;

// For any ciphersuite C (e.g. Ristretto):
let forged = SchnorrAggregate::<C>::read(&mut [
  0u8, 0, 0, 0,                 // len = 0
  &[0u8; 32][..],               // s = 0
].concat().as_slice()).unwrap();

// No keys, no challenges: the loop guards never execute.
assert!(forged.verify(b"dst", &[])); // accepts a signature "by nobody"
```

Caveat: I confirmed the empty-input acceptance path in `verify`/`read`/`complete`, but did not enumerate every production callsite of `SchnorrAggregate::verify` in the allowed time; the finding stands at the primitive level — a verify function that accepts a forged signature for an empty statement set — and is exploitable wherever the statement list can be attacker-influenced to zero length.

  pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
      return false;
    }

    let mut digest = DigestTranscript::<C::H>::new(dst);
    digest.domain_separate(b"signatures");
    for (_, challenge) in keys_and_challenges {
      digest.append_message(b"challenge", challenge.to_repr());
    }

    let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
    for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
      let z = weight(&mut digest);
      pairs.push((z, self.Rs[i]));
      pairs.push((z * challenge, *key));
    }
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
  }
