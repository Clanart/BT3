This is exactly the analog: `coin_record_to_crcat()` reconstructs each CR-CAT coin's `CRCAT` object using `self.info.authorized_providers` and `self.info.proofs_checker` — the wallet-level cached values — instead of the actual per-coin values that were curried into that specific coin's on-chain puzzle.

### Title
Wallet caches CR-CAT authorized providers/proofs checker at creation time and never updates them, causing constructed spends to use stale (wrong) restriction parameters - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
`CRCATWallet.get_or_create_wallet_for_cat()` [1](#0-0)  creates the `CRCATInfo` (containing `authorized_providers` and `proofs_checker`) exactly once, keyed only by the CAT's `limitations_program_hash` (tail hash). If a wallet for that asset id already exists, the method returns the existing wallet unconditionally [2](#0-1)  — the newly supplied `authorized_providers`/`proofs_checker` arguments (which could differ, e.g. from a different mint, `create_from_puzzle_info()` [3](#0-2) , or `convert_to_cr()` [4](#0-3) ) are silently discarded and never persisted.

### Finding Description
Every subsequent coin belonging to this wallet is reconstructed as a `CRCAT` object using the cached, stale `self.info.authorized_providers` and `self.info.proofs_checker` fields rather than the parameters actually curried into that coin's on-chain puzzle: [5](#0-4) . This is directly analogous to the reported Convex/Gearbox bug: a set of "reward"/authorization parameters is captured once at construction time and never refreshed even though the underlying protocol object (here, the CR-CAT layer for a given tail hash) can legitimately exist with different `authorized_providers`/`proofs_checker` sets across different mints or across a VC-issuer's provider-list change. The wallet has no logic to detect or reconcile a mismatch between the stored info and the actual coin's curried parameters.

Note that `CRCAT.get_current_from_coin_spend()`/`get_next_from_coin_spend()` do parse the real on-chain values from the puzzle reveal [6](#0-5) , but this correctly-parsed data is discarded once it's used to populate `WalletCoinRecord.metadata` and `add_crcat_coin()` [7](#0-6)  — the lineage proof and inner puzzle hash are stored, but `authorized_providers`/`proofs_checker` are not stored per-coin; they are always re-read from the wallet-level `self.info` in `coin_record_to_crcat()`.

### Impact Explanation
When the wallet's cached `authorized_providers`/`proofs_checker` diverge from what is actually curried into a specific coin's puzzle (e.g., because the wallet was first created for an asset id from one CR-CAT mint, and later a different CR-CAT with the same tail hash but a different provider list/proofs checker is added to the same wallet), `_generate_unsigned_spendbundle()` will build the `CR` layer solution using the wrong `authorized_providers`/`proofs_checker`, since `coin_record_to_crcat()` is the source of truth used for spend construction. This causes the constructed CLVM solution to not match the coin's actual puzzle hash, meaning either the spend is rejected on-chain (funds transiently unspendable/incorrect UX) or, in an approval workflow where the taker or `VCWallet` uses `puzzle_info["also"]["authorized_providers"]` from stale offer data compared against the wallet's own stale record, incorrect VC-authorization decisions could be made (e.g., `TradeManager.check_for_requested_payment_modifications` calls `get_vc_with_provider_in_and_proofs` [8](#0-7)  based on the offer's driver dict, not the wallet's cached info, which limits — but does not eliminate — off-chain/on-chain mismatch risk for constructing valid spends of a wallet's own coins).

### Likelihood Explanation
Low-to-medium. It requires a CR-CAT tail hash to be reused with different `authorized_providers`/`proofs_checker` sets across separate CR-CAT launches that map to the same wallet (`get_or_create_wallet_for_cat` matches purely on `limitations_program_hash`). This is a legitimate scenario since `CRCAT.launch()` [9](#0-8)  allows arbitrary `authorized_providers`/`proofs_checker` for a given tail, and CR-CAT asset identity (as reported via `get_asset_id()`) does not include the CR layer parameters.

### Recommendation
Store `authorized_providers` and `proofs_checker` per-coin (in `CRCATMetadata`) rather than only at the wallet level, and use those per-coin values in `coin_record_to_crcat()` instead of `self.info`. Alternatively, reject/warn when `get_or_create_wallet_for_cat()` is called with parameters that differ from an already-existing wallet for the same asset id, and create a distinct wallet or update the record to prevent constructing spends with mismatched restriction parameters.

### Proof of Concept
This analysis is based on static code review of `chia/wallet/vc_wallet/cr_cat_wallet.py`, `chia/wallet/vc_wallet/cr_cat_drivers.py`, and `chia/wallet/trade_manager.py`; no live exploit was executed. The concrete reproduction path (mint CR-CAT #1 with tail T and providers [A], get wallet W; mint CR-CAT #2 with the same tail T but providers [B]; call `get_or_create_wallet_for_cat` for CR-CAT #2, observe it returns W with providers still [A]; then attempt to spend CR-CAT #2's coin via W and observe `coin_record_to_crcat()` uses providers [A] instead of [B]) would need to be validated in a running simulator test, which was not available in this review — flagging this as unverified dynamically.
