### Title
Fee-on-transfer LP tokens cause receipt-token over-minting and protocol insolvency in `WombatStaking.depositLP` - ([File: wombat/WombatStaking.sol])

### Summary
`WombatStaking.depositLP()` mints receipt tokens equal to the caller-supplied `_lpAmount` parameter instead of the amount actually received by the contract after the `safeTransferFrom` call. Unlike `WombatStaking.deposit()` (the stable-token deposit path), which correctly measures `lpReceived` as the balance delta before/after the external Wombat pool deposit, `depositLP()` has no such before/after balance check for the LP token transfer itself.

### Finding Description
In `deposit()`, the contract properly protects against fee-on-transfer / rebasing behavior by measuring the actual LP tokens received: [1](#0-0) 

However, `depositLP()` transfers `_lpAmount` of the LP token from the user and then immediately stakes and mints receipt tokens using the raw `_lpAmount` parameter, without checking how many tokens the contract actually received: [2](#0-1) 

If `poolInfo.lpAddress` is (or ever becomes, e.g. via a pool re-registration or an alt-pool LP with fee-on-transfer semantics) a fee-on-transfer token, the contract will:
1. Receive less than `_lpAmount` in actual LP token balance (fee deducted in transit).
2. Call `_toMasterWomAndSendReward(_lpAddress, _lpAmount, true)` and mint `_lpAmount` of `receiptToken` to `msg.sender` — i.e., mint receipt tokens for LP balance the contract never actually custodied.

This creates a permanent accounting mismatch between the receipt token supply (over-stated) and the actual LP token balance backing it (under-stated). Every subsequent depositor via this pool compounds the shortfall.

### Impact Explanation
This satisfies the "protocol insolvency" / "permanent freezing of funds" criteria: the pool's receipt token supply becomes permanently over-collateralized relative to actual LP token custody. When users later call `withdraw()` (via the pool helper), the contract will progressively run out of actual LP/underlying tokens to return to legitimate holders, causing withdrawal failures for a subset of receipt token holders — i.e., permanent loss/freezing of funds for the last withdrawers, with no admin/privileged action required to trigger it (any ordinary wallet calling `depositLP` with a fee-on-transfer LP token pool triggers the shortfall).

### Likelihood Explanation
Likelihood depends on whether any registered (or future) alt-pool LP token used in `depositLP` implements a transfer fee. Given `registerPool` is a generic owner-configurable mechanism that can point `_lpAddress` at any ERC20-compliant token used as a Wombat/alt-pool LP token, and the contract explicitly documents "in scope" compatibility expectations with fee-on-transfer style tokens elsewhere in comparable protocols, this is a realistic configuration risk rather than a purely theoretical one. Any unprivileged wallet holding such an LP token can trigger the shortfall simply by calling `depositLP`.

### Recommendation
Mirror the pattern already used in `deposit()`: measure the LP token balance of the contract before and after the `safeTransferFrom` call in `depositLP()`, and use the actual received delta (not the caller-supplied `_lpAmount`) for both `_toMasterWomAndSendReward` and the receipt token mint amount.

### Proof of Concept
1. Owner registers a pool via `registerPool()` with `_lpAddress` set to a fee-on-transfer token (or an existing LP token is later swapped to one with fee logic, e.g. via a token upgrade/proxy where allowed by the token's own admin — no privileged action on WombatStaking itself is required).
2. User A calls `WombatPoolHelper.depositLP(1000)`, which calls `WombatStaking.depositLP(lpToken, 1000, userA)`.
3. `safeTransferFrom(userA, address(this), 1000)` results in the contract actually receiving only 950 tokens (5% fee).
4. `_toMasterWomAndSendReward(_lpAddress, 1000, true)` and `IMintableERC20(receiptToken).mint(msg.sender, 1000)` both use the full 1000, while only 950 LP tokens actually back the position.
5. Repeating this deposit path accumulates a shortfall between receipt token supply and actual LP custody, so eventual withdrawals by legitimate receipt-token holders will fail once the shortfall exceeds available LP balance — freezing funds for the affected users. [3](#0-2)
