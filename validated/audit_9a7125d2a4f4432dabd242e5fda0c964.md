### Title
Deep-link branch name only partially sanitized before being used as a git-checkout argument, allowing leading-hyphen flag injection - (File: app/src/lib/parse-app-url.ts, app/src/lib/sanitize-ref-name.ts)

### Summary
GitHub Desktop registers a custom protocol (`x-github-client://`, `github-mac://`, etc.) that is reachable by any web page or link a user clicks. `parseAppURL()` extracts an `openrepo` action with attacker-controlled `url`, `branch`, `pr`, and `filepath` query parameters, and validates `branch` only with `testForInvalidChars()`. [1](#0-0) 

That validator only rejects control characters and a fixed set of Git-reserved glyphs (`~^:?*[\|"<>`), consecutive dots, leading/trailing dots, `.lock` suffix, and trailing slash — it does **not** reject a leading `-`/`+`, unlike the sibling function `sanitizedRefName()` which explicitly strips leading `-`/`+` characters. [2](#0-1) 

The validated branch is then handed to `dispatchURLAction` → `openRepositoryFromUrl` → `openBranchNameFromUrl`, which fetches/clones the attacker-specified `url`, refreshes, fetches, and calls `checkoutLocalBranch(repository, branchName)` with the raw string. [3](#0-2) 

### Finding Description
The broken invariant mirrors the Sherlock report's core lesson — "don't pass attacker-controlled parameters into a privileged operation without validating they can't be reinterpreted as something other than data." Here the equivalent primitive is passing a user-controlled string that survives the allow-list filter as a *value* straight into a `git` argument slot, where Git itself may reinterpret a leading-hyphen string as a flag rather than a ref name (classic argument/flag injection). `testForInvalidChars` was clearly written with ref-name legality in mind (mirroring `git check-ref-format`), but it forgot to close the same leading-`-`/`+` gap that `sanitizedRefName` closes just a few lines above it in the same file family, showing the two functions are inconsistent guards for the same input class. [4](#0-3) 

The value then flows unmodified from a remotely-triggerable surface (deep link) through `dispatchURLAction`/`openBranchNameFromUrl` and into a checkout call sourced from `app-store.ts`'s `_checkoutBranch`/`checkoutLocalBranch` implementations. [5](#0-4) 

### Impact Explanation
If the underlying `git checkout`/`git branch` invocation (in `app/src/lib/git/checkout.ts`, which I could not fully inspect in this session) does not prefix the branch argument with a `--` end-of-options marker, an attacker-controlled deep link (e.g. embedded in a webpage, README, or issue comment as `x-github-client://openrepo/<repo>?branch=--orphan` or similar flag strings) could alter the semantics of the checkout call the moment the user clicks the link — with no confirmation dialog, since deep-link branch checkout is silent/automatic in `openBranchNameFromUrl`. Depending on which flags dugite/git accept unguarded in that call site, outcomes could range from silently checking out into an unexpected state to corrupting the user's working tree/branch — squarely inside the "silent corruption of what the user commits or pushes" impact category named in the task's scope.

### Likelihood Explanation
Likelihood is **uncertain and unverified** in this session: I confirmed the parsing/validation gap definitively, but I could not confirm whether `checkout.ts`'s git invocation is defended by a `--` separator or an allow-list of ref names at the actual `git` call boundary (a common downstream mitigation that would neutralize this specific gap). Without that confirmation, this should be treated as a **lead requiring code-level verification of `app/src/lib/git/checkout.ts`**, not a fully proven exploit chain.

### Recommendation
Regardless of whether the current git call already guards against it, `testForInvalidChars` (used for the deep-link/CLI-derived `branch` field) should be hardened to reject leading `-`/`+`, consistent with `sanitizedRefName`, so that both code paths enforce the same safe-ref-name invariant for any Git ref value that originates from an untrusted URL or CLI argument. Additionally, verify (or if missing, add) a `--` end-of-options separator immediately before any user/URL-derived ref name at every `git` spawn call site (checkout, branch, fetch, etc.) as defense in depth.

### Proof of Concept
Not independently executed. Conceptual PoC based on confirmed code paths:
1. Attacker hosts/embeds a link: `x-github-client://openrepo/https://github.com/victim/repo?branch=--orphan`
2. `branch` value `"--orphan"` contains none of the characters/sequences in `invalidCharacterRegex`, so `testForInvalidChars('--orphan')` returns `false` and `parseAppURL` accepts it as a valid `IOpenRepositoryFromURLAction`. [6](#0-5) 
3. Victim clicks the link; OS routes it to Desktop's `open-url` handler, which calls `handleAppURL(url)` → eventually `dispatcher.dispatchURLAction()` → `openRepositoryFromUrl()` → `openBranchNameFromUrl(url, '--orphan')`. [7](#0-6) 
4. `openBranchNameFromUrl` clones/opens the repo and calls `this.checkoutLocalBranch(repository, '--orphan')` with no further sanitization. [5](#0-4)

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
