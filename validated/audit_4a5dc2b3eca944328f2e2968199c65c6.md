### Title
`ReceivedOutput::read` accepts an attacker-fabricated `offset`/`output`/`outpoint` triple that is never bound to a real UTXO, letting an unprivileged party cause the FROST multisig to sign a spend of non-existent or foreign funds - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput` is the unit the wallet treats as "an output we can spend". Its deserializer (`ReceivedOutput::read`, `networks/bitcoin/src/wallet/mod.rs:122-134`) blindly accepts the `offset` scalar, the entire `TxOut` (amount + `script_pubkey`), and the `OutPoint` from untrusted bytes. Nowhere in the pipeline is the tuple bound to the real on-chain UTXO: `SignableTransaction::new` sums `input.output.value` for the funds check (`send.rs:175`), builds `Prevouts::All` from the claimed `output`s (`send.rs:253`, `send.rs:375`), and `multisig` only checks that the claimed `offset` is consistent with the *claimed* `script_pubkey` (`send.rs:276-279`). Like the Chakra `payload_type`, a field traveling alongside verifiable data is fully attacker-controlled and is consumed by the signing path without being bound to the object it claims to describe.

### Finding Description
`Scanner::scan_transaction` produces honest `ReceivedOutput`s by looking up `output.script_pubkey` in the registered script→offset map (`mod.rs:199-214`), so internally-produced outputs are consistent. But `ReceivedOutput::read` (`mod.rs:122`) is a separate entry point accepting `offset || TxOut || OutPoint` from a byte stream with no consistency or provenance checks:

```rust
// networks/bitcoin/src/wallet/mod.rs
let offset = Secp256k1::read_F(r)?;              // arbitrary scalar
output   = TxOut::consensus_decode(&mut buf_r)?; // arbitrary value + script_pubkey
outpoint = OutPoint::consensus_decode(&mut buf_r)?; // arbitrary txid:vout
```

When such an output is fed to `SignableTransaction::new` / `multisig` (`send.rs:273-285`):

- `offsets[i]` comes from the attacker (`send.rs:176`);
- the only check is `p2tr_script_buf(keys.offset(offset).group_key()) == prevouts[i].script_pubkey` (`send.rs:277`), which validates offset↔*claimed* script consistency — an attacker can trivially satisfy it by choosing `offset` and setting `script_pubkey = p2tr(key + offset·G)` themselves;
- nothing verifies that `prevouts[i]` (value and script) actually matches the UTXO at `outpoint` on-chain;
- `Prevouts::All(&self.tx.prevouts)` (`send.rs:375`) then commits the fabricated `TxOut` into every BIP-341 sighash, and `input_sat` accounting (`send.rs:175`) counts the fabricated value as real funds.

The transaction completes FROST signing successfully (`TransactionSignatureMachine::complete`, `send.rs:413-428`) and is returned as a valid signed `Transaction` — but the signatures are only valid for the fabricated prevout set, so the transaction is unbroadcastable/unspendable, and balance was counted that does not exist.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` can report outputs that are counted as received and spendable when they are not (fabricated `value`/`outpoint`, or an outpoint belonging to a third party). This is the accepted "funds reported received that are not spendable" impact: the system signs and returns a transaction whose inputs don't exist on-chain, while `SignableTransaction::new`'s `NotEnoughFunds` check, `fee()`, and change computation all act on phantom input value. In the extreme, a fabricated high-value input makes a real payment + change + fee look funded, and the signed transaction is silently invalid — the analog of Chakra's "transaction processed by the code but never completing" outcome. Because `Prevouts::All` commits the forged `TxOut`, the produced signatures also attest to a false prevout set.

### Likelihood Explanation
The `ReceivedOutput::read` path exists precisely to accept externally-supplied serialized outputs (the rules classify it as an untrusted-bytes sink, and `processor/src/networks/bitcoin.rs` `Output::read` embeds it when hydrating outputs from storage/messages). Any flow where a peer, relay, or deserialized record supplies a `ReceivedOutput` — rather than one freshly produced by the local `Scanner` — is reachable by an unprivileged party. Satisfying the only consistency check (`multisig`'s offset↔script test) is trivial: pick any `offset`, compute `p2tr(group_key + offset·G)`, and set that as the claimed `script_pubkey`. Medium severity: the impact is bounded to availability/mis-accounting of deposits rather than direct theft, since the forged spend cannot actually move coins.

### Recommendation
Bind the claimed output to verifiable commitment rather than trusting the serialized triple:

- In `multisig`/`SignableTransaction::new`, reject inputs whose `offset` fails to re-derive `prevouts[i].script_pubkey` — already done — but additionally require producers to authenticate `ReceivedOutput`s (e.g., only accept outputs from `Scanner::scan_transaction`/`scan_block`, or re-validate `outpoint`/`output` against a confirmed block via the RPC before constructing `SignableTransaction`).
- Make `ReceivedOutput::read` — or a wrapper used for untrusted input — the integrity boundary: include the group key (or a keyed MAC/commitment over `offset || output || outpoint`, written by `write` and checked on `read`) so a fabricated or mutated triple is rejected at deserialization, mirroring the Chakra fix of binding `payload_type` into the signed hash.

### Proof of Concept
```rust
// Attacker crafts bytes for ReceivedOutput::read targeting group key K:
//   offset = arbitrary scalar o
//   output = TxOut { value: 1_000_000_000,                 // phantom value
//                    script_pubkey: p2tr_script_buf(K + o*G).unwrap() }
//   outpoint = OutPoint { txid: <any real txid>, vout: 0 } // a UTXO Serai doesn't own
let forged = ReceivedOutput::read(&mut attacker_bytes).unwrap();

// Honest signer path:
let tx = SignableTransaction::new(vec![forged], &payments, change, None, fee_rate).unwrap();
// passes: input_sat includes the phantom 10 BTC; multisig() passes because
// p2tr_script_buf(K.offset(o)) == forged script_pubkey by construction.
let machine = tx.clone().multisig(&keys).unwrap();
let signed: Transaction = sign(&keys, &tx); // completes, all shares verify
// signed.input[0].previous_output points at a foreign/nonexistent UTXO;
// each witness sig commits (Prevouts::All) to the fabricated TxOut.
// Broadcast fails / funds counted but unspendable — identical to the report's
// "processed by the code but considered unfinished" outcome.
```

Uncertainty note: whether a deployment actually deserializes `ReceivedOutput`s from attacker-controlled channels is integration-dependent; within the in-scope code itself, the missing offset→script/outpoint→chain binding is present and exploitable wherever `ReceivedOutput::read` is fed untrusted bytes.
