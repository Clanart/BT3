### Title
Attacker-controlled length field in `ThresholdKeys::read` enables memory-amplification denial of service - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` in `crypto/dkg/src/lib.rs` trusts a 2-byte `n` field from the input stream and immediately performs `Vec::with_capacity(usize::from(n))` and an `n`-iteration `HashMap` population before validating that any backing bytes exist. An unprivileged party able to feed bytes to `ThresholdKeys::read` can force a multi-megabyte allocation with a ~13-byte input, and repeat it to exhaust memory — the same small-input/large-allocation DoS shape as the OnionShare advisory (tiny serialized payload amplified into gigabytes of consumption on the deserializing side).

### Finding Description [1](#0-0) 

`ThresholdKeys::read` deserializes `t`, `n`, `i` from the reader, then for `Interpolation::Constant` executes:

```rust
let mut res = Vec::with_capacity(usize::from(n));
for _ in 0 .. n {
  res.push(C::read_F(reader)?);
}
```

and subsequently:

```rust
for l in (1 ..= n).map(Participant) {
  verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
}
```

Two problems combine:

1. `n` is fully attacker-controlled (any `u16` up to 65535) and is used in `Vec::with_capacity` *before* a single scalar byte is confirmed present. A buffer containing only the ID header, `t`, `n = 65535`, `i`, and the interpolation tag (`0`) causes an immediate allocation of `65535 * size_of::<C::F>()` (≈2 MB for 32-byte fields) even though the stream then fails on the first `read_F`.
2. The `verification_shares` loop iterates `n` times calling `C::read_G`, each performing a full point decode (decompression + subgroup/validity checks). A truncated stream forces up to 65535 attempted decodes; a crafted stream of valid points forces 65535 expensive group operations driven by ~2 MB of attacker bytes — CPU amplification in addition to the allocation.

Notably, the Ethereum `Call::read` in this codebase explicitly guards against exactly this class ("A valid DoS would be to claim a 4 GB data is present for only 4 bytes / We read this in 1 KB chunks"), showing the pattern was recognized elsewhere but not applied in `ThresholdKeys::read`. [2](#0-1) 

### Impact Explanation
Any deployment that deserializes `ThresholdKeys` from a source an unprivileged party can influence (per the prompt's reachability rules, `ThresholdKeys::read` is an admitted untrusted-bytes sink) permits a memory-amplification DoS: each request of a few dozen bytes yields ~2 MB of allocation plus up to 65535 point-decode attempts. Repeated submissions linearly multiply consumption, allowing OOM or sustained CPU exhaustion of the key-handling component without any signing capability or validator status. Severity: Medium — availability impact only, no secret leakage or forgery.

### Likelihood Explanation
Exploitation requires only that the attacker reach a code path passing their bytes to `ThresholdKeys::read`. No authentication, threshold control, or protocol position is needed — the allocation happens during parsing, before any semantic validation (`ThresholdParams::new` / `ThresholdKeys::new` run only after all reads). Every call with `n = 65535` costs the victim ~2 MB alloc + decode work regardless of how truncated the input is.

### Recommendation
Cap `n` before allocation:

- Reject `n` above a protocol maximum (e.g., `u16` cap used elsewhere such as the `Participant`/params limits) immediately after reading it, before `Vec::with_capacity`.
- Grow the Vec incrementally (`Vec::new()` + `push`, as in `musig`'s `check_keys` pattern) or bound capacity to the smaller of `n` and remaining-input-derived length, mirroring the chunked-read approach in `networks/ethereum/src/machine.rs` `Call::read`.
- Perform the same cap before the `verification_shares` loop so `n` cannot drive unbounded `read_G` work on a truncated stream.

### Proof of Concept
```
// Input to ThresholdKeys::read<Ristretto>(reader):
//   [4-byte id_len][C::ID][u16 t=2][u16 n=0xFFFF][u16 i=1][u8 interpolation=0]
// Total: ~ 6 + ID.len() bytes.
//
// Result: Vec::with_capacity(65535) allocates ~2 MB for C::F elements;
// the first C::read_F fails on EOF, but the allocation already occurred.
// Repeat N times => ~2N MB memory pressure plus 65535 read_G iterations
// if the stream is padded with valid point encodings instead.
```

Confidence caveat: whether `ThresholdKeys::read` is exposed to unprivileged bytes in the production deployment (rather than only local/keystore reads) was not fully verifiable within the in-scope crates; the finding stands if the admitted reachability assumption holds.
