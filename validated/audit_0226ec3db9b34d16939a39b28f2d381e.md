### Title
Out-of-bounds atom-length parsing in CLVM canonical-form check can crash spend-bundle validation - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` in `chia/full_node/mempool_manager.py` parses an attacker-controlled CLVM byte buffer's variable-length atom-size prefix without ever checking that the buffer contains enough bytes to satisfy the declared prefix length before it starts loops over the length octets. This mirrors the FFmpeg `decode_dds1` bug class in ALPINE-CVE-2017-9992: a size/prefix field taken from untrusted input drives a read loop with no bounds check against the actual remaining buffer size.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` inspects the leading byte at `offset` to determine how many additional prefix bytes encode the atom length (1–5 extra bytes depending on the high bits of the first byte): [1](#0-0) 

The function then does:
```python
atom_len = b & mask
for i in range(prefix_len):
    atom_len <<= 8
    offset += 1
    atom_len |= clvm_buffer[offset]
```
There is no check that `offset` (after incrementing up to `prefix_len` times) stays within `len(clvm_buffer)` before indexing `clvm_buffer[offset]`. If a crafted CLVM buffer ends with a multi-byte length-prefix marker (e.g. `0xF8`/`0xFC` class bytes) but is truncated before the trailing length bytes are actually present, `clvm_buffer[offset]` raises an unhandled `IndexError`.

This function is invoked by `is_clvm_canonical()`, which walks an entire serialized CLVM program (a submitted `puzzle_reveal` or `solution`) atom-by-atom to decide whether the spend uses strictly canonical/shortest-form encoding: [2](#0-1) 

`is_clvm_canonical()` is exercised directly against `spend.puzzle_reveal` / `spend.solution` bytes taken from a submitted `SpendBundle`, as shown by the test harness that asserts canonical-form invariants over the bundle's raw coin-spend bytes: [3](#0-2) 

and the mempool explicitly rejects non-canonical CLVM with `Err.INVALID_COIN_SOLUTION` in the normal (bounds-safe) case, confirming this canonical check runs on every submitted coin spend during mempool admission: [4](#0-3) 

The bug-class parallel to CVE-2017-9992 is direct: both take a length/size value parsed from untrusted, attacker-supplied bytes and use it to drive further reads without validating it against the actual remaining buffer size before dereferencing.

### Impact Explanation
Because Python performs bounds checking on `bytes`/`bytearray` indexing, this does not yield memory corruption like the native FFmpeg case — instead it raises an uncaught `IndexError` inside the canonical-form check. If that exception is not caught by the caller of `is_clvm_canonical`/`is_atom_canonical` in the DEDUP/fast-forward eligibility path (unlike the `ValueError`/`AssertionError` paths that are deliberately caught and converted into `Err.INVALID_COIN_SOLUTION`), an unprivileged submitter can trigger an unhandled exception during per-spend-bundle processing, i.e., a spend-triggered halt of that mempool admission pathway rather than a clean rejection. This is reachable from any mempool submitter (RPC, peer relay, or wallet) supplying a `puzzle_reveal`/`solution` whose bytes end in a truncated multi-byte atom-length prefix.

### Likelihood Explanation
Likelihood is high for triggering the code path itself — any submitted spend bundle's `puzzle_reveal` and `solution` are run through `is_clvm_canonical`/`is_atom_canonical` as part of DEDUP-eligibility/canonical-form validation, and constructing a truncated multi-byte length prefix is trivial (a handful of crafted bytes). What is not independently verified here is whether every call site wraps this specific function in a broad exception handler that degrades gracefully to `INVALID_COIN_SOLUTION` (as it does for the documented `ValueError`/`AssertionError` cases) or whether an `IndexError` can propagate uncaught out of spend-bundle validation — this distinction determines whether the impact is a benign rejection or a genuine processing halt, and could not be conclusively confirmed from the available code/tests.

### Recommendation
Add an explicit bounds check in `is_atom_canonical()` before advancing `offset` and indexing `clvm_buffer[offset]` in the prefix-length loop, e.g. validate `offset + prefix_len < len(clvm_buffer)` up front and raise a well-defined, caught exception (or return non-canonical) instead of relying on implicit `IndexError`. Ensure all call sites of `is_clvm_canonical`/`is_atom_canonical` catch `IndexError` (or the new explicit exception) and map it to `Err.INVALID_COIN_SOLUTION` exactly like existing malformed-CLVM handling.

### Proof of Concept
Construct a `puzzle_reveal` or `solution` byte string whose last atom begins with a multi-byte length-prefix marker but is cut off before the required trailing length bytes exist, for example a buffer ending in a single `0xF8` byte (which signals a 5-byte length encoding) with no further bytes following it. Submitting a `CoinSpend`/`SpendBundle` containing this puzzle_reveal or solution and letting it reach the canonical-form check in `is_clvm_canonical()` drives `is_atom_canonical()` to index past the end of `clvm_buffer`, as in: [5](#0-4)

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```
