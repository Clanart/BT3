### Title
Deserialized `ThresholdKeys` can bind an arbitrary public key to an unrelated secret share - ([File: crypto/dkg/src/lib.rs](https://github.com/Kirstentat/serai--016/blob/main/crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts untrusted serialized keys whose `secret_share` does not correspond to the local participant’s `verification_shares[i]`. `ThresholdKeys::new` derives `group_key` solely from the first `t` verification shares and never checks that `secret_share * G == verification_shares[i]`. An application can therefore import bytes for a wallet, derive and scan an attacker-selected group key, report received funds, and subsequently be unable to produce a valid FROST signature for them. [1](#0-0) [2](#0-1) 

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation mode, the local `secret_share`, and `n` verification shares from the input byte stream, then passes them to `ThresholdKeys::new`. [3](#0-2) 

The constructor validates only the number and participant indexes of the verification shares, plus whether the interpolation mode is applicable. It then calculates `group_key` by interpolating verification shares for participants `1..=t`. [4](#0-3) 

There is no constraint binding the deserialized `secret_share` to `verification_shares[i]`. The correct invariant for a usable key is:

```text
verification_shares[i] == secret_share * C::generator()
```

For the simplest `t = n = i = 1` Lagrange encoding, an attacker can supply:

```text
secret_share = x
verification_shares[1] = A
```

where `A != x * G`. `ThresholdKeys::new` accepts the object and sets `group_key = A`, even though the imported secret is `x`. [5](#0-4) 

Later signing uses the interpolated private `secret_share`, while signature verification uses the separately derived `group_key`. The share therefore corresponds to `x * G`, not `A`, and cannot satisfy the Schnorr relation under `A`. [6](#0-5) [7](#0-6) 

This is the Serai analogue of the missing default-value/finalization constraint: deserialization reconstructs a structured object without enforcing the semantic relation between its default/current value and the committed public state.

### Impact Explanation
An attacker who can supply serialized `ThresholdKeys` can make an application believe it controls `group_key = A` while the imported secret share actually corresponds to a different key. `Scanner::new(keys.group_key())` registers the address for `A`, so incoming outputs to that script are reported as received. [8](#0-7) [9](#0-8) 

`SignableTransaction::multisig` accepts the malformed keys because it checks only that the requested output script equals the script for `keys.group_key()`. [10](#0-9)  During FROST completion, however, the summed response validates against `A`, while the local response is generated with `x`; final verification fails and the funds cannot be spent with the imported object. [11](#0-10) 

This produces the concrete impact of funds reported as received but not spendable. With an arbitrary valid curve point `A`, the attacker does not need to know its discrete logarithm; the malformed serialization is still accepted and the derived wallet address is still advertised as controlled by the key.

### Likelihood Explanation
The required input is only a serialized `ThresholdKeys` blob supplied to the public `ThresholdKeys::read` API, one of the explicitly reachable untrusted-byte inputs. No malicious validator, colluding threshold, leaked private key, invalid curve implementation, or misuse of private internals is required. [12](#0-11) 

Likelihood is deployment-dependent because an application must accept threshold-key material from an untrusted source, such as a recovery/import endpoint or peer-supplied backup. Once such bytes are accepted, the malformed state is deterministic and does not rely on a race, probabilistic failure, or signature malleability.

### Recommendation
In `ThresholdKeys::new`, enforce the key-share consistency invariant after parameter and participant validation:

```rust
if (C::generator() * secret_share.deref()) != verification_shares[&params.i()] {
  return Err(DkgError::InvalidSecretShare);
}
```

This must account for the intended semantics of `secret_share`: the serialized value is the uninterpolated local share, while `verification_shares[i]` is exactly its public counterpart. If an interpolation mode deliberately stores something else, that mode needs an explicit documented verification relation instead of omitting validation.

The check should be performed in `ThresholdKeys::new`, not only in `ThresholdKeys::read`, so all constructors enforce the same invariant. Add a regression test which serializes a `t = n = i = 1` key with `secret_share = 2` and `verification_shares[1] = G`, and asserts that `ThresholdKeys::read` rejects it.

### Proof of Concept
The following conceptual Rust PoC constructs a malformed serialized `ThresholdKeys<Ristretto>` whose claimed public key is `G` while its private share is `2`:

```rust
use std::io::Write;
use zeroize::Zeroizing;
use ciphersuite::{group::{ff::{Field, PrimeField}, GroupEncoding}, Ciphersuite};
use frost::{curve::Ristretto, Participant, ThresholdKeys};

let mut encoded = vec![];

// Curve identifier.
encoded.extend(u32::try_from(Ristretto::ID.len()).unwrap().to_le_bytes());
encoded.extend(Ristretto::ID);

// t = 1, n = 1, i = 1.
encoded.extend(1u16.to_le_bytes());
encoded.extend(1u16.to_le_bytes());
encoded.extend(Participant::new(1).unwrap().to_bytes());

// Lagrange interpolation.
encoded.push(1);

// Private share: 2.
let stored_secret = <Ristretto as Ciphersuite>::F::ONE +
    <Ristretto as Ciphersuite>::F::ONE;
encoded.extend(stored_secret.to_repr().as_ref());

// Claimed verification share and hence group key: G, i.e. secret 1.
let claimed_verification_share = Ristretto::generator();
encoded.extend(claimed_verification_share.to_bytes().as_ref());

// Currently succeeds despite 2G != G.
let keys = ThresholdKeys::<Ristretto>::read(&mut encoded.as_slice()).unwrap();

assert_eq!(keys.group_key(), claimed_verification_share);
assert_eq!(
  *keys.original_secret_share(),
  stored_secret,
);
assert_ne!(
  Ristretto::generator() * *keys.original_secret_share(),
  keys.original_verification_share(Participant::new(1).unwrap()),
);
```

`Scanner::new(keys.group_key())` will scan for outputs paying to `G`, but any signature share generated with the imported secret `2` is a share for `2G`, not for the advertised group key `G`, so final signature verification fails and the reported outputs are unspendable through this imported key.
