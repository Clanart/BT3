### Title
Empty serialized Schnorr aggregate verifies as a valid signature - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::read` accepts an aggregate containing zero signatures. When paired with an empty `keys_and_challenges` slice, `SchnorrAggregate::verify` accepts the empty aggregate whenever `s == 0`. This bypasses the explicit empty-aggregate rejection in `SchnorrAggregator::complete` and creates a deserialization-only forgery for an empty signing set.

### Finding Description
`SchnorrAggregator::complete` refuses to construct an aggregate when no signatures were supplied, establishing that an empty aggregate is not a valid local aggregation result. [1](#0-0) 

The deserializer does not enforce that invariant. It reads a four-byte count and permits that count to be zero, then reads `s`. [2](#0-1) 

During verification, `self.Rs.len() == keys_and_challenges.len()` passes when both are zero. No statements are added except `(-s, generator)`, so an `s` of zero makes the multiexponentiation the identity and verification succeeds. [3](#0-2) 

### Impact Explanation
An untrusted party can submit a canonical serialized aggregate that `SchnorrAggregator::complete` could never produce and have it accepted by `verify` for an empty verification batch. The forged encoding consists only of a zero signature count and a zero scalar. This is an incorrect verifier acceptance caused by a zero-length input, analogous to the reported unchecked empty-input failure.

### Likelihood Explanation
The trigger is reachable wherever attacker-controlled bytes are passed to `SchnorrAggregate::read` and then verified against an empty `keys_and_challenges` slice. No private key, nonce, valid signer, malformed point encoding, or invalid scalar is required.

### Recommendation
Reject `len == 0` in `SchnorrAggregate::read`. Verification can additionally defensively reject `self.Rs.is_empty()` or `keys_and_challenges.is_empty()` so the empty statement set cannot be accepted even if the type is constructed through another path.

### Proof of Concept
For any supported `C: Ciphersuite`, construct an encoding containing:

```rust
u32::to_le_bytes(0) || C::F::ZERO.to_repr()
```

Then:

```rust
let aggregate = SchnorrAggregate::<C>::read(&mut encoded.as_slice()).unwrap();
assert!(aggregate.verify(dst, &[]));
```

The first four bytes make `Rs` empty, the scalar encoding makes `s == 0`, the length check succeeds against the empty `keys_and_challenges`, and `multiexp_vartime` returns the identity.

  /// Read a SchnorrAggregate from something implementing Read.
  pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    #[allow(non_snake_case)]
    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }

    Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
  }
