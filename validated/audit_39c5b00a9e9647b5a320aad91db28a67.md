### Title
Forgery of aggregate Schnorr signatures via unbound aggregation weights - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::verify` derives the random linear-combination weights `z_i` for the multiexp solely from a transcript of the *challenges* (`crypto/schnorr/src/aggregate.rs:132-136`). The signers' public keys and the submitted nonce commitments `Rs` are never bound into the weight derivation, and the weights are fully deterministic. Because an attacker can predict every `z_i` before choosing `Rs` and `s`, they can craft an aggregate signature that passes `verify` for arbitrary public keys and messages without knowing any private key — a direct analog of the reported class (attacker-supplied input escaping the intended constraint envelope of the verifier).

### Finding Description

In `verify`, the transcript absorbs only the challenges:

```rust
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, challenge) in keys_and_challenges {
  digest.append_message(b"challenge", challenge.to_repr());
}
```

then each pair `(z_i, Rs[i])` and `(z_i * challenge_i, key_i)` is queued (`crypto/schnorr/src/aggregate.rs:138-145`). Neither `keys_and_challenges`' keys nor `self.Rs` enter `digest`, so `weight(&mut digest)` values are computable by the attacker with zero knowledge of the secrets.

The verification equation is `sum_i z_i * R_i + z_i*c_i*A_i - s*G == 0`. Since the `R_i` values are attacker-chosen bytes parsed via `SchnorrAggregate::read`/`C::read_G`, and `z_i` are known, the attacker simply picks `R_i = -c_i * A_i` for all but one index and solves for `s` in the remaining term.

Per the aggregation scheme this library cites (eprint 2021/350), the combination weights must commit to the *entire* statement (keys, nonces, challenges), typically by hashing them together — or at minimum binding `Rs` and keys — so that the attacker cannot choose `Rs` after knowing the weights.

### Impact Explanation

An unprivileged attacker produces a `SchnorrAggregate` byte string that `verify(dst, keys_and_challenges)` accepts for any target public keys/challenges — a universal forgery of aggregate signatures. Anywhere aggregate Schnorr verification gates authorization, this permits signing statements attributed to keys the attacker does not control.

### Likelihood Explanation

Reachable by any party able to submit bytes to `SchnorrAggregate::read` followed by `verify` — both public APIs over untrusted input. Exploitation requires only public data (the keys and challenges) and linear algebra over the base group; no secret knowledge, collusion, or malformed-encoding tricks are needed.

### Recommendation

Bind the full verification statement into the weight transcript: before deriving each `weight`, append each `Rs[i]`'s encoding and each public key to `digest` (or hash all of `(R_i, A_i, c_i)` once and derive weights from that digest). Alternatively, per the referenced scheme, derive a single seed hash over all challenges *and* nonces *and* keys, and expand `z_i` from it.

### Proof of Concept

Let `keys_and_challenges = [(A_1, c_1), (A_2, c_2), ...]`. The attacker:

1. Computes the deterministic weights `z_i` by replaying the transcript over the public challenges.
2. Sets `R_i = -c_i * A_i` for all `i > 1`, sets `R_1 = r*G - c_1*A_1` for a random `r`, and sets `s = z_1 * r`.
3. Serializes `(Rs, s)` via `write`/`serialize`.

Verification computes `z_1*(R_1 + c_1*A_1) + sum_{i>1} z_i*0 - s*G = z_1*r*G - z_1*r*G = 0`, so `multiexp_vartime(...)` is identity and `verify` returns `true` — a valid aggregate signature over keys with no known discrete logs.
