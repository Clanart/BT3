### Title
Unbounded recursion in `PuzzleInfo`/`Solver` driver parsing allows a spend-triggered stack-overflow DoS via a malicious offer or wallet RPC request - (File: chia/wallet/puzzle_drivers.py)

### Summary
`PuzzleInfo` and `Solver` (`chia/wallet/puzzle_drivers.py`) wrap attacker-controlled JSON dictionaries that describe layered asset "drivers" for offers (CAT/CR-CAT/NFT/DataLayer/singleton puzzles). The `also()` accessor and `check_type()` method recurse into nested `"also"` sub-dictionaries with **no depth limit**, exactly the CWE-674 "uncontrolled recursion on deeply nested structure" pattern described in the Nimbus JOSE+JWT advisory (CVE-2025-53864), just applied to Chia's own driver-dictionary format instead of JWT claims.

### Finding Description
`PuzzleInfo.also()` recursively instantiates a new `PuzzleInfo` for every nested `"also"` key: [1](#0-0) 

`check_type()` walks the same chain recursively as well. Both are ordinary Python recursion with no maximum-depth guard, unlike the CLVM byte-stream deserializer (which runs through the Rust/CLVM cost-limited parser) or `sha256_treehash()` (which was deliberately made iterative specifically to avoid Python recursion limits on deeply nested structures, per the module's design notes).

`PuzzleInfo`/`Solver` values are populated directly from JSON supplied by:
- an **offer counterparty**, via `Offer.driver_dict` construction from `PuzzleInfo.from_json_dict()` (used when handling offer summaries/negotiation, e.g. `GetOfferSummaryResponse`/`OfferSummary` JSON round trips) [2](#0-1) 
- a **local wallet RPC caller**, directly via `CreateOfferForIDs.driver_dict: dict[bytes32, PuzzleInfo] | None` and `solver: Solver | None` fields, which are `from_json_dict`-deserialized straight into nested-dict form [3](#0-2) 

Once constructed, this driver information is walked recursively throughout the outer-puzzle machinery — e.g. `OwnershipOuterPuzzle.construct/get_inner_puzzle/get_inner_solution/solve` and `CROuterPuzzle` all call `constructor.also()` and recurse into `self._construct(also, ...)`/`self._get_inner_puzzle(also, ...)` for every layer [4](#0-3) [5](#0-4) , and `TradeManager.check_for_final_modifications`/`check_for_requested_payment_modifications` call `puzzle_info.check_type([...])` and `puzzle_info.also()[...]` while processing an offer being taken [6](#0-5) .

Because none of `also()`, `check_type()`, `construct()`, `get_inner_puzzle()`, or `get_inner_solution()` enforce a maximum nesting depth, a crafted `driver_dict`/`PuzzleInfo`/`Solver` JSON with thousands of nested `"also"` levels will drive Python's call stack to `RecursionError` (or, in pathological cases with C-level recursion inside dependent libraries, an unrecoverable interpreter/process crash) while the wallet is processing an offer summary, taking an offer, or handling `create_offer_for_ids`/`take_offer` RPC calls.

### Impact Explanation
A wallet processing a hostile offer file/bech32 blob from an untrusted counterparty, or a local RPC client submitting a deeply nested `driver_dict`/`solver` JSON body to `create_offer_for_ids`/`take_offer`, can trigger unbounded Python recursion in the offer/puzzle-driver code path. This can crash or hang the wallet service mid transaction-processing, matching the accepted "spend-triggered transaction-processing halt" impact category. This is a denial-of-service against the wallet's offer/trade subsystem, not a coin-forgery or signature-bypass bug.

### Likelihood Explanation
The attack requires no privileges beyond being an offer counterparty (sending a `.offer` file/bech32 blob or advertised offer summary to the victim's wallet) or a local RPC caller supplying `driver_dict`/`solver` JSON. Constructing a deeply nested `{"type": ..., "also": {"type": ..., "also": {...}}}` structure is trivial and requires no cryptographic material or valid signatures — only the ability to get the victim wallet to run `also()`/`check_type()`/`construct()` over the payload (e.g., during offer summary display or trade acceptance).

### Recommendation
Add an explicit maximum recursion/nesting depth check to `PuzzleInfo.also()`, `Solver` construction, and `check_type()` (e.g., track depth in `__init__`/`also()` and raise a `ValueError` once a configurable cap, such as 20–50 layers, is exceeded). Apply the same cap to all outer-puzzle driver-chasing helpers (`construct`, `get_inner_puzzle`, `get_inner_solution`, `solve`) that recurse via `constructor.also()`, or convert them to an iterative loop pattern the way `sha256_treehash()` was already converted to avoid the same class of issue for CLVM trees.

### Proof of Concept
Construct a deeply nested `PuzzleInfo`/offer `driver_dict` JSON and feed it through the normal offer-summary/parsing path:
```python
from chia.wallet.puzzle_drivers import PuzzleInfo

def make_nested(depth: int) -> dict:
    d = {"type": "CAT", "tail": "0x" + "00"*32}
    for _ in range(depth):
        d = {"type": "CAT", "tail": "0x" + "00"*32, "also": d}
    return d

nested = make_nested(50_000)   # trivially constructible JSON, no signatures needed
info = PuzzleInfo.from_json_dict(nested)
info.check_type(["CAT"])       # recurses `depth` times -> RecursionError / stack overflow
```
Submitting the equivalent structure as `driver_dict`/`solver` in a `create_offer_for_ids`/`take_offer` RPC call, or embedding it in an offer that a victim wallet parses/summarizes (`GetOfferSummaryResponse`, `TradeManager.check_for_final_modifications`), reaches the same recursive code paths from an unprivileged offer counterparty or local RPC caller.

**Note on confidence**: I was not able to fully trace every call site that ultimately invokes `also()`/`check_type()` from raw untrusted offer bytes (some offer JSON round-tripping happens through several dataclasses in `chia/wallet/wallet_request_types.py` I only partially reviewed), so the exact minimal external trigger (offer-file parsing alone vs. requiring an RPC call) should be confirmed with a live reproduction before treating this as fully validated.
