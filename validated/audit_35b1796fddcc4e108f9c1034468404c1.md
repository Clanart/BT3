## Title
Copilot merge-conflict resolver silently rewrites non-conflict content that merely *looks like* Git conflict markers, corrupting what the user commits - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

## Summary
The PoolTogether bug is a "composition of independently-derived values without checking them against the real invariant" problem: `startDraw`/`finishDraw` fractions are each computed correctly in isolation but their *sum* is never checked against the single ground truth (`availableRewards`), so the system silently overspends. The closest concrete analog I can support with code evidence in this repo is in the Copilot AI merge-conflict resolution pipeline: `extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts:179-279` identifies "conflict hunks" purely by line-start regexes (`<{7}`, `={7}`, `>{7}`) with no verification against the real ground truth — i.e., whether Git itself actually produced those markers for a real merge conflict. `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts:549-599` then blindly re-splices content into every matched block, by order, and the caller (`app/src/lib/stores/app-store.ts:7233-7259`) writes the entire reassembled buffer back to disk and stages it with `git add`.

## Finding Description
`extractConflictHunks` treats any line matching `/^<{7}(?:\s|$)/` … `/^={7}$/` … `/^>{7}(?:\s|$)/` at column 0 as the start/middle/end of a genuine merge conflict: [1](#0-0) 

This heuristic cannot distinguish real Git-generated conflict markers from attacker-controlled file content that happens to contain the same 7-character sequences at line start — for example a tutorial file, a test fixture, or documentation about Git conflict resolution committed to a cloned/fetched repository. There is no cross-check against Git's own conflict metadata (e.g. `git diff --check`/`ls-files -u` ranges) to confirm the extracted block is a real conflict versus attacker-authored text that merely matches the pattern; the code even has an explicit test acknowledging the pattern is purely syntactic ("does not treat markers inside content as boundaries" only rejects markers *not at column 0*, it does nothing to authenticate that a matched block is a real Git conflict): [2](#0-1) 

Once such a block is (mis)classified as a conflict, its content is sent to the Copilot model as "ours"/"theirs" text, and the model's response is spliced back into the file unconditionally, by matching hunk order, in `reassembleResolvedFile`: [3](#0-2) 

The final write path in `app-store.ts` overwrites the on-disk file wholesale with the reassembled content and stages it for commit, with the only safety check being whether the file *still has unresolved conflict markers* according to `git status` — which does nothing to detect that a "hunk" was never a real conflict in the first place: [4](#0-3) 

Just like the PoolTogether bug where each fraction is locally valid but their aggregate is never checked against the true cap (`availableRewards`), here each "hunk" is locally well-formed (has open/separator/close markers) but is never checked against the true ground truth of what Git actually flagged as conflicted. The result: content that was never in conflict can be silently replaced by LLM-generated text and committed/pushed without the user's changes being what they intended.

## Impact Explanation
An attacker who controls a cloned/fetched repository (e.g. a fork the victim merges from, or a file introduced via a PR branch) can plant benign-looking lines that match the 7-character marker pattern in a file that later becomes part of an unrelated real merge/rebase/cherry-pick with actual conflicts elsewhere. When the victim invokes GitHub Desktop's AI conflict resolution, the attacker's crafted block is misidentified as a conflict, sent to Copilot, and replaced by generated content that is then written to disk and `git add`ed — silently corrupting content the user did not intend to touch. This falls squarely under "silent corruption of what the user commits or pushes."

## Likelihood Explanation
Requires a real merge/rebase/cherry-pick with at least one genuine conflict (to trigger the Copilot conflict-resolution flow) plus attacker-controlled content elsewhere in a touched file matching the marker syntax. This is a plausible, low-effort trigger for anyone who can get a victim to merge/pull from a crafted branch or repository, and needs no elevated privileges or local access. I could not verify, due to index limits, whether the result-review UI (`copilot-conflicts-changes.tsx`) surfaces a diff that would let an attentive user notice the spurious change before accepting — this materially affects real-world exploitability and should be checked directly in the full source.

## Recommendation
Cross-validate extracted "hunks" against Git's authoritative conflict state (e.g., unmerged blob stages from `git ls-files -u` or `git diff --check`) rather than relying solely on textual marker matching. Reject or flag hunks whose surrounding content cannot be correlated with a real unmerged path/region, and surface a diff/confirmation step before overwriting and staging files whose "conflicts" were not corroborated by Git itself.

## Proof of Concept
1. Prepare a repository where `sample.md` contains lines that are not part of any git conflict but match the marker regex, e.g.:
```
Example of a conflict block:
<<<<<<< HEAD
some legit content A
=======
some legit content B
>>>>>>> feature
```
2. Separately introduce a real conflicting change in another part of the same repository (a different file or a different hunk in the same file) so a genuine merge conflict occurs.
3. Have the victim merge/rebase and open GitHub Desktop's "Resolve with Copilot" flow.
4. `extractConflictHunks` (as shown in `app/src/lib/copilot-conflict-context.ts:179-279`) will parse the benign `sample.md` block as a real conflict hunk (verified by the existing unit tests demonstrating identical syntactic matching, e.g. `app/test/unit/copilot-conflict-context-test.ts:101-118`), send it to the Copilot model, and `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) will replace "some legit content A"/"some legit content B" with the model's generated text — content the user never intended to change is written to disk and staged via `git add` in `app-store.ts:7258-7267`.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
