### Title
Off-by-one in `TxPool.validateAuth`'s per-authority in-flight tx limit allows two pool-resident SetCode (EIP-7702) transactions to share one authority - (File: blockchain/tx_pool.go)

### Summary
The comment and design intent of `validateAuth` in `blockchain/tx_pool.go` is to "allow at most one in-flight tx for any authority" referenced by a `TxTypeEthereumSetCode` transaction's authorization list. However, the enforcement check uses `count > 1` instead of `count >= 1`, mirroring the exact class of bug reported in the external `FootiumAcademy` report where a boundary comparison off-by-one allows one extra unit to be admitted (`generationId > maxGenerationId` instead of `>=`).

### Finding Description
`checkDelegationLimit`/`validateAuth` are called from `pool.validateTx` for every transaction submitted to the pool (including `TxTypeEthereumSetCode` transactions submitted by any unprivileged sender via RPC) [1](#0-0) .

For each authority address named in the SetCode transaction's authorization list, the code sums the number of currently pooled transactions from that authority in `pending` and `queue`, and only rejects the incoming transaction if that pre-existing count is already `> 1`: [2](#0-1) 

Because the check fires only when the *existing* count already exceeds 1, an authority with exactly one already-pooled transaction (count == 1) passes the check, and the new transaction is added as well — resulting in two in-flight transactions for the same authority address, when the stated invariant ("allow at most one in-flight tx ... for any authority") requires the check to trigger once the existing count reaches 1 (i.e., `count >= 1`), not 2. This is the identical bug pattern to the reported `FootiumAcademy` issue: a strict `>` comparison against a limit that is meant to represent an inclusive cap allows one extra unit — an off-by-one that expands the intended maximum from N to N+1 (here N=1, allowing 2).

### Impact Explanation
The "at most one in-flight tx per authority" invariant exists specifically to prevent conflicting/duplicate delegation authorizations from co-existing in the pool for the same address (an EIP-7702-style authority, i.e., an `AccountKey`/delegation target). Allowing two simultaneously pooled transactions that reference the same authority undermines this invariant: it enables an unprivileged transaction sender to have two independent SetCode transactions in the pool concurrently authorizing/altering delegation state for the same account, which can be used to race conflicting delegation states into block assembly, evade the "replacement only" semantics documented in the code (`// Replacement of the existing in-flight transaction for delegated accounts are still supported`), and potentially get two incompatible authorizations processed across different blocks/proposers, causing state divergence in how the account's delegated code is set depending on which of the two txs is included. This falls into the "acceptance of an invalid/unintended transaction combination violating a stated pool invariant" bug class.

### Likelihood Explanation
This is reachable by any single unprivileged transaction sender: submit one `TxTypeEthereumSetCode` transaction whose authorization list names authority address `A` (accepted into pending/queue), then submit a second SetCode transaction (from any sender, with a different nonce than the first, non-replacing) whose authorization list also names authority `A`. The second transaction's `count` computed in `validateAuth` will be `1` (from the first tx) at the time of the check, which is not `> 1`, so it passes and both remain pooled. No special privileges, timing races with other peers, or consensus-layer conditions are required — this is a straightforward two-transaction sequence through the standard `AddLocal`/`AddRemote` public entry points.

### Recommendation
Change the comparison in `validateAuth` from a strict "greater than the limit" check to an inclusive check that reflects the stated "at most one" invariant, e.g.:
```diff
-		if count > 1 {
+		if count >= 1 {
 			return ErrAuthorityReserved
 		}
```
(with appropriate handling to still allow legitimate nonce-based replacement of the sender's own existing transaction, consistent with the surrounding comment).

### Proof of Concept
1. Fund two accounts, `S1` and `S2`.
2. Craft `TxTypeEthereumSetCode` transaction `tx1` from `S1` (nonce 0) whose `AuthList` includes an authorization tuple for authority address `A`. Submit via `pool.AddLocal(tx1)` — succeeds, `pool.pending[S1]` now contains one tx, and `A` is counted once.
3. Craft a second, distinct `TxTypeEthereumSetCode` transaction `tx2` from `S2` (nonce 0, not a nonce-replacement of `tx1`) whose `AuthList` also includes authority address `A`. Submit via `pool.AddLocal(tx2)`.
4. In `validateAuth`, for authority `A`, `count` is computed as `1` (from `tx1` in `pending[A]`/`queue[A]` depending on ordering) which does not satisfy `count > 1`, so `tx2` is also accepted.
5. Result: two independent, non-replacing SetCode transactions referencing authority `A` coexist in the pool simultaneously, violating the intended "at most one in-flight tx per authority" invariant enforced by `checkDelegationLimit`/`validateAuth` [3](#0-2) .

func (pool *TxPool) checkDelegationLimit(tx *types.Transaction) error {
	from, _ := types.Sender(pool.signer, tx) // validated

	// Short circuit if the sender has neither delegation nor pending delegation.
	if pool.currentState.GetCodeHash(from) == types.EmptyCodeHash && !pool.all.hasAuth(from) {
		return nil
	}
	pending := pool.pending[from]
	if pending == nil {
		// Transaction with gapped nonce is not supported for delegated accounts
		if pool.getPendingNonce(from) != tx.Nonce() {
			return ErrOutOfOrderTxFromDelegated
		}
		return nil
	}
	// Transaction replacement is supported
	if pending.Contains(tx.Nonce()) {
		return nil
	}
	return ErrInflightTxLimitReached
}

// validateBlobTx validates the blob transaction fields.
func (pool *TxPool) validateBlobTx(tx *types.Transaction) error {
	sidecar := tx.BlobTxSidecar()
	if sidecar == nil {
		return errors.New("missing sidecar in blob transaction")
	}
	// Ensure the blob fee cap satisfies the minimum blob gas price
	if tx.BlobGasFeeCapIntCmp(pool.blobBaseFee) < 0 {
		return fmt.Errorf("%w: blob fee cap %v, minimum needed %v", ErrTxGasPriceTooLow, tx.BlobGasFeeCap(), pool.blobBaseFee)
	}
	// Ensure the number of items in the blob transaction and various side
	// data match up before doing any expensive validations
	hashes := tx.BlobHashes()
	if len(hashes) == 0 {
		return errors.New("blobless blob transaction")
	}
	if len(hashes) > params.BlobTxMaxBlobs {
		return fmt.Errorf("too many blobs in transaction: have %d, permitted %d", len(hashes), params.BlobTxMaxBlobs)
	}
	if err := sidecar.ValidateWithBlobHashes(hashes); err != nil {
		return err
	}
	return nil
}

// validateAuth verifies that the transaction complies with code authorization
// restrictions brought by SetCode transaction type.
func (pool *TxPool) validateAuth(tx *types.Transaction) error {
	// Allow at most one in-flight tx for delegated accounts or those with a
	// pending authorization.
	if err := pool.checkDelegationLimit(tx); err != nil {
		return err
	}

	// For symmetry, allow at most one in-flight tx for any authority with a
	// pending transaction.
	for _, auth := range tx.SetCodeAuthorities() {
		var count int
		if pending := pool.pending[auth]; pending != nil {
			count += pending.Len()
		}
		if queue := pool.queue[auth]; queue != nil {
			count += queue.Len()
		}
		// Replace the existing in-flight transaction for delegated accounts
		// are still supported
		if count > 1 {
			return ErrAuthorityReserved
		}
	}
	return nil
}
