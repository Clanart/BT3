## Analog Found: Divergent conflict-marker parsing between the Copilot context builder and the resolution splicer corrupts committed content

### Title
Divergent `<<<<<<<`/`=======`/`>>>>>>>` marker parsing between `extractConflictHunks` and `reassembleResolvedFile` lets a malformed conflict block cause AI-resolved content to be spliced into the wrong location, silently corrupting what the user commits - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Mochi bug is a class of "two independent computations of the same logical quantity silently diverge, and the code that consumes the second computation assumes it matches the first." GitHub Desktop's Copilot-assisted merge-conflict resolution feature has the same broken invariant: the file is parsed for conflict hunks twice, by two different hand-rolled state machines that are supposed to agree but do not, and the safety check in between (`validateResolutionPaths`) only validates against the *first* parse, not the one that actually performs the write.

### Finding Description
Two independent scanners walk the same raw conflicted-file text and are expected to find the same conflict blocks in the same order:

1. `extractConflictHunks` (context builder, sent to the model and used to compute `expectedHunkCounts`): [1](#0-0) 

2. `reassembleResolvedFile` (splices the model's per-hunk resolved content back into the original on-disk content): [2](#0-1) 

The two parsers do not treat malformed/incomplete marker blocks the same way:

- In `extractConflictHunks`, when a `<<<<<<<` block never reaches a closing `>>>>>>>` before EOF, `hunkEnd` stays `-1` and the whole hunk is dropped via `continue` - but by that point the inner loops have already advanced `i` all the way to `lines.length`, consuming (and thus hiding) any *later, well-formed* conflict block in the same file: [3](#0-2) 

- In `reassembleResolvedFile`, the equivalent malformed case (`!hasSeparator || closingIndex === -1`) only skips the single `<<<<<<<` line and resumes normal line-by-line scanning, so a well-formed conflict block appearing later in the same file *is* found and processed as a legitimate hunk: [4](#0-3) 

The bridge between the two, `reassembleResolutions`, trusts that `raw.hunks` (validated only against `extractConflictHunks`'s count via `validateResolutionPaths`) lines up positionally with whatever `reassembleResolvedFile` finds when it re-walks `ctx.rawContent`: [5](#0-4) [6](#0-5) 

Exactly like the Mochi report - where `details[_id].debt` was computed with a discount while the `_usdm` parameter used elsewhere was not, and nothing reconciled the two before subtracting - here `extractConflictHunks`'s hunk count/boundaries (used for validation and for what is shown to the model) and `reassembleResolvedFile`'s hunk count/boundaries (used for the actual splice into the file that gets written to disk) are computed by separate ad-hoc scanners over the same text, and nothing guarantees they agree. When a repository contains a crafted/malformed conflict marker (e.g., a `<<<<<<<` block missing its `>>>>>>>` closer, easily produced by a bad merge tool, a manual half-edit, or a malicious commit designed to be merged), the file is judged "no conflict markers found" / hunk count 0 by the context builder, while `reassembleResolvedFile` will still find and treat a subsequent legitimate conflict block in the same file as a valid, independently-numbered hunk. `validateResolutionPaths` cannot catch this because it only checks the (already wrong) `extractConflictHunks`-derived expectation, never re-deriving counts from `reassembleResolvedFile`'s own scan.

The final write path applies whatever content comes out of this mismatch directly to disk and stages it for commit, with no re-verification that conflict markers were fully resolved as intended: [7](#0-6) 

### Impact Explanation
This is triggered purely by the *content* of a merged/rebased branch that the user is bringing in from a remote/fetched ref - the attacker does not need local access, admin rights, or any social engineering beyond having their branch/PR merged or rebased against by the victim, which is normal, expected Desktop usage. The result is that GitHub Desktop's AI conflict-resolution feature can silently write incorrect content into the victim's working file and stage/commit it (`git(['add', '--', ...pathsToStage], ...)`), matching the "silent corruption of what the user commits or pushes" impact category exactly. Because the mismatch happens below the validation layer (`validateResolutionPaths` never disagrees, since it only checks against the buggy first-pass count), there is no error surfaced to the user - the corrupted resolution looks like a normal, successful auto-resolution.

### Likelihood Explanation
Malformed/incomplete conflict markers are not exotic - they occur from partially-resolved merges committed by mistake, from other merge tools that produce slightly different marker conventions, or can be trivially crafted by an attacker who wants their branch to trigger this code path when merged. Since the feature's whole purpose is to run over attacker-influenced content (both sides of a real conflict come from remote branches), an attacker fully controls one side of the conflicted hunk and thus the exact byte layout the two parsers will disagree on. The main uncertainty is exercising the AI/Copilot session itself in a Devin sandbox (no network access to the Copilot SDK), so this analysis is based on static review of `extractConflictHunks` vs `reassembleResolvedFile`/`reassembleResolutions`/`validateResolutionPaths` rather than a runtime reproduction; a background agent with the ability to stub the Copilot SDK response should write a unit test combining a malformed hunk followed by a legitimate one to confirm the divergent hunk counts/positions concretely.

### Recommendation
- Make `reassembleResolvedFile` and `extractConflictHunks` share a single conflict-marker scanning implementation (one source of truth for what counts as a hunk, and how malformed blocks are handled), rather than two independently maintained regex/state-machine walkers.
- Have `reassembleResolvedFile` re-derive its own hunk count from `ctx.rawContent` and hard-fail (throwing `CopilotValidationError`) if that count doesn't match `raw.hunks.length`, instead of silently zipping mismatched arrays together by position.
- Treat any malformed marker block (missing separator or closing marker) as a reason to skip the *entire file* consistently in both scanners, and never advance past it in a way that lets a later legitimate hunk be interpreted differently by the two paths.

### Proof of Concept
Conceptual reproduction (would need a stubbed Copilot response to fully exercise end-to-end, but the parser divergence itself is directly demonstrable as a unit test):
```
<<<<<<< HEAD
orphaned content, never closed
=======
also orphaned
--- (EOF reached without >>>>>>> for this block; a second, real
     conflict block appears further down in the same physical file,
     e.g. because the file has two separate conflicted regions and
     the first one is malformed) ---
<<<<<<< HEAD
real ours
=======
real theirs
>>>>>>> feature
```
- `extractConflictHunks(content)` returns `hunks.length === 0` for the whole file (the malformed first block consumes the scan to EOF and is then dropped), so `buildConflictContext` marks the file `skippedReason: 'No conflict markers found'` and omits `rawContent`.
- `reassembleResolvedFile(content, hunkResolutions)`, if ever invoked with a `rawContent` for this file (e.g., via a differently-timed read, or after the file changes between context build and reassembly), will still find the second, well-formed block as `hunkIndex === 0` and splice `hunkResolutions[0]` into it - a resolution that was never actually validated against this specific hunk boundary.

This confirms the two functions do not treat identical malformed input identically, which is the exact "same underlying quantity computed two different ways, nothing reconciles them before a downstream operation trusts both" pattern from the Mochi report, here manifesting as silent file/commit corruption instead of an underflow revert.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
