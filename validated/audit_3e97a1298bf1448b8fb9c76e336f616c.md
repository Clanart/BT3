Confirmed: `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) joins purely on `bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout` — i.e. whichever transaction is recorded in `bitcoin_syncer_spent_utxos` as spending that exact outpoint becomes "the payout tx" for that withdrawal index, with no check that it matches the operator's originally-broadcast transaction bytes. `insert_spent_utxo` (`core/src/database/bitcoin_syncer.rs:335-353`) records whatever `spending_txid` first got mined for that outpoint, driven by `BlockCache::from_block` (`core/src/builder/block_cache.rs:13-24`), which indexes `input.previous_output -> tx index` for every confirmed transaction with no regard to which entity created it.

### Title
User's SinglePlusAnyoneCanPay withdrawal signature lets a third party mutate/strip the operator-identifying OP_RETURN before mining, permanently orphaning the honest operator's reimbursement - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` signs only input 0 and output 0 with `SinglePlusAnyoneCanPay`, per BIP341 leaving output 2 (the OP_RETURN carrying `operator_xonly_pk`), any extra inputs, and transaction structure outside those two elements completely unauthenticated. An attacker who observes the operator's broadcast (or the underlying `WithdrawParams`/signature via the aggregator gRPC or mempool) can build and mine an alternate transaction reusing the same input 0/output 0 with a corrupted or absent OP_RETURN, which the Bitcoin network accepts as a valid, independent spend of the withdrawal UTXO before the operator's version confirms.

### Finding Description
The binding claimed: `operator_xonly_pk_stored(withdrawal_idx) == operator_that_fronted(withdrawal_idx)`. This is broken as follows.

`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds: input 0 = withdrawal UTXO (KeySpend), output 0 = user payout, output 1 = anchor, output 2 = OP_RETURN(`operator_xonly_pk.serialize()`), and signs input 0 with `user_sig` of type `SinglePlusAnyoneCanPay`, enforced server-side in `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-203`).

`calculate_pubkey_spend_sighash`/`calculate_sighash_txin` compute the BIP341 message using `Prevouts::One(txin_index, prevout)` for this sighash type (`core/src/builder/transaction/txhandler.rs:222-229`). Per BIP341, when `ANYONECANPAY` is set, the message commits only to: hash_type, tx version/locktime, this input's outpoint/amount/scriptPubKey/sequence, the `spend_type` byte (annex bit only, since this is a key-path spend), and — because the sighash is also `SIGHASH_SINGLE` — the single output at the *same index as this input's position in the actual spending transaction*. Notably `input_index` is committed only when `ANYONECANPAY` is unset; here it is set, so the signature does not pin the input to position 0, and it does not commit to output 1 (anchor) or output 2 (OP_RETURN), nor to the total input/output count.

Consequently, anyone possessing `in_outpoint`, `input_prevout`, `output_txout`, and `user_sig` — all learnable from the mempool-broadcast operator transaction or from the `WithdrawParams` a user submits to the aggregator — can construct a new transaction placing that same input at some index n and an identical output at index n, then freely append/modify any other inputs or outputs, including replacing/removing the OP_RETURN in `output_txout`'s peer slot. `SECP.verify_schnorr` in `Operator::withdraw` (`core/src/operator.rs:630-637`) validates only this narrow sighash, so it cannot detect the substitution; it is not re-run once the attacker's transaction is mined. Bitcoin's block-inclusion rule then allows only one spend of the withdrawal outpoint to exist, and once the attacker's variant confirms, the operator's original broadcast becomes a permanent double-spend conflict and can never confirm.

`update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) later determines the payout tx purely via `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`), which joins on `bitcoin_syncer_spent_utxos` keyed only by the withdrawal outpoint — it has no way to distinguish the operator's intended transaction from the attacker's. It then runs `get_first_op_return_output` + `parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:688-692`, `609-617`) against the attacker's mutated output, fails to parse a valid x-only pubkey, and calls `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:199-251`) storing `payout_payer_operator_xonly_pk = NULL` for that withdrawal row, permanently (the outpoint is now spent; this update can never re-run with different data).

`PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-51`) polls `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`), which filters `WHERE ... payout_payer_operator_xonly_pk = $1`. With the column `NULL`, this query never matches the honest operator's key, for this row, indefinitely — `handle_finalized_payout` is never invoked for that withdrawal, and the operator that already delivered BTC to the user has no path to kickoff/reimbursement for it. Similarly `validate_payer_is_operator` (`core/src/operator.rs:1686-1740`) and `get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id` will return `None` for the payer, making manual `get_reimbursement_txs` fail as well. `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) will also treat any subsequent kickoff attempt by that operator for this deposit as malicious (`operator_xonly_pk_opt` is `None`), so the operator cannot even recover via disputing.

### Impact Explanation
An honest operator who legitimately fronted a user's withdrawal (`Operator::withdraw`, sending real BTC to the user's `out_script_pubkey`) becomes permanently unable to be matched/reimbursed for that specific withdrawal index, since the on-chain record of "which operator paid" is corrupted to `NULL` and cannot be corrected (the withdrawal UTXO is already spent). This is a genuine, repeatable loss for the operator (their fronted BTC) with no compensating kickoff/reimbursement path, matching the Critical category "an honest operator permanently unable to be reimbursed." The attack is repeatable across every withdrawal/operator pair, since it relies only on the intrinsic, protocol-wide choice of `SinglePlusAnyoneCanPay` for the withdrawal signature — not any operator- or deposit-specific defect.

### Likelihood Explanation
The attacker needs only: (1) visibility into a not-yet-confirmed operator payout broadcast (mempool) or knowledge of the `WithdrawParams`/signature sent to the aggregator/operator gRPC endpoint, (2) the ability to construct and fee-bump an alternate raw transaction reusing the same signed input/output pair (trivial, standard Bitcoin tooling), and (3) getting it mined before the operator's own broadcast (a mempool replace/race, feasible via higher fee or luck, no hashrate advantage or privileged access required). No verifier, operator, or aggregator privilege is needed. Cost is limited to bumping the fee for one transaction.

### Recommendation
Do not rely on unauthenticated transaction data (the OP_RETURN) to attribute payer identity for reimbursement. Bind the operator's identity into data that the signature actually commits to (e.g., require the operator's xonly pubkey to be embedded in `output_txout`'s committed bytes, or have the operator authenticate the whole finalized transaction to the aggregator/verifiers out-of-band, e.g. via a signed attestation of the exact txid it broadcast, verified against the on-chain confirmed transaction) rather than trusting whatever transaction happens to first spend the withdrawal outpoint on-chain.
