### Title
Unchecked u64 addition on attacker-influenced payment amounts overflows/wraps in `SignableTransaction::new`, bypassing the not-enough-funds check — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes `payment_sat + needed_fee` and `payment_sat + fee_with_change` as plain `u64` additions on values derived from the caller-supplied `payments` slice. An excessively large payment amount either panics (when overflow checks are enabled) or wraps to a small value, causing the `NotEnoughFunds` and change-amount checks to be bypassed. The resulting `SignableTransaction` is later signed by the FROST `TransactionMachine`, producing a consensus-invalid transaction whose outputs exceed 21M BTC.

### Finding Description
The analog to CVE-2018-10124 (an extreme integer argument — `INT_MIN` — reaching a negation that overflows, causing DoS) is extreme integer input reaching unchecked arithmetic in transaction construction:

- `input_sat` is bounded by real wallet funds, but `payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>()` has no bound other than `u64` (`send.rs:187`).
- The solvency check `if input_sat < (payment_sat + needed_fee)` (`send.rs:215`) adds the attacker-influenced `payment_sat` to `needed_fee` without `checked_add`. With `payment_sat` near `u64::MAX`, this either panics under `overflow-checks = true` or wraps to a small residue that is `<= input_sat`, so `NotEnoughFunds` is never returned.
- The change path repeats the pattern: `input_sat.checked_sub(payment_sat + fee_with_change)` (`send.rs:228`) subtracts a *wrapped* sum, so `checked_sub` returns `Some` for a nonsense residual, and a change `TxOut` may even be appended.

The resulting transaction (with outputs near `u64::MAX` sats) is passed to `TransactionSignMachine::sign` (`send.rs:373-397`), which computes taproot sighashes over it and produces threshold FROST shares; `complete` yields a fully signed `Transaction` that is permanently invalid — every satoshi of output exceeds any possible input, and consensus/standardness rules reject it. Each `payments` entry only needs to clear `DUST` (`send.rs:165-169`); there is no upper bound and no `Amount::MAX_MONEY`-style check.

### Impact Explanation
- With `overflow-checks` enabled (debug builds, or any profile enabling them), `payment_sat + needed_fee` is an immediate panic — a remote-triggerable denial of service in transaction construction whenever payment amounts originate from an unprivileged requester (e.g., a withdrawal/burn request feeding `SignableTransaction::new`).
- Under wrapping arithmetic, the solvency and change checks are bypassed, a signing session is consumed, and the multisig produces a transaction that can never confirm — a wasted/aborted signing round and a `fee()` accessor that itself wraps (`sum(inputs) - sum(outputs)` underflow at `send.rs:139-141`).

### Likelihood Explanation
Reachability requires `payments` values to be influenced by an unprivileged party, which holds wherever `SignableTransaction::new` is driven by externally requested withdrawals — the documented threat surface for this wallet code. The exploit needs only `payment.1` chosen within `[DUST, u64::MAX)`; no cryptographic assumption is required.

### Recommendation
Use `checked_add`/`checked_sub` for all satoshi arithmetic (`payment_sat + needed_fee`, `payment_sat + fee_with_change`, and the subtraction in `fee()`), reject payment amounts above `Amount::MAX_MONEY.to_sat()` (21M BTC), and return `TransactionError::NotEnoughFunds` on overflow rather than panicking or wrapping.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Given one funded ReceivedOutput `utxo` worth, say, 100_000 sats:
let payments = vec![
  (script_pubkey, u64::MAX - 100), // passes the DUST check
];
// payment_sat + needed_fee overflows u64:
//   - debug / overflow-checks: panic (DoS)
//   - wrapping: (u64::MAX - 100) + needed_fee wraps to a small value
//     < input_sat, so `NotEnoughFunds` is skipped and a tx paying
//     ~u64::MAX sats is constructed and handed to the FROST signer.
let _ = SignableTransaction::new(vec![utxo], &payments, None, None, 10);
```
