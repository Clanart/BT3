## Analog Found: Unchecked/unsafe ERC20 transfer in escrow withdrawal — `IntentGatewayV2.withdraw()` (Tron)

### Title
`withdraw()` releases escrow and marks orders filled based on an unchecked low-level `token.call()` instead of a real safe transfer — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core invariant break is: a function that is supposed to move funds via a *safe* transfer mechanism instead performs a transfer whose success is never actually verified, so the accounting (marking something settled/transferred) can diverge from what actually happened. The Hyperbridge analog is in the Tron variant of `IntentGatewayV2`: its escrow-release function `withdraw()` (and the `SweepDust` branch of `onAccept()`) call ERC20 `transfer()` via a raw low-level `.call()` and only check that the *call itself* didn't revert (`success`), never decoding/validating the returned boolean. This is despite the contract explicitly importing and aliasing `SafeERC20` (`using SafeERC20 for IERC20;`) — the safe path exists in the codebase but is bypassed in exactly the function that moves user/solver funds out of escrow.

### Finding Description
`withdraw()` is the internal settlement function invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` request kinds, and it is what finalizes cross-chain intent settlement on the source chain: [1](#0-0) 

For every escrowed token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
and unconditionally marks the order filled before the loop even starts: [2](#0-1) 

The same unchecked pattern is used for transaction-fee payout in the same function and for dust-sweeping in `onAccept()`'s `SweepDust` branch: [3](#0-2) [4](#0-3) 

`success` here only reflects whether the call reverted — it says nothing about whether `transfer()` actually returned `true`. Two concrete failure modes both slip through this guard:
- A non-standard/malicious ERC20 whose `transfer()` returns `false` on failure instead of reverting (a well-known and common ERC20 deviation) will still report `success == true`.
- A raw `.call()` to an address with no deployed code (`token.code.length == 0`) always returns `success == true` with empty return data on the EVM — there is no code to execute, so nothing reverts and nothing is transferred.

Contrast this with the sibling EVM implementation of the same escrow-release logic, `IntentsBase._withdraw()`, which correctly uses `SafeERC20.safeTransfer`, the exact mitigation the original report recommends: [5](#0-4) 

The Tron contract already imports `SafeERC20` (`using SafeERC20 for IERC20;`) and even uses `safeTransferFrom` on the escrow-in side elsewhere in the file, so the safe primitive is available but simply not used on the escrow-out / settlement path — the same class of gap the bug report calls out for `safeTransferMany()` not actually being safe.

### Impact Explanation
`withdraw()` is the function that finalizes cross-chain intent settlement (`RedeemEscrow` for solver payout, `RefundEscrow` for user refund on cancellation/timeout) and also the dust-sweep governance path. Because it decrements `_orders[commitment][token]` and marks `_filled[commitment] = beneficiary` regardless of whether tokens actually moved, a transfer that silently fails (either via a token contract that returns `false`, or because `token` resolves to an address without code) results in:
- The escrow being marked as released/refunded and the commitment consumed, while the beneficiary receives nothing — permanent loss of the escrowed funds (they can never be re-claimed because the commitment/order state is already finalized).
- No revert, no error surfaced to relayers or users — the ISMP message is treated as successfully processed on the destination/source side, so there's no timeout-triggered retry either.

This directly matches the bounty's "stealing or loss of funds" and "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" pivots — the beneficiary gets zero amount instead of the correct amount, with the protocol's own bookkeeping asserting the transfer succeeded.

### Likelihood Explanation
The `token` addresses that reach `withdraw()` originate from user-supplied `order.inputs[i].token` at order-creation time and are echoed back through the settlement message body (`WithdrawalRequest.tokens`), so an attacker/user fully controls which token contract is escrowed and later withdrawn. No relayer, prover, or admin collusion is required — an order creator simply needs to use a token that returns `false` on failure rather than reverting (numerous real-world ERC20s, and any custom token an attacker deploys), or engineer a scenario where the token's code is later removed/self-destructed (or was never a contract to begin with, if upstream escrow validation on this Tron variant doesn't strictly enforce `token.code.length > 0`, which was not fully verifiable from the available snippets). This is a standalone logic bug in the destination-side settlement function reachable by any permissionless order flow, not a gas/DoS/style issue.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `withdraw()` and in the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(...)`, using the `SafeERC20` library the contract already imports (mirroring `IntentsBase._withdraw()` in `evm/src/apps/intentsv2/IntentsBase.sol`). `SafeERC20.safeTransfer` reverts on a `false` return and validates that the call target actually returned decodable data, closing both failure modes described above.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer()` always returns `false` without reverting (or simply routes escrow through a `token` address that is later left with no contract code).
2. Attacker places a same-chain or cross-chain intent order using `EvilToken` (or the code-less address) as an input token, escrowing real value is not even required for `EvilToken` since only accounting matters, but the PoC generalizes to any token with this behavior.
3. On fill/cancel, `onAccept()` decodes the `WithdrawalRequest` and calls `withdraw(body, ...)`: [6](#0-5) 
4. Inside `withdraw()`, `token.call(...)` returns `success == true` (call didn't revert) even though `EvilToken.transfer` returned `false` / no code executed: [7](#0-6) 
5. `_orders[commitment][token]` is decremented and `_filled[commitment]` is set — the order is now permanently considered settled, `EscrowReleased`/`EscrowRefunded` is emitted, yet the beneficiary's token balance never changed. The escrowed value is unrecoverable.
