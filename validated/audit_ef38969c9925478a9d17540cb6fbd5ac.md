### Title
Unhandled revert in `BaseRewardPool.getReward()` reward-token loop permanently freezes claimable yield for unrelated tokens - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool.getReward()` iterates over all registered `rewardTokens` and performs an unconditional `IERC20.safeTransfer` for each token with a non-zero pending balance. There is no isolation (try/catch) between tokens: if a single reward token's transfer reverts, the entire call reverts, which blocks the claim of every other, otherwise-healthy reward token in the same pool. This mirrors the referenced Gravity Bridge finding, where an unhandled revert from one external ERC20 transfer (e.g., due to a blacklist) DoSes an entire batch/flow instead of being isolated.

### Finding Description
`getReward()` is the only path an ordinary user (via `MasterMagpie`) has to claim accrued rewards from a `BaseRewardPool`: [1](#0-0) 

The loop performs a hard `safeTransfer` for every reward token with `reward > 0`:
```
for (uint256 index = 0; index < length; ++index) {
    address rewardToken = rewardTokens[index];
    uint256 reward = userRewards[rewardToken][_account];
    if (reward > 0) {
        userRewards[rewardToken][_account] = 0;
        IERC20(rewardToken).safeTransfer(_receiver, reward);
        ...
    }
}
```
`rewardTokens` can contain any ERC20 registered via `queueNewRewards()`/`donateRewards()` by a manager (e.g. `WombatStaking`, `vlMGPBaseRewarder`), including third-party tokens such as `wom`, `mWom`, or governance/bribe tokens supplied through `WombatBribeManager`/`WombatStaking._sendRewards()` flows: [2](#0-1) 

If any one of these external tokens becomes non-transferable to a specific receiver (e.g., a blacklist-style token, a paused token, or a token that reverts on transfer for certain addresses — the exact scenario cited in the Gravity Bridge report), `userRewards[rewardToken][_account]` for that user has already been zeroed via the `updateReward` modifier's `_updateFor` call before the transfer executes... but because the whole `getReward()` transaction reverts on the failed `safeTransfer`, state changes are rolled back, and the entire claim — for every reward token in that pool, not just the problematic one — is unable to succeed. This is the same class of bug as the external report: an external call to a token transfer function is not fenced off, so a single misbehaving token can DOS the shared batch/claim path for all users of that reward pool.

The same unfenced pattern (loop of unconditional `safeTransfer` per reward token) is repeated in: [3](#0-2) [4](#0-3) 

### Impact Explanation
Because every reward token for a given pool is transferred in a single, non-isolated loop, one non-transferable/reverting reward token permanently blocks users from claiming all of their other legitimately claimable rewards from that pool via `getReward()`. Yield that would otherwise be claimable becomes permanently frozen for as long as the problematic token remains registered as a reward token for that pool, satisfying the "permanent freezing of unclaimed yield" impact bar. This affects every staker of the associated LP/staking token, not just a single account, since the reward-token list is shared per pool.

### Likelihood Explanation
Reward tokens are supplied by pool managers (e.g., `WombatStaking`, `WombatBribeManager`) and can include externally controlled ERC20s (bribe tokens, `wom`, converted `mWom`, etc.) that are outside Magpie's control. Any of these tokens implementing a blacklist, pause, or fee-on-transfer-with-revert behavior — a realistic and previously-observed pattern in production ERC20s — would trigger this DoS the next time any holder calls `getReward()`/`multiclaim`. No privileged or malicious-admin action is required; a normal user simply attempting to claim rewards triggers the revert.

### Recommendation
Wrap each per-token `safeTransfer` in `getReward()` (and the analogous loops in `vlMGPBaseRewarder._sendReward`/`getRewards` and `DelegateVoteRewardPool`) in a low-level call with error handling (e.g., `try/catch` or manual `call` + success check) so that a failure transferring one reward token does not revert the transfers of other tokens; any failed transfer amount should be re-credited to `userRewards[rewardToken][_account]` so it can be retried or recovered later instead of being lost or perpetually blocking the whole claim.

### Proof of Concept
1. A pool manager (e.g. `WombatStaking._sendRewards`) registers an external ERC20 `T` as a reward token for a `BaseRewardPool` via `queueNewRewards(amount, T)`.
2. Token `T`'s issuer later blacklists the `BaseRewardPool` contract's receiver `_receiver` (or the pool itself), causing `T.transfer` to revert for that address — a state entirely outside Magpie's control, analogous to the Gravity Bridge scenario.
3. Any user with pending balances in both `T` and any other healthy reward token (e.g. `wom`) calls `getReward(_account, _receiver)` via `MasterMagpie`.
4. The loop in `BaseRewardPool.getReward()` reaches the `safeTransfer` call for `T`, which reverts; the whole transaction reverts, including the transfer of the user's otherwise fully claimable `wom` rewards.
5. Every holder of that staking token is now permanently unable to claim any reward token from that pool through `getReward()` until the contract is manually redeployed/migrated, since there is no code path to skip or isolate the failing token.

    /// @param _account Address account
    function getReward(address _account, address _receiver)
        override
        public
        onlyMasterMagpie
        updateReward(_account)
        returns (bool)
    {
        uint256 length = rewardTokens.length;
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = rewardTokens[index];
            uint256 reward = userRewards[rewardToken][_account]; // updated during updateReward modifier
            if (reward > 0) {
                userRewards[rewardToken][_account] = 0;
                IERC20(rewardToken).safeTransfer(_receiver, reward);
                emit RewardPaid(_account, _receiver, reward, rewardToken);
            }
        }

        return true;
    }
