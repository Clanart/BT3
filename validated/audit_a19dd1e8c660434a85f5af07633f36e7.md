### Title
Attacker-controlled `n` triggers speculative `Vec::with_capacity(n)` allocation before input validation in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
The Erlang/OTP KEX vulnerability class — a small attacker-controlled field causing disproportionate memory allocation because limits on protocol-declared counts are not enforced before allocation — is present in `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`. The deserializer reads an attacker-supplied `u16` participant count `n` and immediately calls `Vec::with_capacity(usize::from(n))` for `Interpolation::Constant` coefficients, before a single scalar byte is read or `ThresholdParams::new` sanity-checks `n`.

### Finding Description
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632), the parsing order is:

1. Read curve ID (lines 578-588).
2. Read `t`, `n`, `i` from the stream (lines 591-602). `n` is a raw `u16` — fully attacker-controlled, up to 65535, with no bound checked at parse time.
3. Read the interpolation discriminant; for `0` (`Interpolation::Constant`), execute `Vec::with_capacity(usize::from(n))` (line 608) — allocating `n × size_of::<C::F>()` (~2 MB for 32-byte fields, ~3.7 MB for ed448's 56-byte scalar) based purely on the two attacker bytes.
4. Only then attempt `C::read_F` per element (lines 609-611), which fails at EOF — but the allocation has already been made, and is only freed on drop.

A ~10-byte header (`id_len || id || t || n || i || 0x00`) therefore forces a multi-megabyte heap allocation. Because Rust's `Vec::with_capacity` aborts on allocation failure rather than returning an error, sustained or concurrent calls with `n = 0xFFFF` can drive a process to OOM-abort — the same denial-of-service shape as CVE-2025-30211, where a short malformed init message produces disproportionate allocation during error handling.

The analogous pattern was mitigated elsewhere in the codebase — `Transaction::read` in the coordinator checks `commitments_len * each_commitments_len > TRANSACTION_SIZE_LIMIT` *before* allocating (coordinator/src/tributary/transaction.rs:286) — confirming this is a recognized hazard class that `ThresholdKeys::read` fails to guard against.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (explicitly in-scope: untrusted bytes to `ThresholdKeys::read`, e.g., key imports, recovery flows, or any handler deserializing peer-supplied `ThresholdKeys` blobs) forces ~3.7 MB allocation per call for a handful of input bytes — an amplification factor on the order of 10⁵×. Since allocation failure aborts rather than erroring, repeated calls create memory pressure and can crash the process, denying service to all signing/DKG operations in that process. No secret material is exposed; the impact is availability.

### Likelihood Explanation
Reachability depends on the integrator: `ThresholdKeys::read` is a public deserialization API and the rules enumerate it as an acceptable untrusted-bytes sink. Any code path that reads `ThresholdKeys` from bytes influenced by another party (key recovery payloads, session resumption, verifier-side imports) is exposed. The trigger requires only setting `n = 0xFFFF` and interpolation byte `0`; no valid signature, key, or protocol state is needed, and the failure occurs before any cryptographic check. Per-call amplification is bounded (~4 MB), so exploitation requires repeated invocation — moderate likelihood as a resource-exhaustion vector.

### Recommendation
In `ThresholdKeys::read` (crypto/dkg/src/lib.rs:604-613):

- Defer allocation until `n` is validated: construct `ThresholdParams::new(t, n, i)` (which currently runs at line 626, after the allocation) *before* reading the interpolation vector, and reject `t == 0`, `t > n`, `i > n` early.
- For `Interpolation::Constant`, drop the speculative `with_capacity(n)` or cap it (e.g., `with_capacity(n.min(1024))`), letting the Vec grow only as bytes are actually consumed — mirroring `SchnorrAggregate::read` (crypto/schnorr/src/aggregate.rs:82-85), which pushes without pre-sizing.
- Optionally impose a hard documented maximum on `n` (the protocol's real validator-set bound) before any allocation.

### Proof of Concept
```rust
// crypto/dkg/src/lib.rs — ThresholdKeys::read amplification
// Input bytes (~10 bytes for a curve with 8-byte ID):
//   id_len:   u32 = 8
//   id:       C::ID
//   t:        u16 = 1
//   n:        u16 = 0xFFFF   <-- attacker-controlled, unchecked
//   i:        u16 = 1
//   interp:   u8  = 0        (Interpolation::Constant)
//   (no further bytes)
let mut serialized = vec![];
serialized.extend(8u32.to_le_bytes());
serialized.extend(C::ID);            // e.g. b"Ed448" padded as required
serialized.extend(1u16.to_le_bytes()); // t
serialized.extend(u16::MAX.to_le_bytes()); // n = 65535
serialized.extend(1u16.to_le_bytes()); // i
serialized.push(0u8);                // Interpolation::Constant

// At line 608: Vec::with_capacity(65535) allocates ~3.7 MB for ed448 scalars
// (or ~2 MB for 32-byte fields) BEFORE any scalar is read.
// The subsequent read_exact at line 610 fails on EOF and the Vec is dropped —
// but the allocation already occurred.
let _ = ThresholdKeys::<C>::read(&mut serialized.as_slice()); // io::Error, after allocating
// Issued concurrently/repeatedly -> cumulative heap pressure -> abort on OOM.
```

Note on scope: verification_shares parsing (lines 620-623) uses `HashMap::new` with no pre-sizing and grows only on successful reads, so it is not exploitable the same way; the defect is specifically the `Vec::with_capacity(usize::from(n))` at line 608.
