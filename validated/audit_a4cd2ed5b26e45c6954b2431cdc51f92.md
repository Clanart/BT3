## Analysis

The Panoptic bug's core broken invariant: **an accounting variable is mutated with an operation (`+=`) whose author assumed a bound/uniqueness that the code never actually enforces**, silently corrupting a balance ledger that governs how much can later be released.

Searching Hyperbridge for the same broken-invariant class in escrow/order accounting reveals a direct structural analog between two sibling implementations of the same contract.

The current EVM `IntentGatewayV2.sol::placeOrder` explicitly guards against merging escrow buckets for duplicate input tokens: [1](#0-0) 

and the test suite documents this exact defense as a regression fix for an "over-release" bug: [2](#0-1) 

The Tron deployment of the same gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) never received this guard — it still accumulates escrow per token with an unconditional `+=`, exactly the "assumed-safe accumulation" pattern from the Panoptic report: [3](#0-2) [4](#0-3) 

### Title
Missing duplicate-input-token guard in Tron `IntentGatewayV2.placeOrder` merges escrow buckets, enabling over-release of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` on the Tron `IntentGatewayV2` accumulates escrow per token via `_orders[commitment][token] += reducedInputs[i].amount;` for every input leg, with no check that `token` is unique across `order.inputs`. The mainline EVM `IntentGatewayV2.sol` was patched to explicitly reject this exact case (`if (_orders[commitment][token] != 0) revert InvalidInput();`), with an accompanying regression test stating that duplicate input tokens previously "merged into one escrow bucket" and caused "over-release" during partial fills. The Tron contract still has the pre-fix behavior.

### Finding Description
An order creator fully controls `order.inputs` in `placeOrder`. By listing the same token address twice as two separate input legs (e.g., two entries each escrowing 1000 USDC), the Tron contract writes `_orders[commitment][USDC] += 1000` twice, producing a single merged bucket of 2000, while the order's `inputs` array retains two legs each nominally worth 1000. Downstream fill/withdraw logic (same pattern as `IntrinsicIntents._fillSameChain` / `_withdraw`) computes and releases escrow **per input leg index**, not per merged token bucket. Because both legs reference the same underlying storage slot, per-leg release logic can read/drain the full merged balance multiple times (once per leg) instead of a bounded, per-leg proportional share — the same class of "value read/consumed against a bucket that no longer reflects the invariant the code assumed" as the removedLiquidity overflow in the seed report. This lets a user/solver extract more tokens from escrow than were ever legitimately owed for a given leg, at the expense of the pooled escrow that other legs (and, in aggregate, the protocol's honest accounting of "who is owed what") depend on.

### Impact Explanation
This is reachable from the unprivileged, public `placeOrder` entrypoint with no relayer, prover, or admin involvement — matching the bounty's "unauthorized transaction/execution" and "fund loss" categories. The merged escrow bucket breaks the 1:1 mapping between an order's declared input legs and actual custody, which is the core safety property the mainline EVM contract's duplicate-token check was added to protect.

### Likelihood Explanation
High for any deployment of the Tron variant: the attack requires only crafting an order with a repeated `token` address in `order.inputs`, something the contract does not validate, unlike its EVM sibling which does. The existence of a dedicated regression test on the fixed EVM contract confirms the vendor already treats this exact scenario as an exploitable historical bug that was deliberately mitigated — but that mitigation was not carried over to `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Recommendation
Port the duplicate-input-token rejection from `evm/src/apps/IntentGatewayV2.sol` (`if (_orders[commitment][token] != 0) revert InvalidInput();` before assignment) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, replacing the unconditional `+=` accumulation, so every input leg maps to a unique, non-mergeable escrow slot.

### Proof of Concept
1. Construct an `Order` with `order.inputs = [ {token: USDC, amount: 1000}, {token: USDC, amount: 1000} ]` and matching output legs.
2. Call `placeOrder` on the Tron `IntentGatewayV2`; both legs write to the same `_orders[commitment][USDC]` slot via `+=`, resulting in a merged balance of 2000 while the order still logically declares two independent 1000-unit legs.
3. Trigger the same-chain/cross-chain fill or cancel path that iterates `order.inputs` per-leg and releases/refunds escrow referencing `_orders[commitment][USDC]` for each leg — this is analogous to the pattern fixed in `IntrinsicIntents._fillSameChain`/`_withdraw` on the mainline contract (see `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1931-1937`).
4. Because both legs reference the identical merged bucket, the release/refund logic can pay out against the full 2000 for what should be a single 1000-unit leg, over-releasing escrowed funds relative to what was actually deposited for that specific leg.

Note: I was not able to fully re-read the Tron contract's `_withdraw`/`fillOrder` release logic within the available tool budget to trace the exact per-leg release arithmetic line-by-line; the finding is based on (a) the confirmed absence of the duplicate-token guard in the Tron `placeOrder`, and (b) the vendor's own regression-test evidence that this exact missing-check pattern previously caused "over-release" of escrow on the sibling EVM contract before it was patched there.
