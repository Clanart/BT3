### Title
`ThresholdKeys::read` accepts semantically inconsistent key material (secret share not bound to verification shares), enabling deserialization of attacker-controlled `ThresholdKeys` - (File: crypto/dkg/src/lib.rs)

### Summary
The bug class is CWE-502: deserialization produces an object whose internal invariants were never validated, so later code trusts state that was never proven consistent. The Serai analog is `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, which parses a threshold key (params `t/n/i`, interpolation coefficients, secret share, and `n` verification shares) entirely from a byte stream and passes it to `ThresholdKeys::new`. `ThresholdKeys::new` validates counts, participant bounds, and interpolation applicability, and derives `group_key` by interpolating `verification_shares[1..=t]` — but it never checks that `C::generator() * secret_share == verification_shares[i]`, nor any other relation between the deserialized secret share and the deserialized verification shares [1](#0-0) . The FROST code itself acknowledges this hole: `AlgorithmSignatureMachine::complete` notes that the only known way to reach `InternalError` "for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" [2](#0-1) .

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, an interpolation method (with `n` coefficients for `Constant`), one secret-share scalar, and `n` group elements as verification shares [3](#0-2) . `ThresholdKeys::new` then computes `group_key` solely from `verification_shares[Participant(1..=t)]` via interpolation [4](#0-3)  and stores everything without a consistency proof. Consequently, a crafted byte stream can specify:

- a `secret_share` that does not correspond to `verification_shares[i]`, and/or
- `verification_shares` chosen so the interpolated `group_key` is a key whose discrete log the supplier knows.

Downstream, `ThresholdView` interpolates this inconsistent state into `secret_share`/`verification_shares` used for share production and share validation [5](#0-4) , and `AlgorithmSignMachine::sign`/`complete` produce and aggregate signature shares under `self.view.group_key()` derived from the attacker-influenced shares [6](#0-5) .

### Impact Explanation
Two concrete outcomes:

1. **Signing under an unintended key.** Because `group_key` is recomputed from attacker-supplied `verification_shares` and is not checked against any independent commitment, a deserialized `ThresholdKeys` silently re-binds the signer to a group key chosen by whoever supplied the bytes. Shares signed under this view verify under that (attacker-known) key — the node produces valid signatures for a key it never performed a DKG for.
2. **Integrity failure / crash.** If only `secret_share` is corrupted relative to the shares, honest signing still proceeds through `sign`, but `complete` fails aggregate verification and falls into the per-share `BatchVerifier` blame path; when all individual shares verify yet the aggregate doesn't (or vice versa), it hits `FrostError::InternalError` [7](#0-6) , which callers treat as `unreachable!()` — e.g., `processor/src/batch_signer.rs` maps `InternalError` to `unreachable!()` [8](#0-7) . A poisoned serialized key therefore converts into a node panic at signing time.

### Likelihood Explanation
Reachability requires that an `ThresholdKeys::read` input be attacker-influenced (the rules scope this to untrusted bytes fed to `ThresholdKeys::read`). Within the DKG flow, `EncryptedMessage`/keygen paths deserialize peer-provided data before key confirmation, and any integrator that loads keys from an untrusted or recoverable source (backup, migration, peer-provided state) hits this path. The defect is unconditional — there is no consistency check anywhere in `read`/`new`/`view`, so any untrusted serialized key triggers it deterministically. That said, honest local key storage is the primary intended source, so practical exploitability hinges on an integrator or protocol path feeding non-self-produced bytes to `read`. Severity: Medium.

### Recommendation
In `ThresholdKeys::new` (or at the end of `ThresholdKeys::read`), enforce the semantic invariant before returning:

- verify `C::generator() * secret_share == verification_shares[&params.i()]`, and
- for `Interpolation::Constant`, verify each share consistency relation the scheme requires (e.g., that the interpolated polynomial's evaluation at each participant matches `verification_shares[l]`), or at minimum that `group_key` computed from `1..=t` equals the group's intended key if an external commitment is available.

Reject deserialization (`io::Error`/`DkgError`) rather than constructing an inconsistent `ThresholdKeys`.

### Proof of Concept
```rust
// crypto/dkg — concept: craft a byte stream for ThresholdKeys::<C>::read
// Layout (per ThresholdKeys::write/read):
//   u32 id_len || C::ID || u16 t || u16 n || u16 i ||
//   interpolation (0x00 + n scalars | 0x01) ||
//   secret_share (F repr) ||
//   n * verification_share (G bytes)
//
// Attack: pick x_attacker known to attacker.
//   verification_shares[l] = G * f(l) for a degree-(t-1) polynomial f with f(0)=x_attacker
//   secret_share          = arbitrary y (y != f(i))
// ThresholdKeys::read succeeds: counts, bounds, interpolation checks all pass.
// group_key = G * x_attacker  (attacker knows the discrete log)
// Node signs msg -> share arithmetic consistent with group_key = G*x_attacker,
// yielding a signature verifiable under an attacker-controlled key;
// or, with mismatched y, complete() reaches FrostError::InternalError,
// which callers escalate to unreachable!() (panic).
```
