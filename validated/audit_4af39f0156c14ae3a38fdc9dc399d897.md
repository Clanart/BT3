### Title
User-supplied `security-patterns.yaml` regex can bypass `_has_redos_structure` heuristic and hang PostToolUse pattern matching on diff/file content (fail-open) - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_validate_pattern` in `extensibility.py` only rejects regexes matching two narrow structural shapes (`_REDOS_SHAPES`) plus overlapping-alternation-under-repetition (`_ALT_UNDER_REP`), then compiles and stores any regex that doesn't match those shapes. Because Python's `re` engine is a backtracking engine with no execution time bound, a regex that is catastrophic-backtracking-prone but structurally outside the heuristic's coverage (e.g., chained top-level quantifiers with no enclosing group, or repetition using `{n,m}` bounds instead of literal `+`/`*`/`?`) will pass validation and later be executed via `re.search(pattern["regex"], content)` in `security_reminder_hook.check_patterns` against attacker-influenced file/diff content, with no timeout guard.

### Finding Description
The load path is `extensibility.load_for_session` → `_load_user_patterns` → `_validate_pattern`, which gates custom regexes only through `_has_redos_structure` [1](#0-0) . That heuristic explicitly checks for exactly two shapes:

```
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")
``` [2](#0-1) 

This is explicitly documented as "not a proof," catching only "the common shapes" [3](#0-2) . Notably absent from coverage:
- Chained top-level quantifiers with no enclosing parentheses at all, e.g. `a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?b` — a classic catastrophic-backtracking shape that requires zero parenthesized groups, so `_REDOS_SHAPES` (which requires a literal `(` ... `)[+*?]`) never fires.
- Nested repetition expressed with `{n,m}` bounds instead of literal `+`/`*`/`?`, e.g. `(a{1,40}){1,40}b` — `_REDOS_SHAPES`'s first pattern requires `[+*]` characters inside/after the group and will not match `{...}` syntax.
- Similarly, alternation-under-`{n,m}`-repetition bypasses `_ALT_UNDER_REP`, which only matches `[+*]` after the group.

Any such regex passes the heuristic, compiles successfully via `re.compile(regex)` (line 229), and is stored in `_user_patterns`. It is later applied, unguarded, in `check_patterns`:
```
if not matched and "regex" in pattern and content:
    try:
        if re.search(pattern["regex"], content):
            matched = True
    except Exception:
        pass
``` [4](#0-3) 

Because a ReDoS hang is not a Python exception, the `try/except Exception` wrapper does nothing to bound execution time — the process simply blocks inside `re.search`. There is no `signal.alarm`/timeout wrapper around this call (confirmed absent from `security_reminder_hook.py`'s pattern-matching code path), so a crafted regex matched against attacker-influenced diff/file content (tens of KB, fully attacker-controlled since `content` originates from file/diff text under review) can stall the hook process for an extended, unbounded period. `debug_log` (from `_base.py`) is only ever called on already-completed branches (skip/error paths); since the hang occurs mid-`re.search`, no log entry is ever written recording the stall, matching the premise in the question.

### Impact Explanation
This is a resource-exhaustion / hang bug in a security-gating hook: a hang inside `check_patterns` during `PostToolUse` pattern checking stalls the hook's synchronous response, which delays or effectively suppresses the pattern-based security reminder for that tool call (fail-open on the pattern-check layer, though not necessarily on the separate LLM review path). This matches a low/informational availability-style impact (hook-level DoS causing delayed/failed enforcement) rather than a direct compromise (no data exfiltration, no code execution, no approval bypass of the LLM-based review). It requires the attacker to already control repo content that gets merged into `.claude/security-patterns.{yaml,json}` — i.e., this is a supply-chain-style trust boundary (whoever can commit that file to the project already influences local hook behavior in an additive, opt-in way per the file's own trust-model documentation).

### Likelihood Explanation
Feasible and reproducible: crafting `{n,m}`-bounded catastrophic backtracking patterns or parenthesis-free chained-quantifier patterns is well documented and easy to construct. The main precondition is the ability to place a `security-patterns.yaml`/`.json` file at `~/.claude/`, `<cwd>/.claude/`, or `<cwd>/.claude/security-patterns.local.*` [5](#0-4)  — meaning the attacker needs either repo-commit access to the project-local file or write access to the local `.claude` directory, which is a real but narrower attack surface (an "ordinary repository content" PR adding this file to a project that doesn't restrict `.claude/` writes). Given that the file's own docstring already promises "validated at load for catastrophic-backtracking structure and skipped ... if they look ReDoS-prone" [6](#0-5) , the heuristic's actual coverage gap represents a real correctness deficiency in that promise.

### Recommendation
Do not rely solely on static shape heuristics for user-supplied regexes executed against untrusted/large content. Recommended fixes: (1) execute custom-pattern regex matching with a hard wall-clock timeout (e.g., run `re.search` in a subprocess/thread with `signal.alarm` on POSIX, or use `regex` module's timeout support, or the `re2`-style linear-time engine) and treat timeout as "no match" plus a `debug_log` entry; (2) broaden `_has_redos_structure` to also flag parenthesis-free chained quantifiers/`{n,m}` bounded repetition adjacent to other quantified atoms; (3) cap the size of `content` passed into `re.search` for user-supplied patterns.

### Proof of Concept
Unit/fuzz test plan for `plugins/security-guidance/hooks/extensibility.py`:
1. Add regex `r"a{1,40}{1,40}b"`-style or realistically `r"(a{1,30}){1,30}c"` (or a parenthesis-free `r"a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?a?b"`) as `regex` in a `security-patterns.json` fixture with a valid `rule_name`/`reminder`.
2. Call `extensibility._validate_pattern(entry, source="test")` and assert it returns a non-`None` rule (i.e., `_has_redos_structure` returned `False` — heuristic bypass confirmed).
3. Feed the returned rule into `security_reminder_hook.check_patterns(file_path, content)` where `content` is a 10–50KB string of `"a" * N` (no trailing `b`/`c`), simulating attacker-controlled diff content.
4. Wrap the call with a hard timeout (e.g., `signal.alarm(5)` or run in a subprocess with `multiprocessing.Process` + `.join(timeout=5)`); assert the call does **not** complete within 5 seconds, demonstrating the hang.
5. Assert no corresponding `debug_log` entry exists for this rule at the time of the hang (grep the debug log file), confirming the hang is unrecorded per the question's premise.
