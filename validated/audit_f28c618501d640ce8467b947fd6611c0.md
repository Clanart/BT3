### Title
Stack exhaustion via unbounded recursive nesting in `AccountKeyRoleBased` RLP/JSON decoding - (File: `blockchain/types/accountkey/account_key_serializer.go`)

### Summary
The `AccountKeyRoleBased` account key type is decoded recursively through `AccountKeySerializer.DecodeRLP`/`UnmarshalJSON`, which dispatches to `NewAccountKey(keyType)` and then decodes the concrete key. Because a `RoleBased` key's elements are themselves generic `AccountKey` values, a `RoleBased` key can (during decoding) contain another `RoleBased` key, which contains another, and so on, with no depth limit enforced before or during decode. The only guard against "nested composite" keys (`checkAccountKeyZeroValues` in `api/api_kaia.go` and `CheckInstallable`/`CheckUpdatable` in `blockchain/types/accountkey/account_key_role_based.go`) runs *after* the value has already been fully decoded/recursed through the RLP/JSON stack. An attacker can craft a single `TxTypeAccountUpdate` transaction (or any RLP payload that ends up going through `AccountKeySerializer.DecodeRLP`, e.g. via the public `klay_decodeAccountKey`/`klay_encodeAccountKey` RPC) with thousands of nested `RoleBased` keys, causing unbounded Go call-stack recursion during decode and crashing the node process (goroutine stack overflow => fatal, unrecoverable panic), independent of any prior semantic validation.

### Finding Description
`AccountKeySerializer.DecodeRLP` reads the key type tag and then recursively decodes the concrete key type: [1](#0-0) 

The equivalent JSON path has the same structure: [2](#0-1) 

`AccountKeyRoleBased` is itself a slice of `AccountKey` interface values, each of which may again be a `RoleBased` key at decode time — there is no depth check anywhere in the decode path: [3](#0-2) 

The only "no nested RoleBased" enforcement exists in code paths that run **after** the key has already been recursively decoded — `checkAccountKeyZeroValues` in the public RPC handler: [4](#0-3) 

and `CheckInstallable`/`CheckUpdatable`, which are only invoked when an `AccountUpdate` transaction attempts to install/update the key on state, again after full decoding of the transaction (and thus the nested key) has already completed: [5](#0-4) 

Because RLP list/struct decoding recurses once per nesting level with no explicit maximum-depth guard (only an overall byte-size input limit is enforced by the RLP stream), an attacker can construct a payload where each nesting level costs only a few bytes of RLP framing, allowing many recursion levels within a modest-size transaction payload. This directly mirrors the CVE-2023-2793 bug class: parsing/recursing into attacker-supplied nested structure before any validation of "reasonable depth" is performed, exhausting the call stack and crashing the process — a denial-of-service.

### Impact Explanation
A single unprivileged transaction sender can submit (or relay via public RPC) a `TxTypeAccountUpdate` transaction, or call `klay_decodeAccountKey`/`klay_encodeAccountKey`, containing a deeply nested `AccountKeyRoleBased` value. When any node (validator, full node, or RPC server) decodes this transaction/key — during tx-pool ingestion, block execution, or the RPC call itself — the recursive decode can exhaust the goroutine stack, causing a fatal, unrecoverable Go runtime crash (`fatal error: stack overflow`) that terminates the process. This is a network-reachable denial-of-service affecting any node that processes the transaction, matching the "AccountKey authorization" and "public RPC" reachable categories.

### Likelihood Explanation
High likelihood: no special privileges, funds, or timing are required — a single, syntactically valid (well before final semantic validation) transaction or a single RPC call with a crafted payload is sufficient. The nested-`RoleBased` restriction is enforced only after decode completes, so the vulnerable code path is unconditionally reached by any submitted `AccountUpdate` transaction or `DecodeAccountKey`/`EncodeAccountKey` RPC call carrying a maliciously nested key.

### Recommendation
Enforce a maximum recursion/nesting depth check at decode time, before or during `AccountKeySerializer.DecodeRLP`/`UnmarshalJSON` and within `AccountKeyRoleBased`'s decoding logic, rejecting any key whose nesting exceeds the single level Kaia's protocol already intends to allow (RoleBased keys must not contain RoleBased sub-keys). This should happen as an early bound check inside the recursive decode itself (e.g., track/limit nesting depth via a depth counter passed through decode calls), not only in `checkAccountKeyZeroValues`/`CheckInstallable`, so that the recursive stack growth itself is bounded regardless of when validation runs.

### Proof of Concept
1. Construct an RLP-encoded `AccountKeySerializer` payload where `keyType = AccountKeyTypeRoleBased` and its single element is itself an `AccountKeySerializer` with `keyType = AccountKeyTypeRoleBased`, repeated recursively N times (e.g., N = 100,000), each level adding only a few bytes of RLP list/tag framing.
2. Wrap this payload as the `AccountKey` field of a `TxTypeAccountUpdate` transaction (or submit the raw bytes directly to the public `klay_decodeAccountKey` RPC endpoint exposed by `KaiaAPI.DecodeAccountKey`, see `api/api_kaia.go:167-173`).
3. Submit the transaction via `eth_sendRawTransaction`/tx-pool ingestion, or call the RPC directly.
4. The node's RLP decoder recurses through `AccountKeySerializer.DecodeRLP` -> `NewAccountKey` -> nested `AccountKeyRoleBased` decode N times before any nested-composite-type check (`checkAccountKeyZeroValues`, `CheckInstallable`) is ever reached, exhausting the goroutine stack and crashing the process.

Note: I was unable to directly inspect the exact `AccountKeyRoleBased.DecodeRLP` implementation (only its non-decoding methods were retrieved) to confirm the precise internal recursive call chain byte-for-byte; the analysis is based on the confirmed `AccountKeySerializer` recursive dispatch pattern and the confirmed post-hoc nature of the nested-RoleBased validation checks. A Devin session with full file access would be needed to pin down the exact decode function signature for final confirmation.

func (serializer *AccountKeySerializer) UnmarshalJSON(b []byte) error {
	var keyJSON AccountKeyJSON

	if err := json.Unmarshal(b, &keyJSON); err != nil {
		return err
	}

	if keyJSON.KeyType == nil {
		return errNoKeyType
	}
	serializer.keyType = *keyJSON.KeyType

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return json.Unmarshal(keyJSON.Key, serializer.key)
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
}
