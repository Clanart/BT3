## Title
Path-containment check in `resolveWithin` uses an unbounded string-prefix comparison, allowing repository-scoped operations to escape into sibling directories - (File: `app/src/lib/path.ts`)

### Summary
The report's root cause is a boundary/threshold check that is *supposed* to enforce "value must be within range X" but, due to a comparison error, silently accepts values that are technically outside the intended range (`factor >= precision` incorrectly treated as "fully unlocked", `factor < precision` incorrectly treated as "under-unlocked"). The Desktop analog is the containment check in `_resolveWithin`, which is meant to guarantee "resolved path is inside `rootPath`" but implements that guarantee with a raw string-prefix test instead of a path-boundary-aware test.

### Finding Description
`_resolveWithin` computes the final decision with:

```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

`String.prototype.startsWith` has no concept of a path separator boundary. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo`, then `realResolved` values such as `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa` or `/Users/victim/Documents/GitHub/myrepo.bak/creds.json` also satisfy `startsWith(realRoot)`, even though they live in a completely different directory that merely shares the root path as a *string* prefix. The function's own documentation states the invariant it's supposed to enforce — "the resolved path is guaranteed to reside at, or underneath this path" — but the implementation only checks a substring relationship, not a directory-boundary relationship (e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`).

This helper is treated as the authoritative sandbox boundary at the one call site that accepts attacker-influenced input directly from a clickable deep link: `dispatcher.openRepositoryFromUrl` handles the `open-repository-from-url` action (parsed in `parseAppURL`/`parse-app-url.ts` from a `x-github-client://openRepo/...?filepath=...` URL) and only performs one extra check — rejecting absolute paths — before delegating the entire "is this safe" decision to `resolveWithin`:

```ts
if (isAbsolute(filepath)) {
  log.error(`Refusing to open absolute path: ${filepath}`)
  return
}
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else { ... }
``` [2](#0-1) 

The `isAbsolute` guard does nothing to stop a relative traversal like `../myrepo-secrets/id_rsa`, and the symlink-safe `realpath` resolution inside `resolveWithin` does not help either, because the escape here happens at the plain path-arithmetic level (`resolve(root, "..​/sibling")`), not via a symlink — the final `startsWith` test is the *only* remaining guard, and it is exactly the check that is broken.

### Impact Explanation
`resolveWithin` is the shared containment primitive for repository-scoped filesystem operations reachable from remote/attacker-influenced input (deep-link `filepath`, and file paths in `copilot-conflict-context.ts`'s `buildConflictContext`, `app-store.ts`). Because the boundary check accepts sibling paths that merely share a prefix, an attacker who can get the victim to click a crafted `x-github-client://openRepo/...` link can point Desktop's file-reveal/file-read logic at a directory outside the intended repository whenever the victim's local clone directory name is a prefix of another directory name on disk (a common pattern for backup/duplicate clones such as `myrepo`, `myrepo.bak`, `myrepo-old`, `myrepo2`). This breaks the "operations stay inside the repo" invariant the function exists to guarantee, matching the class of "silent corruption/escape of a value the sandbox was supposed to bound" called out in the source report.

### Likelihood Explanation
Exploitability depends on the coincidental existence of a same-prefixed sibling directory on the victim's disk, which is a real but not universal condition (common for people who keep multiple copies/forks of a repo, e.g. `Project` and `Project-fork`, side by side in the same parent folder such as the default `~/Documents/GitHub`). The attack requires only a single click on a link the attacker controls (the standard `x-github-client://openRepo` deep-link flow already used by GitHub.com's "Open in Desktop" button), with no local access, no admin rights, and no pre-existing malware — matching the in-scope "link or deep link the user clicks" primitive.

### Recommendation
Replace the string-prefix comparison in `_resolveWithin` (`app/src/lib/path.ts`) with a boundary-safe check, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the report's own recommendation pattern of fixing the boundary logic itself rather than adding more downstream special-casing.

### Proof of Concept
1. Victim has two directories side by side: `/Users/victim/Documents/GitHub/myrepo` (a Desktop-managed clone) and `/Users/victim/Documents/GitHub/myrepo-secrets` (any other folder, e.g. another clone or a backup dir).
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/<owner>/myrepo?filepath=..%2Fmyrepo-secrets%2Fid_rsa`
3. Desktop parses this via `parseAppURL` into an `open-repository-from-url` action with `filepath = "../myrepo-secrets/id_rsa"` [3](#0-2) .
4. `dispatcher.openRepositoryFromUrl` opens/selects `myrepo`, sees `filepath` is not absolute, and calls `resolveWithin(repository.path, filepath)` [4](#0-3) .
5. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa`, and `realResolved.startsWith(realRoot)` (`realRoot = ".../myrepo"`) evaluates `true` because `"myrepo-secrets"` starts with `"myrepo"` — the null-returning containment guard is bypassed [5](#0-4) .
6. `shell.showItemInFolder(resolved)` reveals a file outside the intended repository directory tree, confirming the escape.
