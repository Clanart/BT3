Confirmed: `authorized_providers` is permanently curried into the CR-CAT puzzle at creation time via `construct_cr_layer` [1](#0-0) , and there is no mechanism in the codebase to change or bypass this list once the coin exists on-chain.

### Title
CR-CAT funds can be permanently locked if the required Verified Credential (VC) hook is unavailable, with no user emergency exit - (File: `chia/wallet/vc_wallet/cr_cat_wallet.py`)

### Summary
Spending a Credential-Restricted CAT (CR-CAT) is enforced by a CLVM-level "hook" — the `CREDENTIAL_RESTRICTION` layer — that requires a valid proof-of-inclusion signed by a VC (Verified Credential) singleton belonging to one of the CAT's hardcoded `authorized_providers`. If the wallet cannot obtain a matching VC with valid, current proofs (VC lost, provider unresponsive, proofs revoked/expired, or the VC coin otherwise unusable), the wallet-level code raises and refuses to build a spend, and there is no alternative/emergency path defined at the puzzle level to move the coin. This mirrors the reported Algebra bug: closing/spending a position depends on an external hook, and a broken hook blocks user funds with no rescue mechanism.

### Finding Description
`CRCATWallet._generate_unsigned_spendbundle` looks up a VC wallet and requires `vc_wallet.get_vc_with_provider_in_and_proofs(self.info.authorized_providers, self.info.proofs_checker.flags)` to succeed; if no wallet of type `VC` exists it raises `RuntimeError("CR-CATs cannot be spent without an appropriate VC")`, and if `vc is None` afterward it raises `RuntimeError("Spending no cat coins is not an appropriate use of _generate_unsigned_spendbundle")` [2](#0-1) [3](#0-2) .

At the puzzle level, `construct_cr_layer` curries a fixed `authorized_providers` list and `proofs_checker` into the CAT's inner puzzle at coin-creation time [1](#0-0) . Every subsequent spend must supply `solve_cr_layer` arguments (`proof_of_inclusions`, `proof_checker_solution`, `provider_id`, `vc_launcher_id`, `vc_inner_puzhash`) derived from a live, currently-held, currently-authorized VC [4](#0-3) . `claim_pending_approval_balance` (the mechanism by which a user recovers CR-CATs sent to them without immediate VC availability) also unconditionally requires a valid VC and raises if none exists: `"No VC exists that can approve spends for CR-CAT wallet"` [5](#0-4) .

Because `authorized_providers` is baked into the coin's puzzle hash forever, there is no path in the CLVM or wallet code to spend a CR-CAT coin using anything other than proofs from one of those exact providers' VCs. If the last usable VC for a given provider set is destroyed, melted, revoked, or its proofs become stale/unrenewable (e.g., the issuing DID/provider goes offline or the VC coin is inadvertently spent to an incompatible state), the underlying CAT value becomes permanently unspendable — there is no "melt", "burn", or "emergency exit" analogous to a standard CAT's TAIL-based melt path that bypasses the credential-restriction hook.

### Impact Explanation
This is a spend-triggered transaction-processing halt for the affected user: legitimately-owned CAT value becomes permanently inaccessible with no on-chain or wallet-level recovery mechanism, matching the "concrete unauthorized coin movement ... or a spend-triggered transaction-processing halt" acceptance criterion. Unlike ordinary CATs (which only need the TAIL/inner puzzle), CR-CATs add a mandatory external dependency (the VC/provider hook) that, once broken, cannot be worked around by the coin owner, wallet, or full node — the funds are functionally destroyed while still existing as unspendable coins.

### Likelihood Explanation
CR-CATs are explicitly designed for regulated/credentialed use cases where a `VerifiedCredential` must be periodically re-proved and where `authorized_providers` are external, potentially centralized identity issuers. Any of the following ordinary operational events triggers the failure: the user's VC coin is spent/melted (see `magic_condition_for_new_proofs` noting "TP update is not allowed because then the singleton will leave the VC protocol" [6](#0-5) ), the provider ceases to issue/renew proofs, or the user simply loses the VC wallet's key material. None of these require a malicious actor — they are foreseeable operational failures for a user holding CR-CAT balances long-term.

### Recommendation
Add an emergency/self-recovery exit for CR-CAT holders that does not depend on a live, authorized-provider-issued VC — for example, a time-locked or multi-provider fallback path, or a documented, puzzle-level melt/escape condition analogous to standard CAT melting, so that coin value is not permanently strandable purely because an external credential-issuing hook becomes unavailable. At minimum, the wallet and documentation should clearly flag that CR-CAT balances are irrecoverable if the associated VC/provider becomes unusable, and provide tooling to proactively renew/rotate proofs well before expiry.

### Proof of Concept
1. Create a CR-CAT with `authorized_providers = [provider_did]` via `construct_cr_layer` and mint/receive CR-CAT coins to a wallet.
2. Obtain a VC from `provider_did` and use `CRCATWallet` to spend/receive CR-CATs normally (`_generate_unsigned_spendbundle`, `claim_pending_approval_balance`), which succeeds because `vc_wallet.get_vc_with_provider_in_and_proofs` returns a usable VC [7](#0-6) .
3. Simulate the VC becoming unusable: delete/spend the VC coin outside the wallet, or have `provider_did`'s DID stop signing new proof announcements so `proof_hash`/proof-of-inclusion can no longer be freshly generated.
4. Attempt any further CR-CAT spend or `claim_pending_approval_balance` call: `get_vc_with_provider_in_and_proofs` returns `None`, causing `RuntimeError` at [3](#0-2)  or [8](#0-7) , and no other code path exists in `cr_cat_drivers.py` or `cr_cat_wallet.py` to construct a valid `solve_cr_layer` solution without such a VC — the CR-CAT coin(s) remain permanently unspendable.

```python
def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,
) -> Program:
    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)
```

```python
def solve_cr_layer(
    proof_of_inclusions: Program,
    proof_checker_solution: Program,
    provider_id: bytes32 | None,
    vc_launcher_id: bytes32 | None,
    vc_inner_puzhash: bytes32 | None,
    my_coin_id: bytes32,
    inner_solution: Program,

    solution: Program = Program.to(
        [
            proof_of_inclusions,
            proof_checker_solution,
            provider_id,
            vc_launcher_id,
            vc_inner_puzhash,
            my_coin_id,
            inner_solution,
        ]
    )
    return solution
```
