## Finding

`build_refute_prompt` in `plugins/security-guidance/hooks/review_api.py` truncates the diff passed into the self-refute (Stage 2) prompt with a hard, non-anchored character slice: `diff_text[:8000]` [1](#0-0) . This is independent of, and far smaller than, the `DIFF_TOTAL_BYTES` cap (400000 bytes) already applied upstream by `cap_diff_for_prompt` for the Stage 1 investigate prompt [2](#0-1) . The identical pattern is duplicated inline in `llm.py`'s `agentic_review` at the refute-prompt construction step [3](#0-2) .

The refute prompt explicitly instructs the model to refute a candidate as "PRE-EXISTING" whenever the cited `vulnerableCode` "does NOT appear on any + line in the DIFF block above" [4](#0-3) . Because the "DIFF block above" is silently cut at the first 8000 characters with no anchoring to file boundaries or to the specific lines cited by the Stage-1 candidates, any diff content in the actual malicious/high-risk change that lands past that 8000-character offset is invisible to the Stage 2 adversarial-verification pass. A crafted diff that front-loads low-risk filler content (e.g. a large but benign file, verbose comments, padding) before the truly dangerous `+` lines will push the dangerous lines past the cutoff. The refute model, unable to see those `+` lines in its truncated "DIFF" section, will apply the PRE-EXISTING rule and refute the legitimate Stage-1 finding, causing the vulnerability to be dropped from `survived` and never surfacing in the final guidance returned to the user [5](#0-4) .

This satisfies the stated invariant violation: truncation in the Stage 2 refute path is not anchored to the specific lines the candidates cite, so it can consistently and predictably drop the high-risk lines a user expects to be reviewed, by an attacker simply padding the diff.

### Title
Unanchored 8000-char diff truncation in self-refute prompt causes false-negative refutation of real Stage-1 findings - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` truncates the diff shown to the Stage 2 adversarial-refute model to the first 8000 characters with no regard for where the Stage-1 candidate's cited `vulnerableCode` actually sits in the diff. An attacker who controls diff ordering/padding can push the real malicious `+` lines past this cutoff, causing the refute model to wrongly classify the true finding as "PRE-EXISTING" (not present in the visible diff) and refute it, suppressing the security guidance that would otherwise flag the change.

### Finding Description
`build_refute_prompt(candidates, diff_text)` builds the Stage 2 prompt as `"...DIFF:\n" + diff_text[:8000]` [1](#0-0) . The `diff_text` passed in already went through `cap_diff_for_prompt`/`_cap_files_for_prompt` at Stage 1 (400000-byte total cap) [6](#0-5) , but Stage 2 re-truncates far more aggressively and with a flat slice rather than per-file/anchored logic. The refute instructions explicitly tell the model to refute when the cited code is absent from "any + line in the DIFF block above" [4](#0-3) , and also to refute `off_diff`-tagged candidates unless the "enabling diff line" can be named [7](#0-6) . Since none of the truncation logic checks whether the 8000-char window actually contains the lines the candidates reference, a diff engineered with sufficient benign leading content will have its dangerous lines silently excluded from the model's view, systematically triggering the PRE-EXISTING refutation path and causing `survived` (the set of findings that make it into the final guidance) to omit the real vulnerability [8](#0-7) . The identical unanchored `diff_text[:8000]` truncation exists in `llm.py`'s inline duplicate of this refute-prompt construction [3](#0-2) , so both the CC hook path and the `review_api.py` importable surface (documented as being used by external agentic harnesses) [9](#0-8)  are affected.

### Impact Explanation
This is a review-evasion / false-negative issue: the security reviewer is fooled into suppressing findings about genuinely introduced vulnerable code, so dangerous changes ship without the guidance that the Stop hook / commit reviewer is meant to surface to the user. This maps to the stated "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink" impact category indirectly — a suppressed vulnerability finding (e.g. a genuine secret-exfiltration or SSRF sink introduced in the diff) proceeds unflagged into the codebase/commit, defeating the review control whose entire purpose is to catch exactly that class of sink.

### Likelihood Explanation
The precondition is simply that a diff under review exceeds ~8000 characters with the truly dangerous `+` lines occurring after that offset — a low bar, easily satisfied by padding with legitimate refactor noise, generated code, or large unrelated file changes ahead of the injected vulnerability, all of which is normal content an attacker fully controls when the diff itself is the artifact being reviewed. No special privilege is needed; it only requires the ability to shape the diff content that gets reviewed, which is the explicit attacker model for this question.

### Recommendation
Replace the flat `diff_text[:8000]` slice with anchored truncation: for each candidate, guarantee the file/line context containing its cited `vulnerableCode` is included in the refute prompt (e.g., build a per-candidate context window around the cited lines, or truncate per-file after ensuring every candidate's anchor file is represented) instead of a single global character cutoff. At minimum, raise the cap enough to match `DIFF_TOTAL_BYTES` consistency with Stage 1, and/or drop the "PRE-EXISTING" auto-refute rule when the diff was truncated (flag truncation and require the refute model to treat unseen sections as "cannot confirm absence" rather than defaulting to REFUTE).

### Proof of Concept
Unit test plan (extends `review_api.py` test coverage):
1. Construct a diff with a large benign leading file (~9000+ chars of `+` lines, e.g. a generated lockfile) followed by a second file whose `+` lines contain an obviously dangerous sink (e.g. `+    subprocess.run(user_input, shell=True)`).
2. Build a `candidates` list containing one dict whose `vulnerableCode` is `"subprocess.run(user_input, shell=True)"` and `filePath` pointing at the second file.
3. Call `build_refute_prompt(candidates, diff_text)` and assert that the resulting prompt's `"DIFF:\n"` section (i.e., `diff_text[:8000]`) does NOT contain the string `"subprocess.run(user_input, shell=True)"` — demonstrating the anchor line is dropped.
4. Assert that under the current implementation, this predictably reproduces regardless of which file the dangerous line is in, purely as a function of its byte offset exceeding 8000 — showing truncation is not anchored to any candidate's cited evidence.
5. (Integration) Feed this prompt through the refute LLM call and confirm it returns the candidate in `refuted` with a "PRE-EXISTING"/"not found in diff" reason despite the line being genuinely new, validating the false-negative behavior end-to-end.

```python
def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```
