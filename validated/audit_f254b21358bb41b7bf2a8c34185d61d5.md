### Title
`extractSecretScanningResults()` extracts an unvalidated `bypassURL` from attacker-controlled git remote error text and passes it straight to `shell.openExternal()` - ([File: app/src/ui/dispatcher/error-handlers.ts])

### Summary
`extractSecretScanningResults()` parses GitHub's secret-scanning push-protection message off the raw stderr of `git push` and extracts a `bypassURL` via a permissive regex with no scheme/host allowlist. [1](#0-0)  That string is stored as `ISecretScanResult.bypassURL` and rendered as the `uri` prop of `LinkButton` in `PushProtectionErrorDialog`, and `LinkButton`'s click handler unconditionally forwards `uri` to `shell.openExternal(uri)`. [2](#0-1)  The dialog only decides between two flows based on `requiresApproval`: either `LinkButton uri={secret.bypassURL}` (delegated bypass, requires approval) or a same-origin dispatcher call (self bypass). [3](#0-2) 

### Finding Description
The invariant that's broken is: "a bypass link shown to the user for GitHub's push-protection feature is always a `github.com` URL." Nothing in the code enforces that. The regex used to extract `bypassURL` is `.*?(?<bypassURL>https[\s\S]*?) ` — it only requires the substring to start with `https` and end at the next whitespace; it does not anchor to `github.com` or any specific path. [4](#0-3)  `requiresApproval` is likewise derived from freeform text matching (`match.at(0)?.includes('request an exemption')`), also attacker-influenced. [5](#0-4) 

This `remoteMessage` originates from the stderr/output of the git remote during `push` — i.e., from whatever the remote (or a MITM/malicious proxy sitting on that connection) returns as the rejection message text, which Desktop treats as trusted content to build a clickable "Bypass" UI element. `LinkButton` has no allowlist check on `uri`; any string, including `javascript:`, `file:`, or a custom/malicious `https://` phishing domain crafted to look like an approval URL, is passed straight into `shell.openExternal()`. [6](#0-5)  The button is rendered specifically for the `requiresApproval` (delegated bypass) case, which a malicious/compromised remote can trigger by crafting the push-rejection text to include the "request an exemption" marker. [7](#0-6) 

This is the structural analog of the ERC721/ERC1155 `balanceOf()` bug: the code assumes a narrower/trusted shape of input (a well-formed GitHub bypass URL) but the actual extraction path accepts a broader, attacker-influenced value without the extra validation needed to enforce that assumption — directly mirroring "detect condition X and validate accordingly" being skipped.

### Impact Explanation
A malicious or compromised git remote/proxy (attacker fully controls the response bytes on push rejection) can inject an arbitrary URL that Desktop will render as a legitimate "Bypass"/"request an exemption" button and, on click, hand directly to `shell.openExternal()`. This is a classic Electron `shell.openExternal` abuse vector: depending on OS handling of URI schemes, this can range from convincing-phishing (fake GitHub OAuth/login page to steal credentials or tokens) up to invoking arbitrary registered URI-scheme handlers or local files, since no scheme/host restriction exists at any point in this pipeline.

### Likelihood Explanation
Requires only that the user push to (or fetch push-protection errors from) a remote controlled or intercepted by the attacker, and click the resulting "Bypass" link inside a dialog Desktop itself presents as a legitimate GitHub UI flow — no local access, admin rights, or pre-existing malware needed, matching the required threat model of an attacker-controlled git remote/proxy response.

### Recommendation
Validate `bypassURL` (and the `requiresApproval` classification) against a strict allowlist — e.g., require the parsed URL to have `https:` scheme and host `github.com` (or the enterprise instance host) before storing/rendering it — before ever passing it to `LinkButton`/`shell.openExternal()`. This mirrors the ERC1155 fix pattern: detect the actual shape of untrusted data and apply the correct validation branch rather than assuming a fixed trusted format.

### Proof of Concept
1. Attacker controls (or MITMs) a git remote endpoint used for `git push`.
2. On push, the remote returns rejection text crafted like GitHub's real secret-scanning message but with the "request an exemption" marker present and a `bypassURL` such as `https://attacker.example.com/login`, matching the accepted regex `https[\s\S]*? `.
3. Desktop's `extractSecretScanningResults()` parses this into an `ISecretScanResult` with `requiresApproval: true` and `bypassURL: "https://attacker.example.com/login"`. [8](#0-7) 
4. `PushProtectionErrorDialog` renders `<LinkButton uri={secret.bypassURL} onClick={onDelegatedBypassLinkClick}>Bypass</LinkButton>`. [7](#0-6) 
5. User clicks "Bypass"; `LinkButton.onClick` calls `shell.openExternal("https://attacker.example.com/login")` with no validation, opening the attacker's phishing page in the user's default browser under the guise of a trusted GitHub bypass flow. [6](#0-5)
