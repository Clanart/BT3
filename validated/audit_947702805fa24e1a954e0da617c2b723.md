### Title
Duplicate-key detection in pure-Python `json_format.Parse` compares raw JSON key strings instead of resolved field identity, silently allowing a second differently-spelled key to override a field - (File: `python/google/protobuf/json_format.py`)

### Summary
Keycloak's `PathMatcher` bug compares an unnormalized request URI string against configured security-policy paths; because the comparator doesn't canonicalize the input before the check, an attacker can present a semantically-identical-but-differently-spelled URI and get matched to a different (less restrictive) rule than intended. The proven analog in this Protobuf checkout is in the pure-Python ProtoJSON parser: its "reject duplicate keys" invariant is enforced on the literal JSON key text, not on the canonical field identity the key resolves to. Since `json_name` (camelCase) and the proto field name (snake_case) both resolve to the same `FieldDescriptor`, an attacker-controlled JSON payload containing both spellings of one field is not recognized as a duplicate and both assignments are applied, with the later one silently winning — exactly like PathMatcher applying the "wrong" (differently-spelled) rule because normalization/canonicalization was skipped before the equality check.

### Finding Description
`google.protobuf.json_format.Parse` (pure-Python implementation) is a public, documented parsing API that consumes attacker-controlled ProtoJSON. The project's own test suite documents the flaw as an acknowledged behavioral bug: [1](#0-0) 

```
def testDuplicateFieldAlternateNames(self):
    # Note: this behavior is non-spec and an oversight bug in the
    # implementation, but would be a breaking change to fix. The duplicate field
    # checker intends reject inputs with duplicate key names, but it only
    # catches keys that are exact matches and not alternate spellings that
    # correspond to the same field.
    parsed_message = json_format_proto3_pb2.TestMessage()
    json_format.Parse('{"int32Value": 1,"int32_value":2}', parsed_message)
    self.assertEqual(parsed_message.int32_value, 2)

def testDuplicateFieldAlternateNamesMap(self):
    ...
    json_format.Parse(
        '{"int32Map": {"1": 2}, "int32_map": {"3": 4}}', parsed_message
    )
    self.assertEqual(parsed_message.int32_map, {3: 4})
```

Compare with the correct behavior expected/enforced by the standard test, which does detect exact literal duplicates:
`self.CheckError('{"int32Value": 1,\n"int32Value":2}', 'Failed to load JSON: duplicate key int32Value.')` — a check that operates purely on the *string* key before it is resolved against the schema. [2](#0-1) 

The invariant that fails to transfer correctly is: "each field may be assigned at most once / duplicate assignment should be rejected (or deterministically flagged), based on the field the key represents." Instead, the check is keyed on the raw JSON text before name normalization (camelCase↔snake_case via `json_name`), so two spellings of the same `FieldDescriptor` are treated as two different, unrelated keys. This mirrors PathMatcher's failure mode: the security-relevant comparison (duplicate-field / policy-path matching) is performed on the untransformed textual representation rather than on the canonical identity it maps to.

By contrast, the C++/upb JSON parser explicitly tracks "seen" state per resolved `FieldDescriptor`/`Traits::Field`, not per string, and therefore correctly rejects the second assignment regardless of which spelling was used: [3](#0-2) 

This confirms the pure-Python path is the outlier implementation lacking the correct invariant, and that upstream protobuf is aware fixing it is a breaking change they have chosen not to make yet.

### Impact Explanation
This is a data-integrity / silent-override issue in a schema-trusted, bounded-input parsing path, not a memory-safety or RCE issue. Its practical impact depends entirely on the consuming application: if application logic performs a check on the first-seen or dict-derived representation of a JSON payload and then trusts the parsed protobuf message for a security decision (e.g., authorization "field mask," a "last-writer" merge policy, or logs `int32Value` as the audited value while `int32_value` is what actually lands in the object), the mismatch between apparent intent and actual assigned value could enable request-smuggling-style confusion. It does not itself grant memory corruption, and does not violate confirmed size/depth/allocation limits (excluded per the report's scope). Given Protobuf's exclusions of "harmless canonical-signature/catchable exception" classes, this sits at low-to-moderate severity: a real but narrow confusion/integrity primitive, not the "authorization bypass" severity level Keycloak's CVE carries, because Protobuf itself makes no policy decisions — any authorization impact requires an external application built on top of this behavior.

### Likelihood Explanation
High likelihood of occurrence given normal, unprivileged use: any ordinary client calling the public `json_format.Parse` API with attacker-supplied JSON can trigger this by simply including both the camelCase and snake_case spelling of one field (or one map field) in the same JSON object. No special schema, extension, or privileged capability is required, and the behavior is deterministic ("last one wins"), as already codified by the project's own regression tests.

### Recommendation
- In `python/google/protobuf/json_format.py`, perform duplicate-key detection using the resolved `FieldDescriptor` (or the canonical/default `json_name`) as the key for the "already seen" set, mirroring the approach used by the C++/upb JSON parser (`SeenState` tracked on `*field`), rather than deduplicating on the literal JSON text.
- If a full fix is judged a breaking change (as noted by the existing TODO), at minimum surface a warning/strict-mode option so security-sensitive callers can opt into rejecting alternate-spelling duplicates.
- Audit other per-name string-based caches/dedup logic in the pure-Python implementation for the same class of "compare-before-normalize" gap.

### Proof of Concept
Using the pure-Python protobuf implementation (`api_implementation.Type() != 'upb'`):
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2 as pb2

msg = pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2          # both keys accepted; no duplicate-key error raised

msg2 = pb2.TestMap()
json_format.Parse('{"int32Map": {"1": 2}, "int32_map": {"3": 4}}', msg2)
assert dict(msg2.int32_map) == {3: 4}  # second spelling silently replaces the first map entirely
```
This exact reproduction is already codified upstream as `testDuplicateFieldAlternateNames` / `testDuplicateFieldAlternateNamesMap` in `python/google/protobuf/internal/json_format_test.py:1197-1217`, confirming the behavior is real, reproducible, and acknowledged (not merely theoretical). [4](#0-3)
