Based on my investigation, `associateAddresses` in `precompiles/addr/addr.go` only checks that the **Sei address** side isn't already associated — it never checks whether the target **EVM address** already has an existing `EVMAddressToSeiAddressKey` mapping to a *different* Sei address before calling `SetAddressMapping`, which unconditionally overwrites both directions of the mapping.

### Title
Missing check for pre-existing EVM→Sei mapping allows overwrite/orphaning of address association resource identifiers - (File: precompiles/addr/addr.go)

### Summary
`associateAddresses` (and its `AssociateAddresses`/`SetAddressMapping` call chain) validates only that the caller's Sei address has no prior EVM association, but does not verify that the target EVM address is not already mapped to a *different* Sei address before overwriting the store entries.

### Finding Description
`PrecompileExecutor.associateAddresses` [1](#0-0)  only guards against re-associating an already-associated `seiAddr`:
```go
_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
if found {
    return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
}
```
It never calls `GetSeiAddress(ctx, evmAddr)` to check whether `evmAddr` is already bound to some other Sei address. `AssociateAddresses` in `utils/helpers/associate.go` [2](#0-1)  then unconditionally calls `SetAddressMapping`, which blindly overwrites both `EVMAddressToSeiAddressKey(evmAddress)` and `SeiAddressToEVMAddressKey(seiAddress)` [3](#0-2) . If `evmAddr` was previously mapped from Sei address `A` (e.g., a real, pubkey-derived association) and the actual private-key holder of `evmAddr` later calls `associate`/`associatePubKey` from a fresh Sei address `B`, the store update rewrites `evmAddr -> B`, but `A`'s `SeiAddressToEVMAddressKey(A) -> evmAddr` stale entry is left untouched (not deleted). This creates an inconsistent, non-bijective identifier state: two Sei addresses (`A` and `B`) both hold a "true" claim on `evmAddr`, while the reverse map only reflects `B`. This mirrors the CVE's root cause (improper control of a resource identifier during a "creation"/binding handler, permitting collision/overwrite of an existing resource's identity).

The ante-handler comment at `x/evm/ante/preprocess.go` [4](#0-3)  confirms the project is aware of a related orphaning hazard for EIP-7702 delegated (cast) mappings and specifically patched that one path — but the general `associate`/`associatePubKey` precompile entrypoint still lacks a symmetric check on the EVM-address side.

### Impact Explanation
An inconsistent bidirectional mapping can desynchronize the usei/wei balance bridge and account state tied to `seiAddr`↔`evmAddr` resolution (`GetSeiAddressOrDefault`/`GetEVMAddressOrDefault`, `CanAddressReceive`) [5](#0-4) . Because `AssociateAddresses` also triggers `MigrateBalance`, which moves the cast-address's coins/wei to the new `seiAddr` and can `RemoveAccount` on the old cast address [6](#0-5) , a stale forward mapping (`A -> evmAddr`) combined with a new reverse mapping (`evmAddr -> B`) can misdirect fund routing/receivability checks for account `A`, and other subsystems (e.g. staking/distribution hooks referenced in the ante-handler comment) that key off the EVM/Sei mapping to resolve identity could act on an orphaned or duplicate identity, per the exact failure mode already documented as dangerous in the `preprocess.go` comment.

### Likelihood Explanation
Reaching the vulnerable path requires the caller to actually hold the private key for `evmAddr` (since `associate`/`associatePubKey` derive `evmAddr` from a valid signature/pubkey), so an attacker cannot hijack a victim's *real* keypair-controlled EVM address. However, this is still reachable in realistic scenarios: any address that received an implicit "cast"/default `evmAddr -> seiAddr` binding (e.g. through prior interaction, EIP-7702 delegation before the recent authority-preassociation patch, or any code path calling `SetAddressMapping` without symmetric validation) can be re-pointed by its true key-holder to a brand-new Sei address via the public `Associate`/`AssociatePubKey` precompile, an operation reachable by any unprivileged EOA.

### Recommendation
In `associateAddresses` (`precompiles/addr/addr.go`) and in `helpers.AssociationHelper.AssociateAddresses`, before calling `SetAddressMapping`, check `evmKeeper.GetSeiAddress(ctx, evmAddr)`; if it resolves to an existing Sei address different from `seiAddr`, either reject the association or explicitly clean up the stale reverse mapping (`DeleteAddressMapping` for the old pair) so that the store cannot hold two Sei addresses both claiming the same `evmAddr`.

### Proof of Concept
1. Get `evmAddr` bound to Sei address `A` via any codepath that only sets a one-sided/cast mapping for `evmAddr` (e.g., prior interaction establishing `EVMAddressToSeiAddressKey(evmAddr) -> A`, or via a pubkey-based `SetAddressMapping` call from another module) without full bijective enforcement.
2. As the holder of the private key for `evmAddr`, call the `addr` precompile's `associatePubKey(pubkeyBytesOf(evmAddr))` (or `associate` with a signed custom message) with a target Sei address `B` that has no existing EVM association.
3. `associateAddresses` passes its only check (`GetEVMAddress(ctx, B)` not found) and calls `SetAddressMapping(ctx, B, evmAddr)`, overwriting `EVMAddressToSeiAddressKey(evmAddr) -> B` while leaving `SeiAddressToEVMAddressKey(A) -> evmAddr` unchanged.
4. Query `getEvmAddr(A)` (still returns `evmAddr`) vs `getSeiAddr(evmAddr)` (now returns `B`) to observe the inconsistent, non-bijective mapping.

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}

func (k *Keeper) GetSeiAddress(ctx sdk.Context, evmAddress common.Address) (sdk.AccAddress, bool) {
	store := ctx.KVStore(k.storeKey)
	bz := store.Get(types.EVMAddressToSeiAddressKey(evmAddress))
	if bz == nil {
		return []byte{}, false
	}
	return bz, true
}

func (k *Keeper) IterateSeiAddressMapping(ctx sdk.Context, cb func(evmAddr common.Address, seiAddr sdk.AccAddress) bool) {
	iter := prefix.NewStore(ctx.KVStore(k.storeKey), types.EVMAddressToSeiAddressKeyPrefix).Iterator(nil, nil)
	defer func() { _ = iter.Close() }()
	for ; iter.Valid(); iter.Next() {
		evmAddr := common.BytesToAddress(iter.Key())
		seiAddr := sdk.AccAddress(iter.Value())
		if cb(evmAddr, seiAddr) {
			break
		}
	}
}

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}
