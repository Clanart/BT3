Based on my investigation, the strongest local analog to the external report is a **metadata/bytecode verification gap in the Aptos package-publishing and `aptos move verify-package` flow**: the on-chain `code::publish_package` function never checks that a module's declared source metadata corresponds to its actual bytecode, and the CLI's package `verify()` routine only diffs `PackageMetadata` structs — never the actual deployed bytecode — against a locally built package.

### Title
Package `source`/`manifest` metadata is never bound to actual published bytecode, allowing "verified" packages to run different code than their displayed source - (File: aptos-move/framework/aptos-framework/sources/code.move, aptos-move/cli/src/stored_package.rs)

### Summary
`code::publish_package` [1](#0-0)  and the VM-side `validate_publish_request` [2](#0-1)  only verify that the *module name* declared in `PackageMetadata.modules[i].name` matches the self-name of the i-th `CompiledModule` in the bundle. They never verify that `ModuleMetadata.source` (the gzipped Move source shown by explorers/verification tools) or `PackageMetadata.manifest`/`source_digest` actually correspond to the bytecode bundle (`code: vector<vector<u8>>`) being published, since `metadata_serialized` and `code` are two entirely independent transaction arguments [3](#0-2) .

The CLI-side `verify()` used for source verification of a deployed package compounds this: it compares only `PackageMetadata` struct fields (`name`, `deps`, `modules`, `manifest`, `upgrade_policy`, `extension`, `source_digest`) between the locally-built metadata and the on-chain metadata fetched from `PackageRegistry` — it never diffs the actual deployed `.mv` bytecode against bytecode compiled from the local source [4](#0-3) . `CachedPackageRegistry` does have the capability to fetch actual on-chain bytecode via `get_bytecode`/`with_bytecode` [5](#0-4) , but this bytecode is not used inside `verify()`, which only operates on `CachedPackageMetadata` (a struct holding just the `&PackageMetadata`, with no bytecode reference) [6](#0-5) .

### Finding Description
- `source_digest`, `manifest`, and each `ModuleMetadata.source` are self-reported, base64/gzip-encoded blobs supplied by the publisher's client tooling; nothing on-chain hashes or binds them to the compiled bytecode bytes.
- On-chain publish validation (`validate_publish_request`) checks only `m.self_id().name()` against `expected_modules` (derived from `pack.modules[i].name`) and dependency-address/name pairs against `allowed_deps` [7](#0-6) . Byte-level content of `ModuleMetadata.source` is never inspected against the actual `CompiledModule` bytes.
- The CLI verification path (`CachedPackageMetadata::verify`) is a pure struct-equality check between two `PackageMetadata` values; it has no access to bytecode at all in its own signature, so it structurally cannot detect a package whose declared source metadata differs from what was actually compiled into the deployed module.
- As a result, a publisher can submit a `PackageMetadata` whose `modules[i].source`/`manifest` describe innocuous, human-reviewable Move source, while the accompanying `code` bundle contains different, functionally divergent bytecode compiled from other source (or hand-crafted bytecode) — as long as module *names* match. Both the protocol's publish path and the CLI's "verify-package" workflow will accept this as a legitimate, verified publication.

### Impact Explanation
Block explorers, auditors, and the `aptos move verify-package` workflow rely on `PackageMetadata.modules[*].source` and `verify()` to assert "this on-chain module was compiled from this reviewed source." Because neither the protocol nor the CLI ties source metadata to the actual bytecode, this assurance is false: a malicious or careless publisher (including via resource-account or object-code-deployment flows that build trust via metadata, e.g. `resource_account::create_resource_account_and_publish_package` [8](#0-7)  and `object_code_deployment::publish`/`upgrade` [9](#0-8) ) can present benign, security-reviewed-looking source for a module while executing arbitrary different logic. This directly matches the allowed "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" impact category, since downstream consumers of the metadata (wallets, explorers, security reviewers, the official CLI verify command) make trust decisions based on data the protocol never actually authenticates against the code that runs.

### Likelihood Explanation
The gap is exercised by any account publishing a package (`code::publish_package_txn`, resource-account publish, or object-code-deployment publish/upgrade) — all permissionless flows on mainnet. No special privilege is required; the only requirement is being able to submit two independent byte arrays (`metadata_serialized`, `code`) that are never cross-checked beyond the module name. I was not able to fully confirm within the available tool budget whether the `VerifyPackage` CLI command (in `aptos-move/cli/src/commands.rs`) performs an additional raw bytecode diff outside of the `verify()` function shown here using `CachedPackageRegistry::get_bytecode`; this remains an open question that should be checked against the actual command implementation before treating the CLI-side gap as fully confirmed. The on-chain gap (no binding between `ModuleMetadata.source`/`manifest` and actual bytecode) is confirmed directly from `code.move` and `aptos_vm.rs`.

### Recommendation
- Require the publisher-supplied `source_digest` to be computed and checked on-chain (or at minimum, verified by the CLI) as a genuine hash of the compiled bytecode bundle (or of a canonical recompilation of `modules[*].source`), not an arbitrary trusted string.
- Extend `CachedPackageMetadata::verify` (or the CLI command that calls it) to fetch actual on-chain module bytecode via `CachedPackageRegistry::get_bytecode` and compare it byte-for-byte against bytecode recompiled from the local/verified source before reporting success.
- Consider recording a bytecode hash per module inside `PackageRegistry` at publish time and exposing it for independent verification, closing the gap between "displayed source" and "executing code."

### Proof of Concept
1. Build a benign Move package locally (e.g., a simple transfer module) and extract its `PackageMetadata` via `BuiltPackage::extract_metadata()`.
2. Separately compile a different, malicious module with the same module name (e.g., one that drains resources on `init_module`), and take its `code` bytes.
3. Submit `code_publish_package_txn(bcs::to_bytes(&benign_metadata), vec![malicious_code_bytes])` (via `aptos_stdlib::code_publish_package_txn` [10](#0-9) , or through `resource_account_create_resource_account_and_publish_package`/`object_code_deployment::publish`).
4. `validate_publish_request` only checks that the malicious module's self-name matches `benign_metadata.modules[0].name` — it succeeds. `PackageRegistry` now stores `benign_metadata` (with benign `source`) at the address, while the actually loaded/executing bytecode is the malicious one.
5. Running `aptos move verify-package` against this address with the benign local source will invoke `CachedPackageMetadata::verify`, which compares the on-chain `PackageMetadata` (benign) to the locally-built benign `PackageMetadata` — reporting success, even though the deployed bytecode is malicious.

    /// Publishes a package at the given signer's address. The caller must provide package metadata describing the

    public fun publish_package(owner: &signer, pack: PackageMetadata, code: vector<vector<u8>>) acquires PackageRegistry {
        // Disallow incompatible upgrade mode. Governance can decide later if this should be reconsidered.
        assert!(
            pack.upgrade_policy.policy > upgrade_policy_arbitrary().policy,
            error::invalid_argument(EINCOMPATIBLE_POLICY_DISABLED),
        );

        let addr = signer::address_of(owner);
        if (!exists<PackageRegistry>(addr)) {
            move_to(owner, PackageRegistry { packages: vector::empty() })
        };

        // Checks for valid dependencies to other packages
        let allowed_deps = check_dependencies(addr, &pack);

        // Check package against conflicts
        // To avoid prover compiler error on spec
        // the package need to be an immutable variable
        let module_names = get_module_names(&pack);

        // Record, per module in this package, the object's transitive root owner at (re)publish, so
        // lazy self-init can detect a later transfer of the object or an ancestor since that module
        // was published (see `init::internal_maybe_initialize`). Objects only; feature-gated.
        if (features::is_lazy_module_initialization_enabled() && object::is_object(addr)) {
            let owner = object::address_to_object<object::ObjectCore>(addr).root_owner();
            module_names.for_each_ref(|name| {
                init::record_deploy_owner(addr, *name.bytes(), owner);
            });
        };
        let package_immutable = &borrow_global<PackageRegistry>(addr).packages;
        let len = package_immutable.length();
        let index = len;
        let upgrade_number = 0;
        package_immutable.enumerate_ref(|i, old| {
            let old: &PackageMetadata = old;
            if (old.name == pack.name) {
                upgrade_number = old.upgrade_number + 1;
                check_upgradability(old, &pack, &module_names);
                index = i;
            } else {
                check_coexistence(old, &module_names)
            };
        });

        // Assign the upgrade counter.
        pack.upgrade_number = upgrade_number;

        let packages = &mut borrow_global_mut<PackageRegistry>(addr).packages;
        // Update registry
        let policy = pack.upgrade_policy;
        if (index < len) {
            pack.modules.for_each_ref(|m| {
                let m: &ModuleMetadata = m;
                init::reset_initialized(addr, *m.name.bytes());
            });
            *packages.borrow_mut(index) = pack
        } else {
            packages.push_back(pack)
        };

        event::emit(PublishPackage {
            code_address: addr,
            is_upgrade: upgrade_number > 0
        });

        // Request publish
        if (features::code_dependency_check_enabled())
            request_publish_with_allowed_deps(addr, module_names, allowed_deps, code, policy.policy)
        else
        // The new `request_publish_with_allowed_deps` has not yet rolled out, so call downwards
        // compatible code.
            request_publish(addr, module_names, code, policy.policy)
    }

                self_metadata.modules

            bail!(
                "Manifest doesn't match {:?} : {:?}",

                self_metadata.manifest

        publisher: &signer,
        metadata_serialized: vector<u8>,

        });

    inline fun object_seed(publisher: address): vector<u8> {
        let sequence_number = account::get_sequence_number(publisher) + 1;
        let seeds = vector[];
        seeds.append(bcs::to_bytes(&OBJECT_CODE_DEPLOYMENT_DOMAIN_SEPARATOR));
        seeds.append(bcs::to_bytes(&sequence_number));
        seeds
    }
