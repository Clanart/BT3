### Title
Unbounded recursive `MofN` memo parsing causes stack-overflow DoS during PlotNFT wallet sync - (File: `chia/wallet/puzzles/custody/custody_architecture.py`)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs `MofN` custody structures from an on-chain coin's memo with no depth or size bound. This function is invoked automatically by `PlotNFT.get_next_from_coin_spend()` whenever a wallet or pool participant syncs a singleton coin whose custody puzzle cannot be matched by prior state, and any peer/attacker who can create a coin (including anyone farming a plotnft-shaped singleton chain or crafting an arbitrary coin with a `CHIP-0043` memo format) fully controls the nesting depth of that memo. This mirrors the ALPINE-CVE-2024-31228 bug class: attacker-controlled, unbounded-depth input driving unbounded Python recursion in a parser reachable from a normal, unprivileged protocol path, causing a stack overflow / crash (DoS) rather than a memory-safety exploit.

### Finding Description
`PuzzleWithRestrictions.from_memo()` recurses into itself for every `MofN` member when `further_branching` is true, with no limit on nesting depth: [1](#0-0) 

Each recursive call reads more fields from the attacker-supplied `Program` memo (`memo.at("rf")`, `.at("rrf")`, etc.) and constructs another `MofN`/`PuzzleWithRestrictions` layer. Nothing bounds `len(m_of_n_hint.member_memos)` recursion depth, the total memo size, or CLVM cost — this is a pure Python-object parse that happens *after* CLVM execution and outside any cost-metered CLVM runtime, so the normal CLVM cost limits that would otherwise bound recursion (see `chia/types/blockchain_format/tree_hash.py`'s deliberately iterative design, and `sha256_treehash()`'s non-recursive implementation specifically written "so we don't have to worry about blowing out the python stack") do not apply here.

This function is reached from a fully unprivileged path: `PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` whenever it cannot recognize the singleton's inner puzzle transition from prior wallet state (e.g., a brand-new singleton, a reorg, or any as-yet-unseen custody shape): [2](#0-1) 

`get_next_from_coin_spend()` is invoked directly during normal wallet sync via `PlotNFT2Wallet.identify()`, which every wallet processing PlotNFT-shaped singleton spends calls automatically: [3](#0-2) 

An attacker only needs to submit a spend bundle that creates a singleton-shaped coin with a `CREATE_COIN` memo containing a deeply nested `("CHIP-0043", [nonce, restrictions, 1, (m, [deeply-nested-member-memos...])])` structure. Because `MofN.from_program`/`from_memo` recurse per nesting level with no cap, sufficiently deep nesting (thousands of levels, trivially cheap to construct since the memo is just nested CLVM pairs) will exhaust the Python call stack and raise `RecursionError`, crashing/hanging the wallet or pool-participant process that attempts to sync it.

### Impact Explanation
This is a spend-triggered transaction-processing halt: any wallet, pool participant, or plotnft-tracking client that observes and attempts to sync a maliciously crafted coin's spend will crash with an unhandled `RecursionError` (the `try/except` in `get_next_from_coin_spend()` and `identify()` only catches `ValueError`/`GetNextPlotNFTError`, not `RecursionError`). This denies service to legitimate wallet/pool operations and can be triggered remotely by anyone able to broadcast a spend bundle, without requiring the victim to own the coin.

### Likelihood Explanation
Likelihood is high for any wallet that tracks or scans plotnft/pool singleton lineage, since `identify()`/`get_next_from_coin_spend()` runs automatically on relevant coin spends during normal sync with no attacker cooperation needed beyond broadcasting one transaction. Constructing the deeply-nested memo requires no special privilege — it is just nested CLVM data attached to any `CREATE_COIN` condition.

### Recommendation
Add an explicit recursion-depth (and/or memo-size) limit to `PuzzleWithRestrictions.from_memo()`/`MofN.from_program()` and raise a caught `ValueError`/`GetNextPlotNFTError` when exceeded, mirroring the deliberate non-recursive design already used for `sha256_treehash()`. Alternatively, convert the recursive parse into an iterative work-stack traversal, and ensure callers (`get_next_from_coin_spend()`, `PlotNFT2Wallet.identify()`) treat `RecursionError`/`ValueError` uniformly as "invalid/untrusted memoization" rather than allowing an unhandled exception to propagate and crash the sync loop.

### Proof of Concept
1. Construct a nested memo program: start with a leaf `MemberHint` memo, then repeatedly wrap it in `MofNHint(m=1, member_memos=[prev]).to_program()` combined with a `PuzzleWithRestrictions` wrapper thousands of levels deep (each level only costs a few CLVM cons cells, well under any per-spend cost limit).
2. Submit a spend bundle whose `CREATE_COIN` condition sets this nested `Program` as the coin's memo (`memo_blob`), targeting a singleton puzzle hash recognized by `cls.singleton_puzzles.singleton_mod`.
3. Any wallet/pool client that subsequently calls `PlotNFT.get_next_from_coin_spend()` (via `PlotNFT2Wallet.identify()` during normal sync) on this coin's spend triggers `PuzzleWithRestrictions.from_memo()`, which recurses once per nesting level and raises an unhandled `RecursionError`, crashing that wallet sync/process.
