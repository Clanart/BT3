## Title
Wallet `Offer` parsing runs untrusted counterparty CLVM inner puzzles with `INFINITE_COST`, allowing a malicious offer to hang or crash the wallet process before the offer is even accepted - (File: `chia/wallet/trading/offer.py`)

### Summary
Chia's `Offer` class exposes `_get_offered_coins()`, which is used to identify which coins in a received (and not-yet-accepted) offer correspond to the assets being offered. For every coin spend in the untrusted counterparty's offer bundle, it runs the spend's *inner puzzle* with `cost_left = INFINITE_COST`, i.e. with no cost bound at all, rather than the bounded `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM` used everywhere else in this same class (`__post_init__`, `conditions()`). [1](#0-0) 

### Finding Description
This is the CLVM-cost analog of the reported issue: an external/untrusted callee (here, a counterparty-supplied inner puzzle inside an `Offer`) is executed without any resource limit, so it can consume unbounded local computation and block legitimate wallet functionality that depends on it.

- `Offer.__post_init__()` and `Offer.conditions()` correctly bound every CLVM run to `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, decrementing a running `max_cost` budget and raising `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)` when exceeded. [2](#0-1) [3](#0-2) 
- `_get_offered_coins()`, by contrast, initializes `cost_left = INFINITE_COST` and calls `inner_puzzle.run_with_cost(cost_left, inner_solution)` for the untrusted counterparty's inner puzzle with no upper bound, only decrementing `cost_left` after the run completes. [4](#0-3) 
- `INFINITE_COST` is imported directly from `chia.types.blockchain_format.program`, and `Program.run_with_cost()` simply forwards the `max_cost` argument straight into `run_chia_program`, which enforces cost as a hard ceiling — but only if a finite one is provided. [5](#0-4) 

Because a wallet user (or a Data-Layer/offer-file consumer) parses/reviews an `Offer` object (e.g. via CLI/RPC "examine offer" or trade-manager summary flows) before deciding whether to accept it, an attacker can craft an offer whose inner puzzle is a computationally expensive-but-otherwise-cheap-looking CLVM program (e.g. deep recursion or large loops as demonstrated by the `deep_recursion`/`create_coins_loop` test puzzles used elsewhere in this codebase to exercise cost limits) that takes an extremely long time or huge memory to execute under `INFINITE_COST`. Since the CLVM interpreter is otherwise always metered by a finite `max_cost` in every other production code path in this file and in mempool/block validation, this is the sole place shown where an untrusted, attacker-controlled program is run with no bound at all. [6](#0-5) 

### Impact Explanation
A malicious offer counterparty can submit an offer file that, when merely inspected/summarized by a victim wallet (calling code that reaches `_get_offered_coins()`), causes the wallet's single-threaded process to spend unbounded CPU/memory executing the attacker's inner puzzle. This can hang or crash the wallet process, blocking all other wallet functionality (balance checks, other transaction processing, other trade handling) for as long as the runaway computation continues — directly analogous to the reported "staticcall consumes all gas, blocking other functionality" bug class, except here the unmetered resource is CLVM cost/CPU instead of EVM gas. This qualifies as a spend/action-triggered transaction-processing halt reachable by an unauthorized offer counterparty.

### Likelihood Explanation
Likelihood is high for any user who opens/reviews offer files from untrusted sources, which is the normal offer workflow (offers are shared out-of-band and inspected before acceptance). No signature or on-chain broadcast is required to trigger the DoS — it happens purely from local parsing/summarization of the offer object using `_get_offered_coins()`.

### Recommendation
Bound the inner-puzzle execution in `_get_offered_coins()` with the same finite cost budget used elsewhere in `Offer` (e.g. `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, decremented per spend as in `__post_init__`/`conditions()`), and treat cost-exceeded as a `ValidationError` rather than allowing an unmetered `INFINITE_COST` run of untrusted CLVM.

### Proof of Concept
1. Construct a `WalletSpendBundle` whose `coin_spends` include one spend where the *inner puzzle* recognized by `match_puzzle`/`get_inner_puzzle` (e.g. under a CAT/singleton outer layer) is a computationally expensive CLVM program (structurally similar to the `deep_recursion`/`create_coins_loop` test puzzles that other tests use specifically to exercise cost limits, but here run with `INFINITE_COST`). [6](#0-5) 
2. Wrap this bundle into an `Offer` (`driver_dict` populated so `match_puzzle` recognizes an outer layer, as in `Offer.from_spend_bundle`). [7](#0-6) 
3. Have the victim call any code path that invokes `Offer._get_offered_coins()` (offer summary/additions inspection) — this executes `inner_puzzle.run_with_cost(INFINITE_COST, inner_solution)` with no cost ceiling. [8](#0-7) 
4. Observe the wallet process hang/consume excessive resources while evaluating the malicious inner puzzle, blocking further wallet operations, in contrast to `__post_init__`/`conditions()` in the same file which bound cost and fail cleanly with `Err.BLOCK_COST_EXCEEDS_MAX`.
