### Title
Sub-dust deposits are reported as received yet can never be economically spent, permanently burning user funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report concerns a user-supplied gas parameter (`l2Gas`) that, if underpaid, makes the L2-side `finalizeDeposit` fail while the L1 deposit already locked funds — funds are moved into a state where they can never be claimed. The Serai analog: `Scanner::scan_transaction` / `scan_block` accept outputs of any value, including outputs below the dust/economic-spendability threshold. A depositor can send an arbitrarily small amount to a scanned script; the output is reported as received, yet spending it costs more in fees than it is worth (or fails `SignableTransaction`'s funding checks entirely), so the credited funds are effectively burned.

### Finding Description
`Scanner::scan_transaction` iterates every `tx.output` and returns a `ReceivedOutput` whenever `output.script_pubkey` matches a registered script, with no check on `output.value` [1](#0-0) .

The spend side, `SignableTransaction::new`, requires `input_sat >= payment_sat + needed_fee` and rejects payments below `DUST` (546 sats) [2](#0-1) . A Taproot input costs ~57 vbytes to spend (230 WU: outpoint + sequence + 64-byte witness signature), and the processor itself requires outputs be spendable under a 5000 sat/kvB rate, deriving `DUST = 10_000` [3](#0-2) .

Consequences split into two cases for a deposit of `v` sats:

- `v < ~285` sats (input cost at minimum relay fee): the output can never be included without the fee exceeding its value; it is permanently unspendable, yet `scan_transaction` still reports it as received.
- `v` between that and `DUST = 10_000`: `SignableTransaction::new` returns `NotEnoughFunds`/`DustPayment` for any payment, and the processor maps these to `Ok(None)` — i.e., "no transaction", not an error worth surfacing [4](#0-3) . The deposit is credited but can never fund a payment, and there is no aggregation path that can economically combine it.

This mirrors the LiFi bug exactly: a user-controlled parameter (here the output value; there `l2Gas`) that, if too low, moves funds into a state where the completion step is impossible, with the loss only discoverable after the fact.

### Impact Explanation
Any unprivileged Bitcoin user can send a dust-value output to a Serai-controlled P2TR script. The scanner reports it as a `ReceivedOutput` and, in the processor flow, the deposit is credited. Because every downstream spend path either rejects it as dust or cannot cover its own input fee, the value is permanently locked — funds reported received that are not spendable.

### Likelihood Explanation
Requires only that a user send a standard Bitcoin transaction paying to the group's address with an amount below ~10,000 sats. No validator collusion, malformed encodings, or special access is needed; dust deposits occur naturally through user error or fee miscalculation, analogous to underpaying `l2Gas`.

### Recommendation
Filter outputs by a minimum spendable value in `Scanner::scan_transaction`/`scan_block` (e.g., ignore `output.value < DUST`), or explicitly track and refund/aggregate sub-threshold outputs rather than crediting them. Alternatively, treat `ReceivedOutput`s below the threshold as a distinct "unspendable" class so they are not credited.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }

  /*
    A Taproot input is:
    - 36 bytes for the OutPoint
    - 0 bytes for the script (+1 byte for the length)
    - 4 bytes for the sequence
    Per https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format

    There's also:
    - 1 byte for the witness length
    - 1 byte for the signature length
    - 64 bytes for the signature
    which have the SegWit discount.

    (4 * (36 + 1 + 4)) + (1 + 1 + 64) = 164 + 66 = 230 weight units
    230 ceil div 4 = 57 vbytes

    Bitcoin defines multiple minimum feerate constants *per kilo-vbyte*. Currently, these are:
    - 1000 sat/kilo-vbyte for a transaction to be relayed
    - Each output's value must exceed the fee of the TX spending it at 3000 sat/kilo-vbyte
    The DUST constant needs to be determined by the latter.
    Since these are solely relay rules, and may be raised, we require all outputs be spendable
    under a 5000 sat/kilo-vbyte fee rate.

    5000 sat/kilo-vbyte = 5 sat/vbyte
    5 * 57 = 285 sats/spent-output

    Even if an output took 100 bytes (it should be just ~29-43), taking 400 weight units, adding
    100 vbytes, tripling the transaction size, then the sats/tx would be < 1000.

    Increase by an order of magnitude, in order to ensure this is actually worth our time, and we
    get 10,000 satoshis.
  */
  const DUST: u64 = 10_000;
