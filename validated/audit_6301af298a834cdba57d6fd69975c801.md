## Finding

### Title
Re-enabling `protocol.file.allow=always` for submodule updates reintroduces the local-file-disclosure submodule vulnerability (CVE-2022-39253 class) - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` flag that, when true, prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. This flag overrides Git's own hardened default (`protocol.file.allow=user`, the fix shipped for the "local clone" submodule disclosure class, e.g. CVE-2022-39253) and lets a `file://` URL declared in an attacker-controlled `.gitmodules` be honored during a recursive submodule update. [1](#0-0) 

### Finding Description
`git submodule update --init --recursive` reads submodule URLs from `.gitmodules`, a file fully controlled by whoever authored the repository/commit being fetched — i.e., an attacker who controls a cloned or fetched repository. Upstream Git deliberately restricts `file://` submodule URLs by default (`protocol.file.allow=user`) precisely because a malicious `.gitmodules` entry like `url = file:///some/local/path` can make Git "clone" an arbitrary local directory on the victim's machine into the submodule path, copying its contents into the working tree. GitHub Desktop's `updateSubmodulesAfterOperation` explicitly re-arms this disabled protocol via `-c protocol.file.allow=always` whenever it is invoked with `allowFileProtocol: true`: [2](#0-1) 

Because the flag is a boolean parameter threaded in by the caller rather than something derived from validating the actual submodule URLs, any call site that opts in (`allowFileProtocol: true`) unconditionally weakens the `protocol.file.allow` guard for the *entire* recursive submodule update — including submodules whose URLs come straight out of the attacker-supplied `.gitmodules`, not just the one the caller intended to permit.

### Impact Explanation
If reachable with attacker-controlled `.gitmodules` content, this allows an attacker who merely gets the victim to clone/fetch/checkout a crafted repository (no local access, no admin rights, no leaked credentials) to have Desktop copy arbitrary local file-system paths into the repository working directory as a "submodule". That corrupts the user's working tree with exfiltrated local content and, if the user is not careful, that content can be staged/committed/pushed — silently corrupting what the user commits, or disclosing local file contents to whoever reviews/receives the push. This matches the same "broken invariant" pattern as the original report: a supposedly narrow, purpose-scoped exception (minting for `strategy` / `file://` for a specific known case) is applied without a constraint tying it to the legitimate case, letting an untrusted input control the outcome.

### Likelihood Explanation
The severity depends entirely on how `allowFileProtocol: true` is passed by callers of `updateSubmodulesAfterOperation`. I was not able to fully trace, within the remaining tool budget, every call site that sets `allowFileProtocol: true` (e.g., checkout, pull, clone flows) to confirm whether Desktop scopes this to a specific known-safe submodule URL or applies it globally to the recursive update regardless of the `.gitmodules` contents. This is the key open question that determines whether the path is trivially triggerable by a hostile clone/fetch or is otherwise constrained (e.g., only enabled for local test fixtures, or gated behind a check that no submodule uses `file://` unexpectedly). Given the function signature and the `-c` flag placement shown above, the guard as written applies to the whole `submodule update --recursive` command, not to a single vetted URL, which is the concerning part.

### Recommendation
- Do not use a blanket `allowFileProtocol` boolean that flips `protocol.file.allow` for the whole recursive submodule update. Instead, validate each individual submodule URL from `.gitmodules` and only allow `file://` for URLs that are already known/trusted (e.g., pointing within the already-cloned repository's own object store), rejecting or warning on unexpected `file://` submodule URLs from third-party content.
- If `allowFileProtocol` exists to support a specific legitimate scenario, scope the override with `git -c protocol.file.allow=always submodule update -- <specific-path>` rather than applying it recursively to all submodules.
- Audit all call sites of `updateSubmodulesAfterOperation` to confirm none pass `allowFileProtocol: true` on a code path that processes an untrusted/attacker-supplied repository.

### Proof of Concept
1. Attacker publishes/forks a repository containing a `.gitmodules` entry:
   ```
   [submodule "evil"]
       path = evil
       url = file:///Users/victim/Documents/SensitiveFolder
   ```
2. Victim opens/clones/fetches this repository in GitHub Desktop and triggers a code path that calls `updateSubmodulesAfterOperation(..., allowFileProtocol: true)`.
3. Desktop runs `git -c protocol.file.allow=always submodule update --init --recursive`, and Git "clones" `/Users/victim/Documents/SensitiveFolder` into `evil/` inside the repository working tree — despite Git's own default hardening (`protocol.file.allow=user`) being designed to prevent exactly this.
4. The victim's local files are now embedded in the repository working directory and may be staged, committed, or pushed without the victim realizing the content originated from outside the repository. [3](#0-2)
