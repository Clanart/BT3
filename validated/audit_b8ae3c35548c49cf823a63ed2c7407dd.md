### Title
Stale `safe.directory` trust grant persists after repository identity changes, enabling silent execution of untrusted repository content - ([File: app/src/lib/git/config.ts])

### Summary
The double-voting report's broken invariant is: a security decision (voting eligibility) is bound to a *fungible* credential (token balance) rather than the *identity* of the resource being decided about, so once the credential moves to a new principal the stale decision is replayed. GitHub Desktop has the same class of bug in its "unsafe repository" trust flow: trust is granted permanently to a filesystem **path** via Git's `safe.directory` global config, but Desktop never re-validates that the repository *at that path* is still the same repository the user originally trusted.

### Finding Description
When Desktop encounters a repository owned by a different user (a classic multi-user-machine or synced-folder attack vector), `getRepositoryType()` returns `{ kind: 'unsafe', path }` [1](#0-0) . The UI then offers a "Trust Repository" action which calls `addSafeDirectory(path)`, permanently appending the path to the global `safe.directory` git config [2](#0-1) . This is invoked from both `AddExistingRepository.onTrustDirectory` [3](#0-2)  and `MissingRepository.onTrustDirectory` [4](#0-3) .

Once trusted, that path is trusted *forever*, for *any* content that later occupies it — Git's `safe.directory` mechanism keys on path only, and Desktop's own repository tracking in `matchExistingRepository` also keys purely on normalized path equality [5](#0-4) , with no binary/commit/remote-identity check. Nothing in `getRepositoryType`, `_refreshRepository`, or `recoverMissingRepository` re-verifies that the repository found at a previously-trusted path is the same repository (same `.git` origin, same initial commit, same remote) as when trust was granted [6](#0-5) .

This mirrors the guild double-voting flaw precisely: `lockTime` (trust) is bound to a token balance/path rather than a specific proposal/repository identity; once the underlying content is swapped (tokens transferred / directory contents replaced), the previously-approved authorization is silently replayed against a completely different object, because the guard (`lockTime >= proposalTime` / an "unsafe" check) only fires once, at first encounter.

### Impact Explanation
An attacker who can write to a path Desktop has previously been trusted for (e.g. a shared machine, a synced network/cloud folder, or a path a previous legitimate different-owner repo occupied and was later removed and replaced) can drop a malicious repository containing crafted hooks, `.gitattributes` filters, or build/config files at that exact path. Because `safe.directory` already lists the path, Git and Desktop will operate on the new, attacker-controlled repository without ever re-prompting the "this repository is owned by another user, files may be automatically executed" warning shown in `MissingRepository`/`AddExistingRepository` [7](#0-6) . This can lead to code execution via Git hooks or filter/clean/smudge configs that Desktop or Git will run without the user seeing any indication the repository's ownership/content changed.

### Likelihood Explanation
Requires the attacker to control a path a user previously trusted (common on shared/multi-user machines, or via network shares / removable media Desktop users commonly clone to), and does not require the local attacker to be an admin — only write access to that filesystem location, which is the exact scenario the original "unsafe repository" warning exists to defend against. This satisfies "attacker controls a cloned/fetched repository" while bypassing the intended one-time consent gate because the check-then-trust decision is not re-validated against changed repository identity.

### Recommendation
Bind the `safe.directory` trust decision (and Desktop's internal repository record) to a stable identity marker in addition to path — e.g., verify the `.git` directory's inode/creation time, initial commit hash, or remote URL match what was present when trust was granted, and re-prompt the "Trust Repository" warning if the underlying repository content at a previously-trusted path has changed. At minimum, `updateUnsafePathState`/`validatePath` flows should not silently skip the warning for a path Git already considers "safe" without confirming the repo is the one previously reviewed.

### Proof of Concept
1. On a shared or synced machine, User A clones/creates repo R1 at `/shared/proj`, is warned it's "unsafe" (different owner), and clicks "Trust Repository" → `addSafeDirectory('/shared/proj')` is called, adding the path to global `safe.directory`.
2. Repo R1 is later removed from `/shared/proj` (e.g. user removes it from Desktop, or it's deleted).
3. Attacker (or another process with write access to that path) places a different, malicious repository R2 at `/shared/proj`, containing a malicious `core.hooksPath` config or post-checkout hook.
4. User re-adds `/shared/proj` in Desktop via `AddExistingRepository` or Desktop reopens it via `MissingRepository`'s "Check again" flow. `getRepositoryType('/shared/proj')` now succeeds as `'regular'` (not `'unsafe'`) because `safe.directory` already whitelists the path — the ownership-mismatch warning never fires again, even though the content is entirely different from what was originally reviewed and trusted [8](#0-7) .
5. Desktop proceeds to run Git operations (fetch/checkout/status) against R2 without any unsafe-repository prompt, executing attacker-controlled hooks/config.

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }

export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

export function matchExistingRepository<T extends { readonly path: string }>(
  repos: ReadonlyArray<T>,
  path: string
): T | undefined {
  // Windows is guaranteed to be case-insensitive so we can be a bit less strict
  const normalize = __WIN32__
    ? (p: string) => Path.normalize(p).toLowerCase()
    : (p: string) => Path.normalize(p)

  const needle = normalize(path)
  return repos.find(r => normalize(r.path) === needle)
}
