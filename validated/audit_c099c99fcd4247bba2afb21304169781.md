### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub Enterprise identity, auto-triggering the OAuth/PAT sign-in flow against an arbitrary remote host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's git credential trampoline classifies a remote endpoint as GitHub-flavored (`'enterprise'`) based on an unauthenticated `WWW-Authenticate` header value that Git forwards from the remote server's HTTP response, with no verification against the actual host. This is directly analogous to the Fluid report's root cause: a security-relevant classification (there, LP composition/penalty; here, "is this a trusted GitHub host") is derived from a permissionless, attacker-controlled input (there, DexV2 spot price; here, an HTTP response header from a remote/proxy) instead of from a verified source, and that classification drives a sensitive downstream action (there, collateral seizure amount; here, launching the GitHub sign-in/OAuth flow).

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts:137-179` determines how the credential helper should treat a remote endpoint. After checking known first-party hosts (`isGist`, `isDotCom`, `isGHE`), it falls back to inspecting `wwwauth[...]` entries that were forwarded from the credential map: [1](#0-0) 

The comment itself acknowledges this is a "happy path" substitute for verification: *"We use them as a happy-path to determine if the host is a GitHub host without having to resort to making a request ourselves."* The `wwwauth[]` value originates from the HTTP response of whatever server the git operation is talking to — this is fully attacker-controlled when the remote is a malicious/compromised repository host or a MITM/malicious proxy sitting on the network path (e.g. a corporate/public proxy, or a server the user was pointed at via a crafted remote URL or `x-github-client`/deep-link "clone" flow). By simply returning a `401` with `WWW-Authenticate: Basic realm="GitHub"`, any such server causes `getEndpointKind` to classify itself as `'enterprise'` regardless of hostname.

This classification is consumed in `getCredential` (`trampoline-credential-helper.ts:94-135`): [2](#0-1) 

If no account already exists for that endpoint, the app calls `ui.promptForGitHubSignIn(endpoint)` — automatically, without any git-operation-specific user consent beyond having initiated a clone/fetch/push against that remote. `promptForGitHubSignIn` (`app/src/lib/trampoline/trampoline-ui-helper.ts:80-104`) then opens the real sign-in popup (`PopupType.SignIn`) and, for non-`github.com` hostnames, calls `dispatcher.beginEnterpriseSignIn` and `dispatcher.setSignInEndpoint(origin)` using the attacker's own origin — i.e., the "Enterprise" sign-in target is the attacker's server.

The credential-lookup/storage boundary itself (`findGitHubTrampolineAccount` in `app/src/lib/trampoline/find-account.ts:20-29`) does correctly scope by `origin`, so an *existing* GitHub.com/enterprise token is not directly leaked to a mismatched origin. The exploitable primitive is upstream of that: the trigger and framing of the sign-in UI is decided by unverified, remote-supplied header content, not by a verified property of the host.

### Impact Explanation
When a user clones/fetches/pushes against a repository controlled by an attacker (or an attacker sits as a proxy on the connection), the attacker can force GitHub Desktop to present its official-looking "Sign in to GitHub Enterprise" flow for the attacker's own domain, entirely unprompted by the user beyond the normal git operation. Because the resulting OAuth/PAT flow is bound to `setSignInEndpoint(origin)` = the attacker's origin, any token or PAT the user enters in that flow is submitted to the attacker's server, and if OAuth device/browser flow is used, the resulting account object could be persisted and associated with the attacker endpoint in the accounts store. This matches the allowed impact class "unauthorized OAuth or account binding" / credential exfiltration via a git remote response, without requiring local access, admin rights, or pre-existing malware.

### Likelihood Explanation
This requires an attacker to control (or MITM) the remote HTTP endpoint the user is fetching/pushing/cloning against — the exact class of attacker Desktop already treats as untrusted (git remote/proxy response), and setting a spoofed `WWW-Authenticate` header on a `401` response is a trivial server-side change requiring no special git protocol knowledge. The only user action needed is performing a normal fetch/push/clone against that remote, which is an expected workflow, not an "unnatural" step. Note that the header only triggers the *prompt*; whether the user ultimately submits a PAT/OAuth grant to that endpoint is user-dependent, which somewhat limits automatic/silent exploitation but the framing (a legitimate-looking GitHub sign-in dialog triggered by Desktop itself) is a strong phishing amplifier compared to a normal external phishing page.

### Recommendation
Do not trust the `WWW-Authenticate` header as authoritative for classifying a host as GitHub/GitHub Enterprise. At minimum, corroborate it with an actual verification request (`isGitHubHost`, which already exists and is used as the final fallback) before offering the "enterprise" sign-in flow, or require this classification to only lower friction for hosts that independently pass `isGitHubHost`. If the header optimization must be kept for latency reasons, restrict its effect to a narrower, low-consequence codepath (e.g., only affects `storeCredential`/`eraseCredential` generic-vs-github routing) and never let it alone trigger user-facing sign-in/OAuth prompts bound to attacker-controlled origins.

### Proof of Concept
1. Attacker stands up an HTTP(S) git server (or MITM proxy) at `https://evil.example.com/attacker/repo.git`.
2. Server responds to Git's authentication probe with `401 Unauthorized` and header `WWW-Authenticate: Basic realm="GitHub"`.
3. Victim runs `git fetch`/`clone`/`push` in GitHub Desktop against this remote.
4. Git invokes Desktop's credential trampoline; `parseCredential` populates a `wwwauth[0]` entry containing the spoofed realm.
5. `getEndpointKind` (`trampoline-credential-helper.ts:157-165`) matches `realm="GitHub"` and returns `'enterprise'` for `evil.example.com`.
6. `getCredential` finds no existing account for that origin and calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`.
7. `promptForGitHubSignIn` opens the Sign-In popup, calling `dispatcher.setSignInEndpoint('https://evil.example.com')`, presenting the victim with what looks like Desktop's native GitHub Enterprise sign-in for that attacker-controlled origin.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }
