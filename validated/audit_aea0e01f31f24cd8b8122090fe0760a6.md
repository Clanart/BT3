### Title
Unchecked `u64` sums in `SignableTransaction::new`/`fee()` allow wrapped payment totals and underflowed fee reporting - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report concerns an accounting accessor (`getEarnings`) returning a huge wrapped value because a tracked quantity was decremented below zero for an entity with no real balance. The analog in bitcoin-serai is the fee/accounting math in `SignableTransaction`: `input_sat`, `payment_sat`, and `fee()` all use plain `u64` `sum()`/subtraction with no overflow checks, so crafted payment amounts (public inputs selecting withdrawal outputs) or crafted `ReceivedOutput` values (untrusted bytes via `ReceivedOutput::read`) wrap the accounting, producing a transaction whose outputs exceed its inputs and a `fee()`/`needed_fee` view that reports a near-`u64::MAX` value or panics.

### Finding Description
`SignableTransaction::new` sums inputs and payments with unchecked `u64` addition: `let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();` and `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` [1](#0-0) . Each payment is only checked against `DUST`, with no upper bound or `MAX_MONEY` check [2](#0-1) . The solvency check then compares the wrapped sums: `if input_sat < (payment_sat + needed_fee)` [3](#0-2) .

Two payments of `2^63` sats each sum to `2^64`, which wraps `payment_sat` to 0, so the `NotEnoughFunds` check passes even though the real output total is ~1.8e19 sats per output. `fee()` then computes `sum(prevouts) - sum(outputs)` with plain subtraction [4](#0-3) , which underflows to ~`u64::MAX` in release or panics in debug — the same "accessor returns a huge wrapped value for an inconsistent accounting state" shape as `getEarnings`. Symmetrically, `input_sat` can wrap when `ReceivedOutput`s are decoded from untrusted bytes via `ReceivedOutput::read`, whose `TxOut::consensus_decode` accepts any `u64` value [5](#0-4) .

### Impact Explanation
An unprivileged party who can influence the payment list (e.g., withdrawal/burn instructions that become `payments`) or feed bytes to `ReceivedOutput::read` can cause the threshold signing pipeline (`TransactionSignMachine::sign` / `TransactionSignatureMachine::complete`) to produce a transaction whose declared outputs exceed the sum of its real inputs. Such a transaction is consensus-invalid (per-output value exceeds `MAX_MONEY` and inputs are insufficient), so the signing round yields an unspendable artifact and can wedge retry logic; `fee()` reports a near-`u64::MAX` fee or panics, corrupting any accounting/decision built on it. This is a reachable integrity failure in fee/fund accounting driven purely by public input values.

### Likelihood Explanation
Reachability requires the attacker to control either the `payments` slice (plausible where outputs are derived from user-submitted withdrawal instructions) or serialized `ReceivedOutput` bytes — both are listed as untrusted-input surfaces. No validator collusion or key compromise is needed; the flaw is purely missing overflow checks on attacker-chosen `u64`s. Severity is Medium: it cannot steal funds (the resulting tx is consensus-invalid), but it reliably produces an incorrect accounting state / signed unintended transaction and can panic the signing path.

### Recommendation
Use `checked_add`/`saturating_add` when summing `input_sat`, `payment_sat`, and in `fee()`; reject any single payment above Bitcoin's `MAX_MONEY` (21e14 sats) and error when outputs exceed inputs instead of relying on wrapped arithmetic — mirroring the upstream fix to keep the accounting view consistent with real balances.

### Proof of Concept
```rust
// Attacker supplies two payments whose sum wraps u64
let payments = vec![
  (attacker_script.clone(), u64::MAX / 2 + 1), // 2^63 sats
  (attacker_script.clone(), u64::MAX / 2 + 1), // payment_sat wraps to ~2
];
// One honest small UTXO suffices to pass the NotEnoughFunds check
let stx = SignableTransaction::new(vec![honest_output], &payments, None, None, fee_per_vbyte)?;
// fee() underflows: sum(inputs) << sum(outputs) -> panic or u64::MAX-ish value
let reported_fee = stx.fee();
assert!(reported_fee > stx.needed_fee()); // misleading, wrapped accounting
```
The resulting `tx` would carry outputs vastly exceeding inputs; nodes complete `sign`/`complete` for a consensus-invalid transaction while `fee()` returns a wrapped value instead of erroring.
