### Title
App proxy signed-request verification has no timestamp/staleness check, allowing indefinite replay of captured requests - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates only that the HMAC signature matches the query parameters; it never checks the `timestamp` parameter against the current time. This is the same bug class as the Chainlink `latestRoundData()` issue: a data/signature source is trusted as "current" without verifying it isn't stale/outdated, so old-but-validly-signed data is treated as fresh indefinitely.

### Finding Description
`query_string_valid?` extracts the `signature` param and recomputes an HMAC over the remaining sorted params (which includes `timestamp`), then does a `secure_compare`. There is no logic anywhere in `verify_proxy_request` or `query_string_valid?` that rejects a request whose `timestamp` is far in the past. [3](#0-2) 

Because the `timestamp` value is merely one of the signed fields (not an expiry check), any request that was legitimately signed by Shopify and observed/captured by an attacker (e.g., via logs, proxies, browser history, referrer leakage, or a compromised network intermediary) remains permanently valid and replayable — `verify_proxy_request` will accept it at any point in the future, exactly as `getOraclePrice()` accepted stale round data because it never checked `answeredInRound >= roundID` or enforced a heartbeat/staleness bound.

The test suite itself demonstrates this: a query string carrying `timestamp=1466106083` (June 2016) with its corresponding valid signature is asserted to pass verification, with no time-based rejection. [2](#0-1) 

### Impact Explanation
An app proxy request that was captured once (its full query string plus signature) can be replayed by an unrelated/anonymous attacker at any later time and will be accepted as an authentic Shopify-originated proxy request. Since app proxy requests are used by merchant storefronts to invoke privileged app endpoints (often performing state changes or returning shop-specific data), a replayed forged/old request effectively constitutes an accepted forged/stale signed request being processed as current, which can result in unintended state changes or data exposure depending on how the consuming app uses the (attacker-controlled) `shop` and other proxied parameters.

### Likelihood Explanation
Exploitation requires only that an attacker previously observe one legitimate app-proxy request (its full URL/query string is often visible in browser history, referrer headers, shared logs, or unencrypted network paths) — no secret key or privileged access is needed at replay time, matching the "unprivileged, anonymous HTTP request" bar for this analog.

### Recommendation
In `query_string_valid?` (or `verify_proxy_request`), after signature verification succeeds, additionally validate the `timestamp` query parameter against the current server time and reject requests outside an acceptable freshness window, e.g.:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)
  signature = query_hash.delete("signature")
  return false if signature.nil?

  return false unless timestamp_fresh?(query_hash["timestamp"])

  ActiveSupport::SecurityUtils.secure_compare(
    calculated_signature(query_hash),
    signature,
  )
end

def timestamp_fresh?(timestamp)
  return false if timestamp.blank?
  (Time.now.to_i - timestamp.to_i).abs <= MAX_ALLOWED_SKEW_SECONDS
end
```

### Proof of Concept
1. An attacker observes (e.g. via server logs, browser history, a shared network, or referrer leakage) a legitimate storefront app-proxy request URL such as `.../apps/my-app?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid-hmac>`.
2. At any later time (days, months, or years afterward), the attacker replays this exact request to the app's proxy endpoint.
3. `ShopifyApp::AppProxyVerification#verify_proxy_request` calls `query_string_valid?`, which recomputes the HMAC over the same params and finds it matches — the request is accepted as legitimate and processed, exactly as demonstrated by the existing test asserting a 2016-dated `timestamp` passes validation with no rejection.     def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
