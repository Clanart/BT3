### Title
Security-review budget exhaustion silently disables `Stop`-hook vulnerability detection - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The `security-guidance` plugin's `Stop` hook is the automated "privileged" check that reviews every turn's diff for newly introduced vulnerabilities and forces Claude to fix them via `sys.exit(2)` before the response reaches the user. Like `arbitraryCall()` in the original report, this protective action is gated by a piece of shared, mutable state that has to be below a threshold before the check will run at all, and that state can be driven to the blocking value by content the review itself is supposed to be defending against.

### Finding Description
`MAX_STOP_HOOK_FIRINGS` (default 3) caps how many times the `Stop` hook may fire within a single `STOP_LOOP_STATE_TTL_SEC` (120s) window [1](#0-0) . The counter `stop_hook_fire_count` is only incremented when the review actually finds vulnerabilities (`concrete_guidance` truthy) and is stored in shared, TTL-scoped session state [2](#0-1) . Before doing any review work, `handle_stop_hook` checks this counter and, once it reaches the max, skips the review entirely for the rest of the TTL window with no guidance shown to the user: [3](#0-2) 

This mirrors the `Locke.sol` pattern precisely: a `require`-style gate (`incentives[who] == 0` ↔ `fire_count < MAX_STOP_HOOK_FIRINGS`) protects a privileged action (`arbitraryCall()` ↔ the `Stop`-hook LLM security review), and the gate's state can be pushed into the "blocked" condition by content the attacker controls (an incentive transfer from any address ↔ agent-introduced vulnerable diffs triggered across several turns via prompt injection, a malicious skill/subagent, or content fetched from an untrusted MCP/web source that steers Claude into repeatedly writing dangerous patterns). Once three such fires occur inside 120 seconds, `_skip(2)` fires silently — the reset path is purely time-based (`STOP_LOOP_STATE_TTL_SEC` expiry) rather than requiring any owner/gov-style unlock, so there is no user-facing acknowledgment that protection is temporarily off [4](#0-3) .

### Impact Explanation
While the plugin's other layers (pattern warnings, commit-review) still operate independently, this specific `Stop`-hook diff-review layer — the one that runs on every ordinary turn, not just `git commit`/`git push` — can be forced into a "review skipped" state for up to 120 seconds by any actor (prompt-injected content, a malicious dependency's install script suggestions, a compromised MCP tool result, etc.) capable of causing three vulnerability-triggering edits inside that window. During the window, genuinely new and higher-severity vulnerabilities introduced in the same turn/session are not caught by this layer and reach the user unreviewed and unannounced. This is a confidentiality/integrity-adjacent gap in an unprivileged-user-triggerable protective mechanism (tool-authorization/hook-bypass trust boundary), not a crash or pure inconvenience.

### Likelihood Explanation
Reaching the condition requires only that the `Stop` hook fire three times with detected vulnerabilities inside 120 seconds, which is plausible in an "asyncRewake" fix-loop scenario (vuln → exit(2) → attempted fix → vuln again) that can be nudged by adversarial content steering Claude toward repeated unsafe edits. It requires no special privileges — any content reachable by the agent (files, fetched pages, MCP tool output) that influences edit patterns can drive it. It's a moderate-likelihood, session-scoped griefing condition rather than a one-shot trivial trigger, since it depends on the specific asyncRewake timing/TTL window.

### Recommendation
- Surface a visible `systemMessage`/notification when a `_skip(2)` (budget-exhausted) event occurs, so the user knows a review was withheld, mirroring the "acknowledge the risk" mitigation used for the original C4 finding.
- Consider scoping the budget/TTL more conservatively (e.g., per-distinct-vulnerability-category rather than global fire count) so that a burst of unrelated findings doesn't exhaust the shared budget for all subsequent findings.
- Emit a metrics/log signal distinguishable from normal skip reasons specifically for budget exhaustion (it already uses `skip_reason=2`, but it is not currently surfaced to the end user).

### Proof of Concept
Not independently reproduced beyond static code reading (no execution environment available). Conceptually: within one interactive session, cause three separate turns/asyncRewake cycles in under 120 seconds where the diff Claude writes trips the LLM security reviewer's high/critical findings (e.g., via a prompt-injected file or fetched web content that repeatedly nudges Claude to reintroduce a flagged pattern after a partial fix). On the fourth such vulnerability-triggering fire within the same 120-second window, `handle_stop_hook` will hit the `fire_count >= MAX_STOP_HOOK_FIRINGS` branch and call `_skip(2)` [3](#0-2) , silently exiting 0 without reviewing the new diff, until `STOP_LOOP_STATE_TTL_SEC` (120s) elapses since the last recorded fire.
