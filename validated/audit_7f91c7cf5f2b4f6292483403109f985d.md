### Title
Unchecked `u32` subtraction in Bitcoin difficulty-adjustment calculation inverts the clamping direction on negative epoch timespans, producing an incorrect difficulty target - (File: circuits-lib/src/header_chain/mod.rs)

### Summary
`calculate_new_difficulty` computes `actual_timespan = last_timestamp - epoch_start_time` using plain unchecked `u32` arithmetic. Real Bitcoin Core performs this subtraction with a signed 64-bit type specifically to correctly clamp negative timespans to the minimum bound. Here, if `last_timestamp < epoch_start_time`, the `u32` subtraction wraps around to a huge value near `u32::MAX` instead of producing a negative number, which then gets clamped by the *upper* bound instead of the *lower* bound — the opposite of consensus behavior. This is a direct analog of the MIPS `ADD`/`SUB` overflow finding: an arithmetic instruction that should raise/branch on an "overflow" condition instead silently wraps, causing state-machine divergence from the emulated specification.


Bitcoin Core computes `nActualTimespan` as a signed 64-bit quantity, so a negative timespan (last block earlier than the epoch's first block) is correctly recognized as "less than `nPowTargetTimespan/4`" and clamped to the *minimum* bound (harder difficulty). In this circuit, `last_timestamp - epoch_start_time` is unsigned `u32` arithmetic: when `last_timestamp < epoch_start_time`, the subtraction underflows/wraps to a value close to `u32::MAX` (e.g. `4_294_9xx_xxx`), which is *greater* than `EXPECTED_EPOCH_TIMESPAN * 4` (1,209,600 × 4 ≈ 4,838,400 for mainnet — note the wrapped value can be either above or below this threshold depending on the magnitude of the underflow). In many cases this pushes execution into the wrong clamp branch (or an unclamped/very large value), computing a new difficulty target that diverges from the one Bitcoin Core would derive for the same header sequence.

This mirrors the reported MIPS bug class precisely: `apply_block_headers`/`calculate_new_difficulty` acts as the "instruction executor" for the header-chain circuit's arithmetic, and — just like the un-trapped MIPS `ADD`/`SUB` — an integer wraparound condition that should be handled explicitly (matching signed-arithmetic semantics) is instead silently swallowed by `u32` wraparound, producing a value the real protocol would never produce.

`self.block_height.wrapping_add(1)` and the `U256::wrapping_add`/`wrapping_mul`/`wrapping_div` calls elsewhere in the same file are intentional (they operate on values that cannot legitimately exceed their bounds within the protocol's assumptions, e.g. block height overflow after billions of blocks, or U256 total work accumulation which mirrors Bitcoin Core's own `arith_uint256` wraparound-tolerant behavior). The `last_timestamp - epoch_start_time` case is different: it is the one place where Bitcoin Core deliberately uses a *signed* type to preserve the sign of the result for correct clamping, and this circuit does not.

### Impact Explanation
The header-chain circuit is the consensus-critical component that produces `ChainState.current_target_bits`/`total_work`, which downstream bridge logic and light-client-style verification rely upon to certify that a chain of Bitcoin block headers represents valid, real proof-of-work equivalent to mainnet consensus rules. If the wrap-clamp divergence causes the circuit to accept/require a *weaker* difficulty target for the following epoch than Bitcoin Core would compute, this is exactly the "a false circuit claim proved" case: the circuit could certify a chain segment as satisfying Bitcoin consensus rules for an epoch whose difficulty target it computed incorrectly, when in fact the emulated Bitcoin difficulty adjustment differs. Conversely, if it wrongly demands a *harder* target than consensus mandates, then a "true circuit claim [could be] made unprovable" for legitimately-mined chains that hit this edge case, since `check_hash_valid` would reject correctly-mined block hashes as insufficient.

### Likelihood Explanation
Triggering this bug requires the total epoch timespan (`last_timestamp - epoch_start_time`) to actually be negative in real Bitcoin history for the chain the header-chain circuit is fed — i.e., the last block of a 2016-block epoch has an earlier timestamp than the first block of that same epoch. Individual out-of-order timestamps are common (only the median-of-11 rule constrains monotonicity), but a *net negative* span across an entire ~2-week/2016-block epoch on mainnet is exceptionally unlikely (would require systemic backward-timestamp drift across the whole epoch), making exploitation on mainnet effectively theoretical absent a specific historical epoch where this occurred. It is far more plausible on lower-difficulty/short-epoch networks (e.g., custom signet with 10-second blocks, `EXPECTED_EPOCH_TIMESPAN = 20,160`), where such a swing is comparatively easier for a block producer with mining control to arrange. This is the same likelihood pattern the source report itself documents (op-program never observed to trigger it) — a deviation from spec that lacks a demonstrated concrete trigger under the currently deployed network parameters.

### Recommendation
Compute `actual_timespan` using a signed type (e.g., `i64`) mirroring Bitcoin Core's arithmetic, then clamp within signed space before converting back to the unsigned representation used for the U256 multiplication:
```rust
let mut actual_timespan = last_timestamp as i64 - epoch_start_time as i64;
if actual_timespan < (EXPECTED_EPOCH_TIMESPAN / 4) as i64 {
    actual_timespan = (EXPECTED_EPOCH_TIMESPAN / 4) as i64;
} else if actual_timespan > (EXPECTED_EPOCH_TIMESPAN * 4) as i64 {
    actual_timespan = (EXPECTED_EPOCH_TIMESPAN * 4) as i64;
}
let actual_timespan = actual_timespan as u32; // now guaranteed non-negative and within bounds
```

```rust
fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target: u32,
) -> [u8; 32] {
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < EXPECTED_EPOCH_TIMESPAN / 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN / 4;
    } else if actual_timespan > EXPECTED_EPOCH_TIMESPAN * 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4;
    }

    let current_target_bytes = bits_to_target(current_target);
    let mut new_target = U256::from_be_bytes(current_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(EXPECTED_EPOCH_TIMESPAN));

    if new_target > NETWORK_CONSTANTS.max_target {
        new_target = NETWORK_CONSTANTS.max_target;
    }
    new_target.to_be_bytes()
}
```
