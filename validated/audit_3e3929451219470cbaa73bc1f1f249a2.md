### Title
Stale `safe.directory` git trust exceptions are never revoked when a repository is removed from Desktop or a path is reused - ([File: app/src/lib/git/config.ts])

### Summary
The external report's broken invariant is: *a "trust/approval" grant is recorded but never fully revoked when the context that justified it changes, allowing a later, unrelated actor to inherit that trust.* GitHub Desktop's local analog is `addSafeDirectory()`, which appends a path to the global `safe.directory` git config entry whenever the user clicks "Trust Repository", but Desktop has no corresponding call that removes that entry when the repository is removed from Desktop, relocated, or when the path is later reused by different content/owner.

### Finding Description
When Desktop detects a repository owned by a different user (`getRepositoryType` returning `kind: 'unsafe'`), it shows a "Trust Repository" action in `MissingRepository` and `AddExistingRepository`. Accepting it calls: [1](#0-0) 

which appends the path with `git config --global --add safe.directory <path>`: [2](#0-1) 

This is a permanent, additive grant in the user's global `~/.gitconfig`. Unlike other config helpers in the same file (`removeConfigValue`, `removeGlobalConfigValue`) which do support unsetting values: [3](#0-2) 

there is no `removeSafeDirectory`/revocation call anywhere in the codebase. When a user removes a repository from Desktop (`_removeRepository` / `repositoriesStore.removeRepository`) the app only deletes the local DB record and clears push-tag tracking state — it never unsets the corresponding `safe.directory` entry: [4](#0-3) [5](#0-4) 

Similarly, `_relocateRepository` can rebind a `Repository` record to a brand-new user-chosen path without any interaction with `safe.directory` state: [6](#0-5) 

Because `safe.directory` entries are keyed purely by filesystem path string (not by content hash, owner SID, or repository identity), once a path has been trusted it stays trusted for git operations against *whatever* is at that path in the future — mirroring exactly the OwnableSmartWallet pattern where an approval keyed by an identifier (there: an address; here: a path) outlives the specific grant context and is inherited by a different, later "owner" of that identifier.

### Impact Explanation
On systems where directories are reused across trust boundaries — shared drives, temp directories, container/VM provisioning scripts, CI runners with recycled paths, or a machine handed off between users — an attacker who can plant a Git repository at a path a victim previously trusted (and later removed from Desktop) benefits from a stale `safe.directory` bypass. Git's `safe.directory` protection exists specifically to stop `execute-on-open`-type attacks (hooks, `.gitattributes` filters, etc.) from repos owned by another user; a stale trust entry silently defeats that protection for content the user never explicitly reviewed at that path. This can lead to unwanted command/hook execution the next time Desktop (or the user's `git`) operates against that path — a legitimate "silent corruption of expected trust boundary" primitive per the impact criteria.

### Likelihood Explanation
Moderate. It requires: (1) a user having trusted a directory at some point via Desktop's UI, (2) that repository later being removed/relocated in Desktop without git-level revocation, and (3) the path being reused by attacker-controlled content. This is more plausible in shared-machine, CI, or provisioning scenarios than on a single-user personal laptop, but it does not require local/physical access beyond normal Desktop usage patterns already exercised by the app's own "Trust Repository" feature — no admin rights, malware, or credential leakage needed.

### Recommendation
- When a repository is removed from Desktop (`_removeRepository`) or its path changes (`_relocateRepository`), remove the corresponding `safe.directory` entry (`git config --global --unset-all safe.directory <path>`), mirroring the existing `removeGlobalConfigValue` helper.
- Consider re-verifying ownership/trust at the time of each git operation rather than relying solely on a persistent, path-keyed allowlist, or scoping trust decisions per repository identity in Desktop's own DB rather than delegating permanently to global git config state.

### Proof of Concept
1. On a shared machine, clone/open a repository at `C:\shared\repo` (or `/shared/repo`) owned by another local user; Desktop flags it "unsafe" and the user clicks "Trust Repository", triggering `addSafeDirectory` and adding the path to global `safe.directory`.
2. The user later removes this repository from Desktop via `_removeRepository` (path is deleted from Desktop's repository DB only; `safe.directory` entry is untouched).
3. A different, less-trusted local user or process later creates a new Git repository (with malicious hooks/`.gitattributes` filters) at the exact same path `C:\shared\repo`.
4. Because `safe.directory` still contains that path in the victim's global `.gitconfig`, git will treat the new, attacker-controlled repository as trusted and skip the ownership-mismatch protection, potentially executing attacker-supplied hooks/filters on the victim's next git operation against that path — even though no fresh trust decision was ever made for this specific content.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

  public async _relocateRepository(repository: Repository): Promise<void> {
    const path = await showOpenDialog({ properties: ['openDirectory'] })

    if (path === null) {
      return
    }

    const rt = await getRepositoryType(path)

    if (rt.kind === 'regular') {
      // The repository has moved, so any main worktree we recorded before now
      // points at where it used to be. Resolve it again from the new location.
      await this.repositoriesStore.updateRepositoryPath(
        repository,
        rt.topLevelWorkingDirectory,
        rt.gitDir,
        await this.findMainWorktreePath(rt.topLevelWorkingDirectory)
      )
    } else if (rt.kind === 'unsafe') {
      // Git refuses to run in a repository it considers unsafe, so there's no
      // resolving the main worktree here. Drop the recorded path rather than
      // keep one we know is stale.
      await this.repositoriesStore.updateRepositoryPath(
        repository,
        path,
        undefined,
        undefined,
        true
      )
    } else {
      this.emitError(new Error(this.getInvalidRepoPathsMessage([path])))
    }
  }
