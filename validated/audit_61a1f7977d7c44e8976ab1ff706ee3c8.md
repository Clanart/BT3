### Title
Unchecked KIP-71 `GasTarget` governance parameter of `0` causes division-by-zero panic in `NextMagmaBlockBaseFee`, halting base-fee computation for block production and validation - (File: `params/kip71_config.go`)

### Summary
The `Kip71GasTarget` governance parameter has a no-op format checker, so it can be voted/set to `0`. `NextMagmaBlockBaseFee` uses `GasTarget` as a divisor whenever the parent block's gas usage differs from the target, so a `GasTarget` of `0` triggers a division-by-zero panic in `math/big`. This function is invoked both when validating incoming blocks and when assembling new blocks, so a `0` value halts base-fee-dependent block processing across the network — directly analogous to the Olympus `RANGE::setSpreads` bug where an unchecked boundary value (`wallSpread == 10000`) caused a division by zero that bricked price updates.

### Finding Description
The governance parameter registry defines `Kip71GasTarget` with `FormatChecker: noopFormatChecker`, meaning no validation is performed on the value beyond canonicalizing it to `uint64`: [1](#0-0) 

This value flows unchecked into `KIP71Config.GasTarget`, which is used in `NextMagmaBlockBaseFee` as a divisor: [2](#0-1) 

When `parentGasUsed != gasTarget` and `gasTarget == 0`, the branch enters either the "used more than target" or "used less than target" path, both of which perform `x.Div(x, new(big.Int).SetUint64(gasTarget))` with a zero divisor — `math/big.Int.Div` panics on division by zero. The only case a `gasTarget == 0` is safely handled is when `parentGasUsed == 0` too (the `parentGasUsed == gasTarget` branch short-circuits before any division): [3](#0-2) 

Unlike `BaseFeeDenominator`, which has an explicit non-zero check (`return ok && v != 0`), and `MaxBlockGasUsedForBaseFee`, whose zero value is defensively guarded at the call site in `feehistory.go`, `GasTarget` has no such protection anywhere in the governance parameter table or in `NextMagmaBlockBaseFee` itself: [4](#0-3) [5](#0-4) 

Votes for this parameter only go through the generic `NewVoteData` validation path, which calls the parameter's own (no-op) `FormatChecker`, so nothing rejects `0`: [6](#0-5) 

`NextMagmaBlockBaseFee` is a consensus-critical function reached from block validation (`blockchain/block_validator.go`) and block assembly (`work/worker.go`), meaning once the parameter takes effect, every node computing the next block's base fee — whether validating a submitted block or producing a new one — will panic. This exactly mirrors the referenced Olympus bug class: an unchecked boundary/zero governance-controlled numeric parameter reaching a division operation on a consensus-critical code path, permanently breaking a core protocol function (there, price updates via `beat`/`operate`; here, base-fee computation via `NextMagmaBlockBaseFee`).

### Impact Explanation
If `Kip71GasTarget` is set to `0` via the governance voting mechanism, every node that subsequently attempts to compute or verify the base fee for a Magma-enabled block will panic in `math/big.Int.Div`. Because this is invoked both in header verification (`VerifyMagmaHeader`) and block assembly, this affects both block producers and passive validators, functionally halting the chain until the parameter is corrected — a severe availability impact matching "state divergence between honest nodes" / consensus-breaking DoS categories.

### Likelihood Explanation
The parameter is only settable through the governance module (requires governance-council voting privileges), which reduces the likelihood compared to a fully permissionless call, but it is not privileged in the sense of node/validator-key compromise — it is a normal, sanctioned governance action that lacks the intended safety check that other adjacent KIP-71 parameters (like `BaseFeeDenominator`) already have. Given the codebase already special-cases zero-avoidance for `BaseFeeDenominator` and `MaxBlockGasUsedForBaseFee`, the omission for `GasTarget` appears to be an oversight rather than an intentional design choice, making accidental or malicious governance misconfiguration plausible.

### Recommendation
Add a non-zero `FormatChecker` for `Kip71GasTarget` analogous to the one already used for `Kip71BaseFeeDenominator`:
```go
Kip71GasTarget: {
    Canonicalizer: uint64Canonicalizer,
    FormatChecker: func(cv any) bool {
        v, ok := cv.(uint64)
        return ok && v != 0
    },
    ...
}
```
Additionally, consider adding a defensive zero-check inside `NextMagmaBlockBaseFee` itself (similar to the existing `baseFeeDenominator == 0` fallback) so that a bad historical/legacy config value cannot crash the node even if the governance-level guard is bypassed.

### Proof of Concept
1. Governance council votes to set `governance.kip71.gastarget` (parameter name `Kip71GasTarget`) to `0`; the vote passes `NewVoteData`'s `FormatChecker` unchanged because it is a no-op.
2. Once the parameter takes effect at the target block, any block whose gas usage is non-zero (`parentGasUsed != 0`) causes `NextMagmaBlockBaseFee` to enter the increase/decrease branch with `gasTarget = 0`.
3. The call `x.Div(x, new(big.Int).SetUint64(gasTarget))` at `params/kip71_config.go` lines 102 and 120 panics with "division by zero".
4. All nodes calling this function during header verification (`blockchain/block_validator.go`) or block sealing (`work/worker.go`) crash/panic, halting block production and validation network-wide.
