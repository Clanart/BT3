I have sufficient evidence to write up the finding on the EVM host's global `challengePeriod` desync.

### Title
Global, live-read `challengePeriod` desyncs from per-height frozen `stateMachineCommitmentUpdateTime`, allowing already-stored state commitments to be actioned before their originally-promised fraud-detection window elapses - (File: `evm/src/core/EvmHost.sol`, `evm/src/core/HandlerV2.sol`)

### Summary
`EvmHost` stores a single, host-wide `challengePeriod` value that governance (via `hostManager`) can update at any time through `updateHostParams`, with no bound relative to the previous value and no per-state-machine-height snapshotting. Every message-processing entry point in `HandlerV2` (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) reads this *current* `challengePeriod` value and compares it against `stateMachineCommitmentUpdateTime`, a per-height timestamp that was frozen the moment the commitment was stored. This is structurally identical to the Aragon bug: the "eligibility" data (the commitment and its storage timestamp) is a frozen snapshot, but the "threshold" (the required waiting period) is read live and can change underneath it, desynchronizing the two.

### Finding Description
`HostParams.challengePeriod` is a single global field [1](#0-0) , updated wholesale by `updateHostParamsInternal`, which validates `hostManager`, `handler`, `consensusClient`, `hyperbridge` id, `stateMachines` length and `unStakingPeriod`, but performs **no validation at all on `challengePeriod`** — it can be set to any value, including a drastic reduction or zero, in a single call [2](#0-1) .

Every handler that consumes state commitments computes the elapsed delay from the commitment's *frozen* update time and compares it to the *live* `challengePeriod`:

```solidity
uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
``` [3](#0-2) 

The same live-read pattern repeats in `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` [4](#0-3) [5](#0-4) [6](#0-5) . `stateMachineCommitmentUpdateTime` itself is a per-height mapping written once when the commitment is stored and never revisited [7](#0-6) .

The Substrate/pallet-ismp side follows the identical pattern: `verify_delay_passed` reads `host.challenge_period(proof_height.id)` live and compares it to the frozen `state_machine_update_time` [8](#0-7) .

This is exactly the "M-03" pattern: the commitment-storage timestamp is the snapshot (analogous to `snapshotBlock`), and `challengePeriod` is the threshold parameter that is supposed to be evaluated as it existed at snapshot time but is instead read from current, mutable state (analogous to `multisigSettings.minApprovals`).

### Impact Explanation
The `challengePeriod` exists specifically to give fishermen a window to submit fraud proofs and freeze the host before a state commitment can be acted upon, as documented in the protocol's own consensus-proofs design (`docs/content/protocol/interoperability/consensus-proofs.mdx`, "Optimistic Bridging" / "Unstaking Periods" sections). Because the check uses the *live* value of `challengePeriod` rather than the value in effect when the specific commitment was stored, a reduction in `challengePeriod` retroactively shortens the safety window for **every already-stored, still-pending commitment across every state machine**, not just future ones. Any commitment stored under the old (larger) challenge period that has not yet accumulated the old required delay can immediately become actionable the instant the parameter is lowered — even if it is still within the window during which fishermen were promised the opportunity to freeze the host over a fraudulent commitment. This directly undermines the "false remote state must never become trusted" invariant, since it shrinks the fraud-detection window for state that is already in flight, potentially allowing a fraudulent or premature state commitment to be acted upon (funds released, messages dispatched) before it would otherwise have been eligible.

### Likelihood Explanation
`updateHostParams` is reachable only via the configured `hostManager` cross-chain governance path (or `admin` on `TestnetHost`), so triggering the desync requires a governance-level parameter change — this is a legitimate, expected protocol operation (e.g., re-tuning the challenge period for cost or UX reasons), not a compromised-key or malicious-relayer scenario. The bug is that this ordinary, permitted action has an unintended and unbounded blast radius on all pre-existing, unelapsed commitments simultaneously, with no grandfathering, floor, or gradual-transition mechanism, and no validation guarding against the reduction in `updateHostParamsInternal`.

### Recommendation
Snapshot the `challengePeriod` value applicable to a state commitment at the time the commitment is stored (e.g., alongside `stateMachineCommitmentUpdateTime`, similar to how `StateCommitmentHeight` already pairs height with commitment), and use that stored value — not the live `host.challengePeriod()` — when evaluating `verify_delay_passed`/`ChallengePeriodNotElapsed` checks in both `HandlerV2.sol` and `modules/ismp/core/src/handlers.rs`. Alternatively, enforce that `challengePeriod` reductions only apply to commitments stored after the update, and/or require a minimum notice/transition period before a reduced value takes effect.

### Proof of Concept
1. Governance calls `updateHostParams` with `challengePeriod = 7 days` (typical fraud-detection window). A relayer submits a consensus update that stores a new `StateCommitment` at height `H`; `stateMachineCommitmentUpdateTime(H)` is set to `t0` [9](#0-8) .
2. At `t0 + 1 hour`, before any fisherman has had a realistic chance to detect fraud in the commitment at `H` (only 1 of the promised 7 days has elapsed), governance (through `hostManager`) issues a legitimate `updateHostParams` call that lowers `challengePeriod` to `0` or a small value for unrelated reasons (e.g. cost tuning, migrating to a faster consensus client).
3. Immediately after that transaction, a relayer calls `handlePostRequests` (or any of the other handlers) with a proof anchored at height `H`. The check `challengePeriod > delay` now evaluates against the new, near-zero `challengePeriod` instead of the `7 days` that was in effect — and in effect for the commitment's entire pending life — when the commitment was stored [10](#0-9) .
4. Requests/timeouts referencing the still-young commitment at `H` are dispatched to destination modules years before fishermen's promised 7-day window elapses, even though nothing about commitment `H` itself changed — only the unrelated, global `challengePeriod` did.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params
        emit HostParamsUpdated({oldParams: _hostParams, newParams: params});

        _hostParams.feeToken = params.feeToken;
        _hostParams.admin = params.admin;
        _hostParams.handler = params.handler;
        _hostParams.hostManager = params.hostManager;
        _hostParams.uniswapV2 = params.uniswapV2;
        _hostParams.unStakingPeriod = params.unStakingPeriod;
        _hostParams.challengePeriod = params.challengePeriod;
        _hostParams.consensusClient = params.consensusClient;
        _hostParams.stateMachines = params.stateMachines;
        _hostParams.hyperbridge = params.hyperbridge;

```rust
pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
