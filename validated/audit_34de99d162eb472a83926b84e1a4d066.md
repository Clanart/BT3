Based on my analysis of the mathematics of the FFT-based erasure decoding in `recoverPolynomialCoeffs`, this is a genuine finding.

### Title
Truncation in `recoverPolynomialCoeffs` breaks the invariant `recovered[cellIDs[i]] == cells[i]` for over-supplied cell sets - ([File: internal/erasure_code/erasure_code.go])

### Summary
`Context.RecoverCells`/`RecoverCellsAndComputeKZGProofs` call `recoverPolynomialCoeffs` (`api_eip7594.go:97`), which delegates to `DataRecovery.RecoverPolynomialCoefficients` (`internal/erasure_code/erasure_code.go:110`). The routine computes an exact FFT-based polynomial quotient `h(x) = g(x)/Z(x)` and then unconditionally truncates it to the first `numScalarsInDataWord` coefficients [1](#0-0) , without ever checking that the truncated polynomial still reproduces the caller-supplied cell values at the caller-supplied indices.

### Finding Description
The equality claimed to hold is: for every supplied index `i`, `recovered_poly(x_{cellIDs[i]}) == cells[i]`, and `deg(recovered_poly) < ScalarsPerBlob (n)`.

Trace: `recoverPolynomialCoeffs` places supplied cells into `extendedBlob` at `cellID*scalarsPerCell` [2](#0-1) , computes `missingCellIds` as literally *all* cellIDs not supplied [3](#0-2) , and calls `RecoverPolynomialCoefficients(extendedBlob, missingCellIds)`.

Inside `RecoverPolynomialCoefficients`, `zX` is the vanishing polynomial over exactly the missing indices, of degree `M = (number of missing cells)*scalarsPerCell` [4](#0-3) . The routine forms `g(x)`, the exact degree-`<N` interpolant of `data_i * Z(x_i)` over all `N` points, then computes the quotient `h = g/Z` via coset FFT/IFFT, and returns only the first `n = numScalarsInDataWord` coefficients [5](#0-4) .

By construction, `h(x_i) = data_i` exactly for every known index `i` **only when `deg(h) < n`**, which is guaranteed only when the number of missing cells equals exactly `N-n` (i.e. the caller supplies *exactly* the minimum number of cells, `CellsPerExtBlob/2`). If the caller supplies more than the minimum (over-determined), `M < N-n`, so `deg(h)` can be as large as `K-1` where `K` is the number of known scalars — exceeding `n-1`. The code still truncates to `n` coefficients (`cosetQuotientEval[:dr.numScalarsInDataWord]`), silently discarding the higher-degree terms of `h`. If the attacker crafts `cells` values so that those discarded terms are non-zero when evaluated at the known points, the truncated polynomial no longer satisfies `recovered(x_i) == cells[i]` for the supplied `i`, even though no error is returned.

None of the guards in `recoverPolynomialCoeffs` (length check, ascending check, `cellID < CellsPerExtBlob`, `NumBlocksNeededToReconstruct`) protect against this, because they only bound the *minimum* number of supplied cells, not the internal consistency of cell values relative to each other, nor do they reject the case of supplying *more* than the minimum. There is no post-hoc check anywhere in the codebase (`api_eip7594.go`, `erasure_code.go`) verifying `recovered_poly` reproduces the caller-supplied cell values, unlike what a correct decoder must do.

### Impact Explanation
An attacker (or any node) that calls `RecoverCells`/`RecoverCellsAndComputeKZGProofs` with more than the minimum required cells and internally-inconsistent cell values (not evaluations of a single low-degree polynomial) causes the library to silently emit recovered cells/proofs that disagree with the caller-supplied data at the supplied indices — with no error. This is a client-split risk: different nodes reconstructing from different (even legitimately overlapping/redundant) cell subsets for the same logical data could derive different "recovered" cells and proofs, or diverge from c-kzg/consensus-specs behavior for the same input, matching the "High" impact category (library/spec disagreement or pooled state divergence).

### Likelihood Explanation
Preconditions: the caller must supply more cells than `NumBlocksNeededToReconstruct()` (i.e., over the 50% minimum) with mutually-inconsistent cell contents — fully within reach of an unprivileged, ordinary caller through the normal `RecoverCells`/`RecoverCellsAndComputeKZGProofs` API, no special privileges required, and repeatable per call. This is likely to occur in practice whenever gossip/networking layers pass in "extra" cells beyond the strict minimum (a normal and encouraged behavior for redundancy), combined with cells that aren't perfectly consistent (e.g., a subset comes from a different/faulty peer).

### Recommendation
After computing `polyCoeff`, re-evaluate the returned polynomial at each supplied `cellID` (or equivalently at the coset used to build cells) and assert that it matches the caller-supplied `cells[i]` exactly; return an error (e.g. a new `ErrRecoveredCellMismatch`) otherwise. Alternatively, restrict decoding to use exactly `NumBlocksNeededToReconstruct()` cells (discard/ignore extras before building `missingCellIds`/`zX`) so `deg(Z)` always equals `N-n` and the truncation is provably lossless.

func (dr *DataRecovery) constructVanishingPolyOnIndices(missingBlockErasureIndices []BlockErasureIndex) []fr.Element {
	// Collect all of the roots that are associated with the missing block erasure indices
	missingBlockErasureIndexRoots := make([]fr.Element, len(missingBlockErasureIndices))
	for i, index := range missingBlockErasureIndices {
		missingBlockErasureIndexRoots[i] = dr.rootsOfUnityBlockErasureIndex.Roots[index]
	}

	shortZeroPoly := vanishingPolyCoeff(missingBlockErasureIndexRoots)

	zeroPolyCoeff := make([]fr.Element, dr.numScalarsInCodeword)
	for i, coeff := range shortZeroPoly {
		zeroPolyCoeff[i*dr.blockErasureSize] = coeff
	}

	return zeroPolyCoeff
}

func (dr *DataRecovery) RecoverPolynomialCoefficients(data []fr.Element, missingIndices []BlockErasureIndex) ([]fr.Element, error) {
	zX := dr.constructVanishingPolyOnIndices(missingIndices)

	// Compute zX evaluations without mutating zX since we need zX later for a coset FFT
	zXForEval := make([]fr.Element, len(zX))
	copy(zXForEval, zX)
	dr.domainExtended.FftFr(zXForEval)
	zXEval := zXForEval

	if len(zXEval) != len(data) {
		return nil, errors.New("length of data and zXEval should be equal")
	}

	eZEval := make([]fr.Element, len(data))
	for i := 0; i < len(data); i++ {
		eZEval[i].Mul(&data[i], &zXEval[i])
	}

	dr.domainExtended.IfftFr(eZEval)
	dzPoly := eZEval

	dr.domainExtendedCoset.CosetFFtFr(zX)
	cosetZxEval := zX
	dr.domainExtendedCoset.CosetFFtFr(dzPoly)
	cosetDzEVal := dzPoly

	cosetQuotientEval := make([]fr.Element, len(cosetZxEval))
	cosetZxEval = fr.BatchInvert(cosetZxEval)

	for i := 0; i < len(cosetZxEval); i++ {
		cosetQuotientEval[i].Mul(&cosetDzEVal[i], &cosetZxEval[i])
	}

	dr.domainExtendedCoset.CosetIFFtFr(cosetQuotientEval)

	// Truncate the polynomial coefficients to the number of scalars in the data word
	polyCoeff := cosetQuotientEval[:dr.numScalarsInDataWord]
	return polyCoeff, nil
