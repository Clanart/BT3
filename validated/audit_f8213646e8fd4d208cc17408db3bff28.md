### Title
`SignableTransaction` computes weight/fee from `payments` only, omitting the OP_RETURN output, so the signed transaction underpays its intended fee rate - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the Controller sending funds to an immutable address rather than the per-vault treasury (using a stale/wrong value instead of the authoritative one), `SignableTransaction::new` builds the actual transaction with an extra `OP_RETURN` output appended to `tx_outs`, but computes both the weight/vbytes and the required fee from `payments` alone. The authoritative object — the transaction actually signed — contains more outputs than the set used for fee estimation, so the transaction commits less fee than the caller-specified `fee_per_vbyte` rate requires.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs`):

1. The OP_RETURN output is pushed into `tx_outs` when `data` is supplied:
```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
``` [1](#0-0) 

2. Yet weight/vbytes — and therefore `needed_fee` — are calculated from `payments`, which never includes the OP_RETURN output:
```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
``` [2](#0-1) 

3. The change path reuses the same `payments`-only estimate, so the fee is under-charged there too:
```rust
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
``` [3](#0-2) 

4. The minimum-relay-fee check is also done against the underestimated `vbytes`, so it does not catch the shortfall:
```rust
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
``` [4](#0-3) 

`calculate_weight_vbytes` builds its mock transaction only from `payments` and an optional `change` script — there is no accounting for the `data`/OP_RETURN output anywhere in the function [5](#0-4) .

### Impact Explanation
Any transaction carrying `data` pays `fee_per_vbyte * vbytes` for a vbyte count that excludes the OP_RETURN output (~9 + 2 + `data.len()` bytes, up to ~92 extra bytes ≈ up to ~92 vbytes). The effective fee rate of the broadcast transaction is therefore lower than the caller-specified rate, and can drop below Bitcoin's default minimum relay fee even though the constructor's `TooLowFee` check passed — the check runs against the same underestimated `vbytes`. The result is a fully-signed, valid transaction that nodes will refuse to relay or that sits unconfirmed, forcing an expensive re-sign/re-broadcast cycle with new nonces. Since `data` is attacker-influenced transaction data fed into the signing flow, an unprivileged party can force the underestimation to its maximum by supplying the full 80 bytes.

### Likelihood Explanation
The miscalculation is deterministic: every `SignableTransaction` constructed with `data.is_some()` underestimates its size and fee. Whether it crosses the minimum-relay threshold depends on the margin between the intended `fee_per_vbyte` and the minimum rate; at intended rates near the minimum, an ~80-vbyte shortfall on a small transaction is decisive. Even when the transaction still relays, the multisig systematically pays a lower effective rate than requested, degrading confirmation reliability. No special positioning is required — supplying `data` via the normal out/in-instruction path is sufficient to reach `SignableTransaction::new`.

### Recommendation
Compute weight and fee against the final `tx_outs` set (or pass the serialized OP_RETURN `ScriptBuf` into `calculate_weight_vbytes`) rather than `payments` alone. Both the no-change and with-change estimations, and the `TooLowFee` minimum-relay check, must use the actual transaction shape — i.e., use the authoritative transaction being signed, not the pre-construction payment list. A regression test should assert `needed_fee == fee_per_vbyte * actual_signed_tx_vbytes` for a transaction including `data`.

### Proof of Concept
```rust
let inputs = vec![/* one ReceivedOutput worth, e.g., 100_000 sats */];
let payments = vec![(dest_script, 50_000)];
let data = Some(vec![0xaa; 80]); // max allowed per the 80-byte check

let stx = SignableTransaction::new(inputs, &payments, change_script, data.clone(), 10).unwrap();

// The unsigned transaction contains the extra OP_RETURN output
assert!(stx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// But calculate_weight_vbytes was only ever invoked with `payments` (+ optional change),
// never with the OP_RETURN output, so:
//   stx.needed_fee() == 10 * vbytes(inputs, payments[, change])
// while the real signed tx vbytes is larger by ~ (8 + script overhead + 80) bytes.
// Effective rate = stx.fee() / actual_vbytes < 10 sat/vbyte.
```
Concretely: `SignableTransaction::new` pushes the OP_RETURN `TxOut` into `tx_outs` at line ~195, but `vbytes` used for `needed_fee` at line ~204 and for the change decision at line ~226 is derived exclusively from `payments` — the OP_RETURN weight is never included in any fee or weight computation.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }

    let weight = tx.weight();

    // Now calculate the size in vbytes

    /*
      "Virtual transaction size" is weight ceildiv 4 per
      https://github.com/bitcoin/bips/blob/master/bip-0141.mediawiki

      https://github.com/bitcoin/bitcoin/blob/306ccd4927a2efe325c8d84be1bdb79edeb29b04
        /src/policy/policy.cpp#L295-L298
      implements this almost as expected, with an additional consideration to signature operations

      Signature operations (the second argument of the following call) do not count Taproot
      signatures per https://github.com/bitcoin/bips/blob/master/bip-0342.mediawiki#cite_ref-11-0

      We don't risk running afoul of the Taproot signature limit as it allows at least one per
      input, which is all we use
    */
    (
      weight.to_wu(),
      u64::try_from(bitcoin::policy::get_virtual_tx_size(
        i64::try_from(weight.to_wu()).unwrap(),
        0i64,
      ))
      .unwrap(),
    )
  }
```
