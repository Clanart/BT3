## Finding: JSON parser skips duplicate-key detection when a field/oneof member is expressed as `null` [1](#0-0) 

### Title
Duplicate-key/oneof-conflict detection bypassed for `null`-valued JSON fields - (`src/google/protobuf/json/internal/parser.cc`)

### Summary
The C++ ProtoJSON parser's `ParseField` marks a field as "seen" (for duplicate-key and oneof-conflict enforcement) only *after* it decides the value is not a bare `null` no-op. Fields whose JSON value is `null` (other than `google.protobuf.Value`/`NullValue`) are consumed and the function returns immediately, without ever calling `Traits::RecordAsSeen`. This means a `null` occurrence of a field never "counts" toward duplicate/oneof-conflict detection, so a genuinely duplicate key — where one of the two occurrences is `null` — is silently accepted instead of being rejected, in violation of the JSON parsing spec (which requires duplicate-key rejection regardless of value).

### Finding Description
In `ParseField`, the null short-circuit happens before `SeenState seen = Traits::RecordAsSeen(*field, msg);`: [2](#0-1) 

The code comment explicitly acknowledges this is a known deviation from spec: [3](#0-2) 

This mirrors the Nested-Finance bug pattern: an entry (there, a token pushed with `amount=0`; here, a field occurrence expressed as JSON `null`) is inserted/consumed without being properly registered in the tracking structure (`parsed_fields_`/`parsed_oneofs_indices_` via `RecordAsSeen`, analogous to the array-existence check that Nested's `NestedRecords.store` failed to perform). Later processing (the "already set" duplicate/oneof check) only consults that tracking structure, so it never sees the earlier `null` occurrence — exactly like Nested's downstream logic that "considers the first occurrence" and never learns about the shadow/duplicate entry.

The existing Java `JsonFormat` test suite documents the intended (spec-conformant) behavior and shows it diverges from the C++/legacy behavior: [4](#0-3) 

### Impact Explanation
Because the `null` occurrence is invisible to `RecordAsSeen`, a payload containing two members of the same `oneof` (or two occurrences of the same field), where one is `null`, is accepted where the JSON1/ProtoJSON spec calls for rejection with an "already set" error: [5](#0-4) 

This is a parser-conformance/parsing-differential issue: two conformant ProtoJSON parsers (or the same parser in "strict" vs "legacy nonconformant" mode) can disagree on whether a message is valid and on which oneof member ends up set, which is the same class of "wrong element silently wins/survives" integrity failure as the original Nested report (there, a stale zero-amount entry silently persisted instead of being flagged as a conflicting duplicate). It does not, by itself, grant memory corruption or code execution — it is a spec-conformance/integrity gap in duplicate-key handling.

### Likelihood Explanation
Any ordinary client sending a bounded ProtoJSON payload through the public `JsonStringToMessage`/`MessageToJsonString` (or the equivalent `Traits`-based) parsing entry point can trigger this by including a `null` for one member of a `oneof` (or a repeated/duplicate field) alongside another real occurrence of a sibling member, exactly as exercised by `testNullFirstInDuplicateOneof` / `testNullLastInDuplicateOneof`: [6](#0-5) 
No privileged access or malicious schema is needed; the bug is reachable via the standard public parse API with a trusted, valid schema and attacker-controlled JSON bytes.

### Recommendation
Call `Traits::RecordAsSeen` for the field before (or independent of) the `null` short-circuit path, so that a `null` occurrence of a field/oneof member is registered in `parsed_fields_`/`parsed_oneofs_indices_` just like any other occurrence, and the subsequent "already set" check in `ParseField` correctly fires for duplicate keys/oneof conflicts regardless of whether the conflicting value is `null`. Track and resolve the referenced internal bug `b/519557203` before relying on this parser as a canonical source for any cross-implementation validation/signature logic.

### Proof of Concept
Given the tracked-but-unfixed behavior already codified in tests, a payload such as:
```json
{"oneofNestedMessage": null, "oneofInt32": 1}
```
parses successfully with `oneofInt32` set and no "already set" error, per: [7](#0-6) 
whereas per spec (and per the C++ implementation's own comment) this should be rejected as a duplicate/conflicting oneof entry, since `RecordAsSeen` is never invoked for the `null` branch in `ParseField`: [2](#0-1)

  // Any `null` values eagerly no-op, except for exactly the special cases of
  // google.protobuf.Value message and google.protobuf.NullValue enum.
  // Note that spec behavior is that we should do duplicate key checking in the
  // case of a null value, but this implementation currently does not
  // (b/519557203).
  if (lex.Peek(JsonLexer::kNull)) {
    MessageType type = ClassifyMessage(Traits::FieldTypeName(*field));
    if (type != MessageType::kValue && type != MessageType::kNull) {
      return lex.Expect("null");
    }
  }

  SeenState seen = Traits::RecordAsSeen(*field, msg);

  // Legacy nonconformant behavior only enforces duplicate key checking for
  // fields within the same oneof, otherwise enforce duplicate keys for all
  // fields.
  if (seen == SeenState::kOneofAlreadySeen ||
      (seen == SeenState::kFieldAlreadySeen &&
       !lex.options().allow_legacy_nonconformant_behavior)) {
    return lex.Invalid(absl::StrFormat(
        "'%s' has already been set (either directly or as part of a oneof)",
        name));
  }
