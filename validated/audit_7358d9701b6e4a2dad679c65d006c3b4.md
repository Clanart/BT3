### Title
Automatic remote-URL rewrite from unverified GitHub API `clone_url` allows silent redirection of pushes/fetches - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The report's broken invariant is: a value that controls where a user's assets/output are sent (`creatorFeeRecipient`) is taken from unvalidated input and used without confirming it is a value the user actually intends, so real value flows to an unintended destination. The closest structural analog in GitHub Desktop is `updateRemoteUrl`, which automatically rewrites the local `origin` remote URL to whatever `clone_url` value is present in a `GitHubRepository`/API repository object, with no verification that the new host is the same GitHub instance the user originally trusted — only that the URL *protocol* matches. This silently redirects future `git push`/`git fetch` operations for the repository to a different destination without any user confirmation.

### Finding Description
`updateRemoteUrl` is invoked to reconcile a repository's local git remote with metadata retrieved from the GitHub API (`IAPIRepository.clone_url`), typically to handle repo renames: [1](#0-0) 

The function performs three checks before rewriting the remote:
1. `protocolsMatch` — only verifies the URL scheme (`https:` vs `https:`), not the hostname.
2. `remoteUrlUnchanged` — verifies the user hasn't manually edited the remote away from the previously known `cloneURL`.
3. `!urlsMatch` — the new URL differs from the current one.

If all three hold, it calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` unconditionally — there is no check that `updatedRemoteUrl` still points at the same hostname/owner as the account the repository was originally associated with. `urlMatchesRemote` (used only to detect whether URLs already match, not to gate the rewrite) is the one place hostname is compared, but it is not used to reject a host change: [2](#0-1) 

The `apiRepo` object (and thus `clone_url`) originates from a GitHub API response. Because Desktop trusts this field completely once the protocol matches and the remote hasn't been manually altered, any actor who can influence the API repository object seen by the client (e.g., a malicious/compromised GitHub Enterprise Server endpoint, a repo owner who can set an attacker-controlled `clone_url`-shaped host via API/enterprise config, or any path that lets an attacker's response reach this code) can cause Desktop to silently rewrite the trusted `origin` remote to point at an arbitrary host with a matching protocol. Existing guards (`protocolsMatch`, `remoteUrlUnchanged`) do not stop this because they never compare hostnames between the old and new remote URL — they only compare against the previously cached `cloneURL`, which itself derives from the same untrusted API source.

### Impact Explanation
This maps to the "silent corruption of what the user commits or pushes" category in the accepted impact list: once the remote URL is rewritten, subsequent `git push` operations from `performPush` (which resolve `remote` from repository state, itself derived from `gitStore.defaultRemote`) will target the new, attacker-influenced host without any dialog or confirmation shown to the user: [3](#0-2) 

Fetch/pull operations against the rewritten remote could also cause the user's local repository to merge in attacker-controlled history from the new host. This is a medium-severity integrity issue: it does not itself grant code execution, but it corrupts the destination of push/fetch — the same class of "unintended transfer" the source report flags, translated from ETH fee routing to git object routing.

### Likelihood Explanation
Likelihood is constrained by needing control over the `IAPIRepository`/`GitHubRepository.cloneURL` value that Desktop consumes — which normally requires either a compromised/malicious GitHub Enterprise Server the victim has added as an account, or some other flaw feeding this code an attacker-influenced API repository object. Given the required precondition of an attacker-influenced API response (rather than local/physical access or leaked credentials, which are excluded), this is a plausible but not trivially-exploitable path from a normal GitHub.com session; it's most concretely reachable against GHES accounts where the client already trusts whatever host the admin/API configures.

### Recommendation
In `updateRemoteUrl`, require that the hostname parsed from `updatedRemoteUrl` matches the hostname of the account's configured endpoint (or at minimum matches the hostname of the existing remote) before calling `setRemoteURL`. If the hostname differs, treat this as a repository migration requiring explicit user confirmation (similar to the existing `ChooseForkSettings`/`PublishRepository` popups) rather than performing a silent rewrite.

### Proof of Concept
1. Add a GitHub Enterprise account whose API server is attacker-controlled or compromised (or otherwise arrange for `IAPIRepository.clone_url` returned for a tracked repository to be attacker-influenced).
2. Have that API server report the tracked repository's `clone_url` as `https://attacker-host.example/owner/name` (same `https:` protocol as the current origin, so `protocolsMatch` is true, and matching the previously cached `gitHubRepository.cloneURL` so `remoteUrlUnchanged` is true).
3. Desktop's refresh cycle calls `updateRemoteUrl`, which finds `protocolsMatch && remoteUrlUnchanged && !urlsMatch` all satisfied and calls `gitStore.setRemoteURL(name, 'https://attacker-host.example/owner/name')`, rewriting `origin` with no user prompt.
4. The next `git push`/`git fetch` in the app silently targets `attacker-host.example` instead of the user's real GitHub host. [4](#0-3)

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
