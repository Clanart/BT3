### Title
Fee/weight calculation omits the OP_RETURN data output, producing an under-calculated `needed_fee` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds the output set with an optional OP_RETURN `data` output, but when estimating the transaction weight/vbytes for the fee it calls `calculate_weight_vbytes(tx_ins.len(), payments, None)` — passing only `payments`, which excludes the OP_RETURN output already pushed into `tx_outs`. This is the same bug class as the reference report: a quantity that should be `base + delta` (all outputs, including the added one) is computed from only the partial component, so the derived value (`needed_fee`, and the change amount that depends on it) is silently too small.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the weight estimation: [1](#0-0) 

The subsequent calls at lines 204 and 225–226 pass `payments` (the caller-supplied payment list) into `calculate_weight_vbytes`, which builds a model `Transaction` containing exactly those outputs: [2](#0-1) 

Since the OP_RETURN output (8-byte value + varint + up to ~83-byte script) is never in `payments`, the computed `weight`/`vbytes` underestimate the real transaction, so `needed_fee = fee_per_vbyte * vbytes` is too low. When change is used, the change output value `input_sat - payment_sat - fee_with_change` is correspondingly too large, and the actual fee paid (`sum(inputs) - sum(outputs)`, per `fee()`) equals this underestimated amount rather than the requested rate. The `TooLowFee` check at line 211 is also evaluated against the underestimated `vbytes`, so a data-carrying transaction whose *real* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` can pass validation. [3](#0-2) 

### Impact Explanation
Any caller passing `data` gets a signed transaction paying a lower fee rate than `fee_per_vbyte` specified. In the worst case the real fee rate drops below the minimum relay fee: the fully-signed Taproot transaction will be rejected by `send_raw_transaction`/mempool policy, leaving the referenced inputs allocated to an unbroadcastable transaction — funds committed to an output set that is not spendable on-chain as constructed. Even when relayable, the change output is overvalued and the fee underpaid relative to the caller's explicit requirement. Medium severity: reachable purely through the public `data` argument, with a concrete correctness failure (signed TX violating the requested fee floor), but no key/share compromise.

### Likelihood Explanation
Triggered deterministically whenever `SignableTransaction::new` is invoked with `Some(data)` — no adversarial timing or validator misbehavior required. Whether it causes a relay rejection depends on margin: with `fee_per_vbyte` near the minimum or with large (up to 80-byte) data payloads, the ~10–90 WU underestimate can push the real rate under the floor. The processor currently passes `data: None` (`make_signable_transaction`), so impact is confined to direct users of the in-scope wallet API, lowering breadth but not the underlying defect.

### Recommendation
Include all outputs in the fee model. Either compute weight from the final `tx_outs` (e.g., pass a slice built from `tx_outs` plus the pending change output) or push the OP_RETURN `TxOut` into the model before `calculate_weight_vbytes` is called — i.e., compute `vbytes` over `payments + data output (+ change)`, the analog of assigning `splitterEthBalance + amountsOut[1]` rather than `amountsOut[1]` alone. The `TooLowFee` check and change-value computation must use the same complete output set.

### Proof of Concept
```rust
// Conceptual: one input worth `v` sats, one payment, 80-byte OP_RETURN data.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(inputs, &payments, Some(change), Some(data), fee_per_vbyte)?;
// Model used for needed_fee contains only `payments` (+ change).
// Real tx additionally carries the OP_RETURN output (~+40 vbytes at 80-byte payload).
// needed_fee = fee_per_vbyte * vbytes(without OP_RETURN)
// actual fee = sum(inputs) - sum(tx.output) == needed_fee  (change absorbs the difference)
// => effective rate = actual_fee / real_vsize < fee_per_vbyte.
// With fee_per_vbyte at/below ~1 sat/vb, real rate < DEFAULT_MIN_RELAY_TX_FEE,
// yet the check at line 211 passed because it used the smaller vbytes.
```
