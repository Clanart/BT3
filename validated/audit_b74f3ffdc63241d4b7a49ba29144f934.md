## Title
Relayer fee liabilities (`Fees` map) are denominated in the old `feeToken` but paid out in the new one after `updateHostParams` changes it, because the change-guard only checks the host's own token balance - ([File: evm/src/core/EvmHost.sol], [File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
This is the local analog of the reported "accounting issues after underlying asset change" bug. `EvmHost.updateHostParamsInternal()` allows governance to change `feeToken`, guarded only by a check that the host contract's own balance of the *old* fee token is zero. That guard has no visibility into liabilities recorded on the separate Hyperbridge chain: relayers accrue unclaimed reward balances in `pallet-relayer`'s `Fees` storage, denominated in fee-token units at accrual time. `withdrawal.rs` always looks up the *current* `HostParams::fee_token` when building the payout message, so a fee-token change silently reinterprets a previously-accrued balance as an amount of the new token, at the same nominal (not equivalent-value) amount.

### Finding Description
`EvmHost.updateHostParamsInternal()` performs this check before allowing a fee-token change: [1](#0-0) 

```
address oldFeeToken = feeToken();
if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
    uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
    if (balance != 0) revert CannotChangeFeeToken();
}
```

This only proves the *host contract's own* old-token balance is zero. It says nothing about relayer reward liabilities that are tracked entirely off-chain-from-the-host's-perspective, in `pallet-relayer::Fees` on the Hyperbridge parachain: [2](#0-1) 

The `available_amount` here was accrued via `accumulate_fees`/state proofs of `RequestPayments` (fees paid by users in the fee token that was live on the destination chain at request time), and it is a raw numeric balance with no record of which token or its decimals it corresponds to.

When the relayer later calls `withdraw`, the pallet fetches the *current* `HostParams` (post fee-token-change) and builds the withdrawal body with `token: params.fee_token` (the NEW token) but `amount: available_amount` (denominated against the OLD token): [3](#0-2) 

The destination `EvmHost.withdraw()` just blindly transfers the specified token/amount with no further validation: [4](#0-3) 

So exactly like the H-07 report: the "cached asset amount" (`claimableAssetFees` there, `Fees::<T>` here) survives an underlying-asset swap, and the reset/guard logic (`if (profit == 0) return` there, `balanceOf(oldFeeToken) == 0` here) is insufficient to guarantee the stale amount is actually zero or reconciled, because it only inspects local host-contract state and misses liabilities recorded on the counterparty chain.

### Impact Explanation
Any relayer with an un-withdrawn `Fees` balance at the moment governance rotates `feeToken` on a destination `EvmHost` will, upon withdrawal, be paid the same raw integer amount but in a different ERC-20 (potentially different decimals/value). This is a direct violation of the "relayer rewards must move exactly once and only to the rightful beneficiary and amount" invariant: the relayer can be overpaid (draining the new fee-token treasury of value it never should have received) or underpaid (losing legitimate rewards), and the host has no mechanism to detect or correct this since the liability lives entirely in `pallet-relayer` storage on a different chain.

### Likelihood Explanation
Medium: it requires a legitimate, authorized `updateHostParams` fee-token rotation (a supported operational action, not requiring a malicious actor) to occur while any relayer has an outstanding, unclaimed `Fees` balance for that destination chain — a realistic operational scenario since fee-token rotations are explicitly supported and relayers are not required to withdraw immediately after each accrual.

### Recommendation
Before allowing a `feeToken` change in `EvmHost.updateHostParamsInternal`, or as part of the governance flow that dispatches the `SetHostParam` request, require that all outstanding relayer `Fees` liabilities for that destination state machine on Hyperbridge be zero (or forcibly settled/migrated) — not merely that the host contract's own token balance is zero. Alternatively, have `pallet-relayer` record the fee-token address (or a value-normalized amount) alongside each accrued `Fees` entry, and reject/convert withdrawals whose recorded token no longer matches the destination's current `fee_token`.

### Proof of Concept
1. Relayer accrues a reward of `X` units of `feeToken = TokenA` for `dest_chain = EVM-1` via `accumulate_fees`, recorded in `Fees::<T>[EVM-1][relayer] = X`.
2. Governance drains `TokenA` from the `EVM-1` host (e.g., via `withdraw`) to make `balanceOf(TokenA) == 0`, satisfying `updateHostParamsInternal`'s guard, and rotates `feeToken` to `TokenB` (e.g., different decimals/value) via `updateHostParams`.
3. Relayer calls `withdraw_fees`; `withdrawal.rs` reads the now-current `HostParams::fee_token = TokenB` and dispatches `WithdrawalParams{ token: TokenB, amount: X, ... }`.
4. `EvmHost.withdraw()` transfers `X` units of `TokenB` to the relayer — a value mismatched from the originally accrued `X` units of `TokenA`, with no on-chain check preventing this.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
