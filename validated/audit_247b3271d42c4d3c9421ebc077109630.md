### Title
Aggregate Schnorr verifier weights bind only challenges, letting a forger satisfy the batch equation for keys that never signed - (File: crypto/schnorr/src/aggregate.rs)

### Summary

`SchnorrAggregate::verify` computes per-signature weights `z_i` from a transcript that commits only to the destination tag and the list of *challenges* — never to the signatures' `R_i` points, the public keys, or `s`. Because every term except `R_i` is attacker-chosen or public before the weight is needed, an attacker can solve for the final `R_n` to make the multiexp sum to identity, producing an "aggregate signature" that verifies even though no valid individual signature exists.

### Finding Description

In `crypto/schnorr/src/aggregate.rs` (lines 127–145):

```rust
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, challenge) in keys_and_challenges {
  digest.append_message(b"challenge", challenge.to_repr());
}
...
for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
  let z = weight(&mut digest);
  pairs.push((z, self.Rs[i]));
  pairs.push((z * challenge, *key));
}
pairs.push((-self.s, C::generator()));
multiexp_vartime(&pairs).is_identity()
```

The verification equation is `Σ z_i·R_i + Σ z_i·c_i·K_i − s·G == 0`. For half-aggregation (eprint 2021/350) to be secure, each weight `z_i` must be bound to the *entire signature content* (all `R`s, keys, and `s`) so the attacker cannot choose `R_i` after learning `z_i`. Here `z_i` is derived solely from `dst` and the challenges — all public, fixed inputs. This is the analog of the OpenClaw flaw: the random weight is the "pending approval" gate on the batch equation, and it is effectively overridden because it isn't bound to the data it is supposed to guard.

`SchnorrAggregate::read` (lines 77–88) accepts untrusted bytes for `Rs` and `s`, and `verify` is a `#[must_use]` boolean API directly reachable with attacker-controlled input.

### Impact Explanation

A forger produces a `SchnorrAggregate` that passes `verify` for a set of keys whose owners never produced signatures. Concretely: given public keys `K_1..K_n` and challenges `c_1..c_n` (caller-computed, binding key+message), the attacker picks any `s`, picks arbitrary points for `R_1..R_{n-1}`, and sets

`R_n = (s·G − Σ_{i<n} z_i·R_i − Σ_{i<n} z_i·c_i·K_i − z_n·c_n·K_n) · z_n^{-1}`

All `z_i` are computable publicly from `dst || challenges`, so `R_n` is a well-defined point the attacker encodes into the signature. The multiexp then sums to identity and `verify` returns `true` — a forged aggregate signature over victim keys. Any caller treating a passing `verify` as "all n signers signed their challenges" is convinced of signatures that do not exist.

### Likelihood Explanation

Reachable by an unprivileged party: the attack only needs to submit bytes to `SchnorrAggregate::read`/`verify` — exactly the untrusted-bytes surface in scope. The forgery is deterministic and works for any key set and challenge list; no malformed encodings, no secret knowledge, and no interaction with the victims are required. It does require the attacker to control (or append) the last entry's `R_n`, which is always satisfiable since the attacker constructs the entire aggregate. Severity is bounded by the need for a caller to aggregate signatures for challenges/keys rather than verify individually, but when this API is used it produces a concrete forged-signature acceptance — Medium-to-High impact consistent with the bug class.

### Recommendation

Bind each weight to the full aggregate content. Before drawing weights, append to the digest: every `R_i` (`R.to_bytes()`), every public key, and `s` — or better, derive `z_i` per-signature from a transcript committing to `(R_i, K_i, c_i)` plus a transcript-level commitment to the whole aggregate, matching the "partially deterministic" weight scheme of eprint 2021/350 section on half-aggregation. E.g.:

```rust
digest.domain_separate(b"signatures");
for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
  digest.append_message(b"R", self.Rs[i].to_bytes());
  digest.append_message(b"key", key.to_bytes());
  digest.append_message(b"challenge", challenge.to_repr());
}
digest.append_message(b"s", self.s.to_repr());
```

Alternatively, document and enforce that `verify` is only sound when callers commit `z` inputs themselves — though fixing the transcript is the correct gate.

### Proof of Concept

Sketch against `crypto/schnorr/src/aggregate.rs`:

```rust
// Victim keys K1, K2 and challenges c1, c2 (e.g. honest signing oracles' params)
let ks_cs = [(K1, c1), (K2, c2)];

// Recompute the weights exactly as verify() does
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, c) in &ks_cs { digest.append_message(b"challenge", c.to_repr()); }
let z1 = weight(&mut digest);
let z2 = weight(&mut digest);

// Attacker-chosen s and R1
let s = C::F::random(&mut OsRng);
let R1 = C::generator() * C::random_nonzero_F(&mut OsRng);

// Solve the batch equation for R2
let R2 = (C::generator() * s - R1 * z1 - K1 * (z1 * c1) - K2 * (z2 * c2))
           * z2.invert().unwrap();

let agg = SchnorrAggregate { Rs: vec![R1, R2], s };
assert!(agg.verify(dst, &ks_cs)); // passes despite neither signer having signed
```

Neither `K1` nor `K2`'s owner ever produced a signature share; the equation is satisfied purely by construction of `R2`. Relevant code: `crypto/schnorr/src/aggregate.rs` lines 127–145 (transcript omits `Rs`, keys, and `s`) and `crypto/multiexp/src/batch.rs` shows the same-weight model is only safe when weights are bound after inputs are fixed.
