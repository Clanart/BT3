### Title
Coinbase outputs are reported as spendable `ReceivedOutput`s, letting an unprivileged miner lock funds in an unspendable-transaction attempt - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase transaction (`block.txdata[0]`). `ReceivedOutput`s derived from a coinbase output are indistinguishable from normal outputs: `SignableTransaction::new` and `SignableTransaction::multisig` will accept them as inputs and produce a fully-signed transaction spending an immature coinbase. Bitcoin consensus requires coinbase outputs to mature for 100 blocks; the resulting transaction is invalid and rejected by the network. Any miner can trigger this with no special privilege: they simply point their coinbase payout (or a coinbase output) at the Serai P2TR `script_pubkey`, which is public knowledge. The wallet reports funds "received" that cannot actually be spent, and the signed spend of them is consensus-invalid.

### Finding Description
`scan_block` iterates over all transactions unconditionally: [1](#0-0) 

The doc comment acknowledges maturity ("If received outputs must be immediately spendable, a post-processing pass is needed") but the library performs no maturity check itself, and `scan_transaction` — the only alternative — still treats each output identically, with no marker that an outpoint originated in a coinbase.

Downstream, `SignableTransaction::new` consumes `inputs: Vec<ReceivedOutput>` and builds the spend with no awareness of coinbase status: [2](#0-1) 

`multisig` validates only that the offset key matches the input's `script_pubkey`, and `TransactionSignMachine::sign` signs `Prevouts::All` sighashes for every input — an immature coinbase prevout is included and signed like any other: [3](#0-2) [4](#0-3) 

### Impact Explanation
- The scanner reports a `ReceivedOutput` whose funds are not spendable — the analog of the report's "prize locked, no way to transfer".
- Worse, the output is poisoned, not just immature-but-eventually-spendable from the caller's view unless the caller separately tracks maturity: if it is bundled into `SignableTransaction::new` alongside other inputs, the *entire* transaction is consensus-invalid (BIP-30/COINBASE_MATURITY rule), so the other legitimate inputs' spend also fails. The threshold signing round is wasted and must be redone after 100 blocks, and a naive caller that treats the scan result as final accounting will permanently misreport the balance.
- Unlike the Ethereum case, funds are recoverable after maturity — but only if the integrator implements the post-processing pass the comment mentions; nothing in the API enforces it, and `scan_block` is the natural API to call.

### Likelihood Explanation
Low-to-moderate. It requires a miner to include an output paying the Serai script in a coinbase (or a miner paying a pool member who crafts the payout), which is cheap and requires no privilege — miners routinely set arbitrary coinbase outputs. Whether damage occurs depends on the integrator calling `scan_block` rather than filtering coinbase transactions. In-scope severity is Medium: funds are not permanently lost, but the wallet emits "received, spendable" outputs that are not spendable and will cause signed transactions to be rejected.

### Recommendation
Have `scan_transaction`/`scan_block` detect coinbase inputs (`tx.is_coinbase()` / `input.previous_output.is_null()`) and either skip those outputs or flag the `ReceivedOutput` as immature (e.g., add a `maturity: Option<u64>` or a `is_coinbase` marker). `SignableTransaction::new` should reject coinbase-sourced `ReceivedOutput`s unless a block-height/maturity parameter confirms they are spendable. At minimum, refuse to sign them in `multisig`.

```rust
    vec![outputs[0].clone()],
    &payments, Some(change), None, fee_rate,
).unwrap(); // send.rs:150 — accepted, no maturity check
let tx = sign(&keys, &stx); // multisig/send.rs:273 + sign() produce valid witnesses

```

I could not fully verify (within the remaining tool budget) whether the processor's `get_outputs` path filters `txdata[0]` before reaching `Scanner`; the in-scope wallet code itself unconditionally scans the coinbase transaction, and the finding stands on `networks/bitcoin/src/wallet/mod.rs` and `send.rs` alone.
