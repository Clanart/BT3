### Title
OP_RETURN data output is excluded from the fee/weight calculation, underpaying the requested fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the required fee from a transaction skeleton built only from `payments`, while the actual transaction additionally includes an OP_RETURN output whenever `data` is specified. Any caller that attaches data therefore bypasses the fee charged on those bytes — the analog of Y2K's deposit queue path skipping the deposit fee.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before the fee is computed, but `calculate_weight_vbytes` is invoked with `payments` — a list that does not contain the data output [1](#0-0) . The same omission occurs for the change-bearing estimate, which again passes only `payments` [2](#0-1) . `calculate_weight_vbytes` builds the weight-estimation transaction exclusively from `tx.output = payments`, so up to 80 bytes of caller-controlled data plus output overhead (~10 bytes) contribute zero to `needed_fee` [3](#0-2) .

Consequences:
- `needed_fee()` and `fee()` diverge from the intended `fee_per_vbyte * actual_vsize`; the transaction broadcasts an effective feerate strictly below the requested one whenever `data.is_some()`.
- The minimum-relay-fee check is evaluated against the underestimated `vbytes`, so a transaction whose true vsize would fail `TooLowFee` is still constructed [4](#0-3) .
- The change computation `input_sat - (payment_sat + fee_with_change)` uses the underestimated `fee_with_change`, so the change output is credited the sats that should have paid for the data output's weight — i.e., the fee for carrying data is silently skipped rather than charged [5](#0-4) .

### Impact Explanation
Any transaction carrying an OP_RETURN payload underpays the network fee relative to the caller-requested rate, and `needed_fee()` misreports the required fee. When change is present, the unpaid weight is absorbed into the change output, so the caller effectively receives a fee discount of up to ~`fee_per_vbyte * (80 + output_overhead)` sats while still producing a broadcastable but mis-priced transaction. In the processor flow this path is currently unreachable (`data` is always `None`) [6](#0-5) , but `SignableTransaction` is a public wallet API and any consumer attaching data gets a systematically wrong fee.

### Likelihood Explanation
Deterministic whenever `data` is supplied to `SignableTransaction::new`; no adversarial setup required. Likelihood of real-world loss is gated on a consumer using the `data` parameter, which the in-repo processor does not currently do, keeping this at Medium rather than High.

### Recommendation
Pass the full output list (including the OP_RETURN output) into `calculate_weight_vbytes`, e.g. compute weight/vbytes from `tx_outs` after the data output is pushed, and pass `tx_outs` (or an `extra_outputs` slice) in the change-bearing recalculation as well, so `needed_fee` and the `TooLowFee` check reflect the transaction actually built.

### Proof of Concept
```rust
// Conceptual: two otherwise identical transactions, one with data
let no_data = SignableTransaction::new(inputs.clone(), &payments, Some(change.clone()), None, FEE).unwrap();
let with_data = SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0u8; 80]), FEE).unwrap();
// with_data.needed_fee() == no_data.needed_fee(), yet with_data serializes ~90 bytes larger.
// Its actual feerate = needed_fee / actual_vsize < FEE, and if FEE were the minimum relay rate,
// the resulting TX would fall under DEFAULT_MIN_RELAY_TX_FEE despite passing the TooLowFee check.
```
