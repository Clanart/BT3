### Title
Validator reward permanently burned to zero address when `RewardAddr` is unset/zero due to missing fallback in staking reward allocation - (File: kaiax/reward/impl/getter.go)

### Summary
The Kaia reward module (`kaiax/reward`) distributes minting and fee rewards to validators based on `StakingInfo.RewardAddrs`, which is populated from the AddressBook contract's per-node reward address (settable via `AddressBookV2.updateRewardAddress`, exposed in [1](#0-0) ). While the reward-allocation code explicitly falls back to the block proposer when the pool-level fund addresses (KIF/KEF/KPF) are empty, it performs no equivalent zero-address check for individual validator/staker reward addresses before crediting balances, mirroring the reported bug class of a fee/reward recipient that can silently become unrecoverable.

### Finding Description
`assignStakingRewards` and `assignStakingRewardsFlex` compute per-validator staking rewards keyed by `cn.RewardAddr` and directly insert them into the allocation map without validating that the address is non-zero: [2](#0-1) 

Contrast this with the explicit, deliberate zero-address handling that exists for the fund addresses (KIF/KEF/KPF), which redirect their portion to the proposer when unset: [3](#0-2) 

No such fallback exists for `cn.RewardAddr` (the individual validator's reward address). The allocation is later applied unconditionally in `FinalizeState`: [4](#0-3) 

`RewardSpec.IncRecipient`/`Validate` also do not reject a zero-address recipient — they only check that amounts are non-negative: [5](#0-4) 

The reward address itself is sourced from `StakingInfo.RewardAddrs`/`RewardAddr`, which is populated straight from the AddressBook/CL registry read without filtering out zero addresses: [6](#0-5) 

The on-chain entrypoint that sets this value, `AddressBookV2.updateRewardAddress(nodeId, newRewardAddress)`, is reachable by the node's registered account (a staker/validator operator persona explicitly in-scope) as a directly submitted transaction: [7](#0-6) 
Because the actual Solidity source of `AddressBookV2` is not present in this index (only the generated Go bindings), I could not directly confirm from source whether `updateRewardAddress` itself enforces a non-zero check on-chain; this is a limitation of the available index, not a confirmed absence. However, even if the contract validated the input, the consuming reward-distribution logic in `kaiax/reward` has no independent zero-address guard/fallback for `RewardAddr`, unlike its symmetric treatment of KIF/KEF/KPF, which is the analogous root cause to the audited issue (a fund/recipient address that can end up unusable with the protocol offering no correction path).

### Impact Explanation
If a validator's `RewardAddr` is or becomes the zero address (via misconfiguration, incomplete registration, or a bug in the on-chain update flow), every subsequent minting reward, staking reward, and (post-Prague) consensus-liquidity split destined for that validator is credited via `state.AddBalance(common.Address{}, amount)` — i.e., burned to the zero address every block. This is an irreversible loss of validator rewards analogous to the reported "losing of all pool fees" issue: value is permanently and silently destroyed rather than reaching the intended party, with no update/recovery function in the reward module itself to redirect it (unlike the explicit KIF/KEF/KPF fallback-to-proposer design).

### Likelihood Explanation
Medium. It requires an operator error or a validator registering/updating its reward address to the zero address (or the AddressBook returning empty addresses for a consolidated node, which the code apparently permits since only KIF/KEF/KPF are explicitly special-cased). This is not attacker-forced against another party's funds, but is a realistic misconfiguration path reachable by a permitted persona (staker/node operator submitting an on-chain transaction) with no automatic protocol-level safeguard, distinguishing it from a pure operator-only/no-impact issue.

### Recommendation
Add an explicit `common.EmptyAddress(cn.RewardAddr)` check in `assignStakingRewards`/`assignStakingRewardsFlex` (and in the proposer-reward path keyed by `config.Rewardbase`) mirroring the existing KIF/KEF/KPF fallback: redirect any reward destined to a zero/empty reward address to a safe recipient (e.g., the proposer, or exclude the CN from staking-reward apportionment and redistribute its share), and add defensive validation in `RewardSpec.Validate()`/`IncRecipient` to reject or flag zero-address recipients before `state.AddBalance` is called in `FinalizeState`.

func (spec *RewardSpec) IncRecipient(addr common.Address, amount *big.Int) {
	_, ok := spec.Rewards[addr]
	if !ok {
		spec.Rewards[addr] = big.NewInt(0)
	}
	spec.Rewards[addr].Add(spec.Rewards[addr], amount)
}

func (spec *RewardSpec) Validate() error {
	for addr, amount := range spec.Rewards {
		if amount.Sign() < 0 {
			return errNegativeRewardAmount(addr, amount)
		}
	}
	return nil
}
