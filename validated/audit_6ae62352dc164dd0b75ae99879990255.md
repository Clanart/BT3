### Title
Unhandled non-`ValueError`/`ValidationError` exceptions from spend bundle validation propagate uncaught out of `add_transaction`, risking a spend-triggered transaction-processing halt - (File: chia/full_node/full_node.py)

### Summary
The external report flags `ChainlinkAdapterOracle.getPrice()` for calling an external dependency (Chainlink registry) without a defensive try/catch, so a single failure in that external call halts price-dependent processing (DoS). The analogous pattern in this codebase is `FullNode.add_transaction()`, which calls into `MempoolManager.pre_validate_spendbundle()` — a routine that executes attacker-supplied CLVM/BLS validation in a worker process — but only defensively catches `ValueError` and `ValidationError`. Any other exception type raised from that validation path is allowed to propagate all the way out of `add_transaction()` uncaught.

### Finding Description
`FullNode.add_transaction()` wraps the call to `self.mempool_manager.pre_validate_spendbundle(...)` in a narrow exception handler: [1](#0-0) 

Only `ValueError` (converted to a soft `INVALID_SPEND_BUNDLE` failure) and `ValidationError` (kept in the seen-cache) are treated as expected outcomes of validating attacker-supplied spend-bundle content. Everything else — e.g. a bug or edge case surfaced inside `validate_clvm_and_signature`, BLS cache update, or the atoms/pairs bookkeping in `pre_validate_spendbundle` — is not caught here and re-raises out of `add_transaction`.

This is explicitly confirmed by the test suite, which documents the exact behavior: when `pre_validate_spendbundle` raises a `RuntimeError` (representing "an unexpected exception"), the test asserts that the exception propagates all the way out of `add_transaction()` rather than being converted into a `FAILED` status: [2](#0-1) 

`add_transaction()` is the function invoked for every peer-submitted or RPC-submitted (`/push_tx`) spend bundle, and per the module's own contract notes, transaction admission is dequeued and processed per-item from `TransactionQueue`/`PeerTransactionsQueue` (`chia/full_node/tx_processing_queue.py`), which round-robins between peers' pending transactions. If the coroutine/task driving that dequeue loop calls `add_transaction()` directly inside its own iteration without a blanket `except Exception`, an uncaught exception raised from a single crafted spend bundle can terminate that processing task.

### Impact Explanation
If the task or loop that repeatedly calls `add_transaction()` for incoming peer transactions has no top-level catch-all around this call (which is consistent with the narrow `except ValueError` / `except ValidationError` seen here and mirrored in the `respond_transaction` handler pattern), a single spend bundle that triggers a non-`ValueError` exception anywhere inside `pre_validate_spendbundle`/`validate_clvm_and_signature` can kill that task. Because this is the single admission path for all subsequent transactions from that queue/peer, it results in a spend-triggered halt of transaction processing — matching the "spend-triggered transaction-processing halt" impact class from the validation rules, analogous to the Chainlink DoS pattern where a single external-call failure blocks all subsequent processing.

### Likelihood Explanation
Reachability is high in principle: any unprivileged party who can submit a spend bundle (via P2P `RespondTransaction`, or RPC `/push_tx`) can attempt to trigger this path. However, this analysis could not fully verify (within tool/time limits) whether the specific outer task loop consuming `TransactionQueue` entries has its own blanket exception handler around the `add_transaction()` call that would prevent a full loop crash (i.e., whether the failure is scoped per-task-per-transaction and would just need a new task spawned, versus corrupting a persistent shared loop). This uncertainty affects whether the impact is a full sustained DoS versus a transient one-off failure per malformed bundle. Actually triggering the uncaught-exception condition also requires finding a concrete input that causes an exception type other than `ValueError`/`ValidationError` inside the CLVM/BLS validation pipeline, which was not independently confirmed to exist as a currently-exploitable code path — only that the exception-handling gap itself is real and test-documented.

### Recommendation
Broaden the exception handling in `FullNode.add_transaction()` (and any other callers on the transaction-admission path, e.g. `respond_transaction`) to catch unexpected exceptions from `pre_validate_spendbundle`/`validate_clvm_and_signature` defensively, converting them into a `FAILED`/`Err.UNKNOWN` result (as is already done in `_pre_validate_block`'s `except Exception:` fallback, see `chia/consensus/multiprocess_validation.py` lines 190-193) rather than letting them propagate out of the per-transaction processing task. This ensures a single malformed/adversarial spend bundle cannot take down the task or loop responsible for servicing the shared transaction queue for all peers.

### Proof of Concept
1. An unprivileged peer or RPC caller submits a spend bundle designed (or, more realistically, happens) to trigger an exception type other than `ValueError`/`ValidationError` somewhere inside the CLVM-execution/BLS-cache path invoked by `MempoolManager.pre_validate_spendbundle()`.
2. `FullNode.add_transaction()` only catches `ValueError`/`ValidationError` around this call: [1](#0-0) 
3. The exception propagates out of `add_transaction()`, as confirmed by the test harness explicitly exercising and asserting this exact propagation behavior: [3](#0-2) 
4. If the caller of `add_transaction()` in the live transaction-queue processing loop lacks its own catch-all, the task servicing that queue dies, halting further processing of queued transactions until externally restarted/re-spawned.

@pytest.mark.anyio
async def test_add_transaction_remove_seen_on_unexpected_exception(
    one_node_one_block: tuple[FullNodeSimulator, ChiaServer, BlockTools],
) -> None:
    """When pre_validate_spendbundle raises an unexpected exception, the
    seen-cache entry must be removed and the exception re-raised."""
    full_node_1, _server_1, _bt = one_node_one_block
    fn = full_node_1.full_node

    spend_bundle = make_spend_bundle(1)
    spend_name = spend_bundle.name()

    original_pre_validate = fn.mempool_manager.pre_validate_spendbundle

    async def raise_runtime_error(*_args: Any, **_kwargs: Any) -> SpendBundleConditions:
        raise RuntimeError("simulated unexpected failure")

    fn.mempool_manager.pre_validate_spendbundle = raise_runtime_error  # type: ignore[method-assign]
    try:
        with pytest.raises(RuntimeError, match="simulated unexpected failure"):
            await fn.add_transaction(spend_bundle, spend_name, test=True)
    finally:
        fn.mempool_manager.pre_validate_spendbundle = original_pre_validate  # type: ignore[method-assign]

    assert not fn.mempool_manager.in_flight(spend_name)
    assert not fn.mempool_manager.seen(spend_name)
