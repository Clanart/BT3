### Title
Governance-settable `Kip71GasTarget` accepts 0 with no `FormatChecker`, causing division-by-zero panic in `NextMagmaBlockBaseFee` - (File: params/kip71_config.go)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` when the parent block's gas usage differs from `gasTarget`, but the governance parameter `Kip71GasTarget` that supplies this value has no format/validation check preventing `0`, unlike the sibling `Kip71BaseFeeDenominator` parameter which explicitly rejects `0` and even has an in-code fallback guard for the zero case.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee (KIP-71 dynamic pricing) using `gasTarget := kc.GasTarget` as a divisor: [1](#0-0) 

Notice the code explicitly guards against a zero `BaseFeeDenominator` ("To avoid panic, set the fluctuation range small") but performs no equivalent guard for `gasTarget`: [2](#0-1) 

If `parentGasUsed != gasTarget` (guaranteed true whenever `gasTarget == 0` and any gas was used, or even when `parentGasUsed == 0` and `gasTarget == 0`... actually when both are 0 they are equal and this path is skipped, but any nonzero `parentGasUsed` with `gasTarget == 0` triggers the "used more than target" branch), the code executes:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 -> panic: division by zero
```
This is a Go runtime panic (`big.Int` division by zero panics rather than returning an error), which occurs inside consensus-critical block-header validation/assembly code (`VerifyMagmaHeader` calls `NextMagmaBlockBaseFee`), executed by every node validating or building a block.

The governance parameter itself is defined with no bounds check: [3](#0-2) 

and in `kaiax/gov/param.go`'s parameter table, `Kip71GasTarget` uses `noopFormatChecker` (no validation at all), in contrast to `Kip71BaseFeeDenominator`, which explicitly checks `v != 0`. This asymmetry mirrors exactly the bug class in the referenced Tokemak report: a value that can legitimately be `0` is used unguarded as a divisor elsewhere in the code, while a structurally similar sibling value received the safety check.

### Impact Explanation
If `Kip71GasTarget` is ever set to `0` (via a governance vote, or via a misconfigured/incorrect genesis/chain-config value), every node computing the next block's base fee under the "gas used ≠ target" branches will panic. Since base-fee calculation happens during block validation and block building (`FinalizeState`/header verification), this is a **network-wide consensus-halting condition** — all honest nodes attempting to validate or produce the next block would crash or diverge, rather than gracefully rejecting an invalid parameter. This falls squarely into the "state divergence between honest nodes / acceptance of invalid block" impact category, since one path (e.g., a node using a cached/stale target) could behave differently, and importantly the entire network would halt (denial of service at the protocol level) rather than only a single actor being harmed.

### Likelihood Explanation
The likelihood depends on whether `Kip71GasTarget = 0` can actually be voted in or configured. The `FormatChecker` for this parameter is `noopFormatChecker`, meaning the governance-vote validation layer performs no rejection of `0` (or any other value) for this parameter, whereas the adjacent `BaseFeeDenominator` parameter is explicitly hardened against `0`. This indicates a real oversight rather than an intentional design choice. Because governance-parameter changes are still gated behind the governance/voting mechanism (validator/governing-node privilege), this is not exploitable by a fully unprivileged externally-owned account in a single transaction; it requires a governance vote to succeed, or an operator/genesis misconfiguration. This reduces the practical likelihood but does not eliminate the underlying code defect — the validation layer that is supposed to protect the network accepts an unsafe value.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and `Kip71MaxBlockGasUsedForBaseFee`/`Kip71UpperBoundBaseFee` if similarly unguarded) that rejects `0`, consistent with the existing `Kip71BaseFeeDenominator` check (`v != 0`). Additionally, as defense-in-depth, add the same "avoid panic" fallback in `NextMagmaBlockBaseFee` for `gasTarget == 0` that already exists for `BaseFeeDenominator == 0`, so that a corrupted or legacy config value cannot crash node consensus code.

### Proof of Concept
1. Set chain config (or push a governance vote, depending on `GovernanceMode`) so that `Governance.KIP71.GasTarget = 0`.
2. Produce/validate any block where `parentHeaderGasUsed > 0` (i.e., any transaction consumed gas in the parent block).
3. `NextMagmaBlockBaseFee` executes the `parentGasUsed > gasTarget` branch:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - 0)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(0)) // panics: division by zero
```
This can be directly reproduced by calling `KIP71Config.NextMagmaBlockBaseFee(parentNum, parentBaseFee, parentGasUsed)` with `GasTarget: 0` and any nonzero `parentGasUsed`, analogous to the existing test harness in `params/kip71_config_test.go` (`TestNextBlockBaseFee`), but supplying `GasTarget = 0`. [4](#0-3)
