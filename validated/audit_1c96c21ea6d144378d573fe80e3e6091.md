## Analysis

The external Sherlock report concerns `RioLRTIssuer::issueLRT` blindly trusting that `ERC20.approve()` returns a `bool`, which reverts for non-standard tokens (e.g., USDT) that return no data. This repository (`Annirich/push-chain-evm--013`, a Cosmos EVM chain) contains a directly analogous pattern in its native-Go-to-EVM bridge code, but with a materially worse, Critical-severity consequence: permanently stuck user funds instead of a mere revert.

### Comparison of the two ABI-unpack call sites

The `x/erc20` module's own `ConvertCoinNativeERC20`/`convertERC20IntoCoinsForNativeToken` correctly defends against non-bool-returning `transfer` calls: [1](#0-0) 

But the destination IBC callback handler, which sets an ERC20 allowance for a native ERC20 token pair before invoking a user-supplied contract, has no such fallback and unconditionally unpacks a `bool` from the `approve` return data: [2](#0-1) 

If `res.Ret` is empty (a non-standard ERC20 that doesn't return a bool from `approve`, exactly like the USDT scenario in the source report), `erc20.ABI.UnpackIntoInterface` errors out and `IBCReceivePacketCallback` returns an error before the target contract can pull the tokens out of the isolated receiver address.

### Title
Non-bool-returning ERC20 `approve` call in `IBCReceivePacketCallback` permanently strands IBC-received tokens at an unrecoverable isolated address - (File: `x/ibc/callbacks/keeper/keeper.go`)

### Summary
`IBCReceivePacketCallback` calls `approve` on a native ERC20 token-pair contract and unconditionally unpacks the return value as a `bool` via `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)`. Unlike the module's own `transfer` handling (which has a `len(res.Ret) == 0` fallback that checks for the `Transfer` event in logs), there is no equivalent fallback for `approve`. Non-standard ERC20 tokens that omit the boolean return value on `approve` (the same class of tokens referenced in the source Sherlock report, e.g. USDT-style tokens) cause this unpack to fail, aborting the callback after the underlying ICS20 transfer has already delivered tokens to a deterministic, non-custodial "isolated address."

### Finding Description
The destination callback flow works as follows:
1. IBC-Go's standard `OnRecvPacket` has already run and minted/unescrowed the transferred coin to the isolated receiver address, per `ConvertCoinNativeERC20`-style logic elsewhere in the module.
2. `IBCReceivePacketCallback` is then invoked to `approve` a downstream contract to pull the tokens and then to actually call that contract: [3](#0-2) 
3. The isolated receiver address is deterministically derived and is explicitly documented as unrecoverable if the flow does not fully drain it: [4](#0-3) 
4. If the token-pair ERC20 contract does not return a `bool` from `approve` (returns no data), `UnpackIntoInterface` fails, the function returns `types.ErrAllowanceFailed`, and the callback aborts before the contract-pull step ever executes. `writeFn()` (which would commit the cached execution context) is never called for this path, so the allowance itself is not even persisted, and the tokens already sitting in the isolated address remain there with no path to move them out, since that address has no known private key and no other entry point moves funds out of it.

This is a structural analog to the report's root cause (assuming the ERC-20 ABI standard return type on `approve`/`transfer` without handling non-compliant tokens), but instead of a benign revert of an issuance transaction (Medium in the original report), the consequence here is unrecoverable freezing of already-transferred user funds — a Critical outcome under this repo's impact gate.

### Impact Explanation
Any IBC transfer of a coin backed by a native ERC20 token pair that does not return `bool` from `approve` will strand the transferred tokens at the isolated receiver address whenever the sender/relayer memo requests a destination callback. Since token pairs for native ERC20 contracts can be registered permissionlessly when `PermissionlessRegistration` is enabled (`RegisterERC20`, `x/erc20/keeper/msg_server.go:324-362`), or via any already-registered non-standard ERC20 token pair, ordinary unprivileged users performing a routine ICS20 transfer-with-callback lose access to their funds permanently — meeting the "permanent freezing/locking/unauthorized... loss of user funds" Critical impact criterion.

### Likelihood Explanation
Triggering this requires only:
- A token pair backed by a native ERC20 contract whose `approve` does not return a bool (a well-known, common non-standard token behavior explicitly called out in the very report this task is seeded from).
- A user or relayer including IBC callback memo data on an ordinary ICS20 transfer to that chain.

No privileged role, validator collusion, or governance action is needed; it is triggered through the normal transaction/IBC packet flow available to any unprivileged user, making the likelihood significant for chains that support such tokens or permissionless ERC20 registration.

### Recommendation
Mirror the pattern already used for `transfer` in `x/erc20/keeper/msg_server.go`: after the `approve` `CallEVM`, check `len(res.Ret) == 0` and, in that case, verify success via the emitted `Approval` event (or otherwise verify allowance was set via a subsequent `allowance()` query) instead of unconditionally unpacking a `bool`. Additionally, consider making the isolated-address recovery path exist (e.g., an escape hatch/refund mechanism) so that any callback failure, regardless of cause, does not result in irrecoverable fund loss.

### Proof of Concept
1. Governance (or a permissionless caller, if `PermissionlessRegistration` is enabled) registers a native ERC20 contract whose `approve(address,uint256)` function returns no data (mirroring the PoC in the source report using a USDT-like implementation) as a token pair via `RegisterERC20`.
2. A user sends an ICS20 transfer of this coin to the chain with `destination callback` memo data pointing at a receiver contract (per `callbacktypes.DestinationCallbackKey`).
3. `OnRecvPacket`/`ConvertCoinNativeERC20` mints/unescrows the ERC20 tokens to the deterministic isolated address for the (channel, sender) pair.
4. `IBCReceivePacketCallback` executes `CallEVM(..., "approve", contractAddr, amount)`; because the token doesn't return a `bool`, `res.Ret` is empty.
5. `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` returns an unpack error, and the function returns `types.ErrAllowanceFailed` without ever calling `writeFn()` or invoking the target contract's pull logic.
6. The tokens remain permanently in the isolated address controlled by nobody, with no built-in mechanism in this file to retry, cancel, or reclaim them.
