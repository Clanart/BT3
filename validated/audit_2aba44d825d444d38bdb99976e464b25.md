### Title
Unauthenticated `superApprove` in `HyperFungibleTokenImpl` allows any attacker to grant unlimited ERC20 allowances over any holder's balance, enabling unrestricted `transferFrom` draining - (File: `evm/src/utils/HyperFungibleTokenImpl.sol`)

### Summary
`HyperFungibleTokenImpl.superApprove(address owner, address spender)` calls `_approve(owner, spender, type(uint256).max)` with no access control and no signature/authorization check on `owner`. Any address can call this function to set an unlimited ERC20 allowance from *any* token holder to *any* spender, including a spender the attacker itself controls, and then drain that holder's balance via `transferFrom`.

### Finding Description
The function is declared `public` with no modifier, no `msg.sender == owner` check, and no role/authorization gate: [1](#0-0) 

Contrast this with every other privileged mutator in the same contract (`mint`, `burn`, `grantMinterRole`, etc.), which are all protected by `onlyRole`: [2](#0-1) 

`superApprove` breaks the fundamental ERC20 invariant that only the token owner (or an already-approved spender) can authorize allowances. An attacker can:
1. Call `superApprove(victim, attackerContract)` directly (no need for it to be a "settlement" contract - the attacker's own address works as `spender`).
2. Call `transferFrom(victim, attacker, victim.balanceOf(victim))` to move the victim's entire balance, repeatable indefinitely since the allowance is `type(uint256).max`.

This is not confined to the "settlement/fill" framing in the question — it is a direct, unauthenticated theft primitive against any holder of this token.

Critically, this contract is not test-only scaffolding: it is deployed as the production fee token in the non-mainnet deployment path of `evm/script/DeployIsmp.s.sol`, where it becomes the `feeToken` used by `EvmHost` for protocol fee accounting: [3](#0-2) 

It is also inherited directly by `FeeToken` used elsewhere: [4](#0-3) 

### Impact Explanation
Any unprivileged attacker can steal the entire balance of any holder of this token (including protocol fee balances, faucet-minted user balances, or any deployment of `HyperFungibleTokenImpl`/`FeeToken`) by self-granting an unlimited allowance and calling `transferFrom`. This is direct, unauthorized asset movement/theft of funds, matching the "stealing or loss of funds" / "unauthorized transaction or execution" impact categories.

### Likelihood Explanation
Trivial and always exploitable: `superApprove` requires no prior state, no proof, no relayer, and no privileged role — a single unprivileged transaction sets the allowance, and a second transferFrom call drains funds. No mitigating check exists anywhere in the call path.

### Recommendation
Remove `superApprove` entirely from production code, or, if retained for test convenience, restrict it to `msg.sender == owner` (self-approval only) or gate it behind an `onlyRole`/test-only compilation flag, and ensure it is never linked into any contract that is deployed with real user balances (e.g. exclude it from `HyperFungibleTokenImpl` used by `DeployIsmp.s.sol`/`FeeToken`).

### Proof of Concept
1. Attacker (no special role) calls `token.superApprove(victim, attacker)`.
2. `allowance(victim, attacker)` is now `type(uint256).max`.
3. Attacker calls `token.transferFrom(victim, attacker, token.balanceOf(victim))`, draining the victim's full balance without any prior approval from the victim.
4. Repeat for any other holder — no per-victim consent or signature is ever checked.
