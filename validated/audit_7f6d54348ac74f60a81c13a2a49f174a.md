### Title
Payout OP_RETURN operator attribution is not covered by the signature, allowing payout reimbursement credit to be misattributed away from the operator who actually fronts the withdrawal - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the `payout_tx` with an input spent via `SpendPath::KeySpend` and a witness set only for that single input/output pair [1](#0-0) . The only cryptographic commitment produced by the user is the Schnorr signature over input 0, which — because `withdraw()` validates a `SinglePlusAnyoneCanPay`-type sighash — only binds input index 0 and output index 0 (the user payout output) [2](#0-1) . The second output (`op_return_txout`, carrying the fronting operator's x-only pubkey) is appended to the transaction template but is never covered by that signature [3](#0-2) . The verifier side later trusts this unauthenticated OP_RETURN value as ground truth for "who fronted the payout": `update_finalized_payouts` parses it directly out of the confirmed on-chain payout tx and persists it as `payout_payer_operator_xonly_pk` [4](#0-3) . That column subsequently drives which operator's `PayoutCheckerTask` is triggered to claim reimbursement (`get_first_unhandled_payout_by_operator_xonly_pk`, filtered by the operator's own pubkey) [5](#0-4) [6](#0-5) , and which operator is allowed to request reimbursement transactions for that deposit (`validate_payer_is_operator`) [7](#0-6) .

### Finding Description
This is the same bug class as the reported issue: a value that determines "who gets credited/paid" is derived from attacker-influenceable data instead of from an authenticated binding to the party that actually performed the action. In the external report, `msg.sender` (the VRF coordinator) was wrongly used instead of the actual reward recipient. Here, the OP_RETURN pubkey embedded by whoever *assembles/broadcasts* the payout transaction is used as the reward recipient identifier (the operator entitled to reimbursement), but that value is not bound by the only signature present on the transaction.

Because the payout tx uses `SIGHASH_SINGLE|ANYONECANPAY` on its sole "authorizing" input/output pair, and is funded with additional inputs via RBF-capable `NON_STANDARD_V3` (`fund_raw_transaction`, `subtractFee`, replaceable transactions) [8](#0-7) , any party that observes the unconfirmed payout transaction in the mempool can reconstruct a variant transaction that:
- keeps input 0 and output 0 byte-for-byte identical (so the existing signature remains valid), and
- substitutes its own fee-funding input(s) and a different `op_return_txout` value (a different operator's x-only pubkey, or garbage that decodes to `None`),

and get that variant confirmed instead (e.g. via a higher-fee replacement, since the tx opts into full replaceability). The verifier's chain-sync logic (`update_finalized_payouts`) will then attribute the payout to whatever pubkey is present in the *confirmed* transaction's OP_RETURN, not to the operator who actually funded/broadcast the original payout.

This breaks the binding "the operator credited for fronting the withdrawal == the party that actually paid the user out of its own funds," which is exactly the value/attribution boundary specified in scope (operator credited vs. party that paid).

### Impact Explanation
Two concrete, in-scope impacts follow directly from `is_kickoff_malicious`'s trust in the DB-stored `payout_payer_operator_xonly_pk` [9](#0-8) :
1. **Honest operator permanently unable to be reimbursed**: If an attacker replaces the honest operator's broadcast OP_RETURN with a bogus/invalid pubkey (or another operator's pubkey) before confirmation, the honest operator who actually fronted the withdrawal from its own funds is never marked as the payer in `withdrawals.payout_payer_operator_xonly_pk`. When that operator later tries `get_reimbursement_txs`, `validate_payer_is_operator` will reject it ("Payer is not own operator for deposit") [10](#0-9) , permanently blocking reimbursement for BTC it already paid out.
2. **A different operator credited for a payout it never funded**: If the substituted OP_RETURN names another live operator, that operator's `PayoutCheckerTask` will pick up the "unhandled payout" for its own xonly pubkey (`get_first_unhandled_payout_by_operator_xonly_pk`) and proceed through `handle_finalized_payout` / kickoff / reimbursement for a withdrawal it never actually funded [11](#0-10) , letting that operator draw the deposit's vault funds via `create_reimburse_txhandler` without having fronted the corresponding payout.

Both map to the specified Critical impacts ("an operator reimbursed for a payout it never funded" / "an honest operator permanently unable to be reimbursed").

### Likelihood Explanation
The precondition is only that the attacker observe the unconfirmed payout transaction (which is broadcast publicly to the Bitcoin mempool) before it confirms and be able to relay a fee-bumped replacement — no verifier/operator/watchtower privilege, no key compromise, and no protocol misconfiguration is required, satisfying the "unprivileged attacker" bar. The transaction explicitly opts into non-standard/full-RBF handling (`NON_STANDARD_V3`), which is what makes such a same-signature substitute broadcastable and preferentially minable. The main uncertainty (not fully confirmed from index-limited reading) is the exact runtime mempool/RBF policy enforcement and precise timing window used in production deployments, which would affect how reliably an attacker can win the race; this would need to be validated against the live fee-bumping/TxSender behavior (`crates/clementine-tx-sender/src/rbf.rs`), which I could not fully inspect due to index limits.

### Recommendation
Bind the fronting operator's identity to the same signature that authorizes spending the payout input, e.g. by:
- Including the OP_RETURN output within the sighash committed by the payout signature (use `SIGHASH_ALL` or explicitly commit to output index 2 as well), or
- Deriving the "payer" identity from a signature the operator itself produces over the whole transaction (in addition to the user's authorization signature) rather than from unauthenticated plaintext script data, so that `update_finalized_payouts` can verify — not just parse — the payer attribution before persisting `payout_payer_operator_xonly_pk`.

### Proof of Concept
Conceptual (Bitcoin-transaction-malleability) PoC, following the flow in `core/src/operator.rs::withdraw` and `core/src/builder/transaction/operator_reimburse.rs::create_payout_txhandler`:
1. Honest Operator A calls `withdraw()`, producing `payout_tx_A` with input0 spent via the user's `SinglePlusAnyoneCanPay` signature, output0 = the user's payout, and `op_return_txout` = Operator A's x-only pubkey; A funds and broadcasts it (RBF-enabled) [12](#0-11) .
2. Attacker observes `payout_tx_A` in the mempool, copies input0's outpoint/witness and output0 unchanged (so the existing Schnorr signature stays valid), replaces the funding input(s) with its own UTXO(s), and sets `op_return_txout` to Operator B's x-only pubkey (or an invalid value), then rebroadcasts as `payout_tx_attacker` with a higher fee, causing it to replace `payout_tx_A` in mempools/blocks.
3. Once confirmed, verifier's `update_finalized_payouts` reads `payout_tx_attacker`'s OP_RETURN and sets `payout_payer_operator_xonly_pk = Operator_B` (or `NULL`) for that withdrawal [13](#0-12) .
4. Operator A's later `get_reimbursement_txs` call fails at `validate_payer_is_operator` ("Payer is not own operator for deposit") even though A is the one who actually fronted the withdrawal amount to the user [10](#0-9) , while Operator B (if named) becomes eligible to claim reimbursement it never funded via `PayoutCheckerTask` [11](#0-10) .

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,

    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
