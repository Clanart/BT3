## Analog Identified: Balance-Handler Event-Cursor Desync on Reentrant/Nested Precompile Calls

The Hyperliquid report is about a component (`Overseer.rebase()`) relying on a *stale/inconsistent snapshot* to compute an aggregate accounting value when intervening state-changing actions occur within the same execution window. The closest Cosmos EVM analog is not in `x/bank` supply precompiles (those read the live `sdk.Context` synchronously, so they are not "start-of-block" snapshots), but in the precompile→StateDB balance-sync mechanism, `precompiles/common/BalanceHandler`, which uses a stateful event-index "snapshot" (`prevEventsLen`) that can be silently invalidated by a nested/recursive precompile call occurring inside the same window — a documented issue directly evidenced in this codebase's own test suite.

### Title
Recursive/Nested Precompile Calls Corrupt Shared `BalanceHandler` Event Cursor, Desynchronizing EVM `StateDB` Balances from `x/bank` State - (File: `precompiles/common/balance_handler.go`)

### Summary
`BalanceHandler.BeforeBalanceChange` records `len(ctx.EventManager().Events())` as a cursor (`prevEventsLen`) before a precompile's native action executes, and `AfterBalanceChange` replays only the bank `CoinSpent`/`CoinReceived` (and precisebank fractional) events emitted after that cursor into the EVM `StateDB` via `AddBalance`/`SubBalance` [1](#0-0) [2](#0-1) . If a precompile call recursively/nestedly triggers another call into the same (or another) precompile that shares the same `BalanceHandler` instance, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, and the inner call's `AfterBalanceChange` consumes/advances the cursor. When control returns to the outer call, events emitted by the *outer* call's own bank operations that occurred before the inner call's cursor was set are never replayed to `StateDB`, because the shared cursor no longer reflects the outer call's starting point.

### Finding Description
The repository's own integration test, `TestRecursivePrecompileCallsWithDebugPrecompile`, is explicitly documented as reproducing this exact class of bug:

> "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [3](#0-2) 

The test uses a debug precompile (`Call0`) that recursively invokes itself through `CallEVMWithData` while sandwiching `Call1` calls that emit `debug_precompile` events [4](#0-3) [5](#0-4) , showing the same code path (`GetBalanceHandler().BeforeBalanceChange`/`AfterBalanceChange` wrapping `p.Execute`) that real stateful precompiles use directly, rather than the newer per-call-scoped `BalanceHandlerFactory.NewBalanceHandler()` pattern seen in `RunNativeAction`/`runNativeAction` [6](#0-5) . Several production precompiles (`staking`, `distribution`, `gov`, `ics20`, `slashing`, `erc20`) reference `GetBalanceHandler()` directly rather than the factory, based on their imports of the balance-handler API — meaning if any of these hold or reuse a single handler instance across nested/recursive invocations (e.g., a contract calling into a precompile whose native execution triggers a callback into the caller, which itself re-enters the same or another balance-handler-using precompile before the outer call unwinds), the cursor-overwrite bug applies to live user-fund-moving precompiles, not just the debug one.

Since `BeforeBalanceChange`/`AfterBalanceChange` is the sole mechanism translating real `x/bank` coin movements (`SendCoins`, `MintCoins`/`BurnCoins` via precisebank, staking delegation payouts, IBC transfer escrow movements, etc.) into corresponding `StateDB.AddBalance`/`SubBalance` calls, any missed replay window means the EVM-visible balance for an account permanently diverges from its true `x/bank` balance for the rest of the transaction (and is then committed via `stateDB.Commit()` / `commitWithCtx`, persisting the corrupted value) [7](#0-6) .

### Impact Explanation
This breaks the core Cosmos EVM invariant that ERC-20/EVM-visible balances must reconcile 1:1 with native `x/bank` state. A missed `CoinSpent` event means `StateDB` balance is never debited even though the coins truly left the account in `x/bank` — creating spendable "phantom" EVM balance the attacker can use again in the same or later transactions (double-spend / unauthorized value duplication). Conversely a missed `CoinReceived` replay silently deletes real economic value from the EVM's view, effectively freezing/locking those funds from EVM-side spending. Both outcomes are Critical: unauthorized duplication of spendable value, or permanent freezing/loss of user funds mediated through a precompile.

### Likelihood Explanation
Low-to-Medium. It requires a call path where a precompile's native execution causes re-entry into a precompile that shares the same handler instance before the original call unwinds (the debug precompile demonstrates this is achievable purely through a Solidity contract calling a precompile recursively/in a loop with intervening precompile submethods that emit bank events). Whether any of the currently shipped precompiles (staking, distribution, gov, ics20, slashing, erc20) actually share a *single, non-per-call* `BalanceHandler` instance (as opposed to a fresh one per `Run`) could not be fully confirmed from indexed code within the available search budget — this is the key remaining uncertainty and should be verified directly against `GetBalanceHandler()`'s definition and each precompile's `Run` implementation.

### Recommendation
- Ensure every precompile allocates a fresh `BalanceHandler` per top-level `Run`/native-action invocation (as `runNativeAction` already does via `BalanceHandlerFactory.NewBalanceHandler()`), and audit `staking.go`, `distribution.go`, `gov.go`, `ics20.go`, `slashing.go`, `erc20.go` to confirm none hold a cached/shared handler instance across calls.
- Make the event-replay window reentrancy-safe by using a stack of cursors (push/pop) instead of a single mutable `prevEventsLen` field, so nested calls cannot clobber an outer call's starting index.
- Add an invariant check (e.g., in integration tests or a debug assertion) that sums of `StateDB` balance deltas applied via `BalanceHandler` match the net bank-keeper balance deltas for the same address within a transaction.

### Proof of Concept
The existing repository test is itself a working PoC of the underlying mechanism: `evmd/tests/integration/balance_handler/balance_handler_test.go::TestRecursivePrecompileCallsWithDebugPrecompile` deploys `DebugPrecompileCaller.sol`, which calls the debug precompile recursively with interleaved event-emitting calls (`Call1`) inside a self re-entering `Call0` [8](#0-7) , and asserts a specific reduced count of processed `debug_precompile` events relative to what was emitted, directly demonstrating that recursive precompile invocation loses/corrupts events tracked by the shared cursor [9](#0-8) . Reproducing this against a production precompile that moves real coins (e.g., a staking-precompile flow that triggers a callback into a caller contract, which re-enters a bank-event-emitting precompile before the outer call's `AfterBalanceChange` runs) would need to be validated to confirm exploitability of fund-affecting balances, which is the unverified step flagged above.

contract DebugPrecompileCaller {
    address constant debugPrecompile = 0x0000000000000000000000000000000000000799;
    error CallFailed(bytes data);
    function callback(uint256 counter) public {
        bool result;
        bytes memory data;

        // emit events
        for (uint i = 0; i < counter; i++) {
            (result, data) = debugPrecompile.call(abi.encodePacked(uint8(1)));
            if (!result) {
                revert CallFailed(data);
            }
        }

        if (counter > 3) {
            // stop the recursion
            return;
        }

        // recursive call
        (result, data) = debugPrecompile.call(abi.encodePacked(uint8(0), counter));
        if (!result) {
            revert CallFailed(data);
        }
    }

// Commit writes the dirty states to keeper

func (s *StateDB) Commit() error {
	// writeCache func will exist only when there's a call to a precompile.
	// It applies all the store updates preformed by precompile calls.
	if s.writeCache != nil {
		s.writeCache()
	}
	return s.commitWithCtx(s.ctx)
}

// CommitWithCacheCtx writes the dirty states to keeper using the cacheCtx.
// This function is used before any precompile call to make sure the cacheCtx
// is updated with the latest changes within the tx (StateDB's journal entries).
func (s *StateDB) CommitWithCacheCtx() error {
	return s.commitWithCtx(s.cacheCtx)
}
