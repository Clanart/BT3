I examined the in-scope Bitcoin wallet code for an analog of the report's bug class — a fee mechanism that is implicit/non-dedicated, where the general-purpose transaction-construction checks can interfere with or bypass the intended fee payment. There is a concrete flaw in `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`.

### Title
SignableTransaction omits the OP_RETURN data output from its weight/fee calculation, producing transactions that underpay and can fall below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts a caller-supplied `data` field and appends an OP_RETURN output to the transaction (send.rs:194-202), but computes the transaction weight, the `needed_fee`, and the change amount solely from `inputs` + `payments` + optional `change` via `calculate_weight_vbytes` (send.rs:204, 62-127). The OP_RETURN output — up to ~91 vbytes of non-witness data for an 80-byte payload — is never counted. Like the FeeCollector issue (fees handled by an implicit side path rather than a dedicated, correctly-scoped mechanism), the fee here is not a dedicated, checked quantity covering the actual transaction: it is derived from a partial reconstruction of the TX that silently excludes an attacker/caller-influenced output.

### Finding Description
In `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs):

```rust
// line 194-202: data output is pushed to tx_outs
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}

// line 204: weight is computed from `payments` only — tx_outs / data are ignored
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (send.rs:62-127) builds a template `Transaction` containing only `inputs` and `payments` (plus an optional change output) and calls `tx.weight()`. The OP_RETURN output pushed into `tx_outs` is absent from this template, so:

1. `vbytes` under-reports the real virtual size by roughly `(8 + script_len + ~2)` bytes — about 91 vbytes for the maximum permitted 80-byte payload (data length is only checked against `> 80` at send.rs:171).
2. `needed_fee = fee_per_vbyte * vbytes` is therefore smaller than the fee required to actually achieve `fee_per_vbyte` on the signed transaction.
3. The minimum-fee gate at send.rs:211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) is evaluated against the under-estimated vbytes, so a transaction paying exactly `needed_fee` can sit below the real minimum relay fee for its actual size.
4. The same omission applies to the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:225-226) also excludes the data output, so `change = input_sat − payment_sat − fee_with_change` sets the actual paid fee to exactly `fee_with_change` — a fee that does not cover the bytes of the OP_RETURN output the transaction really contains.

Because `fee()` (send.rs:138-141) defines the real fee as `sum(inputs) − sum(outputs)`, the network sees a fee rate strictly lower than the `fee_per_vbyte` the caller specified, and potentially below `DEFAULT_MIN_RELAY_TX_FEE` for the true size.

### Impact Explanation
A transaction constructed with a non-empty `data` payload is underpriced relative to the requested fee rate, and in the boundary case is underpriced below the minimum relay fee. Such a transaction will not propagate or confirm despite `needed_fee()` reporting a value that passed the `TooLowFee` check. For a threshold-controlled wallet (the intended consumer via `multisig()`/`TransactionMachine`), the result is a signed transaction paying an unintended, too-low fee that stalls in the mempool or is rejected — the funds are committed to that TX's inputs until a replacement is coordinated and re-signed, exactly the "checks interfere with the fee purpose" failure mode the external report describes, but realized concretely as an incorrect fee formula.

### Likelihood Explanation
The bug triggers deterministically whenever `data.is_some()`: the weight template never includes the OP_RETURN output, so every data-carrying transaction underpays by ~the serialized size of that output times `fee_per_vbyte`. Whether it crosses the relay-minimum boundary depends on `fee_per_vbyte` and the payload size, but the underestimation itself is unconditional. Reachability is through the public `SignableTransaction::new` constructor — the `data` bytes are caller-supplied, and the resulting transaction is what `TransactionMachine` causes the threshold group to sign.

### Recommendation
Include the OP_RETURN output in the weight template — e.g., have `calculate_weight_vbytes` take the fully assembled `tx_outs` (or append the data output inside it) so `vbytes`, `needed_fee`, the `TooLowFee` check, and the change computation all account for the data output. Alternatively, treat the fee as a dedicated, explicitly-computed quantity over the final transaction rather than deriving it from a partial reconstruction, mirroring the report's recommendation of a dedicated fee mechanism instead of an incidental one.

### Proof of Concept
```rust
// Conceptual: construct a SignableTransaction with maximal data and a minimal
// fee rate. The OP_RETURN output (~91 vbytes) is excluded from vbytes.
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    vec![input],                    // ReceivedOutput(s)
    &[(payment_script, DUST)],      // payments
    Some(change_script),            // change
    Some(data),                     // <- data output pushed to tx_outs
    1,                              // fee_per_vbyte = 1 sat/vb
).unwrap();

// tx.fee() == needed_fee == 1 * vbytes(template WITHOUT the OP_RETURN output)
// Actual signed tx is ~91 vbytes larger, so the realized fee rate is
// needed_fee / real_vsize < 1 sat/vb, below DEFAULT_MIN_RELAY_TX_FEE
// (1000 sat/kvb) for the true size — yet the TooLowFee check at send.rs:211
// passed because it compared against the smaller template vbytes.
```
