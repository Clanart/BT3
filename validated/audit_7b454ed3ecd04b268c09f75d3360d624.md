### Title
Silent field-default in `Condition.from_dict` causes explicit `conditions:` block rules to silently never match, bypassing enforcement - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Condition.from_dict` defaults a missing `field` key to the empty string `''` instead of erroring or inferring it the way the legacy `pattern:` code path does. A hookify rule file (whether repo-shipped or produced by `/hookify` generation) that uses the new-style explicit `conditions:` list and omits `field` on any entry silently compiles into a `Rule` whose condition can never be satisfied, so a `block` action rule never actually blocks anything.

### Finding Description
`Rule.from_dict` (`plugins/hookify/core/config_loader.py:44-84`) supports two ways to specify what to match:
- Legacy: a top-level `pattern:` string, for which the loader explicitly infers the correct `field` from `event` (`command` for bash, `new_text` for file, `content` otherwise) at lines 60-67. [1](#0-0) 
- New style: an explicit `conditions:` list, each item converted via `Condition.from_dict` (line 54), which uses `data.get('field', '')` — defaulting to an empty string with no inference and no validation. [2](#0-1) 

At evaluation time, `RuleEngine._check_condition` calls `_extract_field(condition.field, ...)` (`plugins/hookify/core/rule_engine.py:158`). `_extract_field` checks `if field in tool_input`, then several hard-coded `field == '...'` branches (`reason`, `transcript`, `user_prompt`, `command`, `content`, `new_text`, etc.) — none of which match `''` — and falls through to `return None` at the end. [3](#0-2) 
Back in `_check_condition`, `field_value is None` short-circuits to `return False` (line 159-160), and `_rule_matches` requires *all* conditions to match (lines 120-123), so the rule can never match. [4](#0-3) [5](#0-4) 

The reachable path is: `load_rule_file` → `extract_frontmatter` (parses `.claude/hookify.*.local.md`) → `Rule.from_dict` → `Condition.from_dict`, invoked from `load_rules()` which is called during hook execution (`pretooluse.py`/`posttooluse.py`/`stop.py`/`userpromptsubmit.py`). [6](#0-5) 

The security-relevant asymmetry: the legacy `pattern:` path guarantees a sane, event-appropriate field is always populated, but the "more explicit/modern" `conditions:` path has weaker guarantees — a missing `field` doesn't raise, doesn't fall back to event-based inference, and doesn't cause a load-time error; it silently produces a permanently-false, hence no-op, rule with `action: block`. This is exactly the "no-op block rule" hazard: a maintainer or `/hookify`-generated rule intended to block a dangerous command (e.g., `rm -rf`) can be rendered completely inert by a small, easy-to-produce/omit YAML mistake, and the codebase gives no signal that the rule is dead — `load_rules()` swallows parse-time issues only, not semantic ones, and the rule loads "successfully" but as an enforcement no-op. Any content that influences generated frontmatter (e.g. injected instructions consumed by `/hookify`, or a rule file merged into the repo) can trigger this — the attacker doesn't need to modify existing rule files, only to cause a new/modified rule using `conditions:` without `field` to be shipped, silently defeating enforcement instead of raising a visible parse/config error.

### Impact Explanation
A `block`-action hookify rule (e.g., meant to prevent dangerous `Bash` commands or edits) that is written/generated using the `conditions:` style without an explicit `field` becomes permanently unmatchable, so it never blocks anything, effectively disabling the intended local guardrail. In `plugins/hookify/core/rule_engine.py`, a blocking rule that never matches simply falls through to allow the operation, which for a rule meant to prevent unauthorized/dangerous local command execution constitutes unauthorized local command execution that bypasses the intended block behavior. This is a scoped, local, silent-failure enforcement bypass rather than a broad-scope widening — but it directly weakens the invariant that default inference must not weaken enforcement.

### Likelihood Explanation
Feasibility is high and requires no special privilege: any content that shapes a hookify rule file's frontmatter (an LLM-generated `/hookify` rule missing `field:` in a condition item, or a rule file added/edited in a PR) triggers this. The bug is a straightforward default-value flaw in `Condition.from_dict`, deterministically reproducible, and does not depend on any admin/maintainer/credential assumption — only that some `conditions:`-based block rule omits `field`.

### Recommendation
In `Condition.from_dict`, require `field` to be explicitly present (raise `ValueError`/reject the rule at load time rather than defaulting to `''`), or apply the same event-based inference used for the legacy `pattern:` path when `field` is absent. Additionally, `load_rules()`/`load_rule_file()` should validate that any loaded `conditions` entries have non-empty, recognized `field`/`operator` values and refuse to silently load a `block` rule whose conditions can never be satisfied — surfacing a warning/error instead of loading a dead rule.

### Proof of Concept
Unit test in `plugins/hookify/core/config_loader.py`/`rule_engine.py` test style:
```python
frontmatter = {
    "name": "block-rm",
    "enabled": True,
    "event": "bash",
    "action": "block",
    "conditions": [
        {"operator": "regex_match", "pattern": r"rm\s+-rf"}  # 'field' omitted
    ],
}
rule = Rule.from_dict(frontmatter, "Dangerous rm command!")
assert rule.conditions[0].field == ''  # confirms silent default

engine = RuleEngine()
result = engine.evaluate_rules([rule], {
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"},
    "hook_event_name": "PreToolUse",
})
assert result == {}  # BUG: block rule never fires, command is allowed
```
Compare against the equivalent legacy-style rule (`pattern: "rm\\s+-rf"`, no `conditions`) on the same input, which correctly infers `field="command"` and returns a `permissionDecision: deny` result — demonstrating the differential between legacy and explicit condition parsing and the resulting enforcement bypass.

    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields
            if field == 'reason':
                return input_data.get('reason', '')
            elif field == 'transcript':
                # Read transcript file if path provided
                transcript_path = input_data.get('transcript_path')
                if transcript_path:
                    try:
                        with open(transcript_path, 'r') as f:
                            return f.read()
                    except FileNotFoundError:
                        print(f"Warning: Transcript file not found: {transcript_path}", file=sys.stderr)
                        return ''
                    except PermissionError:
                        print(f"Warning: Permission denied reading transcript: {transcript_path}", file=sys.stderr)
                        return ''
                    except (IOError, OSError) as e:
                        print(f"Warning: Error reading transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')

        # Handle special cases by tool type
        if tool_name == 'Bash':
            if field == 'command':
                return tool_input.get('command', '')

        elif tool_name in ['Write', 'Edit']:
            if field == 'content':
                # Write uses 'content', Edit has 'new_string'
                return tool_input.get('content') or tool_input.get('new_string', '')
            elif field == 'new_text' or field == 'new_string':
                return tool_input.get('new_string', '')
            elif field == 'old_text' or field == 'old_string':
                return tool_input.get('old_string', '')
            elif field == 'file_path':
                return tool_input.get('file_path', '')

        elif tool_name == 'MultiEdit':
            if field == 'file_path':
                return tool_input.get('file_path', '')
            elif field in ['new_text', 'content']:
                # Concatenate all edits
                edits = tool_input.get('edits', [])
                return ' '.join(e.get('new_string', '') for e in edits)

        return None
