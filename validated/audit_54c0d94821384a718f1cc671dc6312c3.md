### Title
Untrusted `offset` in deserialized `ReceivedOutput` is trusted for spend-key attribution and spending - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes an attacker-controlled scalar `offset`, a `TxOut`, and an `OutPoint` without verifying that `offset` actually maps the output's `script_pubkey` back to the wallet's group key. Downstream code uses this untrusted `offset` as a security decision: `Output::key()` computes the owning multisig key as `script_key - G * offset`, and `SignableTransaction` / `Scanner` treat the output as spendable under that offset. This mirrors CVE-2026-63041: an untrusted, client-supplied label-like field (`offset`, analogous to `consumer-label`) is consumed in a security decision without sanitization.

### Finding Description
`ReceivedOutput::read` accepts any scalar for `offset` and any `script_pubkey`, binding them together unconditionally. The correct relationship — `p2tr_script_buf(group_key + G * offset) == output.script_pubkey` — is only checked inside `SignableTransaction::multisig` (send.rs), and only against *whichever keys* the caller passes in. Nothing validates that the `offset`/`script_pubkey` pair corresponds to a key this wallet actually owns, nor that the offset was one produced by `Scanner::register_offset`.

When `ReceivedOutput::read` output is fed into `Output::read` in processor code, `Output::key()` derives the attributed multisig key as `script_pubkey_key - G * offset`. An attacker supplying serialized output bytes can therefore attribute an arbitrary on-chain P2TR output to an arbitrary point `K = script_key - G*offset`, e.g., a retired, rotated, or foreign multisig key — a trust decision made entirely on attacker-supplied bytes.

### Impact Explanation
- **Funds reported received that are not spendable:** an attacker-forged `ReceivedOutput` (wrong `offset` for a real `script_pubkey`, or a fabricated `TxOut`/`OutPoint`) is recorded as a received, spendable output for some key. Any plan built on it fails to spend (the signature won't satisfy the real output) — misaccounting of multisig funds.
- **Misattribution across keys:** `key()` arithmetic lets an attacker route an output to a different registered key (e.g., an old multisig during rotation), corrupting the existing-vs-new output split used for rotation.
- Reachable per the threat model: untrusted bytes flow through `ReceivedOutput::read` / `Output::read` from serialized/DB/network paths into these decisions.

### Likelihood Explanation
Any party able to supply or inject serialized output bytes (malformed data fed to `ReceivedOutput::read`/`Output::read`, matching the prompt's accepted input surface) controls all three fields. No signature or secret is required; the fields are unchecked plaintext. Exploitation requires the resulting `Output` to reach `key()`-based attribution or `multisig` signing setup, which is the normal processing path for scanned outputs.

### Recommendation
In `ReceivedOutput::read` (or at `Output::read`/`key()`), verify the invariant `p2tr_script_buf(derived_key + G * offset) == output.script_pubkey` for the wallet's key set, or store/verify the group key alongside the output rather than deriving it from untrusted `offset`. At minimum, reject deserialized `ReceivedOutput`s whose `(script_pubkey, offset)` pair was never produced by `Scanner::scan_transaction`.

### Proof of Concept
1. Craft bytes: `offset = o` (arbitrary scalar), `TxOut` with any real on-chain P2TR `script_pubkey` paying to script key `P`, any `OutPoint`.
2. `ReceivedOutput::read` succeeds — no consistency check exists (`wallet/mod.rs` lines 122–134).
3. `Output::key()` returns `P - G*o`, an arbitrary point not equal to any registered multisig key, or equal to a different key than intended (`processor/src/networks/bitcoin.rs` lines 112–122).
4. The output is reported received/misattributed; if spent, `SignableTransaction::multisig` either fails (unspendable "received" funds) or, when the forged check happens to pass for a wrong key context, produces a signature under a key that does not control the output.
