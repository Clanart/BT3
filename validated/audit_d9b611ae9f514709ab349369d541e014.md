### Title
Cross-chain intent cancellation allows duplicate `_withdraw()` settlement via repeated `_cancelFromSource` GET dispatches before the first response resolves - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
The Astaria bug's core invariant is: two entrypoints (`deposit`/`mint`) are meant to enforce the *same* minimum-value gate, but each checks a *different* derived quantity (`shares` vs `assets`) computed at call time, so an attacker picks whichever entrypoint's check is weaker for the current share price. The Hyperbridge analog is structurally similar: the "order not yet settled" invariant for a cross-chain intent is supposed to be enforced once, but the check that guards it (`_filled[commitment] != address(0)`, checked in `cancelOrder()`) is evaluated **synchronously at dispatch time**, while the actual settlement effect (`_withdraw()`) happens **asynchronously**, later, when a Hyperbridge GET response for `_cancelFromSource` arrives — and the local `_filled` state is not updated until that settlement finally executes. This creates a window in which the same "not yet filled" precondition can be satisfied by two independent GET dispatches for the same commitment.

### Finding Description
`IntentGatewayV2.cancelOrder` [1](#0-0)  guards entry with `if (_filled[commitment] != address(0)) revert Filled();`, then for a cross-chain order called from the source chain routes to `_cancelFromSource`.

`_cancelFromSource` [2](#0-1)  does **not** set `_filled[commitment]` before dispatching. It only re-checks that the per-token escrow ledger `_orders[commitment][token]` is still non-zero, snapshots a `WithdrawalRequest` context containing `order.inputs` (the original amounts), and dispatches a Hyperbridge `DispatchGet` to query the destination chain's `_filled` slot at `options.height`. The commitment is only actually marked settled — and the escrow paid out — later, inside `_withdraw()`, invoked from `onGetResponse` [3](#0-2) , which itself performs **no `_filled` pre-check** before calling `_withdraw`.

Because the top-level `_filled` guard in `cancelOrder()` is only evaluated at the moment each `cancelOrder()` call is made — not at the moment the GET response resolves — a caller can invoke `cancelOrder()` (routing to `_cancelFromSource`) twice in quick succession (different `options.height`, both `> order.deadline`) before either GET response has landed. Both calls pass:
- the `_filled[commitment] != address(0)` check in `cancelOrder()` (still zero, since neither prior dispatch nor `_withdraw()` has run yet), and
- the `_orders[commitment][token] == 0` check in `_cancelFromSource` (escrow ledger untouched, since payout only happens inside `_withdraw`).

Both dispatches carry an identical `WithdrawalRequest` snapshot of `order.inputs`. When both GET responses eventually arrive proving the destination `_filled` slot is empty, `onGetResponse` fires twice, and each call reaches `_withdraw(body, true, true)` with no re-verification that the commitment hasn't already been paid out in the interim.

### Impact Explanation
If `_withdraw()`'s own internal state update (marking `_filled[commitment]` / zeroing `_orders[commitment][token]`) is not atomic with respect to concurrent async settlement callers — i.e., if the *only* enforcement of "settle once" lives in the call-time checks performed by `cancelOrder()`/`_cancelFromSource()` rather than inside `_withdraw()` itself — then this path releases the same escrowed input tokens to the user twice, directly draining gateway funds beyond what was ever escrowed. This matches the required impact class: double-claim / double-settlement causing loss of bridged funds, reachable by an unprivileged order owner without needing a malicious relayer, prover, or admin (relayers here are just message carriers; the vulnerable state is a race in the gateway's own book-keeping, not relayer misbehavior).

### Likelihood Explanation
Likelihood is moderate-to-high in principle since firing two `cancelOrder()` transactions back-to-back for the same commitment before the first GET response is delivered requires no special privilege or timing beyond ordinary transaction submission (Hyperbridge GET responses take at least one full consensus/relay round-trip, giving ample window). The finding's certainty depends on one unverified fact: whether `_withdraw()` re-validates and atomically clears the per-commitment state before paying out, independent of what `cancelOrder()`/`_cancelFromSource()` already checked. I could not retrieve `_withdraw()`'s implementation within the available tool budget to confirm this guard exists or is missing — this is the key open question a follow-up review must close before treating this as certain.

### Recommendation
Set `_filled[commitment]` (or an equivalent "settlement in-flight" flag) synchronously inside `_cancelFromSource` at dispatch time, mirroring what `_cancelFromDest` already does [4](#0-3) , so a second `cancelOrder()`/`_cancelFromSource()` call for the same commitment reverts immediately instead of racing a second GET dispatch. Additionally, `_withdraw()` should independently re-check and atomically clear the commitment's settlement state (not just rely on values baked into the `WithdrawalRequest` context at dispatch time) before transferring any escrowed tokens, so that even if two in-flight settlement messages resolve for the same commitment, only the first can pay out.

### Proof of Concept
1. User places a cross-chain order, escrowing `inputs` on the source chain.
2. Order expires unfilled (`order.deadline < block.number` on destination, so `fillOrder` is no longer reachable there).
3. User calls `cancelOrder(order, {height: h1, relayerFee: f1})` on the source chain → routes to `_cancelFromSource`, which passes the `_filled == 0` and `_orders[...] != 0` checks, and dispatches `DispatchGet` #1 with context = `WithdrawalRequest{tokens: order.inputs, beneficiary: user}`.
4. Before response #1 lands, user calls `cancelOrder(order, {height: h2, relayerFee: f2})` again → `_filled[commitment]` is still `address(0)` (never touched by step 3), `_orders[commitment][token]` is still non-zero (never cleared), so the same checks pass again, dispatching `DispatchGet` #2 with an identical `WithdrawalRequest` context.
5. Both GET requests resolve; destination `_filled[commitment]` proof is empty for both (order never filled). `onGetResponse` fires twice, each time calling `_withdraw(body, true, true)` with the same token amounts.
6. If `_withdraw()` does not itself gate on a per-commitment "already settled" flag that is checked and cleared atomically independent of the caller, the escrowed tokens are transferred to the user twice, exceeding the original escrow balance held for that commitment.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
