### Title
Malicious order creator can permanently block `RedeemEscrow` settlement with a hostile input token, extracting solver output for free and locking the escrow forever - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2` accepts arbitrary, user-supplied ERC20 addresses as order `inputs` at `placeOrder` time with no allowlist (confirmed by fee-on-transfer token tests operating against arbitrary tokens). For cross-chain orders, the solver delivers real output value to the beneficiary on the destination chain in `_fillCrossChain` *before* the escrowed input tokens are ever paid out; payment only happens later, when the `RedeemEscrow` message lands on the source chain and `_withdraw` calls `safeTransfer` to the solver.

### Finding Description
In `_fillCrossChain` [1](#0-0) , the solver unconditionally transfers output tokens to `beneficiary` (chosen by the order creator), then dispatches a `RedeemEscrow` post request back to the source chain [2](#0-1) . Only after this message is proven and delivered does the source-chain gateway pay the solver, via `onAccept` → `_withdraw(finalize=true)` [3](#0-2) , which iterates `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` on the *original input token the order creator chose* [4](#0-3) .

Because the input token contract address is fully attacker-controlled (no allowlist is enforced anywhere in `placeOrder`), the malicious order creator can deploy a token that behaves like a normal ERC20 for the purposes of escrowing (accepting `transferFrom` from anyone into the gateway), but reverts transfers whose recipient is not the original creator (a blacklist/hook check on `to`, functionally equivalent to an ERC777 `tokensReceived` hook that reverts for unwanted counterparties — the exact bug class in the seed report). Since the eventual payout recipient is the *solver* (an address unknown to the attacker until fill time, but always different from the attacker), the token can simply revert any transfer whose `to != owner`.

The result: `safeTransfer` in `_withdraw` reverts, so `onAccept` reverts, and `EvmHost.dispatchIncoming` catches the failed external call and deletes the receipt "so it can be retried" [5](#0-4) . But every retry re-executes the same reverting transfer — the settlement can never succeed. The escrow can also never be recovered through cancellation, because cross-chain cancellation from the source chain requires proving `_filled[commitment]` is empty on the destination via a GET request [6](#0-5) ; once the solver has filled the order, `_filled` is non-empty, so `onGetResponse` reverts with `Filled()` and refund is blocked as well.

### Impact Explanation
The malicious order creator receives the solver's real output tokens on the destination chain for free (extracted via `_fillCrossChain`) while permanently preventing the solver from ever collecting the escrowed input tokens on the source chain. This is a direct loss of solver funds and a permanent lock of the escrowed assets — the exact "borrower escapes the negative consequence via a hostile token hook" pattern from the seed report, translated to Hyperbridge's escrow settlement path. It requires no relayer, prover, or admin compromise; the entire attack is executable by an ordinary unprivileged user who simply deploys a hostile ERC20 and places an order with it as an input token.

### Likelihood Explanation
High. Placing an order with an attacker-controlled "input" token requires no special privilege — `placeOrder` performs no token allowlist check, and the codebase already demonstrates first-class support for arbitrary/non-standard ERC20 tokens (fee-on-transfer tests exist). Any solver monitoring the auction who is unaware of the token's hostile logic will unknowingly fill it, since the malicious behavior triggers only on the payout leg (`to == solver`), not on the initial escrow deposit (`to == gateway`), making the token look benign at order-placement time.

### Recommendation
- Do not let escrow settlement success depend on an unbounded/attacker-supplied token's `transfer` succeeding for a specific recipient. Wrap the `safeTransfer` for each input token in `_withdraw` in a try/catch (or low-level call) per-token so a single hostile token cannot block the entire settlement or the release of other, well-behaved tokens in the same order.
- If a per-token transfer fails, credit the amount to a pull-based "claimable balance" for the solver instead of reverting the whole withdrawal, so the solver can still recover value through an alternate token or an admin/governance sweep path.
- Consider requiring input tokens to come from a governance-curated allowlist (as Moonwell's remediation suggested for `emissionToken`), since arbitrary attacker-deployed tokens as escrow inputs is the root enabler of this class of attack.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer`/`transferFrom` succeed normally when `to == attacker` or `to == IntentGatewayV2` (the escrow deposit), but revert whenever `to` is any other address.
2. Attacker calls `placeOrder` on the source chain with `order.inputs = [{token: EvilToken, amount: X}]` and a normal `output` (e.g., DAI) requesting `outputs` from a solver — this deposits `X` EvilToken into escrow via a normal-looking `transferFrom(attacker, gateway, X)` [7](#0-6) .
3. An honest solver, unaware of the hostile logic, calls `fillOrder` on the destination chain, delivering real DAI to `order.output.beneficiary` (the attacker) via `_fillCrossChain` [1](#0-0) , then the `RedeemEscrow` message is dispatched to the source chain.
4. On the source chain, `onAccept` calls `_withdraw(finalize=true)`, which attempts `EvilToken.safeTransfer(solver, X)` [8](#0-7) ; because `to == solver ≠ attacker`, `EvilToken` reverts, `onAccept` reverts, and `EvmHost.dispatchIncoming` deletes the receipt for retry [5](#0-4)  — every retry fails identically.
5. The solver never receives the `X` EvilToken payment despite having already paid out DAI to the attacker; the escrow is permanently stuck and cross-chain cancellation is also blocked since `_filled[commitment]` is already set by the solver's fill.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
