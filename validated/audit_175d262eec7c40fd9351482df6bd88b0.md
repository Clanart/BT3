### Title
Auto-sync of `origin` remote URL from GitHub API trusts stale owner/name matching, enabling silent redirection of push/fetch traffic to an attacker-controlled repository - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically runs `git remote set-url` against the value returned by the GitHub API (`apiRepo.clone_url`) whenever Desktop refreshes a repository's GitHub association, with no user confirmation and no verification that the new URL still points to the repository the user originally trusted.

### Finding Description
Every time `repositoryWithRefreshedGitHubRepository` runs (triggered on repository selection, account changes, etc.), Desktop calls `api.fetchRepository(owner, name)` and then feeds the *entire, attacker-influenceable* API response straight into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` decides whether to rewrite the git remote based only on: (1) whether the URL protocol (`http`/`https`) is unchanged, and (2) whether the *previously stored* `gitHubRepository.cloneURL` still matches the current remote (i.e., the user hasn't manually edited it). Crucially, it never re-validates that the new `clone_url`'s owner/repo still corresponds to the same underlying repository identity the user originally added — it only compares the *string* URL: [2](#0-1) 

The repository association used to build this API call (`matchGitHubRepository`) resolves by `endpoint/owner/name`, not by GitHub's immutable numeric repository id. This is the well-known "repo-jacking" primitive: if the original `owner/name` combination becomes available again (owner renames/deletes the account or repository, or the repo is transferred and the old slug becomes free), an unprivileged attacker can register that exact `owner/name` on github.com and create a new repository there. The next time the victim opens Desktop, `fetchRepository(owner, name)` returns the *attacker's* repository object — an "attacker controls a GitHub API object" scenario — with a `clone_url` pointing at the attacker's own git host under the same protocol. Because `remoteUrlUnchanged` is still true (the user never touched `origin`) and `protocolsMatch` is still true, `!urlsMatch` becomes true and Desktop silently calls `gitStore.setRemoteURL(...)`, rewriting `origin` to the attacker's repository without any prompt, warning, or diff shown to the user: [3](#0-2) 

Existing guards do not stop this path:
- `urlMatchesRemote` only prevents the update when the *new* URL trivially matches the *current* remote — it is not a safety check, it's the trigger condition for the rewrite.
- `protocolsMatch` only checks `http:` vs `https:` — it does nothing to validate hostname or repository identity.
- There is no re-confirmation step, no diffing of owner/hostname against the previously known-good value, and no user-facing dialog (unlike the enterprise URL flow, which does validate via `validateURL` in `app/src/ui/lib/enterprise-validate-url.ts`, but that only applies to manually entered GHES addresses, not this automatic sync).

### Impact Explanation
Once `origin` is silently repointed, all subsequent `git fetch`/`git pull`/`git push` operations target the attacker's server instead of the legitimate one. This is a direct instance of "silent corruption of what the user commits or pushes": commits the user believes are going to their own project are instead pushed to (and potentially disclosed via) an attacker-controlled remote, and future pulls/fetches bring in objects served by that attacker, which the app then treats as trusted history. Because `envForRemoteOperation`/`envForProxy` resolve proxy and authentication context off of `remoteUrl` at the time of each git invocation, the app's own credential/token plumbing is invoked against the attacker's URL, creating conditions for token or credential exposure if the attacker's server solicits credentials during the operation.

### Likelihood Explanation
The precondition (owner/name becoming re-registrable while a stale association still lives in Desktop's local database) is a documented, real-world "repo-jacking" scenario on GitHub and requires no privileged access, malware, or social engineering — only that the attacker register the freed `owner/name` slug on github.com and wait for the victim's Desktop to run its normal, automatic background refresh of the selected repository. No unusual user action is required beyond opening/using the app as normal.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that the new `apiRepo` still represents the *same* underlying repository as previously known (e.g., compare GitHub's immutable repository `id`, not just `owner/name` strings), and/or surface an explicit, dismissible confirmation to the user before silently changing `origin`. At minimum, `updateRemoteUrl` should refuse to auto-update when the hostname of the new URL is unexpected, and always require the repository `id` match in addition to the current owner/name heuristic.

### Proof of Concept
1. Victim uses Desktop with a repository tracked as GitHub repo `victim/my-repo` (endpoint github.com), `origin` = `https://github.com/victim/my-repo`.
2. `victim/my-repo` becomes available for re-registration (owner renames account/repo, or deletes it).
3. Attacker (unprivileged) creates a new public repository at the exact same slug: `https://github.com/victim/my-repo`.
4. Victim reopens/selects the repository in Desktop, or Desktop's periodic refresh runs `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository('victim', 'my-repo')` — returning the attacker's repository object (`apiRepo.clone_url` = attacker's repo URL, same protocol/hostname). `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (origin never modified by user), `urlsMatch === false` (attacker repo id differs even though string form of URL might coincidentally match hostname), and calls `gitStore.setRemoteURL('origin', attackerCloneUrl)` with no prompt (confirmed by the unit test asserting exactly this auto-update behavior): [4](#0-3) 
5. Victim's next `git push`/`git fetch` in Desktop silently operates against the attacker's repository.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
```

```typescript
  public async setRemoteURL(name: string, url: string): Promise<boolean> {
    const wasSuccessful =
      (await this.performFailableOperation(() =>
        setRemoteURL(this.repository, name, url)
      )) === true
    await this.loadRemotes()

    this.emitUpdate()
    return wasSuccessful
  }
```
