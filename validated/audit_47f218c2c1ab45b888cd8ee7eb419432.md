### Title
Duplicate encryption-key registration message panics the node, enabling remote denial of service - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The WebKit CVE class is "crafted input reaches a parser/handler and corrupts state or crashes the process." In memory-safe Rust the reachable analog is an unguarded panic on attacker-controlled input. `Decryption::register` in the PedPoP DKG encryption layer uses `assert!` to reject a second `EncryptionKeyMessage` from the same `Participant`, converting a malicious protocol message into a process abort.

### Finding Description
`Decryption::register` is called for every `EncryptionKeyMessage<C, M>` received during the PedPoP key-generation protocol (`Encryption::register` delegates to it at [1](#0-0) ). The message itself is fully attacker-controlled: `EncryptionKeyMessage::read` deserializes arbitrary bytes via `M::read` and `C::read_G` with no protocol-state validation [2](#0-1) .

On receipt, the handler indexes internal state and then asserts uniqueness:

```rust
// crypto/dkg/pedpop/src/encryption.rs:351-362
pub(crate) fn register<M: Message>(
  &mut self,
  participant: Participant,
  msg: EncryptionKeyMessage<C, M>,
) -> M {
  assert!(
    !self.enc_keys.contains_key(&participant),
    "Re-registering encryption key for a participant"
  );
  self.enc_keys.insert(participant, msg.enc_key);
  msg.msg
}
```

Any DKG participant who sends two registration messages (or whose message is redelivered/duplicated by an unreliable transport) triggers a panic in the receiving honest party's process. The same anti-pattern exists in `decrypt_with_proof`, which performs `self.enc_keys[&decryptor]` — a `HashMap` index that panics if the `decryptor` participant never registered an encryption key [3](#0-2)  — reachable when the blamed-party index is attacker-influenced.

The library otherwise treats faulty behavior as an error to surface (e.g., `io::Error` in `Commitments::read`, `FrostError::DuplicatedParticipant` in `sign` at crypto/frost/src/sign.rs:306-310), so this `assert!` on untrusted input is an inconsistent and reachable panic.

### Impact Explanation
An unprivileged counterparty in the DKG can crash any honest participant's node at will by broadcasting a duplicate `EncryptionKeyMessage`. In a validator/coordinator context this aborts key generation and can take a signer offline during the ceremony, matching the CVE's "application crash / denial of service" impact. Severity: **Medium** — availability impact only, no secret leakage or forgery, but remotely triggerable by a single protocol participant with no special privileges.

### Likelihood Explanation
Triggering requires only sending a well-formed duplicate protocol message — trivial for any DKG participant. PedPoP's own comments acknowledge multiple-commitment senders must be "presumed malicious" (crypto/dkg/pedpop/src/lib.rs:98-101), yet the encryption-key path does not return an error — it panics. Reachability is direct through `EncryptionKeyMessage::read` → `Encryption::register` → `Decryption::register`.

### Recommendation
Replace the `assert!` with an error return (e.g., extend `DecryptionError` with a `DuplicateRegistration` variant, or return `io::Result`/`Result<M, DkgError>`) so the caller can mark the participant faulty. Similarly, replace `self.enc_keys[&decryptor]` in `decrypt_with_proof` with `.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` to avoid a panic on missing entries.

### Proof of Concept
```rust
// Conceptual: participant P sends EncryptionKeyMessage twice.
let mut enc = Encryption::<C>::new(context, our_i, &mut rng);
let msg_p: EncryptionKeyMessage<C, M> = /* deserialize P's message */
  EncryptionKeyMessage::read(&mut bytes, params).unwrap();

enc.register(p, msg_p.clone()); // OK
enc.register(p, msg_p);         // panic: "Re-registering encryption key for a participant"
```
No cryptographic forgery is needed; `EncryMessage::read` succeeds for any syntactically valid message, and the panic is hit purely by repeating the registration call for the same `Participant`.
