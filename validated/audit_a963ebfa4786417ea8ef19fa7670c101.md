## Title
Divergent conflict-marker parsers let unresolved merge conflicts be silently deleted by Copilot conflict resolution - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Elixir report describes a consensus invariant that is broken because two different subsystems compute a "count" over the same nominal domain using different rules: the required-proposal threshold is derived from the full set of active validators, while the actual enforcement (`/verify`) only admits a fixed subset (`CORE_VALIDATOR_SET_SIZE`). Because the counting domain and the enforcement domain diverge, the invariant "enough participants exist to satisfy the requirement" can be broken by an attacker who inflates the counted domain.

The same *class* of bug exists in GitHub Desktop's Copilot merge-conflict-resolution feature: the "expected hunk count" used to gate the model's response is computed by one conflict-marker parser (`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts`), while the actual splicing of resolved content back into the file is done by a **second, independent parser** (`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts`). The two parsers disagree on what counts as a conflict hunk when a malformed/unbalanced marker is present, so the validation gate can pass while the write path silently drops a legitimate, unresolved conflict block.

### Finding Description
`buildConflictContext` calls `extractConflictHunks` to enumerate conflict hunks and build `IFileConflictContext.hunks`, which becomes both (a) the content shown to Copilot in the prompt, and (b) `expectedHunkCounts` used by `validateResolutionPaths` to gate the model's output: [1](#0-0) [2](#0-1) 

`extractConflictHunks` has an early-exit bug: when an ours-marker (`<<<<<<<`) is found but no matching closing marker (`>>>>>>>`) is ever found before EOF, the inner collection loops advance `i` all the way to `lines.length`, and the outer loop then simply `continue`s — but since `i === lines.length`, the `while (i < lines.length)` loop terminates. **Any well-formed conflict block located after such an unbalanced marker is never scanned or counted:** [3](#0-2) 

`reassembleResolvedFile`, which is the function that actually writes the final file content, uses its **own separate regex-based scan** (`reassemblyOursMarker`/`reassemblySeparatorMarker`/`reassemblyTheirsMarker`) and, critically, does **not** share this early-exit behavior: when it hits an unbalanced marker it treats only that single line as literal content (`resultLines.push(lines[i]); i++`) and keeps scanning forward for further real conflict blocks: [4](#0-3) 

The consequence: if a legitimate conflict block sits *after* an unbalanced marker line in the file,
1. `extractConflictHunks` undercounts (e.g. reports 1 hunk instead of 2), so Copilot is never shown the second conflict and only returns 1 hunk resolution.
2. `validateResolutionPaths` compares `resolution.hunks.length` (1) against `expectedHunkCounts` (1, because the context builder undercounted the same way) — the counts match, so **the security-relevant gate passes**.
3. `reassembleResolutions` → `reassembleResolvedFile` is invoked against the **raw, unmodified file** (not the truncated context), so it *does* discover the second, unshown conflict block via its own scan. But `hunkIndex` has already exceeded `hunkResolutions.length` (which is only 1), so the splice guard `if (hunkIndex < hunkResolutions.length)` is false and nothing is inserted for that block — both the `<<<<<<<...>>>>>>>` markers *and* all of the "ours"/"theirs" content inside them are silently removed from the output with no error, no warning, and no indication to the user: [5](#0-4) 

The `IFileResolution.resolvedContent` produced this way is then what the app writes to disk as the "resolved" file and what the user subsequently stages and commits.

### Impact Explanation
This matches the requested impact category "silent corruption of what the user commits or pushes." An attacker who controls content the victim merges (a branch, a fork, a fetched remote) can craft a file that, when it later collides with the victim's local changes in a real merge/rebase/cherry-pick, contains an unbalanced conflict-marker-like line ahead of the genuine conflict. When the victim invokes Desktop's Copilot conflict-resolution feature, the tool reports the conflict as fully resolved (no markers remain, validation passes), but an entire legitimate hunk of code — either the attacker's or the victim's own concurrent changes — is silently deleted from the file that gets committed and pushed. This is a data-integrity/corruption issue reachable purely from repository content the attacker controls, with no local access, admin rights, or social engineering beyond a normal merge.

### Likelihood Explanation
Exploitability requires: (1) the victim to be using the AI/Copilot-assisted conflict resolution feature, (2) a real conflicting file, and (3) that file to contain, prior to the real conflict, a stray marker-like line (e.g. `<<<<<<< ` at start of a line followed by whitespace) with no subsequent `=======`/`>>>>>>>` pair before EOF — plausible in generated diffs, changelogs, documentation containing example conflict markers, or leftover artifacts from a prior improperly-resolved merge that got committed. It does not require an unusual or exotic file format, only a single mis-shaped line. The two-parser architecture (context builder vs. reassembler) makes this a structural risk rather than a one-off typo, since any future divergence between the two marker scanners reproduces the same class of bug.

### Recommendation
- **Short term:** Make `reassembleResolvedFile` and `extractConflictHunks` share a single conflict-marker-parsing implementation (or have the reassembler consume the hunk boundaries already discovered by `extractConflictHunks` instead of re-scanning the raw file independently), so the "expected" and "actual" splice points can never diverge. Additionally, treat an unbalanced ours-marker as a hard stop for the *entire file* (skip file / mark as `skippedReason`) rather than silently truncating hunk enumeration or silently discarding content in the reassembler.
- **Long term:** Add an invariant check after reassembly that the reassembled file contains zero residual conflict markers **and** that the total non-marker line count is consistent with the input (e.g., diffing hunk regions against `rawContent` to guarantee every original `<<<<<<<...>>>>>>>` block was either replaced or explicitly accounted for), failing loudly instead of writing a silently-truncated file.

### Proof of Concept
1. Create a file `example.md` on `main` containing, verbatim, a documentation snippet with an unbalanced marker line, e.g.:
   ```
   Example of a conflict marker: <<<<<<< HEAD
   (no closing markers follow in this file)
   ```
2. On a separate branch, modify a later, unrelated section of the same file to create a real merge conflict against `main`'s later edits to that same section.
3. Merge the branch into `main` locally, producing a file with: the harmless-looking unbalanced `<<<<<<<` line near the top, and a real `<<<<<<< HEAD ... ======= ... >>>>>>> branch` block further down.
4. Invoke Desktop's Copilot conflict-resolution on this file.
   - `extractConflictHunks` will stop enumerating after failing to close the first marker, returning 0 real hunks parsed correctly for the *legitimate* conflict (or, depending on exact line layout, will report a count lower than the true number of real conflicts).
   - `validateResolutionPaths` will pass because Copilot's response hunk count matches the (already wrong) `expectedHunkCounts`.
   - `reassembleResolvedFile`, scanning the raw file independently, will find the real conflict block that was never sent to the model, and because `hunkIndex >= hunkResolutions.length`, it removes the conflict markers and drops all of that hunk's content without writing any replacement or raising an error.
5. Inspect the resulting "resolved" file: the real conflicting section is missing entirely (neither side's content is present), and the file appears fully resolved with no conflict markers, ready to be committed and pushed.

Note: I was not able to locate the exact UI/write call site that ultimately persists `IFileResolution.resolvedContent` to disk (`app/src/lib/stores/copilot-store.ts` references `reassembleResolutions`/related functions but the write path itself wasn't found within available index coverage) — this would need to be confirmed against the full source (e.g. via a live Devin session) to verify whether any additional diff/review step is shown to the user before the corrupted content is committed.
