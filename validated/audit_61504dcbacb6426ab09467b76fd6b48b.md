### Title
Escrow-accounting mismatch between fee-reduced escrowed amount and full `order.inputs` amount causes a guaranteed subtraction revert in `withdraw()`, permanently locking user funds on cancel - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` escrows the **protocol-fee-reduced** amount per token, but `cancelOrder` builds the on-chain withdrawal request using the **full, pre-fee** `order.inputs` amount. `withdraw()` then performs a raw Solidity subtraction of that mismatched (larger) amount against the smaller escrowed balance, which reverts on underflow whenever a protocol fee is configured — exactly the same broken-invariant class as the reported Solana vault bug (a `checked_sub`/unwrap-style subtraction between two balances that were never guaranteed to reconcile, causing deterministic panics/reverts and blocking all forward progress for the affected state).

### Finding Description
In `placeOrder` (lines 353–458), whenever `protocolFeeBps > 0` (from `_destinationProtocolFees[destinationHash]` or the fallback `_params.protocolFeeBps`), the contract computes `reducedInputs[i].amount = originalAmount - protocolFee` and stores the *reduced* amount in escrow accounting: [1](#0-0) [2](#0-1) 

`cancelOrder`, however, constructs the `WithdrawalRequest.tokens` using `order.inputs` — the original, full, pre-fee amounts — for both the same-chain path and the cross-chain source-side path: [3](#0-2) [4](#0-3) 

`withdraw()` then blindly subtracts that (larger) `amount` from the actually-escrowed (smaller) balance, gated only by a "non-zero" check rather than a sufficiency check: [5](#0-4) 

Because Solidity ≥0.8 reverts on arithmetic underflow, `_orders[commitment][token] -= amount` panics whenever `amount > _orders[commitment][token]`, i.e., whenever `protocolFeeBps > 0`. The guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` only checks presence, not sufficiency, so it does nothing to prevent this — the exact same defect pattern documented in the external report, where `checked_sub().unwrap()` between two independently-tracked balances (`product.max_deposit_limit` vs. `product.underlying_amount`) was never validated to stay reconciled.

### Impact Explanation
Any order routed to/from a destination configured with a non-zero protocol fee becomes permanently uncancellable: the `cancelOrder` transaction always reverts, so the user's escrowed tokens (`_orders[commitment][token]`) can never be released back to them through this path. This is a direct loss/permanent lock of user funds reachable by the unprivileged order owner performing a normal, expected action (cancelling their own order) — it fits the bounty's "stealing or loss of funds" / logic-attack category, without requiring any malicious peer, relayer, or governance action beyond the routine configuration of protocol fees.

### Likelihood Explanation
This is deterministic, not probabilistic: it fires on *every* cancellation of *every* order whose destination (or default) protocol fee is non-zero, which is an ordinary governance configuration (`UpdateParams` / `_destinationProtocolFees`), not an edge case. Given protocol fees are a first-class supported feature of the contract, the bug is triggered under normal expected operating conditions.

### Recommendation
Make the amount used in `withdraw()` consistent with what was actually escrowed:
- Either recompute/store the fee-reduced amounts and use them (not `order.inputs`) when building the `WithdrawalRequest` in `cancelOrder`, for both the same-chain and cross-chain paths; or
- Change `withdraw()` to clamp the debit to the available escrowed balance instead of performing a naive subtraction (mirroring the vault patch's approach of removing the unchecked/naive subtraction entirely), e.g. `uint256 escrowed = _orders[commitment][token]; uint256 toSend = amount > escrowed ? escrowed : amount;` and transfer/decrement using `toSend`.

### Proof of Concept
1. Governance configures `protocolFeeBps > 0` for a destination (or the global `_params.protocolFeeBps`).
2. User calls `placeOrder` with `inputs = [{token: USDC, amount: 1000e6}]`. The contract computes `protocolFee`, `reducedAmount = 1000e6 - protocolFee`, and stores `_orders[commitment][USDC] = reducedAmount` (< 1000e6).
3. Before the order is filled, the user calls `cancelOrder` on the same chain. The `WithdrawalRequest` is built with `tokens: order.inputs`, i.e. `amount = 1000e6` (the full, unreduced amount).
4. `withdraw()` executes `_orders[commitment][USDC] -= 1000e6` against a balance of only `reducedAmount` → arithmetic underflow → the entire `cancelOrder` transaction reverts.
5. The user cannot retrieve their escrowed tokens via cancellation; the funds remain stuck in the contract for as long as this mismatch exists.

**Uncertainty note:** I was not able to read the destination-side `fillOrder`/`RedeemEscrow`-dispatch code in this session to confirm whether the normal (non-cancel) settlement path constructs its `WithdrawalRequest` with the same mismatched full-amount value (which would mean fills are equally blocked, making the lock permanent with no recovery path at all). The cancellation path alone, however, is a fully verified, directly reachable, unprivileged entrypoint that already demonstrates the fund-locking defect.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
