### Title
Tokenfactory denom admin can retroactively freeze existing holders' funds via `MsgUpdateDenom` allow-list with no delay or opt-out - (File: `sei-cosmos/x/bank/keeper/send.go`, `x/tokenfactory/keeper/createdenom.go`)

### Summary
A tokenfactory denom's admin (any account that created a `factory/{creator}/{subdenom}` token — an unprivileged, permissionless role reachable by an ordinary transaction sender) can unilaterally attach or change a bank `AllowList` for that denom via `MsgUpdateDenom` at any time after the token has already been minted and distributed to holders. This mirrors the `SetProtocol` `SetToken`/`StreamingFeeModule` "unstable functionality" pattern: a privileged component owner can post-hoc change enforcement rules that were not agreed to when users acquired the asset, with no time delay and no opt-out for existing holders.

### Finding Description
The tokenfactory module documents that a denom's admin has broad unilateral power (mint, burn, force-transfer, change admin) and that a `MsgUpdateDenom` message lets the admin set an `AllowList` on the denom's bank metadata at will [1](#0-0) . The bank keeper's `SendCoins`/`MultiSend` paths enforce this allow list by rejecting any sender or receiver of a factory-prefixed coin who is not present in the currently stored `AllowList` for that denom [2](#0-1) , using `IsInDenomAllowList` which returns `false` (blocking the transfer) for any factory-denom holder not explicitly listed [3](#0-2) .

Because the allow list is looked up fresh at every transfer (not snapshotted at mint time or gated by a waiting period), a denom admin can:
1. Create a denom and let users freely acquire/trade it while no allow list exists.
2. Later call `MsgUpdateDenom` to set an allow list containing only addresses of the admin's choosing (e.g., an exchange the admin controls) — instantly making all previously-acquired balances non-transferable for every excluded holder, confirmed by the existing test `TestUpdateDenom`/`TestSendReceiverNotInAllowList`/`TestSendSenderNotInAllowList` which show sends are rejected with "not allowed to send/receive funds" once an allow list excluding an address is set [4](#0-3) [5](#0-4) .
3. The only requirement is that the sender of `MsgUpdateDenom` is the current denom admin — no consent from holders, no time delay, no restriction that the allow list can only be set before tokens are distributed [6](#0-5) .

This is the direct sei-chain analog of the `SetToken` bug class: a component whose behavior users implicitly trust (a fungible token) can be reconfigured after the fact by its privileged creator/admin to defraud or lock out holders, exactly as the report describes managers bypassing agreed fee/behavior bounds by altering module state with no delay for users to react.

### Impact Explanation
Any tokenfactory denom admin (an ordinary, permissionless role — anyone who called `MsgCreateDenom`) can permanently freeze the funds of any other holder of that denom simply by submitting `MsgUpdateDenom` with a restrictive `AllowList`. Holders who acquired the token believing it was freely transferable (as it was at acquisition time) have no on-chain recourse and no advance warning; their balance becomes unspendable/untransferable immediately upon the admin's transaction being included in a block. This satisfies the "permanent freezing of funds" impact category.

### Likelihood Explanation
High. `MsgCreateDenom` and `MsgUpdateDenom` are fully permissionless and reachable by any signed transaction; no governance or validator involvement is required. The allow-list enforcement path in `bank` keeper's `Send`/`MultiSend` is exercised on every token transfer, so the attack requires only two ordinary transactions from the denom admin (create denom, then later update it), with no special timing constraints or race conditions.

### Recommendation
Consider one or more of: (1) disallowing `MsgUpdateDenom` from narrowing an existing allow list to exclude addresses that already hold a nonzero balance of the denom, (2) requiring the allow list to be fixed at `MsgCreateDenom` time and immutable thereafter (or only settable before the first mint), or (3) introducing a time-delayed activation for allow-list changes (analogous to the report's suggested `PENDING` → `INITIALIZED` delay) so existing holders have a window to exit before new restrictions take effect.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` to create `factory/attacker/TOKEN` with no allow list; `AuthorityMetadata.Admin = attacker`.
2. Attacker mints and freely distributes/sells `TOKEN` to victims (no allow list exists yet, so `IsInDenomAllowList` returns `true` for everyone) [3](#0-2) .
3. Attacker later submits `MsgUpdateDenom` for `factory/attacker/TOKEN` with `AllowList{Addresses: [attackerControlledAddr]}` [7](#0-6) .
4. Any subsequent `MsgSend`/`MsgMultiSend` involving a victim's balance of `TOKEN` is rejected with `"%s is not allowed to send funds"` / `"...receive funds"` [8](#0-7) , permanently freezing victims' holdings while the admin's own address remains unaffected.

# Token Factory

The tokenfactory module allows any account to create a new token with
the name `factory/{creator address}/{subdenom}`. Because tokens are
namespaced by creator address, this allows token minting to be
permissionless, due to not needing to resolve name collisions. A single
account can create multiple denoms, by providing a unique subdenom for each
created denom. Once a denom is created, the original creator is given
"admin" privileges over the asset. This allows them to:

- Mint their denom to any account
- Burn their denom from any account
- Create a transfer of their denom between any two accounts
- Change the admin. In the future, more admin capabilities may be added. Admins
  can choose to share admin privileges with other accounts using the authz
  module. The `ChangeAdmin` functionality, allows changing the master admin
  account, or even setting it to `""`, meaning no account has admin privileges
  of the asset.

func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
