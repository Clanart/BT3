### Title
Shared custody pool across chains with independently-set `Precisions` lets mismatched decimals drain escrow via `pallet-hyper-fungible-token` - (File: modules/pallets/hyper-fungible-token/src/lib.rs, modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token` registers one asset against multiple destination chains, each with its own `Precisions::<AssetId, StateMachine> -> u8` decimal record, but backs *all* of those chains with a single, shared custody account (`pallet_account()` for native assets, or a single fungible supply for non-native assets). The only guard on the per-chain decimal value is `config.decimals >= local_decimals`; there is no requirement that the decimals be *consistent with the real token deployed on that chain*, nor is escrow segregated per destination chain. A decimal misconfiguration for any one of the registered chains lets inbound/outbound conversion mint or release amounts against the shared pool that don't match what was actually escrowed — the same broken invariant as the reported `TokenMapConfigType` / `update_mapping` decimal-mismatch bug.

### Finding Description
`register_token` and `update_token` accept, per `(asset, chain)` pair, a `decimals: u8` value that is stored in `Precisions` and later used, unchecked against the actual on-chain ERC20/ERC6160 contract's `decimals()`, to convert amounts at the ISMP boundary: [1](#0-0) 

The same escrow pot is used regardless of which destination chain a `send` targets — for the native asset it is always `Self::pallet_account()`: [2](#0-1) 

and for non-native assets it is the single fungible-asset supply managed by `T::Assets` (burn on send, mint on receive) with no per-chain accounting at all: [3](#0-2) 

Outbound scaling multiplies by `10^(erc_decimals - local_decimals)` using whatever `Precisions` value is on file for the destination chain: [4](#0-3) 

Inbound scaling in `on_accept` divides by `10^(erc_decimals - local_decimals)` using the `Precisions` value on file for the *source* chain of the incoming message: [5](#0-4) 

Because a single asset can be registered against several EVM chains (`registration.chains` is a map, and `update_token` lets an admin `add_chains` incrementally), and because the only validation is `config.decimals >= local_decimals` with no cross-chain consistency check and no verification against the destination contract's actual `decimals()`, two chains holding the "same" token can end up with different `Precisions` entries relative to their real on-chain decimals. Since custody is pooled globally rather than per-chain, an amount escrowed after being scaled up using chain A's (correct) precision can be redeemed by triggering an inbound message that is scaled down using chain B's (wrong/lower) precision, releasing a disproportionately larger amount from the shared pool than was ever escrowed for chain B. This is the exact cross-chain decimal-mismatch invariant break described in the seed report, just realized through `Precisions`/`pallet_account()` instead of `TokenMapConfigType`/`ChainAddress`.

### Impact Explanation
If the shared pool's `Precisions` records diverge from a chain's real token decimals (an admin config error when onboarding a second/third destination chain for an already-registered asset — the same class of realistic mistake called out in the seed report), an attacker can mint/withdraw far more value than was deposited from the pallet's single custody account, draining funds owed to all other users of that asset across every registered chain. This is a direct "stealing or loss of funds" / cross-chain value-extraction impact matching the bounty's accepted impact categories.

### Likelihood Explanation
Likelihood is Medium: it requires an admin misconfiguration of `Precisions` when calling `register_token`/`update_token` for a new chain (same precondition as the original H-01 report, which was still accepted and fixed upstream). No malicious relayer, prover, or governance actor is needed — the vulnerable code path is the pallet's own conversion and custody logic which lacks any structural guard (e.g. verifying the destination contract's `decimals()` on-chain, or segregating escrow per chain) to catch or contain such a mistake, unlike the fix applied to the analogous `TokenMapConfigType` bug.

### Recommendation
- Segregate custody per `(asset, chain)` pair (e.g. per-chain escrow sub-accounts or per-chain issuance tracking) so a decimal error on one chain cannot be redeemed against funds escrowed for another chain.
- When registering/updating a chain's `Precisions`, cross-check consistency: either fetch/attest the real ERC20 `decimals()` at governance-proposal time, or require that all chains for a given asset agree on a canonical precision unless explicitly justified, mirroring the `normalize_decimals` / decimal-mismatch validation adopted for the seed report's fix.
- Add an invariant check (e.g. a runtime storage migration/consistency check) that total minted-outstanding-per-chain never exceeds what was actually escrowed for that chain, closing the shared-pool arbitrage surface even if a decimal error is introduced.

### Proof of Concept
1. Admin registers native asset (local `Decimals = 10`) for `StateMachine::Evm(1)` with `Precisions(asset, Evm(1)) = 18` (correct — the real ERC20 on chain 1 uses 18 decimals).
2. User calls `send` with `destination = Evm(1)`, `amount = 100` (10-decimal units). `pallet_account()` escrows `100`; `erc20_amount = 100 * 10^(18-10) = 100 * 10^8` is dispatched to chain 1's contract. This is correct and matches the real token's decimals.
3. Admin later calls `update_token` to `add_chains` for `StateMachine::Evm(2)`, mistakenly registering `Precisions(asset, Evm(2)) = 10` even though chain 2's real ERC20 deployment actually uses 18 decimals (passes the `config.decimals >= local_decimals` check since `10 >= 10`) — see `modules/pallets/hyper-fungible-token/src/lib.rs` lines 390-421.
4. An inbound `Send` message purportedly "from" chain 2's registered contract with `amount = 100 * 10^8` (an amount an attacker can construct because it is merely ABI-decoded call data from the registered contract address, not independently verified against real transferred value) arrives at `on_accept`. Using `Precisions(asset, Evm(2)) = 10`, `convert_to_balance` computes `100*10^8 / 10^(10-10) = 100*10^8`, releasing `100*10^8` units (10-decimal) from the single shared `pallet_account()` — 10^8 times larger than the `100` units actually escrowed in step 2.
5. `pallet_account()` is drained far beyond the funds legitimately owed, at the expense of all other holders of the asset across every chain it is registered on.
