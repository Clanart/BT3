### Title
Unbounded recursive parsing of attacker-controlled coin memos causes stack-consumption crash in wallet sync - ([File: chia/wallet/puzzles/custody/custody_architecture.py])

### Summary
CVE-2017-5950 describes `yaml-cpp`'s `SingleDocParser::HandleNode` recursing without depth limits on attacker-supplied YAML, causing stack exhaustion and crash. The analogous bug class in this codebase is unbounded recursive parsing of an attacker/spend-bundle-controlled structure with no depth cap — found in `PuzzleWithRestrictions.from_memo()`.

### Finding Description
`PuzzleWithRestrictions.from_memo()` recursively rebuilds a custody structure from a CLVM `Program` memo. When the parsed hint indicates an `MofN` node, it recurses into `PuzzleWithRestrictions.from_memo()` once per member, with no bound on nesting depth: [1](#0-0) 

The `member_memos` list comes straight from an arbitrary CLVM `Program` (`MofNHint.from_program`) supplied inside a coin's memo: [2](#0-1) 

This memo blob is untrusted, attacker-controlled data: any coin spend can attach an arbitrary `CREATE_COIN` memo, and `chia/pools/plotnft_drivers.py`'s `PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` directly on the memo of a newly created coin while syncing plotNFT/pool state from a coin spend: [3](#0-2) 

Because `from_memo` recurses once per `MofN` layer with no maximum-depth check, a crafted coin memo containing a deeply nested `MofN` hint (e.g. thousands of nested single-member `MofN` wrappers) causes Python's call stack to grow unbounded during parsing, exactly mirroring the `HandleNode` stack-consumption pattern in the CVE.

### Impact Explanation
A wallet (or any code path, such as pool/plotNFT sync) that parses on-chain coin memos through `PuzzleWithRestrictions.from_memo()` can be crashed by a `RecursionError`/native stack overflow when processing a maliciously crafted memo attached to an ordinary coin spend. This is a spend-triggered denial-of-service against wallet/pool-sync processing — an unprivileged spend-bundle submitter can construct such a memo and have it processed by any wallet client that later parses that coin's memo (e.g. during plotNFT pool-transition sync), halting or crashing that client's transaction-processing/sync logic. This matches the "spend-triggered transaction-processing halt" impact category permitted by the validation rules.

### Likelihood Explanation
Likelihood is limited by reachability: this parser only runs when a wallet client actively interprets a specific memo shape (`CHIP-0043` custody namespace) associated with plotNFT/pool singleton coins, not on every incoming spend bundle or in consensus-critical mempool/block validation. An attacker would need to get a target wallet to sync/inspect a coin whose memo they control (e.g., by directing a plotNFT-style singleton coin at the target, or otherwise causing the target's pool/plotNFT sync code to call `from_memo` on attacker data). This is plausible for plotnft/pool wallet users who sync arbitrary singleton lineages, but it is not a universally-reachable mempool-admission path, so likelihood is moderate rather than high.

### Recommendation
Add an explicit recursion-depth limit (or convert `PuzzleWithRestrictions.from_memo`/`MofNHint.from_program` recursion into an iterative, stack-based traversal, similar to the non-recursive pattern already used in `sha256_treehash`) and reject memos whose `MofN` nesting exceeds a sane maximum before recursing.

### Proof of Concept
1. Construct a CLVM memo program matching the `CHIP-0043` `PuzzleWithRestrictions` shape where the puzzle hint is an `MofN` with `m=1` and a single member whose puzzle hint is itself another `MofN` with `m=1` and one member, nested thousands of times deep (each nesting level built with `MofNHint.to_program()`/`PuzzleWithRestrictions.memo()` shape as consumed by `from_memo`).
2. Attach this memo blob to a `CREATE_COIN` condition as the memo of a coin created by an ordinary spend (e.g., mimicking a plotNFT/pool singleton coin creation), and get it included in a block or observed by a target wallet.
3. Trigger the target wallet's pool/plotNFT sync path that calls `PlotNFTPuzzle.get_next_from_coin_spend()` → `PuzzleWithRestrictions.from_memo(memo_blob)` on the coin's memo.
4. Observe the process crash with a `RecursionError` or native stack overflow before any validation of the memo's semantic correctness occurs, since the recursive descent in `from_memo`/`MofNHint.from_program` runs to full depth before any content validation happens.

    @classmethod
    def from_memo(cls, memo: Program) -> PuzzleWithRestrictions:
        if memo.atom is not None or memo.first() != Program.to(cls.spec_namespace):
            raise ValueError("Attempting to parse a memo that does not belong to this spec")
        nonce = memo.at("rf")
        restriction_hints_prog = memo.at("rrf")
        further_branching_prog = memo.at("rrrf")
        puzzle_hint_prog = memo.at("rrrrf")
        additional_memos = memo.at("rrrrrf") if memo.at("rrrrr").atom is None else None
        restriction_hints = [RestrictionHint.from_program(hint) for hint in restriction_hints_prog.as_iter()]
        further_branching = further_branching_prog != Program.to(None)
        if further_branching:
            m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
            puzzle: MIPSComponent = MofN(
                m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]
            )
        else:
            puzzle_hint = MemberHint.from_program(puzzle_hint_prog)
            puzzle = UnknownMember(puzzle_hint)

        return PuzzleWithRestrictions(
            nonce=nonce.as_int(),
            restrictions=[UnknownRestriction(hint) for hint in restriction_hints],
            puzzle=puzzle,
            additional_memos=additional_memos,
        )
