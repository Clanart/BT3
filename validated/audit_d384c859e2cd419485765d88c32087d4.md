### Title
DKG participant can register another participant's encryption key, letting that party decrypt shares not intended for them - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The bug class of the external report (CVE-2023-25150) is *missing authorization on whose resource is accessed*: any user who can reach the endpoint can read another user's content because the code never validates that the accessor is entitled to that specific file. The direct analog in Serai is in PedPoP's per-recipient encryption layer: `Decryption::register` accepts any `enc_key` for a participant with no proof of possession and no uniqueness check across participants, and `EncryptionKeyMessage` carries no proof binding the key to its registrant. A participant can therefore register *someone else's* public encryption key as their own; every share "for" them is then encrypted under the victim's ECDH key and — since all `DkgShares` ciphertexts are published on the tributary — the victim (or any holder of the corresponding private key) can read share contents addressed to a different participant index without any permission check on the binding.

### Finding Description
`Encryption::new` generates a long-term ECDH key pair per participant, advertised inside `EncryptionKeyMessage.enc_key` [1](#0-0) . When processing commitments, `SecretShareMachine::verify_r1` calls `self.encryption.register(l, msg)`, which stores `msg.enc_key` under `participant` — the only validation is an assert that the same participant doesn't register twice [2](#0-1) . Nothing proves the registrant knows the discrete log of `enc_key` (the Schnorr PoK in `Commitments` covers only `commitments[0]` [3](#0-2) ), and nothing rejects a key already registered by another participant.

`Encryption::encrypt` then encrypts each share to `self.decryption.enc_keys[&participant]` [4](#0-3) , and `encrypt` derives the ChaCha20 key solely from `ecdh(key, to)` — the message binds `from` via `pop_challenge` but never binds the intended *recipient* index [5](#0-4) [6](#0-5) .

In the coordinator, all `DkgShares` ciphertexts are stored on-chain via `DkgShare::set` for every (from, to) pair [7](#0-6) , so any participant can read ciphertexts addressed to others. A malicious participant B who sets `enc_key_B = enc_key_A` causes every share addressed to B's index to be encrypted under A's key: A computes `ecdh(enc_key_A_priv, msg.key)` and recovers plaintext `f_i(B)` for all senders `i`, i.e. the exact contents of share messages A was never entitled to read — the share file's "permission check" (which participant index the ciphertext is for) is never validated because the recipient identity is cryptographically absent from the encryption and registration.

### Impact Explanation
A obtains B's incoming secret share `Σ f_i(B)` — secret key material belonging to another participant — purely from public on-chain bytes and their own key. The attacker needs control of one index (B, to register the duplicated key) plus read access to A's private key path, or equivalently two colluding-but-sub-threshold participants A and B. This leaks a FROST secret share and its verification relationship, degrading the threshold: any party holding B's share can produce valid signature shares as B in subsequent signing sessions for a key B participated in forming. This is a secret-material disclosure reachable by unprivileged DKG participants with public inputs, matching the Medium severity class of the report.

### Likelihood Explanation
Medium-low. It requires a malicious DKG participant willing to register a duplicated/foreign `enc_key` (which makes their own shares undecryptable and may fault their DKG participation), and a second party (A) whose key was targeted, or a colluding pair. However, no protocol check detects it: `verify_r1` accepts the registration, `encrypt` happily encrypts under the copied key, and the share verification in `calculate_share` still passes for shares A legitimately receives. The window is real whenever all shares are published (as Serai's tributary does for blame) and DKG retries/removals let a t-of-n key still form.

### Recommendation
- Require a Schnorr proof of possession over `enc_key` bound to `(context, participant)` inside `EncryptionKeyMessage`, verified in `Decryption::register`.
- Reject `enc_key` values already registered to a different `Participant` (enforce global uniqueness of encryption keys per DKG attempt).
- Optionally bind the intended recipient index into `pop_challenge`/`cipher` so ciphertexts are non-reassignable even if keys are duplicated.

### Proof of Concept
1. In a PedPoP round with participants {A=1, B=2, C=3}, B observes A's broadcast `EncryptionKeyMessage` and copies `enc_key_A` into B's own `EncryptionKeyMessage` (`Decryption::register` accepts it — no PoP, no uniqueness check, `crypto/dkg/pedpop/src/encryption.rs:351-362`).
2. Each sender `i` calls `generate_secret_shares`; `Encryption::encrypt(i → B)` uses `enc_keys[B] = enc_key_A`, producing `EncryptedMessage { key: kG, msg: ChaCha20(ecdh(k, enc_key_A)) ⊕ f_i(B) }` (`crypto/dkg/pedpop/src/lib.rs:366-369`).
3. A reads B's ciphertexts (published via `DkgShare::set` on the tributary) and computes `cipher(context, ecdh(enc_key_A_priv, msg.key)).apply_keystream(msg)`, recovering each `f_i(B)` in the clear — content addressed to participant B obtained by participant A with no authorization check on the binding, exactly the "read another user's file" shape.

fn encrypt<R: RngCore + CryptoRng, C: Ciphersuite, E: Encryptable>(
  rng: &mut R,
  context: [u8; 32],
  from: Participant,
  to: C::G,
  mut msg: Zeroizing<E>,
) -> EncryptedMessage<C, E> {
  /*
  The following code could be used to replace the requirement on an RNG here.
  It's just currently not an issue to require taking in an RNG here.
  let last = self.last_enc_key.to_bytes();
  self.last_enc_key = C::hash_to_F(b"encryption_base", last.as_ref());
  let key = C::hash_to_F(b"encryption_key", last.as_ref());
  last.as_mut().zeroize();
  */

  // Generate a new key for this message, satisfying cipher's requirement of distinct keys per
  // message, and enabling revealing this message without revealing any others
  let key = Zeroizing::new(C::random_nonzero_F(rng));
  cipher::<C>(context, &ecdh::<C>(&key, to)).apply_keystream(msg.as_mut().as_mut());

  let pub_key = C::generator() * key.deref();
  let nonce = Zeroizing::new(C::random_nonzero_F(rng));
  let pub_nonce = C::generator() * nonce.deref();
  EncryptedMessage {
    key: pub_key,
    pop: SchnorrSignature::sign(
      &key,
      nonce,
      pop_challenge::<C>(context, pub_nonce, pub_key, from, msg.deref().as_ref()),
    ),
    msg,
  }
}

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}
