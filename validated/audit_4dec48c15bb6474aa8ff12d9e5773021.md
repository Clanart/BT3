### Title
All-or-nothing multi-asset price resolution causes healthy, unrelated positions to be permanently blocked when any single enabled collateral/debt price fails - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`get-assets` resolves prices for every asset currently enabled as collateral or debt for a user's position mask in a single batch call, and unconditionally `unwrap-panic`s the result. If price resolution for even one of those assets fails (staleness check, confidence check, oracle call failure), the entire call aborts, blocking every market operation that depends on `get-assets` for that user — even operations that only concern a different, healthy asset.

### Finding Description
`get-assets` builds a list of every enabled collateral/debt asset in the user's mask, fetches their oracle configs, and resolves all their prices together via `price-multi-resolve`, which internally uses `fold iter-price-multi` and marks the whole batch invalid if any single asset's `price-resolve` fails: [1](#0-0) 

`price-resolve` itself reverts with `ERR-ORACLE-INVARIANT` if the price is non-positive or the timestamp is not fresh (staleness gating) for any asset in that batch: [2](#0-1) 

`get-assets` then calls `unwrap-panic` on `price-multi-resolve`'s result rather than propagating a graceful error: [3](#0-2) 

Because the mask passed into `get-assets` covers *all* of the user's enabled collateral and debt assets (not just the asset relevant to the current operation), a single asset in that mask with a stale/invalid price (e.g., an oracle feed that has not updated within `max-staleness`) causes `unwrap-panic` to abort the whole transaction. This blocks all position operations gated through `get-assets` — including withdrawing a completely different, healthy collateral asset or repaying debt — for as long as that one unrelated asset's price remains unresolvable. This mirrors the reported bug class: one bad item in a batch (there: a zero-address `rewardToken`; here: one stale/invalid-price asset) causes the *entire* batch operation to revert, denying service to unrelated, otherwise-valid items in the same batch.

### Impact Explanation
This lands on **temporary freezing of funds**: a user holding multiple collateral/debt assets can be fully locked out of managing their position — including withdrawing healthy collateral or repaying debt to avoid liquidation — solely because one unrelated enabled asset in their mask has a stale or momentarily-unavailable price feed. Liquidators relying on the same `get-assets`/notional-evaluation path for unhealthy positions could similarly be blocked, delaying liquidations and increasing bad-debt risk.

### Likelihood Explanation
Oracle staleness or transient unavailability for any single supported asset (Pyth/DIA feed delay, congestion, etc.) is a realistic and periodically expected condition, not a hypothetical edge case. Any user holding more than one enabled asset is exposed as soon as any one of those feeds goes stale, making this reachable without any privileged action or misconfiguration — it is a structural design gap in how `get-assets` batches price resolution.

### Recommendation
Avoid a single failing asset price from blocking unrelated operations:
- Only resolve prices for assets that are actually required for the specific operation being performed, rather than the full enabled mask, where feasible.
- Replace `unwrap-panic` in `get-assets` with a graceful error path (e.g., `try!`/`unwrap!` returning a typed error) so callers can decide whether to proceed with a partial result or fail predictably instead of panicking.
- Consider allowing operations that don't touch the stale asset (e.g., withdrawing a different, fully-priced collateral, or repaying debt) to proceed even if one unrelated asset's price is temporarily unavailable.

### Proof of Concept
1. User has two enabled collaterals, Asset A (STX) and Asset B (sBTC), both healthy.
2. Asset B's Pyth feed stops updating and its cached timestamp exceeds `max-staleness`.
3. User calls `collateral-remove` (or `borrow`/`repay`) against Asset A only.
4. Internally, `get-assets` is invoked with the user's full position mask, which includes Asset B. [3](#0-2) 
5. `price-multi-resolve`/`iter-price-multi` attempts to resolve Asset B's price, `price-resolve` fails the `oracle-timestamp-fresh` check and returns `ERR-ORACLE-INVARIANT`, which `iter-price-multi` converts to `{valid: false}`. [4](#0-3) 
6. `price-multi-resolve` asserts `valid` is true and returns `ERR-ORACLE-MULTI`; `get-assets`'s `unwrap-panic` then aborts the entire transaction.
7. Result: the user cannot withdraw Asset A, repay debt, or perform any `get-assets`-gated action until Asset B's oracle feed becomes fresh again, even though Asset A and the operation itself never needed Asset B's price.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))

  (let ((mask-enabled (get-enabled-bitmap))

        (asset-ids (map get-asset-id assets-list))
