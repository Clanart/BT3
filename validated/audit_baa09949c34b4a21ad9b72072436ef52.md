### Title
`SchnorrAggregate::verify` vacuously accepts an empty aggregate signature — a zero-signer "signature" verifies as valid - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The reported bug class is a permission/validity check that iterates an attacker-supplied list, vacuously returns `true` on an empty list, and thereby authorizes an operation with no actual authorization behind it (`CheckPermission` over `Servers=[]` followed by a fanout to every server). The direct Serai analog lives in `SchnorrAggregate::verify` (`crypto/schnorr/src/aggregate.rs:127-146`): when the aggregate carries `Rs=[]` and `s=0`, and the statement list `keys_and_challenges` is empty, the length parity check passes (`0 == 0`), zero statements are queued, and the multiexp reduces to `0 * G = identity`, so `verify` returns `true`. An aggregate signature that attests to nothing is accepted as fully valid — the exact same vacuous-true-on-empty-list root cause. This is reachable entirely from public bytes via `SchnorrAggregate::read` (`aggregate.rs:77-88`), which accepts a `u32` count of `0` with no rejection.

### Finding Description
`SchnorrAggregate::verify` performs only a length-parity check before building the multiexp:

```rust
pub fn verify(&self, dst: &'static [u8], keys_and_challenges: &[(C::G, C::F)]) -> bool {
    if self.Rs.len() != keys_and_challenges.len() {
        return false;
    }
    ...
    pairs.push((-self.s, C::generator()));
    multiexp_vartime(&pairs).is_identity().into()
}
```

With `Rs=[]`, `s=0`, and `keys_and_challenges=[]`:

- `self.Rs.len() == keys_and_challenges.len()` → `0 == 0` passes.
- The `for` loop over `keys_and_challenges` iterates zero times — no challenges are appended to the digest, no pairs are queued.
- `pairs = [(-0, G)]`; `multiexp_vartime` yields the identity; `verify` returns `true`.

The encoding side confirms `read` accepts `len = 0` (`aggregate.rs:78-85` reads a `u32` count and loops zero times), so the entire forgery is a 5-byte blob: `00 00 00 00` followed by the encoding of scalar `0`.

The producer side is asymmetric: `SchnorrAggregator::complete` (`aggregate.rs:175-178`) explicitly refuses to emit an aggregate over zero signatures (`if self.sigs.is_empty() { return None; }`). Honest code can never produce the empty aggregate, yet the verifier accepts it — so the `verify` side is strictly weaker than the `sign` side, the same asymmetry as nezha's `createCron` accepting `Servers=[]` where no legitimate flow produces it. Downstream, any caller that derives `keys_and_challenges` from an attacker-influenced batch of statements (e.g., "verify that every claimed signer signed their message" where the claim set is empty, or a batched-approval check that short-circuits to zero statements) will treat an empty forgery as authorization for the whole batch — the structural mirror of `Cover=CronCoverAll, Servers=[]` skipping `CheckPermission` and applying to everything.

A secondary observation worth noting: `weight()` (`aggregate.rs:22-65`) derives the per-signature weights from a transcript that commits only to the challenges — the public keys and `R` values are never appended to the digest. The doc-comment at `aggregate.rs:120-125` does document that challenges MUST bind the key/nonce/message, so a rogue-`R` forgery against non-empty statement lists falls under documented-MUST misuse; the empty-list acceptance, however, is not covered by any documented precondition and is a defect in the verifier itself.

### Impact Explanation
A forged aggregate signature is one of the explicitly accepted impact classes. Any protocol built on this verifier that can reach the empty-statement path accepts a signature no one produced — e.g., a "the set approved this batch" check satisfied with an empty `keys_and_challenges` list, granting unauthenticated approval. Severity is bounded by the requirement that the calling context reach `verify` with an empty statement list; where it does, the result is a complete authentication bypass (Medium–High depending on the integrator's gating).

### Likelihood Explanation
Reachability requires a caller that constructs `keys_and_challenges` from attacker-influenced inputs such that it can be empty (e.g., a batch of zero pending items, or a signer set derived from attacker-supplied data) and then calls `verify` on attacker-supplied bytes. `SchnorrAggregate::read` makes the forgery trivially constructible (`[0u32 len][s=0]`). I was not able to enumerate in-repo callers of `SchnorrAggregate::verify` within the available search budget, so the concrete in-repo caller reachability is unconfirmed; the defect in the in-scope verifier itself is confirmed by the code.

### Recommendation
Reject vacuous verification, mirroring the suggested "reject empty `Servers` for `Cover=CronCoverAll`" fix:

```rust
if keys_and_challenges.is_empty() || self.Rs.len() != keys_and_challenges.len() {
    return false;
}
```

Optionally also commit each `(key, Rs[i])` pair into the weight transcript (defense-in-depth against callers whose challenges don't bind `R`), though the primary fix is the non-empty statement requirement.

### Proof of Concept
```rust
// For any Ciphersuite C and any dst:
let mut bytes = vec![0u8; 4];            // Rs count = 0
bytes.extend(C::F::ZERO.to_repr());      // s = 0
let sig = SchnorrAggregate::<C>::read(&mut &bytes[..]).unwrap();
assert!(sig.verify(b"any_dst", &[]));    // vacuously true — forged "signature"
```
No private key, nonce, or participation is needed; the 5-byte encoding verifies for every `dst` against an empty statement list.
