### Title
Citrea LCP Prover External Call Blocks Operator Kickoff and Reimbursement — (`core/src/task/payout_checker.rs`, `core/src/operator.rs`)

---

### Summary

`PayoutCheckerTask::run_once` and `get_next_txs_to_send` both call `fetch_validate_and_store_lcp` — an external RPC call to the Citrea light-client prover — **before** the operator's kickoff connector is committed to the database. If the Citrea LCP prover is unavailable or returns an error, the entire database transaction is rolled back, the payout is never marked as handled, and the kickoff is never initiated. This is a direct analog of M-03: an external call that, when it fails, permanently impairs a critical bridge operation until the external service recovers.

---

### Finding Description

In `PayoutCheckerTask::run_once`, the sequence is:

1. `handle_finalized_payout` is called — it assigns a kickoff connector and may advance the round index.
2. `fetch_validate_and_store_lcp` is called to pre-cache the light-client proof for a potential future challenge response.
3. `end_round` is called (automation path).
4. `mark_payout_handled` is called.
5. `dbtx.commit()` is called. [1](#0-0) 

If step 2 fails — because `get_light_client_proof_by_l1_height` returns an error or `None` — the `?` operator propagates the error, `dbtx` is dropped without committing, and **all effects of step 1 are rolled back**. The payout remains in the unhandled queue. [2](#0-1) 

The same pattern exists in `get_next_txs_to_send` (the manual reimbursement RPC path): `fetch_validate_and_store_lcp` is called with `?` before the kickoff transaction is pushed to `txs_to_send`, so the kickoff tx is never returned if the LCP prover is unavailable. [3](#0-2) 

The external call itself reaches the Citrea light-client prover via `get_light_client_proof_by_l1_height`. If the prover is lagging, misconfigured, or temporarily down, it returns `None` or an RPC error, which `fetch_validate_and_store_lcp` converts to a hard `BridgeError`: [4](#0-3) 

The LCP is only **needed** during the assert phase (when responding to a challenge). Pre-fetching it in `PayoutCheckerTask` is a caching optimisation, but the code treats a cache-miss or prover error as a fatal blocker for the kickoff itself.

---

### Impact Explanation

The operator has already fronted BTC for the user's withdrawal (payout transaction on-chain). To recover those funds, the operator must initiate a kickoff transaction within the protocol's timelock window. If `PayoutCheckerTask` cannot complete because the Citrea LCP prover is unavailable:

- The kickoff connector is never assigned in the DB.
- The kickoff transaction is never sent.
- If the timelock window expires before the prover recovers, the operator's collateral UTXO becomes slashable and the reimbursement path is permanently closed.

This is a **loss/permanent lock of operator collateral and reimbursement outputs** — within the allowed impact gate.

---

### Likelihood Explanation

The Citrea light-client prover is a separate service (`light_client_prover_url`) that generates ZK proofs for L1 block heights. It can legitimately be:

- Temporarily unavailable (restart, upgrade, network partition).
- Lagging behind the current L1 tip (proof not yet generated for the payout block height).
- Returning `None` for a block height it has not yet processed.

Any of these transient conditions causes `fetch_validate_and_store_lcp` to return an error, which blocks the kickoff indefinitely. No privileged access or malicious actor is required — normal operational variance of the prover service is sufficient.

---

### Recommendation

**Short term**: Decouple the LCP pre-fetch from the kickoff commitment. Catch the error from `fetch_validate_and_store_lcp` in `PayoutCheckerTask`, log a warning, and allow `mark_payout_handled` and `dbtx.commit()` to proceed. The LCP can be fetched (and retried) lazily when `send_asserts` actually needs it — where it is already fetched again independently.

**Long term**: Introduce a dedicated retry task for LCP caching that is separate from the kickoff lifecycle, so a prover outage never blocks the critical reimbursement path.

---

### Proof of Concept

1. Operator fronts BTC for withdrawal index `N`; payout tx is mined at Bitcoin block height `H`.
2. `PayoutCheckerTask::run_once` fires; `handle_finalized_payout` assigns kickoff connector `(round=R, kickoff=K)` inside `dbtx`.
3. `fetch_validate_and_store_lcp(H, N, ...)` calls `get_light_client_proof_by_l1_height(H)` on the Citrea LCP prover.
4. Prover returns `None` (proof not yet generated) → `fetch_validate_and_store_lcp` returns `Err("Light client proof could not be fetched found for block height H")`.
5. `?` propagates; `dbtx` is dropped without commit; kickoff connector assignment is rolled back.
6. `mark_payout_handled` is never called; payout remains in the unhandled queue.
7. Task retries every `PAYOUT_CHECKER_POLL_DELAY` (60 s in production). If the prover is down for longer than the protocol's kickoff timelock, the operator's collateral is permanently lost. [5](#0-4) [6](#0-5) [7](#0-6)

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;

        dbtx.commit().await?;

        Ok(true)
    }

    ) -> Result<Receipt, BridgeError> {
        let saved_data = db
            .get_lcp_for_assert(dbtx.as_deref_mut(), deposit_index)
            .await?;
        if let Some(lcp) = saved_data {
            // if already saved, do nothing
            return Ok(lcp);
