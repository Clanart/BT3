Based on my investigation, the incoming daemon message logging path is already redacted — `redact_sensitive_data()` is applied before the "Received message" debug log at [1](#0-0) , and the redaction is verified by `test_message_logging_redaction` [2](#0-1) .

However, one code path bypasses this redaction: the unknown-command fallback at [3](#0-2)  logs the **raw, unredacted** `message` dict (`self.log.error(f"UK>> {message}")`) when a command doesn't match `get_command_mapping()`, is not a keychain command, and is not `ping`. Since `message["data"]` here is the original unredacted dict (not the `redacted_data` copy created earlier at line 296), any caller sending a bogus/misspelled `command` name together with sensitive fields (e.g., `password`, `private_key`, `mnemonic`, `passphrase`) in `data` would have those secrets written in plaintext to the daemon log file via this branch — a local, unprivileged RPC caller could trigger this simply by sending any unrecognized command.

That said, this requires local RPC/daemon-socket access, which is inside the semi-trusted local/admin RPC surface per the scope rules, but it is a real gap independent from the already-tested/patched main redaction path. Given the report's CVSS requires local/adjacent access with elevated privilege (AV:A, PR:H), and here the daemon socket is already only reachable by an authenticated local TLS client (same trust boundary as the original Yugabyte bug — local log access by a lesser-privileged actor), this is a plausible, narrow analog.

I was not able to fully confirm whether any additional non-keychain endpoints elsewhere (e.g. plotting, wallet RPC over HTTP) log raw request bodies without going through `redact_sensitive_data()`, since the tool budget is exhausted; the daemon's main WS ingress point is the only one I could verify in depth.

### Title
Unredacted credential logging on unknown daemon command - (File: chia/daemon/server.py)

### Summary
The Chia daemon's WebSocket message handler redacts sensitive fields (`password`, `key`, `secret`, `mnemonic`, etc.) before logging incoming messages, but only on the initial "Received message" debug log. When a message specifies an unrecognized `command`, the fallback branch logs the raw, unredacted message dictionary at ERROR level, bypassing the redaction entirely.

### Finding Description
In `WebSocketServer.incoming_connection()`, the daemon builds `redacted_data` via `redact_sensitive_data(decoded)` and logs it at line 296-298 [1](#0-0) . This redacted copy, however, is discarded after the debug log — `handle_message()` is called with the original, unredacted `decoded` message.

Inside `handle_message()`, if the command is not in `commands_with_data`, not a keychain command, not `ping`, and not present in `get_command_mapping()`, it falls into the final `else` branch:
```
self.log.error(f"UK>> {message}")
``` [3](#0-2) 

`message` here is the full original dict, including `data`, with no redaction applied. Any field placed under `data` (e.g., `password`, `private_key`, `mnemonic`, `passphrase`, `api_key`) will be written verbatim into the application log at ERROR level.

### Impact Explanation
Any local process capable of establishing a daemon WebSocket connection (which only requires possessing daemon-issued client TLS certs, the same trust level as other daemon RPC callers) can force secret material into the persistent log file by sending a single message with a nonsense `command` field and a `data` payload containing credentials/secrets. This is a direct information-exposure vulnerability analogous to CVE-2024-0006: any process, backup, log-shipping pipeline, or lower-privileged local reader of the log file gains access to keychain passphrases, mnemonics, or private-key material that legitimately-redacted logging paths were designed to prevent.

### Likelihood Explanation
High, given no special conditions are required beyond normal local daemon connectivity. The trigger is trivial — one out-of-band or misspelled command name — and does not require exploiting the underlying command logic; it purely abuses the daemon's own error-logging code path. Any client that already sends keychain-related commands (which routinely carry secrets) could hit this path accidentally through a typo, or an attacker could deliberately craft it.

### Recommendation
Route the `message` (or at minimum `message["data"]`) through `redact_sensitive_data()` before including it in the `"UK>> {message}"` log line, mirroring the redaction already applied to the "Received message" debug log. Ideally, extract a small helper that redacts once and reuses the redacted copy for every subsequent log statement in `incoming_connection()`/`handle_message()`, so no future logging call site can regress by using the raw `message`/`decoded` object.

### Proof of Concept
1. Establish a WebSocket connection to the local daemon (as any local RPC client capable of connecting, e.g. as done in `test_daemon.py` fixtures) [4](#0-3) .
2. Send a payload with an unrecognized command and sensitive data, e.g.:
```json
{
  "command": "totally_bogus_command",
  "data": {"password": "super_secret_pw", "mnemonic": "word1 word2 ... word24"},
  "ack": false,
  "request_id": "x",
  "destination": "daemon",
  "origin": "attacker"
}
```
3. Observe the daemon log file: the "Received message" line will show `data` redacted, but a subsequent `UK>> {...}` ERROR line (from `chia/daemon/server.py` line 445) will contain the plaintext `password` and `mnemonic` values, confirming the leak.
