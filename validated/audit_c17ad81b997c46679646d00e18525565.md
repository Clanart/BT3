Found the analog: `installAuthenticatedImageFilter` in `app/src/main-process/authenticated-image-filter.ts` attaches an `Authorization` token header based solely on request `origin` and a regex match on `pathname`, without validating that the path actually corresponds to a repository/asset the signed-in account is entitled to access — mirroring the original bug where a privileged value (`_safe.lead` / here, the `Authorization` header) is assigned based on an incomplete condition set (role-type match / here, origin+path-shape match) instead of validating the actual authorization/enablement state.

### Title
Authorization header attached to any URL on a GitHub-host origin matching a loose asset-path regex, without validating the target repo is the authenticated account's - ([File: app/src/main-process/authenticated-image-filter.ts])

### Summary
`installAuthenticatedImageFilter` decides whether to attach a signed-in account's OAuth `token` as an `Authorization` header purely by checking (a) that the request `origin` matches an origin for which Desktop holds a token, and (b) that the `pathname` matches a broad regex meant to identify "avatar" or "repo asset" URLs. It never checks that the `owner/repo` segment in the path belongs to a repository the account under that token is authorized for. ` [1](#0-0) `

### Finding Description
The filter builds an `originTokens` map of `origin -> token` for all signed-in accounts and, for the GitHub.com case, additionally maps the `github.com` HTML origin to the same token used for `api.github.com`: ` [2](#0-1) `

Then, on every outgoing request, it attaches `Authorization: token <token>` whenever the origin is in the map and the path matches either `isEnterpriseAvatarPath` or `isGitHubRepoAssetPath`:

```
function isGitHubRepoAssetPath(pathname: string) {
  // Matches paths like: /repo/owner/assets/userID/guid
  return (
    /^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/.test(pathname) ||
    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}
```
` [3](#0-2) `

The two path segments captured by `[^/]+\/[^/]+` are matched against *any* value — they are not validated to be the `owner/name` of a repository the account is a collaborator on, nor are they checked against the repository currently open in Desktop. Because the check is keyed only on origin (host-level), the same token is attached for `https://github.com/<any-owner>/<any-repo>/assets/<id>/<guid>` for *every* owner/repo on that host, as long as the account has a token for `github.com`/the GHE origin. This is the same class of defect as the report: a privileged artifact (`_safe.lead` in the report; the bearer `Authorization` token here) is granted based on a coarse condition (`role` type match; `origin` + loose regex match) instead of validating the specific entitlement (`enabled` flag; actual ownership/collaborator access to that specific `owner/repo` asset).

The renderer process routinely loads such asset URLs when rendering markdown (PR/issue/commit bodies, README) that can originate from *any* repository content — including a repository the attacker controls and that the victim merely views/clones/fetches. An attacker who can get the victim to render markdown containing an `assets`/`user-attachments` URL under an arbitrary `owner/repo` path on the same host that the victim is authenticated to controls the exact request the token will be attached to.

### Impact Explanation
If an attacker can influence which URL gets requested with this pattern (e.g., through markdown content in a PR/README/commit message that the victim opens, or through a crafted link), Desktop's main process will silently attach the victim's live OAuth token in the `Authorization` header to a GET request whose path/host the attacker chose (within the constraint that the host equals the authenticated origin and the path fits the loose regex). Depending on where the request lands (e.g., an enterprise instance where the attacker/administrator of the receiving path can log request headers, or a self-hosted/proxying setup), this can result in token exfiltration to a party who was never supposed to see it, since the filter does not verify the asset actually belongs to a repo the requester should be allowed to access with that credential.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to view/render content (markdown asset URL) that the attacker planted in a repository/PR/comment reachable by the victim on the same GitHub/GHE host they're signed in to, and for that content to be rendered as an image/asset request by Desktop's renderer. No local access, malware, or leaked credentials are required — only content served from a cloned/fetched repository or PR the user opens in Desktop, which matches the "unprivileged, attacker-controlled repository/GitHub API content" threat model in scope.

### Recommendation
Do not authorize solely on origin + generic path shape. Validate that the `owner/name` captured from `isGitHubRepoAssetPath` corresponds to a repository the currently authenticated account is actually associated with (e.g., cross-check against `GitHubRepository`/`IAPIRepository` data already known to Desktop, or restrict the filter to the specific repository context that triggered the render) before attaching the `Authorization` header, mirroring how `setRole` should have gated the `_safe.lead` assignment on the `enabled` flag rather than on role-type alone.

### Proof of Concept
1. Sign in to Desktop with a GitHub.com/GHE account (token cached in `originTokens` for that origin).
2. As an attacker, create/control a public repository or PR comment containing markdown that references an asset URL of the form `https://github.com/<attacker-owner>/<attacker-repo>/assets/<id>/<guid>` (or `/user-attachments/assets/<guid>`) pointing at attacker-controlled infrastructure that reflects/logs headers (via an open redirect or a GHE-like path a malicious/compromised instance controls), or observe that the filter attaches the header for any such path regardless of whether it belongs to a repo the victim is authorized to access.
3. When the victim's Desktop renders that content (opening the PR/notification/README preview), `authenticated-image-filter.ts` attaches `Authorization: token <victim token>` to the request because origin matches and the path satisfies `isGitHubRepoAssetPath`, without verifying the `owner/repo` in the path is one the victim is entitled to see with that token. ` [4](#0-3) `

```typescript
export function installAuthenticatedImageFilter(
  orderedWebRequest: OrderedWebRequest
) {
  let originTokens = new Map<string, string>()

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const { origin, pathname } = new URL(details.url)
    const token = originTokens.get(origin)

    if (
      token &&
      (isEnterpriseAvatarPath(pathname) || isGitHubRepoAssetPath(pathname))
    ) {
      return {
        requestHeaders: {
          ...details.requestHeaders,
          Authorization: `token ${token}`,
        },
      }
    }

    return {}
  })
```
