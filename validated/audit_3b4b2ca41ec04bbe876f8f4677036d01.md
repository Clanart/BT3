### Title
Unchecked u64 addition overflow in `payment_sat + needed_fee` bypasses the `NotEnoughFunds` check, causing the threshold multisig to sign a consensus-invalid transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` validates sufficiency of inputs via `input_sat < (payment_sat + needed_fee)`, but both the summation of payment amounts (`payment_sat`) and the addition to `needed_fee` are performed with unchecked `u64` arithmetic. In release builds these wrap silently, so an attacker-influenced payment list whose amounts sum past `u64::MAX` passes the solvency check while the emitted `TxOut`s individually carry enormous values. The resulting transaction exceeds `MAX_MONEY`/inputs and is consensus-invalid, yet is still fed to the FROST signing machine. Additionally, `fee()` performs an unchecked subtraction `sum(prevouts) - sum(outputs)` which underflows in exactly this scenario.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:187`, `payment_sat` is computed as `payments.iter().map(|payment| payment.1).sum::<u64>()` with no overflow handling. Each payment is only validated to be `>= DUST` (`send.rs:165-169`), so a single payment of e.g. `u64::MAX` sat, or a few payments whose sum exceeds `u64::MAX`, is accepted.

The solvency check at `send.rs:215` is:

```rust
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { ... })?;
}
```

`payment_sat + needed_fee` (and `payment_sat` itself, when there are multiple payments) wraps modulo 2^64 in release builds (and panics in debug builds). If it wraps below `input_sat`, the check is bypassed even though the true output total vastly exceeds the inputs — the direct analog of the report's missing-balance/overflow issue. The change-output path at `send.rs:228` uses `checked_sub`, but on the already-wrapped `payment_sat + fee_with_change`, so it too computes a wrong change value.

The constructor then returns a `SignableTransaction` whose outputs sum to more than its inputs and whose individual output values exceed Bitcoin's `MAX_MONEY` (21M BTC), making the transaction consensus-invalid and unbroadcastable. `TransactionSignMachine::sign` (`send.rs:355-398`) still computes sighashes and produces FROST signature shares for it, and `TransactionSignatureMachine::complete` returns the invalid signed `Transaction`. Separately, `SignableTransaction::fee` (`send.rs:138-141`) computes `sum(inputs) - sum(outputs)` with a plain subtraction that underflows/panics in this state.

### Impact Explanation
A caller able to influence the `payments` list (e.g. a withdrawal request amount) can cause the threshold wallet to (a) panic on the wrapped arithmetic in debug/sanitized builds or `fee()`'s underflow, and (b) in release builds, drive the entire FROST signing ceremony — preprocesses, shares, aggregation — to produce a signed transaction that no node will ever accept. This wastes a signing session, produces funds-reported-as-sent that are actually unspendable/undeliverable, and any accounting built on `fee()`/`needed_fee` records nonsensical values. It is a signing of an unintended (invalid) message under the threshold key's authority.

### Likelihood Explanation
The overflow requires payment amounts near `u64::MAX` or a crafted set summing past it, which is outside realistic Bitcoin amounts (real outputs are capped at 21M BTC), but the `payments` slice is attacker-influenced input with no upper-bound validation other than `>= DUST`. Medium likelihood: it needs a large-value payment request to reach `SignableTransaction::new`, but no validator collusion or special access is required — just a crafted amount.

### Recommendation
Use checked arithmetic throughout `SignableTransaction::new`: compute `payment_sat` with `try_fold`/`checked_add`, compute `payment_sat + needed_fee` and `payment_sat + fee_with_change` with `checked_add` (returning `NotEnoughFunds` on overflow), and additionally reject individual payments exceeding `MAX_MONEY`. Make `fee()` use `checked_sub` and return an error instead of underflowing.

### Proof of Concept
```rust
// Release build (wrapping arithmetic).
// inputs: a single ReceivedOutput worth 1_000_000 sat.
let inputs = vec![received_output_worth_1m];

// One payment of u64::MAX sat passes `*amount < DUST` check.
let payments = vec![(attacker_script, u64::MAX)];

// needed_fee is small (e.g. ~200).
// payment_sat + needed_fee wraps: u64::MAX + 200 -> 199
// 1_000_000 < 199 is false -> NotEnoughFunds is NOT raised.
let tx = SignableTransaction::new(inputs, &payments, None, None, 1).unwrap();

// tx.output[0].value == u64::MAX sat > MAX_MONEY: consensus-invalid.
// tx.fee() computes 1_000_000 - u64::MAX -> underflow panic / wrapped garbage.
// multisig(..).preprocess(..) / sign(..) still produces a FROST signature over it.
```

Root cause locations: `payment_sat` sum at `send.rs:187`, unchecked `payment_sat + needed_fee` at `send.rs:215`, unchecked subtraction in `fee()` at `send.rs:139-140`.
