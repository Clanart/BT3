### Title
Unauthenticated OP_RETURN payer attribution lets anyone front a withdrawal and get an arbitrary operator reimbursed for a payout it never funded - (File: core/src/verifier.rs, core/src/operator.rs)

### Summary
The payout transaction's attribution of "which operator funded this withdrawal" is derived solely from an unsigned OP_RETURN push (`parse_op_return_data` / `XOnlyPublicKey::from_slice`) in `Verifier::update_finalized_payouts`, which is not covered by the withdrawer's `SinglePlusAnyoneCanPay` signature and not bound to the transaction's actual funding inputs. Anyone who owns a withdrawal UTXO (i.e., any depositor who calls Citrea `withdraw`) can self-fund their own payout while writing an arbitrary registered operator's x-only pubkey into the OP_RETURN, causing that operator's own automated `PayoutCheckerTask` to claim a full reimbursement it never paid for.

### Finding Description
The broken binding is: `operator_xonly_pk` parsed from the confirmed payout tx's OP_RETURN (`core/src/verifier.rs` L2319-2321) should equal the operator that actually supplied the BTC paid to the withdrawer, but nothing enforces this equality.

`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs` L407-436) builds the payout tx with a single signed input (the withdrawal UTXO, keyspend) and an unsigned, freely-chosen OP_RETURN output containing an x-only pubkey [1](#0-0) . The withdrawer's signature is required to be `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs` L174-187, `core/src/operator.rs` L630-637), which under BIP-341 only commits to input index 0 and output index 0 — it does not cover the OP_RETURN output nor any additional funding inputs, and `AnyoneCanPay` explicitly allows arbitrary extra inputs to be added by anyone holding that signature [2](#0-1) .

`Verifier::update_finalized_payouts` then trusts this OP_RETURN blindly to attribute the payout to an operator, storing it in `withdrawals.payout_payer_operator_xonly_pk` with no check against the tx's actual funding inputs: [3](#0-2) . `is_kickoff_malicious` (used by verifiers to sanity-check a kickoff) only re-checks that this same DB-stored `operator_xonly_pk` equals `kickoff_data.operator_xonly_pk` and that the committed blockhash matches — again no funding-source check: [4](#0-3) . On the operator side, `validate_payer_is_operator` (`core/src/operator.rs` L1686-1740) only compares the DB-stored `payer_xonly_pk` to `self.signer.xonly_public_key`, again with no cross-check that the operator itself constructed/broadcast that payout tx.

Exploit flow: an attacker deposits into the bridge and calls Citrea's `withdraw`, choosing their own withdrawal UTXO and destination output, and signs it `SinglePlusAnyoneCanPay`. Instead of using the normal operator/aggregator `withdraw()` flow (where the operator funds the extra inputs via `fund_raw_transaction`, `core/src/operator.rs` L620-655), the attacker constructs their own transaction reusing the same signature, adds their *own* funding inputs to cover the committed output, and appends an OP_RETURN naming any real, registered operator's x-only pubkey (public information). They broadcast and get it mined. `update_finalized_payouts` records that operator as the payer. That operator's fully automated `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs` L39-111) then detects the "unhandled payout" attributed to itself via `get_first_unhandled_payout_by_operator_xonly_pk` and proceeds through `handle_finalized_payout` → `get_reimbursement_txs`/`get_next_txs_to_send` to claim the Reimburse tx — all driven purely by DB attribution, with no verification that the named operator's wallet/kickoff actually funded the payout.

### Impact Explanation
This lets an attacker who is merely a depositor/withdrawer cause bridge collateral (the round/reimbursement UTXO value, up to `bridge_amount`) to be paid out to a named operator that never funded that specific withdrawal — a duplicate payout from the protocol's perspective (the withdrawer already got their money from the attacker's self-funded inputs, and the operator now also gets reimbursed from vault/collateral for the same withdrawal). This matches "an operator reimbursed for a payout it never funded" (Critical). It is repeatable per withdrawal and requires no special operator or verifier privileges, only the ability to observe a target operator's public x-only pubkey and to broadcast a Bitcoin transaction with attacker-chosen inputs/outputs/OP_RETURN.

### Likelihood Explanation
Preconditions are all within the declared unprivileged attacker capability set: deposit into the bridge, call Citrea `withdraw`, choose a withdrawal UTXO, a Schnorr signature with `SinglePlusAnyoneCanPay`, and an OP_RETURN. The attacker needs BTC to self-fund the output amount (their own withdrawal amount, which they get back), plus fees — no operator collusion required, since the assignment/attribution is entirely OP_RETURN-driven and any registered operator's automation reacts to it automatically. This is directly reachable via normal Bitcoin transaction construction and confirmation, no mainnet needed to demonstrate in a regtest/test harness.

### Recommendation
Bind the OP_RETURN operator attribution to actual proof of funding, e.g., require the payout tx's additional (non-withdrawal) inputs to be spendable only via that operator's known key/address, or require an operator signature (e.g., over the payout tx or a commitment covering the OP_RETURN and all inputs) that verifiers/operators check before trusting `payout_payer_operator_xonly_pk`. At minimum, cover the OP_RETURN output and all input provenance under the sighash the operator explicitly co-signs, so attribution cannot be forged by a third-party funder.

### Proof of Concept
`cargo test` plan:
1. Set up two operators A (target/victim) and B in the standard e2e test harness; perform a deposit and register a withdrawal via Citrea `insert_withdrawal_utxo` as in existing e2e tests (`core/src/test/deposit_and_withdraw_e2e.rs`).
2. Using `generate_withdrawal_transaction_and_signature` (`core/src/test/common/setup_utils.rs` L430-449) as the attacker/withdrawer, sign the dust UTXO with `SinglePlusAnyoneCanPay`.
3. Instead of calling operator A/B's `withdraw` RPC, manually build a payout `Transaction` (mirroring `create_payout_txhandler`) that: (a) spends the withdrawer's dust UTXO with the collected signature, (b) adds a *test-wallet-funded* extra input unrelated to any operator, (c) pays the committed output, (d) sets OP_RETURN to operator A's `xonly_pk` (a value known only from public config, not derived from any operator action).
4. Broadcast and mine this transaction; run block sync so `Verifier::update_finalized_payouts` processes it, and assert `withdrawals.payout_payer_operator_xonly_pk == operator_A_xonly_pk` in the DB.
5. Assert operator A's `PayoutCheckerTask::run_once` (or directly `Operator::get_reimbursement_txs`/`handle_finalized_payout`) succeeds and returns kickoff/reimbursement transactions for this deposit, despite operator A having never called `withdraw`, never funded the payout tx, and never invoked `fund_raw_transaction`.
6. Assert this is a genuine binding failure by comparing: `payout_tx.input` funding source (test wallet, not operator A) vs. `operator_xonly_pk` stored/trusted for reimbursement (operator A) — they diverge, and the divergence is never rejected by `is_kickoff_malicious` or `validate_payer_is_operator`.
