## Title
Non-atomic ERC20 unescrow in ICS20 `OnRecvPacket`/`OnAcknowledgementPacket`/`OnTimeoutPacket` callbacks can permanently strand IBC-received coins in the erc20 module account while the source chain refunds the sender - (File: `x/erc20/keeper/ibc_callbacks.go`)

### Summary
This is the Cosmos EVM analog of the Sublime `SavingsAccount.withdrawAll`/`switchStrategy` bug: an operation that moves value between two accounting systems (there: strategy shares vs. underlying pool; here: bank coins vs. native ERC20 balances) commits the "debit" side unconditionally while the "credit" side can fail, and the surrounding code treats the whole thing as atomic without actually branching/rolling back state. In `x/erc20/keeper/ibc_callbacks.go`, `ConvertCoinNativeERC20` first escrows the recipient's bank coin into the `erc20` module account and only afterward attempts the EVM `transfer` call that unescrows the underlying native ERC20 tokens to the recipient. If the EVM call fails or the post-transfer balance-invariance check fails, the function returns an error, but the earlier `SendCoinsFromAccountToModule` escrow step is never undone because none of the three call sites (`OnRecvPacket`, `OnAcknowledgementPacket` via `ConvertCoinToERC20FromPacket`, `OnTimeoutPacket`) wrap the call in a cached/branched context the way other IBC callback code in this same repo does (compare `x/ibc/callbacks/keeper/keeper.go`'s explicit `ctx.CacheContext()` / `writeFn()` pattern).

### Finding Description
`x/erc20/keeper/ibc_callbacks.go` `OnRecvPacket` runs the core ICS20 receive first (`im.Module.OnRecvPacket`, which mints/unescrows bank coins to the recipient and returns a success ack), then calls the erc20 middleware's `OnRecvPacket` on the *same, uncached* `ctx`: [1](#0-0) 

For a registered native-ERC20 token pair, this calls `k.ConvertCoinNativeERC20`: [2](#0-1) 

`ConvertCoinNativeERC20` escrows the coin into the module account first, and only then calls the EVM `transfer` to unescrow the underlying ERC20 tokens to the receiver; any failure in the EVM call, the return-value check, or the post-transfer balance invariance check causes the function to return an error *after* the escrow step has already mutated state: [3](#0-2) 

Because no `ctx.CacheContext()`/`writeFn()` pattern is used around this call (unlike the analogous pattern that IS used elsewhere in the codebase for IBC EVM callbacks): [4](#0-3) 

the escrow of the recipient's coin into the `erc20` module account is never rolled back. `OnRecvPacket` then returns an `ErrorAcknowledgement`: [5](#0-4) 

Writing an error acknowledgement for a `RecvPacket` causes the **source** chain to treat the transfer as failed and refund the original sender (unescrow on the source chain), while on the **destination** chain the coins that were minted by the successful core-IBC receive are now sitting, unrecoverable through any exposed keeper method, inside the `erc20` module account (escrowed but never unescrowed to ERC20 and never burned).

The same non-atomic pattern exists in the refund path used for error-acks/timeouts: [6](#0-5)  and [7](#0-6) 

Here, when `ConvertCoinNativeERC20` fails partway (after escrow), the error is deliberately swallowed (`return nil`) with only a best-effort event, under the stated assumption that "the user receives the corresponding bank token from the TokenPair instead" — but if the escrow step already ran, the user does **not** retain the bank token; it is stuck in the module account.

### Impact Explanation
This corrupts the 1:1 accounting invariant between native bank coins and their ERC20 representation for a token-pair-backed asset (an explicitly in-scope "Critical … duplication … or irreversible accounting corruption of spendable user value across native balances … token-pair-backed balances" and "permanent freezing … of user funds … token-pair-backed balances"):
- On `OnRecvPacket` failure mid-conversion: the destination-chain recipient's minted coin becomes permanently trapped in the `erc20` module account (no burn, no ERC20 credit), while the source chain independently refunds the original sender the full escrowed amount — net result is duplicated value (sender keeps original funds on-chain A, and phantom voucher supply is permanently locked on chain B) and a stranded, irrecoverable balance for the destination recipient.
- On `OnAcknowledgementPacket`/`OnTimeoutPacket` refund paths: the refunded coin escrowed by `ConvertCoinNativeERC20` mid-flow is likewise stuck in the module account instead of being returned to the user as intended by the code comments, resulting in a straightforward loss/freezing of user funds.

### Likelihood Explanation
The EVM `transfer` call inside `ConvertCoinNativeERC20` can fail for reasons entirely outside the recipient's control and reachable by an unprivileged actor who controls (or governance registers) the underlying ERC20 contract of a "native ERC20" token pair: pausable tokens, blacklist/deny-list tokens, tokens that revert for the module address under certain conditions, or a token that returns a boolean `false` instead of reverting (already explicitly handled as an error path: `unpackedRet.Value == false`). Given `RegisterERC20` supports `PermissionlessRegistration`, an attacker-deployed token pair with a conditionally reverting `transfer` gives an unprivileged user precise control over when the escrow succeeds but the unescrow fails, deterministically triggering fund freezing/duplication on ordinary IBC receive/refund flows.

### Recommendation
Wrap the coin-escrow + EVM-unescrow sequence in `ConvertCoinNativeERC20` (and its callers in `ibc_callbacks.go`) in a `ctx.CacheContext()` and only call the returned `writeFn()` if every step (escrow, EVM transfer, balance-invariance check, burn) succeeds — mirroring the existing pattern already used in `x/ibc/callbacks/keeper/keeper.go`. This ensures that any failure after the escrow step leaves the recipient's original bank balance untouched, so the fallback behavior described in the code comments ("user receives the corresponding bank token instead") is actually guaranteed rather than assumed.

### Proof of Concept
1. Governance (or a permissionless registration, if enabled) registers a native ERC20 token pair whose contract's `transfer` function can be made to revert or return `false` under an attacker-chosen condition (e.g., a pausable/blacklistable token, or one that reverts when called by the module address for particular amounts).
2. An IBC transfer of that token's bank-coin representation is received on this chain (`OnRecvPacket`), or is sent from this chain and times out/errors (`OnTimeoutPacket`/`OnAcknowledgementPacket`).
3. Before `ConvertCoinNativeERC20`'s `CallEVM("transfer", ...)` step executes, the attacker triggers the malicious/paused condition on the token contract so the transfer reverts or returns `false`.
4. `ConvertCoinNativeERC20` returns an error after `SendCoinsFromAccountToModule` has already moved the coin into the `erc20` module account.
5. For the `OnRecvPacket` path: an `ErrorAcknowledgement` is written, causing the sending chain to refund the original sender; meanwhile the coin is left balance-locked inside the `erc20` module account on the receiving chain with no path to recovery via any exposed keeper/msg-server method.
6. For the ack/timeout refund path: the error is swallowed and the coin remains stuck in the module account instead of being returned to the user as the code intends.

// OnAcknowledgementPacket responds to the success or failure of a packet
// acknowledgement written on the receiving chain. If the acknowledgement was a
// success then nothing occurs. If the acknowledgement failed, then the sender
// is refunded and then the IBC Coins are converted to ERC20.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnAcknowledgementPacket
// still succeeds, but the user receives the corresponding bank token from the
// TokenPair instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)

// ConvertCoinToERC20FromPacket converts the IBC coin to ERC20 after refunding the sender
// This function is only executed when IBC timeout or an Error ACK happens.
func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}

		// Convert from Coin to ERC20
		if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
			// We want to record only the failed attempt to reconvert the coins during IBC.
			defer func() {
				telemetry.IncrCounter(1, types.ModuleName, "ibc", "error", "total")
			}()
			ctx.EventManager().EmitEvents(
				sdk.Events{
					sdk.NewEvent(
						types.EventTypeFailedConvertERC20,
						sdk.NewAttribute(types.AttributeCoinSourceChannel, pair.Denom),
						sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
						sdk.NewAttribute("error", err.Error()),
					),
				},
			)
			return nil
		}
	}

	return nil
}
