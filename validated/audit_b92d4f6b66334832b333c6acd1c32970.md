### Title
OP_RETURN data output excluded from fee weight calculation, undercharging the fee and overpaying change - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` supports an optional `data` payload that is appended as an `OP_RETURN` output, but `calculate_weight_vbytes` — the sole function used to size the transaction and price the fee — reconstructs a model transaction containing only the payment outputs (plus optional change). The `OP_RETURN` output is never included, so the computed vbytes/weight is too small whenever `data` is specified. The result mirrors the audited bug class: in a less-frequently-exercised path (a transaction carrying data, analog of a locked/cancel-pending quote), the accounting that determines how much value is retained versus consumed is wrong — the transaction underpays its intended fee rate and silently returns too much "change" / can fall below the minimum relay fee, leaving funds unmovable.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` pushes an `OP_RETURN` output onto `tx_outs` when `data` is present (lines 194–202). Both fee computations then call `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204) and `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (lines 225–227). Inside `calculate_weight_vbytes` (lines 62–127) the model `Transaction` is built with `output` derived exclusively from `payments` (and the change `TxOut`); there is no parameter or handling for the data output. Consequently:

- `vbytes` (and `vbytes_with_change`) underestimate the real transaction size by roughly `11 + data.len()` serialized bytes (up to ~91 bytes given the 80-byte cap plus output overhead).
- `needed_fee = fee_per_vbyte * vbytes` is too small, so the real transaction's effective fee rate is below `fee_per_vbyte`.
- The minimum-relay guard at lines 211–213 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the *underestimated* vbytes, so a transaction that actually sits below the relay minimum after the OP_RETURN is added can pass the check.
- The change computation `input_sat - (payment_sat + fee_with_change)` (line 228) credits the caller with change as if the smaller fee were paid, while the actual weight is larger — so the real fee rate is even lower than `needed_fee` implies.

Because `Prevouts::All` sighash (line 375) and the witness construction are independent of this, the transaction still signs; the defect is purely economic/accounting — exactly the same class as the reported issue, where an edge-state path (here, `data.is_some()`) skips the value that should have been accounted for (here, output weight; in the report, the fee refund).

### Impact Explanation
Any caller that passes `data` produces a transaction paying strictly less than `fee_per_vbyte` sat/vbyte. With `data` near the 80-byte maximum, the fee shortfall is ~80–90 vbytes × `fee_per_vbyte` sats. Two concrete harms:

1. The transaction can fall below the mempool minimum relay fee despite the `TooLowFee` check passing, causing it to be rejected/non-propagating — the inputs it spends become effectively unspendable until reconstructed (funds reported spendable that are not usable on-chain, analogous to "funds reported received that are not spendable").
2. `needed_fee()` misreports the required fee and the change amount is computed against a fictitious weight, breaking the fee/change accounting invariant (`sum(inputs) - sum(outputs) == needed_fee * actual_vsize/vsize` no longer holds at the intended rate).

### Likelihood Explanation
The bug triggers deterministically whenever `data.is_some()` and the transaction would otherwise be near a fee boundary — no attacker secret, no timing, no collusion is needed. A caller only has to invoke the public `SignableTransaction::new(..., data: Some(...), fee_per_vbyte)` path; the miscalculation is unconditional on that path. In low-fee regimes (1 sat/vbyte) the proportional shortfall can exceed 30% of the intended fee for small transactions, making the below-minimum-relay outcome realistic.

### Recommendation
Include the data output in the weight model: either pass the serialized `OP_RETURN` `TxOut` into `calculate_weight_vbytes` (e.g., extend its signature to accept an extra `Option<&TxOut>` appended to `tx.output` before `tx.weight()` is measured), or compute the fee on the fully-constructed `tx_outs` (including the OP_RETURN) rather than on a payment-only model. Recompute both the no-change and with-change variants with the data output present.

### Proof of Concept
1. Build `SignableTransaction::new(vec![input], &[(payment_script, DUST)], Some(change_script), Some(vec![0xAA; 80]), fee_per_vbyte)`.
2. Compare `tx.transaction().vsize()` (via `tx.transaction().weight()`) against `tx.needed_fee() / fee_per_vbyte`: the latter is smaller by the serialized size of the OP_RETURN output (~91 weight units ≈ ~23 vbytes, plus base overhead), since `calculate_weight_vbytes` (send.rs lines 62–127) never receives the data output pushed at send.rs lines 194–202.
3. Set `fee_per_vbyte` so `needed_fee` just exceeds `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`; the resulting signed transaction's actual fee rate is below the relay minimum and will not propagate, despite `TransactionError::TooLowFee` not being returned.
