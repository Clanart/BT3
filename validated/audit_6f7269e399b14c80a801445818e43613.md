### Title
Unsynchronized lazy extension promotion in `upb_Message_GetOrPromoteExtension` allows concurrent-reader data corruption of shared parsed messages - (`File: upb/message/promote.c`)

### Summary
The hpb C++ wrapper's own internal documentation (`hpb/internal/message_lock.h`) acknowledges an unresolved concurrency defect: `upb_Message_GetOrPromoteExtension()` — invoked from what application code treats as a read-only extension getter on an already-parsed message — mutates shared, arena-backed message state (creating an extension slot and deleting/compacting unknown-field storage) with no internal locking. A lock is only applied if the embedding language explicitly registers a global locker callback via `hpb_extension_locker_global`; the plain upb C API and any caller that does not opt into that callback get no protection at all.

### Finding Description
`upb_Message_GetOrPromoteExtension()` in [1](#0-0)  is called by generated "getter" style accessors for extension fields on an already-parsed message (see `UpbExtensionTrait<T>::Get` in [2](#0-1) ). Despite looking like a read accessor, the function:

1. Scans the message's unknown-field list, parsing/decoding matching unknown bytes into a new sub-message on the arena, via `upb_MiniTable_ParseUnknownMessage` [3](#0-2) .
2. Creates a new extension slot with `_upb_Message_GetOrCreateExtension` and then **deletes/compacts the unknown-field storage** with `upb_Message_DeleteUnknown2` in a loop [4](#0-3) .

Both operations mutate the message's internal unknown-field array/extension array in place. This is exactly the pattern the hpb maintainers flagged as unsafe: `hpb/internal/message_lock.h` states this is a "TODO: Temporary locking api for cross-language concurrency issue around extension api that uses lazy promotion from unknown data to `upb_MiniTableExtension`. Will be replaced by a core runtime solution in the future" [5](#0-4) . The mitigation is `hpb::internal::MessageLock`, which only takes effect if a locker function pointer has been registered in the global atomic `upb_extension_locker_global` [6](#0-5) ; by default this is null, so `MessageLock` is a no-op, and `GetOrPromoteExtension` performs the same unsynchronized mutation as calling `upb_Message_GetOrPromoteExtension` directly from the plain C API.

The ksmbd bug's failed invariant is: shared object state (`conn->preauth_info`) is freed/mutated under a lock in one code path, but read/dereferenced in a concurrent path without taking that same lock, so the reader can observe a half-mutated or freed object. The upb analog transfers directly: shared object state (a message's unknown-field array and extension array) is mutated (compacted/reallocated) by one thread calling an "extension getter," while a second thread concurrently reading the same message's unknown fields (`upb_Message_NextUnknown2`/`upb_Message_FindUnknown2`, or serializing it, or promoting a *different* extension number) can observe an iterator, pointer, or field-count reflecting a stale/torn view of storage that is being reshaped concurrently, or race on the extension array being reallocated (`_upb_Message_GetOrCreateExtension`) while another thread is iterating it via `upb_Message_NextExtension`.

### Impact Explanation
Because `upb`'s arena model never returns memory to the OS mid-lifetime, the ksmbd-style "kfree, then dereference stale pointer" scenario doesn't map 1:1 to a classic heap UAF — the arena block backing the old unknown/extension storage stays allocated until the whole arena is freed. However, the concurrent unsynchronized array/iterator mutation still creates a real memory-safety and data-integrity hazard: a reader's cached `iter`/pointer into the unknown-field or extension list can become inconsistent mid-iteration (indices shifted or reused by realloc within the same arena), leading to reading garbage/reused-slot data (information disclosure of unrelated field bytes), corrupted field values being returned to the application, or an out-of-bounds/incorrect array index dereference within the arena block if a realloc changed backing storage layout underneath a reader that cached the old base pointer. Because the bug is a data race (not a checked error), impacts range up to memory corruption; a full RCE proof is not established here, so severity is assessed as High rather than Critical.

### Likelihood Explanation
This is reachable purely through the ordinary "parse then read extension field" pattern that consuming applications commonly use — no privileged access, malicious peer, or hostile schema is required, and it triggers on a bounded, otherwise-valid message that contains unknown/extension data requiring lazy promotion. The realistic trigger requires the consuming application to share one parsed `upb_Message`/hpb message object across two or more threads and call extension getters/other message accessors concurrently on it — a pattern the code explicitly anticipates and tries (incompletely) to guard against via the opt-in `MessageLock`. This is consistent with protobuf's documented thread-safety contract (`src/google/protobuf/package_info.h`) that non-const-like mutation must not race with concurrent access, but `GetOrPromoteExtension` presents itself as effectively const/read-only to callers while secretly mutating, making the hazard easy for application authors to hit unknowingly.

### Recommendation
Add locking (or lock-free CAS-based promotion, as already done for `PYUPB_LAZYPTR`/`LazyUniquePtr` in the Python free-threading support code, see `python/free_threading/lazy_ptr.h` and `python/google/protobuf/pyext/lazy_unique_ptr.h`) directly inside `upb_Message_GetOrPromoteExtension` and `upb_MiniTable_PromoteUnknownToMessage`/`...Array`/`...Map` in the core upb runtime, rather than relying on an opt-in, disabled-by-default callback (`upb_extension_locker_global`) that only the hpb C++ layer wires up. At minimum, document loudly (and ideally `UPB_ASSERT`/runtime-check) that these "getter" APIs are unsafe to call concurrently on the same message without external synchronization, and provide the built-in locking as the default rather than a TODO.

### Proof of Concept
A full reproduction was not run in this session (no execution environment available in ask-only mode); the following is a minimal outline based on the traced code paths that a Devin session with build tooling could execute to confirm the race (e.g. under ThreadSanitizer):

1. Build a schema with an extendable message `M` and extension `Ext` (as used in `upb/message/promote_test.cc`, e.g. `upb_test_ModelWithExtensions`/`upb_test_ModelExtension1`).
2. Serialize an `M` containing the extension only as unknown bytes (not linked at parse time), matching the setup in `TEST(GeneratedCode, Extensions)` in [7](#0-6) .
3. Parse once to get a single shared `upb_Message* base_msg` on one arena.
4. From two threads, without registering `upb_extension_locker_global`, concurrently call `upb_Message_GetOrPromoteExtension(base_msg, ext_table, 0, arena, &value)` for the same (or different) extension numbers, and on a third thread concurrently call `upb_Message_NextUnknown2`/`upb_Message_NextExtension` to iterate unknown/extension state.
5. Run under ThreadSanitizer (as the existing `upb/mem/arena_test.cc` `FuzzFuse*` tests already do for arena fuse/free races, see [8](#0-7)  for the harness pattern) to confirm the data race is flagged on the unknown-field/extension array mutation versus concurrent iteration.

Note on uncertainty: I was not able to find, within the indexed portion of this repository, an existing regression/fuzz test that specifically races `upb_Message_GetOrPromoteExtension` against concurrent readers (only `promote_test.cc` single-threaded functional tests and unrelated arena-fuse race tests were found), so the exact crash/corruption signature (vs. a benign but still-incorrect race) would need to be confirmed by actually running the PoC above.

/**
 * MessageLock(msg) acquires lock on msg when constructed and releases it when
 * destroyed.
 */
class MessageLock {
 public:
  explicit MessageLock(const upb_Message* msg) : msg_(msg) {
    UpbExtensionLocker locker =
        upb_extension_locker_global.load(std::memory_order_acquire);
    unlocker_ = (locker != nullptr) ? locker(msg) : nullptr;
  }
  MessageLock(const MessageLock&) = delete;
  void operator=(const MessageLock&) = delete;
  ~MessageLock() {
    if (unlocker_ != nullptr) {
      unlocker_(msg_);
    }
  }

 private:
  const upb_Message* msg_;
  UpbExtensionUnlocker unlocker_;
};

bool HasExtensionOrUnknown(const upb_Message* msg,
                           const upb_MiniTableExtension* eid) {
  MessageLock msg_lock(msg);
  if (upb_Message_HasExtension(msg, eid)) return true;

  const uint32_t number = upb_MiniTableExtension_Number(eid);
  return upb_Message_FindUnknown2(msg, number, 0).status == kUpb_FindUnknown_Ok;
}

bool GetOrPromoteExtension(const upb_Message* msg,
                           const upb_MiniTableExtension* eid, upb_Arena* arena,
                           upb_MessageValue* value) {
  // TODO: Fix const correctness issues.

  upb_GetExtension_Status ext_status =
      upb_Message_GetOrPromoteExtension(mutable_msg, eid, 0, arena, value);
  return ext_status == kUpb_GetExtension_Ok;
}
