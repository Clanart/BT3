### Title
Malicious order creator can force a token list on the fill beneficiary that permanently locks escrow on release — (File: evm/src/apps/intentsv2/IntentsBase.sol, evm/src/apps/intentsv2/IntrinsicIntents.sol, evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`_withdraw`/`withdraw` release escrowed tokens by iterating unconditionally over the full `body.tokens` array and transferring every entry to a single beneficiary in one atomic loop. That token list is `order.inputs` — chosen entirely by the order creator at `placeOrder` time, with no allowlist or validation on the token address. When a solver fills the order, `_withdraw` is invoked with the *solver* as beneficiary, forcing the solver to receive whatever token list the order creator picked. If even one entry is a token that reverts on transfer (blacklist token, pausable token, token with a hostile `transfer`/`balanceOf` override, etc.), the entire release — and thus the whole `fillOrder`/cross-chain redeem transaction — reverts every single time, permanently. This is the same broken invariant as `erc20TokensToIncludeInQuit`: a party that doesn't control the token list is compelled to accept an unmodifiable, attacker-chosen set of tokens, and a single bad entry blocks/permanently locks the fund release for everyone.

### Finding Description
`_withdraw` in `IntentsBase.sol` loops over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each entry, with no ability to skip or exclude any token: [3](#0-2) 

The token list itself is `order.inputs`, set unconditionally from user-supplied data in `placeOrder` — only `amount != 0` and no-duplicate checks are enforced, no token-address validation exists: [1](#0-0) [4](#0-3) 

At fill time, `_fillSameChain` calls `_withdraw` with the *solver* (`msg.sender`) as beneficiary of the escrowed input tokens — i.e., the order creator's token choice is imposed on a party (the solver) who never selected or agreed to that list: [5](#0-4) 

The same one-shot, all-or-nothing pattern repeats for the cross-chain settlement path in `IntentGatewayV2.sol` (tron variant), where `onAccept` handles `RedeemEscrow`/`RefundEscrow` by decoding a `WithdrawalRequest` and calling `withdraw`, which loops over `body.tokens` with no per-token skip/retry capability: [6](#0-5) [7](#0-6) 

Because this message is the *only* mechanism that releases the escrow (there is no per-token withdrawal, no ability for the beneficiary to specify "skip this token"), a single malicious/broken ERC20 among `order.inputs` makes every future delivery attempt of `RedeemEscrow`/`RefundEscrow` for that commitment revert. Unlike a normal same-chain revert (which is retryable with different parameters), here the WithdrawalRequest body is fixed by the order's escrowed token set — there is no path to reconstruct it excluding the bad token, so the escrow (including any well-behaved tokens bundled in the same order) is permanently unrecoverable.

### Impact Explanation
This directly maps to the accepted impact categories: loss/lock of funds and a logic attack enabling denial of legitimate settlement. A malicious order creator can:
1. Place an order whose `inputs` include a token that behaves normally on deposit (so `placeOrder` succeeds and escrow is credited) but reverts on `transfer`/`safeTransfer` to specific addresses (e.g., a blacklist/permission token, or a token the creator later pauses/blacklists the eventual solver on).
2. Lure a solver into filling the order (solver sends real, valuable output assets to the order's beneficiary as part of `_fillSameChain`/`fillOrder`).
3. Because `_withdraw`/`withdraw` is atomic and covers the full token list unconditionally, the malicious token's revert causes the whole fill transaction (and therefore the solver's genuine payout leg) to also revert. On the cross-chain path, this makes the escrow release message permanently non-deliverable, locking the solver's earned escrow (and any co-escrowed legitimate tokens) forever, exactly mirroring the DAO report's "prevented from taking out pro rata funds" and "forced to receive all tokens without choice" findings.

### Likelihood Explanation
Any unprivileged user can call `placeOrder` with attacker-controlled ERC20 addresses; no admin or relayer collusion is required. The trigger condition (a solver choosing to fill the order) is a normal, expected interaction pattern for the intents system, so exploitation only requires a solver to be tricked (or simply unaware) into filling a maliciously crafted order — the fee/output incentives of the order can be made attractive enough to draw solvers in. This satisfies the "unprivileged attacker, no malicious relayer/prover/admin needed" bar.

### Recommendation
Do not force an all-or-nothing token release. Options: (1) release each token in `body.tokens` independently, using try/catch around external transfer calls so a single bad token doesn't block release of the others, recording any failed transfer as a separately claimable balance for the beneficiary; (2) allow the beneficiary to specify/opt out of individual tokens they don't want (mirroring the `erc20TokensToIncludeInQuit` fix — accept a subset list from the caller); (3) validate/allowlist tokens eligible as `order.inputs` at `placeOrder` time so untrusted/malicious ERC20s cannot be escrowed in the first place.

### Proof of Concept
1. Deploy `EvilToken`, an ERC20 whose `transfer()` succeeds for the deployer/order creator address but reverts for any other `to` address (or is pausable/blacklistable by the creator after deposit).
2. Order creator calls `placeOrder` with `order.inputs = [ {token: EvilToken, amount: X}, {token: LegitToken, amount: Y} ]`; both tokens get escrowed successfully since `placeOrder` performs no destination-address checks (transfer is `msg.sender -> gateway`, which succeeds).
3. A solver calls `fillOrder`/`_fillSameChain`, sending the real output assets to the order's beneficiary, expecting `_withdraw` to pay out `EvilToken` + `LegitToken` escrow to itself.
4. `_withdraw`'s loop reaches `EvilToken` and calls `safeTransfer(solver, X)`, which reverts (creator blacklists/never allowlists the solver). The entire `fillOrder` transaction reverts, including the solver's already-attempted output transfer and the `LegitToken` payout.
5. Repeat: every future fill/redeem attempt for this commitment fails the same way — the escrowed `LegitToken` amount is now permanently unclaimable by any solver, since there is no code path to release `body.tokens` partially or exclude `EvilToken`.
