### Title
Permissionless `RegisterERC20` combined with self-reported `balanceOf`/`transfer` checks allows minting of fully-backed-looking native Cosmos coins from a fake ERC20 contract - ([File: x/erc20/keeper/msg_server.go])

### Summary
`MsgRegisterERC20` can, depending on the `PermissionlessRegistration` param, be submitted by *any* unprivileged account to register an arbitrary, attacker-deployed ERC20 contract as a `TokenPair`. [1](#0-0)  Once registered, `MsgConvertERC20` mints real native Cosmos-SDK bank coins for that token pair's denom, relying entirely on the attacker-controlled contract's own `balanceOf`/`transfer` return data to prove that tokens were actually escrowed. [2](#0-1)  This is the direct on-chain analog of the reported `buyCredits` bug: value (spendable native coins) is minted in exchange for an arbitrary, unvetted ERC20 token whose legitimacy/behavior is never independently verified.

### Finding Description
`RegisterERC20` explicitly documents itself as permissionless: "Any account can permissionlessly register a native ERC20 contract to map to a Cosmos Coin" when `params.PermissionlessRegistration` is true, in which case `validateAuthority` is skipped entirely. [3](#0-2)  The registration path (`registerERC20`) only checks for duplicate registration and pulls ERC20 metadata via `CreateCoinMetadata`; it performs no code/behavior audit of the contract. [4](#0-3) 

Once a token pair exists, `ConvertERC20` → `convertERC20IntoCoinsForNativeToken` mints native coins as follows:
1. Reads `balanceToken` (module's ERC20 balance) via a `BalanceOf` **view call into the very contract being converted**.
2. Calls `transfer(moduleAddress, amount)` on that same contract.
3. Re-reads `balanceToken` after the call and requires `balanceTokenAfter == balanceToken + amount` (`ErrBalanceInvariance`).
4. If the check passes, it calls `bankKeeper.MintCoins` and sends the newly minted coins to the receiver. [5](#0-4) 

Because the attacker fully controls the bytecode of the registered contract, both `balanceOf` and `transfer` are just Solidity functions the attacker writes. A contract can trivially satisfy the invariance check (e.g., `balanceOf` simply returns a value derived from a counter incremented on every `transfer` call, or unconditionally returns "expected" numbers, without ever custodying real value) while performing no genuine escrow of anything of value. The repository's own test fixtures demonstrate that this pattern is exploitable by "evil tokens" that manipulate transfer semantics (`ERC20DirectBalanceManipulation.sol`, `ERC20MaliciousDelayed.sol`), showing the balance-invariance check is a self-referential trust check on attacker-supplied code, not an external verification of value transfer. [6](#0-5) [7](#0-6) 

The result: an attacker can register a purpose-built fake ERC20, call `MsgConvertERC20`, and have the chain's `bankKeeper.MintCoins` mint genuine native Cosmos coins under a legitimate-looking denom (`erc20:<contractAddr>`) with zero backing value, since the "proof of escrow" is entirely self-reported by the same malicious contract. [8](#0-7) 

### Impact Explanation
This breaks the core `x/erc20` accounting invariant that the module documents itself as enforcing (1:1 correspondence between ERC20 token custody and native coin supply) and directly matches the allowed Critical impact: "unauthorized minting ... of spendable user value across native balances ... ERC20 representations." An attacker can mint an arbitrary amount of a native denom that appears identical (same code path, same events, same query surface) to a legitimately-escrowed ERC20-backed coin, then use IBC transfer, DEX liquidity, or governance/community trust in the `erc20:` denom naming convention to extract real value from other users who assume the coin is genuinely backed 1:1.

### Likelihood Explanation
Likelihood is high for an unprivileged, financially motivated attacker: registering a token pair for an arbitrary contract requires only deploying a contract and submitting `MsgRegisterERC20` (permissionless in the default-analog configuration where `PermissionlessRegistration=true`), and then submitting a single `MsgConvertERC20`. No special privileges, validator collusion, or governance approval is needed in that mode. Even when `PermissionlessRegistration=false` is set (requiring authority/governance) the underlying flaw — that the escrow "proof" is self-reported by the same contract being converted — remains present for any contract that governance chooses to approve without a full security audit, meaning the invariant itself is fundamentally weak regardless of registration gating.

### Recommendation
- Do not rely solely on the same contract's `balanceOf`/`transfer` return values as proof of escrow. Cross-validate against independent signals (e.g., verify `Transfer` event topics/from/to/value match expectations exactly, rather than trusting `balanceOf` deltas that the same contract computes).
- Require additional standards conformance checks and/or a maintained allow-list/deny-list for tokens eligible for `MsgRegisterERC20`, especially while `PermissionlessRegistration` is enabled.
- Consider requiring a bonded/staked deposit or time-delay + challenge period for permissionless registrations so that malicious token pairs can be detected and disabled (`ToggleConversion`) before large-scale minting occurs.
- Cap or rate-limit minting per newly-registered, unaudited token pair.

### Proof of Concept
1. Attacker deploys a malicious ERC20 contract (analogous to `ERC20DirectBalanceManipulation.sol`/`ERC20MaliciousDelayed.sol` in this repo's own test fixtures) whose `balanceOf` and `transfer` functions are crafted to satisfy `balanceTokenAfter == balanceToken + amount` without any real token custody (e.g., `balanceOf(moduleAddr)` returns a value computed to always match the expected post-transfer number, while `transfer` performs no genuine value movement).
2. Attacker submits `MsgRegisterERC20{Signer: attacker, Erc20Addresses: [maliciousContract]}` — succeeds without governance if `PermissionlessRegistration=true` (see `x/erc20/keeper/msg_server.go:326-336`).
3. Attacker submits `MsgConvertERC20{ContractAddress: maliciousContract, Amount: X, Receiver: attacker, Sender: attackerHex}`.
4. `convertERC20IntoCoinsForNativeToken` calls `transfer` and re-checks `BalanceOf`, both served by the attacker's contract, so the invariance check passes trivially.
5. `bankKeeper.MintCoins(ctx, types.ModuleName, coins)` mints `X` native coins of denom `erc20:<maliciousContract>`, sent to the attacker — real, spendable native supply created from nothing.

Note: I could not fully confirm the compiled default value of `PermissionlessRegistration` (whether `true` or `false` at genesis) due to index limits on `x/erc20/types/params.go`; this affects only whether the exploit requires governance approval of the initial contract registration or is fully permissionless out-of-the-box — the core minting-invariant weakness in `convertERC20IntoCoinsForNativeToken`/`ConvertCoinNativeERC20` is independent of that setting.

func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
