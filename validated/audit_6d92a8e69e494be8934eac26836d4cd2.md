## Analysis

The report's core flaw is that a single unified admin-role signing/authorization scheme is reused for multiple, functionally-different privileged actions, so a signature or credential meant for one purpose can be repurposed for another. Hyperbridge's `pallet-relayer` reproduces this exact class of bug in its off-chain-signature based fee model: two independent, permissionless (`ensure_none`) extrinsics hash their signed payloads identically over a **shared nonce namespace**, with no domain separator distinguishing them.

`modules/pallets/relayer/src/withdrawal.rs` computes the message a relayer signs to authorize a fee **withdrawal**: [1](#0-0) 

`modules/pallets/relayer/src/accumulate.rs` computes the message a relayer signs to redirect the **beneficiary of a fee-accumulation claim**: [2](#0-1) 

Both hash `keccak256(encode(nonce: u64, state_machine: StateMachine, beneficiary: Vec<u8>))` — byte-for-byte identical encodings, with no tag distinguishing "withdraw" from "beneficiary redirect." Both consume the *same* `Nonce<T>` map keyed by `(address, state_machine)`: [3](#0-2) [4](#0-3) 

Both entry points (`accumulate_fees` and `withdraw_fees`) are unsigned/permissionless, dispatchable by anyone who has a valid signature payload: [5](#0-4) 

### Title
Cross-function signature replay between `withdraw_fees` and `accumulate`'s beneficiary redirect due to identical unsalted message hashing and a shared nonce namespace - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-relayer` signs two structurally different authorizations — "redirect this accumulate() claim's beneficiary" and "withdraw my entire accumulated balance to this beneficiary" — with the exact same `keccak256(nonce, state_machine, beneficiary)` scheme and the same per-`(relayer, state_machine)` nonce counter. There is no function-specific domain tag. Any unprivileged party who observes a relayer's beneficiary-redirect signature (submitted as part of an `accumulate_fees` call, or otherwise obtained) can replay it against `withdraw_fees` for the same `state_machine`, since the message hash and nonce match exactly, triggering an unintended full withdrawal instead of the intended partial-claim redirect.

### Finding Description
`withdrawal::message` and `accumulate::beneficiary_message` produce identical digests for the same `(nonce, state_machine, beneficiary)` triple. Because `Nonce<T>` is shared between the withdraw path (`dest_chain` key) and the accumulate path (`source` `state_machine` key) for the same relayer address, a signature the relayer created for one call is a fully valid, un-expired signature for the other call as long as the relevant nonce has not yet advanced. This is a classic missing-domain-separator replay bug: neither function encodes which pallet action it authorizes, so `Signature::verify` cannot distinguish "I intend to redirect this specific accumulate claim" from "I intend to withdraw my whole accumulated balance."

### Impact Explanation
An unprivileged actor who captures a relayer's beneficiary-redirect signature (visible in the public unsigned-extrinsic mempool/block data before or as `accumulate_fees` executes) can submit `withdraw_fees` with the same `(nonce, state_machine, beneficiary)` tuple. Because the check in `withdraw()` only validates the signature and nonce — not which action was intended — this forces:
- an unauthorized, premature drain of the relayer's entire `Fees<T>` balance for that chain via a real ISMP dispatch to the destination host manager, and
- consumption of the nonce, which invalidates the relayer's still-pending, legitimately-intended `accumulate_fees` call (since its nonce no longer matches), potentially stranding the fee amount from that batch (it can no longer be redirected as planned, and the underlying `RequestCommitments` leaf may already have been marked `claimed` if `accumulate` executes anyway with a different nonce path).

This is unauthorized execution of a fund-moving extrinsic (`withdraw_fees`) triggered by replaying a signature that was never intended to authorize a withdrawal, satisfying the "unauthorized transaction/execution" and "logic attack" bounty categories without requiring any admin, relayer collusion, or leaked key — only observation of already-broadcast signed data.

### Likelihood Explanation
Both `accumulate_fees` and `withdraw_fees` are unsigned extrinsics (`ensure_none`), meaning their payloads (including the relayer's signature) are visible in the transaction pool / block body before or as they execute — no special access is required to obtain them. The replay requires only that the withdrawal nonce for `(relayer, state_machine)` has not advanced past the value used in the captured signature, which is the common case immediately after the relayer builds their beneficiary-redirect signature and before it lands on-chain, or any time it has not yet been consumed elsewhere.

### Recommendation
Add a per-function domain separator (e.g., a distinct byte prefix or string literal such as `b"RELAYER_WITHDRAW"` vs `b"RELAYER_BENEFICIARY_REDIRECT"`) into both `message()` and `beneficiary_message()` so a signature valid for one action can never be replayed as the other. Additionally, consider using independent nonce counters (or namespacing the nonce map by function) so consuming a nonce in one flow cannot invalidate or be confused with the other flow's pending signature.

### Proof of Concept
1. Relayer `R` finishes a delivery and signs `beneficiary_message(nonce=N, state_machine=Evm(1), beneficiary=B)` intending to redirect the fee credit from an upcoming `accumulate_fees(withdrawal_proof)` call (with `beneficiary_details = Some((B, sig))`).
2. Before `R`'s `accumulate_fees` transaction is included, attacker `A` observes `sig` (public in the mempool/blockchain).
3. `A` submits `withdraw_fees(WithdrawalInputData { signature: sig, dest_chain: Evm(1), beneficiary: Some(B) })`.
4. `Pallet::withdraw` computes `message(Nonce::<T>::get(R, Evm(1)), Evm(1), Some(B))`, which equals the exact digest `R` signed in step 1 (same nonce value, same encoding), so `signature.verify(&msg, None)` succeeds and recovers `R`'s address.
5. The pallet dispatches an ISMP withdrawal of `R`'s entire `Fees<T>::get(Evm(1), R)` balance to `B`, zeroes `Fees`, and increments the nonce — all before `R`'s intended `accumulate_fees` call executes, which now fails on nonce mismatch and/or double-affects the same beneficiary-redirect authorization.
