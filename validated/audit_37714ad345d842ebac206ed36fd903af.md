### Title
CW721 pointer's `approve()` can never revoke a per-token approval - ([File: contracts/src/CW721ERC721Pointer.sol])

### Summary
`CW721ERC721Pointer.approve()` unconditionally forwards every approval call to the backing CosmWasm CW721 contract as an `{"approve":{...}}` execute message. It never issues the CW721 `Revoke` message, and it has no dedicated revoke path for single-token approvals (unlike `setApprovalForAll`, which correctly branches to `approve_all`/`revoke_all`). As a result, an NFT owner who grants a per-token approval through the standard ERC721 `approve()` call has no way to withdraw that approval.

### Finding Description
`CW721ERC721Pointer.approve()`: [1](#0-0) 

always builds an `approve` wasm payload regardless of the `approved` argument value. Compare this to `setApprovalForAll`, which correctly distinguishes the approve/revoke cases: [2](#0-1) 

The underlying reference CW721 contract that the pointer wraps exposes a distinct `Approve` vs `Revoke` execute variant, and only `Revoke` actually clears an existing per-token approval: [3](#0-2) [4](#0-3) 

Under the standard ERC721/OpenZeppelin semantics that `CW721ERC721Pointer` inherits, a spender's approval is supposed to be revocable by calling `approve(address(0), tokenId)`. But the pointer's `approve()` implementation has no special case for `address(0)` — it calls `AddrPrecompile.getSeiAddr(address(0))` to build the "spender" field of an `approve` (not `revoke`) wasm message. Since the zero address has no Sei association, this call reverts (the `getSeiAddr`/association lookups elsewhere in the codebase revert with an association-missing error for unassociated addresses), so the standard revoke pattern is unusable, and there is no alternative function on the pointer that ever emits a `Revoke` message to the CW721 contract.

### Impact Explanation
Once an owner calls `approve(spender, tokenId)` through the ERC721-compatible pointer, that approval is permanent from the pointer's perspective — the owner has no way, through any exposed pointer function, to revoke the single-token approval (only `setApprovalForAll(operator, false)`/`revoke_all` works, which is a different, broader authorization). This grants the approved spender indefinite unauthorized-transfer capability over that specific token even after the owner wants to withdraw trust (e.g., in case of a compromised dApp, mistaken approval, or a former counterparty), matching "unauthorized transfer via ... pointer" from the accepted impact categories.

### Likelihood Explanation
Any user of a CW721 NFT collection exposed through the standard `CW721toERC721` pointer path can trigger this by simply calling `approve()` once (a completely ordinary, permissionless ERC721 action) — no privileged role or special setup is required. The bug is deterministic and always reachable whenever a per-token approval is granted through the pointer.

### Recommendation
In `CW721ERC721Pointer.approve()`, mirror the `setApprovalForAll` pattern: when `approved == address(0)`, build and send a CW721 `revoke` message (with the token's current spender, if any) instead of an `approve` message with an unresolvable zero-address spender, so that per-token approvals can be properly cleared.

### Proof of Concept
1. Owner (via the pointer) calls `approve(spenderEvmAddr, tokenId)` — this succeeds and sends `{"approve":{"spender": "<sei addr of spender>", "token_id": "..."}}` to the CW721 contract, granting `spender` transfer rights over `tokenId` [1](#0-0) .
2. Owner later wants to revoke this and calls the standard ERC721 revoke pattern `approve(address(0), tokenId)`.
3. This calls `AddrPrecompile.getSeiAddr(address(0))`, which reverts because the zero address has no Sei association — the transaction fails, and even if it somehow succeeded it would still send an `approve` (not `revoke`) message, which the underlying CW721 contract treats as granting approval to whatever bech32 address is derived, not clearing it [5](#0-4) .
4. There is no other pointer method that emits `Revoke`, so `spender`'s approval for `tokenId` remains active indefinitely, confirmed by the absence of any revoke branch in `CW721ERC721Pointer.approve()` [1](#0-0) .

```rust
pub fn execute_approve(
    deps: DepsMut<EvmQueryWrapper>,
    info: MessageInfo,
    spender: String,
    token_id: String,
    approved: bool,
) -> Result<Response<EvmMsg>, ContractError> {
    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let mut payload_spender = spender.clone();
    let mut action = "approve";
    if !approved {
        payload_spender = "".to_string();
        action = "revoke";
    }
    let payload = querier.erc721_approve_payload(payload_spender, token_id.clone())?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("action", action)
        .add_attribute("token_id", token_id)
        .add_attribute("sender", info.sender)
        .add_attribute("spender", spender.clone())
        .add_message(msg);

    Ok(res)
}
```
