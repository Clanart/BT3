### Title
KeyMachine::calculate_share panics on a share from a participant who never sent commitments - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
`KeyMachine::calculate_share` iterates over every `EncryptedMessage` share it is handed and unconditionally indexes `self.commitments[&l]` to build the share-verification statements. The `commitments` map only contains entries for participants who actually supplied a commitments message in round 1 (inserted at `pedpop/src/lib.rs:331` for senders, and `:336` for ourselves). `validate_map` only constrains the share keys to the valid participant-index range `1..=n` (`pedpop/src/lib.rs:468-472`) — it does not require the sender to have appeared in round 1. A participant who withholds their round-1 commitments message but still sends a round-2 share therefore causes a `HashMap` index panic, crashing the honest party running the DKG. This is the Serai analog of CVE-2018-3284's bug class: a remotely reachable, repeatable crash/DoS of a protocol participant via crafted peer input, requiring no special privileges beyond being a DKG participant.

### Finding Description
In `verify_r1`, commitments are only inserted into the map for participants whose `commitment_msgs` entry was present (`let Some(msg) = commitment_msgs.remove(&l) else { continue };` at `pedpop/src/lib.rs:314`, insertion at `:331`). The resulting `commitments` map is stored in the `KeyMachine` (`:377`).

Later, in `calculate_share` (`pedpop/src/lib.rs:463-499`):

```rust
validate_map(&shares, &all_participant_indexes, self.params.i())?;  // only checks index range
for (l, share_bytes) in shares.drain() {
  let (mut share_bytes, blame) = self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
  ...
  batch.queue(rng, BatchId::Share(l),
    share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share));  // panics if l ∉ commitments
}
```

`share_verification_statements` is called with `&self.commitments[&l]`, a `HashMap` index that panics when `l` is absent (`pedpop/src/lib.rs:490`). Since `validate_map` (`dkg/src/lib.rs` / `frost` helper) only enforces that every key is a valid participant index within `1..=n` and is not ourselves, a participant `l` who never sent a `Commitments` message passes validation yet has no entry in `self.commitments`.

Notably, the panic occurs *before* the batch is verified and regardless of whether the share's decryption/PoP was valid, because `self.commitments[&l]` is evaluated while queueing statements, not as part of the batch. Even if `self.encryption.decrypt` internally treats an unregistered sender gracefully (queuing a failing statement via the `BatchId::Decryption(l)` ID, which the blame machinery at `:493-499` is designed to handle by returning `PedPoPError::InvalidShare`), the subsequent unconditional indexing of `self.commitments` defeats that blame path entirely.

### Impact Explanation
An unprivilege-equivalent party (any participant index in the DKG's `1..=n` range, which is exactly who feeds `EncryptedMessage` shares into `calculate_share`) can deterministically panic an honest participant's key-generation run. A panic in the processor aborts the running protocol task / thread; under Serai's processor usage (`processor/src/key_gen.rs:416` calls `machine.calculate_share` and only converts `PedPoPError`s into blame messages), a Rust panic is not caught by the `Err` handling — it unwinds past `handle_machine`, crashing the honest node's key generation rather than producing an `InvalidShare` report. This is a complete, repeatable availability loss for the victim's DKG participation, matching the CVE's "unauthorized ability to cause a hang or frequently repeatable crash" impact class.

### Likelihood Explanation
Likelihood is high for a faulty/malicious counterparty: the trigger requires only *not* sending a round-1 commitments message while still sending a round-2 share — trivial to construct, no cryptographic work, fully deterministic, and no timing/race requirements. The only mitigating factor is that the attacker must be one of the `n` registered DKG participants (the same reachability constraint the prompt's rules accept for `calculate_share` inputs), and that callers are expected to panic-catch or restart. Compared to the source CVE (which required high privileges and high attack complexity), this analog is easier to trigger but targets a smaller blast radius (one honest participant's key-gen execution rather than a database server).

Caveat: if `self.encryption.decrypt` itself panics or errors for unregistered senders before reaching line 490, the panic still occurs (availability impact identical), just via a different line — the `&self.commitments[&l]` index is reached unconditionally for every validated share key.

### Recommendation
In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-492`), treat a missing `self.commitments` entry the same as any other faulty share: check `self.commitments.get(&l)` first and return/queue `PedPoPError::InvalidShare { participant: l, blame: None }` (or the appropriate `BatchId`-based blame) instead of indexing. Similarly, ensure `self.encryption.decrypt` cannot panic for an unregistered `l` (return a blame-`None` invalid-share result). Optionally, reject share senders in `validate_map` who were not commitment senders.

### Proof of Concept
1. Run a PedPoP DKG with `n >= 2`, `t >= 1`. Honest party `i` completes round 1 via `SecretShareMachine::generate_secret_shares`, having received commitments only from a subset of participants (participant `l` sends none — `verify_r1`'s `else { continue }` skips inserting `l` into `commitments`).
2. In round 2, `l` sends `i` an `EncryptedMessage<C, SecretShare<C::F>>` (any bytes parseable by `EncryptedMessage::read`, or even well-formed encryption under any key `l` chooses).
3. `i` calls `KeyMachine::calculate_share` with `shares` containing key `l`. `validate_map` passes (`l ∈ 1..=n`, `l != i`).
4. The drain loop reaches `share_verification_statements::<C>(..., &self.commitments[&l], ...)` → `HashMap` index panic: `no entry found for key`. The honest node's key generation crashes instead of emitting `InvalidShare` blame.

Relevant code: `crypto/dkg/pedpop/src/lib.rs:313-336` (commitments only inserted for round-1 senders), `crypto/dkg/pedpop/src/lib.rs:468-499` (unconditional `self.commitments[&l]` at line 490), `processor/src/key_gen.rs:404-431` (in-scope caller where the panic propagates uncaught through the `Err` matching).
