### Title
Cross-function signature replay: `withdraw()` and `accumulate()` share an identical SCALE-encoded message format and nonce, letting a relayer's beneficiary-redirect signature be replayed between the two functions - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet-relayer` authenticates two distinct fund-moving operations - `Pallet::withdraw` (immediate disbursement of already-accumulated fees) and `Pallet::accumulate` (crediting newly-proven delivery fees, optionally to a redirected beneficiary) - with signatures over messages built from the exact same tuple shape `(nonce: u64, StateMachine, Vec<u8>/&[u8])` and the exact same per-`(address, state_machine)` `Nonce` counter. Because SCALE-encodes `Vec<u8>` and `&[u8]` identically, `withdrawal::message(nonce, dest_chain, Some(beneficiary))` and `accumulate::beneficiary_message(nonce, state_machine, &beneficiary)` produce byte-identical preimages (and therefore identical keccak256 hashes and identical valid signatures) whenever `nonce`, chain, and beneficiary bytes match. This is the same broken invariant as the `KeystoreAccount.isValidSignature` report: a signature that doesn't bind which "account"/context it authorizes can be replayed into a sibling context that shares a signer.

### Finding Description

`accumulate::beneficiary_message` (used inside `accumulate()`): [2](#0-1) 

Both messages hash `(nonce, StateMachine, beneficiary_bytes).encode()`. `withdraw()` reads the nonce via `Nonce::<T>::get(address, withdrawal_data.dest_chain)`: [3](#0-2) 

`accumulate()` reads the *same* `Nonce` map keyed by `(delivery_address, state_machine)` and verifies the same signature format against it: [4](#0-3) 

Because the two functions share (a) the identical message-encoding scheme and (b) the identical nonce counter keyed by `(signer, state_machine)`, a signature the relayer produced to authorize one action is inherently a valid signature for the other action, as long as the nonce hasn't advanced. `withdraw()` has a code path where the nonce is *not* consumed even though signature verification already succeeded: the `available_amount < min_withdrawal` check happens **after** signature verification but **before** `Nonce::try_mutate` increments the counter: [5](#0-4) 

So any `withdraw_fees` extrinsic that verifies the relayer's signature but then reverts on `NotEnoughBalance` leaves a fully valid, publicly-visible `(nonce, dest_chain, beneficiary, signature)` tuple on-chain with the nonce still un-consumed. That exact tuple is a drop-in valid `beneficiary_details` argument for a subsequent, unrelated `accumulate_fees` call for that relayer's next proven delivery on the same `state_machine` - redirecting the newly-accumulated fee to whatever beneficiary the relayer had put in the reverted withdrawal attempt, entirely independent of what the relayer intended to authorize with that signature at accumulation time. The reverse direction also holds: because the format only differs in the presence/absence of a beneficiary and message() drops to a 2-tuple when `beneficiary` is `None`, any signed 3-tuple beneficiary message the relayer produces for one function is generically reusable in the other function's verification path as long as nonce/chain/bytes line up.

### Impact Explanation
This breaks the "one-time, single-purpose authorization" guarantee that `Nonce` is supposed to provide (the module doc explicitly claims "Includes the per-relayer nonce so a captured signature cannot be replayed" - true for replay against the *same* function, false across functions). The result is fund misdirection: a relayer's fee earnings can be redirected to a beneficiary the relayer only authorized for a different, narrower purpose (or under different balance/context assumptions), without the relayer's current consent for that specific accumulation event. Since `Nonce` is shared, this is not a hypothetical coincidence - it's guaranteed collision by construction whenever the signed fields match, and the withdrawal code path structurally produces publicly-visible unconsumed signatures whenever a withdrawal reverts on the balance-floor check.

### Likelihood Explanation
No malicious relayer, prover, admin, or governance actor is required. The attacker is any unprivileged party who can read chain state (the reverted `withdraw_fees` extrinsic and its signature are public) and submit a permissionless, unsigned `accumulate_fees` extrinsic with a legitimate state proof of any of that relayer's subsequent, unclaimed deliveries. The precondition (a `withdraw_fees` call that reverts on `NotEnoughBalance` after signature verification) is a normal, easily-reachable operational occurrence for any relayer testing withdrawal below `MinWithdrawal`/per-chain minimum, not an edge case requiring privileged behavior. This is distinct from front-running: the attacker does not need to race or preempt a specific pending transaction — the leaked, nonce-unconsumed signature remains valid and reusable at leisure against any future qualifying delivery.

### Recommendation
Domain-separate the two signed payloads so a signature cannot be structurally valid for both functions — e.g., include a distinct action tag/discriminator byte (or the function selector / pallet call index) as the first encoded field of both `message()` and `beneficiary_message()`, so `(ACTION_WITHDRAW, nonce, dest_chain, beneficiary)` and `(ACTION_ACCUMULATE, nonce, state_machine, beneficiary)` can never collide even when all other fields match. Additionally, consider using separate `Nonce` maps (or a per-purpose sub-key) for `withdraw` versus `accumulate` beneficiary redirection so that a nonce left un-consumed by a reverted `withdraw` can never be valid input to `accumulate`, and vice versa.

### Proof of Concept
1. Relayer `R` has delivered messages and accumulated fee credit as `delivery_address = R` on `state_machine = X`. `Nonce[R][X] = N`.
2. `R` submits `withdraw_fees(WithdrawalInputData { signature: sig_over(message(N, X, Some(B))), dest_chain: X, beneficiary: Some(B) })` intending a routine withdrawal, but `Fees[X][R] < MinWithdrawal`, so the call passes signature verification and then reverts with `NotEnoughBalance` **before** `Nonce::try_mutate` runs (`modules/pallets/relayer/src/withdrawal.rs:116-131`). `Nonce[R][X]` remains `N`. The failed extrinsic (containing `sig`, `X`, `B`) is on-chain/public.
3. `R` later delivers a new, unclaimed request on `state_machine = X` (still unclaimed, `Nonce[R][X]` still `N` since `R` never successfully called anything that consumes the nonce).
4. Attacker `A` (no special role) submits `accumulate_fees(WithdrawalProof { commitments: [new_commitment], source_proof, dest_proof, beneficiary_details: Some((B, sig)) })` using the public state proofs of `R`'s delivery and the leaked `sig`/`B` from step 2.
5. `accumulate()` computes `beneficiary_message(N, X, &B)` — byte-identical to `message(N, X, Some(B))` from step 2 — so `sig` verifies against `delivery_address = R`, `Nonce[R][X]` increments to `N+1`, and the newly accumulated fee is credited to `Fees[X][B]` instead of `Fees[X][R]` (`modules/pallets/relayer/src/accumulate.rs:106-147`), even though `R` never authorized this specific accumulation to be redirected.

		let address = match &withdrawal_data.signature {
			Signature::Evm { address, .. } => address.clone(),
			Signature::Sr25519 { public_key, .. } => public_key.clone(),
			Signature::Ed25519 { public_key, .. } => public_key.clone(),
		};

		let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);
		let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());

		match &withdrawal_data.signature {
			Signature::Evm { address, .. } => {
				let eth_address = withdrawal_data
					.signature
					.verify(&msg, None)

				if &eth_address != address {

			},

				// Verify signature with public key provided in signature enum

			},

pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
