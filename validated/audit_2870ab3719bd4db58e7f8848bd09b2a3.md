### Title
`onAccept` `UpdateParams` stores destination protocol fees keyed by raw `bytes32` while `placeOrder` looks them up keyed by `keccak256(order.destination)`, causing destination-fee overrides to silently never apply - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The canonical `DestinationFee` struct defines `chain` as `bytes` (the raw, variable-length state machine ID), and the correct pattern — used consistently in `evm/src/apps/intentsv2/IntentsBase.sol` — is to key `_destinationProtocolFees` by `keccak256(chain)`. The Tron fork of `IntentGatewayV2` diverges: its local `DestinationFee` usage in `onAccept` treats `update.destinationFees[i].stateMachineId` as an already-computed `bytes32` and writes it directly into `_destinationProtocolFees[stateMachineId]` with no hashing, while `placeOrder` reads the same map with `keccak256(order.destination)` as the key.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`:

- `onAccept` (governance `UpdateParams` path): [1](#0-0) 
writes `_destinationProtocolFees[stateMachineId] = feeBps` where `stateMachineId` is used directly as the map key (not hashed).

- `placeOrder` (user-facing path): [2](#0-1) 
reads the fee via `_destinationProtocolFees[keccak256(order.destination)]`.

These two code paths use different key derivations for the same mapping: one path never hashes the identifier, the other always hashes the raw destination bytes. The result is that whatever key governance intends to register (`stateMachineId`) essentially never matches the key `placeOrder` computes (`keccak256(order.destination)`), since a raw `bytes` value equals its own `keccak256` hash only in the astronomically unlikely case of a hash collision with a legitimate chain identifier. This mirrors the reported `_fillOrders`/`isPairZeroFee` bug class exactly: a lookup function is fed the wrong derived parameter (unhashed identifier vs. hashed identifier) so the intended check/override never actually matches, and the fallback ("no fee configured") path is silently taken instead.

### Impact Explanation
The practical effect is that `_destinationProtocolFees` set via cross-chain governance (`RequestKind.UpdateParams`) never takes effect on `placeOrder`, and the contract silently falls back to `_params.protocolFeeBps` for every destination: [3](#0-2) 
This is a fee-determination correctness bug in a live intent-settlement path — every order placed against the Tron gateway silently ignores destination-specific protocol fee configuration set by governance, producing a fee mismatch between the intended (governance-approved) fee schedule and what is actually deducted from user escrow. Since protocol fee dust is retained by the gateway (`DustCollected`), this is a form of "wrong amount charged," directly matching the required impact class of financial-logic bugs in fee/settlement accounting, though it does not on its own let an attacker steal funds beyond the protocol's own configured default fee.

### Likelihood Explanation
This triggers deterministically on every `placeOrder` call to the Tron `IntentGatewayV2` any time governance has configured a non-default per-destination fee, with no attacker action required — any user placing an order is affected. The bug is purely a code-level key-derivation inconsistency between the write path and read path, not dependent on any relayer/prover/admin misbehavior, so it passes the impact gate as a genuine logic/accounting bug rather than a trust-assumption complaint.

### Recommendation
Make the key derivation consistent between write and read in `evm/tron/contracts/apps/IntentGatewayV2.sol`:
```solidity
// onAccept — UpdateParams
bytes memory rawChain = update.destinationFees[i].chain; // or however the struct field is decoded
_destinationProtocolFees[keccak256(rawChain)] = feeBps;
```
Ensure the `DestinationFee` struct/ABI used in the Tron contract matches the canonical `bytes chain` field (as in `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`), and hash it the same way both when writing (`onAccept`) and reading (`placeOrder`) — mirroring the fix pattern from the external report (use the correct, consistently-derived identifier rather than an unrelated/differently-typed one).

### Proof of Concept
1. Governance dispatches `RequestKind.UpdateParams` with `destinationFees = [{ chain: "ARBITRUM" (bytes), destinationFeeBps: 50 }]` intending a reduced 0.5% fee for Arbitrum.
2. `onAccept` executes `_destinationProtocolFees[stateMachineId] = 50` where `stateMachineId` is decoded as a `bytes32` — effectively distinct from `keccak256("ARBITRUM")`.
3. A user calls `placeOrder` with `order.destination = "ARBITRUM"`.
4. `placeOrder` computes `destinationHash = keccak256(order.destination)` and looks up `_destinationProtocolFees[destinationHash]`, which is `0` (never written by step 2).
5. The gateway falls back to `_params.protocolFeeBps` (e.g., 1%) instead of the governance-intended 0.5%, over-charging every order to that destination — the destination-fee override is unreachable/dead code in practice.

Note: I could not locate the exact ABI decode statement that converts `update.destinationFees[i]` into the local `stateMachineId` variable inside the Tron `onAccept` function beyond what's shown (the surrounding struct field types for the Tron-specific `DestinationFee`/`ParamsUpdate` decode were not fully visible in the indexed excerpts). If the Tron contract's local struct actually declares `chain` as `bytes32` already pre-hashed off-chain by the coprocessor before dispatch, the mismatch would instead be a documentation/consistency issue rather than an exploitable bug — confirming this precisely requires reading the full Tron `IntentGatewayV2.sol` struct definitions and the `intents-coprocessor` pallet's Tron-specific encoding, which is best done in a full Devin session with complete file access.
