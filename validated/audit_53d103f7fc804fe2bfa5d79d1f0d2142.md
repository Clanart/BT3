### Title
Automatic remote-URL rewrite driven entirely by a self-reported GitHub API field, silently redirecting future pushes/fetches - (`app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` silently rewrites a repository's `origin` remote whenever the cached `GitHubRepository.cloneURL` still matches the local remote and the newly fetched API repository's `clone_url` differs, gated only by a same-protocol check. Because `apiRepo.clone_url` is data returned by whatever endpoint the account is configured against (github.com or a GitHub Enterprise Server the user added), and none of the guard conditions actually validate that the *new* URL still points at a trustworthy host, an attacker who controls that API response (malicious/compromised GHES instance, or a MITM of the API endpoint) can redirect the local git remote to an attacker-controlled server without any user confirmation.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches repository metadata from the API on every repository selection/refresh cycle and unconditionally feeds the result into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then applies three checks before silently calling `gitStore.setRemoteURL`: [2](#0-1) 

- `remoteUrlUnchanged` only checks that the *previously cached* `gitHubRepository.cloneURL` (itself populated from a prior, equally untrusted API response) still matches the current git remote — i.e., "the user hasn't manually diverged from what the API told us last time."
- `protocolsMatch` only compares the URL scheme (`https:` vs `https:`), not host/owner/name.
- Neither check validates that the *new* `apiRepo.clone_url` points at the expected host/owner/repo, or prompts the user in any way.

This mirrors the Suzaku pattern exactly: a consistency check exists (`protocolsMatch`, `remoteUrlUnchanged`) but is trivially satisfiable by the very same untrusted input it's supposed to guard, so the "guard" never actually blocks a hostile value — the branch that performs the sensitive state change (`setRemoteURL`) executes with attacker-controlled data intact. There is no confirmation dialog anywhere in this path; `_selectRepositoryRefreshTasks` invokes it automatically on every repository selection. [3](#0-2) 

### Impact Explanation
The corrupted value is the git `origin` remote URL used for all future `fetch`/`pull`/`push` operations. If an attacker controls the API response for an added GitHub Enterprise endpoint (compromised GHES, or a network position that can MITM API traffic to a GHES the user trusts — note dotcom traffic is TLS-pinned via GitHub's cert, but self-hosted/enterprise endpoints are user-added and Desktop does not pin certs to a specific expected host in this code path), they can set `clone_url` in the repository payload to any HTTPS/SSH URL with the same scheme. On the next repository refresh, Desktop silently repoints `origin` to that URL. Subsequent user pushes then send commits to the attacker's server (which can further relay to a real GitHub host, harvesting private code, or simply diverge history), and subsequent fetches/pulls pull attacker-supplied refs into the user's working copy — this is "silent corruption of what the user commits or pushes" carried out via an attacker-controlled GitHub API object, one of the explicitly valid impact categories.

### Likelihood Explanation
The check only requires: (a) the locally cached `cloneURL` still equalling the current remote (true for the overwhelming majority of unmodified clones), and (b) the new URL sharing the same URL scheme as the old one — both trivial for an attacker who fully controls the API response body. No user interaction or confirmation is required; the rewrite happens automatically as part of routine background refreshes (`_selectRepositoryRefreshTasks`, periodic indicator refresh). The main constraint is that the attacker must control the API endpoint data (GHES compromise/MITM), which the report's valid-impact criteria explicitly allow ("attacker controls ... a GitHub API object").

### Recommendation
Do not let `apiRepo.clone_url` alone drive `setRemoteURL`. At minimum:
- Require the new URL's parsed hostname/owner/name (via `parseRemote`) to match the expected identifier of the associated `GitHubRepository` (endpoint hostname, owner, name) rather than only comparing protocol.
- If a repository transfer/rename legitimately changes the clone URL, prompt the user to confirm the remote change instead of applying it silently, mirroring the existing `UpstreamAlreadyExists`/`AddSSHHost`-style confirmation popups used elsewhere in Desktop for security-sensitive git state changes.

### Proof of Concept
1. Add and sign in to a GitHub Enterprise Server endpoint that the attacker controls (or intercept traffic to a legitimate but network-compromised GHES).
2. Have the user clone/add a repository from that endpoint; Desktop stores `gitHubRepository.cloneURL` matching the current `origin`.
3. On the next `repositoryWithRefreshedGitHubRepository` call (triggered by simply reselecting the repository or the periodic indicator refresh), have the attacker-controlled API return the same repository object but with `clone_url` changed to `https://attacker.example/owner/name.git` (same `https:` scheme as before).
4. `updateRemoteUrl` computes `remoteUrlUnchanged = true`, `protocolsMatch = true`, `urlsMatch = false`, and calls `gitStore.setRemoteURL('origin', 'https://attacker.example/owner/name.git')` with no dialog or confirmation.
5. The user's next `git push`/`git pull` now targets the attacker's server.

This is confirmed by the existing test suite, which demonstrates the update happens automatically whenever `clone_url` changes and the protocol/cached-URL conditions hold: [4](#0-3)

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
