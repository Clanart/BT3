## Analog Found

### Title
Lack of Slippage Control in `PublicDelegation.stake` / `PublicDelegation.stakeFor` Can Cause Stakers to Receive Fewer Shares Than Expected - (File: contracts/bindings/publicdelegation/PublicDelegation.go, source: PublicDelegation.sol)

### Summary
`PublicDelegation` is Kaia's ERC-4626-style staking vault: users send native KAIA via `stake()`/`stakeFor(address)` and receive shares computed from the current assets/shares exchange ratio (`convertToShares`/`previewDeposit`), exactly the pattern flagged as vulnerable in the `AuraVault::deposit`/`AuraVault::mint` report. Neither entry point accepts a minimum-shares (or maximum-assets) parameter, so an unprivileged staker's transaction can be executed against a share price that has moved unfavorably between submission and execution, with no on-chain mechanism to abort the trade.

### Finding Description
The `PublicDelegation` contract exposes `stake()` and `stakeFor(_recipient)` as payable entry points with no other arguments: [1](#0-0) [2](#0-1) 

Shares minted for a deposit are computed from the vault's asset-to-share exchange rate, exposed via `convertToShares`/`previewDeposit`: [3](#0-2) [4](#0-3) 

The `Staked(user, assets, shares)` event confirms that a variable `shares` amount is emitted for a given `assets` input, i.e., the conversion is not fixed at 1:1 and depends on vault state at execution time: [5](#0-4) 

Because `stake`/`stakeFor` take no `minShares` (or equivalent) parameter, a staker cannot bound the acceptable exchange rate at call time. This is structurally identical to the `AuraVault::deposit`/`mint` functions described in the external report, which compute shares via `previewDeposit`/`previewMint` and proceed with the deposit unconditionally.

The exchange rate underlying `convertToShares` can move between transaction submission and inclusion due to independent, permissionless actions reachable in the same block window — e.g., another user's `stakeFor` call, `redelegateByAssets`/`redelegateByShares` calls, or `redeem`/withdrawal requests changing total assets/total shares before the staker's transaction lands: [6](#0-5) [7](#0-6) 

### Impact Explanation
A staker submitting `stake()`/`stakeFor()` has no way to guarantee a minimum number of shares for the KAIA they lock up. If the exchange rate shifts unfavorably before their transaction executes (whether from ordinary vault activity, a classic ERC-4626 "donation"/inflation-style front-run, or simply commission/reward accrual changing the ratio), the staker permanently receives fewer shares than expected for the same amount of staked KAIA, i.e., unauthorized value loss for the staker with no recourse — matching the "unauthorized value movement" category required by this scan.

### Likelihood Explanation
Likelihood is moderate: any address can call `stake`/`stakeFor` as a plain, permissionless transaction (no special role required), and the exchange rate is influenced by other permissionless actions (deposits, redemptions, redelegations) that can be sequenced around a victim's transaction, particularly in a proposer-controlled block-building context. No privileged access, node compromise, or consensus-level assumption is required.

### Recommendation
Add explicit slippage-protection parameters to `stake`/`stakeFor` (e.g., a `minShares` argument that reverts if the computed shares fall below it), following the EIP-4626 guidance cited in the original report for EOA-facing deposit/mint paths.

### Proof of Concept
1. Alice calls `stakeFor(Alice)` sending X KAIA, expecting to receive Y shares based on the currently observed `convertToShares(X)`.
2. Before Alice's transaction is included, another party's `stakeFor`/`redelegateByShares`/withdrawal transaction changes total assets/total shares, shifting the exchange rate.
3. Alice's transaction executes with the new, worse rate and she receives fewer than Y shares for the same X KAIA, with no revert condition available to protect her, since `stake`/`stakeFor` accept no minimum-shares bound. [8](#0-7)
