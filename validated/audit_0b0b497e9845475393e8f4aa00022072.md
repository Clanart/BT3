## Analysis

The BarnBridge bug's core invariant: a proportional fee computed as `(amount * feeBps) / DENOMINATOR` truncates to `0` for small `amount`, letting an attacker repeat the action fee-free. The direct local analog is the protocol-fee deduction in `IntentGatewayV2.placeOrder` (and its Tron port), which uses the exact same integer-division pattern with no floor/minimum-amount guard.### Title
Protocol fee on `IntentGatewayV2.placeOrder` truncates to zero for sub-threshold amounts, letting users bypass fees entirely - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` computes the protocol fee taken from each escrowed input as `protocolFee = (originalAmount * protocolFeeBps) / 10_000`, the same Solidity-truncation pattern flagged in the BarnBridge report. There is no minimum-order-size check and no rounding-in-protocol's-favor: when `originalAmount` is small enough relative to `protocolFeeBps`, the division floors to `0`, so `reducedAmount == originalAmount` and the fee is silently skipped. A user can repeatedly place orders sized just under this threshold (or choose a low-decimal input token so the threshold corresponds to non-trivial value) and systematically avoid ever paying the protocol fee, exactly mirroring the "repeatedly call `buyTokens` for small amounts" bypass in the external report.

### Finding Description
In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`, and identically in `evm/tron/contracts/apps/IntentGatewayV2.sol`): [1](#0-0) 
```
if (protocolFeeBps > 0) {
    ...
    uint256 originalAmount = order.inputs[i].amount;
    if (originalAmount == 0) revert InvalidInput();
    uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
    uint256 reducedAmount = originalAmount - protocolFee;
    ...
    if (protocolFee > 0) emit DustCollected(token, protocolFee);
```
The only guard is `originalAmount == 0` — there is no check that `protocolFee > 0`, and no minimum order amount is enforced anywhere else in `placeOrder`. Whenever `originalAmount * protocolFeeBps < 10_000`, `protocolFee` truncates to `0` and the order proceeds with `reducedAmount == originalAmount`, i.e. the fee-reduced escrow equals the full escrow. The docs confirm current deployments run `protocolFeeBps = 5` (0.05%), meaning any input amount below `2000` base units of the input token yields zero fee. [2](#0-1) 

Because `order.inputs[i].token` is an arbitrary caller-supplied ERC20 (`address token = address(uint160(uint256(order.inputs[i].token)))`), the attacker fully controls which token — and therefore which decimals/real-world value — the truncation threshold applies to. For a low-decimal token, `2000` base units can represent significant real value, and for any token the attacker can simply repeat many sub-threshold orders to move an arbitrary aggregate amount while never paying a bps of protocol fee. This directly parallels the BarnBridge finding's core primitive: iterating a division-that-floors-to-zero to defeat a proportional fee.

### Impact Explanation
Every order placed at or below the truncation threshold escrows `100%` of the input with `0` protocol fee retained (no `DustCollected` emission, `reducedInputs[i].amount == originalAmount`). This is a direct, repeatable loss of protocol fee revenue — the exact fund-diversion category the report describes (fee bypass), reachable by any unprivileged user calling the public `placeOrder` entrypoint with no relayer, prover, or admin involvement.

### Likelihood Explanation
High for a determined actor: the check is purely on-chain, gas-bounded, and requires no privileged role — only calling `placeOrder` with a small `TokenInfo.amount` on an attacker-chosen ERC20. `protocolFeeBps` is public (`_params.protocolFeeBps` / `_destinationProtocolFees`), so the exact truncation boundary is computable off-chain before submission.

### Recommendation
Round the protocol fee up (in the protocol's favor) instead of down, e.g. `protocolFee = ceilDiv(originalAmount * protocolFeeBps, 10_000)` when `protocolFeeBps > 0`, or alternatively reject orders where the computed `protocolFee == 0` while `protocolFeeBps > 0` (mirroring the `originalAmount == 0` revert already present) to force a minimum economically-meaningful order size.

### Proof of Concept
1. Governance sets `protocolFeeBps = 5` (documented default, 0.05%).
2. Attacker calls `placeOrder` with `order.inputs[0] = {token: <arbitrary ERC20>, amount: 1999}`.
3. In the fee-computation loop: `protocolFee = (1999 * 5) / 10_000 = 0` (floor).
4. `reducedAmount = 1999 - 0 = 1999`; no `DustCollected` event fires; the full `1999` units are escrowed and offered to solvers fee-free.
5. Repeat with fresh `amount` values ≤ `1999` (or choose a token with fewer decimals so `1999` base units represent meaningful value) to move funds through the gateway indefinitely without ever contributing to `DustCollected`/protocol fee revenue — reproducing the BarnBridge "small purchase bypasses fee" primitive.

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.
```
