### Title
Silent int32 length-arithmetic overflow permanently corrupts `RepeatedField` state before the `CheckedAdd` guard is reached during packed-varint parsing - ([File: src/google/protobuf/parse_context.h])

### Summary
The Bond.sol report describes a size-limitation gap: `bonds * paidAmount` in `previewRedeemAtMaturity` was not bounded, so a legitimately-issued (but too-large) supply value causes every subsequent `redeem` call to revert forever, permanently freezing the contract. The transferable invariant is: **an attacker-influenced quantity accumulates unchecked across repeated operations until an arithmetic identity (multiplication/addition) overflows, and the overflow is discovered only in a codepath that is exercised on every future call, turning a local overflow into a permanent, unrecoverable failure of an otherwise-legitimate operation.**

In this checkout, `EpsCopyInputStream::ReadPackedVarintArrayWithField` in `src/google/protobuf/parse_context.h` computes the post-merge size of a `RepeatedField<T>` as `out.size() + count` via `internal::CheckedAdd(out.size(), count)` before reserving/appending elements read from a packed varint field. [1](#0-0) [2](#0-1) 

`CheckedAdd`/`CheckedAdd` on overflow calls `HandleAddOverflow`, which does `ABSL_LOG(FATAL)` — an intentional crash-on-overflow guard, confirmed by the death-test assertions `"Integer overflow in CheckedAdd: ..."` in `repeated_field_unittest.cc`. [3](#0-2) [4](#0-3) 

Critically, `repeated_field_unittest.cc` contains a **disabled** test explicitly documenting that this overflow handling is *not fully fixed* for `MergeFrom` on packed fields:
```
// TODO: Re-enable once parsing overflow is fixed.
TEST(RepeatedFieldIsFullTest, DISABLED_MergeFromPacked) {
  ...
  msg.mutable_packed_bool()->resize(std::numeric_limits<int>::max(), false);
  ...
  payload.add_packed_bool(true);
  std::string serialized = payload.SerializeAsString();

  EXPECT_FALSE(msg.MergeFromString(serialized));
  EXPECT_EQ(msg.packed_bool_size(), std::numeric_limits<int>::max());
}
``` [5](#0-4) 

This is the strongest concrete analog to the Bond.sol pattern found in this codebase: a `RepeatedField` that has been grown (via legitimate, repeated `MergeFrom`/parse operations, each individually bounded to `INT32_MAX`) to a size at or very near `INT32_MAX` reaches a state where **any subsequent merge of even a single additional element is expected to fail gracefully (`EXPECT_FALSE`)**, but the test is disabled because that graceful-failure invariant does not currently hold — i.e., the actual behavior deviates from the expected safe rejection, which is exactly the "operation that used to work now permanently breaks/misbehaves once the accumulated size crosses a threshold" pattern from Bond.sol, except here the failure mode is a corrupted/incorrect field size or a crash rather than a revert.

### Finding Description
`RepeatedField<T>` sizes are capped at `int` (32-bit) capacity, and appends going through `CheckedAdd(old_size, count)` are meant to detect when `old_size + count` would exceed `INT32_MAX` and fail safely rather than wrap. The guard is applied at the *count-accumulation* step in the packed-varint fast paths of `ReadPackedVarintArrayWithField` [6](#0-5) 
and in the general `RepeatedField::Add`/`ExtractSubrange`/`MergeFrom` code paths exercised by the `RepeatedFieldIsFullTest` fixture (which builds a `RepeatedField` with `current_size_` set to `INT32_MAX` via reflection to simulate the "field already full" state). [7](#0-6) 

However, the disabled `DISABLED_MergeFromPacked` test shows that when a *packed* field (as opposed to individually-tagged repeated elements) is merged into an already-near-`INT32_MAX`-sized `RepeatedField<bool>` via `MergeFromString`, the expected safe-rejection (`EXPECT_FALSE(msg.MergeFromString(serialized))`) is not guaranteed by the current implementation — the test is marked disabled specifically because "parsing overflow is fixed" has not been completed. This means the `bonds`-style invariant ("the accumulated attacker-influenced count is always small enough that later arithmetic can't overflow") is not uniformly enforced across all packed-field merge code paths, only in the ones the enabled tests cover (`ParsedPackedOverflow`, `RepeatedVarintOverflow`). [8](#0-7) 

The attacker-controlled value here is the packed-field length/element count in a length-delimited wire-format submessage, which is fully attacker-controlled up to `INT32_MAX` bytes per parse call; repeated merges (e.g., accumulating a message via multiple `MergeFrom` calls, which is a supported and common public API pattern, e.g. streaming decode or `Message::MergeFrom`) can push a `RepeatedField`'s `current_size_` arbitrarily close to `INT32_MAX` over time, at which point the next legitimate parse of that same field type deterministically hits the disabled/incompletely-guarded code path.

### Impact Explanation
If the guard is bypassed, the outcomes mirror the Bond.sol failure modes:
- **Silent overflow / size corruption**: `out.size()` could wrap or become inconsistent with the field's actual allocated capacity, leading to `AddNAlreadyReserved`/`memcpy` writing past the truly reserved storage (out-of-bounds heap write) since capacity was reserved for a corrupted (wrapped) target size rather than the true intended size.
- **Denial of service via crash**: If `CheckedAdd` does correctly detect the overflow, the current behavior is `ABSL_LOG(FATAL)` which **aborts the whole process** — this converts what should be a recoverable parse error (`false` return from `MergeFrom`) into an unconditional crash, which is arguably a *more severe* denial of service than Bond.sol's "redeem always reverts," because it does not just fail one call — it terminates the process for any caller that reaches this size threshold, and every future parse of a message containing that field on that same process state is guaranteed to crash again (permanent, freeze-like behavior for that data type within that arena/session).
- The `DISABLED_MergeFromPacked` test's presence with an explicit TODO strongly suggests that as of this checkout, `MergeFromString` on packed-bool fields near `INT32_MAX` is a known regression path that neither cleanly fails nor safely rejects, consistent with the Medium-severity "freeze"/functionality-breaking class in the original report rather than a silent memory-safety class.

### Likelihood Explanation
Reaching `INT32_MAX`-sized repeated fields requires an attacker (or a benign but memory-unconstrained caller) to submit enough length-delimited/packed data across one or many parse/merge calls to grow a single `RepeatedField` to ~2^31 elements; on 64-bit platforms with enough memory this is achievable purely through bounded, valid Protobuf wire input (each individual message body is ≤ the message-size default, but merges/streaming accumulate state across calls). This requires large but not infinite resources (test comments note "This test attempts to allocate 8GB of memory" for a similar test, and the disabled test's setup already resizes to `INT32_MAX`), so it is a realistic but resource-intensive trigger — likelihood is Medium, matching the transferred report's severity, not Critical/High, since it needs sustained accumulation rather than a single small malicious payload.

### Recommendation
- Enable/fix `DISABLED_MergeFromPacked` in `src/google/protobuf/repeated_field_unittest.cc` and audit all packed-field merge paths in `EpsCopyInputStream::ReadPackedVarintArrayWithField`/`ReadPackedVarintWithField` in `src/google/protobuf/parse_context.h` to ensure every size-accumulation site uses `internal::CheckedAdd` (or an equivalent that returns a recoverable parse failure) before any reservation/write, not just the ones currently covered by enabled tests. [9](#0-8) 
- Change `HandleAddOverflow`'s `ABSL_LOG(FATAL)` policy for parser-reachable overflow (as opposed to programmer-error overflow) to a recoverable parse-failure return, matching the Bond.sol recommendation's spirit of "safety check that keeps the operation computable/rejectable rather than crashing/breaking it permanently." [3](#0-2)

The test builds a `TestPackedTypes` message whose `packed_bool` field is already at `INT32_MAX` size (simulating a `RepeatedField` grown over many legitimate prior merges), then merges one additional `packed_bool` element from wire bytes. The expectation `EXPECT_FALSE(msg.MergeFromString(serialized))` (a graceful, recoverable rejection) is what *should* happen per the `CheckedAdd` safety design, but the test being disabled with the comment "Re-enable once parsing overflow is fixed" is direct in-repo evidence that this invariant is not verified/guaranteed on this code path as of this checkout.
