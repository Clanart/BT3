### Title
Attacker-controlled file content with embedded fake conflict-marker lines causes `reassembleResolvedFile` to mis-locate hunk boundaries, silently committing unreviewed content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The external report describes a value (fees) being derived once but then re-applied a second time downstream without reconciling the two computations, silently corrupting the final output. The closest verifiable analog in this GitHub Desktop checkout is in the Copilot conflict-resolution reassembly path: the boundary of a conflict "hunk" is computed twice, independently, by two different naive line-matching passes over the same file content — once by `extractConflictHunks` (to build the model prompt and the expected hunk count) and again by `reassembleResolvedFile` (to splice the model's resolutions back into the file). Both passes identify a hunk's terminal `>>>>>>>` marker using a bare per-line regex test with no validation that the match is the *true* git-inserted closing marker rather than attacker-supplied content that merely matches the pattern. Because the two passes can disagree on where a hunk actually ends, the resolved content that gets spliced in — and the leftover raw lines that get carried through verbatim — can silently diverge from what the reviewer/model believed they were resolving.

### Finding Description
`reassembleResolvedFile` locates each conflict block purely with three regexes: [1](#0-0) 

and determines the "closing" marker with a simple forward scan that stops at the *first* line matching `^>{7}(?:\s|$)`: [2](#0-1) 

If that check passes (`hasSeparator && closingIndex !== -1`), the function unconditionally treats everything between `i` and `closingIndex` as "the conflict block" and splices in `hunkResolutions[hunkIndex]` verbatim: [3](#0-2) 

Anything after `closingIndex` is no longer recognized as part of any hunk — it is simply copied through as ordinary content by the outer loop: [4](#0-3) 

The companion function `extractConflictHunks`, used to build the prompt and the expected hunk counts checked by `validateResolutionPaths`, performs an equivalent but independently-implemented line-by-line scan using the same fragile markers (`oursMarker`, `baseMarker`, `separatorMarker`, `theirsMarker`): [5](#0-4) [6](#0-5) 

Neither function's marker detection distinguishes a genuine git-inserted marker from a line that merely matches the pattern (e.g. a line consisting of exactly seven `>` characters) that originates from attacker-controlled branch content — such as documentation about git conflict markers, ASCII banners, or content deliberately crafted by a malicious PR/branch author. Because this content is fully attacker-controlled (a "cloned/fetched repository" scenario per the given impact criteria — the file in question is literally the merge/rebase input from a remote branch the user is merging), an attacker who controls one side of the merge can plant a line that exactly matches `^>{7}(?:\s|$)` inside their branch's version of a file that will end up in conflict with the user's own changes.

When such a file is conflicted and run through Copilot conflict resolution:
- `reassembleResolvedFile` will detect the attacker's fake `>>>>>>>`-like line as `closingIndex` for the *first* real hunk it scans, well before the genuine closing marker.
- The model's `resolvedContent` for that hunk (which was generated against the *true*, full hunk boundaries reported by `extractConflictHunks`/the prompt) gets spliced in at the wrong (earlier) location.
- Everything from the genuine hunk that lies after the fake marker — potentially including the real `=======`/`>>>>>>>` structure and unresolved "theirs"/"ours" text — is no longer recognized as conflict content by the outer loop and is copied through **verbatim** into the file that Desktop believes is "fully resolved."

This is the direct structural analog of "fees applied twice": a quantity (the hunk boundary/count) is computed independently in two places from the same untrusted input, the two computations are never reconciled against each other, and the mismatch causes a value (resolved content) to be misapplied — resulting in unreviewed, attacker-influenced content being silently baked into what the user commits.

### Impact Explanation
The write path treats `reassembleResolvedFile`'s output as the final, fully-resolved file content with no leftover conflict markers, and it is written straight to disk and staged/committed via the normal commit flow. If the attacker's crafted content causes leftover raw lines (including a genuine, un-reviewed hunk fragment or even literal conflict-marker-adjacent text) to be committed verbatim, the user unknowingly commits and potentially pushes content they never reviewed or approved — this is "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories. Depending on what the attacker plants in the surviving leftover fragment, this can range from broken/nonsensical code to attacker-chosen code being merged into the user's tree without passing through the intended review/resolution step.

### Likelihood Explanation
Exploitation only requires the attacker to control the content of one side of a merge/rebase (e.g., an external PR branch a maintainer pulls and merges, or any git remote the user fetches and merges against) — no local access, no elevated privileges, and no unusual user action beyond the normal act of resolving conflicts through the Copilot conflict-resolution feature that ships in this codebase (`3.6.0` changelog entry "Resolve merge conflicts with Copilot"). The safeguard closest to catching this — `validateResolutionPaths`'s hunk-count check — cannot help because both `extractConflictHunks` (used to compute the expected count) and `reassembleResolvedFile` (used to splice) apply the *same* naive, unvalidated marker matching, so they can agree on a wrong boundary/count while still being wrong relative to the actual git-inserted markers.

### Recommendation
Do not re-derive hunk boundaries independently in `reassembleResolvedFile`. Instead, have `extractConflictHunks` return the exact line ranges (start/separator/end indices) it used for each hunk, and have `reassembleResolvedFile` consume those same indices directly rather than re-scanning the raw text with regexes. If re-scanning cannot be avoided, harden the marker detection so it cannot be spoofed by ordinary file content — for example, require exact reconciliation between the count/positions found by both passes before committing, and fail closed (surface the file as "skipped — needs manual resolution") whenever the two independently-computed boundary sets disagree, rather than silently proceeding with mismatched splicing.

### Proof of Concept
1. Attacker pushes a branch/PR whose file `foo.ts` contains, among ordinary code, a stand-alone line consisting of exactly `>>>>>>>` followed by a space and arbitrary text (matching `^>{7}(?:\s|$)`), placed inside what will become the "ours"/"theirs" region of a future conflict — e.g. as part of a code comment demonstrating git conflict markers.
2. The victim pulls this branch and merges/rebases it against local changes to the same region of `foo.ts`, producing a real conflict block:
   ```
   <<<<<<< HEAD
   local change
   =======
   >>>>>>> spoofed line embedded in incoming content
   more of their real change
   >>>>>>> incoming-branch
   ```
3. The victim runs Copilot conflict resolution. `extractConflictHunks` sends the *whole* hunk (including the embedded spoofed line as ordinary "theirs" text) to the model, which returns a `resolvedContent` reflecting the full, true hunk.
4. `reassembleResolvedFile` scans the same raw text but stops at the *first* line matching `^>{7}(?:\s|$)` — the attacker's spoofed line — treating it as `closingIndex`. It splices the model's resolution in at that point, and the remainder of the real conflict (`more of their real change` and the genuine `>>>>>>> incoming-branch` line) is copied through verbatim by the outer loop as if it were ordinary code.
5. The resulting file, which Desktop reports as fully resolved with no conflict markers to the naive check, actually contains leftover unresolved content (in this PoC, a literal residual `>>>>>>> incoming-branch` marker line and un-reviewed text) that gets staged and committed without the user's awareness. export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
