### Title
`ReceivedOutput::read` skips the offset-to-script consistency check, admitting outputs the wallet cannot spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` couples an on-chain `TxOut`/`OutPoint` with a scalar `offset` used to derive the spendable key (`key + offset·G`). The byte-level deserializer `ReceivedOutput::read` accepts the two halves independently and never re-derives `p2tr_script_buf(self.key + offset·G)` to compare it against `output.script_pubkey`. This mirrors the Kubernetes admission-control bypass class: a crafted, patched object is admitted without the validation that would be enforced had it entered through the legitimate constructor (`Scanner::scan_transaction`, which only creates `ReceivedOutput`s whose `script_pubkey` is a registered `scripts` key).

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) is the only integrity source: it emits a `ReceivedOutput` only when `output.script_pubkey` is present in `self.scripts`, which was populated by `Scanner::new`/`register_offset` as `p2tr_script_buf(key + offset·G)` (lines 162-196). By construction, `offset` therefore satisfies `output.script_pubkey == p2tr(key + offset·G)`.

`ReceivedOutput::read` (lines 122-134) deserializes:

```rust
let offset = Secp256k1::read_F(r)?;
let output = TxOut::consensus_decode(&mut buf_r)...;
let outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

No check ties `offset` to `output.script_pubkey`. Downstream consumers assume the invariant holds. `Output::read` in processor/src/networks/bitcoin.rs:145-166 wraps `ReceivedOutput::read` with additional metadata (`kind`, `presumed_origin`, `data`) and likewise performs no consistency check. `OutputTrait::key()` (lines 112-122) computes `point(script_pubkey) - offset·G`, which for an inconsistent pair silently yields an arbitrary wrong key rather than erroring.

An attacker who supplies bytes to `ReceivedOutput::read`/`Output::read` (e.g., output records relayed between components rather than produced by a local `Scanner`) can claim a `ReceivedOutput` pairing:

1. A real on-chain UTXO whose `script_pubkey` pays to some unrelated P2TR key, with any `offset`, or
2. A UTXO paying to the wallet's script but with a wrong `offset`.

### Impact Explanation
The wallet treats the output as a spendable input it owns. When `SignableTransaction::multisig` consumes it, the signing keys are offset by `ReceivedOutput::offset`; with an inconsistent offset the threshold signature is produced for a key that does not control the input, yielding a transaction that fails Taproot script-path verification, or crediting a balance the wallet can never actually spend. This is a "funds reported received that are not spendable" condition: accounting/reporting admits the output (the admission-check bypass) while the spend path cannot satisfy it. Reachability requires only untrusted bytes into `read_F`/`read` — within the accepted input surface.

### Likelihood Explanation
Medium. Exploitation requires attacker-controlled serialized `ReceivedOutput`/`Output` records rather than scanner-produced ones. In topologies where output records cross a trust boundary (relayed scanner results, restored or injected DB/payload data), a malicious relayer can inject mismatched records without needing validator threshold participation, key material, or control of any on-chain funds. Where records are strictly locally produced by `Scanner`, the bug is latent rather than exploitable, which limits the rating.

### Recommendation
In `ReceivedOutput::read`, recompute the expected `script_pubkey` for a caller-provided base `key` (`p2tr_script_buf(key + GENERATOR·offset)`) and reject when it differs from `output.script_pubkey`. If the base key is unavailable at parse time, expose a `ReceivedOutput::verify(&self, key: &ProjectivePoint) -> bool` and require callers to check it before admitting a deserialized record into scanning/spending pipelines. Alternatively, validate in `Output::read`/`Output::key()` by comparing the derived key against the expected scanner key.

### Proof of Concept
```rust
// bitcoin-serai: attacker crafts a ReceivedOutput with an inconsistent offset
use k256::{Scalar, ProjectivePoint, elliptic_curve::group::Group};
use bitcoin_serai::{bitcoin::{TxOut, OutPoint, ScriptBuf, Amount, Txid, hashes::Hash}, wallet::{ReceivedOutput, p2tr_script_buf}};
use std::io::Write;

// Wallet key
let wallet_key = ProjectivePoint::GENERATOR * Scalar::from(7u64);
// A UTXO paying to a DIFFERENT P2TR key (e.g. the attacker's own)
let foreign_key = ProjectivePoint::GENERATOR * Scalar::from(42u64);
let foreign_script = p2tr_script_buf(foreign_key).unwrap();

// offset claims the output belongs to wallet_key + offset*G = wallet_key (offset 0)
let offset = Scalar::ZERO;

let mut buf = vec![];
buf.write_all(offset.to_bytes().as_ref()).unwrap();
buf.extend(bitcoin_serai::bitcoin::consensus::serialize(
    &TxOut { value: Amount::from_sat(100_000), script_pubkey: foreign_script },
));
buf.extend(bitcoin_serai::bitcoin::consensus::serialize(
    &OutPoint::new(Txid::all_zeros(), 0),
));

// Deserializer admits the record — no check that the script corresponds to
// wallet_key + offset*G
let ro = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
assert_eq!(ro.value(), 100_000); // reported as received and spendable
// Signing with .offset(Scalar::ZERO) produces a signature for wallet_key,
// which does not control foreign_script -> funds credited but unspendable.
```
