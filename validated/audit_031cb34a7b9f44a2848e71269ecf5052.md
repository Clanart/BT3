## Title
Same-chain intent fills mark orders complete and release full escrow using nominal output amounts, without verifying the beneficiary's actual received balance - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

## Summary
`_fillSameChain()` in `IntrinsicIntents.sol` computes `fillAmount`/`amountFilled` from the *requested* transfer amount and immediately uses that nominal value to update `_partialFills`, decide `isFullyFilled`, and release 100% of the escrowed input to the solver — all before confirming the beneficiary actually received that amount. This is the same broken-invariant class as the Union `UToken.borrow()` report: state that certifies "the transfer happened for X amount" is set from the requested amount rather than the amount actually delivered.

## Finding Description
In `_fillSameChain`, for ERC20 outputs the contract does: [1](#0-0) 

`fillAmount` is derived purely from `solverAmount`/`remaining` (the nominal, requested amount), and is written into `_partialFills[commitment][outputToken]` and used to decide `isFullyFilled` *before* the transfer executes and *without ever checking the beneficiary's actual received balance*. The `safeTransferFrom` call only reverts if the transfer call itself reverts; it does not guarantee the beneficiary balance increased by `beneficiaryTotal` (e.g. fee-on-transfer, deflationary/rebasing, or otherwise non-standard ERC20 output tokens).

Once `amountFilled == totalRequired`, the code takes the "fully filled" branch: [2](#0-1) 

which releases the *entire* remaining escrowed input to the solver via `_withdraw(body, false, true)` and permanently finalizes `_filled[commitment] = msg.sender` (set optimistically at function entry, line 57, and never rolled back on the full-fill path).

Notably, the codebase already recognizes and defends against this exact class of bug on the escrow *input* side — `placeOrder`/`_collectInputs` measure actual received balance via before/after diffs specifically to survive fee-on-transfer tokens, and this is explicitly tested: [3](#0-2) 

But the symmetric protection is absent on the *output* delivery side inside `_fillSameChain`: there is no balance-before/balance-after check on the beneficiary to confirm `beneficiaryTotal` was actually received before crediting `_partialFills` and releasing escrow.

## Impact Explanation
If an order's output asset is a non-standard ERC20 (fee-on-transfer, rebasing, or one with a broken/short transfer), any solver filling that order will have the fill accounted as fully satisfied and will collect 100% of the escrowed input, while the beneficiary receives less than `order.output.assets[i].amount`. The shortfall is a direct, permanent loss to the order's beneficiary — `_filled[commitment]` is finalized and the order can never be filled again or cancelled to recover the difference. This is an unauthorized reallocation of escrowed funds to the wrong (over-paid) party, matching the "wrong beneficiary or amount / fund loss" bounty category. No privileged actor, relayer, or prover is needed — any ordinary solver calling the public `fillOrder` entrypoint triggers it.

## Likelihood Explanation
Likelihood is bounded by the output token's transfer semantics being non-standard (fee-on-transfer/rebase/deflationary), which is a property of the order the *user* creates, not something the solver can force onto an arbitrary token. However, such tokens are common in production (many popular tokens carry transfer taxes), and the flaw fires automatically and silently on every fill of such an order — there is no attacker precondition beyond "be a solver," and the code path is on the primary, unprivileged `fillOrder` execution flow.

## Recommendation
Mirror the input-side fix already used in `placeOrder`/`_collectInputs`: measure the beneficiary's actual balance delta (or dispatcher balance delta for calldata-routed outputs) before crediting `_partialFills`/`isFullyFilled`, and use the actually-delivered amount — not the nominal `fillAmount` — to determine whether the order is fully filled and how much escrow to release.

## Proof of Concept
1. User places a same-chain order whose `output.assets[0].token` is a 1% fee-on-transfer ERC20, requiring `totalRequired = 1000` tokens, escrowing e.g. 1000 USDC as input.
2. Solver calls `fillOrder` supplying `outputs[0].amount = 1000` of the fee-on-transfer token.
3. `_fillSameChain` computes `fillAmount = 1000`, sets `_partialFills[commitment][outputToken] = 1000 == totalRequired`, and treats the order as fully filled.
4. `IERC20(token).safeTransferFrom(msg.sender, beneficiary, 1000)` executes, but due to the 1% fee the beneficiary only receives 990.
5. `_withdraw(body, false, true)` releases the *entire* escrowed 1000 USDC to the solver and `_filled[commitment]` is permanently finalized — the beneficiary is short 10 tokens with no recourse, while the solver over-collects escrow relative to what was actually delivered. [4](#0-3)

    function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                uint256 dust = solverAmount - totalRequired;
                if (order.output.call.length > 0) {
                    protocolShare = dust;
                } else {
                    protocolShare = (dust * _params.surplusShareBps) / 10_000;
                    beneficiaryShare = dust - protocolShare;
                }
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});
        }

        // Orders carrying output calldata must be filled completely in a single fill.
        // The attached call is only executed on a full fill, so a partial fill would
        // leave the intended side effect unexecuted while releasing proportional escrow.
        if (order.output.call.length > 0 && !isFullyFilled) revert PartialFillNotAllowed();

        WithdrawalRequest memory body = WithdrawalRequest({
            commitment: commitment, tokens: escrowedInputs, beneficiary: bytes32(uint256(uint160(msg.sender)))
        });
        _withdraw(body, false, isFullyFilled);

        if (isFullyFilled) {
            _execute(order, outputsLen);
            emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        } else {
            delete _filled[commitment];
            emit PartialFill({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: escrowedInputs});
        }

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            (bool sent,) = msg.sender.call{value: msgValue}("");
            if (!sent) revert InsufficientNativeToken();
        }
    }
