### Title
Cached FROST preprocess is not bound to the participant set or message, enabling deterministic nonce reuse across heterogeneous signing sessions — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class from the external report — protocol parameters changing underneath an in-flight operation so that state derived under old parameters is consumed under new ones — maps directly onto Serai's cached-preprocess signing protocol. `SigningProtocol::preprocess_internal` persists a deterministic preprocess seed keyed solely by `self.context` (e.g., `(b"DkgConfirmer", attempt)`), while the `ThresholdKeys` and the signing set are rebuilt on every call from whatever `participants`/preprocess map is passed in. The cached seed is never invalidated or rebound when those parameters differ, so the same FROST nonces (`d`, `e` derived via `seeded_preprocess` → `Commitments::new` from a `ChaCha20Rng` seeded by the cached `[u8; 32]`) are reused across invocations that carry different `participants`, different included signer sets, or different effective `msg`.

### Finding Description
In `coordinator/src/tributary/signing_protocol.rs:100-148`, `preprocess_internal`:

1. Derives `keys` fresh each call via `musig(musig_context(...), self.key.clone(), participants)` (lines 117–121).
2. Looks up `CachedPreprocesses` keyed only by `self.context` (line 123). If present, the stored seed is decrypted and passed to `AlgorithmSignMachine::from_cache` (lines 137–145).

In `crypto/frost/src/sign.rs:121-144`, `seeded_preprocess` deterministically regenerates `nonces` and `commitments` from `ChaCha20Rng::from_seed(*seed.0)`. The seed — and therefore the nonces — is identical regardless of the `participants`/`keys`/`msg` used on subsequent calls.

`share_internal` (lines 150–181) and `complete` (lines 312–327) both re-enter `preprocess_internal`, reloading the same seed, then call `machine.sign(preprocesses, msg)`. `sign` computes per-signer binding factors `rho` over the submitted preprocess set and the message (`rho_transcript` at `crypto/frost/src/sign.rs:362-371`), then produces share `s = d + e·rho_i + λ_i·x·c` where `x` is the secret share (lines 383–398).

Because `context` does not commit to the signing set or the message, an external participant who submits preprocess bytes (parsed via the untrusted `read_preprocess` path at `sign.rs:276-281`) can cause the coordinator to invoke `sign` multiple times under the same cached context with different included sets / binding factors. Each such signature share is a linear equation `s_i = d + e·rho_i + λ_i·x·c_i` sharing the same unknowns `d`, `e`, `x`. Once the number of distinct equations meets/exceeds the number of unknowns (three heterogeneous sessions suffice; fewer if `rho` collides or `msg` varies while the set is fixed), the system is solvable and the signer's secret key share `x` is recovered — exactly the consequence `sign.rs:85-87` warns about for preprocess reuse.

### Impact Explanation
Recovery of a validator's FROST secret share for the set's MuSig/Schnorrkel key. Combined with threshold-1 other shares this enables forgery of signatures authorizing `set_keys` (via `set_keys_message` at line 296) and other set-level attestations. Even short of full key recovery, reusing a seeded preprocess across differing sessions violates the FROST security precondition documented in `spec/cryptography/FROST.md:51-62`.

### Likelihood Explanation
Reachable by an unprivileged participant: preprocess bytes are attacker-controlled network input fed to `read_preprocess`, and the included set is whatever map is supplied to `share`/`complete`. The trigger requires the coordinator to produce shares under the same `context` (same `attempt`) with two-or-more distinct preprocess sets or messages — e.g., a failed consensus round retried with a different signer subset, or `share` followed by `complete` re-signing with a different map. The determinism of `CachedPreprocess` (`sign.rs:127`, `ChaCha20Rng::from_seed`) makes nonce reuse guaranteed whenever this occurs; it is not probabilistic. The residual uncertainty is how often the coordinator actually re-invokes `sign` under one context with heterogeneous sets — that call-site behavior was not fully traceable, but the cryptographic precondition violation is unconditional in the code.

### Recommendation
Bind the cached preprocess to everything that can vary: derive the `CachedPreprocesses` key (or the `ChaCha20Rng` seed) from `context || participants || msg`, or delete the cached entry once a share has been produced and refuse to serve a second `sign` under the same context. At minimum, extend the DB key in `SigningProtocolDb::CachedPreprocesses` to include a hash of the participant list and message so a parameter change can never resurrect a spent nonce.

### Proof of Concept
1. Coordinator initializes `SigningProtocol` with `context = (b"DkgConfirmer", attempt)`. `preprocess_internal` stores seed `S` in `CachedPreprocesses` and publishes preprocess `P`.
2. Attacker supplies preprocess set `A = {P, P_a1, ...}` → `share` is invoked → coordinator emits `s_1 = d + e·rho_A + λ_1·x·c_A`.
3. Attacker supplies a different set `B = {P, P_a2, ...}` (same context, different included participants or addenda) → `share`/`complete` re-enters `preprocess_internal`, `from_cache` regenerates identical `d, e` from `S` under the rebuilt `keys` → emits `s_2 = d + e·rho_B + λ_2·x·c_B`, `rho_B ≠ rho_A`.
4. A third heterogeneous session yields `s_3`. With `rho_i`, `λ_i`, `c_i` all public (computable from published preprocesses and `group_key`), solve the linear system for `x` — the validator's secret share. Alternatively, if any two sessions share `rho` but differ in `msg`, `d + e·rho` cancels directly and `x` falls out of a single subtraction.
