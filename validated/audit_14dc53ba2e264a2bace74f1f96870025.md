Webhook shop identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification` authenticates a webhook request by checking only the HMAC of the raw request body, but the gem's own documented pattern for custom webhook controllers derives the *shop identity* for that verified payload from a separate, unsigned HTTP header. Any legitimate merchant of the app can replay one of their own genuine webhook deliveries while altering that header, causing the verified webhook body to be attributed to an arbitrary shop domain of the attacker's choosing.

### Finding Description
`hmac_valid?` computes the HMAC digest over `request.raw_post` only, using the app's shared secret: [1](#0-0) 

`WebhookVerification#verify_request` uses exactly this check to gate the request, and the same module exposes a `shop_domain` helper that reads an HTTP header which is never part of the signed data: [2](#0-1) 

The gem's own documentation instructs developers to build custom webhook controllers exactly this way — verifying via the module and then trusting `shop_domain` to route/attribute the payload: [3](#0-2) 

The webhook signing secret (`ShopifyApp.configuration.secret`) is the app's single client secret shared across every installing shop — it is not per-shop. Consequently, any merchant who installs the app receives real webhook deliveries whose body+HMAC pair is valid for that shared secret regardless of which shop it originated from. Because the `X-Shopify-Shop-Domain` header is not included in the HMAC computation, an attacker-merchant can take one of their own genuine, validly-signed webhook requests and resend it to the app's endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different (victim) shop, while the body and HMAC remain untouched and therefore still pass `hmac_valid?`.

This is directly analogous to the reported `GnosisSafeZk` issue: a security-relevant identity (`refundRecipient` / `tx.origin` there, `shop_domain` here) is taken from an unauthenticated, caller-controlled channel instead of from data that is actually covered by the authorization/signature check (the multisig-authorized transaction there, the HMAC-signed body here).

### Impact Explanation
An app following the gem's documented custom-webhook pattern will process/store attacker-supplied webhook data (which the attacker fully controls, since it's their own shop's event) under a victim shop's domain. Depending on what the downstream job does with `shop_domain` (e.g., updating shop-scoped records, triggering shop-specific side effects, or associating attacker data with a victim's account), this enables cross-shop data injection/corruption and tenant confusion — a legitimate accepted-forged-signed-request, cross-shop-access vulnerability.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant of the target app (an "unrelated merchant"), which is a low bar — anyone can install a public Shopify app. No secret knowledge or privileged access is required beyond triggering one real webhook event for their own store and replaying it with a modified header.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` header (or any other non-signed header) for shop attribution. Instead, derive the shop identity from data that is part of the HMAC-signed payload (e.g., the `myshopify_domain`/shop field embedded in the webhook body, as `ShopifyAPI::Webhooks::Request` does), or bind the header value into the HMAC verification itself so any tampering invalidates the signature.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` and register/receive a real webhook (e.g. `carts/update`) — Shopify sends `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com` with body `B`.
2. Capture this request. Resend it to the app's custom webhook endpoint, keeping body `B` and the HMAC header identical, but replace the header with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb`) calls `hmac_valid?(request.raw_post)`, which recomputes HMAC over `B` with the shared secret and matches — the request is accepted.
4. The controller's action (per the documented pattern) calls `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)`, where `shop_domain` now returns `victim.myshopify.com`, causing the attacker-controlled payload `B` to be processed as if it belonged to `victim.myshopify.com`.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
