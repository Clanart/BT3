### Title
Ambiguous conflict-marker parsing in Copilot conflict resolution lets attacker-controlled file content corrupt merged output written to disk - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The bug class in the report is "a downstream action (fund transfer) trusts an upstream value (amount/token) without verifying it actually corresponds to the thing it's supposed to represent." The closest real analog in GitHub Desktop is the Copilot-assisted merge-conflict resolution feature: it extracts "conflict hunks" from a file by naive regex line-matching for `<<<<<<<`/`=======`/`>>>>>>>`, sends that extracted region to an LLM, and later splices the model's response back into the file **by hunk order, not by verified marker identity**. Nothing confirms that what was extracted/spliced actually corresponds to the real git-emitted conflict region rather than incidental attacker-controlled text that merely matches the marker pattern.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` walks a conflicted file line-by-line using bare regexes: [1](#0-0) 
It treats *any* line matching `/^<{7}(?:\s|$)/` as the start of a hunk, then greedily consumes lines until it hits whatever it interprets as the next `|||||||`/`=======`/`>>>>>>>` marker: [2](#0-1) 

Later, `reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` re-scans the *same* raw file content independently, using its own look-ahead logic to find `<<<<<<<` → `=======` → `>>>>>>>` boundaries, and splices the model's per-hunk `resolvedContent` into those boundaries **matched purely by ordinal position, not by any cross-check against the original extraction**: [3](#0-2) 

The only integrity check performed before writing to disk is `validateResolutionPaths`, which validates that the *count* of hunks per file matches, and that file paths match — it does not verify that each hunk's *content* corresponds to a genuine git-conflict boundary: [4](#0-3) 

Because git conflict markers are just plain text lines with no escaping mechanism, any file on either side of the merge that already contains lines looking like `<<<<<<< something`, `=======`, or `>>>>>>> something` (e.g. documentation about git, a test fixture, a heredoc, ASCII art, or a deliberately crafted string in source) — content fully controlled by whoever authored that branch/commit — will be mis-identified as a real conflict boundary by `extractConflictHunks`. This can cause the parser to swallow surrounding *non-conflicted* code into a phantom "hunk," which is then sent to the LLM and, following user approval, written back to disk via `writeFile` in `_applyCopilotConflictResolutions`: [5](#0-4) 

There is no verification that the "hunks" extracted, sent to the model, and spliced back actually align with the git-reported conflict, nor any diffing of the final reassembled content against the original non-conflicted portions to confirm nothing outside the true conflict region changed.

### Impact Explanation
If exploited, this results in silent corruption of what the user commits during a merge/rebase/cherry-pick — the AI-assisted feature can overwrite or delete legitimate, non-conflicted code adjacent to the fabricated "conflict" without the user realizing the diff shown/reasoning covers more (or different) content than the actual git conflict. This matches the "silent corruption of what the user commits or pushes" impact category. The attacker only needs to control content merged from a branch/fork/PR the victim pulls or merges — no local access, admin rights, or credentials required.

### Likelihood Explanation
Exploitation requires: (1) the victim to have a merge/rebase/cherry-pick that produces a real conflict against a branch containing attacker-planted marker-like text, and (2) the victim to opt into "Resolve with Copilot" and accept the result without carefully diffing every changed line. Given the review-and-accept UX of this feature, and how easy it is to plant marker-like text in a code comment, README, or test fixture, this is plausible but requires the AI feature to be enabled/used and the user to not scrutinize the diff before continuing.

### Recommendation
- After extracting hunks, verify each detected marker triple originates from a real, well-formed unnested conflict block (e.g., reject/flag files where a `<<<<<<<`/`=======`/`>>>>>>>` marker appears anywhere other than the exact boundaries git itself would emit, or where nested/duplicate markers are detected within what should be plain "ours"/"theirs" content).
- Cross-validate the content-level hunk boundaries used for extraction against the same boundaries used for reassembly (not just counts), so mismatches abort the operation with `CopilotValidationError` instead of silently proceeding.
- Before writing to disk, diff the reassembled file against the original raw content outside of confirmed conflict regions, and fail/warn if any non-conflicted lines differ.

### Proof of Concept
1. Prepare a repository where one branch's version of `notes.md` includes real merge-conflicting content plus an unrelated code block containing literal marker-like text, e.g.:
   ```
   <<<<<<< HEAD
   real ours change
   =======
   real theirs change
   >>>>>>> feature
   ...later in the same file...
   Example of a conflict marker in docs:
   <<<<<<< example
   fake ours text
   ```
   with a legitimate `=======`/`>>>>>>>`-style closing appearing further down in unrelated content.
2. Trigger a real merge that conflicts at the first block.
3. `buildConflictContext` → `extractConflictHunks` (app/src/lib/copilot-conflict-context.ts:179-279) will mis-parse the second, fabricated block as a real hunk, potentially swallowing legitimate trailing content into `theirsContent`/`oursContent`.
4. The model resolves the (incorrectly bounded) hunk; `reassembleResolvedFile` (app/src/lib/copilot-conflict-resolution.ts:549-599) splices the model's output back at the same ordinal position with no cross-check.
5. `_applyCopilotConflictResolutions` (app/src/lib/stores/app-store.ts:7233-7259) writes the corrupted result to disk and stages it for commit, all without the app detecting that content outside the genuine conflict was altered.

Note: I was not able to execute this end-to-end in a live app instance (no runtime access in this environment); the analysis above is based on static review of the parsing/reassembly/write-path code shown. If deeper confirmation is needed (e.g. actually reproducing a mis-parsed hunk end-to-end), a Devin session with file/terminal access would be needed to run the extraction and reassembly functions against a crafted fixture file.

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
}

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
