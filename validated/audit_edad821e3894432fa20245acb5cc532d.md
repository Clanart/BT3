### Title
DKG confirmation mis-removes MuSig participant entry by threshold index, crashing honest validators or mis-blaming an innocent participant - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug is a cleanup path acting on the wrong object because a `void*` was passed where a `void**` (the address of the pointer) was expected — the destructor dereferences/operates on the wrong thing. The Serai analog lives in `threshold_i_map_to_keys_and_musig_i_map` (coordinator/src/tributary/signing_protocol.rs:208-250), the helper that re-keys per-validator preprocess/share maps from *threshold* `Participant` indexes to *MuSig* `Participant` indexes (sorted position + 1). After re-keying, it removes "our own" entry with `map.remove(&our_threshold_i)` (line 247) — but `our_threshold_i` is the *pre-rekey* index, and the map is now keyed by *post-rekey* musig_i. The removal operates on the wrong key, exactly like freeing the wrong object.

### Finding Description
`spec.i(removed, key)` returns a `Range<Participant>` over *share indexes*, so a validator's `start` equals `1 + Σ(weights of earlier validators)`, not their ordinal position (coordinator/src/tributary/spec.rs:105-139). The function then sorts the threshold indexes and re-keys the map so each participant's musig_i is `raw_i + 1` — their *position* in the sorted order (signing_protocol.rs:240-245). These coincide only when every earlier validator has weight 1 and none were removed ahead of us. With weighted validators (a designed feature — `shares = u16::from(our_i.end) - u16::from(our_i.start)`, coordinator/src/main.rs:128-129, and multi-share removal logic in scanner.rs:437-444), a validator holding ≥2 shares shifts every later validator's `start` above their sorted position.

Two outcomes:
- If `our_threshold_i > number of remaining validators`, `map.remove(&our_threshold_i)` returns `None` and `.unwrap()` panics — a deterministic crash inside `DkgConfirmer::share`/`complete` (signing_protocol.rs:219, 247, 312-327) via `generated_key_pair` (coordinator/src/tributary/handle.rs:47-60).
- Otherwise, it removes a *different* signer's real preprocess/share and leaves our own dummy `vec![]` entry (inserted at line 219) in the map under our musig_i. `share_internal` then hits `read_preprocess(&mut vec![].as_slice())` on the empty entry and returns `Err(participant)` for the wrong musig index (signing_protocol.rs:161-178). In `complete`, `share_internal` is `.expect()`ed, so it panics (line 321-323); in `share`, the `Err(Participant)` propagates out of `generated_key_pair`, which is used to slash a participant — the musig index is misinterpreted as a threshold participant, so an innocent validator gets voted for `RemoveParticipantDueToDkg` and fatally slashed (handle.rs:444-455, 258-284).

### Impact Explanation
An honest validator node deterministically panics during DKG confirmation whenever any validator earlier in the ordering holds multiple shares (or after mid-attempt removals shift indexes non-trivially). In the non-panicking variant, `generated_key_pair` returns `Err(participant)` naming the wrong participant index; downstream that index is treated as a faulty DKG participant, producing `RemoveParticipantDueToDkg` votes and `fatal_slash` of an innocent validator (handle.rs:282). This is a reachable consensus-path failure producing unjustified fatal slashing and/or a liveness-killing crash — matching the accepted "incorrect verifier formula / funds reported not spendable" tier via wrongful stake destruction and DKG abort.

### Likelihood Explanation
No malicious input is required beyond normal weighted validator sets; the trigger is any set where `validators` contains a weight > 1 before us, or where `removed` parties shift indexes — a routine configuration since stake allocations map to multiple key shares (validator-sets `allocation_per_key_share`). Every honest coordinator for that set executes this path on every DKG attempt and confirmation (`DkgConfirmer::share`, `DkgConfirmer::complete`, `dkg_confirmation_nonces`, handle.rs:36-60), so the failure is deterministic and set-wide rather than probabilistic.

### Recommendation
Compute our musig index from the sorted position, not the threshold index: track `raw_i` where `sorted[raw_i].0 == our_key` (or record the position while inserting our placeholder), and `map.remove(&Participant::new(raw_i as u16 + 1).unwrap())`. Equivalently, keep `our_musig_i` captured during the `enumerate()` loop and remove by that. Add a test with weighted validators (e.g., weights [2, 1, 1]) exercising `share`/`complete` for the last validator.

### Proof of Concept
Set `validators = [(A, 2), (B, 1)]` (A weight 2, us = B). Then `spec.i(&[], B).start = Participant(3)`. `map` contains `{1: shareA}`; we insert `{3: vec![]}` (our threshold start). Sorted threshold_is `[1, 3]` → musig keys `{1: shareA, 2: vec![]}`; `participants = [A, B]`. Then `map.remove(&Participant(3))` returns `None` → `unwrap()` panics in `threshold_i_map_to_keys_and_musig_i_map` during `DkgConfirmer::share`. With `validators = [(A,1),(B,2),(C,1)]` and us = B (start=2, musig_i=2), `map.remove(&2)` removes C's real share, leaves `{1: shareA, 2: vec![]}`; `read_preprocess` on the empty entry returns `Err(Participant(2))` — mis-blaming the wrong participant or panicking in `complete`'s `.expect()`.
