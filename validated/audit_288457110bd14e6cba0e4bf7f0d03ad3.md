## Title
Fee-on-transfer / non-conforming ERC20 inputs let `placeOrder` over-credit escrow, enabling drain of other users' funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` computes the escrowed amount for each input token from the user-supplied `order.inputs[i].amount` *before* performing `safeTransferFrom()`, and never verifies how much the contract actually received. For any ERC20 that doesn't deliver the full nominal amount (fee-on-transfer, rebasing, or non-standard tokens), the gateway's internal escrow accounting (`_orders[commitment][token]`) will record more tokens than it actually holds, while withdrawals pay out strictly from this inflated bookkeeping against the contract's single shared token balance.

### Finding Description
In `placeOrder()`, the protocol fee and `reducedInputs` are derived from the caller-declared amount prior to any transfer: [1](#0-0) 

The tokens are only pulled afterward, with no balance-before/after verification: [2](#0-1) 

Escrow is credited with `reducedInputs[i].amount` — a value computed from the declared amount, not the amount actually received: [3](#0-2) 

Contrast this with the primary EVM implementation, which explicitly snapshots the contract's balance before and after `safeTransferFrom()` and uses the delta (actual received amount) for all downstream escrow/fee accounting: [4](#0-3) [5](#0-4) 

The Tron contract lacks this actual-vs-declared reconciliation entirely — it is the exact bug class from the external report (`safeTransferFrom` used without confirming receipt), applied to the intent-escrow custody path instead of an AMM pair.

Because `_orders[commitment][token]` is pure bookkeeping against a single pooled ERC20 balance held by the gateway contract, any order that inflates its own escrow credit (relative to what was truly deposited) creates a shortfall that is paid for out of tokens belonging to *other* orders/users of the same token. The withdrawal path in `IntentsBase._withdraw()` decrements and pays out strictly from this bookkeeping map without ever checking the contract's real token balance: [6](#0-5) 

### Impact Explanation
This is a fund-loss / accounting-desync vulnerability in bridge/order custody: an unprivileged user can place an order using a fee-on-transfer or non-conforming ERC20 as input, causing the contract to record escrow greater than what it actually received. When that order is later filled/cancelled/withdrawn, the payout comes from the shared token pool, silently consuming tokens deposited by unrelated users/orders of the same token. This satisfies the "stealing or loss of funds" and "false state acceptance" impact classes — no malicious relayer, prover, or admin is required, and it is fully reachable from the public `placeOrder()` entrypoint by any depositor choosing (or being tricked into accepting) a non-standard ERC20 as an order input.

### Likelihood Explanation
Likelihood is moderate: it requires the input token to be fee-on-transfer, rebasing, or otherwise non-1:1 on `transferFrom` — the same class of token explicitly acknowledged and handled in the primary EVM `IntentGatewayV2.sol` (and covered by dedicated tests `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`), but the fix was evidently not ported to the Tron contract variant, which still uses the unguarded pattern. Since token listing on the pair/order side is permissionless (any ERC20 address can be used as `order.inputs[i].token`), an attacker fully controls when this path is triggered.

### Recommendation
Mirror the balance-based reconciliation already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before `safeTransferFrom()`, compute the actually-received amount from the post-transfer balance delta, and only then compute protocol fees / `reducedInputs` / escrow credit from that actual amount — for both the direct-transfer branch and the predispatch/dispatcher-sweep branch in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 `FOT` (e.g. 1% fee) as in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` (`FeeOnTransferToken`).
2. Attacker calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and `protocolFeeBps = 0` for simplicity.
3. `reducedInputs[0].amount` is computed as `1000e18` (no fee deducted since `protocolFeeBps == 0`), and `_orders[commitment][FOT] += 1000e18` is recorded.
4. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but due to the 1% transfer fee the gateway's actual `FOT` balance only increases by `990e18`.
5. The gateway now owes `1000e18` in bookkeeping (`_orders[commitment][FOT]`) but only holds `990e18` of the real tokens contributed by this order — the missing `10e18` must come from other users' escrowed `FOT` balances in the same contract.
6. When this order (or any other legitimate `FOT` order) is later filled/cancelled via `withdraw`, the shared pool is depleted faster than it should be, and the last withdrawer(s) receive less than their rightful escrowed amount or the transfer reverts, while earlier withdrawers effectively extracted value contributed by others.
