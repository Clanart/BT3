<thinking### Title
Stale Header Chain Proof Return in `prove_till_hash` due to Missing Hash Validation - ([File: core/src/header_chain_prover.rs](core/src/header_chain_prover.rs))

### Summary
The `prove_till_hash` function in `HeaderChainProver` short-circuits and returns an existing proof if a proof at the requested height already exists in the database. However, it fails to verify that the existing proof's block hash matches the requested `block_hash`. In the event of a Bitcoin fork, this allows the function to return a stale proof from a different fork at the same height. This is a direct analog to the [FNG-15] bug where a short-circuit return of a "fresh" state without verifying the specific value leads to incorrect behavior in the caller. [1](#0-0) 

### Finding Description
The function `prove_till_hash` in `core/src/header_chain_prover.rs` is responsible for providing a header chain proof up to a specific `block_hash`. It first retrieves the height of the requested hash and then looks for the latest proven block in the database with a height less than or equal to that height using `get_latest_proven_block_info_until_height`. [2](#0-1) 

If the database contains a proven block at the exact same height as the requested `block_hash`, the function short-circuits and returns the existing receipt. [1](#0-0) 

The vulnerability lies in the fact that `latest_proven_block.0` (the hash of the proven block) is not checked against the requested `block_hash`. If Bitcoin has forked and a block on a different fork at the same height was previously proven and stored in the database, `prove_till_hash` will return the proof for the wrong fork. [3](#0-2) 

### Impact Explanation
This vulnerability allows the retrieval and use of a stale or reorged header chain proof as if it were a valid proof for the current tip.
1. **Watchtower/Verifier Malfunction**: Verifiers and Watchtowers use `get_tip_header_chain_proof` (which calls `prove_till_hash`) to generate `WorkOnlyProof`s for challenges. If they receive a proof for the wrong fork, they will generate and broadcast an invalid challenge transaction, leading to a loss of the funds used to trigger the challenge and failing to stop a malicious operator. [4](#0-3) 
2. **Bridge Safety Invariants**: The bridge relies on the header chain proof to bind the Bitcoin L1 state to the bridge logic. Providing a proof for the wrong hash at the same height breaks the binding between the proof and the canonical chain, potentially allowing an operator to use a stale chain state to satisfy bridge conditions in the `bridge_circuit`. [5](#0-4) 

### Likelihood Explanation
The likelihood is medium to high in a distributed environment where multiple actors (Aggregators, Verifiers, Operators) might be tracking different forks or where reorgs occur. Since the database persists all proofs, a proof from a discarded fork will remain in the database and trigger this short-circuit for any future request at the same height on the canonical fork. [1](#0-0) 

### Recommendation
Modify the short-circuit condition in `prove_till_hash` to verify that the hash of the proven block matches the requested `block_hash`.

```rust
if latest_proven_block.2 == height as u64 && latest_proven_block.0 == block_hash {
    // ... return existing receipt
}
``` [6](#0-5) 

### Proof of Concept
1. A Bitcoin fork occurs at height `H`. Fork A has block hash `HashA`, Fork B has block hash `HashB`.
2. The Verifier node processes Fork A and generates/saves a header chain proof for `HashA` at height `H`.
3. A reorg occurs, and Fork B becomes the canonical chain.
4. The Verifier node now calls `prove_till_hash(HashB)`.
5. `get_latest_proven_block_info_until_height` returns the info for `HashA` because it is at height `H`. [7](#0-6) 
6. `prove_till_hash` sees `latest_proven_block.height == H` and returns the receipt for `HashA`. [1](#0-0) 
7. The Verifier uses this receipt (which is for `HashA`) as if it were for `HashB`, leading to invalid downstream proofs and transactions. [8](#0-7)
