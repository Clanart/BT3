# Finding: Unrestricted `CallDispatcher.dispatch()` allows anyone to steal residual token/ETH balances left behind by Intent Gateway swap calldata

### Title
Permissionless `CallDispatcher.dispatch()` combined with incomplete sweep logic in Intent Gateway allows theft of stranded funds - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
The external report's core broken invariant is: a "flash-style" primitive moves funds into a contract to execute arbitrary calldata, relying entirely on an external, trusted wrapper to atomically settle up afterward — and when that settlement is incomplete or bypassable, anyone can intercept the temporarily-parked funds. Hyperbridge's `CallDispatcher` is exactly this primitive: it is a shared, standing contract that IntentGatewayV2 (and HyperFungibleToken) uses to temporarily hold assets and execute arbitrary swap/DeFi calldata (predispatch/postdispatch), before sweeping the result back. The sweep logic only returns the specific tokens declared in `order.inputs`/`order.output.assets`, and `CallDispatcher.dispatch()` itself has **no caller restriction**, so any leftover balance of an off-list token (or ETH) is directly and permissionlessly stealable by any unprivileged address.

### Finding Description
`CallDispatcher.dispatch()` executes an arbitrary caller-supplied `Call[]` with no access control at all: [1](#0-0) 

Any address can call `dispatch()` directly and force the `CallDispatcher` to transfer out any ERC20/ETH balance it currently holds, since the function never checks `msg.sender` against the Intent Gateway or any authorized caller.

`IntentGatewayV2`/`IntrinsicIntents`/`ExtrinsicIntents` use this single shared dispatcher (`_params.dispatcher`) as a temporary holding contract for predispatch and postdispatch calldata:

- **Predispatch**: assets are transferred to the dispatcher, arbitrary user-supplied swap calldata is executed, then only the tokens listed in `order.inputs` are swept back to the gateway: [2](#0-1) 

- **Postdispatch** (`_execute`): arbitrary output calldata runs, then only the tokens listed in `order.output.assets` (up to `outputsLen`) are swept back: [3](#0-2) 

Both sweep routines iterate strictly over the order's declared input/output token list. If the arbitrary calldata (predispatch swap route, postdispatch DeFi routing, Uniswap multi-hop, etc.) produces or leaves behind **any token not in that declared list** — e.g., an intermediate hop token, reward token, refund, or dust from a multi-step swap — that balance is never swept and remains parked in the `CallDispatcher` indefinitely. Because `dispatch()` has zero access control, any unprivileged attacker can then call `CallDispatcher.dispatch()` directly with their own `Call[]` (e.g., an ERC20 `transfer` to themselves) to drain that stranded balance. Since the dispatcher is a single shared, standing contract reused across all orders and all users of the gateway (and also used by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution), stranded value from any order accumulates in one place and is exploitable by anyone watching the dispatcher's balance — no relayer, prover, or admin compromise is required.

This is a direct structural analog to H02: the Trader-style safety wrapper (IntentGatewayV2's sweep logic) only guards the specific assets it knows about, while the underlying "flash executor" (`CallDispatcher`, playing the role of `Option.exercise`) has no independent safety validation and is reachable by anyone — exactly the risk the original report flags for uses of the flash primitive outside the intended safe wrapper.

### Impact Explanation
This directly falls under the bounty's "stealing or loss of funds" category. Any unprivileged attacker can extract ERC20/ETH balances left in the `CallDispatcher` by unswept intermediate tokens from predispatch/postdispatch execution, resulting in a wrong beneficiary (attacker instead of the protocol/dust sink) receiving funds that rightfully belong to the protocol/order participants. No malicious relayer, prover, governance actor, or leaked key is needed — the attacker only needs to observe the dispatcher's token balances and submit a plain transaction calling `dispatch()`.

### Likelihood Explanation
Likelihood is driven by how often predispatch/postdispatch calldata touches tokens outside the declared `order.inputs`/`order.output.assets` set — which is common with multi-hop swaps (e.g., a 2-hop Uniswap route through an intermediate token, or a DeFi call that returns reward tokens alongside the primary output). Every such order leaves dust that becomes a public bounty for anyone to sweep via `dispatch()`, and the surface compounds over the life of the shared dispatcher contract.

### Recommendation
- Add access control to `CallDispatcher.dispatch()` restricting the caller to a registered/authorized invoker (e.g., an immutable "owner" gateway address, or a one-time-use ephemeral dispatcher per call), rather than leaving it fully public.
- Alternatively, make the sweep logic exhaustive: instead of sweeping only tokens in the declared input/output list, snapshot the dispatcher's balance for every token actually touched by the calldata (or require the calldata to explicitly declare all tokens it may produce) and sweep all of them back unconditionally after each dispatch.
- Consider deploying an ephemeral `CallDispatcher` per order/execution (e.g., via `CREATE2`/minimal proxy, destroyed or zero-balance-guaranteed afterward) so no value can persist between unrelated transactions.

### Proof of Concept
1. A user places a predispatch order whose swap calldata routes ETH → TokenA → TokenB via a two-hop path, but `order.inputs` only lists TokenB (the final desired input). Because of slippage/partial-fill quirks in the router, or because the route intentionally leaves a small TokenA remainder, TokenA balance remains on the `CallDispatcher` after the transfer-back sweep in `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol:230-259`), since the sweep only builds `transferCalls` for `order.inputs` tokens.
2. An attacker observes `TokenA.balanceOf(dispatcher) > 0`.
3. The attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: TokenA, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — `dispatch()` has no caller check (`evm/src/utils/CallDispatcher.sol:44-62`), so this succeeds and transfers the stranded TokenA to the attacker.
4. The same pattern applies to postdispatch dust not covered by `_execute`'s sweep loop (`evm/src/apps/intentsv2/IntentsBase.sol:438-468`), which only sweeps `order.output.assets` tokens.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
