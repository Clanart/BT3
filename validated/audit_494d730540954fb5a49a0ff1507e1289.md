### Title
Silent, unprompted remote-URL rewrite driven by GitHub API metadata allows a malicious repo owner/collaborator to redirect victims' pushes and fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The reported bug class is: an admin-style entity (`quantammAdmin`) is allowed to swap out a critical dependency (`UpdateWeightRunner`) and the swap is trusted blindly, with no re-validation of authority or state, breaking the invariant that the pool's controller and rules stay consistent. The Desktop analog is `updateRemoteUrl()`, which automatically rewrites a local repository's git remote URL to whatever `clone_url` the GitHub API currently reports for that repository, with no user confirmation and no verification that the new destination is actually a location the user trusts, other than loose string matching.

Inside `updateRemoteUrl`, the decision to rewrite the remote is: [4](#0-3) 

The only guards are:
1. `protocolsMatch` – the URL scheme (https/ssh) must be the same as before.
2. `remoteUrlUnchanged` – the *previous* API `cloneURL` must still match the *current* local remote (i.e., the user hasn't manually customized the remote).
3. `!urlsMatch` – the new API `clone_url` differs from what's configured locally.

None of these validate that the **new** `clone_url` is safe to trust — they only check that the *old* value hadn't been tampered with locally. The actual authority for the new destination is the GitHub API response itself (`apiRepo.clone_url`), which reflects whatever the repository's current owner/name is on the server side. `urlMatchesRemote`/`urlsMatch` in `app/src/lib/repository-matching.ts:90-148` compare only hostname/owner/name strings, not a stable repository identity (e.g., the GitHub repository's numeric ID), so a rename or ownership transfer of the *same* underlying repository record is indistinguishable at this layer from a hostile redirect to a different destination that merely reuses the expected schema of a GitHub-shaped URL.

Once the guard passes, `gitStore.setRemoteURL` (`app/src/lib/stores/git-store.ts:1534-1543`) executes `git remote set-url` directly, silently rewriting the repository's `.git/config`: [5](#0-4) [6](#0-5) 

This mirrors the reported flaw precisely: a privileged party (in the report, `quantammAdmin`; here, whoever controls the GitHub repository's metadata — an owner, or any collaborator/org-admin permitted to rename or transfer the repo) can cause the client to unilaterally re-point a critical configuration value (`UpdateWeightRunner` address / git remote URL) that the rest of the system implicitly trusts, and the client applies the change with no re-validation of intent and no confirmation from the actual end user who will push/fetch through it.

### Impact Explanation
If a shared/organization repository is renamed or transferred by someone with sufficient GitHub-side permissions (not the Desktop user under attack — this is a distinct, less-trusted party such as an org owner, or any account with rename/transfer rights that the victim did not personally grant local trust to), every other Desktop user with that repository open and background fetching enabled will have their local `origin` remote silently rewritten to the new location the very next time a background fetch runs — with no dialog, no diff shown, no opt-out. Because `git push`/`git pull` afterward use this rewritten remote, this is a "silent corruption of what the user commits or pushes": commits can be pushed to, and future work pulled from, a destination the user never explicitly agreed to trust, without any visible indication that the remote changed. This is a background/unattended write to sensitive repository configuration triggered purely by a GitHub API object.

### Likelihood Explanation
The path is reachable via completely ordinary Desktop functionality — repository rename/transfer is a normal GitHub feature, and Desktop's periodic `BackgroundFetcher` (`app/src/lib/stores/helpers/background-fetcher.ts`) runs unattended for every open repository. No unusual user action, elevated privileges on the victim's machine, or social engineering step is needed beyond the attacker (who already has some legitimate write/admin access to the shared repository on GitHub) performing a rename/transfer. The existing checks (`protocolsMatch`, `remoteUrlUnchanged`) were designed to prevent overriding a user's manual remote customization, not to validate the legitimacy of the *new* destination, so they do not mitigate this path.

### Recommendation
Before silently applying `setRemoteURL`, require confirmation or at minimum a persistent, dismissible in-app notice when the GitHub API's reported repository owner/name has changed for a repository whose *stable identity* (e.g., the numeric GitHub repository ID cached in `GitHubRepository.dbID`) still matches, rather than only comparing scheme/owner/name strings. Track and compare the repository ID (already stored via `repositories-store.ts`'s `upsertGitHubRepository`) to distinguish a legitimate rename-of-the-same-repo from a URL that merely looks GitHub-shaped, and surface the pending remote change to the user for explicit approval rather than applying it automatically inside a background fetch cycle.

### Proof of Concept
1. User A adds `https://github.com/org/repo` in GitHub Desktop with an account that has push access; Desktop caches `gitHubRepository.cloneURL = https://github.com/org/repo`.
2. An org owner/collaborator (attacker) with rename/transfer rights on `org/repo` renames or transfers the repository to `attacker-org/repo` (GitHub preserves the internal repository ID and API `clone_url` becomes `https://github.com/attacker-org/repo`).
3. On User A's machine, the next scheduled `BackgroundFetcher` tick (`app/src/lib/stores/helpers/background-fetcher.ts`) triggers `_fetch` → `withRefreshedGitHubRepository` → `repositoryWithRefreshedGitHubRepository` (`app-store.ts:4874-4914`), which calls `api.fetchRepository(owner, name)` and receives the new `clone_url`.
4. `updateRemoteUrl` (`update-remote-url.ts:7-45`) evaluates `protocolsMatch=true`, `remoteUrlUnchanged=true` (User A never touched the remote), `urlsMatch=false` (owner differs) → condition passes → calls `gitStore.setRemoteURL('origin', 'https://github.com/attacker-org/repo')`.
5. `git remote set-url origin https://github.com/attacker-org/repo` runs silently with no dialog shown to User A.
6. User A's next `git push` sends commits to `attacker-org/repo` instead of the original repository, with no visible warning that the destination changed.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
