## Title
Wallet crash via malformed NFT metadata‑update solution in `update_metadata`/`prepend_value` - (File: `chia/wallet/nft_wallet/nft_puzzle_utils.py`)

### Summary
`update_metadata()` and `prepend_value()` in `chia/wallet/nft_wallet/nft_puzzle_utils.py` parse the `-24` (metadata‑updater) condition's argument tree and index into an attacker‑controlled `metadata` dict without validating that the expected CLVM structure or dict key actually exists, mirroring the CVE‑2024‑27913 pattern of "attempted access to a missing attribute field" from unvalidated, remotely supplied data. [1](#0-0) 

### Finding Description
`update_metadata(metadata, update_condition)` blindly walks the `update_condition` CLVM tree with `update_condition.rest().rest().first()` and then `uri.first()` / `uri.rest()`, assuming the standard `(-24 UPDATER (key . value))` shape:
```
new_metadata: dict[bytes, Any] = nft_program_to_metadata(metadata)
uri: Program = update_condition.rest().rest().first()
prepend_value(uri.first().as_python(), uri.rest(), new_metadata)
``` [2](#0-1) 

`prepend_value(key, value, metadata)` then indexes `metadata[key]` directly, with no `key in metadata` guard:
```
def prepend_value(key: bytes, value: Program, metadata: dict[bytes, Any]) -> None:
    if value != Program.to(0):
        if metadata[key] == b"":
            metadata[key] = [value.as_python()]
        else:
            metadata[key].insert(0, value.as_python())
``` [3](#0-2) 

This code path is reached from `NFTWallet.puzzle_solution_received()`, which is invoked by the wallet sync machinery when processing a parent coin spend for an NFT that a peer/counterparty has spent (an untrusted, remotely supplied `CoinSpend.solution`):
```
metadata, p2_puzzle_hash = get_metadata_and_phs(uncurried_nft, data.parent_coin_spend.solution)
``` [4](#0-3) 

Because `data.parent_coin_spend.solution` is data the wallet receives from the network (any party that ever spent an NFT coin the wallet is tracking — e.g. via an offer counterparty, DID/NFT transfer, or wallet-observed spend), an attacker can craft an NFT spend whose `-24` condition argument either:
- omits the expected `(key . value)` pair (making `uri.first()`/`uri.rest()` fail or return an unexpected atom), or
- uses a `key` that does not exist in the NFT's current `metadata` dict (`b"u"`, `b"mu"`, `b"lu"`, etc.), causing `metadata[key]` in `prepend_value` to raise `KeyError`.

Neither `update_metadata` nor `prepend_value` catches these exceptions, and the call site in `nft_wallet.py` (`puzzle_solution_received`) does not wrap the call in a try/except either. The unhandled `KeyError`/`AttributeError`/`ValueError` propagates out of the coin-state processing callback.

### Impact Explanation
This is directly analogous to CVE-2024-27913: a remotely-observable, attacker-crafted spend (an NFT parent coin spend containing a malformed `-24 METADATA_UPDATER` condition) causes an unhandled exception deep in metadata parsing on the victim wallet when it processes puzzle/coin-state data for an NFT it tracks. Depending on how the calling wallet-sync task handles the exception, this can crash or wedge the wallet's coin-state processing for that NFT, effectively halting further sync/spend processing (transaction-processing halt) without any signature or consensus violation needed — the attacker only needs to get the victim wallet to observe/process a spend of an NFT it holds interest in (e.g., by completing an offer, transferring, or updating an NFT it created together with the victim, or DID-linked NFTs).

### Likelihood Explanation
Reaching this code requires the victim wallet to already be tracking the specific NFT coin (via ownership, DID relationship, or an in-progress offer) and for an adversarial party to spend that NFT's parent coin with a solution whose `-24` argument doesn't match the standard `(key . value)` shape or references an unrecognized key. This is a normal wallet action a counterparty controls (e.g., during a trade, DID update, or malicious peer serving a crafted `parent_coin_spend`), making it moderately likely and requiring no special privileges beyond a standard NFT-related interaction.

### Recommendation
- In `prepend_value()`, check `key in metadata` before indexing, and handle unknown keys by inserting a new list rather than raising `KeyError`.
- In `update_metadata()`, wrap the CLVM extraction (`update_condition.rest().rest().first()`, `uri.first()`, `uri.rest()`) with defensive checks or a `try/except (ValueError, EvalError)` that raises a well-typed `ValueError`/`ConsensusError` instead of an unhandled builtin exception.
- Ensure `NFTWallet.puzzle_solution_received()` (and any other caller of `get_metadata_and_phs`/`update_metadata`) catches parsing exceptions from untrusted `parent_coin_spend.solution` data and treats the coin as "not ours"/skip, rather than letting the exception propagate out of the sync callback.

### Proof of Concept
Not directly executed in this analysis (index-only investigation); the described crash path is derived from static review of:
- `update_metadata`/`prepend_value` at [1](#0-0) 
- the untrusted call site `data.parent_coin_spend.solution` at [4](#0-3) 

To confirm exploitability, a Devin session with repo/test access should construct an NFT coin spend whose solution's `-24 METADATA_UPDATER` argument uses a metadata key not present in the target NFT's current metadata (or omits the `(key . value)` pair entirely), feed it as `data.parent_coin_spend.solution` in a `puzzle_solution_received` unit test, and verify whether an unhandled `KeyError`/`ValueError` escapes the wallet's coin-state processing.
