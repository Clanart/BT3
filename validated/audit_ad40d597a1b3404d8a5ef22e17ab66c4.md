## Finding: `resolveWithin` path-containment guard is bypassed by sibling directories sharing a name prefix

The external `DebtKernel` report's core lesson is the same failure mode found here: a security guard (`EXTERNAL_QUERY_GAS_LIMIT` / here, a "must resolve within root" check) *looks* protective but is implemented with an off-by-boundary flaw that lets the guarded value slip past it. In Desktop, the analogous guard is `resolveWithin()` in [1](#0-0) , which is used to sandbox an attacker-influenced `filepath` coming from a "Open Repository from URL" deep link before it's handed to `shell.showItemInFolder`.

### Title
Directory-containment check `startsWith(realRoot)` in `resolveWithin` allows deep-link `filepath` to escape the repository into sibling directories - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin` is meant to guarantee that a resolved path is at or below a given root directory before it is used. The final check is a plain string prefix test, `realResolved.startsWith(realRoot)` [2](#0-1) , with no path-separator boundary enforced after the prefix. Any directory whose name textually starts with the root directory's full path (e.g. `myrepo-secrets` next to `myrepo`) will pass the check even though it is not contained within the root at all.

### Finding Description
`openRepositoryFromUrl` in the dispatcher handles the `x-github-client://openRepo/...` deep link action. After resolving/opening the target repository, it takes the attacker-supplied `filepath` query parameter and:
1. Rejects it only if it is an absolute path [3](#0-2) .
2. Otherwise calls `resolveWithin(repository.path, filepath)` and, if non-null, passes the result straight to `shell.showItemInFolder(resolved)` [4](#0-3) .

`resolveWithin` (`_resolveWithin`) computes `resolved = resolve(normalizedRoot, normalizedRelative)`; a relative `filepath` containing `../` sequences is perfectly legal input (only absolute paths are rejected upstream), so `resolved` can legitimately point outside `repository.path` entirely, e.g. to a sibling folder. The function then calls `realpath()` on both root and resolved path and checks containment with `realResolved.startsWith(realRoot)` [2](#0-1) . Because this is a bare string comparison with no trailing separator, `"/Users/victim/Documents/GitHub/myrepo-secrets"` incorrectly satisfies `startsWith("/Users/victim/Documents/GitHub/myrepo")`. The traversal-only guard in `parse-app-url.ts` does not help either — it only validates `branch`, not `filepath` [5](#0-4) .

This mirrors the DebtKernel report's structure exactly: a limit/guard exists (`EXTERNAL_QUERY_GAS_LIMIT` there, `startsWith(realRoot)` here) that was assumed sufficient, but the attacker-controlled input (arbitrary token gas cost / attacker-crafted `filepath`) can be shaped to slip past the boundary the guard was supposed to enforce.

### Impact Explanation
A malicious website/email can embed a `x-github-client://openRepo/<repo-url>?filepath=../<victim-sibling-dir>/<file>` link. If the user has any locally cloned/organized folder next to the target repository whose name shares the repository directory's name as a prefix (a very common pattern — `project` / `project-old`, `project-backup`, `project-private`, `app` / `app-internal`, or multiple forks cloned side by side), clicking the link causes Desktop to reveal/open that out-of-repo file or directory via `shell.showItemInFolder`, i.e., file access outside the intended repository root triggered purely by an attacker-controlled link — squarely in the "link/deep link" + "read outside the repo" valid-impact category.

### Likelihood Explanation
Requires: (1) the victim to click a crafted `x-github-client://` link (default protocol handler registered by Desktop, see `possibleProtocols` in `main.ts` [6](#0-5) ), and (2) a qualifying sibling directory name to exist locally. Given how commonly developers keep `repo`, `repo-old`, `repo2`, `repo-fork`, etc. under the same parent folder, condition (2) is plausible without any additional local/privileged access from the attacker. No malware, no leaked credentials, and no unnatural steps beyond "click a link" are required.

### Recommendation
Fix the containment check in `_resolveWithin` to enforce a path-separator boundary, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Apply this consistently to `resolveWithin`, `resolveWithinPosix`, and `resolveWithinWin32`, and add regression tests for sibling-directory-name-prefix cases (this class of bug is exactly the kind that unit tests like the existing `clone-path-safety-test.ts` were written to catch for the clone-path issue, but no equivalent boundary test exists for `resolveWithin`, based on what was inspected).

### Proof of Concept
1. Victim has `~/Documents/GitHub/project` (a Desktop-tracked repo) and `~/Documents/GitHub/project-secrets/passwords.txt` on disk.
2. Attacker sends: `x-github-client://openRepo/https://github.com/owner/project?filepath=..%2Fproject-secrets%2Fpasswords.txt`
3. `parseAppURL` accepts this filepath unmodified (no traversal check applied to `filepath`, only to `branch`) [5](#0-4) .
4. `openRepositoryFromUrl` finds/opens `project`, `isAbsolute(filepath)` is `false` so it proceeds, and calls `resolveWithin("~/Documents/GitHub/project", "../project-secrets/passwords.txt")` [7](#0-6) .
5. Inside `_resolveWithin`, `resolved` = `~/Documents/GitHub/project-secrets/passwords.txt`; `realResolved.startsWith(realRoot)` is `true` because the string `"...GitHub/project-secrets/passwords.txt"` starts with `"...GitHub/project"` [2](#0-1) .
6. `shell.showItemInFolder` opens/reveals `passwords.txt`, outside of `project`'s directory tree, solely from a link click.

**Note on confidence:** I could not execute the test suite here to confirm whether `app/test/unit/path-test.ts` already covers this exact sibling-prefix boundary case (I only confirmed the test file exists and exercises `resolveWithin`, not its specific assertions). If that suite already asserts separator-boundary behavior, this would indicate the flaw is already covered/mitigated elsewhere and the report should be treated as unconfirmed; I recommend verifying `app/test/unit/path-test.ts` directly before treating this as unpatched.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
