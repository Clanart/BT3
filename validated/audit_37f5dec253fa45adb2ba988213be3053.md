### Title
DID `transfer_did()` retains stale recovery/backup-DID authority after ownership change - ([File: chia/wallet/did_wallet/did_wallet.py])

### Summary
`DIDWallet.transfer_did()` moves ownership of a DID singleton to a new p2 puzzle hash, but it explicitly re-uses the current `backup_ids` (the recovery list) and `num_of_backup_ids_needed` when constructing the new owner's inner puzzle, rather than clearing them. This is the same bug class as the reported `CouncilMember.removeFromOffice()` issue: a stale "approval"/authority (there, an ERC721 `approve()` grant; here, the DID's recovery/backup-ID list) survives a change of ownership and continues to grant a third party control-equivalent rights over the asset after transfer.

### Finding Description
`transfer_did()` at [1](#0-0)  builds the new DID inner puzzle hash using the *old* `self.did_info.backup_ids` and `self.did_info.num_of_backup_ids_needed`: [2](#0-1) 

The companion helper `get_innerpuz_for_new_innerhash()`, used when generating the inner puzzle for a new owner key, has an explicit code comment acknowledging this design choice: "the recovery list will be kept. In a selling case, the seller should clean the recovery list then transfer to the new owner." [3](#0-2) 

The DID puzzle's recovery mechanism (`recovery_list`/`num_of_backup_ids_needed`, curried into `DID_INNERPUZ_MOD`) allows the addresses on the backup list to co-sign a "recovery" spend that changes the DID's owner p2 puzzle without the current owner's private key, once the required threshold of backup-DID attestations is met — this is the on-chain analogue of the ERC721 `approve()` mapping: a delegated authority independent from the actual holder's key. `did_wallet_puzzles.uncurry_innerpuz`/`create_innerpuz` show these fields are curried directly into the spendable puzzle: [4](#0-3) 

Because `transfer_did()` (and `create_new_did_wallet_from_coin_spend`, which likewise defaults to keeping a discovered recovery list, logging only a warning when the hash marks it deprecated: [5](#0-4) ) does not force clearing of `backup_ids`/`num_of_backup_ids_needed` on transfer, any backup DIDs that were configured by the *previous* owner remain capable of triggering the DID's recovery path against the *new* owner's DID coin — i.e., stale approval persists across an ownership change, exactly mirroring the reported bug class where `approve()`'s grant survives `removeFromOffice()`'s NFT transfer.

Note: The RPC-facing `DIDTransferDID` request type forces `with_recovery_info=True` unconditionally (raising if `False` is passed) at [6](#0-5) , meaning there is currently no supported RPC/CLI path for a normal user to opt out of preserving the recovery list at transfer time — the mitigation ("the seller should clean the recovery list then transfer") described in the code comment is not enforceable/automatic and depends entirely on the transferring party manually resetting recovery info via a separate call before transferring.

### Impact Explanation
If a DID owner sells/transfers a DID (used for NFT ownership, offers, VC/CR-CAT authorization, or DID-gated wallet features) without manually resetting its recovery list first, the old owner's chosen backup-DID holders retain the ability to force a recovery-style ownership change on the DID coin now held by the new owner, without the new owner's consent or private key. This is an unauthorized/coerced coin-authority takeover of an asset the buyer believes they fully own — a concrete unsigned/unauthorized coin movement of a valued, transferable singleton asset.

### Likelihood Explanation
Likelihood depends on whether: (1) the transferring party had actually set a non-empty recovery list at some point, and (2) they transfer without resetting it. Given `DIDTransferDID` requires `with_recovery_info=True` and there is no automatic reset baked into `transfer_did()`, any casual sale/transfer of a DID with a previously configured recovery list is exposed by default unless the seller separately and correctly resets recovery info first — an easy step to omit since it is not enforced or defaulted by the transfer path.

### Recommendation
Force clearing of `backup_ids`/`num_of_backup_ids_needed` (or require the caller to explicitly confirm they intend to preserve recovery info) inside `transfer_did()`/`get_innerpuz_for_new_innerhash()` by default, rather than relying on the seller to manually reset recovery settings in a separate step before transferring. At minimum, the wallet RPC/CLI should surface a strong warning or require an explicit flag to preserve a non-empty recovery list across a DID transfer.

### Proof of Concept
1. Owner A creates a DID wallet with `num_of_backup_ids_needed >= 1` and a non-empty `backup_ids` list (backup DID `B`).
2. Owner A sells/transfers the DID to Owner C via `transfer_did()`/`DIDTransferDID` RPC without first resetting the recovery list.
3. Because `transfer_did()` re-curries `self.did_info.backup_ids` and `self.did_info.num_of_backup_ids_needed` into the new inner puzzle ( [2](#0-1) ), backup DID `B` retains the puzzle-level authority to co-sign a recovery spend on the now-Owner-C-controlled DID coin.
4. Backup DID `B` (still controlled by Owner A or a party Owner A configured) initiates a recovery spend against the DID coin now owned by C, changing its p2 puzzle hash without C's consent — demonstrating unauthorized coin-authority transfer analogous to the retained ERC721 `approve()` grant in the source report.

def uncurry_innerpuz(puzzle: Program) -> tuple[Program, Program, Program, Program, Program] | None:
    """
    Uncurry a DID inner puzzle
    :param puzzle: DID puzzle
    :return: Curried parameters
    """
    r = puzzle.uncurry()
    if r is None:
        return r
    inner_f, args = r
    if not is_did_innerpuz(inner_f):
        return None

    p2_puzzle, id_list, num_of_backup_ids_needed, singleton_struct, metadata = list(args.as_iter())
    return p2_puzzle, id_list, num_of_backup_ids_needed, singleton_struct, metadata
