## Title
Stale line-selection indices applied to a freshly re-fetched diff cause silent partial-commit content corruption - (File: `app/src/lib/git/apply.ts`)

### Summary
`DistributionEvent` in the smart-contract report stored a scale-dependent value (`totalTournamentEarnings`/decimals) that was later applied against a different scale (new token decimals), silently producing an incorrect distributed amount. The GitHub Desktop analog is `applyPatchToIndex`, which reapplies a `WorkingDirectoryFileChange.selection` — a set of line indices computed against the diff that was rendered to the user at selection time — against a **newly, independently fetched** diff of the same file at commit time. If the file's content on disk changes between when the user made their partial-line selection and when `stageFiles`/`applyPatchToIndex` runs, the selection indices no longer correspond to the same lines, and `git apply` will silently stage/commit a patch that does not match what the user actually selected in the UI.

### Finding Description
`DiffSelection` is a bitmap/range keyed purely on `absoluteIndex = hunk.unifiedDiffStart + lineIndex` — an index into a specific diff's flattened hunk/line layout [1](#0-0) . This selection is attached to a `WorkingDirectoryFileChange` and persisted in `changesState.workingDirectory` while the user reviews the Changes view and decides which lines to commit.

When the user finally commits, `_commitIncludedChanges` simply reads whatever files/selections are already cached in `repositoryStateCache` and passes them straight to `createCommit` [2](#0-1) . It performs no diff refresh or selection revalidation immediately before staging.

Down in the git layer, `stageFiles` routes any file with a partial selection to `applyPatchToIndex` [3](#0-2) . Crucially, `applyPatchToIndex` does **not** reuse the diff the selection was built against — it calls `getWorkingDirectoryDiff(repository, file)` again, fetching a brand-new diff from git at commit time, and then feeds the (old) `file.selection` straight into `formatPatch(file, diff)` against that new diff [4](#0-3) . `formatPatch` blindly trusts `absoluteIndex` positions from the old selection against the new hunk/line layout [5](#0-4) , then applies the result with `git apply --cached --unidiff-zero --whitespace=nowarn`, a lenient invocation that is likely to succeed even though the mapping is wrong [6](#0-5) .

The only place selection indices are ever revalidated against a fresh diff is `updateChangesWorkingDirectoryDiff`, and that logic explicitly only recomputes `selectableLines` for the **single currently-displayed file** in reaction to specific UI events (file selection change, diff reload) [7](#0-6) . The code comment itself acknowledges the limitation: *"The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines"* [8](#0-7) . There is no equivalent revalidation for files that are not currently displayed but still carry a partial selection, nor any revalidation performed by `_commitIncludedChanges`/`applyPatchToIndex` right before staging.

### Impact Explanation
A cloned/checked-out repository can legitimately contain tooling that rewrites tracked files after checkout or while the app is open (build/watch scripts, formatters, git smudge/clean filters, LFS filters, or a pre-commit/post-checkout hook the repo ships) — content fully controlled by whoever authored the repository. If such a process alters a file's line layout (reflow, added/removed lines) between the moment the user reviews the diff and selects specific lines to commit and the moment they click "Commit", the stale `absoluteIndex` selection is silently reapplied to the new diff. The result is a patch built from a different set of physical lines than the ones the user visually selected/deselected — i.e., silent corruption of what actually gets committed and later pushed, with no error surfaced to the user (`git apply --whitespace=nowarn --unidiff-zero` is deliberately lenient and prone to succeeding on a slightly different context). This falls squarely under "silent corruption of what the user commits or pushes."

### Likelihood Explanation
This requires a repository whose contents (scripts/hooks/filters) can modify a tracked file's contents during the window between diff-render and commit — a scenario entirely under the control of a malicious repository author and requiring no local/physical access, no admin rights, and no prior host compromise. It does need a race window (the file changing after the user staged a partial selection but before commit), which is a timing dependency, so likelihood is moderate rather than trivially reproducible on every commit — but it is deterministic and easily triggerable by a repository that runs a watch/build task or filter on save/checkout.

### Recommendation
Before staging, `applyPatchToIndex` (or its caller `stageFiles`/`_commitIncludedChanges`) should re-derive/re-validate the selection against the diff it is about to apply — not reuse indices computed from a possibly stale diff. At minimum, compare a content hash/fingerprint of the diff used to build the selection against the diff fetched at commit time, and if they differ, refuse to auto-apply the stale selection (re-prompt the user or fall back to reselecting lines), mirroring the `selectableLines` invalidation already done for the actively displayed file in `updateChangesWorkingDirectoryDiff`, but applied uniformly to every file about to be committed, not just the one currently shown in the UI.

### Proof of Concept
1. Clone a malicious repository that ships a background script/hook (e.g., a `postinstall`/watch task, or a `.gitattributes` clean/smudge filter) which periodically rewrites a tracked file's content (inserting/removing lines) without changing the file being "closed" or triggering a full Desktop refresh cycle for a non-displayed file.
2. In GitHub Desktop, open the file in the Changes view, and make a partial line selection (e.g., select only the first hunk to commit).
3. Switch focus away from that file (or simply wait) while the malicious background process alters the file's line layout on disk.
4. Click Commit. `_commitIncludedChanges` uses the cached `file.selection` (indices computed from the old diff) [2](#0-1) ; `applyPatchToIndex` fetches a fresh diff and applies those stale indices to it [4](#0-3) .
5. Inspect the resulting commit: it contains a different set of lines than what was visually checked/unchecked by the user in the UI, with no warning or error shown.

Note: I was unable to fully trace the exact merge logic in `app/src/models/status.ts` / `app/src/lib/stores/updates/changes-state.ts` that decides whether a non-displayed file's `DiffSelection` object is carried over unchanged across a background repository refresh (vs. being reset), due to index size limits on file contents in this environment. Confirming the precise window/trigger conditions (e.g., whether a routine background status poll resets selections) would benefit from a full Devin session with direct file access.
