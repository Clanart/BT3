### Title
`((warning_count++))` under `set -e` silently aborts validation before the `tools:` field is displayed, hiding malicious tool grants from review - ([File: plugins/plugin-dev/skills/agent-development/scripts/validate-agent.sh])

### Summary
The script runs with `set -euo pipefail` [1](#0-0)  and increments `warning_count`/`error_count` via bare post-increment arithmetic commands like `((warning_count++))` [2](#0-1) . In bash, `((var++))` evaluates to the pre-increment value, so the very first increment (`0`→`1`) evaluates to `0`, which bash treats as a failing command (exit status 1); combined with `set -e` this kills the script immediately. Because description-related warnings (line 100-118) are checked before the `model`, `color`, and especially the `tools:` field disclosure block (lines 161-168), a short/malformed description silently terminates the script before the `tools:` value is ever printed for review.

### Finding Description
The validator extracts `DESCRIPTION` and checks its length: if `desc_length -lt 10`, it prints a warning and executes `((warning_count++))` [2](#0-1) . Since `warning_count` starts at `0` [3](#0-2) , this is a classic bash `set -e` pitfall: the arithmetic expression `warning_count++` evaluates to `0` (the value *before* increment), and `((0))` is a "failing" arithmetic command in bash, giving exit status `1`. With `set -euo pipefail` active, this untested command failure causes the whole script to exit immediately — well before execution reaches the `tools:` field extraction/echo at lines 161-168, and well before the final summary block at lines 205-217 that would normally report `Validation failed/passed with N warning(s)`.

An attacker who controls `agent.md` (e.g., a plugin/agent file submitted for review) can trivially trigger this by supplying any of the first-encountered warning conditions — most simply, a `description:` under 10 characters — while also including an over-broad or dangerous `tools:` grant (e.g., `tools: Bash(*)`, wildcard/all-tool access). A reviewer who runs `validate-agent.sh agent.md` expecting it to surface field-level issues (including the `tools:` grant) instead sees the script die silently after printing only the short-description warning, never reaching the `✅ tools: ...` / `💡 tools: not specified` line that a human reviewer would use to spot excessive tool access.

This is not specific to the description warning alone — the same bug applies to every `((warning_count++))` and `((error_count++))` call in the file whenever the counter transitions from 0 to 1 [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) , meaning the very first issue found in any agent.md unconditionally aborts the review process before later checks (including the security-relevant `tools:` disclosure) execute.

### Impact Explanation
This is a review-tooling trust-boundary bypass: a reviewer relying on `validate-agent.sh` to flag suspicious agent definitions (particularly wildcard/dangerous `tools:` grants) will not see that field at all when the file also happens to contain any earlier-ordered warning condition, and no error message indicates *why* the script stopped early. This can let a malicious plugin/agent file with an over-broad `tools:` grant (e.g., unrestricted `Bash`) pass through human review undetected, since the reviewer sees an abrupt, silent stop rather than a clear failure or the expected summary.

### Likelihood Explanation
Highly likely/trivial to trigger: any agent.md with a `description:` under 10 characters (or any other first-encountered warning condition earlier in the script than the `tools:` check) reproduces this deterministically on any standard bash without `errexit`-suppressing wrappers. No special privileges are needed — only the ability to submit/author an `agent.md` file for validation, which is the exact normal workflow this script is designed for.

### Recommendation
Replace all `((counter++))` / `((counter--))` style increments with forms that don't produce a zero-valued (falsy) arithmetic result, e.g. use `: $((counter++))`, `counter=$((counter + 1))`, or `((counter += 1)) || true`. Alternatively, temporarily disable `set -e` around these increments, or restructure counters to start at a non-zero sentinel. Add a regression test that runs the validator against an agent.md with a short description and a wildcard `tools:` field and asserts the script reaches the final summary and prints the `tools:` line.

### Proof of Concept
Integration test (bash):
```bash
cat > /tmp/agent.md <<'EOF'
---
name: test-agent
description: short
model: sonnet
color: blue
tools: Bash(*)
---
You are a test agent used for security testing purposes.
EOF

./validate-agent.sh /tmp/agent.md
echo "exit=$?"
```
Expected (buggy) behavior: script prints the "description too short" warning line and then exits immediately (exit status 1) without ever printing `✅ tools: Bash(*)` or the final `━━━` summary/`Validation passed/failed` line — confirming the `tools:` field was never surfaced for review. Expected (fixed) behavior: script continues past the description warning, prints the `tools:` field value, and reaches the final summary with the correct warning count.
