### Title
Gateway-instance reassignment via `NewDeployment` permanently orphans in-flight cross-chain settlements - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2` authenticates inbound `RedeemEscrow`/`RefundEscrow` settlement messages by comparing the sender address embedded in the ISMP request (`request.from`) against the currently registered gateway instance for that source chain, stored in `_instances[stateMachineId]` [1](#0-0) . This mapping can be updated at any time via a `NewDeployment` governance message processed in `onAccept` [2](#0-1) . If the registered instance address for a chain changes while an order's settlement message (dispatched from the *old* instance address) is still in flight, `_authenticate` will permanently reject it because `request.from` (old address) no longer matches `_instance(request.source)` (new address) [3](#0-2) .

### Finding Description
This is a direct structural analog of the SecondSwap `VestingManager.setMarketplace` bug: a single admin-controlled pointer (`marketplace` there, `_instances[chainId]` here) is repointed to a new contract instance, and previously created cross-contract state (listings there, escrowed orders here) that was authorized against the *old* pointer becomes permanently unreachable through the new pointer.

Flow:
1. User places a cross-chain order on chain A (source), escrowing input tokens under `_orders[commitment][token]` [4](#0-3) .
2. A solver fills the order on chain B (destination) via `_fillCrossChain`, delivers output tokens to the beneficiary, and dispatches a `RedeemEscrow` POST request back to chain A naming `_instance(order.source)` as the target contract identity [5](#0-4) . Chain B also marks the order filled locally.
3. Before this message is relayed and finalized on chain A, Hyperbridge governance issues a legitimate `NewDeployment` message updating `_instances[keccak256(chainB)]` on chain A to a newly redeployed gateway address on chain B (e.g. as part of a routine contract migration) [2](#0-1) .
4. When the pending `RedeemEscrow` message finally arrives at chain A's `onAccept`, `_authenticate` compares `request.from` (the *old*, now-unregistered gateway address of chain B that actually filled the order) against `_instance(request.source)` (the *new* address) — the values no longer match, so it reverts with `Unauthorized()` on every future relay attempt [3](#0-2) [6](#0-5) .
5. The escrow on chain A remains locked (`_orders[commitment][token]` still nonzero, `_filled[commitment]` never set), while chain B has already recorded the order as filled (`_filled[commitment] = solver`) [7](#0-6) . The user cannot use the source-side cancellation GET-proof route either, because that route reverts with `Filled()` once the destination shows the order as filled [8](#0-7) . The solver, who already delivered output tokens on chain B, can never redeem the escrowed input tokens on chain A — permanent fund lock with no recovery path, exactly mirroring the SecondSwap pattern where the vested listing becomes stuck once the pointer changes.

### Impact Explanation
This is a genuine, permanent loss/lock of escrowed bridge funds reachable purely through the intended, non-malicious `NewDeployment` governance flow combined with normal user/solver activity — no malicious relayer, prover, or admin is required, only ordinary redeployment operations racing with in-flight settlement messages. Funds already delivered by the solver on the destination chain become unrecoverable, and the user's escrow becomes permanently unredeemable via any code path, since the settlement authentication is now a one-way, un-reversible identity gate with no allowance for previously-valid, in-flight senders.

### Likelihood Explanation
Likelihood is moderate: it requires a legitimate protocol maintenance action (adding/replacing a `Deployment` for a chain via `NewDeployment`) to occur while at least one cross-chain order settlement message is in flight for that chain — a realistic operational scenario for any long-lived cross-chain protocol that redeploys or migrates gateway contracts, especially given ISMP's relay + challenge-period delay window, which widens the race window considerably.

### Recommendation
Do not treat `_instances[chainId]` reassignment as a destructive overwrite. Options: (1) maintain a history/set of previously valid instance addresses per chain and accept messages authenticated against any of them for a grace period, or (2) require in-flight settlement messages to drain/settle (or provide an explicit fallback claim path keyed by commitment rather than by currently-registered instance address) before a chain's instance mapping may be updated, or (3) add a dedicated recovery function allowing the rightful beneficiary (solver/user) to redeem an escrow once `_filled` proof exists but a live authentication mismatch is detected, bypassing the stale `_instance` lookup.

### Proof of Concept
1. Deploy `IntentGatewayV2` on chain A and chain B, register `_instances[B] = gatewayB_v1` on chain A via `NewDeployment`.
2. User places a cross-chain order on chain A with destination B; tokens escrowed in `_orders[commitment]`.
3. Solver fills the order on `gatewayB_v1`, which sets `_filled[commitment] = solver` on B and dispatches `RedeemEscrow` with `from = gatewayB_v1`.
4. Before the message reaches chain A, governance dispatches `NewDeployment` updating `_instances[B] = gatewayB_v2` on chain A.
5. The `RedeemEscrow` message is delivered to chain A's `onAccept`; `_authenticate` computes `_instance(order.source) == gatewayB_v2 != gatewayB_v1 == request.from` → reverts `Unauthorized()` every time it's retried.
6. Attempt `cancelOrder` (source route) — `onGetResponse` sees `_filled[commitment]` non-empty on B and reverts `Filled()`.
7. Escrowed tokens are permanently stuck: neither the solver (owed the escrow) nor the user (already lost the escrow to a delivered fill) can retrieve them.
