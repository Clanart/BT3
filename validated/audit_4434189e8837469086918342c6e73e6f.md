### Title
Deserialization trusts attacker-supplied verification shares: `ThresholdKeys::read` never checks share consistency, enabling a rogue group key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a fully attacker-controlled `secret_share` scalar and `verification_shares` map, then `ThresholdKeys::new` derives `group_key` purely from `verification_shares[1..=t]` without ever verifying that `generator() * secret_share == verification_shares[i]` or that the shares belong to a consistent polynomial. This is the same bug class as the SAM `create()` finding: security-critical parameters (the group key / bonding-curve parameters) are set from untrusted, unvalidated external input rather than from a trusted, locally-enforced source. A party that feeds crafted bytes into `ThresholdKeys::read` (e.g., during key recovery/resharing, where serialized `ThresholdKeys` are the untrusted input) can make the reconstructed keys point to a group key whose discrete logarithm they know.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, an interpolation method, a raw `secret_share` via `C::read_F`, and `n` verification-share points via `C::read_G`, then calls `ThresholdKeys::new` [1](#0-0) .

`ThresholdKeys::new` validates only structural properties: the number of verification shares equals `n`, participant indexes are `<= n`, and `Constant` interpolation requires `t == n` [2](#0-1) . It then computes the group key as an interpolation over `verification_shares[1..=t]` [3](#0-2) . Nowhere is it checked that `secret_share` is consistent with `verification_shares[i]`, nor that the verification shares lie on a common polynomial. The honest generation path (`KeyMachine::calculate_share` → `ThresholdKeys::new`) guarantees this consistency internally [4](#0-3) , but the deserialization path — the one reachable via untrusted bytes — bypasses it entirely.

An attacker supplies serialized keys where `verification_shares[i] = a_i * G` for known `a_i` and `secret_share` is arbitrary (e.g., `1`). All structural checks pass. `group_key()` then returns `A * G` where `A = sum(lambda_i * a_i)` is known to the attacker [5](#0-4) .

### Impact Explanation
Any downstream consumer that derives a receive address or verifies signatures against `group_key()` — e.g., a Bitcoin scanner deriving the multisig's Taproot output key after a recovery/resharing flow — will credit funds to a key controlled solely by the attacker. Conversely, if `view()` is used to sign, the interpolated `secret_share` is inconsistent with the attacker-set verification shares, producing invalid shares and silently corrupting the signing set — a mismatch only an attacker-controlled input could create. Either way, the group loses exclusive control: funds reported as received under the reconstructed group key are spendable by the attacker alone.

### Likelihood Explanation
`ThresholdKeys::read` is an explicitly public deserialization API intended for keys exchanged/stored across protocol boundaries (resharing and recovery flows). Any flow that accepts serialized `ThresholdKeys` from a counterparty — which the recovery crate exists to support — reaches this path with fully attacker-controlled bytes. No collusion, validator status, or leaked secrets are required; only the ability to supply the byte blob.

### Recommendation
In `ThresholdKeys::new` (or `ThresholdKeys::read` immediately after construction), enforce the internal invariant that `C::generator() * secret_share == verification_shares[params.i()]`, and reject keys failing it. Where the protocol also knows the expected group key (e.g., the prior set's committed key), additionally verify the computed `group_key` against it — mirroring the SAM fix's principle that the guard on critical parameters must come from a trusted, locally-stored value rather than from the untrusted input itself.

### Proof of Concept
```rust
// Attacker crafts serialized ThresholdKeys: any valid t, n, i header,
// Interpolation::Lagrange tag, arbitrary secret_share, and
// verification_shares[i] = a_i * G for attacker-known a_i.
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(2u16.to_le_bytes()); // t
buf.extend(2u16.to_le_bytes()); // n
buf.extend(Participant::new(1).unwrap().to_bytes()); // i
buf.push(1); // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // inconsistent secret_share
let a1 = C::F::from(7u64);
let a2 = C::F::from(11u64);
buf.extend((C::generator() * a1).to_bytes().as_ref());
buf.extend((C::generator() * a2).to_bytes().as_ref());

let keys = ThresholdKeys::<C>::read(&mut buf.as_slice()).unwrap();
// group_key = a1*G*lam(1) + a2*G*lam(2) = (a1*lam(1) + a2*lam(2)) * G
// The attacker knows the discrete log; the honest share (secret_share = 1)
// does not correspond to verification_shares[1], yet no check fails.
assert_eq!(
  keys.group_key(),
  C::generator() * (a1 * keys.interpolation().interpolation_factor(...)
    + a2 * keys.interpolation().interpolation_factor(...))
);
```

Note: I was unable to fully trace `crypto/dkg/recovery` to confirm the exact call site that feeds peer-supplied bytes into `ThresholdKeys::read` before the iteration limit; the vulnerability in `read`/`new` itself is confirmed by the cited code, but the concrete remote delivery path should be verified against the recovery crate's usage.
