### Title
Deterministic cached preprocess reuse lets a `DkgConfirmer` sign two distinct `set_keys` messages with the same FROST nonces, enabling secret-share recovery — (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The analog of "factory nonce rolls back → same address recreated with attacker-chosen parameters" is Serai's `CachedPreprocesses` table: a validator's FROST preprocess seed is derived deterministically and persisted under the context `(b"DkgConfirmer", attempt)`. Every call to `share_internal`/`complete` for the same attempt re-derives the *same* nonce pair `(d, e)`, while the signed message (`set_keys_message`) and the participant set depend on externally-mutable state (`removed_as_of_dkg_attempt`, `key_pair`). If the node produces a second confirmation share for the same attempt after that state changes — exactly the reorg/state-rollback scenario of the original report — the two published `DkgConfirmed` shares form a nonce-reuse pair from which the validator's Ristretto secret share is recoverable.

### Finding Description
`SigningProtocol::preprocess_internal` generates a seed once per `context` and stores it XOR-encrypted in `CachedPreprocesses`; on subsequent calls it reloads the same seed and rebuilds identical nonces via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` (`ChaCha20Rng::from_seed(*seed.0)`). [1](#0-0) [2](#0-1) 

`DkgConfirmer` fixes `context = (b"DkgConfirmer", attempt)`: [3](#0-2) 

The message signed is `set_keys_message(&self.spec.set(), removed, key_pair)`, where `removed` comes from `removed_as_of_dkg_attempt(txn, spec.genesis(), attempt)` — a DB-derived value that reflects votes/removals observed as of a given tributary ordering — and `key_pair` comes from the processor via `generated_key_pair`, which overwrites `DkgKeyPair` each call and has no "already shared for this attempt" guard: [4](#0-3) [5](#0-4) 

Nothing in `share_internal`/`complete` records that a share was already emitted for a context. The spec acknowledges reuse is fatal ("Reusing preprocesses would enable a third-party to recover your private key share") but delegates prevention to callers: [6](#0-5) 

Attack sequence mirroring the reorg report:
1. DKG attempt `a` runs; the coordinator caches seed under `(b"DkgConfirmer", a)` and emits the confirmation preprocess via `dkg_confirmation_nonces`.
2. `generated_key_pair` signs `set_keys_message(set, removed₁, key_pair₁)` → share `s₁ = d + e·b·ρ₁ + λ₁·x·c₁`, published as `DkgConfirmed`.
3. The tributary's ordering/finality is re-executed (reorg, crash between the coordinator's `DkgKeyPair::set` commit and tributary publication, or a removal vote landing between two evaluations), so `removed_as_of_dkg_attempt` now yields `removed₂ ≠ removed₁` — or a retry signs `key_pair₂`. The same cached seed produces the same `(d, e)` and same commitments `(D, E)`.
4. A second share `s₂ = d + e·b·ρ₂ + λ₂·x·c₂` is produced and published. Any observer of the two public `DkgConfirmed` transactions solves the 2×2 linear system for the signer's MuSig/FROST secret share `x` (and the nonces), since `c₁ ≠ c₂` whenever the message or signing set differs.

### Impact Explanation
Full recovery of a validator's Ristretto secret key share for the DKG-confirmation MuSig key — the exact "sign unintended message / key share recovery" class. Both shares are broadcast on the public tributary (`Transaction::DkgConfirmed`), so no private channel access is needed. Combined with `t − 1` other shares (or as one share toward threshold forgery), this undermines the confirmation signature authorizing `set_keys` on Substrate.

### Likelihood Explanation
Medium-low: it requires the node to invoke share generation twice for one attempt with differing `removed`/`key_pair` inputs. This is reachable via tributary re-ordering of `RemoveParticipantDueToDkg`/removal handling relative to the confirmation flow (the precise reorg analog of the original finding — the "nonce" here is the cached preprocess, rolled back into a context whose inputs changed), or via processor retry after a crash between DB commits. A malicious validator can influence timing by publishing removal votes, nudging the honest node into re-evaluating `removed` between calls. No cryptographic assumption is broken; the flaw is the missing single-use enforcement on a deterministic, context-keyed nonce.

### Recommendation
- Track per-context consumption: set a `PreprocessUsed`/`ShareEmitted` flag in the same DB transaction that produces the first share for `(b"DkgConfirmer", attempt)` (and generally for any `SigningProtocol` context), and panic or refuse on a second `share`/`complete` call.
- Alternatively bind the seed to the signed content: derive the cached-seed key as `H(context || H(set_keys_message) || removed)` so differing inputs deterministically yield different nonces rather than reuse.
- Make `DkgConfirmer::new` snapshot `removed` at preprocess time and assert it is unchanged when `share`/`complete` is called, fatal-slashing or aborting on mismatch.

### Proof of Concept
Conceptual reproduction (no network required):

1. In a test harness, instantiate `DkgConfirmer` for `(spec, attempt)` with `removed = []`, call `share(preprocesses, key_pair₁)` → `s₁`.
2. Re-open the same DB txn (so `CachedPreprocesses` persists), construct `DkgConfirmer` again with `removed = [victim_key]` (simulating a removal observed after re-ordering) or pass a different `key_pair`, call `share(preprocesses, key_pair₂)` → `s₂`. No error is raised; the same `(D, E)` commitments appear in the emitted preprocess both times.
3. Recompute the challenges `c₁, c₂` per `sign.rs` FROST completion (`rho` bound over group key, `hash_msg`, commitments) and solve:
   `x = ((s₁ − d − e·b·ρ₁)·λ₂·c₂ − (s₂ − d − e·b·ρ₂)·λ₁·c₁) / (λ₁·c₁·λ₂·c₂ − λ₂·c₂·λ₁·c₁)` — with `d, e` simultaneously recoverable since `D, E` and the two shares give four equations in `d, e·b, x`.
4. Verify `x·G` equals the signer's Ristretto public key, confirming key-share recovery from two public `DkgConfirmed` shares.

Note: I verified the caching/reuse path and the absence of a single-use guard in `signing_protocol.rs`/`handle.rs`; the exact triggering condition (whether `removed_as_of_dkg_attempt` or `key_pair` can realistically differ across two calls in production flow) depends on processor retry/reorg behavior outside the indexed snippets, so the likelihood is rated accordingly.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

# Caching

modular-frost supports caching a preprocess. This is done by having all
preprocesses use a seeded RNG. Accordingly, the entire preprocess can be derived
from the RNG seed, making the cache just the seed.

Reusing preprocesses would enable a third-party to recover your private key
share. Accordingly, you MUST not reuse preprocesses. Third-party knowledge of
your preprocess would also enable their recovery of your private key share.
Accordingly, you MUST treat cached preprocesses with the same security as your
private key share.

Since a reused seed will lead to a reused preprocess, seeded RNGs are generally
frowned upon when doing multisignature operations. This isn't an issue as each
new preprocess obtains a fresh seed from the specified RNG. Assuming the
provided RNG isn't generating the same seed multiple times, the only way for
this seeded RNG to fail is if a preprocess is loaded multiple times, which was
already a failure point.
