### Title
Unbounded RPC retry on presumed-origin lookup permanently stalls the scanner - (File: processor/src/networks/bitcoin.rs)

### Summary
The external report describes a griefing pattern: an unprivileged caller can repeatedly force a victim contract into expensive execution paths that perform work and burn resources even though the triggering input is worthless (a zero-claimable claim), because there is no early rejection of the useless input.

The analogous pattern exists in Serai's Bitcoin network layer. `Bitcoin::get_outputs` unconditionally resolves `tx.input[0].previous_output` into a "presumed origin" for *any* transaction containing an output to the Serai multisig script, and the RPC lookup retries forever on error with a fixed 5-second sleep and no error propagation or bound. A remote, unprivileged party only needs to send one ordinary on-chain Bitcoin transaction paying the multisig's external/branch/forward address whose first input's previous transaction is not retrievable from the connected `bitcoind` (e.g. the node runs without `txindex`, is pruned, or the prev tx predates the index) to wedge this loop permanently. Because `get_outputs` is invoked from the scanner loop while holding the scanner write lock, this is a one-shot, permanent denial of service of deposit scanning — the strongest reachable mapping of the "attacker forces expensive/wasted work with no early check" bug class onto in-scope code.

### Finding Description
In `processor/src/networks/bitcoin.rs`, `get_outputs` scans each block's transactions and, for any tx producing at least one matched output, computes `presumed_origin` by fetching `tx.input[0].previous_output.txid` from the RPC:

```rust
// processor/src/networks/bitcoin.rs ~L714-727
let spent_output = {
  let input = &tx.input[0];
  let mut spent_tx = input.previous_output.txid.as_raw_hash().to_byte_array();
  spent_tx.reverse();
  let mut tx;
  while {
    tx = self.rpc.get_transaction(&spent_tx).await;
    tx.is_err()
  } {
    log::error!("couldn't get transaction from bitcoin node: {tx:?}");
    sleep(Duration::from_secs(5)).await;
  }
  tx.unwrap().output.swap_remove(usize::try_from(input.previous_output.vout).unwrap())
};
```

This loop has no retry bound, no error return, and no early validation that the origin lookup is even needed (it runs whenever `outputs` is non-empty, before `extract_serai_data`, for all `OutputType`s, not only `External`). Any persistent RPC failure — the previous transaction not being indexed, the node being pruned, an RPC error class that never resolves — causes `get_outputs` to never return.

The caller in `processor/src/multisigs/scanner.rs` invokes this while holding `scanner_hold.write()`, with an in-code TODO explicitly warning that "These lines are the ones which will cause a really long-lived lock acquisition". A hang therefore blocks the entire scan pipeline for that key/session, not just one block.

Additionally, `swap_remove(usize::try_from(input.previous_output.vout).unwrap())` will panic if the RPC returns a transaction whose output vector is shorter than `vout` (reachable if the RPC layer returns a mismatched/wrong transaction), turning the griefing into a crash.

### Impact Explanation
An unprivileged Bitcoin user can permanently halt deposit detection for a Serai multisig by sending one valid, cheap transaction to the multisig address crafted so the RPC prev-tx lookup fails (e.g. spending an input from an unindexed transaction while Serai's node lacks `txindex=1`). Once `get_outputs` enters the retry loop it never exits: the block is never marked scanned, no `ScannerEvent::Block` is emitted, no batches are built, and the scanner write lock is held indefinitely, stalling all other keys registered on the scanner. This is a persistent, remotely triggerable denial of service of the bridge's deposit flow — materially worse than the original report's per-call gas waste, since one trigger suffices and the failure is not self-healing.

### Likelihood Explanation
The trigger requires only a standard on-chain Bitcoin transaction to a publicly known multisig address (the external deposit address is public by design), plus an RPC environment where the prev-tx fetch fails — which is the default for nodes without `txindex` when the input's parent tx is unrelated to the wallet. No privileged access, collusion, or malformed consensus data is needed; the attacker pays only one transaction fee. Operators commonly run bitcoind without full txindex, making the failing-RPC condition realistic rather than exotic.

### Recommendation
Bound the retry loop and propagate failure: replace the infinite `while tx.is_err()` with a bounded attempt count (or treat the origin as `Option`/`Address::new(...).ok()` → `None`) so a failed lookup degrades `presumed_origin` to `None` instead of hanging. Only compute `presumed_origin` when at least one `External` output needs it. Replace `swap_remove(...unwrap())` with a checked `.get(vout)` that returns `None`/errors rather than panicking. Optionally make `get_outputs` itself return a `Result` so network-layer faults cannot wedge the scanner lock.

### Proof of Concept
1. Deploy Serai's processor with a bitcoind lacking `txindex` (or otherwise unable to serve arbitrary historical txs).
2. From an external wallet, create tx `A` paying to the multisig's external address, where `A.input[0].previous_output.txid` refers to a transaction the processor's node cannot retrieve (not in its index/mempool).
3. Mine/confirm `A`. When the scanner reaches that block, `get_outputs` matches the deposit output, enters the `while tx.is_err()` retry loop at `processor/src/networks/bitcoin.rs:719-725`, and never returns.
4. Observe: `ram_scanned` stops advancing, no `ScannerEvent::Block` is emitted, the deposit is never batched, and subsequent blocks/keys stall behind the held scanner write lock (`processor/src/multisigs/scanner.rs:544-567`). Restarting the processor re-enters the same loop on the same block, so the DoS persists across reboots.
