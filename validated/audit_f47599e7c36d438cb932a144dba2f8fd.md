### Title
Double-application of bank balance-change events to StateDB during nested/recursive precompile calls causes balance duplication - (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
The external report describes a class of bug where a stateful accounting variable (`rewardRate`) is not reset at a period boundary, causing the same value to be reused and rewards to be double-counted. The Cosmos EVM analog is the precompile `BalanceHandler`'s event-window tracking (`prevEventsLen`), used to translate `x/bank` events into `StateDB.AddBalance`/`SubBalance` calls after every precompile call in `precompiles/common/precompile.go` and `precompiles/common/balance_handler.go`. When a precompile call recursively invokes another (or the same) precompile during its execution (e.g. ERC20/staking/distribution/ICS20/gov/slashing precompiles calling into another precompile, or a caller contract that re-enters a precompile), the outer call's `BeforeBalanceChange` records an event-length "baseline" before the nested call runs, but the nested call's own `AfterBalanceChange` already applies (and thereby "consumes") the events created *after* that baseline. When control returns to the outer call, `AfterBalanceChange` re-slices `events[bh.prevEventsLen:]`, which is the entire window since the outer call started - it re-includes the events that were already applied to `stateDB` by the inner call. This causes the same bank-driven balance delta to be applied to `StateDB` twice.

### Finding Description
- `runNativeAction` in [1](#0-0)  instantiates a fresh `BalanceHandler` for every precompile invocation and calls `BeforeBalanceChange(ctx)` immediately before executing the native action, then `AfterBalanceChange(ctx, stateDB)` immediately after.
- `BeforeBalanceChange` simply snapshots the *current length* of the SDK event manager's event list: [2](#0-1) .
- `AfterBalanceChange` iterates `events[bh.prevEventsLen:]` — i.e., every event since the snapshot was taken — and for each `coin_spent`/`coin_received`/precisebank fractional-balance event, applies the corresponding `AddBalance`/`SubBalance` to the EVM `StateDB`: [3](#0-2) .
- Because the SDK `EventManager` inside a single cached context accumulates events cumulatively across nested calls, if precompile A's native action internally triggers precompile B (a nested/recursive precompile call, which itself runs through `runNativeAction` and applies its own `AfterBalanceChange` against the *same* underlying event log), B's bank events get applied to `stateDB` once by B's own `AfterBalanceChange`. When execution returns to A, A's `AfterBalanceChange` re-slices from A's earlier `prevEventsLen`, which still includes all the events B already consumed and applied — so those same bank-balance events get reapplied to `stateDB` a second time.
- The repository already contains a regression test explicitly built around this exact failure mode — recursive precompile calls causing the `prevEventsLen`/event-window bookkeeping to desync balances between the native bank keeper and the EVM `StateDB`: [4](#0-3)  and the test itself constructs a caller contract that triggers multiple nested `debug_precompile` calls and asserts a specific event/count invariant: [5](#0-4) .
- This is the direct structural analog of the `rewardRate` bug: a "baseline" value (`prevEventsLen`, analogous to the reward-rate/period start) is not properly reset/isolated per nested execution scope, so a later "distribution" step (the `AfterBalanceChange` StateDB-balance replay) re-processes value that was already distributed, producing a duplicated/incorrect balance rather than an under- or non-distributed one.

### Impact Explanation
If exploitable end-to-end, this breaks the core Cosmos EVM invariant that `StateDB` (EVM-visible) balances must be 1:1 consistent with native `x/bank`/`x/precisebank` balances (the same invariant `BalanceHandler` exists to enforce, per its own doc comment about avoiding balance desync — see the surrounding explanation in [6](#0-5) ). A double-applied `AddBalance` event would let a user's EVM-visible balance be inflated relative to their actual bank balance without any corresponding mint, i.e. unauthorized duplication of spendable value — a Critical accounting-corruption impact under the stated scope (native/EVM/precompile-mediated balance duplication).

### Likelihood Explanation
Reachability depends on whether any production precompile actually re-enters another precompile (or itself) synchronously within a single `RunNativeAction` call while both go through `runNativeAction`/`BalanceHandler`. I was not able to fully confirm, within the remaining investigation budget, a concrete unprivileged call path in mainnet precompiles (ERC20, staking, distribution, ICS20, gov, slashing, werc20) that recursively invokes a second `BalanceHandler`-wrapped precompile in the same call stack — the debug precompile used in `evmd/tests/testdata/debug/debug.go` is test-only scaffolding built specifically to reproduce this scenario, and I could not verify from the retrieved code whether the ERC20/ICS20/WERC20 precompiles' interactions with each other (e.g. ERC20 transfer callbacks invoking IBC transfer precompile, or ICS20 callbacks invoking ERC20) create a real nested `BalanceHandler` chain in production. This is the key uncertainty limiting confidence in exploitability, and it would need direct engineering verification (tracing actual precompile-to-precompile call paths, e.g. `precompiles/erc20`, `precompiles/ics20`, `precompiles/werc20`) to confirm whether a genuine unprivileged nested-call trigger exists.

### Recommendation
Ensure the event-window baseline used by `BalanceHandler.AfterBalanceChange` cannot double-count events already consumed by a nested call — e.g., by tracking a shared/monotonic "already-processed" watermark (rather than a per-instance snapshot taken before nested execution), or by having nested `BalanceHandler` instances advance a shared cursor on the outer context so the outer's `AfterBalanceChange` only processes events emitted after the inner call's watermark, not from its own original snapshot.

### Proof of Concept
The repository's own [7](#0-6)  test is the closest available reproduction: it deploys a `DebugPrecompileCaller` contract that invokes the debug precompile recursively via `callback(0)`, and asserts a fixed count of `debug_precompile` events and total events. I was unable to fully trace, within the remaining tool budget, whether this test currently passes (indicating the bug is mitigated by the per-call `NewBalanceHandler()` instantiation seen in `runNativeAction`) or fails/needs a fix (indicating the duplication is still live for genuine nested calls between two different production precompiles that both use `BalanceHandlerFactory`). Confirming this requires either running the test suite or manually tracing a concrete production precompile-to-precompile nested call path.

// It handles the bank events for coin spent and coin received, updating the balances
// of the spender and receiver addresses respectively.
//
// NOTES: Balance change events involving BlockedAddresses are bypassed.
// Native balances are handled separately to prevent cases where a bank coin transfer
// initiated by a precompile is unintentionally overwritten by balance changes from within a contract.

// Typically, accounts registered as BlockedAddresses in app.go—such as module accounts—are not expected to receive coins.
// However, in modules like precisebank, it is common to borrow and repay integer balances

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
