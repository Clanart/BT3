## Finding

Reducing the report to its core: a single-tenant resource (ETH supply / a `uint96` balance) is protected by a *local*, per-call invariant check that assumes exclusivity, but a second, independently-checked code path can run concurrently against the same underlying resource, so the two paths — each individually "valid" — combine into a state that violates the global invariant.

The closest verified analog in this codebase is **`AppStore._fetchRefspec`**, which explicitly and admittedly bypasses the single-network-operation invariant that guards every other git network action on a repository.

### Title
Concurrent git network operations on the same working directory bypass the single-in-flight-operation invariant via `_fetchRefspec` - (File: `app/src/lib/stores/app-store.ts`)

### Summary
Every push/pull/fetch initiated from the UI is wrapped in `withPushPullFetch`, which sets `isPushPullFetchInProgress` on the repository's cached state and refuses to start a second network operation while one is in flight [1](#0-0) . However, `_fetchRefspec` — used to fetch the exact refspec of a fork-originated pull request — is documented as intentionally *not* participating in this guard: "it does not opt-in to checks that prevent multiple concurrent network actions" [2](#0-1) . Because it operates on the same `GitStore` instance (keyed only by `repository.hash` in `GitStoreCache`) [3](#0-2)  and the same on-disk `.git` directory, it can run its own `git fetch` while a regular push/pull/fetch is simultaneously mutating refs, the index, or pack files in that very same repository.

### Finding Description
`withPushPullFetch` and `withIsCommitting` are the app-layer "sequencer checks" that are supposed to guarantee at most one git write operation touches a given repository at a time [4](#0-3) . `_fetchRefspec` is reachable whenever the user views a pull request originating from a fork, and by design skips this exclusivity check so that PR previews aren't blocked by an in-progress push/pull. This means:

- Path A: user clicks "Pull" → `_pull` → `withPushPullFetch` sets the "in progress" flag and runs `git pull` on the repo.
- Path B (concurrently): Desktop's own PR-preview logic (or a crafted PR/fork viewed via a malicious remote) triggers `_fetchRefspec` → runs `git fetch <refspec>` on the *same* physical repository, ignoring Path A's flag entirely.

Each path individually passes its own local check ("no other fetch/pull I know about is running" for Path A, "I never check" for Path B), but the combination breaks the implicit global invariant the rest of the app relies on: that no two git write processes are ever mutating the same working directory/refs/pack files concurrently. This is structurally identical to the reported bug's "cycle nets out to being accepted, but the mid-execution state is invalid" — here the mid-execution state is two live `git` child processes writing to the same `.git` metadata.

### Impact Explanation
Concurrent, uncoordinated `git fetch`/`git pull`/`git push` invocations against the same repository directory can race on ref/pack updates. Git's own locking (`.git/refs/heads/*.lock`, `packed-refs.lock`) will stop the crudest collisions, but partial races (one process reading `packed-refs` while another rewrites it, or a fetch updating `FETCH_HEAD`/remote-tracking refs mid-way through a push's ahead/behind computation) can leave Desktop's in-memory model of "what will be committed/pushed" out of sync with the actual repository state. Since Desktop trusts this state to decide what to stage, commit, and push next, this can silently corrupt what the user believes they are committing or pushing — matching the "silent corruption of what the user commits or pushes" impact class in the report's valid-impact list.

### Likelihood Explanation
The trigger (viewing a fork PR while another network operation is running) is unprivileged and requires no local access — it can be reached simply by the user having a PR-from-fork open while a background/manual fetch or push happens to be running, which is a normal, common Desktop usage pattern. The code comment itself acknowledges the gap ("This might require some rework in the future to chain these actions"), which mirrors the report's own "Acknowledged" status for the analogous smart-contract issue.

### Recommendation
Make `_fetchRefspec` participate in the same exclusivity guard as other network operations (`withPushPullFetch`), or serialize it behind the existing in-flight operation so refspec fetches queue rather than run concurrently with pushes/pulls/fetches on the same repository.

### Proof of Concept
1. Open a repository in Desktop and add a remote pull request from a fork.
2. Start a manual `git pull` on the repository (Path A) — `isPushPullFetchInProgress` is set.
3. While the pull is executing, trigger the fork-PR view flow that calls `_fetchRefspec` for the same repository (Path B) — verify in `app-store.ts` that no check on `isPushPullFetchInProgress` exists in this path [5](#0-4) .
4. Observe two `git` subprocesses running concurrently against the same `.git` directory, with no shared lock in the app layer — the only protection is whatever Git's own file locks happen to catch.

**Caveat:** I was not able to fully trace all the ways `_fetchRefspec` is invoked from the UI (e.g., exact React component wiring the fork-PR preview to this method) within the available search budget, so the exact end-to-end user trigger sequence should be verified against the full `app/src/ui` tree before treating this as conclusively exploitable in production. The core structural gap (documented, intentional bypass of the exclusivity invariant) is confirmed directly from the cited source.

import { GitStore } from './git-store'
import { Repository } from '../../models/repository'
import { IAppShell } from '../app-shell'
import { IStatsStore } from '../stats'

export class GitStoreCache {
  /** GitStores keyed by their hash. */
  private readonly gitStores = new Map<string, GitStore>()

  public constructor(
    private readonly shell: IAppShell,
    private readonly statsStore: IStatsStore,
    private readonly onGitStoreUpdated: (
      repository: Repository,
      gitStore: GitStore
    ) => void,
    private readonly onDidError: (error: Error) => void
  ) {}

  public remove(repository: Repository) {
    if (this.gitStores.has(repository.hash)) {
      this.gitStores.delete(repository.hash)
    }
  }

  public get(repository: Repository): GitStore {
    let gitStore = this.gitStores.get(repository.hash)
    if (gitStore === undefined) {
      gitStore = new GitStore(repository, this.shell, this.statsStore)
      gitStore.onDidUpdate(() => this.onGitStoreUpdated(repository, gitStore!))
      gitStore.onDidError(error => this.onDidError(error))

      this.gitStores.set(repository.hash, gitStore)
    }

    return gitStore
  }
