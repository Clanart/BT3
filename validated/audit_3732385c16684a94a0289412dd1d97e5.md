### Title
Missing cross-round participation check in `KeyMachine::calculate_share` lets a DKG participant crash honest nodes by sending shares without commitments - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The Libreswan CVE-2026-50721 pattern is "verify a signature payload without first checking that required associated data is present/well-formed, yielding an assertion abort (DoS) reachable by a remote peer." The Serai analog lives in PedPoP's `calculate_share`: it validates that every share sender is a legitimate participant index, then unconditionally indexes `self.commitments[&l]` — a map containing only participants who sent valid round-1 `Commitments`. A participant who skips round 1 (or whose commitments were rejected/dropped) yet still sends a round-2 `EncryptedMessage` share triggers a `HashMap` index panic in every honest recipient.

### Finding Description
`calculate_share` iterates the attacker-influenced `shares` map after `validate_map(&shares, &all_participant_indexes, i)`, which constrains keys to the participant index set but does not require the sender to have completed round 1 [1](#0-0) . For each `(l, share_bytes)` it decrypts, parses the scalar, then evaluates `share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share)`. `self.commitments` is populated in `verify_r1` only for participants that supplied a `Commitments` message, plus `self.params.i()` [2](#0-1) . `HashMap`'s `Index` impl panics on a missing key, so any `l` in `all_participant_indexes()` absent from `commitments` aborts the process with no `Err` path. The same shape exists at line 507 where `commitments[t]` is indexed per stripe — a `Commitments` vector shorter than `t` (not re-checked here, only checked in `verify_r1`) would also panic, though the missing-key panic is the cleaner trigger.

### Impact Explanation
This mirrors the CVE's denial-of-service half: a malformed/missing precondition on attacker-supplied protocol data causes an abort instead of a catchable `PedPoPError`. An unprivileged DKG participant sends bytes that parse cleanly through `EncryptedMessage::read` [3](#0-2)  and through the scalar `from_repr` check, so decryption blame and share verification are never reached — the process panics first. Every honest node evaluating `calculate_share` on that share set crashes identically; repeating the message on retry causes sustained abort-restart DoS of key generation, exactly the "continued exploitation causes sustained denial of service" shape. There is no forgeable signature or key-recovery impact, so Medium is appropriate.

### Likelihood Explanation
The trigger requires only that the attacker be a valid `Participant` in the DKG's index space and omit (or have dropped) their `Commitments` message while still delivering an `EncryptedMessage` — both are ordinary protocol messages an unprivileged counterparty controls. `validate_map` cannot reject the sender because being a participant is sufficient. Any deployment performing PedPoP key generation with an untrusted or faulty participant reaches the panic deterministically.

### Recommendation
In `calculate_share`, replace `&self.commitments[&l]` with a fallible lookup: `let Some(commitments) = self.commitments.get(&l) else { Err(PedPoPError::InvalidShare { participant: l, blame: None })? };` and likewise bound-check `commitments.len() == t` before striping at line 507, so all attacker-induced inconsistencies surface as blame-able errors rather than aborts.

### Proof of Concept
1. Honest node runs `SecretShareMachine` → `generate_secret_shares` receiving `commitment_msgs` that excludes participant `l` (attacker simply never sends round-1 commitments); `verify_r1` succeeds and `self.commitments` has no entry for `l`.
2. Attacker `l` delivers a syntactically valid `EncryptedMessage<C, SecretShare<C::F>>` (valid `key`, valid PoP `sig`, well-formed share scalar) in the `shares` map passed to `calculate_share`.
3. `validate_map` accepts `l` (it is a legitimate participant index). Decryption and `C::F::from_repr` succeed.
4. `self.commitments[&l]` at `crypto/dkg/pedpop/src/lib.rs:490` panics (`HashMap` index on absent key), aborting the honest node — where the correct behavior is `PedPoPError::InvalidShare`.

  pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
