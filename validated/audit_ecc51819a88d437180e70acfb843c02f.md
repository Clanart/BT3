### Title
Empty serialized Schnorr aggregate is accepted as a valid signature - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::read` permits an aggregate containing zero nonce commitments, while `SchnorrAggregate::verify` only requires the aggregate’s `Rs` length to equal the caller-provided key/challenge list. When both are empty and `s = 0`, the resulting multiexp statement is just the identity, so verification returns `true` for a signature that the aggregator API explicitly refuses to produce. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The deserializer accepts a four-byte length of zero followed by a canonical zero scalar. During verification, the length check succeeds for an empty `keys_and_challenges` slice, no aggregation weights or signature statements are queued, and the sole verification term is `-0 * G`, which is the group identity. [4](#0-3) 

This is semantically inconsistent with `SchnorrAggregator::complete`, which returns `None` when no signatures were aggregated, establishing that an empty aggregate is not a valid output of the signing-side API. [3](#0-2) 

### Impact Explanation
An unauthenticated party can supply a 36-byte serialized aggregate that verifies successfully against an empty expected-signer set without possessing any private key or creating any Schnorr signature. Any consumer that treats `SchnorrAggregate::verify` as proof that at least one supplied signature was valid can therefore accept a forged aggregate signature. [1](#0-0) [5](#0-4) 

### Likelihood Explanation
The attack requires the verifier to authorize an empty `keys_and_challenges` list. It is deterministic whenever that degenerate call is reachable through attacker-controlled serialized aggregate bytes; no malformed curve encodings, private state, timing behavior, or secret access is required. [2](#0-1) 

### Recommendation
Reject empty aggregates in both `SchnorrAggregate::read` and `SchnorrAggregate::verify`. At minimum, make `verify` return `false` when `keys_and_challenges.is_empty()`, matching the signing-side invariant enforced by `SchnorrAggregator::complete`. [6](#0-5) [3](#0-2) 

### Proof of Concept
For a ciphersuite with a 32-byte scalar representation, such as `Ristretto`, the following bytes form an aggregate with zero `Rs` and `s = 0`:

```rust
let mut encoded = vec![];
encoded.extend(0u32.to_le_bytes()); // zero Rs
encoded.extend([0u8; 32]);          // canonical zero scalar

let aggregate =
  SchnorrAggregate::<Ristretto>::read(&mut encoded.as_slice()).unwrap();

assert!(aggregate.verify(b"example DST", &[]));
```

`read` consumes the zero length and zero scalar successfully. `verify` then builds no weighted signature terms and checks only `-0 * G == identity`, returning `true`. [1](#0-0) [5](#0-4)
