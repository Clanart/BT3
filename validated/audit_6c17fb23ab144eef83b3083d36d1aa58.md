### Title
Untrusted `ReceivedOutput` bytes mint unspendable Bitcoin balance - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without proving that the outpoint exists, is unspent, contains the claimed amount, or is controlled by the associated key. This creates a direct analogue to accepting an attacker-supplied payment amount and crediting it without server-side transaction verification.

### Finding Description
The deserializer first reads an arbitrary secp256k1 scalar, then independently consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns them as a supposedly spendable `ReceivedOutput` [1](#0-0) . There is no consistency check that `output.script_pubkey` corresponds to `key + offset * G`, no lookup of `outpoint`, and no check that the claimed `TxOut` equals the chain's output.

The resulting object exposes the attacker-controlled `TxOut.value` through `ReceivedOutput::value()` [2](#0-1) . The Bitcoin processor wraps that directly into the reported `ExternalBalance` [3](#0-2)  and derives the claimed controlling key from the untrusted script and offset [4](#0-3) .

Unlike `Scanner::scan_transaction`, which binds the offset, script, value, and transaction-derived outpoint to an observed transaction [5](#0-4) , deserialization loses that provenance and accepts all three components independently.

### Impact Explanation
An unprivileged party able to supply serialized `ReceivedOutput`/`Output` bytes can cause downstream code to report arbitrary BTC amounts as received or spendable. The claimed outpoint may be nonexistent, already spent, owned by another script, or contain a different amount.

If the forged output reaches transaction construction, `SignableTransaction::new` sums the fake input values and uses them to authorize payments, calculate change, and decide whether sufficient funds exist [6](#0-5) . The claimed prevouts are then committed into the Taproot `Prevouts::All` sighash set [7](#0-6) . A forged amount produces an invalid consensus transaction, while accounting code may still have recorded and acted on the false balance before broadcast failure.

This satisfies the “funds reported received that are not spendable” condition: the object claims a valid spendable output and value without any chain or ownership validation.

### Likelihood Explanation
The byte format has no authentication or provenance marker, so any environment that treats deserialized `ReceivedOutput` data as equivalent to scanner-produced output is reachable. Exploitation does not require private-key material, threshold participation, malformed cryptography, or control of a Bitcoin node—only control over the serialized input bytes.

The impact depends on where the untrusted object is consumed. Direct balance reporting and transaction selection are immediately affected; obtaining a valid Bitcoin signature additionally requires the script to match a key controlled by the signing set. Even when the final transaction is invalid, false crediting, incorrect change calculation, and denial of legitimate withdrawal construction can already occur.

### Recommendation
Do not treat `ReceivedOutput` serialization as proof of spendability or ownership. At minimum:

- Add an authenticated/internal representation or explicit “unverified output” type for deserialization.
- Re-derive the expected script from the intended base key and offset and compare it to `TxOut.script_pubkey`.
- Resolve `outpoint` against the confirmed UTXO set and compare the complete on-chain `TxOut`, including value.
- Track spent state and confirmation/maturity requirements before reporting balance or selecting inputs.
- Keep scanner-derived objects distinct from deserializer-produced claims unless a chain verification step succeeds.

### Proof of Concept
Construct bytes containing:

1. `offset = 0`.
2. `TxOut { value: 1_000_000_000, script_pubkey: p2tr_script_buf(group_key) }`.
3. `outpoint = OutPoint { txid: arbitrary_or_real_low_value_txid, vout: arbitrary_index }`.

Feed them to `ReceivedOutput::read`. It returns `Ok`, `value()` reports 1 BTC-equivalent units, and `Output::balance()` reports that amount without validating the outpoint. If the script is chosen for the signer’s key, `SignableTransaction::multisig` passes the key/script check, while the signature commits to the forged prevout amount and the resulting transaction cannot spend the actual output.

  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }
