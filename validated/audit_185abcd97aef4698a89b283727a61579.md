### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee/vbytes calculation, silently discarding it like the dropped `remainder` — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Munchables finding — where a value was accumulated (`quantity = _quantity + remainder`) and then unconditionally overwritten with a freshly computed `remainder` that ignored the prior accumulation — `SignableTransaction::new` builds a transaction whose final output set silently includes an extra OP_RETURN output that was never accounted for in the weight/vbytes/fee computation. The computed `needed_fee` is therefore systematically too low whenever `data` is present, dropping the OP_RETURN's bytes from the accounting exactly as the migrator dropped the user's prior `remainder`.

### Finding Description
In `SignableTransaction::new`, the fee is computed from a weight estimate that only models the payment outputs:

```rust
// networks/bitcoin/src/wallet/send.rs:188-206
let mut tx_outs = payments.iter().map(...).collect::<Vec<_>>();

// Add the OP_RETURN output
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(PushBytesBuf::try_from(data)...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` constructs a dummy `Transaction` from `tx_ins`, `payments`, and an optional `change` — it has no parameter for `data`, so the OP_RETURN output appended to `tx_outs` is never represented in `weight`/`vbytes`/`needed_fee`. The change calculation at `send.rs:225-227` (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`) repeats the same omission.

The analogous defect pattern: a composite quantity is assembled (`tx_outs` = payments + OP_RETURN + change) but the accounting step (`calculate_weight_vbytes`) only sees the subset passed to it (`payments`), so the extra component's contribution is silently zeroed — the same shape as `lockedToken.remainder = remainder` discarding the pre-existing remainder on the `MigrationManager` path.

Reachability: `data` is attacker-influenced transaction content (an OP_RETURN payload up to 80 bytes, gated only by `TooMuchData` at `send.rs:171`), and it flows into the exact transaction the FROST multisig signs via `TransactionSignMachine::sign` → `taproot_key_spend_signature_hash` (`send.rs:373-390`). An unprivileged depositor/withdrawer who can cause an OutInstruction with data reaches this path.

### Impact Explanation
The signed transaction's actual vsize exceeds the accounted vsize by the OP_RETURN output's serialized size (~11 + up to 80 bytes). Consequences:

- The effective fee rate is `needed_fee / actual_vbytes < fee_per_vbyte`. When `fee_per_vbyte` is at or near the configured minimum, `needed_fee` satisfies the `TooLowFee` check against the *underestimated* vbytes (`send.rs:211`), but the real transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` per-vbyte and be rejected by relay/mempool policy.
- `needed_fee()` (`send.rs:133-135`) misreports the required fee, so downstream fee accounting is wrong.
- The result is a signed transaction that cannot propagate — funds committed to inputs are stranded until re-signed at a corrected fee, i.e. a liveness/correctness failure of the spend path analogous to locked "remainder" funds.

### Likelihood Explanation
Any spend carrying a `data` payload hits the under-accounting deterministically. Falling below the relay minimum additionally requires a low `fee_per_vbyte`, but the code explicitly permits the minimum-fee boundary (`TooLowFee` is evaluated against the wrong vsize). Given an 80-byte data output adds ~91+ vbytes, at 1 sat/vbyte the shortfall is ~91+ sats against a required minimum — enough to drop a borderline transaction below relay policy. Medium likelihood; Medium impact (incorrect fee formula producing an unspendable/stuck spend rather than permanent loss).

### Recommendation
Pass the `data` output into `calculate_weight_vbytes` (e.g., include a `data: Option<&ScriptBuf>` parameter appended to the dummy `tx.output`, mirroring how `tx_outs` is built), or compute `weight`/`vbytes` on the fully assembled `tx_outs`. Also ensure the `TooLowFee` check uses the post-change, post-data vbytes, so `needed_fee` always covers the final transaction.

### Proof of Concept
Conceptual trace against `SignableTransaction::new`:

1. Call `SignableTransaction::new(inputs, payments, None, Some(vec![0u8; 80]), 1)`.
2. `data` check passes (80 ≤ 80). `tx_outs` gains an OP_RETURN output of ~92 serialized bytes (`send.rs:194-202`).
3. `calculate_weight_vbytes(tx_ins.len(), payments, None)` (`send.rs:204`) builds a dummy tx containing only `payments` — no OP_RETURN — so `vbytes` is short by the OP_RETURN's ~92 vbytes-equivalent weight contribution.
4. `needed_fee = 1 * vbytes` passes `TooLowFee` since `needed_fee ≥ DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` holds for the underestimated `vbytes`.
5. The returned `SignableTransaction` serializes the OP_RETURN in `tx.output` (`send.rs:250`), so the signed transaction's real vsize exceeds what `needed_fee` pays for, and `fee() / actual_vbytes` can be below the relay minimum — producing a fully signed, policy-rejected transaction.

Caveat: I was unable to exhaustively verify every in-scope crate path (e.g., the full `sign.rs` binding-factor transcript block) within the available iterations; the fee/vbytes omission above is confirmed directly from the source shown, and is the strongest in-scope analog of the "accumulated value silently dropped" class reachable from untrusted transaction data.
