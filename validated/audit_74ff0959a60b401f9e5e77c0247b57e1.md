### Title
Cached FROST preprocess is never revoked after `sign`, enabling nonce reuse across distinct signing sessions in the same attempt - ([File: coordinator/src/tributary/signing_protocol.rs](https://github.com/Annirich/serai--025/blob/master/coordinator/src/tributary/signing_protocol.rs))

### Summary
Analogous to the unrevoked ERC-20 allowance that is left over after `swap()` and corrupts subsequent operations, `SigningProtocol::preprocess_internal` stores a deterministic FROST preprocess seed in `CachedPreprocesses` keyed only by `context = (b"DkgConfirmer", attempt)`, and **never deletes or rotates it**. Every call to `share_internal` (directly, or via `complete`, which internally re-runs `share_internal`) rebuilds the sign machine `from_cache` with the same seed, producing identical nonces. If `sign` is executed more than once under the same attempt with a different preprocess set or message — which is precisely what happens when a call fails with `InvalidPreprocess`/`InvalidShare` blame and is retried, or when `share` and `complete` are invoked with different preprocess maps — the same nonce is committed to two distinct FROST sessions, enabling recovery of the validator's MuSig secret share.

### Finding Description
- `preprocess_internal` only writes `CachedPreprocesses::set` when the entry is absent, and reads it back unconditionally on every invocation (`signing_protocol.rs:123-145`). There is no `del`/`take` anywhere; `CachedPreprocesses` is only ever `get`/`set` (grep confirms the only uses are in this file).
- `AlgorithmSignMachine::from_cache` deterministically regenerates nonces from the seed via `ChaCha20Rng::from_seed` (`crypto/frost/src/sign.rs:121-145`), so reuse of the seed = reuse of the nonces and commitments.
- `share_internal` (`signing_protocol.rs:150-181`) calls `preprocess_internal` then `machine.sign(preprocesses, msg)`. On `FrostError::InvalidPreprocess(p)` / `InvalidShare(p)` it returns `Err(p)` — the seed stays cached, and a subsequent call with a corrected/different `serialized_preprocesses` map reuses the same nonces against different peer commitments (a ROS-style nonce-reuse condition).
- `DkgConfirmer::complete` (`signing_protocol.rs:312-327`) calls `share_internal` again to rebuild the machine, so any path where `share` was executed with one preprocess map and `complete` with another (different validator submissions under the same attempt, or a different `key_pair` altering `set_keys_message`) produces two signature shares bound to the same nonce.
- The file's own safety argument (lines 25-54) rests entirely on BFT ordering guaranteeing identical inputs across re-executions, and admits missing checks: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)". An adversary who can cause a first `sign` to abort (by feeding malformed bytes to `read_preprocess`, which are untrusted validator-supplied bytes) forces a second `sign` under the same context with a different participant set — the case the design does not defend.

### Impact Explanation
Reuse of a FROST nonce across two signing sessions with different binding values/challenges leaks the signer's secret share via standard two-equation solving. The affected key is the coordinator-side MuSig validator key used to confirm DKG results on-chain (`set_keys_message`), i.e., the root-of-trust key for validator sets. Recovery of a share contributes to threshold compromise of the confirmation key; the cached seed is documented in `crypto/frost/src/sign.rs:85-87` as equivalent in sensitivity to the private key share itself.

### Likelihood Explanation
Triggering requires two `sign` executions under one `attempt` with differing preprocess sets or message. This is reachable whenever a validator supplies a preprocess that fails `read_preprocess` or `sign` validation (causing `Err(blame)` and a retry with a different set), or when `share`/`complete` are driven with different inputs — all inputs are on-chain messages an unprivileged-toward-this-code participant controls. The missing TODO check means nothing verifies the presumed commitments match what was used before re-signing.

### Recommendation
Delete (or rotate) the `CachedPreprocesses` entry after the first successful `sign`/`share` for a context, and before re-signing under the same context verify on-chain that the commitments derived from the cached seed equal the preprocess this validator already published (the TODO at lines 50-54); refuse to sign if they differ or if a share was already produced for that context.

### Proof of Concept
1. Attempt `a`: call `DkgConfirmer::share(preprocesses_A, key_pair)` where one peer preprocess is malformed → `share_internal` consumes the cached seed in `machine.sign`, returns `Err(InvalidPreprocess(p))`; `CachedPreprocesses` still holds seed S.
2. Call `DkgConfirmer::share(preprocesses_B, key_pair)` (same attempt, corrected/different map) → `preprocess_internal` reloads S → identical nonces/commitments, but different peer preprocess map → different binding factors ρ and challenge.

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  commitments generated from the decided nonces are in fact its commitments on-chain (TODO).

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
