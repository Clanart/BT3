### Title
Missing Bounds Check on CLVM Atom Length Prefix Causes Out-of-Bounds Read in Mempool Canonical-Form Check - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` in `chia/full_node/mempool_manager.py` decodes a CLVM atom's variable-length size prefix (1–6 bytes) directly from a spend-bundle-supplied puzzle reveal/solution buffer and returns the declared `atom_len` without ever checking it against the number of bytes actually remaining in `clvm_buffer`. Its caller, `is_clvm_canonical()`, then advances its cursor by that unchecked `atom_len` and immediately re-indexes the buffer at the new offset. This is the same bug class as CVE-2024-38373: a length field taken from untrusted input is trusted to bound a read/skip operation instead of being validated against the real remaining buffer size.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` computes `atom_len` purely from the length-prefix bits of the byte(s) at `offset` [1](#0-0) . Nowhere in this function is `atom_len` (or `offset + prefix_len + atom_len`) compared against `len(clvm_buffer)`.

`is_clvm_canonical(clvm_buffer)` calls this in a loop and does `offset += atom_len` before looping back to `b = clvm_buffer[offset]` [2](#0-1) . If a crafted puzzle reveal or solution contains an atom whose size prefix encodes a length larger than the bytes actually remaining in the buffer (directly analogous to the FreeRTOS DNS response whose declared domain-name length exceeds the actual name length), `offset` jumps past the end of `clvm_buffer`, and the next `clvm_buffer[offset]` access reads past the intended CLVM payload boundary.

This function is reachable from ordinary spend-bundle admission logic: `is_clvm_canonical()` is used to decide whether a coin spend's puzzle reveal/solution is DEDUP-eligible during mempool processing, so any unprivileged party submitting a spend bundle controls the exact bytes fed into this parser.

### Impact Explanation
In Python, indexing a `bytes` object past its end raises `IndexError` rather than silently returning adjacent-memory bytes as in C, so this does not directly leak process memory the way the FreeRTOS heap over-read does. However, it still means a single attacker-crafted spend bundle can drive `is_clvm_canonical()`/`is_atom_canonical()` into an unhandled `IndexError` during mempool processing, which is a spend-triggered failure in transaction-processing logic that the analog scope explicitly accepts (spend-triggered transaction-processing halt), rather than a graceful "not canonical" rejection. Whether this crashes the mempool worker or is only caught far up the call stack could not be fully confirmed — I was not able to locate and inspect the exact call site that invokes `is_clvm_canonical()`/sets `eligible_for_dedup` before running out of investigation budget, so I cannot state with certainty whether an outer `try/except` currently shields this failure mode.

### Likelihood Explanation
Triggering the malformed length prefix requires only constructing a CLVM-encoded puzzle reveal or solution with a large declared atom length and a short remaining buffer — this is fully attacker-controlled and requires no privileges, matching the "single submitted spend bundle" reachability required by scope. However, because the missing check surfaces as a Python exception (not a raw memory disclosure) and I could not confirm the exact exception-handling behavior at the call site, likelihood of the strongest impact (processing halt) is uncertain rather than confirmed.

### Recommendation
In `is_atom_canonical()`, validate that `offset + prefix_len + atom_len` does not exceed `len(clvm_buffer)` before returning, and have `is_clvm_canonical()` treat an out-of-range atom length as "not canonical" (return `False`) rather than allowing the cursor to advance past the buffer end.

### Proof of Concept
Not fully verified due to inability to confirm the exact call path from spend-bundle admission into `is_clvm_canonical()` and its exception handling; conceptually, a CLVM buffer such as a single atom byte `0xC0` (5+8 bit length prefix) followed by a length byte encoding a value larger than the actual remaining bytes (e.g., `b"\xc0\xff"` with no further data) would cause `is_atom_canonical` to return an `atom_len` that, when added to `offset` in `is_clvm_canonical`, indexes past the buffer, raising `IndexError` on the next `clvm_buffer[offset]` access [3](#0-2) .

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
