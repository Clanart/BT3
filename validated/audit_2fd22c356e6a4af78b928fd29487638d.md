### Title
Attacker-controlled `WWW-Authenticate` realm spoofing forces GitHub sign-in prompt / account binding for a non-GitHub host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The Desktop credential-helper trampoline decides whether a git host should be treated as a trusted GitHub/GitHub-Enterprise endpoint (`getEndpointKind`) partly by trusting an HTTP response header (`WWW-Authenticate`) that is fully controlled by the remote git server being contacted. This classification is supposed to be a trust decision Desktop makes about the *identity* of a host, but it can be set by the attacker-controlled server itself, with no verification step, similar in spirit to the reported `setInfo()` issue where a value that should be fixed/validated can instead be freely (re)written by an untrusted party.

### Finding Description
`getEndpointKind` in [1](#0-0)  classifies a credential request as `'github.com'`, `'enterprise'`, or `'generic'`. When the URL doesn't match a known dotcom/GHE hostname and doesn't correspond to an existing signed-in account, Desktop falls back to inspecting the `wwwauth[...]` credential fields that git forwards from the server's `WWW-Authenticate` response header:

```
if (v.includes('realm="GitHub"')) {
  return 'enterprise'
}
```

This header value originates entirely from the remote HTTP server that git is talking to — i.e., any git remote (or a MITM/malicious proxy sitting in front of a remote configured in a cloned repository) can return `WWW-Authenticate: Basic realm="GitHub"` on a 401 and have Desktop treat it as an "enterprise" GitHub endpoint, without any corroborating check (no TLS pinning, no `/meta` API confirmation, no manual `isGitHubHost()` verification is even attempted once this branch succeeds).

That classification then flows into `getCredential` [2](#0-1) : if the (spoofed) endpoint kind is not `'generic'` and no existing account matches it, Desktop calls `ui.promptForGitHubSignIn(endpoint)`. That helper [3](#0-2)  pops the standard GitHub Enterprise sign-in dialog, sets the sign-in endpoint to the attacker's `origin`, and — critically — is presented to the user in the exact same UI flow used for legitimate GitHub sign-in, with `isCredentialHelperSignIn: true`. The invariant that should hold ("this endpoint is really a GitHub/GHE server, so it's safe to prompt the user for their GitHub credentials against it") is entirely attacker-settable via a single response header, the same class of problem as a value that "should be immutable/validated once" but can instead be rewritten by an untrusted party at will.

### Impact Explanation
An attacker who controls a git remote (e.g., a URL embedded in a cloned/fetched repository's `.git/config`, a submodule URL, or a man-in-the-middle/malicious proxy in front of any HTTPS git remote the user fetches from) can:
- Force GitHub Desktop's credential helper to treat that arbitrary host as a "GitHub Enterprise" endpoint.
- Trigger the built-in GitHub Enterprise sign-in dialog bound to the attacker's `origin`, which the user may reasonably believe is a legitimate Desktop-initiated GitHub Enterprise auth prompt (unprivileged UI/OAuth-flow confusion) — leading to account binding against an attacker-controlled endpoint and, depending on how a user proceeds through the ensuing enterprise sign-in flow (e.g. supplying a PAT), credential exposure to that attacker infrastructure.

This satisfies the "unauthorized OAuth or account binding" / "credential exfiltration" impact categories: the attacker is a git remote/proxy response, not a local/privileged actor.

### Likelihood Explanation
Moderate. It requires the user to fetch/push against a repository whose remote is attacker-controlled (or intercepted) and to actually interact with the resulting sign-in prompt; git will only invoke the credential helper on an actual 401/authentication challenge, so the attacker's server must respond appropriately. No special local privileges, malware, or leaked credentials are needed — only an untrusted git remote returning a crafted header, which is a realistic scenario matching the "attacker controls a git remote/proxy response" category the task explicitly allows.

### Recommendation
Do not trust the `WWW-Authenticate` realm string alone to classify a host as GitHub/Enterprise. At minimum, corroborate it with the existing `isGitHubHost()` network check (already implemented but only used as a last resort) before triggering `promptForGitHubSignIn`, and/or clearly disclose the actual hostname/origin in the sign-in dialog so users can recognize a spoofed enterprise prompt before entering credentials.

### Proof of Concept
1. Attacker sets up an HTTPS git server (or a MITM proxy in front of a URL a victim will clone/fetch, e.g. `https://evil.example.com/repo.git`) that responds to unauthenticated git-http requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. Victim adds/clones this remote in GitHub Desktop and triggers a fetch/push.
3. Git's credential helper (`credential.helper=desktop`) calls into `createCredentialHelperTrampolineHandler` → `getCredential` → `getEndpointKind`, which matches the `wwwauth[...]` realm and returns `'enterprise'` [4](#0-3) .
4. Since no account exists for `evil.example.com`, Desktop calls `ui.promptForGitHubSignIn('https://evil.example.com')`, which opens the "Sign in to your GitHub Enterprise" flow bound to `evil.example.com` [5](#0-4) .

I was not able to fully trace what happens after a user completes this sign-in dialog against a non-genuine GHE instance (e.g., whether/how a resulting PAT or OAuth token would be persisted via `AccountsStore.addAccount`), so the exact downstream token-exfiltration severity is not fully confirmed from local code alone — this would benefit from a live Devin session tracing the enterprise sign-in flow end-to-end.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
