### Title
Unvote from Deactivated Pool Reverts, Permanently Freezing a User's vlMGP Unlock Rights - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager.unvote()` is documented as the mechanism that lets a user withdraw their vote allocation from a pool that has been deactivated so that pool removal or rewarder changes "doesn't block users from withdrawing." The actual implementation does the opposite: it reverts unless the pool is still active, permanently trapping the user's voted MGP allocation once the pool becomes inactive, with cascading effects on `VLMGP.startUnlock()`.

### Finding Description
`unvote()` is intended to let a user clear their vote on a pool that is no longer active: [1](#0-0) 

```
/// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
function unvote(address _lp) public {
    Pool storage pool = poolInfos[_lp];
    uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
    if(!pool.isActive)
        revert PoolNotActive();
    ...
```

The guard is inverted relative to the stated intent: instead of allowing unvoting *because* the pool is inactive, the function reverts with `PoolNotActive()` precisely when the pool is inactive, and only succeeds while the pool is still active. Once a pool curator deactivates a pool (a routine, non-malicious lifecycle event for pool management, analogous to the "reject" event in the external report that is a normal, expected action rather than an attack), any user who voted MGP into that pool has no path to zero out `userVotedForPoolInVlmgp[msg.sender][pool.poolAddress]` or reduce `userTotalVotedInVlmgp[msg.sender]`.

This matters because `VLMGP.startUnlock()` gates unlocking of locked MGP against the user's outstanding vote commitment tracked in the bribe manager: [2](#0-1) 

```
function startUnlock(uint256 _amountToCoolDown) external override whenNotPaused nonReentrant {
    if (_amountToCoolDown > getUserTotalLocked(msg.sender))
        revert NotEnoughLockedMPG();

    uint256 totalLockAfterStartUnlock = getUserTotalLocked(msg.sender) - _amountToCoolDown;
    if (address(wombatBribeManager) != address(0) && 
        totalLockAfterStartUnlock < IWombatBribeManager(wombatBribeManager).userTotalVotedInVlmgp(msg.sender))
        revert NotEnoughLockedMPG();
```

Because `userTotalVotedInVlmgp[msg.sender]` can never be decremented for the vote portion allocated to the now-inactive pool (the only decrement path, `unvote()`, reverts), the user is permanently prevented from starting an unlock for the MGP amount equal to that stuck vote — this is a direct analog of the reported bug class: a state-transition on one side of the system (pool deactivation, analogous to `rejectRequest`) leaves user-owned value (here, the right to unlock locked MGP) stranded with no on-chain recovery function reachable by the affected wallet.

### Impact Explanation
The user's MGP corresponding to the stuck vote amount becomes permanently non-unlockable through the intended interfaces, since `startUnlock()` will always revert with `NotEnoughLockedMPG()` for any amount that would bring `totalLockAfterStartUnlock` below the phantom `userTotalVotedInVlmgp` value that can never be reduced. This is a permanent freeze of user funds (locked MGP), satisfying the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
Pool deactivation is a normal, expected lifecycle operation (pools get deprecated, rewarders get swapped) and does not require any malicious behavior — only ordinary protocol maintenance. Any user who voted for a pool prior to its deactivation is affected purely by calling the documented, unprivileged `unvote()` function, which is the officially intended recovery path and simply does not work as designed.

### Recommendation
Correct the guard in `unvote()` so that it permits unvoting when the pool is inactive (matching the doc comment's stated intent), or alternatively allow unvoting regardless of `isActive` status while only blocking new votes to inactive pools in `vote()`.

### Proof of Concept
1. User calls `vote()` allocating locked vlMGP to pool `P`, incrementing `userVotedForPoolInVlmgp[user][P]` and `userTotalVotedInVlmgp[user]`.
2. Pool owner calls the admin function that sets `poolInfos[P].isActive = false` (routine pool deprecation).
3. User calls `unvote(P)` to reclaim voting capacity — this reverts with `PoolNotActive()` due to the `if(!pool.isActive) revert PoolNotActive();` check.
4. User calls `VLMGP.startUnlock()` for an amount that would reduce their locked balance below `userTotalVotedInVlmgp[user]` — this reverts with `NotEnoughLockedMPG()` indefinitely, since step 3 can never succeed to lower that value.

Note: I could not fully verify within the available context whether `vote()` itself contains an alternate path (e.g., re-voting zero to the same pool) that bypasses the `isActive` check in a way that would also decrement `userTotalVotedInVlmgp`; the retrieved `vote()` snippet only showed the tail-end accounting logic, not the per-pool `isActive` gating at the top of the loop. This would need to be checked directly in the full contract to confirm there is no alternate recovery path.
