### Title
Silent misalignment of Copilot conflict-hunk resolutions into wrong file locations via marker-mimicking content in an attacker-controlled branch - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's AI conflict resolution feature reassembles a resolved file by splicing per-hunk LLM output into the raw on-disk file **purely by positional order**, matched only against a line-by-line regex scan for `<<<<<<<`/`=======`/`>>>>>>>` sequences [1](#0-0) . The only safety check, `validateResolutionPaths`, verifies that the *count* of hunks returned by the model equals the *count* originally extracted, but never verifies that each hunk still corresponds to the same conflict boundary in the file [2](#0-1) . This is the same broken invariant as the reported bug class: matching by aggregate count/order instead of verifying per-item identity.

### Finding Description
Two independent parsers walk the same raw conflicted file content using identical, naive regexes (`^<{7}(?:\s|$)`, `^={7}$`, `^>{7}(?:\s|$)`):

- `extractConflictHunks`, used when building the prompt context from the file on disk [3](#0-2) 
- `reassembleResolvedFile`, used to splice the model's resolved hunks back into that same raw content [4](#0-3) 

Both scanners locate the "closing" `>>>>>>>` for a hunk by scanning forward and stopping on the **first** line that matches the theirs-marker regex, with no verification that this line is the delimiter that git actually generated versus an incidental line of *file content* that happens to start with exactly seven `>` characters followed by whitespace/EOL (e.g. ASCII banners, quoted-email text, diff/patch examples embedded in documentation, or test fixtures containing literal conflict-marker strings — a pattern that already exists elsewhere in this very codebase's test fixtures) [5](#0-4) .

Because a hostile branch/commit that gets merged, rebased, or cherry-picked by the victim is entirely attacker-authored content, an attacker can craft a file whose real Git-generated conflict region contains embedded lines that satisfy the marker regexes. Both `extractConflictHunks` and `reassembleResolvedFile` will mis-locate the true block boundary **the same way**, so the hunk *count* still matches between the two independent scans — satisfying `validateResolutionPaths`'s only check — while the actual boundaries used for splicing no longer correspond to the genuine `<<<<<<<`/`=======`/`>>>>>>>` triple that git produced. The model's resolution, generated for what it believed was the full "theirs" region, gets spliced against a truncated/shifted region, and everything after the spoofed marker (including the true closing marker and, in multi-conflict files, all subsequent conflicts) is shifted out of alignment. `reassembleResolutions` then takes this output verbatim as the new full file content with no secondary check that markers are gone or that boundaries were correctly consumed [6](#0-5) .

Existing guards do not stop this:
- `validateResolutionPaths` only compares hunk **counts**, not positions/content [2](#0-1) .
- The check that a returned hunk's `resolvedContent` doesn't "still contain conflict markers" only inspects the *model's own output*, not the original file, and does not detect boundary desynchronization [7](#0-6) .
- `reassembleResolvedFile`'s own malformed-marker fallback ("copy through as regular content") only triggers when no separator/closing marker is found at all — it does not detect a *wrong* (spoofed) closing marker, since one is always found [8](#0-7) .

### Impact Explanation
The result is silent corruption of code the user believes has been correctly conflict-resolved and then commits/pushes. Because the resolved content is applied automatically as the "fully resolved" file and only a summary/reasoning card is shown to the user (not necessarily a line-accurate re-diff against the true original markers), the true closing marker or trailing real conflict content can leak into the committed source, or a completely unrelated hunk's resolution can land in the wrong location, corrupting code with no error surfaced. This matches the "silent corruption of what the user commits or pushes" impact category — no privilege, local access, or social engineering beyond a normal merge/rebase from an attacker-controlled branch/PR is required.

### Likelihood Explanation
Requires only that the victim merges, rebases, or cherry-picks from a branch/PR authored (or influenced) by the attacker that produces a real merge conflict in a file also containing attacker-crafted marker-mimicking text. This is a realistic, unprivileged scenario (e.g., contributing a PR with a legitimately conflicting change, or a dependency/vendor file update) and requires no unusual interaction from the user beyond invoking the standard Copilot "resolve conflicts" flow.

### Recommendation
- Track and pass through original marker *positions* (line indices) from `extractConflictHunks` to `reassembleResolvedFile` instead of re-scanning independently by regex; splice using those exact indices rather than re-detecting markers.
- When re-scanning, require that a `>>>>>>>` closing marker consumed as a hunk boundary be immediately preceded by content collected since the matching `<<<<<<<`/`=======` pair recorded during extraction, and reject/flag a file for manual resolution if the counts or content used for splicing don't structurally match what was extracted (not just counts).
- After reassembly, re-run `extractConflictHunks` (or an equivalent marker scan) over the *final* reassembled content and fail closed (mark unresolved / require manual resolution) if any genuine-looking marker sequence remains, rather than trusting the model's `resolvedContent` marker check alone.

### Proof of Concept
Conceptual repro (based on the documented logic of `extractConflictHunks` and `reassembleResolvedFile`):
1. Attacker's branch modifies a file so that, when merged against the victim's branch, git produces:
```
<<<<<<< HEAD
victim's real change
=======
attacker's real change
>>>>>>> some example text
still more attacker content that should be part of "theirs"
>>>>>>> feature
```
Here the attacker deliberately places a line `>>>>>>> some example text` (7 `>` + space, satisfying `theirsMarker`) inside what git actually delimits as the "theirs" section, ahead of the real closing marker `>>>>>>> feature`.
2. `extractConflictHunks` and `reassembleResolvedFile`, using identical regexes, both stop "theirs" collection at the spoofed line, producing a truncated hunk; the hunk count still matches (1 expected, 1 returned), so `validateResolutionPaths` passes [2](#0-1) .
3. `reassembleResolvedFile` splices the model's resolution in place of the truncated block and then copies through, verbatim, the remaining lines (`still more attacker content...`, `>>>>>>> feature`) as if they were normal file content, since they no longer sit inside any recognized conflict block [9](#0-8) .
4. The final "resolved" file therefore contains a stray real conflict marker (`>>>>>>> feature`) and attacker-authored content injected outside the model's actual review, which the user then commits/pushes as if fully resolved.

Note: I was unable to trace the exact call site in `app/src/lib/stores/copilot-store.ts` that consumes `reassembleResolutions`'s output and writes it to disk before staging/committing (the file exceeded available inspection budget), so the assumption that no independent re-validation/diff-view occurs there is inferred from the absence of any such check in the resolution/reassembly module itself; confirming this fully would require reading that store file in a follow-up session.

 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
