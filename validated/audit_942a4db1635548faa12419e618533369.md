### Title
Reward-per-token model has no time-weighting, allowing front-run `vlMGP.lockFor` staking to snipe forfeited MGP rewards - (rewards/vlMGPBaseRewarder.sol)

### Summary
`_queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()))` does correctly add forfeited MGP into the same `rewards[MGP]` bucket that regular MGP-denominated bonus rewards use, since both `queueNewRewards` and `queueMGP`'s forfeiture path write to the same `mapping(address => Reward) public rewards` keyed by reward-token address. However, because reward accrual is a discrete, non-time-weighted `rewardPerTokenStored` snapshot model with no vesting/holding-period gate, an attacker can front-run a known large forfeiting `queueMGP` call by increasing their `vlMGP` balance via `lockFor` immediately beforehand, then call `getReward` right after, capturing a share of the forfeiture proportional to their newly inflated balance rather than their true time-weighted contribution.

### Finding Description
`_queueNewRewardsWithoutTransfer` and `queueNewRewards` both operate on the exact same `rewards[_rewardToken]` struct [1](#0-0) , and `queueMGP` calls it with `address(vlMGP.MGP())` as the token key [2](#0-1) , so forfeited MGP is deposited into the identical bucket used for ordinary MGP bonus rewards — this part of the question is confirmed correct.

The exploitable issue is in how balance changes interact with `rewardPerTokenStored`. Reward accrual for a user is `_userVlmgpShare * (rewardPerToken - userRewardPerTokenPaid) / 1e18 + userRewards` [3](#0-2) . There is no per-second/time-integrated accrual — `rewardPerTokenStored` only increases in discrete jumps whenever `queueNewRewards`/`_queueNewRewardsWithoutTransfer` is called, and the jump size is fixed at that transaction (`_amountReward * 1e18 / totalStaked()`) [4](#0-3) .

`VLMGP._lock` calls `IMasterMagpie(masterMagpie).depositVlMGPFor(_amount, _for)` **before** incrementing `totalAmount`, with the code comment explicitly noting this ordering triggers the pool-share/reward update first [5](#0-4) . This means: (1) the attacker's existing checkpoint (`userRewardPerTokenPaid`) is set to the current `rewardPerTokenStored` at lock time (pre-forfeiture), (2) their balance then jumps to the new large amount, (3) the forfeiting `queueMGP` call executes and bumps `rewardPerTokenStored`, and (4) `getReward`/`_updateFor` grants the attacker `newBalance * delta` where `delta` originates entirely from the forfeiture event the attacker had zero time exposure to [6](#0-5) , [7](#0-6) .

No modifier, cooldown, or minimum-holding-period gates reward *eligibility* on `lockFor` — `whenNotPaused`/`nonReentrant` guard reentrancy/pausing only, not timing [8](#0-7) . The `queueMGP` forfeiture amount is deterministically computable pre-trade via the public view `calExpireForfeit`/`_calExpireForfeit`, which reads on-chain `vlMGP.getRewardablePercentWAD` state [9](#0-8) , so an attacker observing a pending large forfeiting claim in the mempool can size their front-run stake accurately.

### Impact Explanation
This results in theft of a disproportionate share of unclaimed forfeited-MGP yield from legitimate long-term vlMGP holders, who lose part of what should have accrued to their actual time-weighted stake. This matches the Immunefi impact class "theft of unclaimed yield."

### Likelihood Explanation
Preconditions: attacker needs capital to lock a large amount of MGP via `vlMGP.lockFor`/`lock`, and must monitor the mempool for a `queueMGP` call carrying a large, predictable forfeiture (computable via the public `calExpireForfeit` view). No privileged role is required — `lock`/`lockFor` and `getReward` (via MasterMagpie) are both open to any EOA. The attack is repeatable for every sizeable forfeiture event and does not require flash loans, since capital merely needs to sit in `vlMGP` for one block before the forfeiting tx and can remain locked afterward (cooldown for principal withdrawal does not block reward claiming). Profitability scales with the forfeiture size relative to total staked supply and the attacker's capacity to size their stake accordingly.

### Recommendation
Introduce a minimum holding/checkpoint delay before newly deposited balance becomes eligible for reward-per-token accrual (e.g., snapshot balance changes to only apply to accrual starting in the next block/epoch), or convert to a linear, time-integrated reward-rate accrual model (reward-per-second streaming) rather than instantaneous lump-sum `rewardPerTokenStored` jumps, so that newly staked balance cannot retroactively capture an entire pending reward injection.

### Proof of Concept
Foundry test outline:
1. Deploy `VLMGP`, `MasterMagpie`, `vlMGPBaseRewarder`, mock MGP token; set forfeiting logic so a known user has a large forfeitable `queueMGP` claim pending.
2. Baseline: measure `rewardPerTokenStored` and attacker's `earned()` before any action, with attacker holding zero (or small) prior stake.
3. Attacker calls `vlMGP.lockFor(largeAmount, attacker)` in block N.
4. In the same/next block, the manager (simulating the pending mempool tx) calls `queueMGP(amount, forfeitingUser, receiver)`, triggering `_queueNewRewardsWithoutTransfer` and bumping `rewardPerTokenStored`.
5. Attacker calls `getReward(attacker, attacker)` immediately after.
6. Assert: attacker's captured MGP reward ≈ `forfeitAmount * largeAmount / totalStaked` despite having zero time-weighted exposure prior to block N, and that this captured amount would otherwise have gone to pre-existing long-term stakers — demonstrating the disproportionate/undeserved capture (dilution of other stakers' expected share, quantifiable via `historicalRewards` vs. per-account time-weighted stake).

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
