## Title
Freezing incoming messages via `notFrozen` also blocks timeout-driven fund refunds - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handlePostRequestTimeouts` and `HandlerV2.handleGetRequestTimeouts` are gated by the same `notFrozen(host)` modifier used for regular incoming message delivery (`handlePostRequests`, `handleGetResponses`). This modifier reverts whenever `EvmHost`'s `FrozenStatus` is `Incoming` or `All` [1](#0-0) . Timeout processing is the mechanism by which relayer fees are refunded and dispatching applications (e.g. cross-chain intent escrows) are notified to release locked funds when a destination chain fails to deliver in time [2](#0-1) . Because the same freeze flag blocks both "new usage" (incoming request/response delivery) and "timeout refunds," an admin/guardian freeze intended only to stop new cross-chain traffic also strands users' already-escrowed funds until the freeze is lifted — the same broken invariant as the audit source (`GUARDIAN` should stop new usage but not block withdrawals).

### Finding Description
`HandlerV2` defines a single `notFrozen` modifier that checks `host.frozen()` and reverts with `HostFrozen` if the status is `Incoming` or `All`: [3](#0-2) 

This modifier is applied uniformly to:
- `handlePostRequests` — delivers new incoming POST requests [4](#0-3) 
- `handleGetResponses` — delivers new incoming GET responses [5](#0-4) 
- `handlePostRequestTimeouts` — processes timeouts for **outgoing** POST requests, refunding relayer fees and notifying the source app to release escrow [6](#0-5) 
- `handleGetRequestTimeouts` — processes timeouts for **outgoing** GET requests [7](#0-6) 

`FrozenStatus.Incoming` is documented as "prevents receiving cross-chain messages" and is distinct from `Outgoing` [8](#0-7) . However, timeout processing is conceptually an *exit/refund path* for funds already escrowed on the source chain by an earlier outgoing dispatch — not "new incoming usage." The dispatch-timeout handler in `EvmHost` refunds the relayer's fee and invokes `dispatchTimeOut` which calls into the source application's `onPostRequestTimeout`/`onGetTimeout` callback, which is the exact hook applications like `IntentGatewayV2`/`ExtrinsicIntents`/`IntentsBase` use to unwind escrowed order inputs back to the user when a cross-chain fill or cancellation round-trip fails to complete [2](#0-1) .

Because `handlePostRequestTimeouts`/`handleGetRequestTimeouts` share the `Incoming`-gated `notFrozen` modifier rather than being gated on `Outgoing` (or not gated at all), setting `FrozenStatus.Incoming` or `FrozenStatus.All` — the natural "pause new usage" action for an admin/guardian responding to an incident — simultaneously blocks:
1. Relayer fee refunds for timed-out outgoing dispatches.
2. Delivery of `PostRequestTimeout`/`GetRequestTimeout` callbacks that unwind escrowed funds in dependent apps (e.g. Intent Gateway orders, cross-chain cancel-from-source flows relying on GET-request proofs).

This mirrors the audited bug precisely: a modifier meant to gate "new protocol usage" also blocks the code path that lets users recover funds they already committed.

### Impact Explanation
While frozen with `Incoming` or `All`, any user whose cross-chain POST/GET request has timed out cannot have that timeout processed. Concretely:
- Relayers cannot claim/refund the fee held in `_requestCommitments` for the timed-out request (funds stay locked in the host) [2](#0-1) .
- Apps such as `IntentGatewayV2`/`IntentsBase` that rely on GET-request timeouts/responses (e.g., source-side order cancellation, which dispatches a `DispatchGet` and expects `onGetResponse` to run `withdraw()` and release escrow) cannot process that response/timeout while frozen, leaving user escrow locked [9](#0-8) .

This is a fund-lock condition reachable without any privileged/malicious actor beyond the intended guardian freeze action itself — the freeze is a legitimate incident-response tool, but its side effect traps user funds that should remain withdrawable, consistent with the required impact class ("stealing or loss of funds"/fund lock via logic attack on custody).

### Likelihood Explanation
This triggers deterministically any time the host is frozen with `Incoming` or `All` (a documented, expected operational action, not a rare edge case) while there exist any in-flight timed-out requests/responses. Since freezing is the standard emergency response to a detected issue, the exact moment guardians are most likely to freeze the host is also the moment users most need timeout-driven refunds to still work.

### Recommendation
Separate the freeze semantics used for timeout processing from those used for new incoming message delivery. `handlePostRequestTimeouts` and `handleGetRequestTimeouts` are refund/exit paths for already-committed funds and should not be blocked by `FrozenStatus.Incoming`/`All`. Consider either exempting these two functions from the `notFrozen` modifier entirely, or introducing a dedicated frozen state that only affects new inbound dispatch delivery (`handlePostRequests`/`handleGetResponses`) while leaving timeout handling (and any other refund-only code paths) always callable, mirroring the recommended `emergencyWithdraw` pattern from the referenced audit finding.

### Proof of Concept
1. Guardian/admin calls `EvmHost.setFrozenState(FrozenStatus.Incoming)` (or `All`) in response to an incident — this is the intended "freeze new usage" action, restricted to admin/handler [10](#0-9) .
2. Prior to the freeze, Alice's app (e.g. `IntentGatewayV2`) dispatched a `DispatchGet`/`DispatchPost` on the source chain that escrows her tokens (`_orders[commitment][token] += amount`) and is now pending a destination response/timeout.
3. The destination fails to answer in time; a relayer submits a `PostRequestTimeoutMessage`/`GetTimeoutMessage` via `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` to trigger the refund callback into Alice's app.
4. Because the host is frozen with `Incoming`/`All`, the call reverts with `HostFrozen` at the `notFrozen(host)` modifier check [11](#0-10) , so `dispatchTimeOut` never runs, the relayer fee is never refunded, and any app-level escrow release tied to that timeout callback never fires.
5. Alice's escrowed tokens (and the relayer's fee) remain locked until the guardian unfreezes the host — even though the freeze was meant only to stop *new* protocol usage, not prevent withdrawal of already-committed funds.

Note: I was unable to fully trace whether `IntentGatewayV2`/`ExtrinsicIntents` register an explicit `onPostRequestTimeout`/`onGetTimeout` callback (no matches found in `evm/src/apps/**`); the relayer-fee-refund impact in `EvmHost.dispatchTimeOut` is directly confirmed in code, while the app-level escrow-unwind-via-timeout impact is inferred from the intents cancellation design docs and should be verified against the actual `IApp` timeout callback implementations before treating it as fully confirmed.
