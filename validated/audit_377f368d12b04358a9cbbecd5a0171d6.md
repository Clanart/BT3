### Title
Lagrange `interpolation_factor` recomputes an O(included) product per participant — `ThresholdKeys::read`/`view` on untrusted input costs O(n²) field work from bounded input (DoS) - (crypto/dkg/src/lib.rs)

### Summary
`Interpolation::Lagrange::interpolation_factor` computes the full Lagrange coefficient for a single participant by looping over the entire `included` set (`crypto/dkg/src/lib.rs:226-249`). Callers invoke it once per participant: `ThresholdKeys::new` calls it for each of `t` indexes in `1..=t` to derive the group key (`crypto/dkg/src/lib.rs:376-378`), and `ThresholdKeys::view` calls it once per included signer to derive each interpolated verification share (`crypto/dkg/src/lib.rs:495-507`). This is structurally identical to the stream-json bug: a per-element computation that re-scans the whole list, turning an n-element input into O(n²) work.

`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`) parses attacker-controlled `t`, `n`, and `i` as raw `u16`s, reads `n` scalars (for `Constant`) or `n` points, then calls `ThresholdKeys::new`, which performs `t` separate O(t) interpolations — O(t²) field multiplications plus `t` full field inversions. With `n = t = 65535` (the `u16` cap), a ~2.1 MB serialized blob forces ~4.3×10⁹ scalar multiplications and 65 535 inversions inside `interpolation_factor`/group-key derivation, and any subsequent `view()` repeats O(included²) work including a point multiplication per factor.

### Impact Explanation
An unprivileged party that can feed bytes to `ThresholdKeys::read` (explicitly in scope) causes CPU consumption superlinear in input size — the same "small input, large work" amplification as CVE-2026-71429. Where `read` output is used for signing, `view()` adds another O(m²) interpolation with a scalar multiplication of a stored point per factor (`crypto/dkg/src/lib.rs:500-507`), blocking the calling thread for seconds to minutes on maximal parameters. Impact is availability only; no key material or forgery results, consistent with a Medium-severity DoS.

### Likelihood Explanation
Reachability requires a code path that deserializes `ThresholdKeys` from bytes an attacker controls, or a `view()`/`sign` invocation where the attacker influences `n`/`included`. Within a multisig, `sign()` builds `included` from preprocess map keys and calls `view()` (`crypto/frost/src/sign.rs:290-312`), so any participant in a large multisig forces every honest signer through the quadratic interpolation on each signing attempt. The cost is bounded by `u16` (`n ≤ 65535`), so this is not unbounded amplification, but it is superlinear and attacker-triggerable wherever attacker-influenced parameters or serialized keys are processed.

### Recommendation
Compute Lagrange coefficients incrementally: build the product of all `(x_j)` and `(x_j - x_i)` terms once (O(n) with a single batch inversion via the prefix/suffix-product trick) instead of per-participant O(n) loops with individual inversions. Alternatively, cache per-set denominators/numerators in `view()`/`new`. Also consider bounding `n`/`t` at deserialization time in `ThresholdKeys::read` to a protocol-justified maximum rather than the full `u16` range.

The quadratic structure is directly visible at `crypto/dkg/src/lib.rs:226-249` (per-participant full loop with inversion) invoked inside per-participant loops at `crypto/dkg/src/lib.rs:376-378` and `crypto/dkg/src/lib.rs:500-507`, reached from `ThresholdKeys::read` at `crypto/dkg/src/lib.rs:591-632` and from `SignMachine::sign` at `crypto/frost/src/sign.rs:290-312`.
