### Title
`DkgConfirmer` deterministically regenerates the same FROST nonce seed for every `share`/`complete` call within an attempt, so an attacker who varies their submitted preprocess bytes across calls obtains two signature shares over identical secret nonces under different binding factors, enabling private key share recovery - (File: `coordinator/src/tributary/signing_protocol.rs`)

### Summary
The Velociraptor bug class is "a required check/guard exists but can be bypassed by an action that resets the enforcement context." In Serai's FROST usage, the load-bearing guard is that a cached preprocess seed `MUST only be used once` — reuse enables recovery of the private key share. `SigningProtocol::preprocess_internal` stores a `CachedPreprocess` in the DB keyed only by `context` and regenerates the identical `AlgorithmSignMachine` (and therefore identical secret nonces) on every invocation, never deleting the cache. `share_internal` calls `preprocess_internal` again internally, and `DkgConfirmer::complete` re-executes `share_internal` with a fresh, separately-supplied `preprocesses` map. An attacker-supplied preprocess that differs between the `share` and `complete` calls (or across retries after an `InvalidPreprocess`/`InvalidShare` error) forces two `sign()` executions reusing the same nonce scalars under different `rho` binding factors — a ROS-style nonce reuse that yields the victim validator's MuSig private key.

### Finding Description
In `preprocess_internal` (coordinator/src/tributary/signing_protocol.rs:123-147), the cached seed is created once per `context` and is read back, decrypted, and passed to `AlgorithmSignMachine::from_cache` on every call; there is no deletion of `CachedPreprocesses` after use. `share_internal` (lines 150-180) rebuilds the machine via `self.preprocess_internal(participants).0` each time it runs. `DkgConfirmer::share` (lines 304-310) and `DkgConfirmer::complete` (lines 312-327) each take an independent `preprocesses: HashMap<Participant, Vec<u8>>` of untrusted bytes, mapped through `threshold_i_map_to_keys_and_musig_i_map`, then parsed by `read_preprocess` inside `sign` — so a counterparty fully controls the commitments/addenda transcribed into the rho transcript. In `crypto/frost/src/sign.rs`, `sign` binds `msg`, `group_key`, and the per-participant commitments into `rho_transcript` (lines 362-371), while the secret nonces derive solely from the reused `seed`. Per the `SignMachine::cache`/`from_cache` contract (sign.rs:209-224), any reuse of the same seed across differing signing sessions leaks the private key share.

### Impact Explanation
`DkgConfirmer` produces the MuSig signature over `set_keys_message`, which confirms network key pairs for a validator set. Recovering one honest validator's MuSig private key lets the attacker (colluding with knowledge of other keys, or unilaterally if n-of-n reconstruction permits) forge `DkgConfirmer` signatures for the victim, including confirmations of attacker-chosen `KeyPair`s — i.e., signing unintended messages with the victim's key share and driving consensus-level key confirmation without authorization. This is a confidentiality/integrity break: private key share recovery plus signature forgery on an authorization-critical message.

### Likelihood Explanation
The trigger requires only that `share` (or `share_internal` inside `complete`) be executed more than once for the same `(b"DkgConfirmer", attempt)` context with different preprocess sets. Both surfaces accept attacker-chosen preprocess bytes: an attacker participating in the confirmation submits a valid preprocess at the `share` step and a mutated one at the `complete` step (or causes `Err(InvalidPreprocess)` to force a retry with an altered map). Each `sign` run reuses `(k0, k1)` while `rho` and the resulting challenge differ, giving two linear equations in the same nonce scalars — sufficient to solve for them and then the secret share, since each share is `s = k0 + rho*k1 + c*share` (verification form per `SchnorrSignature`/FROST share equations in crypto/frost/src/sign.rs and crypto/schnorr/src/lib.rs:74-84). The attacker only needs to be a validator participating in the DKG confirmation — an unprivileged-in-this-context party supplying public message bytes, satisfying the reachability rules.

### Recommendation
Treat the cached preprocess as single-use at the protocol layer: delete `CachedPreprocesses` for `context` inside `share_internal` immediately after `from_cache` reconstructs the machine (before returning the share), and make `complete` reuse the already-generated share rather than re-running `preprocess_internal`. Alternatively, bind a monotonically increasing per-use counter (or the full preprocess-set hash) into the context key so retries derive a fresh seed, and persist the generated preprocess so `share` and `complete` operate on one machine instance.

### Proof of Concept
Sketch: as validator `j` in a DKG confirmation for `attempt = a`, (1) at `DkgConfirmer::share`, submit preprocess bytes `P_j` for yourself — the victim validator `v` produces share `s1 = k0 + rho_A*k1 + c_A*x_v`; (2) at `DkgConfirmer::complete` (or after an induced `InvalidPreprocess` retry), submit mutated bytes `P_j'` so the reconstructed preprocess map differs — victim's `share_internal` re-derives the same `(k0, k1)` from the unchanged `CachedPreprocess` seed and computes `s2 = k0 + rho_B*k1 + c_B*x_v` with `rho_B != rho_A` and `c_B` known to the attacker (all transcript inputs are public: `group_key`, `hash_msg(msg)`, participant commitments). Two equations, two unknowns `(k0, k1)` scaled by known `rho`s, plus the `c*x_v` terms — extend to three shares/sessions or solve jointly to extract `x_v`, the victim's MuSig private key, which directly equals its `ThresholdKeys` secret share. Then forge `set_keys` confirmations as `v`.
