### Title
Zero-address `order.user` lets `_filled[commitment]` collapse to the "unfilled" sentinel, bypassing the fill/cancel guard - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2` uses `_filled[commitment] == address(0)` as the sole sentinel meaning "not yet settled." Every fill and cancel-from-destination path writes an address derived from user- or solver-controlled data into `_filled[commitment]` to permanently lock the commitment against re-use. When that written address happens to be `address(0)`, the write is indistinguishable from "never touched," so the guard `if (_filled[commitment] != address(0)) revert Filled();` never trips — exactly the same broken-invariant class as the referenced report, where transferring an NFT to `address(0)` is indistinguishable from "never happened" and lets protected state be reused.

### Finding Description
`cancelOrder` / `fillOrder` both gate on the same single value: [1](#0-0) [2](#0-1) 

The destination-side cancellation path writes the order owner directly into that sentinel with no zero check: [3](#0-2) 

`order.user` is a `bytes32` field fully controlled by whoever places the order (no non-zero validation was found at `placeOrder`). If a user places an order with `order.user = bytes32(0)`, then when `_cancelFromDest` runs, `_filled[commitment] = address(uint160(uint256(order.user)))` assigns `address(0)` — the same value as the "unfilled" default. The `RefundEscrow` message is still dispatched to the source chain, refunding the escrowed input there, but on the destination chain the guard `_filled[commitment] != address(0)` remains false, so the same order commitment can still be accepted by `fillOrder` afterward. A solver that fills the "cancelled" order will deliver output tokens to the beneficiary and dispatch a `RedeemEscrow` request back to source, where `_withdraw`'s `escrowed == 0` check (already zeroed by the refund) will reject the second redemption — but only after the solver has irreversibly delivered output assets on the destination chain expecting escrow release. The same collapse applies to `_fillSameChain`/`_fillCrossChain`, which write `_filled[commitment] = msg.sender`; only when `msg.sender` itself is zero is this irrelevant (accounts can't be zero), but the cancellation path is fully attacker-steerable through `order.user`.

This mirrors the report's root cause precisely: a state-machine "burn"/"settled" marker that is supposed to be permanent and unambiguous collapses into the default/uninitialized value under attacker-chosen input, breaking the one-time-settlement invariant that request/order flows are required to preserve.

### Impact Explanation
Setting `order.user = 0` lets an order-placer craft an order whose "cancelled" state is silently unrecorded on the destination chain. This breaks the fill-once invariant Hyperbridge requires for order settlement: a destination-side cancellation intended to permanently block fills does not actually block them, so a solver can be induced into a real fill (delivering output assets) against an order whose escrow has already been drained via the refund path, causing the solver to lose the value they delivered with no corresponding escrow to redeem. This is a direct "logic attack"/"double-settlement class" violation of the one-time redemption guarantee for escrowed intent inputs, matching the required impact of transaction manipulation / double-claim around bridge custody funds.

### Likelihood Explanation
The order is fully attacker-authored (the user constructs `order` off-chain and can set any `bytes32` value for `user`, including zero) — no relayer, prover, or admin collusion is needed. The only external actor drawn in is an honest, unprivileged solver who fills the order in good faith after seeing it on-chain/via the auction flow, unaware that the "unfilled" state is a forged artifact of a zero address rather than a genuinely open order.

### Recommendation
Reject `order.user == bytes32(0)` at `placeOrder` (and reject a solver `msg.sender`/beneficiary of zero anywhere it is written into `_filled`), or replace the `_filled` sentinel with a two-state representation (e.g. a `bool settled` flag alongside the stored address) so that "settled to zero" can never collapse into "not yet settled."

### Proof of Concept
1. User calls `placeOrder` with `order.user = bytes32(0)` (and a valid `beneficiary` in `order.output` so the order otherwise looks legitimate) on the source chain, escrowing input tokens.
2. Before any fill, the user (as any caller matching `order.user == bytes32(0)`, or after `order.deadline` anyone) calls `cancelOrder` on the destination chain. `_cancelFromDest` executes `_filled[commitment] = address(uint160(uint256(order.user))) == address(0)` and dispatches `RefundEscrow` to source, which zeroes the source-chain escrow via `_withdraw`.
3. On the destination chain, `_filled[commitment]` is still `address(0)`. A solver, seeing the order as apparently unfilled (the on-chain guard shows unfilled), calls `fillOrder`, delivering output tokens to `beneficiary` and dispatching `RedeemEscrow` to source.
4. On source, `onAccept` → `_withdraw` finds `_orders[commitment][token] == 0` (already refunded) and reverts with `UnknownOrder`, so the solver's `RedeemEscrow` fails permanently while the solver has already paid out the output tokens on the destination chain — the solver takes a real loss and order accounting/state remains inconsistent, directly caused by the zero-address collapse of the `_filled` sentinel.

```text
    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        if (order.deadline < _blockNumber()) revert Expired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();
```

```text
    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }
```

```text
    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );
```
