### Title
Path-containment check uses unanchored `startsWith`, letting a crafted `x-github-client://openrepo` deep link escape the repository directory - (File: `app/src/lib/path.ts`)

### Summary
The external report's broken invariant is a boundary check that is *too permissive* (`>=` instead of `==`), letting a value slip past a guard that was meant to be a hard containment/equality check. The Desktop analog is `_resolveWithin()` in `app/src/lib/path.ts`, which is supposed to guarantee that a resolved path lies *at or under* a root directory before the caller trusts it. Instead of anchoring the comparison to a path boundary, it does a raw string prefix test: [1](#0-0) 

`realResolved.startsWith(realRoot)` is true for any string that merely shares the same leading characters as `realRoot` — not just for paths that are actually inside it. This is the same class of bug as the Solidity report: a "containment" invariant that should be a strict equality/boundary test is implemented as a loose comparison, so an attacker-influenced value (here, a `..`-relative path segment) can satisfy the check while violating the real invariant.

### Finding Description
`resolveWithin(rootPath, ...pathSegments)` is Desktop's canonical guard against path traversal/symlink escapes for anything that mixes a trusted root with an untrusted relative path segment: [2](#0-1) 

The final check should assert that `realResolved` is `realRoot` itself or a path *under* `realRoot` (i.e. `realResolved === realRoot || realResolved.startsWith(realRoot + sep)`). Instead it only checks `realResolved.startsWith(realRoot)`. Because `resolved` is computed via `resolve(normalizedRoot, normalizedRelative)`, a relative segment such as `../<sibling-dir>/...` is fully permitted to escape `rootPath` into a sibling directory — and if that sibling directory's name happens to start with the same characters as the root directory's basename (e.g. `myrepo` vs. `myrepo-secrets`, or the common wiki-clone convention `<repo>` vs. `<repo>.wiki`), the string-prefix test wrongly reports the escaped path as "within" the root.

Interestingly, the codebase shows the *correct* pattern exists elsewhere — `isClonePathSensitive()` in `app/src/lib/git/clone.ts` appends the separator before comparing (`clonePath.startsWith(sensitive + Path.sep)`), and the "delete"/"rename" boundary logic in `copilot-in-memory-session-fs-provider.ts` builds an explicit `${prefix}/` before matching: [3](#0-2) [4](#0-3) 

This confirms `_resolveWithin` is the outlier that omits the separator, i.e. exactly the kind of "should be a strict boundary check, isn't" gap the external report is about.

The reachable, attacker-controlled trigger is the `openrepo` deep link. `app.on('open-url', ...)` feeds any externally supplied URL straight into `handleAppURL` → `parseAppURL`, which extracts an unauthenticated, unsanitized `filepath` query parameter: [5](#0-4) [6](#0-5) 

That `filepath` is passed into `dispatcher.openRepositoryFromUrl`, which relies solely on `isAbsolute()` and `resolveWithin()` to keep it inside the target repository before acting on it: [7](#0-6) 

`isAbsolute(filepath)` only blocks absolute paths, not `..`-relative traversal, so the entire containment guarantee rests on `resolveWithin`'s flawed prefix check.

### Impact Explanation
An attacker who gets a victim to click a `x-github-client://openrepo/<repo-url>?filepath=../<sibling>/...` link (a normal, "GitHub" branded deep link the app already registers itself to handle) can make Desktop resolve and act on a path in a directory *outside* the repository that the victim believes they are opening, as long as a sibling directory whose name has the repo's directory name as a string prefix exists next to it on disk (a very common layout in practice — e.g., `<repo>` next to `<repo>.wiki`, `<repo>-old`, `<repo>-fork`, `<repo>2`, etc., which Desktop itself and GitHub's own wiki-clone convention produce). This breaks the "path is outside repo" guard the code explicitly relies on and defeats its own error-logging/rejection branch (`Prevented attempt to open path outside of the repository root`), which is silently bypassed for prefix-colliding directories.

`resolveWithin` is the same primitive reused for Copilot's conflict-resolution file reader, so any future or existing caller that trusts it to keep reads within the repo inherits this exact containment defect.

### Likelihood Explanation
This requires only: (1) the victim has GitHub Desktop's URL-scheme handler registered (default install behavior), (2) the victim clicks an attacker-supplied link, and (3) a sibling directory with a colliding name prefix exists (a routine, not contrived, occurrence given common cloning/naming conventions such as `.wiki` clones or numbered duplicate clones). No local access, no credentials, and no unnatural user steps beyond clicking a link are needed — this satisfies the "link the user clicks" attacker primitive called out as valid impact.

### Recommendation
Change `_resolveWithin`'s final comparison from an unanchored prefix test to a proper boundary/equality check, mirroring the already-correct pattern used in `isClonePathSensitive`:

```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```

Apply the equivalent fix to the `win32`/`posix` option variants (`options.join/normalize/resolve` need a matching `sep`). After the fix, re-audit every caller of `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` (dispatcher's deep-link filepath handling, Copilot conflict-context file reads) to confirm they now correctly reject prefix-colliding sibling paths.

### Proof of Concept
1. On disk, have two directories side by side: `~/Documents/GitHub/octokit.net` (a normal Desktop-managed clone) and `~/Documents/GitHub/octokit.net.wiki` (also a common, legitimately-named clone) containing a file `SECRET.md`.
2. Craft the link:
   `x-github-client://openrepo/https://github.com/octokit/octokit.net?filepath=..%2Foctokit.net.wiki%2FSECRET.md`
3. Victim clicks the link. `parseAppURL` extracts `filepath = "../octokit.net.wiki/SECRET.md"` [8](#0-7) .
4. `openRepositoryFromUrl` opens/selects the `octokit.net` repository, then calls `resolveWithin(repository.path, "../octokit.net.wiki/SECRET.md")` [7](#0-6) .
5. Inside `_resolveWithin`, `resolved` becomes `.../GitHub/octokit.net.wiki/SECRET.md`, and `realResolved.startsWith(realRoot)` is `true` because `"octokit.net.wiki"` starts with `"octokit.net"` as a raw string [1](#0-0) , even though this path is a sibling directory, not a subdirectory of `octokit.net`.
6. The "outside repository" guard is bypassed silently, and Desktop calls `shell.showItemInFolder()` on the sibling-directory file instead of rejecting it as intended.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```
