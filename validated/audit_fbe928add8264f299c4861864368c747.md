### Title
Unencrypted-share blame path panics on unregistered decryptor index — reachable `HashMap` indexing panic - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The libtiff advisory describes a crash (denial of service) triggered by a specially crafted file reaching a vulnerable function. The analogous shape in Serai is a panic reachable purely through bytes an unprivileged participant supplies to `EncryptedMessage::read` / `EncryptionKeyProof::read` and the blame-decryption API: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` with `HashMap`'s `Index` impl, which panics when the key is absent, instead of returning an `io::Error`/`DecryptionError`. A single crafted accusation message naming a participant who never registered an encryption key crashes the node.

### Finding Description
`Decryption::register` only inserts into `enc_keys` when a participant's `EncryptionKeyMessage` is registered [1](#0-0) . Later, `decrypt_with_proof` verifies the accuser's `EncryptionKeyProof` DLEq against `self.enc_keys[&decryptor]` using direct indexing [2](#0-1) . `std::collections::HashMap`'s `Index` panics on a missing key, so if `decryptor` was never registered — because that participant never broadcast an `EncryptionKeyMessage`, sent a malformed one rejected by `EncryptionKeyMessage::read`, or the accusation names an arbitrary `Participant` index — the process panics rather than returning `DecryptionError::InvalidProof`.

All inputs on this path are attacker-controlled bytes: `key`, `pop`, and `msg` are parsed by `EncryptedMessage::read` [3](#0-2) , and the proof by `EncryptionKeyProof::read` [4](#0-3) . Both succeed on well-formed encodings, so the panic is reachable without corrupting deserialization. The PoP verification at line 374–379 is performed against `msg.key` with the ciphertext as the committed message — an attacker can produce a valid PoP trivially since they choose `key`'s discrete log — so the panic line is genuinely reached, not gated behind an unforgeable proof.

The same pattern exists symmetrically in `Decryption::register`, which `assert!`s a participant is not re-registered [5](#0-4)  — a participant who submits two `EncryptionKeyMessage`s panics the host — and in `Encryption::encrypt`, which indexes `self.decryption.enc_keys[&participant]` [6](#0-5) .

### Impact Explanation
A panic in library code invoked by a host handling DKG traffic aborts or unwinds the signing/validator process. This is a remote denial of service: any participant able to submit an accusation (`EncryptionKeyProof` + `EncryptedMessage`) can crash a victim processor mid-DKG or mid-blame-resolution, halting key generation/signing. This matches the advisory's impact class (crafted input → crash → availability loss; CVSS 6.5, A:H). No secret material is leaked.

### Likelihood Explanation
The trigger requires only that the `decryptor` index be absent from `enc_keys`. `enc_keys` is populated exclusively via `register`, and PedPoP explicitly tolerates missing/faulty participants (the whole blame mechanism exists for absent or invalid shares), so accusations referencing participants who never registered are a normal protocol edge case. A malicious participant can also deliberately withhold their own `EncryptionKeyMessage` and then file an accusation, guaranteeing the missing key. Crafted bytes fully control `msg`, `key`, `pop`, and `proof`; no honest-party cooperation is needed. Medium likelihood: it requires a DKG participant slot, consistent with the "public inputs they cause to be processed" scope.

### Recommendation
Replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`. Similarly, change `Decryption::register`'s `assert!` into a returned error (e.g., a new `DecryptionError`/`io::Error` variant) so duplicate registrations are rejected rather than fatal, and have `Encryption::encrypt` return an error on a missing `enc_keys` entry instead of indexing.

### Proof of Concept
```rust
// Conceptual PoC against crypto/dkg/pedpop
// Victim: runs PedPoP DKG; Mallory is a participant who never calls
// Encryption::registration / never broadcasts an EncryptionKeyMessage,
// so victim.decryption.enc_keys contains no entry for Mallory.

// Mallory constructs a blame/accusation targeting herself:
let mut msg_bytes = vec![];
// EncryptedMessage::read layout: key (G) || pop (G, F) || ciphertext (E)
msg_bytes.extend(attacker_chosen_pubkey.to_bytes().as_ref());   // key = k*G, k known to Mallory
msg_bytes.extend(valid_pop_sig.serialize().as_slice());        // SchnorrSignature Mallory signs with k
msg_bytes.extend(arbitrary_ciphertext.as_slice());             // E::read fixed-size body
let msg = EncryptedMessage::<C, ShareBytes>::read(&mut msg_bytes.as_slice(), params).unwrap();

// EncryptionKeyProof: key (G) || dleq (serialize)
let mut proof_bytes = vec![];
proof_bytes.extend(fake_shared_key.to_bytes().as_ref());       // any point; DLEq checked against enc_keys[decryptor]
proof_bytes.extend(dleq_bytes.as_slice());
let proof = EncryptionKeyProof::<C>::read(&mut proof_bytes.as_slice()).unwrap();

// Victim executes during blame resolution:
let decryption = victim_encryption.into_decryption();
decryption.decrypt_with_proof(mallory_i, mallory_i, msg, Some(proof));
// panics at encryption.rs:388  ->  self.enc_keys[&decryptor]
// thread 'main' panicked: "key not found" (HashMap Index)
```

The panic occurs before the DLEq result matters: `enc_keys[&decryptor]` is evaluated to build the `verify` arguments, so even a garbage `dleq` suffices — the crash precedes proof failure.
