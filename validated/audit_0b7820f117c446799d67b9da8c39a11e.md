## Analysis

The HackerOne report's core "broken invariant" is: **attacker-influenced data reaches a security-relevant server operation without validation that the receiving endpoint expects**, causing an unintended side-effect. The Desktop analog with the same shape — untrusted, attacker-controlled data (a remote-provided ref name) flowing into a subprocess invocation without a required separator — exists in the branch-checkout code path. [1](#0-0) 

### Title
Argument Injection via Attacker-Controlled Branch/Ref Names in `git checkout` (missing `--` before untrusted refs) - (File: app/src/lib/git/checkout.ts)

### Summary
`getBranchCheckoutArgs` builds the argument list for `git checkout` by placing the untrusted `branch.name` / `branch.nameWithoutRemote` values *before* the `--` end-of-options marker: `[branch.name, ...(remote ? ['-b', nameWithoutRemote] : []), '--']`. Git parses arguments positionally before an explicit `--`, so any ref value that begins with a `-` is interpreted as an option rather than a ref/pathspec. Ref names such as the remote's default branch (`HEAD` symref) or a plain branch name are populated straight from data returned by `git for-each-ref`/`git branch -r` against a remote the user cloned or fetched from — i.e., data an attacker fully controls if the victim clones or adds their repository as a remote. [2](#0-1) 

### Finding Description
`checkoutBranch()` calls `getBranchCheckoutArgs(branch)`, which returns `[branch.name, '-b', branch.nameWithoutRemote (if remote), '--']` and prepends it after `['checkout', ...]`. Because the `--` terminator comes *after* the ref arguments instead of before them, `branch.name`/`branch.nameWithoutRemote` are not protected from being interpreted as `git checkout` flags if they happen to start with `-`.

Git's `check-ref-format` rules (enforced in `sanitize-ref-name.ts`'s `invalidCharacterRegex`) block control characters, `~^:?*[\|"<>`, `@{`, leading `.`, trailing `.`/`.lock`/`/`, but they do **not** block a leading `-`. This is confirmed by the sanitizer itself, which handles leading `-`/`+` as a *separate*, optional cosmetic step (`.replace(/^[-\+]*/g, '')`) that is not applied by `testForInvalidChars` — the function actually used to gate the deep-link branch parameter in `parse-app-url.ts`. [3](#0-2) [4](#0-3) 

A remote repository (attacker-controlled) can freely advertise a ref/branch whose name (or, more directly, whose `HEAD` symref target checked out on clone) starts with `-`, since nothing in Desktop's fetch/clone/branch-listing path (`git/branch.ts`, `git-store.ts`) rejects or re-sanitizes ref names coming back from `git for-each-ref`. When such a branch reaches `checkoutBranch`, the resulting command line effectively becomes `git checkout <flag-like-string> --` (or `... -b <flag-like-string> --`), causing `git` to treat the attacker's string as a command-line option to `checkout` rather than a ref.

Existing guards do not stop this path because:
- `testForInvalidChars` (used only for the deep-link `branch=` query parameter) does not reject a leading `-`.
- Locally listed/fetched branch names are never re-validated before being embedded in the checkout argv; there is no `--` placed before them.
- `checkoutLocalBranch` (dispatcher) only requires the branch to exist among `state.branchesState.allBranches` — which is populated straight from git's own ref listing for the attacker's remote, so a hostile remote can trivially seed exactly the branch name it wants checked out.

### Impact Explanation
At minimum this permits a hostile clone/fetch source to make `git checkout` consume one of its ref-name-shaped arguments as a flag it did not intend (e.g. `-f`/`--force`), silently changing checkout semantics — for example forcing a checkout that discards uncommitted local changes without the confirmation dialog Desktop normally shows, i.e. silent corruption/loss of the user's uncommitted work, which is explicitly in-scope per the task's Valid Impact list ("silent corruption of what the user commits or pushes"). Because `checkoutBranch` also feeds `branch.name` straight into `updateSubmodulesAfterOperation`, an attacker-controlled ref/branch name can additionally influence downstream submodule operations that already run with `protocol.file.allow=always` when `allowFileProtocol` is enabled, widening the practical consequences of controlling the checkout invocation. [5](#0-4) 

### Likelihood Explanation
Exploitation requires only that the victim clone or fetch from, or add as a remote, an attacker-controlled repository — a scenario explicitly in-scope (attacker controls a cloned/fetched repository). No local access, admin rights, or prior compromise is needed; the malicious ref name is delivered purely through normal git fetch/clone protocol data.

### Recommendation
Insert `--` immediately after `checkout` (before any ref/branch arguments) in `getBranchCheckoutArgs`, e.g. `['--', branch.name]` / `['--', branch.name, '-b', branch.nameWithoutRemote]` reordered so the separator precedes all ref values, consistent with the defensive pattern already used in `checkoutPaths`, `checkoutConflictedFile`, and `clone.ts` (`args.push('--', url, path)`). Additionally, apply `testForInvalidChars`-equivalent (including leading-dash) validation to any ref names sourced from a remote before they are used to construct git command lines.

### Proof of Concept
1. Attacker hosts a git repository whose default branch ref name (or an additional branch) is set to a string beginning with `-`, e.g. `git symbolic-ref HEAD refs/heads/-f` on the attacker's server (or simply push a branch literally named `-f`).
2. Victim opens `x-github-client://openrepo/<attacker-url>?branch=-f` (bypassing the deep-link branch check, since `testForInvalidChars('-f')` is `false`) or otherwise adds/fetches the attacker remote and later checks out the branch named `-f` from the Branches list.
3. Desktop calls `checkoutBranch`, producing the arguments `['checkout', 'origin/-f', '-b', '-f', '--']` (or similar) — because `nameWithoutRemote` (`-f`) is not preceded by `--`, git parses it as the `-f`/force flag on the `checkout` invocation rather than as the intended branch name argument.
4. `git checkout` executes with unintended force/behavioral flags, silently discarding any uncommitted changes in the victim's working directory without the confirmation dialog Desktop normally presents for that action.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
