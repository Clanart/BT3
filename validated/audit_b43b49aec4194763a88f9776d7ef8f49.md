### Title
Stale partial-selection line indices are blindly reapplied to a freshly re-fetched diff when staging, allowing silent corruption of committed content - ([File: app/src/lib/git/apply.ts], [File: app/src/lib/patch-formatter.ts])

### Summary
GitHub Desktop lets a user select individual added/removed lines of a file for a partial commit. These selections are stored as numeric "absolute indices" computed against the specific `Diff` object that was rendered in the UI at the time of selection (`hunk.unifiedDiffStart + lineIndex`). When the user actually commits, `applyPatchToIndex` does **not** reuse that same diff — it independently re-fetches a brand-new diff from disk via `getWorkingDirectoryDiff` and then calls `formatPatch(file, diff)`, which re-applies the old `file.selection.isSelected(absoluteIndex)` indices to the **new** diff's hunk/line layout. ### Finding Description
The line-selection model (`DiffSelection`) is purely index-based and has no intrinsic tie to the content it was computed from. Desktop's own state-management code acknowledges this fragility: [3](#0-2) 

That reconciliation logic only runs for the file that is *currently being viewed* in the Changes pane, whenever its diff is explicitly reloaded (`updateChangesWorkingDirectoryDiff`). It does **not** run for other files that have a partial (line-level) selection but are not the actively selected file, and it does not run again immediately before `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` executes.

`applyPatchToIndex` fetches the diff fresh at staging time: [4](#0-3) 

`formatPatch` then walks the **new** diff's hunks and, for every non-context line, decides whether to include it in the patch using `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is derived from the new hunk's `unifiedDiffStart` but the selection bitmap itself reflects the old hunk layout: [5](#0-4) 

If the on-disk working-tree content of the file changes between (a) the moment the user made their line-level selection while viewing an older diff render and (b) the moment `stageFiles`/`applyPatchToIndex` recomputes the diff for staging, the hunk boundaries, `unifiedDiffStart` offsets, and line ordering can shift. The old selection bitmap will then be misapplied against the new line layout — lines the user intended to exclude can be silently included in the patch (and vice versa), because `git apply --cached` will happily accept a syntactically valid but semantically mismatched patch as long as the context lines around the hunk still match.

### Impact Explanation
This directly threatens the "commit integrity" invariant that Desktop users rely on: what is shown/selected as included in the diff view is what actually gets staged and committed. A desync here means a user could unknowingly commit lines they explicitly deselected (or omit lines they selected), which is a form of silent corruption of what the user commits — the file ends up in the object graph with content the user did not intend, without any error being surfaced (the underlying `git apply --cached` call in `applyPatchToIndex` succeeds because the resulting patch is syntactically well-formed even though it no longer matches the user's true intent).

### Likelihood Explanation
This requires the working-tree content of a partially-selected, unviewed file to change between selection time and commit time — e.g. through an external tool, a Git LFS smudge/clean filter (which Desktop pre-configures on install), a watch/build process, or another concurrent Git operation. In multi-file, real-world workflows where users select individual lines across several files and then leave the "Changes" tab open for a while before committing, this window is not implausible, but it does require a code path that mutates tracked file contents outside of the current, actively-viewed selection — which is a materially weaker trigger than a purely remote/attacker-controlled input, and arguably borders on the "local/concurrent modification" pattern this analysis is supposed to reject.

### Recommendation
Before generating the patch in `applyPatchToIndex`, revalidate the file's `DiffSelection` against the freshly fetched diff's actual hunk/line structure (the same "selectable lines" reconciliation already implemented in `app-store.ts`'s `updateChangesWorkingDirectoryDiff`), for every file being staged — not just the currently viewed one — and abort/re-prompt the user if the diff has materially changed since the selection was made, rather than silently reapplying stale indices.

### Proof of Concept
1. Modify a tracked file and open it in the Changes view; Desktop computes a `Diff` with hunk `unifiedDiffStart` offsets based on this content.
2. Select only a subset of the added/removed lines (a `Partial` `DiffSelectionType`), producing a `DiffSelection` bitmap keyed to those offsets.
3. Without re-viewing the file's diff in Desktop, have the working-tree content of that same file change externally (e.g., a filter driver, another process, or a second git operation) such that the number/order of hunks or lines shifts.
4. Trigger a commit. `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches a new diff and `formatPatch` (`app/src/lib/patch-formatter.ts:143-170`) reapplies the old selection bitmap to the new hunk layout, producing a patch whose included/excluded lines no longer match what the user selected in the UI, which is then applied to the index and committed without error.

Given the uncertainty in establishing a purely remote/attacker-controlled trigger for this specific TOCTOU pattern, treat this as a lower-confidence analog rather than a definitive finding equivalent in strength to the original report.
