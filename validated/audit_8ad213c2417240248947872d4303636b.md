### Title
Untrusted `ReceivedOutput` bytes can encode a mismatched offset and output, causing later signing setup to reject the input - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, `TxOut`, and `OutPoint` without verifying that `offset` derives the key committed to by `output.script_pubkey`. The invariant is only checked later by `SignableTransaction::multisig`, which returns `None` when `p2tr_script_buf(key + offset)` does not equal the recorded output script. An unprivileged party supplying malformed serialized output data can therefore cause an input represented as spendable to become unusable during transaction creation.

### Finding Description
`ReceivedOutput` is documented as “a spendable output” and stores both the scalar needed to reach the spending key and the Bitcoin output being spent. Its deserialization function reads each field independently and immediately returns the reconstructed object, with no consistency check between `offset` and `output.script_pubkey`. [1](#0-0) [2](#0-1) 

The consistency requirement exists, but it is deferred to `SignableTransaction::multisig`: each input offset is applied to the threshold keys, the resulting key is converted to its expected P2TR script, and the function returns `None` unless that script equals the prevout’s script. [3](#0-2) 

This mirrors the asymmetric-validation bug class: an earlier boundary accepts state that a later operation requires to satisfy an additional invariant. The relevant earlier boundary is attacker-controlled bytes passed to `ReceivedOutput::read`; the later operation is spend construction/signing through `SignableTransaction::new` and `SignableTransaction::multisig`. [4](#0-3) [5](#0-4) 

### Impact Explanation
A malformed serialized `ReceivedOutput` can be accepted as an input record even though no valid machine can be constructed for it. When the wallet attempts to spend it, `multisig` rejects the input by returning `None`, preventing the transaction-signing path from producing witnesses for that input. [6](#0-5) 

If this object crosses a trust boundary and is persisted or scheduled before `multisig` is called, the mismatch can make affected funds appear spendable to earlier accounting/selection logic while being unusable in the final signing path. This is a concrete “funds reported received that are not spendable” condition rather than a purely cosmetic validation mismatch. [1](#0-0) [6](#0-5) 

### Likelihood Explanation
The attacker only needs to control serialized `ReceivedOutput` bytes consumed by `ReceivedOutput::read`: a canonical scalar, any consensus-valid `TxOut`, and any consensus-valid `OutPoint`. The parser performs no binding check, so mismatch creation is deterministic and does not require race conditions, malformed encodings, collusion, or validator compromise. [2](#0-1) 

The inconsistency is guaranteed to be caught only once the matching threshold keys and transaction context are available, because `read` does not receive the base group key needed to evaluate `key + offset`. [2](#0-1) [5](#0-4) 

### Recommendation
Do not treat `ReceivedOutput::read` as establishing the “spendable output” invariant. Either restrict deserialization to trusted internal state, rename/document it as unchecked deserialization, or add a validation step at the ingestion boundary that applies the claimed offset to the active threshold keys and requires the resulting `p2tr_script_buf` to equal `output.script_pubkey`. The validation should occur before the output is persisted, selected as an input, or reported as spendable; `SignableTransaction::multisig` should remain a defense-in-depth check. [1](#0-0) [7](#0-6) 

### Proof of Concept
```rust
use bitcoin::{Amount, OutPoint, ScriptBuf, TxOut};
use frost::{curve::Secp256k1, Ciphersuite};
use serai_bitcoin::wallet::ReceivedOutput;

// Any scalar and any P2TR-looking or arbitrary script are accepted.
let mut bytes = Vec::new();
bytes.extend(Secp256k1::F::ZERO.to_repr());
bytes.extend(bitcoin::consensus::encode::serialize(&TxOut {
  value: Amount::from_sat(10_000),
  script_pubkey: ScriptBuf::new(), // does not have to equal p2tr(key + offset)
}));
bytes.extend(bitcoin::consensus::encode::serialize(&OutPoint::null()));

let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

// The inconsistent object is constructed successfully.
assert_eq!(output.offset(), Secp256k1::F::ZERO);
assert_eq!(output.output().script_pubkey, ScriptBuf::new());
```

When this object is placed in `SignableTransaction::new`, it is incorporated into `offsets` and `prevouts`; afterward, `multisig` derives `keys.offset(offset)` and returns `None` because the derived P2TR script is not `ScriptBuf::new()`. [4](#0-3) [8](#0-7) [6](#0-5)

  /// Read a ReceivedOutput from a generic satisfying Read.
  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  /// Create a multisig machine for this transaction.
  ///
  /// Returns None if the wrong keys are used.
  pub fn multisig(self, keys: &ThresholdKeys<Secp256k1>) -> Option<TransactionMachine> {
    let mut sigs = vec![];
    for i in 0 .. self.tx.input.len() {
      let offset = keys.clone().offset(self.offsets[i]);
      if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
        None?;
      }

      sigs.push(AlgorithmMachine::new(Schnorr::new(), keys.clone().offset(self.offsets[i])));
    }

    Some(TransactionMachine { tx: self, sigs })
  }
