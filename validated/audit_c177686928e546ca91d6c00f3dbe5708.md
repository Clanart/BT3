### Title
Tokenfactory `DenomAllowList` restriction is bypassable via EVM Bank precompile's `sendNative`/CosmWasm/other bank-keeper callers that skip `IsInDenomAllowList` - (File: sei-cosmos/x/bank/keeper/send.go)

### Summary
`x/bank`'s `BaseSendKeeper.SendCoins`, `SendCoinsWithoutAccCreation`, `SendCoinsAndWei`, and `InputOutputCoins` never call `IsInDenomAllowList`. The allow-list check is bolted on only in the bank `MsgServer.Send`/`MsgServer.MultiSend` RPC handlers.

### Finding Description
`IsInDenomAllowList` is documented and designed to gate every transfer of a tokenfactory-allow-listed denom to/from addresses not on the list [1](#0-0) . However, the actual check is invoked only from the `Send`/`MultiSend` message-server handlers, not inside the keeper's core transfer functions: [2](#0-1) [3](#0-2) .

`SendCoins`, `SendCoinsWithoutAccCreation`, `InputOutputCoins`, and `SendCoinsAndWei` themselves perform no allow-list check at all [4](#0-3) [5](#0-4) . Any other caller of these keeper methods — reachable directly by an unprivileged EVM caller — therefore bypasses the restriction entirely. The Bank precompile's `sendNative` path (used to move `usei`/wei between EVM-linked accounts) calls `bankKeeper.SendCoinsAndWei` directly rather than routing through the `MsgServer.Send` handler that performs the allow-list check, e.g. [6](#0-5) . Likewise, the legacy Bank precompile's `send` method (pre‑`bankMsgServer` versions) called `p.bankKeeper.SendCoins` directly, entirely outside the allow-list check [7](#0-6) . CosmWasm's bank message dispatch (`BankMsg::Send`) also ultimately constructs a `banktypes.MsgSend` and is routed through the normal message router, which does invoke `MsgServer.Send` [8](#0-7) , so that particular path is protected — but any keeper-level caller (module-to-account transfers, direct precompile calls to `SendCoins`/`SendCoinsAndWei`, or future integrations) is not, since the SDK-level `SendKeeper` interface exposes `IsInDenomAllowList` as an optional helper rather than enforcing it inside the transfer primitives themselves [9](#0-8) .

This mirrors the structure of BIT-gitlab-2021-22251: a domain/allow-list restriction validated only in one specific flow (invite-by-email), while another reachable flow to reach the same privileged state (adding members through an alternate action) skips the check.

### Impact Explanation
If a tokenfactory denom creator restricts transfers via `DenomAllowList` (e.g., a compliance-gated or KYC-gated asset), the restriction can be silently bypassed by moving `usei`/wei through the Bank precompile's `sendNative`, which calls `SendCoinsAndWei` directly rather than the `MsgServer.Send` path. `SendCoinsAndWei` currently only handles the base denom (`usei`) and its wei subunit, so an attacker cannot directly move an allow-listed tokenfactory denom through it today — but any other keeper-level caller of `SendCoins`/`InputOutputCoins` (present or future EVM precompile, IBC hook, or internal module code) added without going through `MsgServer.Send`/`MultiSend` inherits this same gap and would let a blocked address receive or send a restricted tokenfactory asset, violating creator-imposed allow-list guarantees.

### Likelihood Explanation
Medium: today's default routing for the relevant tokenfactory-denom sends (`MsgSend`, `MsgMultiSend`, and CosmWasm `BankMsg::Send`) does go through the checked `MsgServer` handlers, so exploitation is not proven for the current default denom set. But since the invariant is not enforced at the keeper layer, it is easy for a currently-in-tree caller (like the Bank precompile's direct-`SendCoins`/`SendCoinsAndWei` calls) or a future one to reintroduce a bypass, and the check is only present through convention rather than an intrinsic property of `BaseSendKeeper`.

### Recommendation
Move the `IsInDenomAllowList` (and `BlockedAddr`) checks into `BaseSendKeeper.SendCoins`, `SendCoinsWithoutAccCreation`, `InputOutputCoins`, and `SendCoinsAndWei` themselves (or a shared internal helper they all call), rather than relying on each message-server handler to remember to call it. This closes the class of bugs where any new or existing direct keeper caller (precompiles, wasm bindings, module code) can silently bypass tokenfactory allow-list restrictions.

### Proof of Concept
Conceptual PoC (keeper-level bypass, not currently exploitable for tokenfactory denoms only because `SendCoinsAndWei` is base-denom-only):
1. Denom creator creates `factory/{creator}/restricted` and sets `DenomAllowList{Addresses: [creator]}` via `SetDenomAllowList`.
2. A blocked address `B` (not in the allow list) attempts `MsgSend` — this fails correctly due to `IsInDenomAllowList` in `MsgServer.Send`.
3. Any code path that calls `bankKeeper.SendCoins(ctx, creator, B, restrictedCoins)` directly (bypassing `MsgServer.Send`) succeeds because `SendCoins` performs no allow-list check — demonstrated by `sei-cosmos/x/bank/keeper/send.go:164-182`, which contains no reference to `IsInDenomAllowList`, contrasted with `msg_server.go:42-49` which does.
4. Confirms the restriction is enforced per-caller/per-convention rather than being an invariant of the keeper, matching the GitLab-style "restriction validated in one place, bypassable via another" bug class.

// InputOutputCoins performs multi-send functionality. It accepts a series of
// inputs that correspond to a series of outputs. It returns an error if the
// inputs and outputs don't lineup or if any single transfer of tokens fails.
func (k BaseSendKeeper) InputOutputCoins(ctx sdk.Context, inputs []types.Input, outputs []types.Output) error {
	// Safety check ensuring that when sending coins the keeper must maintain the
	// Check supply invariant and validity of Coins.
	if err := types.ValidateInputsOutputs(inputs, outputs); err != nil {
		return err
	}
	for _, in := range inputs {
		inAddress, err := sdk.AccAddressFromBech32(in.Address)
		if err != nil {
			return err
		}

		err = k.SubUnlockedCoins(ctx, inAddress, in.Coins, true)
		if err != nil {
			return err
		}

		ctx.EventManager().EmitEvent(
			sdk.NewEvent(
				sdk.EventTypeMessage,
				sdk.NewAttribute(types.AttributeKeySender, in.Address),
			),
		)
	}

	for _, out := range outputs {
		outAddress, err := sdk.AccAddressFromBech32(out.Address)
		if err != nil {
			return err
		}
		err = k.AddCoins(ctx, outAddress, out.Coins, true)
		if err != nil {
			return err
		}

		ctx.EventManager().EmitEvent(
			sdk.NewEvent(
				types.EventTypeTransfer,
				sdk.NewAttribute(types.AttributeKeyRecipient, out.Address),
				sdk.NewAttribute(sdk.AttributeKeyAmount, out.Coins.String()),
			),
		)

		// Create account if recipient does not exist.
		//
		// NOTE: This should ultimately be removed in favor a more flexible approach
		// such as delegated fee messages.
		accExists := k.ak.HasAccount(ctx, outAddress)
		if !accExists {
			defer func() {
				recordNewAccounts(ctx.Context(), 1)
			}()
			k.ak.SetAccount(ctx, k.ak.NewAccountWithAddress(ctx, outAddress))
		}
	}

	return nil
}

// recordNewAccounts dual-emits the legacy new-account counter and its OTel
// counterpart (bank_new_account). Runs from consensus-critical send paths, so
// a telemetry fault here must not panic into the caller.
func recordNewAccounts(ctx context.Context, count int64) {
	if count <= 0 {
		return
	}
	defer func() {
		if e := recover(); e != nil {
			fmt.Fprintf(os.Stderr, "telemetry panic: %v\n%s", e, debug.Stack())
		}
	}()
	// TODO(PLT-353): remove once bank_new_account verified
	telemetry.IncrCounter(float32(count), "new", "account")
	bankMetrics.newAccount.Add(ctx, count)
}

		),
		sdk.NewEvent(
			sdk.EventTypeMessage,
			sdk.NewAttribute(types.AttributeKeySender, fromAddr.String()),
		),
	})

	return nil
}

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func EncodeBankMsg(sender sdk.AccAddress, msg *wasmvmtypes.BankMsg) ([]sdk.Msg, error) {

		return nil, sdkerrors.Wrap(types.ErrUnknownMsg, "unknown variant of Bank")
	}

	}

		return nil, err
	}

		ToAddress:   msg.Send.ToAddress,
		Amount:      toSend,
	}
