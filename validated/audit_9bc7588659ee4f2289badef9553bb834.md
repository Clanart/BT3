### Title
Rate-limit counter exhaustion allows unprivileged/prompt-injected commits to silently disable the automated security-review hook - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The `security-guidance` plugin's commit/push security-review hooks are gated by a shared, per-session rolling-hour counter (`atomic_check_rate_limit`). Any sequence of `git commit` invocations — including ones driven by untrusted, prompt-injected instructions with no special privilege — increments this counter. Once the cap is reached, all subsequent commit/push reviews in that window are silently skipped (fail-open), so a genuinely malicious commit made shortly after can land without ever being scanned. This mirrors the Lido `KEYS_OP_INDEX_POSITION` pattern: an unprivileged, repeatable action increments a shared counter that gates a separate, higher-value operation, allowing that operation to be blocked/bypassed.

### Finding Description
`atomic_check_rate_limit` implements a rolling-window counter keyed by `(session_id, key)` and is fail-open when the state store is unavailable: [1](#0-0) 

It gates `handle_commit_review_posttooluse` — every `git commit` triggers this PostToolUse hook, which burns a `"CommitReview"` slot before the LLM scan runs, and skips the review entirely (silently, with only a debug log and `skip_reason=23`) once `MAX_COMMIT_REVIEWS_PER_HOUR` is reached: [2](#0-1) 

The identical pattern gates `handle_push_sweep_posttooluse`: [3](#0-2) 

There is no differentiation between "legitimate" commits and low-value/junk commits generated to burn the quota — any code path that causes Claude to invoke `git commit` repeatedly (e.g. content processed by Claude from an untrusted file, issue, PR description, or web page instructing it to make many small/no-op commits) can exhaust the shared counter. Once exhausted, the review that would otherwise scan a diff for injected vulnerabilities (`analyze_code_security` / agentic review) and force Claude to fix them via `sys.exit(2)` no longer runs for the rest of the rolling window: [4](#0-3) 

### Impact Explanation
This is the same bug class as the report: an unprivileged, repeatable action increments a shared index/counter that gates a security-relevant function, and exhausting it disables that function for others sharing the same window. Here, the disabled function is the automated LLM-based commit/push security review — a defense-in-depth control designed to catch vulnerable or malicious code (including code introduced via prompt injection) before/while it is committed or pushed. Exhausting the quota lets a subsequently introduced malicious diff (e.g., backdoored code, secret exfiltration, unsafe eval) slip past this control silently, with no user-visible warning that reviews are being skipped (only a `debug_log` and a metrics field).

Impact is more limited than the Lido analog because the review is explicitly documented as "supplementary feedback, not a replacement" (see `CONTINUATION_SUFFIX`) and is scoped per-session rather than protocol-wide, and it does not bypass any hard authorization/approval gate (e.g., PreToolUse command approval) — only a best-effort detective control.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to get Claude to perform enough `git commit` invocations within the rolling window (`COMMIT_REVIEW_RATE_WINDOW_S`) to reach `MAX_COMMIT_REVIEWS_PER_HOUR`, which is plausible via prompt injection from untrusted content Claude reads (issue text, file contents, tool output) instructing it to make many trivial commits before the actual malicious change. It does not require any credential or privilege beyond what a normal Claude Code session already has.

### Recommendation
- Do not silently fail-open when the review rate limit is hit; surface a clear, persistent warning to the user that security review coverage was skipped for subsequent commits/pushes in the window.
- Consider decoupling "cheap junk commits" from the review budget (e.g., only counting commits with non-trivial diffs), or increasing granularity so an attacker cannot cheaply burn the quota with no-op commits.
- Add an explicit audit trail/metric surfaced to the user (not just `debug_log`/telemetry) when `skip_reason=23` triggers repeatedly in a short time, since that pattern indicates possible deliberate quota exhaustion.

### Proof of Concept
Not independently executable from static analysis alone; the exhaustion path is directly supported by code: repeatedly invoking `git commit` (any content) drives `handle_commit_review_posttooluse` → `atomic_check_rate_limit(session_id, "CommitReview", MAX_COMMIT_REVIEWS_PER_HOUR, COMMIT_REVIEW_RATE_WINDOW_S)` until `_allowed` becomes `False`, at which point line 1213's `emit_metrics({"skipped": True, "skip_reason": 23, ...})` / `sys.exit(0)` path is taken for all further commits in the window, per [5](#0-4) , confirming no LLM review runs against the next (potentially malicious) commit.

def atomic_check_rate_limit(session_id, key, max_per_window, window_s):
    """Rolling-window rate limit: allow at most `max_per_window` calls per
    `window_s` seconds, per (session_id, key).

    Returns (allowed: bool, count_in_window: int). count_in_window is the
    post-decision count (i.e., includes this call if allowed) so callers can
    emit it directly as a telemetry gauge.

    Replaces session-lifetime `atomic_check_counter` for commit-review and
    push-sweep. Telemetry showed a small but persistent share of sessions hit
    the lifetime cap, and those were multi-day persistent sessions that then
    lost coverage for many subsequent commits — not burst abusers. A rolling
    hour keeps the same cost ceiling for any 1h window while letting long
    sessions regain coverage.

    State key: rate_limits: {"<key>": [ts, ts, ...]}. Timestamps are pruned
    on every call so the list is bounded by max_per_window; no migration
    needed from the old `counters` dict — different key.
    """
    import time as _time
    now = _time.time()
    cutoff = now - window_s

    def _check(state):
        buckets = state.setdefault("rate_limits", {})
        ts_list = buckets.get(key, [])
        # Prune; tolerate non-numeric junk from a corrupted state file.
        ts_list = [t for t in ts_list if isinstance(t, (int, float)) and t > cutoff]
        if len(ts_list) >= max_per_window:
            buckets[key] = ts_list
            return False, len(ts_list)
        ts_list.append(now)
        buckets[key] = ts_list
        return True, len(ts_list)

    result = with_locked_state(session_id, _check)
    # State unavailable → fail-open (same posture as atomic_check_counter).
    return result if result is not None else (True, 0)
