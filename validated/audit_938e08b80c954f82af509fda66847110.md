### Title
Unsanitized PR head ref name from GitHub API used to construct git branch/ref names bypasses the same validation applied to deep-link branch names - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop validates a branch name that arrives via a deep link (`x-github-client://openrepo/...`) with `testForInvalidChars` before using it in any git operation, but the equivalent value taken from a Pull Request object returned by the GitHub API (`pullRequest.head.ref`) is passed straight into git ref construction and branch creation with no equivalent check. This mirrors the report's root cause: a validation guard exists, but it is applied on the wrong data path, so the actual value that reaches the sensitive sink is unchecked.

### Finding Description
`parseAppURL` explicitly filters the `branch` query parameter for a deep link with `testForInvalidChars(branch)` before it is allowed to reach `IOpenRepositoryFromURLAction`: [1](#0-0) 

That validated value later reaches `checkoutLocalBranch`/git checkout via `openBranchNameFromUrl`: [2](#0-1) 

However, the parallel "open PR" flow pulls the ref name straight from the PR object served by the GitHub API — an object that is entirely attacker-controlled because any user can open a pull request from their own fork with an arbitrary head branch name: [3](#0-2) 

That unsanitized `headRefName` is threaded straight into `_checkoutPullRequest` → `_findPullRequestBranch`, where it is concatenated into `remoteRef` and passed as the starting point for `_createBranch`, as well as interpolated directly into error messages shown to the user: [4](#0-3) 

The same unchecked ref name is also used by `checkoutPullRequest` in the "Checkout this PR" UI action, taking it from `pullRequest.head.ref` on the API object: [5](#0-4) 

No call in this chain applies `testForInvalidChars` (or any other ref-name sanitizer) to `headRefName`, unlike the deep-link path that explicitly guards the semantically identical value.

### Impact Explanation
The consequence is bounded by how `_createBranch`/underlying git calls handle the string (I was not able to inspect `app/src/lib/git/branch.ts` in this session to confirm whether arguments are passed to git as an argv array or via any string concatenation, so I cannot conclusively demonstrate command/argument injection). What is concretely confirmed from local code is: (1) the same class of value is validated on one entry path and not on another, breaking the intended invariant that "ref/branch names reaching git operations are checked for invalid/dangerous characters," and (2) the unchecked value is used verbatim inside a locally-created branch name (`pr/${prNumber}` uses the number, but `remoteRef` embeds the raw ref) and inside user-facing error strings. At minimum this allows a malicious fork owner to corrupt local ref-naming/state or produce misleading UI text when their PR is checked out from within Desktop; if `headRefName` can begin with `-` and is ever passed as a bare argument to a git invocation elsewhere in the checkout chain, it could escalate to git option/argument injection.

### Likelihood Explanation
Likelihood is Medium: no unusual user action is required beyond checking out a pull request or clicking "Open in Desktop" for a PR link — both are standard, expected Desktop workflows — and the attacker fully controls the PR head ref name since it's just the branch name of their own fork.

### Recommendation
Apply the same ref-name validation used in `parse-app-url.ts` (`testForInvalidChars`, or a stricter git-ref-name validator) to `pullRequest.head.ref` at the point it is received from the API, before it is used in `_checkoutPullRequest`/`_findPullRequestBranch`/`checkoutPullRequest`, so all code paths that end up calling git with a ref name enforce the identical guarantee instead of relying on validation that only exists in the deep-link path.

### Proof of Concept
1. Attacker forks a public repository and creates a branch with a name containing characters normally rejected by `testForInvalidChars` (e.g. control characters, or a leading `-`), then opens a pull request from that branch.
2. Victim, using GitHub Desktop, opens that PR (via "Open in Desktop" link or the in-app "Checkout this PR" action).
3. `dispatcher.ts`'s `openPullRequestFromUrl`/`checkoutPullRequest` reads `pullRequest.head.ref` from the GitHub API response and passes it unchecked into `appStore._checkoutPullRequest` → `_findPullRequestBranch`, where it is embedded into `remoteRef` and into the branch created via `_createBranch`, and into error messages surfaced to the victim — none of which is subject to the `testForInvalidChars` check that would have applied had the same branch name been supplied through the `x-github-client://openrepo` deep-link path.

**Caveat:** I could not access `app/src/lib/git/branch.ts` / the underlying `git()` argv construction in this session to conclusively verify whether this asymmetry escalates beyond ref-name/state corruption and misleading error text into git flag/argument injection — that would need to be confirmed by a follow-up session with full repo access.

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

  public async _checkoutPullRequest(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<void> {
    const prBranch = await this._findPullRequestBranch(
      repository,
      prNumber,
      headRepoOwner,
      headCloneUrl,
      headRefName
    )
    if (prBranch !== undefined) {
      await this._checkoutBranch(repository, prBranch)
      this.statsStore.increment('prBranchCheckouts')
    }
  }

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }

    return existingBranch
  }
