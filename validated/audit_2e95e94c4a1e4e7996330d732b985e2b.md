### Title
Copilot conflict-resolution hunk reassembly can silently splice a resolution into the wrong conflict region when a file contains malformed/look-alike merge markers - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`Dynamo4626.vy`'s bug was an invariant assertion (`total_strategy_fees_claimed + total_yield_fees_claimed <= total_fees_ever`) that could be violated by a legitimate, attacker-independent state transition (partial loss), causing a hard revert instead of a graceful degrade — corrupting the *availability* of the vault rather than its accounting values. The Desktop analog is not a revert/DoS case (rejected by scope) but a **silent value-corruption** case with the same root cause pattern: two independently-computed counters/positions that are assumed to always stay in lockstep, with no cross-check when they diverge. In `reassembleResolvedFile`, the per-hunk resolutions returned by the Copilot model are spliced into the working-directory file **purely by ordinal position** (`hunkIndex`), based on a private, ad-hoc regex scan of `<<<<<<<`/`=======`/`>>>>>>>` lines [1](#0-0) . Nothing in this function, nor in `validateResolutionPaths`, verifies that the number/order of conflict blocks this scan finds matches the number/order of hunks the context-builder presented to the model. `validateResolutionPaths` only checks that the *count* of hunks returned by the model equals the *expected count* from `IFileConflictContext.hunks.length` — it never re-validates against the raw file at splice time [2](#0-1) .

### Finding Description
`reassembleResolvedFile` walks the on-disk file line by line and, for every line matching `^<{7}(?:\s|$)`, looks ahead for a `=======` separator and a `>>>>>>>` closer [3](#0-2) . If either is missing, the block is deemed "malformed" and passed through untouched **without incrementing `hunkIndex`** — but if it *is* well-formed, the corresponding `hunkResolutions[hunkIndex]` entry is spliced in and `hunkIndex` is incremented [4](#0-3) .

This ordinal-matching logic is completely independent from whatever routine originally built `IFileConflictContext.hunks` (the "Conflict 1 of N" list shown to the model in the prompt, per the system prompt's field rules) [5](#0-4) . The two parsers only need to agree on total count for `validateResolutionPaths` to pass — that check compares `resolution.hunks.length` to `expectedHunkCounts.get(path)` and nothing more [6](#0-5) .

The invariant this code silently assumes — *"the Nth marker block this scanner finds is the same conflict as the Nth hunk the context-builder extracted and the model was shown"* — can be broken by attacker-controlled repository content:
- A file that legitimately contains 7+ `<`/`=`/`>` sequences as literal text (e.g. a README/tutorial about Git merge conflicts, a diff/patch fixture file, or generated documentation) sitting *outside* the real conflict region. If a genuine conflict is introduced (via a crafted PR/branch merged by the victim) in the same file, the ad-hoc regex scanner can pick up extra or reordered "conflict blocks" that the context-builder's own parser did not surface as hunks (or surfaced differently), while the total count coincidentally still matches `expectedHunkCounts`.
- Any divergence between the two hunk-detection passes over the same raw content (e.g., different handling of a conflict nested inside another due to a criss-cross merge, or Windows/Unix line-ending edge cases affecting where a block boundary falls) shifts `hunkIndex` for every subsequent hunk in the file.

When this happens, `reassembleResolutions` (the caller) writes the reassembled content straight into the file with **no additional verification** [7](#0-6) , and this becomes the content the user reviews and commits.

### Impact Explanation
The corrupted value is the final on-disk/committed file content for a conflicted file resolved via Copilot. Because the mismatch is silent — no exception, no warning surfaced to the user — the user can commit and push code where:
- A resolution meant for conflict block #2 is written into conflict block #3 (or vice versa), potentially re-inserting code the user thought was dropped, dropping a security fix that was supposed to be kept, or juxtaposing unrelated logic in a way that changes program behavior.
- The corruption is indistinguishable from a "normal" AI resolution in the diff review UI unless the user manually re-reads every hunk carefully, defeating the purpose of the feature (fast, trusted conflict resolution).

This matches the required impact class: "silent corruption of what the user commits or pushes," triggered by content in a cloned/fetched/merged repository under attacker influence (a maliciously crafted file with marker-like text, or a crafted branch designed to produce nested/anomalous conflicts).

### Likelihood Explanation
Moderate-to-low but plausible. It requires:
1. The victim to use the Copilot AI conflict-resolution feature (opt-in, but increasingly promoted UI flow).
2. A file in the repository that either already contains marker-like text sequences, or a merge/rebase/cherry-pick scenario producing an atypical conflict structure (nested conflicts from criss-cross merges are a known Git edge case, not exotic).
3. No manual full review by the user before committing — plausible given the feature's value proposition is trusting the AI-assembled diff.

It does not require local access, admin rights, or leaked credentials — only that the user merges/fetches attacker-influenced content and invokes the AI resolver, consistent with the valid-impact criteria.

### Recommendation
- Have the context-builder (whatever produces `IFileConflictContext.hunks`) and `reassembleResolvedFile` share a single conflict-marker parser, so hunk boundaries can never diverge between the two passes.
- After reassembly, re-scan the produced blocks and assert the number of well-formed conflict blocks consumed equals `hunkResolutions.length` exactly (not just that `hunkIndex` reaches the end); if they don't match, fail the operation and surface the file as "skipped — could not safely reassemble" rather than silently writing best-effort output.
- Optionally, tag each `IHunkResolution` with a content fingerprint (e.g., hash of the original `oursContent`/`theirsContent`) at context-build time, and verify that fingerprint against the block being replaced at splice time, rather than relying purely on ordinal position.

### Proof of Concept
1. Attacker crafts a branch/PR that, when merged by the victim, produces a conflict in `docs/CONTRIBUTING.md` (or any file) that already contains an *unrelated* literal block of text resembling merge markers, e.g.:
   ```
   Example of a conflict:
   <<<<<<< example
   old
   =======
   new
   >>>>>>> example
   ```
   placed just before or after the real conflict block introduced by the merge.
2. The victim runs the Copilot "Resolve with AI" feature. The context-builder computes `IFileConflictContext.hunks` from the real conflict (say, 1 hunk) and prompts the model accordingly; the model returns exactly 1 hunk resolution, satisfying `validateResolutionPaths`.
3. `reassembleResolvedFile`'s independent regex scan encounters the example block's `<<<<<<< example` first (matches `^<{7}(?:\s|$)`), finds a well-formed `=======`/`>>>>>>>` pair (because the example text is itself syntactically well-formed), consumes `hunkResolutions[0]` for it, and increments `hunkIndex` to 1 — leaving the *real* conflict block later in the file with `hunkIndex` now out of range, causing `if (hunkIndex < hunkResolutions.length)` to be false and the real conflict marker text to be silently dropped/passed through unresolved, while the unrelated example text gets replaced with the model's resolved content.
4. The user sees a file that "the AI resolved" and commits it; the actual conflict markers may remain in the shipped file, or the model's resolution text lands in the wrong location — either way, the committed content is silently wrong, with no error from `validateResolutionPaths` or `reassembleResolutions`.

Note: I was not able to fully inspect the exact hunk-extraction implementation in `app/src/lib/copilot-conflict-context.ts` within the available tool budget (only confirmed via `grep_search` that it independently defines its own hunk/marker-related logic, separate from `reassembleResolvedFile`'s scanner). If that file happens to reuse the exact same line-scanning routine as `reassembleResolvedFile`, the two parsers would be less likely to diverge in the exact PoC above, though the core design flaw (no re-validation against the raw file at splice time, only a count check) remains present regardless.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
}
