The bug class here is "missing validation on attacker-influenced inputs reaching a privileged operation" — in Serai, the analogous privileged operation is threshold signing of a Bitcoin transaction constructed from a deserialized `ReceivedOutput`. `ReceivedOutput::read` accepts arbitrary bytes, and the signing path only validates the prevout's `script_pubkey`, not its value or outpoint.

### Title
Attacker-controlled `ReceivedOutput` fields cause the threshold multisig to sign an invalid/unintended transaction (prevout value and outpoint are never authenticated) - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction` treats the `TxOut` value and `OutPoint` inside each `ReceivedOutput` as authentic. When a `ReceivedOutput` is reconstructed from untrusted bytes via `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122-134`), an attacker can claim any value and any outpoint. `SignableTransaction::multisig` only checks that the claimed prevout's `script_pubkey` equals the offset group key's P2TR script; the claimed `value` and `outpoint` are never authenticated against chain data. The signers then produce FROST/BIP-340 signature shares over a sighash committing to attacker-chosen prevout amounts and attacker-chosen UTXOs.

### Finding Description
- `ReceivedOutput::read` deserializes `offset`, `output: TxOut`, and `outpoint: OutPoint` straight from the reader with no binding to actual chain state — `networks/bitcoin/src/wallet/mod.rs:122-133`.
- `SignableTransaction::new` sums `input.output.value` for fee/change math (`send.rs:175`), builds `tx_ins` from `input.outpoint` (`send.rs:180`), and stores `prevouts` verbatim (`send.rs:253`).
- `multisig` verifies only the script: `if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey { None? }` (`send.rs:277`). Value and outpoint are unchecked.
- `sign` then signs `cache.taproot_key_spend_signature_hash(i, &Prevouts::All(&self.tx.prevouts), TapSighashType::Default)` (`send.rs:375-390`), so every signature cryptographically commits to the attacker-supplied amounts, while the inputs commit to attacker-supplied outpoints.

Because BIP-341 key-path sighashes commit to the real prevout amounts, a signature produced over a forged value is invalid against the real UTXO: the signed transaction can never be accepted by the network. Likewise a fabricated or duplicated outpoint yields a transaction spending a nonexistent/foreign input.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` and have them reach `SignableTransaction::new`/`multisig`/`sign` causes the honest threshold validators to produce a full transaction signature set over an attacker-drafted, provably unbroadcastable message. Concretely:

- **Unintended-message signing**: signers emit valid signature shares and a "completed" `Transaction` (`send.rs:397`, `417-427`) that the Bitcoin network will always reject — either the sighash prevout amounts mismatch the real UTXOs, or the referenced outpoints don't exist/are duplicated.
- **Fee/change corruption**: `input_sat`, `needed_fee`, and the change output (`send.rs:215-235`) are all computed from the forged value, so the generated outputs/change encode attacker-chosen fictitious amounts.
- **Signing-session burn**: each attempt consumes a fresh FROST preprocess round; repeated forged inputs let the attacker waste coordinator/validator signing rounds at no cost.

Severity: Medium — it is a concrete "signing of an unintended message" primitive reachable from untrusted bytes, but it does not by itself leak key material or produce a spendable-to-attacker output (all prevouts must still carry the multisig's own script_pubkey).

### Likelihood Explanation
The vulnerability requires a path where a `ReceivedOutput` comes from untrusted bytes rather than from `Scanner::scan_transaction` (which builds it from real chain data, `mod.rs:199-213`). Wherever the wallet/processor round-trips outputs through `ReceivedOutput::read`/`Output::read` (e.g., `processor/src/networks/bitcoin.rs:156`) from data an external party can influence, the check gap is live. The multisig script check gives a false sense of authentication — it authenticates the *script* but not the *value* or *location* of the coin being spent.

### Recommendation
Authenticate the full prevout, not just the script:
- In `SignableTransaction::multisig` (or `new`), additionally confirm each `input.outpoint` resolves to a UTXO whose `TxOut` exactly equals `input.output` (query the node's `gettxout`/tx index), rather than trusting deserialized fields.
- Reject duplicate outpoints in `SignableTransaction::new` before computing `input_sat` (currently `input_sat` double-counts duplicates, `send.rs:175`).
- Document `ReceivedOutput` as untrusted until cross-checked against chain data, mirroring how the Kyverno fix adds URL validation where none existed.

### Proof of Concept

use bitcoin::{OutPoint, TxOut, Amount, Txid, hashes::Hash};
use frost::curve::Secp256k1;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};

// Attacker crafts bytes for ReceivedOutput::read:
//  - offset: Scalar::ZERO (external address path)
//  - output: TxOut { script_pubkey: <group P2TR script>, value: Amount::from_sat(1_000_000_000) }
//    (claims 10 BTC; the real UTXO may hold 10_000 sats, or not exist at all)
//  - outpoint: arbitrary/real-but-wrong txid:vout
let forged = ReceivedOutput::read(&mut &attacker_bytes[..]).unwrap();

// Fee math, change and prevouts all consume the forged value
let tx = SignableTransaction::new(
  vec![forged],
  &payments,
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap();

// multisig() succeeds: forged.output.script_pubkey == p2tr_script_buf(group_key)
let machine = tx.clone().multisig(&keys).unwrap();

// Signers produce BIP-340 shares committing to the forged prevout amount —
// the completed Transaction is permanently invalid on-chain (bad sighash /
// nonexistent input), yet `complete` returns Ok and shares are published.
