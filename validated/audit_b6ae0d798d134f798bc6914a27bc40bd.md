### Title
False-blame claims publicly reveal a valid secret share via `EncryptionKeyProof`'s disclosed ECDH key - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The Glances advisory is about reusable credential material (a derived auth secret) being embedded in data returned to unauthenticated callers. The PedPoP analog: when a participant's `calculate_share` fails, they publish an `EncryptionKeyProof` — which contains the raw ECDH shared-secret point `key` — to the coordinator's `VerifyBlame` handler. The ECDH key alone is sufficient to decrypt the targeted `EncryptedMessage`. Because validity of the share is only determined *after* decryption inside `blame_internal`, an accuser can attach a proof for a *perfectly valid* share, causing every observer of the blame procedure to recover that secret share in the clear, while the accusation is adjudicated "recipient at fault" only after the share is already exposed.

### Finding Description
`Encryption::decrypt` always returns an `EncryptionKeyProof` pairing the ECDH result `key` with a DLEq proof that `key = enc_key * msg.key` [1](#0-0) . `calculate_share` stores one of these proofs per sender and returns it inside `PedPoPError::InvalidShare` when the batch verification fails [2](#0-1) . The proof is forwarded on-chain via `CoordinatorMessage::VerifyBlame`, where every validator re-executes `AdditionalBlameMachine::blame` → `decrypt_with_proof` [3](#0-2) . The cipher key is derived solely from the transcript over the ECDH point [4](#0-3) , so whoever sees the `EncryptionKeyProof` (which is `read`/`write` serializable and broadcast) can recompute the ChaCha20 keystream and decrypt `msg` themselves. Only after decrypting does `blame_internal` check whether the share is a canonical scalar and satisfies the verification statement — returning `recipient` as faulty if it is valid [5](#0-4) .

The proof-of-possession on `msg.key` only prevents *forging* a blame for a message whose key the attacker doesn't own; it does not prevent an honest-but-griefing (or compromised-but-not-yet-slashed) recipient from publishing their legitimate `EncryptionKeyProof` for a share that was correctly formed.

### Impact Explanation
A single `VerifyBlame` message with an accuser's own valid ECDH proof discloses the accused sender's secret share to all validators/observers. A leaked Pedersen share `f_sender(recipient)` is a reusable credential: any party that learns shares for `t` distinct (sender polynomials summed) indices — or that already holds `t-1` shares from a collusion set — can interpolate the victim's portion of the group secret key, recovering key-share material that was supposed to be known only to the recipient. Like the Glances pbkdf2 hash, the disclosed value is not the private key itself but is functionally equivalent for reconstructing signing power.

### Likelihood Explanation
The accuser needs only to be a DKG participant willing to take a slash. Falsely blaming an honest sender requires zero cryptographic breaks: the accuser's own `EncryptionKeyProof` verifies correctly (the DLEq over `enc_key` and `msg.key` is honest), `decrypt_with_proof` returns the share bytes, and the "share was canonical and valid → blame recipient" branch fires *after* the plaintext share is computable by everyone who ran the blame check [6](#0-5) . Any validator or off-chain observer that records the `VerifyBlame` payload plus the accused's commitment vector gains the share. Economic cost is one slashing, which may be cheap relative to compromising a threshold key.

### Recommendation
Do not broadcast the decryption-enabling `key` in the blame proof. Either:
- Have the accuser publish only the DLEq proof plus a commitment to the decrypted share, with the share opening revealed to the coordinator over a private channel; or
- Redesign blame so the accuser proves a predicate over the decrypted share (e.g., a ZK proof that `from_repr` fails or the verification multiexp is non-identity) without revealing the plaintext.

### Proof of Concept
1. Participants 1..n run PedPoP normally; sender S produces a valid `EncryptedMessage<C, SecretShare>` to recipient R.
2. R calls `calculate_share`, obtains `EncryptionKeyProof { key, dleq }` for S's message via `self.encryption.decrypt` [1](#0-0) .
3. R submits `CoordinatorMessage::VerifyBlame { accuser: R, accused: S, share: <S's message>, blame: Some(proof.serialize()) }`.
4. Every validator executes `blame_internal`, decrypts via `cipher(context, &key)` [4](#0-3) , finds the share valid, and returns `Blame { participant: R }` — R is slashed, but S's secret share `f_S(R)` is now computable by any party that observed the `key` field of the published `EncryptionKeyProof` and the ciphertext.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
