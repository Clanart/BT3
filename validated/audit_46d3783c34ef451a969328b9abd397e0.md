### Title
Tier gaming via transient mWomSV lock inflates non-lock MGP reward multiplier in `getRewardAmount(_lock=false)` - (File: wombat/ArbWomUp3.sol)

### Summary
`getUserTier` derives the reward tier purely from the caller's *current* `mWomSV.getUserTotalLocked` balance, with no vesting/duration requirement. An attacker can lock a large amount of mWomSV, immediately call `incentiveDeposit(_amount, _convertRatio, _bullMode, _mode=1)` to receive `_amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR` MGP (locked into `vlMGP`), then start unwinding the mWomSV position, permanently capturing a reward multiplier that a genuinely sustained lower-tier or unlocked user would never qualify for.

### Finding Description
In `getRewardAmount` [1](#0-0) , the `_lock == false` branch applies a single flat multiplier to the *entire* `_amountToConvert`:
```
mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
```
`getUserTier` [2](#0-1)  reads `mWomSV.getUserTotalLocked(_account)`, which reflects only the instantaneous locked balance held in `MasterMagpie` via `mWomSV` — there is no time-weighting, snapshotting, or minimum-duration requirement. Locking mWomSV is instantaneous (`lock`/`lockFor` in `wombat/mWomSV.sol` lines 226-240 immediately update `MasterMagpie` staking info), so a user's tier can be inflated in the same transaction (or immediately preceding transaction) that calls `incentiveDeposit`.

Contrast this with the `_lock == true` branch, which computes the reward incrementally across all tier boundaries and subtracts `calDoubledCounted(_account)` (the reward already implied by the user's existing locked balance) to avoid double-counting [3](#0-2) . The non-lock branch has no equivalent anti-double-counting/anti-gaming logic — it simply multiplies the whole `_amountToConvert` by the tier multiplier corresponding to whatever balance the attacker happens to hold at call time.

Exploit flow:
1. Attacker acquires/holds mWom (or WOM, converts to mWom) and calls `mWomSV.lock(_amount)`/`lockFor` to instantly push `getUserTotalLocked` above the top reward tier threshold.
2. Attacker calls `ArbWomUp3.incentiveDeposit(_amountToConvert, _convertRatio, false, 1)` (`_mode=1`, non-lock/stake mode). `getRewardAmount` returns `_amountToConvert * rewardMultiplier[topTier] / DENOMINATOR`, paid out via `vlMGP.lockFor(rewardToSend, msg.sender)` [4](#0-3) .
3. Attacker then calls `mWomSV.startUnlock(_amount)` to begin the cooldown and, after `coolDownInSecs` elapses, `mWomSV.unlock(_slotIndex)` to retrieve the full mWom principal back with no penalty [5](#0-4) .

Existing checks that fail to prevent this: `incentiveDeposit` only guards `_amount != 0`, `whenNotPaused`, and `nonReentrant`; none of these validate tier sustainment. There is no minimum holding period, no snapshot-based tier calculation, and no requirement that `_amountToConvert` be proportionate to the locked mWomSV balance in the non-lock branch.

### Impact Explanation
This causes a disproportionate drain of the MGP reward pool held by `ArbWomUp3` (bounded per-call by `mgpleft`, `IERC20(mgp).balanceOf(address(this))`, but repeatable). Legitimate/sustained low-tier users receive `rewardMultiplier[0]` (or a lower blended rate) for the same `_amountToConvert`, while an attacker willing to temporarily park capital in mWomSV extracts the top-tier multiplier — a real, quantifiable over-issuance of MGP (locked in vlMGP for the attacker) relative to the intended reward curve. This is a theft/over-extraction of unclaimed yield/reward-pool funds at the expense of the protocol's MGP reserve and of other users who follow the intended tiered incentive design (Immunefi class: theft of yield / protocol insolvency of the incentive pool).

### Likelihood Explanation
Feasibility is bounded by the `coolDownInSecs` delay in `mWomSV` (locking is instant, but unlocking requires `startUnlock` + waiting + `unlock`, so this is not a flash-loan-atomic exploit). The attacker must temporarily commit capital (buy/hold mWom and lock it) for at least the cooldown duration, but incurs no slashing/penalty on the standard `unlock` path, so the capital is fully recovered — only opportunity cost is paid, not principal loss. Because tier calculation is not time-weighted and reward is claimed immediately after locking (no minimum lock duration before `incentiveDeposit` is checked), the attack is fully permissionless, repeatable each cooldown cycle, and requires only capital an unprivileged EOA can obtain in the open market.

### Recommendation
- In `getRewardAmount`'s non-lock branch, apply the same incremental/tiered accumulation logic used in the lock branch (summing across tier boundaries) rather than a flat multiplier based on current tier, and/or subtract `calDoubledCounted(_account)`-style adjustment to avoid rewarding balance the user did not "grow into" via this conversion.
- Require a minimum lock duration (time-weighted average balance) before `mWomSV`-derived tier can be used to determine `getUserTier`, e.g., checkpoint balances and only count balance that has been locked for at least N blocks/seconds.
- Alternatively, gate `_mode=1` reward multiplier on the user's locked balance *before* the current transaction (e.g., snapshot at start of block or require the locked balance predate `incentiveDeposit` call by a cooldown period).

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3`, `mWomSV`, `MasterMagpie` mocks/fixtures with `rewardTier = [0, T1, T2]`, `rewardMultiplier = [m0, m1, m2]` (m2 >> m0), and fund `ArbWomUp3` with MGP.
2. As attacker EOA: acquire mWom, call `mWomSV.lock(largeAmount)` where `largeAmount >= T2` to hit tier 2.
3. Call `arbWomUp3.incentiveDeposit(smallAmountToConvert, 0, false, 1)`.
4. Assert `vlMGP` locked amount for attacker == `smallAmountToConvert * m2 / DENOMINATOR`, which is strictly greater than `smallAmountToConvert * m0 / DENOMINATOR` (what a non-tiered/genuine small holder would receive).
5. Call `mWomSV.startUnlock(largeAmount)`, warp `coolDownInSecs`, call `mWomSV.unlock(slotIndex)`.
6. Assert attacker recovers full `largeAmount` mWom (no penalty) while retaining the tier-2-multiplied MGP reward from step 3/4 — demonstrating captured reward exceeds the sustained-stake entitlement (tier 0/1) at negligible net cost (only time-value of locked capital during cooldown).

    function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
