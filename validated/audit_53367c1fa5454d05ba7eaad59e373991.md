## Analysis

The Sherlock report's broken invariant is: **an exact-output/price-limited swap can leave residual input value unused, and that residual must be returned to the depositor — but the calling contract instead retains it.** In UXD's case the leftover quote token stayed in the Perp vault instead of going back to the rebalance caller.

The Hyperbridge codebase has a direct structural analog in `IntentGatewayV2.placeOrder()`'s fee-escrow path, which performs an **exact-output** Uniswap V2 swap (`swapETHForExactTokens`) using the *entire remaining native `msgValue`* as the spending cap, but never captures or forwards the router's automatic ETH refund back to the order-placing user.

### Title
`placeOrder` fee-swap leaks unrefunded native ETH into the contract instead of returning it to the user - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
When a user places an order with `order.fees > 0` and pays the fee in native ETH, `placeOrder()` swaps the leftover `msgValue` for an exact amount of `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`. This is an exact-output swap where the router refunds unspent ETH — but the refund target is `address(this)` (the contract itself, since it is the immediate caller of the router), not the original user who supplied the ETH.

### Finding Description
In `placeOrder()`, after escrowing order inputs, the remaining `msgValue` is used to acquire the fee token: [1](#0-0) 

`swapETHForExactTokens` is an **exact-output** call: the caller supplies an amount-in ceiling (here, the *entire* remaining `msgValue`) and the router only consumes what the current pool price requires to produce `order.fees` units of `feeToken`, refunding the rest of the ETH to `msg.sender` of that call. Because `IntentGatewayV2` itself invokes the router (`{value: msgValue}`), the router's ETH refund lands on the `IntentGatewayV2` contract's own balance — not on the user who originally sent that ETH via `msg.value`.

Nothing in `placeOrder()` measures a before/after ETH balance delta or forwards any leftover ETH back to `msg.sender`. The function only records `_orders[commitment][TRANSACTION_FEES] = order.fees` and emits `OrderPlaced`; there is no bookkeeping entry or later sweep path that returns this residual ETH to the depositing user. This mirrors the reported bug precisely: a price-bounded swap that can leave unused input value stranded inside the protocol rather than returned to the party who funded it.

The user cannot pre-compute the exact ETH needed at the on-chain execution price (which can move between transaction signing and mining, or simply differs from any off-chain estimate), so they must send `msgValue` with a buffer to guarantee the exact-output swap succeeds — guaranteeing that some non-zero refund is generated and silently absorbed by the contract on essentially every such order.

### Impact Explanation
This is a direct, unprivileged loss of user funds through a normal public entrypoint (`placeOrder`), matching the bounty's "stealing or loss of funds" category. Any user placing a fee-in-native order effectively donates the unspent ETH buffer to the protocol/contract balance with no path to reclaim it, since there is no per-user accounting of this residual and no refund transfer in the same call.

### Likelihood Explanation
High likelihood: this triggers on the ordinary, documented flow of paying `order.fees` in native ETH (`msgValue > 0` branch) whenever the caller supplies any ETH buffer above the exact swap requirement — which is unavoidable in practice since the precise Uniswap V2 execution price is not knowable with certainty ahead of the transaction. No malicious peer, relayer, or governance actor is required — a single ordinary user calling `placeOrder` triggers the loss against themselves.

### Recommendation
After the `swapETHForExactTokens` call, compute the actual ETH spent (e.g., via `amounts[0]` return value or a balance snapshot) and refund `msgValue - amountSpent` directly to `msg.sender` before returning from `placeOrder`, analogous to how `_fillSameChain` already correctly refunds unspent native value to the solver: [2](#0-1) 

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` with `order.fees = X` (in `feeToken`), no `predispatch`, and sends `msg.value = inputAmount(native, if any) + feeBudget` where `feeBudget` intentionally exceeds the ETH needed at current pool price to buy `X` units of `feeToken` (a realistic buffer, since exact price at execution time is unknown).
2. `placeOrder` computes `msgValue` as the residual native value after input escrow, then calls:
   `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` [3](#0-2) 
3. The router spends only `amounts[0] < msgValue` ETH to acquire exactly `X` `feeToken`, and refunds `msgValue - amounts[0]` ETH to `msg.sender` of the swap call, i.e., to the `IntentGatewayV2` contract address.
4. `placeOrder` never reads this refund nor sends it back to the user; the function completes and emits `OrderPlaced`.
5. The user's transaction receipt shows `msg.value` fully consumed, but on-chain the contract's ETH balance permanently increased by `msgValue - amounts[0]`, with no `_orders[...]` entry or later withdrawal path crediting it to the user — a silent, unrecoverable loss for every fee-in-native order with any ETH buffer.
