### Title
DAI deposits accepted by the Ethereum Router cannot be paid out because transaction construction only accepts Ether balances - (File: processor/src/networks/ethereum.rs)

### Summary
Serai accepts DAI deposits through both Router `inInstruction` calls and top-level ERC-20 transfers to the Router. Those deposits are reported as `ExternalCoin::Dai`. When a Serai burn creates a payment denominated in DAI, `signable_transaction` unconditionally asserts that every payment uses `ExternalCoin::Ether`, causing transaction construction to panic instead of producing a Router `Execute` command. The deposited DAI therefore remains held by the Router with no valid processor path to transfer it back out. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Router::inInstruction` accepts ERC-20 deposits by calling `transferFrom(msg.sender, address(this), amount)` and emitting an `InInstruction` event. [4](#0-3)  Serai also accepts direct top-level ERC-20 transfers to the Router by matching the token `Transfer` event to the transaction's `transfer` or `transferFrom` calldata. [5](#0-4) 

The processor explicitly maps `EthereumCoin::Erc20(DAI)` to `ExternalCoin::Dai` and converts the token amount into Serai's eight-decimal representation. [6](#0-5)  Scanned top-level DAI transfers and Router events are both converted into external outputs carrying that DAI balance. [7](#0-6)  A burn/out instruction then becomes a `Payment` preserving `payment.balance.coin`. [8](#0-7) 

The bug occurs when constructing the Ethereum transaction: every payment's balance is asserted to be `ExternalCoin::Ether`. [9](#0-8)  There is no branch that converts a `Dai` payment into an ERC-20 `transfer(to, amount)` `Call`; the code even marks the Ether-only assumption as `TODO`. [3](#0-2) 

### Impact Explanation
A user can deposit real DAI to the Router and have Serai account for it as an `ExternalCoin::Dai` output. If the corresponding Serai asset is later burned for withdrawal, or an instruction/refund schedules a DAI payment, `signable_transaction` panics instead of signing a spend. The Router retains the ERC-20 balance, so the external funds are recorded as received but cannot be redeemed through the production path. [10](#0-9) [11](#0-10) 

This is not fixed by Router `execute`'s generic call support: that path could invoke arbitrary calls, but the processor never constructs an ERC-20 transfer call for a DAI payment and panics before producing the command. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
The reachable input is an ordinary public DAI `transfer`/`transferFrom` to the Router, or a public `inInstruction` call naming the DAI token. [14](#0-13) [5](#0-4)  DAI is an explicitly recognized production coin, and the resulting withdrawal requires only a normal Serai out instruction carrying `ExternalCoin::Dai`. [15](#0-14) [16](#0-15) 

### Recommendation
Represent ERC-20 withdrawals distinctly from ETH value transfers. For `ExternalCoin::Dai`, construct a `Call` to the DAI contract invoking `transfer(recipient, amount)` with zero ETH value, rather than assigning the token amount to `OutInstruction.value`. Continue using the Router's sandboxed call path or add a dedicated token-transfer execution path, and test both direct top-level DAI deposits and Router `inInstruction` deposits through deposit, burn, signing, and on-chain redemption. [13](#0-12) [17](#0-16) 

### Proof of Concept
1. Deploy the Router and activate its Schnorr key.
2. From an external account, call `DAI.transfer(router, amount)` with arbitrary appended instruction bytes, or call `router.inInstruction(DAI, amount, instruction)` after approval. The first route emits a verified token `Transfer`, while the second route emits `InInstruction`. [18](#0-17) [19](#0-18) 
3. `get_outputs` converts the deposit into an `EthereumInInstruction` with `coin = EthereumCoin::Erc20(DAI)`. [20](#0-19) 
4. `balance()` reports `ExternalCoin::Dai` and scales the amount from 18 to 8 decimals. [6](#0-5) [10](#0-9) 
5. Burn the resulting Serai DAI into an external address, producing a `Payment` whose `balance.coin` remains `ExternalCoin::Dai`. [16](#0-15) 
6. `signable_transaction` reaches `assert_eq!(payment.balance.coin, ExternalCoin::Ether)` and panics; no `RouterCommand::Execute` is returned. [11](#0-10) 
7. The DAI remains owned by the Router, but Serai's production signing path cannot construct the ERC-20 transfer needed to release it. [12](#0-11)

fn amount_to_serai_amount(coin: ExternalCoin, amount: U256) -> Amount {
  assert_eq!(coin.network(), ExternalNetworkId::Ethereum);
  assert_eq!(coin.decimals(), 8);
  // Remove 10 decimals so we go from 18 decimals to 8 decimals
  let divisor = U256::from(10_000_000_000u64);
  // This is valid up to 184b, which is assumed for the coins allowed
  Amount(u64::try_from(amount / divisor).unwrap())

  function inInstruction(
    address coin,
    uint256 amount,
    bytes memory instruction
  ) external payable {
    if (coin == address(0)) {
      if (amount != msg.value) {
        revert InvalidAmount();
      }
    } else {
      (bool success, bytes memory res) =
        address(coin).call(
          abi.encodeWithSelector(
            IERC20.transferFrom.selector,
            msg.sender,
            address(this),
            amount
          )
        );

      // Require there was nothing returned, which is done by some non-standard
      // tokens, or that the ERC20 contract did in fact return true
      bool nonStandardResOrTrue =
        (res.length == 0) || abi.decode(res, (bool));
      if (!(success && nonStandardResOrTrue)) {
        revert FailedTransfer();
      }
    }

    /*
    Due to fee-on-transfer tokens, emitting the amount directly is frowned upon.
    The amount instructed to transfer may not actually be the amount
    transferred.

    If we add nonReentrant to every single function which can effect the
    balance, we can check the amount exactly matches. This prevents transfers of
    less value than expected occurring, at least, not without an additional
    transfer to top up the difference (which isn't routed through this contract
    and accordingly isn't trying to artificially create events).

    If we don't add nonReentrant, a transfer can be started, and then a new
    transfer for the difference can follow it up (again and again until a
    rounding error is reached). This contract would believe all transfers were
    done in full, despite each only being done in part (except for the last
    one).

    Given fee-on-transfer tokens aren't intended to be supported, the only
    token planned to be supported is Dai and it doesn't have any fee-on-transfer
    logic, fee-on-transfer tokens aren't even able to be supported at this time,
    we simply classify this entire class of tokens as non-standard
    implementations which induce undefined behavior. It is the Serai network's
    role not to add support for any non-standard implementations.
    */
    emit InInstruction(msg.sender, coin, amount, instruction);

#[derive(Clone, PartialEq, Eq, Debug)]
pub struct Call {
  pub to: [u8; 20],
  pub value: U256,
  pub data: Vec<u8>,
}
impl Call {
  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<Self> {
    let mut to = [0; 20];
    reader.read_exact(&mut to)?;

    let value = {
      let mut value_bytes = [0; 32];
      reader.read_exact(&mut value_bytes)?;
      U256::from_le_slice(&value_bytes)
    };

    let mut data_len = {
      let mut data_len = [0; 4];
      reader.read_exact(&mut data_len)?;
      usize::try_from(u32::from_le_bytes(data_len)).expect("u32 couldn't fit within a usize")
    };

    // A valid DoS would be to claim a 4 GB data is present for only 4 bytes
    // We read this in 1 KB chunks to only read data actually present (with a max DoS of 1 KB)
    let mut data = vec![];
    while data_len > 0 {
      let chunk_len = data_len.min(1024);
      let mut chunk = vec![0; chunk_len];
      reader.read_exact(&mut chunk)?;
      data.extend(&chunk);
      data_len -= chunk_len;
    }

    Ok(Call { to, value, data })
