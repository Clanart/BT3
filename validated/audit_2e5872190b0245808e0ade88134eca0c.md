# No Vulnerability found for this question.

**Reasoning:**

The premise that `git status --porcelain=2 -z` can be made to emit an entry whose `path` contains literal `../` segments pointing outside the repository is not realizable through attacker-controlled repository content.

`getLargeFilePaths` does compute `filePath = join(repository.path, file.path)` without any additional sanitization of `file.path` [1](#0-0) , and `status-parser.ts` extracts `path` directly from the porcelain fields via regex capture groups (for changed, renamed/copied, and unmerged entries) or by substring for untracked entries [2](#0-1) [3](#0-2) [4](#0-3)  — none of these perform explicit traversal sanitization.

However, the values `git status` reports for tracked (changed/renamed) entries come from real tree entries that git itself resolves relative to the repository's top-level directory, and Git enforces protections against tree entries named `.` or `..` (or path components resolving to them) at the object/tree validation and checkout layers — this is longstanding hardening against path-traversal attacks via crafted trees (related to historical CVEs like the `.git`/case-insensitive filesystem and `..` tree-entry issues). A malicious repository cannot get Git to materialize or report a tracked path containing a literal `../` segment; Git will refuse such trees.

For untracked entries, the path is derived from an actual filesystem walk of the working directory rooted at `repository.path` [4](#0-3) , so the reported path is inherently a real relative path under `repository.path` — Git isn't inventing string content here, it's reporting names of files/directories that genuinely exist on disk under the working tree.

Therefore, an attacker cannot control the content of a cloned repository (commits, trees, working tree files) in a way that causes `git status --porcelain=2 -z` to emit a `path` field containing traversal segments that would let `join(repository.path, file.path)` in `large-files.ts` escape `repository.path`. Since the required precondition ("repo with a rename or untracked entry whose reported path was not sanitized... containing literal `../`") cannot be produced by Git itself, the described flow does not constitute a reachable vulnerability.

function parsedRenamedOrCopiedEntry(
  field: string,
  oldPath: string | undefined
): IStatusEntry {
  const match = renamedOrCopiedEntryRe.exec(field)

  if (!match) {
    log.debug(`parsedRenamedOrCopiedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for renamed or copied entry`)
  }

  if (!oldPath) {
    throw new Error(
      'Failed to parse renamed or copied entry, could not parse old path'
    )
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    oldPath,
    renameOrCopyScore: parseInt(match[8].substring(1), 10),
    path: match[9],
  }
}
