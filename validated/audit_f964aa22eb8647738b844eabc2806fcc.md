### Title
Reward-sniping via `vote()`→`castVotes()` sandwich lets an unprivileged vlMGP holder capture bribe yield accrued by other voters - (File: wombat/WombatBribeManager.sol, rewards/BribeRewardPool.sol, rewards/BaseRewardPoolV2.sol)

### Summary
`BribeRewardPool`/`BaseRewardPoolV2` distribute harvested bribe rewards pro-rata over the *current* `totalSupply()` at the moment `queueNewRewards` is called, with no minimum stake duration or time-weighting. An attacker who already holds vlMGP can call `WombatBribeManager.vote(+delta)` (or the atomic `voteAndCast`) immediately before/with `castVotes()` to inflate `totalSupply` right as accumulated bribes are queued, then `unvote()` to withdraw and claim, capturing yield that accrued entirely from other users' pre-existing votes.

### Finding Description
`WombatBribeManager.vote()` calls `IBribeRewardPool(pool.rewarder).stakeFor(msg.sender, uint256(delta))` [1](#0-0)  which runs the `updateRewards(_for, rewardTokens)` modifier *before* increasing `totalSupply`/`_balances`, checkpointing `userRewardPerTokenPaid` at the pre-harvest `rewardPerTokenStored` value [2](#0-1) [3](#0-2) .

`WombatBribeManager.castVotes()` then calls `wombatStaking.vote(...)`, which harvests the Wombat bribe and calls `IBaseRewardPool(_rewarders[i]).queueNewRewards(rewardAmount, ...)` [4](#0-3) . `_provisionReward` computes the reward-per-token increment using `totalStaked()` **at harvest time**, i.e. `totalSupply` including the attacker's just-added delta: `rewardPerTokenStored += (_amountReward * scale) / totalStaked()` [5](#0-4) .

Because the attacker's `userRewardPerTokenPaid` was frozen at the pre-harvest value and their balance is now non-zero, `_earned`/`earned` computes `_userShare * (rewardPerToken - userRewardPerTokenPaid) / scale`, giving the attacker a full share of the harvest based on the entire delta stake they just added, despite having contributed 0 to the vote weight that generated the bribe over the prior epoch [6](#0-5) . The attacker can then call `unvote()`, which withdraws the stake and immediately claims (`claim=true`) via `withdrawFor` [7](#0-6) .

Critically, no front-running/mempool timing is even required: `voteAndCast()` performs `vote(_lps, _deltas)` then `castVotes(swapForBnb)` atomically in a single transaction [8](#0-7) , allowing risk-free, single-tx reward sniping. `castVotes()` is fully permissionless (any caller, no access control, no minimum interval enforced beyond recording `lastCastTime`) [9](#0-8) , so an attacker doesn't need to guess timing or compete with mempool races — they control both steps.

Existing checks do not stop this: `updateRewards`/`updateReward` correctly checkpoint balances against `rewardPerTokenStored`, but this mechanism assumes rewards accrue continuously and smoothly — it has no concept of "time staked" or vesting, so a stake added in the same block as a lumpy bribe harvest is treated identically to a stake held throughout the entire accrual period.

### Impact Explanation
This is theft of unclaimed yield from long-term voters: capital that should be distributed to vlMGP holders who voted throughout the epoch is diverted to a last-second staker who added no vote-weight during bribe accrual. This matches the "theft of unclaimed yield" / disproportionate yield-capture impact class. The magnitude scales with the delta the attacker can vote and the size of the pending harvestable bribe (`previewBnbAmountForHarvest`/`previewBribes` even let the attacker see pending bribe size before acting) [10](#0-9) .

### Likelihood Explanation
Feasible for any unprivileged EOA holding vlMGP with unused votable power (`getUserVotable`), requiring no special permissions, flash loans, or governance/admin access. The attack is fully atomic via `voteAndCast()` in a single transaction, making it riskless and repeatable every time a meaningful bribe balance accumulates before a cast. The only capital requirement is vlMGP (obtained via normal MGP locking, an ordinary user action) and gas.

### Recommendation
Introduce a minimum stake-duration / time-weighted accrual mechanism before newly staked vote-weight becomes eligible for a reward distribution — e.g., snapshot eligible balances prior to `queueNewRewards`/`castVotes`, or accrue rewards using a checkpoint system that excludes stakes added within the same block/epoch as the harvest (similar to a "reward eligibility delay" or epoch-boundary snapshotting used in veToken/gauge systems). Alternatively, require `castVotes` to use the vote-weight snapshot from *before* any `vote()` calls executed later in the same block, and/or enforce a cooldown between `vote()` and reward eligibility (e.g., new stake only starts earning from the next `castVotes` cycle, not the one that triggered the harvest).

### Proof of Concept
Foundry test plan:
1. Deploy `WombatBribeManager`, `BribeRewardPool` (or `DelegateVoteRewardPool`), mock `WombatStaking`, mock `Voter`/`Bribe` contract that returns a large pending bribe on `pendingBribes`/`vote`.
2. Set up two long-term voters (Alice, Bob) who call `vote(+X)` on a pool at time T0, well before any harvest.
3. Advance time / accumulate bribe on the mock Wombat bribe contract.
4. Attacker (holding vlMGP but never voted before) calls `voteAndCast(lps, [+delta], false)` in a single tx — this executes `vote(+delta)` then `castVotes()` atomically.
5. Assert: `earned(attacker, rewardToken) > 0` immediately after this single tx, despite the attacker's `userRewardPerTokenPaid` checkpoint having been set in the very same transaction (i.e., zero elapsed accrual time for the attacker).
6. Attacker calls `unvote(lp)` in the same or next block, receiving the claimed reward via `withdrawFor(..., true)`.
7. Assert attacker's claimed reward / delta stake ratio is comparable to Alice/Bob's ratio despite Alice/Bob having accrued votes for the entire epoch and the attacker for zero blocks — demonstrating disproportionate capture.
8. Add a fix-invariant assertion: `earned(account, token)` for any stake added in the same block/epoch as the triggering `queueNewRewards` call should be 0 (or bounded by a proper time-weighted formula), and re-run the test against the proposed fix to confirm the attacker's captured reward drops to (near) zero.

    modifier updateRewards(address _account, address[] memory _rewards) {
        uint256 length = _rewards.length;
        uint256 userShare = balanceOf(_account);
        
        for (uint256 index = 0; index < length; ++index) {
            address rewardToken = _rewards[index];
            // if a reward stopped queuing, no need to recalculate to save gas fee
            if (userRewardPerTokenPaid[rewardToken][_account] == rewardPerToken(rewardToken))
                continue;
            userRewards[rewardToken][_account] = _earned(_account, rewardToken, userShare);
            userRewardPerTokenPaid[rewardToken][_account] = rewardPerToken(rewardToken);
        }
        _;
    }
