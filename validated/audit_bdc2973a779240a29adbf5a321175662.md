### Title
OP_RETURN data output excluded from weight/fee calculation causes underpaid fee and unrelayable transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` pushes an OP_RETURN output onto `tx_outs` when `data` is specified, but the weight/vbytes used to derive `needed_fee` is computed by `calculate_weight_vbytes`, which rebuilds a transaction solely from `payments` (plus optional change). The OP_RETURN output (up to 80 bytes of data plus output overhead) is never included in the measured transaction, so `needed_fee` is systematically under-calculated whenever `data` is `Some`, mirroring the reported bug class: the amount budgeted/collected for distribution does not account for everything the final transaction actually commits to. [1](#0-0) 

### Finding Description
`calculate_weight_vbytes` constructs a `Transaction` whose outputs are only `payments` and, optionally, `change`; it has no awareness of the OP_RETURN output appended earlier at `send.rs:194-202`. [2](#0-1) 

`SignableTransaction::new` then does:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

and, if change applies:

```rust
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
let fee_with_change = fee_per_vbyte * vbytes_with_change;
```

Neither measurement includes the OP_RETURN output that is already in `tx_outs`. [3](#0-2) 

Two consequences follow:

1. **Underpaid fee rate.** When a change output exists, the change absorbs `input_sat - payment_sat - fee_with_change`, leaving the actual fee exactly equal to `needed_fee` (`fee()` confirms the fee is `sum(inputs) - sum(outputs)`). The real transaction is larger than the measured one by the size of the OP_RETURN output, so `needed_fee / actual_vbytes < fee_per_vbyte`. If the discrepancy drops the effective rate below `DEFAULT_MIN_RELAY_TX_FEE`, the signed transaction will not be relayed or mined even though the `TooLowFee` check passed. [4](#0-3) 

2. **Incorrect size bound.** The `TooLargeTransaction` check compares `weight` (excluding the OP_RETURN output) against `MAX_STANDARD_TX_WEIGHT`, so a near-maximum transaction with `data` set can exceed the standard weight limit and be unrelayable. [5](#0-4) 

### Impact Explanation
The result is a correctly signed transaction that cannot achieve its intended confirmation behavior: either it pays an effective fee rate below the requested rate (and potentially below the network's minimum relay fee, causing the funds to be locked in-flight until abandoned/expired), or it silently exceeds the standard transaction weight and is rejected at broadcast. The committed UTXOs remain spent-pending, matching the "insufficient funds at distribution time / locked funds" failure mode of the reference report.

### Likelihood Explanation
Triggering requires the `data` parameter to be `Some`, which adds up to 80 bytes (~90 weight units for the output plus payload). Whether this causes a relay failure depends on how close `fee_per_vbyte` is to the minimum relay fee and how close the transaction weight is to the cap. The fee-rate shortfall is deterministic whenever `data` is specified; the practical impact is only realized at boundary fee rates or near-maximum weights, so likelihood is moderate.

### Recommendation
Include the OP_RETURN output in the transaction measured by `calculate_weight_vbytes`. Either pass the fully constructed `tx_outs` (payments + OP_RETURN) into `calculate_weight_vbytes`, or add the data length as an explicit parameter so the weight of the `ScriptBuf::new_op_return` output is accounted for in both the no-change and with-change measurements, and in the `MAX_STANDARD_TX_WEIGHT` check.

### Proof of Concept
```rust
// Conceptual test in networks/bitcoin/tests/wallet.rs
let inputs = vec![output]; // a single ReceivedOutput worth `v` sats
let data = vec![0u8; 80];  // max allowed, passes the 80-byte check
let tx = SignableTransaction::new(
  inputs, &payments, Some(change_addr), Some(data), fee_per_vbyte,
).unwrap();

// The actual transaction contains the OP_RETURN output
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// actual vbytes exceeds the vbytes the fee was computed on
let actual_vbytes = tx.transaction().vsize() as u64;
assert!(tx.fee() < actual_vbytes * fee_per_vbyte);
// With fee_per_vbyte == minimum relay rate, tx.fee() is below the
// minimum relay fee for the transaction's true size -> unrelayable.
```
