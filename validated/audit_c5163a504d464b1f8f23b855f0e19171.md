### Title
`Verifier::is_deposit_valid` never checks that a `ReplacementDeposit`'s outpoint was funded by spending `old_move_txid`'s vault output via the security-council path, allowing a self-funded taproot output to be N-of-N signed as a "replacement" - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` only checks that the `deposit_outpoint`'s scriptPubKey matches `ReplacementDepositScript(new_nofn_pk, old_move_txid) + Multisig(security_council)` and that its value equals `bridge_amount` and it's confirmed above `start_height`. It never verifies that the coin sitting at `deposit_outpoint` was actually produced by spending `old_move_txid`'s `MoveToVault` output through the security-council multisig path. `create_replacement_deposit_txhandler` (`core/src/builder/transaction/mod.rs:404-446`), which does enforce that binding by consuming the old vault's `CheckSig(old_nofn_pk)+Multisig(security_council)` output, is `#[cfg(test)]`-only and is not part of the enforced deposit-validation path used by the aggregator/verifier RPC flow (`is_deposit_valid`/`deposit_sign`).

### Finding Description
The binding that should hold is:
`funding_input(deposit_outpoint's tx) == old_move_txid:UtxoVout::DepositInMove, spent via ScriptPath(Multisig::from_security_council)`

Tracing `Verifier::is_deposit_valid` (`core/src/verifier.rs:659-731`):
- It builds `deposit_scripts` from `deposit_data.get_deposit_scripts(...)`, which for `DepositType::ReplacementDeposit` returns `[ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid), Multisig::from_security_council(...)]` (`core/src/deposit.rs:206-217`).
- It computes `expected_scriptpubkey` from those scripts and fetches the on-chain tx at `deposit_outpoint`, checking only:
  - `deposit_txout_in_chain.value == bridge_amount`
  - `deposit_txout_in_chain.script_pubkey == expected_scriptpubkey`
  - block height `>= start_height`
- At no point does it look at `deposit_tx.input[0].previous_output` (or any input) to confirm it equals `OutPoint{ txid: old_move_txid, vout: UtxoVout::DepositInMove }`, nor does it check that such an input was spent via the security-council script path. The only place that enforces "spend the old vault via security council" is `create_replacement_deposit_txhandler`, gated behind `#[cfg(test)]` (`core/src/builder/transaction/mod.rs:403-446`), used solely in test helpers `send_replacement_deposit_tx`/`run_single_replacement_deposit` (`core/src/test/common/mod.rs:604-812`). This helper is never invoked from the aggregator/verifier production code path (`core/src/rpc/aggregator.rs`, `core/src/verifier.rs`).

Exploit flow:
1. Attacker (or anyone who knows a real, already-broadcast `old_move_txid` -- move-to-vault txids are public on-chain) computes `generate_replacement_deposit_address(old_move_txid, nofn_xonly_pk, network, security_council)` (`core/src/builder/address.rs:89-103`), which is deterministic from public inputs (nofn key and security council are public/known, `old_move_txid` is attacker-chosen from any real prior deposit).
2. Attacker funds that address with their own BTC, unrelated to spending the old vault output (no security council signature involved; they simply send-to-address).
3. Attacker calls the aggregator's `new_deposit` gRPC with `Deposit{ deposit_outpoint: <attacker's own outpoint>, deposit_data: ReplacementDeposit{ old_move_txid } }` (proto `core/src/rpc/clementine.proto:120-123`, parsed in `core/src/rpc/parser/mod.rs:363-374`).
4. Aggregator forwards to verifiers' `deposit_sign`, which calls `is_deposit_valid` (`core/src/verifier.rs:866-876`). All checks above pass because they only check the *destination* scriptPubKey/amount/height of the new outpoint, not its funding provenance.
5. Verifiers musig2-partial-sign a new `MoveToVault` transaction for the attacker's self-funded outpoint as though it legitimately supersedes `old_move_txid`.

The old vault UTXO named by `old_move_txid` is never touched, remains spendable by the legitimate nofn/security-council paths, while a second, unrelated, attacker-funded UTXO now also gets a fully-signed presigned transaction graph "as a replacement" for it -- but since it was never derived from the old vault, this is effectively indistinguishable in this specific vulnerability from a normal new deposit; the actual "mint" claim requires that citrea-side accounting treats the replacement's presence as retiring/superseding the old deposit_id's credit without the underlying BTC having moved. That downstream on-chain/off-chain bookkeeping (`replaceDeposit` on the Citrea contract, `register_replacement_deposit_to_citrea`) is out of scope of this repo's enforceable guarantees per the audit rules (Citrea contract logic), but the Bitcoin-side guarantee that Clementine is supposed to provide -- "a replacement deposit can only be created by spending the old vault via the security council" -- is absent from `is_deposit_valid`.

### Impact Explanation
Within this repository's verifiable guarantees, the missing check means Clementine's verifiers will N-of-N presign a `MoveToVault` transaction for a `ReplacementDeposit` whose funding was never tied to the old vault UTXO named by `old_move_txid`. This directly matches the Critical category "N-of-N partial signatures for an unauthorised spend": the security-council-authorization step that `ReplacementDepositScript`/`create_replacement_deposit_txhandler` conceptually exist to enforce is bypassed for any attacker able to fund a taproot address and call `new_deposit`/`deposit_sign`. It is repeatable for every existing `old_move_txid` and does not require compromising any verifier, operator, or the security council itself -- only broadcasting a normal-looking deposit transaction and calling the standard deposit RPCs, both of which are within the unprivileged attacker's stated capabilities.

### Likelihood Explanation
No special privileges are needed: the attacker only needs (a) a real `old_move_txid` (public, trivially obtainable from any prior deposit), (b) enough BTC to fund one `bridge_amount`-sized taproot output at the replacement address, and (c) the ability to call `new_deposit`/`send_move_to_vault_tx` on the aggregator's public gRPC port, all of which are explicitly permitted attacker capabilities. There is no rate limiting or additional gate in `is_deposit_valid` blocking this. This is fully reproducible offline against a regtest verifier/aggregator setup with `cargo test`, no mainnet or live Citrea required.

### Recommendation
Add a provenance check in `Verifier::is_deposit_valid` (or in a shared `get_deposit_scripts`/deposit-fetch helper) for `DepositType::ReplacementDeposit` that:
1. Fetches the raw `deposit_tx` (already done) and, before accepting it, resolves its input(s) previous outpoints,
2. Confirms exactly one input exists and its `previous_output == OutPoint{ txid: old_move_txid, vout: UtxoVout::DepositInMove.get_vout() }`,
3. Confirms that input's witness is a valid script-path spend of the `Multisig::from_security_council(...)` leaf of the old vault's taproot tree (i.e., the security council actually authorized moving those exact funds), matching what `create_replacement_deposit_txhandler` builds today but promoting it out of `#[cfg(test)]` into production-enforced validation logic.
4. Reject the deposit with `BridgeError::InvalidDeposit` if provenance doesn't match.

#[cfg(test)]
pub fn create_replacement_deposit_txhandler(
    old_move_txid: Txid,
    input_outpoint: OutPoint,
    old_nofn_xonly_pk: XOnlyPublicKey,
    new_nofn_xonly_pk: XOnlyPublicKey,
    paramset: &'static ProtocolParamset,
    security_council: SecurityCouncil,
) -> Result<TxHandler, BridgeError> {
    Ok(TxHandlerBuilder::new(TransactionType::ReplacementDeposit)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NoSignature,
            SpendableTxIn::from_scripts(
                input_outpoint,
                paramset.bridge_amount,
                vec![
                    Arc::new(CheckSig::new(old_nofn_xonly_pk)),
                    Arc::new(Multisig::from_security_council(security_council.clone())),
                ],
                None,
                paramset.network,
            ),
            crate::builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_output(UnspentTxOut::from_scripts(
            paramset.bridge_amount,
            vec![
                Arc::new(ReplacementDepositScript::new(
                    new_nofn_xonly_pk,
                    old_move_txid,
                )),
                Arc::new(Multisig::from_security_council(security_council)),
            ],
            None,
            paramset.network,
        ))
        // always use 0 sat anchor for replacement deposit tx, this will keep the amount in replacement deposit tx exactly the bridge amount
        .add_output(UnspentTxOut::from_partial(anchor_output(Amount::from_sat(
            0,
        ))))
        .finalize())
}
