## Analog Identified: Input/Output Index Mismatch in `_fillSameChain`

### Title
Same-chain fill releases escrow keyed off a mismatched `inputs[i]`/`output.assets[i]` index pairing when `order.inputs.length != order.output.assets.length` - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The Sherlock report's core defect is a calculation function (`previewDeposit`) that implicitly assumes an invariant (fcash present in the market) that is not always true, and derives the wrong value by indexing/using the wrong data source when that assumption breaks. The same class of bug exists in `IntrinsicIntents._fillSameChain`: it assumes `order.inputs` and `order.output.assets` are always the same length and positionally correspond 1:1, but nothing in the codebase enforces that invariant, and the loop is bounded by `outputsLen` while indexing into `order.inputs[i]`.

### Finding Description
`_fillSameChain` iterates `for (uint256 i; i < outputsLen; i++)` where `outputsLen = order.output.assets.length`, and inside the loop computes the escrow release amount from `order.inputs[i]`: [1](#0-0) [2](#0-1) 

The escrow amount released to the solver is computed either as the full remaining `_orders[commitment][token]` balance for `order.inputs[i].token` (on full fill) or proportionally as `(order.inputs[i].amount * fillAmount) / totalRequired` (on partial fill) — in both cases keyed by `order.inputs[i]`, positionally matched to `order.output.assets[i]`.

Nothing in `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) or `IntentsBase` validates `order.inputs.length == order.output.assets.length` before escrowing funds and computing the commitment: [3](#0-2) 

If a user (or a malicious order-placer targeting their own order, or one crafted to trick a solver) places an order where the input array and output array have different lengths or a different value ordering (e.g., 2 low-value inputs escrowed but only 1 output asset expected, or inputs ordered so that a high-value input token sits at an index that lines up with a cheap/small output requirement), a solver filling `output.assets[0]` triggers escrow release keyed by `order.inputs[0]`, not by whatever input was actually meant to correspond to that specific output. Because `escrowedInputs` is sized to `outputsLen`, any `order.inputs` entries beyond `outputsLen` are silently never released/accounted for in this loop's output array, while the values used for the released amount are taken from whichever `order.inputs[i]` happens to share the same index as `output.assets[i]` — an assumption never checked against the actual per-input escrow structure the user funded via `placeOrder`.

This directly parallels the reported bug class: a fund-computation path takes an unvalidated shortcut (index/positional correspondence, or "market has fcash" assumption) instead of consulting the actual state that was recorded during the deposit/escrow step, and diverges from the true, per-asset ledger when that shortcut's precondition doesn't hold.

### Impact Explanation
A mismatch between `order.inputs` and `order.output.assets` lengths/ordering causes the wrong token/amount to be computed and released from escrow to the solver on fill, and can leave some escrowed input tokens permanently stuck (never referenced by any loop index) or released against the wrong output requirement. This is an unauthorized/incorrect transfer of escrowed funds to the wrong beneficiary/amount — squarely inside the required impact set (loss of funds, transaction manipulation, wrong amount/beneficiary).

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged entrypoint that accepts an arbitrary `Order` struct with independently-sized `inputs` and `output.assets` arrays; I found no length-equality check anywhere in `IntentGatewayV2.sol` or `IntrinsicIntents.sol`/`IntentsBase.sol` guarding this invariant. Exploiting it requires only crafting an order with mismatched array lengths/ordering — no relayer, prover, governance, or leaked-key assumption is needed, satisfying the "unprivileged attacker, public entrypoint" requirement.

### Recommendation
In `IntentGatewayV2.placeOrder` (or in `IntentsBase`), enforce `order.inputs.length == order.output.assets.length` before escrowing, or redesign `_fillSameChain` to release escrow based on an explicit input→output mapping (rather than implicit positional index equality), and size `escrowedInputs` to `order.inputs.length` so every escrowed input is accounted for on every fill.

### Proof of Concept
Not independently executed against a live fork/test harness in this pass — recommend a Devin session to write a Foundry test that: (1) places an order with `inputs.length = 2` and `output.assets.length = 1` (or reordered token values), (2) has a solver fill `output.assets[0]`, and (3) asserts that the amount released from escrow does not match the amount actually owed for the corresponding input, and/or that the second input remains permanently locked in the gateway.

**Uncertainty note:** I was not able to fully trace every call site that constructs `Order` structs (e.g., the cross-chain `ExtrinsicIntents.sol` path and SDK order-building helpers) to confirm whether any of them independently enforce equal array lengths before dispatch; this should be verified in a full session, since if some upstream, always-invoked validation elsewhere silently enforces the invariant, the practical severity would be reduced (though I found no such check in the contracts I read).
