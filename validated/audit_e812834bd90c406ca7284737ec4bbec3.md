### Title
Secret key material leaked via `Debug` output on `ThresholdCore`/`ThresholdKeys`/`ThresholdView` - (File: crypto/dkg/src/lib.rs)

### Summary
Mirroring the advisory's class — secret material that is protected on the success path but exposed through error/diagnostic output — the `Debug` implementations for Serai's threshold-key structures print fields containing secret scalars. `ThresholdCore::fmt` emits the `interpolation` field, which for `Interpolation::Constant(Vec<F>)` is a vector of field elements used as per-participant keying factors; `ThresholdKeys` derives `Debug`, printing its secret `scalar` and `offset` fields; `ThresholdView::fmt` prints `scalar` and `offset`, which are secret additive/multiplicative key adjustments.

### Finding Description [1](#0-0) 
`ThresholdCore::fmt` prints `interpolation` via `.field("interpolation", &self.interpolation)`. `Interpolation::Constant(Vec<F>)` derives `Debug` [2](#0-1) , so when constant interpolation is in use (permitted whenever `t == n`, per `ThresholdKeys::new` [3](#0-2) ), the raw `Vec<C::F>` coefficients — secret keying factors that determine each participant's share — are rendered into the debug string. Notably, `secret_share` is carefully omitted via `finish_non_exhaustive`, showing the intent to hide secrets, while `interpolation` was missed.

Additionally, `ThresholdKeys` uses `#[derive(Debug)]` [4](#0-3) , which prints `scalar` and `offset` — secret adjustments applied by `scale`/offset APIs — and `ThresholdView::fmt` similarly emits `scalar` and `offset` [5](#0-4) .

### Impact Explanation
Any code path that formats these structures with `{:?}` — error contexts, `anyhow`/panic payloads, tracing/event logs, or `expect`/`unwrap` diagnostics — writes secret scalar material to logs. For `Interpolation::Constant`, the leaked coefficients directly determine each key share (share recovery class). For `scalar`/`offset`, the leaked values are the secret adjustments to the group key; combined with public key data they reveal secret key offsets used by downstream schemes (e.g., FROST key offsets/tweaks).

### Likelihood Explanation
Debug formatting of key material is a realistic occurrence in failure handling: callers routinely wrap `Result`s containing or adjacent to these structures, and panic/debug paths (e.g., the `{e:?}` patterns used throughout the processor) surface `Debug` output. The leak requires no cryptographic break — only that some diagnostic path formats the keys — matching the advisory's "sanitized on success, leaked on failure" shape.

### Recommendation
Remove `interpolation` from `ThresholdCore::fmt` (keep `finish_non_exhaustive` without it), replace the `derive(Debug)` on `ThresholdKeys` with a manual impl that omits `scalar` and `offset`, and drop `scalar`/`offset` from `ThresholdView::fmt`. Audit `Interpolation`'s derived `Debug`/`Clone` on `Constant(Vec<F>)` for the same reason `SecretShare` uses a manual redacted `Debug` [6](#0-5) .

### Proof of Concept
```rust
// Construct keys using constant interpolation with secret coefficients
let keys = ThresholdKeys::<C>::new(
    params, // t == n
    Interpolation::Constant(vec![secret_coeff_1, secret_coeff_2]),
    secret_share,
    verification_shares,
)?;
// Any diagnostic that formats the keys leaks the coefficients:
let log = format!("{keys:?}"); // contains "interpolation: Constant([...secret scalars...])"
```

Caveat: I verified the `Debug` implementations and field secrecy statically; I could not fully trace whether a specific in-scope caller currently formats these structures into attacker-visible output, so the exposure depends on downstream logging/error paths. The redacted `secret_share` in the same impl confirms the intent that sibling secret fields should not be printable.

/// A method of interpolation.
#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]
pub enum Interpolation<F: Zeroize + PrimeField> {
  /// A list of constant coefficients, one for each of the secret key shares.
  /*
    There's no benefit to using a full linear combination here, as the additive term would have
    an entirely known evaluation with a fixed, public coefficient of `1`. Accordingly, the entire
    key can simply be offset with the additive term to achieve the same effect.
  */
  Constant(Vec<F>),
  /// Lagrange interpolation.
  Lagrange,
}
