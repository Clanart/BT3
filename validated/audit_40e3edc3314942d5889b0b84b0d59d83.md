### Title
`internal_send_tx` broadcasts arbitrary attacker-supplied `raw_tx` with no application-layer binding to the aggregator's own signing pipeline when TLS client verification is disabled - ([File: core/src/rpc/aggregator.rs])

### Summary
`ClementineAggregator::internal_send_tx` deserializes `SendTxRequest.raw_tx` directly into a `bitcoin::Transaction` and hands it to `self.tx_sender.insert_try_to_send(...)` with no check that the aggregator itself produced, signed, or authorized that transaction. The only protection against an arbitrary caller invoking this RPC is the transport-layer `Interceptors::OnlyAggregatorAndSelf` mTLS check; when the server is configured with `client_verification = false` (`Interceptors::Noop`), that check is entirely absent, and any unauthenticated caller reaching the aggregator's gRPC port can get the aggregator's tx-sender to schedule and (via the aggregator's funded bitcoind wallet, for fee bumping/CPFP) broadcast an arbitrary transaction.

### Finding Description
The claimed binding is: `tx_broadcast_via_aggregator_rpc == a_tx_this_aggregator_itself_presigned_or_authored`.

Tracing the handler: [1](#0-0) 
shows that `internal_send_tx` only requires `#[cfg(feature = "automation")]`, decodes `send_tx_req.raw_tx` into `signed_tx: bitcoin::Transaction` with a plain `try_into()`, and immediately calls `self.tx_sender.insert_try_to_send(&mut dbtx, None, &signed_tx, fee_type.try_into()?, None, &[], &[], &[], &[])`. There is no lookup against any presigned transaction table, deposit ID, kickoff ID, or signature verification against N-of-N/verifier keys — the raw bytes are trusted as-is.

The only gate preventing an arbitrary caller from reaching this handler is transport-level, implemented in `core/src/rpc/interceptors.rs`. `is_internal` flags any gRPC method whose name starts with `"Internal"` (which `InternalSendTx` does) as requiring `leaf_cert == our_cert` under `Interceptors::OnlyAggregatorAndSelf`: [2](#0-1) [3](#0-2) 

Whether this check is even installed depends entirely on deployment configuration in `create_grpc_server`: if `config.client_verification` is `false`, the service is wrapped with `Interceptors::Noop` instead, which performs no identity check at all: [4](#0-3) 

Under `Interceptors::Noop`, an unprivileged attacker with network access to the aggregator's gRPC port can call `InternalSendTx` with any valid Bitcoin transaction they authored (e.g., paying to themselves), and `internal_send_tx` will accept it and queue it in `tx_sender` with no accounting link to any deposit or withdrawal — breaking the claimed binding, since the broadcast tx need not have been presigned or authored by the aggregator's own signing pipeline at all.

Existing guards referenced in the audit checklist (`is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`, `lc_proof_verifier`) are not invoked anywhere in this code path, so none of them mitigate this. The only real guard is `only_aggregator_and_self`, and it is bypassed by design whenever `Interceptors::Noop` is configured.

### Impact Explanation
This matches the High-severity category "an unauthenticated state-changing or broadcasting call" directly: any reachable caller can get the aggregator's tx-sender background task to accept and process (and, via its bitcoind wallet connection, fee-bump/broadcast) a transaction the aggregator never authored, with zero database linkage to a deposit or withdrawal. The action is repeatable on every call and is not scoped to a single deposit/operator — it applies globally to the aggregator instance as long as the RPC is reachable without authentication. It does not itself move funds out of a move-to-vault UTXO or forge N-of-N signatures (no bridge collateral is spent by this call alone; the tx must already be attacker-funded/attacker-signed), so the concrete financial-loss categories (Critical) are not directly demonstrated here, but the unauthenticated broadcasting-call category (High) applies as stated in the question.

### Likelihood Explanation
The finding is entirely conditional on the precondition explicitly stated in the question: `Interceptors::Noop` is active, i.e., the aggregator is deployed with `client_verification = false` in its `BridgeConfig`. I was not able to confirm, within the available index, what the default/production value of `client_verification` is (the code, tests, and docker configs reference it in `core/src/config/mod.rs`, `core/src/config/env.rs`, and the sample `bridge_config.toml` files, but I could not read their contents in this session to determine the shipped default). If `client_verification = true` (the `OnlyAggregatorAndSelf` interceptor), this call is blocked for any caller lacking the aggregator's own leaf certificate, and the finding does not apply. The attacker cost is minimal (no BTC/fees required to merely call the RPC; fees are only needed if they want their own tx to actually confirm), but the precondition (misconfigured/disabled mTLS) must hold for exploitation.

### Recommendation
Add an application-layer check inside `internal_send_tx` that does not rely solely on the transport-level interceptor: verify the decoded transaction against a known presigned-transaction record (e.g., match it by txid/inputs against `tx_sender`'s or a bridge-transaction-graph table keyed to a deposit/round/kickoff ID) before calling `insert_try_to_send`, and reject any transaction that cannot be attributed to the aggregator's own signing pipeline. Additionally, ensure `client_verification` cannot be disabled for production-facing aggregator deployments (e.g., fail startup if `client_verification == false` outside of test builds) so `Interceptors::Noop` is never used for internet-reachable aggregator gRPC ports.

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}
