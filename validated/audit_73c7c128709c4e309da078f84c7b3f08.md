This confirms the impact: jobs use `shop = Shop.find_by(shopify_domain: shop_domain)` and then run `shop.with_shopify_session` — i.e., the value of the unauthenticated `x-shopify-shop-domain` header directly selects which shop's stored access token/session is used to process the (attacker-supplied-body) webhook data.

### Title
Webhook HMAC verification does not bind the shop domain, allowing cross-shop webhook forgery - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
`ShopifyApp::WebhookVerification#verify_request` validates only that `request.raw_post` matches an HMAC computed with the app's shared secret; the `X-Shopify-Shop-Domain` header used to select which shop the webhook applies to is never included in that HMAC computation, so it is not authenticated at all.

### Finding Description
The verification logic computes and compares an HMAC purely over the raw request body: [1](#0-0) 

```ruby
def hmac_valid?(data)
  secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)
  secrets.any? do |secret|
    ...
    ActiveSupport::SecurityUtils.secure_compare(shopify_hmac, Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)))
  end
end
```

`WebhookVerification#verify_request` only checks `hmac_valid?(request.raw_post)`, and the shop is read separately, unauthenticated, from a plain header: [2](#0-1) 

The app-level secret used for HMAC is identical for every shop that installs the app — it is not shop-specific. This means a valid `(body, HMAC)` pair produced for one shop's webhook remains valid for the exact same body regardless of what value is placed in the `X-Shopify-Shop-Domain` header, since that header is not part of the signed material. This is directly analogous to the reported `Gateway` issue, where a signed message lacked the `account` field, letting a signature valid for one account be replayed for any account controlled by the same signer — here, a signature valid for one shop's webhook body can be replayed while claiming any other shop's domain.

Generated webhook job templates then trust this unauthenticated header to select the shop record and its persisted OAuth session, and run the webhook body's contents against that shop's access token: [3](#0-2) 

Because `Registry.process`/the job handler receives `shop:` straight from the header, an attacker who owns (or has previously observed) any shop with the app installed can capture one legitimately-HMAC'd webhook request to the app's shared webhook endpoint, then replay that exact body/HMAC to the same endpoint while substituting an arbitrary victim `myshopify.com` domain in the `X-Shopify-Shop-Domain` header. The signature check passes because it never covered the header, and the resulting job executes using the victim shop's `with_shopify_session`/stored access token, with webhook content the attacker fully controls (subject only to whatever body they previously captured/observed).

### Impact Explanation
This allows cross-shop webhook forgery: an attacker-controlled webhook body can be attributed to and processed against an unrelated victim shop's stored session/access token. Depending on the job's logic (order/customer/product update handlers, GDPR redact jobs, etc.), this can result in unauthorized data processing, deletion, or state changes performed under a victim merchant's authenticated session, all triggered by an unrelated party's HTTP request with no interaction from the victim. This satisfies the "accepted forged signed request" / "cross-shop access" bar.

### Likelihood Explanation
Exploitation requires the attacker to have access to at least one valid `(body, HMAC)` pair for the target app (trivially available to anyone who installs the app themselves and receives their own legitimate webhooks, since they can inspect/log the request their own server receives), then simply resend it with a modified domain header to the app's fixed webhook endpoint. No secret material needs to be broken; the shared secret being identical across shops for the same app is standard Shopify behavior, so this is straightforward and reliably reproducible for any app relying on the generated webhook flow.

### Recommendation
Bind the shop identity into the authenticated material, e.g. verify the HMAC over `request.raw_post` plus the `X-Shopify-Shop-Domain` header (or otherwise incorporate the shop into the signed payload), or independently confirm the header's shop actually matches a shop for which this specific webhook body/topic was legitimately issued (e.g., cross-check against `ShopifyAPI::Webhooks::Registry`'s own shop-binding if available in the underlying `shopify_api` gem, which typically ties verification to the exact request as received from Shopify rather than re-derivable fields). At minimum, document that generated job templates must not blindly trust `shop_domain` from the webhook payload without additional shop-scoped authorization checks before acting with the shop's session.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook event (e.g. `products/update`) and capture the resulting HTTP request Shopify sends to the app's webhook endpoint, including `X-Shopify-Hmac-Sha256` and the raw body.
2. Replay that exact request to the same webhook endpoint, changing only the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`.
3. Observe that `ShopifyApp::WebhookVerification#verify_request` still passes (`hmac_valid?` only checks the unmodified body against the HMAC), per [4](#0-3) .
4. The dispatched job resolves `shop = Shop.find_by(shopify_domain: "victim.myshopify.com")` and executes `shop.with_shopify_session` using the victim's stored token while processing the attacker-supplied webhook body, per [3](#0-2) .
