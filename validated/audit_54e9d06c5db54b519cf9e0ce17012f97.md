### Title
Shared `BalanceHandler` instance across nested/recursive precompile calls corrupts balance-sync accounting between native bank ledger and EVM StateDB - (File: `precompiles/common/balance_handler.go`)

### Summary
The C4 report describes a reentrancy hazard where `Trader.executeTrade` calls an untrusted external `market` contract mid-execution, allowing a re-entrant call to corrupt in-progress accounting before the outer call finishes. The Cosmos EVM analog is the precompile `BalanceHandler` mechanism used to reconcile native bank-module coin movements with the EVM `StateDB`: several production precompiles (staking, distribution, erc20, gov, ics20, slashing, werc20, bank) hold a single long-lived `BalanceHandler` instance rather than creating a fresh one per call frame. When a precompile call causes a nested/recursive EVM or precompile call within the same transaction (analogous to the untrusted callback in the report), the inner invocation's `BeforeBalanceChange` overwrites the shared `prevEventsLen` field, so the outer call's `AfterBalanceChange` computes the wrong "delta window" of bank events and applies incorrect (or missing/duplicated) balance adjustments to the EVM `StateDB`.

### Finding Description
`BalanceHandler.BeforeBalanceChange` simply records the current event count and `AfterBalanceChange` replays events from that recorded index onward, applying `StateDB.AddBalance`/`SubBalance` for every `coin_spent`/`coin_received`/fractional-balance event emitted since: [1](#0-0) [2](#0-1) 

This is safe only if `BeforeBalanceChange`/`AfterBalanceChange` pairs never interleave. The generic `RunNativeAction` helper avoids this by allocating a brand-new `BalanceHandler` for every single call via a factory: [3](#0-2) 

However, the debug precompile (which mirrors the pattern used by the production precompiles, all of which reference `GetBalanceHandler()`/`NewBalanceHandler()` per their constructors rather than per call) instead reuses a single handler instance stored on the precompile struct: [4](#0-3) [5](#0-4) 

Because the handler instance is shared, a nested precompile/EVM call executed in between (e.g. `Call0` making a re-entrant `CallEVMWithData` call before the outer `Call0`'s `AfterBalanceChange` executes) resets `prevEventsLen` to the inner call's start point. The outer call's subsequent `AfterBalanceChange` then processes the wrong slice of the event log — either replaying events that were already applied by the inner call's own `AfterBalanceChange` (double-crediting/debiting a `StateDB` balance) or skipping legitimate events belonging to the outer call (under-crediting, i.e., silently dropping a balance update). The repository itself documents and reproduces this exact defect: [6](#0-5) [7](#0-6) 

The affected precompiles that reference the shared-handler pattern (2 references each to `NewBalanceHandler`/`GetBalanceHandler`, in constructor + `Run`) include: `precompiles/staking/staking.go`, `precompiles/distribution/distribution.go`, `precompiles/erc20/erc20.go`, `precompiles/gov/gov.go`, `precompiles/ics20/ics20.go`, `precompiles/slashing/slashing.go`, `precompiles/werc20/werc20.go`, `precompiles/bank/bank.go`.

### Impact Explanation
This breaks the "Asset-representation path" invariant explicitly called out in scope: native bank coins, EVM `StateDB` balances, and precompile-visible balances must remain 1:1. If nested/recursive precompile invocation (a contract calling one precompile which in turn triggers another precompile call, or two sequential precompile calls interleaved with an internal call, all within one EVM message) causes `AfterBalanceChange` to mis-replay events, the EVM-visible balance of an account can diverge from its true bank-module balance — either being credited more EVM-side balance than actually exists in the bank ledger (spendable-value duplication) or having a legitimate credit silently dropped (fund freezing from the EVM's perspective). Either outcome matches the Critical impact gate (accounting corruption / unauthorized duplication or freezing of spendable user value across native and EVM balances).

### Likelihood Explanation
Triggering requires an unprivileged user to deploy/call a contract that performs a nested call sequence into a precompile such that two `BeforeBalanceChange`/`AfterBalanceChange` windows on the same precompile instance overlap within a single transaction — the project's own regression test demonstrates this is reachable via ordinary contract-to-precompile calls (`callback()`/nested `CallEVMWithData`), not via any privileged path. This is a normal, permissionless interaction pattern (a caller contract invoking a precompile method that itself performs further calls), making the likelihood non-trivial, though the exact confirmed reproduction here uses the test/debug precompile; whether every listed production precompile (staking/distribution/erc20/ics20/gov/slashing/werc20/bank) is reachable via the same recursive-call pattern in normal transaction flow was not independently verified within this investigation and would need targeted testing per precompile.

### Recommendation
Instantiate a new `BalanceHandler` (or equivalent event-window state) per call frame for every precompile, matching the `RunNativeAction`/`BalanceHandlerFactory` pattern already used elsewhere in the codebase, instead of storing a shared handler on the long-lived `Precompile` struct. Alternatively, make `prevEventsLen` stack-based (push/pop) so nested calls cannot clobber an outer call's recorded starting offset.

### Proof of Concept
The repository's own test reproduces the mechanism end-to-end: it deploys a caller contract that invokes the debug precompile's `callback()` method, which recursively calls back into the EVM/precompile before its own `AfterBalanceChange` runs, and the test explicitly asserts the resulting (documented-as-buggy) event/state counts, confirming that recursive precompile invocation corrupts the shared `BalanceHandler`'s bookkeeping. 		ConstructorArgs: []interface{}{},
	}

	s.Require().NoError(err)
	s.chain.NextBlock()
