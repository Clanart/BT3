## #Vulnerability found

### Title
Missing threshold/zero-value check on governance parameter `kip71.gastarget` causes division-by-zero panic in base fee calculation - ([File: params/kip71_config.go])

### Summary
The KIP-71 (Magma) dynamic base-fee mechanism computes the next block's base fee using `GasTarget` as a divisor. The governance parameter `Kip71GasTarget` that feeds this value has no lower-bound/threshold validation — its `FormatChecker` is a no-op that accepts any `uint64`, including `0`. If this parameter is ever set to `0` (via either contract governance's `GovParam.setParam`/`setParamIn`, which is owner-controlled similarly to the referenced report's `setMinRental()`, or via header governance voting), every node that later computes `NextMagmaBlockBaseFee` for a block with nonzero gas usage divides by zero and panics.

### Finding Description
`Kip71GasTarget` is declared with `noopFormatChecker`, meaning no range check whatsoever is enforced when the parameter is set: [1](#0-0) 

Compare this to the sibling parameter `BaseFeeDenominator`, whose consumer function explicitly guards against a zero value by falling back to a safe default: [2](#0-1) 

No equivalent guard exists for `GasTarget`. In `NextMagmaBlockBaseFee`, `gasTarget := kc.GasTarget` is used directly as a divisor in both the "gas used > target" and "gas used < target" branches: [3](#0-2) 

If `GasTarget == 0`, then for any block with `parentGasUsed > 0`, the code takes the `parentGasUsed > gasTarget` branch and executes `y := x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e. `big.Int.Div(x, 0)`, which panics in Go's `math/big` package.

The value is set through the GovParam contract's `setParam`/`setParamIn` (owner-gated, transaction-reachable): [4](#0-3) 

or through header-governance voting, where `checkConsistency` performs bound checks for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` against each other but has no such consistency check for `Kip71GasTarget`, `Kip71BaseFeeDenominator`, or `Kip71MaxBlockGasUsedForBaseFee`: [5](#0-4) 

This is the same bug class as the referenced finding: a critical safety-relevant divisor parameter (`minRentalDayDivisor` in the report, `GasTarget` here) can be set by a privileged-but-reachable-via-transaction actor without any threshold/zero check, breaking a core protocol invariant.

### Impact Explanation
Once `Kip71GasTarget` is set to `0` and takes effect, every node computing the next base fee for a block that used any gas (`parentGasUsed > 0`) — both during block production and during header verification via `VerifyMagmaHeader` — will panic inside `NextMagmaBlockBaseFee`. Because this logic runs identically on every full node/validator processing the chain, this results in a simultaneous crash across the network, effectively halting block production and header verification network-wide (chain halt / consensus-critical DoS), not merely a resource-only issue on a single node.

### Likelihood Explanation
The value is only settable through governance mechanisms (contract governance owner via `setParam`/`setParamIn`, or a governance vote submitted by the governing node/validator), so it requires a privileged party in the governance path, matching the "governance parameters" class in scope. There is no on-chain validation preventing the value `0` from being accepted and activated once submitted, since `noopFormatChecker` accepts any `uint64` and no consistency check exists for this parameter in `checkConsistency`.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) in `kaiax/gov/param.go` that rejects `0` (and any other value that would break the base-fee formula), analogous to the bound check already present for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` in `checkConsistency`. Additionally, add a defensive zero-check fallback in `NextMagmaBlockBaseFee` (`params/kip71_config.go`) for `GasTarget`, mirroring the existing fallback already implemented for `BaseFeeDenominator`.

### Proof of Concept
1. Governance owner (via `GovParam.setParam`/`setParamIn`) or governing node (via header vote) sets `kip71.gastarget` to `0`.
2. Once the parameter activates, at the next block with `parentHeaderGasUsed > 0`, `NextMagmaBlockBaseFee` executes `x.Div(x, new(big.Int).SetUint64(0))` in the `parentGasUsed > gasTarget` branch: [6](#0-5) 
3. This causes a panic in every node calling `NextMagmaBlockBaseFee` (both proposers building blocks and validators verifying headers via `VerifyMagmaHeader`), halting the chain.
