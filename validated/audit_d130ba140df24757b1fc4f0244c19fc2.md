### Title
Unauthenticated OP_RETURN in `payout_tx` lets an unprivileged party rebind `deposit_constant`'s operator key away from the actual kickoff operator, causing an honest operator's Disprove-defense proof to fail and their collateral to be burned - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` builds the `payout_tx`'s OP_RETURN (naming the fronting operator) as a plain, unsigned output while the user's withdrawal input is only ever signed with `SinglePlusAnyoneCanPay`, which covers input0 and output0 only. Anyone possessing that reusable signature (the withdrawing party, or anyone who observes it before confirmation) can broadcast a variant of `payout_tx` that keeps input0/output0 intact but sets the OP_RETURN to name a different operator, and if this variant is the one that gets mined, the bridge circuit's `deposit_constant` (`operator_xonlypk` field, parsed from that OP_RETURN) diverges from the value the verifier independently derives from `kickoff_data.operator_xonly_pk` when checking the Disprove conditions, causing an honest operator's collateral to be burned.

### Finding Description
The claimed binding is:
`deposit_constant.operator_xonlypk` (as read by the bridge circuit / verifier's expected-value computation) `==` `kickoff_data.operator_xonly_pk` (the operator that actually spent its own Round UTXO to send the Kickoff).

`create_payout_txhandler` [1](#0-0)  builds `payout_tx` with:
- input0: the user's withdrawal UTXO, spent key-path with `user_sig`
- output0: the user's payout
- output2: an OP_RETURN containing `operator_xonly_pk` (whichever operator calls `withdraw`)

The user signature's sighash type is enforced to be `SinglePlusAnyoneCanPay` [2](#0-1) , and it is verified against exactly that sighash in `Operator::withdraw` [3](#0-2) . `SIGHASH_SINGLE|ANYONECANPAY` only commits to input0 and the output at the same index (output0); it commits to neither output1 (anchor) nor output2 (OP_RETURN). Consequently, the OP_RETURN naming the operator is **not cryptographically bound** by the withdrawing user's signature, and anyone who has that signature (the withdrawer themselves, or anyone who intercepts it) can construct and race an alternate `payout_tx` that reuses the exact same input0/output0/signature but a different OP_RETURN naming an arbitrary registered operator B, while operator A is the one who actually performs (or intends to perform) the real fronting and subsequently sends the real Kickoff from its own Round UTXO.

Once a payout tx is mined, `update_finalized_payouts` blindly trusts whatever OP_RETURN ends up on-chain to populate the DB's payer-operator column [4](#0-3) .

Two independent consumers then read this externally-malleable field:

1. `is_kickoff_malicious` compares the DB's OP_RETURN-derived operator against `kickoff_data.operator_xonly_pk` and flags A's legitimate kickoff as malicious if they differ [5](#0-4) . This confirms the binding is *intended* to hold, but does not stop the divergence from happening or from later causing damage — it only triggers a Challenge in permissive network configs (challenges are not sent automatically on mainnet/testnet4).

2. Once Challenged, A must go through the assert+Disprove-defense flow. The bridge circuit computes `deposit_constant` by parsing the OP_RETURN of the **actually mined** `payout_spv.transaction` (`operator_xonlypk` = B, since that's what got mined) combined with `round_txid`/`vout` taken from the actual `kickoff_tx.input[0]` (A's Round, since A genuinely sent the kickoff) [6](#0-5) . This is the value baked into A's real proof's journal hash.

But `verify_additional_disprove_conditions`, which the verifiers run to decide whether to burn the operator's collateral, computes the "expected" `deposit_constant` using `kickoff_data.operator_xonly_pk` directly (i.e., always A), independent of whatever OP_RETURN actually got mined [7](#0-6) . The two computed values now differ (B vs A in the `operator_xonlypk` field), the operator's on-chain-committed Groth16 public-input assertions produced from their real proof cannot match this "expected" script, and `verify_additional_disprove_conditions` treats this exactly like a faulty proof, allowing verifiers to send `Disprove` and burn operator A's collateral [8](#0-7)  — despite A having behaved completely honestly. The root cause is that the only on-chain anchor for "who fronted this payout" (the OP_RETURN) is unauthenticated and freely rewritable by anyone with the reusable `SinglePlusAnyoneCanPay` signature, while the rest of the protocol (verifier's expected value, `is_kickoff_malicious`) assumes it faithfully reflects the operator that later sends the Kickoff.

### Impact Explanation
An unprivileged party (the withdrawing user themselves, or anyone racing to mine a competing spend of the same withdrawal UTXO reusing its `ANYONECANPAY` signature) can pick an arbitrary OP_RETURN operator key with zero special privilege, at the cost of ordinary Bitcoin transaction/relay fees. This can cause an honest operator's Kickoff to be flagged malicious pre-emptively, and — more critically — can make the honest operator's real Disprove-defense proof permanently unable to satisfy the verifier's independently-computed "expected" `additional_disprove_script` constant, resulting in the operator's 5-week-timelocked disprove/collateral output being burned via a legitimate-looking `Disprove` transaction. This is repeatable per withdrawal/deposit and does not depend on which operator is targeted, since the attack only requires access to the reusable user signature for that specific withdrawal.

### Likelihood Explanation
The precondition is simply that the attacker (who may be the withdrawing user itself, per the given threat model capabilities: choosing withdrawal UTXO bytes, a Schnorr signature and its sighash flag, and calling the aggregator's `withdraw` gRPC) gets a variant of the payout tx with a differing OP_RETURN mined instead of, or in a race against, the operator's own broadcast — feasible at the cost of normal transaction fees, without needing hashrate, keys, or any privileged role.

### Recommendation
Cryptographically bind the OP_RETURN operator commitment to the signed payout data — e.g. require the withdrawing user's signature to cover the OP_RETURN output (use `SIGHASH_ALL`/`SIGHASH_SINGLE` covering all relevant outputs, or move the operator commitment into a script/output that participates in sighash computation), or otherwise have the bridge circuit and `verify_additional_disprove_conditions` derive the operator identity from a source that cannot be rewritten independently of the Kickoff/Round input (e.g., re-derive strictly from `kickoff_data`/`kickoff_tx` inputs on both sides consistently) rather than trusting an unauthenticated OP_RETURN in the mined payout transaction.

### Proof of Concept
```
cargo test -p circuits-lib bridge_circuit_op_return_malleation -- --nocapture
```
Plan for the test (to be run against regtest, no mainnet/live Citrea needed):
1. Build a `payout_tx` via `create_payout_txhandler` for operator A with a `SinglePlusAnyoneCanPay` user signature.
2. Construct a second variant of the same tx reusing input0/output0/signature but replacing the OP_RETURN with operator B's xonly pk; verify with `SECP.verify_schnorr` (as done in `Operator::withdraw`) that the same signature validates for both variants under `calculate_sighash_txin(0, SinglePlusAnyoneCanPay)`.
3. Feed operator A's real `kickoff_tx` (with round input pointing at A's Round UTXO) plus the "B-named" mined `payout_spv.transaction` into `host_deposit_constant`/`deposit_constant` (`circuits-lib/src/bridge_circuit/mod.rs`) and assert the resulting `operator_xonlypk` equals B, not A.
4. Separately call the equivalent of `verify_additional_disprove_conditions`'s inline `deposit_constant(kickoff_data.operator_xonly_pk.serialize(), ...)` with A's key and the same `round_txid`/`vout`, and assert the two `DepositConstant` values are unequal — demonstrating the binding break and that an honest proof from step 3 cannot satisfy the verifier's expectation from step 4.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }
