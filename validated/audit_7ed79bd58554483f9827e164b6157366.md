## Title
Fee-on-transfer / rebasing input tokens create escrow insolvency in `IntentGatewayV2.placeOrder` (Tron deployment) — attacker withdraws more than actually escrowed - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external report's core invariant — "escrow accounting must reflect the amount the contract *actually* received, not the amount requested" — is enforced in the canonical EVM `IntentGatewayV2.sol` (which measures `balanceOf` before/after every `safeTransferFrom` and mutates `order.inputs[i].amount` to the real received value), but this fix is missing from the Tron variant of the same contract. There, escrow credit is derived purely from the user-supplied `order.inputs[i].amount` even though the actual token transfer may deliver less (fee-on-transfer/rebasing tokens), producing a ledger that overstates the contract's true token balance.

### Finding Description
In the canonical contract, `placeOrder` reconciles escrow to real transfers: [1](#0-0) 

In the Tron deployment, the equivalent path never re-measures balances. The protocol-fee-reduced amount is computed directly from the *requested* `order.inputs[i].amount` before any transfer occurs: [2](#0-1) 

Then tokens are pulled with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`, and the escrow ledger `_orders[commitment][token]` is credited with `reducedInputs[i].amount` — which is derived from the pre-transfer, pre-fee amount — with no comparison against the contract's actual post-transfer balance: [3](#0-2) 

If `token` charges a transfer fee (or is a rebasing/deflationary token), the gateway physically receives less than `order.inputs[i].amount`, yet `_orders[commitment][token]` is credited with the full (minus only the protocol fee) amount. This inflates the ledger relative to the contract's real balance of that token.

Both `withdraw()` (used for normal fills) and the cancellation/refund path debit `_orders[commitment][token]` and push out `amount` via `token.call(transfer, beneficiary, amount)` without ever checking that the contract's actual token balance supports the payout: [4](#0-3) 

### Impact Explanation
Any unprivileged user can place an order using a fee-on-transfer or rebasing ERC20 as an input. The escrow ledger will record more of that token than the contract actually holds. When that order is later cancelled (refund path) or filled (withdrawal path), the contract pays out the inflated `reducedInputs[i].amount` from its *general* token balance — which is funded by other, unrelated orders' legitimately-escrowed tokens of the same token address. This lets an attacker extract more value than they deposited, at the expense of other users' escrowed funds sharing that token, and/or causes later legitimate withdrawals to revert once the pooled balance is exhausted (fund lock for honest users). This is a direct loss-of-funds / wrong-amount payout scenario, not merely a DoS as in the original Sandclock report.

### Likelihood Explanation
High for any deployment of this Tron `IntentGatewayV2` that allows arbitrary/permissionless input tokens (no on-chain allowlist check on `order.inputs[i].token` is visible in `placeOrder`). No relayer, prover, or governance compromise is needed — a single unprivileged `placeOrder` call with a fee-charging or rebasing token is sufficient to desynchronize escrow accounting from real custody.

### Recommendation
Port the balance-reconciliation logic already present in the canonical `evm/src/apps/IntentGatewayV2.sol` into the Tron variant: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`, and base `reducedInputs`/`_orders[commitment][token]` on the actually-received amount rather than the caller-supplied `order.inputs[i].amount`. Additionally, consider tracking per-token escrow independent of shared contract balance (or validating available balance before payout) so that one order's shortfall cannot be silently subsidized by another order's escrow.

### Proof of Concept
1. Attacker deploys/uses a fee-on-transfer ERC20 `FOT` with e.g. a 50% transfer fee, and has another (unrelated) victim order already escrowing `FOT` in the same gateway (common liquidity, since `_orders` is keyed by `(commitment, token)` but paid out of the contract's shared `FOT` balance).
2. Attacker calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000}`. `safeTransferFrom` moves 1000 nominal, but due to the 50% fee the gateway's actual `FOT` balance only increases by 500.
3. `reducedInputs[0].amount` is computed from `originalAmount = 1000` (minus protocol fee), e.g. ~990 (with 1% protocol fee), and `_orders[commitment][FOT] = 990` even though the contract only holds 500 new `FOT`.
4. Attacker immediately cancels the order (same-chain path calls `withdraw(body, true)`), which transfers `amount = 990` `FOT` to the attacker — 490 more than they actually contributed — drawn from the victim's separately escrowed `FOT` balance held in the same contract.
5. When the victim's own order is later filled/cancelled, the contract lacks sufficient `FOT` balance to honor the legitimate escrow, causing reverts (fund lock) or, if further overdrawn by other attackers, eventual loss for legitimate depositors. [5](#0-4)

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
