### Title
Tokenfactory denom allow-list (recipient/sender restriction) can be bypassed when a CosmWasm contract issues a native `BankMsg::Send` - ([File: sei-wasmd/x/wasm/keeper/keeper.go])

### Summary
The bank module's `IsInDenomAllowList` check — the mechanism by which a tokenfactory admin restricts who may send/receive a given denom (functionally equivalent to a "sanctioned/denylisted user" style restriction) — is enforced only inside `x/bank`'s `MsgSend`/`MsgMultiSend` handlers, not inside the shared low-level `SendCoins` primitive. The CosmWasm bank-transfer bridge (`BankCoinTransferrer.TransferCoins`, used whenever a wasm contract emits a native `BankMsg::Send`) calls `SendCoins` directly after only checking `IsSendEnabledCoins` and `BlockedAddr`, completely skipping the allow-list check. This mirrors the reported bug class: a security precondition exists on one transfer entry point but is missing on another code path that reaches the same underlying transfer primitive.

### Finding Description
`x/bank`'s `msgServer.Send` and `msgServer.MultiSend` enforce the tokenfactory allow-list on both sender and recipient before calling `SendCoins`: [1](#0-0) [2](#0-1) 

`IsInDenomAllowList` is the function that implements this restriction; it is documented as gating token-factory denoms by an explicit address allow-list: [3](#0-2) 

However, `SendCoins` itself (the shared low-level primitive) has no allow-list awareness — this check is a caller responsibility, and not every caller performs it. In particular, the CosmWasm→bank bridge used for native token transfers issued by any wasm contract via `BankMsg::Send` only checks `IsSendEnabledCoins` and `BlockedAddr(toAddr)` before invoking `SendCoins`: [4](#0-3) 

This means any CosmWasm contract that forwards a `BankMsg::Send` for a tokenfactory denom with a configured allow-list (`SetDenomAllowList`, settable at denom creation via `MsgCreateDenom.AllowList` or later via `MsgUpdateDenom.AllowList`) can move that denom to/from addresses that are **not** on the allow-list, bypassing the exact control that a direct `MsgSend`/`MsgMultiSend` transaction enforces: [5](#0-4) [6](#0-5) 

This is structurally identical to the external report's root cause: a `_transfer`-equivalent check ("not sanctioned"/"in allow-list") that is present on one call path but was never added to `_beforeTokenTransfer`-equivalent shared logic reachable via another path.

### Impact Explanation
Denom allow-lists exist specifically so a tokenfactory admin can restrict which addresses may hold/transact a given denom (e.g., compliance-gated or permissioned assets). A CosmWasm contract execution — reachable by any unprivileged user submitting a wasm execute message — that triggers a native coin `BankMsg::Send` bypasses this restriction entirely, letting a restricted/denylisted address receive or move the restricted asset. This undermines the compliance/permission guarantee the allow-list is meant to enforce and could enable unauthorized transfer of a permissioned token, which the admin explicitly intended to prevent by setting an allow-list.

### Likelihood Explanation
Any CosmWasm contract with logic that returns/forwards a `BankMsg::Send` (a first-class capability of essentially every CW contract, e.g., escrow, vault, DEX, payment-splitter contracts) can trigger this path with no special privilege. The bypass requires only that a tokenfactory denom has an allow-list configured, and that some CW contract is deployed which will forward that denom via `BankMsg::Send` — both are ordinary, permissionless conditions.

### Recommendation
Move the `IsInDenomAllowList` (and ideally `BlockedAddr`) enforcement down into the shared `SendCoins`/`InputOutputCoins` primitives in `x/bank/keeper` (or equivalently, add the allow-list check to `BankCoinTransferrer.TransferCoins` in `sei-wasmd/x/wasm/keeper/keeper.go`), so that every caller of the bank transfer primitive is subject to the same restriction, rather than relying on each caller (message handlers, precompiles, wasm bridge, IBC, etc.) to independently re-implement the check.

### Proof of Concept
1. Tokenfactory admin creates denom `factory/<admin>/RESTRICTED` with `AllowList{Addresses: [admin]}` via `MsgCreateDenom`, so only `admin` may hold/transact it (per `x/tokenfactory/keeper/msg_server.go` `CreateDenom`).
2. Attempting a direct `MsgSend` of this denom to a non-allow-listed address `evil` fails with `"is not allowed to receive funds"` (enforced in `sei-cosmos/x/bank/keeper/msg_server.go`).
3. Deploy/execute any CosmWasm contract that returns a `BankMsg::Send` transferring `factory/<admin>/RESTRICTED` to `evil` (e.g., a simple pass-through/escrow contract executed by `admin` or by any account holding the funds).
4. The wasm keeper routes this through `BankCoinTransferrer.TransferCoins` (`sei-wasmd/x/wasm/keeper/keeper.go:1198-1221`), which only checks `IsSendEnabledCoins` and `BlockedAddr(evil)` — both pass — and calls `SendCoins` directly, succeeding despite `evil` not being on the denom's allow-list.
5. `evil` now holds the restricted token, which the allow-list was configured to prevent.

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

// TransferCoins transfers coins from source to destination account when coin send was enabled for them and the recipient
// is not in the blocked address list.
func (c BankCoinTransferrer) TransferCoins(parentCtx sdk.Context, fromAddr sdk.AccAddress, toAddr sdk.AccAddress, amount sdk.Coins) error {
	em := sdk.NewEventManager()
	ctx := parentCtx.WithEventManager(em)
	if err := c.keeper.IsSendEnabledCoins(ctx, amount...); err != nil {
		return err
	}
	if c.keeper.BlockedAddr(toAddr) {
		return sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", toAddr.String())
	}

	sdkerr := c.keeper.SendCoins(ctx, fromAddr, toAddr, amount)
	if sdkerr != nil {
		return sdkerr
	}
	for _, e := range em.Events() {
		if e.Type == sdk.EventTypeMessage { // skip messages as we talk to the keeper directly
			continue
		}
		parentCtx.EventManager().EmitEvent(e)
	}
	return nil
}

func (server msgServer) CreateDenom(goCtx context.Context, msg *types.MsgCreateDenom) (*types.MsgCreateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.Keeper.CreateDenom(ctx, msg.Sender, msg.Subdenom)
	if err != nil {
		return nil, err
	}

	createDenomEvent := sdk.NewEvent(
		types.TypeMsgCreateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeNewTokenDenom, denom),
	)

	if msg.AllowList != nil {
		err = server.validateAllowList(ctx, msg.AllowList)
		if err != nil {
			return nil, err
		}
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		createDenomEvent = createDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}
