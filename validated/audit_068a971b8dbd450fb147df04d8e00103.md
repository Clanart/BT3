### Title
Unbounded allocation/CPU loop in `SchnorrAggregate::read` allows remote denial of service via a 4-byte attacker-controlled count - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The external advisory describes a Denial of Service reachable through a library dependency. The analog in Serai is a DoS reachable through Serai's own deserialization surface: `SchnorrAggregate::<C>::read` reads a little-endian `u32` count directly from an untrusted reader and then iterates that many times calling `C::read_G`, with no upper bound, no size limit, and no relationship to the actual amount of data available. A peer feeding untrusted bytes into `SchnorrAggregate::read` can declare up to `0xFFFFFFFF` aggregate signature nonces, forcing up to ~4.29 billion point-deserialization attempts and vector growth proportional to attacker-supplied length.

### Finding Description [1](#0-0) 

`read` performs:

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
```

Unlike the other length-prefixed readers in the in-scope crates, this count is not clamped:

- `Commitments::read` in PedPoP allocates `Vec::with_capacity(params.t())` — bounded by the locally-configured threshold, not by the peer [2](#0-1) .
- `ThresholdKeys::read` loops `1 ..= n` where `n` is a `u16` and is validated by `ThresholdParams::new` [3](#0-2) .
- FROST `Commitments::read` reads exactly `generators.len()` nonce commitments derived from the local algorithm, not from the wire [4](#0-3) .

`SchnorrAggregate::read` is the outlier: it trusts a 32-bit wire value. Because `read` accepts any `R: Read` (including a streaming/network-backed reader), an attacker is not limited to a pre-sized buffer — they can keep a stream open and feed group elements continuously, and the `Vec<C::G>` keeps growing one heap-allocated point per ~32 bytes of input, so memory consumption grows linearly with attacker traffic with no cap, and the loop can be stretched to billions of iterations.

Additionally, the matching verifier allocates `Vec::with_capacity(2 * keys_and_challenges.len() + 1)` [5](#0-4) , so a deserialized aggregate paired with a caller-built challenge list drives a second large allocation and a `multiexp_vartime` over attacker-controlled statement counts, compounding CPU cost.

### Impact Explanation
An unprivileged party who can cause a Serai-based node/verifier to call `SchnorrAggregate::read` on bytes they control (e.g., any protocol message embedding an aggregate Schnorr signature, or any application feeding peer-supplied bytes into this public API) can cause:

- Memory exhaustion: the `Rs` vector grows without bound for as long as the attacker supplies validly-encoded points.
- CPU exhaustion: up to ~4.29 billion `C::read_G` invocations (each performing a full group decode/validation) even if the input is eventually truncated; the error is only returned when the stream ends.
- Downstream amplification in `verify`, which builds a `pairs` vector of size `2*len+1` and runs a variable-time multiexponentiation over it [5](#0-4) .

This is a classic reachable DoS matching the advisory's class: availability loss triggered entirely by untrusted input size fields, with no cryptographic precondition.

### Likelihood Explanation
`SchnorrAggregate::read` is a public API explicitly designed for reading signatures "from something implementing Read" [6](#0-5) . Any network protocol or service built on `serai-schnorr` that accepts aggregate signatures from peers exposes this. Exploitation requires only sending a 4-byte length of `0xFFFFFFFF` followed by a stream of valid (or even truncated-after-N) group encodings — no valid signature, key, or protocol position is needed. Effort is trivial; the limiting factor is only how long the victim tolerates the connection. Caveat: whether a production Serai component currently wires an unauthenticated network path into this specific reader depends on integrator usage; the vulnerability is in the library contract itself (no bound, no length check), which is what makes it the analog of a dependency-level DoS.

### Recommendation
- Impose a hard upper bound on `len` in `SchnorrAggregate::read` before looping (e.g., a `MAX_AGGREGATE_SIGNATURES` constant consistent with the protocol's threshold `n`, or a parameter the caller supplies), returning an `io::Error` when exceeded.
- Alternatively, require the caller to pass the expected count and verify `len == expected`, mirroring how `Commitments::read` derives its count from `ThresholdParams` rather than from the wire [3](#0-2) .
- Consider pre-checking remaining input length where the reader supports it, so a declared count larger than available bytes fails immediately instead of after partial allocation.
