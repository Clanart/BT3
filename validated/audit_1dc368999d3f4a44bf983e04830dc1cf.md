Based on my research, I found a genuine analog. The `mempool_manager.py` module contains a canonical-CLVM-encoding checker that walks an untrusted, attacker-supplied byte buffer using length-prefix fields to compute how far to advance an offset — structurally the same bug class as CVE-2019-20629 (parsing a length-prefixed field in an untrusted binary blob without validating the offset stays within buffer bounds before dereferencing).

### Title
Unbounded offset advance in `is_atom_canonical`/`is_clvm_canonical` on attacker-controlled spend-bundle CLVM bytes causes unhandled out-of-bounds read - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` parse a CLVM-serialized buffer byte-by-byte, using the high bits of each byte to determine a variable-length-prefix size (1–6 bytes) and then indexing further into the buffer to read those prefix bytes and compute `atom_len`, without ever checking that `offset` stays within `len(clvm_buffer)` before dereferencing.

### Finding Description
`is_atom_canonical` inspects `clvm_buffer[offset]` and, depending on the top bits, decides a `prefix_len` of up to 5 additional bytes it must read to build the atom length: [1](#0-0) 

The loop `for i in range(prefix_len): offset += 1; atom_len |= clvm_buffer[offset]` never verifies that `offset < len(clvm_buffer)` before indexing. `is_clvm_canonical` drives this in an unbounded `while True` loop over the whole buffer, likewise indexing `clvm_buffer[offset]` on each iteration without bounds checks (the only length check happens at the very end, `return offset == len(clvm_buffer)`, which is unreachable if an earlier read already threw): [2](#0-1) 

This directly mirrors the GPAC root cause in `gf_m2ts_process_pmt`: a length/descriptor field read from attacker-controlled input is trusted to compute how far into the buffer to read next, without validating that the buffer actually contains that many bytes. In Python, indexing past the end of a `bytes` object raises `IndexError` instead of silently reading adjacent heap memory, so the practical failure mode here is an unhandled exception rather than a silent over-read — but the underlying missing-bounds-check defect and the "crafted, truncated variable-length-prefixed input" trigger are the same class of vulnerability.

Per the surrounding documentation, this canonical-form check runs as part of dedup-eligibility handling for spend bundles processed by the mempool manager (`pre_validate_spendbundle()` / `is_clvm_canonical()` path noted in the `.cursor/context/clvm-execution.md` file map): [3](#0-2) [4](#0-3) 

### Impact Explanation
If a crafted, truncated puzzle-solution buffer (an atom byte whose top bits declare a multi-byte length prefix, e.g. `0xFC`, but the buffer ends before all declared prefix bytes are present) reaches `is_atom_canonical`/`is_clvm_canonical` unguarded by a try/except at the call site, an `IndexError` will propagate out of the canonicalization check during spend-bundle admission. Depending on how the caller handles exceptions, this can abort spend-bundle processing for that item or, in the worst case, propagate further and disrupt mempool-manager request handling for a legitimate submitter — a spend-triggered transaction-processing disruption reachable purely through the mempool admission path from an untrusted spend bundle submitter.

### Likelihood Explanation
The trigger requires only crafting a CLVM-serialized atom/solution blob with a truncated multi-byte length prefix and submitting it as (or as part of) a spend bundle that reaches the dedup-eligibility canonical check — this is directly reachable by any unprivileged spend-bundle submitter with no special privileges, matching the "single submitted spend bundle" reachability bar.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` (verify `offset + prefix_len < len(clvm_buffer)` before the prefix-reading loop) and in `is_clvm_canonical`'s main loop (verify `offset < len(clvm_buffer)` before each `clvm_buffer[offset]` read), raising a handled/expected error (e.g., returning `False`/non-canonical, or a caught `ValueError`) instead of letting an `IndexError` propagate, and ensure the call site of `is_clvm_canonical` in `pre_validate_spendbundle()` catches malformed-input errors gracefully so a single malformed bundle cannot disrupt processing of others.

### Proof of Concept
1. Construct a CLVM byte buffer whose only content is a single byte `0xFC` (indicating a 6-byte length-prefix atom requiring 5 additional prefix bytes) with no following bytes.
2. Call `is_clvm_canonical(b"\xfc")` (or route it through the dedup-eligibility check during spend-bundle admission in `mempool_manager.py`).
3. Execution enters `is_atom_canonical`, matches the `0b11111110 == 0b11111100` branch (`prefix_len = 5`), then the loop attempts `clvm_buffer[offset]` for `offset` values 1 through 5, which are out of range for a 1-byte buffer, raising `IndexError` instead of being rejected as malformed input gracefully.

Note: I was not able to fully trace the exact call site and exception-handling wrapper around `is_clvm_canonical()` within `pre_validate_spendbundle()` due to tool-call budget limits in this session — confirming whether the `IndexError` is actually caught/handled upstream (which would reduce this to a benign rejection rather than a processing-halt DoS) requires reviewing that call site directly.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```

def is_clvm_canonical(clvm_buffer: bytes) -> bool:
    """
    checks whether the CLVM serialization is all canonical representation.
    atoms can be serialized in more than one way by using more bytes than
    necessary to encode the length prefix. This functions ensures that all atoms are
    encoded with the shortest representation. back-references are not allowed
    and will make this function return false
    """
    assert clvm_buffer != b""

    offset = 0
    tokens_left = 1
    while True:
        b = clvm_buffer[offset]

        # pair
        if b == 0xFF:
            tokens_left += 1
            offset += 1
            continue

        # back references cannot be considered canonical, since they may be
        # encoded in many different ways
        if b == 0xFE:
            return False

        # small atom or NIL
        if b <= 0x80:
            tokens_left -= 1
            offset += 1
        else:
            atom_len, canonical = is_atom_canonical(clvm_buffer, offset)
            if not canonical:
                return False
            tokens_left -= 1
            offset += atom_len

        if tokens_left == 0:
            break

    # if there's garbage at the end, it's not canonical
    return offset == len(clvm_buffer)
```

## Canonical serialization

**Location**: `mempool_manager.py:185`

### `is_clvm_canonical(clvm_buffer)`

Checks that a CLVM program uses shortest-form atom encoding:

- No unnecessary length prefix bytes
- No back-references (`0xFE` byte)
- No trailing garbage

### When enforced

Required for DEDUP-eligible spends. Without canonical form, identical
solutions could have different serializations, breaking dedup.

### `is_atom_canonical(clvm_buffer, offset)`

Validates a single atom's length prefix encoding. The CLVM format uses
variable-length prefixes (1-6 bytes) based on atom size. Each prefix
length has a minimum atom size threshold.
