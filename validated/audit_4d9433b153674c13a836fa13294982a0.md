### Title
Attacker can frequently claim vlMGP/mWOMSV rewards in small increments to round the expiration-forfeit down to zero, stealing yield owed to other stakers - (File: rewards/vlMGPBaseRewarder.sol / rewards/mWOMSVBaseRewarder.sol)

### Summary
`vlMGPBaseRewarder._calExpireForfeit()` (mirrored identically in `mWOMSVBaseRewarder._calExpireForfeit()`) computes a percentage-based forfeiture of a user's accrued rewards depending on how much of their vlMGP/mWomSV position is currently unlocked or in cooldown, and explicitly rounds the forfeit down to zero for "dust" amounts. Because the function is invoked every time a user calls `getReward`/`getRewards`, an ordinary user can claim in many small increments instead of one large claim, causing the truncating division and the explicit dust-skip to zero out the forfeit almost every time, letting them keep reward that should have been redistributed to other stakers as `forfeitAmount`. [1](#0-0) [2](#0-1) 

### Finding Description
`_calExpireForfeit` computes:
```
rewardableAmount = _amount * rewardablePercentWAD / 1e18;
forfeitAmount = _amount - rewardableAmount;
if (forfeitAmount < (_amount / 1000)) { forfeitAmount = 0; rewardableAmount = _amount; }
``` [1](#0-0) 

This is called from `_sendReward`, which is reached on every user-initiated `getReward`/`getRewards` claim:
```
function _sendReward(address _rewardToken, address _account, address _receiver) internal {
    uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
    uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;
    ...
    if(forfeitAmount > 0)
        _queueNewRewardsWithoutTransfer(forfeitAmount, _rewardToken);
}
``` [3](#0-2) 

The forfeit represents the share of new rewards that a user with a partially-unlocked/expired position should give up (redistributed as new rewards to other stakers via `_queueNewRewardsWithoutTransfer`). Both the truncating multiplication/division (`_amount * rewardablePercentWAD / 1e18`) and, more critically, the explicit `forfeitAmount < _amount/1000` dust-skip mean that whenever a user claims a *small enough* pending reward amount, the entire forfeit is waived. `getReward`/`getRewards` are freely callable by the account owner (via MasterMagpie) with no minimum-amount check and no cooldown between claims:
```
function getRewards(address _account, address _receiver, address[] memory _rewardTokens)
    public onlyMasterMagpie updateRewards(_account, _rewardTokens) nonReentrant
``` [4](#0-3) 

A user whose `rewardablePercentWAD` (computed in `VLMGP.getRewardablePercentWAD`) is below 100% — i.e., anyone who still has locked-then-cooling-down/expired vlMGP — normally forfeits a proportional slice of every reward claim. By claiming very frequently (each call keeping `userRewards[token][account]` tiny), the attacker forces `forfeitAmount` to compute to 0 (via truncation or the explicit dust bypass) on essentially every claim, so across the full accrual period they pay effectively no forfeit at all, versus the intended proportional forfeit that a single lump-sum claim would incur.

This is the direct analog of the reported DeliHook bug: a percentage fee/penalty computed via integer division on a user-controlled-size amount, callable repeatedly and cheaply, can be driven to zero by shrinking the per-call amount, causing systemic underpayment of the amount owed to other protocol participants.

### Impact Explanation
The forfeited amount is not burned; it is redistributed as new rewards to other vlMGP/mWOMSV stakers (`_queueNewRewardsWithoutTransfer`). By evading the forfeit, the attacker directly steals yield that other stakers are entitled to receive — a theft of unclaimed yield from the reward pool, satisfying the "theft or permanent freezing of unclaimed yield" impact bar. Because reward accrual and the ability to claim in small chunks is unrestricted and repeatable indefinitely, this can be exploited continuously and at scale for any account with `rewardablePercentWAD` < 100%.

### Likelihood Explanation
Likelihood is high for any user who intentionally keeps part of their MGP/mWom locked position in cooldown/expired state while still farming vlMGP/mWOMSV rewards — a state reachable through normal, unprivileged `startUnlock`/`unlock` interactions. The only cost to the attacker is gas from calling `getReward`/`getRewards` frequently, which is cheap and can be automated/bundled, mirroring the gas-economics argument in the original report.

### Recommendation
Round the forfeit calculation up (ceiling division) instead of down, and remove (or dramatically shrink and make time/amount-invariant) the dust-skip threshold so that splitting claims into many small calls cannot cause the cumulative forfeit to differ from a single large claim. Alternatively, track forfeiture on a rate/time-accrual basis independent of the size of each individual claim, so that claim frequency cannot be used to manipulate the amount forfeited.

### Proof of Concept
1. User locks MGP in `VLMGP` and starts an unlock (`startUnlock`) for part of their position, then lets the slot's cooldown expire without calling `unlock()`. This gives them a `rewardablePercentWAD` below 100% (per `VLMGP.getRewardablePercentWAD`), meaning normally a percentage of any new vlMGP-related reward accrual should be forfeited on claim. [5](#0-4) 
2. Instead of calling `getReward` once after rewards have accumulated substantially, the user calls `getReward`/`getRewards` on `vlMGPBaseRewarder` every block (or as often as gas allows), each time claiming only the tiny amount of `userRewards[token][account]` accrued since the last call.
3. Each call computes `_calExpireForfeit(account, tinyAmount)`; because `tinyAmount * (1e18 - rewardablePercentWAD)/1e18` truncates to 0, or falls below the `_amount/1000` dust threshold, `forfeitAmount` is 0 on (nearly) every call. [1](#0-0) 
4. Over time, the attacker receives the full accrued reward with effectively zero forfeiture, whereas a single lump-sum claim of the same total accrued amount would have forfeited a meaningful percentage to `_queueNewRewardsWithoutTransfer` for other stakers.

The core rounding-down/dust-skip logic and its reachability from an unprivileged user's `getReward` calls is, however, directly supported by the code shown above.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
