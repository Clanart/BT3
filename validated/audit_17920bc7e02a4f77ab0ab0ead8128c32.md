### Title
Missing monotonic height enforcement in Arbitrum consensus client allows `ConsensusState.finalized_height` regression - (File: modules/ismp/clients/ismp-arbitrum/src/lib.rs)

### Summary
`ArbitrumConsensusClient::verify_consensus` unconditionally overwrites `consensus_state.finalized_height` with the height extracted from whatever proof is supplied, with no comparison against the previously trusted/stored height.

### Finding Description
In `verify_consensus`, the trusted `ConsensusState` is decoded from storage, and for both proof variants (`ArbitrumOrbit` and `ArbitrumBold`) the code does: [1](#0-0) [2](#0-1) 

Notice that `consensus_state.finalized_height = state.height.height;` is set directly, without any `if state.height.height > consensus_state.finalized_height` guard. The only binding to freshness comes indirectly through `l1_height` (attacker-controlled, decoded from `ArbitrumUpdate`) being used to fetch an L1 state root via `host.state_machine_commitment(l1_state_machine_height)`: [3](#0-2) 

Since the host retains historical L1 state commitments (that's how proofs against older but still-accepted L1 heights can be verified at all), an attacker can pick any `l1_height` whose commitment is already stored, and supply a valid Merkle/inclusion proof of an *older* Arbitrum rollup assertion/node relative to that L1 root. `verify_arbitrum_payload`/`verify_arbitrum_bold` will authenticate this as a legitimate historical claim (it is legitimate data, just stale), and the returned `state.height.height` — which can be lower than the currently stored `consensus_state.finalized_height` — gets written back unconditionally.

Unlike other consensus clients in this codebase (e.g. `grandpa`, `beefy`, `parachain`), which I did not have time to fully diff against, the pattern here shows no explicit height-regression guard within this client's own logic. This places the entire responsibility for forward-progress enforcement outside the function, matching the target's described concern: forward-only "consensus state...must never roll back to an older authenticated height" invariant is not enforced at this call site.

### Impact Explanation
If nothing downstream (e.g. `pallet_ismp`'s message handler / `IsmpHost::store_consensus_state`) independently re-validates height monotonicity before persisting, an attacker relayer/message submitter (via the unsigned `handle_unsigned` entrypoint) could roll back the tracked Arbitrum `finalized_height`, potentially re-opening acceptance windows for state/commitment proofs tied to already-superseded heights, undermining challenge-period and freshness assumptions relied on elsewhere in the bridge (cross-chain request/response verification, withdrawal authorization). This matches "Critical: false state acceptance" if downstream logic trusts `finalized_height` as a forward-moving watermark.

### Likelihood Explanation
Likelihood is **uncertain** rather than confirmed: I was unable to verify, within the available tool budget, whether `pallet_ismp`'s consensus-message handling path (`modules/pallets/ismp/src/lib.rs`) applies its own comparison against the previously stored consensus state's height before calling `IsmpHost::store_consensus_state`, which is the standard mitigation pattern used elsewhere in ismp-rs-derived designs. If such a check exists centrally, this specific client-level gap may be non-exploitable in practice. This needs to be confirmed by inspecting the consensus-message handler in `modules/pallets/ismp/src/lib.rs` (or `ismp/src/handlers/consensus.rs` if present) for any `finalized_height`/`latest_height` comparison prior to state commitment persistence.

### Recommendation
Add an explicit monotonicity check inside `verify_consensus` before overwriting `finalized_height`, e.g.:
```rust
if state.height.height <= consensus_state.finalized_height {
    return Err(ArbitrumError::StaleHeight.into());
}
```
for both the `ArbitrumOrbit` and `ArbitrumBold` branches, so the client itself enforces forward-only progress regardless of whether an outer layer also does so.

### Proof of Concept
Not independently reproducible here without running the full pallet test harness; suggested test: accept one Arbitrum update at height N (with L1 height H2), then submit a second, otherwise-valid `ArbitrumUpdate` referencing an earlier L1 height H1 (< H2, still present in `host.state_machine_commitment` storage) with a genuine proof of an assertion/node at height M < N. Assert that `finalized_height` in the resulting `ConsensusState` is rejected/unchanged rather than regressing to M — currently, the code does not perform this check, so it would regress.
