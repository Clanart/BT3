### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes quadratic Lagrange interpolation in `ThresholdKeys::new` (CPU DoS) - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a serialized `n` (u16) from untrusted bytes and reads `n` verification shares before calling `ThresholdKeys::new`. `ThresholdKeys::new` computes `group_key` by evaluating `interpolation_factor` for every participant `1..=t` over the set `1..=t`. With `Interpolation::Lagrange`, each `interpolation_factor` call is `O(t)` scalar multiplications plus one field inversion, making `group_key` derivation `O(t²)`. An input declaring `t = n = 65535` (~2 MB of point encodings) forces ~4.3·10⁹ field multiplications plus 65,535 inversions, stalling the deserializing thread for a resource cost wildly disproportionate to input size.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i` from the byte stream, then reads `n` group elements into `verification_shares`, and finally calls `ThresholdKeys::new` [1](#0-0) . Inside `ThresholdKeys::new`, the group key is derived by interpolating the verification shares of participants `1..=t` [2](#0-1) . `Interpolation::Lagrange`'s `interpolation_factor` iterates over the entire `included` slice per participant [3](#0-2) , and `included` here is the full `1..=t` set, so total work is `Θ(t²)` scalar operations plus `t` field inversions (`denom.invert().unwrap()` inside the loop-scoped computation). Because `n`/`t` are only bounded by `u16` and `t <= n` [4](#0-3) , a single serialized blob can demand hours-scale CPU relative to its size. No upper bound on `n` is enforced at deserialization time, unlike the `TRANSACTION_SIZE_LIMIT` checks applied elsewhere in the codebase.

### Impact Explanation
Any code path that feeds adversary-controlled bytes to `ThresholdKeys::read` (the accepted untrusted surface for this audit) lets an unprivileged party burn orders of magnitude more CPU than bandwidth: ~4 billion scalar multiplications and ~65k inversions for a ~2 MB input. Repeated submissions can keep a validator/processor thread saturated, delaying signing rounds and DKG completion — a medium-severity availability impact matching the ReDoS bug class (small input → superlinear compute).

### Likelihood Explanation
Exploitation requires reaching a `ThresholdKeys::read` call with attacker-influenced bytes. All field elements/points must still be canonically encoded (`read_F`/`read_G` enforce canonicity), so the attacker must actually transmit `n` encoded points — but this only makes the attack linear-in-bandwidth while the compute remains quadratic, preserving a ~2000× asymmetry factor at the maximum `n`.

### Recommendation
Enforce a sane upper bound on `n`/`t` in `ThresholdKeys::read`/`ThresholdParams::new` (real deployments use `n` in the hundreds at most), or precompute the `1..=t` Lagrange denominators/numerators productively (e.g., prefix products with a single inversion) to reduce `group_key` derivation to `O(t)`.

### Proof of Concept
Serialize a `ThresholdKeys` blob with `t = n = 0xffff`, `i = 1`, interpolation byte `1` (Lagrange), followed by any valid scalar and `65535` canonical encodings of the same generator point. Feeding it to `ThresholdKeys::<C>::read` reaches `ThresholdKeys::new`, which evaluates `interpolation_factor` 65,535 times, each looping over 65,535 participants — ~4.3·10⁹ field multiplications and 65,535 inversions — before returning.
