The core broken invariant in the report is: **a security gate that blocks a dangerous operation gets explicitly and unconditionally disabled by the calling code**, leaving attacker-controlled data (the cloned repository/token supply) able to drive the app into the exact state the gate was meant to prevent. GitHub Desktop has a direct parallel: it deliberately disables Git's own clone-time protection mechanism before cloning attacker-controlled remotes.

### Title
Git's clone protection is explicitly disabled during recursive clones, re-exposing malicious-repository RCE (CVE-2024-32004-class attack) - (File: app/src/lib/git/clone.ts)

### Summary
Git added `GIT_CLONE_PROTECTION_ACTIVE` as a runtime safety check to stop a known remote-code-execution class of attack (CVE-2024-32004) where a maliciously crafted repository — using symlinked `.git` directories/hooks paths surfaced through nested/recursive submodules — gets its hooks executed on the victim's machine during `git clone --recursive`. Desktop's `clone()` function explicitly sets this protection to `'false'` for every clone it performs.

### Finding Description
`clone()` in [1](#0-0)  builds the clone environment with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and always passes `--recursive`, meaning submodules (which are entirely attacker-controlled content coming from the untrusted remote) are initialized and checked out automatically as part of every clone Desktop performs. This mirrors the report's pattern exactly: a protective invariant (`liquidityGoalReached()` gating unsafe transfers / Git's clone protection gating unsafe hook execution) is neutralized by the calling code itself rather than by attacker exploitation of a computation — the difference here is Desktop unconditionally turns the safety check off for every clone rather than only under attacker-influenced conditions, which is arguably worse since it removes the mitigation universally instead of leaving a residual gap.

Desktop does add its own compensating controls — `isClonePathSensitive()` blocks path traversal into sensitive directories [2](#0-1)  and `sanitizeCloneName`/`resolveWithin` guard against traversal payloads in the repository name [3](#0-2) . None of these guards address the hook-execution vector that `GIT_CLONE_PROTECTION_ACTIVE` was designed to stop; they only constrain *where* the clone lands, not *what code runs* while cloning submodules recursively from an untrusted remote.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE=false` reinstates the vulnerable behavior that Git's upstream fix was meant to close, a malicious/compromised repository — reachable simply by a user cloning it, no local access or credentials required — could achieve arbitrary code execution on the victim's machine during the clone, since submodule initialization happens automatically via `--recursive`. That satisfies the "attacker controls a cloned/fetched repository ... result is code execution" criterion directly.

### Likelihood Explanation
Cloning an attacker-supplied URL is a completely ordinary, expected user action in Desktop (via the Clone dialog, `x-github-client://openRepo` deep links, or CLI `--cli-clone`), so the attacker precondition is trivial to satisfy — no elevated privileges, no social engineering beyond getting a victim to clone a URL, which is Desktop's core use case.

### Recommendation
Determine why `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` (likely to unblock cloning into paths Git's heuristic falsely flags) and replace this blanket bypass with a narrower fix — e.g., only disabling the check for verified-safe destination paths, or upgrading the bundled Git/dugite version and relying on its protection while fixing false positives through Desktop's own destination validation (`isClonePathSensitive`) instead of disabling Git's own hook-execution safety net.

### Proof of Concept
1. Attacker publishes a public repository containing a submodule configuration crafted to exploit the symlinked-`.git`/hooks class of issue that `GIT_CLONE_PROTECTION_ACTIVE` was introduced to block (per CVE-2024-32004).
2. Victim opens Desktop and clones the malicious repository URL (via UI, deep link, or CLI clone action handled in [4](#0-3) ).
3. `clone()` invokes `git ... clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` set in the environment [1](#0-0) , so Git's built-in protection does not intervene during the recursive submodule checkout.
4. If the underlying Git version is otherwise vulnerable when this protection is off, hook execution from the malicious submodule content occurs on the victim's machine during the clone.

Note: exploitability is contingent on the bundled `dugite`/Git version's behavior when this variable is unset; I could not verify from the indexed files which Git version is bundled or whether upstream has since hard-disabled the vulnerable code path independent of this variable — this would need to be confirmed in a live/build environment (Devin session) before treating this as fully confirmed rather than a strong analog.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
