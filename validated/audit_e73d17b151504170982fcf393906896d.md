### Title
Permissionless FIFO-eviction griefing of paid bandwidth subscriptions in `pallet-bandwidth` — ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`BandwidthManager.purchase()` on EVM (and the resulting `pallet-bandwidth::on_accept` credit path) lets *any* unprivileged caller top up bandwidth for *any* `(chain, app)` pair by simply paying the tier price. The pallet stores subscriptions per `(app_chain, app)` in a FIFO list capped at `MAX_SUBSCRIPTIONS = 1024`; once full, a new push evicts the oldest entry regardless of its remaining value. An attacker can therefore pay the cheapest tier 1024+ times against a victim app to flush out the victim's real, larger/longer-duration subscription before it is consumed — permanently destroying bytes the victim already paid for, mirroring the `Locke.sol` pattern where an unprivileged actor sends value into shared state to block/griеf legitimate use of a resource that only resets under limited conditions.

### Finding Description
`BandwidthManager.purchase()` is fully permissionless — it takes an arbitrary `app` (bytes) and `chain` argument and only requires the caller to pay `tierPrice[tier] * months` in the fee token: [1](#0-0) 

The dispatched `BandwidthPurchaseMsg` is credited on Hyperbridge keyed by `(app_chain, app)` from the message body — not by `request.source` — and any purchaser can specify any target app: [2](#0-1) 

Each `(chain, app)` bucket is a bounded FIFO `SubscriptionList` capped at 1024 entries; pushing past the cap evicts the oldest entry unconditionally, independent of its `remaining_bytes` or `expires_at`: [3](#0-2) 

The documentation confirms this eviction semantics explicitly: "pushing onto a full list evicts the oldest entry with `SubscriptionEvicted`", and that a subscription's value (`lost_bytes`) can simply be discarded on eviction: [4](#0-3) [5](#0-4) 

Because insertion order (`purchased_at`) determines eviction order and any unprivileged party can push new subscriptions into the same bucket, an attacker who buys 1024 cheap TierOne subscriptions against a target app will evict every entry present in the bucket at attack time, including a victim's large, still-mostly-unused, high-value subscription — with the app's actual gate balance immediately dropping regardless of how many bytes the victim originally paid for and had not yet consumed. This is analogous to `Locke.sol`'s `incentives[who]` being pushed to a non-zero, un-resettable-by-the-rightful-party state by an unprivileged token holder: here an unprivileged purchaser mutates shared, capacity-bounded state (`Allowance<T>`) belonging to another app, and the only "reset" path (consuming or waiting for expiry) is unavailable once the entries have already been evicted.

### Impact Explanation
This directly causes loss of paid-for value: bandwidth bytes purchased and not yet consumed by a legitimate app can be permanently destroyed by a third party at comparatively low cost (limited by the cheapest tier price × count needed to fill the 1024-slot cap), with no compensation or refund path back to the victim. This falls under "logic attacks" / "loss of funds" in the bounty gate: the victim's paid escrow of bandwidth (an on-chain economic asset) is deleted by an unprivileged actor through a normal, permissionless entrypoint, not through a compromised relayer/prover/admin.

### Likelihood Explanation
The attack requires no privileged role, no malicious relayer/prover, and no race condition beyond normal transaction submission — only capital to buy up to 1024 cheap-tier purchases against the specific `(app_chain, app)` pair being targeted. Cost scales with the cheapest configured tier price and the current occupancy of the target's FIFO list (fewer purchases needed if the list is already near capacity from normal legitimate top-ups). This is comparable in cost/effort to the original report's acknowledged griefing vector ("it does cost the user" / attacker), making it a realistic, moderately-priced grief rather than a free DoS.

### Recommendation
- Do not evict purely by FIFO insertion order; prioritize evicting already-expired or near-zero `remaining_bytes` entries first, and only fall back to oldest-non-expired eviction if the list is genuinely full of live, valuable subscriptions.
- Consider bounding the FIFO cap per payer or reserving capacity so a single purchase burst from one payer cannot fully displace a different payer's subscriptions in the same `(chain, app)` bucket (e.g., per-purchase-batch subscription merging instead of always appending a new row).
- Alternatively, when a repurchase of the same tier occurs, merge/stack into the existing subscription's `remaining_bytes` and extend `expires_at` rather than appending a brand-new FIFO row, sharply reducing the number of entries a griefer must create to overflow a bucket.
- Emit clearer monitoring/alerting on `SubscriptionEvicted` volume per `(chain, app)` so anomalous eviction bursts are detectable, and document this griefing trade-off to app operators as the C4 report's mitigation did.

### Proof of Concept
1. Attacker identifies a target `(app_chain, app)` pair with an existing, large, mostly-unconsumed subscription (e.g., victim just bought the $1000/8MB tier for 12 months).
2. Attacker calls `BandwidthManager.purchase(app, TierOne, 1, chain)` 1024 times (or enough times to exceed remaining FIFO capacity), each dispatching a `BandwidthPurchaseMsg` credited via `on_accept`: [6](#0-5) 
3. On Hyperbridge, each inbound purchase message calls the pallet credit path which pushes onto the same `Allowance<T>` FIFO bucket keyed by `(app_chain, app)`: [7](#0-6) 
4. Once the bucket reaches `MAX_SUBSCRIPTIONS = 1024`, further pushes evict the oldest entries — including the victim's large legitimate subscription — emitting `SubscriptionEvicted` with `lost_bytes` equal to whatever the victim had not yet consumed: [5](#0-4) 
5. The victim's app now has its purchased, unconsumed bandwidth gone, while the attacker only spent the cumulative TierOne price for however many pushes were needed — a permanent, low-cost destruction of another party's paid-for on-chain resource.

```text
    function purchase(bytes calldata app, uint256 tier, uint256 months, bytes calldata chain)
        external
        returns (bytes32 commitment)
    {
        if (app.length == 0 || chain.length == 0 || months == 0) revert InvalidPurchase();
        uint256 price18d = tierPrice[tier];
        if (price18d == 0) revert UnknownTier();

        uint256 total18d = price18d * months;
        address feeToken = IDispatcher(_host).feeToken();
        uint8 dec = IERC20Metadata(feeToken).decimals();
        uint256 scale = 10 ** (18 - dec);
        if (total18d % scale != 0) revert PriceNotRepresentable();
        uint256 amount = total18d / scale;

        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
```
