## Title
NFT royalty amount computed via division-before-multiplication in `compute_royalty_amount` causes royalty underpayment/truncation to zero - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()` in `chia/wallet/nft_wallet/nft_wallet.py` (used by `NFTWallet.make_nft1_offer()` to size real `CreateCoin` royalty payments in NFT offer spend bundles) performs integer division before the final multiplication/division, exactly the precision-loss pattern described in the referenced Ajna report.

### Finding Description
`compute_royalty_amount` computes: [1](#0-0) 
```
amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
```
The `abs(offered_amount) // royalty_split` integer division happens first, discarding remainder, before multiplying by `percentage` and dividing by `MAX_ROYALTY_BASIS_POINTS` (10000). This truncates precision earlier than necessary; the mathematically correct order (multiply first, divide last) would preserve more precision: `abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)`.

This helper is called from `NFTWallet.make_nft1_offer()` when constructing the actual royalty `CreateCoin` payments embedded in an NFT offer's spend bundle: [2](#0-1) 

A separate, similarly-flawed helper `NFTWallet.royalty_calculation()` (used only for the `nft_calculate_royalties` RPC / CLI display estimate, not on-chain enforcement) has the identical bug pattern: [3](#0-2) 

### Impact Explanation
For small `offered_amount` relative to `royalty_split` (multiple royalty-bearing NFTs split across one payment asset — `request_side_royalty_split`), `abs(offered_amount) // royalty_split` can floor to 0 before the percentage is ever applied, causing the computed royalty to truncate to 0 mojos even when a nonzero royalty is intended by the NFT's `royalty_percentage`. More generally, for any non-trivial split/percentage/amount combination, the party constructing the offer systematically pays less royalty than the mathematically correct amount, at the expense of the NFT creator/royalty recipient.

However, I was unable to locate and confirm the CLVM-side enforcement code (e.g., an ownership/transfer-program puzzle that independently validates the trade price / royalty amount against `royalty_percentage`) within the indexed content to determine whether the chain enforces an independently-computed "correct" royalty amount that would reject an offer using this truncated value, or whether it merely trusts the value supplied by the offer-maker's wallet. If the CLVM puzzle only checks that *a* royalty payment condition exists (structurally) rather than independently recomputing and requiring the mathematically precise amount, then this rounding-down systematically shifts value away from royalty recipients with no on-chain rejection — a legitimate value-loss bug reachable by any wallet user constructing/countersigning NFT offers with royalty splits. If instead the puzzle enforces the same (buggy) formula on both sides symmetrically, the practical impact is limited to consistent underpayment relative to the NFT's stated royalty percentage rather than a cross-party exploit.

### Likelihood Explanation
This code path is exercised by any wallet user or offer counterparty creating/accepting NFT offers that include royalty-enabled NFTs split across a bundle (`request_side_royalty_split > 1`) or where `abs(offered_amount)` is not a clean multiple of `royalty_split * MAX_ROYALTY_BASIS_POINTS`. This is a common, unprivileged, user-triggerable path (standard NFT offer creation), not requiring any special permissions — but I could not confirm from the indexed code whether it is exploitable for asymmetric value transfer versus being a consistent (if incorrect) global rounding convention.

### Recommendation
Reorder the arithmetic in `compute_royalty_amount` (and `royalty_calculation`) to multiply before dividing, minimizing precision loss:
```python
amount = abs(offered_amount) * percentage // (royalty_split * MAX_ROYALTY_BASIS_POINTS)
```
Confirm that any CLVM-side royalty/trade-price validation is updated to match, and add regression tests for small-amount/high-split combinations that currently truncate to 0 under the old formula (extending the existing tests in `chia/_tests/wallet/nft_wallet/test_nft_royalty.py`). [4](#0-3) 

### Proof of Concept
Using `compute_royalty_amount(offered_amount=-1999, royalty_split=2, percentage=9999)`:
- Current code: `1999 // 2 = 999`; `999 * 9999 // 10000 = 998` (loss vs. precise value).
- Precise order: `1999 * 9999 // (2 * 10000) = 999` (or `999.4` floored appropriately) — demonstrating the division-before-multiplication order yields a different (lower) result than multiply-first-divide-last, consistent with the reported bug class. [1](#0-0) 

**Note:** I could not verify within the indexed codebase whether an independent CLVM-side check recomputes/enforces the "correct" royalty amount (which would determine whether this is a pure economic-loss bug or also a spend-validity/DoS issue). A Devin session with full repository/browser access would be needed to trace the NFT ownership/transfer-program puzzle's royalty verification logic to confirm exploitability and severity conclusively.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
