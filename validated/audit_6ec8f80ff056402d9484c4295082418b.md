## Analysis

The core "broken invariant" in the Mellow report is: **a value used to make a critical, execution-triggering decision (`tvl()`) is computed from stale/partial state, and the code applies fresh execution against that stale value without re-validating it**, letting an attacker exploit the gap between "what the user/contract believes" and "what actually gets executed."

GitHub Desktop has no economic/vault concept, but it has a structurally identical pattern in its **partial-commit (line-by-line staging) feature**: the user's line selection is stored as *positional indices into a diff snapshot*, but the actual patch applied to the index at commit time is generated from a **freshly re-fetched diff**, with no verification that the two diffs are the same. This is the same "decision made against stale state, then blindly executed against current state" bug class.

### Title
Stale line-position `DiffSelection` is silently re-applied to a freshly fetched diff during partial commits, allowing corrupted commit contents - (File: `app/src/lib/git/apply.ts`)

### Summary
When a user stages only *some lines* of a modified file, GitHub Desktop stores the selection as a set of **absolute line indices** into the diff that was rendered in the UI (`DiffSelection`), not as content hashes or stable line identities. At commit time, `applyPatchToIndex()` does not reuse that reviewed diff — it re-runs `getWorkingDirectoryDiff()` against the working tree at that instant and reinterprets the old index-based selection against the new diff via `formatPatch()`. If the file on disk changes between the time the diff was shown/selected and the moment the user clicks "Commit," the committed content silently diverges from what the user actually reviewed and approved.

### Finding Description
The partial-commit pipeline is:

1. UI renders a diff and the user selects specific lines; selection is stored as `DiffSelection` keyed by `absoluteIndex` (hunk-relative line offsets), e.g. in `formatPatch()`: [1](#0-0) 

2. At commit time, `_commitIncludedChanges()` takes whatever `WorkingDirectoryFileChange.selection` currently sits in `repositoryStateCache` and passes it straight to `createCommit` → `stageFiles` → `applyPatchToIndex`: [2](#0-1) 

3. Critically, `applyPatchToIndex` does **not** use the diff that was shown to the user; it fetches a brand-new diff of the file from the working tree at that exact moment and formats a patch from it using the old selection object: [3](#0-2) 

4. The application itself acknowledges this exact class of bug is only partially handled — and only in the UI display path, not the commit path. The comment in `app-store.ts` admits the diff "might have changed dramatically since last we loaded it," and the mitigation is limited to dropping indices that are no longer "includeable" — it does not validate that a *retained* index still points to the same content: [4](#0-3) 

5. This UI-side pruning is asynchronous and, more importantly, is never invoked as part of the commit path at all — `applyPatchToIndex` performs its own independent `getWorkingDirectoryDiff` call, so even a perfectly pruned in-memory selection can be stale relative to the diff actually used to build the patch. There is no synchronization or invalidation across `updateChangedFiles`/`updateChangesWorkingDirectoryDiff` and `applyPatchToIndex`: [5](#0-4) [6](#0-5) 

The net effect: **the diff the user visually reviewed and selected lines from is not the diff that generates the actual staged/committed patch.** If content shifts between those two points (extra/removed lines shifting hunk offsets, or content substitution at the same offset), the resulting commit can include lines the user explicitly deselected, or omit lines the user explicitly selected — without any error, warning, or diff-mismatch detection.

### Impact Explanation
This is a **silent corruption of what the user commits** — the exact class of impact called out as valid. Because Desktop routinely supports and even bundles common dev-workflow tooling that mutates tracked files asynchronously (file watchers, `post-checkout`/`post-merge` hooks that Desktop explicitly proxies and executes, LFS smudge/clean filters, autoformatters), a repository shipping such tooling (e.g. via `package.json` scripts, a `.husky` hook, or `.gitattributes` filters) can cause tracked file content to change in the window between when a partial-commit selection is made and when the commit executes. A victim using such a project could unknowingly commit and push content they never reviewed or approved — including attacker-planted lines that were never shown in the diff view, or exclude security-relevant lines the user believed they were committing.

### Likelihood Explanation
The race window is real and not merely theoretical: Desktop already proxies and executes numerous git hooks (`post-checkout`, `post-merge`, etc.) and supports LFS smudge/clean filters and shell-based hook environments, all of which are legitimately shipped inside repositories and run automatically as part of normal user workflows (`app/src/lib/hooks/get-repo-hooks.ts`, `app/src/lib/hooks/with-hooks-env.ts`). No user action beyond normal use of the affected repository (checkout, pull, partial-stage, commit) is required, and the existing "guard" (`withSelectableLines`) is acknowledged in-code as incomplete and is not even wired into the actual commit path.

### Recommendation
- Before generating the commit patch in `applyPatchToIndex`, compare the freshly fetched diff against the diff the selection was created from (e.g., by diff/hunk content hash or `oldStartLine`/`newStartLine` + line-text fingerprinting), and refuse to commit / force a re-review if they diverge.
- Alternatively, capture and reuse the exact `ITextDiff` object the user selected against (already fetched in the UI/store) when calling `formatPatch`, instead of re-fetching a new diff at commit time in `apply.ts`.
- Surface an explicit error/warning to the user ("the file has changed since you reviewed this diff — please re-review before committing") rather than silently applying stale selections to new content.

### Proof of Concept
1. Clone a repository containing a `package.json` `"scripts"` entry (or `.husky` hook) intended to run as a background formatter/watcher during normal development — a completely legitimate-looking dev dependency.
2. Open the repo in GitHub Desktop, modify `src/auth.ts`, and select only a subset of lines to commit (e.g., a bug fix, deliberately excluding an unrelated debug line).
3. While the diff is open/selected but before clicking "Commit," the malicious watcher script (triggered by the earlier `npm install`/`post-checkout`) rewrites `src/auth.ts`, shifting line offsets and inserting an extra line (e.g. re-enabling a debug backdoor) at a position that lands inside the still-"selectable" range of the new diff.
4. The user clicks "Commit." `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches the new diff and `formatPatch` (`app/src/lib/patch-formatter.ts:157`) reinterprets the old absolute-index selection against it.
5. The resulting commit silently includes the attacker-inserted line (never shown to or approved by the user in the diff view) and/or drops content the user intended to include, with no warning from Desktop.
