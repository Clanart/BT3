### Title
Attacker can manipulate `getRewardablePercentWAD` by bundling `VLMGP.lock` before `getReward`/`cancelUnlock`, avoiding intended yield forfeiture - (File: rewards/vlMGPBaseRewarder.sol)

### Summary
`vlMGPBaseRewarder._calExpireForfeit` computes the forfeited portion of a user's earned rewards by reading `vlMGP.getRewardablePercentWAD(_account)` at claim time, not the ratio that prevailed while the reward was accruing. Because `getRewardablePercentWAD` is a pure function of the *current* lock/cooldown state, and `lock()`/`cancelUnlock()` are freely callable by the account holder itself, an unprivileged attacker can atomically bundle a `lock()` (or `cancelUnlock()`) call immediately before `getReward()` in the same transaction to inflate their rewardable ratio and reduce/eliminate forfeiture that should have applied to rewards earned while their vlMGP was in cooldown or already time-expired.

### Finding Description
`_calExpireForfeit` in `rewards/vlMGPBaseRewarder.sol` uses the live percentage from `VLMGP.getRewardablePercentWAD`: [1](#0-0) 

`getRewardablePercentWAD` in `VLMGP.sol` computes:
```
percent = fullyInLock * 1e18 / userTotalVlmgp
+ for each cooldown slot still cooling down: amountInCoolDown * 1e18 / userTotalVlmgp   (full weight, no decay)
+ for each expired (fully unlocked but not withdrawn) slot: amountInCoolDown * 1e18 * (endTime-startTime) / userTotalVlmgp / (now-startTime)   (decays over time)
``` [2](#0-1) 

Mathematically, letting `a = fullyInLock + Σ(decayed cooldown contributions)` and `b = userTotalVlmgp`, the ratio is `a/b` with `a < b`. Adding freshly locked MGP `X` via `lock()` increases both numerator and denominator by `X` (`(a+X)/(b+X)`), which is strictly closer to 1 than `a/b` whenever `a<b`. Thus locking additional MGP immediately before calling `getReward` mechanically raises `rewardablePercentWAD`, lowering the forfeited amount computed in `_calExpireForfeit`, `_sendReward`, and `queueMGP`: [3](#0-2) [4](#0-3) 

Separately, `cancelUnlock()` lets a user instantly convert an *already-expired* cooldown slot (whose weight has decayed under the `f = (endTime-startTime)/(now-startTime)` formula) back into fully-locked status with zero penalty, resetting its contribution to full weight: [5](#0-4) 

Neither `lock()` nor `cancelUnlock()` has any cooldown, fee, or time-lock restricting when they can be called relative to `getReward()`, and `getReward` itself has no check that the lock/cooldown ratio matches the ratio that prevailed while the reward accrued (accounting is done via `rewardPerTokenStored`/`userRewardPerTokenPaid`, which track amount accrued, not the historical rewardable ratio). Because `getReward` is only gated by `onlyMasterMagpie` and `updateReward`, an attacker's own EOA/contract can trivially sequence `lock()` (or `cancelUnlock()`) and the `getReward` call (via `MasterMagpie.claim`) in one atomic transaction — no mempool race against a third party is even required since both calls originate from the attacker. [6](#0-5) 

### Impact Explanation
Forfeited rewards are redistributed to all remaining stakers via `_queueNewRewardsWithoutTransfer`, which folds the forfeit back into `rewardPerTokenStored` for the pool: [7](#0-6) 

By gaming the ratio just before claiming, an attacker keeps yield that the protocol's forfeiture mechanism intends to claw back and redistribute to loyal (still-locked) stakers, resulting in theft of yield from the honest staker pool — matching the "theft or permanent freezing of unclaimed yield" impact class. This applies per-claim and can be repeated indefinitely at low cost (only requires temporarily locking MGP the attacker already owns, or calling the fee-free `cancelUnlock`).

### Likelihood Explanation
- No privileged role required: only vlMGP/MGP holding and normal `lock`/`cancelUnlock`/`getReward` calls.
- Fully deterministic and atomic (can be done via a single helper contract calling `VLMGP.lock` then `MasterMagpie.claim`/`getReward` in one transaction) — no reliance on winning a mempool race against another party.
- Repeatable on every claim cycle; capital requirement for the `lock()` variant is temporary (MGP can be re-locked and is not lost), and the `cancelUnlock()` variant requires no extra capital at all.
- High feasibility given the straightforward mathematical proof that `(a+X)/(b+X) > a/b` for `a<b`.

### Recommendation
Snapshot/checkpoint the rewardable ratio at the time rewards accrue (e.g., update a per-user or per-reward-period weighted ratio whenever `rewardPerTokenStored` advances, similar to a checkpointed `userRewardPerTokenPaid`) instead of reading the live `getRewardablePercentWAD` at claim time. Alternatively, apply a timelock/cooldown on `lock()`/`cancelUnlock()` before it affects forfeiture eligibility, or compute forfeiture using a time-weighted average of the lock ratio over the accrual period rather than the instantaneous value at claim.

### Proof of Concept
Foundry test plan:
1. Deploy `VLMGP`, `MasterMagpie`, and `vlMGPBaseRewarder`; fund the rewarder with reward tokens via `queueNewRewards`.
2. Attacker locks MGP, then calls `startUnlock` to move a portion into cooldown; warp time past `coolDownInSecs` so the slot is "expired but not withdrawn" (decayed weight per `getRewardablePercentWAD`).
3. Let reward accrue (via `queueNewRewards` and time passage) while the attacker's cooldown slot is in the decayed state.
4. Baseline: call `vlMGPBaseRewarder.calExpireForfeit(attacker, rewardToken)` and record `forfeitAmount_before`.
5. Deploy a helper contract that in a single transaction: (a) calls `VLMGP.lock(X)` with freshly acquired MGP (or calls `VLMGP.cancelUnlock(slotIndex)`), then (b) calls `MasterMagpie.claim`/`vlMGPBaseRewarder.getReward(attacker, attacker)`.
6. Assert that the actual forfeited amount transferred to `_queueNewRewardsWithoutTransfer` during step 5 is strictly less than `forfeitAmount_before` (or zero), and that the attacker receives more reward tokens than they would have without bundling the `lock`/`cancelUnlock` call — demonstrating forfeiture is computed on post-manipulation state rather than the state during which the reward accrued.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalVlmgp = fullyInLock + inCoolDown;
        if (userTotalVlmgp == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalVlmgp;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalVlmgp / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalVlmgp;
                }

            }
        }

        return percent;
    }
