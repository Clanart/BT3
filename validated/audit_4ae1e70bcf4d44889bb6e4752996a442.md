## Title
`git clone` explicitly disables Git's `GIT_CLONE_PROTECTION_ACTIVE` embedded-repository safety check during `--recursive` clones of attacker-controlled URLs - (File: `app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` function always runs `git clone --recursive` against a user-supplied (and, via deep links / `openrepo`, attacker-influenced) URL, and explicitly forces `GIT_CLONE_PROTECTION_ACTIVE=false` in the child process environment: [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced (Git ≥2.45.1, as part of the fix for the embedded-repository / recursive-clone advisories, e.g. CVE-2024-32004/GHSA family) to detect and reject clones that abuse nested/embedded `.git` directories and symlink tricks to smuggle hooks or config into the outer working tree during a recursive clone. Setting it to `'false'` deliberately turns this upstream Git protection off for every clone Desktop performs, including recursive submodule clones triggered by opening `github-mac://openRepo/...` / `x-github-desktop://openRepo/...` deep links or by pasting/selecting a URL in the Clone dialog.

### Finding Description
The GMX report's broken invariant was "an optional/derived code path silently drops a safety check that the primary path enforces." The equivalent broken invariant here is: Desktop's own `clone()` wrapper adds defense-in-depth for path traversal (`isClonePathSensitive`) but simultaneously **removes** the safety net Git upstream ships for exactly this class of attack (malicious repository content abusing recursive/embedded clones), by forcing `GIT_CLONE_PROTECTION_ACTIVE=false` unconditionally, with no compensating check elsewhere in the clone pipeline for embedded repositories, malicious `.gitmodules` entries, or symlinked `.git` directories.

The URL that is cloned is attacker-influenced in several real Desktop flows:
- `parseAppURL`'s `openrepo` action extracts an arbitrary `url` from a deep link and forwards it, largely unvalidated, into `IOpenRepositoryFromURLAction`: [2](#0-1) 
- `Dispatcher.openRepositoryFromUrl` / `openOrCloneRepository` route that URL straight into the Clone dialog / `dispatcher.clone(url, path, ...)`: [3](#0-2) [4](#0-3) 
- The eventual clone call always appends `--recursive` and the disabled-protection env var, regardless of how the URL was obtained: [5](#0-4) 

Because `--recursive` is always used and the upstream Git-side guard against malicious embedded/nested repositories is explicitly disabled, a hostile remote (attacker-controlled repo, or a repo reached via a crafted `openRepo` deep link) can potentially structure its tree/submodule/symlink content to have Git write files outside the intended working directory or into locations that behave like hooks — exactly the class of bug `GIT_CLONE_PROTECTION_ACTIVE` exists to stop. The `isClonePathSensitive()` guard in the same function only checks the *destination* path against a fixed deny-list (home dir, `.ssh`, `.gnupg`, etc.) and does nothing to constrain what the *clone content itself* can do once protection is turned off.

### Impact Explanation
If the disabled protection is in fact required to stop the embedded-repository/symlink attack class it was built for, cloning a malicious repository (whether chosen directly by the user or reached via an `x-github-desktop://openRepo/<attacker-url>` link) could result in files being written outside the intended clone directory or malicious hook-like content being materialized on disk — i.e., file write outside the repo and a path toward local code execution on subsequent Git operations. This matches the "corruption of what the user commits/clones, code execution, or file write outside the repo" impact bar for this scan.

### Likelihood Explanation
Likelihood is high for exposure (every clone goes through this code path, and clone URLs are reachable via deep links, which are explicitly an unprivileged, attacker-triggerable surface), but I could not confirm from the available index whether Desktop compensates for the disabled Git-side check with equivalent logic elsewhere (e.g., in `dugite`, in post-clone integrity checks, or in a newer Git default that makes the flag redundant). No such compensating check was found in `app/src/lib/git/clone.ts`, `submodule.ts`, or the surrounding clone/hooks code reviewed. This uncertainty should be resolved before treating this as confirmed-exploitable; it is reported as a strong analog based on the code evidence that the protection is explicitly and unconditionally disabled with no visible replacement guard.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE=false` unconditionally. If it must be disabled for a specific legacy compatibility reason, scope it narrowly (e.g., only for known-trusted/local clone sources) and add an equivalent application-level check — analogous to checking `minLongTokenAmount`/`minShortTokenAmount` after a swap in the GMX fix — that validates the cloned tree for embedded `.git` directories, unexpected symlinks pointing at hook locations, or path traversal in submodule paths before/after the recursive clone completes, regardless of whether Git's own protection ran.

### Proof of Concept
Not independently reproducible from the indexed code alone (no compensating/alternative safety check was found to disprove reliance on `GIT_CLONE_PROTECTION_ACTIVE`, and the exact Git version behavior and dugite version pinned by Desktop were not available in the index). Conceptually:
1. Host a malicious Git repository containing a crafted submodule/embedded-repository structure of the kind `GIT_CLONE_PROTECTION_ACTIVE` is designed to reject (e.g., a `.gitmodules`/nested `.git` combination that would normally trigger Git's embedded-repository protection).
2. Get the victim to open it via `x-github-desktop://openRepo/<url>` or paste the URL into the Clone dialog. [2](#0-1) [4](#0-3) 
3. Desktop calls `clone()` with `--recursive` and `GIT_CLONE_PROTECTION_ACTIVE=false`, so Git's own safety check that would otherwise reject/flag the malicious structure never runs. [6](#0-5) 

A background Devin session with a live checkout and access to run `git clone --recursive` against a crafted malicious repo with and without `GIT_CLONE_PROTECTION_ACTIVE` set would be needed to confirm actual exploitability and produce a concrete file-write/RCE PoC.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
