### Title
Identity verification shares are accepted, producing a forgeable identity group key - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` accepts canonical identity points as verification shares, and `ThresholdKeys::new` validates only their count and participant indexes before deriving the group key from them. [1](#0-0)  Because `Ciphersuite::read_G` checks only point validity and canonical encoding, not `is_identity`, an encoded identity share passes deserialization. [2](#0-1)  The resulting identity group key makes Schnorr verification forgeable because the public-key term contributes zero to the verification equation. [3](#0-2) 

### Finding Description
The vulnerable path is attacker-controlled bytes passed to `ThresholdKeys::<C>::read`. [4](#0-3)  That function reads each verification share with `<C as Ciphersuite>::read_G`, which accepts the identity point as a valid canonical group element. [5](#0-4)  `ThresholdKeys::new` rejects missing shares and out-of-range participant indexes, but never rejects identity verification shares or an identity-derived `group_key`. [6](#0-5) 

This differs from FROST network inputs, where `Curve::read_G` explicitly rejects identity points. [7](#0-6)  The DKG deserialization path uses the weaker `Ciphersuite::read_G` instead. [5](#0-4) 

### Impact Explanation
If the first `t` verification shares are identity, the group key calculation sums identity multiples and produces the identity. [8](#0-7)  `SchnorrSignature::verify` evaluates `R + cA - sG == 0`; with `A` set to identity, any attacker-selected `s` and `R = sG` satisfies the equation regardless of the challenge. [9](#0-8)  This permits forged signatures under a deserialized identity threshold key, including through the FROST Schnorr adapter, which passes `group_key` directly into signature verification. [10](#0-9) 

### Likelihood Explanation
An unprivileged party only needs to cause crafted serialized threshold-key bytes to reach `ThresholdKeys::read`, an input path explicitly exposed by the API. [4](#0-3)  The simplest construction uses `t = n = i = 1`, Lagrange interpolation, any canonical scalar as `secret_share`, and the canonical identity encoding as the sole verification share. [11](#0-10)  No malformed encoding, validator compromise, collusion, or private-key knowledge is required. [2](#0-1) 

### Recommendation
Reject identity verification shares in `ThresholdKeys::new` and reject an identity computed `group_key` before returning `ThresholdKeys`. [1](#0-0)  `ThresholdKeys::read` should use identity-rejecting point parsing where available, or explicitly test each deserialized share with `is_identity`. [5](#0-4)  Schnorr verification should also reject an identity `public_key` and identity `R` at API boundaries accepting those values from untrusted encodings. [12](#0-11) 

### Proof of Concept
For any prime-order `Ciphersuite`, construct serialized `ThresholdKeys` bytes with:

- `t = 1`, `n = 1`, `i = 1`
- interpolation tag `1` (`Interpolation::Lagrange`)
- any canonical scalar for `secret_share`
- `C::G::identity().to_bytes()` as verification share `1`

`ThresholdKeys::<C>::read` accepts these bytes because identity passes `C::read_G`, while `ThresholdKeys::new` performs no identity check. [13](#0-12)  The generated `group_key` is identity because it is the sum over the identity verification share. [8](#0-7) 

For an arbitrary challenge `c`, choose any nonzero scalar `s` and set `R = C::generator() * s`. Then:

```text
R + c * group_key - s * G
= sG + c * identity - sG
= identity
```

Therefore `SchnorrSignature { R, s }.verify(keys.group_key(), c)` returns true, forging a Schnorr signature without a private key. [9](#0-8)
