### Title
Unvalidated `openExternal` on attacker-controlled CI check-run URL enables arbitrary local file/protocol execution - ([File: app/src/ui/check-runs/ci-check-run-popover.tsx])

### Summary
`CICheckRunPopover.onViewCheckDetails` and `onViewJobStep` take the `htmlUrl` field from a `IRefCheck`/check-run object — sourced from the GitHub Checks/Statuses API for a pull request — and pass it unmodified to `dispatcher.openInBrowser(url)`, which calls `shell.openExternal(url)` in the main process. Unlike the markdown-rendering path, which enforces `/^https?:/` before allowing a link click to reach `openExternal` [1](#0-0) , this CI-check code path performs no scheme, host, or format validation at all before calling `openExternal`.

### Finding Description
`onViewCheckDetails` reads `checkRun.htmlUrl` and forwards it directly to `openInBrowser`: [2](#0-1) 

`onViewJobStep` similarly derives a URL via `getCheckRunStepURL(checkRun, step, repository, prNumber)` and opens it without validation: [3](#0-2) 

`dispatcher.openInBrowser` maps straight to `_openInBrowser`, which is just `shell.openExternal(url)`: [4](#0-3) 

And in the main process, the `open-external` IPC handler only *logs* when the URL starts with `http(s)://` — it never rejects or restricts other schemes before calling Electron's `shell.openExternal`: [5](#0-4) 

This mirrors the “too generic calls” pattern from the report: a value that is treated as trusted/structured (a check-run “details URL”) but is actually attacker-supplied API data, is handed to a maximally powerful, unrestricted primitive (`shell.openExternal`, which can invoke arbitrary registered URL-scheme handlers or open local `file://` paths) with no allow-list of schemes. `IRefCheck.htmlUrl` and workflow job-step URLs are populated from the GitHub Checks API response (`ci-checks.ts`), which any check-run creator (e.g., a malicious or compromised CI integration/GitHub App with `checks:write` on a repo, or any workflow run associated with a fork PR the user is viewing) fully controls. Nothing in `getCheckRunStepURL` or the check-run ingestion code enforces `https:`-only, whereas the SandboxedMarkdown component demonstrates the project is aware this validation is necessary for user-facing URLs and applies it in that one path only.

### Impact Explanation
An attacker who controls a check run’s `details_url` (or a job/step URL) on a PR that a GitHub Desktop user views can supply a non-`http(s)` URI — e.g. a `file://` path, a `javascript:`-like custom scheme understood by an installed helper application, or a registered OS URL-protocol handler (as used elsewhere in the app for `x-github-client://`) — and have it opened via `shell.openExternal` when the user clicks “View details” in the CI checks popover. Depending on installed applications/protocol handlers, this can result in local file execution, triggering privileged application actions, or chaining into another installed program’s own vulnerable URL handling — all without the user typing anything or leaving the normal “view check status” UI flow.

### Likelihood Explanation
Likelihood is moderate-to-high for the specific unprivileged threat model in scope: any party able to post/report check-run status against a PR (common for third-party CI apps, and often available to anyone who can push to a fork used in a PR) fully controls `htmlUrl`. The user only needs to open the CI Checks popover for that PR and click “view details” — a completely natural, expected interaction, not a special unnatural sequence.

### Recommendation
Before calling `openInBrowser`/`shell.openExternal` with `checkRun.htmlUrl` or job/step URLs, validate that the URL parses successfully and its protocol is `https:` (mirroring the check already done in `SandboxedMarkdown.setupLinkInterceptor`). Apply the same validation centrally, ideally inside `_openInBrowser` (`app-store.ts`) or the `open-external` IPC handler in `main.ts`, so all callers (CI checks, PR notifications, etc.) are protected rather than relying on each call site to remember to validate.

### Proof of Concept
1. As the owner of a check-run reporting integration (e.g., a GitHub App or CI system) with write access to check runs on a repository/PR, set the check run’s `details_url` to a non-http(s) URI, e.g. `file:///Users/victim/Library/Application%20Support/GitHubDesktop/some-sensitive-file` or a registered custom protocol like `outlook://` or another vulnerable app's URI scheme.
2. Wait for a GitHub Desktop user to open that pull request and view the CI Checks popover for the associated commit.
3. The user clicks “View details” on the check run (`onViewCheckDetails`) or a job step (`onViewJobStep`).
4. `dispatcher.openInBrowser(url)` → `shell.openExternal(url)` is invoked with the attacker-controlled URI unchanged, with no scheme allow-list enforced anywhere on this path, unlike the equivalent markdown-link flow.
