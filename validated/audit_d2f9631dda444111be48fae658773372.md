### Title
Missing zero-address validation in `lockFor` allows permanent freezing of locked MGP/mWOM tokens - (File: `VLMGP.sol`, `wombat/mWomSV.sol`)

### Summary
`VLMGP.lockFor` and `mWomSV.lockFor` let any wallet lock tokens on behalf of an arbitrary `_for` address, but neither function (nor the internal `_lock` helper, nor `MasterMagpie.depositVlMGPFor`/`depositMWomSVFor` that they call into) validates that `_for != address(0)`. This mirrors the reported bug class (missing `_owner`/beneficiary address validation causing a permanent, unrecoverable state), except here the unvalidated address is reachable directly by any ordinary wallet.

### Finding Description
`lockFor` transfers tokens from `msg.sender` and credits the lock position to the caller-supplied `_for` address with no validation: [1](#0-0) 

The internal `_lock` function that both `lock()` and `lockFor()` funnel through also performs no check on `_for`, and forwards it straight into `MasterMagpie.depositVlMGPFor`: [2](#0-1) 

The exact same unguarded pattern exists in `mWomSV.sol`: [3](#0-2) [4](#0-3) 

Since `UserInfo` (amount, rewardDebt, unlock slots) is always tracked by `MasterMagpie` keyed on the `_for`/`msg.sender` address, and every unlock/withdraw path in `VLMGP`/`mWomSV` (`startUnlock`, `_unlock`, `_checkIdexInBoundary`, etc.) operates strictly on `msg.sender`, there is no code path that lets anyone ever act as `address(0)` to retrieve locked tokens credited to it. If `_for` resolves to `address(0)` (or any address nobody controls/expects), the locked MGP/mWOM balance becomes permanently unrecoverable by any account.

`SmartWomConvert` also forwards a similarly-unvalidated `_for` into `mWomSV.lockFor` and `MasterMagpie.depositFor`: [5](#0-4) 

### Impact Explanation
Locking tokens for `address(0)` (whether by direct mistaken call, a front-end bug, or a malicious contract integrating with these lock functions and mis-handling a recipient parameter) permanently removes the underlying MGP/mWOM principal from any possibility of withdrawal, since no unlock function can operate on `address(0)`'s position. This is a permanent freezing of user funds, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
The affected functions (`lockFor`) are `external`, unprivileged, and directly callable by any wallet without restriction beyond `whenNotPaused`/`nonReentrant`. Any integrating contract, relayer, or user script that passes an unvalidated or defaulted address (e.g., an uninitialized `address` variable, which defaults to `address(0)` in Solidity) as `_for` triggers the freeze. Given `_for` is a raw external parameter with zero validation anywhere in the call chain, likelihood of accidental triggering is non-trivial, matching the "high difficulty to catch, easy to trigger" characterization of the original report.

### Recommendation
Add an explicit zero-address check in `VLMGP.lockFor`, `mWomSV.lockFor`, `SmartWomConvert`'s `_for`-forwarding paths, and defensively in `MasterMagpie.depositVlMGPFor`/`depositMWomSVFor`/`depositFor`, e.g. `require(_for != address(0), "zero address")`, before any transfer or accounting update occurs.

### Proof of Concept
1. Attacker (or a buggy integrator) calls `VLMGP.lockFor(amount, address(0))`.
2. `_lock` transfers `amount` MGP from the caller into the `VLMGP` contract and calls `MasterMagpie.depositVlMGPFor(amount, address(0))`.
3. `MasterMagpie` credits `userInfo[address(vlmgp)][address(0)].amount += amount` with no zero-address check present in the reviewed code.
4. No function in `VLMGP` (or `MasterMagpie`) allows unlocking/withdrawing a position keyed on `address(0)` — `startUnlock`/`_unlock` always operate on `msg.sender`, and `address(0)` cannot be `msg.sender` in a transaction — so the locked MGP is permanently unrecoverable.

Note: I was unable to fully verify the internal body of `MasterMagpie._deposit`/`_withdraw` (only partial ranges were retrieved) to confirm with certainty that there is no zero-address guard anywhere in that internal function; based on all directly reachable call sites and the absence of any such check in `VLMGP.sol` and `mWomSV.sol`, the freeze scenario holds, but a full read of `MasterMagpie._deposit` would provide additional certainty.
