### Title
Tokenfactory denom admin can forge an arbitrary `decimals()` value on the native-token ERC20 pointer, decoupled from the actual (unscaled) transfer amounts, enabling mispricing/fund-loss for any protocol composing with the pointer - (File: `precompiles/pointer/pointer.go`, `contracts/src/NativeSeiTokensERC20.sol`)

### Summary
The `AddNative` pointer-precompile flow derives the immutable `decimals()` of a generated ERC20 pointer contract from the bank denom's self-reported `DenomMetadata`, which any tokenfactory denom admin freely controls via `MsgSetDenomMetadata`. The generated pointer contract, however, never applies any decimal scaling to the actual amounts it moves — `balanceOf`, `totalSupply`, and `transfer` all pass the raw, unscaled `sdk.Coin` integer straight through the Bank precompile. This is the same class of bug as the referenced Axelar finding: an ERC20-interface token whose declared `decimals()` does not correspond to the real granularity of the value it moves, letting a token creator mint a token that lies about its own decimal scale to any composing protocol (AMMs, lending markets, other pointers/bridges) that trusts `decimals()` for pricing.

### Finding Description
`AddNative` reads the bank module's `DenomMetadata` and picks the largest `DenomUnit.Exponent` as `decimals`, with no validation that it corresponds to any real scaling convention of the underlying integer amounts: [1](#0-0) 

This `DenomMetadata` is fully attacker-controlled: any tokenfactory denom admin can call `MsgSetDenomMetadata` at any time (including immediately before pointer creation), with only a generic `Metadata.Validate()` format check and an admin-authorization check — there is no requirement that the declared exponent bears any relationship to how the denom's raw integer amount is actually intended to be interpreted: [2](#0-1) 

The resulting `decimals` value is baked immutably into the constructor of the deployed `NativeSeiTokensERC20` pointer contract as `ddecimals`, and is returned unconditionally by `decimals()`: [3](#0-2) 

Critically, `balanceOf`, `totalSupply`, and the internal `_update` (used for `transfer`/`transferFrom`) all forward the *raw* bank-module integer amount unchanged via the Bank precompile — there is no scaling applied based on `ddecimals` anywhere in the contract: [4](#0-3) 

Because pointer creation via the precompile is permissionless (`AddNativePointer`, reachable by any EVM caller for any denom with metadata), a tokenfactory denom admin can:
1. Create a tokenfactory denom and mint some raw integer amount of it (e.g., `1` unit).
2. Set `DenomMetadata` with an arbitrarily chosen `Exponent` (e.g. `18`) that has no correspondence to the real intended granularity of the token.
3. Trigger `AddNativePointer` to deploy the ERC20 pointer, which will report `decimals() == 18` while `balanceOf`/`transfer` still move the raw integer `1` unmodified.

Any downstream DeFi protocol, AMM, or bridge that composes with this ERC20 pointer and normalizes/values amounts by `10^decimals()` (a universally standard ERC20 integration pattern) will misprice the token by the chosen factor, exactly mirroring the "StandardizedToken with mismatched decimals" scenario in the referenced report, which the Axelar judge ultimately classified as Medium because it "presents an issue for users... and the token pools themselves... [and] can also be purposefully bridged to steal funds."

### Impact Explanation
An attacker who is nothing more than a normal, unprivileged tokenfactory denom creator can deploy a native ERC20 pointer whose `decimals()` is deliberately inconsistent with the real (unscaled) integer amounts moved by `transfer`/`balanceOf`. Any protocol on Sei's EVM side that composes with this pointer (liquidity pools, lending markets, other pointers/bridges) and relies on the standard ERC20 `decimals()` convention to price or collateralize the asset will be tricked into over- or under-valuing balances by an attacker-chosen power of ten, resulting in fund loss for counterparties/pools that interact with the forged token — an unauthorized-value-transfer analog via pointer composition, consistent with Medium severity as judged in the source report for the equivalent StandardizedToken scenario.

### Likelihood Explanation
Likelihood is high: creating a tokenfactory denom, setting arbitrary `DenomMetadata`, and calling the permissionless `AddNativePointer` precompile method are all ordinary, unprivileged actions requiring no special access, governance, or validator collusion — only a single transaction sequence from a public RPC client.

### Recommendation
Either (a) reject pointer creation / disallow using declared `decimals` unless the denom's `DenomMetadata` exponent structure is independently verifiable against the actual on-chain unit convention (e.g., require `decimals == 0` for tokenfactory denoms unless a canonical, chain-enforced scaling relationship is proven), or (b) have `NativeSeiTokensERC20` actually scale the raw bank amount by the declared `decimals` consistently in `balanceOf`/`totalSupply`/`_update`, so the reported `decimals()` is always truthful with respect to the values actually transferred, removing the ability for a denom admin to declare an arbitrary, disconnected decimals value.

### Proof of Concept
1. As an unprivileged user, submit `MsgCreateDenom` to create `factory/<sender>/mytoken` via the tokenfactory module.
2. Submit `MsgMint` to mint `1` raw unit of `factory/<sender>/mytoken` to self.
3. Submit `MsgSetDenomMetadata` for this denom with a `DenomUnit` whose `Exponent = 18` (arbitrary, unrelated to the "1 unit" minted) — this passes `Metadata.Validate()` and admin-authorization checks with no consistency requirement, per `x/tokenfactory/keeper/msg_server.go` `SetDenomMetadata`.
4. Call the pointer precompile's `AddNativePointer(denom)` from any EVM account — this is permissionless and deploys `NativeSeiTokensERC20` with `ddecimals = 18` baked in, per `precompiles/pointer/pointer.go` `AddNative`.
5. Query the pointer's `decimals()` → returns `18`; query `balanceOf(self)` → returns the raw integer `1` (not `1e18`), because `NativeSeiTokensERC20.balanceOf`/`totalSupply`/`_update` simply forward the raw bank amount with no scaling.
6. Any external protocol treating this pointer as a standard `decimals=18` ERC20 and computing value as `balance / 10^18` will see effectively "0.000000000000000001" tokens for a full raw unit — or, in the reverse mismatch case (declaring `decimals=0` for a token intended to be fine-grained), a protocol will overvalue the raw integer balance by `10^18`, allowing the denom admin to extract disproportionate value from any pool/market that accepts this pointer as collateral or a trading pair, exactly mirroring the "loss of funds due to decimals mismatch that the source/destination side both trust blindly" pattern from the referenced report.

```go
func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
```

```text
    constructor(string memory denom_, string memory name_, string memory symbol_, uint8 decimals_) ERC20("", "") {
        BankPrecompile = IBank(BANK_PRECOMPILE_ADDRESS);
        denom = denom_;
        nname = name_;
        ssymbol = symbol_;
        ddecimals = decimals_;
    }

    function name() public view override returns (string memory) {
        return nname;
    }

    function symbol() public view override returns (string memory) {
        return ssymbol;
    }

    function balanceOf(address account) public view override returns (uint256) {
        return BankPrecompile.balance(account, denom);
    }

    function decimals() public view override returns (uint8) {
        return ddecimals;
    }

    function totalSupply() public view override returns (uint256) {
        return BankPrecompile.supply(denom);
    }

    function _update(address from, address to, uint256 value) internal override {
        bool success = BankPrecompile.send(from, to, denom, value);
        require(success, "NativeSeiTokensERC20: transfer failed");
        emit Transfer(from, to, value);
    }
```
