### Title
Silent remote-URL takeover via unvalidated GitHub API `clone_url` — (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically rewrites a repository's local git remote URL to match the `clone_url` field returned by the GitHub API for the associated `GitHubRepository`, with no restriction that the new host be the same as the previously-trusted host. This mirrors the "reserve desync" bug class from the external report: a critical accounting/authoritative value (here, the trusted push/fetch destination) is updated based on an external, attacker-influenceable object (`IAPIRepository.clone_url`) instead of being re-derived/verified against ground truth, and the guard conditions do not actually validate the new value's legitimacy — only that it "looks like" a URL with a matching protocol.

### Finding Description
`updateRemoteUrl` [1](#0-0)  updates `gitStore.defaultRemote` to `apiRepo.clone_url` whenever three conditions hold:
1. `protocolsMatch` — only checks that the URL scheme (`https:`/`ssh:`-parseable) is unchanged, not that the host is unchanged [2](#0-1) .
2. `remoteUrlUnchanged` — checks the *current* remote still matches the *previously cached* `gitHubRepository.cloneURL` via `urlMatchesRemote` [3](#0-2) .
3. `!urlsMatch` — the new `apiRepo.clone_url` differs from the current remote [4](#0-3) .

None of these conditions constrain the new URL's **hostname** to be the same as (or a known-safe variant of) the original. `urlMatchesRemote` only compares hostname/owner/name equality between two given URLs [5](#0-4)  — it is never used here to assert that the *incoming* `clone_url`'s hostname equals the *existing* remote's hostname. So if the GitHub API repository object's `clone_url` reports a different host (same protocol), Desktop will call `gitStore.setRemoteURL(...)` and silently repoint the local remote to that host.

The broken invariant: "the local git remote must only be updated to a URL that is verified to belong to the same host/identity the user originally trusted" is not enforced — the code enforces protocol continuity and "no manual override" but not host continuity.

### Impact Explanation
If an attacker can influence the `clone_url` returned for a tracked `GitHubRepository` (e.g., a compromised/malicious GitHub Enterprise Server the user is signed into, a proxy/MITM on an HTTP(S) GHE endpoint without certificate pinning, or any code path that constructs an `IAPIRepository` from externally-supplied/attacker-controlled data), Desktop will silently rewrite the user's git remote to point at an attacker-controlled host of the same scheme. Subsequent `git push`/`git fetch` operations — and the credential material sent for them via the trampoline credential helper — go to the attacker's host instead of the real one, satisfying the "silent corruption of what the user commits or pushes" / "credential exfiltration" impact class in scope.

### Likelihood Explanation
Exploitation requires the attacker to control or manipulate a GitHub API repository response reaching this code path — realistic for a compromised/rogue GHE instance or a network-position attacker against non-pinned HTTP(S) API traffic, but not for the default github.com flow (which is TLS-protected and server-trusted). This narrows applicability primarily to GHE/self-hosted scenarios and does not require local access, admin rights, or prior malware, matching the in-scope "GitHub API object" attacker primitive. I could not fully trace every call site of `updateRemoteUrl` in `app-store.ts` within the available tool budget (only reference counts were retrieved, not the surrounding refresh-trigger logic), so the exact refresh cadence/trigger conditions (e.g., whether it runs on every repository refresh or only after specific user actions) remain unverified.

### Recommendation
In `updateRemoteUrl`, add an explicit hostname-equality check between the current `gitStore.defaultRemote.url` and `apiRepo.clone_url` (or otherwise validate the new host against an allow-list derived from the signed-in account's endpoint) before calling `setRemoteURL`. Do not treat "same protocol" as sufficient proof of trust; only auto-update the remote when the hostname is unchanged (e.g., only the owner/name path segment differs, such as after a rename/transfer within the same host).

### Proof of Concept
Not executable from static analysis alone (requires a controlled/malicious GHE-like API endpoint). Conceptual reproduction:
1. User has repository `R` with remote `https://ghe.example.com/org/repo.git`, tracked as a `GitHubRepository` with cached `cloneURL = https://ghe.example.com/org/repo.git`.
2. Attacker controls (or MITMs) the GHE API endpoint and returns an `IAPIRepository` object for `R` with `clone_url: "https://evil.example.com/org/repo.git"`.
3. On the next repository refresh, `updateRemoteUrl` is invoked: `protocolsMatch` is true (both `https:`), `remoteUrlUnchanged` is true (user hasn't manually edited the remote), `urlsMatch` is false (hostnames differ) [6](#0-5) .
4. `gitStore.setRemoteURL(remote.name, "https://evil.example.com/org/repo.git")` executes silently, with no user prompt, redirecting future pushes/fetches (and credential-helper lookups) to `evil.example.com`.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
