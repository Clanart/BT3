### Title
Attacker-controlled `Interpolation::Constant` coefficients and `secret_share` in `ThresholdKeys::read` fabricate share weight with only a self-referential consistency check — (File: crypto/dkg/src/lib.rs)

### Summary
The vault-inflation bug class — minting a disproportionate share relative to what was actually contributed, by writing into a "denominator" that nobody re-validates — maps onto `ThresholdKeys::read` / `ThresholdKeys::new` in `crypto/dkg`. The deserialization accepts (a) an arbitrary `secret_share`, (b) arbitrary per-participant verification shares, and (c) for `Interpolation::Constant`, an arbitrary weight vector `c`. The holder's effective share of the group key is `c[i-1] * secret_share` (crypto/dkg/src/lib.rs:228), yet no code path ever binds `secret_share` to `verification_shares[i]` (`ThresholdKeys::new` checks only counts and index ranges, crypto/dkg/src/lib.rs:355-365), and the sole "consistency" check in `recover_key` compares `G * recovered` against a `group_key` that is itself derived from the same untrusted coefficients and verification shares (crypto/dkg/recovery/src/lib.rs:73-84). The check is circular: crafted inputs trivially satisfy it, exactly as crafted deposit/balance pairs satisfy a vault whose share price was skewed after slashing.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses the interpolation tag, and for tag `0` reads `n` arbitrary scalars as `Interpolation::Constant(c)` (lines 604-616), an arbitrary `secret_share` (line 618), and `n` arbitrary verification-share points (lines 620-623), then calls `ThresholdKeys::new`. `new` validates only that the share count equals `n`, indexes are `<= n`, and `t == n` for Constant interpolation (lines 355-374) — it never verifies `C::generator() * secret_share == verification_shares[params.i()]`. The group key is then computed as `sum(verification_shares[i] * c[i-1])` over `1..=t` (lines 376-378), i.e., the weight each participant's "deposit" contributes is wholly defined by attacker-chosen `c` and `V_i`.

Downstream, `view` multiplies the holder's secret share by `interpolation_factor` = `c[i-1]` (lines 494-498), so a participant's effective claim on the group key is decoupled from any verified contribution — the inflation primitive. `recover_key`'s "from distinct sessions or otherwise corrupt" guard recomputes the group key from the interpolated shares but compares it against `first_keys.group_key()`, which was derived from the same adversarial bytes (crypto/dkg/recovery/src/lib.rs:73-84), so forgery is undetectable. The `group_key` consistency comparison across supplied keys (lines 51-70) likewise compares attacker-written group keys to each other, not to any externally committed value, and notably does not compare the `interpolation` method at all — keys with different coefficient vectors but equal derived group keys are accepted as "consistent."

### Impact Explanation
An unprivileged party who can supply `ThresholdKeys` bytes to a victim (key-package distribution, coordinated recovery, backup restore — precisely what `write`/`serialize`/`read` exist for) can fabricate a threshold key where the entire signing weight resolves to a scalar they chose. By setting e.g. `c = [1, 0, ..., 0]`, `V_1 = G * s` for known `s`, and `secret_share = s`, the resulting `group_key()` is a key the attacker fully controls, while the victim believes they hold a `t`-of-`n` share of a collectively backed key. Any funds the victim (or integrator crediting deposits to `group_key()`) sends to that address are spendable solely by the attacker — "funds reported received that are not spendable" by the presumed owner, and the first/honest depositor's deposit is captured, mirroring the report's primary risk.

### Likelihood Explanation
Reachability requires an integrator to load key material from an untrusted transport, which is the stated purpose of the serialization API and is an explicitly in-scope untrusted-byte sink (`ThresholdKeys::read`). The `Constant` interpolation variant exists specifically for `t == n` full-teams (crypto/dkg/src/lib.rs:368-371), the most common deployed configuration. No additional cryptographic assumptions are needed; the forgery is a byte-level construction.

### Recommendation
In `ThresholdKeys::new` (and on the `read` path), verify `C::generator() * secret_share == verification_shares[params.i()]`, and for `Interpolation::Constant` reject all-zero or degenerate coefficient vectors and verify the coefficients reconstruct the expected commitment (e.g., that `sum(c_i * V_i)` is consistent with a domain-separated hash of the parameter set stored alongside). In `recover_key`, include `interpolation` (and its coefficients) in the cross-key consistency tuple at crypto/dkg/recovery/src/lib.rs:51-70 rather than accepting keys with divergent weights.

### Proof of Concept
```rust
// Attacker-chosen secret and group key under their sole control
let s = <Secp256k1 as Ciphersuite>::F::random(&mut OsRng);

// t == n == 2, victim is Participant 1
let params = ThresholdParams::new(2, 2, Participant::new(1).unwrap()).unwrap();

// Constant weights: participant 1 holds 100% of the "vault shares"
// regardless of what was actually dealt
let interpolation = Interpolation::Constant(vec![
  <Secp256k1 as Ciphersuite>::F::ONE,
  <Secp256k1 as Ciphersuite>::F::ZERO,
]);

let mut verification_shares = HashMap::new();
verification_shares.insert(Participant::new(1).unwrap(), Secp256k1::generator() * s);
verification_shares.insert(Participant::new(2).unwrap(), ProjectivePoint::random(&mut OsRng));

// ThresholdKeys::new never checks G * secret_share == verification_shares[i];
// group_key() == G * s, fully known to the attacker
let keys = ThresholdKeys::new(params, interpolation, Zeroizing::new(s), verification_shares)
  .unwrap();
assert_eq!(keys.group_key(), Secp256k1::generator() * s);

// Serialized; any victim deserializing and crediting group_key() with a deposit
// hands the funds to the attacker — the "inflated share" was minted from bytes,
// not from a verified contribution to the shared secret.
let bytes = keys.serialize();
let _loaded = ThresholdKeys::<Secp256k1>::read(&mut bytes.as_slice()).unwrap();
```
