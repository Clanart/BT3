## Analysis

This is a strong structural analog. The Solidity bug is: a sentinel value (`type(int128).max`) used to signal a special state (canceled) is not actually validated against real/attacker-reachable inputs, so an attacker can produce a legitimate-looking value that collides with the sentinel and forces the code down the "special state" branch unintentionally.

The equivalent pattern in GitHub Desktop is in the porcelain-v2 status header parser.

### Title
Attacker-controlled branch name `(detached)` collides with the detached-HEAD sentinel, causing GitHub Desktop to silently misreport/mistreat a real branch as detached HEAD - (File: `app/src/lib/git/status.ts`)

### Summary
`parseStatusHeader` treats the literal string `(detached)` as a sentinel meaning "HEAD is detached," which is how `git status --porcelain=v2 --branch` legitimately reports a detached HEAD. However, `(detached)` is also a syntactically valid Git branch name. If a remote/cloned repository defines (and the user checks out) a branch literally named `(detached)`, Git's own `branch.head` header is textually identical to the detached-HEAD case, and Desktop's parser cannot distinguish the two.

### Finding Description
In `parseStatusHeader`: [1](#0-0) 
the code does `if (match[1] !== '(detached)') { currentBranch = match[1] }` — i.e. it uses the string `(detached)` purely as a sentinel to decide "this is not a real branch." This mirrors the Solidity bug's use of `type(int128).max` as a sentinel without checking whether that sentinel is actually reachable through a legitimate/attacker-controlled path.

Downstream, `GitStore.loadStatus` consumes `currentBranch`/`currentTip` from that same header data: [2](#0-1) 
Because `currentBranch` was suppressed by the sentinel check, `currentBranch` is falsy even though `currentTip` (the OID) is present, so the code falls into `else if (currentTip) { this._tip = { kind: TipState.Detached, currentSha: currentTip } }` — exactly the same "state gets overridden by the sentinel-triggering value" pattern as the Solidity bug, where the sentinel forces the auction into the canceled branch regardless of actual state.

`TipState.Detached` is a `Tip` variant checked throughout the app (`app/src/models/tip.ts`, `app/src/lib/stores/app-store.ts`, `app/src/lib/create-branch.ts`, `app/src/ui/toolbar/push-pull-button.tsx`, `app/src/ui/toolbar/branch-dropdown.tsx`, `app/src/lib/menu-update.ts`) to gate branch-name display, push/pull button behavior, and "create branch"/"publish branch" flows — all of these would treat the user as being on a detached commit rather than the real branch named `(detached)`.

### Impact Explanation
Git ref names permit parentheses; `(detached)` is not a reserved or disallowed ref name, so a malicious repository owner can push/name a branch literally `(detached)`. Any user who fetches/checks out that branch will have Desktop's own status parser misclassify their `HEAD` as detached, even though the real Git state has a proper symbolic ref. This corrupts the app's internal model of "what branch am I on," which:
- can mislead commit/branch-protection logic that keys off `TipState.Valid` vs `TipState.Detached`,
- can disable/alter push behavior (Desktop treats detached HEAD differently for push/pull UI),
- can hide the actual branch name from the user in the toolbar/branch dropdown.

This matches the "silent corruption of what the user commits or pushes"/mis-tracked repo state impact category, since the discrepancy is invisible to the user (the UI will show a plausible but wrong "detached HEAD" state).

### Likelihood Explanation
Requires only that the attacker control a repository/branch name that the victim fetches or clones and checks out — no local access, no elevated privileges, and no unusual user action beyond a normal checkout of an attacker-supplied branch. This satisfies the "attacker controls a cloned/fetched repository" trigger condition.

### Recommendation
Do not rely on the literal string `(detached)` as an unambiguous sentinel. Instead, use the porcelain-v2 `branch.oid` + absence/presence of the `branch.head` semantics more strictly: Git always additionally omits the `branch.upstream` header and marks the OID as `(initial)`-independent for detached state, or the parser can distinguish detached state via the actual `HEAD` symbolic-ref resolution status (`git symbolic-ref -q HEAD` failing) rather than string-matching header text that is also a legal ref name. At minimum, validate that a real branch named `(detached)` cannot exist/be checked out via this path, or escape/quote ambiguity by consulting `git rev-parse --symbolic-full-name HEAD` in addition to the porcelain header.

### Proof of Concept
1. Attacker creates a repository, runs `git checkout -b '(detached)'`, commits, and pushes it to a remote the victim will fetch/add.
2. Victim clones/fetches the repo in GitHub Desktop and checks out branch `(detached)`.
3. Git's `status --porcelain=v2 --branch` reports `# branch.head (detached)` (same as a genuine detached HEAD).
4. `parseStatusHeader` in `app/src/lib/git/status.ts` (lines 369-372) discards the branch name because it matches the sentinel.
5. `GitStore.loadStatus` (`app/src/lib/stores/git-store.ts` lines 1140-1161) sets `this._tip = { kind: TipState.Detached, currentSha: currentTip }` even though the user is actually on the real branch `(detached)`.
6. All downstream UI/state (branch dropdown, push/pull button, create-branch flow, menu state) now treats the session as detached HEAD instead of reflecting the true branch, silently diverging Desktop's model of repo state from Git's actual state.

Note: I was unable to execute the actual `git status --porcelain=v2` command against a live repository from the index alone to double-confirm Git's exact header text for a branch named `(detached)`; this is based on the documented porcelain-v2 format and the parser's sentinel comparison in code. Confirming this in a live sandbox/terminal would strengthen certainty, and full behavioral confirmation of every downstream consumer (`app-store.ts`, `push-pull-button.tsx`, etc.) would benefit from a Devin session with terminal access to trace the exact code paths, since only partial file contents were retrievable via the index.
