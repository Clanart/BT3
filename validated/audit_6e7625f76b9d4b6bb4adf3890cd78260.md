### Title
Zero-value `order.user`/beneficiary collapses `_filled` finalization sentinel, enabling refund/fill race and fund loss - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The `TwabController` bug stems from overloading `address(0)` as both "default/self-delegate" and "explicit reset target," so writing the sentinel value destroys the real state. The `IntentGatewayV2` intents system has the same overloaded-sentinel pattern: the `_filled` mapping uses `address(0)` to mean "order not yet finalized," but the value written into `_filled` on refund/cancel paths is derived directly from the attacker-controlled `order.user` field with no non-zero check.

### Finding Description
`_filled` is documented as: "A non-zero value indicates the order has been finalized and cannot be filled again" [1](#0-0) .

The finalize path writes the beneficiary address straight into this sentinel-typed mapping without validating it is non-zero:
```
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    if (finalize) _filled[body.commitment] = beneficiary;
``` [2](#0-1) 

For the refund flow, `body.beneficiary` is set to `order.user` verbatim: `WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user})` [3](#0-2) . `order.user` is a field the order creator supplies as part of the `Order` struct that gets hashed into the commitment — there is no check anywhere in the read code path that rejects `order.user == bytes32(0)`.

The destination-side cancel path also writes this same value as an immediate anti-refill lock: `_filled[commitment] = address(uint160(uint256(order.user)));` [4](#0-3) . If `order.user` is `bytes32(0)`, this "lock" write is indistinguishable from the mapping's default/never-touched state, so any downstream guard of the form `_filled[commitment] != address(0)` (used both to prevent double-fills and to prevent double-cancel, e.g. `if (_filled[commitment] != address(0)) revert Filled();`) treats a *cancelled* order as still open.

### Impact Explanation
An order whose `user` field is `bytes32(0)`:
1. On the destination chain, `_cancelFromDest`'s anti-refill write is a no-op (it writes back the sentinel value), so a solver can still call the fill path afterward and dispatch a competing `RedeemEscrow` message, even though a `RefundEscrow` message is already in flight to the source chain.
2. On the source chain, `_withdraw` decrements `_orders[commitment][token]` on the *first* message it processes and sends tokens to `beneficiary`. If the `RefundEscrow` message (beneficiary = `address(0)`) lands first, escrowed input tokens are sent to `address(0)` — permanently burned — and `_filled[commitment]` is written back to the sentinel `address(0)`. The subsequent `RedeemEscrow` message for the solver who already paid out real output tokens on the destination chain then hits `if (escrowed == 0) revert UnknownOrder();` [5](#0-4)  and reverts, so the solver is never reimbursed.

Net effect: input tokens are irrecoverably burned to `address(0)` and/or a solver who fulfilled the order legitimately loses their output-token payment with no recovery path — a direct, unauthorized loss-of-funds condition triggered purely by how the order was constructed, not by any relayer, prover, or admin misbehavior.

### Likelihood Explanation
The trigger is fully within the control of an ordinary, unprivileged user who calls `placeOrder`: they simply set `order.user = bytes32(0)` while genuinely escrowing tokens under `msg.sender`'s deposit. No malicious relayer, prover, or governance actor is required — this satisfies the bounty's "unprivileged attacker" and "false state acceptance / duplicate settlement" bar. The main open question (not fully verifiable in the available index) is whether `placeOrder` enforces `order.user == msg.sender`; the presence of an independent `session` field in `Order` (seen in test fixtures) suggests the gateway supports placing/authorizing orders where `user` is not strictly tied to `msg.sender`, which would make this field attacker-settable at order-creation time.

### Recommendation
- Reject `order.user == bytes32(0)` at `placeOrder` time (mirroring the `TwabController` mitigation of rejecting `_to == address(0)`).
- Independently, harden `_filled` semantics so "finalized" is tracked via a separate boolean/flag rather than overloading `address(0)` with a real, attacker-influenced beneficiary address; e.g. use a struct `{bool finalized; address beneficiary;}` or a sentinel that cannot collide with a valid address such as `address(1)`.
- Add an explicit `beneficiary != address(0)` check inside `_withdraw` before performing any transfer or `_filled` write, reverting instead of silently burning funds or resetting the finalize flag.

### Proof of Concept
1. User calls `placeOrder` with `order.user = bytes32(0)` and `order.destination` a different chain, escrowing real USDC from `msg.sender`.
2. Before the order is filled, the user (or anyone, after `deadline`) calls `cancelOrder` on the destination chain → `_cancelFromDest` executes `_filled[commitment] = address(uint160(uint256(order.user)))`, which writes `address(0)`, i.e. a no-op against the "unfilled" sentinel [6](#0-5) .
3. A solver observes `_filled[commitment] == address(0)` (still looks unfilled) and calls the cross-chain fill path, delivering real output tokens to the order's beneficiary and dispatching `RedeemEscrow` to the source chain.
4. Both `RefundEscrow` (beneficiary=`address(0)`) and `RedeemEscrow` (beneficiary=solver) messages arrive at the source-chain gateway's `onAccept`, both calling `_withdraw`. Whichever is processed first drains `_orders[commitment][token]` to zero and sends funds to its `beneficiary`; if `RefundEscrow` wins, the escrowed input is sent to `address(0)` (burned) and the second message reverts with `UnknownOrder`, leaving the solver unpaid for tokens it already delivered [7](#0-6) .

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
