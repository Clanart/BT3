### Title
`ReceivedOutput::read` accepts outputs whose script cannot be spent with the encoded offset - ([File: `networks/bitcoin/src/wallet/mod.rs`](networks/bitcoin/src/wallet/mod.rs#L120-L134))

### Summary
`ReceivedOutput::read` deserializes an arbitrary secp256k1 offset, `TxOut`, and `OutPoint`, then returns them as a spendable output without checking that the `TxOut` script is the P2TR output derived from the scanner key plus the claimed offset. Untrusted serialized output records can therefore claim arbitrary Bitcoin outputs or scripts as spendable by the wallet.

### Finding Description
`ReceivedOutput` models “a spendable output” and carries both the scalar offset needed to derive the spending key and the claimed `TxOut`/`OutPoint` [1](#0-0) . Its deserializer only calls `Secp256k1::read_F` and Bitcoin consensus decoding for the two fields [2](#0-1) . It never verifies that `output.script_pubkey == p2tr_script_buf(group_key + G * offset)`.

`Scanner::scan_transaction` only creates internally consistent objects by looking up the transaction output’s `script_pubkey` in the registered script map [3](#0-2) . `ReceivedOutput::read` lacks that invariant, however, and exposes a direct way to construct a malformed object from bytes [4](#0-3) .

The malformed object is not caught at transaction construction: `SignableTransaction::new` sums the claimed `TxOut` value, copies the claimed offset and outpoint, and stores the claimed `TxOut` as a prevout without checking the script/offset relation [5](#0-4) . The first consistency check occurs only later in `multisig`, where the transaction is silently rejected if `p2tr_script_buf(offset.group_key())` does not equal the stored prevout script [6](#0-5) .

### Impact Explanation
A maliciously encoded `ReceivedOutput` can cause an invalid token/output deposit to be represented as wallet value. For example, attacker bytes can encode:

- an honest wallet offset, such as `Scalar::ZERO`;
- an attacker-controlled P2TR `TxOut`;
- an arbitrary or attacker-owned outpoint.

The resulting `balance()` reports the full attacker output value as Bitcoin received by the wallet [7](#0-6) . `SignableTransaction::new` also counts that value toward available funds [8](#0-7) . The output is nevertheless not spendable by the wallet because `multisig` ultimately finds that the encoded offset derives a different P2TR script and returns `None` [6](#0-5) .

This maps to funds being reported received that are not spendable. Depending on how the caller stores or credits deserialized outputs before constructing the multisig machine, deposits can be credited while the subsequent signing flow cannot spend them.

### Likelihood Explanation
An unprivileged party only needs to supply bytes accepted by `ReceivedOutput::read`; no private keys or validator privileges are required. Bitcoin consensus decoding does not establish that a `TxOut` belongs to Serai’s scanner or is spendable under the serialized offset. The malformed object is accepted by the public reader and value/accounting path, while detection is delayed until signing setup.

### Recommendation
Make `ReceivedOutput`’s invariant explicit at deserialization or construction:

- include the scanner/group key or expected script in validation context;
- derive `key + G * offset`;
- require `p2tr_script_buf(derived_key)` to equal `output.script_pubkey`;
- reject malformed or non-P2TR scripts during `read`.

If the group key cannot be available inside `ReceivedOutput::read`, provide a checked constructor/read API such as `ReceivedOutput::read_for_key(key, reader)` and avoid exposing an unchecked reader for untrusted data. `SignableTransaction::new` should additionally reject inputs failing this relation before accounting for their value.

### Proof of Concept
Conceptually, for group key `K`:

```text
offset = Scalar::ZERO
txout = TxOut {
  value: 100_000,
  script_pubkey: P2TR(attacker_key),
}
outpoint = arbitrary_valid_encoding
encoded = offset || consensus(txout) || consensus(outpoint)
```

`ReceivedOutput::read(encoded)` returns `Ok`, while:

```text
P2TR(K + G * offset) == P2TR(K) != P2TR(attacker_key)
```

Thus `value()` reports `100_000`, but `SignableTransaction::new(...).multisig(keys_for_K)` returns `None` because the script check fails.
