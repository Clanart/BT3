### Title
`SignableTransaction::new` undercounts transaction weight when `data` is set, producing a `needed_fee` inconsistent with the actual signed transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a fee calculated with an inconsistent formula between two functions (`redeem` vs `withdraw`), so that the value actually charged differs from the value derived by the sibling function. `SignableTransaction` has the same shape: `calculate_weight_vbytes` derives the fee from a reconstructed transaction that includes only `payments` and an optional `change` output, while `new` additionally appends an `OP_RETURN` output for `data` *after* the weight/vbytes (and therefore `needed_fee`) have already been fixed. The fee formula is computed against a transaction that is not the transaction actually signed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` builds `tx_outs` from `payments`, pushes an `OP_RETURN` output when `data` is specified (lines 194-202), and only *then* calls `calculate_weight_vbytes(tx_ins.len(), payments, None)` (line 204). `calculate_weight_vbytes` (lines 62-127) reconstructs a `Transaction` whose `output` vector is built solely from `payments` plus the optional `change` output — it has no knowledge of `data`. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on a vbytes that excludes the `OP_RETURN` output (~92 extra bytes / ~92 extra vbytes for a maximal 80-byte payload, since it is entirely non-witness data).
- The `TooLowFee` check (line 211) compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same underestimated `vbytes`, so the minimum-relay-fee guard is evaluated against the wrong transaction size.
- The same omission applies to the second call at lines 225-226 (`vbytes_with_change`), and to the `weight > MAX_STANDARD_TX_WEIGHT` check at line 241, which is evaluated on a weight that never includes the `OP_RETURN` output.

Because the actual fee paid is `sum(inputs) - sum(outputs)` and the `OP_RETURN` output is zero-valued, the transaction pays exactly `needed_fee` — an amount computed for a smaller transaction than the one broadcast. The realized feerate is therefore strictly lower than `fee_per_vbyte`, and can fall below the 1 sat/vbyte minimum relay feerate the `TooLowFee` check was intended to enforce.

### Impact Explanation
A `SignableTransaction` constructed with a `data` payload and a `fee_per_vbyte` at or near the minimum relay rate produces a transaction whose *actual* feerate is below `DEFAULT_MIN_RELAY_TX_FEE` — e.g., a ~200-vbyte payment transaction paying `~200` sats while its real size is ~292 vbytes (~0.68 sat/vb). Such a transaction will not be relayed by standard nodes, leaving the inputs it spends effectively stuck until a replacement is constructed — funds locked despite `TooLowFee` "passing". At higher fee rates the transaction still systematically underpays versus the caller's requested rate, degrading confirmation reliability. This mirrors the report's class: a fee computed under a different formula/basis than the one it is meant to satisfy.

### Likelihood Explanation
Any caller that supplies `data` (a documented, public parameter of `new`, validated to fit 80 bytes) triggers the discrepancy deterministically — no adversarial timing or privileged position is needed. Whether an unprivileged party can force the multisig to attach `data` depends on the integrator; the defect itself is reachable purely through public inputs (`inputs`, `payments`, `change`, `data`, `fee_per_vbyte`) to `SignableTransaction::new`. Impact is moderate (stuck/unrelayable transactions, underpaid fees), not direct theft.

### Recommendation
Include the `data` output inside the weight estimation. Either:
- Pass `data` into `calculate_weight_vbytes` and append the `OP_RETURN` `TxOut` to the template transaction before calling `tx.weight()`, or
- Call `calculate_weight_vbytes` on `tx_outs` (the final output vector, including any `OP_RETURN`) rather than on `payments` alone — noting this must happen for both the no-change and with-change estimations.

This makes `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check all evaluated against the same transaction that is actually signed and broadcast.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs context; Secp256k1 keypair and rpc as in test_send
// fee_per_vbyte = 1 sat/vb equals DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvB)
let data = vec![0u8; 80]; // largest permitted OP_RETURN payload

let tx = SignableTransaction::new(
  vec![output.clone()],          // one spendable input
  &[(p2tr_script_buf(key).unwrap(), 10_000)],
  None,                          // no change: leftover beyond needed_fee also becomes fee
  Some(data),                    // OP_RETURN output appended after weight calc
  1,                             // 1 sat/vbyte — the minimum relay rate
).unwrap();

let real_vsize = /* vsize of tx.transaction() including the OP_RETURN output */;
let needed = tx.needed_fee();

// needed_fee passed the TooLowFee check against the smaller, data-less estimate,
// but the real transaction is ~90 vbytes larger:
assert!(real_vsize > needed); // needed == estimated vbytes < real vsize

// Realized feerate = needed / real_vsize < 1 sat/vb, so standard nodes will not relay it.
// The TooLowFee guard is defeated: the signed TX is systematically under-fee'd.
```

The fix is a one-line scope correction: compute weight/vbytes from the complete output set (payments + OP_RETURN + optional change) so `needed_fee` is the fee of the transaction actually produced.
