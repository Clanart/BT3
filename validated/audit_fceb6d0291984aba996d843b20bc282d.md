### Title
Excess native-token fee payment to `EvmHost.dispatch` is permanently trapped in the host contract instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
The external report's core broken invariant is: a payable entrypoint computes a fee/cost internally, forwards that fee via `{value: ...}` to an inner call, but never reconciles the *actual* `msg.value` sent by the caller against what was consumed — so any surplus is neither refunded nor accounted for, and is effectively lost (or, worse, later spendable by someone else). `EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` reproduce exactly this pattern for native-token fee payment.

### Finding Description
`dispatch(DispatchPost)` and `dispatch(DispatchGet)` are public payable entrypoints that accept `msg.value` and, when non-zero, forward the **entire** `msg.value` into a Uniswap-style swap to acquire the exact `post.fee`/`get.fee` amount of the fee token: [1](#0-0) [2](#0-1) 

`swapETHForExactTokens` only needs to consume `amounts[0] <= msg.value` (the input required to buy exactly `post.fee`). Any unspent amount is refunded by the swap implementation to **its own caller**, i.e. `msg.sender` of that inner call — which is `EvmHost` itself, not the original transaction sender (`_msgSender()`). This is visible in the project's own router wrapper: [3](#0-2) 

The refund (`refundETH`) is sent to `msg.sender`, which from `EvmHost`'s perspective is `EvmHost` itself when it calls the wrapper on the user's behalf. After the swap call returns, `EvmHost.dispatch` does not read back any leftover value and does not forward anything to `_msgSender()` — there is no refund path at all in the function body shown above.

The `GnosisUniswapV2Wrapper` variant is even more direct: it consumes the caller's entire `msg.value` regardless of the `amountOut` requested, permanently converting 100% of whatever was sent into the fee token balance held by `EvmHost`: [4](#0-3) 

This is the same class of bug as the PhiFactory report: the payable entrypoint (`claim`/`dispatch`) computes a required payment (`mintFee`/`post.fee`), forwards `msg.value` (or the fee amount) to an external call `{value: ...}`, and never validates/reconciles the caller's actual payment against what was truly needed — so overpayment is unrecoverable by the payer and accrues silently to the contract's own balance.

By contrast, the newer intent contracts (`IntentGatewayV2`, `ExtrinsicIntents`) correctly track a local `msgValue` variable, decrement it as it's spent, and explicitly refund any remainder to `msg.sender` at the end of the function — proving the codebase is aware of this exact hazard and has a fix pattern, but `EvmHost.dispatch` (the primary dispatch entrypoint used by every `HyperApp`, including `HyperFungibleToken`, `WrappedHyperFungibleToken`, and the LayerZero endpoint adapter) does not apply it.

### Impact Explanation
Every dispatch of a POST or GET request paid for in native token risks silent loss of funds for the caller whenever the supplied `msg.value` exceeds the exact wei amount required to buy `fee` units of the fee token (a near-certainty in practice, since callers must overestimate the swap price to avoid reverts, per the documented guidance to send generous buffers, e.g. `quote(request) * 2` in the LayerZero endpoint adapter). The excess ETH is absorbed into `EvmHost`'s own balance with no bookkeeping tying it back to the original payer, and there is no user-facing sweep/refund mechanism for it. This constitutes a direct, repeatable loss of user funds on the core dispatch path used across the entire HyperApp ecosystem (HFT, WrappedHFT, LZ endpoint), matching the bounty's "stealing or loss of funds" and "bridged assets/fees must move exactly once to the rightful beneficiary" criteria.

### Likelihood Explanation
High. This triggers on the unprivileged, primary, publicly documented usage path — every native-fee dispatch call where the caller doesn't send the *exact* wei amount, which the SDK/docs explicitly recommend overestimating (e.g. 2x buffer). No malicious peer, relayer, or governance actor is required; a single honest user calling `dispatch{value: msg.value}(post)` with any buffer above the exact swap cost loses that buffer permanently.

### Recommendation
In `EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)`, capture the actual native amount consumed by the swap (e.g., `amounts[0]` returned by `swapETHForExactTokens`) and refund `msg.value - amounts[0]` back to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2`/`ExtrinsicIntents` (track a local `msgValue`, decrement by amount spent, refund remainder via a low-level `call`).

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: X}(post)` where `post.fee = F` (fee-token units) and the ETH needed to buy exactly `F` fee tokens via `swapETHForExactTokens` is `Y < X` (a normal scenario since the caller must send a buffer to avoid price-slippage reverts, as documented for `HyperFungibleToken.send` and the LayerZero endpoint's `2x` fee buffer).
2. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X}(F, path, address(this), block.timestamp)` executes, consuming `Y` and refunding `X - Y` to its caller, `EvmHost`.
3. `dispatch` returns without ever reading back or forwarding the refunded `X - Y` to the original sender.
4. `X - Y` remains stranded in `EvmHost`'s native balance permanently; the caller has no way to reclaim it. Repeating this across all dispatch calls accumulates ETH loss for users with no corresponding accounting entry pointing back to any payer.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
    }
