### Title
GitHub `GitHubRepository` records are keyed by mutable `owner+name` instead of the immutable GitHub repo ID, letting a renamed/deleted-and-recreated repository silently take over another repository's cached identity - ([File: app/src/lib/stores/repositories-store.ts])

### Summary
`RepositoriesStore._upsertGitHubRepository` deduplicates `GitHubRepository` database rows by `[ownerID+name]` rather than by GitHub's immutable numeric repository ID. This is structurally the same class of bug as the Mini Pool "reinitialization" report: a resource that should have a single, stable identity (an aToken/reserve in the report; a `GitHubRepository` DB record here) can be looked up and overwritten using a *derived, mutable* key, so a second, unrelated real-world entity can be mapped onto — and silently overwrite — the state of the first.

### Finding Description
`_upsertGitHubRepository` resolves the "existing" row to update like this: [1](#0-0) 

and then unconditionally persists the new API payload's `cloneURL`, `htmlURL`, `parentID`, and (when the new payload includes permissions) `permissions` into that same row, preserving its Dexie primary key (`id`) if one already existed: [2](#0-1) 

`owner.id` itself is derived only from `endpoint + login`, not from GitHub's numeric user/org ID, via `putOwner`. So the composite key that identifies a `GitHubRepository` row is entirely `(endpoint, owner-login-string, repo-name-string)` — all attacker-influenceable values that GitHub allows to be reused over time (a user can rename/delete a repo, or an org member can be removed and a name reused, etc.), unlike the numeric `id` field that GitHub API objects (`IAPIRepository`/`IAPIFullRepository`) actually carry to uniquely identify a repository.

Any local `Repository` that already points at this `GitHubRepository` row via `gitHubRepositoryID` (set once, in `setGitHubRepository`) will transparently start resolving to the *new* underlying GitHub repo's `cloneURL`, `htmlURL`, and cached `permissions`/`parentID` the next time Desktop refreshes GitHub metadata (`repositoryWithRefreshedGitHubRepository`, pull request fetches, branch protection checks, etc. all funnel through `upsertGitHubRepository`/`upsertGitHubRepositoryLight`), without the local clone's actual `.git` remote changing at all.

This mirrors the report's broken invariant precisely: `MiniPoolReserveLogic.init` only checked that the *asset* matched, not that the reserve slot hadn't already been bound to a different token identity, so re-adding overwrote `liquidityIndex`, `aTokenID`, and `interestRateStrategyAddress` for an unrelated position. Here, `_upsertGitHubRepository` only checks that `(owner login, repo name)` match, not that the underlying GitHub repository (`id`) is the same, so re-fetching overwrites `cloneURL`, `permissions`, and `parentID` for what Desktop treats as "the same" `GitHubRepository`, even when it is a different repository entirely.

### Impact Explanation
Because `GitHubRepository.cloneURL`/`htmlURL` (attacker-influenced via reused owner/name) get silently re-attached to a pre-existing `dbID` that a user's local clone already references, and because `permissions`/fork `parentID` bookkeeping (used to decide fork/PR/push-protection UI behavior) is also blindly copied over from whatever API object last resolved to that owner+name pair, this falls in the "silent corruption of what the user commits/pushes/collaborates on" bucket: the app's understanding of which remote repository, its permissions, and its fork lineage may become desynchronized from the actual `git remote` in the working directory, all driven by attacker-controlled GitHub API response data (repo name/owner strings), without any user action beyond Desktop's normal background metadata refresh.

### Likelihood Explanation
This requires a somewhat narrow but realistic real-world sequence (rename/delete-then-recreate of a repository under the same owner+name, or owner-login squatting after deletion/rename — a known GitHub phenomenon), plus the victim already having a local Desktop-tracked repository whose `GitHubRepository` metadata gets refreshed after the swap. No local/physical access, no malware, and no unusual user action are needed — Desktop performs these refreshes automatically. This keeps it at a moderate, not "trivial," likelihood, consistent with the "Medium Risk" severity of the original report which had a comparably narrow trigger (unique-token double registration).

### Recommendation
Key `GitHubRepository` upserts by the immutable numeric GitHub repository `id` (present on `IAPIRepository`/`IAPIFullRepository`) rather than by `[ownerID+name]`, falling back to owner+name only as a rename-detection heuristic that still verifies the numeric id matches before reusing a row. This is the same fix pattern the original report recommended for the mini pool: ensure the identity check is against a stable, unique identifier before allowing state to be reused/overwritten.

### Proof of Concept
Conceptual (I could not run this against a live GitHub Desktop instance, only trace it through the codebase):
1. User A adds `attacker/pretend-repo` (real repo, id `111`) to Desktop; Desktop stores a `GitHubRepository` row keyed `[ownerID(attacker), "pretend-repo"]` with `dbID=5`, `cloneURL=https://github.com/attacker/pretend-repo`, `permissions={push:true}`.
2. Attacker deletes `attacker/pretend-repo` and immediately creates a *new*, different repository also named `pretend-repo` under the same `attacker` login (id `222`, different permission set, marked as a fork of some other repo).
3. On Desktop's next background refresh (`repositoryWithRefreshedGitHubRepository` → `upsertGitHubRepository`), `_upsertGitHubRepository` finds the existing row via `[ownerID+name]` match [3](#0-2)  and overwrites `dbID=5`'s `cloneURL`, `permissions`, `parentID` with the new repo's data [4](#0-3) , even though it is a semantically unrelated repository.
4. Any local `Repository` still pointing at `gitHubRepositoryID=5` now silently reports the new repo's URL/permissions/fork-parent state, potentially affecting push-protection bypass and fork-PR handling logic that consult `GitHubRepository.permissions`/`parent`.

I was not able to fully confirm downstream consumers' exact reaction to a `parentID`/`permissions` swap (e.g., whether push-protection bypass logic or fork PR checkout logic could be tricked into an unsafe action) within the available index; a Devin session with full repo access would be needed to trace all `gitHubRepository.parent`/`permissions` consumers to determine the maximum concrete impact.
