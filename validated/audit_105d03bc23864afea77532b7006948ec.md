Confirmed: `tokenConfigs[token].tokenDecimals` is cached once via `IERC20Metadata(token).decimals()` at `_registerToken()` time [1](#0-0) , and this cached value is used forever afterward in `_tokenPrice()` and `_fetchDetails()`/`_validatePaymasterUserOp()` to compute the ERC-20 cost charged to users for gas [2](#0-1) . There is no re-sync of `tokenDecimals` if the underlying token contract's `decimals()` changes after registration (e.g., an upgradeable stablecoin like USDC/USDT proxy increasing/decreasing its decimal count).

### Title
Stale cached `tokenDecimals` in `SimplexPaymaster` mispricing gas after a token decimals upgrade - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` caches a registered ERC-20 token's `decimals()` value once, at `RegisterToken` governance time, into `TokenConfig.tokenDecimals`. This cached value is never invalidated or refreshed, and it feeds directly into `_tokenPrice()`, which computes `erc20Cost = weiCost * tokenPrice / 1e18` for every UserOp paid with that token.

### Finding Description
`_registerToken` sets `tokenDecimals: IERC20Metadata(token).decimals()` a single time [3](#0-2) . `_tokenPrice()` then computes:
```
(nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000)
``` [4](#0-3) 

If the registered token is a proxy-upgradeable stablecoin (the exact class of token this contract is built for — USDC/USDT, per the contract's own NatSpec: "accepts ERC-20 stablecoins (USDC, USDT...)" [5](#0-4) ) and that token's issuer upgrades the implementation to change `decimals()` (this is the same fact pattern the external report describes for USDC), `cfg.tokenDecimals` becomes stale relative to the token's real base-unit scale. Every `validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` call keeps using the old decimals to compute `tokenPrice`, which `PaymasterERC20` then multiplies by `weiCost` to derive `erc20Cost` charged via `transferFrom`/permit prefund. The re-registration path exists (`RequestKind.RegisterToken` calling `_registerToken` again, explicitly documented as "the recovery path for a misbehaving oracle" [6](#0-5) ) but nothing forces or auto-triggers it when only `decimals()` changes — governance re-registration is a manual, discretionary act that can lag or never happen.

If decimals increase (e.g., 6 → 18), the stale (smaller) `tokenDecimals` causes `tokenPrice` to be under-scaled by 10^12, so `erc20Cost` charged to the user is 10^12 times too small — the paymaster prefunds/refunds gas essentially for free while giving up nearly all its ability to recoup gas cost, draining the treasury's EntryPoint deposit relative to fees collected (loss of protocol funds). Conversely, if decimals decrease, users get overcharged by orders of magnitude, extracting excess ERC-20 tokens from unwitting solver accounts via permit/allowance (fund loss to users). This directly mirrors the external report's broken invariant: an assumption that a token's decimals stay fixed across the lifetime of a stored value, invalidated by a token contract upgrade.

### Impact Explanation
This produces a false accounting value (`tokenPrice`) that governs actual token transfers pulled via `transferFrom`/permit for every UserOp. A wrong `tokenDecimals` scale by 10^n directly causes fund loss: either the paymaster's treasury is drained relative to the gas it actually spends (severely under-collects), or users are overcharged (funds taken from user accounts, since Circle/paymaster clients pre-approve amounts sized to the "expected" 6/18-decimal price and could be charged far beyond that if the mismatch runs the other direction). This matches the bounty's "stealing or loss of funds" / "logic attacks" categories since it needs no malicious relayer, prover, or governance actor — only a legitimate token-issuer decimals change (which the report explicitly treats as an in-scope trigger, just as with the original Beanstalk USDC scenario).

### Likelihood Explanation
Requires a supported token's decimals to actually change post-registration — an event outside attacker control, matching exactly the external report's precondition (USDC-style upgradeable proxy changing decimals). Given this contract explicitly targets and reasons about USDC/USDT-class tokens, and offers no re-validation or decimals-drift check anywhere in the hot path (`_validatePaymasterUserOp`, `_fetchDetails`, `_tokenPrice`), the exposure window persists indefinitely until governance manually notices and re-registers.

### Recommendation
Either (a) read `IERC20Metadata(token).decimals()` live in `_tokenPrice()` instead of using the cached `TokenConfig.tokenDecimals`, or (b) add a permissionless `refreshTokenDecimals(address token)` function that reverts if `tokenConfigs[token].tokenDecimals == IERC20Metadata(token).decimals()` and otherwise updates the cache, callable by anyone so drift can't be governance-gated, similar in spirit to the report's suggested `synchronizeFundraiserDecimals`. Additionally consider caching a timestamp/version and periodically forcing re-validation for all `active` tokens.

### Proof of Concept
1. Governance registers `USDC` (6 decimals) via `RegisterToken`; `_registerToken` caches `tokenDecimals = 6` [3](#0-2) .
2. USDC's proxy implementation is later upgraded (by its own issuer, independent of Hyperbridge) so `decimals()` now returns `18`.
3. A user submits a UserOp paying gas with USDC. `_fetchDetails`/`_tokenPrice` still use the stale `cfg.tokenDecimals = 6` [7](#0-6) [4](#0-3) , computing `tokenPrice` scaled by `10^6` instead of the correct `10^18`.
4. `PaymasterERC20` computes `erc20Cost = weiCost * tokenPrice / 1e18`, which is now 10^12 too small; the paymaster charges the user a negligible fraction of a cent in USDC-18-decimal base units for real gas spent, draining the paymaster's EntryPoint deposit over repeated UserOps until governance notices and manually calls `RegisterToken` again.

    function _registerToken(address token, AggregatorV3Interface oracle) internal {
        if (token == address(0) || address(oracle) == address(0)) revert ZeroAddress();

        bool isNew = !tokenConfigs[token].active && address(tokenConfigs[token].tokenOracle) == address(0);

        tokenConfigs[token] = TokenConfig({
            tokenOracle: oracle,
            tokenOracleDecimals: oracle.decimals(),
            tokenDecimals: IERC20Metadata(token).decimals(),
            active: true
        });

        if (isNew) {
            registeredTokens.push(token);
        }

        emit TokenRegistered(token, address(oracle));
    }

    /// @dev Returns the token to charge and its price relative to native gas.
    ///
    ///      PaymasterERC20 computes `erc20Cost = weiCost * tokenPrice / 1e18`,
    ///      so tokenPrice must be token base units per wei, scaled by 1e18:
    ///        tokenPrice = (nativeUsd * 10^tokenDecimals) / tokenUsd
    ///      e.g. BNB at $600, USDC at $1 with 6 decimals: 0.001 BNB (1e15 wei)
    ///      should cost 0.60 USDC (600000 units), giving tokenPrice = 6e8, which
    ///      is exactly (600e8 * 1e6) / 1e8. Markup is applied on top.
    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction
    }

    /// @dev Parse and execute the EIP-2612 permit from paymasterData.
    ///      Layout: mode(1) + token(20) + permitAmount(32) + deadline(32) + v(1) + r(32) + s(32) = 150 bytes
    function _executePermit(PackedUserOperation calldata userOp) internal {
        bytes calldata data = userOp.paymasterData();
        if (data.length != 150) revert InvalidPaymasterData(data.length);

        address tokenAddr = address(bytes20(data[1:21]));
        uint256 permitAmount = uint256(bytes32(data[21:53]));
        uint256 deadline = uint256(bytes32(data[53:85]));
        uint8 v = uint8(data[85]);
        bytes32 r = bytes32(data[86:118]);
        bytes32 s = bytes32(data[118:150]);

        address owner = userOp.sender;

        try IERC20Permit(tokenAddr).permit(owner, address(this), permitAmount, deadline, v, r, s) {
            emit PermitExecuted(tokenAddr, owner, permitAmount);
        } catch {
            revert PermitFailed(tokenAddr);
        }
    }

    // ── Pricing ──────────────────────────────────────────────────────

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }
