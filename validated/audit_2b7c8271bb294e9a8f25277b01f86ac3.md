### Title
Cached FROST preprocess seed is reused across `share()` and `complete()` calls and never deleted, enabling nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to CVE-2021-47416 (a state flag conflating two distinct lifecycle states so cleanup is skipped), the tributary `SigningProtocol` conflates "preprocess cached for this signing session" with "preprocess still valid to sign with". The `CachedPreprocesses` DB entry is written once per `context` and is never cleared or versioned. Every call to `share_internal` — including the second one performed by `DkgConfirmer::complete` — reloads the same seed and re-signs, producing a second FROST signature share under identical nonces whenever the signing set or message differs.

### Finding Description
`SigningProtocol::preprocess_internal` generates a fresh preprocess only when `CachedPreprocesses::get(self.txn, &self.context)` is `None`; otherwise it decrypts and reuses the stored ChaCha20 seed via `AlgorithmSignMachine::from_cache` (`crypto/frost/src/sign.rs`, `seeded_preprocess` derives all nonces deterministically from `ChaCha20Rng::from_seed(*seed.0)`). There is no `CachedPreprocesses::del` anywhere in the codebase — the seed persists forever under `context` and is served on every call.

`DkgConfirmer` sets `context = (b"DkgConfirmer", self.attempt)`. Its `share()` calls `share_internal`, which calls `preprocess_internal` → `machine.sign(preprocesses, msg)`. Its `complete()` calls `share_internal` **again** (`"trying to complete a machine which failed to preprocess"`), which calls `preprocess_internal` → obtains the **same seed** → signs again.

The FROST spec and the code itself document that this is fatal: "Reusing preprocesses would enable a third-party to recover your private key share" (`spec/cryptography/FROST.md`, `crypto/frost/src/sign.rs` doc comments on `CachedPreprocess`/`from_cache`).

The signed message `msg` is `set_keys_message(&self.spec.set(), &removed, key_pair)` and the binding factor `rho` is computed over `group_key`, `hash_msg(msg)` and the per-participant preprocess transcript. Both `key_pair` and the `preprocesses` map are parameters supplied by the caller of `share`/`complete`, which are populated from tributary messages (validator-supplied preprocesses and the DKG's `key_pair`). If the preprocess map or `key_pair` seen by `complete` differs from what was seen by `share` (a participant appearing/disappearing, a differing `key_pair`, or a validator deliberately sending distinct preprocess bytes in the two phases), the coordinator emits two Schnorr shares `s_i = k + e_i·x_share` with the **same** nonce `k` but different challenges `e_i`. Any observer of the tributary (which broadcasts shares) computes `x_share = (s_1 - s_2)/(e_1 - e_2)`.

Additionally, the same stale-state pattern means that if `attempt` ever collides (e.g., a reboot resetting the attempt counter while the DB retains the old entry — the code path in `processor/src/signer.rs` explicitly notes the attempt DB "may not be committed with the expected timing"), a previously consumed seed is silently reused for a wholly new signing session.

### Impact Explanation
An unprivileged tributary validator who causes `complete` to be executed over a different preprocess set or `key_pair` than `share` obtains two signature shares bound to the same nonce. Solving the linear system recovers the coordinator validator's MuSig/FROST secret share over Ristretto, which is the key used to authenticate all tributary (validator-set) signatures — enabling forgery of set-key confirmations and any other protocol signed under `DkgConfirmer`/related `SigningProtocol` contexts. This is key-share recovery, the highest-severity outcome in scope.

### Likelihood Explanation
Both `share()` and `complete()` unconditionally re-derive the machine from the same persisted seed; nothing prevents the second signing from occurring with attacker-influenced inputs (the preprocess map is built from validator-supplied `HashMap<Participant, Vec<u8>>`). The likelihood hinges on whether the coordinator ever re-enters `share_internal` with differing inputs for the same `(b"DkgConfirmer", attempt)` context — reachable via validators publishing distinct preprocesses across DKG phases or across a reboot where `attempt` repeats. Since the seed is never deleted, any context reuse guarantees reuse rather than failing closed.

### Recommendation
Delete `CachedPreprocesses[context]` (or mark it consumed) the first time `share_internal` produces a share, and make `complete` reuse the already-built `AlgorithmSignatureMachine` from `share` rather than re-invoking `share_internal`/`preprocess_internal`. If `complete` must reconstruct state, it should fail when the cached entry is absent/consumed instead of re-signing. Bind the cache to a hash of the intended `(preprocesses, msg)` and refuse to sign if they differ.

### Proof of Concept
1. A tributary validator publishes a valid preprocess for DKG confirmation attempt `a`; the coordinator calls `DkgConfirmer::share(preprocesses_A, key_pair_A)` → emits share `s_1` under nonce seed `seed = CachedPreprocesses[("DkgConfirmer", a)]`.
2. The same (or another) validator causes `DkgConfirmer::complete(preprocesses_B, key_pair_B, shares)` to run where `preprocesses_B ≠ preprocesses_A` (different included set, e.g., withholds its own preprocess in one phase) or `key_pair_B ≠ key_pair_A`. `share_internal` reloads `seed`, producing identical nonces, and emits share `s_2` over a different rho transcript / message.
3. From the broadcast shares, compute `x_share = (s_1 - s_2)·(e_1 - e_2)^{-1} mod ℓ`, recovering the coordinator's Ristretto secret share — exactly the leak the `CachedPreprocess` documentation warns against.

Caveat: I could not fully trace `handle.rs` to confirm that `complete` is reachable with a preprocess set differing from `share`'s for the same attempt; if the coordinator enforces identical inputs, the residual bug is the never-deleted seed enabling reuse on any `context`/`attempt` collision (e.g., across reboots), which still warrants the fix above.
