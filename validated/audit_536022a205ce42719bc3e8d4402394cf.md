### Title
Untrusted `ReceivedOutput` bytes can fabricate Bitcoin inputs and inflate spendable balances - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes the spending offset, complete `TxOut`, and `OutPoint` from attacker-controlled bytes without proving that the referenced UTXO exists or that the claimed amount belongs to that outpoint. `SignableTransaction::new` then trusts the embedded `TxOut.value` as available input value and uses the embedded `TxOut` as the prevout committed by the Taproot sighash. This lets an unprivileged party turn a valid scanner output encoding into a fabricated high-value or nonexistent input, causing Serai to treat unspendable funds as received and to coordinate signatures for a transaction Bitcoin consensus will reject.

### Finding Description
`ReceivedOutput::read` accepts three independent fields—scalar offset, `TxOut`, and `OutPoint`—but performs only syntactic consensus decoding and scalar validity checking. [1](#0-0) 

The returned object directly exposes the attacker-chosen Bitcoin amount through `value()`. [2](#0-1) 

`SignableTransaction::new` treats those attacker-controlled fields as authoritative input state: it sums `input.output.value`, places `input.outpoint` into the transaction inputs, and stores the supplied `TxOut`s as `prevouts`. [3](#0-2) [4](#0-3) [5](#0-4) 

The only key-related check is that the forged prevout's script equals the script derived from the group key plus the supplied offset; it does not verify that `outpoint` resolves to that exact `TxOut` on-chain. [6](#0-5) 

Signing commits to `Prevouts::All`, so the forged amount and script become part of each Taproot signature message. [7](#0-6) 

`TransactionSignatureMachine::complete` attaches the resulting signatures and returns the transaction without checking the UTXO set. [8](#0-7) 

### Impact Explanation
An attacker can report a nonexistent or mispriced UTXO as spendable Serai funds. The fabricated amount can satisfy `input_sat >= payment_sat + needed_fee`, produce payments or change that exceed real reserves, and drive the threshold signing flow to completion. [9](#0-8) 

If the outpoint is fabricated, the transaction is invalid because it spends a nonexistent input. If the outpoint exists but the supplied `TxOut.value` was altered, the transaction is still invalid because the Taproot sighash commits to the false prevout amount. [7](#0-6) 

This creates a concrete accounting/availability failure: funds represented as received and spendable cannot actually be spent, and scheduling or signing work based on those funds produces an unusable transaction. The closest permitted impact is “funds reported received that are not spendable.”

### Likelihood Explanation
Any party able to supply bytes to `ReceivedOutput::read` can perform the attack with public information. They need only know or reuse a Serai Taproot script and preserve the offset/script relationship while changing the amount or outpoint; `multisig` still accepts the input because it compares only the script against `key + offset * G`. [6](#0-5) 

No private key, validator role, miner capability, malformed curve point, or market manipulation is required. The exploit is prevented only if every caller guarantees that `ReceivedOutput` objects came from authenticated chain data before deserialization or use.

### Recommendation
Do not allow deserialized `ReceivedOutput` values to cross a trust boundary as authoritative UTXO state. Before constructing or signing a `SignableTransaction`, resolve each `OutPoint` against the confirmed chain and compare the full canonical `TxOut`—script and value—rather than trusting the serialized object.

A robust design would:

- Restrict `ReceivedOutput::read` to authenticated internal/database data.
- Re-scan the containing confirmed transaction or fetch the prevout by `OutPoint` before use.
- Reject any mismatch between the supplied `TxOut` and the canonical UTXO.
- Require `SignableTransaction::new` or `multisig` to receive verified prevouts, not merely self-describing `ReceivedOutput`s.
- Track whether the referenced transaction is confirmed, non-coinbase or mature, and still unspent.

### Proof of Concept
The attacker starts with a legitimate serialized output for a low-value UTXO controlled by the target key, preserves its zero offset and P2TR script, changes its encoded value to a large amount, and replaces its outpoint with either a nonexistent outpoint or another lower-value outpoint:

```rust
// `encoded` is a legitimate ReceivedOutput serialization:
// [32-byte offset][consensus TxOut][consensus OutPoint].
let mut encoded = legitimate_received_output.serialize();

// Patch the TxOut's amount and/or following OutPoint using the Bitcoin
// consensus encoding offsets.
patch_txout_value(&mut encoded, 10_000_000_000);
patch_outpoint(&mut encoded, fake_outpoint);

let forged =
  ReceivedOutput::read(&mut encoded.as_slice()).unwrap();

// The claimed balance is now attacker-controlled.
assert_eq!(forged.value(), 10_000_000_000);

// The payment and fee checks use the forged amount.
let tx = SignableTransaction::new(
  vec![forged],
  &[(attacker_or_destination_script, 5_000_000_000)],
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap();

// This succeeds whenever the preserved script equals the script for
// group_key + offset * G, including offset zero for the base key.
let machine = tx.clone().multisig(&keys).unwrap();
let signed_tx = run_threshold_signing(machine);

// `signed_tx` contains valid-looking signatures for a sighash committing
// to the forged prevout data, but Bitcoin consensus rejects it because
// the outpoint is nonexistent or its actual amount does not match the
// amount committed through Prevouts::All.
```
