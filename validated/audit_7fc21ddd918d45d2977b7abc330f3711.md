### Title
Coinbase outputs reported as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_block` iterates `block.txdata` including `txdata[0]` (the coinbase transaction) and passes every transaction to `scan_transaction`, which matches only `script_pubkey` against the registered scripts. A coinbase output paying to a scanned Taproot script produces a `ReceivedOutput` that is structurally indistinguishable from a normal confirmed payment — same type, no flag, same `value()`, `outpoint()`, and `offset()` accessors. This mirrors the reported bug class: a payment which must not yet be accepted (an immature coinbase, unspendable for 100 blocks under consensus rule `COINBASE_MATURITY`) ends with no error and produces the exact same observable result as a fully valid, spendable payment.

### Finding Description
- `scan_block` loops over all of `block.txdata` with no `tx.is_coinbase()` check: `for tx in &block.txdata { res.extend(self.scan_transaction(tx)); }` (`networks/bitcoin/src/wallet/mod.rs:221-227`).
- `scan_transaction` builds a `ReceivedOutput` purely from `script_pubkey` matching: `if let Some(offset) = self.scripts.get(&output.script_pubkey)` (`networks/bitcoin/src/wallet/mod.rs:199-214`). There is no maturity, coinbase, or spendability discriminator anywhere in `ReceivedOutput` (`networks/bitcoin/src/wallet/mod.rs:89-97`).
- A miner is an unprivileged external party; a coinbase transaction paying to any script is a Bitcoin transaction they send. Any miner can make a coinbase pay to Serai's scanned script and it will be reported as an ordinary received output.
- The code comments acknowledge the caveat ("bound by maturity… a post-processing pass is needed") but the function itself silently emits the immature output identically to a valid one — precisely the "failed vote ends with a normal-looking `VoteResult(0,0,0,0)`" pattern.

### Impact Explanation
The downstream accounting path treats `ReceivedOutput`s as received, spendable funds (they carry `offset` + `outpoint` for `SignableTransaction`/`multisig` consumption in `networks/bitcoin/src/wallet/send.rs`). If a coinbase output is credited and selected as an input, the resulting spend transaction is consensus-invalid for 100 blocks, so the funds are reported received yet are not spendable — matching the accepted impact class "funds reported received that are not spendable". Because the immature output is indistinguishable from a mature one, any consumer that does not itself re-check `tx.is_coinbase()` cannot tell the two cases apart, and a malicious miner can repeatedly feed immature outputs to inflate reported balances.

### Likelihood Explanation
Any miner on the Bitcoin network can include an output to the well-known Serai multisig script in their coinbase at negligible additional cost. Mining a block is non-trivial on mainnet, but the capability is entirely within an unprivileged party's reach (no validator status, no keys, no internal access required). Exploitation additionally requires the consumer to skip the documented maturity post-processing; the library itself provides no enforcement and emits the output silently.

### Recommendation
In `scan_block` (or `scan_transaction`), explicitly skip `block.txdata[0]` or check `tx.is_coinbase()` and exclude/flag those outputs — i.e., fail loudly or tag the result rather than returning an immature `ReceivedOutput` indistinguishable from a spendable one. If immature outputs must be surfaced for tracking, add a maturity/confirmations field to `ReceivedOutput` so the two cases are distinguishable, analogous to emitting a distinct `VoteFailed` event rather than a zero-valued `VoteResult`.

### Proof of Concept

```rust
// networks/bitcoin/src/wallet/mod.rs
// scan_block iterates every tx, including the coinbase:
for tx in &block.txdata {
  res.extend(self.scan_transaction(tx));

// output paying to our script — no maturity check anywhere:
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```
Concretely: a miner constructs a block whose coinbase contains `TxOut { script_pubkey: <serai p2tr script>, value: 6.25 BTC+fees }`. `scanner.scan_block(&block)` returns a `ReceivedOutput` with `offset == Scalar::ZERO`, a valid-looking `outpoint`, and the full coinbase `value()` — indistinguishable from a real deposit. Any attempt to spend it via `SignableTransaction::new`/`TransactionMachine` produces a transaction that every node rejects until block height +100, yet it was already reported and credited as received.

Caveat: I could not fully verify whether the in-scope callers in `processor/src/networks/bitcoin.rs` perform the documented coinbase post-processing pass before crediting outputs; if they do, the reachable impact is reduced to the library-level ambiguity rather than credited-unspendable funds. The library defect itself (silent indistinguishable emission of an invalid/unspendable result) is confirmed by the cited code.
