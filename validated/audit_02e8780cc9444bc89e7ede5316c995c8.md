## Summary

Reducing the external report to its core invariant: the audited token contract mixed unrelated concerns (balances, crowdfund, vesting, presale) behind one interface, so a single code path ended up doing several different jobs with different trust assumptions, which is exactly the shape of bug that hides authorization mistakes. The equivalent pattern exists in Hyperbridge's `IntentGatewayV2` cross-chain callback: `onAccept` is one entrypoint that handles both **escrow settlement** (`RedeemEscrow`/`RefundEscrow`) and **governance/admin** actions (`NewDeployment`, `UpdateParams`, `SweepDust`, `UpgradeContract`), and the two classes of action are authenticated with different, inconsistent strength.

### Title
Governance-class `onAccept` actions on `IntentGatewayV2` are authorized only at chain level (`request.source`), not by sender module identity (`request.from`) - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Finding Description
`ExtrinsicIntents.onAccept` dispatches on `RequestKind` decoded from the incoming ISMP `PostRequest` body: [1](#0-0) 

For `RedeemEscrow`/`RefundEscrow` it calls `_authenticate`, which checks that `request.from` (the specific 20-byte module address) equals the registered peer `IntentGatewayV2` instance for `request.source`: [2](#0-1) 

But for the far more privileged actions — `NewDeployment`, `UpdateParams`, `SweepDust`, and `UpgradeContract` (an arbitrary ERC-1967 implementation swap with attacker-controlled `initData`) — the *only* check is:

```
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
```

This validates that the request originated from the **Hyperbridge chain**, but never checks `request.from` — i.e., it does not verify which pallet/module *on* Hyperbridge dispatched the message. The same pattern is duplicated in `SimplexPaymaster.onAccept`, whose test suite confirms the check is purely chain-level (`testOnAcceptRejectsNonHyperbridgeSource` only asserts on `source`, not `from`): [3](#0-2) 

Hyperbridge's own architecture routes many independent pallets through the same generic `IsmpDispatcher::dispatch_request`, each free to set `from` to its own module id and `to`/`body` to arbitrary values. The repo's own `pallet-ismp-demo` shows this pattern concretely — any signed account can call `dispatch_to_evm` to send a `PostRequest` with `source = host_state_machine()` (Hyperbridge itself) to **any** EVM address: [4](#0-3) 

In the current demo pallet the body is hardcoded to `b"Hello from polkadot"`, so it cannot itself be shaped into a valid `RequestKind` payload — this specific pallet is not directly weaponizable today. But it proves the general capability exists on Hyperbridge: any pallet that lets a user control the outgoing `body` and `to` fields (which is the norm for the coprocessor pattern used by host-executive, intents-coprocessor, token-governor, and future modules per `docs/outbound-request-incentivization.md`) can produce a `PostRequest` with `source == hyperbridge` that `IntentGatewayV2`/`SimplexPaymaster` will treat as fully governance-authenticated, since `from` is never checked for these `RequestKind`s.

### Impact Explanation
If any additional or future Hyperbridge-side pallet exposes a permissionless (or lower-privilege) path to dispatch an ISMP `PostRequest` with attacker-chosen `to` and `body` bytes, an unprivileged caller could forge:
- `UpgradeContract` → replace the `IntentGatewayV2`/`SimplexPaymaster` implementation with an attacker contract (full fund drain of all escrowed intent inputs / paymaster token balances).
- `SweepDust` / `WithdrawAssets` → steal protocol dust or paymaster treasury balances to an attacker address.
- `UpdateParams` → change `dispatcher`, `priceOracle`, fee parameters to attacker-controlled values, enabling further exploitation.

This is exactly the "cross-chain admin or host-management effects... reachable through... wrong module bindings or unauthenticated message flow" class called out as in-scope.

### Likelihood Explanation
Medium-to-low as currently instantiated: I could not find a currently-shipped pallet on Hyperbridge whose `body` bytes a normal user can freely set while dispatching to an arbitrary `to` address (the `pallet-ismp-demo` body is fixed, and the intended governance dispatcher — the intents-coprocessor pallet — is presumably origin-gated). However, the vulnerability is a real code-level authorization gap independent of that: the destination contracts trust "any request whose `source` is the Hyperbridge chain" for their highest-privilege operations, rather than binding governance actions to the specific, intended module identity (`from`), the same way `_authenticate` correctly does for settlement messages. This is a latent privilege-escalation surface that only requires *one* future or overlooked pallet on Hyperbridge with a user-influenced dispatch body to become fully exploitable, with no relayer, prover, or admin compromise needed — only a permissionless extrinsic on Hyperbridge.

### Recommendation
Require both `request.source == hyperbridge` **and** `request.from == <the one governance module id, e.g. the intents-coprocessor pallet's module id>` for all governance-class `RequestKind`s in `ExtrinsicIntents.onAccept` and `SimplexPaymaster.onAccept`, mirroring the stricter binding already used by `_authenticate` for settlement messages. Do not rely on chain-level trust alone for high-privilege actions.

### Proof of Concept
Conceptual (cannot be fully weaponized against the exact `pallet-ismp-demo` shipped today because its body is hardcoded, but the destination-side gap is directly reproducible):
1. Identify any Hyperbridge-side call (present or future) that lets a signed account invoke `IsmpDispatcher::dispatch_request` with `from` set to that caller's own module id, and with attacker-controlled `to`/`body`.
2. Set `to = <IntentGatewayV2 address on target EVM chain>`, `body = bytes1(uint8(RequestKind.UpgradeContract)) || abi.encode(attackerImpl, initData)`.
3. Dispatch to the target EVM chain; `source` naturally equals `host_state_machine()` since the dispatch originates on Hyperbridge.
4. On delivery, `ExtrinsicIntents.onAccept` decodes `kind == UpgradeContract`, checks only `keccak256(request.source) == keccak256(hyperbridge)` (true), and calls `ERC1967Utils.upgradeToAndCall(attackerImpl, initData)` — full contract takeover, without ever validating that the *specific* Hyperbridge module authorized to perform governance actually sent the message.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.UpgradeContract) {
            (address newImpl, bytes memory initData) = abi.decode(incoming.request.body[1:], (address, bytes));
            ERC1967Utils.upgradeToAndCall(newImpl, initData);
        }
    }
