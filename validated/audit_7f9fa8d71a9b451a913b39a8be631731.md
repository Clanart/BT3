### Title
Anyone can send Bitcoin to the deterministic Branch/Change/Forwarded offset addresses, causing deposits to be miscategorized as internal outputs and their instruction data discarded - (File: processor/src/networks/bitcoin.rs)

### Summary
The Serai Bitcoin scanner classifies every received output purely by which registered script_pubkey it matches (`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs:199-214`), mapping the matched offset back to an `OutputType` via `kinds[offset_repr_ref]` in `processor/src/networks/bitcoin.rs:686-700`. The Branch, Change, and Forwarded offsets are deterministically derived with `Secp256k1::hash_to_F(KEY_DST, b"branch" | b"change" | b"forward")` (`processor/src/networks/bitcoin.rs:333-344`), so any unprivileged party can compute these P2TR addresses and pay to them. Serai mirrors the Tokemak bug class: a permissionless on-chain action pushes value into a protocol-controlled destination through a path that bypasses the intended accounting flow — exactly like calling `getReward()` directly instead of `collectRewards()`, sending to these addresses bypasses the `External` deposit flow.

### Finding Description
`get_outputs` reconstructs the full `Scanner` for a key, scans every non-coinbase transaction, and assigns each matched output a `kind` from its offset (`processor/src/networks/bitcoin.rs:686-700`). Crucially, the Serai instruction data extracted via `extract_serai_data` is only attached when `output.kind == OutputType::External` (`processor/src/networks/bitcoin.rs:730-735`):

```rust
for output in &mut outputs {
  if output.kind == OutputType::External {
    output.data.clone_from(&data);
  }
  output.presumed_origin.clone_from(&presumed_origin);
}
```

The offset constants are derived solely from the public group key plus public domain-separated hashes (`KEY_DST = b"Serai Bitcoin Output Offset"`, `processor/src/networks/bitcoin.rs:308-344`). `branch_address`, `change_address`, and `forward_address` are plain point additions of these public scalars (`processor/src/networks/bitcoin.rs:661-673`), so an attacker — or merely a mistaken user — can send BTC directly to them. Because Bitcoin pays to script_pubkeys and `Scanner` matches on script_pubkey alone (`networks/bitcoin/src/wallet/mod.rs:205`), there is no way to distinguish "our own change/forward output" from "a third party's payment to the same script".

Two consequences follow:

1. **Lost attribution**: a transaction paying to the Branch/Change/Forwarded address that also carries an `InInstruction` produces an output with `kind != External`, so `data` is left empty. The deposit is scanned, emitted as a `ScannerEvent::Block` output, and treated as an internal protocol output rather than a user deposit — the value is received but never creditable to a depositor.
2. **Polluted internal accounting**: Branch/Change/Forwarded outputs are intended to be created only by Serai's own `SignableTransaction`s (change is generated inside `SignableTransaction::new` with `Some(change_addr)`). An attacker who pays these addresses injects outputs the scheduler will later consume as if they were protocol-internal funds, mixing unsolicited satoshis into fee/change math and forcing aggregation of outputs the protocol never intended to exist — the same "untracked tokens sitting in the vault" shape as the Tokemak report.

### Impact Explanation
Funds sent to any of the three deterministic offset addresses are spendable by the multisig (the offset scalar is known), but they are permanently misclassified at scan time: their `InInstruction`/memo data is dropped, they are not reported as `External` deposits, and downstream crediting logic never sees the sender's intent. A user depositing to the `forward_address` (which is publicly derivable and could plausibly be leaked/phished as a "deposit address") loses attribution of their funds — the analog of Tokemak's rewards landing in the vault with no path through `liquidateVaultsForToken()`/`feeReceiver`. Additionally, injected fake Change/Branch outputs inflate the multisig's UTXO set and distort `median_fee`/`needed_fee`/change calculations the next time `SignableTransaction` is constructed.

### Likelihood Explanation
Reachable by any unprivileged party sending a Bitcoin transaction — the addresses are deterministic functions of the public group key and a fixed domain separator, requiring no leaked secrets. User error (sending to a previously exposed forward address) is plausible on its own; a deliberate griefer can also generate arbitrary amounts of misclassified outputs, bounded only by the ≥10,000 sat `DUST` filter (`processor/src/networks/bitcoin.rs:638`). Severity is Medium: funds are not directly stolen (the multisig can technically spend them via the offset key), but attribution is irreversibly lost at scan time and internal accounting is polluted.

### Recommendation
Distinguish first-party from third-party payments at scan/acknowledgment time rather than by script_pubkey alone. Options:
- Treat any output paying to a Branch/Change/Forwarded script that arrives in a transaction Serai did not construct (i.e., not matching a pending `SignableTransaction` txid) as `External`-like, preserving `extract_serai_data` on it so a misdirected deposit can still be credited or refunded.
- Track expected change/branch outpoints when `SignableTransaction`s are broadcast, and only classify scanned outputs as Change/Branch if they match a recorded expected outpoint; report unmatched ones with their data attached.
- At minimum, attach `data` to all matched outputs, not just `OutputType::External`, so misclassified deposits retain their instruction.
