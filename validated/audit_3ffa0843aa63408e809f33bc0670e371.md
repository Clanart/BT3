### Title
Use-after-free of Python message-map value wrapper after `MergeFrom`/`MergeFromString` overwrites a colliding map key — (File: `python/google/protobuf/pyext/message.cc`)

### Summary
The TensorFlow report describes a UAF where `png::CommonFreeDecode(&decode)` frees decoder state, after which the code keeps reading `decode.width`/`decode.height` from the now-invalid struct. The invariant that fails is: **an object is deallocated as a side effect of processing attacker-controlled input, while a live reference to that object is used afterward.**

In the Protobuf C++/Python binding (`pyext`), the exact same invariant fails for message-valued `map<K, Message>` fields. When a client calls `MergeFrom()` / `MergeFromString()` on a message that already exposes a Python wrapper (`CMessage`) for a map value, and the incoming (attacker-controlled) serialized data contains an entry with the **same map key**, the underlying C++ `Message` object backing that map entry is deleted and replaced, but the live Python `CMessage` wrapper object that a caller is holding is not detached/invalidated first. The wrapper's raw pointer becomes dangling, exactly as `decode.width`/`decode.height` become stale after `CommonFreeDecode`.

This is a documented, currently open gap: the repository already fixed the analogous class of bug for `oneof` fields (via `MaybeReleaseOneofBeforeMerge` / `FixupMessageAfterMerge`), but the fix is explicitly scoped to exclude repeated/map fields.

### Finding Description
`MaybeReleaseOneofBeforeMerge` in `python/google/protobuf/pyext/message.cc` walks `self->composite_fields` (the map of live Python wrapper objects for sub-messages) and detaches/releases any wrapper whose backing oneof member is about to be destroyed during a merge: [1](#0-0) 

Critically, the predicate explicitly skips repeated fields — which includes map fields, since map entries are modeled as a repeated message field internally: [2](#0-1) 

The comment says: *"For normal repeated message, MergeFrom will append the messages. For message map with same keys, it is overwrite"* — i.e., the author is aware maps get overwritten in-place but does not extend the release/detach protection there.

`MergeFromStringImpl` (used by both `MergeFromString` and `ParseFromString`) parses attacker-controlled bytes directly into the destination message (or a temp message that is then `MergeFrom`'d), and only calls `MaybeReleaseOneofBeforeMerge`/`FixupMessageAfterMerge` — the mechanism that protects oneof wrappers, not map wrappers: [3](#0-2) [4](#0-3) 

The gap is directly confirmed by the project's own regression test, which documents that for the C++ backend, merging into a message-valued map with a colliding key **deallocates the underlying C++ message while a live Python reference to it still exists**, and the assertion exercising this is skipped specifically because it segfaults under the C++ implementation: [5](#0-4) 

Compare this to the `oneof` case, where an almost identical scenario (`testOneofSwitchMergeUAF`) is asserted to be **fixed** and safe precisely because of `MaybeReleaseOneofBeforeMerge`: [6](#0-5) 

So the exact same UAF bug class that was identified and fixed for `oneof` fields remains open for message-valued map fields, which are excluded by design (`!descriptor->is_repeated()` at line 777 above) from the very protection mechanism built to prevent this.

### Impact Explanation
Attacker-controlled, bounded ProtoBinary input sent to a public parse API (`MergeFromString`/`ParseFromString`/`MergeFrom`) on the `cpp` implementation of the Python protobuf bindings can cause a C++ object backing a Python-visible map value to be freed while a Python-level reference to it is retained by application code (e.g., a variable holding `msg.some_map[key]` before re-parsing/merging new data into `msg`). Subsequent access of that Python object dereferences freed memory — a classic UAF with the same disclosure/corruption potential (CWE-416) as the TensorFlow report: reading stale/freed data (as with `decode.width`/`decode.height`), or a crash (as the test comment states, "likely to cause a segmentation fault"), and depending on heap reuse, a memory-corruption/type-confusion primitive exploitable for information disclosure or worse. This matches the consuming-application exposure model in the rules: any server-side Python application using `google.protobuf` with the C++ backend that parses attacker-supplied bytes into a message containing message-valued maps, while holding Python references to prior map values, is exposed.

### Likelihood Explanation
Moderate-to-high. The trigger requires: (1) the C++ (`cpp`) implementation of `google.protobuf` for Python (the default/fastest backend in most deployments), (2) a proto schema with a `map<K, Message>` field, and (3) application code that retains a Python reference to a map value across a `MergeFrom`/`MergeFromString`/`ParseFromString` call with attacker-controlled bytes containing a colliding key. This is a common and natural coding pattern (cache a submessage from a map, then merge new/updated data into the parent message), and requires no privileged access or malicious schema — only bounded, well-formed protobuf bytes through the public parse API. The maintainers' own test explicitly flags and works around this exact scenario for the `cpp` backend, indicating it is a known, reproducible, currently-unfixed condition rather than a theoretical one.

### Recommendation
Extend the UAF-prevention mechanism already implemented for `oneof` fields (`MaybeReleaseOneofBeforeMerge` / `InternalReleaseFieldByDescriptor` / `FixupMessageAfterMerge`) to cover message-valued map fields when a merge would overwrite an existing key:
- Before performing the C++ `Message::MergeFrom` (or the internal map merge) for message-valued map fields, detect keys present in both `self` and the incoming message where a live Python wrapper exists in `composite_fields`/child map value cache, and detach/release those wrappers (copy out their current value into the wrapper, similar to `InternalReleaseFieldByDescriptor`) before the underlying C++ entry is destroyed and replaced.
- After the merge, run an equivalent of `FixupMessageAfterMerge` for map containers so previously-read-only wrappers are repointed to the new backing storage instead of being left dangling.
- Add/enable the currently-skipped assertion in `testMergeFrom` (`python/google/protobuf/internal/message_test.py:3153-3161`) for the `cpp` implementation as a regression test once fixed.

### Proof of Concept

```python
msg.map_int32_foreign_message[222].c = 5

msg2 = map_unittest_pb2.TestMap()

msg2.map_int32_foreign_message[222].d = 20

# "attacker" input containing an overlapping map key 222 for msg2's field

msg2.MergeFromString(attacker_bytes)   # or msg2.MergeFrom(msg)
```

```text
int MaybeReleaseOneofBeforeMerge(CMessage* self, const Message& other) {
  CMessage::CompositeFieldsMap* composite_fields =
      self->composite_fields.TryGet();
  if (!composite_fields) {
    return 0;
  }

  Message* message = AssureWritable(self);
  if (message == nullptr) return -1;
  const Reflection* reflection = message->GetReflection();
  PyMessageFactory* factory = GetFactoryForMessage(self);
  std::vector<const FieldDescriptor*> fields_to_release;
  std::vector<std::pair<const FieldDescriptor*, ScopedPyObjectPtr>>
      nested_message_fields;
  composite_fields->ForEach([&](const void* key, PyObject* value) {
    const FieldDescriptor* descriptor =
        reinterpret_cast<const FieldDescriptor*>(key);
    if (descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE &&
        // For normal repeated message, MergeFrom will append the messages.
        // For message map with same keys, it is overwrite
        !descriptor->is_repeated() &&
        reflection->HasField(*message, descriptor)) {
      if (reflection->HasField(other, descriptor)) {
        Py_INCREF(value);
        nested_message_fields.emplace_back(descriptor, value);
      } else {
        // Release oneof message if the other message has set a different oneof
        const OneofDescriptor* oneof = descriptor->containing_oneof();
        if (oneof && reflection->HasOneof(other, oneof)) {
          fields_to_release.push_back(descriptor);
        }
      }
    }
  });
```

```text
static PyObject* MergeFromStringImpl(CMessage* self, PyObject* arg,
                                     bool is_cleared) {
  Py_buffer data;
  if (PyObject_GetBuffer(arg, &data, PyBUF_SIMPLE) < 0) {
    return nullptr;
  }
  auto cleanup_data = absl::MakeCleanup([&data] { PyBuffer_Release(&data); });

  Message* message = AssureWritable(self);
  if (message == nullptr) {
    return nullptr;
  }

  // We parse into a temporary message first to detect oneof switches before
  // modifying the target message. This allows us to release the wrappers
  // for switching oneof fields in the target message before they are deleted
  // by C++ during the merge, preventing use-after-free bugs.
  // We use heap allocation (nullptr arena) for the temporary message so that
  // it is collected immediately after the merge, avoiding wasting arena memory.
  std::unique_ptr<Message> temp_message;
  Message* merge_dst;

  if (is_cleared) {
    // Check that it is really empty.
    ABSL_DCHECK_EQ(message->ByteSizeLong(), 0);
    merge_dst = message;
  } else {
    temp_message.reset(message->New(nullptr));
    merge_dst = temp_message.get();
  }

  PyMessageFactory* factory = GetFactoryForMessage(self);
  int depth = allow_oversize_protos
                  ? INT_MAX
                  : io::CodedInputStream::GetDefaultRecursionLimit();
  const char* ptr;
  internal::ParseContext ctx(
      depth, false, &ptr,
      absl::string_view(static_cast<const char*>(data.buf), data.len));

  ctx.data().pool = factory->pool->pool->get();
  ctx.data().factory = factory->message_factory;

  ptr = merge_dst->_InternalParse(ptr, &ctx);

  if (is_cleared) {
    // If we merged into the final destination, fix up now before we might have
    // an early exit.
    FixupMessageAfterMerge(self);
  }

  // Python makes distinction in error message, between a general parse failure
  // and in-correct ending on a terminating tag. Hence we need to be a bit more
  // explicit in our correctness checks.
  if (ptr == nullptr) {
    PyErr_Format(
        DecodeError_class, "Error parsing message with type '%s'",
        std::string(self->GetMessageClass()->message_descriptor->full_name())
            .c_str());
    return nullptr;
  }
  if (ctx.BytesUntilLimit(ptr) < 0) {
    // The parser overshot the limit.
    PyErr_Format(
        DecodeError_class,
        "Error parsing message as the message exceeded the protobuf limit "
        "with type '%s'",
        std::string(self->GetMessageClass()->message_descriptor->full_name())
            .c_str());
    return nullptr;
  }
  // ctx has an explicit limit set (length of string_view), so we have to
  // check we ended at that limit.
  if (!ctx.EndedAtLimit()) {
    PyErr_Format(DecodeError_class,
                 "Unexpected end-group tag: Not all data was converted");
    return nullptr;
  }

  if (!is_cleared) {
    // If we are doing a real merge, fix oneofs, merge the object, then do
    // after-merge fixup.

    if (MaybeReleaseOneofBeforeMerge(self, *temp_message) < 0) {
      return nullptr;
    }

    message->MergeFrom(*temp_message);

    // Child message might be lazily created before MergeFrom. Make sure they
    // are mutable at this point if child messages are really created.
    FixupMessageAfterMerge(self);
  }
```
