### Title
Attacker-Controlled `WWW-Authenticate` Header Spoofs GitHub Host Classification, Triggering GitHub OAuth Sign-In for Arbitrary Git Remote and Leaking Real GitHub Tokens - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
The upstream report describes an interface/invariant mismatch between `PendlePowerManager` and `PendleRouterV3` where an untrusted/changed external call breaks an internal assumption. The equivalent broken invariant in GitHub Desktop is: **the credential helper trusts an attacker-controlled HTTP response field (`WWW-Authenticate`) to decide whether a completely arbitrary git remote is a "GitHub" host**, and then feeds that classification into the OAuth sign-in flow that ultimately hands out the user's real GitHub token for that remote.

### Finding Description
When Git performs HTTP authentication, it forwards captured `WWW-Authenticate` response headers to the credential helper as `wwwauth[]` fields. `getEndpointKind()` uses this attacker-controlled data as a shortcut to decide if a host is GitHub-owned: [1](#0-0) 

If a malicious or compromised git server (any `http(s)://` remote the user clones/fetches/pushes to) returns a response containing `WWW-Authenticate: ... realm="GitHub" ...`, this function returns `'enterprise'` for a host that has no relationship to GitHub whatsoever. That classification then flows into `getCredential()`: [2](#0-1) 

Since `endpointKind !== 'generic'` and no existing account matches the attacker's `apiEndpoint`, Desktop calls `ui.promptForGitHubSignIn(endpoint)` with the attacker's own URL as the sign-in endpoint. This routes into a real GitHub OAuth device/browser flow: [3](#0-2) 

The resulting `Account` — containing the user's genuine GitHub OAuth token — is then bound via `credWithAccount` and returned as the git credential for the attacker's host: [4](#0-3) 

Crucially, this new account gets persisted with `endpoint` set to the attacker's own origin (not `github.com`/a real GHE instance). On any subsequent git operation against that same attacker remote, `findGitHubTrampolineAccount()` will match it purely by origin comparison and hand back the same real token without any further prompt: [5](#0-4) 

### Impact Explanation
The corrupted value is the **endpoint-kind classification and the resulting persisted `Account.endpoint` binding** — a value that should only ever be `github.com` or a genuinely verified GitHub Enterprise host, but instead becomes attacker-controlled via response header spoofing. Once bound, the user's real, long-lived GitHub OAuth token is transmitted to the attacker's server as Basic-Auth credentials on every future git operation against that remote, and the token is persisted in the OS credential store associated with that attacker endpoint. This is a genuine credential/token exfiltration path: unprivileged, remote-triggerable by any server the user's remote points at (self-hosted git server, forge behind a proxy, compromised mirror), and requires no local access, malware, or leaked secrets — only that the user perform an ordinary fetch/push/clone against that server and complete what looks like a legitimate "Sign in to GitHub" flow (the UI shows the attacker's raw endpoint URL, which is easy to overlook for typosquatted or unfamiliar internal-looking domains).

### Likelihood Explanation
Exploitation requires only that the attacker control the HTTP server backing a git remote the victim adds (a common scenario: internal proxies, malicious forks distributed with a custom remote, or compromised self-hosted Git servers). The header-based shortcut exists specifically "to avoid making a request ourselves" (per the code comment), which means the app deliberately trusts server-supplied data for a security-relevant classification, and there is no independent verification (e.g., confirming the host is actually `*.github.com` or querying the real GitHub API) before triggering the sign-in flow and reusing tokens for that origin. The only mitigating factor is the visible sign-in prompt — but the endpoint text is a URL that most users, especially on internal/vanity domains, do not scrutinize as a phishing signal.

### Recommendation
1. Do not treat the `wwwauth[]`-derived `'enterprise'` classification as sufficient to trigger OAuth sign-in without cross-checking against `isGitHubHost(endpoint)` (an actual network-based verification), rather than relying solely on the response header content.
2. Before persisting or reusing an `Account` for a non-github.com endpoint, require it to have passed real host verification (e.g., a documented GitHub Enterprise Server ping/metadata check) rather than trusting the credential's declared `apiEndpoint`.
3. Surface a clear, hard-to-miss warning in the sign-in dialog when the endpoint was inferred from a server-supplied header rather than user input or verified discovery, so users can recognize spoofing attempts.

### Proof of Concept
1. Stand up an HTTP git server at `https://evil.example.com/repo.git` that, on an authentication challenge, responds with header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, add/clone this remote and perform a `fetch`/`push` that triggers credential lookup.
3. `getEndpointKind()` scans the forwarded `wwwauth[]` value, matches `realm="GitHub"`, and returns `'enterprise'` [6](#0-5) .
4. `getCredential()` sees no existing account bound to `evil.example.com` and calls `ui.promptForGitHubSignIn('https://evil.example.com/repo.git')` [7](#0-6) .
5. The victim, believing this is a legitimate GitHub Enterprise sign-in prompt, completes real GitHub OAuth. The resulting `Account` (with genuine token) is bound to `evil.example.com`'s origin.
6. `credWithAccount` returns this token as the git password for `evil.example.com`, so Desktop performs the push/fetch while sending `Authorization: Basic <login>:<real-token>` to the attacker's server [4](#0-3) .
7. Every subsequent operation against `evil.example.com` silently reuses the same real token via `findGitHubTrampolineAccount` origin matching [5](#0-4) , exfiltrating the credential on every future git call.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
