### Title
Non-atomic checkout-then-submodule-update lets a malicious cloned/fetched repository leave the working tree in a silently mismatched state - ([File: app/src/lib/git/checkout.ts])

### Summary
The Sherlock report's broken invariant is: a sequence of operations that the protocol *treats* as atomic (`approve` + `issue`/`revoke`) is actually executed as two independent steps at the message layer, and an attacker who controls execution conditions (gas) can force only the first step to succeed, leaving state (assets vs. shares) permanently out of sync while the caller believes the whole operation completed. The Desktop analog is `checkoutBranch()` / `checkoutCommit()` in [1](#0-0) , which performs `git checkout` and then, as a *separate, subsequent* async git invocation, `updateSubmodulesAfterOperation()` (`git submodule update --init --recursive`). These two git calls are not wrapped in any transaction/rollback and there is no verification step tying the outcome of the second call back to the first.

### Finding Description
`checkoutBranch` first runs the top-level `git checkout` [2](#0-1) , which updates HEAD/index/working tree for the parent repository, and only afterward invokes `updateSubmodulesAfterOperation` [3](#0-2) , which shells out to `git submodule update --init --recursive` [4](#0-3) . `checkoutCommit` has the identical two-step pattern [5](#0-4) .

Because a repository's `.gitmodules` and submodule commit pointers are attacker-controlled content (they are cloned/fetched from a remote or checked out from a branch an attacker contributed to), the second step can be made to fail independently of the first: a submodule URL pointing at an unreachable host, a nonexistent recorded submodule commit, an auth-requiring host that trips `AuthenticationErrors`, or a huge/slow submodule causing the invocation to error out. In every such case `git checkout` for the top-level repository has already committed its effects (HEAD moved, index updated, top-level working-tree files rewritten) before `updateSubmodulesAfterOperation` throws. The caller only sees a single rejected promise from `checkoutBranch`/`checkoutCommit` and typically surfaces it as one generic checkout error, with no state reconciliation back to the pre-checkout branch/commit.

This is structurally the same defect pattern as the report: two operations that must be observed as a unit (checkout of parent tree + checkout of submodule content it references) are executed as two independently-failable steps, and the content that decides whether step two succeeds or fails (`.gitmodules`, submodule SHAs, submodule remote reachability) is attacker-supplied. Nothing in `checkoutBranch`/`checkoutCommit` guards against, detects, or rolls back this partial completion — there's no "gas requirement" or pre-flight validation that submodules will resolve before committing to the top-level checkout.

### Impact Explanation
After a partial failure, the repository is left with HEAD/index pointing at the new branch/commit while one or more submodule working directories are stale, uninitialized, or partially checked out — a state Desktop's UI does not distinguish from a fully-successful checkout beyond a raised error toast. Because the top-level index entries (gitlinks) for submodules come from the tree being checked out and are not altered by whether the submodule content actually materialized, a user who is unaware of the partial failure and proceeds to stage/commit/push unrelated changes will do so on top of an index that already contains submodule pointer values they never had a chance to inspect (the submodule working copy that would let them review the actual diff never got checked out). This matches the "silent corruption of what the user commits or pushes" impact class: the user's mental model of "what's in my working tree/what I'm about to commit" is wrong, and Desktop provides no atomic guarantee or reconciliation to prevent it.

### Likelihood Explanation
Any repository the user clones, adds as a remote, or merges/pulls from can define `.gitmodules` entries with unreachable, slow, or invalid submodule references — this requires no special privilege beyond being able to get the user to check out a branch/commit containing that content (a normal, expected Desktop workflow). No local access, admin rights, or pre-existing compromise is required; the trigger is purely attacker-controlled repository content combined with normal use of `checkoutBranch`/`checkoutCommit`.

### Recommendation
- Treat checkout + submodule update as a single failable unit: if `updateSubmodulesAfterOperation` throws, surface a distinct, explicit warning that the top-level checkout succeeded but submodules are inconsistent, rather than a single opaque error.
- Consider validating/pre-fetching submodule reachability before the top-level `git checkout` is allowed to complete, or offering an automatic rollback (`git checkout <previous-ref>`) when submodule initialization fails.
- Surface submodule-update failures distinctly in the UI so users are not left believing a checkout fully succeeded when it did not.

### Proof of Concept
1. Attacker creates/publishes a repository with a branch `feature` whose `.gitmodules` references a submodule pointing to an unreachable URL (e.g., `https://nonexistent.invalid/x.git`) or to a valid URL but a submodule commit SHA that has been rewritten/force-pushed away so it no longer exists.
2. Victim adds/clones this repository (or fetches this branch) in GitHub Desktop and checks out `feature` via `checkoutBranch` (`app/src/lib/git/checkout.ts:102-145`).
3. `git checkout` succeeds — HEAD, index, and top-level working tree now reflect `feature` — before `updateSubmodulesAfterOperation` is invoked and fails on the unreachable/invalid submodule (`app/src/lib/git/submodule.ts:29-55`).
4. Desktop surfaces a single checkout error; the user is now on `feature` with a partially-initialized/stale submodule tree and no reconciliation step, and can proceed to stage and commit/push further changes without ever having reviewed the submodule content tied to the gitlink already present in the index.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
