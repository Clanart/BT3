### Title
Attacker-controlled `n` in `ThresholdKeys::read` causes amplified memory allocation DoS - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` deserializes an attacker-controlled 16-bit participant count `n` and immediately performs `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector before reading/validating a single scalar. A ~10-byte input therefore forces allocation of ~2 MiB (`65535 × 32` bytes for a 256-bit field), giving a large memory-amplification DoS analogous to the crafted-input memory exhaustion in CVE-2020-22679.

`n` comes straight from `u16::from_le_bytes` on the input stream ( [2](#0-1) ), so an attacker can set `n = 0xFFFF`. `Vec::with_capacity(65535)` then eagerly allocates capacity for 65535 field elements before `read_F` is ever called. Even though the subsequent read loop will fail on a short input, the backing allocation has already been committed. The same untrusted `n` then drives the verification-share map loop ( [3](#0-2) ) — a `HashMap` populated one `read_G` at a time — but the up-front `with_capacity` reserve means no input bytes are needed at all to trigger the ~2 MiB allocation per call.

Additionally, `ThresholdParams::new(t, n, i)` is only validated *after* the allocation and coefficient reads, so `t`/`n` sanity checks cannot gate the allocation.

### Impact Explanation
An unprivileged party who can feed crafted bytes to `ThresholdKeys::read` (listed as a reachable deserialization surface) can force roughly `n × size_of::<C::F>()` bytes of heap allocation per invocation with only a handful of input bytes — an ~4,000× memory amplification. Repeated calls exhaust available memory and deny service (allocation failure / OOM kill), matching the medium-severity DoS impact class of the reference CVE. Since deserialization itself is stateless, the attacker needs no key material or protocol role.

### Likelihood Explanation
The trigger requires only the 4-byte ID length, curve ID bytes, two `u16`s, a participant `u16`, and the interpolation byte `0` — trivially crafted. Anywhere `ThresholdKeys` bytes are accepted from a peer or from untrusted storage, the path is reachable in a single call. The allocation is unconditional and precedes all semantic validation, so no valid-protocol behavior is required.

### Recommendation
Cap `n` before allocating: parse `t, n, i` and immediately construct/validate `ThresholdParams` (rejecting `t > n` and bounding `n` to a sane maximum), and avoid `Vec::with_capacity(n)` on untrusted input — push into an empty `Vec` so memory grows only as bytes are actually consumed. The same pattern should be checked anywhere else a length field is used to pre-size a container.
