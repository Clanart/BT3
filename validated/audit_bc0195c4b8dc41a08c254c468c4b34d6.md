Confirmed vulnerable analog: `on_timeout` (and `on_accept`) in the `hyper-fungible-token` pallet look up `ContractToAsset::<T>::get(dest, &to)` and `Precisions::<T>::get(local_asset_id, dest)`, both of which `update_token`'s `remove_chains` path deletes with no check for outstanding escrowed/in-flight transfers to that chain [1](#0-0) .

### Title
`update_token` chain removal permanently strands escrowed native assets when in-flight transfers time out - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::update_token`'s `remove_chains` branch deletes `TokenContracts`/`ContractToAsset`/`Precisions` for a `(asset, chain)` pair immediately, with no check that there are no outbound `send()` transfers still in flight (escrowed in `pallet_account()`, dispatched but not yet timed out) to that chain. This is the direct analog of the `MarinateV2` bug: removing an approved token/route without verifying the contract's custody balance is fully settled first.

### Finding Description
`send()` escrows/burns funds and dispatches a cross-chain `Send` message keyed to `(dest, to=token_contract)` [2](#0-1) . If that message times out, `on_timeout` recovers the refund path purely from on-chain lookups: `ContractToAsset::<T>::get(dest, &to)` to find `local_asset_id`, then `Precisions::<T>::get(local_asset_id, dest)` to get `erc_decimals` for the amount conversion [3](#0-2) . Both lookups return `HftError::UnknownContractOnTimeout` / `HftError::DecimalsNotConfigured` if missing, aborting the refund.

`update_token`'s `remove_chains` loop unconditionally removes exactly these entries — `ContractToAsset::remove(chain, old_contract)`, `TokenContracts::remove`, and `Precisions::remove` — for any governance-supplied chain, with no check of pending dispatches or the pallet's escrowed balance for that route [1](#0-0) . `CreateOrigin` is a privileged/governance origin, but the resulting fund-loss condition is identical in shape to the reported bug class: state is stripped from a still-in-use route while custody balance is nonzero, and no invariant check (`ensure!(no pending sends for this chain)` or "balance == 0") exists to block it, unlike the fix applied elsewhere in this same codebase for `EvmHost.updateHostParamsInternal`, which explicitly reverts with `CannotChangeFeeToken` if the old fee token still has a nonzero balance before changing it [4](#0-3) . This pallet has no equivalent guard.

### Impact Explanation
If a chain/asset route is removed (deliberately, or via a config mistake/migration) while any `send()` requests are still un-timed-out in flight to that `(chain, asset)` pair, the eventual `on_timeout` refund permanently fails with `UnknownContractOnTimeout`/`DecimalsNotConfigured`. Because ISMP timeout processing typically retries a failed handler, and this failure is deterministic (the mapping is gone, not transient), the refund can never succeed unless an operator re-registers the exact same `(chain, contract, decimals)` tuple, which conflicts with the intent of removal. The user's escrowed native/local-asset funds held in `pallet_account()` become permanently unrecoverable through the normal on_timeout path — a direct loss/lock of user funds, matching the "unrecoverable balances after token removal" bug class from the report.

### Likelihood Explanation
This requires only an ordinary operational sequence: a `send()` in flight to a chain, followed by a `CreateOrigin` call to `update_token` removing that chain before the timeout fires (or before the message is ever delivered/timed out). No malicious relayer, prover, or attacker is needed — it is a straightforward config-change race that any operator/governance process can trigger unintentionally, since nothing in `update_token` warns about or blocks in-flight/escrowed balances. The likelihood of hitting this in production increases whenever chain configs are updated for redeployments/migrations while cross-chain sends are outstanding.

### Recommendation
Before removing a chain's `TokenContracts`/`ContractToAsset`/`Precisions` entries in `update_token`, either: (1) require the caller to prove there are no pending un-timed-out `Send` requests targeting that `(asset, chain)` pair (e.g., track an outstanding-transfer counter/set per `(asset, chain)` and `ensure!` it is zero), or (2) retain a "tombstoned" mapping for removed chains so `on_timeout`/`on_accept` can still resolve `ContractToAsset`/`Precisions` for messages dispatched before removal, only fully purging once no more timeouts can arrive for that chain.

### Proof of Concept
1. Governance registers asset `A` for `StateMachine::Evm(42)` via `register_token`, with `TokenContracts`, `ContractToAsset`, `Precisions` populated [5](#0-4) .
2. A user calls `send()` for asset `A` to `Evm(42)` with a nonzero `timeout`; funds are escrowed into `pallet_account()` and a `Send` message is dispatched [6](#0-5) .
3. Before the request times out, governance calls `update_token` with `remove_chains = [Evm(42)]`, which deletes `ContractToAsset`, `TokenContracts`, and `Precisions` for `(A, Evm(42))` [1](#0-0) .
4. The original message times out; `on_timeout` calls `ContractToAsset::<T>::get(dest, &to)`, which now returns `None`, and the handler errors with `HftError::UnknownContractOnTimeout` [7](#0-6) , permanently blocking the refund while the user's funds remain locked in `pallet_account()`.

		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}

			Self::deposit_event(Event::<T>::TokenRegistered {
				asset_id: registration.local_id,
				native: registration.native,
				chains,
			});
			Ok(())
		}
