### Title
Silent `instance()` Fallback in Tron `IntentGatewayV2` Breaks Cross-Chain Authentication, Enabling Unauthorized Escrow Drains - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The DIMO report's core lesson is: a refactor silently removed/changed a safety-critical primitive (`ERC20VotesUpgradeable`) that a downstream authorization/consistency check (`getPastVotes`) depended on, and the assumption was never re-validated. The local Hyperbridge analog is in the Tron fork of `IntentGatewayV2`: the peer-lookup helper `instance()` was refactored to return a **silent fallback value (`address(this)`)** instead of reverting when a source chain has no registered peer gateway — unlike the canonical EVM implementation, whose equivalent `_instance()` always reverts with `UnknownInstance` for unregistered chains. Because `authenticate()` (the only gate protecting `RedeemEscrow`/`RefundEscrow` settlement) trusts `instance()`'s return value, this silent fallback converts "chain has no registered peer" into "sender is trivially satisfied by the contract's own address," breaking the authentication invariant and allowing forged settlement messages to drain escrowed funds.

### Finding Description
In the canonical EVM contracts, cross-chain settlement authentication is strict: [1](#0-0) 

The documented behavior for the underlying `_instance()` helper is explicit: it must revert for unregistered peers, never silently substitute a default: [2](#0-1) 

The Tron fork of the same contract implements the analogous lookup differently — it substitutes `address(this)` whenever the peer mapping is empty, instead of reverting: [3](#0-2) 

This `instance()`/`authenticate()` pair is the sole gate protecting the fund-moving branch of `onAccept`: [4](#0-3) 

Because `IntentGatewayV2` is deployed via CREATE2 with an identical salt and constructor arguments so its address is byte-identical across every connected chain (confirmed by the deploy script's own design rationale): [5](#0-4) 

...the value `address(this)` on the Tron gateway is a publicly-known, chain-agnostic constant. Any state machine that Hyperbridge has connected (has a valid consensus client) but for which the IntentGateway operators have **not yet dispatched a `NewDeployment` peer registration** — a normal, transient, or permanently-unconfigured condition for any new chain — has `_instances[keccak256(thatChain)] == address(0)`. For such a chain, `instance(thatChain)` returns `address(this)` instead of reverting.

Since `IntentGatewayV2`'s implementation contract and its exact constructor arguments (`admin`) and salt (`keccak256(VERSION)`) are all public (verifiable from any live deployment or from this very repository), an attacker can reproduce the identical CREATE2 preimage and deploy the **same bytecode to the same address** on the unconfigured source chain via the standard, permissionless deterministic-deployment proxy that Foundry uses for `new X{salt: ...}()` broadcasts. From that self-deployed contract (whose address equals the destination gateway's `address(this)`), the attacker dispatches an ISMP `PostRequest` to the Tron gateway with `RequestKind.RedeemEscrow` (or `RefundEscrow`) and an arbitrary `WithdrawalRequest{ commitment, tokens, beneficiary }` naming themselves as beneficiary for any known/computable order commitment (including their own freshly placed order, guaranteeing a valid escrow entry to steal). `authenticate()` computes `module = request.from` (their contract's address) and compares it to `instance(request.source)`, which — because `request.source` is unregistered — resolves to `address(this)`, exactly matching `module`. Authentication passes and `withdraw()` releases the escrowed tokens to the attacker without any real solver fill having occurred.

### Impact Explanation
This is a direct, unauthorized fund-release path: an attacker can drain escrowed input tokens from the Tron `IntentGatewayV2` for any order, or for orders they place themselves, by forging a settlement message from a chain that has no registered peer instance. This falls squarely under "stealing or loss of funds," "unauthorized transaction or execution," and "false proof/state acceptance" (the contract accepts a forged settlement it should have rejected). It requires no relayer, prover, admin, or governance compromise — only an unprivileged attacker able to dispatch an ISMP message from any chain Hyperbridge already treats as a valid, connected state machine.

### Likelihood Explanation
Likelihood is tied to whether any Hyperbridge-connected state machine currently lacks a registered `IntentGatewayV2` peer deployment on the Tron side (a normal, expected transient state during any chain rollout, or a permanent state for chains never intended to run the Tron variant). Given the explicit divergence from the safe (`revert`) EVM implementation, and the fact that "unregistered chain" is a routine configuration state rather than an edge case, this is straightforward to trigger the moment such a gap exists — no race condition, no privileged access, and no reliance on a leaked key (deployment reproduction relies solely on public bytecode/salt and the standard, universally-available CREATE2 factory, not the operator's private key).

### Recommendation
Change `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g., with `UnknownInstance`) when no peer is registered, matching the canonical `_instance()` behavior in `evm/src/apps/intentsv2/IntentsBase.sol`. Do not allow any codepath that feeds into `authenticate()` to silently default to `address(this)`; any legitimate self-referential authorization ("this chain trusts itself") should be an explicit opt-in registration, never an implicit fallback for "unknown."

### Proof of Concept
1. Identify a Hyperbridge-connected state machine `X` for which the Tron `IntentGatewayV2` has no registered peer (`_instances[keccak256(X)] == address(0)`).
2. Compute the Tron gateway's deployed address (public, deterministic via CREATE2 with known `admin` and `salt = keccak256(VERSION)`); deploy identical bytecode to that same address on chain `X` using the standard permissionless CREATE2 deployment proxy.
3. From that contract on `X`, place (or observe) an order with escrowed tokens on the Tron gateway, computing `commitment = keccak256(abi.encode(order))`.
4. Dispatch an ISMP `PostRequest` from the attacker's contract on `X` to the Tron gateway with body `bytes.concat(bytes1(uint8(RequestKind.RedeemEscrow)), abi.encode(WithdrawalRequest({commitment, tokens: order.inputs, beneficiary: attacker})))`.
5. When the Tron gateway's `onAccept` processes the message, `authenticate()` calls `instance(X)`, which returns `address(this)` (fallback), matching `request.from` (attacker's contract address, which equals `address(this)` by construction) — authentication passes.
6. `withdraw()` releases the escrowed input tokens to the attacker-controlled beneficiary, with no legitimate destination-chain fill having occurred.

    function instance(bytes calldata stateMachineId) public view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        return gateway == address(0) ? address(this) : gateway;
    }
