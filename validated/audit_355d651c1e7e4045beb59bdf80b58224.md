### Title
`ReceivedOutput::read` accepts an unvalidated offset/script pairing, letting a forged "received" output brick spending of the whole transaction - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class is "an action is accepted without checking the subject's eligibility/state" (voting on non-approved projects). The analog in Serai's Bitcoin wallet is that a `ReceivedOutput` — the artifact that claims "these funds were received and are spendable by key + offset·G" — is constructed from raw bytes by `ReceivedOutput::read` without ever verifying that the claimed `offset` actually maps a wallet key to the output's `script_pubkey`. `Scanner::scan_transaction` establishes that invariant implicitly (it only emits offsets it registered against scripts), but the deserialization path and any non-Scanner constructor skip the check entirely.

### Finding Description
`ReceivedOutput` stores three independent fields: `offset` (the scalar added to the group key to derive the spending key), the `TxOut`, and the `OutPoint` (`mod.rs:90-97`). `ReceivedOutput::read` (`mod.rs:122-134`) simply reads a scalar via `Secp256k1::read_F`, then consensus-decodes the `TxOut` and `OutPoint`, and returns the struct — no consistency check ties `offset` to `output.script_pubkey`.

Downstream, `SignableTransaction::new` (`send.rs:150-256`) copies `input.offset` into `offsets` and `input.output`/`input.outpoint` into the transaction without validation. The only place the invariant is checked is `SignableTransaction::multisig` (`send.rs:273-285`), which returns `None` if `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey`. Because this check is per-`multisig` (after `SignableTransaction::new` already committed the inputs into `prevouts`), a single `ReceivedOutput` carrying a mismatched `offset` causes `multisig` to return `None` for the *entire* transaction — every input in the batch becomes unspendable through this path, and callers that unwrap the `Option` panic.

Likewise, `Scanner::scan_block` (`mod.rs:221-227`) scans the coinbase transaction, whose outputs are maturity-bound; the doc comment admits a post-processing pass is required. That is documented, but `scan_transaction`/`read` still happily report any matching output — including dust-value outputs or outputs to registered Branch/Change/Forwarded scripts — as generic `ReceivedOutput`s indistinguishable from real deposits.

### Impact Explanation
Any component that ingests `ReceivedOutput` bytes it did not itself produce via `Scanner` (e.g., `Output::read` in the processor, or a peer/supplier-provided output list) will treat the output as spendable funds. When the batch is later signed, `multisig` either returns `None` (batch silently dropped → funds reported received but never spendable) or panics in unwrapping callers (liveness failure). An unprivileged party who can feed crafted bytes to `ReceivedOutput::read` can therefore poison the input set and lock all inputs co-batched with the forged one — analogous to donations being routed to a project that can never receive them.

### Likelihood Explanation
Reachability requires an untrusted `ReceivedOutput` byte stream — the prompt's attack surface explicitly includes `ReceivedOutput::read`, and the processor does deserialize these (`processor/src/networks/bitcoin.rs:156`). No cryptographic break is needed: the attacker just picks an `offset` that does not correspond to the script. Likelihood is moderate since honest deployments normally produce these via `Scanner` internally, but the struct gives no way to detect forgery/corruption before it contaminates a batch.

### Recommendation
Validate on construction/deserialization: `ReceivedOutput::read` (or a checked constructor) should take the wallet `key` and verify `p2tr_script_buf(key + GENERATOR * offset) == Some(output.script_pubkey)`, rejecting mismatches. Alternatively/additionally, `SignableTransaction::new` should perform this check per input at construction time so a bad input is rejected before it poisons the whole transaction, and `multisig` should surface a per-input error rather than `None`. Coinbase/dust filtering should also move into `scan_transaction`/`scan_block` rather than relying on callers.

### Proof of Concept
1. Craft bytes: `offset = random nonzero Scalar`, `TxOut` paying to the victim multisig's P2TR script for `key + 0·G` (i.e., `offset = 0`'s script), any valid `OutPoint`.
2. Feed to `ReceivedOutput::read` — succeeds; result claims funds spendable via `key + offset·G`, which does not match the script.
3. Build `SignableTransaction::new(vec![forged, real_input], ...)` — succeeds.
4. Call `.multisig(&keys)` — `p2tr_script_buf(keys.offset(forged_offset).group_key()) != prevout.script_pubkey`, so the function returns `None` (or the caller panics on unwrap), rendering `real_input` unspendable in this attempt as well.

Uncertainty noted: I could not fully trace every production caller of `ReceivedOutput::read`/`Output::read` to confirm a remote byte-supply path beyond the processor's deserialization; the bug stands on the missing validation itself, which the in-scope code (`mod.rs:122`, `send.rs:273`) confirms.
