### Title
Scanner reports economically unspendable dust outputs as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The dust-loan bug class is "no minimum size lets an attacker create positions whose processing cost exceeds their value." In `bitcoin-serai`, `Scanner::scan_transaction` matches only `script_pubkey` and accepts outputs of any value with no lower bound, while `SignableTransaction::new` credits every input's full value even though each P2TR input adds ~58 vB of weight that must be paid for. An unprivileged sender can therefore create outputs the wallet reports as received but which cannot be spent without a net loss.

### Finding Description
`Scanner::scan_transaction` iterates transaction outputs and registers a `ReceivedOutput` whenever `self.scripts.get(&output.script_pubkey)` matches — there is no check on `output.value` at all [1](#0-0) . The `DUST` constant (546 sats) exists in the codebase but is only applied to *outgoing* payments and the change output in `SignableTransaction::new` [2](#0-1) [3](#0-2) . On the spend side, every input unconditionally contributes its full `output.value` to `input_sat` and adds a fixed-size TxIn (41 bytes) plus a 64-byte witness (~58 vB total) to the transaction weight [4](#0-3) [5](#0-4) . The fee accounting `needed_fee = fee_per_vbyte * vbytes` charges for that added weight, but never nets it against the input's value — a 100-sat input counted as +100 sats of funding actually costs `fee_per_vbyte * ~58` sats to include, a guaranteed loss whenever `fee_per_vbyte > value / 58`.

### Impact Explanation
An attacker sends small (below or near dust) outputs to a registered scanner script. The scanner reports them as `ReceivedOutput`s — funds the wallet believes it holds. Spending them costs more in fee weight than they contribute, so the value is effectively unspendable / burned while still credited. Accumulated dust inputs also bloat every transaction that includes them (weight → fee, and can push toward `MAX_STANDARD_TX_WEIGHT`), and if input selection is greedy, dust inputs silently degrade the real usable balance. This is the same economic asymmetry as the dust loan: the cleanup/spend cost is bounded below by per-input weight while the attacker's cost is just the dust value, so rational handling is a loss either way.

### Likelihood Explanation
Fully reachable by an unprivileged party: anyone can send a Bitcoin transaction paying to the scanner's script_pubkey, and `scan_transaction` will report it with no value filter. There is no authentication or minimum-deposit gate anywhere in the in-scope code path. Severity is Medium rather than High because dust outputs remain cryptographically spendable (the loss is economic, and sub-dust outputs require miner cooperation to create), and the harm is unspendable credited value / fee drainage rather than direct theft.

### Recommendation
Apply a minimum-value check symmetric to `DUST`: in `Scanner::scan_transaction` (or at `ReceivedOutput` ingestion), skip outputs whose value is below the spend threshold — i.e., below `DUST` or below `fee_per_vbyte * per-input vbytes`. Alternatively, track per-input spend cost in `SignableTransaction::new` and exclude inputs whose value is less than the marginal fee they add.

### Proof of Concept
```rust
// Attacker crafts a tx paying `value` sats to the wallet's P2TR script,
// where value < fee_per_vbyte * ~58 (marginal input weight cost).
let received = scanner.scan_transaction(&attacker_tx);
assert_eq!(received.len(), 1);          // reported as funds received
assert_eq!(received[0].value(), 100);   // e.g. 100 sats

// SignableTransaction::new counts all 100 sats toward input_sat...
// but calculate_weight_vbytes adds ~58 vB for the input + witness.
// At fee_per_vbyte = 10, including this input costs ~580 sats of fee
// while contributing only 100 sats — a net loss of ~480 sats.
// There is no code path that rejects or deprioritizes this input.
```
Confirmed by code inspection: `scan_transaction` (wallet/mod.rs:199–214) has no value filter, and `SignableTransaction::new` (send.rs:175, 204–235) credits full input value while charging flat weight-based fees.

Caveat: whether dust inputs are actually consumed depends on the out-of-scope processor's input-selection policy (`processor/src/networks/bitcoin.rs` was not fully analyzed); the receipt-without-spendability issue stands regardless since the scanner reports the output as valid received funds.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
