Based on my research, I found a strong local analog in Agave's epoch-reward distribution pipeline. The original report's core pattern is: a reward-calculation step computes an amount to mint/pay based on a snapshot of external state, then a *later*, separate step actually applies that payment against potentially-changed external state, and the code enforces the resulting invariant with a hard failure (in Solidity: a revert on `RED.mint()`; in Agave: a Rust `assert!`/`panic!`). In Solana's validator, unlike a single contract call reverting a single transaction, a panic inside `Bank::process_new_epoch` is executed identically and deterministically by every validator at every epoch boundary — so an invariant violation there is a chain-wide consensus halt, not merely a locked reward. [1](#0-0) 

The `distribute_reward_commissions` function computes an assertion that the total commission lamports distributed, sent to the incinerator, burned, and paid as stake rewards never exceeds the previously-computed `point_value.rewards` budget for the epoch: [2](#0-1) 

Critically, the code comments explicitly acknowledge that commission account state is *intentionally* re-read at distribution time rather than reused from calculation time, specifically to reflect "intervening account mutations (e.g. VAT burns in `update_epoch_stakes`)": [3](#0-2) 

This is the same TOCTOU (time-of-check/time-of-use) shape as the RED-token report: an amount is computed against one view of state (`calculate_rewards_for_partitioning` / `calculate_stake_rewards_and_commissions`, using `point_value` derived from capitalization/inflation at the epoch boundary) and is only actually credited later, against a different, mutated view of state (`load_and_reward_commission_accounts`, which re-fetches accounts with `get_account_with_fixed_root_no_cache` after `update_epoch_stakes` may have burned VAT). A dedicated test even documents this drift as expected behavior: [4](#0-3) 

Because `custom_commission_collector` (SIMD-0232) lets an unprivileged vote-account withdrawer designate an arbitrary system-owned account as the commission collector, an attacker fully controls the account that is re-read and mutated between calculation and distribution: [5](#0-4) 

If the deferred re-check ever computes a sum that exceeds the epoch's `point_value.rewards` budget (e.g., through interaction of rounding in per-account reward math, block-reward accounting, or unexpected interleaving with VAT-burn timing), the `assert!` at line 398 panics inside mandatory, per-epoch-boundary bank processing, which runs identically on all validators: [6](#0-5) 

### Title
Deterministic panic in epoch-boundary reward-commission accounting invariant can halt the network - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`Bank::distribute_reward_commissions`, invoked unconditionally from `process_new_epoch` at every epoch boundary on every validator, asserts that the sum of distributed, incinerated, burned, and stake-reward lamports never exceeds the epoch's precomputed `point_value.rewards` budget. This amount is computed once against a snapshot of vote/stake state, but the commission accounts it is checked against are deliberately re-loaded later, after intervening account mutations (VAT burns in `update_epoch_stakes`, or attacker-controlled custom commission-collector accounts under SIMD-0232). If the deferred re-read ever yields a total that exceeds the originally computed budget, the `assert!` panics.

### Finding Description
`begin_partitioned_rewards` calls `distribute_reward_commissions` with a `PartitionedRewardsCalculation` that was produced earlier from a state snapshot (stake history, vote accounts, capitalization) via `calculate_rewards`/`calculate_rewards_for_partitioning`. Inside `distribute_reward_commissions`, the actual commission accounts are only loaded and credited at this later point via `load_and_reward_commission_accounts`, which explicitly re-fetches account state with `get_account_with_fixed_root_no_cache` so that "intervening account mutations (e.g. VAT burns in `update_epoch_stakes`)" are reflected. The function then asserts that `point_value.rewards >= distributed_lamports + distributed_to_incinerator_lamports + burned_lamports + total_stake_rewards_lamports`. Because the collector account identity is attacker-influenceable (via `custom_commission_collector`/SIMD-0232, any system-owned account can be designated), and because the check-then-use gap allows external mutation of that exact account between the two points in time, the invariant assumed by the assert depends on timing and state that is not fully controlled by the code that computed the budget.

### Impact Explanation
A failed assertion here is a `panic!` inside `Bank::process_new_epoch`, which every validator executes deterministically as part of normal epoch-boundary block processing. Unlike the original report (a localized revert that blocks reward harvesting for a subset of users), a panic in this code path crashes/halts validator processing of the epoch-boundary block network-wide, since all validators reach the same state and same assertion. This is a consensus-halt-class impact.

### Likelihood Explanation
Low-to-medium: triggering requires finding a concrete interleaving of account mutation (e.g., VAT burn or custom-collector account changes) and reward math that pushes the total distributed above the computed budget — the arithmetic is `>=` (allows leftover) so ordinary rounding-down should not trip it, but the explicit design comment acknowledging deferred re-reads for "intervening account mutations" signals fragility in the invariant across cases the existing tests may not fully cover.

### Recommendation
Either compute and apply the commission distribution atomically without a deferred re-read gap, or replace the `assert!` (which panics validator-wide) with a saturating/clamped accounting path (mirroring how `store_stake_accounts_in_partition` already tolerates and logs a per-account error instead of panicking), so that even an unexpected accounting drift degrades gracefully instead of halting the bank.

### Proof of Concept
A concrete transaction-level trigger was not established from local code alone — the finding is based on identifying an unresolved TOCTOU pattern between reward-budget calculation and deferred, attacker-influenceable commission-account re-reads, protected only by a validator-crashing `assert!`. Confirming exploitability would require constructing a specific sequence of vote-account commission-collector changes and VAT-burn timing that pushes the computed sum past `point_value.rewards`, which needs runtime experimentation beyond static code review.

    fn test_load_and_reward_commission_accounts_reflects_vat_burn() {
        let (genesis_config, _mint_keypair) = create_genesis_config(1_000 * LAMPORTS_PER_SOL);
        let bank = Bank::new_for_tests(&genesis_config);
        let thread_pool = ThreadPoolBuilder::new().num_threads(1).build().unwrap();
        let pubkey = solana_pubkey::new_rand();

        let pre_burn_balance = 10 * crate::bank::DEFAULT_VAT_TO_BURN_PER_EPOCH;
        let commission_lamports = 12_345;

        // Commission is planned against the pre-burn account state.
        let mut commission_account = AccountSharedData::default();
        commission_account.set_lamports(pre_burn_balance);
        bank.store_account_and_update_capitalization(&pubkey, &commission_account);
        let mut reward_commissions = RewardCommissions::default();
        reward_commissions.insert(
            pubkey,
            RewardCommission {
                commission_bps: Some(500),
                commission_lamports,
                burned_lamports: 0,
                is_vote_account: true,
            },
        );

        // Simulate the VAT burn that would run in `update_epoch_stakes`
        // between reward calculation and distribution.
        let post_burn_balance = pre_burn_balance - crate::bank::DEFAULT_VAT_TO_BURN_PER_EPOCH;
        let mut burned_account = commission_account.clone();
        burned_account.set_lamports(post_burn_balance);
        bank.store_account_and_update_capitalization(&pubkey, &burned_account);

        let result = bank.load_and_reward_commission_accounts(&reward_commissions, &thread_pool);

        assert_eq!(result.accounts_with_rewards.len(), 1);
        let (pubkey_result, reward_info, account) = &result.accounts_with_rewards[0];
        assert_eq!(*pubkey_result, pubkey);
        // Commission is credited on top of the post-burn balance, not the
        // pre-burn snapshot captured at calculation time.
        let expected_post_balance = post_burn_balance + commission_lamports;
        assert_eq!(account.lamports(), expected_post_balance);
        assert_eq!(
            *reward_info,
            RewardInfo {
                reward_type: RewardType::Voting,
                lamports: commission_lamports as i64,
                post_balance: expected_post_balance,
                commission_bps: Some(500),
            }
        );
        assert_eq!(result.amounts.distributed_lamports, commission_lamports);
    }

impl NewCommissionCollector<'_, '_> {
    /// Validates the collector per SIMD-0232 and returns its pubkey.
    ///
    /// The designated commission collector must either be equal to the vote
    /// account's address OR satisfy ALL of the following constraints:
    ///
    /// 1. Must be a system program owned account.
    /// 2. Must be rent-exempt.
    /// 3. Must not be a reserved account (checked via writable flag).
    pub fn validate_and_resolve_key(
        &self,
        vote_account: &BorrowedInstructionAccount,
        rent: &Rent,
    ) -> Result<Pubkey, InstructionError> {
        match self {
            NewCommissionCollector::VoteAccount => Ok(*vote_account.get_key()),
            NewCommissionCollector::NewAccount(collector_account) => {
                // 1. Must be a system program owned account.
                if collector_account.get_owner() != &system_program::id() {
                    return Err(InstructionError::InvalidAccountOwner);
                }

                // 2. Must be rent-exempt.
                if !rent.is_exempt(
                    collector_account.get_lamports(),
                    collector_account.get_data().len(),
                ) {
                    return Err(InstructionError::InsufficientFunds);
                }

                // 3. Must not be a reserved account (checked via writable flag).
                if !collector_account.is_writable() {
                    return Err(InstructionError::InvalidArgument);
                }

                Ok(*collector_account.get_key())
            }
        }
    }
