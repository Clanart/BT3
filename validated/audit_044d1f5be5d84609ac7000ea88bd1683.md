Based on my research, I found a real analog in the codebase: a boundary-check bug in the path-containment helper that is structurally identical to the reported flaw (a comparison that should enforce a strict boundary but instead allows a value that is technically outside it).

### Title
`resolveWithin()` uses unanchored `String.startsWith()` for repo-containment check, allowing sibling-directory escape via crafted deep-link `filepath` - (File: `app/src/lib/path.ts`)

### Summary
The EIP-4626 report's core defect is a boundary condition that is checked in the wrong direction/without the correct guard, so a value that should be excluded (rounds the "wrong way") is treated as valid. The closest real analog in GitHub Desktop is `_resolveWithin()` in `app/src/lib/path.ts`, which is meant to guarantee that a resolved path is "at, or underneath" a root path, but implements that guarantee with a bare string prefix comparison instead of a path-boundary-aware comparison.

### Finding Description
`_resolveWithin()` computes the real (symlink-resolved) root and the real resolved target path, then decides containment purely with: [1](#0-0) 

`String.prototype.startsWith` has no concept of path separators. If `realRoot` is `/Users/victim/Documents/GitHub/myrepo`, any path that textually begins with that string — such as `/Users/victim/Documents/GitHub/myrepo-secrets/config` or `/Users/victim/Documents/GitHub/myrepo.bak/id_rsa` — will satisfy `realResolved.startsWith(realRoot)` even though it is a sibling directory, not a subdirectory of the repository. The function's own documentation promises the resolved path is "guaranteed to reside at, or underneath" the root, but the implementation does not enforce this: it never checks that `realResolved === realRoot` or that the next character after the root prefix is a path separator. [2](#0-1) 

This helper is exposed via `resolveWithin`, `resolveWithinPosix`, and `resolveWithinWin32`, and is consumed at several security-relevant call sites, including the "Open Repository from URL" deep-link handler: [3](#0-2) 

Here, `filepath` originates from an attacker-controlled `x-github-client://openRepo/...?filepath=...` deep link parsed by `parseAppURL()` — an unprivileged, remote-triggerable input (a link the user clicks) — with no traversal-segment sanitization performed beyond an `isAbsolute()` check. [4](#0-3) 

I also found other consumers of `resolveWithin` in `app/src/lib/copilot-conflict-context.ts` and `app/src/lib/stores/app-store.ts`, but I was unable to fully trace those call chains and their attacker-reachability within the available search budget — this should be verified separately, as they may represent a higher-impact instance of the same broken invariant (e.g., reading file contents outside the repo rather than just revealing a path in the file manager).

### Impact Explanation
The confirmed sink (`shell.showItemInFolder`) discloses/reveals the existence and location of a sibling filesystem entry outside the intended repository boundary to the OS file manager — a boundary violation of "read outside the repo" in a weak form. Because the same broken invariant (`_resolveWithin`) is reused as the general-purpose containment guard across the codebase, any call site that performs a stronger operation (read, write, or exec) using this guard would inherit a genuine unauthorized file-access primitive from a single string-prefix flaw, matching the "file read/write outside the repo" impact class from an attacker-controlled deep link.

### Likelihood Explanation
Triggering `openRepositoryFromUrl`'s `filepath` branch requires only that a victim click an `x-github-client://` (or platform-equivalent `github-mac://`/`github-windows://`) link with a `filepath` query parameter — no local access, no admin rights, and no prior compromise, satisfying the "unprivileged... link the user clicks" impact criterion. The only existing guard, `isAbsolute(filepath)`, does not stop this class of bug, since the sibling-directory string-prefix collision is a fully relative path resolution issue, not an absolute-path issue. [5](#0-4) 

### Recommendation
Fix `_resolveWithin()` to enforce a real path boundary rather than a string prefix: after computing `realRoot` and `realResolved`, accept the result only if `realResolved === realRoot` or `realResolved.startsWith(realRoot + Path.sep)` (using the appropriate separator for the `options` variant, i.e. `/` for `resolveWithinPosix`, `\\` for `resolveWithinWin32`). Add regression tests with sibling directories that share a root as a string prefix (e.g., `root` vs `root-evil`, `root` vs `root.bak`) to prevent recurrence, mirroring the existing `clone-path-safety-test.ts` traversal tests. [6](#0-5) 

### Proof of Concept
1. Victim has a repository open at `/Users/victim/Documents/GitHub/myrepo`, and a sibling directory `/Users/victim/Documents/GitHub/myrepo-secrets` exists containing a sensitive file `token.txt`.
2. Attacker sends the victim a link:
   `x-github-client://openRepo/https://github.com/victim/myrepo?filepath=..%2Fmyrepo-secrets%2Ftoken.txt`
3. `parseAppURL` extracts `filepath = "../myrepo-secrets/token.txt"`, which is not absolute, so it passes the only existing guard.
4. `resolveWithin(repository.path, filepath)` computes `realResolved = /Users/victim/Documents/GitHub/myrepo-secrets/token.txt` and `realRoot = /Users/victim/Documents/GitHub/myrepo`; since `realResolved.startsWith(realRoot)` is `true` (string prefix match), the function returns the path as "contained."
5. `shell.showItemInFolder(resolved)` reveals `token.txt` from outside the repository to the victim's file manager, confirming the boundary check is bypassed. [1](#0-0)
