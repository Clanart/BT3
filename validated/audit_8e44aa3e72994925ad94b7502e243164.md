### Title
Forged secret-share message frames an innocent participant as faulty — sender identity is an attacker-chosen label, not bound to the participant - (File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs)

### Summary
In the PedPoP DKG, the only cryptographic "authentication" of who sent an `EncryptedMessage` is a Schnorr proof-of-possession whose challenge binds a `sender`/`from` field. That `from` value is not derived from any participant identity (key, commitments, index); it is simply whatever `Participant` value the prover/verifier choose — the verifier uses the `HashMap` key under which the message was delivered (`l` in `calculate_share`, `sender` in `blame_internal`). An attacker can therefore mint a fully valid `EncryptedMessage` whose PoP, decryption path, and blame proof all consistently claim an arbitrary victim `Participant` as the sender, causing that victim to be reported as `faulty` (invalid share / invalid signature) and blamed/slashed by `VerifyBlame`.

### Finding Description
`EncryptedMessage::decrypt` (via `Encryption::decrypt`, encryption.rs:469-501) and `Decryption::decrypt_with_proof` (encryption.rs:366-397) verify `msg.pop` against `pop_challenge(context, R, key, from, msg)` where `from` is the caller-supplied map key. `encrypt` (encryption.rs:135-168) signs the PoP with `from = self.i` for honest senders, but nothing forces `from` to correspond to a real identity — it is a field inside the attacker's own signature. In `KeyMachine::calculate_share` (lib.rs:463-499) each incoming share is processed under the attacker-influenced key `l`; a batch failure maps to `PedPoPError::InvalidShare { participant: l, blame }`. In `BlameMachine::blame_internal` / `AdditionalBlameMachine::blame` (lib.rs:575-633, 674-682), `sender` and `recipient` are caller-supplied; `VerifyBlame` in `processor/src/key_gen.rs:504-549` consumes `accuser`/`accused` from the network message and returns `ProcessorMessage::Blame { participant: accused }` when the forged evidence verifies.

Attack: attacker constructs an `EncryptedMessage` — fresh ephemeral key `k`, PoP signed over `pop_challenge(context, R, k*G, victim, ct)` — and submits it under `victim`'s participant index. The PoP verifies (challenge uses `victim`, matching the attacker's chosen `from`), decryption succeeds (attacker knows `k`), and share verification against `commitments[victim]` fails because the attacker cannot know victim's polynomial share. Result: `InvalidShare { participant: victim, blame: Some(valid_dleq_proof) }` — a self-consistent, third-party-verifiable blame proof convicting an innocent participant. Alternatively, replaying any honest participant's real message under a different index makes the PoP check fail and yields `InvalidSignature`/`faulty: victim` with `blame: None`.

### Impact Explanation
The blame system is the "privileged helper": its verdict drives `ProcessorMessage::InvalidShare`/`Blame`, which fatally slashes the named participant and aborts the key-generation session. Because sender attribution trusts a label rather than a cryptographically bound identity (analogous to trusting a spoofable callerID), an unprivileged party who can feed `EncryptedMessage` bytes into `calculate_share`/`blame`/`VerifyBlame` (via `EncryptedMessage::read` on shares in `CoordinatorMessage::Shares`/`VerifyBlame`) can cause an honest validator to be adjudicated faulty and removed — a forged-proof / false-attribution primitive that also lets a real cheater evade blame by pinning faults on others.

### Likelihood Explanation
Reachable by any party able to submit or relay DKG share/blame messages; requires no key material beyond a freshly generated ephemeral scalar. Certainty of impact (honest participant marked faulty, session aborted) is high; the on-chain slashing consequence depends on how the coordinator authenticates the `HashMap<Participant, _>` keys — the library itself assumes an external authenticated channel, but the PoP's `sender` field gives a false impression of in-band authentication and `VerifyBlame` accepts blame evidence without any identity binding beyond it. Severity: Medium/High (integrity of blame attribution; no direct key recovery, since the attacker learns nothing about victim's actual share).

### Recommendation
Bind sender identity cryptographically rather than to a label: e.g., require the PoP (or a separate signature) under the sender's registered encryption key / commitments-derived identity, or include the sender's `enc_key` in `pop_challenge` so a message can only verify as coming from the holder of the registered key. In `blame_internal`, additionally verify that `proof.key` corresponds to `ecdh` between `enc_keys[recipient]` and `msg.key` *and* that `msg` could only have been authored by `sender` (e.g., require the share plaintext to verify against `commitments[sender]` for the "valid share" verdict rather than defaulting to blaming `sender` on any PoP failure). Reject blame statements where the supplied `msg` fails the PoP check when `sender` was not the authenticated origin, instead of returning `sender` as faulty.

### Proof of Concept
```rust
// Attacker wants to frame honest participant `victim` in session `context`.
let k = random_scalar();            // ephemeral "encryption" key the attacker controls
let r = random_scalar();            // PoP nonce
let plaintext_share = SecretShare(b"garbage"); // any bytes
let mut msg = plaintext_share.clone();
// Encrypt to the real recipient's registered enc_pub_key (public data)
cipher::<C>(context, &ecdh::<C>(&k, enc_keys[recipient])).apply_keystream(msg.as_mut());
let forged = EncryptedMessage {
    key: C::generator() * k,
    pop: SchnorrSignature::sign(&k, r,
        pop_challenge::<C>(context, C::generator()*r, C::generator()*k,
                           victim,               // <-- attacker-chosen identity
                           plaintext_share.as_ref())),
    msg,
};
// Submit `forged` under HashMap key `victim` in the Shares message.
// In KeyMachine::calculate_share: PoP verifies (challenge uses `victim`),
// decryption succeeds, share check vs commitments[victim] fails ->
//   InvalidShare { participant: victim, blame: Some(valid DLEq proof) }
// VerifyBlame re-verifies the same forged evidence and returns
//   Blame { participant: victim } -> innocent victim slashed.
```

Confidence caveat: the finding holds if the `Participant` map keys in the `Shares`/`VerifyBlame` messages are attacker-influenceable (i.e., not already bound to an authenticated channel upstream). The code comments explicitly delegate channel authentication to the caller; the gap is that the PoP's `sender` field is presented as sender authentication while binding only an attacker-chosen label, making forged blame evidence internally consistent.
