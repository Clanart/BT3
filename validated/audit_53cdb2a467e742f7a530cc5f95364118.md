### Title
Untrusted length field in `ThresholdKeys::read` causes attacker-controlled heap allocation and O(n) deserialization work — Denial of Service - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The `johnzon-mapper` advisory is a deserialization-of-untrusted-data bug where a small attacker-supplied input (a JSON number like `1e20000000`) triggers disproportionately expensive computation, yielding a denial of service. The analog in Serai is `ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs`: it reads a 2-byte `n` from the input stream and immediately performs `Vec::with_capacity(usize::from(n))` and `HashMap` insertion work scaled to `n` — all driven by the declared length rather than by bytes actually present or validated — so a handful of attacker bytes force a ~2 MiB heap allocation plus an `O(n)` read/insert loop. `ThresholdKeys::read` is an explicitly in-scope sink for untrusted bytes.

### Finding Description
In `ThresholdKeys::read`, after the curve-ID check, `t`, `n`, and `i` are read as little-endian `u16`s from the reader — fully attacker-controlled [1](#0-0) . If the interpolation tag byte is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` and then loops `n` times calling `C::read_F(reader)` [2](#0-1) . `with_capacity` allocates the full backing store eagerly: with `n = 0xFFFF` (65535) and 32-byte scalar field elements, a single short input forces an immediate ~2 MiB allocation before a single payload byte is validated. Independently of the interpolation tag, the function then loops `1..=n` inserting into a `HashMap<Participant, C::G>` via `read_G` [3](#0-2) , performing `n` point decodings and hash-table insertions sized entirely by the declared count, not the input size.

The same "trusted declared length" pattern is the root cause: the deserializer commits resources proportional to an unauthenticated length field rather than to the actual byte stream. By contrast, other in-scope readers bound work by caller-supplied parameters (`Commitments::read` uses `params.t()` [4](#0-3) ) or fail fast on truncation (`SchnorrAggregate::read`'s loop is bounded by bytes actually present [5](#0-4) ), so `ThresholdKeys::read` is the strongest reachable instance of the class.

### Impact Explanation
An unprivileged party who can cause a Serai node to feed bytes to `ThresholdKeys::read` (e.g., loading/relaying serialized threshold keys) can force repeated ~2 MiB heap allocations and tens of thousands of scalar/point decoding operations per message, each triggered by only ~8–14 input bytes. Repeated invocations cause memory pressure / allocator exhaustion and CPU burn on the victim process — a denial of service matching the CVE's `A:L` impact class (Medium).

### Likelihood Explanation
Likelihood is moderate: `ThresholdKeys::read` is a public API explicitly in the untrusted-bytes sink list, and the malicious input is trivially constructed (any stream whose `n` field is `0xFFFF`). The amplification is capped at `u16::MAX` elements per call, so exploitation requires repeated calls rather than a single shot, keeping severity at Medium rather than High.

### Recommendation
Do not size allocations from the untrusted `n` field before validation. Concretely in `crypto/dkg/src/lib.rs::ThresholdKeys::read`:
- Reject `n` values above a protocol-maximum participant count (e.g., the protocol's real `MAX_KEY_SHARES_PER_SET` bound) before allocating.
- Replace `Vec::with_capacity(usize::from(n))` with incremental `push` so allocation tracks bytes actually consumed.
- Consider checking `ThresholdParams::new(t, n, i)` *before* deserializing the interpolation/verification-share bodies, since an invalid `(t, n, i)` makes all subsequent work wasted.

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Ciphersuite;
use dkg::{ThresholdKeys, ThresholdParams};
// Any in-scope ciphersuite, e.g.:
// type C = ciphersuite::ristretto::Ristretto; // or kp256 Secp256k1

fn poc() {
    let mut bytes = Vec::new();
    // Curve ID length + ID (must match C::ID to pass the preamble check)
    bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
    bytes.extend(C::ID);
    bytes.extend(1u16.to_le_bytes());      // t = 1
    bytes.extend(u16::MAX.to_le_bytes());  // n = 65535  <-- attacker controlled
    bytes.extend(1u16.to_le_bytes());      // i = 1
    bytes.push(0u8);                       // Interpolation::Constant
    // No further bytes needed: Vec::with_capacity(65535) is executed
    // before the first read_F fails on EOF.
    let _ = ThresholdKeys::<C>::read(&mut Cursor::new(bytes));
}
```
With `n = 0xFFFF`, the call eagerly allocates ~65535 scalar slots (~2 MiB) and, if enough bytes are supplied to keep it going, performs `O(n)` `read_F`/`read_G` decodes and `HashMap` insertions — all driven by a 2-byte attacker field, i.e., resource consumption disproportionate to input size, the same failure mode as CVE-2023-33008.

Caveat: I verified the allocation/loop behavior directly in `crypto/dkg/src/lib.rs` but did not trace every caller that pipes network-received bytes into `ThresholdKeys::read`; the reachability claim rests on the API being a listed untrusted-bytes sink.
