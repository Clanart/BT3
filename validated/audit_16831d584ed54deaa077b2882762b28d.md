## Title
Divergent conflict-marker parsers in Copilot conflict resolution let attacker-controlled file content desynchronize hunk boundaries, silently committing leftover git conflict markers or corrupted code - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The report's core defect is that a state-tracking mechanism (the outtx tracker's `HashList`) is capped/limited while a second, independent process (the observer) relies on that state being complete, and a validation gate (`isDup`/proof check) doesn't catch the mismatch — so stale/incomplete tracking silently corrupts downstream processing. GitHub Desktop's Copilot-based conflict-resolution feature has an equivalent broken invariant: two independently-written conflict-marker parsers — `extractConflictHunks` (used to build the prompt and the *expected* hunk count) and `reassembleResolvedFile` (used to splice the model's answer back into the on-disk file) — use different, non-equivalent marker-matching rules. When the conflicted file's *content itself* contains marker-like text (`<<<<<<<`, `=======`, `>>>>>>>`), the two parsers can disagree about where a hunk ends, while still agreeing on the *count* of hunks. Because `validateResolutionPaths` only checks that hunk *counts* match, this desync passes validation silently, and `reassembleResolvedFile` ends up copying real, un-resolved conflict-marker lines straight into the file that `_applyCopilotConflictResolutions` writes to disk and `git add`s.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) walks the file sequentially and, once inside a hunk, only checks for `baseMarker`/`separatorMarker` while collecting "ours" lines, and only checks for `theirsMarker` while collecting "theirs" lines — it never re-checks for a nested `oursMarker` (`<<<<<<<`) inside those inner loops: [1](#0-0) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) uses a *different* rule to find the end of a hunk: it scans forward from the `<<<<<<<` line looking for *any* `=======` line (in any position) and the *first* `>>>>>>>` line, regardless of the ordering the first parser enforced: [2](#0-1) 

If a conflicted file's own content (fully attacker-controlled — e.g. a doc, test fixture, or sample-diff file on the attacker's branch that legitimately contains git-marker-like text) embeds a second, nested `<<<<<<< / ======= / >>>>>>>` sequence inside one real conflict block, both parsers latch onto the *same inner* `>>>>>>>` as the "closing" marker (so hunk *count* stays consistent — 1 in, 1 out). But `extractConflictHunks` never sends the remaining real content (the true `=======` and `>>>>>>>` markers, and everything after the nested block) to the model at all — it's silently dropped from context. `reassembleResolvedFile`, however, still walks the *entire* raw file afterward, and because the outer/real `<<<<<<<` was already consumed with `i = closingIndex + 1` pointing past the *inner* marker, the leftover real `=======` / `>>>>>>>` lines no longer match `reassemblyOursMarker` and are copied through **verbatim as ordinary file content**.

The only cross-check between the two stages is `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`), which only compares `resolutions.length`/`hunks.length` counts against `expectedHunkCounts` derived from `extractConflictHunks` — it never re-validates hunk boundaries against the raw file, so this scenario passes validation cleanly: [3](#0-2) 

The per-hunk marker check inside `parseCopilotConflictResolution` only inspects the *model's own* `resolvedContent` string for stray markers — it never re-checks the final reassembled full-file content for leftover markers before it's written: [4](#0-3) 

Finally, `_applyCopilotConflictResolutions` writes `resolution.resolvedContent` straight to disk and stages it with `git add`, with no final "no markers remain" gate: [5](#0-4) 

### Impact Explanation
The result is that the user clicks "Continue Merge" believing Copilot cleanly resolved the conflict, but the file that actually gets written and staged for commit can contain: (a) literal residual git conflict markers (`=======`, `>>>>>>> feature`) mixed into otherwise-valid code, or (b) genuinely dropped/misattributed "theirs" or "ours" content that never reached the model and is now silently missing from the committed file. This is a silent corruption of what the user commits/pushes — for source files this typically breaks the build (syntax error from stray markers), but for config, data, docs, or generated files it can silently ship wrong/incomplete content without any error surfaced to the user, since validation reports success. This is entirely driven by content on an attacker-controlled cloned/fetched branch (a documentation file, changelog, or test fixture describing git conflicts is a completely natural, unsuspicious vector), matching the "silent corruption of what the user commits/pushes" impact category.

### Likelihood Explanation
The attacker only needs to get the victim to merge/rebase/cherry-pick a branch that touches a file containing marker-like text that creates a real conflict on a nearby region (e.g. editing a `README.md`/tutorial that documents git conflict markers, a test fixture, or an intentionally crafted file). This requires no special privileges beyond the victim voluntarily merging with the attacker's fork/PR, and no unnatural user steps beyond the normal "Resolve with Copilot" flow already offered by the app when conflicts occur.

### Recommendation
Make hunk-boundary detection consistent and authoritative in one place: derive `reassembleResolvedFile`'s splice points from the exact same structural walk `extractConflictHunks` used (or have `extractConflictHunks` return explicit line-range offsets that `reassembleResolvedFile` consumes directly), rather than two independently re-implemented, less-strict regex scans of the same file. Additionally, after reassembly, scan the final full resolved content for leftover conflict markers (`^<{7}`, `^={7}$`, `^>{7}`) and treat any hit as a hard validation failure (surfaced to the user) rather than writing/staging it.

### Proof of Concept
1. On a branch the attacker controls, add/modify `docs/git-conflicts.md` (or any text/config file) so that when merged it produces exactly one real conflict block whose "ours" content is:
```
<<<<<<< HEAD
Some real explanatory text about conflicts, including a nested example:
<<<<<<< HEAD
example
=======
example2
>>>>>>> branch
real ours tail content
=======
real theirs content
>>>>>>> feature
```
2. Victim merges/rebases with this branch in GitHub Desktop, triggering a conflict on that file, and clicks "Resolve with Copilot".
3. `extractConflictHunks` (in `buildConflictContext`) finds exactly 1 hunk, bounded by the *inner* `>>>>>>> branch` marker, and never sends "real ours tail content", the real `=======`, "real theirs content", or the real `>>>>>>> feature` to the model.
4. The model returns 1 hunk resolution (matching the expected count of 1), so `validateResolutionPaths` passes.
5. `reassembleResolvedFile` splices the model's single resolution at the same inner closing-marker position, then copies the remaining real lines — including the literal `=======` and `>>>>>>> feature` markers — through verbatim into the final `resolvedContent`.
6. `_applyCopilotConflictResolutions` writes this content to disk and runs `git add`, staging a file that still contains real, unresolved git conflict markers (or missing real content) with no error shown to the user. [6](#0-5) [7](#0-6)

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
