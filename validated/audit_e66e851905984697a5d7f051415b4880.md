### Title
JSON field/extension name collision causes cross-field value confusion in `JsonFormat` parsing - ([File: java/util/src/main/java/com/google/protobuf/util/JsonFormat.java])

### Summary
Django's `get_signed_cookie` bug stems from a non-injective mapping: `salt derivation = name + salt`, so two distinct `(name, salt)` pairs can collapse to the same string, letting a signature computed for one context be replayed/accepted in a different context. Protobuf's ProtoJSON layer has the same class of invariant failure: the mapping from a `FieldDescriptor` (or extension) to a JSON object key is not guaranteed to be injective. Regular fields and extensions can be assigned the *same* JSON key (via default json_name derivation, explicit `json_name` option, or the legacy short-extension-name mode), and the codebase's own design docs and tests confirm this leads to undefined, cross-field-confusing behavior when parsing JSON that an attacker fully controls.

### Finding Description
Protobuf normally disambiguates extension keys from regular field keys in ProtoJSON by wrapping extensions in brackets, e.g. `"[pkg.ExtensionName]"` — this bracket is the delimiter that keeps the two namespaces (field names vs. extension full names) from colliding, analogous to the delimiter Django's `get_signed_cookie` is missing between `name` and `salt`.

That delimiter/namespace separation is removed under the legacy compatibility option `printingDeprecatedNonConformantShortExtensionNames()`, which prints extensions using their *short name* instead of the bracketed full name. If a proto2 message declares a regular field and an extension whose short names coincide (which the descriptor validator only *warns* about, and does not reject, under `LEGACY_BEST_EFFORT`/legacy proto2 json handling — see the explicit design note that conflicting JSON mappings are allowed and produce "undefined behavior... inconsistent across runtimes"): [1](#0-0) 

the descriptor builder's uniqueness check treats such non-custom/legacy conflicts as a warning, not a hard error, in `CheckFieldJsonNameUniqueness`: [2](#0-1) 

This is demonstrated end-to-end by the runtime's own regression test, which shows that serializing a message with a same-named field and extension produces **duplicate JSON keys**, and that re-parsing that JSON silently drops the extension value and/or writes it into the regular field: [3](#0-2) 

The equivalent ambiguity also exists on the "alternate spelling" side: the Python duplicate-key detector during parsing only rejects *exact string* duplicates, not different JSON spellings (snake_case vs. camelCase) that resolve to the same underlying field, so `{"int32Map": {"1":2}, "int32_map": {"3":4}}` silently "last-wins" instead of erroring: [4](#0-3) 

The failed invariant transferred from the Django CVE is exactly this: a derived lookup key (JSON name) is supposed to injectively identify one semantic entity (one field/extension), but the derivation collapses two distinct entities to the same key, and the consuming code (the JSON→field map used during parse) has no secondary check to detect or reject the collision — it just overwrites/drops one of the two colliding values.

### Impact Explanation
An attacker who controls only the bounded ProtoJSON body sent to a public `JsonFormat.parse`/merge API can supply a single JSON key that is ambiguous between a regular field and an extension (or between two spellings of the same field). Depending on which entry was inserted last into the parser's name→field lookup, the attacker's JSON value can be silently applied to the *wrong* field, or an intended extension write can be silently dropped while a differently-typed regular field is populated instead — a data-integrity/type confusion at the application layer, structurally identical to the Django bug's context confusion (value verified/accepted for a different logical field than the schema author intended). This does not cause memory corruption; the impact is limited to the affected message being semantically wrong (Medium severity, matching the source advisory's severity), consistent with the report's own characterization as a namespace-collision class issue rather than an RCE-class primitive.

### Likelihood Explanation
This requires a precondition already permitted by a trusted proto2 schema (a field and extension — or two fields — whose JSON names collide, which the descriptor builder only warns about under legacy/`LEGACY_BEST_EFFORT` json_format), and, for the extension case, use of the deprecated `printingDeprecatedNonConformantShortExtensionNames` legacy compatibility path. Given those (schema-only, non-adversarial) preconditions, exploitation from the attacker's bounded JSON input alone is straightforward and requires no additional capability — it is entirely determined by which JSON key the attacker sends. Likelihood is therefore Medium: it is not universally reachable across all schemas/configurations, but wherever the legacy/collision-permitting configuration exists, the confusion is deterministically triggerable by ordinary client-supplied JSON.

### Recommendation
- Make `CheckFieldJsonNameUniqueness` a hard error for all json_format levels (not just default/`ALLOW`), including proto2/`LEGACY_BEST_EFFORT` and the deprecated short-extension-name printing mode, eliminating the possibility of two distinct fields/extensions sharing one JSON key.
- Fully deprecate and disable `printingDeprecatedNonConformantShortExtensionNames`, since it removes the bracket delimiter that is the only thing keeping the extension and field JSON namespaces disjoint.
- In the JSON parser's alternate-name duplicate detector (Python and other runtimes), canonicalize every incoming key to its resolved `FieldDescriptor` before duplicate-checking, rather than comparing raw key strings, so that different spellings resolving to the same field are also rejected as duplicates instead of silently last-wins.

### Proof of Concept
The existing conformance/unit test already demonstrates the collision end-to-end (not merely theorized): [5](#0-4)

2. Set both: `setExtensionSameName("Field entry")` and `setExtension(JsonTestProto2.extensionSameName, "Extension entry")`.
3. Print with `usingTypeRegistry(registry).printingDeprecatedNonConformantShortExtensionNames()` → produces JSON with two identical keys `"extensionSameName"`.
4. Today, by default, we transform each field name to a CamelCase name that will
always be valid, but not necessarily unique in JSON. We also support a
`json_name` field option to override this for JSON parsing/serialization. This
allows conflicts to potentially arise where many proto fields map to the same
JSON field. Our JSON handling has the following behaviors:

*   All proto messages can be serialized to JSON
    *   Conflicting mappings will produce JSON with duplicate keys
*   All proto messages can be parsed from JSON
    *   Conflicting mappings lead to undefined behavior. While the behavior is
        deterministic in all of the cases we've encountered, it's inconsistent
        across runtimes and unexpected.

void internal::DescriptorBuilder::CheckFieldJsonNameUniqueness(
    const absl::string_view message_name, const DescriptorProto& message,
    const Descriptor* descriptor, bool use_custom_names) {
  absl::flat_hash_map<std::string, JsonNameDetails> name_to_field;
  for (const FieldDescriptorProto& field : message.field()) {
    JsonNameDetails details = GetJsonNameDetails(&field, use_custom_names);
    if (details.is_custom && JsonNameLooksLikeExtension(details.orig_name)) {
      auto make_error = [&] {
        return absl::StrFormat(
            "The custom JSON name of field \"%s\" (\"%s\") is invalid: "
            "JSON names may not start with '[' and end with ']'.",
            field.name(), details.orig_name);
      };
      AddError(message_name, field, DescriptorPool::ErrorCollector::NAME,
               make_error);
      continue;
    }
    auto it_inserted = name_to_field.try_emplace(details.orig_name, details);
    if (it_inserted.second) {
      continue;
    }
    JsonNameDetails& match = it_inserted.first->second;
    if (use_custom_names && !details.is_custom && !match.is_custom) {
      // if this pass is considering custom JSON names, but neither of the
      // names involved in the conflict are custom, don't bother with a
      // message. That will have been reported from other pass (non-custom
      // JSON names).
      continue;
    }
    auto make_error = [&] {
      absl::string_view this_type = details.is_custom ? "custom" : "default";
      absl::string_view existing_type = match.is_custom ? "custom" : "default";
      // If the matched name differs (which it can only differ in case), include
      // it in the error message, for maximum clarity to user.
      std::string name_suffix = "";
      if (details.orig_name != match.orig_name) {
        name_suffix = absl::StrCat(" (\"", match.orig_name, "\")");
      }
      return absl::StrFormat(
          "The %s JSON name of field \"%s\" (\"%s\") conflicts "
          "with the %s JSON name of field \"%s\"%s.",
          this_type, field.name(), details.orig_name, existing_type,
          match.field->name(), name_suffix);
    };

    bool involves_default = !details.is_custom || !match.is_custom;
    if (descriptor->features().json_format() ==
            FeatureSet::LEGACY_BEST_EFFORT &&
        involves_default) {
      // TODO Upgrade this to an error once downstream protos
      // have been fixed.
      AddWarning(message_name, field, DescriptorPool::ErrorCollector::NAME,
                 make_error);
    } else {
      AddError(message_name, field, DescriptorPool::ErrorCollector::NAME,
               make_error);
    }
  }

  /**
   * This test demonstrates the currently known bad behavior of printing extension fields when the
   * name of the extension is the same as the name of a regular field.
   *
   * <p>The JSON serialization of the proto contains a duplicate key. Trying to parse this JSON will
   * result possibly the wrong value being assigned to the regular field and the extension field to
   * be dropped.
   */
  @Test
  public void
      testExtensionFields_printingDeprecatedNonConformantShortExtensionNames_withSameShortName_printsDuplicateJsonKeys()
          throws Exception {
    com.google.protobuf.TypeRegistry registry =
        com.google.protobuf.TypeRegistry.newBuilder()
            .add(TestAllTypesProto2.getDescriptor())
            .build();
    JsonFormat.Printer printer =
        JsonFormat.printer()
            .usingTypeRegistry(registry)
            .printingDeprecatedNonConformantShortExtensionNames();
    JsonFormat.Parser parser = JsonFormat.parser().usingTypeRegistry(registry);
    TestAllTypesProto2 message =
        TestAllTypesProto2.newBuilder()
            .setExtensionSameName("Field entry")
            .setExtension(JsonTestProto2.extensionSameName, "Extension entry")
            .build();

    String json = printer.print(message);
    Message.Builder builder = message.newBuilderForType();
    parser.merge(json, builder);
    Message parsedMessage = builder.build();

    String expectedJsonWithDuplicateKeys =
        "{\n"
            + "  \"extensionSameName\": \"Field entry\",\n"
            + "  \"extensionSameName\": \"Extension entry\"\n"
            + "}";
    assertThat(json).isEqualTo(expectedJsonWithDuplicateKeys);
    // Short names prevent round-trip success, collision occurs due to duplicate json keys.
    assertThat(parsedMessage.toString()).isNotEqualTo(message.toString());
  }
