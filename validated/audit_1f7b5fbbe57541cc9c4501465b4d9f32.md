Let me check how `ReceivedOutput` offsets are used in spending (whether the taproot tweak is accounted for) and the nonce/`actual` combination logic.### Title
`ReceivedOutput::read` accepts untrusted bytes claiming any value/outpoint without binding the claimed output to the registered offset, enabling phantom-balance credit — (`File: networks/bitcoin/src/wallet/mod.rs`)

### Summary
The LBP exploit's core is an accounting divergence: `LBP.balanceOf` reported an inflated, sellable balance that `rawBalanceOf` (the actually-backed balance) did not. Serai's bitcoin wallet has the same structural flaw at its deserialization boundary: `ReceivedOutput::read` reconstructs a "received" output from raw bytes — an `offset`, a `TxOut`, and an `OutPoint` — with no check that the claimed `TxOut` is consistent with the offset, that the outpoint exists, or that the claimed `value` is real. The only integrity check in the entire spend path is the offset↔script_pubkey binding in `SignableTransaction::multisig`; the value and outpoint fields are trusted blindly.

### Finding Description
`ReceivedOutput` stores three fields: `offset: Scalar`, `output: TxOut`, `outpoint: OutPoint`. [1](#0-0)  `read` decodes all three verbatim and returns them — no validation relates them to each other or to chain state. [2](#0-1)  Contrast with the construction path: `Scanner::scan_transaction` only produces a `ReceivedOutput` when `output.script_pubkey` is present in the registered `scripts` map, so the offset is guaranteed to correspond to the output. [3](#0-2)  The deserialize path drops that guarantee.

Downstream, `value()` returns the claimed `output.value`. [4](#0-3)  `SignableTransaction::new` sums `input.output.value` to compute `input_sat`, gates `NotEnoughFunds` on it, and sizes the change output from it. [5](#0-4) [6](#0-5)  `multisig` verifies only `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — the value and outpoint are never checked. [7](#0-6)  The claimed prevouts are then committed into the Taproot sighash via `Prevouts::All`. [8](#0-7) 

Analogously to the bug class: `balanceOf` = the face value `ReceivedOutput` reports; `rawBalanceOf` = what is actually on chain. An unprivileged party who can feed bytes to `ReceivedOutput::read` (e.g., relayed/synced output records, the explicitly in-scope deserialization surface) fabricates `ReceivedOutput` entries with a script_pubkey matching a registered offset (satisfying the only check in `multisig`), an arbitrary large `value`, and a nonexistent or attacker-owned `outpoint`.

### Impact Explanation
Funds are reported received that are not spendable. The wallet's balance becomes inflated exactly as LBP's `balanceOf` did: `SignableTransaction::new` accepts the phantom inputs, computes change/fees against the fake `input_sat`, and the threshold signs a transaction committing (`Prevouts::All`) to prevout values that do not exist on chain. The signed transaction is unbroadcastable/invalid, so every real input co-spent in the same transaction is effectively locked behind the fabricated entry — a persistent denial of service on the multisig's funds and corrupted accounting that can drive incorrect payment/change decisions upstream (e.g., treating attacker-pennies deposits as large balances, releasing goods/services or routing logic against phantom sats before broadcast failure). Severity: Medium — integrity loss and fund liveness DoS; direct theft is bounded because the fabricated prevout makes the transaction invalid on chain.

### Likelihood Explanation
Exploitation requires the attacker to supply serialized `ReceivedOutput` bytes to a wallet/integrator that deserializes rather than scans them — the surface the scope rules explicitly whitelist. It does not require validator collusion, leaked keys, or RPC compromise. Attackers can learn valid script_pubkeys (they are the public deposit addresses) and arbitrary scalars round-trip through `Secp256k1::read_F`, so crafting a passing `offset`+`script_pubkey` pair with a forged `value`/`outpoint` is trivial once the deserialization path is reachable.

### Recommendation
Add a consistency check at the deserialization boundary or at use time: `ReceivedOutput::read` cannot verify offsets alone (it lacks the group key), so `SignableTransaction::new`/`multisig` should additionally reject outputs whose values/outpoints weren't produced by `Scanner::scan_transaction` — e.g., have callers pass only scanner-derived outputs, or have `multisig` confirm the `prevouts` against chain data (the sighash already commits to them, but the check should occur before accounting decisions in `new`/`needed_fee`/`fee` consume the claimed values).
