## Analysis

The core broken invariant from the Connext report: **crediting an internal ledger with the "expected" amount, while accounting nothing for what was *actually* received**, creates a mismatch between recorded liabilities and real custody, leading to insolvency where later legitimate operations drain balances belonging to other users/orders.

I found a direct structural analog in `evm/tron/contracts/apps/IntentGatewayV2.sol`. Notably, the primary EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against exactly this class of bug — it explicitly snapshots balances before/after every token movement and mutates `order.inputs[i].amount` to the *actually received* amount before crediting escrow (see `evm/src/apps/IntentGatewayV2.sol:260-280` and `:289-291`, confirmed by the fee-on-transfer tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2256-2308`). The Tron variant was not updated with this fix and retains the vulnerable unconditional-crediting pattern.

### Title
IntentGatewayV2 (Tron) predispatch escrow crediting ignores actual tokens received, causing escrow over-crediting and fund drain from other orders - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron `IntentGatewayV2.placeOrder`, the predispatch escrow path credits `_orders[commitment][token]` with `reducedInputs[i].amount` — a value derived purely from the user-declared `order.inputs[i].amount` — without ever measuring what the gateway contract actually received after the two-hop transfer (`user → dispatcher → gateway`). For any token whose transferred amount can differ from the nominal amount (fee-on-transfer tokens, deflationary/tax tokens, rebasing tokens), the escrow ledger records more than the contract actually holds. This mirrors the Connext bug exactly: a `withdraw()`-equivalent (`transfer`) call's actual output is not checked/used, only the requested amount is bookkept.

### Finding Description
In `placeOrder`'s predispatch branch: [1](#0-0) 

```solidity
Call[] memory transferCalls = new Call[](inputsLen);
for (uint256 i; i < inputsLen;) {
    ...
    balance = IERC20(token).balanceOf(dispatcher);
    if (balance < requiredAmount) revert InvalidInput();
    transferCalls[i] = Call({
        to: token, value: 0,
        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
    });
    uint256 dust = balance - requiredAmount;
    if (dust > 0) emit DustCollected(token, dust);

    // Store reduced amount (after protocol fees) in escrow
    _orders[commitment][token] += reducedInputs[i].amount;
    ...
}
// Execute transfer calls from call dispatcher
ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls));
```

The check `balance < requiredAmount` only validates the `dispatcher`'s balance *before* the sweep transfer executes. The `transferCalls[i]` sends `balance` from `dispatcher` to `address(this)` (the gateway), but this transfer call is dispatched *after* the loop has already unconditionally incremented `_orders[commitment][token] += reducedInputs[i].amount`. There is no re-measurement of the gateway's actual token balance after the sweep (unlike the mainline EVM contract, which snapshots `balancesBefore[i]` and computes `received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]` per `evm/src/apps/IntentGatewayV2.sol:229-280`).

If `token` is a fee-on-transfer/tax token (very common on BSC/Tron-adjacent stablecoin forks and meme tokens), the gateway's real balance increase from this `transfer` call will be strictly less than `balance`, hence less than `reducedInputs[i].amount`. The `_orders` mapping — the sole source of truth used by `withdraw()`/`_execute()` for later `RedeemEscrow`/`RefundEscrow` payouts — is now inflated relative to the contract's actual token holdings.

### Impact Explanation
Because `_orders[commitment][token]` is a shared accounting map across all orders for a given token, and the actual ERC-20 balance held by the gateway is a single pooled value, over-crediting one order's escrow entry creates a systemic deficit: the sum of all `_orders[*][token]` entries can exceed `IERC20(token).balanceOf(gateway)`. On the withdrawal path: [2](#0-1) 

`withdraw()` performs a plain `token.call(transfer(beneficiary, amount))` for whatever amount was recorded, with no check that the contract's real balance covers it. Whichever orders happen to be redeemed first will succeed and drain real tokens that are needed to back other (unfilled/uncancelled) orders' escrow claims — this is fund loss/lock for those later victims exactly as described in the Connext finding ("partial insolvency ... bridge functionality can become unavailable"). This is reachable by any unprivileged user simply by placing an order using the `predispatch` feature with a fee-on-transfer token, with no relayer, prover, or admin compromise required.

### Likelihood Explanation
Any user can trigger this by calling `placeOrder()` with `predispatch.call`/`predispatch.assets` populated for a token that charges a transfer fee (fee-on-transfer/tax/deflationary token) — no special privileges are needed, and this is exactly the case the mainline EVM contract added explicit tests and fixes for (`testPlaceOrder_FeeOnTransferToken_Predispatch`, `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2437`), confirming this is a realistic, anticipated token class for this protocol. The Tron contract, however, has no equivalent post-sweep balance verification.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `address(this)`'s (or the relevant balance) before dispatching `transferCalls`, execute the sweep, then compute `received = balanceAfter - balanceBefore` per token and credit `_orders[commitment][token]` with `received` (minus protocol fee applied to `received`, not to the nominal `order.inputs[i].amount`) instead of the pre-fee `reducedInputs[i].amount`. Any excess above the required amount should be emitted as dust exactly as the EVM version does, and the commitment/escrow bookkeeping should be computed from the actually-received amounts, not the user-declared ones.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with `dispatcher` set to a `CallDispatcher`.
2. Deploy a fee-on-transfer ERC-20 `FOT` (e.g. 1% fee), mint `user` `10000 FOT`.
3. `user` calls `placeOrder` with `order.predispatch.assets = [{FOT, 1000}]` and `order.inputs = [{FOT, 990}]` (the amount expected to land on `dispatcher` after the first fee-on-transfer hop), `predispatch.call` a no-op dispatch.
4. Inside `placeOrder`:
   - `dispatcher` receives `990 FOT` (after 1% fee on the `user → dispatcher` transfer).
   - `balance = IERC20(FOT).balanceOf(dispatcher) = 990`; `requiredAmount = 990`; `dust = 0`.
   - `_orders[commitment][FOT] += reducedInputs[0].amount` credits `990` (or slightly less if protocol fee bps > 0).
   - The sweep `transfer(gateway, 990)` from `dispatcher` executes afterward and, due to the 1% fee, the gateway actually receives only `980.1 FOT`.
5. `_orders[commitment][FOT] == 990` but `IERC20(FOT).balanceOf(gateway) == 980.1` — a `9.9 FOT` deficit is now baked into the escrow ledger for this order alone; the deficit compounds across every predispatch order routed through a fee-charging token, while `withdraw()`/`_execute()` will still attempt to pay out the full recorded `990`, drawing the shortfall from other orders' pooled balance.
