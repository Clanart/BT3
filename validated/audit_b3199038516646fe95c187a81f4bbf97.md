### Title
`placeOrder` predispatch escrow crediting uses total `CallDispatcher` balance instead of the amount actually produced by the predispatch call, letting a caller claim escrow funded by stray/residual tokens - (`evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch branch determines how much of each input token to sweep from the shared `CallDispatcher` and credit to the caller's own order by reading `IERC20(token).balanceOf(dispatcher)` — the dispatcher's *total* balance — rather than the amount actually produced by the predispatch call the caller just triggered. This is the same broken invariant as the TreehouseRouter bug: an operation's output is substituted with a raw balance read of a shared/external-facing contract, so any tokens that already sit there (leftover dust from a previous order, a failed sweep, or an accidental direct transfer to the publicly known `CallDispatcher` address) get folded into whichever order happens to run next.

### Finding Description
In the predispatch branch of `placeOrder`: [1](#0-0) 

the code reads `balance = IERC20(token).balanceOf(dispatcher)` for the *entire* dispatcher balance of the token — not a before/after delta on the dispatcher itself — and requires only `balance >= requiredAmount`. It then builds a `transfer` call that moves the dispatcher's *whole* balance back to the gateway: [2](#0-1) 

Once the funds land in the gateway, the code computes `received = balanceOf(gateway) - balancesBefore[i]` and credits it to `order.inputs[i].amount` (crediting only the caller-requested amount and shunting any excess to `DustCollected`):

```
if (received > order.inputs[i].amount) {
    dust = received - order.inputs[i].amount;
    emit DustCollected(token, dust);
} else {
    order.inputs[i].amount = received;
}
```

The delta computed on the gateway side (`received`) does correctly avoid crediting pre-existing gateway balance, but the *source-side* measurement is wrong: the amount actually swept out of the dispatcher is derived from `balanceOf(dispatcher)`, not from what the predispatch call itself produced. `CallDispatcher` is a single, permissionlessly-callable, address-known utility contract shared by every order (predispatch and postdispatch phases across all users), and per the intended dust-sweep design it is not supposed to retain balances between calls (`_execute` in `IntentsBase.sol` sweeps any dispatcher residue after fills as protocol dust: [3](#0-2) ). If — for any reason (a prior predispatch that reverted partway leaving unswept tokens, a fee-on-transfer/rounding remainder from another user's earlier order, or a plain accidental direct transfer to the well-known `CallDispatcher` address) — the dispatcher holds a residual balance of a token when a new `placeOrder` predispatch runs for that same token, the new caller's `balance` read picks up that residue and the entire amount (up to `order.inputs[i].amount`) is silently escrowed as *that caller's own order input*, without the caller having actually funded it through the predispatch swap. The `if (balance < requiredAmount) revert InvalidInput();` guard only enforces a lower bound; it does nothing to verify that the swept balance originated from this transaction's own predispatch call, which is exactly the class of defect described in the TreehouseRouter report (returning a raw balance instead of the value actually produced by the specific operation).

The tron variant of the contract has the identical pattern: [4](#0-3) 

### Impact Explanation
This lets an unprivileged caller obtain escrowed order-input credit funded by tokens they never contributed, at the expense of whoever's tokens were sitting in (or accidentally sent to) the shared `CallDispatcher`. Since escrowed inputs are exactly what solvers/relayers redeem after a fill (`withdraw`/`_withdraw` pay out `_orders[commitment][token]` to the beneficiary), a caller who engineers or opportunistically finds a stray dispatcher balance can place — and later have filled/settled — an order whose input side is effectively free, causing a real loss of funds for whoever's tokens ended up misappropriated into that order's escrow. This matches the bounty's "stealing or loss of funds" / "unauthorized transaction or execution" impact classes and requires no malicious peer, relayer, prover, or admin — only a public call to `placeOrder`.

### Likelihood Explanation
Exploitability depends on the `CallDispatcher` actually holding a residual balance of the targeted token at the moment `placeOrder` is called with matching predispatch parameters. This can happen through normal operational conditions (a prior predispatch execution that leaves dust due to fee-on-transfer tokens, partial swap slippage, or an interrupted multi-call sequence) rather than requiring a malicious relayer/prover — an attacker only needs to monitor the dispatcher's token balances (a public, non-privileged read) and race a `placeOrder` call before the dust is naturally swept elsewhere. This is a data-validation gap in a public entrypoint, not a front-running-only or peer-compromise scenario.

### Recommendation
Do not credit `order.inputs[i].amount` from `IERC20(token).balanceOf(dispatcher)`. Instead, snapshot the dispatcher's balance for each predispatch token *before* dispatching the predispatch call, and derive the swept amount from the delta (`balanceOf(dispatcher)_after − balanceOf(dispatcher)_before`), mirroring the delta-based measurement already correctly used on the gateway side. Only the amount actually produced by this transaction's own predispatch call should ever be escrowed as the caller's order input; any pre-existing dispatcher balance should be swept separately and unconditionally to protocol dust (or a rescue mechanism), never credited to a caller's order.

### Proof of Concept
1. Assume the `CallDispatcher` at a known, fixed address ends up holding `X` units of token `T` (e.g., leftover from a previous predispatch swap that produced slightly more output than a prior order's `requiredAmount`, or from direct accidental transfer since the dispatcher address is publicly documented).
2. Attacker calls `placeOrder` with `predispatch.assets`/`predispatch.call` configured to trigger any swap that outputs token `T`, and `order.inputs[0] = {token: T, amount: X}` (matching or less than the residual `X`).
3. In `_execute`'s predispatch handling, `balance = IERC20(T).balanceOf(dispatcher)` reads `X` (which already sat there before this predispatch call even ran, plus whatever the attacker's own swap produced, e.g. `0` for a swap into an unrelated token, or an amount the attacker under-funds).
4. The full `balance` (`X`) is swept to the gateway via the `transfer` call: [5](#0-4) .
5. `received = X` and since `X <= order.inputs[0].amount`, `order.inputs[0].amount = X` is escrowed under the attacker's commitment — funded entirely by the pre-existing residual balance rather than by the attacker's own predispatch call output.
6. The attacker (or a colluding/self-solver) later fills and redeems this escrow via `_withdraw`, receiving `X` units of `T` they never actually contributed.
