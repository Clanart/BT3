### Title
Divide-by-zero DoS via deduplicated spend cost fully offsetting item cost in block-building loop - (File: chia/full_node/mempool.py)

### Summary
`Mempool.create_bundle_from_mempool_items()` computes `item_cost = cost - cost_saving` for every mempool item scanned while building a block, and immediately uses it as a divisor in a log-formatting call: `fee / item_cost`. When a mempool item's entire CLVM cost is attributable to a single coin spend that has already been deduplicated against an earlier-processed item with an identical solution, `cost_saving` can equal `cost` exactly, making `item_cost == 0` and triggering a `ZeroDivisionError`.

### Finding Description
`IdenticalSpendDedup.get_deduplication_info()` accumulates `cost_saving` from `DedupCoinSpend.cost` for every coin whose solution matches a coin previously seen in the same block-building pass: [1](#0-0) 

That `cost_saving` value equals the exact `cost` recorded for that coin spend the first time it was seen: [2](#0-1) 

In `create_bundle_from_mempool_items()`, the item's total cost (`item.conds.cost`, i.e. `cost`) is reduced by `cost_saving` to get `item_cost`, and that value is used as a divisor before any zero-check: [3](#0-2) 

For a mempool item consisting of a single dedup-eligible coin spend, `item.conds.cost` equals exactly the `BundleCoinSpend.cost` of that one spend — the same value stored as `DedupCoinSpend.cost` when it was first encountered. `check_removals()` in the mempool admission path explicitly permits two mempool items to coexist when both spend the same coin with `eligible_for_dedup=True` and an identical solution (this is the "DEDUP" no-conflict case, documented in `.cursor/context/mempool.md`). An attacker can therefore submit two single-coin-spend bundles, `B1` and `B2`, that spend the same dedup-eligible coin with the identical solution but different fees, and have both accepted into the mempool without conflict. During the next `create_bundle_from_mempool_items()` pass, the higher fee-per-cost item is processed first (`cost_saving = 0`, its cost is cached), and the second item is then processed with `cost_saving` equal to its full `cost`, producing `item_cost = 0` and a `ZeroDivisionError` at the `fee / item_cost` log-format expression, well before block construction completes.

This is directly analogous to the referenced Wireshark CVE-2016-6505 divide-by-zero: a crafted, otherwise well-formed input (a spend bundle) drives an internal size/cost field to exactly zero, which is then used as an unchecked divisor, causing a crash in a core processing routine that is invoked automatically (block building), not merely something the attacker must specifically request.

### Impact Explanation
An unprivileged spend-bundle submitter can craft two ordinary spend bundles (no unusual permissions required — only mempool acceptance of dedup-eligible spends, which is a supported/normal mempool feature) that, once both sit in the mempool together, cause `Mempool.create_bundle_from_mempool_items()` to raise an unhandled `ZeroDivisionError` the next time the full node attempts to build a block from the mempool. This halts block-template generation from the affected mempool state, a spend-triggered transaction-processing halt, which matches the accepted impact category ("spend-triggered transaction-processing halt").

### Likelihood Explanation
Likelihood depends on:
1. Confirming that dedup-eligible spends (singleton/CAT dedup-eligible puzzles) can indeed produce a mempool item whose *entire* `conds.cost` is contributed by a single coin spend (no other coins in the bundle) — this appears achievable since dedup eligibility is evaluated per-coin-spend and bundles with a single spend are permitted.
2. Confirming `create_bundle_from_mempool_items()` (as opposed to the newer `create_block_generator2()`) is still reachable in the live block-building path. I was not able to fully confirm this within available tool budget — the caller in `mempool_manager.py` still references it, and both functions coexist, but I could not verify from the index whether the older path is actively invoked during normal farming/full-node operation versus only used in specific fallback/test scenarios.

Because of this open verification gap around which code path (`create_bundle_from_mempool_items` vs. `create_block_generator2`) is exercised in production block assembly, I flag this finding with **moderate confidence** rather than certainty. If `create_bundle_from_mempool_items` is dead/legacy code no longer called from the main full-node block-farming flow, the practical severity would be much lower (test-only or unreachable).

### Recommendation
Guard the divisor before use, e.g. `fee / item_cost if item_cost > 0 else float('inf')`, or restructure the log statement to avoid the division entirely when `item_cost == 0`. More fundamentally, treat `item_cost == 0` as a defensive-skip case (log and `continue`) rather than allowing a zero-cost item to flow further into block-size accounting, since a zero-cost item is not physically meaningful for cost-based block limits.

### Proof of Concept
1. Fund two coins is not required — submit two spend bundles `B1` and `B2` that each spend the **same** coin `C` (a dedup-eligible puzzle, e.g. matching solution to a supported singleton/CAT dedup pattern) with an **identical solution**, but with different fee (achieved via different removal/addition sets elsewhere — but to keep the item single-spend, encode the fee difference in the coin amount consumed vs. created by the identical puzzle/solution, or otherwise ensure two single-spend items with equal solution but distinguishable fees are both admitted).
2. Both are accepted into the mempool without conflict because `check_removals()` treats same-coin/same-solution/dedup-eligible spends as non-conflicting.
3. Trigger block building; `create_bundle_from_mempool_items()` processes the higher-priority item first (caching its full cost as the `DedupCoinSpend`), then processes the second item, computing `item_cost = cost - cost_saving = 0`, and crashes at `fee / item_cost`. [4](#0-3) [5](#0-4)

    def get_deduplication_info(
        self, *, bundle_coin_spends: dict[bytes32, BundleCoinSpend]
    ) -> tuple[list[CoinSpend], uint64, int, int, list[Coin], dict[bytes32, DedupCoinSpend]]:
        """
        Checks all coin spends of a mempool item for deduplication eligibility and
        provides the caller with the necessary information that allows it to perform
        identical spend aggregation on that mempool item if possible.

        This does not mutate the deduplication state. The returned state update
        must be explicitly committed by the caller via
        `update_deduplication_spends()` once the item is confirmed to be included,
        so that items which are processed but ultimately dropped don't leave stale
        deduplication entries behind.

        Args:
            bundle_coin_spends: the mempool item's coin spends data

        Returns:
            list[CoinSpend]: list of unique coin spends in this mempool item
            uint64: the cost we're saving by deduplicating eligible coins
            int: the atoms we're saving by deduplicating eligible coins
            int: the pairs we're saving by deduplicating eligible coins
            list[Coin]: list of unique additions in this mempool item
            dict[bytes32, DedupCoinSpend]: the deduplication state update to
                commit via `update_deduplication_spends()` if the item ends up
                included

        Raises:
            ValueError to skip the mempool item we're currently in, if it's
            attempting to spend an dedup coin with a different solution than the
            one we're already deduplicating on.
        """
        cost_saving = 0
        atoms_saving = 0
        pairs_saving = 0
        unique_coin_spends: list[CoinSpend] = []
        unique_additions: list[Coin] = []
        # Map of coin ID to deduplication information
        new_dedup_spends: dict[bytes32, DedupCoinSpend] = {}
        # See if this item has coin spends that are eligible for deduplication
        for coin_id, spend_data in bundle_coin_spends.items():
            if not spend_data.eligible_for_dedup:
                unique_coin_spends.append(spend_data.coin_spend)
                unique_additions.extend(spend_data.additions)
                continue
            # See if we processed an item with this coin before
            dedup_coin_spend = self.deduplication_spends.get(coin_id)
            if dedup_coin_spend is None:
                # We didn't process an item with this coin before. If we end up including
                # this item, add this pair to deduplication_spends
                new_dedup_spends[coin_id] = DedupCoinSpend(
                    spend_data.coin_spend.solution,
                    spend_data.cost,
                    spend_data.atom_count,
                    spend_data.pair_count,
                )
                unique_coin_spends.append(spend_data.coin_spend)
                unique_additions.extend(spend_data.additions)
                continue
            # See if the solution was identical
            if dedup_coin_spend.solution != spend_data.coin_spend.solution:
                # This should not happen. DEDUP spends of the same coin with
                # different solutions are rejected in check_removals().
                raise SkipDedup("Solution is different from what we're deduplicating on")
            cost_saving += dedup_coin_spend.cost
            atoms_saving += spend_data.atom_count
            pairs_saving += spend_data.pair_count
        return (
            unique_coin_spends,
            uint64(cost_saving),
            atoms_saving,
            pairs_saving,
            unique_additions,
            new_dedup_spends,
        )
