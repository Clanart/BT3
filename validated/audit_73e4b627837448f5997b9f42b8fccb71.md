### Title
Selective-line commit stages a freshly-fetched diff against a stale line-index selection, silently committing unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
The bug report's broken invariant is that a value is fetched, used to compute a delta, and then applied non-atomically — allowing the underlying state to change between the read and the write, so the applied delta no longer matches what was validated/shown. GitHub Desktop's partial (line-by-line) commit/staging path has the same class of flaw: the user reviews and selects individual diff lines in the UI against one snapshot of `git diff`, but `applyPatchToIndex` independently re-fetches the working directory diff at commit time and blindly re-applies the old line-index selection to it.

### Finding Description
When a user stages/commits only some lines of a file, the UI computes a diff once (`getWorkingDirectoryDiff`) and stores a `DiffSelection` keyed by absolute line index within that specific diff [1](#0-0) . Later, when the commit is actually created, `createCommit` calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex` [2](#0-1) [3](#0-2) .

Critically, `applyPatchToIndex` does **not** reuse the diff the user reviewed. It re-fetches a brand-new diff from disk right before formatting the patch: [4](#0-3) 

`formatPatch` then walks this newly-fetched diff's hunks and decides which lines to include purely by calling `file.selection.isSelected(absoluteIndex)` [5](#0-4)  — i.e., it trusts that the line-index positions in the old (reviewed) diff still line up with the line-index positions in the new (re-fetched) diff. There is no hash/content check, no diff-identity check, and no re-validation that the selection is still valid for the current file content.

If the file on disk changes between the moment the diff was rendered/selected and the moment the commit runs (a window that can be seconds to minutes — e.g. an editor auto-save, a build tool, a linter/formatter run, a git hook, a background process, or content restored by a `checkout`/`stash pop`/LFS smudge filter triggered by another Desktop background operation), the hunk boundaries and absolute line indices shift. `formatPatch` will then apply the user's old selection indices to the wrong lines of the new diff, and `git apply --cached` will stage a patch whose content the user never reviewed or intended to select.

This mirrors the reported invariant violation exactly: "retrieval" (diff fetch for display) and "increment/apply" (diff fetch + patch generation for staging) are not atomic, and nothing detects that the underlying value changed in between.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A user could unknowingly commit and push lines/content they explicitly did not select (or fail to commit lines they did select), based on stale index math from a diff that no longer reflects the working tree. In collaborative or CI-integrated workflows this can leak content the user intended to exclude (e.g., partially-selected secrets, debug code, or WIP fragments) into a commit, or omit intended changes without any error being surfaced to the user — the operation completes "successfully."

### Likelihood Explanation
The race window is not contrived: any external mutation of the file between the diff being rendered in the Changes view and the user clicking "Commit" (auto-formatters, editors, build watchers, git hooks such as `pre-commit` normalizing whitespace, or another Desktop-triggered background git operation) is enough to trigger the mismatch. No admin rights, local malware, or unnatural user steps are required — this is a normal editing workflow with partial-line staging, which is a commonly used Desktop feature.

### Recommendation
`applyPatchToIndex`/`stageFiles` should not silently re-derive a fresh diff and reuse an old line-index selection against it. Instead:
- Bind the `DiffSelection` to an identity/hash of the diff it was computed against (e.g., diff content hash or file mtime/size at diff time), and refuse to apply the patch if the current working-directory diff no longer matches that identity.
- If a mismatch is detected, re-render the diff, clear or re-map the stale selection, and require the user to re-confirm their line selection before staging/committing.
- Add regression tests that mutate the file on disk between diff-fetch and `applyPatchToIndex` to ensure the stale selection is rejected rather than silently misapplied.

### Proof of Concept
1. Modify a tracked file to introduce two separate hunks of changes.
2. In Desktop's Changes view, open the file diff and select only specific lines in the second hunk to be committed (this fixes `DiffSelection` absolute indices against the diff fetched at that moment).
3. Before pressing "Commit", externally modify the file (e.g., an editor auto-save inserts/removes a line above the selected hunk, or a `pre-commit` hook/formatter reformats part of the file) so hunk boundaries/line offsets shift.
4. Press "Commit". `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` (now reflecting the just-changed file) and calls `formatPatch` with the *original* `file.selection`, whose absolute indices now point at different lines.
5. Inspect the resulting commit: it contains lines that were never explicitly selected by the user (or omits lines that were), even though Desktop reports success with no warning.
