## Title
SSH `keyboard-interactive` prompt text is trusted verbatim as the TokenStore lookup key, letting a malicious SSH server harvest passwords stored for other hosts - (File: `app/src/lib/trampoline/trampoline-askpass-handler.ts`)

## Summary
`handleSSHUserPassword` treats the literal text of an SSH "password" prompt as an authenticated statement of *which host* the credential belongs to. That text, however, is not something GitHub Desktop derives from the real connection target — for `keyboard-interactive` authentication, OpenSSH lets the *remote server* supply the prompt strings shown to the user/askpass handler verbatim. A malicious SSH remote can therefore emit a prompt whose text is `"git@github.com's password: "` while the actual TCP connection is to the attacker's own host, and Desktop will happily look up and hand back the password it previously stored for the real `github.com` account.

## Finding Description
When Desktop performs a git operation over SSH, it sets `SSH_ASKPASS` to `desktop-askpass-trampoline`, which forwards `argv[1]` (the exact prompt string the `ssh` client wants to display) unmodified over a local TCP socket, as seen in `runTrampolineClient` in `vendor/desktop-trampoline/src/desktop-trampoline.c`. [1](#0-0) 

This raw argument is parsed as-is by `TrampolineCommandParser` with no validation of its content, and delivered to the registered `AskPass` handler. [2](#0-1) 

In `createAskpassTrampolineHandler`, any parameter ending in `"'s password: "` is routed to `handleSSHUserPassword`, which parses out the "username" purely via the greedy regex `/^(.+@.+)'s password: $/` and immediately uses it as the TokenStore lookup key, with **no correlation to the actual host/operation the trampoline token (`operationGUID`) is associated with**: [3](#0-2) 

```
async function handleSSHUserPassword(operationGUID: string, prompt: string) {
  const promptRegex = /^(.+@.+)'s password: $/
  const matches = promptRegex.exec(prompt)
  ...
  const username = matches[1]
  const storedPassword = await getSSHUserPassword(username)
  ...
}
```

`getSSHUserPassword` / `setSSHUserPassword` use this string directly as the keytar/TokenStore `login` key, scoped only by the fixed store name `"SSH user password"` — there is no per-host namespace, no verification against the SSH host actually being contacted, and no check that this text originated from the local `ssh` client rather than from data the remote server chose. [4](#0-3) 

Critically, this prompt text is not guaranteed to be generated solely by the local OpenSSH binary from the real connection parameters. OpenSSH's `keyboard-interactive` authentication method (RFC 4256) allows the *server* to send arbitrary "name"/"instruction"/prompt strings as part of `SSH2_MSG_USERAUTH_INFO_REQUEST`, and the OpenSSH client displays these prompts to the user (and to `SSH_ASKPASS`) verbatim. Nothing in the reviewed code path validates that the string handed to `handleSSHUserPassword` corresponds to the host that the current git operation (`operationGUID`) is actually connecting to. The comment in the sibling function even documents the assumption "usually in the form of `user@hostname`" without ever verifying it against the real target. [5](#0-4) 

As a result, if the user has previously stored a password under key `git@github.com` (via a legitimate password-authenticated SSH remote), an attacker-controlled SSH server reached during any subsequent fetch/push can issue a keyboard-interactive challenge whose literal prompt text is `git@github.com's password: `. The regex reconstructs the exact string `git@github.com`, `getSSHUserPassword('git@github.com')` returns the previously-stored secret, and that secret is sent back as the answer to the attacker's own keyboard-interactive challenge — i.e., directly disclosed to the attacker's SSH server.

## Impact Explanation
This breaks the intended host-scoping invariant of the SSH credential store and results in credential exfiltration to an attacker-controlled remote: a password meant for one host (e.g. `git@github.com`) can be disclosed to a completely different, attacker-controlled remote purely by that remote crafting its authentication prompt text, with no need to compromise or spoof the real target host at the network level. This matches the "credential/token exfiltration" impact category for an attacker-controlled git remote response.

## Likelihood Explanation
Exploitation requires:
1. The victim to have previously stored an SSH user/password credential (`"Remember password"`) for some real host — a common and encouraged workflow for SSH password auth.
2. The victim to perform a fetch/push against a remote pointing at an attacker-controlled SSH server (e.g., a remote added via a malicious cloned repository, submodule, or a link the user is guided to add) — this is squarely within the accepted attacker capability set (attacker-controlled git remote/response).
3. The attacker's SSH server to offer `keyboard-interactive` authentication with a prompt string crafted to match the previously-stored key (an easily guessable format such as `<login>@<well-known-host>'s password: `, e.g. `git@github.com's password: `).

No admin rights, local access, or social engineering beyond "user performs a git operation against attacker's remote" is needed, making this a realistically triggerable, moderate-likelihood issue.

## Recommendation
Do not derive the TokenStore key solely from unauthenticated prompt text. Bind the SSH password lookup/storage key to the actual host/operation context known to Desktop (e.g., the trampoline `operationGUID`'s associated repository/remote host, verified independently of the ssh-supplied prompt string), or at minimum validate that the host portion of the parsed `user@host` matches the real destination host of the current git operation before using it as a TokenStore key.

## Proof of Concept
1. User connects once via SSH password auth to `git@github.com`, checks "Remember password" so `TokenStore` stores password under key `git@github.com` in the `"SSH user password"` store (`setSSHUserPassword`).
2. User later fetches/pushes to a different repository whose remote is `ssh://attacker@evil.example.com/...`.
3. `evil.example.com`'s SSH server offers `keyboard-interactive` auth and sends an `INFO_REQUEST` with prompt text literally `git@github.com's password: `.
4. Desktop's SSH_ASKPASS trampoline forwards this string unmodified to `handleSSHUserPassword`; the regex extracts `git@github.com`; `getSSHUserPassword('git@github.com')` returns the stored GitHub password.
5. Desktop supplies that password as the answer to the attacker's keyboard-interactive prompt, sending the victim's GitHub SSH password to `evil.example.com`.

```typescript
async function handleSSHUserPassword(operationGUID: string, prompt: string) {
  const promptRegex = /^(.+@.+)'s password: $/

  const matches = promptRegex.exec(prompt)
  if (matches === null || matches.length < 2) {
    return undefined
  }

  const username = matches[1]

  const storedPassword = await getSSHUserPassword(username)
  if (storedPassword !== null) {
    // Keep this stored password around in case it's not valid and we need to
    // delete it if the git operation fails to authenticate.
    setMostRecentSSHUserPassword(operationGUID, username)
    return storedPassword
  }
```

```typescript
    return TokenStore.getItem(SSHUserPasswordTokenStoreKey, username)
```
