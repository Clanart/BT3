### Title
Payout attribution relies solely on attacker-controlled OP_RETURN data, allowing a withdrawer to frame an uninvolved operator as the payer - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` attributes a payout to an operator purely by parsing the first OP_RETURN output of whatever transaction spends the registered withdrawal UTXO, with no cryptographic check that the named operator actually signed, funded, or authorized that transaction. Since the withdrawal UTXO's spending authorization is controlled by the withdrawer (the attacker) via a signature that (per the described `SIGHASH_SINGLE|ANYONECANPAY`-style construction) does not cover extra outputs, the attacker can append an arbitrary OP_RETURN naming any operator's `xonly_pk` and get that operator falsely credited as the payer.

### Finding Description
The binding claimed by the protocol is:
`withdrawals.payout_payer_operator_xonly_pk[idx] == xonly_pk of the operator whose own funds paid output_txout to the withdrawer`

In `Verifier::update_finalized_payouts` [1](#0-0) , the verifier:
1. Fetches candidate payout txids strictly from `Database::get_payout_txs_for_withdrawal_utxos`, i.e., whatever transaction spends the registered withdrawal UTXO for `idx`.
2. Locates the first OP_RETURN output via `get_first_op_return_output` and parses it with `parse_op_return_data` into an `XOnlyPublicKey` [2](#0-1) .
3. Writes this parsed key directly into the DB as `operator_xonly_pk` for that withdrawal index via `update_payout_txs_and_payer_operator_xonly_pk`, with no signature verification, no check that the named operator's key ever signed this specific transaction, and no check that this is the canonical/first spend intended by the protocol [3](#0-2) .

Downstream, `PayoutCheckerTask::run_once` queries unhandled payouts strictly by `operator_xonly_pk` via `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, on a match, calls `Operator::handle_finalized_payout`, entering that operator's reimbursement/kickoff path [4](#0-3) . There is no re-verification anywhere in this call chain that the operator whose key was parsed from the OP_RETURN actually supplied the funds in `output_txout` or co-signed the transaction.

Because the withdrawal UTXO is chosen and controlled by the withdrawer (the attacker), and the pre-agreed signature securing the input is (per the threat model) a `SIGHASH_SINGLE|ANYONECANPAY`-style signature that only commits to the input and a specific paid output (not to additional outputs), the attacker can assemble their own transaction that spends their withdrawal UTXO, pays themselves (or anywhere), and appends a spoofed OP_RETURN copied from a real prior payout by operator A. This transaction requires no participation, signature, or funds from operator A at all.

None of the existing guards checked prevent this: `Verifier::is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, `verify_storage_proofs`, and `SPV::verify` operate on deposit/withdrawal registration and later kickoff/challenge flows, but none of them re-derive or validate `operator_xonly_pk` against an actual signature or funding proof at the point it is recorded in `update_finalized_payouts`.

### Impact Explanation
If exploited, an operator (A) is enrolled into the reimbursement/kickoff path for a withdrawal it never funded, matching the Critical category "an operator reimbursed for a payout it never funded." This is repeatable across any withdrawal index and any operator whose `xonly_pk` has appeared in a prior legitimate OP_RETURN (which is public on-chain data, trivially harvestable by the attacker). The blast radius spans every operator and withdrawal in the system, since the attribution logic contains no per-transaction authenticity check tying the named key to actual signing/funding.

### Likelihood Explanation
The attacker only needs to be an ordinary withdrawer: deposit into the bridge, call `withdraw` on the Citrea contract to register a withdrawal UTXO under their control, and later broadcast a self-crafted spend of that UTXO with a copied OP_RETURN. This requires no verifier, operator, or aggregator privileges, no key compromise, and costs only ordinary Bitcoin transaction fees. It is fully repeatable for every withdrawal the attacker initiates.

### Recommendation
Do not treat the OP_RETURN-embedded xonly_pk as authoritative proof of who funded the payout. Require the payout transaction to be co-signed or otherwise cryptographically bound to the claiming operator (e.g., verify a Schnorr signature from the operator over the payout transaction, or bind attribution to the presigned transaction graph created during `Operator::withdraw` rather than parsing arbitrary output data from whatever transaction happens to spend the UTXO) before writing `operator_xonly_pk` in `update_payout_txs_and_payer_operator_xonly_pk`.

### Proof of Concept
Add a test under `core/src/test/deposit_and_withdraw_e2e.rs` (background-agent-executed, not part of this audit's in-repo fix) that:
1. Registers a withdrawal UTXO controlled by a test "attacker" keypair (not any operator's key).
2. Constructs and broadcasts a payout-shaped transaction spending that UTXO, paying the attacker's own address, with an OP_RETURN containing a real operator A's `xonly_pk` copied from a separate genuine payout, while operator A never signs or funds this transaction.
3. Mines it and runs `Verifier::update_finalized_payouts` / `get_payout_info_from_move_txid`.
4. Asserts `payout_payer_operator_xonly_pk == Some(A's xonly_pk)` even though A never funded/signed the transaction, demonstrating the equality binding is broken — establishing that attribution is spoofable and that `PayoutCheckerTask` would then invoke `handle_finalized_payout` for operator A for a payout it never made.

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;
