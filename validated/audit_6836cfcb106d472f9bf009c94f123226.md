### Title
`ReceivedOutput::read` accepts attacker-supplied outputs as spendable without validating the offset/script binding or the outpoint - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The audited bug class is a privileged-appearing acceptance function (`setGoalReached()`) that marks a goal/state as achieved without verifying the required precondition (`totalRaised >= fundraisingGoal`), permanently disabling the refund path and finalizing incorrect proportions. The analogous shape in Serai is `ReceivedOutput::read`, which deserializes untrusted bytes and produces a `ReceivedOutput` — the object downstream code treats as a confirmed, spendable deposit — without performing any of the validity checks that the honest scanner path enforces.

### Finding Description
When `Scanner::scan_transaction` produces a `ReceivedOutput`, two invariants hold by construction: the output's `script_pubkey` is a P2TR script for `key + offset·G` (established in `Scanner::register_offset`/`scan_transaction`, mod.rs:180-214), and the `outpoint` references a real transaction output that was observed on-chain. `ReceivedOutput::read` (mod.rs:122-134) reconstructs a `ReceivedOutput` from a byte stream — reading an arbitrary `Scalar` offset via `Secp256k1::read_F`, then an arbitrary `TxOut` and `OutPoint` via consensus decoding — and returns it as a fully-formed spendable output with **no verification** that:

1. `p2tr_script_buf(key + offset·G) == output.script_pubkey` (the offset actually derives the key that controls the output), or
2. the `outpoint` exists and is unspent/mature (e.g., a fabricated `OutPoint` or an immature coinbase output — which `scan_block` itself warns about at mod.rs:216-220 but `read` cannot detect at all). [1](#0-0) 

An unprivileged party who can feed bytes to `ReceivedOutput::read` (an explicitly in-scope untrusted-input surface) can therefore cause a "goal reached" acceptance: bytes claiming a high-value `TxOut` at a fabricated `OutPoint`, or a real-looking output whose `offset` does not map to its `script_pubkey`, are accepted as received funds. This mirrors the report exactly — a state transition to "funds received/spendable" occurs without the `require(totalRaised >= fundraisingGoal)`-equivalent check that the claimed output is real and bound to this key.

### Impact Explanation
- **Funds reported received that are not spendable**: an attacker supplies a `ReceivedOutput` with a nonexistent `outpoint` or a mismatched `offset`/`script_pubkey` pair. Downstream spend construction (`wallet/send.rs` uses `offset` to re-derive the signing key for each input) either produces a transaction spending a UTXO that doesn't exist, or attempts to sign for a script the key cannot satisfy. If accounting credits the claimed `value()` (mod.rs:116-118), the attacker is credited funds never deposited — the direct analog of contributors' funds being locked/misallocated by a false `goalReached`.
- No secret leakage is required; the forged object alone corrupts the accepted state, matching the Medium-severity class.

### Likelihood Explanation
Reachability requires only that attacker-controlled bytes reach `ReceivedOutput::read` (e.g., over a peer/message channel carrying serialized outputs), which is within the permitted untrusted-input model. The missing checks are total: `read` performs no key-derivation comparison and no chain-confirmation check, so any crafted `offset || TxOut || OutPoint` triple succeeds. Exploitation impact depends on how the consumer spends/credits the output, which is not fully verifiable from the in-scope code alone — the `ReceivedOutput` API exposes `offset()`, `output()`, `outpoint()`, and `value()` as trusted accessors (mod.rs:99-118) with no "unverified" marker, so consumers have no signal that a deserialized instance was never scanned.

### Recommendation
Bind the deserialized fields to the scanner's key at read time, mirroring the `require`-style fix:

```rust
pub fn read<R: Read>(r: &mut R, key: &ProjectivePoint) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output = TxOut::consensus_decode(...)?;
    let outpoint = OutPoint::consensus_decode(...)?;
    // Enforce the invariant scan_transaction guarantees:
    if p2tr_script_buf(*key + (ProjectivePoint::GENERATOR * offset))
        != Some(output.script_pubkey.clone())
    {
        return Err(io::Error::other("offset does not bind output to key"));
    }
    Ok(ReceivedOutput { offset, output, outpoint })
}
```

Outpoint on-chain existence/maturity cannot be proven at deserialization; document that `read`d outputs must still be re-verified against the chain (or carry the scanning block/confirmation metadata) before being credited or spent.

### Proof of Concept
```rust
// Attacker-controlled bytes: an offset of 0, a TxOut with value = 21M BTC in sats,
// and a fabricated outpoint. No such UTXO exists on chain.
let mut buf = vec![];
buf.extend(Scalar::ZERO.to_bytes());                    // offset
buf.extend(serialize(&TxOut {
    value: Amount::from_sat(2_100_000_000_000_000),
    script_pubkey: ScriptBuf::new(),                    // not even a P2TR script
}));
buf.extend(serialize(&OutPoint::null()));               // fake outpoint

let forged = ReceivedOutput::read(&mut &buf[..]).unwrap();
assert_eq!(forged.value(), 2_100_000_000_000_000);      // accepted as received funds
// forged.offset() does not satisfy output.script_pubkey for the scanner's key,
// yet nothing in `read` detects this — the "goal reached" flag was set without
// the required precondition check.
```
Root cause: `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) omits the `key + offset·G == script_pubkey` check that `Scanner::register_offset`/`scan_transaction` enforce (mod.rs:180-214) and cannot verify `outpoint` reality, allowing attacker bytes to produce "confirmed spendable" outputs that are neither confirmed nor spendable.
