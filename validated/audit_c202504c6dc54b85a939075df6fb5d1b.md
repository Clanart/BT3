### Title
Payout tx OP_RETURN operator attribution is unauthenticated (`SIGHASH_SINGLE|ANYONECANPAY` doesn't cover it), letting a decoy payout mis-attribute a withdrawal and get the true fronting operator wrongly marked malicious - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
`create_payout_txhandler` signs the payout transaction's input with the user's `TapSighashType::SinglePlusAnyoneCanPay` signature, which only commits to input 0 and the output at the same index (output 0). The OP_RETURN output (index 2) carrying the fronting operator's `xonly_pk` is **not covered by any signature**, so anyone who observes a valid signed payout transaction spending the withdrawal UTXO can rebroadcast a variant with the same input/output-0 but a different OP_RETURN naming a different, uninvolved registered operator. If that decoy is mined first, `update_finalized_payouts` records the wrong operator as payer for that withdrawal index, and `Verifier::is_kickoff_malicious` will later flag the true fronting operator's kickoff as malicious, triggering a challenge that the operator cannot resolve (their own `send_asserts` also refuses because the DB-recorded payer doesn't match).

### Finding Description
The broken binding: the verifier DB's single `withdrawals.payout_payer_operator_xonly_pk` for withdrawal `idx` is supposed to equal the operator who actually fronted that withdrawal's output 0. In reality it equals whatever OP_RETURN pubkey happens to be present in the transaction that first spends `withdrawal_utxo`, which is determined purely by `get_payout_txs_for_withdrawal_utxos` joining on the spent UTXO (`core/src/database/verifier.rs:170-196`), with no check binding the OP_RETURN pubkey to who actually paid.

Root cause: `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds:
- output 0: user payout (amount/script committed by the withdrawal signature)
- output 1: anchor
- output 2: OP_RETURN with `operator_xonly_pk.serialize()`

and signs only input 0 with `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) . Under BIP341, `SIGHASH_SINGLE|ANYONECANPAY` commits to input 0 and only the output with the same index (output 0); outputs 1 and 2 (including the OP_RETURN operator attribution) are completely unsigned. This is enforced/consistent with `parse_withdrawal_sig_params` which requires exactly this sighash type [2](#0-1) .

`update_finalized_payouts` then trusts the OP_RETURN blindly: it parses whatever operator pubkey is embedded, without any authentication tying it to a party who actually funded output 0 [3](#0-2) , and persists it as the payer for that withdrawal index via `update_payout_txs_and_payer_operator_xonly_pk` (matched strictly by `w.idx`, one row, single value) [4](#0-3) .

`Verifier::is_kickoff_malicious` then compares the stored (attacker-controllable) operator against the kickoff's real operator and marks a mismatch as malicious [5](#0-4) . Because `get_payout_txs_for_withdrawal_utxos` joins strictly on the spent UTXO identity (`bsu.txid = w.withdrawal_utxo_txid AND bsu.vout = w.withdrawal_utxo_vout`), only one transaction (whichever wins the UTXO-spend race on chain) is ever recorded — a decoy variant spending the same withdrawal UTXO with the honest operator's own broadcasted signature but a forged OP_RETURN silently displaces the true attribution if it confirms first.

Exploit flow:
1. An honest operator observes a withdrawal on Citrea and broadcasts their real `payout_tx` (signed by the withdrawing user with `SinglePlusAnyoneCanPay`), spending `withdrawal_utxo`, paying output 0 correctly, with OP_RETURN = their own `xonly_pk`.
2. The attacker (any unprivileged party watching the mempool/relay network) copies the input, witness (signature), and output 0 unchanged, but constructs their own transaction replacing the anchor/OP_RETURN outputs, setting the OP_RETURN to a different real, registered-but-uninvolved operator's `xonly_pk`.
3. Attacker gets their variant mined first (e.g. by paying a higher fee, exploiting TRUC/v3 replacement rules used by `NON_STANDARD_V3`, or simple network race).
4. `update_finalized_payouts` records the decoy's OP_RETURN operator as the payer for that withdrawal idx.
5. When the true fronting operator later kicks off with their correct `kickoff_data.operator_xonly_pk`, `is_kickoff_malicious` compares it to the DB-stored (wrong) operator and returns `true`, triggering a Challenge.
6. The honest operator's own `send_asserts` also refuses to proceed since `payout_op_xonly_pk != kickoff_data.operator_xonly_pk` [6](#0-5) , leaving them unable to complete the disprove flow, resulting in deadline-driven collateral loss.

Existing guards checked and found insufficient: `Verifier::is_deposit_valid` and `only_aggregator_and_self` do not run at payout-observation time; `SECP.verify_schnorr` only validates the withdrawal user's signature over output 0, not the OP_RETURN; `verify_storage_proofs`/`SPV::verify`/`lc_proof_verifier` validate L2 state and payout-tx inclusion but not payer identity; no DB uniqueness or reconciliation step cross-checks the OP_RETURN against anything the honest operator committed beforehand.

### Impact Explanation
This is Critical: an honest operator who genuinely fronted a withdrawal has their kickoff flagged malicious and challenged purely due to attacker-controlled metadata in an unrelated decoy transaction, matching "an honest operator's collateral burned" and "an operator reimbursed for a payout it never funded" (the decoy-named operator gets attributed credit they didn't earn, and if they don't dispute it, could wrongly proceed to claim reimbursement). It is repeatable per withdrawal and requires no special access — any withdrawal fronted by any operator is vulnerable as long as the attacker can observe/relay the unconfirmed payout transaction and mine a variant first.

### Likelihood Explanation
Preconditions: attacker needs to see the honest operator's broadcast payout transaction (public, in mempool) before it confirms, and needs to know at least one other real registered operator's `xonly_pk` (public information, since operators register with the aggregator). Cost is just fees to get the decoy mined first (potentially cheaper via CPFP/fee-bump abuse of the v3 anchor outputs). No special privileges, keys, or majority hashrate needed — feasible for any user able to broadcast Bitcoin transactions, matching the stated attacker capability set exactly.

### Recommendation
Commit the operator's `xonly_pk` (and ideally all outputs) inside the sighash covered by the withdrawal signature — e.g., require `SIGHASH_ALL` (or `SIGHASH_ALL|ANYONECANPAY` if multi-input flexibility for fee-bumping is desired) so the OP_RETURN output cannot be altered without invalidating the user's signature, or otherwise cryptographically bind the OP_RETURN operator pubkey to the signature/commitment made at withdrawal time so it can't be forged/replaced by a third party.

pub fn parse_withdrawal_sig_params(
    params: WithdrawParams,
) -> Result<(u32, taproot::Signature, OutPoint, ScriptBuf, Amount), Status> {
    let mut input_signature =
        taproot::Signature::from_slice(&params.input_signature).map_err(|e| {
            Status::invalid_argument(format!("Can't convert input to taproot Signature - {e}"))
        })?;

    // If the Taproot sighash type is Default (no explicit type attached; i.e. a 64-byte
    // signature without a sighash flag), normalize it to SinglePlusAnyoneCanPay.
    // Prior to v0.5 this was Clementine's implicit behavior; we retain it here for
    // backwards compatibility when a 64-byte signature is provided.
    if input_signature.sighash_type == TapSighashType::Default {
        tracing::warn!(
            "Input signature for withdrawal {} has sighash type default, setting to SinglePlusAnyoneCanPay", params.withdrawal_id,
        );
        input_signature.sighash_type = TapSighashType::SinglePlusAnyoneCanPay;
    }

    // enforce sighash type here
    if input_signature.sighash_type != TapSighashType::SinglePlusAnyoneCanPay {
        return Err(Status::invalid_argument(format!(
            "Input signature has wrong sighash type, SinglePlusAnyoneCanPay expected, got {}",
            input_signature.sighash_type
        )));
    }

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;
