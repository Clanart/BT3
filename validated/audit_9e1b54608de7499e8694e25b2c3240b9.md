## Reduction of the report to its broken invariant

The Deriverse bug is: a stale/incorrectly-scoped value (`soc-loss-funds` that has gone negative, i.e. "already paid in") is used in a payout calculation without re-validating that it still represents an amount the protocol owes back to the user. The code trusts a cached signed value instead of the true, current state, and pays back funds that were already consumed.

The GitHub Desktop analog is `AppStore._applyCopilotConflictResolutions` in `app/src/lib/stores/app-store.ts`. It decides whether to overwrite a conflicted file on disk with AI-generated content based on a **cached** in-memory working-directory status snapshot rather than the file's live state, and the AI content itself is derived from attacker-influenced repository text (commit summaries / PR bodies from a remote fork the user is merging/rebasing against).

### Title
Silent overwrite of user's manual conflict resolution with stale-status-gated, attacker-influenced Copilot content - (File: app/src/lib/stores/app-store.ts)

### Summary
`_applyCopilotConflictResolutions` writes Copilot's AI-generated conflict resolutions to disk and stages them for commit. It attempts to protect the user's own manual edits with a guard that skips a file if the user "resolved it externally" — but that guard reads from `this.repositoryStateCache.get(repository)`, a cached status snapshot, not a fresh `git status` at write time. If that cache is stale relative to the real file on disk, the guard's `hasUnresolvedConflicts(onDiskFile.status)` check can be wrong, and the AI-authored content silently overwrites what the user actually intended to commit.

### Finding Description [1](#0-0) 
`_applyCopilotConflictResolutions` fetches `state = this.repositoryStateCache.get(repository)` once at the top of the function and uses `state.changesState.workingDirectory.files` for the "already resolved externally" guard: [2](#0-1) 
The comment explicitly documents the intent — don't clobber a file the user already fixed in their own editor — but the check only inspects the *cached* `onDiskFile.status`, which is only as fresh as the last background status refresh. Between that refresh and the click of "Continue Merge" (during which the Copilot SDK call itself may run for a noticeable amount of time, per `_abortCopilotConflictResolution`'s existence), the user's own edit is invisible to this guard, so `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` proceeds and clobbers it — the exact same class of error as the report: a value trusted as authoritative (`onDiskFile.status` / `soc-loss-funds`) is stale/incorrectly signed relative to true state, and the code "gives back"/writes something it should not.

Compounding this, the *content* being written is not neutral — it is produced by an LLM prompted with attacker-reachable data. `formatConflictContextForPrompt`/`buildConflictContext` feed PR titles/bodies and commit summaries from both sides of the merge (including the "theirs" side, which can be a remote branch/fork controlled by anyone the user is merging from) directly into the prompt sent to the Copilot SDK: [3](#0-2) 
There is no sanitization of this text as a prompt-injection vector, and no verification after the model responds that `resolution.resolvedContent` doesn't contain markers the user's own edit already resolved, or that it matches the user's intent — the only gate is the stale-status check above.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": the user's actual, hand-resolved fix can be silently discarded and replaced by AI-generated text whose semantics were influenced by content from an untrusted remote (a forked repo's PR description or commit messages), and the corrupted result is then `git add`-staged automatically: [4](#0-3) 
This can introduce logic changes, reintroduce vulnerabilities the user manually removed during conflict resolution, or otherwise cause the user to commit/push code they did not actually approve, without any error or warning surfaced.

### Likelihood Explanation
The precondition is a timing gap between the last status refresh and the completion of the (network-bound) Copilot SDK call — a normal, easily-occurring race in everyday use (the user notices the AI is taking a while, switches to their editor, resolves it themselves, then returns and clicks "Continue Merge" before Desktop happens to re-poll git status). No local/admin access or pre-existing malware is required; the "attacker" role is limited to the author of the remote branch/PR being merged, which is squarely in-scope as a controlled git remote/API object.

### Recommendation
Re-run (or at least re-stat/re-read) the on-disk file status immediately before each `writeFile` call in `_applyCopilotConflictResolutions` rather than relying on the `repositoryStateCache` snapshot captured at function entry, and treat the file content on disk (not just the cached `status` enum) as the source of truth for "already resolved" (e.g., re-parse for conflict markers). Additionally, treat PR bodies/commit messages sourced from the remote/incoming side as untrusted input to the prompt and clearly delineate them so model output cannot be steered by adversarial text.

### Proof of Concept
1. Attacker publishes a branch/PR with a merge conflict against the victim's branch; the PR body/commit messages contain adversarial instructions crafted for prompt injection into an AI conflict resolver.
2. Victim starts a merge/rebase in Desktop, triggers Copilot conflict resolution (`buildConflictContext` → SDK call), which takes several seconds.
3. While waiting, the victim manually resolves the conflicted file correctly in their external editor.
4. Desktop's background status watcher has not yet re-polled `git status`, so `repositoryStateCache` still reflects the pre-edit conflicted state.
5. Copilot's response arrives; the victim clicks "Continue Merge". `_applyCopilotConflictResolutions` checks `onDiskFile.status` from the stale cache, sees it as still "unresolved", skips the "already resolved externally" branch, and calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, silently overwriting the victim's correct manual resolution with the attacker-influenced AI output, which is then staged via `git add` and ready to be committed/pushed.

**Uncertainty note:** I could not fully verify the exact timing/refresh cadence of `repositoryStateCache`/background status polling (the code that triggers status refresh wasn't in the retrieved context), which affects how wide the race window realistically is in practice. Confirming that would require inspecting the status-refresh scheduling code, which the index did not surface in this session.
