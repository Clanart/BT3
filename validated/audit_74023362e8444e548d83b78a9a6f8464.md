### Title
Malicious FROST participant can force an identity aggregate nonce and panic BIP-340 signing - ([File: crypto/frost/src/nonce.rs])

### Summary
A signing participant can submit a syntactically valid preprocess whose two nonce commitments cancel under their public binding factor. `AlgorithmSignMachine::sign` then calculates an identity aggregate nonce, and Bitcoin’s BIP-340 `Hram` unconditionally extracts the nonce’s x-coordinate, panicking because the point at infinity has none. This is a remotely triggerable assertion-failure/DoS analog to CVE-2020-8620.

### Finding Description
`read_preprocess` accepts each participant’s nonce commitments as two non-identity points without checking that their eventual bound combination cannot make the aggregate nonce identity. [1](#0-0) [2](#0-1) 

After all preprocesses are transcripted, Serai computes a public per-participant binding factor `rho`. [3](#0-2)  Each participant’s effective nonce commitment is then `D + rho * E`, and all participants’ effective nonces are summed. [4](#0-3) 

A participant who observes the other preprocesses before publishing their own can compute their `rho`, choose any non-identity `D`, and set:

```text
E = -(rho^-1) * D
```

Then:

```text
D + rho * E = identity
```

If every other contribution to the aggregate nonce is known, the attacker can equivalently solve for `D + rho * E = -R_other`, causing the full aggregate nonce to be identity. The algorithm then passes this point to BIP-340 `Hram`, whose `x()` helper calls `encoded.x().expect("point at infinity")`. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged signing participant can repeatedly submit crafted preprocess bytes and cause every coordinator or signer executing `sign` to panic instead of producing a signature share. If the implementation treats Rust panics as process/task termination, this is a persistent signing availability failure; if caught, it still aborts the signing operation and can be repeated for every session.

### Likelihood Explanation
The malformed bytes satisfy the only preprocessing-time validation: each encoded commitment point is canonical and non-identity. [2](#0-1)  The attacker only needs public preprocess data and public transcript/hash definitions to calculate their binding factor. Deployments that collect commitments asynchronously or allow the attacker to publish last make this directly practical.

### Recommendation
Reject identity aggregate nonces before calling `Hram`. At minimum, check `nonce_sums[0][0].is_identity()` in `Algorithm::sign_share` or the Bitcoin wrapper and return `FrostError::InvalidPreprocess`/an equivalent signer-specific error rather than proceeding. More robustly, reject any per-participant bound nonce `D + rho * E` that is identity and blame that participant before summing the aggregate nonce.

### Proof of Concept
For participant `a`:

1. Collect every other participant’s preprocess commitments.
2. Reconstruct the `FROST_rho` transcript used by `calculate_binding_factors`. [3](#0-2) 
3. Compute `rho_a` for `a`.
4. Compute the sum `R_other` of all other participants’ effective nonce commitments.
5. Choose non-identity `D_a`, then submit:

   ```text
   E_a = -(rho_a^-1) * (D_a + R_other)
   ```

   If `rho_a` is zero—which has negligible probability—restart the session/commitment calculation.

6. Serai accepts both `D_a` and `E_a` as canonical non-identity points, computes `D_a + rho_a * E_a`, and obtains `identity` for the aggregate nonce. [4](#0-3) 
7. `Schnorr::sign_share` calls `H::hram(&nonce_sums[0][0], ...)`, which reaches `x(R)` and panics on the identity encoding. [5](#0-4) [6](#0-5)
