No vulnerability found for this question.

**Rationale:** The dedup key in `AcceptedProvers`/`settle_uncle_proof` is explicitly per-account (the SP1-committed nonce bound to the extrinsic signer), not per proof-bytes, and this is documented intended design, not an oversight [1](#0-0) . The pallet's actual invariant is "at most one reward per account per height, total slots capped at `MaxUncleProvers + 1`" — not "one reward per genuine unique physical prover." That invariant is enforced correctly:

- Uncle position is bounded before any reward is paid: `position = ProverCount::get(height); if position > MaxUncleProvers { Err(UncleSlotsFull) }` [2](#0-1) .
- Per-account dedup is checked against `AcceptedProvers` before payout and before the push, and `ProverCount` is only incremented after a successful uncle accept [3](#0-2) .
- `AcceptedProvers` is a `BoundedVec<H256, MaxStoredProvers<T>>` where `MaxStoredProvers = MaxUncleProvers + 1`, so the storage itself cannot exceed the configured cap regardless of how many distinct accounts attempt to claim slots [4](#0-3) .

Crucially, each accepted slot still requires a cryptographically valid, independent SP1 Groth16 proof whose public values commit that specific account as the nonce — the nonce cannot be changed without re-running the SP1 program for that account, so an attacker controlling N accounts must actually generate N separate valid SP1 proofs (the same cost any N independent genuine provers would incur) [5](#0-4) . Sybil accounts submitting genuinely distinct, valid proofs is economically indistinguishable from N independent provers, and the total payout across all positions for a given height is still hard-capped by `MaxUncleProvers` and the decreasing `RewardCurve`, which governance validates so no position's fraction can exceed 1x the base reward [6](#0-5) [7](#0-6) . The protocol was never designed to guarantee prover uniqueness/Sybil-resistance — it's explicitly permissionless and pays for redundant *liveness*, bounded by a fixed slot count, not for provably-distinct operators [8](#0-7) . Since the accounting invariant actually enforced (bounded total slots, one reward per account, cryptographically-bound nonce) is not violated, this does not constitute wrongful asset movement or broken accounting under the review's decision standard.

		/// at position 0 and zero at later positions, preserving pre-uncle behaviour.
		///
		/// Uses a u128 round-trip for `* num / denom`. Hyperbridge runtimes use a u128
		/// balance, so the trip is lossless; on any runtime where balances exceed u128
		/// we'd saturate, which is acceptable since rewards are small relative to total
		/// supply.
		fn position_reward(base: BalanceOf<T>, position: u32) -> BalanceOf<T> {
			let curve = RewardCurve::<T>::get();
			if curve.is_empty() {
				return if position == 0 { base } else { BalanceOf::<T>::default() };
			}
			let Some((num, denom)) = curve.get(position as usize).copied() else {
				return BalanceOf::<T>::default();
			};

			let base_u128: u128 = base.saturated_into();

```text
### Uncle Proofs

To reward redundancy and keep proving live, Hyperbridge rewards more than just the single fastest prover. The **first** prover to land a valid proof for a given finality target advances the chain's state and earns the **full** reward. Additional **independent** provers that generate their own valid proof for the **same** target are accepted as **uncles** and paid on a *decreasing reward curve*, up to a governance-configured limit (`MaxUncleProvers`).

The curve (set via `set_reward_curve`) pays each position a fraction of the base reward. The current curve is **100% / 50% / 30% / 20% / 10% / 5%** — the first prover receives the full reward (100%), and the next five uncles receive 50%, 30%, 20%, 10%, and 5% respectively. Uncle rewards apply to SP1 proofs only.

### Prover-Bound Proofs

Each SP1 proof commits a nonce into its public values, and the runtime requires that nonce to equal the extrinsic signer. This binds a proof to the prover that produced it:

- A proof **cannot be stolen** — copying the proof bytes from the mempool and submitting them under a different account is rejected, because the committed account no longer matches the signer.
- Reward **deduplication is per-account** — an account is rewarded at most once per finality target, so a single prover cannot mint many byte-distinct variants of one proof (e.g. via Groth16 re-randomization) to sweep multiple uncle slots.
```
