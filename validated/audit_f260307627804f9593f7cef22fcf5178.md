### Title
Non-standard ERC20 `approve()` unpack failure permanently freezes user IBC funds in `IBCReceivePacketCallback` - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`IBCReceivePacketCallback` calls `approve()` on the token-pair's ERC20 contract and unconditionally unpacks a `bool` from the return data, without the fallback logic that other conversion paths in the same codebase use for non-standard tokens (e.g. USDT-style contracts that return no data from state-changing calls). Because `RegisterERC20` is permissionless and allows registering arbitrary externally-deployed ERC20 contracts as "native ERC20" token pairs, an attacker/user can register a USDT-like token whose `approve()`/`transfer()` do not return a `bool`. When IBC packets with destination callbacks are received for such a token, the `approve` call's ABI-unpack step always fails, the callback keeper returns an error, and the tokens already credited to the deterministic, keyless "isolated address" become permanently stuck.

### Finding Description
`IBCReceivePacketCallback` sets up an ERC20 allowance for the destination callback contract using the standard `ERC20MinterBurnerDecimalsContract.ABI`: [1](#0-0) 

```go
res, err := k.evmKeeper.CallEVM(cachedCtx, erc20.ABI, receiverHex, tokenPair.GetERC20Contract(), true, remainingGas, "approve", contractAddr, amountInt.BigInt())
...
var approveSuccess bool
err = erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)
if err != nil {
    return errorsmod.Wrapf(types.ErrAllowanceFailed, "failed to unpack approve return: %v", err)
}
```

Unlike the sibling conversion functions in `x/erc20/keeper/msg_server.go` (`ConvertCoinNativeERC20` and `convertERC20IntoCoinsForNativeToken`), which explicitly handle the case where the called ERC20 contract returns no data (`len(res.Ret) == 0`) by falling back to checking for a `Transfer` event in the logs: [2](#0-1) 

the callback keeper's `approve()` call has no such fallback — any contract that doesn't return a `bool` (the exact bug class from the external report) causes `UnpackIntoInterface` to error and the whole callback to abort.

The `tokenPair.GetERC20Contract()` address used here is not guaranteed to be a well-behaved contract deployed by the module. `RegisterERC20` is permissionless (governed only by a `PermissionlessRegistration` param) and lets anyone register an arbitrary, already-deployed ERC20 contract as a "native ERC20" token pair: [3](#0-2) 

Meanwhile, the IBC receive flow (via `x/ibc/transfer` middleware / `packetforward`/`callbacks`) credits tokens to a deterministic, non-user-controlled "isolated address" *before* invoking `IBCReceivePacketCallback`: [4](#0-3) 

If the callback then fails (as it will for a non-standard-return-value ERC20), the cached context is never written back (`writeFn()` at line 227 is never reached), so the intended forwarding/contract execution never happens. Since the isolated address has no known private key, tokens credited there via the standard (non-callback) ICS20 receive path become unrecoverable.

### Impact Explanation
This matches the "Critical permanent freezing/locking of user funds" allowed impact: any IBC transfer with a destination callback targeting a token pair backed by a non-standard ERC20 (no bool return on `approve`/`transfer`) will always fail at the `approve` unpack step, and the tokens that were already transferred to the isolated address (which has no recoverable private key) become permanently stuck with no path to reclaim them.

### Likelihood Explanation
Likelihood is high given:
- `RegisterERC20` is permissionless by default configuration (`PermissionlessRegistration`), so anyone can register a real-world non-standard ERC20 (e.g., a USDT-style bridged/mirrored token) as a token pair.
- Once such a token pair exists, any user (attacker or victim) sending an ICS-20 transfer with `dest_callback` memo data targeting that denom will trigger this code path — no privileged action required.
- The bug is deterministic: it triggers on every attempt for that token, not a race condition.

### Recommendation
Apply the same fallback pattern used in `ConvertCoinNativeERC20`/`convertERC20IntoCoinsForNativeToken` to the `approve` call in `IBCReceivePacketCallback`: check `len(res.Ret) == 0` and, if empty, validate success via the `Approval` event logs instead of unconditionally unpacking a `bool`. Additionally, consider providing a governance/permissioned recovery mechanism for funds stuck at isolated addresses when destination callbacks fail irrecoverably.

### Proof of Concept
1. Deploy a minimal ERC20 contract (e.g., mimicking mainnet USDT) whose `approve(address,uint256)` and `transfer` functions perform state changes but return no data (`outputs: []` in the ABI, not `bool`).
2. Permissionlessly register this contract via `MsgRegisterERC20` as a "native ERC20" token pair (assuming `PermissionlessRegistration` param is enabled, or via a governance vote otherwise).
3. From a counterparty chain, send an ICS-20 transfer of this token's denom to this chain, with `memo` containing `dest_callback` data pointing at a valid, deployed EVM contract address.
4. The ICS20 transfer credits the isolated address (as computed by `types.GenerateIsolatedAddress`) with the transferred tokens as part of normal receive processing.
5. `IBCReceivePacketCallback` executes, calls `approve` on the non-standard token contract; `res.Ret` is empty; `erc20.ABI.UnpackIntoInterface(&approveSuccess, "approve", res.Ret)` returns an error; the function returns `ErrAllowanceFailed` before `writeFn()` is called.
6. The destination callback (and thus the intended contract forwarding logic) never executes, and the tokens remain at the isolated address, which has no known private key — permanently locking the transferred value.

Note: I could not fully verify from the index whether `GenerateIsolatedAddress` guarantees no recoverable key material exists for that address (only the function's file location was found, not its full body), and I could not verify whether `PermissionlessRegistration` defaults to `true` or `false` at genesis in this repository — both would need confirmation in a live session to fully validate the exploitability preconditions.

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}
