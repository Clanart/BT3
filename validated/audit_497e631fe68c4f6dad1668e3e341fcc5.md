### Title
Malicious signer forces `Hram::hram` panic by making aggregate nonce `R` the point at infinity - (File: networks/bitcoin/src/crypto.rs)

### Summary
A malicious FROST participant can craft their nonce commitments so that the aggregate signature nonce `R` is the point at infinity. When the Bitcoin `Schnorr` algorithm calls `Hram::hram(R, A, m)` during `verify`/`complete`, `x(R)` panics on `expect("point at infinity")`, deterministically aborting the signing session. This is the same bug class as M-02: an attacker supplies public inputs that force a call to fail rather than return an error.

### Finding Description
`x` extracts the x-coordinate of a point and panics if the point is infinity: [1](#0-0) 

`x_only` and `needs_negation` build on it, and `Hram::hram` calls `x(R)` unconditionally on the aggregate nonce: [2](#0-1) 

`Schnorr::verify` delegates to the IETF Schnorr `verify`, which computes the BIP-340 challenge via `hram(R, group_key, msg)` over the summed nonce commitments: [3](#0-2) 

The doc comment claims a panic has "negligible probability ... even with malicious participants present" (lines 78–83), but that reasoning is wrong: a signer who publishes their `Preprocess` last sees all other participants' nonce commitments and the binding factors `rho_i`, so they can solve `D_i + rho_i * E_i = -(sum of everyone else's contributions)` and force `R = sum(nonce_sums)` to be exactly the identity element. A grep over `crypto/frost/src` shows only one `is_identity` check (in `curve/mod.rs`), with none in `sign.rs`/`algorithm.rs` on the preprocess/aggregate-nonce path, and `Commitments::read`/`read_G` accept the identity encoding (identity points are valid encodings; only `Signed::read` in the out-of-scope tributary code rejects `R.is_identity()`).

### Impact Explanation
Any call to `AlgorithmMachine::sign`/`complete` that reaches `Schnorr::verify` with this poisoned preprocess panics the host process instead of returning `FrostError`/`None`. A single malicious signer (or anyone who can feed crafted preprocess bytes to `read_preprocess`/`sign`/`complete` — e.g., a coordinator/relayer supplying the commitments map) can deterministically crash or abort every honest participant's signing attempt for Bitcoin outputs, halting withdrawals indefinitely. This is a forced-failure/griefing vector directly analogous to the relayer forcing `tryCatch`/`tryCatchLimit` to revert in M-02.

### Likelihood Explanation
The attack requires only that the attacker submit their nonce commitments after observing the others — trivially achievable by the last participant to publish a `Preprocess` or by any party ordering the preprocess map. The malicious preprocess parses cleanly through `Commitments::read` since each individual commitment point is a valid non-identity encoding; only the weighted sum becomes identity. Deterministic, no brute force needed.

### Recommendation
Reject the identity element for `R` (and for individual nonce commitments) before calling `hram`. Concretely: in `networks/bitcoin/src/crypto.rs`, make `Hram::hram`/`Schnorr::verify` return `None`/an error when `R.is_identity()` rather than letting `x()` panic, and/or add an `is_identity` check on aggregate nonces in `crypto/frost/src/algorithm.rs`'s `verify`/`sign_share` so the panic is unreachable regardless of the `Hram` implementation.

### Proof of Concept
1. Honest participants `1..t` each publish `Preprocess`es with nonce commitments `(D_j, E_j)`.
2. Attacker (participant `t`, publishing last) computes the FROST binding factors `rho_j` over the full preprocess set, then chooses `E_t` arbitrarily and sets `D_t = -( Σ_j D_j + Σ_j rho_j·E_j ) - rho_t·E_t`, i.e., solves so the weighted nonce sum `R = Σ_j (D_j + rho_j·E_j) = O` (identity). Both `D_t`, `E_t` are valid encodings and pass `read_preprocess`.
3. All participants call `sign`/`complete` with this preprocess set. `Schnorr::verify` → `self.0.verify` → `Hram::hram(&R, &group_key, msg)` → `x(R)` → `expect("point at infinity")` panics (networks/bitcoin/src/crypto.rs:15), aborting the session/process instead of returning an error.

```rust
    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
```
