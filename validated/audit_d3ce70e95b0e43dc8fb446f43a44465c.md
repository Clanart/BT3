### Title
Payout tx OP_RETURN operator identity is unauthenticated and spoofable due to `SIGHASH_SINGLE|AnyoneCanPay` and unbounded `get_first_op_return_output` selection - ([File: circuits-lib/src/bridge_circuit/mod.rs], [File: core/src/operator.rs], [File: core/src/verifier.rs])

### Summary
The withdrawer's payout signature is verified with `TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) , which does not commit to any output other than the one at the same index as the signed input (output 0). This leaves the anchor output and the `OP_RETURN` output (which encodes the fronting operator's x-only pubkey) completely unauthenticated by the withdrawer's signature, and neither `get_first_op_return_output`/`parse_op_return_data` nor the downstream consumers of this data (`deposit_constant`, `update_finalized_payouts`, `is_kickoff_malicious`) verify that the named operator actually funded the payout.

### Finding Description
The claimed binding is:
`operator_xonlypk` parsed from the payout tx's first `OP_RETURN` (used in `deposit_constant` in `circuits-lib/src/bridge_circuit/mod.rs:206-229` and stored in the DB via `update_finalized_payouts` in `core/src/verifier.rs:2283-2352`) == the identity of the party whose funds actually paid the withdrawer on-chain.

Tracing the code:
- `create_payout_txhandler` builds the payout tx with input 0 = the withdrawal UTXO (spent via the withdrawer's own signature, `SpendPath::KeySpend`), output 0 = user payout, output 1 = anchor, output 2 = `OP_RETURN` containing whichever `operator_xonly_pk` the tx-builder is given [2](#0-1) .
- The withdrawer's signature is checked against a sighash computed with the withdrawer-supplied `sighash_type`, and the operator code explicitly documents the expectation that this is `SinglePlusAnyoneCanPay` [1](#0-0) .
- Under BIP-341/BIP-143 `SIGHASH_SINGLE`, only the output at the *same index as the signed input* (output 0, the payout) is committed to the signature; with `ANYONECANPAY` set, other inputs (fee funding) are also unconstrained. This means **outputs 1 and 2 (anchor, OP_RETURN) are not covered by the withdrawer's signature at all**. Any party who can obtain that signature (which the withdrawer/attacker themselves control, per the threat model: "a Schnorr signature and its sighash flag") can build an alternative, fully-valid payout transaction reusing input 0's signature while substituting arbitrary anchor/`OP_RETURN` outputs — including one, or several, `OP_RETURN` outputs naming an arbitrary `operator_xonlypk` that never contributed a satoshi.
- `get_first_op_return_output` simply returns `tx.output.iter().find(is_op_return)` with no dedup or uniqueness check [3](#0-2) , and `parse_op_return_data` blindly extracts the first push after `OP_RETURN` [4](#0-3) . Neither checks that the tx's actual value-carrying output (output 0) was funded by the entity whose pubkey is embedded in the (possibly attacker-chosen, possibly duplicated) `OP_RETURN`.
- On the verifier side, `update_finalized_payouts` reads exactly this unauthenticated `operator_xonly_pk` straight off mined chain data and persists it as the payer identity for the withdrawal [5](#0-4) .
- `is_kickoff_malicious` later compares this DB-recorded `operator_xonly_pk` against `kickoff_data.operator_xonly_pk` from a real kickoff to decide whether the kickoff is malicious [6](#0-5) , and the ZK bridge circuit independently commits the (equally unauthenticated) `operator_xonlypk` into `deposit_constant` [7](#0-6) .

None of `is_deposit_valid`, `SPV::verify`, `verify_storage_proofs`, or `lc_proof_verifier` check the funding source of the payout tx's outputs versus the `OP_RETURN` claim — they only validate that the withdrawal UTXO was spent and that the transaction is included in a valid chain, not who funded which output.

### Impact Explanation
- If an attacker (the withdrawer) reuses their own `SinglePlusAnyoneCanPay` signature but funds/broadcasts a variant of the payout transaction naming a **victim honest operator's** `operator_xonly_pk` in the `OP_RETURN`, `update_finalized_payouts` will record that operator as the payer even though that operator spent nothing. If that operator's automation later relies on this DB record (`validate_payer_is_operator` in `get_reimbursement_txs`, `core/src/verifier.rs:2116-2119`) without independently verifying it actually broadcast/funded that specific transaction, it could be tricked into treating a payout it never made as its own, or conversely an honest operator that *did* pay could be marked malicious by `is_kickoff_malicious` if the attacker front-runs the same withdrawal UTXO with a spoofed-`OP_RETURN` transaction, permanently preventing that operator from being reimbursed for a payout it legitimately fronted.
- This falls under Critical: "an operator reimbursed for a payout it never funded" or "an honest operator permanently unable to be reimbursed," since the OP_RETURN-derived attribution is trusted downstream by both the on-chain DB bookkeeping and the ZK circuit's `deposit_constant` commitment.
- The attack is repeatable per withdrawal/deposit and does not require privileged access — only control over the withdrawer's own payout request and sighash flag choice.

### Likelihood Explanation
Preconditions: the withdrawer's payout signature must use (or be permitted to use) `SinglePlusAnyoneCanPay`, which is the documented/expected sighash type in `core/src/operator.rs` — this is not merely a hypothetical but the intended flow. The attacker only needs to be the withdrawer requesting their own withdrawal, pay ordinary Bitcoin fees, and construct a transaction reusing the signed input with substituted anchor/`OP_RETURN` outputs. No majority hashrate, key compromise, or privileged role is required.

### Recommendation
Do not trust the on-chain `OP_RETURN` alone as proof of who funded a payout. Either (a) require the withdrawer's signature to use `SIGHASH_ALL` (or a sighash type that commits to all outputs) so the `OP_RETURN`/operator identity cannot be altered after the withdrawer signs, or (b) have operators track and verify by txid/psbt that *they themselves* broadcast the specific payout transaction (e.g., persist the exact signed transaction they sent rather than re-deriving payer identity from scanning `OP_RETURN` data on-chain), and reject/ignore transactions with more than one `OP_RETURN` output or an `OP_RETURN` that doesn't match a locally-tracked, operator-signed record.

### Proof of Concept
```
cargo test -p core spoofed_payout_op_return_attribution
```
Plan:
1. Simulate a withdrawal: obtain a withdrawer signature with `TapSighashType::SinglePlusAnyoneCanPay` over the withdrawal UTXO input, as done in `Operator::withdraw` (`core/src/operator.rs:630-637`).
2. Build two payout tx variants sharing input 0 + witness (same signature): (A) the honest operator's tx via `create_payout_txhandler` with `operator_xonly_pk = operator_A`; (B) an attacker-built tx with the same input/witness but `OP_RETURN` naming `operator_B` (a different, uninvolved key), funded entirely by the attacker's own UTXOs for fee/anchor.
3. Assert both (A) and (B) pass Bitcoin script/witness validation (`SECP.verify_schnorr` succeeds for both, since neither output 1 nor the OP_RETURN is covered by the sighash).
4. Feed tx (B) through `update_finalized_payouts`/`get_first_op_return_output`/`parse_op_return_data` and assert the derived `operator_xonly_pk == operator_B`, while asserting no funds from `operator_B`'s wallet were spent in tx (B) — demonstrating the equality `OP_RETURN pubkey == actual funder` is false.
5. Feed the same forged `operator_xonlypk` into `deposit_constant` (`circuits-lib/src/bridge_circuit/mod.rs:221-229`) and show it matches `operator_B`'s expected `deposit_constant`, even though `operator_B` never funded the payout.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}
