### Title
Malicious git remote can spoof a `WWW-Authenticate` header to auto-trigger an unrequested "GitHub Enterprise" OAuth sign-in flow pointed at an attacker-controlled endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`VoterProxy`'s report is about a privileged role (`owner`) redirecting a trust decision (`operator`) toward an attacker-controlled address, letting that address later drain funds via `execute()`/`withdraw()`. The reducible primitive is: **an entity that is supposed to be validated/trusted is instead set from an attacker-influenced value, and downstream code treats it as trusted without re-checking.**

The Desktop analog is in the credential-helper's host-classification logic. `getEndpointKind()` in `app/src/lib/trampoline/trampoline-credential-helper.ts` classifies a git remote as a `'enterprise'` (i.e., "this is a GitHub-like host") purely by inspecting a `wwwauth[]` header value that git forwarded from the **remote server's own HTTP response**, with no server-side verification: [1](#0-0) 

Because this check happens before any network-verified check like `isGitHubHost()`, an attacker who controls the git remote (or a MITM proxy for it) can make Desktop believe a plain, unrelated host is a "GitHub" host simply by returning `WWW-Authenticate: realm="GitHub"` on a 401.

### Finding Description
When Git needs credentials for an HTTP(S) remote, it invokes Desktop's trampoline credential helper (`createCredentialHelperTrampolineHandler`) with the `wwwauth[]` values captured from the server's actual `WWW-Authenticate` response header: [2](#0-1) 

`getCredential()` calls `getEndpointKind()`, which trusts that header content over other checks, and if the endpoint is deemed non-`'generic'` and no existing account matches it, Desktop automatically opens a "Sign in to GitHub" prompt for that exact remote endpoint: [3](#0-2) 

That prompt is implemented in `TrampolineUIHelper.promptForGitHubSignIn`, which — for any non-`github.com` hostname — automatically calls `beginEnterpriseSignIn()` and then `setSignInEndpoint(origin)` using the **attacker-controlled remote's own origin**, with no manual user entry/validation step (the normal `EndpointEntry` UI step, which is meant to let the user consciously type/confirm the Enterprise server URL, is skipped): [4](#0-3) 

`sign-in-store.ts#setEndpoint()` accepts this attacker-chosen `origin`, validates only its URL syntax (not its legitimacy), and transitions straight into the OAuth `Authentication` step: [5](#0-4) 

When the user clicks "Sign in using your browser" on that dialog (which shows a generic "Git requesting credentials to access `<url>`" message that does not distinguish a legitimate Enterprise instance from an attacker-controlled one), `authenticateWithBrowser()` calls `shell.openExternal(getOAuthAuthorizationURL(endpoint, csrfToken))`, opening the user's real system browser to an OAuth authorize URL built from the attacker-supplied endpoint: [6](#0-5) [7](#0-6) 

The subsequent OAuth code exchange (`requestOAuthToken(endpoint, action.code)`) and user fetch (`fetchUser(endpoint, token)`) are likewise both directed at the attacker-controlled `endpoint`: [8](#0-7) 

### Impact Explanation
An untrusted git remote (or a network position that can tamper with HTTP responses to it, e.g., a compromised/malicious proxy) fully controls whether Desktop treats the connection as a "GitHub Enterprise" identity and controls the `endpoint` value used to construct the OAuth authorize URL that Desktop's `shell.openExternal` opens in the user's default browser — without the user ever having typed or confirmed that URL. This:
- Bypasses the intended manual "Enterprise address" confirmation step (`EndpointEntry`), which exists specifically so users consciously vet what server they're authorizing against.
- Causes Desktop to silently drive the user into a GitHub-Enterprise-styled OAuth consent/sign-in flow against an arbitrary attacker-chosen origin, which the resulting Account object (and its token) then gets stored in the local `AccountsStore` as a trusted account, associated with that attacker's endpoint. Combined with any subsequent flow that treats "having any signed-in account" as elevated trust (e.g. matching remotes to accounts, autocompletion, notifications, PR/CI fetch), this could be leveraged for further phishing/social-engineering follow-through once the fake account exists in Desktop's UI.
- More broadly, it demonstrates the credential-helper trusting a value the remote fully controls (`wwwauth[]`) to short-circuit trust classification without invoking `isGitHubHost()`'s network verification, and to determine what external URL Desktop opens via `shell.openExternal`.

This aligns with "attacker controls...a git remote/proxy response, and the result is...unauthorized OAuth or account binding."

### Likelihood Explanation
Triggering this only requires the victim to attempt a git operation (clone/fetch/push) against a remote the attacker controls or can tamper responses for, and to receive a 401 with a crafted `WWW-Authenticate: realm="GitHub"` header — a single-line server response, requiring no local access, no malware, and no unnatural extra steps by the user beyond normal git usage and clicking "Sign in" on a dialog Desktop itself presents as legitimate-looking. The classification logic (`getEndpointKind`) explicitly documents that it relies on this header as a "happy path," acknowledging the header is attacker-influenced input.

### Recommendation
- Do not let the `wwwauth[]` classification alone gate an automatic transition into the Enterprise sign-in / OAuth flow; require the network-verified `isGitHubHost()` check (or equivalent server-side confirmation) before offering/auto-initiating any sign-in UI.
- When `promptForGitHubSignIn` is invoked for a non-`github.com` endpoint, route through the normal `EndpointEntry` UI step (requiring explicit user confirmation of the target URL) instead of silently calling `setSignInEndpoint(origin)` with a value derived from the credential-helper's remote/header-driven `endpoint`.
- Clearly differentiate, in the sign-in dialog, whether the endpoint was auto-detected from a remote/response header versus manually entered by the user, so users have the information needed to distrust unexpected Enterprise sign-in prompts.

### Proof of Concept
1. Attacker hosts a git-over-HTTPS server (or sits as a MITM/tampering proxy for one) at `https://evil.example`.
2. Victim adds/uses this as a git remote in Desktop (e.g., clones or fetches it).
3. When Git requests credentials, the attacker's server returns a `401` with header `WWW-Authenticate: realm="GitHub"`.
4. Desktop's `getEndpointKind()` classifies `https://evil.example` as `'enterprise'` purely from that header.
5. Since no existing account matches `https://evil.example`'s computed API endpoint, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example')`.
6. `promptForGitHubSignIn` calls `beginEnterpriseSignIn()` + `setSignInEndpoint('https://evil.example')` automatically (no manual URL entry step) and shows a "Sign in to your GitHub Enterprise" dialog with "Git requesting credentials to access https://evil.example."
7. Victim clicks "Sign in using your browser"; Desktop calls `shell.openExternal` with an OAuth authorize URL built from `https://evil.example`, and later exchanges the returned OAuth code and fetches "user" data against that same attacker-controlled origin, storing the resulting fake "account" in Desktop's account store.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
    }).catch(e => {
      log.error(`Could not prompt for GitHub sign in`, e)
      return undefined
    })
  }

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }

  public async setEndpoint(url: string): Promise<void> {
    const currentState = this.state

    if (
      currentState?.kind !== SignInStep.EndpointEntry &&
      currentState?.kind !== SignInStep.ExistingAccountWarning
    ) {
      const stepText = currentState ? currentState.kind : 'null'
      return fatalError(
        `Sign in step '${stepText}' not compatible with endpoint entry`
      )
    }

    /**
     * If the user enters a github.com url in the GitHub Enterprise sign-in
     * flow we'll redirect them to the GitHub.com sign-in flow.
     */
    if (/^(?:https:\/\/)?(?:api\.)?github\.com($|\/)/.test(url)) {
      this.beginDotComSignIn(currentState.resultCallback)
      return
    }

    this.setState({ ...currentState, loading: true })

    let validUrl: string
    try {
      validUrl = validateURL(url)
    } catch (e) {
      let error = e
      if (e.name === InvalidURLErrorName) {
        error = new Error(
          `The GitHub Enterprise instance address doesn't appear to be a valid URL. We're expecting something like https://example.ghe.com.`
        )
      } else if (e.name === InvalidProtocolErrorName) {
        error = new Error(
          'Unsupported protocol. Only https is supported when authenticating with GitHub Enterprise instances.'
        )
      }

      this.setState({ ...currentState, loading: false, error })
      return
    }

    const endpoint = getEnterpriseAPIURL(validUrl)

    const existingAccount = this.accounts.find(x => x.endpoint === endpoint)

    if (existingAccount) {
      this.setState({
        kind: SignInStep.ExistingAccountWarning,
        endpoint,
        existingAccount,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    } else {
      this.setState({
        kind: SignInStep.Authentication,
        endpoint,
        error: null,
        loading: false,
        resultCallback: currentState.resultCallback,
      })
    }
  }
