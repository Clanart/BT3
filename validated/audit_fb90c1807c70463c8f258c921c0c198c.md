### Title
`Scanner::scan_block` credits immature coinbase outputs as received funds that are not yet spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
The DCA bug class is: a state-changing cleanup/finalization proceeds without verifying that a prerequisite fallible operation (the token transfer) actually succeeded, so the system records a successful outcome (order cancelled, funds "returned") that does not match reality and the user loses funds. The Serai analog lives in the Bitcoin wallet scanner: `Scanner::scan_block` iterates over **all** transactions in a block, including `block.txdata[0]` (the coinbase), and returns every matching output as a `ReceivedOutput` — a spendable-output record — even though coinbase outputs are immature and cannot be spent for 100 blocks. Funds are reported received that are not spendable, and downstream consumers that feed these `ReceivedOutput`s into `TransactionSignatureMachine`/`SignableTransaction` will attempt to sign spends of immature coinbases, producing transactions the network rejects — or worse, permanently accounting outputs that can never be confirmed spent if the coinbase is orphaned before maturity.

### Finding Description
`ReceivedOutput` documents itself as "A spendable output" (`mod.rs:88-97`). `Scanner::scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script (`mod.rs:199-214`), and `scan_block` extends this over the entire `block.txdata` slice (`mod.rs:221-227`) with no exclusion of `txdata[0]` and no maturity check. The only mitigation is a doc comment on `scan_block` (`mod.rs:216-220`) stating "If received outputs must be immediately spendable, a post-processing pass is needed" — i.e., the same class of failure as the DCA report: the function completes and hands out state (a "spendable" output record) even though the success precondition (the output being mature/spendable) was never verified. Within the in-scope crate nothing enforces the post-processing; an unprivileged party (anyone who can get a miner to pay the multisig's tweaked address in a coinbase, e.g. by mining to it or via a pool payout) causes `ReceivedOutput`s to be produced for outpoints that Bitcoin consensus forbids spending for 100 blocks.

### Impact Explanation
A `ReceivedOutput` for an immature coinbase is treated identically to a confirmed spendable UTXO. If it is fed to `SignableTransaction`/`TransactionSignatureMachine` in `send.rs`, the threshold signature will be produced over a transaction that Bitcoin nodes reject (bad-txns-premature-spend-of-coinbase). Depending on the consumer, this either wastes a signing attempt or, if the plan/attempt state is cleaned up on completion (mirroring the DCA cleanup-before-verification shape), the input selection may not be retried correctly. Coinbase outputs are also at elevated orphan risk relative to normal confirmed outputs, so the "received funds" record may correspond to an outpoint that ceases to exist.

### Likelihood Explanation
Any party paying the Serai multisig address can cause this path to trigger — a miner or mining pool paying out to a scanned `register_offset` address creates matching coinbase outputs routinely. Reachability requires only a Bitcoin transaction (explicitly in-scope as attacker input). Whether the damage materializes depends on the integrator heeding the doc comment; within the audited crate the API hands out a struct typed as "spendable" for unspendable outpoints.

### Recommendation
In `Scanner::scan_block` (`networks/bitcoin/src/wallet/mod.rs:221`), either skip `block.txdata[0]` entirely, or tag each `ReceivedOutput` with whether it originates from the coinbase (e.g. a `coinbase: bool` field set in `scan_transaction` from `tx.is_coinbase()`) so callers cannot accidentally treat it as spendable. The maturity invariant should be enforced in the type rather than delegated to a doc comment.
