### Title
External outputs received during `ForwardFromExisting`/`ClosingExisting` that yield no instruction or refund are silently dropped and become permanently unspendable - ([File: processor/src/multisigs/mod.rs])

### Summary
The audit report's bug class is "a code path accepts funds but lacks the capability to move/withdraw them" (missing `payable` making ETH deposits unwithdrawable). The Serai analog lives in the multisig rotation flow: when the rotation step is `ForwardFromExisting` or `ClosingExisting`, an externally-received output to the existing multisig is only forwarded or refunded if `instruction_from_output` produces an `InInstruction` or a parseable refund address. If neither is produced, the output is dropped entirely — it is marked `seen` by the scanner yet is never added to the scheduler's UTXO set and never forwarded to the new multisig. The coins remain at an address the threshold key controls but which no `Plan` will ever spend: funds reported received that are not spendable.

### Finding Description
In `scanner_event_to_multisig_event`, during `RotationStep::ForwardFromExisting` the code iterates new `External` outputs for the existing key and only creates a `PlanFromScanning::Forward`/`Refund` when `instruction_from_output` returns an instruction or a refund address; otherwise the output is retained (`plans_at_start == plans.len()` → `should_retain` = true) [1](#0-0) . The retained outputs then fall into the second loop, where the step check `RotationStep::ForwardFromExisting | RotationStep::ClosingExisting => true` combined with `output.key() == self.existing.key` causes an unconditional `continue` — the output is skipped with no plan, no instruction, and no scheduler insertion [2](#0-1) . The scanner has already recorded the output ID as `seen`, so it will never be reprocessed [3](#0-2) . The comment "we'll report it once it hits the new multisig" assumes the earlier loop created a forwarding plan, which it does not for outputs lacking a valid instruction or refund address. An unprivileged sender triggers this simply by broadcasting a Bitcoin transaction paying the existing multisig's external P2TR address (publicly derivable from the group key via `p2tr_script_buf`) with no/absent Serai `data` embedding during the rotation window [4](#0-3) .

### Impact Explanation
Any output received under these conditions is permanently locked: it is never scheduled as a UTXO, never forwarded, never refunded, and never re-scanned. For Bitcoin this is a strict subset of "funds reported received that are not spendable" — the threshold key mathematically controls the coins but the processor will never produce a `Plan` spending them. This also applies to user deposits racing the rotation boundary, where an honest user loses funds with no refund path (no `InInstruction` → no presumed refund target is honored since `refund_to` parsing may also fail for malformed/absent data).

### Likelihood Explanation
Medium. The trigger requires only a public-input action (sending a Bitcoin tx to a public address during a bounded window — the 6-hour `ForwardFromExisting`/`ClosingExisting` rotation periods, which recur at every multisig rotation). No collusion or privileged position is needed; an attacker can also grief by sending dust-free deposits deliberately timed to the window, permanently burning BTC into the multisig's unspendable set and inflating locked balance.

### Recommendation
In the second loop of `scanner_event_to_multisig_event`, do not `continue`/drop `External` outputs to the existing key when no instruction was produced. Instead, for `ForwardFromExisting`, always emit a `PlanFromScanning::Forward` (or `Refund` to `presumed_origin` when instruction parsing fails but an origin exists) so every output to the existing key is consumed by a plan; for `ClosingExisting`, explicitly forward remaining outputs or add them to the new multisig's scheduler rather than dropping them. Add an assertion post-processing that no scanned output is left unconsumed by a plan or instruction.

### Proof of Concept
1. Wait for (or time a deposit to) a block within the `ForwardFromExisting`/`ClosingExisting` window.
2. Broadcast a Bitcoin transaction paying `p2tr_script_buf(existing_group_key)` with no Serai OP_RETURN data, or with data that fails `instruction_from_output` and refund parsing.
3. The scanner classifies it `OutputType::External` and marks it `seen` [5](#0-4) .
4. In the `ForwardFromExisting` loop, `instruction` and `refund_to` are both `None`; `plans_at_start == plans.len()` retains the output [6](#0-5) .
5. The second loop hits the `ForwardFromExisting | ClosingExisting => true` arm and `continue`s, permanently discarding the output [7](#0-6) . The BTC is thereafter unspendable by the protocol.
