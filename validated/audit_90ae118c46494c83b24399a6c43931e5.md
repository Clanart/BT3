### Title
`ThresholdKeys::read`/`ThresholdKeys::new` accepts identity verification shares producing an identity `group_key` - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is a setter/constructor accepting a zero/invalid value without validation (address zero assigned to `nft`). In Serai's in-scope DKG crate, `ThresholdKeys::new` and `ThresholdKeys::read` accept untrusted verification-share points and compute `group_key` as their interpolated sum, but never validate that the resulting `group_key` — or any of the per-participant verification shares — is non-identity.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574) deserializes attacker-controlled bytes: it reads `n` group elements via `<C as Ciphersuite>::read_G` (line 622), which enforces only a canonical encoding (crypto/ciphersuite/src/lib.rs:91-101) and does *not* reject the identity point — unlike FROST's stricter `Curve::read_G` which does (crypto/frost/src/curve/mod.rs:125-131). It then calls `ThresholdKeys::new` (line 625), which computes `group_key` as the interpolated sum of shares `1..=t` (lines 376-378) with no check that the result is non-identity, and no check that individual shares are non-identity.

An unprivileged party feeding crafted bytes to `ThresholdKeys::read` can therefore install a `ThresholdKeys` whose `group_key()` is the identity point (e.g., all shares identity, or shares summing to identity under Constant interpolation with chosen coefficients).

### Impact Explanation
The discrete log of the identity group key is 0, which is publicly known. Any Schnorr/FROST verification performed against this group key is forgeable by anyone: the signature `(R = sG, s)` satisfies `sG == R + c·O` for arbitrary `s` since `c·O = O`. Any validator that accepts these keys (e.g., from deserialized peer/protocol data) would treat signatures under a publicly-known key as valid threshold signatures — a concrete signature forgery, not merely a benign invalid-parameter error.

### Likelihood Explanation
Reachability requires an attacker to supply the serialized `ThresholdKeys` bytes to a victim. The bytes are fully attacker-controlled (curve ID, t, n, i, interpolation, secret share, and `n` point encodings), and neither the deserializer nor the constructor rejects identity shares. Crafting identity-summing shares is trivial (e.g., all shares identity, or `A` and `-A`). Exploitation depends on a downstream consumer using `ThresholdKeys::read`/`new` on untrusted input rather than only on locally-produced keys — the API itself provides no defense.

### Recommendation
In `ThresholdKeys::new`, after computing `group_key`, reject `group_key.is_identity()`, and reject any `verification_shares` value that `is_identity()` before interpolation. For completeness, `ThresholdKeys::read` could also reject a zero `secret_share`, since a zero share combined with identity group key makes the "threshold" property vacuous.

### Proof of Concept
```rust
// For any C: Ciphersuite (e.g., Ristretto), build serialized ThresholdKeys
// with n = t = 1, i = 1, Lagrange interpolation, arbitrary secret share,
// and a single verification share set to the identity point.
let mut bytes = vec![];
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(1u16.to_le_bytes()); // t
bytes.extend(1u16.to_le_bytes()); // n
bytes.extend(1u16.to_le_bytes()); // i
bytes.push(1);                    // Interpolation::Lagrange
bytes.extend(C::F::ONE.to_repr().as_ref());          // secret_share
bytes.extend(<C::G as Group>::identity().to_bytes().as_ref()); // share[1] = identity

let keys = ThresholdKeys::<C>::read(&mut &bytes[..]).unwrap();
assert!(bool::from(keys.group_key().is_identity())); // accepted: group key is identity

// Anyone can now forge a signature against keys.group_key():
// pick arbitrary s, set R = s * G; then sG - R - c*O == O for any challenge c.
```
