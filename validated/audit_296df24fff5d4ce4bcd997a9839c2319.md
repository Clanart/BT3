### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` causes stack-overflow DoS - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively re-invokes `rlp.DecodeBytes` for every sub-key it contains, and each sub-key may itself be another `AccountKeyRoleBased`. Neither the RLP decode path nor the account-update transaction validation path enforces a "no nested RoleBasedKey" rule or any recursion-depth limit, unlike the JSON encode path which does check for this. An unprivileged party can submit a single crafted transaction (or call a public RPC method) containing a deeply self-nested `AccountKeyRoleBased` blob, causing the node to recurse until the Go goroutine stack overflows — a process-crashing denial of service, directly analogous to the Eclipse Parsson deeply-nested-JSON stack overflow (CVE-2023-7272).

### Finding Description
`AccountKeyRoleBased` is decoded as: [1](#0-0) 

For each element of the outer list, it calls `NewAccountKeySerializer()` and then `rlp.DecodeBytes(b, &serializer)`, which dispatches through: [2](#0-1) 

If the embedded `keyType` is `AccountKeyTypeRoleBased` again, `serializer.key` becomes a new `AccountKeyRoleBased`, and its `DecodeRLP` is invoked again, restarting the same recursive chain. Because each level only needs a small, valid RLP-encoded list, an attacker can nest this structure thousands of times within a transaction-sized payload, and each level adds a fresh set of Go stack frames (`DecodeRLP` → `rlp.DecodeBytes` → `Stream.Decode` → `DecodeRLP` → …) with no depth counter or limit anywhere in this call chain.

The codebase does contain an explicit guard against nested `RoleBasedKey`, but it only exists in the JSON-based `EncodeAccountKey` API path via `checkAccountKeyZeroValues(key, isNested)`: [3](#0-2) 

This check is never invoked from the RLP decode path (`AccountKeyRoleBased.DecodeRLP`) nor from account-update transaction handling, so the protection does not cover:
1. `kaia_decodeAccountKey` RPC, which directly RLP-decodes attacker-supplied bytes: [4](#0-3) 
2. `TxTypeAccountUpdate` (and its fee-delegated variants) transactions submitted via `eth_sendRawTransaction` / `kaia_sendRawTransaction`, which embed an `AccountKeySerializer`-typed key field decoded through the same recursive `DecodeRLP` chain when the raw transaction bytes are parsed by `Transaction.DecodeRLP` before any semantic validation occurs: [5](#0-4) [6](#0-5) 

Since RLP decoding happens unconditionally as soon as bytes are received (before nonce/signature/type checks), an attacker does not even need a valid signature or sufficient balance to trigger the recursive decode — the stack overflow happens during `rlp.DecodeBytes(encodedTx, tx)` itself.

### Impact Explanation
A stack overflow in Go is a fatal, unrecoverable runtime error (`runtime: goroutine stack exceeds ... stack overflow`) that crashes the entire process, not just the handling goroutine. Any public RPC endpoint (`eth_sendRawTransaction`, `kaia_sendRawTransaction`, `kaia_decodeAccountKey`) that decodes attacker-supplied RLP bytes into an `AccountKeySerializer`/`AccountKeyRoleBased` is exposed. A single unauthenticated request can crash a full node, which meets the "no-impact/DoS-only" exclusion boundary only if it were pure resource exhaustion — here it is a hard crash of the node process reachable by any public RPC caller or gasless/ordinary transaction sender, which is a High-severity availability impact on validator/full nodes providing RPC service.

### Likelihood Explanation
Likelihood is high: no authentication, balance, or gas payment is required to trigger the crash via `kaia_decodeAccountKey`, and via `eth_sendRawTransaction`/`kaia_sendRawTransaction` only a syntactically well-formed but semantically invalid transaction bytestream is needed (the recursive decode happens before the transaction is checked against the pool or account state). The payload is small (each nesting level costs only a handful of bytes), so a deeply nested structure large enough to overflow the default goroutine stack can fit well within normal transaction/RPC size limits.

### Recommendation
- Add an explicit recursion-depth counter/limit to `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., reject any `AccountKeyRoleBased` value nested inside another `AccountKeyRoleBased`), mirroring the existing `isNested` check already used in `checkAccountKeyZeroValues`.
- Apply the same "no nested RoleBasedKey" rule uniformly across all decode paths (RLP, JSON, and transaction validation), not just the `EncodeAccountKey` JSON RPC helper.
- Consider adding a general nesting-depth limit to the RLP package itself for types dispatched dynamically by an embedded type tag (as opposed to statically-typed struct fields), since this class of bug can recur wherever "self-describing"/polymorphic RLP structures are decoded.

### Proof of Concept
Conceptual construction (cannot be executed in this read-only environment):
1. Build the innermost `AccountKeyNil` or `AccountKeyFail` key and RLP-encode it via `AccountKeySerializer{keyType: AccountKeyTypeNil}`.
2. Wrap it as a single-element `AccountKeyRoleBased` (`[][]byte{innerEncoded}`) and RLP-encode that with `keyType = AccountKeyTypeRoleBased`.
3. Repeat step 2 tens of thousands of times, each iteration wrapping the previous encoded blob as the sole element of a new `AccountKeyRoleBased`.
4. Submit the final blob either:
   - directly to `kaia_decodeAccountKey`, or
   - embedded as the `key` field of a `TxTypeAccountUpdate` transaction, RLP-encoded and submitted via `eth_sendRawTransaction` / `kaia_sendRawTransaction`.
5. The node's decode of the nested structure recurses through `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` at each of the tens-of-thousands of levels, exhausting the goroutine stack and crashing the node process.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}
	return nil
