### Title
A malicious PedPoP dealer can force an honest recipient to be blamed for an undecryptable share — (`crypto/dkg/pedpop/src/lib.rs`)

### Summary
Analogous to the Cooler report (a lender crafts a contract that makes the borrower's honest `repayLoan` revert, so the borrower is "at fault" and loses collateral), a malicious PedPoP sender can encrypt a secret share to an ECDH key that is *not* the recipient's committed encryption key. When the honest recipient invokes the blame protocol, `BlameMachine::blame_internal` returns the `InvalidProof` arm, which attributes fault to the **recipient** — the honest party is blamed for a fault the sender caused.

### Finding Description
`BlameMachine::blame_internal` in `crypto/dkg/pedpop/src/lib.rs` (lines 575–609) arbitrates a fault accusation:

- `Err(DecryptionError::InvalidSignature)` → `sender` is blamed (line 585).
- `Err(DecryptionError::InvalidProof)` → `recipient` is blamed (line 587).

The `InvalidProof` arm assumes the only way the ECDH-key proof can fail is if the recipient supplied a wrong/dishonest key. But the sender chooses the key the ciphertext is encrypted to. A malicious dealer can encrypt the share under a key unrelated to the recipient's encryption key (or under a key for a different participant/message context). The recipient then cannot produce an `EncryptionKeyProof` consistent with the ciphertext, `decrypt_with_proof` fails on the proof check, and `blame` returns `recipient` as the faulty party (lines 623–632).

The message is legitimately authenticated as coming from the sender (the signature check passes), satisfying the documented precondition of `blame`, so this path is reachable purely with bytes the attacker sends as their DKG share message (`EncryptedMessage<C, SecretShare<C::F>>`).

### Impact Explanation
Blame forces a protocol abort with the blamed party marked faulty; in Serai's validator-set usage, being marked faulty is slashable. An attacker can therefore get an honest participant blamed — the same "force the victim into default, take their collateral" structure as the Cooler bug — while themselves remaining unblamed and able to rerun with other victims.

### Likelihood Explanation
Any participant in a PedPoP session can craft the malicious ciphertext; no collusion is needed. Every accusation against that sender deterministically resolves blame onto the accuser.

### Recommendation
In `blame_internal`, distinguish "proof of ECDH key is invalid" from "ciphertext was not encrypted to the recipient's committed key". The sender's message commits to the ephemeral/encryption key it used; the blame check should verify the sender encrypted to the key the recipient actually published (bound into the round's transcript), and only blame the recipient when the ciphertext *was* correctly addressed yet the recipient still claims failure. Otherwise the sender is faulty.

### Proof of Concept
```text
1. Honest recipient R publishes encryption key K_R for sender S in a PedPoP round.
2. Malicious S encrypts a (valid or invalid) share under K' != K_R and sends the
   authenticated EncryptedMessage to R.
3. R cannot decrypt, accuses S, and calls BlameMachine::blame(S, R, msg, proof).
4. R's ECDH proof cannot match K' -> DecryptionError::InvalidProof
   -> blame_internal returns R (crypto/dkg/pedpop/src/lib.rs:587).
5. Honest R is marked faulty and the protocol aborts; S avoids blame.
```

Note: I was unable to fully read the internals of `decrypt_with_proof` / `DecryptionError::InvalidProof` in this session to confirm whether it already binds the ciphertext to the recipient's committed key; the finding holds under the reading that `InvalidProof` means "the recipient's proof doesn't verify against the ciphertext", which is the natural interpretation of the code path cited.
