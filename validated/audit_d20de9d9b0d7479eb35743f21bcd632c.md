### Title
Zero-supply reward accumulation lets a dust re-staker capture the entire `queuedRewards` backlog in `_provisionReward` - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`_provisionReward` (used by `queueNewRewards`/`donateRewards`) routes any reward pushed while `totalStaked() == 0` into `rewardInfo.queuedRewards`, and folds the entire accumulated backlog into `rewardPerTokenStored` on the very next call where `totalStaked() > 0`, dividing by whatever `totalStaked()` is at that instant. Because the fold uses the instantaneous stake amount rather than a time-weighted measure, a staker who deposits a dust amount immediately before that fold captures the whole backlog, even though the backlog accrued while they held zero (or no) stake.

### Finding Description
`_provisionReward` in [1](#0-0)  implements:
```
if (totalStaked() == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    if (rewardInfo.queuedRewards > 0) {
        _amountReward += rewardInfo.queuedRewards;
        rewardInfo.queuedRewards = 0;
    }
    rewardInfo.rewardPerTokenStored += (_amountReward * 1e18) / totalStaked();
}
```
`earned()`/`_earned()` compute a user's share purely from `rewardPerToken() - userRewardPerTokenPaid` times their current balance [2](#0-1) , with no time-weighting of stake duration. `userRewardPerTokenPaid` is only updated in `_updateFor`, which is invoked through `updateReward`/`updateRewards` modifiers on reward claim/deposit paths, meaning a depositor's checkpoint is set to the rewardPerToken *at the time of their deposit*, before the next fold occurs.

Exploit flow (per the question's preconditions): sole staker withdraws all, driving `totalStaked()` to zero; manager (a permissioned actor, but the queuedRewards conservation invariant should hold regardless of who calls it) pushes rewards multiple times, all landing in `queuedRewards`; attacker deposits a dust amount (checkpointing `userRewardPerTokenPaid` at the pre-fold value); the next `queueNewRewards`/`donateRewards` call observes `totalStaked() > 0` and folds the *entire* queued backlog into `rewardPerTokenStored`, dividing only by the dust `totalStaked()`. Because the attacker is the sole staker at that point, `earned()` attributes the whole backlog to them.

Existing checks that fail to prevent this: there is no minimum holding period, no time-weighted average balance in the reward math, and no requirement that `queueNewRewards` be time-locked or streamed (the entire injected amount is applied to whoever holds balance at the moment of the call). `onlyManager` restricts who can call `queueNewRewards`, but does not restrict *when* an unprivileged staker can withdraw-then-redeposit around those calls to capture the payout.

However, the critical caveat is that `totalStaked()` here is not the pool-local sum of deposits, but `IERC20(mWOMSV).totalSupply()` — the total supply of the vote-escrow share token across the *entire* protocol [3](#0-2) . An unprivileged attacker can only drive this to zero by being the sole holder of `mWomSV` system-wide, not merely the sole staker registered in this specific rewarder/MasterMagpie instance. This is a materially different (and far more restrictive) precondition than "sole staker in the reward pool," and outside of a bootstrap phase with zero other holders, an ordinary attacker cannot unilaterally zero `totalStaked()`.

### Impact Explanation
If achievable, this is a direct theft of yield: an attacker captures reward tokens accrued over a period during which they held little or no economic stake, at the expense of other stakers who contributed real token-seconds. This matches the "theft of unclaimed yield" Immunefi impact class described in scope.

### Likelihood Explanation
Feasibility is gated entirely on the precondition that the attacker can force `totalStaked()` (global `mWomSV` supply) to zero, which requires them to be the sole holder of that token across the whole protocol — not just the sole depositor in this rewarder. In any live deployment with other `mWomSV` holders (which is the expected operating condition for a "Protocol Overview"-scale audit target), this precondition does not hold and the attack is not reachable by an unprivileged actor acting alone. The scenario is only realistic in a narrow bootstrap window (e.g., immediately after deployment before any other user has minted `mWomSV`), and it additionally depends on the reward manager repeatedly calling `queueNewRewards`/`donateRewards` at exactly the times the attacker orchestrates — a timing coincidence not fully controllable by the attacker since `queueNewRewards` is `onlyManager`-gated (though `donateRewards` is public and could be used by the attacker themselves to force the final fold).

### Recommendation
Compute reward shares using a time-weighted stake measure (e.g., checkpointed cumulative token-seconds, similar to Synthetix's `rewardPerToken` accrual model with per-second streaming) rather than instantaneous `totalStaked()` at the moment `queueNewRewards`/`donateRewards` is folded. Alternatively, stream previously queued rewards linearly over a vesting window after re-staking resumes rather than applying the entire backlog atomically to whatever balance exists at fold time, and/or require a minimum stake duration before a depositor's balance participates in folding queued rewards accrued before their deposit.

### Proof of Concept
Foundry test plan:
1. Deploy `mWOMSVBaseRewarder` with a mock `mWomSV`/`ILocker` and `MasterMagpie`, and a manager address.
2. Have the sole holder of `mWomSV` deposit into MasterMagpie/rewarder, then withdraw fully so `IERC20(mWomSV).totalSupply() == 0`.
3. As manager, call `queueNewRewards(amount1, token)` and `queueNewRewards(amount2, token)` — assert `rewards[token].queuedRewards == amount1 + amount2` and `rewardPerTokenStored` unchanged.
4. Attacker deposits `1 wei` equivalent of `mWomSV` (re-mint/re-lock dust), making `totalStaked() == 1`.
5. Manager calls `donateRewards(amount3, token)` (or `queueNewRewards`) — assert `rewardPerTokenStored` jumps by `(amount1+amount2+amount3)*1e18/1`.
6. Call `getReward(attacker, attacker)` and assert `earned` before the call equals the full backlog `amount1+amount2+amount3`, while attacker's actual token-seconds contribution is ~0 — demonstrating the accounting fails conservation relative to real stake-time contribution.
7. Note in the test that step 2 requires the attacker to be the *sole* holder of the underlying `mWomSV` token supply globally, not just the sole depositor in the rewarder, and flag this as the binding precondition for real-world exploitability.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20Metadata(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**mWOMSVDecimal) / totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```
