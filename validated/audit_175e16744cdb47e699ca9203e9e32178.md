Based on the evidence gathered, I found a solid Desktop analog. The broken invariant in the Seaport report — "a value is computed and applied against a shared mutable resource whose state can change between calculation and application, without re-validating that the calculation is still consistent with the resource's current state" — maps to how GitHub Desktop turns a user's line-level commit selection into a `git apply` patch.

### Title
Stale line-index-based diff selection can cause Desktop to silently stage/commit different lines than the user selected - ([File: app/src/lib/git/apply.ts])

### Summary
When a user makes a partial (line/hunk-level) commit selection in the Changes view, Desktop stores that selection as a set of **numeric line indices** (`DiffSelection`) tied to the diff that was rendered at selection time. When the commit is actually performed, `applyPatchToIndex` re-fetches a **fresh** diff from disk and blindly re-applies the old index-based selection to it via `formatPatch`, with no verification that the file (and therefore the hunk/line layout) hasn't changed between the time the user reviewed/selected lines and the time the commit executes.

### Finding Description
The commit flow is:
1. `app-store.ts` `_commitIncludedChanges` takes `state.changesState.workingDirectory.files`, filters by `file.selection.getSelectionType() !== DiffSelectionType.None`, and passes these `WorkingDirectoryFileChange` objects straight into `createCommit`. [1](#0-0) 
2. That funnels into `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`. [2](#0-1) 
3. `applyPatchToIndex` re-fetches the diff **at commit time** via `getWorkingDirectoryDiff(repository, file)` — a brand new read of the current on-disk state — and then formats a patch using `file.selection`, the selection object computed against whatever diff was loaded earlier (e.g., during the last UI refresh). [3](#0-2) 
4. `formatPatch` decides whether each line of the **freshly fetched** diff is included by calling `file.selection.isSelected(absoluteIndex)`, where `absoluteIndex` is a raw numeric offset (`hunk.unifiedDiffStart + lineIndex`) into the new diff's hunks. [4](#0-3) 
5. `DiffSelection.isSelected` is purely index-based with no content/hash validation — it just checks whether a given index diverges from the default selection state. [5](#0-4) 

Desktop is aware that diff content can drift from a stale selection — there is reconciliation logic in `app-store.ts` that recomputes `selectableLines` from a newly loaded diff and prunes selections that "no longer exist" — but this reconciliation happens only during a status/diff **refresh** cycle, not immediately before `applyPatchToIndex` performs its own independent, unsynchronized diff re-fetch at commit time. [6](#0-5) 

### Impact Explanation
If the file's content changes between when the working-directory diff was last loaded into UI state (from which the user made line selections) and when `applyPatchToIndex` re-fetches the diff to build the patch, the numeric line indices in the old selection no longer correspond to the same lines/hunks in the new diff. Because there's no hash/consistency check tying `file.selection` to the diff instance it was computed against at the exact moment of staging, this can result in the wrong lines being included in — or excluded from — the resulting commit, without any warning to the user. This is a "silent corruption of what the user commits" scenario: the user believes they reviewed and approved a specific line-level change set, but the actual staged/committed content can diverge from what was shown and approved.

A realistic trigger is any process that rewrites the working file between the diff being rendered and the commit executing — for example, a git `clean`/`smudge` filter or `pre-commit`/`post-checkout` hook defined in a cloned repository's `.gitattributes`/hooks (attacker-controlled repository content), a background formatter/linter integration, or simply another tool touching the file — none of which require local/physical access or prior malware beyond cloning an untrusted repository that ships such filters/hooks.

### Likelihood Explanation
This requires a specific timing window: the diff must be loaded/rendered, the user must make a partial line selection, and the underlying file content must change (via a filter, hook, or external tool) before the user clicks "Commit." This is plausible in workflows using auto-formatting-on-save tools, lint-staged/husky-style hooks, or malicious git attribute filters shipped in a cloned repository, but it is not trivially triggerable by a remote attacker without some local tooling being present. Likelihood is therefore moderate rather than trivial, but the invariant genuinely lacks any consistency check.

### Recommendation
Before applying a patch based on a cached `DiffSelection`, `applyPatchToIndex` (and the broader commit flow) should verify that the diff it just fetched is structurally/content-equivalent to the diff the selection was computed against (e.g., by comparing a hash of the diff text, or by re-validating that all selected line indices still map to includeable lines of the same type in the fresh diff, analogous to the reconciliation already done in `app-store.ts`'s `selectableLines` logic). If a mismatch is detected, Desktop should refuse to stage the stale selection and instead prompt the user to re-review the diff.

### Proof of Concept
1. Clone a git repository that defines a `clean`/`smudge` filter (via `.gitattributes` + `.git/config` filter driver) or a `pre-commit`/other hook that rewrites a tracked file's content when it's touched.
2. Modify the file so it has multiple hunks; open it in Desktop's Changes view and partially select specific lines (e.g., select only lines in hunk 2).
3. Trigger the filter/hook to rewrite the file's content in a way that shifts line numbers/hunks (e.g., insert/remove lines earlier in the file) right before clicking Commit.
4. Click "Commit". `applyPatchToIndex` re-fetches the diff (now shifted) and applies the stale index-based selection via `formatPatch`, resulting in a patch that stages different lines than the ones visually selected by the user, with no warning shown. [3](#0-2) [7](#0-6)
