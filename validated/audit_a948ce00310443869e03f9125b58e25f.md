### Title
Missing on-curve validation in `AccountKeyWeightedMultiSig.CheckInstallable` allows an `AccountUpdate` transaction to install off-curve public keys into consensus state - ([File: blockchain/types/accountkey/account_key_weighted_multi_sig.go])

### Summary
The `secp256k1-node` advisory (CVE-2024-48930) is a missing "point is on the curve" check when a compressed public key is loaded, which lets an attacker feed malformed key material into later elliptic-curve operations. Kaia contains the exact same missing-check pattern in its account-key validation layer: `AccountKeyPublic.CheckInstallable` validates that `(X,Y)` lies on the S256 curve before the key is allowed into consensus state, but the sibling type `AccountKeyWeightedMultiSig.CheckInstallable` — which is reachable from any account holder's `AccountUpdate`/`FeeDelegatedAccountUpdate` transaction — never performs this check for any of its member keys.

### Finding Description
`AccountKeyPublic.CheckInstallable` explicitly rejects a key whose point is not on the S256 curve: [1](#0-0) 

`AccountKeyWeightedMultiSig.CheckInstallable`, however, only checks zero-length keys, zero threshold, key-count limits, duplicate keys, zero weight, weighted-sum overflow, and threshold-satisfiability — it never calls `IsOnCurve` on any member key's `(X, Y)`: [2](#0-1) 

`CheckInstallable` is the sole gatekeeper used during transaction validation/execution to admit a new key into an account, invoked via `AccountCommon.ReplaceKey`: [3](#0-2) 

and reached by any signer through `TxInternalDataAccountUpdate.Validate` → `accountkey.CheckReplacable` → `CheckInstallable`, followed by `Execute` → `stateDB.UpdateKey`: [4](#0-3) 

Once an off-curve `(X, Y)` pair is accepted into a `WeightedPublicKey.Key` (`*PublicKeySerializable`), the divergence with the properly-checked `AccountKeyPublic` path becomes visible at serialization time: `PublicKeySerializable.EncodeRLP` (used to persist every key inside `AccountKeyWeightedMultiSig.Keys` into the account trie) explicitly guards against this and returns `errNotS256Curve`: [5](#0-4) 

But this guard fires only at RLP-encoding time — i.e., after `CheckInstallable` has already accepted the malformed key and after `UpdateKey`/`Execute` have already mutated the in-memory state object, deep inside `StateDB.Commit`'s trie update path: [6](#0-5) 

This is structurally identical to the reported bug class: a decode/deserialize path (`loadCompressedPublicKey` in the advisory, `AccountKeyWeightedMultiSig.CheckInstallable` here) is missing the on-curve check that a sibling path (`loadUncompressedPublicKey` in the advisory, `AccountKeyPublic.CheckInstallable` here) correctly performs, letting attacker-chosen invalid curve points flow deeper into the system than intended.

### Impact Explanation
Any externally-owned account holder can submit a single `AccountUpdate` (or `FeeDelegatedAccountUpdate`/`...WithRatio`) transaction whose new key is an `AccountKeyWeightedMultiSig` containing one or more `WeightedPublicKey` entries with attacker-chosen `(X, Y)` values that do not satisfy `y² = x³ + 7`. `CheckInstallable` accepts it, `Validate`/`Execute` commit it into the state object as the account's new key, and the inconsistency only surfaces later when the state object is serialized for trie storage during block commit. Because `EncodeRLP` on the malformed key returns an error rather than being caught during transaction admission, this is a state-transition-time failure rather than a mempool/tx-pool rejection — meaning the divergence between "accepted at execution" and "rejected at commit" can produce inconsistent behavior across the codebase's serialization call sites (RPC `MakeRPCOutput`, trie commit, snapshot journaling, etc.), risking node crashes on block commit or state root divergence between honest nodes that handle the resulting encode error differently.

### Likelihood Explanation
High reachability: the attack requires only one signed `AccountUpdate` transaction from any address, no special privileges, no consensus/network position, and no reliance on any other party's cooperation. The vulnerable `CheckInstallable` implementation is unconditionally exercised on every multisig `AccountUpdate`.

### Recommendation
Add the same on-curve validation performed in `AccountKeyPublic.CheckInstallable` to `AccountKeyWeightedMultiSig.CheckInstallable` (and transitively ensure `AccountKeyRoleBased.CheckInstallable` propagates it for multisig sub-roles), rejecting any key whose `(X, Y)` is not `IsOnCurve` before the key is admitted, matching `kerrors.ErrNotOnCurve` used in `AccountKeyPublic`.

### Proof of Concept
1. Attacker crafts `WeightedPublicKeys` containing at least one `PublicKeySerializable{X: <arbitrary>, Y: <arbitrary>}` not satisfying the S256 curve equation, wrapped in `AccountKeyWeightedMultiSig` with a valid threshold and weights (satisfying all other `CheckInstallable` checks).
2. Attacker submits an `AccountUpdate` transaction (`TxInternalDataAccountUpdate`) from their own account, signed with the account's current valid key, setting `TxValueKeyAccountKey` to this malformed multisig key — see the existing legitimate flow shown in `tests/kaia_scenario_test.go` for how such a tx is normally built and signed. [7](#0-6) 
3. `TxInternalDataAccountUpdate.Validate` → `accountkey.CheckReplacable` → `AccountKeyWeightedMultiSig.CheckInstallable` returns `nil` (no on-curve check present), so the transaction is accepted and executed, setting the account's key in state.
4. On the next `StateDB.Commit`, the account's `AccountKeyWeightedMultiSig` (containing the off-curve key) is RLP-encoded for the account trie; `PublicKeySerializable.EncodeRLP` returns `errNotS256Curve`, which fires only at this late stage rather than at transaction validation, illustrating the exploitable gap between admission-time and serialization-time validation.

func (a *AccountKeyWeightedMultiSig) CheckInstallable(currentBlockNumber uint64) error {
	sum := uint(0)
	prevSum := uint(0)
	if len(a.Keys) == 0 {
		return kerrors.ErrZeroLength
	}
	if a.Threshold == 0 {
		return kerrors.ErrZeroThreshold
	}
	if uint64(len(a.Keys)) > MaxNumKeysForMultiSig {
		return kerrors.ErrMaxKeysExceed
	}
	keyMap := make(map[string]bool)
	for _, k := range a.Keys {
		// Do not allow zero weight.
		if k.Weight == 0 {
			return kerrors.ErrZeroKeyWeight
		}
		sum += k.Weight

		b, err := rlp.EncodeToBytes(k.Key)
		if err != nil {
			// Do not allow unserializable keys.
			return kerrors.ErrUnserializableKey
		}
		if _, ok := keyMap[string(b)]; ok {
			// Do not allow duplicated keys.
			return kerrors.ErrDuplicatedKey
		}
		keyMap[string(b)] = true

		// Do not allow overflow of weighted sum.
		if prevSum > sum {
			return kerrors.ErrWeightedSumOverflow
		}
		prevSum = sum
	}
	// The weighted sum should be larger than the threshold.
	if sum < a.Threshold {
		return kerrors.ErrUnsatisfiableThreshold
	}
	return nil
}

// EncodeRLP encodes ecdsa.PublicKey using RLP.
// For now, it supports S256 curve only.
// For that reason, this function serializes only X and Y using CompressPubkey().
func (p *PublicKeySerializable) EncodeRLP(w io.Writer) error {
	// Do not serialize if it is not on S256 curve.
	if !crypto.S256().IsOnCurve(p.X, p.Y) {
		return errNotS256Curve
	}
	return rlp.Encode(w, crypto.CompressPubkey((*ecdsa.PublicKey)(p)))
}
