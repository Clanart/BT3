### Title
Untrusted `ReceivedOutput` deserialization accepts an offset that cannot spend the embedded output - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` reconstructs the semantic invariant linking a Taproot output to the scalar offset required to spend it without validation. An attacker can supply a syntactically valid serialized object containing an arbitrary `TxOut`, `OutPoint`, and unrelated scalar. The object is subsequently reported as spendable wallet value, but `SignableTransaction::multisig` rejects it because the offset-derived key does not match the output’s `script_pubkey`. Severity: Medium.

### Finding Description
`ReceivedOutput` contains three fields: the scalar `offset`, the claimed Bitcoin `output`, and the claimed `outpoint` [1](#0-0) . Its deserializer independently reads those fields and returns them without proving that `output.script_pubkey` equals the script derived from the wallet’s base key plus `offset` [2](#0-1) .

The actual invariant exists only later in `SignableTransaction::multisig`, which applies the stored offset to the threshold key and compares the derived P2TR script to the previous output’s `script_pubkey` [3](#0-2) . Consequently, deserialization accepts a state that the spend path necessarily rejects.

This is analogous to reinitializing a boundary value under inconsistent state: the serialized object initializes a derived accounting claim—the spendable output and its offset—from independent fields without enforcing the relation that makes the claim valid.

### Impact Explanation
An attacker able to feed bytes to `ReceivedOutput::read` can cause an application to account for funds as received even though those funds cannot be spent through this wallet implementation. `SignableTransaction::new` sums the embedded output value and carries the unverified offset into the spendable transaction [4](#0-3) . Signing setup then fails when the derived key’s script does not match the claimed output [5](#0-4) .

The result is false balance accounting and unusable reported funds. It does not directly produce an unauthorized signature because the spending path catches the inconsistency.

### Likelihood Explanation
The attack requires the calling application to deserialize attacker-controlled `ReceivedOutput` data rather than obtaining the object solely from `Scanner::scan_transaction` or `Scanner::scan_block`. Objects produced by the scanner are internally consistent because they pair a registered offset with the matching observed `script_pubkey` [6](#0-5) . The vulnerability is therefore conditional on untrusted serialized wallet state, but that input path is explicitly exposed by the public `read` API.

### Recommendation
Do not deserialize `ReceivedOutput` as trusted spendable state. Prefer one of:

- Re-scan the embedded transaction output and outpoint through `Scanner`, deriving the offset instead of trusting the serialized scalar.
- Change deserialization to take the wallet base key and enforce  
  `p2tr_script_buf(base_key + G * offset) == Some(output.script_pubkey)`.
- Store authenticated scanner state only, and reject any unauthenticated serialized `ReceivedOutput`.

At minimum, document that `ReceivedOutput::read` is only safe for trusted storage and must not be used for attacker-supplied input.

### Proof of Concept
Conceptually, serialize:

1. Any canonical secp256k1 scalar as `offset`.
2. Any valid `TxOut` whose `script_pubkey` is not the P2TR script for `base_key + offset`.
3. Any valid `OutPoint`.

`ReceivedOutput::read` succeeds because it performs only syntactic parsing [2](#0-1) . Passing the resulting object to `SignableTransaction::new` includes its claimed value and offset [4](#0-3) , while `SignableTransaction::multisig` returns `None` when the derived script does not equal the embedded `script_pubkey` [3](#0-2) .
