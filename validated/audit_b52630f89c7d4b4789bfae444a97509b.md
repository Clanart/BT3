## Title
Duplicate-input-token full-fill escrow drain in same-chain partial fills - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` computes the escrow to release for a completed output leg by reading the *entire* remaining `_orders[commitment][token]` balance whenever that leg's cumulative fill reaches `totalRequired`, instead of computing the leg's own proportional share. Because `_orders` is keyed only by `(commitment, token)` — not by output index — an order whose `inputs[]` array reuses the same token address for two different output legs lets a solver who completes the *smaller* leg first sweep escrow that was reserved for the *other*, still-unfilled leg.

### Finding Description
`_orders` is a flat `mapping(bytes32 => mapping(address => uint256))` that accumulates escrow per `(commitment, token)`, not per output index: [1](#0-0) 

During `placeOrder`, escrow is added with `_orders[commitment][token] += reducedInputs[i].amount;` for each input index `i`, so if two indices share the same input token, their escrow amounts are merged into a single balance (confirmed in the Tron sibling contract, which has identical semantics): [2](#0-1) 

`_fillSameChain` iterates output legs by index `i`, tracking per-leg progress in `_partialFills[commitment][outputToken]`, and computes the escrow to release for leg `i` like this: [3](#0-2) 

When `amountFilled == totalRequired` for leg `i` (i.e. that specific output leg is now fully satisfied), the code takes a shortcut and releases `_orders[commitment][token]` in full — the entire live balance for that token — rather than the proportional amount tied to leg `i`. If `order.inputs[j].token == order.inputs[i].token` for some other leg `j != i` that has not yet been filled, the balance being released also contains `j`'s escrow. The solver who happens to complete leg `i` (which can be made deliberately small) collects both legs' escrow, while leg `j`'s output has not been delivered to the beneficiary at all — `isFullyFilled` stays `false` for the order, but `_withdraw` has already paid out `j`'s escrowed tokens to leg `i`'s filler.

Nothing in `_validateParams` or `placeOrder` rejects duplicate input tokens across indices, and the "full fill" shortcut path has no additional check that other legs remain unfilled before it snapshots the whole per-token balance.

### Impact Explanation
This is a direct loss-of-funds / wrong-beneficiary bug for the Intent Gateway's same-chain escrow: a user's escrowed input tokens meant to pay for output leg `j` can be captured by whoever completes an unrelated, smaller leg `i` that happens to share the same input token address. This matches the bounty's "stealing or loss of funds" and "logic attacks / wrong beneficiary or amount" categories, is triggerable by an ordinary unprivileged solver with no relayer/prover/admin trust assumption, and requires only crafting/selecting an order whose `inputs[]` array has a duplicate token across two output legs (fully permitted by current validation).

### Likelihood Explanation
Likelihood is constrained by whether order-placers (users or the off-chain SDK) actually construct multi-leg orders with a repeated input token backing two different output assets — a legitimate but non-default use of the multi-asset order schema. Because there is no on-chain guard preventing this construction, and a solver (not the user) chooses fill order/amounts, a solver can specifically target such an order once one exists, making exploitation straightforward once the precondition (duplicate input token across legs) occurs; the precondition itself is not enforced against by the protocol.

### Recommendation
Track escrow per output index (or per `(commitment, index)`) rather than aggregating purely by token address, or compute the full-fill release for a leg as `order.inputs[i].amount - previously released for index i` instead of reading the shared token balance. Alternatively, reject orders at `placeOrder` time whose `inputs[]` contain duplicate non-zero token addresses when they back multiple output legs, closing the aliasing precondition entirely.

### Proof of Concept
1. User places a same-chain order with two output legs, both backed by the same input token `USDC`:
   - leg 0: output `1 DAI`, input `1 USDC` (`order.inputs[0].token = USDC`)
   - leg 1: output `1000 DAI`, input `1000 USDC` (`order.inputs[1].token = USDC`)
   - `_orders[commitment][USDC]` = `1001 USDC` after `placeOrder` (merged, per `IntentsBase.sol` line 140 and the accumulation logic shown above).
2. Solver A fills leg 0 completely by sending `1 DAI` to the beneficiary. In `_fillSameChain`, for `i = 0`: `alreadyFilled = 0`, `fillAmount = 1 DAI`, `amountFilled = totalRequired = 1 DAI` → the `if (amountFilled == totalRequired)` branch executes:
   `escrowedAmount = _orders[commitment][USDC]` → returns `1001 USDC` (the full merged balance), not `1 USDC`.
   See [4](#0-3)  and `_withdraw` decrementing `_orders[commitment][USDC]` to `0`: [5](#0-4) .
3. Solver A receives all `1001 USDC` for delivering only `1 DAI` of value. Leg 1 (`1000 DAI` owed to the beneficiary) is never filled — `isFullyFilled` is `false` (leg 1 still shows `remaining = 1000 DAI`), so the order stays open — but there is no escrow left to pay whoever eventually fills leg 1, since `_orders[commitment][USDC]` is now `0`.
4. Any subsequent solver attempting to fill leg 1 will have their proportional escrow computation `(order.inputs[1].amount * fillAmount) / totalRequired` — or a `_withdraw` call — draw against an already-zeroed balance, reverting with `UnknownOrder()` or paying out zero, permanently locking/losing the user's second-leg funds while the beneficiary/user is shorted the intended in-kind value.
