### Title
`ReceivedOutput` treats an embedded, unverified `TxOut` as the authoritative definition of the referenced UTXO — claimed value/script conflated with the actual outpoint's contents - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the vault using `totalSupply` to mean `totalAssets`, `ReceivedOutput` defines a spendable input by a self-declared `TxOut` rather than by the actual contents of the `OutPoint` it references. `ReceivedOutput::read` accepts an arbitrary scalar offset, an arbitrary `TxOut` (value + script_pubkey), and an arbitrary `OutPoint` from raw bytes, with no consistency check. [1](#0-0)  `SignableTransaction::new` then computes the input sum (`input_sat`) from these claimed values and uses them for fee/change accounting. [2](#0-1) 

### Finding Description
A real "received output" is defined by the UTXO set: `outpoint` identifies it, and the chain determines its `value` and `script_pubkey`. `ReceivedOutput` inverts this definition — it carries a `TxOut` supplied alongside the outpoint and treats it as authoritative. When deserialized via `ReceivedOutput::read`, nothing verifies that `output` is the real content of `outpoint`. Downstream, `SignableTransaction::new` sums `input.output.value` to decide solvency and derive the change amount. [3](#0-2)  The only validation, in `SignableTransaction::multisig`, checks that the claimed `script_pubkey` equals the script derived from `keys.offset(offset)` — it never verifies the value, nor that the `TxOut` matches the outpoint. [4](#0-3)  Finally, `TransactionSignMachine::sign` commits to the claimed prevouts via `Prevouts::All` in the Taproot sighash. [5](#0-4) 

### Impact Explanation
Two consequences follow from using the claimed `TxOut` as the definition of the input:

1. **Misaccounting of received funds.** Any consumer that credits deposits based on the `ReceivedOutput`'s `output.value` will account an arbitrary amount for a real (or nonexistent) outpoint — funds reported received that are not actually present, the exact class of the M-04 accounting-vs-spec violation.
2. **Unspendable transactions / fee corruption.** Because the Taproot key-spend sighash commits to `Prevouts::All` (i.e., the claimed amounts and scripts), any deviation between the claimed `TxOut` and the real UTXO makes the produced signature invalid; the change computation can also be driven off the inflated value, producing outputs the inputs cannot cover. The multisig signs a transaction that can never confirm.

### Likelihood Explanation
Reachable by any unprivileged party able to feed bytes to `ReceivedOutput::read` (explicitly in-scope) or otherwise supply a `ReceivedOutput` to `SignableTransaction::new`/`multisig`. No key material, validator status, or collusion is required — only a crafted scalar/TxOut/OutPoint triple whose script matches the tweaked key, which is trivially constructed for a known group key via `p2tr_script_buf`. [6](#0-5) 

### Recommendation
Do not treat the embedded `TxOut` as definitional. Either:
- Resolve the prevout from the chain by `outpoint` at signing time (or carry a proof such as the block/merkle path) so `value`/`script_pubkey` are chain-derived, not caller-derived; or
- At minimum, keep `ReceivedOutput` construction exclusive to `Scanner::scan_transaction`/`scan_block` — which populate `output` from real transaction data [7](#0-6)  — and remove or gate the untrusted-bytes `read` path; where deserialization is required, re-validate each input's `TxOut` against the outpoint before signing.

### Proof of Concept
1. Attacker learns the vault tweaked script `S = p2tr_script_buf(key + G*offset)`.
2. Attacker serializes `ReceivedOutput { offset, output: TxOut { value: 100_000_000, script_pubkey: S }, outpoint: <real outpoint with dust or attacker-controlled> }` and feeds it through `ReceivedOutput::read`.
3. `SignableTransaction::new` computes `input_sat = 100_000_000`, approves payments/change accordingly, and `multisig` accepts it because the script check passes.
4. `sign` produces shares committing to `Prevouts::All` containing the fabricated amount; `complete` yields a transaction whose signatures fail BIP-341 verification, while any accounting layer that trusted `output.value` has recorded 1 BTC received that is not spendable.
