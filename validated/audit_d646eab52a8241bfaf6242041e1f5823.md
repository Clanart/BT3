This is a real, locally-provable analog: exit intent does not immediately revoke privileged authority, letting an already-departing party act with a permission it should no longer hold, exactly like the ragequit report's "still-valid No vote."

### Title
Exiting collator retains fisherman veto power for a full session after declaring exit, enabling griefing deletion of valid state commitments - (File: parachain/runtimes/nexus/src/ismp.rs, modules/pallets/fishermen/src/lib.rs, modules/pallets/collator-manager/src/lib.rs)

### Summary
`pallet-fishermen`'s `veto_state_commitment`/`blacklist_*` calls are gated by `IsCollator::contains(&account)`. On the nexus runtime, `IsCollator` is defined as membership in `pallet_session::Validators::<Runtime>`, the *current session's* validator set [1](#0-0) . A collator that calls `collatorManager.unbond` is immediately excluded from the `candidates` list computed for the *next* session [2](#0-1) , but `pallet_session::Validators` is only updated at the *next* session rotation, and Substrate's session-key queuing model means the effective validator set for session N+1 is decided during session N — the outgoing collator keeps `Validators` membership (and thus `IsCollator == true`) for the remainder of the current session. During that entire window the exiting/unbonding collator can still call `veto_state_commitment`, which unconditionally deletes any state commitment (`ensure!(T::IsCollator::contains(&account), ...)` is the only gate, no re-check of stake/bond status) [3](#0-2) .

### Finding Description
The trust model for fishermen is: a fisherman is an actively-bonded, currently-selected collator who has skin in the game and is subject to the 7‑day unbonding delay specifically so "the protocol has time to act on any detected misbehaviour ... before the operator can walk away with their stake" [4](#0-3) . However, `unbond()` only stops future *selection*; it does not revoke the account's current-session validator membership, and `IsCollator` is keyed off that stale membership rather than off `Unbonding`/`RemovedValidators` state [5](#0-4) [6](#0-5) .

This is structurally identical to the ragequit bug: the account has declared exit (`unbond`, analogous to ragequit) and is already excluded from future participation (`candidates` filter, `Unbonding` map), yet its stale authorization (`IsCollator` / session `Validators`) remains valid and lets it exercise privileged one-sided power — here, unilateral deletion of a `StateCommitment` via `veto_state_commitment`, requiring no proof of fraud ("They aren't required to provide any proofs for this — any single collator's call deletes the commitment" [7](#0-6) ). Since the departing account already stopped being economically incentivized to act honestly (it is walking away and no automatic slashing exists — "cryptographic slashing conditions" are explicitly future work [8](#0-7) ), it has the same "revenge" incentive as the ragequitting shareholder: veto (delete) legitimate state commitments on its way out, with only governance-after-the-fact as a remedy.

`delete_state_commitment` also resets `LatestStateMachineHeight` back to the previous height when the vetoed height is the current latest [9](#0-8) , which reopens that height for a fresh consensus update — meaning the corrupted value directly reachable through this path is `LatestStateMachineHeight[id]` / `BoundedStateCommitments[id, height]`, and a subsequent resubmission at that height could differ from the one honestly vetoed, since no other guard cross-checks the resubmitted state against the deleted one.

### Impact Explanation
This does not steal funds directly, but it does cause **unauthorized state mutation**: an account that has already relinquished its stake/authority (mid-unbonding) can unilaterally delete a validly-accepted `StateCommitment` that other messages/relayers depend on, and force a height reset that reopens the slot for a different commitment to be accepted later. This is a manipulation of consensus state acceptance — matching the "false proof/state acceptance" and "logic attacks" categories in the impact gate — arising from a local authorization-staleness bug rather than any assumption of a malicious peer/relayer/prover (the actor here is a previously-legitimate, currently-departing collator exploiting a stale permission check, not an external compromised party).

### Likelihood Explanation
Any collator can trigger this by simply calling `collatorManager.unbond()` and then, before the session rolls over, calling `fishermen.veto_state_commitment` (or the blacklist calls) on a legitimate height/proxy/claim. No special privilege, proof, or timing race with other actors is required — only knowledge of the session boundary, which is public. This is a straightforward, self-triggerable sequence available to any current collator planning to exit.

### Recommendation
Gate `IsCollator` (or add an explicit check inside `pallet-fishermen`'s calls) on `!pallet_collator_manager::Unbonding::<Runtime>::contains_key(account)` in addition to session-validator membership, so that once an account has started unbonding it immediately loses veto/blacklist authority, mirroring how it's already excluded from `new_session`'s `candidates` filter. Alternatively, revoke `Validators` membership (or intersect `IsCollator` with `RemovedValidators`/`Unbonding`) at the moment `unbond()` is called rather than waiting for the next session rotation.

### Proof of Concept
1. Collator `A` is in the current session's `pallet_session::Validators` set (has previously registered/bonded via `pallet-collator-manager`).
2. `A` calls `CollatorManager::unbond(origin=A)` — succeeds, inserts `Unbonding[A] = withdrawable_at`, excludes `A` from `new_session`'s candidate filter [5](#0-4) .
3. Before the session rotates, `A` calls `Fishermen::veto_state_commitment(origin=A, height)` targeting a currently valid, in-challenge-period `StateCommitment`.
4. `IsCollator::contains(&A)` still returns `true` because `pallet_session::Validators` has not yet been updated [6](#0-5) .
5. `BoundedStateCommitments[id, height]` is deleted and, if `height` was the latest, `LatestStateMachineHeight[id]` is rolled back to `PreviousStateMachineHeight[id]` [10](#0-9) , even though `A` no longer has any stake-backed accountability for this action since it is already exiting.

		pub fn veto_state_commitment(
			origin: OriginFor<T>,
			height: StateMachineHeight,
		) -> DispatchResult {
			let account = ensure_signed(origin)?;
			ensure!(T::IsCollator::contains(&account), Error::<T>::UnauthorizedAction);

			let ismp_host = <T as Config>::IsmpHost::default();
			let commitment =
				ismp_host.state_machine_commitment(height).map_err(|_| Error::<T>::VetoFailed)?;
			ismp_host.delete_state_commitment(height).map_err(|_| Error::<T>::VetoFailed)?;

			Self::deposit_event(Event::StateCommitmentVetoed {
				height,
				commitment,
				fisherman: account.clone(),
			});
			pallet_ismp::Pallet::<T>::deposit_event(
				ismp::events::Event::StateCommitmentVetoed(StateCommitmentVetoed {
					height,
					fisherman: account.as_ref().to_vec(),
				})
				.into(),
			);

			Ok(())
		}
