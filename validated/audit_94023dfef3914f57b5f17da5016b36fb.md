### Title
Worker pool close/submit race causes panic from send on closed channel - (File: evmrpc/worker_pool.go)

### Summary
`WorkerPool.Submit` / `SubmitWithMetrics` check the `closed` flag under a read lock, release the lock, and only afterward attempt to send the task on `wp.taskQueue`. `WorkerPool.Close` sets `closed = true` under the write lock and then closes both `wp.done` and `wp.taskQueue`. Because the closed-check and the channel send are not performed atomically under the same lock, a `Close()` call can run to completion in the window between a submitter's `RUnlock` and its subsequent `wp.taskQueue <- task`, leaving the submitter to send on an already-closed channel.

### Finding Description
`Submit` and `SubmitWithMetrics` both follow the same pattern: [1](#0-0) 

The closed check is released before the actual channel operation happens: [2](#0-1) 

`Close()` acquires the write lock, flips `closed`, releases the lock, and then closes the channels the submitter is about to write to: [3](#0-2) 

This is structurally the same bug class as CVE-2021-47577: the code checks an exit/closing condition, but the resource teardown that the exit path performs (`close(wp.taskQueue)`) can complete after the check succeeds but before the dependent operation (`send` in Go, `task_work` creation in the kernel) executes. In Go, sending on a closed channel unconditionally panics, regardless of a concurrent `select` with a `done` case — the race is between `RUnlock` and entry into the `select`, not something the `select`'s `<-wp.done` case can protect against, since the channel could already be closed by the time the `select` statement's send case is evaluated.

### Impact Explanation
A goroutine that hits `wp.taskQueue <- task` (or `<- wrappedTask`) on a closed channel panics with "send on closed channel." Unlike the worker goroutines themselves, which wrap task execution in `recover()` [4](#0-3) , the `Submit`/`SubmitWithMetrics` call sites are not shown to have equivalent panic recovery. If the calling code (e.g. request/filter handling paths in `evmrpc/filter.go` and `evmrpc/server.go`) doesn't itself recover, an unrecovered panic on a goroutine crashes the entire process, i.e. the public EVM JSON-RPC node.

### Likelihood Explanation
The global worker pool (`GetGlobalWorkerPool`) is shared for concurrent request-processing work in the EVM RPC layer [5](#0-4) . The race requires `Close()` to run concurrently with `Submit`, which is plausible during node shutdown/restart or wherever the pool lifecycle is managed outside of steady-state serving. This is a narrow timing window and requires the pool to be closed while requests are still in flight, so likelihood is moderate rather than trivially reproducible on every request.

### Recommendation
Perform the closed-check and the channel send under the same lock (or use a single `sync.Once`-guarded close combined with holding the read lock across the entire send), so that `Close()` cannot complete channel teardown while a `Submit` call is in the process of checking-then-sending. Alternatively, recover from panics at the `Submit`/`SubmitWithMetrics` call boundary and treat a panic there identically to the "pool is closing" error path.

### Proof of Concept
1. Create a `WorkerPool` and call `Start()`.
2. From goroutine A, call `Submit(task)`; have it pause right after `wp.mu.RUnlock()` (line 157) and before the `select` (line 159) — e.g. via a scheduler race or `GOMAXPROCS(1)` with a preemption point.
3. From goroutine B, call `Close()` concurrently — it sets `closed = true`, then `close(wp.done)` and `close(wp.taskQueue)`.
4. Goroutine A resumes and executes `wp.taskQueue <- task` on the now-closed channel, causing an unrecovered panic ("send on closed channel"), crashing the process if not recovered up the stack.

func (wp *WorkerPool) SubmitWithMetrics(task func()) error {
	// Check if pool is closed first
	wp.mu.RLock()
	if wp.closed {
		wp.mu.RUnlock()
		return fmt.Errorf("worker pool is closing")
	}
	wp.mu.RUnlock()

	queuedAt := time.Now()

	// Wrap the task with metrics
	wrappedTask := func() {
		startedAt := time.Now()
		wp.Metrics.RecordTaskStarted(queuedAt)
		defer wp.Metrics.RecordTaskCompleted(startedAt)
		task()
	}

	select {
	case wp.taskQueue <- wrappedTask:
		wp.Metrics.RecordTaskSubmitted()
		return nil
	case <-wp.done:
		return fmt.Errorf("worker pool is closing")
	default:
		// Queue is full - fail fast
		wp.Metrics.RecordTaskRejected()
		return fmt.Errorf("worker pool queue is full")
	}
}

func (wp *WorkerPool) Close() {
	wp.mu.Lock()
	if wp.closed {
		wp.mu.Unlock()
		return // Already closed
	}
	wp.closed = true
	wp.mu.Unlock()

	close(wp.done)      // Signal that no new tasks should be submitted.
	close(wp.taskQueue) // Close the queue to signal workers to drain and exit.
	wp.wg.Wait()        // Wait for all workers to finish their remaining tasks.
}
