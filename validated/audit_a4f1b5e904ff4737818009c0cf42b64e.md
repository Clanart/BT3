### Title
Unchecked `u64` multiplication/addition in fee and funds arithmetic wraps, bypassing the `NotEnoughFunds` and minimum-fee checks - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` performs fee and balance accounting with plain `u64` arithmetic in release mode, where overflow wraps silently. Two sites are affected: `let mut needed_fee = fee_per_vbyte * vbytes` (line 206, repeated at line 227 for `fee_with_change`) and `if input_sat < (payment_sat + needed_fee)` (line 215), plus the unchecked sums at lines 175, 187, and `fee()` at lines 138–141. A wrapped `needed_fee` or `payment_sat + needed_fee` lets the `NotEnoughFunds` and `TooLowFee` checks pass when they should fail, producing a transaction whose outputs exceed or barely underspend its inputs — an invalid or unrelayable transaction the threshold group then signs. ### Finding Description
The analog of the APR integer-overflow-leading-to-out-of-bounds-write bug class in Serai is the silent wraparound in `SignableTransaction::new`'s value accounting. Unlike the change-amount path, which correctly uses `checked_sub` (line 228), the primary paths do not:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) can wrap if `fee_per_vbyte` is large, collapsing the required fee toward zero. The `TooLowFee` check on line 211 then compares a wrapped (small) `needed_fee` against the relay minimum and passes, while the change branch (lines 227–233) computes `fee_with_change` with the same wrapped multiply, so the change output absorbs nearly all input value minus a tiny fee — the transaction is signed with a near-zero real fee and will never relay/confirm, freezing the change output.
- `payment_sat` (line 187) sums attacker-influenced payment amounts with plain `Sum`, and `payment_sat + needed_fee` (line 215) can wrap to a small value, defeating the `NotEnoughFunds` check. `SignableTransaction::new` then returns `Ok` with outputs whose declared `Amount`s exceed the inputs, and `fee()` (lines 138–141) underflows, wrapping to a huge `u64` or panicking depending on build flags.
- `commitments[c]` indexing in `TransactionSignMachine::sign` (line 368) and `shares.remove(0)` (line 419) assume well-formed preprocess/share vectors, but the overflow above is the root-cause reachable defect matching the reported class.

The inputs to this arithmetic — `payments`, `fee_per_vbyte`, `change`, and `inputs` (`Vec<ReceivedOutput>`, populated by the `Scanner` from untrusted on-chain transaction data) — are all reachable from public inputs per the scan scope: an unprivileged party causes a plan/payment to be constructed, and the resulting `SignableTransaction` is what the FROST machines sign via `TransactionSignMachine::sign` → `taproot_key_spend_signature_hash` (lines 383–390). ### Impact Explanation
Two concrete impacts:

1. **Signing of an unintended / invalid transaction.** With `payment_sat + needed_fee` wrapped, `NotEnoughFunds` is bypassed and the multisig produces a signed transaction whose outputs exceed its inputs. Depending on `Amount::from_sat` validation this either panics at construction or produces a transaction Bitcoin nodes reject as consensus-invalid — burning a signing attempt and, where a `Prevouts::All` sighash commits to the malformed `prevouts`, yielding signatures over a transaction that can never confirm.
2. **Funds frozen via wrapped fee.** With `needed_fee` wrapped small, the real fee becomes `input_sat - payment_sat - change ≈ dust`, below the relay minimum. The signed transaction is valid but unbroadcastable/unconfirmable, leaving the change output (the bulk of the multisig's funds) locked behind a transaction that will not mine — funds reported as moved that are not spendable.

### Likelihood Explanation
Reachability is moderate-to-high: `fee_per_vbyte` and `payments` flow from the signing plan built by the processor from scanned/submitted data, and `inputs` come from `ReceivedOutput`s the scanner derives from arbitrary Bitcoin transactions sent to the multisig address. Overflow of `payment_sat` requires crafted payment amounts, and `fee_per_vbyte * vbytes` requires only a large fee parameter, neither of which requires any key material or validator privilege. The code itself acknowledges the value of checked arithmetic (line 228 uses `checked_sub` for change) yet leaves the identical operations unchecked elsewhere, indicating the overflow path was not systematically handled.

### Recommendation
- Replace `fee_per_vbyte * vbytes` and `fee_per_vbyte * vbytes_with_change` with `checked_mul`, and `payment_sat + needed_fee` / `payment_sat + fee_with_change` with `checked_add`, returning `NotEnoughFunds`/`TooLowFee` errors on overflow.
- Bound `payment_sat` and `input_sat` against `bitcoin::Amount::MAX_MONEY` (21M BTC in sats) before summation, since any sum exceeding the money supply is necessarily invalid.
- Make `fee()` use `checked_sub` and return an error rather than wrapping.
- Optionally compile the crate with `overflow-checks = on` or audit all `wallet/` arithmetic for consistency.

### Proof of Concept
```rust
// Conceptual: fee_per_vbyte chosen so fee_per_vbyte * vbytes wraps to < min relay fee.
// With vbytes ~ 200, fee_per_vbyte = u64::MAX / 200 + 1 makes needed_fee wrap to ~0.
// Lines 206 & 211: needed_fee (wrapped, tiny) < min_fee comparison is evaluated on the
// wrapped value logic-wise but needed_fee is then used at line 215 where
// input_sat < payment_sat + needed_fee can wrap as well.
//
// Alternatively: payments = [(script, u64::MAX - 1000), (script, u64::MAX - 1000)]
// -> payment_sat wraps to ~u64::MAX - 2000 - u64::MAX ≈ small via Sum::<u64> wrap
// -> line 215 passes -> tx_outs contain Amounts totaling far above input_sat
// -> SignableTransaction::new returns Ok -> multisig signs an invalid transaction.
```
The exact overflow behavior depends on build profile (release wraps; debug panics at line 139's subtraction or the `+` at line 215), but either outcome — a panic in the signing pipeline or a signed invalid/unrelayable transaction — stems from the same unchecked arithmetic root cause.
