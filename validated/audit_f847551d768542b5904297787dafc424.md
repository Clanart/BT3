### Title
Strict equality check in `SignableTransaction::multisig` aborts the entire transaction when any supplied `ReceivedOutput` mismatches - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::multisig` performs a strict `!=` comparison between each input's stored `script_pubkey` and the script derived from its declared scalar offset. If even one supplied `ReceivedOutput` (deserializable from untrusted bytes via `ReceivedOutput::read`) fails this check for any reason — including a single-byte difference — the function returns `None` for the *entire* transaction, denying signing of every input rather than rejecting only the offending one. This mirrors the audited bug class where an exact-equality check conflates "success" with "no deviation whatsoever," turning any deviation into a full denial of service.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::multisig` iterates all inputs and applies the offset to the threshold keys, then requires the recomputed Taproot script to exactly equal the prevout's `script_pubkey`:

```rust
// networks/bitcoin/src/wallet/send.rs:273-285
pub fn multisig(self, keys: &ThresholdKeys<Secp256k1>) -> Option<TransactionMachine> {
  let mut sigs = vec![];
  for i in 0 .. self.tx.input.len() {
    let offset = keys.clone().offset(self.offsets[i]);
    if p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey {
      None?;
    }
    sigs.push(AlgorithmMachine::new(Schnorr::new(), keys.clone().offset(self.offsets[i])));
  }
  Some(TransactionMachine { tx: self, sigs })
}
```

`self.prevouts[i]` and `self.offsets[i]` both come from `ReceivedOutput` values supplied to `SignableTransaction::new` (send.rs:175-185), and `ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes the `offset`, `TxOut`, and `OutPoint` independently from an arbitrary byte stream with no consistency check between them. A `ReceivedOutput` can therefore be constructed whose `offset` does not correspond to the key paying its `script_pubkey` — e.g., an offset registered via `Scanner::register_offset` paired with the base-key script, or an offset belonging to a different registered offset (offsets are surjective per `register_offset`, mod.rs:180-196).

There is also a second failure mode in the same check: `p2tr_script_buf` returns `None` when the offset group key is odd (mod.rs:80-86), and `None?` propagates out of `multisig` entirely. Any odd-key offset input silently kills the whole machine.

### Impact Explanation
When any single input in `inputs` fails the equality (or yields an odd tweaked key), `multisig` returns `None`, and no `TransactionMachine`/`PreprocessMachine` is ever created — the entire spend is aborted even though the remaining inputs are valid and spendable. An unprivileged party who can get a malformed or mismatched `ReceivedOutput` into the input list (the serialized form is plainly attacker-reachable bytes via `ReceivedOutput::read`) permanently blocks the threshold spend of all other inputs in that transaction, with no error distinguishing which input failed. This is the same consequence as the reference finding: a trivial input perturbation converts into a full denial of service on the operation.

### Likelihood Explanation
The check fires deterministically on any mismatch — there is no probabilistic element. The likelihood depends on an integrator passing attacker-influenced `ReceivedOutput`s into `SignableTransaction::new`; since `ReceivedOutput::read` performs no offset↔script consistency validation, nothing upstream prevents such inputs from reaching `multisig`. Scanner-produced outputs are always self-consistent, so purely scanner-fed pipelines are unaffected; the risk exists wherever received-output data is transported, stored, or assembled from untrusted serialization.

### Recommendation
Validate consistency at ingestion rather than at signing time, and fail per-input rather than for the whole batch:

1. In `SignableTransaction::new` or `multisig`, filter inputs: skip (or error on) only the inputs whose `offset` fails `p2tr_script_buf(offset.group_key()) == prevout.script_pubkey`, and return a descriptive error instead of bare `None` so the caller can identify the bad input.
2. Add a consistency check inside `ReceivedOutput::read` or a `verify(&self, key: &ProjectivePoint)` method asserting `p2tr_script_buf(key + G*offset) == Some(output.script_pubkey)` so mismatched offsets are rejected at deserialization.
3. Handle the odd-key case explicitly (e.g., apply the same even-ness normalization used in `tweak_keys`/`register_offset`) instead of propagating `None`.
