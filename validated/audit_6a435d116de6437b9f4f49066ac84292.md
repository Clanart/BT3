### Title
Attacker-controlled `x-github-enterprise-version` response header permanently poisons endpoint capability detection - ([File: app/src/lib/endpoint-capabilities.ts])

### Summary
The Aave report's root cause is a `require` invariant that trusts externally-influenceable state (the raw token balance of a shared contract) as a proxy for internal accounting, letting anyone permanently disable a feature by desynchronizing that state. The closest verifiable Desktop analog is `tryUpdateEndpointVersionFromResponse` / `updateEndpointVersion`, which trusts an attacker-observable/controllable HTTP response header to permanently (across app restarts, via `localStorage`) set the "capability" state used to decide whether GHES-only security/behavior features are enabled, with no validation of the header's provenance.

### Finding Description
`getEndpointVersion`/`updateEndpointVersion` in `app/src/lib/endpoint-capabilities.ts` cache the `x-github-enterprise-version` response header, keyed only by endpoint URL, into an in-memory map **and** `localStorage` (persisted indefinitely, survives restarts): [1](#0-0) 

This value is later used by `endpointSatisfies` to gate a set of feature predicates (`supportsAvatarsAPI`, `supportsRerunningChecks`, `supportsAliveSessions`, `supportsRepoRules`, etc.): [2](#0-1) 

The cache is populated from `tryUpdateEndpointVersionFromResponse`, called on essentially every API response (`ghRequest`), on the OAuth token exchange response, and — critically — on the unauthenticated discovery `HEAD /meta` request used by `isGitHubHost`: [3](#0-2) [4](#0-3) 

Notably, the `isGitHubHost` discovery request explicitly calls `suppressCertificateErrorFor(metaUrl)` before issuing the request, meaning Desktop will accept a response over a connection whose certificate error is being deliberately ignored for that URL — a scenario reachable when a network attacker/proxy sits in front of the enterprise endpoint (`git remote/proxy response`, in-scope attacker model). There is no check that the header comes from an authenticated/trusted response, no signature, and no server-identity binding beyond the endpoint string itself.

Once written, `updateEndpointVersion` only re-writes the cache if the raw string differs from the last cached raw value — it never expires, never re-validates, and is shared by *every* repository/account connected to that endpoint. Because the write goes straight to `localStorage`, the corrupted "invariant" (the endpoint's supposed GHES version) persists across app restarts.

### Impact Explanation
By supplying a bogus `x-github-enterprise-version` header (e.g., an old version string, or a malformed one that fails `semver.parse` and forces the "assumed" old GHES fallback), any party capable of influencing a single response to the user's GHES endpoint — a MITM/corporate proxy, a compromised/spoofed enterprise server, or an attacker able to trigger the `isGitHubHost` discovery probe against a look-alike host — can force `endpointSatisfies` to permanently report the endpoint as an old/unsupported GHES version. This silently and durably (post-restart) disables endpoint-gated capabilities such as `supportsRepoRules` for that endpoint, which controls whether Desktop fetches/enforces repo rulesets and warns the user about restricted branch names (used in `checkBranchNameRules`), and other gated features such as `supportsAliveSessions`, `supportsRerunningChecks`, and `supportsAvatarsAPI`. This is analogous to the Aave bug: an unprivileged actor externally influences shared state used in a security-relevant invariant check, causing a feature to be silently and durably disabled for legitimate users without their consent or awareness.

### Likelihood Explanation
Any response reaching `ghRequest`, the OAuth callback, or the certificate-error-suppressed `/meta` HEAD discovery request can set this value; a network-position attacker on an enterprise network, or an attacker who can get the user to trigger a discovery probe against a spoofed/incorrect host, can trigger this with a single crafted response. No authentication or elevated access is required, and the persistence via `localStorage` means a single injected response has a lasting effect.

### Recommendation
- Only trust `x-github-enterprise-version` from fully authenticated, TLS-validated API responses (never from the certificate-error-suppressed discovery probe in `isGitHubHost`).
- Avoid persisting this value indefinitely in `localStorage`; treat it as a soft hint with a short TTL and re-verify periodically from a trusted call path.
- Consider bounding how much a single header can degrade functionality (e.g., don't let an unverified version downgrade previously-established higher capability state without additional confirmation).

### Proof of Concept
1. Configure Desktop against a GHES endpoint (or intercept traffic to it via a network position, e.g., corporate proxy/MITM).
2. On any response to that endpoint (including the `HEAD /meta` discovery request performed with certificate-error suppression, per `isGitHubHost`), inject a header `x-github-enterprise-version: 3.0.0`.
3. `tryUpdateEndpointVersionFromResponse` stores this in `rawVersionCache`/`versionCache` and `localStorage` under `endpoint-version:<endpoint>`.
4. Restart Desktop — the poisoned value persists. `supportsRepoRules(endpoint)`, `supportsAliveSessions(endpoint)`, etc. now evaluate against the attacker-supplied version and remain false/disabled for that endpoint until another response happens to supply a different value, exactly mirroring the "anyone can permanently disable the feature by desynchronizing an invariant" pattern of the original Aave finding.

**Note on confidence:** I could not fully trace every downstream security-relevant consequence of `supportsRepoRules`/`supportsAliveSessions` being disabled (e.g., whether any of these gates are relied upon as an actual security control rather than a UX hint), due to index/time constraints on tracing all call sites. This should be verified further, ideally by starting a full Devin session with complete file access, before treating this as a confirmed high-severity finding.

/**
 * Update the known version number for a given endpoint
 */
export function updateEndpointVersion(endpoint: string, version: string) {
  const key = endpointVersionKey(endpoint)

  if (rawVersionCache.get(key) !== version) {
    const parsed = semver.parse(version)
    localStorage.setItem(key, version)
    rawVersionCache.set(key, version)
    versionCache.set(key, parsed)
  }
}

function tryUpdateEndpointVersionFromResponse(
  endpoint: string,
  response: Response

  const gheVersion = response.headers.get('x-github-enterprise-version')
  if (gheVersion !== null) {
