### Title
Cached FROST preprocess seed reused after validator-set context change enables nonce reuse and secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The kernel bug class — a cached entry surviving a context ("zone") switch because it is keyed on the wrong/insufficient identifier — has a direct analog in the tributary DKG-confirmation signing protocol. `SigningProtocol::preprocess_internal` caches a FROST preprocess seed keyed only by `context = (b"DkgConfirmer", attempt)`, while the material the seed signs for — the `removed` validator list (and therefore the `participants` vector fed to `musig()`, the resulting `ThresholdKeys`, and the `set_keys_message` payload) — is resolved per-call by `removed_as_of_dkg_attempt` and is *not* part of the cache key. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`preprocess_internal` checks `CachedPreprocesses::get(txn, &context)`; if an entry exists it is decrypted and fed to `AlgorithmSignMachine::from_cache`, which deterministically regenerates the identical nonces via `seeded_preprocess` → `ChaCha20Rng::from_seed`. The file's own header acknowledges the hazard: safety of the re-execution model "is derived from the nonces being context-bound", and nonce reuse occurs only if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again." [4](#0-3) [5](#0-4) 

Yet the context bound in the DB key is `(b"DkgConfirmer", self.attempt)` only — it does not include `removed`, `participants`, or `key_pair`. `DkgConfirmer::new` calls `removed_as_of_dkg_attempt(txn, spec.genesis(), attempt)`, i.e. the removal set is computed lazily from DB state at each invocation, and `share_internal` then builds `msg = set_keys_message(&spec.set(), &removed..., key_pair)` and derives `keys` from the *current* `participants`. [6](#0-5) 

The mirror of "switching zones without ct clear": a validator removal transaction finalized mid-attempt (removals are a normal, non-adversarial protocol path — `spec.i(removed, key)` exists precisely because the set varies with `removed`) changes `removed` between the original `preprocess()` execution and a subsequent `share()`/`complete()` re-execution under the same `attempt`. The stale cached seed — the "old ct entry" — is silently kept, while `share_internal` re-signs a *different* message (`set_keys_message` now lists a different `removed` set) under a *different* MuSig participant ordering (removal shifts `threshold_i` → `musig_i` mapping in `threshold_i_map_to_keys_and_musig_i_map`, changing binding factors `rho` in `BindingFactor::calculate_binding_factors`). [7](#0-6) [8](#0-7) 

Two `sign()` calls then emit signature shares `s_i = r_i + c·λ_i·share` with the *same* nonce scalars `r_i` but different challenges `c` (different `msg` and different participant/commitment transcript). Any observer of the tributary preprocesses/shares — which are published publicly — can solve for `λ_i·share` and recover the coordinator's MuSig private key share, exactly the "third-party recovery of your private key share" the `CachedPreprocess` docs warn against. [9](#0-8) [10](#0-9) 

### Impact Explanation
Deterministic nonce reuse across two distinct Schnorr signing sessions leaks the signer's private key share — the highest-impact outcome class in scope ("key share recovery"). The leaked key is a validator's MuSig root-of-trust key, not merely a per-network share.

### Likelihood Explanation
The trigger is an ordinary protocol event (a removal landing during an ongoing DKG confirmation attempt, or any other divergence in `removed` between the `preprocess`, `share`, and `complete` re-executions within one `attempt`), not an exotic race: re-execution is the intended design here. No collusion or BFT violation is required — unlike the reorganization case the code explicitly dismisses, a mid-attempt removal does not rebuild the process, so the "we'd re-decide nonces" safety argument does not apply and the stale cache entry is used as-is. Reachability caveat: triggering a removal is a validator-set action rather than a purely anonymous input, which constrains likelihood; severity rests on the fact that no misbehavior is needed to trigger it.

### Recommendation
Bind the full signing context into the cache key — e.g. key `CachedPreprocesses` on `(b"DkgConfirmer", attempt, removed-hash, key_pair-hash, participants-hash)` — or delete/invalidate the cached seed whenever `removed` or the participant set resolved for `share`/`complete` differs from what was cached. Before publishing a share, verify the regenerated `preprocess` commitments equal the ones originally broadcast for this attempt (the file's own TODO at line 51), and fail rather than sign if they differ.

  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be

  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial

  our_key: &Zeroizing<<Ristretto as Ciphersuite>::F>,
  mut map: HashMap<Participant, Vec<u8>>,

    .i(removed, <Ristretto as Ciphersuite>::generator() * our_key.deref())
    .expect("MuSig t-of-n signing a for a protocol we were removed from")
    .start;

        return *key;

    participants.push(key);
    map.insert(Participant::new(musig_i).unwrap(), share);

  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {

      &params.algorithm.nonces(),

    rng.fill_bytes(&mut blame_entropy);

      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
