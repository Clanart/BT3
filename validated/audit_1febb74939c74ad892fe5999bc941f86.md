### Title
Hookify `PreToolUse` blocking rules can be silently bypassed via `MultiEdit` due to unimplemented `old_text`/`old_string` field extraction - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The `hookify` plugin's `RuleEngine._extract_field()` is documented to support the field names `file_path`, `new_text`, `old_text`, and `content` for `file`-type rules [1](#0-0) , but the implementation only maps `old_text`/`old_string` for `Write`/`Edit` tools, not for `MultiEdit`. When a project author writes a blocking rule that inspects `old_text` (e.g., "block removal of a security marker" or "block editing of a secret placeholder"), the rule silently never matches when the same edit is performed through the `MultiEdit` tool instead of `Edit`/`Write`, because `_extract_field` returns `None` for that combination, and `_check_condition` treats `None` as "no match" rather than surfacing a configuration gap.

### Finding Description
`_extract_field` dispatches based on `tool_name` and `field`: [2](#0-1) 

For `Write`/`Edit`, `old_text`/`old_string` is explicitly handled (mapped to `tool_input.get('old_string', '')`). For `MultiEdit`, only `file_path` and `new_text`/`content` (via concatenation of `edits[].new_string`) are handled; there is no branch for `old_text`/`old_string`, so the function falls through to `return None` at the end of the method.

`_check_condition` treats a `None` field value as "condition does not match" rather than as an error: [3](#0-2) 

Since `_rule_matches` requires **all** conditions to match, any rule that conditions on `old_text` against a `MultiEdit` tool call can never trigger, regardless of the actual content of `old_string` in the edit — the check field (as documented and configured by the rule author) is decoupled from the field actually used at decision time, exactly mirroring the Li.Fi pattern of "the value used for the final decision doesn't correspond to the value that was actually validated/intended."

The documentation for the `writing-rules` skill explicitly lists `old_text`/`old_string` as a valid, supported `field` for `file` events without qualifying that it's unsupported for `MultiEdit` [1](#0-0) , so a plugin author following the documented interface has no way to know their protection is incomplete.

### Impact Explanation
Any `PreToolUse`/`file`-event `block` rule that relies on `old_text` (a documented, supported condition field) is silently inert against the `MultiEdit` tool. An agent (or any code path that chooses to use `MultiEdit` instead of `Edit`) can bypass content-based blocking policies — e.g., rules meant to prevent stripping a `.env` guard comment, removing a security banner, or editing out a "DO NOT MODIFY" marker — simply by routing the same logical change through `MultiEdit`. Because hookify blocking rules are the mechanism plugin authors use to enforce hard stops on dangerous edits [4](#0-3) , this is a genuine hook-bypass of a locally-configured guard rail, not merely a documentation nit.

### Likelihood Explanation
Likelihood is moderate-to-high: any hookify user who writes an `old_text`-based rule (a documented, first-class feature) and expects it to cover general file edits will be silently bypassed the moment `MultiEdit` is used instead of `Edit`/`Write`. No attacker sophistication is required — using `MultiEdit` is a normal, unprivileged tool choice available to any agent session, and the bypass requires no malicious crafting beyond selecting a different (equally normal) tool.

### Recommendation
Add `old_text`/`old_string` handling for `MultiEdit` in `_extract_field`, mirroring the `new_text`/`content` handling by concatenating `edits[].old_string`:

```python
elif tool_name == 'MultiEdit':
    if field == 'file_path':
        return tool_input.get('file_path', '')
    elif field in ['new_text', 'content']:
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('new_string', '') for e in edits)
    elif field in ['old_text', 'old_string']:
        edits = tool_input.get('edits', [])
        return ' '.join(e.get('old_string', '') for e in edits)
```
Additionally, consider treating an unrecognized `(tool_name, field)` combination as a hard configuration error (e.g., log a warning at load time) rather than silently falling through to `None`, so rule authors are alerted when a documented field is not actually implemented for a given tool.

### Proof of Concept
1. Configure a hookify blocking rule:
```yaml
name: block-marker-removal
enabled: true
event: file
action: block
conditions:
  - field: old_text
    operator: contains
    pattern: "SECURITY-MARKER"
```
2. Trigger via `Edit` tool removing text containing `SECURITY-MARKER` — rule correctly blocks (via `old_string` handling in the `Write`/`Edit` branch).
3. Trigger the identical logical change via `MultiEdit` with an `edits` array entry whose `old_string` contains `SECURITY-MARKER` — `_extract_field` returns `None` for `field == 'old_text'` under `tool_name == 'MultiEdit'`, `_check_condition` short-circuits to `False`, `_rule_matches` returns `False`, and the operation proceeds unblocked despite matching the intended protection semantics.
