### Title
Integer Underflow in `AccountKeyWeightedMultiSig.SigValidationGas` Post-Istanbul Path Can Produce a Wildly Wrong Gas Charge - (File: blockchain/types/accountkey/account_key_weighted_multi_sig.go)

### Summary
`AccountKeyWeightedMultiSig.SigValidationGas` computes the extra intrinsic-gas cost of signature validation for a multisig `AccountKey` from the number of recovered signatures (`numSigs`), an attacker-influenced value taken from the number of signatures attached to a transaction. In the Istanbul-and-later branch the function does `uint64(numSigs-1) * params.TxValidationGasPerKey` without first checking `numSigs > 0`. This mirrors exactly the bug class in the reported osslsigncode CVE: an unchecked subtraction of an untrusted, attacker-controlled length value that can go negative and, once reinterpreted as unsigned, produces a huge (near `math.MaxUint64`) value that then feeds further arithmetic.

### Finding Description
```go
func (a *AccountKeyWeightedMultiSig) SigValidationGas(currentBlockNumber uint64, r RoleType, numSigs int) (uint64, error) {
	numKeys := uint64(len(a.Keys))
	if numKeys > MaxNumKeysForMultiSig {
		return 0, kerrors.ErrMaxKeysExceedInValidation
	}
	if numKeys == 0 {
		return 0, kerrors.ErrZeroLength
	}

	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul
	if isIstanbul {
		return uint64(numSigs-1) * params.TxValidationGasPerKey, nil
	}
	return (numKeys - 1) * params.TxValidationGasPerKey, nil
}
``` [1](#0-0) 

The function validates `numKeys` (the number of keys registered on the account) is non-zero, but it never validates `numSigs` (the number of signatures presented in the transaction being processed) before subtracting 1 from it in the post-Istanbul branch. If `numSigs == 0`, `numSigs - 1` is computed as a signed `int` equal to `-1`, and the subsequent `uint64(...)` conversion wraps it to `18446744073709551615` (`math.MaxUint64`). Multiplying that by `params.TxValidationGasPerKey` then silently overflows the `uint64` multiplication (Go does not panic or error on unsigned overflow), yielding an essentially arbitrary, attacker-uncontrollable-but-wrong gas value rather than a caught error.

This is structurally identical to the `pe_page_hash_calc()` bug: an unsigned subtraction of a caller-influenced quantity without a `>=` guard, producing underflow that propagates into further computation. The `numKeys == 0` guard demonstrates the code recognizes the need for this class of check but omits the equivalent guard for `numSigs`.

### Impact Explanation
`SigValidationGas` output feeds into `IntrinsicGas`/`ValidatedGas` computation used in `StateTransition.TransitionDb` to determine both the minimum required gas (`ErrIntrinsicGas` check) and, ultimately, the fee charged to the sender: [2](#0-1) 
An incorrect (wrapped/overflowed) `IntrinsicGas` value can cause acceptance of a transaction whose actual charged intrinsic gas differs from what should be economically required to authorize a multisig-key transaction, i.e., state divergence in fee/gas accounting for `AccountKeyWeightedMultiSig`-controlled accounts and potential acceptance of a transaction with an intrinsic-gas figure that does not reflect the true signature-validation cost. Because the value participates in balance-affecting fee computation, this falls under fee/gas accounting abuse.

### Likelihood Explanation
Reachability depends on whether the codebase's transaction-processing / validation pipeline can invoke `SigValidationGas` with `numSigs == 0` for an account whose current `AccountKey` is `AccountKeyWeightedMultiSig` (e.g., a transaction that carries zero signatures, or where signature-count derivation yields zero before the "at least one valid signature" check runs). I was not able to fully trace the exact call site in `blockchain/types/transaction.go` (three references found) within the available iterations to confirm whether an earlier check unconditionally guarantees `numSigs >= 1` before this function is reached. This is a genuine gap in the function's own input validation and is a direct code-level analog to the reported CVE's root cause, but I could not conclusively verify end-to-end exploitability from a single unprivileged transaction without further call-graph tracing of `transaction.go`.

### Recommendation
Add an explicit `numSigs == 0` (or `numSigs < 1`) guard in `AccountKeyWeightedMultiSig.SigValidationGas` before computing `numSigs - 1`, returning an error (e.g., `kerrors.ErrZeroLength`) analogous to the existing `numKeys == 0` check, and audit all call sites in `blockchain/types/transaction.go` to confirm `numSigs` is always sourced from validated signature data prior to gas computation.

### Proof of Concept
Not independently constructed/verified against a running node within this investigation; the code-level PoC is: call `AccountKeyWeightedMultiSig.SigValidationGas(currentBlockNumber, roleType, 0)` on/after the Istanbul fork block with a non-empty `Keys` slice — this returns `(18446744073709551615 * params.TxValidationGasPerKey) mod 2^64` instead of an error, demonstrating the underflow. Full transaction-level exploitability requires confirming a code path that reaches this function with `numSigs == 0`, which I was unable to fully trace before running out of tool-call budget.
