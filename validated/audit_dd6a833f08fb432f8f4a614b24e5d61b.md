### Title
Untrusted `ReceivedOutput` value is trusted as input balance, corrupting change/fee accounting and producing unspendable signed transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` treats the `TxOut` embedded in each `ReceivedOutput` as ground truth for the input's value, without verifying that the declared `outpoint` actually resolves to a UTXO of that value (or that the declared `offset` matches the script the output pays to). An attacker who can supply bytes to `ReceivedOutput::read` (an explicitly untrusted deserialization entry point) can inflate the claimed input value. The wallet then computes `input_sat`, the change amount, and the signed prevout commitment from the forged value — the exact analog of crediting the *declared* transfer amount instead of the *actually received* amount from the reference report.

### Finding Description
- `ReceivedOutput::read` at `networks/bitcoin/src/wallet/mod.rs:122-134` deserializes `offset`, `output` (a full `TxOut` including `value` and `script_pubkey`), and `outpoint` from raw bytes with no consistency checks — the `script_pubkey` need not match `key + offset*G`, and the `value`/`outpoint` pair need not correspond to any real UTXO. [1](#0-0) 
- `SignableTransaction::new` sums `input.output.value` into `input_sat` at `networks/bitcoin/src/wallet/send.rs:175` and uses it for the `NotEnoughFunds` check and change computation (`input_sat - payment_sat - fee_with_change` at lines 228-233). It also stores the supplied `TxOut`s verbatim as `prevouts` (line 253), which are committed into the Taproot sighash during signing. [2](#0-1) [3](#0-2) 
- There is no check anywhere that `prevouts[i]` equals the on-chain output at `outpoint`, nor that `output.script_pubkey` is the P2TR script for `key + offset*G` (compare with `Scanner::scan_transaction`, which only ever builds `ReceivedOutput`s from real chain data and derives the offset from the script at `mod.rs:199-214`). [4](#0-3) 

### Impact Explanation
This mirrors the fee-on-transfer accounting bug: accounting records the claimed amount, not the actual one. An inflated `output.value` causes `input_sat` to exceed the real sum of input UTXOs. If a `change` script is provided, the change output is sized as `input_sat - payments - fee` (send.rs:228-230), creating a transaction whose outputs exceed its real input value — consensus-invalid. The multisig still signs it (the forged value is committed in the prevouts, so the signature is internally consistent), yielding funds reported as spendable change that can never be broadcast — a direct financial-loss/DoS analog to the report's "received 90, paid out 100". Conversely, an understated value or mismatched `offset`/`script_pubkey` can silently burn real funds as fee or produce inputs the group key cannot actually spend.

### Likelihood Explanation
Reachability requires attacker-controlled bytes reaching `ReceivedOutput::read` and the resulting object being passed to `SignableTransaction::new`. The crate exposes `read`/`serialize` as the canonical transport format for these outputs (mod.rs:120-148); any pipeline that round-trips outputs through storage, network messages, or coordinator-mediated input selection accepts this shape. Within the crate's own API surface, `SignableTransaction::new` performs zero validation of the fields it consumes, so a single forged or tampered serialized `ReceivedOutput` is sufficient.

### Recommendation
Bind the fields of `ReceivedOutput` at construction/deserialization time:
1. In `SignableTransaction::new` (or `ReceivedOutput::read`), verify `output.script_pubkey == p2tr_script_buf(group_key + GENERATOR * offset)`, i.e., recompute the script rather than trusting the supplied one.
2. Verify the claimed `value` against the actual UTXO at `outpoint` before computing `input_sat`/change — e.g., require callers to pass a UTXO-verification closure, or only accept `ReceivedOutput`s produced by `Scanner::scan_transaction` (make `offset`/`output`/`outpoint` fields non-forgeable by gating construction behind the scanner, mirroring the "measure pre/post balance" fix: account for the *actual* on-chain value, not the declared one).
3. Reject `value` of 0 / dust inputs explicitly.

### Proof of Concept
Conceptual, using the crate's public API:

```rust
// Attacker crafts a ReceivedOutput claiming a real outpoint holds more than it does.
let mut forged = ReceivedOutput::read(&mut bytes).unwrap();
// bytes encode: outpoint = <real UTXO of 10_000 sat>,
//               output   = TxOut { value: 1_000_000, script_pubkey: <ours> },
//               offset   = Scalar::ZERO

let tx = SignableTransaction::new(
    vec![forged],
    &[(payment_script, 900_000)],
    Some(change_script),
    None,
    fee_rate,
).unwrap();
// input_sat = 1_000_000 -> passes NotEnoughFunds
// change = 1_000_000 - 900_000 - fee, but real input is only 10_000 sat.
// The FROST multisig signs it (prevouts commit the forged value);
// the resulting tx is consensus-invalid -> change/accounting can never settle.
```

No on-chain check exists between `ReceivedOutput::read` and the signed `prevouts`, so the corrupted internal accounting propagates end-to-end. [5](#0-4)

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
