### Title
`Airdrop.claim` – unguarded public `updateEndRemainingAllocation()` allows repeated re-snapshotting of the bonus denominator, letting later claimers over-extract `totalBonus` - (File: rewards/Airdrop.sol)

### Summary
`claim()` only calls `updateEndRemainingAllocation()` automatically when `totalEndRemainingAllocation == 0`, intending a one-shot snapshot of the bonus-splitting denominator at the moment the airdrop's final period ends. However, `updateEndRemainingAllocation()` itself is `public` with no access control and no re-entry guard, so any unprivileged account can call it directly and repeatedly after `periodsEndTime[4]`, each time resetting `totalEndRemainingAllocation` to the *current* (shrinking) `totalRemainingAllocation`. This breaks the invariant that the snapshot denominator used to distribute `totalBonus` is fixed, letting later claimants receive a disproportionately large share of `totalBonus`, exceeding the total amount actually forfeited.

### Finding Description
`totalBonus` accumulates from users who claim early (before period 4 fully vests) and forfeit their unvested share: [1](#0-0) 

After `periodsEndTime[4]`, remaining (not-yet-claimed) users are meant to split `totalBonus` proportionally to their allocation over a *fixed* denominator `totalEndRemainingAllocation`, computed once as the `totalRemainingAllocation` outstanding at that moment: [2](#0-1) 

`claim()` enforces the "once" semantics only through the automatic call: [3](#0-2) 

but `updateEndRemainingAllocation()` is a standalone `public` function with no guard preventing repeat calls and no access control: [4](#0-3) 

Any unprivileged EOA can call `updateEndRemainingAllocation()` directly at any time after `periodsEndTime[4]`. Since `totalRemainingAllocation` shrinks every time a user claims (`totalRemainingAllocation -= userAllocation` at line 164), calling `updateEndRemainingAllocation()` again after some remaining users have already claimed re-bases `totalEndRemainingAllocation` down to only the allocation of the users who are *still* unclaimed. Because `totalBonus` is not correspondingly reduced, `getBonusAmount` for the remaining claimants (`userAllocation * totalBonus / totalEndRemainingAllocation`) becomes inflated — the same fixed `totalBonus` pool is effectively distributed multiple times over ever-shrinking denominators. The sum of bonus payouts across all claimants can then exceed the actual `totalBonus` that was forfeited, draining `aidropToken` reserved for other purposes or leaving later legitimate claimants with `InsufficientBalance` reverts (funds frozen) once the contract's balance runs out.

Concrete example: Alice and Dave each hold allocation 100; `totalBonus = 200` from earlier forfeits at the moment period 4 ends, with `totalRemainingAllocation = 200` (Alice+Dave). Alice calls `claim()` first — this auto-snapshots `totalEndRemainingAllocation = 200`, she receives her fair share of the bonus (100), and `totalRemainingAllocation` drops to 100 (Dave only). Before Dave claims, anyone calls `updateEndRemainingAllocation()` directly, resetting `totalEndRemainingAllocation` to 100. Dave then calls `claim()`; since `totalEndRemainingAllocation != 0` the auto-path is skipped, and `getBonusAmount` computes `100 * 200 / 100 = 200` for Dave alone — the *entire* original `totalBonus` pool, even though Alice already received her 100-token share from it. Total bonus paid out (300) exceeds `totalBonus` (200), so `totalBonus` no longer reconciles with `aidropToken.balanceOf(address(this))`.

### Impact Explanation
This directly breaks the accounting invariant that `totalBonus` tracks what is actually available/owed for bonus distribution, and the contract can pay out more `aidropToken` than was legitimately forfeited by early claimants. Depending on timing, this manifests as: (a) an attacker (or any late claimant who benefits from the re-snapshot, whether intentionally or opportunistically) receiving tokens that belong to other allocation-holders, i.e., direct theft of user funds, or (b) the contract running out of balance, permanently freezing legitimate claimants' remaining allocation (`InsufficientBalance` revert with no retry path since their `allocations[msg.sender]` state hasn't been zeroed, but the pool is drained and cannot be replenished by unprivileged users). This matches the Critical "Direct theft of user funds" class.

### Likelihood Explanation
No privileged role is required. `updateEndRemainingAllocation()` is `public` with zero access control, callable by any EOA or contract at any time once `block.timestamp >= periodsEndTime[4]`. The only precondition is that at least one remaining claimant has already claimed after period 4 (naturally reducing `totalRemainingAllocation`) and that `totalBonus` is non-trivial from earlier forfeits — both are expected, ordinary states of the airdrop lifecycle, not adversarial setups. Any observer can front-run/call this function between other users' `claim()` transactions with no capital cost beyond gas, and can repeat it multiple times as more users claim, compounding the miscalculation.

### Recommendation
Guard `updateEndRemainingAllocation()` so it can only ever set `totalEndRemainingAllocation` once, matching the intended one-shot semantics already assumed by `claim()`'s `if (totalEndRemainingAllocation == 0)` check — e.g., add the same `if (totalEndRemainingAllocation == 0)` condition inside `updateEndRemainingAllocation()` itself (or merge the two functions so there is a single code path with a single guard), and/or restrict who may trigger it. This ensures the manual/public path and the automatic path enforce the identical constraint.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `Airdrop` with `startTime` in the near future; register Alice and Dave each with allocation `100`; fund the contract with `aidropToken` sufficient for allocations + expected bonus.
2. Warp time past `periodsEndTime[1]` (partial vesting) and have a third registered user with allocation `X` call `claim()` early so that `claimableAmount < userAllocation`, causing `totalBonus` to accumulate (e.g. `totalBonus = 200`) and `totalRemainingAllocation` to drop accordingly, leaving `totalRemainingAllocation == 200` (Alice + Dave).
3. Warp time to/after `periodsEndTime[4]`.
4. Call `Alice.claim()`. Assert `totalEndRemainingAllocation == 200` (auto-snapshot fired) and Alice receives `100 (base) + 100 (bonus) = 200` tokens; assert `totalRemainingAllocation == 100`.
5. From an arbitrary unprivileged address, call `updateEndRemainingAllocation()` directly. Assert `totalEndRemainingAllocation` changes to `100`.
6. Call `Dave.claim()`. Assert `getBonusAmount(Dave)` returns `200` (full original `totalBonus`) instead of the fair `100`, so total bonus paid (`Alice 100 + Dave 200 = 300`) exceeds `totalBonus` (`200`).
7. Assert `totalBonus != (sum of bonuses paid)` and/or `aidropToken.balanceOf(address(this))` is insufficient for any additional legitimate claimant, demonstrating the broken invariant and fund drain/freeze.

    function updateEndRemainingAllocation() public {
        if (block.timestamp >= periodsEndTime[4]) {
            totalEndRemainingAllocation = totalRemainingAllocation;
        }
    }
