### Title
Signed-integer overflow via unchecked negation of `Duration.seconds()`/`.nanos()` at `INT64_MIN`/`INT32_MIN` in `TimeUtil::ToString(const Duration&)` - (File: `src/google/protobuf/util/time_util.cc`)

### Summary
`google::protobuf::util::TimeUtil::ToString(const Duration&)` negates the `seconds` and `nanos` fields of an attacker-controlled `Duration` message without first validating that the message is within the documented valid range. If `seconds` is `INT64_MIN` (or `nanos` is `INT32_MIN`), the negation `-seconds` / `-nanos` is signed-integer overflow, which is undefined behavior in C++ — the same invariant violation as the Fuel-core report's unguarded `abs()` on `i128::MIN`.

### Finding Description
`Duration` is a normal, publicly settable protobuf message (`seconds: int64`, `nanos: int32`). Any component that parses an untrusted binary/ProtoJSON payload into a `google.protobuf.Duration` (or constructs/deserializes one from attacker-controlled bytes) can produce a message whose `seconds()` is `INT64_MIN` — there is no wire-format-level restriction that seconds stay in `[-315576000000, 315576000000]`; that range is only enforced by `TimeUtil::IsDurationValid()`, which callers are not required to invoke, and the binary parser does not call it. Once such a `Duration` is passed to `TimeUtil::ToString`, the following happens: [1](#0-0) 

```cpp
std::string TimeUtil::ToString(const Duration& duration) {
  std::string result;
  int64_t seconds = duration.seconds();
  int32_t nanos = duration.nanos();
  if (seconds < 0 || nanos < 0) {
    result = "-";
    seconds = -seconds;
    nanos = -nanos;
  }
  ...
```

There is no check that `seconds != INT64_MIN` (or `nanos != INT32_MIN`) before negating. `-INT64_MIN` and `-INT32_MIN` cannot be represented in their respective signed types, making this classic signed overflow UB (`-x` is only well-defined for `x` in `[INT_MIN+1, INT_MAX]`), directly analogous to the Fuel-core `abs(i128::MIN)` bug: an attacker-controlled boundary value is fed into an unguarded negation/abs operation.

The class documentation for `TimeUtil::ToString(const Duration&)` explicitly warns that behavior is undefined outside the valid `Duration` range, but this is a documentation-only caveat — the function itself performs no defensive check, unlike the sibling `WriteDuration` unparser used by the JSON serializer. [2](#0-1) 

By contrast, the JSON path (`json/internal/unparser.cc`, `WriteDuration`) explicitly range-checks `secs`/`nanos` against `kMaxSeconds`/`kMaxNanos` before calling `std::abs`, which prevents `INT64_MIN`/`INT32_MIN` from ever reaching the `abs()` call: [3](#0-2) 

This confirms the maintainers are aware negation/abs of `Duration` fields needs bounds-checking — but `TimeUtil::ToString` (the `util/time_util.h` public API, used e.g. by `operator<<` for `Duration`) lacks the equivalent guard.

### Impact Explanation
Signed integer overflow is undefined behavior in C++. In practice on two's-complement platforms this typically evaluates to `INT64_MIN`/`INT32_MIN` again (no crash), but under UBSan/ASan builds it is a defined sanitizer abort (DoS in fuzzing/CI or code compiled with `-fsanitize=undefined -fno-sanitize-recover`), and compilers are permitted to exploit the UB for otherwise-surprising codegen. Because `Duration` is a common Well-Known Type consumed by many services that call `TimeUtil::ToString` (or the `operator<<` overload) directly on deserialized/user-supplied `Duration` messages without first calling `IsDurationValid()`, this is reachable from ordinary parsing + logging/debug-printing paths. This is a Medium-severity correctness/UB issue rather than memory corruption or RCE.

### Likelihood Explanation
Likelihood is Medium: it requires (a) an attacker able to set `Duration.seconds` to exactly `INT64_MIN` (trivial via any public parse API, since binary/ProtoJSON parsing doesn't enforce `IsDurationValid`), and (b) an application calling `TimeUtil::ToString` (or `operator<<`) on that value without first validating it via `IsDurationValid()`. Many applications do call `ToString`/stream a `Duration` for logging without validation, since the function's contract only mentions UB in a code comment rather than enforcing it.

### Recommendation
In `TimeUtil::ToString(const Duration&)` (and the analogous `TimeUtil::ToString(const Timestamp&)`/other negation sites in `time_util.cc`), either:
1. Call `IsDurationValid(duration)` at the top of `ToString` and return an error/empty string (or `ABSL_CHECK`) for out-of-range inputs, or
2. Use unsigned-negation-safe idioms, e.g. compute `static_cast<uint64_t>(seconds) * -1` reinterpretation the way `TimeUtil::ToUint128`/`ToDuration` already do elsewhere in the same file (they use `static_cast<uint64_t>(-value.seconds())` style, but those are similarly guarded by prior `CreateNormalizedDuration` ABSL_DCHECK range assertions in debug builds only — release builds are unguarded too and should be revisited).

Also mirror the `WriteDuration`-style explicit bounds check (`secs > kMaxSeconds || secs < -kMaxSeconds`) before negating, as already done in `json/internal/unparser.cc`.

### Proof of Concept
```cpp
google::protobuf::Duration d;
d.set_seconds(std::numeric_limits<int64_t>::min());  // INT64_MIN, e.g. deserialized from attacker bytes
d.set_nanos(0);
// No call to TimeUtil::IsDurationValid(d) is made by the parser or required by ToString.
std::string s = google::protobuf::util::TimeUtil::ToString(d);
// `seconds = -seconds;` in ToString() executes `-INT64_MIN`, which is signed integer
// overflow (UB). Under -fsanitize=undefined this aborts; under normal optimized
// builds it silently wraps back to INT64_MIN, producing an incorrect/undefined string.
```
