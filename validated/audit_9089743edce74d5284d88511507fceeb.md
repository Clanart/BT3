## Assessment: Valid Finding (with a location correction)

The reported UI file is wrong — `app/src/ui/diff/diff-options.tsx` is a pure presentational component (whitespace/side-by-side toggle popover) and contains no file-path or diff-content logic at all. [1](#0-0) 
The actual sink for `getResolutionDiff` is `app/src/lib/git/diff.ts`, invoked from `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-changes.tsx`. The underlying containment-bypass issue described, however, is real.

### Title
Missing symlink/path containment check in `getResolutionDiff` allows off-repo file disclosure via conflicted symlink entries - (File: `app/src/lib/git/diff.ts`)

### Summary
`getResolutionDiff` reads the working-tree "base" content for a conflicted file with a raw `Path.join(repository.path, filePath)` and `readFile`, with no symlink/containment guard, unlike the sibling Copilot-context builder which explicitly guards against exactly this.

### Finding Description
`getResolutionDiff` computes the baseline content for the conflict-resolution diff view directly from disk: [2](#0-1) 
`filePath` is the repository-relative path of a conflicted entry (as surfaced by git status/merge-conflict data) and is joined onto `repository.path` with plain `Path.join`, then passed to Node's `readFile`. Node's `fs.readFile` follows symlinks by default. If the working tree contains a tracked symlink (git blob mode `120000`) at that path pointing outside the repository (e.g. to `~/.ssh/id_rsa`, a config file, or another user directory), `readFile` transparently dereferences it and returns the **target file's** contents as `baseContent`, which is then diffed and rendered in the Copilot conflict-resolution dialog.

This is notably inconsistent with how the codebase already treats this exact class of risk. `buildConflictContext` — the function that gathers conflict data for the Copilot prompt — explicitly resolves and validates the path with `resolveWithin` before reading, specifically to guard against "path traversal and symlink escapes": [3](#0-2) 
`getResolutionDiff` has no equivalent check, so it bypasses the containment invariant that the rest of the conflict-resolution flow enforces.

### Impact Explanation
An attacker who can get a symlinked file merged/checked out as a conflicted entry in the victim's working directory (e.g., via a branch in a repo the victim clones/fetches, containing a `120000`-mode symlink at a path that later conflicts) can cause Desktop to read and display the contents of an arbitrary file the victim's OS user account can access, inside the local diff view. The `oldContents`/`baseContent` returned by `getResolutionDiff` is off-repo data smuggled into an in-repo abstraction (`IResolutionDiff`), breaking the working-directory containment invariant. Note: based on the code available, this `baseContent` is used for the local diff render only — I could not fully verify (index/tool budget exhausted) whether this specific value is also forwarded into any outbound channel (e.g., a Copilot request, telemetry, or error report) as opposed to `buildConflictContext`'s independently-guarded `rawContent`, which is what's actually sent to Copilot. If it stays purely client-side, the practical impact is local information disclosure to the same user viewing their own diff (still real disk-scope violation and content corruption of a security-relevant abstraction), rather than direct disclosure to a remote attacker.

### Likelihood Explanation
Requires the attacker to control repository content merged/checked out on the victim's machine and get it into a conflicted state at a symlinked path — this is a git-native, unprivileged capability (no local access, no admin rights, no social engineering beyond a normal clone/fetch/merge). Symlink creation during checkout is platform-dependent (works readily on macOS/Linux; Windows requires Developer Mode or admin for arbitrary symlinks), which somewhat limits universal exploitability but does not eliminate it.

### Recommendation
Apply the same `resolveWithin` (or equivalent lstat-based symlink check) used in `app/src/lib/copilot-conflict-context.ts` to `getResolutionDiff` in `app/src/lib/git/diff.ts` before the `readFile(Path.join(repository.path, filePath), 'utf8')` call, rejecting or safely handling paths that resolve outside `repository.path` (including via symlink). The same audit should be applied to other unguarded `Path.join(repository.path, ...)` + `readFile` sites in that file (e.g. `getWorkingDirectoryImage` at line 930) for consistency.

### Proof of Concept
1. Create/clone a repository containing a tracked symlink `conflict.txt -> /etc/passwd` (or, on the victim's machine, any absolute/relative path escaping the repo) on one branch, and a regular file `conflict.txt` with different content on another branch.
2. Merge the branches so `conflict.txt` becomes a conflicted entry with the symlink present on disk in the working directory.
3. Open the merge-conflict resolution dialog in Desktop and select the conflicted file to view its diff (`getResolutionDiff` invoked via `copilot-conflicts-changes.tsx`).
4. Observe that `baseContent`/the rendered diff's "old" side contains the contents of `/etc/passwd` (or whatever the symlink target is) rather than being rejected, confirming the working-directory containment invariant is broken — compare against `buildConflictContext`, which would instead report `"File path is outside the repository"` for the same input.
