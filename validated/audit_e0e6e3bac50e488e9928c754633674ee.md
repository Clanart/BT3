### Title
Global unscoped "Open in Desktop" promise resolver allows cross-request repository/branch mix-up via deep links — ([File: app/src/lib/stores/app-store.ts])

### Summary
The reported Move bug is a broken-invariant class: a stateful "receipt" (the flash-loan receipt's `order_id`) is consumed without verifying it corresponds to the operation that created it, letting an attacker redirect the effect of one flow into another. GitHub Desktop's "Open in Desktop" deep-link flow has the same structural weakness: a single, unscoped instance field (`resolveOpenInDesktop`) is used as the "receipt" for whichever "Open in Desktop" request is currently pending, with no identifier tying a specific `_startOpenInDesktop` call to its matching `_completeOpenInDesktop` call. [1](#0-0) 

### Finding Description
`_startOpenInDesktop(fn)` stores the promise's `resolve` callback in the single instance field `this.resolveOpenInDesktop`, then invokes `fn()` (which typically shows a popup, e.g. `PopupType.CloneRepository` or `PopupType.AddRepository`) and returns a promise that will resolve once `_completeOpenInDesktop` is later called: [1](#0-0) 

`_completeOpenInDesktop(fn)` simply grabs whatever resolver is *currently* stored in `this.resolveOpenInDesktop`, clears it, computes a result, and resolves it — with no check that this resolver actually belongs to the request that is completing:

```
public async _completeOpenInDesktop(fn) {
  const resolve = this.resolveOpenInDesktop
  this.resolveOpenInDesktop = null
  const result = await fn()
  if (resolve) resolve(result)
  return result
}
```

This mirrors the vulnerable pattern in `limit_order::repay_flash_loan`: the "receipt" (`resolveOpenInDesktop`) carries no `order_id`-equivalent, so if two "Open in Desktop" flows are started before the first completes, the second `_startOpenInDesktop` call silently overwrites the resolver for the first (now-orphaned) flow, exactly like a second `flash_loan` order overwriting the expected recipient of a repay.

The flow is reachable from attacker-controlled input: the `x-github-client://openrepo/...` deep-link handler is parsed here, [2](#0-1) 

and dispatched without any per-request correlation id via `dispatchURLAction` → `openRepositoryFromUrl` → `openOrCloneRepository`/`openPullRequestFromUrl`/`openBranchNameFromUrl`, all of which call `this.appStore._startOpenInDesktop(...)`: [3](#0-2) [4](#0-3) [5](#0-4) 

Nothing in `dispatchURLAction`, `openRepositoryFromUrl`, or `_startOpenInDesktop`/`_completeOpenInDesktop` validates that the resolver being fulfilled corresponds to the URL/action that created it — the "order_id" equivalent (the originating URL, PR, or branch request) is never checked.

### Impact Explanation
If a malicious page or a chain of `x-github-client://` links delivers two "open repository from URL" (or CLI clone/open) requests to Desktop before the user finishes interacting with the first popup, the second call to `_startOpenInDesktop` overwrites the pending resolver. When the second flow's popup is later dismissed/completed (e.g., user cancels the `CloneRepository` popup for a benign second link, which calls `_completeOpenInDesktop(() => Promise.resolve(null))` in `_closePopup`), it resolves the *stored* resolver — which may actually belong to the first, still in-flight flow. The `await` in `openBranchNameFromUrl` / `openPullRequestFromUrl` / `openOrCloneRepository` then unblocks with a mismatched result (e.g., `null`, or a `Repository` object belonging to the wrong request), and the caller proceeds to fetch/checkout a branch, or to open a folder via `resolveWithin(repository.path, filepath)` and `shell.showItemInFolder`, against a repository object that was never validated to correspond to the URL the flow was working on. This can silently redirect a branch checkout or file-open action to the wrong local repository, corrupting the working tree the user believes they are operating on, or resolving a request early/incorrectly (permanently hanging the legitimate original flow).

This is weaker in severity than the original Move report (no direct fund loss equivalent exists in Desktop), but it is a genuine violation of the same invariant class: **a stateful completion token is consumed without verifying it matches its originator**, reachable purely through attacker-controlled deep links/CLI-style URL actions with no local access required.

### Likelihood Explanation
Exploitability requires the attacker to get the victim's Desktop app to process two "Open in Desktop" style requests in overlapping time windows (e.g., two `x-github-client://openrepo/...` links delivered back-to-back, or a link plus a stray CLI invocation). Electron/OS-level protocol-handler prompts on first navigation and the fact that a popup must be open when overwritten make this a timing-dependent, moderate-likelihood condition rather than a trivially reliable one; it also depends on the user having a `CloneRepository`/`AddRepository` popup open (or dismissing it) while a second link arrives. I was not able to fully confirm from the indexed code how the main-process `url-action` IPC event is queued/serialized across multiple incoming protocol invocations (i.e., whether `dispatchURLAction` calls can genuinely overlap in practice) — this would need to be verified in a live/Devin session against `app/src/main-process/app-window.ts` and `app/src/ui/index.tsx`'s `url-action` listener registration, which the index did not fully expose.

### Recommendation
Scope the "Open in Desktop" receipt to the specific request that created it instead of a single shared field: generate a per-request token/id when `_startOpenInDesktop` is called (analogous to adding `order_id` to the flash-loan receipt), thread it through to `_completeOpenInDesktop`, and only resolve if the completing request's token matches the currently pending one. Alternatively, maintain a queue/map of pending Open-in-Desktop requests keyed by a generated id (or by the originating URL/action) rather than a single mutable field, and reject/ignore completions that don't match the expected pending request.

### Proof of Concept
1. Attacker page issues two rapid navigations to `x-github-client://openrepo/https://github.com/victim/repoA?branch=main` then `x-github-client://openrepo/https://github.com/attacker/repoB` (or attacker triggers a CLI-style `clone-url` action shortly after a deep link, per `dispatchCLIAction`).
2. First call reaches `openBranchNameFromUrl` → `openOrCloneRepository(urlA)` → `appStore._startOpenInDesktop(...)`, storing `resolveOpenInDesktop` and showing the `CloneRepository` popup for repoA.
3. Before the user acts on the repoA popup, the second request arrives and calls `_startOpenInDesktop` again (for repoB), overwriting `resolveOpenInDesktop` and replacing the popup content/target with repoB's clone flow.
4. User dismisses/cancels what they believe is the repoB popup; `_closePopup` calls `_completeOpenInDesktop(() => Promise.resolve(null))`, resolving the currently stored resolver.
5. Because the resolver was never bound to a specific request id, this can resolve the *original* `openBranchNameFromUrl(urlA)` await with `null` or with repoB's `Repository` object, causing the branch-checkout/file-open logic intended for repoA to run against the wrong repository or fail to run against the correct one — without any error surfaced to the user (silent state confusion, mirroring the "receipt applied to the wrong order" root cause in the source report). [6](#0-5)

export function parseAppURL(url: string): URLActionType {
  const parsedURL = URL.parse(url, true)
  const hostname = parsedURL.hostname
  const unknown: IUnknownAction = { name: 'unknown', url }
  if (!hostname) {
    return unknown
  }

  const query = parsedURL.query

  const actionName = hostname.toLowerCase()
  if (actionName === 'oauth') {
    const code = getQueryStringValue(query, 'code')
    const state = getQueryStringValue(query, 'state')
    if (code != null && state != null) {
      return { name: 'oauth', code, state }
    } else {
      return unknown
    }
  }

  // we require something resembling a URL first
  // - bail out if it's not defined
  // - bail out if you only have `/`
  const pathName = parsedURL.pathname
  if (!pathName || pathName.length <= 1) {
    return unknown
  }

  // Trim the trailing / from the URL
  const parsedPath = pathName.substring(1)

  if (actionName === 'openrepo') {
    const pr = getQueryStringValue(query, 'pr')
    const branch = getQueryStringValue(query, 'branch')
    const filepath = getQueryStringValue(query, 'filepath')

    if (pr != null) {
      if (!/^\d+$/.test(pr)) {
        return unknown
      }

      // we also expect the branch for a forked PR to be a given ref format
      if (branch != null && !/^pr\/\d+$/.test(branch)) {
        return unknown
      }
    }

    if (branch != null && testForInvalidChars(branch)) {
      return unknown
    }

    return {
      name: 'open-repository-from-url',
      url: parsedPath,
      branch,
      pr,
      filepath,
    }
  }

  return unknown
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }

  public async dispatchURLAction(action: URLActionType): Promise<void> {
    switch (action.name) {
      case 'oauth':
        await this.appStore._resolveOAuthRequest(action)

        if (__DARWIN__) {
          // workaround for user reports that the application doesn't receive focus
          // after completing the OAuth signin in the browser
          const isFocused = await isWindowFocused()
          if (!isFocused) {
            log.info(
              `refocusing the main window after the OAuth flow is completed`
            )
            window.focus()
          }
        }
        break

      case 'open-repository-from-url':
        this.openRepositoryFromUrl(action)
        break

      default:
        const unknownAction: IUnknownAction = action
        log.warn(
          `Unknown URL action: ${
            unknownAction.name
          } - payload: ${JSON.stringify(unknownAction)}`
        )
    }
  }

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )
