### Title
Deep-link "Open Pull Request" handler selects and mutates a local repository without verifying it matches the link's target URL - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The reported bug class is a missing consistency check between two identifiers that should always match before a privileged action is taken (mint vs. token-account mint). The Desktop analog is in the `x-github-client://openRepo` deep-link handler: `openPullRequestFromUrl` fetches a `PullRequest` object using the link's `url`/`pr` parameters, but then hands off to `getRepositoryFromPullRequest`, which selects which *local* repository to operate on by matching the PR's `head`/`base` `clone_url` (both values come straight from the GitHub API and, for `head`, are fully attacker-controlled) against the origin/upstream remotes of the user's already-open repositories. The function never checks that the repository it picks corresponds to the `url` the user actually clicked. It then calls `_checkoutPullRequest` with the attacker-controlled `head.repo.clone_url` / `head.ref`, causing Desktop to add a remote and check out an attacker-chosen branch into whichever local repository happened to structurally match.

### Finding Description
`openPullRequestFromUrl` [1](#0-0)  is reached from `openRepositoryFromUrl`, the entry point for the `x-github-client://` protocol handler [2](#0-1) . Both `url` and `pr` in this flow are attacker-controlled: they come from a link the attacker crafts and the victim clicks.

Instead of validating that the eventually-selected repository corresponds to the `url` supplied in the link, `getRepositoryFromPullRequest` iterates over *every* repository the user currently has tracked in Desktop and returns the first one whose origin or upstream remote URL structurally matches the PR's `head.repo.clone_url` or `base.repo.clone_url` — values taken from the GitHub API response for the PR, not from the link itself: [3](#0-2)  and [4](#0-3) .

There is no equivalent of the missing `token_account.base.mint != *mint_info.key` check here: nothing verifies `urlsMatch(url, repository's GitHub URL)` before proceeding. Once a repository is "matched" this way, Desktop calls `_checkoutPullRequest` with the PR's `head.repo.owner.login`, `head.repo.clone_url`, and `head.ref` — all attacker-controlled if the attacker is the PR/fork author: [5](#0-4) . `_checkoutPullRequest`/`_findPullRequestBranch` then adds a new git remote for that clone URL and fetches/checks out the attacker's branch into the selected repository, without ever confirming the repository is the one named in the original deep link: [6](#0-5) .

### Impact Explanation
If an attacker crafts a public PR (on any repository, including one they fully control as author/fork owner) whose `head.repo.clone_url` happens to structurally match the origin/upstream of a repository the victim already has open in Desktop, then getting the victim to click a "Open in GitHub Desktop" deep link referencing that PR causes Desktop to silently add a remote pointing at the attacker's fork and check out the attacker's branch into a repository the victim did not intend to touch, changing the working tree to attacker-supplied content. This falls into "silent corruption of what the user commits or pushes" / unintended checkout of untrusted code triggered purely by a clicked link, which matches the accepted impact categories for this class.

### Likelihood Explanation
The likelihood is constrained: exploitation requires the attacker to know (or guess) the clone URL of a repository the victim already has cloned/tracked in Desktop, since matching is against the victim's local repository list rather than the link's declared target. This narrows practical targeting to well-known/public repositories the victim is likely to have open (e.g. the project itself, via a "head fork just happens to equal origin" trick is not directly exploitable, but `base.repo.clone_url` matching the victim's own tracked project is very plausible for popular open-source repos). Still, this is a genuine logic gap: the code was designed to associate a deep link with the exact repository named in it, but the actual selection logic silently substitutes a different, unrelated repository based on unrelated PR metadata, with no cross-check against the original `url` parameter.

### Recommendation
In `getRepositoryFromPullRequest` (or its caller `openPullRequestFromUrl`), require that the selected repository also satisfies `urlsMatch(url, repository's GitHub htmlURL/cloneURL)`, i.e. only allow a match against the deep link's own `url` (or an explicit, user-confirmed fallback), before invoking `_checkoutPullRequest`. This restores the missing "identifier consistency" check analogous to verifying `token_account.base.mint == mint_info.key` in the original report — ensuring the repository being mutated is provably the one the link named, not merely one whose remotes happen to structurally coincide with attacker-supplied API data.

### Proof of Concept
1. Attacker opens a PR (as author, using their own fork) against any public repository, setting the fork's clone URL to a value they control and that they know matches the origin/upstream of a repository commonly cloned by targets (e.g. the project's own canonical URL for `base.repo.clone_url`, which the attacker does not even need to control since it's simply the base repo they PR'd against).
2. Attacker sends the victim a link of the form `x-github-client://openRepo/<attacker-chosen-url>?pr=<PR number>&branch=...`.
3. Victim, who already has that (or a matching) repository open in Desktop, clicks the link.
4. `openRepositoryFromUrl` → `openPullRequestFromUrl` fetches the PR, `getRepositoryFromPullRequest` matches on `head`/`base` clone URL against the victim's existing repositories (not the link's `url`), and `_checkoutPullRequest` adds the attacker's fork remote and checks out the attacker's branch into that repository — all without any dialog confirming the repository identity matches the link.

Note: I could not find any additional guard (e.g., a confirmation dialog or explicit URL/repository binding check) elsewhere in `dispatcher.ts` or `app-store.ts` for this flow; if such a check exists outside the indexed portions of these files, it was not visible in the available code.

  private getRepositoryFromPullRequest(
    pullRequest: IAPIPullRequest
  ): RepositoryWithGitHubRepository | null {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const headUrl = pullRequest.head.repo?.clone_url
    const baseUrl = pullRequest.base.repo?.clone_url

    // This likely means that the base repository has been deleted
    // and we don't support checking out from refs/pulls/NNN/head
    // yet so we'll bail for now.
    if (headUrl === undefined || baseUrl === undefined) {
      return null
    }

    for (const repository of repositories) {
      if (this.doesRepositoryMatchUrl(repository, headUrl)) {
        return repository
      }
    }

    for (const repository of repositories) {
      if (this.doesRepositoryMatchUrl(repository, baseUrl)) {
        return repository
      }
    }

    return null
  }

  private doesRepositoryMatchUrl(
    repo: Repository | CloningRepository,
    url: string
  ): repo is RepositoryWithGitHubRepository {
    if (repo instanceof Repository && isRepositoryWithGitHubRepository(repo)) {
      const originRepoUrl = repo.gitHubRepository.htmlURL
      const upstreamRepoUrl = repo.gitHubRepository.parent?.htmlURL ?? null

      if (originRepoUrl !== null && urlsMatch(originRepoUrl, url)) {
        return true
      }

      if (upstreamRepoUrl !== null && urlsMatch(upstreamRepoUrl, url)) {
        return true
      }
    }

    return false
  }
