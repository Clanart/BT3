### Title
Submodule checkout can enable `file://` protocol (`protocol.file.allow=always`), letting a malicious repository read arbitrary local files via a submodule URL - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation()` conditionally appends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation whenever it is called with `allowFileProtocol = true`. [1](#0-0)  This flag is threaded through `checkoutBranch()` and `checkoutCommit()` in `app/src/lib/git/checkout.ts`, both of which default the parameter to `false` but accept a caller-supplied override. [2](#0-1) [3](#0-2)  `protocol.file.allow=always` disables Git's default hardening (added after CVE-2017-1000117/CVE-2018-11235-class issues) that normally blocks `file://` submodule URLs during recursive submodule operations.

### Finding Description
The `.gitmodules` file and the submodule URLs recorded in a repository's tree are fully attacker-controlled content once a user clones or fetches a hostile repository. Git's own protection against untrusted submodule URLs is the default-disabled `protocol.file.allow` setting, which normally prevents a submodule entry such as `url = file:///home/victim/.ssh` from being resolved during `git submodule update --init --recursive`. Desktop's code path deliberately re-enables this protection bypass (`-c protocol.file.allow=always`) whenever `allowFileProtocol` is `true` when calling `updateSubmodulesAfterOperation` from `checkoutBranch`/`checkoutCommit`. [4](#0-3) 

Because the value of `allowFileProtocol` is passed down from the checkout call sites (`app-store.ts`, `dispatcher.ts`) rather than derived from any verification of the submodule URLs actually present in the (possibly malicious) repository, there is no on-path check that the submodule URLs being resolved with `file://` allowed are safe or intended by the current remote — the same "offchain trust with no onchain verification" pattern as the source report: a privileged capability (`protocol.file.allow=always`) is granted based on a context decision (e.g., "we're checking out a local/trusted-looking repo") rather than validating the *actual* untrusted data (`.gitmodules` submodule URLs) that will be consumed by that capability.

### Impact Explanation
If a crafted repository is cloned/fetched and checked out through a path where `allowFileProtocol` is `true`, `git submodule update --init --recursive` will honor a submodule URL of `file:///arbitrary/local/path`. Git will "clone" that local path's `.git` contents into the submodule directory inside the repository working tree, effectively copying arbitrary local filesystem content into a location the user can browse, diff, and — critically — commit and push, i.e., silently exfiltrating local data outside the intended repo into version control, or providing a primitive for reading files outside the repo. This satisfies the valid-impact category of "file read outside the repo" / "silent corruption of what the user commits or pushes" driven purely by cloning/fetching an attacker-controlled repository.

### Likelihood Explanation
Medium/Low-confidence without full call-site verification: I confirmed that `allowFileProtocol` is a real, plumbed-through parameter with a concrete effect (`protocol.file.allow=always`), and that its default is `false` at the `checkout.ts` API layer, but I was not able to fully enumerate every call site in `app-store.ts`/`dispatcher.ts` (8 and 6 matches respectively) to confirm under exactly which application-level condition Desktop passes `true`. This is a genuine gap in my analysis — the exploitability hinges entirely on whether any reachable UI/dispatcher flow sets `allowFileProtocol = true` for repositories whose submodule URLs come from untrusted/attacker-controlled content (e.g., a first-time checkout of a branch from a freshly cloned malicious repo), versus only being used for previously-trusted local fixtures/tests.

### Recommendation
- Never gate `protocol.file.allow` on a boolean flag that isn't derived from actually inspecting the submodule URLs about to be resolved.
- Before allowing `file://` submodule protocol, parse `.gitmodules`/`git config --get-regexp submodule\..*\.url` and confirm every URL resolves to a path already known to be part of the user's own filesystem trust boundary (e.g., only allow it for submodules whose target is inside the same repository clone's directory tree, matching upstream Git's own submodule protocol allowlist model), otherwise default to Git's stock protection (deny `file://`).
- Surface a warning/confirmation to the user when a submodule requests the `file://` protocol, similar to the existing force-push and clone-path-safety confirmations already present elsewhere in the codebase (`app/src/lib/git/clone.ts`, `isClonePathSensitive`).
