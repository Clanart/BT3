### Title
Hardcoded 1 sat/vB Fallback Fee Rate in `get_fee_rate_sat_per_kvb` Stalls All Time-Sensitive Bridge Transactions When Both Fee Sources Fail — (`File: crates/clementine-extended-rpc/src/client.rs`)

---

### Summary

`get_fee_rate_sat_per_kvb` silently falls back to a hardcoded `1000 sat/kvB` (= 1 sat/vB) when both mempool.space and Bitcoin Core `estimatesmartfee` fail simultaneously on mainnet/testnet4/signet. Every bridge transaction submitted or fee-bumped by the tx-sender during that window uses this floor rate. During a fee-spike event (common on mainnet), 1 sat/vB is below the mempool minimum relay fee, causing kickoff, challenge, payout, and reimbursement transactions to be evicted or never confirmed — potentially within their timelock windows — exposing operator collateral and bridged BTC to loss.

---

### Finding Description

In `crates/clementine-extended-rpc/src/client.rs`, the private function `get_fee_rate_sat_per_kvb` handles the dual-source fee estimation for mainnet/testnet4/signet:

```rust
(Err(mempool_err), Err(rpc_err)) => {
    tracing::warn!(
        "Both fee sources failed (mempool: {:#}, rpc: {:#}), using default of 1000 sat/kvB",
        mempool_err, rpc_err
    );
    Amount::from_sat(1000) // 1 sat/vB * 1000 = 1000 sat/kvB
}
``` [1](#0-0) 

The value `1000 sat/kvB` is hardcoded with no operator-configurable floor. `TxSenderLimits` exposes `fee_rate_hard_cap` (a ceiling) but no `fee_rate_fallback` (a floor): [2](#0-1) 

The tx-sender task calls `get_fee_rate()` on every cycle and passes the result directly to all fee-paying operations: [3](#0-2) 

`TxSender::get_fee_rate()` is a thin wrapper that forwards to `get_fee_rate_kvb`: [4](#0-3) 

The same fee rate is used for the payout transaction (operator-side): [5](#0-4) 

The fee-bumping path (CPFP/RBF) also calls `get_fee_rate()` each bump cycle, so if both sources remain down, every subsequent bump attempt also uses 1 sat/vB — the bump loop is rendered ineffective.

---

### Impact Explanation

Bitcoin mainnet regularly operates at 5–200+ sat/vB. At 1 sat/vB:

- **Kickoff, challenge, payout, and reimbursement transactions** submitted by the tx-sender will be rejected by mempools enforcing a minimum relay fee above 1 sat/vB, or will be evicted during congestion.
- **Timelock-bounded operations** (challenge window `OPERATOR_CHALLENGE_TIMEOUT_TIMELOCK`, disprove window `DISPROVE_TIMEOUT_TIMELOCK`, reimbursement window `OPERATOR_REIMBURSE_TIMELOCK`) will expire unconfirmed.
- An operator whose challenge or reimbursement transaction does not confirm in time loses collateral (`OPERATOR_CHALLENGE_AMOUNT`, `COLLATERAL_FUNDING_AMOUNT`).
- A user whose payout transaction does not confirm loses bridged BTC.
- The fee-bump loop (`fee_bump_after_blocks = 10`) does not recover the situation because each bump iteration re-queries the same failing sources and receives the same 1 sat/vB fallback.

This matches the allowed impact gate: **slashable exposure of operator collateral and permanent lock of bridged BTC** due to a hardcoded static value in the tx-sender fee path.

---

### Likelihood Explanation

Both sources can fail simultaneously in realistic scenarios:

1. `estimatesmartfee` returns an error when the node has insufficient block history (fresh sync, pruned node, or the node is syncing after a restart).
2. mempool.space is rate-limited, unreachable, or returns a non-success HTTP status — the retry logic exhausts its 4 attempts with exponential back-off and then returns `Err`.
3. A network partition or firewall rule blocks outbound HTTP to both endpoints simultaneously.
4. A deliberate DoS against the operator's mempool.space API key or IP triggers rate-limiting on the external API while the local node is also temporarily unavailable.

The combination is low-frequency but not negligible, and the impact when it coincides with a fee spike is material.

---

### Recommendation

1. **Make the fallback configurable.** Add a `fee_rate_fallback_sat_kvb: u64` field to `TxSenderLimits` with a safe default (e.g., `10_000 sat/kvB` = 10 sat/vB). Operators can tune this to their risk tolerance.

2. **Fail loudly instead of silently.** When both sources fail, return an error from `get_fee_rate_sat_per_kvb` rather than silently proceeding. The tx-sender task can then skip the send cycle and alert operators, rather than submitting transactions at a rate that will be rejected.

3. **Add a configurable floor guard.** Even when one source succeeds, enforce `max(selected_fee, fee_rate_floor)` so that a spuriously low estimate from a single source does not produce the same outcome.
