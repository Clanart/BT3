### Title
Endianness Mismatch in `verify_storage_proofs` Produces Wrong Withdrawal Vout, Causing Bridge Circuit Panic and Operator Collateral Slashing — (`circuits-lib/src/bridge_circuit/storage_proof.rs`)

---

### Summary

`verify_storage_proofs` decodes the withdrawal UTXO's `vout` from EVM storage using `u32::from_le_bytes`, but EVM (Citrea L2) stores `uint32` values in big-endian order. For any withdrawal whose UTXO has `vout != 0`, the decoded value is wrong by a factor of up to `0x01000000` (16,777,216 for `vout = 1`). The bridge circuit then asserts this corrupted value against the actual `vout` in the payout transaction, causing an unconditional panic. An operator who paid out against such a UTXO cannot generate a valid bridge-circuit proof, cannot post correct assert transactions, and therefore cannot disprove a challenge — resulting in their collateral being slashed.

---

### Finding Description

In `circuits-lib/src/bridge_circuit/storage_proof.rs`, the `verify_storage_proofs` function reads the withdrawal output index from the Citrea L2 storage proof:

```rust
let buf: [u8; 32] = vout_storage_proof.value.to_be_bytes();

// ENDIANNESS SHOULD BE CHECKED THIS FIELD IS 4 BYTES in the contract
let vout = u32::from_le_bytes(
    buf[28..32]
        .try_into()
        .expect("Vout value conversion failed"),
);
``` [1](#0-0) 

`vout_storage_proof.value` is a `U256` whose `.to_be_bytes::<32>()` produces a 32-byte big-endian array. For a Solidity `uint32` stored in an EVM slot, the value is right-aligned in big-endian. For `vout = 1`:

- `U256::from(1).to_be_bytes::<32>()` → `[0x00, …, 0x00, 0x01]`
- `buf[28..32]` → `[0x00, 0x00, 0x00, 0x01]`
- `u32::from_le_bytes([0x00, 0x00, 0x00, 0x01])` → **`0x01000000` = 16,777,216** ✗
- `u32::from_be_bytes([0x00, 0x00, 0x00, 0x01])` → **`1`** ✓

The developer's own comment — `// ENDIANNESS SHOULD BE CHECKED THIS FIELD IS 4 BYTES in the contract` — flags this as unresolved. The wrong endianness was chosen.

The corrupted `vout` is then used directly in the bridge circuit's assertion:

```rust
assert_eq!(
    vout,
    input.payout_spv.transaction.input[payout_input_index]
        .previous_output
        .vout,
    "Invalid withdrawal transaction output index"
);
``` [2](#0-1) 

Because the actual payout transaction references `vout = 1` but the circuit computed `16,777,216`, the assertion panics unconditionally. The operator cannot produce a valid RISC0 receipt, cannot post correct WOTS-committed assert transactions, and cannot disprove a challenge.

The `verify_storage_proofs` function is called from the main `bridge_circuit` entry point: [3](#0-2) 

And the host-side `prove_bridge_circuit` also calls the same path: [4](#0-3) 

---

### Impact Explanation

- **Operator collateral slashing**: Any operator who fronted a withdrawal whose UTXO has `vout != 0` cannot run the bridge circuit successfully. They cannot post valid assert transactions. A challenger can then execute the disprove transaction and burn the operator's collateral.
- **Reimbursement loss**: Even without an active challenge, the operator cannot prove the payout was valid and cannot claim reimbursement from the bridge vault.
- **Bridged BTC at risk**: If operators are systematically slashed or exit the protocol, bridge liveness degrades and deposited BTC may become inaccessible.

This matches the allowed impact gate: *slashable exposure of operator collateral* and *permanent lock of reimbursement outputs*.

---

### Likelihood Explanation

Bitcoin transactions routinely place outputs at `vout > 0`. A `send_to_address` call with a change output places the target at `vout = 0` only if the wallet orders it that way — this is wallet-implementation-dependent and not guaranteed. Any user who initiates a withdrawal whose UTXO lands at `vout = 1` (e.g., because the funding transaction has another output first) triggers the bug. No privileged access is required; normal withdrawal flow is sufficient.

---

### Recommendation

Replace `from_le_bytes` with `from_be_bytes` to match EVM's big-endian storage layout:

```diff
-let vout = u32::from_le_bytes(
+let vout = u32::from_be_bytes(
     buf[28..32]
         .try_into()
         .expect("Vout value conversion failed"),
 );
``` [5](#0-4) 

Add a test that exercises `vout = 1` and `vout = 2` to prevent regression.

---

### Proof of Concept

Given a withdrawal UTXO at `vout = 1` (stored in the Citrea bridge contract as `U256::from(1)`):

1. `vout_storage_proof.value = U256::from(1)`
2. `buf = [0x00; 28] ++ [0x00, 0x00, 0x00, 0x01]`
3. `buf[28..32] = [0x00, 0x00, 0x00, 0x01]`
4. `u32::from_le_bytes([0x00, 0x00, 0x00, 0x01]) = 16_777_216`
5. Payout transaction has `input[0].previous_output.vout = 1`
6. `assert_eq!(16_777_216, 1)` → **panic: "Invalid withdrawal transaction output index"**
7. Operator cannot produce a RISC0 receipt → cannot post assert transactions → challenger executes disprove → collateral slashed.

The existing test in `storage_proof.rs` only exercises `expected_vout = 1` against a pre-baked binary fixture: [6](#0-5) 

That test passes only because the fixture's raw bytes happen to produce `vout = 1` under the current (wrong) little-endian decoding — meaning the fixture itself was generated with the same endianness bug, masking the defect.
