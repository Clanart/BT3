## Analog Identified

The C4 finding is about low-level calls silently returning `success=true` when the target has no code. A direct analog exists in the **Tron deployment** of the Intent Gateway, which deliberately bypasses `SafeERC20` (used everywhere else in the codebase) and performs raw low-level calls for token transfers, checking only the boolean `success` flag.

### Title
Escrow redemption/refund in Tron `IntentGatewayV2` uses raw low-level `token.call` for transfers, accepting false success from codeless (self-destructed) tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron variant of `IntentGatewayV2` move escrowed ERC20/TRC20 funds using `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only check the boolean `success` return value, instead of using `SafeERC20.safeTransfer`, which the mainline EVM contracts (`evm/src/apps/intentsv2/IntentsBase.sol`) use for the identical operation. [1](#0-0) [2](#0-1) 

### Finding Description
In `withdraw()`, escrow accounting is decremented and `EscrowReleased`/`EscrowRefunded` is emitted purely based on the boolean success of a raw `.call()`: [3](#0-2) 

A call to an address with no deployed contract code trivially returns `success = true` because there is no code to execute and nothing to revert. Unlike `SafeERC20.safeTransfer` (used in `IntentsBase.sol`), which internally checks `target.code.length` via OpenZeppelin's `Address.functionCall` and reverts (`AddressEmptyCode`) when the target has no code, the Tron contract's raw `.call()` has no such guard, even though `SafeERC20` is already imported and used elsewhere in the same file for `safeTransferFrom`: [4](#0-3) 

An order creator fully controls the `order.inputs[].token` address supplied to `placeOrder`/`create`, and can deploy an arbitrary ERC20-like contract that behaves normally at escrow time (so `safeTransferFrom` in the create path succeeds) but can later self-destruct that contract once a filler has completed delivery on the destination chain and the `RedeemEscrow` message is dispatched back. If the Tron VM honors classic `SELFDESTRUCT` semantics (removing contract code), the token address becomes codeless before `withdraw()` executes on the source chain. When the honestly-relayed `RedeemEscrow` message is processed, `token.call(...)` against the now-codeless address returns `success = true` with no state change, `_orders[commitment][token]` is decremented as if funds were paid out, and `EscrowReleased` fires — but the filler/beneficiary receives nothing.

### Impact Explanation
This is a false state acceptance / fund-loss path: the solver who legitimately delivered output assets on the destination chain is never actually paid the corresponding escrowed input tokens on the source chain, yet the protocol's bookkeeping marks the order as settled. No relayer, prover, or admin misbehavior is required — the relayer is honestly relaying a legitimate cross-chain message; the vulnerability is solely in `withdraw()`'s unchecked low-level call accepting a no-op as a successful transfer.

### Likelihood Explanation
The attacker (order creator) fully controls the token contract used as an escrowed input asset and its self-destruct timing, requiring no privileged role, malicious peer, or compromised infrastructure — only that the underlying Tron VM still executes destructive `SELFDESTRUCT` (code removal) for pre-existing contracts, which is the standard legacy EVM/TVM behavior that OpenZeppelin's `Address.functionCall` code-existence check was specifically introduced to guard against.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(...)` (already imported via `SafeERC20` in this file), matching the pattern used in `evm/src/apps/intentsv2/IntentsBase.sol`, so that transfers to codeless addresses revert instead of silently "succeeding."

### Proof of Concept
1. Attacker deploys `EvilToken`, a normal-looking ERC20/TRC20 with an added `selfDestruct()` function callable by attacker.
2. Attacker calls `placeOrder` on the source-chain `IntentGatewayV2`, escrowing `EvilToken` as `order.inputs[0]`; `safeTransferFrom` succeeds since the token has code and behaves normally.
3. A filler fills the order on the destination chain, delivering real output assets to the beneficiary and triggering dispatch of a `RedeemEscrow` `WithdrawalRequest` back to the source chain.
4. Before this message is delivered/processed, the attacker calls `EvilToken.selfDestruct()`, removing its code.
5. The relayer honestly relays the `RedeemEscrow` message; `onAccept` → `withdraw()` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` against the codeless `EvilToken` address, which returns `success = true` with no transfer occurring.
6. `_orders[commitment][token]` is decremented, `EscrowReleased` is emitted, and the filler never receives the escrowed tokens despite having delivered on the destination chain. [5](#0-4)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
