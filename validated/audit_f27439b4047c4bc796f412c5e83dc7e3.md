## Title
Uncontrolled recursive puzzle-driver matching on attacker-supplied offer/spend puzzle reveals can cause a Python stack overflow (`RecursionError`) — analogous to CVE-2021-30470 — ([File: chia/wallet/outer_puzzles.py])

## Summary
The reported CVE describes uncontrolled mutual recursion between `PdfTokenizer::ReadArray()`, `GetNextVariant()`, and `ReadDataType()` that overflows the native stack when parsing deeply nested, attacker-controlled input. Chia's core CLVM byte-parser (`Program.from_bytes()`) is not vulnerable to this class of bug because it delegates parsing to the Rust CLVM engine, and `sha256_treehash()` was deliberately rewritten as an iterative stack machine specifically "to avoid Python recursion limits on deeply nested CLVM" [1](#0-0) . However, the wallet's *puzzle-driver matching* layer reintroduces the same bug class in pure Python.

## Finding Description
`chia/wallet/outer_puzzles.py` dispatches `match_puzzle()`, `get_inner_puzzle()`, `get_inner_solution()`, and `solve_puzzle()` across a fixed table of outer-puzzle drivers (`CATOuterPuzzle`, `SingletonOuterPuzzle`, `MetadataOuterPuzzle`, `OwnershipOuterPuzzle`, `CROuterPuzzle`, etc.) [2](#0-1) . Each driver's `match`/`get_inner_puzzle`/`get_inner_solution`/`solve` implementation recurses into the *inner* layer via `self._match`, `self._get_inner_puzzle`, `self._get_inner_solution`, or `self._solve` whenever the puzzle's `also()` chain indicates another layer is present — e.g. `CATOuterPuzzle.get_inner_puzzle()` [3](#0-2) , `MetadataOuterPuzzle` [4](#0-3) , `OwnershipOuterPuzzle` [5](#0-4) , `SingletonOuterPuzzle` [6](#0-5) , and `CROuterPuzzle` [7](#0-6) .

This recursion depth is bounded only by how many "curry" layers an attacker can wrap into a puzzle reveal (e.g. `CAT_MOD(CAT_MOD(CAT_MOD(...ACS...)))`), not by CLVM execution cost — the matching happens on the raw `Program` structure before/independent of running it. There is no depth limit, cycle check, or `sys.setrecursionlimit`-aware guard anywhere in this driver chain, unlike `sha256_treehash`'s explicit iterative rewrite.

This matching path is directly reachable from an untrusted, attacker-supplied `Offer`: `Offer._get_offered_coins()` calls `match_puzzle(parent_puzzle)` → `get_inner_puzzle(puzzle_driver, ...)` on every coin spend inside a received offer file/spend bundle, using the counterparty-controlled `puzzle_reveal` [8](#0-7) . Offers are parsed via `Offer.from_bech32()`/`Offer.from_bytes()` when a user runs `take_offer`/examines an offer file [9](#0-8) , i.e., a wallet-user or offer-counterparty–controlled entry point.

## Impact Explanation
A malicious offer-file counterparty (or a peer broadcasting a crafted spend bundle later inspected by wallet driver-matching code) can nest asset layers (CAT-in-CAT, singleton+metadata+ownership+CR stacks, etc.) deeply enough to exceed the default CPython recursion limit while remaining well within the puzzle byte-size and CLVM cost limits enforced elsewhere. This raises an uncaught `RecursionError` deep inside the wallet's offer-processing / puzzle-matching code, which is not caught as a `ValidationError` and can crash or hang the wallet's transaction-processing task — a spend/offer-triggered transaction-processing halt, matching the impact classes the scan explicitly accepts.

## Likelihood Explanation
Medium: constructing a puzzle reveal with hundreds of thousands of nested curry layers requires crafting valid CLVM bytes but no signatures, special privileges, or consensus-level cost limits are hit before the Python-side matcher runs (matching happens on the raw `Program` tree, not gated by CLVM execution cost). The main constraints are puzzle-reveal byte size and offer/RPC transport limits, which are large enough to accommodate a stack-overflow-depth of nesting given each CAT/singleton curry layer is only tens of bytes.

## Recommendation
Rewrite the recursive `match`/`get_inner_puzzle`/`get_inner_solution`/`solve` chain in `chia/wallet/outer_puzzles.py` and its per-asset drivers (`cat_outer_puzzle.py`, `metadata_outer_puzzle.py`, `ownership_outer_puzzle.py`, `singleton_outer_puzzle.py`, `cr_outer_puzzle.py`) as an iterative loop over the `also()`/layer chain (mirroring the pattern already used in `sha256_treehash`), or impose an explicit maximum layer-depth check before recursing, and ensure `RecursionError` is caught and converted into a `ValidationError`/rejection rather than propagating and crashing the wallet task.

## Proof of Concept
Conceptually: construct a puzzle reveal `P` such that `P = CAT_MOD.curry(CAT_MOD_HASH, tail, P')` repeated N times (N ≈ Python recursion limit, e.g. 2,000–10,000, each layer costing a small, fixed number of bytes), wrap it into an `Offer`/`CoinSpend`, and call `Offer.from_bech32(offer)` followed by `offer._get_offered_coins()` (invoked internally during `Offer.summary()`/`take_offer`). The nested `match_puzzle()` → `CATOuterPuzzle.match()` → `self._match(...)` recursion will exceed CPython's stack depth and raise `RecursionError`, halting wallet processing of that offer. (I was not able to execute this PoC in this environment; the depth threshold and exact byte size needed would need to be empirically confirmed with a running wallet instance.)
