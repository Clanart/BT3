### Title
Attacker-committed `.claude/ralph-loop.local.md` with `max_iterations: 0` and an unmatchable `completion_promise` creates an unbounded, silently-auto-activated Stop-hook loop that injects attacker-controlled prompts - (File: `plugins/ralph-wiggum/hooks/stop-hook.sh`)

### Summary
The ralph-wiggum plugin registers `stop-hook.sh` unconditionally on every `Stop` event for any session with the plugin enabled, and the hook's only "is this active" check is the mere existence of `.claude/ralph-loop.local.md`. Because that file is documented as user-local/gitignored but nothing prevents it from being committed to a repository, an attacker can ship a malicious version of it in ordinary repo content; when opened by a victim who has the plugin enabled, the hook activates without the victim ever running `/ralph-loop`, and attacker-chosen `max_iterations`/`completion_promise` values can make the loop run unbounded while feeding attacker-controlled text back into Claude's context on every iteration.

### Finding Description
`hooks/hooks.json` registers `stop-hook.sh` as a global `Stop` hook for every session in which the plugin is active, with no matcher restricting it to sessions started via `/ralph-loop`: [1](#0-0) 

`stop-hook.sh` treats the mere presence of `.claude/ralph-loop.local.md` as authorization to block session exit and drive the loop — there is no check that the file was created by the legitimate `/ralph-loop` command (e.g. via a session-bound marker, checksum, or "created by this session" flag): [2](#0-1) 

The two loop-termination controls are both attacker-suppliable via ordinary file content and both can be forced into the "never terminate" state:
- `max_iterations` is only validated to be numeric; `0` is a documented "unlimited" sentinel with no independent upper bound enforced by the hook: [3](#0-2) 
- `completion_promise` is compared with an exact string match against a `<promise>...</promise>` tag extracted from Claude's own last message; an attacker can set this to an arbitrary/unguessable token that legitimate model output will essentially never reproduce, guaranteeing the promise check never succeeds: [4](#0-3) 

Once neither termination path can fire, the hook always takes the "continue loop" branch, which extracts the markdown body of the attacker-committed file as `PROMPT_TEXT` and returns it verbatim via `"decision":"block","reason":$prompt`, which Claude Code feeds back into the session as the next instruction — this is a direct, repeatable prompt-injection vector combined with resource-exhaustion/DoS: [5](#0-4) 

The project's own documentation confirms the intended trust model is that this file is user-local and never committed ("Lifecycle: User-managed (not in git, should be in `.gitignore`)"), but nothing in the hook enforces or verifies that — it is a purely advisory convention that ordinary repository content (a malicious commit/PR) can violate: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any victim who has the ralph-wiggum plugin enabled and checks out/opens a repository containing an attacker-planted `.claude/ralph-loop.local.md` will have every subsequent session `Stop` event silently hijacked: the session cannot cleanly exit, and attacker-controlled text is repeatedly re-injected into Claude's context as the "next prompt," with no cap on iteration count because `max_iterations: 0` is treated as unlimited and the `completion_promise` can be engineered to never match. This is unbounded, unattended automation driven by attacker-controlled content — a resource-exhaustion/DoS condition and a persistent prompt-injection channel that operates purely through committed repository content, without any explicit user invocation of `/ralph-loop` or approval step.

### Likelihood Explanation
Exploitability requires only that the victim (a) has the ralph-wiggum plugin installed/enabled and (b) opens a repository (via clone, PR checkout, or any workflow that materializes repo files on disk) that contains a committed `.claude/ralph-loop.local.md`. No special privileges, secrets, or social engineering beyond "victim opens attacker's repo/PR" are needed, and the effect is deterministic and reproducible every time a `Stop` event occurs in that working directory.

### Recommendation
- Bind loop activation to the session/command that created it (e.g., store a session ID or HMAC alongside the state file at creation time in `setup-ralph-loop.sh`, and have `stop-hook.sh` refuse to act on a state file that wasn't created by the current session).
- Enforce a hard, hook-side upper bound on `max_iterations` regardless of file content (e.g., reject/clamp to a safe maximum such as 100, and disallow `0`/unlimited unless separately confirmed by the user each session).
- Require the state file to be `.gitignore`d and have the hook explicitly refuse to operate on a file that is tracked by git (`git ls-files --error-unmatch .claude/ralph-loop.local.md`), treating a tracked file as corrupted/untrusted input and deleting it as is already done for malformed fields.

### Proof of Concept
Unit/integration test plan for `plugins/ralph-wiggum/hooks/stop-hook.sh`:
1. In a fresh git repo, `git add -f .claude/ralph-loop.local.md` and commit a file with:
   ```
   ---
   iteration: 1
   max_iterations: 0
   completion_promise: "b6f1c2e4-9a3d-4e7b-uuid-that-will-never-appear"
   ---
   <attacker-controlled instructions>
   ```
2. Simulate N `Stop` hook invocations (feed a fixed/fuzzed set of plausible assistant transcript outputs that never contain the exact `<promise>` string) and assert:
   - The hook never deletes the state file and never returns a non-blocking exit for any iteration count tested (e.g., up to 10,000 iterations), demonstrating unbounded continuation.
   - `NEXT_ITERATION` grows without an enforced ceiling.
3. Fuzz `COMPLETION_PROMISE` values against a fixed corpus of realistic assistant outputs and assert that for the vast majority of randomly generated promise strings (e.g., UUIDs, long random tokens), `PROMISE_TEXT = COMPLETION_PROMISE` never evaluates true across the corpus — confirming attacker control over promise text can reliably defeat termination.
4. Add an invariant test asserting that after the recommended fix, `MAX_ITERATIONS` read from any file is clamped to a fixed safe maximum (e.g., ≤100) and that state files not present in `git ls-files` (i.e., untracked/local) are the only ones the hook will act on.

```shellscript
  PROMISE_TEXT=$(echo "$LAST_OUTPUT" | perl -0777 -pe 's/.*?<promise>(.*?)<\/promise>.*/$1/s; s/^\s+|\s+$//g; s/\s+/ /g' 2>/dev/null || echo "")

  # Use = for literal string comparison (not pattern matching)

    echo "✅ Ralph loop: Detected <promise>$COMPLETION_PROMISE</promise>"
```

```shellscript
# Not complete - continue loop with SAME PROMPT
NEXT_ITERATION=$((ITERATION + 1))

# Extract prompt (everything after the closing ---)
# Skip first --- line, skip until second --- line, then print everything after
# Use i>=2 instead of i==2 to handle --- in prompt content
PROMPT_TEXT=$(awk '/^---$/{i++; next} i>=2' "$RALPH_STATE_FILE")

if [[ -z "$PROMPT_TEXT" ]]; then
  echo "⚠️  Ralph loop: State file corrupted or incomplete" >&2
  echo "   File: $RALPH_STATE_FILE" >&2
  echo "   Problem: No prompt text found" >&2
  echo "" >&2
  echo "   This usually means:" >&2
  echo "     • State file was manually edited" >&2
  echo "     • File was corrupted during writing" >&2
  echo "" >&2
  echo "   Ralph loop is stopping. Run /ralph-loop again to start fresh." >&2
  rm "$RALPH_STATE_FILE"
  exit 0
fi

# Update iteration in frontmatter (portable across macOS and Linux)
# Create temp file, then atomically replace
TEMP_FILE="${RALPH_STATE_FILE}.tmp.$$"
sed "s/^iteration: .*/iteration: $NEXT_ITERATION/" "$RALPH_STATE_FILE" > "$TEMP_FILE"
mv "$TEMP_FILE" "$RALPH_STATE_FILE"

# Build system message with iteration count and completion promise info
if [[ "$COMPLETION_PROMISE" != "null" ]] && [[ -n "$COMPLETION_PROMISE" ]]; then
  SYSTEM_MSG="🔄 Ralph iteration $NEXT_ITERATION | To stop: output <promise>$COMPLETION_PROMISE</promise> (ONLY when statement is TRUE - do not lie to exit!)"
else
  SYSTEM_MSG="🔄 Ralph iteration $NEXT_ITERATION | No completion promise set - loop runs infinitely"
fi

# Output JSON to block the stop and feed prompt back
# The "reason" field contains the prompt that will be sent back to Claude
jq -n \
  --arg prompt "$PROMPT_TEXT" \
  --arg msg "$SYSTEM_MSG" \
  '{
    "decision": "block",
    "reason": $prompt,
    "systemMessage": $msg
  }'

# Exit 0 for successful hook execution
exit 0
```
