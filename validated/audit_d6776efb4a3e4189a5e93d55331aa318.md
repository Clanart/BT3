### Title
`open-external` IPC handler forwards attacker-controlled strings to `shell.openExternal` without enforcing a protocol allowlist - (File: app/src/main-process/main.ts)

### Summary
The renderer-to-main IPC handler for `open-external` is the sole gate between renderer-originated URLs (including those derived from commit messages, PR/issue bodies, and other repository/API content rendered by `RichText` and `SandboxedMarkdown`) and Electron's `shell.openExternal`. It performs no scheme validation — it merely checks whether the string starts with `http://`/`https://` for logging purposes, then calls `shell.openExternal(path)` regardless of the outcome of that check. Renderer-side guards exist in some paths (e.g. `SandboxedMarkdown`'s `setupLinkInterceptor` restricts to `^https?:`), but this is not enforced end-to-end at the trust boundary, and the `RichText`/`LinkButton` path used for free-text tokens (commit messages, release notes) has no such restriction before reaching `shell.openExternal`.

### Finding Description
`text-token-parser.ts`'s `scanForHyperlink` auto-linkifies any substring matching `/^https?:\/\/.+/` found in repository-controlled text (e.g., a commit message body rendered via `RichText` in `expandable-commit-summary.tsx`), producing a `Link` token that is rendered as a `LinkButton`. [2](#0-1) [3](#0-2) 

`LinkButton.onClick` calls `shell.openExternal(uri)` directly with whatever string was matched, with no further validation of the resolved value (e.g. after redirects encoded into the URL, or unicode/host confusables not filtered by the naive regex). [4](#0-3) 

That call is proxied over IPC to the main process, where the actual `open-external` handler is the final and only trust boundary before Electron's `shell.openExternal` executes. The handler's check is purely cosmetic: it only decides *whether to log*, and unconditionally forwards the value to `shell.openExternal` in all cases, including any non-`http(s)` string that slipped through renderer-side matching (e.g., if a future/alternate caller — of which there are many `dispatcher.openInBrowser`/`_openInBrowser` callers throughout the codebase — passes a value assembled from repository or API data without the `^https?:` renderer check). [1](#0-0) 

This mirrors the audit's underlying pattern: a downstream security-relevant sink (`SubgroupCheckG1WithValidX` / here, Electron's `shell.openExternal`) assumes an invariant about its input (well-formed BigInt limbs / here, a benign `http(s)` URL) that is enforced inconsistently upstream and not re-validated at the actual trust boundary (the IPC handler in the main process, which is the last line of defense since the renderer is the less-trusted process).

### Impact Explanation
`shell.openExternal` can be abused by malformed URIs/paths to launch arbitrary local applications or trigger OS-level protocol handlers (this is the class of issue behind several past Electron `shell.openExternal` advisories on Windows). Because the real enforcement point (the main-process IPC handler) does not reject non-`http(s)` values, any code path that reaches `dispatcher.openInBrowser`/`shell.openExternal` with attacker-influenced text bypasses the intended protection, potentially executing arbitrary local binaries or protocol handlers when the user merely views a commit message, release note, or similar content sourced from a cloned/fetched repository or the GitHub API.

### Likelihood Explanation
Medium-low. The most obvious paths (`SandboxedMarkdown`) already gate on `^https?:` client-side, and `text-token-parser.ts`'s own regex is also `^https?://` at time of matching. Exploitability therefore depends on finding a caller of `openInBrowser`/`shell.openExternal` that passes an unvalidated, attacker-influenced string, or on a client-side validation bypass (encoding tricks, whitespace, or Electron/URL parser quirks) that the naive regex does not catch but that Electron's OS-level URL/path handling still interprets specially. I was not able to fully verify within the available context whether such a bypass exists in the current codebase, since this requires exhaustively tracing every `_openInBrowser`/`shell.openExternal` caller and the exact regex/URL-parsing edge cases — this is the main uncertainty in this finding.

### Recommendation
Enforce protocol validation at the actual trust boundary — the `open-external` IPC handler in the main process — rejecting (not just logging) any value that does not parse as an `http:`/`https:`/`mailto:` URL via the `URL` constructor, rather than relying on renderer-side `startsWith` checks that can be bypassed or omitted by any current or future caller.

### Proof of Concept
Not independently verified end-to-end due to tool limitations (no runtime/browser access). Conceptually: any code path that calls `dispatcher.openInBrowser(value)`/`shell.openExternal(value)` with a `value` not pre-filtered to `^https?:` (e.g., a future feature reusing `RichText`/`LinkButton` with repository- or API-derived text, or a regex/encoding edge case in `text-token-parser.ts`'s `scanForHyperlink`) will reach the main-process `open-external` handler, which performs no protocol enforcement and unconditionally calls `shell.openExternal(path)`.     const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
