### Title
`open-external` IPC handler forwards any scheme to `shell.openExternal` with no allow-list, unlike the sandboxed-markdown link interceptor - ([File: app/src/main-process/main.ts])

### Summary
The report's bug class is: a security invariant (`MAX_TOTAL_SUPPLY`) is enforced on one entry point (`lock`) but a sibling entry point (`increase`) that reaches the same mutable state skips the check entirely. The same "guarded on one path, unguarded on the sibling path" pattern exists in Desktop's external-link handling: the renderer's markdown viewer (`SandboxedMarkdown.setupLinkInterceptor`) only forwards `https?:` links to the callback, but the main-process IPC endpoint that actually performs the privileged action (`shell.openExternal`) has no such allow-list — it accepts and executes on any string handed to it.

### Finding Description
`SandboxedMarkdown.setupLinkInterceptor` in `app/src/ui/lib/sandboxed-markdown.tsx` intentionally restricts which links can even reach the `onMarkdownLinkClicked` callback: [1](#0-0) 
only `a.protocol` matching `/^https?:/` is forwarded.

However, the actual privileged sink — the main-process handler invoked via `main-process-proxy` → `ipcRenderer.invoke('open-external', ...)` — performs no such validation: [2](#0-1) 
It only *logs* if the string starts with `http://`/`https://`; for anything else it proceeds straight to `shell.openExternal(path)` unconditionally. `shell.openExternal` on Electron/OS will hand off arbitrary URI schemes (e.g. `file:`, custom registered protocol handlers, `mailto:`, platform-specific handler schemes) to the OS shell.

Other call sites reach the same unguarded sink directly without the markdown filter's `https?` gate:
- `LinkButton.onClick` calls `shell.openExternal(uri)` directly with a caller-supplied `uri` prop [3](#0-2) .
- `release-notes-dialog.tsx`'s `onMarkdownLinkClicked` calls `shell.openExternal(url)` directly [4](#0-3) .

Because the enforcement of "only http/https" lives only in the renderer-side markdown filter (an "increase()"-style sibling path that skips the check) rather than in the trusted main-process sink (the "lock()"-style path that should own the invariant), any code path that constructs a URL from attacker-controlled data (a PR/issue/comment body, a repo's release notes, or any future `dispatcher.openInBrowser` caller) and calls `openExternal`/`open-external` without itself re-validating the scheme will pass whatever string reaches it straight to the OS shell-open API.

### Impact Explanation
`shell.openExternal` with a non-`http(s)` URI can hand off to OS-level protocol handlers. On Windows, `shell.openExternal` with crafted URIs has historically been usable to execute arbitrary commands/files if any registered handler (including ones from other installed software) treats its input unsafely, and at minimum allows launching local files/protocol handlers registered on the victim's machine that the attacker fully controls the payload of (e.g. `file://` paths pointing at attacker-supplied content baked into the cloned repo, or `mailto:`/custom scheme injection). This matches the report's "attacker controls a GitHub API object" input model (PR body, comment, or repo content) leading to unauthorized/unexpected privileged action outside the sandbox — i.e., renderer-sandbox escape into OS-level shell action.

### Likelihood Explanation
Reaching this sink requires only that a value the attacker controls (PR/issue comment body, repo release notes, etc., rendered via `SandboxedMarkdown`, `LinkButton`, or other markdown consumers) end up passed to `shell.openExternal`/`open-external`. The `sandboxed-markdown.tsx` filter's `https?` check gives a false sense that the risk is mitigated, but it is enforced in only one of several code paths reaching the actual privileged sink, and the sink itself performs no validation — so any caller that doesn't re-implement the same filter (as `LinkButton` and `release-notes-dialog.tsx` do not) is exposed.

### Recommendation
Move the scheme allow-list enforcement into the trusted boundary: validate/reject the URL scheme inside the `ipcMain.handle('open-external', ...)` handler in `app/src/main-process/main.ts` (and/or centrally inside `shell.openExternal` in `app-shell.ts`) rather than relying on renderer-side callers to pre-filter. Reject anything that isn't `http:`/`https:` (and `mailto:` if intentionally supported) before calling `electronShell.openExternal`.

### Proof of Concept
1. Add a comment/PR body containing a link with a non-http scheme, e.g. `[click me](file:///C:/some/attacker/dropped/file.exe)` or a custom-scheme URI registered by other software on the victim's machine, on a repository the victim has open in Desktop.
2. Note that `SandboxedMarkdown.setupLinkInterceptor` will *not* forward this link (protocol check fails) — but this is only enforced in that one component.
3. Any path that instead uses `LinkButton` with an attacker-influenced `uri` prop, or any future markdown consumer that omits the `https?` filter, calls `shell.openExternal(uri)` / IPC `open-external` directly.
4. Confirm in `app/src/main-process/main.ts` lines 581-597 that the handler performs no scheme validation and unconditionally calls `shell.openExternal(path)`, demonstrating the invariant ("only http/https may be opened") is not enforced at the trusted boundary, exactly mirroring the `increase()` vs `lock()` gap in the source report.

    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
