## Title
Malicious/reverting CW721 token can permanently block a user's asset migration in the `solo` precompile's `ClaimSpecific` - (File: `precompiles/solo/solo.go`)

### Summary
The `solo` precompile's `ClaimSpecific` function lets a legacy Cosmos account migrate native coins, CW20 balances, and CW721 NFTs to an EVM-associated address in a single atomic call. For CW721 assets, when no specific `token_id` is provided, the precompile automatically enumerates **all** tokens owned by the sender under that contract and transfers them in a `for` loop, aborting the entire `ClaimSpecific` call (and all bundled asset transfers) the moment any single token transfer fails [1](#0-0) . An attacker who can get one non-transferable or reverting NFT into that same collection (e.g. a soulbound token, a token blocked by a royalty/allowlist hook, or simply any CW721 contract logic that reverts for a given token/id) can permanently prevent the victim from ever completing that `ClaimSpecific` call, freezing all bundled assets — native coins, CW20 balances, and any other legitimate NFTs — in the same message.

### Finding Description
`ClaimSpecific` iterates over `claimSpecificMsg.GetIAssets()`, handling native coins, CW20, and CW721 assets in one pass [2](#0-1) . For a CW721 asset entry that does not specify a single `token_id` via `asset.GetDenom()`, the code queries the contract for **every token owned by `sender`** and builds `allTokens`, then transfers each one with `p.wasmKeeper.Execute(..., CW721TransferPayload(...))`: [1](#0-0) 

Crucially, if `wasmKeeper.Execute` returns an error for **any single token** in that loop, the function immediately returns the error, aborting the whole `ClaimSpecific` call:
```go
for _, token := range allTokens {
    _, err := p.wasmKeeper.Execute(ctx, contractAddr, sender, CW721TransferPayload(callerSeiAddr, token), sdk.NewCoins())
    if err != nil {
        return nil, 0, fmt.Errorf("failed to transfer token %s on CW721 contract %s: %w", token, contractAddr.String(), err)
    }
}
```
Because the precompile executor returns a non-nil `err`, the EVM call reverts, rolling back **all** state changes made earlier in the same `ClaimSpecific` invocation — including any native-coin `SendCoins` and CW20 `Execute` transfers for other, unrelated assets bundled in the same `MsgClaimSpecific` message [3](#0-2) .

This means:
1. If a victim's legacy account holds multiple NFTs from the same CW721 contract, and even one of them cannot be transferred (e.g. a soulbound/locked token, or a token an attacker deliberately sent that the contract refuses to transfer under certain conditions), the entire NFT batch — including otherwise-transferable NFTs — becomes permanently stuck, since the enumeration always re-includes the poisoned token on every retry.
2. If the same `ClaimSpecific` message additionally bundles native coin or CW20 asset entries alongside the poisoned CW721 asset, those legitimate assets are also blocked from ever being migrated in that call, since the atomic EVM revert undoes everything.

This is the same failure class as the OpenQ report: an "unfiltered" or automatically-enumerated set of token transfers in one atomic operation, where a single adversarial/uncooperative token forces a revert that blocks withdrawal/claim of unrelated legitimate assets bundled in the same operation.

### Impact Explanation
A victim's legacy Sei account funds (native coins, CW20 tokens, and other legitimate NFTs) can be rendered permanently unclaimable/unmigratable via the `solo` precompile if the account holds even one CW721 token that cannot be transferred out (whether due to legitimate contract logic like soulbound tokens, or an attacker engineering such a token into the victim's holdings). This is a fund-freezing griefing vector reachable by any user who can get a non-transferable token associated with the victim's legacy account, satisfying the "permanent freezing" impact bar.

### Likelihood Explanation
Exploitability depends on the victim owning/being sent a token that reverts on `transfer_nft`. Many CW721 implementations support soulbound-style restrictions, royalty enforcement hooks, or allowlist-gated transfers that can revert under attacker-controlled conditions (e.g. sending a token to an address not on an allowlist, or a token flagged non-transferable). Since the enumeration path is automatic (no way for the caller to skip a poisoned token while claiming the rest of that same contract's tokens, other than specifying single `token_id`s one at a time, which the current message structure and UI tooling may not surface), the likelihood of an affected user getting stuck is moderate to high whenever such NFT collections are involved in migration.

### Recommendation
- Do not fail the entire `ClaimSpecific` call when a single asset transfer (especially within the CW721 "transfer all tokens" loop) errors out; instead, skip/continue past failed tokens and report them back to the caller so other legitimate assets in the same batch can still be migrated.
- Alternatively, require/allow per-token `token_id` granularity for CW721 claims by default (rather than always enumerating and batching all owned tokens), so a user can exclude a known-poisoned token and still successfully migrate the rest of their holdings.
- Consider isolating each asset's transfer in its own sub-context that can be rolled back independently on failure, rather than failing the entire outer `ClaimSpecific` transaction.

### Proof of Concept
1. Victim owns several NFTs (`token_1`, `token_2`, `token_3`) under CW721 contract `C`, plus native `usei` and a CW20 balance, all associated with a not-yet-EVM-migrated legacy Sei address.
2. `token_2` is (or becomes) non-transferable — e.g. it is soulbound, or contract `C` has royalty/allowlist logic that reverts `transfer_nft` for that specific token when transferred to the caller's target address.
3. Victim signs and submits a `MsgClaimSpecific` bundling the native coin asset, the CW20 asset, and the CW721 asset for contract `C` (no explicit `token_id`, so all three tokens are auto-enumerated) via the `solo` precompile's `claimSpecific` method.
4. In `ClaimSpecific`, the loop over `allTokens` successfully executes `transfer_nft` for `token_1`, but fails on `token_2` [4](#0-3) , causing the function to return an error.
5. The EVM call reverts entirely: the native coin transfer, CW20 transfer, and the `token_1` NFT transfer that already executed within this call are all rolled back.
6. Every subsequent retry of the same claim re-triggers the identical failure at `token_2`, permanently blocking the victim from migrating any of their bundled assets through this call.
