### Title
Bandwidth allowance is permanently drained on retried failed message deliveries because `try_consume` mutates the FIFO balance before the destination module's `on_accept` can fail - (File: `parachain/runtimes/gargantua/src/ismp.rs`)

### Summary
`ProxyModule::on_accept` calls `BandwidthGate::try_consume` (which mutates `pallet_bandwidth::Allowance` by draining `remaining_bytes` from the app's FIFO subscription list) *before* dispatching to the destination module's own `on_accept`. If the downstream module callback subsequently fails, `pallet-ismp`'s request handler deletes the stored request receipt specifically so the message "can be timed out" (in practice: can be resubmitted). Because the bandwidth deduction already happened and is not reverted on that failure, and because the deleted receipt allows the exact same request to be resubmitted and reprocessed, an attacker can trigger unlimited re-consumption of the same app's bandwidth balance for a message that is never actually delivered - draining bandwidth the app paid real BRIDGE for, with no corresponding service rendered and no refund path. This mirrors the `MinipoolManager.recordStakingError` bug class: a state counter/balance is mutated on a path whose surrounding operation is treated as "didn't really happen" (and is therefore left retryable), producing an accounting invariant break that benefits an attacker at the paying party's expense.

### Finding Description
`BandwidthGate::try_consume` (`modules/pallets/bandwidth/src/lib.rs`, `impl BandwidthGate for Pallet<T>`) atomically drains bytes from the `Allowance` FIFO for `(source, app)`: [1](#0-0) 

This is invoked from `ProxyModule::on_accept` *before* the request is dispatched to the actual destination module callback: [2](#0-1) 

The ISMP request handler (`modules/ismp/core/src/handlers/request.rs`) calls this `on_accept`, and on any error it deliberately deletes the just-stored request receipt so the request remains retryable/timeout-able: [3](#0-2) 

The developers explicitly designed the gate to make **no mutation** when a message would be rejected for insufficient balance (`GateError::Insufficient` documented as no-mutation, load-bearing for safe top-up races): [4](#0-3) 

But this "no mutation on failure" property only covers the gate's own rejection path. It does **not** extend to the case where `try_consume` succeeds (bytes are deducted, subscriptions popped/evicted) and the *subsequent* destination-module `on_accept` call fails for its own reasons (malformed body, unregistered contract, decoding errors, etc., e.g. as seen in `pallet_hyper_fungible_token`'s callback error paths). In that scenario:
1. Bandwidth is deducted from the `(source, app)` FIFO — a real, non-reverted storage mutation.
2. The overall `on_accept` returns `Err`.
3. `host.delete_request_receipt` removes the just-written receipt (per the explicit comment: "Delete receipt if module callback failed so it can be timed out").
4. Because the receipt is gone, the identical `PostRequestMessage` can be resubmitted by anyone with a valid membership proof (submission of proofs is permissionless) and will re-enter the same code path, calling `try_consume` again and deducting the same bytes a second time — and so on, indefinitely, as long as the destination module deterministically fails on that malformed/unsupported request.

### Impact Explanation
This breaks the core Hyperbridge bandwidth invariant that a `(source, app)` bandwidth allowance should move exactly once per unit of service consumed. Here, an app's prepaid bandwidth (real BRIDGE spent via `BandwidthManager.purchase()`) can be drained to zero by a party who never has to successfully deliver anything — each failed-and-retried delivery burns real balance with no corresponding message ever landing at the app. This is a direct "fund loss" / logic-attack impact matching the bounty's accepted categories: bridged/prepaid balances move to nobody's benefit (burned) instead of exactly once to the rightful beneficiary (the app that should receive the message, or nobody if legitimately rejected).

### Likelihood Explanation
This requires only:
- An app that has purchased bandwidth (any subscriber on the allowlist is unaffected, but any paying app is exposed).
- A message to that app's `(source, app)` key that deterministically fails the destination module's `on_accept` after the gate consumes bytes (e.g., malformed body causing a decode error in the target pallet/contract's callback, or an unregistered/misconfigured destination inside a legitimate-looking request).
- Ability to resubmit the same `PostRequestMessage` with a fresh/valid membership proof — this is explicitly permissionless per the handler design (any relayer, in fact any caller, can submit `handlePostRequests`).

No malicious relayer, prover, or governance actor is needed — an ordinary user can craft one intentionally-malformed message and resubmit it repeatedly to drain a victim app's paid-for bandwidth.

### Recommendation
Make bandwidth consumption atomic with the destination module's success: either (a) call `try_consume` only after the destination module's `on_accept` succeeds, or (b) if bandwidth must be checked/reserved up front, refund/restore the consumed bytes when the downstream callback errors and the receipt is deleted (mirroring the "no mutation on failure" property already implemented for `GateError::Insufficient`). Additionally, consider whether deleting the request receipt on a *deterministic* module failure (as opposed to a timeout-based failure) is the right retry semantics at all, since it currently allows unlimited free retries of a message that will never succeed.

### Proof of Concept
1. App `A` purchases bandwidth via `BandwidthManager.purchase()`, crediting `(source, A)` with N bytes in `pallet_bandwidth::Allowance`.
2. Attacker crafts a `PostRequest` addressed to a module that will deterministically fail `on_accept` for a specific payload (e.g., a body that fails ABI decoding in the target pallet, guaranteeing an `Err` from `on_accept` while still being large enough to be costly in bytes) and directs `request.to`/`request.from` such that `try_consume` charges against `(source, A)`.
3. Attacker submits the message via the permissionless `handlePostRequests`/ISMP request handler with a valid membership proof.
   - `ProxyModule::on_accept` runs `try_consume`, deducting `bytes` from `A`'s FIFO subscription list (`modules/pallets/bandwidth/src/lib.rs:509-555`).
   - The destination module's `on_accept` then fails, causing `handlers/request.rs` to call `host.delete_request_receipt` (`modules/ismp/core/src/handlers/request.rs:122-125`), deleting the receipt that would otherwise mark this request as processed.
4. Because the receipt is gone, the attacker resubmits the exact same request with the same (or freshly re-derived) proof; `try_consume` fires again, deducting the same bytes a second time from `A`'s allowance.
5. Repeating step 4 drains `A`'s entire purchased bandwidth allowance to zero without a single successful message ever being delivered to `A`, and with no event or refund indicating the loss (unlike `SubscriptionEvicted`, there is no accounting event for this drain). [1](#0-0) [5](#0-4) [3](#0-2)

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
