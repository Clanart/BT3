### Title
`ThresholdKeys`/`ThresholdView` `Debug` impls leak secret scalar and offset tweak values - (File: crypto/dkg/src/lib.rs)

### Summary
The external report (GHSA-q683-8468-r6h6, CWE-532) concerns a component serializing a full sensitive object into INFO-level log context, leaking secrets to any log reader. The analog in Serai: `ThresholdKeys` and `ThresholdView` implement `fmt::Debug` in a way that prints the secret `scalar` and `offset` fields — the ephemeral re-keying/tweak scalars applied via `ThresholdKeys::scale()` and `ThresholdKeys::offset()`. Any log statement, error message, or panic formatting that includes these structures writes the secret tweak material in clear text.

### Finding Description
`ThresholdKeys` derives `Debug` (`crypto/dkg/src/lib.rs:291`). The derived implementation prints every field: `core` is protected because `ThresholdCore` has a hand-written `Debug` that deliberately ends with `finish_non_exhaustive()` to hide `secret_share` (`crypto/dkg/src/lib.rs:266-275`), but `scalar` and `offset` — plain `C::F` field elements — are printed verbatim.

`ThresholdView` has a manual `Debug` impl (`crypto/dkg/src/lib.rs:316-329`) that likewise excludes `secret_share` via `finish_non_exhaustive()`, yet explicitly emits `.field("scalar", &self.scalar)` and `.field("offset", &self.offset)`.

The doc comments on `scale()` and `offset()` state the scalar/offset are "ephemeral and will not be included when these keys are serialized" (`crypto/dkg/src/lib.rs:393-417`) — i.e., they are treated as secret material that must not be persisted or transmitted, exactly like the HTTP headers in the report. `scalar` is not publicly recoverable: `group_key()` returns `core.group_key * scalar + G * offset` (`crypto/dkg/src/lib.rs:446`), so recovering `scalar` requires solving a discrete log. It is secret by construction, used for account/privacy derivation schemes (e.g., bitcoin-serai's per-input re-keying / offset registration patterns). The `offset` value is similarly secret: it is injected into the lowest-indexed participant's share and verification share at `crypto/dkg/src/lib.rs:518-521`, not published as a scalar.

Because the privacy/accountability of tweaked outputs depends on `scalar`/`offset` remaining known only to the holder, writing them to a log stream — precisely the "sensitive value reaches log context via a too-verbose formatter" bug class — leaks them to anyone with log access.

### Impact Explanation
A scalar leaked via `{:?}` formatting of a `ThresholdKeys` or `ThresholdView` exposes the secret tweak linking the base `ThresholdCore` to the tweaked `group_key`. For schemes where `scalar`/`offset` derive other secrets or bind funds to intended outputs (the documented purpose is "various account and privacy schemes", and bitcoin-serai registers per-input offsets), a log reader obtains material the serialization layer explicitly refuses to emit. This is the same impact shape as the advisory: log consumers get broader access than application consumers, and the leaked values are secret-by-design but absent from the public transcript.

### Likelihood Explanation
These types are the central key-carrying structures of the DKG/FROST stack; printing them in `unwrap`/`expect`/`thiserror` contexts, tracing spans, or debug logs is a realistic usage — `Participant`, `DkgError`, and machine types all derive `Debug` to support exactly this. Unlike the upstream bug, no attacker-sent bytes are required; the leak occurs whenever a node's own secret-bearing struct is formatted. Reachability and preconditions: requires only that application code log/debug-format a tweaked `ThresholdKeys`/`ThresholdView` — no malicious validator or peer is involved.

### Recommendation
Do not emit `scalar`/`offset` in `Debug` output. Remove `Debug` from the `derive` on `ThresholdKeys` (or hand-implement it like `ThresholdCore`, printing `core` and finishing non-exhaustive), and drop the `.field("scalar", ...)` / `.field("offset", ...)` lines from `ThresholdView`'s `Debug` impl. Audit other secret-bearing types (`BlameMachine`, `SecretShareMachine`, etc.) — these already use `finish_non_exhaustive()` correctly and should be the model.

### Proof of Concept
```rust
// crypto/dkg tests context; any Ciphersuite C
let keys = ThresholdKeys::<C>::new(params, Interpolation::Lagrange, secret_share, shares)?;
let tweaked = keys.offset(secret_offset).scale(secret_scalar).unwrap();
// Any of the following writes secret_scalar / secret_offset to output:
let s = format!("{tweaked:?}");            // derived Debug prints `scalar:`/`offset:` fields
let view = tweaked.view(included).unwrap();
let s2 = format!("{view:?}");              // explicit .field("scalar")/.field("offset")
```
