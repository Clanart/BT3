### Title
Fail-closed owner-record gate permanently DoSes lazy self-initialization for pre-existing object-hosted modules — (File: `aptos-move/framework/aptos-framework/sources/init.move`)

### Summary
The lazy module initialization feature adds new per-module state (`ModuleState.deploy_owner`) that is only populated by `code::publish_package` at the moment a package is published/upgraded to an object address while `features::is_lazy_module_initialization_enabled()` is true. Any object-hosted module that was published (or last upgraded) *before* the feature flag was turned on will never have a recorded `deploy_owner`. When such a module later calls the compiler-inserted `internal_maybe_initialize`, `assert_may_self_initialize` treats an object address with no recorded owner as fail-closed, permanently aborting self-initialization even though the object was never transferred — an exact analog of the reported bug class (new storage fields default to an "empty" value that is not properly initialized for pre-existing on-chain data, causing legitimate operations to always revert).

### Finding Description
`ModuleState { only_once, deploy_owner }` is recorded per module only inside `code::publish_package`, gated on both the feature flag and `object::is_object(addr)`: [1](#0-0) 

The gating logic in `init.move` explicitly fails closed when there is no recorded owner for an object address: [2](#0-1) 

`recorded_deploy_owner` returns `option::none()` both when `InitializationState` doesn't exist at all and when the module simply was never recorded — the two cases (never-recorded vs. genuinely-transferred-but-unrecorded) are indistinguishable: [3](#0-2) 

Because `check_and_set_initialized` flips `only_once` before the owner check runs, and a Move abort rolls back all state changes for the transaction, the failure is not transient — every subsequent call to `internal_maybe_initialize` for that module will hit the same fail-closed branch and abort again: [4](#0-3) [5](#0-4) 

This mirrors the external report precisely: three new configuration fields defaulted to zero for pre-existing entities caused `getPSlippage()` to revert on valid input; here, a new `deploy_owner: Option<address>` field defaults to `none` for pre-existing object-hosted modules and causes `assert_may_self_initialize` to abort on a valid (never-transferred) object.

### Impact Explanation
Any dApp that deploys modules to objects (a widely used deployment pattern via `object_code_deployment::publish`/`upgrade`) and adopts lazy self-initialization will be permanently unable to run its module initializer if the module was published/upgraded prior to the feature being enabled by governance, or if `object_code_deployment::publish`/`upgrade` is otherwise invoked without the feature flag active at that time. Since module initialization commonly gates the creation of core on-chain resources for that package, this can permanently brick the module's core functionality with no owner-side remediation short of a full republish, which fits the gate's "module-init ... failure that reaches protected state mutation" category. This is a genuine self-inflicted (non-malicious) denial-of-service on protected state initialization rather than an unauthorized-write vulnerability, so I rate it Medium rather than Critical.

### Likelihood Explanation
Medium: this requires (a) the `LAZY_MODULE_INITIALIZATION` feature to be rolled out after some object-hosted packages using it are already live, or (b) a publish/upgrade transaction to occur while the feature is momentarily disabled (e.g., during a feature-flag rollback/rollout window), which is a realistic and plausible sequencing issue for any staged mainnet feature activation, not a contrived edge case.

### Recommendation
Distinguish "never recorded" (new/never-transferred object, feature not active at publish time) from "recorded owner mismatches current owner" (an actual transfer). For the former case, either (a) have `code::publish_package` retroactively backfill `deploy_owner` for object packages on every republish regardless of the feature flag state, or (b) treat "no `InitializationState` entry ever created for this address" (i.e., no republish has occurred since the feature became relevant) as fail-open when the object's ownership history cannot possibly have diverged, and only fail-closed when a Move-level per-object "root owner at first `move_to`" invariant is explicitly established at object creation time rather than deferred to publish time.

### Proof of Concept
1. Deploy an object-hosted package with `object_code_deployment::publish` while `LAZY_MODULE_INITIALIZATION` is disabled (any module compiled to call `internal_maybe_initialize` in its init logic).
2. Governance enables `LAZY_MODULE_INITIALIZATION` (`aptos_features.rs` flag flip) without anyone republishing the package, so `code::publish_package`'s owner-recording branch in `aptos-move/framework/aptos-framework/sources/code.move:182-187` never ran for this object.
3. A user calls any entry function that triggers the module's lazy `internal_maybe_initialize(only_once)`.
4. `check_and_set_initialized` marks `only_once = Some(false)` (rolled back on abort), then `assert_may_self_initialize` finds `recorded_deploy_owner` = `none` for an `object::is_object(addr) == true` address and aborts with `EOWNER_CHANGED_SINCE_DEPLOY`, even though the object was never transferred — every future call to this init path aborts identically.

Note: I could not fully confirm from the indexed code whether `LAZY_MODULE_INITIALIZATION` is currently live on mainnet or still gated as an internal/experimental feature (only partial references were found in `types/src/on_chain_config/aptos_features.rs` and `aptos_release_builder/src/components/feature_flags.rs`); if it is still pre-mainnet/experimental this would lower real-world likelihood — starting a full Devin session with repository access would let this be verified precisely.

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);
        let ok = if (recorded.is_some()) {
            object::is_object(addr)
                && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
        } else {
            !object::is_object(addr)
        };
        assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
    }

    /// The object root owner recorded for `module_id` at its last publish, or `none` if the module
    /// has no such record (an account module, or an object module never recorded).
    fun recorded_deploy_owner(addr: address, module_id: ModuleId): Option<address> {
        if (!exists<InitializationState>(addr)) return option::none();
        let modules = &InitializationState[addr].modules;
        if (modules.contains(&module_id)) modules.borrow(&module_id).deploy_owner else option::none()
    }

    /// `only_once`: if true the entry survives upgrades (initializer never re-runs); if false an

    fun check_and_set_initialized(addr: address, module_id: ModuleId, only_once: bool): bool {
        ensure_module_state(addr, module_id);
        let state = InitializationState[addr].modules.borrow_mut(&module_id);
        if (state.only_once.is_some()) {
