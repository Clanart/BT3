### Title
Unbounded blocking broadcast in shared filter/subscription event loop enables single unprivileged RPC subscriber to hang all filters and subscriptions node-wide - (File: node/cn/filters/filter_system.go)

### Summary
`EventSystem.eventLoop` is a single, shared goroutine that serializes delivery of new pending transactions, logs, removed logs, and chain-head events to every registered filter/subscription on the node via unbuffered per-subscription channels. A single unprivileged, public-RPC subscriber (e.g. a websocket client subscribing to pending transactions or logs) that stops reading its channel can make the shared broadcast loop block indefinitely, stalling delivery to *all other* filters and subscriptions — a network-reachable hang/DoS analogous to the CVE-2020-2925 "hang or frequently repeatable crash" class.

### Finding Description
`EventSystem.broadcast` performs synchronous, unbuffered sends to each subscription's channel from the single `eventLoop` goroutine: [1](#0-0) 

Each subscription's `txs`, `logs`, and `headers` channels are created unbuffered: [2](#0-1) 

`eventLoop` calls `es.broadcast(index, ev)` directly in its main `select` loop for every incoming event: [3](#0-2) 

Because `broadcast` iterates over *every* filter of the matching type and performs a blocking channel send (`f.txs <- e.Txs`, `f.logs <- matchedLogs`, `f.headers <- e.Block.Header()`) for each one, a single slow or unresponsive consumer stalls the loop before it can reach the next filter, and — critically — before the loop can process the *next* incoming event of any kind (new pending tx, new log, new block header) for *any other subscriber*. The project's own test explicitly documents and guards against this exact deadlock/hang scenario: [4](#0-3) 

For subscription-consuming goroutines that forward events to a live network connection (websocket `eth_subscribe`/`kaia_subscribe` pending-tx or logs subscriptions), delivery ultimately depends on writing to the underlying TCP socket. The websocket write path has no default timeout: [5](#0-4) 

If an unprivileged client opens such a subscription and then simply stops reading from the socket (fills the TCP receive window without disconnecting), the server-side write into that connection blocks. That block propagates back through the subscription's forwarding goroutine failing to drain its `txs`/`logs`/`headers` channel, which in turn blocks `EventSystem.broadcast`'s send to that channel, which blocks the single shared `eventLoop` for the entire node — halting event delivery to every other legitimate filter/subscription client until the stalled connection is forcibly closed (or forever if no deadline is configured).

### Impact Explanation
This allows any unprivileged, unauthenticated public-RPC/websocket caller to cause a denial-of-service hang of the node's entire filter/subscription notification subsystem (pending-tx filters, log filters, new-block-header subscriptions) affecting all other users of that RPC endpoint, without requiring any special privilege, staking, or authorization — directly analogous to the CVE-2020-2925 "network-reachable hang / repeatable crash causing complete DOS of availability" bug class, scoped to the RPC-serving component rather than validator/consensus logic.

### Likelihood Explanation
The precondition is minimal: any client able to open a websocket (or IPC) connection and call a subscription method (`eth_subscribe`/`kaia_subscribe` for pending transactions, logs, or new heads) and then stop reading responses. No authentication or elevated privilege is required for public RPC endpoints, and `WebsocketWriteDeadline`/`WebsocketReadDeadline` default to `0` (no timeout) unless explicitly configured by the node operator, making the condition trivially reproducible by a slow/unresponsive TCP peer.

### Recommendation
Decouple event delivery from the shared `eventLoop`: use buffered channels with drop/backpressure policy per subscription, enforce write deadlines by default on websocket connections, and/or dispatch `broadcast` sends to each filter via a bounded-time `select` with a `default`/timeout branch (dropping or disconnecting slow subscribers) so a single unresponsive client cannot stall delivery to unrelated subscribers.

### Proof of Concept
1. Start a Kaia node with the websocket RPC endpoint enabled and default `WebsocketWriteDeadline=0`.
2. Client A opens `eth_subscribe("newPendingTransactions")` (or `kaia_subscribe`) over websocket, then stops reading from the socket (e.g., pause the client without closing the TCP connection) while keeping the connection open and not exceeding OS-level TCP buffer limits, so the server never observes a read/write error.
3. Client B (any other user) submits transactions or opens its own log/pending-tx filter/subscription.
4. Once the TCP send buffer for Client A's connection fills, the websocket write blocks; because the subscription goroutine can't drain the channel, `EventSystem.broadcast`'s send in the shared `eventLoop` (`node/cn/filters/filter_system.go`) blocks, and Client B (and all other filters/subscriptions on the node) stop receiving any events — reproducing the "hang" condition the project's own `TestPendingTxFilterDeadlock` test guards against for the polling filter path, but demonstrating the unmitigated case for the live-connection subscription/broadcast path.

// broadcast event to filters that match criteria.
func (es *EventSystem) broadcast(filters filterIndex, ev interface{}) {
	if ev == nil {
		return
	}

	switch e := ev.(type) {
	case []*types.Log:
		if len(e) > 0 {
			for _, f := range filters[LogsSubscription] {
				if matchedLogs := filterLogs(e, f.logsCrit.FromBlock, f.logsCrit.ToBlock, f.logsCrit.Addresses, f.logsCrit.Topics); len(matchedLogs) > 0 {
					f.logs <- matchedLogs
				}
			}
		}
	case blockchain.RemovedLogsEvent:
		for _, f := range filters[LogsSubscription] {
			if matchedLogs := filterLogs(e.Logs, f.logsCrit.FromBlock, f.logsCrit.ToBlock, f.logsCrit.Addresses, f.logsCrit.Topics); len(matchedLogs) > 0 {
				f.logs <- matchedLogs
			}
		}
	case blockchain.NewTxsEvent:
		for _, f := range filters[PendingTransactionsSubscription] {
			f.txs <- e.Txs
		}
	case blockchain.ChainEvent:
		for _, f := range filters[BlocksSubscription] {
			f.headers <- e.Block.Header()
		}
	}
}
