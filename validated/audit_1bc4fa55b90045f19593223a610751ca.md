The Tron deployment of `IntentGatewayV2.sol` never received the fee-on-transfer fix that was applied to the main EVM contract, leaving it vulnerable to the exact accounting break described in the report.

### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with nominal (pre-fee) amounts instead of actual tokens received, allowing fee-on-transfer tokens to drain other users' escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The main EVM `IntentGatewayV2.sol` was hardened against fee-on-transfer tokens: `placeOrder` snapshots the gateway's balance before and after each `safeTransferFrom`, and mutates `order.inputs[i].amount` to the *actual* amount received before computing the commitment and crediting escrow [1](#0-0) . This fix is proven by the dedicated Foundry fee-on-transfer test suite [2](#0-1) .

The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still uses the old, unpatched logic: it calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits the escrow ledger with `reducedInputs[i].amount`, which is derived purely from the user-supplied nominal `order.inputs[i].amount` minus the protocol fee — never from the gateway's actual measured balance change [3](#0-2) . The predispatch code path has the same flaw: it emits a `dust` event for the "sweep" transfer but still credits escrow using `reducedInputs[i].amount` (nominal minus protocol fee), not the amount actually collected from the dispatcher after transfer fees [4](#0-3) .

### Finding Description
`IntentGatewayV2` is a shared, multi-order, multi-token escrow contract — not a per-token vault, but the same "credit an internal ledger, then blindly pay out from a pooled token balance" pattern applies. Because Tron's `placeOrder` never checks `IERC20(token).balanceOf(address(this))` before/after the transfer, if `token` charges a transfer fee (as USDT does on some chains, and as explicitly warned about in the bug report), `_orders[commitment][token]` is credited for more than the contract actually received.

When `withdraw()` is later invoked (via `fillOrder` or `cancelOrder`), it only checks that the internal ledger entry is non-zero and then transfers `amount` to the beneficiary, decrementing the ledger accordingly — it never checks that the gateway's actual on-chain token balance is sufficient for that specific commitment [5](#0-4) . Since the gateway pools escrowed balances from many different orders/users for the same token, the shortfall created by one fee-on-transfer deposit is silently paid out of other users' deposited principal. Early withdrawers for that token are made whole using funds that belong to later depositors, and the last order(s) needing withdrawal of that token will revert with an ERC20 transfer failure (`InvalidInput`/`TransferFailed`) because the pooled balance has been exhausted — a permanent loss/lock of the last beneficiary's funds and unauthorized transfer of other users' escrowed principal.

### Impact Explanation
This is a direct loss-of-funds / fund-lock bug reachable by any unprivileged user simply placing an order with a fee-charging ERC20 as input — no relayer, prover, or admin compromise required. The internal escrow accounting silently diverges from the real token balance held by the contract, and later legitimate withdrawals for other orders using the same token can be starved or drained, matching the "stealing or loss of funds" and "logic attack" impact categories.

### Likelihood Explanation
Likelihood is moderate to high in any deployment where the Tron gateway accepts an arbitrary or governance-added token list. This is not a theoretical concern — it is the same exact scenario the original bug report and Hyperbridge's own test suite (`testPlaceOrder_FeeOnTransferToken_*`) already validate against on the main EVM contract, proving the team is aware of and actively guarding against this exact class of token. The Tron contract is a byte-for-byte-adjacent fork that simply missed the fix, so any fee-on-transfer token (or a token later upgraded/re-configured to charge fees, as explicitly warned about in the original report) immediately triggers the issue.

### Recommendation
Apply the same balance-snapshot pattern used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`/sweep in `placeOrder`, mutate `order.inputs[i].amount` to the actual delta, and only then compute `reducedInputs`, the commitment, and the escrow credit. Additionally, `withdraw()` should never assume the internal ledger accurately reflects available token balance — consider validating against `IERC20(token).balanceOf(address(this))` or otherwise ensuring the ledger can never be created out of sync with real balances.

### Proof of Concept
1. Governance/owner permits a token that later starts charging (or is a token that already charges) a 1% transfer fee — e.g., the `FeeOnTransferToken` used in the EVM test suite [6](#0-5) .
2. Attacker (or any user) calls Tron `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`. `safeTransferFrom` moves only 990e18 into the gateway (1% fee burned), but `_orders[commitment][FOT] += reducedInputs[0].amount` credits ~1000e18 (minus only the protocol fee, not the transfer fee) [7](#0-6) .
3. A second, unrelated user places a normal order depositing 1000e18 of the same FOT token, similarly under-crediting the pool by the transfer-fee delta.
4. Both orders are filled/cancelled and `withdraw()` is called for each commitment; the first beneficiary's payout succeeds by consuming FOT balance that actually belongs to the second depositor's escrow, since `withdraw()` never reconciles the commitment-specific credited amount against real available balance [8](#0-7) .
5. The last beneficiary attempting to withdraw FOT for their commitment finds the gateway's actual FOT balance insufficient — their withdrawal reverts, and their principal is permanently stuck/lost, while earlier beneficiaries collectively received more real tokens out of the shared pool than they should have deposited-for.

        assertEq(

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
