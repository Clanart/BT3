### Title
Attacker-controlled submodule path bypasses containment checks when opening a submodule from a diff - (File: `app/src/lib/git/diff.ts`)

### Summary
Desktop has a dedicated `resolveWithin` helper [1](#0-0)  whose explicit purpose is to make sure a path derived from repository data cannot resolve outside of the repository root (guarding against `..`/symlink escapes). However, `buildSubmoduleDiff`, which builds the `fullPath` shown for a submodule change, does not use this guard: it just does `Path.join(repository.path, path)` where `path` is `file.path`, a value that ultimately comes from `git status`/`.gitmodules` data inside the (possibly attacker-supplied) cloned repository.

### Finding Description
`buildSubmoduleDiff` computes the submodule's path directly from attacker-influenced repository data: [2](#0-1) 

This is analogous to the `StakingRewards.recoverERC20` bug: a "sweep"/utility code path (there, arbitrary ERC20 recovery; here, arbitrary "open submodule path") is missing the one guard needed to keep it constrained to a safe scope. Desktop *does* have the equivalent guard available (`resolveWithin`), and uses it elsewhere (e.g. `app/src/lib/copilot-conflict-context.ts`, `app/src/ui/dispatcher/dispatcher.ts`), but it is not applied when constructing `ISubmoduleDiff.fullPath`.

The resulting `fullPath` flows unchanged to the UI: `SubmoduleDiff` exposes an `onOpenSubmodule` callback that is invoked with `this.props.diff.fullPath` [3](#0-2) , and the prop type documents that this value is expected to be a `fullPath: string` that downstream consumers will act on (e.g. opening the folder / opening as a repository) [4](#0-3) .

Because `path` here is derived from `file.path`/submodule status entries — data that is parsed out of `.gitmodules` and `git submodule status` output inside a repository the user cloned or fetched — a malicious repository could declare a submodule with a path that is not itself sanitized (e.g. containing `..` segments), and `Path.join` will happily normalize that into a location outside `repository.path` before the containment check that exists elsewhere in the codebase is ever applied.

### Impact Explanation
If the resulting `fullPath` is used later to open a folder in the file manager or open it as a Desktop repository, a malicious `.gitmodules` entry could cause Desktop to point file-system operations (open/reveal) at a path outside of the cloned repository, e.g. sensitive user directories, since there is no `resolveWithin`-style containment check on this specific path construction (unlike `app/src/lib/path.ts`'s intended use pattern). This matches the "attacker controls a cloned/fetched repository ... result is file read/access outside the repo" impact class.

### Likelihood Explanation
Likelihood is moderate-to-uncertain: this requires the user to open the "Changes" view for a submodule change and click through to "open submodule," so it needs a user gesture, and I was not able to fully trace the final consumer of `onOpenSubmodule` all the way down to the exact `shell`/`spawn` call within the indexed portion of the codebase (the search tools did not surface an `_openSubmodule`-style dispatcher action or an app-store implementation), so I cannot confirm with certainty what OS-level operation is finally performed with `fullPath`, nor whether a downstream check re-validates the path before use.

### Recommendation
Route the submodule `path` through `resolveWithin(repository.path, [path])` (already implemented in `app/src/lib/path.ts`) when constructing `fullPath` in `buildSubmoduleDiff`, and reject/sanitize the diff if the resolved path is `null` (i.e., outside the repository root) instead of trusting `Path.join` directly on attacker-controlled submodule path data.

### Proof of Concept
1. Craft a malicious repository whose `.gitmodules`/submodule status advertises a submodule with a path such as `../../../../Users/victim/Desktop` (or a path that traverses out via `..` segments) is present in `file.path` when a change is detected for that entry.
2. Victim clones/fetches this repository and opens the Changes view; `getWorkingDirectoryDiff`/`buildDiff` calls `buildSubmoduleDiff` [5](#0-4) , which computes `fullPath = Path.join(repository.path, path)` without any `resolveWithin` containment check [6](#0-5) .
3. The victim clicks "open submodule" in the UI, invoking `onOpenSubmodule(this.props.diff.fullPath)` [3](#0-2)  with the escaped path.

Note: I was unable to fully verify the final sink (the exact dispatcher/app-store function that consumes `onOpenSubmodule`) within the indexed code — this is a known limitation of the local search coverage, and confirming the complete exploit chain would require inspecting the full `Dispatcher`/`AppStore` implementation, which a Devin session with full repository access could trace precisely.

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```

```typescript
async function buildSubmoduleDiff(
  buffer: Buffer,
  repository: Repository,
  file: FileChange,
  status: SubmoduleStatus
): Promise<IDiff> {
  const path = file.path
  const fullPath = Path.join(repository.path, path)
  const url = await getConfigValue(repository, `submodule.${path}.url`, true)

  let oldSHA = null
  let newSHA = null

  if (
    status.commitChanged ||
    file.status.kind === AppFileStatusKind.New ||
    file.status.kind === AppFileStatusKind.Deleted
  ) {
    const diff = buffer.toString('utf-8')
    const lines = diff.split('\n')
    const baseRegex = 'Subproject commit ([^-]+)(-dirty)?$'
    const oldSHARegex = new RegExp('-' + baseRegex)
    const newSHARegex = new RegExp('\\+' + baseRegex)
    const lineMatch = (regex: RegExp) =>
      lines
        .flatMap(line => {
          const match = line.match(regex)
          return match ? match[1] : []
        })
        .at(0) ?? null

    oldSHA = lineMatch(oldSHARegex)
    newSHA = lineMatch(newSHARegex)
  }

  return {
    kind: DiffType.Submodule,
    fullPath,
    path,
    url,
    status,
    oldSHA,
    newSHA,
  }
}
```
