### Title
Naive `---` delimiter splitting in `extract_frontmatter` lets malformed frontmatter silently downgrade `action: block` rules to non-blocking - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` parses hookify rule files with a hand-rolled, non-schema-validating splitter (`content.split('---', 2)`) instead of a real YAML parser. A `.claude/hookify.*.local.md` file that visually contains `action: block` can have that field (and its `conditions`/`pattern`) silently excluded from the parsed frontmatter dict if a decoy `---` sequence appears anywhere before the intended closing delimiter, causing `Rule.from_dict` to fall back to the default `action='warn'` (or drop the rule entirely), while the file on disk still reads as a blocking rule.

### Finding Description
`extract_frontmatter` determines the frontmatter/body boundary purely by literal string splitting: [1](#0-0) 

Because this is a blind `str.split('---', 2)` rather than a proper YAML document boundary parser, any extra `---` occurring before the file author's intended closing delimiter (e.g. a markdown horizontal rule accidentally embedded in a multi-line value, a four-dash typo `----`, or a stray `---` inside the message the rule-writer pastes in) truncates `parts[1]` early. Anything after that point — including a trailing `action: block` or `conditions:` block that a human reviewing the raw markdown would still visually associate with the rule — ends up in `message` (`parts[2]`) and is never fed into the key/value parsing loop at lines 106-193.

`Rule.from_dict` then computes: [2](#0-1) 
`action=frontmatter.get('action', 'warn')` silently defaults to `'warn'` when the `action` key was lost to the truncation. If `conditions`/`pattern` are also lost, `RuleEngine._rule_matches` requires at least one condition and returns `False` outright: [3](#0-2) 
meaning the rule never fires at all — a silent complete bypass of an intended block rule.

Nothing in `load_rule_file` or `load_rules` detects or reports this: `load_rule_file` only checks `if not frontmatter` (empty dict) to warn about missing frontmatter; a partially/incorrectly parsed non-empty dict is accepted as valid without any schema or field-completeness check: [4](#0-3) 
And the `PreToolUse` hook is designed to always exit 0 and only prints diagnostics to stderr, which is not surfaced to the operator during normal Claude Code use: [5](#0-4) 

Reachability: `.claude/hookify.*.local.md` files are loaded automatically for every `Bash`/`Edit`/`Write`/`MultiEdit`/`Stop` tool invocation via `load_rules()`/`glob.glob('.claude/hookify.*.local.md')`, with no signature, provenance, or authorship check: [6](#0-5) 
This means any repository content (a file introduced through a PR, a shared/templated `.claude` config, or generated by the `/hookify` command itself while summarizing untrusted conversation/repo text) can carry this crafted malformation, and it will be parsed and enforced (or silently not enforced) the next time any tool executes in that working directory — no shell access beyond normal Claude Code tool use is required.

### Impact Explanation
A project's declared blocking security policy (e.g. "block `rm -rf`", "block edits leaking `.env` secrets") can be silently downgraded to a no-op or a mere warning due to a delimiter-parsing defect, while the on-disk file still visually reads as `action: block`. This breaks the invariant that a deny rule must never be parsed into a non-blocking configuration, allowing dangerous `Bash`/`Edit`/`Stop` operations that the user/organization believed were hard-blocked to execute unblocked — a policy/enforcement bypass with real security impact, matching "Cross-repo, cross-session, or wrong-target mutation" class impact since the same malformed rule file can be reused/templated across many repos and sessions, silently disabling protection everywhere.

### Likelihood Explanation
Feasible and repeatable: the parser is deterministic and the malformation is a simple, easily reproducible pattern (an extra `---`-like sequence before the intended closing delimiter). No special privileges beyond the ability to have a hookify rule file present in the working directory's `.claude/` folder are required — this can happen via a shared/templated config, a PR-introduced file, or content the `/hookify` workflow itself writes based on prior conversation/repo text. The bug is silent (errors only go to stderr, hook always exits 0), so it is unlikely to be noticed by the user until the "blocked" dangerous action actually executes.

### Recommendation
Replace the hand-rolled frontmatter splitter/parser with a real YAML parser (e.g. `yaml.safe_load`) applied only to the text between the first line-anchored `^---$` and the next line-anchored `^---$` (using `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or splitting on lines rather than raw substring occurrences). Additionally, add schema validation in `Rule.from_dict`/`load_rule_file` that rejects (rather than silently defaults) files where `action` is present in the raw text but not recognized, and fails loudly (surfacing to the user, not just stderr) when a rule cannot be fully parsed, rather than falling back to `warn`.

### Proof of Concept
Add a unit test in `plugins/hookify/core/config_loader.py`'s test module:
```python
def test_malformed_delimiter_downgrades_block_rule():
    content = """---
name: block-dangerous-rm
enabled: true
event: bash
pattern: rm\\s+-rf
---
action: block
---

⚠️ This should have been a BLOCK rule
"""
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # The raw file text clearly shows "action: block" intended for this rule,
    # but due to the extra '---' delimiter it lands in `message`, not `frontmatter`.
    assert "action: block" in content
    assert rule.action != 'block'  # FAILS invariant: deny rule parsed as non-blocking ('warn')
```
Expected result: `rule.action` evaluates to `'warn'` (the default) instead of `'block'`, demonstrating that `extract_frontmatter`/`Rule.from_dict` silently produced a non-blocking `Rule` object from a file whose visible content specifies a blocking action — violating the "deny rule must never be parsed into a non-blocking configuration" invariant. A follow-up integration test should pipe a `Bash` `tool_input` matching the `pattern` through `RuleEngine.evaluate_rules([rule], input_data)` and assert that it returns `{}` (allowed) instead of a `permissionDecision: deny` response.
