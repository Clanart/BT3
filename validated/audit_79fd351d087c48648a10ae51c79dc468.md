## Finding [1](#0-0) 

### Title
Unbounded `order.inputs` / escrow-token array lets a user permanently lock their own escrow via out-of-gas `_withdraw` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` only checks `order.inputs.length == 0` — there is no upper bound on the number of `TokenInfo` entries a user can escrow. Every downstream consumer of that array (`_withdraw` in `IntentsBase.sol`, `_execute`'s sweep loop, and the cross-chain `_fillCrossChain` dispatch) iterates over it with a plain `for` loop and no chunking, exactly the unbounded-loop pattern from the Putty `_transferERC20sOut`/`_transferERC721sOut` report.

### Finding Description
`placeOrder` validates only `order.inputs.length == 0`, with no maximum: [2](#0-1) 

The escrowed `order.inputs` array is later replayed, unbounded, inside `_withdraw`, which is the function responsible for releasing (or refunding) every escrowed token to the beneficiary: [3](#0-2) 

For a **cross-chain** order, this same unbounded array becomes the `WithdrawalRequest.tokens` payload of a Hyperbridge `RedeemEscrow` POST request dispatched from the destination back to the source chain after a solver fills the order: [4](#0-3) 

On the source chain, that request is delivered via `IHandlerV2.handlePostRequests`, which decodes and invokes the app's `onAccept` (which calls `_withdraw`) inside the *same transaction* as membership-proof verification and receipt bookkeeping: [5](#0-4) 

Because Solidity `for` loops over dynamic arrays have no protocol-level bound, and `_withdraw`'s per-token work includes an SSTORE-heavy escrow read + write plus an external token transfer per entry, a sufficiently long `order.inputs` array makes the delivering transaction exceed the destination block gas limit deterministically. Every relayer attempting `handlePostRequests` for that commitment fails the same way, since the loop length is fixed by the original order and cannot be reduced after the fact (unlike an unbounded but attacker-choosable proof size, the escrow token count is baked into the commitment/order hash at `placeOrder` time).

### Impact Explanation
This directly reproduces the Putty analog's core invariant break: "loop length is unbounded and gas cost is not future-proofed, so a legitimately created position becomes permanently unexercisable/unwithdrawable." Here:
- A user who places an order with many input tokens (or a solver who fills a cross-chain order with a token list that happens to be long) can never have `RedeemEscrow` succeed once the per-item gas cost multiplied by array length exceeds the destination chain's block gas limit.
- `_withdraw` reverts the whole request, `host.request_receipt` is not marked handled, and the message can be resubmitted indefinitely but will keep reverting the same way — since the loop bound never shrinks.
- The escrowed input tokens sitting in `_orders[commitment][token]` (or the equivalent Tron mapping) become permanently stuck: `EscrowReleased`/`EscrowRefunded` can never fire, `_filled[commitment]` never gets a beneficiary, and there is no owner/admin path to force a release for an over-sized order. This is a genuine "loss/lock of funds" outcome, matching the bounty's accepted-impact class, reachable by an ordinary user through the public `placeOrder`/`fillOrder` entry points with no relayer, prover, or admin involvement required.

### Likelihood Explanation
Likelihood is low-to-moderate, same as the original Putty finding (judge-assessed Medium): it requires either (a) a user self-inflicting this by placing an order with an unusually large token list, or (b) gas-cost drift over the order's lifetime (input tokens can be arbitrary ERC-20s, some with expensive `transfer`/`transferFrom` hooks, e.g. fee-on-transfer or rebasing tokens already explicitly supported by this codebase) pushing a previously-fillable order's redemption loop over the block gas limit. No malicious relayer, prover, or governance action is needed — the attacker primitive is simply "escrow enough distinct tokens."

### Recommendation
Add an explicit maximum on `order.inputs.length` (and `order.output.assets.length`, `order.predispatch.assets.length`) inside `placeOrder`/`_fillSameChain`/`_fillCrossChain`, sized so that the worst-case `_withdraw` loop (using the most gas-expensive supported token behavior) stays comfortably under the gas limit of every supported destination chain. Alternatively, support incremental/partial `_withdraw` calls keyed by a start/end index so a large order's escrow can still be drained token-by-token even if a single call cannot process the whole array.

### Proof of Concept
1. Call `placeOrder` with `order.inputs` containing e.g. 500+ distinct ERC-20 `TokenInfo` entries and a matching `order.output` for a cross-chain destination.
2. Have a solver call `fillOrder`/`_fillCrossChain` on the destination; the resulting `RedeemEscrow` dispatch encodes `WithdrawalRequest.tokens = order.inputs` (500+ entries) as the POST request body: [6](#0-5) 
3. On the source chain, any relayer's `handlePostRequests(host, request)` call must execute `IntentGatewayV2.onAccept` → `_withdraw`, looping 500+ times over `_orders[commitment][token]` SSTORE + external `safeTransfer`: [7](#0-6) 
4. The transaction reverts due to out-of-gas on any chain whose block gas limit is smaller than the loop's total cost; the request receipt is never written, so the same failure recurs on every retry, and the escrowed inputs remain locked in `_orders[commitment]` indefinitely.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

                if (!sent) revert InsufficientNativeToken();

            }
        }
