### Title
Attacker-front-run substitution of an operator's payout tx (stripped OP_RETURN) causes an honest operator's kickoff to be flagged malicious and challenged - (File: core/src/verifier.rs)

### Summary
The payout transaction's operator-identity commitment lives in a plain `OP_RETURN` output that is not covered by any signature — the only signature present on the payout tx (the user's) uses `SinglePlusAnyoneCanPay`, which commits solely to input0 and output0. Because of this, anyone who observes the operator's unconfirmed payout tx in the mempool can extract the signature and rebroadcast a competing double-spend of the same withdrawal UTXO with the identical input0/output0 but a corrupted or missing `OP_RETURN`, causing `payout_payer_operator_xonly_pk` to be stored as `NULL`. When the honest operator later sends its kickoff for that deposit, `Verifier::is_kickoff_malicious` reads `operator_xonly_pk_opt = None` and unconditionally treats it as malicious, causing every verifier to queue a `Challenge` against the operator.

### Finding Description
The broken binding is: **the operator identity recorded in `withdrawals.payout_payer_operator_xonly_pk` for a given `move_to_vault_txid` should equal the operator who actually funded that withdrawal**. In reality, this binding is derived from unauthenticated bytes in an output of whichever transaction happens to be mined spending the specific withdrawal outpoint.

- `create_payout_txhandler` builds the payout tx with: output0 = user payout (covered by the user's `SinglePlusAnyoneCanPay` signature), output1 = anchor, output2 = OP_RETURN with the operator's x-only pubkey [1](#0-0) . The OP_RETURN output is not committed by the user's signature (`SinglePlusAnyoneCanPay` only binds input0+output0) and is not signed by the operator at all.
- The operator funds/broadcasts this tx via `Operator::withdraw`, verifying only the user's signature over input0 [2](#0-1) ; the additional structure (fee inputs, anchor, OP_RETURN) is added locally and is visible to anyone once broadcast to the network, before confirmation.
- `Database::get_payout_txs_for_withdrawal_utxos` records **whichever transaction actually spends** `withdrawal_utxo_txid`/`vout` in a finalized block as the "payout_txid" for that withdrawal index, with no check that it matches the operator's originally intended transaction [3](#0-2) .
- `Verifier::update_finalized_payouts` then parses the OP_RETURN of that mined transaction to derive `operator_xonly_pk`; if the OP_RETURN is missing/invalid, `operator_xonly_pk` is set to `None` and persisted as `NULL` [4](#0-3) .
- `Verifier::is_kickoff_malicious` treats `operator_xonly_pk_opt == None` as an unconditional "assume malicious" signal [5](#0-4) , and `Verifier::handle_kickoff` queues a `Challenge` tx against the operator's kickoff whenever this holds and the round hasn't already been challenged [6](#0-5) .
- Once challenged, the operator side's `send_asserts` flow hard-fails if `payout_op_xonly_pk_opt` is `None` (it cannot construct a valid disprove-defeating assert proof), because it requires the DB-recorded payout operator pubkey to exist and match the kickoff operator [7](#0-6) .

Exploit flow: attacker monitors the mempool, sees operator O's broadcast (unconfirmed) payout tx spending the withdrawal UTXO, extracts the input0 outpoint/witness (user's `SinglePlusAnyoneCanPay` signature) and output0, constructs a new transaction with the same input0/output0 but different auxiliary outputs (added fee input(s) of their own, no OP_RETURN or a corrupted one), and races it into a block ahead of/against O's original broadcast. Because it is a valid double-spend of the exact UTXO with a signature that remains valid (the sighash flag explicitly allows this), it can be mined instead of O's version. `update_finalized_payouts` then records `payout_payer_operator_xonly_pk = NULL` for that withdrawal/deposit. O, having genuinely funded the payout in good faith, later sends its normal `kickoff_tx` for the same deposit; verifiers read `None` from the DB and issue a Challenge, and O cannot subsequently produce a valid assert proof (since the DB lacks the operator attribution needed by `send_asserts`), so it cannot escape Disprove — its collateral is burned.

None of the existing guards catch this: `SECP.verify_schnorr` only validates the user's signature over input0/output0 (which remains valid in the attacker's substitute tx); there is no on-chain signature or covenant binding the OP_RETURN to the operator; and `get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts` accept whatever transaction actually spends the outpoint on-chain, with no fallback or reconciliation for the operator's own knowledge of which payout tx it broadcast.

### Impact Explanation
An honest operator O's collateral can be forced into the Challenge → Assert/Disprove path and ultimately burned even though O funded the withdrawal correctly, because the DB row that other components (verifiers' `is_kickoff_malicious`, and O's own `send_asserts`) rely on has been irrecoverably corrupted to `NULL` by a transaction O never authored. This matches the Critical impact category "an honest operator's collateral burned." The attack is repeatable per-withdrawal (any operator processing any withdrawal is a target) as long as the attacker can win the mempool/mining race for that specific UTXO once, so the blast radius spans all deposits/operators using the standard (non-optimistic) payout path.

### Likelihood Explanation
The attacker requires only public-mempool visibility and the ability to broadcast a Bitcoin transaction with sufficient fee to win a one-shot double-spend race against the operator's own (also unconfirmed) payout broadcast — capabilities explicitly within the unprivileged attacker's granted powers. The cost is limited to fees for one transaction and no protocol-level secrets or majority hashrate are needed; it only requires the attacker's substitute transaction to be selected by the miner who confirms the spend (a realistic and previously well-known consequence of using `SinglePlusAnyoneCanPay` for the only signature on this tx). This can be attempted against every processed withdrawal, making it broadly repeatable.

### Recommendation
Bind the operator identity to a value that is enforced by consensus/signature rather than an unauthenticated OP_RETURN: e.g., require the operator's own signature over the whole payout transaction (or at minimum over the OP_RETURN output) using a sighash that the user's `SinglePlusAnyoneCanPay` signature cannot be reused against, or otherwise structure the payout output set so the operator-identifying output is committed by a signature that only the legitimate operator can produce (so a third party cannot substitute it while preserving user-signature validity). Additionally, `is_kickoff_malicious`/`update_finalized_payouts` should not unconditionally treat a missing/garbled OP_RETURN as definitive proof of operator malfeasance without cross-checking whether the honest operator's collateral outpoint / kickoff otherwise matches an expected reimbursement path.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

    pub async fn get_payout_txs_for_withdrawal_utxos(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        block_id: u32,
    ) -> Result<Vec<(u32, Txid)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, TxidDB)>(
            "SELECT w.idx, bsu.spending_txid
             FROM withdrawals w
             JOIN bitcoin_syncer_spent_utxos bsu
                ON bsu.txid = w.withdrawal_utxo_txid
                AND bsu.vout = w.withdrawal_utxo_vout
             WHERE bsu.block_id = $1",
        )
        .bind(i32::try_from(block_id).wrap_err("Failed to convert block id to i32")?);

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_all)?;

        results
            .into_iter()
            .map(|(idx, txid)| {
                Ok((
                    u32::try_from(idx).wrap_err("Failed to convert withdrawal index to u32")?,
                    txid.0,
                ))
            })
            .collect()
    }
