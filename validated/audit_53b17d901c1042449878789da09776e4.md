### Title
Unauthenticated disclosure of aggregator-only `InternalGetEmergencyStopTx` when `client_verification=false` - ([File: core/src/rpc/aggregator.rs])

### Summary
The gRPC method binding for internal calls (`is_internal` checking the `grpc-method` header for an `Internal` prefix) is only enforced by the `OnlyAggregatorAndSelf` interceptor. `create_grpc_server` swaps that interceptor for `Interceptors::Noop` whenever `config.client_verification` is `false`, so any caller reaching the aggregator's public gRPC port can invoke `InternalGetEmergencyStopTx` and obtain `encrypted_emergency_stop_txs` for arbitrary move txids, without any peer-certificate or ownership check.

### Finding Description
Binding claimed: requester of the emergency-stop tx for move txid `T` == authorized internal caller (self/aggregator), enforced by `only_aggregator_and_self` via `is_internal` in `core/src/rpc/interceptors.rs` (lines 12-20, 62-69).

Trace:
- `AggregatorServer::internal_get_emergency_stop_tx` (`core/src/rpc/aggregator.rs:1938-1971`) takes a list of txids straight from the request, looks them up with `self.db.get_emergency_stop_txs(None, txids)`, and returns `encrypted_emergency_stop_txs` with zero caller-identity check inside the handler itself.
- The only place that binds "internal" methods to a trusted caller is the `Interceptors::OnlyAggregatorAndSelf` variant in `core/src/rpc/interceptors.rs`, which inspects the mTLS peer's leaf certificate and rejects the call unless `leaf_cert == our_cert` for internal methods.
- `create_grpc_server` in `core/src/servers.rs:106-139` only installs `OnlyAggregatorAndSelf` when `config.client_verification` is `true`; otherwise it installs `Interceptors::Noop` (line 137), whose `call` implementation is a pass-through (`core/src/rpc/interceptors.rs:30`) with **no authentication of any kind**, not even a coarse "same caller" check.
- With `Noop` active, an attacker with only network access to the aggregator's gRPC port can call `InternalGetEmergencyStopTx` directly (the generated server dispatch at `core/src/rpc/clementine.rs:5296-5346` routes any client request to `internal_get_emergency_stop_tx` regardless of caller identity) and retrieve `encrypted_emergency_stop_tx` for any move txid stored in `emergency_stop_sigs` (`core/src/database/aggregator.rs:33-61`), including deposits that belong to other users.

This matches the described attacker action exactly: an unauthenticated caller submits arbitrary move txids and receives the corresponding emergency-stop artifacts.

### Impact Explanation
The value returned is `emergency_stop_tx` from the `emergency_stop_sigs` table, described in the code as a signed, encrypted emergency-stop transaction tied to a specific move txid. Premature/undesired disclosure of this artifact to an unauthorized party is a protocol-commitment disclosure issue: it lets an outside party learn/pre-stage material that is meant to be reachable only by the aggregator/self, ahead of any authorized emergency-stop trigger. This is repeatable across every deposit whose move txid the attacker can guess or observe on-chain (move txids are public once broadcast), so the blast radius covers the whole set of active deposits, not a single one. However, whether this constitutes a WOTS/secret-bearing leak in the strict sense depends on the encryption scheme used for `encrypted_emergency_stop_tx` (payload is stored as `Vec<u8>` and its encryption/decryption path was not verifiable within index limits) — if it's encrypted to a security-council key the attacker cannot use, no bridge value moves or gets frozen as a direct, mechanical result of this call alone; it is a "premature disclosure of a protocol commitment" (matches the High-severity category in the rules), not by itself a fund-freezing/fund-loss event.

### Likelihood Explanation
Preconditions: aggregator deployed with `client_verification=false` (a supported, real configuration path, not a test-only toggle — see `core/src/config/mod.rs`/`env.rs`), and the attacker only needs network access to the aggregator's gRPC port plus a valid move txid (public on-chain data). No BTC spend, no fee payment, and no privileged role is required; the call can be repeated for every known move txid.

### Recommendation
Enforce internal-method authorization independent of `client_verification`/TLS peer identity — e.g., require `client_verification=true` for aggregator deployments (fail startup/warn-and-refuse if `Noop` is selected while internal methods are exposed), or add an explicit application-level check inside `internal_get_emergency_stop_tx` that rejects calls unless they originate from the aggregator's own trusted context (e.g., a loopback/unix-socket-only channel, or a secondary shared secret / mTLS enforced regardless of `client_verification`). At minimum, split `Internal*` RPCs onto a listener that is never exposed on the public port and never wrapped with `Noop`.
