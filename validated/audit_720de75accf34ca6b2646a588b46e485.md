### Title
Symlink Following in README.md Write Allows Arbitrary File Overwrite - (File: app/src/ui/add-repository/write-default-readme.ts)

### Summary
`writeDefaultReadme` writes to a hardcoded `README.md` path via Node's `fs.promises.writeFile`, which follows symlinks by default. There is no `lstat`/symlink check before the write, so if a `README.md` at the destination is a symlink, the write will follow it and truncate/overwrite whatever file it points to.

### Finding Description
`writeDefaultReadme` builds the target path with `Path.join(path, DefaultReadmeName)` (`DefaultReadmeName = 'README.md'`) and calls `writeFile(fullPath, contents)` with no flags and no pre-check for an existing symlink at that path. [1](#0-0) 

Node's `fs.writeFile`/`fs.promises.writeFile` opens the destination with the default `'w'` flag, which resolves symlinks and writes through them rather than replacing the link itself. There is no `O_NOFOLLOW`, no `lstat` check, and no `fs.unlink`-then-recreate pattern used here.

The caller, `CreateRepository.createRepository` in `create-repository.tsx`, only checks whether an existing `README.md` is present (`pathExists`) to show a generic "will be overwritten" warning — it never distinguishes a regular file from a symlink: [2](#0-1) [3](#0-2) 

Critically, the "Create Repository" flow does not require the target directory to be empty or attacker-free. The Create button is disabled only when the folder is itself a recognized Git repository (`isRepository`), but a folder that is merely a *subfolder* of an existing repository (`isSubFolderOfRepository`) only produces a non-blocking warning about submodules and does not disable creation: [4](#0-3) [5](#0-4) 

This means an attacker-controlled cloned repository can contain a subdirectory with a committed symlink named `README.md` pointing to an arbitrary file outside the repository (e.g., `~/.ssh/authorized_keys`, a shell profile, or another repo's file). If the victim later uses "Create repository" targeting that subdirectory (a plausible action hinted at by the UI's own submodule-conversion messaging) and checks "Initialize this repository with a README", `writeDefaultReadme` follows the planted symlink and overwrites the linked file with attacker-influenceable content (the README header is derived from the repository name/description entered by the user, but the *location* of the write is fully attacker-controlled via the symlink target).

### Impact Explanation
This allows file write outside the intended repository directory, satisfying the "file write... outside the repo" impact category. The attacker controls the write destination completely (any path the OS user has write access to); the content is partially attacker-influenced indirectly, but the primary damage is overwriting/corrupting an arbitrary file (e.g., truncating configuration files, dotfiles, or scripts that get executed later).

### Likelihood Explanation
Exploitation requires a specific sequence: the victim must clone/obtain the malicious repository, then separately invoke "Create Repository" and select a path inside (or equal to) that repository's tree that contains the planted `README.md` symlink, and enable the "Initialize with README" checkbox despite the (generic, non-alarming) overwrite warning. This is a plausible but non-default user flow — it's not triggered by simply cloning or browsing the repository. Likelihood is moderate-low due to the required manual folder selection and checkbox interaction, but the missing symlink check is a genuine, unmitigated gap since none of the existing checks (`pathExists`, `isRepository`) detect or block a symlink.

### Recommendation
Before writing, `lstat` the destination path and refuse to write (or remove and recreate the file, or open with `wx`/`O_NOFOLLOW`-equivalent semantics) if the existing entry is a symlink. This same pattern should be reviewed for the sibling helpers `writeGitIgnore`, `writeLicense`, `writeGitAttributes`, and `writeGitDescription`, which appear to follow the same write-without-symlink-check approach in the same repository-creation flow.

### Proof of Concept
1. Create a malicious repository containing a directory `evil/` with a committed symlink `evil/README.md -> ../../../outside-target.txt` (or an absolute path to a sensitive file).
2. Victim clones the repository.
3. Victim opens "Create Repository" in GitHub Desktop and sets the path/name to point at the cloned repo's `evil/` subdirectory (UI allows this since it's only flagged as "subfolder of repository," not blocked).
4. Victim checks "Initialize this repository with a README" and clicks "Create repository".
5. `writeDefaultReadme(fullPath, name, description)` runs `writeFile(Path.join(fullPath, 'README.md'), contents)`, which follows the symlink and overwrites `outside-target.txt` with the generated README content, confirming file write outside the repository root.

```typescript
import { writeFile } from 'fs/promises'
import * as Path from 'path'

const DefaultReadmeName = 'README.md'

function defaultReadmeContents(name: string, description?: string): string {
  return description !== undefined
    ? `# ${name}\n${description}\n`
    : `# ${name}\n`
}

/**
 * Write the default README to the repository with the given name at the path.
 */
export async function writeDefaultReadme(
  path: string,
  name: string,
  description?: string
): Promise<void> {
  const fullPath = Path.join(path, DefaultReadmeName)
  const contents = defaultReadmeContents(name, description)
  await writeFile(fullPath, contents)
}
```
