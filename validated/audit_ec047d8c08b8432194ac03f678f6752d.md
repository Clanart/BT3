## Finding: EIP-712 multi-message type confusion allows unauthorized messages to be smuggled into a "single-message" signed transaction

### Title
Multi-Msg EIP-712 Type Confusion in `VerifySignature` Allows Unsigned/Unapproved Messages to Execute - (`ante/cosmos/eip712.go`)

### Summary
`VerifySignature` in `ante/cosmos/eip712.go` derives the EIP-712 type schema (`MsgValue`) solely from `msgs[0]`, but signs the hash over `txData` (unmarshalled from `txBytes`) which is built from **all** messages in the tx via `legacytx.StdSignBytes(... , msgs, ...)`. Because the schema used to compute the EIP-712 struct hash for the `"msgs"` array element type (`Msg` → `MsgValue`) is fixed to the fields discovered by walking `msgs[0]`'s Go struct, any field present in `msgs[1..N]` that is not part of that schema is silently excluded from the signed hash. [1](#0-0) 

### Finding Description
The relevant code path:
1. `msgs := tx.GetMsgs()` — no restriction that `len(msgs) == 1` (only `len(msgs) == 0` is rejected).
2. `txBytes` is computed via `legacytx.StdSignBytes(...)` over **all** `msgs`, so the JSON `txData["msgs"]` array contains every message in the tx.
3. `eip712.LegacyWrapTxToTypedData(evmCodec, extOpt.TypedDataChainID, msgs[0], txBytes, feeDelegation)` sets `typedData.Message = txData` (all msgs) but derives `typedData.Types["MsgValue"]` **only from `msgs[0]`** via `extractMsgTypes`/`walkFields`. [2](#0-1) 

The `"Tx"` type declares `"msgs"` as `Msg[]`, and `"Msg"` declares `"value"` as the single, globally-shared type name `MsgValue`: [3](#0-2) 

Since `apitypes.TypedDataAndHash` (go-ethereum) hashes struct fields strictly according to the declared `Types` schema, every element of the `msgs` array — including `msgs[1..N]` — is hashed using the **same** `MsgValue` schema derived from `msgs[0]`. Fields of `msgs[1..N]` that don't exist in that schema are never included in the struct hash, meaning the resulting `sigHash` does not commit to that content.

Critically, this ante decorator (`VerifySignature`) calls `LegacyWrapTxToTypedData` directly and does **not** invoke the `legacyValidatePayloadMessages` guard (which does exist and enforces "all messages must share the same type and signer") that is used only by the separate `LegacyGetEIP712TypedDataForMsg` / `legacyDecodeAminoSignDoc` decode helpers in `ethereum/eip712/encoding_legacy.go`: [4](#0-3) 

That validation only exists in a code path used for decoding/tooling (e.g. `client/debug/debug.go`), not in the actual on-chain signature-verification function. An attacker does not need to go through any client library that enforces this check — EIP-712 hashing is fully deterministic and public, so a malicious dApp/relayer can independently construct a `msgs[0]` that a wallet will faithfully display and sign (e.g., an innocuous zero-value message), then append additional attacker-chosen messages (`msgs[1..N]`) whose fields fall outside `msgs[0]`'s schema (or reuse field names that don't overlap, e.g. mismatched Msg types). These extra messages are not committed to the signed hash, yet they are present in `tx.GetMsgs()` and will be executed by the message router after the ante chain passes.

### Impact Explanation
This is a Critical, unauthorized extraction of user funds: a victim who is shown and signs a message they believe is benign (`msgs[0]`) can have arbitrary additional Cosmos messages (`bank.MsgSend`, `MsgDelegate`, ERC20/precompile calls, `authz.MsgExec`, etc.) silently smuggled into the same transaction and executed against their account, without those messages ever contributing to the signed hash. This directly satisfies the "Critical … theft, unauthorized extraction of user funds" impact gate.

### Likelihood Explanation
Exploitation requires only an unprivileged attacker (e.g., operating a malicious dApp/frontend or relaying wallet requests) that can present an EIP-712 signing request to a victim and then reassemble/broadcast the raw Cosmos tx with additional messages appended before submission — a capability inherent to how EIP-712-signed Cosmos txs are normally constructed and broadcast by third-party tooling. No validator, governance, or node privilege is required.

### Recommendation
- In `VerifySignature` (`ante/cosmos/eip712.go`), reject the transaction unless `len(msgs) == 1`, matching how the ante loop already restricts to a single signature, OR
- Call `legacyValidatePayloadMessages`/an equivalent check before calling `LegacyWrapTxToTypedData` to enforce that every message shares the same type/schema and signer as `msgs[0]`, OR
- Derive the EIP-712 type schema per-message index (not just from `msgs[0]`) so that all fields of every message are actually included in the signed hash.

### Proof of Concept
1. Attacker (malicious dApp) prepares `msgs[0]` = an innocuous message the victim's wallet will render and sign, e.g. a zero-amount `bank.MsgSend` from victim to self.
2. Attacker computes the exact EIP-712 typed data the ante handler will construct (`LegacyWrapTxToTypedData` is deterministic and public), obtains the victim's signature over that hash via the wallet UI.
3. Attacker builds the actual broadcast transaction with `msgs = [msgs[0], MsgSend{From: victim, To: attacker, Amount: victim_balance}]` and the same `feeDelegation`/`ExtensionOptionsWeb3Tx`, reusing the victim's signature.
4. `VerifySignature` recomputes `txBytes` over both messages (matching what was submitted) but `typedData.Types["MsgValue"]` is derived only from `msgs[0]` (the zero-value send), so the hash used for `TypedDataAndHash` does not depend on `msgs[1]`'s from/to/amount fields being drained — signature check passes.
5. Message routing executes both `msgs[0]` and `msgs[1]`, draining the victim's account via `msgs[1]`, which was never actually bound by the signature. [5](#0-4)

func LegacyWrapTxToTypedData(
	cdc codectypes.AnyUnpacker,
	chainID uint64,
	msg sdk.Msg,
	data []byte,
	feeDelegation *FeeDelegationOptions,
) (apitypes.TypedData, error) {
	txData := make(map[string]interface{})

	if err := json.Unmarshal(data, &txData); err != nil {
		return apitypes.TypedData{}, errorsmod.Wrap(errortypes.ErrJSONUnmarshal, "failed to JSON unmarshal data")
	}

	domain := apitypes.TypedDataDomain{
		Name:              "Cosmos Web3",
		Version:           "1.0.0",
		ChainId:           math.NewHexOrDecimal256(int64(chainID)), //#nosec G115 -- int overflow is not a concern here
		VerifyingContract: "cosmos",
		Salt:              "0",
	}

	msgTypes, err := extractMsgTypes(cdc, "MsgValue", msg)
	if err != nil {
		return apitypes.TypedData{}, err
	}

	if feeDelegation != nil {
		feeInfo, ok := txData["fee"].(map[string]interface{})
		if !ok {
			return apitypes.TypedData{}, errorsmod.Wrap(errortypes.ErrInvalidType, "cannot parse fee from tx data")
		}

		feeInfo["feePayer"] = feeDelegation.FeePayer.String()

		// also patching msgTypes to include feePayer
		msgTypes["Fee"] = []apitypes.Type{
			{Name: "feePayer", Type: "string"},
			{Name: "amount", Type: "Coin[]"},
			{Name: "gas", Type: "string"},
		}
	}

	typedData := apitypes.TypedData{
		Types:       msgTypes,
		PrimaryType: "Tx",
		Domain:      domain,
		Message:     txData,
	}

	return typedData, nil
}

// validatePayloadMessages ensures that the transaction messages can be represented in an EIP-712
// encoding by checking that messages exist, are of the same type, and share a single signer.
func legacyValidatePayloadMessages(msgs []sdk.Msg) error {
	if len(msgs) == 0 {
		return errors.New("unable to build EIP-712 payload: transaction does contain any messages")
	}

	var msgType string
	var msgSigner sdk.AccAddress

	for i, m := range msgs {
		t, err := getMsgType(m)
		if err != nil {
			return err
		}

		signers, _, err := protoCodec.GetMsgV1Signers(m)
		if err != nil {
			return err
		}
		if len(signers) != 1 {
			return errors.New("unable to build EIP-712 payload: expect exactly 1 signer")
		}

		if i == 0 {
			msgType = t
			msgSigner = signers[0]
			continue
		}

		if t != msgType {
			return errors.New("unable to build EIP-712 payload: different types of messages detected")
		}

		if !msgSigner.Equals(sdk.AccAddress(signers[0])) {
			return errors.New("unable to build EIP-712 payload: multiple signers detected")
		}
	}

	return nil
}
