### Title
SignableTransaction underpays the network fee by excluding the OP_RETURN data output from the weight/vbytes calculation, producing transactions below the requested (and possibly minimum-relay) fee rate - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the CrosschainDistributor bug (a cross-chain message dispatched without paying the fee required to relay/process it), `SignableTransaction::new` in `bitcoin-serai` builds the final transaction with an extra `OP_RETURN` output carrying caller-supplied `data`, but computes the transaction's weight and vbytes — and therefore `needed_fee` — before accounting for that output. The signed transaction pays less than the specified `fee_per_vbyte`, and can fall below Bitcoin's minimum relay fee, so it will not be relayed and the recipient never receives the funds.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is appended to `tx_outs` when `data` is supplied:

```rust
// networks/bitcoin/src/wallet/send.rs:193-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}
```

But the size used for the fee is computed only from `tx_ins` and `payments`:

```rust
// networks/bitcoin/src/wallet/send.rs:204-211
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
if needed_fee < ((u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * vbytes) / 1000) {
  Err(TransactionError::TooLowFee)?;
}
```

`calculate_weight_vbytes` only includes `payments` (plus optional `change`) in `tx.output`; the `data` output is never passed in. `data` may be up to 80 bytes (`TooMuchData` check, line 171), which adds ~90+ serialized bytes / ~360+ weight units (~90+ vbytes) to the real transaction that are never charged for.

Two consequences:

1. **Underpaid fee.** `needed_fee` is computed for a smaller transaction than the one actually signed and returned in `SignableTransaction.tx`. `fee()` (line 138) confirms the actual fee equals `needed_fee`, so the effective feerate is strictly below `fee_per_vbyte` whenever `data` is present.

2. **Broken `TooLowFee` guard.** The minimum-relay-fee check uses the underestimated `vbytes`. If `fee_per_vbyte` is at/near the minimum relay rate (e.g., 1 sat/vB), the signed transaction's actual feerate falls below `DEFAULT_MIN_RELAY_TX_FEE` for its real size, so nodes will reject it from their mempool entirely — mirroring the reported issue where the message "will not be relayed on the target chain and the user will not receive" the funds.

The same omission affects the `TooLargeTransaction` check at line 241: `weight` only reflects `payments` + optional `change`, never the data output, so a transaction that actually exceeds `MAX_STANDARD_TX_WEIGHT` can be produced.

Unlike a normal wallet, these transactions are FROST-threshold-signed (`TransactionMachine`), use `Sequence::MAX` (no RBF flagging), and the protocol machinery tracks completion via `Eventuality(txid)` — a transaction that cannot be relayed never reaches the mempool, cannot be fee-bumped without a fresh threshold signing round, and stalls the plan whose inputs are being spent.

### Impact Explanation
Any transaction built with `Some(data)` pays a lower feerate than requested; at the minimum fee rate it becomes unrelayable, leaving payments undelivered — the same "dispatched but never relayed, recipient never paid" outcome as the external report. Recovering requires assembling the full threshold signing set again to re-sign with corrected fees, and any `Eventuality` bound to the original `txid` will never complete. Medium severity: conditional on the `data` field being used and on the fee rate being near minimum, but the failure is silent and requires a new signing ceremony to resolve.

### Likelihood Explanation
The `data` argument is part of the public `SignableTransaction::new` API and accepts arbitrary caller-controlled bytes up to 80 bytes. The current processor call site passes `None`, so the buggy path is not exercised by the default flow — but the function is the designated send path of the in-scope `bitcoin-serai` wallet and any consumer (or future plan type embedding instruction/refund data in the OP_RETURN) silently triggers it. The `TooLowFee` guard exists precisely to prevent unrelayable transactions, yet is checked against the wrong size, so no other validation catches this.

### Recommendation
Include the data output in the size calculation: either push the `OP_RETURN` `TxOut` into the payment list before calling `calculate_weight_vbytes`, or extend `calculate_weight_vbytes` to accept the data output explicitly. Apply the same fix to the `weight` value used for the `MAX_STANDARD_TX_WEIGHT` check, so both the minimum-relay-fee check and the max-weight check are evaluated against the true transaction size.

### Proof of Concept
```rust
// Conceptual — inside networks/bitcoin
let data = vec![0u8; 80]; // max permitted OP_RETURN payload
let tx = SignableTransaction::new(
  vec![funded_output],
  &[(payment_script, PAYMENT_AMOUNT)],
  None,
  Some(data.clone()),
  1, // fee_per_vbyte = minimum relay rate (1 sat/vB)
).unwrap();

// needed_fee was computed for a tx WITHOUT the 80-byte OP_RETURN output,
// but tx.transaction() includes it.
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// The real vsize is larger than the vbytes used to derive needed_fee:
let real_vbytes = u64::try_from(tx.transaction().vsize()).unwrap();
let effective_rate = tx.fee() as f64 / real_vbytes as f64;
assert!(effective_rate < 1.0); // below DEFAULT_MIN_RELAY_TX_FEE -> rejected by relay

// Nodes will refuse to relay/accept this transaction into the mempool;
// the payment is never delivered and cannot be RBF'd (Sequence::MAX).
```

Root cause is confined to `networks/bitcoin/src/wallet/send.rs`: the `OP_RETURN` output is added to `tx_outs` at lines 194–202 after, and independently of, the size/fee computation at lines 204–213 and the weight check at line 241.
