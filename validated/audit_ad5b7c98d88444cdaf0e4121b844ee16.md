## Analysis

The external report's core invariant: **raw ERC‑20 transfer calls whose success is inferred only from the low‑level call outcome, without validating the token's actual boolean return value, let the caller falsely believe funds moved when they did not** — leading to accounting/state advancing as if a transfer succeeded.

The Tron variant of `IntentGatewayV2` reproduces exactly this pattern in its escrow payout paths, while the "sibling" mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol` / `evm/src/apps/intentsv2/IntentsBase.sol`) correctly uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which decodes the returned boolean and reverts on `false`.

### Title
Escrow payout in Tron IntentGatewayV2 accepts a silent `false` ERC‑20 return as success, allowing fund loss/lock for solvers and refund beneficiaries - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` branch of `onAccept()` in the Tron `IntentGatewayV2` release escrowed ERC‑20 tokens using a raw low-level `.call()` and only check the outer `success` boolean returned by the EVM call, never decoding/validating the ERC‑20 function's own boolean return value: [1](#0-0) [2](#0-1) [3](#0-2) 

Per the ERC‑20 spec, `transfer`/`transferFrom` are permitted to return `false` on failure instead of reverting; several deployed tokens do exactly this. Because the code only checks the outer `.call()` success flag (`success`), a call to such a token that returns `false` still evaluates `success == true` (the call itself did not revert), so the contract proceeds as though the transfer succeeded: it decrements `_orders[commitment][token]`, marks `_filled[commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded`/`DustSwept` — all while the token balance was never actually moved to the beneficiary.

This directly contrasts with the rest of the codebase, which imports and correctly relies on `SafeERC20` for the same operations, e.g. in the escrow release logic of the non‑Tron `IntentsBase.sol`: [4](#0-3) 

and the deposit side of the very same Tron file, which does correctly use `safeTransferFrom`: [5](#0-4) 

Even though `SafeERC20` is imported in the Tron file, it is bypassed in `withdraw()`, the fee-redemption branch, and `SweepDust`.

### Impact Explanation
When an order's escrowed input token returns `false` on transfer failure instead of reverting (a valid, standards-compliant behavior some real tokens exhibit — e.g. can be triggered deliberately by an order-creator who selects such a token as `order.inputs[i].token`), the solver who fulfilled the order on the destination chain (delivering real value to the user) will never receive their escrowed payout on the source chain via `withdraw()`, yet the contract emits `EscrowReleased` and marks `_filled`/decrements escrow as if payment succeeded. The solver's payment is lost while the escrowed tokens remain stuck in the contract (fund loss/lock) and the on-chain event log falsely attests a successful transfer — a false-state-acceptance/loss-of-funds condition reachable entirely by an unprivileged order creator choosing the escrowed token, with no reliance on a malicious relayer, prover, or admin.

### Likelihood Explanation
The order creator (an ordinary, unprivileged user) fully controls which ERC‑20 address is used as `order.inputs[i].token` when calling the deposit/place-order entrypoint. No special access is required to deploy or use a token whose `transfer` returns `false` on failure rather than reverting; this is a legal ERC‑20 implementation choice used historically by some tokens (pre‑EIP20 return-value inconsistency is exactly the class of bug the referenced Solmate report warns about). The vulnerable payout code path (`withdraw`, `SweepDust`) is reached on every order settlement/cancellation cycle, making exploitation straightforward and repeatable.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (lines 693–699, 710–713 fee redemption) and the `SweepDust` branch of `onAccept()` (lines 661–667) with `SafeERC20.safeTransfer`, matching the pattern already used at the deposit site of this same file (`safeTransferFrom`) and in the mainline `IntentsBase.sol`. `SafeERC20` decodes non-empty return data and reverts on `false`, closing the false-success gap.

### Proof of Concept
1. Order creator deploys/uses a malicious/non-standard ERC‑20 token `T` as `order.inputs[i].token`, where `T.transfer()` always returns `false` (no revert) when called by the `IntentGatewayV2` contract, but `T.transferFrom()` succeeds normally when called by the creator during deposit.
2. Order creator calls `placeOrder(...)`, depositing `T` into escrow via the working `safeTransferFrom` path (`evm/tron/contracts/apps/IntentGatewayV2.sol:452-453`), so `_orders[commitment][token]` is correctly funded.
3. A solver fills the order on the destination chain (delivers real assets to the user) and the fill triggers a `RedeemEscrow` request back to the source chain.
4. `onAccept` → `withdraw(body, false)` executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` against `T`; `T.transfer` returns `false` without reverting, so `success == true` at the low level.
5. The check `if (!success) revert TransferFailed();` passes (no revert), `_orders[body.commitment][token] -= amount` executes, `_filled[body.commitment] = beneficiary` is set, and `EscrowReleased` is emitted — even though the solver received zero tokens.
6. The solver's collateral is permanently lost/stuck in the contract while all on-chain state and events indicate a successful, final settlement.
