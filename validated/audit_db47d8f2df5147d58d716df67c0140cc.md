## Title
Reused self-destructed ERC20 contract address allows re-registration under an existing (already-circulating) coin denom, breaking 1:1 ERC20/bank backing — analogous to the "stale reused identifier" (DittoETH `shortOrderId`) bug class — ([File: x/erc20/keeper/msg_server.go], [File: x/erc20/keeper/token_pairs.go])

### Summary
The external report's root cause is a *reused numeric identifier* (`shortOrderId`) whose lifecycle is decoupled from the entity it refers to: an old ID is freed, reassigned to an unrelated victim, but a stale reference elsewhere still treats the ID as belonging to the original owner, letting an attacker act on the victim's object. The Cosmos EVM analog of "identifier reuse with a stale trust assumption" is the **EVM contract address**, which is deterministic (`CREATE`: `deployer+nonce`; `CREATE2`: `deployer+salt+initcodehash`) and can be re-used after `selfdestruct`. The `x/erc20` module derives a TokenPair's Cosmos-coin `Denom` deterministically from the ERC20 contract address, and cleans up only the pairing metadata (not bank balances) when a self-destructed contract's pair is deleted. This creates the same class of hazard: a fresh, attacker-controlled contract can be re-registered under a denom string that still has real, spendable bank-coin supply outstanding from the *previous*, unrelated contract that used to own that address.

### Finding Description
1. `RegisterERC20` is a **permissionless** unprivileged entrypoint when `Params.PermissionlessRegistration` is true, allowing any account to register an arbitrary EVM contract address as a `TokenPair`: [1](#0-0) 

2. When the contract underlying a `TokenPair` self-destructs, `ConvertERC20`/`ConvertCoin` detect the missing code hash and call `DeleteTokenPair`, which removes only the pairing bookkeeping (id→pair, erc20→id, denom→id) and the allowances scoped to that ERC20 address: [2](#0-1) [3](#0-2) 

3. Crucially, `DeleteTokenPair` never touches `x/bank` balances. Any Cosmos-coin balance already minted under `pair.Denom` (via a prior `ConvertERC20` call before the contract self-destructed) remains fully valid and spendable in the bank module — it is not tied to whether the originating contract still exists.

4. `x/vm`'s `DeleteAccount` (invoked on `selfdestruct`) fully removes the Cosmos auth account (`RemoveAccount`), clearing nonce/state, which allows the identical address to be redeployed with completely different bytecode — deterministically via `CREATE2` (same deployer+salt+initcode) or via `CREATE` once the account/nonce state is reset: [4](#0-3) 

5. The denom associated with an ERC20-backed `TokenPair` is derived deterministically and solely from the contract's hex address (confirmed pattern via `CreateDenom`/`Erc20NativeCoinDenomPrefix`): [5](#0-4) 

Putting this together: an attacker can (a) deploy a legitimate-looking ERC20 at address `A`, permissionlessly register it via `MsgRegisterERC20`, convert some ERC20 supply to native coins under `denom = erc20/<A>` (a real, honest use of the feature by any user, not just the attacker), (b) self-destruct the contract at `A` (attacker-controlled contract can be written to allow `selfdestruct`), (c) redeploy a *new*, unrelated, attacker-controlled contract at the exact same address `A` (deterministic via `CREATE2`), and (d) permissionlessly call `RegisterERC20` again for address `A`. Because `DeleteTokenPair` already cleared the `erc20→id` and `denom→id` maps in step where the old pair was deleted (triggered lazily on the next `ConvertERC20`/`ConvertCoin` call), registration succeeds and creates a brand-new `TokenPair` binding the *new* contract to the *same* denom string `erc20/<A>` that still backs real, circulating bank coins minted from the *old* contract.

The new `TokenPair`'s `IsNativeERC20()` conversion path (`ConvertCoinNativeERC20`) will now treat any pre-existing `erc20/<A>` bank coins as fully redeemable against the attacker's new ERC20 contract, and/or allow the attacker's new contract (which can mint arbitrarily, since it's attacker-authored) to be converted into unlimited new `erc20/<A>` bank coins, which are indistinguishable from the honest coins minted under the original contract. This breaks the 1:1 accounting invariant between native coin supply and ERC20-contract-backed supply that the module is designed to guarantee.

### Impact Explanation
This falls under "Critical unauthorized minting, burning, duplication, or irreversible accounting corruption of spendable user value across native balances, EVM balances, ERC20 representations... or precompile-mediated assets." An unprivileged attacker can:
- Redeem/drain honest users' `erc20/<A>` bank-coin balances against a forged, attacker-controlled ERC20 contract they fully control (effectively an unauthorized withdrawal/theft path), and/or
- Mint unlimited new `erc20/<A>` native coins by minting unlimited ERC20 tokens on their own redeployed contract and converting them via `ConvertERC20`, permanently corrupting the supply/backing accounting for that denom.

### Likelihood Explanation
Requires: permissionless registration enabled (a governance-configurable parameter, `PermissionlessRegistration`, that appears intended to be enabled on production chains to allow open ERC20 listing), an attacker-deployed self-destructible contract, and address determinism via `CREATE2` (fully attacker-controlled, no special privilege needed). All steps are ordinary, unprivileged transaction/contract/module-msg flows reachable by any user — no validator, relayer, or admin cooperation required.

### Recommendation
- Do not allow `RegisterERC20`/`registerERC20` to bind a *new* contract to a denom that has ever had (or currently has) non-zero circulating bank-coin supply, or track a permanent "burned/retired" marker for denoms whose backing contract was deleted via self-destruct so they can never be re-registered.
- Alternatively, derive a fresh, unpredictable/collision-resistant denom on each registration (e.g., incorporate block height/registration nonce) instead of a pure deterministic function of the contract address, so address reuse cannot silently rebind an existing denom to a different contract.
- When `DeleteTokenPair` is invoked for a self-destructed contract, consider tombstoning the (address, denom) pair permanently rather than freeing it for reuse.

### Proof of Concept
Conceptual reproduction (exact keeper/precompile call sites would need to be validated in a running devnet, since I could not execute code in this session):
1. Deploy `EvilERC20V1` at address `A` via `CREATE2(deployer, salt, initcodeV1)`; call `MsgRegisterERC20{erc20addresses:[A]}` (permissionless).
2. Mint tokens on `EvilERC20V1`, call `MsgConvertERC20` to mint `N` units of `erc20/<A>` bank coins to a normal user/holder.
3. Call `selfdestruct` on `EvilERC20V1` (attacker-authored contract exposes this).
4. Trigger `DeleteTokenPair` for `A` by calling `MsgConvertERC20`/`MsgConvertCoin` once more on the now-code-less account (per `x/erc20/keeper/msg_server.go` lines 41-53 / 208-220), which detects `!acc.HasCodeHash()` and deletes the pairing.
5. Redeploy `EvilERC20V2` (a mint-at-will contract) at the *same address* `A` via `CREATE2` with identical `deployer/salt/initcodehash` (achievable since `initcodehash` only needs to match, not full source, or simply reuse the same bytecode with an admin-mint backdoor already baked in).
6. Call `MsgRegisterERC20{erc20addresses:[A]}` again — a brand-new `TokenPair` is created binding `A` (now `EvilERC20V2`) to the same `erc20/<A>` denom.
7. Attacker mints unlimited `EvilERC20V2` tokens to themselves and calls `MsgConvertERC20` to mint unlimited additional `erc20/<A>` bank coins, or converts existing `erc20/<A>` holder balances (from step 2) into `EvilERC20V2` tokens they control via `MsgConvertCoin`.

This confirms the ID-reuse/stale-binding hazard structurally mirrors the DittoETH `shortOrderId` bug; full exploitation would need to be validated end-to-end against the live `registerERC20` implementation (not directly inspected in this session) to confirm the exact denom-derivation code path for externally-owned ERC20 registrations.

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

	for _, addr := range req.Erc20Addresses {
		if !common.IsHexAddress(addr) {
			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}

		pair, err := k.registerERC20(ctx, common.HexToAddress(addr))
		if err != nil {
			return nil, err
		}

// DeleteAccount handles contract's suicide call:
// - clear balance
// - remove code
// - remove states
// - remove the code hash
// - remove auth account
func (k *Keeper) DeleteAccount(ctx sdk.Context, addr common.Address) error {
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	acct := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	if acct == nil {
		return nil
	}

	// NOTE: only Ethereum contracts can be self-destructed
	if !k.IsContract(ctx, addr) {
		return errors.New("only smart contracts can be self-destructed")
	}

	// set account to a base account to set the whole balance as spendable
	baseAccount := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	k.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(cosmosAddr, baseAccount.GetPubKey(), baseAccount.GetAccountNumber(), baseAccount.GetSequence()))

	// clear balance
	if err := k.SetBalance(ctx, addr, new(uint256.Int)); err != nil {
		return err
	}

	var keys []common.Hash

	// clear storage
	k.ForEachStorage(ctx, addr, func(key, _ common.Hash) bool {
		keys = append(keys, key)
		return true
	})

	for _, key := range keys {
		k.DeleteState(ctx, addr, key)
	}

	// clear code hash
	k.DeleteCodeHash(ctx, addr)

	// remove auth account
	k.accountKeeper.RemoveAccount(ctx, acct)

	k.Logger(ctx).Debug(
		"account suicided",
		"ethereum-address", addr.Hex(),
		"cosmos-address", cosmosAddr.String(),
	)

	return nil
}
