## Validation of the binding

**Binding claimed broken:** `withdrawals.payout_payer_operator_xonly_pk` (the operator credited/reimbursed for withdrawal `i`) == the xonly-pubkey of the operator whose own funds paid output 0 of the transaction that spent `withdrawal_utxo` for withdrawal `i`.

Tracing the code confirms this equality is **not enforced** — attribution is derived solely from unauthenticated bytes in whichever transaction happens to win the race to spend the withdrawal input.

- `create_payout_txhandler` builds the payout tx with `SpendPath::KeySpend` and `DEFAULT_SEQUENCE = Sequence::ENABLE_RBF_NO_LOCKTIME` (`0xFFFFFFFD`), i.e., BIP-125 RBF is explicitly enabled on this transaction. [1](#0-0) [2](#0-1) 
- The user's signature has `TapSighashType::SinglePlusAnyoneCanPay`, which commits only to input 0 and output 0; outputs 1 (anchor) and 2 (OP_RETURN) are unauthenticated and can be freely substituted by anyone who reconstructs the transaction, as documented in the function itself ("Outputs: 1. User payout output 2. OP_RETURN output (with operator's x-only pubkey that fronts the peg-out)"). [3](#0-2) 
- Attribution is computed purely from whichever tx is observed on-chain spending `withdrawal_utxo_txid`/`vout`: `get_payout_txs_for_withdrawal_utxos` joins on the spent-UTXO tracking table with no signer/funder check, and `update_finalized_payouts` parses the OP_RETURN of that confirmed tx to set `payout_payer_operator_xonly_pk`. [4](#0-3) [5](#0-4) 
- `get_first_unhandled_payout_by_operator_xonly_pk` then simply looks up unhandled rows matching an operator's own xonly_pk and feeds them to `PayoutCheckerTask::run_once`, which unconditionally calls `handle_finalized_payout` for that operator — there is no check that the operator actually broadcast/funded the winning transaction. [6](#0-5) [7](#0-6) 
- The bridge circuit's SPV/storage-proof checks only validate output 0 (correct recipient/amount per Citrea's withdrawal record) and the operator-claimed chain of work; the operator identity used for attribution comes from "the first OP_RETURN output of the payout transaction" with no binding to who funded the extra inputs. [8](#0-7) 

None of the listed guards (`is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `SPV::verify`, `verify_storage_proofs`, presigned tx graph) checks that the operator named in OP_RETURN is the one who actually supplied the payout funds — they only validate that output 0 correctly pays the withdrawing user and that the claimed chain/proof data is internally consistent.

### Title
Unauthenticated OP_RETURN in the payout transaction lets an attacker redirect withdrawal attribution to an uninvolved operator via RBF replacement - ([File: core/src/verifier.rs])

### Summary
The payout transaction's operator-attribution output (OP_RETURN) and anchor output are outside the scope of the user's `SinglePlusAnyoneCanPay|Single` signature and the transaction signals RBF (`DEFAULT_SEQUENCE`). An attacker who observes an operator O's broadcast-but-unconfirmed payout transaction in the mempool can replace it with a fee-bumped variant that keeps input 0 and output 0 identical but swaps the OP_RETURN to name a different, uninvolved operator Q, getting Q credited as the payer once mined.

### Finding Description
The equality that should hold — `withdrawals.payout_payer_operator_xonly_pk == operator who funded output 0` — is broken because `update_finalized_payouts` (`core/src/verifier.rs:2283`) attributes payment purely from the OP_RETURN of whichever transaction ends up spending `withdrawal_utxo_txid/vout` on-chain, with the mapping recorded via `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:168`), which only checks the *input* the tx spends, not who signed/funded the rest of it.

Exploit flow: O broadcasts its legitimate payout tx (`create_payout_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:407`) which is RBF-enabled (`DEFAULT_SEQUENCE`). While unconfirmed, the attacker copies O's witness for input 0 (valid only for input0+output0 per SIGHASH_SINGLE|ANYONECANPAY) and constructs a new transaction: same input 0, same witness, same output 0 (paying the withdrawing user, funded from the attacker's own coins added as extra inputs), but a different OP_RETURN naming operator Q, and a higher fee, then broadcasts it. Standard Bitcoin Core RBF rules will replace O's mempool transaction with this variant, and it gets mined instead of O's.

Once confirmed, `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282`) will surface this withdrawal as "unhandled" for Q, and Q's own `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39`) will automatically call `Operator::handle_finalized_payout` (`core/src/operator.rs:839`), using Q's own pre-signed kickoff connectors to build a kickoff, ultimately entitling Q to a `Reimburse` payout from its own round chain — for a withdrawal Q never funded. The bridge circuit's SPV/proof checks validate output 0 against Citrea's withdrawal record and the operator's chain-of-work claims, but never verify that the operator named in OP_RETURN supplied the transaction's funding inputs, so this forged attribution passes challenge/disprove as well.

### Impact Explanation
Operator Q becomes eligible to claim a `Reimburse` transaction from its own round/kickoff chain for a withdrawal it never fronted — a false credit matching "an operator reimbursed for a payout it never funded." This is repeatable against any operator O whose payout tx is caught unconfirmed in the mempool for any withdrawal, and the attacker can name any registered operator Q as the target of the mis-attribution. Because operator identity registration is public (all operator xonly_pks are known via `fetch_operator_keys`), the blast radius spans every future withdrawal/operator pair as long as an attacker can win the RBF race.

### Likelihood Explanation
The attacker needs no privileged role: any unprivileged party monitoring the mempool for payout transactions (easily identifiable by their output structure) can win the RBF race by paying a marginally higher fee, funding output 0 out of pocket. The attacker's cost is roughly the withdrawal amount plus fees (paid to the withdrawing user, not lost, since it is a real payment on their crafted tx) — this is an economic griefing/attribution-hijack, not a value-extraction attack requiring large capital beyond fronting the payout once. Feasibility is high given RBF is explicitly enabled on this transaction type and mempool visibility is inherent to Bitcoin.

### Recommendation
Bind operator attribution to something the operator actually signs, e.g., require the OP_RETURN commitment (or an operator signature over the full payout tx / a covenant restricting outputs 1 and 2) to be authenticated as part of the transaction the operator constructs, or have the aggregator/verifiers co-sign the exact payout transaction (including its OP_RETURN) via MuSig2 rather than relying on a `SinglePlusAnyoneCanPay|Single` user signature that leaves attribution malleable.
