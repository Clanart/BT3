### Title
Hookify hook executors fail open on import/parse error, allowing security-relevant operations to bypass PreToolUse/PostToolUse/Stop/UserPromptSubmit rule enforcement - (File: plugins/hookify/hooks/userpromptsubmit.py, pretooluse.py, posttooluse.py, stop.py)

### Summary
All four Hookify hook executors (`userpromptsubmit.py`, `pretooluse.py`, `posttooluse.py`, `stop.py`) wrap module import and rule evaluation in try/except blocks that, on any failure (ImportError, JSON parse error, rule-loading error, or any other exception during `main()`), print a diagnostic `systemMessage` and unconditionally `sys.exit(0)`. Because Claude Code interprets a hook's non-blocking exit/JSON output as "allow," any condition that triggers this except-path silently disables the block/deny decision that the rule engine would otherwise return, converting a would-be deny into an allow.

### Finding Description
Each hook file follows the same pattern. In `userpromptsubmit.py`: [1](#0-0) , an `ImportError` on `hookify.core.config_loader`/`hookify.core.rule_engine` results in printing an error message and exiting 0 rather than surfacing a blocking decision. The same pattern exists in `main()`: [2](#0-1) , where any exception raised while reading stdin, loading rules, or evaluating them is caught, converted into a `systemMessage`, and the process exits 0 in the `finally` block regardless of outcome. `pretooluse.py` has identical logic, explicitly commented "ALWAYS exit 0 - never block operations due to hook errors": [3](#0-2) .

The rule engine (`rule_engine.py`) is the actual enforcement mechanism that would otherwise return a blocking decision — e.g., `{"decision": "block", ...}` for Stop events or `{"hookSpecificOutput": {"permissionDecision": "deny"}, ...}` for PreToolUse/PostToolUse: [4](#0-3) . If evaluation never reaches this point — because `json.load(sys.stdin)` throws on malformed/attacker-influenced input, `load_rules()` throws while parsing a malformed `.claude/hookify.*.local.md` rule file, or the plugin's Python path resolution fails so the `hookify` package cannot be imported — the hook silently emits `{}`-equivalent allow behavior via `sys.exit(0)` instead of a deny.

An attacker able to influence content that flows into these hooks (e.g., repository-controlled rule/config files that `load_rules()` parses, or a crafted transcript/tool_input causing an unhandled exception in `_extract_field`/`_check_condition` prior to the deny branch being reached) can induce an exception in `main()` before the blocking rule is evaluated/returned, causing the hook to fall through to the generic except handler that always allows. This breaks the intended invariant that a hook whose job is to enforce a security boundary (blocking dangerous Bash commands, dangerous Edits, or dangerous Stop transcripts) must not silently downgrade to "allow" on internal failure — instead it should fail closed or otherwise ensure the protected operation is not allowed to proceed unchecked.

### Impact Explanation
If Hookify is configured to block dangerous operations (e.g., `rm -rf`, unauthorized writes, dangerous Bash commands) via rules evaluated by `RuleEngine.evaluate_rules`, any parse/import failure in the corresponding hook causes that protection to be bypassed and the underlying tool call (Bash, Edit, Write, MultiEdit) to proceed unchecked. This matches "Unauthorized local command execution that bypasses Claude Code approval or deny controls," since the hook is the mechanism substituting for/backing an approval-or-deny decision, and its failure mode is "fail open" rather than "fail closed."

### Likelihood Explanation
Triggering the except-path requires only causing an exception during hook startup or rule evaluation — e.g., a malformed `.claude/hookify.*.local.md` file (which `load_rules()` parses) or environment/path issues affecting `CLAUDE_PLUGIN_ROOT` resolution. Because rule files can be repository-controlled content (per the plugin's own design of reading `.claude/hookify.*.local.md`), a low-privilege contributor who can add/modify such a file, or any bug in the rule parser triggered by unusual but plausible content, can reliably force this fail-open behavior across any of the four events. The pattern is present in all four hook scripts, and one (`pretooluse.py`) explicitly documents it as intentional in a comment, indicating this fail-open behavior is by design rather than a one-off bug, which raises questions about whether it is a genuine vulnerability versus a known/accepted design tradeoff. I was not able to confirm from the README or other docs whether this fail-open behavior is explicitly documented/accepted as intended (the search for "fail-open"/"advisory" language matched only the code comments themselves, not design docs), so this could be an intentional design decision that a maintainer would classify as expected behavior rather than a security bug.

### Recommendation
Change the failure semantics of all four hooks so that exceptions during import or rule evaluation cause the hook to fail closed for security-relevant events (at minimum for `PreToolUse`/`PostToolUse`/`Stop` block rules), e.g., by returning a `permissionDecision: "ask"` or blocking response with a clear error message on internal failure, or by distinguishing between "no rules configured" (safe to allow) and "rules exist but could not be evaluated" (should not silently allow). At minimum, log/surface load/parse errors distinctly and avoid using a blanket `except Exception: ... sys.exit(0)` for the entire evaluation path.

### Proof of Concept
1. Unit test `test_userpromptsubmit_fail_open`: monkeypatch `hookify.core.config_loader.load_rules` to raise an exception (simulating a malformed `.claude/hookify.prompt.local.md`); provide valid stdin JSON matching a rule that would otherwise produce `{"systemMessage": ..., "hookSpecificOutput": {"permissionDecision": "deny"}}`; run `userpromptsubmit.main()`; assert exit code is 0 and stdout JSON contains only a generic `Hookify error` `systemMessage` with no `permissionDecision`/`decision` field — demonstrating the deny is lost.
2. Repeat for `pretooluse.py` with a `Bash` tool_input containing a rule-matching dangerous command (`rm -rf /`) and a forced exception in `RuleEngine.evaluate_rules` (e.g., malformed regex pattern raising outside the existing try/except in `_regex_match`, or an exception in `_extract_field`); assert exit code 0 and no `permissionDecision: deny` in output, confirming the Bash command would be allowed to execute.
3. Integration-level assertion: verify that under normal (non-error) conditions the same crafted input does produce a `deny`/`block` decision, establishing that the only difference is the injected exception, isolating the fail-open behavior as the root cause.
