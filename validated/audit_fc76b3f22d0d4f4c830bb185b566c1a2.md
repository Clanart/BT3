## Analysis

The dForce bug is a broken invariant: a cached numeric state (`currentDebt`) is trusted as authoritative even though the real underlying value (accrued debt) has silently diverged, and the code that consumes it (`afterRepayBorrow`) has no mechanism to detect or reconcile the drift — it just reverts.

The closest structural analog in GitHub Desktop is the line-index-based `DiffSelection` used for partial staging/committing, which is likewise treated as authoritative against a diff that may have silently changed by the time it's consumed.

### Title
Stale line-index diff selection can silently stage/commit unintended content on diff drift - (`app/src/lib/git/apply.ts`)

### Summary
When a user partially selects lines/hunks to commit, GitHub Desktop records the selection as **absolute line indices** into a previously rendered `ITextDiff`. When the commit is actually performed, `applyPatchToIndex` re-fetches the working directory diff fresh from git and reuses the old index-based selection against this new diff object without verifying the two diffs are the same.

### Finding Description
The UI computes selection using `hunk.unifiedDiffStart + lineIndex` as an absolute index into a diff object obtained at render time, e.g. in tests: [1](#0-0)  and in `formatPatch`, which walks `hunk.lines` and calls `file.selection.isSelected(absoluteIndex)` purely by index: [2](#0-1) .

At commit time, `applyPatchToIndex` does not reuse the diff that was shown to the user — it re-runs `getWorkingDirectoryDiff` against the current working tree and feeds the *stale* `file.selection` into `formatPatch` against this *new* diff: [3](#0-2) . There is no comparison of the old and new diff content/hunk structure, no hash check, and no re-validation that the previously computed indices still correspond to the same lines.

If the tracked file's content changes between the moment the diff is rendered (and the user picks specific lines) and the moment `_commitIncludedChanges` executes (`app/src/lib/stores/app-store.ts:3681`), the hunk boundaries and `unifiedDiffStart`/`unifiedDiffEnd` offsets shift. The same numeric indices in `DiffSelection` then silently resolve to different lines in the new diff, and `formatPatch` builds a patch from the wrong set of additions/deletions — with no error, since `formatPatch` only throws if the resulting patch is completely empty: [4](#0-3) .

This is the same class of bug as the report: a piece of state (`currentDebt` / `DiffSelection` indices) is assumed to remain valid against a moving target (accruing interest / a mutating working tree) with no reconciliation step, and the consuming code (`afterRepayBorrow` / `formatPatch`) has no way to detect the drift.

### Impact Explanation
A crafted/cloned repository can contain tooling that mutates a tracked file shortly after checkout or on focus/save events (e.g. a formatter, linter auto-fixer, generated file, or a file watcher script invoked via an editor integration or npm/yarn postinstall/husky hook that Desktop itself may trigger through hooks it intercepts). If this happens in the window between the user reviewing a diff and pressing "Commit" (which is realistic for larger diffs where the user reviews first, then scrolls back and commits), the committed content silently diverges from what the user selected and saw in the diff viewer — meeting the "silent corruption of what the user commits or pushes" impact bar. There's no execution or credential impact, but the integrity of the commit content is broken without any error or warning to the user.

### Likelihood Explanation
This requires a timing window between diff render and commit rather than a single deterministic click, and Desktop generally re-renders the diff on file-system changes, which would somewhat mitigate (but not fully eliminate, given async debouncing) the race. It is not trivially triggerable in one interaction, but it doesn't need local/admin access or leaked credentials — it only needs a repository capable of writing to its own working tree at an opportune time (via a hook or background tool), which is within the "attacker controls a cloned/fetched repository" threat model.

### Recommendation
Before calling `formatPatch`/`applyPatchToIndex`, re-validate that the diff being staged matches the diff the selection was computed against (e.g., compare the diff's raw hunk headers/content hash, or recompute the selection against the freshly fetched diff by content rather than raw index). If a mismatch is detected, abort the partial-stage operation and force the UI to refresh the diff and require the user to re-select lines, rather than silently proceeding with an index-based selection against different content.

### Proof of Concept
1. Attacker distributes/clones a repository with a script wired to a git hook Desktop intercepts (e.g. `post-checkout`) or a file-watcher outside Desktop's own file-watch debounce window, configured to append/change lines in a tracked file a few seconds after any write.
2. User opens a modified file's diff, selects only specific lines/hunks to include in the commit (partial stage), and pauses (e.g. to write the commit message).
3. Meanwhile, the working tree file's content mutates, shifting subsequent hunk boundaries.
4. User clicks "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` [5](#0-4)  and applies the old `DiffSelection` indices to the new hunk layout in `formatPatch` [2](#0-1) .
5. The resulting commit contains different lines than the ones the user visually reviewed and selected, with no error surfaced.
