Based on my investigation, I found a concrete analog. `checkRun.htmlUrl` (from the GitHub Checks API `html_url` field) flows unvalidated into `Dispatcher.openInBrowser()` → `shell.openExternal()`, and the main-process IPC handler for `open-external` performs no protocol allowlisting before calling Electron's `shell.openExternal`.

### Title
Unvalidated Check-Run `html_url` from CI/Checks API reaches `shell.openExternal` with no protocol allowlist - (File: `app/src/main-process/main.ts`, `app/src/ui/notifications/pull-request-checks-failed.tsx`, `app/src/ui/check-runs/ci-check-run-popover.tsx`)

### Summary
The `open-external` IPC handler in the main process forwards any string it receives straight to Electron's `shell.openExternal`, only logging (not restricting) when the value starts with `http(s)://` [1](#0-0) . Several UI code paths feed a check run's `htmlUrl` — a field taken verbatim from the GitHub Checks/Statuses API (`checkRun.html_url`) — into `dispatcher.openInBrowser(url)` without any scheme or host validation [2](#0-1) [3](#0-2) [4](#0-3) . This mirrors the Votium report's core flaw: a value originating from an untrusted/external source (there, arbitrary `swapTarget`/`swapCallData`; here, an attacker-influenced `html_url`/`target_url`) is handed to a powerful, unguarded sink (`shell.openExternal`) without validating that it points where it's supposed to (0x entrypoint vs. GitHub's checks UI).

### Finding Description
Check runs and legacy commit statuses on a pull request are populated by third-party GitHub Apps/Actions and can set an arbitrary `target_url`/`html_url` for the check (this is standard, unauthenticated-by-Desktop content coming from the Checks/Statuses API of the PR's base or head repo, including PRs from forks). GitHub Desktop's `LinkButton`/CI check UI (`CICheckRunListItem`, `CICheckRunStepListHeader`, `CICheckRunNoStepItem`, `pull-request-checks-failed.tsx`, `ci-check-run-popover.tsx`) surfaces a "View on GitHub"/"View check details" button that calls `dispatcher.openInBrowser(url)` using that value directly [2](#0-1) . `Dispatcher.openInBrowser` in turn calls `AppStore._openInBrowser`, which is `shell.openExternal(url)` [5](#0-4) , which is proxied to the main process's `open-external` IPC handler [1](#0-0) . That handler does not restrict the scheme to `http(s)` — the `http://`/`https://` check only controls a log line, and any other URL (e.g. `file://`, a Windows UNC path, or a registered custom URI scheme like `ms-excel:`, `search-ms:`, etc.) is passed through to Electron's `shell.openExternal` unchanged.

Notably, other parts of the codebase *do* guard against this class of bug: `SandboxedMarkdown`'s link interceptor explicitly checks `/^https?:/.test(a.protocol)` before invoking `onMarkdownLinkClicked` [6](#0-5) , and the BYOK URL validator explicitly rejects `file://`/`javascript:` schemes [7](#0-6) . The check-run "view externally" path has no equivalent guard, so it's an inconsistent trust boundary — the same class of "arbitrary target, no destination validation" the external report flags for the 0x swap call.

### Impact Explanation
If a malicious actor controls (or compromises) a GitHub App/Action that posts check runs/statuses on a repository or PR the victim views in Desktop (including forked-PR checks), they can set `html_url`/`target_url` to a non-`https` URI. Depending on OS URL-handler registrations, `shell.openExternal` on such a value can lead to opening/executing a local file, traversing to attacker-controlled local resources via `file://`, or invoking other registered protocol handlers on the victim's machine — all triggered by the victim clicking a legitimate-looking "View on GitHub"/"View check details" button inside Desktop's own UI, with no additional confirmation of the destination.

### Likelihood Explanation
The user only has to click the standard "View check details" or "View on GitHub" action on a failing/any check for a PR — an action Desktop actively invites the user to take (e.g., in the "Pull Request Checks Failed" dialog). No local access, malware, or leaked credentials are needed; the attacker only needs the ability to report a check/status with a custom `target_url`, which is available to any GitHub App or Action with `statuses`/`checks` write access to the repo, including on many public repos accepting external contributions.

### Recommendation
Before calling `shell.openExternal`/`dispatcher.openInBrowser` for `checkRun.htmlUrl` (and any other API-derived URL fields reaching this sink), validate that the URL parses successfully and has an `https:` (or `http:`) scheme — mirroring the existing guard already implemented in `sandboxed-markdown.tsx`'s `setupLinkInterceptor`. Additionally, harden the `open-external` IPC handler in `main.ts` itself to reject non-`http(s)` schemes centrally, so every call path is protected regardless of caller.

### Proof of Concept
1. As the owner of a GitHub App/Action with check-run write access to a repository, create a check run (or push a commit) whose `details_url`/`target_url` is set to `file:///C:/Windows/System32/calc.exe` (or, on other platforms, a locally-resolvable path/URI-scheme of interest) instead of an `https://` URL.
2. In GitHub Desktop, open that repository's pull request and open the "Checks" popover or trigger the "Checks Failed" notification dialog for that commit.
3. Click "View check details" / "View on GitHub" for the malicious check.
4. Trace the call: `CICheckRunListItem.onViewCheckExternally` → `ci-check-run-popover.tsx:onViewCheckDetails` (`checkRun.htmlUrl`) [3](#0-2)  → `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser` [5](#0-4)  → IPC `open-external` handler, which performs no scheme validation and calls `shell.openExternal(path)` directly [1](#0-0) .
