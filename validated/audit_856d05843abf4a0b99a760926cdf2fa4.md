## Title
Silent remote-URL rewrite based on trusted GitHub API `clone_url` with no owner-identity re-verification and no user confirmation - (`app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically re-fetches repository metadata from the GitHub API (`api.fetchRepository`) and, if the API's `clone_url` no longer matches the locally configured `origin` remote, silently rewrites the local git remote URL to the new value via `gitStore.setRemoteURL`, with no user prompt. [1](#0-0) [2](#0-1)  This mirrors the Monero bug class: a client blindly trusts a value supplied by a remote/API endpoint (analogous to `get_outs.bin`'s bogus public keys) and uses it to silently alter security-relevant client state (there: mixin selection; here: the push/fetch destination), without adequately validating the response or informing the user.

### Finding Description
The flow is:
1. `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` and, if the local `Repository` already has an associated `gitHubRepository`, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`. [3](#0-2) 
2. `updateRemoteUrl` compares the current `origin` remote URL to `apiRepo.clone_url`. If the *protocol* matches and the *previously stored* `gitHubRepository.cloneURL` still matches the current remote (i.e., the user hasn't manually customized the remote), and the new `clone_url` differs from the current remote, it calls `gitStore.setRemoteURL(...)` unconditionally — no dialog, no user confirmation. [4](#0-3) 
3. `setRemoteURL` runs `git remote set-url <name> <url>` directly against the value taken from the API response. [5](#0-4) [6](#0-5) 
4. The only equivalence check performed, `urlMatchesRemote`/`urlsMatch`, is a **string-parsing comparison of owner/name/hostname extracted from the URL itself** — it never validates the new URL against a stable repository identifier (e.g., the GitHub repository's numeric `id`). [7](#0-6)  There's no cross-check that `apiRepo.id` (or `node_id`) is the same repository object previously associated with this local clone.

Because `owner`/`name` are the only inputs used to fetch the repository (`api.fetchRepository(owner, name)`), the same design that allows Desktop to legitimately follow GitHub repository renames also means that **whatever `clone_url` string the API endpoint returns for that owner/name is trusted and written into the user's `.git/config`**, as long as it "looks like" a differently-hostnamed/owned repo (the code explicitly permits `urlsMatch` to be false — that's the trigger condition for the rewrite) while keeping the same URL scheme (http/https or ssh consistently). There is no verification tying the new `clone_url` back to the same underlying repository identity (e.g. via GitHub's stable numeric repo `id`), and no confirmation dialog comparable to the one that exists for the analogous "upstream remote mismatch" case (`UpstreamAlreadyExists` dialog, which does prompt the user). [8](#0-7) 

### Impact Explanation
If the API endpoint the user's account is configured against returns an attacker-influenced or corrupted `clone_url` for the `owner/name` pair Desktop is tracking (e.g., a compromised/malicious GitHub Enterprise Server the user authenticated against, a MITM'd/compromised API response, or a crafted response an attacker controls through server-side repository configuration), Desktop will silently repoint the user's `origin` remote to that URL. Subsequent pushes/fetches performed by the user would then be silently redirected — this is "silent corruption of what the user commits or pushes" as defined in the Valid Impact criteria: the user believes they are pushing to their known repository but Desktop has quietly changed the destination based on untrusted server data, with no warning shown comparable to `UntrustedCertificate`/`UpstreamAlreadyExists` dialogs used elsewhere in the same codebase for similar remote-mutation actions.

### Likelihood Explanation
This path runs automatically during routine background repository refreshes (`repositoryWithRefreshedGitHubRepository`, triggered from `_selectRepositoryRefreshTasks` and account-change refreshes) — no unusual user action is required beyond having the app open with the repository selected. [9](#0-8)  The attacker precondition ("attacker controls a GitHub API object") is explicitly listed as valid impact scope. The main uncertainty is exactly how an attacker would get their bogus `clone_url` served for a specific `owner/name` pair the victim already trusts (e.g. via a compromised GHES instance, a repository-rename race, or a server bug) — this could not be fully confirmed from local code alone since it depends on server-side behavior, so likelihood should be treated as Medium pending further investigation of concrete delivery vectors.

### Recommendation
- Before rewriting the local remote URL, validate that the new `clone_url` refers to the same repository identity as before (e.g., compare the GitHub repository's stable numeric `id`/`node_id` rather than only comparing the URL's parsed owner/name/hostname).
- Prompt the user for confirmation before silently mutating `origin`'s URL, similar to the existing `UpstreamAlreadyExists` dialog pattern, rather than performing the rewrite unconditionally in `updateRemoteUrl`.
- Log/audit remote URL rewrites so users can detect unexpected changes.

### Proof of Concept
1. User has a repository configured with `gitHubRepository.cloneURL = https://github.com/my-user/my-repo` and local `origin = https://github.com/my-user/my-repo`.
2. During a routine background refresh, `api.fetchRepository('my-user', 'my-repo')` returns (from a compromised/malicious API endpoint) `clone_url: https://github.com/my-user/my-updated-repo` (or any other owner/repo with a matching protocol).
3. `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (user never manually changed remote), and `urlsMatch === false` (new URL differs) — it calls `gitStore.setRemoteURL('origin', 'https://github.com/my-user/my-updated-repo')` with no prompt. This exact scenario is already exercised (with a benign, non-malicious rename) in the existing unit test. [10](#0-9) 
4. The user's next `git push`/`git fetch` silently targets the attacker-influenced remote.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

/**
 * The dialog shown when a repository is a fork but its upstream remote doesn't
 * point to the parent repository.
 */
export class UpstreamAlreadyExists extends React.Component<IUpstreamAlreadyExistsProps> {
  public render() {
    const name = this.props.repository.name
    const gitHubRepository = forceUnwrap(
      'A repository must have a GitHub repository to add an upstream remote',
      this.props.repository.gitHubRepository
    )
    const parent = forceUnwrap(
      'A repository must have a parent repository to add an upstream remote',
      gitHubRepository.parent
    )

    const existingURL = this.props.existingRemote.url

    return (
      <Dialog
        title={
          __DARWIN__ ? 'Upstream Already Exists' : 'Upstream already exists'

        onDismissed={this.props.onDismissed}
        onSubmit={this.onUpdate}

            </li>
            <li>

            </li>
          </ul>

            cancelButtonText="Ignore"
            onCancelButtonClick={this.onIgnore}

  }
