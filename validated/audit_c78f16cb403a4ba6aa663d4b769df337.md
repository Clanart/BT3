### Title
Missing length check on `Interpolation::Constant` coefficients enables index out-of-bounds panic in `ThresholdKeys` - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the Omni `GetMultiProof()` out-of-bounds panic caused by an unchecked `siblingIndex`, `Interpolation::Constant::interpolation_factor` in `crypto/dkg/src/lib.rs` indexes the coefficient vector by participant index (`c[usize::from(u16::from(i) - 1)]`) without ever verifying that the coefficient vector is long enough to cover the participant set. `ThresholdKeys::new` only checks that `t == n` for Constant interpolation — it never validates `c.len() == t`/`n`. The same unchecked index is hit again inside `ThresholdKeys::view` when computing per-participant verification shares for the signing set.

### Finding Description
`interpolation_factor` computes `c[usize::from(u16::from(i) - 1)]` for `i` in `1..=t` (during `ThresholdKeys::new` at line 378) and for `i` over the entire `included` signing set (during `ThresholdKeys::view` at line 505, for `i` up to `n`). [1](#0-0) [2](#0-1) [3](#0-2) 

The only invariant enforced is `params.t() == params.n()`; the length of the `Constant(Vec<F>)` coefficient list is unconstrained. Notably, `musig()` (crypto/dkg/musig/src/lib.rs:155-160) constructs `Interpolation::Constant(binding_factors)` where the vector length is derived from an attacker-influenced `keys` list, and `ThresholdKeys::new` is a public constructor consumed by downstream crates (promote/recovery/dealer flows) that build `ThresholdKeys` from share data supplied by other DKG participants. If a short (e.g., empty) coefficient vector is combined with `t > c.len()` participants, `interpolation_factor` indexes out of bounds and the process panics — the same crash class as the audited `GetMultiProof()` issue, where a computed index exceeds the container size because a length/structure check was omitted.

### Impact Explanation
A runtime index-out-of-bounds panic in any node/process constructing or using `ThresholdKeys` built from a malformed `Interpolation::Constant`. If reached while processing DKG-related data influenced by another participant (promotion, recovery, or MuSig-style aggregation paths that feed participant-controlled material into `ThresholdKeys::new`), an unprivileged counterparty can crash the victim's signer — a denial of service on the threshold-signing node, matching the Medium severity of the audited analog. Note: `ThresholdKeys::read` is safe in isolation since it always reads exactly `n` scalars for Constant interpolation; the vulnerability is the missing invariant on the public constructor/`view` path, which other in-scope crates rely on.

### Likelihood Explanation
Low-to-moderate. Exploitation requires a caller to construct `ThresholdKeys` with `Interpolation::Constant` whose coefficient count is smaller than `t`/`n`, which honest `musig()` and `ThresholdKeys::read` never produce — exactly paralleling the Omni report's observation that `MakeTree()` always produces well-formed trees but malformed inputs can arrive via other paths (promote/recovery flows reconstructing keys from peer-supplied share polynomials). The panic then requires only indexing a participant `i > c.len()`.

### Recommendation
- In `ThresholdKeys::new`, for `Interpolation::Constant(c)`, enforce `c.len() == usize::from(params.t())` (and error with a new `DkgError` variant such as `IncorrectAmountOfInterpolationCoefficients`) before computing `group_key`.
- Alternatively/additionally, make `interpolation_factor` return `Option<F>`/`Result` instead of indexing directly, and propagate the error — mirroring the recommended `siblingIndex` bounds check in the Omni report.
- Audit `promote`, `recovery`, `dealer`, and `musig` call sites that assemble `Interpolation::Constant` from peer-derived data to confirm they cannot yield a short vector.

### Proof of Concept
```rust
use std::collections::HashMap;
use zeroize::Zeroizing;
use ciphersuite::{group::ff::Field, Ciphersuite, Secp256k1};
use dkg::{Participant, ThresholdParams, ThresholdKeys, Interpolation};

fn panic_threshold_keys_new() {
    // t = n = 2, but Constant interpolation carries only 1 coefficient.
    let params = ThresholdParams::new(2, 2, Participant::new(1).unwrap()).unwrap();

    let interpolation = Interpolation::Constant(vec![<Secp256k1 as Ciphersuite>::F::ONE]);
    // Only one coefficient for participants 1..=2 -> indexing c[1] panics.

    let mut shares = HashMap::new();
    shares.insert(Participant::new(1).unwrap(), Secp256k1::generator());
    shares.insert(Participant::new(2).unwrap(), Secp256k1::generator());

    // Panic: index out of bounds at crypto/dkg/src/lib.rs:228
    // when ThresholdKeys::new evaluates interpolation_factor(Participant(2), [1,2]).
    let _ = ThresholdKeys::<Secp256k1>::new(
        params,
        interpolation,
        Zeroizing::new(<Secp256k1 as Ciphersuite>::F::ONE),
        shares,
    );
}
```

The panic is triggered at `Interpolation::interpolation_factor` (`crypto/dkg/src/lib.rs:228`) because `c[usize::from(u16::from(Participant(2)) - 1)] = c[1]` exceeds `c.len() == 1`, exactly as the audited `GetMultiProof()` crash computed `siblingIndex = 2` on a tree of size 2.

impl<F: Zeroize + PrimeField> Interpolation<F> {
  /// The interpolation factor for this participant, within this signing set.
  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
