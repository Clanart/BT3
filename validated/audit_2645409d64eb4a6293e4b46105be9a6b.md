### Title
`SignableTransaction` computes funds/change/fee from attacker-controlled `TxOut.value` in `ReceivedOutput::read`, signing transactions whose prevout amounts do not match the chain — (`networks/bitcoin/src/wallet/mod.rs`, `networks/bitcoin/src/wallet/send.rs`)

### Summary
Analogous to the report's "collateral computed from a manipulable spot value", `SignableTransaction::new` treats the `value` field of each `ReceivedOutput` as ground truth when summing inputs, deciding whether funds are sufficient, sizing the change output, and pinning the fee. `ReceivedOutput::read` (an explicitly untrusted-bytes entry point) accepts an arbitrary `offset`, an arbitrary `TxOut` (including `value`), and an arbitrary `OutPoint` with no consistency check. The only validation later performed in `SignableTransaction::multisig` is that the offset-derived key's `p2tr` script equals `prevouts[i].script_pubkey` — the `value` is never checked against anything. The serialized prevouts are then committed into each input's BIP-341 sighash via `Prevouts::All`, so the produced signatures are over attacker-chosen amounts.

### Finding Description
- `ReceivedOutput::read` deserializes `offset` (`Secp256k1::read_F`), `TxOut::consensus_decode`, and `OutPoint::consensus_decode` from untrusted bytes and stores them verbatim (networks/bitcoin/src/wallet/mod.rs:122-133).
- `SignableTransaction::new` computes `input_sat` as `sum(input.output.value)` from those attacker-supplied values (send.rs:175) and uses it for the `NotEnoughFunds` gate (send.rs:215-221) and for the change output amount `input_sat - payment_sat - fee_with_change` (send.rs:228-234).
- `multisig` validates only `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey`; nothing ties `prevouts[i].value` to the real UTXO (send.rs:276-279).
- `TransactionSignMachine::sign` builds `Prevouts::All(&self.tx.prevouts)` and signs `taproot_key_spend_signature_hash` per input (send.rs:373-390), so the fabricated value is committed into the signature message.

Attack: a party able to feed bytes to `ReceivedOutput::read` supplies an output whose `script_pubkey`/`offset` correspond to a real Serai-owned output (so `multisig` passes) but with an inflated `value`. The threshold then produces a validly-signed transaction that consensus will reject (prevout amounts committed in the sighash don't match the UTXO set), or — if the platform uses the claimed `value` for accounting/change — pays out a change output larger than the real inputs. Either way the group's spend is computed from a manipulable "price" (the claimed input amount), exactly the spot-price-dependence bug class.

### Impact Explanation
The FROST group is induced to sign a transaction committing to false prevout amounts: the signed transaction is unbroadcastable (per-input sighash commits to the false `TxOut`), burning a nonce/preprocess session and halting the spend. Where the claimed value drives downstream accounting (change sizing, fee reporting via `fee()`), incorrect values propagate into signed outputs. This is a concrete signing-of-unintended-message outcome reachable purely through untrusted `read` bytes.

### Likelihood Explanation
Requires the attacker to reach the `ReceivedOutput::read` path (e.g., supplying outputs to a signer/processor) rather than only sending on-chain transactions, and needs a matching script_pubkey — so it is not reachable by an arbitrary Bitcoin sender alone. Medium-to-low likelihood within the permitted attacker model; impact is primarily invalid-signature/DoS rather than direct theft.

### Recommendation
Like the report's "use TWAP instead of spot", bind the value to a trusted source: have `ReceivedOutput` carry only the `OutPoint` and fetch/verify the `TxOut` against the confirmed chain state before signing, or verify the full transaction proving the output. At minimum, document that `ReceivedOutput` bytes must only originate from the node's own `Scanner::scan_transaction` results and never from peer-supplied data.

### Proof of Concept
1. Observe a legitimate `ReceivedOutput` for a group-owned output: `(offset o, TxOut{value: v, script: s}, outpoint p)` where `s = p2tr(key + o·G)`.
2. Craft `ReceivedOutput'` via `ReceivedOutput::read` bytes with the same `o`, `s`, `p` but `value: v' >> v`.
3. `SignableTransaction::new(vec![ReceivedOutput'], payments, change, ...)` passes `multisig` (script matches) and computes `input_sat = v'`, producing a change output of `v' - payments - fee`.
4. `sign` commits `Prevouts::All([TxOut{value: v', ...}])` into `taproot_key_spend_signature_hash`; `complete` yields a signed `Transaction` that Bitcoin consensus rejects because the prevout descriptor in the sighash does not match the actual UTXO — an unintended message signed by the threshold group.
