## Analysis

The yAxis `addToken` bug is a **missing-uniqueness-check on a key→object mapping**: adding the same token twice (or a token to two vaults) is accepted without validation, silently corrupting the `vaults[_token]` pointer and the vault's token array.

The closest verified analog in this GitHub Desktop codebase is in `RepositoriesStore._upsertGitHubRepository`, which persists the local `GitHubRepository` DB record used to bind a local clone to permissions, branch-protection state, and pull-request data.

### Title
Local `GitHubRepository` records are keyed by `[ownerID + name]` instead of GitHub's immutable repository ID, allowing repo-identity confusion on rename/recreate - ([File: app/src/lib/stores/repositories-store.ts])

### Summary
`_upsertGitHubRepository` looks up an "existing" repository row solely by the tuple `[ownerID, name]`: [1](#0-0) 

and if found, it **overwrites** that row in place (`...(existingRepo?.id !== undefined && { id: existingRepo.id })`) rather than creating a new record keyed by GitHub's actual numeric repository id: [2](#0-1) [3](#0-2) 

The lookup key never uses the API repository's real GitHub `id`; it is derived purely from the owner login and the repository `name`, both of which are mutable strings on GitHub (repos can be renamed, deleted, and a *different* repository can later be created under the same owner/name).

### Finding Description
Every local `Repository` is linked to a `GitHubRepository` DB row via `gitHubRepositoryID` (a foreign key to this table), and that row is looked up/created by `[ownerID+name]`. This value is written whenever a repository is opened, refreshed, or resolved via a PR/clone-URL: [4](#0-3)  — `repositoryWithRefreshedGitHubRepository` fetches an API repo based only on the parsed `owner`/`name` of the current remote and calls `upsertGitHubRepository(endpoint, apiRepo)`. [5](#0-4)  — `matchGitHubRepository` derives `owner`/`name` purely by string-parsing the git remote URL; it performs no verification that this owner/name still refers to the same underlying repository the user originally added.

Because the DB key is `[ownerID+name]` and not GitHub's immutable repository id, if a `name` is freed up (the original repo is renamed or deleted) and later reused by *any* different repository under the same owner (repo-name squatting), the next refresh cycle will match the *stale* `existingRepo` row for that name and silently overwrite its `cloneURL`, `htmlURL`, `parentID`, and `permissions` fields: [2](#0-1) 

Every local `Repository` whose `gitHubRepositoryID` still points at that row (comment on this pattern even acknowledges cross-repo bleed risk for the `parentID` field): [6](#0-5) 

now transparently inherits the identity, remote URL, and cached permissions of the new/unrelated repository, without any check that the numeric GitHub id is unchanged. This is structurally identical to the yAxis bug: a mutable, attacker-influenceable string ("name") is used as the sole uniqueness key for a mapping whose value drives trust decisions (branch protection lookups keyed by `dbID`, PR association via `findRepositoriesForGitHubRepository` matching on `dbID`), with no re-validation against the stable identifier.

### Impact Explanation
Consequences of the pointer being silently repointed:
- `updateRemoteUrl`/`_convertRepositoryToFork` and PR association (`findRepositoriesForGitHubRepository`, keyed on `dbID`) will now treat the local clone as belonging to whatever repository currently occupies `owner/name`, mixing in that repo's PR/branch data: [7](#0-6) 
- Branch protection cache entries keyed by `dbID` are not invalidated when the underlying repository identity silently changes: [8](#0-7) 
- Because `matchGitHubRepository`/`repositoryWithRefreshedGitHubRepository` re-derive the association purely from the remote URL string on every refresh (not from a stored immutable id), a git remote URL is effectively an attacker-controllable input for this lookup.

### Likelihood Explanation
This requires a specific but realistic sequence: original repo renamed/deleted, name later reused by another repository (owner-controlled or via github "dangling name" reuse), and the user still has a stale local remote URL. Desktop's own design doc/TODO already flags related risk ("We currently never clear GitHub repository associations"): [9](#0-8) 
This is a data-integrity/identity-confusion issue rather than a trivially triggerable RCE, so likelihood is moderate, gated on GitHub-side name reuse and a refresh occurring while the local remote still targets the old owner/name.

### Recommendation
Key `IDatabaseGitHubRepository` lookups and dedup by GitHub's immutable numeric `id` (available on `IAPIRepository`/`IAPIFullRepository`) rather than `[ownerID+name]`, and additionally verify that a repository's numeric id matches the previously stored id before reusing/overwriting an existing DB row; if it doesn't match, create a new record instead of merging into the old one.

### Proof of Concept
Not independently executable from this analysis — confirming the exact reuse-of-freed-name scenario against live GitHub semantics, and tracing every downstream consumer of `dbID` that could be poisoned, would require running the app end-to-end (cloning, renaming/recreating a fixture repo under a controlled test GitHub org, and observing DB state). This is noted as unverified beyond the static code evidence cited above.

  public async updateBranchProtections(
    gitHubRepository: GitHubRepository,
    protectedBranches: ReadonlyArray<IAPIBranch>
  ): Promise<void> {
    const dbID = gitHubRepository.dbID

    await this.db.transaction('rw', this.db.protectedBranches, async () => {
      // This update flow is organized into two stages:
      //
      // - update the in-memory cache
      // - update the underlying database state
      //
      // This should ensure any stale values are not being used, and avoids
      // the need to query the database while the results are in memory.

      const prefix = getKeyPrefix(dbID)

      for (const key of this.protectionEnabledForBranchCache.keys()) {
        // invalidate any cached entries belonging to this repository
        if (key.startsWith(prefix)) {
          this.protectionEnabledForBranchCache.delete(key)
        }
      }

      const branchRecords = protectedBranches.map<IDatabaseProtectedBranch>(
        b => ({ repoId: dbID, name: b.name })
      )

      // update cached values to avoid database lookup
      for (const item of branchRecords) {
        const key = getKey(dbID, item.name)
        this.protectionEnabledForBranchCache.set(key, true)
      }

      await this.db.protectedBranches.where('repoId').equals(dbID).delete()

      const protectionsFound = branchRecords.length > 0
      this.branchProtectionSettingsFoundCache.set(dbID, protectionsFound)

      if (branchRecords.length > 0) {
        await this.db.protectedBranches.bulkAdd(branchRecords)
      }
    })

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
