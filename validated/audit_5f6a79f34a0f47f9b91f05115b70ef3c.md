## Title
Malformed commit body with embedded NUL byte corrupts `createLogParser` field alignment, misattributing commit SHAs/bodies/parents across commits - (File: `app/src/lib/git/git-delimiter-parser.ts`)

### Summary
`createLogParser` builds `git log` format strings by joining requested fields with the literal placeholder `%x00` and passes `-z` to terminate each record with a NUL byte as well [1](#0-0) . Its `parse()` function then splits the raw output on every `\0` byte and re-groups the flat array into fixed-size chunks of `keys.length`, assuming there are exactly N NUL-delimited fields per commit record [2](#0-1) . `getCommits()` in `app/src/lib/git/log.ts` uses this parser with 9 fields, including `%b` (commit body) [3](#0-2) . Git's object format does not forbid raw `0x00` bytes inside a commit message — the commit message region is a length-delimited byte blob, not a NUL-terminated string, and `git fsck` only *warns* (does not error/reject) on `nulInCommit`. This is not gated by `transfer.fsckObjects`/`fetch.fsckObjects` in default configurations, so a commit crafted via low-level plumbing (`hash-object`/`mktree`/direct pack construction) with a raw `0x00` inside `%b` content can be pushed to a remote and fetched/cloned by a victim without rejection.

### Finding Description
When `%b` expands to content containing a raw `0x00` byte, `git log -z --format=...` emits that byte verbatim into the output stream. Because `parse()` treats every `\0` as an equally-weighted field boundary (it has no way to distinguish an intentional `%x00` field separator, the `-z` record terminator, and an attacker-injected literal NUL inside a field's content), an extra NUL inside the body field splits that single field into two array records. Since the loop advances strictly by `i += keys.length` [4](#0-3) , this off-by-one shift is never resent — every subsequent field position for the corrupted commit, and every commit parsed after it in the same invocation, is now read from the wrong offset. Concretely, with the 9-field layout `sha, shortSha, summary, body, author, committer, parents, trailers, refs` used in `getCommits` [3](#0-2) , a single injected NUL in one commit's body causes: that commit's own `author`/`committer`/`parents`/`trailers`/`refs` to be read from the next commit's data, and every following commit's `sha`, `summary`, `body`, and `parents` to be shifted by one field, silently mixing data between unrelated commits. The resulting `Commit` objects are built directly from these misaligned values with no sanity check on `sha` format/length or `parentSHAs` [5](#0-4) .

### Impact Explanation
This corrupts the in-memory commit graph that drives the History view, commit dialog, cherry-pick, and reset flows in GitHub Desktop, since these features trust `commit.sha` and `commit.parentSHAs` as returned by `getCommits`/`getCommit`. A user could see one commit's message/body attributed to a different SHA, or an incorrect parent chain, potentially causing a reset, cherry-pick, or diff view to target the wrong commit than what's displayed — a silent misrepresentation of what will be checked out/reset/cherry-picked, matching the "Scope" description in the question. It does not directly cause code execution or credential leakage, so the impact is bounded to UI/data integrity corruption for git history metadata.

### Likelihood Explanation
Requires the attacker to control repository content the victim clones or fetches, and to inject a raw NUL byte into a commit's message body using low-level plumbing (this is straightforward, doesn't require compromising the victim, and git's default fsck behavior does not reject it). No user interaction beyond a normal clone/fetch and opening the History view is needed, which is consistent with the accepted threat model ("attacker controls a cloned/fetched repository"). No existing check in `git-delimiter-parser.ts` or `log.ts` filters or escapes NUL characters inside field values before or after parsing.

### Recommendation
Sanitize/validate parsed fields after `createLogParser.parse()` (e.g., reject or strip any residual literal NUL bytes that shouldn't appear given the expected `-z`/`%x00` framing), or use a self-synchronizing separator scheme that can detect and recover from an unexpected extra delimiter (e.g., validate that the expected number of total NUL-delimited records is an exact multiple of `keys.length`, and if not, fail closed with an error rather than silently misaligning data). At minimum, `Commit`'s constructor should validate that `sha` matches a 40-hex-character pattern and log/reject otherwise, preventing corrupted records from silently propagating into cherry-pick/reset UI flows.

### Proof of Concept
1. Using low-level git plumbing, craft a commit object whose message body contains a literal `0x00` byte, e.g.:
   ```
   printf 'tree <tree-sha>\nparent <parent-sha>\nauthor A <a@a> 0 +0000\ncommitter A <a@a> 0 +0000\n\nSummary\n\nBefore\x00After' | git hash-object -w -t commit --stdin
   ```
   Update a ref to point at this commit, then push/serve this repo for the victim to clone/fetch.
2. In the victim's checkout, call `getCommits(repository)` from `app/src/lib/git/log.ts`.
3. Assert on the returned array: the commit immediately following the malicious commit will have `commit.sha`/`commit.summary` mismatched against `git log --format=%H%x09%s` output for the same range (fields shifted by one), demonstrating the sha-to-summary/body/parents misalignment described.

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }
