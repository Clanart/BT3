### Title
`SignableTransaction::new` computes `needed_fee` and the minimum-relay-fee check on a transaction that omits the OP_RETURN data output, underpaying the intended fee rate and potentially producing an unrelayable transaction (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` builds `tx_outs` including an `OP_RETURN` output carrying up to 80 bytes of attacker-influenced `data`, but then calculates transaction weight/vbytes via `calculate_weight_vbytes(tx_ins.len(), payments, None)`, which reconstructs a model transaction from `payments` only — the data output is never included. The resulting `needed_fee` and the `DEFAULT_MIN_RELAY_TX_FEE` floor check are therefore computed against a smaller transaction than the one actually signed and broadcast.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- The OP_RETURN output is pushed into `tx_outs` before the size calculation:
  - `send.rs:194-202` — `tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })`
- The weight/vbytes used for `needed_fee` and for the `TooLowFee` minimum-relay check is derived from a *different* transaction that contains only `tx_ins` and `payments` (and optionally `change`), with no data output:
  - `send.rs:204` — `let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);`
  - `send.rs:62-99` — `calculate_weight_vbytes` builds the model `Transaction` from `inputs`, `payments`, and `change` only.
  - `send.rs:206-213` — `needed_fee = fee_per_vbyte * vbytes` and the `DEFAULT_MIN_RELAY_TX_FEE` comparison both use the under-sized `vbytes`.
  - `send.rs:225-227` — the same omission repeats in `fee_with_change` when a change output is present.

A P2TR output carrying an 80-byte `OP_RETURN` adds roughly 9 (output overhead) + 1 (`OP_RETURN`) + 1–2 (push opcode) + 80 (data) ≈ 90+ serialized bytes that are entirely absent from the fee model. The broadcast transaction's true vsize is larger than `vbytes`, so:

1. `fee()` (= `sum(inputs) − sum(outputs)`) equals `needed_fee`, which corresponds to a *lower* effective sat/vbyte rate than the caller-requested `fee_per_vbyte`.
2. The `TooLowFee` guard can pass (e.g., `fee_per_vbyte` set exactly at the minimum relay rate) while the *actual* transaction's feerate falls below `DEFAULT_MIN_RELAY_TX_FEE`, causing relay rejection by standard Bitcoin nodes.

The `data` payload is reachable from untrusted network inputs in the production path: OutInstructions/withdrawal data is serialized into this field by the processor (`processor/src/networks/bitcoin.rs`), and payment destinations/amounts are user-controlled, so the discrepancy is triggered by public inputs, not integrator misuse alone.

### Impact Explanation
A transaction produced by `TransactionMachine` signing can be silently below the requested fee rate, and at boundary fee rates can be outright rejected by peer relay policy while the processor believes a correctly-priced transaction was broadcast. Funds are not stolen, but outbound transfers can be stuck: the threshold-signed transaction commits to all inputs via `Prevouts::All` (`send.rs:375`) and `TapSighashType::Default`, so the signatures cannot be re-applied to a corrected transaction — recovery requires a fresh signing round, and any consumed-coin bookkeeping that assumed broadcast success leaves the funds effectively frozen, mirroring the "deposits accepted, withdrawals frozen" shape of the reference incident. Rated Medium: concrete correctness bug on a reachable path, impact is fund liveness rather than direct theft.

### Likelihood Explanation
Triggered whenever `data` is non-empty — every OutInstruction-carrying Bitcoin transaction goes through this path. The relay-rejection case additionally requires `fee_per_vbyte` near the minimum; the fee-rate underpayment case occurs for any non-empty `data` regardless of fee rate.

### Recommendation
Include the `OP_RETURN` output (and its real `data` length) in the model transaction inside `calculate_weight_vbytes` — e.g., pass the already-constructed `tx_outs` (or append a `TxOut` with the real `ScriptBuf::new_op_return(data)`), so `weight`, `vbytes`, `needed_fee`, `fee_with_change`, and the `TooLowFee` check all reflect the transaction that will actually be signed.

### Proof of Concept
Conceptual, against `send.rs`:

```rust
// inputs: one ReceivedOutput of value V; payments: [(script, P)]; change: None
let data = Some(vec![0u8; 80]);
let st = SignableTransaction::new(inputs, &payments, None, data.clone(), fee_per_vbyte).unwrap();

// st.tx contains an extra ~90-byte OP_RETURN output that was never counted:
// model vbytes  = size(tx without OP_RETURN output)
// actual vsize  = size(tx with OP_RETURN output)  > model vbytes
// effective rate = needed_fee / actual_vsize < fee_per_vbyte

// With fee_per_vbyte == 1 (== DEFAULT_MIN_RELAY_TX_FEE at 1000 sat/kvB granularity),
// the TooLowFee check passes on the model, while the real tx's rate < 1 sat/vB,
// so standard nodes reject it from their mempool despite the guard at send.rs:211-213.
```

Verification: compare `st.tx.vsize()` (after signing via `TransactionMachine`) against the `vbytes` returned by `calculate_weight_vbytes`; the difference equals the serialized size of the `OP_RETURN` output that was omitted from the fee model.
