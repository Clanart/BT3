### Title
Frontrunning risk in `CW20ERC20Pointer.approve()` allows spender to combine old and new allowance ("Multiple Withdrawal Attack") - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
`CW20ERC20Pointer` is the EVM-facing ERC20 pointer contract that any public EVM caller uses to interact with a CW20 token through Sei's pointer bridge. Its `approve()` function directly overwrites the allowance (via `increase_allowance`/`decrease_allowance` calls sized to the delta) without requiring the caller to first reset the allowance to zero, and without providing safe `increaseAllowance`/`decreaseAllowance` entry points. This reproduces the classic ERC20 "Multiple Withdrawal Attack" pattern identified in the reported analog, applied here to Sei's CW20↔ERC20 pointer bridge, which is directly reachable by any public EVM transaction sender.

### Finding Description
`CW20ERC20Pointer.approve(spender, amount)` at [1](#0-0)  computes the delta between the current allowance and the requested new allowance and issues an `increase_allowance` or `decrease_allowance` CW20 message for that delta. Functionally this is equivalent to unconditionally setting the allowance to the new value in one transaction — there is no requirement to zero out the allowance first, and no `increaseAllowance`/`decreaseAllowance`-style interface is exposed for safe adjustment by callers who want to avoid the race.

A malicious spender that has an existing non-zero allowance can watch the mempool for the owner's `approve()` transaction that is changing (increasing or decreasing) the allowance. The spender front-runs it with a `transferFrom` that consumes the old allowance, and then, once the owner's `approve()` transaction lands and sets/adjusts the allowance to the new value, the spender calls `transferFrom` again to also consume the new allowance — resulting in the spender extracting `old + new` tokens despite the owner only ever intending to authorize `new`.

Because `CW20ERC20Pointer` inherits OpenZeppelin's `ERC20` base and only overrides `approve()`/`transfer()`/`transferFrom()` to proxy calls to the wasmd precompile, the underlying allowance bookkeeping behaves the same as a standard vulnerable ERC20 `approve()`. The same pattern also exists in `NativeSeiTokensERC20.sol` (which uses OpenZeppelin's stock `approve()` unmodified) at [2](#0-1) , and in the CW20 contract's own `increase_allowance`/`decrease_allowance` executes at [3](#0-2) , which similarly compose the new allowance atop the currently-read allowance and are themselves vulnerable to the same reordering when a user intends to reset rather than adjust.

### Impact Explanation
An owner who intends to reduce or change a spender's allowance (a routine operation, e.g. before re-approving a DEX or bridge contract) can have funds transferred in excess of their final intended allowance if the spender is malicious or colludes with a block builder/searcher to reorder transactions. This is a concrete fund-loss risk for any user of nToken/pCash-style ERC20-wrapped assets on Sei's pointer contracts, matching "concrete fund loss" impact criteria.

### Likelihood Explanation
Exploitation requires a spender with an existing non-zero allowance and either mempool visibility or MEV/searcher capability to reorder transactions within a block (or across blocks under OCC scheduling) — a widely known and easily automated technique against any live token that has this approve pattern. The precondition (owner changing an existing non-zero allowance) is common in real usage (re-approvals, allowance revocations, allowance adjustments for DEX routers), making this a realistically reachable and previously-demonstrated bug class.

### Recommendation
Add explicit `increaseAllowance(address spender, uint256 addedValue)` and `decreaseAllowance(address spender, uint256 subtractedValue)` functions to `CW20ERC20Pointer` (and any other Sei pointer/native ERC20 wrapper such as `NativeSeiTokensERC20`), matching OpenZeppelin's mitigation pattern, and document/recommend their use over `approve()` for allowance modifications. Alternatively, require `approve()` to only transition between zero and non-zero values (revert on non-zero→non-zero changes) to force explicit two-step approval, consistent with widely-adopted ERC20 safety guidance.

### Proof of Concept
1. Owner Alice grants Spender Bob an allowance of 1000 CW20-pointer tokens via `pointer.approve(bob, 1000)`.
2. Bob immediately calls `pointer.transferFrom(alice, bob, 1000)`, fully consuming the allowance (transaction pending).
3. Alice later decides to reduce Bob's allowance and submits `pointer.approve(bob, 500)`, intending Bob to only be able to spend 500 more.
4. Bob (or a colluding searcher) orders transactions so that step 2's `transferFrom(1000)` executes after Alice's balance still supports it but the mempool has visibility of the new `approve(500)`; Bob front-runs to spend the original 1000, and once `approve(500)` lands, calls `transferFrom(alice, bob, 500)` again.
5. Net result: Bob extracts 1500 tokens total from Alice despite Alice only intending a maximum simultaneous exposure of 1000 (the pre-change amount) or 500 (the post-change amount) at any single point in time — the classic ERC20 multiple-withdrawal outcome, reproduced against `CW20ERC20Pointer.approve()` at [1](#0-0) .

// Increase the allowance of spender by amount.
// Expiration does not work here since it is not supported by ERC20.
pub fn execute_increase_allowance(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    spender: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&spender)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);

    // Query the current allowance for this user
    let current_allowance = querier.erc20_allowance(erc_addr.clone(), info.sender.clone().into_string(), spender.clone())?.allowance;

    // Set the new allowance as the sum of the current allowance and amount specified
    let new_allowance = current_allowance + amount;

    // Send the message to approve the new amount
    let payload = querier.erc20_approve_payload(spender.clone(), new_allowance)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };

    let res = Response::new()
        .add_attribute("action", "increase_allowance")
        .add_attribute("spender", spender)
        .add_attribute("amount", amount)
        .add_attribute("new_allowance", new_allowance)
        .add_attribute("by", info.sender)
        .add_message(msg);

    Ok(res)
}
