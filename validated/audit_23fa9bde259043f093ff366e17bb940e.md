### Title
Unaccounted reward-token balance in `ManualCompound` can be swept by any caller via `compound()` - (File: `rewards/ManualCompound.sol`)

### Summary
`ManualCompound.compound()` distributes rewards to the caller using the contract's **total current balance** of each registered reward token (`IERC20(_tokenAddress).balanceOf(address(this))`), instead of only the amount that was actually claimed on the caller's behalf via `multiclaimOnBehalf`. Any registered-reward-token balance that ends up sitting in the contract without being attributed to a specific user — for the same class of reason the NFTMarket bug allowed unescrowed NFTs to be grabbed via `acceptOffer` (no structure tying the asset to an owner) — can be swept in full by the next unrelated caller.

### Finding Description
`compound()` is fully permissionless and lets the caller pass arbitrary `_lps`/`_rewards` arrays: [1](#0-0) 

After calling `multiclaimOnBehalf`, the function loops over every *registered* compoundable reward token and forwards `IERC20(_tokenAddress).balanceOf(address(this))` — the entire contract balance of that token — to the caller (directly, or via convertor/locker/helper, all parameterized with `msg.sender`): [2](#0-1) 

There is no per-user accounting structure (no mapping of "reward owed to X") analogous to the `buyPrice`/auction structs in the referenced Foundation bug that verifies the current balance actually belongs to `msg.sender`. Just as the NFTMarket relied solely on `buyPrice`/auction structs to gate custody of an escrowed NFT — and anything held without one of those structs could be taken by anyone through `acceptOffer` — `ManualCompound` relies solely on "whatever token balance happens to be sitting in this contract right now" to decide what to hand to the caller. Since `_convertRatio` is caller-supplied and forwarded to `IConverter.convertFor` for partial conversion, and the loop only ever forwards the *observed balance* rather than a tracked/owed amount, any reward-token residue left behind from a previous `compound()` call (e.g., because a convertor/locker/helper did not consume 100% of the approved/transferred amount, or dust remains after a partial conversion) is not reserved for the user who generated it. The very next caller of `compound()` — even passing empty `_lps`/`_rewards` arrays so they claim nothing of their own — will have that leftover balance swept entirely to themselves.

This mirrors the root cause of the referenced report exactly: assets residing in a shared contract are guarded only by "does a balance/structure exist for this asset," not "is this asset owed to the caller," letting an unrelated actor claim value they never earned.

### Impact Explanation
This results in direct theft of another user's unclaimed/residual yield: reward-token balances that should ultimately belong to the user whose `compound()` call generated them can instead be collected in full by any subsequent, unrelated caller of the same permissionless function, with no capital or privilege required beyond calling `compound()`.

### Likelihood Explanation
Likelihood depends on whether any downstream component (`IConverter.convertFor`, `ILocker.lockFor`, `ISimpleHelper.depositFor`) ever leaves reward-token dust or a partial remainder in `ManualCompound` rather than fully consuming/returning it (e.g., a `_convertRatio` less than 100% causing only part of the approved balance to be pulled, or a helper that does not consume the full approved amount). Given `_convertRatio` is explicitly a caller-controlled parameter for partial conversion, and the sweep logic uses `balanceOf(address(this))` rather than a tracked receivable, this is readily reachable through ordinary use of `compound()` by any wallet, without needing privileged access — matching the report's characterization of a scenario that "seems to leave only mistakenly sent/left-over assets exposed," but here reachable through the very compounding flow itself.

### Recommendation
Track owed amounts per compounding call explicitly (e.g., compute `receivedBalance` as the delta actually attributable to the current caller's `multiclaimOnBehalf` result and downstream conversion output, not the raw `balanceOf(address(this))`), so that any unconsumed remainder is either returned to the rightful prior caller or explicitly accounted for, rather than being distributable to any subsequent caller.

### Proof of Concept
1. User A calls `compound()` with a `_convertor` set for one of the registered reward tokens and a `_convertRatio` that results in the convertor consuming less than the full `receivedBalance` approved to it (partial conversion), leaving residual reward tokens in `ManualCompound`. [3](#0-2) 
2. That residual balance remains in the `ManualCompound` contract, not credited to User A anywhere.
3. User B (unrelated) calls `compound()` with empty `_lps`/`_rewards` arrays, so `multiclaimOnBehalf` claims nothing for User B: [4](#0-3) 
4. The reward-distribution loop still runs, reading `IERC20(_tokenAddress).balanceOf(address(this))` — which now equals User A's leftover residue — and sends/converts/locks it entirely to/for User B. [5](#0-4) 
5. User B has stolen User A's unclaimed yield with no on-chain check preventing it.
