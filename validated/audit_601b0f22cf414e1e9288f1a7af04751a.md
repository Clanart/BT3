## Finding: Native-ERC20 IBC receive can permanently trap recipient funds in the erc20 module account when the wrapped ERC20's `transfer()` reverts

This is a direct structural analog of the reported auction bug: an untrusted external `transfer()` call is invoked in the middle of a value-moving function, after other balance-affecting state changes have already been committed, with no compensating/rollback or "clearBid()"-style recovery path.

### Root cause

`Keeper.ConvertCoinNativeERC20` (used both by `MsgConvertCoin` and by the IBC receive callback) first moves bank coins from the user into the module account, and only afterwards attempts to unescrow the corresponding ERC20 tokens via an external EVM call to the token contract's `transfer()`: [1](#0-0) 

If that external `transfer()` reverts (blacklisted recipient, paused token, `SendEnabled=false`, or any other legitimate/adversarial revert condition), the function returns an error: [2](#0-1) 

This is exactly the function invoked from the IBC receive path for native-ERC20 token pairs: [3](#0-2) 

Unlike a Go-level `error` returned from a `Msg` handler (which aborts and rolls back the whole tx), `OnRecvPacket` returns an `exported.Acknowledgement`. The IBC core `RecvPacket` handler commits whatever state mutations already occurred and simply writes an error acknowledgement — it does not roll back the `SendCoinsFromAccountToModule` escrow that already succeeded inside `ConvertCoinNativeERC20`. There is no `ctx.CacheContext()`/`writeFn()` pattern wrapping this call (contrast with `x/ibc/callbacks/keeper/keeper.go`, which does use `CacheContext` for its EVM callback execution): [4](#0-3) 

Because an error acknowledgement is returned to the counterparty chain, the counterparty will treat the transfer as failed and refund the original sender there (standard ICS-20 semantics). Meanwhile on this chain, the recipient's coins have already been irrevocably moved into `types.ModuleAddress` by the escrow step, and the compensating unescrow (ERC20 `transfer`) never happened. There is no retry or reclaim function reachable from this code path (no "clearBid()" analog) — the funds sit permanently in the erc20 module account.

The project's own integration test acknowledges this exact failure mode (using `SendEnabled=false` to simulate a reverting/blocked transfer), with the comment explicitly noting the funds are *not* sent back to escrow: [5](#0-4) 

That test only demonstrates safe recovery when a **destination callback** is present in the packet memo (via `x/ibc/callbacks`, which isolates the funds to a recoverable "isolated address"). For an ordinary IBC transfer with no destination-callback memo — the common case — `Keeper.OnRecvPacket` in `x/erc20/keeper/ibc_callbacks.go` has no such isolation/recovery mechanism at all.

### Attacker path

Token-pair registration is permissionless (`PermissionlessRegistration` param): [6](#0-5) 

An attacker can: (1) deploy a malicious/pausable/blacklist-capable ERC20 contract, (2) permissionlessly register it as a native-ERC20 token pair, (3) convert ERC20 to the native coin form, (4) send it out over IBC and back (or engineer/relay any packet targeting a recipient the attacker has blacklisted on their own contract). When the packet is received back, `ConvertCoinNativeERC20`'s escrow step succeeds, the `transfer()` call reverts, and the recipient's coins are trapped in the erc20 module account forever while the sending chain refunds the original sender — a critical, irreversible loss/duplication of user value triggerable by an ordinary unprivileged user.

### Recommendation

Wrap the conversion step of `OnRecvPacket`/`ConvertCoinNativeERC20` in a `ctx.CacheContext()` that is only committed on full success, so that a failing unescrow `transfer()` leaves the recipient's bank balance untouched (falling back to the bank-coin representation, consistent with the documented behavior of `OnAcknowledgementPacket`/`OnTimeoutPacket`). Alternatively/additionally, route all such packets (not just ones with an explicit destination-callback memo) through the isolated-address trap-and-recover mechanism already implemented in `x/ibc/callbacks`, so trapped value always remains recoverable by the intended recipient. [7](#0-6) 

This is analogous to the audited fix pattern in the report: replace the direct external-call-then-mutate pattern with an internal balance/escrow bookkeeping step that is atomic with the external call, or make the external call's failure fully reversible.

func (k Keeper) OnAcknowledgementPacket(
	ctx sdk.Context, _ channeltypes.Packet,
	data transfertypes.FungibleTokenPacketData,
	ack channeltypes.Acknowledgement,
) error {
	switch ack.Response.(type) {
	case *channeltypes.Acknowledgement_Error:
		// convert the token from Cosmos Coin to its ERC20 representation
		return k.ConvertCoinToERC20FromPacket(ctx, data)
	default:
		// the acknowledgement succeeded on the receiving chain so nothing needs to
		// be executed and no error needs to be returned
		return nil
	}
}

// OnTimeoutPacket converts the IBC coin to ERC20 after refunding the sender
// since the original packet sent was never received and has been timed out.
// If the ERC20 conversion fails for whatever reason, such as an attempt to call
// a self-destructed ERC20 contract or an invalid function, OnTimeoutPacket still
// succeeds, but the user receives the corresponding bank token from the TokenPair
// instead. A user may then manually re-attempt the conversion.
func (k Keeper) OnTimeoutPacket(ctx sdk.Context, _ channeltypes.Packet, data transfertypes.FungibleTokenPacketData) error {
	return k.ConvertCoinToERC20FromPacket(ctx, data)
}
