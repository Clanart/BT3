This confirms the intended and actual behavior: `updateRemoteUrl` deliberately auto-rewrites the local git remote to whatever `clone_url` the GitHub API returns for the tracked `owner/name`, gated only by protocol-match and "did the user manually change the remote" — with no check that the new URL still refers to the *same repository identity* (no owner/repo-id pinning, no user confirmation).

### Title
Automatic, unconfirmed remote-URL rewrite from GitHub API `clone_url` allows silent push/fetch redirection - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`repositoryWithRefreshedGitHubRepository` refreshes a tracked repository by calling `api.fetchRepository(owner, name)` and then feeding the result straight into `updateRemoteUrl`, which silently calls `git remote set-url` whenever the API's `clone_url` differs from the local remote but the local remote still matches what was last cached, and the URL protocol hasn't changed. [1](#0-0) [2](#0-1) 

### Finding Description
The check that gates the rewrite is a "state-comparison" check, not an identity check — the exact same bug class as the CDP report (a threshold/gate is evaluated against a manipulable, attacker-influenced value instead of validating the actual invariant that matters):

- `remoteUrlUnchanged` only verifies the *old* cached `gitHubRepository.cloneURL` still matches the *current* git remote (i.e., "the user didn't manually edit the remote away from what we last set").
- `protocolsMatch` only verifies `https:`/`https:` or `ssh:`/`ssh:` consistency.
- Neither check validates that the *new* `apiRepo.clone_url` still points at the same repository identity (no comparison against a stable identifier such as the GitHub repo `id`, no owner/name pinning, no user confirmation dialog). [3](#0-2) 

If those two loose conditions hold, Desktop calls `gitStore.setRemoteURL(...)`, which shells out to `git remote set-url` with no further validation: [4](#0-3) 

This function is invoked on essentially every "keep this repo's GitHub metadata fresh" path — repository selection, adding a repository, account changes, publish flow — because `repositoryWithRefreshedGitHubRepository` re-fetches the repo by `owner/name` and is the only gate before the URL is rewritten: [5](#0-4) [6](#0-5) 

The "GitHub API object" that drives this decision (`IAPIRepository`/`clone_url`) is attacker-influenceable: GitHub natively redirects requests for a renamed repository or a repository transferred to a different owner, and `fetchRepository(owner, name)` will transparently follow that redirect and return the *new* `clone_url` for the same `owner/name` the app is still tracking. An attacker who can rename/transfer a shared repository (e.g., a malicious collaborator with admin rights on a repo the victim already has cloned, or a compromised/rogue GHES/proxy sitting between Desktop and the API) can cause the next background refresh to point the victim's `origin` remote at an entirely different repository — while keeping the hostname (and hence protocol) identical, satisfying `protocolsMatch`.

The credential trampoline attaches OAuth credentials purely by hostname/origin match, not by repository identity, so the token is handed to whatever repository the remote now points at: [7](#0-6) 

Existing guards do not stop this path:
- `urlMatchesRemote` is used only to compare URLs to each other, never to a repository ID, so a redirected/renamed repo passes the "unchanged" check trivially.
- There is no popup, confirmation, or diff shown to the user before the remote is silently rewritten — confirmed by the unit tests, which show the rewrite happening unconditionally in-process with no user-facing gate. [8](#0-7) 

### Impact Explanation
Once the remote is silently repointed, every subsequent `git push`/`git fetch`/`git pull` performed through Desktop's UI targets the new (attacker-chosen) repository using the victim's real GitHub credentials, obtained transparently via the trampoline's ASKPASS/credential-helper flow. This can:
- Silently corrupt what the user believes they are committing/pushing to (their commits land in a different repository than intended).
- Exfiltrate private code/history if the redirected target is an attacker-accessible repository (fork, private org repo the attacker admins, etc.).
This matches the accepted impact category "silent corruption of what the user commits or pushes" / credential misdirection via an attacker-controlled GitHub API object.

### Likelihood Explanation
The attacker needs no local access, no malware, and no leaked credentials — only the ability to rename or transfer ownership of a repository the victim already has open in Desktop (a normal GitHub permission many collaborators/org admins legitimately have), or the ability to sit as a malicious/compromised GitHub Enterprise Server or network proxy between Desktop and the API. The refresh path runs automatically and repeatedly during ordinary use (repository selection, background indicator refresh, add-repository flow), so no unusual user action is required to trigger the rewrite; it is a background/automatic process.

### Recommendation
Do not treat "old cached URL vs. current remote" and "protocol match" as sufficient authorization to auto-rewrite an existing remote. Instead:
- Pin the comparison to a stable identifier (`GitHubRepository.dbID`/API repo `id`) rather than the mutable `clone_url`, and treat an owner/name change on the same ID as a rename to surface via an explicit, user-confirmed prompt.
- Require explicit user confirmation before calling `setRemoteURL` when the API-reported clone target diverges from the currently configured remote, rather than performing it silently in the background refresh path.
- Consider not auto-updating the remote at all outside of an explicit "repository renamed/transferred" notification flow.

### Proof of Concept
1. Victim clones/adds `github.com/victim-org/app` in GitHub Desktop; `origin` is set to `https://github.com/victim-org/app.git` and `gitHubRepository.cloneURL` is cached identically.
2. Attacker (a collaborator/admin on `victim-org/app`, or a MITM GHES proxy) renames the repository or transfers it to `attacker-org/app`. GitHub's API/redirect layer means a request for `victim-org/app` now resolves to and returns `clone_url: https://github.com/attacker-org/app.git`.
3. On the victim's next Desktop repository-select/refresh (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`), `api.fetchRepository('victim-org', 'app')` returns the attacker-controlled `clone_url`.
4. `updateRemoteUrl` computes `protocolsMatch = true` (https/https) and `remoteUrlUnchanged = true` (old cached cloneURL still equals current `origin` URL), and `urlsMatch = false` — satisfying the condition at [9](#0-8) , so `origin` is silently rewritten to `https://github.com/attacker-org/app.git` with no user prompt (exactly reproduced by the existing test at lines 68-81 of `update-remote-url-test.ts`, using an arbitrary "updated" clone URL).
5. The victim's next push in Desktop goes to `attacker-org/app`, authenticated with the victim's real GitHub credentials via the trampoline (hostname-based lookup only), silently redirecting/exfiltrating the pushed commits.

```typescript
  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }
```

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
