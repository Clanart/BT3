## Analysis

The external report's core complaint is that a signature/transaction payload doesn't disambiguate *what action* is actually being authorized — the same raw bytes can be misread or misused for something other than what the signer intended. The closest concrete analog in this repository is a **signature domain collision between two separate `pallet-relayer` unsigned extrinsics** that both hash the exact same `(nonce, StateMachine, Vec<u8>)` tuple with no purpose tag, letting a signature meant for one call be replayed into the other to trigger an unintended, higher-impact action.

### Title
Cross-entrypoint signature replay between `accumulate_fees` beneficiary redirect and `withdraw_fees` forces unauthorized premature fund withdrawal - ([File: modules/pallets/relayer/src/accumulate.rs](modules/pallets/relayer/src/accumulate.rs), [File: modules/pallets/relayer/src/withdrawal.rs](modules/pallets/relayer/src/withdrawal.rs))

### Summary
`pallet-relayer` signs two functionally different actions with byte-identical message preimages and shares the same `Nonce` storage between them, with no domain separator distinguishing "redirect where newly accumulated fees are credited" from "withdraw and cross-chain-dispatch my entire accumulated balance." Because both extrinsics are unsigned/permissionless (`ensure_none`), an attacker can copy a relayer's in-flight `accumulate_fees` beneficiary-redirect signature straight out of the mempool and submit it as a `withdraw_fees` call, forcing an immediate, unauthorized cross-chain payout of the relayer's *entire* accumulated fee balance and burning the relayer's nonce.

### Finding Description
`beneficiary_message` (used by `accumulate`) and `message` (used by `withdraw`) hash the identical structure when a beneficiary is supplied: [1](#0-0) [2](#0-1) 

Both encode `(nonce: u64, StateMachine, Vec<u8>).encode()` and hash with `keccak_256` — there is no discriminator tying the signature to "accumulate" vs "withdraw". Both consume the **same** `Nonce::<T>` map keyed by `(address, state_machine)`: [3](#0-2) [4](#0-3) 

Both entrypoints are unsigned/permissionless, so their calldata (including the relayer's signature) is publicly visible in the transaction pool before finalization: [5](#0-4) 

An attacker who observes a relayer's pending `accumulate_fees` call carrying `beneficiary_details = Some((B, sig))` can extract `(B, sig)` and submit `withdraw_fees` with `WithdrawalInputData { signature: sig, dest_chain: state_machine, beneficiary: Some(B) }`. The signature verifies in `withdraw` because the preimage is identical to what was signed for `accumulate`. `withdraw` then reads `Fees::<T>::get(dest_chain, address)` — the relayer's **entire currently accumulated balance**, not just the amount pending in the front-run batch — zeroes it, and dispatches a cross-chain payout to `B`, incrementing the shared nonce. This causes the relayer's own `accumulate_fees` call (still using the now-stale nonce) to subsequently fail signature verification and revert, since the on-chain nonce has moved past what was signed.

### Impact Explanation
This is unauthorized/forced execution of a different action than the relayer consented to at signing time: a signature scoped for "credit this batch's newly earned fee to beneficiary B's ledger balance" is repurposed to trigger "immediately withdraw and cross-chain-dispatch my entire historical fee balance to B." This can drain a relayer's whole `Fees` balance earlier and in larger amount than intended, and can be repeated by any observer to griefing-DoS the relayer's beneficiary-redirect flow by continually burning its nonce, per `Hyperbridge Pivots` guidance that reward-claim flows "must move exactly once and only to the rightful beneficiary and amount" — here the amount moved is not what was authorized for that action.

### Likelihood Explanation
Both `accumulate_fees` and `withdraw_fees` are unsigned, permissionless extrinsics (`ensure_none`), so any unprivileged party monitoring the transaction pool can copy a broadcast `Signature` value and resubmit it against the sibling call before the original is included — no malicious relayer, prover, or privileged actor is required, matching the "unprivileged attacker" requirement in the task's method.

### Recommendation
Include a domain-separation tag (e.g., a distinct byte/string constant identifying "ACCUMULATE_BENEFICIARY" vs "WITHDRAW") inside both `beneficiary_message` and `message` before hashing, so a signature produced for one call can never satisfy verification for the other, even when `(nonce, state_machine, beneficiary)` coincide.

### Proof of Concept
1. Relayer R has accumulated fees on `StateMachine::X` and wants to redirect a new batch's fee credit to beneficiary `B`. R signs `beneficiary_message(nonce=n, X, B)` and submits `accumulate_fees(withdrawal_proof)` (unsigned extrinsic) to the pool.
2. Attacker observes the pending extrinsic, extracts `(B, signature)`.
3. Attacker submits `withdraw_fees(WithdrawalInputData { signature, dest_chain: X, beneficiary: Some(B) })` before R's transaction lands.
4. In `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs:81-131`), `Nonce::<T>::get(R, X)` still equals `n`; `message(n, X, Some(B))` byte-matches `beneficiary_message(n, X, B)`, so signature verification succeeds and the call proceeds using R's real address and R's full `Fees::<T>::get(X, R)` balance, dispatching an immediate cross-chain payout to `B` and bumping `Nonce(R, X)` to `n+1`.
5. R's original `accumulate_fees` transaction later executes, re-derives `Nonce::<T>::get(R, X) == n+1`, re-hashes `beneficiary_message(n+1, X, B)`, which no longer matches R's original signature — the call fails with `InvalidSignature`, and R's legitimate action never lands while the attacker-forced withdrawal has already fired.

/// Signed payload for [`WithdrawalInputData`]. Includes the per-relayer nonce so a captured
/// signature cannot be replayed.
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
