### Title
`aptos move verify-package` and on-chain publish validation never bind declared package source/metadata to the actually-deployed module bytecode - ([File: aptos-move/cli/src/stored_package.rs])

### Summary
The Aptos publish flow lets a publisher submit arbitrary compiled bytecode (`code: vector<vector<u8>>`) alongside self-declared `PackageMetadata` (source, `source_digest`, manifest, dependency list). Nothing in the framework's on-chain publish path or in the CLI's `verify-package` tool actually checks that the declared source/metadata corresponds to the bytecode that gets executed. This is directly analogous to the Sablier bug: a "trusted-looking" declared value (there: the wrapped-asset address; here: the package's declared source/metadata) is accepted at face value while the code path that actually moves value/executes logic (there: `deposit()`; here: the raw `code` bytes passed to `request_publish[_with_allowed_deps]`) is decoupled and can diverge from what was claimed.

### Finding Description
On-chain, `aptos_framework::code::publish_package` (and the entry wrapper `publish_package_txn`) accepts a `PackageMetadata` struct and a separate `code: vector<vector<u8>>` bundle of compiled modules: [1](#0-0) 

Validation performed by `AptosVM::validate_publish_request` only checks module-name registration, allowed dependencies, native validation, resource-group/event metadata, and re-verifies structural bytecode - it never recomputes or checks the `source_digest`/manifest/source fields against the actual compiled modules: [2](#0-1) 

The only artifact meant to give downstream users assurance that on-chain code matches a given source tree is the CLI's `aptos move verify-package` command. Its implementation:
- Builds the package locally to get `compiled_metadata`.
- Fetches only the on-chain `PackageRegistry` resource (metadata), explicitly with `with_bytecode = false`, so **actual on-chain bytecode is never downloaded**: [3](#0-2) [4](#0-3) 

- Calls `package.verify(&compiled_metadata)`, which compares only metadata struct fields (`name`, `deps`, `modules` metadata, `manifest`, `upgrade_policy`, `extension`, `source_digest`) between the locally-rebuilt metadata and the on-chain metadata resource - it never diffs any bytecode bytes: [5](#0-4) 

Because `source_digest` is computed purely from the source files supplied by the publisher (sha256 of each source, sorted, re-hashed) and is stored as an ordinary, unenforced metadata field, a publisher fully controls both the `code` bundle and the metadata independently. There is no mechanism anywhere in the publish path (Move framework, VM validation, or the verification CLI) that recompiles or otherwise cryptographically binds the declared metadata/source to the bytecode that will actually execute at that address.

### Impact Explanation
A malicious (or compromised) publisher can publish a package whose `PackageMetadata` (source, manifest, `source_digest`) matches a known-good, audited codebase, while the actual `code` bytes deployed are arbitrary malicious bytecode (backdoors, admin bypass, fund-draining logic, etc.). `aptos move verify-package` will happily report "Successfully verified source of package" because it only ever compares metadata-to-metadata and never fetches or diffs the real on-chain bytecode. Any user, auditor, indexer, or wallet that relies on this command (or similarly implemented tooling) as an assurance that deployed code matches reviewed/expected source will be misled into trusting malicious code as verified - directly enabling silent code replacement/backdoor deployment under the appearance of a verified, benign package.

### Likelihood Explanation
No special privilege is required beyond being any account able to publish a package (or an upgrade under a `compatible` policy, or via `object_code_deployment`/resource-account publish flows, which all funnel through the same `code::publish_package`). Constructing mismatched metadata/bytecode requires no VM or verifier bypass - it is simply supplying two independently-controlled parameters (`pack: PackageMetadata` and `code: vector<vector<u8>>`) that the protocol never cross-checks. The only barrier is that a victim must choose to trust the `verify-package` output (or equivalent metadata-only tooling) instead of independently re-deriving expected bytecode, which is precisely the intended purpose of that command and thus a very plausible trust point.

### Recommendation
- Extend `aptos move verify-package` to always fetch on-chain module bytecode (`with_bytecode = true`) and compare it byte-for-byte (or via a canonical bytecode digest) against bytecode produced from local compilation of the declared source, not merely comparing metadata struct fields.
- Consider adding an on-chain or protocol-level binding between `PackageMetadata.source_digest`/`modules[].source` and the actual compiled module bytes (e.g., a verifiable digest of compiled bytecode included in metadata and optionally checked by the VM at publish time), so metadata cannot silently diverge from what is executed.
- Document clearly (and warn in the CLI output) that current `verify-package` output only asserts metadata self-consistency and does **not** prove that on-chain bytecode matches the declared/reviewed source, until the bytecode comparison is implemented.

### Proof of Concept
1. Prepare two Move packages, `Benign` (innocuous, e.g. audited) and `Evil` (contains a hidden admin-bypass or fund-drain function), such that `Evil`'s compiled bytecode is what will actually be deployed.
2. Compile `Benign` locally to obtain its `PackageMetadata` (`manifest`, `modules[].source`, `source_digest`, etc.) via `BuiltPackage::extract_metadata()` as done in `aptos-move/cli/src/commands.rs`.
3. Compile `Evil` locally to obtain its compiled module bytecode via `BuiltPackage::extract_code()`.
4. Submit a publish transaction (`code::publish_package_txn`) using `Benign`'s metadata bytes but `Evil`'s compiled `code` bundle - `AptosVM::validate_publish_request` only checks module names/dependencies/native rules, not metadata-vs-bytecode source consistency, so this transaction succeeds.
5. Run `aptos move verify-package --account <addr>` pointed at the local `Benign` source tree - the command builds `Benign` locally, fetches only the on-chain metadata (no bytecode), and `verify()` matches every field since the on-chain metadata is indeed `Benign`'s metadata - producing `"Successfully verified source of package"`, even though the deployed, executing bytecode is actually `Evil`.

    pub fn verify(&self, package_metadata: &PackageMetadata) -> anyhow::Result<()> {
        let self_metadata = self.metadata;

        if self_metadata.name != package_metadata.name {
            bail!(
                "Package name doesn't match {} : {}",
                package_metadata.name,
                self_metadata.name
            )
        } else if self_metadata.deps != package_metadata.deps {
            bail!(
                "Dependencies don't match {:?} : {:?}",
                package_metadata.deps,
                self_metadata.deps
            )
        } else if self_metadata.modules != package_metadata.modules {
            bail!(
                "Modules don't match {:?} : {:?}",
                package_metadata.modules,
                self_metadata.modules
            )
        } else if self_metadata.manifest != package_metadata.manifest {
            bail!(
                "Manifest doesn't match {:?} : {:?}",
                package_metadata.manifest,
                self_metadata.manifest
            )
        } else if self_metadata.upgrade_policy != package_metadata.upgrade_policy {
            bail!(
                "Upgrade policy doesn't match {:?} : {:?}",
                package_metadata.upgrade_policy,
                self_metadata.upgrade_policy
            )
        } else if self_metadata.extension != package_metadata.extension {
            bail!(
                "Extensions doesn't match {:?} : {:?}",
                package_metadata.extension,
                self_metadata.extension
            )
        } else if self_metadata.source_digest != package_metadata.source_digest {
            bail!(
                "Source digests doesn't match {:?} : {:?}",
                package_metadata.source_digest,
                self_metadata.source_digest
            )
        }

        Ok(())
    }
