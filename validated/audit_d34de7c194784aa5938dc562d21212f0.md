### Title
Attacker-controlled `ReceivedOutput` deserialization permits excessive memory allocation - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an untrusted serialized Bitcoin `TxOut` and passes it directly to `TxOut::consensus_decode` without imposing a Serai-specific size limit on the embedded `script_pubkey`. A malformed or oversized serialized output can therefore cause a disproportionately large memory allocation while the reader attempts to consume the declared script bytes.

### Finding Description
`ReceivedOutput` stores a scalar offset, a complete `TxOut`, and an `OutPoint`. [1](#0-0) 

Its public deserializer first reads the scalar and then deserializes the entire Bitcoin output and outpoint from the caller-controlled stream. [2](#0-1) 

`TxOut` consensus encoding contains a variable-length `script_pubkey`, so the attacker controls the encoded length and bytes consumed by `TxOut::consensus_decode`. [3](#0-2) 

Serai places no maximum on that field before delegating decoding to the external `bitcoin` crate, which is used for Bitcoin consensus serialization. [4](#0-3) [5](#0-4) 

Outputs generated by `Scanner` are Taproot outputs whose expected script is fixed-size, but `ReceivedOutput::read` accepts an arbitrary serialized `TxOut` rather than enforcing the expected Taproot script shape or size. [6](#0-5) 

### Impact Explanation
An unprivileged party that can submit serialized `ReceivedOutput` bytes can force the parser to allocate and retain attacker-sized `TxOut.script_pubkey` data. Repeated requests can exhaust process memory or trigger an allocation failure, producing a denial of service comparable to requesting an arbitrarily large remote object.

Because decoding occurs before any check that the output script is one of the scanner’s expected Taproot scripts, oversized data does not need to be a valid spendable output to consume resources. [2](#0-1) [6](#0-5) 

### Likelihood Explanation
The vulnerable function is public and explicitly accepts an arbitrary `Read` implementation, so callers can expose it to serialized data supplied by another participant or recovered from an untrusted channel. [2](#0-1) 

The attacker only needs to control the serialized `ReceivedOutput` bytes; they do not need valid signatures, consensus acceptance, private keys, or cooperation from honest signers. [1](#0-0) 

### Recommendation
Bound `ReceivedOutput::read` before decoding the Bitcoin `TxOut`. Since scanner-generated outputs are expected to use the fixed 34-byte P2TR `script_pubkey`, reject any encoded output whose script is not that expected size and form, or at minimum enforce a small explicit byte limit and read script data incrementally. Ensure trailing bytes are rejected after the `OutPoint` is decoded. [7](#0-6) [6](#0-5) 

### Proof of Concept
The following input uses a canonical zero scalar, an 8-byte amount, a Bitcoin CompactSize script length of `4_000_000`, and script bytes supplied by the reader. `ReceivedOutput::read` attempts to materialize the declared output rather than rejecting it as a non-Taproot or oversized output:

```rust
// networks/bitcoin/src/wallet/mod.rs
use bitcoin_serai::wallet::ReceivedOutput;

fn malicious_received_output(script: Vec<u8>) -> Vec<u8> {
    let mut encoded = Vec::new();

    // Secp256k1 scalar representation: 32 bytes.
    encoded.extend([0u8; 32]);

    // TxOut.amount: 8-byte little-endian value.
    encoded.extend(0u64.to_le_bytes());

    // TxOut.script_pubkey CompactSize length.
    let script_len = script.len() as u64;
    if script_len > u16::MAX.into() {
        encoded.push(0xff);
        encoded.extend(script_len.to_le_bytes());
    }

    // Attacker-controlled script bytes.
    encoded.extend(script);

    // OutPoint: 32-byte txid + 4-byte vout.
    encoded.extend([0u8; 36]);
    encoded
}

let bytes = malicious_received_output(vec![0u8; 4_000_000]);
let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(output.output().script_pubkey.len(), 4_000_000);
```

Calling this repeatedly causes proportional memory growth; callers that process attacker-supplied serialized outputs concurrently can be driven into memory exhaustion. [2](#0-1)

  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
