## Title
`updateConflictState()` carries over `manualResolutions` keyed only by file path across distinct merge/rebase/cherry-pick operations, letting stale conflict resolutions be silently applied to unrelated files - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`FollowNFT.tryMigrate()` was vulnerable because it wrote into a new state variable (`_followTokenIdByFollowerProfileId`) without checking whether prior state (`follow()`'s tracking) already existed for that key, letting an old/stale record leak into a new operation and corrupt counters. The GitHub Desktop analog is `updateConflictState()` in `app/src/lib/stores/updates/changes-state.ts`, which reuses the previous conflict operation's `manualResolutions` map (keyed only by file `path`) as the seed for a brand-new conflict state, without invalidating entries whose underlying blob/commit context has changed.

### Finding Description
`updateConflictState` computes the new conflict state like this: [1](#0-0) 

```
const prevConflictState = state.conflictState
const manualResolutions =
  prevConflictState !== null
    ? prevConflictState.manualResolutions
    : new Map<string, ManualConflictResolution>()
const newConflictState = getConflictState(status, manualResolutions)
```

`manualResolutions` is a `Map<string, ManualConflictResolution>` keyed purely by file `path`, and it is threaded, unmodified, straight from `prevConflictState` into `getConflictState()`, which then stamps it onto the brand-new `ConflictState` (`merge`/`rebase`/`cherryPick`) regardless of whether the current conflict is even the same operation: [2](#0-1) 

The only place this map is invalidated is the explicit "different operation kind" branch, which is a no-op for effects but still returns `newConflictState` carrying the old resolutions: [3](#0-2) 

```
// Otherwise we transitioned from a merge conflict to a rebase conflict or
// vice versa, and we should avoid any side effects here
return newConflictState
```

Critically, within the *same* operation kind (e.g. two different merges, or a rebase against a different upstream, performed in immediate succession without the conflict state having gone through a `null` reset in between - e.g. aborting one merge and immediately starting another before a full status refresh clears `conflictState`, or a multi-step rebase against a malicious remote that repeatedly produces conflicts on the same file path with different content each step) the stale `manualResolutions[path]` entry survives and is consumed downstream by `createMergeCommit()`: [4](#0-3) 

```
for (const [path, resolution] of manualResolutions) {
  const file = files.find(f => f.path === path)
  if (file !== undefined) {
    await stageManualConflictResolution(repository, file, resolution)
  } else {
    log.error(...)
  }
}
```

`stageManualConflictResolution` stages "ours"/"theirs" for that path based purely on the path match - it has no way to know the resolution was computed for a *different* conflict (different base/target tips, different blobs) than the one currently in progress. Because the key is only the file `path` (not path+blob-sha or path+operation-id), a resolution the user made deliberately for conflict A ("keep my version of `config.yml`") can be silently reapplied to a *different*, unrelated conflict B on the same path that arose from a subsequently fetched/merged malicious branch, without the user ever being shown or confirming the new conflicting content.

### Impact Explanation
This is a "silent corruption of what the user commits or pushes" class bug, matching the External Report's core invariant violation (`follow` state incremented/reused without verifying prior state was cleared). An attacker who controls a remote branch (e.g. a fork's PR branch, or a pushed-to shared branch) can craft a file at a path the victim previously resolved manually in an earlier conflict, so that when the victim performs a subsequent merge/rebase involving the attacker's branch, Desktop reuses the stale resolution and stages/commits the attacker-influenced or victim's-previous-but-now-wrong content without prompting the user to re-resolve. The victim then unknowingly commits and pushes content they never reviewed for that specific conflict, which can reintroduce vulnerable code, remove security fixes, or otherwise corrupt the repository history that gets pushed upstream.

### Likelihood Explanation
The trigger requires the app to go through two same-kind conflicted operations back-to-back without an intervening `null` conflictState (e.g., aborting a merge/rebase and immediately re-merging/re-rebasing against a different branch, or a multi-step rebase touching the same path across different commits) while a file at an identical path is involved. This is a plausible, low-friction workflow in normal usage of GitHub Desktop's rebase/merge/cherry-pick tooling, and does not require local/admin access - only that the user perform normal git operations against attacker-influenced remote content. It requires no unusual user steps beyond typical merge/rebase actions the app already encourages.

### Recommendation
Key `manualResolutions` (or otherwise invalidate it) by more than just file `path` - include the conflict operation identity (e.g., `currentTip`/`baseBranchTip`/`targetBranch` or a generated operation id) so that resolutions from a prior, distinct conflict operation cannot be silently reapplied. At minimum, `updateConflictState` should reset `manualResolutions` to an empty map whenever the identifying fields of the new conflict state (branch tips, target branch, or the underlying operation) differ from the previous state, even when `prevConflictState` and `newConflictState` are of the same `kind`.

### Proof of Concept
1. Start a merge of a branch (or add a remote from an attacker-controlled fork) that conflicts on `config.yml`; manually resolve it via "Use my version" (populates `manualResolutions.set('config.yml', ours)`).
2. Abort that merge (or it completes) without the app's `conflictState` first collapsing to `null` due to a lagging/racy status refresh (achievable by triggering rapid consecutive `_mergeBranch`/`_rebase` dispatcher calls or by aborting and instantly starting a new merge/rebase before `updateChangedFilesForCurrentRepository` runs a full status pass).
3. Immediately merge/rebase in a second branch (attacker-controlled) that also conflicts on `config.yml` but with entirely different, unrelated content on both sides.
4. `updateConflictState` seeds the new `ConflictState.manualResolutions` from the stale map (still containing `config.yml -> ours`), and `createMergeCommit`/rebase continuation stages the *previous* resolution's side for the *new* conflict without prompting the user, silently committing unreviewed content for `config.yml`.

Note: full exercise of this path (repro across `app-store.ts`'s dispatch of merge/rebase operations vs. `updateConflictState`) could not be completely traced within available search budget; the exact sequence of dispatcher calls that leaves `conflictState` non-null between two distinct operations should be verified with a live debugging session (e.g. a Devin session) against `app-store.ts`'s rebase/merge/cherry-pick flows.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }
