### Title
Coinbase outputs reported as immediately spendable by the Bitcoin scanner, enabling immature funds to enter signing plans - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The analog of CVE-2017-14449 (a crafted input triggering premature/double release of a resource in a parser) maps onto Serai as a crafted Bitcoin transaction causing the wallet scanner to release an output for spending before the protocol allows it. `Scanner::scan_block` iterates `block.txdata` including `txdata[0]` — the coinbase — and `scan_transaction` emits a `ReceivedOutput` for any coinbase output paying to a registered `script_pubkey`. A coinbase output is unspendable for 100 blocks (COINBASE_MATURITY), yet `ReceivedOutput` carries no height/maturity marker, so downstream code treats it as a normal spendable input.

### Finding Description
`Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214) matches outputs purely on `self.scripts.get(&output.script_pubkey)` and pushes `ReceivedOutput { offset, output, outpoint }` with no transaction-type or maturity check. `Scanner::scan_block` (mod.rs:221-227) feeds it every transaction in the block, explicitly including the coinbase:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for tx in &block.txdata {
      res.extend(self.scan_transaction(tx));
    }
    res
}
```

The doc comment acknowledges the gap ("If received outputs must be immediately spendable, a post-processing pass is needed"), but `ReceivedOutput` exposes only `offset`, `output`, and `outpoint` (mod.rs:99-118) — there is no field recording which transaction index or block height the output came from, so a consumer holding only the `ReceivedOutput` cannot determine it is coinbase-immature. Worse, `Output::id()` (processor/src/networks/bitcoin.rs:92-104) derives identity solely from the consensus-encoded outpoint, so the immature output is deduplicated and persisted exactly like a normal output.

When such an output reaches `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256), it is summed into `input_sat` and used as `previous_output` for a `TxIn`. The resulting transaction spends an immature coinbase, which every Bitcoin node rejects for 100 blocks.

### Impact Explanation
An unprivileged miner (or any party able to get a coinbase mined, e.g., via a pool paying directly to a supplied address — a supported feature of pools like Ocean) sends funds to Serai's P2TR `script_pubkey` inside a coinbase. The processor then (a) reports funds as received that are not spendable for ~100 blocks, and (b) may include the immature outpoint in a `SignableTransaction`, causing the threshold signing round to produce a transaction that cannot be broadcast — stalling the batch/plan that consumed the output. This satisfies the "funds reported received that are not spendable" impact class, and mirrors the original bug: an attacker-controlled crafted input causes the system to act on a resource it is not permitted to use.

### Likelihood Explanation
Requires an attacker to mine a block paying Serai's script in the coinbase, or to arrange a pool payout to a Serai address. Mining a block is expensive, but pool payouts to arbitrary addresses are routine and the attack can also occur unintentionally. Once the output is scanned, inclusion in a spending plan is automatic — the scheduler has no data to exclude it since maturity is not tracked on `ReceivedOutput`. Moderate likelihood; Medium severity.

### Recommendation
- In `Scanner::scan_block`, skip `block.txdata[0]` (or filter `tx.is_coinbase()`), or
- record the coinbase flag/block height on `ReceivedOutput` and have `SignableTransaction::new` (or the scheduler) reject outputs younger than 100 confirmations. If coinbase outputs should be supported, gate them until maturity rather than dropping them.
