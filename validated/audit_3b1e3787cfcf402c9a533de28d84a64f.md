### Title
Legacy `pattern` shorthand for `event: file` rules silently fails to block `Write` tool operations - ([File: plugins/hookify/core/config_loader.py])

### Summary
`Rule.from_dict` converts the legacy `pattern` frontmatter field for `event: file` rules into a `Condition` hardcoded to `field='new_text'`. `RuleEngine._extract_field` only resolves `new_text` to `tool_input['new_string']`, which is populated for the `Edit` tool but never for the `Write` tool (which uses `content`). As a result, a `block`/`warn` rule authored via the legacy shorthand — including rules auto-generated by `/hookify` — silently never matches `Write` tool calls, while the semantically equivalent explicit-conditions form (`field: content`) does match.

### Finding Description
`Rule.from_dict` in `plugins/hookify/core/config_loader.py` has two code paths for building conditions:
- Explicit: `conditions:` list is parsed via `Condition.from_dict`, letting the rule author pick any `field`, including `content`.
- Legacy: if only `pattern` is given, the field is inferred purely from `event`: `event == 'file'` always yields `field = 'new_text'`, with no way to choose `content`. [1](#0-0) 

`plugins/hookify/hooks/pretooluse.py` maps the `Edit`, `Write`, and `MultiEdit` tools all to the same `event = 'file'` filter before loading and evaluating rules, so a single `event: file` rule is expected to cover all three tools uniformly. [2](#0-1) 

However, `RuleEngine._extract_field` resolves `new_text` only to `tool_input.get('new_string', '')`, which is the `Edit` tool's field. The `Write` tool's payload lives in `tool_input['content']`, which is only reachable via `field == 'content'`: [3](#0-2) 

Because `tool_input.get('new_string', '')` returns `''` (not `None`) for a `Write` call, `_check_condition` does not short-circuit on the `None` check — it proceeds to run the regex/contains/etc. check against an empty string, which practically never matches a non-trivial pattern: [4](#0-3) 

The `/hookify` slash command's documented "Simple Rule" generation path explicitly produces this legacy `pattern:` form for `file` events by default: [5](#0-4) 

So any legacy-style block/warn rule targeting `event: file` — whether shipped in the repo or generated by `/hookify` — is silently blind to the `Write` tool. An attacker (or a prompt-injected/compromised agent turn) can trivially evade such a rule by having Claude create the forbidden content with `Write` (e.g., writing a new file containing the blocked pattern) instead of `Edit`ing an existing file, since the rule's condition field never observes the `content` the tool actually writes. The same policy expressed with explicit `conditions: [{field: content, ...}]` would have caught it — this is exactly the "legacy vs explicit" semantic divergence the invariant requires to not exist. No allowlist, approval prompt, or parser validation exists to catch this: the hook silently returns `{}` (allow) since no condition matched, and errors are swallowed by the hook's `finally: sys.exit(0)` always-allow behavior. [6](#0-5) 

### Impact Explanation
This is a Security-control bypass: a block rule intended to prevent dangerous file content (e.g., committing secrets, blocking known-bad code patterns) from being written is silently disabled for one of the three tool types it is documented to cover. Because the hook always exits 0 and returns an empty/allow result on non-match, there is no error, warning, or log indicating the control failed — the bypass is silent. This matches the "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries" impact category.

### Likelihood Explanation
- No special privilege is required beyond the ability to influence what tool Claude uses to write content (e.g., through normal repository content, task framing, or a prompt-injection-adjacent scenario) — using `Write` instead of `Edit` is an ordinary and common code-generation action, not an unusual or suspicious one.
- The bug is deterministic and 100% reproducible: any legacy `pattern` + `event: file` rule with `action: block` fails against `Write` tool calls every single time, regardless of pattern content.
- The vulnerable pattern is also the one `/hookify`'s own documented "Simple Rule" generation path produces by default, so this is likely to occur in real, unmodified deployments, not just contrived configs.

### Recommendation
- In `Rule.from_dict`'s legacy-pattern branch, for `event == 'file'`, either check both `new_text`/`new_string` and `content` (i.e., generate two conditions combined with OR semantics, or a field alias that `_extract_field` resolves across all file-tool payload keys), or default legacy file-event rules to `field='content'` and have `_extract_field` treat `content` as covering `Edit`'s `new_string` too.
- Alternatively, fix `_extract_field` so that `new_text` resolves to `tool_input.get('new_string') or tool_input.get('content', '')` for both `Write` and `Edit`, removing the asymmetry, and add a unit test asserting a legacy `pattern`/`event: file`/`action: block` rule matches an equivalent `Write` and `Edit` tool call identically to an explicit `conditions: [{field: content}]` rule.
- Add a regression/invariant test that constructs a rule via both the legacy and explicit forms with equivalent intent and asserts `RuleEngine.evaluate_rules` produces the same block/allow decision for `Bash`, `Edit`, `Write`, and `MultiEdit` inputs.

### Proof of Concept
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

# Legacy-style rule as generated by /hookify's "Simple Rule" format
frontmatter = {
    "name": "block-secret",
    "enabled": True,
    "event": "file",
    "pattern": "SECRET_KEY",
    "action": "block",
}
legacy_rule = Rule.from_dict(frontmatter, "Blocked: secret detected")

engine = RuleEngine()

write_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Write",
    "tool_input": {"file_path": "config.py", "content": "SECRET_KEY = 'abc123'"},
}
edit_input = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {"file_path": "config.py", "old_string": "x=1", "new_string": "SECRET_KEY = 'abc123'"},
}

write_result = engine.evaluate_rules([legacy_rule], write_input)
edit_result = engine.evaluate_rules([legacy_rule], edit_input)

# Expected (broken) behavior: write_result == {} (bypass, no block)
# while edit_result contains a "permissionDecision": "deny" (blocked)
assert write_result == {}, "Write bypassed the block rule"
assert edit_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Equivalent explicit-conditions rule correctly catches both:
explicit_frontmatter = {
    "name": "block-secret-explicit",
    "enabled": True,
    "event": "file",
    "action": "block",
    "conditions": [{"field": "content", "operator": "contains", "pattern": "SECRET_KEY"}],
}
explicit_rule = Rule.from_dict(explicit_frontmatter, "Blocked: secret detected")
explicit_write_result = engine.evaluate_rules([explicit_rule], write_input)
assert explicit_write_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny", \
    "Explicit rule correctly blocks Write, proving legacy/explicit divergence"
```
This demonstrates the differential: identical security intent expressed via legacy `pattern` vs explicit `conditions` yields different (bypassable vs. correct) enforcement for the `Write` tool.
