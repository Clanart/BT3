### Title
CW20-wrapped-ERC20 pointer relays a nominal `amount` to `Cw20ReceiveMsg` instead of the actual received balance, enabling fee-on-transfer/deflationary ERC20 accounting mismatches - (File: example/cosmwasm/cw20/src/contract.rs)

### Summary
The ERC20-to-CW20 pointer contract (deployed for any user-registered ERC20 pointer, e.g. `WASM.POINTER_CW20`/`registerPointerForERC20`) forwards a caller-specified `amount` unchanged to downstream contracts via `Cw20ReceiveMsg`, without verifying that the underlying ERC20 `transfer`/`transferFrom` actually moved that amount.

### Finding Description
`execute_send` and `execute_send_from` build a `Cw20ReceiveMsg{ sender, amount, msg }` using the caller-requested `amount` and dispatch it to the destination contract's `receive` hook, while the actual token movement is delegated to the underlying ERC20 via a fire-and-forget `EvmMsg::DelegateCallEvm` message with no balance-before/after check: [1](#0-0) [2](#0-1) 

The underlying `transfer`/`transfer_from` helpers only build the delegatecall payload from the *requested* `amount` and never inspect the ERC20's actual balance delta: [3](#0-2) 

If the wrapped ERC20 implements a fee-on-transfer or deflationary mechanism (e.g., transferring `100` tokens but only delivering `95` to the recipient), the pointer contract still reports `amount = 100` in the `Cw20ReceiveMsg` sent to the receiving contract, and in the `transfer`/`transfer_from` event attributes. Any downstream CW20-aware contract that trusts the `Cw20ReceiveMsg.amount` field (rather than independently querying its own post-transfer balance) will believe it received 100 tokens when it only received 95 — the exact bug class described in the referenced report ("A call to transfer(recipient, 100) with a 5% FOT will entitle the recipient with 95 tokens" but callers/receivers assume the full 100 landed).

### Impact Explanation
A DeFi contract (lending pool, DEX, escrow, vault) built to accept CW20 deposits via `Send`/`SendFrom` on a pointer wrapping a fee-on-transfer ERC20 would credit the depositor for the nominal `amount` rather than the amount actually received. This creates a shortfall between recorded liabilities and actual backing assets in the receiving contract, which can be exploited to withdraw more value than was deposited — a concrete fund-loss/insolvency vector reachable by any unprivileged pointer user or contract deployer who registers a fee-on-transfer ERC20 and interacts with a CW20-consuming contract through the pointer.

### Likelihood Explanation
Likelihood is moderate: it requires (1) an ERC20 with fee-on-transfer/deflationary logic being pointer-registered (permissionless via the pointer precompile), and (2) a downstream CW20-consuming contract that trusts `Cw20ReceiveMsg.amount` instead of re-querying balances. Both conditions are realistic for third-party ERC20 tokens and typical CW20 receiver implementations, and no privileged access is required to trigger the mismatch — any transaction sender can register the pointer and initiate the `send`/`send_from` calls.

### Recommendation
In `transfer`/`transfer_from` (and by extension `execute_send`/`execute_send_from`), query the underlying ERC20 balance of the recipient (or of the pointer/owner context) before and after issuing the `DelegateCallEvm` transfer, and use the observed balance delta — not the caller-supplied `amount` — when populating `Cw20ReceiveMsg.amount` and the `transfer`/`transfer_from` response attributes. Alternatively, explicitly document/reject pointer registration for tokens whose `balanceOf` delta does not match the requested transfer amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 5% fee on `transfer`/`transferFrom`).
2. Register a CW20 pointer for it via the pointer precompile (`registerPointerForERC20`), instantiating the contract at `example/cosmwasm/cw20/src/contract.rs`.
3. Deploy a mock CW20-receiver contract that trusts `Cw20ReceiveMsg.amount` to credit an internal ledger.
4. Call `Send{contract: receiver, amount: 100, msg}` on the pointer.
5. Observe: `transfer(receiver, 100)` on the underlying ERC20 only delivers `95` tokens to `receiver`'s associated EVM address, but the receiver's CW20 hook is invoked with `amount = 100`, and the receiver contract credits `100` — a `5`-token accounting shortfall confirmed by comparing the receiver's real ERC20 balance (via `query_balance`) against its internally credited ledger.

Note: I could not fully confirm from the index whether `example/cosmwasm/cw20/src/contract.rs` is the exact bytecode compiled into the on-chain `POINTER_CW20`/CW20-wrapping-ERC20 pointer artifact used in production (vs. purely an example/reference implementation) — the repository's embed/wasm-binary wiring for this specific pointer type was not directly located within the available index. If it is only a reference/example and not the production pointer bytecode, this finding would not be reachable on-chain, and I'd recommend confirming the actual compiled pointer source before treating this as production-impacting.

    _env: Env,
    info: MessageInfo,

    amount: Uint128,
    msg: Binary,
) -> Result<Response<EvmMsg>, ContractError> {

        msg,
    };

        .add_message(cw20receive_into_cosmos_msg(contract.clone(), send)?)
        .add_attribute("action", "send");
    Ok(res)
}

fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}

pub fn transfer_from(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    owner: String,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&owner)?;
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_from_payload(owner.clone(), recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", owner)
        .add_attribute("to", recipient)
        .add_attribute("by", info.sender)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
