Confirmed: the conflict-detection model in `app/src/models/status.ts` has no notion of a conflict-entry identity (blob SHA) — `ConflictsWithMarkers`/`ManualConflict` only carry `entry` (side descriptors) and `conflictMarkerCount`, not the underlying `us`/`them` blob hashes of the specific conflict. This confirms that `_applyCopilotConflictResolutions` can only detect "resolved externally" (via `conflictMarkerCount === 0`), not "conflict content changed to a different conflict" — i.e., there is no equivalent of an "is this still eligible" check.

### Title
Stale Copilot-generated conflict resolution can be silently applied to a changed conflict, corrupting committed content - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated `resolvedContent` to disk for each conflicted path using only the file path as the correlation key, with no check that the on-disk conflict is still the same conflict (same `us`/`them` sides) that was analyzed when the resolution was produced.

### Finding Description
The Copilot conflict-resolution flow works in two disjoint phases:
1. `buildConflictContext` snapshots each conflicted file's raw content and conflict hunks and sends that as `ICopilotConflictContext` for resolution [1](#0-0) .
2. Later, when the user clicks "Continue Merge", `_applyCopilotConflictResolutions` looks up `state.multiCommitOperationState.copilotResolutions` (produced from step 1) and, for each resolution, checks only whether the file `isConflictedFileStatus` and `!hasUnresolvedConflicts` (i.e., whether conflict markers are gone), then overwrites the file with the stored `resolvedContent` and stages it [2](#0-1) .

The only staleness guard present is "did the user resolve markers manually in an editor" — it does not verify that the conflict entry itself (the specific `us`/`them` pair, i.e., which commits/branches are being merged) is unchanged since the resolution was generated. This mirrors the ADL bug pattern exactly: a decision (which files/which content to apply) was computed against a snapshot of state, and the only re-check performed at execution time is a narrow, unrelated invariant (`conflictMarkerCount === 0`), not "is this still the same conflict I analyzed."

`ConflictsWithMarkers`/`ManualConflict` status types carry no blob-identity fields (no `us`/`them` SHAs), only side labels and a marker count [3](#0-2) , so the app has no data available even in principle to detect "this is now a different conflict at the same path" without adding such tracking.

A realistic path for the underlying conflict to change between analysis and application: the user aborts the in-progress merge/rebase/cherry-pick from the Copilot result dialog (`onAbort`) and restarts the multi-commit operation against a different `theirBranch`/remote-tracking ref (e.g., after a background fetch from an attacker-controlled remote updates the tracking branch, or the user picks a different branch to merge) while `copilotResolutions` from the previous analysis are not guaranteed to be cleared/invalidated before the new conflict step is entered, because the correlation is by `path` string only, not by conflict identity.

### Impact Explanation
If a stale resolution is applied, `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` silently overwrites the working copy of a conflicted file with content that was computed for a different `theirs`/`ours` pairing than what is currently staged for commit, and the resulting content is subsequently `git add`-ed and committed as the merge resolution [4](#0-3) . This is a silent corruption of what the user commits/pushes — the exact impact class called out as valid ("silent corruption of what the user commits or pushes"), reached through a git/remote-driven state change rather than any local/admin action.

### Likelihood Explanation
This requires a specific sequence (Copilot resolution computed → user aborts/changes the operation target before continuing → resolution map not fully invalidated), which is a narrower trigger window than the original GMX report's "keeper races position size" scenario, but the missing invariant is structurally identical: the code checks a global/local proxy state ("are there still conflict markers") instead of validating that the specific decision (this resolution, for this conflict) is still valid for the current state. I could not fully verify from the available index whether `copilotResolutions`/`multiCommitOperationState` are reset on every branch-selection change in the choose-branch dialogs (the grep results found 13 occurrences of `copilotResolutions` in `app-store.ts` but I was not able to inspect all of them within available iterations), so likelihood should be treated as uncertain until that reset behavior is confirmed by a Devin session with full file access.

### Recommendation
Add an explicit "is this resolution still applicable" check before applying a stored Copilot resolution: compare a stable identity for the current conflict (e.g., the `us`/`them` blob OIDs from `git ls-files -u`, or at minimum the `ourBranch`/`theirBranch` tip SHAs recorded when the resolution was generated) against the conflict currently on disk, and refuse to apply / re-surface for re-analysis if they differ, rather than relying solely on `conflictMarkerCount === 0`.

### Proof of Concept
Conceptual reproduction (not independently executed, based on code reading only):
1. Start a merge with conflicts; trigger Copilot conflict resolution, which computes `resolvedContent` based on the current `ourBranch`/`theirBranch` conflict hunks.
2. While the Copilot result dialog is open, use `onAbort` to abort the merge, then start a new merge/rebase against a different branch/remote ref that happens to touch the same file path and produce a conflict again.
3. If `copilotResolutions` from step 1 are not cleared before entering the new conflict step, click "Continue Merge" on the new dialog: `_applyCopilotConflictResolutions` finds a resolution entry keyed by the same `path`, sees the file `isConflictedFileStatus` and has unresolved markers (fresh conflict), and overwrites it with the stale `resolvedContent` from the first (now-irrelevant) conflict, which then gets staged and committed.

Note: I was unable to fully trace, within the tool budget, every code path that sets/clears `multiCommitOperationState.copilotResolutions` (13 references in `app-store.ts` not all inspected), so confirmation that the stale-resolution window is actually reachable end-to-end would need a follow-up Devin session with full-file access.

export type ConflictsWithMarkers = {
  kind: AppFileStatusKind.Conflicted
  entry: TextConflictEntry
  conflictMarkerCount: number
  submoduleStatus?: SubmoduleStatus
}

/**
 * Details about a file marked as conflicted in the index which needs to be
 * resolved manually by the user.
 */
export type ManualConflict = {
  kind: AppFileStatusKind.Conflicted
  entry: ManualConflictEntry
  submoduleStatus?: SubmoduleStatus
}

/** Union of potential conflict scenarios the application should handle */
export type ConflictedFileStatus = ConflictsWithMarkers | ManualConflict

/** Custom typeguard to differentiate Conflict files from other types */
export function isConflictedFileStatus(
  appFileStatus: AppFileStatus
): appFileStatus is ConflictedFileStatus {
  return appFileStatus.kind === AppFileStatusKind.Conflicted
}

/** Custom typeguard to differentiate ConflictsWithMarkers from other Conflict types */
export function isConflictWithMarkers(
  conflictedFileStatus: ConflictedFileStatus
): conflictedFileStatus is ConflictsWithMarkers {
  return conflictedFileStatus.hasOwnProperty('conflictMarkerCount')
}

/** Custom typeguard to differentiate ManualConflict from other Conflict types */
export function isManualConflict(
  conflictedFileStatus: ConflictedFileStatus
): conflictedFileStatus is ManualConflict {
  return !conflictedFileStatus.hasOwnProperty('conflictMarkerCount')
}
