### Title
Validator staking weight is derived from a staking contract's raw native balance, allowing anyone to inflate reward/consensus weight via a plain KAIA transfer - ([File: kaiax/staking/impl/getter.go])

### Summary
The Merlin Lab incident stemmed from `MerlinStrategyAlpacaBNB` treating BNB the attacker simply *transferred* to the contract as legitimate "mining revenue," letting the attacker mint outsized MERL rewards purely by sending native tokens rather than performing the intended economic action. The analogous pattern in kaia's reward/staking pipeline is that a validator's `StakingAmount` — the figure that drives both reward distribution weight (`kaiax/reward`) and (indirectly) validator eligibility — is computed from the **native token balance** of the registered CN staking contract address, not from an accounted, function-gated "staked" ledger entry.

### Finding Description
`StakingModule.getFromState` reads staking amounts via a MultiCall against the `AddressBook` contract [1](#0-0) , and `parseCallResult`/`parsePermissionlessCallResult` convert the returned `amounts` directly into `StakingAmounts` by dividing by `params.KAIA` [2](#0-1) [3](#0-2) .

The test fixtures make explicit that these "amounts" are simply the native balance held at the registered staking address, with no bookkeeping of how that balance got there: `Balance: new(big.Int).Mul(big.NewInt(42_000_000), big.NewInt(params.KAIA))` is set directly on the staking contract's genesis account and is expected to appear verbatim as the `StakingAmount` [4](#0-3) . This confirms the underlying `AddressBook`/`MultiCall` on-chain logic reports `address(stakingContract).balance` (or an equivalent raw-balance read) rather than an internally tracked "amount actually staked via the staking function."

This `StakingAmount` then feeds directly into consensus-weight and reward-weight calculations:
- `assignStakingRewards`/`assignStakingRewardsFlex` distribute the staker reward pool proportionally to `cn.StakingAmount` exceeding `MinimumStake`/`StakingRewardThreshold` [5](#0-4) [6](#0-5) .
- `collectStakingAmounts` in the valset module uses the same `StakingAmount` to determine demotion/promotion eligibility for the validator set [7](#0-6) .

Because `CnStakingV4` (and legacy CN staking contracts) expose a plain `receive()`/fallback payable function [8](#0-7) , **any unprivileged transaction sender can send a plain native-token transfer to a registered CN staking contract address**, increasing its balance without going through any staking/locking accounting. If the reported `StakingAmount` used by governance/reward/valset is sourced from this raw balance (as the test fixtures and code path above strongly indicate for at least the legacy `AddressBook` code path), the sender (or a colluding node operator) can artificially inflate:
1. The staker's share of the block staking-reward pool (`assignStakingRewards`), redirecting minted-token rewards, and
2. The staker's weight for validator promotion/demotion decisions.

This mirrors the Merlin Lab root cause exactly: a value transfer that was never intended as an economic commitment (a plain top-up, not a "stake" call) is mistakenly counted as the metric that drives reward issuance.

### Impact Explanation
If validator/staking weight can be inflated by simply transferring native KAIA to a public, non-privileged contract address, an attacker (or any staker wanting extra yield) can cheaply increase their share of block rewards (Kore/Prague staking reward pool, see `assignStakingRewards`) beyond what their legitimately locked stake justifies, and potentially tip validator promotion decisions. This constitutes reward redirection / supply-accounting corruption reachable from a single, unprivileged transaction.

### Likelihood Explanation
The action requires only a standard value-transfer transaction from any account to a known, public CN staking contract address (these addresses are public in `AddressBook`). No special privileges, governance access, or validator role are needed to send the transfer. However, whether the *actual* on-chain `AddressBook`/staking-contract logic differentiates the "staking balance" state variable from the raw `address(this).balance` (e.g., some CnStaking versions may track a separate `staking` counter incremented only in the `delegate()`/staking functions, as suggested by `CnStakingV4.Staking()` return a stored variable rather than raw balance) is not directly verifiable from the indexed contents available. The genesis-state test fixtures for `kaiax/staking` set the balance directly and expect it to equal `StakingAmount`, which is consistent with a raw-balance read, but the production `AddressBook`/`CnStakingV4` Solidity source computing the amount actually reported to `MultiCall` was not found in the indexed contents (only bindings/mocks were available), so this cannot be treated as fully confirmed against the real contract logic.

### Recommendation
Verify whether the `AddressBook` (and `AddressBookV2`) contracts report a staking contract's "amount" as `address(stakingContract).balance` versus an internally accounted `staking` variable that is only incremented through authorized `stake()`/`delegate()` calls (as `CnStakingV4.Staking()` getter suggests it may already do). If raw balance is used anywhere in the amount computation path (legacy `AddressBook` in particular), change it to use the accounted staking variable so that unsolicited/plain-transfer top-ups cannot inflate reward or valset weight. Add an invariant test ensuring that a direct value transfer to a CN staking contract (bypassing `stake()`/`delegate()`) does not change the `StakingAmount` reported by `kaiax/staking.GetStakingInfo`.

### Proof of Concept
1. Identify a registered CN staking contract address from `AddressBook` (public information).
2. From any unprivileged EOA, send a plain value-transfer transaction (or call the contract's `receive()`) with an arbitrary amount of native KAIA to that address — no `stake()`/`delegate()` call needed, as shown by the exposed `Receive()` payable binding [9](#0-8) .
3. On the next staking-interval boundary, query `kaia_getStakingInfo` / observe `assignStakingRewards` allocation — if the reported `StakingAmount` (and thus reward share) increases by the transferred amount without the sender having gone through the legitimate staking flow, the analog vulnerability is confirmed, mirroring the Merlin Lab pattern of treating a transferred balance as legitimate protocol-tracked revenue/stake.

```go
		return nil, staking.ErrMultiCallCall(err)
```

```go
// assignStakingRewardsFlex assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewardsFlex(config *reward.RewardConfig, budget *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		minStake  = config.MinimumStake.Uint64()
		threshold = config.StakingRewardThreshold.Uint64()
		isPrague  = config.Rules.IsPrague

		cns            = si.ConsolidatedNodes()
		excessInt      = make(map[common.Address]uint64)
		totalExcessInt = uint64(0)
	)

	// Calculate the excess stakes (the amount over the threshold) for each CN.
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it. Even if (CNStaking + CLStaking) could be more than minStake,
		// the CNStaking alone must be at least minStake to be eligible.
		if cn.StakingAmount < minStake {
			continue
		}

		amount := cn.StakingAmount
		if isPrague && cn.CLStakingInfo != nil {
			amount += cn.CLStakingInfo.CLStakingAmount
		}

		// Excess is the amount over the threshold (not over minStake).
		if amount > threshold {
			excessInt[cn.RewardAddr] = amount - threshold
			totalExcessInt += excessInt[cn.RewardAddr]
		}
	}

	// Distribute the budget to the CNs based on the excess stakes.
	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(budget)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		if excessInt[cn.RewardAddr] <= 0 {
			continue
		}
		excess := new(big.Int).SetUint64(excessInt[cn.RewardAddr])

		// The KAIA unit will cancel out:
		// reward (kei) = excess (KAIA) * budget (kei) / totalExcess (KAIA)
		reward := new(big.Int).Div(new(big.Int).Mul(excess, budget), totalExcess)
		if reward.Sign() <= 0 {
			continue
		}

		// If Prague and CL is configured for this CN, split the reward between CN and CL.
		if isPrague && cn.CLStakingInfo != nil {
			cnAmount, clAmount := cn.Split(reward)
			alloc[cn.RewardAddr] = cnAmount
			alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
		} else {
			alloc[cn.RewardAddr] = reward
		}
		remaining.Sub(remaining, reward)
	}
	return alloc, remaining
```

```go
// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
```

```go
// TODO-kaiax: move the feature into staking_info.go
// collectStakingAmounts returns the staking amounts for the given nodes(i.e., the registered validator set).
// The staking amount for each node is determined based on the consolidated nodes,
// which aggregate stakes across multiple staking contracts that share the same reward address.
// Under a single RewardAddr, only one representative NodeId is included in the validator set,
// and that NodeId will be assigned the total aggregated stake.
//
// for example, consolidated nodes:
//
//	CN1 = {[N1,N2], [S1,S2], R1, A1+A2}
//	CN3 = {[N3],    [S3],    R3, A3}
//
// Given nodes = [N2, N3], the resulting stakingAmounts will be:
//
//	{N2: A1 + A2, N3: A3}
//
// Note: This function assumes that validator registration is controlled,
// and that only one NodeId per reward address can be part of the validator set.
// If this assumption changes, this logic may need to be revisited.
func collectStakingAmounts(nodes []common.Address, si *staking.StakingInfo) map[common.Address]float64 {
	cns := si.ConsolidatedNodes()
	stakingAmounts := make(map[common.Address]float64, len(nodes))
	for _, node := range nodes {
		stakingAmounts[node] = 0
	}
	for _, cn := range cns {
		for _, node := range cn.NodeIds {
			if _, ok := stakingAmounts[node]; ok {
				stakingAmounts[node] = float64(cn.StakingAmount)
			}
		}
	}
	return stakingAmounts
}
```
