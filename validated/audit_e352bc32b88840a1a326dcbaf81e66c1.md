### Title
Panic on out-of-set Participant in blame evaluation crashes the DKG blame handler - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`BlameMachine::blame_internal` and `Decryption::decrypt_with_proof` index `HashMap`s (`self.commitments[&sender]`, `self.enc_keys[&decryptor]`) keyed only by the participants registered during the DKG (indexes `1..=n`). The public `BlameMachine::blame` / `AdditionalBlameMachine::blame` APIs accept arbitrary `sender`/`recipient` `Participant` values (any non-zero `u16`, per `crypto/dkg/src/lib.rs`). Passing a `Participant` that is syntactically valid but not a member of the DKG panics instead of returning an error — a crash triggered purely by attacker-influenced accusation fields, analogous to the LES `GetProofsV2` crash-on-request class (CVE-2020-26264).

### Finding Description
Two unchecked indexing sites:

```rust
// crypto/dkg/pedpop/src/encryption.rs (decrypt_with_proof)
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],   // panics if decryptor not registered
)
```

```rust
// crypto/dkg/pedpop/src/lib.rs (blame_internal)
if !bool::from(
  multiexp_vartime(&share_verification_statements::<C>(
    recipient,
    &self.commitments[&sender],              // panics if sender not in commitments
    Zeroizing::new(share),
  ))
```

`enc_keys` and `commitments` are populated exclusively for `1..=n` (`AdditionalBlameMachine::new`, `pedpop/src/lib.rs:656-660`; `Decryption::register`, `encryption.rs:351-362`). `Participant` accepts any non-zero `u16`, so a `blame` call naming e.g. `Participant::new(n + 1)` or any non-member index reaches the indexing panics. The panic paths are reached only when the earlier `verify`/`from_repr` checks pass, but the `sender` panic at `self.commitments[&sender]` fires whenever decryption succeeds — i.e., whenever the accused message is well-formed — so an accusation naming a non-existent sender with any validly-formed `EncryptedMessage` (readable via `EncryptedMessage::read`, `encryption.rs:171-177`) triggers it.

### Impact Explanation
Same class as the reference advisory: a request that deserializes cleanly crashes the evaluating node. Any deployment calling `blame()`/`AdditionalBlameMachine::blame` on accusation data carrying peer-supplied `Participant` indexes aborts on panic, killing the validator/blame-evaluation process. Note the library's own docstring (`pedpop/src/lib.rs:645-648`) only warns about *invalid commitment messages* causing panics — it does not document that out-of-range `sender`/`recipient` indexes to `blame()` are UB, so this is an undocumented panic surface.

### Likelihood Explanation
`sender` and `recipient` are direct function arguments typically populated from deserialized blame/accusation messages (`accuser`/`faulty` fields). Serai's coordinator does pre-validate these (`handle.rs:474-492` checks `range.contains(&accuser)` and `DkgShare::get(accuser, faulty)`), which mitigates the in-tree path — but the library is a standalone crate (`serai--025/crypto/dkg/pedpop`) intended for external integrators, and nothing in its API prevents or documents the panic. Severity Medium: a reachable crash with an in-tree mitigating layer.

### Recommendation
Replace the indexing lookups with fallible accessors:

```rust
let Some(sender_commitments) = self.commitments.get(&sender) else { return sender };
let Some(decryptor_key) = self.enc_keys.get(&decryptor) else { return recipient };
```

(or return a `Result`/`PedPoPError::MissingParticipant`). Apply the same fix to `Encryption::encrypt` (`encryption.rs:466`, `self.decryption.enc_keys[&participant]`).

### Proof of Concept
```rust
let machine = AdditionalBlameMachine::<Ristretto>::new(context, n, commitment_msgs)?;
// Attacker supplies an accusation naming a participant index outside the DKG
let bad_sender = Participant::new(n + 40).unwrap();
// msg: any EncryptedMessage whose PoP verifies (e.g., self-produced by attacker)
machine.blame(bad_sender, Participant::new(1).unwrap(), msg, None);
// -> panic at self.enc_keys[&decryptor] if proof is Some,
//    or self.commitments[&bad_sender] once decryption succeeds
```

Caveat: I verified the panic sites and map-population logic in `pedpop`, but could not fully trace every downstream caller (e.g., the processor's `VerifyBlame` handler) within the iteration budget; the in-tree coordinator partially guards the inputs, so the clearest exposure is via the library API itself.
