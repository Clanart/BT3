## Title
Argument injection via unsanitized git ref names (leading `-`) reaching `git()`/`spawnGit` positional arguments - (File: `app/src/lib/git/core.ts`, `app/src/lib/git/spawn.ts`)

### Summary
`getBranches()` reads ref names directly from `git for-each-ref` output (`%(refname:short)`) with no filtering of the returned strings, and `sanitizedRefName()` — the only place Desktop rejects a leading `-`/`+` — is applied solely to *user-typed* text in the branch/tag creation UI, not to names originating from a fetched/cloned repository's actual refs. Several call sites (e.g. `push()` and `deleteRemoteBranch()` in `app/src/lib/git/branch.ts`/`push.ts`) then splice these names directly as positional arguments into `git` invocations without a preceding `--` end-of-options marker.

### Finding Description
- `sanitizedRefName()` strips a leading run of `-`/`+` characters, but its regex (`invalidCharacterRegex` plus `.replace(/^[-\+]*/g, '')`) does not otherwise forbid `-` appearing elsewhere in a name, and — critically — it is only invoked from UI input components such as `RefNameTextBox` (`app/src/ui/lib/ref-name-text-box.tsx:90,174,196`) and `AddWorktreeDialog` (`app/src/ui/worktrees/add-worktree-dialog.tsx:75`). It is never applied to ref names that Desktop reads back from git itself. [1](#0-0) 
- `getBranches()` builds `Branch` objects straight from `%(refname:short)` output with no validation of the shortname's first character: [2](#0-1) 
- Those `Branch` objects (and their `remoteName`/`nameWithoutRemote`) are later used as raw argv elements in commands such as `push()` — `['push', remote.name, localBranch]` with no leading `--` — and `deleteRemoteBranch()` — `['push', remote.name, ':' + remoteBranchName]`: [3](#0-2) [4](#0-3) 
- All of these eventually funnel through `git()` in `app/src/lib/git/core.ts`, which passes `args` straight into dugite's `exec(args, path, ...)`, and `spawnGit` in `app/src/lib/git/spawn.ts` passes `args` straight into dugite's `spawn(args, path, ...)`: [5](#0-4) [6](#0-5) 
- Because dugite invokes the git binary via `child_process` with an argv array (no shell), there is no shell-metacharacter injection risk, but that same argv-array mechanism provides **no protection against argument/flag injection** — a string beginning with `-` immediately after `push <remote>` (or similar) is parsed by git itself as an option rather than a literal refname/argument. This is exactly the class of bug that other call sites in the codebase (`checkout.ts`, `diff.ts`, `add.ts`, `rm.ts`, `apply.ts`, `reset.ts`, etc.) already defend against by inserting `--` before user-controlled data: [7](#0-6) 

However, exploitability hinges on one fact I could **not verify from the indexed source alone**: whether the bundled/embedded `git` binary's own low-level ref validation (`check_refname_format` in git's `refs.c`) actually permits a ref component beginning with `-` to exist in the refs database at all (as opposed to only git's higher-level porcelain, e.g. `git branch <name>`, refusing to *create* such a name). If git's ref-format layer already rejects leading-dash components universally (irrespective of how the ref was created — via push, low-level `update-ref`, or receive-pack), then a hostile remote could never actually get such a ref into the victim's `refs/remotes/*` in the first place, and the described chain would be unreachable. Desktop's own tests (`app/test/unit/sanitize-ref-name-test.ts:30-34`) only demonstrate that Desktop *chooses* to strip a leading `-` for names it lets the user type — they don't demonstrate that git itself permits or forbids receiving such a name from a remote via `for-each-ref`/`fetch`. I do not have terminal/browser access to run the proof-of-concept described in the question (`git(['branch', '--upload-pack=evil'], ...)` against a temp repo) to confirm whether git rejects it, so I cannot confirm actual exploitability end-to-end.

### Impact Explanation
If a hostile remote/fork can indeed publish a branch whose name begins with `-` (e.g. `-o`, `--upload-pack=...`, `--exec=...`), and the victim adds it as a remote/fetches it in GitHub Desktop, subsequent Desktop-initiated operations that place the branch name as a bare positional argument (`push`, `deleteRemoteBranch`) could have that string parsed by git as a flag instead of a refname. Depending on which flag is smuggled, this could range from corrupting the push (denial of an intended operation) up to remote/local command execution via git's own `--upload-pack=<path>`/`--receive-pack=<path>``-style options that specify an arbitrary program to invoke, which would be Critical if reachable.

### Likelihood Explanation
Low-to-Medium given current unknowns. It requires: (1) confirming git itself will store/return a ref component starting with `-` when received via fetch/for-each-ref (not proven here), and (2) the victim performing a follow-on action (push/delete) on that specific branch. Desktop's UI-level `sanitizedRefName` protections do not cover this path, and several sink call sites (`push.ts`, `branch.ts:deleteRemoteBranch`) lack the `--` hardening that other call sites already have, which is a real gap even if git's own validation happens to close the door in practice.

### Recommendation
- Apply `testForInvalidChars`/a hardened check (rejecting any refname component or shortname beginning with `-`) to branch/tag names sourced from `getBranches()`/`for-each-ref` output before they are used in any subsequent `git` invocation, not just to user-typed input.
- Add `--` end-of-options markers before branch/remote-derived positional arguments in `push()` (`app/src/lib/git/push.ts`) and `deleteRemoteBranch()` (`app/src/lib/git/branch.ts`), mirroring the pattern already used in `checkout.ts`, `add.ts`, `rm.ts`, `diff.ts`, and `apply.ts`.
- Independently confirm (this requires running the bundled git binary, which I could not do here) whether `check_refname_format` in the vendored git version actually rejects leading-dash ref components on `receive-pack`; if it does not, the recommendation above is necessary to close a real gap. A background Devin session with terminal access could run the proof-of-concept in the question to settle this definitively.

### Proof of Concept
