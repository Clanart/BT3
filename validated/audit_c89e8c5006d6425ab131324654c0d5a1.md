### Title
Unchecked u32 Subtraction in `calculate_new_difficulty` Silently Corrupts Difficulty in the Header-Chain ZK Circuit — (`File: circuits-lib/src/header_chain/mod.rs`)

### Summary

`calculate_new_difficulty` performs a bare u32 subtraction `last_timestamp - epoch_start_time` without overflow protection. In the RISC Zero zkVM guest (compiled at `opt-level = 3`, i.e., release mode), integer underflow wraps silently. When `epoch_start_time > last_timestamp` — a condition that is valid under Bitcoin's MTP rule — the wrapped value is clamped to `EXPECTED_EPOCH_TIMESPAN * 4`, forcing the next epoch's difficulty to be 4× easier than it should be. Every subsequent block in the same proof run is then validated against this artificially relaxed target, and the accumulated `total_work` is proportionally understated. The header-chain proof that the bridge circuit consumes is therefore incorrect, and a chain with 4× less real proof-of-work can pass circuit verification.

### Finding Description

`calculate_new_difficulty` is called inside `apply_block_headers` at every epoch boundary (every 2016 blocks):

```rust
// circuits-lib/src/header_chain/mod.rs  line 499-505
if !IS_REGTEST && self.block_height % BLOCKS_PER_EPOCH == BLOCKS_PER_EPOCH - 1 {
    current_target_bytes = calculate_new_difficulty(
        self.epoch_start_time,
        block_header.time,
        self.current_target_bits,
    );
    self.current_target_bits = target_to_bits(&current_target_bytes);
}
```

Inside `calculate_new_difficulty`:

```rust
// line 640
let mut actual_timespan = last_timestamp - epoch_start_time;   // ← bare u32 sub
if actual_timespan < EXPECTED_EPOCH_TIMESPAN / 4 {
    actual_timespan = EXPECTED_EPOCH_TIMESPAN / 4;
} else if actual_timespan > EXPECTED_EPOCH_TIMESPAN * 4 {
    actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4;              // ← clamped here
}
``` [1](#0-0) 

Bitcoin's MTP rule only requires each block's timestamp to be strictly greater than the median of the previous 11 timestamps. It does **not** require the last block of an epoch to have a timestamp ≥ the first block of the epoch. A chain where timestamps drift backwards within an epoch (while still satisfying MTP) is consensus-valid. In that case `epoch_start_time > last_timestamp`, the subtraction wraps to a value near `u32::MAX`, the `> EXPECTED_EPOCH_TIMESPAN * 4` branch fires, and `actual_timespan` is fixed at `EXPECTED_EPOCH_TIMESPAN * 4`. The resulting new target is:

```
new_target = current_target × (EXPECTED_EPOCH_TIMESPAN × 4) / EXPECTED_EPOCH_TIMESPAN
           = current_target × 4
```

This is the maximum allowed upward adjustment (4× easier). All blocks processed after this epoch boundary in the same `apply_block_headers` call are validated against this inflated target, and `work_to_add` per block is proportionally smaller, so `total_work` is understated. [2](#0-1) 

The header-chain circuit is the root proof consumed by the bridge circuit and the work-only circuit. A `ChainState` with a corrupted `current_target_bits` and understated `total_work` is committed as the circuit output and propagated to downstream bridge verification. [3](#0-2) 

### Impact Explanation

An attacker who can present a header chain where one epoch boundary satisfies `epoch_start_time > last_timestamp` can mine all subsequent blocks in that proof batch at 4× the normal target (i.e., with 4× less hash-rate). The bridge circuit, which relies on the header-chain proof for chain validity, would accept this weaker chain as legitimate. Depending on how the bridge circuit uses `total_work` and `current_target_bits`, this could allow:

- Acceptance of a forged or low-work Bitcoin chain as the canonical chain, enabling fraudulent deposit finalization or withdrawal authorization.
- Incorrect difficulty state propagated into chained proofs (each subsequent `PrevProof` inherits the corrupted `ChainState`), compounding the error across multiple proof batches. [4](#0-3) 

### Likelihood Explanation

On mainnet, timestamps almost never decrease across a full 2016-block epoch, making accidental triggering extremely unlikely. However, a sophisticated adversary with moderate mining power could deliberately craft a chain where the last block of an epoch carries a timestamp slightly below `epoch_start_time` (which is valid under MTP) and then mine the next epoch at the 4× easier target. On testnet4, where timestamps are more erratic and difficulty is lower, the condition is easier to reach. The RISC Zero guest is compiled in release mode (wrapping arithmetic), so there is no panic — the corruption is silent and the proof is generated successfully.

### Recommendation

Replace the bare subtraction with a saturating or checked subtraction, and treat the underflow case as a zero (or minimum-clamped) timespan:

```rust
fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target: u32,
) -> [u8; 32] {
    // Use saturating_sub: if last_timestamp < epoch_start_time, treat as 0
    // which will then be clamped up to EXPECTED_EPOCH_TIMESPAN / 4.
    let raw_timespan = last_timestamp.saturating_sub(epoch_start_time);
    let mut actual_timespan = raw_timespan;
    if actual_timespan < EXPECTED_EPOCH_TIMESPAN / 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN / 4;
    } else if actual_timespan > EXPECTED_EPOCH_TIMESPAN * 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4;
    }
    // ... rest unchanged
}
```

This matches Bitcoin Core's own handling, which treats a negative timespan as the minimum clamped value. [5](#0-4) 

### Proof of Concept

1. Construct a 2016-block chain where:
   - Block 0 of the epoch has `time = T` (this becomes `epoch_start_time`).
   - Each subsequent block satisfies MTP (timestamp > median of previous 11).
   - Block 2015 (last of the epoch) has `time = T - 1` (valid under MTP if the median of its 11 predecessors is < `T - 1`).
2. Feed this chain to `apply_block_headers`. At block 2015, `calculate_new_difficulty(T, T-1, bits)` is called.
3. `T - 1 - T` wraps to `u32::MAX` in release mode. The `> EXPECTED_EPOCH_TIMESPAN * 4` branch fires; `actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4`.
4. `new_target = current_target × 4` — the easiest allowed adjustment.
5. Append 2016 more blocks mined at this 4× easier target. Each block passes `check_hash_valid` and `assert_eq!(block_header.bits, expected_bits)` because `expected_bits` was derived from the corrupted target.
6. The resulting `BlockHeaderCircuitOutput` contains a `ChainState` with `total_work` that is ~4× less than a legitimately mined chain of the same length, yet the proof verifies successfully.
7. Submit this proof to the bridge circuit as the header-chain input; the bridge accepts the low-work chain as canonical. [6](#0-5) [7](#0-6)

fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target: u32,
) -> [u8; 32] {
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < EXPECTED_EPOCH_TIMESPAN / 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN / 4;
    } else if actual_timespan > EXPECTED_EPOCH_TIMESPAN * 4 {
        actual_timespan = EXPECTED_EPOCH_TIMESPAN * 4;
    }

    let current_target_bytes = bits_to_target(current_target);
    let mut new_target = U256::from_be_bytes(current_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(EXPECTED_EPOCH_TIMESPAN));

    if new_target > NETWORK_CONSTANTS.max_target {
        new_target = NETWORK_CONSTANTS.max_target;
    }
    new_target.to_be_bytes()
}
