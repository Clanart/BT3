### Title
Integer Truncation in `WomUp.initializeRewards` Permanently Locks Unstreamed MGP Rewards - (File: `wombat/WomUp.sol`)

### Summary
`WomUp` is a Synthetix-style staking-rewards contract that streams MGP to WOM-stakers (who receive `mWom`) over a fixed `duration` (7 days). The reward rate is computed with plain integer division of the MGP balance by `duration`, discarding the remainder, and the contract has no mechanism to recover or re-stream that remainder once the period starts. This mirrors the reported bug class (rate truncation over a fixed period, with the residual permanently lost) found in the external report's `IncentiveGauge._upsertIncentive`.

### Finding Description
In `initializeRewards()`, the reward rate is derived from the full MGP balance divided by the fixed `duration`: [1](#0-0) 

```solidity
function initializeRewards() external onlyOwner returns (bool) {
    if(rewardRate > 0) revert MustZero();

    uint256 rewardsAvailable = IERC20(mgp).balanceOf(address(this));
    if(rewardsAvailable == 0) revert MustNotZero();

    rewardRate = rewardsAvailable / (duration);

    lastUpdateTime = block.timestamp;
    periodFinish = block.timestamp + (duration);

    emit RewardAdded(rewardsAvailable);

    return true;
}
```

`duration` is fixed to 7 days in the initializer: [2](#0-1) . `rewardsAvailable % duration` is truncated by the integer division and is never accounted for anywhere.

Streaming is bounded strictly by `rewardRate * (elapsed time capped at periodFinish)`: [3](#0-2) 

The total amount that can ever be streamed to all stakers over the lifetime of the pool is `rewardRate * duration`, which is strictly less than `rewardsAvailable` whenever `rewardsAvailable` is not an exact multiple of `duration`. There is no code path that redistributes or reclaims this remainder:
- `initializeRewards()` can only be called once (guarded by `if(rewardRate > 0) revert MustZero();`), so the rate is never recomputed to absorb the leftover dust.
- `rescueReward()` can only pull out the MGP balance before the stream starts (`if(block.timestamp >= startTime || rewardRate > 0) revert AlreadyStarted();`) [4](#0-3) , so once the stream is active the owner cannot recover the residual either.
- There is no "top-up"/"donate" function analogous to `BaseRewardPool.donateRewards` that would let the leftover be folded back into distribution.

As a result, the truncated remainder of MGP tokens is permanently stuck in the `WomUp` contract balance, unreachable by both stakers and the owner, exactly the "dust becomes permanently locked" pattern described in the external report.

### Impact Explanation
Any amount of MGP funded into `WomUp` that is not an exact multiple of `604800` (seconds in `duration`) results in `rewardsAvailable % 604800` MGP being permanently frozen with no recovery path — this is a permanent freezing of unclaimed yield belonging to WOM/mWom stakers (and effectively a loss to the protocol treasury that funded the rewards). This satisfies the "permanent freezing of unclaimed yield" bar, since the funds are inaccessible for the lifetime of the contract, not just a temporary delay.

### Likelihood Explanation
This is deterministic and requires no attacker — it fires automatically on every legitimate call to `initializeRewards()` by the owner, since MGP token amounts funded to the contract are extremely unlikely to be an exact multiple of `604800` wei-scaled units. Because `initializeRewards()` is callable only once and irreversibly locks `rewardRate`, the dust is guaranteed to occur once, at contract initialization, with no repeated top-up path to compound it (unlike the original multi-top-up scenario), but the loss is still permanent once it occurs.

### Recommendation
Round `rewardsAvailable` down to a multiple of `duration` before setting `rewardRate`, and either:
1. Transfer the truncated remainder back to the funder/owner immediately in `initializeRewards()`, or
2. Track the remainder in a `pendingRemainder` accumulator so a subsequent funding round can add it back to reach a clean multiple of `duration`.

Concretely:
```solidity
uint256 effective = (rewardsAvailable / duration) * duration;
uint256 remainder = rewardsAvailable - effective;
rewardRate = effective / duration;
if (remainder > 0) {
    IERC20(mgp).safeTransfer(owner(), remainder); // or accumulate for next funding
}
```

### Proof of Concept
Given `duration = 7 days = 604800` seconds:
1. Owner sends `100_000_000` wei of MGP (or any amount not divisible by 604800) to the `WomUp` contract.
2. Owner calls `initializeRewards()`. `rewardRate = 100_000_000 / 604800 = 165` (floor), so `rewardRate * duration = 165 * 604800 = 99,792,000`.
3. `dust = 100_000_000 - 99,792,000 = 208,000` wei of MGP.
4. Over the full 7-day period, `rewardPerToken()`/`earned()` can only ever account for `rewardRate * duration = 99,792,000` wei of MGP being distributed to stakers via `getReward()`.
5. After `periodFinish`, `rewardRate` remains fixed at `165` and cannot be reset (`initializeRewards()` reverts with `MustZero()` since `rewardRate > 0`); `rescueReward()` also reverts since `rewardRate > 0`.
6. The `dust = 208,000` wei of MGP remains in the `WomUp` contract balance forever, unclaimable by any user or the owner. [1](#0-0) [4](#0-3)
