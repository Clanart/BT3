### Title
Attacker-controlled participant count in `ThresholdKeys::read` forces oversized allocation before parameter validation - (File: crypto/dkg/src/lib.rs)

### Summary
The analog of CVE-2017-7624 (crafted input causing excessive memory consumption) exists in `ThresholdKeys::read`: a u16 `n` field read directly from untrusted bytes drives `Vec::with_capacity(n)` for the `Interpolation::Constant` coefficient vector and a loop inserting `n` entries into a `HashMap` of verification shares, all before `ThresholdParams::new(t, n, i)` is invoked to validate the parameters. A short crafted blob therefore causes a disproportionate allocation (~2 MB for the coefficient vector alone at `n = 65535`, plus ~4+ MB of `HashMap`/point storage when enough bytes are supplied), yielding large allocation amplification per input byte.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs`), the deserialization order is:

1. `t`, `n`, `i` are read as raw u16s (lines 591–602). No bound is applied to `n` at this point.
2. If the interpolation tag byte is `0`, `Interpolation::Constant` immediately executes `Vec::with_capacity(usize::from(n))` and then reads `n` field elements (lines 607–613).
3. `n` verification shares are read and inserted into a `HashMap` keyed by `Participant` (lines 620–623).
4. Only at the end is `ThresholdParams::new(t, n, i)` called to validate the parameter set (lines 625–626).

The attacker controls `n` (and the tag byte) with a handful of input bytes. Because allocation and the `HashMap` population happen before validation, a blob can claim `n = 65535`:

- `Vec::with_capacity(65535)` reserves ~2 MB instantly, even if the stream then hits EOF.
- If the attacker supplies the body, `65535 × 32` bytes of `C::F` coefficients plus `65535 × ~33` bytes of `Ristretto` points are stored, producing a `ThresholdKeys` object backed by several MB of heap memory from a single small logical message.

This is reachable wherever untrusted bytes are fed to `ThresholdKeys::read` (an in-scope, listed entry point), e.g. key material loaded or transmitted during DKG/signing setup.

### Impact Explanation
An unprivileged party supplying crafted key material can force each `ThresholdKeys::read` call to reserve and populate multiple MB of heap from ~10 bytes of header fields, and can have the oversized structure retained in memory once deserialization "succeeds" (parameters are only validated at the end, and a syntactically consistent blob with `t <= n = 65535` and a matching body fully materializes). Repeated submission or storage of such blobs exhausts available memory, matching the CVE's availability-impact class (CVSS A:H). The allocation amplification is on the order of 10^5× per call for the speculative `with_capacity` path.

### Likelihood Explanation
Likelihood is moderate-to-high where `ThresholdKeys::read` consumes peer-supplied or externally loaded bytes without an outer length/size cap: the cost to the attacker is trivial (a u16 field plus optional filler bytes), and no cryptographic validity is needed to trigger the allocation since validation is deferred to `ThresholdParams::new`. The amplification is bounded per call (u16 max `n`), so sustained or concurrent submissions are required for full exhaustion, which keeps this at Medium rather than High.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` *before* performing any `n`-dependent allocation in `ThresholdKeys::read`, and/or cap `n` at a protocol maximum (e.g., the key-share-per-set limit used elsewhere in the codebase) prior to `Vec::with_capacity` and the verification-share loop. Reorder so interpolation and verification-share deserialization only occurs after a successful `ThresholdParams::new` check.

### Proof of Concept
Conceptual byte stream fed to `<C as ...>::ThresholdKeys::read` for e.g. Ristretto (`C::ID` = `b"ristretto"`):

```
// C::ID length + ID
0x09 0x00 0x00 0x00  "ristretto"
// t = 1, n = 0xFFFF, i = 1
0x01 0x00  0xFF 0xFF  0x01 0x00
// interpolation tag = 0 (Constant)
0x00
```

Upon reading tag `0`, `ThresholdKeys::read` executes `Vec::with_capacity(65535)` (crypto/dkg/src/lib.rs, line 608), reserving ~2 MB before any parameter validation or sufficient-length check. Supplying a body of `65535` scalar encodings, one secret share, and `65535` point encodings with `t <= n` causes `ThresholdKeys::new` to succeed and retain ~6 MB of attacker-dimensioned state; iterating this consumes available memory.
