### Title
SSRF via attacker-published DataLayer mirror URLs consumed by `fetch_and_validate`/`http_download` - (File: `chia/data_layer/download_data.py`, `chia/data_layer/data_layer.py`)

### Summary
Any wallet holding a small amount of XCH can publish an on-chain "mirror" coin for **any DataLayer singleton launcher_id that a victim node is tracking**, embedding arbitrary attacker-controlled URLs (including internal/private-network hosts) in the coin's memo. The victim's DataLayer service ingests these URLs from chain state and, on each sync cycle, performs unauthenticated outbound HTTP requests to them via `http_download`, providing an SSRF primitive analogous to CVE-2026-82477 (Heimdall2 Tenable proxy SSRF), but reachable as a "Data Layer client" surface rather than through an RPC proxy.

### Finding Description
`DataLayerWallet.create_new_mirror()` lets any wallet spend a coin to the mirror puzzle, attaching a `launcher_id` and a list of URL bytes as memos: [1](#0-0) 

Crucially, when a peer observes this coin, `DataLayerWallet.coin_added()` accepts and stores the mirror **as long as the launcher_id is merely tracked** (`is_launcher_tracked`), not necessarily owned by the local wallet: [2](#0-1) 

The DataLayer service then pulls these attacker-supplied URLs unfiltered via `update_subscriptions_from_wallet()`: [3](#0-2) 

and feeds them as `ServerInfo.url` into `fetch_and_validate()`, which shuffles servers and calls `insert_from_delta_file()`: [4](#0-3) 

`insert_from_delta_file()` calls `download_file()`, which — when no plugin downloader is configured (the default) — passes `server_info.url` straight into `http_download()`, an aiohttp-based HTTP client fetch, with no destination validation (no blocklist for loopback/link-local/RFC1918/metadata-service addresses): [5](#0-4) 

This mirrors the CVE's bug class exactly: a remote/unprivileged party supplies a URL that gets fetched server-side without validating that the destination is safe, letting them probe or interact with internal network resources (e.g., cloud metadata endpoints, internal admin services, loopback-bound RPC ports) reachable from the victim's node.

### Impact Explanation
An unprivileged wallet user (anyone who can create a spend bundle and pay a small fee) can force any other Chia node running DataLayer with a subscribed/tracked store to issue outbound HTTP requests to attacker-chosen internal or otherwise unreachable addresses. This can be used to:
- Port-scan/probe internal infrastructure behind the victim's network from the victim's own machine.
- Reach cloud metadata services (e.g., `169.254.169.254`) if the victim node runs in a cloud environment, potentially leaking credentials.
- Interact with other locally-bound services (e.g., the victim's own RPC ports) that are otherwise not exposed externally.

This satisfies "Medium" severity network-reachable SSRF impact and fits the allowed category "Data Layer roots and proofs" / "Data Layer client" reachable surface.

### Likelihood Explanation
Likelihood is high for any DataLayer-participating node that tracks external stores: mirror creation only requires the launcher_id to be tracked, is a cheap standard-wallet spend (`create_new_mirror`), and the URL content is never validated for scheme/host safety before being used in `http_download`. The sync loop (`periodically_manage_data`) runs automatically without operator interaction once a store is subscribed.

### Recommendation
- Validate and restrict mirror/server URLs before they are used for outbound requests: reject non-HTTP(S) schemes, and block loopback, link-local, private (RFC1918), and cloud-metadata address ranges unless explicitly allowlisted by the operator.
- Consider requiring operator opt-in / an allowlist of trusted mirror hosts rather than trusting all on-chain-published mirror URLs.
- Apply the same URL validation to plugin downloader URLs and `get_downloader()` requests (`chia/data_layer/data_layer.py`), which also POST to attacker-influenced URLs.

### Proof of Concept
1. Attacker creates/tracks a DataLayer store the victim already tracks (or gets the victim to track any launcher_id, e.g. via an offer/subscription).
2. Attacker calls wallet RPC `dl_new_mirror` (or CLI `chia data add_mirror`) targeting that `launcher_id` with `urls=["http://169.254.169.254/latest/meta-data/", "http://127.0.0.1:<victim-internal-port>/..."]` and a minimal fee, then confirms the spend on chain: [6](#0-5) 
3. Once confirmed, the victim's `DataLayerWallet.coin_added()` records the mirror for the tracked launcher_id.
4. On the victim's next `periodically_manage_data()` cycle, `update_subscription()` → `fetch_and_validate()` picks the malicious URL from `get_available_servers_for_store()` and issues an HTTP GET to it via `http_download()`, with the victim's node acting as an SSRF proxy for the attacker's target.

    async def dl_new_mirror(
        self,
        request: DLNewMirror,
        action_scope: WalletActionScope,
        extra_conditions: tuple[Condition, ...] = tuple(),
    ) -> DLNewMirrorResponse:
        """Add a new on chain message for a specific singleton"""
        if self.service.wallet_state_manager is None:
            raise ValueError("The wallet service is not currently initialized")

        dl_wallet = await self.service.wallet_state_manager.get_dl_wallet()
        async with self.service.wallet_state_manager.lock:
            await dl_wallet.create_new_mirror(
                request.launcher_id,
                request.amount,
                Mirror.encode_urls(request.urls),
                action_scope,
                fee=request.fee,
                extra_conditions=extra_conditions,
