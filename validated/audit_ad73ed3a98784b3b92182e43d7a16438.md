### Title
Zero-slippage token swap during bribe/fee conversion enables sandwich/MEV extraction of protocol fee value - (File: wombat/WombatBribeManager.sol)

### Summary
`WombatBribeManager._swapFeesForBnb` swaps collected bribe/fee reward tokens into BNB via the `PancakeZapper` but hardcodes the minimum-received parameter to `0`, exactly mirroring the reported `AutoCompounder.sol` `amountOutMin = 0` pattern.

### Finding Description
`_swapFeesForBnb` iterates over collected reward/fee tokens and, for each non-zero fee amount, approves and calls `IBNBZapper(PancakeZapper).zapInToken(rewardTokens[i][j], feeAmounts[i][j], 0, msg.sender)`, passing `0` as the `minRec` slippage-protection argument: [1](#0-0) 

Internally, `zapInToken` forwards this `minRec` straight into a router swap (`_swapTokenForBNB`) with no independent minimum-output enforcement of its own beyond whatever value is passed in: [2](#0-1) 

Because `_swapFeesForBnb` always supplies `0` regardless of the fee token amount or current market price, every swap executed through this path accepts any output amount, disabling slippage protection entirely — structurally identical to the `router.swapExactTokensForTokens(balance, 0, routes, address(this), block.timestamp)` pattern flagged in the external report for `AutoCompounder.sol`.

For comparison, other swap paths in the same codebase (e.g., `SmartWomConvert._convertFor`) do enforce a caller/owner-supplied `_minRec` check against the aggregate output before proceeding: [3](#0-2) 

but `_swapFeesForBnb` bypasses this pattern entirely by hardcoding zero.

### Impact Explanation
Any swap routed through `_swapFeesForBnb` can be sandwiched or MEV-extracted, causing the bribe/fee tokens collected on behalf of voters/protocol to be converted into BNB at a suboptimal rate. Since these fee tokens represent unclaimed yield ultimately distributable to voters/participants, the value lost to MEV extraction is a permanent, unrecoverable loss of that yield — the difference is captured by the attacker/searcher rather than by the intended recipients, and cannot be recovered after the swap executes.

### Likelihood Explanation
The swap amounts are driven by whatever fee/bribe balances accumulate in the contract and are not attacker-controlled in size, but the zero-slippage swap executes unconditionally whenever `_swapFeesForBnb` runs, with no per-call override or dynamic bound. On any chain/mempool configuration where transaction ordering can be influenced (front-running/back-running), this is directly and repeatedly exploitable, and the report itself notes this class of issue is realistic wherever MEV/sandwiching is possible.

### Recommendation
Compute a dynamic `minRec` for each swap inside `_swapFeesForBnb` based on a manipulation-resistant price reference (e.g., on-chain TWAP or oracle) and an acceptable maximum slippage bound, rather than passing a hardcoded `0`. Alternatively, restrict who can trigger this fee-conversion path and require the caller to supply a bounded, validated minimum-output parameter checked against a trusted reference price before the swap executes.

### Proof of Concept
1. Bribe/fee tokens accumulate in `WombatBribeManager` from `poolInfos[lp].rewarder` claims via `_claimBribeFor`. [4](#0-3) 
2. When the fee-conversion flow calls `_swapFeesForBnb(rewardTokens, feeAmounts)`, for each token/amount pair it calls `PancakeZapper.zapInToken(token, amount, 0, msg.sender)`. [5](#0-4) 
3. `zapInToken` executes the underlying router swap using the supplied `minRec` (here `0`) with no additional check. [6](#0-5) 
4. An MEV searcher observing the pending transaction sandwiches the swap (front-run buy / back-run sell around the trade), pushing the executed price against the contract and extracting the difference, since the `0` minimum accepts any output amount.
5. The resulting BNB balance credited to `msg.sender` (and ultimately distributed as fee/bribe yield) is permanently reduced relative to fair market value, with no on-chain mechanism to detect or reject the degraded output.

Note: due to tool-call limits I was not able to fully trace every external caller of `_swapFeesForBnb` (e.g., confirm whether it is triggered by a permissionless "distribute fees" entry point or restricted to owner-only maintenance calls) — this should be verified in a full session, as it affects whether the swap is truly reachable from an ordinary/unprivileged wallet on every invocation.
