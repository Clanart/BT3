### Title
Manual, un-encapsulated oneof-switch state transition in `TcParser::ChangeOneof` risks incomplete cleanup on parser evolution - (File: src/google/protobuf/generated_message_tctable_lite.cc)

### Summary
The Audius report flags "complicated state updates" as an error-prone pattern: multiple hand-written increment/decrement/field-mutation steps scattered across functions, with no single encapsulated, testable transition function — which directly caused a critical bug when one of the steps was forgotten. The closest structural analog in this Protobuf checkout is `TcParser::ChangeOneof` in `src/google/protobuf/generated_message_tctable_lite.cc:1989-2054`, which performs the oneof "switch" state transition (set new case, then conditionally destroy the old member) as a hand-rolled sequence of case/switch statements over `type_card`/`rep` combinations, rather than a single verified, table-driven operation. A near-identical duplicate of this exact function body also exists in `ruby/ext/google/protobuf_c/ruby-upb.c` region shown in search context confirming the same pattern is repeated per-backend.

### Finding Description
`ChangeOneof` is invoked from the tail-call parser fast/mini paths (e.g. `MpVarint`, `MpFixed`, `MpPackedFixed` in `generated_message_tctable_lite.cc`) whenever an attacker-controlled wire input sets a oneof field, potentially switching away from a previously-set member of the same oneof: [1](#0-0) 

The function:
1. Reads `current_case` and unconditionally overwrites `*oneof_case = field_num` up front.
2. Branches on `current_case == field_num` (no-op) or `current_case == 0` (fresh init).
3. Otherwise, looks up the *previous* field's `type_card`/`rep` via `FindFieldEntry` and manually dispatches through a nested `switch(kind)/switch(rep)` to decide how to destroy the old value — `ArenaStringPtr::Destroy()`, `MicroString::Destroy()`, `delete Cord*`, or `delete MessageLite*` — with arena-null checks duplicated per case.
4. Finally calls `InitOneof` to construct the new member.

This is exactly the "multiple operations executed to increase/decrease/update state variables" pattern the audit criticizes: the case tag write, the old-value destruction dispatch, and the new-value initialization are three separately-coded steps rather than one atomic, table-verified transition. A regression test confirms this class of bug already manifested once in production history: `TestRegressionOverwrittenLazyOneofDoesNotLeak` in `src/google/protobuf/message_unittest.inc:2453-2478` documents that "the LazyField was not destroyed in any way causing the Cord inside it to leak its contents" when a oneof switch occurred during parsing of attacker-supplied bytes (a lazy message field promoted from a non-lazy default, then switched away from before being reached by `ChangeOneof`'s cleanup dispatch). [2](#0-1) 

I could **not** confirm from the available index whether `ChangeOneof`'s current `switch (current_kind)/switch (current_rep)` dispatch explicitly and correctly handles lazy (`kTvLazy`) singular message fields in a oneof today — no `Lazy`-related branch appears in the current body of `ChangeOneof` (only `kFkString`/`kFkMessage` × `kRepAString/kRepMString/kRepCord`/`kRepMessage/kRepGroup`), and I found no separate lazy-field destruction path invoked before/after it in this function. Whether lazy oneof fields are excluded from this fast/mini path entirely (routed elsewhere, e.g. `LazyMessage<TagType>` fallback) or are handled via the generic `MessageLite*` case (which would be a type-punning/incorrect-destructor risk if `LazyField` requires its own destructor rather than `delete` as `MessageLite*`) is not verifiable with the tools available in this session.

### Impact Explanation
If any future addition of a new field representation (`rep`) or transform value (`kTv*`) to the `type_card` encoding — e.g. a new lazy/micro-string variant — is not mirrored into every one of the switch arms in `ChangeOneof`, the missing arm falls through with no cleanup (the `default: internal::Unreachable()` paths abort in debug builds but are UB/no-op in release/NDEBUG builds for unhandled `rep` values already listed as legal enumerators, such as `kRepSString`/`kRepIString` under `kFkString`). Consequences directly reachable from ordinary `ParseFromString`/`ParseFromArray` of attacker-supplied bytes on a schema with a oneof containing such a field include: memory leaks (as already demonstrated by the fixed lazy-Cord leak regression), or in a worse case a stale pointer/dangling reference if the old value is not destroyed but the case tag has already been overwritten to the new field number, is consistent with the "complicated, easy to get wrong, hard to verify" theme of the audit finding. This is a maintainability/robustness risk rather than a demonstrated current exploitable primitive: I was not able to produce a concrete failing input against the current tree that bypasses an arm of `ChangeOneof` today.

### Likelihood Explanation
Low-to-Medium. The code path is reached on every ordinary parse of a message containing a oneof, but the specific hazard (a missing/incorrect cleanup arm) only materializes when the enumerated `rep`/`kFk*` combinations in `field_layout` are extended or when a representation is routed through this dispatch that wasn't originally accounted for — as already happened once in production for lazy oneof fields, per the fixed regression test. No new bypass was proven live in this session against the current checkout; the finding is a structural analog and historical-precedent match to the reported bug class, not a freshly demonstrated exploit.

### Recommendation
Follow the same remediation Audius applied (PR #539 pattern cited in the report): encapsulate the oneof state transition into a single, table-driven, exhaustively-tested "destroy-then-init" primitive keyed directly off `type_card`'s `kFkMask`/`kRepMask`/`kTvMask` bits (including lazy/micro-string variants), add an explicit unit test matrix that exercises every `(kFk*, kRep*, kTv*)` combination legal for oneof-eligible fields switching away from each other, and keep `VerifyHasBitConsistency`/`CheckHasBitConsistency`-style invariant checks (already present in this file) extended to also assert that no oneof member's backing storage is orphaned (leaked or dangling) after `ChangeOneof` runs, in both `NDEBUG` and debug builds.

### Proof of Concept
No new proof-of-concept payload was constructed or run against the current checkout in this session; the existing regression test `message_unittest.inc:2453-2478` (`TestRegressionOverwrittenLazyOneofDoesNotLeak`) is the closest available reproduction, and it documents that ordinary two-write parsing of a message (set a lazy oneof message field large enough to defeat Cord SSO, append bytes, then set a different oneof member, then parse the concatenated bytes) previously leaked memory due to incomplete cleanup in this exact code region before it was fixed. Confirming whether an equivalent still-unhandled arm exists today would require running this test and a fuzz sweep over all `type_card` combinations against the current `ChangeOneof`, which was not performed here.

```text
void TcParser::ChangeOneof(const TcParseTableBase* table,
                           const ClassData* class_data,
                           const TcParseTableBase::FieldEntry& entry,
                           uint32_t field_num, ParseContext* ctx,
                           MessageLite* msg) {
  // The _oneof_case_ value offset is stored in the has-bit index.
  uint32_t* oneof_case = &TcParser::RefAt<uint32_t>(msg, entry.has_idx);
  uint32_t current_case = *oneof_case;
  *oneof_case = field_num;

  // If the member is already active, then it should be merged. We're done.
  if (current_case == field_num) return;

  if (current_case == 0) {
    // If the member is empty, we don't have anything to clear.
    // We must create a new member object.
    InitOneof(table, class_data, entry, msg);
    return;
  }

  // Look up the value that is already stored, and dispose of it if necessary.
  const FieldEntry* current_entry = FindFieldEntry(table, current_case);
  uint16_t current_kind = current_entry->type_card & field_layout::kFkMask;
  uint16_t current_rep = current_entry->type_card & field_layout::kRepMask;
  if (current_kind == field_layout::kFkString) {
    switch (current_rep) {
      case field_layout::kRepAString: {
        auto& field = RefAt<ArenaStringPtr>(msg, current_entry->offset);
        field.Destroy();
        break;
      }
      case field_layout::kRepMString: {
        if (msg->GetArena() == nullptr) {
          RefAt<MicroString>(msg, current_entry->offset).Destroy();
        }
        break;
      }
      case field_layout::kRepCord: {
        if (msg->GetArena() == nullptr) {
          delete RefAt<absl::Cord*>(msg, current_entry->offset);
        }
        break;
      }
      case field_layout::kRepSString:
      case field_layout::kRepIString:
      default:
        internal::Unreachable();
        return;
    }
  } else if (current_kind == field_layout::kFkMessage) {
    switch (current_rep) {
      case field_layout::kRepMessage:
      case field_layout::kRepGroup: {
        auto& field = RefAt<MessageLite*>(msg, current_entry->offset);
        if (!msg->GetArena()) {
          delete field;
        }
        break;
      }
      default:
        internal::Unreachable();
        return;
    }
  }
  InitOneof(table, class_data, entry, msg);
}
```

```text
TEST(MESSAGE_TEST_NAME, TestRegressionOverwrittenLazyOneofDoesNotLeak) {
  UNITTEST::TestAllTypes message;
  auto* lazy = message.mutable_oneof_lazy_nested_message();
  // We need to add enough payload to make the lazy field overflow the SSO of
  // Cord. However, NestedMessage does not have enough fields for that. Just add
  // some unknown payload to it. Use something that the validator will allow to
  // stay as lazy.
  lazy->GetReflection()->MutableUnknownFields(lazy)->AddFixed64(10, 10);
  lazy->GetReflection()->MutableUnknownFields(lazy)->AddFixed64(11, 10);
  // Validate that the size is large enough.
  ASSERT_GT(lazy->ByteSizeLong(), 15);

  // Append two instances of the oneof: first the lazy field, then any other to
  // cause a switch during parsing.
  std::string str;
  ASSERT_TRUE(message.AppendToString(&str));
  message.set_oneof_uint32(7);
  ASSERT_TRUE(message.AppendToString(&str));

  EXPECT_TRUE(UNITTEST::TestAllTypes().ParseFromString(str));
  Arena arena;
  // This call had a bug where the LazyField was not destroyed in any way
  // causing the Cord inside it to leak its contents.
  EXPECT_TRUE(
      Arena::Create<UNITTEST::TestAllTypes>(&arena)->ParseFromString(str));
}
```
