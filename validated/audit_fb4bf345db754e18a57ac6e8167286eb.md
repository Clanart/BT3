### Title
Length-prefixed field decode in Lite Java parser validates against the whole backing array instead of the enclosing message limit, permitting intra-buffer disclosure of adjacent bytes - (File: `java/core/src/main/java/com/google/protobuf/ArrayDecoders.java`)

### Summary
`ArrayDecoders.decodeString`, `decodeStringRequireUtf8`, `decodeBytes`, and `decodeBytesList` each validate an attacker-controlled length-delimited field by calling `decodeLengthPrefixVarint(data, position, data.length, registers)`, i.e. the bound check is against the physical length of the backing `byte[]`, not against the logical `limit` of the message/submessage currently being parsed. ### Finding Description
The external report's failed invariant is: a length-prefixed record's declared length is trusted for a memory copy without confirming the length stays within the *logical* boundary of the structure being parsed (IPTC block inside a TIFF IFD entry), so the read walks past the intended field into adjacent heap bytes.

The Protobuf analog is the same "trust the length, check the wrong boundary" pattern. `decodeLengthPrefixVarint` is the single choke point that is supposed to enforce "the length-delimited payload must fit within the current parse boundary": [4](#0-3) 

But its callers for `string`/`bytes`/`repeated bytes` fields hard-code `data.length` as the `limit` argument rather than passing the actual limit of the message or submessage currently being decoded:
- `decodeString`: `decodeLengthPrefixVarint(data, position, data.length, registers)` [5](#0-4) 
- `decodeStringRequireUtf8`: same pattern [6](#0-5) 
- `decodeBytes`: same pattern [7](#0-6) 
- `decodeBytesList` (repeated bytes fast path, used for `repeated bytes`/`repeated string`): same pattern for both the first and subsequent elements [8](#0-7) 

Because the Lite/Java "array decoder" fast path (used by `GeneratedMessageLite` generated `mergeFrom`) operates directly on a shared `byte[]` rather than a `CodedInputStream` with an explicit `currentLimit` stack, the only thing stopping an inner length-delimited field (e.g. a `bytes` field nested inside a submessage, or a later element of a `repeated bytes` list) from reading past its own submessage/segment boundary is `data.length`. If the true logical end of the current field/submessage is earlier than `data.length` — which is the normal case for any submessage, since a submessage is a slice of the parent's `byte[]` — a crafted length value can walk the copy (`ByteString.copyFrom(data, position, length)` / `new String(data, position, length, ...)`) across that logical boundary and copy bytes that belong to sibling fields, later tags, or (if the backing array is larger than the parsed region, e.g. from an offset/length `parseFrom(byte[], off, len)` call or a pooled/reused buffer) truly unrelated trailing bytes in the same allocation.

This mirrors the CVE's invariant failure precisely: the check exists (`length > limit - position` throws `truncatedMessage`), but it is checked against the wrong boundary (whole allocation) instead of the structurally-correct one (current record/segment), so the copy silently succeeds while reading adjacent memory that does not belong to the field being decoded.

### Impact Explanation
The consuming-application exposure model in scope is: an ordinary client sends a bounded, otherwise well-formed Protobuf message to a service using `GeneratedMessageLite.parseFrom`/`mergeFrom` (Android/Lite runtime consumers). If the attacker crafts a submessage whose length-delimited `string`/`bytes` field declares a length that exceeds the submessage's own boundary but stays within `data.length`, the resulting parsed value can contain bytes copied from adjacent, logically-unrelated regions of the same backing array — for example subsequent sibling field bytes, or, when the caller supplies an offset/length view over a larger reused buffer, stale bytes left over from a previous parse. Because the copied bytes are exposed as ordinary `String`/`ByteString` field values, an application that echoes, logs, or forwards them can leak adjacent process memory content to the attacker, analogous to the IPTC-over-read disclosure in the CVE. No crash or exception occurs because the copy is still within `data.length`, so this is a silent confidentiality issue rather than a DoS.

### Likelihood Explanation
Reaching this code path only requires calling the standard public `parseFrom`/`mergeFrom` entry points of a Lite-generated message with a nested message, or a `repeated bytes`/`repeated string` field, which is the default runtime for Android and any project using `optimize_for = LITE_RUNTIME`. Crafting the necessary length prefix is a simple varint value, no privileged access or hostile schema is required, and the trusted-schema/bounded-payload assumptions in the prompt are respected.

### Recommendation
Thread the true current parse boundary (the submessage's own end offset or the caller's logical `limit`, not `data.length`) through to `decodeString`, `decodeStringRequireUtf8`, `decodeBytes`, and `decodeBytesList`, and validate the length-prefix against that boundary in `decodeLengthPrefixVarint` for every callsite, matching the limit-stack discipline already used by `CodedInputStream`/`parse_context.h` in the non-Lite/array-free paths.

### Proof of Concept
I was not able to fully trace, in the remaining investigation budget, whether `MessageSchema`'s submessage decode path (`decodeMessageField`) ever invokes these functions with a `limit` strictly less than `data.length` for a genuinely nested submessage (i.e., confirm that a submessage boundary shorter than `data.length` is reachable and that no other check re-validates the post-copy position against that boundary before it is consumed as valid). This is the one remaining piece needed for a concrete, minimal reproduction with byte-level offsets; the code evidence above shows the check-bypass mechanism itself (`data.length` used uniformly in place of the caller's real limit) but a full working repro would require confirming the caller-side limit propagation in `MessageSchema.java`, which I could not complete before this iteration limit.
