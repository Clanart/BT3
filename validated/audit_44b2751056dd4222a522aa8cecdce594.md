## Title
Repository-controlled Git hooks executed with the user's full interactive shell environment via the "Load Git hook environment variables from shell" feature - (File: `app/src/lib/hooks/get-repo-hooks.ts`, `app/src/lib/hooks/with-hooks-env.ts`, `app/src/lib/hooks/hooks-proxy.ts`)

### Summary
GitHub Desktop's hooks-environment feature (`app/src/lib/hooks/*`) intercepts hook invocations for `commit`, `pull`, `push`, and `merge` operations and re-executes whatever hook binary exists in the resolved hooks directory of the *current repository* using a full, real, interactive shell environment (`getShellEnv`), instead of Git's normal minimal spawn environment. This mirrors the report's bug class — a package silently running an externally-influenced payload with a powerful execution context — except here the "payload" is any executable dropped in the repository's hooks path, and the "powerful execution context" is the user's actual shell profile/environment rather than a stripped-down one.

### Finding Description
`withHooksEnv` (`app/src/lib/hooks/with-hooks-env.ts:29-42`) is invoked whenever `opts.interceptHooks` is set (commit, pull, push, merge — see `app/src/lib/git/commit.ts`, `pull.ts`, `push.ts`, `merge.ts`) and `getHooksEnvEnabled()` is true. It calls `getRepoHooks(path, opts.interceptHooks)` [1](#0-0)  which resolves the effective hooks directory via `git config --get core.hooksPath` (falling back to `.git/hooks`) and enumerates any file in that directory whose name matches one of the `knownHooks` and is executable [2](#0-1) .

For every discovered hook, Desktop copies a `process-proxy` stub into a temp directory and points `core.hooksPath` at that stub directory via `GIT_CONFIG_PARAMETERS` [3](#0-2) . When Git invokes the stub, `createHooksProxy` (`app/src/lib/hooks/hooks-proxy.ts`) spawns `git hook run <hookName>` with an environment built from `getShellEnv(cwd)` — the user's actual shell (bash/zsh/PowerShell/cmd) startup environment, obtained by literally spawning the user's configured shell and dumping its environment variables [4](#0-3)  — merged with a small allow-list of `GIT_`/`GITHEAD_` variables from the original invocation [5](#0-4) [6](#0-5) . Git's own `hook run` then locates and executes the *real* hook script from the repository's hooks path (again resolved via `core.hooksPath`/`.git/hooks`) using that shell-derived environment.

The critical point is that the entire chain trusts whatever executable is found under the repository's own hooks directory and grants it the user's PATH, shell aliases, and any secrets exported by the user's shell profile (`.bashrc`, `.zshrc`, PowerShell profile, etc.) — a strictly more powerful execution context than a normal Git hook invocation would receive. The feature is a legitimate opt-in convenience (documented in the Preferences UI, `app/src/ui/preferences/git.tsx:76-137`), but the enumeration/execution logic itself performs no verification that the hooks directory or its contents originated from a source the user actually intended to trust (e.g., it does not distinguish "hooks I wrote in `.git/hooks`" from a `core.hooksPath` value or hooks directory that ends up pointing at attacker-influenced content, such as a directory inside the working tree that was populated by a crafted `.gitmodules`/submodule layout or a hostile `core.hooksPath` config).

### Impact Explanation
If any executable ends up in the resolved hooks path — through any means, including a Git-layer bug that allows a cloned/fetched/submodule-containing repository to place files into the hooks directory, or through a user unknowingly checking out a `core.hooksPath` value that resolves inside the working tree — this feature guarantees that script is executed with the user's real shell environment (full PATH, aliases, and any secrets the shell profile exports), by default for beta-channel users and available as a one-click Preferences toggle for everyone (`enableHooksByDefault = enableBetaFeatures`, `enableHooksEnvironment = () => true`) [7](#0-6) . Compared to a plain Git hook execution (minimal environment), this significantly raises the value of a successful hook-plant, since it exposes developer secrets and shell-level trust (e.g., cloud CLI sessions, ssh-agent sockets, API tokens exported in shell rc files) to the executed hook.

### Likelihood Explanation
Reaching this path requires an attacker to get an executable into the resolved hooks directory of a repository the user opens in Desktop. Desktop already has an explicit guard for the classic case — repositories owned by another local user are flagged "unsafe" and require an explicit "Trust Repository" action before Desktop will operate on them at all (`app/src/ui/add-repository/add-existing-repository.tsx:129-174`, `app/src/ui/missing-repository.tsx:111-134`), which mitigates the well-known `core.hooksPath`/ownership attack. However, that guard is orthogonal to this feature: it protects against local ownership tricks, not against any other mechanism (e.g., Git-layer bugs enabling hook files to be planted via `git clone --recursive` with submodules, or misconfigured `core.hooksPath` values) that could place an executable in the hooks directory. Because `getRepoHooks`/`withHooksEnv` perform no additional provenance check of their own — they simply trust "whatever is executable in the resolved hooks path" — this code is a force-multiplier for any hook-planting bug, since it converts a routine hook execution into an execution with full access to the user's real shell environment. Given the feature is now enabled by default for beta users and just a checkbox away for all others, and given hook interception now covers `commit`, `pull`, `push`, and `merge` (added incrementally through the 3.5.5-beta series per `changelog.json`), the exposure window is broad.

### Recommendation
- Treat hook execution with the enriched shell environment as an elevated-trust operation: gate it behind the same repository-trust/ownership check already used for the "unsafe repository" warning, and re-validate that check whenever `core.hooksPath` resolves to a path that was not explicitly configured by the user through Desktop's own UI.
- When `core.hooksPath` resolves to a location inside the repository's working tree (as opposed to outside it, e.g. a user's home-directory hook store), require explicit user confirmation before intercepting/executing hooks from that path with the enriched shell environment, similar to the existing "Trust Repository" flow.
- Continue restricting the environment passed to hooks to the documented `GIT_`/`GITHEAD_` allow-list, but also consider giving users visibility (e.g., in the "Running <hook> hook..." UI) into which environment source (Desktop-managed vs. full shell) is being used, and surface a warning the first time a hook is about to run with the full shell environment for a given repository.

### Proof of Concept
Conceptual PoC (not fully verifiable from static code alone, since it depends on Git being tricked into placing a file into the hooks directory of a repository Desktop treats as trusted):
1. Enable "Load Git hook environment variables from shell" in Preferences → Git (or use a beta build where it's on by default).
2. Obtain/construct a repository whose hooks directory (default `.git/hooks`, or wherever `core.hooksPath` resolves) contains an executable named after one of the intercepted hook names (e.g. `pre-commit`) that is attacker-controlled.
3. Perform a normal Desktop operation that triggers hook interception, e.g. commit (`app/src/lib/git/commit.ts`, `interceptHooks: [...]`) — Desktop's `withHooksEnv` will detect the hook via `getRepoHooks` and execute it through `hooks-proxy.ts` with the environment obtained from `getShellEnv`, which spawns the user's real shell and captures its full environment (`app/src/lib/hooks/get-shell-env.ts:33-40`).
4. The hook script, running with the user's real shell environment, can read any secret exported by the user's shell profile and exfiltrate it (e.g., via network call), or perform arbitrary file writes.

I was unable to fully confirm from the indexed code alone the exact upstream mechanism by which an attacker-controlled repository could place a file into the hooks directory in the first place (this is normally prevented because `.git/hooks` is not part of tracked/cloned content); that half of the chain depends on either a bundled-Git-version vulnerability (outside this repo's control) or a `core.hooksPath` misconfiguration, neither of which I could verify against the exact dugite/git version bundled by this repo. If you need certainty on the bundled Git version and whether it is subject to known hook-planting bugs, a Devin session with full repository/dependency access would be needed to check `package.json`/`dugite` lockfile versions.

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
```

export const getShellEnv = async (
  cwd?: string,
  shellKind?: SupportedHooksEnvShell,
  printenvzPath?: string
): Promise<ShellEnvResult> => {
  const ext = __WIN32__ ? '.exe' : ''
  printenvzPath ??= join(__dirname, `printenvz${ext}`)

  const shellInfo = await getShell(shellKind)

  if (!shellInfo) {
    return { kind: 'failure', shellKind }
  }

  const { shell, args, quoteCommand, windowsVerbatimArguments, argv0 } =
    shellInfo

  return await new Promise((resolve, reject) => {
    const child = spawn(shell, [...args, quoteCommand(printenvzPath)], {
      env: {},
      windowsVerbatimArguments,
      argv0,
      stdio: 'pipe',
      cwd,
    })
```
