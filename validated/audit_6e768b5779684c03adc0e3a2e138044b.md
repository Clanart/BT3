### Title
`ThresholdKeys::read` accepts identity verification shares, producing an identity `group_key` that makes Schnorr signatures trivially forgeable and any funds addressed to it unspendable/stealable - (File: crypto/dkg/src/lib.rs)

### Summary
The audit issue is a missing zero-check on a critical initialization parameter (`_owner`), which bricks the deployed contract. The Serai analog: `ThresholdKeys` is the "ownership" root of a threshold multisig — its `group_key` is the sole authority under which Schnorr/Bitcoin signatures are produced and under which `ReceivedOutput`s are recognized. `ThresholdKeys::new` / `ThresholdKeys::read` validate the *count* and *indexes* of `verification_shares` but never reject the identity (zero) point, so attacker-controlled serialized bytes can construct keys whose `group_key` is the identity — the exact analog of `owner = address(0)`, except worse: the key is not merely unusable, it is forgeable-by-anyone.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation mode, a secret share, and `n` verification shares, then calls `ThresholdKeys::new`. Each verification share is read with `<C as Ciphersuite>::read_G` (crypto/dkg/src/lib.rs:622), the generic ciphersuite decoder which only enforces canonicality — it explicitly does *not* reject the identity (crypto/ciphersuite/src/lib.rs:91-101). The identity-rejecting variant exists only as `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) and is used for FROST preprocess/nonce commitments (`GeneratorCommitments::read`, crypto/frost/src/nonce.rs:34-36), but `ThresholdKeys` is generic over `Ciphersuite` and never calls it.

`ThresholdKeys::new` then checks only that `verification_shares.len() == n` and that every participant index `<= n` (crypto/dkg/src/lib.rs:355-365). It computes `group_key = Σ_{i∈1..=t} shares[i] * interpolation_factor(i)` (lines 376-378) with no check that the shares or the resulting `group_key` are non-identity. Feeding bytes encoding `t=1, n=1, i=1`, Lagrange, `secret_share = 0`, and `verification_shares = {1: identity}` yields a fully "valid" `ThresholdKeys` whose `group_key()` is the identity point.

Downstream, `AlgorithmSignatureMachine::complete` verifies the aggregate signature via `algorithm.verify(self.view.group_key(), ...)` (crypto/frost/src/sign.rs:465), and the code itself acknowledges this failure mode only in a comment: "The only known way to cause this ... is to deserialize a semantically invalid FrostKeys" (sign.rs:492-494) — the deserialization path that produces it is left open.

### Impact Explanation
A Schnorr verification against `A = identity` degenerates to `R = s·G - c·identity = s·G` with `c = H(R, A, m)`, so *any* party can produce a valid signature for any message under this group key by picking `s` and setting `R = s·G`. In the bitcoin-serai context, outputs scanned/matched to this group key (`Scanner` matching `script_pubkey` derived from it) are either unspendable (identity has no valid x-only encoding) or spendable by anyone — "funds reported received that are not spendable", an accepted impact class. This is strictly stronger than the source bug: not only is the key "unusable", it authenticates forgeries.

### Likelihood Explanation
The trigger only requires attacker-controlled bytes reaching `ThresholdKeys::read` — e.g., a validator loading a key-set blob supplied over an unauthenticated/recovery channel, or any integrator persisting key material that a peer can influence. No threshold collusion, validator malice, or leaked secrets are needed; the reader itself constructs the poisoned key.

### Recommendation
In `ThresholdKeys::new`, reject any identity verification share and a resulting identity `group_key`, e.g. `if bool::from(share.is_identity()) { Err(...) }` and `assert!(!group_key.is_identity())` mapped to a `DkgError` variant — the direct analog of `require(_owner != address(0))`. Alternatively/additionally, have `ThresholdKeys::read` use an identity-rejecting point decoder for the verification shares.

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))

    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
