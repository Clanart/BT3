I found a concrete local analog of the `TokenIdsToPoolIds` default-zero bug: `IntentGatewayV2.sol`'s `instance()` helper returns `address(this)` — instead of reverting — when a source chain has no registered gateway instance, which lets `RedeemEscrow`/`RefundEscrow` authentication be satisfied by an attacker-controlled `from` field from any unregistered source chain.

### Title
`instance()` default fallback to `address(this)` lets any unregistered source chain forge `RedeemEscrow`/`RefundEscrow` withdrawals - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.instance()` on the Tron build resolves an unmapped `_instances[keccak256(stateMachineId)]` to `address(this)` instead of reverting, unlike the sibling EVM implementation (`IntentsBase._instance()`), which reverts with `UnknownInstance()` on the same zero-default condition. Because `authenticate()` — the only gate on `RedeemEscrow`/`RefundEscrow` withdrawals in `onAccept` — compares the request's `from` field against `instance(request.source)`, an attacker who can get a `PostRequest` accepted from any state machine that has never had `_addDeployment`/`NewDeployment` called for it can set `from = address(this)` and pass authentication, triggering an unauthorized escrow withdrawal.

The broken invariant mirrors the report exactly: a mapping (`_instances`) that should represent "no trusted counterpart registered for this chain" instead resolves to a meaningful, exploitable default (`address(this)`) rather than reverting. This corrupts the semantics of `instance(stateMachineId)` for every state machine ID for which `NewDeployment`/`_addDeployment` has not yet been called — which includes any state machine ID the gateway operator has not gotten around to registering, or any that governance later deregisters back to zero.

The EVM sibling contract (`evm/src/apps/intentsv2/IntentsBase.sol`) implements the same lookup correctly by reverting on the zero default:
```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
``` [5](#0-4) 

This confirms the Tron contract's behavior is a real deviation/regression from the intended (and already-fixed-elsewhere) pattern, not an intentional design choice.

### Impact Explanation
This directly maps to the bounty's "false proof/state acceptance" and "unauthorized transaction or execution" / "logic attacks" categories, and risks direct fund loss: any escrow balance held by the Tron `IntentGatewayV2` for orders whose destination/source chain is not yet registered in `_instances` can be drained by forging a `RedeemEscrow` or `RefundEscrow` `PostRequest` whose `source` is an unregistered state machine and whose `from` bytes equal `address(this)`. `withdraw()` will pay out any escrowed token amount and fees to an attacker-chosen `beneficiary` for any known commitment, and will also happily process a `RefundEscrow` to double-cancel/redirect a genuine order before its legitimate counterpart message arrives, since `authenticate()` no longer distinguishes "unregistered chain" from "chain whose gateway is `address(this)`."

### Likelihood Explanation
Exploitability depends on the request actually being routed and accepted by the local ISMP host as coming from some `source` state machine that is unregistered in `_instances` (i.e., `onlyHost` still gates `onAccept`, so a fully-forged ISMP message without valid consensus proof would still be rejected). However, the attacker does not need a malicious relayer, prover, or admin: any state machine reachable from Hyperbridge that has not yet had `NewDeployment` called for it (a very likely operational state during progressive multi-chain rollout, or after a deliberate `_instances` reset) is enough — the attacker only needs to dispatch a genuine cross-chain post request from that unregistered chain with `body[0] = RequestKind.RedeemEscrow/RefundEscrow` and `from = address(this)`. This is a pure unprivileged-attacker, public-entrypoint path with no reliance on a compromised relayer or governance actor.

### Recommendation
Change `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g. `revert UnknownInstance();`) when `_instances[keccak256(stateMachineId)] == address(0)`, matching the EVM `IntentsBase._instance()` implementation, so that authentication against an unregistered chain can never resolve to `address(this)`. Also consider explicitly rejecting `RequestKind.RedeemEscrow`/`RefundEscrow` messages whose `request.source` has no registered `_instances` entry, independent of the `authenticate()` fix, as defense in depth.

### Proof of Concept
1. Deploy `IntentGatewayV2` on chain X (Tron), with escrowed orders funded via `placeOrder`.
2. Do not call `_addDeployment`/`NewDeployment` for state machine `Y` (i.e., leave `_instances[keccak256(Y)] == address(0)`), which is the normal state for any chain not yet onboarded.
3. From chain `Y` (any real, ISMP-connected but unregistered chain, or via the router the operator uses to bridge into chain X), dispatch a genuine `PostRequest` to `IntentGatewayV2` on chain X with:
   - `source = Y`
   - `from = abi.encodePacked(address(intentGatewayOnX))` (20 bytes equal to the target contract's own address)
   - `body = abi.encodePacked(bytes1(uint8(RequestKind.RedeemEscrow)), abi.encode(WithdrawalRequest({commitment: <victim commitment>, tokens: <victim's escrowed tokens>, beneficiary: <attacker address>})))`
4. The destination ISMP host on chain X delivers this to `onAccept`. `authenticate()` computes `instance(Y)`, which is `address(0)` in `_instances`, so it returns `address(this)`; `module` decoded from `from` is also `address(this)`; the check `instance(request.source) != module` passes.
5. `withdraw()` executes, transferring the victim's escrowed tokens/fees to the attacker-controlled `beneficiary`.
