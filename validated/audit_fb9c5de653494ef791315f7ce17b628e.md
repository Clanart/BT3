## Title
`IntentGatewayV2.withdraw()` / `SweepDust` on Tron use raw, unchecked-return `.call` transfers instead of the imported `SafeERC20.safeTransfer` — silent-failure tokens cause escrow to be marked released while funds stay stuck - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports `SafeERC20` and declares `using SafeERC20 for IERC20;` [1](#0-0) , and correctly uses `safeTransferFrom` when pulling user inputs into escrow [2](#0-1) . However, the escrow payout path (`withdraw`) and the governance `SweepDust` handler both bypass the safe wrapper and instead perform a raw low-level `.call` with the `transfer` selector, checking only that the call did not revert — never decoding/validating the returned boolean [3](#0-2) [4](#0-3) [5](#0-4) . This is the exact bug class from the report: `SafeERC20` is declared for use but unsafe functions are used for the actual token movement.

### Finding Description
`withdraw()` is invoked from `onAccept` when a `RedeemEscrow`/`RefundEscrow` request lands, after authentication [6](#0-5) . For every escrowed ERC-20 token it does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` only reflects whether the call reverted, not whether the token's own `transfer` logic returned `true`. Tokens that follow the pre-EIP20-strict convention of returning `false` on failure instead of reverting (a well-known and common non-standard ERC-20 behavior, and the exact instruction that TRC20 tokens on Tron — the very chain this contract targets — frequently emulate) will make this call succeed with `success == true` while no tokens actually move.

Immediately after this unchecked "transfer", the function unconditionally decrements the escrow accounting:
```solidity
_orders[body.commitment][token] -= amount;
```
and later emits `EscrowReleased`/`EscrowRefunded`, permanently marking the order settled. Because the guard `if (_orders[commitment][token] == 0) revert UnknownOrder()` only fires before the transfer attempt (and the accounting is now zeroed), there is no path left to retry or recover the payout — the tokens remain custodied in the gateway contract but the internal ledger says they were paid out. The same unchecked pattern exists in the fee payout (feeToken) and in `SweepDust`.

`SafeERC20.safeTransfer` exists precisely to close this gap: it uses `abi.decode`/inline assembly to require that the call both succeeds AND returns `true` (or no data at all, per OZ's convention for compliant tokens), reverting otherwise. `IntentsBase.sol`, `ExtrinsicIntents.sol`, and `IntrinsicIntents.sol` in the main EVM implementation correctly use `safeTransfer`/`safeTransferFrom` throughout, confirming the Tron variant is the outlier that regressed to unsafe calls despite declaring `using SafeERC20 for IERC20`.

### Impact Explanation
This is a direct loss-of-funds bug matching the bounty's "stealing or loss of funds" category: for any ERC-20 (or Tron TRC20-style token) that signals failure via a `false` return rather than a revert, a legitimate beneficiary's escrow redemption or refund silently fails while the contract's bookkeeping records it as settled. The tokens become permanently stuck in `IntentGatewayV2` with no code path to re-attempt the transfer, since the escrow amount has already been zeroed out. This is not a peer/relayer/prover compromise or a front-run — it is a deterministic consequence of the contract's own token-transfer code for any token exhibiting this common non-reverting-failure behavior.

### Likelihood Explanation
Likelihood is high on Tron specifically, since TRC20 tokens are well known for return-value/edge-case inconsistencies relative to strict ERC-20 semantics, which is exactly the scenario `SafeERC20` was adopted to guard against elsewhere in this same file (input-side `safeTransferFrom`) and across the rest of the codebase. Any deployment of `IntentGatewayV2` on Tron that lists such a token for output/fee settlement will hit this path on every failed transfer attempt (e.g., paused token, blacklisted beneficiary, insufficient allowance-adjacent conditions the token itself may swallow).

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` sites in `withdraw()`, the fee payout branch, and `SweepDust` with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with the already-declared `using SafeERC20 for IERC20;` and with the rest of the codebase's intent-gateway implementations.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token whose `transfer` implementation returns `false` on failure instead of reverting (e.g., simulate a paused/blacklist condition that the token handles by returning `false`).
2. Place an order that escrows this token via `placeOrder`, which correctly uses `safeTransferFrom` [7](#0-6) .
3. Trigger a legitimate `RedeemEscrow`/`RefundEscrow` request via `onAccept`, causing `withdraw()` to run.
4. Have the token's `transfer(beneficiary, amount)` return `false` under the simulated condition; the `.call` itself does not revert, so `success == true`.
5. Observe: `_orders[commitment][token]` is decremented to zero, `EscrowReleased`/`EscrowRefunded` is emitted, but `beneficiary`'s token balance is unchanged — the escrowed tokens are now unrecoverable, stuck in the gateway contract. [8](#0-7)

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
