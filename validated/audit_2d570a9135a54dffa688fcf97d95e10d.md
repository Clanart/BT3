## Title
`CallDispatcher.dispatch()` has no caller restriction, letting anyone drain dust/leftover assets left behind by other orders' predispatch/postdispatch calldata - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, singleton contract used by `IntentGatewayV2` (and other Hyperbridge apps such as the Wrapped Hyper Fungible Token bridge) to execute arbitrary order-supplied calldata (`predispatch`/`output.call`) while transiently holding user/protocol assets. Its `dispatch()` entrypoint has **no access control whatsoever** — any address can call it directly and force the contract to execute arbitrary `Call[]` against arbitrary targets. Combined with the fact that the gateway's post-dispatch "sweep" logic only ever collects tokens matching the specific `order.inputs` / `order.output.assets` token list, any token (or native asset) that ends up sitting in `CallDispatcher` outside that enumerated list — from slippage, partial consumption, or a different asset type touched by the order's own calldata — is never swept back and remains permanently exposed. Because `dispatch()` is public, an unprivileged attacker can call it directly and transfer that residual balance to themselves.

### Finding Description
`CallDispatcher.dispatch()` is declared `external` with no modifier and no `msg.sender` check at all: [1](#0-0) 

It simply decodes an attacker-supplied `Call[]` and executes each entry with `to.call{value: call.value}(call.data)` — the only restriction is that `to` must have code. There is no restriction that the caller must be a registered `IntentGatewayV2`/gateway contract, nor any restriction preventing calls to arbitrary ERC-20 tokens to move out whatever balance the dispatcher currently holds.

`IntentGatewayV2`/`IntentsBase` route both `predispatch` (swap-then-escrow) and `output.call` (postdispatch, fill-then-act) calldata through this same shared dispatcher, and only sweep back tokens that are explicitly part of `order.inputs` (predispatch) or `order.output.assets` (postdispatch): [2](#0-1) [3](#0-2) 

The sweep in each case only iterates the token set the order declared as inputs/outputs. Any other asset that ends up on the dispatcher — e.g. an unconsumed source asset from a swap that doesn't fully spend its input, dust from a different intermediate token in a multi-hop route, native ETH remainder, or any other token type an order's own arbitrary calldata happens to move onto the dispatcher — is left there indefinitely once the transaction completes successfully, because no `msg.sender`-gated withdrawal path exists other than the two hard-coded sweep loops above.

Because `dispatch()` itself is unauthenticated, that leftover balance is not merely "stuck" — it is **directly stealable by anyone**, at any time, by calling `CallDispatcher.dispatch(encoded)` with a `Call` such as `token.transfer(attacker, balance)` or native-value forwarding. No relayer, prover, admin, or privileged role is required; the attacker only needs to know the (public) `CallDispatcher` address, which is exposed via `_params.dispatcher` and documented publicly (it is also shared with the Wrapped Hyper Fungible Token bridge, per the docs).

This mirrors the external report's broken invariant precisely: a component that is supposed to act only as a scoped, single-purpose executor for a specific owner/session (there: the SCW's `sessionKey`; here: `IntentGatewayV2`'s own predispatch/postdispatch flow) fails to verify *who* is invoking privileged token-moving logic, letting an unrelated party redirect value that was never meant to be theirs.

### Impact Explanation
Any ERC-20 or native-asset dust left in the shared `CallDispatcher` — whether from ordinary slippage/rounding in a legitimate order's swap-then-escrow or fill-then-act calldata, or from any other app sharing the same dispatcher — is not protocol-owned custody in a meaningful sense: it can be permissionlessly extracted by any attacker monitoring the contract's balance. This is a direct loss-of-funds vector against protocol/user assets that should have been swept back to the gateway (and eventually to a treasury or the affected users) as `DustCollected`, per the documented design.

### Likelihood Explanation
No privileged actor, relayer, or malicious peer is required. Any externally-owned account can call `CallDispatcher.dispatch()` at any time; the only precondition is that the dispatcher currently holds a non-zero balance of some asset outside the specific input/output token set of whichever order last touched it. Given routine slippage in DEX swaps used for predispatch/postdispatch composition, and the fact that the dispatcher is shared across multiple apps/orders over time, non-trivial balances are expected to accumulate periodically, making exploitation a matter of simply watching the contract's token balances and front-running the (non-existent) sweep.

### Recommendation
Restrict `CallDispatcher.dispatch()` to callers explicitly authorized to invoke it — e.g., an `onlyOwner`/allowlist of registered gateway contracts set at construction/governance time, or make each gateway deploy/own its own dispatcher instance rather than sharing one singleton across unrelated apps and orders. Additionally, broaden the sweep logic (or add a permissioned governance sweep) to capture any token balance left on the dispatcher after calldata execution, not just the tokens enumerated in `order.inputs`/`order.output.assets`.

### Proof of Concept
1. Any order's `predispatch.call` (or `output.call`) executes a swap/router call that, due to slippage/partial fill or multi-hop routing, leaves a nonzero balance of an intermediate/unrelated token (or native ETH) on the `CallDispatcher` after the transaction completes — this is a routine, non-malicious occurrence given `_execute`/predispatch sweep only handles the order's declared input/output tokens.
2. An attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: leftoverToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, leftoverToken.balanceOf(address(dispatcher)))})]))` directly (no relationship to `IntentGatewayV2` required, since `dispatch()` has no caller check).
3. The call succeeds because `CallDispatcher.dispatch()` performs no `msg.sender` validation; the leftover balance transfers to the attacker's address, permanently removing it from protocol/user custody. [1](#0-0)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }

                ++i;
            }
