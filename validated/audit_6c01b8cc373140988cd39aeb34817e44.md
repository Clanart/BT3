### Title
Borrow debt-ledger update happens after the external token transfer, breaking Checks-Effects-Interactions and enabling a stale health verdict - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`borrow()` in `v0-4-market.clar` computes the health check, then performs the external token transfer (`vault-system-borrow` → underlying `ft-trait` transfer to `funds-receiver`), and only afterwards records the new debt in the ledger via `debt-add-scaled`. This mirrors the dHedge report's root cause exactly: an external interaction is sandwiched between a check and the effect that should immediately follow it, so any control-flow transfer during the interaction sees stale state where the debt effect has not yet been applied.

### Finding Description
In `borrow()`:
```
(asserts! (try! (is-healthy-with-mask collateral-value debt-post-increased future-mask)) ERR-UNHEALTHY)

(try! (vault-system-borrow asset-id amount funds-receiver))   ;; INTERACTION: external ft transfer to receiver
(let ((scaled-debt-added (convert-to-scaled-debt asset-id amount true))
      (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id)))))
  (try! (contract-call? .v0-market-vault             ;; EFFECT: debt recorded only here
                        debt-add-scaled
                        account
                        scaled-debt-added
                        asset-id))
  ...
``` [1](#0-0) 

`vault-system-borrow` is dispatched per-vault (e.g. `v0-vault-stx.clar`'s `system-borrow`), which updates internal vault accounting and then calls `send-underlying` to transfer the underlying asset to the caller-specified `receiver` via a `<ft-trait>` contract call before returning control to `market.clar`: [2](#0-1) 

The health check (`is-healthy-with-mask`) is evaluated against `debt-post-increased`, a locally computed value, but the *ledger* (`market-vault.clar`'s scaled-debt map, which backs `get-account-scaled-debt` used by every future health computation) is not updated until after the external transfer completes. This is the same ordering flaw the report describes for the dHedge buyback contract: `l1BurntAmountOf` (here, the pre-transfer health check) is validated, an external/try-catch interaction occurs, and only afterward is the authoritative accounting (`claimedAmountOf` / here, `debt-add-scaled`) updated.

### Impact Explanation
If control flow can be regained during the interaction step (e.g., a registered underlying asset contract or receiver-side logic invoked as part of the `<ft-trait>` transfer call executes further logic before returning), a caller can re-enter `borrow()` (or any other debt/collateral-mutating entry point) while the ledger still reflects the pre-borrow debt state. Each reentrant call recomputes `is-healthy-with-mask` against the stale (too-low) debt figure and passes, permitting multiple borrows to be authorized against the same collateral before any of them are actually recorded as debt. This produces a wrong health verdict, allowing debt to be issued far beyond what collateral supports — a direct path to draining vault liquidity, i.e., theft of user funds / protocol insolvency (Critical).

### Likelihood Explanation
Exploitability depends on whether any registered SIP-010-conforming underlying asset (or an intermediate contract invoked during the transfer flow) can execute code that calls back into `market.clar` before the transfer call returns. Standard SIP-010 tokens deployed today do not have transfer hooks, so this is not immediately triggerable, exactly as in the original report ("not currently possible... but possible with a token that has callbacks"). Because asset onboarding in Zest is DAO-governed, the likelihood is currently low, but the code itself is not robust against any future registered asset (or trait implementation) that introduces such behavior, matching the report's forward-looking risk framing.

### Recommendation
Apply the same fix pattern dHedge used (Option 1/2/3 from the report): move the ledger update (`debt-add-scaled`) to occur before the external transfer (`vault-system-borrow`), or perform the state update first and roll back on failure, or guard `borrow()` (and the vault `system-borrow`/`send-underlying` path) with a reentrancy lock so no nested call into debt/collateral-mutating functions can execute before the effect of the current call is committed.

### Proof of Concept
1. Governance (legitimately) registers an underlying asset whose `<ft-trait>`-conforming contract executes additional logic during its `transfer` function (or the configured `funds-receiver` is a contract that regains control before `send-underlying` returns).
2. Attacker calls `borrow(ft, amount, receiver, feeds)`. The health check passes against current legitimate debt.
3. Inside `vault-system-borrow` → `send-underlying`, control returns to attacker-controlled code before `debt-add-scaled` has executed.
4. Attacker re-enters `borrow()` for the same account; `get-account-scaled-debt`/ledger state still reflects the pre-first-borrow debt, so `is-healthy-with-mask` passes again.
5. Repeat until both borrow calls unwind, each independently calling `debt-add-scaled`, resulting in total debt recorded that exceeds what a single health check would have allowed, while the receiver has already received both transfers. [3](#0-2)
