### Title
`calExpireForfeit`/`_calExpireForfeit` always return 0 regardless of lock/cooldown ratio, breaking forfeiture redistribution - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never queries any lock/cooldown ratio (e.g., `getRewardablePercentWAD` used by the analogous `vlMGPBaseRewarder`) and instead hardcodes `rewardableAmount = _amount`, so `forfeitAmount` is mathematically always zero. This dead-code forfeiture logic means users who withdraw/cooldown early never forfeit yield to long-term stakers, unlike the intended design mirrored in `vlMGPBaseRewarder`.

### Finding Description
In `mWOMSVBaseRewarder.sol`, `calExpireForfeit(_account, _rewardToken)` calls `_earned` then `_calExpireForfeit(_account, earned(...))` [3](#0-2) . Inside `_calExpireForfeit`:
```solidity
uint256 rewardableAmount = _amount;
if (rewardableAmount > _amount) revert InvalidRewardableAmount();
uint256 forfeitAmount = _amount - rewardableAmount;
``` [2](#0-1) 
Since `rewardableAmount` is assigned `_amount` directly (rather than a fraction based on account lock ratio), `forfeitAmount` is always `_amount - _amount = 0`, for every `_account`, every ratio, every state. Compare to `vlMGPBaseRewarder._calExpireForfeit`, which computes `rewardableAmount = _amount * vlMGP.getRewardablePercentWAD(_account) / 1e18` before subtracting [1](#0-0) , so forfeiture is a real, ratio-dependent value there.

The same broken logic is invoked internally by `_sendReward`, meaning the on-chain reward-claim path (`getReward`/`getRewards` via `masterMagpie`) also never withholds forfeited yield from partially-unlocked/cooldown accounts and redistributes it via `_queueNewRewardsWithoutTransfer` [4](#0-3) . No modifier, `nonReentrant`, or access control changes this behavior since it's a pure arithmetic/logic defect, not an access-control gap.

### Impact Explanation
This is a Backing/Conservation invariant violation for unclaimed yield: forfeiture-eligible amounts that should stay in the pool to be redistributed to compliant long-term lockers instead go entirely to the withdrawing/cooling-down user. Concretely, honest long-term `mWOMSV` stakers permanently lose the redistributed-forfeiture yield they would otherwise be entitled to (matches Immunefi "theft of unclaimed yield" impact class), because the pool's `rewardPerTokenStored` is never incremented via `_queueNewRewardsWithoutTransfer` from forfeited amounts (since `forfeitAmount` is always 0, the `if(forfeitAmount > 0)` branch never executes) [5](#0-4) .

### Likelihood Explanation
This triggers on every single `getReward`/`getRewards` call by any staker (any unprivileged EOA that owns `mWOMSV`/staking position), with no special preconditions beyond a funded reward pool — it is deterministic and 100% reproducible, not probabilistic. It requires no attacker capital or special call sequence; it happens automatically as part of normal reward claiming.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to compute `rewardableAmount` based on the account's actual lock/cooldown ratio (analogous to `vlMGP.getRewardablePercentWAD(_account)`), using whatever ratio-reporting function `ILocker`/`mWOMSV` exposes (e.g., a `getRewardablePercentWAD` or equivalent on the `ILocker` interface), instead of hardcoding `rewardableAmount = _amount`.

### Proof of Concept
Foundry test plan:
1. Deploy `mWOMSVBaseRewarder` with a mock `ILocker`/`IMasterMagpie` returning a `staked` amount that reflects a partial-lock/cooldown ratio for account A (analogous to `getRewardablePercentWAD` returning e.g. 50%).
2. Deploy `vlMGPBaseRewarder` with a mock `IVLMGP.getRewardablePercentWAD` returning 50% for the same nominal earned amount.
3. Fund both pools' `earned(account, token)` to identical nonzero values.
4. Fuzz over ratio inputs (0–100%) and assert:
   - `mWOMSVBaseRewarder.calExpireForfeit(account, token) == 0` for all ratios < 100%.
   - `vlMGPBaseRewarder.calExpireForfeit(account, token) > 0` for all ratios < 100%.
5. Additionally call `getReward` on `mWOMSVBaseRewarder` and assert `rewards[token].rewardPerTokenStored` is unchanged by any forfeiture credit (i.e., `_queueNewRewardsWithoutTransfer` never called), confirming no redistribution occurs to remaining stakers.
