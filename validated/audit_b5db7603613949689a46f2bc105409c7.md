## Analysis

The strongest local analog to the "malicious `AutoTrader`" bug-class — an attacker-controlled, unvetted piece of code that gets implicitly trusted and executed inside a privileged context — is GitHub Desktop's **Git hooks shell-environment feature**, introduced in v3.5.5 (`#21319`) and later enabled by default for beta users (`#21590`).

### Title
Repository-tracked Git hooks executed with the user's full shell environment (credential exposure via `core.hooksPath`) - (`app/src/lib/hooks/hooks-proxy.ts`)

### Summary
Desktop's opt-in "Load Git hook environment variables from shell" feature intercepts all Git hooks it knows about and re-executes them via a spawned child process that is handed the user's **entire interactive/login shell environment**, in addition to a "safe" subset of Git's own variables. Git hooks are frequently resolved from `core.hooksPath`, which many popular tooling ecosystems (Husky, `pre-commit`, `lefthook`, etc.) configure to point at a directory that is *committed inside the repository itself* (e.g. `.husky/`). Any attacker who can get content merged/pushed into such a hooks directory — a malicious PR, a compromised collaborator, or a maintainer merging a crafted contribution — gets their script executed automatically the next time the victim commits, pushes, pulls, merges, rebases or checks out in Desktop, with access to the victim's full shell environment (SSH agent sockets, cloud/CLI tokens, `NPM_TOKEN`, etc.), not just the minimal env Git itself would otherwise expose to a spawned hook.

### Finding Description
`withHooksEnv` decides whether to intercept a given hook invocation based on `getHooksEnvEnabled()` and the caller-supplied `interceptHooks` list, which is populated for essentially every meaningful mutating Git operation: [1](#0-0) [2](#0-1) [3](#0-2) 

Which hooks exist is discovered by reading `core.hooksPath` (or the default `.git/hooks`) straight from the repository being operated on: [4](#0-3) 

Because `core.hooksPath` is a completely normal, widely-used configuration to point at a version-controlled directory (Husky-style setups do this on `npm install`/`prepare`), the "hook scripts" enumerated here can be ordinary tracked files that arrive via `git pull`/`git fetch`/PR checkout — i.e., attacker-controlled content, exactly analogous to a user-supplied `AutoTrader` contract address being trusted implicitly.

When such a hook fires, `createHooksProxy` builds the execution environment for the actual hook process: [5](#0-4) [6](#0-5) 

Note line 253: `env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' }`. `shellEnv.env` is obtained by literally spawning the user's configured shell and dumping its resolved environment via `printenvz`: [7](#0-6) 

This is the *entire* environment a user's login/interactive shell would have — anything exported in `.bashrc`/`.zshrc`/`.profile`, PowerShell profile, etc. — unfiltered. The `excludedEnvVars` allowlist/blocklist logic (`GIT_ASKPASS`, `GIT_SSH_COMMAND`, etc.) is only applied to `proxyEnv` (the Git-supplied `GIT_*` variables), not to `shellEnv.env`: [8](#0-7) 

Electron apps normally do **not** inherit a rich shell environment when launched from Finder/Start-menu/Dock, so this feature is a deliberate, Desktop-specific broadening of what an executed hook can see, well beyond what plain `git` invoked from a bare subprocess context would expose.

### Impact Explanation
An attacker who can influence tracked repository content pointed to by `core.hooksPath` (a routine, encouraged configuration in many JS/Python ecosystems) achieves arbitrary code execution on the victim's machine, automatically triggered by ordinary Desktop actions (commit, push, pull, merge, rebase, checkout), with access to the victim's full shell environment. This can result in exfiltration of cloud/CI credentials, SSH agent access, npm/PyPI registry tokens, or any other secret the user's shell environment holds — a materially worse outcome than plain `core.hooksPath` execution via CLI git, because Desktop actively reconstructs and injects the full login-shell environment that the GUI app would not otherwise have.

### Likelihood Explanation
This requires: (1) the feature enabled (`git-hooks-env-enabled`, on by default for beta channel, opt-in and user-toggleable for stable per `app/src/ui/preferences/git.tsx`), and (2) a repository configured with `core.hooksPath` pointing at a tracked directory (a mainstream, non-exotic configuration). No local access, admin rights, or social engineering beyond "open/clone a repo and merge/pull a change" is required — this matches the "attacker controls a cloned/fetched repository" impact class exactly. The "dubious ownership" safety prompt (`getRepositoryType` → `unsafe`) does **not** cover this scenario, since it only checks filesystem ownership, not whether tracked hook scripts inside an already-trusted, self-cloned repository are benign.

### Recommendation
- Do not merge the full shell environment unfiltered into hook execution; apply the same allow/deny-list philosophy currently used for `safeEnv`/`excludedEnvVars` to `shellEnv.env` as well, stripping known credential/secret-bearing variables (cloud provider keys, tokens, SSH agent sockets) unless explicitly required by the hook.
- Warn users, similar to the existing "unsafe repository" prompt, the first time Desktop is about to execute a hook resolved via a repository-tracked `core.hooksPath` (as opposed to the default, non-tracked `.git/hooks`), since this hook content came from the remote/committed history rather than purely local configuration.
- Consider not caching the shell environment across operations/repositories (`getCacheHooksEnv`) by default, to reduce the blast radius of a leaked environment snapshot.

### Proof of Concept
1. Attacker forks/contributes to a repository that already uses (or convinces a maintainer to adopt) Husky-style hooks: `git config core.hooksPath .husky` with `.husky/pre-commit` tracked in the repo.
2. Attacker submits a PR that modifies `.husky/pre-commit` to read `~/.aws/credentials`, `$SSH_AUTH_SOCK`, `$NPM_TOKEN`, or other secrets from the environment and POST them to an attacker-controlled endpoint.
3. Victim, using GitHub Desktop with "Load Git hook environment variables from shell" enabled, merges/pulls the branch and then performs a normal commit (`createCommit` intercepts `pre-commit`).
4. `withHooksEnv` → `createHooksProxy` executes `.husky/pre-commit` with `env: { ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' }`, exposing the victim's full shell environment to the attacker-authored script, exfiltrating secrets without any additional user consent beyond the routine "Commit" action.

export const getShellEnv = async (
  cwd?: string,
  shellKind?: SupportedHooksEnvShell,
  printenvzPath?: string
): Promise<ShellEnvResult> => {
  const ext = __WIN32__ ? '.exe' : ''
  printenvzPath ??= join(__dirname, `printenvz${ext}`)

  const shellInfo = await getShell(shellKind)

  if (!shellInfo) {
    return { kind: 'failure', shellKind }
  }

  const { shell, args, quoteCommand, windowsVerbatimArguments, argv0 } =
    shellInfo

  return await new Promise((resolve, reject) => {
    const child = spawn(shell, [...args, quoteCommand(printenvzPath)], {
      env: {},
      windowsVerbatimArguments,
      argv0,
      stdio: 'pipe',
      cwd,
    })
