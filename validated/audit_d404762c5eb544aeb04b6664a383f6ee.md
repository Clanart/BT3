### Title
Payout transaction's operator-credit (OP_RETURN) output is not covered by the user's withdrawal signature, letting anyone redirect bridge reimbursement credit to an arbitrary operator - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the on-chain payout transaction with the user's withdrawal UTXO as input 0 and the user's payout as output 0, protected by a `SinglePlusAnyoneCanPay` signature that the user gives "off-chain" to whichever operator fronts the withdrawal. That sighash type commits only to input 0 and output 0 - it explicitly does **not** commit to any other input or output, including the second output, an `OP_RETURN` carrying the fronting operator's x-only pubkey that the protocol later uses to decide which operator gets reimbursed from the vault. Because that pubkey is unauthenticated, anyone who obtains the user's signature (an off-chain artifact that is also visible in any partially-broadcast/mempool transaction, since `ANYONECANPAY` signatures are trivially reusable in new transactions) can construct and broadcast a valid payout transaction that pays the user correctly but attributes the "payer" credit to an arbitrary operator's x-only pubkey of their choosing.

### Finding Description
`create_payout_txhandler` at [1](#0-0)  builds:
1. Input 0: the user's withdrawal UTXO, spent via `SpendPath::KeySpend` with the user's `taproot::Signature`.
2. Output 0: the user's payout.
3. Output 1: anchor output (CPFP).
4. Output 2: `OP_RETURN` containing `operator_xonly_pk` - the pubkey of whichever operator is claimed to have fronted the payout.

The user's signature is required to use `SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params`: [2](#0-1) . `calculate_pubkey_spend_sighash` computes the sighash using `Prevouts::One` for this sighash type [3](#0-2) , and the BIP341 encoding logic confirms that when `sighash != TapSighashType::Single` and `!= None`, the full output set is hashed into the signature - but for `Single`/`SinglePlusAnyoneCanPay` only the matching-index output is committed, and `ANYONECANPAY` means only the signer's own input is committed: [4](#0-3) . Consequently, the `OP_RETURN` operator-pubkey output (index 2) and any additional funding inputs are entirely outside what the user authorized.

On the verifier side, `update_finalized_payouts` blindly reads whichever payout transaction ends up confirmed on-chain and extracts the operator pubkey from its `OP_RETURN`, storing it as `payout_payer_operator_xonly_pk` with no check that the named operator actually signed, funded, or authorized that specific transaction: [5](#0-4) .

Each operator's own automation (`PayoutCheckerTask`) then queries the DB for unhandled payouts matching **its own** xonly pubkey and, if found, unconditionally proceeds to build a kickoff and claim reimbursement via `handle_finalized_payout` - trusting the DB-recorded payer field rather than verifying it actually broadcast/funded the transaction itself: [6](#0-5) .

Because `ANYONECANPAY` signatures are reusable in any transaction that keeps the signer's input/output pair intact, and because the operator-attribution output is unsigned, any party who sees this signature (once the honest operator broadcasts it, it is visible in the mempool to any network observer even before confirmation) can front-run/replace it with their own transaction: paying the user identically (amount/script are signature-bound and cannot be altered), funding it from their own wallet, but writing an arbitrary operator's x-only pubkey into the `OP_RETURN`. This breaks the equality that should hold between "the operator credited for having fronted a withdrawal" and "the party that actually paid it," letting the credited operator later drain reimbursement BTC from the bridge vault via the normal kickoff/challenge-timeout flow for a payout it never funded.

### Impact Explanation
This matches the Critical impact category "an operator reimbursed for a payout it never funded." An unprivileged party can cause the protocol to record an arbitrary operator as the payer of a withdrawal that operator never actually paid for, and that operator's own automated `PayoutCheckerTask`/kickoff flow will subsequently claim vault-funded reimbursement for it, consuming that operator's round/kickoff-connector slot and drawing bridge collateral/vault BTC on the basis of unauthenticated on-chain data rather than a binding commitment from the credited operator.

### Likelihood Explanation
Exploitation requires only observing a broadcast (or even just mempool-relayed) `SinglePlusAnyoneCanPay`-signed payout input for a pending withdrawal and constructing a replacement transaction with a different `OP_RETURN` payload and one's own funding input - no privileged role, key, or insider access is needed, and Bitcoin's `ANYONECANPAY` semantics are explicitly designed to allow exactly this kind of third-party augmentation.

### Recommendation
Bind the operator's identity to the transaction the user actually signs, e.g. by having the user's off-chain signature commit to the full output set (use `SIGHASH_ALL`/a sighash flag that hashes all outputs, or otherwise incorporate the intended operator pubkey into the signed message/output that the `SinglePlusAnyoneCanPay` signature does cover), or require an additional operator-authenticated signature over the `OP_RETURN` payload before crediting a payout to that operator in `update_finalized_payouts`. At minimum, `PayoutCheckerTask`/`handle_finalized_payout` should verify that the operator's own wallet/signing key actually contributed the funding input(s) of the on-chain payout transaction before treating it as self-fronted.

### Proof of Concept
1. Operator A prepares and broadcasts (or it enters the mempool prior to confirmation) a valid `payout_tx` per `create_payout_txhandler`: input 0 = user's withdrawal UTXO with the user's `SinglePlusAnyoneCanPay` signature, output 0 = user's payout, output 2 = `OP_RETURN(operator_A_xonly_pk)`.
2. Attacker observes this transaction (network/mempool) and extracts input 0's witness (the reusable `ANYONECANPAY` signature).
3. Attacker crafts a new transaction reusing input 0 with the same witness, adds their own UTXO as an additional funding input, keeps output 0 identical (amount/script pubkey are signature-bound, so the user is paid correctly), but sets output 2's `OP_RETURN` to `operator_B_xonly_pk` (an arbitrary, uninvolved operator).
4. Attacker broadcasts this transaction with higher fee/priority so it confirms instead of (or as) the payout transaction for that withdrawal.
5. `update_finalized_payouts` records `payout_payer_operator_xonly_pk = operator_B_xonly_pk` for this withdrawal [7](#0-6) .
6. Operator B's `PayoutCheckerTask` finds this as its own unhandled payout [8](#0-7)  and proceeds through `handle_finalized_payout` to build a kickoff and eventually claim vault reimbursement for a withdrawal Operator B never funded.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
