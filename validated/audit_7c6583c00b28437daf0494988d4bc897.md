### Title
EVM smart contracts can never associate a Sei address, permanently freezing their funds from wasmd bridge execution - (File: precompiles/wasmd/wasmd.go)

### Summary
The wasmd precompile's `execute`, `executeBatch`, and `instantiate` functions require the EVM `caller` to have an *explicit* Sei↔EVM address association before any CosmWasm message can be dispatched on its behalf. Association can only be created via ECDSA signature recovery (the `Associate`/`AssociatePubKey` precompile methods) or, for the reverse direction, via `MsgAssociateContractAddress` which is restricted to CosmWasm contract addresses. A native EVM smart contract (deployed via `CREATE`/`CREATE2`) has no private key and is not a CosmWasm contract, so it can never obtain an association. Any funds a contract holds under its deterministic default/cast Sei address are permanently unusable via the wasmd precompile, mirroring the reported bug class where a verification path fails to recognize a legitimately-aliased/derived address as valid, permanently blocking otherwise-valid execution.

### Finding Description
Sei maintains a "Dual Address Model" where every account has a Sei (bech32) address and an EVM (hex) address, bridged bidirectionally. When no explicit association exists, the system uses a deterministic "default/cast" address (`GetSeiAddressOrDefault`), and this cast address is treated as the account's canonical Sei-side identity for balance/state purposes: [1](#0-0) [2](#0-1) 

However, the wasmd precompile does not accept this default/cast identity as the sender. `execute`, `executeBatch`, and `instantiate` all call `GetSeiAddress` (strict lookup, no fallback) and hard-fail with an association-missing error if the caller has no explicit mapping: [3](#0-2) 

The only way to create that explicit mapping is:
1. The `Associate`/`AssociatePubKey` precompile methods, which recover the account's EVM/Sei address pair from an ECDSA signature (`v, r, s` over a custom message) — this fundamentally requires a private key, which contracts do not have: [4](#0-3) 

2. `MsgAssociateContractAddress`, which is explicitly gated to only work for CosmWasm contract addresses (`wasmViewKeeper.GetContractInfo(ctx, addr) == nil` → error), with no equivalent message to associate a native EVM contract address: [5](#0-4) 

As a result, a deployed EVM smart contract — which structurally cannot sign a message and is not a wasm contract — can never satisfy `GetSeiAddress(ctx, caller)` for the wasmd precompile's `execute`/`executeBatch`/`instantiate` paths. This exactly parallels the reported bug class: a verification check (here, "is the caller a recognized Sei-side identity") fails to account for the deterministically-derived/aliased identity that the rest of the protocol (balance/state bridging) already treats as valid, permanently blocking legitimate execution rather than merely delaying it.

### Impact Explanation
Any usei or native token balance credited to an EVM contract's cast Sei address (e.g., received via EVM `value` transfers, bank precompile sends, or CW20/CW721 pointer flows) can never be spent through a CosmWasm `Execute`/`Instantiate` call issued via the wasmd precompile, because the contract can never become "associated." This is a permanent freezing of funds for any protocol pattern where a smart contract (e.g., a vault, multisig, DEX router, or liquidity-management contract) needs to programmatically call into CosmWasm to redeem, unwrap, or route funds — analogous to the reported urgent liquidity-redemption scenario, except here the block is permanent and unconditional rather than tied to transient downtime.

### Likelihood Explanation
This is deterministically reachable by any unprivileged user: deploy any EVM contract, fund it (directly or via a pointer/bank flow), and have that contract call the wasmd precompile's `execute`, `executeBatch`, or `instantiate` methods as `caller`. No special privileges, timing, or race conditions are needed — the failure is guaranteed on every attempt for every EVM contract address.

### Recommendation
Allow the wasmd precompile's `execute`/`executeBatch`/`instantiate` paths to use `GetSeiAddressOrDefault` (the deterministic cast address) as the CosmWasm `Sender` when no explicit association exists for the EVM `caller`, consistent with how the rest of the protocol (balance/state bridging) already treats unassociated addresses. Alternatively, introduce an `AssociateContractAddress`-equivalent mechanism for native EVM contract addresses so they can obtain a first-class Sei identity without requiring an ECDSA signature.

### Proof of Concept
1. Deploy an EVM smart contract `C` (via `CREATE`) with no ability to sign transactions.
2. Fund `C`'s balance (e.g., send it usei via a normal EVM `value` transfer, credited to `C`'s cast Sei address per `GetSeiAddressOrDefault`).
3. Have `C` call the wasmd precompile's `execute(contractAddr, msg, coins)` at `0x0000000000000000000000000000000000001002`, attempting to spend its own funds against a CosmWasm contract.
4. `p.evmKeeper.GetSeiAddress(ctx, caller)` returns `found=false` because `C` was never explicitly associated (and cannot be, lacking a private key and not being a wasm contract).
5. The call reverts with `types.NewAssociationMissingErr(caller.Hex())` — permanently, for every future call from `C`, freezing `C`'s funds from ever being spent via CosmWasm execution. [3](#0-2)

func (p PrecompileExecutor) getSeiAddr(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}

	seiAddr, found := p.evmKeeper.GetSeiAddress(ctx, args[0].(common.Address))
	if !found {
		metrics.IncrementAssociationError("getSeiAddr", types.NewAssociationMissingErr(args[0].(common.Address).Hex()))
		return nil, 0, fmt.Errorf("EVM address %s is not associated", args[0].(common.Address).Hex())
	}
	ret, err = method.Outputs.Pack(seiAddr.String())
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}

func (server msgServer) AssociateContractAddress(goCtx context.Context, msg *types.MsgAssociateContractAddress) (*types.MsgAssociateContractAddressResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)
	addr := sdk.MustAccAddressFromBech32(msg.Address) // already validated
	// check if address is for a contract
	if server.wasmViewKeeper.GetContractInfo(ctx, addr) == nil {
		return nil, errors.New("no wasm contract found at the given address")
	}
	evmAddr := common.BytesToAddress(addr)
	existingEvmAddr, ok := server.GetEVMAddress(ctx, addr)
	if ok {
		if existingEvmAddr.Cmp(evmAddr) != 0 {
			logger.Error("unexpected associated EVM address exists for contract", "existing", existingEvmAddr, "contract", addr, "expected", evmAddr)
		}
		return nil, errors.New("contract already has an associated address")
	}
	server.SetAddressMapping(ctx, addr, evmAddr)
	return &types.MsgAssociateContractAddressResponse{}, nil
}
