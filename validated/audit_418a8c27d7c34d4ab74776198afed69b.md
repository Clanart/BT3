# Title
Shared `_partialFills` key across duplicate output-asset entries lets a solver drain full escrow for a partially-filled multi-leg order - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`IntrinsicIntents._fillSameChain` computes each leg's escrow release using a per-token "final leg" shortcut that mirrors the rounding-error fix pattern requested by the seed report (use the direct remaining balance instead of accumulating proportional shares). However, the progress-tracking map `_partialFills[commitment][outputToken]` is keyed only by the **output token address**, not by array index, and the "is this leg done" check compares that shared counter against the **current index's own `totalRequired`**. When an `Order` contains two or more output legs that reference the same output token (and correspondingly indexed input legs for the same input token), a solver can fully satisfy the first leg and have the shared counter make every later same-token leg appear pre-satisfied (`remaining == 0`) without ever paying for it, while the first leg's "final release" grabs `_orders[commitment][token]` — the entire remaining escrow balance for that input token, not just this leg's share.

### Finding Description
In `_fillSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:66-124`):

```solidity
uint256 alreadyFilled = _partialFills[commitment][outputToken];   // keyed by token only
uint256 remaining = totalRequired - alreadyFilled;                // totalRequired = THIS index's amount
...
uint256 amountFilled = alreadyFilled + fillAmount;
_partialFills[commitment][outputToken] = amountFilled;            // shared write
...
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))]; // grabs ALL remaining escrow for this input token
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

The contract never enforces that `order.output.assets[]` (or `order.inputs[]`) tokens are unique per index. If an order has two output legs `i=0` and `i=1` both denominated in the same `outputToken` (e.g. two USDC legs of 50 each, with correspondingly indexed input legs both in the same input token, e.g. two DAI legs escrowed under one aggregate `_orders[commitment][DAI]` balance), a solver can:

1. Fully fill leg `i=0` (pay 50 USDC). `_partialFills[commitment][USDC]` becomes 50, which equals `totalRequired` for leg 0 → the "final release" branch fires and pays the solver `_orders[commitment][DAI]` — the **entire** aggregate DAI escrow for both legs, not leg 0's 50% share.
2. At `i=1`, `alreadyFilled = _partialFills[commitment][USDC] = 50` is read from the shared key, so `remaining = totalRequired(50) - 50 = 0`. The loop hits `if (remaining == 0 || solverAmount == 0) { ...; continue; }` and, because `remaining == 0`, the `isFullyFilled = false` branch is skipped — `isFullyFilled` stays `true` for the whole order.

The order is marked `OrderFilled` (fully settled) even though the solver only ever paid for one of the two output legs, and the solver has already collected 100% of the aggregated input escrow via step 1's "final release" grab.

The existing rounding-dust fix (`amountFilled == totalRequired` ⇒ use `_orders[commitment][token]` directly, verified by `testPartialFill_RoundingDustReleasedToFinalSolver` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:1550-1657`) correctly solves the *single-leg* truncation problem the seed report describes, but it implicitly assumes each `(input token, output token)` index pair is unique within a commitment. That assumption is not enforced anywhere in `placeOrder`/`_fillSameChain`, so the "grab everything remaining" shortcut becomes an over-release primitive whenever a legitimate multi-leg order happens to repeat a token.

### Impact Explanation
This directly violates "bridged assets/escrow must move exactly once and only to the rightful beneficiary and amount." A permissionless solver (no relayer/prover/admin/malicious-peer assumptions required — `fillOrder` is a public entrypoint) can pay a fraction of the promised output and drain the full escrowed input balance, at the expense of the order's beneficiary/placer, while the contract still emits `OrderFilled` and treats the order as legitimately and fully settled. This is a direct fund-loss / wrong-amount settlement bug in the intent-settlement path.

### Likelihood Explanation
Requires an `Order` with a duplicate token across `output.assets[]` (and matching duplicate `inputs[]` token feeding the same aggregate `_orders[commitment][token]` bucket) — the contract performs no uniqueness validation on either array, so any order placer (naively or otherwise) constructing a multi-leg order with a repeated token exposes this path to any watching solver. No collusion with the order placer, no admin/governance action, and no malicious relayer/prover is required — an ordinary solver simply calls `fillOrder` twice against a normal order.

### Recommendation
- Track partial-fill progress and "is this leg fully paid" per-index rather than per-token, e.g. use `_partialFills[commitment][i]` (or hash of `(commitment, i)`), and validate `amountFilled == totalRequired` against that same per-index counter.
- Alternatively, reject orders at `placeOrder` time whose `output.assets[]` (or `inputs[]`) contain duplicate token addresses, eliminating the shared-key collision entirely.
- The "final release grabs full remaining escrow" optimization should only be applied when it can be proven that no other leg still expects a release from the same aggregate escrow bucket (i.e., only correct when the token-to-index mapping is 1:1).

### Proof of Concept
1. User places a same-chain `Order` with:
   - `inputs = [ {token: DAI, amount: 100}, {token: DAI, amount: 100} ]` (aggregate escrow of 200 DAI recorded once in `_orders[commitment][DAI]`)
   - `output.assets = [ {token: USDC, amount: 50}, {token: USDC, amount: 50} ]`
2. Solver calls `fillOrder` with `outputs = [ {USDC, 50}, {USDC, 0} ]`:
   - `i=0`: `alreadyFilled=0`, `fillAmount=50`, `amountFilled=50==totalRequired(50)` → `escrowedAmount = _orders[commitment][DAI] = 200` released to solver; `_partialFills[commitment][USDC]=50`.
   - `i=1`: `alreadyFilled = _partialFills[commitment][USDC] = 50`, `totalRequired=50` → `remaining=0` → loop `continue`s without setting `isFullyFilled=false`.
3. `isFullyFilled` remains `true`; `_withdraw(..., isFullyFilled=true)` and `OrderFilled` fire. Solver has paid 50 USDC total but withdrawn all 200 DAI of escrow — a 4x-favorable settlement instead of the intended 1:1 exchange, at the order beneficiary's expense. [1](#0-0) [2](#0-1)

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
