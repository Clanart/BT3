## Analysis

`readGitIgnoreAtRoot` resolves the path to `.gitignore` and reads it with the standard Node `fs.readFile`, which — unlike `fs.lstat`/`fs.readlink` — transparently follows symlinks: [1](#0-0) 

The path is built with a plain `Path.join(repository.path, '.gitignore')` with no `fs.lstat`/`fs.realpath` check to verify that the resolved target still lives inside `repository.path`: [2](#0-1) 

Git supports committing symlinks as regular blobs (mode `120000`). On Linux/macOS (and on Windows when symlink checkout support is enabled), a normal `git clone`/checkout will materialize such a blob as a real filesystem symlink pointing wherever the attacker chose — including outside the working tree (e.g. `../../.ssh/id_rsa`, `/etc/passwd`, or an absolute path to `.git-credentials`). This value is fully attacker-controlled repository content, matching the in-scope threat model ("attacker controls a cloned/fetched repository").

This function is invoked from the Repository Settings "Ignored Files" tab and the result is stored directly in component state and rendered into a text area for the user: [3](#0-2) [4](#0-3) 

Because `FS.readFile` follows the symlink, opening the "Ignored Files" settings tab on such a repository will display the contents of whatever out-of-tree file the symlink points to, instead of an in-repo `.gitignore`. If the user then saves, `saveGitIgnore` unlinks the symlink and writes those secret contents as a plain `.gitignore` file inside the repo, which can subsequently be committed/pushed — completing an exfiltration path back to a remote the attacker (as a collaborator/maintainer of that same repo) can observe: [5](#0-4) 

### Title
Symlinked `.gitignore` in a cloned repository allows out-of-tree file disclosure via `readGitIgnoreAtRoot` - (File: `app/src/lib/git/gitignore.ts`)

### Summary
`readGitIgnoreAtRoot` reads `.gitignore` with `FS.readFile`, which follows symlinks. A malicious repository can commit `.gitignore` as a symlink to a file outside the working tree (e.g. an SSH private key), causing GitHub Desktop's "Ignored Files" settings view to display that out-of-tree file's contents.

### Finding Description
`readGitIgnoreAtRoot` builds `ignorePath` via `Path.join(repository.path, '.gitignore')` and passes it straight to `FS.readFile` without verifying (via `fs.lstat`/`fs.realpath`) that the resolved file actually resides inside the repository root. Git supports tracking symlinks (mode `120000`) as ordinary blobs, so a repository author can commit `.gitignore` as a symlink pointing to any path reachable by the user's OS account. On checkout, Git materializes that as a real filesystem symlink on platforms/configurations where `core.symlinks` is honored, and `fs.readFile` (unlike `fs.lstat`) transparently dereferences it, returning the target file's content as if it were the repo's `.gitignore`.

### Impact Explanation
The dereferenced content is set into `IRepositorySettingsState.ignoreText` and rendered in the "Ignored Files" tab, disclosing the content of a file outside the repository working tree to the renderer/user (e.g. private keys, `.git-credentials`, `.netrc`, other repos' secrets). If the user saves the dialog, `saveGitIgnore` will overwrite the symlink with a regular file containing that secret content inside the tracked working tree, which can then be staged, committed, and pushed — providing a path for the secret to leave the local machine entirely if the attacker also controls or monitors the remote.

### Likelihood Explanation
Requires only that the victim clones an attacker-authored repository and opens Repository Settings → Ignored Files, which is a normal workflow, not an unnatural user step. Exploitation is dependent on the OS/Git configuration honoring symlink checkout (default on Linux/macOS; requires symlink support enabled on Windows), and on a predictable/known target path existing on the victim's machine (e.g. `~/.ssh/id_rsa`, `~/.git-credentials`).

### Recommendation
Before reading, verify the `.gitignore` path with `fs.lstat`/`fs.realpath` and reject (treat as absent, like `ENOENT`) if the entry is a symlink or if its resolved real path escapes `repository.path`. Apply the same guard in `saveGitIgnore` (unlink-then-write already helps, but should also refuse to follow an existing symlink there).

### Proof of Concept
1. Create a repository containing a symlink named `.gitignore` pointing to a known file outside the tree, e.g. `ln -s /Users/victim/.ssh/id_rsa .gitignore`, commit and push it.
2. Have the victim clone the repository with GitHub Desktop on a platform where symlink checkout is honored.
3. Open the repository in GitHub Desktop → Repository → Repository settings → Ignored Files tab.
4. Observe that the contents of `~/.ssh/id_rsa` (or whatever the symlink target is) are displayed in the Ignored Files text area instead of an error or empty state.

```typescript
export async function readGitIgnoreAtRoot(
  repository: Repository
): Promise<string | null> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  return new Promise<string | null>((resolve, reject) => {
    FS.readFile(ignorePath, 'utf8', (err, data) => {
      if (err) {
        if (err.code === 'ENOENT') {
          resolve(null)
        } else {
          reject(err)
        }
      } else {
        resolve(data)
      }
    })
  })
}
```

```typescript
export async function saveGitIgnore(
  repository: Repository,
  text: string
): Promise<void> {
  const ignorePath = Path.join(repository.path, '.gitignore')

  if (text === '') {
    return new Promise<void>((resolve, reject) => {
      FS.unlink(ignorePath, err => {
        if (err) {
          reject(err)
        } else {
          resolve()
        }
      })
    })
  }

  const fileContents = await formatGitIgnoreContents(text, repository)
  await writeFile(ignorePath, fileContents)
}
```
