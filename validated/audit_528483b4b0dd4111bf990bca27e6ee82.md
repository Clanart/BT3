This is an existing, already-acknowledged bug in the repo (there's a dedicated regression test for it), but it maps directly onto the TOTP-lock bug class: a piece of shared, single-slot mutable state (`prevEventsLen` on `BalanceHandler`) is set as a "checkpoint/lock" at the start of an operation and consumed at the end, but reentrant/recursive invocations of the same code path overwrite that single checkpoint before the outer invocation reads it back — exactly like the TOTP lock being clobbered/misread across nested attempts.

### Title
Recursive precompile calls corrupt shared `BalanceHandler.prevEventsLen` checkpoint, causing EVM StateDB/bank balance desync - (File: precompiles/common/balance_handler.go)

### Summary
`BalanceHandler` records a single `prevEventsLen` "checkpoint" (`BeforeBalanceChange`) marking where in the event log a precompile call's bank events begin, then replays events after that offset into the EVM `StateDB` (`AfterBalanceChange`). When a precompile call recursively (or via nested/try-catch Solidity calls) re-enters a precompile that shares the *same* `BalanceHandler` instance, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, corrupting the checkpoint the outer call still needs. This is functionally the same class of bug as the TOTP lock: a single mutable "position/lock" value meant to scope one attempt is shared and clobbered by a nested/retried invocation.

### Finding Description
`BalanceHandler.BeforeBalanceChange` simply overwrites `bh.prevEventsLen = len(ctx.EventManager().Events())` [1](#0-0)  and `AfterBalanceChange` replays `events[bh.prevEventsLen:]` into the `StateDB` via `AddBalance`/`SubBalance` [2](#0-1) .

Each precompile's `Precompile.runNativeAction` (and the `debug` precompile's `Run`) creates one `BalanceHandler` per top-level `Run` invocation via `BalanceHandlerFactory.NewBalanceHandler()` and calls `BeforeBalanceChange`/`AfterBalanceChange` around `action(ctx)` [3](#0-2) . Because `action(ctx)` runs arbitrary EVM/Cosmos logic (e.g. `distribution.claimRewards`, `staking.delegate`, or a contract that calls back into the precompile — as in `DebugPrecompileCaller.sol`'s recursive `debugPrecompile.call(...)` pattern) [4](#0-3) , a nested call into the *same* stateful-precompile instance reuses the very `BalanceHandler` object (it is stored on the `Precompile` struct as a resolvable/gettable field, e.g. `p.GetBalanceHandler()` in the debug precompile) [5](#0-4) .

When recursion occurs: outer call sets `prevEventsLen = N`; inner (nested) call overwrites it to `prevEventsLen = M > N` and, on its own return, correctly consumes `events[M:]` and resets nothing back to `N`. The outer call, upon its own completion, then reads `events[M:]` instead of `events[N:]`, silently skipping (or double-counting, depending on ordering) all bank events emitted between the outer checkpoint and the inner one. Because `AfterBalanceChange` is the sole mechanism synchronizing native `x/bank` coin-spent/coin-received events into the EVM `StateDB` balances, any skipped or misattributed event range causes the `StateDB` (in-EVM view of balances) to diverge from the actual `x/bank` ledger.

The repository itself documents and reproduces this exact defect: `evmd/tests/integration/balance_handler/balance_handler_test.go` states "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB" [6](#0-5) , and a related suite explicitly frames it as "native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated" [7](#0-6) .

### Impact Explanation
A desync between the canonical `x/bank` balance and the EVM `StateDB`'s cached balance for an address is an accounting-corruption bug matching the Critical impact gate ("irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets"). If the EVM-side `StateDB` balance is inflated relative to the real bank balance (missed `SubBalance` from a skipped spend event, or double `AddBalance` from misattributed receive events), a subsequent EVM-level transfer/call inside the same transaction (or via journal/snapshot commit) can allow spending value that was never actually credited by `x/bank`, i.e., unauthorized extraction/duplication of value. Conversely, if credit events are dropped, user funds sent to a contract via a precompile call become invisible to the EVM view, potentially causing them to be permanently unrecoverable from the contract's perspective (funds freezing).

### Likelihood Explanation
This is triggerable by any unprivileged user who can deploy/call a contract that makes a nested/recursive call into a stateful precompile that uses `BalanceHandlerFactory` (staking, distribution, gov, slashing, bank precompiles all wire `BalanceHandlerFactory: cmn.NewBalanceHandlerFactory(bankKeeper)`), e.g. via a `try/catch` reentry pattern as demonstrated in `StakingReverter.sol`'s `nestedTryCatchDelegations` [8](#0-7)  or the ERC20 `_beforeTokenTransfer` hook that recursively calls `claimRewardsAndRevert` [9](#0-8) . No special privileges are required — only ordinary contract deployment and a single transaction. The repository already contains multiple dedicated regression tests reproducing the desync, indicating the maintainers are aware of and have been actively hardening this exact class of bug, which suggests it is a live, previously-identified issue rather than a purely theoretical one.

### Recommendation
Do not share a single mutable `prevEventsLen` across nested precompile invocations. Instead:
- Maintain a stack (not a single int) of checkpoints in `BalanceHandler`, pushing on `BeforeBalanceChange` and popping the corresponding value on `AfterBalanceChange`, so nested calls restore the outer call's correct starting offset.
- Alternatively, instantiate a fresh `BalanceHandler` per call frame (already done via `NewBalanceHandlerFactory` at `runNativeAction` entry) and ensure it is not retrievable/reusable by nested reentrant calls into the same precompile instance (i.e., the same `Precompile` struct must not expose a shared handler via `GetBalanceHandler()` across concurrent/nested invocations).
- Add invariant checks that assert the sum of `StateDB`-tracked balance deltas after a whole top-level EVM message equals the net `x/bank` events for all involved addresses, failing/reverting the transaction rather than committing a silently desynced state.

### Proof of Concept
The repository's own test demonstrates the corrupted event count: a caller contract invokes a debug precompile recursively (`callback(0)` → recurses until `counter > 3`, emitting one `debug_precompile` event per call), and the test explicitly checks event counts (`s.Require().Equal(len(res.Events), 15, ...)`, `s.Require().Equal(10, debug_count, ...)`) to characterize the (buggy) aggregation behavior [10](#0-9) . Replacing the debug precompile's no-op event emission with a real bank-balance-affecting precompile (e.g., `distribution.claimRewards` or `staking.delegate`, as in `StakingReverter.sol`'s `nestedTryCatchDelegations`) and asserting `StateDB` balance vs. `x/bank` balance equality after the top-level call would show a nonzero divergence, since intervening events consumed by the inner call's `AfterBalanceChange` are never seen by the outer call's checkpoint.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

    /// where inner calls revert intentionally. Only the successful delegations
    /// outside the reverting scope should persist.
    ///
    /// Expected successful delegations: 1 (before loop) + outerTimes (after each catch) + 1 (after loop)
    function nestedTryCatchDelegations(uint outerTimes, uint innerTimes, string calldata validatorAddress) external {
        // Initial successful delegate before any nested reverts
        STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);

        for (uint i = 0; i < outerTimes; i++) {
            // Outer call that will revert and be caught
            try StakingReverter(address(this)).performDelegation(validatorAddress) {
                // no-op
            } catch {
                // After catching the revert, perform a successful delegate
                STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);

                // Inner nested loop of reverting calls
                for (uint j = 0; j < innerTimes; j++) {
                    try StakingReverter(address(this)).performDelegation(validatorAddress) {
                        // no-op
                    } catch {}
                }
            }
        }

        // Final successful delegate after the loops
        STAKING_CONTRACT.delegate(address(this), validatorAddress, 10);
    }
