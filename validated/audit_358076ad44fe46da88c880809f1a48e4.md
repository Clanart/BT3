## Title
Arbitrary command execution via `ext::` / `file://` git transport-helper injection through `openrepo` deep-link URL - (File: `app/src/lib/parse-app-url.ts`)

## Summary
The `openrepo` custom-protocol deep link (e.g. `x-github-client://openRepo/<url>`) is parsed by `parseAppURL` and the extracted `url` value is passed, without any scheme allowlist, all the way to `dispatcher.ts`'s `openRepositoryFromUrl` → `openOrCloneRepository`, which ultimately reaches `clone()` in `app/src/lib/git/clone.ts`, where it is handed directly to `git clone -- <url> <path>`. Git's own transport-helper syntax (`ext::`, `fd::`, or `file://`) is not blocked anywhere in this path.

## Finding Description
`parseAppURL` extracts the path segment after `openrepo://` as the repository `url` with essentially no validation of its content: [1](#0-0) 

Only `pr`, `branch`, and `filepath` query parameters are checked (numeric regex, `pr/\d+` format, `testForInvalidChars`). The `url` itself is passed through untouched as `parsedPath` — no scheme allowlist (e.g. restricting to `https:`/`ssh:`/`git:`) is applied.

This action is then consumed in `dispatcher.ts`: [2](#0-1) 

which calls `openOrCloneRepository(url)`. I was not able to retrieve the full body of `openOrCloneRepository` in this pass (the file is large and the index may not have surfaced that specific section), but the eventual clone sink, `app/src/lib/git/clone.ts`, shows that whatever URL is supplied is passed straight to git with no protocol restriction: [3](#0-2) [4](#0-3) 

The environment-preparation helper used for all remote git operations (`envForRemoteOperation` → `envForProxy`) only special-cases `http`/`https` URLs for proxy resolution and sets no `GIT_PROTOCOL_FROM_USER=0` / `GIT_ALLOW_PROTOCOL` restriction: [5](#0-4) 

Separately, the manual "Clone repository" GUI dialog does route input through `parseRemote`/`sanitizeCloneName` in `app/src/lib/remote-parsing.ts`, which validates against known `https`/`ssh`/`git` remote regexes: [6](#0-5) 

However, the deep-link path (`openRepositoryFromUrl`/`dispatchCLIAction`'s `clone-url` case) does not appear to call `parseRemote` before invoking `openOrCloneRepository`/`clone()` — the raw parsed URL is used directly: [7](#0-6) 

If this is correct, an attacker-controlled deep link such as `x-github-client://openRepo/ext::sh$IFS-c$IFStouch$IFS/tmp/pwned` would be parsed into `{ name: 'open-repository-from-url', url: 'ext::sh$IFS-c$IFStouch$IFS/tmp/pwned' }` and passed unmodified into `git clone -- <url> <path>`. Git's `ext::` remote helper executes the given shell command as a subprocess — the classic transport-helper command-injection primitive (same class as CVE-2017-1000117 / GHSA-family "arbitrary command execution via crafted URL" issues).

## Impact Explanation
If reachable, this results in arbitrary command execution on the victim's machine merely by them clicking a crafted `x-github-client://` / `github-mac://` link, satisfying "clicked deep link → code execution," which is explicitly in-scope as Critical impact.

## Likelihood Explanation
Deep links are the normal "Open in Desktop" flow triggered from any web page or GitHub Pages the user visits, so the attack requires only a single click and no other user interaction — high likelihood if the sink is unguarded as traced. However, I could not fully confirm the intermediate `openOrCloneRepository` implementation in `dispatcher.ts` (its full body was not retrieved by the tools within my available iterations, and the index has size limits), so I cannot rule out an intermediate guard (e.g., a call to `parseRemote`/protocol check) that I did not see. This should be verified directly by reading the complete `openOrCloneRepository` function and confirming whether it calls `clone()` with the raw `url` or first validates/normalizes it via `parseRemote`.

## Recommendation
- In `parseAppURL` (or immediately in `openRepositoryFromUrl`/`openOrCloneRepository`), enforce an explicit allowlist of remote URL schemes (`https:`, `ssh:`, `git:`, and the bare `user@host:path` SCP-like form) using the same validated regexes as `parseRemote` in `remote-parsing.ts`, rejecting anything else (`ext::`, `file://`, `fd::`, etc.) before it reaches `clone()`/`fetch()`/`ls-remote`.
- Additionally, harden the git invocation itself by setting `GIT_ALLOW_PROTOCOL=http:https:ssh:git` (or `protocol.allow=never` combined with explicit allows) in `envForRemoteOperation`, providing defense-in-depth regardless of upstream validation gaps.

## Proof of Concept
Conceptual PoC (pending confirmation of the exact `openOrCloneRepository` code path):
```ts
import { parseAppURL } from './app/src/lib/parse-app-url'

const action = parseAppURL(
  'x-github-client://openRepo/ext::sh$IFS-c$IFStouch$IFS/tmp/pwned'
)
// action.name === 'open-repository-from-url'
// action.url === 'ext::sh$IFS-c$IFStouch$IFS/tmp/pwned'
```
This action, dispatched via the OS-level protocol handler (a user clicking such a link), reaches `dispatcher.ts`'s `openRepositoryFromUrl` → `openOrCloneRepository(url)`. If that function calls `clone(url, path, options)` in `app/src/lib/git/clone.ts` without prior scheme validation, `git clone -- ext::sh$IFS-c$IFStouch$IFS/tmp/pwned <path>` executes, invoking git's `ext::` remote helper which runs `sh -c touch /tmp/pwned` as a subprocess.

**Confidence note:** This finding is based on confirmed absence of scheme validation in `parse-app-url.ts`, `clone.ts`, and `environment.ts`, but I was unable to view the complete `openOrCloneRepository` implementation to confirm there's no intermediate check. A Devin session with full file access should verify this function's source directly before treating this as fully confirmed.

/** Parse the remote information from URL. */
export function parseRemote(url: string): IGitRemoteURL | null {
  for (const { protocol, regex } of remoteRegexes) {
    const match = regex.exec(url)
    if (match !== null && match.length >= 4) {
      return { protocol, hostname: match[1], owner: match[2], name: match[3] }
    }
  }

  return null
}
