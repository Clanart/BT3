### Title
Copilot merge-conflict "Continue Merge" writes AI-generated content to disk without re-verifying the target file is still an unresolved conflict - ([File: app/src/lib/stores/app-store.ts])

### Summary
The Copilot-assisted conflict resolution "Continue Merge" flow decides whether to skip writing a resolution only when it can *positively confirm* the file is no longer conflicted. If the lookup for the file in the current working-directory state comes back empty (`undefined`), the code treats that as "safe to write" instead of "cannot verify — do not write," and falls through to overwrite the file with model-generated content. This mirrors the reported Trie bug class: a lookup that may or may not have actually found the target is used to gate a destructive mutation, without checking the boolean outcome of that lookup before proceeding.

### Finding Description
`_applyCopilotConflictResolutions` in `app-store.ts` writes the Copilot-produced resolutions to disk when the user clicks "Continue Merge": [1](#0-0) 

The guard is:
```
const onDiskFile = state.changesState.workingDirectory.files.find(
  f => f.path === resolution.path
)
if (
  onDiskFile !== undefined &&
  isConflictedFileStatus(onDiskFile.status) &&
  !hasUnresolvedConflicts(onDiskFile.status)
) {
  continue
}
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
```
This only skips the write when `onDiskFile` is *found* and is *provably resolved*. It does not handle the third, unguarded case: `onDiskFile === undefined`, i.e., the lookup did not find the path at all in the current `workingDirectory.files` list captured from `state` at the very top of the function [2](#0-1) . In that case the code has no positive evidence that the file is still a pending, unresolved conflict — yet it proceeds to overwrite it anyway.

The `resolution.path` values themselves are constrained to the set of files that were conflicted when the AI request was built (`validateResolutionPaths` enforces this against `expectedFiles`) [3](#0-2) . But that validation happens once, at prompt-construction time in `copilot-store.ts`'s `resolveChunk` [4](#0-3) , well before the (potentially long-running, up to 600s per chunk) model turn completes and the user reviews/confirms the result dialog. The `state` used at apply-time is re-fetched fresh from `repositoryStateCache` [5](#0-4) , so it reflects whatever the working directory looks like *now*, not what it looked like when resolutions were requested.

The code does have an explicit comment acknowledging the need to detect externally-resolved files and skip them [6](#0-5) , but the detection logic only covers the case where the file is still present with markers healed (`!hasUnresolvedConflicts`). It does not cover the file disappearing from the conflict list entirely (already staged/committed elsewhere, deleted, or the operation state having moved on), which is exactly the case the report's underlying invariant ("verify `found` before mutating") is meant to prevent.

### Impact Explanation
If the working-directory snapshot used at apply time no longer contains the target path as a conflicted entry — because the user resolved and staged it manually during the (multi-minute) AI resolution wait, or because git state changed for any other reason during that window — Desktop silently overwrites that file on disk with stale, model-generated content instead of preserving the user's own resolution. This is exactly the "silent corruption of what the user commits or pushes" impact category: the user believes they are committing/merging their own resolved content, but Desktop writes something else without warning, and the merge then proceeds and gets committed/pushed with the wrong content. Because the underlying conflicts originate from merging/rebasing against a remote branch or fetched history, an attacker who controls the branch being merged controls the conflicting content and can shape scenarios (e.g., many large/slow-to-resolve conflicts) that widen the race window between resolution-gathering and apply.

### Likelihood Explanation
Exploitation requires no local/admin access or malware — only that the victim runs Desktop's built-in "Resolve with Copilot" feature against an attacker-influenced merge/rebase/cherry-pick (a supported, unprivileged workflow), and that the user (or another concurrent event) changes the state of one of the conflicted files during the async resolution window, which the UI/comment explicitly anticipates as a realistic case. The missing branch is a straightforward oversight in an `if` condition, not a deep architectural flaw, making it plausible to trigger.

### Recommendation
Invert the guard to be default-deny: only proceed with the `writeFile` when `onDiskFile` is found, is still `isConflictedFileStatus`, and still `hasUnresolvedConflicts`. If `onDiskFile` is `undefined` or no longer conflicted, skip the write (mirroring the `continue` used for the "resolved externally" case) rather than assuming it is safe to overwrite. This makes the "found" check a precondition to mutation, per the same principle the external report identifies for the Trie contract.

### Proof of Concept
1. Start a merge/rebase/cherry-pick against an attacker-controlled branch that produces multiple conflicted files.
2. Click "Resolve with Copilot"; wait while the (potentially long) model turn runs in `resolveChunk` [7](#0-6) .
3. While waiting, manually resolve and stage one of the conflicted files outside of Desktop's tracked "still conflicted" list (e.g., resolve and stage it such that it is no longer returned in `workingDirectory.files` at all, rather than merely healed of markers).
4. When the Copilot result dialog appears and the user clicks "Continue Merge", `_applyCopilotConflictResolutions` runs; for that file, `onDiskFile` lookup returns `undefined`, the skip-guard is false, and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` executes, overwriting the user's manually-resolved file with the stale AI-generated content [8](#0-7) .

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }
