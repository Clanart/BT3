## Title
Treasury-drained reward payout hard-reverts legitimate messaging consensus proofs, permanently halting Hyperbridge state advancement and all dependent cross-chain settlement - (File: `modules/pallets/beefy-consensus-proofs/src/lib.rs`)

### Summary
The Isomorph report's core broken invariant is: a mandatory, non-essential side computation (an oracle price bound) is wired into the same all-or-nothing transaction as an essential state transition (releasing custodied collateral), so that when the side computation reverts, the essential transition can never complete. `pallet-beefy-consensus-proofs` reproduces this exact pattern: `settle_first_proof` bundles the *reward payout* to a prover with the *acceptance of a valid consensus/messaging proof* inside one dispatchable, and for non-rotation ("messaging") proofs a failed reward transfer is propagated as a hard `Err`, rolling back the entire proof settlement — including the state-commitment advance that `verify_and_apply` already computed.

### Finding Description
`do_submit_proof` first calls `verify_and_apply`, which runs `handlers::handle_incoming_message` and mutates consensus state / parachain-height commitments, then calls `settle_first_proof` to record bookkeeping and pay the submitter [1](#0-0) .

Inside `settle_first_proof`, the reward transfer is attempted via `pay_position_reward`. For a rotation proof, a failed transfer is caught and logged so the rotation still lands. For a **messaging proof**, the error is propagated with `Err(e)?`, which fails the whole extrinsic: [2](#0-1) 

`pay_position_reward` transfers from the `TreasuryPalletId` account and returns `RewardTransferFailed` whenever the treasury balance is insufficient to cover `ProofReward` (as `Currency::transfer` with `Preservation::Preserve` will fail below the treasury's ED/available balance): [3](#0-2) 

Because Substrate wraps a `DispatchResultWithPostInfo`-returning call in a transactional storage layer, an `Err` return unwinds **all** storage writes performed during that dispatch — including the consensus-state and state-machine-commitment updates that `verify_and_apply` already persisted via `handle_incoming_message`. The comment in the code explicitly documents this design and calls it acceptable because "the work is re-attempted by the next proof once the treasury can pay": [4](#0-3) 

The unit test confirms the exact asymmetry: a rotation survives an unpayable reward, but a messaging proof is hard-rejected when the reward cannot be paid: [5](#0-4) 

Crucially, `ProofReward` is a permissionless, non-zero constant that every accepted first-proof submission draws from the treasury (`TreasuryPalletId` account), and `submit_proof` is a permissionless signed extrinsic [6](#0-5) . Nothing caps total payouts against the treasury balance, and no fallback path exists to advance the parachain height for a messaging proof without also attempting the reward transfer. Once the treasury balance drops below `ProofReward` (from ordinary operation, or from an attacker deliberately racing to land first-position proofs across many heights to drain it faster), **every subsequent messaging proof reverts in its entirety**, since `verify_and_apply` requires `latest_height` to strictly advance past `prev_height` for non-rotation proofs [7](#0-6) , and the reward-payment guard sits directly on that same path with no bypass.

### Impact Explanation
`MessagingProofs` are what advance `latest_height`/state-machine commitments carrying new ISMP request/response dispatch roots into Hyperbridge. If they can never settle, no new cross-chain requests, responses, or timeouts that depend on a fresh state commitment for that origin chain can be proven or delivered going forward — this is a full liveness halt on the bridge's message pipeline, not a cosmetic DoS: assets already committed cross-chain (order escrow, intent fills, refunds, relayer rewards keyed to proofs) cannot be settled or timed out because the underlying state commitment their proofs need never lands. This matches the bounty's "logic attacks" and fund-loss/lock category — the corrupted value is the halted `latest_height`/state-machine commitment for the coprocessor state machine, and existing guards (the `StaleProof`/`NoNewWork` checks) do nothing to prevent the reward-payment side effect from vetoing an otherwise-valid, already-verified proof.

### Likelihood Explanation
The condition is reachable without any privileged actor: `submit_proof` is a permissionless signed extrinsic, and every successful first-position submission drains `ProofReward` from a fixed treasury account with no balance-aware backpressure. An attacker (or simply high proof volume under a governance-misconfigured `ProofReward`) can exhaust the treasury, at which point the hard-revert on messaging proofs triggers deterministically on every subsequent legitimate submission until an admin manually replenishes the treasury via governance — an out-of-band, non-atomic recovery step, exactly mirroring the Isomorph "won't fix... less terminal" resolution rationale.

### Recommendation
Apply the same fix pattern already used for rotation proofs to messaging proofs: log-and-continue on `RewardTransferFailed` for `settle_first_proof`'s reward payout instead of propagating `Err(e)?`, so the already-verified state-commitment advance is never rolled back due to an unrelated treasury-liquidity failure. Additionally, consider capping/rate-limiting `ProofReward` payouts against the observed treasury balance so depletion cannot be trivially forced by rapid first-position proof submission.

### Proof of Concept
1. Governance sets `ProofReward` to a non-trivial value via `set_proof_reward`.
2. An attacker (or ordinary provers) repeatedly submits valid SP1/naive first-position consensus proofs across increasing heights; each accepted submission calls `pay_position_reward`, transferring `ProofReward` out of the `TreasuryPalletId` account [8](#0-7) .
3. Once the treasury balance drops below `ProofReward`, the next valid messaging proof (non-rotation, `has_new_messages = true`) is submitted via `submit_proof` → `do_submit_proof` → `verify_and_apply` (succeeds, verifies cryptographically and would advance `latest_height`) → `settle_first_proof` → `pay_position_reward` fails with `RewardTransferFailed` → `Err(e)?` at line 580 unwinds the entire extrinsic, including the consensus-state advance from `verify_and_apply`.
4. This is reproduced deterministically by the existing test `an_unpayable_reward_cannot_block_a_rotation`, whose final assertion shows the messaging-proof submission returning `Err` under the identical treasury-empty condition that a rotation proof tolerates [9](#0-8) .
5. Every subsequent legitimate messaging proof for that state machine fails identically until governance manually tops up the treasury, halting delivery of all new cross-chain requests/responses/timeouts that depend on the advanced state commitment.

		fn pay_position_reward(
			submitter: &T::AccountId,
			position: u32,
		) -> Result<BalanceOf<T>, Error<T>> {
			let zero = BalanceOf::<T>::default();
			let base = ProofReward::<T>::get();
			if base == zero {
				return Ok(zero);
			}

			let reward = Self::position_reward(base, position);
			if reward == zero {
				return Ok(zero);
			}

			let treasury: T::AccountId =
				<T as Config>::TreasuryPalletId::get().into_account_truncating();
			<T as Config>::Currency::transfer(&treasury, submitter, reward, Preservation::Preserve)
				.map_err(|e| {
					log::warn!(
						target: "ismp",
						"[beefy-consensus-proofs] treasury reward transfer failed: {e:?}",
					);
					Error::<T>::RewardTransferFailed
				})?;

			if let Err(e) = T::ReputationAsset::mint_into(submitter, reward) {
				log::warn!(
					target: "ismp",
					"[beefy-consensus-proofs] reputation mint failed: {e:?}",
				);
			}

			Ok(reward)
		}

/// Same hazard, different source: an unpayable reward. `pay_position_reward` runs after the
/// caller has applied the rotation, so propagating `RewardTransferFailed` rolls it back — and
/// since the mandatory justification is the only one obtainable for that session, every retry
/// fails identically until the treasury is topped up, leaving consensus on the old set. The
/// reward is the cheaper thing to drop. Messaging proofs deliberately keep the hard error.
#[test]
fn an_unpayable_reward_cannot_block_a_rotation() {
	let mut ext = new_test_ext();
	let height = 800u64;

	ext.execute_with(|| {
		// The BEEFY proofs treasury holds nothing in genesis, so any non-zero reward makes the
		// transfer fail with `RewardTransferFailed`.
		ProofReward::<Test>::put(1_000_000u128);

		pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
			submitter(11),
			vec![PROOF_TYPE_SP1, 0xab],
			Some(H256::repeat_byte(11)),
			PROOF_TYPE_SP1,
			Vec::new(),
			rotation_outcome(height, 30),
		)
		.expect("an unpayable reward must not reject the rotation");

		assert_eq!(
			RotationProofs::<Test>::get().get(&30).copied(),
			Some(height),
			"the rotation must be recorded even though the reward could not be paid",
		);

		// The asymmetry is deliberate: reverting a messaging proof is recoverable, because the
		// next proof re-attempts the same work once the treasury can pay.
		assert!(
			pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
				submitter(12),
				vec![PROOF_TYPE_SP1, 0xac],
				Some(H256::repeat_byte(12)),
				PROOF_TYPE_SP1,
				Vec::new(),
				messaging_outcome(height + 1, 30),
			)
			.is_err(),
			"a messaging proof must still fail hard when the reward cannot be paid",
		);
