### Title
Silent, unconfirmed rewrite of the `origin` remote URL from an attacker-controlled GitHub API response - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` automatically rewrites a repository's local `origin` remote to whatever `clone_url` the GitHub/GHE API currently returns for that repository, with no user confirmation. The `IAPIRepository`/`IAPIFullRepository` object it trusts comes straight from the account's API endpoint, which is attacker-influenced whenever the attacker controls the repository being tracked (rename/transfer) or, more strongly, whenever the account's endpoint is a GitHub Enterprise Server the attacker operates or has compromised. This is the same class of bug as the Foundation report: one piece of state (`gitHubRepository.cloneURL` / the API-reported location) is updated based on a party-controlled input while the *consequence* (what the local `origin` remote now points to, and where the user's next push goes) is changed silently, without the confirmation that exists for the analogous "upstream remote" flow.

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches the current API state for the repo the user has locally and, if the repo already has a cached `gitHubRepository`, calls `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`: [1](#0-0) 

`updateRemoteUrl()` compares the currently configured remote URL to `apiRepo.clone_url`. If the protocols match and the current remote is unchanged from the previously cached `cloneURL`, it silently calls `gitStore.setRemoteURL(...)` to overwrite the `origin` remote with the new API-provided URL — no dialog, no user action required: [2](#0-1) 

`setRemoteURL` then unconditionally runs `git remote set-url`: [3](#0-2) 

The `apiRepo.clone_url` value is not attacker-arbitrary in the strict sense of an unrelated domain — it is scoped to the "owner/name" that Desktop derived from the *existing* remote via `matchGitHubRepository()`, and then fetched from the *account's endpoint*: [4](#0-3) 

That endpoint is attacker-controlled data in two realistic situations that require no local access, no leaked credentials, and no social engineering:
1. The account endpoint is a GitHub Enterprise Server the attacker operates (a normal, supported Desktop configuration for many orgs) — in that case the entire `IAPIFullRepository` JSON, including `clone_url`, is fully attacker-controlled.
2. The tracked repository itself is one the attacker administers (they created it, or are an org owner) — a repo rename/transfer changes what GitHub's API reports as `clone_url` for the same owner/name lookup, and Desktop applies it automatically.

Critically, Desktop already recognizes that changing a remote URL behind the user's back is dangerous — for the analogous `upstream` remote (fork parent tracking) it explicitly shows a confirmation dialog before changing anything: [5](#0-4) [6](#0-5) 

No equivalent guard/confirmation exists for the `origin` remote update path in `updateRemoteUrl()`, which is invoked as part of routine background repository refreshes rather than an explicit user action.

### Impact Explanation
Once `origin` is rewritten, every subsequent `git push`/`git fetch`/`git pull` the user performs through Desktop silently targets the new location instead of the one the user originally configured — this is exactly the "silent corruption of what the user commits or pushes" impact category. Because the change happens transparently inside a background refresh routine (not a user-initiated remote edit), the user has no visual cue that their commits are now landing in a different repository/location than they intended. In the GHES-attacker case, this could redirect a user's work (potentially proprietary/private code) toward a server fully controlled by the attacker.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) the victim to be using an attacker-influenced/malicious GitHub Enterprise Server account, or (b) the victim tracking a repository the attacker administers (own repo, or shared org repo with rename/transfer rights) — both plausible without any local machine compromise, admin rights, or social engineering step beyond the user's ordinary existing use of Desktop with that account/repo. The refresh path (`repositoryWithRefreshedGitHubRepository`) runs as part of normal background repository-state refresh, so no unusual user action is needed to trigger it.

### Recommendation
Apply the same guard used for the `upstream` remote: before silently calling `gitStore.setRemoteURL()` in `updateRemoteUrl()`, surface a confirmation dialog (mirroring `UpstreamAlreadyExists`) showing the old and new URLs for `origin` and requiring explicit user approval, rather than auto-applying the API-reported `clone_url`.

### Proof of Concept
1. Victim adds a GitHub Enterprise account whose endpoint is controlled by the attacker (or clones/tracks a repo the attacker administers on github.com).
2. Victim clones/opens the repo in Desktop; `gitHubRepository.cloneURL` is cached matching the current `origin` remote.
3. Attacker changes what the API reports for that owner/name lookup (renames/transfers the repo, or simply returns a different `clone_url` from the malicious GHES endpoint), keeping the URL protocol identical (e.g. `https://...`).
4. On the next background refresh, `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts:7-45`) detects `urlsMatch === false`, `protocolsMatch === true`, `remoteUrlUnchanged === true`, and calls `gitStore.setRemoteURL(...)` (`app/src/lib/git/remote.ts:56-64`), silently rewriting `origin`.
5. Victim runs `git push` from Desktop; the push is sent to the attacker-determined destination with no warning shown, unlike the confirmation flow that exists for `upstream` remote changes (`app/src/ui/upstream-already-exists/upstream-already-exists.tsx`).

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
