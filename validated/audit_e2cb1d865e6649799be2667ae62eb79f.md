### Title
Just-in-time locking to snipe forfeited-reward re-queue in `vlMGPBaseRewarder` - (File: `rewards/vlMGPBaseRewarder.sol`)

### Summary
`vlMGPBaseRewarder` distributes rewards via a synthetix-style, non-time-weighted `rewardPerTokenStored` checkpoint that is updated **instantly and in full** whenever a forfeiture is re-queued (`_queueNewRewardsWithoutTransfer`), using `totalStaked()` measured at that exact instant. Because `VLMGP.lock()` is a permissionless, unthrottled deposit that immediately counts toward `totalStaked()`/`balanceOf()`, an attacker can front-run a mempool-visible `VLMGP.unlock()`/`startUnlock()` call (which forces `multiclaimFor` → `vlMGPBaseRewarder.getReward()` → forfeits part of the unlocking user's accrued rewards back into the pool) by locking MGP in the same block just before it, then immediately claiming afterward to capture a share of the freshly forfeited rewards with zero holding duration.

### Finding Description
1. `VLMGP.unlock()` and `VLMGP.startUnlock()` unconditionally call `IMasterMagpie(masterMagpie).multiclaimFor(lps=[vlmgp], rewardTokens=[[]], msg.sender)` before mutating state: [1](#0-0) 
2. Because the reward-token array is empty, `MasterMagpie._claimBaseRewarder` calls `rewarder.getReward(_account, _receiver)` (not `getRewards`): [2](#0-1) 
3. `vlMGPBaseRewarder.getReward` → `_sendReward` computes `forfeitAmount = _calExpireForfeit(_account, userRewards[token][_account])` from the unlocking user's `getRewardablePercentWAD` (still reflecting the not-yet-zeroed cooldown slot), and re-injects the forfeited amount into the pool via `_queueNewRewardsWithoutTransfer`: [3](#0-2) 
4. `_queueNewRewardsWithoutTransfer` updates `rewardPerTokenStored` **immediately**, in full, using `totalStaked()` at that instant — there is no vesting/streaming period and no minimum holding duration: [4](#0-3) 
5. `totalStaked()`/`balanceOf()` are read live from `MasterMagpie.stakingInfo`, and `VLMGP.lock()`/`lockFor()` deposit is instantaneous with no cooldown before counting: [5](#0-4) [6](#0-5) 
6. `MasterMagpie._deposit` checkpoints the depositor's `userRewardPerTokenPaid` via `_harvestBaseRewarder` (`updateFor`) at deposit time, i.e., *before* the forfeiture bump, so the attacker is entitled to the entire subsequent increase in `rewardPerTokenStored`: [7](#0-6) [8](#0-7) 

No modifier, `nonReentrant` guard, or accounting check prevents this — `nonReentrant` only blocks reentrancy within a single call, not cross-transaction front-running, and there is no minimum-stake-duration requirement gating reward accrual in `_earned`/`rewardPerToken`. The attack requires only: attacker holds MGP, calls `VLMGP.lock()` in the block immediately preceding a pending `unlock()`/`startUnlock()` transaction visible in the mempool, then calls `MasterMagpie.multiclaim`/`multiclaimSpec` (which routes to `vlMGPBaseRewarder.getReward`) to realize the gain.

### Impact Explanation
The attacker captures a proportional share (`attacker balance / totalStaked at requeue time`) of yield that is forfeited by an unlocking user, despite having staked for zero economically meaningful duration. This dilutes and effectively steals unclaimed/forfeited yield that should accrue to genuine long-term `vlMGP` holders — matching the "theft of unclaimed yield" impact class. The loss is proportional to pool size and forfeiture size and is fully quantifiable and repeatable each time a sizeable unlock/forfeiture event is pending in the mempool.

### Likelihood Explanation
High feasibility: the only precondition is holding spare MGP and monitoring the public mempool for `VLMGP.unlock()`/`startUnlock()` calls, both of which are unprivileged, frequent user actions. No flash loan is even strictly required (regular MGP holdings suffice, since `lock()` is unrestricted), and the attack is repeatable indefinitely against any future forfeiture event. No special permissions are needed — `lock()`, `multiclaim`, and `multiclaimSpec` are all public/external.

### Recommendation
Introduce a minimum staking duration or linear reward-vesting/streaming mechanism (e.g., stream newly queued/forfeited rewards over a fixed duration similar to Synthetix `rewardsDuration`, or require a lock-up snapshot period) before a deposit's balance becomes eligible for a `rewardPerTokenStored` increase. Alternatively, checkpoint `balanceOf` at the start of the block/epoch preceding the forfeiture event rather than reading `totalStaked()` live at the moment of `_queueNewRewardsWithoutTransfer`, so JIT deposits cannot capture already-in-flight reward injections.

### Proof of Concept
Foundry test outline:
1. Deploy `MasterMagpie`, `VLMGP`, `vlMGPBaseRewarder`, MGP token, and a reward token; register `vlmgp` as a pool with the rewarder.
2. Victim locks a large MGP amount, waits, accrues reward-token earnings in `vlMGPBaseRewarder`, then calls `startUnlock()` followed (after cooldown) by a pending `unlock()` transaction (simulate as the next call in the same block in the test).
3. Attacker, holding MGP but with **zero prior stake**, in the same block:
   a. calls `VLMGP.lock(amount)` immediately before the victim's `unlock()` call,
   b. lets the victim's `unlock()` execute (triggering `multiclaimFor` → `getReward` → forfeiture re-queue, bumping `rewardPerTokenStored`),
   c. calls `MasterMagpie.multiclaimSpec([vlmgp], [[rewardToken]])` to harvest.
4. Assert: attacker's realized reward-token balance after step (c) is > 0, and greater than what a fair, time-weighted allocation (proportional to actual holding duration ≈ 0) would give (i.e., `attackerReward == attackerBalance * (deltaRewardPerToken) / 1e18 > 0` despite `stakingDuration == 0`), while the victim's forfeiture amount used in the calculation matches `calExpireForfeit`. This demonstrates the attacker extracted yield from a stake held for a single block.

    function _queueNewRewardsWithoutTransfer(uint256 _amountReward, address _rewardToken) internal
    {
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards = rewardInfo.historicalRewards + _amountReward;
        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**vlMGPDecimal) / totalStaked();
        }
        emit ForfeitRewardAdded(_amountReward, _rewardToken);
    }

        uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]);
        uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;


        userRewards[_rewardToken][_account] = 0;
