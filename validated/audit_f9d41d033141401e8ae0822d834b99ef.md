### Title
Algorithmic complexity DoS in offer cancellation-coin computation via attacker-crafted announcement/dependency graph - (File: `chia/wallet/trading/offer.py`)

### Summary
The CVE describes a quadratic-time DoS in Botan's X.509 name-constraint checking, where an attacker-controlled certificate with many SubjectAlternativeNames checked against many constraints causes superlinear CPU cost. `Offer.get_cancellation_coins()` in `chia/wallet/trading/offer.py` [1](#0-0)  contains an analogous pattern: it builds per-coin `dependencies` and `announcements` dictionaries from every coin spend in an offer bundle, then repeatedly scans all remaining coins' dependency lists against the removed coin's announcement set using nested loops and set intersections, restarting the scan whenever new announcements are removed.

### Finding Description
`get_cancellation_coins()` iterates over every non-addition coin spend in the offer's `SpendBundle`, executing each puzzle/solution pair to extract `CREATE_COIN_ANNOUNCEMENT` (opcode 60) and `ASSERT_COIN_ANNOUNCEMENT` (opcode 61) conditions, populating `dependencies[name]` and `announcements[name]` [2](#0-1) . It then enters an outer `while True` loop calling `detect_dependent_coin(coin_names, dependencies, announcements)`, and for each match, an inner `while True` loop that scans `dependencies.items()` against `removed_announcements` via `set(deps) & set(removed_announcements)` for every remaining coin, repeating until no more announcements propagate [3](#0-2) .

Both `coin_names` and `dependencies` are entirely attacker-controlled: an offer counterparty constructs the `SpendBundle` (coins, puzzles, solutions) embedded in the `.offer` file, and can freely include a large number of coin spends, each emitting many `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions to build a dense dependency graph. Because the inner loop re-scans the full `dependencies` dict for every coin removed from the outer loop, and the outer loop can run once per coin, the algorithm scales at least quadratically (and the repeated `set(deps) & set(removed_announcements)` construction adds further cost per pair), mirroring the CVE's core defect: checking many attacker-supplied names against many constraints without linearizing the comparison.

### Impact Explanation
An unprivileged offer counterparty who crafts a `.offer` file with a large number of coin spends and cross-referencing coin announcements can force any wallet user who imports/inspects that offer (e.g., to determine coins needed to cancel it) into evaluating a quadratic-or-worse dependency-resolution loop entirely in Python, executing CLVM (`run_with_cost`) for every included spend along the way. This can stall or hang the wallet process handling the offer, denying service to the local wallet/RPC caller — consistent with the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
Likelihood is limited by the fact that this path is reached specifically when a wallet computes cancellation coins for an offer (via `Offer.get_cancellation_coins`, referenced from `chia/wallet/trade_manager.py`), which requires the victim to load/process the malicious offer file rather than this happening automatically during normal offer settlement. The offer file itself is entirely attacker-supplied and does not require any privileged access, making crafting a pathological input straightforward, but triggering the vulnerable code path requires the victim to take an explicit cancellation-related action on the malicious offer.

### Recommendation
Bound `get_cancellation_coins()` computation: cap the number of coin spends/announcements processed per offer, and replace the repeated `set(deps) & set(removed_announcements)` full-dictionary rescans with an incremental/queue-based propagation (e.g., building a reverse index from announcement hash to dependent coin once, then processing removals via a work-queue) so the algorithm runs in linear or near-linear time relative to the number of coins and announcements, regardless of how the attacker structures the dependency graph.

### Proof of Concept
Not independently executed; based on static analysis of `chia/wallet/trading/offer.py:425-470`. A proof-of-concept would construct an `Offer` whose underlying `SpendBundle` contains N coin spends, each emitting an `ASSERT_COIN_ANNOUNCEMENT` referencing announcements created by many other coins in the set (a densely interconnected announcement graph), then call `offer.get_cancellation_coins()` and measure wall-clock time growth as N increases — expected to grow faster than linearly given the nested full-dictionary rescans in the algorithm. I was unable to fully trace the exact call site inside `chia/wallet/trade_manager.py` within the available search budget, so the precise wallet-facing trigger point (e.g., specific RPC or CLI command) should be confirmed before treating this as fully proven in production.

    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
