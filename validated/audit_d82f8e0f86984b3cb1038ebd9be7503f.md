## Title
GitHub Desktop disables Git's clone-time submodule hook protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), allowing a malicious cloned/forked repository to execute attacker-controlled hooks during `clone --recursive` - ([File: app/src/lib/git/clone.ts])

### Summary
The PolyNetwork report's underlying bug class is that an attacker-controlled, externally-supplied message ("cross-chain data") is trusted to bypass a security modifier/check that is supposed to gate privileged execution. The GitHub Desktop analog is `clone()`, which explicitly forces the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` for every clone, deliberately disabling the upstream Git safety guard (introduced by Git in response to CVE-2024-32002) that prevents malicious repositories from smuggling executable hooks through crafted submodule/`.git` structures during `clone --recursive`. [1](#0-0) 

### Finding Description
`clone()` always appends `--recursive` to the git clone invocation, meaning any submodules referenced by an attacker-controlled remote are automatically initialized and checked out without prompting the user. [2](#0-1) 

At the same time, the function unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment passed to the `git clone` process: [3](#0-2) 

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git itself introduced to enable/disable its built-in defenses against symlinked `.git` directories and case-insensitive-filesystem hook-name collisions that let a crafted repository (with nested submodules) plant an executable file in `.git/hooks` of the *host* repository during a recursive clone — the exact vulnerability class fixed by Git 2.45.1 (CVE-2024-32002). By hard-coding this flag to `'false'`, GitHub Desktop reintroduces that protection gap for every clone it performs, regardless of the user's installed Git version's default behavior.

The only other check performed before cloning is `isClonePathSensitive`, which only validates the *destination path* is not a sensitive system location (e.g., `~/.ssh`, `~/.gnupg`) — it does nothing to validate the *content* of the remote repository or its submodules. [4](#0-3) 

There is no other invocation in the code that re-enables or overrides `GIT_CLONE_PROTECTION_ACTIVE`, and `envForRemoteOperation` (spread first, so it can be overwritten by the explicit key) does not set this variable, meaning the disabling is unconditional and not something addressed later in the pipeline. [3](#0-2) 

### Impact Explanation
An attacker who controls the content of a repository a user clones through GitHub Desktop (e.g., via a malicious fork, a link shared to the user, a compromised upstream, or a supply-chain-planted submodule) can craft a repository/submodule layout that — with Git's built-in clone protection intentionally disabled by Desktop — plants an executable hook (e.g., `post-checkout`, `pre-commit`) into the resulting repository's hooks directory. Because Desktop's own hook-interception pathway (`withHooksEnv`/`getRepoHooks`) discovers and later helps proxy/execute hooks that exist on disk, a hook smuggled in this way is a genuine path to attacker code execution on the victim's machine the next time a corresponding git operation runs. This satisfies the "attacker controls a cloned/fetched repository ... resulting in code execution" impact category. [5](#0-4) 

### Likelihood Explanation
The path requires only that a victim clone an attacker-controlled or attacker-influenced repository via GitHub Desktop's normal clone UI — no local access, no admin rights, and no prior malware are needed. `clone()` is the single, unconditional code path used for every clone operation and always passes `--recursive` while always disabling the protection variable, so there is no user setting or code branch that avoids the exposure. [6](#0-5) 

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE` to `'false'`. Leave Git's default protections enabled (or explicitly set to `'true'`) so the upstream CVE-2024-32002 mitigations apply, and only disable them if a concrete, narrowly-scoped compatibility reason is documented and the disabling is paired with equivalent application-level validation of submodule paths/symlinks before recursive clone.

### Proof of Concept
1. Attacker publishes a public repository containing a submodule configured with a crafted `.gitmodules`/nested `.git` layout designed to place an executable file into the parent repository's `hooks` directory during `git submodule update --init --recursive` (the class of layouts fixed by CVE-2024-32002).
2. Victim uses GitHub Desktop's "Clone repository" feature with the attacker's URL.
3. `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment, disabling Git's built-in defenses against the crafted layout. [1](#0-0) 
4. The malicious hook file is written into `path/.git/hooks/<hookname>`.
5. The next git operation that triggers that hook (e.g. `post-checkout` on the initial checkout, or a subsequent `commit`/`checkout` in Desktop) executes the attacker's payload with the victim's privileges.

Note: I could not execute an end-to-end reproduction (no sandbox/terminal access in this mode) to confirm the exact submodule layout still bypasses Desktop's higher-level checks in the exact installed Git version; the finding is based on static code evidence that the protection variable is deliberately disabled with no compensating control found elsewhere in the codebase.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

export async function* getRepoHooks(path: string, filter?: string[]) {
  const hooksPath = await getConfigValue(path, 'core.hooksPath')
    .catch(() => getHooksPath(path))
    .then(p => resolve(path, p))

  const files = await readdir(hooksPath, { withFileTypes: true })
    .then(entries => entries.filter(x => x.isFile()))
    .catch(() => [])

  const matchAll = filter?.includes('*')

  for (const file of files) {
    const hookName = basename(file.name, '.exe')

    if (matchAll || filter?.includes(hookName) === false) {
      continue
    }

    if (!knownHooks.includes(hookName)) {
      continue
    }

    if (__WIN32__) {
      // On Windows we have to assume that any valid hook name is executable
      // because the executable bit is not used there. Git looks for a shebang
      // but that seems expensive to check here :shrug:
      yield hookName
    } else if (await isExecutable(join(file.parentPath, file.name))) {
      yield hookName
    }
  }
