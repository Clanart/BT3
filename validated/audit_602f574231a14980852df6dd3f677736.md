## Analysis

The report's core invariant is: **a security-relevant "already done" state is keyed by an identifier that is not actually stable/unique to the entity it was meant to represent**, allowing a new entity that reuses that identifier to inherit privileges it never earned.

GitHub Desktop has a direct structural analog in its "unsafe repository" / `safe.directory` trust flow.

### Title
Repository trust ("safe.directory" exception) is bound to a filesystem path instead of repository identity, allowing a new/attacker-controlled repository at a previously-trusted path to silently bypass Git's dubious-ownership protection - (File: `app/src/lib/git/config.ts`)

### Summary
When Git detects that a repository directory is owned by a different user than the current process ("dubious ownership"), it refuses to operate on it. GitHub Desktop surfaces this as an "unsafe repository" warning and offers a "Trust Repository" action [1](#0-0)  and [2](#0-1) . Clicking it calls `addSafeDirectory(path)`, which permanently appends the raw filesystem `path` string to the **global** `safe.directory` git config [3](#0-2) . Once added, Git will consider *any* repository later found at that same path as trusted, forever, regardless of who owns or controls its contents.

### Finding Description
`addSafeDirectory` records trust keyed solely by `path`: [3](#0-2) . This is analogous to the audited contract tracking `claimed[eraIndex][recipient]` where `recipient` is derived from a mutable identifier (`operatorKey`) instead of a stable one. Here, `path` is treated as if it uniquely and permanently identifies "the repository the user inspected and decided to trust," but a filesystem path is not a stable identity — it can be reoccupied by completely different content/ownership over time (directory removed and recreated, a different repository cloned into the same location, a mount point pointing elsewhere, restoring an archive to that path, etc.).

The trust check performed before showing the warning is purely `getRepositoryType(path)` returning `unsafe` based on git's own ownership check [4](#0-3) . There is no binding of the trust decision to a content hash, remote URL, or any property of the repository other than the path string itself, and no code path in the repository re-validates that a "trusted" path still points at the repository the user originally trusted — `addGlobalConfigValueIfMissing('safe.directory', path)` is a one-time, indefinite grant with no corresponding removal when a repository is removed from Desktop or when Desktop detects the directory was recreated. `MissingRepository`'s "Trust Repository" flow re-checks `getRepositoryType` only to see if the *ownership mismatch* is gone, not whether the content is the one previously trusted [5](#0-4) .

### Impact Explanation
Git treats paths listed in `safe.directory` as exempt from the "dubious ownership" protection, which exists specifically to stop execution of repository-controlled hooks/config (e.g., `core.fsmonitor`, `core.hooksPath`, and other repo-local settings capable of running arbitrary commands) when a repo is not owned by the current user. If an attacker can cause new, attacker-controlled repository content to land at a path a victim previously trusted (e.g., a shared/multi-user machine, a temp/build directory, a network share, or any workflow where the original repository directory is deleted and something else — legitimately or via a supply-chain step — is placed there), Desktop and the embedded Git will silently treat that new content as trusted and execute repository-controlled configuration/hooks without re-prompting the user. This can lead to arbitrary code execution under the victim's account, matching the "Impact: High" bar in the seed report because the "reward" (elevated trust bypassing ownership checks) can be reused/re-triggered by a different, untrusted principal than the one the check was meant to authorize.

### Likelihood Explanation
Likelihood is Low-to-Medium, similar to the seed's rated likelihood, because it requires the specific precondition that a previously-trusted path gets reoccupied by different, attacker-influenced content — most plausible on shared machines, CI/build agents, or temp-directory reuse patterns where GitHub Desktop is used against ephemeral working directories. It requires no local/physical access beyond what Desktop's own trust model already contemplates (the whole feature exists to handle "a different user owns this directory" scenarios), no admin rights, and no credential leakage — only that the attacker can influence what occupies a path Desktop remembered as safe.

### Recommendation
Do not treat `safe.directory` grants as an indefinite, path-only trust decision inside Desktop's own bookkeeping:
- Bind the "trusted" decision to a stronger identity signal in addition to path (e.g., record the repository's initial commit/root tree, `.git` directory identity, or remote URL at the time of trust, and re-validate before silently proceeding on subsequent app runs).
- When Desktop detects that a path's underlying repository identity has changed (different initial commit, different `.git` gitdir, different remote) from what was recorded at trust time, re-surface the "unsafe repository" warning rather than relying solely on Git's global `safe.directory` allowlist persisting.
- Remove the corresponding `safe.directory` entry when the associated repository is removed from Desktop (`repositoriesStore.removeRepository`), rather than leaving a permanent global exception.

### Proof of Concept
1. Victim clones/opens a legitimate repository at `C:\Users\victim\work\project` (or any path); Git flags it as "unsafe" (e.g., differing owner from a previous restore, network share, or container mount), and the victim clicks "Trust Repository" in `MissingRepository`/`AddExistingRepository`, calling `addSafeDirectory('C:\Users\victim\work\project')` [6](#0-5) . This permanently adds that path to the global `safe.directory` list.
2. At a later time, that same path is emptied and repopulated with a different, attacker-crafted Git repository (e.g., via a build script, container re-provisioning, restored backup, or any process that deletes and recreates the directory) containing a malicious `core.hooksPath`/`.git/hooks` or `core.fsmonitor` command.
3. Desktop calls `getRepositoryType(path)` again [7](#0-6) ; because the path is already in the global `safe.directory` list, Git no longer reports `unsafe`, so Desktop proceeds to run ordinary Git operations (status, fetch, checkout) against the new repository without any warning, executing the attacker's repository-controlled hooks/config under the victim's account.

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}

export async function getRepositoryType(path: string): Promise<RepositoryType> {
  if (!(await directoryExists(path))) {
    return { kind: 'missing' }
  }

  try {
    const result = await git(
      ['rev-parse', '--is-bare-repository', '--show-cdup', '--git-dir'],
      path,
      'getRepositoryType',
      { successExitCodes: new Set([0, 128]) }
    )

    if (result.exitCode === 0) {
      // Bare repositories will not include gitdir so we handle that separately
      if (result.stdout.startsWith('true\n')) {
        return { kind: 'bare' }
      }

      // --is-bare-repository and --show-cdup each produce a single line but
      // --git-dir could theoretically contain newlines so we parse the known
      // fields first and treat the remainder as the git dir. We use [\s\S]*
      // instead of .* for the git dir capture group because .* doesn't match
      // newlines whereas [\s\S]* matches any character including newlines.
      const match = result.stdout.match(/^(true|false)\n(.*)\n([\s\S]*)\n$/)

      if (match) {
        const [, isBare, cdup, gitDir] = match

        return isBare === 'true'
          ? { kind: 'bare' }
          : {
              kind: 'regular',
              topLevelWorkingDirectory: resolve(path, cdup),
              gitDir: resolve(path, gitDir),
            }
      }
    }

    const unsafeMatch =
      /fatal: detected dubious ownership in repository at '(.+)'/.exec(
        result.stderr
      )
    if (unsafeMatch) {
      return { kind: 'unsafe', path: unsafeMatch[1] }
    }

    return { kind: 'missing' }
