Based on my investigation, the strongest genuine analog I found relates to a deliberate override of Git's own file-protocol safety default for submodules.

### Title
Submodule `file://` protocol re-enablement allows attacker-controlled repository to read arbitrary local files during checkout - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol` flag that, when true, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation [1](#0-0) . This function is invoked from checkout flows in `app/src/lib/git/checkout.ts` (7 call sites), which are the paths triggered when a user checks out a branch/commit — including branches originating from a cloned/fetched repository that is not necessarily trusted. Upstream Git deliberately changed the default for `protocol.file.allow` from `always` to `user` (i.e., disabled by default) specifically to close a disclosure vector where a malicious repository's `.gitmodules` file declares a submodule with a `file://` URL pointing at an arbitrary local path (e.g., a sibling repository, SSH config, or other sensitive local directory), causing that content to be silently pulled into the working tree during a routine checkout/submodule update.

### Finding Description
The broken invariant is: submodule URLs are attacker-controlled data (they live in `.gitmodules`, which is committed content of a repository the user cloned or checked out), yet Desktop conditionally re-widens Git's own protection (`protocol.file.allow=always`) around that same attacker-controlled input [2](#0-1) . If any checkout path passes `allowFileProtocol = true` for content coming from an untrusted remote/branch, an attacker who controls the repository (or a branch/PR the victim checks out) can craft a `.gitmodules` entry such as:
```
[submodule "x"]
  path = x
  url = file:///Users/victim/.ssh
```
When the victim checks out that branch and Desktop runs `git submodule update --init --recursive` with the file-protocol override enabled, Git will treat the local path as a clonable repository source and copy its tree into the working directory, silently exfiltrating file contents outside the intended repository boundary into the user's own working tree (from which it could then be committed/pushed, or simply read from disk).

### Impact Explanation
If reachable from an untrusted checkout path, this permits file read outside the repository sandbox and potential exfiltration of sensitive local data (SSH keys, config files) purely by the victim checking out a branch from a repository they cloned — matching the "unprivileged, repo-controlled, results in file read/write outside repo" impact class.

### Likelihood Explanation
I was not able to confirm, within this investigation, which of the 7 call sites in `checkout.ts` pass `allowFileProtocol = true` versus `false`, nor whether that decision is gated on the branch/remote being locally-created versus fetched from a remote. This is the critical missing piece: if `allowFileProtocol` is only ever `true` for repositories the user explicitly created/trusts locally (not for arbitrary fetched/cloned content), then this is not exploitable by a remote attacker. I could not verify this distinction with the tools available in this session.

### Recommendation
Confirm (via a full Devin session with file access) whether any `checkout.ts` call site passes `allowFileProtocol = true` for branches/commits sourced from an untrusted remote. If so, restrict the override to Desktop-initiated/local-only scenarios, or better, drop the override entirely and rely on Git's default `protocol.file.allow=user` behavior for any submodule update triggered by checking out fetched content.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm the exact call-site conditions in `checkout.ts`; the PoC would be: attacker creates a repo with a `.gitmodules` submodule using a `file://` URL to a sensitive local path, victim clones/fetches and checks out the malicious branch, and if the checkout path invokes `updateSubmodulesAfterOperation` with `allowFileProtocol: true`, the local directory content is copied into the victim's working tree.

**Note on confidence:** This finding is based on real code (`app/src/lib/git/submodule.ts`) showing the mechanism exists, but I could not fully verify exploitability (i.e., whether attacker-reachable checkout paths actually pass `allowFileProtocol: true`) within the available tool budget. A follow-up session with direct file access to `app/src/lib/git/checkout.ts` call sites is needed to confirm or refute reachability before treating this as a confirmed vulnerability.
