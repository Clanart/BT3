### Title
Silent, unconfirmed rewrite of a repository's Git remote URL from attacker‑controlled GitHub API data — (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop keeps two independent representations of "where does this repository live": the `IRemote` recorded in the local Git config (read/written via `GitStore`) and the `GitHubRepository` metadata cached from the GitHub API (`endpoint`, `owner`, `name`, `cloneURL`). `updateRemoteUrl` reconciles these by silently rewriting the local `origin` remote whenever the cached API `cloneURL` no longer matches the freshly fetched `apiRepo.clone_url` — with no user confirmation, unlike the analogous `UpstreamAlreadyExists` dialog used for the upstream remote.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` re-resolves a tracked repository's association periodically (e.g. when the repository is selected, or a background refresh occurs): [1](#0-0) 

It calls `api.fetchRepository(owner, name)` and, if the repository already has an associated `gitHubRepository`, passes the result straight into `updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)`.

`updateRemoteUrl` then compares the *previously cached* `gitHubRepository.cloneURL` against the *current* local remote URL and the *newly fetched* `apiRepo.clone_url`: [2](#0-1) 

If the protocol of old vs. new URL matches, and the local remote is still equal to the previously-cached `cloneURL` (i.e. the user hasn't manually customized it), and the new URL differs, it calls `gitStore.setRemoteURL(...)` to overwrite the on-disk Git remote — with **no user prompt**. This is a very different UX than the sibling case for the upstream remote, where `UpstreamAlreadyExists` explicitly asks the user before changing a remote URL: [3](#0-2) 

The value being trusted, `apiRepo.clone_url`, is attacker-influenced whenever the endpoint queried is not github.com — i.e., a GitHub Enterprise Server the user has signed into (`isGHES`), or any host reachable through `API.fromAccount(account)` for that account's `endpoint`. On such a server, the operator (or anyone who compromises/MITMs it) fully controls the JSON body returned for `GET repos/{owner}/{name}`, including the `clone_url` field, since there is no validation that `clone_url` corresponds to `endpoint`, `owner`, or `name`: [4](#0-3) 

The only guard rails are: (1) protocol must match the previously-known protocol, and (2) the current local remote must still equal what Desktop previously cached as `cloneURL`. Neither of these validates the *host* of the new URL — an https→https rewrite pointing at a completely different, attacker-chosen host passes both checks.

### Impact Explanation
This breaks the invariant that a repository's Git remote is only ever changed with the user's explicit knowledge/consent. A malicious or compromised GitHub Enterprise Server that a user has added an account for can cause Desktop to silently repoint the `origin` remote of any repository whose GitHub association resolves to that server, to an arbitrary attacker-controlled Git host, on a routine background refresh. Subsequent `git push`/`fetch` operations performed through Desktop will silently go to the attacker's server instead of the legitimate one — i.e., silent corruption of what the user commits/pushes, matching the specified valid-impact class ("attacker controls...a GitHub API object...and the result is...silent corruption of what the user commits or pushes"). Depending on the attacker's server configuration this can exfiltrate source code/commit history pushed by the victim without any warning dialog being shown (contrast with the `UpstreamAlreadyExists` flow, which explicitly confirms).

### Likelihood Explanation
Requires the victim to have an account configured against an attacker-controlled or compromised GHES endpoint and to have added/cloned a repository whose owner/name resolves against that endpoint — a plausible, low-friction condition in enterprise/GHES environments (no local access, no prior malware, no leaked credentials required; the "attacker controls...a git remote/proxy response" precondition in the Valid Impact list is satisfied by controlling the API host). The rewrite happens automatically as part of routine repository refresh (`repositoryWithRefreshedGitHubRepository`), requiring no unusual user action beyond normal use of Desktop.

### Recommendation
- Do not silently rewrite the default remote URL based on API data; require explicit user confirmation (reusing the `UpstreamAlreadyExists`-style dialog) before changing `origin`, and additionally validate the new URL's hostname is consistent with the account's configured `endpoint`.
- Treat `IRemote`/on-disk Git config as the single source of truth and never let `GitHubRepository` cache data mutate it without an explicit, auditable user action, mirroring the recommendation from the referenced report to keep dependent state in sync through a single, guarded write path rather than two independent update paths (`updateRemoteUrl` silent path vs. `UpstreamAlreadyExists` confirmed path).

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop pointing at `https://malicious-ghes.example` (attacker controlled or compromised).
2. Clone/add a repository whose remote resolves (via `matchGitHubRepository`) to that endpoint, e.g. `https://malicious-ghes.example/acme/widgets`.
3. Attacker's server responds to `GET repos/acme/widgets` with a JSON body where `clone_url` is `https://attacker-server.example/acme/widgets` (any host, same `https` protocol).
4. On the next periodic refresh, `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` sees `protocolsMatch === true`, `remoteUrlUnchanged === true` (user hasn't touched the remote), `urlsMatch === false`, and calls `gitStore.setRemoteURL('origin', 'https://attacker-server.example/acme/widgets')` with no prompt.
5. The next `git push`/`fetch` performed in Desktop silently targets `attacker-server.example` instead of the legitimate host. [5](#0-4)

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

      const response = await this.ghRequest('GET', `repos/${owner}/${name}`)

      }
      return await parsedResponse<IAPIFullRepository>(response)

      log.warn(`fetchRepository: an error occurred for '${owner}/${name}'`, e)
