### Analysis

The observed behavior is real but does not constitute exfiltration of the token to an unauthorized party.

`isGitHubRepoAssetPath` intentionally has no owner/repo ownership check because Desktop's main process has no reliable client-side way to know which private repos a given account token has access to [1](#0-0) . Authorization is delegated to GitHub's own backend: the filter only decides *whether to attach the token to a request that is already going to `github.com`*, not whether the request should be trusted.

Two things bound the impact:

1. **The token is only ever attached to requests whose origin equals `getHTMLURL(dotComAPIEndpoint)`**, i.e. `https://github.com` itself (or the correct GHE host, mapped from the corresponding account endpoint) — never to a third-party or attacker-controlled origin [2](#0-1) .
2. **Cross-origin redirects are separately sanitized** by `installSameOriginFilter`, which strips the `Authorization` header if a request is redirected to a different origin than it started at, preventing the token from leaking off `github.com` even via a redirect chain [3](#0-2) .

So the scenario described — fetching an asset path belonging to an unrelated private repo — results in Desktop sending the user's own token to `github.com`/`api.github.com`, exactly as a normal authenticated browser request to GitHub would. GitHub's server-side authorization is what determines whether the response is `200` (repo accessible) or `401/403` (not accessible); Desktop is not bypassing or weakening that check, and the token never reaches any host controlled by the third party who set up the "unrelated" repo. This is the same trust model as any authenticated HTTP client hitting a REST API — the origin is fixed and trusted, and per-object access control is the server's job, not the client's regex matcher.

Both `installAuthenticatedImageFilter` and `installSameOriginFilter` are registered together in the main process startup, confirming the intended layered design (token attached only for the fixed known origin, then protected against onward leakage) [4](#0-3) .

Since GitHub's server-side authorization is the existing control that stops unauthorized access to the unrelated private repo's asset, and the token is never sent to an attacker-controlled host, this does not meet the "credential/token exfiltration" or other valid-impact categories in scope.

function isGitHubRepoAssetPath(pathname: string) {
  // Matches paths like: /repo/owner/assets/userID/guid
  return (
    /^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/.test(pathname) ||
    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}
