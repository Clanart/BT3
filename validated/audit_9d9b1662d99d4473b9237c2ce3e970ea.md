### Title
Unrestricted HTTP redirect following in GitHub API client enables SSRF via malicious/compromised GitHub Enterprise endpoint - (File: `app/src/lib/http.ts`)

### Summary
GitHub Desktop's core GitHub/GHE API request function, `request()` in [1](#0-0) , calls the browser `fetch()` API without setting a `redirect` option, so it defaults to `redirect: "follow"`. Every authenticated call made through `API.ghRequest`/`API.request` in [2](#0-1)  — repository, issue, PR, comment, OAuth-token-exchange, etc. — inherits this behavior. If a configured GitHub Enterprise Server (GHES) endpoint is compromised or otherwise attacker-controlled, it can respond to any of these API calls with an HTTP redirect to an arbitrary internal/local address, and Desktop will automatically follow it, exactly mirroring the price-feeder SSRF pattern in the report (redirect response causing an unintended internal request).

### Finding Description
The only redirect-related safeguard shipped in Desktop is `installSameOriginFilter` in [3](#0-2) , which tracks the origin of the initial request per `webRequest` request ID and, on a cross-origin redirect, strips only `authentication`, `authorization`, and `cookie` headers from the follow-up request. Critically, this filter:
- Never cancels or blocks the redirected request.
- Never inspects or restricts the destination host/IP (no blocklist for `127.0.0.1`, `169.254.169.254`, RFC1918 ranges, etc.).
- Only protects three specific header names — it does nothing to prevent the redirected request's method, path, query string, or POST body from reaching the new destination.

By contrast, the one place in the codebase that *does* correctly defend against this class of bug is `isGitHubHost()` in [4](#0-3) , which explicitly sets `redirect: 'error'` for its discovery probe. This shows the team is aware of the risk for that single call site, but the fix was not applied to the general-purpose `request()` function that backs essentially all other API traffic, including the OAuth code-exchange flow in `requestOAuthToken()` [5](#0-4) .

### Impact Explanation
A malicious or compromised GitHub Enterprise Server endpoint (one the user has legitimately added as an account) can turn Desktop into a confused deputy performing SSRF against the victim's local machine or internal network: any `ghRequest`/`request` call — e.g. `fetchRepository`, `forkRepository`, `fetchIssues`, `fetchMentionables`, `requestOAuthToken` — can be redirected via a 30x response to `http://127.0.0.1:<port>/...` or an internal-only host, and Desktop's fetch will transparently issue the follow-up request, carrying whatever method/body/query the original request had (headers are stripped only for cross-origin authentication/authorization/cookie). This can be used to probe or interact with local-only services running on the user's workstation (as in the price-feeder/Tendermint mempool example) or with internal network endpoints unreachable from the internet, without any user interaction beyond having previously added the GHE account.

### Likelihood Explanation
Requires the attacker to control (via compromise or malicious operation) a GitHub Enterprise Server that a victim has configured as an account in Desktop — this is a real, supported configuration (not requiring local/physical access, admin rights, or prior malware), and every subsequent API call Desktop performs against that endpoint is an opportunity to redirect. No unusual user action is needed; ordinary usage of the app (viewing PRs, fetching issues, forking) triggers these requests.

### Recommendation
Apply the same fix already used in `isGitHubHost()` more broadly: set an explicit `redirect` policy (e.g. `redirect: 'manual'` or `'error'`) in `request()` in `app/src/lib/http.ts`, and if redirects must be supported for legitimate API pagination/link headers, validate the resolved redirect target's hostname/IP against a denylist of loopback/link-local/private ranges before manually re-issuing the request. This closes the gap left by `same-origin-filter.ts`, which only sanitizes headers but never blocks the request from reaching an attacker-chosen internal destination.

### Proof of Concept
1. Add a GitHub Enterprise account in Desktop pointing to `https://ghe.attacker-controlled.example/api/v3`.
2. Attacker compromises or configures that GHES instance so that any API path (e.g. `repos/:owner/:repo`) responds with:
   ```
   HTTP/1.1 302 Found
   Location: http://127.0.0.1:<internal-service-port>/some/sensitive/action
   ```
3. Desktop performs a normal action that triggers `API.fetchRepository()` (→ `ghRequest` → `request()` in `app/src/lib/http.ts`).
4. `fetch()` follows the redirect automatically (default `redirect: 'follow'`); `same-origin-filter.ts` strips only `Authorization`/`Cookie`/`Authentication` headers because the origin changed, but still issues the GET/POST to `http://127.0.0.1:<port>/...`, demonstrating the SSRF primitive against any locally-listening service.

export function request(
  endpoint: string,
  token: string | null,
  method: HTTPMethod,
  path: string,
  jsonBody?: Object,
  customHeaders?: Object,
  reloadCache: boolean = false
): Promise<Response> {
  const url = getAbsoluteUrl(endpoint, path)

  let headers: any = {
    Accept: 'application/vnd.github.v3+json, application/json',
    'Content-Type': 'application/json',
    'User-Agent': getUserAgent(),
  }

  if (token) {
    headers['Authorization'] = `Bearer ${token}`
  }

  headers = {
    ...headers,
    ...customHeaders,
  }

  const options: RequestInit = {
    headers,
    method,
    body: JSON.stringify(jsonBody),
  }

  if (reloadCache) {
    options.cache = 'reload' as RequestCache
  }

  return fetch(url, options)
}

    }

    return response
  }

      urlBase,

  }

export function installSameOriginFilter(orderedWebRequest: OrderedWebRequest) {
  // A map between the request ID and the _initial_ request origin
  const requestOrigin = new Map<number, string>()
  const safeProtocols = new Set(['devtools:', 'file:', 'chrome-extension:'])
  const unsafeHeaders = new Set(['authentication', 'authorization', 'cookie'])

  orderedWebRequest.onBeforeRequest.addEventListener(async details => {
    const { protocol, origin } = new URL(details.url)

    // This is called once for the initial request and then once for each
    // "subrequest" thereafter, i.e. a request to https://foo/bar which gets
    // redirected to https://foo/baz will trigger this twice and we only
    // care about capturing the initial request origin
    if (!safeProtocols.has(protocol) && !requestOrigin.has(details.id)) {
      requestOrigin.set(details.id, origin)
    }

    return {}
  })

  orderedWebRequest.onBeforeSendHeaders.addEventListener(async details => {
    const initialOrigin = requestOrigin.get(details.id)
    const { origin } = new URL(details.url)

    if (initialOrigin === undefined || initialOrigin === origin) {
      return { requestHeaders: details.requestHeaders }
    }

    const sanitizedHeaders: Record<string, string> = {}

    for (const [k, v] of Object.entries(details.requestHeaders)) {
      if (!unsafeHeaders.has(k.toLowerCase())) {
        sanitizedHeaders[k] = v
      }
    }

    log.debug(`Sanitizing cross-origin redirect to ${origin}`)
    return { requestHeaders: sanitizedHeaders }
  })
