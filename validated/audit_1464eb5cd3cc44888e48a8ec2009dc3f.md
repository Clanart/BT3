## Analysis

Now I have enough evidence to identify the strongest analog. The core broken invariant in the report is: **a security-relevant check is performed on one identity (`msg.sender`), while the actual privileged action is applied to a different, related identity (`from`) that isn't independently re-validated** — allowing an unchecked value to silently drive a sensitive state change.

`updateRemoteUrl` in GitHub Desktop exhibits the same class of flaw: it validates the *protocol* and the *previous* clone URL of the locally-recorded `gitHubRepository`, but the value it actually writes to the git config (`apiRepo.clone_url`) comes from a live GitHub API response that is never itself checked against an allow-list of trusted hosts/owners — it's implicitly trusted because it "came from the API." This mirrors the report's structure: the check (`notBlacklisted`/protocol+previous-url check) targets one value, while the write operation is silently performed using a second, less-scrutinized value (`from`/`apiRepo.clone_url`).

### Title
Silent Git Remote URL Rewrite from Unvalidated GitHub API `clone_url` - (File: app/src/lib/stores/updates/update-remote-url.ts)

### Summary
`updateRemoteUrl()` automatically rewrites a repository's `origin` remote URL using the `clone_url` field from a GitHub API repository object, without validating that URL against an allow-list of trusted hosts or requiring user confirmation. It only checks the *protocol* of the old vs. new URL, and whether the *previously known* clone URL still matches — the incoming `apiRepo.clone_url` value itself is never validated before being used with `git remote set-url`. [1](#0-0) 

### Finding Description
`repositoryWithRefreshedGitHubRepository()` fetches the repository object from GitHub's API (`api.fetchRepository(owner, name)`) each time a repository is selected or refreshed, and passes the raw API object into `updateRemoteUrl()`: [2](#0-1) 

Inside `updateRemoteUrl`, the guard conditions only compare:
1. whether the *protocol* of the current remote matches the protocol of the new URL, and
2. whether the *previously recorded* `gitHubRepository.cloneURL` still matches the current remote (i.e., the user hasn't manually changed it).

If both hold and the new URL differs from the current remote, the code calls `gitStore.setRemoteURL(...)` and rewrites `origin` to `apiRepo.clone_url` with no independent validation of the new URL's host/owner: [3](#0-2) 

This is directly analogous to the reported bug: the check is applied to a proxy value (protocol equality, prior recorded URL) rather than to the actual value being written (the new API-supplied clone URL). `setRemoteURL` then calls `git remote set-url` unconditionally on whatever string is passed: [4](#0-3) 

`urlMatchesRemote`/`matchGitHubRepository` only compare hostname/owner/name structure of URLs — they do not consult any list of trusted GitHub endpoints beyond the account's own configured endpoint, and `matchGitHubRepository` resolves the *account* purely from the existing remote's hostname: [5](#0-4) 

The `apiRepo` comes from a network round-trip to the endpoint associated with the matched account (`API.fromAccount(account)`), so the exact value of `apiRepo.clone_url` depends entirely on what that endpoint's `/repos/{owner}/{name}` response contains — a value that is attacker-influenced if the endpoint is a GitHub Enterprise instance under attacker administrative control, or if the account/repo has been renamed/transferred/hijacked server-side. Existing guards (`getRepositoryType`'s "unsafe" ownership check, clone-time `isClonePathSensitive` sensitive-path check) protect the *filesystem path* of the repository, not the *remote URL string* rewritten post-hoc by this function; none of them re-validate `apiRepo.clone_url` before it's written into the user's `.git/config`.

### Impact Explanation
Since `setRemoteURL` directly executes `git remote set-url origin <url>` with no host allow-list, this silently changes where the user's *next fetch, pull, or push* goes — without any prompt, diff, or confirmation dialog. If the attacker can influence the value returned for `clone_url` on the account's associated API endpoint (e.g., a compromised or malicious GitHub Enterprise Server the user is authenticated against, or an API response tampered with in transit/by a compromised intermediary), subsequent operations against `origin` would silently target the attacker-controlled remote. This matches the "silent corruption of what the user commits or pushes" impact category — credentials scoped to that endpoint (via the askpass/credential trampoline) would also be sent to whatever host the config now points at.

### Likelihood Explanation
`repositoryWithRefreshedGitHubRepository` is invoked routinely — on repository selection, on adding a repository, and after publishing — meaning `updateRemoteUrl` runs frequently and without user awareness. The only preconditions are: the repository must already be associated with a GitHub repository record, the remote protocol must be unchanged, and the previously-known clone URL must still match — all easily satisfied in normal usage. The main limiting factor is that in the common case (github.com), the attacker would need to control the API response for that endpoint, which requires either a malicious/compromised GHES instance the user already trusts, or an in-path attacker against the API connection — this is a meaningful precondition but does not require local access, admin rights, or prior malware, and is consistent with the "attacker controls...a GitHub API object" allowed impact category.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that `apiRepo.clone_url` resolves to the same trusted endpoint/hostname the account is configured against (not just protocol equality), and surface the change to the user (e.g., a confirmation dialog showing old vs. new remote URL) rather than rewriting it silently. Consider also validating the URL scheme against an allow-list (`https`/`ssh`) to reject unexpected schemes.

### Proof of Concept
1. User adds/authenticates against a GitHub Enterprise Server endpoint that is later compromised (or is a MITM-capable proxy the user's traffic passes through) — precondition consistent with "attacker controls...a git remote/proxy response."
2. User has a repository in Desktop already associated with a `GitHubRepository` record whose `cloneURL` matches `origin`.
3. On next repository selection/refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` against that endpoint.
4. The compromised endpoint returns an API repository object with the same `owner/name` structure but a `clone_url` pointing to an attacker-controlled repo (protocol kept identical, e.g. `https`).
5. `updateRemoteUrl` finds `protocolsMatch === true`, `remoteUrlUnchanged === true` (based on last known good URL), and `urlsMatch === false`, so it calls `gitStore.setRemoteURL('origin', <attacker-controlled-url>)` — silently rewriting `.git/config` with no user confirmation.
6. The user's next `git push`/`git pull` (and any credentials issued via the askpass trampoline for that host) target the attacker-controlled remote.

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
