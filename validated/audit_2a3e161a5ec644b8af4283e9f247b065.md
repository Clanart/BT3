### Title
Unauthenticated OP_RETURN in `create_payout_txhandler` lets anyone forge `payout_payer_operator_xonly_pk` attribution via `SinglePlusAnyoneCanPay` malleability - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The payout transaction's operator-attribution data (the OP_RETURN pushing `operator_xonly_pk`) is not covered by the user's withdrawal signature, because that signature is required to use `TapSighashType::SinglePlusAnyoneCanPay`. This sighash type only commits to the single signed input and the output at the same index (index 0, the user payout output) — outputs 1 (anchor) and 2 (OP_RETURN) and any additional funding inputs are completely unconstrained. Any party holding a valid withdrawal signature (including the withdrawing user/attacker themselves) can build and broadcast their own payout transaction that reuses that signature but substitutes an arbitrary OP_RETURN naming any operator's `xonly_pk`, and fund the deficit from their own wallet.

### Finding Description
The claimed binding is: `withdrawals.payout_payer_operator_xonly_pk == xonly_pk of the party whose wallet actually funded the payout output`.

Code path:
- `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-203`) enforces `input_signature.sighash_type == TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) .
- `create_payout_txhandler` builds the payout tx with input 0 = withdrawal UTXO (`SpendPath::KeySpend`), output 0 = user payout, output 1 = anchor, output 2 = `op_return_txout(operator_xonly_pk)`, and sets the witness from the caller-supplied `user_sig` [2](#0-1) .
- `calculate_script_spend_sighash`/sighash computation treats `SinglePlusAnyoneCanPay` as using `Prevouts::One` (only the spent input) [3](#0-2) ; combined with BIP-341/BIP-118 semantics of `SIGHASH_SINGLE`, the signature covers only output index 0 and input index 0 — it says nothing about output 1, output 2, or any other inputs added by `fund_raw_transaction` in `Operator::withdraw` (`core/src/operator.rs:620-674`).
- On the verifier side, `update_finalized_payouts` extracts the operator identity purely from the OP_RETURN of whatever transaction actually confirms on-chain, with no check that the named operator's wallet paid anything: `op_return_output = get_first_op_return_output(...)`, then `operator_xonly_pk = ... XOnlyPublicKey::from_slice(bytes)` is written straight into `payout_payer_operator_xonly_pk` [4](#0-3) .
- `is_kickoff_malicious` only compares the DB-recorded `operator_xonly_pk` (from the forged OP_RETURN) against `kickoff_data.operator_xonly_pk` (the operator actually kicking off) — if they match, it's judged non-malicious, with no check that the named operator's wallet funded the payout [5](#0-4) .
- `PayoutCheckerTask::run_once` polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and automatically triggers `handle_finalized_payout` + kickoff/reimbursement whenever the DB attributes a payout to that operator's own key [6](#0-5) .

Exploit flow: the attacker (as the withdrawing user, who already possesses the `SinglePlusAnyoneCanPay` signature, or who intercepts it from a broadcast/mempool tx) constructs their own payout transaction: same input 0 + witness (same signed output 0), plus their own funding input(s) to cover the deficit, plus an OP_RETURN naming an arbitrary operator B's `xonly_pk` (public information, obtainable via the aggregator's operator-key RPCs). The attacker broadcasts this transaction directly to Bitcoin (no operator or aggregator interaction is required at all), winning the single-spend race for the withdrawal input. Once confirmed, `update_finalized_payouts` writes `payout_payer_operator_xonly_pk = B` even though B's wallet never funded anything. Operator B's own `PayoutCheckerTask` then autonomously initiates the kickoff/reimbursement flow and is legitimately reimbursed (per `is_kickoff_malicious`) from the deposit's move-to-vault UTXO, having fronted nothing.

Existing guards do not stop this: `SECP.verify_schnorr` in `Operator::withdraw` only proves the user authorized the signed input/output(0) pair, not who else funds or names themselves in the transaction; `is_kickoff_malicious` checks operator/kickoff self-consistency and blockhash commitment, not funding provenance; `verify_storage_proofs`/`SPV::verify` validate that the payout tx is really mined and matches Citrea's committed withdrawal, not who paid for it.

### Impact Explanation
This is Critical impact per the given taxonomy: "an operator reimbursed for a payout it never funded." Operator B receives a genuine reimbursement (BTC from the move-to-vault UTXO via the presigned kickoff/reimburse transaction graph) without having spent any of its own collateral/wallet funds on the user's payout. This directly harms bridge economics: the false attribution is entirely attacker-controlled (any public operator key can be named), repeatable across every withdrawal index and every operator, and requires no privileged access, key material, or cooperation from any operator or verifier. Since attribution is written to the `withdrawals` table and gates the automatic kickoff-triggering logic in `PayoutCheckerTask`, this is a systemic break of the fronting-attribution invariant across the whole payout/reimbursement subsystem.

### Likelihood Explanation
Preconditions are minimal and match the defined unprivileged attacker capability set exactly: the attacker can choose the withdrawal UTXO bytes, the sighash flag, the signature, and the OP_RETURN content, and can broadcast Bitcoin transactions and deposit/withdraw via the Citrea contract. No majority hashrate, no compromised keys, no TLS interception, no verifier/operator privileges are needed. The attacker only needs to win a standard single-input double-spend race in the mempool (achievable by fee-bumping), which is routine and does not require any protocol-level compromise. This is directly reproducible in the existing regtest-based integration test harness (`core/src/test/deposit_and_withdraw_e2e.rs`, `core/src/test/manual_reimbursement.rs`) which already exercises `generate_withdrawal_transaction_and_signature` + `create_payout_txhandler` + `update_finalized_payouts`.

### Recommendation
Do not rely on an unauthenticated OP_RETURN for fronting attribution. Options: (1) require the withdrawal signature to cover the OP_RETURN output (e.g., use `SIGHASH_ALL` semantics for a distinguished commitment output, or embed the operator commitment as part of what `SIGHASH_SINGLE` binds by putting it at the signed output index, or require an additional operator-signed commitment tied to the specific payout transaction), and/or (2) have `update_finalized_payouts`/`PayoutCheckerTask` additionally verify that the named operator's own wallet actually supplied one of the extra funding inputs (e.g., cross-check against the operator's known reimbursement address or a wallet-linked proof), rather than trusting the raw OP_RETURN bytes.

### Proof of Concept
`cargo test` plan (add under `core/src/test/`, e.g. extending `deposit_and_withdraw_e2e.rs`):
1. Run a normal deposit via `run_single_deposit`; register the resulting `move_to_vault_txid` with two operator identities A and B (`actors.get_operator_client_by_index(0)`, `..._by_index(1)`).
2. Generate a withdrawal UTXO and a `SinglePlusAnyoneCanPay` signature over `(withdrawal_utxo, output_txout)` using `generate_withdrawal_transaction_and_signature` (attacker/user controls this).
3. Instead of calling operator A's `withdraw` RPC, directly call `builder::transaction::create_payout_txhandler(input_utxo, output_txout, operator_B_xonly_pk, user_sig, network)` from the test to build a payout tx naming operator **B**, fund the deficit with a test-controlled wallet input (not A's, not B's), and broadcast it via `rpc`.
4. Mine blocks until finality; run the verifier's Citrea/withdrawal sync path (`update_citrea_deposit_and_withdrawals` + `update_finalized_payouts`) as in existing e2e flows.
5. Assert: `db.get_payout_info_from_move_txid(...)` returns `payout_payer_operator_xonly_pk == operator_B_xonly_pk` (the forged value) `while` asserting that operator B's wallet balance/UTXO set was never spent from for this payout (i.e., B never funded it) — demonstrating the binding `payout_payer_operator_xonly_pk == payer's actual wallet` is broken.
6. Optionally continue the flow and assert operator B's `PayoutCheckerTask`/`handle_finalized_payout` proceeds to kickoff and is not rejected by `is_kickoff_malicious`, confirming the downstream reimbursement path is reachable.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    async fn run_once(&mut self) -> Result<Self::Output, BridgeError> {
        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self
            .db
            .get_first_unhandled_payout_by_operator_xonly_pk(
                Some(&mut dbtx),
                self.operator.signer.xonly_public_key,
            )
            .await?;

        if unhandled_payout.is_none() {
            return Ok(false);
        }

        let (citrea_idx, move_to_vault_txid, payout_tx_blockhash) =
            unhandled_payout.expect("Must be Some");

        tracing::info!(
            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self
            .db
            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
                &mut dbtx,
                deposit_data.get_deposit_outpoint(),
                payout_tx_blockhash,
            )
            .await?;

        // fetch and save the LCP for if we get challenged and need to provide proof of payout later
        let (_, payout_block_height) = self
            .operator
            .db
            .get_block_info_from_hash(Some(&mut dbtx), payout_tx_blockhash)
            .await?
            .ok_or_eyre("Couldn't find payout blockhash in bitcoin sync")?;

        let _ = self
            .operator
            .citrea_client
            .fetch_validate_and_store_lcp(
                payout_block_height as u64,
                citrea_idx,
                &self.operator.db,
                Some(&mut dbtx),
                self.operator.config.protocol_paramset(),
            )
            .await?;

        #[cfg(feature = "automation")]
        self.operator.end_round(&mut dbtx).await?;

        self.db
            .mark_payout_handled(Some(&mut dbtx), citrea_idx, kickoff_txid)
            .await?;
