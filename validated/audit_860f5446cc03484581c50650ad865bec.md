### Title
Silent, unconfirmed rewrite of a repository's `origin` remote URL based on trusted GitHub API `clone_url` — enables silent push/fetch redirection - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` is invoked as part of the routine background refresh path `repositoryWithRefreshedGitHubRepository` [1](#0-0)  and automatically rewrites the local `origin` remote to whatever `clone_url` the GitHub API returns for the tracked repository, with no user prompt, confirmation dialog, or notification. This mirrors the core broken invariant of the original report: a value is fetched from a source the app does not fully control at the moment of use (here, `apiRepo.clone_url` from the API) and is trusted to silently change security-relevant behavior (the destination of `git push`/`git fetch`), with no user-facing safeguard beyond a same-hostname/same-protocol heuristic.

### Finding Description
`repositoryWithRefreshedGitHubRepository` looks up the tracked repo by owner/name derived from the *current* local remote URL via `matchGitHubRepository`, then calls `api.fetchRepository(owner, name)` [2](#0-1) . Whatever `IAPIFullRepository` object is returned is passed straight into `updateRemoteUrl`: [3](#0-2) 

The only checks performed before silently calling `gitStore.setRemoteURL(...)` are:
- the new URL's protocol matches the old one (`protocolsMatch`),
- the *old* remote URL still matches the previously cached `gitHubRepository.cloneURL` (`remoteUrlUnchanged`, i.e. the user hasn't manually edited it),
- the new URL differs from the current remote (`!urlsMatch`).

Crucially, `urlMatchesRemote`/`urlsMatch` only compare `hostname`, `owner`, and `name` extracted via regex (`parseRemote`) [4](#0-3) . They do **not** verify that the "owner" identity has any relationship to the previously known owner beyond string equality/inequality — any repository under the same hostname is accepted as a valid redirect target. Compare this to the explicit, user-initiated path for changing a remote URL in Repository Settings, which requires the user to type/confirm the change themselves [5](#0-4) . The automatic path bypasses that user gate entirely.

Because the API lookup is keyed by owner/name (not a stable repository ID) and the GitHub API is trusted to have followed a rename/transfer legitimately, any change in the API's `clone_url` for that owner/name — whether from a legitimate rename, a repository transfer to a different account, or a malicious/compromised GitHub Enterprise API endpoint the user has added as an account — is silently applied to the user's local git configuration.

### Impact Explanation
If `apiRepo.clone_url` points to an attacker-controlled repository (same hostname, different owner/name — e.g. following a malicious repo transfer performed by a repo owner/admin, or returned by a compromised/malicious GitHub Enterprise server the victim has configured as an account), Desktop will silently repoint `origin` to that repository. Consequences:
- **Silent corruption of what the user pushes**: the next `git push` (`app/src/lib/git/push.ts`) sends the user's commits to the new, attacker-chosen remote instead of the repository the user believes they are working with, potentially leaking private source code to a different owner.
- **Silent corruption of what the user fetches/pulls**: subsequent fetches will pull history/refs from the attacker-controlled repository into the user's local clone without any indication the remote changed.
- No toast, dialog, or log visible to the end user surfaces this change; it is buried in a background refresh routine.

This matches the requested valid-impact class: "the attacker controls ... a GitHub API object ... and the result is ... silent corruption of what the user commits or pushes."

### Likelihood Explanation
The mechanism triggers automatically as part of normal background repository refresh (`repositoryWithRefreshedGitHubRepository`), requiring no unusual user action — it fires whenever the API's `clone_url` for the tracked owner/name differs from the current remote and the remote hasn't been manually customized. The main constraint is that the attacker must be able to make the GitHub API endpoint (github.com or a configured GitHub Enterprise Server) return a different `clone_url` for the repository the user is tracking — e.g. via a repository transfer performed by any actor with admin rights on that specific repo, or via a malicious/compromised Enterprise API endpoint. This does not require local/physical access, leaked credentials, or social engineering of the victim beyond their pre-existing use of Desktop against the affected repo/endpoint, but does depend on write/admin capability over the tracked GitHub repository or control of the API endpoint, which somewhat bounds severity to Medium — analogous to the original Turbo report's "malicious governance" contingency.

### Recommendation
- Require explicit user confirmation (a dialog, similar to how manual remote URL edits work in Repository Settings) before automatically applying a `clone_url` change discovered via API refresh.
- Track and compare a stable, unforgeable repository identifier (the numeric GitHub repository `id`, which persists across renames/transfers) rather than relying solely on owner/name string matching, and only offer the auto-redirect when that ID matches what was last recorded.
- Log/surface a visible notification whenever the local remote URL is changed automatically so users can detect and revert unexpected redirections.

### Proof of Concept
1. Victim clones `https://github.com/legit-owner/legit-repo` in GitHub Desktop; `gitHubRepository.cloneURL` is cached as this URL.
2. An actor with admin rights on `legit-repo` (or a compromised/malicious GitHub Enterprise Server endpoint the victim has added) causes the API's `repos/legit-owner/legit-repo` response to report `clone_url: https://github.com/attacker-owner/legit-repo` (e.g., via a genuine repository transfer, or a manipulated API response from a malicious Enterprise instance).
3. On the next background refresh, `repositoryWithRefreshedGitHubRepository` fetches this API object and calls `updateRemoteUrl` [6](#0-5) .
4. Because protocol matches, the old remote still matches the previously cached `cloneURL`, and the new URL differs, `gitStore.setRemoteURL('origin', 'https://github.com/attacker-owner/legit-repo')` executes silently [7](#0-6) .
5. The victim, unaware of the change, runs "Push" from the UI; `push.ts` pushes commits to `remote.url` — now `attacker-owner/legit-repo` — without any warning [8](#0-7) .

Note: I was unable to fully verify (due to index limits) whether any UI-level toast/banner exists elsewhere in the codebase that surfaces remote-URL auto-changes to the user; my search of `repositoryWithRefreshedGitHubRepository`'s callers and the `updateRemoteUrl` module did not surface one, but a Devin session with full repo access could confirm this exhaustively before implementing the fix.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
