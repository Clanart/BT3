### Title
OP_RETURN data output omitted from fee/weight calculation, causing underpriced transactions that may never confirm - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a `transfer()` whose success is never checked, so funds may not actually arrive at the vault. The Serai analog lives in `SignableTransaction::new`: when an OP_RETURN `data` output is requested, its weight is never included in `calculate_weight_vbytes`, so `needed_fee` (and the change-affordability check) are computed against a transaction that is smaller than the one actually built and signed. The resulting transaction pays a lower fee rate than the caller requested, meaning the broadcast transaction — carrying real payments — can be evicted from mempools or left unconfirmed, so the intended recipient never receives the funds even though the wallet produced a valid signed TX.

### Finding Description
`SignableTransaction::new` accepts an optional `data` payload which is appended as a zero-value OP_RETURN output (up to 80 bytes) at `send.rs:194-202`. However, the fee calculation calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204, and `calculate_weight_vbytes` builds its weight-estimation transaction only from `payments` plus the optional `change` output (lines 85-99) — the OP_RETURN output is never added. The same omission occurs in the change branch at lines 225-227 (`fee_with_change` is also computed without the data output).

An OP_RETURN output carrying 80 bytes of data contributes roughly 8 (value) + ~2 (script length) + 82 (push opcode + data) ≈ 92 weight-bearing bytes — about 92 vbytes entirely missing from the estimate. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` undercounts the true virtual size.
- The change-creation check `input_sat.checked_sub(payment_sat + fee_with_change)` at line 228 uses the undercounted `fee_with_change`, so a change output may be emitted where, at the true size, the remainder would fall below `DUST` or below zero-margin affordability.
- The signed transaction's actual fee rate is `needed_fee / actual_vsize`, strictly less than `fee_per_vbyte` requested — by up to ~10-20% for small transactions.

The only floor is the `TooLowFee` check against `DEFAULT_MIN_RELAY_TX_FEE` (line 211), which is also computed on the understated `vbytes`. A caller requesting e.g. exactly minimum relay fee gets a TX whose real feerate dips below it for the omitted bytes, risking rejection at broadcast.

### Impact Explanation
The wallet produces and the threshold group signs a transaction whose true fee rate is lower than intended. For transactions near the relay/confirmation margin — precisely the ones where an accurate `fee_per_vbyte` matters — the TX can fail initial relay (if it slips under `DEFAULT_MIN_RELAY_TX_FEE` in real terms) or linger/evict from mempools, so the payee never receives funds despite a fully "successful" sign-and-broadcast flow. This is the direct analog of "transfer performed but vault doesn't receive the money": the send path silently produces an ineffective transfer. Additionally, change-amount accounting is computed against the wrong fee, perturbing UTXO change bookkeeping.

### Likelihood Explanation
Reachability is via public inputs: `data` flows into `SignableTransaction::new` from transaction data an unprivileged party causes to be processed (Bitcoin deposits/outputs carrying instruction data are fed through this path). Any `data` in `1..=80` bytes triggers the underestimation; larger payloads worsen it. The bug is deterministic whenever `data.is_some()`.

### Recommendation
Include the OP_RETURN output in the weight-estimation transaction. Either pass the serialized `data` length into `calculate_weight_vbytes` (e.g., an extra `Option<&PushBytesBuf>`/script argument handled like `change`), or build the estimator directly from the final `tx_outs` vector rather than reconstructing outputs from `payments`/`change`, eliminating the divergence between the estimated and actual transaction entirely.

A transaction constructed as `SignableTransaction::new(inputs, &payments, change, Some(vec![0; 80]), FEE)` yields `needed_fee` computed on a vsize ~90 bytes smaller than the real signed transaction, so `tx.fee() / tx.vsize() < FEE`. The existing test at `networks/bitcoin/tests/wallet.rs:269` (`needed_fee == vsize * FEE`) only passes because it exercises a transaction with `data: None`; a variant with `Some(vec![0; 80])` would expose the discrepancy.
