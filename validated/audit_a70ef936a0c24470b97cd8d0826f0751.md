### Title
Unrecovered Go type-assertion panic in CW→ERC pointer registration lets any user crash block processing by deploying a malicious CW20/CW721/CW1155 contract - (File: precompiles/pointer/pointer.go)

### Summary
The `pointer` precompile's `AddCW20`, `AddCW721`, and `AddCW1155` executors query a target CosmWasm contract's `contract_info` and unconditionally type-assert the JSON fields `name` and `symbol` to `string` with the unchecked, panicking form `formattedRes["name"].(string)` / `formattedRes["symbol"].(string)`, instead of the two-value `v, ok := formattedRes["name"].(string)` form. Since the JSON response comes from an arbitrary CosmWasm contract that any unprivileged user can deploy, the contract can trivially return a non-string `name`/`symbol` (a number, `null`, object, or array), causing a Go runtime `panic: interface conversion: interface {} is not string`, in the same class as CVE-2019-6467: a programming error where an ordinarily-benign feature overlap (arbitrary contract response content ingested by a privileged code path with an unchecked assumption) triggers an unhandled assertion/panic in query/execution processing.

### Finding Description
`AddCW721` (and the CW20/CW1155 analogs) build a pointer contract for an arbitrary CosmWasm address supplied by the caller: [1](#0-0) 

The relevant unchecked assertions are: [2](#0-1) 

`p.wasmdKeeper.QuerySmartSafe`/`QuerySmart` executes the target contract's own `contract_info` query handler and returns whatever JSON that contract emits — this content is entirely attacker-controlled because the "contract" is any CosmWasm contract the caller (or anyone) has deployed. The code assumes `name` and `symbol` are always JSON strings and performs a single-value type assertion, which panics if the field is missing type-wise (e.g., serialized as a number, boolean, `null`, nested object, or array). This same unsafe pattern is repeated in every historical/legacy version of the pointer precompile (`precompiles/pointer/legacy/v552` through `v67`) and in the analogous `AddCW20`/`AddCW1155` functions, so this is not a one-off but a systemic pattern across the pointer registration surface: [3](#0-2) 

The `Keeper.UpsertERCPointer` upgrade path (used to refresh/upgrade pointer bytecode, also reachable from user-triggered pointer creation flows) similarly `panic(err)` on ABI packing failures: [4](#0-3) 

I was not able to confirm, within the scope of the available index, whether the outer precompile dispatch loop or EVM interpreter wraps native-precompile `Run`/`RunAndCalculateGas` calls with a `recover()` that converts an arbitrary Go panic into an EVM revert. If such a top-level `recover()` exists and correctly converts this panic into a reverted transaction, the practical impact is limited to a failed/reverted transaction (denial-of-service against the caller only, not the node), which would fall outside the High/Critical scope required by the rules. If no such `recover()` wraps this specific call path, an unhandled panic during `DeliverTx`/`ProcessProposal`/`CheckTx` processing on a block containing such a transaction would crash the node process handling it, which — if that happens deterministically across validators — would constitute a validator halt/liveness failure reachable by a single unprivileged transaction sender.

### Impact Explanation
If the panic is not recovered before it escapes into the ABCI/consensus critical path, any single transaction sender can:
1. Deploy a trivial CosmWasm contract whose `contract_info` (or an equivalent minter/marketing query used elsewhere) returns `{"name": 123, "symbol": {}}` instead of strings.
2. Call `RegisterPointer`/the pointer precompile's `AddCW20`/`AddCW721`/`AddCW1155` method against that contract (via EVM tx or the `seid tx evm register-cw-pointer` CLI, which ultimately hits the same precompile path).
3. Trigger an unhandled type-assertion panic during block execution, which — if unrecovered by the caller (EVM interpreter / precompile dispatcher / baseapp) — crashes every validator/full node that processes that transaction, producing a chain-wide halt (a "crash of default-configuration RPC/consensus nodes" per the validation criteria).

### Likelihood Explanation
The trigger requires only permissionless contract deployment (already possible for any account) and a single follow-up transaction invoking pointer registration against that contract — no elevated privileges, no validator collusion, and no complex state setup. This is a low-effort, high-determinism trigger if the panic path is unrecovered.

### Recommendation
- Replace every unchecked type assertion of contract-supplied JSON fields (`formattedRes["name"].(string)`, `formattedRes["symbol"].(string)`, and any other `.(string)`/`.(float64)` assertions on `contract_info`/similar wasm query responses) across `precompiles/pointer/pointer.go` and all `precompiles/pointer/legacy/*/pointer.go` variants with the two-value, error-returning form (`v, ok := formattedRes["name"].(string); if !ok { return nil, 0, fmt.Errorf(...) }`).
- Audit the EVM/precompile execution path to confirm a `recover()` boundary exists around every native precompile invocation so that any residual panics degrade to a reverted transaction rather than a node crash, and add one if missing.
- Add fuzz/unit tests that register pointers against malicious CW20/721/1155 contracts returning malformed `contract_info` JSON (wrong types, missing fields, deeply nested structures) to ensure graceful error handling instead of panics.

### Proof of Concept
1. Deploy a CosmWasm contract whose `contract_info` query handler returns `{"name": 123, "symbol": null}` (valid JSON, invalid types) instead of the expected `ContractInfoResponse{name: String, symbol: String}`.
2. From any account, submit an EVM transaction calling the `pointer` precompile's `addCW721`/`addCW20`/`addCW1155` method with that contract's Sei address as the argument (equivalently, run `seid tx evm register-cw-pointer ERC721 <malicious_cw_address>`).
3. Observe that `formattedRes["name"].(string)` panics with `interface conversion: interface {} is not string` inside `precompiles/pointer/pointer.go`'s `AddCW721`, since `formattedRes["name"]` is a `float64`/`nil`, not a `string`.
4. Confirm whether this panic propagates past the EVM/ante pipeline into the node process (crash) or is caught and turned into a transaction revert — this determines whether the finding rises to node-crash severity, which I could not fully verify from the indexed code.
