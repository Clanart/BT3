### Title
Deterministic per-transaction coinbase address sweeps its *entire* usei/wei balance to the fee collector at EndBlock, permanently destroying any funds sent to it directly - (File: x/evm/keeper/abci.go)

### Summary
Each EVM transaction is assigned a deterministic, precomputed "coinbase" account (`state.GetCoinbaseAddress(idx)`, derived only from tx index) that temporarily collects that transaction's fee surplus. At `EndBlock`, the keeper indiscriminately sweeps **all** spendable `usei` and `wei` currently sitting at that address to the real fee collector — not just the amount the fee logic actually credited. This mirrors the Shelter bug pattern: a helper/escrow account whose "activation" (fee credit tracked internally) is conflated with its raw on-chain balance, so any additional value deposited into it (accidental or malicious) is swept away with the tracked amount and is irrecoverably lost to the depositor, exactly like Shelter's `donate()` funds being swept back on `exitShelter` regardless of the internally tracked `amountInShelter`.

### Finding Description
`state.GetCoinbaseAddress(idx)` computes a fully deterministic Sei/EVM address from only the transaction index within the block (`crypto.CreateAddress(seed, nonce)` pattern seen for the fixed coinbase, and per-tx variant keyed by `idx`) [1](#0-0) . Because it is deterministic and requires no privilege, any unprivileged actor can predict a future or even the currently-executing transaction's coinbase address and send `usei` (via a plain bank `MsgSend`) or wei to it before `EndBlock` runs for that block.

At `EndBlock`, the module reads **the account's full current balance**, not the fee-surplus amount that was actually credited during tx execution, and unconditionally transfers it to the real coinbase/fee collector: [2](#0-1) 

```
idx := int(deferredInfo.TxIndex)
coinbaseAddress := state.GetCoinbaseAddress(idx)
useiBalance := k.BankKeeper().GetBalance(ctx, coinbaseAddress, denom).Amount
lockedUseiBalance := k.BankKeeper().LockedCoins(ctx, coinbaseAddress).AmountOf(denom)
balance := useiBalance.Sub(lockedUseiBalance)
weiBalance := k.BankKeeper().GetWeiBalance(ctx, coinbaseAddress)
if !balance.IsZero() || !weiBalance.IsZero() {
    if err := k.BankKeeper().SendCoinsAndWei(ctx, coinbaseAddress, coinbase, balance, weiBalance); err != nil {
        ...
    }
}
```

There is no bookkeeping analogous to Shelter's `amountInShelter` that would let the sweep distinguish "the fee surplus this tx generated" from "anything else that happens to be sitting in this address." Just as Shelter's `exitShelter()` transferred the *entire* LP token balance (tracked + donated) back to `ConvexStakingWrapper` with no way to recover the donated portion, `EndBlock` transfers the *entire* balance of the deterministic coinbase address (fee surplus + any externally sent funds) to the fee collector, with no path for the original sender of those extra funds to reclaim them. The address itself is never registered as untouchable/quarantined against direct incoming transfers — the send is a normal bank transfer that succeeds without any check that the recipient is this reserved system address.

### Impact Explanation
Any account that sends `usei` (or credits wei) directly to a `state.GetCoinbaseAddress(idx)` address — whether by mistake, by following a leaked/derived address, or deliberately — has those funds unconditionally and permanently redirected to the fee collector at the next `EndBlock`, with no mechanism to reclaim them. This is a direct fund-loss condition for the sender and an inflation-of-fee-collector-revenue condition, matching the accepted-medium-severity class in the source report (irrecoverable "donated" funds swept away on deactivation/cleanup of a system-owned holding account). Unlike the Shelter bug, the sender here isn't "donating" intentionally to support a mechanism, but the loss vector — collateral damage from a system sweep that fails to segregate "legitimately owed" balance from "everything else present" — is structurally identical.

### Likelihood Explanation
The coinbase address is deterministic and derivable off-chain by anyone (`crypto.CreateAddress` from public seed/index), and sending tokens to any Sei address is an ordinary unprivileged `MsgSend`/EVM transfer available to any user. No special permission, precompile access, or validator collusion is required — only knowledge of the deterministic derivation formula, which is public via test assertions in the repo (`TestGetCoinbaseAddress`). This makes the trigger trivially reachable, though the loss is limited to whatever the user chooses to send to that specific address, and typically only affects a user who mistakenly or deliberately targets this reserved address.

### Recommendation
Segregate the fee-surplus tracking from the raw account balance: instead of computing the swept amount as "current full balance minus locked coins," record and sweep exactly the surplus amount actually credited during `AddBalance`/fee-crediting for that tx index (already available via `deferredInfo.Surplus`/journal), and either reject/quarantine (e.g., disallow `SendCoins` to the reserved coinbase address range) or explicitly refund any excess balance back to its original sender before/instead of forwarding it to the fee collector. This mirrors the Shelter fix recommendation: only sweep the tracked/intended amount, and provide a recovery path for anything beyond it.

### Proof of Concept
1. Compute `coinbaseAddr = GetCoinbaseAddress(idx)` for a target tx index in an upcoming block (deterministic, derivable by any observer using the same formula as `x/evm/keeper/coinbase.go` / `state.GetCoinbaseAddress`).
2. As an unprivileged user, submit a plain `MsgSend` transferring `usei` to `coinbaseAddr` before or during the block whose `EndBlock` will process tx index `idx`.
3. When `EndBlock` executes, it computes `balance := useiBalance.Sub(lockedUseiBalance)` for `coinbaseAddr`, which now includes the attacker/victim's transferred funds in addition to (or instead of) any actual fee surplus, and unconditionally forwards the full amount via `SendCoinsAndWei` to the fee collector.
4. The sender's funds are now held by the fee collector module account with no on-chain trace distinguishing them from legitimate fee surplus, and no recovery mechanism exists for the original sender. [3](#0-2) [4](#0-3) [5](#0-4)

const CoinbaseSeedAddress = "0000000000000000000000000000000000000001"
const CoinbaseNonce = 42

func (k *Keeper) GetFeeCollectorAddress(ctx sdk.Context) (common.Address, error) {
	k.cachedFeeCollectorAddressMtx.RLock()
	cache := k.cachedFeeCollectorAddress
	k.cachedFeeCollectorAddressMtx.RUnlock()
	if cache != nil {
		return *cache, nil
	}
	moduleAddr := k.accountKeeper.GetModuleAddress(authtypes.FeeCollectorName)
	// we don't want to charge gas for this query, since it could cause non-determinism
	evmAddr, ok := k.GetEVMAddress(ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx)), moduleAddr)
	if !ok {
		return common.Address{}, errors.New("fee collector's EVM address not found")
	}
	k.cachedFeeCollectorAddressMtx.Lock()
	// ok to write multiple times since it's idempotent
	k.cachedFeeCollectorAddress = &evmAddr
	k.cachedFeeCollectorAddressMtx.Unlock()
	return evmAddr, nil
}

func GetCoinbaseAddress() common.Address {
	return crypto.CreateAddress(common.HexToAddress(CoinbaseSeedAddress), CoinbaseNonce)
}
