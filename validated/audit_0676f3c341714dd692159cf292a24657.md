Confirmed vulnerability: the `bridge_circuit` function's on-chain proof verification (`circuits-lib/src/bridge_circuit/mod.rs`) and the underlying `verify_storage_proofs` (`circuits-lib/src/bridge_circuit/storage_proof.rs`) only bind the withdrawal outpoint's **input** reference (`txid`/`vout`) between the Citrea contract's stored withdrawal record and the actual payout transaction — they never verify the payout transaction's **output amount or destination script_pubkey** against anything committed on Citrea. This is a structural analog of the "gas fee not shown" bug class: a value that should be bound to what the user actually receives is left unchecked, letting the party constructing the transaction (the operator) get reimbursed for a payout that doesn't match what was fronted.

### Title
Bridge circuit never verifies the payout transaction's output amount/script_pubkey against the Citrea withdrawal request, allowing an operator to be reimbursed without fronting the correct amount to the user - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
The `bridge_circuit` function proves that an operator's payout (fronting) transaction spends the correct withdrawal UTXO (matching `txid`/`vout` from the Citrea contract's storage), but it never asserts that the transaction's *output* — the amount and script_pubkey actually paid to the user — matches the amount/address the user requested in their withdrawal.

### Finding Description
In `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs`), after `verify_storage_proofs` returns `(user_wd_outpoint, vout, move_txid)`, the circuit only checks: [1](#0-0) 
i.e., that `input.payout_spv.transaction.input[payout_input_index].previous_output` matches the withdrawal outpoint recorded on Citrea. No assertion anywhere in this function (or in `verify_storage_proofs`, `circuits-lib/src/bridge_circuit/storage_proof.rs:44-133`) checks `input.payout_spv.transaction.output[...]` against a requested amount or script_pubkey.

`verify_storage_proofs` reads only three storage slots from the Citrea Bridge contract: the withdrawal UTXO (`utxo_storage_proof`), its vout (`vout_storage_proof`), and the deposit's move-txid (`deposit_storage_proof`): [2](#0-1) 
There is no storage slot or check for the payout output amount/destination in this circuit code path.

Contrast this with the off-chain, unprivileged/attacker-controllable RPC path: `Operator::withdraw` (`core/src/operator.rs:560-627`) does validate the output amount there via `is_profitable` and signature checks against the *user's* signed `output_amount`/`output_script_pubkey`: [3](#0-2) 
and the signature verification binds the operator's payout tx to the user-signed amount: [4](#0-3) 
However, these checks are enforced only by the *operator's own RPC service logic* at the time it voluntarily calls `withdraw`/constructs the payout — they are not re-verified anywhere in the on-chain-provable `bridge_circuit` that ultimately gates reimbursement eligibility (via kickoff → assert → disprove, documented in `docs/bridge-circuit.md:47-49`: "Checks that the data on the contract matches with the payout transaction data" — but this claim is not actually backed by any output-amount/script check in the code). Once an operator has fronted *any* transaction spending the correct withdrawal outpoint (regardless of amount/destination paid), the circuit's proof succeeds, and the reimbursement chain (kickoff/assert/disprove) treats the claim as valid because `is_kickoff_malicious` in `core/src/verifier.rs:1859-1915` only checks the operator xonly pubkey and payout blockhash commitment — not the output amount: [5](#0-4) 

This breaks the binding: **operator reimbursed for a payout it never fronted** — the amount reimbursed from the bridge (via kickoff/reimburse-connector) is decoupled from the amount actually delivered to the withdrawing user.

### Impact Explanation
Critical — this matches the listed Critical impact "an operator reimbursed for a payout it never funded." An operator can spend the withdrawal UTXO with an output paying a dust amount (or to their own address) instead of the amount the user is owed, and still obtain a valid bridge-circuit proof and subsequent full reimbursement from bridge funds, since neither the circuit's storage-proof check nor the disprove path's `is_kickoff_malicious` validate the payout output amount/destination against the withdrawal request.

### Likelihood Explanation
An operator is a privileged role in this system's threat model (the ruleset excludes findings that "require a verifier, operator, watchtower..." role) — however, this analysis was driven purely by the operator's ability to construct the payout transaction differently from what off-chain RPC logic checks (`Operator::withdraw`), while the on-chain-provable circuit path that governs actual fund release provides no cryptographic enforcement of the amount/destination binding at all. Since the reimbursement path is provable and challengeable purely by machine-checkable rules (SPV + storage proof + txid/vout match), and none of those rules bind the output, any operator bypassing the cooperative RPC flow (e.g., by broadcasting a self-constructed payout transaction directly to Bitcoin instead of going through `Operator::withdraw`) can exploit this without needing any additional compromise.

### Recommendation
Add an assertion in `bridge_circuit` (or `verify_storage_proofs`) that the payout transaction's output amount and script_pubkey (`input.payout_spv.transaction.output[...]`) match values proven via an additional Citrea storage proof of the withdrawal request's expected amount/destination (or otherwise cryptographically bind the payout's output to the user-signed withdrawal parameters), so reimbursement can only be claimed when the correct amount was actually paid to the correct destination.

### Proof of Concept
1. A withdrawal `withdrawal_utxo` (owned/controllable by the withdrawing user) is registered in the Citrea Bridge contract with intended `output_amount`/`output_script_pubkey`.
2. Instead of following the cooperative `Operator::withdraw` RPC flow (which enforces `is_profitable` and signature checks against the user-signed amount), the operator directly constructs and broadcasts a payout transaction spending `withdrawal_utxo` as input, but sends the output to their own address (or a dust amount) rather than the amount/address the user requested.
3. The operator then proceeds through kickoff → generates a `bridge_circuit` proof using this self-crafted payout transaction as `payout_spv.transaction`.
4. `bridge_circuit` succeeds because it only checks `input[payout_input_index].previous_output.txid/vout == user_wd_outpoint/vout` (`circuits-lib/src/bridge_circuit/mod.rs:190-204`); it never inspects the transaction's outputs.
5. `is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) also does not check output amount, only the operator xonly pubkey and payout blockhash commitment, so verifiers do not flag this kickoff as malicious.
6. The operator obtains full reimbursement from the bridge despite never fronting the withdrawal amount to the user.
