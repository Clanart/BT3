## Finding Description

The claimed binding is: `count(fully-signed N-of-N optimistic payout transactions for deposit_id d) == 1`.

Tracing `Aggregator::optimistic_payout` in `core/src/rpc/aggregator.rs` (lines 1010–1230), the only guard against a double payout is the single read `self.rpc.is_utxo_spent(&input_outpoint)` at line 1033-1038, which queries the live Bitcoin UTXO set via RPC — it is not a database lock, mutex, or transactional check. Between this read and the point where the aggregator collects N-of-N partial signatures from verifiers (lines 1129–1229) and produces `final_sig` / the signed `RawSignedTx`, there is no re-check of spend status, no per-`deposit_id` mutex, and no unique-constraint write recorded anywhere in this function. Two concurrent gRPC calls with identical `deposit_id`, `input_outpoint = U`, and `move_txid = M` will both pass `is_utxo_spent`, both call `create_optimistic_payout_txhandler` against the same `withdrawal_utxo` and `move_txid`, both call out to verifiers via `optimistic_payout_sign`, and both can independently complete MuSig2 nonce aggregation and partial-signature aggregation to produce two distinct, fully valid, N-of-N-signed transactions spending the same `M:DepositInMove` output.

I could not fully verify whether the verifier-side `optimistic_payout_sign` handler in `core/src/rpc/verifier.rs` or the deposit/withdrawal database layer (`get_move_to_vault_txid_from_citrea_deposit`, `get_withdrawal_utxo_from_citrea_withdrawal`) enforces any additional serialization, session uniqueness, or "already signing this deposit" guard before releasing a partial signature — this would need inspection of the verifier's nonce/session state machine and the DB schema for withdrawal state transitions, which I was not able to complete before running out of tool budget. If such a guard exists (e.g., a per-`deposit_id` signing session lock or a DB row that is atomically marked "payout in progress" before nonces are handed out), the race would not produce two independently completed N-of-N signatures. Based on what is confirmed in `aggregator.rs`, the aggregator's own code path shows no such guard.

## Impact Explanation

If the race succeeds as described, the aggregator produces two independently valid N-of-N-signed transactions for a single Citrea withdrawal authorization, matching the "N-of-N partial signatures for an unauthorised spend" Critical category — the second signature set is not backed by any second withdrawal event on Citrea. Only one transaction can confirm on Bitcoin (double-spend of the same UTXO), so custody leaving the vault is bounded to the single fronted amount; the direct on-chain value-movement invariant holds. The residual harm is a signing-authority violation: the bridge attests validity to two conflicting spends instead of one, which could be leveraged for downstream issues (e.g., mempool/relay races, RBF/fee manipulation between the two variants, or operator/verifier confusion in reimbursement bookkeeping) even though direct fund loss is not demonstrated.

## Likelihood Explanation

Preconditions are attacker-triggerable: any address holding the withdrawal UTXO and its private key (the withdrawing user, who is within the defined attacker capability set) can submit two concurrent `OptimisticWithdrawParams` requests. No key compromise, TLS interception, or privileged role is needed — this uses only the public gRPC port and standard user-level withdraw capability. The race window depends on the latency between the `is_utxo_spent` check and completion of the N-of-N MuSig2 round trip to all verifiers, which is a network round-trip window (likely tens to hundreds of ms), making it plausible for a motivated attacker with good network positioning relative to the aggregator/verifiers. However, without confirming the verifier-side session/lock behavior, I cannot state with certainty that the race fully succeeds end-to-end in this codebase as deployed — this is the key unresolved uncertainty.

## Recommendation

Add a per-`deposit_id`/`withdrawal_utxo` mutual-exclusion mechanism in `Aggregator::optimistic_payout` before initiating nonce collection — e.g., an atomic DB row (or in-memory lock keyed by `deposit_id`) that is set when a payout attempt begins and checked-and-rejected on concurrent entry, released only on completion or failure. Additionally, re-check `is_utxo_spent` immediately before releasing the final aggregated signature, and have verifiers refuse to produce a second partial signature for a `deposit_id` that already has an in-flight or completed signing session.
