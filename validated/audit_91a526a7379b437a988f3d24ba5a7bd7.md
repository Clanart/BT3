### Title
Webhook `shop_domain` is not covered by the HMAC, allowing an attacker to forge webhooks attributed to a different shop - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb](lib/shopify_app/controller_concerns/webhook_verification.rb))

### Summary
`ShopifyApp::WebhookVerification` (and the underlying `ShopifyApp::PayloadVerification`) authenticate an incoming webhook by computing an HMAC over the raw request body only, using a single app-wide secret shared by every installed shop. The `shop_domain` value that consuming code uses to attribute the payload to a specific merchant is read straight from an unsigned request header and is never included in the HMAC computation. This is the same class of flaw as the reported issue: a value that determines *how the signed payload is interpreted/attributed* (`nlrType` in the original report, `shop_domain` here) is not part of the data that is cryptographically bound together, enabling a type/tenant-confusion attack.

### Finding Description
`hmac_valid?` computes and compares the HMAC exclusively over `request.raw_post`: [1](#0-0) 

`WebhookVerification#verify_request` calls `hmac_valid?(data)` with `data = request.raw_post`, and separately exposes `shop_domain`, which is read directly from the `X-Shopify-Shop-Domain` header — a value that is never part of the signed digest: [2](#0-1) 

Because the app's webhook secret is a single global secret (`ShopifyApp.configuration.secret`) shared across all shops that have installed the app, not a per-shop secret, any merchant that has installed the app can legitimately trigger a webhook for their own store (e.g. `products/update`) and obtain a valid `(raw_body, HMAC)` pair signed with that shared secret. The officially documented pattern for custom webhook controllers explicitly uses this unsigned `shop_domain` to route/attribute data to a shop: [3](#0-2) 

An attacker who controls one shop can capture the raw body + valid HMAC of a webhook fired from their own store, then resend that exact `(raw_body, HMAC)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `hmac_valid?` will still pass because it never examines the shop domain header, and the downstream job will be dispatched with `shop_domain: <victim shop>` and attacker-controlled `webhook` body content, exactly mirroring how an `nlrType` value could be swapped to route otherwise-valid signed data into the wrong validator/schema.

### Impact Explanation
Any consuming application built on the documented `ShopifyApp::WebhookVerification` pattern will process attacker-controlled webhook data as though it originated from a shop the attacker does not control, since `shop_domain` and `hmac` are independently trusted but never bound together. Depending on what the app's webhook job does with `shop_domain` (e.g. looking up/mutating per-shop records, updating billing state, triggering shop-scoped side effects), this enables cross-shop data injection or corruption using only a body/HMAC pair that the attacker legitimately obtained for their own shop.

### Likelihood Explanation
Exploitation requires only that the attacker (any merchant who has installed the app) can trigger at least one webhook event for their own store — a routine, unprivileged action available to every installer — and can then replay the HTTP request with a modified header. No secret, session token, or elevated privilege is required beyond having the app installed on any single shop.

### Recommendation
Bind `shop_domain` (and any other header-derived routing metadata) into the authenticated payload before verifying, e.g. by validating that the shop domain returned from Shopify's registry/session lookup matches the domain recorded for the session that issued the webhook, or by requiring the caller to pass shop identity through a channel that is itself covered by the HMAC (as Shopify's own webhook payloads typically embed shop identifiers in the JSON body, which should be cross-checked against the header value rather than trusting the header alone).

### Proof of Concept
1. App merchant A installs the app; app configures a single shared `ShopifyApp.configuration.secret` used for HMAC validation of all shops' webhooks.
2. Merchant A performs an action on their own store (e.g., updates a product) causing Shopify to send a `products/update` webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Merchant A intercepts/logs this legitimate request (e.g., via a debugging proxy they control since it's their own webhook traffic).
4. Merchant A resends an HTTP POST to the app's webhook endpoint with the identical body `B` and identical valid HMAC header, but replaces `X-Shopify-Shop-Domain` with victim shop B's domain.
5. `WebhookVerification#verify_request` (`lib/shopify_app/controller_concerns/webhook_verification.rb`) calls `hmac_valid?(request.raw_post)`, which passes because the body is unchanged and the secret is shared across shops.
6. The controller/job processes the payload using `shop_domain` read from the now-forged header, attributing attacker-controlled content to victim shop B.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
