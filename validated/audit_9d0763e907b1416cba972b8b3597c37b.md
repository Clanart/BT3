## Finding [1](#0-0) 

### Title
Recursive-Clone Path/Symlink-Collision Protection Explicitly Disabled (`GIT_CLONE_PROTECTION_ACTIVE=false`) - (File: app/src/lib/git/clone.ts)

### Summary
Every clone performed by Desktop unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment passed to `git clone --recursive`, unconditionally turning off Git's own built-in protection against maliciously-crafted repositories/submodules that try to make Git write files outside the intended clone directory (the class of bug fixed upstream by Git 2.45.1's clone-protection work for CVE‑2024‑32002/32004). This mirrors the original TokenMessaging bug's broken invariant: a safety mechanism that exists specifically to stop an untrusted, attacker-supplied object (there: `msg.sender`; here: a cloned/fetched repository) from causing an unintended, dangerous side effect is bypassed by explicit code, not merely missing by omission.

### Finding Description
`clone()` in [2](#0-1)  builds the environment for `git clone --recursive ... -- <url> <path>` and hard-codes:
```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```
`GIT_CLONE_PROTECTION_ACTIVE` is the internal flag Git itself toggles to enable stricter validation of submodule destination paths during recursive clones — the mechanism added to stop a crafted submodule (e.g., one whose name/path collides with `.git`, or that uses case-folding/Unicode-normalization/symlink tricks on case-insensitive filesystems such as macOS/Windows default filesystems) from causing Git to write files into the superproject's `.git` directory instead of the submodule's own working tree. Forcing this to `'false'` disables that check for every clone Desktop performs, for every remote URL a user opens via the `x-github-client://openrepo/...` deep link ( [3](#0-2) ), a "clone repository" action, or a `--cli-clone` argument ( [4](#0-3) ).

This is different from — and not compensated by — the other hardening already present in the same file: `isClonePathSensitive()` only checks the *top-level* destination directory against a fixed deny-list (home dir, `.ssh`, `.gnupg`, `.gitconfig`, etc.) ( [5](#0-4) ). It does nothing to validate paths derived from submodule entries *inside* the cloned repository during the `--recursive` step, which is exactly what `GIT_CLONE_PROTECTION_ACTIVE` is meant to police. Likewise, `resolveWithin()`/symlink guards used elsewhere for reading files ( [6](#0-5) ) are never applied to the recursive submodule checkout that `git clone --recursive` performs internally — that step happens entirely inside the `git` subprocess, governed only by Git's own protection, which Desktop has explicitly turned off.

### Impact Explanation
An attacker who controls a repository (or a fork/PR the user is asked to clone via a link, deep link, or GitHub API-provided clone URL) can include a submodule crafted to collide with the superproject's `.git` metadata directory. With Git's clone-time protection disabled, `git clone --recursive` invoked by Desktop can be tricked into writing attacker-controlled content (e.g., a hook script) into the `.git`/`.git/hooks` area of the checked-out repository rather than confined to the submodule's own path — i.e., file write outside the intended repository content boundary, with a path to arbitrary code execution the next time a Git hook fires (e.g., `post-checkout`, which Git itself may invoke immediately after the same clone completes). This satisfies the "attacker controls a cloned/fetched repository ... code execution / file write outside the repo" criterion.

### Likelihood Explanation
Every single clone Desktop performs — including ones triggered by a single click on an untrusted `x-github-client://openrepo/<url>` link or by opening a PR/fork suggested through the GitHub API/UI — goes through this code path with the protection disabled. No user interaction beyond the normal "clone this repo" action is required, and the environment variable is not conditioned on any user setting or on `allowFileProtocol`-style flags (unlike `protocol.file.allow=always`, which the codebase does gate). The only remaining defense is upstream Git's own general safety net (e.g., `core.protectNTFS`/HFS defaults still active outside the clone-specific flag), but the reason the `GIT_CLONE_PROTECTION_ACTIVE` gate exists at all is that those general defaults were previously shown to be insufficient for the recursive-submodule-clone scenario.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in [7](#0-6)  so Desktop relies on Git's built-in clone-time protection, and add a regression test cloning a repository containing a submodule whose path is engineered to collide with `.git`/`.git/hooks`, asserting the clone fails safely instead of writing outside the submodule boundary.

### Proof of Concept
1. Attacker publishes a public repository containing a `.gitmodules` entry whose submodule path is crafted (using case-folding on HFS+/APFS/NTFS or a path constructed to alias `.git`) to overlap with the superproject's `.git` directory once checked out.
2. Attacker shares a normal-looking clone/PR link, or the victim clicks an `x-github-client://openrepo/<attacker-url>` deep link handled by [8](#0-7) , causing Desktop to call `clone()`.
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` in [9](#0-8) , Git's recursive submodule step skips the collision check it would otherwise perform, allowing content from the malicious submodule to land in the superproject's `.git` metadata (e.g., `hooks/post-checkout`).
4. On the very next Git-triggered hook execution against that same repository (which Desktop itself invokes as part of normal operations), the attacker's script runs with the privileges of the Desktop process/user.

I could not verify from the available index whether there is an accompanying code comment or CI test explaining/justifying this override elsewhere in the repo (the file itself contains none, and I was not able to inspect the `changelog.json` "CVE" references in more detail before running out of tool calls) — if such a justification exists, it should be reviewed against the current Git version bundled with Desktop before treating this as unintentional.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
