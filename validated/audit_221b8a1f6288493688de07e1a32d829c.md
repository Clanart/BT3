## Analysis

The Cryptopunks report is fundamentally about **non-standard token behavior breaking an implicit ERC-standard assumption** in the protocol's transfer logic. The Hyperbridge local analog is in the Tron deployment of `IntentGatewayV2`, whose `withdraw()` function releases escrowed ERC-20 tokens using a raw low-level `call` and only checks that the call didn't revert — it never inspects the returned boolean.

### Title
Escrow release accepts non-reverting `transfer` failures as success, permanently burning user/solver funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron `IntentGatewayV2.withdraw()` internal function, tokens are transferred to the beneficiary via `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`, and only the call's `success` boolean (i.e., "did not revert") is checked — the ABI-decoded return value of `transfer` (`bool`) is discarded entirely. [1](#0-0) 

### Finding Description
Standard ERC-20 `transfer` reverts on failure, but some tokens (non-standard, "soft-fail" style ERC-20s, similar in spirit to how Cryptopunks silently deviates from the expected ERC-721 interface) return `false` instead of reverting when a transfer cannot be completed. Because the Tron gateway's `withdraw()` only checks `success` from the low-level `.call(...)` (which is `true` whenever the callee doesn't revert, regardless of what boolean it returns), a token that returns `false` on failure will be treated as a fully successful payout: [2](#0-1) 

Immediately after this unchecked transfer, the code unconditionally decrements internal escrow accounting `_orders[body.commitment][token] -= amount` and marks the order `_filled[body.commitment] = beneficiary`, then emits `EscrowReleased`/`EscrowRefunded`.

This contrasts with:
- the same-chain path in `IntentsBase._withdraw`, which correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, reverting on failed/non-standard transfers: [3](#0-2) 
- the main (non-Tron) EVM `IntentGatewayV2` cross-chain fill path, which uses balance-diff accounting (`balanceOf` before/after) to tolerate fee-on-transfer tokens safely: [4](#0-3) 

The Tron variant's `withdraw()` neither uses `SafeERC20` nor balance-diff verification — it trusts a bare `success` flag from a raw `.call`.

### Impact Explanation
Once a token's `transfer` call returns `false` without reverting (a real behavior class for several deployed ERC-20 tokens), the gateway:
1. Considers the escrow released to the beneficiary (decrements `_orders`, sets `_filled`, emits success events) even though the beneficiary received **zero tokens**.
2. Leaves the actual token balance stuck in the contract with no accounting path to recover it (the escrow slot has already been zeroed out), permanently locking/losing user or solver funds.

This is a direct loss-of-funds condition reachable by any user/solver interacting with such a token via the normal cross-chain settlement flow — no malicious relayer, prover, or admin is required; the flaw is purely in the destination-side accounting logic triggered by `onAccept`/`onGetResponse` after a legitimate proof/settlement message.

### Likelihood Explanation
The corrupted path is exercised on every `withdraw()` invocation for ERC-20 tokens (i.e., every cross-chain fill settlement, refund, or cancellation redemption on this Tron deployment). It is triggered purely by the properties of the escrowed token contract, not by any adversarial relayer/prover behavior, so any order that escrows a soft-failing ERC-20 will silently lose funds under normal operation.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` (and the equivalent pattern in `onAccept`'s `SweepDust` handling) with OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and validates the boolean return value (or accepts no-return-value tokens safely) and reverts on failure — consistent with the pattern already used in `IntentsBase.sol` and the fee-token payout logic later in the same file (`IDispatcher(host()).feeToken()` transfer also uses the same unchecked pattern and should be fixed identically).

### Proof of Concept
1. Deploy a malicious/non-standard ERC-20 token `T` whose `transfer(address,uint256)` returns `false` (instead of reverting) whenever an internal condition fails (e.g., a paused state, blacklist, or simply always returns `false` post some block).
2. User places a cross-chain order on the source chain escrowing `T` as input via `IntentGatewayV2.placeOrder` (Tron chain acting as source).
3. Solver fills the order on the destination chain, triggering the `RedeemEscrow` message back to the Tron source chain.
4. Hyperbridge relays the message; `onAccept` calls `withdraw(body, false)`.
5. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` succeeds (no revert) but `T.transfer` internally returns `false`.
6. `success == true` so no revert occurs; `_orders[commitment][token] -= amount` executes, `_filled[commitment]` is set, and `EscrowReleased` is emitted — even though the solver's beneficiary balance of `T` never increased.
7. The escrowed `T` tokens remain trapped in the `IntentGatewayV2` contract with no state left indicating they are still owed, resulting in permanent fund loss for the beneficiary.
