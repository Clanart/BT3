### Title
`VerifyBlame` swaps accuser/accused when invoking `BlameMachine::blame`, causing honest accusers to be slashed and guilty share-senders to escape blame - (File: processor/src/key_gen.rs)

### Summary
The Vault bug class is an identity-mapping confusion: two identities sharing a namespace let one party's actions/policies be attributed to another. In Serai, the PedPoP blame protocol identifies a faulty party as either the `sender` of a secret share or the `recipient` accusing them. `BlameMachine::blame(sender, recipient, ...)` is unambiguous about this ordering, and the PedPoP test harness calls it as `blame(ONE, TWO, ...)` where `ONE` is the accused sender and `TWO` the accusing recipient [1](#0-0) . The processor's `VerifyBlame` handler, however, calls `.blame(accuser, accused, ...)` — passing the `accuser` into the `sender` position and the `accused` into the `recipient` position [2](#0-1) .

### Finding Description
`blame_internal` decrypts the accused's message via `decrypt_with_proof(sender, recipient, msg, proof)`, which verifies the message's Schnorr PoP against a challenge bound to `from = sender` [3](#0-2) [4](#0-3) . Because `encrypt` produces a PoP bound to the real sender's `Participant` ID [5](#0-4) , a blame statement naming the actual guilty `accused` will fail `InvalidSignature` when evaluated with `from = accuser`. `blame_internal` then returns `sender` — i.e., the accuser — as the faulty party [6](#0-5) , and `VerifyBlame` emits `Blame { participant: accuser }` when neither machine blames `accused` [7](#0-6) .

Note the ordering asymmetry in the handler itself: malformed share bytes blame `accused` before the machines run [8](#0-7) , but any well-formed-but-invalid share (the common attack: a share that fails `share_verification_statements` or PoP-bound verification for the wrong sender) flows into the swapped machine call.

### Impact Explanation
A malicious DKG participant can broadcast/commit correctly but send an invalid encrypted secret share to a victim. When the victim submits a `VerifyBlame` accusation, the swapped arguments cause the Schnorr PoP to verify against the accuser's identity, fail, and the protocol fatally blames the honest accuser while exonerating the guilty sender. This is a direct privilege/identity-confusion: the guilty party's actions are attributed to an innocent party. Consequences: honest validators get slashed, aborts are induced without accountability, and an attacker can repeatedly poison key-generation attempts with impunity.

### Likelihood Explanation
Any participant in a DKG session can reach this path with ordinary protocol messages (a crafted `EncryptedMessage<SecretShare>` they send, then waiting for or inducing the blame report). The bug is deterministic — argument order is unconditionally wrong — so every blame evaluation through `VerifyBlame` inverts the sender/recipient roles. False accusations against honest senders are coincidentally still resolved "correctly" (the accuser is blamed either way), which masks the bug, but genuine faults always punish the reporter.

### Recommendation
Swap the arguments in `VerifyBlame` to `.blame(accused, accuser, ...)` for both the substrate and network `AdditionalBlameMachine` calls in `processor/src/key_gen.rs`, matching the `blame(sender, recipient, ...)` contract used in `crypto/dkg/pedpop/src/lib.rs` and the tests. Add a regression test where a genuinely invalid share is reported and the accused — not the accuser — is blamed.

### Proof of Concept
Conceptual trace (mirroring `crypto/dkg/pedpop/src/tests.rs` `invalid_ecdh_blame`):
1. Participant 2 (TWO) sends participant 1 (ONE) an `EncryptedMessage` whose ciphertext is mutated so the share fails verification (as `invalidate_msg` does).
2. ONE calls `calculate_share`, obtains `PedPoPError::InvalidShare { participant: TWO, blame }`, and submits a `CoordinatorMessage::VerifyBlame { accuser: ONE, accused: TWO, share, blame }`.
3. The handler calls `AdditionalBlameMachine::new(...).blame(ONE /* sender */, TWO /* recipient */, share, blame)`.
4. Inside `decrypt_with_proof`, `msg.pop.verify(msg.key, pop_challenge(ctx, R, key, from = ONE, msg))` fails because the PoP was bound to `from = TWO` when TWO encrypted it → `DecryptionError::InvalidSignature` → `blame_internal` returns `sender = ONE`.
5. `VerifyBlame` emits `Blame { participant: ONE }`: the honest accuser is slashed; the malicious sender TWO is declared faultless. With correct ordering (`blame(TWO, ONE, ...)`), step 4 instead proceeds to share re-verification and returns `sender = TWO`.

```rust
fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
```
