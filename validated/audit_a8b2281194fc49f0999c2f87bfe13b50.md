## Finding: Path‑prefix bypass in `resolveWithin` allows deep‑link file access outside the intended repository

The bug‑class parallel to the CurveTricryptoOracle math error — a single wrong operator in a security‑relevant computation that silently produces the wrong verdict — exists in GitHub Desktop's own path‑containment guard.

### Title
Sibling-directory escape via `startsWith` prefix check in `resolveWithin` allows a malicious deep link to read/open files outside the target repository - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin` decides whether a resolved path is "inside" a repository root using `realResolved.startsWith(realRoot)` without ensuring a path‑separator boundary follows the prefix. [1](#0-0)  Just like the oracle's stray `/ ethPrice` silently turned a correct USD value into a wrong ETH‑denominated one, this stray missing separator silently turns a correct "is it inside the root?" check into "does the resolved path merely start with the same characters as the root?" — a completely different (and wrong) invariant.

### Finding Description
`resolveWithin(rootPath, ...pathSegments)` is the app-wide guard used to prevent path traversal when handling attacker/model/remote-influenced relative paths. [2](#0-1)  It resolves the path, canonicalizes both the root and the resolved path with `realpath`, then checks containment purely with a string prefix test:

```
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

This is the same class of defect as the oracle bug: a single operator (`startsWith` instead of `startsWith(realRoot + sep)` or an explicit `relative()` check) inverts the intended semantics. If the repository's real path is `/Users/victim/Documents/GitHub/app` and there exists a sibling directory `/Users/victim/Documents/GitHub/app-secrets` (or `app2`, `app-internal`, etc. — an extremely common pattern for developers who keep related repos side by side), then a resolved path of `/Users/victim/Documents/GitHub/app-secrets/config.json` **incorrectly** satisfies `startsWith(realRoot)`, even though it is a completely different directory that only shares a name prefix with the repo.

One consumer of this guard is directly reachable from an attacker-controlled input: the `x-github-client://openRepo/...` deep-link handler. `parseAppURL` extracts an unsanitized `filepath` query parameter (only `branch` is validated with `testForInvalidChars`; `filepath` is passed through as-is). [3](#0-2)  `Dispatcher.openRepositoryFromUrl` only rejects absolute paths, then trusts `resolveWithin` to stop traversal before calling `shell.showItemInFolder`:

```
if (isAbsolute(filepath)) { ... return }
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
}
``` [4](#0-3) 

`open-url`/protocol-launcher events feed directly into `handleAppURL`, which is the trusted-looking but externally-triggerable entry point for these actions. [5](#0-4) 

### Impact Explanation
A crafted link such as `x-github-client://openRepo/https://github.com/org/app?filepath=..%2Fapp-secrets%2Fcredentials.json` (URL-encoded `../app-secrets/credentials.json`), when clicked by a user who already has both `app` and a sibling `app-secrets`/similarly-prefixed directory cloned, causes Desktop to reveal/open a file completely outside the repository the deep link nominally targets. This is exactly the "file read outside the repo" / "link the user clicks" primitive called out as valid impact — the containment check that is supposed to prevent it is defeated by the missing separator, not bypassed by any unusual user action.

### Likelihood Explanation
The only precondition is that the victim has a sibling directory whose name is prefixed by the repository directory name — a routine occurrence for developers (`api` / `api-gateway`, `app` / `app-strings`, `foo` / `foo2`, etc.), combined with clicking an attacker-supplied deep link (a normal, expected Desktop interaction, not a privileged or unnatural step). No local access, admin rights, or pre-existing malware is required.

### Recommendation
Fix the containment check in `_resolveWithin` to require a path-separator boundary (or use `path.relative()` and confirm the result does not start with `..`), e.g.:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
``` [1](#0-0) 
This should be applied to `_resolveWithin` so all consumers (`resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`) are corrected uniformly. [6](#0-5) 

### Proof of Concept
1. Victim has `/Users/victim/Documents/GitHub/app` (a repo) and `/Users/victim/Documents/GitHub/app-secrets/credentials.json` (any other directory whose name is prefixed by "app").
2. Attacker sends/publishes a link: `x-github-client://openRepo/https://github.com/org/app?filepath=..%2Fapp-secrets%2Fcredentials.json`.
3. Victim clicks the link; Electron's `open-url` fires, `handleAppURL` → `parseAppURL` produces `{ name: 'open-repository-from-url', url: 'https://github.com/org/app', filepath: '../app-secrets/credentials.json' }`. [3](#0-2) 
4. `Dispatcher.openRepositoryFromUrl` clones/opens `app`, then calls `resolveWithin(repository.path, '../app-secrets/credentials.json')`. [7](#0-6) 
5. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/app-secrets/credentials.json`; `realRoot` = `/Users/victim/Documents/GitHub/app`; `realResolved.startsWith(realRoot)` is `true` due to the shared string prefix, even though `app-secrets` is not nested under `app`. [8](#0-7) 
6. `shell.showItemInFolder(resolved)` reveals `credentials.json` from the unrelated `app-secrets` directory to the attacker's chosen target, confirming the escape.
