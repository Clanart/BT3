### Title
Unbounded attacker-controlled length in `SchnorrAggregate::read` enables remote hang / memory-exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::read` trusts a little-endian `u32` length prefix from the input stream and loops that many times calling `C::read_G(reader)`, with no upper bound and no pre-validation that the declared count is consistent with the remaining input. An unprivileged party who can feed bytes to `SchnorrAggregate::read` can declare a count of up to `u32::MAX` (4,294,967,295) elements, forcing the victim to attempt to read and store up to ~137 GiB of group elements. This mirrors CVE-2023-21940's bug class: a remotely triggerable, repeatable hang/crash (availability impact) reachable purely through network-supplied data.

### Finding Description
In `crypto/schnorr/src/aggregate.rs` (lines 77–88):

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
    let mut len = [0; 4];
    reader.read_exact(&mut len)?;

    let mut Rs = vec![];
    for _ in 0 .. u32::from_le_bytes(len) {
      Rs.push(C::read_G(reader)?);
    }
    ...
}
```

The 4-byte `len` field is fully attacker-controlled. The loop performs `u32::from_le_bytes(len)` iterations, each deserializing one `C::G`. There is:

- No cap on `len` (e.g., relative to a protocol-defined maximum aggregate size).
- No check that `len` is consistent with the actual stream length before starting.
- No `Vec::with_capacity` reservation limit or streaming verification — the `Rs` vector grows unboundedly in memory.

Two distinct resource-exhaustion modes result:

1. **Hang**: on a streaming/blocking reader (e.g., a socket `Read` impl), each `read_G` blocks for more bytes; an attacker dribbling data keeps the victim parsing for an unbounded duration — a "frequently repeatable hang" exactly matching the CVE class.
2. **Memory exhaustion / crash (OOM)**: on a non-blocking or buffered reader supplying the data, the process allocates ~32 bytes (plus `Vec` overhead) per element × 4 billion elements, guaranteed to abort the process.

By contrast, the sibling readers are safe: `Commitments::read` / `NonceCommitments::read` in `crypto/frost/src/nonce.rs` (lines 74–80, 133–139) derive their counts from the locally configured `algorithm.nonces()` generators, not from the wire, and `MultiDLEqProof::read` in `crypto/dleq/src/lib.rs` (lines 308–315) takes `discrete_logs` as a caller-supplied parameter rather than from untrusted bytes. `SchnorrAggregate::read` is the outlier that trusts wire data for its iteration bound.

### Impact Explanation
Any node/service that deserializes `SchnorrAggregate` from peer-supplied bytes (signature aggregation is used to combine many Schnorr signatures, so its deserialized form is inherently multi-party input) can be hung in the read loop or OOM-killed by a ~4-byte malicious prefix (`FF FF FF FF`). This is a complete, repeatable denial of service of the verifying process, requiring no privileges, no valid keys, and no correct cryptography — directly analogous to the CVE's "unauthorized ability to cause a hang or frequently repeatable crash."

### Likelihood Explanation
Medium. Exploitation requires only that the target expose a code path deserializing `SchnorrAggregate` from untrusted input — the exact scenario the type exists for (aggregating signatures from multiple signers). The attack is trivial: a 4-byte length prefix followed by arbitrary bytes. Impact is capped at availability (no key recovery, no forgery), consistent with the Medium severity of the source CVE.

### Recommendation
Bound the declared length before iterating:

```rust
const MAX_AGGREGATE_SIGS: u32 = /* protocol limit, e.g. u16::MAX */;
let len = u32::from_le_bytes(len);
if len > MAX_AGGREGATE_SIGS {
  Err(io::Error::other("too many signatures in aggregate"))?;
}
```

and/or verify lazily without storing all `Rs`, or require callers to pass an expected count (as `MultiDLEqProof::read` already does with `discrete_logs`).

### Proof of Concept
```rust
use std::io::Cursor;
use ciphersuite::Secp256k1;
use schnorr::aggregate::SchnorrAggregate;

// Attacker-controlled bytes: len = u32::MAX, followed by any filler.
let mut malicious = u32::MAX.to_le_bytes().to_vec();
malicious.extend_from_slice(&[0xAA; 1024]);

// Hangs in the read loop on a streaming reader, or OOMs on a buffered one.
let _ = SchnorrAggregate::<Secp256k1>::read(&mut Cursor::new(malicious));
```

On a `Read` impl backed by a network socket, the victim blocks inside `read_G` for up to ~4 billion iterations; on a sufficiently large buffered input, `Rs` grows until the allocator aborts the process.
