### Title
Missing `chain_id` in EIP-712 Domain Separator Enables Cross-Chain Replay of Withdrawal Authorization Signatures — (`File: core/src/rpc/ecdsa_verification_sig.rs`)

### Summary

`CLEMENTINE_EIP712_DOMAIN` is constructed without a `chain_id` field. Every withdrawal authorization signature produced by the aggregator is therefore valid on any Citrea chain deployment or hard fork that shares the same aggregator key, allowing an attacker to replay a signature from one chain to authorize an unauthorized BTC withdrawal on another.

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as a compile-time static with only `name` and `version`:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

This domain is used in `recover_address_from_ecdsa_signature` to compute the EIP-712 hash for both `OptimisticPayoutMessage` and `OperatorWithdrawalMessage`:

```rust
let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);
let address = signature.recover_address_from_prehash(&eip712_hash)...;
``` [2](#0-1) 

The recovered address is then compared against `aggregator_verification_address` from config in both the operator `withdraw` RPC handler and the verifier `sign_optimistic_payout` path: [3](#0-2) [4](#0-3) 

The config already carries `citrea_chain_id: u32` (e.g., `5655` for Citrea mainnet): [5](#0-4) 

but it is **never incorporated** into the domain separator. The `BatchProofMethodIdBody` struct in the tx-sender codebase explicitly includes `chain_id` for the same reason — to prevent cross-network replay — demonstrating that the developers are aware of the requirement: [6](#0-5) 

Because the domain separator is chain-agnostic, the EIP-712 hash for any given `(withdrawal_id, input_outpoint, output_script_pubkey, output_amount)` tuple is **identical** across every Citrea deployment or hard fork that uses the same aggregator key.

### Impact Explanation

If Citrea is hard-forked (both forks retain the same state at the fork point, including the same withdrawal UTXOs and withdrawal IDs), or if the same aggregator key is reused across a mainnet and a testnet Citrea deployment that share the same Bitcoin network:

1. The aggregator legitimately signs an `OptimisticPayoutMessage` or `OperatorWithdrawalMessage` for withdrawal ID `N` on chain A.
2. An attacker captures that signature.
3. The attacker submits the identical signature to operators/verifiers on chain B via the `withdraw` or `optimistic_payout_sign` gRPC endpoint.
4. `recover_address_from_ecdsa_signature` produces the same recovered address (domain hash is identical), the address matches `aggregator_verification_address`, and the withdrawal is authorized.
5. The operator pays out BTC from the bridge vault on chain B without a legitimate withdrawal request on that chain.

This constitutes unauthorized spending of bridge-controlled UTXOs / bridged BTC.

### Likelihood Explanation

The precondition is that the same aggregator ECDSA key is used across two Citrea deployments or forks that share overlapping withdrawal state (same `withdrawal_id` and `input_outpoint`). This is realistic in:

- A Citrea hard fork that retains the same chain state (the exact scenario described in the external report).
- A testnet and mainnet deployment sharing the same aggregator key and the same Bitcoin network (e.g., testnet4 bridge used for both).

The `aggregator_verification_address` field is `Option`al; if unset, the check is skipped entirely and no signature is required at all, which is a separate but compounding weakness. [7](#0-6) 

### Recommendation

**Short term**: Include `citrea_chain_id` from `BridgeConfig` in the EIP-712 domain separator. Replace the static `CLEMENTINE_EIP712_DOMAIN` with a function that constructs the domain dynamically from the runtime chain ID:

```rust
pub fn clementine_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass `config.citrea_chain_id as u64` wherever `CLEMENTINE_EIP712_DOMAIN` is currently used.

**Long term**: Document that the aggregator ECDSA key must never be shared across Citrea deployments with different chain IDs, and add a startup assertion that `citrea_chain_id` is non-zero and matches the connected Citrea node's reported chain ID.

### Proof of Concept

1. Deploy two Citrea instances: chain A (`chain_id=5655`) and chain B (`chain_id=5656`), both connected to the same Bitcoin testnet4 network, both configured with the same `aggregator_verification_address`.
2. On chain A, create a legitimate deposit and withdrawal UTXO for `withdrawal_id=0`.
3. Have the aggregator sign an `OperatorWithdrawalMessage` for `withdrawal_id=0` on chain A. Capture the hex signature `S`.
4. On chain B, ensure `withdrawal_id=0` exists with the same `input_outpoint` (possible if both chains started from the same state, or if the same Bitcoin UTXO is registered on both).
5. Submit `S` to chain B's operator `withdraw` RPC with the same parameters.
6. `recover_address_from_ecdsa_signature` computes `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` — identical on both chains because `CLEMENTINE_EIP712_DOMAIN` has no `chain_id` — recovers the aggregator address, passes the check, and the operator pays out BTC on chain B without a valid chain-B authorization.
