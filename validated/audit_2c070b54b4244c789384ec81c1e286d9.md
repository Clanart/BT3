The key analog area is PedPoP blame proofs revealing ECDH keys. Let me check how `EncryptionKeyProof` is serialized and whether `ThresholdKeys`/secret material leaks via `Debug` or public messages.### Title
Public `EncryptionKeyProof` discloses the ECDH key (plaintext share) to all observers, and a malicious sender can forge it to frame an honest recipient - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP blame mechanism publishes `EncryptionKeyProof`, whose `key` field is the raw ECDH shared point `k * enc_pub_recipient`. Whoever sees the serialized proof can derive the ChaCha20 cipher via `cipher()` and decrypt the accused `EncryptedMessage` — i.e. the secret share is disclosed in plaintext to any observer of the blame message. Worse, the DLEq proof binds only `(G, msg.key) -> (enc_keys[decryptor], proof.key)`; it does not require the prover to be the recipient. The *sender*, who knows the per-message scalar `k` such that `msg.key = k*G`, can compute `proof.key = k * enc_pub_victim` for any `decryptor` index and produce a valid proof. Submitting this via `blame()`/`AdditionalBlameMachine::blame` causes `blame_internal` to decrypt a perfectly valid share, concluding the recipient lied, and returns `recipient` as the faulty party — letting a malicious sender get an honest participant slashed while simultaneously publishing their share plaintext.

### Finding Description
`Encryption::decrypt` returns an `EncryptionKeyProof` containing `key = ecdh(enc_key, msg.key)` for every processed message (crypto/dkg/pedpop/src/encryption.rs:487-499). `EncryptionKeyProof::write` serializes `key` verbatim (encryption.rs:271-274), and `calculate_share` surfaces it inside `PedPoPError::InvalidShare`, which the processor serializes into `ProcessorMessage::InvalidShare` (processor/src/key_gen.rs:419-425). Because `cipher(context, ecdh)` derives the ChaCha20 keystream deterministically from the ECDH point with a static IV (encryption.rs:101-132), any party holding the proof bytes holds the plaintext.

For verification, `Decryption::decrypt_with_proof` checks `proof.dleq.verify(..., &[G, msg.key], &[enc_keys[decryptor], proof.key])` (encryption.rs:381-390). The DLEq only proves `proof.key = dlog(msg.key) * enc_keys[decryptor]` — a value the original sender can compute for an arbitrary `decryptor`, since they chose `k` and all `enc_keys` are public. In `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609), a successfully decrypted share that parses as a scalar and satisfies `share_verification_statements` returns `recipient` as faulty. So a sender who transmitted a *valid* share to victim V can generate the proof themselves and submit `blame(sender, V, msg, proof)`; the machine blames V.

### Impact Explanation
Two consequences: (1) plaintext disclosure of a secret share to all observers of the (public) blame transcript — the direct analog of plaintext credential disclosure; (2) incorrect blame attribution enabling an unprivileged participant, using only bytes they generated, to cause an honest party to be marked faulty and slashed via `ProcessorMessage::Blame` (key_gen.rs:558-563).

### Likelihood Explanation
Reachable by any DKG participant acting as a share sender; requires no collusion and only publicly available data (their own ephemeral scalar and the victim's published encryption key). The blame path is explicitly designed for untrusted input (`AdditionalBlameMachine::new` is callable by non-participants).

### Recommendation
Bind the blame proof to the accuser: e.g., require the DLEq transcript to commit to `decryptor`/`recipient` identity and require the accuser to prove knowledge of `enc_key` (PoK on `enc_keys[decryptor]`) rather than accepting a bare ECDH point; or have blame revelation go through a commit-reveal so only the actual recipient can open it. Also consider encrypting `proof.key` or limiting proof publication, since it is itself the decryption key for the message.

### Proof of Concept
1. Sender S runs `encrypt` for victim V producing `EncryptedMessage{key=kG, pop, msg}` with a *valid* share.
2. S computes `proof.key = k * enc_pub_V` and proves `DLEq((G, kG), (enc_pub_V, k*enc_pub_V))` — valid since S knows `k`.
3. S submits `AdditionalBlameMachine::new(context, n, commitment_msgs).blame(S, V, msg, Some(proof))`.
4. `decrypt_with_proof` verifies the DLEq and decrypts the valid share; `blame_internal` returns `V`. V is blamed/slashed, and `proof.key` publicly decrypts the share.
