### Title
Git clone-time RCE protection explicitly disabled via `GIT_CLONE_PROTECTION_ACTIVE=false` on recursive clones - (File: `app/src/lib/git/clone.ts`)

### Summary
GitHub Desktop's `clone()` helper performs every clone with `--recursive` (submodules fetched automatically) while explicitly setting the environment variable `GIT_CLONE_PROTECTION_ACTIVE=false`. This variable is git's own built-in guard (added to harden `git clone`/`git submodule` against maliciously-crafted repositories that ship an embedded/symlinked `.git` directory or hostile hook files, historically exploitable for RCE on case-insensitive filesystems). Explicitly forcing this protection off means a remote-controlled, attacker-authored repository (or one of its submodules) can potentially plant files that escape the intended working tree/`.git` layout during an ordinary "Clone" or "Open in Desktop" action, with no additional user interaction beyond entering/clicking a clone URL.

### Finding Description
`clone()` builds the git invocation like this: [1](#0-0) 

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = [
  '-c',
  `init.defaultBranch=${defaultBranch}`,
  'clone',
  '--recursive',
]
```

`GIT_CLONE_PROTECTION_ACTIVE` is a real upstream Git safety switch that git itself checks internally when cloning (including recursive submodule clones) to detect and reject repositories that attempt to place a `.git` directory, symlink, or hook file in a location that would let content escape the intended checkout directory on case-insensitive or case-mapping filesystems (the class of bug behind the Git RCE advisories fixed via `clone.protection`/`GIT_CLONE_PROTECTION_ACTIVE` hardening). By setting it to `'false'` unconditionally for every clone Desktop performs, the application actively opts out of this upstream defense for both the top-level repository and, because `--recursive` is always passed, for every submodule pulled in transitively.

This is directly reachable by an unprivileged, network-side attacker: any repository or fork can be crafted to include such a payload, and the only action required from the victim is to clone it via GitHub Desktop's normal "Clone repository" dialog, "Open in Desktop" deep link (`openrepo` action parsed in `app/src/lib/parse-app-url.ts`), or a CLI `--cli-clone` invocation — none of which require the user to inspect the repository contents first.

Other guards in the same file (`isClonePathSensitive`, checked at `app/src/lib/git/clone.ts:16-47`) only validate the *destination directory* chosen by the user; they do nothing to stop content written *inside* the clone by git itself once cloning begins, so they do not compensate for the disabled protection.

### Impact Explanation
If the disabled protection is what stands between a hostile repository and file writes/execution outside the intended working directory (e.g., writing into `.git/hooks` of the top-level repo or a submodule's real `.git` directory via a crafted embedded/symlinked path), the impact is arbitrary file write outside the repository root and potential code execution the next time git runs a hook (commit, checkout, merge, etc.) inside that repository — all triggered by simply cloning an attacker's repo, matching the "unprivileged, attacker-controlled repo → code execution / file write outside the repo" impact class called out in scope.

### Likelihood Explanation
Likelihood is high for exposure (every clone operation, including submodule recursion, unconditionally disables the check — there is no opt-in/opt-out toggle, no confirmation dialog, and the disabling is unconditional code, not test-only). Whether it is currently exploitable depends on the exact CVE/version of the bundled git binary and whether other layers (e.g., git's own default `protocol.file.allow` restrictions, filesystem case sensitivity) still block the underlying primitive; that residual git-level protection could not be fully verified from the indexed source alone. The comment/rationale for disabling the flag is not present in the file, and no compensating check for embedded/symlinked `.git` paths exists elsewhere in `app/src/lib/git/clone.ts` or `app/src/lib/git/submodule.ts`.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override (or set it to `'true'`/leave it unset so git's default hardened behavior applies) unless there is a well-documented, narrowly-scoped reason tied to a specific compatibility issue — and if so, gate it behind a feature flag/allowlist rather than applying it to all clones and all recursive submodules unconditionally. Add regression tests (mirroring `app/test/unit/git/clone-test.ts`) that assert a crafted repository with an embedded/symlinked `.git` directory is rejected during clone, rather than only testing destination-path sensitivity as currently done in `isClonePathSensitive`.

### Proof of Concept
1. Craft a malicious repository (or submodule) containing an embedded/symlinked `.git` entry structured to defeat the case-insensitive-filesystem protection that `GIT_CLONE_PROTECTION_ACTIVE` is designed to catch (following the pattern of the git advisories this flag was introduced to mitigate).
2. Host it publicly and have the victim clone it through GitHub Desktop's "Clone a Repository" dialog, or send them an `x-github-client://openRepo/<attacker-repo-url>` deep link (handled by `parseAppURL` in `app/src/lib/parse-app-url.ts:66-125` and dispatched to `openOrCloneRepository` in `app/src/ui/dispatcher/dispatcher.ts:2215-2233`).
3. Because `clone()` in `app/src/lib/git/clone.ts:68-126` always runs with `GIT_CLONE_PROTECTION_ACTIVE=false` and `--recursive`, git's internal safety check that would normally abort the clone/submodule-update on detecting the hostile layout is bypassed, allowing the payload to land where the protection would otherwise have blocked it.

Note: full confirmation that this results in a working RCE requires validating against the specific dugite/git version bundled with this build (not resolvable from indexed source alone) — flagging this as the residual uncertainty in an otherwise clear, code-verifiable deviation from git's recommended hardening.
