### Title
Path traversal in `revealInFileManager` via unvalidated repository-relative `file.path` — (File: `app/src/lib/app-shell.ts`)

### Summary
`revealInFileManager` builds the file-manager target path with a bare `Path.join(repository.path, path)` and passes the result straight to `shell.showItemInFolder`, without ever confirming that the joined path still resolves underneath `repository.path`. [1](#0-0) 

### Finding Description
The `path` argument to `revealInFileManager` ultimately originates from file entries surfaced by git (`WorkingDirectoryFileChange`/`CommittedFileChange.path`) that are rendered in the Changes list, History view, conflict resolution UI, and PR file list, and forwarded unchanged to this function. [2](#0-1) 

The codebase already has a purpose-built containment primitive, `resolveWithin` (and its `Posix`/`Win32` variants), which resolves a root + relative segments, `realpath`s both sides, and rejects the result unless it stays underneath the root — precisely the check needed to defend against symlinked directories that escape the repository root: [3](#0-2) 

This primitive is consumed elsewhere (e.g. `app-store.ts`, `dispatcher.ts`, `copilot-conflict-context.ts`), confirming it is the project's established mitigation for repo-relative path handling. `revealInFileManager`, however, does not call it at all — it only does `Path.join(repository.path, path)`: [1](#0-0) 

If a tracked path component is (or, on checkout, becomes) a symlink pointing outside the repository — e.g. `evil-link -> /` committed/checked out as part of a cloned repo — then a file entry such as `evil-link/etc/passwd` will `Path.join` to `repository.path/evil-link/etc/passwd`. When the OS/file manager resolves this path, the symlinked component causes the final target to physically reside outside `repository.path`. `Path.join`/`Path.normalize` alone do not detect or prevent this because they operate purely lexically and are symlink-unaware; only a `realpath`-based check (like `resolveWithin`) can catch it. A literal `../` segment surviving in a git-tracked pathname is not itself achievable (git normalizes tree entries and canonicalizes paths through `git status`/`diff` parsing), but the symlink-based escape achieves the same effect and is the realistic proof vector here.

### Impact Explanation
`shell.showItemInFolder` (Electron) opens the OS file manager and selects/reveals the resolved path. If that path escapes the repository (via a symlinked directory), the user's file manager will be opened and pointed at a location outside the repo — silently corrupting the "path is inside repository.path" invariant the rest of the app assumes when handling repository-relative paths. This is a file-system-scoped disclosure/reveal primitive operating outside the intended sandbox of the checked-out repo, triggered purely by content in a cloned/fetched repository.

### Likelihood Explanation
Requires the victim to clone/fetch a malicious repository containing a symlinked directory that escapes the repo root, have that path show up as a changed/committed file in Desktop's Changes or History view, and then invoke "Reveal in Finder/Explorer" on it — a normal, expected user action once such a file is shown in the list. No special permissions or additional user trickery beyond opening the attacker's repo in Desktop are needed. Platform symlink checkout behavior (git for Windows/macOS/Linux config, `core.symlinks`) affects reliability, but the code-level containment check is unconditionally absent regardless of platform.

### Recommendation
Apply the existing `resolveWithin` (or `resolveWithinWin32`/`resolveWithinPosix` as appropriate) helper inside `revealInFileManager` before calling `shell.showItemInFolder`, and refuse to reveal the file (or fall back to revealing the repository root) if the resolved real path does not stay underneath `repository.path`, mirroring the pattern already used in `app-store.ts`/`dispatcher.ts`/`copilot-conflict-context.ts`.

### Proof of Concept
1. Create a repository containing a symlink `link` pointing to `/` (or another directory outside the repo), and a nested path `link/tmp/target` that git tracks/reports as part of a diff.
2. Have the victim clone/fetch this repository in GitHub Desktop such that `link` is checked out as a real symlink (depends on `core.symlinks`/platform).
3. Select the file entry `link/tmp/target` in the Changes or History list and invoke "Reveal in Finder/Explorer".
4. `revealInFileManager(repository, 'link/tmp/target')` computes `Path.join(repository.path, 'link/tmp/target')`; because `link` is a symlink escaping the repo, the OS resolves this to a path outside `repository.path`, and `shell.showItemInFolder` reveals a location outside the repository, without any `resolveWithin`-style check having rejected it. async function _resolveWithin(
```typescript
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
