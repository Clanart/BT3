### Title
Stale line-selection state is silently reapplied to an unrelated diff, causing corruption of what gets committed - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts` merges a freshly computed `git status` result with the previously held `WorkingDirectoryFileChange` objects by matching purely on `file.id` (path-derived), then blindly transplants the *old* `DiffSelection` (including its `divergingLines` line-index set) onto the *new* file object via `file.withSelection(existingFile.selection)`. There is no check that the new diff's line numbering/content still corresponds to what the diverging-line indices were computed against. Revalidation of selectable/diverging lines (`app/src/lib/stores/app-store.ts`, `updateChangesWorkingDirectoryDiff`, lines ~3478-3497) only happens for the single file currently open in the diff viewer — every other partially-selected file in the working directory keeps its stale line-index selection carried straight through to the next commit.

### Finding Description
The relevant code: [1](#0-0) 

For each file, if an `existingFile` with the same `id` is found, its `selection` (a `DiffSelection` holding a `Set<number>` of "diverging" line indices, see `app/src/models/diff/diff-selection.ts` lines 53-84) is copied onto the new file object regardless of whether the new diff's hunks/line numbering actually match the old one. The only guard, `clearPartialState`, resets the selection solely when the caller explicitly requests it (used only after a commit); ordinary background status refreshes (file-watcher events, `_loadStatus`, `refreshIndicatorForRepository`, background fetch cycles) call this with `clearPartialState = false`.

Line-index validation against the *current* diff only happens in `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts`, lines 3478-3497), and only for the single file that is presently selected/open in the diff view: [2](#0-1) 

Any other file that has a partial selection but is not the actively-viewed file never gets its `selectableLines`/`divergingLines` reconciled against new diff content before commit.

At commit time, `formatPatch` (`app/src/lib/patch-formatter.ts`, lines 129-206) walks the *current* diff hunks and decides per-line inclusion purely via `file.selection.isSelected(absoluteIndex)` — i.e., it trusts the stale line-index selection object against a diff it was never validated against: [3](#0-2) 

The broken invariant: "a `DiffSelection`'s diverging-line indices are only meaningful relative to the diff they were computed from" is not enforced when the working tree content for a tracked file changes underneath a stale, non-viewed selection. Analogous to the BoostController bug, a stateful accounting object (there: `totalBoost`/`workingSupply`; here: per-line `divergingLines`) is carried forward across a state transition (delegation removal / diff refresh) without validating it against the new authoritative state, and the guard that exists (`clearPartialState`, `updateChangesWorkingDirectoryDiff`) only covers a narrow subset of the actual state-transition paths.

### Impact Explanation
If the content of a tracked file changes between the time a user partially selects lines to include in a commit and the time they actually commit — e.g., because a git hook shipped in a cloned/fetched malicious repository (`post-checkout`, `post-merge`, `pre-commit` rewriting a tracked file) fires during a background operation Desktop performs automatically (pull, fetch-triggered status refresh, checkout), or because a concurrently running `git` process/proxy response mutates the working tree — the previously computed line-index selection for that file is reused verbatim against the new diff content. Because line indices are absolute positions in the diff, not content hashes, this can cause git to stage/commit (or exclude) different code than what the user actually reviewed and checked in the UI. This is a silent corruption of what the user commits/pushes, without any error or warning shown, matching the requested "silent corruption" impact class.

### Likelihood Explanation
The attacker-controlled surface needed (a cloned/fetched repository containing hooks, or a remote/proxy able to alter working-tree content as part of normal git operations Desktop triggers automatically such as background fetch/pull) is within the stated valid-impact scope (attacker controls a cloned/fetched repository or git remote/proxy response). The bug requires no admin rights, no local/physical access, and no unnatural user steps beyond normal usage (partially select lines in one file, let Desktop refresh status in the background — which it does routinely via file watchers and background fetch — then commit). The main uncertainty is the precise timing window and exact hook mechanism needed to reliably alter file content without changing `file.id`; I could not fully trace the git-hook execution paths invoked during Desktop's automatic operations to confirm end-to-end exploitability, so this should be validated with a live PoC before treating it as fully confirmed.

### Recommendation
- In `updateChangedFiles`, don't unconditionally carry over `existingFile.selection` for partially-selected files; instead recompute/validate `selectableLines`/`divergingLines` against the new diff for every file with `DiffSelectionType.Partial`, not just the actively-viewed one, before merging state.
- Consider tagging `DiffSelection` with a content fingerprint (e.g., diff hash) so stale selections can be detected and reset rather than silently reapplied.
- At minimum, before generating a commit patch (`formatPatch`/`stageFiles`), re-diff each file with a partial selection and refuse (or reset to "select all"/prompt the user) if the stored diverging-line indices no longer align with the current diff's line count/hunks.

### Proof of Concept
Conceptual PoC (I could not run this against the live app, so this is a logical walkthrough based on the cited code):
1. User opens a repository, edits `file.txt`, and in the Changes view selects only some lines of the diff for `file.txt` to include in the next commit (`DiffSelectionType.Partial`, `divergingLines = {3, 4}`).
2. User switches focus to a different file in the UI (so `file.txt` is no longer the actively viewed diff — `updateChangesWorkingDirectoryDiff`'s revalidation in `app-store.ts` no longer applies to it).
3. While `file.txt` is not being viewed, a background git operation Desktop performs automatically (e.g., background fetch that runs a `post-fetch`/`post-merge` hook from a cloned malicious repo, or an attacker-controlled remote/proxy response that alters tracked content as part of a fetch/pull) rewrites `file.txt`'s content, changing its diff hunks and line numbering while keeping the same path (`id`).
4. Desktop's file watcher triggers `_loadStatus` → `updateChangedFiles` (`changes-state.ts` lines 43-61), which matches the file by `id` and reapplies the stale `divergingLines = {3, 4}` selection onto the brand-new diff without validation.
5. User commits. `formatPatch` (`patch-formatter.ts` lines 143-171) builds the patch using `file.selection.isSelected(absoluteIndex)` against the new hunks, staging/omitting lines at positions 3–4 of the *new* content — which may be entirely different code than what the user visually reviewed — resulting in a commit whose content silently diverges from user intent.
