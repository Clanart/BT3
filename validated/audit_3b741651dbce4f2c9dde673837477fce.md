### Title
Infinite loop denial-of-service in offer processing via crafted cyclic coin parent references - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_root_removal()` walks backwards through the coin-parent chain of an offer's removals until it finds a "non-ephemeral" coin (a coin whose `parent_coin_info` is not itself one of the removals in the bundle). Because the `coin_spends` list inside an `Offer`/`WalletSpendBundle` is attacker-supplied data (an offer file crafted by a counterparty, not yet chain-validated), a malicious offer can define two or more coins whose `parent_coin_info` fields reference each other in a cycle, causing the `while` loop to never reach a coin in `non_ephemeral_removals` and spin forever.

### Finding Description
`get_root_removal` is defined as: [1](#0-0) 

```
def get_root_removal(self, coin: Coin) -> Coin:
    all_removals: set[Coin] = set(self.removals())
    all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
    non_ephemeral_removals: set[Coin] = {
        c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
    }
    if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
        raise ValueError("The specified coin is not a coin in this bundle")

    while coin not in non_ephemeral_removals:
        coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

    return coin
```
`non_ephemeral_removals` is the set of removal coins whose parent is *not* one of the other removals. If an attacker constructs an offer whose `_bundle.coin_spends` contains two synthetic coins `A` and `B`, where `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`, then neither `A` nor `B` qualifies as non-ephemeral (each one's parent is present among the removals). Starting the walk at `A`, the loop toggles between `A` and `B` forever, since the `next()` lookup always succeeds (each parent id resolves to the other coin) and the loop never reaches the `non_ephemeral_removals` set. `Coin` objects and their `parent_coin_info` fields are simply data fields inside the `CoinSpend`s that make up the offer's `WalletSpendBundle`; nothing in `Offer.__post_init__` ( [2](#0-1) ) validates that the parent-child coin lineage is acyclic or chain-consistent — it only checks for duplicate spent coins and computes additions/hints.

`get_root_removal` is the building block for `get_primary_coins()`: [3](#0-2) 
which is used to determine primary/cancellation coins of an offer, and this function chain is invoked from `chia/wallet/trade_manager.py` when a wallet inspects or manages an incoming/outgoing offer (2 usages found there).

### Impact Explanation
An unprivileged party can hand a crafted offer file (never touching the chain) to a wallet user or service; when the wallet computes offer summaries or cancellation coins for that offer, it enters an unbounded loop, hanging the async task that holds the wallet lock. This matches the CVE's bug class of "incorrect initialization/validation of internal object relationships causing an infinite loop leading to denial of service" — here the internal object graph (coin parent/child lineage) is never validated against a cycle before the traversal loop runs.

### Likelihood Explanation
Reachable purely by supplying attacker-controlled offer data (a `.offer` file or `WalletSpendBundle` before it is ever pushed to the mempool/chain), requiring no privileged access, no signature validation, and no chain state — trivial for any offer counterparty to construct two coins with reciprocal `parent_coin_info` values.

### Recommendation
In `get_root_removal` (and any lineage-walking logic that trusts unvalidated `parent_coin_info` fields from an untrusted `Offer`/`SpendBundle`), track visited coin names and bound the traversal to `len(all_removals)` steps, raising a `ValueError`/`ValidationError` if a cycle or unresolved chain is detected instead of looping unbounded.

### Proof of Concept
1. Construct two `Coin` objects `A` and `B` with `A.parent_coin_info = B.name()` and `B.parent_coin_info = A.name()` (arbitrary puzzle hashes/amounts), each with a corresponding `CoinSpend` in an `Offer._bundle.coin_spends`.
2. Instantiate an `Offer` with these coin spends among `removals()`/`get_involved_coins()`.
3. Call `offer.get_primary_coins()` (or directly `offer.get_root_removal(A)`); the call never returns because the `while coin not in non_ephemeral_removals` loop toggles indefinitely between `A` and `B`.
