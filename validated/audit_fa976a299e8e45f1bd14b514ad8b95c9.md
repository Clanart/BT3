### Title
Unbounded Python recursion in outer-puzzle driver matching (`match_puzzle`) allows an attacker-crafted offer / spend bundle to crash a wallet's RPC process via `RecursionError` - ([File: chia/wallet/outer_puzzles.py])

### Summary
`match_puzzle()` in `chia/wallet/outer_puzzles.py` recursively descends into every "inner puzzle" layer of a CLVM puzzle reveal (CAT, singleton, metadata, ownership, CR/credential-restricted, revocation layers) with no depth limit. Each outer-puzzle driver's `match()` method calls back into `match_puzzle()` (bound as `self._match`) for the puzzle's inner puzzle, and this chain continues for as many curried layers as are present in the reveal. A malicious offer counterparty (or any spend-bundle/offer submitter reaching this code path) can construct a puzzle reveal with an arbitrarily large number of nested recognizable outer-puzzle layers (e.g. many nested CAT-in-CAT or singleton/metadata/ownership/CR wrappers), which drives Python's call stack past `sys.getrecursionlimit()` and raises an unhandled `RecursionError`, crashing the wallet process that is parsing the offer/spend bundle. This is the same bug class as the reported NLTK `JSONTaggedDecoder.decode_obj()` issue: recursive traversal of attacker-controlled nested structure with no depth bound.

`match_puzzle` is invoked while parsing offers, e.g. in `Offer._get_offered_coins()` where each coin spend's puzzle reveal from an incoming (attacker/counterparty supplied) offer is matched:
```python

...

``` [8](#0-7) 

Offer objects (and their embedded puzzle reveals) are user/counterparty-supplied bech32m-encoded blobs that reach this code via RPC endpoints such as `take_offer`/`get_offer_summary` in `chia/wallet/wallet_rpc_api.py` and `TradeManager`, so the puzzle nesting depth is fully attacker-controlled and unbounded by consensus/CLVM cost limits (the recursion happens in Python, not in metered CLVM execution).

### Impact Explanation
An attacker can craft an offer file (or any spend bundle presented for offer inspection) whose puzzle reveal contains a puzzle stack with a large number of nested curried outer-puzzle layers that each satisfy one of the recognized `match_*_puzzle` patterns (CAT-wrapping-CAT is trivially constructible via `construct_cat_puzzle` with an inner CAT puzzle, as shown in existing tests). When a victim wallet calls `take_offer`, `get_offer_summary`, or otherwise parses the offer through `Offer._get_offered_coins()` / `match_puzzle()`, the unbounded Python recursion exceeds the interpreter's recursion limit and raises `RecursionError`, crashing or hanging the wallet's RPC-serving process/thread. This is a denial-of-service against a wallet user or offer counterparty processing an untrusted offer — it does not directly allow theft of funds, forged asset identity, or coin-set divergence, but it does constitute a spend/offer-triggered halt of transaction processing for the affected wallet.

### Likelihood Explanation
Constructing nested CAT/singleton/metadata/ownership/CR puzzle layers is straightforward using existing puzzle-construction helpers (`construct_cat_puzzle`, `puzzle_for_singleton`, `puzzle_for_metadata_layer`, `construct_cr_layer`, etc., all present in the codebase and exercised in tests such as `test_cat_outer_puzzle`, `test_ownership_outer_puzzle`, `test_cat_outer_puzzle` for CR). Any wallet user who receives/inspects an offer file from an untrusted counterparty, or any RPC caller who submits a spend bundle for offer analysis, can trigger this without any privileged access, and no special network position is required — it purely depends on the depth of Python's default recursion limit (~1000), which is easy to exceed with a puzzle reveal a few hundred layers deep (well within CLVM program size/serialization limits).

### Recommendation
Add an explicit depth counter/limit to `match_puzzle()` (and to `PuzzleInfo.also()`/`check_type()`), raising a controlled `ValueError`/`InvalidTypeError` once a maximum nesting depth (e.g. 100) is exceeded, mirroring the suggested NLTK fix. Alternatively, convert the recursive matching into an iterative loop that walks inner puzzles level by level with a bounded iteration count, similar to how `sha256_treehash` was deliberately made iterative to avoid the same class of stack-overflow issue.

### Proof of Concept
Conceptually (cannot be executed in this environment, but derivable from existing test helpers such as `test_cat_outer_puzzle` in `chia/_tests/wallet/cat_wallet/test_cat_outer_puzzle.py`):
```python
from chia.wallet.cat_wallet.cat_utils import CAT_MOD, construct_cat_puzzle
from chia.types.blockchain_format.program import Program
from chia.wallet.outer_puzzles import match_puzzle
from chia.wallet.puzzles.puzzle_drivers import UnknownPuzzle

ACS = Program.to(1)
tail = bytes([0] * 32)
puzzle = ACS
# Nest CAT-in-CAT thousands of times to exceed Python's recursion limit
for _ in range(2000):
    puzzle = construct_cat_puzzle(CAT_MOD, tail, puzzle)

match_puzzle(UnknownPuzzle(known_program=puzzle))  # raises RecursionError
```
Feeding a puzzle reveal built this way into an offer/spend bundle and having a wallet call `take_offer`/`get_offer_summary` (which internally calls `Offer._get_offered_coins()` → `match_puzzle()`) reproduces the crash on the receiving node/wallet.
