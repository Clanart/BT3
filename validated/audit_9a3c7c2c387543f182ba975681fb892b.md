### Title
`HyperbridgeWithdrawalModule::on_accept` authenticates by source chain only, not by sending module — unauthorized relayer-fee drain - (File: `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
`HyperbridgeWithdrawalModule::on_accept` — the built-in ISMP module that pays out `RELAYER_FEE_ACCOUNT` funds — only validates that an incoming `PostRequest` originates from the configured coprocessor **chain** (`request.source == T::Coprocessor::get()`). It never checks `request.from`, the identifier of the specific module/account on that chain that dispatched the message. Every other privileged `IsmpModule::on_accept` in this codebase (bandwidth pallet, hyper‑fungible‑token pallet, EVM `HostManager.onAccept`) validates *both* the chain-level `source` **and** the sender-level `from`/module id. This module is the odd one out, matching the ERC1820 pattern of a function that is supposed to accept a narrowly-scoped identity but instead "accepts" any input matching only a coarse condition.

### Finding Description
`HyperbridgeWithdrawalModule::on_accept` at [1](#0-0)  does:

The only guard is "does this request's `source` chain equal the coprocessor id?" — there is no check that `request.from` equals a specific, trusted module/pallet address on the coprocessor (e.g. a governance or treasury pallet id). Compare this to the two sibling modules in the same codebase that correctly bind both fields:

- `pallet_bandwidth::Pallet::on_accept` checks `BandwidthManager::<T>::get(&request.source)` **and** `request.from != manager.0.to_vec()` before honoring a purchase [2](#0-1) .
- `pallet_hyper_fungible_token`'s `on_accept` looks up `ContractToAsset::<T>::get(source, &from)` — keyed by the pair `(source, from)`, not `source` alone [3](#0-2) .
- EVM's `HostManager.onAccept` checks `request.source.equals(hyperbridge())` — but this is a single-purpose contract with no other module competing for the "governance" role on the source chain, so chain-level checking is sufficient there; not so for `HyperbridgeWithdrawalModule`, which is a global built-in intercepted by `id.as_slice() == HYPERBRIDGE_MODULE_ID` for *every* connected chain's `pallet-ismp` [4](#0-3) .

Because the coprocessor (Hyperbridge parachain) is a general-purpose ISMP state machine hosting many pallets/apps and end-user dispatch paths, `request.source` being the coprocessor's state machine id does not imply the message was authored by a trusted treasury/fee-accounting component — it only proves the message crossed a verified consensus/state proof from that chain. Any entity on the coprocessor capable of dispatching an outbound ISMP `Post` request with `to = HYPR-FEE` and an attacker-chosen `body` can cause this module to execute `WithdrawRelayerFees{account: <attacker>, amount: <X>}` on the destination chain, transferring funds out of `RELAYER_FEE_ACCOUNT` to an arbitrary beneficiary.

### Impact Explanation
A successful forgery drains `RELAYER_FEE_ACCOUNT` — the pooled fees escrowed on the destination chain to pay relayers for message delivery (funded via `IsmpDispatcher::dispatch_request`'s fee-collection step at [5](#0-4) ) — to an attacker-controlled account of an attacker-chosen amount. This is a direct "stealing or loss of funds" / "wrong beneficiary or amount" impact against a live custody account shared by all relayers on that chain.

### Likelihood Explanation
Exploitability hinges entirely on whether some component on the coprocessor allows a message with `to = HYPR-FEE` and attacker-controlled `body` to be dispatched cross-chain while `request.from` is not separately checked by the recipient. I could not fully verify, within this codebase snapshot, whether the coprocessor exposes a permissionless "raw dispatch" extrinsic where an ordinary user directly controls both the destination module id (`to`) and `body` of an outbound request (as opposed to every concrete pallet on the coprocessor hardcoding its own `from`/`to` values, as seen in the `dispatch_to_evm` example and the `pallet_bandwidth::dispatch_governance` helper, which always sets `to = manager` and requires `AdminOrigin`). If the coprocessor's ISMP dispatch surface is entirely mediated by pallets that hardcode `to`, this specific path is not reachable by an unprivileged account. What is certain and locally provable is the structural gap itself: this is the only privileged `on_accept` implementation in the repo that authenticates solely by chain id and omits the sender/module check that every sibling implementation performs, which is a direct code-level regression matching the reported bug class (accepting a broader set of callers/identities than intended).

### Recommendation
Add an explicit `request.from` check to `HyperbridgeWithdrawalModule::on_accept`, binding it to a specific, governance-configured treasury/fee-management module id on the coprocessor (mirroring `BandwidthManager::<T>::get(&source)` / `ContractToAsset::<T>::get(source, &from)`), so that only that specific authorized module — not any account or pallet capable of dispatching a message from the coprocessor chain — can trigger `WithdrawRelayerFees`.

### Proof of Concept
1. Identify (or gain access to) any dispatch path on the Hyperbridge coprocessor chain that lets a caller set an outbound ISMP `PostRequest`'s `to` field to `b"HYPR-FEE"` and its `body` to an attacker-chosen payload, targeting the victim destination chain running `pallet-ismp`.
2. Encode `body = Message::WithdrawRelayerFees(WithdrawalRequest { account: <attacker_account>, amount: <RELAYER_FEE_ACCOUNT_BALANCE> })` per [6](#0-5) .
3. Once the message is proof-verified and routed by `IsmpHostRouter::module_for_id` to `HyperbridgeWithdrawalModule` [7](#0-6) , `on_accept` only checks `request.source == coprocessor` and proceeds to transfer funds from `RELAYER_FEE_ACCOUNT` to the attacker's `account` [8](#0-7) , with no verification of which module/account on the coprocessor actually authored the request.

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}
