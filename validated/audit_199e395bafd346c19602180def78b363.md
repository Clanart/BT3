Cross-chain replay of signed calldata authorization due to missing chain-domain separator in `on_accept` signature payload - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
The `SubstrateCalldata::signature` verification in `on_accept` signs only `(local account nonce, runtime_call)`. It contains no `StateMachine`/chain id, genesis hash, or pallet-instance domain separator. Because the `nonce` used is the *destination chain's own* `frame_system` account nonce for the beneficiary — not a value transmitted and bound inside the cross-chain message itself — the exact same signed authorization bytes are valid on every destination chain running this pallet for that beneficiary account, as long as the beneficiary's nonce there happens to match. This is trivially true for any never-before-used account (nonce = 0), which is the common case for a first bridge deposit to a chain.

### Finding Description
In `on_accept`, the beneficiary-authorized runtime call is checked as follows: [1](#0-0) 

The signed payload is `(nonce, runtime_call).encode()`, where `nonce` is fetched fresh from local chain state: [2](#0-1) 

Nothing in this payload identifies which `source`/`dest` `StateMachine`, which chain's genesis, or which pallet instance the authorization was intended for — despite the `PostRequest` itself carrying `source`/`dest`/`from` fields that are otherwise available in scope (`from`, `source` are destructured in the function signature). `SubstrateCalldata` (with its `signature` and `runtime_call` fields) is fully attacker-controlled input placed in the `data` field of the cross-chain `Message`: [3](#0-2) 

Any unprivileged caller can invoke the token bridge's public send/teleport entrypoint specifying an arbitrary `to` (beneficiary), arbitrary `dest` chain, and arbitrary `data` payload while only spending their own tokens (see `SendParams`/`Message.data` in the Solidity and Substrate send paths). Because a previously used signed blob `(nonce=0, runtime_call)` for a given beneficiary is publicly visible on-chain (it travels inside the ISMP request body), an attacker can re-submit the same `data` bytes as the calldata of a brand-new outgoing transfer targeting a *different* destination chain that also runs this pallet, addressed to the same beneficiary. If the beneficiary's account nonce on that new chain is still 0 (the normal case for an account that has never interacted with the pallet there), the exact same signature verifies and the arbitrary `runtime_call` is dispatched with `RawOrigin::Signed(beneficiary)`: [4](#0-3) 

This breaks the intended one-time, chain-specific binding of the beneficiary's authorization: the signature is not scoped to the destination chain/pallet instance it was created for, only to a locally-observable, non-unique nonce value.

### Impact Explanation
An attacker who observes any previously broadcast `(nonce, runtime_call)` signature for a victim beneficiary (visible in any historical ISMP `PostRequest` body for this pallet) can force execution of that same `runtime_call` under the victim's signed origin on any other destination chain deploying this pallet where the victim's nonce happens to coincide (trivially, nonce = 0 for a fresh account). This is unauthorized execution/transaction manipulation performed via an unprivileged bridging call, matching the bounty's "unauthorized transaction or execution" and "logic attacks" categories. The severity depends on what `runtime_call` can be replayed (e.g., `remark`, `transfer`, governance votes, staking operations, proxy additions) — any dispatchable reachable from a signed origin and not blocked by `BaseCallFilter` is replayable.

### Likelihood Explanation
High for the common case: newly onboarded accounts on any given destination chain start at nonce 0, so any first-time signed authorization intended for chain A is immediately replayable on chain B (or any other chain deploying the pallet) as long as the victim hasn't yet transacted there. The attacker only needs to observe a public signature/calldata pair and call the permissionless send/teleport function with their own funds — no privileged access, malicious relayer, or node compromise is required.

### Recommendation
Bind the signed payload to a chain/domain-specific value in addition to the account nonce, e.g. include the destination `StateMachine` (`dest`), the local pallet's genesis hash or `T::PalletId`, and ideally the `source` module id, before hashing: `(dest_state_machine, genesis_hash_or_pallet_id, nonce, runtime_call).encode()`. This ties the signature to a specific chain/pallet instance so an identical signed blob cannot validate on more than one destination.

### Proof of Concept
1. Deploy two mock runtimes, Chain A and Chain B, each with `pallet-hyper-fungible-token` configured with the same `ContractToAsset`/source mapping and both trusting the same source EVM contract address.
2. Victim beneficiary account (nonce = 0 on both chains) signs `(0u32, runtime_call.encode()).encode()` (e.g., an Sr25519/Ed25519/ECDSA signature per the supported branches) intending to authorize `runtime_call` on Chain A only.
3. Construct `SubstrateCalldata { signature: Some(sig), runtime_call }`, ABI-encode as `Message.data`, and dispatch a `PostRequest` with `dest = ChainA`. `on_accept` on Chain A verifies the signature against nonce 0 and dispatches `runtime_call` as `RawOrigin::Signed(beneficiary)`, then increments the local nonce to 1.
4. Attacker (any unprivileged sender) copies the identical `data` bytes and issues a second, independent `send()`/teleport call from the source chain with `dest = ChainB`, `to = beneficiary`, funding it with their own tokens.
5. On Chain B, `on_accept` fetches beneficiary's nonce, which is still 0 (Chain B nonce namespace is independent of Chain A). The identical signature verifies again, and `runtime_call` is dispatched a second time as `RawOrigin::Signed(beneficiary)` on Chain B — demonstrating cross-chain replay of a signature that was never intended for Chain B.
