### Title
Static ECDH oracle: crafted secret-share message forces victim to publish `enc_key * K` for an attacker-chosen point `K` via the blame proof - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the OpenClaw token-leakage class (a lower-trust caller coerces a trusted party into returning a credential derived from a long-term secret), PedPoP's blame mechanism returns an `EncryptionKeyProof` that publicly reveals `e * K` — the raw ECDH output of the victim's long-term encryption key `e` — where `K` (`msg.key`) is a group element fully chosen by the accusing/sending party. The victim computes and discloses this DH value without ever checking whether the sender legitimately derived the message or whether `K` is related to the victim's own key material.

### Finding Description
In `Decryption::decrypt` (`crypto/dkg/pedpop/src/encryption.rs:469-501`), for every received `EncryptedMessage` the recipient computes `key = ecdh(&self.enc_key, msg.key)` — i.e., `enc_key * msg.key` — decrypts the ciphertext, and produces `EncryptionKeyProof { key, dleq }` where `dleq` proves the revealed `key` equals `enc_key * msg.key` against the recipient's registered public encryption key.

`msg.key` is deserialized from untrusted bytes (`EncryptedMessage::read`) and its PoP is only *queued* into a batch verifier (`msg.pop.batch_verify(...)` at line 479-485), not verified before `ecdh` is computed and packaged into the proof.

In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-498`), if the decrypted bytes fail `C::F::from_repr` or the share-verification batch fails, the `EncryptionKeyProof` is returned in `PedPoPError::InvalidShare { blame: Some(blame) }` and is subsequently broadcast to *all* participants for public adjudication via `BlameMachine::blame` / `AdditionalBlameMachine::blame` (lines 623-682), which verify the DLEq and decrypt the accused message at `decrypt_with_proof` (encryption.rs:366-397).

So a malicious participant `S` can:
1. Choose arbitrary scalar `k`, set `msg.key = k * G`, and produce a valid PoP (they know `k`), or even re-use the victim's own `enc_pub_key` as `msg.key`.
2. Fill `msg` with garbage ciphertext.
3. The victim's `calculate_share` fails `from_repr`/share verification, emitting a blame proof that reveals `enc_key_victim * K` — a DH output of the victim's long-term secret on an attacker-selected base point, authenticated by a DLEq proof so everyone accepts it.

This is a textbook static-ECDH (static-gap-DH) oracle. The PoP binds `k` to the sender but does not prevent the oracle: knowledge of `k` is required, yet the attacker trivially has it for a `K` they generated. The comment at `encryption.rs:99-100` acknowledges reuse leaks messages, and the PoP (lines 84-90) was added precisely because blame disclosure of ECDH keys is dangerous — but it only prevents *claiming another party's* key, not forcing disclosure of a DH value on an attacker-fresh point.

### Impact Explanation
The leaked `e * K` is a raw ECDH output, computed *before* the `context` domain separation inside `cipher()` (encryption.rs:101-133). If the victim's `enc_key` is ever reused across sessions or contexts (the `Encryption` key is per-machine but `Encryption::new` gives no uniqueness guarantee tying it to `context`), the oracle output on `K` decrypts any message encrypted to the same `(e, K)` pair under a different context. More generally, a static ECDH oracle on a long-term secret is exactly the "credential crossing the trust boundary" primitive: an unprivileged party obtains authenticated DH outputs of a secret that should never leave the victim, enabling shared-key computation for any point of their choosing and undermining the confidentiality assumptions the per-message-key design was built to preserve. Repeated queries with related `K` values can be combined for further cryptanalytic leverage depending on the curve.

### Likelihood Explanation
Fully reachable by any DKG participant with public inputs only: they send one malformed `EncryptedMessage` (valid PoP trivially producible since they choose `k`) and the honest victim's `calculate_share` deterministically emits the blame proof containing `e * K`, which the protocol then broadcasts. No collusion, no timing, no unsafe code required. Severity Medium: it leaks DH outputs of a long-term secret rather than the secret itself, and full exploitation toward share/key recovery requires key reuse or further cryptanalysis, consistent with the source advisory's Medium rating.

### Recommendation
Bind the blame-disclosed key to the message context and enforce point validation before computing `ecdh`: (1) derive the published proof key from `cipher`'s transcript output rather than raw `e * K` (already context-bound), or include `context` in the DLEq transcript for the revealed point — note `encryption_key_transcript` (encryption.rs:326-330) does include `context`, but the disclosed value `key` is still the context-free `e * K`; (2) verify `msg.pop` synchronously before producing the `EncryptionKeyProof` so a proof is only emitted for authenticated messages; (3) reject `msg.key` values equal to any registered `enc_keys` value or previously seen per-message key, preventing replay/co-option forcing disclosure on meaningful points.

```rust
// Attacker S in a PedPoP session with victim V (victim enc secret e, pub E = e*G):
let k = C::F::random(&mut rng);
let malicious_msg = EncryptedMessage {
  key: C::generator() * k,                                  // attacker-chosen K
  pop: SchnorrSignature::sign(&Zeroizing::new(k), nonce,    // valid PoP: knows k
        pop_challenge::<C>(ctx, pub_nonce, k*G, S, garbage.as_ref())),
  msg: Zeroizing::new(SecretShare(garbage_bytes)),          // invalid scalar bytes
};
// Victim: calculate_share -> encryption.decrypt computes ecdh(e, K) = e*K,
// decrypts garbage, builds EncryptionKeyProof { key: e*K, dleq }.
// C::F::from_repr fails (or share verification fails) =>
//   PedPoPError::InvalidShare { participant: S, blame: Some(proof) }
// proof.key = e*K is published to all participants via AdditionalBlameMachine::blame,
// which accepts it after verifying dleq against E and K.
// => attacker obtained an authenticated DH output of victim's long-term secret
//    on a base point of their choice; if e is reused in another context,
//    that output directly yields the ChaCha20 key for messages encrypted to (e, K).
```
