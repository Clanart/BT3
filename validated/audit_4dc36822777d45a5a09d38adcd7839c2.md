## Finding: `placeOrder` Predispatch Sweep Pulls Entire Dispatcher Balance — Leftover/Dust Tokens From Other Orders Can Be Stolen Into a New Order's Escrow

### Title
Shared `CallDispatcher` Balance Not Isolated Per-Order in `placeOrder` Predispatch Sweep Allows Cross-Order Theft of Leftover Tokens - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` sweeps input tokens from the shared `CallDispatcher` singleton by reading `IERC20(token).balanceOf(dispatcher)` — the dispatcher's **total** current balance — rather than only the amount actually produced by the current order's own predispatch call. [1](#0-0) 
The `_params.dispatcher` is a single global `CallDispatcher` contract shared by every user and every order, with no per-caller or per-order isolation — it is a generic call executor that blindly forwards arbitrary `to`/`data`/`value` from the order's `predispatch.call` field. [2](#0-1) 

### Finding Description
In the predispatch branch of `placeOrder`:
1. The caller's predispatch assets are pushed to the dispatcher, then `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` executes attacker-controlled calls.
2. For each token in `order.inputs`, the code snapshots the gateway's own balance (`balancesBefore[i]`), then builds a sweep call that transfers the dispatcher's **entire** balance of that token to the gateway. [3](#0-2) 
3. The "received" delta (gateway balance after minus before) is used to populate `order.inputs[i].amount`, which is then escrowed under the new order's commitment. [4](#0-3) 

Critically, the sweep is keyed only on `order.inputs` — tokens the *current* order lists — and pulls **all** dispatcher-held balance of that token, regardless of who deposited it or when. Nothing ties the swept amount to only the assets the current caller supplied to the dispatcher in this same call.

Compare this to `_execute` (used in the output/fill path), which explicitly treats *any* residual dispatcher balance as protocol dust and sweeps/logs it as such via `DustCollected`. [5](#0-4) 
No equivalent unconditional dust-sweep exists in the `placeOrder` predispatch path for tokens *not* listed in `order.inputs` — such leftover balances simply remain parked on the shared `CallDispatcher` indefinitely.

This creates the exploit path described in the question: if any order's `predispatch.call` (attacker- or user-controlled, arbitrary calldata) leaves a residual balance of some token on the shared dispatcher (e.g., DEX swap slippage, multi-hop remainder, an unlisted output token from the predispatch swap), that balance is not attributable to any specific order and sits available to whoever next lists that same token in their own `order.inputs` with a predispatch call. Because the sweep uses `balanceOf(dispatcher)` unconditionally, the next caller's order will absorb that leftover into its own escrow — funds it never supplied — as long as `received >= order.inputs[i].amount` (no revert; only `received < amount` is flagged as insufficient).

The predispatch step also lacks any binding to `msg.sender` or the specific transaction that produced the leftover — the dispatcher is a bare pass-through, so any account can trigger `dispatch()` calls that route tokens there, and any subsequent `placeOrder` caller can be the one to sweep them out into their own commitment's escrow.

### Impact Explanation
Because escrow is what backs `fillOrder`/`cancelOrder` payouts, an attacker who can direct unrelated/leftover dispatcher balance into their own order's escrow effectively:
- Steals another party's residual/dust tokens by wrapping them into their own order and later withdrawing them via `fillOrder` proceeds or `cancelOrder` refund.
- Can create escrow balances not actually backed by the attacker's own contribution, undermining the 1:1 relationship between what a user deposited and what is redeemable — directly matching the "wrongful mint/unlock/withdrawal/refund/redirect of protocol-controlled or user escrowed assets" impact category.

### Likelihood Explanation
Exploitation requires: (a) some transaction (by any user, potentially even the attacker's own prior order, or a naturally slippage-producing swap) to leave a token balance on the shared `CallDispatcher` that is not swept because it wasn't listed in that order's `inputs`; and (b) the attacker subsequently places an order listing that exact leftover token as an input with a minimal predispatch contribution. Since predispatch calldata is fully attacker-controlled and the dispatcher performs no allowlisting or per-caller accounting, an attacker can also self-seed the leftover in one order and reap it in a following order within the same or a later transaction — making the "duplicate/reordered batch item" scenario in the prompt a variant of the same underlying flaw: the dispatcher-balance sweep has no per-order uniqueness or provenance guarantee.

### Recommendation
- Do not read `balanceOf(dispatcher)` unconditionally in the sweep. Instead, track the exact delta produced by *this* order's predispatch execution (e.g., snapshot dispatcher balances immediately before transferring the caller's predispatch assets and immediately after `dispatch(order.predispatch.call)`, then only sweep that delta), or require the dispatcher to be deployed/cleared per-order (e.g., ephemeral clone/proxy per `placeOrder` call) so no state can persist across orders.
- Treat any dispatcher balance not attributable to the current order's own predispatch delta as protocol dust to be swept via governance (`SweepDust`) rather than something a future arbitrary order can claim.
- Add explicit tests placing an order whose predispatch intentionally strands a non-listed token on the dispatcher, then verify a second, unrelated order cannot sweep that stranded balance into its own escrow.

### Proof of Concept
1. User A calls `placeOrder` with a `predispatch.call` that swaps token X for token Y via an external DEX (attacker- or user-supplied arbitrary calldata routed through `CallDispatcher.dispatch`), but lists only token Z (not Y) in `order.inputs` — e.g., a partial-path order where Y is an unintended byproduct/slippage remainder. Token Y balance (`balanceOf(dispatcher)`) remains on the shared `CallDispatcher` after User A's `placeOrder` completes, since predispatch sweeping only iterates `order.inputs` tokens (Z), never touching Y. [6](#0-5) 
2. Attacker B calls `placeOrder` with `order.inputs` listing token Y with `amount = balanceOf(dispatcher)_Y` (observable on-chain), and a trivial/no-op `predispatch.call` (empty `Call[]`) plus a minimal (even 1-wei) `predispatch.assets` entry for some token to satisfy the `amount == 0` check and take the predispatch branch. [7](#0-6) 
3. The sweep step in Attacker B's `placeOrder` call reads `IERC20(Y).balanceOf(dispatcher)`, which still includes User A's stranded balance, and transfers all of it to the gateway; `received >= order.inputs[i].amount` so no dust event fires and the full amount is credited to Attacker B's escrow under their own commitment. [4](#0-3) 
4. Attacker B then calls `fillOrder`/`cancelOrder` to redeem the escrow, walking away with token Y that User A's predispatch call produced and that Attacker B never funded.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
