## Title
Unhandled KeyError in NFT metadata-update handling can halt wallet coin-state processing - ([File: chia/wallet/nft_wallet/nft_puzzle_utils.py])

## Summary
`update_metadata`/`prepend_value` in `chia/wallet/nft_wallet/nft_puzzle_utils.py` process an attacker-controlled `-24` (metadata update) condition emitted by an NFT's inner puzzle solution without validating that the referenced metadata key already exists in the metadata dict, and without validating the shape/emptiness of the value the CVE hint (mishandling of an "empty" field leading to unexpected access) maps to. This mirrors the FFmpeg SDP bug class: a value the parser assumes is well-formed/present is dereferenced without a defensive check, and a crafted "empty"/missing-key case reaches an unguarded access.

## Finding Description
`get_metadata_and_phs()` is invoked from `puzzle_solution_received()` in `chia/wallet/nft_wallet/nft_wallet.py` whenever a wallet processes a coin-state update for an NFT it owns: [1](#0-0) 

For every condition with opcode `-24` in the p2 puzzle's output, `update_metadata()` is called: [2](#0-1) 

which delegates to `prepend_value()`: [3](#0-2) 

`prepend_value` performs `metadata[key] == b""` / `metadata[key].insert(...)` using **direct dict indexing** (`metadata[key]`), not `.get(key)`. If the `-24` condition supplies a `key` atom that does not already exist in `new_metadata` (built from `nft_program_to_metadata`), this raises an uncaught `KeyError`. Similarly, if the existing value under `key` is neither `b""` nor a list (e.g., an atom of some other type), `.insert()` will raise `AttributeError`.

`get_metadata_and_phs` is called synchronously from `NFTWallet.puzzle_solution_received`, which is invoked by the wallet during coin-state sync processing for any NFT coin spend the wallet is notified about — i.e., it is reachable simply by an offer counterparty/any party spending an NFT that the target wallet is tracking (e.g., after receiving/transferring an NFT), analogous to the FFmpeg bug being reachable via crafted, untrusted input (`sprop-parameter-sets`) that the parser assumed to be well-formed.

## Impact Explanation
An attacker who controls the NFT's inner-puzzle solution (e.g., a malicious transfer/offer counterparty, or a spend crafted against an NFT the victim's wallet is tracking) can emit a `-24` metadata-update condition referencing a key absent from the existing metadata dict (or of an incompatible on-chain type). This throws an unhandled `KeyError`/`AttributeError` inside `puzzle_solution_received`, which is on the wallet's synchronous coin-processing path. Depending on how far up the call stack this exception propagates without being caught, it can interrupt/abort the wallet's coin-state processing for that sync batch, effectively denying the wallet the ability to properly index/update the NFT (and potentially subsequent coins in the same batch), a spend-triggered processing halt on the wallet side.

## Likelihood Explanation
Likelihood is moderate: it requires the victim wallet to already be tracking/receiving the specific NFT (common in normal transfer/offer/DID flows), and the attacker must control (or induce) the inner puzzle's condition output containing a `-24` condition with a bogus key — achievable by anyone constructing an alternative inner puzzle/solution for an NFT sent to the victim, or via a crafted offer/transfer. No special privileges beyond normal wallet-to-wallet NFT transfer are required.

## Recommendation
- In `prepend_value`, use `metadata.get(key)` and validate that the key exists and that the existing value is a list (or `b""`) before mutating; otherwise treat the update condition as invalid and skip it rather than raising.
- Wrap `update_metadata` invocation in `get_metadata_and_phs` in a `try/except` that logs and ignores malformed `-24` conditions rather than propagating an exception into wallet sync code.
- Add fuzz/unit tests for `-24` conditions referencing unknown keys and non-list existing values to ensure the wallet degrades gracefully instead of raising.

## Proof of Concept
1. Mint/receive an NFT with metadata that does not contain a given key, e.g. metadata `[(b"u", ["https://..."])]` (no `b"h"` key).
2. Craft an NFT inner-puzzle solution whose p2 puzzle outputs a condition `(-24 <updater> (h . <value>))` referencing key `b"h"`, which is absent from current metadata.
3. Spend the NFT coin with this solution and have the victim wallet observe/sync the coin state (e.g., via `puzzle_solution_received` → `get_metadata_and_phs` → `update_metadata` → `prepend_value`).
4. Observe `KeyError: b'h'` raised inside `prepend_value` at `chia/wallet/nft_wallet/nft_puzzle_utils.py:161`, propagating uncaught through `get_metadata_and_phs` and `puzzle_solution_received`.

Note: I was not able to fully trace, within the remaining investigation budget, whether an outer exception handler in `wallet_state_manager.py`'s sync loop catches and simply logs this exception versus allowing it to abort/retry the whole sync batch — that would materially affect the concrete severity (isolated NFT indexing failure vs. broader sync halt). This should be verified with a live Devin session before treating the impact as more than a localized processing failure.

def prepend_value(key: bytes, value: Program, metadata: dict[bytes, Any]) -> None:
    """
    Prepend a value to a list in the metadata
    :param key: Key of the field
    :param value: Value want to add
    :param metadata: Metadata
    :return:
    """
    if value != Program.to(0):
        if metadata[key] == b"":
            metadata[key] = [value.as_python()]
        else:
            metadata[key].insert(0, value.as_python())

def update_metadata(metadata: Program, update_condition: Program) -> Program:
    """
    Apply conditions of metadata updater to the previous metadata
    :param metadata: Previous metadata
    :param update_condition: Update metadata conditions
    :return: Updated metadata

def get_metadata_and_phs(unft: UncurriedNFT, solution: SerializedProgram) -> tuple[Program, bytes32]:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(Program.from_serialized(solution)))
    metadata = unft.metadata
    puzhash_for_derivation: bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.list_len() < 2:
            # invalid condition
            continue
        condition_code = condition.first().as_int()
        log.debug("Checking condition code: %r", condition_code)
        if condition_code == -24:
            # metadata update
            metadata = update_metadata(metadata, condition)
            metadata = Program.to(metadata)
