## Title
IntentGatewayV2 (Tron) trusts an unregistered chain's `from` address by defaulting to `address(this)`, letting a CREATE2-replayed attacker deployment forge `RedeemEscrow`/`RefundEscrow` messages and drain escrow - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The external report's core defect is a function that trusts an attacker-supplied contract address as an authoritative price/state source instead of checking it against a registry (`accreditedAddresses`). The Tron variant of `IntentGatewayV2` has the same class of defect: its `instance()` lookup silently falls back to `address(this)` for any state machine that hasn't been explicitly registered as a peer, and `authenticate()` uses that fallback as the trust anchor for accepting cross-chain escrow-release messages.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
...
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
``` [2](#0-1) 

`onAccept` calls `authenticate()` for `RedeemEscrow`/`RefundEscrow` and, once it passes, calls `withdraw()`, which drains `_orders[commitment][token]` to whatever beneficiary the request carries: [3](#0-2) 

For any state machine `X` that Hyperbridge routes messages for but that has never received a `NewDeployment` registration for this particular Tron gateway, `instance(X)` returns `address(this)` instead of reverting. Because this Solidity contract is deployed via deterministic CREATE2 (the sibling non-Tron contract's comments explicitly describe "identical across chains under deterministic CREATE2"), the exact same bytecode+salt combination produces the exact same 20-byte address on any EVM/TVM-compatible chain. An attacker can:
1. Redeploy the identical `IntentGatewayV2` bytecode with the same CREATE2 salt on a legitimate Hyperbridge-connected chain `X` that the Tron gateway has not yet registered as a peer, obtaining a contract at the identical address `address(this)`.
2. Call `initialize()` on their own deployment with attacker-controlled `host`/`dispatcher` params, since `initialize()` is a normal `initializer`-gated call open to whoever deploys the proxy.
3. From that attacker-controlled instance (whose address matches the Tron gateway's address by construction), dispatch a `RedeemEscrow` or `RefundEscrow` `PostRequest` with `source = X`, `from = abi.encodePacked(address(this))`.
4. On the Tron side, `instance(X)` falls back to `address(this)` (Tron gateway's own address) because `X` was never registered, and `module` (derived from `request.from`) equals that same address by construction — `authenticate()` passes.
5. `withdraw()` then transfers any live `_orders[commitment][token]` balance to a beneficiary of the attacker's choosing. Order commitments and their escrowed token/amount are public (from `placeOrder` events / order structs), so the attacker can target any live escrow.

This is the same broken invariant as the external report: a public entry path trusts a value derived from an attacker-controlled/attacker-reachable address instead of validating it against an actual registry, and the "default" behavior (fallback to `address(this)`) silently substitutes for the missing check rather than rejecting.

Note that the sibling, non-Tron implementation used elsewhere in the repo (`evm/src/apps/intentsv2/IntentsBase.sol` / `ExtrinsicIntents.sol`) does **not** have this flaw — its `_instance()` reverts with `UnknownInstance` for unregistered chains, and its Foundry test explicitly asserts that behavior: [4](#0-3) 

The Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated to match, leaving the vulnerable fallback in place.

### Impact Explanation
Unauthorized fund loss: an unprivileged attacker can forge cross-chain `RedeemEscrow`/`RefundEscrow` messages against the Tron `IntentGatewayV2` and drain escrowed user input tokens to an arbitrary beneficiary, without ever filling or being selected as a solver for the targeted order. This is a direct "stealing/loss of funds" and "false state acceptance via wrong module binding" impact matching the bounty scope.

### Likelihood Explanation
The attack requires only: (a) a Hyperbridge-connected chain not yet registered as a peer for the Tron gateway (a normal, expected transient state during progressive chain rollout since registrations happen one-by-one via governance `NewDeployment`), and (b) the ability to redeploy the open-source gateway bytecode with the same CREATE2 salt on that chain and self-initialize it — both trivial for any user, no relayer/prover/governance compromise needed. This makes it a realistic, unprivileged, single-actor attack.

### Recommendation
Make `instance()` revert (as the non-Tron `IntentsBase._instance()` already does) instead of defaulting to `address(this)` when a state machine has no registered peer:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```
Only allow a "self" match for the gateway's own home chain (an explicit constant), never as an implicit default for arbitrary unregistered chains.

### Proof of Concept
1. Note that the Tron `IntentGatewayV2` has not registered chain `X` (e.g. a newly onboarded Hyperbridge state machine) via `NewDeployment`.
2. Deploy the identical `IntentGatewayV2` implementation/proxy bytecode with the matching CREATE2 salt on chain `X`, yielding a contract at the same address as the Tron gateway. Call `initialize()` with a self-controlled `host`/`dispatcher`.
3. From this attacker-deployed instance, dispatch a `PostRequest` (via the attacker's own fake/controlled dispatcher-to-host path that ultimately reaches the real Hyperbridge network as `source = X`) with body `bytes.concat(bytes1(uint8(RequestKind.RedeemEscrow)), abi.encode(WithdrawalRequest({commitment: knownCommitment, tokens: knownOrder.inputs, beneficiary: attackerAddress})))` and `from = abi.encodePacked(gatewayAddress)`.
4. On delivery, Tron `IntentGatewayV2.onAccept` → `authenticate()` computes `instance(X) == address(this) == module`, passes, and `withdraw()` transfers the escrowed `knownOrder.inputs` tokens to `attackerAddress`, as shown in `withdraw()`: [3](#0-2) .
