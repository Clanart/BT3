## Finding

### Title
Missing chain ID (domain separation) in the EVM↔Sei address association signature scheme allows cross-chain/cross-context signature replay - (File: `precompiles/addr/addr.go`, `app/ante/evm_checktx.go`, `utils/helpers/associate.go`)

### Summary
The `Associate`/`AssociatePubKey`/`AssociateTx` mechanism that links an EVM address to a Sei address recovers the signer's pubkey from an arbitrary, attacker-suppliable `customMessage` hashed with a bare `keccak256`/EIP-191 personal-sign envelope. Nowhere in this hash is Sei's chain ID, a contract/verifying-contract address, or any other domain separator included, so any personal-sign signature a user has ever produced for that exact string — on any chain or in any context — can be relayed by an unrelated third party into Sei's association flow.

### Finding Description
The `associate` precompile method recovers `evmAddr`, `seiAddr` and `pubkey` purely from `keccak256(customMessage)` and the supplied `v, r, s`: [1](#0-0) 

The exact same pattern (raw `customMessage` hash, no chain ID/domain separator) is used for the native `MsgEVMTransaction`-wrapped `AssociateTx` in the ante handler: [2](#0-1) 

and is duplicated verbatim across every legacy precompile version (`v575` through `v640`), e.g.: [3](#0-2) 

Once the signature recovers a valid pubkey/address pair, `AssociateAddresses` is called unconditionally by any caller who submits the (message, v, r, s) tuple — it is not restricted to the account owner submitting their own transaction, by design (this lets a sponsor with no funds relay a user's off-chain signature). Critically, `AssociateAddresses` does not just record a mapping — it also **migrates funds**: [4](#0-3) [5](#0-4) 

`MigrateBalance` unconditionally moves all spendable coins and wei balance from the EVM-cast Sei address to the newly-associated true Sei address, and deletes the cast account if it has no locked coins.

The codebase itself already recognizes this exact bug class and has fixed it for one specific path: EIP-7702 `SetCode` authorizations. The comment in `AuthorityToPreAssociate` explicitly describes the risk of a chain-id-agnostic signature being replayed to force-associate a victim and "migrat[e] their direct-cast balance and orphan[] staking/distribution state," and that function was hardened with an explicit chain-ID equality check: [6](#0-5) 

No equivalent chain ID (or any other domain-separation) check exists for the `Associate`/`AssociatePubKey`/`AssociateTx` signature schemes, so the same class of forced-association/forced-migration attack that was fixed for `SetCode` authorities remains open here.

### Impact Explanation
Because the hashed payload contains no chain ID, contract address, or nonce, any EIP-191 personal-sign signature a user has ever produced for the literal association message text (or any other message an attacker gets them to sign, since `customMessage` is fully attacker-controlled and only needs to match what the victim actually signed) can be captured off-chain (from another chain, testnet, a phishing site, or any dApp using the same personal-sign flow) and replayed by an unrelated third party into Sei's `associate` precompile or `AssociateTx`. This forces an unrequested, third-party-triggered state transition: it creates the address association, overwrites the account's pubkey, and unconditionally moves the victim's spendable/wei balance out of the EVM-cast address into the newly-derived Sei address — all without the victim submitting any Sei transaction or intending this action to occur on Sei at that time. This is exactly the "cross-chain replay of a signature schema missing chain ID" bug class from the reference report, reachable by any public RPC/precompile caller.

### Likelihood Explanation
The precompile and native message are permissionlessly callable by anyone holding a (message, signature) pair — this is intentional (to allow gasless/sponsored association), but it also means an attacker only needs to obtain any signature the victim produced for the fixed association string (or, for `AssociateTx`/`associatePubKey`, an even weaker bar since `associatePubKey` needs no signature verification against a message beyond the pubkey itself) in any context to trigger it on Sei. The codebase's own explicit fix and reasoning for the structurally identical `SetCode` authority case confirms the project considers this attack pattern realistic and worth chain-ID gating.

### Recommendation
Bind the association signature to Sei's chain ID (and ideally a purpose-specific domain tag / contract address / nonce), mirroring the fix already applied to `AuthorityToPreAssociate` for EIP-7702 authorizations, e.g. requiring `customMessage` to embed the chain ID and validating it on-chain before hashing/recovering, so a signature produced for one chain/context cannot be replayed to force association (and the accompanying balance migration) on another.

### Proof of Concept
1. A victim signs the fixed personal-sign string `"Please sign this message to link your EVM and Sei addresses. No SEI will be spent as a result of this signature.\n\n"` in an unrelated context (e.g., a different network, a phishing page mimicking a wallet-linking flow, or a testnet deployment of the same dApp), producing `(v, r, s)`.
2. An attacker who observes this signature (from another chain's mempool/explorer, or a compromised frontend) submits it directly to Sei mainnet's `addr` precompile: `addr.associate(v, r, s, eip191Envelope(ASSOCIATE_MESSAGE))`, exactly as exercised in the existing test harness: [7](#0-6) 
3. `CheckAndDecodeSignature`/`associate` recovers the victim's EVM/Sei address pair from the replayed signature and calls `AssociateAddresses`, which immediately migrates the victim's `usei`/wei balances from their cast address to the newly associated address — a state change the victim never submitted or authorized on Sei at that time.

func HandleAssociateTx(ctx sdk.Context, ek *evmkeeper.Keeper, atx *ethtx.AssociateTx, readOnly bool) (sdk.Context, error) {
	V, R, S := atx.GetRawSignatureValues()
	V = new(big.Int).Add(V, utils.Big27)
	// Hash custom message passed in
	customMessageHash := crypto.Keccak256Hash([]byte(atx.CustomMessage))
	evmAddr, seiAddr, seiPubkey, err := helpers.GetAddresses(V, R, S, customMessageHash)
	if err != nil {
		return ctx, err
	}
	_, isAssociated := ek.GetEVMAddress(ctx, seiAddr)
	if isAssociated {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInvalidRequest, "account already has association set")
	}
	if !IsAccountBalancePositive(ctx, ek, seiAddr, evmAddr) {
		return ctx, sdkerrors.Wrap(sdkerrors.ErrInsufficientFunds, "account needs to have at least 1 wei to force association")
	}
	if !readOnly {
		if err := AssociateAddress(ctx, ek, evmAddr, seiAddr, seiPubkey); err != nil {
			return ctx, err
		}
	}
	return ctx.WithPriority(antedecorators.EVMAssociatePriority), nil
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}

// already associated. Mirroring validateAuthorization is essential to security: the
// authorization sig hash is computed from the auth's own ChainID, so recovery and
// auth.Authority() succeed for an authorization signed for ANY chain. Without these checks a
// publicly-visible authorization a user signed for another chain (e.g. Ethereum mainnet)
// could be replayed in a sponsored Sei SetCode tx to force-associate them — migrating their
// direct-cast balance and orphaning staking/distribution state — even though the EVM skips
// the wrong-chain authorization and installs no delegation.
func AuthorityToPreAssociate(ctx sdk.Context, k AuthorizationStateReader, auth ethtypes.SetCodeAuthorization) (common.Address, sdk.AccAddress, cryptotypes.PubKey, bool) {
	// Chain ID must be null or match the local chain.
	if !auth.ChainID.IsZero() && auth.ChainID.CmpBig(k.ChainID(ctx)) != 0 {
		return common.Address{}, nil, nil, false
	}
