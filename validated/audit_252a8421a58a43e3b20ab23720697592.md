### Title
Unescaped attacker-controlled bytes embedded in ProtoJSON parser error `absl::Status` messages enable log injection when applications log parse failures - (File: `src/google/protobuf/json/internal/lexer.cc`)

### Summary
CVE-2019-7351 is a classic log-injection/log-forging bug: ZoneMinder took an attacker-controlled string (`message=` parameter) and wrote it verbatim into a log view without neutralizing control characters, letting an attacker inject fake log lines/records. The Protobuf analog is in the ProtoJSON parser's error-reporting path: `JsonLocation::Invalid()` builds human-readable `absl::Status` error messages that directly embed raw, attacker-controlled bytes from the untrusted JSON input (e.g., the literal offending character or excerpted token text), with no escaping of control characters such as `\n`/`\r`. If a consuming application logs these status messages (a very common pattern for JSON-parsing diagnostics), an attacker can inject newlines/control sequences into the application's log stream, splitting or forging log entries — the same failed invariant as the ZoneMinder issue, just moved from "log view HTML" to "log file/stream."

### Finding Description
`JsonLocation::Invalid()` constructs the failure message like this: [1](#0-0) 

Note that `message` (passed in by call sites such as `PeekKind()`) is formatted with `%c`/`%s` directly from the raw input byte/text, e.g.: [2](#0-1) 

The only post-processing applied is `HardenAgainstHyrumsLaw()`, which is explicitly documented as inserting *extra whitespace* to defeat brittle string-matching — it is **not** a security control and does not escape or strip control characters: [3](#0-2) 

So a byte such as `\n`, `\r`, or other control characters appearing at the point of a JSON syntax error is carried through unmodified into the returned `absl::InvalidArgumentError` message. This is architecturally the same failure as ZoneMinder's: an attacker-controlled value flows into a text sink (there: an HTML log view; here: a status/log message) with no invariant enforced that the value cannot contain record-delimiting characters (newline).

By contrast, Protobuf's TextFormat/JSON *printers* (the "known good" pattern) do enforce this invariant for message field values: `TextFormat::FastFieldValuePrinter::PrintString` and `TextFormat::Printer::HardenedPrintString` explicitly escape newlines and other control bytes via `CEscape`/`\n`-substitution before emitting field values into DebugString/TextFormat output: [4](#0-3) [5](#0-4) 

This shows the project is aware that attacker-controlled string content must be escaped before being placed in human-readable/log-adjacent output — but that discipline is not applied to the raw excerpt/character embedded in JSON lexer/parser error messages.

### Impact Explanation
If the host application (Java/C++/Python/etc. binding user) logs the `absl::Status`/exception message returned from ProtoJSON parsing failures — a routine debugging/observability pattern — an attacker who controls the JSON payload sent to a public parse API can inject `\n`/`\r` and other control bytes into that log line. This enables classic log-forging consequences: fabricating additional, seemingly legitimate log entries, splitting a single log record into multiple lines to mislead log analysis/SIEM tooling, or (depending on the log sink, e.g. a web-based log viewer) reflected content injection analogous to the original ZoneMinder issue. Confidentiality and availability are not affected; this is an integrity issue on log data, matching the Medium severity classification of the original CVE (CIA vector C:N/I:H/A:N).

### Likelihood Explanation
Likelihood is meaningful but bounded: it requires (a) the consuming application to accept untrusted JSON via a Protobuf JSON-parsing API (`JsonStringToMessage` / language-specific bindings) and (b) the application to log the resulting error message verbatim, which is a common but not universal practice. No privileged access or unusual conditions are needed — any client sending a malformed/adversarial JSON payload with a strategically placed control character can trigger this, and the process is fully within the "ordinary client sending bounded ProtoJSON" threat model specified.

### Recommendation
Sanitize/escape non-printable and control characters (particularly `\n`, `\r`, and other bytes below 0x20) out of the attacker-influenced portions of `JsonLocation::Invalid()` messages (the offending character in `PeekKind()`'s `%c` format and any other raw-input excerpts threaded through `Invalid()` in `lexer.cc`/`parser.cc`) before they are placed into the returned status message, mirroring the `CEscape`-based approach already used by `TextFormat::FastFieldValuePrinter::PrintString`. Documentation for `JsonStringToMessage` and language bindings should also explicitly warn that returned error strings may contain attacker-influenced bytes and must not be logged/rendered without escaping.

### Proof of Concept
Conceptual reproduction (based on code inspection; not executed in this environment):
1. Call the ProtoJSON parser's public entry point (e.g. `google::protobuf::json::JsonStringToMessage`) with a trusted schema and a malformed JSON payload where the byte at the point of failure is a control character, e.g. a value fragment containing a raw `\n` where a JSON token is expected — this reaches `JsonLexer::PeekKind()`'s default branch: `return Invalid(absl::StrFormat("unexpected character: '%c'", c));` with `c == '\n'`.
2. `JsonLocation::Invalid()` (lines 84–103 of `lexer.cc`) formats this into the returned `absl::Status` message without escaping the embedded `\n`.
3. An application that does `ABSL_LOG(ERROR) << status.message();` (or an equivalent log call) on parse failure will emit a log record containing an embedded newline, effectively injecting an attacker-controlled additional "log line" — the direct analog of the ZoneMinder `message=` log-injection payload.

I was not able to execute this PoC in the current read-only environment; the trace is based on static analysis of `lexer.cc`/`parser.cc`'s `Invalid()` call sites and the absence of any escaping step besides the non-security `HardenAgainstHyrumsLaw` whitespace obfuscation.

// Randomly inserts bonus whitespace of a few different kinds into a string.
//
// This utility is intended to make error messages hostile to machine
// interpretation as a Hyrum's Law countermeasure, without potentially confusing
// human readers.
void HardenAgainstHyrumsLaw(absl::string_view to_obfuscate, std::string& out) {
  // Get some simple randomness from ASLR, which is enabled in most
  // environments. Our goal is to be annoying, not secure.
  static const void* const kAslrSeed = &kAslrSeed;
  // Per-call randomness from a relaxed atomic.
  static std::atomic<uintptr_t> kCounterSeed{0};

  constexpr uint64_t kA = 0x5851f42d4c957f2dull;
  constexpr uint64_t kB = 0x14057b7ef767814full;

  uint64_t state = absl::bit_cast<uintptr_t>(kAslrSeed) + kB +
                   kCounterSeed.fetch_add(1, std::memory_order_relaxed);
  auto rng = [&state, &kA, &kB] {
    state = state * kA + kB;
    return absl::rotr(static_cast<uint32_t>(((state >> 18) ^ state) >> 27),
                      state >> 59);
  };
  (void)rng();  // Advance state once.

  out.reserve(to_obfuscate.size() + absl::c_count(to_obfuscate, ' '));
  for (char c : to_obfuscate) {
    out.push_back(c);
    if (c != ' ' || rng() % 3 != 0) {
      continue;
    }

    size_t count = rng() % 2 + 1;
    for (size_t i = 0; i < count; ++i) {
      out.push_back(' ');
    }
  }
}

void TextFormat::Printer::HardenedPrintString(
    absl::string_view src, TextFormat::BaseTextGenerator* generator) {
  // Print as UTF-8, while guarding against any invalid UTF-8 in the string
  // field.
  //
  // If in the future we have a guaranteed invariant that invalid UTF-8 will
  // never be present, we could avoid the UTF-8 check here.

  generator->PrintLiteral("\"");
  while (!src.empty()) {
    size_t n = SkipPassthroughBytes(src);
    if (n != 0) {
      generator->PrintString(src.substr(0, n));
      src.remove_prefix(n);
      if (src.empty()) break;
    }

    // If repeated calls to CEscape() and PrintString() are expensive, we could
    // consider batching them, at the cost of some complexity.
    generator->PrintString(absl::CEscape(src.substr(0, 1)));
    src.remove_prefix(1);
  }
  generator->PrintLiteral("\"");

bool ContainsCharactersToCEscape(absl::string_view val) {
  bool needs_escape = false;
  for (unsigned char c : val) {
    needs_escape |=
        ((c < 32) | (c > 126) | (c == '"') | (c == '\'') | (c == '\\'));
  }
  return needs_escape;
}

}  // namespace

void TextFormat::FastFieldValuePrinter::PrintString(
    const std::string& val, BaseTextGenerator* generator) const {
  generator->PrintLiteral("\"");
  if (!val.empty()) {
    if (ABSL_PREDICT_FALSE(ContainsCharactersToCEscape(val))) {
      generator->PrintString(absl::CEscape(val));
    } else {
      generator->PrintString(val);
    }
  }
  generator->PrintLiteral("\"");
}
