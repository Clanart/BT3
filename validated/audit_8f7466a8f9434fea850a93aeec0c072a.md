### Title
Bitcoin FROST Schnorr algorithm never normalizes the group key's Y parity, producing BIP-340-invalid signatures for odd-Y aggregate keys - (File: networks/bitcoin/src/crypto.rs)

### Summary
The bug class in CVE-2017-1000071 is a verification path that accepts/validates under a legacy interpretation instead of the protocol's canonical one. Serai's analog lives in `networks/bitcoin/src/crypto.rs`, where the BIP-340 `Hram` and `Schnorr::verify` account for the parity of the nonce point `R` but never normalize the parity of the group key `A`. BIP-340 verification lifts the x-only public key to its even-Y representative; when the FROST group key has odd Y, the emitted signature verifies against `-group_key`, not the actual key, and is rejected on-chain.

### Finding Description
BIP-340 defines the public key as x-only: the verifier computes the effective key as the even-Y lift of the 32-byte encoding. Correctly signing for an odd-Y internal key `A = d·G` requires signing with `d' = q - d` (equivalently, producing `s` that satisfies `s·G = R' + c·(-A)`).

In `crypto.rs`:

- `Hram::hram` hashes only `x(R) || x(A) || m` and negates `c` when `R` has odd Y, so the signer effectively computes `r - c·a` and later negates `s` to get `-r + c·a` with an even-Y `R'`. This fixes nonce parity only.
- `Schnorr::verify` (lines 139-150) calls the inner FROST `verify`, which checks `s·G == R + c·A` against the *full* `group_key`, then conditionally negates `s` based on `needs_negation(&sig.R)`. No branch ever handles `needs_negation(&group_key)`.

So when `group_key` has odd Y (~50% for any honestly generated DKG key, and forceable by a participant via key offset/addendum influence on the aggregate key), the internally verified equation is `s·G = R' + c·A`, while a Bitcoin verifier checks `s·G = R' + c·(even_lift(A)) = R' - c·A`. The signature is silently emitted as valid yet fails on-chain verification.

### Impact Explanation
For any threshold Bitcoin wallet whose aggregate `group_key` has odd Y, every BIP-340 signature the FROST protocol successfully completes and emits is invalid under Bitcoin consensus rules. Outputs controlled by that key (e.g., key-path Taproot spends of the x-only encoding) cannot be spent with the produced signatures: the signing session reports success while yielding a signature the network rejects. Depending on surrounding key handling, this can render deposited funds unspendable or force repeated failed signing attempts, meeting the "signature produced that does not actually authorize / funds not spendable" impact class.

### Likelihood Explanation
The condition is purely a function of the discrete log of the aggregate key: `group_key` is odd-Y with probability ~1/2 for any DKG output that isn't explicitly constrained to even Y. Nothing in `crypto.rs` constrains it (no offset to force even parity, no check in `verify`). It is reachable with no malicious behavior at all; a participant able to influence the group key or its offset can also deliberately select the odd-parity case.

### Recommendation
Normalize the group key parity for BIP-340 signing: in `sign_share`/`verify`, detect `needs_negation(&group_key)` and, when set, sign as if the secret share were negated — e.g., emit `s` satisfying `s·G = R' + c·(-A)` by negating the final `s` contribution (or equivalently negate `c`'s key term). Concretely, after computing `sum` in `verify`, apply `conditional_select(&sum, &-sum, needs_negation(&group_key))` in addition to the existing `R` parity fix, and ensure `verify_share` is adjusted consistently so share-level blame still validates. Alternatively, force the group key to even Y at key-generation/offset time and assert parity in `Schnorr::verify`.

### Proof of Concept
1. Run FROST key generation for `Secp256k1` until `ThresholdKeys::group_key()` has odd Y (`needs_negation(&group_key) == 1`), or apply an offset that yields odd Y.
2. Complete a signing session with `bitcoin::crypto::Schnorr` over any 32-byte sighash `m`. `verify` succeeds internally (the multiexp statement `R + cA - sG = 0` holds for the true odd-Y `A`), and returns `sig[0..64]` bytes.
3. Submit to a BIP-340 verifier (`XOnlyPublicKey` = `x(group_key)`): the verifier computes `c' = H(x(R') || x(A) || m)` (same `c`), uses `P = even_lift(A) = -A`, and checks `s·G = R' + c'·P = R' - c·A`, which does not hold since the emitted `s` satisfies `s·G = R' + c·A`. Verification fails.

      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
