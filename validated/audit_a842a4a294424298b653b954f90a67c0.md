### Title
Payout transaction's OP_RETURN attribution output is not covered by the user's SIGHASH_SINGLE|ANYONECANPAY signature, allowing the attacker who controls that signature to replace the operator-attribution output without operator cooperation - ([File: core/src/builder/transaction/operator_reimburse.rs], [File: core/src/operator.rs])

### Summary
`Operator::withdraw` (core/src/operator.rs:560-637) verifies the user-supplied `in_signature` against a sighash computed with an attacker-chosen `in_signature.sighash_type` (`calculate_sighash_txin(0, in_signature.sighash_type)`), with no code-level enforcement that the flag must be `SIGHASH_ALL`. `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) builds a 1-input, 3-output payout tx (`output0`=user payout, `output1`=anchor, `output2`=OP_RETURN carrying `operator_xonly_pk`), and only the single input is authorized by the user's Taproot key-spend signature. If that signature uses `SIGHASH_SINGLE|ANYONECANPAY` — the exact flag the code's own error message instructs users to use — the signature commits only to input 0 and the output at the same index (output 0); it does **not** commit to output 2 (the OP_RETURN attribution output) or output 1 (anchor).

### Finding Description
Binding claimed: `operator_xonly_pk` recorded in the OP_RETURN output of the confirmed payout transaction for a given `withdrawal_index` == `self.signer.xonly_public_key` of the operator whose `Operator::is_profitable` check passed and who assembled/broadcast the payout tx.

Trace:
- `Operator::withdraw` (core/src/operator.rs:560-637) fetches `input_prevout`/`in_outpoint` and `out_script_pubkey`/`out_amount`, both attacker-supplied per the threat model ("choose the bytes of a withdrawal UTXO... a Schnorr signature and its sighash flag").
- `is_profitable` (core/src/operator.rs:503-537) validates only the numeric relationship between `input_amount`, `withdrawal_amount`, `bridge_amount_sats`; it has no interaction with output ordering or the OP_RETURN.
- `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) places the operator's identity exclusively in `output2` (`op_return_txout(operator_xonly_pk.serialize())`), while the *only* signature in the transaction is the user's, verified at core/src/operator.rs:630-637 using `in_signature.sighash_type` as supplied by the caller.
- Because the sighash type is taken verbatim from attacker input and not constrained in code, a `SIGHASH_SINGLE|ANYONECANPAY` signature (the flag the code's own wrap_err message asks for) leaves `output2` completely outside the signed message. Any party holding that same signature and `in_outpoint`/`output0` values — which is exactly the attacker/user who produced the signature in the first place — can construct an alternate transaction with identical input and `output0` but a different, missing, or arbitrary `output2` (OP_RETURN), reusing the same valid witness, and get it confirmed instead of the operator's version (e.g., by broadcasting with a higher-fee CPFP anchor before or in place of the operator's broadcast).
- `is_profitable`, `SECP.verify_schnorr` (which only checks input 0's signature, not output 2), and no other guard visible in `Operator::withdraw` ties the confirmed transaction's OP_RETURN content to the operator that actually ran the profitability check and broadcast the tx.

### Impact Explanation
If the confirmed payout tx's OP_RETURN is altered to name a different (or non-existent, or colluding) operator pubkey, the honest operator who ran `is_profitable`, signed/funded and broadcast the correct payout can no longer point to a confirmed on-chain transaction bearing their own pubkey for that withdrawal index — their kickoff/reimbursement claim, which is validated against this OP_RETURN downstream (bridge circuit / kickoff validation, see `core/src/builder/transaction/operator_reimburse.rs:69` doc and `circuits-lib/src/bridge_circuit/mod.rs` OP_RETURN handling), can never succeed for that withdrawal. This is repeatable per withdrawal and does not require operator or verifier compromise, matching "an honest operator permanently unable to be reimbursed" (Critical), and potentially "an operator reimbursed for a payout it never funded" if the attacker names a colluding operator's pubkey instead.

### Likelihood Explanation
The attacker only needs to be the withdrawal-initiating user: they already control `in_outpoint`, the signature, and the sighash flag per the threat model, and the vulnerable flag (`SIGHASH_SINGLE|ANYONECANPAY`) is the one the codebase's own comment/error text expects operators to receive. No key compromise, no operator or verifier privilege, and no reconstruction of `is_profitable` logic is required — the attacker reuses their own already-issued signature. The only requirement is winning a fee/race to get their alternate `output2` variant confirmed instead of (or via RBF replacing) the operator's broadcast, which is a standard, low-cost Bitcoin mempool operation.

### Recommendation
Enforce that `in_signature.sighash_type` used for the payout input must be `SIGHASH_ALL` (or otherwise a flag that commits to every output, including the OP_RETURN and anchor), rejecting `SIGHASH_SINGLE|ANYONECANPAY`/`SIGHASH_NONE` variants in `Operator::withdraw` before calling `create_payout_txhandler`; alternatively, restructure `create_payout_txhandler` so the OP_RETURN attribution output is committed to by a signature the operator controls exclusively (e.g., have the operator co-sign or place attribution somewhere covered by an operator-controlled input) rather than relying solely on an externally supplied, flag-selectable user signature.

```rust
    fn is_profitable(
        input_amount: Amount,
        withdrawal_amount: Amount,
        bridge_amount_sats: Amount,
        operator_withdrawal_fee_sats: Amount,
    ) -> bool {
        // Use checked_sub to safely handle potential underflow
        let withdrawal_diff = match withdrawal_amount
            .to_sat()
            .checked_sub(input_amount.to_sat())
        {
            Some(diff) => Amount::from_sat(diff),
            None => {
                // input amount is greater than withdrawal amount, so it's profitable but doesn't make sense
                tracing::warn!(
                    "Some user gave more amount than the withdrawal amount as input for withdrawal"
                );
                return true;
            }
        };

        if withdrawal_diff > bridge_amount_sats {
            return false;
        }

        // Calculate net profit after the withdrawal using checked_sub to prevent panic
        let net_profit = match bridge_amount_sats.checked_sub(withdrawal_diff) {
            Some(profit) => profit,
            None => return false, // If underflow occurs, it's not profitable
        };

        // Net profit must be bigger than withdrawal fee.
        // net profit doesn't take into account the fees, but operator_withdrawal_fee_sats should
        net_profit >= operator_withdrawal_fee_sats
    }
```

```rust
pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
```
