### Title
Stale line-index selection combined with re-fetched diff causes silent mis-application of partial commits - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
GitHub Desktop's partial-commit feature (selecting individual lines/hunks to include in a commit) stores the user's selection as a set of **line indices** into a previously-rendered diff (`file.selection`). When the commit is actually created, the code does **not** reuse that rendered diff — it silently re-computes a brand-new diff from the working directory at commit time and then re-applies the old index-based selection to it. If the file content on disk changes between the moment the diff was shown/selected and the moment the commit executes, the selection indices no longer correspond to the same logical lines, so the wrong lines get included/excluded from the commit — a silent corruption of what the user actually commits.

### Finding Description
The Changes view renders a diff and stores the resulting `IDiff` together with the user's line selection in `IChangesState.selection.diff`, refreshed via `updateChangesWorkingDirectoryDiff`: [1](#0-0) 

That function does attempt to reconcile selection with a newly fetched diff by recomputing `selectableLines`, but this reconciliation is index-based, not content-based — it only removes indices that are no longer "includeable," it cannot detect that index `N` now refers to a *different* line than when the user selected it: [2](#0-1) 

When the commit is actually performed, the flow is `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`: [3](#0-2) [4](#0-3) 

Critically, `applyPatchToIndex` does **not** use the diff/selection state cached in the UI — it independently re-fetches a fresh diff from the working directory right before building the patch: [5](#0-4) 

That freshly-fetched diff is then combined with `file.selection` (built from the earlier, now possibly-stale diff) inside `formatPatch`, which decides what to keep purely by index (`file.selection.isSelected(absoluteIndex)`): [6](#0-5) 

This is exactly the same class of bug as the reported LiquidityReserveV2/PolicyManagerV2 issue: a downstream calculation (`_computeDailyCap`) trusts a value (`reserveBalance`) that fails to account for a pending, already-committed state change (queued withdrawal), producing an artifact (the frozen cap) that no longer matches reality. Here, `formatPatch`/`applyPatchToIndex` trust a value (`file.selection`, i.e., "which line indices are included") that fails to account for a pending, already-happened state change (the working directory content mutating), producing an artifact (the generated patch/commit) that no longer matches what the user actually reviewed and intended.

### Impact Explanation
The mismatch is applied via `git apply --cached`, so it can silently:
- Include unintended lines/hunks in a commit (lines the user explicitly excluded).
- Exclude lines the user explicitly selected.
- Produce a hunk with header counts (`oldCount`/`newCount`) that no longer correspond to actual file content, since these counts are derived from the stale diff's line classification, not the new one.

This is squarely within the accepted "silent corruption of what the user commits or pushes" impact category — the user believes they reviewed and approved exactly the diff shown, but the committed content can differ without any error surfaced (in the case where `git apply` still succeeds against different-but-compatible context).

### Likelihood Explanation
The window between diff render and commit is not instantaneous — a user reviews a diff, selects lines, potentially switches tabs/files, and only later clicks "Commit." During that window, any process with write access to the working tree (an editor autosave, an auto-formatter, a file-watcher/build tool such as webpack or a linter running in the background, another Desktop tab open on the same repo) can mutate the file. Nothing in the flow blocks committing simply because the diff has changed since it was last rendered — `updateChangesWorkingDirectoryDiff`'s reconciliation only prunes indices that vanished, it does not force a full re-render/re-selection or block the commit action when the diff has meaningfully drifted. Because partial-commit users are, by definition, actively working in the file being partially staged, this condition is not a contrived edge case for that workflow.

### Recommendation
- In `applyPatchToIndex` (`app/src/lib/git/apply.ts`), do not re-fetch the diff independently at commit time. Reuse (or re-validate against) the exact diff object that was current when the user made their line selection, and fail the commit (with a clear error) if the working directory content for that file has changed since.
- Alternatively, key `DiffSelection` off diff content hashes/line content rather than raw indices so that a content-based diff between "selection-time diff" and "commit-time diff" can be detected and safely rejected instead of silently mis-applied.
- Surface an explicit error/refresh-and-retry UX when `formatPatch` detects the underlying diff has changed shape since the selection was made, rather than proceeding with index-based application.

### Proof of Concept
1. Open a repository in GitHub Desktop and modify a tracked file with several separate changes (multiple hunks).
2. In the Changes view, select only some lines of one hunk for partial commit (this captures `file.selection` against diff snapshot D1).
3. Before clicking "Commit," let a background process (e.g., an editor auto-format-on-save, a file watcher/build tool, or simply editing the file again) alter line offsets in the file (e.g., insert/remove a line above the selected hunk) so that on-disk content now differs from D1.
4. Click "Commit." `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches a new diff D2 from the changed working directory, but `formatPatch` (`app/src/lib/patch-formatter.ts:143-170`) applies the D1-based selection indices to D2's hunks.
5. Inspect the resulting commit content: the staged lines no longer match the lines the user actually selected in the UI, or `git apply --cached` fails/produces unexpected hunk boundaries — silently corrupting the commit relative to user intent.

export async function stageFiles(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<void> {
  const normal = []
  const oldRenamed = []
  const partial = []
  const deletedFiles = []

  for (const file of files) {
    if (file.selection.getSelectionType() === DiffSelectionType.All) {
      normal.push(file.path)
      if (file.status.kind === AppFileStatusKind.Renamed) {
        oldRenamed.push(file.status.oldPath)
      } else if (file.status.kind === AppFileStatusKind.Deleted) {
        deletedFiles.push(file.path)
      }
    } else {
      partial.push(file)
    }
  }

  // Staging files happens in three steps.
  //
  // In the first step we run through all of the renamed files, or
  // more specifically the source files (old) that were renamed and
  // forcefully remove them from the index. We do this in order to handle
  // the scenario where a file has been renamed and a new file has been
  // created in its original position. Think of it like this
  //
  // $ touch foo && git add foo && git commit -m 'foo'
  // $ git mv foo bar
  // $ echo "I'm a new foo" > foo
  //
  // Now we have a file which is of type Renamed that has its path set
  // to 'bar' and its oldPath set to 'foo'. But there's a new file called
  // foo in the repository. So if the user selects the 'foo -> bar' change
  // but not the new 'foo' file for inclusion in this commit we don't
  // want to add the new 'foo', we just want to recreate the move in the
  // index. We do this by forcefully removing the old path from the index
  // and then later (in step 2) stage the new file.
  await updateIndex(repository, oldRenamed, { forceRemove: true })

  // In the second step we update the index to match
  // the working directory in the case of new, modified, deleted,
  // and copied files as well as the destination paths for renamed
  // paths.
  await updateIndex(repository, normal)

  // This third step will only happen if we have files that have been marked
  // for deletion. This covers us for files that were blown away in the last
  // updateIndex call
  await updateIndex(repository, deletedFiles, { forceRemove: true })

  // Finally we run through all files that have partial selections.
  // We don't care about renamed or not here since applyPatchToIndex
  // has logic to support that scenario.
  for (const file of partial) {
    await applyPatchToIndex(repository, file)
  }
