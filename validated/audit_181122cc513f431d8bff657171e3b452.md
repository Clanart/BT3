### Title
`Operator::withdraw` passes collateral UTXO to `fund_raw_transaction` without exclusion, enabling accidental collateral spend - (File: core/src/operator.rs)

---

### Summary

`Operator::withdraw` calls Bitcoin Core's `fund_raw_transaction` with `add_inputs: Some(true)` and no mechanism to exclude the operator's collateral UTXO. Because the collateral UTXO lives at `signer.address` — the same address managed by the Bitcoin Core wallet — it is a candidate for automatic coin selection. If selected, the collateral is permanently spent outside the protocol, stripping the operator of its bridge participation rights and destroying the UTXO chain that all pending reimbursements depend on.

---

### Finding Description

The payout transaction built in `Operator::withdraw` uses `SinglePlusAnyoneCanPay` for the user's input, so the operator must add its own wallet inputs to cover both the fee and the shortfall between `out_amount` (≈ `bridge_amount`, e.g. 10 BTC) and the user's small withdrawal UTXO value. [1](#0-0) 

The call is:

```rust
fund_raw_transaction(
    payout_txhandler.get_cached_tx(),
    Some(&FundRawTransactionOptions {
        add_inputs: Some(true),   // wallet adds its own UTXOs
        include_unsafe: Some(false),
        lock_unspents: Some(false), // no locking of selected UTXOs
        fee_rate: ...,
        // no exclude_utxos / no pre-lock of collateral
        ..
    }),
    None,
)
```

The collateral UTXO is created at `signer.address` (the operator's taproot key-path address): [2](#0-1) 

Because `send_to_address(&signer.address, collateral_funding_amount)` is a standard wallet send, Bitcoin Core tracks that UTXO in its UTXO set. `fund_raw_transaction` therefore considers it a spendable coin. There is no `lockunspent` call before the fund step, no `exclude_utxos` option, and no post-fund inspection of the returned inputs.

By contrast, `transfer_outpoints_to_wallet` — the only other function that spends wallet UTXOs — explicitly enumerates all collateral outpoints and rejects any request that touches them: [3](#0-2) 

That guard is entirely absent from `withdraw`.

---

### Impact Explanation

If Bitcoin Core's coin-selection picks the collateral UTXO (e.g., when the operator's hot wallet has insufficient other confirmed UTXOs):

1. **Collateral is permanently destroyed** outside the protocol. `collateral_check` will immediately return `false` for this operator.
2. **All future deposits are blocked** for this operator: verifiers reject deposits that include an operator whose collateral is gone.
3. **All pending reimbursements are broken**: the round-tx chain (`collateral → Round → ReadyToReimburse → Round → … → Reimburse`) requires the collateral UTXO as its root input. Spending it outside the chain makes every pre-signed `Round` transaction invalid, so the operator can never recover the BTC it fronted for withdrawals.

This is a direct, permanent loss of operator collateral (a large BTC amount, e.g. `collateral_funding_amount`) and a liveness break for all deposits that operator participated in. [4](#0-3) [5](#0-4) 

---

### Likelihood Explanation

The normal withdrawal flow requires the operator to cover `out_amount − user_utxo_value`, which is close to `bridge_amount` (e.g. 10 BTC). An operator whose hot wallet holds only the collateral UTXO and a small operational balance — a realistic bootstrapping state — will have `fund_raw_transaction` select the collateral UTXO as the only UTXO large enough to cover the shortfall. No attacker capability is required; any legitimate user withdrawal request triggers the path.

---

### Recommendation

Before calling `fund_raw_transaction`, lock the collateral UTXO with `lockunspent false [{txid, vout}]` and unlock it afterward. Alternatively, verify after funding that none of the added inputs match any known collateral outpoint (using the same `get_all_collateral_outpoints` logic already present in `transfer_outpoints_to_wallet`), and abort if one is found. A third option is to maintain the collateral UTXO in a descriptor wallet that is separate from the hot-wallet used for fee payment.

---

### Proof of Concept

1. Operator initialises with only the collateral UTXO (e.g. 10 BTC) in its Bitcoin Core wallet and a small hot-wallet balance insufficient to cover a full bridge withdrawal.
2. A user calls `Withdraw` with a small `in_outpoint` (e.g. 0.001 BTC) and `out_amount = 9.999 BTC`.
3. `create_payout_txhandler` builds a transaction: input = 0.001 BTC (user, `SinglePlusAnyoneCanPay`), output = 9.999 BTC to user.
4. `fund_raw_transaction(add_inputs=true)` needs ~9.998 BTC from the wallet. The only UTXO large enough is the 10 BTC collateral UTXO. Bitcoin Core selects it.
5. `sign_raw_transaction_with_wallet` signs the collateral input with the operator's key.
6. `send_raw_transaction` broadcasts the transaction. The collateral UTXO is spent outside the protocol.
7. `collateral_check` now returns `false`; the operator is ejected from all future deposits and cannot execute any round-tx reimbursement. [6](#0-5) [7](#0-6)

pub fn create_round_txhandler(
    operator_xonly_pk: XOnlyPublicKey,
    txin: RoundTxInput,
    pubkeys: &[bitvm::signatures::winternitz::PublicKey],
    paramset: &'static ProtocolParamset,
) -> Result<TxHandler, BridgeError> {
    let mut builder = TxHandlerBuilder::new(TransactionType::Round).with_version(NON_STANDARD_V3);
    let input_amount;
    match txin {
        RoundTxInput::Prevout(prevout) => {
            input_amount = prevout.get_prevout().value;
            builder = builder.add_input(
                NormalSignatureKind::OperatorSighashDefault,
                *prevout,
                SpendPath::KeySpend,
                Sequence::from_height(paramset.operator_reimburse_timelock),
            );
        }
        RoundTxInput::Collateral(outpoint, amount) => {
            let (op_address, op_spend) =
                create_taproot_address(&[], Some(operator_xonly_pk), paramset.network);
            input_amount = amount;
            builder = builder.add_input(
                NormalSignatureKind::OperatorSighashDefault,
                SpendableTxIn::new(
                    outpoint,
                    TxOut {
                        value: input_amount,
                        script_pubkey: op_address.script_pubkey(),
                    },
                    vec![],
                    Some(op_spend.clone()),
                ),
                SpendPath::KeySpend,
                DEFAULT_SEQUENCE,
            );
        }
    }

    // This 1 block is to enforce that operator has to put a sequence number in the input
    // so this spending path can't be used to send kickoff tx
    let timeout_block_count_locked_script =
        Arc::new(TimelockScript::new(Some(operator_xonly_pk), 1));

    let total_required = (paramset.kickoff_amount + paramset.default_utxo_amount())
        .checked_mul(paramset.num_kickoffs_per_round as u64)
        .and_then(|kickoff_total| kickoff_total.checked_add(paramset.anchor_amount()))
        .ok_or_else(|| {
            BridgeError::ArithmeticOverflow("Total required amount calculation overflow")
        })?;

    let remaining_amount = input_amount.checked_sub(total_required).ok_or_else(|| {
        BridgeError::InsufficientFunds("Input amount insufficient for required outputs")
    })?;
