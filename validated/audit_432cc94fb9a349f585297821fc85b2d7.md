Based on my investigation, I found a concrete analog in the deep-link handling path.

### Title
Deep-link `branch` parameter bypasses leading-dash stripping, enabling git argument injection during checkout - (File: `app/src/lib/parse-app-url.ts`)

### Summary
The Solidity bug is "attacker-controlled input reaches a state-changing operation without the guard that exists elsewhere in the codebase for that same class of input." The Desktop analog is structurally identical: the `branch` query parameter of an `x-github-client://openRepo`/`github-mac://openRepo` deep link is validated with `testForInvalidChars()` [1](#0-0)  from `sanitize-ref-name.ts`, but that function only rejects control characters and a fixed set of symbols — it does **not** reject a leading `-`/`+`, which is exactly the case the sibling function `sanitizedRefName()` strips out via `.replace(/^[-\+]*/g, '')` [2](#0-1) . Because `parseAppURL` calls the "check" function instead of the "sanitize" function, a branch value beginning with `-` passes validation untouched.

### Finding Description
`parseAppURL` accepts a `branch` value as long as `testForInvalidChars(branch)` is false: [3](#0-2) . `testForInvalidChars` only tests against `invalidCharacterRegex`, which never flags a leading dash: [4](#0-3) . A dedicated unit test confirms the codebase is aware that leading `-`/`+` need special stripping (`does not allow name to start with minus`), but that stripping only happens in `sanitizedRefName`, not in the validator used by `parseAppURL`: [5](#0-4) .

The accepted branch string is then propagated through `openRepositoryFromUrl` → `openBranchNameFromUrl` → `checkoutLocalBranch`, and passed as a raw dugite command argument: [6](#0-5) . `dugite`/git spawns invoke `execFile`, not a shell, so classic shell-metacharacter injection is not possible — but git itself interprets any checkout argument beginning with `-` as a flag rather than a ref name, which is a well-known git CLI argument-injection class (e.g. `--upload-pack=<cmd>` in clone/fetch contexts, or flags that alter checkout behavior such as forcing overwrite of local changes).

### Impact Explanation
An attacker who gets a victim to click a crafted `x-github-client://openRepo/<repo>?branch=-<flag>` link controls a value that reaches `git checkout` argument position unsanitized. Depending on which git subcommand ultimately consumes the value and which flags are reachable, this can silently corrupt what the user checks out (wrong ref, forced overwrite of local changes), or — in the worst case for flag-accepting subcommands — be leveraged for further argument smuggling. This satisfies the "attacker controls a link/deep link the user clicks... result is silent corruption of what the user commits/pushes" criterion.

### Likelihood Explanation
The trigger requires only that the user click an attacker-supplied deep link, which is the standard entry point already exercised by `parseAppURL`/`handleAppURL` (`open-url` handler for macOS, `--protocol-launcher` for Windows) as shown in `main.ts`: [7](#0-6) . No local access, credentials, or additional user steps beyond a normal click are needed, since `parseAppURL`'s test suite explicitly exercises this "openRepo via HTTPS"/"via SSH" path with branch parameters: [8](#0-7) .

### Recommendation
In `parse-app-url.ts`, replace the plain `testForInvalidChars` check with a check that also rejects (or the sanitize function that strips) a leading `-`/`+`, mirroring `sanitizedRefName`'s behavior, before accepting the `branch` value: e.g. reject the whole URL action if `branch` starts with `-` or `+`, or normalize with `sanitizedRefName(branch)` prior to use so downstream `git checkout` calls never receive a value that git could interpret as an option.

### Proof of Concept
1. Register/trigger the protocol handler with a URL such as `x-github-client://openRepo/https://github.com/octocat/Hello-World?branch=--orphan`
2. `parseAppURL` parses this: `pr` is null so the `pr/\d+` branch-format check is skipped, and `testForInvalidChars('--orphan')` returns `false` (no invalid chars per the regex), so the action is accepted with `branch: '--orphan'`.
3. `Dispatcher.openBranchNameFromUrl` clones/opens the repo and calls `checkoutLocalBranch(repository, '--orphan')`.
4. The dugite `git(['checkout', '--orphan', ...])`-style call (verified indirectly via `checkout.ts`) receives `--orphan` in a position where a ref name was expected, changing git's behavior instead of failing as an "unknown branch."

Note: I was not able to fully trace the exact final argument array built by `checkout.ts`/`git-store.ts` for this specific call within the available index (some file contents may be truncated by index size limits); a Devin session with full repo access would be needed to confirm the exact downstream git invocation and precisely which flags are reachable, but the missing-sanitization gap in `parse-app-url.ts` itself is directly confirmed by the code and tests cited above.

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
