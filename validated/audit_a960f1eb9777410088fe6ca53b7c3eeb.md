### Title
ReDoS heuristic (`_has_redos_structure`) only detects `+`/`*` quantifiers, letting bounded `{m,n}` catastrophic-backtracking regexes into `check_patterns` and hanging the PostToolUse pattern gate - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_validate_pattern` accepts any user-supplied regex from a committed `.claude/security-patterns.yaml` as long as it passes the static heuristic `_has_redos_structure`, which only looks for `+`/`*` repetition syntax. A regex using curly-brace bounded quantifiers (`{m,n}`) nested or chained to build catastrophic backtracking passes the heuristic untouched and is then executed unbounded via `re.search(pattern["regex"], content)` inside `check_patterns` on every subsequent `Write`/`Edit` in the repo, with no timeout guard.

### Finding Description
`_has_redos_structure` (`plugins/security-guidance/hooks/extensibility.py:265-289`) uses two static regexes:
```
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
```
and `_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")`.

Both templates hard-code detection of `+`/`*` repetition characters. Python's `re` engine also supports `{m,n}` bounded repetition, which produces the exact same catastrophic-backtracking dynamics when nested or chained (e.g. `(a{1,20}){1,20}b`, or an alternation-under-repetition written as `(a|aa){1,50}`). Since these constructs contain no literal `+`/`*`, they are invisible to `_REDOS_SHAPES` and `_ALT_UNDER_REP`, so `_has_redos_structure` returns `False` and `_validate_pattern` (`extensibility.py:199-244`) accepts the regex, compiling it successfully with `re.compile` (which does not itself detect algorithmic complexity) and storing it as `rule["regex"]`.

This rule is merged into `extensibility.user_patterns()`, loaded once per hook invocation via `load_for_session` → `_load_user_patterns`, and then evaluated on every future `PostToolUse` Edit/Write by `check_patterns` (`security_reminder_hook.py:386-427`):
```python
if not matched and "regex" in pattern and content:
    try:
        if re.search(pattern["regex"], content):
            matched = True
    except Exception:
        pass
```
There is no timeout, no `signal.alarm`, no subprocess/thread cancellation around `re.search` — only a bare `except Exception`, which does not catch a hang (catastrophic backtracking is not an exception, it's unbounded CPU time in the C regex engine). Because the crafted pattern is committed to the repo, it applies to content edited by any subsequent Claude Code session working in that repo (not just the attacker's own edits), so an ordinary Edit/Write by the model or user on unrelated files can trigger multi-second-to-effectively-unbounded regex evaluation on every single PostToolUse call.

### Impact Explanation
This is a hook-level denial-of-service on the pattern-warning gate: an unprivileged contributor who can get a `.claude/security-patterns.yaml` file merged/checked out (a normal PR, a cloned malicious template repo, etc.) can plant a regex that evades the only defense (`_has_redos_structure`) and causes `check_patterns` to hang or take excessively long on ordinary edits. If the PostToolUse hook stalls or is killed on timeout, the pattern-warning mechanism silently fails to complete for that edit, and per the plugin's fail-open posture elsewhere in the codebase (`try/except: continue` patterns throughout `check_patterns`), a dangerous `Write`/`Edit` (e.g. one matching `eval_injection`, `pickle_deserialization`, etc.) can go through without the intended warning being surfaced — directly undermining the stated invariant that "deny-by-pattern must not be bypassable or DoS'able via untrusted regex/glob input."

### Likelihood Explanation
Preconditions are minimal and match the threat model exactly: the repo must contain a `.claude/security-patterns.yaml` (committed, project-scoped, loaded automatically by `extensibility.load_for_session(cwd)` with no privilege check beyond file presence). Constructing a `{m,n}`-based catastrophic regex is a well-known, easily reproducible technique, and the heuristic gap is deterministic (any `{m,n}`-quantified nested/alternation regex bypasses it every time), so this is fully repeatable and requires no race conditions or timing luck.

### Recommendation
- Extend `_has_redos_structure` to normalize `{m,n}`, `{m,}`, and `{n}` bounded quantifiers to the same detection class as `+`/`*` before running `_REDOS_SHAPES` and `_ALT_UNDER_REP` (e.g. pre-process the regex string to replace `\{[0-9]*,?[0-9]*\}` with a `+` marker before pattern matching).
- More robust: don't rely solely on static heuristics — enforce a hard execution timeout around every `re.search` call in `check_patterns` (e.g., via a worker thread/process with `future.result(timeout=...)`, or the `regex` module's timeout support), so a pattern that evades the static check still cannot hang the hook.
- Consider capping matched-content length passed to user-supplied regexes, and logging/metrics on any `check_patterns` invocation exceeding a latency budget so ReDoS attempts are observable.

### Proof of Concept
Unit/fuzz test to add near `plugins/security-guidance/hooks/extensibility.py`:
```python
import time, re
from extensibility import _has_redos_structure, _validate_pattern

def test_curly_brace_redos_bypasses_heuristic():
    evil_regex = r"(a{1,20}){1,20}$"
    assert _has_redos_structure(evil_regex) is False  # heuristic gap

    rule = _validate_pattern(
        {"rule_name": "evil", "reminder": "x", "regex": evil_regex},
        source="Project",
    )
    assert rule is not None  # accepted despite catastrophic backtracking

    content = "a" * 30 + "!"  # non-matching tail forces backtracking
    start = time.monotonic()
    re.search(rule["regex"], content)
    elapsed = time.monotonic() - start
    assert elapsed < 0.5, f"regex search took {elapsed}s — ReDoS not bounded"
```
Expected result on current code: `_has_redos_structure` returns `False`, `_validate_pattern` accepts the rule, and the final assertion fails/times out (demonstrating unbounded `re.search` time), proving `check_patterns` can be made to hang via a committed `security-patterns.yaml`.
