### Title
Unvalidated serialized `ReceivedOutput` is accepted as spendable wallet input - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes an attacker-supplied scalar offset, `TxOut`, and `OutPoint`, but performs no validation that the output exists on-chain, that the outpoint refers to the supplied `TxOut`, or that the output was discovered by a trusted scanner. The resulting object is indistinguishable from a legitimate scanned output and is accepted by `SignableTransaction::new` as spendable wallet input.

### Finding Description
The issue is in `ReceivedOutput::read` at `networks/bitcoin/src/wallet/mod.rs:122-133`. It accepts arbitrary bytes and constructs a `ReceivedOutput` containing:

- an arbitrary offset;
- an arbitrary claimed `TxOut`;
- an arbitrary `OutPoint`.

By contrast, `Scanner::scan_transaction` normally creates `ReceivedOutput` only after matching an on-chain transaction output script and calculating the real transaction ID and vout at `networks/bitcoin/src/wallet/mod.rs:198-213`.

`SignableTransaction::new` then trusts the deserialized output’s amount and outpoint when calculating available funds and constructing inputs at `networks/bitcoin/src/wallet/send.rs:175-185`. `SignableTransaction::multisig` only checks that the claimed script corresponds to `keys.offset(offset)` at `networks/bitcoin/src/wallet/send.rs:273-282`; it does not prove that the referenced UTXO exists or contains the claimed `TxOut`.

### Impact Explanation
An attacker able to supply serialized `ReceivedOutput` bytes can inject a nonexistent or stale UTXO into wallet processing. The wallet will report and account for it as spendable value even though it cannot be spent. When combined with real inputs, the fake value can distort payment, change, and fee decisions and cause the threshold wallet to produce signatures for a transaction that consensus will reject.

This is a funds-integrity issue rather than only malformed input handling: an untrusted serialized object crosses a trust boundary and is treated as equivalent to scanner-authenticated chain state.

### Likelihood Explanation
Exploitation requires an interface that accepts serialized `ReceivedOutput` values from an untrusted source. In that reachable configuration, exploitation is straightforward because all required fields are attacker-controlled and canonical decoding alone is sufficient. A fake output can be made to pass the wallet’s later script/offset consistency check by choosing an offset and script corresponding to the wallet’s group key.

If `ReceivedOutput` bytes are only ever locally generated by `Scanner` and never accepted from untrusted callers, this is not externally exploitable. The library nevertheless exposes the deserializer as a public API and does not encode or enforce that trust assumption.

### Recommendation
Do not expose `ReceivedOutput::read` as a constructor of trusted spendable outputs without authentication. Either:

- make deserialization crate-private and only persist scanner-produced outputs;
- include authenticated provenance tying the object to a scanned block and registered scanner key; or
- revalidate every deserialized output against the chain and derive its offset from the scanner’s registered script map before treating it as spendable.

`SignableTransaction::new` should also reject outputs that have not been confirmed by a trusted scanner or independently resolved from the outpoint.

### Proof of Concept
Conceptually, with the wallet’s base public key `K`:

1. Choose any scalar `offset`.
2. Compute the Taproot script for `K + offset*G`.
3. Serialize a `ReceivedOutput` containing:
   - `offset`;
   - a `TxOut` using that script and a large fake amount;
   - a nonexistent or already-spent `OutPoint`.
4. Feed those bytes to `ReceivedOutput::read`.
5. Pass the resulting object to `SignableTransaction::new` together with a payment.
6. `SignableTransaction::multisig` succeeds because the offset/script relationship is internally consistent, and signing produces an invalid transaction spending the fabricated UTXO.

The fake value is included in `input_sat` at `networks/bitcoin/src/wallet/send.rs:175`, allowing it to influence payment and change calculations despite not being spendable.
