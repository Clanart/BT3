## Title
Excess native-token payment in `EvmHost.dispatch()` (POST/GET) is swallowed by the host instead of refunded to the caller — ([File: evm/src/core/EvmHost.sol])

## Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `msg.value` and perform a Uniswap V2 `swapETHForExactTokens` to buy exactly `post.fee`/`get.fee` worth of the `feeToken`. Uniswap V2's `swapETHForExactTokens` refunds any unused ETH to `msg.sender` of the *router call*, which is `EvmHost` itself (since `EvmHost` is the contract invoking the router), not the original external caller who sent `msg.value`. Neither dispatch function contains any subsequent step that forwards this leftover ETH back to `_msgSender()`. This is structurally identical to the M-8 pattern: a fee delta is correctly computed by an external process (the swap), but the protocol has no reimbursement path back to the party that overpaid — the surplus is simply retained in `commonData`-equivalent storage (the host contract's own ETH balance) with no accounting or withdrawal mechanism for the payer.

## Finding Description
In `evm/src/core/EvmHost.sol`, `dispatch(DispatchPost)`: [1](#0-0) 

and `dispatch(DispatchGet)`: [2](#0-1) 

Both call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. This function signature asks Uniswap to spend **up to** `msg.value` in ETH to acquire an exact amount of `feeToken`. The standard Uniswap V2 router implementation of `swapETHForExactTokens` refunds any unspent ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])` — but the `msg.sender` observed by the router is `EvmHost`, because `EvmHost` is the direct caller of the router. The refund therefore lands back inside `EvmHost`'s own balance, not the account (EOA or contract) that originally called `dispatch()` and sent the native token.

Neither `dispatch(DispatchPost)` nor `dispatch(DispatchGet)` contains any logic to compute the leftover ETH and forward it to `_msgSender()`. Contrast this with the `IntentGatewayV2` contract elsewhere in the same repo, which has been hardened specifically for this scenario — its `placeOrder` path is tested to refund unused ETH after a fee swap: [3](#0-2) 

That test demonstrates the codebase is aware refund-after-swap is required, yet `EvmHost.dispatch()` — the core, most-used entrypoint for dispatching cross-chain POST/GET requests — lacks the equivalent protection.

This exactly mirrors the reported bug class: a computed "loss" (here, `msg.value - amountUsed`) is not reimbursed to the party that incurred it (the fee payer/keeper-equivalent), and there is no governance-configurable or user-triggerable withdrawal for these stranded funds documented in the reviewed code.

## Impact Explanation
Any application or user calling `IDispatcher(host).dispatch{value: X}(post)` or `dispatch{value: X}(get)` with `X` greater than what the swap actually requires (which is common, since callers must overestimate `msg.value` to tolerate slippage/price movement, exactly as the SDK's fee-estimation code in this repo anticipates) permanently loses the difference. Funds accumulate in the `EvmHost` contract with no exposed withdrawal path back to payers in the reviewed dispatch logic, meeting the bounty's "stealing or loss of funds" / "wrong beneficiary or amount" criteria: value moves to the wrong beneficiary (the host contract) instead of being returned to its rightful owner (the fee payer).

## Likelihood Explanation
This is triggered by ordinary, permissionless, non-adversarial use: any unprivileged caller dispatching a POST/GET request with native-token payment and providing `msg.value` even slightly above the exact swap cost (which is the normal/expected case, since exact costs are unknowable in advance due to AMM price movement) will trigger the loss. No malicious relayer, prover, or admin is required — it happens on the standard dispatch path.

## Recommendation
After the `swapETHForExactTokens` call in both `dispatch(DispatchPost)` and `dispatch(DispatchGet)`, check `address(this).balance` (or capture the swap's actual `amounts[0]`) and refund `msg.value - amountUsed` to `_msgSender()`, mirroring the pattern already implemented and tested in `IntentGatewayV2`.

## Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires ~0.1 ETH worth of `feeToken` at the current pool price.
2. `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), ...)` executes; Uniswap spends ~0.1 ETH and refunds ~4.9 ETH to `msg.sender` of the router call — which is `EvmHost`.
3. `dispatch()` returns without forwarding the ~4.9 ETH back to the original caller.
4. The ~4.9 ETH remains in `EvmHost`'s balance indefinitely; the caller has no way to reclaim it through the reviewed dispatch/withdrawal interfaces.

Note: I was unable to fully verify at what point (or whether) any separate host-level sweep/withdrawal function exists elsewhere in the codebase that could recover this stranded ETH for payers specifically (as opposed to governance-only treasury sweeps like `_withdrawAssets` in `SimplexPaymaster`, which is a different contract). If such a payer-specific recovery mechanism exists in `EvmHost` or its inherited contracts outside what was reviewed, it would mitigate this finding; this should be confirmed with a full read of `EvmHost.sol` and its base contracts.

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
