## Finding

### Title
`placeOrder` fails to validate `output.assets[i].amount`, letting escrowed input tokens be claimed for a zero-value output - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
The external report's bug class is "an entity can be created while skipping mandatory field validation, corrupting downstream behavior." In `IntentGatewayV2.placeOrder`, every **input** token amount is checked for non-zero (`revert InvalidInput()` if `amount == 0`), but the symmetric requirement that requested **output** amounts also be non-zero is never enforced anywhere in the order-creation or order-fill path.

### Finding Description
`placeOrder` explicitly guards against zero-value inputs: [1](#0-0) 

but the `Order.output.assets` array (the `PaymentInfo` a solver must deliver to fulfil the order) is stored and emitted with no equivalent validation: [2](#0-1) 

`fillOrder` only checks that array *lengths* match between `order.inputs`, `order.output.assets`, and the filler-supplied `options.outputs` — it never checks that any of the amounts are non-zero: [3](#0-2) 

Because escrow crediting in `placeOrder` is keyed purely off `order.inputs` (with real, validated, non-zero amounts) and is decoupled from any check on `order.output`, an order with `output.assets[i].amount == 0` is fully accepted, real tokens are escrowed under `_orders[commitment][token]`, and any solver can subsequently call `fillOrder`/`_fillSameChain`/`_fillCrossChain` supplying `options.outputs[i].amount == 0` (satisfying the length-only check) to redeem the full escrowed input for free.

This is the same missing-required-field root cause as the source report (`register_appchain` skipping checks on `appchain_id`, `beneficiary`, token metadata, etc.): a downstream-critical field (`output.assets[*].amount`) that the protocol design assumes is always populated with a meaningful, non-zero value is never actually enforced at the point of intake.

### Impact Explanation
This is a direct, unauthorized transfer/theft of escrowed bridge funds: a solver who is not the rightful beneficiary can claim the full escrowed input amount for a fill that costs them nothing, because the "amount owed" invariant on the output leg is never validated. This matches the bounty's "stealing or loss of funds" and "wrong beneficiary or amount" categories, since the actual amount enforced on the fill side can legitimately be zero.

### Likelihood Explanation
Any user who constructs an `Order` with a zero (or partially zero) `output.assets[i].amount` — whether by a client bug, a malformed SDK call, or a griefing/social-engineering vector against a filler-integration — immediately exposes their escrowed tokens to being drained by any unprivileged actor simply calling `fillOrder` with a matching zero-value `FillOptions.outputs` entry. No relayer, prover, governance, or malicious peer is required — it is a pure on-chain, unprivileged-caller interaction between `placeOrder` and `fillOrder`.

### Recommendation
Mirror the existing input-amount guard on the output side inside `placeOrder` (and ideally re-validate in `fillOrder`/`_fillSameChain`/`_fillCrossChain`):
```solidity
for (uint256 i; i < order.output.assets.length;) {
    if (order.output.assets[i].amount == 0) revert InvalidInput();
    unchecked { ++i; }
}
```
This closes the asymmetry between validated inputs and unvalidated outputs and prevents zero-value fills from redeeming non-zero escrow.

### Proof of Concept
1. Victim (or a buggy client) calls `placeOrder` with `inputs = [{token: USDC, amount: 1000e6}]` and `output = {assets: [{token: DAI, amount: 0}], beneficiary: victim}`. No revert occurs since only `order.inputs[i].amount == 0` is checked (`evm/src/apps/IntentGatewayV2.sol:283`); `order.output.assets[0].amount == 0` is never checked.
2. 1000 USDC is escrowed under `_orders[commitment][USDC]` (`evm/src/apps/IntentGatewayV2.sol:334-343`).
3. Attacker (any address, no special role) calls `fillOrder(order, FillOptions({outputs: [{token: DAI, amount: 0}], ...}))`. The only checks performed are array-length equality (`evm/src/apps/IntentGatewayV2.sol:438-440`), which pass since both arrays have length 1.
4. Attacker's fill routes through `_fillSameChain`/`_fillCrossChain`, transferring `0` DAI to the beneficiary while claiming the escrowed `1000 USDC` input — a full-value theft for zero cost.

Note: I was unable to fully trace `_fillSameChain`/`_fillCrossChain`/`SolverAccount.sol` internals in this session due to iteration limits, so the exact token-transfer bookkeeping inside those functions (e.g., whether a separate check exists there) was not directly verified — this should be confirmed against `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `IntrinsicIntents.sol` before treating this as fully proven.
