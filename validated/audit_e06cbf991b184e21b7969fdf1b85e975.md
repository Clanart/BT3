### Title
Reachable AssertionError in `Offer.__post_init__` from a maliciously crafted offer file crashes the wallet's offer-processing coroutine - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.__post_init__` uses a bare Python `assert cs.coin not in adds` to guard against a spend bundle containing two identical `CoinSpend` entries for the same `Coin`. This mirrors the CVE-2019-9211 bug class: a reachable assertion abort triggered by attacker-controlled input during processing/serialization of a data structure, causing denial of service instead of a handled error.

### Finding Description
Inside `Offer.__post_init__`, when iterating the coin spends of the wrapped `WalletSpendBundle`, the code enforces the "no duplicate coin in one bundle" invariant with a bare `assert`: [1](#0-0) 

Every other invariant check in this constructor uses explicit `raise ValueError(...)` or `raise ValidationError(...)` (see the duplicate-payments check and the driver-dict check just above), which are caught and converted into structured errors by RPC/CLI/trade-manager callers. The `assert` on line 168, however, is not one of those handled exception types.

`Offer` objects are constructed directly from untrusted, counterparty-supplied bytes (an offer file/bech32m blob) via the trade manager and wallet RPC "take offer" / "get offer summary" endpoints (`chia/wallet/trade_manager.py`, `chia/wallet/wallet_rpc_api.py`), which decompress and deserialize the bundle before building an `Offer`. Because Python `assert` statements raise a bare `AssertionError`, and only `ValueError`/`ValidationError` are treated as "expected" input-validation failures on the offer-parsing/accept paths, an attacker (offer counterparty) can supply an offer whose underlying `WalletSpendBundle.coin_spends` contains two `CoinSpend` entries referencing the identical `Coin` (same parent, puzzle hash, and amount) to hit this assert deterministically. Since assertions are enabled by default in production Python processes (no `-O` flag), this reliably raises `AssertionError` inside offer summary/inspection/acceptance code, which is a spend-triggered halt in the class of the reported CVE (reachable assertion abort caused by data provided by an external actor), rather than a graceful rejection.

### Impact Explanation
An unhandled `AssertionError` surfacing through offer-parsing code that is not explicitly caught alongside `ValueError`/`ValidationError` can propagate up through wallet RPC handlers or CLI flows, producing an unstructured/uncaught exception at a point where the code path was designed to reject bad input gracefully. This is a wallet-user-reachable denial-of-service condition: any counterparty can hand a wallet operator a single malicious offer file, and merely inspecting/summarizing/accepting it (an unprivileged, user-driven action) can crash the request/coroutine instead of being rejected with a normal error response. This matches the CVE's "reachable assertion abort ... denial of service" pattern precisely, scoped to the "offer counterparty" reachable surface allowed in this analysis.

### Likelihood Explanation
High likelihood of triggering: constructing a `WalletSpendBundle` with two `CoinSpend` objects that reference the exact same `Coin` (same parent id, puzzle hash, and amount) is trivial for anyone crafting an offer file by hand (no signature or execution constraints prevent this at the bundle-construction stage prior to `Offer.__post_init__` running). No special privileges, network position, or timing are required — only handing the crafted offer bech32m/file to a wallet user and having them run offer summary/accept.

### Recommendation
Replace the bare `assert cs.coin not in adds` in `Offer.__post_init__` with an explicit `raise ValidationError(Err.INVALID_SPEND_BUNDLE, "duplicate coin in offer bundle")` (or equivalent `ValueError`), consistent with the other invariant checks in the same constructor, so that malformed/malicious offers are rejected through the same structured-error path already used for `ValidationError`/`ValueError` in offer parsing and RPC handling, instead of raising an uncaught `AssertionError`.

### Proof of Concept
1. Construct two `CoinSpend` objects with an identical `Coin` (same `parent_coin_info`, `puzzle_hash`, and `amount`) but any puzzle reveal/solution.
2. Build a `WalletSpendBundle` containing both `CoinSpend`s (aggregate signature can be empty/zero since no CLVM execution or full mempool validation happens before `Offer.__post_init__` runs).
3. Construct `Offer(requested_payments={}, _bundle=<that bundle>, driver_dict={})` directly, or encode it into a bech32m offer string and feed it through the wallet's offer-summary/accept RPC path (`chia/wallet/wallet_rpc_api.py` offer endpoints / `chia/wallet/trade_manager.py`).
4. Observe that instead of a `ValidationError`/`ValueError` being raised (as with the other checks in `__post_init__`), a bare `AssertionError` is raised at `chia/wallet/trading/offer.py:168`, which is not caught by the same handlers that catch `ValidationError`/`ValueError` in the offer-processing call chain, causing an unhandled failure of the offer-processing operation.

Note: I could not fully trace every call site that wraps `Offer(...)` construction to confirm whether some outer RPC boundary generically catches all `Exception` types (in which case the practical impact would be reduced to a normalized RPC error rather than a hard crash); this should be verified with a live Devin session that can trace `chia/wallet/wallet_rpc_api.py` and `chia/wallet/trade_manager.py` call paths and run the PoC end-to-end.
