### Title
Fee and weight calculation omit the OP_RETURN output, producing transactions whose actual fee rate and weight differ from the checked values - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` computes the transaction weight/vsize — and therefore `needed_fee`, the minimum-relay-fee check, and the `MAX_STANDARD_TX_WEIGHT` check — using `calculate_weight_vbytes`, which reconstructs a template `Transaction` from only `inputs` and `payments` (plus optional change). The OP_RETURN `data` output is appended to `tx_outs` after the weight calculation and is never included in any of the three estimates. This is the same bug class as the Joyn finding: two inconsistent "denominators" — the size the code accounts for versus the size of the transaction actually produced and signed.

### Finding Description
`calculate_weight_vbytes` builds a mock transaction to derive `weight` and `vbytes` (send.rs:62-127). In `new`, it is invoked with `payments` at line 204 (no change) and line 226 (with change). However, when `data` is `Some`, an additional `TxOut` (zero value, `OP_RETURN` script of up to 80 bytes of pushed data) is pushed onto `tx_outs` at lines 194-202 and is part of the final signed transaction — yet it is absent from both weight estimates. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) underprices the true transaction.
- The minimum relay fee check `needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000` (line 211) is evaluated against an underestimated `vbytes`.
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` (line 241) is evaluated against an underestimated `weight`.

### Impact Explanation
The transaction that gets FROST-signed and broadcast is strictly larger than the one measured. Its true fee rate is `fee / actual_vbytes < fee_per_vbyte`. If the caller specifies a `fee_per_vbyte` just above the minimum relay threshold, or the pushed data pushes the real vsize above what was checked, the resulting transaction's effective fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE` (1 sat/vB) and be rejected by default policy relay — or exceed `MAX_STANDARD_TX_WEIGHT` and never propagate. Since the produced transaction commits to specific prevouts via `Prevouts::All` (line 375), and Serai's signing flow binds preprocesses to this exact transaction (caching is explicitly unsupported, lines 333-349), a non-relayable transaction means the spent outputs cannot be moved by this signed artifact; the fee-bumping/resigning path requires a fresh threshold signing ceremony. Funds are effectively bricked until signers coordinate a new ceremony — mirroring the Joyn impact of "claims failing and funds permanently locked" caused by a mismatched scale.

### Likelihood Explanation
Any caller supplying `data` (an in-protocol feature: `TransactionError::TooMuchData` caps it at 80 bytes) combined with a low `fee_per_vbyte` or a near-max-size transaction triggers the discrepancy. The bug is deterministic and requires no privileged access — the payment/data parameters are untrusted inputs to `SignableTransaction::new`.

### Recommendation
Include the OP_RETURN output in the weight/vsize estimate: pass the fully-formed `tx_outs` (or `payments` plus the serialized data output) into `calculate_weight_vbytes` at both call sites (lines 204, 226), so `needed_fee`, the min-relay check, and the weight check reflect the transaction that is actually signed.

### Proof of Concept
```rust
// Conceptual: construct a SignableTransaction with data and fee_per_vbyte = 1
let payments = vec![(some_script, 10_000u64)];
let data = Some(vec![0u8; 80]); // max allowed
let tx = SignableTransaction::new(inputs, &payments, None, data, 1).unwrap();
// needed_fee was computed as vbytes(tx without OP_RETURN) * 1
// actual tx contains an extra ~90-byte output, so real fee rate < 1 sat/vB
// -> below DEFAULT_MIN_RELAY_TX_FEE, rejected by standard relay policy
```
The mismatch is directly visible in `networks/bitcoin/src/wallet/send.rs`: the `data` output is added at lines 194-202 while both `calculate_weight_vbytes` calls (lines 204, 226) receive only `payments` and `change`, never `data`.
