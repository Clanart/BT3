This is exactly the same bug class as the `getMultiplier` report: an explicit `!= 0` check exists for one "denominator-like" governance parameter (`Kip71BaseFeeDenominator`), but the closely-related parameter that is also used as a divisor (`Kip71GasTarget`) has only a `noopFormatChecker` — i.e., no validation at all. The downstream function (`NextMagmaBlockBaseFee`) implicitly assumes `GasTarget` is non-zero and unwinds (panics) rather than returning a "safe" value when it is not.

### Title
Missing validation of `reward.kip71gastarget`/`GasTarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - ([File: params/kip71_config.go])

### Summary
`kaiax/gov/param.go`'s `Kip71BaseFeeDenominator` entry explicitly guards against a zero denominator (`FormatChecker: func(cv any) bool { v, ok := cv.(uint64); return ok && v != 0 }` [1](#0-0) ), and `NextMagmaBlockBaseFee` even contains a defensive fallback for `BaseFeeDenominator == 0` (`if kc.BaseFeeDenominator == 0 { ... baseFeeDenominator = 64 }` [2](#0-1) ). However, the sibling parameter `Kip71GasTarget`, which is used as a divisor twice in the very same function, uses `noopFormatChecker` and has no zero-guard at all [3](#0-2) .

### Finding Description
`NextMagmaBlockBaseFee` computes the KIP-71 base fee for the next block and divides by `gasTarget` unconditionally in both the "gas used above target" and "gas used below target" branches: [4](#0-3) [5](#0-4) 

Both branches call `x.Div(x, new(big.Int).SetUint64(gasTarget))` where `gasTarget := kc.GasTarget` [6](#0-5) . `big.Int.Div` panics on division by zero. Since `gasTarget` originates from the `reward.kip71gastarget` (governance) parameter, and that parameter's `FormatChecker` is a no-op that accepts any `uint64` value including `0` [3](#0-2) , a governance vote (submitted the same way as any other governance parameter change, reachable by any governing/voting party under the existing governance mechanism) can set `GasTarget = 0`.

This exactly mirrors the reported bug class: the function (`getMultiplier`/`NextMagmaBlockBaseFee`) is expected to always return a usable value given a range of caller-controlled inputs; one invalid-input combination (`BaseFeeDenominator == 0`) is explicitly handled, but a structurally identical invalid-input combination (`GasTarget == 0`) is not, and the "unwinding" (panic) is not accounted for by the many callers that assume `NextMagmaBlockBaseFee` always successfully returns a `*big.Int`.

### Impact Explanation
`NextMagmaBlockBaseFee` is called from core, security-critical paths that every node executes, including header preparation/verification, block generation, and gas price oracle logic: [7](#0-6) [8](#0-7) [9](#0-8) 

Because the function panics deterministically for a given `(GasTarget=0, parentGasUsed != GasTarget)` state, once such a governance parameter is activated, every full node that reaches `VerifyMagmaHeader`/`NextMagmaBlockBaseFee` (e.g., during block validation or block proposal) will panic, halting block production/validation network-wide, i.e. a consensus-critical denial-of-service triggered purely through the standard governance parameter update mechanism rather than any privileged/off-chain access.

### Likelihood Explanation
This is reachable purely through the governance parameter set path (`reward.kip71gastarget` a.k.a. `Kip71GasTarget`), which the task rules explicitly list as an in-scope reachable surface ("governance parameters"). No malicious peer, validator collusion, or node compromise is required — only a governance vote setting `GasTarget` to `0`, which the current `FormatChecker` (`noopFormatChecker`) fails to reject, unlike the sibling `Kip71BaseFeeDenominator` parameter which is explicitly protected.

### Recommendation
Add an explicit non-zero `FormatChecker` for `Kip71GasTarget` (mirroring the check already used for `Kip71BaseFeeDenominator`), for example: `func(cv any) bool { v, ok := cv.(uint64); return ok && v != 0 }`. Additionally, as defense in depth, `NextMagmaBlockBaseFee` should guard against `gasTarget == 0` the same way it already guards `BaseFeeDenominator == 0`, returning a safe fallback (e.g. `lowerBoundBaseFee`) instead of allowing `big.Int.Div` to panic.

### Proof of Concept
1. Submit governance votes to set `reward.kip71gastarget` (`gov.Kip71GasTarget`) to `0`. Because its `FormatChecker` is `noopFormatChecker`, the vote is accepted as valid input by `kaiax/gov` [3](#0-2) .
2. Once the parameter takes effect (after the vote finalization interval per the governance module), any subsequent block whose parent `GasUsed != GasTarget (=0)` — i.e., essentially any block with `GasUsed > 0` — causes `NextMagmaBlockBaseFee` to execute `x.Div(x, new(big.Int).SetUint64(0))` in the "gas used above target" branch [4](#0-3) .
3. `big.Int.Div` panics with "division by zero", crashing header preparation/verification in `VerifyMagmaHeader`, `worker.commitNewWork`, and the gas price oracle across all nodes, since all of them call `NextMagmaBlockBaseFee` without a `gasTarget != 0` guard.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
