### Title
Consensus-incentive reward misattribution to first-listed relayer for unrelated state-machine updates in a batch - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives` pays out treasury funds for every `StateMachineUpdated` event in a `handle_messages` batch, but attributes **all** of those payouts to the relayer recovered from `messages[0]` only, regardless of which consensus message actually produced which state machine's update.

### Finding Description
`FeeHandler::on_executed` [1](#0-0)  recovers a single `relayer_account` from the **first** message in the batch (`messages.get(0)`), decoding its `Signature` and verifying it against that message's `consensus_proof`. It then collapses **all** `StateMachineUpdated` events in the batch — across every state machine, produced by every consensus message in the batch, not just `messages[0]` — into a per-`state_machine_id` map of highest `latest_height` [2](#0-1) , and pays the reward for **every** one of those state machines to the single relayer recovered from `messages[0]` [3](#0-2) .

`process_message`/`calculate_reward` transfers `block_cost * (latest_height - baseline)` from `TreasuryAccount` to the given `relayer_account` for each state machine [4](#0-3) [5](#0-4) .

`FeeHandler::on_executed` is documented as being invoked once per **batch of successfully processed messages** [6](#0-5) , and nothing in the trait or the pallet restricts a batch to a single `Message::Consensus` entry — a submitter (`handle_messages` extrinsic in `pallet-ismp`) can legitimately batch consensus updates for multiple independent state machines from multiple distinct relayer signatures in one call. Because the per-state-machine collapse in `on_executed` intentionally aggregates the union of `StateMachineUpdated` events from the whole batch, but the relayer identity is taken only from index `0`, any relayer who arranges for their own consensus message to occupy slot 0 of a batch that also includes other relayers' consensus updates for different state machines receives the entire treasury reward for work performed by the other relayers. The existing intra-state-machine double-count fix (deduping by state machine, keeping only the highest height) does not address this cross-relayer misattribution — it only prevents a single relayer's own repeated updates for one state machine from being paid multiple times within a batch. There is no check that the state machine associated with an event actually corresponds to the consensus message the relayer identity was recovered from.

### Impact Explanation
This causes an incorrect beneficiary of protocol funds: treasury BRIDGE/native currency intended to reward the relayer who actually delivered a given consensus update for state machine B can instead be captured by an unrelated relayer whose own message happens to occupy `messages[0]` of the same batch, for state machine A. This is a direct "wrong beneficiary" fund-movement bug in the reward/claim path, matching the bounty's in-scope class of stealing/loss of funds via logic attack, without requiring a malicious peer, prover, or governance actor — any two unprivileged relayers whose messages get batched together (batching order can plausibly be influenced by the caller submitting `handle_messages`, or by whichever relayer submits the encompassing extrinsic) can trigger this misattribution.

### Likelihood Explanation
Likely requires the ability to influence which messages land together in a single `handle_messages` batch and their ordering (submitter of the extrinsic controls the `Vec<Message>` order), which is realistic since relayers competing for rewards would be incentivized to include their own consensus message first alongside pending relay-worthy consensus updates for other chains submitted by others (e.g., via mempool/block-builder timing). No admin, governance, or malicious-relayer-signature forgery is needed — the flaw is purely a bookkeeping/attribution defect in `on_executed`.

### Recommendation
- Track relayer identity per `StateMachineId`/message rather than a single global `relayer_account` from `messages[0]`: build a map from `state_machine_id -> relayer_account` by associating each `Message::Consensus` entry with the `StateMachineUpdated` event(s) it actually produced (e.g., by correlating consensus client/state machine id embedded in the consensus proof, or by processing `StateMachineUpdated` events in-order against the specific message that triggered them) before disbursing rewards.
- Reject/ignore state machine updates in the aggregated event set that cannot be attributed to a verified relayer signature for that specific state machine's consensus message.
- Add regression tests with multi-message batches containing consensus updates from distinct relayers for distinct state machines, asserting each relayer is paid only for their own delivered proof.

### Proof of Concept
Conceptual (no test harness execution possible within this session):
1. Relayer R1 crafts and submits a valid `Message::Consensus` proof updating `StateMachineId(A)` with a large height jump (`latest_height - baseline` large ⇒ large reward).
2. R1 arranges (via extrinsic submission ordering, or by being the extrinsic caller assembling the batch) for their message to be placed at index 0 of a `handle_messages` call that also includes a legitimately-submitted `Message::Consensus` from relayer R2 updating an unrelated `StateMachineId(B)`.
3. `pallet-ismp` processes both messages successfully, emitting two `StateMachineUpdated` events (for A and B).
4. `on_executed` in `modules/pallets/consensus-incentives/src/impls.rs` recovers `relayer_account = R1` from `messages[0]`, then iterates the union of `StateMachineUpdated{A}` and `StateMachineUpdated{B}`, calling `process_message` for **both**, transferring the treasury reward for B's update to R1 instead of R2.
5. R2 receives nothing for the work they actually performed (proof relay for chain B); R1 captures both rewards.

Note: I could not fully trace the exact `pallet-ismp` `handle_messages`/dispatch code path that assembles and orders the `Vec<Message>` batch passed into `FeeHandler::on_executed` (searches for it in `modules/pallets/ismp/src/lib.rs` did not return the relevant call site within available iterations), so the precise mechanism by which an attacker can control batch composition/ordering is inferred from the trait's documented "batch of messages" semantics rather than directly confirmed against the dispatch entrypoint code. This should be verified against `modules/pallets/ismp/src/lib.rs`'s message-handling dispatchable before treating exploitability as fully confirmed.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
