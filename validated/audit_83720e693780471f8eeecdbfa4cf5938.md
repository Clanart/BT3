### Title
Unauthenticated state-mutating `GetEntityStatuses{restart_tasks: true}` call reachable when `client_verification=false` - ([File: core/src/servers.rs])

### Summary
When `client_verification` is `false`, `create_grpc_server` builds a `ServerTlsConfig` with only `.identity(server_identity)` and no `.client_ca_root`, and wires the service with the `Noop` interceptor instead of `OnlyAggregatorAndSelf`. Any TLS client (self-signed cert or none) can therefore complete the handshake and invoke `ClementineAggregator::get_entity_statuses` with `restart_tasks: true`, which is documented to restart operator/verifier background tasks.

### Finding Description
The intended binding is: `CALLER_AUTHORITY(peer_leaf_cert) == {aggregator_cert, our_cert}` for any state-mutating RPC, enforced by `only_aggregator_and_self` in `core/src/rpc/interceptors.rs`. That binding is only wired up when `config.client_verification == true`: [1](#0-0) 

When `client_verification` is `false`:
- `ServerTlsConfig` omits `.client_ca_root(...)`, so the TLS layer performs no client-certificate validation — the server still requires TLS for encryption/identity of itself, but does not require or check any client certificate.
- The service is wrapped with `Interceptors::Noop`, which does no authorization at all: [2](#0-1) 

This means an attacker who is not a verifier/operator/aggregator, holds no TLS certificate at all, can still open a TLS connection to the aggregator's public port (no client cert required since there's no `client_ca_root`) and call any RPC on `ClementineAggregatorServer`, including `get_entity_statuses(restart_tasks=true)`, without any authentication or authorization check. The `only_aggregator_and_self` guard — which is the only mechanism in this repo enforcing `CALLER_AUTHORITY` — is entirely bypassed because it is never installed in this configuration branch.

### Impact Explanation
The attacker gains the ability to invoke any RPC exposed by the aggregator (and, if the operator/verifier servers are ever run with `client_verification=false`, on those too) without proving any identity. Restarting entity background tasks (`get_entity_statuses(true)`) is state-mutating; per the rules this qualifies as an "unauthenticated state-changing call," which is explicitly listed as **High** severity. It is repeatable at will (attacker can call it at any time, on any deployment running with `client_verification=false`) and applies uniformly across all deposits/operators served by that aggregator instance, since it is a control-plane call rather than one scoped to a specific deposit.

The further escalation to Critical (an operator's Disprove/Challenge timer being disrupted mid-round, permanently losing its Reimburse path) is plausible given the documented effect of `restart_tasks`, but I could not fully trace the internal implementation of what "restarting background tasks" does to any in-flight timer/state machine within the available index (`core/src/aggregator.rs` internals for `get_entity_statuses`/`restart_tasks` were only located via grep, not fully read). The High-severity unauthenticated state-mutating call itself is confirmed and directly supported by code; the Critical escalation claim is not independently verified here.

### Likelihood Explanation
Preconditions: the deployment must run with `client_verification=false` (this is a config value, not a hardcoded default confirmed from the index — `core/src/config/mod.rs` truncated read did not show the default value definitively, though `core/src/servers.rs::create_aggregator_grpc_server` logs a warning only when verification is enabled, implying it is expected to sometimes be disabled). If so, the attack requires only network access to the aggregator's gRPC port and a TLS client capable of connecting without a valid client certificate — no BTC spend, no privileged role, no key material. This is low-cost and trivially repeatable.

### Recommendation
Always enforce client certificate verification on the aggregator/operator/verifier gRPC servers regardless of `client_verification` config, or at minimum require the `OnlyAggregatorAndSelf` interceptor unconditionally on all state-mutating RPCs (e.g. `get_entity_statuses` with `restart_tasks=true`), decoupled from the TLS client-cert config flag so a misconfiguration cannot fully disable RPC authorization.

impl Interceptor for Interceptors {
    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
