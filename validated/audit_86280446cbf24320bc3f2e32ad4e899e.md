### Title
Panic on out-of-range participant index in blame evaluation allows remote denial of service - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP blame-evaluation path dereferences attacker-chosen `Participant` indexes through unchecked `HashMap` indexing (`self.commitments[&sender]` in `blame_internal`, and `self.enc_keys[&decryptor]` in `Decryption::decrypt_with_proof`). A `Participant` is only constrained to be a non-zero `u16` (`Participant::new`), never bounds-checked against `n`. An accusation naming a `sender`/`faulty` index outside `1..=n` — as admitted by `Transaction::InvalidDkgShare` deserialization, which accepts any non-zero `u16` for `accuser`/`faulty` — causes an unconditional panic, crashing the node evaluating the blame. This is the Serai analog of CVE-2021-47307: an optional/indexed value assumed present is dereferenced without a NULL/absence check.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` take `sender` and `recipient` as `Participant` and pass them to `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575`). `blame_internal` calls `Decryption::decrypt_with_proof`, which indexes `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`) — panicking if `decryptor` was never registered. After successful decryption, `blame_internal` evaluates share-verification statements with `&self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:599`) — panicking if `sender` is not a key in the commitments map.

`Participant::new` only rejects zero (`crypto/dkg/src/lib.rs`), so any `u16` in `1..=65535` is a valid `Participant` regardless of the actual `n`. The accusation inputs originate from untrusted serialized data: `Transaction::read` for `InvalidDkgShare` parses `accuser` and `faulty` via `Participant::new(u16::from_le_bytes(..))` with no upper bound check (`coordinator/src/tributary/transaction.rs:346-354`), and the encrypted share `msg` plus `proof` are attacker-controlled bytes fed to `EncryptedMessage::read` / `EncryptionKeyProof::read` (`crypto/dkg/pedpop/src/encryption.rs:171-177`, `:267-269`).

For the `commitments[&sender]` panic specifically, the attacker must supply an `EncryptedMessage` with a valid PoP signature and a valid `EncryptionKeyProof` — both trivially constructible: the accuser generates a fresh ephemeral key pair for `msg.key`, signs the PoP themselves, and produces the DLEq using their own registered encryption private key (`ecdh` = `msg.key * enc_priv`, `crypto/dkg/pedpop/src/encryption.rs:95-97`). The plaintext needs only deserialize as a canonical scalar (`C::F::from_repr` succeeds at `crypto/dkg/pedpop/src/lib.rs:590`). All checks then pass until the unchecked map index on the out-of-range `sender`.

### Impact Explanation
A single malicious DKG participant (or anyone able to submit an `InvalidDkgShare` accusation, which requires only a valid signed transaction) can crash every honest node that evaluates the blame claim. This aborts the DKG/blame-resolution process and, in the coordinator setting, halts the tributary/consensus handling of that transaction — a remote, unprivileged-party-reachable availability failure matching the CVE's `A:H` impact class.

### Likelihood Explanation
Triggering requires only control of the `sender`/`faulty`/`recipient` participant indexes in an accusation plus the ability to encrypt a well-formed scalar to oneself — no collusion, no threshold compromise, no secret knowledge beyond the accuser's own encryption key. Any single participant can do it deterministically.

### Recommendation
In `blame_internal` and `decrypt_with_proof`, replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with fallible lookups (`HashMap::get`) that return blame against the accuser/`InvalidProof` on absent keys, mirroring the CVE fix's "check for NULL before dereferencing." Additionally, validate `sender`/`recipient` against `1..=n` in `BlameMachine::blame`/`AdditionalBlameMachine::blame` and bound `accuser`/`faulty` against the session's `n` in `Transaction::InvalidDkgShare` deserialization.

### Proof of Concept
1. Set up a PedPoP DKG with `n = 3`, `t = 2`. Complete rounds so an honest node holds a `BlameMachine` (or construct `AdditionalBlameMachine::new(context, n, commitment_msgs)`).
2. Attacker (participant 1) builds `msg`: pick scalar `k`, set `msg.key = G*k`, encrypt `SecretShare(repr(1))` to their own `enc_pub_key` via `ecdh(enc_priv, msg.key)`, sign the PoP with `k`.
3. Attacker builds `proof`: `EncryptionKeyProof { key: ecdh, dleq: DLEqProof::prove(.., &[G, msg.key], &enc_priv) }`.
4. Call `blame(sender = Participant::new(0xFFFF).unwrap(), recipient = attacker_i, msg, Some(proof))`.
5. PoP verify passes, DLEq verify passes, decrypt yields scalar 1, then `self.commitments[&Participant(0xFFFF)]` at `crypto/dkg/pedpop/src/lib.rs:599` panics with "no entry found for key". Variant: pass `recipient` out-of-range with `proof = Some(..)` to panic earlier at `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`). [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
