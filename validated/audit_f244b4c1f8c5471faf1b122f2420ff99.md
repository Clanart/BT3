### Title
OP_RETURN data output is omitted from transaction weight/fee accounting in `SignableTransaction::new` — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to `IndexPool` collecting swap rewards but never accounting a `barFee` to `barFeeTo`, `SignableTransaction::new` appends an OP_RETURN output carrying user data to the transaction but never includes that output in the weight/vbyte calculation used to derive `needed_fee`, the `TooLowFee` check, or the change computation. A real transaction component is silently excluded from the accounting it should participate in.

### Finding Description
`SignableTransaction::new` pushes the OP_RETURN output into `tx_outs` when `data` is present (send.rs:194-202), then computes the fee via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204). `calculate_weight_vbytes` builds the template transaction's outputs solely from `payments` plus optional change (send.rs:85-99); the data output is never represented. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) is under-charged by the vsize of the OP_RETURN output (~9 + push overhead + up to 80 bytes of data, i.e. up to ~90 extra vbytes unaccounted).
- The `TooLowFee` minimum-relay check (send.rs:211) is evaluated against a vsize smaller than the real transaction's, so a transaction which is actually below `DEFAULT_MIN_RELAY_TX_FEE` for its true size can pass the check.
- The same omission applies to `fee_with_change` (send.rs:225-227): the change output value is computed as `input_sat - payment_sat - fee_with_change`, so the change absorbs funds which should have covered the data output's weight, and the effective fee rate of the broadcast transaction is lower than the requested `fee_per_vbyte`.

The actual fee paid, `sum(inputs) - sum(outputs)` (`fee()`, send.rs:138-141), therefore does not meet the requested fee rate for the transaction's real virtual size. An unprivileged depositor's InInstruction data is exactly what populates `data` (see `extract_serai_data` usage in processor/src/networks/bitcoin.rs:730), so the undersized output is attacker-controllable up to the 80-byte cap.

### Impact Explanation
Every transaction carrying a Serai data payload underpays its declared fee rate by `fee_per_vbyte * (vbytes of the OP_RETURN output)`. At low margin this can drop the real fee below the relay minimum, causing the transaction the threshold network signed to be rejected by mempool policy — outputs committed to the plan are not spendable as intended until a new transaction is planned and re-signed, and each failed attempt burns a signing round. At minimum, all data-bearing transactions propagate more slowly than priced for.

### Likelihood Explanation
Deterministic: any `SignableTransaction` built with `data: Some(_)` is affected; no adversarial conditions needed beyond a non-empty payload, which is the normal deposit-instruction flow.

### Recommendation
Include the data output in the weight calculation, e.g. extend `calculate_weight_vbytes` to accept the already-built `tx_outs` (or the OP_RETURN script) so that `vbytes`, `fee_with_change`, the `TooLowFee` check, and the change amount all reflect the final transaction.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, change, Some(vec![0; 80]), fee_per_vbyte)`. Compare `tx.weight()`/`vsize` of `tx.transaction()` against `needed_fee / fee_per_vbyte`: the transaction's real vsize exceeds the vsize used for the fee by the size of the OP_RETURN output (~90 vbytes), and `fee()` / real-vsize < `fee_per_vbyte`.
