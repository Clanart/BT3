This confirms a concrete, exploitable path: `updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` rewrites the user's local `origin` remote URL to whatever `clone_url` the GitHub API returns for the repository Desktop has associated with the local checkout — and that association is never invalidated once made.

### Title
Stale `gitHubRepository` association silently redirects the local git remote to a hijacked/renamed repository - (File: `app/src/lib/stores/updates/update-remote-url.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
This is the closest Desktop analog to the NFTR-1 pattern: an aliasing map (`tokenByName` there, `Repository.gitHubRepository`/`RepositoriesStore` here) is created once and never dereserved/invalidated when the underlying "name" (repository owner/name on the remote host) changes ownership. The explicit TODO in the code acknowledges this: `// TODO: We currently never clear GitHub repository associations (see https://github.com/desktop/desktop/issues/1144)` [1](#0-0) .

### Finding Description
`matchGitHubRepository` only checks that the remote URL's hostname matches an account's endpoint hostname — it does not verify that the account is authorized for, or matches, the specific owner/name pair already cached on the `Repository` model [2](#0-1) .

`repositoryWithRefreshedGitHubRepository` uses this loose match to re-fetch the repository from the GitHub API by `owner`/`name` parsed out of the current remote URL, and if the fetch succeeds it unconditionally calls `updateRemoteUrl` on the existing cached `gitHubRepository`, then persists a fresh `GitHubRepository` association via `repoStore.upsertGitHubRepository`/`setGitHubRepository` [3](#0-2) .

`updateRemoteUrl` then compares the *previously cached* `gitHubRepository.cloneURL` against the current remote. If they still match (i.e., the user hasn't manually changed anything) but the API's `clone_url` for that owner/name has changed, Desktop silently rewrites the local `origin` remote to the new URL: [4](#0-3) .

The broken invariant: once a `(local path) -> (GitHub owner/name)` association is cached, Desktop keeps refreshing and trusting it forever, based only on hostname + owner/name string matching — with no re-verification that the *same* underlying repository still exists at that owner/name. This is structurally identical to the `tokenByName` bug: an old "name" (owner/name pair) keeps pointing at a "token" (a `GitHubRepository`/remote) even after the real-world entity behind that name has changed, and downstream logic (`updateRemoteUrl`) acts on the stale pointer without ever calling the equivalent of `releaseTokenByName`.

### Impact Explanation
If a GitHub owner/name that a victim once had cloned locally is later renamed, transferred, or deleted and re-squatted by an attacker (a well-known GitHub "repo-jacking" primitive that requires no access to the victim's machine or credentials — only that the attacker control a GitHub repository object reachable at that same owner/name), the next background refresh in Desktop will:
1. Match hostname-only via `matchGitHubRepository`.
2. Fetch the attacker's now-squatted repository via the GitHub API for the stale `owner/name`.
3. Silently call `gitStore.setRemoteURL` to point the user's `origin` at the attacker's `clone_url`, per `updateRemoteUrl`'s `remoteUrlUnchanged && !urlsMatch` branch [4](#0-3) .

This silently corrupts the destination of the user's future `git push`/`git fetch` operations without any prompt, satisfying the "silent corruption of what the user commits or pushes" impact category — the user's next push would go to the attacker-controlled repository, potentially exposing private commits/code, and any credentials sent as part of that push (HTTPS Basic Auth / token in Authorization header, depending on credential helper config) would be transmitted to the attacker's endpoint.

### Likelihood Explanation
This requires no local access, no prior malware, and no leaked credentials — only that the attacker control a GitHub-hosted repository object at a name that a victim previously cloned. This is a realistic and previously-documented Desktop bug class (`desktop/desktop#1144`, explicitly cited in the code comment), and the automatic background refresh path (`repositoryWithRefreshedGitHubRepository`) runs without user interaction, so exploitation does not require any unnatural user steps beyond the attacker waiting for/causing the name to become available (e.g., after the legitimate owner renames or deletes it, which GitHub allows).

### Recommendation
Before trusting `updateRemoteUrl` to rewrite the local remote, verify that the fetched `apiRepo`'s stable identifier (GitHub repository `id`) matches the previously cached `GitHubRepository`'s id — not just that the owner/name string still resolves to *some* repository. If the id differs, treat the association as stale and require explicit user confirmation before changing the remote URL (the equivalent of "dereserving" the old association via `releaseTokenByName` before creating the new one), rather than silently reusing/refreshing it.

### Proof of Concept
1. Victim clones `https://github.com/alice/project.git`; Desktop caches `GitHubRepository` (`owner=alice`, `name=project`, `cloneURL=...`) on the local `Repository` model.
2. Alice renames or deletes `alice/project` on GitHub (a normal, permitted action).
3. Attacker (unprivileged, only needs their own GitHub account) creates a new repository at `alice/project` (if `alice` allows it) or, more directly, gains control of the `alice` namespace slot via a renamed org/user — a documented "repo-jacking" pattern.
4. On the victim's next app refresh, `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` (hostname-only match) → `api.fetchRepository('alice','project')` returns the attacker's repo object [5](#0-4) .
5. `updateRemoteUrl` sees `remoteUrlUnchanged` (victim never touched the remote) and `!urlsMatch` (attacker's `clone_url` differs), and calls `gitStore.setRemoteURL(...)`, silently repointing `origin` to the attacker's repository [6](#0-5) .
6. Victim's next `git push` sends commits (and potentially credentials, depending on auth transport) to the attacker-controlled remote.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo
  }

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}
