### Title
Coarse `(filePath, category)` dedup key lets a genuinely new dangerous finding be silently suppressed by an unrelated same-category finding during concurrent Stop/commit-review races - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`, `plugins/security-guidance/hooks/llm.py`)

### Summary
`handle_stop_hook` and the commit-review PostToolUse hook share session state keyed by dedup tuples of `(filePath, category)` only, never by line number/content hash. Because `git commit`/`git push` are configured as concurrent `asyncRewake` hooks alongside `Stop` in `hooks.json`, an attacker-controlled diff that produces two distinct vulnerabilities of the same broad category in the same file (e.g., two different SQL-injection sinks) can cause a genuinely new, unrelated dangerous finding to be silently dropped and the Stop hook to exit 0 with no warning and no rewake.

### Finding Description
`hooks.json` wires `Stop` and `PostToolUse[Bash]` on `git commit:*`/`git push:*` as independent `asyncRewake` invocations of the same script [1](#0-0) , so the Stop-hook LLM review and the commit-review LLM review can run concurrently against overlapping diff content — a scenario the code itself anticipates: `_dedup_against_state` exists specifically to "Drop vulns that a CONCURRENT asyncRewake hook wrote to previous_findings while this hook's LLM was running" [2](#0-1) .

The dedup/identity key used everywhere is `(filePath, category)` — never line number, byte offset, or a hash of the vulnerable snippet — explicitly because "vulnerableCode includes diff context lines that drift between fires" [3](#0-2) . The same coarse key is fed into the LLM prompt telling it to treat any (file, category) match as already-handled and not re-flag it unless it judges the fix "incomplete" [4](#0-3) .

In `handle_stop_hook`, after the LLM returns `vulns` for the current diff, `_dedup_against_state` re-reads state and computes `race_delta = fresh_keys - prompted_keys`, dropping any of this turn's `vulns` whose `(filePath, category)` key appears in that delta — regardless of whether the underlying vulnerable code is the same issue or a completely different one [5](#0-4) . If this drops *all* vulns, the hook calls `_skip(35, ...)`, which exits 0 without ever writing to stderr or triggering a rewake [6](#0-5) , [7](#0-6) .

Exploit flow: a repository/diff under attacker influence (e.g., prompt-injected instructions, or a malicious PR the assistant is asked to work on) contains two distinct dangerous constructs of the same LLM-assigned category in the same file (e.g., a hardcoded secret already flagged/fixed earlier in the session, and a brand-new, unrelated hardcoded secret introduced later in the same file). If the developer/agent triggers a `git commit` mid-turn (concurrent commit-review asyncRewake) while the Stop hook's LLM call for the newer secret is in flight, the commit-review hook's write to `previous_findings` under the same `(file, "Hardcoded Secrets")` key causes the Stop hook's independent, new finding to be dropped by the race-delta filter — the new dangerous change is never surfaced, breaking the invariant that dangerous edits must remain reviewable/blockable across retries and commits.

### Impact Explanation
This is a logic-level bypass of a required security guard: a genuinely new, dangerous code change can avoid triggering the Stop-hook `exit(2)`/rewake warning path entirely because it happens to share a coarse `(filePath, category)` tuple with an unrelated finding recorded by a concurrently racing hook. The user/agent receives no indication that a dangerous pattern was introduced, undermining the plugin's core guarantee that dangerous edits/commits remain reviewable and blockable.

### Likelihood Explanation
Requires: (1) attacker-influenced diff content containing two distinct instances of the same broad vulnerability category in the same file, and (2) a timing window where `git commit`/`git push` (asyncRewake, PostToolUse[Bash]) runs concurrently with the turn-ending `Stop` hook's LLM call — both configured as standard, expected flows in `hooks.json` and explicitly anticipated by the `_dedup_against_state` docstring. This is a real but timing-dependent condition (not always deterministic), since it depends on hook scheduling/race timing rather than attacker-controlled ordering guarantees.

### Recommendation
Strengthen the dedup key to include a stable identifier tied to the actual vulnerable location/content (e.g., line-range plus a normalized hash of the vulnerable snippet, or an LLM-assigned stable finding ID) rather than the coarse `(filePath, category)` pair, so structurally distinct vulnerabilities of the same category are never conflated. Additionally, when `_dedup_against_state` drops all vulns via the race-delta path, do not silently `_skip`/exit 0 — instead re-verify against the fresh state's actual finding content (not just the key) before suppressing, or log/emit a rewake-eligible signal so a legitimately new finding sharing a key isn't lost.

### Proof of Concept
Integration test plan (extending existing hook test harness):
1. Simulate a session where `previous_findings` already contains `{"filePath": "app.py", "category": "Hardcoded Secrets", "vulnerableCode": "API_KEY = 'sk-old'"}`.
2. Craft a Stop-hook diff for `app.py` that introduces a *different* hardcoded secret at a different line (e.g., `DB_PASSWORD = 'hunter2'`), which the LLM correctly categorizes as `"Hardcoded Secrets"`.
3. Concurrently (mock `with_locked_state` to simulate a race) have the commit-review hook write a finding for `("app.py", "Hardcoded Secrets")` to `previous_findings` while the Stop hook's `analyze_code_security` call is "in flight" (mocked to return the new vuln after the concurrent write).
4. Call `handle_stop_hook` and assert:
   - Expected (vulnerable) current behavior: `_dedup_against_state` drops the new `DB_PASSWORD` finding because its key collides with the race-delta key; `_skip(35)` fires with `sys.exit(0)` and no stderr output — the dangerous secret is never surfaced.
   - Desired assertion after fix: the new finding for `DB_PASSWORD` (a distinct vulnerable snippet) is NOT dropped, `sys.exit(2)` fires, and `PROVENANCE_BANNER` + guidance text mentioning `DB_PASSWORD` is written to stderr.

```python
def _dedup_against_state(session_id: str, vulns: List[Dict[str, Any]],
                         prompted: set) -> Tuple[List[Dict[str, Any]], int]:
    """Drop vulns that a CONCURRENT asyncRewake hook wrote to
    previous_findings while this hook's LLM was running.

    `prompted` is the (filePath, category) set the LLM was already told about
    via the prev_section prompt block. The LLM is instructed to only re-flag
    those if the attempted fix is incomplete, so a re-flag of a `prompted`
    entry is an intentional "fix didn't work" verdict and MUST pass through.
    We therefore re-read state now and only filter the race delta —
    (seen_now − prompted) — i.e. findings the LLM was never told about
    because they were written mid-review by the other hook.
    Returns (surviving_vulns, n_dropped).
    """
    if not vulns:
        return vulns, 0
    fresh = with_locked_state(
        session_id, lambda s: list(s.get("previous_findings", []))
    ) or []
    race_delta = _finding_keys(fresh) - prompted
    kept = [v for v in vulns
            if (v.get("filePath", ""), v.get("category", "")) not in race_delta]
    return kept, len(vulns) - len(kept)
```
