### Title
OP_RETURN data output omitted from fee/weight calculation, causing underpaid fee and oversized change — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds `tx_outs` including an OP_RETURN output carrying `data`, but computes the transaction weight/vbytes — and therefore `needed_fee` and the change amount — from `payments` only, never including the data output. The actual signed transaction is larger than the size the fee was calculated for, so the transaction pays less than the requested fee rate and can fall below the minimum relay fee, while the change output absorbs value that should have covered the fee.

### Finding Description
The bug class of the external report — a fee computed once at a "total" level but deducted/derived from components that do not sum back to that total — maps onto `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`:

1. `tx_outs` is built from `payments`, then a zero-value OP_RETURN output encoding `data` (up to 80 bytes, checked at line 171) is pushed at lines 194-202.
2. The weight/vbytes are computed via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204. `calculate_weight_vbytes` constructs a model `Transaction` whose `output` field is built **only from `payments`** (lines 85-93) plus optionally `change` (lines 95-99). The OP_RETURN output is never modeled.
3. `needed_fee = fee_per_vbyte * vbytes` (line 206) therefore excludes the OP_RETURN output's weight (~9-90 vbytes for a 0-80 byte push).
4. The change calculation at lines 224-235 also calls `calculate_weight_vbytes(..., payments, Some(&change))`, so `fee_with_change` and hence `value` (the change amount) are computed against the same undercounted size. The change output is credited `input_sat - payment_sat - fee_with_change`, i.e., it absorbs the sats that a correctly-sized fee would have consumed.
5. The final transaction returned at lines 245-255 contains the extra OP_RETURN output, so `fee()` (lines 138-141, `sum(inputs) - sum(outputs)`) equals `needed_fee` while the real transaction is larger than the modeled one — the effective fee rate is below `fee_per_vbyte`, and may fall below `bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE` even though the check at line 211 passed against the smaller `vbytes`.

### Impact Explanation
A transaction constructed with `data` is signed with a fee rate lower than requested and potentially below the network minimum relay fee, making it unbroadcastable/stuck while its change output reports the plan as executed — an instance of "funds accounted for but not spendable as intended." Even when relayable, `needed_fee()` reports a fee that does not correspond to the real transaction's vsize, so any caller computing an effective rate (e.g., `median_fee`-derived `fee_per_vbyte` in `processor/src/networks/bitcoin.rs`) systematically underpays, delaying confirmation of threshold-signed spends. The change output is correspondingly inflated, masking the discrepancy from accounting.

### Likelihood Explanation
Deterministic whenever `data` is `Some`. Any caller of `SignableTransaction::new` that passes data (the API publicly supports it, size-checked at 80 bytes) produces a fee that ignores the OP_RETURN output. Whether the tx falls below min-relay depends on the margin between `fee_per_vbyte * vbytes` and `DEFAULT_MIN_RELAY_TX_FEE * (vbytes + data_vbytes) / 1000`, which is reachable whenever `fee_per_vbyte` is chosen near the minimum — precisely the regime `median_fee` can produce in low-fee markets.

### Recommendation
Include the OP_RETURN output in the weight model: pass `tx_outs` (or `payments` plus the data output) to `calculate_weight_vbytes`, or add a `data: Option<&ScriptBuf>` parameter that appends the OP_RETURN `TxOut` in both the no-change and with-change weight calculations at lines 204 and 226. Alternatively, compute the fee from the weight of the fully-constructed `Transaction` rather than a partial model.

### Proof of Concept
```rust
// Given 1 input of 100_000 sats, one payment of 50_000 sats,
// change = Some(script), data = Some(vec![0; 80]), fee_per_vbyte = 1
//
// calculate_weight_vbytes(1, payments, Some(&change)) models:
//   inputs(1) + payment outputs + change output   (~ no OP_RETURN)
// => vbytes_with_change = V, fee_with_change = V
// change value = 100_000 - 50_000 - V
//
// The real tx also contains an ~91-byte OP_RETURN output:
//   actual_vsize = V' > V  (≈ V + ~91)
// fee() returns V (sum(inputs) - sum(outputs)), but the required
// fee for the requested rate is fee_per_vbyte * V'.
// Effective rate = V / V' < 1 sat/vbyte; if V' * 1000-based min
// relay fee > V, the signed tx is rejected by the mempool.
//
// Root cause: line 204 and line 226 pass `payments`, not `tx_outs`,
// so the OP_RETURN pushed at lines 194-202 is never weighed.
```
Key lines: OP_RETURN appended at `networks/bitcoin/src/wallet/send.rs:194-202`; weight computed without it at `:204` and `:226`; `calculate_weight_vbytes` builds outputs only from `payments`/`change` at `:85-99`; `fee()` reports `sum(inputs) - sum(outputs)` at `:138-141`.
