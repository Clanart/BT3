Based on my investigation, I found a strong analog to the reported bug class: **a security guard implemented as a boolean parameter that is only enforced at the checkout/submodule-update layer but is completely bypassed in the clone code path**, which is exactly the same "detection function doesn't apply the same restriction as the enforcement function" pattern as the Deriverse `is_long_margin_call()`/`check_long_margin_call()` mismatch.

### Title
`clone()` unconditionally disables Git's submodule file-protocol protection while `checkoutBranch`/`checkoutCommit` enforce it by default — inconsistent guard allows arbitrary local file read via malicious submodule URL - ([File: app/src/lib/git/clone.ts])

### Summary
`checkoutBranch()` and `checkoutCommit()` default `allowFileProtocol` to `false` and only pass `-c protocol.file.allow=always` to `git submodule update` when explicitly opted in [1](#0-0) , mirroring upstream Git's CVE-2022-39253 mitigation that blocks submodules from using `file://` URLs (which can be used to read/exfiltrate arbitrary local files by pointing a submodule at a sensitive directory such as `~/.ssh`). However, `clone()` — the code path used for every "Open in Desktop", "Clone repository", and deep-link clone operation — unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment for the `git clone --recursive` invocation [2](#0-1) , which disables Git's own upstream protection entirely, regardless of whether the URL is trusted.

### Finding Description
The intended invariant is: "Desktop must never let a repository's `.gitmodules` file cause it to read files from outside the repository via `file://` submodule URLs, unless the user/flow has explicitly acknowledged the risk (`allowFileProtocol=true`)." This invariant is correctly implemented for checkout flows: `updateSubmodulesAfterOperation` only appends `-c protocol.file.allow=always` when `allowFileProtocol` is `true`, and both `checkoutBranch`/`checkoutCommit` default that flag to `false` [3](#0-2) .

But `clone()`, which is reached from `openOrCloneRepository` for every "Clone in Desktop" / `x-github-client` deep link and the tutorial-repository flow, disables Git's built-in `protocol.file.allow=user` default behavior globally for the whole clone+recursive-submodule-init operation by setting `GIT_CLONE_PROTECTION_ACTIVE=false` [4](#0-3) . This is the exact same class of bug as the report: one code path (`checkoutBranch`/`checkoutCommit`) implements the "margin call" check correctly (threshold/guard applied), while a parallel code path that performs conceptually the same operation (initializing submodules, here during clone rather than checkout) silently omits the guard — an inconsistency between detection/enforcement that an attacker-controlled input (a malicious `.gitmodules` shipped in a cloned repository) can exploit.

### Impact Explanation
An attacker who controls a repository that a victim clones through GitHub Desktop (e.g., via "Clone in Desktop" deep link, or a public/malicious repo the user clones normally) can add a `.gitmodules` entry with a `file://` URL pointing at a sensitive local path (e.g. `file:///home/victim/.ssh`, or a Windows UNC/`file://` path to `AppData`). Since `GIT_CLONE_PROTECTION_ACTIVE` is forced to `'false'` for every clone, `git clone --recursive` will honor the `file://` submodule URL and copy the contents of that directory into the victim's working directory as a "submodule." If the user is unaware and commits/pushes, sensitive local files could be exfiltrated to the attacker's remote. This matches the "Valid Impact" criteria (attacker controls a cloned repository; unprivileged; results in file read outside the repo and silent corruption of what the user commits/pushes).

### Likelihood Explanation
Likelihood is high for any user who clones a maliciously crafted or compromised repository through Desktop's normal clone flow (not just deep links) — no unusual user action is required beyond a normal "Clone repository" or "Open in Desktop" action, since `clone()` is the single code path used for both. The existing hardening seen elsewhere in the codebase (e.g., `checkoutBranch`/`checkoutCommit` defaulting `allowFileProtocol=false`, and `isClonePathSensitive` guarding destination paths in the same file) indicates the project is aware of and mitigates this class of submodule/path issue elsewhere, but the mitigation was not applied consistently to `clone()`.

### Recommendation
Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()`, or make it conditional on an explicit, narrowly-scoped `allowFileProtocol` parameter analogous to the one already used in `checkoutBranch`/`checkoutCommit`, defaulting to `false` for all normal clone operations. Ensure `updateSubmodulesAfterOperation`'s existing guard is the single source of truth for whether `protocol.file.allow=always` is applied, rather than having a separate, more permissive override in the clone path.

### Proof of Concept
1. Attacker creates a public repository containing a `.gitmodules` file with:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/victim/.ssh
   ```
2. Victim uses GitHub Desktop's normal "Clone a repository" flow (or clicks an `x-github-client://openRepo/...` deep link) to clone the attacker's repository, which invokes `clone()` [5](#0-4) .
3. Because `GIT_CLONE_PROTECTION_ACTIVE` is set to `'false'` unconditionally, Git's built-in submodule file-protocol block does not trigger, and `git clone --recursive` follows the `file://` URL, copying `~/.ssh` into `leak/` in the victim's working directory.
4. If the victim stages/commits/pushes (or Desktop's status view exposes the files), the contents of `~/.ssh` are now tracked in the working directory and can be exfiltrated, whereas the equivalent `checkoutBranch`/`checkoutCommit` path would have blocked this by default (`allowFileProtocol=false`) [6](#0-5) .

**Note on verification limits**: I was not able to fully trace every caller of `clone()` (e.g., `openOrCloneRepository` in `app-store.ts`) within the tool budget to confirm there is no additional guard applied between the URL and the `clone()` call, nor was I able to confirm the exact Git version/behavior of `GIT_CLONE_PROTECTION_ACTIVE` bundled with Desktop. If deeper confirmation is needed (e.g., testing the actual clone behavior end-to-end), a Devin session with full repository and terminal access would be needed to reproduce this PoC concretely.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
