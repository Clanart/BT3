### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/vsize calculation, undercharging fees — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the GoGoPool finding — where a naive `rate * amount * duration` formula produced an inaccurate reward estimate that downstream logic (slashing) relied on — `SignableTransaction::new` computes the transaction weight and required fee from `payments` alone, even though the caller-supplied `data` is materialized as an extra OP_RETURN output. The estimate the fee is derived from does not match the actual transaction that gets built and signed, so the resulting fee is systematically understated by the size of the data output.

### Finding Description
In `SignableTransaction::new`, the `data` argument is converted into a `TxOut` with a `ScriptBuf::new_op_return` script and pushed onto `tx_outs` at networks/bitcoin/src/wallet/send.rs:194-202. The weight/vbytes used to derive `needed_fee` are then computed at line 204 via `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — which builds a model transaction whose outputs are only `payments` (lines 85-93). The OP_RETURN output is never included in the model. The same omission occurs in the change branch at lines 225-226, where the recomputation with the change output still passes `payments`, not `tx_outs`.

`calculate_weight_vbytes` itself correctly feeds the real script pubkeys into the bitcoin library's `tx.weight()` and `get_virtual_tx_size` (lines 101-125), so the only problem is that the data output is absent from the model. With `data` up to 80 bytes (allowed by the `TooMuchData` check at line 171), the OP_RETURN output adds roughly 90+ weight units (8-byte amount + script + output overhead) that are never priced.

Consequences:
- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on a smaller vbytes than the final transaction, so the actual fee rate paid is below the caller-requested `fee_per_vbyte`.
- The minimum relay fee check at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) uses the understated vbytes, so a transaction can pass this check while its true fee rate is below the network's minimum relay fee.
- `fee()` (lines 138-141) returns `inputs - outputs`, which will be a fee lower than `fee_per_vbyte * actual_vsize` whenever data is present, and `needed_fee()` reports an estimate that cannot be achieved by the built transaction.

This is reachable from public inputs: `data` is a caller-controlled `Option<Vec<u8>>` to `SignableTransaction::new`, the same public API used to construct signable spends.

### Impact Explanation
Any transaction built with `data` pays a lower effective fee rate than requested. If the requested rate is near the minimum relay fee, the produced transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` on its true vsize and be rejected by relay/mining nodes — the signed transaction is valid but unbroadcastable, leaving the funds unmovable by that transaction. Unlike GoGoPool's display-only component, here the inaccurate estimate directly determines the signed transaction's economics.

### Likelihood Explanation
The bug triggers deterministically whenever `data: Some(_)` is passed. It requires no attacker sophistication, no collusion, and no environmental assumptions — the fee model simply never accounts for the output. Impact is limited to fee underpayment/unrelayable transactions rather than theft, which is consistent with Medium severity (matching the judge's reasoning in the original report that an incorrect formula used downstream warrants Medium).

### Recommendation
Include the OP_RETURN output (and any other outputs added to `tx_outs`) in the model passed to `calculate_weight_vbytes`. The cleanest fix is to compute weight from the actual `tx_outs` vector (or pass `payments` plus the data output's script) at both call sites, so the modeled transaction is identical in shape to the one constructed in the `Ok` branch.

### Proof of Concept
```rust
// networks/bitcoin: SignableTransaction::new with data
let inputs = vec![output]; // a ReceivedOutput worth >> payment + fee
let payments = vec![(p2tr_script_buf(key).unwrap(), 1000)];

// 80-byte OP_RETURN payload: allowed by the TooMuchData check
let tx = SignableTransaction::new(inputs, &payments, None, Some(vec![0u8; 80]), fee_per_vbyte).unwrap();

// The OP_RETURN output (~9 base bytes + ~83 script bytes ≈ 90+ wu ≈ 23+ vbytes)
// was never included in calculate_weight_vbytes, which was called with `payments` only.
// Therefore:
assert!(tx.fee() < fee_per_vbyte * u64::try_from(tx.transaction().vsize()).unwrap());
// i.e. the realized fee rate is strictly below the requested fee_per_vbyte,
// and can dip under DEFAULT_MIN_RELAY_TX_FEE without triggering TooLowFee.
```
