### Title
Unchecked `PublicKey::from_bytes` result panics in `Schnorrkel::verify`, aborting signature completion - (File: crypto/schnorrkel/src/lib.rs)

### Summary
`Schnorrkel::verify` performs a fallible conversion of the FROST group key — a compressed Ristretto point — into a schnorrkel (ed25519) `PublicKey` via `PublicKey::from_bytes(&group_key.to_bytes())`, and unconditionally `.unwrap()`s the `Result`. This is the same defect class as CVE-2021-47206: a fallible lookup/decoding function whose failure return value is ignored, producing a crash (null-ptr-deref in C; panic in Rust) instead of an error path.

### Finding Description
In `crypto/schnorrkel/src/lib.rs`, `Schnorrkel::verify` builds a candidate schnorrkel `Signature` and then checks it against the group key: [1](#0-0) 

`group_key` is a `RistrettoPoint`; `group_key.to_bytes()` yields a Ristretto group encoding, not an Edwards-y encoding. `schnorrkel::PublicKey::from_bytes` decompresses the bytes as a `CompressedEdwardsY`, which rejects roughly half of all 32-byte inputs (non-canonical y or no square root for x). There is no guarantee that an arbitrary Ristretto encoding is a valid compressed ed25519 point, so `from_bytes` can legitimately return `Err`, at which point `.unwrap()` panics.

The call site is `AlgorithmSignatureMachine::complete` in `crypto/frost/src/sign.rs`, which invokes `self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum)` while aggregating signature shares from participants: [2](#0-1) 

The panic propagates out of `complete` rather than returning a `FrostError`, killing the signing task/thread. The same unchecked pattern appears in `SchnorrkelHram::hram` at `crypto/schnorrkel/src/lib.rs` lines 49 and 52, where `PublicKey::from_bytes(&point.to_bytes()).unwrap()` is applied to attacker-influenced points `R` and `A`, and `Scalar::from_repr(...).unwrap()` assumes the merlin `challenge_scalar` output is a canonical Ristretto scalar repr.

### Impact Explanation
Availability loss (matching the CVE's C:N/I:N/A:H profile): if the group's threshold key happens to serialize to bytes that do not decode as an ed25519 point — a property determined entirely by the DKG output — every call to `complete()` for that group panics instead of returning `FrostError::InternalError`, permanently DoSing signing for that key. An abort inside `complete` after shares have been broadcast also forfeits the blame path (`verify_share`/`BatchVerifier` at `crypto/frost/src/sign.rs` lines 474-489), so the panic cannot be converted into accountable blame. In hram, a panic during share aggregation similarly kills the verifier.

### Likelihood Explanation
Whether a given group key triggers the panic is a coin-flip property of the Ristretto encoding vs. ed25519 decompressibility. Reachability through the in-scope API is direct: `SignMachine::sign` → `SignatureMachine::complete` → `Algorithm::verify` with `self.view.group_key()` derived from `ThresholdKeys`. For any Schnorrkel multisig whose DKG-produced group key fails Edwards decompression, the panic is deterministic on every signing attempt. The `msg.as_ref().unwrap()` in the same function is safe only because `sign_share` (lib.rs:117) runs first; the `from_bytes` unwrap is the fragile one.

### Recommendation
Replace the `unwrap()` with graceful failure: `let Ok(pk) = PublicKey::from_bytes(&group_key.to_bytes()) else { return None };` so `verify` falls through to the per-share blame path. Apply the same to the `from_bytes`/`from_repr` unwraps in `SchnorrkelHram::hram` (or restructure so a malformed R/A returns a `FrostError`/`InvalidShare` rather than panicking). If the group key is required to be ed25519-decompressible, enforce that constraint at key-generation time rather than at verify time.

### Proof of Concept
1. Create a `ThresholdKeys<Ristretto>` set whose `group_key().to_bytes()` is not a valid `CompressedEdwardsY` (e.g., y ≥ p or non-square x² — ~50% of random keys).
2. Instantiate `AlgorithmMachine::<Ristretto, Schnorrkel>::new(Schnorrkel::new(b"ctx"), keys)`, run `preprocess`, exchange preprocesses, and call `sign(...)`.
3. Call `complete(...)` on the resulting `AlgorithmSignatureMachine` with the other shares.
4. `complete` reaches `self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum)` (sign.rs:465), which executes `PublicKey::from_bytes(&group_key.to_bytes()).unwrap()` (lib.rs:141-142) and panics instead of returning `None`/`FrostError`.
