### Title
Out-of-range blame recipient causes reachable panic in `Decryption::decrypt_with_proof` - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`AdditionalBlameMachine::blame` accepts attacker-controlled `sender` and `recipient` participant indexes without checking that they belong to the DKG participant set. If a blame request supplies a recipient outside `1..=n` and includes any syntactically valid `EncryptionKeyProof`, `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` while preparing the DLEq verification arguments. Because `Decryption::new` only populates `enc_keys` for registered participants, this indexing operation panics instead of returning `InvalidProof`.

### Finding Description
`AdditionalBlameMachine::new` creates a `Decryption` instance and registers only participants `1..=n` in `enc_keys`. [1](#0-0)  The subsequent public `AdditionalBlameMachine::blame` API forwards the caller-supplied `sender` and `recipient` directly to `blame_internal` without validating either index. [2](#0-1)  `blame_internal` then passes `recipient` to `decrypt_with_proof` as `decryptor`. [3](#0-2) 

When a proof is supplied, `decrypt_with_proof` constructs the point list `[self.enc_keys[&decryptor], *proof.key]`. [4](#0-3)  HashMap indexing panics for an absent key, so any `decryptor` greater than `n` reaches a panic before `DLEqProof::verify` can reject the supplied proof. The encrypted message must first pass its Schnorr proof-of-possession check, but `from` is attacker-controlled and is bound into the challenge, so the requester can generate a valid PoP for its own ephemeral encryption key. [5](#0-4) 

### Impact Explanation
A remote participant able to submit a blame verification request can abort the process handling it with a panic. This prevents the blamed material from being adjudicated and may terminate the processor/task instead of yielding a `Participant` result. The issue matches a reachable assertion/panic denial-of-service pattern: malformed protocol input reaches an unchecked invariant and crashes the caller.

### Likelihood Explanation
The triggering inputs are public protocol values: an out-of-range `Participant`, an `EncryptedMessage` whose PoP the attacker can generate, and any syntactically valid `EncryptionKeyProof`. The DLEq proof itself does not need to verify because the missing-map-entry panic occurs while constructing its verification inputs. `Participant::new` accepts every nonzero `u16`, while the `AdditionalBlameMachine` map contains only `1..=n`, making `n + 1` a straightforward trigger. [6](#0-5) 

### Recommendation
Validate `sender` and `recipient` in `AdditionalBlameMachine::blame` or `BlameMachine::blame_internal` before consulting protocol state. Specifically:

- Reject `sender > n`, `recipient > n`, and `sender == recipient`.
- Prefer `HashMap::get` plus an explicit error/fault result over `HashMap` indexing for attacker-controlled identifiers.
- Consider returning `sender` or another deterministic faulty party when an invalid participant is supplied, according to the protocol’s blame semantics.

### Proof of Concept
Conceptually, for a DKG with `n` participants:

```rust
let out_of_range_recipient = Participant::new(n + 1).unwrap();

// Construct bytes for an EncryptedMessage with:
// - key = G * k for attacker-known nonzero k
// - pop = Schnorr signature for challenge
//   pop_challenge(context, R, key, sender, ciphertext)
// - ciphertext = arbitrary SecretShare-sized bytes
let msg = EncryptedMessage::<C, SecretShare<C::F>>::read(
    &mut attacker_generated_bytes,
    params,
).unwrap();

// Any parseable EncryptionKeyProof is sufficient; its DLEq proof is not reached
// before the panic.
let proof = EncryptionKeyProof::read(&mut syntactically_valid_proof).ok();

machine.blame(attacker_sender, out_of_range_recipient, msg, proof);
```

Execution reaches `self.enc_keys[&decryptor]` with `decryptor == n + 1`, where `enc_keys` contains only `1..=n`, causing a panic.
