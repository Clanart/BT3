### Title
Cached FROST preprocess is never cleared, causing deterministic nonce reuse across repeated signing calls - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` persists a FROST preprocess seed in `CachedPreprocesses` keyed by `context` and regenerates the exact same `AlgorithmSignMachine` — and therefore the exact same secret nonces — on every subsequent call. `share_internal` invokes `preprocess_internal` again each time it runs, and both `DkgConfirmer::share` and `DkgConfirmer::complete` route through `share_internal`. The cached seed is never deleted after use. Because the message signed (`set_keys_message`) and the signing set are derived from per-call inputs (`key_pair`, `preprocesses` map), any two invocations under the same context with differing message or differing participant set produce two FROST signature shares under identical nonces with different challenges — the classic nonce-reuse equation that yields the signer's private key share.

### Finding Description
- `CachedPreprocesses` is written only when the key is absent: `if CachedPreprocesses::get(self.txn, &self.context).is_none() { ... CachedPreprocesses::set(...) }` (lines 123–134). There is no removal anywhere in the codebase; every future call hits `CachedPreprocesses::get(...).unwrap()` at line 137 and decrypts the same 32-byte seed.
- `AlgorithmSignMachine::from_cache` → `seeded_preprocess` seeds `ChaCha20Rng::from_seed(*seed.0)` and derives `nonces` and `commitments` deterministically (`crypto/frost/src/sign.rs:127-132`). Same seed ⇒ identical nonces `d, e` and identical preprocess.
- `share_internal` (line 156) calls `self.preprocess_internal(participants).0`, so each call to `share`/`complete` rebuilds a machine with the same nonces. `DkgConfirmer::share` (line 304) and `DkgConfirmer::complete` (line 312, which internally calls `share_internal` again at line 322) both sign `msg = set_keys_message(set, removed, key_pair)` (lines 296–300), where `key_pair` and the `preprocesses`/`shares` maps are supplied per call.
- FROST share: `z = d + e·ρ + λ·s·c`, where `c` binds the message and the aggregate commitment `R` of the included participant set. Two shares from the same `(d, e)` under different `(c, ρ, λ)` give two linear equations in `d, e, s`, recovering the secret share `s` — precisely the failure the API documents: "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" (`crypto/frost/src/sign.rs:218-219`), and "Reusing preprocesses would enable a third-party to recover your private key share" (`spec/cryptography/FROST.md:51-52`).
- The abort-handling analog of the CVE (a stale pointer left set after an abort path) maps exactly: the cached preprocess is the "pending pointer" that must be cleared on first use, and it is left populated for the lifetime of the context.

### Impact Explanation
Recovery of the coordinator node's MuSig/FROST private key share for the validator set context (`("DkgConfirmer", attempt)`). The encrypted-at-rest protection (lines 104–115) only guards DB reads; the vulnerability is deterministic reuse, not storage. With the key share recovered, combined with threshold-1 other shares, the set's Schnorrkel key — used to attest DKG key confirmations — can be compromised, enabling forged set-keys signatures.

### Likelihood Explanation
Medium. The reuse is unconditional in code — every `share`/`complete` under one context reloads the same seed. Exploitation additionally requires two distinct signing inputs under the same context (e.g., `share` then `complete` invoked with a different `key_pair`, or a differing participant preprocess set changing `R`/`c`). Those inputs arrive via tributary DKG-confirmation messages, so the trigger depends on protocol flow rather than purely external bytes; however, nothing in this file enforces that the message or set is identical across calls, and the documented safety invariant ("delete after first use") is violated by design.

### Recommendation
Delete the cache entry atomically when it is loaded in `preprocess_internal` (a `CachedPreprocesses::kill`/`remove` immediately after `get`, within the same transaction), so a second signing attempt generates a fresh preprocess instead of reusing the seed. Alternatively, cache the `AlgorithmSignMachine`/nonces in memory for the single intended session and never re-derive from a persisted seed. Add a regression test asserting two `share_internal` calls under the same context cannot produce identical commitments.

### Proof of Concept
Conceptual reproduction against `DkgConfirmer`:

```rust
// Same spec, same attempt => same context ("DkgConfirmer", attempt)
let mut confirmer = DkgConfirmer::new(&key, &spec, txn, attempt).unwrap();

// First signing: broadcasts share for confirmation A.
// Internally: CachedPreprocesses::set(ctx, seed) once, then from_cache(seed).
let share1 = confirmer.share(preprocesses_A, &key_pair_A).unwrap();

// Second signing under the SAME context: preprocess_internal reloads the same
// seed (line 137), seeded_preprocess regenerates identical nonces d, e.
// If key_pair_B != key_pair_A, msg differs; even with equal msg, a different
// preprocesses map changes R and c.
let _machine = confirmer.share_internal(preprocesses_B, &key_pair_B).unwrap();
// share2 = d + e*rho' + lambda*s*c'   (same d, e as share1)
// Solve: s = (z1 - z2 - (d' terms)) / (lambda*(c1 - c2)) => secret share recovered
```

Verification that the seed is identical is direct: `from_cache` at `crypto/frost/src/sign.rs:273` calls `seeded_preprocess`, and `ChaCha20Rng::from_seed(*seed.0)` at line 127 makes `Commitments::new` (line 128) deterministic. The only divergence between the two shares is the transcript-challenge terms driven by the caller-supplied `preprocesses`/`key_pair`.
