## Analysis

The external report's core pattern — an unprivileged caller flooding a bounded queue with minimal-cost entries to evict/grief another party's stake, or forcing a limit-triggered revert to block a legitimate operation — maps onto Hyperbridge's `pallet-bandwidth` / `BandwidthManager.sol` subscription ledger.

### Title
Unprivileged Griefing of Any App's Bandwidth Allowance via FIFO Eviction in `push_subscription` - (File: `modules/pallets/bandwidth/src/lib.rs`, `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` on EVM lets **any caller** credit bandwidth to **any `app` on any `chain`** — the `app` parameter is fully attacker-chosen and is never checked against `msg.sender`. On the Hyperbridge side, `pallet_bandwidth::push_subscription` appends every credited subscription to a `(app_chain, app)` FIFO list capped at `MAX_SUBSCRIPTIONS = 1024`; once full, each new push **silently evicts the oldest entry**, discarding whatever unconsumed `remaining_bytes` it still held. Because purchases are keyed purely by the attacker-supplied `(chain, app)` pair rather than by the payer's identity, an attacker can target a victim app's bucket directly, buying the cheapest configured tier repeatedly until the victim's real, already-paid-for, unconsumed subscription(s) are evicted out of the list — permanently destroying bandwidth the victim already paid for.

### Finding Description
`purchase()` takes `app` and `chain` as raw calldata with no ownership check: [1](#0-0) 

The pallet-side `on_accept` path credits whatever `(app_chain, app)` the message specifies via `push_subscription`, which enforces the 1024 cap by evicting the oldest live entry regardless of who purchased it: [2](#0-1) 

The cap itself is fixed at 1024 with no per-payer or per-purchase-count throttling: [3](#0-2) 

`Allowance` storage is keyed by `(app_chain, AppKey)` derived only from the message body — not from `msg.sender`/`payer`/`paid_from` — so there is no notion of "my own bucket" versus "someone else's bucket": [4](#0-3) 

The docs themselves confirm the eviction design was reasoned about only for the legitimate owner's own repeat-buy behavior, not for a targeted third party: [5](#0-4) 

This is the direct structural analog of the report's "small deposits fill the queue" vector: instead of 1-wei deposits, the attacker spends the cheapest tier price repeatedly against a victim's `(chain, app)` key to force-evict the victim's legitimately purchased, still-unconsumed subscription(s).

### Impact Explanation
Eviction destroys `remaining_bytes` the victim already paid for — this is a direct loss of funds for the victim app, achieved by an unprivileged, unauthenticated caller with no relayer/prover/admin assumptions. It also degrades the victim's live bandwidth gate check (`BandwidthGate::try_consume`), which can cause the victim's genuine ISMP dispatches to start failing with `GateError::Insufficient`/`NoAllowance` — a form of unauthorized denial of legitimate cross-chain execution for the targeted app: [6](#0-5) 

### Likelihood Explanation
Any address can call `purchase()` for any `(app, chain)` pair once at least one tier is configured and its manager registered — no whitelist or ownership check gates who may top up an app's bucket: [7](#0-6) 
The only cost is the fixed tier price × number of pushes needed to walk the FIFO to the victim's entry (worst case up to 1024 × cheapest tier price). This is economically bounded but fully achievable by a motivated attacker (e.g., a competitor wanting a specific app starved of bandwidth), and requires no compromise of relayers, provers, or governance.

### Recommendation
- Scope `Allowance` (or at least eviction eligibility) by payer/owner so a third party cannot push into another app's queue, or require `force_credit`-style admin gating for cross-payer top-ups.
- Alternatively, disallow eviction of subscriptions that were not purchased by the same payer chain/relationship, or refund/notify on eviction so it's not silent loss for the legitimate holder.
- Consider a minimum reservation policy (e.g., protect the front N entries from eviction if `paid_from` differs from the evicting purchase's `paid_from`), or raise/parametrize `MAX_SUBSCRIPTIONS` per-app rather than a shared global constant that any address can pressure.

### Proof of Concept
1. Victim buys the `$1000` / 8 MB tier for `app = V`, `chain = "EVM-8453"`, creating one `Subscription` in `Allowance[EVM-8453][V]` with `remaining_bytes = 8_000_000`.
2. Attacker calls `BandwidthManager.purchase(app = V, tier = TierOne ($50/100KB), months = 1, chain = "EVM-8453")` on the same source-chain manager, repeatedly (up to 1024 times if the bucket starts near-empty, fewer if it already has entries ahead of the victim's).
3. Each attacker purchase dispatches a `BandwidthPurchaseMsg` to `pallet-bandwidth`; `on_accept` → `push_subscription` appends the attacker's tiny subscription, and once the list reaches 1024 entries, every further attacker purchase evicts the oldest entry per: [8](#0-7) 
4. Once the victim's entry becomes the oldest and gets evicted, `SubscriptionEvicted` fires with `lost_bytes = 8_000_000` — the victim's paid allowance is gone even though they never consumed it, and their app is now denied by the gate on its next dispatch.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
