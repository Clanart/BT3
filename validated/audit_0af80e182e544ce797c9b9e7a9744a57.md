### Title
Same-chain intent fills pool escrow by token address, letting a solver drain another output-pair's reserved input tokens - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` computes the escrow to release for a completed output-token pair by reading the *entire* current balance of `_orders[commitment][token]` instead of the amount specifically attributable to that `(input[i], output[i])` pair. Because `_orders` is keyed only by `(commitment, token address)` — the same aggregation pattern as `CErc721`'s flat, non-differentiated `heldNFTs`/exchange-rate accounting — multiple distinct escrowed input allocations that happen to share a token address are pooled into one fungible bucket. A solver can complete one output pair first and receive the whole pool, starving/locking the other output pair.

### Finding Description
`Order.inputs` and `Order.output.assets` are parallel arrays with no uniqueness constraint on `inputs[i].token`, and `_orders` escrow storage is keyed purely by `(commitment, tokenAddress)`: [1](#0-0) 

In `_fillSameChain`, when a fill completes an output pair (`amountFilled == totalRequired`), the code does **not** compute the proportional remainder for that pair — it instead reads whatever is currently sitting in the pooled escrow slot for that input token and releases all of it: [2](#0-1) 

For any *incomplete* fill it correctly uses the proportional formula `(order.inputs[i].amount * fillAmount) / totalRequired`, matching the documented behavior ("proportional share of escrowed inputs is released" per `docs/content/developers/evm/intent-gateway/overview.mdx:33`), but the "full completion" branch abandons per-pair attribution and just drains the shared pool.

If an order has two output pairs whose corresponding `inputs[i].token` is the *same* address (a normal configuration — e.g. one USDC input funding two different output tokens), both allocations are escrowed under the single `_orders[commitment][USDC]` counter at `placeOrder`. Whichever output pair a solver chooses to fully fill *first* triggers `escrowedAmount = _orders[commitment][USDC]`, which at that point still contains the reserve meant for the *other*, not-yet-filled pair. `_withdraw` then transfers that entire pooled amount to the first solver and decrements `_orders[commitment][USDC]` to zero.

### Impact Explanation
This is a false/incorrect escrow-accounting acceptance analogous to the reported bug's fixed/undifferentiated valuation: distinct, differently-earmarked escrow allocations are treated as fungible and released in full to whichever fill happens first. Consequences:
- **Unjust enrichment of one solver / fund loss to the user**: the first solver to complete any output pair sharing the token receives input tokens that were meant to also cover a second output pair, while only having delivered one output's worth of value.
- **Griefing/locking the order**: the second output pair's fill later reads `_orders[commitment][token] == 0` and `_withdraw` reverts with `UnknownOrder` (escrowed == 0 check), permanently blocking that output pair from ever being filled — escrow for it is gone, and the corresponding output is never delivered to the user.
- No malicious relayer, prover, admin, or leaked key is required — any unprivileged solver calling the public `fillOrder`/`_fillSameChain` entrypoint can trigger this by choosing fill order.

### Likelihood Explanation
Requires only that an order contains two (or more) output-asset entries whose paired `inputs[i].token` addresses coincide — a legitimate and unrestricted configuration (nothing in `_validateParams` or the `Order`/`TokenInfo` structures forbids duplicate input tokens). Any solver observing such an order in the mempool/auction can simply choose which output pair to fully complete first to capture the pooled escrow. This requires no privileged role and no cross-chain proof manipulation, making it directly reachable by a normal (even honest-looking) solver.

### Recommendation
Track escrow per `(commitment, inputIndex)` rather than per `(commitment, tokenAddress)`, or compute the released amount for the "final increment" of a pair using the same proportional formula (`totalRequired - alreadyFilled` scaled against `order.inputs[i].amount`) instead of reading the shared token-keyed balance. If pooling by token address is intentional for gas efficiency, add an invariant that rejects orders whose `inputs[i].token` values collide across indices that fund different output pairs, or reconcile using running per-index escrow ledgers so a full-completion release can never exceed the specific pair's proportional entitlement.

### Proof of Concept
1. User places a same-chain order with:
   - `inputs = [ {token: USDC, amount: 1000}, {token: USDC, amount: 1000} ]`
   - `output.assets = [ {token: DAI, amount: 900}, {token: WETH, amount: 0.3} ]`
   At `placeOrder`, both 1000 USDC entries are pulled into escrow and aggregated as `_orders[commitment][USDC] = 2000`.
2. Solver A calls `fillOrder` providing only `options.outputs[0] = {DAI, 900}` (full amount for output pair 0) and `options.outputs[1] = {WETH, 0}` (skips pair 1, so `remaining>0, solverAmount==0` sets `isFullyFilled=false`, i.e., a partial fill of the order overall but a *full* completion of output-pair 0).
3. In the loop, for `i = 0`: `amountFilled == totalRequired` (900==900) → `escrowedAmount = _orders[commitment][USDC]` = **2000** (the full pool, not the 1000 earmarked for pair 0). `_withdraw` sends 2000 USDC to Solver A and sets `_orders[commitment][USDC] = 0`.
4. Solver B later attempts to fill output pair 1 (WETH) for the remaining order. At `i = 1` (assuming a second call re-derives the same commitment/order), the code tries `escrowedAmount = _orders[commitment][USDC]` = 0 while `amount != 0` is required by `_withdraw`'s `if (escrowed == 0) revert UnknownOrder()` check — the fill reverts, permanently locking output pair 1's fulfillment even though the user already lost 2000 USDC of escrow for delivering only 900 DAI worth of output.
