### Title
Excess native token sent to `EvmHost.dispatch`/`dispatch(GetRequest)`/`fundRequest` is never refunded and gets permanently stuck in the Host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost` accepts native-token payment for outbound POST/GET dispatch and for `fundRequest`, converting `msg.value` into `feeToken` via a Uniswap-V2-style `swapETHForExactTokens` call. The function only requests conversion of the exact `post.fee`/`get.fee`/`amount` needed, but never checks for or forwards back any leftover native token/feeToken to the original caller. This is the same broken invariant as the referenced Sherlock M-7 report: a contract that is supposed to only consume a partial amount of the caller's `msg.value` silently retains the remainder instead of sweeping it back.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all follow the same pattern: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
}
```

The whole `msg.value` is forwarded into the swap, requesting only `post.fee` in output tokens (`swapETHForExactTokens` semantics = "exact tokens out, variable ETH in"). Whatever is not consumed by the swap is expected to be refunded to the caller of the router — but the caller here is `EvmHost` itself (`address(this)` performing the external call), not the original transaction sender (`_msgSender()`). Depending on which router/wrapper is configured for `_hostParams.uniswapV2`:

- The `GnosisUniswapV2Wrapper` deposits the *entire* `msg.value` into WETH and transfers the entire amount to `msg.sender` (the Host) regardless of `amountOut`, meaning any native-token overpayment is converted 1:1 into feeToken and simply added to the Host's own feeToken balance: [2](#0-1) 

- The `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper` do refund unused ETH, but the refund target is `msg.sender`, i.e. `EvmHost`, not the end user: [3](#0-2) [4](#0-3) 

Either way, the surplus lands and stays inside `EvmHost`. `dispatch`, `dispatch(GetRequest)`, and `fundRequest` have no analogous `_refundExcess()` step: [5](#0-4) [6](#0-5) 

This is directly reachable by unprivileged, legitimate protocol usage: multiple downstream apps forward the caller's full `msg.value` straight into `EvmHost.dispatch` without pre-computing/capping the exact swap input, exactly mirroring the `Edition.mint` pattern in the referenced report: [7](#0-6) [8](#0-7) [9](#0-8) 

The docs themselves instruct users to send `msg.value` liberally ("User must send enough native tokens to cover fees") without describing any refund mechanism: [10](#0-9) 

By contrast, `IntentGatewayV2`/`ExtrinsicIntents` explicitly compute the exact `nativeDispatchFee`/`amounts[0]` consumed and refund the remainder to `msg.sender` at their own layer before ever calling `EvmHost.dispatch`, proving the team is aware overpayment must be refunded — but this discipline is missing inside `EvmHost` itself and in the simpler token-bridge apps that call it directly: [11](#0-10) [12](#0-11) 

### Impact Explanation
Any user or app contract that sends more native token than strictly required to `EvmHost.dispatch`/`dispatch(GetRequest)`/`fundRequest` (which is the expected usage pattern for client-side fee estimation, per the docs) permanently loses the difference — it is converted to feeToken or ETH and retained inside `EvmHost` with no user-facing sweep path. Over time this can accumulate non-trivial value across many callers of `HyperFungibleToken.send`, `WrappedHyperFungibleToken.send`, and `HyperbridgeLzEndpoint.send`, none of which pre-trim `msg.value` to the exact fee before forwarding. Because `EvmHost` exposes a governance-controlled `withdraw(WithdrawParams)` path reachable only via the `hostManager`, this trapped user value is indistinguishable on-chain from legitimate protocol revenue and could be swept out by governance, i.e. user funds end up diverted from their rightful owner (the overpaying depositor) to whatever the withdraw beneficiary is set to.

### Likelihood Explanation
High likelihood in normal operation: users/integrators are explicitly told to estimate and send native token for fees, and price movement between quote-time and execution or naive over-provisioning of `msg.value` (a common practice to ensure the swap doesn't revert) will routinely leave a remainder. No malicious actor, relayer, or governance participant is needed — the loss occurs purely from standard fee-paying interactions with the public `dispatch`/`fundRequest` entry points.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the actual amount spent from `swapETHForExactTokens`'s return value and refund `msg.value - amountSpent` back to `_msgSender()` before returning, exactly as `IntentGatewayV2`/`ExtrinsicIntents` already do for their own inbound `msg.value`. Alternatively, require callers to pass the exact expected native amount and revert on mismatch rather than silently absorbing the difference.

### Proof of Concept
1. Configure `EvmHost` with any of the supported Uniswap-V2-compatible wrappers (`GnosisUniswapV2Wrapper`, `UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`).
2. A user calls `HyperFungibleToken.send{value: 1 ether}(params)` where `params.relayerFee` only requires e.g. 0.1 ETH worth of feeToken (a normal safety-margin overpayment as instructed by the docs).
3. `HyperFungibleToken.send` forwards the full `msg.value` to `EvmHost.dispatch{value: 1 ether}(request)`.
4. Inside `dispatch`, `swapETHForExactTokens{value: 1 ether}(post.fee, ...)` swaps only enough ETH to produce `post.fee` feeToken; any refund (native, per UniV3/V4 wrapper) or over-converted feeToken (per Gnosis wrapper) is returned to `address(this)` (`EvmHost`), not to the user.
5. `dispatch` returns without ever checking or forwarding a remaining balance to `_msgSender()`; the ~0.9 ETH-equivalent surplus is now permanently held by `EvmHost`, unrecoverable by the user, and only extractable later via the governance-only `withdraw` path.

        external

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);

    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee

        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
