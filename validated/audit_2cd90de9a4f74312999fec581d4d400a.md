### Title
Reentrancy-style guard bypass: `_fetchRefspec` races with in-flight push/pull/fetch and can corrupt refs before a push completes - ([File: app/src/lib/stores/app-store.ts])

### Summary
GitHub Desktop uses an in-memory, per-repository flag (`isPushPullFetchInProgress`) as a "non-reentrant"-style guard to prevent two network operations (push/pull/fetch) from mutating the same repository's refs and working tree concurrently. However, `_fetchRefspec` — a dispatcher-exposed method explicitly documented as bypassing this guard — can run a `git fetch` against the same repository while a guarded push/pull/fetch is in flight, breaking the single invariant the guard exists to protect. This is the same class of bug as the reported issue: a protective check exists on some entry points but not all of the code paths that can mutate the same shared state, so an attacker who controls what gets fetched (a malicious fork remote / PR head) can race an in-progress push and cause Desktop to read/act on inconsistent ref state.

### Finding Description
`withPushPullFetch` is the only mechanism Desktop uses to prevent concurrent network git operations against a repository: [1](#0-0) 

It is used by `performPull` and `performFetch` (which back `_pull`, `_fetch`, `_fetchRemote`), and it also guards the follow-up state-mutating steps that run on the *same* repository after a push: `fastForwardBranches`, `refreshBranchProtectionState`, and `_refreshRepository`: [2](#0-1) 

But `_fetchRefspec` is explicitly carved out of this protection, by design, per its own doc comment: [3](#0-2) 

It is exposed to the rest of the app through `Dispatcher.fetchRefspec`: [4](#0-3) 

and ultimately calls `git fetch <remote> <refspec>` for every configured remote of the repository (including any attacker-influenced fork remote added for PR checkout, see `ForkedRemotePrefix`/`forkPullRequestRemoteName` remotes in `_findPullRequestBranch`): [5](#0-4) [6](#0-5) 

Because `_fetchRefspec` does not check or set `isPushPullFetchInProgress`, it can execute concurrently with an in-flight `_push`/`_pull`/`_fetch` on the exact same repository working directory and `.git` ref namespace. A concurrently running `git fetch` mutates remote-tracking refs and `FETCH_HEAD`/objects while the guarded operation is mid-sequence (`pushRepo` → `fetchRemotes` → `fastForwardBranches` → `refreshBranchProtectionState` → `_refreshRepository`), so the state Desktop reads back (`gitStore.tip`, `gitStore.aheadBehind`, `branchesState`) can reflect a mix of the two operations' results rather than either operation's atomic outcome — analogous to the report's "components redeemed at different conversion rates" because the corrupted invariant is: *at most one network mutation of this repository's refs is in flight at a time*. Just as in the original report, the guard (`nonReentrant`/`withPushPullFetch`) only protects the entry points on "one contract" (the dispatcher's push/pull/fetch trio) and not a sibling entry point (`_fetchRefspec`) that touches the same shared resource.

### Impact Explanation
If a malicious fork/remote's ref content changes between the moment Desktop decides what to fast-forward/push and the moment `_fetchRefspec` races in a fetch of that same remote, Desktop's cached `tip`/`aheadBehind`/branch-protection state used to drive the next commit/push can silently reflect stale or attacker-influenced data. Because `fastForwardBranches` and subsequent `_refreshRepository` calls are not isolated from the concurrent fetch, this can lead to Desktop computing incorrect ahead/behind information, fast-forwarding a local branch based on refs updated out of the expected sequence, or refreshing branch-protection state incorrectly — i.e., silent corruption of what the user believes they are about to commit or push, which matches the "Valid Impact" criteria (silent corruption of what the user commits or pushes) driven by an attacker-controlled remote/fork.

### Likelihood Explanation
The bypass is not theoretical: it is explicitly acknowledged in the source comment as an intentional, undocumented-elsewhere gap ("it does not opt-in to checks that prevent multiple concurrent network actions... this might require some rework in the future to chain these actions"). I was unable to conclusively confirm, within the scope of the code available to me, an existing UI call site for `Dispatcher.fetchRefspec`/`_fetchRefspec` (my search for `dispatcher.fetchRefspec(` only surfaced the definitions, not a caller) — a full Devin agent session with complete repository access should verify whether this is currently wired to the PR-from-fork UI or to a URL/deep-link handler, since the doc comment states its intended purpose is "viewing a Pull Request from a fork." Because the timing window depends on the user (or an automatic background/PR-preview flow) triggering a fetch while a push/pull is in progress, exploitation requires some coincidence of timing but is entirely attacker-triggerable by controlling the fork/remote content that gets fetched.

### Recommendation
Route `_fetchRefspec` (and any other git-mutating method on `AppStore` that touches remote-tracking refs) through the same `withPushPullFetch` guard, or replace the boolean in-memory flag with a per-repository operation queue/mutex in `GitStoreCache`/`RepositoryStateCache` so that *all* ref-mutating git invocations for a given repository are serialized, not just the push/pull/fetch trio. If `_fetchRefspec` must run without blocking (e.g., to keep PR-preview UX responsive), it should at minimum avoid mutating shared branch/tip state consumed by an in-flight push, e.g., by fetching into a private/anonymous ref namespace rather than the shared remote-tracking refs.

### Proof of Concept
1. Open a repository in Desktop with an in-progress long-running `git push` (e.g., large repo/slow network) so `isPushPullFetchInProgress` is `true`.
2. While the push is in flight, trigger a code path that calls `Dispatcher.fetchRefspec` / `AppStore._fetchRefspec` against the same repository (e.g., via the pull-request-from-fork flow referenced in the method's doc comment) targeting a fork remote whose ref content is attacker-controlled.
3. Because `_fetchRefspec` bypasses `withPushPullFetch`, the fetch runs concurrently with the push's post-processing (`fetchRemotes` → `fastForwardBranches` → `_refreshRepository`), updating remote-tracking refs/`FETCH_HEAD` mid-sequence.
4. Observe that `gitStore.tip`/`aheadBehind`/branch state reflects a mix of both operations, demonstrating the invariant "only one network ref mutation at a time" no longer holds — confirmable statically from the code paths cited above (`app/src/lib/stores/app-store.ts:5427-5450`, `5866-5885`) without needing to reproduce exact timing, since the guard bypass is unconditional and by design.

  private async withPushPullFetch(
    repository: Repository,
    fn: () => Promise<void>
  ): Promise<void> {
    const state = this.repositoryStateCache.get(repository)
    // Don't allow concurrent network operations.
    if (state.isPushPullFetchInProgress) {
      return
    }

    this.repositoryStateCache.update(repository, () => ({
      isPushPullFetchInProgress: true,
    }))
    this.emitUpdate()

    try {
      await fn()
    } finally {
      this.repositoryStateCache.update(repository, () => ({
        isPushPullFetchInProgress: false,
      }))
      this.emitUpdate()
    }
  }

export async function fetchRefspec(
  repository: Repository,
  remote: IRemote,
  refspec: string

  await git(['fetch', remote.name, refspec], repository.path, 'fetchRefspec', {
    successExitCodes: new Set([0, 128]),
