### Title
mWOMSVBaseRewarder never applies cooldown-based forfeiture, allowing mWomSV holders to claim rewards forfeit-free while equivalent vlMGP holders are penalized - (rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` sets `rewardableAmount = _amount` unconditionally and never calls `mWomSV.getRewardablePercentWAD(_account)`, so `forfeitAmount` is always `_amount - _amount = 0`. The structurally identical `vlMGPBaseRewarder._calExpireForfeit` correctly calls `vlMGP.getRewardablePercentWAD(_account)` and scales `rewardableAmount` by that percentage, causing real forfeiture during cooldown. This asymmetry lets any mWomSV holder claim 100% of rewards through `mWOMSVBaseRewarder.getReward`/`getRewards` regardless of cooldown state, while an equivalent vlMGP holder in the same cooldown state is penalized.

### Finding Description
In `rewards/mWOMSVBaseRewarder.sol`:
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
``` [1](#0-0) 

`rewardableAmount` is set to `_amount` directly, with no reference to `mWOMSV.getRewardablePercentWAD(_account)`. This is unlike `vlMGPBaseRewarder._calExpireForfeit`:
```
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
``` [2](#0-1) 

Both `mWomSV.getRewardablePercentWAD` [3](#0-2)  and `VLMGP.getRewardablePercentWAD` [4](#0-3)  are structurally identical, computing a rewardable percentage based on `amountInCoolDown`/`startTime`/`endTime` per unlock slot — confirming both lockers intended to enforce the same partial-forfeiture mechanism during cooldown.

`_calExpireForfeit` in `mWOMSVBaseRewarder` is invoked from `_sendReward`, which is called by `getReward`/`getRewards` (both gated only by `onlyMasterMagpie`, forwarded from user-initiated claim calls through `MasterMagpie`): [5](#0-4) 

Since `mWOMSVBaseRewarder` never queries `mWOMSV.getRewardablePercentWAD`, `forfeitAmount` is always `0` for every claim, irrespective of whether the account has active cooldowns. No modifier, pausability, or accounting check compensates for this — the omission is purely in the arithmetic of `_calExpireForfeit`.

### Impact Explanation
This is a theft/misallocation of unclaimed yield: forfeited rewards are meant to be redistributed to remaining stakers (via `_queueNewRewardsWithoutTransfer`), but for `mWomSV`/`mWOMSVBaseRewarder` this pool never receives any forfeiture, and cooling-down or partially-locked mWomSV holders keep 100% of rewards they would have forfeited under the vlMGP-equivalent path. This matches the "theft or permanent freezing of unclaimed yield" impact class — attackers preferentially route yield-bearing lock positions through mWomSV to systematically avoid the cooldown-forfeiture mechanism that vlMGP holders are subject to, extracting value that should have been redistributed to loyal (non-cooling-down) stakers.

### Likelihood Explanation
Any unprivileged holder of mWomSV (obtained via direct wrap/mint or via `SmartWomConvert`) can trigger this at zero extra cost: start unlock (`startUnlock`), then call `getReward`/`getRewards` through `MasterMagpie` at any time, including immediately during cooldown. No special capital, timing, or governance/admin privilege is required, and the behavior is 100% reproducible on every claim. This is a fully deterministic code-path bug, not a probabilistic/race-based exploit.

### Recommendation
Update `mWOMSVBaseRewarder._calExpireForfeit` to mirror `vlMGPBaseRewarder._calExpireForfeit`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = mWOMSV.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
    }
    return forfeitAmount;
}
```
Ensure `ILocker` (the interface typed for `mWOMSV`) exposes `getRewardablePercentWAD`, since `mWomSV` implements it per the code read above.

Assert: vlMGP path — `RewardPaid` amount is `earned * rewardablePercentWAD/1e18` (with forfeiture emitted via `ForfeitRewardAdded`); mWomSV path — `RewardPaid` amount equals full `earned` amount with `forfeitAmount == 0` despite identical cooldown percent, directly demonstrating the missing `getRewardablePercentWAD` call in `mWOMSVBaseRewarder._calExpireForfeit`.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
