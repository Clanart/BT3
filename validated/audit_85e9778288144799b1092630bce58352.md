### Title
Scanner credits unspendable dust outputs as received funds, with no per-output skip — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
Analogous to the Asymmetry M-02 mitigation gap — where a small residual amount could not be skipped on a call-by-call basis and instead blocked the whole operation — `bitcoin-serai`'s `Scanner` accepts *any* on-chain output paying to a watched script, regardless of value. There is no minimum-value/`previewRedeem`-style check, so an unprivileged attacker can send dust outputs (below `DUST` = 546 sat, or below the processor's economic-spendability threshold of 10,000 sat) to the multisig's external address. These are registered as `ReceivedOutput`s, reported upstream by `Bitcoin::get_outputs`, and treated as real received funds even though they are economically — or even literally — unspendable.

### Finding Description
`Scanner::scan_transaction` filters solely on `script_pubkey` membership:

```rust
// networks/bitcoin/src/wallet/mod.rs:201-211
for (vout, output) in tx.output.iter().enumerate() {
  let Ok(vout) = u32::try_from(vout) else { break };
  if let Some(offset) = self.scripts.get(&output.script_pubkey) {
    res.push(ReceivedOutput {
      offset: *offset,
      output: output.clone(),
      outpoint: OutPoint::new(tx.compute_txid(), vout),
    });
  }
}
```

No check on `output.value` is performed anywhere in the scan path. `Bitcoin::get_outputs` (processor) wraps each scanned output and reports it without an amount filter (`processor/src/networks/bitcoin.rs:691-700`). On the spend side, `SignableTransaction::new` happily consumes any input value (`send.rs:175-185`), and the fee amortization/`DUST` checks only apply to *payments* and *change*, never to inbound outputs.

The external report's key insight — "the issue presents when the amount is small, so it doesn't matter much if the call is skipped in that case; the fix is to check and skip" — maps directly here: the scanner is the inbound equivalent of `unstake()`, and it lacks the "skip when economically worthless" guard.

### Impact Explanation
- **Funds reported received that are not spendable**: an attacker can pay a miner (or use a low-value but standard ≥546-sat output whose spending cost exceeds its value under the processor's `DUST`/`COST_TO_AGGREGATE` model — a Taproot input costs ~57 vbytes, i.e. ~285+ sat at 5 sat/vB before output costs) to create outputs credited by Serai while being net-negative to spend. Serai reports balance it cannot realize.
- **Fee griefing**: when the scheduler aggregates these inputs, each dust input adds ~57 vbytes of weight while contributing nearly nothing, inflating `needed_fee` (`send.rs:204-206`) and burning real funds on every transaction that includes them. Unlike the mitigated Asymmetry case, there is no way to "disable" an output once scanned — `ram_outputs`/`seen` persistence means the output is permanently tracked.

### Likelihood Explanation
Any Bitcoin user can send a transaction to the publicly known/derivable multisig address (and to the Branch/Change/Forwarded offset addresses, whose scripts are deterministic functions of the group key). No validator cooperation, key material, or protocol privilege is required. Creating sub-546-sat outputs requires miner cooperation, but ≥546-sat economically-unspendable outputs are trivially relayable, making the attack cheap and repeatable.

### Recommendation
Apply the external report's own fix pattern: skip, on a per-output basis, any scanned output whose value is below a spendability threshold. Add a value check in `Scanner::scan_transaction` (or in `Bitcoin::get_outputs`, using `Network::DUST`/`COST_TO_AGGREGATE` so the threshold reflects the cost to spend the input plus its proportional share of the transaction), e.g. `if output.value.to_sat() < MIN_SPENDABLE { continue; }`, so dust outputs are never reported rather than tracked as unspendable-but-credited funds.

### Proof of Concept
1. Derive the multisig's external P2TR address (public group key → `p2tr_script_buf`, `mod.rs:80-86`) or any registered offset script.
2. Broadcast a transaction with an output paying that script_pubkey with value 546 sat (standard, relayable) — or a smaller value via a cooperative miner.
3. `Bitcoin::get_outputs` (`processor/src/networks/bitcoin.rs:686-700`) returns it as `OutputType::External`; the processor scanner emits it in `ScannerEvent::Block`, and it is entered into the UTXO pool (`scheduler/utxo.rs:295`) and reported as received balance.
4. At a fee rate of ≥ ~10 sat/vB, spending the 57-vbyte input costs more than 546 sat; the output is a net liability. Every sweep/aggregation transaction including it pays more in marginal fee than the output contributes — funds credited but not spendable — with no mechanism to reject or skip the output.
