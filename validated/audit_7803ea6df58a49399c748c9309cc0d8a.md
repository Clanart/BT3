### Title
`ReceivedOutput::read` accepts an arbitrary `offset`/`TxOut` pair with no consistency check, letting untrusted bytes report outputs that cannot be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to functions missing their gating checks in the reference report, `ReceivedOutput::read` deserializes a spendable-output claim — a scalar `offset`, a `TxOut`, and an `OutPoint` — without performing the one check that gives the type meaning: that `p2tr_script_buf(scanner_key + G * offset)` equals `output.script_pubkey`. Any untrusted byte stream can therefore manufacture a `ReceivedOutput` that the wallet treats as a spendable received output yet whose declared offset does not derive the key the output actually pays to.

### Finding Description
`Scanner::scan_transaction`/`scan_block` are the only honest producers of `ReceivedOutput`, and they populate `offset` from the `scripts` map so the invariant `script_pubkey == p2tr(key + G*offset)` holds by construction (networks/bitcoin/src/wallet/mod.rs:199-214). `ReceivedOutput::read` (lines 122-134) reconstructs the same type from raw bytes but never re-establishes that invariant — it reads a scalar via `Secp256k1::read_F` and a `TxOut`/`OutPoint` via consensus decoding and stores them verbatim:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;
  ... // output and outpoint decoded, no cross-check
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

Downstream, `SignableTransaction`/`TransactionSignMachine` in `networks/bitcoin/src/wallet/send.rs` spend each input by applying the recorded offset to the threshold keys (`keys.offset(offset)` style re-keying), so the signature is only valid if `offset` actually derives the output's key. A mismatched offset yields an invalid BIP-340 signature; a fabricated `TxOut`/`OutPoint` yields an input that doesn't exist or pays someone else.

### Impact Explanation
An attacker who can feed bytes to `ReceivedOutput::read` (e.g., a malicious or compromised data source supplying serialized outputs to a processor/integrator) can cause funds to be reported as received that are not spendable: the wallet credits/queues an input whose declared offset does not correspond to the output's script key, so any spend attempt produces an invalid signature and fails on the network. This is the "funds reported received that are not spendable" impact class. Severity: Medium — it corrupts the wallet's view of spendable balance without leaking key material.

### Likelihood Explanation
The bug is deterministic once attacker-controlled bytes reach `read`. Whether it is exploitable depends on integrators deserializing `ReceivedOutput` from untrusted sources rather than producing it solely via `Scanner` locally; the public `read` API performs no authentication or consistency check, so nothing in the crate prevents it.

### Recommendation
Either:
- Make `ReceivedOutput` construction private to `Scanner` (remove/deprecate the public `read`, or gate it behind re-verification), or
- Add a `verify(&self, key: &ProjectivePoint) -> bool` / checked constructor that recomputes `p2tr_script_buf(key + G * offset)` and compares it to `output.script_pubkey`, and require callers to run it on deserialized outputs before treating them as spendable.

### Proof of Concept
1. Build a `Scanner` for an even key `K` and note script `S = p2tr(K)` for `offset = 0`.
2. Craft bytes: `offset' = random scalar` (≠ 0), `output = TxOut{ script_pubkey: S, value: V }`, `outpoint = arbitrary`.
3. `ReceivedOutput::read(&bytes)` returns `Ok(...)` with `offset'` despite `S` being derived from offset `0`.
4. Pass the result to `SignableTransaction`/`TransactionSignMachine`: the signer applies `offset'`, producing a Schnorr signature under key `K + G*offset'` — which does not equal the output's key, so the spend fails even though the wallet recorded `V` sats as received.
