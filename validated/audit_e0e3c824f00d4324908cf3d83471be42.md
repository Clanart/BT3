### Title
DataLayer Mirror URLs Allow Attacker-Controlled SSRF to Internal Services via Unvalidated HTTP Fetch - (File: chia/data_layer/download_data.py)

### Summary
Chia's DataLayer subsystem lets any singleton owner publish a list of arbitrary mirror URLs on-chain via `add_mirror`, and any other node that subscribes to that DataLayer store will have its local DataLayer service automatically fetch data from those attacker-supplied URLs with no allow-listing or destination restriction. This mirrors the Skipper `ExternalName` issue: an attacker-controlled "route" (here, an on-chain mirror URL) causes another party's networked service to make outbound requests to a target of the attacker's choosing, which can be used to reach internal/private services reachable from the victim's host.

### Finding Description
`DataLayer.add_mirror()` publishes an arbitrary, user-supplied list of URL strings on-chain with no validation of scheme, host, or target (e.g., no rejection of `127.0.0.1`, RFC1918 private ranges, link-local metadata endpoints, etc.): [1](#0-0) 

These mirror URLs are attacker-controlled from the perspective of any node that later subscribes to that store — `update_subscriptions_from_wallet()` pulls the mirror URL list straight from wallet/chain state for a given `store_id` and stores it as subscription server info, with only a trailing-slash strip, no host/scheme filtering: [2](#0-1) 

The periodic sync loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`) then iterates these server URLs and issues outbound HTTP requests to them via `insert_from_delta_file()`/`download_file()`/`http_download()`: [3](#0-2) [4](#0-3) 

The `.cursor/context/data-layer.md` notes explicitly acknowledge that "Plugin and mirror URLs are external trust inputs" and that downloaded data is verified against the wallet-advertised Merkle root, but this only protects the *content* returned — it does nothing to prevent the *request itself* from being sent to an internal address. There is no equivalent of Skipper's `-kubernetes-only-allowed-external-names` allow-list for DataLayer mirror/plugin URLs: [5](#0-4) 

An attacker who creates a DataLayer store and publishes mirror URLs pointing at internal-only endpoints (e.g., cloud metadata services, internal admin APIs, or other localhost services on the victim's machine/network) can cause any victim that subscribes to that store — a routine, low-privilege DataLayer client action — to issue outbound HTTP requests to those internal targets on a recurring, timed basis via the sync loop.

### Impact Explanation
This is a genuine SSRF primitive reachable by an unprivileged Data Layer client: subscribing to a store is a normal, expected DataLayer action (`subscribe`/RPC), and the resulting outbound requests are made by the DataLayer service process, not by the browser or a sandboxed context. Depending on network placement (cloud metadata endpoints, internal RPC/admin ports, other local services bound to localhost), this can leak credentials/tokens or allow limited interaction with internal-only services. It does not directly cause coin-state divergence, fund theft, or consensus-level failure, so this is a service-side SSRF issue rather than a critical wallet/consensus vulnerability — it's a network-reachable-from-a-remote-node information-disclosure/internal-service-access issue, matching the External Report's High severity (CWE-441/CWE-918) and comparable to Skipper's `ExternalName` bug: a spend-bundle-adjacent action (publishing a mirror coin) results in unauthorized access to internal services on someone else's node.

### Likelihood Explanation
Likelihood is moderate-to-high: creating a DataLayer store and adding mirror URLs is a standard, cheap on-chain action available to any wallet user (`add_mirror` RPC/CLI), and subscribing to third-party stores is a normal DataLayer usage pattern (e.g., following public/shared datasets). The periodic `periodically_manage_data()` loop automatically and repeatedly attempts these fetches without operator intervention, and there is no built-in allow-list to mitigate it (unlike Skipper's post-patch behavior).

### Recommendation
- Add an opt-in allow-list/deny-list for mirror and plugin URLs (host/scheme regex or explicit allow-list), analogous to Skipper's `-kubernetes-only-allowed-external-names` / `-kubernetes-allowed-external-name` flags.
- By default, reject mirror URLs resolving to loopback, link-local, private (RFC1918), and cloud-metadata address ranges (e.g., `169.254.169.254`) at both `add_mirror` validation time and at fetch/download time (`http_download`, `download_file`, plugin POST calls).
- Validate resolved IPs at connection time (not just hostname string) to prevent DNS-rebinding bypasses of any host-based allow-list.
- Document and surface a config option (e.g., `data_layer.allowed_mirror_hosts`) so operators running DataLayer services in sensitive network environments can restrict fetch destinations.

### Proof of Concept
1. Attacker creates a DataLayer store and calls `add_mirror` with `urls=["http://169.254.169.254/latest/meta-data/", "http://internal-admin.local:8080/"]`: [6](#0-5) 
2. Victim subscribes to attacker's `store_id` (a normal DataLayer client action).
3. Victim's `periodically_manage_data()` loop calls `update_subscriptions_from_wallet()`, pulling the attacker's URLs into the subscription's server list: [2](#0-1) 
4. `fetch_and_validate()`/`download_file()`/`http_download()` issue outbound HTTP requests to the attacker-chosen internal targets from the victim's DataLayer process: [4](#0-3) 
5. Any response is discarded on Merkle-root validation failure, but the outbound request to the internal target has already been made, and side effects (e.g., metadata service state changes, internal-service probing/timing, or plugin-relayed data leakage if a custom downloader plugin forwards responses) can still occur.

async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True

## Fragility Hotspots

- High-risk edits move work across DB writer transactions, `_update_confirmation_status()`, pending-root status changes, or wallet RPC calls. These boundaries encode publication and rollback assumptions.
- File-system writes for Merkle blobs, key/value blobs, and `.dat` files have TODOs around locking. Concurrent service/plugin/server access should be treated as a real consistency concern.
- Empty-root normalization is subtle and historically uneven. Audit any change touching `bytes32.zeros`, `None`, `Root.node_hash`, or proof roots with both empty and non-empty stores.
- Plugin and mirror URLs are external trust inputs. Downloaded data must continue to be verified against wallet-advertised roots, and file path/name validation must stay strict.
- DataLayer wallet code depends on singleton CLVM structure, odd singleton amounts, lineage proofs, and offer solver field names. Changes in wallet puzzle drivers or offer summaries can break this module without direct edits here.
