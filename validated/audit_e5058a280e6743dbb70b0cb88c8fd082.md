### Title
OP_RETURN outputs are excluded from Bitcoin fee and weight accounting - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` adds a caller-supplied OP_RETURN output to the transaction but calculates the transaction’s weight, virtual size, required fee, and standardness bound using only `payments` and the optional change output. [1](#0-0)  An 80-byte OP_RETURN payload can therefore cause a signed transaction to pay substantially less than the requested fee rate and less than Bitcoin’s minimum relay rate. [2](#0-1) 

### Finding Description
`SignableTransaction::new` accepts up to 80 bytes of caller-provided `data` and appends a zero-value OP_RETURN output to `tx_outs`. [3](#0-2)  The subsequent `calculate_weight_vbytes` call receives `tx_ins.len()` and `payments`, but not `tx_outs` or `data`, so the OP_RETURN output is absent from the transaction used to derive `weight` and `vbytes`. [4](#0-3) [5](#0-4) 

The minimum-fee check and funds check therefore use an understated `needed_fee`. [6](#0-5)  When change is added, `fee_with_change` is also calculated without the OP_RETURN output, and the change value is set so the final transaction pays exactly that understated fee. [7](#0-6)  The maximum-standard-weight check uses the same incomplete `weight`, so an OP_RETURN output can additionally push a borderline transaction over the checked limit. [8](#0-7) 

### Impact Explanation
An unprivileged caller able to supply transaction data can cause the threshold wallet to produce and sign a transaction whose actual fee rate is below the caller-requested rate or below Bitcoin’s default relay minimum. [9](#0-8) [10](#0-9)  The completed transaction commits the inputs to the incorrectly priced transaction, and ordinary Bitcoin peers can refuse to relay it, preventing the intended payment or data-bearing transaction from completing. [11](#0-10) 

### Likelihood Explanation
The flaw is deterministic whenever `data` is supplied because every OP_RETURN output is omitted from both fee calculations. [1](#0-0)  At a requested rate of 1 sat/vbyte, the calculated fee passes the minimum check using the smaller virtual size, while the larger final transaction necessarily has an actual rate below 1 sat/vbyte. [12](#0-11) [13](#0-12)  The public `data` parameter accepts arbitrary payloads up to 80 bytes, making the size discrepancy attacker-controlled. [9](#0-8) [14](#0-13) 

### Recommendation
Include the OP_RETURN output in the transaction passed to `calculate_weight_vbytes`, either by accepting the finalized `tx_outs` or by accepting `data` and constructing the equivalent output inside that helper. [15](#0-14) [16](#0-15)  Perform the no-change and with-change fee calculations, minimum-relay check, and maximum-standard-weight check against the complete final output set. [17](#0-16) 

### Proof of Concept
The following transaction shape demonstrates the issue without requiring malformed inputs:

```rust
use bitcoin::ScriptBuf;
use k256::Scalar;

fn underpriced_op_return_transaction(
  input: ReceivedOutput,
  change: ScriptBuf,
) -> Result<SignableTransaction, TransactionError> {
  SignableTransaction::new(
    vec![input],
    &[],                  // no payment outputs
    Some(change),          // a change output makes the fee exactly needed_fee
    Some(vec![0xaa; 80]),  // caller-controlled OP_RETURN payload
    1,                     // 1 sat/vbyte
  )
}
```

The constructor first appends the 80-byte OP_RETURN output to `tx_outs`. [18](#0-17)  It then calculates `vbytes` using an empty payment-output list and no change, rather than the transaction containing the OP_RETURN output. [19](#0-18) [5](#0-4)  With `fee_per_vbyte = 1`, `needed_fee` equals that underestimated virtual size and passes the minimum-relay check because the check uses the same underestimated value. [12](#0-11) 

If the input is large enough, the change path calculates `fee_with_change` from a transaction containing only the change output, still omitting the OP_RETURN output. [20](#0-19)  It then assigns `input_sat - fee_with_change` to change, causing the final transaction containing both outputs to pay only `fee_with_change`. [21](#0-20)  The resulting signed transaction is larger than the transaction used for pricing and has an actual fee rate below 1 sat/vbyte, so default-policy peers can reject it despite the constructor returning `Ok`. [22](#0-21)

    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
