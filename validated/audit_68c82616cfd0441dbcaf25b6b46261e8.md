### Title
Permissionless `smartConvert` in SmartWomConvert relies on unprotected single-block Wombat AMM spot price and pool cash/liability state to size a favorable mWOM buyback, allowing flash-swap price/imbalance manipulation for profit extraction from the WOM/mWOM pool - ([File: wombat/SmartWomConvert.sol])

### Summary
`SmartWomConvert.smartConvert()` is an external, unauthenticated function ("should mainly used by wombat staking" is only a comment, not an enforced modifier) that decides how much of a caller-supplied WOM amount is minted 1:1 into mWOM versus routed through a live swap on the `womMWomPool` Wombat AMM, based entirely on that pool's current spot price (`currentRatio()`) and current cash/liability imbalance (`maxSwapAmount()`). Both of these values are read directly from the same on-chain, swappable pool in the same transaction, with no TWAP, staleness check, or manipulation resistance — mirroring the reported bug class where a lending/valuation module trusts a manipulable spot price from a pool the attacker can skew in the same transaction.

### Finding Description
`smartConvert(uint256 _amountIn, uint256 _mode)` [1](#0-0)  has no access-control modifier restricting the caller, despite the code comment stating it "should mainly used by wombat staking upon sending wom." Any EOA can call it directly, supplying arbitrary WOM via `_convertFor`, which pulls WOM `IERC20(wom).safeTransferFrom(msg.sender, address(this), _amount)` [2](#0-1) .

Inside `smartConvert`, the decision of how much of the input is minted 1:1 via `IMWom(mWom).deposit()` versus swapped through the AMM is driven by two on-chain, freely-readable, and freely-influenceable values:
- `currentRatio()` — the instantaneous spot output of swapping `1e18` mWOM for WOM via `IWombatRouter(router).getAmountOut(...)` against `womMWomPool` [3](#0-2) .
- `maxSwapAmount()` — computed directly from `IAsset(womAsset).cash()` and `IAsset(womAsset).liability()`, i.e., the live coverage-ratio state of the same Wombat asset [4](#0-3) , [5](#0-4) .

Both `cash()`/`liability()` and the AMM spot price are trivially and cheaply moved within a single transaction by executing an ordinary swap against `womMWomPool` through the public Wombat router (the same router `SmartWomConvert` itself uses for its own swap, `IWombatRouter(router).swapExactTokensForTokens(...)` in `_convertFor`) [6](#0-5) . An attacker can therefore, in one atomic transaction/multicall from an ordinary wallet:
1. Swap a large amount of mWOM into `womMWomPool` for WOM, depressing `currentRatio()` below `buybackThreshold` and skewing `cash()`/`liability()` in the asset used by `maxSwapAmount()`.
2. Call `smartConvert()` with WOM, which — because `mWomToWom < buybackThreshold` — routes the maximum permitted portion (`maxSwapAmount()`) of the caller's WOM through a swap back into mWOM on the very same, still-skewed pool, buying mWOM at the artificially depressed price the attacker just created, rather than at the pool's fair value.
3. The `_minRec` check in `_convertFor` only protects the caller from getting *less* than they demand [7](#0-6) ; it does nothing to protect the pool/protocol from the caller extracting more than fair value because the reference price used to size the trade is the same price the caller just manipulated.

This is the same root-cause pattern as the reported Atomic exploit: a module (`SmartWomConvert`) values/sizes an economically consequential action off the spot state of an AMM pool that is reachable and swappable by the same unprivileged caller in the same transaction, with no manipulation-resistant price source.

### Impact Explanation
Repeated exploitation drains value from the `womMWomPool` liquidity (WOM/mWOM backing) and can permanently reduce the amount of mWOM properly backed by WOM, indirectly harming the mWOM peg and everyone else's ability to redeem/convert at fair value, and reducing protocol solvency of the WOM/mWOM conversion mechanism relied on by MasterMagpie users, mWOM holders, and mWomSV lockers. This is unclaimed-yield/insolvency-adjacent impact stemming purely from an ordinary wallet's transaction, matching the accepted impact categories.

### Likelihood Explanation
The attack requires only: (1) capital to move `womMWomPool`'s spot price/cash-liability state (feasible via flash loan of WOM/mWOM, same technique as the reference report), and (2) a direct, unauthenticated call to `smartConvert()`. No privileged role, no governance action, and no external protocol compromise is needed — only public functions on `SmartWomConvert`, the Wombat router, and the Wombat asset/pool, all of which are reachable by any wallet.

### Recommendation
- Restrict `smartConvert()` (and ideally `convert`/`convertFor`) to be callable only by `wombatStaking` or another trusted, rate-limited caller, consistent with the code's own comment that it "should mainly [be] used by wombat staking."
- Replace the single-block spot-price read in `currentRatio()` and the instantaneous `cash()`/`liability()` read in `maxSwapAmount()` with a manipulation-resistant reference (e.g., TWAP, multi-block average, or a bound on maximum swap size relative to pool depth with slippage/price-impact caps).
- Add a check that rejects execution if the pool's price/coverage ratio deviated abnormally within the current block (e.g., comparing against a stored previous state or requiring the call to originate outside of the same transaction as any swap against `womMWomPool`).

### Proof of Concept
Conceptual, since the live pool/router bytecode isn't in-repo (only interfaces/mocks are), but the flow is fully supported by the code paths cited above:
1. Attacker flash-loans mWOM and WOM.
2. Attacker swaps a large amount of mWOM → WOM directly against `womMWomPool` via the public Wombat router, depressing `currentRatio()` (mWOM/WOM spot price) below `buybackThreshold` (9000) and skewing `IAsset(womAsset).cash()`/`liability()`.
3. Attacker calls `SmartWomConvert.smartConvert(_amountIn, _mode)` with `_amountIn` = remaining WOM. Since `currentRatio() < buybackThreshold`, `maxSwapAmount()` (computed off the now-skewed `cash()`/`liability()`) permits a large `amountToSwap`, causing most of `_amountIn` to be swapped WOM → mWOM on the same still-depressed pool inside `_convertFor` [6](#0-5) , netting more mWOM than the pool's undisturbed fair price would allow.
4. Attacker reverses/unwinds the initial mWOM position (or repays the flash loan) and keeps the mWOM/WOM difference as profit, extracted from `womMWomPool` liquidity. [8](#0-7)

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
