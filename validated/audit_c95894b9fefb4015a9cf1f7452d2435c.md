## Title
`resolveWithin()` boundary check uses a naive string-prefix match, allowing escape into sibling directories with a shared name prefix - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` (and its `posix`/`win32` variants) is the app-wide guard used to keep attacker/repository-influenced relative paths from escaping a trusted root directory. Its containment check is `realResolved.startsWith(realRoot)` with no path-separator boundary enforcement, so a resolved path that merely shares a *string prefix* with the root (e.g. a sibling directory `repo-secrets` next to `repo`) is incorrectly treated as "inside" the root. This is the exact bug-class equivalent of DAOsis's `invest()`: a limit/invariant check exists syntactically but is implemented incorrectly, so the boundary it's supposed to enforce can be silently exceeded. [1](#0-0) 

### Finding Description
`_resolveWithin()` resolves the caller-supplied path segments against a root, then checks containment purely with `String.prototype.startsWith`: [2](#0-1) 

There is no check that `realResolved` equals `realRoot` or continues with `realRoot + path.sep`. Consequently, if the real root is `/Users/victim/Documents/GitHub/repo`, a resolved candidate `/Users/victim/Documents/GitHub/repo-secrets/config.json` (a sibling directory whose name merely starts with the same characters) passes the check even though it is a completely different directory tree.

This helper is relied upon in two attacker-reachable sinks:

1. `buildConflictContext()` in `copilot-conflict-context.ts` calls `resolveWithin(workingDirectory, file.path)` for every conflicted file path before reading its content into the Copilot AI prompt. `file.path` originates from git conflict status entries, which are derived from tree/index entries that can be crafted by a malicious remote/fork the user merges, rebases, or cherry-picks from. [3](#0-2) 

2. `_processCopilotConflictResolutions` in `app-store.ts` resolves the same kind of `resolution.path` value and then **writes** the AI-produced resolution content to the resolved absolute path with `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`. [4](#0-3) 

3. `openRepositoryFromUrl()` in `dispatcher.ts` resolves a `filepath` parameter taken directly from a `x-github-client://` deep link that a user clicks, then calls `shell.showItemInFolder(resolved)`. [5](#0-4) 

In all three cases, the code *intends* to enforce "resolved path must be strictly within the repository/root directory," matching the DAOsis pattern where `invest()` intended to enforce "tokens sold must not exceed `tokensForSale`" but implemented the check incorrectly (or omitted it), letting the invariant be broken by crafted input.

### Impact Explanation
- Via the Copilot conflict-resolution write path, a maliciously crafted fork/branch that a user merges can cause an attacker-influenced conflict "resolution" to be written to a file **outside** the current repository (a sibling directory sharing a name prefix), corrupting or overwriting files the user did not intend to touch — a silent file write outside the repo.
- Via the deep-link `filepath` path, a link the user clicks can cause Desktop to reveal (and, with different sinks, potentially read) files located in a sibling directory outside the intended repository, an unauthorized file-read/disclosure outside the repo.
- Both paths match the accepted impact categories: attacker controls a cloned/fetched repository or a deep link the user clicks, and the result is file write/read outside the repo.

### Likelihood Explanation
Exploitability depends on the victim having (or the attacker being able to induce, e.g. via clone-name collisions with the sanitization logic in `remote-parsing.ts`) a second directory on disk whose name shares a prefix with the target repository's directory name — a common real-world situation (`app`/`app-old`, `service`/`service-backup`, `repo`/`repository`). No admin rights, local access, or pre-existing malware are required beyond normal Desktop usage (merging a hostile branch, or clicking a link), satisfying the "unprivileged" requirement.

### Recommendation
Fix the containment check in `app/src/lib/path.ts` to enforce a real path boundary instead of a string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator for the `win32`/`posix` variants). Add regression tests covering sibling directories that share a name prefix with the root (e.g. root `/a/b/repo`, candidate `/a/b/repo-evil/x`) to `app/test/unit/path-test.ts`.

### Proof of Concept
1. Clone two repositories into the same parent directory: `~/Documents/GitHub/repo` and `~/Documents/GitHub/repo-secrets` (the latter containing a sensitive file, e.g. `~/Documents/GitHub/repo-secrets/token.txt`).
2. From within `repo`, merge/rebase a branch from a malicious remote whose tree contains a conflicting entry crafted so that, when combined with `Path.resolve`, the git-relative conflict path normalizes to `../repo-secrets/token.txt` relative to `repo`.
3. `buildConflictContext()` calls `resolveWithin('~/Documents/GitHub/repo', '../repo-secrets/token.txt')`; `Path.resolve` produces `~/Documents/GitHub/repo-secrets/token.txt`, and `realResolved.startsWith(realRoot)` returns `true` because the string `"...GitHub/repo-secrets/token.txt"` starts with `"...GitHub/repo"`.
4. The out-of-repo file's contents are read and sent to the Copilot conflict-resolution prompt (exfiltration), and/or the AI's "resolution" for that path is subsequently written back via `writeFile(absolutePath, ...)` in `app-store.ts`, corrupting the sibling directory outside the actual repository.
