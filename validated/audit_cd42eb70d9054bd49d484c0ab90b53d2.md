I found a confirmed, locally-supported analog: the `aptos move verify-package` command's `CachedPackageMetadata::verify` never compares actual on-chain compiled bytecode against the locally rebuilt bytecode — it only compares the `PackageMetadata` fields.

### Title
`verify-package` reports a false "verified" result because `CachedPackageMetadata::verify` never checks on-chain module bytecode - (File: `aptos-move/cli/src/stored_package.rs`)

### Summary
`aptos move verify-package` is the mainnet-relevant tool used by developers, auditors, and dependent-package authors to confirm that on-chain bytecode matches a claimed source tree before trusting or depending on it [1](#0-0) . Its `execute` path only calls `package.verify(&compiled_metadata)`, which compares `PackageMetadata` struct fields (`name`, `deps`, `modules`, `manifest`, `upgrade_policy`, `extension`, `source_digest`) between the locally rebuilt metadata and the fetched on-chain metadata [2](#0-1) [3](#0-2) . It never fetches or diffs the actual compiled module bytes returned by `get_account_module`, even though `CachedPackageRegistry` explicitly supports fetching bytecode (`with_bytecode` flag → `get_bytecode`) [4](#0-3) . `VerifyPackage::execute` constructs `CachedPackageRegistry::create(client, self.account, false)` — passing `false` for `with_bytecode` — so the bytecode map is always empty and is unused entirely in the verify flow [5](#0-4) .

### Finding Description
`ModuleMetadata` (part of `PackageMetadata`) only carries a module `name`, zipped `source`, zipped `source_map`, and an `extension` — it does not carry a bytecode hash of the actually-published module bytes [6](#0-5) . The on-chain `PackageRegistry`/`PackageMetadata` resource (verified at publish time by `code::publish_package` / `validate_publish_request` in the VM) governs what bytecode is *legally stored*, but says nothing that binds the metadata to the exact bytes that were pushed in the same transaction beyond the compatibility/dependency checks performed once at publish time [7](#0-6) . `verify-package`'s job is to independently confirm "the code that is actually verified and stored" matches the claimed source, but its `verify()` function silently reduces this to a metadata-only equality check, never touching `get_account_module`/`get_bytecode` [3](#0-2) . Since `source_digest` in `PackageMetadata` is set by the *publisher* at publish time and is not independently recomputed from the deployed module bytes by the chain (it's just another field in the same struct being compared), a malicious publisher can publish a package with metadata (name, deps, module names, manifest, source_digest) matching an audited/benign source, while the actual bytecode bytes for one or more modules differ (e.g., contain a backdoor), and `verify-package` will still print "Successfully verified source of package" because every field it inspects matches.

### Impact Explanation
This breaks the "Mismatch between verified bytes, package metadata, dependency declarations, and committed module bytes" invariant called out in the publish impact gate. Anyone relying on `aptos move verify-package` for code-safety assurance (auditors, dependent-package authors doing `is_policy_exempted_address`/compatible-dependency checks, end users deciding to trust a contract) can be given a false positive, allowing malicious bytecode to run under an approved-looking package. This is a code-safety/verification-integrity defect with direct mainnet relevance (it's a shipped CLI subcommand documented as the reproducibility/code-review tool) [1](#0-0) .

### Likelihood Explanation
High likelihood of being hit in practice: `verify-package` is documented as *the* mechanism for code review/reproducibility [8](#0-7) , so it is presumably used exactly in the trust-critical scenario the report's bug-class targets (verifying externally facing contract code before relying on it, analogous to trusting an external DEX router). No privileged assumptions are needed by the attacker — a normal publisher can construct metadata whose `source_digest`/fields match public/known-good source while shipping different bytecode, since nothing on-chain or in the CLI cross-checks metadata against the deployed bytes at verify time.

### Recommendation
In `CachedPackageMetadata::verify` (or `VerifyPackage::execute`), always fetch bytecode via `CachedPackageRegistry::create(..., with_bytecode: true)` and compare each locally-compiled module's serialized bytes (or a hash thereof) against `get_bytecode(module_name)` for every module in the package, failing verification on any mismatch, in addition to (not instead of) the existing metadata-field checks.

### Proof of Concept
1. Publisher builds package `P` with source `A` (benign, e.g. a well-audited example) and computes `source_digest`, `manifest`, `deps`, and module-name metadata for `A`.
2. Publisher swaps in a different `CompiledModule` bytecode (with identical module name/self-address, satisfying `MODULE_ADDRESS_DOES_NOT_MATCH_SENDER` and compatibility checks, e.g. adding a hidden backdoor entry function) and publishes `metadata_serialized` (still describing `A`) together with these substituted `code` bytes via `code::publish_package_txn` [9](#0-8) . The VM's `validate_publish_request` only checks module name registration, allowed deps, and metadata format — not that the bytes match the given `source`/`source_digest` [7](#0-6) .
3. A third party runs `aptos move verify-package --account <addr>` against the published `A` source. `VerifyPackage::execute` rebuilds `A` locally, fetches on-chain `PackageMetadata` (which still literally describes `A`), and calls `package.verify(&compiled_metadata)` [2](#0-1) .
4. `verify()` compares only metadata fields (all equal, since publisher didn't alter them) and returns `Ok(())` — never fetching or diffing the swapped-in bytecode [3](#0-2) .
5. CLI prints "Successfully verified source of package" even though the deployed module bytes differ from source `A`.

    async fn execute(self) -> CliTypedResult<&'static str> {
        // First build the package locally to get the package metadata
        let build_options = BuildOptions {
            install_dir: self.move_options.output_dir.clone(),
            bytecode_version: fix_bytecode_version(
                self.move_options.bytecode_version,
                self.move_options.language_version,
            ),
            ..self.included_artifacts.build_options(&self.move_options)?
        };
        let w = self.env.writer();
        let pack = BuiltPackage::build_to(&w, self.move_options.get_package_path()?, build_options)
            .map_err(|e| CliError::MoveCompilationError(format!("{:#}", e)))?;
        let compiled_metadata = pack.extract_metadata()?;

        // Now pull the compiled package
        let client = self.rest_options.client(&self.profile_options)?;
        let registry = CachedPackageRegistry::create(client, self.account, false).await?;
        let package = registry
            .get_package(pack.name())
            .await
            .map_err(|s| CliError::CommandArgumentError(s.to_string()))?;

        // We can't check the arbitrary, because it could change on us
        if package.upgrade_policy() == UpgradePolicy::arbitrary() {
            return Err(CliError::CommandArgumentError(
                "A package with upgrade policy `arbitrary` cannot be downloaded \
                since it is not safe to depend on such packages."
                    .to_owned(),
            ));
        }

        // Verify that the source digest matches
        package.verify(&compiled_metadata)?;

        Ok("Successfully verified source of package")
    }

impl CachedPackageRegistry {
    /// Creates a new registry.
    pub async fn create(
        client: Client,
        addr: AccountAddress,
        with_bytecode: bool,
    ) -> anyhow::Result<Self> {
        // Need to use a different type to deserialize JSON
        let inner = client
            .get_account_resource_bcs::<PackageRegistry>(addr, "0x1::code::PackageRegistry")
            .await?
            .into_inner();
        let mut bytecode = BTreeMap::new();
        if with_bytecode {
            for pack in &inner.packages {
                for module in &pack.modules {
                    let bytes = client
                        .get_account_module(addr, &module.name)
                        .await?
                        .into_inner()
                        .bytecode
                        .0;
                    bytecode.insert(module.name.clone(), bytes);
                }
            }
        }
        Ok(Self { inner, bytecode })
    }

    /// Returns the list of packages in this registry by name.
    pub fn package_names(&self) -> Vec<&str> {
        self.inner
            .packages
            .iter()
            .map(|p| p.name.as_str())
            .collect()
    }

    /// Finds the metadata for the given module in the registry by its unique name.
    pub async fn get_module(
        &self,
        name: impl AsRef<str>,
    ) -> anyhow::Result<CachedModuleMetadata<'_>> {
        let name = name.as_ref();
        for package in &self.inner.packages {
            for module in &package.modules {
                if module.name == name {
                    return Ok(CachedModuleMetadata { metadata: module });
                }
            }
        }
        bail!("module `{}` not found", name)
    }

    /// Finds the metadata for the given package in the registry by its unique name.
    pub async fn get_package(
        &self,
        name: impl AsRef<str>,
    ) -> anyhow::Result<CachedPackageMetadata<'_>> {
        let name = name.as_ref();
        for package in &self.inner.packages {
            if package.name == name {
                return Ok(CachedPackageMetadata { metadata: package });
            }
        }
        bail!("package `{}` not found", name)
    }

    /// Gets the bytecode associated with the module.
    pub async fn get_bytecode(
        &self,
        module_name: impl AsRef<str>,
    ) -> anyhow::Result<Option<&[u8]>> {
        Ok(self
            .bytecode
            .get(module_name.as_ref())
            .map(|v| v.as_slice()))
    }
}
