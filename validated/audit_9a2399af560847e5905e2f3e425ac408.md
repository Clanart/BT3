I found the same "third-party-transfer-forbidden disables withdrawal" bug class in the staking module's `CompleteUnbonding` path, and it is **not** mitigated the way the distribution module's equivalent path is.

## Title
Unbonding delegations for unreceivable delegator addresses cause staking `EndBlock` to skip removal, permanently stalling that delegator's unbonding queue entry - (File: sei-cosmos/x/staking/keeper/delegation.go)

### Summary
`CompleteUnbonding` calls `k.bankKeeper.UndelegateCoinsFromModuleToAccount` to pay a matured unbonding delegation to the delegator address [1](#0-0) . That bank call fails (`ErrInvalidRecipient`) whenever the recipient cannot receive funds, e.g. via `CanSendTo`/`BlockedAddr` checks enforced deeper in `UndelegateCoins` [2](#0-1) . The caller in `BlockValidatorUpdates` (EndBlock) explicitly swallows this error with `continue`, without removing the mature entry from the UBD time-slice queue tracking [3](#0-2) . This mirrors the EigenLayer pattern exactly: a legitimate withdrawal path silently reverts because the destination address becomes unable to receive funds via a third-party-style restriction (the direct-cast/EVM-association gate implemented by `CanAddressReceive`/`CanSendTo`) [4](#0-3) , and there is no fallback route for the stuck funds analogous to the community-pool fallback added for distribution's `AfterValidatorRemoved`.

### Finding Description
When an EVM address is direct-cast to a Sei `AccAddress` (used as delegator when nobody has associated a "true" Sei address yet) and later that EVM address gets a genuine association via `SetAddressMapping`/`associatePubKey`, `CanAddressReceive`/`CanSendTo` starts returning `false` for the stale direct-cast address [4](#0-3) . If that direct-cast address had an in-flight `MsgUndelegate` unbonding entry queued before the re-association, `CompleteUnbonding` will fail permanently when the entry matures: `UndelegateCoinsFromModuleToAccount` → `UndelegateCoins` → `CanSendTo` check fails and the whole `CompleteUnbonding` call returns an error [5](#0-4) . `BlockValidatorUpdates` treats this as `continue` — it does *not* delete the UBD entry, does not retry with a fallback address, and does not route the coins to any recoverable pool [6](#0-5) . The existing regression test `TestEndBlockRetainsUnbondingForInvalidRecipient` confirms this exact behavior is present and by design left as "retained" state rather than fixed with a payable fallback [7](#0-6) .

Unlike the distribution module, which was hardened with `canReceiveWithdrawAddr` and a community-pool fallback in `AfterValidatorRemoved` for exactly this scenario [8](#0-7) , the staking module's `CompleteUnbonding`/`CompleteRedelegation` EndBlock path has no such fallback: the tokens remain parked in the `NotBondedPool` module account and the mature UBD entry stays queued forever, effectively freezing that user's principal indefinitely since nothing re-attempts the transfer or reroutes it.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any ordinary user: submit a `MsgUndelegate` (or via the staking precompile) from a direct-cast address, then associate that address's EVM key to a different true Sei address (a normal `associatePubKey`/EVM tx flow) before the unbonding period elapses. When the entry matures, the payout silently and permanently fails every block, and the principal is locked in the `NotBondedPool` account with no user-triggered retry path and no admin migration referenced in the code (unlike the gov module's `RefundDeposits`, which explicitly documents "recovering a permanently unreceivable deposit requires a migration" [9](#0-8) , staking has no equivalent acknowledgment or recovery hook).

### Likelihood Explanation
Likelihood is moderate: it requires the delegator to first delegate/undelegate under a direct-cast address and then associate a different Sei pubkey to the same EVM address — a sequence fully achievable by an ordinary EVM user experimenting with address association, not requiring any privileged role.

### Recommendation
Mirror the distribution module's fix: before attempting `UndelegateCoinsFromModuleToAccount`/redelegation payout, check `bankKeeper.CanSendTo`/`BlockedAddr` on the delegator address. If unreceivable, either (a) retain the entry only while additionally emitting a clear on-chain signal / retry mechanism, or (b) reroute matured unbonding funds to a recoverable pool (e.g. community pool) as done for `AfterValidatorRemoved`, rather than leaving both the entry and coins in indefinite limbo. At minimum, provide a permissionless way for the delegator to redirect the payout to a receivable address once its original address becomes blocked.

### Proof of Concept
1. Associate `evmAddr` to no Sei address yet; delegator uses the direct-cast address `sdk.AccAddress(evmAddr[:])` to call `MsgDelegate` then `MsgUndelegate` on a validator, creating an `UnbondingDelegation` entry maturing at time `T`.
2. Before `T`, call `SetAddressMapping`/`associatePubKey` to bind `evmAddr` to a different, "true" Sei address — this makes `CanAddressReceive`/`CanSendTo` return `false` for the original direct-cast address, exactly as exercised by `TestEndBlockRetainsUnbondingForInvalidRecipient` [7](#0-6) .
3. Advance the chain past `T`. `BlockValidatorUpdates`/`CompleteUnbonding` attempts the payout, `UndelegateCoins` fails on `CanSendTo`, and the error is swallowed via `continue` — the UBD entry is never removed and the pool balance never decreases, reproducing the "unauthorized transaction sender's funds are frozen forever" outcome from the source EigenLayer report.

func (k BaseKeeper) UndelegateCoins(ctx sdk.Context, moduleAccAddr, delegatorAddr sdk.AccAddress, amt sdk.Coins) error {
	moduleAcc := k.ak.GetAccount(ctx, moduleAccAddr)
	if moduleAcc == nil {
		return sdkerrors.Wrapf(sdkerrors.ErrUnknownAddress, "module account %s does not exist", moduleAccAddr)
	}

	if !amt.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, amt.String())
	}
	if !k.CanSendTo(ctx, delegatorAddr) {
		return sdkerrors.ErrInvalidRecipient
	}

	err := k.SubUnlockedCoins(ctx, moduleAccAddr, amt, true)
	if err != nil {
		return err
	}

	if err := k.trackUndelegation(ctx, delegatorAddr, amt); err != nil {
		return sdkerrors.Wrap(err, "failed to track undelegation")
	}

	err = k.AddCoins(ctx, delegatorAddr, amt, true)
	if err != nil {
		return err
	}

	return nil
}

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func (k Keeper) canReceiveWithdrawAddr(ctx sdk.Context, withdrawAddr sdk.AccAddress) bool {
	// BlockedAddr mirrors the gate SendCoinsFromModuleToAccount actually enforces:
	// beyond the module-account blocklist it also rejects dynamically-derived
	// addresses such as the EVM coinbase addresses (an "evm_coinbase"-prefixed
	// address), which CanSendTo does not catch. Consulting it here keeps this
	// predicate in lockstep with the send, so AfterValidatorRemoved never concludes
	// an address is receivable and then panics on the resulting bank error.
	return !k.blockedAddrs[withdrawAddr.String()] &&
		!k.bankKeeper.BlockedAddr(withdrawAddr) &&
		k.bankKeeper.CanSendTo(ctx, withdrawAddr)
}

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by

func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}
