### Title
Attacker-controlled `ThresholdKeys` deserialization preallocates up to ~2 MiB per truncated message - (File: `crypto/dkg/src/lib.rs`)

### Summary
`ThresholdKeys::read` trusts the serialized participant count `n` and immediately allocates a `Vec` with capacity for `n` scalar coefficients when the interpolation tag selects `Constant`. The allocation occurs before `ThresholdParams::new` validates the parameters and before any coefficient bytes have been received. On 32-byte scalar suites such as Secp256k1 and Ristretto, `n = u16::MAX` reserves approximately 2 MiB from a roughly 20-byte header. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The deserializer reads the curve ID, then `t`, `n`, and `i`, followed by the interpolation discriminant. For discriminant `0`, it executes `Vec::with_capacity(usize::from(n))`, where `n` is directly attacker-controlled, and only then begins reading the `n` scalars. [1](#0-0) 

`ThresholdParams::new(t, n, i)` is invoked only after all coefficients, the secret share, and all verification shares have been read, so it cannot reject an abusive allocation before it occurs. [4](#0-3) 

For Secp256k1, the serialized prefix is:

- `u32` curve-ID length: `9`
- curve ID: `b"secp256k1"`
- `t = 1`
- `n = 0xffff`
- `i = 1`
- interpolation tag: `0`

The Secp256k1 suite defines `C::F` as `k256::Scalar` and its ID as `b"secp256k1"`, so the 20-byte prefix reserves space for 65,535 scalar objects. [2](#0-1) [5](#0-4) 

### Impact Explanation
This is an asymmetric memory-consumption primitive. A caller feeding `ThresholdKeys::read` from a stream can send only the small header and then stall; the allocation remains live while `read_F` waits for the first promised coefficient. Thousands of concurrent stalled reads can therefore consume gigabytes of memory while transferring only a small amount of input. [6](#0-5) [7](#0-6) 

Even when the input is already buffered, repeated calls cause approximately 2 MiB allocation/free cycles from approximately 20 bytes of attacker input, producing allocator pressure and CPU churn. This is a reachable denial-of-service risk wherever serialized `ThresholdKeys` are accepted from an untrusted party.

### Likelihood Explanation
No cryptographic validity is required: the attacker only needs the correct curve ID and a syntactically plausible header. The deserialization API is explicitly exposed as `ThresholdKeys::read`, and the malicious value is contained entirely within the byte stream. [8](#0-7) 

Exploitability depends on the integration exposing this parser over a streaming or concurrent input path rather than only over locally generated, fully buffered data. Under that stated reachable-input model, the attack is straightforward and repeatable.

### Recommendation
Do not allocate collections based on untrusted lengths before the corresponding bytes arrive. In `crypto/dkg/src/lib.rs`:

- Construct and validate `ThresholdParams` immediately after reading `t`, `n`, and `i`.
- Remove `Vec::with_capacity(n)` or cap it to a small, constant initial capacity.
- Read coefficients incrementally so memory consumption is proportional to bytes actually supplied.
- Prefer an API-level expected-parameter check when the caller already knows the legitimate threshold configuration.
- Apply a maximum serialized-key length at the transport boundary so stalled reads cannot hold parser state indefinitely.

### Proof of Concept
The following input shape reaches the oversized allocation before any coefficient is supplied:

```rust
use std::io::Read;

// For C = Secp256k1.
let mut prefix = Vec::new();
prefix.extend_from_slice(&9u32.to_le_bytes()); // C::ID.len()
prefix.extend_from_slice(b"secp256k1");        // C::ID
prefix.extend_from_slice(&1u16.to_le_bytes()); // t
prefix.extend_from_slice(&u16::MAX.to_le_bytes()); // n = 65_535
prefix.extend_from_slice(&1u16.to_le_bytes()); // i
prefix.push(0);                                // Interpolation::Constant

// Feed `prefix` through a stream to `ThresholdKeys::<Secp256k1>::read`,
// then keep the stream open without sending the first coefficient.
//
// At crypto/dkg/src/lib.rs:608, this allocates capacity for 65_535
// `k256::Scalar` values, approximately 2 MiB, while only ~20 bytes have
// been consumed.
```

A tracking allocator or resident-memory measurement around a blocking `Read` implementation demonstrates the allocation occurring before `C::read_F` receives coefficient bytes. [9](#0-8)
