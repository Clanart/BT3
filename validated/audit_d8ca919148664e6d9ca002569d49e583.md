### Title
`WombatStaking.mWom` can be updated via `setMWom` while `SmartWomConvert.mWom` is immutable, corrupting reward-fee conversion and permanently freezing WOM rewards - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking` stores a mutable `mWom` address that can be changed by the owner via `setMWom`, but the `SmartWomConvert` contract it delegates WOM→mWOM conversion to holds its own `mWom` as an `immutable` set once at deployment. `WombatStaking` relies on both addresses being identical when routing harvested WOM reward fees through `smartWomConverter`. If `mWom` is ever rotated on `WombatStaking`, the two contracts diverge, and any subsequent reward harvest silently loses the converted WOM fee.

### Finding Description
`WombatStaking` keeps a state variable `mWom` and exposes an owner-only setter: [1](#0-0) 

`SmartWomConvert`, however, captures `mWom` as `immutable` in its constructor and has no way to update it after deployment: [2](#0-1) [3](#0-2) 

`WombatStaking._sendRewards` (invoked from the harvest path `_toMasterWomAndSendReward` → `_sendRewards`, reachable whenever any user or the pool helper triggers a harvest/deposit/withdraw that pulls WOM rewards from Wombat) uses its own `mWom` to measure how much converted mWOM it received back from `smartWomConverter`: [4](#0-3) 

Internally, `SmartWomConvert.smartConvert` → `_convertFor` performs the actual WOM→mWOM deposit/swap and transfers the resulting tokens using **its own** (old) immutable `mWom`, not the one currently configured on `WombatStaking`: [5](#0-4) 

If the owner ever rotates `WombatStaking.mWom` to a new mWOM token address (e.g., for an upgraded token) without redeploying/re-pointing `SmartWomConvert` (which is architecturally impossible since it's `immutable`), the two contracts' notions of "mWom" diverge permanently. `_sendRewards` will then measure `IMWom(mWom_new).balanceOf(address(this))` before and after calling `smartConvert`, but the actual tokens minted/transferred by `SmartWomConvert` are in `mWom_old`. The balance delta on `mWom_new` will be zero, so `feeTosend` computed at line 745 becomes `0`, and the WOM that was pulled into `SmartWomConvert` and converted into `mWom_old` is never forwarded to the rewarder — it is stranded inside `SmartWomConvert`/`WombatStaking` with no function to recover or redirect it to the correct destination.

### Impact Explanation
This causes permanent freezing of protocol yield: every harvest that routes a WOM fee through the (now-mismatched) `smartWomConverter` computes a zero fee-to-send while actually consuming real WOM (swapped/converted to the old mWOM token), so both the intended `mWom_new` reward accounting and the underlying converted WOM value become permanently unrecoverable/stuck. Since harvests are triggered continuously through ordinary user deposit/withdraw/harvest flows in `WombatStaking`, this silently and repeatedly loses value on every harvest cycle after the mismatch is introduced, satisfying "permanent freezing of unclaimed yield."

### Likelihood Explanation
Likelihood depends on the owner ever calling `setMWom` after `smartWomConverter` has been wired up — this requires an intentional configuration change, not attacker action, but is a legitimate operational path (e.g., migrating to a new mWOM implementation) that the codebase provides no safeguard against, and once triggered, corruption is silent (no revert) and affects every subsequent harvest that uses `smartWomConverter`, making it a realistic and persistent post-deployment risk rather than a one-off edge case.

### Recommendation
Remove the independent, unsynchronized `mWom` state from `WombatStaking`/`SmartWomConvert` duplication. Either (a) make `SmartWomConvert.mWom` mutable and add a restricted setter that is atomically updated alongside `WombatStaking.setMWom` (e.g., have `setMWom` also call `smartWomConverter.setMWom(...)`), or (b) have `WombatStaking` always read `mWom` from `SmartWomConvert` (single source of truth) instead of keeping its own copy, so the two can never diverge.

### Proof of Concept
1. Deploy `WombatStaking` with `mWom = mWomA` and `smartWomConverter` pointing to a `SmartWomConvert` instance constructed with `_mwom = mWomA`.
2. Owner calls `WombatStaking.setMWom(mWomB)` to rotate to a new mWOM implementation, per [6](#0-5) . `SmartWomConvert.mWom` remains `mWomA` (immutable), per [7](#0-6) .
3. A user triggers a normal deposit/withdraw that causes `WombatStaking` to harvest WOM rewards, invoking `_sendRewards` for a fee configured with `isMWOM = true`.
4. `_sendRewards` calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`; internally, `SmartWomConvert._convertFor` deposits/swaps WOM into `mWomA` and transfers `mWomA` tokens back to `WombatStaking` (`msg.sender`), per [5](#0-4) .
5. `_sendRewards` measures `IMWom(mWom).balanceOf(address(this))` where `mWom == mWomB`, which never changed, so `feeTosend = 0`, per [8](#0-7) .
6. `IBaseRewardPool(feeInfo.to).queueNewRewards(0, mWomB)` is called — zero rewards are ever queued, and the WOM fee that was actually converted into `mWomA` sits in `WombatStaking` with no code path to distribute or recover it, permanently freezing that yield.
