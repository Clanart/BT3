### Title
Silent Git remote hijack via unverified hostname in automatic remote-URL correction - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` automatically rewrites a repository's local `origin` remote URL whenever the GitHub API's `clone_url` for that repository differs from what's configured on disk. The function only validates that the **protocol** (`https`/`ssh`) of the old and new URL match — it never validates that the **hostname** matches. A GitHub API response (or a GHES/API endpoint response reachable via a compromised/mismatched proxy) that supplies a `clone_url` pointing at a different host is enough to make Desktop silently call `gitStore.setRemoteURL()` and repoint `origin` at an attacker-controlled server, with no user confirmation.

### Finding Description
`updateRemoteUrl` in [1](#0-0)  computes:
- `remoteUrl` — the repo's current git `origin` URL
- `updatedRemoteUrl` — `apiRepo.clone_url`, taken directly from the GitHub API response
- `protocolsMatch` — compares `URL.parse(remoteUrl).protocol` to `URL.parse(updatedRemoteUrl).protocol` only
- `remoteUrlUnchanged` — checks that the *previously cached* `gitHubRepository.cloneURL` still matches the current git remote (via `urlMatchesRemote`, which does check hostname/owner/name)

If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, the code calls `gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` unconditionally — no hostname check is applied to the *new* URL at all.

The `remoteUrlUnchanged` guard is meant to prevent overwriting an origin the user manually customized, but it validates against the **previously fetched API data**, not against any independently trusted value. If the API/proxy response that populated `gitHubRepository.cloneURL` originally, and the one supplying the new `apiRepo.clone_url`, come from the same (compromised or attacker-controlled) endpoint/response path, both checks pass trivially, and Desktop will rewrite `origin` to any arbitrary `https://` (or `ssh://`) URL the attacker supplies, as long as the scheme matches.

`repositoryMatchesRemote`/`urlMatchesRemote` in [2](#0-1)  do enforce hostname equality — but they are only used to build the `remoteUrlUnchanged` precondition against old cached data, not to validate the destination URL being written.

### Impact Explanation
A silently rewritten `origin` remote causes all subsequent `git push`/`git fetch`/`git pull` operations Desktop performs for that repository to target the attacker's server instead of the real one, without any visible warning in the UI (the repository name/tab still shows the original project). Consequences:
- Source code the user pushes is silently exfiltrated to the attacker's git server.
- Fetches/pulls silently pull attacker-supplied history/commits into the user's local repo, corrupting what the user believes they are building on and later pushing/committing on top of.
- Because git credential resolution (`envForRemoteOperation`, trampoline credential helpers) is driven by the remote URL's host, redirecting to an unknown host can also trigger generic-credential prompts against the attacker's domain, risking credential entry/exfiltration for that host.

This matches the report's underlying "broken invariant" class (a value that should be protected by validation is instead trusted and propagated unchecked), reframed for Desktop: **the destination remote URL, not a fee value, is corrupted silently.**

### Likelihood Explanation
Exploitation requires the attacker to control or intercept the API/metadata response describing the repository (e.g., a malicious/compromised GHES endpoint, or a network position able to tamper with the API response for that repository) — this is within the stated valid-impact scope ("a GitHub API object... or a git remote/proxy response"). It does not require local access, admin rights, or social engineering beyond the user having previously added/cloned the repository normally. However, it does require the attacker to already have influence over the API responses returned for that repository/endpoint, which for github.com proper is not attacker-controllable, so realistic exploitation is narrowed largely to GitHub Enterprise Server integrations or MITM'd API traffic — a real but somewhat harder-to-reach precondition than a fully unauthenticated remote-repo attack.

### Recommendation
In `updateRemoteUrl`, validate the **hostname** of `updatedRemoteUrl` against an allow-listed/trusted value (e.g., the account's configured API endpoint host) before calling `setRemoteURL`, not just the protocol. At minimum, require that the new URL's hostname match either the current remote's hostname or the endpoint the account/API request was made against, and surface a confirmation/notification to the user whenever the remote URL is programmatically changed.

### Proof of Concept
1. Configure/point Desktop at a GitHub Enterprise Server endpoint (or otherwise position to tamper with the JSON response of the repository metadata API call) that is attacker-controlled or compromised.
2. Have the victim add/clone a repository through that endpoint normally; Desktop caches `gitHubRepository.cloneURL` matching the real `origin`.
3. On a later repository refresh, have the attacker-controlled endpoint return a `clone_url` field of `https://attacker.example.com/evil/repo.git` (same `https` scheme as the original).
4. `updateRemoteUrl` sees `protocolsMatch === true` and `remoteUrlUnchanged === true` (since it only compares against the previously-cached, equally attacker-influenced value) and `urlsMatch === false`, so it calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/evil/repo.git')` — rewriting the user's `origin` without any prompt.
5. The next push/fetch operation the user performs targets `attacker.example.com` instead of the real host.

**Note:** I was unable to fully confirm, within available tool calls, the exact call site in `app/src/lib/stores/app-store.ts` that invokes `updateRemoteUrl` (to verify exactly when/how often this refresh path runs and whether any additional gating exists there), nor whether `gitStore.setRemoteURL` performs any hostname sanity check of its own in `app/src/lib/git/remote.ts`. If a Devin session is available, verifying those two files directly would strengthen or potentially refute part of this finding.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
