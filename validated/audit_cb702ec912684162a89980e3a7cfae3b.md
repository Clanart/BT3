### Title
Permissionless native-ERC20 token pair deletion on self-destruct permanently strands/unbacks bank-module minted coin supply - (File: `x/erc20/keeper/msg_server.go`)

### Summary
Anyone can permissionlessly register an externally-owned (attacker-controlled) ERC20 contract as an `OWNER_EXTERNAL` "native ERC20" token pair via `MsgRegisterERC20` [1](#0-0) , backed by `registerERC20` [2](#0-1) . Converting the attacker's ERC20 tokens into native coins via `ConvertERC20`/`convertERC20IntoCoinsForNativeToken` escrows the ERC20 tokens on the module account and **mints** an equal amount of bank coins to the user [3](#0-2) . Because the attacker fully controls the ERC20 contract bytecode, they can subsequently make the contract account appear as "selfdestructed" (no code hash). The next `ConvertERC20`/`ConvertCoin` call for that pair silently calls `k.DeleteTokenPair(ctx, pair)` [4](#0-3) [5](#0-4) , which removes all bookkeeping (`deleteTokenPair`, `deleteERC20Map`, `deleteDenomMap`, `deleteAllowances`) [6](#0-5)  **without burning or otherwise reconciling the bank coins that were already minted 1:1 against the now-unreachable/destroyed escrowed ERC20 collateral**. This mirrors the reported `CollateralManager.removeCollateral()` pattern exactly: removing the backing asset (collateral type / token pair) leaves already-issued liabilities (ICR-relevant debt / minted bank coins) instantly unbacked, with no guard rail in the removal path.

### Finding Description
The conversion invariant for `OWNER_EXTERNAL` pairs is: bank-module coin supply of `pair.Denom` must always be 1:1 backed by ERC20 tokens escrowed at `types.ModuleAddress` on the specific ERC20 contract [7](#0-6) . The "unescrow" direction (`ConvertCoinNativeERC20`) subsequently burns bank coins and releases the escrowed tokens back [8](#0-7) , so the design assumes the token pair — and by extension the underlying ERC20 contract's storage/balance mapping — remains permanently available and consistent for the life of the outstanding coin supply.

However, both entrypoints that touch an `OWNER_EXTERNAL` pair unconditionally delete the pair the moment the ERC20 account looks "gone" (`acc == nil || !acc.HasCodeHash()`):
- `ConvertERC20` [9](#0-8) 
- `ConvertCoin` [5](#0-4) 

There is no check of `k.bankKeeper` supply/escrow balance for `pair.Denom` before deletion, and no burn of the outstanding coin supply that corresponds to the (now unreachable) escrowed tokens. Since registration is permissionless (`params.PermissionlessRegistration`) [10](#0-9) , an attacker fully controls the contract that becomes the backing asset. They can:
1. Deploy and register their own ERC20 contract as an `OWNER_EXTERNAL` pair.
2. Mint themselves ERC20 tokens (arbitrary amount, since they own the contract) and call `ConvertERC20` to escrow them at the module address and mint themselves an equal amount of freely spendable native bank coins.
3. Make the account become "no code hash" (e.g., self-destructing it, exploiting go-ethereum's SELFDESTRUCT semantics, or any state-transition that clears `CodeHash`) so `acc.HasCodeHash()` returns false.
4. Trigger any subsequent `ConvertERC20`/`ConvertCoin` call referencing the pair (even a failing/no-op one), which silently deletes the token pair and its escrow/allowance bookkeeping — while the bank coins minted in step 2 remain fully circulating and spendable.

The result is native bank coins with no possibility of ever being redeemed/burned against real collateral again (the token pair mapping, denom map, and ERC20 map are gone), i.e., permanently unbacked "duplicated" spendable value sitting in the attacker's (or any other holder's, if transferred) balance. This is the direct analog of the ERD/Certik finding: removing the "collateral type" (`DeleteTokenPair`) instantly and irreversibly corrupts the backing ratio for issued value, exactly as removing a collateral type corrupts ICR/TCR for issued debt, but with no guard checks in the Cosmos EVM equivalent path either.

I was unable to fully verify, given index limits, the exact mechanics of how `HasCodeHash()`/`GetAccountWithoutBalance` transition to "no code" under this repo's EVM configuration (e.g., whether SELFDESTRUCT here follows EIP-6780 same-transaction-creation restriction, or an older full-wipe semantics, or whether some other state-clearing path such as account pruning of empty accounts can zero the code hash for a still-referenced contract). Confirming the precise trigger for `!acc.HasCodeHash()` requires reading `x/vm/statedb/state_object.go` (`HasCodeHash`) and the SELFDESTRUCT opcode handling in `x/vm/statedb/statedb.go`, which time did not permit tracing to completion. Regardless of the exact trigger mechanism, the missing invariant — that `DeleteTokenPair` for an `OWNER_EXTERNAL` pair never checks or reconciles outstanding `pair.Denom` bank supply before erasing the pair — is present and unconditional in the shown code.

### Impact Explanation
This falls under the Critical "unauthorized minting/duplication/irreversible accounting corruption of spendable user value" gate. Coins minted 1:1 against ERC20 collateral become permanently divorced from any recoverable backing once the pair is deleted, effectively duplicating value system-wide (the ERC20 side's economic backing disappears while the Cosmos-coin side remains fully transferable/tradeable), and this corruption is irreversible because `DeleteTokenPair` removes the denom/ERC20 mappings needed to ever re-establish or unwind the relationship.

### Likelihood Explanation
Reaching the vulnerable path only requires: permissionless registration to be enabled (a common configuration; controlled by a governance param but not a privileged action by the attacker), deploying/owning the backing ERC20 contract (attacker has full control), and calling ordinary `MsgConvertERC20`/`MsgConvertCoin` messages. No relayer, validator, or governance action is needed. The main open question (moved to Uncertain) is exactly which state transition of the attacker's own contract yields `!acc.HasCodeHash()`; since the attacker fully controls the contract bytecode/lifecycle, they have wide latitude to attempt this (e.g., via SELFDESTRUCT if permitted by the EVM's supported semantics in this codebase).

### Recommendation
Mirror the report's own recommendations, adapted to this repo:
1. Before calling `DeleteTokenPair` for an `OWNER_EXTERNAL` pair inside `ConvertERC20`/`ConvertCoin`, query the current bank supply/module escrow balance of `pair.Denom`; if any bank coin supply is currently outstanding, either (a) refuse the deletion and instead disable further conversions for the pair (freeze it in a query-only "disabled" state) while preserving denom/ERC20 mappings for potential remediation, or (b) burn/quarantine the outstanding supply via a governance-gated recovery process before removing the mapping.
2. Do not perform destructive `DeleteTokenPair` bookkeeping (denom map, ERC20 map, allowances) automatically inside a permissionless, unprivileged message handler; require this to go through a privileged/governance path with an explicit accounting reconciliation step.
3. Add an explicit invariant check (e.g., in `BeginBlocker`/`InvariantsRegistry`) verifying that for every `OWNER_EXTERNAL` token pair, `bankKeeper.GetSupply(pair.Denom)` never exceeds the actual `BalanceOf(contract, ModuleAddress)` on the corresponding ERC20 contract, and vice versa.

### Proof of Concept
1. Attacker deploys `EvilERC20` (own contract, arbitrary logic) and calls `MsgRegisterERC20{Erc20Addresses: [EvilERC20]}` (permissionless) → creates `TokenPair{ContractOwner: OWNER_EXTERNAL, Denom: erc20/<EvilERC20>}` [2](#0-1) .
2. Attacker mints themselves `1,000,000` `EvilERC20` tokens (their own contract, arbitrary mint control) and calls `MsgConvertERC20{Amount: 1_000_000, ContractAddress: EvilERC20}` → `convertERC20IntoCoinsForNativeToken` escrows `1,000,000` tokens at `types.ModuleAddress` on `EvilERC20` and mints `1,000,000 erc20/<EvilERC20>` bank coins to the attacker [3](#0-2) .
3. Attacker causes `EvilERC20`'s account to report `!HasCodeHash()` (e.g. via SELFDESTRUCT logic embedded in the contract, callable by attacker).
4. Attacker calls `MsgConvertERC20` (or `MsgConvertCoin`) again referencing the same pair. `acc == nil || !acc.HasCodeHash()` is true, so `k.DeleteTokenPair(ctx, pair)` runs, wiping `KeyPrefixTokenPair`, `KeyPrefixTokenPairByERC20`, `KeyPrefixTokenPairByDenom`, and allowances for `EvilERC20` [6](#0-5) , with **no check or burn of the outstanding `1,000,000 erc20/<EvilERC20>` bank coin supply**.
5. Attacker now holds `1,000,000` freely transferable, spendable native bank coins with zero recoverable ERC20 backing and no path to ever re-link/redeem/burn them via the erc20 module (mappings gone) — a permanent, unauthorized duplication of spendable value.

// convertERC20IntoCoinsForNativeToken handles the erc20 conversion for a native erc20 token
// pair:
//   - escrow tokens on module account
//   - mint coins on bank module
//   - send minted coins to the receiver
//   - check if coin balance increased by amount
//   - check if token balance decreased by amount
//   - check for unexpected `Approval` event in logs
func (k Keeper) convertERC20IntoCoinsForNativeToken(
	ctx sdk.Context,
	pair types.TokenPair,
	msg *types.MsgConvertERC20,
	receiver sdk.AccAddress,
	sender common.Address,
) (*types.MsgConvertERC20Response, error) {
	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()
	balanceCoin := k.bankKeeper.GetBalance(ctx, receiver, pair.Denom)
	balanceToken := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceToken == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow tokens on module account
	transferData, err := erc20.Pack("transfer", types.ModuleAddress, msg.Amount.BigInt())
	if err != nil {
		return nil, err
	}

	res, err := k.evmKeeper.CallEVMWithData(ctx, sender, &contract, transferData, true, nil)
	if err != nil {
		return nil, err
	}

	// Check evm call response
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return nil, err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return nil, err
		}
		if !unpackedRet.Value {
			return nil, sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute transfer")
		}
	}

	// Check expected escrow balance after transfer execution
	// NOTE: coin fields already validated in the ValidateBasic() of the message
	coins := sdk.Coins{sdk.Coin{Denom: pair.Denom, Amount: msg.Amount}}
	tokens := coins[0].Amount.BigInt()
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, types.ModuleAddress)
	if balanceTokenAfter == nil {
		return nil, sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	expToken := big.NewInt(0).Add(balanceToken, tokens)

	if r := balanceTokenAfter.Cmp(expToken); r != 0 {
		return nil, sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v",
			expToken, balanceTokenAfter,
		)
	}

	// Mint coins
	if err := k.bankKeeper.MintCoins(ctx, types.ModuleName, coins); err != nil {
		return nil, err
	}

	// Send minted coins to the receiver
	if err := k.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, receiver, coins); err != nil {
		return nil, err
	}

// RegisterERC20 implements the gRPC MsgServer interface. Any account can permissionlessly
// register a native ERC20 contract to map to a Cosmos Coin.
func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {
			return nil, err
		}
	}

	// Check if the conversion is globally enabled
	if !k.IsERC20Enabled(ctx) {
		return nil, types.ErrERC20Disabled.Wrap("registration is currently disabled by governance")
	}

// RegisterERC20 creates a Cosmos coin and registers the token pair between the
// coin and the ERC20
func (k Keeper) registerERC20(
	ctx sdk.Context,
	contract common.Address,
) (*types.TokenPair, error) {
	// Check if ERC20 is already registered
	if k.IsERC20Registered(ctx, contract) {
		return nil, errorsmod.Wrapf(
			types.ErrTokenPairAlreadyExists, "token ERC20 contract already registered: %s", contract.String(),
		)
	}

	metadata, err := k.CreateCoinMetadata(ctx, contract)
	if err != nil {
		return nil, errorsmod.Wrap(
			err, "failed to create wrapped coin denom metadata for ERC20",
		)
	}

	pair := types.NewTokenPair(contract, metadata.Name, types.OWNER_EXTERNAL)
	err = k.SetToken(ctx, pair)
	if err != nil {
		return nil, err
	}
	return &pair, nil
}

// DeleteTokenPair removes a token pair.
func (k Keeper) DeleteTokenPair(ctx sdk.Context, tokenPair types.TokenPair) {
	id := tokenPair.GetID()
	k.deleteTokenPair(ctx, id)
	k.deleteERC20Map(ctx, tokenPair.GetERC20Contract())
	k.deleteDenomMap(ctx, tokenPair.Denom)
	k.deleteAllowances(ctx, tokenPair.GetERC20Contract())
}
