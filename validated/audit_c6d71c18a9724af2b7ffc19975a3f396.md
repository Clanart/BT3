### Title
Symlink path escape via "Open in External Editor" / "Reveal in File Manager" on repo file entries - (File: app/src/ui/history/selected-commits.tsx, app/src/ui/changes/filter-changes-list.tsx, app/src/lib/app-shell.ts)

### Summary
Several context-menu actions that operate on file paths coming from git history/working-directory listings build the file's on-disk path with a naive `Path.join(repository.path, file.path)` and pass it directly to the OS (`shell.openExternal`, `shell.showItemInFolder`) without verifying the resolved path stays inside the repository. The codebase already has a purpose-built guard for exactly this class of bug, `resolveWithin()` (which explicitly resolves symlinks via `realpath` and rejects escapes, per its own tests), and it is used in `app/src/ui/dispatcher/dispatcher.ts` (`openRepositoryFromUrl`), `app/src/lib/copilot-conflict-context.ts`, and `app/src/lib/stores/app-store.ts` (Copilot conflict resolution write path). The file-list/history/pull-request context menus never call it.

### Finding Description
`revealInFileManager()` in [1](#0-0)  computes `Path.join(repository.path, path)` and hands it straight to `shell.showItemInFolder`, with no traversal or symlink check. The same unguarded pattern (`Path.join(repository.path, file.path)` followed by `openFile()`/`revealInFileManager()`/`dispatcher.openInExternalEditor()`) is used for: working-directory changes context menu [2](#0-1) , committed-file (History tab) context menu [3](#0-2) , pull-request diff viewer context menu [4](#0-3) , and the merge-conflict marker dropdown [5](#0-4) . `openFile()` then forwards the joined path unchanged to `shell.openExternal` [6](#0-5) , and `isSafeFileExtension()` only blocks four executable extensions on Windows and is not even applied to "Open in External Editor" or "Reveal in File Manager" [7](#0-6) .

Git tracks symlinks as normal blobs (mode `120000`) whose content is an arbitrary target string. A malicious cloned/fetched repository can contain a tracked symlink, e.g. `notes.txt -> /Users/victim/.ssh/id_rsa` (or a `.gitconfig`, browser profile, crypto wallet file, etc.). When checked out on macOS/Linux (where `core.symlinks` defaults to true), git materializes this as a real OS symlink inside the working directory pointing outside the repo. `Path.join(repository.path, 'notes.txt')` returns the *symlink's own path*, not its resolved target, so no lexical `..` is needed — the path looks perfectly benign and repo-relative, yet the OS call (`shell.openExternal('file://...')` or `shell.showItemInFolder`) follows the symlink and operates on the attacker-chosen target outside the repository.

This is precisely the invariant the report's bug class hinges on: some code paths correctly gate a dangerous operation on a security check (`_revertIfAuctionDebtLocked` in `moveQuoteToken`/`removeQuoteToken`; `resolveWithin` in `openRepositoryFromUrl`/`buildConflictContext`/Copilot resolution write), while a sibling code path performing an equivalent dangerous operation on attacker-influenced input (`kickWithDeposit`; the file-list/history context-menu "open"/"reveal" actions) omits it entirely.

### Impact Explanation
Clicking "Open in External Editor" on a symlinked entry from History or Changes opens the attacker-chosen target file's contents in the user's editor — a **file read outside the repository**, potentially exposing SSH keys, cloud credentials, browser cookie stores, or other sensitive local files. If the user then edits and saves in that editor believing they are editing a repo file, or if the file is later staged/committed as if it were the tracked symlink, contents of an out-of-repo file can leak into the repository/history, or worse, editing-and-saving directly writes to the target path — a **silent write outside the repo**. This satisfies the stated valid-impact criteria (attacker controls a cloned/fetched repository; result is file read/write outside the repo) without requiring local/physical access, admin rights, prior malware, or unnatural user steps — reviewing history/changes and using "Open in External Editor" is a completely normal Desktop workflow.

### Likelihood Explanation
High reachability, low complexity for the attacker: creating a tracked symlink pointing to a well-known sensitive path (`~/.ssh/id_rsa`, `~/.aws/credentials`) requires nothing beyond normal git operations (`ln -s`, `git add`, `git commit`) and is trivially embedded in any public repo, PR, or fork the victim clones/fetches/reviews. The only user action required is a single, routine right-click → "Open in External Editor" (or "Reveal in File Manager") on a file shown in Changes, History, or a Pull Request diff — no warning is shown because the UI only checks file existence (`pathExists`) and extension safety, neither of which detects a symlink pointing outside the repo.

### Recommendation
Route every attacker-influenced repository file path through `resolveWithin(repository.path, file.path)` (already implemented and symlink-aware, per `app/src/lib/path.ts` and its tests) before calling `revealInFileManager`, `openFile`, or `dispatcher.openInExternalEditor`, in `app/src/lib/app-shell.ts`, `app/src/ui/changes/filter-changes-list.tsx`, `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`, and `app/src/ui/lib/conflicts/unmerged-file.tsx`; reject (and log, as already done in `dispatcher.ts`) if the resolved path escapes the repository root.

### Proof of Concept
1. Attacker creates a repo containing a symlink: `ln -s /Users/victim/.ssh/id_rsa steal.txt && git add steal.txt && git commit -m "notes"`, then hosts/pushes it.
2. Victim clones or fetches this repository in GitHub Desktop and opens the History tab, selecting the commit containing `steal.txt`.
3. Victim right-clicks `steal.txt` and selects "Open in External Editor" (enabled regardless of extension, per `getOpenInExternalEditorMenuItem` in `filter-changes-list.tsx`/equivalent in `selected-commits.tsx`).
4. `Path.join(repository.path, 'steal.txt')` yields the symlink path; `openFile()` calls `shell.openExternal('file://<repoPath>/steal.txt')`, and the OS follows the symlink, opening `/Users/victim/.ssh/id_rsa` in the victim's default text editor — content outside the repository is now displayed and could be leaked/modified with no traversal-detection or warning ever shown. async function _resolveWithin(
```typescript
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
