### Title
Unvalidated `sender`/`recipient` participant indexes in PedPoP blame handling panic on missing map entries, crashing the validator - ([File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs])

### Summary
The PocketMine-MP bug class is "a party may request more of a resource than exists because the server never checked the requested count/index against what is actually available, causing a crash instead of an error." Serai's PedPoP DKG has the same shape: blame evaluation trusts the `sender` and `recipient` `Participant` indexes supplied with a blame accusation and indexes `self.enc_keys[&decryptor]` and `self.commitments[&sender]` directly. If either index was never registered (not part of the DKG set 1..=n), the `HashMap` index operator panics, aborting the process evaluating the blame.

### Finding Description
`AdditionalBlameMachine::blame` / `BlameMachine::blame` take `sender: Participant` and `recipient: Participant` from an external accusation and pass them to `blame_internal` without checking membership. `blame_internal` calls `Decryption::decrypt_with_proof`, which performs `self.enc_keys[&decryptor]` — a panicking `HashMap` index — to fetch the recipient's registered encryption key. [1](#0-0)  The keys map is only populated in `Decryption::register` for participants 1..=n via `AdditionalBlameMachine::new` / `verify_r1`. [2](#0-1)  Likewise, `blame_internal` evaluates `&self.commitments[&sender]`, which panics if `sender` was not among the registered commitments. [3](#0-2)  `Participant::new` only rejects zero; any index n+1..=u16::MAX is a well-formed `Participant` yet absent from both maps, so the missing-key case is fully reachable with crafted inputs.

The library even acknowledges this hazard in the `AdditionalBlameMachine::new` doc: "Usage of invalid commitments is considered undefined behavior, and may cause everything from inaccurate blame to panics" — but the panic path is in `blame` itself, driven by attacker-chosen indexes, not by invalid commitments. [4](#0-3) 

### Impact Explanation
A party able to submit a blame accusation (an unprivileged participant or anyone relaying blame messages to a validator/coordinator) can name a `recipient` or `sender` outside the registered set. The `HashMap` index panics, killing the thread/process evaluating the blame — the same crash-only impact as the reference advisory. Since blame evaluation is typically run to attribute faults before aborting a DKG, a crash aborts key generation with no blame attribution, letting a faulty DKG participant additionally evade being identified.

### Likelihood Explanation
Likelihood depends on the calling protocol authenticating blame messages: any party that can cause `blame(sender, recipient, msg, proof)` to be invoked controls both indexes. No signature or proof is needed to reach the panic — `decrypt_with_proof` touches `enc_keys[&decryptor]` before validating anything about the indexes, and `blame_internal` touches `commitments[&sender]` unconditionally when the PoP signature check passes (or `None` proof path still reaches `commitments[&sender]` via the share verification after a successful `Ok`... note: with `proof: None` it returns `InvalidProof` early, so the `enc_keys` panic requires `Some(proof)`; the `commitments[&sender]` panic additionally requires a valid PoP signature and canonical share, which the sender can produce honestly for any index pair). A malicious DKG participant satisfies both easily, so this is a reliably triggerable crash.

### Recommendation
Replace the panicking `HashMap` index operations with `get` + explicit error/`Participant` result: in `decrypt_with_proof`, return `DecryptionError::InvalidProof` (or a new `UnknownParticipant` variant) when `enc_keys.get(&decryptor)` is `None`; in `blame_internal`, treat a missing `commitments.get(&sender)` as fault of the accuser (`return recipient`) or a dedicated error rather than indexing. Additionally, validate `sender` and `recipient` against the known participant set at the `blame` entry point.
