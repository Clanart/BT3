### Title
Unbounded attacker-controlled participant count causes CPU exhaustion in `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` reads the `n` (number of participants) value directly from untrusted input and then loops `n` times performing expensive elliptic-curve point decompressions (`read_G`) before ever validating the threshold parameters. A crafted byte stream can force up to 65,535 point decompressions per call, a direct analog of CVE-2017-9257's attacker-controlled-count loop causing CPU-consumption DoS.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::<C>::read` deserializes `t`, `n`, and `i` as raw `u16` values from the reader [1](#0-0) . Validation of these parameters via `ThresholdParams::new(t, n, i)` only happens *after* all reads complete, inside the `ThresholdKeys::new` call at the end [2](#0-1) .

Two attacker-controlled loops run before validation:

1. **Constant interpolation**: if the interpolation byte is `0`, `Vec::with_capacity(n)` is allocated and `n` scalar reads (`C::read_F`) are performed [3](#0-2) .
2. **Verification shares**: a `HashMap` is populated by looping `for l in (1..=n)` and calling `read_G` on each iteration [4](#0-3) . Each `read_G` performs a full compressed-point decode/decompression — the most expensive operation in the deserialize path — and additionally the share polynomial is recomputed inside `ThresholdKeys::new` (group key derived over the interpolation/`verification_shares`), compounding the work.

`n` is a `u16`, so a single message can drive up to 65,535 point decompressions plus a 65,535-entry `HashMap` insertion — orders of magnitude more than any legitimate threshold set (the protocol caps key shares far lower, e.g. `MAX_KEY_SHARES_PER_SET`). There is no early bound check against the actual validator-set size; the loop bound is entirely attacker-controlled, exactly the `mp4ff_read_ctts` pattern of a crafted count field driving a large loop.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as a reachable untrusted-bytes sink) can cause each deserialization call to burn CPU proportional to a fully attacker-chosen `n` — up to ~65k EC decompressions and hash-map insertions per ~2 MB of input — stalling the thread performing key loading/recovery. Repeated submissions produce sustained CPU exhaustion (denial of service) against the validator/processor performing the read, matching the Medium severity, availability-only profile of the reference CVE (CVSS 5.5, `A:H`).

### Likelihood Explanation
The trigger is trivial: set `id_len`/`id` correctly, set interpolation byte `1` (Lagrange) to skip the scalar loop, then set `n = 0xFFFF` and append as many valid compressed points as desired. Any well-formed prefix passes; invalid points only cause an early per-iteration error, so worst case requires valid encodings — still just 32 bytes each. Reachability depends on an integrator feeding untrusted bytes to `ThresholdKeys::read`; within Serai this occurs wherever serialized `ThresholdKeys` are loaded from externally influenced storage/messages. The cost per input byte (~tens of microseconds of decompression per 32 bytes) makes this a meaningful amplification, though bounded by the `u16` count rather than unbounded — hence Medium, not High.

### Recommendation
Validate `t`, `n`, and `i` via `ThresholdParams::new` *before* performing any `n`-bounded loops, and reject `n` exceeding the protocol's maximum key-share count. Move the `ThresholdParams::new(t, n, i)` call to immediately after reading the three `u16`s, then use the validated `params.n()` for the interpolation and `verification_shares` loops.

### Proof of Concept
```rust
// Pseudocode against crypto/dkg ThresholdKeys::read (e.g. C = Ristretto)
let mut buf = vec![];
// curve ID framing
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
// t=1, i=1, n=u16::MAX
buf.extend(1u16.to_le_bytes());        // t
buf.extend(u16::MAX.to_le_bytes());    // n — attacker controlled
buf.extend(1u16.to_le_bytes());        // i
buf.push(1);                           // Interpolation::Lagrange (skips F loop)
buf.extend([1u8; 32]);                 // secret_share (must be valid F)
// ~65,535 valid compressed points -> ~65,535 read_G decompressions
for _ in 0 .. u16::MAX {
  buf.extend(valid_compressed_point);  // 32 bytes each
}
// Each call spends ~seconds of CPU before ThresholdParams::new is even reached
let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
```
