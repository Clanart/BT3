## Analog Found: Vesting-Locked `usei` Can Be Drained Through the Wei Sub-Denomination Bridge Without a Lock Check

### Title
Wei sub-unit debits bypass `LockedCoins` checks, letting vesting/locked `usei` be spent through the EVM StateDB - (File: `sei-cosmos/x/bank/keeper/send.go`)

### Summary
The reported Ubiquity bug is a class of "a subsystem debits a shared balance while ignoring an amount that must remain reserved for another obligation, producing improper accounting and fund misuse." The analogous path in sei-chain is the `usei`/`wei` StateDB bridge: `SubUnlockedCoins` correctly deducts the `LockedCoins` reserve before debiting the whole-`usei` portion of an EVM balance change, but the wei sub-unit debit path, `BaseSendKeeper.SubWei`, computes its available balance from the raw, unlocked-unaware `GetBalance` call and never consults `LockedCoins`. This lets an EVM account with vested/locked `usei` tokens spend those locked funds by repeatedly triggering tiny wei-denominated value transfers.

### Finding Description
`DBImpl.SubBalance` in the EVM StateDB splits every debited amount into a `usei` component and a `wei` component and applies them through two different keeper calls: [1](#0-0) 

The `usei` component correctly goes through `SubUnlockedCoins`, which subtracts `LockedCoins` from the raw balance before allowing the debit: [2](#0-1) 

But the `wei` component goes through `SubWei`, which — whenever the account's dust wei balance is insufficient — pulls directly from `k.GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount` (the *total* `usei` balance, not the spendable/unlocked balance) to cover the shortfall, with no reference to `LockedCoins` anywhere in the function: [3](#0-2) 

This mirrors the Ubiquity bug precisely: `freeCollateralBalance()` should have deducted `unclaimedPoolCollateral` before letting the AMO minter borrow, but the borrow path used the raw balance instead. Here, `SubUnlockedCoins` is the "correct" path that respects the reserve (`LockedCoins`), while `SubWei` is the "AMO minter" path that ignores the same reserve and draws on the raw total balance.

Because every EVM value transfer is split into `usei`/`wei` components via `SplitUseiWeiAmount`, and dust wei amounts almost always require borrowing one whole `usei` from the aggregate balance when the wei remainder is insufficient, a user (or a self-calling contract executing many small-value internal calls in one transaction) can repeatedly convert locked `usei` into spendable wei credit and then spend it — entirely bypassing the vesting/lock guarantee that `SubUnlockedCoins`/`LockedCoins` is supposed to enforce.

### Impact Explanation
This breaks the fund-locking guarantee of vesting accounts (or any account relying on `LockedCoins`, e.g. bonded/staked amounts represented as locked coins) for value transferred through the EVM. An attacker with a vesting or otherwise-locked `usei` balance can, through ordinary EVM transactions/internal calls, unlock and spend funds that should remain frozen — a direct violation of the fund-locking invariant and a concrete case of unauthorized transfer via the `usei`/`wei` bridge, reachable by any unprivileged EVM transaction sender.

### Likelihood Explanation
High. No special privileges are required — any account holding locked `usei` (e.g., a vesting account with an associated EVM address) can trigger this by sending EVM value transfers (or a contract making repeated tiny-value internal calls in a single transaction) that force the wei sub-unit shortfall path in `SubWei`.

### Recommendation
`SubWei` must respect `LockedCoins` the same way `SubUnlockedCoins` does: when computing `currentUseiBalance` for the aggregate wei/usei calculation, subtract the account's `LockedCoins` amount for the base denom (or otherwise ensure the post-aggregate balance check accounts for locked funds), rejecting the debit with `ErrInsufficientFunds` if it would dip into locked `usei`.

### Proof of Concept
1. Create/fund a vesting account and associate it with an EVM address, giving it a locked `usei` balance and zero/near-zero spendable balance and zero wei dust, mirroring the address-association test pattern used elsewhere in the repo. [4](#0-3) 
2. From that EVM address, submit (or have a contract submit via internal `CALL`s) repeated small-value transfers whose wei remainder exceeds the current wei dust balance, forcing `SubWei` to draw from `GetBalance` (total, lock-unaware) each time. [5](#0-4) 
3. Observe that the vesting/locked `usei` balance is depleted and effectively spent, even though `SubUnlockedCoins`/`LockedCoins` would have rejected an equivalent direct `usei` debit.

// SubUnlockedCoins removes the unlocked amt coins of the given account. An error is
// returned if the resulting balance is negative or the initial amount is invalid.
// A coin_spent event is emitted after.
func (k BaseSendKeeper) SubUnlockedCoins(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Coins, checkNeg bool) error {
	if !amt.IsValid() {
		return sdkerrors.Wrap(sdkerrors.ErrInvalidCoins, amt.String())
	}

	lockedCoins := k.LockedCoins(ctx, addr)

	for _, coin := range amt {
		balance := k.GetBalance(ctx, addr, coin.Denom)
		if checkNeg {
			locked := sdk.NewCoin(coin.Denom, lockedCoins.AmountOf(coin.Denom))
			spendable := balance.Sub(locked)

			_, hasNeg := sdk.Coins{spendable}.SafeSub(sdk.Coins{coin})
			if hasNeg {
				return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%s is smaller than %s", spendable, coin)
			}

func (k BaseSendKeeper) SubWei(ctx sdk.Context, addr sdk.AccAddress, amt sdk.Int) (err error) {
	if amt.Equal(sdk.ZeroInt()) {
		return nil
	}
	defer func() {
		if err == nil {
			ctx.EventManager().EmitEvent(
				types.NewWeiSpentEvent(addr, amt),
			)
		}
	}()
	currentWeiBalance := k.GetWeiBalance(ctx, addr)
	if amt.LTE(currentWeiBalance) {
		// no need to change usei balance
		return k.setWeiBalance(ctx, addr, currentWeiBalance.Sub(amt))
	}
	currentUseiBalance := k.GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount
	currentAggregatedBalance := currentUseiBalance.Mul(OneUseiInWei).Add(currentWeiBalance)
	postAggregatedbalance := currentAggregatedBalance.Sub(amt)
	if postAggregatedbalance.IsNegative() {
		return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%swei is smaller than %swei", currentAggregatedBalance, amt)
	}
	useiBalance, weiBalance := SplitUseiWeiAmount(postAggregatedbalance)
	if err := k.setBalance(ctx, addr, sdk.NewCoin(sdk.MustGetBaseDenom(), useiBalance), true); err != nil {
		return err
	}
	return k.setWeiBalance(ctx, addr, weiBalance)
}
