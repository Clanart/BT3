### Title
Deserialized `ReceivedOutput` accepts arbitrary outpoint/output pair, enabling spoofed wallet funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes an offset, a `TxOut`, and an `OutPoint` independently, but never checks that the supplied `OutPoint` actually refers to the supplied `TxOut`. An attacker can therefore submit a `ReceivedOutput` naming a real wallet-controlled outpoint while substituting a fabricated higher-value output with the wallet’s script. `SignableTransaction::new` then treats the fabricated output as spendable input value and commits it into the Taproot sighash data.

### Finding Description
The Mellium issue is a response-spoofing flaw caused by accepting a message without verifying that it has the expected type/relationship. The analogous condition here is that `ReceivedOutput::read` accepts three attacker-controlled fields without checking the essential relationship between them:

- `offset` is read as a secp256k1 scalar.
- `output` is decoded as an arbitrary Bitcoin `TxOut`.
- `outpoint` is decoded as an arbitrary transaction ID and output index.
- No transaction, block, UTXO lookup, Merkle proof, or other consistency check proves that `outpoint` resolves to `output`. [1](#0-0) 

The spend path trusts this association twice. First, `SignableTransaction::new` sums `input.output.value` as available funds while constructing inputs that spend `input.outpoint`. [2](#0-1)  Second, it stores the attacker-supplied `TxOut`s as `prevouts` and later passes all of them to `Prevouts::All` for Taproot signing. [3](#0-2) [4](#0-3) 

`SignableTransaction::multisig` checks only that the tweaked group key matches `prevouts[i].script_pubkey`; it does not check that the amount or the complete `TxOut` belongs to `tx.input[i].previous_output`. [5](#0-4) 

### Impact Explanation
An unprivileged party able to provide serialized `ReceivedOutput`s can cause a wallet or signing component to report funds that are not actually spendable. The fake record can point at an existing wallet output while claiming a larger amount, because the script can remain the wallet’s real Taproot script while the value is forged.

If this value is used for balance accounting, the attacker inflates apparent funds. If it reaches transaction construction, the signer signs a sighash computed over fabricated prevout data while the transaction references the real outpoint. The resulting transaction either commits to incorrect input data or fails consensus validation when verified against the real UTXO set. In both cases, funds represented to the local wallet differ from funds spendable on Bitcoin.

### Likelihood Explanation
The parser is explicitly public and accepts attacker-controlled bytes. The exploit does not require invalid scalar encodings, invalid points, key compromise, malicious validators, or protocol collusion: Bitcoin consensus decoding permits arbitrary `TxOut`/`OutPoint` pairs, and Serai performs no lookup or binding check.

The practical severity depends on the caller’s trust boundary. If `ReceivedOutput::read` is reserved exclusively for trusted local serialization, this is an unsafe trust assumption rather than remotely exploitable behavior. If untrusted scan results, wallet backups, peer responses, or processor messages can reach it, the spoof is directly reachable and can produce materially false balances and doomed signing attempts.

### Recommendation
Do not let `ReceivedOutput::read` establish wallet ownership or value. Either make deserialization internal to a trusted storage format, or add an explicit verified constructor that resolves each `OutPoint` against a trusted UTXO source and compares the returned `TxOut` byte-for-byte, including amount and script. `SignableTransaction::new` or `multisig` should reject outputs that have not passed that lookup, and coinbase maturity/confirmation status should be enforced before reporting an output as spendable.

At minimum, rename or type-separate untrusted decoded records from verified `ReceivedOutput`s so arbitrary `offset`, `TxOut`, and `OutPoint` tuples cannot enter the balance/signing path.

### Proof of Concept
```rust
use bitcoin::{consensus::encode::deserialize, OutPoint, TxOut};
use serai_bitcoin::wallet::{ReceivedOutput, SignableTransaction};

// `claimed` is crafted by an untrusted party.
// It contains:
//   1. a valid scalar offset for a registered wallet address,
//   2. a fabricated TxOut whose script_pubkey is the wallet script but whose
//      value is much larger than the real output,
//   3. the real wallet OutPoint.
let received = ReceivedOutput::read(&mut claimed.as_slice()).unwrap();

// No check proves `received.outpoint()` resolves to `received.output()`.
assert_eq!(received.outpoint(), real_wallet_outpoint);
assert_eq!(received.output().value.to_sat(), forged_large_value);

// The wallet treats `forged_large_value` as available input and spends
// `real_wallet_outpoint`.
let signable = SignableTransaction::new(
    vec![received],
    &payments,
    Some(change_script),
    None,
    fee_per_vbyte,
).unwrap();

// `signable` can pass the script check and enter threshold signing while its
// accounting/sighash data uses the forged prevout value.
```

The vulnerable root cause is that deserialization succeeds solely from byte validity; no semantic check binds `OutPoint` to `TxOut`.
