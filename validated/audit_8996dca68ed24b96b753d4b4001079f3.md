### Title
`ReceivedOutput::read` trusts caller-supplied spend offset, reporting unspendable outputs as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The CVE describes an OS-level routing mechanism that treats caller-supplied tag data as if it had been physically scanned — i.e., a path that normally derives authenticity from the input channel is replaced by one that trusts attacker-chosen bytes. The Serai analog is `Scanner`/`ReceivedOutput`: `Scanner::scan_transaction` derives the spend `offset` itself from on-chain `script_pubkey` matching, but `ReceivedOutput::read` deserializes an `offset` supplied by whoever produced the byte stream, with no consistency check that `key + offset * G` actually maps to `output.script_pubkey`. Untrusted bytes fed to `ReceivedOutput::read` therefore produce a `ReceivedOutput` claiming funds are received under a spend key that does not correspond to the output.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` and in `scan_transaction` looks up each `output.script_pubkey`, storing the verified `offset` into the returned `ReceivedOutput`. The offset is what makes the output spendable: `send.rs` uses `output.offset()` to re-key the threshold keys before producing the BIP-340 signature for each input. `ReceivedOutput::read` (lines 122–134) reads `offset` via `Secp256k1::read_F`, then decodes the `TxOut` and `OutPoint` from the same stream, and returns them unconditionally. There is no binding between the read `offset` and the read `output` — the caller never re-derives `p2tr_script_buf(key + offset * G)` nor compares it to `output.script_pubkey`.

### Impact Explanation
An unprivileged party who can cause a `ReceivedOutput` byte string to be consumed (e.g., relayed processor/coordinator messages carrying serialized received outputs) can attach an arbitrary scalar `offset` to a real, well-formed `TxOut`/`OutPoint`. The consumer accepts it as a spendable output: the wallet treats the funds as received and later attempts to sign with keys offset by an unrelated scalar. Because the offset does not correspond to the script_pubkey's tweaked key, the produced signature is invalid — the funds are reported received but are not spendable (liveness/funds-availability failure), and depending on accounting, a batch/plan can be constructed around an input that can never be signed, stalling signing retries.

### Likelihood Explanation
Reachability requires an attacker-controlled serialization path to `ReceivedOutput::read`; the type is explicitly in scope as an untrusted-bytes sink and is passed between components rather than only produced locally by `scan_transaction`. The attack needs only a valid on-chain output (or any TxOut bytes) plus a chosen scalar — no key material, no collusion, no mining. Impact is integrity/availability of received-funds tracking rather than direct theft, placing it at Medium.

### Recommendation
After deserializing in `ReceivedOutput::read` (or at the consumption site before signing), recompute `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)` and reject the input if it does not equal `output.script_pubkey`. Alternatively, store the scanner `key` alongside and make `ReceivedOutput` unforgeable by construction — e.g., serialize only the `(offset, outpoint)` pair and re-fetch/verify the `TxOut` from chain data.

### Proof of Concept
```rust
// Given a Scanner for `key` and an honest on-chain output `txout`
// paying to p2tr(key + offset_real * G):
let mut buf = Vec::new();
// Attacker writes a WRONG offset (e.g., Scalar::ZERO instead of offset_real)
buf.extend(Secp256k1::F::to_bytes(&Scalar::ZERO));
buf.extend(bitcoin::consensus::encode::serialize(&txout));   // real TxOut
buf.extend(bitcoin::consensus::encode::serialize(&outpoint)); // real OutPoint

let received = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// `received` is accepted: value() reports the funds as received,
// but offset() = 0, so SignableTransaction/TransactionSignMachine will
// sign with the un-offset key. The BIP-340 signature will not verify
// against the tweaked output key; the output is unspendable despite
// being reported received.
```

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
