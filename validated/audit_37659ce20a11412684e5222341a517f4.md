### Title
Daemon logs unredacted sensitive data (passphrases, keys, mnemonics) at ERROR level for unrecognized commands - (File: `chia/daemon/server.py`)

### Summary
The Chia daemon's local websocket RPC handler redacts sensitive fields before debug-logging *known* incoming messages, but a separate fallback branch that handles unrecognized commands logs the **raw, unredacted** message dictionary at `ERROR` level. This mirrors the Airflow bug class (CWE-200): a sensitive-data masking mechanism exists but is applied inconsistently, so secrets end up in plaintext logs that operators/users with log-view access can read.

### Finding Description
`WebSocketServer.incoming_connection()` explicitly redacts sensitive keys before logging a received message: [1](#0-0) 

The redaction function only strips values whose *key name* contains one of a fixed set of substrings (`"pass"`, `"key"`, `"secret"`, `"mnemonic"`): [2](#0-1) 

However, `handle_message()` — the function that actually dispatches the command — has a fallback path for any command not found in `get_command_mapping()`. This path logs the **original, unredacted** `message` dict (which still contains the full `"data"` payload, e.g. passphrases, keys, mnemonics, or keychain entropy) at `ERROR` level, completely bypassing `redact_sensitive_data()`: [3](#0-2) 

Additionally, the keychain command handlers (`get_all_private_keys`, `get_first_private_key`, `get_key_for_fingerprint`) return raw seed material under the field name `"entropy"` — a name that does not match any of the redaction triggers (`pass`, `key`, `secret`, `mnemonic`), so even the "successful" redaction logic would silently fail to mask this field if it were ever logged: [4](#0-3) 

This is the same root cause pattern as the Airflow advisory: a maintained allow/deny-list of "sensitive" field names is incomplete and inconsistently enforced across code paths, so secret values that should never be exposed end up in logs viewable by anyone with local log/file access.

### Impact Explanation
Any client connected to the local daemon (wallet UI, CLI, GUI, or any other locally-authorticated but non-privileged process using the daemon websocket) can trigger the unredacted `"UK>> {message}"` log line simply by sending a command name that doesn't match `get_command_mapping()` while embedding sensitive fields (e.g. `current_passphrase`, `mnemonic`, `key`, or arbitrary keychain data) in the `data` payload. Because the log statement is unconditionally at `ERROR` level (unlike the redacted "Received message" line, which is gated behind `DEBUG`), it is far more likely to be captured in default log files. Exposure of a keyring passphrase, private key, or mnemonic through logs directly leads to unauthorized/unsigned coin movement, since anyone who reads the log (support staff, log aggregation systems, or any local process with read access to the log file) obtains the material needed to derive spend keys and move coins without the owner's authorization.

### Likelihood Explanation
Reaching this path requires only sending a single malformed/unknown daemon command with a crafted `data` field over the local daemon websocket — no special privilege beyond the ability to connect to the daemon (the same access level as any legitimate wallet/CLI client). This is easy to trigger accidentally (e.g., a client using an outdated/misspelled command name) or deliberately.

### Recommendation
- Apply `redact_sensitive_data()` (or an equivalent) to the `message` object before it is included in the `"UK>> {message}"` error log in `handle_message()`.
- Expand/replace the substring-based `redaction_triggers` list with an explicit denylist/allowlist that also covers non-obvious sensitive field names such as `entropy`, `sk`, `seed`, `sk_hex`, etc., rather than relying on ad hoc substring matches.
- Audit all other `self.log.error/debug/info` call sites in `chia/daemon/server.py` and `chia/daemon/keychain_server.py` that log request/response dictionaries directly, ensuring none bypass the shared redaction helper.

### Proof of Concept
1. Connect to the local daemon websocket (same access as a normal wallet/CLI client).
2. Send a JSON payload with an unrecognized `"command"` (not in `get_command_mapping()` and not in `keychain_commands`) and a `"data"` field containing sensitive content, e.g.:
```json
{
  "command": "totally_unknown_command",
  "ack": false,
  "data": {"current_passphrase": "my-real-passphrase", "mnemonic": "24 word secret ..."},
  "request_id": "abc",
  "destination": "daemon",
  "origin": "attacker"
}
```
3. Observe the daemon log: `handle_message()` hits the `else` branch and executes `self.log.error(f"UK>> {message}")` with the full, unredacted dict, writing the passphrase/mnemonic to the log file in cleartext — unlike the "Received message" debug line, which would have redacted it.

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```

```python
        all_keys: list[dict[str, Any]] = []
```
