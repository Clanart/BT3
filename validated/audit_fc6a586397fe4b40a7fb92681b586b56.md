### Title
`forceUnLock` in VLMGP fails to claim pending MGP/base rewards before reducing staked balance, causing permanent loss of unclaimed rewards - (File: `VLMGP.sol`)

### Summary
`VLMGP.forceUnLock()` reduces a user's staked vlMGP balance in `MasterMagpie` via `_unlock()` without first claiming the user's pending MGP and base-rewarder rewards, unlike the sibling functions `startUnlock()` and `unlock()`, which both explicitly call `IMasterMagpie(masterMagpie).multiclaimFor(...)` immediately before adjusting the staked amount.

### Finding Description
`VLMGP` implements a MasterChef-style reward accounting model where `MasterMagpie` tracks `user.amount` and `user.rewardDebt` per `(stakingToken, account)` pair, and pending reward = `user.amount * accMGPPerShare / 1e12 - user.rewardDebt` [1](#0-0) . Whenever the staked amount changes, any pending reward accrued under the old amount must be harvested/claimed before the amount and `rewardDebt` are recalculated, otherwise the differential accrued under the old balance is permanently lost.

Both `startUnlock()` and `unlock()` in `VLMGP.sol` correctly follow this pattern by calling `IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender)` right before reducing the user's locked/staked amount: [2](#0-1) [3](#0-2) 

However, `forceUnLock()` omits this claim step entirely and goes straight into `_unlock(slot.amountInCoolDown)`, which calls `IMasterMagpie(masterMagpie).withdrawVlMGPFor(...)` to reduce the user's staked amount without any preceding harvest: [4](#0-3) [5](#0-4) 

This mirrors the reported bug class exactly: one function in a pair of otherwise-equivalent state-transition functions (`merge` vs `withdraw` in the original report; `forceUnLock` vs `unlock`/`startUnlock` here) forgets to claim pending rewards before an operation that changes the reward-accounting basis (burn vs. balance reduction), permanently losing the user's already-accrued but unclaimed MGP and base-rewarder rewards for the amount being force-unlocked.

### Impact Explanation
Any user who calls `forceUnLock()` to exit a cooldown slot early loses whatever pending MGP (and any queued base-rewarder rewards tied to the vlMGP pool) had accrued on the amount in that slot up to that point, since `rewardDebt` is recalculated against the reduced balance without first crediting the pending differential to the user. This is a permanent freezing/loss of unclaimed yield reachable by any ordinary wallet holding a vlMGP lock — no privileged role is required.

### Likelihood Explanation
`forceUnLock()` is a standard user-facing function (already in cooldown, exiting early with a penalty) that any vlMGP holder can call at will; the missing claim step is deterministic and triggers on every invocation, so the loss occurs on the normal, unprivileged usage path.

### Recommendation
Add the same `IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender)` call in `forceUnLock()` immediately before invoking `_unlock(slot.amountInCoolDown)`, mirroring the pattern already used in `startUnlock()` and `unlock()`.

### Proof of Concept
1. User locks MGP via `VLMGP.lock()`, accrues MGP/base rewards over time via `MasterMagpie`.
2. User calls `startUnlock()` to place part of the balance into a cooldown slot (this correctly claims pending rewards at this point).
3. Rewards continue to accrue on the user's remaining/cooling balance is not the focus; instead, before the slot naturally matures, the user calls `forceUnLock(_slotIndex)`.
4. Because `forceUnLock()` never calls `multiclaimFor`, any MGP/base-rewarder rewards accrued between the last claim and the `forceUnLock` call are lost: `_unlock()` triggers `withdrawVlMGPFor` which recalculates `rewardDebt` against the new (lower) balance, discarding the pending differential rather than crediting it to the user, and there is no other function that can retroactively recover that lost differential.
