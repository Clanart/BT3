### Title
Shared `BalanceHandler` state across recursive/nested precompile calls causes StateDB/bank balance desync - (File: precompiles/common/balance_handler.go, precompiles/common/precompile.go)

### Summary
The Analog Report describes a Bunni/FloodPlain vulnerability where a stateful pairing mechanism between a "pre-hook" and a "post-hook" was not properly enforced, letting an attacker execute a valid pre-hook and an unrelated malicious post-hook, corrupting the pool's accounting. The Cosmos EVM analog is the `BalanceHandler`'s `BeforeBalanceChange`/`AfterBalanceChange` pairing mechanism used by stateful precompiles: `prevEventsLen` is meant to mark exactly which bank events belong to the current precompile invocation so `AfterBalanceChange` can translate only those events into `StateDB` balance mutations. The repository's own integration test explicitly documents that when precompile calls recurse (e.g., a precompile that internally triggers another EVM call into a precompile, such as the debug precompile's `CallEVMWithData` re-entering itself), the same `BalanceHandler` instance can be shared across the nested invocations, and the inner call's `BeforeBalanceChange` overwrites `prevEventsLen`, desynchronizing the "pre" and "post" state so that the outer call's `AfterBalanceChange` processes the wrong window of events.

### Finding Description
`BalanceHandler.BeforeBalanceChange` records `prevEventsLen = len(ctx.EventManager().Events())` [1](#0-0) , and `AfterBalanceChange` later slices `events[bh.prevEventsLen:]` to determine which bank `CoinSpent`/`CoinReceived`/fractional-balance events to translate into `StateDB.AddBalance`/`SubBalance` calls [2](#0-1) . This is precisely a "pre-hook / post-hook" pairing mechanism analogous to `rebalanceOrderPreHook`/`rebalanceOrderPostHook` in the original report — it depends on `Before` and `After` being executed as a strictly paired, non-interleaved unit against a single, stable event-log baseline.

In the normal (non-recursive) case, `RunNativeAction`/`runNativeAction` allocates a brand-new `BalanceHandler` per call via `p.BalanceHandlerFactory.NewBalanceHandler()` [3](#0-2) , so each precompile invocation gets its own isolated `prevEventsLen`. However, other precompile implementations (e.g., the debug/test precompile pattern and, per the repository's own test suite, real precompiles that make EVM calls that recurse back into a precompile) instead use a shared/singleton handler obtained via `p.GetBalanceHandler()` [4](#0-3) . When such a call is nested (an outer precompile call triggers, via `CallEVMWithData`/`CallEVM`, another EVM execution that re-enters the same precompile or another one sharing the handler), the inner call's `BeforeBalanceChange` overwrites the single `prevEventsLen` field that the outer call is still relying on. When the outer call's `AfterBalanceChange` eventually runs, it slices events from the *inner* call's baseline instead of its own, either skipping legitimate balance events that occurred between the outer `Before` and the inner `Before`, or double-processing/misattributing events belonging to the inner call.

The repository itself contains a dedicated regression test, `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile`, whose docstring states: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [5](#0-4) . This confirms the bug class exists in the production balance-reconciliation path connecting `x/bank`-driven precompile state changes to the EVM `StateDB`.

### Impact Explanation
`StateDB` balances are what the EVM opcodes (`BALANCE`, `CALL` value transfers, subsequent precompile balance checks) observe during the remainder of the transaction, while `x/bank` is the source of truth for the native ledger. If `AfterBalanceChange` uses a stale/overwritten `prevEventsLen`, the `StateDB` balance for accounts involved in the precompile call can diverge from the actual `x/bank` balance changes that were committed via `CommitWithCacheCtx`. Since the native bank state has already moved (coins spent/received) but the EVM `StateDB` view is not correctly reconciled, this can result in: (1) accounts observing an inflated `StateDB` balance relative to their real bank balance, which can be spent again in the same or later EVM calls before the discrepancy is corrected (double-spend of the same underlying value), or (2) legitimate balance credits being silently dropped from `StateDB`, permanently understating a user's spendable balance relative to bank truth causes irreversible accounting corruption between the two balance views that back the same spendable value — matching the Critical "unauthorized minting/duplication ... or irreversible accounting corruption of spendable user value across native balances, EVM balances ... or precompile-mediated assets" impact category.

### Likelihood Explanation
Reachability depends on which precompiles use a shared/singleton `BalanceHandler` and can be recursively invoked (a precompile call that itself triggers an EVM sub-call landing on a precompile using the same handler instance, e.g. via `CallEVM`/`CallEVMWithData` patterns as seen in the debug precompile and IBC callback keeper). An unprivileged EVM caller only needs to construct a call path that recurses into a precompile-backed balance-changing operation (e.g., wrapping a precompile call inside a contract that itself calls back into a precompile, or chaining precompile calls that internally perform further EVM calls) — no privileged role is required. The repository has already written and merged a dedicated reproduction test for exactly this scenario, indicating the maintainers recognize it as a genuine, reachable bug rather than a theoretical one; whether it has since been fully fixed for all precompiles or only demonstrated/partially mitigated could not be confirmed from the available index (see caveat below).

### Recommendation
- Ensure every precompile invocation (including nested/recursive ones) obtains a freshly-scoped `BalanceHandler` instance rather than sharing one via a `GetBalanceHandler()` singleton accessor, mirroring the `BalanceHandlerFactory.NewBalanceHandler()` pattern already used in `precompiles/common/precompile.go`.
- Make the `Before`/`After` pairing reentrancy-safe: push/pop `prevEventsLen` on a stack (or track it per call-depth) instead of a single mutable field, so nested calls cannot clobber an outer call's baseline.
- Add an explicit invariant check after `AfterBalanceChange` that reconciles the cumulative `StateDB` delta against the actual `x/bank` delta for all touched addresses within the same transaction, reverting the precompile call on mismatch — analogous to the "long-term" recommendation of redesigning the flow so pre/post state validation is provably atomic rather than relying on convention.

### Proof of Concept
Not independently reproduced here; the existence and mechanics are demonstrated by the repository's own test, `TestRecursivePrecompileCallsWithDebugPrecompile`, in `evmd/tests/integration/balance_handler/balance_handler_test.go`, which deploys a caller contract that recursively invokes the debug precompile (`callback(0)`) and asserts on the resulting event/state counts to characterize the desync [6](#0-5) .

**Caveat / uncertainty:** I could not fully confirm within the available index (1) the exact current mitigation status (whether this specific bug is already fixed for all production precompiles or only reproduced/tracked via this test), or (2) which specific in-scope production precompiles (beyond the test-only debug precompile) currently use a shared `GetBalanceHandler()` accessor versus the per-call `BalanceHandlerFactory.NewBalanceHandler()` pattern, since the grep search for `GetBalanceHandler` definitions did not complete successfully before the session ended. A Devin session with full repository access should verify whether any shipped precompile (ERC20, WERC20, staking, distribution, ICS20, callbacks) shares a `BalanceHandler` instance across nested/recursive EVM calls in production code paths, not just in test/debug precompiles.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
