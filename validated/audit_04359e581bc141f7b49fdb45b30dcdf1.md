### Title
Unbounded `io.ReadAll` on RPC request body before size validation enables memory-exhaustion DoS - (File: `networks/rpc/http_newrelic.go`)

### Summary
When Kaia's HTTP JSON-RPC server is configured with NewRelic APM or Datadog APM tracing enabled, every inbound HTTP RPC request is first routed through `getRPCRequests`, which reads the *entire* request body into memory with `io.ReadAll(r.Body)` before any of the server's content-length/size validation is applied. This mirrors the exact bug class in CVE-2023-6337 (HashiCorp Vault): a public HTTP endpoint maps an attacker-controlled request body fully into memory prior to enforcing any size limit, allowing a single unauthenticated request to exhaust host memory.

### Finding Description
`NewHTTPServer` builds the middleware chain for the JSON-RPC HTTP endpoint. The APM instrumentation handlers (`newNewRelicHTTPHandler`, `newDatadogHTTPHandler`) are installed as the **outermost** wrappers, executing before the CORS/vhost/timeout handlers and before the core `Server.ServeHTTP`, which is where `validateRequest` enforces `r.ContentLength > common.MaxRequestContentLength` and where `newHTTPServerConn` applies `io.LimitReader(r.Body, common.MaxRequestContentLength)`: [1](#0-0) 

Both APM wrappers unconditionally call `getRPCRequests(r)` at the very start of the handler, before delegating to the inner `handler.ServeHTTP`: [2](#0-1) [3](#0-2) 

`getRPCRequests` itself performs an unbounded `io.ReadAll(r.Body)` with no length check whatsoever, buffering the full attacker-supplied body into a Go byte slice regardless of size: [4](#0-3) 

The only size enforcement in the codebase (`common.MaxRequestContentLength`, default 512 KiB) is applied later, inside `validateRequest`/`newHTTPServerConn`, which never runs until *after* `getRPCRequests` has already consumed the entire body into memory: [5](#0-4) [6](#0-5) 

Because `http.Server` (as constructed in `NewHTTPServer`) does not set `MaxHeaderBytes`-equivalent body ceiling or wrap `r.Body` with `http.MaxBytesReader`, and `ReadTimeout`/`WriteTimeout` only bound time, not size, an attacker who sends a very large (multi-GB, chunked or declared) POST body to the public RPC endpoint forces the node to allocate memory proportional to the request size before any rejection occurs — for every request, without authentication.

### Impact Explanation
A single unauthenticated HTTP RPC caller can send an arbitrarily large POST request to any Kaia node with the NewRelic or Datadog APM handler enabled, driving unbounded heap allocation via `io.ReadAll`. Repeated or concurrent such requests exhaust available memory on the node, crashing or OOM-killing the process — a denial-of-service against the node's public RPC availability, matching CWE-770 (uncontrolled resource consumption) and the High-severity classification of the analogous Vault advisory.

### Likelihood Explanation
Exploitation requires no authentication or special privileges — only that the operator has enabled NewRelic (`NEWRELIC_APP_NAME`/`NEWRELIC_LICENSE`) or Datadog (`DD_TRACE_ENABLED`) instrumentation, which is a common production observability configuration, not a hardening/security boundary. Once enabled, every request to the HTTP JSON-RPC listener passes through the vulnerable `getRPCRequests` path unconditionally, so the attack surface is the normal public RPC port.

### Recommendation
Wrap `r.Body` with `http.MaxBytesReader(w, r.Body, common.MaxRequestContentLength)` (or apply an equivalent `io.LimitReader`) before calling `io.ReadAll` in `getRPCRequests`, and/or move the `validateRequest` content-length check ahead of the APM instrumentation layer so oversized requests are rejected before any body-buffering middleware executes.

### Proof of Concept
1. Start a Kaia node with HTTP RPC enabled and set `NEWRELIC_APP_NAME`/`NEWRELIC_LICENSE` (or `DD_TRACE_ENABLED=true`) so `newNewRelicHTTPHandler`/`newDatadogHTTPHandler` wraps the RPC server.
2. Send an HTTP POST to the RPC endpoint with `Transfer-Encoding: chunked` (or a very large `Content-Length`) streaming several GB of arbitrary bytes as the body, e.g.:
   ```
   curl -X POST http://node:8551 -H "Content-Type: application/json" \
        --data-binary @large_multi_gb_file.bin
   ```
3. Observe that `newNewRelicHTTPHandler`/`newDatadogHTTPHandler` calls `getRPCRequests` → `io.ReadAll(r.Body)`, buffering the full multi-GB body into memory before `validateRequest`'s `MaxRequestContentLength` check is ever reached in `Server.ServeHTTP`.
4. Repeating this with concurrent requests exhausts node memory, causing degraded service or a crash.

	if r.Method == http.MethodPut || r.Method == http.MethodDelete {

	}

func getRPCRequests(r *http.Request) ([]*jsonrpcMessage, bool, error) {
	reqBody, err := io.ReadAll(r.Body)
	if err != nil {
		logger.Error("cannot read a request body", "err", err)
		return nil, false, err
	}

	r.Body = io.NopCloser(bytes.NewReader(reqBody))
	conn := &httpServerConn{Reader: io.NopCloser(bytes.NewReader(reqBody)), Writer: bytes.NewBufferString(""), r: r}

	codec := NewCodec(conn)

	defer codec.close()

	return codec.readBatch()
}
