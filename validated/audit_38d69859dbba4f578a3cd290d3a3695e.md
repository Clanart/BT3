## Analysis: Nested Precompile Balance-Event Double-Application (analog of the absorb ordering bug)

### Title
Overlapping event ranges in nested/recursive precompile calls cause double-application of balance deltas to EVM StateDB — (File: `precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
The external report's root cause is an ordering bug: a caller-visible balance is computed from a "before" state snapshot, but an update that should have happened first is deferred, so the caller either misses or double-counts value. The Cosmos EVM analog is `BalanceHandler.BeforeBalanceChange`/`AfterBalanceChange` in `precompiles/common/balance_handler.go`, which uses an event-index watermark (`prevEventsLen`) to slice `ctx.EventManager().Events()` and replay bank-balance deltas onto the EVM `StateDB`. This pattern already has a documented regression test explicitly describing this exact class of bug.

### Finding Description
Each precompile call goes through `Precompile.runNativeAction` [1](#0-0) , which:
1. Records `prevEventsLen = len(ctx.EventManager().Events())` before executing the native action.
2. Runs the native action, which may perform bank/precisebank transfers (emitting `EventTypeCoinSpent`, `EventTypeCoinReceived`, `EventTypeFractionalBalanceChange`) and, in cases like the staking/distribution/erc20/gov precompiles, may re-enter the EVM (e.g., invoking a contract callback) which can trigger another nested precompile call.
3. After the action returns, replays `events[prevEventsLen:]` onto `stateDB.AddBalance`/`SubBalance` [2](#0-1) .

Because `ctx.EventManager()` is shared across the entire cached context tree used by nested calls, if an outer precompile call's native action triggers an inner precompile call (nested `RunNativeAction`), the inner call captures its own `prevEventsLen` (a later watermark) and applies only the events generated during its own execution. However, the outer call's watermark was recorded *before* the inner call began, so when the outer call's `AfterBalanceChange` runs, its event slice `events[outerPrevEventsLen:]` still includes all the events that were already consumed and applied to `StateDB` by the inner call's `AfterBalanceChange`. This results in those balance-changing events being replayed a second time against `stateDB.AddBalance`/`SubBalance`, artificially inflating or duplicating balances recorded in the EVM `StateDB` relative to the actual bank-module ledger.

This is precisely the scenario documented by the repository's own regression test, `TestRecursivePrecompileCallsWithDebugPrecompile`, whose comment states: "tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." [3](#0-2) 

I was not able to fully confirm from the available index whether this specific double-counting path is still open or has been fully closed by later code (e.g., whether `stateDB.GetCacheContext()` returns per-call isolated event managers that prevent the overlap, or whether `AddPrecompileFn`/journal snapshot logic in `runNativeAction` [4](#0-3)  deduplicates replayed events across nesting depths). The presence of a dedicated regression test targeting exactly this scenario indicates the maintainers treated it as a real, previously-reachable bug class, but I cannot verify from the indexed files whether the currently-tested fix (mentioned as "fixed by updating the EVM state after each function call" in the staking precompile integration tests [5](#0-4) ) fully closes all nested-call event-overlap paths across every precompile pairing (e.g., staking → distribution → erc20 chains), or only the specific pattern exercised by the debug precompile test.

### Impact Explanation
If exploitable, this would allow an unprivileged contract to trigger a chain of nested precompile calls (e.g., a contract that calls a precompile, which internally issues a call back into the EVM invoking a second precompile) such that bank-module balance-change events get replayed multiple times onto the EVM `StateDB`. This would desynchronize `StateDB` balances from the actual `x/bank`/`x/precisebank` ledger, effectively duplicating spendable EVM-visible balance for an address without a corresponding mint in the bank module — a Critical unauthorized-duplication-of-spendable-value issue matching the required impact gate.

### Likelihood Explanation
Given that a dedicated regression test already exists targeting this exact scenario, the bug class was reachable in a prior version of the code via ordinary, unprivileged contract calls (no privileged keys required — just a contract that recursively invokes precompiles). Whether it remains reachable in the current `main` state of this repo is uncertain from the available index; the fix referenced in the staking integration tests suggests mitigation is in place, but I could not confirm its completeness across all precompile combinations from indexed content alone.

### Recommendation
Verify that `BalanceHandler` watermarking is robust across arbitrary nesting depth and precompile combinations — e.g., by tracking a globally-shared "last processed event index" across nested `BalanceHandler` instances within a single EVM call (rather than a value scoped to the individual `runNativeAction` call), or by having `AfterBalanceChange` advance a shared cursor so overlapping ranges can never be replayed twice. Extend `balance_handler_test.go`-style regression tests to cover heterogeneous nested precompile pairs (e.g., staking-calls-distribution-calls-erc20) rather than only the debug precompile self-recursion case.

### Proof of Concept
Not independently reproducible from the indexed files alone. The existing test `TestRecursivePrecompileCallsWithDebugPrecompile` [6](#0-5)  is the closest available reproduction scaffold: it deploys a caller contract that recursively invokes a debug precompile and asserts on the resulting event/balance counts. A full PoC would require constructing a similar recursive-call scenario using two *different* production precompiles (each with `BalanceHandlerFactory` configured, e.g. `precompiles/staking/staking.go` [7](#0-6) ) where the outer precompile's native action triggers an EVM call into a second precompile that itself moves bank balances, then asserting whether `StateDB` balances diverge from `x/bank`/`x/precisebank` ledger balances after the call — which I was unable to execute or trace to completion given tool/iteration limits.

func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case precisebanktypes.EventTypeFractionalBalanceChange:
			addr, err := ParseAddress(event, precisebanktypes.AttributeKeyAddress)
			if err != nil {
				return fmt.Errorf("failed to parse address from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}
			if bh.bankKeeper.BlockedAddr(addr) {
				// Bypass blocked addresses
				continue
			}

			delta, err := ParseFractionalAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", precisebanktypes.EventTypeFractionalBalanceChange, err)
			}

			deltaAbs, err := utils.Uint256FromBigInt(new(big.Int).Abs(delta))
			if err != nil {
				return fmt.Errorf("failed to convert delta to Uint256: %w", err)
			}

			if delta.Sign() == 1 {
				stateDB.AddBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			} else if delta.Sign() == -1 {
				stateDB.SubBalance(common.BytesToAddress(addr.Bytes()), deltaAbs, tracing.BalanceChangeUnspecified)
			}

		default:
			continue
		}
	}

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
