### Title
Deserialized `ReceivedOutput` grants an arbitrary key-derivation scope to any output, reporting unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner` establishes a strict binding between a registered `offset` and the `script_pubkey` it produces (`key + offset*G`, even-Y only). `ReceivedOutput::read`, however, deserializes `(offset, output, outpoint)` as three independent untrusted fields with no consistency check. A crafted blob can therefore attach a "spend authority" claim (an offset, the analog of owner-scope authority) to an output that was never derived for it — the same confused-deputy shape as the reference advisory: an untrusted ingress path selects authority it was never granted.

### Finding Description
`Scanner::register_offset` computes `p2tr_script_buf(self.key + GENERATOR * offset)` and stores `scripts[script] = offset`, so `scan_transaction` only ever emits `ReceivedOutput`s whose offset provably derives the output's `script_pubkey` (networks/bitcoin/src/wallet/mod.rs:180-214). By contrast, `ReceivedOutput::read` reads a `Scalar` offset via `Secp256k1::read_F`, then an arbitrary `TxOut` and `OutPoint`, and returns them as a "spendable output" without verifying `output.script_pubkey == p2tr_script_buf(key + offset*G)` for the scanning key (networks/bitcoin/src/wallet/mod.rs:122-134). The `offset` is documented as "the scalar offset to obtain the key usable to spend this output" (line 91) and is later applied via `ThresholdKeys::offset`, which adds `offset*G` to the group key and to `included[0]`'s share in `ThresholdKeys::view` (crypto/dkg/src/lib.rs:414-417, 518-521). There is no re-derivation anywhere on the deserialize path.

### Impact Explanation
An attacker who feeds bytes to `ReceivedOutput::read` can report funds as received under an offset/key that does not correspond to the output's `script_pubkey`. Two variants: (a) an output paying to the wallet's real tweaked key paired with a wrong offset — the wallet counts the value and produces a FROST signature for the wrong tweaked key, which the Bitcoin network rejects, so funds "received" are not spendable; (b) an output paying to an attacker-controlled script paired with a wallet offset — the wallet credits a deposit it can never spend. Both inflate reported balance with unspendable outputs, a concrete "funds reported received that are not spendable" impact.

### Likelihood Explanation
Reachable whenever serialized `ReceivedOutput`s cross a trust boundary (coordinator→processor, disk state, RPC payloads) — precisely the untrusted-byte ingestion surface this format is designed for. Exploitation requires no threshold collusion, no malicious validator, and no leaked keys; only control of the input bytes. Severity is bounded by whether downstream code acts on the credited value before an on-chain spend fails, so Medium is appropriate.

### Recommendation
Bind the offset to the output at deserialization or spend time: either store the scanning key in `ReceivedOutput` and re-verify `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey` in `read`, or require callers to pass the expected `ScriptBuf`/`key` to `read` and reject mismatches. Alternatively, have `scan_transaction` outputs be the only constructor and make `read` verify against a `Scanner` instance.

### Proof of Concept
1. Register `offset_a` with `Scanner::register_offset`, obtaining `script_a` for `key + offset_a*G`.
2. Craft a buffer containing `offset_b != offset_a`, followed by a `TxOut` whose `script_pubkey` is `script_a` (or an attacker script), followed by any valid `OutPoint`.
3. `ReceivedOutput::read` accepts it; the wallet reports `value()` as a spendable receipt.
4. Spending uses `keys.offset(offset_b)`; the resulting threshold signature authorizes `key + offset_b*G`, which does not control `script_a` — the output is unspendable despite being credited.
