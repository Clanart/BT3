This confirms hookify runs as a `PreToolUse` hook that evaluates rules *before* the `MultiEdit` tool actually executes, and the block/allow decision depends entirely on `RuleEngine._extract_field`'s naive `' '.join(...)` reconstruction rather than the true post-edit file content.### Title
Hookify MultiEdit `content`/`new_text` extraction can be bypassed by splitting a secret across multiple `edits`, evading `block` rules - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._extract_field` reconstructs the text checked against `regex_match`/`contains` rules for `MultiEdit` by naively joining each edit's `new_string` with a single space (`' '.join(e.get('new_string', '') for e in edits)`). Because the join always inserts a literal space at every edit boundary regardless of where the edits actually land in the target file, an attacker-controlled instruction that causes Claude to write a secret split across two or more `MultiEdit` edits can produce a reconstructed check-string that never contains the secret contiguously, while the actual resulting file content does (when the edits' insertion points are adjacent). This lets a `block`-action hookify rule (e.g. a `.env`/`API_KEY` pattern) silently fail to fire on a `PreToolUse` MultiEdit call that would otherwise leak/write a secret.

### Finding Description
`pretooluse.py` invokes `RuleEngine.evaluate_rules` on every `PreToolUse` event for `Edit`, `Write`, `MultiEdit` [1](#0-0) . `evaluate_rules` -> `_rule_matches` -> `_check_condition` -> `_extract_field(condition.field, ...)`, then applies `regex_match`/`contains` against the extracted string [2](#0-1) . For `MultiEdit`, the `content`/`new_text` field is built as `' '.join(e.get('new_string', '') for e in edits)` [3](#0-2) . This concatenation is a heuristic approximation of "what will end up in the file" — it is neither the real post-apply file content nor a substring-preserving transform. Splitting a sensitive literal (e.g. an `API_KEY` value) across two `new_string` entries, e.g. `"API_KEY=sk-ABCDE"` and `"F12345"`, produces the checked string `"API_KEY=sk-ABCDE F12345"`, which does not match a regex expecting the contiguous key, while the two edits — if their `old_string` anchors are adjacent in the actual file — will produce `API_KEY=sk-ABCDEF12345` contiguously once applied. A user-authored `block` rule such as the one hookify itself generates for `.env`/`API_KEY` cases [4](#0-3)  would therefore fail to block the MultiEdit call. No allowlist, workspace guard, or secondary content check exists in this path — `evaluate_rules` returns `{}` (allow) whenever no rule matches, and there's no PostToolUse re-verification against the actual final file bytes in the hookify plugin itself.

### Impact Explanation
This is a detection/enforcement bypass of a user-configured secret-blocking safety control (Claude Code bounty category: security control/guardrail bypass leading to secret disclosure/exfiltration). The impact is scoped to the hookify plugin's own `block` rules for the `MultiEdit` tool — it does not touch Claude Code's core permission system, sandboxing, or the security-guidance plugin's own `extract_content_from_input`, which has the identical join-based limitation [5](#0-4)  but that hook only runs at `PostToolUse` for advisory pattern-based warnings, not blocking, so its impact is lower (it doesn't prevent the write, only fails to warn afterward).

### Likelihood Explanation
Exploitation requires an attacker to get Claude to actually issue a `MultiEdit` call fragmented in this specific way — this is realistically achievable via prompt injection from untrusted repo content (e.g., a poisoned README/issue instructing the agent to "make these two small edits" that happen to compose a secret at adjacent positions in the target file), rather than the attacker directly crafting `tool_input` themselves. It requires the attacker to already have some ability to influence agent behavior (via injected instructions) and knowledge of the target secret/pattern being guarded, and for the two edits' insertion points to be adjacent in the file for the final content to be genuinely contiguous. This narrows likelihood somewhat but is a real, repeatable trigger given the exact code path.

### Recommendation
Do not evaluate `MultiEdit` content by naively space-joining `new_string` fragments. Instead:
1. Simulate the actual post-apply file content for `MultiEdit` (apply each `old_string`→`new_string` replacement against the current file content, in order) and run detection rules against that reconstructed content rather than a lossy join.
2. If full simulation isn't feasible, at minimum join edits with an empty string (or check both empty-join and space-join variants) and additionally check each edit's `new_string` individually, so fragmented literals are still caught when concatenated directly.
3. Consider adding a PostToolUse "verify" pass in hookify that re-checks block rules against the real file-on-disk content after a MultiEdit completes, and treats a match there as a policy violation to alert on even though the tool already ran.

    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
