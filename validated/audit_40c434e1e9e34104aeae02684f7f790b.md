### Title
OP_RETURN `data` output excluded from fee/weight calculation, transactions pay less than the requested fee rate and can fall below the minimum relay fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an optional `data` payload that is appended as an `OP_RETURN` output to `tx_outs`, but both calls to `calculate_weight_vbytes` only account for `payments` and the optional `change` output. The OP_RETURN output's bytes are never counted toward the transaction's vbytes, so `needed_fee` is under-computed and the effective fee rate of the signed transaction is lower than `fee_per_vbyte` — potentially below the minimum relay fee. This is the Serai analog of the reported "fees not deducted from the amount moved" bug class: value (fee) is not properly accounted for the utility (block space for OP_RETURN data) consumed.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed to `tx_outs` before the weight/fee calculation, but is not included in it:

- The `data` output is appended to `tx_outs` at networks/bitcoin/src/wallet/send.rs:194-202.
- `calculate_weight_vbytes` is then invoked as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204, and again for the change case at send.rs:225-226 — both calls reconstruct a `Transaction` using only `payments` (and optionally `change`); there is no parameter for the OP_RETURN output at send.rs:62-99.
- `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) and the minimum-relay-fee check (send.rs:211) are therefore computed over a transaction that is missing the OP_RETURN output.
- The change amount is computed as `input_sat - payment_sat - fee_with_change` (send.rs:228-230), so the *actual* fee paid (`inputs - outputs`) equals `fee_with_change` for a transaction whose real vsize is larger than `vbytes_with_change` by the OP_RETURN output's weight.

Consequences:
- The effective fee rate is strictly lower than the `fee_per_vbyte` requested, growing worse with larger `data` (up to 80 bytes of payload plus ~3+ bytes of script overhead per output).
- When `fee_per_vbyte` is at or near the minimum relay rate (the `TooLowFee` check at send.rs:211 divides by 1000 sat/kvB), the final transaction's actual fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE`, producing a validly-signed transaction that nodes will not relay.

### Impact Explanation
The threshold signing group produces transactions whose real fee rate does not match what was requested and validated. In the worst case (minimum fee rate + OP_RETURN data), the transaction is silently under the relay floor: it will be signed and emitted as a completion but never propagate, stalling the associated plan and forcing fee-bumping/re-planning. More generally, callers are undercharged for block space they consume — fees are not deducted for the data output, directly mirroring the "protocol offers a service without collecting the corresponding fee" class from the external report.

### Likelihood Explanation
`data` is a public parameter of `SignableTransaction::new` (send.rs:154), and the miscalculation is deterministic — it triggers on every call where `data.is_some()`. Whether it becomes consensus-relevant depends only on `fee_per_vbyte` being near the relay minimum, which the code explicitly permits (it only checks `needed_fee >= min_rate * underestimated_vbytes`). The current processor integration passes `None` for `data`, which lowers present-day reachability, but the wallet API itself is in-scope production code and the defect is unconditional within it.

### Recommendation
Include the OP_RETURN output in the weight calculation. Pass the constructed `tx_outs` (or an equivalent output list including the `data` output) into `calculate_weight_vbytes` rather than rebuilding the output list from `payments` alone, e.g. change the signature to take `&[TxOut]` and push the OP_RETURN `TxOut` before computing weight, so both the no-change and change paths account for it. Re-run the `TooLowFee` and `NotEnoughFunds` checks against the corrected vbytes.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs
// Given one input of value V, payments = [(addr, 1000)], change = Some(addr), and
// data = Some(vec![0; 80]):
//
// 1. calculate_weight_vbytes(tx_ins.len(), payments, Some(&change)) builds a tx with
//    outputs = [payment, change] only — the OP_RETURN output (~93 bytes of witness-excluded
//    data ≈ 372 weight units ≈ 93 vbytes) is omitted.
// 2. fee_with_change = fee_per_vbyte * vbytes_with_change, missing those ~93 vbytes.
// 3. change output value = input_sat - payment_sat - fee_with_change.
// 4. Actual fee = input_sat - (payment_sat + change) = fee_with_change,
//    but real vsize = vbytes_with_change + ~93.
//    effective_rate = fee_per_vbyte * vbytes_with_change / (vbytes_with_change + 93)
//                   < fee_per_vbyte.
//
// With fee_per_vbyte = 1 sat/vB and a small tx (~171 vB without data), the real tx is
// ~264 vB while paying ~171-264 sats — actual_rate ≈ 0.65 sat/vB < 1 sat/vB minimum,
// so the signed TX fails DEFAULT_MIN_RELAY_TX_FEE despite the TooLowFee check passing.
```
