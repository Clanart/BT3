## Analysis

The reported bug class (`totalSupply()` used as a divisor without a zero-check, causing a revert / panic) maps to a concrete division-by-zero path in the Kaia reward/staking module, which runs on every full node during state finalization.

### Title
Division-by-zero panic in `consolidatedNode.Split` during block-reward finalization when a proposer's CN stake and CL stake both round down to zero - (File: kaiax/staking/staking_info.go)

### Summary
`consolidatedNode.Split()` divides a reward amount by `totalAmount = CNStakingAmount + CLStakingAmount` without checking whether that sum is zero. Both components are computed as *integer* KAIA amounts (wei balance divided by `params.KAIA`, i.e. truncated/rounded down), so both can legitimately be `0` for a validator whose CN staking contract and CL pool each hold less than 1 KAIA. This function is invoked on the current block's proposer node unconditionally (no minimum-stake guard) inside the deferred-reward assembly path that runs at the end of every block.

### Finding Description
`consolidatedNode.Split` is defined as: [1](#0-0) 

`StakingAmount` and `CLStakingInfo.CLStakingAmount` are both derived by dividing the raw wei balance by `params.KAIA` and truncating to `uint64`: [2](#0-1) 

This means a staking contract or CL pool holding any amount less than 1 KAIA is recorded as staking amount `0`.

`Split` is called on the proposer's `consolidatedNode` entry regardless of whether that node satisfies `minStake`, inside `specWithProposerAndFundsFlex` (and analogously `specWithProposerAndFunds`), which is reached from `getDeferredRewardFullFlex`/`getDeferredRewardFullKore`/`getDeferredRewardFullLegacy` — functions executed for every block under the Kore/Prague/Osaka reward rules: [3](#0-2) 

If the block's proposer (identified by `config.Rewardbase`) is a consolidated node whose `StakingAmount` is `0` (CN staking contract balance < 1 KAIA) and whose `CLStakingInfo.CLStakingAmount` is also `0` (registered CL pool with balance < 1 KAIA), then `totalAmount` in `Split` becomes `big.NewInt(0)`, and `clAmount.Div(clAmount, totalAmount)` panics with a division-by-zero in Go's `math/big`, since unlike Solidity's `require`, there is no bounds check here.

Because `assignStakingRewards`/`assignStakingRewardsFlex` only include CNs whose combined stake exceeds `minStake`/threshold when computing `totalExcess` (so those call sites are safe), the unguarded call site is specifically the proposer-fund assignment path, which does not filter on `minStake` at all — it only checks `cn.RewardAddr == config.Rewardbase` and `cn.CLStakingInfo != nil`.

### Impact Explanation
A panic inside `FinalizeState`/`GetBlockReward` (called for every block, both during normal block production and by all full nodes replaying/validating the chain) would crash the node process or otherwise halt block processing, since Go panics from `math/big.Div` are not gracefully recovered in this call chain. This affects the "state transition and gas/burn accounting" / "staking and reward distribution" surface explicitly in scope, and a node-wide crash/consensus halt triggered merely by a specific but attacker-reachable staking/CL-registration state (rather than a malicious peer message) constitutes acceptance-of-invalid-state / state-divergence-class impact once some nodes crash while others may handle it differently (or all nodes crash identically, halting the chain).

### Likelihood Explanation
Reaching this requires: (1) a validator/proposer registered in the AddressBook with a CN staking contract balance under 1 KAIA, and (2) the same validator also registering (or having registered for it) a CL pool in `CLRegistry` whose balance is also under 1 KAIA. Both values are attacker/validator-controlled (KAIA amounts held in contracts the validator or a permissionless CL pool creator controls), and no privileged access is needed beyond normal AddressBook/CLRegistry registration and eventually being selected as a block proposer. I was not able to fully verify, within the available tool budget, whether validator/proposer selection (in `kaiax/valset`) enforces a non-zero or `minStake` requirement before a node can become the elected proposer for a block — if such a floor is strictly enforced there, likelihood is reduced to requiring only the CL side to be zero (a more easily attacker-controlled condition, since CL pools appear to be independently registrable with arbitrary initial balances). This point remains an open verification item.

### Recommendation
In `consolidatedNode.Split` (kaiax/staking/staking_info.go), guard against `totalAmount.Sign() == 0` and return `(amount, big.NewInt(0))` (or `(big.NewInt(0), big.NewInt(0))`) in that case, mirroring the recommended pattern from the referenced report (short-circuit before dividing by a value that can be zero).

### Proof of Concept
1. Register a validator CN in AddressBook whose staking contract balance is `< 1 KAIA` (e.g., 0).
2. Register a CL pool for the same validator's node ID in `CLRegistry` with a balance `< 1 KAIA` (e.g., 0), so that `StakingInfo.parseCallResult`/`parsePermissionlessCallResult` produces `StakingAmount = 0` and `CLStakingInfo.CLStakingAmount = 0` for that consolidated node (as shown in `kaiax/staking/impl/getter.go:286-300`).
3. Have that validator become the block proposer (`header.Rewardbase` matches this CN's `RewardAddr`).
4. When `FinalizeState`/`GetBlockReward` runs `getDeferredRewardFullKore`/`Flex` → `specWithProposerAndFunds(Flex)` → `cn.Split(proposer)`, `totalAmount = 0 + 0 = 0`, and `big.Int.Div(clAmount, totalAmount)` panics, crashing the node processing this block. [1](#0-0) [3](#0-2) [2](#0-1)

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
