### Title
Escrow credited by nominal order amount instead of actual received balance in Tron IntentGatewayV2 `placeOrder` — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` on the Tron/EVM-fork contract credits the shared escrow ledger `_orders[commitment][token]` using the nominal, fee-deducted order amount instead of the token balance actually received by the gateway. This is the exact "mint accounting credit without a matching balance increase" pattern from the referenced report (BunniHub minting vault shares without increasing pool balance): a bookkeeping value is incremented on the assumption that a transfer moved the full stated amount, without verifying it. The mainline EVM implementation of the same contract (`evm/src/apps/IntentGatewayV2.sol`) explicitly guards against this with a balance-diff check; the Tron variant omits it.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the non-predispatch escrow path is: [1](#0-0) 

```solidity
for (uint256 i; i < inputsLen;) {
    if (order.inputs[i].amount == 0) revert InvalidInput();
    address token = address(uint160(uint256(order.inputs[i].token)));
    if (token == address(0)) {
        if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
        msgValue -= order.inputs[i].amount;
    } else {
        IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
    }
    // Store reduced amount (after protocol fees) in escrow
    _orders[commitment][token] += reducedInputs[i].amount;
    unchecked { ++i; }
}
```

`safeTransferFrom` only guarantees the call succeeded and did not revert — it does **not** guarantee the gateway's balance increased by `order.inputs[i].amount`. For any fee-on-transfer / deflationary ERC-20, the actual balance increase is strictly less than the requested amount, yet `_orders[commitment][token]` is still credited with `reducedInputs[i].amount` (the full input minus only the protocol fee), which is larger than what the contract actually received.

The sibling, presumably-hardened implementation in `evm/src/apps/IntentGatewayV2.sol` explicitly closes this gap by measuring the balance delta instead of trusting the nominal transfer amount: [2](#0-1) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            uint256 balBefore = IERC20(token).balanceOf(address(this));
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
            order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
        }
        unchecked { ++i; }
    }
}
```

The Tron variant's `placeOrder` credits escrow ("mints" an entitlement) that is not backed by an equivalent real-token balance increase in the contract, exactly mirroring the BunniHub class of bug where shares/entitlements are created without the corresponding vault/pool balance rising. Because `IntentGatewayV2` is a **shared custody contract holding escrow for many concurrent orders in the same token**, this deficit is not isolated to the depositor who used the fee-on-transfer token — it silently reduces the pool of real tokens backing every other order's escrow denominated in that same token.

### Impact Explanation
`withdraw()` (invoked from `onAccept` on `RedeemEscrow`/`RefundEscrow`, or on-chain fill/cancel paths) pays out based on the `_orders[commitment][token]` ledger value, not on a per-order-isolated balance. Once the ledger total across orders for a token exceeds the contract's actual token balance:
- Legitimate users/solvers whose orders are settled later can have their `withdraw()` calls revert (insufficient contract balance) — loss/lock of escrowed funds for uninvolved orders.
- Depending on settlement ordering, an early claimant (solver or a colluding user cancelling/refunding first) can extract more real tokens than the pool actually holds, at the expense of other users' legitimate escrow — a fund-theft vector, not merely inconvenience.

This satisfies the required impact class: "stealing or loss of funds" / "logic attacks" through a corrupted accounting value (`_orders[commitment][token]`) that no longer represents actual custodied balance, in a public, unprivileged entrypoint (`placeOrder`) reachable by any user who selects a fee-on-transfer token as an order input.

### Likelihood Explanation
Likelihood is Medium: it requires the deployment to accept an arbitrary/attacker-influenced ERC-20 as an order input token (fee-on-transfer or otherwise balance-deflating on transfer). Whether this is reachable depends on whether the Tron deployment allows arbitrary caller-specified `order.inputs[i].token` values (which the code does — the token address comes directly from `order.inputs[i].token`, not from an allowlist visible in this function). No relayer, prover, or admin compromise is needed; the caller alone triggers the mismatch by placing an order.

### Recommendation
Port the balance-diff pattern from `evm/src/apps/IntentGatewayV2.sol` into the Tron variant: measure `balanceOf(address(this))` before and after each `safeTransferFrom` in the non-predispatch branch, and derive `reducedInputs[i].amount` (and the amount credited to `_orders[commitment][token]`) from the actual received delta rather than the nominal `order.inputs[i].amount`. Apply the same fix everywhere else in the Tron contract that credits escrow based on a stated amount rather than a measured balance delta (e.g., the fee-token escrow step further down in `placeOrder`).

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and a mock ERC-20 that burns 5% on every `transfer`/`transferFrom` (a standard fee-on-transfer mock).
2. User A places an order with `order.inputs[0] = {token: feeToken, amount: 1000}` and no predispatch calldata. `safeTransferFrom` moves only 950 tokens into the gateway (5% fee burned), but `_orders[commitment][feeToken]` is credited with `reducedInputs[0].amount` (≈1000 minus protocol fee), i.e. more than the 950 tokens actually held for this order.
3. User B places a normal order with the same `feeToken` as input, contributing real balance to the shared gateway balance.
4. Both orders are legitimately filled/settled. When `withdraw()` is called for User A's order, it succeeds and pays out the over-credited amount, drawing on tokens that belong to User B's escrow. When User B's order later attempts to settle via `withdraw()`, the transfer reverts due to insufficient gateway balance — locking/losing User B's funds — or, in an adversarial ordering, an attacker front-runs settlement to extract the extra 50 tokens that were never actually deposited.
5. Compare against `evm/src/apps/IntentGatewayV2.sol`, where the same sequence cannot occur because `order.inputs[i].amount` (and thus everything derived from it, including the escrow credit) is overwritten with the measured `balanceOf` delta, so the ledger can never exceed the real balance contributed.
