### Title
Permanent, unrevocable `safe.directory` trust exception allows silent code-execution after directory reuse - ([File: app/src/lib/git/config.ts])

### Summary
GitHub Desktop mirrors Git's `safe.directory` protection: when a repository's working directory is owned by a different user than the current process, Git refuses to operate on it and Desktop shows a "Trust Repository" prompt. Once the user clicks trust, Desktop calls `addSafeDirectory()`, which permanently appends the literal path string to the user's **global** `~/.gitconfig` `safe.directory` list. There is no corresponding function anywhere in the codebase to remove a path from this list — not when the repository is removed from Desktop (`missing-repository.tsx`'s `remove()` only calls `dispatcher.removeRepository`), not when it goes missing, and not on any timer/session boundary.

### Finding Description
`addSafeDirectory` in [1](#0-0)  unconditionally adds the path to the global config the moment the user clicks through the warning shown in `MissingRepository.onTrustDirectory` [2](#0-1)  or `AddExistingRepository.onTrustDirectory` [3](#0-2) .

The invariant Git's `safe.directory` mechanism is supposed to enforce is "this exact directory is currently owned by a user I trust." Desktop's implementation only checks the **path string**, not any binding to filesystem identity (inode, owner UID at time of grant, or content hash). Because there is no deregistration/expiry counterpart — exactly the missing symmetric guard described in the source report — once a path is trusted it stays trusted in the global gitconfig forever, even after:
- The user removes the repository from Desktop (`remove()` in `missing-repository.tsx` calls only `dispatcher.removeRepository`, never touching `safe.directory`).
- The directory is deleted and later repopulated (e.g., a shared machine, a re-imaged path, a container/VM path reused across sessions, or a path recreated by an installer/sync client) by a different, less-trusted owner.

The next time Desktop (or plain `git`) operates on that path, `getRepositoryType` will report `regular` instead of `unsafe`, and no prompt is shown again — Desktop treats the new, potentially attacker-controlled repository content as fully trusted, including anything that executes automatically as part of normal Git operations at that path (e.g. `core.hooksPath`/hooks, `.gitattributes` filters, submodule config) once it's owned safely enough to pass the check that Desktop itself no longer performs meaningfully.

### Impact Explanation
This breaks the confidentiality/integrity boundary the unsafe-directory warning exists to protect: an attacker who can get content placed at a path a victim previously trusted (shared multi-user boxes, CI/build agents that reuse workspace paths, restored backups, or path recycling after uninstall/reinstall of another tool) gains automatic execution of repository-controlled Git behaviors with no user interaction, because Desktop never re-verifies or revokes the earlier grant. This matches the "attacker controls a cloned/fetched repository ... result is code execution ... outside the repo" impact class.

### Likelihood Explanation
Exploitation requires a specific but realistic precondition: reuse of a previously-trusted absolute path by different repository content owned in a way that would otherwise trigger the unsafe-directory check. This is plausible in shared development environments, ephemeral CI containers with fixed workspace paths, and multi-user Windows/macOS/Linux systems, but does require some form of directory/path reuse, which lowers the standalone likelihood compared to a purely remote trigger. It does not require the excluded "local/physical access" of the *victim's* live session — it only requires the eventual repopulation of a path the victim already interacts with.

### Recommendation
Add a genuine deregistration path: when a repository is removed from Desktop, or when `getRepositoryType` is re-evaluated for a previously-unsafe path and ownership no longer matches what was trusted, remove the corresponding `safe.directory` entry (`git config --global --unset safe.directory <path>`). Additionally, avoid trusting by path string alone — consider re-prompting if the directory's owner/inode changes since the original grant, similar to how the report recommends binding a time-based invariant (`expiry >= now + cooldown`) instead of allowing an unconstrained write path.

### Proof of Concept
1. On a shared or reused-path system, clone/open a repository at `/shared/project`, trigger the "owned by another user" warning, and click "Trust Repository." Desktop calls `addSafeDirectory('/shared/project')`, permanently adding it to `~/.gitconfig`.
2. Remove the repository from Desktop (`Remove` in `MissingRepository`). Note the `safe.directory` entry is never cleaned up — verify via `git config --global --get-all safe.directory`.
3. Delete `/shared/project` and let a different, untrusted user/process recreate a Git repository at the same path (e.g. `git init` with malicious hooks/config, owned by that other user).
4. Re-open the path in Desktop. `getRepositoryType` returns `kind: 'regular'` (not `'unsafe'`) because the path is still globally allow-listed, so no trust prompt is shown, and Desktop/Git operate on the attacker-controlled repository as fully trusted. /**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)
}
