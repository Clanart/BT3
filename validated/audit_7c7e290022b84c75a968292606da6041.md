### Title
Payout transaction's `OP_RETURN` operator-attribution output is not covered by the required `SIGHASH_SINGLE|ANYONECANPAY` signature, letting anyone who observes a withdrawal signature falsely attribute a payout to an operator who never fronted it - (File: `core/src/builder/transaction/operator_reimburse.rs`, `core/src/operator.rs`, `core/src/verifier.rs`)

### Summary
`create_payout_txhandler` builds the payout transaction with three outputs: (1) the user's payout, (2) an anchor, (3) an `OP_RETURN` carrying the fronting operator's x-only pubkey, used later to attribute the payout for reimbursement [1](#0-0) . The user's signature that authorizes spending the withdrawal UTXO is expected/required to use `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`, as documented by the verification error message in `Operator::withdraw` [2](#0-1) . That sighash flag only commits to input 0 and the correspondingly-indexed output 0 (the user payout), leaving the anchor and, critically, the `OP_RETURN` operator-attribution output completely unauthenticated and freely malleable by any third party who obtains the signature.

### Finding Description
The binding that should hold is: `operator credited for a payout == operator that actually funded/broadcast that payout`. Because the `OP_RETURN` output is outside the commitment of `SIGHASH_SINGLE|ANYONECANPAY`, this binding is not enforced by the Bitcoin script/signature layer at all — it is enforced only by convention (whichever operator happens to construct and broadcast the transaction is expected to also stamp their own pubkey in `OP_RETURN`).

Any party in possession of a valid withdrawal signature (obtained off-chain, exactly as any operator would receive it in order to call `withdraw`, or observed once the first operator broadcasts/relays it) can construct their **own** payout transaction: same input (the withdrawal UTXO) and same output 0 (paying the user the same value, which is required to keep the signature valid), but a **different** `OP_RETURN` payload naming an arbitrary x-only pubkey — including that of a legitimate, uninvolved operator — as the fronting operator. Nothing in transaction validation ties the `OP_RETURN` content to the party who actually funded and broadcast the transaction.

Downstream, `update_finalized_payouts` in the verifier parses this unauthenticated `OP_RETURN` data and unconditionally records it as the attributed payer for that withdrawal, with no cross-check against who actually paid: [3](#0-2) . The named operator's own automated `PayoutCheckerTask` then picks up this DB-recorded attribution as an "unhandled payout" and automatically calls `handle_finalized_payout`, proceeding into the kickoff/reimbursement flow: [4](#0-3) . That flow ultimately produces a `reimburse_tx` that pays the full bridge amount to that operator's reimbursement address, without any check that this operator's own funds actually left their wallet to satisfy the withdrawal: [5](#0-4) .

### Impact Explanation
This breaks the "operator credited versus the party that paid" custody binding explicitly listed as a target class. The concrete consequence is BTC leaving via the reimburse path to an operator who never fronted the corresponding withdrawal, i.e., a reimbursement for a payout that operator never funded — a Critical-severity outcome per the impact taxonomy (an operator reimbursed for a payout it never funded / BTC leaving without a matching fronted withdrawal on the operator's side). Because the falsified attribution is driven purely by unauthenticated transaction data, no cooperation or privileged role is required from the attacker to trigger the mis-attribution — only from the (passive, unaware) named operator's own already-running automation, which naturally reacts to the on-chain data exactly as designed for legitimate payouts.

### Likelihood Explanation
Exploitation requires only: (1) obtaining a valid user withdrawal signature — the same signature every honest operator receives off-chain in order to call `withdraw`/RPCs, hence not secret to a single privileged party, and (2) broadcasting a competing raw Bitcoin transaction with modified non-committed outputs, funded from the attacker's own wallet since output 0 must remain identical. This is a plain, unprivileged capability (raw tx construction/broadcast), not requiring any verifier/operator/aggregator role, key compromise, or majority hashrate. The main constraint is that the attacker must actually front the withdrawal amount themselves to keep the signature valid — meaning this is more of a griefing/mis-attribution primitive than a self-enriching one unless the attacker also controls the falsely-credited operator identity, but the underlying binding violation and validation gap are real and exploitable, matching the requested bug class exactly.

### Recommendation
Require the withdrawal signature to use a sighash type that commits to all outputs (e.g., `SIGHASH_DEFAULT`/`SIGHASH_ALL`) rather than `SIGHASH_SINGLE|ANYONECANPAY`, or otherwise cryptographically bind the `OP_RETURN` operator-attribution output to the actual funding party (for example, requiring an additional operator signature over the whole transaction, or deriving attribution from something consensus-verifiable rather than free-form `OP_RETURN` data). At minimum, `update_finalized_payouts` and `handle_finalized_payout` should not trust `OP_RETURN` data as sole proof of who funded the payout without an accompanying binding signature from that operator.

### Proof of Concept
1. User signs a withdrawal payout intent using `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` over input 0 (withdrawal UTXO) and output 0 (their payout), as required by `Operator::withdraw` [6](#0-5) .
2. Attacker obtains this signature (it is routinely shared off-chain with operators / visible once relayed) and independently constructs a payout transaction with the same input and output 0, funding it from their own wallet, but sets the `OP_RETURN` output (uncommitted by the sighash) to an arbitrary, uninvolved operator's x-only pubkey per `create_payout_txhandler`'s output layout [7](#0-6) .
3. Attacker broadcasts and confirms this transaction instead of the legitimate operator's version.
4. `update_finalized_payouts` records the falsely-named operator as payer for that withdrawal [8](#0-7) .
5. The falsely-credited operator's own `PayoutCheckerTask` automatically detects this "unhandled payout" and drives it through kickoff and reimbursement [9](#0-8) , eventually producing a `reimburse_tx` paying the full bridge amount to that operator's address [10](#0-9) , even though that operator never funded the withdrawal.

pub fn create_reimburse_txhandler(
    move_txhandler: &TxHandler,
    round_txhandler: &TxHandler,
    kickoff_txhandler: &TxHandler,
    kickoff_idx: usize,
    paramset: &'static ProtocolParamset,
    operator_reimbursement_address: &bitcoin::Address,
) -> Result<TxHandler, BridgeError> {
    let builder = TxHandlerBuilder::new(TransactionType::Reimburse)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::Reimburse1,
            move_txhandler.get_spendable_output(UtxoVout::DepositInMove)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::Reimburse2,
            kickoff_txhandler.get_spendable_output(UtxoVout::ReimburseInKickoff)?,
            builder::script::SpendPath::ScriptSpend(0),
            DEFAULT_SEQUENCE,
        )
        .add_input(
            NormalSignatureKind::OperatorSighashDefault,
            round_txhandler.get_spendable_output(UtxoVout::ReimburseInRound(
                kickoff_idx,
                paramset.num_kickoffs_per_round,
            ))?,
            builder::script::SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        );

    Ok(builder
        .add_output(UnspentTxOut::from_partial(TxOut {
            value: move_txhandler
                .get_spendable_output(UtxoVout::DepositInMove)?
                .get_prevout()
                .value,
            script_pubkey: operator_reimbursement_address.script_pubkey(),
        }))
        .add_output(UnspentTxOut::from_partial(
            builder::transaction::anchor_output(paramset.anchor_amount()),
        ))
        .finalize())
}

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()

        let mut dbtx = self.db.begin_transaction().await?;
        let unhandled_payout = self

        if unhandled_payout.is_none() {

            unhandled_payout.expect("Must be Some");

            "Unhandled payout found for withdrawal {}, move_txid: {}",
            citrea_idx,
            move_to_vault_txid
        );

        let deposit_data = self

            .get_deposit_data_with_move_tx(Some(&mut dbtx), move_to_vault_txid)
            .await?;
        if deposit_data.is_none() {
            return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
        }

        let deposit_data = deposit_data.expect("Must be Some");

        let kickoff_txid = self
            .operator
            .handle_finalized_payout(
