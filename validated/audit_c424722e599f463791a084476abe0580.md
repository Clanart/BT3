### Title
Auction module's early-deadline (ED) anti-sniping filter is unconditionally bypassed by self-classified gasless transactions - (File: kaiax/auction/impl/builder.go)

### Summary
`AuctionModule.FilterTxs` drops any pending transaction that arrives after `curBlockTime - EDOffset` (the "early deadline"), a rule designed to stop last-moment transaction insertion around the auction's target transaction. However, any transaction that the gasless module classifies as a gasless bundle transaction (`IsBundleTx` → `IsModuleTx`) is unconditionally exempt from this filter, regardless of arrival time, because `g.IsModuleTx(tx)` only checks static ABI-selector shape of the calldata (approve/swap function signatures), not any authorization or freshness property. ### Finding Description
The early-deadline check is the protocol's specific defense against a searcher submitting a transaction at the very last moment before block assembly to snipe or interfere with the target transaction that a winning `Auctioneer` bid is anchored to. `FilterTxs` iterates each sender's pending list and truncates any transactions whose `tx.Time()` is after `now - EDOffset`, unless the transaction is the recognized auction target tx, or `a.isGaslessTx(tx)` returns true:

```go
now := time.Now()
deadline := now.Add(-edOffset)
for addr, list := range txs {
    for i, tx := range list {
        if tx.Time().After(deadline) && !a.isGaslessTx(tx) {
            ...
        }
    }
}
```
`isGaslessTx` simply calls into the registered gasless module's `IsBundleTx`, which delegates to `IsModuleTx` — a purely syntactic check of whether the transaction's calldata matches the gasless approve/swap function selectors. There is no check that the transaction is actually part of a legitimate, executable gasless flow at filter time (that validation happens elsewhere, in the tx pool's `GetCheckBalance`), and no timing/freshness constraint is applied to gasless-classified transactions at all.

Because the exemption is granted purely by calldata shape and not by any deadline-aware condition, a user can submit an ordinary transaction that is shaped as a gasless approve/swap call at any time — including in the last millisecond before block sealing — and it will never be excluded by the ED-offset filter, unlike every other transaction type competing for the same block. This is analogous to the reported Perennial issue in that a security check meant to gate *all* transactions from performing a certain state-affecting action (there: efficiency/liquidity-decreasing actions; here: near-deadline insertion) is bypassed by using a different, superficially unrelated code path (there: liquidation; here: gasless tx classification) that was never intended to carry this side effect.

### Impact Explanation
The ED-offset filter exists specifically to prevent last-instant transaction insertion that could interfere with auction target/bid ordering (front-running/back-running protection for the KIP-249 auction mechanism). A malicious actor can craft/route ordinary swap-shaped calls (recognized purely by selector) to reliably land in the block regardless of the configured `EDOffset`, undermining the auction's timing guarantees and potentially allowing sniping or reordering attacks against auction-target transactions — a fee/auction-settlement-integrity issue reachable by any public-RPC transaction sender, with no special privilege required.

### Likelihood Explanation
Likelihood is high for any attacker capable of constructing calldata that matches the gasless module's approve/swap selector signatures (this is public, well-documented ABI per KIP-247) while targeting an unrelated recipient/token pair or one they control. No coordination with the `Auctioneer`, validators, or gasless swap router state is strictly required to trigger the bypass — only to be classified as `IsModuleTx`==true by decoding of the target signature; deeper business-logic checks (balance/allowance/router quote) are enforced later by the tx pool, not by `FilterTxs`. This makes the bypass trivially reachable from a single submitted transaction.

### Recommendation
Do not grant an unconditional deadline exemption based solely on syntactic gasless-tx classification. Either:
1. Apply the ED-offset deadline check to gasless-classified transactions as well (remove the blanket exemption), or
2. Restrict the exemption to transactions that have already been verified as executable gasless bundle transactions (i.e., reuse the same `VerifyExecutable`/`GetCheckBalance` validation used by the tx pool) rather than the bare selector-matching `IsModuleTx`/`IsBundleTx` check, so that the exemption cannot be obtained by an arbitrary transaction merely shaped like a gasless call.

### Proof of Concept
1. Configure a Kaia CN with the auction module enabled and `auction.ed-offset` set to its default (200ms).
2. An attacker crafts a transaction whose calldata matches the `GaslessSwapRouter` swap-function selector (per KIP-247/`decodeSwapTx`), targeting parameters that will pass the module's static shape recognition (`IsModuleTx`/`IsSwapTx`) — this does not require the swap to actually be economically viable at build time since `FilterTxs` performs no balance/allowance/quote validation, only `IsBundleTx`. [3](#0-2) 
3. The attacker broadcasts this transaction milliseconds before the anticipated block-sealing time, well after `now - EDOffset`.
4. `AuctionModule.FilterTxs` evaluates `tx.Time().After(deadline) && !a.isGaslessTx(tx)`; since `isGaslessTx(tx)` returns true, the `&&` short-circuits false and the transaction is retained in the sender's list regardless of its late timestamp. [4](#0-3) 
5. Meanwhile, a legitimate late-submitted non-gasless transaction from another sender at the same timestamp is truncated/dropped by the same filter, demonstrating the asymmetric bypass available to any transaction shaped as a gasless call.
