### Title
Solver can bypass the protocol's surplus-fee share on `IntentGateway` same-chain fills by front-running/self-dealing a dust partial fill - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
The Foundation Protocol bug lets a primary seller launder a sale into "secondary" classification (5% fee) instead of "primary" (15%) by executing a throwaway/self-dealing transaction that flips the classification flag ("has this been sold before?") before the real, valuable sale happens. `IntentGateway`'s same-chain fill path has the identical broken invariant: whether a fill is treated as "fresh" (subject to the protocol's `surplusShareBps` cut on any solver overpayment) is decided purely by a public, permissionless, per-output-token boolean state (`_partialFills[commitment][outputToken] == 0`), which anyone can flip with a dust-sized call before the real fill lands.

### Finding Description
In `_fillSameChain` [1](#0-0) , the surplus/dust split (which sends part of a solver's overpayment to the protocol via `surplusShareBps`) is only applied when:

```solidity
if (alreadyFilled == 0 && solverAmount > totalRequired) {
    // dust computed and split between beneficiary and protocol
} else {
    fillAmount = solverAmount > remaining ? remaining : solverAmount; // no dust captured
}
```

`alreadyFilled` comes from `_partialFills[commitment][outputToken]`, a value that any address can set by calling `fillOrder` with a trivial partial amount (e.g., 1 wei) on that output token — `fillOrder` has no `msg.sender` restriction tying it to a "selected" or "authorized" solver, and partial fills are explicitly supported and public. The docs even confirm: "Surplus only applies on the first fill of each output token pair." [2](#0-1) 

Once `alreadyFilled != 0`, any subsequent fill — including one where the solver would otherwise have overpaid and triggered the protocol's surplus cut — only transfers `fillAmount` (capped at `remaining`); the "solverAmount" a filler supplies above `remaining` is neither collected nor split with the protocol. The real filler (which can be the same actor operating a second throwaway address, exactly mirroring the report's "transfer to a different wallet" trick) simply:
1. Calls `fillOrder` for 1 wei of the target output token from a disposable address, setting `_partialFills[commitment][outputToken] = 1`.
2. Immediately calls `fillOrder` again as the real solver with a fill that would otherwise have been an "overpay" (surplus-triggering) fill.

Because `alreadyFilled` is now non-zero, the surplus-computation branch is skipped entirely for that output token, and the protocol's `surplusShareBps` cut — which exists specifically to monetize solver overpayments in the intent auction model — is never charged, exactly like avoiding the "primary sale" fee tier by first performing a low-value/self dealing transaction to change the on-chain classification flag.

### Impact Explanation
This breaks the "false state acceptance / logic attack" bounty class: the protocol's designed fee-capture path (surplus share on solver overpayment) is bypassed by manipulating a classification flag that any unprivileged caller controls, at negligible cost (1 wei + gas). This is a direct, repeatable loss of protocol fee revenue on every intent order where a solver would otherwise pay a surplus, using only public entrypoints with no relayer, prover, or admin involvement.

### Likelihood Explanation
High. `fillOrder` is a public entrypoint, requires no special permission from either the order beneficiary or the protocol, and the dust partial-fill transaction costs a single wei plus gas. Any economically-motivated solver (or a solver operating two addresses) can perform this two-step pattern on every order that would otherwise generate a surplus for the protocol, making this a systematic revenue-diversion path rather than an edge case.

### Recommendation
Do not gate the surplus/dust computation on whether *any* prior partial fill exists. Instead:
- Track and always apply the surplus split whenever `solverAmount` (or the aggregate solver contribution across all fills for that output token) exceeds `totalRequired`, regardless of `alreadyFilled` state, or
- Restrict `fillOrder`'s ability to write to `_partialFills` to prevent trivial dust fills from third parties, e.g., require a minimum fill size relative to `totalRequired`, or accumulate solverAmount overpayment across all fills of the same commitment/output token and compute the protocol's dust share on the cumulative total at full-fill time rather than only on the "first" fill.

### Proof of Concept
1. User places a same-chain order via `placeOrder` with `output.assets[0]` requiring `1000 DAI`, `surplusShareBps = 5000` (50%), no calldata.
2. Attacker (or colluding address #1) calls `fillOrder` supplying `solverAmount = 1` wei of DAI as `options.outputs[0].amount`, which is `<= remaining`, so `_partialFills[commitment][DAI] = 1` and no `isFullyFilled` (`PartialFill` emitted). [3](#0-2) 
3. The real solver (address #2, or the same solver) calls `fillOrder` again for the remaining `999.999999...` DAI while actually being willing/able to pay `1050 DAI` (i.e., a genuine 50 DAI overpay/surplus bid). Because `alreadyFilled = 1 != 0`, the code takes the `else` branch: `fillAmount = min(solverAmount, remaining) = remaining`. The protocol's `surplusShareBps` share of the intended 50 DAI overpay is never computed or collected — no `DustCollected` event fires, and the solver only ever needs to actually transfer `remaining`, keeping the entire intended surplus for itself instead of splitting it with the protocol as the un-gamed path would have required. [4](#0-3) 

This exact two-step dust-then-real-fill pattern generalizes to every same-chain order with a non-zero `surplusShareBps`, letting solvers systematically avoid paying the protocol's designed cut of overpayment/surplus — the direct analog of the Foundation primary/secondary fee-classification bypass.
