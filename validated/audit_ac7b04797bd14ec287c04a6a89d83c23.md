### Title
Nil Pointer Dereference in EIP-7702 SetCodeTx Handling via Empty `To` Field - (File: x/evm/types/ethtx/set_code_tx.go)

### Summary
`SetCodeTx.Validate()` treats the `To` field as optional (only validates it `if tx.To != ""`), but `SetCodeTx.AsEthereumData()` unconditionally dereferences `*tx.GetTo()`, which returns `nil` when `To == ""`. Any transaction sender who submits an EIP-7702 (type-4) `MsgEVMTransaction` with an empty `to` field passes `ValidateBasic`/ante-level validation and then crashes the node with a nil pointer dereference the moment the transaction is converted to a Go-Ethereum transaction object.

### Finding Description
`SetCodeTx` is the wrapper type used to represent EIP-7702 transactions inside `MsgEVMTransaction.Data` [1](#0-0) . Its `GetTo()` accessor explicitly returns `nil` for an empty `To` string [2](#0-1) , and its `Validate()` method only checks/validates `To` when it is non-empty — there is no rejection of an empty `To` for this tx type [3](#0-2) . However, `AsEthereumData()` unconditionally dereferences the pointer returned by `GetTo()`: `To: *tx.GetTo()` [4](#0-3) . When `To == ""`, `GetTo()` returns `nil`, and the dereference panics.

This code path is reachable purely through consensus-level transaction processing, not through go-ethereum's own RLP decoder (which requires `To` for type-4 txs and would reject an empty `To` at decode time). The sei message wrapper is a separate Protobuf-encoded structure (`MsgEVMTransaction` → `ethtx.TxData` `Any` → `SetCodeTx`), so a transaction can be crafted directly as a Cosmos SDK transaction carrying a `SetCodeTx` payload with `To == ""`, bypassing go-ethereum's RLP-level guarantee. `AsEthereumData()` is invoked via `AsTransaction()`, which is called throughout the ante pipeline (`EvmStatelessChecks`, `BasicDecorator.AnteHandle`, `EVMSigVerifyDecorator.AnteHandle`, `EVMFeeCheckDecorator.AnteHandle`) [5](#0-4) [6](#0-5) [7](#0-6) , meaning the panic fires during both `CheckTx` (mempool admission) and `DeliverTx` (block execution) for any node running default configuration.

Note: the identical bug pattern also exists in the parallel `giga/deps/xevm/types/ethtx/set_code_tx.go` copy used by the giga EVM path, so both execution paths are affected.

### Impact Explanation
A single unprivileged account can submit an EIP-7702 transaction (`MsgEVMTransaction` wrapping `ethtx.SetCodeTx`) with an empty `to` field to any full node's RPC or via `BroadcastTx`. This causes an immediate Go panic (nil pointer dereference) in the ante handler, which runs for every node that processes the tx in `CheckTx` (mempool) and, if it slips through and reaches consensus, in `DeliverTx` as well. Because `EvmCheckTxAnte`/`EvmStatelessChecks` call `msg.AsTransaction()` before any panic-recovery wrapper specific to this failure mode, a node that does not have a top-level recover for this particular panic during `CheckTx`/mempool gossip processing can crash, producing a denial-of-service against public RPC/mempool nodes — directly matching the "crash of default-configuration RPC nodes" acceptance criterion.

### Likelihood Explanation
High likelihood of triggering: the crafted transaction requires only a validly-signed `MsgEVMTransaction` (any account with a valid EVM key can produce this; the `To` field is not covered by the ECDSA signature integrity in a way that would block an attacker from constructing the payload themselves via `ethtx.NewSetCodeTx` bypass or direct protobuf construction) and passes both `ValidateBasic()` (which does not special-case `To` for `SetCodeTx`) [8](#0-7)  and `Validate()` [9](#0-8) . No special privileges, precompile access, or governance action is required — it is reachable from ordinary `eth_sendRawTransaction`-adjacent flows or direct Cosmos tx submission.

### Recommendation
Add an explicit `To == ""` rejection in `SetCodeTx.Validate()` (EIP-7702 transactions must always have a non-nil `To` per spec — contract creation is disallowed for type-4 txs), returning an error such as "to address cannot be empty for SetCodeTx transactions." Apply the same fix to both `x/evm/types/ethtx/set_code_tx.go` and `giga/deps/xevm/types/ethtx/set_code_tx.go`. As defense-in-depth, also guard `AsEthereumData()` to avoid dereferencing a nil pointer even if validation is bypassed elsewhere.

### Proof of Concept
1. Construct an `ethtx.SetCodeTx` with `To: ""`, valid `GasTipCap`, `GasFeeCap`, non-empty `AuthList`, and valid `V/R/S` signature bytes (satisfying every check in `Validate()`).
2. Wrap it via `types.NewMsgEVMTransaction(setCodeTx)` into a `MsgEVMTransaction`, build and encode a Cosmos SDK transaction carrying that single message.
3. Submit via `BroadcastTx`/`BroadcastTxCommit` (or the corresponding gRPC/CLI path) to a full node.
4. `EvmStatelessChecks`/`EvmCheckTxAnte` (or `BasicDecorator.AnteHandle`) call `msg.AsTransaction()` → `UnpackTxData(msg.Data)` succeeds and passes `Validate()`, then `ethtypes.NewTx(txData.AsEthereumData())` executes `AsEthereumData()`, which evaluates `*tx.GetTo()` on `To == ""`, yielding `*(nil)` and panicking with a nil pointer dereference, crashing/recovering-with-error the node's tx-processing goroutine for that request.

func (tx SetCodeTx) Validate() error {
	if tx.GasTipCap == nil {
		return errors.New("gas tip cap cannot nil")
	}

	if tx.GasFeeCap == nil {
		return errors.New("gas fee cap cannot nil")
	}

	if tx.GasTipCap.IsNegative() {
		return fmt.Errorf("gas tip cap cannot be negative %s", tx.GasTipCap)
	}

	if tx.GasFeeCap.IsNegative() {
		return fmt.Errorf("gas fee cap cannot be negative %s", tx.GasFeeCap)
	}

	if tx.GasFeeCap.LT(*tx.GasTipCap) {
		return fmt.Errorf("max priority fee per gas higher than max fee per gas (%s > %s)",
			tx.GasTipCap, tx.GasFeeCap,
		)
	}

	if !IsValidInt256(tx.Fee()) {
		return errors.New("fee out of bound")
	}

	amount := tx.GetValue()
	// Amount can be 0
	if amount != nil && amount.Sign() == -1 {
		return fmt.Errorf("amount cannot be negative %s", amount)
	}

	if tx.To != "" {
		if err := ValidateAddress(tx.To); err != nil {
			return errors.New("invalid to address")
		}
	}
