Based on the investigation, the concrete local analog to "missing guard rails" from the CI report is a genuine cross-check omission in Hyperbridge's own timeout/response accounting on the EVM host contract — not a CI/workflow issue at all, but a real double-payment path in GET request fee handling.

### Title
GET request fee can be paid twice (once on response delivery, once on timeout) because `dispatchIncoming` never clears `_requestCommitments` - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming(GetResponse ...)` pays the relayer fee for a `GetRequest` but leaves the request's fee-metadata entry in `_requestCommitments` untouched. [1](#0-0) 
Separately, `EvmHost.dispatchTimeOut(GetRequestTimeout ...)` refunds the same fee to the original sender using that same untouched `_requestCommitments[commitment]` entry, deleting it only when it processes the timeout. [2](#0-1) 
No check exists in the timeout path that a response receipt (`_responseReceipts[commitment]`) was already stored for this commitment before refunding the fee and deleting the commitment.

### Finding Description
The two entry points that consume the same `_requestCommitments[commitment]` fee record are not mutually exclusive:

- `dispatchIncoming` (GET response path) reads `_requestCommitments[commitment].fee`, pays it to the delivering `relayer`, but never calls `delete _requestCommitments[commitment]`. [3](#0-2) 
- `dispatchTimeOut` (GET timeout path) independently deletes `_requestCommitments[commitment]` for "replay protection" and, on a successful module callback, refunds `meta.fee` again to `meta.sender`. [2](#0-1) 

Contrast this with the Substrate implementation of the same protocol, `modules/ismp/core/src/handlers/timeout.rs`, which explicitly guards against this exact scenario for GET requests by checking `host.response_receipt(&response).is_some()` and rejecting the timeout with `GetResponseAlreadyReceived` before any commitment is touched. [4](#0-3) 

The EVM host has no equivalent check. If a relayer delivers a valid `GetResponse` (fee paid out via `dispatchIncoming`) and the commitment record is never cleared, a second party (or the same relayer) can later submit a `GetRequestTimeout` for the identical commitment once the timeout window elapses, and `EvmHost` will refund the fee a second time before finally deleting the commitment.

### Impact Explanation
This is a double-settlement/duplicate-claim of protocol fee funds: the same `feeToken` balance backing one `GetRequest` is paid out twice — once as a relayer reward and once as a sender refund — draining the fee reserve. This matches the bounty's "double-claim/double-settlement" and "funds moved more than once" impact category, executed entirely through public, unprivileged entrypoints (`dispatchIncoming`/`dispatchTimeOut`, both gated only by `restrict(_hostParams.handler)`, i.e. permissionless once a valid response/timeout message is relayed).

### Likelihood Explanation
Likelihood depends on whether the upstream `Handler` contract (which calls into `dispatchTimeOut`) independently checks `_responseReceipts` before permitting a timeout submission for an already-responded-to request — that check, if present, would live in the handler contract that I was not able to fully inspect in this pass. Based purely on `EvmHost.sol`'s own state machine, no such guard exists at the host layer, so the invariant relies entirely on an external contract enforcing it correctly.

### Recommendation
- In `dispatchIncoming` (GetResponse), delete `_requestCommitments[commitment]` once the fee is paid out, mirroring how `dispatchTimeOut` clears it.
- In `dispatchTimeOut` (GetRequestTimeout), add an explicit check that `_responseReceipts[commitment]` is unset before proceeding, matching the Substrate pallet's `GetResponseAlreadyReceived` guard in `modules/ismp/core/src/handlers/timeout.rs`.

### Proof of Concept
1. Dispatch a `GetRequest` with a non-zero fee; `_requestCommitments[commitment]` stores the fee metadata.
2. Relayer submits a valid `GetResponse` before the timeout elapses → `dispatchIncoming` pays `fee` to the relayer; `_requestCommitments[commitment]` remains in storage (only `_responseReceipts` is set). [1](#0-0) 
3. After `timeout_timestamp` elapses, submit a `GetRequestTimeout` for the same commitment → `dispatchTimeOut` deletes `_requestCommitments[commitment]` and refunds `meta.fee` again to `meta.sender`. [2](#0-1) 
4. Net effect: the same fee amount is paid out twice from the host's fee reserve for a single `GetRequest`.

**Caveat:** I could not verify within this pass whether the separate `Handler` contract (which invokes `dispatchTimeOut`) independently blocks timeout submission for requests with an existing response receipt — if such a check exists there, the vulnerability would be mitigated at that layer instead. I recommend a Devin session to inspect the handler contracts (`evm/src/handlers/`) to confirm end-to-end exploitability before treating this as fully proven.

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
```

    function dispatchTimeOut(
        GetRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onGetTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit GetRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```
