## Analog Vulnerability Found

### Title
CLVM "Solver" string injection via unescaped `disassemble()` output in offer completion - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.to_valid_spend()` builds a CLVM `Solver` dictionary for CAT/CR-CAT/VC-layer puzzle drivers by string-concatenating hex-encoded coin data together with `disassemble()`-rendered CLVM source of sibling coins' solutions, then hands that concatenated string to `Solver`/`PuzzleInfo`, whose `decode_info_value()` re-parses it with `assemble()` (the CLVM source parser). This is structurally the same bug class as the XWiki advisory: attacker-influenced content is embedded as a substring inside a syntactic context (there, wiki/Velocity markup; here, CLVM assemble source) without confirming the embedded content cannot break out of its intended grouping, and the resulting string is fed back into a parser/interpreter that a privileged downstream consumer trusts.

### Finding Description
In `Offer.to_valid_spend()`, for every asset leg the code manually builds `siblings`, `sibling_spends`, `sibling_puzzles`, and `sibling_solutions` as raw Python strings: [1](#0-0) 

`sibling_solutions` in particular concatenates `disassemble(coin_to_solution_dict[sibling_coin])` — a CLVM textual disassembly of a `Program` built from `NotarizedPayment`/memo data that originates from the **other party's offer file** (fully attacker-controlled input, since anyone can craft and distribute an offer): [2](#0-1) 

These strings are passed as values inside a `Solver({...})` dict: [3](#0-2) 

Every access of a `Solver`/`PuzzleInfo` string value calls `decode_info_value()`, which calls `assemble(value)` — the `clvm_tools` CLVM source parser — on the exact string that was built by concatenation: [4](#0-3) 

If `disassemble()` of an attacker-crafted atom/program does not perfectly quote/escape structural characters (unbalanced `(`/`)`, embedded `"`), the surrounding `"("..."0x..."..." )"` string that `to_valid_spend()` builds can be broken out of, letting the attacker's sibling-coin data inject extra tokens into the `siblings`/`sibling_solutions` fields that are re-parsed by `assemble()` when the `Solver` is consumed. This mirrors the XWiki root cause: user-controlled content assumed to be safely embeddable inside a fixed syntax template is concatenated without a hard escaping/serialization boundary, and a second-stage parser interprets the result as code/structure rather than data.

The consumer of this `Solver` data includes `CROuterPuzzle.solve()` for credential-restricted CATs, which pulls `solver["coin"]`, `vc_authorizations`, and `authorized_providers` to decide whether a CR-CAT spend is authorized by a valid VC/proof-checker: [5](#0-4) 

An injected/forged field here (e.g., a smuggled `siblings`/`sibling_spends` value, or corrupting adjacent solver keys via `**solver.info` merge) reaches CLVM-execution-authoritative logic for CR-CAT authorization on the taker's own machine while building the completion spend.

### Impact Explanation
If exploitable, a malicious offer-maker (or a maker/taker collaborating maliciously) could corrupt or spoof the `Solver` fields consumed by CR-CAT/VC puzzle drivers on the taker's wallet, potentially causing the taker to construct/sign a spend with mismatched or attacker-chosen sibling/authorization data — undermining CR-CAT provider-restriction guarantees or corrupting offer completion in a way that leads to unintended coin movement or asset-identity confusion. This falls under "offer settlement theft" / "forged asset identity" categories.

### Likelihood Explanation
Exploitability hinges entirely on whether `clvm_tools.binutils.disassemble()` can be made, via a crafted `Program`/memo inside an offer, to emit text containing an unescaped `)`  or quote that breaks out of the hand-built string template in `to_valid_spend()`. This has not been independently confirmed against the current `disassemble()` implementation (which is a third-party `clvm_tools` dependency, not in this repo), so likelihood is uncertain without testing actual `disassemble()` escaping behavior on adversarial atoms. This weakens confidence in exploitability compared to the certainty of the pattern match.

### Recommendation
- Stop building `Solver`/CLVM-source values via raw string concatenation of `disassemble()` output and hex digests; construct `Program`/`Solver` values directly from typed objects (bytes, `Program` structures) and only serialize with a format whose round-trip safety is proven (e.g., pass `Program` objects directly into `Solver.info` instead of `disassemble()`d strings wherever the consuming driver can accept objects).
- If string embedding must remain, verify/enforce that `disassemble()` output can never contain a top-level unbalanced `(`/`)`/quote when concatenated inside `to_valid_spend()`'s hand-rolled `"(" + ... + ")"` templates, or add explicit balancing/escaping validation before concatenation.
- Add adversarial-input tests (crafted memos/atoms in an offer's `NotarizedPayment`) to `chia/_tests/wallet/cat_wallet/test_offer_lifecycle.py` asserting the assembled `Solver` structure matches expectations regardless of attacker-controlled sibling coin content.

### Proof of Concept
Not independently demonstrated — building a concrete PoC requires confirming whether `clvm_tools.binutils.disassemble()` on an attacker-chosen `Program` (embedded via a crafted offer's `NotarizedPayment`/memo) can emit unbalanced parentheses/quotes that escape the string template in [1](#0-0) . This is flagged as a structural analog to the XWiki string-injection-into-parser bug class rather than a confirmed exploit chain.
