### Title
`ThresholdKeys::read` deserializes and accepts semantically inconsistent key material without validation, bricking all future signing for that multisig - ([File: crypto/dkg/src/lib.rs](https://github.com/serai-dex/serai/blob/main/crypto/dkg/src/lib.rs))

### Summary
Analogous to the `upgrade_storage` report, `ThresholdKeys::read` reconstructs contract-equivalent "stored state" (a validator's threshold key set) from untrusted bytes and validates only the *shape* of the data — parameter bounds, share count, canonical encodings — but never validates the *semantic consistency* of the data: that `secret_share * G == verification_shares[i]`, that the verification shares are consistent with a single public polynomial, or that they are non-identity. A malformed serialized `ThresholdKeys` is accepted, and every subsequent signing session deterministically fails at `complete()`, permanently DoSing the multisig exactly like a malformed storage cell bricks `load_data`.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation coefficients, `secret_share`, and `verification_shares`, then calls `ThresholdKeys::new`, which only checks `verification_shares.len() == n`, `participant <= n`, `t <= n`, and `t == n` for `Constant` interpolation [1](#0-0) . It never checks that the deserialized `secret_share` corresponds to `verification_shares[params.i()]`, nor that the verification shares are mutually consistent. It also uses `Ciphersuite::read_G`, which accepts the identity point [2](#0-1) , unlike `Curve::read_G`, which rejects identity [3](#0-2) .

The downstream effect is acknowledged in the code itself: `AlgorithmSignatureMachine::complete` notes "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" [4](#0-3) . With an inconsistent `secret_share`, `sign()` still produces a well-formed `SignatureShare`, but `verify_share` — which checks the share against the interpolated `verification_shares` [5](#0-4)  — deterministically fails, so `complete()` always returns `InvalidShare`/`InternalError`. The keys deserialize "successfully" yet can never sign.

This is reachable wherever serialized `ThresholdKeys` are consumed from data an unprivileged party can influence (the scan rules bless `ThresholdKeys::read` as an untrusted-bytes entry point); e.g., `GeneratedKeysDb::read_keys` feeds stored bytes straight into `ThresholdKeys::read` and `unwrap`s [6](#0-5) . Any accept-without-verify path for these bytes produces state that is syntactically valid but semantically unusable — the same defect class as storing an unvalidated data cell.

### Impact Explanation
Persistent denial of service of a threshold signing set: once a semantically invalid `ThresholdKeys` is accepted, every signing attempt for that key produces shares that fail batch verification, so the multisig can never complete a signature. Because `read` returns `Ok`, the corruption is silent and non-recoverable — mirroring the report's "all user actions throw an exception". This matches Medium DoS severity.

### Likelihood Explanation
Exploitation requires malformed `ThresholdKeys` bytes reaching `ThresholdKeys::read`. In Serai's production flow this is local-DB/integrator-supplied data rather than a network-controlled field, so the practical likelihood is lower than the report's admin-triggered case; however the missing validation is unconditional and the failure mode is deterministic once triggered (corrupted backup/restore, downgraded serialization format, or any caller passing externally sourced bytes).

### Recommendation
In `ThresholdKeys::new` (or `read`), verify consistency: reject identity verification shares and check `C::generator() * secret_share == verification_shares[params.i()] * interpolation_factor(i, 1..=t)` — or at minimum that `group_key` recomputation and `secret_share` agree under the declared interpolation. Fail deserialization instead of constructing a permanently broken key set.

### Proof of Concept
Serialize a valid `ThresholdKeys`, then corrupt the `secret_share` field (e.g., add one) or replace a `verification_shares` entry with the identity point encoding. `ThresholdKeys::read` returns `Ok` [7](#0-6) . Construct an `AlgorithmSignMachine`/`AlgorithmMachine` with these keys, complete a `preprocess`, and `sign` with `t` participants: `view()` and `sign()` succeed, but `complete()` fails every time — either `InvalidShare(our_i)` from `verify_share` [8](#0-7)  or the `InternalError` reserved for "deserialize a semantically invalid FrostKeys" [9](#0-8) .

Caveat: the strongest in-scope reachability for untrusted bytes into `ThresholdKeys::read` is via stored/restored key material rather than a live peer message; I could not fully confirm a remote-party-controlled path delivering raw `ThresholdKeys` bytes in this snapshot.
