## Answer

The claimed vulnerability is real and matches the "honest operator permanently unable to be reimbursed" impact category. The core issue is that the OP_RETURN output carrying the operator attribution in the payout transaction is **outside** the commitment scope of the only signature (the user's) that authorizes the payout transaction.

### Title
Payout tx operator-attribution OP_RETURN is outside SIGHASH_SINGLE|ANYONECANPAY scope, enabling attribution hijack via RBF replacement - (core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` builds the payout transaction with output 0 (user payout, signature-committed), output 1 (anchor), and output 2 (OP_RETURN with the funding operator's x-only pubkey), but the only signature present — the user's `SinglePlusAnyoneCanPay` signature over input 0 — commits only to input 0 and output 0. Outputs 1 and 2, including the operator-attribution OP_RETURN, are completely unconstrained, so anyone can rebroadcast a fee-bumped, RBF-replacing version of the transaction that keeps input 0/output 0 but swaps in their own OP_RETURN pubkey, hijacking the on-chain attribution that `Verifier::is_kickoff_malicious` later uses to gate reimbursement.

### Finding Description
The binding claimed to hold is:
```
recorded_operator_xonly_pk_for_withdrawal_index == operator_xonly_pk_passed_by_true_funding_operator_into_create_payout_txhandler
```

`Operator::withdraw` builds the payout tx via `create_payout_txhandler(input_utxo, output_txout, self.signer.xonly_public_key, in_signature, ...)`, which lays out outputs as `[0: user payout, 1: anchor, 2: OP_RETURN(operator_xonly_pk)]` [1](#0-0) , and signs only input 0 keypath with the user's off-chain signature: `payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` followed by `SECP.verify_schnorr(...)`, with the error text explicitly stating the expected sighash type is `SinglePlusAnyoneCanPay` [2](#0-1) .

Per BIP341 sighash encoding (implemented identically in this repo), for `Single+AnyoneCanPay` only the specific input's outpoint/value/scriptPubKey/sequence and the output at the same index as the input (index 0) are hashed; all *other* outputs are never included in the digest computation for this sighash type [3](#0-2) . This means outputs 1 (anchor) and 2 (OP_RETURN operator pubkey) are entirely outside signature scope and can be freely rearranged, replaced, or dropped by anyone while the signature remains valid.

The payout tx's input signals RBF opt-in (`DEFAULT_SEQUENCE = Sequence::ENABLE_RBF_NO_LOCKTIME`) [4](#0-3) , and `Operator::withdraw` broadcasts it via `fund_raw_transaction` (which itself already inserts a change output at a fixed position, shifting anchor/OP_RETURN order) [5](#0-4) . An attacker observing this unconfirmed transaction in the mempool can reuse the exact same witness for input 0 (public data) in an alternative transaction that: keeps input 0 and output 0 byte-identical, adds their own funding input(s) to pay a higher fee, and substitutes an OP_RETURN containing their own chosen x-only pubkey — then gets this replacement mined via standard BIP125 RBF.

Once mined, `Verifier::update_finalized_payouts` locates the OP_RETURN by content-predicate, not fixed index (`get_first_op_return_output` searches `tx.output.iter().find(|out| out.script_pubkey.is_op_return())` [6](#0-5) ), extracts the attacker's bytes via `parse_op_return_data`, and records this as the payer `operator_xonly_pk` for the withdrawal in the database [7](#0-6) .

Later, when the true funding operator submits its kickoff to claim reimbursement, `Verifier::is_kickoff_malicious` compares the DB-recorded pubkey against `kickoff_data.operator_xonly_pk`:
```rust
if operator_xonly_pk != kickoff_data.operator_xonly_pk {
    tracing::warn!("Operator xonly pk for the payout does not match with the kickoff_data");
    return Ok(true);
}
``` [8](#0-7) 

Since the DB now holds the attacker's pubkey (not the true operator's), this mismatch fires, the kickoff is flagged malicious, and a `Challenge` transaction is queued against the honest operator [9](#0-8) .

None of the existing guards prevent this: `SECP.verify_schnorr` in `Operator::withdraw` only validates input 0/output 0 (per sighash scope), `is_profitable` only checks amounts, and there is no on-chain or off-chain check binding the OP_RETURN pubkey to anything the user's signature commits to.

### Impact Explanation
The true funding operator, having fronted BTC to the user via `Operator::withdraw`, becomes unable to claim reimbursement because its kickoff is flagged malicious purely due to attribution hijack — matching "an honest operator permanently unable to be reimbursed" (Critical). This is repeatable per withdrawal that is broadcast unconfirmed with an RBF-signaling sequence (which is every payout tx, since `DEFAULT_SEQUENCE` is fixed), across any operator and deposit, as long as the attacker can win the fee race before confirmation.

### Likelihood Explanation
Preconditions: the payout tx must be observable unconfirmed (normal mempool propagation), and RBF replacement must succeed (payout tx already signals RBF via `ENABLE_RBF_NO_LOCKTIME`; the attacker only needs to pay a marginally higher fee than the honest operator's fee-rate for the replacement). The attacker needs no privileged role, no compromised keys, and no majority hashrate — just fee funds and the ability to broadcast, both explicitly within the unprivileged attacker's granted capabilities.

### Recommendation
Change `create_payout_txhandler` / `Operator::withdraw` to commit the operator-attribution OP_RETURN (and ideally the anchor) inside the signed digest — e.g., require the user's signature to use `SIGHASH_ALL` (or `AllPlusAnyoneCanPay`, which still commits `hashOutputs` over all outputs) instead of `SinglePlusAnyoneCanPay`, or otherwise move operator attribution to a mechanism that isn't malleable independently of the fixed user payout, such as tying it to the input(s) the operator itself signs/funds rather than an unauthenticated OP_RETURN output.

### Proof of Concept

```
Plan:
1. Set up regtest bridge with an honest operator; call `Operator::withdraw` to build/broadcast `payout_tx` with output 0 = user payout, output 2 = OP_RETURN(honest_operator_xonly_pk).
2. Before confirmation, construct `payout_tx_evil`: same input 0 (same witness, reused signature), identical output 0, add an attacker-owned funding input with higher total fee, output OP_RETURN(attacker_xonly_pk) at any index, mine it via RBF replacement (`sendrawtransaction` with higher fee, then `generatetoaddress`).
3. Assert `payout_tx_evil` confirms and `payout_tx`'s honest broadcast does not.
4. Run `update_finalized_payouts` equivalent sync path and assert:
   `db.get_payout_info_from_move_txid(...).0 == Some(attacker_xonly_pk)` while `attacker_xonly_pk != honest_operator_xonly_pk`.
5. Call `is_kickoff_malicious` with `kickoff_data.operator_xonly_pk == honest_operator_xonly_pk` and assert it returns `Ok(true)` (flagged malicious) despite the honest operator having genuinely funded the withdrawal — proving the binding `recorded_operator_xonly_pk == true_funding_operator_xonly_pk` is broken.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Checks if the kickoff is malicious and sends the appropriate txs if it is.
    /// Returns true if the kickoff is malicious.
    /// Sends a challenge tx if the kickoff is first malicious one in the current round, and the network is not mainnet or testnet4.
    pub async fn handle_kickoff<'a>(
        &'a self,
        dbtx: DatabaseTransaction<'a>,
        kickoff_witness: Witness,
        mut deposit_data: DepositData,
        kickoff_data: KickoffData,
        challenged_before: bool,
    ) -> Result<bool, BridgeError> {
        let is_malicious = self
            .is_kickoff_malicious(kickoff_witness, &mut deposit_data, kickoff_data, dbtx)
            .await?;

        let deposit_outpoint = deposit_data.get_deposit_outpoint();

        let (_signed_txs, tx_metadata, challenge_tx) = self
            .get_signed_txs_for_kickoff(dbtx, kickoff_data, deposit_data)
            .await?;

        if is_malicious {
            tracing::warn!(
                "Malicious {} detected. {} Challenge tx: {} for deposit {}",
                kickoff_data,
                match challenged_before {
                    false => "This is the first malicious kickoff in the current round.",
                    true => "This is not the first malicious kickoff in the current round.",
                },
                bitcoin::consensus::encode::serialize_hex(&challenge_tx),
                deposit_outpoint
            );
            // do not automatically send challenge txs on mainnet or testnet4
            if !challenged_before
                && !matches!(
                    self.config.protocol_paramset().network,
                    bitcoin::Network::Bitcoin | bitcoin::Network::Testnet4
                )
            {
                #[cfg(feature = "automation")]
                self.tx_sender
                    .add_tx_to_queue(
                        dbtx,
                        TransactionType::Challenge,
                        &challenge_tx,
                        &[],
                        Some(tx_metadata),
                        self.config.protocol_paramset(),
                        None,
                    )
                    .await?;
            }
