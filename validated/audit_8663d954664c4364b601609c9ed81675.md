### Title
Leftover funds below the dust threshold are silently burned as miner fees instead of being redirected - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
The referenced bug class is "value sent to a contract/address where it becomes stranded; excess should be swept to a sink the protocol controls (treasury)". The Serai analog lives in `SignableTransaction::new`: when a change address is provided but the leftover amount (`inputs - payments - fee`) falls below `DUST` (546 sat), the change output is silently omitted and the entire remainder is folded into the transaction fee, paying it to miners rather than to any destination the protocol controls.

### Finding Description
In `SignableTransaction::new`, the base fee `needed_fee` is computed from the transaction's vbytes without change (`fee_per_vbyte * vbytes`). If a `change` script is supplied, the function recomputes the fee with the change output included and only appends the change output when `input_sat - (payment_sat + fee_with_change) >= DUST`. When the leftover is positive but under `DUST`, no change output is created and `needed_fee` remains the *without-change* value. The transaction then has `sum(outputs) = payment_sat`, so `fee()` — defined as `sum(prevouts) - sum(outputs)` — exceeds `needed_fee` by up to `DUST - 1` sats, with the excess paid to miners. There is no fallback that redirects the sub-dust remainder to a controlled output (e.g., incrementing a payment/branch output to a protocol-owned address, or a treasury output); it is simply destroyed as fee. This contradicts the caller-facing accounting: `needed_fee()` and `fee()` can diverge, and the scheduler in `processor/src/networks/mod.rs` treats the sub-dust change as an "operating cost" that is effectively unrecoverable, even though the funds could have been consolidated into an existing output to the multisig's own key.

### Impact Explanation
Each transaction whose change remainder lands in `[1, DUST)` burns up to 545 sats (at the library's `DUST`) — and up to the network-level `DUST` of 10,000 sats where `processor` filters outputs — as excess fee to miners. Over many transactions this is a steady, silent bleed of protocol-held funds. The lost value benefits no protocol participant and cannot be recovered, matching the "free tokens on the Ledger" class where residual value is stranded instead of swept to a treasury.

### Likelihood Explanation
Reachability is public-input driven: withdrawals and the chosen input set (external `ReceivedOutput`s anyone can send to a scanned script) determine `input_sat`, and requested payments determine `payment_sat`. An unprivileged user requesting a withdrawal whose amount leaves a sub-dust remainder — or simply the natural distribution of payment amounts — deterministically triggers the burn whenever `input_sat - payment_sat - fee_with_change ∈ [1, 546)`. No privileged access is required; it is a property of public payment amounts and on-chain inputs.

### Recommendation
When the computed change value is below `DUST`, redirect the remainder rather than leaving it in the fee: e.g., add the leftover to an existing output paying a protocol-controlled address (branch/change key), or explicitly route it to a treasury/OP_RETURN-adjacent consolidation output. At minimum, document the behavior in `SignableTransaction::new`'s doc comment and make `needed_fee` reflect the true implied fee so callers are not misled by `fee() != needed_fee`.

### Proof of Concept
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:204-235`): construct `inputs` with `input_sat = payment_sat + fee_with_change + 500`, a single payment of `payment_sat`, and `change = Some(...)`. `fee_with_change` is deducted, `value = 500 < DUST`, so no change output is pushed and `needed_fee` keeps the smaller no-change value. `signable.fee()` returns `needed_fee + 500` — 500 sats paid to miners that could have been swept. Calling `needed_fee()` reports the lower figure, hiding the burn from accounting.
