## Title
EVM bank precompile `sendNative` bypasses the `SendEnabled`/pause gate that `MsgSend` enforces - ([File: precompiles/bank/bank.go])

### Summary
The `x/bank` module implements a governance-controlled "outflow gate" via `SendEnabled`/`DefaultSendEnabled` params: the standard `MsgSend` handler calls `IsSendEnabledCoins` before moving funds so operators can halt token transfers chain-wide or per-denom. [1](#0-0)  However, the EVM bank precompile's `sendNative` function moves native `usei`/`wei` balances by calling `bankKeeper.SendCoinsAndWei` directly, which never checks `IsSendEnabledCoins`. [2](#0-1) 

### Finding Description
`SendCoinsAndWei` only performs `SubWei`/`AddWei` and a raw `SendCoinsWithoutAccCreation` call for the usei remainder — it does not gate on `SendEnabled` at all: [3](#0-2) 

Compare this to the code path used by the ordinary `MsgSend` handler (also reachable through the precompile's `send` (ERC20-pointer) method via `p.bankMsgServer.Send`), which explicitly enforces the send-enabled check before doing any transfer: [1](#0-0) 

The precompile's `send` method (for ERC20 pointer tokens) correctly routes through `bankMsgServer.Send`, inheriting the `IsSendEnabledCoins` check: [4](#0-3) 

But `sendNative` skips the msg server entirely and calls the keeper method directly: [5](#0-4) 

This mirrors the reported bug class exactly: one specific fund-moving entry point ("rolloverETH" in the original report; "sendNative" here) omits the outflow/pause check that all the other equivalent paths (`cancel`, `withdrawDeposits` in the report; `MsgSend`/pointer `send` here) enforce.

### Impact Explanation
If chain governance/admin disables `usei` sending (e.g., `DefaultSendEnabled=false` or `SendEnabled` override for `usei`) to halt transfers — for incident response, compliance, or during an upgrade — any EVM account can still move native `usei`/`wei` balances between Sei addresses by calling the bank precompile's `sendNative(receiver)` payable method at `0x0000000000000000000000000000000000001001`, completely bypassing the intended freeze. This is a direct violation of a chain-level transfer-pause control and results in unauthorized fund movement while transfers are supposed to be halted.

### Likelihood Explanation
High likelihood of exercise once the send-enabled gate is toggled off: `sendNative` is a public, permissionless payable precompile method reachable from any EVM transaction or contract call with no special preconditions beyond having an associated Sei address and non-zero value. [6](#0-5)  No privileged access or edge-case state (unlike the original dust-rollover condition) is required — it works for any transfer amount, at any time the gate is disabled.

### Recommendation
Add an `IsSendEnabledCoins` (and ideally `BlockedAddr`) check for the base denom in `sendNative` (and any other keeper-level call sites like `SendCoinsAndWei`) before performing the transfer, mirroring the check already done in `bank/keeper/msg_server.go`'s `Send` handler, so the EVM precompile path cannot be used to route around the module's pause mechanism.

### Proof of Concept
1. Governance/admin sets `x/bank` params with `DefaultSendEnabled=false` (or `SendEnabled` override disabling `usei`).
2. Confirm `MsgSend` now fails: `IsSendEnabledCoins` returns `ErrSendDisabled` per `msg_server.go` lines 29-31.
3. From an EVM account with value > 0, call `sendNative(receiverSeiAddrString)` on the bank precompile at `0x...1001`.
4. Observe the call succeeds: `sendNative` calls `pcommon.HandlePaymentUseiWei` then `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` directly, with no `IsSendEnabledCoins` check anywhere on this path (`precompiles/bank/bank.go` lines 280-287, `sei-cosmos/x/bank/keeper/send.go` lines 438-459), so funds move despite the pause.

func (k BaseSendKeeper) SendCoinsAndWei(ctx sdk.Context, from sdk.AccAddress, to sdk.AccAddress, amt sdk.Int, wei sdk.Int) error {
	if err := k.SubWei(ctx, from, wei); err != nil {
		return err
	}
	if err := k.AddWei(ctx, to, wei); err != nil {
		return err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.EventTypeWeiTransfer,
			sdk.NewAttribute(types.AttributeKeyRecipient, to.String()),
			sdk.NewAttribute(types.AttributeKeySender, from.String()),
			sdk.NewAttribute(sdk.AttributeKeyAmount, wei.String()),
		),
	})
	if amt.GT(sdk.ZeroInt()) {
		return k.SendCoinsWithoutAccCreation(ctx, from, to, sdk.NewCoins(sdk.NewCoin(sdk.MustGetBaseDenom(), amt)))
	}
	return nil
}
