### Title
Partial-commit staging re-derives the diff at apply-time and applies stale UI line-selection indices, allowing silent commit of unintended content - ([File: app/src/lib/git/apply.ts])

### Summary
The Sherlock report describes an accounting invariant (`PublicVault.last`) that is computed once, then silently used stale against a live-changing state (`yIntercept`/`slope`) until an external trigger (a payment) resynchronizes it — causing wrong values to be trusted in the interim. The Desktop analog is `applyPatchToIndex` in `app/src/lib/git/apply.ts`, which fetches a **fresh** diff of the file on disk at commit time and reapplies a `WorkingDirectoryFileChange.selection` (a set of line indices) that was computed against a **different, earlier** diff shown to the user in the Changes view. There is no check that the selection's originating diff still matches the diff being patched.

### Finding Description
When a user stages a partial commit (selecting individual lines/hunks), the selection is stored as line-index ranges (`DiffSelection`) tied to a specific diff snapshot that was rendered in the UI (see `hunk.unifiedDiffStart + lineIndex` indexing in [1](#0-0) ).

At actual commit time, `stageFiles` → `applyPatchToIndex` is invoked [2](#0-1) . Inside `applyPatchToIndex`, the diff is **recomputed from disk** right before formatting the patch: [3](#0-2) 

This freshly-fetched diff is fed into `formatPatch(file, diff)` together with the `file.selection` object that was captured earlier (from `_commitIncludedChanges`, which reads `state.changesState.workingDirectory.files` synchronously at commit-click time: [4](#0-3) ). `formatPatch` blindly maps `hunk.unifiedDiffStart + lineIndex` absolute indices from the *newly-fetched* diff against the selection bitmap that was built from the *previously displayed* diff [5](#0-4) .

If the file's on-disk content changes between the moment the diff was rendered/selected in the UI and the moment the commit executes — e.g., a build tool, a git `smudge`/`clean` filter, a background formatter, an editor autosave, or content written by a process spawned from an attacker-controlled repository (post-checkout/pre-commit hook, `.gitattributes`-driven filter, or any script triggered while the repo is open) — the hunk boundaries and line offsets shift. The stale `DiffSelection` indices no longer point to the same logical lines. `git apply --cached --unidiff-zero` will then either:
- apply successfully against different lines than what the user reviewed and clicked to include (silently staging different content), or
- fail, but with a generic apply error that doesn't communicate line drift to the user.

Existing guards only protect the **UI diff view** from this race — `updateChangesWorkingDirectoryDiff` explicitly re-checks `selectedFileIDsBeforeLoad` against current state before accepting an async diff load [6](#0-5) . No equivalent check (e.g., comparing diff content hash/mtime or the file's original diff snapshot) exists in the actual patch-application path (`apply.ts`/`patch-formatter.ts`), meaning the safety check protects only what the user *sees*, not what actually gets committed.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A repository whose build tooling, hooks, or filters can mutate a tracked file's content between diff render and commit (a scenario plausibly triggered simply by opening/using an attacker-controlled cloned repo with legitimate-looking build scripts or git filters) can cause a user's partial commit to include lines/content they never selected, or omit lines they intended to commit — without any error surfaced to the user in the common "apply succeeds against wrong offsets" case.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires a window between the diff snapshot being captured/rendered and clicking commit, and a concurrent process (build tool, watcher, git hook/filter driven by the repository itself) modifying the exact file being partially committed. Desktop workflows commonly leave the Changes view open while builds/watchers run, so the window is realistic, but the attacker needs some mechanism to write to the file at the right time, which is repository/tooling-dependent rather than a direct network/API primitive.

### Recommendation
Bind the `DiffSelection` to the diff it was generated from (e.g., store a content hash or the diff object itself alongside the selection) and, in `applyPatchToIndex`, verify the freshly-fetched diff matches that snapshot before calling `formatPatch`. If it doesn't match, abort the partial-stage operation and force the UI to refresh the diff and require the user to re-select, mirroring the staleness guard already implemented for the read-only diff view in `updateChangesWorkingDirectoryDiff`.

### Proof of Concept
1. Open a repository in GitHub Desktop and modify `file.txt`, producing a diff with hunks at known line offsets.
2. In the Changes view, select only a subset of lines (partial selection) to include in the commit; do not commit yet.
3. Before clicking "Commit," have a concurrent process (e.g., a `pre-commit`/file-watcher script bundled in the repo, or manually for demonstration) append/insert lines earlier in the same file, shifting subsequent line offsets.
4. Click "Commit." `applyPatchToIndex` ( [7](#0-6) ) re-fetches the diff via `getWorkingDirectoryDiff`, now reflecting the shifted content, but reuses the original `file.selection` indices.
5. Inspect the resulting commit via `git show`: the staged hunk corresponds to different physical lines than what was highlighted/selected in the UI at step 2, demonstrating silent corruption of the committed content.
