### Title
Uneconomical dust deposits are accepted by the `Scanner` and forced into `SignableTransaction`s, permanently draining the multisig - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class is a low-cost griefing/DoS where an unprivileged party performs a public action (here, sending a Bitcoin transaction) that the protocol is forced to accept, and whose subsequent processing makes a victim's operation fail or bleed funds, while the attacker's cost is minimal. In Serai's Bitcoin wallet, `Scanner::scan_transaction` reports any output paying to a registered script as a `ReceivedOutput` as long as a downstream check clears only the bare `DUST` limit, and `SignableTransaction::new` never checks that an input's value exceeds the marginal fee cost of spending it. A griefer can therefore flood the multisig with minimally-above-dust outputs that are *reported as received* yet are uneconomical (or even net-negative) to ever spend.

### Finding Description
`Scanner::scan_transaction` accepts every transaction output whose `script_pubkey` matches a registered script, with no lower bound on value — the only quantity recorded is the outpoint and the offset used to spend it [1](#0-0) . The processor's only filter is `output.balance().amount.0 >= N::DUST`, i.e. the 546-sat relay dust limit [2](#0-1) .

On the spending side, `SignableTransaction::new` sums input values and checks only `input_sat < payment_sat + needed_fee` for sufficiency, and that each *payment* is ≥ `DUST` — there is no check that each input's value exceeds the fee its own ~58-vbyte Taproot input weight will consume [3](#0-2) [4](#0-3) . Since the protocol must eventually spend all scanned outputs of an active key (there is no mechanism to abandon an accepted output), each grief output is either a guaranteed net loss at sufficiently high feerates or a permanently queued input contributing to `MAX_INPUTS` pressure and transaction weight [5](#0-4) .

### Impact Explanation
This is the "funds reported received that are not spendable" outcome: the scanner emits an `ExternalBalance` crediting the vault with an output whose marginal spend cost (≈58 vbytes × prevailing feerate) can exceed its 546–N sat value, so spending it loses money and not spending it leaves an un-actionable liability inflating plan/operating cost accounting and blocking batch transactions as weight approaches `MAX_STANDARD_TX_WEIGHT` (`TooLargeTransaction`, which panics the processor's `make_signable_transaction`) [6](#0-5) . The attacker's cost is only the donated output value (~546 sats) plus one-time tx fees — no capital is locked, mirroring the zero-recurring-cost grief in the reference report.

### Likelihood Explanation
Fully reachable by any unprivileged Bitcoin user: the multisig's deposit scripts are public (they appear in every scanned deposit's `script_pubkey`), so anyone can craft outputs to them at will. It triggers whenever feerates exceed ~9 sat/vB (546 sat / 58 vB) — a routine condition — and can be repeated cheaply to accumulate liability. Impact is bounded per-output, justifying Medium.

### Recommendation
Enforce a minimum acceptable output value in `Scanner::scan_transaction` / the output-acceptance path that accounts for spend cost — e.g. reject (or quarantine, never auto-plan) outputs below `DUST + input_weight_vbytes * max_expected_feerate` — and/or add a per-input profitability check in `SignableTransaction::new` that refuses or defers inputs whose value is below their marginal fee, with an explicit path to permanently abandon such outputs rather than treating them as spendable balance.

### Proof of Concept
1. Observe any deposit to Serai's Bitcoin multisig to learn the external (offset-zero) P2TR `script_pubkey` `S` for the active group key — the script is `new_p2tr_tweaked(x_only(key))` [7](#0-6) .
2. Broadcast a Bitcoin transaction containing, e.g., 100 outputs of 546 sats each to `S`. `scan_transaction` returns 100 `ReceivedOutput`s [8](#0-7) , each passing the `>= N::DUST` filter.
3. At a feerate of 20 sat/vB, each input costs ~1160 sats to spend while contributing 546 — a net loss of ~614 sats per input the protocol is obligated to absorb. `SignableTransaction::new` will happily include them since it only checks aggregate `input_sat >= payment_sat + needed_fee` [9](#0-8) ; if never spent, they permanently remain as received-but-unspendable balance and bloat future plan weight until `TooLargeTransaction` is hit [5](#0-4) .
4. Attacker cost: ~54,600 sats of outputs (which are technically still credited to the vault, i.e. partially recoverable in concept but unspendable in practice) plus one transaction's fee — a one-time, non-recurring cost for a persistent grief.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
