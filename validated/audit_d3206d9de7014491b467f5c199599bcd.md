### Title
`ThresholdKeys::read` skips the identity-point rejection applied by `Curve::read_G`, allowing deserialized verification shares of identity which make arbitrary signature shares pass blame verification - (File: crypto/dkg/src/lib.rs)

### Summary
FROST's `Curve::read_G` deliberately rejects identity points because identity commitments/keys break the security arguments of the signing protocol (`crypto/frost/src/curve/mod.rs:123-131`, with the rationale stated in `random_nonce` at lines 103-108: zero-valued points "will be rejected for being zero (and if they were used, leak the secret share)"). This guard is consistently applied to untrusted preprocess commitments via `GeneratorCommitments::read` / `NonceCommitments::read` / `Commitments::read` (`crypto/frost/src/nonce.rs:34-35`, `74-80`, `133-139`). However, the parallel deserialization entry point `ThresholdKeys::read` reads the per-participant verification shares with `<C as Ciphersuite>::read_G` (`crypto/dkg/src/lib.rs:620-623`), which performs no identity rejection, and `ThresholdKeys::new` does not check for identity shares either (`crypto/dkg/src/lib.rs:354-391`). The guard exists on one path into the same sensitive structure but is absent on the other — the same bug class as `balanceOfNFT` checking `ownershipChange` while `votingPowerOf` omits it.

### Finding Description
In `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:447-495`), when the aggregate signature check fails, each participant's share is verified via `algorithm.verify_share(view.verification_share(l), B.bound(l), share)` which queues `R_l + c·Y_l' − s_l·G == 0` into a `BatchVerifier`. `Y_l'` is `view.verification_share(l)`, computed in `ThresholdKeys::view` as `verification_shares[i] * scalar * λ_i` (`crypto/dkg/src/lib.rs:500-507`). If the underlying `verification_shares[i]` is the identity — only possible because `ThresholdKeys::read` used the non-rejecting `Ciphersuite::read_G` — then `Y_l'` is identity regardless of scalar/λ, and the statement degenerates to `R_l == s_l·G`.

A malicious participant can therefore pick an arbitrary share `s_l` and publish a preprocess commitment `R_l = s_l·G` (already permitted: `R_l` is attacker-controlled and only checked for non-identity). Their corrupted share then passes per-share verification: `batch.verify_vartime_with_vartime_blame` cannot attribute the fault, while the aggregate signature fails. The code itself acknowledges this exact state at `crypto/frost/src/sign.rs:491-494`: "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys", returning `FrostError::InternalError`.

### Impact Explanation
A participant holding a `ThresholdKeys` whose own verification share is identity can repeatedly submit shares that invalidate every signing session's aggregate signature while evading the blame mechanism entirely. Honest participants cannot identify or exclude the malicious signer (no `InvalidShare(l)` is ever produced for them), so FROST signing for that key set can be stalled indefinitely, and operators cannot safely rotate since blame attribution is corrupted. This is a failure of the verifier's correctness guarantee — a share is accepted as valid under a formula that no longer binds it to the participant's key share — reachable via untrusted bytes fed to `ThresholdKeys::read`.

### Likelihood Explanation
Exploitation requires the attacker's `ThresholdKeys` to be deserialized with an identity verification share for their index. `ThresholdKeys::read` is a public API accepting arbitrary bytes and is used to load keys (e.g., `GeneratedKeysDb::read_keys` in `processor/src/key_gen.rs:57-58`). The corrupted structure passes `ThresholdKeys::new`'s validation — share count and participant bounds are checked, identity is not — and `group_key` computed at line 377-378 silently drops the identity contribution, so nothing downstream detects the malformed set until signing sessions fail without attributable blame. Medium likelihood conditioned on key material being deserialized from a store an attacker can influence.

### Recommendation
Reject identity verification shares in `ThresholdKeys::read` (and defensively in `ThresholdKeys::new`), consistent with `Curve::read_G`:

```rust
// crypto/dkg/src/lib.rs, in ThresholdKeys::read
for l in (1 ..= n).map(Participant) {
  let share = <C as Ciphersuite>::read_G(reader)?;
  if share.is_identity().into() {
    Err(io::Error::other("identity verification share"))?;
  }
  verification_shares.insert(l, share);
}
```

Optionally also reject an identity computed `group_key` in `ThresholdKeys::new`.

### Proof of Concept
1. Serialize a valid `ThresholdKeys<C>` blob, then patch the bytes for the attacker's own `verification_shares[i]` entry to the canonical identity encoding (e.g., 32 zero/first-encoding bytes for the ciphersuite).
2. `ThresholdKeys::<C>::read` succeeds: `<C as Ciphersuite>::read_G` accepts identity (`crypto/dkg/src/lib.rs:622`), and `ThresholdKeys::new` performs only count/bounds checks (`crypto/dkg/src/lib.rs:355-365`).
3. Run `AlgorithmMachine::new(alg, malicious_keys).preprocess()` → `sign` → `complete` with the attacker submitting share `s_l` and commitment `R_l = s_l·G` for a chosen wrong `s_l`.
4. Aggregate `verify` fails; the blame loop queues `(ONE, R_l), (c, identity), (-s_l, G)` for the attacker (`crypto/frost/src/sign.rs:476-485`), which sums to zero, so `batch.verify_vartime_with_vartime_blame` reports no faulty participant and `complete` returns `InternalError` instead of `InvalidShare(l)` — the protection present in the commitment read path is bypassed via the key read path.

Note: I was unable to fully trace PedPoP/`EncryptedMessage::read` and the Bitcoin Schnorr algorithm's `verify`/`verify_share` parity handling within the iteration budget; an additional asymmetric-check analog may exist there, but the finding above stands on its own from code directly read.
