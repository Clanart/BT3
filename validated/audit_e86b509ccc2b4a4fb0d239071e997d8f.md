### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee/weight calculation, so the returned `needed_fee` and the enforced minimum-fee check are computed against a smaller transaction than the one actually produced - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The bug-class in the external report is a preview/estimation function whose formula does not compute the value callers actually need (a per-unit rate), producing misleading results. The Serai analog is in `SignableTransaction::new`: the transaction's OP_RETURN data output is pushed into `tx_outs` *before* the weight/vbytes estimation, but `calculate_weight_vbytes` is only given `payments` — the data output is never included in the size used to compute `needed_fee` or the minimum-relay-fee check. An unprivileged caller supplying `data` via the public `SignableTransaction::new` API gets a `needed_fee` that under-pays for the real transaction size.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` accepts an optional `data` payload of up to 80 bytes and appends it as a zero-value `OP_RETURN` output [1](#0-0) . Immediately after, the weight estimate is computed as `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — note `payments`, not `tx_outs`, so the OP_RETURN output (up to ~92 bytes: 8-byte amount + script of up to ~83 bytes) is entirely absent from the estimated size [2](#0-1) . Both `needed_fee = fee_per_vbyte * vbytes` and the `TooLowFee` minimum-relay check use this underestimated `vbytes` [3](#0-2) . When a change output is considered, the recomputation `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` again omits the data output [4](#0-3) . Because the OP_RETURN is zero-valued, the *absolute* fee (`input_sat - outputs`) equals the computed `needed_fee`, but the *actual* transaction is up to ~92 bytes larger than estimated, so the effective fee rate is strictly below `fee_per_vbyte` — the exact quantity `needed_fee()` and the fee-rate parameter promise [5](#0-4) .

### Impact Explanation
Any caller (including the processor's `needed_fee`/`signable_transaction` flow if it ever passes `data`) receives a fee estimate that does not achieve the requested fee rate. If `fee_per_vbyte` is set near `DEFAULT_MIN_RELAY_TX_FEE`, the signed transaction's true fee rate can fall below the network minimum relay fee, producing a signed, broadcastable transaction that mempool nodes reject — the outputs it spends cannot be spent by that transaction. More generally, `needed_fee()` reports an incorrect value: the formula computes the fee for a different (smaller) transaction than the one returned, mirroring the report's "formula does not compute the intended quantity" class. This is reachable purely through the public `data` argument.

### Likelihood Explanation
Deterministic whenever `data: Some(_)` is passed — every byte of the OP_RETURN output is omitted from both weight estimates. Severity is bounded: absolute fee accounting is still self-consistent (zero-value output), so the impact is an understated fee rate rather than fund loss, and current in-repo callers pass `data: None`. Medium.

### Recommendation
Include the OP_RETURN output in the size estimation. Either pass `tx_outs` (rather than `payments`) into `calculate_weight_vbytes`, or add the data output to the payments-style list before calling, e.g. building the template transaction with `output: tx_outs.clone()` for both the change and no-change estimates so `needed_fee` and the `TooLowFee` check reflect the final transaction's real vsize.

### Proof of Concept
```rust
// Construct via the public API with a data payload:
let data = vec![0xAA; 80];
let st = SignableTransaction::new(
    vec![received_output],          // one P2TR input
    &[(payment_script, 10_000)],
    None,                           // no change
    Some(data),
    1,                              // fee_per_vbyte = 1 (minimum relay rate)
).unwrap();

// needed_fee was computed on a tx WITHOUT the OP_RETURN output (~ up to 92 bytes).
// tx.transaction() contains the extra output, so:
//   real_vsize > estimated vbytes
//   actual feerate = needed_fee / real_vsize < 1 sat/vbyte < DEFAULT_MIN_RELAY_TX_FEE
// The transaction passes the internal TooLowFee check yet is below relay minimum.
```
