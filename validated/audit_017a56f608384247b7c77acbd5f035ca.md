### Title
`ThresholdKeys` accepts zero interpolation coefficients / identity verification shares, letting a "null" participant produce valid signature shares with no secret - (File: crypto/dkg/src/lib.rs)

### Summary

Analogous to the DebtRegistry `beneficiary == 0` issue, `ThresholdKeys::new` (and the untrusted-byte path `ThresholdKeys::read`) never rejects a zero `Interpolation::Constant` coefficient or an identity verification share. A participant whose interpolation factor is `0` produces signature shares that verify while contributing nothing to the group key — they are a "null beneficiary" entry the rest of the system assumes cannot exist.

### Finding Description

`ThresholdKeys::new` validates only the *count* of verification shares (`len == n`) and that indexes are `<= n`; it never checks that `interpolation_factor` is non-zero, that `verification_shares[i]` is non-identity, or that `secret_share * G == verification_shares[i]` (`crypto/dkg/src/lib.rs:349-391`). `ThresholdKeys::read` deserializes all of this from attacker-controlled bytes: `Interpolation::Constant` coefficients via `C::read_F` (which accepts zero) and verification shares via `Ciphersuite::read_G` — notably *not* `Curve::read_G`, which is the variant that rejects identity (`crypto/frost/src/curve/mod.rs:125-131`) — then forwards to `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:604-632`).

In `view()`, the secret share is multiplied by `interpolation_factor(i, included)` and each verification share is likewise scaled by it (`crypto/dkg/src/lib.rs:494-507`). With factor `0`:

- `secret_share = 0 * s = 0`, so `sign_share` emits `share = nonce` (`crypto/frost/src/algorithm.rs:201-211`, `SchnorrSignature::sign` computes `s = c*0 + r`).
- `verification_share = identity`, so `verify_share` reduces to `R + c*identity - s*G = R - s*G`, which passes exactly when `s == r` (`crypto/frost/src/algorithm.rs:219-230`, `crypto/schnorr/src/lib.rs:88-100`).
- `group_key` in `ThresholdKeys::new` is computed as `sum(verification_shares[i] * factor)` over `1..=t`, so the zeroed participant's term is silently dropped and the group key remains self-consistent.

`musig()` builds `Interpolation::Constant` from hash-derived binding factors (`crypto/dkg/musig/src/lib.rs:139-160`), and `GeneratorPromotion::complete` reuses `self.base.interpolation().clone()` into a new `ThresholdKeys` (`crypto/dkg/promote/src/lib.rs:158-166`), propagating the poisoned coefficients.

### Impact Explanation

A deserialized `ThresholdKeys` set can declare participant `j` a member of the threshold while their constant coefficient is `0`. Participant `j` — knowing no secret share at all — produces signature shares that pass `verify_share` in `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:447-495`), yet contribute nothing to the aggregated signature. A `t`-of-`n` set silently degrades to `(t-1)`-of-`n`: the "entry" exists, passes all validity checks, and signs, exactly like a DebtRegistry entry with a null beneficiary being treated as a valid issuance.

### Likelihood Explanation

`ThresholdKeys::read` is an explicitly reachable parser for untrusted bytes, and `GeneratorPromotion::complete` amplifies any such malformed interpolation to a new generator. Exploitation requires the attacker to control the serialized key material (or a promotion base), which is a deployment-dependent but documented consumption path; the cryptographic bypass itself is deterministic once zero coefficients are present — no negligible-probability assumptions needed.

### Recommendation

In `ThresholdKeys::new`:

- Reject `Interpolation::Constant` vectors containing a zero coefficient (or at minimum reject `interpolation_factor(i, all) == 0` for every participant).
- Reject identity verification shares and verify `secret_share * G == verification_shares[params.i()]`, plus that the derived `group_key` is non-identity.
- In `ThresholdKeys::read`, use an identity-rejecting point reader (equivalent to `Curve::read_G`) for verification shares.

### Proof of Concept

```rust
// t = n = 2, but participant 2's constant coefficient is 0
let s1 = Scalar::random(&mut OsRng);
let verification_shares = HashMap::from([
  (Participant::new(1).unwrap(), G::generator() * s1),
  // Arbitrary point; its coefficient is 0 so it's never consulted
  (Participant::new(2).unwrap(), G::generator() * Scalar::random(&mut OsRng)),
]);
let keys = ThresholdKeys::new(
  ThresholdParams::new(2, 2, Participant::new(2).unwrap()).unwrap(),
  Interpolation::Constant(vec![Scalar::ONE, Scalar::ZERO]), // j's factor is 0
  Zeroizing::new(Scalar::ZERO),                             // j knows no secret
  verification_shares,
).unwrap(); // Accepted: no zero-coefficient / identity / share-consistency checks
```

`keys.view(vec![p1, p2])` yields `secret_share = 0` and `verification_share = identity` for `p2`; `sign_share` returns `s = r`, and `verify_share` passes since `R - s*G = 0`. The same state is reachable purely from bytes via `ThresholdKeys::read` (interpolation tag `0`, coefficient `0`, arbitrary share/scalar).
