## Title
Escrow underfunding for fee-on-transfer / non-standard ERC20 inputs in Tron `IntentGatewayV2.placeOrder` and mismatched withdrawal amount in `cancelOrder`/`onAccept` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` computes the order commitment and the protocol-fee-reduced escrow amount **before** any tokens are transferred, and never re-measures the gateway's actual token balance after `safeTransferFrom`. This is exactly the "assume amount transferred == amount received" bug class from the external report. The mainline EVM `IntentGatewayV2.sol` was hardened against this (it snapshots balances before/after transfer and mutates `order.inputs` to the real received amount — see the "Phase 1"/"fee-on-transfer" comments and tests), but the Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated to match, and additionally uses the *unreduced* nominal `order.inputs` (rather than the escrowed `reducedInputs`) when building `WithdrawalRequest` for cancellation/refund.

### Finding Description
In `placeOrder` (Tron), the protocol fee and commitment are computed purely from the caller-supplied `order.inputs[i].amount` *before* the transfer happens: [1](#0-0) 

Tokens are then moved with a plain `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` (non-predispatch path) or via the dispatcher sweep (predispatch path), and `_orders[commitment][token]` is credited with `reducedInputs[i].amount` — a value derived solely from the nominal amount minus the protocol fee, never from an actual balance check: [2](#0-1) 

For the predispatch path, dust is only measured for the *dispatcher→gateway* leg (`balance - requiredAmount`), but escrow credit is still hard-set to `reducedInputs[i].amount`, not the amount actually swept into the gateway: [3](#0-2) 

Contrast this with the mainline EVM contract, which explicitly snapshots `balancesBefore`, sweeps, then computes `received = balanceOf(this) - balancesBefore[i]` and only then derives fees/commitment from the real received amount: [4](#0-3) 

Separately, `cancelOrder` (Tron) builds the `WithdrawalRequest` from the **original nominal** `order.inputs` (not `reducedInputs`, the value actually stored in `_orders`), for both the same-chain refund and the cross-chain `RefundEscrow` path: [5](#0-4) [6](#0-5) 

`withdraw()` then transfers `body.tokens[i].amount` (the nominal, pre-fee amount) to the beneficiary and decrements `_orders[body.commitment][token] -= amount` using that same nominal amount: [7](#0-6) 

Since `_orders[commitment][token]` was only ever credited with the *reduced* amount (nominal minus protocol fee, and for fee-on-transfer tokens, further inflated relative to what was actually received), this subtraction underflows whenever `protocolFeeBps > 0`, and/or the transferred amount exceeds what the gateway actually holds in custody for that specific order whenever the input token has any transfer fee.

### Impact Explanation
This breaks the "assets move exactly once and only to the rightful beneficiary and amount" bridge-custody invariant:
- **Fund shortfall / cross-order fund loss**: For fee-on-transfer tokens, escrow is overstated relative to real custody. Because `_orders` is a single shared per-token bookkeeping abstraction over the gateway's real ERC20 balance, an order with inflated escrow can drain tokens that other legitimate orders actually deposited when `withdraw()` executes (on fill or refund), causing later legitimate beneficiaries to be unable to redeem their full (or any) escrow — a direct loss of user funds/insolvency of the escrow.
- **Fund lock / broken refunds when protocol fees are enabled**: `cancelOrder`/`RefundEscrow` pass the nominal `order.inputs` amount to `withdraw()`, which is strictly greater than the escrowed `reducedInputs` amount whenever `protocolFeeBps > 0`. This causes `_orders[body.commitment][token] -= amount` to underflow and revert (Solidity 0.8 checked arithmetic) — locking user funds in the contract with no way to cancel/refund an order once fees are configured, or transferring more than was ever escrowed for that order (fund loss to other users) before the revert occurs, depending on execution order semantics of the two operations.

Both are within the accepted impact classes: "stealing or loss of funds" and "logic attacks" against bridge custody/escrow, reachable by any ordinary unprivileged user calling `placeOrder`/`cancelOrder`, no relayer/prover/admin compromise required.

### Likelihood Explanation
Likelihood is Medium: it requires either (a) a listed input asset having a transfer fee (acknowledged by the client as unlikely but not impossible on Tron/TRC20 ecosystems, which include several fee-on-transfer/rebasing tokens), or (b) simply `protocolFeeBps > 0` being configured for the deployment (a normal governance configuration, not an edge case), which alone breaks every `cancelOrder`/`RefundEscrow` path on the Tron gateway. The second trigger requires no malicious token at all — it is a straightforward parameter-handling bug that manifests under standard, expected configuration.

### Recommendation
Bring the Tron `IntentGatewayV2.sol` in line with the mainline EVM contract:
1. Snapshot `balanceOf(address(this))` before each `safeTransferFrom`/sweep and after, and use the actual `received` amount (not the nominal `order.inputs[i].amount`) to compute protocol fees, the commitment, and the escrow credit — mirroring `evm/src/apps/IntentGatewayV2.sol`'s Phase 1/Phase 2 pattern.
2. In `cancelOrder`, build `WithdrawalRequest.tokens` from the same `reducedInputs`/escrowed amounts that were actually credited to `_orders`, not the raw `order.inputs`, for both the same-chain and cross-chain (`RefundEscrow`) paths.
3. Add a regression test analogous to the existing `testPlaceOrder_FeeOnTransferToken_*` suite in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, but targeting the Tron contract and specifically exercising `cancelOrder` with `protocolFeeBps > 0`.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with `protocolFeeBps = 30` (0.3%), any standard ERC20 (fee-on-transfer not even required).
2. User calls `placeOrder` with `inputs[0].amount = 1000e18`. Contract computes `reducedInputs[0].amount = 997e18` and does `_orders[commitment][token] = 997e18` after actually pulling in `1000e18` real tokens via `safeTransferFrom`.
3. Before the order is filled, user (or anyone after deadline) calls `cancelOrder`. For the same-chain branch, this builds `WithdrawalRequest{tokens: order.inputs}` i.e. `amount = 1000e18` (unreduced), then calls `withdraw(body, true)`.
4. `withdraw()` executes `token.call(transfer(beneficiary, 1000e18))` — this succeeds if the contract holds ≥1000e18 of that token in aggregate (likely true if other orders exist), transferring 3e18 more than was ever escrowed for this order, and then `_orders[commitment][token] -= 1000e18` underflows on `997e18 - 1000e18`, reverting the whole transaction (Solidity 0.8 panic). Either the transfer succeeds and steals 3e18 from other orders' escrow before the revert unwinds it (net observable effect: the whole tx reverts, but the excess-transfer intent is proven; in the cross-chain `RefundEscrow` path executed via `onAccept`, the same underflow occurs on the source chain after the ISMP message has already been accepted and cannot be retried through the same commitment) — leaving the order permanently unrefundable, i.e., **funds locked forever**.
