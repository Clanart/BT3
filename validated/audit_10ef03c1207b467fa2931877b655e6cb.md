### Title
`placeOrder` credits `order.fees` as escrowed transaction fee without verifying the actual fee-token balance received from the swap - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
When a user pays `order.fees` in native token, `IntentGatewayV2.placeOrder` swaps ETH for the fee token via a governance-configured `uniswapV2Router()` and unconditionally records `_orders[commitment][TRANSACTION_FEES] = order.fees` — the *requested* amount — rather than the amount the gateway actually received. This is structurally identical to the SwapX bug: the caller trusts a promised/returned swap amount instead of measuring the balance delta, so if the configured router does not deliver the full nominal output (e.g., it deducts a fee on the output side after computing the swap, as SwapX's `takeFee` does), the gateway under-collects real fee-token balance while over-crediting its internal escrow ledger.

### Finding Description
In `placeOrder`:
```solidity
// evm/src/apps/IntentGatewayV2.sol:345-362
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = IDispatcher(hostAddr).feeToken();
        uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
        msgValue -= amounts[0];
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }

    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```
`order.fees` is written into the escrow ledger unconditionally after the swap, based only on the value the caller *requested*, not on any measured balance delta of `feeToken` on the gateway. The code trusts `amounts` (the "spent" leg) but never checks the "received" leg against `order.fees`.

This is the exact anti-pattern documented in the external report: a router can promise/perform a swap for a nominal output amount and then still deduct a fee from the output before forwarding it to the recipient (SwapX's `takeFee` inside `swapV2ExactIn`/`swapV3ExactIn` does precisely this on native-out swaps). The `uniswapV2Router()` address used here is a host-governance-configurable parameter (see `IDispatcher(hostAddr).uniswapV2Router()`), and the repo's own wrapper contracts (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`, `GnosisUniswapV2Wrapper`) exist specifically because non-standard V2-router-compatible integrations are expected to be plugged in here. Any router in this slot that skims fees on the output side after satisfying the nominal "exact tokens out" contract (or that is later swapped to a fee-charging implementation) will cause the gateway's real `feeToken` balance to be strictly less than the sum of all `_orders[...][TRANSACTION_FEES]` entries recorded.

Because `TRANSACTION_FEES` and all escrowed input tokens live in the same undifferentiated `feeToken` balance of the contract (there is no per-order token custody, only an internal accounting map, per `evm/src/apps/intentsv2/IntentsBase.sol:390-425` `_withdraw`), this shortfall is not contained to the order that caused it. When any order's escrow is later released via `fillOrder`/`onAccept`/cancellation, `_withdraw` unconditionally transfers the full recorded `fees` amount:
```solidity
// evm/src/apps/intentsv2/IntentsBase.sol:412-417
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
    ...
```
If the pooled `feeToken` balance is insufficient (because earlier swaps under-delivered), later legitimate withdrawals for *other, unrelated* orders can fail (fund lock/DoS) or — if a partial-fill/last-writer-wins allocation race occurs — some orders effectively consume feeToken balance that rightfully belonged to other users' escrow, i.e., a false accounting state that no existing guard checks (no invariant enforcing `feeToken.balanceOf(this) >= sum(_orders[*][TRANSACTION_FEES]) + sum(escrowed feeToken inputs)`).

### Impact Explanation
This is a bookkeeping/solvency defect in a live custody contract that escrows real user funds cross-chain. It causes the contract's ledger of owed fee-token amounts to diverge from its actual custodied balance, which can result in reverted withdrawals for unrelated orders (fund lock) or later withdrawals draining balance that belongs to other escrowed positions, i.e., loss of funds for other users' orders. Given `IntentGatewayV2` is the production intent-settlement/escrow contract, this qualifies as a "stealing or loss of funds" / "false state acceptance" class impact per the bounty gate. Severity is Medium: it does not require a malicious actor, only a router in the configured slot that isn't a strict 1:1 exact-output implementation (the codebase's own wrapper contracts hint at diverse, non-canonical router integrations being expected).

### Likelihood Explanation
Likelihood depends on the actual router deployed at `IDispatcher(hostAddr).uniswapV2Router()` for a given host. Canonical Uniswap V2 `swapETHForExactTokens` does deliver the exact requested output with no extra output-side fee, so on canonical Uniswap deployments this path is safe. However, the protocol explicitly supports and ships alternative V2-interface-compatible wrappers (`UniV3UniswapV2Wrapper`, `UniV4UniswapV2Wrapper`, `GnosisUniswapV2Wrapper`) and the router is a governance-mutable parameter (`UpdateParams`/host config), so the guarantee is not structurally enforced by the `IntentGatewayV2` contract itself — it silently depends on the specific router's exact-output semantics holding for all configured chains going forward. Any router that behaves like SwapX (skims the output post-swap) or otherwise under-delivers relative to the requested exact amount reintroduces this bug with no code path to detect it.

### Recommendation
- After the `swapETHForExactTokens` call, measure the actual `feeToken` balance delta on the gateway (balance-before vs. balance-after) instead of trusting `order.fees` was fully received, mirroring the fee-on-transfer handling already implemented elsewhere in the same function for input tokens (see the `received`/`balancesBefore` pattern used for `order.inputs`).
- Store `_orders[commitment][TRANSACTION_FEES] = actualReceived` rather than the nominal `order.fees`.
- If `actualReceived < order.fees`, either revert (`SwapFailed`/`InsufficientFeeAmount`) or explicitly account for the shortfall so the ledger can never diverge from the true custodied balance.
- Add an invariant check/test enforcing `feeToken.balanceOf(this) >= sum of outstanding TRANSACTION_FEES + feeToken-denominated escrow` after each `placeOrder`.

### Proof of Concept
1. Governance configures `IDispatcher(host).uniswapV2Router()` to point to a router that satisfies the V2 `swapETHForExactTokens` interface but, like SwapX's `takeFee`, deducts a small fee from the output token after computing the exact-output swap (e.g., a router that internally over-swaps to cover both the requested `amountOut` and its own fee, but only forwards `amountOut - fee` to `recipient` while still returning `amounts` consistent with the nominal request).
2. User calls `placeOrder` with `order.fees = F`, paying in native ETH (`msgValue > 0`).
3. `swapETHForExactTokens{value: msgValue}(F, path, address(this), ...)` executes; the gateway's actual `feeToken` balance increases by `F - fee` (less than `F`), but `_orders[commitment][TRANSACTION_FEES]` is set to the full `F`.
4. Repeat for additional orders, or note this already causes the gateway's total feeToken balance to be short by `fee` per such order.
5. When any of these orders (or an unrelated order that separately deposited exact feeToken via `safeTransferFrom`) is settled via `fillOrder`/`onAccept` → `_withdraw`, the contract attempts to `safeTransfer(beneficiary, fees)` using the recorded (inflated) `fees` value; once accumulated shortfalls exceed the actual balance, a subsequent legitimate withdrawal reverts (`ERC20InsufficientBalance`) — locking that user's rightful fee/input funds — or, depending on transfer ordering, an earlier finalize can pull balance that was actually funded by a *different* order's feeToken deposit, causing that other order to be unable to redeem its correctly-escrowed fee amount.     function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
