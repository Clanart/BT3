### Title
Merge target identified by mutable branch name instead of pinned SHA, allowing a moved/rewritten ref to be merged unexpectedly - (File: `app/src/lib/git/merge.ts`)

### Summary
`git/merge.ts` builds the `git merge` invocation using `branch.name` (a symbolic ref) rather than `branch.tip.sha` (the commit the user actually saw and reviewed when they clicked "Merge"). [1](#0-0) 

### Finding Description
Desktop's merge flow computes mergeability and shows a preview (`ComputedAction.Clean`/`Conflicts`) using `determineMergeability(repository, currentBranch, branch)` and the ahead/behind count for `branch.tip.sha` at selection time. [2](#0-1) 

The dialog does re-check `branch.tip.sha` against the state before applying the async preview, guarding against the branch object itself changing in local state. [3](#0-2) 

However, this only protects the *preview*, not the actual merge execution. When the user clicks "Start merge", `dispatcher.mergeBranch` is invoked with the `Branch` object and forwards to `GitStore.merge` → `merge()` in `git/merge.ts`, which re-resolves the target purely by `branch.name` at execution time. [4](#0-3) [5](#0-4) [6](#0-5) 

Between the time the mergeability preview is computed and the time the actual `git merge <branch-name>` command runs, there is an `await` gap (`updateStatus` is async, and the user can take arbitrary time to click "Merge"). If the branch is a remote-tracking branch (`origin/foo`) and the remote performs a force-push (or a background auto-fetch updates the ref) during this window, `origin/foo` will point to a different commit than the one the user reviewed. Because the merge command uses `branch.name`, not `branch.tip.sha`, git resolves the *current* value of the ref at merge time — silently merging content the user never saw or approved.

This mirrors the reported bug class exactly: the operation identifies its target by a name/index that can be re-pointed underneath the caller ("re-org"), rather than by an immutable identifier (SHA/claim+position). Just as the dispute game's `move()` should pin the exact claim+position instead of trusting `parentIndex` resolution at execution time, Desktop's merge should pin the exact commit SHA reviewed instead of trusting `branch.name` resolution at execution time.

### Impact Explanation
This causes silent corruption of what the user commits/merges: the merge commit created will pull in commits from an attacker-controlled remote that were never part of the reviewed diff or ahead/behind preview. Since GitHub Desktop performs background fetches (`_refreshRepository`, periodic scheduled fetch) that can update tracking refs without explicit user action, the window for this race is not contingent on the user manually re-fetching. An attacker controlling the compared remote/fork (e.g., a collaborator's fork referenced in a PR-style workflow, or any remote the repo is configured to track) can force-push malicious commits into the tracked branch precisely while the merge dialog is open, and have them silently merged and likely pushed by the unwitting user.

### Likelihood Explanation
GitHub Desktop performs automatic background fetches on a timer as well as fetches triggered by other UI interactions while a modal dialog (like the merge chooser) can remain open indefinitely awaiting user confirmation. Any remote the user has configured — including forks added automatically for PR checkouts — is a valid attacker-controlled surface per the "git remote/proxy response" impact category. No local access, admin rights, or social engineering beyond normal collaboration is required; only a force-push timed against a routine UI interaction.

### Recommendation
Resolve and pin the exact commit SHA (`branch.tip.sha`) at the moment the mergeability preview/dialog is shown, and pass that SHA (not the branch name) to the low-level `merge()` git call, failing/re-confirming if the ref has moved since the preview was computed — analogous to re-validating `commitSelection.shas` before applying async results elsewhere in the codebase (e.g. `_changeCommitSelection`/`_loadChangedFilesForCurrentSelection`). [7](#0-6) 

### Proof of Concept
1. Attacker and victim collaborate via a shared/forked remote; victim has `origin/feature` tracked locally.
2. Victim opens the "Merge into current branch" dialog and selects `origin/feature`. Desktop computes and displays a clean, conflict-free preview based on `origin/feature`'s current tip SHA via `determineMergeability`. [8](#0-7) 
3. Before the victim clicks "Merge branch", the attacker force-pushes malicious commits to `feature` on the remote.
4. Desktop's background auto-fetch (or victim's own next fetch) updates the local `origin/feature` ref to point at the attacker's new tip — the `Branch` object shown in the (still open) dialog is stale, but the underlying `name` still resolves to the new tip.
5. Victim clicks "Merge branch"; `dispatcher.mergeBranch` → `GitStore.merge` → `merge(repository, 'origin/feature', ...)` executes `git merge origin/feature`, which now merges the attacker's rewritten commits, not the reviewed ones, with no additional confirmation dialog re-displaying the new diff. [6](#0-5) 

**Note on confidence**: I could not fully trace whether Desktop's periodic background auto-fetch is enabled by default while a `MultiCommitOperation` popup is open, nor whether there's a higher-level guard elsewhere (outside the indexed files) that re-verifies the branch tip immediately before invoking `git merge`. Given index size limits, some file contents may not be available; a Devin session with full repository access could confirm whether such a guard exists elsewhere (e.g. in `dispatcher.ts`'s `mergeBranch` wrapper) before this is treated as fully unmitigated.
