Based on my investigation, I found a real local analog to the "documentation-only, not code-enforced" pattern from the external report, in the phantom-order price-discovery mechanism of `pallet-intents-coprocessor`.

### Title
`standard_amount` invariant for phantom order price discovery is enforced only by NatSpec/doc comments, not by code, silently poisoning published FX rates that solvers price real orders against - ([File: modules/pallets/intents-coprocessor/src/lib.rs])

### Summary
`PhantomTokenPair::standard_amount` must be exactly `10^decimals(token_a)` — this is stated only in a comment, never validated in `set_phantom_order_config`. If the value is off by an integer factor, every downstream price snapshot for that pair is silently scaled by the same factor, and this corrupted price feeds directly into the SDK's `PhantomSnapshotIntentQuoteStrategy`, which unprivileged users/solvers rely on to price real, fund-moving cross-chain intents.

### Finding Description
`set_phantom_order_config` NatSpec explicitly documents the invariant but the extrinsic performs no check on it: [1](#0-0) 

The struct definition repeats the warning in even stronger terms — "fails silently... will not revert. It will not warn." — yet, as with the `batchSettlement` NatSpec in the original report, nothing in code enforces it: [2](#0-1) 

`standard_amount` is used unmodified as the price-denominator both on-chain (as `PhantomOrderRegistered.standard_amount` and inside the commitment hash) and downstream by the indexer/SDK, which divides the median price by it to compute the actual quoted FX rate: [3](#0-2) [4](#0-3) 

Because `medianPrice / standardAmount` is the "denominator of the truth" for every quote served by `PhantomSnapshotIntentQuoteStrategy`, a governance operator who sets `standard_amount` to, say, `2 * 10^decimals` instead of `1 * 10^decimals` (an easy off-by-factor mistake, exactly the class of "forgot to follow the NatSpec" error the original report is about) will cause every `quote()` call served from that snapshot to be wrong by that same integer factor — permanently and silently, with no on-chain guard, until a human notices the drift.

### Impact Explanation
Unlike the source report's flow (which needs a compromised/forgetful admin acting directly on a rug-capable function), here the *unprivileged* impact is downstream and automatic: once the misconfiguration lands, **any** unprivileged user calling the public SDK quote path is served a mispriced quote and can place real orders (`IntentGatewayV2.placeOrder`) against it. Depending on the direction of the error, this either:
- causes users to systematically overpay/underpay solvers (fund loss for users), or
- allows a solver to structure fills that extract a systematic profit margin baked into the corrupted rate at the expense of the counterparty (unauthorized wealth transfer), functionally identical in shape to the "rug the old pool tokenholders" impact described in the seed report, since the loss stems purely from an undocumented-in-code invariant that is trusted to hold and silently doesn't.

### Likelihood Explanation
Low-to-moderate: it requires a governance operator to set an incorrect `standard_amount` (a plain data-entry mistake, not malicious intent — same likelihood class as the original report's "admin forgets to call `batchSettlement`"). Given `standard_amount` differs per token (6-decimal USDC vs 18-decimal DAI, etc.) and must be supplied per pair in a `BoundedVec` config call, this is a realistic operational hazard, and once misconfigured, exploitation by any ordinary user/solver is trivial and requires no special access.

### Recommendation
Validate `standard_amount` on-chain in `set_phantom_order_config` (and any future update entrypoint) against the actual on-chain decimals of `token_a` — e.g., look up `10^decimals(token_a)` via a registered token-metadata source and `ensure!(pair.standard_amount == expected, Error::<T>::InvalidStandardAmount)` — rather than relying solely on a doc comment, so a misconfiguration reverts at submission time instead of silently poisoning every downstream price feed and quote consumed by unprivileged users.

### Proof of Concept
1. Governance calls `intentsCoprocessor.setPhantomOrderConfig` with a pair `{token_a: USDC (6 decimals), token_b: DAI, standard_amount: 2_000_000}` (2 units instead of the required `1_000_000`) — no revert occurs, per `modules/pallets/intents-coprocessor/src/lib.rs:566-597`.
2. `on_initialize` generates the phantom order and emits `PhantomOrderRegistered { standard_amount: 2_000_000, ... }` (`lib.rs:831-849`); fillers bid against it, and the indexer aggregates `medianPrice` for that `standard_amount`.
3. Any user calls the SDK's intent-quote endpoint; `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot` computes `amountOut = netAmountIn * medianPrice / standardAmount` (`sdk/packages/sdk/src/protocols/intents/quote/phantomSnapshot.ts:83-101`) — since `standardAmount` is double what it should be, every returned quote is exactly half the correct rate.
4. The user places a real `placeOrder` at this quote via `IntentGatewayV2`; a solver fills it at the (correct) real market rate and pockets the difference — fund loss for the user, with no code path ever having checked the invariant the NatSpec demanded.

/// A single token pair the phantom generator probes for price and liquidity.
///
/// Read the note on [`standard_amount`](PhantomTokenPair::standard_amount) before you set this.
/// It is the one field that fails silently.
#[derive(Clone, Debug, Encode, Decode, DecodeWithMemTracking, TypeInfo, PartialEq, Eq)]
pub struct PhantomTokenPair {
	/// The input token being priced (tokenA). Quotes are expressed as how much `token_b`
	/// a filler will give for `standard_amount` of this token.
	pub token_a: H160,
	/// The output token (tokenB) the price is quoted in.
	pub token_b: H160,
	/// ┌─────────────────────────────────────────────────────────────────────────────────┐
	/// │  ⚠  EXACTLY ONE (1) UNIT OF THE INPUT TOKEN. NO MORE. NO LESS. NON-NEGOTIABLE.  ⚠  │
	/// └─────────────────────────────────────────────────────────────────────────────────┘
	///
	/// This MUST be **one whole unit of `token_a`, denominated in the token's smallest unit**
	/// — that is, `10^decimals(token_a)`:
	///   • 6-decimal USDC  →  `1_000_000`
	///   • 18-decimal DAI  →  `1_000_000_000_000_000_000`
	///
	/// WHY THERE IS ZERO WIGGLE ROOM:
	///   Every exchange rate the indexer publishes is `medianPrice / standard_amount`. This number
	///   is the DENOMINATOR OF THE TRUTH. Put `2` units here and every downstream rate is silently
	///   HALVED; put half a unit and every rate silently DOUBLES. It will not revert. It will not
	///   warn. It will simply poison every price snapshot for this pair with an integer-factor
	///   error until a human eventually notices the feed has drifted — and then has to backfill it.
	///
	/// So set it to one unit. `10^decimals(token_a)`. Not a round dollar. Not a "nice" number.
	/// Not two. Not a half. ONE. UNIT.
	pub standard_amount: u128,
}

	private quoteSnapshot(
		params: QuoteIntentParams,
		protocolFeeBps: bigint,
		snapshot: PhantomOrderPriceSnapshot,
	): PhantomSnapshotQuoteIntentResult {
		if (params.amountIn !== undefined) {
			const netAmountIn = deductProtocolFee(params.amountIn, protocolFeeBps)
			const amountOut = (netAmountIn * snapshot.medianPrice) / snapshot.standardAmount
			if (amountOut <= 0n) {
				throw new InvalidPhantomSnapshotError(snapshot.commitment, "quote rounds down to zero output")
			}
			return this.buildResult("EXACT_INPUT", params.amountIn, amountOut, protocolFeeBps, snapshot)
		}

		if (params.amountOut === undefined) throw new Error("Quote amount is missing after validation")
		const netAmountIn = divCeil(params.amountOut * snapshot.standardAmount, snapshot.medianPrice)
		const amountIn = grossUpForProtocolFee(netAmountIn, protocolFeeBps)
		return this.buildResult("EXACT_OUTPUT", amountIn, params.amountOut, protocolFeeBps, snapshot)
	}
