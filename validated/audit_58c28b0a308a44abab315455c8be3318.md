### Title
`advance_round_manually`'s payout attribution trusts an unauthenticated OP_RETURN in the transaction that happens to win the mempool race for the withdrawal UTXO - (File: `core/src/verifier.rs`, `core/src/operator.rs`)

### Summary
The binding the bridge relies on is: `payout_payer_operator_xonly_pk[withdrawal_idx] == the party that actually funded output 0 of the confirmed spend of that withdrawal UTXO`. This is never checked; `update_finalized_payouts` simply parses the OP_RETURN of whichever transaction is found on-chain spending the withdrawal UTXO, and `is_kickoff_malicious`/`validate_payer_is_operator` (which gates whether `advance_round_manually`/`handle_finalized_payout` ever credits a reimbursement) trust that value unconditionally.

### Finding Description
The equality being assumed is:
`withdrawals.payout_payer_operator_xonly_pk == xonly_pk of the operator who funded input 0 of the mined payout tx`

The payout transaction created by `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) has exactly one input — the user's withdrawal UTXO — spent with a single Schnorr key-spend signature (`set_p2tr_key_spend_witness`, line 434). The user's off-chain `in_signature` is a `SinglePlusAnyoneCanPay` signature (used throughout `core/src/operator.rs`, `core/src/rpc/aggregator.rs`), which cryptographically commits **only** to input 0 and output 0 (the user payout). It commits to nothing else: not the anchor output, and critically, not the OP_RETURN output that carries the fronting operator's x-only pubkey (`op_return_txout(...)` at line 418, output index 2).

Attribution of "who paid this withdrawal" is derived purely from parsing that unsigned OP_RETURN of whatever transaction is *actually observed on-chain* spending the withdrawal UTXO: [1](#0-0) [2](#0-1) 

Because the signature is `SIGHASH_SINGLE | ANYONECANPAY`, anyone who observes the honest operator's broadcast payout transaction in the mempool (or who reconstructs input 0 + output 0 independently, since the user's signature and outpoint are not secret to the operator alone) can build a competing transaction reusing exactly input 0 and output 0, adding their own fee-paying input, and substituting an arbitrary or unparsable OP_RETURN. If this competing transaction is mined first, `update_finalized_payouts` records the *attacker's* OP_RETURN as the payer: [3](#0-2) 

This attribution then flows into `is_kickoff_malicious`, which trusts `operator_xonly_pk` from the DB without re-deriving it from actual fund flow: [4](#0-3) 

and into `validate_payer_is_operator`/`get_next_txs_to_send`, whose branches ultimately call `advance_round_manually`/`handle_finalized_payout` to progress the real reimbursement path: [5](#0-4) [6](#0-5) 

None of the invoked guards (`is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`, `lc_proof_verifier`) verify that the xonly pubkey embedded in the OP_RETURN corresponds to whoever actually funded the withdrawal UTXO's value — they only check that a valid SPV/storage proof exists for whatever transaction happened to be mined, and that the embedded pubkey parses.

### Impact Explanation
Two outcomes are reachable by choosing the OP_RETURN payload of the race-winning transaction:
1. Attacker inserts a real operator B's (public) x-only pubkey instead of the true funder A's. B is now the party of record for this withdrawal in the `withdrawals` table. If B later submits a kickoff, `is_kickoff_malicious` will accept it (`operator_xonly_pk == kickoff_data.operator_xonly_pk`), letting B claim a reimbursement for a payout it never funded — Critical impact ("an operator reimbursed for a payout it never funded").
2. Attacker supplies an unparsable/missing OP_RETURN. `operator_xonly_pk` becomes `None`, and `is_kickoff_malicious` treats *any* subsequent kickoff for this withdrawal as malicious ("No operator xonly pk found... assuming malicious"), permanently blocking the true funder A from ever being reimbursed — Critical impact ("an honest operator permanently unable to be reimbursed").

The attack is repeatable per withdrawal and does not require compromising any key material: the attacker only needs to win a fee race on a transaction whose input/output pair they can freely observe and reuse. Blast radius scales with the number of withdrawals processed while an honest operator's payout is still unconfirmed.

### Likelihood Explanation
Preconditions: an honest operator must have broadcast a payout transaction that is not yet confirmed (mempool window), which happens on every normal withdrawal cycle. The attacker's cost is only the fee delta needed to get their replacement mined first (no protocol role, key share, or collateral required — consistent with the "unprivileged attacker" threat model). This is straightforward to execute given standard Bitcoin mempool visibility and fee bumping, making it highly feasible and repeatable across withdrawals/operators.

### Recommendation
Do not derive payout attribution from an unauthenticated OP_RETURN of whichever transaction wins the race for the withdrawal UTXO. Instead, bind attribution cryptographically to the actual signer/funder of the transaction, e.g., by requiring the OP_RETURN operator pubkey to be committed under the same signature that authorizes output 0 (extend the sighash to cover the OP_RETURN output), or by having the aggregator/verifiers record the pre-agreed operator identity for a withdrawal index at `withdraw()`-time (before broadcast) and rejecting any confirmed payout tx whose OP_RETURN does not match that pre-committed value rather than trusting whatever is observed on-chain post-hoc.

### Proof of Concept
```
cargo test -p clementine-core --test manual_reimbursement -- --nocapture
```
Test plan:
1. Run a deposit + `withdraw()` flow with operator A, capturing the resulting `payout_tx` (unconfirmed in mempool) whose OP_RETURN encodes A's xonly pubkey.
2. Construct `payout_tx_evil` reusing `payout_tx.input[0]` (witness intact, since `SIGHASH_SINGLE|ANYONECANPAY`) and `payout_tx.output[0]`, but with a new attacker-funded fee input and OP_RETURN encoding operator B's xonly pubkey (or a malformed OP_RETURN).
3. Broadcast and mine `payout_tx_evil` before `payout_tx`.
4. Assert `db.get_payout_txs_for_withdrawal_utxos` / `withdrawals.payout_payer_operator_xonly_pk` for this withdrawal index equals B's pubkey (or `NULL`), i.e., `payout_payer_operator_xonly_pk != A.xonly_pk` even though A funded the withdrawal — proving the equality `credited party == funder` is violated.
5. Assert that calling the reimbursement flow (`is_kickoff_malicious`/`get_next_txs_to_send`/`advance_round_manually`) for A now returns "malicious"/fails, while (in the B-pubkey variant) a kickoff constructed with B's `kickoff_data.operator_xonly_pk` passes `is_kickoff_malicious` despite B never having funded anything.
