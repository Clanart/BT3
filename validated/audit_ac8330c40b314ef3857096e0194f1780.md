## Title
Line-selection index reuse against a re-fetched working-directory diff can silently stage/commit different lines than the user reviewed - (File: `app/src/lib/git/apply.ts`)

### Summary
`Staking.finalizeStake()`'s bug class is: a per-user calculation is validated against one snapshot of shared state, but executed against a different (attacker-shifted) snapshot of that state, so the value that gets "locked in" for the victim no longer corresponds to what they intended. The closest reachable analog in GitHub Desktop is in the partial-commit ("select individual lines") pipeline: the line-selection bitmap the user builds while reviewing a diff is keyed to *absolute line indices of a specific diff snapshot*, but `applyPatchToIndex` re-fetches a fresh diff of the file from disk at staging time and blindly reapplies those same indices via `formatPatch`, per [1](#0-0)  and [2](#0-1) . If the file content on disk changes between the two diff snapshots, the indices silently point at different content, and the patch generated to stage into the index no longer matches the lines the user actually checked.

### Finding Description
The corrupted value is the mapping from `DiffSelection` (a `Set<number>` of absolute line indices, see `withRangeSelection`/`isSelected` in `app/src/models/diff/diff-selection.ts`) [3](#0-2)  to actual hunk lines.

The intended invariant is: "the lines a user visually selects are the exact lines that get staged/committed." Desktop enforces this only at *render* time — `updateChangesWorkingDirectoryDiff` in `app-store.ts` recomputes `selectableLines` from a freshly-fetched diff and explicitly acknowledges the diff "might have changed dramatically since last we loaded it," pruning selections that no longer exist [4](#0-3) . That reconciliation only happens while the Changes view is being refreshed for display, not at the moment of staging/committing.

At commit time, `_commitIncludedChanges` takes whatever `WorkingDirectoryFileChange` objects are currently in `state.changesState.workingDirectory.files` (with their existing `selection`) and passes them straight to `createCommit` → `stageFiles` [5](#0-4) . For any file with a partial selection, `stageFiles` calls `applyPatchToIndex(repository, file)` [6](#0-5) , which does **not** reuse the diff the user reviewed — it independently calls `getWorkingDirectoryDiff(repository, file)` again, right before formatting the patch [1](#0-0) .

`formatPatch` then walks the *new* diff's hunks and, for each line, asks `file.selection.isSelected(absoluteIndex)` — using indices computed against the *old* diff [2](#0-1) . There is no check that the new diff's hunk layout, line count, or content hash matches what the selection was built from; the code comment even flags this as a known soft spot ("The diff might have changed dramatically since last we loaded it") only in the UI-refresh path, not in the staging path.

Existing guards do not stop this:
- The UI-side reconciliation in `updateChangesWorkingDirectoryDiff` only trims out-of-range indices for *rendering*; it does not gate `_commitIncludedChanges`.
- `formatPatch` only throws if the resulting patch is completely empty (`!patch.length`) [7](#0-6)  — it has no way to detect "wrong but non-empty" line selection caused by index drift.
- Nothing hashes or fingerprints the diff between the time it was shown to the user and the time `applyPatchToIndex` re-reads it.

An attacker who controls repository content that can change on disk between when the user opens/reviews a file's diff and when they click "Commit" (e.g., via a git `clean`/`smudge` filter, a `.gitattributes`-driven text-conversion filter, or any tracked build/watch tooling triggered by opening the cloned repository) can shift line offsets in the working tree file so that the previously-computed line-index selection now maps onto unrelated content — additions, deletions, or context lines the user never reviewed — causing Desktop to silently stage and commit content the user did not select.

### Impact Explanation
This is a silent corruption of what the user commits: the resulting commit can contain code/lines the user explicitly deselected, or omit lines they selected, without any error or warning surfaced (since `formatPatch` only fails on a fully-empty patch). Because this happens inside the ordinary "select individual lines" partial-commit workflow that Desktop advertises as a precise, line-level control, a user could unknowingly commit and push attacker-influenced content while believing they reviewed and approved exactly what was included.

### Likelihood Explanation
Likelihood is **low-to-moderate**: it requires a window between the diff being displayed/selected and the commit being finalized, plus a mechanism for file content to change during that window (e.g., an on-disk filter/build step tied to the attacker's repository, or another process editing the file). Desktop does not run untrusted repository-supplied scripts automatically in most configurations, so the most realistic trigger is a legitimate tool (formatter/linter/watch-mode compiler) racing with the user's review — but the underlying architectural flaw (index reuse against a re-fetched diff with no consistency check) is present regardless of the exact trigger and is a real Desktop-side bug, not merely a hypothetical.

### Recommendation
- Have `applyPatchToIndex` accept and use the same `ITextDiff`/`ILargeTextDiff` object that was used to build the `DiffSelection` (thread it through from `_commitIncludedChanges`/`stageFiles`) instead of re-fetching a new diff from disk.
- If a fresh diff must be fetched for staging, validate that it is structurally equivalent to the diff the selection was computed against (e.g., compare hunk headers/line counts, or a content hash) before applying `formatPatch`; if it differs, abort the commit for that file and force the user to re-review.
- Surface an explicit error/warning to the user rather than silently applying a patch when selection/diff mismatch is detected, mirroring the "no changes" guard already present in `formatPatch`.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked text file so it has multiple hunks.
2. In the Changes view, select individual lines within a hunk (creating a `Partial` `DiffSelectionType` with specific absolute line indices) but do not commit yet.
3. Before pressing "Commit," cause the file on disk to change in a way that shifts line offsets without necessarily changing the file's overall shape enough to be obviously different in the truncated preview (e.g., a background formatter reflows the file, or in a controlled test simply overwrite the file directly via the filesystem while Desktop is idle, bypassing another `getStatus`/diff refresh).
4. Click "Commit." `applyPatchToIndex` calls `getWorkingDirectoryDiff` again and reuses the stale `DiffSelection` indices from step 2 (`app/src/lib/git/apply.ts:60`, `app/src/lib/patch-formatter.ts:143-158`).
5. Inspect the resulting commit with `git show`: it will contain lines that do not correspond to what was visually checked/unchecked in step 2, demonstrating silent corruption of the committed content.
