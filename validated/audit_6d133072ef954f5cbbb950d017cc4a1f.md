### Title
Identity key and identity nonce accepted by `SchnorrSignature::verify` enables signature forgery / unsigned-content acceptance - (File: crypto/schnorr/src/lib.rs)

### Summary
The libzypp CVE-2017-9269 bug class is "the key a signature is checked against is not pinned, so a downgrade to effectively unsigned content is accepted." In Serai, `SchnorrSignature::verify` and `SchnorrSignature::batch_statements` perform the check `R + c·A − s·G == 0` without rejecting the identity point for the public key `A` or the nonce commitment `R`. `Ciphersuite::read_G` only enforces canonical encoding and never excludes the identity, so a caller that reads a key or signature from untrusted bytes can be fed `(A = identity, R = identity, s = 0)`, which satisfies the verification equation for **any** challenge and any message — the cryptographic equivalent of accepting unsigned content.

### Finding Description
`SchnorrSignature::verify` computes `multiexp_vartime(batch_statements)` and checks the result is identity [1](#0-0) . `batch_statements` emits `[(1, R), (c, A), (−s, G)]`, so with `A = R = identity` and `s = 0` the sum is `0` regardless of `c`. `read_G` accepts the canonical identity encoding [2](#0-1) , and `SchnorrSignature::read` places no additional constraint [3](#0-2) . The same hole exists in `SchnorrPoK::verify` in the single-group DLEq (`crypto/dleq/src/schnorr.rs` shape, same formula `(-s)·G + R + hra·A`), and in `SchnorrAggregate::verify`, where `keys_and_challenges` keys are produced by `read_G` from caller-supplied signer IDs — a signer ID decoding to identity contributes a trivially forgeable `s = r` term [4](#0-3) .

### Impact Explanation
An unprivileged party who can cause bytes to be fed to `SchnorrSignature::read` / `SchnorrAggregate::read` / `read_G` and then to a `verify`/`verify_aggregate` call can produce a universally valid signature without any private key: choose `R` and `A` as the identity encodings and `s = 0`. Any verification path that does not pin the public key to a known-good key (exactly the CVE class: unpinned key → unsigned acceptance) is forfeit. In the FROST share-verification path, `verify_share` builds the same `batch_statements` from a deserialized `verification_share` [5](#0-4) , so a share derived from an identity verification share passes blame checks.

### Likelihood Explanation
Reachability requires a caller that accepts the public key (or a verification share / signer ID) from attacker-influenced input rather than a pinned value. `Validators::verify` does pin keys to the weight table [6](#0-5) , but `verify_aggregate` unwraps `read_G` on caller-provided signer lists and `ThresholdKeys`/`EncryptedMessage` deserialization paths pass group elements through `read_G` without identity rejection. The primitive itself is unconditionally forgeable for the identity key; exploitability depends on downstream key-pinning, mirroring the CVE exactly.

### Recommendation
Reject the identity element in `Ciphersuite::read_G` for group elements used as keys/nonces, or explicitly reject `A`/`R` identity inside `SchnorrSignature::verify`, `SchnorrAggregate::verify`, and `SchnorrPoK::verify` (e.g., `if public_key.is_identity().into() || self.R.is_identity().into() { return false }`). Since `read_G` is generic, a `read_G_nonzero`/`read_G_non_identity` helper applied at all verification entry points would be safer than changing `read_G` globally, since identity is a legitimate encoding in some arithmetic contexts.

### Proof of Concept
```rust
// crypto/schnorr — no secret key required
let identity = C::G::identity();
let sig = SchnorrSignature::<C> { R: identity, s: C::F::ZERO };
// For ANY challenge c and ANY message bound into c:
//   R + c*A - s*G = 0 + 0 - 0 = identity  => verifies
assert!(sig.verify(identity, arbitrary_challenge));
```
`identity` serializes canonically (e.g., all-zero compressed Ristretto encoding), so `SchnorrSignature::read` / `read_G` accept the forgery's bytes; the signature therefore validates an attacker-chosen message as if it were signed — unsigned content accepted under an unpinned identity key.

Uncertain/unverified: whether any single concrete production caller feeds a fully attacker-controlled public key into `verify` without pinning; I confirmed the primitive-level forgery and the identity-accepting `read_G`, but could not trace every `verify` call site's key provenance within the iteration budget.

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
  }

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
  }
