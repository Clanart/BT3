### Title
Process-lifetime lock of the global EVM coin decimals (`evmCoinInfo`) can desynchronize from the persisted keeper `EvmCoinInfo`, causing divergent decimal-scaling of the EVM gas coin across validators - (File: `x/vm/types/denom_config.go`, `x/vm/module.go`, `x/vm/keeper/coin_info.go`)

### Summary
This is the closest native analog to the pyUmbral finding: "operations inherit from a global configuration instead of an explicit, canonical, always-consistent source," which silently breaks downstream math (there, curve size; here, coin decimals used to scale every EVM balance/mint/burn operation).

### Finding Description
The EVM module keeps **two representations** of the coin's decimal configuration:

1. A **persisted, keeper-scoped** value, `EvmCoinInfo`, stored in the KV store and readable/writable via `Keeper.GetEvmCoinInfo` / `Keeper.SetEvmCoinInfo` [1](#0-0) , initially derived from bank denom metadata and module params in `LoadEvmCoinInfo`/`InitEvmCoinInfo` [2](#0-1) .

2. A **package-level global**, `evmCoinInfo`, used by essentially all deterministic decimal-scaling math in `x/vm/types` (`GetEVMCoinDecimals`, `ConvertAmountTo18Decimals*`, `ConvertBigIntFrom18DecimalsToLegacyDec`, `ConvertCoinsDenomToExtendedDenom`, and the `BankWrapper` mint/burn/balance conversions) [3](#0-2) [4](#0-3) [5](#0-4) .

The global is populated exactly **once per process lifetime** through a `sync.Once`-guarded call in `PreBlock`:
```go
func (am AppModule) PreBlock(...) {
    coinInfo := am.keeper.GetEvmCoinInfo(ctx)
    am.initializer.Do(func() {
        SetGlobalConfigVariables(coinInfo)
    })
    ...
}
``` [6](#0-5) 

`SetGlobalConfigVariables` calls `EVMConfigurator.Configure()`, which in turn calls `setEVMCoinInfo`. Critically, `setEVMCoinInfo` **refuses to run a second time** in the same process:
```go
func setEVMCoinInfo(eci EvmCoinInfo) error {
    if evmCoinInfo != nil {
        return errors.New("EVM coin info already set")
    }
    ...
}
``` [7](#0-6) 

The keeper-persisted `EvmCoinInfo`, however, is **mutable** at any time via `Keeper.SetEvmCoinInfo` and is meant to be updated (the migration docs explicitly describe upgrade handlers that call `InitEvmCoinInfo`/change `ExtendedDenomOptions` for non-18-decimal chains) [8](#0-7) .

Because the in-memory global is frozen at first `PreBlock` execution and the on-disk value is not, any process that is **already running** when the persisted `EvmCoinInfo`/denom metadata/`ExtendedDenomOptions` changes (e.g., via an upgrade handler or parameter update) keeps operating with the **stale decimals value** for the remainder of its process life, while a **freshly started/restarted node** (or a new validator syncing from genesis+upgrades) will read the **new** value on its first `PreBlock` call and lock that in instead. This is precisely the pyUmbral bug shape: "a global configuration is inherited implicitly instead of being canonically and consistently sourced," and it silently corrupts arithmetic (there: curve size for byte-length checks and pubkey derivation; here: the decimal conversion factor for every EVM-denom mint, burn, balance read/write, and 18-decimal scaling operation).

### Impact Explanation
`GetEVMCoinDecimals()` (backed by the frozen global) drives `ConvertAmountTo18DecimalsBigInt`, `ConvertBigIntFrom18DecimalsToLegacyDec`, `ConvertCoinsDenomToExtendedDenom`, and `BankWrapper.MintAmountToAccount` / `BurnAmountFromAccount` / `GetBalance` [5](#0-4) . These are used on every EVM state transition that touches the native gas coin (EVM balance reads, `msg.value` transfers, gas fee debits, mint/burn during conversions). If two sets of validators in the same network are running with different frozen decimal values for the EVM denom — one set having initialized their process before a legitimate decimals/`ExtendedDenomOptions` change and one set after — they will compute **different converted amounts** for identical transactions (e.g., a transfer of `X` extended-denom units will be scaled to a different 18-decimals EVM balance, and mint/burn amounts during coin conversions will differ by orders of magnitude equal to the decimal exponent difference). This directly produces:
- Divergent EVM/bank balances and mint/burn accounting between validators for identical blocks (irreversible accounting corruption of spendable value), and
- AppHash divergence / consensus fork, since state root computation depends on these balances, which is a Critical, in-scope impact under this repo's chain-halt/consensus-fork gate.

### Likelihood Explanation
The trigger does not require an attacker to craft anything malicious in a transaction; ordinary transaction processing exposes the divergence once the decimals/`ExtendedDenomOptions` configuration is legitimately changed while some validators keep long-running processes and others restart (a routine operational event: rolling restarts, new validator joining, or state-sync). The precondition (a change to the persisted `EvmCoinInfo`/decimals configuration after genesis) is realistic and is explicitly anticipated by the project's own migration documentation, which instructs operators to update `ExtendedDenomOptions`/denom metadata for non-18-decimal chains via upgrade handlers — meaning this is a supported, expected operational path, not a hypothetical misconfiguration. I was not able to fully verify within the available tool budget whether `Keeper.SetEvmCoinInfo` is invoked anywhere besides genesis/`InitEvmCoinInfo` in the current codebase snapshot (e.g., from an `MsgUpdateParams` handler) — this should be confirmed by a full repository review to establish exactly which code paths can mutate the persisted value post-genesis and how long-lived validator processes are expected to pick up the change without a restart. If no other runtime code path ever mutates `EvmCoinInfo` after genesis and no upgrade ever changes it while nodes are live, the practical likelihood is lower and the issue would be latent rather than actively exploitable.

### Recommendation
- Make the global EVM coin decimals/denom configuration re-derive from the canonical persisted keeper state on every use (or at least every block), rather than being locked by a `sync.Once` for the lifetime of the process.
- If a cached/global copy is kept for performance, invalidate and refresh it whenever `Keeper.SetEvmCoinInfo` (or the underlying params/denom metadata) changes, ideally within the same state-machine transition, so all nodes converge on the same value deterministically based on chain state rather than "whatever was in memory when this process first ran `PreBlock`."
- Define the EVM coin decimals/denom in a single canonical, consensus-state-derived location (the keeper store) and eliminate the redundant package-level global that can desynchronize from it — mirroring the pyUmbral recommendation to "define which curve the system is using in a single, canonical location" and make illegal (inconsistent) states unrepresentable.
- Add an explicit runtime invariant/check (e.g., in `BeginBlock` or an ante handler) that compares the in-memory decimals value against the keeper-stored value and halts/errors loudly on mismatch instead of silently using stale data.

### Proof of Concept
Conceptual reproduction (not fully exercised due to read-only/ask-mode constraints):
1. Start a validator node; its first `PreBlock` call locks `evmCoinInfo` (e.g., decimals = 18) via the `sync.Once` in `x/vm/module.go`.
2. Apply a legitimate change to the EVM denom's decimals/`ExtendedDenomOptions` in the persisted `EvmCoinInfo` (e.g., via an upgrade handler calling `Keeper.SetEvmCoinInfo`, consistent with the documented migration path in `docs/migrations/v0.4.0_to_v0.5.0_UNRELEASED.md`), without restarting the already-running validator process.
3. Restart a different validator (or bring up a new one) after the change; its first `PreBlock` call locks in the *new* decimals value.
4. Submit an ordinary EVM transaction involving the native coin (transfer, gas fee, or ERC20↔coin conversion). The original (never-restarted) validator computes converted/scaled amounts using the old decimals; the restarted validator computes them using the new decimals.
5. The resulting balances/mint-burn amounts differ between the two validators for the same transaction and block, producing an AppHash mismatch / consensus fork.

Because tool access ended before I could trace every call site of `Keeper.SetEvmCoinInfo` across `x/vm/keeper/msg_server.go` and `evmd/upgrades.go`, the exact runtime trigger (governance param update vs. upgrade handler only) should be confirmed with a full codebase pass before treating this as launch-ready; the structural flaw (a `sync.Once`-frozen global mirroring a mutable persisted value) is nonetheless clearly present and directly analogous to the reported pyUmbral defect class.

// LoadEvmCoinInfo load EvmCoinInfo from bank denom metadata
func (k Keeper) LoadEvmCoinInfo(ctx sdk.Context) (types.EvmCoinInfo, error) {
	var decimals types.Decimals

	params := k.GetParams(ctx)
	evmDenomMetadata, found := k.bankWrapper.GetDenomMetaData(ctx, params.EvmDenom)
	if !found {
		return types.EvmCoinInfo{}, fmt.Errorf("denom metadata %s could not be found", params.EvmDenom)
	}

	for _, denomUnit := range evmDenomMetadata.DenomUnits {
		if denomUnit.Denom == evmDenomMetadata.Display {
			decimals = types.Decimals(denomUnit.Exponent)
		}
	}

	var extendedDenom string
	if decimals == 18 {
		extendedDenom = params.EvmDenom
	} else {
		if params.ExtendedDenomOptions == nil {
			return types.EvmCoinInfo{}, fmt.Errorf("extended denom options cannot be nil for non-18-decimal chains")
		}
		extendedDenom = params.ExtendedDenomOptions.ExtendedDenom
	}

	return types.EvmCoinInfo{
		Denom:         params.EvmDenom,
		ExtendedDenom: extendedDenom,
		DisplayDenom:  evmDenomMetadata.Display,
		Decimals:      decimals.Uint32(),
	}, nil
}

// InitEvmCoinInfo load EvmCoinInfo from bank denom metadata and store it in the module
func (k Keeper) InitEvmCoinInfo(ctx sdk.Context) error {
	coinInfo, err := k.LoadEvmCoinInfo(ctx)
	if err != nil {
		return err
	}
	return k.SetEvmCoinInfo(ctx, coinInfo)
}

// GetEvmCoinInfo returns the EVM Coin Info stored in the module
func (k Keeper) GetEvmCoinInfo(ctx sdk.Context) (coinInfo types.EvmCoinInfo) {
	store := ctx.KVStore(k.storeKey)
	bz := store.Get(types.KeyPrefixEvmCoinInfo)
	if bz == nil {
		return k.defaultEvmCoinInfo
	}
	k.cdc.MustUnmarshal(bz, &coinInfo)
	return
}

// setEVMCoinInfo allows to define denom and decimals of the coin used in the EVM.
func setEVMCoinInfo(eci EvmCoinInfo) error {
	if evmCoinInfo != nil {
		return errors.New("EVM coin info already set")
	}

	if Decimals(eci.Decimals) == EighteenDecimals {
		if eci.Denom != eci.ExtendedDenom {
			return errors.New("EVM coin denom and extended denom must be the same for 18 decimals")
		}
	}

	evmCoinInfo = new(EvmCoinInfo)

	if err := setEVMCoinDenom(eci.Denom); err != nil {
		return err
	}
	if err := setEVMCoinExtendedDenom(eci.ExtendedDenom); err != nil {
		return err
	}
	if err := setDisplayDenom(eci.DisplayDenom); err != nil {
		return err
	}
	return setEVMCoinDecimals(Decimals(eci.Decimals))
}

func ConvertAmountTo18DecimalsBigInt(amt *big.Int) *big.Int {
	evmCoinDecimal := GetEVMCoinDecimals()

// ConvertAmountTo18Decimals256Int convert the given amount into a 18 decimals

func ConvertAmountTo18Decimals256Int(amt *uint256.Int) *uint256.Int {
	evmCoinDecimal := GetEVMCoinDecimals()

	return new(uint256.Int).Mul(amt, uint256.NewInt(evmCoinDecimal.ConversionFactor().Uint64()))
}

// ConvertBigIntFrom18DecimalsToLegacyDec converts the given amount into a LegacyDec

	evmCoinDecimal := GetEVMCoinDecimals()

// MintAmountToAccount converts the given amount into the evm coin scaling
// the amount to the original decimals, then mints that amount to the provided account.
func (w BankWrapper) MintAmountToAccount(ctx context.Context, recipientAddr sdk.AccAddress, amt *big.Int) error {
	coin := sdk.Coin{Denom: types.GetEVMCoinDenom(), Amount: sdkmath.NewIntFromBigInt(amt)}

	convertedCoin, err := types.ConvertEvmCoinDenomToExtendedDenom(coin)
	if err != nil {
		return errors.Wrap(err, "failed to mint coin to account in bank wrapper")
	}

	coinsToMint := sdk.Coins{convertedCoin}
	if err := w.MintCoins(ctx, types.ModuleName, coinsToMint); err != nil {
		return errors.Wrap(err, "failed to mint coins to account in bank wrapper")
	}

	return w.BankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, recipientAddr, coinsToMint)
}

// BurnAmountFromAccount converts the given amount into the evm coin scaling
// the amount to the original decimals, then burns that quantity from the provided account.
func (w BankWrapper) BurnAmountFromAccount(ctx context.Context, account sdk.AccAddress, amt *big.Int) error {
	coin := sdk.Coin{Denom: types.GetEVMCoinDenom(), Amount: sdkmath.NewIntFromBigInt(amt)}

	convertedCoin, err := types.ConvertEvmCoinDenomToExtendedDenom(coin)
	if err != nil {
		return errors.Wrap(err, "failed to burn coins from account in bank wrapper")
	}

	coinsToBurn := sdk.Coins{convertedCoin}

	if err := w.BankKeeper.SendCoinsFromAccountToModule(ctx, account, types.ModuleName, coinsToBurn); err != nil {
		return errors.Wrap(err, "failed to burn coins from account in bank wrapper")
	}
	return w.BurnCoins(ctx, types.ModuleName, coinsToBurn)
}
