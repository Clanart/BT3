### Title
`ThresholdKeys::read` accepts attacker-supplied params/shares with no consistency check between `secret_share`, `verification_shares`, and the derived `group_key` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation variant, the `secret_share`, and `n` verification shares entirely from the input byte stream, then calls `ThresholdKeys::new`, which derives `group_key` solely as the interpolation of `verification_shares[1..=t]` without ever checking that `secret_share * G == verification_shares[i]` or that the shares lie on a common polynomial. A crafted serialization therefore produces a "valid" `ThresholdKeys` whose group key and secret share are semantically unrelated. This is the Serai analog of CVE-2023-24531: values embedded in a serialized structure are emitted/re-interpreted without sanitization, producing state that is later treated as authoritative key material.

### Finding Description
In `ThresholdKeys::read`, `t`, `n`, and `i` come directly from the reader; `n` controls how many `read_G` calls are performed and the shares are placed into a `HashMap` keyed `1..=n` (`crypto/dkg/src/lib.rs` lines 591–623). `ThresholdKeys::new` only checks that exactly `n` shares exist and indexes `<= n` (lines 355–365), then computes `group_key` from `verification_shares[1..=t]` (lines 376–378). No verification ties the deserialized `secret_share` to `verification_shares[i]`.

The codebase itself acknowledges this gap: `AlgorithmSignatureMachine::complete` comments that "the only known way to cause this... is to deserialize a semantically invalid FrostKeys" (`crypto/frost/src/sign.rs` lines 491–494), yet `read` performs no validation to prevent reaching that state. Additionally, `ThresholdView::secret_share` adds `offset` to `included[0]` unconditionally on `i == included[0]` (lines 518–521), compounding semantic inconsistency when the deserialized view is used.

### Impact Explanation
If untrusted bytes reach `ThresholdKeys::read` (e.g., key blobs relayed during reshare/recovery/promotion flows, or any channel where serialized keys cross a trust boundary), an attacker supplies `secret_share = s_a` and verification shares encoding a group key `Y_b = b·G` with `s_a * G ≠ verification_shares[i]`. The victim then:

- Reports `group_key() == Y_b` as the multisig key — an attacker-known key if they set the shares consistently with `b`, letting the attacker spend any funds sent to it.
- Signs with an unrelated share, producing either unspendable outputs ("funds received that are not spendable") or signatures that fail `algorithm.verify` and trigger the `InternalError` path, or worse, a share consistent with a *different* signing set than the group key implies.

### Likelihood Explanation
Exploitation requires the attacker to control bytes fed to `ThresholdKeys::read`. In the in-repo usage (`processor/src/key_gen.rs::read_keys`) the bytes come from local storage, so remote reachability is limited in the default processor deployment; however the API is public and explicitly documented as usable for serialized keys, and the DKG ecosystem (`promote`, `recovery`, `dealer` modules) is designed around exchanging share material. The check is absent, so any integrator that imports key material over an unauthenticated channel is vulnerable. Given the criticality of accepting a key whose group key the attacker fully controls, this is a High-severity deserialization-of-untrusted-data issue.

### Recommendation
In `ThresholdKeys::new` (or at the end of `read`), verify `C::generator() * secret_share == verification_shares[i]` after interpolation-independent scaling, and for `Interpolation::Constant(c)` verify `c` reproduces the verification shares (`sum c_j * i^j * G == verification_shares[i]`). Reject the blob if the secret share does not match its verification share.

### Proof of Concept
```rust
// crypto/dkg/src/lib.rs - conceptual PoC for C = Ristretto
let mut buf = vec![];
// C::ID len + ID, then t=2, n=2, i=1
buf.extend(2u16.to_le_bytes()); buf.extend(2u16.to_le_bytes()); buf.extend(1u16.to_le_bytes());
buf.push(1); // Lagrange
// secret_share = 5
buf.extend((Scalar::from(5u64)).to_bytes());
// verification_shares: attacker-chosen, consistent with a DIFFERENT secret b=9
buf.extend((RistrettoPoint::generator() * Scalar::from(9u64)).to_bytes());
buf.extend((RistrettoPoint::generator() * Scalar::from(7u64)).to_bytes());

let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap(); // succeeds today
// group_key is derived from shares for secret 9, while our secret_share is 5
// -> keys.original_verification_share(1) != generator() * keys.original_secret_share()
// Signing proceeds against group_key of the attacker's key; blame/complete hits InternalError
// or the produced address is spendable only by the attacker.
```
Root cause: `crypto/dkg/src/lib.rs` `ThresholdKeys::read` (lines 574–632) and `ThresholdKeys::new` (lines 349–391) never bind `secret_share` to `verification_shares`; see also the acknowledgement in `crypto/frost/src/sign.rs` lines 491–494.
