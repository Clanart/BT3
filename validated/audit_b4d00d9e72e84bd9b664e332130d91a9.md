### Title
Attacker-controlled `n` in `ThresholdKeys::read` triggers unbounded pre-allocation before any parameter validation - (File: crypto/dkg/src/lib.rs)

### Summary
The ImageMagick advisory (CWE-400/CWE-770) describes a missing resource-limit check on attacker-influenced input: a declared list length is trusted without being bounded, letting a small input force a disproportionate allocation. The same class exists in `ThresholdKeys::read`, which is one of the explicitly in-scope deserializers for untrusted bytes. It reads the participant count `n` directly from the byte stream and uses it as a `Vec::with_capacity` bound and as a deserialization loop bound *before* `ThresholdParams::new` validates `t`, `n`, and `i`.

### Finding Description
`ThresholdKeys::read` parses `(t, n, i)` as raw `u16`s at `crypto/dkg/src/lib.rs:591-602`, then, when the interpolation tag selects `Interpolation::Constant`, executes `Vec::with_capacity(usize::from(n))` at `crypto/dkg/src/lib.rs:607-613`. It also loops `n` times reading verification shares into a `HashMap` at `crypto/dkg/src/lib.rs:620-623`. Only afterwards does `ThresholdParams::new(t, n, i)` run at `crypto/dkg/src/lib.rs:625-626`, meaning `n` is consumed as a resource bound while still fully attacker-controlled. A handful of bytes (curve ID + 3 `u16`s + interpolation tag `0x00`) causes an immediate allocation of up to 65,535 `C::F` elements (~2 MiB for a 32-byte scalar, before `Option`/repr overhead), plus capacity for 65,535 `HashMap` entries. There is no cap relating `n` to remaining input length or to any sane protocol maximum — the exact "missing check on a length field" bug from the advisory.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (e.g., keys/preprocess material relayed during multisig or DKG recovery flows) achieves a large memory-amplification primitive: each ~10-byte message forces ~2 MiB of heap allocation plus the `read_F`/`read_G` loop work, and the call can be repeated indefinitely. This is uncontrolled resource consumption (CWE-770) leading to process memory exhaustion — the same availability impact class as the reference advisory, rated Medium.

### Likelihood Explanation
Reachability is conditional: it requires an attacker to get `ThresholdKeys::read` invoked on bytes they control. The prompt's threat model explicitly lists `ThresholdKeys::read` as an accepted untrusted-bytes sink, and DKG/multisig deployments deserialize key material received over the network. The allocation itself is guaranteed once reached — no validation precedes `Vec::with_capacity`. The 16-bit `n` bounds each single allocation, so exploitation requires repeated calls rather than one message, keeping this at Medium rather than High.

### Recommendation
Validate `t`, `n`, `i` with `ThresholdParams::new` *before* any allocation or bounded loop, reject `n` values inconsistent with the actual remaining input length, and consider reading into the `Vec` incrementally (push on successful `read_F`) instead of `with_capacity(n)` so a truncated input cannot reserve capacity for elements that never arrive.

### Proof of Concept
```rust
// crypto/dkg: ThresholdKeys::read trusts the serialized `n` before validation
let mut buf = vec![];
buf.extend(&(C::ID.len() as u32).to_le_bytes()); // id_len
buf.extend(C::ID);                             // id
buf.extend(&1u16.to_le_bytes());               // t = 1
buf.extend(&u16::MAX.to_le_bytes());           // n = 65535 (attacker-controlled)
buf.extend(&1u16.to_le_bytes());               // i = 1
buf.push(0);                                   // Interpolation::Constant
// Vec::with_capacity(65535) for C::F executes here, ~2 MiB allocated
// before ThresholdParams::new ever runs; loop then fails on read_F,
// but the capacity was already reserved. Repeat to exhaust memory.
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
```
