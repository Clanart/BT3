### Title
Automatic silent rewrite of a repository's local git remote URL based on an unverified GitHub API `clone_url` value - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Sherlock report's broken invariant is: a piece of state (`_listing`) that should have been retired/deleted when superseded by a new authoritative state is instead left in place, and a later, unrelated action causes the stale value to be treated as valid again, silently redirecting funds. The closest analog in GitHub Desktop is `updateRemoteUrl()`, which takes a value fetched from the GitHub API (`apiRepo.clone_url`) and, based on a set of heuristics rather than explicit user consent, silently overwrites the `origin` remote URL used for every future `git push`/`git fetch`. There is no mapping "deletion," but the same class of bug applies: an externally-supplied value (API response) is trusted to mutate a security-relevant piece of local state (the remote URL that determines where the user's code goes) without confirmation, and the existing guard (`remoteUrlUnchanged`) is derived from previously cached API data rather than from anything the user actively re-verified.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` every time Desktop refreshes a repository's GitHub association (e.g. on repository selection / account sign-in refresh): [1](#0-0) 

```
if (repository.gitHubRepository) {
  const gitStore = this.gitStoreCache.get(repository)
  await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
}
```

The function itself: [2](#0-1) 

It reads:
- `remoteUrl` – the user's currently configured `origin` URL,
- `updatedRemoteUrl = apiRepo.clone_url` – a value returned by the GitHub API for the matched owner/name,
- `remoteUrlUnchanged` – true if the *currently configured* remote still equals the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't manually diverged from what Desktop last wrote),
- `protocolsMatch` – true if the URL scheme (https vs ssh) is unchanged.

If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, Desktop calls `gitStore.setRemoteURL(...)` and **silently rewrites `origin` to `apiRepo.clone_url`, with no user prompt, confirmation dialog, or diff shown**.

The comment in the caller explicitly acknowledges the team never fully worked out invalidation semantics for this association: [3](#0-2) 

```
// TODO: We currently never clear GitHub repository associations (see
// https://github.com/desktop/desktop/issues/1144). So we can bail early at
// this point.
```

This is structurally the same shape as the Sherlock bug: a cached association (`_listing` / `gitHubRepository.cloneURL`) is used as the basis for deciding whether a downstream action (fill listing / rewrite remote) is safe, but the association is never invalidated when the underlying real-world object changes ownership/identity (protected listing created / repository renamed or transferred). The "guard" (`_isLiquidation`/`oldListing.owner != address(0)` in the original bug, `remoteUrlUnchanged` here) only checks a locally cached snapshot, not the current authoritative truth, so a change in the upstream object (GitHub API's `clone_url`) can silently take effect through a path the user did not knowingly trigger.

### Impact Explanation
If a tracked repository is renamed, transferred, or its identity otherwise changes on the GitHub side (or a compromised/incorrect GHES endpoint returns a different `clone_url` for the same owner/name pair the user is tracking), Desktop will automatically update the local `origin` remote to point at the new URL the next time the repository is refreshed — with no user visibility into the change. Because `origin` is the destination for `git push`, this can silently redirect where a user's future commits are pushed, matching the "silent corruption of what the user commits or pushes" impact category. It can also affect `git fetch`, causing the user to unknowingly pull code from a different remote than the one they explicitly configured, without ever seeing a warning that their remote configuration changed.

### Likelihood Explanation
The rewrite path is exercised automatically as part of normal application flow (`repositoryWithRefreshedGitHubRepository`, triggered by repository selection / account refresh), not by any unusual user action, and the value driving the rewrite (`apiRepo.clone_url`) originates from the GitHub API response for the matched repository — an object the attacker can influence in scenarios such as repository renames/ownership changes or a malicious/compromised GHES endpoint. However, the specific conditions (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`) narrow the exploitable window to cases where the user has not manually customized their remote away from what Desktop last recorded, which somewhat limits — but does not eliminate — the practical likelihood.

### Recommendation
Do not silently rewrite a locally configured remote URL based on GitHub API data. At minimum:
- Surface a confirmation prompt/banner to the user before changing `origin` (similar to how `RepositorySettings` already lets users explicitly edit the remote URL), showing old vs. new URL.
- Re-validate repository identity (e.g., compare stable repository `id`, not just owner/name path) before trusting a new `clone_url`, so a same-named-but-different repository cannot silently take over the association.
- Track explicit invalidation of the `gitHubRepository` association when the underlying `id` changes rather than relying on the "unchanged since last cached" heuristic.

### Proof of Concept
Not independently reproducible with certainty from static analysis alone — reproducing this requires controlling or simulating a GitHub API response (`clone_url`) for a repository/owner-name pair that a Desktop user already has cloned and associated, which the index does not let me fully verify end-to-end (e.g., exact preconditions under which `api.fetchRepository(owner, name)` would return a differing `clone_url` for a previously matched repository, and whether GitHub's API/redirect behavior on rename would produce the specific combination `protocolsMatch && remoteUrlUnchanged && !urlsMatch`). This would need to be validated in a running Desktop instance with a controllable GitHub Enterprise/API endpoint or a renamed/transferred test repository — a task suited for a Devin session with full repo/test access rather than static code review alone.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```
