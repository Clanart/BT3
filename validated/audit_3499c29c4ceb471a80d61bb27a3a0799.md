## Title
Lack of Timestamp Freshness Verification in App Proxy Signature Verification Enables Signed Request Replay - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates that an incoming app-proxy request's HMAC `signature` matches the signed query parameters (including `shop`, `path_prefix`, and `timestamp`), but it never checks that the `timestamp` parameter is actually recent. This mirrors the reported oracle bug class: data that carries a freshness indicator (a timestamp) is consumed without ever validating that indicator, so a validly-signed-but-stale payload is accepted indefinitely.

### Finding Description
Shopify signs app-proxy requests by including a `timestamp` query parameter as part of the HMAC-signed payload, specifically so that host applications can reject old/replayed requests. `query_string_valid?` computes the expected signature over all query params (which includes `timestamp`) and does a `secure_compare` against the supplied `signature`: [1](#0-0) 

The `timestamp` value is treated purely as signed payload material used to compute/verify the HMAC — it is never extracted and compared against the current time or any freshness threshold. Because the HMAC secret is static and long-lived, any query string (including the `timestamp`) that was ever validly signed by Shopify for this app remains verifiable forever. This is analogous to `getOraclePrice`/`getCollateralExchangeInfo` in the referenced report using `NodeOutput.Data`'s price without checking its timestamp against a freshness threshold.

### Impact Explanation
An attacker who obtains a previously-valid, fully-signed app-proxy query string (e.g., from browser history, shared links, proxy/CDN logs, Referer headers, or a compromised intermediary) can replay that exact request indefinitely. Since `AppProxyVerification` is the only gate protecting app-proxy actions (`before_action :verify_proxy_request`), and app-proxy requests are typically used to represent authenticated/attributed storefront requests to the app, an old captured request can be replayed to invoke proxy endpoints as if it were a fresh, legitimate Shopify-forwarded request. Severity is Medium: this doesn't directly leak merchant access tokens, but permits a forged/replayed signed request to be accepted well beyond its intended validity window, undermining a core anti-replay assumption of the app-proxy signing scheme.

### Likelihood Explanation
Likelihood is Medium: exploitation requires an attacker to first capture one valid signed app-proxy query string, which can leak via logs, browser history/screenshots, shared URLs, or man-in-the-middle on HTTP-adjacent infrastructure (e.g., URL leaking through Referer to third-party resources on the proxied page). No secret material or privileged access is required beyond obtaining that one URL, and it can be replayed at will since no expiry is ever enforced by the gem.

### Recommendation
Add explicit freshness validation in `query_string_valid?` (or an additional `before_action`) in `lib/shopify_app/controller_concerns/app_proxy_verification.rb`:
- Extract `timestamp` from the query hash before/while validating the signature.
- Reject the request if `timestamp` is missing, malformed, or older than a configurable threshold (e.g., a few minutes) relative to `Time.now.to_i`.
- Apply the same pattern to any other verification module in the gem that consumes a Shopify-provided timestamp as signed data without checking staleness.

### Proof of Concept
1. Configure an app with `ShopifyApp::AppProxyVerification` on a controller action.
2. Capture one legitimately-signed app-proxy request URL, e.g. `?shop=store.myshopify.com&path_prefix=/apps/my-app&timestamp=1466106083&signature=<valid-hmac>` (this is exactly the fixture used in the gem's own tests, showing the signature stays valid regardless of how old the timestamp is): [2](#0-1) 
3. Replay that identical URL/query string at any point in the future (days, months, years later). Because `query_string_valid?` never checks `timestamp` freshness, `secure_compare` still succeeds and the request passes `verify_proxy_request`, granting the same access as when the request was originally issued.

```ruby
    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
