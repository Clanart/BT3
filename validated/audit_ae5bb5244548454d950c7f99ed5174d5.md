### Title
Unauthenticated `X-Shopify-Shop-Domain` header used as shop identity for webhook job dispatch enables cross-shop webhook spoofing - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#shop_domain` reads the shop identity for an incoming webhook directly from the `HTTP_X_SHOPIFY_SHOP_DOMAIN` request header, while `verify_request` only HMAC-validates the raw request body [1](#0-0) . Because the header is not part of the HMAC computation, its value can be freely set by anyone submitting a POST to the webhook endpoint, as long as they can present a body+HMAC pair that is valid for the shared app secret.

### Finding Description
`hmac_valid?` computes the HMAC solely over `request.raw_post` using the app's `ShopifyApp.configuration.secret` (and `old_secret`) — the same secret is shared by the app across every installed shop, it is not shop-specific [2](#0-1) . `verify_request` only checks this body HMAC before allowing the request through [3](#0-2) , and `shop_domain` is derived independently from the unauthenticated header [4](#0-3) .

This documented, first-class pattern is explicitly recommended for custom webhook controllers: `shop_domain` is passed straight into a background job as the target shop for that webhook's side effects [5](#0-4) . Generated job templates then use this attacker-influenceable `shop_domain` to look up and act on a specific `Shop` record — e.g. destroying it (`AppUninstalledJob`) or redacting it (`ShopRedactJob`) — with no secondary binding back to the HMAC-signed content [6](#0-5) [7](#0-6) .

This is the same bug class as the reported `blockBuilderBLSKeyToAddress[]` issue: a value that is treated as an authoritative identity/ownership key (there, the BLS key → provider address mapping; here, the shop-domain header → shop record mapping) is populated/consumed without cryptographically binding it to the entity performing the privileged action, allowing any party who can obtain one valid signed payload for the shared secret to redirect the "who does this apply to" resolution to an arbitrary victim.

### Impact Explanation
Because the app secret is shared across all shops installed on the app (not shop-specific), any entity that can install the public app on a shop they control (or has otherwise captured one legitimate webhook body+HMAC pair, e.g. by triggering an event on their own store) can replay that exact `raw_post`/HMAC while substituting an arbitrary victim shop's domain in the `X-Shopify-Shop-Domain` header. Depending on which webhook/job is wired this way, this can cause cross-shop state corruption, spurious app-uninstalled/redact processing for a victim shop's data, or a job silently operating against a domain that does not correspond to the actual signed source — a cross-shop confused-deputy condition matching the report's "loss of funds/cross-identity" impact class translated to data integrity/authorization scope here.

### Likelihood Explanation
High relative to effort: no secret leak is required beyond having (or capturing) any single valid webhook body/HMAC for the app, which any merchant using a public instance of the app can obtain by simply triggering an event in their own store. Forging the header costs nothing beyond a normal HTTP request.

### Recommendation
Never trust `X-Shopify-Shop-Domain` (or any other webhook header) as the authoritative shop identity. Instead, derive the shop from data that is itself covered by the HMAC (i.e., from the verified JSON body / the `ShopifyAPI::Webhooks::Request` object's parsed payload, which Shopify includes shop context in), or independently verify that the header value matches a shop actually associated with the currently active webhook subscription/session before dispatching a job that performs privileged, shop-scoped actions.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook-worthy event (e.g., updates a cart) on their own shop, capturing the raw POST body and its valid `X-Shopify-Hmac-Sha256` value sent by Shopify to the app's webhook endpoint.
3. Attacker resends this exact `raw_post`/HMAC pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `hmac_valid?` passes because it only checks `raw_post` against the shared app secret [8](#0-7) .
5. The custom/generated controller/job reads `shop_domain` from the spoofed header and performs the webhook's associated action (e.g., `Shop.find_by(shopify_domain: shop_domain)` then destructive processing) against `victim-shop.myshopify.com` instead of the actual originating shop [9](#0-8) .

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end

```text
class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
```
