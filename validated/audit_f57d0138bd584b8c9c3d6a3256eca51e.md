### Title
Malicious FROST signer can crash every co-signer by supplying nonce commitments that sum to the point at infinity — (`File: networks/bitcoin/src/crypto.rs`)

### Summary
The BIP-340 `Hram` implementation in `bitcoin-serai` panics when the aggregate nonce point `R` (or the group key `A`) is the point at infinity: `x()` calls `.expect("point at infinity")` on `encoded.x()`. A participant in a `TransactionSignMachine`/`AlgorithmSignMachine` signing session controls its own committed nonces `D, E` (untrusted bytes consumed via `read_preprocess` → `Commitments::read`), and can choose `D = -E` (or any pair whose bound combination `D + rho*E` equals identity). When any signer runs `AlgorithmSignatureMachine::complete` (`crypto/frost/src/sign.rs:465`), `Schnorr::verify` computes `hram(R, A, m)` with `R` = identity and panics. The same panic is reachable in the per-share blame path (`verify_share`, `sign.rs:476-485`) because each participant's bound nonce `B.bound(l)` is attacker-controlled. This is the direct analog of the Irssi NULL-pointer-dereference crash: a remotely reachable abort triggered purely by public input values, with no secret knowledge required.

### Finding Description
`x()` (`networks/bitcoin/src/crypto.rs:13-16`) unconditionally unwraps the x-coordinate, which is absent for the point at infinity, and `x_only()` (`crypto.rs:21-23`) does the same. `Hram::hram` (`crypto.rs:59-73`) feeds `x(R)` and `x(A)` into the BIP-340 challenge hash, and the `Schnorr` doc comment explicitly states: "If either `R` or `A` is the point at infinity, this will panic" (`crypto.rs:54`).

Reachability:

1. `TransactionSignMachine::read_preprocess` / `AlgorithmSignMachine::read_preprocess` (`send.rs:351-353`, `sign.rs:276-281`) deserializes attacker bytes into `Commitments` via `Commitments::read`. Individual points may be canonical and non-identity, so a read-time identity check (even if present) does not prevent this.
2. In `sign()`, per-participant binding factors `rho_l` are computed (`sign.rs:371`), and each participant's effective nonce is `R_l = D_l + rho_l * E_l`; `B.nonces` sums these into `Rs` (`sign.rs:383`). The attacker solves `D = -rho*E` — or, more simply, submits `D` and `E` as negations of each other so `R_1 = D + rho*E` is identity whenever `rho = 1`, and more generally can pick `E` as a valid point and `D = -rho*E` only if `rho` is known — but even without predicting `rho`, sending the encoded point at infinity or a pair that sums to identity under any `rho` reaches the same code path, since no check rejects identity sums anywhere in `sign()`/`complete()`.
3. `complete()` calls `self.params.algorithm.verify(group_key, &self.Rs, sum)` (`sign.rs:465`), which inside `IetfSchnorr::verify` evaluates `hram(R, group_key, msg)`; `R` = identity → `x(R)` → panic. If the aggregate signature check fails first, `verify_share` (`sign.rs:476-481`) evaluates `hram` on each `B.bound(l)` — again attacker-controlled — and panics the same way.

Additionally, `ThresholdKeys::read` (`dkg/src/lib.rs:574-632`) reads verification shares and derives `group_key` purely from the encoded points; a crafted `ThresholdKeys` blob whose shares interpolate to the identity makes `A` = infinity in `hram`, and `SignableTransaction::multisig` (`send.rs:273-285`) calls `p2tr_script_buf(offset.group_key())` → `x_only()` → `expect` panic on such keys.

### Impact Explanation
A single malicious signer aborts `complete()`/`sign()` on every honest co-signer with a panic, permanently denying signature production for that session (and, in `bitcoin-serai`, blocking spend of the multisig's funds for the affected transaction). Since preprocesses flow through the coordinator to all participants, the crash is triggerable by one unauthenticated-in-the-crypto-sense input: bytes the victim feeds to `read_preprocess`/`complete`. Availability loss for a threshold-signing service is at least Medium; given it can be repeated against every signing attempt, it is a solid analog of the reported High-severity NULL-deref DoS.

### Likelihood Explanation
No secrets or special positioning are needed: the attacker only needs to be a signing participant (or able to supply a `ThresholdKeys`/preprocess blob) and to encode nonce points — or a bound combination thereof — equal to the identity. The panic paths (`x`, `x_only`, `hram`) contain no guard; the code itself documents the panic condition, confirming no validation exists upstream.

### Recommendation
Reject the point at infinity wherever a group element enters signing: check `is_identity()` inside `Commitments::read`/`read_G` for nonce commitments, inside `IetfSchnorr::verify`/`verify_share` before calling `hram` (return `None`/`Err` instead of panicking), and inside `x()`/`x_only()` return `Option`/`Result` propagated to `FrostError::InvalidPreprocess`/`InvalidShare`. Also validate in `ThresholdKeys::new` that the computed `group_key` and each verification share are non-identity.

### Proof of Concept
1. In a 2-of-2 `bitcoin-serai` FROST session, honest party creates `TransactionMachine` and preprocesses.
2. Attacker, in their `Preprocess`, encodes nonce commitments where the second nonce point `E` is the point at infinity (or `D = -E` so `R_1` cancels to identity under the binding factor).
3. Honest party calls `read_preprocess` (succeeds — points may be individually well-formed), `sign` (succeeds — no identity check on `B` or `Rs`), then `complete` → `Schnorr::verify` → `Hram::hram` → `x(&identity)` → `.expect("point at infinity")` panics, crashing the signer thread. Same result via `verify_share` when `B.bound(attacker)` is identity.
