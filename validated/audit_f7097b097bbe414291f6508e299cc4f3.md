Based on the investigation, this is a valid, concrete vulnerability with a demonstrable code path.

### Title
Unauthenticated OP_RETURN operator attribution lets anyone credit an arbitrary operator with a payout it never funded - ([File: core/src/verifier.rs])

### Summary
`Verifier::update_finalized_payouts` derives the `operator_xonly_pk` that is stored as `payout_payer_operator_xonly_pk` for a withdrawal index purely from the OP_RETURN bytes of whatever transaction happens to spend the tracked `withdrawal_utxo`, with no signature, MuSig2 partial-signature check, or any other cryptographic binding to who actually funded/signed that transaction. Because the OP_RETURN is fully attacker-controlled, an attacker who can produce/broadcast a valid spend of a `withdrawal_utxo` can embed an honest operator's `xonly_pk` in it, causing that honest operator's own `PayoutCheckerTask` to pick it up and reimburse itself for a payout it never made.

### Finding Description
The binding the code is supposed to maintain is:
`operator_credited_for_withdrawal_i (DB: withdrawals.payout_payer_operator_xonly_pk)` == `operator_whose_signature/funds_actually_produced_the_payout_tx_spending_withdrawal_utxo_i`.

In `Verifier::update_finalized_payouts` [1](#0-0) , once a transaction is found in a synced block that spends the tracked `withdrawal_utxo` for index `idx` (tracked via `get_payout_txs_for_withdrawal_utxos`, which only checks the outpoint being spent, not who spent it), the code extracts `operator_xonly_pk` solely via `get_first_op_return_output` + `parse_op_return_data` [2](#0-1) [3](#0-2) . This value is written unconditionally into the `withdrawals` table via `update_payout_txs_and_payer_operator_xonly_pk` [4](#0-3) .

Downstream, `PayoutCheckerTask::run_once` trusts this DB column completely: it looks up the first unhandled payout **matching its own operator key** via `get_first_unhandled_payout_by_operator_xonly_pk` [5](#0-4)  and then calls `Operator::handle_finalized_payout`, which allocates an unused kickoff connector and signs/queues the Kickoff and Reimburse transactions for that operator [6](#0-5) . Nowhere in this path is there a check that the operator whose key appears in the OP_RETURN actually signed or funded the payout input; the only real signature check that exists (`in_signature` against the withdrawal UTXO's own P2TR key, used in `Operator::withdraw`/`create_payout_txhandler`) proves only that the payout input was validly spent — it says nothing about who wrote the OP_RETURN bytes, since `create_payout_txhandler` builds the OP_RETURN from a caller-supplied `operator_xonly_pk` parameter with no relation to `user_sig` [7](#0-6) .

Since the threat model explicitly grants the attacker the ability to "choose the bytes of a withdrawal UTXO, a Schnorr signature and its sighash flag," an attacker who legitimately controls (or can produce a valid signature for) the registered `withdrawal_utxo` for their own withdrawal index can construct and broadcast their own payout transaction — spending that UTXO to whatever output they like — while placing an **honest operator's** `xonly_pk` in the OP_RETURN instead of their own (or instead of none, as in the optimistic-payout case). None of `is_deposit_valid`, `SECP.verify_schnorr` against `operator_xonly_pk`, or a MuSig2 session check gate this OP_RETURN value; the guard list in the rubric (`is_kickoff_malicious`, `verify_storage_proofs`, `SPV::verify`, `lc_proof_verifier`) only runs later, inside the bridge circuit used for *disprove/challenge*, not at the point the honest operator's `PayoutCheckerTask` decides to self-reimburse.

### Impact Explanation
The honest operator named in the forged OP_RETURN will have its `PayoutCheckerTask` treat the attacker's transaction as "its" payout, allocate a kickoff connector, sign and broadcast a Kickoff transaction, and eventually receive the Reimburse transaction payout from collateral/round funds it never fronted for this withdrawal — this is BTC moving out of the bridge's reimbursement flow for a payout the credited operator never made, matching the Critical category "an operator reimbursed for a payout it never funded." It is repeatable per withdrawal index and does not require compromising any operator/verifier key; a single unprivileged withdrawer suffices. It also has a secondary effect: once `idx` is marked `is_payout_handled = true` via `mark_payout_handled`, no other, truly-funding operator can later be credited/reimbursed for the same index, permanently locking that operator out of reimbursement for a payout it (or someone else) legitimately paid — matching "an honest operator permanently unable to be reimbursed."

### Likelihood Explanation
No special privileges, key shares, TLS certs, or verifier/operator roles are needed — only the ability to control a withdrawal registration and broadcast a Bitcoin transaction with fees, both explicitly within the unprivileged attacker's stated capabilities. The attacker needs to know/guess a target honest operator's public `xonly_pk` (these are typically public protocol data, published as part of operator registration), and the cost is limited to normal transaction fees for the payout tx they'd broadcast anyway.

### Recommendation
Bind the OP_RETURN `operator_xonly_pk` cryptographically to the actual signer/funder of the payout transaction — e.g., require the payout input to be spent via a script/key path that embeds or is tweaked by the operator's own key (so only that operator can produce the valid witness), or require an additional operator signature over the OP_RETURN payload that `update_finalized_payouts` verifies with `SECP.verify_schnorr` before accepting `operator_xonly_pk` as authoritative, rather than trusting arbitrary push-data.

### Proof of Concept

Test outline:
1. Set up a deposit/withdrawal as in existing e2e helpers (`core/src/test/common/clementine_utils.rs::payout_and_start_kickoff`), registering `withdrawal_utxo` for index `i` under the attacker's own key instead of going through an honest operator's `withdraw` RPC.
2. Attacker constructs a payout transaction spending `withdrawal_utxo` (self-signed with the attacker's key) whose OP_RETURN embeds `operator1_xonly_pk` (an honest, uninvolved operator).
3. Broadcast and mine the tx; run the verifier's block-sync path so `update_finalized_payouts` executes.
4. Assert: `db.get_payout_info_from_move_txid(...)` (or `get_payout_txs_for_withdrawal_utxos`) returns `payout_payer_operator_xonly_pk == operator1_xonly_pk`, i.e., ATTRIBUTION succeeds despite `operator1` never having signed/funded the tx (the assertion the current code fails to reject).
5. Optionally continue and show `operator1`'s `PayoutCheckerTask::run_once` proceeds to call `handle_finalized_payout` and queues a Kickoff/Reimburse tx for index `i`, confirming reimbursement is granted without operator1 ever funding the payout.

pub fn parse_op_return_data(script: &Script) -> Option<&[u8]> {
    let mut instructions = script.instructions();
    if let Some(Ok(Instruction::Op(opcodes::all::OP_RETURN))) = instructions.next() {
        if let Some(Ok(Instruction::PushBytes(data))) = instructions.next() {
            return Some(data.as_bytes());
        }
    }
    None
}

        &'a self,
        dbtx: DatabaseTransaction<'a>,
        deposit_outpoint: OutPoint,
        payout_tx_blockhash: BlockHash,
    ) -> Result<bitcoin::Txid, BridgeError> {
        let (deposit_id, deposit_data) = self
            .db
            .get_deposit_data(Some(dbtx), deposit_outpoint)
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        // get unused kickoff connector
        let (round_idx, kickoff_idx) = self
            .db
            .get_unused_and_signed_kickoff_connector(
                Some(dbtx),
                deposit_id,
                self.signer.xonly_public_key,
            )
            .await?
            .ok_or(BridgeError::DatabaseError(sqlx::Error::RowNotFound))?;

        let current_round_index = self.db.get_current_round_index(Some(dbtx)).await?;
        tracing::info!(
            "Operator: Current round index: {}, round idx for kickoff: {}",
            current_round_index,
            round_idx
        );
        #[cfg(feature = "automation")]
        if current_round_index != round_idx {
            // we currently have no free kickoff connectors in the current round, so we need to end round first
            // if current_round_index should only be smaller than round_idx, and should not be smaller by more than 1
            // so sanity check:
            if current_round_index.next_round() != round_idx {
                return Err(eyre::eyre!(
                    "Internal error: Expected the current round ({:?}) to be equal to or 1 less than the round of the first available kickoff for deposit reimbursement ({:?}) for deposit {:?}. If the round is less than the current round, there is an issue with the logic of the fn that gets the first available kickoff. If the round is greater, that means the next round do not have any kickoff connectors available for reimbursement, which should not be possible.",

                ).into());
            }

            self.end_round(dbtx).await?;

        let kickoff_data = KickoffData {
            operator_xonly_pk: self.signer.xonly_public_key,
            round_idx,
            kickoff_idx,
        };

        let payout_tx_blockhash = payout_tx_blockhash.as_byte_array().last_20_bytes();

        #[cfg(test)]

            .config
            .test_params

            &self.signer,
            self.config.clone(),
            context,
            Some(payout_tx_blockhash),

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
