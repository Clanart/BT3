### Title
Silent auto-rewrite of the `origin` remote URL from an attacker-controlled GitHub API response can redirect future pushes to a squatted repository - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
GitHub Desktop periodically re-associates a local repository with its GitHub metadata and, as part of that flow, will silently rewrite the local `origin` remote URL if it believes the GitHub repository was renamed. The owner/name used to query the GitHub API is derived from the repository's *current git remote URL*, not from any signed/immutable repository id. If a repository is renamed away and the old `owner/name` is later re-registered ("squatted") by an attacker, Desktop's periodic refresh will fetch the attacker's repository object from the API and use its `clone_url` to overwrite the user's local remote — without any user confirmation — because the code only checks that the *previous* remote matched the previously known API clone URL, not that the repository identity (id) is unchanged.

### Finding Description
`matchGitHubRepository` in [1](#0-0)  derives `owner`/`name` purely by parsing the current git remote URL against the hostname of a signed-in account — it performs no verification that the resolved owner/name still refers to the same repository the user originally added.

This match result feeds `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository(owner, name)` and then unconditionally calls `updateRemoteUrl` with whatever `IAPIFullRepository` object the API returns: [2](#0-1) 

`updateRemoteUrl` will rewrite the local remote's URL to the API's `clone_url` as long as (a) the protocol scheme is unchanged, and (b) the *current* remote URL still matches the *previously stored* `gitHubRepository.cloneURL` — i.e., it assumes "nothing has changed locally since last time," and (c) the new API clone_url differs from the current remote: [3](#0-2) 

None of these checks verify the GitHub repository *id* (the immutable identifier returned by the API) stays the same. If a repository is renamed/deleted and a different, attacker-owned repository is later created under the exact same `owner/name`, the next background/foreground refresh will:
1. Resolve `owner`/`name` from the stale local remote URL (still pointing at the old name).
2. Call the GitHub API, which now returns the attacker's repository object for that `owner/name`.
3. Since the local remote hasn't been manually changed and the protocol matches, `updateRemoteUrl` silently repoints `origin` at the attacker's `clone_url`.

### Impact Explanation
This causes silent corruption of the destination of the user's future `git push` operations — the exact "silent corruption of what the user commits or pushes" impact class. A user who is unaware their `origin` was rewritten could push private branches/commits to a repository they do not control, exposing proprietary source code to the attacker (if the attacker's repo is public or if the attacker grants themselves write/read access and monitors incoming pushes/PRs). Because credential resolution in the trampoline layer (`findGitHubTrampolineAccount`) matches accounts by API/HTML *origin* rather than by specific owner/repo ( [4](#0-3) ), the user's normal GitHub token would still be used to authenticate the push attempt, meaning the only barrier to a working push is the user's own token having write access to the squatted namespace/repo — which is under attacker control and can be freely granted by the attacker if they invite the victim as a collaborator via other social means, or simply left public for silent leakage of any pushed content in the interim.

### Likelihood Explanation
This requires no local access, no admin rights, and no pre-existing malware — only that: (1) a previously-tracked repository is renamed/deleted upstream, and (2) an attacker registers a new repository under the freed `owner/name` before the user's Desktop app performs its periodic GitHub repository refresh (`repositoryWithRefreshedGitHubRepository`, called from repository selection/refresh code paths in `app-store.ts`). Repository/organization renaming and name squatting are common occurrences on GitHub, and Desktop's refresh happens automatically and silently (no dialog is shown to the user when the remote URL changes), so the user has no visual indicator that their push target changed.

### Recommendation
Before rewriting the remote URL in `updateRemoteUrl`, verify that the freshly-fetched `IAPIFullRepository.id` matches the previously persisted `GitHubRepository` id (already stored in the repositories DB, see `IDatabaseGitHubRepository`/`upsertGitHubRepository` in `app/src/lib/stores/repositories-store.ts`). If the id differs, treat it as a different repository entirely (do not auto-update the remote) and instead surface a warning to the user that the repository they had configured appears to have changed identity, requiring explicit confirmation before the remote URL is touched.

### Proof of Concept
1. User A clones `https://github.com/acme/widgets` with Desktop; Desktop stores `GitHubRepository` with `cloneURL=https://github.com/acme/widgets` and the corresponding repository `id`.
2. The `acme/widgets` repository is renamed to `acme/widgets-legacy` (or transferred/deleted), freeing the `acme/widgets` name.
3. Attacker creates a new repository at `https://github.com/acme/widgets` (assuming they control/compromise the `acme` org, or the scenario is a personal-account rename where the attacker registers the freed personal-repo slug).
4. User A's Desktop periodically calls `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` (parses `owner=acme, name=widgets` from the still-unchanged local remote URL) → `api.fetchRepository('acme','widgets')`, which now returns the attacker's repository object with a different `id` but same `clone_url` shape.
5. `updateRemoteUrl` compares `remoteUrlUnchanged` (true, since local remote still equals the last known `acme/widgets` clone URL) and `protocolsMatch` (true) and `urlsMatch` — if the attacker's `clone_url` differs at all from the currently configured remote (e.g., different casing, or the attacker's repo returns a distinct-but-similar clone URL), the remote is rewritten via `gitStore.setRemoteURL`, all without a prompt.
6. User A's next `git push` sends commits to the attacker-controlled repository.

Note: I was not able to fully trace every automatic caller of `repositoryWithRefreshedGitHubRepository`/`_convertRepositoryToFork` within `app-store.ts` (12 matches) to confirm the exact background refresh cadence/triggers; a Devin session with full file access would be needed to enumerate all call sites and confirm how frequently/automatically this refresh runs without user interaction.

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export async function findGitHubTrampolineAccount(
  accountsStore: AccountsStore,
  remoteUrl: string
): Promise<Account | undefined> {
  const accounts = await accountsStore.getAll()
  const parsedUrl = new URL(remoteUrl)
  return accounts.find(
    a => new URL(getHTMLURL(a.endpoint)).origin === parsedUrl.origin
  )
}
