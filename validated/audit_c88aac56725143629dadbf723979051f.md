### Title
Payout tx's `SinglePlusAnyoneCanPay` signature does not commit to the OP_RETURN output, letting an attacker strip it and frame the honest operator as malicious - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
`create_payout_txhandler` signs the payout tx's single input with `TapSighashType::SinglePlusAnyoneCanPay`, a sighash flag that only commits to input 0 and the output at the same index (output 0, the user payout). The anchor and OP_RETURN outputs are never covered by the signature, so anyone observing the signature can rebroadcast a variant of the transaction that drops the OP_RETURN output and get it mined instead of the operator's original transaction.

### Finding Description
The broken binding: `withdrawals.payout_payer_operator_xonly_pk == kickoff_data.operator_xonly_pk` for the operator A who fronted the withdrawal (established via `Verifier::update_finalized_payouts` reading operator A's OP_RETURN from the confirmed payout tx). After the attack: `payout_payer_operator_xonly_pk == NULL` even though A funded the payout.

`Operator::withdraw` (`core/src/operator.rs:560-637`) builds the payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), which adds 3 outputs (user payout, anchor, OP_RETURN with operator xonly pk) but signs input 0 with the user-supplied `TapSighashType::SinglePlusAnyoneCanPay` signature, enforced explicitly in `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:182-187`). By BIP-341/consensus rules, `SIGHASH_SINGLE|ANYONECANPAY` only commits to: the spent input's outpoint/value/scriptPubkey/sequence, and the output at the same index as the input (output 0). Outputs 1 (anchor) and 2 (OP_RETURN) are outside the signed message.

An unprivileged attacker who observes operator A's unconfirmed payout tx in the mempool can extract the witness (signature) for input 0, and build a new transaction with the identical input 0 and output 0 but omitting the OP_RETURN output (2 outputs: user payout + anchor). The signature remains valid for this new transaction because the modified/removed bytes are outside the commitment. If the attacker gets this variant mined first (fee-bump/race), it becomes the canonical on-chain payout tx.

Downstream, `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) calls `get_first_op_return_output` on the confirmed tx; finding none, it sets `operator_xonly_pk = None` and persists `payout_payer_operator_xonly_pk = NULL` via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`). When operator A later sends its kickoff, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) reads this NULL through `get_payout_info_from_move_txid` and hits `let Some(operator_xonly_pk) = operator_xonly_pk_opt else { return Ok(true) }` (`core/src/verifier.rs:1882-1885`), unconditionally flagging A's honest kickoff as malicious regardless of the fact that A did front the withdrawal.

No existing guard prevents this: `Operator::is_profitable`/`SECP.verify_schnorr` in `withdraw` only validate the signature against output 0 and profitability, they do not enforce that the anchor/OP_RETURN outputs are covered by the signature or protected from third-party replacement. `Verifier::is_deposit_valid` is unrelated to this payout-time race. There is no mempool/consensus mechanism in this codebase preventing a third party from submitting a fee-competitive variant of a `SIGHASH_SINGLE|ANYONECANPAY`-signed transaction that alters uncommitted outputs.

### Impact Explanation
The consequence cascades further than mislabeling: `circuits_lib::bridge_circuit::bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:206-207`) also calls `get_first_op_return_output(&input.payout_spv.transaction).expect("Payout transaction must have an OP_RETURN output")` on the same on-chain payout transaction to compute `operator_xonlypk` for `deposit_constant`. Since the attacker-mined transaction has no OP_RETURN output at all, the operator cannot construct a valid bridge-circuit proof for its own payout, so it cannot successfully assert/disprove-defend itself. Combined with `is_kickoff_malicious` always returning `true` for this withdrawal, this exposes the honest operator's kickoff to `Challenge` and ultimately `Disprove`, burning the operator's collateral for a payout they legitimately funded — matching the Critical category "an honest operator's collateral burned" (and arguably "an honest operator permanently unable to be reimbursed", since `mark_payout_handled`/reimbursement flow depends on non-malicious kickoff handling). The attack is repeatable against any operator and any withdrawal as long as the attacker can win the race to get the stripped variant mined, and costs the attacker only transaction fees (no bridge funds, no privileged role, no key compromise).

### Likelihood Explanation
Preconditions: a withdrawal must be registered and an operator must have broadcast (not yet confirmed) its 3-output payout transaction. The attacker needs to see this transaction in the mempool (public information), extract input 0's witness, and construct/broadcast a 2-output variant with a competitive fee/RBF signal to get mined ahead of or in place of the original. This requires no special privileges — the actor definition in scope (anyone who can broadcast Bitcoin transactions and pay fees) is sufficient. This is a generic weakness of `SIGHASH_SINGLE|ANYONECANPAY` transactions circulating in the public mempool, well understood as a "sighash pinning/mutation" issue, making the exploit straightforward to reproduce on regtest.

### Recommendation
Do not rely solely on `SIGHASH_SINGLE|ANYONECANPAY` for the payout tx's user signature when downstream logic depends on outputs (anchor, OP_RETURN) that are not covered by that sighash. Either (a) require the user to sign with a sighash type that commits to all outputs (e.g. `SIGHASH_ALL` or `SIGHASH_DEFAULT`) so the OP_RETURN cannot be stripped without invalidating the signature, or (b) if `SinglePlusAnyoneCanPay` must be kept for flexibility, stop relying on the OP_RETURN of the mined payout transaction as the sole binding of "who fronted this withdrawal" — instead record the payer operator at `withdraw()`-call time (before broadcast) keyed by the specific signed transaction/outpoint, and validate on confirmation that the mined transaction's input/output-0 match what that operator broadcast, independent of the mutable trailing outputs.
