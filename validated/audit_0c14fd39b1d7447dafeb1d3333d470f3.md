### Title
Attacker-controlled `n` triggers large pre-validation allocation in `ThresholdKeys::read` - ([File: crypto/dkg/src/lib.rs])

### Summary
CVE-2019-8375 is a missing-bounds-check bug where an attacker-controlled size parameter (script dialog dimensions) causes an oversized allocation / buffer overflow DoS. The closest reachable analog in the in-scope Serai crates is `ThresholdKeys::read`, which allocates a `Vec` of capacity `n` — a u16 taken directly from untrusted input — *before* any data is read or validated. A handful of attacker bytes forces an allocation of up to ~2 MB (65,535 field elements) plus a `HashMap` grown to `n` entries.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reads `t`, `n`, `i` as raw u16s, then reads an interpolation tag byte. If the tag is `0` (`Interpolation::Constant`), it executes:

```rust
// crypto/dkg/src/lib.rs:607-613
0 => Interpolation::Constant({
  let mut res = Vec::with_capacity(usize::from(n));
  for _ in 0 .. n {
    res.push(C::read_F(reader)?);
  }
  res
}),
```

`Vec::with_capacity(n)` allocates `n * size_of::<C::F>()` bytes immediately, before the first `read_F` even runs. An attacker supplies ~10 bytes (curve-ID length + ID + `t`/`n`/`i` + tag) with `n = 0xFFFF` and then a truncated/empty body: the call still allocates ~2 MB (e.g. 32-byte `Repr`-backed fields) and returns an error only afterward. The same `n` also drives `Vec::with_capacity`/`HashMap` growth for `verification_shares` later in the function (crypto/dkg/src/lib.rs:620-623), though those reads fail fast on EOF.

This mirrors the CVE pattern exactly: a size field in untrusted input is trusted to scale a resource (allocation) with no sanity bound relative to actual data available. Compare with `coordinator/src/p2p.rs:264-271`, where Serai explicitly caps a peer-supplied length against `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating — the crypto crates have no equivalent guard.

`ThresholdKeys::read` is reachable by an unprivileged party feeding untrusted bytes to a host that deserializes key material (e.g. a coordinator/processor reading shares or key files supplied by other validators), which the scope rules explicitly list as reachable (`ThresholdKeys::read`).

### Impact Explanation
Each call amplifies ~10 attacker bytes into a ~2 MB heap allocation plus `HashMap` reservation, and the allocation occurs *before* any byte availability check. An attacker that can repeatedly trigger `ThresholdKeys::read` on crafted input can drive memory pressure/OOM on the victim process at a large amplification ratio (~2×10⁵:1 per call). Because the allocation happens inside a `Zeroizing`/`std` `Vec`, repeated calls in a loop or across concurrent connections compound into service denial — the same DoS consequence class as the CVE (buffer sized beyond what the input actually provides).

Severity is limited relative to the CVE: `n` is a u16 (capped at 65,535), and Rust prevents the memory-corruption consequence — this is allocation DoS only, no overflow. That bounds it to Medium rather than Critical.

### Likelihood Explanation
Exploitation requires a deployment that calls `ThresholdKeys::read` on bytes influenced by an untrusted party (e.g. key-share redistribution, recovery flows, or a peer-supplied `ThresholdKeys` blob). It requires no valid signature, no threshold collusion, and no special role — only control of the input bytes. The Constant-interpolation branch is taken whenever tag byte `0` is supplied, independent of what the honest writer would have emitted. Each request costs the attacker ~10 bytes while forcing ~2 MB of allocation, so the attack is cheap and repeatable. Mitigating factor: a single call is transient (the `Vec` is dropped on error), so sustained DoS requires repeatedly exercising the read path.

### Recommendation
Bound `n` before allocating:
- Validate `t <= n` and `n <= i`-range via `ThresholdParams::new` (or a hard protocol maximum such as `MAX_KEY_SHARES_PER_SET`) *before* the interpolation branch runs.
- Replace `Vec::with_capacity(n)` with incremental `push` without pre-reservation, or check `reader` length first (e.g. wrap in a limited/`take()` reader or read the body into a bounded buffer before constructing collections), as done in `networks/ethereum/src/machine.rs` (`Call::read` chunks reads to cap amplification at 1 KB).

### Proof of Concept

// Attacker-controlled input; ~11 bytes of header, no body.
let mut bytes = vec![];
// curve ID length + ID (matches target curve, e.g. b"ristretto" padded as written)
bytes.extend(&(C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
// t = 1, n = 65535, i = 1
bytes.extend(&1u16.to_le_bytes());
bytes.extend(&u16::MAX.to_le_bytes());
bytes.extend(&1u16.to_le_bytes());
// interpolation tag = 0 => Constant
bytes.push(0);
// reader ends here: read_F fails on the first element, but
// Vec::with_capacity(65535 * size_of::<C::F>()) was already performed.
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice()); // allocates ~2 MB, then errors
