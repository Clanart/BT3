### Title
`SignableTransaction::new` accepts arbitrary payment `script_pubkey`s without spendability validation, allowing irreversible burning of funds - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report describes a peg-out `burn` that forwards an unvalidated destination address to release BTC, letting a malformed address permanently destroy user funds with no recovery path. The same shape exists in Serai's Bitcoin wallet: `SignableTransaction::new` consumes caller-supplied `(ScriptBuf, u64)` payments and builds consensus-valid transaction outputs for them without checking that the script is a standard, spendable form. The only payment validation is a dust-amount floor; a caller-supplied provably-unspendable or garbage `script_pubkey` is silently embedded in the signed transaction.

### Finding Description
`SignableTransaction::new` is the sole transaction-construction entry point for spending scanned outputs (`ReceivedOutput`). The payments parameter is arbitrary untrusted bytes per output — exactly the untrusted-input surface this audit covers. The validation performed is limited to:

- `payments` non-empty (combined with `change`/`data`) [1](#0-0) 
- each amount >= `DUST` (546 sats) [2](#0-1) 
- the `OP_RETURN` `data` payload fitting in 80 bytes [3](#0-2) 

Nothing inspects `payment.0` (the `ScriptBuf`). The outputs are built verbatim [4](#0-3) , funded by the threshold key, and committed into the Taproot sighash that all participants sign (`taproot_key_spend_signature_hash` over `Prevouts::All`) [5](#0-4) . Once broadcast, the UTXO is governed entirely by whatever script bytes were supplied — `OP_RETURN`, an empty script (anyone-can-spend, i.e., stealable), a malformed `OP_PUSH`, or a P2TR/P2PKH output to a key nobody controls. There is no rescue mechanism and no re-check of the destination anywhere in `multisig`, `preprocess`, `sign`, or `complete`; `multisig` only verifies the *spent prevouts* match the offset group key, never the destinations [6](#0-5) .

This mirrors the reported bug class exactly: a permissionless supply of destination bytes, no validation of whether those bytes encode a spendable destination, and no revert/recovery once consumed.

### Impact Explanation
Funds in the transaction outputs become permanently unspendable (provably-unspendable scripts like `OP_RETURN`, or outputs whose key is unknown) or immediately stealable (anyone-can-spend scripts such as an empty scriptPubKey or `OP_TRUE`). Because Serai payments are threshold-signed spends of pooled wallet outputs, a malformed destination wastes real BTC the same way the bridge's unvalidated `_btc_addr` did, with no abort path after `complete` returns the signed transaction [7](#0-6) .

### Likelihood Explanation
Reachable by any unprivileged party able to specify a payment destination (the withdrawal flow this code exists to serve). Triggering requires only passing malformed script bytes; no cryptographic attack, collusion, or privileged access is needed — identical difficulty to supplying a bad `_btc_addr` string in the report. Rated Medium rather than High because exploitation requires the destination-supplying caller to err (or a destination byte-processing bug upstream), and the severity is bounded by the amount placed on the malformed output rather than enabling theft of unrelated wallet funds.

### Recommendation
Validate each payment `ScriptBuf` in `SignableTransaction::new` before constructing the transaction: reject non-standard/unspendable destinations (e.g., scripts beginning with `OP_RETURN`, scripts failing `script.is_standard()`/policy checks, and empty scripts). Optionally restrict payments to a whitelist of standard templates (`is_p2tr`, `is_p2wpkh`, `is_p2wsh`, `is_p2pkh`, `is_p2sh`, `is_p2wpkh`-equivalent checks via `bitcoin::script`/`Address`) since the wallet is a custody tool. If validation is intentionally delegated to an off-chain caller, document that `SignableTransaction::new` MUST only receive validated spendable destinations, and consider surfacing a destination-inspection API on `SignableTransaction` so signers can confirm outputs before producing shares.

### Proof of Concept
Conceptual, using only public inputs to `SignableTransaction::new`:

```rust
// networks/bitcoin/src/wallet/send.rs — no validation on payment.0
// A caller supplies a provably unspendable payment:
let payments = vec![(
    // OP_RETURN 0x6a — consensus-valid output, permanently unspendable
    ScriptBuf::from(vec![0x6a]),
    100_000, // >= DUST, so the only check passes
)];

let stx = SignableTransaction::new(
    inputs,            // real ReceivedOutputs controlled by the threshold key
    &payments,
    Some(change_script),
    None,
    fee_per_vbyte,
).unwrap();              // succeeds — no spendability check exists

// stx.multisig(&keys) -> preprocess -> sign -> complete all succeed;
// every signer's share commits to Prevouts::All including this output.
// After broadcast, the 100,000 sats are burned with no recovery path.
```

The only gate is `*amount < DUST` [2](#0-1) ; the script bytes flow unchecked into `tx_outs` [4](#0-3)  and into the signed transaction [8](#0-7) .
