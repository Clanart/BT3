### Title
Forged serialized `ReceivedOutput`s can be signed as non-existent deposits - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`ReceivedOutput` is documented as a spendable output, but `ReceivedOutput::read` accepts an attacker-supplied scalar, `TxOut`, and `OutPoint` without proving that the outpoint exists, is unspent, or contains the claimed `TxOut`. [1](#0-0) [2](#0-1) 

`SignableTransaction::new` treats the embedded `output.value` as available funds and the embedded `outpoint` as the transaction input. [3](#0-2) 

### Finding Description
An unprivileged caller can serialize a fake `ReceivedOutput` containing:

1. `offset = 0` or another offset chosen by the attacker.
2. A `TxOut` with an arbitrary inflated value and the victim multisig's P2TR script.
3. An arbitrary non-existent, spent, or mismatched `OutPoint`.

The claimed value is summed into `input_sat`, allowing the fabricated deposit to satisfy the payment-plus-fee check. [3](#0-2) [4](#0-3) 

`SignableTransaction::multisig` only verifies that the supplied `prevouts[i].script_pubkey` equals the P2TR script for `keys + offset`; it does not verify that the referenced chain output actually has that script or value. [5](#0-4) 

The resulting signing machine then commits the forged `prevouts` through `Prevouts::All` and signs each attacker-selected input. [6](#0-5) 

Completion inserts the resulting Schnorr signature as the input witness and returns the transaction as successful even though the input may not exist. [7](#0-6) 

### Impact Explanation
A fabricated byte string can be reported to the spending pipeline as a spendable deposit despite there being no corresponding spendable UTXO. [2](#0-1) 

This can cause a threshold signing flow to produce a signature for a transaction that Bitcoin consensus cannot accept, while the wallet has already treated the claimed amount as available input value. [3](#0-2) [6](#0-5) 

If such outputs cross a trust boundary, an attacker can cause false accounting, failed withdrawals, and consumption of signing attempts without providing any real deposit. [4](#0-3) [7](#0-6) 

### Likelihood Explanation
The attack requires no private key, threshold compromise, malformed signature, or mining capability: only the ability to feed crafted bytes to `ReceivedOutput::read` and have the result passed to `SignableTransaction::new`. [2](#0-1) [8](#0-7) 

The vulnerability is conditional on applications treating serialized `ReceivedOutput`s as untrusted inputs, but the API exposes a public deserializer for the complete claimed output state. [2](#0-1) 

### Recommendation
Do not treat `ReceivedOutput::read` as proof that an output exists or is spendable. [2](#0-1) 

Before calling `SignableTransaction::new`, resolve every `outpoint` against a trusted Bitcoin node or verified UTXO view and require the chain's actual `TxOut` to equal both the claimed `script_pubkey` and `value`. [3](#0-2) 

If serialized outputs cross a trust boundary, authenticate them as scanner-generated data or remove public construction of `ReceivedOutput` from arbitrary serialized state. [1](#0-0) 

### Proof of Concept
```rust
use bitcoin::{
  Amount, OutPoint, TxOut, Txid,
  consensus::serialize,
  hashes::Hash,
};
use frost::curve::Secp256k1;
use k256::Scalar;
use ciphersuite::group::ff::PrimeField;

// `group_key` is the victim's even, tweaked P2TR key.
let victim_script = p2tr_script_buf(group_key).unwrap();

let forged_txout = TxOut {
  value: Amount::from_sat(1_000_000),
  script_pubkey: victim_script,
};

// This outpoint need not exist, may already be spent, or may point to an output
// with a different script/value.
let forged_outpoint = OutPoint {
  txid: Txid::from_slice(&[0; 32]).unwrap(),
  vout: 0,
};

let mut encoded = Vec::new();
encoded.extend(Scalar::ZERO.to_repr());
encoded.extend(serialize(&forged_txout));
encoded.extend(serialize(&forged_outpoint));

let forged = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();

// The claimed 1,000,000 sats are trusted as spendable input.
let signable = SignableTransaction::new(
  vec![forged],
  &[(destination_script, 546)],
  None,
  None,
  20,
).unwrap();

// This succeeds because only `script_pubkey == p2tr(group_key + offset)` is checked.
let machine = signable.multisig(&keys).unwrap();

// After FROST signing, `complete` returns a transaction spending the forged outpoint.
```

The PoC passes the input-value check because `input_sat` is derived from the serialized `TxOut`, and it passes `multisig` because only the forged `script_pubkey` is compared against the threshold key. [3](#0-2) [5](#0-4)
