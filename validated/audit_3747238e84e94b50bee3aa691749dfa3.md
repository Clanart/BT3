### Title
Aggregate Schnorr forgery: aggregation weights bind only challenges, not public keys or nonces, letting one signer cancel a victim's term - (crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to the reported bug class (a value that is safe when checked in isolation becomes exploitable once evaluated in a shared/batch context), `SchnorrAggregate::verify` validates a *sum* of weighted signature terms where the per-signature weights `z_i` are derived solely from the sequence of challenges. Because the weights never bind the public keys `A_i` or the nonce commitments `R_i`, an attacker can predict every `z_i` before choosing `Rs` and `s`, and can craft a malicious `R` that exactly cancels an honest victim's `(R_v + c_v·A_v)` term. An individual `SchnorrSignature` for the victim key verifies correctly; the same key "validates" inside an aggregate it never participated in.

### Finding Description
In `SchnorrAggregate::verify` (crypto/schnorr/src/aggregate.rs:127-146), the aggregation weight transcript is built as:

```rust
digest.domain_separate(b"signatures");
for (_, challenge) in keys_and_challenges {
  digest.append_message(b"challenge", challenge.to_repr());
}
```

Only the challenges are absorbed; the public keys (`key` is destructured away as `_`) and the aggregate's `Rs` are never transcripted. `weight()` then deterministically reduces the digest to a scalar per index.

Per the half-aggregation scheme this implements (eprint 2021/350), each weight must be unpredictable to the adversary at the time it commits to its nonce/key, otherwise the linear-combination soundness collapses. Here the weight function is a public deterministic function of the challenges alone, so a forger supplying `(Rs, s)` via `SchnorrAggregate::read` / `verify` knows all weights in advance and can solve for its own nonce commitment to cancel any victim term.

Verification equation: `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G = 0`. The forger controls the entire `Rs` vector and `s`, so it sets its own `R` to `- (z_v/z_a)·(R_v + c_v·A_v) + r_a·G`, eliminating the victim's key and nonce entirely without knowing `a_v` or `r_v`.

### Impact Explanation
Critical. Any verifier relying on `SchnorrAggregate::verify` accepts a forged aggregate attesting that an arbitrary victim public key signed an arbitrary challenge (message). This is a universal signature forgery reachable entirely from untrusted bytes fed to `SchnorrAggregate::read`/`verify` — no private key material, collusion, or protocol breach required.

### Likelihood Explanation
Any attacker who can submit an aggregate signature for verification (e.g., a co-signer in a set, or anyone feeding bytes to `read`/`verify`) can perform the forgery deterministically. The weights are computable offline from the public challenge list; constructing the cancelling `R` is a handful of group operations.

### Recommendation
Bind all verification inputs into the weight transcript: absorb each `R_i` and each public key `A_i` (or a commitment to the full ordered `(A_i, c_i, R_i)` tuple list) before deriving `z_i`, in both `SchnorrAggregate::verify` and `SchnorrAggregator` (`new`/`aggregate`/`complete` must hash the same values in the same order). Alternatively derive `z_i = H(R_1..R_n, A_1..A_n, c_1..c_n, i)` per the half-aggregation spec so no signer can know its weight before committing to `R`.

### Proof of Concept
Setup (generic over `C: Ciphersuite`), attacker forges an aggregate "containing" victim key `A_v` with challenge `c_v`:

1. Attacker chooses victim term index 0 with arbitrary `R_v` (e.g., `R_v = C::generator()`), and its own index 1 with known key `a_1`, `A_1 = a_1·G`, and a self-chosen challenge `c_1`.
2. Compute weights exactly as `verify` does: transcript `dst`, `domain_separate(b"signatures")`, append `c_v`, then `c_1`; `z_0 = weight(...)`, `z_1 = weight(...)`. These are fully public.
3. Choose `r_1`, set `R_1 = -(z_0/z_1)·(R_v + c_v·A_v) + r_1·G`.
4. Set `s = z_1·(r_1 + c_1·a_1)`.
5. Submit `SchnorrAggregate { Rs: [R_v, R_1], s }` with `keys_and_challenges = [(A_v, c_v), (A_1, c_1)]`.

Check: `z_0·R_v + z_0·c_v·A_v + z_1·R_1 + z_1·c_1·A_1 − s·G`
`= z_0(R_v + c_v A_v) + z_1(-(z_0/z_1)(R_v + c_v A_v) + r_1 G) + z_1 c_1 a_1 G − z_1(r_1 + c_1 a_1)G = 0`.

`multiexp_vartime(&pairs).is_identity()` returns true — forgery accepted, despite the victim never signing `c_v`. The flaw is entirely within the in-scope weight derivation at crypto/schnorr/src/aggregate.rs:132-143, mirroring the report's pattern of a check that is sound in isolation but fails in a shared evaluation context.
