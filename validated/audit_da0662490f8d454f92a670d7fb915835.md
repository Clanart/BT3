### Title
Missing slippage protection in `PublicDelegation.redeem`/`withdraw` allows commission-rate changes to reduce user proceeds - (File: contracts/bindings/publicdelegation/PublicDelegation.go)

### Summary
The `PublicDelegation` contract is Kaia's ERC4626-style staking vault for CN (Consensus Node) delegation: stakers deposit KAIA, receive shares, and later call `redeem(recipient, shares)` or `withdraw(recipient, assets)` to exit their position, with `previewRedeem`/`previewWithdraw` used off-chain to estimate proceeds. As in the reported bug class, these exit functions take no caller-supplied minimum-output (or maximum-shares-burned) parameter and no deadline, so the amount actually transferred can diverge from what the user previewed.

### Finding Description
`redeem(address _recipient, uint256 _shares)` and `withdraw(address _recipient, uint256 _assets)` are exposed as plain transactor methods with no slippage bound: [1](#0-0) [2](#0-1) .

The vault's exchange rate depends on `commissionRate`, which is mutable via an owner-facing update path, and the contract also emits a `SendCommission` event on distribution, confirming the commission is deducted from delegation rewards and factored into share/asset conversion at redemption time: [3](#0-2) [4](#0-3) .

Users rely on `previewRedeem`/`previewWithdraw` to estimate the assets they will receive for a given share/asset amount before submitting their transaction: [5](#0-4) . Because `redeem`/`withdraw` accept no minimum-assets-out or maximum-shares-burned parameter, if `commissionRate` (or the underlying CN staking reward/penalty state feeding the exchange rate) changes between the time the user signs their transaction and the time it is included on-chain (e.g., due to a pending `updateCommissionRate`/`updateCommissionTo` call, or reward/slashing events on the underlying `baseCnStaking`), the actual assets transferred to `_recipient` can be worse than what was previewed, with no on-chain check to revert the transaction.

This mirrors exactly the reported bug class in `StakedYuzuUSD`/`YuzuUSD`/`YuzuILP`: an ERC4626-like vault interaction function lacking slippage protection against fee/rate changes between submission and execution.

### Impact Explanation
Any staker (an unprivileged transaction sender interacting with `PublicDelegation`) who calls `redeem` or `withdraw` can receive materially fewer KAIA assets than expected if the commission rate or reward accrual changes in the block(s) between transaction signing and inclusion, with no mechanism to abort the transaction. This is a direct, unauthorized-value-movement risk to the staker (receiving less than agreed), matching Medium impact as in the source report — it does not enable protocol insolvency but does cause unexpected loss for individual users relying on previewed values.

### Likelihood Explanation
Commission rate changes and reward/penalty accrual on the underlying CN staking are routine, expected operational events (governance/owner actions and normal validator reward cycles), and transaction inclusion delay (mempool wait, MEV reordering, congestion) is common on any public chain. Any staker submitting a `redeem`/`withdraw` transaction is exposed each time these functions are used, making the likelihood Medium, consistent with the source finding.

### Recommendation
Add slippage-protection parameters to `redeem` and `withdraw` (e.g., `minAssetsOut`/`maxSharesIn`) that revert if the computed output/input from `previewRedeem`/`previewWithdraw` at execution time is worse than the caller's specified bound, and/or add a `deadline` parameter so stale transactions revert instead of executing with unexpected disparity — the same remediation recommended for `StakedYuzuUSD`/`YuzuUSD`/`YuzuILP`.

### Proof of Concept
1. Staker calls `previewRedeem(shares)` off-chain and observes an expected asset amount `A`.
2. Staker submits `redeem(recipient, shares)`: [1](#0-0) .
3. Before the transaction is mined, the contract owner calls `updateCommissionRate`-style function (commission rate is a stored, mutable state variable read at conversion time: [3](#0-2) ), increasing the effective commission taken from rewards backing the vault.
4. The staker's `redeem` transaction executes using the new, worse commission rate; the `Redeemed` event reflects fewer `Assets` than `A`, with no revert since no minimum-out check exists: [6](#0-5) .
5. The staker receives less than previewed with no recourse, confirming the missing slippage protection.
