This confirms the vulnerable path: `DiscardSelection` dialog holds `diff` and `selection` in React props/state captured at dialog-open time [1](#0-0) , and only when the user clicks "Discard changes" does it forward that stale `diff` object to `dispatcher.discardChangesFromSelection` [2](#0-1) , which flows unmodified into `discardChangesFromSelection()` in `apply.ts`, which builds a reverse patch from that stale diff and applies it with `git apply --unidiff-zero` directly to the working tree [3](#0-2) . There is no re-fetch or re-validation of the current file content/diff between confirmation and execution.

### Title
Stale-diff patch application in "Discard changes" allows silent corruption of unrelated working-tree lines - (File: app/src/lib/git/apply.ts)

### Summary
This is the closest Desktop analog to the smart-contract "missing slippage protection" bug class: an action is executed based on a value computed at preview time (`diff`) without re-validating that value against the current state at execution time. In `StakedYuzuUSD`, users approve a redeem based on a previewed asset amount that can drift before execution; in Desktop, users approve a "discard changes" operation based on a previewed diff/hunk selection that can drift (file mutated by an external tool, a background `git` operation, an editor autosave, or a checkout/fetch triggered by an attacker-controlled repository) before the patch is actually applied.

### Finding Description
`discardChangesFromSelection()` never re-derives the diff from the current working-directory state before generating and applying the reverse patch: it uses whatever `ITextDiff` object was handed to it, unmodified, from the moment the user opened the confirmation dialog [3](#0-2) . That diff is captured once in `Changes`/`SeamlessDiffSwitcher` when rendering, stored as a prop on `DiscardSelection`, and re-used unchanged after the user dismisses a confirmation modal [4](#0-3) [2](#0-1) . `formatPatchToDiscardChanges` then builds a reverse unified diff purely from that possibly-stale `diff.hunks`/line offsets and the `DiffSelection` [5](#0-4) . The resulting patch is applied with `git apply --unidiff-zero`, which is zero-context and therefore relies entirely on the encoded line numbers matching the *current* file — it does not tolerate drift and will silently apply the hunk to whatever lines happen to be at those positions instead of failing loudly, because zero-context hunks don't need surrounding text to match [6](#0-5) .

If the on-disk file changes between the moment the diff is rendered/selected and the moment the user confirms discard — e.g., a build tool, editor autosave, git hook, or an attacker-influenced fetch/checkout mutates the file, or the user runs another Desktop operation concurrently (rebase, pull, LFS smudge) — the offsets in the stale diff no longer correspond to the actual content. Because `--unidiff-zero` matches by line number rather than content, `git apply` can succeed silently while discarding/inserting the wrong lines, corrupting unrelated content or discarding work the user never selected. No integrity check (e.g., comparing a hash of the file at generation time vs. apply time, or re-fetching the diff before staging) exists anywhere in this path.

### Impact Explanation
The corrupted value is the working-tree content of the file being "discarded" — the user believes they are reverting a specific, previewed set of lines, but the actually-applied patch can land on different lines if the file drifted, silently corrupting what will subsequently be staged/committed/pushed. This mirrors the audit's "unexpected asset amounts" impact: the user's expectation (based on a stale preview) diverges from the actual on-disk/on-chain outcome, without any confirmation of drift. Impact is Medium: it does not itself grant code execution or credential exfiltration, but it can silently corrupt what a user commits/pushes, matching the "silent corruption of what the user commits or pushes" category called out as valid impact.

### Likelihood Explanation
Likelihood is Medium: it requires a concurrent modification of the exact file between diff render and the user's confirm click, which is a normal, unprivileged occurrence (autosave, linter/formatter, background git hook, or file changes introduced by a fetch/checkout the user triggers on an attacker-controlled repo shortly after opening the discard dialog). No local/admin/malware assumption is needed — only ordinary concurrent file activity or a maliciously timed remote update.

### Recommendation
Re-fetch the working-directory diff for the target file immediately before constructing and applying the discard patch (or immediately before staging the patch in `applyPatchToIndex`), and abort/re-prompt the user if the freshly-fetched diff differs from the one the selection was made against. Alternatively, compute and compare a content hash of the file at dialog-open time vs. apply time, and fail closed (rather than silently applying by line offset) when they differ.

### Proof of Concept
1. Modify a tracked file with several hunks; open Desktop's Changes view and select a subset of lines to discard, triggering the `ConfirmDiscardSelection` popup, which captures the current `diff`/`selection` as props [7](#0-6) .
2. Before clicking "Discard changes" in the dialog, externally modify the same file (e.g., an editor autosave, a script, or a git hook run as part of another Desktop action) so that line numbers shift but the file is still "modified" from Desktop's perspective.
3. Click "Discard changes"; `DiscardSelection.discard()` sends the stale `diff`/`selection` unchanged to `dispatcher.discardChangesFromSelection` [2](#0-1) .
4. `discardChangesFromSelection()` builds the reverse patch from the stale hunks and applies it via `git apply --unidiff-zero` [8](#0-7) , which matches by line offset with zero context and applies successfully even though the underlying content shifted, discarding/altering lines the user never intended to touch, with no error or warning surfaced to the user.

```typescript
export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
```

```typescript
export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}
```
