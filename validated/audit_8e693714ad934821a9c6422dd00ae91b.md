### Title
Unvalidated output-type attribution lets any sender classify a deposit as an internal protocol output, breaking deposit accounting - (File: processor/src/networks/bitcoin.rs)

### Summary

Analogous to `Pools.mintSynth` accepting an attacker-chosen `base` that is then blindly used for reserve accounting, `Bitcoin::get_outputs` determines an output's `OutputType` solely by which registered script offset matched in `Scanner::scan_transaction`, with no check that the output arrived at the address intended for that purpose. An unprivileged sender can pay to the protocol's Branch/Change/Forwarded P2TR scripts (deterministic public functions of the group key) and have the deposit classified as an internal output rather than an `External` deposit, so it is never credited and never carries deposit data.

### Finding Description

`Scanner::scan_transaction` returns a `ReceivedOutput` for any transaction output whose `script_pubkey` equals any registered script, carrying only the scalar `offset` — not the intended purpose (`networks/bitcoin/src/wallet/mod.rs:199-214`). `get_outputs` then recovers the type purely from that offset: `let kind = kinds[offset_repr_ref];` (`processor/src/networks/bitcoin.rs:695`). Deposit metadata is attached only when `output.kind == OutputType::External` (`processor/src/networks/bitcoin.rs:731-735`).

`branch_address`, `change_address`, and `forward_address` derive these scripts via fixed offsets from the public group key (`processor/src/networks/bitcoin.rs:661-674`), so any observer can compute them. The code assumes "matching a registered script implies intended type", the same flawed assumption as `mintSynth` assuming "`base` is a base token". A payment to the Change or Branch script produces an `OutputType::Change`/`Branch` output that downstream scheduling treats as protocol-owned change — it is aggregated/spent by the multisig but never credited to the depositor, and (for `Forwarded`) may trigger automated forwarding, consuming multisig inputs/fees on an attacker-chosen output.

### Impact Explanation

Deposits sent to a non-External script are permanently uncredited: the funds enter multisig-controlled UTXOs but are routed into the internal Branch/Change pipeline, so the depositor's balance is never updated — loss of user funds via misattribution. Payments to the Forwarded script additionally cause the scheduler to spend real fee budget on forwarding attacker-placed outputs (griefing). Root cause: `get_outputs` trusts the script match as type attribution, mirroring H-13's uncredentialed `base` selecting the wrong reserve.

### Likelihood Explanation

Any Bitcoin user can compute the offset addresses (pure functions of the public group key and fixed offsets registered in `scanner(key)`). Accidental or malicious misdirected payments are realistic; no privileges, collusion, or key material required — just a normal Bitcoin transaction, which is squarely within the accepted attacker model.

### Recommendation

Don't let senders choose the output's semantic type. Emit distinct-address validation: only treat payments to the advertised external deposit address as `External` deposits, and/or have `get_outputs` drop or quarantine outputs matching Branch/Change/Forwarded scripts that were not produced by a protocol-constructed transaction (match against expected TXIDs from the scheduler's own plans rather than raw script scans).

### Proof of Concept

1. Obtain the group key; call `scanner(key)`'s offset logic (equivalently `change_address`/`forward_address`) to compute `addr_change = address_from_key(key + G * offsets[OutputType::Change])`.
2. Send a normal Bitcoin transaction paying `addr_change`.
3. `get_outputs` scans it, finds `kinds[offset] == OutputType::Change`, emits an `Output` with `kind: Change`, `data: vec![]`. The deposit is never credited as `External`; it is swept as protocol change.

Caveat: I could not fully trace downstream scheduler handling of misclassified `Change` outputs within available iterations, so the exact fund-disposition (immediate aggregation vs. pending-plan confusion) is inferred from `OutputType` semantics rather than fully verified end-to-end.
