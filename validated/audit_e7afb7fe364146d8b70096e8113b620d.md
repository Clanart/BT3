### Title
Copilot-resolved conflict content is staged and committed without verifying it actually resolves the on-disk conflict - ([File: app/src/lib/stores/app-store.ts])

### Summary
The Copilot conflict-resolution feature reassembles per-hunk model output into full file content ahead of time, then, when the user clicks "Continue Merge", writes that stored content straight to disk and stages it with `git add` — without ever re-validating that the written content actually corresponds to the conflict markers currently present in the working tree, or that it contains no leftover markers. This mirrors the Pendle bug class: code trusts that an external computation (there, `market.mint()`/`skim()`; here, the AI reassembly step) produced the exact expected result, and acts on that trust (staging/committing) without checking the actual outcome, allowing attacker-influenced input to silently corrupt what gets committed.

### Finding Description
`reassembleResolutions`/`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` splice model-provided `resolvedContent` values into the raw file positionally, based on however many conflict-marker blocks the parser finds in the file captured at prompt-build time [1](#0-0) . The repository content that produces these markers — including branch names, commit messages, PR descriptions, and the literal conflicting text — is entirely attacker-controlled if the attacker can get a crafted branch, commit, or PR merged/fetched into the user's repository (the system prompt explicitly ingests "recent commit messages and/or PR title/description" and conflict hunks) [2](#0-1) .

Later, when the user confirms via "Continue Merge", `_applyCopilotConflictResolutions` writes the previously-stored `resolution.resolvedContent` directly to disk and immediately stages the path with `git add`, with no re-check that the resulting file no longer contains conflict markers, that its structure matches what the diff preview showed, or that the hunk boundaries used at reassembly time still correspond to the current on-disk conflict state: [3](#0-2) 

The only safety check performed is whether the user resolved the file *externally* (no more markers at all) — there is no check that the content Desktop is about to write and stage is itself well-formed (free of `<<<<<<<`/`=======`/`>>>>>>>` sequences, or matching the expected number of resolved hunks). Because the model output is JSON text produced from attacker-supplied repository content, a crafted set of nested/duplicated/malformed marker-like sequences embedded in file content, commit messages, or PR text can cause the model (or the reassembly parser, which explicitly treats malformed marker blocks as "regular content" and passes them through unchanged) to produce a resolvedContent string whose marker count/positions no longer align 1:1 with what's actually in the working tree merge state [4](#0-3) . The result is written and staged unconditionally.

### Impact Explanation
If reassembly produces content that doesn't faithfully or completely resolve the real conflict (e.g. residual conflict markers, hunks applied to the wrong location, or a hunk silently dropped because the marker-scan found a different number of blocks than the model was told about), that content is committed as part of a merge/rebase/cherry-pick with no further human-reviewable diff against the live working tree at write time. This is a silent corruption of what the user commits — the exact "Valid Impact" category called out in the task (attacker controls fetched/merged repository content; result is silent corruption of what gets committed/pushed). Depending on the corrupted content, this can range from broken code with literal conflict markers being merged into `main`, to attacker-influenced text (e.g. from a malicious commit message or PR body used as model context) being spliced into unrelated hunks of a file.

### Likelihood Explanation
Exploitation requires only that a victim (a) uses the "Resolve with Copilot" feature on a repository containing attacker-authored branches/commits/PRs with crafted conflicting content and misleading/malformed conflict-marker-like text or metadata, and (b) clicks "Continue Merge" — normal, expected usage. No local access, admin rights, or social engineering beyond a routine "someone else's branch conflicts with mine" workflow is needed; the attacker's payload lives entirely in ordinary git objects (commits, branches, PR descriptions) that get pulled/fetched. The gap (write-time trust of pre-computed content with no post-hoc structural validation) is a real, observed absence of a check rather than a hypothetical.

### Recommendation
Before writing `resolution.resolvedContent` to disk and staging it in `_applyCopilotConflictResolutions`, re-validate the reassembled content against the *current* on-disk file: confirm the number of resolved hunks still matches the number of conflict marker blocks currently present, and reject/flag any resolution whose output still contains `<<<<<<<`, `=======`, or `>>>>>>>` sequences (outside of legitimately-preserved user content) before calling `git add`. Treat any mismatch as a hard failure that routes the file back to manual resolution rather than silently staging it.

### Proof of Concept
1. Attacker opens a PR/branch against the victim's repository whose diff is engineered to produce a merge conflict containing conflict-marker-like text sequences within the conflicting hunks themselves (e.g. a hunk whose "ours"/"theirs" content embeds `<<<<<<<`/`=======`/`>>>>>>>` literal strings, or unusual line-ending/encoding tricks), and whose commit message/PR description is crafted to bias the model's reasoning.
2. Victim merges/fetches the branch in Desktop, hits a conflict, and clicks "Resolve with Copilot".
3. The model, working from attacker-supplied file content and PR/commit text, returns a `hunks` array whose count/content doesn't cleanly correspond 1:1 to the actual conflict blocks the parser detects (or the reassembly's malformed-marker pass-through logic misclassifies a block).
4. `reassembleResolvedFile` splices the mismatched hunks positionally, producing a file that still contains marker text or has hunk content applied in the wrong place [1](#0-0) .
5. User clicks "Continue Merge"; `_applyCopilotConflictResolutions` writes this content and runs `git add` immediately, with no structural re-validation [5](#0-4) , and the corrupted content is committed/pushed.

Note: I was unable to fully inspect the body of `reassembleResolvedFile`'s marker-matching algorithm (only its test cases) before running out of tool budget, so the exact conditions under which hunk-count/marker-count mismatch occurs are inferred from the documented test behavior ("malformed markers... treated as regular content") rather than directly read from the implementation. A Devin session with full repo access should confirm the precise mismatch trigger in `reassembleResolvedFile` before treating this as fully verified.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
