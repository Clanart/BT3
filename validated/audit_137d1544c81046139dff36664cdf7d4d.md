### Title
Unauthenticated senders can forge internal (Branch/Change/Forwarded) outputs and spoof `presumed_origin`, misattributing deposits to arbitrary Bitcoin addresses - ([File: processor/src/networks/bitcoin.rs])

### Summary
CVE-2021-27231 is an ownership-binding failure: an authenticated user could attach a resource (a subdomain) under a domain belonging to someone else because the system never checked ownership of the parent domain. The same class exists in Serai's Bitcoin output scanner. `Bitcoin::get_outputs` in `processor/src/networks/bitcoin.rs` classifies every scanned output purely by which deterministic offset its `script_pubkey` matches (`External`, `Branch`, `Change`, `Forwarded`), and derives `presumed_origin` from the *first input* of the paying transaction — neither of which is bound to any authenticated identity or to an actual protocol operation. Any unprivileged Bitcoin user can compute the deterministic branch/change/forwarded addresses (the offsets are fixed `hash_to_F(KEY_DST, ...)` scalars applied to the public group key) and craft a transaction whose first input is an arbitrary script, causing the processor to record an internal-type output with a fully attacker-chosen origin.

### Finding Description
`scanner()` registers fixed offsets derived only from the public group key: `BRANCH_OFFSET`, `CHANGE_OFFSET`, `FORWARD_OFFSET` are `Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"branch"/"change"/"forward")` (`processor/src/networks/bitcoin.rs:308-344`). These offsets and the resulting P2TR scriptPubKeys (`key + G*offset`) are publicly computable by anyone who knows the group key.

`get_outputs` then (lines 686-740):
1. Matches outputs solely by `script_pubkey` via `Scanner::scan_transaction` (`networks/bitcoin/src/wallet/mod.rs:199-214`) — `self.scripts.get(&output.script_pubkey)` with no check that the payer is the protocol or a registered depositor.
2. Labels the output `OutputType::Branch/Change/Forwarded` purely from the offset — so an external payment to the deterministic change or branch address is indistinguishable from a genuine internal output.
3. Sets `presumed_origin` for **every** matched output in the transaction from `tx.input[0]`'s spent `script_pubkey` (lines 714-729). The payer fully controls `tx.input[0]`, so they can make any deposit appear to originate from any address whose output they can spend — or from any address at all in terms of reported origin metadata.
4. Attaches `extract_serai_data(tx)` to `External`-kind outputs (lines 730-734), letting the same payer attach an arbitrary `InInstruction`.

This is precisely the HestiaCP pattern: a namespace (the set of scripts/offsets owned by the group key, and the origin attribution) where the system fails to bind a claimed association (internal output type, sender identity) to the party actually entitled to it.

### Impact Explanation
- An attacker can deposit to the `Change`/`Branch`/`Forwarded` addresses and have those funds classified as internal outputs rather than external deposits, corrupting accounting: funds the protocol believes are its own change/branch flows were never part of such a flow, and conversely attacker funds may be swept/aggregated under assumptions that don't hold.
- `presumed_origin` spoofing lets an attacker make a deposit appear to originate from a victim's address, misdirecting any refund/attribution logic that consumes `presumed_origin`.
- Combined with `extract_serai_data`, an unauthenticated party controls both the origin metadata and the instruction payload of a "received" output — service/email spoofing in the CVE maps to deposit/instruction spoofing here.

### Likelihood Explanation
Fully reachable by any unprivileged Bitcoin user: it requires only sending a standard transaction (public inputs — Bitcoin transactions they send). No key material, collusion, or validator misbehavior is needed. The group key is public, so all four scriptPubKeys are computable offline. The only mitigation is the `DUST` floor (`output.balance().amount.0 >= N::DUST`, `processor/src/multisigs/scanner.rs:564`), which merely sets a minimum cost. Likelihood is limited mainly by downstream consumers: the practical damage depends on how the processor credits `presumed_origin`/output kind, which could not be fully traced in this scan — some consumers may treat `presumed_origin` as heuristic-only (it is named "presumed").

### Recommendation
- Do not emit `Branch`/`Change`/`Forwarded`-typed outputs for transactions the protocol did not create; match those scripts only when the txid is a known/planned protocol transaction (e.g., cross-check against `EventualitiesTracker` or the scheduler's expected transactions).
- Treat `presumed_origin` as untrusted: either remove it, rename enforcement to make clear it is attacker-controlled metadata, or only trust it when the first input is a known protocol-owned UTXO.
- Document or enforce that `External` deposits' `data`/`presumed_origin` must never authorize actions crediting a different account than the actual sender.

### Proof of Concept
```rust
// Anyone knowing the group key computes the internal addresses:
let branch = *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch"));
let change = *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change"));

// Attacker funds any P2PKH/P2WPKH output they control (input[0]), then pays:
let tx = Transaction {
  input: vec![TxIn { previous_output: attacker_outpoint, /* signed by attacker */ .. }],
  output: vec![TxOut {
    value: Amount::from_sat(Bitcoin::DUST),          // passes the dust filter
    script_pubkey: p2tr_script_buf(group_key + ProjectivePoint::GENERATOR * change).unwrap(),
  }],
  ..
};

// Bitcoin::get_outputs reports this as Output { kind: OutputType::Change,
//   presumed_origin: Some(attacker-chosen script/address), .. }
// even though no protocol change transaction ever occurred and the
// "origin" address may be a victim's address.
```

Key supporting code:
- `processor/src/networks/bitcoin.rs:308-346` — deterministic, publicly computable offsets.
- `processor/src/networks/bitcoin.rs:686-736` — classification by `script_pubkey` only and `presumed_origin` taken from `tx.input[0]`.
- `networks/bitcoin/src/wallet/mod.rs:199-214` — `scan_transaction` matches any output to a registered script with no sender binding.

Uncertainty: I could not fully trace downstream consumers of `Output::kind()`/`presumed_origin` (index excerpt limits), so severity rests on classification/origin spoofing being consumed for crediting or refund decisions; if those fields are purely informational everywhere, impact degrades toward low.
