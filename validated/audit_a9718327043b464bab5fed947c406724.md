### Title
Unlimited passphrase attempts on daemon `unlock_keyring`/`validate_keyring_passphrase` RPCs enable brute force of the keyring master passphrase - ([File: chia/daemon/server.py])

### Summary
The Chia daemon exposes `unlock_keyring` and `validate_keyring_passphrase` websocket RPC commands that check a caller-supplied string against the keyring master passphrase with no attempt counter, lockout, or delay. Any local RPC/daemon client that can reach the daemon websocket (a "local RPC caller" per the trust boundary already recognized by `chia/daemon/`) can issue an unbounded number of guesses to brute force the passphrase that protects all private keys, analogous to CVE-2016-3084's "no limit on active guesses" flaw.

### Finding Description
`WebSocketServer.unlock_keyring()` and `WebSocketServer.validate_keyring_passphrase()` call `Keychain.master_passphrase_is_valid(key, force_reload=True)` directly on every request and return success/failure with no state tracking across calls: [1](#0-0) 

The only place in the codebase that enforces an attempt limit (`MAX_RETRIES = 3`, `FAILED_ATTEMPT_DELAY = 0.5`, raising `KeychainMaxUnlockAttempts`) is the *interactive CLI prompt* helper `obtain_current_passphrase()`, which is a client-side convenience loop, not a server-side control: [2](#0-1) 

The underlying passphrase check itself (`FileKeyring.check_passphrase`) also performs no rate limiting or attempt bookkeeping — it simply tries to decrypt and returns a bool: [3](#0-2) 

Because the RPC-facing entry points (`unlock_keyring`, `validate_keyring_passphrase`, and `set_keyring_passphrase`'s `current_passphrase` check) call these primitives directly without going through `obtain_current_passphrase()`, none of the `MAX_RETRIES`/`KeychainMaxUnlockAttempts` protection applies to daemon RPC traffic. A caller with network access to the daemon websocket can send an arbitrary number of `unlock_keyring`/`validate_keyring_passphrase` requests, each independently checked with no backoff, no lockout counter, and no rate limit — mirroring the UAA flaw where multiple concurrently-valid reset codes let an attacker try unlimited guesses.

### Impact Explanation
A successful brute force of the master passphrase yields full plaintext access to the keyring (`Keychain.set_cached_master_passphrase` on success), i.e., every private key managed by that node/wallet. This is a direct path to unauthorized coin movement: once unlocked, an attacker with local daemon access can derive wallet keys and sign/spend arbitrary coins controlled by the keys, fully compromising custody — a High-severity outcome consistent with the CVSS of the original advisory.

### Likelihood Explanation
Exploitation requires network/socket reachability to the daemon's TLS websocket, which normally requires possessing the daemon's private client certificate. In shared-host, container, or misconfigured-binding scenarios, or where the client cert is available to a lower-privileged local process/user than the passphrase itself, an attacker distinct from the passphrase holder can still reach these RPCs. Given that no throttling exists at all (unlike the deliberate `MAX_RETRIES=3` + delay in the CLI path), any reachable caller can attempt as many guesses per second as the websocket/CPU allows, making brute force practical against weak or short user-chosen passphrases.

### Recommendation
Move `MAX_RETRIES`/`FAILED_ATTEMPT_DELAY`-style lockout (and ideally exponential backoff or a hard lockout with the existing `KeychainMaxUnlockAttempts` exception) into the server-side RPC handlers `unlock_keyring`, `validate_keyring_passphrase`, and `set_keyring_passphrase`'s current-passphrase check in `chia/daemon/server.py`, tracked per-connection or per-daemon-process, so repeated failed passphrase attempts over the websocket are throttled or locked out the same way the interactive CLI path already is.

### Proof of Concept
1. Connect to the daemon's TLS websocket with a valid local client certificate (as any local RPC caller can, per `create_payload`/`connect_to_daemon` usage in `chia/daemon/client.py`).
2. Repeatedly send `create_payload("validate_keyring_passphrase", {"key": guess}, "poc", "daemon")` (or `unlock_keyring`) with different `guess` values in a tight loop, as exercised functionally (without any limiting) in `chia/_tests/core/daemon/test_daemon.py` lines 935-981.
3. Observe that every request is processed independently by `WebSocketServer.validate_keyring_passphrase()`/`unlock_keyring()` with no increasing delay, counter, or lockout response, allowing unlimited automated guessing until the correct passphrase is found. [4](#0-3)

    async def unlock_keyring(self, websocket: WebSocketResponse, request: dict[str, Any]) -> dict[str, Any]:
        success: bool = False
        error: str | None = None
        key: str | None = request.get("key", None)
        if type(key) is not str:
            return {"success": False, "error": "missing key"}

        try:
            if Keychain.master_passphrase_is_valid(key, force_reload=True):
                Keychain.set_cached_master_passphrase(key)
                success = True
                # Inform the GUI of keyring status changes
                self.keyring_status_changed(await self.keyring_status(), "wallet_ui")
            else:
                error = "bad passphrase"
        except Exception as e:
            tb = traceback.format_exc()
            self.log.error(f"Keyring passphrase validation failed: {e} {tb}")
            error = "validation exception"

        if success and self.run_check_keys_on_unlock:
            try:
                self.log.info("Running check_keys now that the keyring is unlocked")
                check_keys(self.root_path)
                self.run_check_keys_on_unlock = False
            except Exception as e:
                tb = traceback.format_exc()
                self.log.error(f"check_keys failed after unlocking keyring: {e} {tb}")

        response: dict[str, Any] = {"success": success, "error": error}
        return response

MAX_RETRIES = 3


def prompt_for_passphrase(prompt: str) -> str:
    if sys.platform == "win32" or sys.platform == "cygwin":
        print(prompt, end="", flush=True)
        prompt = ""
    return getpass(prompt)


def obtain_current_passphrase(prompt: str = DEFAULT_PASSPHRASE_PROMPT, use_passphrase_cache: bool = False) -> str:
    from chia.util.keyring_wrapper import KeyringWrapper

    """
    Obtains the master passphrase for the keyring, optionally using the cached
    value (if previously set). If the passphrase isn't already cached, the user is
    prompted interactively to enter their passphrase a max of MAX_RETRIES times
    before failing.
    """

    if use_passphrase_cache:
        passphrase, validated = KeyringWrapper.get_shared_instance().get_cached_master_passphrase()
        if passphrase:
            # If the cached passphrase was previously validated, we assume it's... valid
            if validated:
                return passphrase

            # Cached passphrase needs to be validated
            if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
                return passphrase
            else:
                # Cached passphrase is bad, clear the cache
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(None)

    # Prompt interactively with up to MAX_RETRIES attempts
    for i in range(MAX_RETRIES):
        colorama.init()

        passphrase = prompt_for_passphrase(prompt)

        if KeyringWrapper.get_shared_instance().master_passphrase_is_valid(passphrase):
            # If using the passphrase cache, and the user inputted a passphrase, update the cache
            if use_passphrase_cache:
                KeyringWrapper.get_shared_instance().set_cached_master_passphrase(passphrase, validated=True)
            return passphrase

        time.sleep(FAILED_ATTEMPT_DELAY)
        print("Incorrect passphrase\n")
    raise KeychainMaxUnlockAttempts
