## Title
Gov `RefundDeposits`/`DeleteDeposits` iterate an attacker-inflatable, unbounded deposit list synchronously in `EndBlock`, unlike votes which received an explicit per-block budget fix - ([File: sei-cosmos/x/gov/keeper/deposit.go])

### Summary
Anyone can call `MsgDeposit` on any depositable proposal with an arbitrarily small `depositAmount` from any number of distinct addresses. Each call creates one more entry keyed by `(proposalID, depositor)` in the gov module's deposit store, an array whose size is entirely attacker-controlled and unbounded. When the proposal finalizes, `RefundDeposits` (or `DeleteDeposits` for vetoed proposals) iterates **every** deposit for that proposal synchronously, in a single `EndBlock` call, with no per-block work budget — the same DoS class as the OpenQ `BountyCore.getLockedFunds`/`refundDeposit` bug, where an unbounded, cheaply-inflatable array is fully scanned inside a fund-release code path.

### Finding Description
`AddDeposit` accepts any positive `depositAmount` and does not enforce a per-call minimum deposit; it only checks that the running `proposal.TotalDeposit` eventually crosses `MinimumDeposit` to activate voting: [1](#0-0) . Each distinct depositor address creates a brand-new, independent deposit record, so an attacker controlling many funded addresses can inflate the number of stored deposits for a single proposal without bound.

At proposal finalization time, `EndBlocker` unconditionally calls `keeper.RefundDeposits(ctx, proposal.ProposalId)` or `keeper.DeleteDeposits(ctx, proposal.ProposalId)` once the (budgeted) tally completes: [2](#0-1) . Both of these functions fully iterate every deposit for the proposal in one synchronous pass with `keeper.IterateDeposits`, performing a bank transfer (or burn) and a store delete per entry: [3](#0-2)  and [4](#0-3) .

This is the exact structural analog of the OpenQ report: `receiveFunds` lets anyone cheaply push into an unbounded `deposits` array, and the refund path (`getLockedFunds`/`refundDeposit`) later scans the *entire* array in one call with no bound, so a spammer can make that scan too expensive to complete. Here, `MsgDeposit` is the unbounded-push primitive and `RefundDeposits`/`DeleteDeposits` is the full unbounded scan performed to release escrowed funds.

Notably, the same module already recognizes and defends against exactly this class of issue for **votes**: proposal tallying was rewritten to process a bounded number of vote records per block (`TallyIncremental`, `remainingRecords`) specifically to avoid "initializing validator snapshots for an unbounded number of proposals" and unbounded per-block work: [5](#0-4) , [6](#0-5) . No equivalent budget exists for deposit refund/burn, which remain an all-at-once, unbudgeted loop.

### Impact Explanation
Because `RefundDeposits`/`DeleteDeposits` run inside the deterministic, consensus-critical `EndBlock`/`ProcessBlock` path (all validators execute the same state transition identically), an attacker-inflated deposit list forces every validator to perform the same large synchronous loop of bank transfers/store writes at the same block height. This can:
- Delay block production well beyond acceptable bounds (block delay), since the work is unbudgeted and proportional to attacker-controlled input size, or
- In degenerate cases, panic deterministically across all nodes inside `ProcessBlock`'s recover handler [7](#0-6) , which is recovered into an error but reproduces identically on every validator, functionally halting block production (chain halt) until the offending proposal's finalization logic is bypassed via an emergency upgrade.
- Escrowed depositor funds held in the gov `ModuleAccount` remain unrefunded/unresolved for as long as this synchronous pass cannot complete, mirroring the "locked funded bounty" freezing described in the source report.

### Likelihood Explanation
No special privilege is required: `MsgDeposit` is a standard, permissionless Cosmos SDK message reachable by any funded account (or via the EVM `Gov` precompile's deposit path). An attacker only needs many funded addresses each submitting a minimal deposit (dust amount) on an already-depositable proposal; there is no per-deposit minimum or per-proposal cap on the number of distinct depositors enforced in `AddDeposit`.

### Recommendation
Apply the same fix already used for vote tallying to deposit refund/burn: process deposits for a finalizing proposal in bounded batches per block (a resumable cursor analogous to `TallyProgress`), so an unbounded number of attacker-created deposit records cannot force an unbudgeted, all-at-once loop inside `EndBlock`. Alternatively/additionally, enforce a minimum per-deposit amount and/or cap the number of distinct depositor entries counted per proposal to make the sybil-inflation attack economically unfeasible.

### Proof of Concept
1. Submit (or wait for) a proposal in `StatusDepositPeriod`/`StatusVotingPeriod`.
2. From N distinct funded accounts, each submit `MsgDeposit{ProposalId: id, Depositor: addr_i, Amount: 1usei}` — `AddDeposit` accepts this with no minimum check [1](#0-0) , creating N deposit store entries.
3. When the proposal's voting period ends and it is accepted/rejected-without-veto, `EndBlocker` calls `RefundDeposits`, which synchronously iterates and refunds all N entries in one `EndBlock` execution [3](#0-2) .
4. For sufficiently large N, this single-block, unbudgeted loop (unlike the budgeted vote tally) drives block processing time up, risking a block-time SLA breach or a deterministic panic/halt across all validators at that height.

// RefundDeposits refunds deposits whose recipients can receive funds and deletes
// their records. Deposits for unpayable recipients remain recorded and backed by
// the governance module balance.
func (keeper Keeper) RefundDeposits(ctx sdk.Context, proposalID uint64) {
	store := ctx.KVStore(keeper.storeKey)

	keeper.IterateDeposits(ctx, proposalID, func(deposit types.Deposit) bool {
		depositor := sdk.MustAccAddressFromBech32(deposit.Depositor)
		if keeper.bankKeeper.BlockedAddr(depositor) || !keeper.bankKeeper.CanSendTo(ctx, depositor) {
			// Retain the deposit so its record continues to account for the backing
			// module balance. Recovering a permanently unreceivable deposit requires
			// a migration.
			return false
		}

		err := keeper.bankKeeper.SendCoinsFromModuleToAccount(ctx, types.ModuleName, depositor, deposit.Amount)
		if err != nil {
			panic(err)
		}

		store.Delete(types.DepositKey(proposalID, depositor))
		return false
	})
}
