### Title
Unverified-PoP blame path in `KeyMachine::calculate_share` leaks the ECDH key for an attacker-chosen message key, decrypting other participants' encrypted shares - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The bug class is exposure of sensitive information: an interface returns secret-bearing material for inputs the requester was not entitled to read. In PedPoP, `KeyMachine::calculate_share` emits an `EncryptionKeyProof` (the ECDH shared key `enc_key · msg.key` plus a DLEq proof) inside `PedPoPError::InvalidShare` when the decrypted share bytes fail `C::F::from_repr`, before the message's Schnorr proof-of-possession has actually been verified. The PoP is only *queued* into the `BatchVerifier` inside `Encryption::decrypt`; `batch.verify_with_vartime_blame()` runs later. A faulty sender can therefore attach an arbitrary `key` point with a garbage PoP and force the victim to publish a valid ECDH key for it, which decrypts any `EncryptedMessage` using that same `key` — including an honest participant's secret share addressed to the victim.

### Finding Description
`Encryption::decrypt` batch-queues the per-message PoP and immediately computes `key = ecdh(enc_key, msg.key)`, returning the plaintext plus `EncryptionKeyProof { key, dleq }` unconditionally (`crypto/dkg/pedpop/src/encryption.rs:479-500`). In `calculate_share`, the `from_repr` failure returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` at `crypto/dkg/pedpop/src/lib.rs:480-482`, while the PoP is only checked inside `batch.verify_with_vartime_blame()` at `lib.rs:493`. When the failure *is* detected by the batch verifier, `BatchId::Decryption(l)` correctly yields `blame: None` — proving the intended invariant is "no decryption-key disclosure without a valid PoP". The early `from_repr` return violates that invariant: the blame proof is published although the PoP was never verified.

The PoP exists precisely to prevent this disclosure — the comment at `encryption.rs:84-90` explains that without proof-of-possession of `key`, an attacker replaying a victim-intended `key` would cause the victim to reveal `b·key` and leak the real message. The `from_repr` path is a residual bypass of that defense: it releases `b·msg.key` for a `key` whose PoP is invalid.

### Impact Explanation
A malicious DKG participant (an unprivileged party feeding `EncryptedMessage` bytes into `calculate_share`) crafts a share message with `key` set to the `key` field `Ka` of an honest participant Alice's `EncryptedMessage` addressed to the victim (the blame arbitration model in `AdditionalBlameMachine` requires these messages be observable/authenticatable, so `Ka` is available), an invalid `pop`, and arbitrary ciphertext. The victim decrypts to uniform garbage and — for fields like Ristretto/Ed25519 where only ~`l/2^256` ≈ 6% of 32-byte strings are canonical — fails `from_repr` with ~94% probability, returning `InvalidShare` carrying `EncryptionKeyProof { key = b·Ka }`. Anyone receiving this published blame proof can apply `cipher(context, b·Ka)` to Alice's ciphertext and recover her encrypted `SecretShare` to the victim — a DKG secret share never intended for the attacker, and a reusable decryption oracle: every `EncryptedMessage` to that victim under that key is exposed.

### Likelihood Explanation
The attack requires no secret knowledge: the PoP is never checked on this path, so the attacker need not know the discrete log of `key`. Success probability per attempt is `1 - l/2^256` (≈ 94% for Ristretto-class scalars; for fields like secp256k1 where `n ≈ 2^256` the attack rarely triggers via `from_repr`, though any non-canonical-garbage path still applies). One honest share can be targeted per session, and the attack repeats each DKG attempt.

### Recommendation
Do not attach the `EncryptionKeyProof` until the message's PoP has been verified. Concretely, in `calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-499`), hold the decrypted bytes without interpreting them until after `batch.verify_with_vartime_blame()` succeeds, or restructure so a non-canonical share maps to `BatchId::Share(l)`-style handling that first confirms the queued `BatchId::Decryption(l)` PoP statement passed — e.g., verify the batch before `from_repr`, or on `from_repr` failure verify the PoP statement alone before releasing `blame`. A message whose PoP fails must never yield a decryption-key proof.

### Proof of Concept
```rust
// Attacker Eve (participant e) in a PedPoP session against victim Bob (participant b).
// Eve observed Alice's honest EncryptedMessage to Bob, whose `key` field is Ka.

// 1. Eve crafts a share message reusing Alice's message key, with an invalid PoP
//    and arbitrary ciphertext bytes.
let forged = EncryptedMessage::<C, SecretShare<C::F>> {
    key: Ka,                                   // copied from Alice's message
    pop: SchnorrSignature::<C> { R: random_G, s: random_F }, // invalid PoP
    msg: Zeroizing::new(SecretShare::<C::F>(random_bytes)),  // garbage
};

// 2. Bob runs calculate_share with shares including `forged` under sender = e.
//    decrypt() queues the PoP (never verified on this path) and returns
//    EncryptionKeyProof { key: enc_key_bob * Ka, dleq }.
//    Decrypted bytes are garbage; with ~94% probability C::F::from_repr fails and:
//    Err(PedPoPError::InvalidShare { participant: e, blame: Some(proof) })
//    is returned — revealing b*Ka + a DLEq proof despite the forged PoP.

// 3. Eve (or anyone receiving the published blame) computes
//    cipher(context, proof.key).apply_keystream(alice_msg.msg)
//    and recovers Alice's SecretShare to Bob — confidential share material.
```
