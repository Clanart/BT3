### Title
Change outputs are created when below Serai's spendable-dust threshold, burning funds as permanently unspendable outputs — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to the Allo report — where a threshold/rounding gap lets value escape the intended accounting — `SignableTransaction::new` decides whether to emit a change output using the raw Bitcoin relay dust limit (`DUST = 546`), while the Serai processor defines its own economic dust threshold (`Bitcoin::DUST = 10_000`) below which outputs are deliberately dropped as not worth spending. A leftover in the range `[546, 10_000)` therefore produces a change output that Serai itself considers uneconomical to ever spend, silently locking those satoshis in the multisig.

### Finding Description
In `SignableTransaction::new`, change handling is:

```rust
// networks/bitcoin/src/wallet/send.rs
pub const DUST: u64 = 546;
...
if let Some(change) = change {
  let (weight_with_change, vbytes_with_change) =
    Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
  let fee_with_change = fee_per_vbyte * vbytes_with_change;
  if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
    if value >= DUST {           // <-- compares against 546, not Bitcoin::DUST (10_000)
      tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
      ...
    }
  }
}
``` [1](#0-0) 

Meanwhile the network layer explicitly defines a much larger economic dust limit, with a lengthy rationale that outputs under ~10 000 sats cost more in fees to spend than they are worth:

```rust
// processor/src/networks/bitcoin.rs
const DUST: u64 = 10_000;
``` [2](#0-1) 

The processor treats `N::DUST` as the boundary for dropping payments in both `prepare_send` and `Scheduler::created_output` (`payment.balance.amount.0 < Self::DUST` is zeroed/dropped). A change output of, e.g., 5 000 sats passes the `>= 546` check in `send.rs` and is included in the signed transaction, yet it is far below the 10 000-sat threshold the system uses to decide an output is worth spending. The change output sits at the `Change`-offset address (`change_address`, `OutputType::Change`), is cryptographically spendable, but will never be economically usable — the sats are effectively burned while still being accounted as recovered change.

The leftover change amount is `input_sat - payment_sat - fee_with_change`, where `payment_sat` is the sum of payments derived from user-submitted OutInstructions/withdrawals. An unprivileged user who can trigger a bitcoin payment (a withdrawal) of a chosen amount can shape `input_sat - payment_sat - fee` to land in `[546, 10_000)`, forcing the multisig to sign a transaction that strands funds in an unspendable change output instead of either adding them to the fee or deferring them into a later, spendable change output.

### Impact Explanation
Funds are reported/tracked as recovered change but are not spendable in practice — matching the "funds reported received that are not spendable" impact class. Repeated across many plans, an attacker can progressively bleed small amounts of multisig-held BTC into dead change outputs (griefing / value destruction up to ~9 454 sats per transaction). The loss per instance is bounded by the dust gap (~10 000 sats), keeping this at Medium rather than High.

### Likelihood Explanation
Change leftover values depend on input UTXO values and payment amounts. A user initiating withdrawals can choose payment amounts, and can first deposit a UTXO of a chosen size to the `External` offset address (the `Scanner` accepts any `ReceivedOutput` paying the tweaked key). By controlling both an input's value and their payment amount, the attacker can reliably place `input_sat - payment_sat - fee_with_change` inside `[546, 10_000)`. The main uncertainty is whether the scheduler's input-selection makes it easy to pair a specific input with a specific payment; if input selection is automatic, exploitation is opportunistic rather than deterministic, but the mis-sized change output is still produced whenever the leftover naturally falls in the gap.

### Recommendation
Compare the prospective change value against the network's economic dust threshold, not the relay minimum — i.e., plumb `Bitcoin::DUST` (or a network-provided constant) into `SignableTransaction::new` and require `value >= network_dust` before pushing the change output, letting sub-threshold leftovers become fee instead of a stranded output. Alternatively, if creating a sub-dust change output is ever intended, explicitly track it so it is aggregated only when profitable.

### Proof of Concept
1. Attacker deposits a UTXO of `V` sats to the multisig's external P2TR address, and submits a withdrawal payment of `P` sats.
2. Processor builds a Plan; `make_signable_transaction` calls `BSignableTransaction::new(inputs, payments, Some(change_addr), None, fee_rate)` with `change.is_some()`.
3. `fee_with_change` is computed over vbytes including the change output; choose `V - P - fee_with_change = 5 000` (i.e., `546 ≤ 5 000 < 10 000`).
4. Line 229's `value >= DUST` check passes (5 000 ≥ 546), so `tx_outs` gains a 5 000-sat change output at the `Change` offset address, and the multisig signs the transaction.
5. Result: 5 000 sats now sit in an output below `Bitcoin::DUST` — the same threshold the processor uses to drop payments as uneconomical — so it will never be selected as a worthwhile input. Had the check used 10 000, those sats would have been absorbed into the fee or handled differently rather than locked in a dead output.

Note: I could not fully confirm whether the UTXO scheduler filters candidate inputs by `N::DUST` (that logic lives in `processor/src/multisigs/scheduler/utxo.rs`, outside the indexed scope I could read in depth). If dust inputs are still spent, the impact reduces to wasted fees rather than stranded funds; if they are filtered, the stranding impact stands as described.
