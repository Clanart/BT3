### Title
Payout tx's uncovered OP_RETURN output (SinglePlusAnyoneCanPay) can be mutated by a third party, corrupting `operator_xonly_pk` in DB and causing `is_kickoff_malicious` to falsely convict the honest operator - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
`create_payout_txhandler` builds and signs the Payout transaction with `TapSighashType::SinglePlusAnyoneCanPay`, which per BIP341 only commits to input 0 and the txout at the *same index* (output 0). Output 2 (the OP_RETURN carrying the operator's x-only pubkey) is unauthenticated, so an unprivileged party who observes the broadcast (unconfirmed) transaction can replace output 2 with an unparsable byte sequence and get a conflicting version mined, leaving the operator's reimbursement credit unrecorded.

### Finding Description
The binding that must hold is: `operator_xonly_pk_recorded(i) == party_whose_funds_paid_output_0(i)` — i.e., whichever operator's key actually funded/signed output 0 of the payout for withdrawal `i` must be the one credited in the `withdrawals.payout_payer_operator_xonly_pk` DB column.

`create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) constructs a 3-output transaction: output 0 (user payout), output 1 (anchor), output 2 (`OP_RETURN` = move_txid‖... actually here just `operator_xonly_pk.serialize()`), and calls `set_p2tr_key_spend_witness(&user_sig, 0)`. The user's signature is enforced to use `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:182-187`). Under BIP341/BIP143 taproot sighash rules, `SIGHASH_SINGLE | ANYONECANPAY` commits only to: the spent input (outpoint, amount, scriptPubKey, sequence) and the output at the same index as the input (output 0). It does **not** commit to any other output, including output 1 (anchor) and output 2 (the OP_RETURN carrying `operator_xonly_pk`).

Once the operator broadcasts this Payout transaction (via `Operator::withdraw`, core/src/operator.rs:560-675) and it sits unconfirmed in mempools, any unprivileged attacker who can observe the transaction/witness can construct an alternate transaction that: keeps input 0 byte-identical (same outpoint/sequence), keeps output 0 byte-identical (required, since it's committed by the signature), and replaces output 2 with an arbitrary/malformed script (wrong push length, non-32-byte payload, or no push at all). The signature remains valid for this mutated transaction because the sighash digest is unchanged. If this variant gets mined instead of (or as a replacement for) the operator's original broadcast, the chain now contains a Payout tx whose OP_RETURN is unparsable.

On the verifier side, `update_finalized_payouts` (core/src/verifier.rs:2283-2353) reads the mined Payout tx, extracts the first OP_RETURN output, and calls `parse_op_return_data` then `XOnlyPublicKey::from_slice`. If either step fails, `operator_xonly_pk` is set to `None` and persisted as `NULL` in `withdrawals.payout_payer_operator_xonly_pk` (core/src/verifier.rs:2319-2321, `update_payout_txs_and_payer_operator_xonly_pk` in core/src/database/verifier.rs:198-251).

Later, when the honest operator sends its Kickoff to claim reimbursement, `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1857-1915) fetches this payout row and, seeing `operator_xonly_pk_opt == None`, explicitly says "No operator xonly pk found in payout tx OP_RETURN, assuming malicious" and returns `Ok(true)` (verifier.rs:1882-1885) — even though the same operator did in fact fund output 0 of the (mutated) Payout tx. The binding `operator_xonly_pk_recorded(i) == party_whose_funds_paid_output_0(i)` is broken: the left side is `None`, the right side is the honest operator's key.

None of the existing guards prevent this: `SECP.verify_schnorr` in `Operator::withdraw` (core/src/operator.rs:630-637) only validates the sighash-committed parts (input 0 + output 0), and the code comment at verifier.rs:2316-2318 itself acknowledges `operator_xonly_pk` can become `None` from "operator constructs payout tx wrong" but does not distinguish that cause from third-party output tampering of an uncommitted output — both are collapsed to "assume malicious."

### Impact Explanation
The honest operator fronts real BTC to the withdrawing user in output 0 of the Payout transaction, but if a third party mutates output 2 (uncommitted by the signature) before/while the transaction confirms, the on-chain payout row is recorded with `operator_xonly_pk == NULL`. This causes `Verifier::is_kickoff_malicious` to treat the operator's legitimate reimbursement kickoff as malicious, matching the Critical-impact category "an honest operator permanently unable to be reimbursed" (and downstream, being marked malicious in the kickoff/challenge state machine can also lead to the operator's collateral being burned, matching "an honest operator's collateral burned"). This is repeatable for every payout/operator, since the root cause (SinglePlusAnyoneCanPay leaving output 2 unauthenticated) is generic to the `create_payout_txhandler` construction and not tied to a specific deposit or operator.

### Likelihood Explanation
Preconditions: the attacker must observe the operator's unconfirmed Payout transaction (public once broadcast/relayed) and get a mutated conflicting version mined instead. This requires either the original transaction to signal opt-in RBF (so a higher-fee conflicting spend of the same input can validly replace it network-wide via standard mempool policy) or winning a first-seen race before the original propagates/confirms. I was not able to fully confirm within this session whether `DEFAULT_SEQUENCE` used for the payout input in `create_payout_txhandler` (operator_reimburse.rs:422-427) signals BIP125 opt-in RBF (`< 0xfffffffe`), which materially affects how easily the attacker's alternate version can be relayed and mined. If RBF is enabled (a common default for fee-bumping flows in this codebase), the attack is fully mechanical and requires only broadcasting one extra transaction with a competitive fee — well within an unprivileged attacker's capabilities (own funds for fees only, no bridge collateral, no keys). If RBF is not signaled, the attacker instead needs a mempool/relay race, which is less reliable but not impossible for a determined attacker connecting to well-positioned nodes/miners.

### Recommendation
Commit output 2 (and ideally all outputs) to the user's signature by using `TapSighashType::All` (or `AllPlusAnyoneCanPay` if additional inputs must remain fundable) for the Payout transaction, or otherwise cryptographically bind the OP_RETURN payload to the signed message so it cannot be altered post-signature. Additionally, harden `is_kickoff_malicious`/`update_finalized_payouts` to distinguish "operator self-inflicted malformed OP_RETURN" from "third-party tampering of an unauthenticated output" — e.g., by validating the mined Payout tx's non-committed outputs against the operator's originally-broadcast/pre-signed tx template (matched by input 0 + output 0 + signature), rather than trusting whatever ends up on-chain for the uncommitted fields.
