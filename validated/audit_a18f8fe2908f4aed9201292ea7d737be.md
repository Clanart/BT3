### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Astaria bug — where a liquidation proceeds while a time-window check silently skips required accounting — `Scanner::scan_block` proceeds to scan `block.txdata[0]` (the coinbase transaction) even though its outputs are bound by the 100-block maturity rule and are not spendable. No maturity check exists anywhere in the scan path; the code only notes in a comment that callers "need" a post-processing pass. An unprivileged miner can pay the vault's `script_pubkey` in a coinbase, causing Serai to report funds as received that cannot actually be spent for 100 blocks.

### Finding Description
`scan_transaction` iterates all outputs and pushes a `ReceivedOutput` for any `script_pubkey` matching a registered script (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` calls it on every transaction in `block.txdata`, including index 0, the coinbase (`networks/bitcoin/src/wallet/mod.rs:221-227`):

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for tx in &block.txdata {
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

The only acknowledgment of the issue is the doc comment: "This will also scan the coinbase transaction which is bound by maturity. If received outputs must be immediately spendable, a post-processing pass is needed to remove those outputs." The function itself enforces nothing. This is exactly the original bug's shape: the operation (auction / scanning-and-reporting an output) proceeds in a window where a required condition (epoch-end proximity / coinbase maturity) makes the result invalid, and the protective logic is skipped rather than enforced.

The maturity requirement is a consensus rule: a coinbase output cannot be spent until 100 blocks deep. A `ReceivedOutput` produced from `txdata[0]` is indistinguishable from any other output — it carries a valid `offset`, `output`, and `outpoint` — so downstream consumers (`SignableTransaction::new`, the scheduler) will treat it as a normal spendable input.

### Impact Explanation
A miner (an unprivileged party who can send arbitrary Bitcoin transactions, including their own coinbase) pays the Serai vault address in the coinbase. `scan_block` reports it as a received output. If any consumer builds a `SignableTransaction` spending it, the resulting transaction is consensus-invalid and rejected by the network — the funds are "locked" until maturity, mirroring the original report's lock-of-funds impact. If the wallet layer credits the deposit immediately (balance accounting proceeds while the spendability gate is skipped), the protocol reports funds received that are not spendable — the accepted analog outcome.

### Likelihood Explanation
Requires a miner to include a payment to the vault's P2TR script in their coinbase, or a pool payout. This is a low-frequency but fully external trigger — no Serai privileges needed. Impact is bounded (outputs become spendable after 100 confirmations), so Medium/Low severity; it fails the "documented-MUST" rejection only partially since the comment admits the gap rather than a hard API contract, but the function silently does the wrong thing by default.

### Recommendation
Skip `txdata[0]` in `scan_block` (or tag `ReceivedOutput`s from coinbase transactions and filter them), matching what `processor/src/networks/bitcoin.rs:691` already does manually with `block.txdata[1 ..]`. Make the safe behavior the default rather than relying on every caller performing the post-processing pass.

### Proof of Concept
1. Construct `Scanner::new(vault_key)` and mine a regtest block whose coinbase pays `p2tr_script_buf(vault_key)`.
2. `scanner.scan_block(&block)` returns a `ReceivedOutput` for the coinbase outpoint (as in `networks/bitcoin/tests/wallet.rs:65-77`, which explicitly asserts `scan_block` output equals `scan_transaction(&block.txdata[0])`).
3. Feeding that `ReceivedOutput` into `SignableTransaction::new` produces a transaction spending an immature coinbase; `send_raw_transaction` rejects it with a `bad-txns-premature-spend-of-coinbase` consensus error — funds reported received that are not spendable.
