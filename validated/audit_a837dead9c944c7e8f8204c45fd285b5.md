### Title
Spoofable `WWW-Authenticate: realm="GitHub"` response header causes Desktop to treat an arbitrary host as GitHub Enterprise and initiate a GitHub sign‑in flow against it - (File: app/src/lib/trampoline/trampoline-credential-helper.ts)

### Summary
The `ZetaChain` report's broken invariant is: data that is supposed to prove the origin of an action (`ZetaReceived`/`ZetaReverted` events, which should only ever be emitted by the trusted connector contract) is accepted at face value because the observer only checks the event *signature*, never the event *emitter address*. Any attacker-controlled callee reachable during `onReceive`/`onRevert` can forge the "proof" and corrupt state (a stuck cctx).

The same broken invariant exists in GitHub Desktop's git-credential trampoline: a value that is supposed to prove "this host is a genuine GitHub/GHE server" (`WWW-Authenticate` header value) is accepted at face value from the remote server itself, with no verification of the server's actual identity, and is used to decide whether to initiate a GitHub sign-in (OAuth) flow against that server.

### Finding Description
`getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` determines whether a git remote endpoint should be treated as `'github.com'`, `'enterprise'`, or `'generic'`: [1](#0-0) 

Two mechanisms exist to classify a host as GitHub Enterprise:
1. `isGitHubHost()` — an actual network probe to the endpoint's `/meta` route that checks for the `x-github-request-id` response header on a real request Desktop itself makes, which is at least a server-controlled but Desktop-initiated check. [2](#0-1) 
2. The `wwwauth[...]` fast-path — Desktop's git credential-helper protocol forwards any `WWW-Authenticate` header the *remote server sent in its 401 response* (captured by git itself), and if the value merely contains the substring `realm="GitHub"`, Desktop unconditionally classifies the endpoint as `'enterprise'` **without making any verification request at all**:

```
for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
``` [3](#0-2) 

This is exactly analogous to `ParseZetaReceived` only checking the event's ABI signature and not its emitter address: Desktop only checks a *string pattern* the remote itself supplied, not any property that the remote cannot forge (Desktop's own probe request, a pinned account/endpoint mapping, or a certificate/identity check).

The corrupted value is the `endpointKind` result (`'enterprise'` vs `'generic'`). This value flows directly into `getCredential`: [4](#0-3) 

If `endpointKind !== 'generic'` and there is no existing account bound to `apiEndpoint` (true the first time a user's git operation hits an attacker-controlled host, e.g. a malicious clone URL, a compromised/hostile proxy on the network, or a redirected remote), Desktop calls `ui.promptForGitHubSignIn(endpoint)` — i.e. it treats the attacker's server as a legitimate GitHub/GHE instance worth signing into, and initiates a sign-in/OAuth flow targeted at that attacker-controlled `endpoint`.

Existing guards do not stop this path because:
- `isGitHubHost()`'s real network verification is explicitly bypassed by the `wwwauth[...]` branch, which is documented in the code itself as a "happy path... without having to resort to making a request ourselves" — i.e., the check is intentionally weaker and is reached first.
- The `wwwauth[...]` value originates from the remote HTTP server's response headers to a `git fetch/clone/push` attempt, which is fully attacker-controlled when the user adds/uses a hostile remote URL (a realistic "attacker controls a git remote/proxy response" scenario per the valid-impact rules).
- No pinning/allow-list of legitimate GHE hostnames or TLS/identity verification gates this branch — a bare substring match on a self-reported header is sufficient.

### Impact Explanation
An attacker who controls (or man-in-the-middles) a git HTTP(S) endpoint that the victim adds as a remote (e.g., a malicious `clone` URL, a corporate-network proxy, or a compromised mirror) can respond to Desktop's credential probe with `WWW-Authenticate: Basic realm="GitHub"`. This causes Desktop's credential-helper trampoline to classify the host as `'enterprise'` and invoke the GitHub sign-in UI/OAuth flow directly against the attacker's endpoint instead of a genuine GitHub Enterprise server. Since the OAuth/sign-in dialog is rendered for that attacker-controlled endpoint, the attacker's server receives the authentication attempt (and can present a convincing phishing login page mimicking GHE), enabling credential/token capture — matching the listed "unauthorized OAuth or account binding" / "credential/token exfiltration" impact categories.

### Likelihood Explanation
The trigger requires only that the victim performs a git operation (fetch/clone/push) against a URL the attacker controls or can intercept — no local access, no admin rights, and no pre-existing malware or leaked credentials are needed. Setting a custom `WWW-Authenticate` header on a 401 response is trivial for any HTTP server the attacker operates. This fits squarely in the allowed threat model ("attacker controls...a git remote/proxy response").

### Recommendation
- Never derive trust in "this is a GitHub/GHE host" purely from data the remote server supplies in-band (the `WWW-Authenticate` header). At minimum, treat the `wwwauth[...]` heuristic as a hint that requires corroboration via the existing out-of-band `isGitHubHost()` network probe (which itself should be hardened, e.g. verified against known GHE license/manifest data) before initiating any sign-in/OAuth UI.
- Require an explicit user action (e.g., "Add Enterprise Account") or a previously-trusted endpoint entry before ever presenting a GitHub-branded sign-in prompt for a new, unrecognized host.
- Clearly surface the destination hostname of any sign-in prompt so users can detect if they're being asked to authenticate to an unexpected server.

### Proof of Concept
1. Attacker stands up an HTTPS server at `https://evil.example.com/repo.git`.
2. Victim adds/clones this URL in GitHub Desktop (e.g., pasted from a phishing message, or reached via a hijacked proxy for an internal git host).
3. Git invokes Desktop's credential helper trampoline; the attacker's server returns `401 Unauthorized` with header `WWW-Authenticate: Basic realm="GitHub"`.
4. `getEndpointKind` in `app/src/lib/trampoline/trampoline-credential-helper.ts` matches `v.includes('realm="GitHub"')` and returns `'enterprise'` without any network verification.
5. `getCredential` sees no account bound to `evil.example.com`'s derived `apiEndpoint` and calls `ui.promptForGitHubSignIn(endpoint)`, presenting a GitHub Enterprise sign-in flow whose destination is the attacker's server.
6. The victim, believing this is a legitimate corporate GHE sign-in prompt (as Desktop itself has branded it), enters credentials/approves OAuth against the attacker's server.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

/**
 * Attempts to determine whether or not the url belongs to a GitHub host.
 *
 * This is a best-effort attempt and may return `undefined` if encountering
 * an error making the discovery request
 */
export async function isGitHubHost(url: string) {
  const { hostname } = new window.URL(url)

  const endpoint =
    hostname === 'github.com' || hostname === 'api.github.com'
      ? getDotComAPIEndpoint()
      : getEnterpriseAPIURL(url)

  if (isDotCom(endpoint) || isGHE(endpoint)) {
    return true
  }

  if (isKnownThirdPartyHost(hostname)) {
    return false
  }

  // github.example.com,
  if (/(^|\.)(github)\./.test(hostname)) {
    return true
  }

  // bitbucket.example.com, etc
  if (/(^|\.)(bitbucket|gitlab)\./.test(hostname)) {
    return false
  }

  if (getEndpointVersion(endpoint) !== null) {
    return true
  }

  // Add a unique identifier to the URL to make sure our certificate error
  // supression only catches this request
  const metaUrl = `${endpoint}/meta?ghd=${crypto.randomUUID()}`

  const ac = new AbortController()
  const timeoutId = setTimeout(() => ac.abort(), 2000)
  suppressCertificateErrorFor(metaUrl)
  try {
    const response = await fetch(metaUrl, {
      headers: { 'user-agent': getUserAgent() },
      signal: ac.signal,
      credentials: 'omit',
      method: 'HEAD',
      redirect: 'error',
    })

    tryUpdateEndpointVersionFromResponse(endpoint, response)

    return response.headers.has('x-github-request-id')
  } catch (e) {
    log.debug(`isGitHubHost: failed with endpoint ${endpoint}`, e)
    return undefined
  } finally {
    clearTimeout(timeoutId)
    clearCertificateErrorSuppressionFor(metaUrl)
  }
}
