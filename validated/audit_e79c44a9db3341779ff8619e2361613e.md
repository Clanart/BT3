### Title
Untrusted serialized `ReceivedOutput` values can inject phantom Bitcoin UTXOs - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary

`ReceivedOutput::read` accepts an attacker-supplied offset, `TxOut`, and `OutPoint` without binding the `OutPoint` to a confirmed transaction or checking that the referenced output has the claimed value. The downstream transaction builder then treats the decoded object as spendable input, while `SignableTransaction::multisig` validates only that the claimed `script_pubkey` matches the selected key offset. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

A legitimate `ReceivedOutput` produced by `Scanner::scan_transaction` has its `script_pubkey`, `TxOut` contents, transaction ID, and output index derived from a transaction observed on chain. [4](#0-3)  That provenance is lost during serialization: `ReceivedOutput::read` independently trusts all three serialized fields and reconstructs the object without requiring any scanner or chain evidence. [5](#0-4) 

`SignableTransaction::new` uses the forged `output.value` as spendable input value and the forged `outpoint` as the transaction input. [2](#0-1)  The key check performed before signing compares the fabricated `TxOut.script_pubkey` to `p2tr_script_buf(keys + offset)`, but it does not check that `previous_output` exists or that its real value equals the serialized `TxOut.value`. [3](#0-2) 

The signing path then commits to the fabricated previous-output set through `Prevouts::All(&self.tx.prevouts)`, causing the participant to sign a sighash for a nonexistent or misrepresented UTXO. [6](#0-5) 

### Impact Explanation

An attacker who can supply serialized `ReceivedOutput` bytes can cause the wallet layer to report arbitrary value as received for an arbitrary outpoint and can cause the threshold signer to attempt spending it. This is the analog of including an attacker-selected resource: the `OutPoint` acts as the resource selector, while the serialized `TxOut` supplies fabricated contents that were never obtained from the chain. [5](#0-4) 

If the forged outpoint is nonexistent, the resulting transaction cannot be mined. If it references a real wallet UTXO but supplies a different `TxOut.value`, the Taproot sighash commits to the wrong amount and the produced signature is invalid. In either case, the object is represented by Serai as a spendable `ReceivedOutput` even though the claimed funds cannot actually be spent. [6](#0-5) 

### Likelihood Explanation

The attack requires an integration to accept serialized `ReceivedOutput` values from an untrusted party rather than generating them exclusively through `Scanner::scan_transaction` or `Scanner::scan_block`. Under that explicit untrusted-input boundary, exploitation is straightforward because the attacker needs only the wallet’s public Taproot script and can choose an arbitrary outpoint and amount. No private key, validator privilege, malicious node assumption, or invalid curve encoding is required. [1](#0-0) 

### Recommendation

Do not expose `ReceivedOutput::read` as a trust-establishing API for spendable chain outputs. At minimum:

- Revalidate every deserialized `OutPoint` against a trusted Bitcoin node before treating it as spendable.
- Compare the chain-returned `TxOut`, including value and `script_pubkey`, with the serialized fields.
- Derive the stored `script_pubkey` from `key + offset * G` instead of accepting it as authoritative serialized state.
- Prefer serializing only the authenticated `OutPoint` and registered offset, then reloading the actual `TxOut` from chain data.
- Document that raw `ReceivedOutput::read` input is not proof of receipt if deserialization without chain validation remains supported.

### Proof of Concept

The following sequence demonstrates the issue conceptually for a wallet whose even tweaked group key is `key` and whose threshold keys are `keys`:

```rust
use bitcoin::{Amount, OutPoint, TxOut, Txid, hashes::Hash};
use frost::{curve::Secp256k1, ThresholdKeys};
use k256::Scalar;
use bitcoin_serai::wallet::{p2tr_script_buf, ReceivedOutput, SignableTransaction};

fn forged_received_output(
  key: k256::ProjectivePoint,
) -> ReceivedOutput {
  // Any recognizable outpoint is sufficient; this outpoint does not need to exist.
  let fake_outpoint = OutPoint::new(Txid::all_zeros(), 0);

  // Claim the outpoint paid a large amount to the wallet's key-path script.
  let fake_txout = TxOut {
    value: Amount::from_sat(1_000_000),
    script_pubkey: p2tr_script_buf(key).unwrap(),
  };

  let mut bytes = Vec::new();
  bytes.extend(Scalar::ZERO.to_bytes()); // offset corresponding to `key`
  bytes.extend(bitcoin::consensus::serialize(&fake_txout));
  bytes.extend(bitcoin::consensus::serialize(&fake_outpoint));

  ReceivedOutput::read(&mut bytes.as_slice()).unwrap()
}

let fake = forged_received_output(keys.group_key());
assert_eq!(fake.value(), 1_000_000);

let payment_script = p2tr_script_buf(keys.group_key()).unwrap();
let signable = SignableTransaction::new(
  vec![fake],
  &[(payment_script, 900_000)],
  None,
  None,
  1,
).unwrap();

// This succeeds because only the fabricated script_pubkey is checked.
assert!(signable.multisig(keys).is_some());
```

The resulting signing machine commits to `Prevouts::All` containing the fabricated `TxOut`. Because the outpoint does not exist, or because the supplied amount differs from the real UTXO, Bitcoin consensus will not accept the signed transaction as spending the reported funds. [6](#0-5)
