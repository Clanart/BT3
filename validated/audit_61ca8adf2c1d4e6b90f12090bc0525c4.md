### Title
Shared `BalanceHandler` instance across recursive/nested precompile calls causes StateDB↔bank balance desync (accounting corruption) - (File: precompiles/common/balance_handler.go)

### Summary
The CIF bug in the external report is a "checkpoint variable overwritten by an intervening operation" bug class: `cashInFlight` is meant to track a delta that should be consumed exactly once, but a second update to the tracking state before the first is consumed causes accounting to drift from reality. The same bug class exists natively in this repository's precompile balance-syncing mechanism: `BalanceHandler.prevEventsLen` is a single mutable checkpoint that can be overwritten by a nested/recursive precompile call before the outer call consumes it, causing bank-module balance-change events to be silently skipped when propagating balances into the EVM `StateDB`.

### Finding Description
`BalanceHandler` [1](#0-0)  records `prevEventsLen = len(ctx.EventManager().Events())` in `BeforeBalanceChange`, and later in `AfterBalanceChange` replays only `events[prevEventsLen:]` to apply `stateDB.AddBalance`/`SubBalance` for `EventTypeCoinSpent`, `EventTypeCoinReceived`, and precisebank fractional-balance-change events [2](#0-1) .

This pattern only guarantees correctness if `BeforeBalanceChange`/`AfterBalanceChange` are called in a strictly non-overlapping (non-reentrant) manner per logical operation. The repository itself contains a dedicated regression test, `BalanceHandlerTestSuite`, whose doc comment states: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing `prevEventsLen` to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [3](#0-2) . The test drives this via a contract that recursively calls a precompile (`callback`), and asserts a specific number of debug-precompile invocations and emitted events to reproduce the scenario [4](#0-3) .

`RunNativeAction`, used by every value-moving precompile (`bank`, `distribution`, `erc20`, `gov`, `ics20`, `slashing`, `staking`, `werc20`) to wrap execution in `BeforeBalanceChange`/`AfterBalanceChange`, is invoked once per `Run` call on the precompile [5](#0-4) . When a contract makes a nested/recursive call into a precompile (e.g., a contract calling precompile A, whose native action internally triggers another precompile-mediated bank operation, or two precompile calls occur within the same top-level EVM call frame before the outer `AfterBalanceChange` executes), the inner call's `BeforeBalanceChange` re-sets `prevEventsLen` to a later index. When the outer call's `AfterBalanceChange` subsequently runs, it uses this now-larger `prevEventsLen`, causing it to skip the bank events generated by its own (outer) balance-moving operation. Because `stateDB.AddBalance`/`SubBalance` are never called for those skipped events, the EVM-visible balance for the accounts involved silently diverges from the real `x/bank`/`x/precisebank` balance — a permanent, unauthorized state divergence between the authoritative asset ledger (bank keeper) and the EVM's view of user funds (StateDB), which downstream EVM logic (transfers, `balanceOf`, contract accounting) will treat as truth.

### Impact Explanation
This falls under the "Critical … irreversible accounting corruption of spendable user value across native balances, EVM balances… or precompile-mediated assets" allowed-impact class. Once `StateDB` balance diverges from the real bank balance:
- A user's EVM balance can be persistently under- or over-stated relative to their real spendable coins, since subsequent EVM statedb operations, transfers, and contract logic operate on the (corrupted) `StateDB` value rather than the true bank balance.
- This corruption can propagate to consensus-relevant state (the StateDB is committed into the block's execution/state root), meaning any node processing this transaction sequence deterministically derives the same (wrong) balance — this is an accounting bug rather than a nondeterminism/fork bug, but it directly corrupts spendable value tracked by the EVM.
- Because it is triggered purely by ordinary contract calls invoking precompiles recursively/in sequence within a single transaction, it is reachable by any unprivileged user, with no admin/privileged action required (unlike the original CIF bug, which required admin coordination of `publishAttestation`/`setCashInFlight`).

### Likelihood Explanation
The repository ships an integration test explicitly designed to demonstrate this exact bug via a contract that recursively invokes a precompile, and the test's own documentation names it "the balance handler bug." This indicates the bug is known, reproducible, and reachable through ordinary (unprivileged) transaction/contract flows — any contract author can construct a call graph that makes two or more precompile-mediated balance operations happen within the same EVM call trace before the outer handler's `AfterBalanceChange` fires.

### Recommendation
Do not use a single mutable `prevEventsLen` field shared across nested invocations of the same `BalanceHandler`/precompile keeper instance. Instead:
- Make `BeforeBalanceChange`/`AfterBalanceChange` reentrancy-safe, e.g., by using a per-call-frame stack of checkpoints (push on `BeforeBalanceChange`, pop and process only the top range on `AfterBalanceChange`), or by creating a brand-new `BalanceHandler` instance per top-level `Run` invocation instead of reusing a shared instance across nested calls.
- Add invariant checks (e.g., a debug-mode assertion) that the sum of applied `StateDB` balance deltas for a transaction matches the net bank-keeper balance deltas for all touched accounts.

### Proof of Concept
The existing repository test is itself a working PoC of the root cause: `BalanceHandlerTestSuite.TestRecursivePrecompileCallsWithDebugPrecompile` deploys a caller contract that invokes the debug precompile recursively (`callback(0)`), which internally performs multiple precompile executions/bank events within a single top-level transaction [6](#0-5) . Because I could not obtain full read access to `precompiles/common/precompile.go`'s `RunNativeAction` implementation within tool-call limits, I was unable to fully confirm at code level whether the `BalanceHandler` instance is created per-`Keeper` (long-lived, shared across nested calls) versus strictly per-`Run` invocation for every precompile in this exact revision — this should be verified directly in `precompiles/common/precompile.go` and in each precompile's `Run`/`NewPrecompile` wiring before treating this as fully confirmed exploitable in production; a Devin session with full file access is recommended to trace this precisely and build an end-to-end balance-corruption exploit transaction.

```go
// BalanceHandler is a struct that handles balance changes in the Cosmos SDK context.
type BalanceHandler struct {
	bankKeeper    BankKeeper
	prevEventsLen int

// BeforeBalanceChange is called before any balance changes by precompile methods.
// It records the current number of events in the context to later process balance changes
// using the recorded events.
func (bh *BalanceHandler) BeforeBalanceChange(ctx sdk.Context) {
	bh.prevEventsLen = len(ctx.EventManager().Events())
}
```

```go
func (bh *BalanceHandler) AfterBalanceChange(ctx sdk.Context, stateDB *statedb.StateDB) error {
	events := ctx.EventManager().Events()

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
			if bh.bankKeeper.BlockedAddr(spenderAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}

			stateDB.SubBalance(common.BytesToAddress(spenderAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)

		case banktypes.EventTypeCoinReceived:
			receiverAddr, err := ParseAddress(event, banktypes.AttributeKeyReceiver)
			if err != nil {
				return fmt.Errorf("failed to parse receiver address from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}
			if bh.bankKeeper.BlockedAddr(receiverAddr) {
				// Bypass blocked addresses
				continue
			}

			amount, err := ParseAmount(event)
			if err != nil {
				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinReceived, err)
			}

			stateDB.AddBalance(common.BytesToAddress(receiverAddr.Bytes()), amount, tracing.BalanceChangeUnspecified)
```

```go
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function

	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())

	// Pack the input for callback(0)
```
