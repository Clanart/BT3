### Title
Attacker can inflate `getUserTier()` via direct `mWomSV.lock`/`lockFor` calls and claim top-tier MGP rewards on a trivial WOM deposit through `incentiveDeposit()` - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.getRewardAmount()`'s non-lock branch (`_mode != 2`) computes the MGP reward multiplier solely from `getUserTier(_account)`, which in turn reads `mWomSV.getUserTotalLocked(_account)` — a balance that any unprivileged account can inflate directly by calling `mWomSV.lock()` or `mWomSV.lockFor()`, since neither function is access-restricted to `ArbWomUp3`. Because `ArbWomUp3` has no internal accounting of deposits made through it, an attacker can build a large externally-locked mWomSV balance to reach the top reward tier, then call `incentiveDeposit()` with a minimal WOM amount and receive a reward computed at the flat top-tier multiplier, disproportionate to the actual value contributed via `ArbWomUp3`.

### Finding Description
- `mWomSV.lock()` (`wombat/mWomSV.sol:226`) and `mWomSV.lockFor()` (`wombat/mWomSV.sol:236`) are `external` functions guarded only by `whenNotPaused`/`nonReentrant`; there is no restriction limiting the caller to `ArbWomUp3`. Both call `_lock(spender, _for, _amount)` (`wombat/mWomSV.sol:370-378`), which pulls `mWOM` from `spender` and calls `IMasterMagpie(masterMagpie).depositMWomSVFor(_amount, _for)`, directly increasing the target account's stake as reported by `stakingInfo`.
- `mWomSV.getUserTotalLocked()` (`wombat/mWomSV.sol:113-117`) reads that stake straight from `masterMagpie`, with no way to distinguish stake that originated from `ArbWomUp3.incentiveDeposit()` versus stake locked directly by the user.
- `ArbWomUp3.getUserTier()` (`wombat/ArbWomUp3.sol:146-155`) uses only `mWomSV.getUserTotalLocked(_account)` to select a tier index into `rewardTier`/`rewardMultiplier`.
- `ArbWomUp3.getRewardAmount()`'s non-lock branch (`wombat/ArbWomUp3.sol:110-111`) computes `mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR` — a flat multiplier applied to the entire deposit amount, with no tiered/marginal calculation and no `calDoubledCounted` deduction (that logic exists only in the `_lock == true` branch, lines 112-124).
- `ArbWomUp3` has no `userWOMDeposited` (or similar) mapping tracking what a user has actually deposited through this contract, so it cannot distinguish "tier earned via this contract's own deposit flow" from "tier built by locking mWomSV through any other path."

Exploit flow: attacker acquires/holds `mWOM` (obtainable by depositing WOM via `IMWom(mWom).deposit`, itself unrestricted), then calls `mWomSV.lock(largeAmt)` or `mWomSV.lockFor(largeAmt, attacker)` directly, which is entirely outside `ArbWomUp3`. This inflates `mWomSV.getUserTotalLocked(attacker)` and thus `getUserTier(attacker)` to the top bracket. Attacker then calls `incentiveDeposit(smallAmount, _, false, 1)`. Inside `incentiveDeposit()`, `_mode == 2` is false, so `getRewardAmount(smallAmount, attacker, false)` hits the non-lock branch and returns `smallAmount * rewardMultiplier[topTier] / DENOMINATOR`, which is minted/locked into `vlMGP` for the attacker (`ArbWomUp3.sol:101-104`). No existing check (no `nonReentrant`-adjacent state check, no deposit-tracking mapping, no restriction on `mWomSV.lockFor` caller) prevents this.

### Impact Explanation
This allows theft/misappropriation of the unclaimed MGP incentive pool held by `ArbWomUp3` (checked/capped only by `mgpleft` in `getRewardAmount`, `wombat/ArbWomUp3.sol:127-128`). An attacker can repeatedly call `incentiveDeposit()` with minimal WOM amounts while sitting at an externally-inflated top tier, extracting a disproportionate share of the program's MGP reward budget intended for genuine large depositors — a direct theft of unclaimed yield/emission share belonging to the protocol's incentive program, consistent with the "theft of unclaimed yield" Immunefi impact class.

### Likelihood Explanation
Feasibility is high and capital requirement is a temporary/recoverable lock rather than a burn: the attacker only needs to acquire `mWOM` (1:1 convertible from `WOM`) and lock it into `mWomSV` (unlockable later after cooldown, `startUnlock`/`unlock` in `wombat/mWomSV.sol:247-303`), then perform a trivial `incentiveDeposit` call. No special privileges are required — `mWomSV.lock`/`lockFor` and `ArbWomUp3.incentiveDeposit` are both public/external entry points. The exploit is repeatable up to the limit of MGP remaining in `ArbWomUp3` and requires only the attacker's own funds.

### Recommendation
Track deposits made specifically through `ArbWomUp3` (e.g., a `userWOMDeposited`/`userTierContribution` mapping updated in `_deposit`) and base `getUserTier()`/the non-lock reward branch on that internal accounting rather than the raw external `mWomSV.getUserTotalLocked()` value. Alternatively, apply the same tiered/marginal reward computation used in the `_lock == true` branch (with `calDoubledCounted`-style deduction) to the non-lock branch so that a flat top-tier multiplier can never be applied to unrelated externally-built balances, and/or restrict `mWomSV.lockFor`/`lock` accounting so `ArbWomUp3` can verify provenance of the locked balance it relies on.

### Proof of Concept
Foundry test outline:
1. Deploy `mWomSV`, `MasterMagpie`, `mWom`, `ArbWomUp3`, `vlMGP`, fund `ArbWomUp3` with MGP, and set `rewardMultiplier`/`rewardTier` (e.g., tier0 = 1x, top tier = 5x at threshold `T`).
2. Attacker: acquire `WOM`, deposit into `mWom` to get `mWOM` ≥ `T`.
3. Attacker calls `mWomSV.lock(T)` directly (bypassing `ArbWomUp3` entirely).
4. Assert `ArbWomUp3.getUserTier(attacker) == topTierIndex`.
5. Attacker calls `ArbWomUp3.incentiveDeposit(dustAmount, 0, false, 1)` with a small `WOM` amount.
6. Assert `vlMGP` balance locked for attacker == `dustAmount * rewardMultiplier[topTierIndex] / DENOMINATOR`, i.e., reward proportional to the top-tier multiplier despite `dustAmount` being the only value ever routed through `ArbWomUp3`.
7. Compare against a control depositor who deposits the same `dustAmount` with no prior `mWomSV` balance, showing a materially lower (tier-0) reward for an economically identical `ArbWomUp3` contribution — demonstrating the disproportionate/unearned reward.     function getRewardAmount(uint256 _amountToConvert, address _account, bool _lock) external view returns (uint256) {
        uint256 mgpReward = 0;

        if (!_lock) {
            mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
        } else {
            uint256 accumulated = _amountToConvert + mWomSV.getUserTotalLocked(_account);
            uint256 rewardAmount = 0;
            uint256 i = 1;

            while (i < rewardTier.length && accumulated > rewardTier[i]) {
                rewardAmount +=
                    (rewardTier[i] - rewardTier[i - 1]) *
                    rewardMultiplier[i - 1];
                i++;
            }
            rewardAmount += (accumulated - rewardTier[i - 1]) * rewardMultiplier[i - 1];
            mgpReward = (rewardAmount / DENOMINATOR) - calDoubledCounted(_account);
        }

        uint256 mgpleft = IERC20(mgp).balanceOf(address(this));
        return mgpReward > mgpleft ? mgpleft : mgpReward;
    }
