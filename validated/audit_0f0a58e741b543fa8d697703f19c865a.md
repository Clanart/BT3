Confirmed: `CallDispatcher.dispatch()` only checks the raw call-success boolean of the low-level `.call()`, not the ABI-decoded `bool` return value from an ERC20 `transfer`/`transferFrom` [1](#0-0) . This is the exact analog to the reported bug class: unchecked ERC-20 return values on transfers used for accounting-critical flows.

### Title
Predispatch escrow accounting trusts unchecked ERC20 `transfer` return value routed through `CallDispatcher` - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder()`'s predispatch flow builds raw `IERC20.transfer` calldata and executes it via `CallDispatcher.dispatch()`, which only checks the low-level call success flag, not the ABI-decoded boolean return value of `transfer`. For a non-reverting ERC20 that returns `false` on failure (the exact token class flagged in the original report), the sweep-back call can "succeed" at the call level while moving zero tokens.

### Finding Description
In `placeOrder`, when an order has `predispatch.call` and `predispatch.assets`, tokens are first sent to the `CallDispatcher`, arbitrary calldata is executed, and then the resulting balances are swept back to the gateway using raw calldata:
```solidity
transferCalls[i] = Call({
    to: token,
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
``` [2](#0-1) 

This is dispatched via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` [3](#0-2) , and `CallDispatcher.dispatch()` only reverts if the low-level `.call()` itself fails — it never decodes or checks the `bool` returned by `transfer()`:
```solidity
(bool success, bytes memory result) = to.call{value: call.value}(call.data);
if (!success) revert CallFailed(to, result);
``` [4](#0-3) 

The gateway then measures `received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]` and uses that as the escrowed/committed `order.inputs[i].amount` [5](#0-4) . Because the amount is derived from an actual balance delta rather than trusting the return value, a `transfer` that returns `false` without moving tokens is correctly reflected as `received == 0` — this specific measurement pattern neutralizes the classic "attacker deposits for free" primitive that the external report describes for GebProxyActions-style code.

However, this protection is confined to the `placeOrder` predispatch sweep. The corresponding sweep in `IntentsBase._execute()` (used after order fill, for postdispatch calldata) does not perform a before/after balance check on the amount actually accounted — it just reads `IERC20(token).balanceOf(dispatcher)` once, builds the same unchecked raw `transfer` calldata, and unconditionally emits `DustCollected(token, balance)` as if the sweep succeeded:
```solidity
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance > 0) {
    sweepCalls[sweepCount] = Call({
        to: token, value: 0,
        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
    });
    sweepCount++;
    emit DustCollected(token, balance);
}
``` [6](#0-5) 

Since `CallDispatcher` will not revert on a `transfer` that returns `false` without reverting, if the `order.output` token used in a postdispatch calldata leg is a non-compliant, non-reverting ERC20, the sweep silently no-ops: tokens remain stranded in the `CallDispatcher` contract while the gateway emits `DustCollected` and treats the dust as already collected — a permanent mismatch between recorded and actual gateway-held balances.

### Impact Explanation
This does not let an attacker steal escrowed order inputs (the `placeOrder` predispatch path is balance-delta protected, and `_withdraw`/`withdraw` in `IntentsBase.sol` correctly uses `SafeERC20.safeTransfer`). The exposure is narrower: it can silently strand solver-output "dust" tokens inside the shared, stateless `CallDispatcher` contract instead of the gateway, and can cause the emitted `DustCollected` accounting event to misreport funds the protocol does not actually hold — a false-state-acceptance/accounting integrity issue rather than a direct fund-theft path from an unprivileged attacker's perspective, since it requires the order to specify a non-standard, non-reverting output token used with postdispatch calldata.

### Likelihood Explanation
Low-to-moderate. It requires an order with `output.call` populated (postdispatch calldata) whose output token is a legacy ERC20 that returns `false` instead of reverting on failed transfer — exactly the token category the original H2O report calls out and that Hyperbridge does not exclude at the protocol level (order tokens are attacker/solver supplied, not an admin-curated allowlist).

### Recommendation
Route the `_execute()` sweep through `SafeERC20.safeTransfer` (as already done in `_withdraw`/`_sweepDust` in the same file) instead of raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` dispatched through `CallDispatcher`, or add a `CallDispatcher`-independent balance-delta check before emitting `DustCollected`, mirroring the pattern already used in `placeOrder`'s predispatch phase.

### Proof of Concept
1. Deploy a non-standard ERC20 whose `transfer()` returns `false` on failure instead of reverting (e.g., a token with a blocklist or paused state that a solver/order can select as `output.assets[i].token`).
2. Create and fill an order whose `output.call` (postdispatch calldata) results in residual balance of that token being left in `_params.dispatcher` after the calldata call executes, and where the transfer-back to `msg.sender`/the token holder subsequently sets up a `transfer(address(this), balance)` call that reverts internally but returns `false` (e.g., token paused between execution and sweep, or balance changed to a value now rejected by an internal cap).
3. Observe `_execute()` builds and dispatches the sweep call; `CallDispatcher.dispatch()` sees `success == true` (the call itself didn't revert) and does not check the decoded return value.
4. `DustCollected(token, balance)` fires even though the tokens never left the `CallDispatcher`, permanently desynchronizing gateway-tracked dust from actual on-chain balances.
