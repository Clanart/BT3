## Title
Automatic remote-URL rewrite trusts repository name continuity, not repository identity - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
The Kamino report describes a broken invariant: an authority binding (farm admin) is established once, from a related-but-distinct entity's current owner, and is never re-validated when that owner changes — so the system keeps trusting a stale identity link. GitHub Desktop has a structurally similar invariant break in how it keeps a local repository's `origin` remote in sync with the GitHub-hosted repository it's supposedly tracking: the binding is re-established by looking up the *same owner/name pair* via the GitHub API and blindly trusting whatever `clone_url` comes back, instead of verifying that the underlying repository identity has not changed.

### Finding Description
`repositoryWithRefreshedGitHubRepository` re-derives the GitHub association for a local repository purely from the current remote URL: [1](#0-0) 

It calls `matchGitHubRepository`, which extracts `owner`/`name` from the local git remote URL and pairs it with whichever locally signed-in `Account` happens to share the same hostname: [2](#0-1) 

It then calls `api.fetchRepository(owner, name)` and, if the fetched repo's `clone_url` differs from what's currently configured, silently rewrites the local `origin` remote via `updateRemoteUrl`: [3](#0-2) 

The only checks performed before rewriting the remote are: (1) the git protocol (ssh vs https) hasn't changed, and (2) the current remote still matches the previously *cached* `cloneURL` (i.e., the user hasn't manually customized the remote). Nowhere is the GitHub repository's stable identity (its database `id`) compared between the old cached `GitHubRepository` record and the newly fetched `apiRepo` — the code only ever compares URLs/owner/name strings, e.g. in `urlsMatch`/`urlMatchesCloneURL`: [4](#0-3) 

This is exactly the Kamino pattern: the trust anchor (farm admin / here, "which upstream repo do I push to") is captured once and then silently re-derived from an external system's current state (lending-market owner / here, "whatever repo currently answers to this owner/name") without confirming that the underlying entity is still the *same* entity. Just as Kamino's farm keeps trusting the old lending-market owner because ownership sync is one-way and unguarded, Desktop keeps trusting "owner/name resolves to my repo" and propagates whatever the API returns for that name into the user's actual push target — a decision the user never re-confirms.

`repositoryWithRefreshedGitHubRepository` runs as part of routine background refresh flows (e.g. `withRefreshedGitHubRepository`, invoked before push/pull operations), so this happens automatically and non-interactively: [5](#0-4) 

### Impact Explanation
If a GitHub repository name is freed and reclaimed under the same owner/org path (a well-known "repo-jacking"/dangling-reference class of issue — deleted repo, renamed-away repo, or an org member's fork left at an old slug), Desktop's background refresh will fetch the *new* repository object living at that same owner/name, see a different `clone_url` (e.g., different casing, host migration, or a genuinely different repo that now occupies that slug), and rewrite the user's `origin` remote to point at it — with no dialog, confirmation, or diff shown to the user. Subsequent `push` operations from Desktop would then silently send the user's commits to a different repository than the one they originally cloned, i.e. **silent corruption of where the user's commits and pushes end up**, without any deliberate action by the user. This satisfies the required impact class ("git remote/proxy response... result is silent corruption of what the user commits or pushes").

### Likelihood Explanation
This requires no local access, admin rights, or social engineering: the attacker only needs to control what the GitHub API returns for a given owner/name pair that a victim's Desktop client is already tracking (e.g., by claiming a vacated repository slug/owner name — a documented real-world attack pattern independent of Desktop). The vulnerable code path (`repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`) runs automatically during normal background repository refresh and pre-push checks, so no unusual user interaction is needed beyond normal use of the app while the repo slug is in a "reclaimable" state. The mitigating conditions (protocol match, `remoteUrlUnchanged` against the last cached URL) are weak because they only guard against the user having manually edited the remote — they do nothing to verify repository identity continuity.

### Recommendation
Store and compare the durable GitHub repository identifier (the API `id` field already retained in `GitHubRepository`, e.g., `dbID`) between the previously associated repository and the newly fetched `apiRepo` before invoking `updateRemoteUrl`. If the id differs from what was last associated, do not silently rewrite the remote — surface a confirmation dialog (similar to the existing `UpstreamAlreadyExists` pattern) so the user explicitly approves re-pointing their push target to a different underlying repository.

### Proof of Concept
1. User clones `https://github.com/owner/repo` in Desktop; Desktop stores this as the tracked `GitHubRepository` (owner=`owner`, name=`repo`).
2. The original `owner/repo` repository is deleted or the owner account is renamed/reused, and an attacker creates a new repository at the exact same `owner/repo` slug (a known repo/name-squatting scenario).
3. On the next background refresh (`repositoryWithRefreshedGitHubRepository`, triggered periodically or before a push), Desktop calls `matchGitHubRepository` (matches purely on owner/name/hostname) then `api.fetchRepository('owner', 'repo')`, which now returns the attacker's repository object, including its `clone_url`.
4. `updateRemoteUrl` compares the new `clone_url` to the cached one; if the URL differs (e.g., protocol-compatible but pointing to the attacker's actual clone endpoint) and the local remote still matches what was cached, it calls `gitStore.setRemoteURL('origin', <attacker clone_url>)` with no user confirmation, per [6](#0-5) .
5. The user's next `git push` (via Desktop) now silently targets the attacker's repository instead of the one they originally intended.

Note: I was unable to fully confirm from local static analysis alone how frequently/under what exact triggers `repositoryWithRefreshedGitHubRepository` is invoked automatically without a corresponding user-visible refresh action; a Devin session with runtime/log access would be needed to enumerate every automatic call site precisely.

/** Try to use the list of users and a remote URL to guess a GitHub repository. */
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

/**
 * Match a URL-like string to the Clone URL of a GitHub Repository
 *
 * @param url A remote-like URL to verify against the existing information
 * @param gitHubRepository GitHub API details for a repository
 */
export function urlMatchesCloneURL(
  url: string,
  gitHubRepository: GitHubRepository
): boolean {
  if (gitHubRepository.cloneURL === null) {
    return false
  }

  return urlsMatch(gitHubRepository.cloneURL, url)
}

export function urlsMatch(url1: string, url2: string) {
  const firstIdentifier = parseRepositoryIdentifier(url1)
  const secondIdentifier = parseRepositoryIdentifier(url2)

  return (
    firstIdentifier !== null &&
    secondIdentifier !== null &&
    firstIdentifier.hostname === secondIdentifier.hostname &&
    firstIdentifier.owner === secondIdentifier.owner &&
    firstIdentifier.name === secondIdentifier.name
  )
}

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
