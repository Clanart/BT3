Found the discrepancy: the main `evm/src/apps/IntentGatewayV2.sol` version correctly decrements `msgValue` by the amount actually spent in the fee swap and refunds any leftover ETH to the user [1](#0-0) , and this is covered by a passing test `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` [2](#0-1) . However, the parallel **Tron** deployment of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, omits this accounting entirely.

### Title
Tron IntentGatewayV2.placeOrder() permanently locks user's excess native fee-swap ETH — (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder()`, when an order carries a non-zero `order.fees` and the user pays with native token (`msgValue > 0`), the contract calls `IUniswapV2Router02.swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` but never captures the returned `amounts[0]` (actual ETH spent) nor decrements/refunds the unspent portion of `msgValue` to the user [3](#0-2) . Unlike the audited EVM version, which does `msgValue -= amounts[0]` and later refunds the leftover to `msg.sender` [1](#0-0) , the Tron contract has no equivalent "refund unspent native tokens" step anywhere after the fee block, and no corresponding test exists in the Tron test suite for excess-ETH refund on fee swaps (only the EVM suite has `testPlaceOrder_FeeSwap_RefundsExcessNativeToken` / `testPlaceOrder_NativeTokenOverpayment_RefundsExcess`) [4](#0-3) .

### Finding Description
`swapETHForExactTokens` is a bounded exact-output swap: the router will only spend as much of `msg.value` as needed to obtain exactly `order.fees` of the fee token, and by the Uniswap V2 Router semantics any unspent ETH is refunded back to the *caller of the router*, which here is the `IntentGatewayV2` contract itself (`address(this)` is only the `recipient` of the output token, not the refund target) [5](#0-4) . Because the router refunds to `IntentGatewayV2`, and the Tron contract does not track or forward that refund to `msg.sender`, any ETH sent by the user beyond what is strictly required for the fee swap (or beyond `sum(order.inputs native amounts)`) becomes trapped in the contract with no accounting path to recover it — there is no `msgValue > 0 → refund` branch at the end of `placeOrder` as exists in the mainline EVM contract.

This is structurally the same "bad partial trading" invariant break as the external report: a swap is executed with `sqrtPriceLimitX96`/exact-output style bounded execution and the resulting leftover value (the counterpart of amountOutMinimum=0 letting the trade only partially execute) is not returned to the party who funded it — it is retained by the contract, exactly the scenario the audit flagged ("the remaining value would be held by the contract and not returned to the user").

### Impact Explanation
Any user calling `placeOrder` on the Tron gateway with `order.fees > 0` and sending more native token than the fee swap actually consumes permanently loses that difference — it is not escrowed under any commitment, not returned, and not recoverable through `withdraw`/`cancelOrder` since those only release amounts recorded in `_orders[commitment][token]`. This is a direct loss-of-funds bug reachable by any unprivileged user through the public, unauthenticated `placeOrder` entry point, matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
Likelihood is high in practice: SDK helpers construct the native value sent for `placeOrder` and would need to know the exact ETH cost of the fee swap in advance; any minor overestimate (gas-price/quote staleness, rounding, or a deliberately generous `msg.value` to guarantee swap success) results in fund loss. No malicious relayer, prover, or governance actor is needed — this triggers on ordinary usage by a normal, honest user.

### Recommendation
Mirror the accounting used in `evm/src/apps/IntentGatewayV2.sol`: capture the `amounts` array returned by `swapETHForExactTokens`, decrement `msgValue -= amounts[0]`, and add a final `if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); ... }` refund step to `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with a configured `uniswapV2Router` and `feeToken`.
2. User calls `placeOrder{value: 5 ether}(order, graffiti)` where `order.fees = 1e18` (of fee token) and `order.inputs` contains no native-token entries (so all 5 ETH is intended only to cover the fee swap).
3. `swapETHForExactTokens{value: 5 ether}(order.fees, ...)` spends only the small amount actually required (e.g., ~0.01 ETH) and the Uniswap V2 router refunds the remaining ~4.99 ETH back to `address(this)` (the `IntentGatewayV2` contract), per router refund semantics.
4. `placeOrder` returns without ever forwarding that refund to `msg.sender`; the ~4.99 ETH remains stuck in the contract's balance with no `_orders` entry referencing it and no code path capable of returning it to the user. [6](#0-5)

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
