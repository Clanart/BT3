### Title
OP_RETURN `data` output omitted from fee/weight accounting in `SignableTransaction::new`, causing the payer to fund a transaction priced on an understated total - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report's bug class is "a component that should be included inside a total is instead accounted for outside it, so the amount actually charged is wrong". In Serai's Bitcoin send path, `SignableTransaction::new` constructs the real `tx_outs` by pushing the caller-supplied OP_RETURN `data` output onto `payments`, yet both calls to `SignableTransaction::calculate_weight_vbytes` are made with `payments` only. The OP_RETURN output's weight is therefore never included in the weight/vbytes/`needed_fee` total used to check sufficiency and set the fee — the analog of the external report's `totalAmount`/`ownerShare` accounting error.

### Finding Description
In `SignableTransaction::new` (`networks/bitcoin/src/wallet/send.rs:150-255`):

- The OP_RETURN output is pushed into the actual transaction outputs at `send.rs:194-202`:
  ```rust
  if let Some(data) = data {
    tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
  }
  ```
- The weight/vbytes/fee computation at `send.rs:204` uses `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` — `payments` does not include the `data` output, so the OP_RETURN output contributes nothing to `weight`, `vbytes`, or `needed_fee`.
- The change-with-fee recomputation at `send.rs:225-227` uses the same `payments` slice, so `fee_with_change` is also understated.
- The standardness check `weight > MAX_STANDARD_TX_WEIGHT` at `send.rs:241` uses the understated `weight`, so a transaction with a large (up to 80-byte) OP_RETURN can silently exceed the standard weight while the code believes it conforms.
- The caller-facing invariant "`needed_fee` is the fee this transaction needs at `fee_per_vbyte`" (`send.rs:129-135`) is violated: the real `fee()` at `send.rs:138-141` is `sum(inputs) - sum(outputs)`, which does not account for the missing output's size.

`data` is attacker-influenceable in the real usage of this code path: the Serai stack encodes user-facing transfer metadata (e.g., `Shorthand::transfer` payloads) into OP_RETURN, so an unprivileged user causes these bytes to be included in a transaction the threshold group signs via `TransactionSignMachine::sign` (`send.rs:355-398`, sighash over `Prevouts::All`).

### Impact Explanation
The transaction's actual effective fee rate is `needed_fee / actual_vbytes`, which is lower than the requested `fee_per_vbyte` (shortfall up to `fee_per_vbyte` × ~23 vbytes for an 80-byte OP_RETURN output). The min-relay check at `send.rs:211` is evaluated against the same understated `vbytes`, so it does not catch this. Result: the signed transaction is created paying less fee than `needed_fee()` reports it "needed", and may be underpriced relative to the intended rate or even below the true relay requirement given a large `data` payload, delaying/stalling confirmation of protocol transactions. Additionally, the `MAX_STANDARD_TX_WEIGHT` check is unsound because it ignores the OP_RETURN output's weight.

### Likelihood Explanation
Deterministic, not probabilistic: any call to `SignableTransaction::new` with `data.is_some()` produces a `needed_fee` that omits the OP_RETURN output's ~90+ weight units. There is no rounding or edge-case requirement; the output is simply never passed to `calculate_weight_vbytes`.

### Recommendation
Include the `data`/OP_RETURN output in the weight calculation: build the `payments`-equivalent output slice used by `calculate_weight_vbytes` from the fully assembled output set (or pass `tx_outs` after the OP_RETURN push, matching the function's own comment that only the script_pubkey size matters since values are fixed size). Recompute `vbytes`/`needed_fee` and the `MAX_STANDARD_TX_WEIGHT` check against that complete output list.

### Proof of Concept
Conceptual construction (no secret material needed):

```rust
let data = vec![0u8; 80]; // max allowed by the len > 80 check
let tx = SignableTransaction::new(
  vec![input],            // one confirmed ReceivedOutput
  &payments,              // N payments summing to payment_sat
  Some(change_script),    // change enabled
  Some(data),             // OP_RETURN output
  fee_per_vbyte,
).unwrap();

// needed_fee was computed over calculate_weight_vbytes(inputs, payments, change),
// which never sees the OP_RETURN TxOut, even though tx.tx.output includes it.
assert_eq!(tx.needed_fee(), fee_per_vbyte * vbytes_without_op_return);
// Actual weight of tx.tx is higher by ~90+ WU -> actual fee rate < fee_per_vbyte,
// and tx.needed_fee() under-reports the fee required for the stated rate.
```
