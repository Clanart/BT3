### Title
Escrow withdrawal treats a raw `.call()`'s outer success as proof of token transfer, permanently locking/losing beneficiary funds on non-reverting ERC20 failures - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` redeems escrowed ERC20 tokens with a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks the outer `success` boolean of the call, never the ABI-decoded return value of `transfer()`. This is the same broken pattern the external report describes: a boolean derived from a low-level call is treated as a definitive pass/fail signal, when in reality it does not capture the semantic outcome. Any ERC20 token escrowed by this gateway that returns `false` instead of reverting on a failed transfer (a common, spec-compliant ERC20 behavior) will cause the contract to believe the transfer succeeded, decrement the internal escrow accounting, and emit `EscrowReleased`/`EscrowRefunded`, while the beneficiary never actually receives the tokens.

### Finding Description
In `withdraw()`: [1](#0-0) 
```solidity
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```
`success` only reflects whether the call reverted, not whether `transfer()` returned `true`. Per the ERC20 standard, a compliant token is permitted to return `false` on failure without reverting. The Tron variant deliberately avoids `SafeERC20.safeTransfer` (which the file imports and uses elsewhere for `safeTransferFrom` in `placeOrder`) and instead performs this unchecked raw call in `withdraw` and in the `SweepDust` handler: [2](#0-1) 

`withdraw()` is reached from multiple entrypoints that an ordinary user can trigger without any relayer/prover/admin compromise:
- Same-chain cancellation, callable directly by the order owner: [3](#0-2) 
- Cross-chain redemption/refund delivered by the host after a legitimate proof/response, via `onAccept` and `onGetResponse`: [4](#0-3) [5](#0-4) 

In every path, `_filled[body.commitment]` is set and `_orders[body.commitment][token]` is decremented before/alongside the unchecked transfer, so once the false-success path executes, the order is marked as filled/refunded and its escrow debited — but the beneficiary's balance never changes. There is no other code path to reclaim these tokens: attempting to withdraw the same commitment again reverts with `UnknownOrder` once `_orders[...] == 0`, and there is no admin sweep for the affected commitment's escrow specifically. This directly mirrors the bug class in the report — treating an ambiguous low-level call result as a strong guarantee — except here it isn't merely rejecting valid tokens, it is silently accepting a failed value transfer as a completed settlement, causing real fund loss/lock rather than a stuck-token inconvenience.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary and amount" invariant. Escrowed user or solver funds can be permanently locked in the `IntentGatewayV2` (Tron) contract while the protocol's own bookkeeping (`_orders`, `_filled`) records the order as settled, with events indicating success. This is a direct loss-of-funds condition for legitimate participants (order placers, solvers, or fee recipients) using any non-reverting-on-failure ERC20/TRC20 token, without requiring a malicious relayer, prover, or admin — the proof/consensus path that invokes `withdraw` can be entirely legitimate.

### Likelihood Explanation
The trigger condition — an ERC20 whose `transfer()` returns `false` instead of reverting on failure (e.g., insufficient balance edge cases, paused/blacklist-style tokens, or certain TRC20 tokens common on Tron) — is a normal, spec-permitted implementation detail, not an exotic attack primitive. Because this is the Tron-targeted contract, and Tron's TRC20 ecosystem includes tokens with return-value based failure signaling, the likelihood of encountering such a token in production is non-trivial, and the resulting fund loss is silent (no revert, matching event emitted) making it hard to detect until beneficiaries report missing funds.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the same file (`safeTransferFrom` in `placeOrder`). `SafeERC20` correctly checks both call success and, when return data is present, that it decodes to `true`, closing the gap that lets a non-reverting failed transfer be recorded as a successful settlement.

### Proof of Concept
1. Deploy or use a TRC20/ERC20 token whose `transfer()` implementation returns `false` on failure conditions instead of reverting (spec-compliant behavior).
2. A user places an order via `placeOrder` escrowing this token in `IntentGatewayV2` (Tron).
3. Trigger a legitimate refund/redeem path, e.g., same-chain `cancelOrder` -> `withdraw(body, true)`, at a moment where the token's `transfer()` would return `false` (e.g., a transfer-restricted state on the token).
4. `token.call(...)` succeeds at the EVM level (`success == true`) even though `transfer()` returned `false` internally; no revert occurs.
5. `withdraw()` proceeds to decrement `_orders[body.commitment][token] -= amount`, set `_filled[body.commitment] = beneficiary`, and emit `EscrowRefunded`.
6. The beneficiary's token balance is unchanged — the funds remain stuck in the `IntentGatewayV2` contract — while the protocol considers the order fully settled and no retry path exists (`_orders[...] == 0` triggers `UnknownOrder` on any future attempt).
