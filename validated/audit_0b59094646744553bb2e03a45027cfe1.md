## Analysis

The external report's broken invariant: a value (rebase reward) is computed and handed off to a dependent bookkeeping component, but the hand-off path re-derives/re-notifies state independently from the state the caller actually validated, so the persisted result silently diverges from what was intended (`VotingEscrow.depositFor` never told `LockedManagedReward` about the deposit that `RewardsDistributor.claim` had already computed).

The closest verified Desktop analog is a **time-of-check/time-of-use split between where a file's line-selection is computed and where it is applied to build the commit patch**. `WorkingDirectoryFileChange.selection` is an index-based selection (via `DiffSelection.isSelected(absoluteIndex)`) that is meaningful only relative to a *specific* `ITextDiff` object — the one that was rendered to the user and against which they picked which lines to stage. However, `applyPatchToIndex` in `app/src/lib/git/apply.ts` does not reuse that diff. Instead it independently re-fetches a brand-new diff straight from the working tree at commit time: [1](#0-0) 

and then feeds the user's stale `file.selection` object into `formatPatch(file, diff)` using that freshly-fetched `diff`, not the one the selection was derived from: [2](#0-1) 

`formatPatch` blindly trusts `hunk.unifiedDiffStart + lineIndex` as an absolute index into whatever diff it is given — it never validates that the diff it received matches the diff the selection was created against. If the working-tree file content changes between the moment Desktop rendered the diff (and the user selected/deselected lines) and the moment `_commitIncludedChanges` → `stageFiles` → `applyPatchToIndex` runs, the hunk boundaries and absolute indices shift, so the "same" numeric offsets now point at different lines/hunks. The patch generated and applied to the index (`git apply --cached`) then no longer corresponds to what the user reviewed and intended to include/exclude — a silent corruption of what gets committed, with no error surfaced (unless `git apply` happens to fail on context-line mismatch, which is not guaranteed for `--unidiff-zero` hunks or when changes are additive-only).

This mirrors the report's pattern exactly: the primary state-changing call (`claim`/here, "select lines to commit") is decoupled from the downstream bookkeeping call (`depositFor`/here, "apply patch to index") which independently re-derives its input rather than being notified with the already-validated state, causing silent divergence.

I was not able to fully confirm, in the remaining budget, whether `_commitIncludedChanges`/`refreshChangesSection` re-validates that the working-directory diff is unchanged immediately before staging (an equivalent freshness check exists in the *history* view's `_changeFileSelection`, comparing `file.id` before applying an async-loaded diff, but I could not verify an analogous check exists on the commit/staging path in `app-store.ts` before `applyPatchToIndex` is invoked). This uncertainty affects likelihood but not the core structural gap in `apply.ts`/`patch-formatter.ts`.

### Title
Stale line-selection applied against a freshly re-fetched diff causes silent commit-content corruption - (File: `app/src/lib/git/apply.ts`)

### Summary
`applyPatchToIndex` re-fetches the working directory diff via `getWorkingDirectoryDiff` at patch-build time instead of using the diff the user's line selection was computed against, then feeds that stale, index-based selection into `formatPatch` against the new diff.

### Finding Description
`WorkingDirectoryFileChange.selection` encodes which diff lines the user wants staged as absolute numeric offsets (`hunk.unifiedDiffStart + lineIndex`), meaningful only relative to the exact `ITextDiff` instance rendered in the UI at selection time. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) discards that context and calls `getWorkingDirectoryDiff(repository, file)` again, producing a new diff object from the current on-disk state. `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`) then walks the *new* diff's hunks and tests `file.selection.isSelected(absoluteIndex)` — indices computed against the *old* diff. If the file changed on disk between the two diff computations (e.g. reformatted by a build/watch/format-on-save tool the repository's own tooling triggers, or modified by a git hook/checkout side effect running concurrently), hunk boundaries shift and the same numeric offsets now reference different lines. The resulting patch is applied to the index with `git apply --cached --unidiff-zero --whitespace=nowarn`, which for additive/no-context hunks can succeed even though it stages content the user never selected, or drops content they did select.

### Impact Explanation
This can silently corrupt what the user commits — staging unintended, unreviewed lines, or omitting lines the user explicitly asked to be included — without any warning to the user, matching the "silent corruption of what the user commits or pushes" impact category. Because it operates purely on local working-tree content and Desktop's own diff/apply pipeline, no dialog, hash confirmation, or re-diff-and-compare step intervenes before `git apply --cached` runs.

### Likelihood Explanation
Requires a window between diff computation (shown to the user, selection made) and commit execution during which the working tree file mutates — a routine occurrence in normal development workflows (auto-formatters, linters, watch-mode builds, or repository-provided tooling that touches tracked files), not requiring local/admin access, leaked credentials, or social engineering. Likelihood is moderated by the fact that `git apply` may reject a patch outright when context lines mismatch, which would surface as a visible error in many but not all hunk-shape scenarios (e.g., pure additions/`--unidiff-zero` deletions), so the corruption is exploitable in a subset of edit patterns rather than universally silent. I could not fully verify whether `app-store.ts` re-diffs and re-validates selection just before staging, which would materially change this likelihood assessment.

### Recommendation
Before calling `applyPatchToIndex`, re-fetch the working directory diff and compare a content fingerprint (e.g., hash of the raw diff text or hunk headers) against the diff the current `file.selection` was built from; if they differ, abort the partial-stage/commit and force the UI to reload the diff and require the user to re-confirm their selection rather than silently applying stale offsets to new hunks.

### Proof of Concept
1. Open a repository in Desktop and modify a tracked file, producing a diff with multiple hunks.
2. In the Changes view, deselect specific lines/hunks (partial-stage selection), leaving the diff visible.
3. Before clicking "Commit", externally modify the same file (e.g., via a save-triggered formatter, linter, or any process with write access to the working tree) so the hunk layout shifts (lines inserted/removed above the selected hunk).
4. Click "Commit changes" without Desktop refreshing the diff shown to the user.
5. Inspect the resulting commit: because `applyPatchToIndex` re-fetches the diff and `formatPatch` applies the old numeric selection offsets against the new hunk layout, the committed content differs from what was displayed/selected — either including deselected lines or excluding selected ones, with no error shown to the user.
