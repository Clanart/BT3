### Title
Untrusted `ReceivedOutput` deserialization permits duplicate or nonexistent inputs to inflate spendable funds - ([File: `networks/bitcoin/src/wallet/mod.rs`](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` deserializes an offset, `TxOut`, and outpoint without establishing that the outpoint exists, contains the supplied output, or is unique. [1](#0-0) [2](#0-1)  `SignableTransaction::new` trusts each supplied object when summing input value and constructing transaction inputs, and performs no outpoint deduplication or UTXO lookup. [3](#0-2)  A caller that accepts serialized `ReceivedOutput`s from an untrusted party can therefore treat the same UTXO as multiple spendable inputs or treat a fabricated UTXO as spendable.

### Finding Description
`ReceivedOutput` represents “a spendable output,” but its reader accepts independently supplied `offset`, `output`, and `outpoint` fields and returns them as a coherent spendable object. [4](#0-3) [5](#0-4)  The transaction constructor calculates `input_sat` by summing every supplied output value, converts every supplied outpoint into a `TxIn`, and retains the supplied `TxOut`s as the prevouts committed to by Taproot sighashes. [3](#0-2) [6](#0-5)  The only later ownership check is that each prevout’s script equals the P2TR script derived from the threshold key plus that input’s offset; it does not prove that the outpoint exists or is distinct. [7](#0-6) 

Consequently, deserializing the same authentic `ReceivedOutput` twice makes its value count twice and creates two inputs referencing the same outpoint. [3](#0-2)  Similarly, an attacker who knows the threshold group key and a registered offset can serialize a synthetic `TxOut` paying the corresponding P2TR script, pair it with a nonexistent or mismatched outpoint, and pass the script check in `multisig`. [7](#0-6)  The signing path then commits to the attacker-supplied prevout set and produces per-input signature shares. [8](#0-7) 

### Impact Explanation
This is a Medium-severity accounting and spendability violation: duplicated or fabricated serialized outputs can be reported and accounted as spendable funds even though the resulting transaction is not validly spendable. [4](#0-3) [3](#0-2)  Because `Prevouts::All` commits signatures to the supplied prevout data, the protocol can be induced to generate threshold signatures for a transaction whose duplicated input or fabricated amount/outpoint will fail Bitcoin validation. [8](#0-7)  This can inflate available balance calculations, authorize payments larger than the real inputs support, and stall fund movement through invalid threshold-signed transactions. [9](#0-8) 

### Likelihood Explanation
The direct variant requires no key compromise or malformed cryptographic object: an attacker can replay the bytes of one previously observed `ReceivedOutput` to `ReceivedOutput::read` twice. [5](#0-4)  No uniqueness check prevents both resulting objects from being included in the input vector. [10](#0-9)  For the fabricated variant, the attacker only needs public information—the group key and offset—to derive the required P2TR script because `multisig` checks only that derived script against the supplied prevout script. [11](#0-10) [7](#0-6) 

### Recommendation
Do not allow deserialization alone to construct a trusted spendable `ReceivedOutput`; reconstruct it through `Scanner::scan_transaction`/`scan_block`, or verify the deserialized outpoint against confirmed chain data before marking it spendable. [12](#0-11) [13](#0-12)  `SignableTransaction::new` should reject duplicate `OutPoint`s before summing input values or constructing inputs. [10](#0-9)  Verification should also compare the chain’s actual `TxOut` at the outpoint to the supplied prevout, since `multisig` presently verifies only that the supplied script is derivable from the offset key. [7](#0-6)

  hashes::Hash,
  transaction::Transaction,
  OutPoint, ScriptBuf,

use frost::{curve::Secp256k1, ThresholdKeys};
use k256::Scalar;
use bitcoin_serai::wallet::{ReceivedOutput, SignableTransaction, p2tr_script_buf};

// `authentic` is any serialized output previously produced by Scanner for `keys`.
let encoded = authentic.serialize();

// The same UTXO is deserialized as two independent inputs.
let first = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
let second = ReceivedOutput::read(&mut encoded.as_slice()).unwrap();
assert_eq!(first.outpoint(), second.outpoint());

// `SignableTransaction` counts `first.value() + second.value()` even though both
// objects reference the same outpoint.
let tx = SignableTransaction::new(
  vec![first.clone(), second.clone()],
  &[(payment_script, first.value() + DUST)],
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap();

assert_eq!(
  tx.transaction().input[0].previous_output,
  tx.transaction().input[1].previous_output,
);

// Both duplicated inputs pass the offset/script check and receive signing machines.
let machine = tx.multisig(&keys).unwrap();

The duplicate case works because the reader preserves the same attacker-replayed outpoint while `SignableTransaction::new` sums and inserts both objects without checking whether their outpoints are equal. [14](#0-13) [3](#0-2)  The resulting machine signs each input against the same duplicated prevout data, producing shares for a transaction Bitcoin consensus cannot accept as spending two distinct UTXOs.
