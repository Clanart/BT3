### Title
Strict Schnorr verification rejects valid RFC 8032 signatures with torsioned nonces/keys, causing denial of service for Ed25519 signing flows - (File: crypto/schnorr/src/lib.rs)

### Summary
The bug class in the external report is "strict interface conformance causing DoS": Solmate's `safeTransfer` reverts on tokens that omit a boolean return even though the transfer succeeded. The Serai analog is `SchnorrSignature::verify`: it enforces the strict equation `R + cA - sG == 0` over a prime-order group and, together with the canonical/identity-rejecting `read_G`, refuses signatures that are valid under RFC 8032's cofactored verification (`8R = 8sG - 8cA`) whenever `R` or `A` carries a torsion component. An unprivileged party can submit such a standards-valid signature and have it permanently rejected.

### Finding Description
`SchnorrSignature::verify` computes `multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity()`, i.e. `R + cA - sG == 0` exactly, and `SchnorrSignature::read` requires `R` to deserialize via `C::read_G`, which errors on non-canonical encodings (and, under `Curve::read_G` in `crypto/frost/src/curve/mod.rs:125-131`, on identity). The crate itself documents the consequence at `crypto/schnorr/src/lib.rs:39-41`: "RFC 8032 has an alternative verification formula, 8R = 8s - 8cX, which is intended to handle torsioned nonces/public keys. Due to this library's strict requirements, such signatures will not be verifiable with this library." For Ed25519-family `Ciphersuite`/`Curve` implementations built on `dalek-ff-group`, `G` is a `PrimeGroup`, so any `R` or `A` with a non-trivial torsion component fails `read_G`/`from_bytes` outright, and even if it decoded, the uncofactored batch statement would fail since `R + cA - sG` would equal a torsion point rather than identity. These signatures are produced in the wild: Ed25519 signers that do not clear the cofactor of the nonce commitment, or public keys with torsion, yield signatures that verify under RFC 8032's cofactored check yet are unverifiable here.

### Impact Explanation
Any protocol path that verifies a `SchnorrSignature` supplied by an external, unprivileged party — PoP checks in PedPoP (`EncryptedMessage::read` reads a `SchnorrSignature` at `crypto/dkg/pedpop/src/encryption.rs:171-176`), blame/proof verification, or a downstream consumer verifying an Ed25519 Schnorr signature against a torsioned key — will deterministically reject an otherwise valid proof/signature. The honest participant's message is dropped or the signer is blamed, producing a liveness failure identical in shape to the report's "transaction reverts → contract DoS": a counterparty conforming to the broader standard but not to Serai's stricter interface wedges the protocol.

### Likelihood Explanation
Ed25519 implementations differ on cofactor handling; torsioned nonces/keys occur in real libraries and in adversarially crafted inputs. An attacker can deliberately inject torsion components into `R` (the nonce commitment) of a signature or into a verification share's public key so that the signature is valid under cofactored verification but unreadable/unverifiable under Serai's strict formula. Only the signature bytes are needed — no keys or validator access — making this reachable purely from public inputs to `SchnorrSignature::read`/`verify`.

### Recommendation
Where signatures from parties not bound by Serai's canonicality conventions are verified (e.g., Ed25519/Ed448 ecosystems), verify with the cofactored equation `h·(sG - R - cA) == 0` (multiply `batch_statements` scalars by the cofactor) or explicitly clear/check torsion and document a uniform policy. Keep `read_G`'s canonicality check for consensus-bound encodings, but relax the *verifier formula* for externally-originated signatures, or reject such inputs at a layer where rejection is non-fatal and attributable.

### Proof of Concept
For an Ed25519-based `C: Ciphersuite` over `dalek-ff-group`:
1. Pick a small-order torsion point `T` (order 8) and a key `A` in the prime-order group.
2. Choose `s`, set `R = s·G - c·A + T` for challenge `c = H(R, A, m)` — constructible by signing with a nonce `r'` plus a torsion offset, as non-hardening Ed25519 signers can emit.
3. `s·G = R - T + c·A` satisfies `8R = 8sG - 8cA` (RFC 8032-valid), but `R + cA - sG = T ≠ identity`, so `verify` at `crypto/schnorr/src/lib.rs:108-110` returns false; if `R`/`A` is non-prime-subgroup, `C::read_G` at `crypto/ciphersuite/src/lib.rs:91-101` errors earlier.
4. The valid signature is permanently rejected → DoS of the verification path, mirroring `safeTransfer` reverting on a conforming-but-nonstandard token.
