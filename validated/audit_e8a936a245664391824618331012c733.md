## Analysis

The IBC-Go advisory's failed invariant is: **the same serialized bytes must deterministically decode to the same in-memory value on every node**, regardless of which software/library instance performs the decode. The non-determinism came from Go's JSON `Unmarshal` behavior differing depending on struct tags/parsing order, so identical acknowledgement bytes produced divergent app-level state across validators, halting consensus.

Protobuf's JSON (ProtoJSON) mapping documents this exact class of risk. `docs/design/editions/edition-zero-json-handling.md` explicitly states that when multiple proto field spellings map to the same JSON key, "conflicting mappings lead to undefined behavior. While the behavior is deterministic in all of the cases we've encountered, it's inconsistent across runtimes and unexpected." [1](#0-0) 

I traced this into the Python `_Parser._ConvertFieldValuePair` duplicate-field guard, which is the "strongest actual analog" because it shows a concrete, currently-shipping bypass rather than only a design-doc warning.

### Title
Cross-runtime non-deterministic ProtoJSON field-duplicate detection allows the same JSON payload to decode differently depending on protobuf language implementation - (File: python/google/protobuf/json_format.py)

### Summary
Python's ProtoJSON parser detects duplicate fields by comparing the *raw JSON key string* seen, not the *resolved `FieldDescriptor`* it maps to. A JSON object containing two different key spellings that both resolve to the same proto field (e.g. the camelCase `json_name` and the original snake_case proto field name) bypasses the duplicate-field check entirely and silently applies "last value wins," while other backends (e.g. the C++ conformant JSON parser) track duplicates by field identity and can reject the same payload. Consuming applications that parse the same bounded, attacker-supplied ProtoJSON payload with different protobuf language runtimes (or even different parser configurations within the same runtime) can therefore derive different application states from byte-identical input — the same invariant violated in the IBC-Go advisory.

### Finding Description
`_ConvertFieldValuePair` builds a `names` list of JSON key strings seen so far and raises only `if name in names`: [2](#0-1) 

Field resolution first tries `fields_by_json_name` and falls back to `fields_by_name`: [3](#0-2) 

Because the duplicate check keys off the JSON *string* `name`, not the resolved `field` object, `{"int32Value": 1, "int32_value": 2}` produces two distinct `name` entries ("int32Value", "int32_value") that resolve to the *same* field, but the check never fires. This is confirmed as a known, accepted bug in the maintainers' own test suite: [4](#0-3) 

The same class of ambiguity is called out generally for the whole JSON mapping layer (not just Python) in the design doc, which states the behavior is "deterministic in all of the cases we've encountered, [but] inconsistent across runtimes": [5](#0-4) 

The C++ implementation, by contrast, records "seen" state keyed on the resolved `field` itself via `Traits::RecordAsSeen(*field, msg)`, and by default (`allow_legacy_nonconformant_behavior = true`) only strictly rejects duplicates that hit the *same oneof*, while non-oneof exact-spelling duplicates are controlled by a different flag: [6](#0-5) [7](#0-6) 

This divergence — Python's string-keyed check vs. C++'s field-keyed check, both configurable and both non-conformant-by-default — means the *same* JSON bytes are not guaranteed to parse identically across the protobuf ecosystem's own supported runtimes. Java's older GSON-based parser independently exhibits the analogous silent-duplicate-key acceptance for extension/regular-field name collisions: [8](#0-7) 

### Impact Explanation
Any consuming application that (a) treats ProtoJSON as a canonical/consensus-relevant encoding, and (b) has multiple parsing entry points implemented in different protobuf language bindings (or mixes strict vs. legacy parser options within one binding) is exposed to state divergence when it decodes attacker-supplied, schema-valid, bounded JSON containing intentionally conflicting key spellings for the same field (or oneof). This is exactly the shape of the IBC-Go bug: an ordinary client can craft a small, valid payload that is accepted everywhere but decoded inconsistently, causing downstream logic (e.g., a state-machine transition) to disagree across nodes. Protobuf itself has no consensus/App-level component, so the concrete impact (chain halt) requires a consuming distributed system; within Protobuf the proven, reachable defect is the decode-time integrity violation (same bytes -> different Message trees) across supported first-party parsers.

### Likelihood Explanation
High for reachability: this requires only a public `Parse`/`ConvertMessage` call with attacker-controlled JSON text against a trusted, ordinary schema — no privileged access, no malicious schema, no huge payload. The specific alternate-name collision is already demonstrated and accepted as unfixed by Google's own test comment ("would be a breaking change to fix"), and the general cross-runtime nonconformance is explicitly acknowledged in the project's own design documentation.

### Recommendation
- Make duplicate-field detection identity-based (keyed on resolved `FieldDescriptor`, not raw JSON key string) consistently across all first-party runtimes (Python, Java GSON path, C++, upb).
- Default `allow_legacy_nonconformant_behavior` to `false` for any application that requires deterministic, cross-implementation-safe ProtoJSON parsing, and document that the legacy default is unsafe for consensus-sensitive use.
- Advise consuming systems (per the existing edition-zero design doc) that ProtoJSON must not be treated as canonical for any protocol requiring cross-node byte-for-byte agreement unless `DISALLOW`/strict conformance mode is enforced end-to-end.

### Proof of Concept
Using the existing, already-passing Python test as the reproduction (no changes needed to demonstrate the divergence):

```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2 as pb2

m = pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', m)
print(m.int32_value)  # -> 2, no ParseError raised
```
This matches `testDuplicateFieldAlternateNames` [9](#0-8) 
and contrasts with `testDuplicateField`, which *does* raise for exact-string duplicate keys handled by the underlying Python `json` decoder: [10](#0-9) 
demonstrating that whether a given semantic duplicate is caught depends on incidental string-matching rather than on the always-invariant resolved field identity — the same category of "non-deterministic based on implementation detail" root cause behind the referenced IBC-Go advisory.

**Caveat/uncertainty:** I was not able to directly execute code in this environment, so the PoC above is derived from the existing test file's asserted behavior rather than a freshly-executed run; I have high confidence in it because it is an existing, currently-passing assertion in the repository's own test suite rather than a hypothesized behavior. I also did not verify the exact current default of `case_insensitive_enum_parsing`/`ignore_unknown_fields` interactions with this path, as they are not necessary to the core finding.
