No vulnerability found for this question.

**Reasoning:**

The claimed attack requires two conditions that don't hold in this codebase:

1. **BLS12-381 compressed point encoding is canonical.** The `BlsPublicKey` type is a 48-byte compressed G1 point [1](#0-0) , and decompression via `pubkey_to_projective`/`bls::pubkey_to_point` [2](#0-1)  relies on the standard BLS12-381 compressed serialization, which (per the standard used by `blst`-style libraries) maps each valid curve point to exactly one 48-byte compressed encoding — there is no non-canonical alternate encoding of the same point to exploit as claimed.

2. **Validators are not added through unprivileged attacker input.** `ValidatorSet::add_validator` is only invoked in two contexts: (a) `PharosProver::build_validator_set`, which decodes RPC-sourced validator data outside consensus verification [3](#0-2) , and (b) `decode_validator_set_from_storage`, which reconstructs the validator set strictly from a **verified Merkle/storage proof against the trusted header state root** of the Pharos staking contract, rejecting duplicates explicitly via `Error::DuplicateValidator` [4](#0-3) . An attacker cannot call `add_validator` directly through any bridge-exposed message/proof path — validator membership is derived from the actual on-chain staking contract state, meaning becoming a second "distinct" entry requires actually registering a second validator/pool on the underlying Pharos chain, which is normal staking behavior on that chain, not an unprivileged exploit of the bridge's verification logic, and is out of scope per the excluded "malicious node/staking infrastructure" category.

3. **Participant deduplication is already enforced independently.** `verify_validator_membership` deduplicates participant keys via a `BTreeSet` over the raw key bytes and rejects any duplicate byte-identical key with `Error::DuplicateParticipant` [5](#0-4) , and this is explicitly tested [6](#0-5) . Even granting the (cryptographically implausible) premise of two distinct byte encodings for one BLS point, `aggregate_public_keys` decompresses every key and would produce an aggregate public key that does not match the actual single signer's point unless both encodings decompress identically — and the code explicitly guards against malformed/junk keys silently padding the quorum [7](#0-6) .

Given canonical BLS12-381 compressed-point serialization and the fact that `ValidatorSet` construction is gated by a proof-verified on-chain source (not unprivileged bridge input), the described double-counting path is not exploitable through any unprivileged Hyperbridge entry point.

			let info = ValidatorInfo { bls_public_key, pool_id, stake };

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
