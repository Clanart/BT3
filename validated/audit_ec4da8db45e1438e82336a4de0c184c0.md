### Title
Unhandled `uint64` underflow (`OverflowError`) in mempool fee calculation causes uncaught exception on malicious spend bundle - (File: `chia/full_node/mempool_manager.py`)

### Summary
`MempoolManager.validate_spend_bundle()` computes the transaction fee as `fees = uint64(removal_amount - addition_amount)` without first checking that `removal_amount >= addition_amount`. `chia_rs`'s `uint64` constructor raises `OverflowError` on negative input (confirmed by `chia/_tests/core/custom_types/test_coin.py:77-83`, which shows `uint64(-1)` raises `OverflowError: can't convert negative int to unsigned`). If `addition_amount` exceeds `removal_amount`, this line raises an uncaught exception instead of returning a structured `Err`. [1](#0-0) 

### Finding Description
`addition_amount` is accumulated purely from the `CREATE_COIN` conditions returned by each coin's CLVM puzzle execution, with no upper bound relative to the amount of the coin being spent: [2](#0-1) 

`removal_amount` is the sum of the actual (existing) coin amounts being spent, looked up from the coin store / ephemeral additions: [3](#0-2) 

The fee is then computed as an unchecked subtraction cast directly to `uint64`: [4](#0-3) 

Unlike full block validation (`validate_block_body`), which explicitly guards against this exact case with an ordered check (`if removed < added: return Err.MINTING_COIN`) *before* computing `fees = removed - added`, the mempool-level fee computation has no equivalent guard: [5](#0-4) 

A spend bundle whose puzzle reveal legitimately unlocks an owned coin (e.g. a custom puzzle designed by the attacker for their own coin) can emit a `CREATE_COIN` condition with an amount far greater than the coin's actual value (any value up to `MAX_COIN_AMOUNT` / `uint64` range is accepted by CLVM condition parsing). Because the CLVM interpreter for a revealed puzzle does not itself enforce "output ≤ input" for standard `CREATE_COIN` conditions (that invariant is only consensus-enforced at the block level, and the discount/fee-style subtraction in mempool code is not similarly protected), `addition_amount` can exceed `removal_amount` for a bundle that reaches this code path in `validate_spend_bundle()`.

This is directly analogous to the reported Hubble `ClearingHouse.sol` bug class: an unchecked subtraction of a value (`discount`/`referralBonus`, here `addition_amount`) from a base value (`feeCharged`/`toFeeSink`, here `removal_amount`) that can be exceeded by an attacker-influenced input, causing underflow/exception instead of a controlled rejection.

### Impact Explanation
This falls into the "spend-triggered transaction-processing halt" category. `validate_spend_bundle()` is invoked as part of processing every spend bundle submitted to the mempool (via `add_spend_bundle`/`pre_validate_spendbundle`, called from `full_node.py` when handling incoming/relayed transactions and from the wallet RPC `push_tx` path). An uncaught `OverflowError` raised deep inside this function, if not defensively caught by the calling code, would propagate as an unhandled exception in the transaction-processing pipeline for that spend bundle. At minimum, this crashes/aborts processing of that specific request; depending on how the calling task's exception is surfaced, it can disrupt the full node's transaction-handling flow for that peer/RPC call. This is reachable purely from a single, unprivileged, submitted spend bundle — no special privileges or peer/node compromise needed.

### Likelihood Explanation
Medium: constructing a spend bundle that reveals a custom puzzle for a coin one owns, and having that puzzle emit a `CREATE_COIN` condition with an amount greater than the coin's own value, is straightforward CLVM authoring within reach of any spend-bundle submitter. The bundle will fail eventual full-block/consensus validation (as `MINTING_COIN`), but the question is whether it reaches the unguarded subtraction in the *mempool* admission path first and whether that raises before any structured error handling. I was not able to fully trace/confirm (within the available tool budget) whether an enclosing `try/except` at the caller (`add_spend_bundle` / `full_node.py` transaction-receive handler) already wraps this call and safely converts any exception into a rejected/failed status rather than propagating further — this would determine whether the practical impact is a benign per-bundle rejection or an actual processing halt. This is the main remaining uncertainty.

### Recommendation
Add an explicit guard in `chia/full_node/mempool_manager.py::validate_spend_bundle()` mirroring the block-validation logic, e.g.:
```python
if addition_amount > removal_amount:
    return Err.MINTING_COIN, None, []
fees = uint64(removal_amount - addition_amount)
```
This converts the case into a normal, structured `Err` result instead of an unhandled `OverflowError`, consistent with how `chia/consensus/block_body_validation.py` already handles the analogous check.

### Proof of Concept
1. Craft a spend bundle spending an owned coin `C` of amount `1` mojo, using a custom puzzle reveal (not the standard puzzle) whose CLVM code unconditionally returns `(CREATE_COIN <attacker_puzzle_hash> 1000000)` regardless of solution — this is valid, self-authored puzzle logic for a coin the attacker owns and can reveal/spend.
2. Submit this spend bundle to a full node (e.g., via `push_tx` RPC or gossip).
3. `MempoolManager.pre_validate_spendbundle()` → `validate_spend_bundle()` computes `removal_amount = 1`, `addition_amount = 1000000` from the parsed conditions, then executes `fees = uint64(removal_amount - addition_amount)` → `uint64(-999999)`, raising `OverflowError` per the confirmed `uint64` behavior (`chia/_tests/core/custom_types/test_coin.py:77-83`), instead of returning `Err.MINTING_COIN` as the equivalent block-validation path does.
