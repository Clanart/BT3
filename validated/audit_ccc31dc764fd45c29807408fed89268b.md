## Analysis

Reducing the referenced report to its core primitive: **a payable entry point accepts `msg.value` greater than the fee actually consumed, and the excess is never returned to the payer** — it is silently retained by the receiving contract.

The Hyperbridge analog is in `EvmHost.dispatch(DispatchPost)` / `EvmHost.dispatch(DispatchGet)` / `EvmHost.fundRequest()`, which handle native-token fee payment by swapping ETH for the exact `feeToken` amount via Uniswap V2:

```solidity
// evm/src/core/EvmHost.sol:921-932
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
``` [1](#0-0) 

`IUniswapV2Router02.swapETHForExactTokens` refunds any unspent ETH to whichever address invoked the router call. That caller is `EvmHost` itself (it is `EvmHost` that calls the router, not the original user/app). The router therefore returns leftover ETH into `EvmHost`'s own balance rather than back to the account that actually funded the transaction (the user calling `dispatch`, or an intermediary app such as `HyperFungibleToken.send()` or `HyperbridgeLzEndpoint._send()` that forwarded `msg.value` on the user's behalf). Neither `dispatch()` nor `fundRequest()` contains any post-swap logic to forward the router's refund back to `_msgSender()`. [2](#0-1) 

Critically, this is not a merely theoretical assumption — the codebase itself documents the (incorrect) belief that this refund reaches the original payer:

```solidity
// sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol:337-345
// Apply a generous 2x buffer to absorb the legacy deployed host's
// per-byte protocol fee (the in-source host has no such markup). Excess
// native is refunded by the uniswap router; excess feeToken approval is
// simply unused.
if (_params.payInLzToken) {
    return MessagingFee({nativeFee: 0, lzTokenFee: request.fee * 2});
} else {
    return MessagingFee({nativeFee: quote(request) * 2, lzTokenFee: 0});
}
``` [3](#0-2) 

This 2x buffer is deliberately applied on the assumption that any excess ends up back with the caller. In reality, the caller (the LZ endpoint contract, funded by the end user) forwards the buffered `msg.value` to `dispatch()`, and the unspent half is captured by `EvmHost`, not refunded to the LZ endpoint or the underlying user: [4](#0-3) 

This differs from other parts of the same codebase where developers explicitly implemented manual excess-refund logic after calling `dispatch()`, confirming the team is aware refunds must be handled manually and does not rely on the Uniswap router to do it correctly for the depositor:

```solidity
// evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-168
// Refund any unspent native tokens to the solver.
if (msgValue > 0) {
    (bool sent,) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
``` [5](#0-4) 

But that refund logic covers only the `IntentGatewayV2`/`ExtrinsicIntents` overpayment *before* the `nativeDispatchFee` is sent to `dispatch()` — it does not, and cannot, recover ETH that is lost *inside* `EvmHost.dispatch()`'s own swap when `msgValue` passed there exceeds the router's required input, since that excess never returns to `ExtrinsicIntents` in the first place.

## Title
`EvmHost.dispatch()`/`fundRequest()` capture excess native-token overpayment instead of refunding the payer - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and swap it for an exact amount of `feeToken` via `swapETHForExactTokens`. Any ETH sent in excess of the exact swap input required is refunded by the Uniswap router to `EvmHost` (the caller of the swap), not to the original payer, and `EvmHost` never forwards that refund onward. The excess is permanently absorbed into the Host contract with no user-facing recovery path.

### Finding Description
`swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is called with the entire `msg.value` EvmHost received, but only enough of it is consumed to buy `post.fee` worth of `feeToken`; Uniswap V2's router refunds the unspent ETH to `msg.sender` of that call, which in this context is `EvmHost` itself. `EvmHost` has no logic afterward to forward the refunded difference to `_msgSender()` (the account or app that funded the original `dispatch`/`fundRequest` call). The same pattern appears in three functions: `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`. [6](#0-5) [2](#0-1) 

This exactly mirrors the external report's broken invariant (payable function accepts `msg.value` > required cost, excess never returned), except here it affects the core dispatch path used by every downstream app (`HyperFungibleToken`, `HyperbridgeLzEndpoint`, `ExtrinsicIntents`/`IntentGatewayV2`, and any third-party `HyperApp`) whenever native-token payment is used, as documented and recommended in the project's own docs. [7](#0-6) 

### Impact Explanation
Any account calling `dispatch()` or `fundRequest()` with `msg.value` greater than the exact amount consumable by the Uniswap swap permanently loses that difference — the funds accrue silently inside `EvmHost`'s own balance rather than the depositor's. Given documentation explicitly recommends sending buffered/generous `msg.value` amounts to guard against slippage, and `HyperbridgeLzEndpoint` deliberately applies a 2x buffer under the false assumption the router refunds it to the payer, this results in systematic, non-trivial loss of user/app funds across every integration that uses native-token dispatch. This satisfies the "stealing or loss of funds" impact criterion.

### Likelihood Explanation
High. This is triggered by ordinary usage, not by a malicious actor: any user or `HyperApp` that follows the documented "Native Token Payment" pattern and sends a safety buffer above the exact estimated fee (a standard, recommended practice due to Uniswap slippage/quote imprecision) will lose the buffered amount on every single dispatch call. The `HyperbridgeLzEndpoint`'s explicit 2x buffer comment demonstrates this is an actual, currently-shipped usage pattern in the codebase, not a hypothetical edge case.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the actual ETH balance change (or use `swapETHForExactTokens`'s return value together with `address(this).balance` before/after) and refund any leftover ETH to `_msgSender()` via a low-level call, reverting on failure — mirroring the pattern already used in `ExtrinsicIntents._fillCrossChain`.

### Proof of Concept
1. Deploy/use `EvmHost` with a configured Uniswap V2 router and `feeToken`.
2. An app (e.g. `HyperbridgeLzEndpoint._send`) or a direct EOA calls `dispatch{value: X}(post)` where `X` includes a buffer above the ETH actually needed to purchase `post.fee` units of `feeToken` (e.g., `X = 2 * requiredNative` as in `HyperbridgeLzEndpoint.quote()`).
3. Inside `dispatch`, `swapETHForExactTokens{value: X}(post.fee, path, address(this), deadline)` consumes only `amountIn <= X` ETH; the router refunds `X - amountIn` ETH to `msg.sender` of the swap call, i.e., `EvmHost`.
4. Observe: `EvmHost`'s native ETH balance increases by `X - amountIn`; the original caller's balance decreases by the full `X`, and no refund event/transfer is emitted back to them.
5. Repeat across multiple dispatches: `EvmHost` accumulates ETH belonging to callers with no user-triggerable withdrawal path, confirming permanent fund loss for the payer.
