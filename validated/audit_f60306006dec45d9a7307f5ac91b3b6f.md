### Title
Time-of-check/time-of-use gap between diff review and patch staging silently commits unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
The Solidity report's broken invariant is: a piece of derived accounting state (`totalDepositToProcess`) is computed once and then trusted at a later point without being reconciled against the current ground truth, letting an attacker desynchronize belief from reality. GitHub Desktop has a structural analog in its partial-commit ("stage part of a file") pipeline: the user's line selection (`DiffSelection`, a set of *absolute line indices*) is computed against one instance of a diff, but is applied — unchecked — against a **freshly re-fetched diff** at staging time, with no verification that the two diffs are the same. If the tracked file's on-disk content changes between the moment the diff was shown/selected and the moment `applyPatchToIndex` runs, the same line indices can now refer to different content, and that content is silently staged and committed.

### Finding Description
When a user reviews a diff in the Changes view, line selections are stored purely as index sets in `DiffSelection` (`app/src/models/diff/diff-selection.ts`), with `isSelected(lineIndex)` operating only on integer positions, not on line content or a diff/content hash: [1](#0-0) 

That `DiffSelection` is carried on the `WorkingDirectoryFileChange` object, but the diff it was computed against is **not** carried along when the file is passed into the commit pipeline. When staging happens, `stageFiles` calls `applyPatchToIndex` for any file with a partial selection: [2](#0-1) 

`applyPatchToIndex` then re-fetches the diff from disk at that moment, rather than reusing the diff the user actually looked at when making the selection: [3](#0-2) 

`formatPatch` then blindly applies the old index-based selection to whatever hunks/lines this new diff produced: [4](#0-3) 

There is no check anywhere in this path that the diff fetched in `applyPatchToIndex` is the same diff the selection was derived from (no hash/tip comparison, no hunk-count/line-content validation). Compare this with the app's own UI code, which *is* careful about this exact race when refreshing the on-screen diff (it discards a freshly loaded diff if the selection changed underneath it): [5](#0-4) 

That defensive re-validation exists for the *UI rendering* path, but the equivalent check is absent from the *staging/commit* path in `applyPatchToIndex`, which is the code that actually determines what bytes end up in the commit.

The corrupted value is effectively the mapping from `DiffSelection` indices → diff content: the app implicitly assumes this mapping is stable between diff-load time and commit time, but nothing enforces that invariant, exactly mirroring how the Solidity contract implicitly assumed `totalDepositToProcess` tracked real deposits without any code enforcing the relationship after withdrawal.

### Impact Explanation
If the tracked file content changes between when the user makes a partial-line selection and when they click "Commit" — e.g., because a repository-provided build/watch process, formatter, code generator, or git hook (many JS/TS projects instruct users to run `npm run dev`/`watch` immediately after cloning, and hook installers like Husky run automatically via `npm install` postinstall scripts) rewrites the file — the stale line indices from the old selection are silently reapplied to the new diff. This can:
- Stage and commit lines the user explicitly deselected (thought they were excluding secrets, debug code, or unwanted changes) — a **silent corruption of what the user commits and subsequently pushes**.
- Produce commits whose diff does not match what was shown/approved in the UI, undermining the entire "review before commit" trust model that Desktop is built around.

This is not a local/physical-access, admin, or malware precondition — the working tree mutation can be driven entirely by content that arrives from the cloned/fetched malicious repository itself (its own scripts/hooks), combined with completely normal developer workflow.

### Likelihood Explanation
Requires: (1) a repository whose normal, expected workflow includes a background process that rewrites tracked files (very common — formatters, code generators, dev-server hot-reload writers, lint-staged/husky hooks), and (2) the user making a partial (line-level) selection and taking some time before committing, which is an entirely ordinary Desktop usage pattern. No unnatural steps, elevated privileges, or pre-existing compromise are required. The main uncertainty is the exact window size and how frequently a given attacker-controlled auto-write process would collide with the specific lines a user has selected — this is probabilistic/racy rather than deterministic, which is the main factor tempering likelihood.

### Recommendation
Make the diff an explicit, immutable input to the staging pipeline instead of re-deriving it:
- Pass the exact `IDiff`/`ITextDiff` that was used to construct the user's `DiffSelection` into `applyPatchToIndex` (similar to how `discardChangesFromSelection` already takes an explicit `diff` parameter) instead of calling `getWorkingDirectoryDiff` again inside `apply.ts`.
- Before applying the patch, verify the freshly-observed working directory diff for the file is unchanged (e.g., compare hunk structure/line counts, or a content hash) relative to the diff the selection maps to; if it differs, abort staging that file and surface an error/refresh requirement to the user rather than silently applying a mismatched selection.

### Proof of Concept
1. Clone a repository whose README instructs running `npm run dev` (a normal step), which starts a watcher that periodically rewrites `tracked-file.txt` (e.g., appends a build timestamp near the top of the file, shifting line numbers).
2. In GitHub Desktop, open the Changes view for `tracked-file.txt`, which now shows several diff hunks. Deliberately deselect a specific added line (e.g., a line containing sensitive data the user does not want to commit) using the line-level selection UI — this creates a `DiffSelection` keyed to the current hunk/line layout.
3. While the watcher process is running, wait for it to rewrite the file again before pressing "Commit" (or trigger it manually to simulate the timing).
4. Click "Commit". `stageFiles` → `applyPatchToIndex` re-fetches the diff (`app/src/lib/git/apply.ts:60`), which now has shifted hunk offsets due to the watcher's edit, and `formatPatch` applies the old selection's absolute-index set to this new diff (`app/src/lib/patch-formatter.ts:157`).
5. Inspect the resulting commit (`git show`): the deselected sensitive line is present in the commit despite the user having explicitly unchecked it in the UI, and/or unrelated lines are included/excluded relative to what was shown at commit time — demonstrating silent corruption of the committed content.
