### Title
Native ERC20 pointer `decimals()` (and name/symbol) can be silently changed for an already‑deployed pointer contract via `addNativePointer` re‑upsert, breaking mid‑cycle scaling assumptions of downstream integrators - (File: `x/evm/keeper/pointer_upgrade.go`)

### Summary
The pointer precompile's `addNativePointer` method has upsert semantics: calling it again for a denom that already has a pointer contract does not create a new contract, it **redeploys the constructor logic in place at the same address**, overwriting the pointer's `name`, `symbol`, and `decimals` storage with whatever the bank module's *current* denom metadata says. Because a tokenfactory denom admin can update that metadata at any time via `MsgSetDenomMetadata`, and `addNativePointer` itself is callable by any unprivileged EVM caller, the `decimals()` value of an existing, already-integrated ERC20 pointer contract can change mid-flight — exactly the same "collateral decimals changes mid deposit/withdraw cycle" bug class described in the SolverVaults report, but reachable here through the sei native pointer + tokenfactory combination instead of a Symmio admin call.

### Finding Description
`AddNative` in the pointer precompile pulls `decimals` from the bank module's live denom metadata and calls `UpsertERCNativePointer`: [1](#0-0) 

`UpsertERCNativePointer` delegates to `UpsertERCPointer`, which checks whether a pointer already `exists` for the denom. If it does, instead of deploying a fresh contract it calls `evm.GetDeploymentCode` against the **existing address** and overwrites its code/storage with the new constructor arguments (name/symbol/decimals), then writes the resulting bytecode with `SetCode`: [2](#0-1) 

This "re-upsert changes decimals in place at the same address" behavior is explicitly exercised and confirmed by the keeper's own test, which re-registers the same token with decimals 6 → 12 and asserts the *same* contract address now reports the new decimals: [3](#0-2) 

Critically, `addNativePointer` has **no access control** beyond rejecting static/delegatecalls — any unprivileged EVM account can call it: [4](#0-3) 

And the source of the decimals value it uses — the bank denom metadata — is itself mutable by an ordinary (non-governance, non-validator) tokenfactory denom admin via `MsgSetDenomMetadata`, which only checks that the sender is the denom's own admin: [5](#0-4) 

Putting this together: a tokenfactory denom admin (an ordinary user, not an operator/validator/governance actor) can change their denom's metadata (e.g. add a higher-exponent denom unit) at any time, and then any user (including the admin) can call `addNativePointer` on the public pointer precompile to force a redeploy of the *existing* pointer contract in place, changing its `decimals()` return value. Any protocol built on top of that pointer's ERC20 interface (vaults, AMMs, lending markets) that reads and caches `decimals()` at deposit time and reuses it later for share/asset conversion will now compute against a stale or inconsistent scale — the same root cause pattern as the reported `setSymmioAddress`/`updateCollateral` issue: a decimals value used for conversion math is mutated mid-lifecycle by a party with only narrow administrative authority (denom admin), not full governance control, and the change is felt by unrelated third-party contracts that never opted into it.

### Impact Explanation
Any external contract that treats the sei-chain ERC20 native pointer's `decimals()` as an immutable per-token constant (a completely standard ERC20 assumption) can have its conversion math corrupted after the fact. If a user deposits collateral/shares while `decimals` = 6 and later withdraws after `decimals` becomes 12 (or vice versa), amount scaling will be off by orders of magnitude, causing fund loss for users or the protocol (users can withdraw far more or far less value than they should) — this matches the accepted "unauthorized transfer via precompile or pointer" / fund-loss impact bar.

### Likelihood Explanation
The path requires only: (1) a tokenfactory denom whose admin is any ordinary account (no special sei-chain privilege — creating a tokenfactory denom is permissionless), (2) that admin issuing `MsgSetDenomMetadata` to change the decimals in the denom unit list, and (3) anyone calling the public `addNativePointer` method on the pointer precompile for that denom again. All three steps are ordinary, permissionless transactions reachable from a normal user, and the keeper's own regression test demonstrates the underlying mechanism works exactly as described (decimals change on redeploy at the same address).

### Recommendation
- Once an ERC20 native pointer has been deployed for a denom, do not allow `decimals` (and ideally `name`/`symbol`) to change on subsequent `addNativePointer`/`UpsertERCNativePointer` calls — either reject the upsert if the decimals differ from the already-stored value (mirroring the `SolverVaults` recommendation of rejecting collateral changes), or make `decimals` genuinely immutable once first set, independent of what the current bank denom metadata reports.
- Alternatively, restrict re-registration of an existing pointer's decimals to a governance-gated path (as is already done for `AddERCNativePointerProposalV2`), rather than allowing the permissionless `addNativePointer` precompile method to silently mutate a live pointer's decimals sourced from admin-controlled denom metadata.

### Proof of Concept
1. User A creates tokenfactory denom `factory/A/foo` and sets initial bank denom metadata with a denom unit exponent of 6 (decimals = 6).
2. Any user calls the pointer precompile `addNativePointer("factory/A/foo")`. This deploys the ERC20 pointer contract at address `P` with `decimals() == 6`.
3. A third-party protocol integrates `P`, and a user deposits funds, with the protocol recording/caching `P.decimals() == 6` for later conversion math.
4. User A (still admin of the denom) calls `MsgSetDenomMetadata` to update the denom's metadata, adding a denom unit with exponent 18 (decimals = 18) — this is confirmed to be an ordinary admin operation, no governance needed: [6](#0-5) 
5. Any user calls `addNativePointer("factory/A/foo")` again. Per `UpsertERCPointer`, since the pointer already exists at `P`, the keeper redeploys constructor logic in place, and `P.decimals()` now returns 18 (exactly as demonstrated by `TestUpsertERCNativePointer`): [3](#0-2) 
6. The user from step 3 now withdraws from the third-party protocol; the protocol's cached decimals=6 assumption no longer matches `P`'s live decimals=18, producing a 10^12 scaling error in the conversion, causing gross overpayment or underpayment.

	var bin []byte
	bin, err = artifacts.GetParsedABI(typ).Pack("", args...)
	if err != nil {
		panic(err)
	}
	bin = append(artifacts.GetBin(typ), bin...)
	// GetDeploymentCode / Create take EVM snapshots that Freeze() Multistore layers.
	// Exists-lookup and commits must use the live unfrozen top (sdb.Ctx): cachekv

	// Prepare time, but is frozen once this Upsert snapshots. Always attach the
	// caller's gas meter (finite precompile meter in deliver) — sdb.Ctx() alone
	// carries the infinite EVM meter.
	sdb := state.GetDBImpl(evm.StateDB)
	liveCtx := func() sdk.Context {
		if sdb == nil {
			return ctx
		}
		return sdb.Ctx().WithGasMeter(ctx.GasMeter())
	}
	existingAddr, _, exists := getter(liveCtx(), pointee)
	suppliedGas := k.getEvmGasLimitFromCtx(ctx)

func TestUpsertERCNativePointer(t *testing.T) {
	k := &testkeeper.EVMTestApp.EvmKeeper
	ctx := testkeeper.EVMTestApp.GetContextForDeliverTx([]byte{}).WithBlockTime(time.Now())
	ctx = ctx.WithGasMeter(sdk.NewInfiniteGasMeterWithMultiplier(ctx))
	var addr common.Address
	err := k.RunWithOneOffEVMInstance(ctx, func(e *vm.EVM) error {
		a, err := k.UpsertERCNativePointer(ctx, e, "test", utils.ERCMetadata{
			Name:     "test",
			Symbol:   "test",
			Decimals: 6,
		})
		addr = a
		return err
	}, func(s1, s2 string) {})
	require.Nil(t, err)
	var newAddr common.Address
	err = k.RunWithOneOffEVMInstance(ctx, func(e *vm.EVM) error {
		a, err := k.UpsertERCNativePointer(ctx, e, "test", utils.ERCMetadata{
			Name:     "test2",
			Symbol:   "test2",
			Decimals: 12,
		})
		newAddr = a
		return err
	}, func(s1, s2 string) {})
	require.Nil(t, err)
	require.Equal(t, addr, newAddr)
	res, err := k.QueryERCSingleOutput(ctx, "native", addr, "name")
	require.Nil(t, err)
	require.Equal(t, "test2", res.(string))
	res, err = k.QueryERCSingleOutput(ctx, "native", addr, "symbol")
	require.Nil(t, err)
	require.Equal(t, "test2", res.(string))
	res, err = k.QueryERCSingleOutput(ctx, "native", addr, "decimals")
	require.Nil(t, err)
	require.Equal(t, uint8(12), res.(uint8))
	_, err = k.QueryERCSingleOutput(ctx, "native", addr, "nonexist")
	require.NotNil(t, err)
}

func (server msgServer) SetDenomMetadata(goCtx context.Context, msg *types.MsgSetDenomMetadata) (*types.MsgSetDenomMetadataResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	// Defense in depth validation of metadata
	err := msg.Metadata.Validate()
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Metadata.Base)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	server.bankKeeper.SetDenomMetaData(ctx, msg.Metadata)

	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgSetDenomMetadata,
			sdk.NewAttribute(types.AttributeDenom, msg.Metadata.Base),
			sdk.NewAttribute(types.AttributeDenomMetadata, msg.Metadata.String()),
		),
	})

	return &types.MsgSetDenomMetadataResponse{}, nil
}
