### Title
ReDoS-detection bypass in `security-patterns.yaml` custom regex validation allows catastrophic-backtracking DoS of the security-guidance hook - (File: `plugins/security-guidance/hooks/extensibility.py`)

### Summary
The bug report describes a regex whose `.* ` quantifier is too permissive/imprecise, causing it to mismatch (match the wrong thing or fail to bound the intended target). The equivalent, reachable analog in this repo is `_has_redos_structure()` in `plugins/security-guidance/hooks/extensibility.py`, which is a regex-based static filter meant to reject catastrophic-backtracking ("evil") regexes supplied by users via a project-level `security-patterns.{yaml,json}` config. Because its detector regexes assume flat (non-nested) parenthesized groups, a classic nested-quantifier ReDoS pattern slips through undetected, is accepted as a valid custom security-scanning rule, and is later run with `re.search()` against every file Claude Code edits — hanging the `PostToolUse` security-guidance hook.

### Finding Description
`_has_redos_structure()` [1](#0-0)  uses three heuristics to reject dangerous regexes before they are added to `_user_patterns`:

```python
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")
```

All three patterns use `[^()]*` to describe "the content inside a group," which by construction cannot span across an inner set of parentheses. This means the detector can only see one level of grouping. A classic catastrophic-backtracking construct written with an extra (functionally pointless) capturing group around the inner quantified atom — e.g. `^(([a-zA-Z])+)+$` — is structurally identical to the canonical `(a+)+` ReDoS shape, but is invisible to all three checks:

- `_REDOS_SHAPES[0]` requires a quantifier character (`+`/`*`) to appear *immediately before the closing paren, inside the same unnested group*. In `(([a-zA-Z])+)+`, the `+` that quantifies the inner group sits *outside* the inner parens and the outer group's content contains a nested `(...)`, so `[^()]*` cannot bridge past it — neither the inner `([a-zA-Z])` nor the outer `(([a-zA-Z])+)` satisfies the pattern.
- `_REDOS_SHAPES[1]` only matches literal `.* ` wildcard groups, not character-class-based nested quantifiers.
- `_ALT_UNDER_REP` only fires on alternation (`|`), which this pattern doesn't use.

`_validate_pattern()` [2](#0-1)  only calls `_has_redos_structure()` and `re.compile()` (which succeeds — the regex is syntactically valid) before accepting the rule, so the pattern is stored with `rule["regex"] = regex` and returned into `_user_patterns`.

At scan time, `check_patterns()` in the main hook runs every accepted user regex with plain `re.search()` against arbitrary file content on every edit, with only a broad `except Exception` (which does not catch or bound a slow-but-not-erroring backtracking search): [3](#0-2) 

Since this hook is invoked as `PostToolUse` on Edit/Write/MultiEdit, any file content containing a long run of matching characters without the anchor's required terminator causes exponential-time backtracking in CPython's `re` engine, hanging the hook process.

### Impact Explanation
`security-patterns.yaml`/`.json` is discovered from `<cwd>/.claude/` — i.e., project-committed config, matching the "project, committed" precedence tier documented in the module's own trust model comment [4](#0-3) . Any contributor who can land such a file in a repository (e.g., via a PR, or simply as a collaborator without elevated trust) can introduce a rule that passes `_has_redos_structure`'s "safety" gate but is a genuine exponential-blowup regex. Once merged, every subsequent Claude Code session in that project that edits a file whose content is large/adversarial with respect to the regex will hang the `PostToolUse` hook, stalling or freezing tool execution for any user of the session — a local availability/DoS impact on the tool-authorization/hook pipeline, achievable by an unprivileged contributor without any special access.

### Likelihood Explanation
Moderate-to-high: constructing the bypass regex requires no special access beyond the ability to add/modify a `.claude/security-patterns.yaml` file (a normal, documented extensibility point), and the bypass pattern is a well-known, simple ReDoS idiom (`(group)+` where `group` itself contains an unbounded quantifier) that is easy to discover by anyone familiar with catastrophic backtracking. The detector's comment itself acknowledges it is a "heuristic... not a proof," but the specific nested-parenthesis blind spot is a mechanical property of the `[^()]*` sub-expression, not merely of adversarial cleverness.

### Recommendation
- Do not rely on a single-level regex heuristic to detect nested catastrophic-backtracking structures; either use a proper regex AST/parser (e.g., Python's `re._parser` or a dedicated ReDoS-analysis library) to recursively inspect quantified subgroups, or
- Enforce a hard runtime bound regardless of static analysis: execute user-supplied regexes with a timeout (e.g., via a worker process/`signal.alarm`, `regex` module's timeout support, or the `re2`/`google-re2` engine, which has no backtracking and is immune to ReDoS) instead of trusting pre-validation alone.
- Treat `_has_redos_structure` purely as a fast-path optimization, not the sole safety boundary.

### Proof of Concept
1. Add `.claude/security-patterns.yaml` to a repository with:
```yaml
patterns:
  - rule_name: fake_rule
    reminder: "test"
    regex: "^(([a-zA-Z])+)+$"
```
2. Confirm the rule loads: `_has_redos_structure("^(([a-zA-Z])+)+$")` returns `False` (verifiable by running the three `_REDOS_SHAPES`/`_ALT_UNDER_REP` regexes against the string directly — none match), so `_validate_pattern` accepts it into `_user_patterns`.
3. Edit any file in the project whose content contains a long run of letters not ending in a way that satisfies the `$` anchor, e.g. a line of 40+ `a` characters followed by a non-letter character (`"a"*40 + "!"`).
4. `check_patterns()` calls `re.search("^(([a-zA-Z])+)+$", content)` [3](#0-2) , which exhibits exponential backtracking on this input, hanging the `PostToolUse` hook process and blocking further tool execution in the session.

```python
# Catastrophic backtracking: nested quantifiers, overlapping alternations
# under repetition, and wildcard groups under repetition. Static check, not a
# proof — catches the common shapes that hang the hook on every edit.
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")


def _has_redos_structure(regex: str) -> bool:
    """Heuristic catastrophic-backtracking check. Not a proof. Catches:
      - nested quantifiers ((a+)*, (a*b)+)
      - wildcard groups under repetition ((.*)*)
      - alternation under repetition where one branch is a prefix of another
        ((a|aa)*, (ab|a)*) — these overlap and explode on non-matching input.
    Does NOT flag non-overlapping alternation ((a|b)*) which is safe."""
    if any(p.search(regex) for p in _REDOS_SHAPES):
        return True
    for m in _ALT_UNDER_REP.finditer(regex):
        branches = [b for b in m.group(0).strip("()*+").split("|") if b]
        for i, a in enumerate(branches):
            for b in branches[i + 1:]:
                # If one branch is a literal prefix of another, the alternation
                # overlaps and the engine backtracks combinatorially.
                if a.startswith(b) or b.startswith(a):
                    return True
    return False
```
