### Title
Anyone can permanently grief WOM staking rewards in `WomUp` by spamming `getReward()` to truncate `rewardPerToken` accrual - (File: `wombat/WomUp.sol`)

### Summary
`WomUp.sol` implements a classic Synthetix-style streaming reward accumulator (`rewardRate`, `lastUpdateTime`, `rewardPerTokenStored`) identical in structure to Rubicon's `BathBuddy`. Because `getReward()` is callable by anyone at any time and its `updateReward` modifier unconditionally resets the global `lastUpdateTime` and recomputes `rewardPerTokenStored` using the elapsed time since the last call, an attacker can repeatedly call `getReward()` at very short intervals (e.g., every block) to force each accrual step to operate on a tiny time delta. Integer division in `rewardPerToken()` then truncates the per-call reward increment toward zero, permanently starving the global reward accumulator and thus all stakers' `earned()` values, indefinitely, at negligible cost.

### Finding Description
The `updateReward` modifier updates global state on every call regardless of the caller's stake: [1](#0-0) 

`rewardPerToken()` computes the accrued-per-token amount by multiplying `rewardRate` by the elapsed time since `lastUpdateTime` and dividing by `totalSupply()`: [2](#0-1) 

`getReward()` is a public, unauthenticated function that any address can invoke — it does not check that `msg.sender` has any stake — and it triggers `updateReward(msg.sender)`, which mutates the shared `lastUpdateTime` and `rewardPerTokenStored`: [3](#0-2) 

Because `(lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * 1e18 / totalSupply()` is computed and truncated (integer division) on every single call, calling `getReward()` at very short intervals (e.g., every L2 block) causes each increment to round down toward zero far more often than if the same elapsed time had accrued in one larger step. This under-accrues `rewardPerTokenStored` compared to the intended linear emission over `duration`, and — critically — this loss is irreversible: once `lastUpdateTime` is advanced, the "lost" fraction of that time window cannot be reclaimed by any subsequent call. This directly mirrors the `BathBuddy` root cause: `rewardsPerTokensStored[token].add(lastTimeRewardApplicable(token).sub(lastUpdateTime[token]).mul(rewardRates[token]).mul(1e18).div(totalSupply()))`.

### Impact Explanation
An attacker can call `WomUp.getReward()` from any address, with or without any staked balance in the contract, at every block on a low-fee L2. Each call finalizes the reward window since the previous call and, due to truncation on small time deltas, causes the effective rate at which `rewardPerTokenStored` increases to be suppressed toward zero. Since all users' `earned()` is derived from the same global `rewardPerTokenStored`, this results in an indefinite, protocol-wide freezing/loss of unclaimed MGP yield for every WOM staker in this contract, not just the attacker — with no cost-effective way for legitimate users to prevent it, satisfying the "permanent freezing/theft of unclaimed yield" bar.

### Likelihood Explanation
High. The `getReward()` function requires no special privileges, no minimum balance, and no approval — a single unprivileged EOA can trigger it. On L2s with sub-cent gas costs, sustaining a per-block call is economically trivial, exactly as described in the original `BathBuddy` report.

### Recommendation
Decouple the truncation-sensitive computation from being repeatedly reset at attacker-controlled short intervals: e.g., accumulate a higher-precision remainder instead of only storing the truncated `rewardPerTokenStored`, or rate-limit/aggregate `updateReward` recalculation (only allow the global reward-per-token update to advance at a minimum interval, independent of `getReward` calls by unrelated accounts). Alternatively, remove the ability for the `updateReward` modifier's global side effects to be triggered by an account with a zero balance / not the caller's own claim, and consider tracking rewards with a higher internal precision (e.g., 1e30) to minimize rounding loss per call.

### Proof of Concept
1. Deploy/initialize `WomUp` and call `initializeRewards()` to set `rewardRate`, `lastUpdateTime`, and `periodFinish` [4](#0-3) .
2. Have one or more legitimate users `stake()` WOM tokens [5](#0-4) .
3. From an attacker EOA (no stake required), repeatedly call `getReward()` every block/short interval for the duration of the reward period [3](#0-2) .
4. Because `rewardPerToken()` truncates `(elapsed * rewardRate * 1e18) / totalSupply()` on each of these many small-elapsed-time calls, observe that `rewardPerTokenStored` at `periodFinish` is significantly lower than it would be if `rewardPerToken()` were called only once at the end (elapsed = full `duration`) — demonstrating that legitimate stakers' `earned()` value is truncated toward zero and permanently unrecoverable, analogous to the original `BathBuddy` POC.

    function rewardPerToken() public view returns (uint256) {
        if (totalSupply() == 0) {
            return rewardPerTokenStored;
        }
        return
            rewardPerTokenStored + (
                (lastTimeRewardApplicable() - (lastUpdateTime)) * rewardRate * (1e18) / (totalSupply())
            );
    }
