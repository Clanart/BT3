## Analysis

The reported issue is a "missing limits on admin-settable parameters" bug class. The closest reachable analog in this codebase is the **`kip71.gastarget` governance parameter**, which is missing a "non-zero" format check that its sibling parameter `kip71.basefeedenominator` explicitly has, leading to a division-by-zero panic in every node's block-header verification path when the value is voted to `0`.

### Title
Missing lower-bound validation on `kip71.gastarget` governance parameter causes division-by-zero panic in `NextMagmaBlockBaseFee` - (File: `params/kip71_config.go`)

### Summary
The `kip71.gastarget` governance parameter has no format/bounds validation (`FormatChecker: noopFormatChecker`) unlike the structurally similar `kip71.basefeedenominator` parameter, which explicitly rejects zero (`return ok && v != 0`). Because `GasTarget` is later used as a divisor in the KIP-71 base-fee update formula, a governance vote that sets `kip71.gastarget` to `0` causes a division-by-zero panic during header verification on every node.

### Finding Description
The parameter registry defines `Kip71GasTarget` with a no-op checker that accepts any `uint64`, including zero: [1](#0-0) 

Contrast this with `Kip71BaseFeeDenominator`, which explicitly guards against zero: [2](#0-1) 

The consistency check performed when a vote is verified on-chain (`checkConsistency`) does not add any additional validation for `Kip71GasTarget` either — it is grouped with several parameters that are unconditionally accepted: [3](#0-2) 

`GasTarget` is then used directly as a divisor in `NextMagmaBlockBaseFee`, which computes the next block's base fee and is invoked from `VerifyMagmaHeader` during header validation: [4](#0-3) 

Note the defensive fallback that exists only for `BaseFeeDenominator == 0` (substituting `64`): [5](#0-4) 

No equivalent fallback exists for `GasTarget`. When `GasTarget == 0` and `parentGasUsed > 0` (the overwhelmingly common case), execution enters the `parentGasUsed > gasTarget` branch and divides by `gasTarget` (`y := x.Div(x, new(big.Int).SetUint64(gasTarget))`), which panics on division by zero in Go's `big.Int` package.

`VerifyMagmaHeader` calls this function to validate the `baseFee` field of every incoming header once Magma is active: [6](#0-5) 

### Impact Explanation
Because `NextMagmaBlockBaseFee` is invoked during header verification on every full/consensus node, a governance vote (malicious or accidental) that sets `kip71.gastarget = 0` causes all nodes to panic while verifying the very next block with non-zero gas usage. This is a chain-halting/node-crash condition affecting the entire network, not just a value bounded to a single actor's funds — matching the "Add Variable Limits to Admin/Governance Functions" bug class from the source report, where a trusted-but-unbounded setter can be pushed to a value that damages the system.

### Likelihood Explanation
Governance votes such as `kip71.gastarget` are cast by council members/proposers and take effect network-wide once accepted in an epoch's `header.Governance`. As with the original report's premise, the admin/governance role is trusted but not infallible — the same trust model that motivated bounding `kip71.basefeedenominator` (which does have a `!= 0` check) was not applied consistently to `kip71.gastarget`, despite both being divisors in the same formula. A single mistaken or malicious vote is sufficient to trigger the panic on the very next block that uses non-zero gas.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects zero (mirroring `Kip71BaseFeeDenominator`'s `v != 0` check), and/or add a defensive fallback inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` analogous to the existing `BaseFeeDenominator == 0` fallback, so that `GasTarget == 0` cannot reach the division operations.

### Proof of Concept
1. Council votes `kip71.gastarget = 0` via `gov.Vote`; the vote is accepted because `noopFormatChecker` allows any `uint64` and `checkConsistency` performs no additional validation for `Kip71GasTarget` (`kaiax/gov/headergov/impl/header.go` lines 213-220).
2. The vote is included in the epoch's governance data and becomes effective in the `ParamSet` for subsequent blocks.
3. On the next block where `parentHeaderGasUsed > 0`, any node calling `VerifyMagmaHeader` → `NextMagmaBlockBaseFee` (`params/kip71_config.go`) executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0`, causing a runtime panic and crashing the node's block-processing routine.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
