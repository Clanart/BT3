### Title
Instant, non-vested reward distribution in `BaseRewardPool` allows deposit/withdraw sniping of undistributed rewards - (File: `rewards/BaseRewardPool.sol`)

### Summary
`BaseRewardPool._provisionReward` (invoked via `queueNewRewards`) applies newly queued rewards to `rewardPerTokenStored` **instantly and in full** the moment they are provisioned, rather than streaming them over time. Any account whose stake is registered at the moment the reward is queued is immediately entitled to a full pro-rata share, regardless of how long they have actually been staked. This mirrors the `TokenisableRange` bug class: a "deposit → liquidity/fee event → withdraw" sequence lets a user capture value that should have accrued to long-term participants, without bearing meaningful economic exposure.

### Finding Description
`_provisionReward` updates `rewardInfo.rewardPerTokenStored` in one shot based on `this.totalStaked()` at the time of the call: [1](#0-0) 

`earned()` computes a user's share purely from their current `balanceOf` (read live from `MasterMagpie.stakingInfo`) multiplied by the delta between the global `rewardPerTokenStored` and the user's last-paid checkpoint: [2](#0-1) 

There is no time-weighting, vesting duration, or minimum staking period — unlike typical `Synthetix`-style reward pools that stream rewards linearly over a `DURATION` window. Because `MasterMagpie.deposit`/`withdraw` update `user.amount`/`user.available` synchronously and pay out via `_harvestBaseRewarder` on every state change (see `_deposit`/`_withdraw`/`_harvestAndUnstake`): [3](#0-2) 

a user can:
1. Observe (from the mempool) or predict an imminent `queueNewRewards` call on a given `BaseRewardPool` (rewards routed from `WombatStaking._sendRewards`/harvest flows, `feeInfo.to` targets, etc. — see `wombat/WombatStaking.sol:721-771` for how harvested WOM/bribe rewards are queued into reward pools).
2. Deposit a large stake into that pool's underlying staking token immediately before the reward-queuing transaction lands (front-run it), inflating `totalStaked()` at that exact moment is not even necessary — simply being staked when `rewardPerTokenStored` jumps is sufficient to be entitled to a full share.
3. Immediately call `withdraw`/`getReward` afterward to claim the harvested share and exit, having held the position for effectively zero economic time or risk.

This directly parallels the audit finding's core defect: value that should be distributed proportionally to time-weighted contribution is instead distributed based on an instantaneous balance snapshot, enabling a deposit/withdraw sandwich to disproportionately capture undistributed value.

### Impact Explanation
An attacker can extract a disproportionate share of periodically-harvested WOM/MGP/bribe rewards relative to their actual time-weighted contribution, diluting genuine long-term stakers' yield. This is a theft of unclaimed yield belonging to other users — reachable purely from an ordinary wallet's transactions (deposit/withdraw calls plus timing against public harvest/queue transactions), with no privileged role required.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to time a large deposit around a `queueNewRewards` call, which happens periodically whenever `WombatStaking` or bribe-distribution flows push harvested rewards into a pool. Since these harvest/queue calls are typically triggered on a schedule or by third-party keepers/bots and are visible in the mempool, an attacker with sufficient capital (or a flash loan, if the staking token can be flash-borrowed) can reliably front-run them. The absence of any minimum holding period or linear-vesting mechanism makes this exploitable whenever queued reward amounts are large relative to `totalStaked()`.

### Recommendation
Stream newly queued rewards linearly over a fixed duration (e.g., a `rewardRate`/`periodFinish` model as used in `Synthetix`-style reward pools) instead of applying the entire `_amountReward` to `rewardPerTokenStored` in a single step. This removes the incentive to snipe deposits immediately before a `queueNewRewards` call, since a user's exposure window would then determine their actual share of the emission.

### Proof of Concept
Conceptual sequence exploiting `rewards/BaseRewardPool.sol:297-320` together with `rewards/MasterMagpie.sol:481-534`:

1. Attacker monitors mempool for a pending `queueNewRewards(amountReward, rewardToken)` call on a target `BaseRewardPool` (routed e.g. from `WombatStaking`'s harvest/fee-distribution logic).
2. Attacker submits `MasterMagpie.deposit(stakingToken, largeAmount)` with higher gas / same block, landing just before the `queueNewRewards` transaction.
3. `_provisionReward` executes, and because `totalStaked()` now includes the attacker's `largeAmount`, `rewardPerTokenStored` increases; the attacker's `balanceOf` immediately entitles them to a full pro-rata cut of `amountReward` (see `earned()` at lines 173-185).
4. Attacker calls `MasterMagpie.withdraw(stakingToken, largeAmount)`, which internally calls `_harvestAndUnstake` → `_harvestBaseRewarder` → `BaseRewardPool.getReward`, paying out the attacker's captured share, then returns the principal.
5. Net effect: attacker earns a slice of the newly queued rewards without any real staking duration/risk, diluting the amount available to genuine long-term stakers.

Note: I was unable to fully trace which specific external call sites trigger `queueNewRewards` on a predictable/public cadence (e.g., whether `WombatStaking`'s harvest function is permissionlessly callable by any wallet) due to truncated visibility into `wombat/WombatStaking.sol`; a full session with file access would be needed to confirm the exact front-runnable entry point, though the reward-math vulnerability in `BaseRewardPool` itself is confirmed directly from the code shown above.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
```

```text
        updatePool(_stakingToken);

        PoolInfo storage pool = tokenToPoolInfo[_stakingToken];
        UserInfo storage user = userInfo[_stakingToken][_account];

        }
        user.rewardDebt = (user.amount * pool.accMGPPerShare) / 1e12;

        if (_amount > 0)
            if (!_isVlmgp)
                emit Deposit(_account, _stakingToken, _amount);
            else
                emit DepositNotAvailable(_account, _stakingToken, _amount);
    }

    /// @notice internal function to deal with withdraw staking token
    function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);

        if (!_isVlMgp)
            IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
        emit Withdraw(_account, _stakingToken, _amount);
    }

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
```
