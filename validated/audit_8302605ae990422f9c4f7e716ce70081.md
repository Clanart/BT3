### Title
`update_finalized_payouts` commits an unauthenticated `operator_xonly_pk` from a malleable OP_RETURN output, letting a non-signing party dictate (or nullify) payout attribution via a mempool-race - ([File: core/src/verifier.rs])

### Summary
The Payout transaction's OP_RETURN output (carrying `operator_xonly_pk`) is not covered by the user's `SinglePlusAnyoneCanPay` signature, so anyone who observes a broadcast Payout tx can rebuild a conflicting, still-validly-signed transaction with an arbitrary OP_RETURN and win the confirmation race. `update_finalized_payouts` then blindly attributes the withdrawal to whatever pubkey appears in whichever transaction actually confirms.

### Finding Description
The claimed binding is: `withdrawals.payout_payer_operator_xonly_pk` for index `i` == the xonly public key of the party whose capital appears in output 0 of the transaction that legitimately fronted withdrawal `i` through the intended flow.

`create_payout_txhandler` builds the Payout tx with input 0 (user's withdrawal UTXO, KeySpend) signed by the user, output 0 (user payout) and an OP_RETURN output containing `operator_xonly_pk` [1](#0-0) . The user's signature is required to be exactly `TapSighashType::SinglePlusAnyoneCanPay`, enforced both when the operator validates it in `Operator::withdraw` and when parsing the gRPC request [2](#0-1) [3](#0-2) . `SinglePlusAnyoneCanPay` only commits input 0 and output 0 (`Prevouts::One`) [4](#0-3)  - it does NOT cover the anchor output or the OP_RETURN output, and it explicitly allows arbitrary additional inputs (`AnyoneCanPay`).

Chain-side attribution is then computed purely from whichever transaction actually spends the tracked `withdrawal_utxo_txid/vout` (recorded from the Citrea withdrawal event) [5](#0-4) , with no check on who broadcast it or whether it matches a specific operator's own signed attempt. `update_finalized_payouts` reads the OP_RETURN of the confirmed tx and writes it verbatim to `payout_payer_operator_xonly_pk` [6](#0-5) , and `update_payout_txs_and_payer_operator_xonly_pk` performs an unconditional last-write-wins UPDATE keyed by `idx` [7](#0-6) .

Exploit flow: attacker sniffs the honest operator's first Payout broadcast from the mempool, extracts the witness (valid S+AP signature over input 0 + output 0 only), constructs a new transaction reusing that exact input 0/output 0, but funds the real payout amount from their own wallet inputs (unsigned by the operator, so freely attacker-controlled) and replaces the OP_RETURN with an arbitrary xonly pubkey. Because the signature does not cover the additional inputs or the OP_RETURN output, this new transaction is fully valid and spends the same withdrawal UTXO. If fee-bumped to confirm first, the honest operator's original transaction becomes an unconfirmable double-spend, and `update_finalized_payouts` permanently commits the attacker-chosen pubkey for that withdrawal index. Neither `is_kickoff_malicious` (verifier.rs:1857) nor any other guard checks that the recorded pubkey belongs to a registered operator for that specific deposit or that it corresponds to whoever actually funded output 0 with their own tracked collateral - it only compares the DB value to whatever the kickoff-sender claims.

### Impact Explanation
Two concrete outcomes, both within the Critical category:
1. If the attacker records an arbitrary/unregistered pubkey, no legitimate operator can ever submit a matching Kickoff for that withdrawal index (kickoff senders can only present their own registered `operator_xonly_pk`), so the corresponding 10 BTC in the deposit's MoveToVault UTXO becomes permanently unreimbursable/frozen - "a move-to-vault UTXO permanently frozen."
2. If the attacker records a real, registered operator's pubkey (one who never touched this withdrawal), that operator's own `PayoutCheckerTask` (`get_first_unhandled_payout_by_operator_xonly_pk`) will pick it up as "its" unhandled payout and drive `handle_finalized_payout`/kickoff/Reimburse for a withdrawal it never funded - "an operator reimbursed for a payout it never funded," while the honest operator who actually intended to front it is permanently blocked from ever being credited for this withdrawal index (its own real broadcast is a rejected double-spend).

This is repeatable per withdrawal/per deposit as long as an attacker can observe an operator's unconfirmed Payout tx and outbid its confirmation.

### Likelihood Explanation
The attacker must front real capital equal to the withdrawal's output amount (near the full bridge amount) to keep output 0 valid, since it is signature-committed - this is not a "zero-cost" attack as characterized in the prompt, but it is a real and fully unauthenticated mechanism: no collateral, registration, or verifier participation is required to determine attribution, only capital and a faster/cheaper-fee competing broadcast. It requires no privileged role, only mempool visibility and the ability to broadcast Bitcoin transactions and pay fees, matching the stated attacker capabilities. It is deterministically reproducible in a regtest/test harness by racing two spends of the same withdrawal UTXO.

### Recommendation
Bind the payer attribution cryptographically rather than trusting an unauthenticated OP_RETURN: e.g., require the OP_RETURN output (and/or the funding inputs) to be covered by a signature tied to the claimed operator's key, or otherwise verify at `update_finalized_payouts` time that the funding inputs of the confirmed payout tx are provably controlled by the operator whose xonly pk appears in the OP_RETURN (e.g., by checking that the additional inputs' signatures/ownership match a registered operator for this deposit) before writing `payout_payer_operator_xonly_pk`.

### Proof of Concept
```

```
Plan:
1. Set up a deposit with a registered honest operator `op_A` and fund a withdrawal (Citrea-side `withdraw`), producing `withdrawal_utxo` for index `i`.
2. Build the honest Payout tx via `create_payout_txhandler(withdrawal_utxo, output_txout, op_A_xonly_pk, user_sig)`, funded from `op_A`'s wallet, and note it's not yet broadcast.
3. Extract the witness of input 0 from the honest tx; build a second, attacker-funded transaction reusing input 0/output 0 exactly, with attacker's own additional funding inputs and an OP_RETURN containing an arbitrary/unregistered xonly pk `pk_X`.
4. Assert both `test_mempool_accept` succeed independently (proving both are validly signed spends of the same UTXO) - equality check BEFORE: `payout_payer_operator_xonly_pk` for idx `i` is NULL/unset for both.
5. Broadcast and mine only the attacker's transaction first (simulating fee-bump win); run `update_finalized_payouts`.
6. Assert AFTER: `db.get_payout_info_from_move_txid(...)` / `withdrawals.payout_payer_operator_xonly_pk` for idx `i` equals `pk_X`, not `op_A_xonly_pk` - i.e., the equality `payout_payer_operator_xonly_pk[i] == xonly_pk of whoever fronted through the intended flow` is broken.
7. Attempt to broadcast the honest `op_A` tx afterward and assert it is rejected as a double-spend (`test_mempool_accept` returns `allowed: false`), proving `op_A` can never be credited for this withdrawal.

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }
