### Title
Payout attribution trusts unauthenticated OP_RETURN bytes instead of who actually funded the payout - ([File: core/src/verifier.rs])

### Summary
`update_finalized_payouts` derives `payout_payer_operator_xonly_pk` solely from the first OP_RETURN output of whatever transaction spends the withdrawal UTXO, with no check that the named operator actually supplied the payout funds. Because the withdrawal UTXO's spending authorization comes from the withdrawer's own signature under `SIGHASH_SINGLE|ANYONECANPAY`, anyone (including the withdrawer) can complete and fund the payout transaction themselves while writing an arbitrary operator's `xonly_pk` into the unauthenticated OP_RETURN, causing that operator to be credited in the DB for a payout it never funded.

### Finding Description
The claimed binding, stated as an equality, is: `payout_payer_operator_xonly_pk[i]` == the xonly_pk of the operator whose signature actually authorized/funded the payout for withdrawal `i`.

Tracing `update_finalized_payouts`:
- `get_payout_txs_for_withdrawal_utxos` joins purely on the withdrawal UTXO bytes to find `payout_txid` [1](#0-0) .
- The matching transaction is pulled from the block, and `get_first_op_return_output` extracts the first OP_RETURN output; its bytes are parsed as an `XOnlyPublicKey` with no further validation [2](#0-1) .
- That value is written directly to `payout_txs_and_payer_operator_idx` and persisted via `update_payout_txs_and_payer_operator_xonly_pk` [3](#0-2) .

Critically, the withdrawal UTXO's key-spend input in the payout transaction is **not** authorized by an operator's signature. In `Operator::withdraw`, the input signature (`in_signature`) is verified against `user_xonly_pk`, derived from the withdrawal UTXO's own script pubkey — i.e. the withdrawer's own key, not the operator's [4](#0-3) . This signature uses `SinglePlusAnyoneCanPay`, which by design lets any third party add additional funding inputs/outputs and complete the broadcast — that's how any operator is meant to "front" the withdrawal. The OP_RETURN naming the funding operator is the *only* signal used to attribute who fronted the funds; the code comment even acknowledges the OP_RETURN can be missing or wrong ("...or the operator constructed the payout tx wrong") without any fallback verification [5](#0-4) .

Because OP_RETURN script data is unauthenticated, the withdrawal owner (who already holds a valid `SINGLE|ANYONECANPAY` signature for their own withdrawal, since they obtained it via `withdraw`) can construct and broadcast their own payout transaction: spend their withdrawal UTXO using their own pre-existing signature, add a funding input from their own wallet, add the required payout output, and add an OP_RETURN containing operator O's `xonly_pk` — a public value with no signature check. Nothing in `update_finalized_payouts`, `get_first_op_return_output`, or `parse_op_return_data` checks that the funding input(s) or any signature ties back to operator O.

### Impact Explanation
This breaks attribution matching the Critical category "an operator reimbursed for a payout it never funded." A malicious withdrawer can, at no cost beyond normal Bitcoin fees, cause the verifier network's database to record `payout_payer_operator_xonly_pk = O` for a payout the attacker funded personally. Downstream, `get_first_unhandled_payout_by_operator_xonly_pk`/`get_payout_info_from_move_txid` use this DB column to determine which operator is credited for having fronted a given withdrawal, which feeds the reimbursement/kickoff attribution path [6](#0-5) . This is repeatable per withdrawal and can name any operator arbitrarily, so the blast radius spans every withdrawal and every operator in the deployment.

### Likelihood Explanation
Preconditions are minimal and fully within the stated attacker capability set: the attacker must own a withdrawal (register it via Citrea `withdraw`, which any unprivileged user can do), and must be able to construct/broadcast a Bitcoin transaction spending their own UTXO with an OP_RETURN of their choosing — both explicitly listed as available to the unprivileged attacker. No signature forgery, key compromise, or majority hashrate is needed, since OP_RETURN is not covered by any signature check relevant to attribution. Cost is limited to Bitcoin transaction fees and the payout amount itself (which the attacker funds from their own wallet, same as an honest operator would).

### Recommendation
Do not derive payout attribution from OP_RETURN bytes alone. Attribution should require the named operator to prove it supplied the payout funds — e.g., verify the additional funding input(s) belong to (are spendable by) the claimed operator's registered wallet key, or require the operator to co-sign/commit to the payout transaction with a mechanism that cannot be replicated by the withdrawer (such as an operator-produced signature over the full transaction, not just an unauthenticated OP_RETURN). Alternately, require any reimbursement claim to independently re-verify that the operator's own signed input actually appears in the payout transaction before crediting `payout_payer_operator_xonly_pk`.

### Proof of Concept
```
cargo test -p clementine-core update_finalized_payouts_op_return_spoof --features test-utils
```
Test plan (regtest, no mainnet/live Citrea):
1. Set up a deposit and register a withdrawal via `Operator::withdraw`/Citrea mock so `withdrawal_utxo` for idx `i` is recorded, obtaining the withdrawer's own `SINGLE|ANYONECANPAY` signature over that input.
2. As the attacker (withdrawal owner), build a payout-shaped transaction: spend the withdrawal UTXO with the withdrawer's own signature, add a funding input from an attacker-controlled wallet (not operator O's), add the compliant payout output, and append an OP_RETURN containing honest operator O's `xonly_pk`.
3. Mine the transaction and run the block-sync path that invokes `update_finalized_payouts`.
4. Assert `payout_payer_operator_xonly_pk` for idx `i` in the DB equals O's `xonly_pk` (left side of binding), then assert none of O's registered wallet keys appear as a signer/funder of the transaction's non-withdrawal inputs (right side of binding) — the mismatch demonstrates the broken binding.
5. Call `get_first_unhandled_payout_by_operator_xonly_pk(O)` and assert it surfaces this payout as belonging to O, confirming downstream misattribution.
