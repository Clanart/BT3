### Title
Front-running bribe distribution via `vote()` to capture instant, un-time-weighted `rewardPerTokenStored` dilution - ([File: rewards/BaseRewardPoolV2.sol])

### Summary
`BribeRewardPool`/`BaseRewardPoolV2` distributes newly queued bribes instantly and non-time-weighted: `_provisionReward` divides the entire incoming reward by `totalStaked()` at the exact moment `queueNewRewards`/`castVotes` executes, with no streaming or checkpoint against time-at-stake. An unprivileged attacker who front-runs the reward-injecting transaction with `WombatBribeManager.vote(lp, +bigDelta)` increases `totalStaked` immediately before the reward is divided in, and because `stakeFor`'s `updateRewards` modifier snapshots `userRewardPerTokenPaid` at the pre-injection (lower) `rewardPerTokenStored`, the attacker's freshly added stake fully participates in the resulting `rewardPerTokenStored` jump — capturing reward that should accrue only to stakers who were present before the bribe was earned, diluting the share of pre-existing voters (the victim).

### Finding Description
The reward accounting in `rewards/BaseRewardPoolV2.sol` is not time-weighted:
- `_provisionReward` (`rewards/BaseRewardPoolV2.sol:290-314`) computes `rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked()` in a single atomic step whenever a bribe is queued, using whatever `totalStaked()` is at that exact instant.
- `stakeFor` (`rewards/BribeRewardPool.sol:57-67`), called from `WombatBribeManager.vote()` (`wombat/WombatBribeManager.sol:199`), is gated by the `updateRewards` modifier (`rewards/BaseRewardPoolV2.sol:107-120`), which sets `userRewardPerTokenPaid[token][_for] = rewardPerToken(token)` at the *current* (pre-injection) value before increasing `totalSupply`/`_balances`.
- `_earned` (`rewards/BaseRewardPoolV2.sol:316-321`) computes reward strictly as `balance * (rewardPerTokenStored - userRewardPerTokenPaid) / 1e18`, with no minimum holding duration.

Sequence: attacker observes an incoming reward-injection transaction (a `queueNewRewards` call reachable through the `castVotes`/`voteAndCast` harvesting path in `WombatBribeManager.sol:241-296`, or any manager `donateRewards`/`queueNewRewards` call) in the mempool, and front-runs it with `vote(lp, +bigDelta)`. This stakes `bigDelta` into the rewarder at the old (lower) `rewardPerTokenStored`. The reward transaction then executes, dividing the full bribe by the now-inflated `totalStaked` (old total + `bigDelta`), producing a smaller but still nonzero `rewardPerTokenStored` delta that the attacker's `bigDelta` balance fully participates in. The attacker's `earned()` for that delta is therefore nonzero despite having staked for zero economic time, and this reward is drawn from what would otherwise have gone entirely to the balances that were staked when the reward was actually earned. The attacker can then reduce/withdraw via `vote(lp, -bigDelta)` (`withdrawFor`, `claim=false`), which still snapshots `userRewards` via the same `updateRewards` modifier before balances change, then call `claimBribe`/`claimAllBribes` to receive the captured tokens.

The `previewBribes(_lp, _for)` function (`wombat/WombatBribeManager.sol:169-176`) itself is not a meaningful oracle for this attack: it only returns `allEarned(_for)`, i.e., rewards already computed/accrued against the current `rewardPerTokenStored`, not a signal of an *upcoming* reward injection. The real, exploitable primitive is not "front-running claimBribeFor to steal from a specific victim" (that call only forwards already-computed `earned()` to the victim, no diversion of funds is possible there — `_sendReward` in `getReward` always pays the `_account`'s own `userRewards`, `rewards/BaseRewardPoolV2.sol:218-235`), but rather "front-running the reward-provisioning transaction itself with a large vote to dilute/skim the instantaneous distribution," which is a generic JIT-staking issue affecting all stakers proportionally, not a targeted theft from one victim.

No `nonReentrant`, time-lock, or minimum-staking-duration check exists to prevent this; `vote()` only checks `userTotalVotedInVlmgp[msg.sender] <= getUserVotable(msg.sender)` (`wombat/WombatBribeManager.sol:218-219`), i.e., the attacker needs real, held vote-lock voting power (vlMGP/veWom-derived) equal to `bigDelta` — this is a capital constraint but does not prevent the mechanism.

### Impact Explanation
This is theft/dilution of unclaimed yield: capital that should accrue pro rata to bribe-eligible stakers who held their vote position when the bribe was earned is partially diverted to a same-block/front-run staker with zero economic staking duration. This matches "theft of unclaimed yield" impact class. The magnitude scales with bribe size and how large a vote delta the attacker can front-run with, bounded by the attacker's own vlMGP voting power.

### Likelihood Explanation
Requires: (1) attacker capable of front-running (any user with mempool visibility/MEV access — no privileged role needed); (2) attacker holding real, non-trivial vlMGP/veWom-derived voting power proportional to the desired `bigDelta` (this is the main capital constraint, since `vote()` enforces `getUserVotable`); (3) a sizeable, predictable, mempool-visible reward-queuing transaction to front-run (e.g., `castVotes`/`voteAndCast`, which are permissionless and can be called by anyone, making the timing of reward injection attacker-triggerable rather than purely opportunistic — an attacker could even call `voteAndCast` themselves in the same transaction sequence they control). This makes the attack realistically repeatable, though bounded by attacker's actual vote-lock balance.

### Recommendation
Replace the instantaneous, snapshot-based reward distribution in `_provisionReward` (`rewards/BaseRewardPoolV2.sol:290-314`) with a time-weighted/streamed model (e.g., Synthetix-style `rewardRate` + `lastUpdateTime`-based accrual over a duration), or impose a minimum staking/checkpoint delay before newly staked balances become eligible for a reward that was queued in the same block, so that `stakeFor` cannot retroactively participate in a reward injection it front-ran.

### Proof of Concept
Foundry test plan:
1. Deploy `BribeRewardPool` (via `BaseRewardPoolV2`) with a mock `stakingToken`/`operator` mimicking `WombatBribeManager`'s `vote()`→`stakeFor` path.
2. Seed pool with an existing staker `victim` holding balance `V` (via `stakeFor(victim, V)`), with `rewardPerTokenStored = 0`.
3. In the same block: (a) attacker calls `stakeFor(attacker, bigDelta)` (simulating `vote(lp, +bigDelta)`) — assert `userRewardPerTokenPaid[token][attacker] == 0`; (b) immediately call `queueNewRewards(R, token)`, which computes `rewardPerTokenStored = R * 1e18 / (V + bigDelta)`.
4. Assert `earned(attacker, token) == bigDelta * rewardPerTokenStored / 1e18 > 0`, proving the flash-voter captured a nonzero share of a reward it staked zero time for, and that `earned(victim, token) = V * rewardPerTokenStored / 1e18 < R` (i.e., victim's share was diluted below what it would have been had attacker not front-run: `R` if attacker were absent).

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =

        if (totalStaked() == 0) {

                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;

                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
