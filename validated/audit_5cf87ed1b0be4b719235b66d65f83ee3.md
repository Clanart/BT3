### Title
Unbacked reward accounting via `donateRewards` with fee-on-transfer/rebasing reward tokens - ([File: rewards/BaseRewardPool.sol / BaseRewardPoolV2.sol])

### Summary
`donateRewards` is a permissionless function that lets any address deposit rewards for any already-registered reward token by calling `_provisionReward`. `_provisionReward` increments `rewardInfo.rewardPerTokenStored` using the nominal `_amountReward` parameter, but only what is actually transferred via `safeTransferFrom` reflects the pool's real balance increase, so a fee-on-transfer or rebasing/deflationary reward token creates a permanent mismatch between claimable rewards and actual pool balance.

### Finding Description
`donateRewards` only checks `isRewardToken[_rewardToken]` before calling `_provisionReward`, with no `onlyManager` restriction, so it is callable by any unprivileged EOA/contract: [1](#0-0) 

Inside `_provisionReward`, the accounting update uses the caller-supplied `_amountReward` directly, not the actual amount received by the contract: [2](#0-1) 

If `_rewardToken` is a fee-on-transfer token (transfers less than the requested amount to the recipient) or a negative-rebasing token (balance can decrease after the transfer), `IERC20(_rewardToken).safeTransferFrom` moves less than `_amountReward` into the pool, yet `rewardInfo.rewardPerTokenStored` and `historicalRewards` are increased by the full nominal `_amountReward`. This breaks the backing invariant: `rewardPerTokenStored * totalStaked / 10**decimals` no longer corresponds to `IERC20(_rewardToken).balanceOf(pool)`. Because `getReward` pays out based on `userRewards`/`rewardPerTokenStored` via plain `safeTransfer` with no balance check, early claimants are paid in full while later claimants find the pool's real token balance exhausted, and their `getReward` calls will revert (transfer failure) — effectively freezing/losing their entitled, previously-registered yield.

No existing modifier stops this: `donateRewards` has no reentrancy guard or balance verification, and `updateReward`/`_updateFor` only recompute `rewardPerToken` from the (already corrupted) `rewardPerTokenStored`, they don't validate it against actual token balance.

### Impact Explanation
This causes real economic loss: theft/permanent freezing of unclaimed yield for stakers of the affected pool (last claimants cannot redeem their accrued reward share because the pool is drained by earlier claimants relative to the corrupted, inflated `rewardPerTokenStored`). This matches the Immunefi impact class "Theft or permanent freezing of unclaimed yield" / partial insolvency of the reward pool for a given reward token.

### Likelihood Explanation
The exploit itself requires zero privilege — any address can call `donateRewards` for any token already present in `isRewardToken`. The precondition is that a fee-on-transfer, deflationary, or negative-rebasing token must be one of the pool's registered reward tokens (added earlier via `queueNewRewards` by a manager, or set at construction). Given Magpie pools support arbitrary ERC20 reward tokens (e.g., partner/incentive tokens), and `donateRewards` was specifically designed to let anyone top up rewards for such tokens, this is a realistic configuration rather than a contrived one. Repeatability is high: every `donateRewards` call on such a token compounds the shortfall.

### Recommendation
In `_provisionReward`, measure the actual amount received by comparing `balanceOf(address(this))` before and after the `safeTransferFrom`, and use that delta (not the nominal `_amountReward`) for updating `historicalRewards`, `queuedRewards`, and `rewardPerTokenStored`.

### Proof of Concept
Foundry test plan:
1. Deploy `BaseRewardPool` with a mock staking token and a mock fee-on-transfer ERC20 (`FeeToken`) that burns/retains e.g. 10% on every `transferFrom`, registered as reward token (`isRewardToken[feeToken] == true`).
2. Have two stakers stake equal amounts of `stakingToken` via `masterMagpie` mocks so `totalStaked() > 0`.
3. Attacker (unprivileged) calls `pool.donateRewards(1000e18, feeToken)`; `FeeToken.transferFrom` only delivers 900e18 to the pool, but assert `rewardInfo.rewardPerTokenStored` was incremented as if 1000e18 arrived (i.e., `rewardPerTokenStored * totalStaked / 1e18 > feeToken.balanceOf(pool)`).
4. First staker calls `getReward`, successfully receiving their pro-rata share (500e18 nominal).
5. Second staker calls `getReward` and assert either the call reverts (ERC20 transfer failure due to insufficient balance) or receives less than their entitled 500e18, confirming pool balance (900e18) was insufficient to cover total nominal claims (1000e18), demonstrating loss/freezing of yield for the last claimant.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
```
