## Analog Analysis

The `oracle-timestamp-fresh` staleness gate in `mainnet/contracts/market/v0-4-market.clar` is the closest analog to the RocketDAO bug class ("does not handle a value greater than the current reference point, silently accepting instead of reverting"). It falls squarely in the permitted "staleness gating" / "monotonic per-feed timestamp" category.

### Title
Oracle Freshness Check Treats a Future `publish-time` as Zero Staleness, Allowing a Bad Timestamp to Permanently Poison the Monotonic `last-update` Cache - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`oracle-timestamp-fresh` is supposed to reject stale oracle prices and enforce monotonically increasing timestamps per feed. Instead of rejecting/reverting when the resolved price timestamp `ts` is greater than the current `stacks-block-time` (analogous to `_blockNumber > block.number` in the reported bug), it silently coerces `delta` to `u0`, i.e. treats an out-of-bounds future timestamp as perfectly fresh, and lets that value be written into the `last-update` map as the new baseline.

### Finding Description [1](#0-0) 

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

This is invoked from `price-resolve`, which then unconditionally advances the per-feed high-water mark whenever the (incorrectly validated) `timestamp` is greater than the previously stored one: [2](#0-1) 

Just like `RocketDAOProtocolProposal._propose()` failed to revert when `_blockNumber > block.number`, `oracle-timestamp-fresh` fails to revert (or otherwise correctly reject) when `ts > stacks-block-time`. Instead of computing a meaningful (negative-turned-positive, or explicitly rejected) delta for a timestamp that lies in the future relative to the chain's own clock, it forces `delta = 0`, which trivially satisfies `<= delta max-staleness` for any `max-staleness > 0` (asset registration is documented to require `max-staleness > 0`). The check therefore cannot distinguish "perfectly fresh" from "arbitrarily far in the future," and any such value is also written back into the `last-update` map since `timestamp > last-update-time` will hold: [3](#0-2) .

Once a future-dated `ts` is accepted and persisted as the feed's `last-update-time`, every subsequent legitimate price resolution for that asset — even ones carrying a correct, current `publish-time` — will fail the monotonic check `(>= ts prev)` in `oracle-timestamp-fresh`, because `prev` is now stuck ahead of real chain time. `price-resolve` will then hit `ERR-ORACLE-INVARIANT` for every call on that asset until real chain time (`stacks-block-time`) finally catches up to the erroneously stored future value.

### Impact Explanation
Because `price-resolve`/`price-multi-resolve` are the sole path by which the market contract obtains a valid price for any asset (used throughout borrow, withdraw, and liquidation health checks per `docs/market.md`/`docs/oracle.md`), poisoning a single feed's `last-update` entry with a future timestamp freezes all price-dependent operations (borrowing against, withdrawing, or liquidating positions collateralized/denominated in that asset) until the timestamp naturally elapses. This is a temporary but protocol-wide freeze of user funds tied to that asset (deposits/collateral become unusable, liquidations of unhealthy positions in that asset are blocked, risking additional bad debt) — matching the in-scope "temporary freezing of funds" impact class. The severity scales with how far in the future the accepted `ts` is (the longer the freeze).

### Likelihood Explanation
The trigger does not require compromising Pyth/DIA's cryptographic guarantees or the Zest DAO/registry — it only requires one oracle update whose `publish-time` is ahead of the Stacks chain's own `stacks-block-time` (e.g., relayer/publisher clock skew between Pythnet and the Stacks chain, or the ms→s conversion path for DIA `resolve-dia`). Note: neither `pyth-storage-v4`'s `write`/`write-batch-entry` nor `resolve-dia` enforce an *upper* bound on `publish-time` relative to `stacks-block-time` — they only check a lower staleness bound (`>= publish-time (+ (- latest-stacks-timestamp stale-price-threshold) STACKS_BLOCK_TIME)`), so nothing upstream prevents a future-dated value from reaching `price-resolve`. This makes the trigger condition plausible through normal operational drift, not just adversarial oracle compromise, which is what keeps the root cause inside Zest's own gating logic rather than "bad third-party data" per se.

### Recommendation
`oracle-timestamp-fresh` should not silently zero out `delta` when `ts > stacks-block-time`. Any oracle timestamp presented as later than the chain's own current time is definitionally invalid and should cause the function to return `false` (rejecting the update as invariant-violating) rather than being treated as the freshest possible price. Concretely:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)                 ;; reject future timestamps outright
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
This also prevents the future value from ever being written into `last-update`, eliminating the DoS on subsequent legitimate updates.

### Proof of Concept
1. An oracle update (Pyth or DIA) for asset `X` is relayed with `publish-time = T_future`, where `T_future > stacks-block-time` at inclusion (e.g., due to clock drift between Pythnet/DIA publishers and the Stacks chain — no upstream check in `pyth-storage-v4`/`resolve-dia` prevents this).
2. `resolve-price-feed` → `price-resolve` computes `timestamp = T_future`. `oracle-timestamp-fresh(T_future, prev, max-staleness)` computes `delta = u0` (because `T_future > stacks-block-time`), so `(<= delta max-staleness)` is `true`, and `(>= T_future prev)` is `true`. The update is accepted.
3. `price-resolve` executes `(if (> T_future last-update-time) (map-set last-update key T_future) false)`, storing `T_future` as the feed's new baseline: [4](#0-3) .
4. On every subsequent block until `stacks-block-time >= T_future`, any legitimate oracle update for asset `X` has `ts = current publish-time < T_future = prev`, failing `(>= ts prev)`; `oracle-timestamp-fresh` returns `false`, and `price-resolve` reverts with `ERR-ORACLE-INVARIANT`.
5. All market operations that need a fresh price for asset `X` (borrow, withdraw, liquidate) revert until real time passes `T_future`, freezing user funds tied to that asset for that duration.
