### Title
Position-indexed diff line-selection is trusted without content revalidation, allowing stale partial-commit selections to silently stage unreviewed content - (File: `app/src/models/diff/diff-selection.ts`, `app/src/lib/stores/app-store.ts`, `app/src/lib/git/apply.ts`)

### Summary
GitHub Desktop's partial-commit ("stage selected lines") feature tracks which lines a user has approved for commit purely by **positional index** within a diff (`DiffSelection.divergingLines`, keyed by `unifiedDiffStart + lineIndex`), not by line content. When the working directory changes between the moment the user visually reviews/selects lines and the moment the commit is actually staged, Desktop revalidates the selection only by checking whether the index is still *includeable* (`withSelectableLines`), never whether the underlying text at that index is still the content the user approved. The patch that is ultimately applied to the index (`applyPatchToIndex`) re-fetches a **fresh** diff from disk at commit time and reapplies the **stale, index-based** selection to it. If the diff’s line structure is preserved but content at a given index changes, the stale selection silently authorizes committing different content than what the user reviewed.

### Finding Description
The commit flow is:

1. User opens a file diff; Desktop computes hunks and line indices and the user makes a partial line selection via `DiffSelection.withRangeSelection`/`withLineSelection`, which only records index numbers in `divergingLines`: [1](#0-0) 

2. On every background/foreground status refresh, `updateChangesWorkingDirectoryDiff` re-diffs the file and reconciles the *old* selection against the *new* diff purely by recomputing which indices are still "includeable" lines (`selectableLines`) — it explicitly does **not** attempt to verify that a previously selected index still points at the same content: [2](#0-1) 

`withSelectableLines` only intersects `divergingLines` with the new `selectableLines` set — it removes entries whose index is no longer an includeable line, but keeps any index that is still includeable, regardless of whether the line's actual text changed: [3](#0-2) 

3. When the user clicks Commit, `_commitIncludedChanges` takes whatever `WorkingDirectoryFileChange` objects (and their `selection`) are currently cached in `repositoryStateCache` and passes them straight to `createCommit`/`stageFiles`: [4](#0-3) 

4. For files with a partial selection, `stageFiles` calls `applyPatchToIndex`, which **re-fetches the diff from disk again** (a third, independent diff computation, potentially different from what the user last saw) and builds a patch by asking `file.selection.isSelected(absoluteIndex)` for each line of this brand-new diff: [5](#0-4) [6](#0-5) 

The invariant that is broken: **"the set of lines flagged as selected in `DiffSelection` refers to the same content the user visually approved."** Nothing in the pipeline ties `divergingLines` to a content hash, blob OID, or line text — only to a numeric offset that is recomputed independently up to three times (initial load, background refresh, and the final `applyPatchToIndex` re-diff) against whatever bytes happen to be on disk at each point in time.

### Impact Explanation
If the working tree content changes between the user's review/selection and the final `applyPatchToIndex` re-diff — while preserving the diff's line/hunk shape (same number of added/removed/context lines at the same offsets) — Desktop will silently include content the user never reviewed or approved in the commit that gets created and potentially pushed. This is a "silent corruption of what the user commits or pushes," matching the explicitly valid impact category: unprivileged application logic causing the actual committed content to diverge from what was shown/approved in the UI, with no additional warning or re-confirmation shown to the user, undermining the entire "partial/hunk-selection" trust model.

### Likelihood Explanation
Exploitation requires an external actor/process to rewrite a tracked file's content on disk with the *same diff shape* at the exact moment between the user's selection and clicking Commit. Desktop already re-diffs on every filesystem-watcher-triggered refresh (`background-fetcher.ts` / periodic status polling calls `_loadStatus` → `updateChangedFiles` → `updateChangesWorkingDirectoryDiff`), so this window is not purely theoretical — it is triggered continuously during normal use. However, achieving the specific "same shape, different content" condition requires either a cooperating local tool (build system, formatter-on-save, LFS/clean-smudge filter) or a git hook triggered by a fetch/merge/checkout performed by Desktop against a malicious remote/config; I could not confirm from the indexed code whether Desktop invokes any hook capable of rewriting working-tree files autonomously between diff computations (this needs further investigation, e.g., of hook invocation and background-fetcher.ts, which is only partially indexed). This uncertainty is the main open question — the vulnerable code path (index-based selection with no content-identity check) is clearly present, but the realistic trigger for content mutation without user action needs confirmation with full file access.

### Recommendation
Bind `DiffSelection` entries to line content (e.g., a hash of the line text) rather than pure positional index, or, at minimum, re-validate at `applyPatchToIndex` time that each selected line's text in the freshly-fetched diff matches the text that was present when the user made the selection; if it does not match, drop the stale selection and force the affected file back to "no partial selection" (or refuse to commit and prompt the user to re-review), rather than silently staging whatever content occupies that index at commit time.

### Proof of Concept
Not independently reproducible from the indexed code alone — a full local checkout is required to confirm whether any Desktop-triggered git operation (fetch/merge/checkout/hook) or LFS/clean-smudge filter can rewrite a tracked file's bytes without user action while preserving diff shape, in order to demonstrate the end-to-end race. The core defect (stale index-based `DiffSelection` reapplied against an independently-refetched diff in `applyPatchToIndex`, with no content-identity check in `withSelectableLines`) is directly evidenced by the cited code paths above.

  public isSelected(lineIndex: number): boolean {
    const lineIsDivergent =
      !!this.divergingLines && this.divergingLines.has(lineIndex)

    if (this.defaultSelectionType === DiffSelectionType.All) {
      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
    } else {
      return assertNever(
        this.defaultSelectionType,
        `Unknown base selection type ${this.defaultSelectionType}`
      )
    }
  }
