### Title
`vote()` never re-syncs `userTotalVotedInVlmgp` when a user's locked balance is reduced by starting/canceling a cooldown, letting cast votes and bribe-reward shares outlive the collateral that backs them - (File: wombat/WombatBribeManager.sol)

### Summary
`getUserVotable()` uses `IVLMGP(vlMGP).getUserTotalLocked(_user)`, which excludes any amount currently in a cooldown/unlock slot [1](#0-0) . The only place this ceiling is checked against `userTotalVotedInVlmgp[msg.sender]` is inside `vote()` itself, at the very end of the function [2](#0-1) . Because `startUnlock`/`cancelUnlock`/`unlock` are called directly on `VLMGP`, completely outside `WombatBribeManager`, a user can cast votes while fully locked, then move MGP into cooldown or fully unlock it, permanently leaving `userTotalVotedInVlmgp[user]` and the corresponding `userVotedForPoolInVlmgp` bribe-pool stake (`IBribeRewardPool.stakeFor`) unreconciled with the user's real locked balance.

### Finding Description
`vote()` performs per-pool accounting and stakes/withdraws shares in each pool's `IBribeRewardPool` based on caller-supplied deltas [3](#0-2) , then updates the aggregate `userTotalVotedInVlmgp[msg.sender]` and finally checks it against `getUserVotable(msg.sender)`:
```
if (userTotalVotedInVlmgp[msg.sender] > getUserVotable(msg.sender))
    revert NotEnoughVote();
``` [2](#0-1) 

This check only fires when `vote()` is called. `getUserVotable` is derived from `getUserTotalLocked`, which per `IVLMGP`/`UserUnlocking` semantics excludes amounts already committed to an unlock cooldown slot [4](#0-3) . The locker's `startUnlock`, `cancelUnlock`, and `unlock` functions are called directly on `VLMGP` by the user, with no hook back into `WombatBribeManager` to revalidate or force-unvote the user's existing positions [5](#0-4) .

Exploit flow:
1. Attacker locks MGP in `VLMGP`, giving `getUserVotable(attacker) = full locked amount`.
2. Attacker calls `vote()` with deltas that consume the full votable amount across one or more active pools right after a large bribe lands, maximizing their share in each pool's `IBribeRewardPool` via `stakeFor` [6](#0-5) . This passes the check because, at that instant, `userTotalVotedInVlmgp == getUserVotable`.
3. Attacker calls `VLMGP.startUnlock(...)` (and eventually `unlock(...)`) directly, moving/withdrawing MGP out of the "locked" bucket. `getUserVotable(attacker)` drops (potentially to 0), but `userTotalVotedInVlmgp[attacker]` and the `IBribeRewardPool` stake are never touched, since nothing in `VLMGP` calls back into `WombatBribeManager.unvote()`.
4. `WombatBribeManager` has no keeper/hook that forces reconciliation; the stale, over-ceiling vote position persists indefinitely unless the attacker voluntarily calls `vote()`/`unvote()` again (which they simply avoid).
5. Result: the attacker keeps full pro-rata bribe-reward entitlement in `IBribeRewardPool` (and continues to weight `pool.totalVoteInVlmgp`, influencing `castVotes()`'s targeting of on-chain Wombat voting power) while holding zero or reduced locked collateral, diluting rewards owed to genuine, still-locked voters and skewing the pools' relative voting weights used by `castVotes()` [7](#0-6) .

The existing check only protects against exceeding the ceiling *at the moment of casting a new vote*; it never protects against the ceiling shrinking afterward through actions outside `WombatBribeManager`.

### Impact Explanation
This lets an unprivileged user extract bribe rewards and inflate a pool's `totalVoteInVlmgp` (and therefore Wombat governance vote weight allocated via `castVotes()`) without maintaining the corresponding locked MGP collateral. This matches "Critical - Governance voting result manipulation": bribe reward distribution and effective on-chain vote weighting no longer reflect real locked stake, and legitimate voters/bribe depositors are diluted.

### Likelihood Explanation
No special privileges are required — any EOA that can lock MGP in `VLMGP` and call the public `vote()`/`startUnlock()`/`unlock()` functions can perform this sequence. It requires only owning MGP to lock (capital is later recoverable via cooldown/unlock), making it fully repeatable and low-cost relative to the size of any bribe that has landed. The precondition stated in the question (large bribe just landed, no cast yet) maximizes the payoff but is not strictly required for the underlying accounting divergence to occur.

### Recommendation
Reconcile `userTotalVotedInVlmgp` (and the corresponding `IBribeRewardPool` stakes) whenever a user's `getUserTotalLocked` balance decreases — either by having `VLMGP.startUnlock`/`unlock` call back into `WombatBribeManager` to force a proportional `unvote`, or by making `getUserVotable` and the check in `vote()` re-validated lazily on every bribe-reward claim/harvest so stale over-ceiling positions cannot continue earning rewards. At minimum, add a public `syncVotes(address user)` that anyone can call to trim `userTotalVotedInVlmgp`/pool stakes down to the current `getUserVotable(user)`, and forbid `castVotes`/reward accrual from crediting positions above that ceiling.

### Proof of Concept
Foundry fork test plan against the deployed `WombatBribeManager`/`VLMGP`:
1. Fund attacker with MGP, call `VLMGP.lock(amount)`.
2. Seed a large bribe into a pool's `IBribeRewardPool` (via existing bribe-deposit path) before any `castVotes()`.
3. Attacker calls `vote(_lps, _deltas)` to fully allocate `amount` across pools; assert `userTotalVotedInVlmgp[attacker] == getUserVotable(attacker) == amount`.
4. Attacker calls `VLMGP.startUnlock(amount)` then, after cooldown, `VLMGP.unlock(slotIndex)`.
5. Assert `getUserVotable(attacker) == 0` while `userTotalVotedInVlmgp[attacker] == amount` (divergence confirmed) and `userVotedForPoolInVlmgp[attacker][pool]` / `IBribeRewardPool` stake unchanged.
6. Trigger bribe reward distribution/claim; assert attacker receives bribe rewards proportional to `amount` despite holding 0 locked MGP, and that this exceeds what an honest voter with the same current locked balance would receive — demonstrating dilution/manipulation.
