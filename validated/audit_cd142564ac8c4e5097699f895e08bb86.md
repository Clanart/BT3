## Analysis

I traced the external `transfer()`/2300-gas withdrawal-lock bug class to Hyperbridge's intent-settlement escrow logic in `IntentGatewayV2.withdraw`. Unlike `PayableProxyController`, Hyperbridge's contracts already replaced raw `transfer()` with low-level `.call{value}()` — but several of them still hard-`revert` the whole transaction on a failed native-ETH push to an attacker-influenced beneficiary, which reproduces the same underlying failure mode (a payment path that can be made permanently un-drainable) in a more damaging, atomic-batch form.

### Title
Atomic-revert native-ETH payout in `IntentGatewayV2.withdraw` permanently locks bundled ERC20 escrow and relayer fees when an order-creator-controlled beneficiary cannot accept ETH - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`, also present in `evm/src/apps/IntentGatewayV2.sol` and `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw` releases all escrowed assets for an order commitment — native ETH, one or more ERC20 tokens, and the transaction-fee token — inside a single loop, then reverts the entire call (`revert InsufficientNativeToken()`) if the native-ETH leg fails to reach `beneficiary`. Because the order's beneficiary is chosen at order-creation time by the (unprivileged) order creator, a malicious creator can set the beneficiary to a contract with no payable `receive()`/`fallback()` (or one that intentionally reverts). Every subsequent attempt to redeem or refund that escrow — including the bundled ERC20 tokens and transaction fees that have nothing to do with the poisoned ETH leg — reverts forever, permanently locking the funds of whichever counterparty (typically the honest solver who already delivered value on the destination chain) is entitled to that escrow.

The `beneficiary` value is derived from `body.beneficiary`, which is set from order/withdrawal data supplied at order-creation or fill time — i.e., attacker-influenced input, not a value the escrow-releasing party (the solver claiming payment, or the depositor being refunded) controls or can change after the fact. Once the order is created with a "poisoned" beneficiary (a non-payable/reverting contract), there is no alternate ERC20-only or pull-based withdrawal path in this contract to recover the co-bundled ERC20 tokens or fees — they are permanently entombed together with the un-deliverable ETH leg.

This mirrors the reported bug class exactly: a hard, non-recoverable payment path (previously Solidity's `transfer()`'s 2300-gas stipend; here, an unconditional revert on a low-level call failure) that an adversary can trivially trigger by controlling the recipient, rendering funds impossible to withdraw — except here the blast radius also swallows unrelated ERC20 and fee-token amounts bundled in the same escrow, whereas the original finding was scoped to a single ETH withdrawal.

### Impact Explanation
An unprivileged attacker (any user creating an intent/order) can designate an ETH-rejecting contract as the order's beneficiary. Any solver that fills the order on the destination chain and later attempts to redeem the source-chain escrow (`RedeemEscrow` via `onGetResponse`) — or the depositor attempting a refund (`RefundEscrow`) — finds the transaction permanently reverting. This causes real loss/lock of bridged assets and relayer/tx fees for an honest counterparty, satisfying the "bridged assets... must move exactly once and only to the rightful beneficiary" pivot and the "loss/lock of funds" impact bar, without requiring a malicious relayer, prover, or admin.

### Likelihood Explanation
High. Setting a beneficiary field to a deliberately hostile contract address is a normal, permissionless action available to any order creator; no privileged role, front-running, or off-chain collusion is needed. The failure is deterministic and reproducible every time the escrow-release path is invoked for that commitment.

### Recommendation
Decouple the native-ETH leg from the rest of the settlement: do not revert the entire `withdraw` call on a failed ETH push. Instead, either (a) credit the failed native-ETH amount to an internal pull-based balance for `beneficiary` (checks-effects-interactions + reentrancy guard) so the ERC20/fee legs still settle atomically, or (b) wrap unclaimable native ETH into the WETH-equivalent (as already done in `WrappedHyperFungibleToken.onAccept`, see `evm/tron/contracts/apps/IntentGatewayV2.sol` peer pattern in `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:309-324`) and deliver it as an ERC20 transfer instead of reverting.

### Proof of Concept
1. Deploy a `Poison` contract with no `receive()`/payable `fallback()` (or one that unconditionally reverts).
2. As an unprivileged user, create/submit an intent order whose escrow includes both native ETH and an ERC20 token, setting the order's beneficiary field to `Poison`.
3. A solver fills the order on the destination chain, delivering real value to the user.
4. The solver (or the depositor, on refund) triggers the ISMP `RedeemEscrow`/`RefundEscrow` flow that calls `IntentGatewayV2.withdraw`.
5. The native-ETH `beneficiary.call{value: amount}("")` at `evm/tron/contracts/apps/IntentGatewayV2.sol:694` fails against `Poison`, `withdraw` reverts with `InsufficientNativeToken`, and the entire settlement — including the unrelated ERC20 tokens and transaction fees bundled in the same commitment — never settles on any retry, permanently locking the solver's/depositor's entitled funds in the contract.
