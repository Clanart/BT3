### Title
Unauthenticated Plain-HTTP JSON-RPC Server Allows Unauthorized Bridge Transaction Queue Manipulation — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

### Summary
The `clementine-tx-sender` JSON-RPC server is started with `ServerBuilder::default()` — plain HTTP, no TLS, no authentication, no authorization. The configuration explicitly permits binding to `0.0.0.0`. Any network-reachable party can call `send_tx` and supply attacker-controlled `cancel_outpoints`, which the tx-sender will honour when the submitted transaction confirms on Bitcoin, silently removing bridge-critical transactions (challenge, disprove, kickoff-timeout) from the broadcast queue and breaking bridge liveness.

### Finding Description

`start_jsonrpc_server` in `crates/clementine-tx-sender/src/jsonrpc/server.rs` constructs the server as:

```rust
let server: Server = ServerBuilder::default()
    .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
    .build(bind_addr)
    .await
    ...
``` [1](#0-0) 

`ServerBuilder::default()` from `jsonrpsee` produces a plain HTTP/1.1 server. There is no `tls_config`, no API-key middleware, no IP allowlist, and no caller identity check of any kind. The two registered methods — `send_tx` and `send_citrea_tx` — are callable by any HTTP client that can reach the socket. [2](#0-1) 

The configuration layer explicitly allows binding to `0.0.0.0`:

```rust
if bind != "127.0.0.1" && bind != "0.0.0.0" {
    return Err(...);
}
``` [3](#0-2) 

The `send_tx` handler accepts a fully caller-controlled `InsertTryToSendParams`, including `cancel_outpoints` — outpoints that the tx-sender will mark as spent/cancelled in its DB when the submitted transaction confirms:

```
/// cancel_outpoints - Outpoints that should be marked invalid if this tx confirms
///                    (in addition to the tx's own inputs).
``` [4](#0-3) 

**Attack path:**

1. Operator deploys tx-sender with `TX_SENDER_JSONRPC_BIND=0.0.0.0` (explicitly supported).
2. Attacker observes on-chain bridge UTXOs (kickoff finalizer, challenge, disprove outpoints — all public).
3. Attacker crafts a valid Bitcoin transaction spending their own UTXOs and submits it via `send_tx` with `cancel_outpoints` set to one or more bridge-critical outpoints (e.g., the kickoff-finalizer UTXO that gates `WatchtowerChallengeTimeout`, or the challenge UTXO that gates `Disprove`).
4. Attacker's transaction confirms on Bitcoin.
5. The tx-sender marks the listed `cancel_outpoints` as cancelled in its DB, removing the corresponding bridge transactions from the broadcast queue.
6. Time-sensitive bridge transactions (challenge, disprove, kickoff-not-finalized timeout) are never broadcast; the operator's challenge window expires.

The `JsonRpcTxSenderClient` used by the bridge itself connects over plain `http://`:

```rust
let url = format!("http://{addr}");
let client = JsonRpcTxSenderClient::new(&url)...;
``` [5](#0-4) 

confirming no TLS is used on either side of this channel.

By contrast, the gRPC inter-actor layer enforces mTLS and the `OnlyAggregatorAndSelf` interceptor: [6](#0-5) 

The tx-sender JSON-RPC surface has no equivalent protection.

### Impact Explanation

The tx-sender is the sole mechanism by which the bridge broadcasts time-critical Bitcoin transactions: `WatchtowerChallengeTimeout`, `AssertTimeout`, `Disprove`, `KickoffNotFinalized`, `Challenge`, and `Payout`. [7](#0-6) 

If an attacker cancels the `Disprove` or `Challenge` transaction from the queue before the on-chain timelock expires, the operator's fraudulent withdrawal goes unchallenged. Verifiers lose their ability to slash the operator, and bridge funds or operator collateral are at risk. This satisfies the "unauthorized state transition in challenge/reimbursement/watchtower flow that breaks bridge liveness with material fund impact" criterion.

### Likelihood Explanation

- `0.0.0.0` binding is explicitly supported and documented in the config comment ("Restricted to 127.0.0.1 or 0.0.0.0").
- The default in `run.sh` is `127.0.0.1`, but Docker or cloud deployments that expose the port externally (or use host networking) are realistic.
- The attacker needs only: network access to the port, knowledge of bridge UTXO outpoints (all on-chain), and the ability to confirm a cheap Bitcoin transaction.
- No privileged keys or insider access are required.

### Recommendation

1. **Remove `0.0.0.0` as a valid bind address** for the JSON-RPC server, or enforce it only when an authentication mechanism is also configured.
2. **Add authentication** to the JSON-RPC server — at minimum a shared secret/API key checked in a middleware layer, or mutual TLS using the same CA infrastructure already present in the gRPC layer.
3. **Validate caller-supplied `cancel_outpoints`** against a whitelist of outpoints the caller is permitted to cancel, rather than accepting arbitrary outpoints.
4. **Restrict `cancel_outpoints` to inputs of the submitted transaction** unless the caller is an authenticated internal actor.

pub async fn start_jsonrpc_server(
    tx_sender_client: TxSenderClient,
    bind_addr: SocketAddr,
) -> Result<TxSenderJsonRpcServer, BridgeError> {
    let server: Server = ServerBuilder::default()
        .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
        .build(bind_addr)
        .await
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let local_addr = server
        .local_addr()
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let mut module = RpcModule::new(tx_sender_client.clone());
    module
        .register_async_method("send_tx", |params, client, _| async move {
            let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;

            let raw_tx = hex::decode(&req.signed_tx_hex).map_err(jsonrpc_err)?;
            let signed_tx: Transaction = consensus::deserialize(&raw_tx).map_err(jsonrpc_err)?;

            let mut dbtx = client.db.begin_transaction().await.map_err(jsonrpc_err)?;

            let try_to_send_id = client
                .insert_try_to_send(
                    &mut dbtx,
                    req.tx_metadata,
                    &signed_tx,
                    req.fee_paying_type,
                    req.rbf_signing_info,
                    &req.cancel_outpoints,
                    &req.cancel_txids,
                    &req.activate_txids,
                    &req.activate_outpoints,
                )
                .await
                .map_err(jsonrpc_err)?;

            client
                .db
                .commit_transaction(dbtx)
                .await
                .map_err(jsonrpc_err)?;

            Ok::<u32, ErrorObjectOwned>(try_to_send_id)
        })
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    // Citrea-specific RPCs.
    #[cfg(feature = "citrea")]
    {
        module
            .register_async_method("send_citrea_tx", |params, client, _| async move {
                let req: InsertCitreaRawTxParams = params.one().map_err(jsonrpc_err)?;

                let insertion_id = client
                    .send_citrea_tx(req.citrea_tx_request)
                    .await
                    .map_err(jsonrpc_err)?;

                Ok::<i64, ErrorObjectOwned>(insertion_id)
            })
            .map_err(|e| BridgeError::Eyre(e.into()))?;
    }

    let handle = server.start(module);

    Ok(TxSenderJsonRpcServer { handle, local_addr })
}
