### Title

Unauthenticated `ReceivedOutput` deserialization can register nonexistent or unspendable Bitcoin deposits - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary

`ReceivedOutput::read` accepts a scalar offset, a Bitcoin `TxOut`, and an `OutPoint` from untrusted bytes, then constructs an object documented as “a spendable output” without verifying that the output exists, that its script corresponds to the scanner’s key and offset, or that the outpoint refers to that output. [1](#0-0) [2](#0-1) 

The legitimate construction path binds outputs to a registered script through `Scanner`, but deserialization bypasses that authorization/binding boundary and allows an attacker to synthesize the same privileged object directly. [3](#0-2) [4](#0-3) 

### Finding Description

`Scanner::new` creates a mapping from the wallet’s Taproot script to the zero offset, while `Scanner::register_offset` adds mappings only after deriving the script for `key + offset * G`. [5](#0-4) [6](#0-5) 

`Scanner::scan_transaction` constructs `ReceivedOutput` only when an on-chain transaction output’s `script_pubkey` is present in that authenticated mapping. [7](#0-6) 

`ReceivedOutput::read`, however, merely parses `offset`, `output`, and `outpoint` from bytes and returns them as a spendable output. [8](#0-7) 

Because `ReceivedOutput` fields are private, this deserializer is the alternate constructor for attacker-supplied records. It does not receive or consult a `Scanner`, does not recompute `p2tr_script_buf(scanner.key + GENERATOR * offset)`, and does not compare the result with `output.script_pubkey`. [9](#0-8) [8](#0-7) 

Downstream, `SignableTransaction::new` trusts each supplied `ReceivedOutput`: it sums `input.output.value` as available funds, copies `input.offset` for signing, and spends `input.outpoint`. [10](#0-9) [11](#0-10) 

### Impact Explanation

An attacker who can feed bytes to `ReceivedOutput::read` can cause the wallet layer to report arbitrary Bitcoin value as received and available, including a nonexistent outpoint, an output with an unrelated script, or an output whose script does not match the claimed signing offset. [12](#0-11) 

The resulting transaction is not spendable on Bitcoin because either the referenced prevout does not exist or the witness signature will not authorize the actual prevout script. This produces funds reported received that are not spendable and can cause incorrect accounting, failed payouts, or repeated signing attempts against invalid inputs. [10](#0-9) [11](#0-10) 

### Likelihood Explanation

The attack requires only control over serialized bytes passed to the public `ReceivedOutput::read` API; it does not require a validator key, leaked secret, malicious Bitcoin node, or participation in threshold signing. [13](#0-12) 

The forged object then follows the same downstream API as an output legitimately produced by `Scanner::scan_transaction`, making the defect directly reachable wherever persisted, mirrored, imported, or otherwise untrusted output records are deserialized. [14](#0-13) [15](#0-14) 

### Recommendation

Bind deserialized outputs to the wallet context before treating them as spendable:

- Change `ReceivedOutput::read` to require the expected base `ProjectivePoint` or a `Scanner`.
- Reject offsets that were never registered with that `Scanner`.
- Recompute `p2tr_script_buf(scanner.key + GENERATOR * offset)` and require equality with `output.script_pubkey`.
- Do not expose a constructor or deserializer that creates a `ReceivedOutput` without proving the script/offset relationship.
- Where the record is consumed for spending, additionally verify that the claimed `OutPoint` exists on-chain and resolves to the same `TxOut`. [13](#0-12) [16](#0-15) 

### Proof of Concept

The following demonstrates the missing binding: the attacker supplies a syntactically valid offset, an arbitrary output, and a nonexistent outpoint. `read` accepts all three as a “spendable output” without any wallet-key or blockchain association.

```rust
use bitcoin::{
  absolute::LockTime,
  consensus::Encodable,
  hashes::Hash,
  Amount, OutPoint, ScriptBuf, TxOut, Txid,
};
use bitcoin_serai::wallet::ReceivedOutput;
use k256::Scalar;

fn forged_received_output() -> ReceivedOutput {
  let mut bytes = Vec::new();

  // Attacker-selected signing offset.
  bytes.extend(Scalar::ZERO.to_bytes());

  // Attacker-selected claimed value/script. This need not be the script that
  // Scanner would derive for the wallet key and offset.
  TxOut {
    value: Amount::from_sat(1_000_000_000),
    script_pubkey: ScriptBuf::new(),
  }
  .consensus_encode(&mut bytes)
  .unwrap();

  // Attacker-selected nonexistent prevout.
  OutPoint {
    txid: Txid::from_byte_array([0; 32]),
    vout: 0,
  }
  .consensus_encode(&mut bytes)
  .unwrap();

  let output = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();

  // The forged object reports attacker-chosen funds as received.
  assert_eq!(output.value(), 1_000_000_000);
  assert_eq!(output.outpoint().vout, 0);

  output
}
```

`SignableTransaction::new` then consumes this forged object’s value, offset, and outpoint exactly as it would for an output produced by `Scanner::scan_transaction`. [10](#0-9)
