## Title
Single shared `maxOracleAge` across heterogeneous Chainlink feeds enables stale-price exploitation and fund loss in `SimplexPaymaster` - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-4337 gas fees off two Chainlink feeds — a shared `nativeOracle` (e.g. ETH/USD, BNB/USD) and a per-token `tokenOracle` (e.g. USDC/USD, USDT/USD) — but validates staleness for **all** of them against one single governance-configured `maxOracleAge` value. Chainlink heartbeats differ significantly per feed/chain (the contract's own comment states "BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h"), so a `maxOracleAge` sized to tolerate the slowest registered feed will silently accept badly stale prices from faster-updating feeds, most critically the `nativeOracle` used to price every transaction.

### Finding Description
`Params.maxOracleAge` is a single `uint256` stored once (`maxOracleAge` state var, [1](#0-0) ) and applied uniformly to both the native asset oracle and every registered token oracle inside `_getOraclePrice`: [2](#0-1) 

Both `_tokenPrice` (used in every `_fetchDetails` call during gas charging) and `swapAndDeposit` call `_getOraclePrice` with the *same* `maxOracleAge` for the `nativeOracle` and the token oracle: [3](#0-2) 

The deployment script explicitly documents the root cause: `maxOracleAge` is deliberately widened to tolerate the *slowest* registered stablecoin heartbeat (24h+buffer), which then also governs the `nativeOracle` staleness check: [4](#0-3) 

This is the exact analog of the external report's Chainlink heartbeat bug: one staleness parameter is reused across price feeds whose actual update cadences differ materially. Here it's cross-feed (native vs. stablecoin) rather than cross-chain, but the broken invariant is identical — the staleness bound is decoupled from each oracle's real heartbeat.

### Impact Explanation
Because `maxOracleAge` is calibrated to the slowest feed (e.g. 25h to accommodate Ethereum/Base stablecoins), the `nativeOracle` (which typically updates far more often, e.g. hourly/0.5% deviation) can go up to ~25 hours without a price update and still be accepted as valid by `_getOraclePrice`. Any unprivileged ERC-4337 user submitting a UserOp through `_fetchDetails`/`_validatePaymasterUserOp` gets gas priced off this stale `nativeUsd` value via `_tokenPrice`: [5](#0-4) 

If the true native asset price has moved significantly during that stale window (a routine occurrence over 25 hours), every UserOp processed in that window is priced against an incorrect exchange rate — the paymaster either overcharges users' escrowed stablecoin allowances or, more critically, undercharges relative to the real gas cost it pays in native currency, systematically draining the paymaster's EntryPoint deposit/treasury funds with no compromised relayer, prover, or admin required. This is a public-entrypoint fund-loss/wrong-amount issue, not merely a DoS.

### Likelihood Explanation
High. No privileged action is needed — any address can submit a standard ERC-4337 UserOp through the EntryPoint at any time the native oracle happens to be stale-but-within-bound (which is the routine, expected steady state given the deliberately widened `maxOracleAge`). The existing guard (`StaleOraclePrice` revert) does not stop this because it is calibrated for the *worst-case* stablecoin heartbeat, not the native oracle's actual, much shorter heartbeat — so it never triggers for a genuinely stale native price within that window.

### Recommendation
Track staleness bounds per-oracle instead of one global `maxOracleAge`. Add a `maxOracleAge` field to `TokenConfig` (and a dedicated bound for `nativeOracle`), validated against each feed's actual heartbeat at registration/update time, and check `_getOraclePrice` against the oracle-specific bound rather than the single shared `Params.maxOracleAge`.

### Proof of Concept
1. Governance deploys/initializes `SimplexPaymaster` with `nativeOracle = ETH/USD` (heartbeat ~1h) and `maxOracleAge = 90_000` (25h) sized for stablecoin feeds, per `evm/script/DeploySimplexPaymaster.s.sol` lines 18-20.
2. `ETH/USD` on-chain feed does not update for ~20 hours (well within Chainlink's normal operational variance, and well under `maxOracleAge`), while the real ETH price moves materially in that window.
3. Any user submits a UserOp with `paymasterData` referencing a registered stablecoin token; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(nativeOracle, ...)` at [6](#0-5)  passes because `block.timestamp - updatedAt (~20h) < maxOracleAge (25h)`.
4. Gas is priced using the stale `nativeUsd` value; the paymaster settles the UserOp at the wrong stablecoin/native exchange rate, causing systematic under/overcharging with no privileged actor involved.

    function _fetchDetails(
        PackedUserOperation calldata userOp,
        bytes32 /* userOpHash */
    ) internal view override returns (uint256 validationData, IERC20 token, uint256 tokenPrice) {
        bytes calldata data = userOp.paymasterData();
        if (data.length < 21) revert InvalidPaymasterData(data.length);

        uint8 mode = uint8(data[0]);
        if (mode > 0x01) revert InvalidMode(mode);

        address tokenAddr = address(bytes20(data[1:21]));

        TokenConfig memory cfg = tokenConfigs[tokenAddr];
        if (address(cfg.tokenOracle) == address(0)) revert TokenNotRegistered(tokenAddr);
        if (!cfg.active) revert TokenNotActive(tokenAddr);

        tokenPrice = _tokenPrice(cfg);
        token = IERC20(tokenAddr);
        validationData = 0; // no time-range restriction

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer, , uint256 updatedAt, ) = oracle.latestRoundData();
