### Title

Malformed per-input FROST preprocess/share vectors can panic Bitcoin transaction signing - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary

`TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` trust every participant-supplied `Vec` to contain exactly one item per transaction input, but neither checks that length before indexing or removing items.

### Finding Description

The Bitcoin transaction signing API represents each participant’s preprocesses and signature shares as a `Vec`, with each element corresponding to a transaction input. [1](#0-0) 

When signing, the implementation iterates over `0 .. self.sigs.len()` and directly indexes `commitments[c]` for every participant. [2](#0-1) 

If a participant provides fewer preprocesses than the transaction has inputs, this indexing panics; extra entries are not explicitly rejected either. [2](#0-1) 

The same issue exists during completion: every input’s signature machine removes the first element from each participant’s share vector without first checking that the vector is nonempty or has exactly one share per input. [3](#0-2) 

`read_preprocess` and `read_share` deserialize the expected number of elements for the local machine, but callers can construct the public `HashMap<Participant, Vec<_>>` inputs with malformed vector lengths. [4](#0-3) [5](#0-4) 

### Impact Explanation

A participant can submit a malformed preprocess or share collection that causes the local signing process to panic while completing a multi-input Bitcoin transaction. This can abort the signing attempt and, depending on caller panic handling, terminate the signer task or process. [6](#0-5) [7](#0-6) 

### Likelihood Explanation

The malformed state is directly reachable through `sign` and `complete`, which accept participant-controlled preprocess/share maps. [8](#0-7) [9](#0-8) 

The issue is easiest to trigger with a transaction having multiple inputs: a peer can provide one preprocess or share where two or more are required. [10](#0-9) 

### Recommendation

Before indexing or draining participant vectors, verify `preprocesses.len() == self.sigs.len()` and `shares.len() == self.sigs.len()` for each participant.

The check should be performed in both `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete`, returning an attributable `FrostError` such as `InvalidPreprocess` or `InvalidShare` rather than panicking. [11](#0-10) [3](#0-2) 

### Proof of Concept

Conceptually:

```rust
// Build a transaction with two inputs, yielding two Schnorr machines.
let (machine, our_preprocesses) = transaction_machine.preprocess(&mut rng);
assert_eq!(our_preprocesses.len(), 2);

// A remote participant supplies only one preprocess.
let mut remote = HashMap::new();
remote.insert(remote_participant, vec![their_first_preprocess]);

// Panics while processing input 1 at commitments[c].
let _ = machine.sign(remote, b"");
```

Likewise, a remote participant can provide an empty or truncated `Vec<SignatureShare>` to `complete`, causing `shares.remove(0)` to panic. [12](#0-11) [13](#0-12)

      panic!("message was passed to the TransactionSignMachine when it generates its own");
    }

    let commitments = (0 .. self.sigs.len())
      .map(|c| {
        commitments
          .iter()
          .map(|(l, commitments)| (*l, commitments[c].clone()))
          .collect::<HashMap<_, _>>()
      })
      .collect::<Vec<_>>();

    let mut cache = SighashCache::new(&self.tx.tx);
    // Sign committing to all inputs
    let prevouts = Prevouts::All(&self.tx.prevouts);

    let mut shares = Vec::with_capacity(self.sigs.len());
    let sigs = self
      .sigs
      .drain(..)
      .enumerate()
      .map(|(i, sig)| {
        let (sig, share) = sig.sign(
          commitments[i].clone(),

            .as_ref(),
        )?;
        shares.push(share);
        Ok(sig)
      })
      .collect::<Result<_, _>>()?;

    Ok((TransactionSignatureMachine { tx: self.tx.tx, sigs }, shares))
