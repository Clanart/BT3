## Finding

The bug class here—performing a state-changing action based on an attacker-controllable identifier (`_taskId`) that is validated only for a *different* thing (ownership of the DCA), not for consistency with the ID actually used—maps to how `shopify_app`'s webhook processing pipeline separates "is this HMAC valid" from "which shop does this webhook belong to."

### Title
Cross-shop webhook forgery via unbound `X-Shopify-Shop-Domain` header - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`, `lib/shopify_app/controller_concerns/payload_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#verify_request` only checks that the raw POST body was HMAC-signed with the app's shared client secret; it never validates that the `X-Shopify-Shop-Domain` header used downstream to determine *which tenant* the webhook applies to is bound to that signed payload.

### Finding Description
`hmac_valid?` computes the HMAC purely over `request.raw_post` using `ShopifyApp.configuration.secret`/`old_secret`, which are single, app-wide secrets shared by every shop that has installed the app: [1](#0-0) 

`verify_request` in `WebhookVerification` gates only on this body HMAC, and `shop_domain` is a completely separate helper that just reads the caller-supplied header, with no cryptographic tie to the signed body: [2](#0-1) 

Because the secret is shared across all shops of the app (not per-shop), any shop that has legitimately installed the app can capture a genuinely-signed `(body, HMAC)` pair from its own real webhook traffic. The `X-Shopify-Shop-Domain` header is not part of what's signed, so that captured pair can be replayed to the same endpoint with the header changed to name a different, victim shop, and `hmac_valid?` will still return true.

This is directly documented as the intended integration pattern in this repo: the recommended custom controller passes the unvalidated `shop_domain` straight to job dispatch: [3](#0-2) 

The generated job templates then act on that attacker-influenced shop identity to make destructive changes, e.g. the uninstall job destroys the shop's local record by the supplied `shop_domain`: [4](#0-3) 

This is the same root cause as the DCA report: an authorization/ownership check is performed on one value (HMAC proves "some installer of this app produced this body"), while a *different*, unrelated value (`shop_domain` header identifying which tenant to act on) is used for the actual privileged operation, with no check that the two are consistent.

### Impact Explanation
A merchant who has legitimately installed the app (an "unrelated" but authenticated actor, not the victim) can forge a webhook POST naming any other shop domain in the header while reusing a validly-signed body/HMAC pair they possess from their own account. Depending on which job the topic routes to, this can destroy or redact another shop's locally stored session (`shop.destroy` in the uninstall job), or feed forged data into any custom per-shop webhook handler that trusts `shop_domain`. This is a cross-shop state-changing forgery, i.e., accepted forged signed request leading to cross-tenant impact.

### Likelihood Explanation
Likelihood is moderate to high in an app that follows the documented `WebhookVerification`/custom-controller pattern in `docs/shopify_app/webhooks.md`, since any shop that has installed the app can obtain a valid signed body (from its own real webhook deliveries) and the header is trivially attacker-controlled on a direct POST to the endpoint (Rails does not otherwise enforce a whitelist of source IPs for this route).

### Recommendation
- Short term: Do not rely on the raw `X-Shopify-Shop-Domain` header for authorization/tenant selection; instead derive the shop from data that is part of the signed payload, and where the gem-provided `ShopifyAPI::Webhooks::Registry`/`Request` abstraction is used, ensure it is always used instead of ad hoc header reads. Document that `shop_domain` from `WebhookVerification` is not itself proof that the payload belongs to that shop.
- Long term: Update `docs/shopify_app/webhooks.md`'s custom-controller example to warn against directly trusting `shop_domain`, and consider binding shop identity into the HMAC computation or requiring a secondary check (e.g., confirming an active `Shop` record and consistency between topic-specific payload contents and the claimed shop) before performing destructive actions like `shop.destroy`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and captures a genuine outbound webhook (e.g., `app/uninstalled`) with its raw body `B` and valid `X-Shopify-Hmac-Sha256: HMAC(B, shared_secret)`.
2. Attacker POSTs to the app's webhook endpoint with body `B`, the captured HMAC header, and `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` → `hmac_valid?(B)` succeeds because the secret is shared, not shop-specific.
4. The generated `AppUninstalledJob` (or any custom job following the documented pattern) receives `shop_domain: "victim-shop.myshopify.com"` and destroys/redacts the victim shop's stored session, even though the attacker has no relationship to that shop.

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
