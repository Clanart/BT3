### Title
Unvalidated `Participant` indexes cause a panic (crash) in PedPoP blame evaluation - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
`Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `enc_keys` / `commitments` HashMaps with the `decryptor`/`sender` participants supplied by the caller, without checking they are within `1 ..= n`. An out-of-range participant index causes a panic — the closest analog in Serai to the UPX "invalid memory access → application crash" class: crafted DKG/blame inputs crash the evaluating party. This is reachable through `AdditionalBlameMachine::blame` / `BlameMachine::blame`, which take attacker-chosen `sender`/`recipient` `Participant` values plus attacker-controlled `EncryptedMessage` bytes.

### Finding Description
`Participant::new` guarantees only non-zero; indexes `> n` are valid `Participant` values. In `decrypt_with_proof`, `self.enc_keys[&decryptor]` panics if `decryptor` was never registered ( [1](#0-0) ). Even when `decrypt_with_proof` returns `InvalidSignature` early (pop challenge fails), a `sender` outside `1 ..= n` still reaches `self.commitments[&sender]` once decryption succeeds — or is avoided only because the message is invalid. If the attacker crafts a valid `EncryptedMessage` (they know the per-message key they encrypted with), the PoP verifies, `enc_keys[&decryptor]` resolves for a legitimate `recipient`, and `blame_internal` then panics on `self.commitments[&sender]` [2](#0-1) . There is no bounds check on `sender`/`recipient` anywhere in `blame`, `blame_internal`, or `AdditionalBlameMachine::new` [3](#0-2) .

The public callers feed these values from untrusted input: `EncryptedMessage::read` parses the message bytes [4](#0-3) , and the processor's blame handler invokes `AdditionalBlameMachine::new(...).blame(accuser, accused, ...)` with `accuser`/`accused` taken from the incoming message and never range-checked against `params.n()` [5](#0-4) .

### Impact Explanation
A participant can submit a blame/accusation naming an out-of-range `sender` or `recipient` participant index. Any node that evaluates the accusation panics — equivalent to the crafted-Mach-O crash in the reference report. Beyond per-node DoS, crashing the blame-evaluating party can also be used to evade or disrupt the slashing/blame process for genuinely faulty DKG participants (the panic occurs before `blame_internal` returns a verdict).

### Likelihood Explanation
Any party able to get a `blame`/`VerifyBlame`-style request evaluated — i.e., a DKG participant or anyone able to submit such accusations through the host protocol — can trigger it deterministically by naming `Participant(n + 1)` (or any unregistered index) as `sender` while supplying a well-formed `EncryptedMessage`, or by naming an unregistered `recipient` when a blame proof is present. No secret knowledge is required for the `enc_keys[&decryptor]` path: providing `proof = Some(_)` with `decryptor` out of range panics regardless of message validity, since the map lookup precedes any check that could fail [6](#0-5) .

### Recommendation
Bounds-check `sender` and `recipient`/`decryptor` against the registered participant set (`self.enc_keys` / `self.commitments` keys, or `params.n()`) before indexing, returning a defined result (e.g., blame the party that supplied the invalid index, or an `InvalidParticipant` error) instead of panicking. Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `get(...).ok_or(...)`. Concretely, in `crypto/dkg/pedpop/src/encryption.rs` `decrypt_with_proof`, validate `decryptor` before the `enc_keys` lookup; in `crypto/dkg/pedpop/src/lib.rs` `blame_internal`, validate `sender`/`recipient` against `self.commitments` before use.

### Proof of Concept
Setup: run a PedPoP DKG with `n` participants to completion so an honest party holds a `BlameMachine` (or build `AdditionalBlameMachine::new(context, n, commitment_msgs)`).

```rust
// attacker: any party whose accusation gets evaluated
let attacker = Participant::new(1).unwrap();          // a real participant
let out_of_range = Participant::new(n + 1).unwrap();  // valid Participant, > n

// Path A: unregistered decryptor -> panic at enc_keys[&decryptor]
// supply any EncryptedMessage plus Some(proof); the lookup precedes DLEq failure
machine.blame(attacker, out_of_range, msg, Some(proof)); // panics

// Path B: unregistered sender -> panic at commitments[&sender]
// craft EncryptedMessage with a PoP valid under `from = out_of_range`
// (attacker encrypts msg under recipient's enc_key and signs PoP for `out_of_range`)
machine.blame(out_of_range, recipient, crafted_msg, Some(valid_proof)); // panics
```

In `processor/src/key_gen.rs` (`CoordinatorMessage::VerifyBlame`), `accused`/`accuser` come straight from the message and are passed unchecked into `blame(...)` [5](#0-4) , so submitting an accusation with an index `> params.n()` crashes the evaluating processor — mirroring the upstream "crafted input → invalid memory access → crash" bug class.
