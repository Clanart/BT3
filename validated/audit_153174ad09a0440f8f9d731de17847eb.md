### Title
Attacker-controlled `n` causes quadratic Lagrange interpolation DoS during `ThresholdKeys::read` - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` trusts the serialized `n` participant count, parses `n` verification shares, and then constructs a threshold key using Lagrange interpolation. `ThresholdKeys::new` computes the group key by evaluating every participant `1..=t` over the same `t`-element participant set, making Lagrange interpolation quadratic in `t`. A serialized key package declaring `t = n = 65_535` therefore turns roughly 2 MiB of encoded data into billions of field operations.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from attacker-controlled bytes, then reads `n` verification-share points before validating `ThresholdParams`. [1](#0-0) 

When the encoded interpolation tag is `1`, it selects `Interpolation::Lagrange`. [2](#0-1) 

`ThresholdKeys::new` constructs `t` as participants `1..=params.t()` and computes the group key by invoking `interpolation_factor` for each of those participants. [3](#0-2) 

For Lagrange interpolation, each `interpolation_factor` call iterates over every participant in `included`, multiplying a numerator and denominator term for each other participant. [4](#0-3) 

This makes the deserialization-time group-key calculation `O(t²)`: 65,535 outer evaluations each scan up to 65,535 participants, or approximately 4.29 billion iterations. The only structural input needed is a valid curve ID, valid `t/n/i` fields, the Lagrange tag, one scalar, and `n` decodable group elements.

### Impact Explanation
An unprivileged party that can submit serialized `ThresholdKeys` bytes can consume CPU disproportionate to the input size. A compact serialized object can keep a verifier or signing component busy in field arithmetic before returning from `ThresholdKeys::read`. Repeated submissions can prevent legitimate threshold operations from being serviced.

### Likelihood Explanation
`n` is a serialized `u16`, so no protocol-level bound smaller than 65,535 is enforced before parsing and key construction. [5](#0-4)  The payload is readily constructible because every verification share can reuse a valid point encoding, such as the canonical identity encoding supported by the selected ciphersuite. The affected API is explicitly a public deserialization API. [6](#0-5) 

### Recommendation
Bound `t` and `n` to the maximum participant set supported by the protocol before reading `n` field elements or group elements. Reject excessive values immediately after reading `t`, `n`, and `i`, rather than after parsing the variable-length sections. For Lagrange interpolation, also avoid the `O(t²)` group-key construction by computing the Lagrange evaluation with a linear-time prefix/suffix product or by batch-inverting denominator terms.

### Proof of Concept
Conceptual serialized input for `ThresholdKeys::<C>::read`:

```text
u32 C::ID.len()
C::ID
u16 t = 65535
u16 n = 65535
u16 i = 1
u8 interpolation = 1        // Lagrange
F secret_share              // any canonical scalar encoding
G verification_share[1..=65535]
                            // each entry may reuse one valid point encoding
```

Processing reaches `ThresholdKeys::new`, which evaluates `interpolation_factor` for all 65,535 included participants. [3](#0-2)  Each evaluation scans the same 65,535-element set and performs field multiplications for every non-self participant. [7](#0-6)  The result is approximately `65_535 * 65_534` loop iterations, amplified by inversion and group operations.
