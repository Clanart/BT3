### Title
Uncaught FFI panic exception in mempool spend-bundle validation can crash the full node transaction-processing path - ([File: chia/full_node/mempool_manager.py])

### Summary
CVE-2024-20380 is a ClamAV DoS caused by a C-to-Rust FFI boundary defect: malformed input crossing the FFI boundary terminates the scanning process instead of being handled as a normal error. Chia's analogous boundary is the Python-to-Rust `chia_rs` FFI used to validate CLVM/spend-bundle data submitted by any unauthenticated wallet/mempool client. `MempoolManager.pre_validate_spendbundle()` only catches `ValueError` from the Rust call `validate_clvm_and_signature()`, and its caller `FullNode.add_transaction()` only catches `ValueError` and `ValidationError`. The test-only helper `get_name_puzzle_conditions()` explicitly guards the equivalent Rust `run_block_generator`/`run_block_generator2` calls with `except BaseException`, which is direct in-repo evidence that this Rust boundary is known to be able to raise exceptions that are *not* ordinary `Exception`/`ValueError` (e.g. a PyO3 panic exception), yet the production mempool path lacks that same guard.

### Finding Description
- `MempoolManager.pre_validate_spendbundle()` runs the untrusted, attacker-submitted `SpendBundle` through the Rust function `validate_clvm_and_signature()` inside a thread-pool worker: [1](#0-0) 
- Only `ValueError` raised by the Rust call is translated into a `ValidationError`; any other exception type propagates unmodified: [2](#0-1) 
- The worker thread pool (`PriorityThreadPoolExecutor._worker`) forwards *any* `BaseException` raised inside the Rust call back onto the awaited future via `set_exception`, so it is not swallowed at the thread boundary: [3](#0-2) 
- The caller, `FullNode.add_transaction()`, only catches `ValueError` and `ValidationError` around the `pre_validate_spendbundle` call: [4](#0-3) 
- Elsewhere in the same codebase, the analogous Rust generator-execution call is wrapped with a broader `except BaseException`, specifically because the Rust/CLVM FFI boundary can raise non-`Exception` failures for malformed/malicious CLVM input: [5](#0-4) 

This asymmetry means: a crafted spend bundle that triggers a failure mode in the Rust `chia_rs` CLVM/signature-validation path that surfaces as anything other than `ValueError`/`ValidationError` (for example a PyO3 panic-derived exception, which typically does not subclass `Exception`) will not be caught by `pre_validate_spendbundle` or by `add_transaction`. Because the call executes inside `MempoolManager.pool` (a shared thread pool used for *all* transaction validation) and the resulting exception is re-raised into the asyncio task handling the peer's transaction message, an unhandled non-`Exception` failure can propagate out of the per-connection message-handling coroutine into the node's task machinery, exactly mirroring the ClamAV bug class where a crafted input crossing the C↔Rust boundary is not funneled through the expected error path and instead terminates request processing.

### Impact Explanation
This is reachable by any unauthenticated wallet user or spend-bundle submitter — no privileged access is required, only the ability to submit a `SpendBundle`/transaction to a full node, exactly matching the "unauthenticated, remote attacker submitting a crafted file" pattern in the original CVE. If exploitable, the impact is a denial-of-service on the full node's transaction-processing path: an uncaught exception surfacing from the shared mempool validation thread pool could disrupt processing of the connection/task handling that transaction and, depending on how far the unhandled exception propagates through the asyncio task hierarchy, degrade or halt further mempool admission for other legitimate submitters — a "spend-triggered transaction-processing halt" as called out in the validation criteria.

### Likelihood Explanation
This is a "likely" rather than "proven" analog. The proof-of-concept step needed to fully confirm it — actually driving `chia_rs::validate_clvm_and_signature` (a Rust/PyO3 extension not present in this Python-only index) to panic via some crafted CLVM byte sequence — cannot be completed from this repository alone, since `chia_rs` is an external compiled dependency whose panic paths are not visible here. What is concretely verifiable in this repo is the structural gap: the production exception handling in `pre_validate_spendbundle`/`add_transaction` is narrower (`ValueError`/`ValidationError` only) than the handling the same codebase's authors apply to the sibling Rust CLVM-execution call (`except BaseException`), which is itself an implicit admission that this FFI boundary can raise exceptions outside the normal `Exception` hierarchy.

### Recommendation
- Broaden exception handling around `validate_clvm_and_signature()` in `MempoolManager.pre_validate_spendbundle` (and around the awaited future in `FullNode.add_transaction`) to catch `BaseException` (or at minimum any PyO3 panic-exception type re-exported by `chia_rs`), logging and converting it into a `ValidationError`/`Err.INVALID_SPEND_BUNDLE` failure the same way `get_name_puzzle_conditions()` already does for the generator-execution path.
- Audit all other production call sites of `chia_rs` FFI functions invoked directly on unauthenticated, attacker-controlled input (spend bundles, generator programs, puzzle reveals/solutions) for the same narrow `except ValueError`/`except Exception` pattern, and align them with the `except BaseException` pattern used in the test utility.
- Confirm with the `chia_rs` maintainers/version pin whether `validate_clvm_and_signature` can panic on malformed/adversarial CLVM and, if so, whether panics are converted to a catchable, well-typed error at the Rust/PyO3 boundary rather than left as a raw panic exception.

### Proof of Concept
Not reproducible from this repository alone because the panic-triggering condition lives in the compiled `chia_rs` extension (an external dependency), not in this Python codebase. The concrete, verifiable artifact supporting this finding is the exception-handling asymmetry itself:
1. `chia/full_node/mempool_manager.py:560-567` — only `ValueError` is caught around `validate_clvm_and_signature`.
2. `chia/full_node/full_node.py:3067-3077` — only `ValueError`/`ValidationError` are caught around `pre_validate_spendbundle`.
3. `chia/_tests/util/get_name_puzzle_conditions.py:64-66` — the sibling Rust CLVM-execution call is deliberately wrapped in `except BaseException`, evidencing that this FFI boundary is known (by the codebase's own authors) to be capable of raising non-`Exception` failures for malicious/malformed CLVM input — the same bug class as CVE-2024-20380, just unmitigated in the production mempool path.
