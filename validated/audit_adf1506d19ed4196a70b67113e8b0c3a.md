### Title
`Scanner::scan_transaction` accepts zero-value/dust outputs and reports them as received funds that cannot be economically spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
A `Scanner` reports any transaction output whose `script_pubkey` matches a registered script as a `ReceivedOutput`, with no check on the output's value. An unprivileged third party can send a zero-value or below-dust output to a multisig's P2TR address; it will be returned by `scan_transaction`/`scan_block` as spendable-looking received funds, yet spending it yields nothing (its value is below the fee required to spend it). This is the same bug class as the reference report: a degenerate zero value passes the "does it match" validation, is recorded as a real deposit, and only later proves worthless/unusable when something tries to use it.

### Finding Description
`scan_transaction` matches only on `output.script_pubkey` and pushes a `ReceivedOutput` unconditionally — `value` is never examined [1](#0-0) . `ReceivedOutput::read` likewise deserializes any `TxOut` (including `value = 0`) without validation [2](#0-1) .

Downstream, `SignableTransaction::new` validates payment amounts against `DUST` and validates `inputs.is_empty()`, but never checks that each input's `output.value` exceeds the cost to spend it [3](#0-2) . The codebase itself acknowledges that dust-level outputs must be excluded: the processor filters scanned outputs by `N::DUST` [4](#0-3)  and documents that `DUST` "MUST exceed the cost to spend said output" [5](#0-4)  — yet the in-scope `Scanner`/`ReceivedOutput`/`SignableTransaction` layer, which is the public API an integrator or caller feeds untrusted chain data into, performs no such check.

### Impact Explanation
- Any user of `bitcoin-serai`'s wallet who scans blocks and treats returned `ReceivedOutput`s as deposits credits an attacker-controlled zero/dust output as received funds. Spending it can only lose money (input weight costs more in fees than the output is worth), so the reported funds are not actually spendable value.
- Such inputs are silently accepted into `SignableTransaction::new`, where they inflate the transaction weight/fee and can push a transaction over `MAX_STANDARD_TX_WEIGHT` or cause `NotEnoughFunds` accounting surprises, degrading to a griefing/DoS against the signing flow.
- Severity: Medium — funds are reported as received that are not spendable (economically negative to spend), matching the "unusable locked/zero-value deposit" shape of the reference bug, though no private key material is at risk.

### Likelihood Explanation
The attacker needs only to send an on-chain transaction paying a dust or zero-value output to the victim's already-public P2TR address — fully unprivileged, and the dust output itself costs the attacker almost nothing. Unlike the reference bug, the malicious input here requires no special encoding: `scan_transaction` matches solely on `script_pubkey`, so any such output is guaranteed to be reported.

### Recommendation
In `scan_transaction` (or at `ReceivedOutput` construction/`read`), reject outputs whose `value` is zero or below a dust threshold, mirroring the `N::DUST` filter the processor applies at `processor/src/multisigs/scanner.rs`. Additionally, `SignableTransaction::new` should reject inputs whose value is below the marginal fee cost of spending them.

### Proof of Concept
1. Obtain the victim multisig's public P2TR script (`p2tr_script_buf(key)` is a pure function of the group key, which is public).
2. Broadcast a transaction with an output `TxOut { value: 0 (or < DUST sats), script_pubkey: <victim script> }`.
3. Call `scanner.scan_block(&block)` — the output is returned in `Vec<ReceivedOutput>` indistinguishably from a real deposit, since matching is script-only and no value check exists [6](#0-5) .
4. `SignableTransaction::new(vec![that_output], ...)` proceeds past all validation (`inputs.is_empty()` is false; only `payments` are dust-checked), proving the reported "funds" are accepted as spendable inputs while being economically unspendable [7](#0-6) .
