### Title
Invalid encryption-key proofs can coerce PedPoP blame proofs into revealing ECDH keys - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`Encryption::decrypt` queues the encrypted message's per-message proof of possession for batch verification, but derives the ECDH key, decrypts the ciphertext, and constructs an `EncryptionKeyProof` before that proof is verified. `KeyMachine::calculate_share` can then return this proof in an error before the queued batch verification runs, allowing a malicious participant to obtain the ECDH key for a victim message whose key they reused.

### Finding Description
An attacker-controlled `EncryptedMessage` is parsed from public bytes, including its ephemeral key, Schnorr proof of possession, and ciphertext. [1](#0-0)  During `calculate_share`, `Encryption::decrypt` only queues the PoP verification in the shared `BatchVerifier`; it does not wait for that verification to succeed. [2](#0-1)  It immediately computes `ecdh(self.enc_key, msg.key)`, decrypts the message, and returns an `EncryptionKeyProof` containing that ECDH point. [3](#0-2) 

If the decrypted bytes are a non-canonical scalar, `calculate_share` returns `InvalidShare` with `blame: Some(blame)` immediately. [4](#0-3)  The batch containing the invalid PoP is not verified until later, so this early return bypasses the check that would otherwise classify the failure as `BatchId::Decryption` and withhold the ECDH proof. [5](#0-4) 

The returned proof serializes the ECDH point, exposing it to the attacker. [6](#0-5)  This undermines the protection described by the protocol comments: reusing another message's encryption key must not let an attacker induce the recipient to reveal the corresponding ECDH key. [7](#0-6) 

### Impact Explanation
A malicious participant can reuse the ephemeral key from an encrypted message addressed to the victim, attach an invalid PoP and ciphertext that decrypts to a non-canonical scalar, and receive a blame proof revealing the victim's ECDH key for that ephemeral key. If the attacker also knows the original ciphertext associated with that key, they can derive the ChaCha20 keystream and recover the plaintext DKG share. [8](#0-7) 

### Likelihood Explanation
The malicious participant only needs to submit serialized message bytes and cause the victim to process them as that participant's share. No validator privileges, threshold collusion, leaked private key, or malformed curve encoding is required. The exploit requires access to a ciphertext/key pair addressed to the victim; PedPoP's authenticated-channel assumption does not itself make those protocol messages confidential from another participant.

### Recommendation
Do not derive or return `EncryptionKeyProof` until the message's PoP has successfully verified. Prefer a two-phase flow in `calculate_share`: first queue and verify every `EncryptedMessage` PoP, returning `InvalidShare { blame: None }` or a dedicated invalid-PoP error on failure; only after that batch succeeds, derive ECDH keys, decrypt shares, and verify share equations. Alternatively, make `Encryption::decrypt` synchronously verify `msg.pop.verify` before calling `ecdh` or constructing `EncryptionKeyProof`.

### Proof of Concept
1. Participant `A` sends victim `B` a valid `EncryptedMessage` using ephemeral public key `X`; attacker `M` learns its serialized `key` and ciphertext.
2. `M` submits an `EncryptedMessage` under `M`'s participant index with:
   - `key = X`, reusing `A`'s ephemeral key;
   - an invalid Schnorr `pop`;
   - ciphertext bytes chosen so post-decryption scalar deserialization yields a non-canonical `C::F`, such as an all-`0xff` representation where supported by the field.
3. `B` calls `calculate_share`. `Encryption::decrypt` queues the invalid PoP, but still computes `B_enc_key * X`, decrypts the supplied ciphertext, and builds an `EncryptionKeyProof` for that ECDH point. [9](#0-8) 
4. The non-canonical scalar causes `calculate_share` to return `PedPoPError::InvalidShare { participant: M, blame: Some(proof) }` before the queued PoP is checked. [4](#0-3) 
5. `M` extracts `proof.key`, computes the same `cipher(context, proof.key)` keystream, and applies it to `A`'s original ciphertext to recover `A`'s secret share for `B`. [8](#0-7)

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
