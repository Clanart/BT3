## Analog Found: Escrow-release underflow guard in `IntentsBase._withdraw` only checks non-zero, not sufficiency

### Title
Escrow subtraction in `_withdraw` reverts on any accounting mismatch, permanently locking remaining input escrow - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The Uniswap report's core broken invariant is: a checked subtraction (`checked_sub`/`.ok_or(...)`) is used as the *only* guard on a value that legitimately needs a different, more permissive check, and because that subtraction is the sole choke point for releasing funds tied to a position, any input that doesn't satisfy the naive check causes a revert that **permanently** blocks every future call through that same function — locking the position's funds forever. The Hyperbridge `IntentsBase._withdraw` function reproduces the identical structural pattern for intent-order escrow.

### Finding Description
`_withdraw` is the single function used to release escrowed input tokens for **every** settlement path in the Intent Gateway: cross-chain `RedeemEscrow`, cross-chain `RefundEscrow`, and same-chain fill/cancel/partial-fill releases [1](#0-0) .

The per-token release guard is:

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();

_orders[body.commitment][token] = escrowed - amount;
``` [2](#0-1) 

This checks only that `escrowed != 0`; it never checks that `amount <= escrowed`. Solidity 0.8's default checked arithmetic means `escrowed - amount` reverts the entire transaction whenever `amount > escrowed`, exactly as `checked_sub(...).ok_or(Error::FeeGrowthSubPos)?` reverts in the Uniswap/Seawater `position.update` bug — the fix is bolted on as an "existence" check rather than a "sufficiency" check, leaving the actual arithmetic unprotected against any legitimate accounting drift.

Because `_orders[commitment][token]` is monotonically decremented across multiple, temporally separate calls to `_withdraw` (same-chain partial fills each release a proportional slice of escrow independently, per the documented formula `inputs[i].amount × fillAmount / totalRequired` [3](#0-2) ), any drift between the sum of amounts requested across successive `_withdraw` calls and what remains in `_orders[commitment][token]` — from independent per-output-asset fill-ratio tracking, a duplicated/late-arriving settlement message for the same commitment, or a final "release the remainder" fill computed against the original order amount instead of the live escrow balance — causes the underflow-revert path to fire on the *last* release. At that point:

- `_filled[commitment]` was never set (it's only set inside the same reverted call when `finalize=true`), so the order is stuck in limbo: not completed, not cancellable (cancellation requires `_orders[commitment][token] > 0` checks that a partially-drained but not-yet-zero balance still satisfies, but any subsequent cancel attempt recomputes the same oversized `amount` and reverts the same way).
- The remaining, already-reduced escrow for that `(commitment, token)` can never be extracted through any code path, because every path into fund release funnels through this same unguarded subtraction with the same computed `amount`.

This is functionally identical to the cited bug: "This function is used every time a position is updated, so it will be impossible to remove funds from it when the underflow happens because it will revert, resulting in locked funds."

### Impact Explanation
Funds locked here are real user/solver escrow (ERC-20 or native token), not just fees. Any order whose partial-fill or settlement accounting produces even a single-wei mismatch between the cumulative `amount` requested and the live `_orders[commitment][token]` balance becomes permanently stuck: the escrow can neither be released to a solver nor refunded to the user, since `_withdraw` is the only path to move it and it reverts deterministically on every future call with the same or larger requested amount. This matches the accepted high-severity classification of the source report — "positions resulting in the underflow would effectively become permanently inaccessible."

### Likelihood Explanation
The trigger condition does not require a malicious relayer, prover, or admin — it only requires an amount/`escrowed` mismatch to arise from ordinary protocol accounting (independent per-asset fill-ratio tracking on multi-output same-chain orders, or a completion fill computed from the order's nominal amount rather than the live escrow remainder). Given multi-asset orders and partial fills are first-class, documented features of the Intent Gateway [4](#0-3) , the condition is reachable by normal solver/user activity, not an edge case requiring privileged behavior.

### Recommendation
Replace the existence-only guard with a sufficiency guard, and clamp/refund the difference instead of reverting:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (amount > escrowed) revert InsufficientEscrow(); // explicit, recoverable error
_orders[body.commitment][token] = escrowed - amount;
```
More importantly, ensure the caller-side computation of `amount` for the final/completing release in a partial-fill sequence is derived from the **live** `_orders[commitment][token]` balance (i.e., "release whatever remains") rather than from a proportional formula applied independently per call, so drift cannot accumulate to exceed the escrowed balance in the first place.

### Proof of Concept
Exact reproduction requires the full proportional fill-amount computation in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol` (same-chain/cross-chain partial-fill callers of `_withdraw`), which could not be fully retrieved before the tool budget was exhausted. The confirmed, directly-cited facts are:
1. `_withdraw`'s only guard before `escrowed - amount` is `escrowed == 0` [2](#0-1) .
2. Partial fills release proportional escrow slices via independent computations per call [3](#0-2) .
3. `_withdraw` is the sole function releasing `_orders[commitment][token]` for fills, cancels, and refunds [5](#0-4) .

Given these, any sequence of calls into `_withdraw` for the same `(commitment, token)` whose requested `amount`s sum to more than the original escrow (due to independent per-call proportional math rather than "release-the-remainder" accounting) reproducibly reverts on the final call and permanently strands the residual escrow, with no alternate code path to recover it. A background engineer with full repo access should trace the exact `fillAmount`/`totalRequired` computation in `IntrinsicIntents.sol` and `ExtrinsicIntents.sol` to confirm whether a concrete rounding/multi-asset sequence produces this exact overshoot, and add a Foundry test that partially fills a multi-output-asset order to completion and asserts the final release succeeds and drains `_orders[commitment][token]` to exactly zero rather than reverting.

    /**
     * @dev Releases escrowed tokens to a beneficiary. Iterates over the withdrawal request's
     * token list, decrements the escrow balance for each, and transfers tokens out.
     *
     * When `finalize` is true, the order is marked as filled in the `_filled` mapping,
     * any accumulated transaction fees (in the protocol fee token) are forwarded to the
     * beneficiary, and the appropriate event (EscrowReleased or EscrowRefunded) is emitted.
     *
     * When `finalize` is false (partial fills), only the proportional token amounts are
     * released without finalizing the order.
     *
     * @param body The withdrawal request containing the commitment, token amounts, and beneficiary.
     * @param isRefund If true, emits EscrowRefunded instead of EscrowReleased on finalization.
     * @param finalize If true, marks the order as complete and releases accumulated fees.
     */
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
