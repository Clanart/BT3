## Title
Zero-fee, timeout-less relayer withdrawal dispatch can permanently strand relayer funds due to lack of delivery incentive - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in the relayer pallet zeroes a relayer's accrued `Fees` balance and dispatches a cross-chain POST request instructing the destination `HostManager`/`HYPERBRIDGE_MODULE_ID` to pay it out — but the dispatch is made with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` and `timeout: 0`. No relayer economic incentive exists for delivering this message, and because the source-side `Fees` entry is already zeroed and the dispatch never times out, there is no retry or refund path if the message is never picked up. [1](#0-0) 

### Finding Description
The withdrawal flow is: verify signature → check `available_amount` ≥ minimum → increment nonce → dispatch an ISMP POST to the destination chain's `HostManager` (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate) → **immediately zero the source-side `Fees` entry** → emit `Withdraw` event. [2](#0-1) 

The dispatch itself carries `fee: Default::default()` (zero) and `payer: [0u8;32].into()` (no accountable payer), and the `DispatchPost` sets `timeout: 0`: [3](#0-2) 

This is not incidental — the repository's own design notes explicitly document that every hyperbridge-originated system message (host-executive withdrawals, intents-coprocessor responses, token-governor messages, **and the relayer pallet's own withdrawal request**) dispatches with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }`, meaning "zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism." [4](#0-3) 

The core broken invariant mirrors the seed report exactly: a critical state-transition (delivering the payout / liquidating the position) depends entirely on an unincentivized third party (relayer / liquidator) acting altruistically. When that assumption fails, the protocol has no fallback:
- The relayer's `Fees::<T>` balance is already set to zero on the source chain the moment `withdraw` is called — before any confirmation the destination ever received or executed the payout. [5](#0-4) 
- The per-relayer `Nonce` is already incremented, so a stuck/never-delivered request cannot simply be resubmitted with the same signed payload — the relayer would need to sign a brand-new nonce, but the pallet retains no record of the original pending payout amount once `Fees` is zeroed. [6](#0-5) 
- `timeout: 0` means the request never times out, so it also never triggers a refund path (unlike user-funded requests, which the docs describe as refundable on timeout via `pallet-ismp`'s `RefundingRouter`). [7](#0-6) [8](#0-7) 

While the protocol team is aware of the general "no incentive for system messages" class (tracking issue polytope-labs/hyperbridge#532, mitigated via a governance-set `OutboundRequestDeliveryReward` allowlist keyed by `module_id`), that mitigation's design doc lists the affected dispatch sites but the fix (per-module reward via `claim_outbound_request_delivery_reward`) is a separate proposed extension, not something visibly wired into `withdrawal.rs`'s dispatch path itself in the code inspected. [9](#0-8) 

### Impact Explanation
If no relayer voluntarily delivers this zero-fee, non-expiring, altruism-dependent withdrawal message, the relayer's entire accrued balance is permanently and irrecoverably zeroed on the source chain with no corresponding payout ever landing on the destination chain — an outright loss/lock of funds with no retry, refund, or timeout mechanism available to the affected relayer. This directly matches the bounty's "stealing or loss of funds" impact category, since the balance-zeroing happens unconditionally and prior to (and independent of) actual delivery/execution.

### Likelihood Explanation
This requires no malicious actor, admin, governance action, compromised relayer/prover, or front-running — it is triggered purely by the ordinary, permissionless relaying market failing to pick up a message that carries zero fee and zero payer, which the project's own documentation acknowledges as a structural problem across every hyperbridge-originated system message including this one. Any relayer who calls `withdraw()` is exposed the moment their withdrawal request isn't delivered by an altruistic third party, which is entirely plausible for chains with thin relayer coverage or during periods where the destination-chain relaying incentive (`OutboundRequestDeliveryReward`) has not been configured for the `ISMP-RLYR` module id.

### Recommendation
Do not zero `Fees::<T>` until delivery is confirmed (e.g., only clear/decrement the balance upon a delivery-receipt callback or a state-proof-verified confirmation, mirroring the `accumulate_fees` pattern used for user-funded requests), or attach a real non-zero fee/timeout to the withdrawal dispatch so it participates in the normal relayer market and can be refunded on timeout via the existing `RefundingRouter` path. Alternatively/complementarily, register the relayer withdrawal module id (`ISMP-RLYR`/`MODULE_ID`) under `OutboundRequestDeliveryReward` by default so relaying withdrawals is economically incentivized like other system messages, closing the "altruism-only" gap called out in `docs/outbound-request-incentivization.md`.

### Proof of Concept
1. A relayer accrues fees on some destination `dest_chain` via `accumulate_fees`, populating `Fees::<T>::get(dest_chain, relayer_address)`.
2. Relayer signs `(nonce, dest_chain, beneficiary?)` and calls `Pallet::withdraw`.
3. `withdraw` verifies the signature, checks `available_amount >= min_withdrawal`, increments `Nonce`, and dispatches a `DispatchPost` to the destination's `HostManager`/`HYPERBRIDGE_MODULE_ID` with `FeeMetadata { payer: [0u8;32].into(), fee: Default::default() }` and `timeout: 0`. [10](#0-9) 
4. Immediately after dispatch succeeds (dispatch success only means the request was queued/committed on-chain, not delivered), `Fees::<T>::insert(dest_chain, address, U256::zero())` zeroes the balance. [11](#0-10) 
5. Because the dispatch carries zero fee/payer, no relayer network has economic reason to deliver it to the destination (as documented project-wide for exactly this class of dispatch). [4](#0-3) 
6. Because `timeout: 0`, the request is not eligible for the timeout-refund path that user-funded requests use. [8](#0-7) 
7. Result: the relayer's balance is gone from `Fees::<T>` with no on-chain record of the pending amount to retry, and no payout ever executes on the destination — funds are permanently lost to the relayer.

```markdown
A regular cross-chain message that flows *through* hyperbridge has a fee attached at origin (the source chain transfers `fee.payer → RELAYER_FEE_ACCOUNT` and records `RequestPayments[commitment]` in pallet-hyperbridge's child trie). When a relayer delivers and the destination receipt lands back on hyperbridge, the existing `accumulate_fees` flow credits that fee to the relayer. That whole pipeline assumes a *user* paid at origin.

But hyperbridge itself originates requests too: host parameter propagation, host-executive updates, intents-coprocessor responses, token-governor messages, the relayer pallet's withdrawal request. Today these all dispatch with `FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() }` (see `modules/pallets/host-executive/src/lib.rs:228`, `modules/pallets/intents-coprocessor/src/lib.rs:486`, `modules/pallets/relayer/src/lib.rs:638`, and `modules/pallets/token-governor/src/impls.rs`). Zero fee, zero payer. So relayers have no economic reason to pick them up, and the only thing that keeps them flowing today is altruism.

## The shape of the solution

The issue creator's preferred shape ([comment 4428807013](https://github.com/polytope-labs/hyperbridge/issues/532#issuecomment-4428807013)): use `pallet-relayer` to pay BRIDGE to whoever proves they delivered a hyperbridge-originated request. The messaging task in the tesseract relayer submits the claim.

Not every pallet on hyperbridge that dispatches a request is in scope. `pallet_ismp::child_trie::RequestCommitments` ends up holding commitments for every successful dispatch via `IsmpDispatcher`, which includes both the system messages we want to incentivize (host-executive, intents-coprocessor, token-governor, the relayer pallet's withdrawal path, future modules like bandwidth) and any other pallet that ends up dispatching from hyperbridge. The reward storage is therefore keyed by `source_module_id` and only modules with a non-zero reward are eligible. The `module_id` is the `from` field on the `PostRequest`, which each pallet sets to its unique module identifier. A module with zero reward is treated as not on the allowlist and rejected before any state proof verification runs.

This is structurally identical to the existing `claim_outbound_consensus_delivery_reward` (see `modules/pallets/relayer/src/outbound_consensus.rs`) on the consensus side. The request claim lives in its own `modules/pallets/relayer/src/outbound_request.rs` module that mirrors it: swap "consensus rotation delivered" for "request delivered," key the reward storage by `module_id`, and have the relayer ship the full `PostRequest` in the claim so the pallet can hash it on chain.

No changes to pallet-hyperbridge or to any of the system-message dispatch sites. The reward is decoupled from the dispatch path and paid out at claim time against a destination state proof.
```

```text
## Hyperbridge-initiated relayer fee withdrawals

Relayers accumulate their earned fees on Hyperbridge. When a relayer initiates a withdrawal, Hyperbridge dispatches a POST request back to the source chain. `pallet-ismp`'s [`RefundingRouter`](https://github.com/polytope-labs/hyperbridge/blob/main/modules/pallets/ismp/src/dispatcher.rs) intercepts requests addressed to the built-in module id `b"HYPR-FEE"`, decodes a `WithdrawRelayerFees` payload, and transfers the owed balance from `RELAYER_FEE_ACCOUNT` to the relayer.

No runtime configuration is required to enable this — it ships with `pallet-ismp`.
```
