### Title
Decimals/balance scale mismatch in the ERC20 native-token pointer causes wrong amount calculations by DeFi consumers - (File: `precompiles/pointer/pointer.go`, `precompiles/bank/bank.go`, `contracts/src/NativeSeiTokensERC20.sol`)

### Summary
The `pointer` precompile's `addNativePointer` sets the ERC20 pointer contract's `decimals()` to the highest display-unit exponent found in the bank denom metadata (e.g. 6, 18, etc.), while the actual integer amounts returned by `balanceOf`/`totalSupply`/`transfer` on that same pointer contract are the raw base-denom (micro-unit) integers from the `bank` precompile, which are never scaled by that exponent. This is the same class of bug as the Cooler `collateralFor()` report: a decimals value used for "amount-per-unit" math does not match the actual integer scale of the balances/amounts being manipulated.

### Finding Description
When a native pointer is registered, `AddNative` reads the denom's `Metadata.DenomUnits` and picks the unit with the highest `Exponent` (≤255) as the ERC20 `decimals`, and uses that unit's name/symbol/alias for `name()`/`symbol()`: [1](#0-0) 

That `decimals` value is passed into `UpsertERCNativePointer`, which deploys `NativeSeiTokensERC20.sol` with `decimals_` stored as `ddecimals` and returned unmodified by `decimals()`: [2](#0-1) 

However, `balanceOf`, `totalSupply`, and `transfer` (`_update`) on that same pointer contract call straight through to the `bank` precompile's `balance`/`supply`/`send`, which operate on the **raw base-denom integer amount** (the smallest, un-scaled unit stored in the bank module) with no scaling applied: [3](#0-2) [4](#0-3) 

The `bank` precompile's own `decimals()` method, in contrast, correctly hardcodes `0` because native bank balances are already integer/base-unit values with no fractional scaling: [5](#0-4) 

So there are two conflicting sources of truth for the same underlying value: the `bank` precompile says decimals=0 (raw integer), but the native ERC20 pointer built on top of it advertises `decimals` = the largest `DenomUnit.Exponent` from metadata while still exposing the exact same raw, unscaled integer balances/amounts. Any external contract or off-chain tool that reads `decimals()` from the pointer and assumes `balanceOf()`/`transfer()` amounts are expressed in that unit (as ERC20 convention requires) will misinterpret the value by `10^decimals`, exactly mirroring the Cooler `collateralFor()` bug where a mismatched decimal constant was multiplied/divided against amounts using the wrong scale.

### Impact Explanation
Any EVM contract composing with a native-token pointer (AMM pools, lending/collateral contracts, price oracles reading on-chain balances, bridges) that trusts ERC20 `decimals()` to normalize `balanceOf`/`transfer` amounts will compute wrong ratios/collateral/swap amounts by orders of magnitude (e.g. `10^6` or `10^18`), leading to fund loss (over- or under-crediting) or the ability for a caller to drain value from any contract that naively does `amount * 10^decimals` math against the pointer's raw balances. This satisfies "unauthorized transfer via precompile or pointer" / concrete fund loss criteria.

### Likelihood Explanation
Any unprivileged user can trigger this by simply calling `addNativePointer(denom)` on the `pointer` precompile (address `0x100b`) for any bank denom that has denom metadata with a nonzero display exponent (a very common case, e.g. tokenfactory denoms with 6 or 18 decimal display units), then interacting with or directing third-party contracts to interact with the resulting pointer contract. No special privileges are required; this is reachable purely by public EVM transactions.

### Recommendation
Either:
1. Make `decimals()` on the native pointer contract always return `0` (matching the `bank` precompile's own semantics, since native balances are never scaled), and stop deriving name/symbol/decimals from `DenomUnits.Exponent` for the ERC20 interface, or
2. Actually scale `balanceOf`, `totalSupply`, and `transfer` amounts by `10^decimals` in `NativeSeiTokensERC20.sol` / the `bank` precompile calls so that the exposed `decimals()` is consistent with the integer amounts returned, matching the ERC20 standard's implicit invariant that `balanceOf` values are expressed in units of `10^-decimals`.

### Proof of Concept
1. Create/observe a bank denom (e.g. via tokenfactory) whose `DenomMetadata` includes a display `DenomUnit` with `Exponent = 6` (a common convention), while the underlying stored balance amounts are raw integers with no such scaling (e.g. `1_000_000` raw units representing "1" display unit).
2. Call `pointer.addNativePointer(denom)` — per `precompiles/pointer/pointer.go` `AddNative`, this selects `decimals = 6` from the metadata and deploys `NativeSeiTokensERC20` with `ddecimals = 6`.
3. Call `pointerContract.decimals()` → returns `6`.
4. Call `pointerContract.balanceOf(holder)` → returns the raw bank balance integer (e.g. `1_000_000` for a holder with "1" full display unit), i.e. exactly the same as `bank.balance(holder, denom)` with no `/10^6` scaling.
5. A third-party DeFi contract that assumes `balanceOf` is denominated in units of `10^-decimals` (as required by ERC20 convention, e.g. Uniswap-style pools computing price = `reserve0/10^decimals0 / reserve1/10^decimals1`) will compute a swap/collateral ratio off by `10^6`, letting an attacker drain the counter-asset or mint disproportionate LP shares.

func (p PrecompileExecutor) balance(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) ([]byte, uint64, error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 2); err != nil {
		return nil, 0, err
	}

	addr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, 0, err
	}
	denom := args[1].(string)
	if denom == "" {
		return nil, 0, errors.New("invalid denom")
	}

	bz, err := method.Outputs.Pack(p.bankKeeper.GetBalance(ctx, addr, denom).Amount.BigInt())
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
