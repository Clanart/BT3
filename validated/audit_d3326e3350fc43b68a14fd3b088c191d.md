## Title
`clone()` unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` while forcing `--recursive`, disabling git's collision-recursive-clone submodule protections on attacker-controlled repository URLs - (File: `app/src/lib/git/clone.ts`)

### Summary
`clone()` builds a `git clone --recursive` invocation and hardcodes an environment variable `GIT_CLONE_PROTECTION_ACTIVE: 'false'` into every clone, regardless of the repository being cloned. Because the `url` argument to `clone()` is reachable from unprivileged, attacker-influenced input (custom-protocol deep links and CLI `clone-url` actions handled by `dispatchCLIAction`, as well as the "Clone Repository" generic URL tab), a malicious repository with a crafted recursive submodule layout could be cloned with this protection deliberately switched off.

### Finding Description
In `app/src/lib/git/clone.ts`: [1](#0-0) 
the `env` object passed to the `git clone` invocation always includes `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, and the `args` array always includes `--recursive`. There is no conditional logic, no check on `url`'s origin, and no way for a caller to opt back into the protection - every call to `clone()` disables it.

The `url` parameter reaches this code from multiple attacker-influenceable entry points:
- `dispatchCLIAction` handles the `clone-url` CLI action and calls `openOrCloneRepository(url)` directly with the URL taken from an `x-github-client://` style deep link or CLI argument: [2](#0-1) 
- `openOrCloneRepository` forwards that `url` unchanged into the `CloneRepository` popup as `initialURL`: [3](#0-2) 
- The Clone Repository dialog resolves and passes the URL to its clone implementation, which ultimately invokes `clone()`: [4](#0-3) 

`isClonePathSensitive()` (added in this file) is a *destination path* backstop only - it protects against clone-target path traversal (e.g., `~/.ssh`), and it does nothing to constrain what happens *inside* the working tree once cloning proceeds, which is exactly the class of issue that recursive-clone submodule collision protections (the fix class associated with CVE-2024-32002) address: a crafted submodule with a case-colliding or symlinked path targeting `.git` can cause files intended for the submodule content to be written into the parent repository's `.git` directory (or, depending on the specific collision, outside the intended tree), potentially leading to arbitrary file write and, via hooks, code execution.

I was unable to independently confirm within this repository that `GIT_CLONE_PROTECTION_ACTIVE` corresponds to a real, currently-shipping git environment variable (it does not appear in any git documentation reachable from this codebase's dependencies, nor is it referenced anywhere else in the tree besides this single line). If this variable name is not one actually recognized by the bundled git/dugite binary, the finding's premise (that it disables an active protection) would not hold, since unrecognized `GIT_*` variables are simply ignored by git. This is a material gap that would need to be verified against the actual git version bundled with the desktop app (e.g. by checking `dugite`'s git version and its source for handling of this variable) before treating the "protection is being disabled" framing as fully verified. However, even setting aside the specific env var name, the code's clear *intent* — as expressed by the variable name and comment-free hardcoding — is to force-disable a clone-time safety mechanism unconditionally.

### Impact Explanation
If `GIT_CLONE_PROTECTION_ACTIVE` does correspond to a real protection toggle in the git version in use, an attacker who can get any URL into `clone()` (via a deep link, CLI clone-url action, or by convincing a user to paste a URL into the Clone dialog) could serve a repository with a crafted `--recursive` submodule tree that collides with `.git` on case-insensitive/case-preserving filesystems (default on macOS and Windows) to write attacker-controlled files into the parent repository's `.git` directory — enabling hook-based code execution or corruption of the checked-out working tree, entirely from an unprivileged, ordinary clone operation.

### Likelihood Explanation
Deep-link driven cloning (`x-github-client://openRepo?url=...`) and CLI `clone-url` invocation are user-click/one-step flows that don't require unusual steps beyond visiting a malicious link or running a crafted URI, which is within the accepted scope ("clicked links/deep links"). Since the disabling is unconditional and there is no code path that re-enables the protection for untrusted URLs, exploitability (if the env var is real) is deterministic rather than probabilistic.

### Recommendation
Remove the hardcoded `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` so that git's default (protection-enabled) behavior applies for all clones, especially those originating from untrusted URLs (deep links, CLI clone-url, and free-text Clone Repository URL entries). If there is a legitimate reason certain clones (e.g., of known-trusted GitHub.com API-resolved repositories) need this disabled, gate it explicitly rather than applying it universally, and document the specific git behavior being bypassed.

### Proof of Concept
1. Register/observe a custom URL scheme handler for GitHub Desktop that accepts `x-github-client://openRepo?url=<attacker-controlled-url>` (handled via `dispatchCLIAction`'s `clone-url` action → `openOrCloneRepository` → `CloneRepository` popup → `clone()`). [2](#0-1) 
2. Host a malicious git repository containing a `.gitmodules` entry and nested submodule directory structure designed to collide with `.git` (case variation such as `.git\u200bfoo` normalized away, or `.GIT`, or a path using a trailing space/dot on Windows) per the CVE-2024-32002 technique.
3. Trigger the deep link (e.g., via a webpage the victim visits) pointing `url` at the malicious repository.
4. Observe `clone()` invoked with `GIT_CLONE_PROTECTION_ACTIVE: 'false'` and `--recursive` set: [1](#0-0) 
5. Inspect the resulting working tree/`.git` directory for files written outside the intended submodule path (e.g., inside `.git/hooks`), confirming the collision protection did not fire.

Note: step 4/5 depend on confirming with the actual bundled git/dugite version whether `GIT_CLONE_PROTECTION_ACTIVE` is a recognized toggle for this protection class; this could not be verified from the repository contents alone and should be checked directly (e.g., by running the PoC against the shipped git binary) before finalizing severity.

  private async openOrCloneRepository(url: string): Promise<Repository | null> {
    const state = this.appStore.getState()
    const repositories = state.repositories
    const existingRepository = repositories.find(r =>
      this.doesRepositoryMatchUrl(r, url)
    )

    if (existingRepository) {
      return await this.selectRepository(existingRepository)
    }

    return this.appStore._startOpenInDesktop(() => {
      this.changeCloneRepositoriesTab(CloneRepositoryTab.Generic)
      this.showPopup({
        type: PopupType.CloneRepository,
        initialURL: url,
      })
    })
  }

  private clone = async () => {
    this.setState({ loading: true })

    const cloneInfo = await this.resolveCloneInfo()
    const { path } = this.getSelectedTabState()

    if (path == null) {
      const error = new Error(`Directory could not be created at this path.`)
      this.setState({ loading: false })
      this.setSelectedTabState({ error })
      return
    }

    if (!cloneInfo) {
      const error = new Error(
        `We couldn't find that repository. Check that you are logged in, the network is accessible, and the URL or repository alias are spelled correctly.`
      )
      this.setState({ loading: false })
      this.setSelectedTabState({ error })
      return
    }

    const { url, defaultBranch } = cloneInfo

    this.props.dispatcher.closeFoldout(FoldoutType.Repository)
    try {
      this.cloneImpl(url.trim(), path, defaultBranch)
    } catch (e) {
      log.error(`CloneRepository: clone failed to complete to ${path}`, e)
      this.setState({ loading: false })
      this.setSelectedTabState({ error: e })
    }
  }
