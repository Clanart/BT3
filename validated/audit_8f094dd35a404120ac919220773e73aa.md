### Title
Submodule update/checkout operations bypass Desktop's git-hook interception ("guard") mechanism - (File: `app/src/lib/git/submodule.ts`)

### Summary
Desktop implements a security/consent layer around Git hooks: `withHooksEnv` (`app/src/lib/hooks/with-hooks-env.ts`) rewrites `core.hooksPath` to a sandboxed proxy directory and routes hook execution through `createHooksProxy`, which lets Desktop show progress, allow the user to abort, and (per user preference) skip/observe hook execution. This mechanism is only engaged when the caller explicitly opts in via `opts.interceptHooks` — see the early return `if (!opts?.interceptHooks || !getHooksEnvEnabled()) return fn(opts?.env)` [3](#0-2) . Callers such as `push`, `pull`, and `merge` correctly populate `interceptHooks` with the relevant hook names [4](#0-3) [5](#0-4) . However, `updateSubmodulesAfterOperation`, which every checkout/clone/pull operation invokes to run `git submodule update --init --recursive`, builds its execution options with only `env` and `expectedErrors` — `interceptHooks` is never set [6](#0-5) . As a result, hook execution triggered inside submodules (e.g. `post-checkout`, `post-merge` fired while Git checks out each submodule) runs through the ordinary, unsandboxed `git()`/`exec()` path with no proxy, no user-visible progress, and no ability to bypass/abort — the exact same class of gap described in the report, where a secondary execution surface ("modules"/submodules) is not subject to the same guard checks as the primary surface.

### Finding Description
Desktop's hook-interception guard is invariant-scoped to the top-level git invocation that explicitly requests `interceptHooks`. `checkoutBranch`/`checkoutCommit` call `git(...)` for the branch/commit checkout (no `interceptHooks` needed there since it's a plain checkout) and then separately call `updateSubmodulesAfterOperation` [7](#0-6) , which recursively initializes/updates submodules — an operation that itself performs checkouts (and can trigger hooks) inside each submodule's own `.git` directory. Because `updateSubmodulesAfterOperation`'s options object never sets `interceptHooks`, `withHooksEnv` short-circuits and no `core.hooksPath` override/proxy is installed for this invocation [2](#0-1) . Additionally, `updateSubmodulesAfterOperation` accepts an `allowFileProtocol` flag that, when true, passes `-c protocol.file.allow=always` [8](#0-7) , permitting a repository's `.gitmodules` to point a submodule at a `file://` URL. `checkoutBranch`/`checkoutCommit` forward this flag straight through from their own callers [9](#0-8) .

The broken invariant: the top-level "guard" (hook interception/consent UI) is assumed to cover all Git-triggered code execution for an operation, but the recursive submodule step — a distinct execution surface analogous to Safe's "module" — is dispatched through a code path that structurally cannot reach the guard, because the option that activates it is never populated.

### Impact Explanation
An attacker who controls a cloned/fetched repository (or a submodule referenced by `.gitmodules`) can rely on the fact that any hook fired while Git recurses into submodules during checkout/clone/pull executes without going through Desktop's sandboxed hook proxy (`hooks-proxy.ts`), the "Bypass Commit Hooks" safety toggle, or the failure/abort callback surfaced to the user. This weakens the protection the interception layer was built to provide (see changelog entries for "Run hooks in user's shell environment and allow bypassing commit hooks") specifically for the submodule-update code path, allowing hook-driven execution to proceed unmonitored whenever a repository the user did not fully vet is checked out with submodules present.

### Likelihood Explanation
Every checkout, clone (`--recursive` is always passed, see `app/src/lib/git/clone.ts` line 92), and pull with `--recurse-submodules` in Desktop invokes `updateSubmodulesAfterOperation`, so the missing `interceptHooks` wiring is hit on the ordinary, unprivileged submodule-update flow, not an edge case. The main uncertainty is whether Git will actually execute an attacker-supplied hook script during submodule init on a fresh clone (hooks directories are not normally part of transferred repository content), so the practical exploitation path likely requires an existing/pre-hooked local target (e.g. combined with `allowFileProtocol`/`protocol.file.allow=always` submodule URLs pointing at a local path) — this composite path could not be fully traced end-to-end within the available tool budget.

### Recommendation
Pass `interceptHooks` (mirroring the hook set relevant to submodule checkouts, e.g. `post-checkout`, `post-merge`) into the options built in `updateSubmodulesAfterOperation`, so `withHooksEnv` engages the same proxy/consent mechanism used for top-level operations. Additionally, audit all call sites that can set `allowFileProtocol: true` to ensure `protocol.file.allow=always` cannot be reached for submodules originating from an untrusted/unverified repository.

### Proof of Concept
Not independently reproducible from the indexed code alone — the gap in `interceptHooks` wiring for `updateSubmodulesAfterOperation` is directly verifiable, but confirming an end-to-end attacker-triggerable hook execution requires runtime verification of Git's submodule-hook resolution behavior that a background Devin session with full repo/terminal access would need to validate.
