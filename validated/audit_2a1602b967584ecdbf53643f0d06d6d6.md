### Title
Deterministic preprocess seed enables parallel-session nonce reuse and secret share recovery - ([File: crypto/frost/src/sign.rs])

### Summary
The ksmbd bug class is missing synchronization around operations on a shared object, letting concurrent sessions corrupt security state. The analog in Serai is `AlgorithmMachine::seeded_preprocess` / `SignMachine::from_cache` in `crypto/frost`: an entire preprocess — nonces included — is deterministically regenerated from a bare 32-byte seed (`CachedPreprocess`). Two parallel signing sessions that both load the same cached preprocess (a read-modify-use operation on a shared stored object with no single-use/locking enforcement in the library) produce identical nonces and identical commitments, yet can be driven to `sign()` on different messages/participant sets — a classic parallel-session/ROS-style nonce reuse that leaks the FROST secret share.

### Finding Description
`seeded_preprocess` rebuilds a full `AlgorithmSignMachine` purely from `ChaCha20Rng::from_seed(*seed.0)` — the nonces, commitments, addendum, and `blame_entropy` are all deterministic functions of the seed only, not of the message or signing set. [1](#0-0) 

`from_cache` is a public API that hands the seed back into `seeded_preprocess`. [2](#0-1)  Nothing in the type or API prevents the same stored cache bytes from being loaded by two concurrent callers before either deletes it — the "lack of proper locking when performing operations on an object" shape of CVE-2023-32250. The library only documents a MUST against reuse, providing no in-code guard (no consumed-once token, no counter, no atomic check-and-clear). [3](#0-2) 

Once two `AlgorithmSignMachine`s share the same nonces, `sign()` computes each nonce as `base + actual * binding_factor` where the base/actual scalars are identical across the two machines, then emits `share = secret_share * c + nonce` via `SchnorrSignature::sign`. [4](#0-3) [5](#0-4)  If the attacker varies the message or the participant set between the two sessions, the binding factors `rho` (derived from `hash_msg(msg)` and the transcribed preprocesses) and/or the challenge `c` differ while the raw nonces are equal, yielding two linear equations that solve for `secret_share`. [6](#0-5) 

### Impact Explanation
Recovery of the victim's FROST secret share. With a share plus public verification data, an attacker participating in the protocol can reduce the effective threshold or, combined with other shares, reconstruct the group private key — equivalent in severity to the kernel-code-execution impact of the original bug: unilateral signing capability on Serai threshold keys (e.g., Bitcoin spends).

### Likelihood Explanation
The precondition is a concurrent double-load of a cached preprocess. The cache exists precisely to be persisted and reloaded (`cache()`/`from_cache`), and integrators store it externally — exactly where a race on load-vs-delete occurs (two workers both reading the stored blob before either removes it). The deterministic `ChaCha20Rng` rederivation makes any such race instantly fatal rather than merely wasteful. A malicious co-signer who can trigger or observe two signing sessions over distinct messages then performs the recovery with public data only.

### Recommendation
Bind freshness into the machine rather than relying on seed deletion: e.g., derive nonces as `hash(seed || secret_share || msg-independent-session-id)` with a mandatory caller-supplied unique session ID, or require `from_cache` to take a transaction/`&mut` handle proving check-and-set deletion of the stored seed. At minimum, mix the secret share and a monotonic counter into the ChaCha seed path so a duplicated cache read cannot produce identical nonces.

### Proof of Concept
1. Obtain a stored `CachedPreprocess` blob `S` for a participant (the object two sessions can race on).
2. Concurrently call `AlgorithmSignMachine::from_cache(algorithm, keys.clone(), CachedPreprocess(Zeroizing::new(S)))` twice → two machines with identical `nonces` and identical broadcast `Preprocess.commitments` (`seeded_preprocess` is a pure function of `S`). [7](#0-6) 
3. Drive session 1 to `sign(preprocesses_A, msg1)` and session 2 to `sign(preprocesses_B, msg2)` where `msg1 != msg2` (or the included sets differ), so the attacker-controlled `rho` binding factors or challenges differ while raw nonces are equal.
4. Collect shares `s1 = c1·x + (d + ρ1·e)` and `s2 = c2·x + (d + ρ2·e)`. Since `d, e` are identical, compute `k = (s1 − s2 − x̂·(c1 − c2))/(ρ1 − ρ2)` — or directly solve the 2×2 linear system in `(x, d + ρ·e)` — recovering the secret share `x` with only public preprocesses, messages, and shares.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }

  pub fn sign(
    private_key: &Zeroizing<C::F>,
    nonce: Zeroizing<C::F>,
    challenge: C::F,
  ) -> SchnorrSignature<C> {
    SchnorrSignature {
      // Uses deref instead of * as * returns C::F yet deref returns &C::F, preventing a copy
      R: C::generator() * nonce.deref(),
      s: (challenge * private_key.deref()) + nonce.deref(),
    }
