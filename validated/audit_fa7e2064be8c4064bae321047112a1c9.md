### Title
`SignableTransaction::new()` calculates `needed_fee` from a weight estimate that omits the OP_RETURN output, understating the real transaction fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
In `SignableTransaction::new`, the OP_RETURN `data` output is appended to `tx_outs` **before** the transaction weight/vbytes are computed, but `calculate_weight_vbytes` reconstructs the transaction from `payments` only. The resulting `vbytes` (and later `vbytes_with_change`) therefore exclude the OP_RETURN output entirely, so `needed_fee` records a fee lower than what the actual signed transaction requires for its real size — the same accounting-divergence class as [H-10], where the recorded quantity (`reserve`/`needed_fee`) is updated with a smaller amount than the state actually requires.

### Finding Description
The function pushes the OP_RETURN output at lines 194-202, then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at line 204:

```rust
// networks/bitcoin/src/wallet/send.rs:194-206
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(/* data */),
  })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` (lines 62-94) builds the mock transaction with `output` containing only `payments` (plus optional change at line 98) — the `data` output is never included. The same omission applies to the change path (lines 225-227). The consequences:

1. `needed_fee = fee_per_vbyte * vbytes` undercounts by the OP_RETURN output's serialized size (~9 + up to 84 bytes of script for a max-size data payload).
2. The minimum-relay-fee check at line 211 (`needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000`) is evaluated against the understated `vbytes`, so it can pass even though the final transaction's real fee rate falls below the relay minimum.
3. The `NotEnoughFunds` check at line 215 validates `input_sat >= payment_sat + needed_fee` using the understated fee; without change, whatever remains becomes the actual fee, which may be less than the true minimum for the real vsize.
4. With change, the change output absorbs the error (`input_sat - payment_sat - fee_with_change`), so the wallet silently pays a lower effective sat/vbyte than `fee_per_vbyte` requested, and `needed_fee`/`fee()` diverge from the intended accounting.

The signed `Transaction` is genuinely larger than the estimate, so every downstream consumer of `needed_fee` (callers treat it as "the fee necessary for this transaction to achieve the fee rate specified at construction", per the doc comment at lines 129-132) operates on an incorrect figure.

### Impact Explanation
The produced transaction's actual fee rate is strictly lower than the caller-specified `fee_per_vbyte`, and can fall below `DEFAULT_MIN_RELAY_TX_FEE` despite passing the explicit check. A threshold-signed Bitcoin transaction that is unrelayable or under-priced stalls in the mempool: the inputs are consumed by the signed txid yet the outputs may never confirm, leaving funds reported as spent/pending that are effectively unspendable — mirroring [H-10]'s "reserves no longer match balances, breaking `swap()`/`mint()`". Additionally, `needed_fee` reports a value that does not bound the real requirement, corrupting any fee accounting built on it.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some`, i.e., whenever `SignableTransaction::new` is used to create a transaction embedding arbitrary bytes (the API's documented purpose: "If data is specified, an OP_RETURN output will be added"). The error magnitude scales with the data length, up to ~93 vbytes unaccounted at the 80-byte limit. With a low `fee_per_vbyte` or inputs only marginally above `payment_sat + needed_fee`, the resulting transaction is reliably below the relay minimum.

### Recommendation
Include the OP_RETURN output in the weight calculation. Either pass `tx_outs` (rather than `payments`) into `calculate_weight_vbytes`, or add the data output to the mock transaction, e.g. extend the signature to `calculate_weight_vbytes(inputs, payments, change, data)` and push `TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(data) }` when `data.is_some()`. Ensure both the initial estimate and the `weight_with_change`/`fee_with_change` recomputation cover every output actually emitted in `tx_outs`, and re-derive `needed_fee` from the final output set.

### Proof of Concept
```rust
// Conceptual: any caller providing data gets a tx whose real vsize exceeds
// the vbytes used for needed_fee and the min-relay check.
let inputs = vec![output]; // ReceivedOutput worth input_sat
let data = vec![0u8; 80];  // maximum allowed payload
let tx = SignableTransaction::new(inputs, &[(addr(), 1000)], None, Some(data), FEE).unwrap();

// tx.needed_fee() == FEE * vbytes(tx without the OP_RETURN output)
// tx.transaction().vsize()  == vbytes + ~93  (OP_RETURN output excluded)
// Effective fee rate = (input_sat - 1000) / actual_vsize < FEE,
// and the DEFAULT_MIN_RELAY_TX_FEE check at send.rs:211 was validated
// against the smaller, incorrect vbytes.
```
The divergence is structural: `tx_outs` at line 188-202 can contain one more output than the mock transaction `calculate_weight_vbytes` ever sees at line 204/226, so `needed_fee` is provably an underestimate whenever `data.is_some()`.
