### Title
Unauthenticated `InternalSendTx` (and other aggregator RPCs) reachable with no client certificate when `client_verification=false` - ([File: core/src/servers.rs])

### Summary
When `config.client_verification` is `false` (the documented aggregator deployment configuration per `docs/usage.md`), `create_grpc_server` wires the aggregator's `InterceptedService` with `Interceptors::Noop` instead of `Interceptors::OnlyAggregatorAndSelf`. Any TLS client that can reach the aggregator's port — with no client certificate, no CA-issued identity, and no knowledge of `aggregator_cert`/`our_cert` — can therefore call every method on `ClementineAggregator`, including `InternalSendTx`, which forwards an attacker-supplied raw transaction directly into `tx_sender.insert_try_to_send` with zero caller check.

### Finding Description
The claimed binding is: `caller reaching AggregatorServer::internal_send_tx == party holding aggregator_cert (Interceptors::OnlyAggregatorAndSelf.aggregator_cert / our_cert)`.

Tracing the code:
- `create_grpc_server` builds the `InterceptedService` as:
```
if config.client_verification { OnlyAggregatorAndSelf {...} } else { Noop }
``` [1](#0-0) 
- `create_aggregator_grpc_server` only emits a `tracing::warn!` when `client_verification` is *enabled*, and does nothing to force verification on when it's disabled. [2](#0-1) 
- `Interceptors::Noop` unconditionally returns `Ok(req)` for every request, performing no identity check at all. [3](#0-2) 
- `only_aggregator_and_self` (the only code that gives `is_internal`/`aggregator_cert`/`our_cert` any real meaning) is never invoked in this configuration; the leaf-certificate comparison logic and the "Internal" method gating it implements simply do not run. [4](#0-3) 
- `docs/usage.md` explicitly documents this as the aggregator's deployment posture: "The aggregator does not enforce client certificates but does use TLS for encryption." [5](#0-4) 
- On the open port, `AggregatorServer::internal_send_tx` decodes an attacker-supplied `raw_tx`, logs it, and inserts it directly into the tx-sender queue with no caller-identity check whatsoever:
```
let signed_tx: bitcoin::Transaction = send_tx_req.raw_tx...try_into()?;
...
self.tx_sender.insert_try_to_send(&mut dbtx, None, &signed_tx, fee_type.try_into()?, None, &[], &[], &[], &[]).await...
``` [6](#0-5) 
- `insert_try_to_send` persists the transaction into the queue that the background tx-sender loop broadcasts/fee-bumps. [7](#0-6) 

Root cause: `only_aggregator_and_self`'s cert-equality check is the *only* mechanism that gives meaning to "internal" vs "public" methods; when it is bypassed via `Noop`, `is_internal` becomes irrelevant and every RPC (including `InternalSendTx`, `Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`) is reachable by an anonymous TLS peer.

However, evaluating both sides of the equality *after* tracing the actual exploit path: while the gRPC call itself is unauthenticated and state-changing (queuing an arbitrary transaction), the tx-sender only broadcasts/fee-bumps whatever bytes it is given — it does not itself sign anything. To actually spend a bridge-controlled UTXO (e.g., a move-to-vault output), the attacker's submitted transaction must carry a *valid* Schnorr/N-of-N witness for that UTXO's script. The attacker described in scope holds no verifier/aggregator key share, no aggregator or verifier private key, and is explicitly barred from key compromise. Without a valid signature, Bitcoin Core (via the tx-sender's RPC calls) will reject the transaction at broadcast/mempool-acceptance time regardless of how it entered the queue. So while the *reachability* of `InternalSendTx` without authentication is real and matches "unauthenticated state-changing/broadcasting call," the specific Critical claim — "BTC leaving a move-to-vault UTXO ... via an attacker-chosen tx with no Citrea withdrawal backing it" — requires a validly-signed spend of that UTXO, which the attacker cannot produce under the stated threat model (no keys, no key compromise).

### Impact Explanation
The demonstrable impact is that an unauthenticated peer can insert arbitrary (syntactically valid) transactions into the aggregator's fee-paying queue and can call every other "internal"/aggregator-restricted method (`Setup`, `NewDeposit`, `Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`, `InternalGetEmergencyStopTx`) without any credential. This matches the **High** severity bucket: "an unauthenticated state-changing or broadcasting call." It does not, on the evidence gathered, rise to the **Critical** "BTC leaving a move-to-vault UTXO" impact, because that requires possession of a valid N-of-N/verifier signature over the target UTXO's spending path, which is outside the attacker capability set (no key share, no key compromise permitted). The blast radius of the confirmed High-severity issue is broad: it applies to the whole aggregator surface (all Setup/deposit/withdrawal/payout/emergency-stop RPCs), repeatable per request, for as long as the deployment runs with `client_verification=false`.

### Likelihood Explanation
This requires only the documented, real deployment configuration (`client_verification=false` on the aggregator, which `docs/usage.md` states is the norm for the aggregator) and network reachability to the aggregator's gRPC port. No BTC cost, no fee outlay, no bridge deposit is required to reach and call `InternalSendTx`/`Setup`/etc. — merely a TLS client. This is fully feasible and repeatable in this configuration.

### Recommendation
Do not gate `InternalSendTx` (and other state-mutating aggregator RPCs) purely on the TLS interceptor's `client_verification` toggle. Either (a) always run the aggregator with `client_verification=true` and a proper CA-issued client identity check (removing the documented "no client cert enforcement" posture from `docs/usage.md`), or (b) add an explicit, code-level authorization check inside handlers like `internal_send_tx` that does not depend solely on the transport-layer interceptor, so that disabling `client_verification` cannot silently strip authorization from every RPC surface.

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}

Clementine uses mutual TLS (mTLS) to secure gRPC communications between entities
