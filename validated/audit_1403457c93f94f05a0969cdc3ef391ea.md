Based on the investigation, I found a genuine but distinct analog in Desktop's Copilot conflict-resolution feature. It shares the report's core broken invariant: **content is applied based on position/order captured at one point in time, while the guard that decides whether to apply it only checks a coarse, stale signal (whether the file is "still conflicted") rather than verifying the underlying data the positional mapping depends on is still valid.**

### Title
Stale Copilot Conflict Resolutions Are Applied by Position, Silently Overwriting Newer On-Disk Content That Still Shows Conflict Markers - (File: app/src/lib/stores/app-store.ts)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated resolutions to disk based on content that was captured and reassembled minutes earlier (Copilot turns are tracked as taking up to 120+ seconds), and only skips a file if it is **fully** resolved (no conflict markers remain) on disk at apply time. If the working copy for that file changed in the interim but conflict markers are still present, the stale, positionally-reassembled resolution silently overwrites the current on-disk content rather than being re-validated.

### Finding Description
`reassembleResolvedFile` splices per-hunk resolutions into the file by walking the file **positionally** and matching each `<<<<<<<...>>>>>>>` block to the corresponding entry in `hunkResolutions` "by order, not by line number" [1](#0-0) . The resulting fully-reassembled `resolvedContent` is stored in app state while the user reviews the result dialog [2](#0-1) .

When the user clicks "Continue Merge", `_applyCopilotConflictResolutions` writes that stored content verbatim to disk: [3](#0-2) 

The only staleness check performed is:
```
If the user resolved this file externally... git status will report it with no remaining conflict markers... skip it
``` [4](#0-3) 

This check is binary (fully-resolved vs. still-conflicted) and never re-derives `rawContent`/hunk boundaries at apply time. If the on-disk file still contains conflict markers — but the number, order, or content of hunks has shifted since the original extraction (e.g. the user partially resolved some hunks manually and left others, or the conflicted file was rewritten by a subsequent fetch/checkout/rebase-continue tied to a different upstream commit) — the code still overwrites the entire file with the stale, positionally-spliced content. Because splicing is done "by order, not by line number," a resolution intended for hunk N can be written into whatever conflict block is now in position N, and any user edits made to the file since extraction are discarded without warning.

### Impact Explanation
This can silently corrupt what the user ultimately commits and pushes: partial manual edits made to a conflicted file during the (often multi-second-to-minute) window while Copilot is resolving conflicts, or content changes introduced by other repository operations in that window, are discarded and replaced by content computed against an earlier snapshot of the file, with hunk resolutions potentially misaligned to the wrong blocks. This is analogous to the `Vault` bug's root cause: a mechanism that finalizes/applies an allocation (here, file content) based on a stale, order-based snapshot rather than validating that the identity/state it was computed against still holds.

### Likelihood Explanation
The precondition — the user (or a concurrent repository operation) modifying a still-conflicted file's markers/hunks after Copilot resolution begins but before "Continue Merge" is clicked — is plausible given the multi-second-to-two-minute round trip explicitly tracked by `copilotConflictResolutionOver120sCount` [5](#0-4) , during which the result dialog remains open and the user can freely edit files in an external editor.

### Recommendation
At apply time, re-read the current on-disk content for each still-conflicted file and re-validate that the hunk count/markers match what was used to produce `resolvedContent` (e.g., by re-extracting hunks and comparing against the stored `rawContent`/hunk boundaries, or hashing the pre-resolution raw content) before splicing/writing. If a mismatch is detected, skip the file and route it back to manual resolution instead of silently overwriting it.

### Proof of Concept
1. Trigger a merge/rebase/cherry-pick with a conflicted file containing multiple hunks; start Copilot conflict resolution.
2. While the Copilot call is in flight (or after it completes but before clicking "Continue Merge"), open the conflicted file in an external editor and manually resolve one of the hunks in the middle of the file, leaving the remaining conflict markers intact (file still reports as conflicted, just with fewer/shifted hunks).
3. Return to Desktop and click "Continue Merge".
4. `_applyCopilotConflictResolutions` finds the file still "conflicted" (`isConflictedFileStatus` true, `hasUnresolvedConflicts` true) and unconditionally overwrites it with the stale, positionally-reassembled content [6](#0-5) , discarding the user's manual edit and potentially applying Copilot's resolution for a different hunk to the wrong location due to the shifted hunk ordering.
