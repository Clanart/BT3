### Title
Spoofable `presumed_origin` resolution lets an attacker hijack depositor/refund identity via crafted `tx.input[0]` — (File: processor/src/networks/bitcoin.rs)

### Summary
The Bitcoin DNS-style "identity resolution" analog lives in `Bitcoin::get_outputs`. For every transaction that pays a registered Serai script, the processor resolves the *origin* of the funds by looking up the spent output of `tx.input[0]` over RPC and adopting its `script_pubkey` as an `Address` [1](#0-0) . `tx.input[0]` is entirely chosen by whoever broadcasts the transaction, so this "who paid" resolution is attacker-controlled — the same bug class as the DeFiSaver DNS hijack (the layer that maps a request to an identity can be poisoned by an untrusted party).

### Finding Description
In `get_outputs`, for each matched transaction the code unconditionally computes:

- `input = &tx.input[0]`
- fetches `input.previous_output` via `rpc.get_transaction`
- sets `presumed_origin = Address::new(spent_output.script_pubkey)` and assigns it to *every* scanned output of that tx [2](#0-1) 

The only constraint on `input[0]` is that it must be a real, spendable UTXO owned by *someone*. In a multi-party transaction — CoinJoin, CoinSwap, PayJoin, or any batched/pay-to-many flow — the sender of the Serai-bound output and the owner of `input[0]` are routinely different entities. The in-code comment already concedes the weakness ("This may identify the P2WSH output *embedding the InInstruction* as the origin") but ships it anyway [3](#0-2) .

Downstream, this spoofed `Address` is stored on the `Output` (`presumed_origin` field, read/written verbatim in `Output::read`/`write` at `bitcoin.rs:136-166`) and consumed by `instruction_from_output` in `processor/src/multisigs/mod.rs` as the `refund_to` fallback when the InInstruction does not pin a refund address [4](#0-3) .

### Impact Explanation
Refunds (and any origin-authenticated handling) for a deposit are routed to whoever controls `tx.input[0]`'s previous-output script — not to the economic depositor. An attacker who co-authors a deposit transaction (PayJoin/collaborative batch, or any flow where a service constructs the funding tx for a user) places their own UTXO as `input[0]` while the victim's InInstruction credits the victim on Serai. If the deposit later triggers a refund, the multisig signs a Bitcoin transaction paying the *attacker's* address. This is theft of refund-bound funds, reachable purely by broadcasting a valid Bitcoin transaction — no validator collusion, no leaked keys.

### Likelihood Explanation
Medium. Exploitation requires: (a) a deposit path where the attacker can dictate input ordering (PayJoin/batched funding transactions are common real-world patterns for bridges), and (b) the InInstruction lacking an explicit refund destination so `presumed_origin` is used. The primitive itself is deterministic — no race or probabilistic element — and `input[0]` control is trivial for the tx assembler. The DNS-attack analog holds: a resolution step trustingly consumes attacker-supplied input.

### Recommendation
Do not infer depositor identity from `tx.input[0]`. Either require the InInstruction to explicitly carry the refund/origin address, or bind origin to the entity that can prove control of the data-bearing input (e.g., the input spending the output that commits to the InInstruction's OP_RETURN/P2WSH hash, matched by the embedded hash rather than position). At minimum, only treat `presumed_origin` as a hint and never use it to authorize fund movement without an in-instruction signature over the refund address.

### Proof of Concept
1. Victim initiates a Serai deposit via a PayJoin/coordinator that lets the attacker assemble the transaction, with InInstruction crediting the victim's Serai address and no explicit refund field.
2. Attacker orders the inputs so their own P2WPKH UTXO is `tx.input[0]`; the Serai external output is in `tx.output`.
3. `get_outputs` resolves `presumed_origin` to the attacker's address (`bitcoin.rs:714-728`) and tags the victim's External output with it.
4. The deposit later fails/is refunded; `instruction_from_output` yields `refund_to = presumed_origin` and the multisig signs a refund paying the attacker's address — stealing the refund of funds the attacker never deposited.

**Caveat:** I could not fully trace `instruction_from_output`'s refund logic in `processor/src/multisigs/mod.rs` within the tool budget to confirm that `presumed_origin` is used as an unauthenticated refund destination in all deposit flows; if an explicit refund address is always mandatory in the InInstruction format, the impact reduces to misattribution metadata rather than theft.
