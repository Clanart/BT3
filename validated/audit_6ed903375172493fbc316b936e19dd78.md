### Title
Unvalidated `htmlUrl`/check-run link scheme reaches `shell.openExternal` without http(s) restriction - (File: `app/src/main-process/main.ts`)

### Summary
`IRefCheck.htmlUrl` is populated directly from untrusted GitHub API data (e.g. `target_url` on legacy statuses, or `html_url` on check runs) and flows unmodified through the UI's "view externally" buttons to `dispatcher.openInBrowser`, which calls `shell.openExternal` in the renderer proxy, which invokes the `open-external` IPC handler in the main process. That handler does not reject non-http(s) schemes before calling Electron's `shell.openExternal(path)`.

### Finding Description
`IRefCheck.htmlUrl` is typed as `string | null` and is populated from raw API values without validation, e.g. `htmlUrl: apiStatus.target_url` in `apiStatusToRefCheck` [1](#0-0) .

From the UI, `CICheckRunStepListHeader.renderLinkExternal` wires a click straight to `props.onViewCheckExternally` [2](#0-1) , which bubbles up through `CICheckRunListItem.onViewCheckExternally` to callers such as `ci-check-run-popover.tsx`'s `onViewCheckDetails` and `pull-request-checks-failed.tsx`'s `onViewOnGitHub`, both of which take `checkRun.htmlUrl` verbatim and pass it to `dispatcher.openInBrowser(url)` [3](#0-2) [4](#0-3) .

`dispatcher.openInBrowser` ultimately calls `AppStore._openInBrowser`, which does no scheme/host validation and directly calls `shell.openExternal(url)` [5](#0-4) . The renderer-side `shell` here is the app-shell proxy that forwards to the main process via the `open-external` IPC invoke channel [6](#0-5) [7](#0-6) .

In the main process, the `open-external` handler only performs a scheme check to decide whether to *log* the URL — it does **not** reject non-http(s) values before invoking Electron's `shell.openExternal(path)`: [8](#0-7) 

This means any scheme value present in `htmlUrl` (`file://`, `javascript:`, a custom registered protocol handler, a Windows UNC-style path, etc.) is passed to Electron's `shell.openExternal` unchanged.

### Impact Explanation
`shell.openExternal` with a `file://` URL/UNC path can open arbitrary local files in the OS default handler (local file disclosure), and with a custom-registered protocol scheme can trigger arbitrary protocol-handler invocation (which upstream has historically been abusable for RCE depending on installed handlers, e.g. known issues with `search-ms:`/`shell:`-style handlers on Windows). Because `IRefCheck.htmlUrl`/`target_url` originates from repository/CI provider-controlled API data (e.g. a malicious CI status context or a third-party Check Run app supplying `target_url`/`html_url`), an attacker who controls check-run/status data for a repository/PR that the victim views can supply a malicious scheme, and a single click on the existing "view check externally" button triggers it — no unusual user steps beyond a normal click.

### Likelihood Explanation
Moderate-to-high. The trigger is a single, natural user action (clicking the existing "View check details"/external link button that Desktop already renders for CI checks) on a check run that is populated from an attacker-influenced status/check API object (e.g. an attacker-controlled or maliciously-configured CI app posting statuses to a PR). The path from `IRefCheck.htmlUrl` to `shell.openExternal` performs no allow-listing on scheme anywhere along the chain (`ci-checks.ts`, `ci-check-run-popover.tsx`, `pull-request-checks-failed.tsx`, `app-store.ts::_openInBrowser`, `main.ts`'s `open-external` handler).

### Recommendation
Add scheme validation immediately before `shell.openExternal(path)` in the `open-external` IPC handler in `app/src/main-process/main.ts` — reject (return `false`/refuse to open) any URL whose scheme is not `http:`/`https:` (parse via `new URL(path)` and check `protocol`), rather than only logging http(s) hits. Defense-in-depth: also validate/sanitize `checkRun.htmlUrl` at the point it is consumed for "view externally" actions (`ci-check-run-popover.tsx`, `pull-request-checks-failed.tsx`) to ensure it is an `http(s)` URL before calling `dispatcher.openInBrowser`.

### Proof of Concept
1. Mock the Checks/Statuses API response so a status object returns `target_url: "file:///etc/passwd"` (or a check run with `html_url` set similarly), which flows into `apiStatusToRefCheck` → `IRefCheck.htmlUrl` [1](#0-0) .
2. Render `CICheckRunStepListHeader`/`CICheckRunNoStepItem` with this check run and simulate a click on the "view check externally" button, which calls `onViewCheckExternally` [2](#0-1) .
3. Assert that `dispatcher.openInBrowser` is called with the unmodified `file://` value, and trace that call to `shell.openExternal` in `app-store.ts` [5](#0-4) , which forwards over IPC to the `open-external` handler in `main.ts` that invokes Electron's `shell.openExternal(path)` without a scheme check [8](#0-7) .

      // A check run may not have a url depending on how it is setup.
      // However, the repository should have one; Thus, we shouldn't hit this
      return

      checkRun.htmlUrl ??
      `${this.props.repository.htmlURL}/pull/${this.props.prNumber}`

    this.props.dispatcher.openInBrowser(url)
    this.props.dispatcher.incrementMetric('viewsCheckOnline')
  }

  private onViewOnGitHub = (checkRun: IRefCheck) => {
    const { repository, pullRequest, dispatcher } = this.props

    // Some checks do not provide htmlURLS like ones for the legacy status
    // object as they do not have a view in the checks screen. In that case we
    // will just open the PR and they can navigate from there... a little
    // dissatisfying tho more of an edgecase anyways.
    const url =
      checkRun.htmlUrl ??
      `${repository.gitHubRepository.htmlURL}/pull/${pullRequest.pullRequestNumber}`
    if (url === null) {
      // The repository should have a htmlURL.
      return
    }
    dispatcher.openInBrowser(url)
  }

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
