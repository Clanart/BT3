### Title
Unauthenticated denial of service: panic on out-of-range participant index in blame/decryption path - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The DDoS bug class (unprivileged traffic → service unavailable) maps onto PedPoP's blame machinery. `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with attacker-controlled `Participant` values. Any participant index not present in the map causes a `HashMap` `Index` panic, crashing the process. An unprivileged party can trigger this by submitting a blame accusation whose `recipient` (or `sender`) index is a valid non-zero `Participant` that is not among the DKG's `1..=n` indexes.

### Finding Description
`Participant` accepts any non-zero `u16` (`Participant::new(read_u16()?)` in `crypto/dkg/src/lib.rs:600`), so indices like `Participant(200)` are representable even in a small `t`-of-`n` DKG.

Two reachable panic sites exist in `crypto/dkg/pedpop/src`:

1. `Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` while building the DLEq verification statement (`encryption.rs:388`). `enc_keys` only contains entries registered via `Decryption::register` for actual participants (`encryption.rs:356-362`, populated in `verify_r1` at `lib.rs:313-315` only for `all_participant_indexes()`). If `decryptor` is any valid `Participant` outside that set, the `HashMap` `Index` impl panics.

2. `BlameMachine::blame_internal` evaluates `self.commitments[&sender]` (`lib.rs:599`). `commitments` is keyed by actual participants only, so an out-of-range `sender` panics identically.

Both paths are entered via `BlameMachine::blame` / `AdditionalBlameMachine::blame` (`lib.rs:623-632`, `lib.rs:674-682`), which take `sender`, `recipient`, an `EncryptedMessage`, and an `Option<EncryptionKeyProof>` — all values an accuser controls. Specifically, an attacker who wants to fault an honest participant (or who is a participant themselves) submits an accusation naming a non-existent `recipient` (e.g. `Participant(0xFFFF)`), plus a `Some(...)` proof. The code path reaches `self.enc_keys[&decryptor]` during argument evaluation of `proof.dleq.verify(...)` before any check that would reject the bogus index — `decrypt_with_proof` only gates on the message PoP signature (`encryption.rs:374-379`) and `proof` being `Some`, both of which the attacker satisfies trivially since the PoP challenge binds whatever `from`/`sender` value they choose (`encryption.rs:302-324`) and the DLEq proof is evaluated *after* the panicking index expression.

The panic unwinds through `blame` — there is no `catch_unwind`, no bounds check, and `Participant` validity against `params.n()` is never verified anywhere in the blame path. This mirrors the incident class: untrusted input causing a hard availability failure.

### Impact Explanation
A single crafted blame accusation aborts the calling process. In a validator/node integration, this lets any party able to submit a blame message (or cause a node to evaluate one) crash the host — a remote, unauthenticated denial of service that can stall threshold signing, DKG completion arbitration, or any blame-round handling. Since blame evaluation is intended to be callable by non-participants (`AdditionalBlameMachine::new` explicitly supports third-party evaluators, `lib.rs:639-662`), the attack surface is broad.

### Likelihood Explanation
Triggering requires only a well-formed `EncryptedMessage` with a valid PoP signature — which any party can generate for a key they chose — and an accusation naming an out-of-range `Participant`. No collusion, valid key share, or honest participation is needed. The vulnerability is a missing validation of `sender`/`recipient` against the registered participant set before `HashMap` indexing.

### Recommendation
In `Decryption::decrypt_with_proof` and `blame_internal`, replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get()` lookups that return `DecryptionError::InvalidProof` / a blame result (or a new error variant) on missing keys. Additionally, validate `sender`/`recipient` against `params.all_participant_indexes()` in `BlameMachine::blame` and `AdditionalBlameMachine::blame` before any map access.

### Proof of Concept
```rust
// After a completed DKG producing `blame_machine: BlameMachine<Secp256k1>`
// (or via AdditionalBlameMachine::new with commitment_msgs):

// Attacker picks an index not among the DKG participants
let fake_recipient = Participant::new(0xFFFF).unwrap();
let some_sender = Participant::new(1).unwrap();

// Attacker crafts an EncryptedMessage with a valid PoP under `from = some_sender`
// (they choose the ephemeral key themselves, so pop.verify passes), plus any
// EncryptionKeyProof value.
let msg: EncryptedMessage<Secp256k1, SecretShare<_>> = /* valid-PoP message */;
let proof: EncryptionKeyProof<Secp256k1> = /* any parsed proof */;

// Panics at encryption.rs:388 evaluating `self.enc_keys[&decryptor]`
// because 0xFFFF was never registered.
let (_machine, _faulty) =
    blame_machine.blame(some_sender, fake_recipient, msg, Some(proof));
```

Key code:
- Panic site 1: `self.enc_keys[&decryptor]` in `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:388`)
- Panic site 2: `self.commitments[&sender]` in `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:599`)
- Unvalidated entry: `BlameMachine::blame` (`crypto/dkg/pedpop/src/lib.rs:623-632`)
- `Participant` admits any non-zero `u16` (`crypto/dkg/src/lib.rs:600`)
