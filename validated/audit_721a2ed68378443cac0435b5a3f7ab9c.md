### Title
Missing Cross-Role Separation Check Allows Operator-as-Watchtower to Suppress Its Own Challenge, Enabling Fraudulent Withdrawal - (`core/src/verifier.rs` / `core/src/deposit.rs`)

### Summary

`is_deposit_valid` in `core/src/verifier.rs` validates that verifiers, watchtowers, and operators are each internally unique, but never checks that an operator's xonly public key is disjoint from the watchtower set (which automatically includes every verifier's xonly key). A participant who registers as both a verifier and an operator with the same key passes all deposit validation, then silently controls their own watchtower challenge UTXO. When they execute a malicious kickoff on a fork, they simply omit their own watchtower challenge, preventing the bridge circuit from seeing the canonical chain's work through that slot and potentially allowing the fraudulent withdrawal to survive the disprove game.

### Finding Description

**Root cause — missing cross-role check in `is_deposit_valid`**

`core/src/deposit.rs` defines three per-role uniqueness helpers:

```rust
pub fn are_all_verifiers_unique(&self) -> bool { ... }   // line 222
pub fn are_all_watchtowers_unique(&self) -> bool { ... } // line 228
pub fn are_all_operators_unique(&self) -> bool { ... }   // line 234
``` [1](#0-0) 

`get_watchtowers()` explicitly merges verifiers' xonly keys with the extra-watchtower list:

```rust
pub fn get_watchtowers(&self) -> Vec<XOnlyPublicKey> {
    let mut watchtowers = self.actors.verifiers.iter()
        .map(|pk| pk.x_only_public_key().0).collect::<Vec<_>>();
    watchtowers.extend(self.actors.watchtowers.iter());
    watchtowers.sort();
    watchtowers
}
``` [2](#0-1) 

`is_deposit_valid` calls all three uniqueness checks but never verifies that `operators ∩ watchtowers = ∅`: [3](#0-2) 

The aggregator builds `deposit_data` by independently fetching verifier full-keys and operator xonly-keys from their respective gRPC endpoints: [4](#0-3) 

Nothing prevents the same secret key from being used for both a verifier node and an operator node. When that happens, the verifier's xonly key appears in `get_watchtowers()` and the operator's xonly key appears in `get_operators()` — they are equal, but the three independent uniqueness checks all pass.

**Exploit path**

1. Attacker runs a verifier node with key `K` and an operator node with the same key `K`.
2. Aggregator fetches `K` (as `PublicKey`) from the verifier endpoint and `K.x_only()` from the operator endpoint; both are included in `deposit_data.actors`.
3. `is_deposit_valid` passes: verifiers are unique, watchtowers are unique, operators are unique — no cross-set check exists.
4. Deposit is co-signed by all verifiers including the attacker's verifier.
5. Attacker (as operator) executes a malicious kickoff on a fork, committing a fraudulent payout blockhash via WOTS.
6. Attacker (as verifier/watchtower) deliberately does **not** call `send_watchtower_challenge` for that kickoff. The watchtower challenge UTXO for their slot goes unspent.
7. The bridge circuit's `verify_watchtower_challenges` sees no challenge from that watchtower slot; the corresponding bit in `challenge_sending_watchtowers` is never set.
8. The operator's HCP only needs to exceed the max work from the remaining watchtowers that *did* challenge. If the attacker's fork has more accumulated work than those watchtowers' chains, the disprove fails.
9. The fraudulent withdrawal is finalized; operator collateral is not slashed. [5](#0-4) [6](#0-5) 

### Impact Explanation

A malicious operator who is also a registered verifier can suppress the watchtower challenge from their own watchtower slot. This corrupts the `challenge_sending_watchtowers` bitmap fed into the bridge circuit, potentially allowing a fraudulent withdrawal (payout on a fork) to survive the disprove game. The direct impact is theft of bridged BTC from the bridge vault and loss of the user's withdrawal funds, with no slashing of the operator's collateral.

### Likelihood Explanation

Requires the attacker to register as both a verifier and an operator with the same key, and for the aggregator to include both in a deposit. In a permissioned deployment this is a realistic insider threat; in a more open deployment it is reachable by any participant who can join both roles. The missing check is a single line of validation that is absent from an otherwise thorough `is_deposit_valid` function.

### Recommendation

Add a cross-role disjointness check inside `is_deposit_valid` (and ideally also in `DepositData` itself):

```rust
// After the existing uniqueness checks:
let watchtower_set: HashSet<XOnlyPublicKey> = deposit_data.get_watchtowers().into_iter().collect();
for op_pk in deposit_data.get_operators() {
    if watchtower_set.contains(&op_pk) {
        return Err(BridgeError::InvalidDeposit(format!(
            "Operator {op_pk:?} is also a watchtower/verifier; cross-role overlap is not allowed"
        )));
    }
}
```

This mirrors the existing per-role uniqueness pattern and closes the gap. [7](#0-6) 

### Proof of Concept

1. Start two nodes sharing the same `secret_key` — one configured as a verifier, one as an operator.
2. Run `aggregator.new_deposit(...)`. The aggregator calls `fetch_verifier_keys()` (returns `K` as `PublicKey`) and `fetch_operator_keys()` (returns `K.x_only()` as `XOnlyPublicKey`).
3. Observe that `is_deposit_valid` returns `Ok(())` — all three uniqueness checks pass, no cross-role check fires.
4. Confirm `deposit_data.get_watchtowers()` contains `K.x_only()` (from the verifier) and `deposit_data.get_operators()` also contains `K.x_only()` (from the operator).
5. Proceed with a malicious kickoff from the operator node; have the verifier node skip `send_watchtower_challenge` for that kickoff.
6. Verify that the bridge circuit's `challenge_sending_watchtowers` bitmap has the corresponding bit unset, and that the disprove attempt fails if the operator's fork work exceeds the remaining watchtowers' reported work. [2](#0-1) [3](#0-2) [4](#0-3)
