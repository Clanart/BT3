### Title
Irreversible EVM↔Sei address association can permanently block bank transfers to a user's cast address, mirroring the "no way to undo a self-set flag" bug class - ([File: x/evm/keeper/address.go])

### Summary
The `addr` precompile's `associate`/`associatePubKey` methods (and the legacy `MsgAssociate`/precompile equivalents) let any EOA permanently bind its EVM address to a Sei bech32 address via `SetAddressMapping`. There is no `disassociate`/`unassociate` message or precompile method anywhere in the codebase. Exactly like the Aloe `enrollCourier`/no-revert bug, once the mapping is written, the transaction sender who created it (or anyone who later sends funds to the "cast" version of that same address) is permanently affected, because `CanAddressReceive` is wired into the bank module's recipient-checker pipeline and starts rejecting the raw cast address for good.

### Finding Description
`SetAddressMapping` writes a two-way EVM⇄Sei mapping with no counterpart "unset" function: [1](#0-0) 

`GetEVMAddress`/`GetSeiAddress` read that mapping, and `CanAddressReceive` encodes the one-way, irrevocable consequence: once an EVM address `X` has been associated with a *different* Sei address `A`, the "cast" account `sdk.AccAddress(X)` (i.e., the Sei address obtained by directly casting the raw EVM address bytes, which is what unassociated EVM users transact from/receive at) can never again receive bank funds, because it is not equal to the now-permanently-registered `A`: [2](#0-1) 

This predicate is plugged into the bank module as a `RecipientChecker` (`RegisterRecipientChecker`/`CanSendTo`) in `app/app.go`, which the send keeper enforces on every `SendCoins`/`AddCoins`/`SendCoinsAndWei` call: [3](#0-2) [4](#0-3) 

The integration test `TestSendingToCastAddress` confirms the effect directly: before association, `SendCoins`/`SendCoinsAndWei` to the cast address succeed; the moment `SetAddressMapping` is called, all subsequent sends to that same cast address permanently fail: [5](#0-4) 

Because `associate`/`associatePubKey` on the `addr` precompile (0x...1004) is callable by any unprivileged EVM transaction sender who can produce a valid signature over the association message, and because the mapping, once written, is enforced permanently with no reverse operation in the entire codebase (`grep` for `DisassociateAddress`/`UnsetAddressMapping`-style functions found none), this is functionally identical to the "no way to unset `isCourier`" class of bug: a user-triggered, one-way flag flip that forecloses a legitimate future action (here, *receiving bank funds at the cast address*) with no recovery path short of never using that raw address again.

### Impact Explanation
Unlike the Aloe report (which only blocks reward claims), this Sei analog blocks receipt of actual funds. Any counterparty (exchange, dApp, script, or the user themself) that continues to send `usei`/tokenfactory denom funds to the raw EVM-address-cast Sei bech32 form after association will have those `MsgSend`/`SendCoinsAndWei` calls permanently and irrecoverably fail with `ErrInvalidRecipient`/"not allowed to receive funds", since `CanSendTo` consults the now-immutable association state. Because there is no disassociate mechanism, this condition can never be lifted for that address pair, which is a permanent freezing/loss-of-access condition on the affected user's fund-receiving path — matching the "permanent freezing" acceptance criterion.

### Likelihood Explanation
Association is a normal, expected, self-service action every EVM user is encouraged to perform (it's exercised by end-to-end tests such as `addr.spec.ts` and is required for many precompile/dApp flows). Any wallet, script, or exchange that keeps sending to the raw cast address of an EVM account after that account associates (a very plausible operational mistake, since the cast address is a valid, previously-functional bech32 Sei address) will trigger silently-failing, permanently-blocked transfers. No special privileges are needed; a normal user transaction (`associate`) suffices to create the irreversible state.

### Recommendation
Provide an explicit code path to reconcile or warn about this state instead of silently and permanently rejecting sends: e.g., have `CanAddressReceive`/bank's blocked-recipient logic auto-redirect transfers destined for a cast address to the associated Sei address rather than simply erroring, or expose a query/precompile view so integrators can detect "this address is a stale cast target" before submitting funds, and document clearly (and enforce client-side) that association is permanent so integrators must always resolve to `GetSeiAddress`/`GetEVMAddress` before sending, not use the raw cast address once association may have occurred.

### Proof of Concept
1. An EVM user `X` has been receiving `usei` at the Sei bech32 form obtained by casting `X`'s raw 20 bytes (`sdk.AccAddress(X)`), which succeeds prior to association, as shown by `TestSendingToCastAddress` lines 55-64 [6](#0-5) .
2. `X` calls the `addr` precompile's `associate`/`associatePubKey` (0x...1004) from an ordinary EVM transaction, which invokes `AssociateAddresses` → `SetAddressMapping(ctx, seiAddr, evmAddr)`, permanently linking `X` to a different Sei address `A` [7](#0-6) .
3. Any subsequent `MsgSend`/`SendCoinsAndWei` targeting the cast address of `X` now fails, as demonstrated by lines 67-70 of the same test, and there is no message/precompile method in the codebase to reverse `SetAddressMapping` or clear the association, so this failure is permanent for that address pair [8](#0-7) .

func (k *Keeper) SetAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Set(types.EVMAddressToSeiAddressKey(evmAddress), seiAddress)
	store.Set(types.SeiAddressToEVMAddressKey(seiAddress), evmAddress[:])
	if !k.accountKeeper.HasAccount(ctx, seiAddress) {
		k.accountKeeper.SetAccount(ctx, k.accountKeeper.NewAccountWithAddress(ctx, seiAddress))
	}
	ctx.EventManager().EmitEvent(sdk.NewEvent(
		types.EventTypeAddressAssociated,
		sdk.NewAttribute(types.AttributeKeySeiAddress, seiAddress.String()),
		sdk.NewAttribute(types.AttributeKeyEvmAddress, evmAddress.Hex()),
	))
}

func (k *Keeper) DeleteAddressMapping(ctx sdk.Context, seiAddress sdk.AccAddress, evmAddress common.Address) {
	store := ctx.KVStore(k.storeKey)
	store.Delete(types.EVMAddressToSeiAddressKey(evmAddress))
	store.Delete(types.SeiAddressToEVMAddressKey(seiAddress))
}

// A sdk.AccAddress may not receive funds from bank if it's the result of direct-casting
// from an EVM address AND the originating EVM address has already been associated with
// a true (i.e. derived from the same pubkey) sdk.AccAddress.
func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func TestSendingToCastAddress(t *testing.T) {
	a := keeper.EVMTestApp
	ctx := a.GetContextForDeliverTx([]byte{})
	seiAddr, evmAddr := keeper.MockAddressPair()
	castAddr := sdk.AccAddress(evmAddr[:])
	sourceAddr, _ := keeper.MockAddressPair()
	require.Nil(t, a.BankKeeper.MintCoins(ctx, "evm", sdk.NewCoins(sdk.NewCoin("usei", sdk.NewInt(10)))))

	require.NotNil(t, a.BankKeeper.SendCoinsAndWei(ctx, sourceAddr, castAddr, sdk.OneInt(), sdk.OneInt()))

func (p PrecompileExecutor) associateAddresses(ctx sdk.Context, method *abi.Method, evmAddr common.Address, seiAddr sdk.AccAddress, pubkey cryptotypes.PubKey) (ret []byte, remainingGas uint64, err error) {
	// Check that address is not already associated
	_, found := p.evmKeeper.GetEVMAddress(ctx, seiAddr)
	if found {
		return nil, 0, fmt.Errorf("address %s is already associated with evm address %s", seiAddr, evmAddr)
	}

	// Associate Addresses:
	associationHelper := helpers.NewAssociationHelper(p.evmKeeper, p.bankKeeper, p.accountKeeper)
	err = associationHelper.AssociateAddresses(ctx, seiAddr, evmAddr, pubkey, false)
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(seiAddr.String(), evmAddr)
	return ret, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
