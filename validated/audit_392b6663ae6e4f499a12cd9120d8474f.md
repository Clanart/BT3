## Title
Reentrancy in `IntentGatewayV2.withdraw()` on Tron allows repeated escrow drain via native-token beneficiary callback - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` contract sends native tokens (or ERC20) to the beneficiary **before** decrementing `_orders[commitment][token]`, unlike the audited EVM version (`IntentsBase.sol`), which computes the new balance and writes state before making the external transfer call. This checks-effects-interactions violation lets a beneficiary with a fallback function re-enter `withdraw()` (via a recursive `RedeemEscrow`/`RefundEscrow` delivery through `onAccept`, or via the same-chain `cancelOrder` path) and pull the same escrowed balance multiple times before it's ever zeroed out, causing loss of funds analogous to the referenced report's "losses not properly recognized/settled before further action is taken."

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines ~682-720) does the external transfer first and the storage decrement second: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;

```

Compare this to the equivalent, correctly-ordered logic in the mainline EVM contract `IntentsBase.sol`, which decrements `_orders[...]` before making the external call: [2](#0-1) 

The check `_orders[body.commitment][token] == 0` (rather than `< amount`) is a weak guard: it only blocks a *second* withdrawal once the balance has already reached exactly zero, not any withdrawal beyond the original escrowed amount, and — because it runs before the external call on every reentrant invocation — it still reads the pre-decrement value on each nested call.

Reachability: `withdraw()` is invoked from `onAccept()` for `RequestKind.RedeemEscrow` and `RequestKind.RefundEscrow` (arriving from a proven cross-chain settlement/cancellation message where `body.beneficiary` is attacker-controlled — the filler/solver address on `RedeemEscrow`, or the order's `user` on `RefundEscrow`), and from same-chain `cancelOrder()`. [3](#0-2) [4](#0-3) 

Since `body.beneficiary` in the `RedeemEscrow` path is set to `msg.sender` (the filler) by the destination-chain fill logic, an attacker can register a contract address as the filler/solver, receive the native-token payout via `.call{value:}`, and in its `receive()`/fallback re-enter the source chain's cross-chain message handler (or a second in-flight settlement for the same commitment on same-chain cancel) before `_orders[commitment][token]` is decremented, draining more than what was escrowed.

### Impact Explanation
This is a direct, unauthorized fund-drain path (stealing/loss of escrowed bridge funds) matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories. An attacker acting purely as an unprivileged order-filler/beneficiary can repeatedly withdraw against a single escrow commitment, draining the gateway's native-token balance beyond the amount legitimately owed, at the direct expense of the protocol/other users' escrowed funds.

### Likelihood Explanation
Likelihood is high for the native-token (`token == address(0)`) branch, since Tron/EVM `.call{value:}` forwards enough gas by default for a fallback to execute a reentrant call, and the attacker only needs to control the beneficiary address used in the withdrawal (trivial — they choose the solver/filler address that fills the order, or they are the order's own `user` on the cancel path). No relayer, prover, or governance compromise is required — only a standard cross-chain settlement flow with an attacker-supplied beneficiary contract.

### Recommendation
Apply the checks-effects-interactions pattern used in the audited `IntentsBase.sol`: decrement `_orders[body.commitment][token]` (checked against `amount`, not just non-zero) before performing the external native/token transfer, and add a reentrancy guard on `withdraw()`/`onAccept()` as defense in depth.

### Proof of Concept
1. Attacker deploys a contract `Attacker` with a `receive()` function that, on first invocation, re-submits/re-triggers delivery of the same `RedeemEscrow` (or `RefundEscrow`) request body for the same `commitment` (e.g., by re-entering through a path that calls `onAccept`/`withdraw` again before the first call returns — feasible because the state write for `_orders[...]` happens after the `.call`).
2. Attacker places/fills an order such that `body.beneficiary = address(Attacker)` and the escrowed token is native (`token == address(0)`).
3. When `withdraw()` executes `beneficiary.call{value: amount}("")`, control transfers to `Attacker.receive()` before `_orders[body.commitment][token] -= amount` runs.
4. `Attacker.receive()` re-enters the withdrawal path for the same commitment; the guard `_orders[body.commitment][token] == 0` still evaluates false (balance not yet decremented), so a second `.call{value: amount}` fires.
5. Repeat until the gas budget/recursion depth is exhausted or the contract's native balance is drained, after which the outer calls unwind and decrement `_orders[...]` multiple times, eventually underflowing/reverting on the way out — but by then the excess native tokens have already left the contract in the nested calls (only the final unwind fails, not the funds already sent).
