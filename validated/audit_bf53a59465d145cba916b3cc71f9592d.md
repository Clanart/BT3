### Title
Unrecovered goroutine panic in `frozen-rpc-router` batch handling can crash the public RPC-facing process — ([File: cmd/frozen-rpc-router/router.go])

### Summary
`cmd/frozen-rpc-router` runs a standalone `net/http` server (`main.go`) that fronts the EVM JSON-RPC surface, dispatching requests to a "live" or "frozen" upstream node based on parsed block parameters [1](#0-0) . For JSON-RPC batch requests, `fetchBatchGroups` spawns one goroutine per upstream group to fan out sub-batches and wait on them with a `sync.WaitGroup`, with **no `recover()`** in the spawned goroutine [2](#0-1) .

### Finding Description
Go's `net/http` server only recovers panics that occur in the request-handling goroutine itself (the one calling `ServeHTTP`); a panic in a goroutine started with `go func(){...}()` from within a handler is **not** caught by the standard library and terminates the entire OS process. `fetchBatchGroups` does exactly this for each distinct upstream target derived from a batch of RPC calls: it marshals the group's raw calls, calls `r.callUpstream`, and decodes the response inside an un-recovered `go func(group *batchGroup)` [3](#0-2) .

This is structurally the same bug class as the imaginAIry report: a public endpoint accepts attacker-controlled input, that input reaches a code path that can panic, and the panic is not contained, so the whole server process dies (`KILLED`), taking down the RPC surface for all users. Contrast this with the rest of the RPC surface in this repo, which is defensively hardened against exactly this pattern: every `evmrpc` API method wraps its body in `defer recover()` (e.g. `SimulationAPI.Call`, `DebugAPI.GetRawHeader`, `TransactionAPI.GetVMError`) [4](#0-3) [5](#0-4) , the Tendermint HTTP JSON-RPC server wraps its handler in `recoverAndLogHandler` [6](#0-5) , and the WebSocket JSON-RPC read loop recovers per-connection [7](#0-6) . `frozen-rpc-router`'s batch fan-out is the one place in the reachable RPC surface lacking this protection.

### Impact Explanation
Because the batch goroutine has no `recover()`, any panic triggered while processing a batched-RPC sub-group (for example inside `decodeBatchResponses`, `json.Marshal`, or a future/embedded bug in `callUpstream`/`newUpstreamRequest`, or simply an upstream response shape that trips an unexpected type assertion or nil dereference added later) crashes the whole `frozen-rpc-router` process, taking the public RPC endpoint offline for all users — a crash of a default-configuration RPC node, matching the accepted impact category.

### Likelihood Explanation
Exploitability depends on finding an actual panic-triggering input inside the goroutine body; from the code reviewed, the JSON handling (`json.Marshal`/`json.Unmarshal`) is defensively checked with `err` returns rather than panics, so I could not confirm a concrete panic-inducing payload with the tools available. This limits confidence that the vulnerability is currently triggerable versus being a latent robustness gap (missing defense-in-depth relative to every other RPC entry point in the codebase, which does wrap panics).

### Recommendation
Add a `defer recover()` inside the goroutine in `fetchBatchGroups` (mirroring the pattern already used throughout `evmrpc` and `sei-tendermint/rpc/jsonrpc/server`), converting any panic into a `group.err` so the batch group returns an upstream error to the caller instead of crashing the process.

### Proof of Concept
Not established — I was unable to identify a concrete attacker-supplied JSON-RPC batch payload that deterministically triggers a panic inside the goroutine body (`json.Marshal` of `[]json.RawMessage`, `callUpstream`, `decodeBatchResponses` all return errors rather than panicking for the code paths inspected). The finding is therefore a defense-in-depth/robustness gap analogous to the reported bug class rather than a confirmed exploit; a background Devin session with terminal access would be needed to fuzz batch payloads against a running instance to confirm reachability.

func (r *router) fetchBatchGroups(request *http.Request, groups []*batchGroup) {
	var wg sync.WaitGroup
	for _, group := range groups {
		wg.Add(1)
		go func(group *batchGroup) {
			defer wg.Done()
			payload := make([]json.RawMessage, 0, len(group.calls))
			for _, call := range group.calls {
				payload = append(payload, call.raw)
			}
			body, err := json.Marshal(payload)
			if err != nil {
				group.err = err
				return
			}
			responseBody, err := r.callUpstream(request, group.upstream, body)
			if err != nil {
				group.err = err
				return
			}
			group.responses, group.err = decodeBatchResponses(responseBody)
		}(group)
	}
	wg.Wait()

// inner handler panics, the wrapper recovers, logs, sends an HTTP 500 error

func recoverAndLogHandler(handler http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// Capture the HTTP status written by the handler.
		var httpStatus int
		rww := newStatusWriter(w, &httpStatus)

		// Recover panics from inside handler and try to send the client
		// 500 Internal server error. If the handler panicked after already
		// sending a (partial) response, this is a no-op.
		defer func() {
			if v := recover(); v != nil {
				var err error

					err = e
