### Title
Escrow withdrawal marks orders as filled and decrements escrow even when the underlying ERC20 `transfer` call returns `false` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2` (Tron build) imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`) but its escrow-release paths (`withdraw()` and the `SweepDust` handler in `onAccept`) bypass it, instead using raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checking that the call did not revert (`success`), never decoding/checking the returned `bool`. This is the exact bug class from the report (`auraPool.withdrawAndUnwrap()`'s unchecked boolean return) applied to token transfers guarding cross-chain escrow settlement.

### Finding Description
`withdraw()` is the internal function invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests (authenticated cross-chain messages from the registered counterpart gateway) and from `onGetResponse` for cancellation refunds: [1](#0-0) 

For every token in the withdrawal, it calls:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the target contract call reverted, not whether the token's `transfer` function actually returned `true`. Some ERC20/TRC20 tokens (most notably the widely-deployed non-standard USDT-style tokens, which do not strictly follow the return-value convention, or a token that intentionally returns `false` on a failed transfer instead of reverting) will make this low-level call succeed (`success = true`) while the transfer itself silently fails and no tokens move.

Despite that, the function proceeds unconditionally to:
- `_orders[body.commitment][token] -= amount;` — decrementing/zeroing the escrow accounting as if funds were paid out,
- `_filled[body.commitment] = beneficiary;` (set at function entry) — marking the order permanently filled,
- emitting `EscrowReleased`/`EscrowRefunded`.

The same unchecked pattern recurs in the transaction-fee redemption a few lines later: [2](#0-1) 

and in the governance-only `SweepDust` handler inside `onAccept`: [3](#0-2) 

By contrast, the EVM-side sibling implementations (`IntentsBase.sol`/`ExtrinsicIntents.sol`) correctly use `SafeERC20.safeTransfer`, which reverts on both call failure and a `false` return value: [4](#0-3) 

The Tron contract even imports `SafeERC20` and declares `using SafeERC20 for IERC20;` at the top of the file, but never calls `safeTransfer`/`safeTransferFrom` in `withdraw()` or `SweepDust`, using the unsafe raw `.call()` pattern instead: [5](#0-4) 

### Impact Explanation
This directly matches the "stealing or loss of funds" and "false state acceptance" impact categories: escrow tokens can be permanently locked/lost (the commitment is marked `_filled` and escrow balance is wiped, so the legitimate beneficiary can never re-claim via a different path) while the intended recipient receives nothing, for any input token that returns `false` rather than reverting on transfer failure (e.g., insufficient balance edge cases in non-standard tokens, blocklisted/paused-recipient tokens, or tokens with quirky failure semantics). It is a protocol/runtime defect in the bridge's fund-custody logic, not a compromised-relayer or malicious-peer scenario — the withdrawal request itself is legitimately authenticated; the flaw is purely in how the local contract interprets the ERC20 return value during settlement.

### Likelihood Explanation
Likelihood depends on the specific input/output tokens configured for a given intent-gateway deployment. If any accepted token can return `false` on failure without reverting (a known real-world category, distinct from OpenZeppelin-standard tokens), then any withdrawal against that token that happens to fail (e.g., because of an edge case in the token's internal state) results in silent fund loss and false settlement — reachable by unprivileged flow through the normal cross-chain redeem/refund/cancel path, requiring no malicious actor.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` invocations in `withdraw()`, the transaction-fee redemption block, and the `SweepDust` branch of `onAccept` with `IERC20(token).safeTransfer(...)` from the already-imported `SafeERC20` library (as is correctly done in the EVM `IntentsBase.sol`/`ExtrinsicIntents.sol` counterparts), so that both a reverting call and a `false` return value cause the transaction to revert before escrow accounting and `_filled` state are mutated.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token `T` implementing a `transfer` function that returns `false` (does not revert) when, e.g., recipient is on an internal blocklist or under any other implementation-specific failure condition, while still passing normal escrow deposit at order placement.
2. A solver fills the destination order, and the source gateway is instructed via ISMP `RedeemEscrow`/`RefundEscrow` to release escrowed `T` tokens to `beneficiary`.
3. `onAccept` → `withdraw()` executes:
   ```solidity
   (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
   if (!success) revert TransferFailed();
   ```
   Because `T.transfer` returns `false` but does not revert, `success == true` (the low-level call completed normally), so execution continues.
4. `_orders[commitment][token] -= amount` zeroes the escrow record and `_filled[commitment] = beneficiary` marks the order permanently settled; `EscrowReleased`/`EscrowRefunded` is emitted — even though `beneficiary`'s `T` balance never increased.
5. The escrowed `T` tokens remain trapped in the contract with no accounting path left to reclaim them, and the order can never be retried since it's marked filled — resulting in a stuck/lost balance equal to `amount`.

Note: I could not fully verify from the index whether Tron-native TRC20 tokens commonly integrated with this deployment exhibit this exact "return false without reverting" semantic in production, since token-selection/whitelisting configuration lives outside the indexed contract code; this assumption underlies the Likelihood assessment above.
