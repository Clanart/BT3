### Title
Consensus-delivery reward attribution uses only the first message's signer to pay for all `StateMachineUpdated` events in a batch, letting a relayer steal rewards earned by other relayers' proofs - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::on_executed` (the `FeeHandler` hook invoked by `pallet-ismp` after executing a batch of messages) determines *who* to pay by decoding the signer of `messages[0]` only, then pays that single relayer for **every** `StateMachineUpdated` event produced anywhere in the batch, regardless of which consensus message in the batch actually produced each event. [1](#0-0) 

### Finding Description
`on_executed` receives `messages: Vec<MessageWithWeight>` and `events: Vec<IsmpEvent>` for an entire executed batch. It extracts `relayer_account` by looking only at `messages.get(0)` and, if that first message is a `Message::Consensus`, recovering the sr25519 signer from its `consensus_proof`/`signer` fields:

```rust
let maybe_relayer_account = messages.get(0).and_then(|first_message| {
    if let Message::Consensus(consensus_msg) = &first_message.message {
        ...
    } else { None::<[u8; 32]> }
});
``` [2](#0-1) 

It then iterates over **all** `IsmpEvent::StateMachineUpdated` events in the batch, collapses them per `state_machine_id` to the highest `latest_height` (this part is a documented, already-applied fix for a double-pay bug), and pays `relayer_account` — the signer of message index 0 only — for the reward computed from every one of those state-machine advances:

```rust
for (state_machine_id, latest_height) in highest_per_state_machine {
    let _ = Self::process_message(state_machine_height, state_machine_id, relayer_account.clone().into());
}
``` [3](#0-2) 

`Message::Consensus.signer` is attacker-controlled data embedded in the message payload (not the extrinsic's on-chain origin) — it is only checked for a valid sr25519 signature over `keccak_256(consensus_proof)`, with no binding of that signer to the specific `state_machine_id`/proof that produced any given `StateMachineUpdated` event. Batches of messages (including multiple independent `Message::Consensus` entries for different state machines) are submitted together and executed by `pallet-ismp` as one call to `on_executed` — this is exactly the mechanism the docs describe for BEEFY rotations landing "as a single batch."

An attacker who controls a relayer key can:
1. Submit (or resubmit, since consensus proof submission is permissionless — "anyone can call them," per the Handler docs) a cheap/trivial consensus message for one state machine as message index 0, signed with their own key.
2. Include, later in the same batch, a legitimate, independently-produced consensus proof for a different (or the same) state machine that another relayer already generated/would have submitted — consensus proofs are publicly verifiable and not restricted to the original submitter, so replaying or repackaging someone else's valid proof into the same extrinsic batch is possible.
3. Because `on_executed` only looks at `messages[0]`'s signer, the attacker's key is credited for the reward computed from **all** `StateMachineUpdated` events in the batch — including the block-span reward that should have been attributed to (and would have compensated) the relayer who actually did the work of updating the other state machine(s).

This lets an unprivileged relayer redirect protocol-funded rewards away from the genuine deliverer to themselves simply by controlling message ordering within a batch, without needing to be malicious relayer/prover collusion beyond normal permissionless proof submission.

### Impact Explanation
This is a direct fund-diversion bug in a live reward-distribution pallet: `T::Currency::transfer` moves treasury funds to `relayer_account`, and `T::ReputationAsset::mint_into` also credits reputation, both keyed off the wrong/attacker-chosen signer. Legitimate relayers are shorted rewards they earned by delivering consensus proofs, while an attacker can harvest rewards for chains/heights they did not actually relay, by merely positioning a trivial self-signed consensus message first in a batch that also happens to contain other consensus updates. This is a wrong-beneficiary fund transfer, matching the bounty's "stealing or loss of funds" / "logic attacks" impact categories.

### Likelihood Explanation
Likelihood is moderate-to-high in an environment where multiple consensus messages for different or sequential updates can land in one executed batch (the pallet's own comments confirm this happens — the "collapse to highest height" fix was added precisely because multiple `StateMachineUpdated` events occur per batch). No governance, admin, or leaked-key access is required — only the ability to submit a valid but otherwise low-value consensus proof and have it ordered as the first message alongside genuine proofs, which any relayer can attempt since proof submission and message batching are permissionless.

### Recommendation
Attribute each `StateMachineUpdated` reward to the signer of the specific `Message::Consensus` that produced it, not to `messages[0]`'s signer applied blanket across the whole batch. Concretely: build a map from `state_machine_id` (or from proof-content correlation) to the signer of the consensus message that generated the corresponding state update, and pay `process_message` per-state-machine using that mapped signer instead of a single global `relayer_account`.

### Proof of Concept
1. Attacker controls key `A` and observes a pending, publicly re-broadcastable consensus proof `P_B` for state machine `X` that would legitimately reward relayer `B`.
2. Attacker submits an extrinsic/batch where `messages[0] = Message::Consensus{ signer: A, consensus_proof: cheap_proof_for_Y }` and a later message includes `P_B` (verified successfully by the consensus client, producing a genuine `StateMachineUpdated` event for `X`).
3. `pallet-ismp` executes the batch, collects `events` (containing `StateMachineUpdated` for both `Y` and `X`), and calls `ConsensusIncentives::on_executed(messages, events)`.
4. `on_executed` decodes `messages[0]`'s signer as `A` and pays `A` for **both** the `Y` reward and the `X` reward (via `process_message` in the `highest_per_state_machine` loop), even though `B` supplied the proof underlying the `X` update.
5. Result: `A`'s account receives `T::Currency::transfer` and `ReputationAsset::mint_into` for `X`'s block-span reward that should have gone to `B`. `RelayerRewarded` events emitted show `relayer: A` for both state machines.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});
