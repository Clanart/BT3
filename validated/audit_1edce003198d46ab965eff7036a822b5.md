Based on my research, the closest analog to the "mulDiv rounds to 0" tax-avoidance pattern in this codebase is in the Chia NFT royalty calculation logic, which uses truncating integer division (`//`) with a fixed basis-point scaler of `10000`, exactly mirroring the reported bug class.

### Title
NFT royalty payment can round down to zero for low-value trades, allowing royalty avoidance - (File: chia/wallet/nft_wallet/nft_wallet.py)

### Summary
`compute_royalty_amount()` and `NFTWallet.royalty_calculation()` compute the royalty owed to an NFT creator using truncating integer division against the fixed `MAX_ROYALTY_BASIS_POINTS = 10000` scaler, the same arithmetic pattern (`amount * percentage / SCALER`) flagged in the external report. When `amount * percentage < 10000`, the computed royalty truncates to `0`, letting a wallet complete an NFT trade while paying no royalty to the creator.

### Finding Description
`compute_royalty_amount` performs: [1](#0-0) 
`abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS` truncates to `0` whenever `abs(offered_amount) // royalty_split * percentage < 10000`. For a realistic 1% royalty (`percentage=100`), any fungible trade amount under 100 mojos (or under 100 units of a low-decimal CAT) results in a royalty of exactly `0`, mirroring the report's numeric example (`300*100/10000` truncating to `0` in Solidity).

The same truncating pattern also appears in `NFTWallet.royalty_calculation`, used by the wallet RPC (`nft_calculate_royalties`) to report/compute expected royalty amounts for trade construction: [2](#0-1) 

This zero-royalty condition is even explicitly leveraged in `make_nft1_offer` when constructing the `trade_prices_list`, which filters out any trade price where the computed royalty would be zero: [3](#0-2) 

A malicious or fee-avoiding wallet user can deliberately split a larger NFT purchase into several small fungible-asset offers (each below the rounding threshold) to avoid ever paying the creator's royalty, while still successfully transferring/settling the NFT trade end-to-end.

### Impact Explanation
Royalty payment is the mechanism by which NFT creators are compensated on secondary trades in Chia's ownership-layer (NFT1) design. Because the royalty calculation is performed off-chain by the wallet (there is no compensating on-chain minimum-royalty check in the reachable Python driver code found), a counterparty can structure trades to systematically avoid paying royalties on low-value/CAT trades with low decimals, depriving creators of intended revenue. This is analogous to the original report's tax-avoidance impact but for NFT royalty fee avoidance rather than a "trade tax."

### Likelihood Explanation
Any unprivileged wallet user constructing or taking an NFT offer for a fungible asset (XCH or a low-decimal CAT) with a small enough amount relative to the royalty percentage can trigger this truncation deterministically and repeatably — no privileged access or special conditions are required, matching the "realistic and repeatable" bar from the original report.

### Recommendation
Introduce a minimum-trade-amount check (or round royalty calculations up, or revert) when `amount * percentage < MAX_ROYALTY_BASIS_POINTS` in `compute_royalty_amount` and `NFTWallet.royalty_calculation`, so that royalty avoidance via sub-threshold trade amounts is not silently possible.

```python
def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:
    """Compute royalty using integer arithmetic, validating against overflow and excessive percentage."""
    if percentage > MAX_ROYALTY_BASIS_POINTS:
        raise ValueError(f"NFT royalty percentage {percentage} exceeds 100% ({MAX_ROYALTY_BASIS_POINTS} basis points)")
    amount = abs(offered_amount) // royalty_split * percentage // MAX_ROYALTY_BASIS_POINTS
    royalty = uint64(amount)
    if royalty >= abs(offered_amount):
        raise ValueError("Royalty amount meets or exceeds the offered amount")
    return royalty
```
