Based on my investigation, I found a concrete Desktop analog to the "shared trusted storage/context is polluted by untrusted input" bug class.

### Title
Attacker-controlled Git hook process can smuggle its own `DESKTOP_TRAMPOLINE_TOKEN`/`GIT_*` environment variables into Desktop's trusted credential-helper trampoline environment - ([File: app/src/lib/hooks/hooks-proxy.ts](file))

### Summary
The `Policy`/`Policed` bug is fundamentally about a *trusted execution context* (the `Policed` contract's storage slots) being blindly shared with *untrusted logic* invoked via `delegatecall`, letting the untrusted code overwrite slots it was never meant to touch, because the "safe" boundary (storage layout) was not actually enforced. The closest analog in GitHub Desktop is the Git-hooks execution pipeline in `app/src/lib/hooks/hooks-proxy.ts` and `app/src/lib/hooks/with-hooks-env.ts`, where a repository-supplied Git hook (attacker-controlled, since it comes from a cloned/fetched repository via `core.hooksPath`) runs as a child process whose environment is partly reused/passed through a "safe" allow-list into a shared execution context that also carries Desktop's own sensitive `GIT_*`/`DESKTOP_*` trampoline state.

### Finding Description
`withHooksEnv` (`app/src/lib/hooks/with-hooks-env.ts:29-96`) intercepts hook invocations by rewriting `core.hooksPath` to a temporary directory of `process-proxy` stub binaries, and starts a local TCP server (`createProxyProcessServer`) protected only by a random `token` that is itself passed to the hook's environment via `GIT_CONFIG_PARAMETERS`. When a hook (which lives inside the cloned/fetched repository's control, since `core.hooksPath`/hook file contents originate from repo/config state) is invoked, `createHooksProxy` (`app/src/lib/hooks/hooks-proxy.ts:144-256`) receives the *hook's own process environment* (`conn.getEnv()`) and filters it with an allow-list: [1](#0-0) 

This `safePrefixes = ['GIT_', 'GITHEAD_']` filter is the "storage boundary" equivalent of the `Policed` contract's storage slots — it's supposed to keep the hook's own environment logically separated from Desktop's internal signaling variables. But the exclusion set is an explicit deny-list, not an allow-list of expected/known variable names: [2](#0-1) 

Because it's a deny-list, any new/renamed internal `GIT_`-prefixed control variable that Desktop introduces later (or that isn't in `excludedEnvVars`) automatically becomes part of `safeEnv` and gets merged into the spawned Git process's real environment (`{ ...shellEnv.env, ...safeEnv, GITHUB_DESKTOP: '1' }`, `hooks-proxy.ts:253`). Meanwhile, the trusted trampoline layer (`app/src/lib/trampoline/trampoline-environment.ts:123-147`) injects its own security-relevant `GIT_*` variables (`GIT_CONFIG_PARAMETERS` carrying `credential.helper=desktop`, `GIT_ASKPASS`, `GIT_USER_AGENT`) plus `DESKTOP_PORT`/`DESKTOP_TRAMPOLINE_TOKEN` (non-`GIT_`-prefixed, so not filtered at all) into the same process tree that ultimately spawns Git, which is the same process family the hook proxy operates within.

The invariant that's supposed to hold — "only Desktop-controlled trampoline/credential state reaches the trusted credential-helper trampoline server, and repo-controlled hook processes never gain visibility into or influence over that channel" — is enforced only by an incomplete deny-list and by `DESKTOP_TRAMPOLINE_TOKEN`/`PROCESS_PROXY_TOKEN` values being treated as bearer secrets passed via plain environment variables into the same OS-level process/environment fabric that untrusted hook code executes in. This mirrors the Policy bug's root cause: a shared, loosely-typed medium (Solidity storage slots ↔ OS process environment variables) is exposed across a trust boundary using an incomplete/negative protection strategy (unstructured storage ↔ deny-listed env var prefixes) instead of a structurally enforced one.

### Impact Explanation
If a hook (attacker-controlled via a malicious cloned repository that sets `core.hooksPath` to a repo-tracked, executable path — a scenario Desktop already partially guards against via the "unsafe directory"/"Trust Repository" prompts in `app/src/ui/missing-repository.tsx` and `app/src/ui/add-repository/add-existing-repository.tsx`) can read the token values from its own environment (`DESKTOP_TRAMPOLINE_TOKEN`, `PROCESS_PROXY_TOKEN`, `DESKTOP_PORT`), it can connect to `trampolineServer`/the hooks proxy server on `127.0.0.1` and impersonate the credential-helper trampoline or another "hook" invocation, potentially exfiltrating GitHub OAuth/credential material handled through `trampoline-credential-helper.ts`, or invoking arbitrary Git operations under Desktop's own authenticated context.

### Likelihood Explanation
Likelihood is limited by two factors I could not fully rule out without a live environment: (1) whether `core.hooksPath` set inside a cloned repo's tracked files can actually be picked up by Desktop given the "unsafe directory" trust prompt, and (2) whether `DESKTOP_TRAMPOLINE_TOKEN` is actually present in the *same* environment inherited by hook child processes or scoped separately per Git invocation. Both `withHooksEnv` and `withTrampolineEnv` independently construct `GIT_CONFIG_PARAMETERS` and could theoretically execute within overlapping or sequential Git invocations sharing process environment inheritance, but I was not able to trace the exact call order between `core.ts`'s `git()` wrapper and confirm whether hook execution and trampoline-token issuance ever coexist in the same live environment for a single git invocation.

### Recommendation
Replace the `excludedEnvVars` deny-list in `hooks-proxy.ts` with a strict allow-list of only the specific `GIT_*`/`GITHEAD_*` variable names Git itself is documented to set for hook invocations, and ensure Desktop-internal secrets (`DESKTOP_TRAMPOLINE_TOKEN`, `PROCESS_PROXY_TOKEN`, `DESKTOP_PORT`) are never present in the environment of any process that can be influenced by, or communicates with, an attacker-controlled repository hook. Consider using per-invocation, single-use tokens bound to a specific socket/pipe rather than long-lived env-var bearer tokens.

### Proof of Concept
I could not construct or run a live Proof of Concept in ask-only mode (no filesystem/terminal access). A concrete PoC would need to: (1) clone a repository with a tracked `core.hooksPath` pointing to a script inside the repo, (2) have that script dump its own environment variables to a file to check for leaked `DESKTOP_TRAMPOLINE_TOKEN`/`PROCESS_PROXY_TOKEN`/`DESKTOP_PORT`, and (3) attempt to connect to the reported port using those tokens to interact with `createProxyProcessServer`. This would need to be executed in a real Desktop dev build/environment, which is outside what I can verify from static code alone — I recommend a background Devin session with the actual repository if you want this validated end-to-end.
