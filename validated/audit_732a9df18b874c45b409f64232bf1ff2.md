### Title
Empty `getRewards()` stub silently drops user reward claims causing permanent freeze of unclaimed yield - ([File: rewards/BaseRewardPool.sol])

### Summary
`BaseRewardPool.getRewards()` is an empty no-op function that is invoked by `MasterMagpie._claimBaseRewarder()` whenever a user specifies a subset of reward tokens to claim via `multiclaim`/`multiclaimFor`/`multiclaimSpec`. Because the intended logic (paying out the requested reward tokens, similar to `getReward()`) was never implemented, the call silently succeeds while doing nothing, and the associated `updateReward` accounting that normally accompanies a reward payout is also skipped.

### Finding Description
`MasterMagpie._claimBaseRewarder()` decides which rewarder function to call based on whether the caller specified explicit reward tokens: [1](#0-0) 

When `_rewardTokens.length > 0` (i.e., an ordinary wallet calls `multiclaimSpec()` or `multiclaimFor()` with a non-empty reward-token array for a given pool), it calls `rewarder.getRewards(_account, _receiver, _rewardTokens)`: [2](#0-1) 

However, `getRewards()` in `BaseRewardPool` (and identically in `BaseRewardPoolV2`) is an empty stub — it has no `onlyMasterMagpie`/`updateReward` modifiers and performs no state changes or token transfers, unlike its sibling `getReward()` which correctly loops through `rewardTokens`, zeroes `userRewards`, and calls `safeTransfer`: [3](#0-2) 

This mirrors the reported bug class exactly: a verification/payout routine ("should invoke X") exists correctly on one code path (`getReward`) but was never implemented on the sibling path (`getRewards`), silently no-oping instead of performing its function — analogous to `wssl_verify_pinned()` never being wired in for the HTTP/3 path in the CVE.

Critically, this stub does not merely fail to pay rewards for that single call — the accounting state (`userRewardPerTokenPaid`, `userRewards`) is only refreshed inside `_updateFor`, which is triggered either directly via `updateFor()` or as part of `getReward()`'s `updateReward` modifier. `getRewards()` never calls `_updateFor`, so any user who calls `multiclaimSpec`/`multiclaimFor` with explicit reward tokens gets no update to their `userRewards[token][account]` tracking for that harvest either — the pending reward amount is simply computed and discarded without being credited or paid.

### Impact Explanation
Any ordinary staking user who uses `multiclaimSpec()` or `multiclaimFor()` (the front-end functions intended to let users select which bonus/reward tokens to claim, e.g., `WombatBribeManager`/`vlMGPBaseRewarder`/`mWOMSVBaseRewarder` bonus tokens) with a non-empty token list will have that harvest cycle's bonus-token rewards silently discarded rather than transferred. Because the underlying `rewardPerTokenStored` accounting still advances globally, the specific pending amount computed via `earned()` at that timestamp for the user is lost forever for that reward token unless the user later calls the full `multiclaim()`/`getReward()` (zero-length reward token array) path before further reward accrual overwrites `userRewardPerTokenPaid`. In practice this causes a freeze/loss of unclaimed yield for any unprivileged user who exercises the "claim specific rewards" flow.

### Likelihood Explanation
High reachability: `multiclaimSpec` and `multiclaimFor` are unauthenticated, unprivileged, user-facing entry points with no special preconditions beyond having a staked position and pending bonus rewards in a pool with a configured rewarder. Any front-end or direct contract caller passing a non-empty `_rewardTokens[i]` array for any pool triggers the empty stub.

### Recommendation
Implement `getRewards()` in `BaseRewardPool` and `BaseRewardPoolV2` to mirror `getReward()`'s logic but restricted to the specified `_rewardTokens` array: apply the `onlyMasterMagpie` and `updateReward(_account)` modifiers, iterate only over the passed-in tokens, zero out `userRewards[token][_account]`, and `safeTransfer` to `_receiver`, emitting `RewardPaid` for each.

### Proof of Concept
1. User stakes LP tokens via `WombatPoolHelper`, accruing bonus-token rewards in the pool's `BaseRewardPool`/`BaseRewardPoolV2` rewarder over time.
2. User calls `MasterMagpie.multiclaimSpec([stakingToken], [[bonusRewardToken]])`.
3. `_multiClaim` → `_claimBaseRewarder` sees `_rewardTokens[0].length > 0` and calls `rewarder.getRewards(account, receiver, [bonusRewardToken])`.
4. `getRewards()` executes its empty body — no `safeTransfer` occurs, no `RewardPaid` event, and `userRewards`/`userRewardPerTokenPaid` are not updated for the account.
5. The bonus reward token balance owed to the user for that period is not received, and the reward-per-token snapshot for the user was not properly refreshed by this call, causing that period's earned rewards for the token to be silently lost.     function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }
