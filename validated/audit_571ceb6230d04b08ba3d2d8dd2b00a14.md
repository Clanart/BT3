### Title
Partial-commit line selection is re-applied against a freshly re-fetched diff, allowing staged content to silently diverge from what the user reviewed and selected - ([File: app/src/lib/git/apply.ts])

### Summary
When a user reviews a diff in the Changes pane and selects individual lines/hunks to include in a commit, GitHub Desktop stores that choice as a set of *absolute line indices* (`DiffSelection`) computed against the specific diff object that was rendered in the UI at that moment. At actual commit time, however, `applyPatchToIndex` does **not** reuse that reviewed diff — it independently re-runs `git diff` via `getWorkingDirectoryDiff` and blindly re-applies the stored line indices to whatever hunks that fresh diff happens to produce. This is the same broken invariant as the reported Solidity bug: a value the user relied on when "committing" to an action (the gold-card distribution / the diff hunks) is allowed to change between commitment and execution, and nothing re-validates that the outcome still matches what the user agreed to.

### Finding Description
- The UI computes selectable/selected line indices from a diff fetched once and cached in `changesState.selection.diff` [1](#0-0) .
- `formatPatch` builds the actual patch to be applied to the index by checking `file.selection.isSelected(absoluteIndex)` against the hunks of whatever `ITextDiff` it is given — it has no way to verify these indices came from the same diff content the user saw [2](#0-1) .
- `applyPatchToIndex` is the function that actually produces the patch used for the commit. Critically, it re-fetches the diff from disk **at apply time**, independent of anything the UI previously showed the user, and then feeds the user's old `file.selection` into `formatPatch` against this new diff: `const diff = await getWorkingDirectoryDiff(repository, file) ... const patch = await formatPatch(file, diff)` [3](#0-2) .
- `stageFiles` (invoked by `createCommit`) makes this worse by staging all fully-selected ("normal") files first via `git update-index`, and only afterward looping over partially-selected files and calling `applyPatchToIndex` for each one [4](#0-3) . This means the second, authoritative `git diff` computed inside `applyPatchToIndex` runs after other files/index state has already changed in the same operation — well after, and independent of, whatever diff the user actually reviewed on screen.
- The reconciliation logic that exists (`updateChangesWorkingDirectoryDiff` re-mapping `selectableLines` when the diff changes) only runs when the Changes pane reloads a diff for display; it explicitly acknowledges "the diff might have changed dramatically since last we loaded it" [5](#0-4)  but this safeguard is never invoked on the commit/apply code path in `apply.ts` — `applyPatchToIndex` has no equivalent check.

The corrupted value is the mapping between "line index the user marked as included/excluded" and "line index in the diff actually used to build the patch." Existing guards (the UI's own reconciliation) exist only for rendering, not for the commit-time patch construction, so nothing stops `applyPatchToIndex` from silently including or excluding different content than what the user selected if the working tree/diff shape changes between UI selection and `createCommit` execution.

### Impact Explanation
If exploited, this leads to **silent corruption of what the user commits**: a victim could deliberately deselect a specific added line (e.g., a malicious payload injected into a file inside a cloned/fetched or PR-forked repository) while intending to commit the rest of the file, yet the actual committed/pushed content could still include that line (or drop content the user meant to keep) because the patch is built from a diff recomputed after the point of user review. This matches the explicitly in-scope impact category "silent corruption of what the user commits or pushes," and the attacker-controlled surface is a git remote/forked repository whose file content and `.gitattributes`/line-ending characteristics can influence diff hunk boundaries between the two `git diff` invocations.

### Likelihood Explanation
This requires a specific, narrow window: the working tree/index state (or normalization behavior affecting diff hunking, e.g., `.gitattributes`) must actually change between when the diff is rendered in the UI and when `stageFiles`/`applyPatchToIndex` runs during `createCommit`. In the common single-file, single-diff-load workflow this window is short, but Desktop's own code comments acknowledge "the diff might have changed dramatically since last we loaded it," confirming this is a known, real possibility rather than a purely theoretical race. Because `stageFiles` sequentially stages other files before running `applyPatchToIndex` for partials, multi-file commits with mixed full/partial selections widen this window further. I was not able to fully construct or verify a concrete step-by-step reproduction (e.g., confirming a specific `.gitattributes` normalization change reliably shifts hunk boundaries) within the scope of this investigation — this would need to be validated with a live Desktop instance.

### Recommendation
- Persist the exact diff (or a content-hash/blob-oid of the diffed file) alongside the `DiffSelection` used to build a commit, and have `applyPatchToIndex`/`formatPatch` fail (or force a re-review) if the freshly-fetched diff does not match what the selection was computed against, rather than silently reapplying stale line indices.
- Alternatively, thread the already-loaded/reviewed diff from the Changes store through to `createCommit` → `stageFiles` → `applyPatchToIndex` instead of re-fetching it independently at apply time.

### Proof of Concept
Not independently reproduced end-to-end; based on static code analysis of the commit path:
1. Open a repository (e.g., a forked/cloned repo where the attacker controls file content and `.gitattributes`) in Desktop.
2. Modify a tracked file so it has multiple hunks; in the Changes pane, review the diff and deselect a specific added line, leaving other lines/files selected for commit.
3. Before the commit executes, arrange for the working tree/diff-affecting state (e.g., another staged file whose content affects normalization, or a background process modifying the file) to change between the initial diff render and `createCommit` running `stageFiles` → `applyPatchToIndex`.
4. Because `applyPatchToIndex` calls `getWorkingDirectoryDiff` fresh at [6](#0-5)  and reapplies the old `DiffSelection` indices via `formatPatch` [7](#0-6) , the resulting committed patch can include/exclude different lines than what was shown and selected in the UI.
