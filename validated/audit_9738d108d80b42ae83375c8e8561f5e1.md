### Title
Stale ERC-20 Max-Allowance to Deprecated `GaslessSwapRouter` Remains Exploitable After Router Rotation - (File: `kaiax/gasless/impl/getter.go`)

### Summary
The `kaiax/gasless` module (KIP-247) requires users to grant `MaxUint256` ERC-20 `allowance` to the `GaslessSwapRouter` contract address in order to use gasless swaps. This router address is not fixed — it is read from the on-chain `Registry` contract each block and can be rotated by governance/owner via `Registry.register(GaslessSwapRouterName, newAddr, activation)`. When the router address is rotated, the client-side validation logic (which decides whether an approve/swap pair is a valid `GaslessTx`) immediately starts enforcing the **new** router address, but this has no effect on the actual ERC-20 `allowance` state that users previously granted to the **old** router. That stale, unlimited allowance remains live on-chain indefinitely, exactly mirroring the `TalentirTokenV1.setMarketplace()` bug class where changing a trusted operator address does not revoke prior blanket approvals granted to the old operator.

### Finding Description
`GaslessModule.updateAddresses` re-reads the swap router address from the `Registry`/`MultiCallContract` on every block and overwrites the in-memory `g.swapRouter` value with no history or revocation step: [1](#0-0) 

The pool/validation logic (`isApproveTx`, `isSwapTx`, and the swap-time allowance check in `checkBalanceForSwap`) only ever reference the *current* `g.swapRouter` value: [2](#0-1) [3](#0-2) 

Per the module's own documented flow, a `GaslessApproveTx` sets `token.approve(spender=swapRouter, amount=MaxUint256)` — an infinite approval to whatever the router address is at approval time: [4](#0-3) 

Because the ERC-20 `allowance(owner, spender)` mapping lives entirely inside the token contract and is controlled solely by the token owner calling `approve`/`decreaseAllowance`, rotating the `GaslessSwapRouterName` entry in the `Registry` (as exercised in `TestPostInsertBlock`'s "update gsr address" case) changes what the Kaia node *will validate as a new gasless tx*, but does absolutely nothing to the allowance a user already granted to the old router address: [5](#0-4) 

This is structurally identical to the `TalentirTokenV1.setMarketplace()` finding: changing the trusted "operator" reference (marketplace address / swap router address) only affects future behavior, while every account that previously granted blanket approval to the old address remains permanently exposed to it.

### Impact Explanation
If the previous `GaslessSwapRouter` contract is later found to be buggy, compromised, or is rotated out for any reason (the very reason a rotation would be performed), it still retains a valid, uncapped `transferFrom` capability over every user who ever executed a `GaslessApproveTx` against it. Any code path in the old router (whether by design, a discovered bug, or if the router is upgradeable/proxied and its logic is later changed by its own admin) can call `transferFrom(user, attacker, allowance)` on the approved ERC-20 token and drain user balances up to the (unlimited) previously-approved amount — this is unauthorized value movement of user funds that the protocol's own rotation mechanism was presumably meant to prevent.

### Likelihood Explanation
Router rotation is an explicit, supported governance operation (`Registry.register` with a future `activation` block, as used by both the auction and gasless modules to migrate system contract addresses), so this is not a hypothetical edge case — it is the intended mechanism for replacing a `GaslessSwapRouter`, e.g., after discovering a defect in the current one. Every account that ever sent a `GaslessApproveTx` remains permanently exposed to the deprecated router with no automatic or even user-facing mechanism to force revocation, since the Kaia client only tracks/enforces the *current* router for pool admission and never emits any warning or revocation transaction for the old one.

### Recommendation
- Require `GaslessApproveTx` to grant bounded (not `MaxUint256`) allowances tied to the specific swap being performed, reducing the blast radius of any single stale approval, or
- When the `GaslessSwapRouterName` registry entry changes, have the protocol/system-contract layer emit an event and/or provide a documented, automated revocation path (e.g., a governance-triggered call that resets `allowance(user, oldRouter)` to 0 for known approvers, comparable to the "second blocklist" recommendation in the source report), and
- At minimum, surface a clear operational warning via the `gasless_info`/`GaslessInfo` RPC when the router address changes, so integrators/wallets can prompt users to revoke stale approvals to the deprecated router.

### Proof of Concept
1. User calls `token.approve(oldGSR, MaxUint256)` as part of a valid `GaslessApproveTx` + `GaslessSwapTx` pair, per `isApproveTx`/`decodeApproveTx` validation (`kaiax/gasless/impl/getter.go:69-140`).
2. Governance rotates the `GaslessSwapRouterName` entry in `Registry` to `newGSR` with some future `activation` block (as in `TestPostInsertBlock`'s "update gsr address" scenario, `kaiax/gasless/impl/execution_test.go:118-142`).
3. After the activation block, `GaslessModule.updateAddresses` updates `g.swapRouter = newGSR` (`kaiax/gasless/impl/getter.go:315-328`); the Kaia node now only recognizes approve/swap pairs targeting `newGSR`.
4. `oldGSR`'s on-chain allowance from step 1 (`token.allowance(user, oldGSR) == MaxUint256`) is untouched — nothing in the protocol ever calls `token.approve(oldGSR, 0)` on the user's behalf.
5. If `oldGSR` is later exploited (bug, malicious upgrade, or leaked owner key), it can call `token.transferFrom(user, attacker, allowance)` directly on the ERC-20 token contract, completely bypassing the Kaia gasless tx-pool validation logic, resulting in unauthorized transfer of user funds.

func (g *GaslessModule) IsApproveTx(tx *types.Transaction) bool {
	args, ok := decodeApproveTx(tx, g.signer)
	return ok && g.isApproveTx(args)
}

func (g *GaslessModule) isApproveTx(args *ApproveArgs) bool {
	g.gaslessInfoMu.RLock()
	defer g.gaslessInfoMu.RUnlock()

	return g.allowedTokens[args.Token] && // A1
		g.swapRouter == args.Spender && // A3
		args.Amount.Cmp(abi.MaxUint256) == 0 // A4
}

// IsSwapTx checks following conditions:
// S1. tx.to is a whitelisted SwapRouter contract.
// S2. tx.data is `swapForGas(token, amountIn, minAmountOut, amountRepay)`.
// S3. token is a whitelisted ERC20 token.
func (g *GaslessModule) IsSwapTx(tx *types.Transaction) bool {
	args, ok := decodeSwapTx(tx, g.signer)
	return ok && g.isSwapTx(args)
}

func (g *GaslessModule) isSwapTx(args *SwapArgs) bool {
	g.gaslessInfoMu.RLock()
	defer g.gaslessInfoMu.RUnlock()

	return g.swapRouter == args.Router && // S1
		g.allowedTokens[args.Token] // S3
}

func (g *GaslessModule) updateAddresses(header *types.Header) error {
	g.gaslessInfoMu.Lock()
	defer g.gaslessInfoMu.Unlock()

	swapRouter, tokens, err := getGaslessInfo(g.Chain, header)
	// proceed even if there is something wrong with multicall contract
	if err != nil {
		g.swapRouter = common.Address{}
		g.allowedTokens = map[common.Address]bool{}
		logger.Warn("there is something wrong with multicall contract", "err", err.Error())
		return nil
	}

	g.swapRouter = swapRouter
