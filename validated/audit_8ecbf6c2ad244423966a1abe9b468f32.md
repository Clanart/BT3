Based on the evidence gathered, I can identify a real analog in Desktop's deep-link handling, though I was unable to fully verify the final git-command construction in `app/src/lib/git/checkout.ts` due to running out of tool iterations — this is called out explicitly below.

### Title
Deep-link `openrepo` action validates branch names with an incomplete check, allowing leading-dash flag-injection into git commands - (File: `app/src/lib/parse-app-url.ts`)

### Summary
`parseAppURL` validates a user-supplied `branch` query-string parameter (attacker-controlled via a clickable `x-github-client://openrepo/...` deep link) using `testForInvalidChars`, but this validator does not reject a leading `-`/`+`, unlike the sibling sanitizer `sanitizedRefName` in the same module, which explicitly strips leading dashes/pluses before use. The branch value that survives this incomplete check is later passed straight into git operations (`checkoutLocalBranch` / `git checkout`) via `Dispatcher.openBranchNameFromUrl`.

### Finding Description
`parse-app-url.ts` exposes two related functions for handling ref names:
- `sanitizedRefName`, which sanitizes a name and additionally removes leading `-`/`+` characters: `name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')` [1](#0-0) 
- `testForInvalidChars`, which is a boolean *validator* used to reject strings, but is defined only in terms of `invalidCharacterRegex`, which does **not** include `-` in its character class: `/[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g` [2](#0-1) 

When Desktop parses the `openrepo` deep-link action, it validates `branch` solely with `testForInvalidChars` and returns the raw, unsanitized string as the action's `branch` field if the test passes: [3](#0-2) 

Because `testForInvalidChars` does not flag a leading dash, an attacker-crafted deep link such as `x-github-client://openRepo/https://github.com/org/repo?branch=--upload-pack%3Dtouch%20/tmp/pwned` is accepted as a valid `IOpenRepositoryFromURLAction` and forwarded unmodified as `branch`.

This action is consumed by `Dispatcher.openRepositoryFromUrl`, which routes to `openBranchNameFromUrl(url, branch)` when a branch is present, cloning/opening the repo and then calling `this.checkoutLocalBranch(repository, branchName)` with the raw, attacker-controlled string: [4](#0-3) 

The invariant that should hold — "any untrusted ref-like value must be passed through the same leading-dash-stripping sanitizer used elsewhere in the same module" — is broken here: the deep-link code path uses the weaker `testForInvalidChars` guard instead of `sanitizedRefName`, exactly mirroring the seed report's pattern of one function ("burn") being protected while a sibling ("burnFrom") performing an equivalent sensitive action is not.

### Impact Explanation
If the underlying git argument builder for checkout (`app/src/lib/git/checkout.ts`, not fully confirmed during this investigation) invokes something equivalent to `git(['checkout', branchName], ...)` without a `--` end-of-options separator, a string beginning with `-` will be interpreted by git as a command-line option rather than a ref name. Depending on which flag is smuggled this can range from an unintended git operation (e.g., forcing checkout behavior) to command execution via flags that accept executable hooks (e.g., options that shell out, such as `--upload-pack=<cmd>` in fetch/clone-adjacent code paths reused by the same URL flow). This would satisfy the "attacker controls a link/deep link the user clicks" -> "code execution / silent corruption of what the user commits or checks out" impact class from the task's scope. I could not confirm within the available budget whether `checkout.ts` already inserts a `--` separator before the branch argument, which would neutralize this specific vector — this is the key remaining uncertainty.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to click an attacker-supplied `x-github-client://openrepo/...` link (a normal, low-friction social step consistent with GitHub Desktop's documented "Open in Desktop" flow, not "social engineering" beyond a single click), and requires the underlying `checkout` git invocation to lack argument-injection hardening. The URL parsing and validation gap itself is confirmed by static analysis of `parse-app-url.ts` and `sanitize-ref-name.ts`; the exploitability past that point depends on `checkout.ts`'s exact argv construction, which was not verified.

### Recommendation
- In `parse-app-url.ts`, reject (or sanitize via `sanitizedRefName`) any `branch` value that starts with `-` or `+` before constructing `IOpenRepositoryFromURLAction`, consistent with the protection already provided by `sanitizedRefName`.
- Independently, ensure every git invocation that accepts a ref/branch derived from an untrusted source (deep links, API responses, CLI args) uses a `--` end-of-options marker before the ref argument, so that even a leading-dash value can never be interpreted as a flag.

### Proof of Concept
1. Attacker hosts/sends a link:
   `x-github-client://openRepo/https://github.com/org/repo?branch=--upload-pack%3Dtouch%20/tmp/pwned`
2. Victim (with GitHub Desktop installed and registered as the protocol handler) clicks the link.
3. `parseAppURL` accepts the branch value because `testForInvalidChars` does not flag a leading `-`: [5](#0-4) 
4. `Dispatcher.openRepositoryFromUrl` clones/opens the target repository and calls `checkoutLocalBranch(repository, branchName)` with the raw string: [6](#0-5) 
5. If the git command builder does not insert a `--` separator, git parses `--upload-pack=...` (or another flag) as an option instead of a ref, deviating from the user's intended action.

Note: step 5's exploitability was not independently confirmed against the actual contents of `app/src/lib/git/checkout.ts`; a Devin session with full file access should verify the exact `git(...)` argv array used for branch checkout before treating this as conclusively exploitable.

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
