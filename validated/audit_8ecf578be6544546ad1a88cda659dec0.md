### Title
Predictable context ID reuses cached FROST nonce seed across distinct MuSig confirmation signings, enabling secret key share recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The DKG-confirmation MuSig signing protocol deterministically derives the FROST preprocess (and therefore the signing nonces `d`, `e`) from a cached 32-byte seed stored under a context identifier of only `(b"DkgConfirmer", attempt)`. This identifier is small, predictable, and omits the validator set / genesis / participants / message. Whenever `share_internal` is executed twice under the same context encoding with different signing inputs (different `key_pair` message or different participant preprocessing set), the same nonce seed is reused. An attacker who supplies identical preprocess commitments in both sessions makes the binding factor `rho` identical, so subtracting the two published signature shares isolates and reveals the victim's MuSig secret share — the root-of-trust validator key.

### Finding Description
`preprocess_internal` in `SigningProtocol` caches the FROST preprocess seed in `CachedPreprocesses`, keyed solely by `self.context.encode()`:

- DB definition: `CachedPreprocesses: (context: &impl Encode) -> [u8; 32]` at `coordinator/src/tributary/signing_protocol.rs:86-90`.
- Context construction: `let context = (b"DkgConfirmer", self.attempt);` at `coordinator/src/tributary/signing_protocol.rs:275` — a static 12-byte tag plus a `u32` attempt counter. It does not include `self.spec.genesis()`, the validator set, the `removed` set, the `key_pair`, or any hash of the message/preprocesses.
- Reuse path: if `CachedPreprocesses::get` returns a value, it is decrypted and passed to `AlgorithmSignMachine::from_cache`, which re-derives the identical nonces via `ChaCha20Rng::from_seed(*seed.0)` in `seeded_preprocess` (`crypto/frost/src/sign.rs:121-144`). The FROST spec in `spec/cryptography/FROST.md:51-55` explicitly states that reusing a preprocess "would enable a third-party to recover your private key share."
- Triggering paths: `DkgConfirmer::share` (called from `generated_key_pair`, `coordinator/src/tributary/handle.rs:47-60`) signs `set_keys_message(set, removed, key_pair)`. If `generated_key_pair` runs again for the same attempt with a different `key_pair` (the `DkgKeyPair::set` at `handle.rs:54` unconditionally overwrites the stored pair), `share_internal` runs a second time under the identical context with a different `msg` and the same nonces. Likewise, because the context is not bound to the genesis/set, the same validator key participating in a confirmation for a different `TributarySpec` with the same `attempt` reuses the identical nonce seed while `musig_context`/`participants` differ.
- Exploitation: the attacker submits the same preprocess bytes in both sessions (preprocesses are supplied per-participant via `ConfirmationNonces`/`DkgShares` in `handle.rs:320-459`), keeping the FROST binding factor `rho` identical. With `z_i = d + e·rho + λ·s·c_i`, `z_1 - z_2 = λ·s·(c_1 - c_2)`, yielding the validator's MuSig secret share `s`.

### Impact Explanation
The victim's secret share is the coordinator/validator's long-lived MuSig key — the "root of trust" per the file header comment (`signing_protocol.rs:1-9`). Recovery of it lets the attacker forge the validator's participation in `DkgConfirmed`, `SubstrateSign`, `Sign`, `SlashReport`, and `RemoveParticipantDueToDkg` flows, i.e., forge `set_keys`/batch confirmations and impersonate the validator in all future tributary signing. This is concrete key share recovery, not a theoretical weakness.

### Likelihood Explanation
The nonce seed is 32 bytes, but the *identifier* deciding reuse is a `(static tag, u32)` tuple. Reuse requires two `share_internal` executions under the same context with attacker-influenced inputs, which occurs when `generated_key_pair` is re-invoked for an attempt (the DB write is unconditional and overwriteable) or when the same validator key confirms across validator sets sharing an attempt number (the context omits genesis/set binding). An attacker participates legitimately in the DKG and controls only published preprocess bytes — a public input. The code's own header notes the safety of this design rests entirely on the received messages never differing under a context (`signing_protocol.rs:25-54`), an assumption the code does not enforce for the `key_pair`/msg input.

### Recommendation
Bind the cache key to everything that defines the signing session: include `spec.genesis()` (or the `ExternalValidatorSet`), the sorted `participants`/`removed` set, and a hash of the `key_pair`/message in `context` (e.g., `context = (b"DkgConfirmer", genesis, attempt, Blake2s256(participants || msg))`). Additionally, before calling `machine.sign`, verify the commitments derived from the cached seed match the preprocess already published for this context (the file's own TODO at `signing_protocol.rs:50-54`), and refuse to produce a second share if the `(preprocesses, msg)` pair differs from the first invocation under a given context.

### Proof of Concept
1. Validator `V` (the coordinator's key) participates in a DKG confirmation for `attempt = a`. An attacker `A` (a fellow participant) publishes their `DkgShares`/`confirmation_nonces` for the attempt; `ConfirmationNonces` is fixed at `handle.rs:417`.
2. `generated_key_pair` runs: `DkgConfirmer::share` → `share_internal` → `preprocess_internal` loads/sets `CachedPreprocesses[(b"DkgConfirmer", a)]` and signs `msg_1 = set_keys_message(set, removed, kp_1)`, publishing share `z_1`.
3. `A` causes `generated_key_pair` to execute again for the same `attempt` with a distinct `key_pair kp_2` (the `DkgKeyPair::set`/`KeyToDkgAttempt::set` overwrite path in `handle.rs:54-55` permits re-registration), or equivalently `V` confirms a different validator set at the same `attempt` number since `context` lacks genesis/set binding.
4. `preprocess_internal` hits the cache (`signing_protocol.rs:123-145`); `seeded_preprocess` regenerates identical nonces `d`, `e` (`crypto/frost/src/sign.rs:127-133`). `A` submits the same preprocess bytes, so `rho` is identical; `msg_2 ≠ msg_1` so `c_1 ≠ c_2`.
5. `A` collects `z_1, z_2` and computes `s = (z_1 - z_2) / (λ·(c_1 - c_2))` mod `l`, recovering `V`'s MuSig secret share, then forges `V`'s signature shares in subsequent confirmation/signing protocols.
