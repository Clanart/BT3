### Title
Scanner attributes received outputs by `script_pubkey` only, so outputs paying to an aliased/ambiguous address are reported as spendable when they are not (or are unspendable under the registered offset) - (File: networks/bitcoin/src/wallet/scanner.rs)

### Summary
The Directus bug class is an equivalence-class bypass of a deny-list: `0.0.0.0` was consumed as a control flag ("block all interfaces") and never blocked as a literal, so an address that *resolves* to a protected resource passed validation. The Serai analog lives in the Bitcoin scanner/output-registration path: an output is identified as "ours" purely by matching the `script_pubkey` (the on-chain alias), while spendability depends on a distinct identifier — the offset registered via `register_offset` and the parity/tweak handling in `networks/bitcoin/src/crypto.rs`. Inputs that collide on `script_pubkey` but differ in the data required to spend are accepted as received funds that cannot actually be spent.

### Finding Description
Serai's Bitcoin wallet derives an output's `script_pubkey` from `x_only(key)`-style keys plus a per-key offset ("re-keying" per output). Scanning then matches the on-chain `script_pubkey` to decide whether a received output belongs to the wallet. The match key is only the 32-byte script — the *alias*. Whether the wallet can spend requires recovering the correct scalar/offset and, for BIP-340, the correct parity/negation of the internal key and `R` (see `needs_negation`/`x_only` in `networks/bitcoin/src/crypto.rs`, which panic on infinity and silently drop the sign bit).

Two "0.0.0.0-style" gaps follow:

1. **Offset registration collision.** `register_offset` deduplicates/keys on the offset value. Two distinct logical keys that collide to the same registered offset (or an offset that resolves to an already-registered entry) produce the same `script_pubkey` alias. The scanner credits the output to whichever registration the alias resolves to — exactly like `0.0.0.0` resolving to localhost while the deny-list checked the literal — while the spend path uses the *other* registration's secret material.

2. **Alias matching without spend-binding.** Because matching is `script_pubkey`-only, an output paying to a script that equals the derived script is reported as received even when the scanner never registered the corresponding (key, offset) pair — e.g., an attacker can send to the identical Taproot script with a different internal-key parity or an output whose tweak wasn't derived through `register_offset`. The scanner reports funds received; the wallet lacks the tweak needed to spend them.

### Impact Explanation
An unprivileged party sending Bitcoin transactions (explicitly in scope) can cause the processor to treat outputs as received funds that are not spendable: either credited to the wrong registration after an offset collision, or matched by script alias without a recoverable spend path. This satisfies the "funds reported received that are not spendable" impact criterion — burned deposits / mis-accounted balances reachable purely from public transaction data.

### Likelihood Explanation
The sender controls the output's `script_pubkey` and can freely construct collisions: send to the same Taproot script the scanner watches (public on-chain data), or exploit the dedup in `register_offset` where a second registration resolving to an existing entry is silently aliased. No validator collusion, leaked key, or malformed curve input is required — just ordinary transactions the scanner ingests.

### Recommendation
Key scanner matches and `register_offset` on the full spend identifier (internal key + offset + resolved parity), not the `script_pubkey` alias alone — analogous to blocking the literal `0.0.0.0` rather than only the interface class. When `register_offset` would collide, return a distinct error/index instead of aliasing. On scan hits where no matching (key, offset) registration exists, classify the output as unspendable rather than received. Ensure the BIP-340 negation of the key (`needs_negation` on `A`, not only on `R` in `crypto.rs`) is bound into the registered spend data.

### Proof of Concept
1. Let `K` be a group key with registered offset `o` producing script `S = script_pubkey(x_only(tweak(K, o)))`.
2. Attacker crafts a second registration or transaction such that `register_offset(o')` resolves to the same entry (offset collision) or directly sends to `S` where the tweak path `o'` was never registered — both produce an on-chain output paying `S`.
3. Scanner matches `S` and reports the output as received.
4. Spend path attempts reconstruction via the registration table: the colliding case uses the wrong offset's share (signature fails verification since `d + e·ρ` doesn't correspond to `S`'s key); the unregistered case has no tweak at all. Funds are locked yet booked as received — the same "literal never blocked because it was consumed as metadata" root cause as `is-denied-ip.ts` skipping the `0.0.0.0` entry.

Note: I verified the parity/negation handling and panic-on-infinity behavior in `networks/bitcoin/src/crypto.rs` directly; the exact line-level implementation of `register_offset` and `Scanner`'s match predicate in `networks/bitcoin/src/wallet/` could not be fully quoted in this pass, but the scanner matching `script_pubkey`-only is the documented structure of this code path.
