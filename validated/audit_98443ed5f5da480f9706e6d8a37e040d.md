### Title
Unchecked "length precedes data" pointer arithmetic in CPI account-length update allows aliased/out-of-bounds VM memory write - (File: `program-runtime/src/cpi.rs`)

### Summary
`update_caller_account()` in `program-runtime/src/cpi.rs` assumes that the 8-byte length field of a serialized account always lives exactly at `vm_data_addr - size_of::<u64>()`, and blindly writes to that computed address without validating that `vm_data_addr` still points at the true, VM-runtime-controlled data pointer. This mirrors the reported bug class: treating a caller-controlled pointer as if it always retains a fixed structural relationship to an adjacent header/length field, when in fact a program can move the underlying pointer, breaking that assumption.

### Finding Description
`CallerAccount::vm_data_addr` is derived from the untrusted, program-controlled `AccountInfo::data` slice pointer inside VM memory [1](#0-0) . After CPI returns, `update_caller_account()` computes the address of the serialized length field like so:

```rust
let serialized_len_ptr = translate_type_mut_for_cpi::<u64>(
    memory_mapping,
    caller_account
        .vm_data_addr
        .saturating_sub(std::mem::size_of::<u64>() as u64),
    check_aligned,
)?;
*serialized_len_ptr = post_len as u64;
``` [2](#0-1) 

This is only sound if `vm_data_addr` still equals the original serialization address, i.e. the length field is guaranteed to be immediately before the data by the serializer layout established in `serialize_parameters_for_abiv1`/`Serializer::write_account` [3](#0-2) . However, `vm_data_addr` is read from the caller's `AccountInfo.data` pointer as stored in VM memory, which a BPF program can move at will (e.g., by writing a new slice pointer into the `RefCell`/`Rc` backing the `AccountInfo::data` field). The code that would prevent this, `check_account_info_pointer()` comparing `data.as_ptr()` against `account_metadata.vm_data_addr`, is only invoked when the `syscall_parameter_address_restrictions` feature is active [4](#0-3) . The function's own doc comment acknowledges this precondition: "Safety: Once `syscall_parameter_address_restrictions` is enabled all fields of [CallerAccount] used in this function should never point inside the address space reserved for accounts" [5](#0-4) , implying that before/without that feature the invariant does not hold.

This is precisely the pattern in the external report: code assumes a length header is a fixed number of bytes before a data pointer that is not guaranteed to still point at the "beginning" of the original structure, because it can be a caller-manipulated/aliased pointer rather than one freshly produced by the trusted encoder. The Agave test harness itself demonstrates this exact class of manipulation, moving the account data pointer past a header before triggering CPI so that "CPI now will update the serialized length in the wrong place" [6](#0-5) , and the accompanying test flag (`TEST_FORBID_LEN_UPDATE_AFTER_OWNERSHIP_CHANGE_MOVING_DATA_POINTER`) is exercised with `syscall_parameter_address_restrictions` both enabled and disabled in `programs/sbf/tests/programs.rs` [7](#0-6) .

### Impact Explanation
When `syscall_parameter_address_restrictions` is not active for a given cluster/epoch, an unprivileged BPF program invoked via CPI can move its own `AccountInfo::data` pointer to an arbitrary VM address (still within the account's serialized parameter region, but not at the offset the address-restriction feature otherwise pins it to). On CPI return, `update_caller_account()` will compute `vm_data_addr - 8` from this attacker-chosen address and perform an unchecked 8-byte write (`*serialized_len_ptr = post_len as u64`) there. This can corrupt adjacent serialized fields (e.g., another account's owner/lamports/length, or the boundary between accounts) within the VM input region, i.e., a concrete aliased/out-of-bounds-relative-to-intended-target memory write reachable purely from within the SBF VM by a hostile but unprivileged program during CPI.

### Likelihood Explanation
The primitive requires only writing to one's own `AccountInfo::data` RefCell/pointer field (ordinary safe/unsafe Rust operations available to any on-chain BPF program) and issuing a CPI that changes the account's data length (e.g., via `realloc`). It requires operating on a cluster/epoch where `syscall_parameter_address_restrictions` has not yet been activated, since that feature's `check_account_info_pointer` check is what currently prevents this pointer manipulation.

### Recommendation
Do not derive the location of the serialized length field via pointer arithmetic on a program-supplied pointer. Instead, always resolve the length field via metadata computed at serialization time (e.g., `SerializedAccountMetadata`), or unconditionally validate `vm_data_addr` against the expected serialized address (as is currently done only under the `syscall_parameter_address_restrictions` feature) regardless of feature-gate state, and reject CPI-account updates when the addresses diverge.

### Proof of Concept
The existing regression test `TEST_FORBID_LEN_UPDATE_AFTER_OWNERSHIP_CHANGE_MOVING_DATA_POINTER` already demonstrates the mechanics: it writes a fabricated `RcBox<RefCell<&mut [u8]>>` into account data and points the account's `data` slice past this header, then invokes a program that reallocs the account, exercising exactly the "CPI updates the serialized length in the wrong place" condition [8](#0-7) . Running this scenario with `syscall_parameter_address_restrictions` (and its dependent `virtual_address_space_adjustments`/`account_data_direct_mapping`) deactivated, as parameterized in `test_account_info_in_account` [7](#0-6) , reaches the vulnerable `caller_account.vm_data_addr.saturating_sub(8)` write path without the pointer-authenticity check.
