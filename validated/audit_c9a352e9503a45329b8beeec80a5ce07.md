### Title
Unauthorized CAT-to-CR-CAT Wallet Conversion via Colliding Tail Hash — Attacker-Controlled `authorized_providers` Adoption Without Scope Validation - ([File: chia/wallet/cat_wallet/cat_wallet.py])

### Summary
`CATWallet.identify()` matches incoming coins to an existing local `CATWallet` purely by `tail_program_hash` (the CAT "asset id"). When the incoming coin is wrapped in a Credential-Restricted CAT (CR-CAT) layer and its `tail_program_hash` collides with an asset id the wallet already tracks as a plain `CATWallet`, the code unconditionally calls `CRCATWallet.convert_to_cr()`, which mutates the existing wallet record in place, adopting the attacker-supplied `authorized_providers` and `proofs_checker` from that single incoming coin — with no verification that the sender is the legitimate issuer/authority for that asset id.

### Finding Description
In `chia/wallet/cat_wallet/cat_wallet.py`, `identify()` uncurries an incoming coin's parent spend and, if it detects a CR-CAT layer, searches the wallet's existing `CATWallet` entries for one whose `limitations_program_hash` equals the new coin's `tail_program_hash`: [1](#0-0) 

If found, it directly calls `CRCATWallet.convert_to_cr(found_cat_wallet, crcat.authorized_providers, ProofsChecker.from_program(...))` using values taken entirely from the untrusted incoming coin/spend, with **no check** that:
- the wallet already holds real, unrestricted CAT coins of that asset id,
- the sender/source is authorized to define a credential-restriction policy for that asset id, or
- the user consented to this change.

`CRCATWallet.convert_to_cr()` then overwrites the wallet's persisted `WalletInfo` in place, changing its `WalletType` from `CAT` to `CRCAT` and replacing the wallet's trust anchor (`authorized_providers`, `proofs_checker`) with attacker-chosen values, without any guard on pre-existing balance: [2](#0-1) 

This is directly analogous to the CVE-2026-72534 bug class: an identity (`tail_program_hash`, the CAT "group name") received from a lower-privileged, source-scoped input is used to "adopt" an existing higher-trust object (the user's established `CATWallet`) and overwrite its authorization/membership data (`authorized_providers`) without validating that the incoming source is scoped/authorized to modify that specific target.

Note that the sibling `RCATWallet.convert_to_revocable()` path does guard against this by refusing conversion when `cat_wallet.lineage_store` is non-empty: [3](#0-2) 

but the CR-CAT conversion path has no equivalent check, showing the guard was known to be necessary for this class of mutation yet omitted here.

### Impact Explanation
Any counterparty can trigger this by sending the victim wallet a tiny CR-CAT coin whose `tail_program_hash` matches an asset id the victim already holds as a normal (unrestricted) CAT — e.g. a widely used token from `DEFAULT_CATS`. This requires no cooperation beyond a standard coin send/hint to the victim's puzzle hash, which is reachable through ordinary wallet sync (`determine_coin_type` → `CATWallet.identify`). Once triggered:
- The victim's local wallet entry for that asset id is silently converted to `WalletType.CRCAT`, with `authorized_providers` set to values chosen by the attacker.
- Because the wallet is a local state-management structure that gates spend construction (VC lookup, proof-of-inclusion requirements) for coins of that asset id, this corrupts the wallet's ability to correctly construct/authorize spends for the user's own pre-existing, unrestricted CAT coins of that asset id — a spend-triggered transaction-processing halt/denial-of-service on the user's legitimate holdings, and it plants attacker-controlled "authority" metadata governing how the wallet will treat future spends of that asset.

This matches the accepted impact categories: forged asset/authorization identity adoption and a spend-triggered transaction-processing halt.

### Likelihood Explanation
High reachability: triggered purely by receiving a coin (a normal wallet-sync event), requiring only that the attacker mint/send a CR-CAT coin with a `tail_program_hash` colliding with an asset id already tracked by the victim. No signature, ownership proof, or opt-in configuration (unlike `automatically_add_unknown_cats`) gates this specific conversion branch — the check occurs before that configuration gate is consulted.

### Recommendation
- Do not allow `identify()` to silently convert an existing `CATWallet`/`RCATWallet` to `CRCATWallet` based solely on a `tail_program_hash` match. Require explicit user confirmation, or at minimum apply the same non-empty-lineage guard used in `RCATWallet.convert_to_revocable()` to `CRCATWallet.convert_to_cr()`, refusing conversion when the wallet already holds coins for that asset id.
- Store/validate a first-seen or user-approved `authorized_providers`/`proofs_checker` binding per asset id, and reject/ignore incoming coins that attempt to redefine it later without explicit reauthorization.

### Proof of Concept
1. Victim wallet already holds a normal CAT (via `CATWallet.get_or_create_wallet_for_cat`) for asset id `X` (e.g. a `DEFAULT_CATS` entry) with real spendable balance.
2. Attacker mints a CR-CAT with tail hash `X` (same `limitations_program_hash`), setting `authorized_providers = [attacker_provider]` and an arbitrary `proofs_checker`, using the standard CR-CAT eve-spend/remark pattern shown in `chia/_tests/wallet/vc_wallet/test_vc_wallet.py::mint_cr_cat`.
3. Attacker sends/creates this CR-CAT coin hinted to the victim's own puzzle hash (a normal coin creation, reachable from any wallet).
4. Victim's wallet syncs the coin; `WalletStateManager.determine_coin_type` → `CATWallet.identify` detects the CR layer, finds the victim's existing plain `CATWallet` for asset id `X`, and calls `CRCATWallet.convert_to_cr(found_cat_wallet, [attacker_provider], attacker_proofs_checker)` — matching `chia/_tests/wallet/vc_wallet/test_vc_wallet.py::test_cat_wallet_conversion`, which already demonstrates this exact conversion path succeeding, but without demonstrating (or checking for) prior existing balance/ownership validation.
5. The victim's wallet entry for asset id `X` is now type `CRCAT` governed by the attacker's `authorized_providers`, corrupting future spend construction for the victim's pre-existing coins of that asset id.

    async def convert_to_cr(
        cls,
        cat_wallet: CATWallet,
        authorized_providers: list[bytes32],
        proofs_checker: ProofsChecker,
    ) -> None:
        replace_self = cls()
        replace_self.standard_wallet = cat_wallet.standard_wallet
        replace_self.log = logging.getLogger(cat_wallet.get_name())
        replace_self.log.info(f"Converting CAT wallet {cat_wallet.id()} to CR-CAT wallet")
        replace_self.wallet_state_manager = cat_wallet.wallet_state_manager
        replace_self.info = CRCATInfo(
            cat_wallet.cat_info.limitations_program_hash, None, authorized_providers, proofs_checker
        )
        await cat_wallet.wallet_state_manager.user_store.update_wallet(
            WalletInfo(
                cat_wallet.id(), cat_wallet.get_name(), uint8(WalletType.CRCAT.value), bytes(replace_self.info).hex()
            )
        )
        updated_wallet_info = await cat_wallet.wallet_state_manager.user_store.get_wallet_by_id(cat_wallet.id())
        assert updated_wallet_info is not None
        replace_self.wallet_info = updated_wallet_info
        replace_self.tail_hash = replace_self.info.limitations_program_hash

        cat_wallet.wallet_state_manager.wallets[cat_wallet.id()] = replace_self
