## Analysis

The Debita report's core primitive — an unprivileged actor fragmenting a single legitimate position into many tiny units, with no minimum-size floor to stop it, causing the rightful owner to lose value they are entitled to — has a direct local analog in `pallet-bandwidth`'s FIFO subscription eviction, paired with `BandwidthManager.sol`'s unauthenticated `chain`/`app` targeting.

### Title
Unprivileged bandwidth-purchase spam can evict a victim's paid, unconsumed subscriptions via unbounded tiny purchases - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`BandwidthManager.purchase()` lets **any caller** credit **any** `(app_chain, app)` pair by supplying arbitrary `chain`/`app` bytes that are never checked against `msg.sender` or the actual source chain. On the pallet side, `push_subscription` appends every credited purchase to a FIFO list capped at `MAX_SUBSCRIPTIONS` (1024), evicting the oldest entry once full — regardless of how much unconsumed `remaining_bytes` that entry holds. Because there is no minimum purchase size/frequency and no relationship required between payer and beneficiary, an attacker can cheaply spam the smallest configured tier against a victim app's key, filling the FIFO with worthless entries and evicting the victim's legitimately-paid, larger/longer subscriptions before the victim ever gets to consume them.

### Finding Description
`purchase()` in `evm/src/apps/BandwidthManager.sol` only validates that `app`/`chain` are non-empty and `months > 0`; it does not tie `app`/`chain` to the caller in any way [1](#0-0) . The pallet keys the allowance ledger by `(app_chain, app)` taken straight from the message body, independent of `request.source` — this is the documented "sponsorship" feature [2](#0-1) , and the docs explicitly confirm `chain` "is not validated against the source chain" [3](#0-2) .

`push_subscription` appends every credited purchase to a `BoundedVec` capped at `MAX_SUBSCRIPTIONS`; once full, it unconditionally evicts index 0 (the oldest entry) — irrespective of how many bytes remain unconsumed on it — and only emits an audit event: `SubscriptionEvicted`: [4](#0-3) 

There is no per-purchase minimum size, no rate limit, and no restriction that only the credited app (or its owner) may add entries to its own queue. Any account holding the cheapest configured tier's fee-token cost can call `purchase(victimApp, cheapTier, 1, victimChain)` repeatedly and cheaply, since months and tier are entirely attacker-chosen and unrelated to the victim's own purchase history.

### Impact Explanation
This directly reproduces the "no minimum size" griefing primitive from the seed report, but with a genuine fund-loss outcome rather than pure gas griefing: a victim app that has already paid for a large/long-duration bandwidth tier can have that paid allowance evicted and permanently lost (`lost_bytes` in `SubscriptionEvicted`) before it is ever drained by the gate, because an unprivileged attacker filled the shared FIFO with cheap junk subscriptions targeting the same `(app_chain, app)` key. This is a loss of funds/paid-for allowance moving away from "the rightful beneficiary" — the victim's IntentGateway, paymaster, or other app instance could be starved of bandwidth it already paid for, causing its ISMP requests to start reverting with `GateError::Insufficient`/`NoAllowance` [5](#0-4) , effectively bricking cross-chain functionality for a paying customer.

### Likelihood Explanation
No privileged role, relayer, or governance action is required — `purchase()` is a fully public entrypoint, and the attacker only needs enough fee tokens to buy the cheapest configured tier (`TierOne`) many times over. Because the FIFO cap is a fixed 1024 and eviction is unconditional on overflow, the attack is deterministic and cheap relative to the value of the bandwidth being destroyed, especially against apps whose owners bought high-tier, long-duration subscriptions expecting them to be consumed gradually.

### Recommendation
- Restrict who may credit a given `(app_chain, app)` bucket (e.g., require `msg.sender == app` unless an explicit sponsorship allowlist entry exists), or
- Change eviction policy to prefer evicting the *caller's own* prior low-value entries rather than blindly popping index 0 regardless of payer, or
- Enforce a minimum tier price/size and/or per-payer rate limiting on `purchase()` so an attacker cannot cheaply flood an unrelated app's queue, and emit a way to reject a purchase that would evict another payer's unconsumed subscription.

### Proof of Concept
1. Governance configures `TierOne` with a small `(bytes, duration_secs)` and a low price on `BandwidthManager.sol`.
2. Victim (e.g., an `IntentGateway` instance) legitimately calls `purchase(victimApp, TierFour, 12, victimChain)`, crediting a large, long-lived subscription.
3. Attacker, with no relationship to `victimApp`, repeatedly calls `manager.purchase(victimApp, TierOne, 1, victimChain)` from any account, each time paying only `tierPrice[TierOne]`.
4. Each purchase credits `Allowance::<T>::mutate(victimChain, victimApp, ...)` per `on_accept` [6](#0-5) , appending to the same FIFO the victim's entry lives in.
5. Once the list reaches 1024 entries, further attacker purchases evict the oldest entry via `push_subscription` [7](#0-6)  — after enough spam this reaches and evicts the victim's high-value `TierFour` subscription, which is emitted as `SubscriptionEvicted { lost_bytes }`, confirming the paid-for bandwidth is gone unused.

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

			let tier = TierIndex::try_from(msg.tier)

				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}

## Sponsoring Another Chain

The `chain` argument is **not validated against the source chain** — see [Overview → Sponsorship](/developers/evm/bandwidth/overview#sponsorship) for the model. A buyer on Ethereum credits an app on Base by passing the credit chain id in `chain`:

```solidity
manager.purchase({
    app:    abi.encodePacked(appAddressOnBase),
    tier:   2,
    months: 6,
    chain:  bytes("EVM-8453")
});
```

The pallet keys allowance storage on `(msg.chain, msg.app)`, so the credit lands on Base regardless of which chain sent the payment. The recommended pattern for teams running a central treasury is to deploy `BandwidthManager` on one low-fee chain and sponsor bandwidth for app instances elsewhere.
