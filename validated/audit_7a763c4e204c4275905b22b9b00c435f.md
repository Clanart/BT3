### Title
Payout OP_RETURN attribution is unauthenticated under `SIGHASH_SINGLE|ANYONECANPAY`, allowing hijack of operator reimbursement or permanent denial of an honest operator's reimbursement - (File: `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` signs the withdrawal input with `TapSighashType::SinglePlusAnyoneCanPay`, which per Bitcoin's Taproot sighash rules (`Prevouts::One`, used in `calculate_pubkey_spend_sighash`, `core/src/builder/transaction/txhandler.rs`) only commits to input 0 and output 0. The OP_RETURN output that names the reimbursed operator (`op_return_txout(operator_xonly_pk.serialize())`) is output index 2 and is never covered by the withdrawer's signature, so any unprivileged party who observes the public `WithdrawParams` on Citrea can build and broadcast a competing payout transaction with an arbitrary or missing OP_RETURN, funding only the fee. `Verifier::update_finalized_payouts` then blindly trusts whatever OP_RETURN is mined and writes it into `withdrawals.payout_payer_operator_xonly_pk`.

### Finding Description
The broken binding is:
`withdrawals.payout_payer_operator_xonly_pk` (written by `Verifier::update_finalized_payouts`, `core/src/verifier.rs:2283-2353`) == the xonly_pk of the party whose own BTC actually funded output[0] of the mined payout transaction.

Trace:
1. `Operator::withdraw` (`core/src/operator.rs:560-637`) builds the payout tx via `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`), which has exactly one signed input (`SpendPath::KeySpend`, `NormalSignatureKind::NotStored`) with the user's pre-supplied `taproot::Signature` set via `set_p2tr_key_spend_witness`, and three outputs: [0] user payout, [1] anchor, [2] `op_return_txout(operator_xonly_pk)`.
2. The user's signature is verified against `sighash = payout_txhandler.calculate_sighash_txin(0, in_signature.sighash_type)` (`core/src/operator.rs:630-637`), which for `SinglePlusAnyoneCanPay` commits only to input 0 and output 0 (`Prevouts::One` semantics used in `TxHandler::calculate_pubkey_spend_sighash`, `core/src/builder/transaction/txhandler.rs`). This is intentional so operators can add fee-funding inputs, but it also lets *anyone* add fee inputs and rewrite outputs 1 and 2 freely - the OP_RETURN naming the reimbursed operator is not authenticated by the withdrawer at all.
3. `WithdrawParams` (`withdrawal_id`, `input_signature`, `input_outpoint`, `output_script_pubkey`, `output_amount`) is fully public once submitted to Citrea's Bridge contract. An unprivileged attacker can reconstruct the identical transaction skeleton, add only a fee input, and choose an arbitrary or absent OP_RETURN at output 2, then broadcast and race the honest operator's identical (input,output[0])-matching transaction.
4. `bitcoin_syncer`/`Verifier::update_finalized_payouts` (`core/src/verifier.rs:2299-2343`) finds whichever payout tx is actually mined for that withdrawal idx, extracts `operator_xonly_pk` via `get_first_op_return_output`/`parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:608-617,686-692`) with no cross-check against who funded the fee input, and calls `Database::update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`), which unconditionally overwrites `payout_payer_operator_xonly_pk` for that idx.
5. Downstream, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`) and `Operator::send_asserts` (`core/src/operator.rs:1275-1295`) both gate the reimbursement path solely on `payout_op_xonly_pk == kickoff_data.operator_xonly_pk` read from this corrupted DB column - neither verifies that the named operator's own BTC funded the payout.

Consequence: whoever wins the race to have their OP_RETURN mined controls attribution:
- If the attacker names a legitimate registered operator's xonly_pk in the OP_RETURN (chosen arbitrarily, e.g. to collude or to grief), that named operator's later kickoff with `kickoff_data.operator_xonly_pk` matching the corrupted value passes `is_kickoff_malicious` and `send_asserts`'s equality check, letting them claim `create_reimburse_txhandler`'s `bridge_amount` output despite never having funded the payout (attacker only paid the fee, the withdrawal value itself came from the pre-signed input, not the named operator).
- If instead the attacker's transaction wins the race against the genuine operator's identical broadcast (both consuming the same `input_outpoint`), the honest operator's payout tx is double-spent out of the mempool/rejected, and the DB is left with a wrong or `NULL` `payout_payer_operator_xonly_pk`. The honest operator can never again submit a matching kickoff (`send_asserts` errors "Payout operator xonly pk does not match kickoff operator xonly pk") and is flagged malicious if it tries (`is_kickoff_malicious` returns `true`), permanently losing the ability to be reimbursed for BTC they already fronted.

None of the existing guards catch this: `SECP.verify_schnorr` only validates the withdrawer's signature over input 0/output 0 (which is untouched by the attack); `Verifier::is_deposit_valid`, `only_aggregator_and_self`, `verify_storage_proofs`, `SPV::verify` and `lc_proof_verifier` validate deposit/withdrawal/L1-inclusion facts unrelated to who funded the fee input; `is_kickoff_malicious` only compares two attacker-influenced/attacker-controllable values against each other, not against ground truth of BTC flow.

### Impact Explanation
- Wrong-party reimbursement: an operator who never fronted the withdrawal can be credited `bridge_amount` via `create_reimburse_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:341-385`), i.e. BTC moves out of the operator-reimbursement path to a party that did not fund the payout - a "false claim proved by the bridge circuit" / "operator reimbursed for a payout it never funded" (Critical).
- Denial of reimbursement: the genuine funding operator's UTXO is consumed by the attacker's competing broadcast, and the corrupted/`NULL` `payout_payer_operator_xonly_pk` makes that operator's kickoff permanently rejected as malicious (Critical: "honest operator permanently unable to be reimbursed").
- Repeatable per withdrawal, and the attacker only needs to observe public Citrea `withdraw` calls and pay Bitcoin transaction fees, so the blast radius covers every standard (non-optimistic) withdrawal handled by any operator across all deposits.

### Likelihood Explanation
Preconditions match a normal operational scenario: a valid withdrawal registered on Citrea and not yet fronted. The attacker needs only: (1) ability to read `WithdrawParams` from the public Citrea Bridge contract event/state, (2) enough BTC to pay the transaction fee (no bridge_amount required, since output[0] value/script are copied verbatim from the legitimate params and covered by the pre-existing `input_outpoint` value), and (3) the ability to broadcast to Bitcoin, all of which are within the stated unprivileged-attacker capabilities. Winning the race against the operator's own broadcast is plausible since the operator also waits on `fund_raw_transaction`/fee-rate lookups (`core/src/operator.rs:639-673`) before broadcasting, giving an attentive attacker a window. This is highly repeatable across withdrawals with low, predictable cost (one transaction fee per attempt).

### Recommendation
Bind the OP_RETURN (and any other outputs beyond output 0) to the withdrawer's authorization, or authenticate operator attribution independently of the payout transaction's raw contents:
- Change the withdrawer signature to cover all outputs (e.g. use `TapSighashType::Single` combined with a covenant/anchor that pins output count/order, or have the withdrawer co-sign a commitment to the specific operator's xonly_pk as part of the off-chain protocol before publishing `WithdrawParams`), so a third party cannot rewrite outputs 1/2.
- Alternatively, require the fee-funding party (the actual claimed operator) to additionally sign an out-of-band commitment (e.g. via aggregator/verifier-witnessed attestation) that is checked against the mined payout tx before `update_payout_txs_and_payer_operator_xonly_pk` accepts an attribution, and treat a first-seen wrong/foreign attribution as reason to allow the genuine operator to publish a corrective, verifier-attested override rather than being permanently locked out.
- At minimum, have `is_kickoff_malicious`/`send_asserts` cross-check that the funding input(s) of the mined payout transaction (beyond input 0) are controlled by the operator named in the OP_RETURN, rather than trusting the OP_RETURN bytes alone.
