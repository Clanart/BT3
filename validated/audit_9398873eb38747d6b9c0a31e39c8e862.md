## Analysis

The external report's core invariant is: **a reward that should be attributed to the party who performed specific work gets attributed to a different party because the crediting logic uses a coarse/wrong identity signal instead of binding the reward to the specific unit of work it was for.** The Hyperbridge equivalent is not the front-run of a public tx — it's a batch-attribution bug in `pallet-consensus-incentives`. [1](#0-0) computes the relayer to reward by reading only `messages.get(0)` — the **first** message in the executed batch — and recovering its signer, then pays that single signer for **every** `StateMachineUpdated` event collapsed across the **entire batch**, regardless of which message actually produced it. [2](#0-1) transfers `reward` from the treasury to whatever `relayer_account` was derived, for each state machine height advance in the batch.

Since ISMP consensus proofs are explicitly public/freely obtainable (`docs/content/developers/explore/nexus/relayer.mdx:8` states "these proofs can be generated by anyone, as they are freely provided by its connected chains"), any unprivileged actor can copy an honest relayer's legitimate `ConsensusMessage` for chain Y, prepend their own cheap self-signed `ConsensusMessage` (for the same or a different tracked chain) as element 0, and submit the combined batch via the normal message-handling path. `on_executed` then pays the *attacker's* account for both state-machine advances, including the one whose underlying proof-fetching work belonged to chain Y's honest relayer.

### Title
Batch reward misattribution in `pallet-consensus-incentives` pays the first message's signer for every state machine update in the batch - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`FeeHandler::on_executed` derives the reward recipient from only the first `Message::Consensus` in an executed batch, but distributes rewards for **all** `StateMachineUpdated` events produced by the batch, including those generated by other, unrelated `ConsensusMessage`s in the same batch signed by different relayers.

### Finding Description
`on_executed` ( [3](#0-2) ) extracts `maybe_relayer_account` exclusively from `messages.get(0)`. It then iterates `events` — collected from the whole batch, not scoped to message 0 — and calls `process_message` once per distinct state machine with the single `relayer_account` derived from message 0 ( [4](#0-3) ). `process_message` then unconditionally transfers treasury funds and mints reputation to that one account ( [5](#0-4) ).

There is no per-event/per-message binding: the pallet never checks that `state_machine_id` in a given event actually corresponds to the consensus message signed by `relayer_account`. Any batch containing more than one `Message::Consensus` entry (which is a normal, permissionless occurrence — consensus proofs are public data anyone may resubmit) collapses attribution onto whichever message happens to sit at index 0.

### Impact Explanation
This is a wrong-beneficiary fund-movement bug: treasury-funded `RelayerRewarded` payouts and reputation mints (an asset with on-chain economic/governance value) go to an account that did not do the work for some or all of the rewarded state-machine advances. An attacker can systematically siphon consensus-incentive rewards away from the relayers who actually produced/delivered the corresponding proofs, by bundling their own trivial signed `ConsensusMessage` ahead of others in a submitted batch.

### Likelihood Explanation
No privileged role, malicious relayer collusion, or front-running of someone else's pending transaction is required — the attacker only needs to submit a batch (a normal, permissionless `pallet-ismp` message-handling call) that places their own signed consensus message first and packs in a second, publicly-obtainable `ConsensusMessage` whose proof they merely copied. Given that "proofs ... are freely provided by its connected chains" is the documented design assumption, constructing such a batch is straightforward and repeatable.

### Recommendation
Track the relayer/signer per individual `Message::Consensus` entry rather than only `messages[0]`, and pair each `StateMachineUpdated` event with the specific message (and its recovered signer) that produced it — e.g., by correlating event order/`state_machine_id` back to the emitting message index — before crediting the reward, instead of collapsing the whole batch onto one account.

### Proof of Concept
1. Honest relayer B publishes/broadcasts a valid `ConsensusMessage` proof advancing `StateMachine::Y` (public data by design).
2. Attacker A crafts their own trivially-signed `ConsensusMessage` for `StateMachine::X` (or a no-op-cost update) and places it as batch element `[0]`.
3. Attacker A appends B's copied `ConsensusMessage` for `Y` as batch element `[1]` and submits the combined `Vec<Message>` through the normal ISMP message-handling entrypoint.
4. Execution succeeds, emitting `StateMachineUpdated` for both `X` and `Y`.
5. `on_executed` recovers only A's signer from `messages[0]`, then calls `process_message` for both `X` and `Y`, paying A's account the treasury reward and reputation mint for **both** advances — including the one produced by B's proof.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
