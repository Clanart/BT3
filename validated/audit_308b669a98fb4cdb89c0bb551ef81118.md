### Title
Untrusted `ReceivedOutput` bytes allow arbitrary `offset` field manipulation, decoupling the claimed scalar offset from the output's `script_pubkey` - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes the `offset` scalar, the `TxOut`, and the `OutPoint` as three fully independent fields with no consistency check between them — the exact analog of the django-unicorn bug class (untrusted input directly setting internal state that is supposed to be constrained). The `offset` is treated as authoritative proof that `output.script_pubkey` locks funds to `key + offset*G`, yet `read` never verifies that relation.

### Finding Description
`ReceivedOutput` is defined in `networks/bitcoin/src/wallet/mod.rs:89-97` with a private `offset: Scalar` field. The only legitimate constructor path, `Scanner::scan_transaction` (`mod.rs:199-214`), computes the offset by looking up `output.script_pubkey` in the `scripts` map populated by `Scanner::new`/`register_offset` (`mod.rs:158-196`), so a legitimately constructed `ReceivedOutput` always satisfies `script_pubkey == p2tr(key + offset*G)`.

`ReceivedOutput::read` (`mod.rs:122-134`) bypasses this invariant entirely:

```rust
let offset = Secp256k1::read_F(r)?;            // arbitrary attacker scalar
output = TxOut::consensus_decode(&mut buf_r)?; // arbitrary script_pubkey
outpoint = OutPoint::consensus_decode(&mut buf_r)?;
Ok(ReceivedOutput { offset, output, outpoint })
```

There is no check that the deserialized `output.script_pubkey` equals `p2tr_script_buf(key + offset*G)` for any key the wallet controls — indeed `read` doesn't even take the group key as a parameter. The deserialized object is then consumed as if scanner-produced:

- `Output::key()` in `processor/src/networks/bitcoin.rs:112-122` computes `script_key − offset*G` and the scanner asserts `output.key() == key` of the multisig being scanned (`processor/src/multisigs/scanner.rs:562-563`). A manipulated offset silently re-attributes the output to a different effective key.
- `SignableTransaction`/`multisig` re-keys the FROST `ThresholdKeys` per input by `keys.offset(output.offset())` (consistent with `ThresholdKeys::offset` in `crypto/dkg/src/lib.rs:414-417` and the `offset` application to `included[0]`'s share in `view()`, `crypto/dkg/src/lib.rs:518-521`), so the produced signature is valid for `key + offset*G` — not for the key the `script_pubkey` actually locks to.

### Impact Explanation
An attacker who feeds crafted bytes to `ReceivedOutput::read` can cause funds to be reported as received that are not spendable under the claimed binding, in either direction:

1. **False credit**: supply a `TxOut` paying to an arbitrary `script_pubkey` together with `offset = script_key_xonly − group_key` — the output is accepted and `Output::key()` resolves to the group key, reporting a received balance that does not exist.
2. **Unspendable spend**: supply a real output locked to `group_key` (offset 0) but claim a nonzero `offset`. The signer produces a valid FROST signature for `group_key + offset*G`, which will not satisfy the Taproot key-path spend — the wallet believes it signed a spend, while the transaction is invalid or pays to a key nobody controls.

This is an integrity violation reachable purely from untrusted bytes, matching the accepted impact class of "funds reported received that are not spendable."

### Likelihood Explanation
Medium, mirroring the source advisory. `ReceivedOutput::read` is a serialization boundary: any path where output bytes cross a trust boundary (peer-supplied data, recovered/replayed state, IPC between components) becomes attacker-controllable. Exploitation requires no secret material — only the public group key, which is known to any depositor since it determines the deposit address — and no cooperation from honest validators. The cryptographic primitives themselves are sound; the flaw is purely missing validation at the deserialization boundary, same as `template_name` being writable via `syncInput`.

### Recommendation
Either:

- Change `ReceivedOutput::read` to take the expected group key (or the `Scanner`) and reject inputs where `p2tr_script_buf(key + offset*G) != output.script_pubkey`; or
- Serialize only `(output, outpoint)` and re-derive `offset` by re-scanning at read time, removing the attacker-controlled field entirely.

At minimum, `Output::read` in `processor/src/networks/bitcoin.rs:145-166` should re-validate `output.key()` against the multisig key it is being loaded under rather than trusting `assert_eq!` alone, which only fires in the scan loop.

### Proof of Concept
```rust
use k256::{ProjectivePoint, Scalar};
use bitcoin::{TxOut, OutPoint, Amount, ScriptBuf};
use bitcoin::hashes::Hash;
use bitcoin::secp256k1::XOnlyPublicKey;

// Attacker knows the multisig's public group key (it determines the deposit address)
let group_key: ProjectivePoint = /* known */;

// 1. Craft an output paying to an arbitrary attacker-chosen key
let attacker_scalar = Scalar::random(&mut OsRng);
let attacker_key = ProjectivePoint::GENERATOR * attacker_scalar;
// P2TR script for attacker_key (x-only, even-Y per p2tr_script_buf)
let fake_output = TxOut {
    value: Amount::from_sat(100_000),
    script_pubkey: p2tr_script_buf(attacker_key).unwrap(),
};

// 2. Set offset = attacker_key - group_key so Output::key() returns group_key
let offset_bytes: Scalar = /* scalar s.t. group_key + offset*G == attacker_key */;
// i.e. offset = attacker_scalar - discrete_log(group_key); for the *false-credit*
// direction the attacker instead crafts an output locked to a key they don't know,
// or simply supplies offset=0 with an unrelated script_pubkey — read() never checks.

// 3. Serialize a forged ReceivedOutput
let mut buf = vec![];
buf.extend(offset_bytes.to_bytes());
buf.extend(bitcoin::consensus::serialize(&fake_output));
buf.extend(bitcoin::consensus::serialize(&OutPoint::null())); // arbitrary outpoint

// 4. Deserialize — accepted without any consistency check
let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// forged.offset() == attacker-chosen scalar
// forged.output().script_pubkey == attacker's script
// Output::key() = script_key - offset*G == group_key  -> reported as group funds
```

Because `read` never recomputes `p2tr_script_buf(key + offset*G)`, the forged `offset` manipulates internal state exactly as the unvalidated `setattr` on `template_name` did in django-unicorn: a private field with a required invariant is set directly from untrusted input, and downstream code (`Output::key`, `SignableTransaction` re-keying via `ThresholdKeys::offset`) trusts it implicitly.

*Uncertainty note:* I was unable to read the exact per-input re-keying code in `send.rs` within the available iterations; the claim that `multisig` applies `output.offset()` to the signing keys is inferred from `ThresholdKeys::offset`, the `offset`-on-`included[0]` logic in `view()`, `Output::key()` subtracting `offset*G`, and the `test_send` test exercising offset-key spends. The deserialization flaw itself is fully verified in `mod.rs:122-134`.
