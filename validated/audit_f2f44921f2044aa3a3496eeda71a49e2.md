### Title
Staking/CL reward map overwrite on colliding `RewardAddr`/`CLPoolAddr` causes silent reward loss and reward redirection - (File: kaiax/reward/impl/getter.go)

### Summary
The reported PoolTogether bug class is: an accounting update that writes to an address-keyed store using plain **assignment** (rather than addition) in two independent code branches, so that when the two branches resolve to the *same key* (`from == to`), one write clobbers the other and the store no longer reflects the true delta. `kaiax/reward/impl/getter.go`'s `assignStakingRewards` / `assignStakingRewardsFlex` contain the same anti-pattern: staking rewards for a consolidated node (CN) and its consensus-liquidity (CL) pool are written into a shared `map[common.Address]*big.Int` with `alloc[addr] = amount` instead of an additive update, so a `RewardAddr`/`CLPoolAddr` collision between two different validators silently drops one party's reward.

### Finding Description
`assignStakingRewards` iterates over all consolidated nodes (`cn`) and, for each one, computes a reward and stores it keyed by address: [1](#0-0) 

```go
for _, cn := range cns {
    ...
    if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
        if isPrague && cn.CLStakingInfo != nil {
            cnAmount, clAmount := cn.Split(reward)
            alloc[cn.RewardAddr] = cnAmount
            alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
        } else {
            alloc[cn.RewardAddr] = reward
        }
        remaining.Sub(remaining, reward)
    }
}
```

The identical pattern exists in `assignStakingRewardsFlex`: [2](#0-1) 

Both functions use `alloc[addr] = amount` (overwrite), not `alloc[addr].Add(...)` (accumulate). `RewardAddr` values come from the AddressBook/AddressBookV2 registration (`kaiax/staking/impl/getter.go`, `parseCallResult`/`parsePermissionlessCallResult`), and `CLPoolAddr` values come from the CL Registry (`readCLInfo`/`MultiCallDPStakingInfo`). Both are attacker-influenceable: a staker who registers/updates their own council node's `RewardAddr` (via AddressBook self-registration under the permissionless fork, KIP-286/287) or their own CL pool address (via CLRegistry, which any staking-eligible party can register per KIP-226) can deliberately set it equal to the `RewardAddr` or `CLPoolAddr` of a different, already-registered validator.

Since `remaining.Sub(remaining, reward)` is unconditionally decremented for *every* computed reward regardless of whether the map write actually landed at a new key, the sum of amounts actually present in `alloc` can be strictly less than the total budget subtracted from `remaining`. Concretely: if attacker's CN (processed after victim's CN in `si.ConsolidatedNodes()` iteration order) sets `RewardAddr == victimCN.CLPoolAddr`, then:
1. Victim's `alloc[victimCN.CLPoolAddr] = clAmount` is written first.
2. Attacker's `alloc[attackerCN.RewardAddr] = reward` (same key) overwrites it.

The victim's CL-pool reward silently disappears from the reward `map`, even though it was already subtracted from `stakersAlloc`'s `remaining` and thus from the minted/emission accounting in `getDeferredRewardFullKore`/`getDeferredRewardFullFlex`. The end result is: (a) permanent loss of the victim's staking reward (an implicit, unaccounted-for burn beyond the protocol-specified reward split), and (b) if the attacker's own `RewardAddr` is the surviving key, the attacker effectively receives their own allocation while erasing the victim's, i.e., unilateral reward redirection favoring the attacker at the honest staker's expense.

### Impact Explanation
This breaks a core supply/reward-distribution invariant: the reward mechanism's `RewardSummary`/emission accounting subtracts amounts that never reach any recipient. This is a "reward redirection"/"unauthorized value movement" class issue — a party who is entitled to a share of block rewards can have that share silently zeroed out (and effectively captured or destroyed) by another staker deliberately colliding reward/CL-pool addresses. This directly affects validator/staker economics on every block where the collision persists (deterministic per staking epoch), which is a Medium/High-severity issue given ongoing, cumulative fund loss to legitimate stakers.

### Likelihood Explanation
Both `RewardAddr` (validator self-registration in AddressBook, and permissionless self-registration per KIP-286/287) and `CLPoolAddr` (CL pool registration in CLRegistry per KIP-226) are attacker-controllable values supplied by an ordinary staking participant — no special/validator-council permission beyond normal staking is required. The collision is deterministic (fully governed by `ConsolidatedNodes()` iteration order, itself a function of on-chain state, identical on all honest nodes), so an attacker can reliably engineer the address collision and trigger the bug on every relevant reward-distribution block once registered.

### Recommendation
Change the reward accumulation in `assignStakingRewards`/`assignStakingRewardsFlex` (and any other reward-map builder) to use additive semantics, e.g.:
```go
if _, ok := alloc[key]; !ok {
    alloc[key] = big.NewInt(0)
}
alloc[key].Add(alloc[key], amount)
```
instead of `alloc[key] = amount`, mirroring the pattern already used safely in `RewardSpec.IncRecipient` (`kaiax/reward/spec.go:110-116`). This ensures that colliding `RewardAddr`/`CLPoolAddr` values correctly sum contributions rather than overwrite them, closing the silent-fund-loss/redirection path.

### Proof of Concept
1. Register (or have already registered) two validators (CN1, CN2) that both exceed `minStake`/`StakingRewardThreshold`, with CN1 having a CL pool registered via CLRegistry at address `P`.
2. As the operator of CN2, set CN2's `RewardAddr` (via AddressBook / AddressBookV2 self-registration) to the same address `P` (CN1's `CLPoolAddr`). This requires only the same staking/registration permission an ordinary staker/validator already has, and CN2 must be processed after CN1 in `ConsolidatedNodes()`'s deterministic ordering (attacker can control by choosing their own council-node registration order/index or by leveraging address-based iteration).
3. On the next reward-distribution block (`FinalizeState` → `GetDeferredReward` → `assignStakingRewards`), CN1's CL-pool reward is written to `alloc[P]`, then CN2's reward for `RewardAddr == P` overwrites it.
4. Observe: `stakersAlloc`'s `remaining` (and hence `spec.Rewards`) accounts for CN1's CL amount as subtracted from the staking budget, but `spec.Rewards[P]` only reflects CN2's reward — CN1's CL stakers never receive their entitled reward for that block, while CN2 keeps the full overwritten balance at `P`.
