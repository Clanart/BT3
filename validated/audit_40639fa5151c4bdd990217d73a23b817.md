### Title
Unauthenticated OP_RETURN operator field in `payout_tx` lets any withdrawer credit an arbitrary operator with a payout it never funded - ([File: core/src/verifier.rs])

### Summary
`is_kickoff_malicious` in `core/src/verifier.rs` only checks that `operator_xonly_pk_opt` (parsed from the confirmed payout tx's `OP_RETURN`, via `update_finalized_payouts`) equals `kickoff_data.operator_xonly_pk`. Neither `update_finalized_payouts` nor `is_kickoff_malicious` verifies that the named operator actually signed or funded the payout's additional inputs, so anyone who can construct and broadcast a valid `payout_tx` (using their own withdrawal signature and self-funded extra inputs) can write any operator's `xonly_pk` into the `OP_RETURN` output, which is not covered by the withdrawer's `SinglePlusAnyoneCanPay` signature.

### Finding Description
The claimed binding is: `operator_xonly_pk_opt` (read from the payout's `OP_RETURN`) `==` `kickoff_data.operator_xonly_pk` should imply the named operator actually funded the payout. [1](#0-0) 

The `OP_RETURN` content is written by whoever broadcasts `payout_tx` via `create_payout_txhandler`, at `core/src/builder/transaction/operator_reimburse.rs:407-436`: [2](#0-1) 

The output layout is: `[0] user payout, [1] anchor, [2] OP_RETURN(operator_xonly_pk)`. Only input 0 (the withdrawer's UTXO) carries a `taproot::Signature` with `TapSighashType::SinglePlusAnyoneCanPay`, which is enforced in `parse_withdrawal_sig_params` in `core/src/rpc/parser/operator.rs:161-187`. `SIGHASH_SINGLE|ANYONECANPAY` only commits the withdrawer's signature to input 0 and output 0 - it does **not** cover output 1 (anchor) or output 2 (`OP_RETURN`), nor does it restrict who may add further funding inputs. Consequently, whoever assembles/funds `payout_tx` (any unprivileged actor who owns a withdrawal UTXO and its `SinglePlusAnyoneCanPay` signature, per the threat-model rules) can freely choose the `OP_RETURN` bytes.

`update_finalized_payouts` blindly trusts this field: it parses the confirmed block's `OP_RETURN` bytes into an `XOnlyPublicKey` and stores it as `payout_payer_operator_xonly_pk`, with no signature or funding-source check: [3](#0-2) 

`is_kickoff_malicious` then treats a match between this stored value and `kickoff_data.operator_xonly_pk` as proof the operator legitimately fronted the payout, and returns `false` (not malicious): [4](#0-3) 

Crucially, an operator's own automation, `PayoutCheckerTask`, polls for unhandled payouts **by its own `operator_xonly_pk`** and, upon finding one, automatically calls `handle_finalized_payout`, entering the kickoff/reimbursement flow without any additional check that the operator itself broadcast or funded the underlying `payout_tx`: [5](#0-4) [6](#0-5) 

No other guard in the traced path (`Verifier::is_deposit_valid`, `SECP.verify_schnorr` in `operator.rs::withdraw`, `only_aggregator_and_self`) authenticates the funding source of `payout_tx`'s additional inputs against the `OP_RETURN` claim; the `SECP.verify_schnorr` check in `operator.rs:630-637` only validates the withdrawer's own signature over input 0, which says nothing about who owns the OP_RETURN-named identity.

### Impact Explanation
An honest operator whose `xonly_pk` is written into a self-funded `payout_tx`'s `OP_RETURN` by an unrelated party will have its automated `PayoutCheckerTask` (if the operator runs the `automation` feature) trigger a kickoff/reimburse cycle for a withdrawal it never funded. If the kickoff completes without challenge/disprove, the named operator collects the bridge-amount `Reimburse` from the move-to-vault UTXO even though it fronted nothing. This is exactly the listed Critical category "an operator reimbursed for a payout it never funded" - real BTC leaves a move-to-vault UTXO to a party who supplied no matching capital for that specific withdrawal. The blast radius is any deposit/withdrawal where the withdrawer (or any funder) can complete the payout themselves and mislabel a target operator's pubkey; it is repeatable across every withdrawal cycle and does not require compromising any operator, verifier, or aggregator key.

### Likelihood Explanation
Per the stated threat model, the attacker is explicitly permitted to be their own withdrawer, choosing the withdrawal UTXO bytes and the `SinglePlusAnyoneCanPay` signature and sighash flag themselves, and to broadcast Bitcoin transactions. Building the full `payout_tx` (self-paying the user output, self-funding the additional inputs to cover the withdrawal amount, and inserting an arbitrary `xonly_pk` in `OP_RETURN`) is fully within their described capability set and needs no operator, verifier, or aggregator collusion. The only capital the attacker must supply is the withdrawal amount itself (which returns to their own address as output 0), plus tx fees - a modest, bounded cost, and the exploit is repeatable on every future withdrawal cycle. This makes the attack economically cheap and highly feasible for anyone wanting to grief or falsely enrich a target operator's automation.

### Recommendation
Bind the `OP_RETURN` operator claim to cryptographic proof of funding, e.g., require the additional payout-funding inputs to be spent by (or otherwise attributably signed by) the operator whose `xonly_pk` appears in `OP_RETURN` (for example by having verifiers check that at least one non-withdrawal input's `scriptPubKey`/witness key matches the claimed `operator_xonly_pk`, or by having the operator counter-sign the whole `payout_tx` with a signature covering the `OP_RETURN` output, rather than trusting an unauthenticated `OP_RETURN` field parsed in `update_finalized_payouts`).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub async fn get_first_unhandled_payout_by_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(u32, Txid, BlockHash)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, Option<TxidDB>, Option<BlockHashDB>)>(
            "SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
             FROM withdrawals w
             WHERE w.payout_txid IS NOT NULL
                AND w.is_payout_handled = FALSE
                AND w.payout_payer_operator_xonly_pk = $1
                ORDER BY w.idx ASC
             LIMIT 1",
        )
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let results = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        results
            .map(|(citrea_idx, move_to_vault_txid, payout_tx_blockhash)| {
                Ok((
                    u32::try_from(citrea_idx).wrap_err("Failed to convert citrea index to u32")?,
                    move_to_vault_txid
                        .expect("move_to_vault_txid Must be Some")
                        .0,
                    payout_tx_blockhash
                        .expect("payout_tx_blockhash Must be Some")
                        .0,
                ))
            })
            .transpose()
    }
