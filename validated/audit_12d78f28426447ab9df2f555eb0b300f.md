### Title
Generator promotion silently drops key tweaks, deriving the wrong threshold key - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` constructs the promoted `ThresholdKeys` from the original secret share and verification shares, but does not carry over the source key’s scalar and offset. Because `ThresholdKeys::new` initializes those values to `1` and `0`, promoting a tweaked key produces a different effective group key than the one represented by the input key.

### Finding Description
`ThresholdKeys` represents an effective key as `original_group_key * scalar + generator * offset`; signing views likewise scale the secret share and add the offset to the lowest-indexed participant. [1](#0-0) [2](#0-1) 

`GeneratorPromotion::promote` proves only `base.original_secret_share()` and binds the proof to `base.original_group_key()`, excluding both `current_scalar()` and `current_offset()`. [3](#0-2) 

`GeneratorPromotion::complete` verifies the same untweaked values and calls `ThresholdKeys::new` with the original secret share. [4](#0-3)  `ThresholdKeys::new` then resets `scalar` to `1` and `offset` to `0`, so the promoted object no longer represents the source key’s effective public key. [5](#0-4) 

For a source key with effective secret `s * x + o`, the correct promoted group key should be `H * (s * x + o)`. The implementation instead returns a key with group key `H * x`.

### Impact Explanation
Any protocol that promotes an already scaled or offset threshold key receives keys for a different group than the one it promoted from. If funds or protocol authority were associated with the tweaked group key, the promoted participants cannot produce signatures for that key without manually reconstructing the dropped tweak.

This is directly analogous to replacing a renderer while leaving per-token attributes behind: the new key object is successfully installed, but state required to reproduce the existing public identity is omitted.

### Likelihood Explanation
The affected values are part of the public `ThresholdKeys` API through `scale` and `offset`. [6](#0-5)  They are also used by Bitcoin Taproot key tweaking, which adds an offset and conditionally scales by `-1`. [7](#0-6) 

`GeneratorPromotion::complete` accepts untrusted serialized proofs through `GeneratorProof::read`, but no malicious proof is required: honestly generated proofs for all participants still produce a promoted key with the wrong effective group key whenever a nonzero offset or non-one scalar is present. [8](#0-7) 

### Recommendation
Preserve the source key’s linear transformation when constructing the promoted key. After `ThresholdKeys::new`, apply:

```rust
promoted
  .scale(base.current_scalar())
  .and_then(|keys| Some(keys.offset(base.current_offset())))
```

or equivalent internal construction. The promotion proof transcript should also bind the effective source group key and the scalar/offset semantics, not only `original_group_key()`, so the proof commits to the complete key identity being promoted.

### Proof of Concept
For a one-of-one key with secret `x`:

```rust
let tweaked = keys.offset(offset);
let (promotion, proof) =
  GeneratorPromotion::<C1, C2>::promote(&mut rng, tweaked.clone());

let promoted = promotion.complete(&HashMap::new()).unwrap();

assert_eq!(
  promoted.group_key(),
  C2::generator() * (*x + offset)
);
```

The implementation instead returns `C2::generator() * x` because `promote` proves `original_secret_share()` and `complete` passes that same untweaked share to `ThresholdKeys::new`, which resets the effective transformation to scalar `1` and offset `0`. [9](#0-8) [10](#0-9) [5](#0-4)
