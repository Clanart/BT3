### Title
Quadratic Lagrange interpolation with per-participant inversion enables resource-exhaustion DoS via `ThresholdKeys::read` - (File: crypto/dkg/src/lib.rs)

### Summary
The analog of the op-geth gas-tracking report (per-item bookkeeping work that is not priced against the resources it consumes) exists in Serai's threshold-key deserialization path. `ThresholdKeys::<C>::read` accepts an attacker-controlled `n`/`t` (each a `u16`, up to 65535) directly from untrusted bytes, then `ThresholdKeys::new` computes the group key by calling `Interpolation::Lagrange::interpolation_factor` once per participant in `1..=t`. Each call is O(t) field multiplications **plus a field inversion**, so deserialization of a single ~2 MB blob triggers O(t²) multiplications and t separate inversion operations — roughly 4.3·10⁹ field multiplications and 65,535 inversions at the maximum. The cost is quadratic in attacker input while the input itself is only linear in size, mirroring the report's "10,000 nested calls forcing 10,000 state updates for cheap" asymmetry.

### Finding Description
`ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574`) reads `t`, `n`, `i` as raw `u16`s with no upper bound beyond `u16::MAX`, then reads `n` serialized group elements via `C::read_G` (lines 620–623) before calling `ThresholdKeys::new`.

`ThresholdKeys::new` (lines 376–378) computes:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

For `Interpolation::Lagrange`, `interpolation_factor` (lines 229–247) iterates over the entire `included` slice performing a numerator/denominator product and then calls `denom.invert().unwrap()` — a full field inversion per participant. This makes group-key reconstruction O(t²) multiplications plus O(t) inversions.

The same quadratic cost is re-incurred later: `ThresholdKeys::view` (lines 500–506) calls `interpolation_factor` once per included signer, and `ThresholdView::interpolation_factor` (lines 657–662) exposes another O(included) Lagrange evaluation per query. An attacker feeding crafted bytes to `ThresholdKeys::read` (a listed untrusted-bytes sink) thus obtains linear-cost input producing quadratic-cost computation — the same resource-consumption/gas-mismatch class as the op-geth finding.

### Impact Explanation
A single maliciously crafted serialized `ThresholdKeys` blob with `t = n = 65535` forces ~65k elliptic-curve point decompressions, ~65k field inversions, and ~4·10⁹ field multiplications during `read`/`ThresholdKeys::new` alone — work orders of magnitude larger than the ~2 MB input. Any node that deserializes attacker-supplied `ThresholdKeys` (or subsequently calls `view()` on keys with large `n`) can be stalled, analogous to the report's sequencer being pushed outside its block-time bound. This is a resource-consumption DoS reachable with purely public input bytes; no collusion, leaked key, or malformed curve is required.

### Likelihood Explanation
Reachability requires an attacker to get untrusted bytes into `ThresholdKeys::read` — an explicitly permitted sink in scope. The trigger needs no special position: `t` and `n` are unvalidated upper bounds (`ThresholdParams::new` only checks `t <= n` and non-zero, lines 166–179). Whether a production service exposes this deserialization to unauthenticated input determines practical exploitability, but within the cryptographic library the amplification is deterministic and fully attacker-controlled.

### Recommendation
- Impose a sane maximum on `n`/`t` at deserialization time (e.g., bounded by the protocol's `MAX_KEY_SHARES_PER_SET`-style limit) rather than accepting the full `u16` range.
- Replace per-participant Lagrange inversion with a single batch inversion (compute all denominators, invert once, multiply back) to reduce O(t) inversions to O(1) inversion + O(t) multiplications.
- Cache interpolation factors or evaluate group keys via a single multiexp over precomputed coefficients instead of recomputing O(t) work per participant.
- Bound `included.len()` in `view()`/`interpolation_factor` to the same cap.

### Proof of Concept
```rust
// Serialize a ThresholdKeys blob with t = n = 65535, i = 1,
// Lagrange interpolation (tag 1), an arbitrary secret share,
// and 65535 arbitrary-but-valid encoded points.
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(&65535u16.to_le_bytes()); // t
buf.extend(&65535u16.to_le_bytes()); // n
buf.extend(&1u16.to_le_bytes());     // i
buf.push(1);                         // Interpolation::Lagrange
buf.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. 65535u32 {
    buf.extend(C::generator().to_bytes().as_ref()); // verification shares
}

// ~2.1 MB of input. Inside `read`, ThresholdKeys::new performs
// 65535 calls to interpolation_factor, each O(65535) muls + 1 inversion:
// ~4.3e9 field multiplications + 65535 inversions.
let keys = ThresholdKeys::<C>::read(&mut &buf[..]).unwrap();
```
