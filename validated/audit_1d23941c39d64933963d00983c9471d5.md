### Title
`ReceivedOutput::read` accepts an unvalidated scalar offset not bound to the output's script key — outputs accepted as spendable that cannot be spent - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
Analogous to the Jenkins vSphere plugin disabling certificate validation (accepting a peer's claimed identity without verifying the binding between the certificate and the endpoint), `ReceivedOutput::read` deserializes a spendable-output record whose `offset` scalar is never validated against the output's `script_pubkey`. The offset is the sole credential authorizing a spend, yet nothing proves `Scanner.key + offset * G` maps to the Taproot key inside `output.script_pubkey`.

### Finding Description
`Scanner` maintains a `scripts: HashMap<ScriptBuf, Scalar>` map where every script is derived from a registered offset via `register_offset`, which computes `p2tr_script_buf(self.key + GENERATOR * offset)` — so a `ReceivedOutput` produced by `scan_transaction`/`scan_block` always carries an offset genuinely bound to the output's key [1](#0-0) . However, `ReceivedOutput::read` — an explicitly in-scope untrusted-bytes sink — reads `offset` via `Secp256k1::read_F` and the `TxOut`/`OutPoint` via consensus decode, then constructs the struct with no consistency check between them [2](#0-1) . There is no `fn key()` accessor and no validation anywhere in `mod.rs` that `p2tr_script_buf(key + offset * G) == output.script_pubkey`; the `key` field of `Scanner` is not even consulted at read time since `read` is an associated function of `ReceivedOutput` [3](#0-2) .

### Impact Explanation
An attacker who supplies a crafted serialized `ReceivedOutput` can claim any on-chain output is received with an arbitrary offset. Downstream spend logic (e.g., `send.rs` / processor code consuming `offset()` to derive the signing key under `tweak_keys`/`needs_negation`) will produce a signature for `key + offset` that does not correspond to the output's actual Taproot key — the signature will fail BIP-340 verification on-chain, so the funds are reported received but are not spendable. Alternatively the attacker can claim an output that does pay to a derived script but pair it with a wrong `outpoint`, causing the wallet to attempt to spend a nonexistent UTXO. This is the "funds reported received that are not spendable" impact class.

### Likelihood Explanation
Exploitation requires an attacker to feed bytes to `ReceivedOutput::read` — e.g., via any path where received outputs are relayed, stored, or reconstructed from untrusted serialization rather than produced locally by `scan_transaction`. Impact is integrity-of-accounting rather than key compromise, matching Medium severity of the reference advisory: no secret leakage, but an authentication binding that should exist by default is absent.

### Recommendation
Either (a) make `ReceivedOutput::read` take the `Scanner`/`key` and verify `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset) == Some(output.script_pubkey)`, rejecting mismatches, or (b) serialize only the `outpoint`/`TxOut` and re-derive `offset` from the scanner's `scripts` map, eliminating the attacker-controlled binding entirely.

### Proof of Concept
```rust
// Construct a ReceivedOutput whose offset does not match the output's key.
let mut bytes = Vec::new();
// offset = 5, but output pays to p2tr(key + 7*G)
bytes.extend((Scalar::from(5u64)).to_bytes());
bytes.extend(serialize(&victim_txout));      // script_pubkey = p2tr(key + 7G)
bytes.extend(serialize(&real_outpoint));
let ro = ReceivedOutput::read(&mut bytes.as_slice()).unwrap(); // accepted
// ro.offset() == 5 -> spend attempt signs with key+5, unspendable
```

Caveat: I could not confirm within the iteration budget whether downstream consumers (`processor/src/networks/bitcoin.rs`, `wallet/send.rs`) re-validate the offset before use; if they do re-derive and check against `script_pubkey`, the reachable impact would be reduced. The deserialization-time validation gap itself is confirmed.

impl ReceivedOutput {
  /// The offset for this output.
  pub fn offset(&self) -> Scalar {
    self.offset
  }

  /// The Bitcoin output for this output.
  pub fn output(&self) -> &TxOut {
    &self.output
  }

  /// The outpoint for this output.
  pub fn outpoint(&self) -> &OutPoint {
    &self.outpoint
  }

  /// The value of this output.
  pub fn value(&self) -> u64 {
    self.output.value.to_sat()
  }

  /// Read a ReceivedOutput from a generic satisfying Read.
  #[cfg(feature = "std")]
  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
