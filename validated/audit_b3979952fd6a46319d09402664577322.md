### Title
Unchecked type assertion on attacker-controlled CW20/CW721/CW1155 metadata causes a panic when registering a pointer contract - (File: `precompiles/pointer/pointer.go`)

### Summary
The `pointer` precompile's `AddCW20` (and equivalent `AddCW721`/`AddCW1155`) executor queries an arbitrary, caller-supplied CosmWasm contract address for its `token_info` (or equivalent) metadata and then extracts the `name`/`symbol` fields from the returned JSON with unchecked Go type assertions, e.g. `formattedRes["name"].(string)`. Any transaction sender can point this call at a CosmWasm contract they control that returns a `token_info` response where `name`/`symbol` are absent, `null`, or a non-string JSON type, causing a runtime panic in the interface-to-string type assertion. This mirrors CVE-2017-9347's root cause: an externally-supplied, insufficiently validated payload (there an ASN.1 OID, here an untrusted CW query response) is consumed without validation and triggers a crash instead of a graceful decode error.

### Finding Description
`AddCW20` in `precompiles/pointer/pointer.go` (and identically in every legacy snapshot from `v552` through `v67`) performs: [1](#0-0) 
1. Accepts `cwAddr` directly from EVM calldata (`args[0].(string)`), with no restriction on which CosmWasm contract it points to.
2. Calls `p.wasmdKeeper.QuerySmart(ctx, cwAddress, []byte("{\"token_info\":{}}"))` / `QuerySmartSafe`, invoking a smart-query on that user-chosen contract.
3. `json.Unmarshal`s the raw response into `map[string]interface{}{}`.
4. Extracts fields with unchecked type assertions: [2](#0-1) 

Because the queried contract is fully attacker-controlled (any user can `Instantiate` a CosmWasm contract that implements a `token_info` query handler returning arbitrary JSON, e.g. `{"name": null, "symbol": 123}` or omitting the fields entirely), the caller of the pointer precompile can force `formattedRes["name"]` to be `nil` or a non-string type. A type assertion `x.(string)` on a `nil` interface or a wrong dynamic type panics ("interface conversion: interface {} is nil, not string" / "... is float64, not string"). The same unchecked-assertion pattern is repeated for `AddCW721`/`AddCW1155` metadata extraction in every version of this precompile file. No `ok`-form assertion, no JSON schema validation, and no `recover()` wraps this path (unlike `precompiles/common/legacy/*/decode_cost.go`'s gas-meter panic recovery, or `TestDynamicGasPrecompileRepanicsNonGas`, which explicitly documents that only gas-meter panics are converted to reverts and any other panic is re-raised): [3](#0-2) 

### Impact Explanation
This precompile is registered as a dynamic-gas precompile invoked from the EVM execution path during `DeliverTx`/block processing, not from an isolated read-only RPC context. A panic raised deep inside `Execute`/`AddCW20` during block execution is not caught by the dynamic-gas wrapper's recover logic (that recover only re-wraps `sdk.ErrorOutOfGas`/`sdk.ErrorGasOverflow`, explicitly re-panicking anything else), so the panic propagates up through the EVM message handling into the ante/msg-server pipeline. If nothing further up the stack recovers it, this crashes the node processing the block — every validator that executes the same transaction hits the identical panic deterministically, since the CW20 pointer contract's response is state and is part of consensus-critical execution. That produces a validator halt / chain liveness impact (network-wide since the same tx is replayed by every validator), matching the "validator halt" acceptance criterion.

### Likelihood Explanation
Likelihood is high for triggering: registering a CosmWasm contract with a custom `token_info` query handler and calling `pointer.addCW20Pointer(cwAddr)` from an EVM transaction requires no special privilege — any account that can deploy a CW contract and send an EVM transaction can do this. The main uncertainty (not fully confirmed from the codebase search) is whether an outer defer/recover exists somewhere in `x/evm/keeper/msg_server.go` or `baseapp` that catches all panics during `DeliverTx` and turns them into a failed transaction rather than a node crash — Cosmos SDK's `baseapp.runTx` typically has a top-level recover that converts panics into an error response for that one transaction, which would downgrade the impact from a full validator crash to "transaction fails with an internal error," but would still be a functional bug (a legitimate cw20 contract lacking a `name`/`symbol` field, or a contract crafted to be indistinguishable from a valid one until decode, silently reverts any interaction with it, and any contract composing with it could be griefed). Because I could not fully verify the presence/absence of an outer top-level recover in `baseapp`/ante for this specific EVM message path from the available search results, I flag this uncertainty explicitly rather than asserting the maximal "validator halt" outcome with full confidence.

### Recommendation
Replace all unchecked type assertions (`formattedRes["name"].(string)`, `formattedRes["symbol"].(string)`, and equivalent uses in `AddCW721`/`AddCW1155`) with the two-value `ok` form, and return a proper error (not a panic) when the field is missing or has an unexpected JSON type, across `precompiles/pointer/pointer.go` and all `precompiles/pointer/legacy/v*/pointer.go` snapshots.

### Proof of Concept
1. Instantiate a CosmWasm contract whose `token_info` query handler returns `{"name": null, "symbol": null}` (or any JSON where `name`/`symbol` are not strings, e.g. numbers or missing).
2. From an EVM account, call the `pointer` precompile's `addCW20Pointer(cwAddr)` method (address `0x000000000000000000000000000000000000100b`) with `cwAddr` set to the contract from step 1.
3. Execution reaches `AddCW20`, calls `QuerySmart`, unmarshals the JSON, and executes `formattedRes["name"].(string)`, panicking with an interface-conversion error instead of returning a decode error, since `nil`/non-string values are not guarded against. [4](#0-3)
