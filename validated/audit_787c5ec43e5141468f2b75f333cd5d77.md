### Title
Payout tx OP_RETURN attributing reimbursement payer is unauthenticated under SIGHASH_SINGLE|ANYONECANPAY, allowing vault funds to become permanently unreimbursable - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
The withdrawal ("payout") transaction that fronts a Citrea withdrawal is signed by the user with `SIGHASH_SINGLE | ANYONECANPAY` [1](#0-0) . This sighash type only commits to the single spent input and the output at the same index; it does **not** commit to any other outputs, including the OP_RETURN output that encodes "the operator's x-only pubkey that fronts the peg-out" [2](#0-1) . The verifier's block-processing logic later reads this uncommitted OP_RETURN field and treats its content as ground truth for "who paid" the withdrawal [3](#0-2) , which is subsequently used to gate which operator is allowed to claim reimbursement via `validate_payer_is_operator` [4](#0-3) .

### Finding Description
`create_payout_txhandler` builds the withdrawal-fronting transaction with three outputs: the user payout, an anchor, and an OP_RETURN carrying the fronting operator's xonly pubkey [5](#0-4) . The transaction is authorized solely by the user's `SinglePlusAnyoneCanPay` signature over input index 0 [1](#0-0) . Because `SIGHASH_SINGLE` commits only to output index 0 (matching the signed input) and `ANYONECANPAY` allows arbitrary additional/alternate inputs, **anyone in possession of this signature and the withdrawal outpoint** can independently reconstruct a payout transaction that pays the correct user output (satisfying the signature) while substituting an arbitrary OP_RETURN value — including the xonly pubkey of an operator who never built, signed off on, or funded that particular payout.

Once this transaction confirms, `update_finalized_payouts` scans the block, extracts the OP_RETURN xonly pubkey with no further validation of who broadcast/funded the transaction, and records it in the database as `payout_payer_operator_xonly_pk` [6](#0-5) . This attribution — not proof of actual funding — is what operators later query via `validate_payer_is_operator` to determine whether they are allowed to build a kickoff and claim reimbursement for that withdrawal [7](#0-6) , and it feeds `handle_finalized_payout` which selects the round/kickoff to reimburse against [8](#0-7) .

The binding that should hold is: **operator credited as payer == party that actually funded the payout tx**. Because the OP_RETURN is not covered by any signature check, an unprivileged attacker can break this binding by broadcasting a payout with a bogus, non-operator xonly pubkey (or one belonging to an operator who did not consent), causing `payout_payer_operator_xonly_pk` to be set to a value no legitimate operator can ever satisfy in `validate_payer_is_operator`.

### Impact Explanation
If the withdrawal is completed on-chain by the attacker (paying the user correctly to satisfy the SINGLE commitment) but with a fabricated/unregistered OP_RETURN pubkey, then:
- No operator's `validate_payer_is_operator` check will ever succeed for that withdrawal index (since `payer_xonly_pk != self.signer.xonly_public_key` for every real operator), so no operator can ever build the kickoff needed to trigger the reimburse transaction chain.
- The optimistic-payout fallback is also foreclosed, since `sign_optimistic_payout` first checks `is_utxo_spent(&input_outpoint)` and rejects if the withdrawal UTXO is already spent [9](#0-8) , which it is (spent by the attacker's payout tx).
- Consequently the corresponding move-to-vault deposit's bridge_amount becomes permanently unreachable — no party has an authorized/attributable path to spend the reimburse chain for that deposit.

This matches the explicit Critical impact categories "an honest operator permanently unable to be reimbursed" and "a vault UTXO permanently frozen."

### Likelihood Explanation
The attack requires only: (1) knowledge of the user's `SinglePlusAnyoneCanPay` signature and withdrawal outpoint, which per the code's own documentation is "given to operators off-chain" and also transmitted through the aggregator's `Withdraw` RPC to potentially many operators [10](#0-9) , widening exposure beyond the intended single operator; and (2) the ability to fund and broadcast a standard Bitcoin transaction, which requires no protocol role, key, or privileged RPC access. No verifier, operator, or aggregator secret is needed — only unprivileged Bitcoin-network access and the (widely distributed) withdrawal signature.

### Recommendation
Do not rely on an uncommitted OP_RETURN field to attribute reimbursement rights. Either:
- Change the payout signature scheme so it commits (e.g., via `SIGHASH_ALL` or a covenant/committed template) to the OP_RETURN output identifying the paying operator, so it cannot be altered by a third party; or
- Require the operator to additionally provide an independent, verifiable signature/commitment (e.g., signed off-chain with their own key over the specific payout txid) before `update_finalized_payouts`/`handle_finalized_payout` attributes reimbursement rights to them, instead of trusting unauthenticated OP_RETURN data.

### Proof of Concept
1. Attacker obtains a user's withdrawal `WithdrawParams` (input_outpoint, input_signature with `SinglePlusAnyoneCanPay`, output_script_pubkey, output_amount) — obtainable since it is sent to all operators via the aggregator's `Withdraw` RPC, or leaked off-chain per design.
2. Attacker constructs their own transaction spending `input_outpoint` with the given signature, keeping output[0] identical (satisfying `SIGHASH_SINGLE`), but sets the OP_RETURN output (output[2]) to a bogus xonly pubkey not controlled by any real operator, and funds/broadcasts it themselves (`ANYONECANPAY` allows adding attacker-owned inputs to cover fees/shortfall).
3. `update_finalized_payouts` (`core/src/verifier.rs:2283`) parses this OP_RETURN and records the bogus pubkey as `payout_payer_operator_xonly_pk` for this withdrawal index.
4. No real operator's `validate_payer_is_operator` (`core/src/operator.rs:1687`) will ever match this pubkey, so `handle_finalized_payout` can never be triggered by a legitimate operator for this deposit, and `sign_optimistic_payout` will refuse since the withdrawal UTXO is already spent — permanently freezing the corresponding vault deposit's `bridge_amount`.

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;
