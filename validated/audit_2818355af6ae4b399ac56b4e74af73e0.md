### Title
WSEI.withdraw() uses `.transfer()` with a fixed 2300-gas stipend, causing permanent fund lock for smart-contract holders - (File: contracts/src/WSEI.sol)

### Summary
`WSEI.sol`, the wrapped-SEI contract deployed as part of the EVM module (referenced by `x/evm/artifacts/wsei/artifacts.go` and `x/evm/client/cli/tx.go`), implements `withdraw()` using Solidity's `.transfer()` to return native SEI to the caller. [1](#0-0) 

### Finding Description
`payable(msg.sender).transfer(wad)` forwards only a 2300 gas stipend to the recipient. Any contract-account holder of WSEI whose `receive()`/`fallback()` function (a) is absent and non-payable, (b) requires more than 2300 gas to execute (e.g. it writes to storage, forwards the call, logs an event, or is behind a proxy that adds gas overhead), will have the transfer revert unconditionally. Since `balanceOf[msg.sender] -= wad` occurs before the transfer, the entire `withdraw` call reverts and the WSEI balance remains locked—no other function path allows the underlying native SEI to be recovered except through the same fixed-stipend path. [2](#0-1) 

This is materially different from EOA use cases: WSEI, being a general ERC20-style wrapper deployed for any EVM user/contract to hold and withdraw native SEI, will be held by smart contract wallets, multisigs, DeFi routers, and proxy contracts (e.g. Dragonswap-style routers referenced elsewhere in the repo's test suite) as part of normal EVM composability on Sei.

### Impact Explanation
Any smart contract that holds WSEI and whose receive/fallback logic requires >2300 gas (a common pattern for gas-metering proxies, multisig wallets like Gnosis Safe, or contracts that emit events/update state on receiving ether) will be permanently unable to redeem their wrapped SEI back to native SEI via `withdraw()`. This constitutes a permanent freezing of funds for any smart-contract holder of WSEI, satisfying the "permanent freezing of funds" impact bucket.

### Likelihood Explanation
Likelihood is high in practice because WSEI is a core wrapped-native-asset primitive that DeFi protocols, routers, and smart-contract wallets are expected to hold and interact with as part of normal EVM composability on Sei (mirroring WETH's role on Ethereum). Any contract wallet or protocol contract with a gas-hungry `receive()` will trigger this on the very first withdrawal attempt—no attacker action is required, only ordinary usage by a smart-contract holder.

### Recommendation
Replace `payable(msg.sender).transfer(wad)` with a low-level `call` and explicit success check, following checks-effects-interactions (state is already updated before the call, so reentrancy risk is low provided this ordering is preserved):
```solidity
(bool success, ) = payable(msg.sender).call{value: wad}("");
require(success, "WSEI: ETH transfer failed");
```

### Proof of Concept
1. Deploy a `Recipient` contract whose `receive() external payable { someMapping[block.number] = msg.value; }` (a state write costing >2300 gas, e.g. a cold `SSTORE`).
2. `Recipient` calls `WSEI.deposit()` with some SEI, receiving WSEI balance.
3. `Recipient` calls `WSEI.withdraw(wad)`.
4. `payable(msg.sender).transfer(wad)` at [3](#0-2)  forwards only 2300 gas to `Recipient.receive()`, which reverts due to the cold `SSTORE` exceeding the stipend; the entire `withdraw` transaction reverts, and `Recipient`'s WSEI balance (and underlying native SEI) remains permanently locked in the WSEI contract with no alternative withdrawal path.

    function deposit() public payable {
        balanceOf[msg.sender] += msg.value;
        emit Deposit(msg.sender, msg.value);
    }
    function withdraw(uint wad) public {
        require(balanceOf[msg.sender] >= wad);
        balanceOf[msg.sender] -= wad;
        payable(msg.sender).transfer(wad);
        emit Withdrawal(msg.sender, wad);
    }
