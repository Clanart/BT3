### Title
`ThresholdKeys::read` deserializes semantically inconsistent keys, causing a panic (`unreachable!`) during signing - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) reconstructs `ThresholdKeys` from raw bytes — `t`, `n`, `i`, an `Interpolation`, a `secret_share` scalar, and `n` verification shares — and validates them only through `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391). `new` checks the count and range of verification shares and the interpolation applicability, but never verifies the consistency invariant `C::generator() * secret_share == verification_shares[i]`. The FROST completion code itself documents this gap: "The only known way to cause this, for valid parameters/algorithms, is to deserialize a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494).

### Finding Description
The deserialization path is:

- `ThresholdKeys::read` reads `params`, `interpolation`, `secret_share` (via `C::read_F`, canonical-checked per crypto/ciphersuite/src/lib.rs:74-83), and `verification_shares` (via `read_G`, canonicality-checked per crypto/ciphersuite/src/lib.rs:91-101), then calls `ThresholdKeys::new`.
- `ThresholdKeys::new` computes `group_key` solely from the first `t` verification shares (crypto/dkg/src/lib.rs:376-378) and stores `secret_share` without checking it matches `verification_shares[params.i()]`.
- During signing, `view()` interpolates `secret_share` (crypto/dkg/src/lib.rs:494-498) while `verify_share`/the aggregate check use the interpolated `verification_shares`. With a mismatched pair, every individually-produced share is "valid" against the stated shares only if the attacker also corrupted them consistently; in the general case `complete()` produces an aggregate that fails `algorithm.verify`, then the per-share `BatchVerifier` blame pass finds all shares valid, hitting `FrostError::InternalError("everyone had a valid share yet the signature was still invalid")` (crypto/frost/src/sign.rs:487-494).
- Every in-tree caller treats `InternalError` as `unreachable!`, e.g. processor/src/batch_signer.rs:275-280, processor/src/cosigner.rs:188-193, processor/src/signer.rs. A deserialized bad `ThresholdKeys` therefore panics the signing process rather than returning a recoverable error.

Notably, the same inconsistency enables a subtler outcome: since `group_key` is derived from attacker-controlled `verification_shares` while the signer uses attacker-controlled `secret_share`, a fully crafted blob is a self-consistent keypair the attacker entirely controls — but the honest-party impact is that any bytes that deserialize but violate the share/verification-share invariant are accepted as load-bearing key material and produce either a signature under an unexpected `group_key` (if shares were re-derived consistently) or a guaranteed crash.

### Impact Explanation
Untrusted bytes fed to `ThresholdKeys::read` (the key-blob format is used to persist/reload threshold keys, e.g. `GeneratedKeysDb::read_keys` in processor/src/key_gen.rs:47-62 which `unwrap()`s the read) yield `ThresholdKeys` violating the secret_share ↔ verification_share invariant. Any subsequent `view()`/`sign`/`complete` either panics via `unreachable!(FrostError::InternalError)` — a remote-triggerable availability loss of the signer if the blob can be influenced — or signs under a `group_key` inconsistent with the node's actual share. Severity: Medium (integrity/availability impact from deserialization of untrusted data; no direct secret disclosure).

### Likelihood Explanation
The `read` path performs only syntactic checks (canonical scalar/point encodings, parameter ranges); the missing semantic check is a one-line omission in `ThresholdKeys::new`. Exploitation requires an attacker to influence the bytes passed to `ThresholdKeys::read` (key backup/recovery, DB import, or any untrusted-serialization path), which is a plausible integration surface; the code comments themselves acknowledge this is the "only known way" to reach the internal error.

### Recommendation
In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), reject keys where `C::generator() * secret_share.deref() != verification_shares[&params.i()]` (adjusted for `Interpolation::Constant`, where the share may need to be checked against its coefficient — at minimum document and enforce whichever invariant `view()` relies on). Additionally, stop mapping `InternalError` to `unreachable!()` in the processor signers so a malformed persisted key degrades to an error rather than a crash.

### Proof of Concept
1. Serialize an honest `ThresholdKeys<C>` for `t = n = 2`, `i = 1`, `Interpolation::Lagrange`.
2. Flip any byte in the encoded `secret_share` scalar (keeping it canonical, e.g. add 1) — or substitute `verification_shares[1]` with a different valid point.
3. `ThresholdKeys::read` accepts the blob: all encodings are canonical, `Participant::new(i)` succeeds, `ThresholdParams::new` and the share-count checks pass.
4. `AlgorithmMachine::new(.., keys).preprocess()` then `sign(..)` succeeds (the local share is used as-is).
5. `complete()` fails `algorithm.verify`, the per-share `BatchVerifier` finds every share valid, and returns `FrostError::InternalError`, which every processor caller escalates to `unreachable!()` — a panic — confirming deserialization of untrusted data reaches a semantically-invalid state the type system fails to reject.
