## Finding: Silent `U256`→`u128` Truncation in Relayer Fee Withdrawal Loses Accrued Fees

### Title
Unsafe `low_u128()` Truncation of Accumulated Relayer Fees Causes Fund Loss on Withdrawal - (`modules/pallets/relayer/src/withdrawal.rs`)

### Summary
The `pallet-relayer` withdrawal path performs an unchecked, lossy narrowing conversion from `U256` to `u128` when building the disbursement amount for substrate destinations, while unconditionally zeroing the full `U256` fee balance regardless of what was actually dispatched. This mirrors the reported bug class (unsafe cast producing distorted fee/PnL values) but lands on the fund-custody path instead of a read-only view function.

### Finding Description
`Pallet::<T>::withdraw` reads the relayer's accrued balance as a `U256`: [1](#0-0) 

For substrate destinations it truncates that `U256` down to `u128` with `.low_u128()` when constructing the `WithdrawRelayerFees` ISMP message body: [2](#0-1) 

Immediately after dispatch, the full `Fees` storage entry is wiped to zero, independent of the (possibly truncated) amount that was actually dispatched: [3](#0-2) 

`Fees` is accumulated as `U256` and incremented via unchecked `AddAssign` in `accumulate()`, with no cap ensuring the value stays within `u128` bounds before a substrate withdrawal is attempted: [4](#0-3) 

The `fee` component added into `Fees` for EVM sources is itself decoded straight from a proven storage slot as an `alloy_primitives::U256` with essentially no upper bound imposed by this pallet: [5](#0-4) 

If the accumulated `Fees[dest_chain][relayer]` value ever exceeds `u128::MAX` (2^128 − 1), `withdraw()` for a substrate destination silently drops the high 128 bits via `.low_u128()`, dispatches only the truncated (much smaller) amount to the destination host, and then zeroes the entire real balance in storage — permanently destroying the difference. This is functionally identical to the reported unsafe-cast pattern: a value near a type boundary is narrowed without a `SafeCast`-style checked conversion, producing a distorted, incorrect settled amount.

### Impact Explanation
This is a fund-loss bug in the live relayer fee-custody path: legitimately accrued relayer rewards in excess of `u128::MAX` are irrecoverably lost (not stolen by another party, but destroyed — the storage is zeroed while only the truncated amount is ever paid out). This falls under the bounty's "loss of funds" impact category since it corrupts a value that directly controls disbursement from bridge-held fee balances on the withdrawal execution path (`Pallet::withdraw`), a public, unprivileged, signature-gated entry point.

### Likelihood Explanation
Reaching a `Fees` balance above `u128::MAX` (~3.4×10^38) requires an extreme accumulated value relative to any realistic 18-decimal fee token supply, which is the same caveat the original report itself flags for the `FeeRouter`/`PositionBook` overflow paths ("would require large ... values, which can only be set by privileged roles"). Here, however, the `fee` field folded into `Fees` is read directly from an EVM source-chain-proven `RequestCommitments` storage slot and is not scaled or bounded by this pallet before being proven and accumulated; whether the upstream EVM host enforces that `fee` matches an actual token transfer at dispatch time was not verifiable from the code reviewed here. Absent that upstream validation, an entity capable of dispatching a request with an arbitrarily large declared `fee` (and later proving delivery) could inflate `Fees` toward the truncation boundary without needing admin/governance privileges. This uncertainty should be resolved before treating likelihood as anything but low-to-speculative.

### Recommendation
Replace `.low_u128()` with a checked conversion (e.g. `u128::try_from(available_amount)` / `TryInto` from `U256`) and reject or clamp the withdrawal if the balance doesn't fit in `u128`, rather than silently truncating. Additionally, only zero the `Fees` entry by exactly the amount that was actually dispatched (subtract, don't blanket-`insert(U256::zero())`), so any leftover balance beyond what could be encoded remains claimable rather than being destroyed.

### Proof of Concept
1. Cause (or assume) `Fees::<T>::get(dest_chain, relayer)` to exceed `u128::MAX` via repeated `accumulate()` calls proving requests whose source-chain `FeeMetadata.fee` field is a very large `U256` (`modules/pallets/relayer/src/accumulate.rs:260-286`, `:134-147`).
2. Relayer calls `withdraw_fees` targeting a substrate `dest_chain`.
3. `withdraw()` computes `available_amount.low_u128()` (`modules/pallets/relayer/src/withdrawal.rs:138`), dropping all bits above 2^128, and dispatches a `WithdrawRelayerFees` message with only the truncated amount.
4. `Fees::<T>::insert(dest_chain, relayer, U256::zero())` (`:177`) wipes the entire real balance.
5. The relayer receives only the truncated (far smaller) amount; the remainder is unrecoverable — no code path re-credits or re-derives it.

Note: the practical trigger conditions for exceeding the `u128` threshold could not be fully confirmed from the indexed code (upstream EVM-side fee-validation-at-dispatch was not located); this should be verified in a full repository checkout before treating the likelihood as high.
