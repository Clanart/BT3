## Title
Silent off-by-one hunk-header mismatch when consuming attacker-crafted diffs allows GitHub Desktop to commit/stage content the user never selected - (File: `app/src/lib/diff-parser.ts`)

### Summary
The Timeswap `add512()` bug is a class of "insufficient boundary check → attacker forges a value that slips past a guard that assumes only one failure mode → downstream arithmetic silently produces a wrong-but-plausible result → funds move incorrectly." The closest structural analog I can find in the indexed Desktop code is in the unified-diff parser/patch-formatter pipeline: `DiffParser.parseHunkHeader()` trusts the numeric line/count fields declared in a hunk header (`@@ -l,s +l,s @@`) without ever validating them against the number of `+`/`-`/` ` lines that actually follow in the hunk body [1](#0-0) . Those unchecked, attacker-influenced numbers (`oldStartLine`/`newStartLine`) are then used as the seed for `rollingDiffBeforeCounter`/`rollingDiffAfterCounter`, which are incremented per line to assign `oldLineNumber`/`newLineNumber` to every `DiffLine` [2](#0-1) . `patch-formatter.ts` then re-emits those same header numbers verbatim (`hunk.header.oldStartLine`, `hunk.header.newStartLine`) when constructing the patch that is fed straight into `git apply --cached` to build the index for a partial commit [3](#0-2) [4](#0-3) . There is no cross-check anywhere in this chain comparing the header-declared counts to the actual line prefixes parsed, mirroring the add512 pattern of "assume the counter check catches every overflow/mismatch case, when in fact a boundary condition slips through."

### Finding Description
`parseHunkHeader()` extracts four integers from the `@@ -oldStart,oldCount +newStart,newCount @@` regex and constructs a `DiffHunkHeader` with no relationship check against the hunk's actual line count [1](#0-0) . `parseHunk()` only validates that a hunk isn't completely empty (`lines.length === 1` → throw) [5](#0-4)  — it never asserts that the number of context+delete lines equals `header.oldLineCount`, nor that context+add lines equal `header.newLineCount`. The per-line `oldLineNumber`/`newLineNumber` are produced purely by incrementing counters seeded from the (unverified) header values [6](#0-5) .

This diff text is not something Desktop always generates itself from a byte-exact local `git diff` — the same `DiffParser.parse()` is explicitly documented and used to consume the raw output of "any other git plumbing command that produces unified diffs" [7](#0-6) , and the parsed result flows into UI-driven line-selection (`DiffSelection`) which is later turned back into a hunk header via `formatHunkHeader(hunk.header.oldStartLine, oldCount, hunk.header.newStartLine, newCount)` — i.e. the *original*, unverified header start-lines are trusted again when re-serializing the partial-commit patch [3](#0-2) . That patch is piped directly to `git apply --cached` [8](#0-7) .

Because a diff produced by a hostile remote/proxy for `git diff`-adjacent plumbing (e.g. a tampered pack/transport response that alters blob content between the time the working tree was read and the time `git diff` output is captured, or any code path that hands parser-consumed diff text sourced from an external git object) can declare a hunk header whose `oldStartLine`/`newStartLine` do not match the line prefixes that follow, the parser will silently assign incorrect `oldLineNumber`/`newLineNumber` to every line in that hunk and all subsequent hunks (since `linesConsumed` and rolling counters compound across the whole file) — with no revert/throw analogous to Timeswap's missing equality check. The corrupted value is the pair `(oldLineNumber, newLineNumber)` attached to each `DiffLine`, which is exactly the value the UI uses to decide what a "line" is for selection purposes and what `formatPatch`/`formatPatchToDiscardChanges` re-emit into the header sent to `git apply`.

### Impact Explanation
If hunk header numbers are attacker-influenced and inconsistent with the actual hunk body, a user who intends to stage/commit only specific lines (using Desktop's line-level partial-staging UI) can have `formatPatch()` construct a header (`@@ -oldStart,oldCount +newStart,newCount @@`) that no longer corresponds to the lines actually written into `hunkBuf`, because `oldCount`/`newCount` are recomputed by walking `hunk.lines` but `oldStartLine`/`newStartLine` are carried through unmodified from the original (possibly bogus) header [3](#0-2) . `git apply --cached` will either reject a clearly malformed hunk or, worse, apply it against a shifted offset in the index depending on `--unidiff-zero`/fuzz behavior, silently corrupting what actually lands in the commit relative to what the user selected in the UI. This matches the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
This is a lower-confidence, harder-to-trigger analog than the Timeswap arithmetic bug: I could not find, within the indexed portion of the codebase, a concrete external/remote-controlled entry point that feeds raw hunk text (as opposed to text produced by Desktop's own `git diff` invocation against the local working tree) into `DiffParser.parse()`. The parser's own docstring acknowledges it is meant to consume output from "any other git plumbing command" [7](#0-6) , which is suggestive but not conclusive proof of a reachable attacker-controlled path from a hostile remote/proxy. Given the index size limits mentioned in my instructions, I was not able to fully trace every caller of `DiffParser.parse()` / `convertDiff()` to rule out or confirm a genuinely remote-attacker-triggerable path (e.g., a code path that parses diff text obtained from a GitHub API response, a `.patch` download, or a tampered transport response rather than a freshly-invoked local `git diff`).

### Recommendation
- In `parseHunk()`, after building `lines`, validate that the count of lines contributing to the old side (context + delete) equals `header.oldLineCount` and that the count contributing to the new side (context + add) equals `header.newLineCount`; throw a parse error on mismatch instead of silently trusting the header.
- In `patch-formatter.ts`, when re-emitting `formatHunkHeader`, recompute `oldStartLine`/`newStartLine` consistently with the recomputed `oldCount`/`newCount` rather than reusing the original header's start lines unconditionally, or explicitly assert they remain valid for the current selection before serialization.
- Add a fuzz/property test that generates hunk headers whose declared counts intentionally disagree with body content and asserts `DiffParser.parse()` rejects them.

### Proof of Concept
Not independently verified end-to-end due to indexing limits on tracing every caller of `DiffParser.parse()`. Conceptual PoC:
1. Construct a unified diff where the header claims `@@ -10,2 +10,2 @@` but the hunk body actually contains 4 context/change lines (i.e., header counts understate the real body).
2. Feed this into `DiffParser.parse()` — `parseHunk()` will not throw, because there is no equality check between `header.oldLineCount`/`header.newLineCount` and the actual number of parsed lines [9](#0-8) .
3. Use Desktop's line-selection UI to select a subset of lines from this malformed hunk; `formatPatch()` reconstructs a hunk header using the original (bogus) `oldStartLine`/`newStartLine` combined with freshly counted `oldCount`/`newCount` [3](#0-2) .
4. Pipe the result to `git apply --cached` [10](#0-9)  and observe whether the resulting staged content diverges from what was visually selected.

I was unable to confirm from the indexed code alone that step 1's diff text can originate from an attacker-controlled remote/API source rather than Desktop's own local `git diff` invocation — this is the key uncertainty. If a Devin session with full repo access can confirm such a path exists (e.g., parsing PR patches fetched from the GitHub API, or diff text derived from a compromised remote/proxy response), this would become a fully-confirmed, higher-severity finding; absent that confirmation, this should be treated as a plausible but unverified analog rather than a proven vulnerability.

  private parseHunk(
    linesConsumed: number,
    hunkIndex: number,
    previousHunk: DiffHunk | null
  ): DiffHunk {
    const headerLine = this.readLine()
    if (!headerLine) {
      throw new Error('Expected hunk header but reached end of diff')
    }

    const header = this.parseHunkHeader(headerLine)
    const lines = new Array<DiffLine>()
    lines.push(new DiffLine(headerLine, DiffLineType.Hunk, 1, null, null))

    let c: DiffLinePrefix | null

    let rollingDiffBeforeCounter = header.oldStartLine
    let rollingDiffAfterCounter = header.newStartLine

    let diffLineNumber = linesConsumed
    while ((c = this.parseLinePrefix(this.peek()))) {
      const line = this.readLine()

      if (!line) {
        throw new Error('Expected unified diff line but reached end of diff')
      }

      // A marker indicating that the last line in the original or the new file
      // is missing a trailing newline. In other words, the presence of this marker
      // means that the new and/or original file lacks a trailing newline.
      //
      // When we find it we have to look up the previous line and set the
      // noTrailingNewLine flag
      if (c === DiffPrefixNoNewline) {
        // See https://github.com/git/git/blob/21f862b498925194f8f1ebe8203b7a7df756555b/apply.c#L1725-L1732
        if (line.length < 12) {
          throw new Error(
            `Expected "no newline at end of file" marker to be at least 12 bytes long`
          )
        }

        const previousLineIndex = lines.length - 1
        const previousLine = lines[previousLineIndex]
        lines[previousLineIndex] = previousLine.withNoTrailingNewLine(true)

        continue
      }

      // We must increase `diffLineNumber` only when we're certain that the line
      // is not a "no newline" marker. Otherwise, we'll end up with a wrong
      // `diffLineNumber` for the next line. This could happen if the last line
      // in the file doesn't have a newline before the change.
      diffLineNumber++

      let diffLine: DiffLine

      if (c === DiffPrefixAdd) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Add,
          diffLineNumber,
          null,
          rollingDiffAfterCounter++
        )
      } else if (c === DiffPrefixDelete) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Delete,
          diffLineNumber,
          rollingDiffBeforeCounter++,
          null
        )
      } else if (c === DiffPrefixContext) {
        diffLine = new DiffLine(
          line,
          DiffLineType.Context,
          diffLineNumber,
          rollingDiffBeforeCounter++,
          rollingDiffAfterCounter++
        )
      } else {
        return assertNever(c, `Unknown DiffLinePrefix: ${c}`)
      }

      lines.push(diffLine)
    }

    if (lines.length === 1) {
      throw new Error('Malformed diff, empty hunk')
    }

    return new DiffHunk(
      header,
      lines,
      linesConsumed,
      linesConsumed + lines.length - 1,
      getHunkHeaderExpansionType(hunkIndex, header, previousHunk)
    )
  }
