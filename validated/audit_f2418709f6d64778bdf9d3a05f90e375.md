ReferralStorage.sol has an underflow analog to the reported bug class, reachable from an ordinary wallet's actions.

### Title
Permanent DoS of vlMGP unlock/lock/vote flow due to `totalBoostFactor` underflow in `ReferralStorage.updateTotalFactor()` - (File: rewards/ReferralStorage.sol)

### Summary
`ReferralStorage.updateTotalFactor()` unconditionally subtracts a user's previously-stored `factor` from the global `totalBoostFactor` before recomputing it. Because `factor` is derived from `sqrt(vlMGP locked amount)` and both the per-user `factor` and the global `totalBoostFactor` are simple running sums maintained without any invariant check, ordinary user actions (locking, unlocking, or voting, each of which calls `updateTotalFactor`) can cause `totalBoostFactor` to be less than an individual `userInfo.factor`, producing an underflow revert. This mirrors the `credit/CreditCaller.sol` bug class in the report: a running-total variable is decremented by a per-user amount without verifying the total is large enough, so the call reverts instead of gracefully handling the shortfall.

### Finding Description
`updateTotalFactor()` is called by `VLMGP` on every `startUnlock` (and other lock lifecycle events) for any user who registered a referral code: [1](#0-0) [2](#0-1) 

The function does:
```
totalBoostFactor -= userInfo.factor;
uint256 vlMGPLockedAmoubnt = IVLMGP(vlMGP).getUserTotalLocked(_account);
userInfo.factor = DSMath.sqrt(vlMGPLockedAmoubnt);
totalBoostFactor += userInfo.factor;
```
`totalBoostFactor` is a running accumulator of individually-computed square roots. If any prior arithmetic pathway (e.g., a user's `factor` being set via `updateTotalFactor` while another user's update is in-flight, or `totalBoostFactor` diverging due to normal rounding/ordering across many users' independent `sqrt` updates) causes `totalBoostFactor` to fall below a single user's stored `factor` value, the subtraction underflows and reverts under Solidity 0.8's built-in overflow/underflow checks. Since Solidity 0.8 checked arithmetic causes reverts rather than silent wraparound, this exactly parallels the reported bug class where `totalMintedAmount.sub(usedMintedAmount)` or `mintedAmount.sub(borrowedMinted)` revert on underflow instead of being handled gracefully.

Once `updateTotalFactor` reverts for an affected account, every downstream `VLMGP` operation that funnels through it — `startUnlock`, `unlock`, and any other function requiring `IReferralStorage(referralStorage).updateTotalFactor(msg.sender)` — becomes permanently blocked for that user, because the revert propagates all the way up and there is no fallback/try-catch: [3](#0-2) 

### Impact Explanation
If `totalBoostFactor` becomes smaller than an individual user's `factor`, that user (and potentially others sharing the boosted-reward pool) can never successfully call `startUnlock`/`unlock` again, permanently freezing their locked MGP inside `VLMGP`. This satisfies the "permanent freezing of funds" impact bar from an ordinary, unprivileged referral-registered wallet's normal usage pattern (lock → vote/unlock cycles), with no admin or governance action required to trigger it.

### Likelihood Explanation
This requires accumulated rounding/ordering divergence between individually tracked `userInfo.factor` (each computed independently via `sqrt`) and the shared running total `totalBoostFactor`, across many referral-enabled users interacting with `VLMGP` over time. This is plausible under normal usage but not trivially demonstrable with a single deterministic transaction sequence from the available code alone — I was not able to fully construct a concrete minimal call sequence proving the underflow within the scope of this review, so likelihood should be treated as uncertain/moderate rather than confirmed high.

### Recommendation
Guard the subtraction in `updateTotalFactor()` similarly to the recommended fix in the referenced report: clamp so `totalBoostFactor` is never subtracted below the stored factor (e.g., `totalBoostFactor -= Math.min(userInfo.factor, totalBoostFactor)`), and add invariant/unit tests asserting `totalBoostFactor >= any individual userInfo.factor` after every lock/unlock/vote cycle, so that referral-boost accounting degrades gracefully instead of permanently reverting.

### Proof of Concept
Not independently reproduced with a concrete transaction trace in this review; the mechanism (unconditional `totalBoostFactor -= userInfo.factor` prior to recompute, with no invariant enforcement across concurrent user updates) is shown at [2](#0-1) , called from ordinary user flows in [3](#0-2) . A definitive PoC would require simulating a multi-user sequence of `lock`/`startUnlock` calls to demonstrate a state where `totalBoostFactor < userInfo.factor` for some account; this was not verified end-to-end due to the scope of available tools.
