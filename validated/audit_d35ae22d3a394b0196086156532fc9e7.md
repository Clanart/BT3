### Title
`ResetMmrTree` migration reuses leaf indices, permanently corrupting proof generation for pre-existing (already fee-paid) requests/responses - (File: `modules/pallets/mmr/src/migrations.rs`)

### Summary

### Finding Description
This is the same broken invariant as the reported EVM deposit bug: a monotonically-increasing index is reset to `0` while pre-existing entries that reference the old index range are left untouched, so subsequent writes silently reuse and corrupt indices that are still "live" for older accounted-for entries.

In `pallet-mmr-tree`, the `ResetMmrTree` migration kills `NumberOfLeaves`, `RootHash`, `InitialHeight` and clears `Nodes`, restarting the leaf counter at `0`: [1](#0-0) 

Crucially, it does **not** touch `child_trie::RequestCommitments` / `ResponseCommitments`, which is the store used by `pallet-ismp` to remember, for every dispatched-but-not-yet-relayed request/response, the `LeafIndexAndPos { leaf_index, pos }` that locates its data in the MMR: [2](#0-1) 

After the reset, `OffchainDBProvider::push` computes new leaf indices from the (now zeroed) `NumberOfLeaves`, so the very next outgoing request dispatched after the upgrade is assigned `leaf_index = 0` again: [3](#0-2) 

Any request/response that was dispatched *before* the migration and is still stored in `RequestCommitments`/`ResponseCommitments` with `leaf_index: 0..N-1` now collides with these freshly-pushed leaves. Proof generation (`generate_proof`/`Self::proof`) always queries the MMR at the *current* `NumberOfLeaves` using the *current* `INDEXING_PREFIX`, so `Self::leaf(pos)`/`get_elem` for leaf index `0` returns the new post-migration leaf's data, not the original request's: [4](#0-3) [5](#0-4) 

The migration's own `post_upgrade` check only verifies that `NumberOfLeaves`, `RootHash`, `InitialHeight`, and `Nodes` are cleared — it never checks whether any fee-bearing `RequestCommitments`/`ResponseCommitments` entries with in-range `leaf_index` values are still outstanding: [6](#0-5) 

This is the exact same root cause as the reported issue: a counter that is authoritative for both storage indexing and consumers' persisted references gets reset to `0` without accounting for records that were already indexed under the old numbering, so new writes silently overwrite/alias the meaning of those indices.

### Impact Explanation
Every request/response dispatched before the migration and not yet delivered/relayed loses its ability to ever be proven once a colliding number of new leaves are pushed post-migration. Since `dispatch_request` collects the relayer fee from the sender up front into `RELAYER_FEE_ACCOUNT` at dispatch time and marks `claimed: false`, and delivery/claim of that fee is gated on producing a valid MMR proof of the original commitment, the funds become permanently unrecoverable — the relayer can never construct a matching inclusion proof for the original leaf because the tree slot has been reassigned to a different, unrelated leaf. This is loss of user/relayer funds and an unauthorized/false linkage between a stored commitment and MMR proof data — squarely a "loss of funds" / "false proof acceptance" class impact on the bridge's core proof-verification pipeline, not a peripheral tooling bug.

### Likelihood Explanation
This is not a hypothetical attacker-triggered path — it fires deterministically the first time `ResetMmrTree` runs on a live chain that has any undelivered request/response in flight at the time of the upgrade, which is the normal, expected operating condition of a live bridge (there are essentially always some requests awaiting relay). No malicious actor, prover, or relayer collusion is required; the migration's own pre/post-upgrade checks do not detect the corrupted state, so the issue would silently manifest as unprovable in-flight messages and stuck fees the first time the runtime is upgraded with any pending ISMP traffic.

### Recommendation
- Before resetting `NumberOfLeaves`/`Nodes`, either (a) refuse to run the migration while any `RequestCommitments`/`ResponseCommitments` entries with `claimed: false` still exist / are undelivered, or (b) offset the leaf counter after reset by continuing from the previous `NumberOfLeaves` value (or a value guaranteed higher than any outstanding `leaf_index`) instead of starting at `0`, so old indices are never reused.
- Add a `post_upgrade` invariant that fails the migration if any outstanding commitment's `leaf_index` falls within the range that will be reused by new leaves.
- Alternatively, migrate/rewrite the `leaf_index`/`pos` fields of all outstanding `RequestCommitments`/`ResponseCommitments` in lock-step with the MMR reset so their references stay valid under the new numbering scheme.

### Proof of Concept
1. On a live chain, dispatch a POST request with a non-zero relayer fee via `pallet_ismp::Pallet::<T>::dispatch_request`; this stores `RequestCommitments[commitment] = { offchain: { leaf_index: k, pos }, fee, claimed: false }` and collects `fee` into `RELAYER_FEE_ACCOUNT`.
2. Do not relay/deliver this request yet.
3. Perform a runtime upgrade that runs `ResetMmrTree` (`modules/pallets/mmr/src/migrations.rs`), which kills `NumberOfLeaves`/`RootHash`/`InitialHeight` and clears `Nodes`, but leaves `RequestCommitments[commitment]` with `leaf_index: k` untouched.
4. Dispatch `k+1` new requests post-migration so the MMR's `NumberOfLeaves` reaches `k+1` again, causing a new leaf to be pushed at leaf index `k` (the same index recorded for the original request).
5. Attempt to call `Pallet::generate_proof(ProofKeys::Requests(vec![commitment]))` for the original commitment: the returned leaf data at position `k` now belongs to the newly-dispatched request, not the original one, so a relayer can never produce a valid proof of the original request's inclusion — the original request is permanently stuck and its already-collected relayer fee cannot be claimed via the normal delivery path.

	pub fn dispatch_request(request: Request, meta: FeeMetadata<T>) -> Result<H256, ismp::Error> {
		let commitment = hash_request::<Pallet<T>>(&request);

		if RequestCommitments::<T>::contains_key(commitment) {
			Err(ismp::Error::Custom("Duplicate request".to_string()))?
		}

		let (dest_chain, source_chain, nonce) =
			(request.dest_chain(), request.source_chain(), request.nonce());
		let leaf_index_and_pos = T::OffchainDB::push(Leaf::Request(request));
		// Deposit Event
		Pallet::<T>::deposit_event(Event::Request {
			request_nonce: nonce,
			source_chain,
			dest_chain,
			commitment,
		});

		RequestCommitments::<T>::insert(
			commitment,
			RequestMetadata {
				offchain: LeafIndexAndPos {
					leaf_index: leaf_index_and_pos.index,
					pos: leaf_index_and_pos.position,
				},
				fee: meta,
				claimed: false,
			},
		);

		Ok(commitment)
	}

	pub fn generate_proof(
		keys: ProofKeys,
	) -> Result<(Vec<T::Leaf>, Proof<H256>), sp_mmr_primitives::Error> {
		let leaf_indices_and_positions = match keys {
			ProofKeys::Requests(commitments) => commitments
				.into_iter()
				.map(|commitment| {
					let val = child_trie::RequestCommitments::<T>::get(commitment)
						.ok_or_else(|| sp_mmr_primitives::Error::LeafNotFound)?
						.offchain;
					Ok(val)
				})
				.collect::<Result<Vec<_>, _>>()?,
			ProofKeys::Responses(commitments) => commitments
				.into_iter()
				.map(|commitment| {
					let val = child_trie::ResponseCommitments::<T>::get(commitment)
						.ok_or_else(|| sp_mmr_primitives::Error::LeafNotFound)?
						.offchain;
					Ok(val)
				})
				.collect::<Result<Vec<_>, _>>()?,
		};
		let indices =
			leaf_indices_and_positions.iter().map(|val| val.leaf_index).collect::<Vec<_>>();
		let (leaves, proof) = Self::proof(indices)?;
		let proof = Proof {
			leaf_indices_and_pos: leaf_indices_and_positions,
			leaf_count: proof.leaf_count,
			items: proof.items,
		};

		Ok((leaves, proof))
	}
