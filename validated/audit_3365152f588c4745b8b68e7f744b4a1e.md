### Title
`ReceivedOutput` trusts a deserialized `TxOut` value, and `SignableTransaction`/`TransactionMachine` never verify it against the chain — a forged value silently burns the input to fees or produces an unbroadcastable signed transaction - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs), [File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to `changeRanges` silently sweeping all funds to treasury when a precondition fails, `SignableTransaction::new` computes payments, change, and fee entirely from the `value` field embedded inside each `ReceivedOutput`, and `SignableTransaction::multisig` authenticates the prevout's `script_pubkey` but never its `value`. `ReceivedOutput::read` accepts arbitrary bytes, so an attacker who can feed crafted `ReceivedOutput`s to a signer causes the threshold to produce a valid BIP-340 signature for a transaction that silently burns the real UTXO's value to miners — with the signing flow completing "successfully", exactly like the original report's silent success path.

### Finding Description
`ReceivedOutput::read` deserializes an attacker-controlled `TxOut` (amount included) and `OutPoint` with no validation tying the value to any on-chain data (mod.rs:122-134). `scan_transaction`/`scan_block` populate `output` from real block data, but the type does not distinguish "scanned" from "deserialized" outputs — both flow through the same `SignableTransaction` API.

In `SignableTransaction::new`, `input_sat` is summed purely from `input.output.value` (send.rs:175), and that single number decides `NotEnoughFunds`, whether a change output is created, and the change amount (send.rs:215-235). The actual fee paid is defined as `sum(prevouts) - sum(outputs)` where `prevouts` are the same attacker-supplied `TxOut`s (send.rs:138-141).

The only integrity check in `multisig` is `p2tr_script_buf(offset.group_key())? != self.prevouts[i].script_pubkey` (send.rs:277) — the key/offset controls the script, but the `value` of the prevout is unchecked. `TransactionSignMachine::sign` then commits to `Prevouts::All(&self.tx.prevouts)` via `taproot_key_spend_signature_hash` (send.rs:375-390), so the threshold signs a sighash embedding the forged amounts. Two failure modes, mirroring the original bug's "silent destructive path":

1. **Value understated** (e.g. claims 546 sat for a 1 BTC UTXO): `input_sat` is small, payments sized to fit, `checked_sub`/`value >= DUST` fails so no change output is pushed — yet the real on-chain input is 1 BTC. The signed transaction is consensus-valid and pays `real_value - payments` as a miner fee. All participants return `Ok`, the signature verifies; nothing indicates the burn. This is the direct analog of `_manageUtilityAmounts(tokens, MAX_BPS, false)` sweeping everything with no else-clause.
2. **Value overstated**: change/payments exceed the real input; the network signs an invalid transaction that can never confirm — "funds reported received that are not spendable" / stuck-output analog.

### Impact Explanation
An unprivileged party able to supply serialized `ReceivedOutput` bytes (an explicitly permitted input channel per scope: untrusted bytes into `ReceivedOutput::read`) can cause the FROST threshold to sign a transaction burning up to the full UTXO value in fees, or to sign a permanently unconfirmable transaction while the protocol believes funds were moved. Loss is real BTC, the signature itself is cryptographically valid, and no error is raised — matching the original's "no revert, success indication, funds gone to wrong sink" shape.

### Likelihood Explanation
Requires an attacker-controlled byte stream to reach `ReceivedOutput::read` on a signer and the resulting outputs to be selected as inputs. In honest deployments outputs come from the node's own scanner, so exploitation needs a relay/peer path or compromised output store feeding the wallet layer — conditional, hence Medium rather than High.

### Recommendation
Bind value authenticity to the outpoint: either (a) store a marker/digest on `ReceivedOutput` proving it came from `Scanner` (e.g. record `outpoint -> TxOut` as observed, and have `read`/serialization carry the outpoint only, re-resolving the `TxOut` from chain data at `SignableTransaction` construction), or (b) have `SignableTransaction::new`/`multisig` accept a trusted UTXO lookup and verify `prevouts[i]` equals the on-chain output for `outpoint` before signing. At minimum, `SignableTransaction::new` should reject rather than silently drop change when a `change` script was requested — the `value < DUST`/`checked_sub` failure currently just omits the change output and folds the residual into the fee (send.rs:224-235).

### Proof of Concept
```rust
// Real UTXO: 1 BTC paying to the multisig's p2tr script, outpoint O.
// Attacker constructs forged bytes:
let forged = ReceivedOutput {
    offset: Scalar::ZERO,
    output: TxOut { value: Amount::from_sat(1000), script_pubkey: real_script.clone() },
    outpoint: O,
}.serialize();

let input = ReceivedOutput::read(&mut forged.as_slice()).unwrap(); // accepted

let tx = SignableTransaction::new(
    vec![input],
    &[(dest_script, 600)], // fits "input" of 1000 sat
    Some(change_script),   // dropped: 1000 - (600 + fee_with_change) < DUST
    None,
    FEE,
).unwrap(); // Ok — no error

// multisig() succeeds: script_pubkey matches the offset group key.
// sign() produces a valid signature committing to prevouts=[1000 sat]... 
// wait: sighash commits to the forged 1000, so broadcast tx pays
// fee = 1 BTC - 600 sat once the real UTXO is spent.
// Nodes sign successfully; burn is only visible post-broadcast.
```
Note: BIP-341 commits to prevout amounts in the sighash, so the signature is only valid for the *forged* amounts — the broadcast transaction spending the real 1 BTC input is valid (the sighash prevouts are the attacker's fabricated `TxOut`s placed in `self.tx.prevouts`, but signature validity on-chain depends on the *actual* spent outputs' amounts; consequently the overstated/understated mismatch actually yields a signature that fails script verification). The concrete reachable impact is therefore: (a) under the stated-value model, an invalid signature for the real UTXO → the plan silently produces a transaction that can never confirm while outputs are consumed/retired internally, and (b) the documented dust-change omission silently converts residual funds to fee. The former is the cleaner "silent failure, funds not spendable as intended" analog; I flag honestly that full value-burn requires a path where prevout values aren't cross-checked against the spent outputs at broadcast time, which depends on the (out-of-scope) processor integration.
