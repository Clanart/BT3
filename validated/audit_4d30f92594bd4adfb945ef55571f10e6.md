### Title
Unbounded recursive `DecodeRLP` in `AccountKeyRoleBased` allows stack-exhaustion DoS via a single crafted `AccountUpdate`/`AccountCreation` transaction - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each sub-key by re-entering the generic `AccountKeySerializer` decode path, which in turn can construct another `AccountKeyRoleBased` and recurse again. No depth limit is enforced during decoding — the composite-type restriction (`kerrors.ErrNestedCompositeType`) is only checked *after* decoding succeeds, in `CheckInstallable`/`CheckUpdatable`/`checkAccountKeyZeroValues`. This mirrors the CVE-2019-9545 bug class: a recursive parser function reachable from a single untrusted, attacker-supplied blob, with no recursion-depth guard at parse time.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of RLP-encoded sub-keys and, for each one, calls `rlp.DecodeBytes` into a fresh `AccountKeySerializer`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads the key type and then decodes the concrete key object via `s.Decode(serializer.key)`: [2](#0-1) 

If the decoded key type is again `AccountKeyTypeRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`, and the cycle repeats. The only place the codebase forbids a `RoleBased` key from containing another `RoleBased` key (`ErrNestedCompositeType`, `IsCompositeType`) is in the **post-decode** validation paths `CheckInstallable`/`CheckUpdatable`: [3](#0-2) 

and in the RPC helper `checkAccountKeyZeroValues`, which explicitly documents that "roleBasedKey cannot contain a roleBasedKey": [4](#0-3) 

None of these checks run during the RLP decode itself. Since `TxInternalDataAccountUpdate`/`TxInternalDataAccountCreation` carry an `AccountKey` field that is RLP-decoded as part of ordinary transaction deserialization (before any pool/consensus validation), an attacker only needs to submit one transaction (via `eth_sendRawTransaction`, p2p tx broadcast, or inside a block) whose `AccountKey` payload is nested `RoleBased` keys N levels deep to force N levels of mutually-recursive Go function calls (`DecodeRLP` → `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `s.Decode` → `AccountKeyRoleBased.DecodeRLP` → …) purely during decoding.

The transaction-size guard (`MaxTxDataSize` = 128 KB) is enforced only **after** the transaction has already been fully RLP-decoded: [5](#0-4) 

so the recursive decode runs unconditionally on every node that receives the raw bytes (RPC node, block proposer, all validators re-executing the block, or peers relaying the tx over p2p) before that size check has any chance to reject it.

### Impact Explanation
Deep unbounded recursion at RLP-decode time can exhaust the goroutine stack, causing a fatal, unrecoverable Go runtime crash (`runtime: goroutine stack exceeds ... - fatal error: stack overflow`), which cannot be caught by `recover()`. Because this decode path runs on:
- any public RPC node processing `eth_sendRawTransaction` / decoding pooled transactions,
- every peer relaying the transaction over the p2p transaction-broadcast protocol,
- every validator/full node executing the block containing this transaction,

a single unprivileged transaction sender can crash multiple/most nodes in the network simultaneously, producing a network-wide denial of service. This satisfies the "state divergence between honest nodes" / node-crash impact bar (a subset of nodes may crash while others that already rejected/haven't processed it don't, and even in the best case it is a broad availability outage triggered by one crafted transaction).

### Likelihood Explanation
High. Constructing the nested payload requires no special privileges — only crafting an `AccountKeyRoleBased` value containing another `AccountKeyRoleBased` (recursively) and RLP-encoding it as the `AccountKey` field of a signed `AccountUpdate`/`AccountCreation` transaction, then submitting it through any public RPC endpoint. Within the existing 128 KB transaction-size limit there is ample budget (each nesting level costs only a handful of bytes) to reach thousands of recursion levels, which is typically enough to overflow a goroutine stack. No authentication, special account state, or governance permission is required.

### Recommendation
Enforce a maximum nesting depth for `AccountKeyRoleBased`/composite key decoding *during* `DecodeRLP` (e.g., pass/track a depth counter through `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP`, and reject decode immediately once depth > 1, consistent with the existing invariant that role-based keys cannot nest). This check must happen at decode time, not only in the later `CheckInstallable`/`CheckUpdatable`/RPC-only validation, since the recursive decode itself already performs the unbounded work before those checks are reached.

### Proof of Concept
Conceptually (cannot be executed in this read-only environment):
1. Recursively construct `k_0 = AccountKeyPublic`, then `k_i = AccountKeyRoleBasedWithValues([]AccountKey{k_(i-1)})` for `i = 1..N`, with `N` chosen so the RLP-encoded size of `k_N` approaches ~120 KB (thousands of nesting levels).
2. Build an `AccountUpdate` transaction (or `AccountCreation`) with `TxValueKeyAccountKey = k_N`, sign it, and RLP-encode the transaction (`rlp.EncodeToBytes(tx)`).
3. Submit the raw transaction via `eth_sendRawTransaction` to a public RPC node, or inject it into the p2p transaction gossip channel.
4. When the receiving node calls `rlp.DecodeBytes` on the transaction (in `TxPool.validateTx`'s decode path, in p2p transaction message handling, or in block processing on validators), `AccountKeyRoleBased.DecodeRLP` recurses `N` times before the transaction-size (`MaxTxDataSize`) or `CheckInstallable`/`ErrNestedCompositeType` checks ever run, exhausting the goroutine stack and crashing the process with a fatal, non-recoverable `stack overflow` runtime error.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
