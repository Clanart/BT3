## Title
Missing "already filled" guard lets a solver double-fill a cross-chain intent and receive two escrow-redemption dispatches for one order - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The external report's core defect is a state-mutating transfer path that omits a required precondition check that exists conceptually elsewhere in the system (a per-user gate that should have blocked the action). The local analog is `_fillCrossChain()` in `ExtrinsicIntents.sol`, which unconditionally writes `_filled[commitment] = msg.sender` without first checking that the commitment isn't already filled, unlike the sibling same-chain path and the public entrypoint pattern used elsewhere in the codebase.

### Finding Description
`_fillCrossChain` is the cross-chain fill handler for `IntentGatewayV2`/`ExtrinsicIntents`: [1](#0-0) 

Line 92 sets `_filled[commitment] = msg.sender;` immediately, with **no preceding check** such as `if (_filled[commitment] != address(0)) revert Filled();`. Compare this to `_cancelFromSource`/`onGetResponse`, which do gate on `_filled` state (via the cross-chain GET proof and `Filled()` revert) [2](#0-1) , and to `_fillSameChain`, which relies on `_partialFills` and escrow-balance decrements (`_orders[commitment][token]`) as the actual double-spend guard rather than `_filled` alone [3](#0-2) .

Because `_fillCrossChain` has no escrow bookkeeping on the destination chain (the escrow lives on the *source* chain, referenced only by `commitment`), the only local invariant that should prevent a second fill of the same order on the destination is `_filled[commitment]`. Since that check is missing, `fillOrder` can be called a second (or Nth) time for the same `commitment` before the first `RedeemEscrow` message is even delivered to the source chain. Each call:
- Re-enters the full output-transfer loop, pulling additional solver funds to the beneficiary and dust to the protocol (harmless to the protocol, but wastes solver funds/griefing surface),
- Re-executes `_execute(order, outputsLen)` a second time,
- Dispatches a second, independent `RedeemEscrow` `WithdrawalRequest` for the exact same `commitment` back to the source chain via `IDispatcher(hostAddr).dispatch(...)`.

On the source chain, `_withdraw()` (in `IntentsBase.sol`) is the only backstop: it reverts on the *second* delivered redeem request only because `_orders[commitment][token]` has already been zeroed by the first successful redeem [4](#0-3) . This means the source-side safety net depends entirely on delivery ordering and existing escrow balance — if the two redeem requests race, or if partial/multi-asset escrow amounts allow both to partially succeed (e.g., outputs list order differs or amounts don't zero out atomically across multiple tokens in one iteration), a duplicate settlement can slip through for whichever token index isn't fully drained by the first call. Even in the fully-blocked case, the second `RedeemEscrow` dispatch still burns a real Hyperbridge request/fee and forces the source-side `onAccept`/`_withdraw` call to revert non-gracefully, which is a wasted/likely stuck message.

### Impact Explanation
This matches the bounty's "duplicate settlement/double-claim" and "unauthorized execution" classes: a normal unprivileged solver (not a malicious relayer, prover, or admin) can trigger multiple settlement dispatches for one order by simply calling the public fill entrypoint twice in the same block/transaction window before the first message is finalized, since the destination-side idempotency check (`_filled`) that should prevent this is absent from `_fillCrossChain`. Even where the source-side escrow decrement ultimately blocks a literal double-payout, the missing guard means the *destination* chain's idempotency invariant is broken, output funds can be pulled from the solver more than once, `_execute` (arbitrary calldata dispatch) can run twice, and duplicate cross-chain messages are generated — all without any peer/relayer/admin compromise.

### Likelihood Explanation
High: `fillOrder` (which reaches `_fillCrossChain`) is a public, unprivileged entrypoint. Nothing prevents a solver — or anyone — from calling it twice for the same `order`/`commitment` back-to-back; there is no reentrancy lock or "already filled" check gating entry into this specific function, unlike its same-chain sibling which at least tracks `_partialFills` per output token.

### Recommendation
Add an explicit idempotency check at the top of `_fillCrossChain`, mirroring the pattern used for cancellation:
```solidity
if (_filled[commitment] != address(0)) revert Filled();
_filled[commitment] = msg.sender;
```
This should be the first state mutation, before any external calls or dispatches, consistent with checks-effects-interactions and with how `onGetResponse`/`_cancelFromSource` already treat `_filled` as the authoritative "already handled" flag.

### Proof of Concept
1. Solver A places/observes a valid cross-chain `Order` with commitment `C` and calls `fillOrder(order, options)` which routes to `_fillCrossChain`.
2. Before the resulting `RedeemEscrow` `DispatchPost` is delivered to the source chain (network delay), Solver A (or any other address) calls `fillOrder(order, options)` again with the same `order`/`commitment` `C`.
3. `_fillCrossChain` runs a second time: `_filled[C]` is overwritten (no revert), a second round of output transfers/`_execute` occurs, and a second `RedeemEscrow` message for commitment `C` is dispatched to the source chain.
4. On the source chain, the first `RedeemEscrow` delivery zeroes `_orders[C][token]` via `_withdraw`; the second delivery either reverts (wasted message, `UnknownOrder`) or, if escrow accounting for a subset of multi-asset tokens hasn't fully zeroed yet, partially double-releases funds — demonstrating that the destination-side idempotency invariant that should stop step 2 from ever happening is missing.

                IERC20(token).safeTransfer(beneficiary, amount);
