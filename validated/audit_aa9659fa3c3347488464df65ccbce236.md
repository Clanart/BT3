### Title
ProtoJSON parser resolves alternate field-name spellings (`camelCase` vs. `original_name`) to the same field, but its duplicate-key detector only compares raw JSON keys — allowing silent, unflagged "last value wins" field overwrite - ([File: python/google/protobuf/json_format.py])

### Summary
Python's ProtoJSON `Parse()`/`ParseDict()` pipeline runs two independent, disagreeing "is this a duplicate?" checks over the same JSON object: a lexical, string-key-only check (`_DuplicateChecker`) and a semantic, field-identity-based resolution (name lookup that accepts both `original_name` and `jsonName`). Because the lexical check never sees that two differently-spelled keys resolve to the identical `FieldDescriptor`, an attacker can supply the same field twice under its two accepted spellings and have the second value silently overwrite the first with no error — exactly the "different components disagree on how many distinct fields/tokens are present" root cause that underlies HTTP request smuggling (CWE-444).

### Finding Description
`json_format.Parse()` first loads the JSON text with `json.loads(text, object_pairs_hook=_DuplicateChecker)` [1](#0-0) , whose only job is to reject **exact string-key** duplicates: [2](#0-1) . This is a purely lexical/tokenizer-level invariant: "no two identical JSON key strings in one object."

However, the downstream message-population logic resolves a JSON key to a `FieldDescriptor` by trying both the field's canonical `name` and its `json_name`/camelCase spelling, so `"int32_value"` and `"int32Value"` are two different JSON keys that resolve to the *same* protobuf field. The library's own test suite explicitly documents this gap as an acknowledged defect: [3](#0-2) 

The comment is unambiguous: *"this behavior is non-spec and an oversight bug in the implementation... the duplicate field checker intends [to] reject inputs with duplicate key names, but it only catches keys that are exact matches and not alternate spellings that correspond to the same field."* The observable result: `{"int32Value": 1, "int32_value": 2}` parses successfully and yields `int32_value == 2` — the second occurrence silently wins, with zero indication to the caller that a "duplicate field" condition (which the library explicitly tries to reject in the exact-match case) occurred.

The C++/Java/C# ProtoJSON implementations show this is a known, cross-language fault line in the spec itself: the conformance suite explicitly permits either "last wins" or "parse failure" for the *exact-duplicate-name* case (`FieldNameDuplicate`, `FieldNameDuplicateDifferentCasing1/2` in `RunValidJsonTestOrParseFailure`) [4](#0-3) , and Java's own `JsonFormatTest` explicitly asserts that duplicated fields under alternate names/oneof members *must* raise `InvalidProtocolBufferException` [5](#0-4) . The Python implementation is the outlier that fails this invariant while claiming to enforce it, because its duplicate check operates at the wrong layer (raw JSON string keys) relative to where the semantic decision is made (resolved `FieldDescriptor` identity).

### Impact Explanation
This is the classic "inconsistent interpretation of the same input by different components" bug class (CWE-444), transplanted from HTTP header parsing to ProtoJSON field parsing:
- A validating/allow-listing gateway, WAF, or logging component that inspects the raw JSON object (as a dict of string keys, the natural and common way to sanity-check JSON before handing it to protobuf) would see two distinct, unique keys — `int32Value` and `int32_value` — and would have no lexical basis to treat them as "the same field twice." It may log/allow/audit based on the *first* value it observes for a given canonical name, or may simply see no duplication at all.
- The protobuf `Parse()` call downstream silently resolves both keys to one field and applies "last value wins," so the attacker-controlled *second* occurrence is what actually lands in the deserialized message and drives application logic — potentially the opposite of what any front-end validation/inspection layer believed was being enforced.
- Because the library's own exact-duplicate detector explicitly treats "duplicate field assignment" as an error condition it aims to reject, but silently permits it via this alternate-spelling bypass, application code relying on `Parse()` raising `ParseError` for duplicate/conflicting field assignments (a documented, deliberate hardening behavior) gets a false sense of security.

This does not cause memory corruption or crashes; the impact is strictly a semantic/integrity disagreement between what a caller may believe was validated/rejected and what protobuf actually accepted, matching the Medium-severity, integrity-only profile (`C:N/I:L`) of the original aiohttp smuggling advisory. No RCE or resource-exhaustion claim is made or implied.

### Likelihood Explanation
Any Protobuf/ProtoJSON consumer exposed to attacker-controlled JSON via `google.protobuf.json_format.Parse`/`ParseDict` (the "supported public parse API" surface named in the assumptions) is affected without any special configuration — `ignore_unknown_fields` is irrelevant, and no privileged access or hostile schema is required. The bypass requires only knowing the two accepted spellings of a field name (`snake_case` and `camelCase`), which are always both derivable from any `.proto` schema (trusted schema assumption is preserved — the attacker only needs the schema, not to control it). This makes the likelihood high wherever ProtoJSON is used as a boundary format between differently-implemented validation/routing layers and the final protobuf deserializer — precisely the "smuggling" deployment pattern (proxy/gateway + backend) called out in the source advisory.

### Recommendation
Move duplicate-field detection in `python/google/protobuf/json_format.py` from the raw-JSON-key layer (`_DuplicateChecker`) to the resolved-`FieldDescriptor` layer, i.e., track "seen" state per `FieldDescriptor` (as the C++/Java implementations already do via `RecordAsSeen`/`seenOneofs`) rather than per literal JSON string key, and raise `ParseError` when the same resolved field (regardless of which of its accepted name spellings was used) is assigned more than once. This aligns Python's behavior with the explicit invariant the exact-duplicate case already enforces, and with the conformance-suite expectation that duplicate-name inputs be either uniformly rejected or uniformly last-wins — not silently divergent depending on which spelling is used.

### Proof of Concept
Using the repository's own Python ProtoJSON runtime (`json_format.Parse`) against a message containing an `int32_value` field:

```python
from google.protobuf import json_format
import json_format_proto3_pb2  # test proto used in json_format_test.py

msg = json_format_proto3_pb2.TestMessage()
# Two different JSON keys resolving to the SAME protobuf field.
json_format.Parse('{"int32Value": 1, "int32_value": 2}', msg)
print(msg.int32_value)  # -> 2, no error raised
```

This exactly reproduces the scenario already codified (and labeled "an oversight bug") in `testDuplicateFieldAlternateNames` [6](#0-5) , contrasted with the exact-duplicate case `testDuplicateField`, which *does* raise `ParseError: Failed to load JSON: duplicate key int32Value.` [7](#0-6) . The divergence between these two nearly-identical inputs — one rejected, one silently accepting a field overwrite — is the concrete, provable analog of the "same bytes, two different interpretations" failure mode described in the source HTTP request-smuggling advisory.

```python
def _DuplicateChecker(js):
  result = {}
  for name, value in js:
    if name in result:
      raise ParseError('Failed to load JSON: duplicate key {0}.'.format(name))
    result[name] = value
  return result
```
