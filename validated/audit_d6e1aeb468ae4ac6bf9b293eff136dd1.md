### Title
Missing identity-point check on registered DKG encryption keys makes secret shares decryptable by anyone — crypto/dkg/pedpop/src/encryption.rs

### Summary
`EncryptionKeyMessage::read` (encryption.rs:57–59) and `Decryption::register`/`Encryption::register` (encryption.rs:351–362, 452–458) accept the registered per-participant encryption public key (`enc_key`) via `C::read_G`, i.e. `Ciphersuite::read_G`. That implementation (crypto/ciphersuite/src/lib.rs:91–101) checks canonicity but does **not** reject the identity point — unlike the stricter `Curve::read_G` in crypto/frost/src/curve/mod.rs:125–131, which explicitly errors on `is_identity()`. A participant who registers `enc_key = identity` causes every dealer's ECDH (`ecdh(private = key, public = to)`, encryption.rs:95–97) to produce the identity point as the shared secret. `cipher()` (encryption.rs:101–133) then derives the ChaCha20 key entirely from public values (`context`, and `shared_key` = the known identity encoding), with the fixed IV `b"DKG IV v0.2\0"`. The result is that the EncryptedMessage carrying that participant's FROST secret share is effectively transmitted in cleartext to any observer — the direct analog of the reported class (CWE-20 missing input validation + CWE-327 broken/risky cryptography: an ECDH producing a publicly known key).

### Finding Description
- `read_G` used for `enc_key` is `Ciphersuite::read_G` (encryption.rs:58), which returns any canonical point including identity; the identity-rejecting variant only exists on `Curve` (frost/curve/mod.rs:125–131) and PedPoP is generic over `Ciphersuite`, not `Curve`.
- `Decryption::register` only asserts non-re-registration (encryption.rs:356–360); it performs no validity check on `msg.enc_key`.
- `encrypt` (encryption.rs:135–168) computes `ecdh::<C>(&key, to)` = `to * key`. With `to` = identity, the shared point is identity regardless of the ephemeral `key`.
- `cipher()` transcripts `"DKG Encryption v0.2"`, `context`, and `shared_key` bytes, then uses a static IV — so with an identity ECDH output the keystream is computable by anyone who knows the (public) context and the identity point's canonical encoding.
- No blame path exists for this: the PoP on `EncryptedMessage` covers the ephemeral `msg.key`, not the registered `enc_key`; the encryption key itself carries no proof of possession and no validity proof. The misbehavior is undetectable — the point is a perfectly canonical encoding.
- The plaintext is a `SecretShare<C::F>` (lib.rs:366–369, `generate_secret_shares`), i.e., a FROST/PedPoP share — the exact secret material the encryption layer exists to protect.

### Impact Explanation
Key share recovery: every share `f_i(victim_index)` sent to a participant who registered an identity (or otherwise publicly-decryptable, e.g. small-subgroup-free prime-order curves make identity the only such point) encryption key is recoverable by any passive observer of the DKG transcript — no authenticated channel access, threshold collusion, or validator privileges required. This defeats PedPoP's stated confidentiality guarantee ("secret shares ... sent over authenticated channels"), enables a corrupted or coerced participant to covertly exfiltrate its key share to a third party (who can then impersonate that participant's share in FROST signing sets containing them) while remaining un-blameable, and precisely mirrors the advisory class: sensitive protocol material transmitted under an encryption layer that yields a publicly computable key.

### Likelihood Explanation
Requires a participant to register an identity encryption key — a one-time substitution of a canonical point in a public message. It needs no secret knowledge, produces no detectable fault (no blame proof is possible for it), and leaks material covertly. On its own it leaks only that participant's incoming share; the severity is bounded below High because confidentiality loss is per-participant and the strongest exploitation requires the registering participant to be complicit or coerced. Rated **Medium**.

### Recommendation
In `EncryptionKeyMessage::read` / `Decryption::register`, reject the identity point for `enc_key` (check `enc_key.is_identity()` and error). More robustly, require a Schnorr proof-of-possession over the registered encryption key at registration time, which both proves scalar knowledge and implicitly excludes identity. Apply the same check anywhere `Ciphersuite::read_G` is used for keys on which ECDH will be performed (e.g., `EncryptedMessage::read`'s `key` field at encryption.rs:173, since an identity `msg.key` likewise produces a publicly known shared secret on the decryption path).

### Proof of Concept
1. Participant `P` builds its round-1 `EncryptionKeyMessage` with `enc_key` = canonical identity encoding (e.g., `0x00 * 32` for Ristretto) instead of `generator * enc_key_scalar`. `EncryptionKeyMessage::read` accepts it; `verify_r1`'s PoK check covers `commitments[0]` (lib.rs:323–329), not `enc_key`, so registration succeeds.
2. Every honest dealer calls `self.encryption.encrypt(rng, P, share_bytes)` → `ecdh = identity * key = identity` (encryption.rs:154).
3. Observer computes the keystream itself: `transcript = RecommendedTranscript::new(b"DKG Encryption v0.2")`, `append_message(b"context", context)`, `domain_separate(b"encryption_key")`, `append_message(b"shared_key", identity.to_bytes())`, `key = challenge(b"key")[..32]`, `iv = b"DKG IV v0.2\0"`, `ChaCha20::new(key, iv)` — then XORs against `msg.msg` from the broadcast `EncryptedMessage` to recover `P`'s secret share bytes, which deserialize to a valid `C::F`.

This was verified against `Ciphersuite::read_G` (ciphersuite/src/lib.rs:91–101, no identity rejection), `Curve::read_G` (frost/curve/mod.rs:125–131, does reject — confirming the check is known but unapplied in DKG), `Decryption::register` (encryption.rs:351–362), `ecdh`/`cipher`/`encrypt` (encryption.rs:95–133, 135–168), and the share-generation path (`generate_secret_shares`, pedpop/src/lib.rs:357–379).
