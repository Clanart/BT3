### Title
Improper anchoring in `githubAssetVideoRegex` allows attacker-controlled video source to bypass the GitHub user-asset allowlist - (File: `app/src/lib/markdown-filters/video-url-regex.ts`)

### Summary
`githubAssetVideoRegex` is meant to restrict `<video>` tags rendered from markdown to only reference GitHub's `user-images.githubusercontent.com` CDN. However, the regex does not require a domain-boundary character (such as `/`, `:`, or end-of-string) after the trusted hostname, so any string that merely *starts with* the literal string `https://user-images.githubusercontent.com` is accepted — including URLs whose real host is entirely attacker-controlled.

### Finding Description
The regex is built as: [1](#0-0) 

`'^' + escapeRegExp(user_images_cdn_url) + '.+' + videoExtensionRegex.source`

Because the trusted literal `https://user-images.githubusercontent.com` is immediately followed by `.+` with no required separator, a URL like:

```
https://user-images.githubusercontent.com.attacker.example/evil.mp4
```

satisfies the pattern: it starts with the exact trusted prefix, followed by arbitrary additional characters, and ends in an allowed video extension. The actual host of this URL is `user-images.githubusercontent.com.attacker.example`, entirely controlled by the attacker, not GitHub's CDN.

This regex is used in two node filters applied to markdown rendered from repository/PR/issue content:
- `VideoTagFilter`, which keeps a `<video src="...">` tag only if `githubAssetVideoRegex.test(el.src)` passes: [2](#0-1) 
- `VideoLinkFilter`, which converts an auto-linked `<a href="...">` pasted video URL into a `<video src="...">` element when `githubAssetVideoRegex.test(node.firstChild.href)` passes: [3](#0-2) 

Both filters are part of the pipeline invoked on every markdown render via `applyFilters` in `SandboxedMarkdown.onDocumentDOMContentLoaded`: [4](#0-3) 

Since the check is a simple string-prefix match rather than a validated URL/host parse, an attacker who controls markdown text (an issue body, PR description, PR comment, or committed markdown file rendered by Desktop) can smuggle a `<video>` element (or a plain pasted link, which `VideoLinkFilter` will helpfully convert to a `<video>` tag) whose `src` resolves to an attacker-controlled origin, while passing the intended GitHub-CDN allowlist check.

### Impact Explanation
The rendered markdown is loaded inside a sandboxed `iframe` via a base64 `data:` URI, and the HTML is passed through `DOMPurify.sanitize` before being embedded: [5](#0-4) 

`DOMPurify` allows `<video src>` for standard `<video>` tags, so this is not blocked by sanitization — the vulnerability is specifically that the intended GitHub-CDN-only allowlist can be bypassed, not that arbitrary HTML/script is injected. The practical outcome is that Desktop will render/preview attacker-controlled media (arbitrary remote resource) as if it were a validated GitHub-hosted asset, which allows: bypassing an explicit intended-content restriction (the whole design purpose of `githubAssetVideoRegex` is to prevent arbitrary attacker-supplied media sources), and leaking the user's IP/UA and request metadata to an attacker-controlled server whenever the video preview attempts to load (a tracking/beacon primitive triggered without further user interaction beyond viewing the issue/PR/commit). It does not, by itself, achieve script execution, IPC/sandbox escape, or credential exfiltration given the iframe/DOMPurify sandboxing already in place — the code-execution/file-write bug bounty tiers described in the scope are not met by this specific regex flaw. It is a real logic bug (broken allowlist) but its concrete impact is limited to loading attacker-controlled media/beaconing under a false trust label, not the higher-severity outcomes listed as in-scope ("valid impact" criteria).

### Likelihood Explanation
This is a straightforward regex construction bug independent of any additional privilege — any GitHub user (or repository/PR content) can trigger it just by supplying a crafted `<video src="...">` tag or a plain URL string in markdown that GitHub Desktop later renders in a PR/issue/commit view. No unusual user action is required beyond viewing normally-rendered content.

### Recommendation
Replace the naive string+regex concatenation with a proper URL parse and origin/host equality check (e.g., `new URL(url).host === 'user-images.githubusercontent.com'`) rather than a prefix match, and keep the extension check separate, applied to the parsed pathname.

### Proof of Concept
1. Create a GitHub issue/PR comment or markdown file containing:
```html
<video src="https://user-images.githubusercontent.com.attacker.example/evil.mp4"></video>
```
or a plain auto-linked URL:
```
https://user-images.githubusercontent.com.attacker.example/evil.mp4
```
2. Open this content in GitHub Desktop (e.g., PR description viewer, which uses `SandboxedMarkdown`).
3. Observe that `githubAssetVideoRegex.test(...)` returns `true` (because the string starts with the trusted literal), the `<video>` tag is retained/created, and the video element attempts to load content from `user-images.githubusercontent.com.attacker.example`, an attacker-owned domain, despite the intended allowlist restricting sources to GitHub's actual CDN host.

**Uncertainty**: I could not fully verify the CSP/`sandbox` attribute settings applied to the iframe element that hosts this markdown (e.g., whether `allow-scripts`/network fetches are restricted at the Electron/webContents level), since the relevant portion of `sandboxed-markdown.tsx` (JSX render method defining the `<iframe>` element itself) was not returned by my searches. This affects only the precise blast radius (e.g., whether the `<video>` element can actually initiate a network request to the attacker host, or whether outbound requests from the iframe are blocked entirely), not the existence of the regex bypass itself, which is confirmed directly from the source. [6](#0-5)

```typescript
import escapeRegExp from 'lodash/escapeRegExp'

const user_images_cdn_url = 'https://user-images.githubusercontent.com'

// List of common video formats obtained from
// https://developer.mozilla.org/en-US/docs/https://developer.mozilla.org/en-US/docs/Web/Media/Formats/Video_codecs/Media/Formats/Video_codecs
// The MP4, WebM, and Ogg formats are supported by HTML standard.
const videoExtensionRegex = /(mp4|webm|ogg|mov|qt|avi|wmv|3gp|mpg|mpeg|)$/

/** Regex for checking if a url is a github asset cdn video url */
export const githubAssetVideoRegex = new RegExp(
  '^' + escapeRegExp(user_images_cdn_url) + '.+' + videoExtensionRegex.source,
  'i'
)
```
