## Title
Stale-content overwrite in Copilot merge-conflict resolution silently discards concurrent manual edits - (File: `app/src/lib/stores/app-store.ts`)

### Summary
`_applyCopilotConflictResolutions` writes AI-generated file content to disk based on a snapshot of the conflicted file (`rawContent`) that was read minutes earlier during `buildConflictContext`. The only staleness guard checks whether the file has become *fully* resolved on disk; it does not detect the case where the user has *partially* edited the still-conflicted file in an external editor while Copilot was thinking or while the result dialog was open. In that case the stale, AI-reassembled content is written over the user's current on-disk edits and staged for commit without warning.

### Finding Description
The conflict-resolution flow reads each conflicted file's content once, at the start of the flow: [1](#0-0) 
This `rawContent` is stored per-file and is later used, well after the (potentially long) Copilot API call completes, to splice the model's per-hunk resolutions back into the file: [2](#0-1) 

The reassembled result is not written immediately — it is stored in app state and only applied when the user later clicks "Continue Merge" in the result dialog: [3](#0-2) 

At apply time, `_applyCopilotConflictResolutions` performs exactly one staleness check: it skips the write only if the file is *no longer* reported as conflicted at all (i.e. the user fully resolved it themselves): [4](#0-3) 

This guard only covers the "fully resolved externally" case. If the user instead makes a partial manual edit to the still-conflicted file (e.g., edits content inside/around a conflict hunk, or resolves some hunks but leaves markers for others so `git status` still reports it as an unresolved conflict), `onDiskFile.status` still satisfies `isConflictedFileStatus(...) && hasUnresolvedConflicts(...)`, so the skip is not taken, and `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` unconditionally overwrites the file with content reassembled from the stale `rawContent` captured before the user's edit — then stages it with `git add`.

The gap between the read and the write is attacker/user-observable and can be long: the SDK call itself can take a documented 15–120+ seconds (see the timing telemetry buckets in the same function), and the result dialog then waits indefinitely for the user to review and click "Continue Merge": [5](#0-4) 

This is directly analogous to the reported bug class: a value (`balanceOf()` in the report; here, on-disk file content / `rawContent`) is checked/read once, trusted for a security/integrity-relevant decision, and can silently change before it's actually used, and the existing guard (the `require` balance check in VTVL; here, the `hasUnresolvedConflicts` check) does not cover the drift that actually occurs in practice.

### Impact Explanation
The result is silent corruption of what the user ultimately commits: their manual, in-progress edits to a conflicted file made through an external editor (or another instance of the app) are discarded and replaced with the AI's earlier-computed content, which is then staged via `git add` and can end up in the merge/rebase/cherry-pick commit without any diff review reflecting the loss. This matches the "silent corruption of what the user commits or pushes" impact category — no local/admin access or malware is required, only concurrent, entirely normal use of an external editor during a merge conflict resolution flow that Desktop itself invites the user to leave open while Copilot works and while they review results.

### Likelihood Explanation
Moderate. It requires the user to edit the same conflicted file outside Desktop while a Copilot resolution run is in flight or its result dialog is open — a realistic workflow, since users commonly jump into an editor to inspect/adjust conflicts while waiting, and the changelog for this codebase already shows the project has once fixed an adjacent, narrower version of this class of bug (`3.5.13-beta3`: "Resolve Copilot conflict resolution data loss where file content outside conflicted regions was overwritten..." — #22349): [6](#0-5) 
That fix addressed clobbering of non-conflicted regions via the hunk-splice reassembly, but it did not add a check for the file's content having changed since `rawContent` was captured, leaving this partial-edit staleness path open.

### Recommendation
Before writing `resolution.resolvedContent` to disk, re-read the file's current content and compare it (or a hash) against the `rawContent`/context captured at `buildConflictContext` time. If the on-disk content differs, treat the file as stale (skip the write and surface it to the user for manual reconciliation, similar to the existing "resolved externally" skip) rather than assuming the only possible change is full resolution.

### Proof of Concept
1. Start a merge/rebase with conflicting files; trigger "Resolve with Copilot" (`dispatcher.attemptCopilotConflictResolution`) so `buildConflictContext` reads and caches `rawContent` for `file.txt`.
2. While the Copilot request is in flight (up to ~120s per the app's own timing buckets) or after it completes while the `CopilotConflictsDialog` result view is shown, open `file.txt` in an external editor and make a manual edit inside one of the still-unresolved conflict hunks (leaving the conflict markers for at least one other hunk so git still reports the file as conflicted/unresolved), then save.
3. Return to Desktop and click "Continue Merge" (`onContinue` → `dispatcher.applyCopilotConflictResolutions`).
4. `_applyCopilotConflictResolutions` finds `onDiskFile` still `isConflictedFileStatus` and still `hasUnresolvedConflicts`, so it does not skip the file; it calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` using content reassembled from the stale `rawContent`, discarding the manual edit made in step 2, then stages it via `git add`.
5. The subsequent commit contains the AI's stale resolution instead of the user's actual latest edit, with no indication to the user that their change was overwritten.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
