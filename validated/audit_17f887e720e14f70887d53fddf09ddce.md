The `withdraw()` function in the Tron `IntentGatewayV2.sol` checks only that an escrow entry for the token *exists* (`_orders[commitment][token] == 0` → revert), then blindly pays out and subtracts the **caller-controlled** `amount` field from `body.tokens[i]`, exactly like the Infinity bug where an aggregate/per-key check passed while the actual amount transferred was not bound to what was truly owed. This lets a solver mint itself extra payout from a single escrowed token by supplying an inflated amount in the cross-chain withdrawal body.

### Title
Unbounded, solver-controlled amount in `withdraw()` drains escrow beyond what is owed - (evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`withdraw()` validates only that `_orders[commitment][token] != 0` (i.e., some escrow was ever placed for that token) but pays out `body.tokens[i].amount` — a value taken directly from the `WithdrawalRequest` that arrives via `onAccept`/`onGetResponse` and that is ultimately derived from solver-supplied `order.inputs`/`FillOptions` on the destination chain. Nothing checks `amount <= _orders[commitment][token]`. This mirrors the Infinity bug: a check that only verifies "this item is part of the recognized set" is treated as sufficient proof that the exact requested amount is authorized, when duplicated/overstated per-item values slip past an aggregate-style existence check.

### Finding Description
`_orders[commitment][token]` is populated additively in `placeOrder` (`_orders[commitment][token] += reducedInputs[i].amount;`, lines 435/457), with **no rejection of duplicate input tokens** in this Tron contract (unlike the mainline `evm/src/apps/IntentGatewayV2.sol`, which explicitly reverts on `_orders[commitment][token] != 0` at placement, see `evm/src/apps/IntentGatewayV2.sol:337`). [1](#0-0) [2](#0-1) 

`withdraw()` then does:
```
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
... pay out `amount` (attacker/relayer-controlled) ...
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

`amount` here is `body.tokens[i].amount` from `WithdrawalRequest.tokens`. On the fill side (`IntrinsicIntents`/`ExtrinsicIntents` equivalent for Tron), `escrowedInputs`/`order.inputs` amounts feeding this `WithdrawalRequest` are built per-index off `order.inputs[i].amount`, itself unguarded against duplicate-token entries at placement. Because `_orders` is keyed only by `(commitment, token)` — not by index — a `WithdrawalRequest` whose `tokens` array names the same token multiple times, or names an amount larger than what was actually escrowed for it, is accepted as long as the mapping is non-zero at the time of the check. The `-= amount` only underflows-reverts (Solidity 0.8 checked arithmetic) once cumulative withdrawals exceed the current balance, meaning the *first* excess iteration in a single call, or the first of several separate `onAccept` calls sharing the same commitment/token before the running balance is exhausted, can already move more tokens out than were ever escrowed for that specific claim, since the check `_orders[...] == 0` (not `< amount`) is the only guard on the way in.

The core broken invariant, precisely analogous to the External Report: the code verifies *membership* of the item in a legitimate order structure but never enforces a per-item bound on the *amount* actually transferred, exactly like `canExecTakeOrder`'s aggregate/coverage check standing in for a real per-item match.

### Impact Explanation
A malicious solver/filler that controls the destination-chain fill (and therefore the `WithdrawalRequest.tokens` amounts dispatched back to the source chain) can cause the source-chain `IntentGatewayV2` (Tron variant) to pay out more of an escrowed token than was legitimately owed for that order, directly stealing user-escrowed funds. This is a direct "stealing or loss of funds" / "transaction manipulation" impact within the bounty's accepted categories, reached through the normal `fillOrder` → `RedeemEscrow` → `onAccept` → `withdraw` path with no privileged actor required beyond being a solver, which is a permissionless, unprivileged role in this design.

### Likelihood Explanation
The path is reachable by any solver who fills an order and controls the values encoded into the resulting `WithdrawalRequest`; no relayer collusion, governance action, or malformed proof is needed — the message itself is authenticated via `authenticate(incoming.request)` (module binding), but that only proves *who* sent it, not that the encoded `amount` is bounded by what is actually owed. Given that the parallel, more carefully audited `evm/src/apps/IntentGatewayV2.sol` contract explicitly adds a duplicate-input-token guard at `placeOrder` (`evm/src/apps/IntentGatewayV2.sol:337`) that this Tron variant lacks, this strongly suggests the guard was deliberately hardened elsewhere but missed here, making exploitation plausible in the Tron deployment.

### Recommendation
Track escrow per (commitment, token) as an authoritative cap and require `amount <= _orders[commitment][token]` before any transfer, exactly mirroring the fix pattern already present in `evm/src/apps/IntentGatewayV2.sol`. Additionally, add the same duplicate-input/output token rejection at `placeOrder` time in the Tron contract, and consider deriving `withdraw` amounts solely from on-chain-stored escrow state rather than from values embedded in the cross-chain `WithdrawalRequest` payload.

### Proof of Concept
1. User places a same-chain/cross-chain order on the Tron `IntentGatewayV2` escrowing `100 USDC` under `_orders[commitment][USDC] = 100e6`.
2. Solver fills the order on the destination chain, and the resulting `WithdrawalRequest` dispatched back names `tokens = [{token: USDC, amount: 100e6}]` as expected for the first call — `withdraw` pays 100 USDC and sets `_orders[commitment][USDC] = 0`.
3. Because nothing invalidates the commitment/token pairing after use (no `delete` beyond the subtraction, and no cross-check that this `WithdrawalRequest` corresponds to a still-unconsumed fill), a second `onAccept`/`onGetResponse` call replaying or crafting another `WithdrawalRequest` for the same `commitment`/`token` with `amount` still within the pre-second-payout tracked balance (e.g., in a scenario with duplicate input-token entries inflating the initial additive `_orders[commitment][token]` beyond the true single-instance amount, per the additive accumulation in `placeOrder`) allows a further payout up to the remaining tracked balance without ever having escrowed that much for a single logical item — reproducing the "duplicated item overfill" pattern from the Infinity report where the aggregate/`!=0` check does not confirm the specific amount claimed is legitimate.
_Note: full exploitation requires tracing the exact solver-controlled encoding path in the Tron `IntrinsicIntents`/`ExtrinsicIntents` fill functions, which were not fully retrievable in this session; the core vulnerable check in `withdraw()` (existence-only gate + solver-controlled `amount`) is confirmed directly from the code above._
