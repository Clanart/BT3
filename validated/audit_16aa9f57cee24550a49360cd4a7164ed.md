### Title
Missing Zero-Address Validation for `evm_address` in Deposit Flow Causes Permanent Lock of Bridged BTC — (`core/src/rpc/parser/mod.rs`, `core/src/verifier.rs`)

---

### Summary

The Clementine deposit flow accepts `evm_address = [0u8; 20]` (the EVM zero address) in a `BaseDeposit` request without any rejection. No guard exists in the protobuf parser, the `EVMAddress` type, or the verifier's `is_deposit_valid` function. A user who submits a deposit with the zero EVM address causes their BTC to be moved into the bridge vault via the `MoveToVault` transaction while cBTC is minted to `0x0000…0000` on Citrea — permanently locking the bridged BTC with no recovery path.

---

### Finding Description

**Step 1 — Parsing (`core/src/rpc/parser/mod.rs`):**

The `TryFrom<clementine::deposit::DepositData> for DepositType` conversion at line 350–356 converts the raw `evm_address` bytes into an `EVMAddress` struct. The only validation performed is a length check (exactly 20 bytes), enforced by the `impl_try_from_vec_u8!` macro in `crates/clementine-primitives/src/lib.rs` at line 35–48. An all-zero 20-byte slice passes this check without error. [1](#0-0) [2](#0-1) 

**Step 2 — `EVMAddress` type has no zero-check:**

`EVMAddress` is a plain `[u8; 20]` newtype. Its `TryFrom<Vec<u8>>` implementation only validates length. There is no `is_zero()` guard or any semantic validation on the inner bytes. [3](#0-2) 

**Step 3 — Verifier `is_deposit_valid` does not check for zero EVM address:**

The verifier's `is_deposit_valid` function (lines 541–731) performs the following checks: security council match, watchtower count limits, actor uniqueness, operator collateral validity, on-chain script pubkey match, bridge amount match, and block height. It does **not** check whether the `evm_address` embedded in the deposit data is the zero address. [4](#0-3) [5](#0-4) 

**Step 4 — Script check is consistency-only, not semantic:**

The verifier's script check at line 666–704 verifies that the on-chain UTXO's `script_pubkey` matches the Taproot address derived from the deposit data (including the `evm_address`). This is a consistency check: if the user sent BTC to an address computed with `evm_address = [0u8; 20]`, the script check passes. It does not reject a zero EVM address — it only confirms that the claimed `evm_address` matches what was used to construct the deposit address. [6](#0-5) 

**Step 5 — `generate_deposit_address` embeds the EVM address without validation:**

`generate_deposit_address` in `core/src/builder/address.rs` passes `user_evm_address` directly into `BaseDepositScript::new` with no zero-address check. [7](#0-6) 

---

### Impact Explanation

When a deposit with `evm_address = [0u8; 20]` is processed:

1. The aggregator orchestrates the full musig2 signing session and produces a valid `MoveToVault` transaction.
2. The `MoveToVault` transaction is broadcast and confirmed on Bitcoin, moving the user's BTC (one full bridge denomination, e.g. 10 BTC) into the bridge vault UTXO.
3. The Citrea bridge contract mints cBTC to `0x0000000000000000000000000000000000000000` — the EVM zero address — which is uncontrolled and unrecoverable.
4. The BTC is permanently locked in the vault with no corresponding claimable cBTC for the depositor.

This constitutes a **permanent, irreversible loss of bridged BTC** matching the allowed impact gate.

---

### Likelihood Explanation

Likelihood is **low-to-medium**. The trigger requires a user to either:
- Accidentally supply an all-zero EVM address (e.g., a frontend bug, a misconfigured backend, or a copy-paste error), or
- Intentionally supply it (self-harm, but the bridge has no duty to allow this).

The attack surface is the `new_deposit` gRPC endpoint, which is exposed to the backend service and, transitively, to end users. No privileged access is required. The deposit address is deterministically derived from the zero EVM address, so the on-chain UTXO and the `new_deposit` call are consistent — the bridge processes it without error.

---

### Recommendation

Add a zero-address check in the `TryFrom<clementine::deposit::DepositData> for DepositType` conversion in `core/src/rpc/parser/mod.rs`, immediately after the `evm_address` is parsed:

```rust
let evm_address: EVMAddress = data.evm_address.try_into().map_err(|e| {
    Status::invalid_argument(format!(
        "Failed to convert evm_address to EVMAddress: {e}",
    ))
})?;
if evm_address.0 == [0u8; 20] {
    return Err(Status::invalid_argument(
        "evm_address must not be the zero address",
    ));
}
```

Additionally, add a corresponding check in `is_deposit_valid` in `core/src/verifier.rs` as a defense-in-depth measure, so that even if the parser check is bypassed, the verifier independently rejects zero-address deposits. [8](#0-7) [9](#0-8) 

---

### Proof of Concept

1. Compute a deposit address using `evm_address = [0u8; 20]`:
   ```
   generate_deposit_address(nofn_xonly_pk, recovery_addr, EVMAddress([0u8; 20]), network, user_takes_after)
   ```
2. Send exactly `bridge_amount` BTC to that address on Bitcoin.
3. Call the aggregator's `new_deposit` gRPC with:
   ```protobuf
   Deposit {
     deposit_outpoint: <outpoint from step 2>,
     deposit_data: BaseDeposit {
       evm_address: [0x00; 20],
       recovery_taproot_address: "<any valid taproot address>",
     }
   }
   ```
4. The verifier's `is_deposit_valid` passes: the on-chain script matches (it was computed with the zero EVM address), the amount matches, and no zero-address check exists.
5. The aggregator completes the musig2 session, produces the `MoveToVault` transaction, and broadcasts it.
6. BTC is locked in the vault; cBTC is minted to `0x0000…0000` on Citrea. The depositor's BTC is permanently lost. [10](#0-9) [5](#0-4) [7](#0-6)

macro_rules! impl_try_from_vec_u8 {
    ($name:ident, $size:expr) => {
        impl TryFrom<Vec<u8>> for $name {
            type Error = &'static str;

            fn try_from(value: Vec<u8>) -> Result<Self, Self::Error> {
                if value.len() == $size {
                    Ok($name(value.try_into().unwrap()))
                } else {
                    Err(concat!("Expected a Vec<u8> of length ", stringify!($size)))
                }
            }
        }
    };
