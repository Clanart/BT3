### Title
Staker can receive 0 `PublicDelegation` shares after staking KAIA due to ERC4626-style rounding-down in `convertToShares`/`previewDeposit` - ([File: contracts/bindings/publicdelegation/PublicDelegation.go])

### Summary
`PublicDelegation` is Kaia's on-chain staking-pool/vault contract that lets any unprivileged account stake native KAIA and receive pool shares in return, following an ERC4626-like accounting model (`convertToShares`, `convertToAssets`, `previewDeposit`, `previewRedeem`, `previewWithdraw`, `totalAssets`, `totalSupply`) [1](#0-0) . Users interact with it directly via the payable `stake()`/`stakeFor(recipient)` entry points, which emit a `Staked(user, assets, shares)` event [2](#0-1) [3](#0-2) . This mirrors exactly the bug class in the external report (Tokemak `LMPVault.deposit`/`previewDeposit`), where shares are computed as `assets * totalSupply / totalAssets` rounded down, and a small enough deposit relative to the pool size can produce `shares == 0` while assets are still taken from the depositor.

### Finding Description
The reachable path is: an unprivileged transaction sender calls `stake()` or `stakeFor(recipient)` on a deployed `PublicDelegation` contract with a small `msg.value` amount of KAIA relative to the pool's `totalAssets()`/`totalSupply()` ratio. Internally this is expected to call `previewDeposit`/`convertToShares` with the assets to determine how many shares to mint, matching the same OpenZeppelin/ERC4626-style share math referenced by the external report's `LMPVault.previewDeposit` (`Math.Rounding.Down`). If `totalSupply * assets / totalAssets` rounds down to zero (e.g., pool has grown large relative to a marginal new stake amount, or share price has appreciated significantly), the staker's KAIA is accepted and added to `totalAssets`, but the minted share count is zero, and the `Staked` event would report `shares = 0`.

I was unable to obtain the actual `.sol` source of `PublicDelegation` in this index — only the auto-generated Go contract bindings are indexed (`contracts/bindings/publicdelegation/PublicDelegation.go`) [4](#0-3) . I could not directly confirm whether the contract already includes a `require(shares != 0)` guard on the stake/deposit path, since the constant/error strings are embedded in the compiled bytecode/ABI JSON, which is truncated in the indexed content. This is a limitation of the current index, not a confirmation that the mitigation exists.

### Impact Explanation
If unguarded, a staker who sends a small stake amount relative to the pool's `totalAssets`-to-`totalSupply` ratio would have their KAIA/asset value absorbed into the pool's `totalAssets` while receiving zero shares, permanently losing their staked value with no way to redeem it (since `redeemAssets`/`redeem` operate on share balances). This is a direct unauthorized value loss to the staker and a corresponding value transfer to existing shareholders (dilution-free donation), which fits the "unauthorized value movement" acceptance criterion.

### Likelihood Explanation
Likelihood depends on the pool's share price (assets-per-share) growing large enough, and a staker submitting a small enough `stake()`/`stakeFor()` value, for the rounding-down division to truncate to zero. This is entirely reachable by any public caller submitting an ordinary staking transaction — no privileged role, consensus, or p2p access is required — but requires specific pool-state conditions (high assets/share ratio) to actually trigger a zero-share outcome, so it is conditional rather than always-exploitable.

### Recommendation
Add an explicit check in the `PublicDelegation` staking/deposit path (wherever `convertToShares`/`previewDeposit` result is consumed to mint shares) that reverts if the computed `shares == 0`, mirroring the audit's original recommendation (`require(shares != 0)`), before transferring/accepting the staker's assets. Since the actual Solidity implementation could not be located in this index, a Devin agent with full repository access should locate the `PublicDelegation.sol` source (likely outside the indexed `contracts/bindings` directory, possibly in a private/parent repo or generated from a separate contracts submodule) and add/verify this zero-shares guard on `stake`, `stakeFor`, and any other asset-in/shares-out entry point.

### Proof of Concept
1. Deploy/observe a live `PublicDelegation` pool where `totalAssets()` and `totalSupply()` have diverged such that `totalSupply() * assets / totalAssets()` rounds to 0 for a small `assets` value (e.g., after significant reward accrual increases `totalAssets` while `totalSupply` stays fixed).
2. Call `previewDeposit(assets)` (or the equivalent internal conversion used by `stake`) with that small `assets` value and observe it returns `0` [5](#0-4) .
3. Call `stake()` (payable) with `msg.value = assets`, sending that same amount of KAIA. If no zero-shares guard exists, the transaction succeeds, `totalAssets` increases by `assets`, and the `Staked` event is emitted with `shares = 0` [6](#0-5) [3](#0-2) , permanently locking the staker's KAIA with no shares to redeem it.

Note: Full confirmation of exploitability (i.e., whether a `shares != 0` check is already present) requires access to the actual `PublicDelegation.sol` source, which is not available in this index — only compiled bindings are indexed. A Devin session with full filesystem access should verify this directly against the source contract before treating this as a confirmed (rather than analog) finding.
