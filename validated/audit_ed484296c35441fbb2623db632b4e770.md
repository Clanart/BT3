### Title
Griefing via pre-funded isolated address causes duplicated IBC value (refund on source chain + trapped but existing minted value on destination chain) - ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`ContractKeeper.IBCReceivePacketCallback` enforces a sanity check requiring that the deterministic "isolated address" holds **exactly zero** ERC20 balance after the destination callback executes. Because the isolated address is a public, deterministic function of `(destChannelID, sender)`, any unprivileged attacker can pre-fund it with a trivial dust amount of the target ERC20 representation before a legitimate ICS-20 callback packet arrives. This permanently forces the balance check to fail, causing the destination chain to emit an `ErrorAcknowledgement` even though the underlying token mint/unescrow to the isolated address already occurred and is not rolled back — producing duplicated spendable value across the two chains (refund on the source chain plus real, though stranded, value on the destination chain). This is the same root-cause pattern as the reported `SeaportDeleverage` bug: an unconditional "balance must be exactly zero" invariant that any third party can violate by simply sending tokens to a fixed, predictable address, bricking/mis-accounting the flow.

### Finding Description
`GenerateIsolatedAddress` computes the isolated receiver address purely from public inputs: [1](#0-0) 

In `IBCReceivePacketCallback`, after the callback contract is invoked with `approve`/`transferFrom`-style calldata and the cached execution context is committed with `writeFn()`, the keeper enforces that the isolated receiver address ends up with **zero** ERC20 balance: [2](#0-1) 

The stated purpose of this check (per the code comment) is to prevent funds from being irretrievably stuck at the isolated address, since — as the module's own README states — "no user has the ability to sign messages on behalf of this account," so any tokens deposited into it are unreachable: [3](#0-2) 

Because the isolated address is deterministic and public, an attacker can compute it ahead of time for any known sender/channel pair and transfer even 1 wei of the corresponding ERC20 token into it before the legitimate transfer-with-callback packet is relayed. When the packet is later processed, even if the callback contract behaves correctly and transfers the entire intended amount out via `transferFrom`, the pre-existing dust guarantees `receiverTokenBalance != 0`, so the function always returns an error.

The wrapping callback middleware only invokes this contract-keeper hook **after** the underlying ICS-20 `OnRecvPacket` logic (mint/unescrow of tokens to the receiver/isolated address) has already run and been committed to the real `ctx` — that state is not part of the `cachedCtx`/`writeFn` scope used only for the EVM contract call. The integration test explicitly documents this behavior: an errored callback yields a failed acknowledgment (`ack.Success() == false`) while the transferred tokens remain, as real bank-layer value, trapped at the isolated address rather than being unwound: [4](#0-3) 

An `ErrorAcknowledgement` returned to the relayer and written back to the source chain causes the source chain's ICS-20 module to refund/unescrow the original sender's coins there. Combined with the fact that the destination chain's mint/unescrow into the isolated address is never reverted, the net effect is that value now exists on **both** chains simultaneously for a single nominal transfer: the sender gets their coins back on the source chain, while equivalent value remains permanently held (though unreachable to the sender) as real state on the destination chain.

### Impact Explanation
This breaks the 1:1 escrow/mint accounting invariant that ICS-20 relies on: an attacker-triggerable error acknowledgement causes a refund on the source chain without reversing the corresponding value increase on the destination chain. This is a duplication of spendable value across chains (effectively unbacked/duplicated token supply), which is an explicitly in-scope Critical impact for asset-representation/accounting invariants (`x/erc20`, bank, ICS20 escrow consistency). It also permanently freezes real destination-chain value at an address nobody can access, another explicitly in-scope Critical impact (permanent freezing/locking of user funds).

### Likelihood Explanation
Trigger requires no privilege: the attacker only needs to (1) know or predict a victim's sender address and the destination channel ID (both public/observable), (2) compute `GenerateIsolatedAddress(channelID, sender)` off-chain (a public, documented, non-secret function), and (3) send a negligible amount of the corresponding ERC20 token to that address before the victim's callback-enabled IBC transfer packet is relayed. This can be done proactively and repeatedly against any address that might ever be used as an isolated-address sender, making it a low-cost, high-reliability griefing/duplication vector.

### Recommendation
Remove or relax the strict `receiverTokenBalance == 0` post-condition in `IBCReceivePacketCallback`. Instead: (a) compare the balance delta expected from the callback (i.e., verify the correct amount was moved rather than that the account is empty), (b) sweep/forward any unexpected residual balance instead of failing the whole packet, or (c) if the check must fail, ensure the failure fully and atomically reverses the underlying token mint/unescrow for that packet within the same state transition, so no error-acknowledgement can be emitted while destination-chain value remains committed.

### Proof of Concept
1. Attacker observes a user intends to use IBC-callbacks-based ICS-20 transfers from chain B into a destination-chain contract, or simply targets any known sender address that might do so on channel `channel-X`.
2. Attacker computes `isolatedAddr = GenerateIsolatedAddress("channel-X", senderBech32)` locally (pure function, no privilege needed) — see [5](#0-4) .
3. Attacker sends `1` unit of the relevant ERC20 token-pair representation to `isolatedAddr` on the destination chain (ordinary ERC20 `transfer`, fully unprivileged).
4. Victim relays a legitimate ICS-20 transfer-with-callback packet targeting `isolatedAddr` as receiver; the destination transfer module mints/unescrows the transferred amount to `isolatedAddr`, then `IBCReceivePacketCallback` runs the contract callback which correctly moves the intended amount out via `transferFrom`.
5. Despite correct callback behavior, the post-check at [6](#0-5)  finds the attacker's leftover 1 unit and returns `ErrEVMCall`, causing the wrapping middleware to return an `ErrorAcknowledgement` (reproduced by the existing test flow at [4](#0-3) , which already shows `ack.Success()==false` with tokens trapped in the isolated address rather than reverted).
6. The relayer delivers the error acknowledgement to the source chain, which refunds/unescrows the sender's original coins there — while the minted/unescrowed value on the destination chain, now permanently stuck at `isolatedAddr`, is never clawed back, resulting in duplicated value across the two chains.

// This provides a safe address to call the receiver contract address with custom calldata

## Limitations

The receiver side callback **must** receive funds to an ephemeral address generated from the channelId and packet
sender address. Note that since this is a generated address, no user has the ability to sign messages on behalf of
this account even though it is a cross-chain representation of the packet sender.

Thus, a contract that receives the funds and calldata from the isolated receiver address **must** send the tokens
onwards to a desired address that is specified in the calldata. If tokens are deposited back into the isolated address,
they are unreachabe. If you wish to interact with a contract that does not implement functionality for sending the
tokens to a different address then you must interact with that contract through some wrapper contract interface that
can receive the funds, call the contract which deposits funds back to `msg.sender` and then the wrapper contract
can move the funds to a final desired address.
