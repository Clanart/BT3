## Title
Trampoline session state (SSH passphrase / background-task flag) is shared across concurrent nested git sub‑processes keyed only by trampoline token, allowing an attacker‑controlled `.gitmodules`/multi‑remote operation to corrupt another remote's credential handling - (File: `app/src/lib/trampoline/trampoline-environment.ts`)

### Summary
The bug report is about Solidity functions that make an external call before finalizing internal state, letting the callee re-enter and corrupt shared state. Desktop's analog is the trampoline credential/SSH-passphrase plumbing: a single `DESKTOP_TRAMPOLINE_TOKEN` is minted once per top-level `git` invocation and is then shared, via inherited environment variables, by every nested git sub-process that the top-level command spawns (e.g. per-submodule fetches during `git submodule update --init --recursive`). All of the "session" bookkeeping used by the trampoline handlers - `mostRecentSSHCredentials`, `isBackgroundTaskEnvironment`, `hasRejectedCredentialsForEndpoint`, `trampolineEnvironmentPath` - is stored in module-level `Map`s keyed *only* by that single token, on the implicit assumption that exactly one credential/passphrase exchange happens per token at a time.

### Finding Description
`withTrampolineEnv` requests one token per outer `git()` call and stores per-token state before invoking `fn`: [1](#0-0) [2](#0-1) 

That same token is exported to the spawned git process as `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT`, and `GIT_CONFIG_PARAMETERS` configures `credential.helper=desktop`, which - unlike command-line `-c` arguments - **is inherited by child/filter/sub-git processes**, exactly as documented in the code itself: [3](#0-2) 

When Desktop runs a single top-level git command that git itself expands into multiple remote operations against attacker-controlled URLs - the canonical case being `git submodule update --init --recursive`, where the submodule URLs come from the attacker-controlled `.gitmodules` file of a cloned/fetched repository - each submodule fetch is a separate nested git process that inherits the *same* `DESKTOP_TRAMPOLINE_TOKEN` and therefore re-enters the same trampoline handlers concurrently, before the outer `withTrampolineEnv`'s `finally` cleanup has run.

The SSH passphrase bookkeeping is keyed purely by that shared token, not by key path/host: [4](#0-3) [5](#0-4) 

and the failure-cleanup path deletes whatever entry currently occupies that token's slot: [6](#0-5) [7](#0-6) 

If the legitimate submodule (private, requiring an SSH key passphrase) and an attacker-supplied submodule remote (pointing to a host that also triggers SSH auth, or simply causes an auth failure) are processed under the *same* token - which is guaranteed here because both are children of one `git submodule update` invocation sharing one `DESKTOP_TRAMPOLINE_TOKEN` - the `mostRecentSSHCredentials` map entry set by one submodule's handshake can be overwritten by the other's before either completes. The `isBackgroundTaskEnvironment` and `hasRejectedCredentialsForEndpoint` maps have the identical last-write-wins keying problem.

### Impact Explanation
Because `mostRecentSSHCredentials`/`deleteMostRecentSSHCredential` is keyed only by the shared token, an attacker who controls one remote referenced from a `.gitmodules` (or any other multi-remote operation reachable from cloned/fetched content) can force a race that:
- causes Desktop to delete/overwrite the OS-keychain entry for the *victim's own, unrelated* SSH key passphrase (the wrong `{store, key}` pair recorded in `mostRecentSSHCredentials`), silently corrupting the user's stored credentials, or
- suppresses/alters interactive-prompt behavior (`isBackgroundTaskEnvironment`) for the legitimate remote's credential exchange because the flag was last set by the attacker's nested request.

This is state corruption triggered purely by attacker-controlled repository content (`.gitmodules` URLs) with no local access, admin rights, or social engineering required - matching the "silent corruption of what the user commits/pushes" and "credential" categories in scope, though the primitive is corruption/clobbering of local secret bookkeeping rather than direct exfiltration to the attacker (the credential value itself is never sent over the attacker's transport).

### Likelihood Explanation
Reaching this requires: (1) the victim clones or fetches a repository containing a `.gitmodules` with a submodule pointing at a host that will legitimately prompt for/require SSH authentication, alongside the victim's own private submodule that also requires SSH auth, and (2) git processing those submodules with enough overlap (parallel `--jobs`, or fast sequential fetches racing the async passphrase-store/finally cleanup) for the shared token's map entries to be clobbered mid-flight. This is a genuine, unprivileged, no-user-interaction-beyond-normal-cloning path, but it depends on timing/race conditions rather than being deterministically triggerable on every run, and the concrete blast radius (which credential gets deleted/overwritten) is not fully attacker-controlled - it's non-deterministic state corruption rather than a guaranteed exfiltration primitive.

### Recommendation
Scope all trampoline session state by a compound key that includes the specific credential/host/key context, not just the coarse-grained trampoline token - or better, mint a distinct trampoline token per nested git sub-process (including submodule recursion) rather than reusing the parent token via inherited environment variables. At minimum, `mostRecentSSHCredentials`, `isBackgroundTaskEnvironment`, and `hasRejectedCredentialsForEndpoint` should be keyed by `(token, keyHash/endpoint)` so concurrent nested requests sharing a parent token cannot overwrite each other's bookkeeping.

### Proof of Concept
1. Attacker publishes a repository with a `.gitmodules` containing two submodules: submodule A (a decoy/attacker-controlled remote whose fetch will fail or prompt SSH auth) and reference the victim's real private submodule B (SSH, requires passphrase) as the second entry.
2. Victim clones the repository in Desktop and chooses to initialize submodules (`git submodule update --init --recursive`), which Desktop runs as one `spawnGit`/`withTrampolineEnv` call, minting a single `DESKTOP_TRAMPOLINE_TOKEN`.
3. Git recurses into both submodules; both nested processes inherit the same `DESKTOP_TRAMPOLINE_TOKEN`/`DESKTOP_PORT` and hit the trampoline server concurrently for SSH passphrase handling (`app/src/lib/trampoline/trampoline-askpass-handler.ts` → `setMostRecentSSHKeyPassphrase`).
4. Craft submodule A's fetch to fail authentication shortly after submodule B's passphrase entry has been recorded under the shared token via `setMostRecentSSHCredential(token, ...)`.
5. The failure path calls `deleteMostRecentSSHCredential(token)` (`app/src/lib/trampoline/trampoline-environment.ts` line 156), which now deletes/targets whichever `{store, key}` is currently stored for that token - potentially submodule B's legitimate passphrase entry instead of A's - demonstrating cross-request state corruption driven entirely by attacker-controlled `.gitmodules` content.
