### Title
Payout attribution in `update_finalized_payouts` trusts unauthenticated OP_RETURN bytes, letting anyone credit a real operator with a payout it never funded - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` attributes a confirmed payout transaction to an operator purely by parsing the first OP_RETURN output's 32 bytes as an `XOnlyPublicKey`, with no check that the named operator's funds, signature, or presigned kickoff/round chain were involved in constructing or funding that transaction. Because the withdrawing user's authorization only covers their own input/output (via a single-input, single-output signed message), any third party can complete the payout transaction with arbitrary funding inputs and an arbitrary OP_RETURN naming a real, active operator, causing that operator's own automated `PayoutCheckerTask` to claim reimbursement for a payout it never made.

### Finding Description
The broken binding: the DB column `withdrawals.payout_payer_operator_xonly_pk` is treated downstream as equivalent to "the operator whose own funds paid out this withdrawal," i.e. the implicit equality `payout_payer_operator_xonly_pk == funder_of(payout_tx inputs)`. In reality this column is set to whatever 32 bytes follow `OP_RETURN` in the payout transaction, with no verification of that equality: [1](#0-0) 

This is the only site that populates `payout_payer_operator_xonly_pk` for later consumption: [2](#0-1) 

Downstream, `Operator::validate_payer_is_operator` and `PayoutCheckerTask::run_once` trust this column at face value: `PayoutCheckerTask` polls `get_first_unhandled_payout_by_operator_xonly_pk` filtered on the *operator's own* signer key, and if a row exists it unconditionally calls `handle_finalized_payout`, which builds/dispatches the kickoff and drives the reimbursement flow: [3](#0-2) [4](#0-3) 

The only place operator identity is cross-checked against a kickoff is `is_kickoff_malicious`, which compares the DB's `operator_xonly_pk_opt` against `kickoff_data.operator_xonly_pk` of the *actual* kickoff being evaluated - not against who funded the payout_tx's inputs: [5](#0-4) 

Similarly, the bridge circuit's `deposit_constant` only asserts that the OP_RETURN-encoded `operator_xonlypk` is consistent with the kickoff's own `round_txid`/`operator_xonlypk` inputs - it never asserts that the operator's own key produced or funded the payout transaction's inputs: [6](#0-5) 

Exploit flow: a user calling `withdraw()`/optimistic-payout on Citrea authorizes only their own claimed UTXO (`in_outpoint`) and their own destination output via a signature over a specific input/output pair (`WithdrawParams.input_signature`), as seen in the withdraw RPC handling: [7](#0-6) [8](#0-7) 

Nothing in the withdrawing user's authorization commits to who supplies the *other* funding inputs of the completing transaction, or to the OP_RETURN's contents. An attacker acting as the withdrawer (or observing an in-flight withdrawal) can therefore build and broadcast their own completing transaction: spend the correct withdrawal outpoint (satisfying the SPV/storage-proof input checks in the bridge circuit), fund the rest of the transaction entirely from their own wallet, pay themselves (or anyone) the withdrawal amount, and append an OP_RETURN of `move_txid || operator_X_xonly_pk` naming a real, currently active operator X who never touched this transaction. Once six confirmations occur, `update_finalized_payouts` parses that OP_RETURN and writes `payout_payer_operator_xonly_pk = X` into the DB - purely from bytes the attacker controls. Operator X's own `PayoutCheckerTask` then picks this up automatically (because the query filters by X's own key) and drives `handle_finalized_payout`, building a kickoff and eventually claiming reimbursement for a withdrawal X never funded.

### Impact Explanation
This matches the listed Critical category "an operator reimbursed for a payout it never funded." An unprivileged attacker can, at will, cause an arbitrary active operator to be credited (and, via the automated `PayoutCheckerTask`/`handle_finalized_payout` pipeline, to actually pursue and receive) reimbursement for a withdrawal it did not pay. This is repeatable per withdrawal (one attack per Citrea withdrawal event) and can target any operator whose x-only public key is public (all operators' keys are public protocol data). It corrupts the withdrawals table's causal record between "funds left an operator's pocket" and "operator gets reimbursed," which is exactly the invariant the reimbursement/disprove machinery is built to protect.

I was not able to fully verify, within the remaining budget, whether the specific "Challenge/Disprove burns operator X's collateral because of a defect the attacker planted" sub-scenario (b) in the question is independently reachable: `is_kickoff_malicious` compares the DB operator field against the kickoff's *own* `operator_xonly_pk` (which, in this scenario, is still X's real key since X itself builds the kickoff), so that specific guard does not flag it as malicious - meaning the credited/attributed payout is accepted by verifiers as consistent with X's kickoff. I could not conclusively trace, in the time available, whether the bridge circuit or reimburse-transaction chain independently re-validates payout output amount/script correctness in a way that could still trigger a Disprove against X for a transaction X never built; the circuit code I reviewed (`circuits-lib/src/bridge_circuit/mod.rs`) only asserts input-outpoint/vout equality against the Citrea storage proof, not output value/script - so a defect in the attacker's output would likely not be independently detected as fraud by the circuit at all, and thus not obviously trigger a Disprove against X either. The demonstrable and clearly reachable harm is scenario (a): mis-attributed reimbursement credit.

### Likelihood Explanation
No special privilege is required: the attacker only needs to be (or coordinate as) the withdrawing party on Citrea, or intercept the public details of a pending withdrawal (input outpoint, user signature, destination) and race to complete the Bitcoin-side transaction before the intended operator does, funding the rest from their own wallet and paying ordinary miner fees. No verifier, operator, aggregator, or key-share compromise is needed. The cost is limited to the withdrawal amount (if the attacker chooses to self-fund a withdrawal to frame an operator) plus fees, and the attack is repeatable across every withdrawal and every operator.

### Recommendation
`update_finalized_payouts` (and/or the bridge circuit's `deposit_constant`) should not accept the OP_RETURN-embedded operator key as authoritative proof of who funded the payout. Require a real binding: either (a) have the operator sign the completing payout transaction (e.g., commit to a per-operator signature over the full transaction, or a Winternitz/committed key exclusive to that operator's kickoff sequence) instead of a bare unauthenticated data push, or (b) require that at least one of the payout transaction's funding inputs be provably spent from that operator's known collateral/round UTXO set before attributing the payout to them in the DB, or (c) require that the operator's own client submits and pre-registers the payout transaction (with its own signature) prior to broadcast, and only accept confirmations matching a pre-registered txid per deposit.

    /// Sets the given payout txs' txid and operator index for the given index.
    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }

    /// For a deposit_id checks that the payer for that deposit is the operator, and the payout blockhash and kickoff txid are set.
    async fn validate_payer_is_operator(
        &self,
        dbtx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
    ) -> Result<(BlockHash, Txid), BridgeError> {
        let (payer_xonly_pk, payout_blockhash, kickoff_txid) = self
            .db
            .get_payer_xonly_pk_blockhash_and_kickoff_txid_from_deposit_id(dbtx, deposit_id)
            .await?;

        tracing::info!(
            "Payer xonly pk and kickoff txid found for the requested deposit, payer xonly pk: {:?}, kickoff txid: {:?}",
            payer_xonly_pk,
            kickoff_txid
        );

        // first check if the payer is the operator, and the kickoff is handled
        // by the PayoutCheckerTask, meaning kickoff_txid is set
        let (payout_blockhash, kickoff_txid) = match (
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid,
        ) {
            (Some(payer_xonly_pk), Some(payout_blockhash), Some(kickoff_txid)) => {
                if payer_xonly_pk != self.signer.xonly_public_key {
                    return Err(eyre::eyre!(
                        "Payer is not own operator for deposit, payer xonly pk: {:?}, operator xonly pk: {:?}",
                        payer_xonly_pk,
                        self.signer.xonly_public_key
                    )
                    .into());
                }
                (payout_blockhash, kickoff_txid)
            }
            _ => {
                return Err(eyre::eyre!(
                    "Payer info not found for deposit, payout blockhash: {:?}, kickoff txid: {:?}",
                    payout_blockhash,
                    kickoff_txid
                )
                .into());
            }
        };

        tracing::info!(
            "Payer xonly pk, payout blockhash and kickoff txid found and valid for own operator for the requested deposit id: {}, payer xonly pk: {:?}, payout blockhash: {:?}, kickoff txid: {:?}",
            deposit_id,
            payer_xonly_pk,
            payout_blockhash,
            kickoff_txid
        );

        Ok((payout_blockhash, kickoff_txid))
    }
