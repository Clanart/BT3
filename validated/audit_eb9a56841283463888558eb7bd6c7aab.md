## Analysis

The Aave/Morpho report's broken invariant is: **an attacker-controlled object, upon first contact with a shared trust boundary, silently sets protocol state (isolation-mode collateral) that the victim never explicitly consented to, and the existing "protection" mechanism doesn't stop it.**

The closest verifiable analog in this codebase is in the clone path, where GitHub Desktop explicitly disables Git's own upstream protection against a known clone-time hook-execution vulnerability class. [1](#0-0) 

`clone()` builds the execution environment for `git clone --recursive` and sets:

```
GIT_CLONE_PROTECTION_ACTIVE: 'false'
```

`GIT_CLONE_PROTECTION_ACTIVE` is the exact environment variable Git introduced to guard against the class of "recursive clone with submodule leads to hook execution during the clone/checkout itself" (the case-collision / symlinked `.git` hook-planting issue class, fixed upstream as `GIT_CLONE_PROTECTION_ACTIVE`). Desktop's `clone.ts` force-disables that guard for every clone it performs, while still passing `--recursive` [2](#0-1) , meaning submodules controlled entirely by the (attacker-controlled) remote repository are recursed into with the safety check turned off.

The rest of Desktop's "untrusted repository" defenses do not cover this path: the ownership-based unsafe-repository warning only triggers when the directory is owned by a *different* user [3](#0-2) , but a freshly cloned repository is owned by the current user, so that prompt never fires for a first-time `git clone` — the exact same "no one is watching the door" gap that let Morpho silently drift into isolation mode on first supply.

Hook interception (`withHooksEnv`/`getRepoHooks`) is only wired into `commit`, `push`, `pull`, and `merge` [4](#0-3) [5](#0-4)  — `clone()` itself does not pass `interceptHooks` at all, so any hook execution that happens as a side effect of the clone/checkout runs through raw Git with `GIT_CLONE_PROTECTION_ACTIVE=false`, completely outside Desktop's hook sandboxing/shell-env layer.

### Title
Recursive clone runs with Git's clone-time hook-protection explicitly disabled - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` unconditionally while performing `git clone --recursive`, defeating the guard Git added specifically to stop repository-supplied submodules/symlinked `.git` directories from causing hook scripts to be written and executed during the clone/checkout sequence — before the user opens, inspects, or is warned about the repository.

### Finding Description
`clone()` builds its execution env as:
```js
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
``` [6](#0-5) 
and invokes `git -c init.defaultBranch=... clone --recursive -- <url> <path>` [7](#0-6) .

`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git exposes to opt out of its internal "clone protection", which was added to prevent a maliciously crafted repository (using recursive submodules and/or symlink/case-collision tricks around `.git`) from causing files — including hook scripts — to be planted and then invoked as part of the same clone/checkout operation. By forcing this to `'false'` on every clone, Desktop deliberately re-enables the vulnerable behavior Git tried to close off, for every remote repository URL a user opens with "Clone repository."

This is analogous to the Aave isolation-mode bug: the attacker-controlled object (the remote repository/submodule tree) determines security-relevant state (whether hook-planting during checkout succeeds) the moment it is first pulled in, and the app's only other safeguard — the "repository owned by another user" trust prompt [8](#0-7)  — structurally cannot apply here because a repository the user just cloned is always owned by the current user, exactly as Morpho's Aave position is "first come" regardless of intent.

### Impact Explanation
If the disabled check is what stands between a crafted submodule/symlink layout and hook execution, a malicious repository can achieve code execution on the victim's machine at clone time, under the user's own privileges, with no explicit "run this script" action from the user — this is squarely "attacker controls a cloned repository" → "code execution" as defined in the Valid Impact scope.

### Likelihood Explanation
Cloning an attacker-supplied or attacker-influenced URL (public repo, fork, or "Open in Desktop"/`openrepo` deep link driving `cloneAgain` [9](#0-8) ) is a completely ordinary Desktop action, not an "unnatural step." No admin rights, local access, or pre-existing malware are required — only that the user clones the repository, which is the app's core function.

### Recommendation
Do not set `GIT_CLONE_PROTECTION_ACTIVE: 'false'`. Let Git's clone protection remain active (the default), and if `--recursive`/submodule handling breaks because of it, fix the interaction explicitly rather than disabling the safety mechanism globally for all clones. Consider also routing `clone()` through `interceptHooks`/`withHooksEnv` the same way `commit`/`push`/`pull` are, so any hook invoked as a byproduct of clone/checkout runs through Desktop's sandboxed hook environment instead of raw Git.

### Proof of Concept
Exact reproduction requires constructing a submodule/`.git`-symlink layout that exploits the specific upstream Git protection `GIT_CLONE_PROTECTION_ACTIVE` was built to close (I could not execute Git locally to confirm the payload mechanics from this environment). The verifiable, in-repo evidence is the unconditional override itself: [10](#0-9) , combined with the fact that `clone()` never passes `interceptHooks`, so no hooks fired during/after clone go through Desktop's sandbox [11](#0-10) . Recommend a Devin/engineer session with a real Git binary to (a) confirm which CVE/protection `GIT_CLONE_PROTECTION_ACTIVE` corresponds to in the vendored Git version Desktop ships, and (b) build a concrete crafted-repository PoC exercising it.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
