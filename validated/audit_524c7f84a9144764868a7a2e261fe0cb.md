Based on the code I was able to examine, the closest verified local analog to the SHER reentrancy pattern (external call made *before* the state that guards against double-redemption is updated) is in the Tron fork of the intent gateway.

### Title
Reentrancy in `IntentGatewayV2.withdraw()` — per-token escrow debited after external transfer, not before - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentsBase`/`ExtrinsicIntents` and the main EVM `IntentGatewayV2` already had a documented reentrancy bug in the withdrawal path (multi-output same-chain fills), which was fixed by moving `_filled[commitment] = msg.sender` to the top of the fill function, as shown by the dedicated regression test suite [1](#0-0) . The Tron fork's `withdraw()` internal function sets the top-level `_filled[body.commitment]` guard first, but the **per-token escrow accounting (`_orders[body.commitment][token]`) is still decremented after the external transfer call**, for every token in the order, exactly mirroring the CEI violation described in the SHER report (`sher.safeTransfer()` before `delete sherRewards_[_id]`).

### Finding Description
In `withdraw()`, for each token in `body.tokens`, the function performs an external call (native ETH send or `token.call(transfer(...))`) to the beneficiary, and only *after* that call succeeds does it decrement `_orders[body.commitment][token]`: [2](#0-1) 

The same pattern repeats for the transaction-fee entry, where the fee-token transfer happens before `delete _orders[body.commitment][TRANSACTION_FEES]`: [3](#0-2) 

Although `_filled[body.commitment] = beneficiary` is assigned at the very top of `withdraw()` (line 684), this only prevents a second, independent invocation of `withdraw()`/the public entrypoint for the *same commitment* from an outer call — it does not stop a beneficiary-controlled contract from reentering during the very first token transfer in the loop and reading/spending the *not-yet-decremented* `_orders[body.commitment][token]` value for the remaining tokens still queued in the same array, since each iteration only clears its own map entry after its own external call returns. This is functionally identical to the previously fixed "EscrowTheft_MultiOutput" bug documented in the test suite for the main EVM contract, where a malicious beneficiary self-filled a secondary ERC-20 output during the ETH leg's `.call` and stole the untouched escrow for another token in the array.

### Impact Explanation
If beneficiary is a malicious contract (a legitimate participant in the fill flow — the user or a colluding solver designates the beneficiary, so no privileged/relayer role is needed), and the order escrows multiple tokens including native value, the beneficiary's `receive()`/fallback can reenter a public function that reads `_orders[body.commitment][token]` for a token whose decrement has not yet executed in the still-unwound call stack, redeeming or double-spending the same escrowed balance. This directly maps to "stealing or loss of funds" and "duplicate settlement/claim" impact categories in the bounty scope.

### Likelihood Explanation
Medium — exploitability depends on there being a reachable public function other than `withdraw()`'s own caller-guard that reads `_orders[commitment][token]` without also being blocked by `_filled`, and on the token/beneficiary configuration allowing a callback (native ETH leg or a beneficiary contract). I was not able to fully trace every caller of `withdraw()` (e.g., `onAccept` dispatch for `RedeemEscrow`/`RefundEscrow`) within the available tool budget to confirm whether an alternate public entrypoint bypasses the `_filled` guard while still touching un-decremented `_orders` entries — this should be verified against the full contract before treating it as conclusively exploitable.

### Recommendation
Apply strict checks-effects-interactions inside the per-token loop itself: decrement (or delete) `_orders[body.commitment][token]` immediately before making the external transfer call, not after, for both the token loop and the transaction-fee payout. This mirrors the exact fix already applied for `_filled` at the top of the function and for `_fillSameChain`/`_fillCrossChain` in the main EVM contract.

### Proof of Concept
1. Attacker places/fills a same-chain order with `body.tokens = [native ETH, TokenX]` and `beneficiary` = attacker-controlled contract.
2. `withdraw()` sets `_filled[commitment] = beneficiary`, then begins the loop: transfers native ETH to `beneficiary` via `.call{value:...}("")` before decrementing `_orders[commitment][address(0)]`.
3. `beneficiary.receive()` fires during the ETH transfer and calls back into any public function that reads `_orders[commitment][TokenX]` (still un-decremented, since the loop hasn't reached index 1 yet) to redeem or otherwise leverage the TokenX escrow a second time.
4. Outer call completes its own (now-stale) decrement for TokenX, resulting in the escrow being paid out twice for TokenX relative to what was actually escrowed.

This exact "self-fill during ETH leg to steal escrow of a different token in the same order" attack shape is the one already fixed and regression-tested for the main EVM contract's `_fillSameChain`, per [4](#0-3) , but the Tron fork's `withdraw()` still performs the external call before its per-token state decrement.
