### Title
Cached DKG-confirmation preprocess reused across validator sets enables FROST nonce reuse and recovery of a validator's MuSig secret key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` caches a deterministic FROST preprocess seed in `CachedPreprocesses`, keyed solely by `context`. For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` — it contains **no validator-set session or genesis**. Because the DB is global, when a new validator set (new `TributarySpec`/session) runs a DKG confirmation with the same attempt number, the same cached seed is loaded and `seeded_preprocess` deterministically regenerates the **same nonces** (`d`, `e`). The validator then signs a different `set_keys_message` (different set, removed keys, and key pair) with the same nonce, producing two public signature shares from which anyone can solve for the validator's long-lived MuSig secret share.

### Finding Description
- `CachedPreprocesses` maps `context -> [u8; 32]` where `context` is any `Encode` value [1](#0-0) .
- `DkgConfirmer::signing_protocol` sets `context = (b"DkgConfirmer", self.attempt)` — the only entropy distinguishing sessions is the attempt counter, which resets for each new validator set's DKG [2](#0-1) .
- On a cache hit, `from_cache` → `seeded_preprocess` regenerates commitments/nonces purely from `ChaCha20Rng::from_seed(seed)` plus the secret share, so identical seed + identical `original_secret_share` (the validator's static MuSig key) ⇒ identical nonces [3](#0-2) .
- The signed message is `set_keys_message(set, removed, key_pair)` [4](#0-3) , which differs across validator sets (different `set`, `removed`, `key_pair`), so the FROST challenge differs while the nonce is identical.
- Shares are published on-chain via `Transaction::DkgConfirmed { confirmation_share }` [5](#0-4) , making both shares publicly observable.
- The file's own safety argument only covers reuse *within* a BFT session ("re-decide nonces on rebuild"); it never considers a fresh validator set colliding on `(b"DkgConfirmer", attempt)` since neither session nor genesis is in the context [6](#0-5) .

### Impact Explanation
FROST shares have the form `z = d + e·ρ + λ·s·c`. With `d`, `e` reused and challenges `c₁ ≠ c₂` (different message/participant set), the two public shares yield `s = (z₁ - z₂ - e·(ρ₁ - ρ₂)) / (λ·(c₁ - c₂))`. The recovered `s` is the validator's MuSig secret key — the root-of-trust key used to confirm every DKG and sign supermajority actions for that validator. The attacker needs no privileges: they merely observe two honestly-published `DkgConfirmed` shares across a routine validator-set rotation where attempt numbers coincide.

### Likelihood Explanation
Validator-set rotations are a normal protocol event, and DKG confirmation attempts for a fresh set start at low attempt numbers (typically 0/1), guaranteeing a context collision with the previous set's cached preprocess. The cache is never cleared per set, so every rotation deterministically reuses the nonce. No malicious or colluding party is required; the honest validator leaks its own key.

### Recommendation
Include the validator-set identity in the cache context, e.g. `context = (b"DkgConfirmer", spec.genesis(), attempt)` or `spec.set().session`, so a cached seed can never be replayed under a different group/message domain. Additionally, delete (rather than retain) the cache entry once `share_internal`/`complete` has consumed it, and complete the noted TODO of verifying that the preprocess published on-chain matches the presumed cached preprocess before publishing shares.

### Proof of Concept
1. Validator `V` participates in DKG confirmation for set `S₁`, attempt `0`. `preprocess_internal` stores seed `k` under `CachedPreprocesses[(b"DkgConfirmer", 0)]` and publishes share `z₁` for `msg₁ = set_keys_message(S₁.set(), removed₁, kp₁)` via `DkgConfirmed`.
2. Set rotation occurs; `V` (same `key`) participates in confirmation for set `S₂`, attempt `0`. `DkgConfirmer::new` succeeds, `CachedPreprocesses::get` hits, and `seeded_preprocess(k)` regenerates identical `d, e`.
3. `share_internal` signs `msg₂ = set_keys_message(S₂.set(), removed₂, kp₂) ≠ msg₁`; share `z₂` is published in `DkgConfirmed`.
4. An observer computes `V`'s secret share `s` from `z₁, z₂` and the public preprocess/commitment data as above, fully compromising `V`'s validator key.

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be

  3) Sign and publish the signature share.

  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
