### Title
Uncaught CLVM path-traversal exception in `compute_spend_hints_and_additions()` allows a malicious offer/spend to crash wallet transaction processing - (File: `chia/wallet/util/compute_hints.py`)

### Summary
`compute_spend_hints_and_additions()` parses `CREATE_COIN` condition output using unchecked `Program.at()` path strings (`"rf"`, `"rrf"`, `"rrr"`, `"rrrf"`, `"rrrff"`) with no exception handling. `Program.at()` raises `clvm.EvalError.EvalError`/`ValueError` when the path walks past the end of a malformed (too-short) condition list. A counterparty can craft an offer whose puzzle output emits a truncated `CREATE_COIN` condition (e.g. `(51)` with no arguments), causing an unhandled exception that propagates out of wallet code that processes untrusted, attacker-supplied CLVM output during offer/trade handling.

### Finding Description
`compute_spend_hints_and_additions()` runs a `CoinSpend`'s puzzle/solution and then, for every emitted condition, blindly walks fixed `f`/`r` paths to pull out the puzzle hash, amount and optional hint: [1](#0-0) 

`Program.at()` is a thin wrapper that calls `.first()`/`.rest()` repeatedly for each character in the path string, with no bounds checking: [2](#0-1) 

Calling `.first()` on an atom (rather than a cons pair) — which happens when a `CREATE_COIN` condition is missing expected arguments — raises `clvm.EvalError.EvalError`, exactly as demonstrated by the existing unit test for `at()`: [3](#0-2) 

Unlike the Rust consensus condition parser (`SpendBundleConditions`) used for real mempool/block validation, this Python helper is invoked directly on the *raw, unvalidated* CLVM output of running an arbitrary puzzle/solution pair. It is reachable through several wallet-side, offer/trade code paths that process attacker-supplied coin spends before (or independent of) mempool admission — e.g. `TradeManager.calculate_tx_records_for_offer()`, which iterates every coin spend in an offer bundle (including the untrusted counterparty's spends) to compute hints: [4](#0-3) 

as well as `cat_wallet.py`, `did_wallet.py`, `cr_cat_wallet.py`, and `wallet_state_manager.py`, all of which call `compute_spend_hints_and_additions()` on coin spends derived from external data (offers, incoming coin notifications) without wrapping the call in exception handling.

This is directly analogous to CVE-2018-11375: a crafted/malformed input structure (there, a disassembled instruction; here, a truncated CLVM condition list) is walked by fixed-offset accessors without verifying the structure is long/deep enough, producing an unhandled crash instead of a controlled validation error.

### Impact Explanation
An attacker who can present a wallet user with a crafted offer file (or otherwise supply a `CoinSpend` whose puzzle emits a truncated `CREATE_COIN` condition, e.g. `(q . (51))`) can trigger an unhandled `EvalError`/`ValueError` inside wallet code paths responsible for evaluating and displaying offer contents. This causes an uncontrolled exception during offer validation/acceptance (`calculate_tx_records_for_offer`), i.e. a spend-triggered transaction-processing halt in the local wallet, rather than the intended graceful rejection (`ValidationError`/`Err.INVALID_CONDITION`) that consensus-level condition parsing (`parse_sexp_to_condition` in `chia/consensus/condition_tools.py`, which safely `break`s on missing args) provides.

### Likelihood Explanation
The trigger requires only crafting a CLVM puzzle that emits a syntactically short `CREATE_COIN` condition — trivial to construct, and delivered via a normal offer file, which is an explicitly user-facing, unprivileged input surface (offers are shared as data files between mutually untrusted parties). No signature, network access, or special privilege is required beyond convincing a wallet user to load/evaluate the offer.

### Recommendation
Wrap the `condition.at(...)` calls in `compute_spend_hints_and_additions()` in exception handling (catching `ValueError`/`EvalError`) and skip/ignore malformed conditions instead of propagating raw parser exceptions, mirroring the defensive `break`-on-missing-argument pattern already used in `chia/consensus/condition_tools.py::parse_sexp_to_condition`. Apply the same hardening to all direct callers that operate on untrusted spend bundles (offers, CAT/DID/CR-CAT wallets) or validate condition arity before calling `.at()`.

### Proof of Concept
1. Construct a coin spend whose puzzle, run with any solution, outputs the condition list `((51))` — a `CREATE_COIN` opcode with zero arguments (e.g. `(mod (args) (list (list 51)))`).
2. Wrap this coin spend as the "requested payment" puzzle/solution inside a crafted offer file, following the pattern in `Offer.to_spend_bundle()`/`from_spend_bundle()`.
3. Have a wallet user load the offer and call `TradeManager.calculate_tx_records_for_offer(offer, validate=True)` (the normal "view/accept offer" flow).
4. `compute_spend_hints_and_additions()` executes the puzzle, iterates the malformed `CREATE_COIN` condition, and calls `condition.at("rf")`; because `condition.rest()` returns `Nil` (an atom), the subsequent `.first()` raises `EvalError`, which propagates unhandled out of the offer-processing call, halting wallet offer processing.

```python
    def at(self, position: str) -> Program:
        """
        Take a string of only `f` and `r` characters and follow the corresponding path.

        Example:

        `assert Program.to(17) == Program.to([10, 20, 30, [15, 17], 40, 50]).at("rrrfrf")`

        """
        v = self
        for c in position.lower():
            if c == "f":
                v = v.first()
            elif c == "r":
                v = v.rest()
            else:
                raise ValueError(f"`at` got illegal character `{c}`. Only `f` & `r` allowed")
        return v
```
