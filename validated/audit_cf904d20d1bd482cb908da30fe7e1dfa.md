### Title
FROST preprocess seed reused across multiple `sign` calls, enabling key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a FROST `CachedPreprocess` seed in the DB keyed by `self.context`, but never deletes it after use. Every call to `share_internal` reconstructs a sign machine via `AlgorithmSignMachine::from_cache` with the *same* seed, deterministically regenerating the same nonces, and then calls `machine.sign(...)`. Within a single attempt, `DkgConfirmer::share` and `DkgConfirmer::complete` (and any repeated share computation) each trigger an independent `sign` on that same nonce set, producing multiple signature shares over distinct bindings/messages — the textbook Schnorr/FROST nonce-reuse break that the code's own documentation forbids.

### Finding Description
The SQLite UAF bug class — a resource that must be dead being accessed again — maps directly onto a consumed-once protocol state being reused. Serai's FROST library states the invariant explicitly: the cached preprocess "MUST only be used once. Reuse will enable third-party recovery of your private key share," and `from_cache` documents "After this, the preprocess must be deleted so it's never reused" (`crypto/frost/src/sign.rs`, `SignMachine::cache`/`from_cache` docs around lines 209-224; `spec/cryptography/FROST.md` lines 51-62).

`preprocess_internal` populates `CachedPreprocesses` once and reads it on every call (`coordinator/src/tributary/signing_protocol.rs` lines 123-145). There is no `del`/`remove`/`take` anywhere — the seed persists for the entire lifetime of the context. `share_internal` then does `self.preprocess_internal(participants).0` and immediately `machine.sign(preprocesses, msg)` (lines 150-178). `DkgConfirmer::share` (lines 304-310) and `DkgConfirmer::complete` (lines 312-327) both route through `share_internal`, and both take attacker-influenced `preprocesses`/`key_pair` parameters from on-chain transaction data (routed through `handle_application_tx` in `coordinator/src/tributary/handle.rs`, where `DkgCommitments`/share transactions are accumulated and dispatched).

Because `seeded_preprocess` derives all nonces from `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs` lines 121-144), every invocation produces identical nonces `d, e`. Two `sign` calls over different preprocess sets produce different binding factors `rho` and challenges `c` (msg also varies via `key_pair`), so `s1 = d + rho1·e + λ·share·c1` and `s2 = d + rho2·e + λ·share·c2` — two equations that an attacker can solve for `d`, `e`, and the private key share.

### Impact Explanation
An unprivileged tributary participant who can publish preprocess/share transactions causes the coordinator to emit two FROST signature shares under identical nonces with different challenges/binding factors. Solving the linear system recovers the coordinator's Ristretto secret share for the tributary MuSig key — full key-share recovery, the maximum-impact outcome for threshold signing, compromising the coordinator's signing identity for that validator set.

### Likelihood Explanation
Reachability requires only public inputs: transaction data published to the tributary that reaches `DkgConfirmer::share`/`complete` with distinct preprocess maps (e.g., different participant subsets or key pairs within the same attempt context, since the context key `(b"DkgConfirmer", attempt)` does not incorporate the signing set). The nonce reuse is deterministic — no race or special conditions needed; the cache is simply never invalidated. The main uncertainty is the exact coordinator code path frequency (how many `share_internal` invocations a single attempt permits), but `share` plus `complete` alone already sign twice, and `complete` explicitly re-signs with attacker-supplied `preprocesses`.

### Recommendation
Delete `CachedPreprocesses` immediately after `get` in `preprocess_internal` (i.e., `get`, remove the entry, then `from_cache`), enforcing the documented consume-once semantics at the type/DB level rather than by convention. Alternatively, key the cache by the full signing context including the preprocess-set hash so a second `sign` under the same context cannot reconstruct nonces.

### Proof of Concept
1. Attacker is a tributary validator. During a DKG confirmation `attempt`, the coordinator's `DkgConfirmer` context is `(b"DkgConfirmer", attempt)`; `CachedPreprocesses` is seeded on the first `preprocess_internal` call.
2. Attacker publishes transaction data causing `DkgConfirmer::share(preprocesses_A, key_pair_A)` → `share_internal` → `sign` → share `s_A` broadcast on-chain.
3. Attacker publishes a second preprocess set `preprocesses_B` (e.g., a different accumulated set or the `preprocesses` argument re-supplied to `complete`) reaching `share_internal` again with the same context → `from_cache` re-derives identical nonces → `sign` → share `s_B`.
4. `s_A − s_B = (rho_A − rho_B)·e + λ·share·(c_A − c_B)`; combining with the two published shares and known `rho`/`c` values (both publicly computable from the transcripts and commitments) yields the coordinator's secret share via standard two-equation nonce-reuse recovery.
