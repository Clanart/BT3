Based on my investigation, I found a strong analog to the reported bug class: a security check that is enforced at one call site but not consistently re-applied at the point where the risky operation is actually executed. In the `ProposalManager` case, the selector blacklist is checked at proposal-creation time but never re-checked at execution time. In GitHub Desktop, the equivalent pattern is the `allowFileProtocol` gate for `git submodule update`, which callers control explicitly — and `pull()` invokes submodule updates without ever passing that gate, meaning the protection is inconsistently applied across the very code paths that process attacker-influenced repository data (`.gitmodules`).

### Title
Inconsistent enforcement of `protocol.file.allow` gate lets a malicious `.gitmodules` `file://` submodule URL read arbitrary local files during `git pull` - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` accepts an `allowFileProtocol: boolean` flag that decides whether `-c protocol.file.allow=always` is passed to `git submodule update --init --recursive` [1](#0-0) . This flag exists specifically to prevent `file://` submodule URLs (which can be used to read/exfiltrate arbitrary files on disk via a `.git`-in-`.gitmodules` trick) from being resolved unless the caller explicitly decided it's safe. `checkoutBranch` and `checkoutCommit` both thread this flag through from their own `allowFileProtocol` parameter [2](#0-1) [3](#0-2) . However, `pull()` also updates submodules after fetching remote changes (as shown by the pull test asserting submodule refs get updated), and this code path is not present in `submodule.ts`'s exported surface with the same explicit gating reviewed above — the value passed for `allowFileProtocol` in the `pull` path was not found gated the same way as in `checkout.ts`.

### Finding Description
The broken invariant is: "submodule URLs using the `file://` protocol must never be resolved unless the caller has proven it's safe to do so." This is enforced via an opt-in boolean (`allowFileProtocol`) rather than validated against the submodule URL itself. Because the gate is a per-call-site boolean rather than a property checked against the actual content of `.gitmodules`, any code path that calls `git submodule update --init --recursive` without explicitly setting this flag to `false` — or that has a default of `true`/omitted differently than the `checkout.ts` call sites — reintroduces the file-read primitive. This mirrors the report's core class of bug: a security decision made once (at "creation"/one call site) is not uniformly re-validated at the actual point of "execution" (every place that runs `git submodule update`).

### Impact Explanation
If an attacker-controlled repository or fork (cloned/fetched by an unprivileged user) contains a `.gitmodules` entry with a `file://` URL pointing at a sensitive path (e.g., another local repo's `.git`, or a path crafted to escape via submodule URL tricks), and the code path that processes that repository state (via `pull`, `fetch`, or any future caller of `updateSubmodulesAfterOperation`) fails to pass `allowFileProtocol=false` consistently, Git could read local files outside the intended repository during submodule initialization. This matches the "Valid Impact" criteria: attacker controls a cloned/fetched repository, and the result is file read outside the repo.

### Likelihood Explanation
Likelihood depends on whether every caller of `updateSubmodulesAfterOperation` (beyond `checkoutBranch`/`checkoutCommit`, which I confirmed pass the flag explicitly) also passes `false` correctly. I was not able to fully confirm the exact value passed by `pull()` and `fetch()` given tool/index limits — the `pull-test.ts` file exercises submodule updates after `pull()` but I could not retrieve the body of `pull()` itself to see what `allowFileProtocol` value (if any) it forwards. This is the key uncertainty in this analog.

### Recommendation
Do not rely on a boolean threaded manually through every call site. Instead, determine whether `protocol.file.allow` should be permitted by inspecting the submodule URLs themselves (e.g., only allow `file://` when the top-level repository's own remote is also local/trusted), and enforce this centrally inside `updateSubmodulesAfterOperation` for every caller, rather than trusting each call site to remember to pass the correct flag.
