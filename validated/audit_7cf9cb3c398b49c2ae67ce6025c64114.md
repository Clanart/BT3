### Title
Panic via unregistered participant key in `Encryption::encrypt` / `Decryption::decrypt_with_proof` aborts the DKG process - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2019-15604 is a crafted-input → process-abort bug: a malicious peer supplies bytes that drive the victim into a fatal path rather than a clean error. The Serai analog lives in the PedPoP DKG encryption layer. `Decryption::enc_keys` is a `HashMap<Participant, C::G>` populated only when an `EncryptionKeyMessage` for a participant is registered, yet both the encryption path and the blame-decryption path index it with unchecked `map[&participant]` lookups, which panic (and abort under `panic = "abort"`) when the key is absent.

### Finding Description
`Encryption::encrypt` performs `self.decryption.enc_keys[&participant]` when generating a per-participant encrypted secret share (crypto/dkg/pedpop/src/encryption.rs:466). Similarly, `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` while verifying an `EncryptionKeyProof` DLEq during the blame/reveal flow (crypto/dkg/pedpop/src/encryption.rs:388). The map is only filled by `Decryption::register`, which itself contains a `assert!(!self.enc_keys.contains_key(&participant))` that panics on re-registration (crypto/dkg/pedpop/src/encryption.rs:356-360). There is no `io::Error`/`Result` path for a missing entry — indexing a `HashMap` with a nonexistent key is an unconditional panic in `core`.

This mirrors the CVE class precisely: attacker-controlled protocol state (whether a given participant's `EncryptionKeyMessage` was delivered/registered, or which `decryptor` index is passed to `decrypt_with_proof`) determines whether the victim hits a fatal panic instead of an error. The library explicitly acknowledges it "does not handle networking" and cannot detect a participant sending duplicate commitment sets (crypto/dkg/pedpop/src/lib.rs:98-101), meaning a participant that withholds or duplicates its `EncryptionKeyMessage` is a reachable scenario, not an abuse of a documented requirement. All other deserialization entry points (`read_G`, `read_F`, `SchnorrSignature::read`, `Commitments::read`, `EncryptedMessage::read`) correctly return `io::Error` on bad bytes (crypto/ciphersuite/src/lib.rs:74-101, crypto/dkg/pedpop/src/encryption.rs:171-177), so the panic surface is specifically these map lookups and the `assert!`.

### Impact Explanation
An unprivileged participant in a PedPoP DKG session can abort the victim's process: by withholding their `EncryptionKeyMessage` (so `enc_keys` has no entry for them) while the victim proceeds to generate/encrypt shares or to process a blame/decryption proof referencing that participant, the victim panics mid-protocol. This is a remote, input-triggered denial of service against the DKG — the same availability impact as CVE-2019-15604 (CVSS 7.5, availability-only). It also gives a malicious participant a blame-evasion angle: crashing a validator during share distribution or during the `decrypt_with_proof` reveal flow prevents the victim from completing the protocol or producing blame evidence against the faulty party.

### Likelihood Explanation
Reachability requires the PedPoP driver to call `encrypt`/`decrypt_with_proof` for a participant that never registered an encryption key, or to feed a `decryptor` index absent from the map. Because `register` is invoked per received `EncryptionKeyMessage` and the library relies on the caller for message dedup/ordering, a participant that sends no key message (or sends one only to a subset of peers — equivocation over the authenticated channel) leaves the map incomplete. Any subsequent share generation for, or decryption proof involving, that participant panics. The `register` `assert!` additionally fires if a caller ever processes a second registration for the same participant. These are ordinary byzantine-behavior paths in a DKG, not contrived misuse.

### Recommendation
Replace map indexing with checked lookups returning errors:
- `Encryption::encrypt`: `let Some(to) = self.decryption.enc_keys.get(&participant) else { return Err(FrostError::InvalidParticipant / DecryptionError) };`
- `decrypt_with_proof`: same for `enc_keys.get(&decryptor)`.
- `Decryption::register`: return a `Result`/`Err` instead of `assert!` on duplicate registration, since duplicate messages are a documented caller responsibility that the library currently enforces with a panic rather than an error.

### Proof of Concept
```rust
// PedPoP session, threshold params (t, n, i), ciphersuite C.
// Honest node creates its Encryption box and registers key messages
// only from the participants who actually sent them.
let mut enc = Encryption::<C>::new(context, our_i, &mut rng);

// Participant 3 (of n) withholds their EncryptionKeyMessage.
// enc_keys now contains entries for {1, 2} but not 3.
enc.register(Participant(1), msg_from_1);
enc.register(Participant(2), msg_from_2);

// The driver proceeds to generate shares for all n participants,
// or a blame/reveal flow calls decrypt_with_proof naming participant 3.
// Either line panics:
enc.encrypt(&mut rng, Participant(3), share_msg);          // enc_keys[&3] -> panic
dec.decrypt_with_proof(from, Participant(3), msg, proof);  // enc_keys[&3] -> panic
```
PoC confidence note: the panic sites themselves are unconditional (`HashMap` index + `assert!`), verified at crypto/dkg/pedpop/src/encryption.rs:388, :466, :356-359. Exact caller flow in `crypto/dkg/pedpop/src/lib.rs` that reaches `encrypt` for non-registered participants was not fully traced in this review; if the driver only encrypts to participants it registered, reachability narrows to the `decrypt_with_proof`/`register` paths during blame handling, which remain attacker-influenced (a participant sends a key to some peers but not others, then triggers a reveal).
