## Finding

The vulnerability report is confirmed valid. `handle_connection` in `rpc/src/rpc_pubsub_service.rs` performs an unbounded `await` on both the WebSocket handshake (`server.receive_request().await?`) and the per-message read (`receive_future` inside the `select!` loop), with no `tokio::time::timeout` wrapper or idle-deadline anywhere in the file or in the calling `listen` function. [1](#0-0) [2](#0-1) 

The only per-connection instrumentation is `TokenCounter`, which is purely a metrics counter (`counter.create_token()` / `drop(counter_token)`), not a connection limiter or timeout mechanism — it does not reject or evict stalled connections. [3](#0-2) 

The `tripwire` future in the `select!` only fires on service-wide shutdown, not on a per-connection idle timer, so it provides no protection against a single client holding a connection open indefinitely. [4](#0-3) 

Each accepted TCP connection is spawned as its own tokio task via `tokio::spawn`, so a client that completes the TCP handshake but never completes the HTTP Upgrade / WebSocket handshake (or never sends a complete WS frame) will keep that task and its socket (and the `IoHandler`, `DashMap` of subscriptions, `broadcast_receiver`, etc. allocated inside `handle_connection`) alive for as long as the TCP connection remains open, with no server-side timeout to reclaim it. [5](#0-4) 

This is a genuine slow-loris-style resource exhaustion path: an unprivileged, unauthenticated attacker can open many TCP connections to the pubsub port, send a partial HTTP Upgrade request (or none at all after the TCP handshake), and hold them open, exhausting file descriptors / tokio tasks on the pubsub runtime with minimal attacker-side resources.

### Title
Unbounded WebSocket handshake/read await in `rpc_pubsub_service::handle_connection` enables slow-loris resource exhaustion - (File: `rpc/src/rpc_pubsub_service.rs`)

### Summary
`handle_connection` awaits `server.receive_request()` and `receiver.receive_data()` with no timeout. A client that never completes the WS handshake, or that opens the connection and never sends a complete frame, ties up a tokio task and the underlying TCP socket indefinitely.

### Finding Description
- `handle_connection` (`rpc/src/rpc_pubsub_service.rs:349-427`) calls `server.receive_request().await?` at line 356 with no surrounding `tokio::time::timeout`.
- After the handshake, the inner `select!` loop's `receive_future` (line 384-398) is likewise unbounded; the only other arms are `broadcast_receiver.recv()` and the global shutdown `tripwire`, neither of which bounds per-connection idle time.
- `listen()` spawns a new task per accepted TCP connection (line 458-467) and only tracks connection count via `TokenCounter`, which is metrics-only and imposes no cap or eviction.
- Consequently, a client can perform the TCP 3-way handshake and then simply stop sending bytes (or send a partial HTTP Upgrade request), and the corresponding server-side task/socket will remain alive until the process shuts down or the OS/network layer forcibly closes the socket.

### Impact Explanation
Repeating this from many connections (or many source ports on one attacker host) allows an unprivileged remote party to exhaust file descriptors and/or tokio task/memory resources dedicated to the RPC pubsub listener, degrading or halting pubsub service availability for legitimate clients without needing to complete authentication or send valid data. This matches the "non-RPC remote exhaustion" / "single-client low-rate degradation" impact category for the pubsub surface.

### Likelihood Explanation
High likelihood: the pubsub endpoint is unauthenticated and exposed to any client able to reach the RPC pubsub port; the attack requires only opening TCP sockets and withholding data, which is trivial and low-cost for the attacker.

### Recommendation
Wrap the handshake await (`server.receive_request()`) and the inner-loop `receive_future` with `tokio::time::timeout(...)`, closing the connection and dropping the task if no progress occurs within a bounded idle window. Additionally, consider bounding total concurrent pubsub connections (using the existing `TokenCounter` as an actual gate rather than a metric) to limit slow-loris style connection accumulation.

### Proof of Concept
1. Start a validator/RPC node with the pubsub websocket listener enabled.
2. From an attacker machine, open a raw TCP connection to the pubsub port and send only a partial HTTP `Upgrade` request line (e.g., `GET / HTTP/1.1\r\n` without the remaining headers/blank line), then stop sending data.
3. Observe via `netstat`/`ss` or process file-descriptor counts that the connection and its associated tokio task remain open indefinitely (the socket is never closed by the server).
4. Repeat the connection-open step many times in parallel to demonstrate cumulative resource retention (FD/task growth) with no corresponding server-side timeout evicting stale connections.
