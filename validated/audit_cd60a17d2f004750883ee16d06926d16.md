### Title
Missing BIP-340 parity normalization of the group key produces Schnorr signatures Bitcoin will reject — ([File: networks/bitcoin/src/crypto.rs](networks/bitcoin/src/crypto.rs))

### Summary
The report's bug class is a normalization-naive check: a value with multiple equivalent encodings (`Transfer-Encoding: ChuNked`) is compared against a single canonical form, so the semantic property ("a body follows") is missed and downstream processing desynchronizes. In `bitcoin-serai`'s FROST→BIP-340 adapter the same class appears as parity normalization: x-only keys and nonces each have two equivalent encodings (even-Y / odd-Y), and the code normalizes the sign of `R` but never the sign of the group key `A`. As a result, whenever the threshold group key has an odd Y coordinate, every signature the protocol produces is invalid under BIP-340.

### Finding Description
`Hram::hram` correctly hashes `x(R)` and `x(A)` and negates the challenge when `R` has odd Y, so that the final `s` can be negated to represent the even-Y nonce `-R` (`crypto.rs:59-73`). `Schnorr::verify` then applies `s = -s` iff `R` was odd and serializes only `x(R)` (`crypto.rs:145-149`). This fully implements BIP-340's nonce-side parity rule — but ignores the identical rule for the key.

BIP-340 verification lifts `x(A)` to the **even-Y** point `P = |A|` and checks `s·G = R' + c·P`. If `A` has odd Y, `P = -A`, and a valid signature must be produced with the negated secret `x' = -x`. Serai's code never negates the secret/key contribution for `A`'s parity: `verify` signs `r + c·x` (negated to `-r + c·x` when `R` is odd), which satisfies `s·G = -R + c·A` — i.e., it verifies against the *odd* representative `A`, not `P = -A`. A Bitcoin verifier computing `x(R') || s` against `x(A)` gets `s·G ≠ R' + c·|A|` and rejects the signature.

### Impact Explanation
Any Taproot-style output controlled by a group key whose Y coordinate is odd — which occurs with probability ~1/2 for any honestly generated `ThresholdKeys<Secp256k1>` set (the DKG/musig key is a full point with no parity constraint) — cannot be spent via this signing path. The threshold protocol completes successfully, `complete` returns a signature, and the "signed" transaction is consensus-invalid. Funds locked to such keys are unspendable, matching the accepted impact class of "funds reported received that are not spendable." This is not fixable post-hoc by the caller: no API exists to negate the distributed secret share, and `view()`/`offset()`/`scale()` don't provide a parity-aware negation hook.

### Likelihood Explanation
No attacker action is required; the failure is a deterministic function of the DKG output, with ~50% probability per key set. The flaw is in the reachable `verify`/`sign_share` path used for every Bitcoin signature the processor produces via `AlgorithmSignMachine`/`AlgorithmSignatureMachine` with `Schnorr::new()`.

### Recommendation
When constructing the signing algorithm (or in `verify`), check `needs_negation(group_key)`; if the group key has odd Y, have every participant negate its secret share contribution (equivalently, negate `s` in addition to the existing `R`-parity negation) so the signature verifies against the even-Y lift `|A|`. A clean implementation: compute `s'` as `±s` under the conjunction of `needs_negation(R)` and `needs_negation(A)`, since `s·G = R' + c·P` requires `s = r' + c·x'` with `r' = ±r`, `x' = ±x` per both parities.

### Proof of Concept
1. Run `musig`/`ThresholdKeys` DKG to obtain a group key `A` with odd Y (`needs_negation(&A) == 1`); retry key generation until so — ~2 attempts expected.
2. Complete any FROST signing round via `Schnorr::new()`; `verify` returns a 64-byte `x(R) || s` signature.
3. Verify with `bitcoin::secp256k1` `verify_schnorr` (or BIP-340 test vectors machinery): `s·G = -R + c·A` holds, but the verifier computes `R' + c·|A|` where `|A| = -A`, yielding `s·G ≠ R' + c·(-A)` unless `c·A` coincidentally vanishes. The signature is rejected.
4. Contrast: for an even-Y `A`, the same code produces valid signatures — confirming the defect is the missing `A`-parity normalization, exactly analogous to h3's missing `.toLowerCase()` on a semantically-equivalent encoding.
