### Title
Boundary check in `resolveWithin` uses raw string-prefix `startsWith` instead of separator-aware comparison, allowing sibling-directory escape via deep link `filepath` - ([File: app/src/lib/path.ts])

### Summary
The reported smart-contract bug is a boundary-condition error where a `<=` comparison lets a value sit exactly on the boundary and be treated as "inside" when it should be treated as "at the edge/outside" the safety threshold. The same class of bug — an off-by-one/boundary check on a string/path comparison — exists in Desktop's repo-root sandbox helper `resolveWithin()`.

### Finding Description
`_resolveWithin()` is Desktop's canonical guard against path traversal: it resolves a target path and only allows it if it is "at, or underneath" a `rootPath`. The final check is:
```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [3](#0-2) 

`startsWith` performs a raw string-prefix comparison, not a path-segment-boundary comparison. There is no trailing path separator appended to `realRoot` before the comparison, and no check that the character immediately following the matched prefix in `realResolved` is a path separator (or end-of-string). This means any real path that merely shares the same string prefix as the root — including a **sibling** directory with a longer name — passes the check even though it does not reside "at, or underneath" the root directory. For example, if `realRoot` is `/Users/victim/Documents/GitHub/myrepo`, a resolved path of `/Users/victim/Documents/GitHub/myrepo-secrets/config` (a completely separate directory) also satisfies `startsWith(realRoot)`.

This is directly analogous to the reported bug: both are boundary-comparison defects (`<=` vs `<`, and unguarded `startsWith` vs separator-aware containment) that make an "edge" value which should be rejected instead pass a security check meant to enforce strict containment.

The attacker-controlled entry point is the `x-github-client://openrepo/...?filepath=...` deep link. `parseAppURL()` extracts `filepath` from the URL query string with no validation of its content (only `isAbsolute()` is checked in the caller) [1](#0-0) , and `Dispatcher.openRepositoryFromUrl()` passes it straight to `resolveWithin(repository.path, filepath)`, then calls `shell.showItemInFolder(resolved)` on success [2](#0-1) .

### Impact Explanation
If an attacker can get a repository cloned locally into a directory whose name is a string-prefix of another sensitive directory on disk (e.g., by controlling the repo/owner name used to derive the clone folder — see `sanitizeCloneName` in `app/src/lib/remote-parsing.ts`), or if the user already has such directories side-by-side (`myrepo` and `myrepo-backup`, `myrepo` and `myrepo.git-old`, etc.), a crafted `x-github-client://openrepo/...&filepath=../myrepo-secrets/id_rsa` style deep link could cause `resolveWithin` to incorrectly validate a path that escapes the intended repository root, and Desktop would then reveal/open that file via `shell.showItemInFolder`. This fits the "link/deep link the user clicks... result is file read outside the repo" impact category.

### Likelihood Explanation
Exploitability depends on the victim having (or the attacker being able to arrange) a directory name that is a superstring of the repository path with the same prefix, which is a real but not universal precondition — it requires either a naming coincidence on the victim's filesystem or attacker influence over the clone destination naming (which Desktop does otherwise try to sanitize via `sanitizeCloneName`/`isClonePathSensitive` in `app/src/lib/git/clone.ts`). Because those other mitigations exist for the *clone* path but not for the `startsWith` boundary check itself, likelihood is moderate — the vulnerable comparison is a latent defect that only manifests under specific directory-naming conditions, but it is a clear violation of the function's documented contract ("resolved path is guaranteed to reside at, or underneath this path").

### Recommendation
Change the containment check in `_resolveWithin()` (`app/src/lib/path.ts`) to be separator-aware, e.g.:
```ts
return realResolved === realRoot ||
  realResolved.startsWith(realRoot.endsWith(Path.sep) ? realRoot : realRoot + Path.sep)
  ? resolved
  : null
```
This ensures a sibling directory that merely shares a string prefix can never satisfy the containment check.

### Proof of Concept
1. Suppose the victim has two folders: `/Users/victim/Documents/GitHub/myrepo` (the actual cloned repository, added to Desktop) and `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa` (an unrelated sensitive file).
2. Attacker sends the victim a link: `x-github-client://openrepo/owner/myrepo?filepath=..%2Fmyrepo-secrets%2Fid_rsa`.
3. `parseAppURL` extracts `filepath = "../myrepo-secrets/id_rsa"` with no path validation [1](#0-0) .
4. `Dispatcher.openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)` where `repository.path` is `/Users/victim/Documents/GitHub/myrepo` [2](#0-1) .
5. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/myrepo-secrets/id_rsa`, and `realResolved.startsWith(realRoot)` evaluates true because the string `"...GitHub/myrepo-secrets/id_rsa"` starts with `"...GitHub/myrepo"` [3](#0-2) .
6. The check incorrectly passes, and `shell.showItemInFolder(resolved)` reveals the file outside the intended repository root.

Note: I was unable to fully verify the reachability of a matching directory-name collision in a default Desktop install without running the app; the existing unit tests in `app/test/unit/path-test.ts` test symlink escapes and `..` traversal but do not appear to cover the sibling-prefix case, which is consistent with this being an untested edge case.
