### Title
Deep-link branch parameter bypasses ref-name validation for leading `-`, enabling git argument/flag injection on checkout - (File: app/src/lib/parse-app-url.ts)

### Summary
GitHub Desktop registers a custom URL protocol (`x-github-client://`, `github-mac://`) handled by `parseAppURL`, which lets a remote web page or link fully control the `branch` parameter used to open/clone a repository and then check out that branch. The validation applied to this attacker-controlled branch name, `testForInvalidChars`, only rejects a fixed set of illegal ref characters but — unlike the sibling function `sanitizedRefName` used elsewhere in the codebase — does not strip or reject a leading `-`/`+`. A branch value such as `--orphan=evil` or other leading-dash strings therefore passes validation and flows into `Dispatcher.openBranchNameFromUrl` → `checkoutLocalBranch`.

### Finding Description
`parseAppURL` in [1](#0-0)  extracts `branch` from the query string of an attacker-supplied `openrepo` deep link and only rejects it if `testForInvalidChars(branch)` returns true.

`testForInvalidChars` and its sibling `sanitizedRefName` are defined in [2](#0-1) . Note that `sanitizedRefName` explicitly strips a leading `-`/`+` (`.replace(/^[-\+]*/g, '')`) when Desktop itself generates ref names (e.g. for newly created branches), but `testForInvalidChars` — used to validate the deep-link `branch` parameter — has no equivalent check. A string like `--orphan=pwn` or `-c core.fsmonitor=...` contains no character matched by `invalidCharacterRegex`, so it is accepted as a "valid" branch name.

The accepted branch name is then passed unmodified through `Dispatcher.openBranchNameFromUrl` into `checkoutLocalBranch` [3](#0-2) , which ultimately invokes a `git checkout` command with the string as a positional argument.

I was not able to fully retrieve the exact argument list constructed in `app/src/lib/git/checkout.ts` for the local-branch-checkout path within the available tool calls, so I cannot confirm with certainty whether a `--` separator is inserted before the branch name (as is done defensively elsewhere in this codebase, e.g. `clone.ts` explicitly appends `args.push('--', url, path)` at [4](#0-3) ). If `checkout.ts` does not apply the same `--` guard for the "checkout existing local branch" invocation, a leading-dash branch value would be interpreted by git as a flag rather than a ref name.

### Impact Explanation
If the underlying `git checkout` invocation does not separate the branch argument with `--`, a malicious deep link (e.g. embedded in a webpage, GitHub Issue, or email) can inject git flags such as `--orphan`, `-b`, or config-altering options into a checkout run against the victim's local clone, without any privilege beyond the victim clicking a link. This falls squarely in the "silent corruption of what the user commits or pushes" impact category called out as valid in the report, since a victim could unknowingly end up on an orphan/detached branch state or with altered checkout semantics while believing normal navigation occurred.

### Likelihood Explanation
The precondition is low-effort for an attacker (a clickable custom-protocol link) and requires no local access, credentials, or social engineering beyond a single click, which Desktop's own protocol-handler design explicitly supports. The validation gap itself (asymmetry between `sanitizedRefName`'s dash-stripping and `testForInvalidChars`'s lack of a dash check) is concrete and directly verifiable in the two functions cited above. The unresolved part — whether `checkout.ts` uses a `--` separator for this call path — determines whether this rises to full exploitability; I could not verify this file's content before running out of tool budget.

### Recommendation
Apply the same leading-dash stripping/rejection used in `sanitizedRefName` to the deep-link `branch` parameter inside `parseAppURL`/`testForInvalidChars`, and audit every `git` invocation that accepts a branch/ref name sourced from `IOpenRepositoryFromURLAction` (or any other externally-controlled string) to ensure a `--` end-of-options marker precedes it, consistent with the pattern already used in `clone.ts`.

### Proof of Concept
1. Attacker crafts a link: `x-github-client://openRepo/https://github.com/some/repo?branch=--orphan%3Dpwn`
2. Victim clicks the link; `handleAppURL` → `parseAppURL` parses `branch = "--orphan=pwn"`, which does not match `invalidCharacterRegex`, so it is accepted as `IOpenRepositoryFromURLAction.branch`.
3. `Dispatcher.openBranchNameFromUrl` calls `checkoutLocalBranch(repository, "--orphan=pwn")`.
4. If the checkout git invocation lacks a `--` separator, git interprets the value as the `--orphan` flag rather than a branch name, altering the checkout behavior against the victim's expectation.

**Caveat:** I was unable to confirm step 4 (the exact argument array in `app/src/lib/git/checkout.ts`) before the tool budget was exhausted. This is a genuine, verifiable validation gap (steps 1–3), but full exploitability depends on that unverified detail — I recommend a Devin session with full file access to confirm `checkout.ts`'s argument construction before treating this as a confirmed, exploitable finding.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
