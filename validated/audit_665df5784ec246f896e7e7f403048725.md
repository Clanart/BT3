### Title
Panic in BIP-340 HRAm on attacker-controlled identity nonce sum crashes FROST signers - ([File: networks/bitcoin/src/crypto.rs])

### Summary
The bor fix addressed a crash caused by calling into math code on unvalidated (nil) input. The analog in Serai is `x()`/`x_only()` in `networks/bitcoin/src/crypto.rs`, which `expect`s the input point to be non-infinity. `Hram::hram` calls `x(R)` on the aggregated nonce `R` derived from `nonce_sums`, which is computed from preprocesses supplied by other (potentially malicious) participants. `Curve::read_G` rejects the identity point only on an individual encoding, not on the sum of commitments, so a participant who submits a nonce commitment that cancels the others' commitments to the identity causes every honest signer to panic inside `sign_share`/`verify` instead of returning a `FrostError`.

### Finding Description
- `x(key)` panics when `key` is the point at infinity: `(*encoded.x().expect("point at infinity"))` [1](#0-0) 
- `Hram::hram` unconditionally calls `x(R)` and `x(A)` on the signature nonce and group key [2](#0-1) 
- The `Schnorr` algorithm's `sign_share`/`verify` delegate to `FrostSchnorr` with `Hram`, and the doc comment admits the code "may panic if called with nonces/a group key which are the point at infinity" while claiming this is "negligible... even with malicious participants" [3](#0-2) 
- That claim is wrong: per-participant preprocess nonces are deserialized with `Curve::read_G`, which rejects identity per point but does not constrain the aggregate sum [4](#0-3) . A malicious participant can choose its nonce commitment `D_i = -(sum of all other participants' commitments)`, yielding `nonce_sums[0] = identity`, so `hram` dereferences `x()` on the infinity point and panics.

### Impact Explanation
An unprivileged participant in a signing session (e.g., a validator submitting a preprocess on tributary) can deterministically crash every honest signer's process during `sign_share`/`verify` for any Bitcoin (secp256k1/Taproot) signing attempt. This is a liveness/DoS failure: the panic occurs before a `FrostError` can be produced, so blame cannot be attributed and the honest multisig cannot proceed or cleanly exclude the faulty party. Repeated attempts crash the signers again.

### Likelihood Explanation
Reachability requires the attacker to choose their nonce commitment after learning the other participants' commitments (or to have the coordinator/ordering allow adaptive submission), which is plausible when preprocesses are exchanged in separate network messages — the attacker simply publishes last. The library itself does not prevent this; it only checks each decoded point for identity, not the summed nonce. I could not fully confirm the internals of `FrostSchnorr::sign_share`/`sign` in `crypto/frost/src/algorithm.rs` (whether it validates the summed nonce before calling `hram`) within the available iterations, but the documented panic condition on infinity nonces indicates no such guard exists upstream of `x()`.

### Recommendation
Reject a nonce aggregate equal to the identity point before invoking `Hram::hram` — e.g., check `nonce_sums`/`R.is_identity()` in `sign_share`/`verify_share`/`verify` and return a `FrostError`/`None` identifying the session as invalid, or have `Hram::hram` return an error/zero challenge instead of panicking in `x()`. Alternatively, check each participant's summed nonce contribution per-participant so the faulty preprocess can be blamed and excluded.

### Proof of Concept
In a 2-of-n Bitcoin FROST signing session:
1. Victims publish preprocess commitments `D_1 = d_1·G`, `D_2 = d_2·G`, …
2. Attacker publishes `D_a = -(D_1 + D_2 + …)` — a valid non-identity point that passes `Curve::read_G`.
3. The library computes `nonce_sums[0] = D_1 + D_2 + … + D_a = O` (identity).
4. `Schnorr::sign_share` → `Hram::hram(&O, A, msg)` → `x(&O)` → `encoded.x().expect("point at infinity")` → panic on every honest signer, crashing the signing process rather than returning an attributable `FrostError`.
