### Title
Insufficient Range/Component Validation in upb JSON Timestamp Parser Accepts Out-of-Spec Values - (File: `upb/json/decode.c`)

### Summary
`jsondec_timestamp()` in the upb JSON decoder (shared by Python-upb, PHP, Ruby, and other upb-backed language bindings) only checks the lower bound of the `seconds` field and never validates the upper bound or the individual calendar/time components (month, day, hour, minute, second, timezone offset), unlike every other Protobuf JSON implementation (C++ `parser.cc`, Java `Timestamps.java`, Python pure `well_known_types.py`, C# `JsonParser.cs`). This lets a client-supplied ProtoJSON string produce a `Timestamp` message whose `seconds`/`nanos` values are outside the documented valid range `[0001-01-01T00:00:00Z, 9999-12-31T23:59:59.999999999Z]`, or that encode a calendar date/time that never existed (e.g., month 13, hour 25, Feb 29 on a non-leap year).

### Finding Description
The external report's failed invariant is: administrative timestamp inputs are not validated against a valid ordering/range before being persisted and relied upon by the contract. The transferable Protobuf analog is: the well-known `google.protobuf.Timestamp` type has a documented valid range and component semantics that other trusted-application code paths rely on (e.g., `Timestamps.checkValid()` in Java [2](#0-1) , and the C++ ProtoJSON serializer/parser which validates both bounds [3](#0-2) ). The upb JSON parser is the parsing backend for ProtoJSON in Python (`_upb`), PHP, and Ruby.

In `jsondec_timestamp()`, the year/month/day/hour/min/sec are extracted digit-by-digit via `jsondec_tsdigits()`, which only validates digit count and the expected separator character — never the semantic range of the value (month ∈ [1,12], day ∈ [1,31] and calendar-valid for the month/year, hour ∈ [0,23], minute/second ∈ [0,59], offset ≤ 18:00) [4](#0-3) . After computing `seconds.int64_val` from these unchecked components, the function performs exactly one check:

```c
if (seconds.int64_val < -62135596800) {
  jsondec_err(d, "Timestamp out of range");
}
```

There is no corresponding `> 253402300799` upper-bound check, and no post-validation of the derived `nanos`/`seconds` combination [5](#0-4) . By contrast, C++'s `ParseTimestamp` validates month/day/hour/minute/second bounds and timezone offset magnitude and the C++ JSON *unparser* validates both the lower and upper bound of `secs` [3](#0-2) , and Java/Python/C# all check both `TIMESTAMP_SECONDS_MIN` and `TIMESTAMP_SECONDS_MAX` [6](#0-5) .

This is not a one-off oversight I'm speculating about — the project's own conformance-test infrastructure documents it as a known, currently-accepted divergence for upb-backed bindings: `Required.*.JsonInput.TimestampJsonInputMonthTooLarge`, `HourTooLarge`, `HourTooLarge25`, `MinuteTooLarge`, `SecondTooLarge`, `NonLeapFeb29`, `OffsetBoundaryOverflow`/`Underflow`, `InvalidOffsetHour`/`Minute` are all listed as "Should have failed to parse, but didn't" in `upb/conformance/conformance_upb_failures.txt` [1](#0-0) , and the same set (plus `DayZero`, `DayTooLarge`, `MonthZero`, `YearTooLong`/`Short`) reappears in the language-specific failure lists that route through upb: `conformance/failure_list_php.txt` [7](#0-6) , `conformance/failure_list_jruby_ffi.txt` [8](#0-7) , and Java's upb-backed variant list.

The upstream Protobuf conformance test suite itself, which is the specification/oracle here, explicitly requires (`REQUIRED` severity) that timestamps with these out-of-bounds components — including "TimestampJsonInputTooLarge" for the year overflow case, seconds `253402300800` for the seconds upper bound — must fail to parse [9](#0-8) . The upb decoder violates this specification for the seconds upper bound and all the calendar-component-range checks.

### Impact Explanation
A client sending a bounded ProtoJSON payload (well within normal size/format expectations, no malicious schema or privileged access) through the public parse API of any upb-backed language binding (Python `_upb`, PHP, Ruby, and consumers linking `upb/json/decode.c` directly) can cause a `Timestamp` message to be populated with a `seconds` value greater than `253402300799` (year > 9999) or one derived from a semantically invalid date/time (month 13, day 32, hour 25, Feb 29 in a non-leap year, out-of-range UTC offset). Because upstream application code — including Protobuf's own `Timestamps`/`TimeUtil` utility classes in other languages — assumes `isValid()`/`checkValid()` semantics for any `Timestamp` that successfully parsed, cross-language interop (parse in upb-backed binding, serialize/consume in Java/C++/Python-pure) can propagate an out-of-spec value that downstream validation elsewhere assumes cannot exist. This is a parser/spec-conformance integrity gap, not a memory-safety bug (no crash, no overflow — `int64_t` accumulation cannot overflow for a 4-digit year), which keeps it in Medium territory, matching the severity of the original report (which is also about accepting semantically invalid/misordered timestamp data with no crash or exploit primitive).

### Likelihood Explanation
High likelihood of occurrence for any application relying on the upb JSON decoder (Python `_upb`, PHP, Ruby) to validate untrusted ProtoJSON `Timestamp` input, since this is a default code path reachable via the standard, documented `JsonToMessage`/`Parse` entry points, requires no special conditions, and is already confirmed (not hypothetical) via the project's own conformance suite results tracked in the failure lists.

### Recommendation
1. Add the missing upper-bound check in `jsondec_timestamp()`: reject if `seconds.int64_val > 253402300799`, mirroring the C++ unparser's symmetric check [3](#0-2) .
2. Validate month ∈ [1,12], day ∈ [1, days-in-month(year,month)] (accounting for leap years), hour ∈ [0,23], minute/second ∈ [0,59], and timezone offset magnitude ≤ 18:00 inside `jsondec_tsdigits`/`jsondec_timestamp`, consistent with the C++ `ParseContext`/`unparser.cc` behavior and the conformance suite's `REQUIRED` expectations.
3. Update the failure lists (`upb/conformance/conformance_upb_failures.txt`, `conformance/failure_list_php.txt`, `conformance/failure_list_jruby_ffi.txt`, `conformance/failure_list_java.txt`) to remove these entries once fixed, closing the tracked conformance gap rather than leaving it permanently allow-listed.

### Proof of Concept
Using any upb-backed binding (e.g., Python `google.protobuf` built with the `_upb` implementation, or PHP), parse the following ProtoJSON into a message containing a `google.protobuf.Timestamp` field:
```json
{"optionalTimestamp": "9999-12-31T23:59:60Z"}
```
or, to exercise the missing upper bound directly:
```json
{"optionalTimestamp": "10000-01-01T00:00:00Z"}
```
Per the conformance suite this must raise a parse error (`ExpectParseFailureForJson("TimestampJsonInputTooLarge", REQUIRED, ...)`) [10](#0-9) , and per the second-too-large test (`TimestampJsonInputSecondTooLarge`) as well [11](#0-10) . Tracing `jsondec_timestamp()`: `jsondec_tsdigits()` will accept `"99"` for seconds (or `"9999"`-plus-extra-digit year handling is bounded by the 4-digit read, but the arithmetic in `jsondec_unixtime` has no upper clamp) and the only guard executed afterward is `if (seconds.int64_val < -62135596800)` [5](#0-4) , which does not fire for an out-of-range-high or component-invalid value, so parsing succeeds and returns a `Timestamp` populated with the invalid value — confirmed by the project's own recorded conformance-test failures for exactly these cases [1](#0-0) .

```c
static int jsondec_tsdigits(jsondec* d, const char** ptr, size_t digits,
                            const char* after) {
  uint64_t val;
  const char* p = *ptr;
  const char* end = p + digits;
  size_t after_len = after ? strlen(after) : 0;

  UPB_ASSERT(digits <= 9); /* int can't overflow. */

  if (jsondec_buftouint64(d, p, end, &val) != end ||
      (after_len && memcmp(end, after, after_len) != 0)) {
    jsondec_err(d, "Malformed timestamp");
  }

  UPB_ASSERT(val < INT_MAX);

  *ptr = end + after_len;
  return (int)val;
}
```
