Based on my investigation, the strongest analog to this bug class in the kaia repo is the `kaiax/gasless` module's sender "EOA-ness" check, which — like the reported `msg.sender != tx.origin` check — relies on an indirect signal to gate an unprivileged/gasless-lending flow, and is now made unreliable by the same underlying feature the report warned about: EIP-7702/EIP-3074-style delegation that lets an EOA temporarily execute as a contract, which this codebase already implements as `TxTypeEthereumSetCode`.

### Title
Gasless module's sender-code ("EOA") check relies on a stale snapshot state, allowing bypass of the `BalanceCheckLevelAll` safeguard - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The `kaiax/gasless` module gates admission of `GaslessApproveTx`/`GaslessSwapTx` (KIP-247) with a check that the sender has no code, intended to prevent contract-based abuse of the proposer-funded gasless lending flow, analogous in intent to `RioLRTCoordinator`'s `msg.sender != tx.origin` EOA check.

### Finding Description
`checkBalanceForApprove` and `checkBalanceForSwap` call `g.getCurrentHasCode(sender)` when `GaslessConfig.ShouldCheckSenderCode()` is enabled (`BalanceCheckLevelAll`), rejecting the tx with `"sender with code is not allowed"` if the sender currently has code [1](#0-0) [2](#0-1) .

This check does not query the live pool state (`pool.currentState`) at the moment of validation; instead it consults `g.currentState`, a separately-cached `*state.StateDB` snapshot guarded by its own mutex, refreshed only in `Init` and in `execution.go`'s block-processing hook [3](#0-2) . The kaia network already supports EIP-7702-style delegation (`TxTypeEthereumSetCode` / `SetCodeAuthorization`), which lets a plain EOA temporarily execute as a contract by attaching an authorization list [4](#0-3) , and the gasless test suite explicitly demonstrates that after a `SetCodeTx` the sender is treated as "has code" and gasless swap admission is rejected [5](#0-4) .

Because `getCurrentHasCode` reads a periodically-refreshed snapshot rather than the state as of the specific block/tx being validated, a delegated (code-bearing) account can bypass the "sender with code is not allowed" check for a window between blocks/refreshes, i.e., after a `SetCodeTx` is included but before `g.currentState` is updated to reflect it. This mirrors the reported class of bug: an EOA-verification mechanism that is not atomic with the actual EVM execution context becomes unreliable in the presence of account-delegation features (EIP-3074/EIP-7702), exactly the concern raised in the report.

### Impact Explanation
If the sender-code check can be bypassed via timing around delegation, a contract-controlled account (via `SetCodeTx` delegation) could be admitted into the gasless flow that `BalanceCheckLevelAll` was specifically designed to exclude. Since gasless transactions are funded up-front by the block proposer (`LendTxGenerator`) and repaid via the `GaslessSwapRouter` [6](#0-5) , admitting non-EOA/contract-controlled senders undermines the anti-abuse assumption the check enforces, potentially enabling contract-driven manipulation (e.g., atomic multi-step exploitation of the lend/repay settlement) of the gasless subsidy that the check was meant to prevent.

### Likelihood Explanation
Exploitation requires precise timing between submission of a `SetCodeTx` and the internal refresh cadence of `g.currentState`, which is refresh-on-block-boundary rather than per-validation. This is a narrower window than the fully worked out flash-loan sandwich in the original report, and I was not able to fully confirm the exact refresh trigger points in `execution.go` within the scope of this review (tool budget exhausted before inspecting that file's contents), so the precision of the exploitable window is not fully verified.

### Recommendation
Perform the sender-code check against the exact state used for the rest of the pool's validation (i.e., `pool.currentState` passed through at call time) rather than a separately cached/refreshed `g.currentState`, and ensure it is re-evaluated at promotion time (`IsReady`) as well as admission time, so that a delegation applied in an intervening block cannot slip through a stale-snapshot window. Confirm and document exactly when `g.currentState` is refreshed relative to the tx pool's own state resets in `execution.go`.

### Proof of Concept
Not independently reproduced; based on static analysis of `getCurrentHasCode`'s separate/cached state versus `TxTypeEthereumSetCode` execution and the existing test `tests/gasless_test.go` lines 264-267, which relies on the state having already been refreshed after the `SetCodeTx`'s receipt is confirmed before the swap tx is submitted [5](#0-4) . Full confirmation of the exploitable timing window would require inspecting `kaiax/gasless/impl/execution.go`'s state-refresh trigger, which I was unable to complete due to iteration limits.

func (g *GaslessModule) setCurrentState(state *state.StateDB) {

	defer g.currentStateMu.Unlock()

func (g *GaslessModule) getCurrentStateNonce(addr common.Address) uint64 {
	g.currentStateMu.Lock()
	defer g.currentStateMu.Unlock()

}

func (g *GaslessModule) getCurrentStateBalance(addr common.Address) *big.Int {
	g.currentStateMu.Lock()
	defer g.currentStateMu.Unlock()

	return g.currentState.GetBalance(addr)
}

func (g *GaslessModule) getCurrentHasCode(addr common.Address) bool {
	g.currentStateMu.Lock()
	defer g.currentStateMu.Unlock()

	return g.currentState.GetCodeHash(addr) != types.EmptyCodeHash
}
