### Title
Unauthorized minting of native bank coins via self-verifying `BalanceOf` check on attacker-controlled native ERC20 - (File: `x/erc20/keeper/evm.go`, `x/erc20/keeper/msg_server.go`)

### Summary
`BalanceOf` blindly trusts the EVM call result from the *same* ERC20 contract being converted, and `convertERC20IntoCoinsForNativeToken` / `ConvertCoinNativeERC20` use `BalanceOf` on that same contract as their sole "invariant" check that a real token transfer occurred before minting/burning bank coins.

### Finding Description
`BalanceOf` performs a `staticcall`-style `CallEVM` to the contract's own `balanceOf` and returns whatever it unpacks, without any independent verification: [2](#0-1) .

`convertERC20IntoCoinsForNativeToken` (reached via `MsgConvertERC20`) reads `balanceToken` before the transfer, executes `transfer(ModuleAddress, amount)` on the (potentially attacker-authored) contract, checks the boolean return / `Transfer` event, then re-reads `balanceTokenAfter` via `BalanceOf` on the *same* contract and compares it to the expected delta before minting bank coins and sending them to the receiver: [3](#0-2) .

Because `RegisterERC20` is permissionless and accepts arbitrary bytecode as a native ERC20 pair (`OWNER_EXTERNAL`) with only cosmetic metadata checks [1](#0-0) , an attacker can deploy a contract whose `transfer()` always returns `true` (or emits a synthetic `Transfer` event) without moving any real value, and whose `balanceOf()` independently returns a value engineered to equal `balanceToken + tokens` (e.g., an internal counter incremented on every `transfer()` call, decoupled from actual balances). Since both the "before" and "after" checks call into the *same* contract the attacker controls, the "invariant" check in `convertERC20IntoCoinsForNativeToken` can never actually detect a fake deposit — it verifies the contract's self-reported state against itself, not against any ledger the module controls. The keeper then unconditionally mints real bank coins (`k.bankKeeper.MintCoins`) and sends them to the receiver, backed by nothing.

The same self-verification pattern exists symmetrically in `ConvertCoinNativeERC20` for the escrow/unescrow direction [4](#0-3) .

### Impact Explanation
An attacker can mint unlimited real, freely transferable native bank coins for a denom backed by zero actual ERC20 collateral, by repeatedly calling `MsgConvertERC20` against their own malicious contract. These coins can then be used elsewhere in the chain (transfers, IBC out, staking, DeFi), constituting unauthorized minting / creation of spendable value out of thin air — a Critical impact under the allowed-impact gate ("Critical unauthorized minting... of spendable user value across native balances").

### Likelihood Explanation
High for an attacker willing to deploy their own malicious ERC20 and register it (permissionless, subject to a governance-settable flag `PermissionlessRegistration`). No privileged role, validator, or admin access is required — only ordinary `MsgRegisterERC20` and `MsgConvertERC20` transactions.

Caveat: if `params.PermissionlessRegistration` is disabled by governance, this specific path requires an admin to register the malicious contract, reducing likelihood to governance-gated. It is unclear from the reviewed code whether this flag defaults to enabled in production genesis — that would need to be checked against the actual chain configuration.

### Recommendation
Do not rely solely on the token contract's own `balanceOf` as authoritative proof of a completed transfer for security-critical minting/burning decisions when the contract is untrusted (native/external ERC20 pairs). Consider: requiring `transferFrom`-style patterns with pre-approved allowances verified independently, tracking escrowed balances via the module's own bookkeeping rather than re-querying the same contract, or restricting native ERC20 registration/minting-enabling to a governance-vetted allowlist so untrusted bytecode cannot enter the minting path.

### Proof of Concept
1. Attacker deploys `EvilToken` implementing ERC20 interface where `transfer(to, amount)` always returns `true` without modifying any real balance mapping, and `balanceOf(addr)` returns a value from an internal counter that the attacker increments by `amount` on every `transfer()` call regardless of `to`.
2. Attacker submits `MsgRegisterERC20` for `EvilToken` (assuming permissionless registration enabled), creating a token pair and denom.
3. Attacker submits `MsgConvertERC20{Amount: X, ContractAddress: EvilToken, Sender: attacker, Receiver: attacker}`.
4. `convertERC20IntoCoinsForNativeToken` reads `balanceToken` (from `EvilToken.balanceOf(ModuleAddress)`), calls `EvilToken.transfer(ModuleAddress, X)` (returns `true`, moves nothing), reads `balanceTokenAfter` (attacker's contract returns `balanceToken + X` from its internal counter), the invariant check passes.
5. Module mints `X` native coins and sends them to attacker's receiver address — real spendable value created with zero real ERC20 backing.
6. Repeat step 3 to mint arbitrary additional amounts.

func (k Keeper) BalanceOf(
	ctx sdk.Context,
	abi abi.ABI,
	contract, account common.Address,
) *big.Int {
	res, err := k.evmKeeper.CallEVM(ctx, abi, types.ModuleAddress, contract, false, nil, "balanceOf", account)
	if err != nil {
		return nil
	}

	unpacked, err := abi.Unpack("balanceOf", res.Ret)
	if err != nil || len(unpacked) == 0 {
		return nil
	}

	balance, ok := unpacked[0].(*big.Int)
	if !ok {
		return nil
	}

	return balance
}

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}
