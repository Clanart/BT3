### Title
Missing-direction decimal scaling in `pallet-hyper-fungible-token` allows wrong-amount mint/unlock across the bridge - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_erc20` and `convert_to_balance` in `pallet-hyper-fungible-token` assume the EVM-side token always has **equal or more** decimals than the local Substrate asset. They compute the scale factor with `erc_decimals.saturating_sub(local_decimals)` and never handle the opposite case (`local_decimals > erc_decimals`). When that happens, `saturating_sub` silently returns `0`, the scale factor becomes `10^0 = 1`, and the raw balance is forwarded/interpreted **unscaled** instead of being divided down — exactly the same asymmetric-decimal assumption bug class as the referenced Uniswap/Chainlink `_checkUniswapRateDifference` report, but here it corrupts the actual bridged amount rather than just a rate comparison.

### Finding Description [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both helpers only handle `erc_decimals >= local_decimals` (scaling up on the outbound leg, scaling down on the inbound leg). There is no `else` branch for `local_decimals > erc_decimals`. `saturating_sub` clamps negative differences to `0`, so the multiplier/divisor becomes `1` — the amount is passed through completely **unscaled** instead of being divided by `10^(local_decimals - erc_decimals)`.

These helpers are used on both directions of `send()` and `on_accept()`: [2](#0-1) 
- outbound: `let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);` (raw local `amount` → ERC20 units placed in the cross-chain `Message.amount`) [3](#0-2) 
- inbound: `let amount = convert_to_balance::<...>(U256::from_big_endian(&message.amount.to_be_bytes::<32>()), erc_decimals, decimals)...` (incoming ERC20 `message.amount` → local balance that gets minted/transferred to the beneficiary)

`local_decimals` for non-native assets comes directly from `fungibles::metadata::Inspect::decimals` (or `T::Decimals::get()` for the native asset), and `erc_decimals` comes from the governance-configured `Precisions` map (per `(asset_id, StateMachine)`), as documented: [4](#0-3) 

There is no on-chain assertion or documentation guarantee that `erc_decimals >= local_decimals` for every registered `(asset, chain)` pair — this is exactly the same unstated cross-precision assumption flagged in the original report (which named USDC/WBTC/DAI/ETH-style decimal mismatches as the trigger). Any asset registered locally with a higher precision than its EVM counterpart (e.g., a locally-created 18-decimal asset bridged to a chain where the paired ERC20 uses 6 decimals) hits this bug on every `send`/`on_accept`/`on_timeout` call.

### Impact Explanation
Once such an asset pair exists, the scaling is off by a factor of `10^(local_decimals - erc_decimals)`:
- Outbound (`send`): a user's small raw local balance (already in the asset's smallest unit, e.g. `1_000_000_000_000_000_000` for "1 token" at 18 decimals) is embedded **unscaled** into `Message.amount` that the destination EVM `HyperFungibleToken` contract will mint/unlock. The destination interprets that raw number as the token's *own* base units (6 decimals), so it releases/mints an amount up to `10^12` times larger than what was actually escrowed — a direct, unbounded fund-creation/drain vector against the destination custody pool, reachable by any ordinary signed account via the public `send` extrinsic.
- Inbound (`on_accept`)/timeout refund: an incoming ERC20 amount (small in 6-decimal ERC20 units) is credited to the beneficiary/refunded sender as if it were already in the local 18-decimal unit, again minting/crediting far more than was locked on the source side.

This matches the bounty's "stealing or loss of funds", "transaction manipulation" and "false state acceptance" categories: cross-chain messages carry a corrupted amount that the destination chain trusts and executes without any additional check, moving funds to the wrong amount.

### Likelihood Explanation
Exploitation requires no malicious relayer, prover, or admin — a normal governance-configured token pair combined with an ordinary user transaction is sufficient. The only precondition is that some registered `(asset_id, destination_chain)` pair has `local_decimals > erc_decimals`, which is a realistic configuration mistake (the same class of mistake — assuming decimal parity across chains/tokens — that the original H01 report demonstrates is common with real-world tokens like USDC/DAI). The code gives operators zero protection against configuring such a pair, and there is no runtime invariant check (`ensure!(erc_decimals >= local_decimals)`) anywhere in `register_token`/`update_token` based on what is visible in the indexed code.

### Recommendation
Make `convert_to_erc20`/`convert_to_balance` symmetric, mirroring the correct pattern already used elsewhere in the codebase (e.g. `VWAPOracle._normalizeAmount` and the SDK's `adjustDecimals`, both of which branch on which side has more decimals):
```rust
pub fn convert_to_balance<B: FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Additionally, add a defense-in-depth check in `register_token`/`update_token` (and/or `on_accept`) that rejects/flags any configured precision pair, so a misconfiguration cannot silently degrade into unscaled 1:1 conversion.

### Proof of Concept
1. Governance registers a local asset `X` with `local_decimals = 18` (e.g., via `fungibles` metadata) and configures `Precisions::<T>::insert(X, EVM-dest, 6)` (i.e., the paired ERC20 on the destination uses 6 decimals) — a plausible real-world config given real tokens differ this way.
2. A user calls `send()` with `amount = 1_000_000` (i.e., `0.000000000000001` token in 18-decimal terms, or any small raw balance) for asset `X` to `EVM-dest`.
3. `erc_decimals.saturating_sub(local_decimals)` = `6u8.saturating_sub(18u8)` = `0`, so `convert_to_erc20` returns `value * 10^0 = 1_000_000` unchanged, instead of the correct `1_000_000 / 10^12 = 0` (rounded).
4. The outbound `Message.amount` embeds `1_000_000` raw units, which the destination EVM `HyperFungibleToken` contract (interpreting it in its native 6-decimal denomination) mints/unlocks as `1_000_000` units = `1.0` full token — vastly more value than the negligible amount actually escrowed on the Substrate side, with no relayer/prover collusion needed.
