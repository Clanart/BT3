### Title
Silent auto-rewrite of `origin` remote URL from GitHub API data can redirect an in-flight push to an attacker-controlled destination - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Solidity report's broken invariant is: a privileged actor can change a critical address (`vusd`) that a pending user operation (`deposit`/`withdraw`) implicitly depends on, and the operation completes using the *new* address while the user believed it was interacting with the *old* one, causing silent loss. The Desktop analog is `updateRemoteUrl()`, which lets the GitHub API's `clone_url` for a tracked repository silently overwrite the local `origin` remote via `gitStore.setRemoteURL()` whenever Desktop refreshes GitHub metadata, with no user confirmation.

### Finding Description
`updateRemoteUrl` compares the currently configured remote URL to the previously known `gitHubRepository.cloneURL` and, if the API now reports a different `clone_url` for the same tracked repository (owner/name changed, or the repo was renamed/transferred) and protocols still match, it calls `gitStore.setRemoteURL(...)` to rewrite `origin` on disk automatically: [1](#0-0) 

This is invoked from `repositoryWithRefreshedGitHubRepository`, a routine background-refresh path that re-fetches the associated GitHub repository and rewrites the remote whenever the app matches the tracked repo and gets an updated API record: [2](#0-1) 

Meanwhile, `performPush` reads the remote's URL from the `RepositoryStateCache` *once*, up front, to build the authentication/proxy environment (`envForRemoteOperation(remote.url)`), while the actual `git push` subprocess is invoked with only `remote.name`, meaning it resolves the destination URL from the on-disk git config *at execution time*. The code even contains an explicit acknowledgment that these two data sources ("remote.name" vs the cached remote object) are not guaranteed to be updated atomically together: [3](#0-2) 

If a background refresh rewrites `origin` (via `updateRemoteUrl`/`setRemoteURL`) in the window between when `performPush` captures `remote.url` for the auth/proxy environment and when the actual `git push origin` command executes and resolves `origin` from disk, the push targets a different destination host/repo than the one the user's session was authenticated/proxy-configured for. Because `IRegistry`-style dependency in `InsuranceFund` is exactly this: an admin-mutable pointer consumed by in-flight user operations, `origin`'s URL here plays the same role — a mutable dependency the running `push`/`fetch` implicitly trusts to stay constant.

### Impact Explanation
This matches the "silent corruption of what the user commits or pushes" impact category explicitly listed as valid. A user who initiates a push believing it is going to `owner/repo` could have their commits silently pushed to a different remote location without any prompt, warning, or diff-review step, if the tracked GitHub repository's `clone_url` changes (rename/transfer, which can be triggered by any collaborator/owner with admin rights on the *remote* repo, not the local Desktop app) at the moment of push. Because `setRemoteURL` mutates the actual git config with no confirmation UI, and pushes proceed automatically, code intended for one destination can be committed to a different, possibly less-trusted repository, with the user only discovering the divergence after the fact — analogous to Alice's `VUSD` being silently redirected to `VUSDv2`.

### Likelihood Explanation
This requires no local/physical access, no malware, and no leaked credentials — it only requires that the GitHub repository object backing the local clone (name/owner reported by the GitHub API) changes while Desktop's background refresh and a push are both active, which is squarely within the "attacker controls a...GitHub API object" impact category. However, the actual race window (between `remote.url` being read into `envForRemoteOperation` and the `git push` subprocess resolving `origin` from disk) is narrow and the codebase's own `safeRemote`/non-fatal-exception guard in `performPush` shows the team is already aware this class of drift can occur, though it currently only guards the `remote.name` vs `branch.upstreamRemoteName` mismatch, not a URL rewrite mid-flight by `updateRemoteUrl`. This makes it a real, but timing-dependent (moderate likelihood) path rather than a guaranteed one.

### Recommendation
- Do not silently rewrite `origin` via `setRemoteURL` from a background refresh; require explicit user confirmation before changing the configured remote URL for a repository that has any in-flight operations (push/pull/fetch) or unpushed commits.
- Serialize `updateRemoteUrl` with any active `performPush`/`performFailableOperation` calls on the same repository (e.g., via the existing `withPushPullFetch` lock) so remote URL mutation cannot occur mid-operation.
- Resolve the remote URL used to build `envForRemoteOperation` and the URL actually used by the `git push`/`git fetch` subprocess from the same atomic read, rather than reading `remote.url` from a possibly-stale cache and `remote.name` for git subcommand args separately.

### Proof of Concept
1. Alice tracks a local clone of `origin` pointing to `github.com/owner/repo`, which Desktop associates with `gitHubRepository` (endpoint + id).
2. The repo owner renames/transfers the repository on GitHub (changing its `clone_url` while keeping the same underlying id that Desktop tracks).
3. Alice's Desktop periodically calls `repositoryWithRefreshedGitHubRepository`, which fetches the updated `apiRepo` and invokes `updateRemoteUrl`, silently calling `setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)` — see [4](#0-3) .
4. If this refresh lands in the small window while Alice's `performPush` has already resolved `envForRemoteOperation(remote.url)` from the old cached remote but the `git push origin ...` subprocess has not yet run, the push executes against the newly-rewritten `origin` URL, silently sending Alice's commits to the renamed/transferred destination instead of the one she intended, with no confirmation dialog shown to her.

**Confidence note:** I was unable to fully trace every caller and exact scheduling/timing of `repositoryWithRefreshedGitHubRepository` (e.g., whether it's triggered on a fixed interval, repository selection, or both) due to reaching the tool-call budget; a Devin session with full repo access would be needed to confirm the exact refresh trigger and precisely measure the race window against `performPush`.

```typescript
  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }
```
