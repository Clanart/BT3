### Title
Single-step, irreversible `ChangeAdmin` in the tokenfactory module can permanently freeze mint/burn authority over a denom - (File: `x/tokenfactory/keeper/msg_server.go`)

### Summary
The tokenfactory module's `MsgChangeAdmin` handler transfers denom admin authority to a new address in a single atomic step, with no two-step "propose/accept" mechanism. Any tokenfactory denom creator (an unprivileged account) is granted admin rights over their own `factory/{creator}/{subdenom}` denom, and can call `ChangeAdmin` to reassign that authority. If the new admin address is mistyped or otherwise unreachable (e.g., no known private key), the change is final and unrecoverable, permanently locking mint/burn/`SetDenomMetadata`/further `ChangeAdmin` calls for that denom.

### Finding Description
`ChangeAdmin` is implemented as a single-step transfer: it validates that `msg.Sender` matches the current `AuthorityMetadata.Admin`, then immediately overwrites the admin with `msg.NewAdmin` with no confirmation step from the new admin. [1](#0-0) 

The module explicitly documents that `ChangeAdmin` can even set the admin to an empty string, permanently disabling admin-gated actions for the denom, and that this is the only mechanism to reassign or revoke admin control. [2](#0-1) 

`ValidateBasic` for `MsgChangeAdmin` only checks that `NewAdmin` parses as a valid bech32 address - it does not, and cannot, check that the address is a "real"/reachable account with a known private key. [3](#0-2) 

Any account can become a denom admin unprivileged, simply by calling `CreateDenom`, which sets the admin to the creator by default. [4](#0-3) 

Because `AuthorityMetadata` is a single-value pointer to an admin bech32 string, mistakenly transferring to an unowned/typo'd address makes the mint/burn/change-admin capability for that denom permanently unreachable, since there is no pending/candidate admin state or acceptance step to recover from a bad input (unlike, e.g., the CosmWasm `wasm` module's contract admin, which suffers the same single-step design but is at least gated behind gov proposals for privileged contracts - here tokenfactory admin transfer is fully permissionless and self-service). [5](#0-4) 

### Impact Explanation
A tokenfactory denom's admin controls minting, burning, and metadata for that denom, all gated by an admin equality check. [6](#0-5) 
If a user (or automated tooling/bot managing many denoms) mistypes the `new-admin` address in a single `ChangeAdmin` transaction, all further supply-management capability for that denom is permanently and irrecoverably frozen with no on-chain recovery path - this matches the "permanent freezing" impact class, since minting/burning authority over the affected denom's supply becomes permanently inaccessible.

### Likelihood Explanation
`ChangeAdmin` is a normal, permissionless, single-signer transaction available to any tokenfactory denom admin; the only precondition for triggering the bug is human/tooling error supplying an incorrect `new_admin` argument, which is a common class of address-input mistake (copy-paste error, wrong network prefix, etc.) and requires no cooperation from any third party once submitted.

### Recommendation
Implement a two-step admin transfer for tokenfactory denoms: `ChangeAdmin` should set a `pending_admin` field rather than overwriting `admin` directly, and require a new `MsgAcceptAdmin` (or similar) transaction signed by the pending admin to finalize the transfer. This allows the current admin to re-propose a corrected address if a mistake is made before the transfer is finalized, mirroring the standard "propose-and-accept" ownership pattern recommended for `Ownable`-style contracts.

### Proof of Concept
1. Account A calls `MsgCreateDenom` to create `factory/A/mydenom`; A becomes the denom's sole admin. [7](#0-6) 
2. A calls `MsgChangeAdmin{Sender: A, Denom: "factory/A/mydenom", NewAdmin: <mistyped/unowned address>}`. The handler validates only that A is the current admin and that the new address differs from the current one, then unconditionally overwrites the admin. [8](#0-7) 
3. Because nobody controls the private key for the mistyped address, no further `MsgMint`, `MsgBurn`, `MsgSetDenomMetadata`, or `MsgChangeAdmin` transactions can ever be authorized for `factory/A/mydenom` again - confirmed by the test showing that after `ChangeAdmin`, the old admin immediately loses all authority (`suite.Require().Error(err)` on `Burn` from the old admin). [9](#0-8)

func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}
