Confirmed: `verify_storage_proofs` (circuits-lib/src/bridge_circuit/storage_proof.rs:44-133) only extracts and verifies the withdrawal outpoint's `txid`/`vout` and the deposit's `move_txid` from Citrea's storage trie — it never touches `output_script_pubkey` or `output_amount`. The withdrawer's payout script/amount that they submitted to Citrea's `withdraw()` (`WithdrawParams.output_script_pubkey`, `output_amount`) is not part of `StorageProof` or `BridgeCircuitInput` at all, and `bridge_circuit` never reads `input.payout_spv.transaction.output`. [1](#0-0) [2](#0-1) 

Critically, the "withdrawal UTXO" (`input_outpoint`) is a UTXO **owned by the withdrawer themselves**, verified via `try_get_taproot_pk()` on its own script and a Schnorr signature check against the withdrawer's own key [3](#0-2) . Since the withdrawer holds the private key for this UTXO, they can spend it in any unrelated on-chain transaction using a completely independent signature — Bitcoin consensus does not enforce that the specific `SinglePlusAnyoneCanPay` withdrawal-authorization signature is the *only* signature ever produced for that key. The bridge circuit's only binding check is `previous_output.txid/vout == user_wd_outpoint` [4](#0-3) , with no signature-scheme check, no `output_script_pubkey` check, and no `output_amount` check against what was registered as `WithdrawParams` on Citrea.

### Title
Bridge circuit accepts any transaction spending the withdrawal outpoint as proof of payout, without verifying it pays the withdrawer - (File: circuits-lib/src/bridge_circuit/mod.rs)

### Summary
`bridge_circuit` verifies only that `payout_spv.transaction.input[payout_input_index].previous_output` matches the withdrawal outpoint (`user_wd_outpoint`, `vout`) taken from Citrea storage proofs; it never inspects `payout_spv.transaction.output` to confirm a payment to the withdrawer's registered `output_script_pubkey`/`output_amount`. Since the withdrawal outpoint is a UTXO owned and controlled by the withdrawer's own key (not a bridge-controlled vault UTXO), any confirmed transaction that happens to spend it — including one the withdrawer creates for an unrelated purpose — satisfies this check, letting an operator fabricate a valid `journal_hash` for a withdrawal it never funded.

### Finding Description
The broken binding: `payout_fronted_to_withdrawer_by_operator == bridge_amount_recorded_by_citrea_withdraw` is never checked. Instead the only equality enforced is `payout_spv.transaction.input[payout_input_index].previous_output == (user_wd_outpoint, vout)` [5](#0-4) .

The withdrawal outpoint originates from the withdrawer's own on-chain UTXO, provided as `WithdrawParams.input_outpoint` and authorized with the withdrawer's own `SinglePlusAnyoneCanPay` signature over a specific `output_script_pubkey`/`output_amount` [6](#0-5) . The operator's `withdraw()` handler fetches this UTXO from the withdrawer's own key (`try_get_taproot_pk`) and verifies the Schnorr signature against a transaction template it builds locally [3](#0-2) . But this signature check happens only off-circuit, at RPC-acceptance time, to decide whether the operator's mempool node will *fund and broadcast* that specific tx. Nothing forces the operator to actually use that transaction as the `payout_spv` input to the zkVM circuit — since the withdrawer controls the private key for that UTXO, any other confirmed spend of the same outpoint (e.g., the withdrawer later consolidating or moving that UTXO for unrelated reasons, using an ordinary signature not bound to the payout output) is equally valid Bitcoin history and equally satisfies the circuit's `previous_output` equality check.

`verify_storage_proofs` (storage_proof.rs:44-133) confirms the withdrawal outpoint's txid/vout and the deposit's `move_txid` against Citrea state, but the `StorageProof` struct carries no `output_script_pubkey`/`output_amount` fields at all [7](#0-6) , so there is no on-chain data path by which the circuit could ever learn or check what the withdrawer was supposed to be paid. `deposit_constant`/`journal_hash` computation likewise never reference the payout's outputs, only the first OP_RETURN carrying the operator's pubkey [8](#0-7) .

Exploit flow: (1) withdrawer registers a withdrawal on Citrea with `input_outpoint` = some UTXO they own; (2) that UTXO is later spent in any transaction — honestly by the withdrawer for unrelated purposes, or maliciously — that confirms on Bitcoin; (3) an operator (who never actually fronted the payout) supplies that confirmed transaction as `payout_spv`, sets `payout_input_index` to the input spending `user_wd_outpoint`, and constructs an OP_RETURN-bearing transaction of its choosing (it must control at minimum a self-authored fictitious `payout_spv.transaction` with a valid OP_RETURN output containing its own xonly pubkey, but that transaction only needs to spend `user_wd_outpoint` as one input — no output paying the withdrawer is required); (4) `bridge_circuit` runs to completion and calls `guest.commit(journal_hash)` — none of `total_work_and_watchtower_flags`, `SPV::verify`, `lc_proof_verifier`, or `verify_storage_proofs` catch this because none of them examine `payout_spv.transaction.output`. This journal then flows unmodified through Assert → ChallengeTimeout (watchtowers only check total work/challenge signatures, not payment correctness, per the module's own doc comment) → Reimburse, since the Disprove path re-derives the same journal from the same unconstrained input and would find no discrepancy.

### Impact Explanation
An operator can be reimbursed via the kickoff/Assert/Reimburse flow for a peg-out it never funded, while the vault BTC still leaves via the Reimburse transaction — this is the Critical category "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." The blast radius is every deposit/withdrawal pair processed by any operator, repeatable across every withdrawal where the registered outpoint is ever spent by any transaction (the withdrawer need not cooperate maliciously — an honest, unrelated spend of their own dust/UTXO management is sufficient).

### Likelihood Explanation
Preconditions are modest: a withdrawal must be registered on Citrea (any user can create one), and the specific `input_outpoint` UTXO must eventually be spent in some confirmed Bitcoin transaction — which happens by definition whenever the withdrawer moves their own funds, even for reasons unrelated to the bridge. The operator needs no special access beyond normal operator capability (already assumed, since the operator is the one submitting the circuit input) to submit a `payout_spv` and drive it through Assert/ChallengeTimeout. The cost is essentially the mining fee for a fabricated OP_RETURN-carrying transaction (which the operator could self-construct or reuse an existing confirmed transaction if it coincidentally has an OP_RETURN) and standard kickoff/assert transaction fees — no watchtower or verifier control catches the missing payment.

### Recommendation
Add an explicit check in `bridge_circuit` (circuits-lib/src/bridge_circuit/mod.rs) that iterates `input.payout_spv.transaction.output` and asserts at least one output pays `output_script_pubkey` (or a committed hash of it) with `value >= output_amount`, where both values must be committed on-chain via Citrea storage proofs (extend `StorageProof`/contract storage layout to include them) so the circuit can bind the payout transaction's actual outputs to the amount/script the withdrawer registered when calling `withdraw()`.

### Proof of Concept
Add a `cargo test` in `circuits-lib/src/bridge_circuit/mod.rs` (or a new integration test under `circuits-lib/tests/`) that:
1. Builds a `BridgeCircuitInput` using the existing `storage_proof.bin` test fixture (which already yields a known `user_wd_outpoint`/`vout`) from `circuits-lib/src/bridge_circuit/storage_proof.rs` tests.
2. Constructs a `payout_spv.transaction` whose `input[payout_input_index].previous_output` equals `(user_wd_outpoint, vout)` but whose `output` vec contains **zero** outputs paying any withdrawer-controlled script (only an OP_RETURN with the operator's xonly pubkey, to satisfy `get_first_op_return_output`).
3. Supplies matching HCP/LCP/SPV proof material (or stub `ZkvmGuest`) so all preceding checks in `bridge_circuit` pass.
4. Calls `bridge_circuit(&guest, work_only_image_id)` and asserts it does **not** panic and calls `guest.commit(journal_hash)` — demonstrating the binding `payout_fronted_to_withdrawer_by_operator == bridge_amount_recorded_by_citrea_withdraw` is never checked on either side.

pub fn verify_storage_proofs(
    storage_proof: &StorageProof,
    state_root: [u8; 32],
) -> (WithdrawalOutpointTxid, u32, MoveTxid) {
    let utxo_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_utxo)
            .expect("Failed to deserialize UTXO storage proof");

    let vout_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_vout)
            .expect("Failed to deserialize vout storage proof");

    let deposit_storage_proof: EIP1186StorageProof =
        serde_json::from_str(&storage_proof.storage_proof_deposit_txid)
            .expect("Failed to deserialize deposit storage proof");

    let storage_address: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(UTXOS_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let storage_key_utxo: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2);

    let storage_key_vout: alloy_primitives::Uint<256, 4> =
        storage_address + U256::from(storage_proof.index * 2 + 1);

    let storage_address_deposit: U256 = {
        let mut keccak = Keccak256::new();
        keccak.update(DEPOSIT_STORAGE_INDEX);
        let hash = keccak.finalize();
        U256::from_be_bytes(
            <[u8; 32]>::try_from(&hash[..]).expect("Hash slice has incorrect length"),
        )
    };

    let deposit_storage_key: alloy_primitives::Uint<256, 4> =
        storage_address_deposit + U256::from(storage_proof.index);

    let deposit_storage_key_bytes = deposit_storage_key.to_be_bytes::<32>();

    if deposit_storage_key_bytes != deposit_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid deposit storage key. left: {:?} right: {:?}",
            deposit_storage_key_bytes,
            deposit_storage_proof.key.as_b256().0
        );
    }

    if storage_key_utxo.to_be_bytes() != utxo_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal UTXO storage key. left: {:?} right: {:?}",
            storage_key_utxo.to_be_bytes::<32>(),
            utxo_storage_proof.key.as_b256().0
        );
    }

    if storage_key_vout.to_be_bytes() != vout_storage_proof.key.as_b256().0 {
        panic!(
            "Invalid withdrawal vout storage key. left: {:?} right: {:?}",
            storage_key_vout.to_be_bytes::<32>(),
            vout_storage_proof.key.as_b256().0
        );
    }

    storage_verify(&utxo_storage_proof, state_root);

    storage_verify(&deposit_storage_proof, state_root);

    storage_verify(&vout_storage_proof, state_root);

    let buf: [u8; 32] = vout_storage_proof.value.to_be_bytes();

    // ENDIANNESS SHOULD BE CHECKED THIS FIELD IS 4 BYTES in the contract
    let vout = u32::from_le_bytes(
        buf[28..32]
            .try_into()
            .expect("Vout value conversion failed"),
    );

    let wd_outpoint = WithdrawalOutpointTxid(utxo_storage_proof.value.to_be_bytes());

    let move_txid = MoveTxid(deposit_storage_proof.value.to_be_bytes());

    (wd_outpoint, vout, move_txid)
}
