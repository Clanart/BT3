### Title
Silent data loss when Trash fails for modified (tracked) files during Discard Changes - ([File: app/src/lib/stores/git-store.ts])

### Summary
`GitStore.discardChanges` mirrors the reported bug-class: a critical side effect (moving a file's local changes to the OS Trash) can silently fail without stopping the destructive operation that depends on it (overwriting the working directory from the index via `checkoutIndex`). This is the same "unchecked/mis-handled failure of a value-preserving step followed by an irreversible action" pattern as the `transferFrom` report, translated to Desktop's discard-changes flow.

### Finding Description
In `discardChanges`, for every file that is not `Deleted` and not a submodule, Desktop attempts to preserve the user's local edits by moving the file to Trash before later overwriting it: [1](#0-0) 

The failure handling only re-throws (aborting the whole operation) when `askForConfirmationOnDiscardChangesPermanently` is true, and only falls back to an explicit manual delete (`rm`) when the file's status is `Untracked`:

```
} catch (e) {
  if (askForConfirmationOnDiscardChangesPermanently) {
    throw new DiscardChangesError(e, this.repository, files)
  }
  if (file.status.kind === AppFileStatusKind.Untracked) {
    await rm(Path.join(this.repository.path, file.path))
  }
}
```

For a `Modified` (tracked) file, if `moveItemToTrash` throws and `askForConfirmationOnDiscardChangesPermanently` is `false`, the catch block does **nothing** — it neither re-throws, nor removes the file, nor logs, nor skips the subsequent overwrite. Execution simply falls through to the rest of `discardChanges`, which unconditionally proceeds to run `resetPaths` and `checkoutIndex` for that same path: [2](#0-1) 

`checkoutIndex` forcefully overwrites the working-directory file with the index/HEAD version: [3](#0-2) 

The net effect: the intended "safety net" (Trash) is bypassed silently, but the destructive overwrite still happens — exactly analogous to the reported pattern where a token-retrieval step's failure is not checked, yet the code proceeds as if it succeeded, causing the caller to lose value with no recourse. Here, the "value" is the user's uncommitted edits, and the "collateral withdrawn regardless" is the forced `checkout-index` overwrite.

### Impact Explanation
If the OS-level Trash operation fails for a modified/tracked file (e.g. `shell.trashItem` failures are a documented cross-platform pain point — reserved Windows device names such as `con`, `aux`, `nul`, overly long paths, paths containing characters some Trash providers reject, files on certain filesystems/mounts, or Trash service unavailable in some Linux/CI/sandboxed environments), Desktop will discard the user's uncommitted local modifications with no backup and no error surfaced to the user. This is silent, irrecoverable data loss of what the user was about to discard — a corruption of local state that the user did not consent to (they expected the changes to be recoverable via Trash, consistent with the documented behavior in `docs/technical/discard-changes.md`, which states Trash is used specifically "as a way to preserve changes, in case the user wishes to recover them later").

Because a malicious/crafted repository can legitimately contain filenames engineered to be problematic for OS trash APIs (e.g., committing a file literally named `con` or `nul` on a repo that will later be checked out on Windows, or extremely long paths that trip trash-move implementations on certain platforms), an attacker who controls repository content can increase the likelihood that Trash silently fails for a victim who later modifies and discards that exact file — turning an ordinary "Discard Changes" click into an unrecoverable loss of their edits.

### Likelihood Explanation
This requires: (1) `askForConfirmationOnDiscardChangesPermanently` to be `false` (the state controlling this flag exists in `app/src/lib/stores/app-store.ts`, `app/src/lib/app-state.ts`; confirmed present but its exact default value could not be fully verified within the available context/tool budget — this is the one uncertain fact in this analysis), and (2) `shell.moveItemToTrash` throwing for the affected path. Trash API failures are a realistically occurring class of platform bugs/limitations rather than a hypothetical, and filenames that reliably trigger such failures can be committed by a repository owner/attacker. No local/physical access, malware, or admin rights are needed — only that the victim opens a repository with a problematic filename, edits that file, and clicks "Discard Changes" (a fully in-app, expected user action).

### Recommendation
- Treat a failed `moveItemToTrash` for **any** tracked/modified file the same way `Untracked` failures with `askForConfirmationOnDiscardChangesPermanently=false` are treated: either abort the discard for that file (skip adding it to `pathsToCheckout`/`pathsToReset`) or explicitly warn/log and require user confirmation before overwriting.
- Never let a silent trash failure fall through to `checkoutIndex`/`resetPaths` for the same path — the check-and-act should be atomic: only proceed to overwrite a path if the trash step for that path succeeded (or the user explicitly opted out of the trash-then-overwrite safety net).
- Add telemetry/non-fatal logging whenever `moveItemToTrash` fails so silent failures are visible to the Desktop team.

### Proof of Concept
1. On a platform/filesystem where `shell.trashItem` is known to fail for a given path (e.g. a file named to collide with a Windows reserved device name, or a path exceeding trash-provider length limits, or a sandboxed Linux environment without a functioning trash daemon).
2. Clone/open a repository containing such a filename, modify the file's tracked content, ensure `askForConfirmationOnDiscardChangesPermanently` is `false` (default/first-time state before the user has ever hit the "trash failed" confirmation dialog).
3. In Desktop, select "Discard Changes" on that file.
4. `GitStore.discardChanges` calls `this.shell.moveItemToTrash(...)`, which throws; the catch block does nothing because the status kind is `Modified`, not `Untracked`, and confirmation is off.
5. Execution continues to `resetPaths`/`checkoutIndex`, which overwrites the file with the HEAD/index version.
6. Result: the user's edits are permanently gone — never placed in Trash, never confirmed with the user, and not recoverable through the app. [4](#0-3)

  public async discardChanges(
    files: ReadonlyArray<WorkingDirectoryFileChange>,
    moveToTrash: boolean = true,
    askForConfirmationOnDiscardChangesPermanently: boolean = false
  ): Promise<void> {
    const pathsToCheckout = new Array<string>()
    const pathsToReset = new Array<string>()

    const submodules = await listSubmodules(this.repository)

    for (const file of files) {
      const foundSubmodule = submodules.some(s => s.path === file.path)

      if (file.status.kind !== AppFileStatusKind.Deleted && !foundSubmodule) {
        if (moveToTrash) {
          try {
            await this.shell.moveItemToTrash(
              Path.resolve(this.repository.path, file.path)
            )
          } catch (e) {
            if (askForConfirmationOnDiscardChangesPermanently) {
              throw new DiscardChangesError(e, this.repository, files)
            }

            // The user has received the confirmation dialog in past and has
            // chosen to always discard the changes permanently if trash failes.
            // We need to remove the file manually.
            if (file.status.kind === AppFileStatusKind.Untracked) {
              await rm(Path.join(this.repository.path, file.path))
            }
          }
        } else if (moveToTrash === false) {
          // The user has received the confirmation dialog and has chosen to
          // discard the changes permanently. We need to remove the file
          // manually.
          if (file.status.kind === AppFileStatusKind.Untracked) {
            await rm(Path.join(this.repository.path, file.path))
          }
        }
      }

      if (
        file.status.kind === AppFileStatusKind.Copied ||
        file.status.kind === AppFileStatusKind.Renamed
      ) {
        // file.path is the "destination" or "new" file in a copy or rename.
        // we've already deleted it so all we need to do is make sure the
        // index forgets about it.
        pathsToReset.push(file.path)

        // checkout the old path too
        pathsToCheckout.push(file.status.oldPath)
        pathsToReset.push(file.status.oldPath)
      } else {
        pathsToCheckout.push(file.path)
        pathsToReset.push(file.path)
      }
    }

    // Check the index to see which files actually have changes there as compared to HEAD
    const changedFilesInIndex = await getIndexChanges(this.repository)

    // Only reset paths if they have changes in the index
    const necessaryPathsToReset = pathsToReset.filter(x =>
      changedFilesInIndex.has(x)
    )

    const submodulePaths = pathsToCheckout.filter(p =>
      submodules.find(s => s.path === p)
    )

    // Don't attempt to checkout files that are submodules or don't exist in the index after our reset
    const necessaryPathsToCheckout = pathsToCheckout.filter(
      x =>
        submodulePaths.indexOf(x) === -1 ||
        changedFilesInIndex.get(x) !== IndexStatus.Added
    )

    // We're trying to not invoke git linearly with the number of files to discard
    // so we're doing our discards in three conceptual steps.
    //
    // 1. Figure out what the index thinks has changed as compared to the previous
    //    commit. For users who exclusive interact with Git using Desktop this will
    //    almost always empty which, as it turns out, is great for us.
    //
    // 2. Figure out if any of the files that we've been asked to discard are changed
    //    in the index and if so, reset them such that the index is set up just as
    //    the previous commit for the paths we're discarding.
    //
    // 3. Checkout all the files that we've discarded that existed in the previous
    //    commit from the index.
    await this.performFailableOperation(async () => {
      if (submodulePaths.length > 0) {
        await resetSubmodulePaths(this.repository, submodulePaths)
      }

      await resetPaths(
        this.repository,
        GitResetMode.Mixed,
        'HEAD',
        necessaryPathsToReset
      )
      await checkoutIndex(this.repository, necessaryPathsToCheckout)
    })
  }

export async function checkoutIndex(
  repository: Repository,
  paths: ReadonlyArray<string>
) {
  if (!paths.length) {
    return
  }

  const options = {
    successExitCodes: new Set([0, 1]),
    stdin: paths.join('\0'),
  }

  await git(
    ['checkout-index', '-f', '-u', '-q', '--stdin', '-z'],
    repository.path,
    'checkoutIndex',
    options
  )
}
