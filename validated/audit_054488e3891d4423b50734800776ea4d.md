### Title
Unreachable/unregistered Participant index causes panic (DoS) via HashMap indexing in PedPoP decryption and encryption paths - ([File: crypto/dkg/pedpop/src/encryption.rs])

### Summary
Analogous to CVE-2015-8731 — where an unvalidated/unknown TLV type was not rejected and led to a crash — several PedPoP code paths consume attacker-chosen `Participant` indexes without verifying the index was previously registered, and then index a `HashMap` with `enc_keys[&participant]`, which panics on a missing key. An unprivileged counterparty who can send DKG/blame messages can crash the victim's DKG process.

### Finding Description
`Decryption<C>` keeps a `HashMap<Participant, C::G>` of registered encryption keys, populated by `register`, which itself `assert!`s on duplicate registration [1](#0-0) . Two reachable sink points then index this map by an unvalidated participant index:

- `decrypt_with_proof` uses `self.enc_keys[&decryptor]` when verifying the blame DLEq proof [2](#0-1) .
- `Encryption::encrypt` uses `self.decryption.enc_keys[&participant]` [3](#0-2) .

The untrusted inputs — `EncryptedMessage::read` / `EncryptionKeyMessage::read` / `EncryptionKeyProof::read` bytes and the caller-selected `from`/`decryptor`/`participant` indexes — are not checked for membership before indexing [4](#0-3) . `HashMap`'s `Index` impl panics when the key is absent, so a message referencing an index that never sent an `EncryptionKeyMessage`, or a second registration from an already-registered index (assert at lines 356-359), aborts the process instead of returning an `io::Error`/`DecryptionError`.

### Impact Explanation
A malicious DKG participant (unprivileged, supplying public protocol bytes) can trigger a guaranteed panic in the victim's PedPoP handling:

1. Send an `EncryptedMessage`/blame flow naming a `decryptor`/`participant` index that never registered an encryption key → `enc_keys[&participant]` panics.
2. Send a second `EncryptionKeyMessage` registration for the same index → the `assert!` in `register` panics.

This is a remote, unauthenticated denial of service on the DKG participant process — the same bug class as the CVE (unrejected/unvalidated tag/index leading to a crash), mapped onto Serai's real message flow. Severity: Medium.

### Likelihood Explanation
Any threshold participant can produce these messages; no collusion or special position is required. The indexes are free fields chosen per message, and no prior-validation layer exists inside the crate — the code explicitly delegates duplicate/malformed-message handling to the caller (`pedpop/src/lib.rs` docs note the library cannot detect faulty participants), so a library-level panic is reachable whenever the caller passes through the offending index, which is the documented usage pattern.

### Recommendation
Replace `HashMap` indexing and the `assert!` with checked lookups returning errors:

- In `register`, return an `io::Result`/`Result` and error on duplicate `participant` instead of `assert!`.
- In `decrypt_with_proof` and `encrypt`, use `enc_keys.get(&participant).ok_or(...)` to surface `DecryptionError`/an error for unregistered indexes rather than panicking.

### Proof of Concept
```rust
// Attacker participates in a PedPoP DKG round but never sends an
// EncryptionKeyMessage (or sends it only for some indexes).
// Then, during the blame/decryption path, the victim executes:

// crypto/dkg/pedpop/src/encryption.rs
// Decryption::decrypt_with_proof called with a `decryptor` Participant
// that was never inserted into `enc_keys`:
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key], // PANIC: index not in map
)

// Alternatively, the attacker sends a second EncryptionKeyMessage
// for their own index; `Decryption::register` hits:
//   assert!(!self.enc_keys.contains_key(&participant), ...); // PANIC
```

Both panics are reached purely by bytes/indexes the attacker supplies; no valid proof or secret knowledge is needed, since the panic occurs during lookup, before (in the `register` case entirely before) any proof verification would reject the message.

(One caveat I could not fully verify within scope: whether higher-level callers pre-filter duplicate registrations or unknown indexes. The library itself documents that it does not, and the panicking sites are in-scope production code reachable by untrusted input.)
