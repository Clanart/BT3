### Title
Dust cross-chain transfers to the `hyper-fungible-token` pallet are silently reduced to zero, burning source-chain funds with no destination mint - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
This is a direct on-chain analog of the Teleporter Token Bridge bug: an amount that is smaller than the destination chain's precision scale factor gets divided down to `0` during decimal conversion, but the source side has already irreversibly debited (burned/escrowed) the full amount. Unlike the Substrate→EVM direction of this pallet (which is provably safe because it only ever scales *up*), the EVM→Substrate direction relies on integer division that can truncate to zero, and `on_accept` never checks for this before declaring success.

### Finding Description
The `hyper-fungible-token` pallet enforces `config.decimals >= local_decimals` at registration time (`register_token`/`update_token` in [1](#0-0) , and again at [2](#0-1) ), so `erc_decimals` (EVM side) is always `>= local_decimals` (Substrate side).

This guarantees that `convert_to_erc20` (used when *sending* from Substrate to EVM) always multiplies by a non-negative power of ten and can never truncate a non-zero amount to zero: [3](#0-2) .

However, the reverse conversion, `convert_to_balance`, is a *division* by `10^(erc_decimals - local_decimals)`, and this is exactly where the same class of rounding-to-zero bug from the external report resurfaces: [4](#0-3) 

It is invoked by `on_accept`, which processes an EVM-originated `Send` message and mints/releases funds to the beneficiary based on the computed `amount`, with **no check that `amount > 0`**: [5](#0-4) 

On the EVM side, `HyperFungibleToken.sol` performs no equivalent decimal-awareness: it burns/locks the raw amount the user supplies (in the EVM contract's own decimals) and dispatches a Teleporter-style message carrying that raw `uint256 amount`, with the destination pallet solely responsible for converting it via `Precisions`. Symmetrically, `onAccept` on the EVM side simply trusts and mints the incoming `message.amount` verbatim with no scaling: [6](#0-5) 

Because the EVM contract debits the sender unconditionally before dispatch (this mirrors the pallet's own `send()` extrinsic, which also debits the full amount from the caller before computing the scaled ERC-20 amount: [7](#0-6) ), a Send message that is smaller than `10^(erc_decimals - local_decimals)` will:
1. Have already burned/locked funds on the EVM side.
2. Arrive at `on_accept`, compute `amount = 0` via integer division truncation.
3. Successfully mint/transfer `0` to the beneficiary and emit `TokenReceived { amount: 0, .. }` — the request is **not** a timeout, so `on_timeout`'s refund path never runs.

The result: funds are permanently destroyed on the EVM side with nothing credited on the Substrate side — the exact "loss of funds due to sub-minimum-denomination bridging" pattern described in the report, except here it manifests specifically in the EVM→Substrate leg because that is the only leg using division instead of multiplication.

### Impact Explanation
Any unprivileged user interacting with a legitimately configured token pair (e.g., a token registered with `erc_decimals = 18` on the EVM side and `local_decimals = 6` on the Substrate side — a completely valid, admin-approved and expected configuration given the `>= ` constraint) can lose funds by sending an amount below `10^12` wei-equivalent (or any dust amount below the destination's minimum representable unit). The loss is unrecoverable: there is no revert, no error path, and no compensating refund mechanism, since the cross-chain message is considered successfully delivered. This directly matches the bounty's "stealing or loss of funds" and "false state acceptance" (zero-value success treated as valid settlement) categories.

### Likelihood Explanation
This requires no malicious peer, relayer, or governance actor — only a normal, unprivileged sender using the standard `send`/teleport flow with a sufficiently small amount (which can happen accidentally via UI rounding/precision mistakes, or be deliberately triggered by an attacker targeting another user's dust-amount transfer, or simply an attacker probing the bridge to confirm/exploit the fund-destruction primitive). Given that decimal mismatches between EVM (commonly 18) and Substrate assets (commonly 6, 8, 10, or 12) are the normal case this pallet is explicitly designed to support (`Precisions` storage exists exactly for this purpose), the vulnerable configuration is not a corner case — it is the expected/common configuration.

### Recommendation
In `on_accept` (and `on_timeout`), after calling `convert_to_balance`, explicitly reject requests where the truncated `amount` is zero while the original `message.amount` (U256) was non-zero, e.g. `ensure!(!(message.amount != 0 && amount == 0), HftError::AmountBelowMinimumDenomination)`. This causes `on_accept` to return an `Err`, forcing hyperbridge/ISMP to treat the request as failed so that a subsequent timeout can trigger `on_timeout`'s refund path on the EVM side, exactly mirroring the "registration + collateral" style fix (PR #108/#124) referenced in the analogous report. Alternatively, expose the local pallet's decimal/precision requirement to the EVM contract so it can reject dust sends before burning, preventing the loss at the source.

### Proof of Concept
1. Admin registers asset `X` with `local_decimals = 6` on Substrate and `erc_decimals = 18` for `StateMachine::Evm(dest)`, satisfying `register_token`'s `config.decimals >= local_decimals` check.
2. A user on the EVM `HyperFungibleToken` contract for asset `X` calls the teleport/send function with `amount = 1` (raw units, 18-decimal token — i.e., `10^-18` of a token). The contract burns/locks `1` from the sender and dispatches a `Send` message with `message.amount = 1`.
3. On Substrate, `on_accept` computes:
   `amount = convert_to_balance(U256::from(1), erc_decimals=18, local_decimals=6)`
   `= 1 / 10^(18-6) = 1 / 10^12 = 0`
4. `on_accept` proceeds to mint/transfer `0` to the beneficiary and emits `TokenReceived { amount: 0, .. }` — no error, no revert.
5. The `1` unit burned/locked on the EVM side is permanently lost; the beneficiary receives nothing, and no timeout/refund is ever triggered because the message was "successfully" processed.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
