### Title
All-identity verification shares deserialize into an identity `group_key`, enabling universally forged Schnorr signatures — zero/identity values accepted as a NOOP-producing input - (File: crypto/dkg/src/lib.rs)

### Summary
The reported bug class is a missing zero check: a code path treats `0` as a valid input, an update becomes a NOOP, and the system silently "mints"/accepts the vacuous result. The analog in Serai is that `ThresholdKeys::new` / `ThresholdKeys::read` never verify that deserialized verification shares are non-identity. An attacker can craft serialized `ThresholdKeys` bytes in which every verification share is the identity (valid, canonical encoding). The resulting `group_key` interpolates to the identity, and then the trivially forgeable signature `(R = identity, s = 0)` passes `SchnorrSignature::verify` for **any** challenge and **any** message.

### Finding Description
`ThresholdKeys::new` validates only the *count* and *indexes* of the supplied verification shares — it checks `verification_shares.len() == n` and `participant <= n`, but performs no check that any share is a non-identity group element. [1](#0-0) 

The group key is then computed as the interpolated sum of those shares:

```rust
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
``` [2](#0-1) 

If every share is `G::IDENTITY`, then `identity * λ_i` is identity for every Lagrange factor, and the sum is the identity — the interpolation is a NOOP, exactly mirroring the report's `_updateLiquidity` NOOP that leaves the point unchanged.

`ThresholdKeys::read` feeds attacker-controlled bytes directly into `C::read_G` for each of the `n` shares and passes them unchecked into `ThresholdKeys::new`. `read_G` enforces canonical encoding, but the identity is a perfectly canonical encoding, so all-identity shares deserialize successfully. [3](#0-2) 

The signature forgery follows from `SchnorrSignature::batch_statements`/`verify`, which checks `R + cA − sG == 0` via `multiexp_vartime(...).is_identity()` with no rejection of `R == identity` or `s == 0` (and `SchnorrSignature::read` accepts both). [4](#0-3) 

With `A = group_key = identity`, choosing `R = identity` and `s = 0` yields `identity + c·identity − 0·G = identity` for **every** challenge `c`.

### Impact Explanation
Any party that loads attacker-supplied `ThresholdKeys` bytes and then verifies Schnorr signatures against `keys.group_key()` accepts forged signatures on arbitrary messages — the analog of funds/validity being credited for an operation that was actually a NOOP. This is a signature forgery primitive under the declared threat model (untrusted bytes into `ThresholdKeys::read` / `SchnorrSignature::read` and a `verify` API), not merely a cosmetic zero-acceptance.

### Likelihood Explanation
Requires an attacker to cause the verifier to deserialize a crafted `ThresholdKeys` blob (all-zero verification shares) and then accept signatures keyed by its group key — plausible wherever key material or multisig descriptors are transmitted/deserialized from peers. The signature itself costs nothing: `(identity, 0)` is hardcodable once the identity group key is in place.

### Recommendation
- In `ThresholdKeys::new` (crypto/dkg/src/lib.rs), reject identity verification shares and reject an identity computed `group_key` before constructing `ThresholdCore`.
- In `SchnorrSignature::verify` (crypto/schnorr/src/lib.rs), reject `R.is_identity()`, `public_key.is_identity()`, and `s == 0` up front — mirroring the report's "prevent minting when amount == 0" fix.

### Proof of Concept
```rust
// Craft a ThresholdKeys blob for (t, n, i) = (1, 1, 1) with an
// identity verification share, then forge a signature.

// bytes: C::ID || t=1 || n=1 || i=1 || Interpolation::Lagrange (0x01)
//        || secret_share (any canonical scalar)
//        || verification_share = C::G::identity().to_bytes()  // canonical
let keys = ThresholdKeys::<C>::read(&mut &bytes[..]).unwrap(); // succeeds today
assert!(bool::from(keys.group_key().is_identity()));

let forged = SchnorrSignature::<C> { R: C::G::identity(), s: C::F::ZERO };
for msg in [b"anything", b"at all"] {
    let c = /* challenge bound to msg, e.g. transcript output */ C::hash_to_F(b"chal", msg);
    // identity + c*identity - 0*G == identity  => true for every c
    assert!(forged.verify(keys.group_key(), c));
}
```
The forgery holds because `verify` computes `R + cA − sG = identity + c·identity − 0 = identity` regardless of `c`, so no knowledge of the secret share or any discrete logarithm is required. [4](#0-3) 

Note: I verified this against the dkg and schnorr crates as indexed; I did not fully enumerate every downstream consumer of `ThresholdKeys::read`, so callers that independently reject identity group keys would limit reachability, but no such guard exists in `ThresholdKeys::new` itself.

  pub fn batch_statements(&self, public_key: C::G, challenge: C::F) -> [(C::F, C::G); 3] {
    // s = r + ca
    // sG == R + cA
    // R + cA - sG == 0
    [
      // R
      (C::F::ONE, self.R),
      // cA
      (challenge, public_key),
      // -sG
      (-self.s, C::generator()),
    ]
  }

  /// Verify a Schnorr signature for the given key with the specified challenge.
  ///
  /// This challenge must be properly crafted, which means being binding to the public key, nonce,
  /// and any message. Failure to do so will let a malicious adversary to forge signatures for
  /// different keys/messages.
  #[must_use]
  pub fn verify(&self, public_key: C::G, challenge: C::F) -> bool {
    multiexp_vartime(&self.batch_statements(public_key, challenge)).is_identity().into()
  }
