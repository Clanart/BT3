### Title
Governance-settable `Kip71GasTarget = 0` causes division-by-zero panic in `NextMagmaBlockBaseFee` for every block, crashing consensus and RPC nodes - ([File: params/kip71_config.go])

### Summary
`KIP71Config.NextMagmaBlockBaseFee` uses the governance parameter `GasTarget` as a divisor without checking for zero, unlike the adjacent `BaseFeeDenominator`, which has an explicit zero-guard. The `Kip71GasTarget` governance parameter definition uses `noopFormatChecker` (accepting any `uint64`, including 0), so a governance vote can set `GasTarget = 0` on-chain. Once active, every node that computes/verifies the next block's base fee (which happens on every single block after the Magma fork) will panic with an integer division-by-zero, crashing all full nodes, consensus nodes, and RPC servers network-wide.

### Finding Description
`NextMagmaBlockBaseFee` divides by `gasTarget` in both the "gas used above target" and "gas used below target" branches: [1](#0-0) [2](#0-1) 

Unlike `BaseFeeDenominator`, which is explicitly zero-guarded with a fallback value before use: [3](#0-2) 

`gasTarget` itself is used raw, straight from `kc.GasTarget`, with no such guard: [4](#0-3) 

If `gasTarget == 0` and `parentGasUsed > 0` (true for essentially any non-empty block), the code takes the "gas used above target" branch and computes `x.Div(x, new(big.Int).SetUint64(gasTarget))`, i.e. division by zero, which `math/big.Int.Div` implements as a run-time panic (not an error return).

The zero value is reachable because the governance parameter definition for `Kip71GasTarget` has no format validation preventing zero: [5](#0-4) 

compare this to `Kip71BaseFeeDenominator`, which explicitly rejects zero: [6](#0-5) 

`NextMagmaBlockBaseFee`/`VerifyMagmaHeader` is invoked on every block header verification and block assembly path (e.g., via `feehistory.Oracle.processBlock`, block header validation, and block-building base fee calculation): [7](#0-6) [8](#0-7) 

This precisely mirrors the CVE-2026-79775 bug class: an attacker-controlled numeric value (there, SquashFS block size; here, `KIP71Config.GasTarget`) is used as a divisor without validating it against zero, causing an integer division-by-zero panic that crashes the process — except here the blast radius is the entire network (every node processing every block), not a single rclone/SFTP server.

### Impact Explanation
Once a `Kip71GasTarget = 0` governance vote is cast and takes effect, block production and block/header verification will panic on the very next non-empty block for every honest node in the network — CNs, PNs, ENs, and RPC servers alike — since `NextMagmaBlockBaseFee` is a mandatory step of header verification (`VerifyMagmaHeader`) and next-base-fee computation used throughout the client (fee history RPC, block assembly, gas price estimation). This is a network-wide denial of service / consensus halt, not merely a resource-exhaustion issue, matching the "Medium/High, no low or resource-only" scope of this analysis and clearly exceeding the severity of the referenced rclone bug because it can halt the entire chain rather than one server process.

### Likelihood Explanation
The governance parameter update mechanism is a reachable, standard mainnet capability (governance votes are part of Kaia's governance module); the format checker for `Kip71GasTarget` is a `noopFormatChecker`, i.e., no validation is performed at all, in clear contrast to the sibling parameter `Kip71BaseFeeDenominator` which is explicitly protected. This strongly suggests an oversight rather than an intentional design decision, and the trigger condition (`GasTarget == 0` plus any block with `GasUsed > 0`) is trivial to reach once the vote is accepted.

### Recommendation
Add a zero-value rejection to the `Kip71GasTarget` `FormatChecker` in `kaiax/gov/param.go` (mirroring the `Kip71BaseFeeDenominator` check), and/or add a defensive zero-guard for `gasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go` analogous to the existing `BaseFeeDenominator` fallback, so that a zero `GasTarget` cannot reach the `big.Int.Div` call.

### Proof of Concept
1. Submit/pass a governance vote setting `governance.kip71.gastarget` (param name `Kip71GasTarget`) to `0`. The `FormatChecker` for this parameter is `noopFormatChecker`, so the vote is accepted without rejection. [5](#0-4) 
2. Once the parameter takes effect at the target block, any subsequent block with `GasUsed > 0` (virtually guaranteed) causes `NextMagmaBlockBaseFee` to execute the `parentGasUsed > gasTarget` branch: [1](#0-0) 
3. `x.Div(x, new(big.Int).SetUint64(0))` panics with a division-by-zero run-time error inside every node computing/verifying the next base fee (header verification, block building, fee history RPC), crashing the process on all participating nodes network-wide.

func (kc *KIP71Config) VerifyMagmaHeader(headerBaseFee *big.Int, parentHeaderNumber *big.Int, parentHeaderBaseFee *big.Int, parentHeaderGasUsed uint64) error {
	if headerBaseFee == nil {
		return fmt.Errorf("header is missing baseFee")
	}
	// Verify the baseFee is correct based on the parent header.
	expectedBaseFee := kc.NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)
	if headerBaseFee.Cmp(expectedBaseFee) != 0 {
		return fmt.Errorf("invalid baseFee: have %s, want %s, parentBaseFee %s, parentGasUsed %d",
			headerBaseFee, expectedBaseFee, parentHeaderBaseFee, parentHeaderGasUsed)
	}
	return nil
}
