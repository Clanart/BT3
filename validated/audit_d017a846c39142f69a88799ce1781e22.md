## Analysis

The Balancer report's core broken invariant is: **an aggregate/security-critical value (the invariant) was computed from an incomplete subset of the inputs that should have contributed to it, while the code assumed it covered the full set** — causing a mismatch between what was priced/decided and what was actually happening in the underlying set.

The closest local analog in Hyperbridge is in the relayer fee-accumulation pipeline, `modules/pallets/relayer/src/accumulate.rs`, where **`total_fee` is aggregated over one set of commitments while the persisted "claimed" marker is applied only to a second, possibly narrower set** (`claimed_commitments`) returned separately by `validate_results`. [1](#0-0) 

### Title
Relayer fee total may be aggregated over commitments not marked as claimed, enabling double-claim of relayer fees - (File: modules/pallets/relayer/src/accumulate.rs)

### Summary
`Pallet::accumulate` verifies source and destination state proofs for a batch of request commitments, then calls `Self::validate_results(...)` which returns both `result` (a map of `delivery_address -> total_fee`) and a separate `claimed_commitments` set. [2](#0-1) 
`total_fee` is credited in full to the beneficiary/delivery address, but only commitments present in `claimed_commitments` are marked `leaf_meta.claimed = true` in storage afterward: [3](#0-2) 
If `claimed_commitments` is not guaranteed to be exactly the set of commitments whose fees were folded into `total_fee` (i.e. `total_fee` is computed/summed across `withdrawal_proof.commitments` broadly rather than strictly gated to the same subset later marked claimed), any commitment excluded from `claimed_commitments` — while still having contributed to `total_fee` — remains `claimed: false` in `RequestCommitments`. A relayer could then resubmit the same commitment in a later `accumulate` call (which only filters out commitments where `leaf_meta.claimed` is already `true`) and be paid for it a second time.

### Finding Description
This mirrors the Balancer bug's shape precisely: a downstream security decision (which commitments get marked "already paid") is driven by a *different, possibly incomplete* input set than the one used to compute the paid-out value (`total_fee`). In the Balancer case, the invariant used two balances instead of all pool balances, causing spot-price checks to be inconsistent with actual pool state; here, the "claimed" bookkeeping subset can be inconsistent with the aggregated fee amount, causing double-payment to be structurally possible rather than prevented.

The double-claim guard in this pallet is explicitly the `leaf_meta.claimed` flag — the code comment even states duplicate commitments within one batch are guarded against by a `BTreeSet`, and previously-claimed commitments are filtered out before proof-building: [4](#0-3) 
But that guard is only as strong as the guarantee that `claimed_commitments` (used at line 149-161 to set the flag) is identical to the set that funded `total_fee`. I was unable to fully inspect `validate_results` in this pass to confirm whether it enforces `claimed_commitments == withdrawal_proof.commitments` on every success path (e.g. whether a delivery-address/leaf mismatch for a subset of commitments causes those specific commitments to be excluded from `claimed_commitments` while still being summed into `total_fee`, or whether it hard-fails the whole batch in that case). This needs to be confirmed against the full `validate_results` implementation before treating this as conclusively exploitable.

### Impact Explanation
If confirmed, this is a direct "loss of funds via double-claim/double-settlement" primitive against the Hyperbridge treasury path: a relayer receives payment for a request commitment's fee, but the commitment is left unmarked as claimed, permitting the same fee to be paid out again in a subsequent `accumulate` call — an unauthorized/duplicate transfer of protocol funds to the same or a colluding relayer.

### Likelihood Explanation
Likelihood is **uncertain/unverified** — I was only able to review `accumulate.rs`'s calling code and could not read `validate_results`'s full body in this session to determine whether it structurally forces `claimed_commitments` to equal the fee-contributing set on every branch. This is the critical missing piece: if `validate_results` always returns exactly one delivery address and a `claimed_commitments` set equal to all validated commitments (with any partial/mismatched entries causing a hard error rather than silent exclusion), then no vulnerability exists here. Given this open question, this finding should be treated as a **candidate requiring direct code review of `validate_results`** (likely in the same `modules/pallets/relayer/src/` directory) before further action, not a confirmed exploit.

### Recommendation
1. Read `validate_results` (and its per-leaf validation helper referenced in the module doc comment) to confirm whether `total_fee` can ever include a commitment absent from `claimed_commitments`.
2. If such a path exists, make the invariant explicit: assert `claimed_commitments` is exactly the key-set that contributed to `total_fee` before crediting `Fees::<T>`, or better, derive `total_fee` strictly as the sum over `claimed_commitments` rather than a separately-computed aggregate.
3. Add a unit test in `modules/pallets/testsuite` that submits a batch where one commitment's destination-receipt leaf fails validation while its source-fee leaf succeeds, asserting that the fee for that specific commitment is never credited and that it remains unmarked (or, symmetrically, is marked with zero payout).

### Proof of Concept
Not established in this session — a POC requires the exact per-leaf pairing logic inside `validate_results`, which was not available in my search results. To confirm/deny, inspect and trace: for a `WithdrawalProof` with N commitments where commitment `k` has a valid source-fee proof leaf but a malformed/missing destination-receipt leaf, verify whether (a) the whole extrinsic fails, (b) commitment `k`'s fee is excluded from `total_fee` and it is excluded from `claimed_commitments` (safe), or (c) commitment `k`'s fee is included in `total_fee` while it is excluded from `claimed_commitments` (the exploitable case matching this report).

	pub fn accumulate(mut withdrawal_proof: WithdrawalProof) -> DispatchResult {
		// Reject duplicate commitments within the batch. The wire format is a
		// `Vec` and this extrinsic is unsigned, so this is the line of defence
		// against an attacker padding the batch with identical commitments to
		// double-claim fees.
		let mut seen = alloc::collections::BTreeSet::new();
		for key in withdrawal_proof.commitments.iter() {
			ensure!(seen.insert(key.encode()), Error::<T>::DuplicateCommitment);
		}

		// Filter out already-claimed / missing commitments
		withdrawal_proof.commitments = withdrawal_proof
			.commitments
			.into_iter()
			.filter(|req| match RequestCommitments::<T>::get(*req) {
				Some(leaf_meta) => !leaf_meta.claimed,
				// If request commitment does not exist in storage which should not be
				// possible, we skip it
				None => false,
			})
			.collect();
		ensure!(!withdrawal_proof.commitments.is_empty(), Error::<T>::MissingCommitments);
