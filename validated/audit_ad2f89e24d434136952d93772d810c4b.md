### Title
Unbounded recursive RLP decoding of `AccountKeyRoleBased` causes stack-overflow resource exhaustion - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes nested `AccountKeySerializer` values without any depth limit or early rejection of nested `AccountKeyTypeRoleBased` sub-keys, unlike the libjxl bug where a crafted file causes uncontrolled recursive parsing (up to 512MB of stack). A crafted `TxTypeAccountUpdate` / `TxTypeFeeDelegatedAccountUpdate` (and its variants) transaction with a deeply nested `AccountKeyRoleBased` key can force the decoder into deep mutual recursion between `AccountKeySerializer.DecodeRLP` and `AccountKeyRoleBased.DecodeRLP` before any "nested composite key" rejection logic runs.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` first decodes the outer RLP list into `[][]byte`, then for every element calls `rlp.DecodeBytes(b, &serializer)`, which invokes `AccountKeySerializer.DecodeRLP`: [1](#0-0) 

`AccountKeySerializer.DecodeRLP` reads a key type, constructs a new `AccountKey` of that type via `NewAccountKey`, and calls `s.Decode(serializer.key)`: [2](#0-1) 

If `serializer.key` is again an `AccountKeyRoleBased`, this re-enters `AccountKeyRoleBased.DecodeRLP`, which again calls `rlp.DecodeBytes` on inner byte strings, re-entering `AccountKeySerializer.DecodeRLP`. This mutual recursion is **unbounded**: nothing in the decode path checks nesting depth or key-type composability. The only defense against nested `RoleBased` keys, `IsCompositeType()`/`CheckInstallable`/`CheckUpdatable` (which return `kerrors.ErrNestedCompositeType`), is applied **after** the full object graph has already been decoded: [3](#0-2) [4](#0-3) 

The regression test in the repo confirms nested `RoleBasedKey` is only rejected at the tx-pool/tx-execution validation stage (`ErrNestedCompositeType`), i.e., strictly after `DecodeRLP` has already succeeded and fully materialized the (potentially deeply nested) key graph: [5](#0-4) 

Since `TxInternalDataAccountUpdate`/`TxInternalDataFeeDelegatedAccountUpdate` decode their `Key` field via exactly this same `AccountKeySerializer`/`AccountKeyRoleBased` decode path during ordinary RLP transaction decoding (before validation), an attacker only needs to submit a single crafted transaction to force the node to walk this recursive decode: [6](#0-5) [7](#0-6) 

Because each level of nesting only costs a small constant number of RLP-encoded bytes (a couple of bytes of list/string framing per level), a modestly sized transaction payload can encode tens of thousands of nesting levels, each adding several Go stack frames (`rlp.DecodeBytes` → `Stream.Decode` → `decodeDecoder` → `AccountKeySerializer.DecodeRLP` → `rlp.Stream.Decode` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` → …). This is directly analogous to the libjxl CVE-2024-11498 bug class: a specially crafted, otherwise well-formed input causes uncontrolled recursive parsing that consumes excessive stack/CPU resources before any structural validation occurs.

### Impact Explanation
This is reachable by any unprivileged transaction sender submitting a single `TxTypeAccountUpdate`/`TxTypeFeeDelegatedAccountUpdate` (or `WithRatio` variant) transaction via public RPC (`eth_sendRawTransaction` or equivalent) or gossip. Successful exploitation can cause excessive CPU/stack consumption on any node that RLP-decodes the transaction (including tx-pool ingestion on every peer and every validator processing the block), i.e. `evm.StateDB`/`from`-independent resource exhaustion (VA:H-equivalent). In Go, unbounded recursion typically manifests as extremely high CPU usage and rapid, uncontrolled goroutine-stack growth (Go stacks can grow up to a 1 GB limit by default before the runtime aborts with `fatal error: stack overflow`), which can crash or stall the node process, satisfying "Availability: High" (state divergence/DoS via crash/hang) similar to the referenced CVE. This is a genuine denial-of-service/resource-exhaustion risk at Medium severity, matching the CVSS profile of the reference advisory (network-reachable, requires attacker to craft data, no privileges beyond submitting a normal transaction).

### Likelihood Explanation
High likelihood of reachability: the vulnerable decode path (`AccountKeySerializer`/`AccountKeyRoleBased.DecodeRLP`) is exercised on every `TxTypeAccountUpdate`/fee-delegated-account-update transaction decode, which happens automatically whenever such a transaction is received via RPC or p2p gossip — no special node configuration or attacker privilege is required. The RLP nesting depth is fully attacker-controlled and independent of any semantic key-type restriction, since the composite-type check happens only after decode completes.

### Recommendation
Enforce a maximum decode/nesting depth for `AccountKeySerializer`/`AccountKey` decoding (e.g., reject `AccountKeyTypeRoleBased` sub-keys as soon as they are encountered inside another `AccountKeyRoleBased`, mirroring the existing `IsCompositeType()` check, but performed incrementally *during* `DecodeRLP` rather than only after full decoding), or add an explicit recursion-depth counter threaded through `rlp.Stream`/`DecodeRLP` calls for `AccountKey` types and abort decoding once a small fixed depth (e.g., 1) is exceeded.

### Proof of Concept
Conceptual construction (not executed, no code execution tools available in this session):
1. Build an `AccountKeyRoleBased` value `K0` containing a single `AccountKeyPublic`.
2. Wrap it: `K1 = AccountKeyRoleBased{K0}`, `K2 = AccountKeyRoleBased{K1}`, … repeat N times (N in the tens of thousands), each wrap only adding a few bytes via `AccountKeySerializer.EncodeRLP`/`AccountKeyRoleBased.EncodeRLP`.
3. RLP-encode `K_N` as the `Key` field of a `TxInternalDataAccountUpdate` and produce a fully signed transaction.
4. Submit the tx via `eth_sendRawTransaction` / p2p; the receiving node's `Transaction.DecodeRLP` → `TxInternalDataAccountUpdate.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recursion chain runs to depth N before `CheckInstallable`/`CheckUpdatable` ever executes, consuming excessive stack/CPU and potentially crashing the node with `fatal error: stack overflow` or causing severe processing delay.

Note: I was not able to execute this PoC or confirm the exact N required to trigger a crash versus mere CPU/latency degradation; a background Devin session with build/test tooling would be needed to actually construct the encoded bytes and measure resource consumption / confirm exploitability against the live tx-pool/RLP size limits (`blockchain/tx_pool.go` `MaxTxDataSize` constants), which limit total transaction size and would bound (but likely not eliminate, given the low per-level byte cost) the maximum achievable nesting depth.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}

func (serializer *AccountKeySerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.keyType); err != nil {
		return err
	}

	var err error
	serializer.key, err = NewAccountKey(serializer.keyType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.key)
