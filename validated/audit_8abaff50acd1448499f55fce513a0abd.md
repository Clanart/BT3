### Title
Cached FROST nonce seed is never released or rebound when the signing context changes, enabling nonce reuse and validator key recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The upstream bug class is a leaked reference: `of_find_compatible_node()` acquires a refcount that is never dropped with `of_node_put()`, so a stale reference outlives the context it was taken in. The Serai analog is in the coordinator's `SigningProtocol`: a FROST preprocess is cached in `CachedPreprocesses` keyed only by `(b"DkgConfirmer", attempt)` — never deleted, never rebound to the participant set or message it is actually used to sign. Every subsequent `share_internal` call for that attempt regenerates a deterministic sign machine from the identical seed via `AlgorithmSignMachine::from_cache`, so the same binomial nonce is reused for whatever `msg`/participant set happens to be in effect at that moment.

### Finding Description
`preprocess_internal` stores the encrypted `CachedPreprocess` seed once per `(b"DkgConfirmer", attempt)` context and reloads it on every call (`coordinator/src/tributary/signing_protocol.rs:123-145`). Because `from_cache` runs `seeded_preprocess` with `ChaCha20Rng::from_seed(*seed.0)` (`crypto/frost/src/sign.rs:121-145`), the nonces are fully deterministic per seed.

`DkgConfirmer` recomputes its effective context on each construction: `DkgConfirmer::new` reads `removed_as_of_dkg_attempt(txn, spec.genesis(), attempt)` at call time (`signing_protocol.rs:263-277`), and `share_internal` derives the MuSig `participants` list from `self.spec.validators()` and builds the signed message via `set_keys_message(&self.spec.set(), &self.removed..., key_pair)` (`signing_protocol.rs:288-301`). Neither `removed` nor `key_pair` is part of the `CachedPreprocesses` key.

`share()` and `complete()` both call `share_internal` (`signing_protocol.rs:304-327`), and each call re-derives the machine from the same cached seed and calls `machine.sign(preprocesses, msg)`. If between two invocations of the same attempt the `removed` set changes (a validator removal finalizes mid-attempt — a routine protocol event, not a reorg), or `complete` is reached with a different `key_pair`/preprocess set than `share`, the identical nonce pair `(d, e)` is consumed to produce a signature share under a different binding factor/challenge and different MuSig key mapping. The file's own safety argument only covers distinct *finalized message sets* via BFT ordering (`signing_protocol.rs:25-48`); it does not account for the `removed`/participant context drifting *within* one finalized attempt, which is exactly the state the cache key fails to capture — the refcounted resource is retained while its referent changed.

### Impact Explanation
Two FROST signature shares published under the same nonce commitment but different challenges linearly reveal the nonce `(d + ρ·e)`, and with the share equation `z = d + ρ·e + λ·s·c`, reveal the validator's MuSig secret share — i.e., the validator's root-of-trust private key (`key`), since `musig()` is constructed directly from `self.key` (`signing_protocol.rs:118-121`). Shares are published publicly on the tributary, so any unprivileged observer who sees two such shares recovers the key, enabling forging of subsequent `DkgConfirmer` signatures and violating the assumed supermajority root of trust.

### Likelihood Explanation
Triggering requires the `removed` set or confirmed `key_pair` to differ between two `share_internal` invocations within a single DKG attempt — e.g., a validator-removal transaction finalizing between the share round and the completion round, or a retried confirmation path. The FROST docs explicitly state reuse of a preprocess "will enable third-party recovery of your private key share" (`crypto/frost/src/sign.rs:85-87`), and the cache key omits every input that actually determines the signed message and participant mapping. This is a deterministic consequence of the missing context binding, not a probabilistic edge case; likelihood is bounded by how often the removal set mutates mid-attempt, which is a normal (if infrequent) protocol occurrence.

### Recommendation
Include all context that determines the signed output in the `CachedPreprocesses` key — at minimum `removed` (or its hash), the participant set, and `key_pair` — or delete/consume the cached preprocess after the first successful `sign` so a second invocation under mutated context generates a fresh nonce. Alternatively, make `DkgConfirmer` snapshot `removed`/`key_pair` into `SigningProtocol::context` so a context change necessarily allocates a new seed rather than silently reusing the old one.

### Proof of Concept
Conceptual: during DKG attempt `a`, validator V calls `share()` producing share `z1` over `msg1 = set_keys_message(set, removed_1, kp)` with nonce `k` from cached seed `s`. Before `complete()` is invoked, a removal transaction finalizes, so `removed_as_of_dkg_attempt` now returns `removed_2 ≠ removed_1`. `complete()` calls `share_internal` again, regenerating the machine from the same seed `s` → same `k`, but now signs `msg2` under a remapped MuSig participant set, yielding `z2` with challenge `c2 ≠ c1`. An observer computes `k = (z1 − z2 − λ·s·(c1 − c2))` style recovery (equivalently `k = (z1 − z2)/(c1 − c2)` after accounting for binding factors), then `s = (z1 − k)/(λ·c1)`, recovering V's Ristretto private key. Both shares are public protocol messages.
