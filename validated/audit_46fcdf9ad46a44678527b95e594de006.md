### Title
Pure-Python ProtoJSON parser deduplicates by raw JSON key instead of resolved field identity, letting an attacker "shadow" a field via an alternate name spelling to silently bypass duplicate-key rejection - ([File: python/google/protobuf/json_format.py])

### Summary
`google.protobuf.json_format.Parse` (the pure-Python ProtoJSON parser, used whenever the pure-Python protobuf backend is active) rejects duplicate JSON keys by comparing the *raw JSON key string* seen so far, not the *canonical field* that key resolves to. Because a single proto field can be addressed by multiple valid JSON key spellings (its `json_name`, e.g. `intValue`, and its original proto field name, e.g. `int_value`), an attacker can send the same logical field twice under two different spellings. The second occurrence silently overwrites the first instead of triggering the "should not have multiple fields" `ParseError` that the code is explicitly designed to raise for exact-duplicate keys.

### Finding Description
In `_ConvertFieldValuePair`, the parser resolves each JSON key `name` to a `field` via `fields_by_json_name`, then `fields_by_name`, then extension lookup: [1](#0-0) 

Duplicate detection then happens purely on the **string** `name`, not on the resolved `field` object's identity: [2](#0-1) 

Since `fields_by_json_name.get(name)` and `fields_by_name.get(name)` can both resolve *different* strings to the *same* `FieldDescriptor`, the `if name in names` check never fires when the two spellings differ, even though the target field is identical. This is confirmed as intentional (but unfixed for backward-compatibility reasons) by the project's own regression tests, which document it as "an oversight bug": [3](#0-2) 

The invariant that fails here is the same class of failure as the AshAdmin report: a security-relevant identity check (which cookie is "the" `actor_authorizing` cookie; which JSON key is "the" field already set) is performed against the wrong granularity — an unanchored/loose name match rather than exact canonical identity — so an attacker-supplied second value with a different-but-equivalent name silently "shadows"/overwrites the first, defeating a check whose whole purpose is to prevent exactly that kind of duplicate/override.

By contrast, the C++/upb JSON parser used by the C++ extension and upb-based Python backend tracks duplicates via `SeenState`/`RecordAsSeen`, which operates on the resolved field object (an index into a `flat_hash_set<int> parsed_fields_`), not the raw string key: [4](#0-3) [5](#0-4) 

so the same attack does not succeed against that backend — the gap is specific to the pure-Python implementation in `json_format.py`.

### Impact Explanation
`json_format.Parse` is a supported public ProtoJSON parsing API. Applications that rely on ProtoJSON parsing to reject ambiguous/duplicate keys (a common defensive assumption against JSON "parameter pollution", used e.g. to detect tampering or conflicting directives sent by a client) can have that assumption silently defeated: an attacker sends `{"intValue": 1, "int_value": 2}` and the parser accepts it without error, with the second value winning. For non-oneof, non-boolean fields this is mostly a data-integrity issue (silent last-write-wins instead of the intended fail-closed duplicate rejection), which matches the Medium severity/integrity-focused profile of the analog report (VI:H, VC:L in the original CVSS vector) rather than enabling remote code execution or memory corruption.

### Likelihood Explanation
This is trivially reachable by any client able to submit JSON to a service that parses it with `google.protobuf.json_format.Parse` using the pure-Python protobuf implementation — no privileged access, malicious schema, or crafted binary payload is required, only two ordinary alternate-spelling keys for the same field. It requires the pure-Python backend (not upb/C++-accelerated) to be in effect, which is still a commonly used, fully supported configuration.

### Recommendation
Change the duplicate-detection bookkeeping in `_ConvertFieldValuePair` to key off the resolved `field` object (e.g. `field.full_name` or the `FieldDescriptor` instance itself) instead of the raw JSON key string `name`, mirroring the `RecordAsSeen`/`SeenState` approach already used by the C++/upb JSON parser, so any two spellings resolving to the same field are correctly flagged as duplicates.

### Proof of Concept
Using the pure-Python protobuf backend:
```python
from google.protobuf import json_format
from google.protobuf.internal import json_format_proto3_pb2 as m

msg = m.TestMessage()
# Two different JSON key spellings resolving to the same field:
json_format.Parse('{"int32Value": 1, "int32_value": 2}', msg)
assert msg.int32_value == 2   # silently overwritten; no ParseError raised
```
This mirrors the exact regression test already present in the repo (acknowledged as unintended behavior, not fixed for compatibility reasons): [3](#0-2) [6](#0-5)
