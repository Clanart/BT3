### Title
Unbounded Python recursion in wallet outer-puzzle driver matching allows a crafted offer/coin puzzle to crash the wallet process (stack-overflow DoS) - ([File: chia/wallet/outer_puzzles.py])

### Summary
The CVE describes a stack overflow reachable via attacker-controlled input (crafted SQL causing unbounded native recursion → DoS). The chia-blockchain analog is the wallet's outer-puzzle driver chain (`CATOuterPuzzle`, `CROuterPuzzle`, `SingletonOuterPuzzle`, `OwnershipOuterPuzzle`, `MetadataOuterPuzzle`) which recursively calls `match()`/`get_inner_puzzle()`/`get_inner_solution()` on itself for every "also" (nested) puzzle layer found in an attacker-supplied `puzzle_reveal`. There is no depth limit on this Python-level recursion, so a spend bundle, offer, or coin whose puzzle reveal is crafted with a very deep stack of curried layers can drive Python's call stack past its recursion limit, raising `RecursionError` (or, in CPython with C-extension frames involved, a genuine native stack overflow/segfault) in the process handling it.

### Finding Description
`match_puzzle()` in `chia/wallet/outer_puzzles.py` iterates over `driver_lookup` and calls each driver's `match()`: [1](#0-0) 

Each driver's `match()` recurses into itself through the shared `_match` callback whenever an inner puzzle also matches a known outer-puzzle type, e.g. `CATOuterPuzzle.match()`: [2](#0-1) 

The same recursive pattern (unbounded by any layer-count cap) exists in `CROuterPuzzle.match`, `SingletonOuterPuzzle.match`, `OwnershipOuterPuzzle.match`, `MetadataOuterPuzzle.match`, and their corresponding `get_inner_puzzle`/`get_inner_solution` methods: [3](#0-2) [4](#0-3) [5](#0-4) 

`match_puzzle()`/`get_inner_puzzle()`/`get_inner_solution()` are invoked directly on attacker-supplied `puzzle_reveal`s when a wallet parses an **offer file from an untrusted counterparty**, e.g. in `Offer._get_offered_coins()` and `Offer.from_spend_bundle()`: [6](#0-5) [7](#0-6) 

Because a puzzle can be curried arbitrarily (e.g. `CAT(CAT(CAT(...CAT(inner)...)))` or nested credential-restricted/singleton/ownership layers), an attacker who crafts an offer with hundreds/thousands of nested outer-puzzle layers can force the wallet's driver-matching code into deep, unbounded Python recursion. This mirrors the CVE's bug class: input-controlled recursion depth with no bound, leading to stack exhaustion, rather than a cost- or size-bounded traversal. This is distinct from CLVM execution itself (which is Rust-based and cost-metered) — this recursion happens entirely in Python driver code that runs *before/around* CLVM execution, and is not subject to `MAX_BLOCK_COST_CLVM` or the mempool's atom/pair bounds.

By contrast, the codebase's own CLVM tree-hash implementation deliberately avoids this exact class of bug: `sha256_treehash()` in `chia/types/blockchain_format/tree_hash.py` is explicitly implemented iteratively "so we don't have to worry about blowing out the python stack" — showing recursion-depth-based DoS is a recognized risk in this codebase, but the outer-puzzle driver-matching code was not hardened the same way. [8](#0-7) 

### Impact Explanation
A wallet user who receives and inspects (or attempts to accept) a maliciously crafted offer — a normal, low-privilege interaction — can trigger unbounded Python recursion in the offer-summary/inner-puzzle resolution path. This can crash the wallet process (`RecursionError` uncaught, or a native stack overflow if C-extension frames are involved), producing a denial of service against the wallet service for any user who opens the offer. This matches the "spend-triggered transaction-processing halt" impact class explicitly accepted by the validation rules.

### Likelihood Explanation
Likelihood is high for any wallet operator who inspects offers from untrusted counterparties (a normal trading workflow) since building a puzzle with many nested outer layers is trivial with the existing puzzle-construction helpers (`construct_cat_puzzle`, `construct_cr_layer`, `puzzle_for_singleton`, `puzzle_for_ownership_layer`, etc.) — no signature or on-chain validity is required to trigger the crash because `match_puzzle`/`get_inner_puzzle` run before economic/signature validation.

### Recommendation
Impose an explicit maximum recursion/nesting depth (and/or convert the outer-puzzle driver chain to an iterative loop) in `chia/wallet/outer_puzzles.py` and each `*_outer_puzzle.py` driver's `match`, `get_inner_puzzle`, and `get_inner_solution` methods. Reject (return `None`/raise a controlled error) once a configurable depth limit (e.g. 50–100 layers) is exceeded, and apply the same input-driven-recursion review to `Offer._get_offered_coins()` and `Offer.from_spend_bundle()` before they process externally supplied puzzle reveals.

### Proof of Concept
1. Build an inner puzzle `P0` (e.g. `Program.to(1)`).
2. Iteratively wrap it N times (N ≈ 2000, comfortably above Python's default recursion limit of 1000) using `construct_cat_puzzle(CAT_MOD, tail, P_i)` (or repeatedly nesting `construct_cr_layer`/`puzzle_for_singleton`) to produce `P_N`.
3. Build a `CoinSpend`/offer whose `puzzle_reveal` is `P_N`.
4. Call `match_puzzle(UnknownPuzzle(known_program=P_N))` (as done inside `Offer._get_offered_coins()`/`Offer.from_spend_bundle()` when a wallet parses a received offer) — this recurses through `CATOuterPuzzle.match()` N times, exceeding CPython's recursion limit and raising `RecursionError`, crashing the offer-parsing code path.
