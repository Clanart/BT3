### Title
Unbounded atom-length read in `is_atom_canonical()` can crash mempool validation on a crafted spend bundle - (File: chia/full_node/mempool_manager.py)

### Summary
`is_atom_canonical()` decodes a CLVM atom's variable-length size prefix (1–6 bytes) from a spend bundle's `puzzle_reveal`/`solution` bytes and returns the decoded `atom_len` without ever validating it against the remaining buffer length before the caller uses it to advance a read offset. This is the same bug class as CVE-2023-33659: a length field parsed straight out of untrusted input is used to index/advance through a buffer without a bounds check against the actual remaining data.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads the size-prefix byte(s) at `offset` and computes `atom_len` purely from attacker-controlled prefix bits, then returns `1 + prefix_len + atom_len` as the "consumed length" of the atom [1](#0-0) . Nowhere in this function is `atom_len` checked against `len(clvm_buffer) - offset`.

Its caller, `is_clvm_canonical()`, uses that unchecked length to advance its own cursor: `offset += atom_len` [2](#0-1) , then on the next loop iteration re-indexes the buffer with `b = clvm_buffer[offset]` [3](#0-2) . Because a crafted atom prefix can declare an `atom_len` far larger than what's actually present, `offset` can be pushed past `len(clvm_buffer)`, and the very next byte access raises an unhandled `IndexError` instead of being treated as "not canonical" or safely rejected.

This function is invoked directly on attacker-supplied bytes for every coin spend in every submitted `SpendBundle`, before mempool acceptance:
```
if not is_clvm_canonical(bytes(coin_spend.puzzle_reveal)) or not is_clvm_canonical(bytes(coin_spend.solution)):
    return Err.INVALID_COIN_SOLUTION, None, []
``` [4](#0-3) 

This call sits inside `MempoolManager.validate_spend_bundle()`, part of the standard spend-bundle admission path reachable by any unprivileged submitter via the mempool/RPC push path [5](#0-4) .

### Impact Explanation
Root cause matches the reported CVE class exactly: a declared length taken from untrusted, attacker-controlled bytes is used to advance/index a buffer without verifying it fits inside the buffer's actual remaining size. In the NanoMQ case this manifested as a heap buffer overflow; in this Python code the same missing bounds check manifests as an unhandled `IndexError` when decoding a crafted `puzzle_reveal`/`solution`. Because `is_clvm_canonical()` is called unconditionally on every coin spend during spend-bundle validation, a single malicious spend bundle reaching this code path can throw an exception mid-validation of `validate_spend_bundle()`, which is not wrapped in an exception handler at this call site — a spend-triggered halt of mempool transaction processing for that bundle/connection, matching the accepted "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
The attack requires only a single crafted `SpendBundle` with a puzzle_reveal or solution containing a size-prefix byte sequence whose declared `atom_len` exceeds the remaining buffer — this is directly constructible bytes, not requiring any special privileges, valid signatures being a separate check, or coordination with other nodes. The `test_mempool_requires_canonical_clvm` tests already exercise non-canonical-but-still-in-bounds prefixes (e.g. `c00101`) and expect a graceful `Err.INVALID_COIN_SOLUTION` [6](#0-5) , but none of the existing tests specifically probe a prefix whose declared `atom_len` overruns the actual buffer length, so this exact edge case does not appear to be covered by current tests.

### Recommendation
In `is_atom_canonical()`, after computing `prefix_len` and before/while reading the prefix bytes, validate that `offset + prefix_len < len(clvm_buffer)`. After computing the final `atom_len`, validate that `1 + prefix_len + atom_len <= len(clvm_buffer) - original_offset` before returning, and treat any prefix that would overrun the buffer as non-canonical (return `False`) or raise a caught/expected error rather than an unguarded index operation. Additionally, wrap the `is_clvm_canonical()` calls in `validate_spend_bundle()` with explicit handling for malformed/out-of-range input so a crafted bundle degrades to rejection (`Err.INVALID_COIN_SOLUTION`) rather than an unhandled exception.

### Proof of Concept
Construct a `puzzle_reveal` (or `solution`) byte string whose first atom uses a wide size-prefix (e.g. the `0xF8`/`0xFC` prefix classes) that declares an `atom_len` larger than the number of bytes actually following it in the buffer, e.g.:
```python
# 0xFC prefix class declares up to a 40-bit length; supply far fewer trailing bytes than declared
buf = bytes([0xFC, 0x00, 0x00, 0x00, 0x01]) + b"\x01"  # declares a huge atom_len, buffer ends almost immediately
is_clvm_canonical(buf)  # raises IndexError instead of returning False
```
Wrapping this buffer as a `coin_spend.puzzle_reveal` or `coin_spend.solution` in a submitted `SpendBundle` reaches `is_clvm_canonical()` in `MempoolManager.validate_spend_bundle()` [4](#0-3)  and triggers the unguarded out-of-bounds index access described above.

**Note on verification limits:** I was not able to trace, within the available tool calls, whether every caller in the full-node request-handling chain around `add_spend_bundle()`/`validate_spend_bundle()` catches generic `Exception`/`IndexError` (only a `ValueError`-specific handler was found around the separate `pre_validate_spendbundle()` Rust call [7](#0-6) ). Confirming the exact blast radius (single-request failure vs. broader task/connection disruption) would require reading the full `add_spend_bundle()` implementation and its RPC/protocol callers, which I could not complete before this response was due — a Devin session with full repo access could verify this precisely.

def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
