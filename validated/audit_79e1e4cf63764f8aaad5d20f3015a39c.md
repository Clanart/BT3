## Analog Confirmed: Attacker-controlled ProtoJSON field content is embedded verbatim into `upb_Status` error messages that PHP/Ruby surface as uncaught exception text, matching the CVE-2017-1000151 pattern (unexpected/malformed input parameters ending up in application error output).

### Title
Attacker-controlled JSON field values embedded verbatim in ProtoJSON parse-error messages surfaced as exception text (PHP/Ruby `upb` JSON decoder) - (File: `upb/json/decode.c`)

### Summary
The `upb` JSON decoder used by the PHP and Ruby native extensions builds parse-error diagnostics with `jsondec_errf`/`upb_Status_SetErrorFormat`, and in several code paths (numeric-as-string coercion, enum lookup) it interpolates the *raw attacker-supplied field value* into the resulting `upb_Status` message via `%s`/`UPB_STRINGVIEW_FORMAT`. That status message is propagated unmodified into a thrown `Exception`/`ParseError` in both language bindings. Any calling application that logs exception messages (a standard practice) will thus write the raw client-supplied field content — which can include values a client intended for a different field, e.g. a credential mistakenly sent as an enum/numeric string — into its error logs.

### Finding Description
- `jsondec_double()` in `upb/json/decode.c` (mirrored in `php/ext/google/protobuf/php-upb.c:5704-5751` and `ruby/ext/google/protobuf_c/ruby-upb.c` equivalents) builds:
  `"Non-number characters in quoted number (field: %s). ..."` — this one only names the field, not the value. [1](#0-0) 
- `jsondec_enum()` in `upb/json/decode.c` / `ruby-upb.c` builds an error with the *actual raw JSON string content* the client sent for that field:
  `jsondec_errf(d, "Unknown enumerator: '" UPB_STRINGVIEW_FORMAT "'", UPB_STRINGVIEW_ARGS(str));` [2](#0-1) [3](#0-2) 
- This `upb_Status` is passed straight through to the language binding without redaction:
  - PHP: `zend_throw_exception_ex(NULL, 0, "Error occurred during parsing: %s", upb_Status_ErrorMessage(&status));` [4](#0-3) 
  - Ruby: `raise ParseError.new "Error occurred during parsing: #{Google::Protobuf::FFI.error_message(status)}"` [5](#0-4) 

**Invariant that fails to transfer safely**: Elsewhere in the codebase, Protobuf explicitly recognizes that field *values* must not leak into diagnostic/debug channels — the C++ `TextFormat`/`DebugString` machinery has a dedicated `debug_redact` mechanism (`FieldOptions.debug_redact`) and `kFieldValueReplacement = "[REDACTED]"` substitution specifically to prevent sensitive field content from being printed. [6](#0-5) [7](#0-6) [8](#0-7) 
The C++ JSON lexer designer was also aware that unhardened error text can leak into logs and only accepted this trade-off for a single non-sensitive control character, explicitly calling out the tension: *"we intentionally do not harden the 'invalid JSON' part, so that people have a hope of grepping for it in logs"*. [9](#0-8) 
The `upb` JSON decoder used by PHP/Ruby has no equivalent redaction/hardening step at all — no `debug_redact` check, no truncation, no generic placeholder — for the enum-value error path, and echoes the full attacker-controlled string unconditionally.

### Impact Explanation
This is an information-disclosure issue: attacker-controlled data supplied as an ordinary (even malformed) ProtoJSON request body is embedded verbatim into an exception message. Because throwing an uncaught exception with a descriptive message is the default behavior of `mergeFromJsonString`/`decode_json`, any application that logs unhandled exceptions (a very common practice for web-facing PHP/Ruby services) will persist the raw client-submitted string — potentially including secrets a client mistakenly or maliciously placed in an enum-typed JSON field — to disk-based or centralized logs. This mirrors the CVE-2017-1000151 pattern precisely: unusual/malformed parameters ending up recorded by the error-logging path rather than being validated/redacted first. Impact is confidentiality-only (C:H/I:N/A:N in CVSS terms for the analog), matching the referenced CVE's rating; there is no RCE, memory corruption, or availability effect.

### Likelihood Explanation
High likelihood of reachability: any client of a PHP or Ruby service exposing `Message::mergeFromJsonString()` / `Message.decode_json` can trigger this by submitting a JSON body with an unrecognized string value for an enum field — no privileges, no malformed wire-format tricks, and no schema control needed; it is a normal validation-failure path in a supported public parsing API. The only precondition for actual sensitive-data exposure is that the calling application logs unhandled/caught exception messages, which is standard operational practice, not an unusual configuration.

### Recommendation
- In `upb/json/decode.c`'s `jsondec_enum()` (and any other `jsondec_errf`/`jsondec_err` call site that interpolates raw JSON token content), stop embedding the raw string value in the status message; report only the field name/location (as already done in `jsondec_checkempty`/`jsondec_double`'s "field: %s" pattern) or a fixed placeholder.
- Apply the same `debug_redact`-aware suppression used by `TextFormat`/`DebugString` (see `TextFormat::Printer::TryRedactFieldValue`, `kFieldValueReplacement`) to JSON parse-error construction so that fields marked `debug_redact = true` never have their value echoed even indirectly through error paths.
- Audit the PHP/Ruby exception wrappers (`GPBDecodeException`, `ParseError`) to confirm they don't unconditionally forward the full native status message to callers/logs without an opt-in "verbose error" flag.

### Proof of Concept
Given a `.proto` schema with an enum field, e.g.:
```proto
enum Status { UNKNOWN = 0; ACTIVE = 1; }
message M { Status status = 1; }
```
Ruby (FFI) reproduction path:
```ruby
M.decode_json('{"status":"super-secret-password-123"}')
# => Google::Protobuf::ParseError:
#    Error occurred during parsing: Error parsing JSON @1:10: Unknown enumerator: 'super-secret-password-123'
```
PHP reproduction path (equivalent):
```php
$m = new M();
$m->mergeFromJsonString('{"status":"super-secret-password-123"}');
// Uncaught Exception: Error occurred during parsing: Error parsing JSON @1:10: Unknown enumerator: 'super-secret-password-123'
```
The exact string `super-secret-password-123` supplied by the caller is reproduced verbatim in the exception message, which application code commonly logs verbatim (`Rails.logger.error(e.message)` / PHP's default exception handler / uncaught-exception log), confirming reachable disclosure of attacker-supplied content through a supported public ProtoJSON parse API. I did not execute this PoC in a live PHP/Ruby build within this session; the trace is derived from static code inspection of `jsondec_enum`, `jsondec_errf`, `zend_throw_exception_ex`, and `Google::Protobuf::FFI.error_message` call sites cited above, so runtime confirmation is recommended before filing.

bool TextFormat::Printer::TryRedactFieldValue(
    const Message& message, const FieldDescriptor* field,
    BaseTextGenerator* generator, bool insert_value_separator) const {
  TextFormat::RedactionState redaction_state =
      DescriptorPool::MemoizeProjection(
          field, [](const FieldDescriptor* field) {
            return TextFormat::GetRedactionState(field);
          });
  if (redaction_state.redact) {
    if (redact_debug_string_) {
      IncrementRedactedFieldCounter();
      if (insert_value_separator) {
        generator->PrintMaybeWithMarker(MarkerToken(), ": ");
      }
      generator->PrintString(kFieldValueReplacement);
      if (insert_value_separator) {
        if (single_line_mode_) {
          generator->PrintLiteral(" ");
        } else {
          generator->PrintLiteral("\n");
        }
      }
      return true;
    }
  }
  return false;
}

absl::Status JsonLocation::Invalid(absl::string_view message,
                                   SourceLocation sl) const {
  // NOTE: we intentionally do not harden the "invalid JSON" part, so that
  // people have a hope of grepping for it in logs. That part is easy to
  // commit to, as stability goes.
  //
  // This copies the error twice. Because this is the "unhappy" path, this
  // function is cold and can afford the waste.
  std::string status_message = "invalid JSON";
  std::string to_obfuscate;
  if (path != nullptr) {
    absl::StrAppend(&to_obfuscate, " in ");
    path->Describe(to_obfuscate);
    to_obfuscate.push_back(',');
  }
  absl::StrAppendFormat(&to_obfuscate, " near %zu:%zu (offset %zu): %s",
                        line + 1, col + 1, offset, message);
  HardenAgainstHyrumsLaw(to_obfuscate, status_message);

  return absl::InvalidArgumentError(std::move(status_message));
}
