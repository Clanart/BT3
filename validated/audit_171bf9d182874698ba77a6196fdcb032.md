### Title
Missing-entry dereference in `GeneratorPromotion::complete` allows a panic on attacker-controlled proof maps - (File: crypto/dkg/promote/src/lib.rs)

### Summary
Analogous to CVE-2022-49895 — where a cleanup path dereferences a decoder that failed to be allocated — `GeneratorPromotion::complete` validates only the *count* and *upper bound* of a `HashMap<Participant, GeneratorProof>` and then unconditionally `unwrap()`s `proofs.get(&i)` for every participant `1..=n` besides self. A proofs map that passes both checks but keys an entry under `params.i()` (our own index, displacing an honest participant) reaches `proofs.get(&i).unwrap()` with `i` absent, panicking the caller.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs two validations:

- `proofs.len() != n - 1` → `IncorrectAmountOfParticipants` (line 125–131)
- each key `i` satisfies `u16::from(i) <= params.n()` (line 132–136)

It then iterates `for i in 1 ..= params.n()`, skips `params.i()`, and executes `let proof = proofs.get(&i).unwrap();` at line 146. The validation never checks that the map does not contain `params.i()` itself. Since `HashMap` keys are unique, an attacker supplying an entry keyed with `params.i()` (index of the receiving party — e.g., by claiming our participant index in their `Participant`-keyed share/proof message) while legitimately holding any other slot produces a map of exactly `n - 1` entries, all `<= n`, that omits some honest participant `j`. The loop hits `proofs.get(&j)` → `None` → `.unwrap()` panic.

This mirrors the CVE precisely: the "was the resource ever supplied?" check is absent on the path that uses it; bounds checks substitute for an existence check and fail.

### Impact Explanation
Reachable with untrusted, publicly-originated input: the `proofs` map is built from `GeneratorProof`s received from peer participants during generator promotion (each `GeneratorProof` is deserialized via `DLEqProof::read` / `C::read_G` from peer-controlled bytes, and the `Participant` key is derived from the sender's message). A single malicious or malfunctioning participant induces a panic in every honest party's `complete`, aborting the key-promotion ceremony — an availability failure identical in class and severity to the kernel NULL-deref crash.

### Likelihood Explanation
Any participant in a `GeneratorPromotion` round can trigger it by emitting a proof keyed as `params.i()` (or arranging the map so one required index is missing while the count still equals `n-1`). No collusion, timing race, or privileged position is needed; the only precondition is that the victim processes the proof map.

### Recommendation
Replace the `1..=n` loop's `unwrap()` with a checked lookup (`proofs.get(&i).ok_or(PromotionError::MissingParticipant(i))?`), and/or pre-validate that `proofs` does not contain `params.i()` and that its key set equals `{1..=n} \ {params.i()}` — i.e., verify existence of each needed entry before dereferencing, as the upstream fix did for `cxld`.

### Proof of Concept
```rust
// crypto/dkg/promote: with params n = 3, our i = 1.
// Attacker-controlled proofs map: {1: proof_i, 2: proof_2} — omits participant 3,
// includes our own index. len() == n - 1 (passes), all keys <= n (passes).
// Loop: i=1 skipped (self), i=2 ok, i=3 -> proofs.get(&3) == None -> unwrap() panic.
let mut proofs = HashMap::new();
proofs.insert(params.i(), attacker_proof_for_our_slot); // keyed as participant 1
proofs.insert(Participant::new(2).unwrap(), proof_2);
promotion.complete(&proofs); // panics at proofs.get(&3).unwrap()
```
