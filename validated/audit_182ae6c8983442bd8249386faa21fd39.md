## Title
`AccountableFixedTerm`-style stale-snapshot / positional-splice mismatch in Copilot conflict resolution can silently corrupt committed file content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

## Summary
The `claimInterest` bug is fundamentally about applying a value computed from a **stale, optimistic snapshot** (the full-term `netReturn`) positionally/order-dependently against a **live, mutable state** (`totalShares`), with no check that the snapshot still matches the current state. GitHub Desktop's Copilot-assisted conflict resolution has the same broken invariant: the LLM's per-hunk resolution is generated against a *cached snapshot* of a conflicted file (`rawContent`), spliced back in **by ordinal position, not by content/line identity**, and then written to disk with a guard that only checks "are there still conflict markers?" — not "does this file still represent the same conflict the resolution was computed for?" If the underlying conflict state changes between analysis and apply (new rebase step reaches the same path, remote/base moves, or the file is re-conflicted), the write silently splices mismatched content into the working tree, which is then committed.

## Finding Description
`reassembleResolvedFile` explicitly documents and implements order-based, not identity-based, matching: [1](#0-0) 

It walks the conflict-marker blocks of `rawContent` in file order and splices `hunkResolutions[hunkIndex]` in sequentially: [2](#0-1) 

`reassembleResolutions` feeds this function with `ctx.rawContent`, i.e., the file content captured in `IFileConflictContext` **at the time Copilot analyzed the conflict**, not content re-read at write time: [3](#0-2) 

The resulting `resolution.resolvedContent` is later written to disk by the store's apply path. The only staleness guard present checks whether the on-disk file *still has unresolved conflict markers* — it does not verify that the on-disk conflict content/hunk-order is the same one the LLM reasoned over: [4](#0-3) 

Because the check is "conflict markers are still present" rather than "this is the same conflict," any scenario where the working tree's conflicted content for the same path changes shape between context-gathering and apply-time (different hunk count/order/content) causes `resolvedContent` to be written verbatim over content it was never actually computed for, since the splice only counts marker blocks positionally.

This mirrors the `claimInterest` invariant break: a value computed against an assumed static reference (`maxNetYield` / `ctx.rawContent`) is applied to a system whose real state (`totalShares` / on-disk conflict hunks) can move before the value is consumed, and no invariant enforces that the reference and the live state still correspond.

## Impact Explanation
If exploited, this results in **silent corruption of what the user commits**: Copilot's review UI shows reasoning/diff for one conflict, but the code path can apply a resolution that no longer corresponds to the actual current conflicted content of that file, and that corrupted content is then staged and committed via `createMergeCommit` / `continueCherryPick` / rebase continuation, all of which trust the working tree without re-diffing against what was reviewed: [5](#0-4) 

This falls squarely under the requested impact class of "silent corruption of what the user commits or pushes," since the user believes they approved a specific resolution but the file actually written can diverge from it without any error or warning.

## Likelihood Explanation
The likelihood is constrained by needing a scenario where the same file path is re-conflicted or its conflict shape changes between Copilot analysis and the user clicking "Apply and Continue" — e.g., in a multi-commit rebase/cherry-pick where the same path conflicts across multiple commits in the sequence, or where the target/base moves (attacker-controlled remote content participating in the merge base) while the dialog is open. The existing `hasUnresolvedConflicts` check specifically ignores this case since it was designed to detect only "user manually fixed it externally," not "the conflict changed underneath us." I was not able to fully trace every intermediate call site between `reassembleResolutions` and the write in `app-store.ts` (e.g., whether `copilotResolutions` is invalidated on every `git status` refresh) within the available tool budget, so the exact trigger conditions for reaching stale application in the current rebase/cherry-pick UI flow could not be fully confirmed from the index alone.

## Recommendation
Do not rely on ordinal hunk-splicing against a cached snapshot. Before applying a stored Copilot resolution, re-extract conflict hunks from the *current* on-disk content and verify structural/content equivalence (e.g., hash or context-line comparison) with the hunks the resolution was generated against; if they differ, discard the stale resolution and re-prompt the user rather than silently writing it.

## Proof of Concept
Conceptual reproduction path (not independently executed):
1. Start a rebase that will conflict on `file.ts` at commit A; invoke "Resolve with Copilot." The context (`IFileConflictContext.rawContent`) captures `file.ts` with hunk set `H_A` (order 1..N).
2. Before the resolution dialog's "Apply and Continue" completes writing, cause the working tree's conflict state for the same path to change shape — e.g., abort and restart with an updated base, or reach the next commit in the sequence which reconflicts the same path with a different number/order of markers (`H_B`).
3. `applyCopilotConflictResolutions` (`app-store.ts:7241-7259`) only checks `isConflictedFileStatus` + `hasUnresolvedConflicts`, both true for `H_B`, and proceeds to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, where `resolvedContent` was spliced via `reassembleResolvedFile` against the stale `H_A` snapshot.
4. The file committed via `continueRebase`/`createMergeCommit` now contains content positionally derived from `H_A`'s resolution applied over what was actually `H_B`'s conflict text — corrupting the commit without any error surfaced to the user.

export function reassembleResolutions(
  rawResolutions: ReadonlyArray<IRawFileResolution>,
  fileContexts: ReadonlyArray<IFileConflictContext>
): ReadonlyArray<IFileResolution> {
  const contextByPath = new Map(fileContexts.map(f => [f.path, f]))

  return rawResolutions.map(raw => {
    // Delete-vs-modify resolutions carry an action, not hunk content.
    // Pass through without reassembly — the resolution is applied as a
    // ManualConflictResolution, not a file write.
    if (raw.action !== undefined) {
      return {
        path: raw.path,
        resolvedContent: '',
        reasoning: raw.reasoning,
        deleteConflictAction: raw.action,
      }
    }

    const ctx = contextByPath.get(raw.path)
    if (ctx?.rawContent === undefined) {
      throw new CopilotValidationError(
        `Cannot reassemble resolution for "${raw.path}": original file content is unavailable`
      )
    }

    const resolvedContent = reassembleResolvedFile(ctx.rawContent, raw.hunks)
    return {
      path: raw.path,
      resolvedContent,
      reasoning: raw.reasoning,
    }
  })
