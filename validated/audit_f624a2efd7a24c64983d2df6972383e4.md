### Title
Non-versioned `EvmHosts` address mapping breaks proof verification for requests/receipts/fees anchored to a prior ISMP host address after `update_evm_hosts` - (File: `modules/pallets/host-executive/src/lib.rs`)

### Summary
The `pallet-ismp-host-executive` stores a single, non-historized ISMP host contract address per EVM state machine in `EvmHosts`. Every EVM-family `StateMachineClient` (`evm`, `substrate_evm`, `tendermint`, `pharos`) resolves this *current* address at proof-verification time via `EvmHosts::<T>::get(&proof.height.id.state_id)` and uses it — regardless of the state-machine height the proof is anchored to. When governance rotates the host address with `update_evm_hosts`, any commitment/receipt/fee data that lived in the *old* host contract's storage (for heights before the rotation) can never again be proven, because verification always targets the new address's storage slots. This is the direct structural analog of the reported Lido `WITHDRAWAL_ADDRESS` issue: a single "current" trusted address used to gate/verify state, with no backward-compatibility or historical tracking across an address rotation.

### Finding Description
`EvmHosts` is defined as a flat, single-valued map: [1](#0-0) 

It is updated wholesale, with no retention of the prior value beyond an event log, and no restriction based on outstanding/undelivered commitments: [2](#0-1) 

Every EVM state-machine client fetches this *current* address and binds the storage-proof key derivation and verification to it, independent of the `proof.height` being verified: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The same current-address lookup is used by the relayer fee-accumulation path, which reads `RequestMetadata`/receipts from source and destination EVM contracts to credit relayer rewards: [8](#0-7) 

Because `EvmHosts` carries no height-scoping or versioning, once governance calls `update_evm_hosts` to point a state machine at a new host contract (a real, supported operational flow — see the dedicated migration script and `HostAddressUpdated` event), the pallet permanently loses the ability to verify membership/non-membership/state proofs for:
- pending outbound requests still sitting in the old host contract's `RequestCommitments` storage,
- delivery receipts in the old host contract's `RequestReceipts` storage (used for timeout proofs),
- unclaimed relayer fees recorded against the old host contract. [9](#0-8) [10](#0-9) 

Existing guards (`IsmpContractNotFound`, storage-proof-not-found errors) only detect a *missing* address entry, not a *stale* one — the code has no way to tell that a proof anchored at height `H` (before rotation) should be checked against the old address rather than the new one.

### Impact Explanation
Any request, timeout, or relayer-fee commitment that was live in the old host contract at the time of a host-address rotation becomes permanently unprovable: `verify_membership`/`verify_non_membership`/`verify_state_proof` will look up storage slots under the new contract address and fail (wrong contract root, missing storage proof), even though the data legitimately exists on-chain under the old address. This causes:
- Loss/lock of relayer fee rewards that had already accrued but not yet been accumulated/withdrawn (`accumulate.rs` fee crediting silently becomes impossible for the affected commitments).
- Permanent inability to timeout or resolve requests dispatched to/through the old host, stranding any bridged value or logic tied to those requests.

This matches the bounty's fund-loss/lock and reward-claim impact bucket, mirroring the original report's "checks fail for old deposits" pattern.

### Likelihood Explanation
`update_evm_hosts` is a legitimate, documented governance operation (not a compromised-actor scenario) exercised via `tesseract/consensus/relayer/src/subcommand.rs` and migration scripts such as `evm/tron/migrations/3_upgrade_consensus.js`. Any real host-contract migration (upgrade, redeploy, chain-specific redeploy such as the Tron consensus upgrade) triggers this exact condition. No code path re-verifies old-address data before or after the swap, so the break is deterministic and not contingent on any malicious behavior.

### Recommendation
Track historical `EvmHosts` addresses per state machine keyed by (or bounded by) the state-machine height/consensus update at which the rotation occurred, and have `verify_membership`/`verify_state_proof`/fee accumulation select the address that was valid at `proof.height` rather than unconditionally using the current value. At minimum, require draining/finalizing all outstanding commitments and relayer-fee accumulation against the old address before allowing `update_evm_hosts` to overwrite it, or retain a bounded history of addresses to check against.

### Proof of Concept
1. Governance calls `pallet_ismp_host_executive::update_evm_hosts` for `StateMachine::Evm(X)`, rotating the stored address from `OLD_HOST` to `NEW_HOST` (real deployed contracts, e.g. as done in the Tron consensus-upgrade migration).
2. A `PostRequest` was dispatched to/through `OLD_HOST` prior to the rotation and is still unclaimed (either its delivery receipt lives in `OLD_HOST` storage, or its relayer fee metadata is stored under `OLD_HOST`).
3. A relayer submits a valid state proof for that pre-rotation commitment at the correct historical height.
4. `SubstrateEvmStateMachine::verify_state_proof` / `EvmStateMachine::verify_membership` resolve `contract_address = EvmHosts::<T>::get(&proof.height.id.state_id)`, which now returns `NEW_HOST` — a contract whose storage never contained that commitment.
5. Verification fails (`ContractAccountProofMissing` / `StorageProofMissing` / mismatched proof), and the relayer fee for that commitment can never be accumulated via `Relayer::accumulate_fees`, nor can the request ever be proven for a timeout — permanently locking the associated reward/message.

		/// Set or update the addresses for the specified evm hosts
		#[pallet::weight(T::DbWeight::get().writes(1))]
		#[pallet::call_index(2)]
		pub fn update_evm_hosts(
			origin: OriginFor<T>,
			params: BTreeMap<StateMachine, H160>,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			for (state_machine, address) in params {
				let old = EvmHosts::<T>::get(&state_machine);
				EvmHosts::<T>::insert(state_machine.clone(), address);
				if let Some(old_address) = old {
					Self::deposit_event(Event::<T>::HostAddressUpdated {
						state_machine,
						old_address,
						new_address: address,
					});
				} else {
					Self::deposit_event(Event::<T>::HostAddressSet { state_machine, address });
				}
			}

			Ok(())
		}

		&self,
		host: &dyn IsmpHost,
		commitments: Vec<H256>,
		root: StateCommitment,
		proof: &Proof,

	pub fn verify_withdrawal_proof(
		state_machine: &dyn ismp::consensus::StateMachineClient,
		proof: &Proof,
		keys: Vec<Vec<u8>>,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, DispatchError> {
		let host = <T as Config>::IsmpHost::default();
		let state = host
			.state_machine_commitment(proof.height)
			.map_err(|_| Error::<T>::ProofValidationError)?;
		// Select the trie root explicitly instead of letting the relayer-supplied proof choose
		// it. Fee accumulation reads ISMP request/receipt metadata, which lives in the global
		// state trie on EVM chains and in the ISMP child trie (overlay root) on substrate
		// chains.
		let root = if proof.height.id.state_id.is_evm() {
			state.state_root
		} else {
			state.overlay_root.ok_or(Error::<T>::ProofValidationError)?
		};
		let result = state_machine
			.verify_state_proof(&host, keys, root, proof)
			.map_err(|_| Error::<T>::ProofValidationError)?;

		Ok(result)
	}
