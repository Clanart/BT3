I found a concrete local analog in the Tron variant of the IntentGateway contract. This isn't a reentrancy bug per se (the `_filled` guard is set before the token loop, same CEI protection the main EVM path has), but it is the same underlying bug class the report describes: **the contract trusts an external call's outcome without verifying the actual transfer succeeded, and settles/accounting state as if funds moved.**

### Title
Unchecked ERC-20 transfer return value in `IntentGatewayV2.withdraw()` allows solver fund theft via malicious input token - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In the Tron deployment of `IntentGatewayV2`, escrow release in `withdraw()` uses a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the low-level call did not revert — it never checks the ERC-20 `transfer` boolean return value. This differs from the canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`), which uses OpenZeppelin's `SafeERC20.safeTransfer`, enforcing the return value. An order creator can escrow a malicious, non-reverting ERC-20 as their order's input, let a solver fill the order (sending real value to the beneficiary), and have `withdraw()` mark the escrow released/refunded and emit success events even though the solver never actually received the escrowed token.

### Finding Description
`withdraw()` releases escrowed tokens to a beneficiary: [1](#0-0) 
For ERC-20 tokens, the transfer is dispatched with a bare `.call` and only `success` (call-didn't-revert) is checked — the ABI-decoded boolean return of `transfer` is discarded. The same pattern is repeated for fee-token payout: [2](#0-1) 

Many non-standard/malicious ERC-20 tokens return `false` on a failed transfer instead of reverting. Because `success` only reflects whether the call executed without reverting, such a token satisfies `success == true` while transferring zero tokens. `withdraw()` then unconditionally decrements `_orders[...]`, sets `_filled[commitment]`, and emits `EscrowReleased`/`EscrowRefunded` as if the transfer succeeded.

The canonical EVM implementation avoids this by using `SafeERC20.safeTransfer`, which reverts on a `false` return: [3](#0-2) 

`withdraw()` is reachable from a fully unprivileged, user-controlled path: an order creator picks the escrowed input token in `placeOrder`, and that same token later flows into `withdraw()` when a solver fills the order and the `RedeemEscrow` message returns to the source chain via `onAccept`: [4](#0-3) [5](#0-4) 

### Impact Explanation
A malicious order creator deploys a fake ERC-20 that returns `false` (without reverting) whenever `IntentGatewayV2` calls `transfer`, but behaves normally to everyone else so it doesn't look obviously broken (e.g., pass basic on-chain checks a naive solver/bot might run). The attacker escrows this token as `order.inputs`, offering a real, valuable output (e.g., stablecoin/ETH) the honest solver must pay to fill the order. The solver fills the order on the destination chain, sending real value to the attacker's beneficiary. The `RedeemEscrow` message settles on the source chain, `withdraw()` "transfers" the fake token to the solver, the low-level call succeeds, `_orders` is zeroed, and `EscrowReleased` fires — but the solver receives nothing. The attacker walks away with the solver's genuine payment while their own "input" was worthless and never actually delivered. This is direct loss of funds for the solver and false settlement-state acceptance by the protocol.

### Likelihood Explanation
Any user can place an order (`placeOrder` is `public payable`, unauthenticated) and can pick an arbitrary ERC-20 contract as an input token — no relayer, prover, or admin collusion is required. The only precondition is that a solver chooses to fill the order without independently validating the input token's transfer semantics, which is a realistic condition for automated/bot solvers competing on price rather than auditing every counter-asset per fill.

### Recommendation
Replace the raw `.call` + `success`-only checks in `withdraw()` (and the `sweepDust`/`SweepDust` handling in `onAccept`, which has the identical pattern) with OpenZeppelin's `SafeERC20.safeTransfer`, matching `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. This ensures a `false` return value causes a revert instead of silently "succeeding."

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20 whose `transfer(to, amount)` returns `false` (no revert) whenever `msg.sender == IntentGatewayV2Address`, and behaves as a normal ERC-20 otherwise.
2. Attacker calls `placeOrder` with `order.inputs = [{token: EvilToken, amount: X}]` and `order.output = {beneficiary: attacker, assets: [{token: USDC, amount: Y}]}`, depositing `X` EvilToken (worthless to attacker, they control the mint).
3. A solver calls `fillOrder` on the destination chain, sending `Y` real USDC to the attacker's beneficiary address, and the gateway dispatches `RedeemEscrow{commitment, tokens:[{EvilToken, X}], beneficiary: solver}` back to the source chain.
4. On the source chain, `onAccept` → `withdraw(body, false)` calls `EvilToken.transfer(solver, X)`, which returns `false` but does not revert; `success == true` at the call-site because the call itself didn't revert.
5. `withdraw()` decrements `_orders[commitment][EvilToken]`, emits `EscrowReleased`, and returns normally. The solver's balance of `EvilToken` never increased, yet the protocol considers escrow fully settled — the solver has permanently lost the `Y` USDC paid to the attacker with no compensating asset received.
