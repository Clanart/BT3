### Title
Unauthenticated TxSender JSON-RPC `send_tx` Endpoint Allows Arbitrary Transaction Injection and Fee-Wallet Drainage — (`crates/clementine-tx-sender/src/jsonrpc/server.rs`)

---

### Summary

The standalone TxSender JSON-RPC server exposes a `send_tx` method with **zero authentication**. When the server is bound to `0.0.0.0` (an explicitly supported and validated configuration), any network-reachable attacker can inject arbitrary Bitcoin transactions into the tx-sender queue with caller-controlled `FeePayingType`, `cancel_outpoints`, `cancel_txids`, and activation parameters. By injecting a valid low-fee transaction with `FeePayingType::CPFP`, the attacker causes the tx-sender to create CPFP child transactions spending from the operator's fee wallet, draining it. Without fee-wallet funds, the tx-sender cannot fee-bump legitimate bridge transactions (kickoff, reimburse, challenge-timeout, etc.), causing bridge liveness failure.

---

### Finding Description

**Root cause — no authentication in `start_jsonrpc_server`:** [1](#0-0) 

The function builds a plain `jsonrpsee` HTTP server and registers `send_tx` with no token, IP-allowlist, mTLS, or any other guard. Every parameter the caller supplies is forwarded verbatim to `TxSenderClient::insert_try_to_send`: [2](#0-1) 

The attacker controls: `signed_tx`, `fee_paying_type`, `rbf_signing_info`, `cancel_outpoints`, `cancel_txids`, `activate_txids`, `activate_outpoints`.

**The bind address `0.0.0.0` is explicitly accepted by the config validator:** [3](#0-2) 

The code rejects any bind address that is *not* `127.0.0.1` or `0.0.0.0`, so `0.0.0.0` is a first-class, code-validated production option — not a misconfiguration.

**Contrast with the gRPC layer**, which enforces mTLS + certificate pinning when `client_verification = true`: [4](#0-3) [5](#0-4) 

The JSON-RPC server has no equivalent guard.

**Attack path — CPFP fee-wallet drainage:**

1. Attacker creates a syntactically valid Bitcoin transaction spending their own UTXOs with a deliberately low fee rate and broadcasts it to the Bitcoin network (it enters the mempool).
2. Attacker calls `send_tx` on the unauthenticated JSON-RPC endpoint, supplying the transaction hex and `fee_paying_type = CPFP`. [6](#0-5) 

3. The tx-sender stores the entry in its DB queue via `insert_try_to_send`: [7](#0-6) 

4. On the next poll cycle the tx-sender sees the transaction in the mempool with insufficient fees and creates a CPFP child transaction spending from the operator's fee wallet to bump it.
5. The attacker repeats steps 1–4 with fresh UTXOs, each iteration consuming fee-wallet funds.

**Secondary impact — queue poisoning via `cancel_outpoints`:**

The attacker can also supply `cancel_outpoints` pointing to outpoints that are inputs of legitimate bridge transactions already in the queue. If the attacker's injected transaction confirms on-chain (spending their own UTXOs), the tx-sender marks those outpoints as cancelled, silently dropping the legitimate bridge transaction from the queue. [8](#0-7) 

---

### Impact Explanation

The tx-sender fee wallet is a **tx-sender-managed balance** explicitly listed in the allowed impact gate. Draining it prevents the tx-sender from fee-bumping kickoff, challenge-timeout, reimburse, and ready-to-reimburse transactions. Stuck transactions mean:

- Operators cannot claim reimbursement UTXOs within the timelock window → **operator collateral at risk of slashing**.
- Challenge-timeout transactions fail to confirm → **watchtower challenges go unanswered** → operator funds slashable.
- Bridge liveness fails for all in-flight deposits/withdrawals.

---

### Likelihood Explanation

- The JSON-RPC feature is production-ready: it has its own `main.rs`, `run.sh` smoke-test script, and standalone `TxSenderConfig`.
- `TX_SENDER_JSONRPC_BIND=0.0.0.0` is a code-validated option. Operators running the tx-sender on a shared host or behind a load balancer are likely to use it.
- The attack requires no privileged keys, no internal network access, and no cryptographic break — only HTTP reachability to the JSON-RPC port.

---

### Recommendation

Add an authentication layer to `start_jsonrpc_server` before registering any method. Options in increasing strength:

1. **Static bearer token** — require a secret header on every request; reject without it.
2. **IP allowlist** — accept connections only from the operator's own gRPC clients.
3. **mTLS** — mirror the gRPC `OnlyAggregatorAndSelf` pattern; require a pinned client certificate.

The fix must be at the code level inside `start_jsonrpc_server`; relying on firewall rules alone is insufficient because the code currently validates and accepts `0.0.0.0` as a legitimate bind address.

---

    tx_sender_client: TxSenderClient,
    bind_addr: SocketAddr,
) -> Result<TxSenderJsonRpcServer, BridgeError> {
    let server: Server = ServerBuilder::default()
        .max_request_body_size(MAX_JSONRPC_REQUEST_BODY_SIZE)
        .build(bind_addr)
        .await
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let local_addr = server
        .local_addr()
        .map_err(|e| BridgeError::Eyre(e.into()))?;

    let mut module = RpcModule::new(tx_sender_client.clone());
    module
        .register_async_method("send_tx", |params, client, _| async move {
            let req: InsertTryToSendParams = params.one().map_err(jsonrpc_err)?;

            let raw_tx = hex::decode(&req.signed_tx_hex).map_err(jsonrpc_err)?;
            let signed_tx: Transaction = consensus::deserialize(&raw_tx).map_err(jsonrpc_err)?;

            let mut dbtx = client.db.begin_transaction().await.map_err(jsonrpc_err)?;

            let try_to_send_id = client
                .insert_try_to_send(
                    &mut dbtx,
                    req.tx_metadata,
                    &signed_tx,
                    req.fee_paying_type,
                    req.rbf_signing_info,
                    &req.cancel_outpoints,
                    &req.cancel_txids,
                    &req.activate_txids,
                    &req.activate_outpoints,
                )
                .await
                .map_err(jsonrpc_err)?;

            client
                .db
                .commit_transaction(dbtx)
                .await
                .map_err(jsonrpc_err)?;

            Ok::<u32, ErrorObjectOwned>(try_to_send_id)
        })
        .map_err(|e| BridgeError::Eyre(e.into()))?;

fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}

    }
