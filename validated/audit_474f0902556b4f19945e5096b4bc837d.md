## Title
Path-traversal via crafted file names bypasses repository boundary check in `revealInFileManager`/"Open with Default Program" flows - ([File: app/src/lib/app-shell.ts])

### Summary
GitHub Desktop has a helper, `resolveWithin` in [1](#0-0) , that is specifically designed to join a repository-relative path to the repo root and reject the result if it resolves outside the root (including symlink escapes, via `realpath`). This guard is correctly applied in security-sensitive flows such as writing Copilot-generated conflict resolutions to disk: [2](#0-1)  and when reading conflicted files: [3](#0-2) , as well as when opening a file path that originates from a deep-link URL action: [4](#0-3) .

However, the far more commonly used function `revealInFileManager`, which is invoked from numerous UI surfaces on file paths that originate from git-tracked content (working directory changes, commit diffs, and pull-request "Files changed" listings), does **not** use `resolveWithin` — it simply does a raw `Path.join`:

```
export function revealInFileManager(repository: Repository, path: string) {
  const fullyQualifiedFilePath = Path.join(repository.path, path)
  return shell.showItemInFolder(fullyQualifiedFilePath)
}
``` [5](#0-4) 

The same unguarded `Path.join`/`join` pattern is repeated for the "Open with Default Program" and "Open in External Editor" actions across the codebase, e.g.: [6](#0-5) , [7](#0-6) , [8](#0-7) , and [9](#0-8) .

### Finding Description
The broken invariant is: *any file path that is displayed to the user as "belonging to the repository" and passed to a shell-opening primitive must be constrained to remain inside the repository root* — exactly the invariant `resolveWithin` was built to enforce, and exactly the invariant that is enforced for Copilot-written files and deep-link filepaths, but not for `revealInFileManager` / `openFile` on `WorkingDirectoryFileChange.path` and `CommittedFileChange.path`.

`file.path` values reach these call sites from git status/diff parsing of a cloned/fetched/checked-out repository — i.e., attacker-controlled content once a user clones a malicious repo, opens a malicious pull request's "Files changed" view, or performs a rebase/merge that reports a conflicted file with a crafted name. On Windows, `Path.join`/`Path.normalize` treat backslash (`\`) as a directory separator, while a valid Git tree entry name is only restricted from containing a literal `/` — a backslash is a perfectly legal character in a Git blob path on POSIX-created repositories. A malicious commit can therefore contain a tracked file named something like:
```
..\..\..\..\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup\evil.exe
```
This is a single, valid tree entry as far as core Git is concerned (no `/`), so it clones/fetches/checks out without any error. When Desktop later constructs `Path.join(repository.path, file.path)` on Windows, the backslashes are reinterpreted as directory separators, walking the resulting path outside `repository.path`, exactly the class of bug that historically affected Git/Git-for-Windows/GitHub Desktop (backslash path-traversal in tree entries).

None of the call sites listed above perform the `resolveWithin` check that exists in the codebase for this exact purpose; they only check `pathExists`/`isSafeFileExtension`, neither of which prevents traversal.

### Impact Explanation
If the resolved path escapes the repository directory, `shell.showItemInFolder` reveals an arbitrary file on the user's disk, and — more seriously — `OpenWithDefaultProgramLabel` (`openFile` → `shell.openExternal('file://' + fullPath)`) will execute/open whatever file the traversal lands on with its associated default program. Combined with a writable location the attacker can predict (e.g., escaping into the user's Startup folder if a file is later dropped/copied there, or targeting an existing sensitive file for disclosure via "reveal"), this satisfies the impact bar of "file read outside the repo" / "code execution", triggered purely by opening a maliciously crafted, already-cloned/fetched repository or a poisoned pull request's file list — no local access, admin rights, or social engineering beyond normal repository/PR review workflow is required.

### Likelihood Explanation
Medium: it requires the victim to clone/fetch a malicious repository (or view a malicious PR's file list) and then explicitly right-click → "Reveal in Finder/Explorer" or "Open with Default Program" on the crafted entry, which is a normal, expected user action when reviewing files. It is Windows-specific due to reliance on backslash-as-separator semantics in `Path.join`/`Path.normalize`, narrowing the affected platform but not the fundamental missing-check pattern (macOS/Linux realistically block `/`-based traversal at the Git object level, but the code has no defense-in-depth check regardless).

### Recommendation
Apply the existing `resolveWithin` (or `resolveWithinWin32`) helper in `app/src/lib/app-shell.ts`'s `revealInFileManager`, and in every other call site currently doing a bare `Path.join`/`join` on a git-derived `file.path` before passing it to `shell.showItemInFolder`, `shell.openExternal`, or an external editor launcher — mirroring the guard already implemented in `_writeCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7233`) and `buildConflictContext` (`app/src/lib/copilot-conflict-context.ts:390-407`). Reject and no-op (with a log message) when the resolved path is outside the repository root.

### Proof of Concept
1. On Windows, create a Git repository containing a tracked blob named `..\\..\\..\\..\\Desktop\\evil.exe` (a single tree-entry name containing backslashes — valid for Git, which only forbids `/`).
2. Have the victim clone this repository, or open a pull request that includes this file in "Files changed," in GitHub Desktop.
3. In the Changes list / Files-changed pane / commit history, right-click the file and choose "Show in Explorer" or "Open with Default Program".
4. `Path.join(repository.path, file.path)` (in `app/src/lib/app-shell.ts:62` or the equivalent sites in `pull-request-files-changed.tsx`/`selected-commits.tsx`) resolves the backslash segments as directory separators on Windows, escaping the repository directory and revealing/opening a file/location outside the intended repo root — unlike the `resolveWithin`-guarded flows, this path is never rejected.
