## Finding [1](#0-0) 

### Title
Vetoing the latest EVM state commitment resets the height floor to a hardcoded `1` instead of the last known-good height, letting a stale consensus proof re-become "latest" - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.sol` and the Substrate `pallet-ismp` host implement the same protocol operation — deleting/vetoing a fraudulent state-machine commitment — but diverge in how they restore the "latest height" bookkeeping afterward. The Substrate host correctly rolls the latest pointer back to the actual previously-recorded height (`PreviousStateMachineHeight`). The EVM host instead hardcodes the rollback to the constant `1`, discarding all memory of how far the chain had legitimately progressed. This is the same class of bug as the reported `OracleAdapterV4` issue: one implementation of a "distrust/recovery" state transition preserves correct prior state, the other collapses to an unrelated, permissive default.

### Finding Description
`delete_state_commitment` in `modules/pallets/ismp/src/host.rs` restores the actual previous height: [2](#0-1) 

The EVM equivalent, `deleteStateMachineCommitmentInternal`, instead does:

```solidity
if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
    _latestStateMachineHeight[height.stateMachineId] = 1;
}
``` [3](#0-2) 

This value feeds directly into the only height-monotonicity guard in the permissionless consensus-update path, `HandlerV2.handleConsensus`:

```solidity
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    ...
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
``` [4](#0-3) 

Once a fisherman vetoes the currently-latest commitment for a counterparty state machine that has already advanced far (e.g. height 1,000,000), the floor collapses to `1`. Any subsequently-submitted, cryptographically valid consensus proof (any historical/superseded finalized header is still capable of producing a valid finality proof from the underlying consensus client, since `IConsensusV2.verify` only checks proof validity against the trusted consensus state, not against Hyperbridge's own bookkeeping) whose intermediate height is merely `> 1` will pass the guard and be written via `storeStateMachineCommitment`, which unconditionally overwrites `_stateCommitments[id][height]` and sets it as the new `_latestStateMachineHeight`. This effectively erases the height-monotonicity protection the veto mechanism is supposed to preserve, because the "previous known good" boundary information (unlike the Substrate host) is not retained anywhere on the EVM side.

### Impact Explanation
This breaks the "false remote state must never become trusted" invariant on the EVM host: once any veto has occurred against the latest commitment of a state machine, the protection against re-accepting an old/superseded state as canonical is reduced to almost nothing (any height `> 1`), rather than being bounded by the last legitimate progress point as intended (and as correctly implemented on Substrate). A stale state commitment becoming "latest" again can be leveraged to reintroduce request/response state roots that let already-superseded or previously-unusable proofs (e.g., for requests/timeouts) pass the state-commitment lookups used throughout `HandlerV2` (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`), which all trust whatever is currently stored at `stateMachineCommitment(height)`.

### Likelihood Explanation
Triggering it only requires: (1) a state machine that has advanced well beyond height 1, (2) a legitimate veto of its current latest commitment (an expected, permissionless fisherman action per protocol design), and (3) any permissionless relayer subsequently calling `handleConsensus` with a valid consensus proof for a low/old height. No malicious relayer, prover, or admin collusion is needed — `handleConsensus` and the veto path are both explicitly permissionless entry points in this codebase.

### Recommendation
Mirror the Substrate host's behavior: track a `_previousStateMachineHeight` mapping in `EvmHost.sol`, updated every time `storeStateMachineCommitment` advances `_latestStateMachineHeight`, and have `deleteStateMachineCommitmentInternal` reset the latest height to that previous value instead of the hardcoded `1`.

### Proof of Concept
1. State machine `X` has commitments up to height `H = 1_000_000`, `_latestStateMachineHeight[X] = 1_000_000`.
2. A fisherman correctly vetoes height `1_000_000` via `deleteStateMachineCommitment`; `_latestStateMachineHeight[X]` becomes `1` per [3](#0-2) .
3. Any relayer calls `HandlerV2.handleConsensus` with a consensus proof containing an intermediate state for `X` at height `500_000` (a header that is old/superseded on Hyperbridge but still yields a valid finality proof from the consensus client).
4. The guard `intermediate.height (500_000) > latestHeight (1)` passes, `storeStateMachineCommitment` is called, and `_latestStateMachineHeight[X]` becomes `500_000` — silently reintroducing an old state as canonical, well below what had already legitimately been achieved and independent of the actual pre-veto progress, which the Substrate host's `PreviousStateMachineHeight` mechanism is designed to prevent.

    /**
     * @dev Delete the state commitment at given state height.

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
