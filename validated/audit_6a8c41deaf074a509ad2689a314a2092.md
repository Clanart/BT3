## Title
Division by zero in `KIP71Config.NextMagmaBlockBaseFee` via governance-settable `GasTarget=0` — ([File: params/kip71_config.go])

### Summary
The KIP-71 dynamic base-fee formula divides by the governance parameter `GasTarget` without checking it is non-zero. The governance module's format checker for `Kip71GasTarget` is a no-op that accepts any `uint64`, including `0`. If governance votes `GasTarget = 0` into effect, the very next block's base-fee computation (`NextMagmaBlockBaseFee`, invoked both when proposing/sealing a block and when every node verifies the header via `VerifyMagmaHeader`) performs `big.Int.Div(x, 0)`, which panics at runtime on every node in the network.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` computes the base-fee delta using `gasTarget` as a divisor twice, once for the "gas used above target" branch and once for "gas used below target": [1](#0-0) 

`gasTarget` comes straight from `kc.GasTarget` with no zero-check (unlike `BaseFeeDenominator`, which explicitly falls back to `64` when zero): [2](#0-1) 

The governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker`, meaning any `uint64` value — including `0` — passes validation when a vote is proposed: [3](#0-2) 

The header vote-consistency checker (`checkConsistency`) also does not special-case `Kip71GasTarget`; it falls into the generic passthrough branch that returns `nil` without additional validation, unlike `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` which do have bound checks: [4](#0-3) 

The existing test suite for vote validity explicitly exercises "bad" `Kip71GasTarget` values (wrong types, `false`/`true`), but never tests/rejects `uint64(0)`, confirming zero is accepted by the current format checker: [5](#0-4) 

Once `GasTarget=0` becomes effective (after being voted in and passing an epoch boundary per Kaia's header-vote governance mechanism), `NextMagmaBlockBaseFee` is called by every node in the network to compute or verify the next block's `BaseFee` (via `VerifyMagmaHeader`, and by block builders through `ToKip71Config()` consumers in `blockchain/block_validator.go`, `blockchain/tx_pool.go`, `work/worker.go`, `node/cn/gasprice/*`). As soon as a block's `parentGasUsed != 0` (i.e., any non-empty block), the `else if parentGasUsed > gasTarget` branch is taken with `gasTarget = 0`, and `x.Div(x, new(big.Int).SetUint64(gasTarget))` panics with a division-by-zero runtime error, because Go's `math/big.Int.Div` panics when the divisor is zero.

### Impact Explanation
This is a consensus-critical panic reachable by all full nodes, not merely a single malicious node: any node that proposes a block, verifies a header, estimates gas price, or builds a block after `GasTarget=0` takes effect will crash. This effectively halts the entire network (a network-wide denial of service / chain halt), which is a High severity impact analogous to the original TFLite division-by-zero DoS, but with network-wide blast radius rather than a single inference crash.

### Likelihood Explanation
Governance-parameter changes are an explicitly in-scope reachable path per the assessment rules. The bug requires a validator/council vote to set `Kip71GasTarget` to `0`, which is accepted by the current format-checker code with no validation, and is not caught by `checkConsistency`. This could occur via a compromised/malicious governing node in single mode, a council majority vote in ballot mode, or an operator mistake (fat-finger/config error), since nothing in the code path prevents it. Given the total absence of a zero-check (contrasted with the `BaseFeeDenominator` field which does have one), this is a plausible, low-effort trigger once a qualifying vote is cast.

### Recommendation
Add a zero-check for `GasTarget` analogous to the existing `BaseFeeDenominator` fallback in `NextMagmaBlockBaseFee`, and/or add an explicit `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `0` (as is already done via `FormatChecker` for `Kip71BaseFeeDenominator`). Consider also adding a `checkConsistency` case for `gov.Kip71GasTarget` in `kaiax/gov/headergov/impl/header.go` mirroring the bound checks used for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`.

### Proof of Concept
1. A validator/governing node casts (and gets committed) a vote setting `kip71.gastarget = 0` (passes `NewVoteData` since `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, and passes `checkConsistency` since there's no specific validation branch for it).
2. Once this vote takes effect at the next epoch/param-set update, `ParamSet.GasTarget = 0` and `KIP71Config.GasTarget = 0` for subsequent blocks.
3. On the following block where `parentGasUsed != 0` (virtually any block with transactions), `NextMagmaBlockBaseFee` executes:
   ```go
   gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // gasTarget = 0
   x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
   y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // Div by zero -> panic
   ```
   This is invoked both by block proposers (in `work/worker.go` block assembly) and by every node validating the header (`VerifyMagmaHeader` in `params/kip71_config.go`), causing a crash/panic on all nodes processing that block.
