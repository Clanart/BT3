## Finding: Stale event-checkpoint (`prevEventsLen`) in `BalanceHandler` causes double-application of balance deltas to the EVM StateDB on nested/recursive precompile calls

### Summary
The Morpho `_update` bug is a class of "stale checkpoint" bug: a snapshot value (`checkpoint.balance`) is captured once and only refreshed on specific entry points (`deposit`/`withdraw`), so any state-changing path that bypasses those entry points (a plain ERC20 `transfer`) leaves the checkpoint out of sync with the real balance. The same *architectural pattern* — snapshot-a-cursor-then-replay-from-it — exists in Cosmos EVM's precompile balance-synchronization mechanism, `BalanceHandler`, and it is reachable by nested/recursive precompile invocations within a single EVM transaction.

### Finding Description
Every stateful precompile (`erc20`, `werc20`, `bank`, `distribution`, `staking`, `gov`, `slashing`, `ics20`) executes through `Precompile.RunNativeAction` → `runNativeAction`: [1](#0-0) 

For each call, a `BalanceHandler` is used to reconcile the Cosmos SDK bank-module events emitted during the call with the EVM `StateDB`'s balance ledger: [2](#0-1) [3](#0-2) 

`BeforeBalanceChange` records `prevEventsLen` — a **checkpoint** of how many bank events already existed in the context. `AfterBalanceChange` replays every event *since that checkpoint* (`events[bh.prevEventsLen:]`) into `stateDB.AddBalance`/`SubBalance`.

This checkpoint is only valid for a *single, non-nested* precompile call. If a precompile call recursively triggers another precompile call before returning (e.g., an EVM sub-call back into a precompile, or a registered ERC20 token's transfer hook invoking a precompile such as `distribution.claimRewards` — exactly the pattern seen in the repo's own test fixtures `ERC20RecursiveNonRevertingPrecompileCall.sol` / `ERC20RecursiveRevertingPrecompileCall.sol`), the inner call's own `BeforeBalanceChange`/`AfterBalanceChange` pair will already consume and apply the bank events generated during the inner call. When control returns to the outer call and its `AfterBalanceChange` runs, it replays `events[outerPrevEventsLen:]`, which still includes the events already consumed and applied by the inner call, because the outer checkpoint was captured *before* the inner call executed. The result is that the same bank-module balance delta gets applied to the `StateDB` twice (once by the inner handler, once again by the outer handler), producing an EVM balance that is higher (or lower, for `CoinSpent`) than the true bank-keeper-tracked balance.

This exact class of bug — recursive precompile calls corrupting `BalanceHandler` bookkeeping and desynchronizing bank keeper vs. EVM `StateDB` balances — is already reproduced by an internal regression test: [4](#0-3) [5](#0-4) 

Because `AddBalance`/`SubBalance` on `StateDB` are pure ledger mutations tracked in the journal and committed to the multi-store, any double-application persists into consensus state once the block commits.

### Impact Explanation
If exploitable via a production, unprivileged call path (e.g. a malicious ERC20 contract registered as a token pair whose transfer hooks re-enter a native precompile such as `distribution`, `staking`, or `bank`, mirroring the repo's own `ERC20RecursiveNonRevertingPrecompileCall.sol` test contract), an attacker could cause the EVM-visible balance of an address to diverge from — and exceed — its true bank-module balance. Since `StateDB` balances back `eth_getBalance`, EVM value transfers, and are committed via `x/vm` keeper's account state, this is an unauthorized duplication/corruption of spendable EVM balance versus the native bank ledger, matching the "Critical unauthorized … duplication … corruption of spendable user value across native balances … EVM balances" impact category. It could also cause AppHash divergence between nodes if the resulting mismatched state is not deterministically reproduced identically across validators (this would need further verification, since gas cost / event ordering should be deterministic, but the desynchronization itself is a determinism-relevant consensus-state corruption).

### Likelihood Explanation
The precondition — an EVM contract call that re-enters a native precompile before an outer precompile call's `AfterBalanceChange` fires — requires a specific but plausible pattern: a registered "native ERC20" token pair whose OpenZeppelin-style transfer hooks (`_beforeTokenTransfer`/`_update`) call a Cosmos EVM precompile (distribution, staking, etc.), triggered from inside another precompile's execution (e.g. `x/erc20`'s `ConvertERC20`/`ConvertCoin` flows call into the ERC20 contract via `CallEVM`, and that same call chain can, in principle, be invoked from within a precompile's own native action). The repository's own test suite (`ERC20RecursiveNonRevertingPrecompileCall.sol`, `ERC20RecursiveRevertingPrecompileCall.sol`, and `balance_handler_test.go`) demonstrates the team is aware recursive precompile invocation is a reachable pattern and has already reproduced balance desync from it, indicating a realistic likelihood, though I was not able to fully trace a concrete top-level, purely-unprivileged transaction that nests two *production* (non-debug) precompile `Run()` calls within the exact same call stack before I ran out of investigation budget — this should be verified further (e.g., whether `x/erc20`'s `CallEVM`-invoked ERC20 hook path can be reached from *inside* an already-active `RunNativeAction`/`BalanceHandler` scope, rather than only from the top-level message-server path which has no outer handler).

### Recommendation
Make the event-checkpoint stack-aware instead of a single mutable cursor per handler instance:
- Track a stack of checkpoints (or use event indices that are only consumed once, e.g. mark/remove processed events, or use a monotonically-increasing global cursor shared across the whole EVM call rather than per-precompile-call snapshots) so that nested/recursive precompile invocations cannot cause the same event to be replayed into `StateDB.AddBalance`/`SubBalance` by more than one handler.
- Alternatively, disallow/short-circuit balance-affecting precompile calls from being invoked reentrantly within another precompile's `BalanceHandler` scope, or merge nested handler scopes into the outer one instead of creating independent overlapping checkpoints.

### Proof of Concept
The repository already contains a working reproduction of the exact double-application mechanism via recursive precompile calls: [6](#0-5) 
This test deploys a caller contract that recursively invokes a (test/debug) precompile and asserts on the resulting event counts; a production analog would substitute the debug precompile with a real precompile call reachable from a malicious registered ERC20 token's transfer hook (as prototyped in `ERC20RecursiveNonRevertingPrecompileCall.sol`) to produce a real EVM-balance/bank-balance divergence rather than just a debug event count. Further work is needed to confirm a concrete unprivileged top-level transaction that nests two *production* precompile calls sharing overlapping `BalanceHandler` event ranges before this should be treated as confirmed-exploitable.

// It records the current number of events in the context to later process balance changes
