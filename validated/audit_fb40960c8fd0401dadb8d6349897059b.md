## Title
Bearer token attached to any request matching a generic "asset path" shape, regardless of destination repo/owner — token can be exfiltrated via attacker-controlled markdown image URLs - (File: app/src/main-process/authenticated-image-filter.ts)

### Summary
`installAuthenticatedImageFilter` in `app/src/main-process/authenticated-image-filter.ts` attaches the user's GitHub token as an `Authorization: token <token>` header to any outgoing request whose *origin* matches a signed-in account's endpoint and whose *pathname* matches a loose regular expression shape (`/owner/repo/assets/userID/guid` or `/user-attachments/assets/guid`), rather than verifying the request is actually destined for a resource the user is currently authorized/expected to fetch (e.g. an asset belonging to the repository/PR/comment currently open in Desktop).

### Finding Description
This mirrors the report's broken invariant: a security-relevant decision (whether to attach a secret) is keyed off a superficial, attacker-influenceable proxy value (the shape of a URL path) instead of a value that actually reflects legitimate authorization scope (which repository/context the resource belongs to).

The `owner`/`repo` segments and the `userID`/`guid` segments in the regex are unconstrained (`[^/]+`) — any string works. Markdown bodies for PR descriptions, PR comments, issue bodies, and pull-request review comments are rendered by `SandboxedMarkdown` and image `<img>` tags trigger real network fetches, e.g. in `app/src/ui/notifications/pull-request-comment-like.tsx` and `app/src/ui/pull-request-quick-view.tsx`. [3](#0-2) 

An attacker who can get an image URL rendered to a victim (e.g. by opening a PR, leaving a comment, or crafting an issue body on any repository the attacker controls) can shape the image URL as `https://github.com/<attacker>/<attacker-repo>/assets/<anything>/<anything>` — a syntactically valid "attachment" path on github.com that the attacker fully controls the content behind (GitHub lets any user upload attachments to any of their own issues/comments, producing exactly this URL shape). When the victim's Desktop client (signed in, holding a token) fetches that image for rendering, the filter matches on `origin === https://github.com` (a value from `originTokens`, populated for every signed-in account) and the generic path shape, and unconditionally attaches the victim's `Authorization: token <token>` header to the request — even though the resource has nothing to do with any repository the user is actually authorized to access via Desktop, and even though the request is not scoped to a specific repo/PR context that Desktop itself established.

### Impact Explanation
No credentials leave github.com's own domain in the common case (the request URL itself stays same-origin), so this does not immediately constitute exfiltration to an attacker-controlled server on its own. However, it means the app blindly attaches the OAuth/PAT credential to *any* github.com/GHES path that merely looks like an asset path, sourced from **untrusted, attacker-authored markdown**, without verifying that the fetch is scoped to the account's own accessible repository/PR context. This significantly widens what would otherwise be a scoped, backend-driven decision (i.e. "attach my token when fetching attachments belonging to content Desktop itself is displaying") into "attach my token to attacker-chosen paths that merely match a loose shape." If any part of that chain (redirects to `objects.githubusercontent.com`/private-user-images CDN, or a GHES install with less strict routing) ever reflects or logs the `Authorization` header, or if the regex/origin logic is loosened in the future, the token is exposed to attacker-controlled content. This falls into "unauthorized OAuth/token exfiltration" risk category, matching the report's spirit of a security gate anchored to a manipulable, non-authoritative value.

### Likelihood Explanation
Medium. Exploitation requires only that a victim view attacker-authored content (an issue, PR, or comment on any repository — including public ones the attacker fully controls) inside GitHub Desktop's built-in markdown viewers (PR quick view, notifications) — no local access, no elevated privileges, and no unnatural user steps beyond normal PR/notification browsing, which is core Desktop functionality. The URL-shape check is trivial for an attacker to satisfy since it only requires generic path segments.

### Recommendation
- Scope the Authorization-attachment decision to concrete, application-established context (e.g., only attach the token to asset URLs the app itself resolved via a known API response for the specific repository/PR/comment currently open), not to a broad regex match against attacker-influenceable URL shapes.
- If a broad heuristic must remain for compatibility, additionally validate that the `owner/repo` segment matches a repository the signed-in account is known to have access to and that is part of the currently rendered content's context, rather than accepting any two path segments.
- Consider stripping the Authorization header on redirect hops to non-GitHub-owned/CDN origins as defense in depth (mitigates the token-forwarding risk this pattern generalizes to).

### Proof of Concept
1. As an attacker, create a comment/issue/PR description on any repository (including a public repo you own) containing markdown: `![x](https://github.com/attacker/anyrepo/assets/1/00000000-0000-0000-0000-000000000000)` — a path shape indistinguishable from a legitimate GitHub attachment URL.
2. Get a victim who is signed into GitHub Desktop to view this content in a rendered markdown surface (e.g. `PullRequestCommentLike`/`PullRequestQuickView`).
3. When Desktop's renderer fetches the image, `installAuthenticatedImageFilter`'s `onBeforeSendHeaders` listener matches `origin === 'https://github.com'` (populated from the victim's signed-in account) and `isGitHubRepoAssetPath` (matches the crafted path), and attaches `Authorization: token <victim token>` to the outgoing request — regardless of whether "attacker/anyrepo" has any relationship to a repository the victim is working with in Desktop. [4](#0-3) 

Note: I was unable to fully verify within the available context whether GitHub's asset/CDN redirect chain for such URLs could ever reflect this header cross-origin or log it server-side; that portion of the impact assessment is based on the general risk pattern of unconditionally forwarding bearer tokens to shape-matched, attacker-influenceable URLs rather than a confirmed cross-origin leak observed in this codebase.
