### Title
Unsafe conditional `approve()` in bribe-fee-to-BNB conversion breaks with USDT-like non-zero-to-non-zero allowance restrictions - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager._approveTokenIfNeeded` uses a raw, unguarded `IERC20(token).approve(_to, type(uint256).max)` call gated only by an `allowance < _amount` check, with no reset-to-zero step. This is the exact anti-pattern flagged in the referenced report (D3Funding.sol): tokens like USDT revert on `approve()` when the current allowance is non-zero and the new value is also non-zero.

### Finding Description
`_approveTokenIfNeeded` is used by `_swapFeesForBnb`, which loops over bribe reward tokens collected from voting and swaps protocol-fee portions to BNB via `PancakeZapper`: [1](#0-0) [2](#0-1) 

The guard only re-approves when `allowance(address(this), _to) < _amount`. On the first call for a given token this transitions allowance `0 -> max`, which is safe. However, as the zapper consumes the allowance over subsequent swaps, the allowance decreases from `max` but does not necessarily hit exactly `0`; it can land on any non-zero remainder. If a later `_amount` exceeds that non-zero remainder, `_approveTokenIfNeeded` will call `approve(_to, type(uint256).max)` again while the current allowance is still non-zero. For USDT (and similar tokens enforcing the "must approve 0 first" restriction), this `approve()` call reverts, because it is a plain `.approve()` and not routed through `SafeERC20.safeApprove` (which itself would also revert on non-zero→non-zero, just with a clearer error) — either way the call fails.

Since `rewardTokens[i][j]` is populated dynamically from third-party bribe tokens registered against pools (`IWombatBribe(bribesContract).rewardTokens()`), any bribe token can be USDT, and the code even flags this itself with the inline comment `// Should replace with safeApprove?` at line 469, indicating the developers were aware this was unresolved.

### Impact Explanation
Because `_swapFeesForBnb` iterates over all bribe reward tokens in a single loop and a revert in any single token's approve call reverts the entire outer transaction, one problematic USDT-denominated (or similarly restrictive) bribe token can permanently block fee-to-BNB conversion for that voting/bribe-claim batch. Since the allowance state that causes the revert persists on-chain (it can only be fixed by an explicit `approve(..., 0)` which this contract never issues), the condition is not self-healing and will recur on every subsequent call touching that token, causing an indefinite freeze of the bribe fee/BNB conversion flow and the yield tied to it.

### Likelihood Explanation
This function is reachable through the ordinary, unprivileged bribe/vote-fee-collection flow (any account triggering vote processing that includes bribe fee amounts) — no privileged role is required to reach `_swapFeesForBnb`/`_approveTokenIfNeeded`. The only precondition is that a listed bribe reward token behaves like USDT (reverts on non-zero→non-zero approval) and that the zapper's actual consumption of the approved allowance across calls leaves a non-zero remainder smaller than a later requested amount — a state reachable through normal, repeated usage over time without any adversarial input.

### Recommendation
Replace the raw `approve()` in `_approveTokenIfNeeded` with a reset-then-approve pattern using OpenZeppelin's `SafeERC20`:
```solidity
IERC20(token).safeApprove(_to, 0);
IERC20(token).safeApprove(_to, type(uint256).max);
```
or use `safeIncreaseAllowance`/`forceApprove` (OZ v4.8+) to safely handle tokens with USDT's approval restriction.

### Proof of Concept
1. A bribe reward token `T` behaving like USDT is registered against a pool via `IWombatBribe`.
2. `_swapFeesForBnb` is invoked (via the normal vote/fee flow) with `feeAmounts[i][j] = X`; allowance for `T` to `PancakeZapper` is `0`, so `_approveTokenIfNeeded` sets it to `type(uint256).max` — succeeds.
3. `PancakeZapper.zapInToken` consumes part of the allowance, leaving it at some non-zero value `R < max`.
4. On a later call, `feeAmounts[i][j] = Y > R`. `_approveTokenIfNeeded` sees `allowance (R) < Y` and calls `approve(_to, type(uint256).max)` while `allowance == R != 0` — USDT reverts this call, reverting the entire `_swapFeesForBnb` transaction and blocking fee/BNB conversion for token `T` from that point forward.     function _swapFeesForBnb(address[][] memory rewardTokens, uint256[][] memory feeAmounts)
        internal
        returns (uint256 bnbAmount)
    {
        if(PancakeZapper == address(0)) revert PancakeZapperNotSet();
        uint256 bribeLength = rewardTokens.length;
        for (uint256 i; i < bribeLength; i++) {
            uint256 rewardLength = rewardTokens[i].length;
            for (uint256 j; j < rewardLength; j++) {
                if (rewardTokens[i][j] != address(0) && feeAmounts[i][j] > 0) {
                    _approveTokenIfNeeded(rewardTokens[i][j], PancakeZapper, feeAmounts[i][j]);
                    bnbAmount += IBNBZapper(PancakeZapper).zapInToken(
                        rewardTokens[i][j],
                        feeAmounts[i][j],
                        0,
                        msg.sender
                    );
                }
            }
        }
    }
