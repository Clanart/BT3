### Title
Panic in `AlgorithmSignatureMachine::complete` when an included participant's share is missing — remote crash DoS - (File: crypto/frost/src/sign.rs)

### Summary
`AlgorithmSignatureMachine::complete` indexes `responses[l]` for every participant `l` in `self.view.included()`, but `responses` is populated only from `self.share` plus whatever keys exist in the caller-supplied `shares` map. If `validate_map` (crypto/frost/src/lib.rs) only checks that share keys are a subset of `included` and exclude `i` — rather than requiring full coverage — then a participant who sent a preprocess (and is therefore in `included`) but withholds their signature share causes an unconditional indexing panic. Any participant in a FROST signing session can thus crash the node performing `complete`, matching the availability-only DoS class of CVE-2019-2584 (hang/crash of the server via a reachable operation).

### Finding Description
In `complete` (sign.rs:447–495):

- `responses` is built from `self.share` and `shares.drain()` (sign.rs:454–460).
- On the failure path — which occurs whenever the aggregated share sum doesn't verify, e.g. precisely when a share is missing and another share can't compensate — the code iterates `for l in self.view.included()` and evaluates `responses[l]` (sign.rs:475–479). A missing key panics via HashMap `Index` (`index out of bounds`/`no entry found`).
- `included` is fixed at `sign` time from the preprocess keys (sign.rs:290–295), so it contains participants who may never submit a share in round two.

The panic path is only reached when `self.params.algorithm.verify(...)` fails on the summed shares (sign.rs:465) — i.e., exactly the case where a share is absent or invalid — so a silent or malicious-but-crashing participant reliably triggers it.

### Impact Explanation
A single participant in a signing set can abort the whole process running `complete` with a panic rather than a `FrostError`, denying signature production / halting the signing pipeline. This is a reachable availability fault triggered purely by message-level behavior (omitting a share), matching the report's "complete DOS" bug class.

### Likelihood Explanation
Withholding a round-two share is trivial for any legitimate participant (crash, disconnect, or malice); no cryptographic work is required. The only precondition is that `validate_map` permits a `shares` map smaller than `included \ {i}` — which the interface suggests, since it takes the shares and the included set as separate arguments and validates membership rather than completeness. Note: I did not confirm `validate_map`'s body; if it enforces exact key-set equality, the panic is unreachable through this path and this finding should be downgraded.

### Recommendation
Replace `responses[l]` with a lookup returning an error (`responses.get(&l).ok_or(FrostError::InvalidShare(*l))?` or a dedicated `MissingShare` variant), and/or require in `validate_map`/`complete` that `shares.len() == included.len() - 1` before use.

### Proof of Concept
1. Set up `ThresholdParams` t=2, n=3; run `preprocess` for participants 1, 2, 3.
2. Participant 1 calls `sign` with preprocesses from 2 and 3 → `included = [1,2,3]`.
3. Participant 3 never submits a share. Call `complete` with `shares = {2: share_2}`.
4. Aggregate `sum` fails verification → blame path iterates `included`; `responses[3]` panics.
