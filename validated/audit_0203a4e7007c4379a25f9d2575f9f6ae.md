### Title
CW20↔ERC20 pointer/bridge trusts EVM call success and ignores the ERC20 `bool` return value on `transfer`/`transferFrom` - (File: `x/evm/client/wasm/query.go`, `contracts/src/CW20ERC20Pointer.sol`)

### Summary
The reported bug class is: an ERC20 `transfer`/`transferFrom` call can return `false` (instead of reverting) on failure, and a caller that only checks "did the call not revert" (rather than decoding the returned boolean) will treat a failed transfer as successful. In sei-chain, the CW20↔ERC20 pointer/bridge machinery follows exactly this pattern when bridging tokens between CosmWasm and the EVM.

### Finding Description
`EVMQueryHandler.HandleERC20TransferPayload` and `HandleERC20TransferFromPayload` in [1](#0-0)  ABI-encode a standard ERC20 `transfer(address,uint256)` / `transferFrom(address,address,uint256)` call for an arbitrary target ERC20 contract address supplied by the CosmWasm caller: [2](#0-1) 

This encoded payload is consumed by CosmWasm contracts (e.g. the example CW20 pointer contract) which submit it as an `EvmMsg::DelegateCallEvm` to the underlying ERC20 contract: [3](#0-2) 

Neither the query-handler path nor the contract-side usage decodes and checks the ABI-encoded `bool` return value from the target ERC20's `transfer`/`transferFrom`. As with the Solidity analog in the report, if the EVM call to the underlying ERC20 does not revert but returns `false` (a known "weird-erc20" no-revert-on-failure behavior), the delegatecall/message will be treated as successful by the bridging layer (the EVM call itself succeeds at the opcode level), and the CosmWasm side will record the transfer as completed even though the tokens never moved.

The same "only check `success`, never check the semantic return value" pattern also appears in the reverse direction, in the CW20→ERC20 pointer contract's `_execute` helper, which only asserts that the low-level `delegatecall` did not revert: [4](#0-3) 

By contrast, the native-token ERC20 wrapper explicitly checks a boolean success flag returned by the bank precompile before proceeding, showing that the codebase is aware of this class of bug in some but not all pointer/bridge paths: [5](#0-4) 

### Impact Explanation
If the ERC20 contract targeted by an `HandleERC20TransferPayload`/`HandleERC20TransferFromPayload`-generated call is a non-compliant ("weird") ERC20 that returns `false` rather than reverting on transfer failure (e.g., due to insufficient balance/allowance edge cases, paused state, blacklists, etc.), the CosmWasm bridging contract will believe the transfer succeeded (since the EVM call did not revert) and update its own accounting/state accordingly, while the actual ERC20 balance is unchanged. This results in permanent desynchronization between the CW20 side's ledger and the real ERC20 balances, causing fund loss/lockup for the affected user, matching the "concrete fund loss or permanent freezing" bar in the validation criteria.

### Likelihood Explanation
This is reachable by any public-RPC/CosmWasm user who deploys or interacts with a CW20 pointer/bridge that wraps an EVM ERC20 token of their choosing, since the target contract address is caller-supplied. No privileged access is required — a malicious or oddly-behaved ERC20 contract that returns `false` on failure is sufficient to trigger the desync.

### Recommendation
Wherever the codebase acts on the result of an ERC20 `transfer`/`transferFrom` call issued through the pointer/bridge machinery (both the Go-side payload construction/consumption and the Solidity `CW20ERC20Pointer.sol`/pointer contracts), decode the ABI-encoded return value and require it to be `true`, not merely that the underlying call did not revert — mirroring what `NativeSeiTokensERC20._update` already does for the bank precompile path.

### Proof of Concept
1. Deploy (or point a CW20-ERC20 bridging contract at) a non-standard ERC20 token whose `transfer`/`transferFrom` returns `false` on failure instead of reverting (a "weird-erc20" no-revert-on-failure token).
2. From CosmWasm, call the bridge contract's transfer entrypoint that uses `HandleERC20TransferPayload`/`HandleERC20TransferFromPayload` to build the calldata and dispatches it via `EvmMsg::DelegateCallEvm` (as in `contract.rs`).
3. Trigger a failure condition on the target ERC20 (e.g., insufficient balance) such that it returns `false` rather than reverting.
4. Observe that the EVM call completes without reverting, so the CosmWasm side treats the transfer as successful and updates its state/emits success events, while the target ERC20 balance is unchanged — leaving the bridged accounting permanently out of sync with actual token balances.

Note: I was unable to fully trace and confirm the exact Go handler that executes `EvmMsg::DelegateCallEvm` messages emitted by CosmWasm contracts (to verify whether it decodes the ERC20 boolean return value) due to tool-call limits; the analysis above is based on the confirmed payload-construction code and the confirmed pattern in `CW20ERC20Pointer.sol`/`NativeSeiTokensERC20.sol`.

```go
func (h *EVMQueryHandler) HandleERC20TransferPayload(ctx sdk.Context, recipient string, amount *sdk.Int) ([]byte, error) {
	abi, err := native.NativeMetaData.GetAbi()
	if err != nil {
		return nil, err
	}
	evmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(recipient))
	if !found {
		return nil, types.NewAssociationMissingErr(recipient)
	}
	bz, err := abi.Pack("transfer", evmAddr, amount.BigInt())
	if err != nil {
		return nil, err
	}
	res := bindings.ERCPayloadResponse{EncodedPayload: base64.StdEncoding.EncodeToString(bz)}
	return json.Marshal(res)
}
```

```go
func (h *EVMQueryHandler) HandleERC20TransferFromPayload(ctx sdk.Context, owner string, recipient string, amount *sdk.Int) ([]byte, error) {
	abi, err := native.NativeMetaData.GetAbi()
	if err != nil {
		return nil, err
	}
	ownerEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(owner))
	if !found {
		return nil, types.NewAssociationMissingErr(owner)
	}
	recipientEvmAddr, found := h.k.GetEVMAddress(ctx, sdk.MustAccAddressFromBech32(recipient))
	if !found {
		return nil, types.NewAssociationMissingErr(recipient)
	}
	bz, err := abi.Pack("transferFrom", ownerEvmAddr, recipientEvmAddr, amount.BigInt())
	if err != nil {
		return nil, err
	}
	res := bindings.ERCPayloadResponse{EncodedPayload: base64.StdEncoding.EncodeToString(bz)}
	return json.Marshal(res)
}
```

```rust
fn transfer(
    deps: DepsMut<EvmQueryWrapper>,
    _env: Env,
    info: MessageInfo,
    recipient: String,
    amount: Uint128,
) -> Result<Response<EvmMsg>, ContractError> {
    deps.api.addr_validate(&recipient)?;

    let erc_addr = ERC20_ADDRESS.load(deps.storage)?;

    let querier = EvmQuerier::new(&deps.querier);
    let payload = querier.erc20_transfer_payload(recipient.clone(), amount)?;
    let msg = EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload };
    let res = Response::new()
        .add_attribute("from", info.sender)
        .add_attribute("to", recipient)
        .add_attribute("amount", amount)
        .add_message(msg);

    Ok(res)
}
```
