### Title
Instant, non-vested reward accrual in `BaseRewardPool.queueNewRewards` allows flash-loaned deposit to steal yield from long-term stakers - (File: `wombat/ArbWomUp3.sol` scope / `rewards/BaseRewardPool.sol`, `rewards/MasterMagpie.sol`)

### Summary
`BaseRewardPool._provisionReward` applies the entire queued reward to `rewardPerTokenStored` instantly, weighted only by `totalStaked()` at the exact moment `queueNewRewards` is called, with no time-based streaming/vesting. An attacker can deposit a large flash-loaned amount of the staking token via `MasterMagpie.deposit` immediately before a reward manager's `queueNewRewards` call, then withdraw right after, capturing a proportional share of the reward despite zero effective holding duration and diluting the share earned by genuine long-term stakers.

### Finding Description
`MasterMagpie.deposit` → `_deposit` transfers the staking token into `MasterMagpie` and increases `user.amount`/`user.available` before any reward is queued: [1](#0-0) . Because `BaseRewardPool.totalStaked()` and `balanceOf(_account)` read live balances from `MasterMagpie` (`IERC20(stakingToken).balanceOf(operator)` and `IMasterMagpie(operator).stakingInfo`), the attacker's flash-loaned balance is immediately reflected: [2](#0-1) .

When the reward manager subsequently calls `queueNewRewards`, `_provisionReward` computes `rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / totalStaked()` using the current (attacker-inflated) `totalStaked()`, applying the reward in one lump-sum step with no vesting duration: [3](#0-2) .

The attacker then calls `MasterMagpie.withdraw`, which routes through `_harvestAndUnstake` → `_harvestBaseRewarder` → `BaseRewardPool.getReward`, computing `earned()` as `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid) / scale`: [4](#0-3)  and [5](#0-4) . Since the attacker's `userRewardPerTokenPaid` was set to the pre-bump value at deposit time (via the `_harvestBaseRewarder` call inside `_deposit`, which runs before `user.amount` increases), the attacker earns a full proportional share of the just-queued reward for the entire deposited amount despite holding it for zero elapsed time.

Existing guards do not prevent this: `nonReentrant` on `deposit`/`withdraw` only blocks reentrancy within a single call, not sequential same-block transactions; there is no cooldown, minimum stake duration, or reward-streaming/vesting mechanism (unlike typical Synthetix-style `rewardRate`/`rewardsDuration` designs) that would time-weight the distribution. `onlyManager` on `queueNewRewards` prevents an attacker from calling it directly, but does not prevent them from opportunistically sandwiching a legitimate manager's call.

### Impact Explanation
This results in theft of unclaimed yield from long-term stakers: the reward pool is fixed at `_amountReward`, but because the denominator `totalStaked()` is inflated by the attacker's flash-loaned balance at the exact block of `queueNewRewards`, and the attacker's own share (`largeAmount * delta / scale`) is paid to them, real stakers who held tokens over the actual accrual period receive proportionally less than they should. This matches the "theft of unclaimed yield" Immunefi impact class.

### Likelihood Explanation
The precondition is that `queueNewRewards` is a known/observable transaction (many protocols run reward funding on a predictable schedule via a bot, or the call is visible in the public mempool and can be front-run/back-run). The attacker needs capital to flash-loan/borrow a large amount of the LP/staking token relative to `totalStaked()` — for illiquid pools with modest TVL this can be inexpensive relative to the reward being queued, making the attack repeatable every time a reward manager funds rewards. No privileged role is required; only public `deposit`/`withdraw` calls are used.

### Recommendation
Change reward distribution from instantaneous lump-sum application to a time-weighted streaming model (e.g., Synthetix-style `rewardRate` accrued linearly over a `rewardsDuration`), so that a deposit made just before/after a `queueNewRewards` call can only capture a vanishingly small fraction of rewards proportional to the time actually staked, not the full instantaneous bump. Alternatively, enforce a minimum staking duration or exclude balance changes within the same block as `queueNewRewards` from the reward-per-token snapshot used for accrual.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, a staking token (mock LP), and a `BaseRewardPool` with a reward token; register a `rewardManager`.
2. Have a long-term staker `alice` deposit `100e18` staking tokens via `MasterMagpie.deposit` and let time pass (irrelevant since accrual is instant, but establishes baseline).
3. In a single test transaction sequence (simulating same block):
   a. Attacker flash-borrows `1_000_000e18` staking tokens (mock via `deal`/mint) and calls `MasterMagpie.deposit(stakingToken, 1_000_000e18)`.
   b. `rewardManager` calls `BaseRewardPool.queueNewRewards(rewardAmount, rewardToken)`.
   c. Attacker calls `MasterMagpie.withdraw(stakingToken, 1_000_000e18)`, triggering `getReward` internally.
4. Assert `IERC20(rewardToken).balanceOf(attacker) > 0` despite the attacker's stake duration being 0 blocks/seconds.
5. Assert `alice`'s subsequently claimable reward (`allEarned`/`pendingTokens`) is measurably less than it would have been had the attacker not injected the flash deposit (compute expected reward without attacker's deposit as `rewardAmount * aliceBalance / aliceBalanceAlone` vs. actual `rewardAmount * aliceBalance / (aliceBalance + attackerFlashAmount)`), confirming dilution/theft of yield.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
