### Title
`ThresholdKeys::read` accepts identity verification shares, yielding an attacker-known/identity group key - (File: crypto/dkg/src/lib.rs)

### Summary
The external bug class is a validation list that enumerates dangerous values but omits an equivalent degenerate case (`0.0.0.0` ≡ localhost bypassing the private-IP deny list). The analog in Serai is the split between two point-deserialization paths: `Curve::read_G` rejects the identity point, but `Ciphersuite::read_G` — used by `ThresholdKeys::read` — does not. `ThresholdKeys::read` feeds untrusted bytes through `C::read_G` (the `Ciphersuite` impl) into `verification_shares`, and `ThresholdKeys::new` validates only the count and index bounds of those shares, never that they are non-identity or that the supplied `secret_share` is consistent with `verification_shares[i]`. A crafted blob therefore yields `ThresholdKeys` whose `group_key` is the identity (or another attacker-known key), while the holder believes it controls a secure threshold key.

### Finding Description
`ThresholdKeys::read` at `crypto/dkg/src/lib.rs:574` reads `t`, `n`, `i`, the interpolation blob, a `secret_share` scalar, and then `n` verification shares via `<C as Ciphersuite>::read_G(reader)` (lines 620–623). `Ciphersuite::read_G` (`crypto/ciphersuite/src/lib.rs:91-101`) enforces only canonical encoding — identity encodes canonically and is accepted. The stricter `Curve::read_G` (`crypto/frost/src/curve/mod.rs:125-131`), which adds an `is_identity` rejection, is not used here because `dkg` is generic over `Ciphersuite`, not `Curve`. `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:349-391`) checks `verification_shares.len() == n` and `participant <= n`, then computes `group_key = Σ_{i=1..=t} verification_shares[i] * λ_i` with no identity check and no consistency check between `secret_share` and `verification_shares[i]`. This mirrors the advisory: the deny/validation list covers bounds, duplicates (in `view`), and canonicality, but misses the degenerate element that is the group-theoretic equivalent of `0.0.0.0`.

### Impact Explanation
An attacker who supplies the serialized `ThresholdKeys` blob (explicitly in-scope per the reachability rules) can set every verification share in positions `1..=t` to the identity, making `group_key()` return the identity — a public key whose discrete log is 0, so any signature under it is trivially forgeable by anyone (any `(R, s)` with `s·G = R + c·0` verifies). Equivalently, the attacker can set all shares to values they interpolate (e.g., `verification_shares[i] = G·k_i` for known `k_i`, and `secret_share` = a known scalar), so the resulting `group_key` corresponds to a fully attacker-known secret. Anything the downstream system treats as secured by this multisig — Serai validator keys, Bitcoin outputs to the group key — is actually spendable by the attacker. This produces "funds reported received that are not spendable [by the honest set]" and signatures that appear valid under the returned `group_key` while being reproducible by the attacker.

### Likelihood Explanation
Exploitation requires the victim to deserialize attacker-controlled bytes via `ThresholdKeys::read` — e.g., key import/recovery flows or reading key material delivered by an untrusted party — which the scope rules explicitly designate as untrusted input. Within that path the bypass is deterministic: no race, no probabilistic condition, just substituting identity encodings where only canonicality is checked — exactly like substituting `0.0.0.0` for `127.0.0.1`. Caveat I could not fully verify: whether production Serai code paths feed network-supplied bytes into `ThresholdKeys::read` (keys are normally produced locally by PedPoP), so the severity depends on an integrator or recovery flow exposing this reader to untrusted data.

### Recommendation
- In `ThresholdKeys::read`/`ThresholdKeys::new` (`crypto/dkg/src/lib.rs`), reject identity points in `verification_shares` and reject a resulting `group_key` that `is_identity()`.
- Verify consistency: `C::generator() * secret_share == verification_shares[&params.i()]` after interpolation-independent scaling checks.
- Consider routing deserialization through a stricter point-reader (the `is_identity` check already present in `Curve::read_G`) or adding a `Ciphersuite::read_G_and_verify`-style helper, mirroring the advisory's suggestion to enumerate the full special-value registry rather than patching one case.

### Proof of Concept
1. Choose `n = t` and any `i ∈ 1..=n`. Serialize a `ThresholdKeys` blob for `C = Ristretto`: `C::ID` length + ID, `t`, `n`, `i` (LE u16s), interpolation tag `1` (Lagrange), then `secret_share = 0` (32 zero bytes — canonical), then `n` copies of the 32-byte canonical identity encoding.
2. `ThresholdKeys::<Ristretto>::read(&mut blob)` returns `Ok`, because `Ciphersuite::read_G` accepts the canonical identity and `ThresholdKeys::new` performs no identity/consistency check.
3. `keys.group_key()` is the identity point. Any `(R, s)` with `s·G = R` verifies against it via `SchnorrSignature::verify` — the attacker needs no secret and never needed the victim's share; the victim's "threshold key" protects nothing.
