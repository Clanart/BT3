### Title
Gasless bundle-tx expiry uses wall-clock time while swap validity uses block.timestamp, allowing eviction/validity desync of bundled approve+swap transactions - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The gasless module tracks bundled `approve`+`swap` transaction pairs using two independent timing mechanisms, analogous to the cvgControlTower/veCVG desync: (1) the `swap.deadline` field is validated against `block.timestamp` (`g.Chain.CurrentBlock().Time()`), which only advances when a new block is produced, and (2) the `knownTxs` bundle bookkeeping (`QueueTimeout`, `PendingTimeout`, `KnownTxTimeout`) is evicted purely by real wall-clock `time.Now()`-based durations. These two clocks can diverge arbitrarily depending on block production cadence, causing the bundle-tracking state to become inconsistent with the on-chain validity window it is meant to protect.

### Finding Description
`checkBalanceForSwap` enforces the swap's deadline against the current block's timestamp: [1](#0-0) 

Meanwhile, the bundle lifecycle (`PreAddTx`, `IsReady`, `PreReset`) tracks and evicts the paired approve/swap transactions using `knownTxs`, whose expiry is computed from real elapsed wall-clock time via `elapsedPromotedOrAddedTime()`, `elapsedPromotedTime()`, and `elapsedAddedTime()`, compared to fixed `time.Duration` constants: [2](#0-1) [3](#0-2) 

This is the same class of bug as the veCVG report: one subsystem (bundle admission/eviction) is clocked by wall-time elapsing independent of chain progress, while the other subsystem (swap validity) is clocked by `block.timestamp`, which is discrete and only advances on block production and can lag or race arbitrarily far from real time (e.g., during network stalls, slow block times, or a burst of rapid blocks). Because `PreAddTx` blocks re-submission of a "known" bundle tx for `KnownTxTimeout` (30s) based on real time, and `PreReset` drops queued/pending bundle txs from the pool after `QueueTimeout`/`PendingTimeout` (10s) also based on real time, a bundle tx can be:
- Evicted from the pool by the wall-clock timeout while its `deadline` (checked against `block.timestamp`) is still valid, or
- Retained/blocked from resubmission in `knownTxs` for up to `KnownTxTimeout` even though the block-timestamp-based deadline check would have already rejected/accepted it differently, creating windows where a bundle appears "known" (blocking honest resubmission via `ErrUnableToAddKnownBundleTx`) purely due to wall-clock drift unrelated to the chain's actual block-time progress.

The root cause mirrors the report precisely: the two logical states of the same lifecycle object (the bundle transaction validity vs. its pool bookkeeping) are measured with two different, drifting clocks.

### Impact Explanation
The mismatch can cause a denial-of-service on legitimate gasless users: a valid, non-expired (per `block.timestamp`) bundle transaction pair can be silently dropped from the pool by the wall-clock-based `QueueTimeout`/`PendingTimeout` in `PreReset` if block production stalls, or conversely a resubmission attempt of a still-relevant bundle can be rejected via `ErrUnableToAddKnownBundleTx` for up to `KnownTxTimeout` even though on-chain state (approvals, balances) has already changed, silently blocking the gasless (fee-delegated) flow that end users rely on to pay gas. This causes loss of intended gasless transaction execution/service availability for the affected user without any way to force resolution except waiting for the wall-clock window to expire, independent of actual chain activity — directly impacting the gasless module reachable by any public transaction sender.

### Likelihood Explanation
This is reachable by any unprivileged sender submitting standard `approve`+`swapForGas` bundle transactions through the public RPC/tx pool — no special privileges are required. The divergence is triggered purely by normal operational conditions (variable block times, network stalls, or bursts of blocks), which are common on production networks, making the desync condition realistically triggerable rather than a purely theoretical edge case.

### Recommendation
Use a single consistent time source for both the swap deadline check and the bundle admission/eviction bookkeeping. Either: (a) validate `swap.deadline` using real wall-clock time consistently with `knownTxs` timeouts, or (b) rebase `QueueTimeout`/`PendingTimeout`/`KnownTxTimeout` on block-number or block-timestamp progression (e.g., a fixed number of blocks) so that pool bookkeeping expiry tracks the same clock as the on-chain deadline enforcement in `checkBalanceForSwap`.

### Proof of Concept
1. A user submits a valid `approve` + `swapForGas` bundle with `deadline = now + 300s`.
2. `PreAddTx` records both txs in `knownTxs` with status `TxStatusQueue`/`TxStatusPending` (bookkeeping keyed to wall-clock `time.Now()`).
3. Block production stalls for >10s (network congestion, consensus delay) but `block.timestamp` of the latest block is still well below `deadline`, so `checkBalanceForSwap` at [1](#0-0)  would still accept the swap as valid.
4. `PreReset` (invoked on any pool reset during this stall) computes `knownTx.elapsedAddedTime() >= QueueTimeout` using wall-clock elapsed time and drops the still block-timestamp-valid bundle tx from the pool at [3](#0-2) .
5. The user's legitimate, still-valid (per chain time) gasless transaction is dropped, and any resubmission attempt within `KnownTxTimeout` (30s wall-clock) is rejected via `ErrUnableToAddKnownBundleTx` in `PreAddTx` at [4](#0-3) , denying the user gasless service despite the transaction remaining valid by the chain's own timestamp-based rule.

var (
	QueueTimeout   = 10 * time.Second // bundle tx is removed from txpool.queue after QueueTimeout
	PendingTimeout = 10 * time.Second // bundle tx is removed from txpool.pending after PendingTimeout
	KnownTxTimeout = 30 * time.Second // bundle tx is removed from knownTxs after KnownTxTimeout
)

func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}

// PreReset removes timed out tx from the tx pool and knownTxs.
func (g *GaslessModule) PreReset(oldHead, newHead *types.Header) []common.Hash {
	g.knownTxsMu.Lock()
	defer g.knownTxsMu.Unlock()

	drops := make([]common.Hash, 0)

	for hash, knownTx := range *g.knownTxs {
		// remove pending timed out tx from tx pool
		if knownTx.status == TxStatusPending && knownTx.elapsedPromotedTime() >= PendingTimeout {
			drops = append(drops, hash)
		}
		// remove queue timed out tx from tx pool
		if knownTx.status == TxStatusQueue && knownTx.elapsedAddedTime() >= QueueTimeout {
			drops = append(drops, hash)
		}
		// remove known timed out tx from knownTxs
		if knownTx.elapsedPromotedOrAddedTime() >= KnownTxTimeout {
			g.knownTxs.delete(hash)
		}
	}

	return drops
}
