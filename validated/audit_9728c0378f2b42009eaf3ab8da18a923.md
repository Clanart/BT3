Post-mint failure in `x/erc20` ICS20 middleware `OnRecvPacket` returns an error acknowledgement after the underlying transfer already credited funds, enabling duplicated cross-chain value - (File: `x/erc20/ibc_middleware.go`, `x/erc20/keeper/ibc_callbacks.go`)

### Summary
`IBCMiddleware.OnRecvPacket` runs the standard ICS20 transfer callback first (which unescrows/mints the voucher coin into the recipient's bank balance and returns a *success* acknowledgement), and only afterwards invokes `erc20.Keeper.OnRecvPacket` to auto-convert that coin into its ERC20 representation. If the conversion step fails, an **error acknowledgement** is returned even though the underlying coin transfer has already been committed to the same, non-cached `ctx`. Because IBC only rolls back state when a module observes failure *before* mutating state (the safe pattern is a `ctx.CacheContext()` + conditional `writeFn()`, which this very codebase uses in `x/ibc/callbacks/keeper/keeper.go`), the erc20 middleware's late failure does not undo the transfer module's already-committed balance credit. The sending chain, upon receiving the error ack, will refund/unescrow the sender's original amount — resulting in the same value existing on both chains simultaneously.

### Finding Description [1](#0-0) 
`IBCMiddleware.OnRecvPacket` first calls `im.Module.OnRecvPacket(ctx, ...)` (the standard ICS-20 transfer app), which performs the unescrow/mint of the voucher coin to the recipient directly on `ctx` and returns a success acknowledgement. Only if that succeeds does it call `im.keeper.OnRecvPacket(ctx, packet, ack)` using the **same** context — no cache-context isolation is applied around this second stage. [2](#0-1) 
Inside `Keeper.OnRecvPacket`, for the "native ERC20 token" case, after the transfer module has already credited the coin to `recipient`, the code calls `k.MintingEnabled` and `k.ConvertCoinNativeERC20` (which escrows the just-received coin into the erc20 module account, then calls the ERC20 contract's `transfer` from the module address to the recipient, and finally burns the escrowed coin). If either call fails — e.g., `ConvertCoinNativeERC20`'s EVM `transfer` call reverts because the erc20 module account does not hold enough escrowed ERC20 tokens for this denom (a normal balance-availability condition, not a privileged assumption) — the function returns `channeltypes.NewErrorAcknowledgement(err)`.

At this point:
1. The recipient already has the bank coin balance from the (already-committed) transfer module state change.
2. An error acknowledgement is written back to the source chain.
3. The source chain, seeing the error ack, refunds/unescrows the original sender's tokens as if the packet had never been delivered.
4. Net effect: the same value now exists both as a credited coin balance on the receiving chain and as a refunded balance on the sending chain — a duplication of spendable value across chains.

This mirrors the Lock.sol/BondNFT bug class conceptually (a downstream step can silently/erroneously fail after an upstream transfer has already been committed, corrupting the intended all-or-nothing accounting), but the concrete Cosmos EVM manifestation is worse than "stuck funds": it is a duplication/double-crediting of user value across two chains via the IBC escrow/acknowledgement mechanism, matching the "unauthorized duplication ... across ... IBC escrows" critical impact category.

Note: I was not able to fully verify, within the available tooling, whether the current `ibc-go v10` core `RecvPacket` handling in this dependency wraps application callback execution in an implicit cache-context that would nullify this path (i.e., whether IBC core itself discards state mutations when the final acknowledgement is an error). The codebase's own callback keeper (`x/ibc/callbacks/keeper/keeper.go`) explicitly implements manual `ctx.CacheContext()` / `writeFn()` isolation for post-processing callbacks, which strongly suggests that IBC core does **not** provide this rollback automatically and that middleware authors are expected to isolate their own side effects — which `x/erc20/keeper/ibc_callbacks.go`'s `OnRecvPacket` does not do for the native-ERC20 path.

### Impact Explanation
If confirmed reachable (i.e., IBC core does not roll back the already-committed transfer-module state when `erc20.Keeper.OnRecvPacket` returns an error ack), this results in duplication of spendable user value across chains — new coins on the receiving chain plus a refund on the sending chain for the same nominal transfer. This fits the "Critical unauthorized minting, burning, duplication ... of spendable user value across native balances ... IBC escrows" impact category.

### Likelihood Explanation
The trigger condition — `ConvertCoinNativeERC20` (or `MintingEnabled`) failing after the underlying ICS20 transfer has already succeeded — is plausible under ordinary conditions with an unprivileged actor: e.g., insufficient ERC20 balance escrowed under the erc20 module account for a "native ERC20" token pair returning from a counterparty chain, or an ERC20 contract that reverts the `transfer` call (e.g., paused token, blacklist enforcement on the recipient). No privileged access is required to cause this failure to occur; it only requires a legitimate but partially-degenerate state (mismatched escrow, blocked recipient, etc.).

### Recommendation
Wrap the erc20-specific conversion logic in `x/erc20/keeper/ibc_callbacks.go`'s `OnRecvPacket` (and in the composing `IBCMiddleware.OnRecvPacket`) in a `ctx.CacheContext()`, applying `writeFn()` only when the conversion succeeds, mirroring the pattern already used in `x/ibc/callbacks/keeper/keeper.go`. If the conversion fails, the acknowledgement should either (a) still report success while leaving the recipient with the un-converted bank coin (the documented fallback behavior already stated in the function's own doc comment — "If conversion fails, then the user will receive the bank token instead" — but which is *not* actually what the code does, since it returns an error ack instead of the original success ack), or (b) if an error ack must be returned, the underlying transfer's mint/unescrow must be reverted in the same atomic operation. Given the doc comment's stated intent contradicts the actual returned acknowledgement type, this is very likely an existing logic bug worth an explicit fix: change lines 134 and 138 in `x/erc20/keeper/ibc_callbacks.go` to `return ack` (falling back to the bank coin, consistent with the documented behavior) instead of `channeltypes.NewErrorAcknowledgement(err)`.

### Proof of Concept
1. Register a "native ERC20" token pair for an ERC20 token `T` originally deployed on Chain A and escrow some `T` via `ConvertERC20`, so the amount currently held as escrowed ERC20 balance on the erc20 module account is `E`.
2. From Chain B, submit an ICS20 transfer that returns more than `E` worth of the IBC voucher denom for `T` back to Chain A (e.g., due to a prior partial send/receive mismatch or a token pair whose module escrow was already partially drained by a legitimate prior conversion).
3. On Chain A, `im.Module.OnRecvPacket` executes normally: the voucher coin is unescrowed/minted directly to the recipient's bank balance, and a success ack is produced.
4. `erc20.Keeper.OnRecvPacket` then attempts `ConvertCoinNativeERC20`, whose EVM `transfer` call from the module address to the recipient reverts because the module's ERC20 balance (`E`) is insufficient to cover the packet amount.
5. `k.ConvertCoinNativeERC20` returns an error; `OnRecvPacket` returns `channeltypes.NewErrorAcknowledgement(err)` at line 138 of `x/erc20/keeper/ibc_callbacks.go`.
6. Chain B, upon receiving the error acknowledgement, refunds/unescrows the original sender.
7. Result: the recipient on Chain A retains the bank-coin credit from step 3, and the sender on Chain B is separately refunded in step 6 — the same value now exists on both chains. [3](#0-2) [4](#0-3)

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
