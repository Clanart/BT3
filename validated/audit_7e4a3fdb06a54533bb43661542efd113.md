### Title
Balance-based sweep in `ManualCompound.compound` lets any caller steal leftover reward-token dust left by a prior user's `compound` call - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound` credits and routes reward tokens purely by reading `IERC20(_tokenAddress).balanceOf(address(this))` at lines 139-160, with no bookkeeping of what was actually harvested for the current caller versus dust already sitting in the contract. Any unprivileged address can call `compound` with empty `_lps`/`_rewards` arrays and sweep any pre-existing balance of a compoundable token (e.g., MGP dust left by another user's prior `lockFor` rounding/partial transfer) entirely to themselves.

### Finding Description
`compound` is `external` with no access restriction on the caller [1](#0-0) . It first calls `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)`. This call succeeds regardless of who the external caller is because MasterMagpie's `_onlyCompounder` modifier checks `msg.sender` from MasterMagpie's perspective, which is the `ManualCompound` contract itself (a registered compounder), not the original EOA [2](#0-1) . Passing empty `_lps`/`_rewards` arrays makes this a no-op claim.

The contract then loops over its configured `rewards` array and, for each token, computes `receivedBalance = IERC20(_tokenAddress).balanceOf(address(this))` and unconditionally routes the *entire* balance to `msg.sender` via convert/lock/helper-deposit/transfer [3](#0-2) . There is no snapshotting of the balance before `multiclaimOnBehalf` was called in this transaction, nor any per-user accounting — the code conflates "tokens just harvested for this caller" with "any token balance currently sitting in the contract." If a prior transaction (any other user's `compound` call) left a nonzero residual balance of a compoundable token — for example because `ILocker.lockFor` rounds down, reverts on dust amounts internally without reverting the whole call, or a helper/convertor doesn't consume 100% of the approved amount — that leftover balance persists in `ManualCompound` and is fully credited to the *next* caller of `compound`, even one who supplies empty `_lps`/`_rewards` and triggers zero real harvesting themselves.

No modifier, reentrancy guard, or reward-index/accounting mechanism in `ManualCompound` prevents this, since the sweep is keyed purely on `balanceOf`.

### Impact Explanation
This is a direct theft-of-funds vector under the Immunefi "Direct theft of user funds" class: an unrelated, unprivileged attacker can claim reward-token dust (e.g., MGP) that rightfully belongs to whichever prior user's harvested rewards produced it. While a single occurrence may be small ("dust"), the vulnerability is systemic — every `compound` call is a potential leak point, and an attacker can front-run/back-run other users' `compound` transactions or simply call `compound([],[],...)` repeatedly and immediately after each detected residual balance, converting the design flaw into a repeatable siphon of protocol reward tokens over time.

### Likelihood Explanation
Feasibility is high and capital-free: the attacker only needs to call the public `compound` function with empty arrays (no LP holdings, no staking, no special role) and gas money. Preconditions rely on the contract accumulating any non-zero residual balance of a compoundable token, which can arise from normal rounding in `lockFor`/converter/helper integrations, or partial harvest mismatches. This is a passive, always-monitorable opportunity (watch `balanceOf` on-chain) rather than a one-off exploit, making it realistically repeatable.

### Recommendation
Track amounts explicitly instead of relying on `balanceOf(address(this))` as the "received" amount: snapshot each reward token's balance immediately before calling `multiclaimOnBehalf` in the current transaction, and use `balanceOf-after - balanceOf-before` as `receivedBalance` for routing to `msg.sender`. Any pre-existing balance/dust should instead be handled via an explicit, owner-controlled sweep/rescue function (or accumulated into a tracked "unaccounted dust" bucket that is not attributable to any single caller), not auto-credited to whoever calls `compound` next.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `ManualCompound`, mock MGP token, and a mock `ILocker` implementation whose `lockFor` intentionally leaves 1 wei (or any nonzero amount) of MGP un-transferred/un-consumed in the caller (simulating rounding) — e.g., mock locker only pulls `amount - 1` via `transferFrom`.
2. User A stakes an LP token in MasterMagpie and accrues pending MGP reward.
3. User A calls `ManualCompound.compound([lp], [[MGP]], 0, 0, true)`. Assert: `multiclaimOnBehalf` transfers MGP into `ManualCompound`; the mock locker only locks `balance - 1`, leaving `1` wei of MGP balance stuck in `ManualCompound` after the call.
4. Attacker (unrelated EOA, no stake, no MGP) calls `ManualCompound.compound([], [], 0, 0, false)`.
5. Assert: `multiclaimOnBehalf` with empty arrays is a no-op (no reward pulled for attacker), yet the sweep loop at lines 139-159 reads `IERC20(MGP).balanceOf(address(this)) == 1`, and since no locker condition applies (`_lockMgp=false`), routes it via `safeTransfer(msg.sender, 1)` — the attacker's MGP balance increases by the dust amount that was rightfully User A's leftover.
6. Assert final state: `ManualCompound` MGP balance == 0, attacker MGP balance == 1 (or whatever dust amount), despite attacker never having harvested anything themselves — demonstrating the theft of another user's reward dust.
