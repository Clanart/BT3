### Title
DLEq verification ignores length mismatches, allowing forged equality proofs - ([File: crypto/dleq/src/lib.rs](crypto/dleq/src/lib.rs))

### Summary
`DLEqProof::verify` and `MultiDLEqProof::verify` detect malformed or incomplete proof inputs, but do not return the constructed errors. Verification then uses `zip`, silently truncating the longer input and validating only the matching prefix. An unprivileged prover can therefore submit a proof covering fewer public points than the verifier expects and have it accepted.

### Finding Description
`DLEqProof::verify` checks `generators.len() != points.len()`, but writes `Err(DLEqError::InvalidProof)?;` as an unused statement rather than returning an error. It then iterates with `generators.iter().zip(points)`, which stops at the shorter slice. [1](#0-0) 

`MultiDLEqProof::verify` repeats the same pattern for the top-level lengths, response length, and each inner series. [2](#0-1)  In each case, the Fiat-Shamir transcript is populated only for pairs consumed by `zip`, so omitted generators or points are not bound into the challenge.

### Impact Explanation
A caller asking to verify equality across multiple generators or discrete logarithms can receive success even though the submitted proof establishes only a prefix of the requested statements. For example, a proof generated for one `(generator, point)` pair can be accepted by a verifier that supplied two pairs; the second point may be arbitrary.

For `MultiDLEqProof`, an attacker can provide fewer `s` responses than required, or provide an inner point list shorter than its generator list, and still pass verification for the processed prefix. This is a forged-proof condition and can bypass downstream authentication/key-ownership logic relying on the proof to establish all supplied equalities.

### Likelihood Explanation
The malformed proof is fully controlled through public proof bytes via `DLEqProof::read` or `MultiDLEqProof` deserialization paths. [3](#0-2)  Exploitation does not require malicious validators, secret material, timing behavior, collusion, or an invalid curve/hash implementation. It succeeds whenever the verifier supplies more generators or points than the proof covers, or more expected proof series than `self.s` contains.

### Recommendation
Replace every non-returning `Err(...)?;` statement with an actual return, e.g. `return Err(DLEqError::InvalidProof);`. Verification must reject:

- `generators.len() != points.len()` in `DLEqProof::verify`
- `points.len() != generators.len()` or `self.s.len() != generators.len()` in `MultiDLEqProof::verify`
- any inner `points.len() != generators.len()`

Add regression tests proving that a valid proof for a proper prefix is rejected when additional generators, points, or expected proof series are supplied.

### Proof of Concept
For `DLEqProof`:

```rust
// Proof generated for exactly one discrete logarithm statement.
let proof = DLEqProof::prove(
  &mut OsRng,
  &mut transcript_for_one_statement,
  &[G0],
  &scalar,
);

// The verifier expects equality across two generators/points.
assert!(
  proof.verify(
    &mut transcript_for_two_statements,
    &[G0, G1],
    &[A0, arbitrary_point],
  ).is_ok()
);
```

Only `(G0, A0)` is consumed by `zip`; `G1` and `arbitrary_point` are ignored, while the challenge remains the one generated for the single processed pair.

For `MultiDLEqProof`, create a proof for `n` scalar series, then verify it against `n + 1` series. `self.s.len() != generators.len()` is detected but ignored, and `zip` validates only the first `n` series, causing the incomplete proof to be accepted.
