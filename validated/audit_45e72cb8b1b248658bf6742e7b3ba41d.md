### Title
Manipulated womMWomPool price causes `smartConvert` to revert, blocking `WombatStaking.withdraw` (and `deposit`/`depositLP`/`harvest`) - (File: wombat/WombatStaking.sol, wombat/SmartWomConvert.sol)

### Summary
`WombatStaking.withdraw` (and `deposit`, `depositLP`, `harvest`) unconditionally routes any harvested WOM reward through `_sendRewards`, which, when `isMWOM` fee is active and `smartWomConverter` is set, calls `IConverter(smartWomConverter).smartConvert(feeAmount, 0)`. `SmartWomConvert.smartConvert` hardcodes `_minRec = _amountIn`, requiring the mWOM/WOM buyback swap to return at least as much value as was put in. An attacker can trade against the `womMWomPool` Wombat pool to push its price so that a WOM→mWOM swap yields less than 1:1, causing `smartConvert` (and thus every `deposit`, `depositLP`, `withdraw`, and `harvest` call for that pool) to revert until the price is restored.

### Finding Description
`WombatStaking.withdraw` calls `_toMasterWomAndSendReward(_lpToken, _liquidity, false)` **before** performing the actual pool withdrawal: [1](#0-0) 

`_toMasterWomAndSendReward` harvests WOM rewards from `MasterWombat` and forwards them via `_sendRewards`: [2](#0-1) 

Inside `_sendRewards`, when the `isMWOM` fee is active and a `smartWomConverter` is configured, the fee-share of WOM is sent through `smartConvert`: [3](#0-2) 

`SmartWomConvert.smartConvert` computes a `convertRatio` (deposit vs. buyback via the AMM), then calls `_convertFor` with `_minRec` hardcoded to the full input amount: [4](#0-3) 

`_convertFor` reverts with `MinRecNotMatch` if `convertAmount + amountRec < _minRec`: [5](#0-4) 

`amountRec` is the output of `IWombatRouter.swapExactTokensForTokens` on the `womMWomPool`, an ordinary Wombat AMM pool whose price any market participant can move by swapping. If `currentRatio()` (mWOM priced in WOM) is below `buybackThreshold`, part of the fee is swapped through this pool rather than 1:1 deposited into mWOM: [6](#0-5) 

An attacker with only market-bought tokens can swap WOM for mWOM (or vice versa) on `womMWomPool` to depress the WOM→mWOM output below par. Since `_minRec = _amountIn` is a strict "no loss" requirement on an AMM swap that will normally incur slippage/price movement whenever `buybackAmount > 0`, the attacker only needs to nudge the pool price so `amountRec < amountToSwap`. This makes `smartConvert` revert, which propagates up through `_sendRewards` → `_toMasterWomAndSendReward` → `withdraw` (also `deposit`, `depositLP`, `harvest`), reverting the whole user transaction. Because the harvest/reward-conversion step happens unconditionally before the deposit/withdraw logic and there is no `try/catch` around `smartConvert`, there is no fallback path — the entire principal-affecting operation for that pool is blocked as long as the attacker keeps the pool price outside the acceptable range.

Neither `nonReentrant` nor `whenNotPaused` nor the `_onlyPoolHelper`/`_onlyActivePoolHelper` modifiers on `withdraw`/`deposit`/`depositLP` mitigate this — they only restrict which contract can call `WombatStaking`, not the harvest/convert path executed internally on every call.

### Impact Explanation
Any user attempting to `deposit`, `depositLP`, `withdraw`, or trigger `harvest` on a pool that (a) has WOM rewards accruing, (b) has the `isMWOM` fee active, and (c) has `smartWomConverter` set, will have their transaction revert whenever the `womMWomPool` price is outside the “no loss” band required by `smartConvert`. Since withdrawal is on this same code path, users cannot retrieve their principal (deposited LP/receipt tokens) while the manipulated price persists, meeting the "Temporary freezing of funds" impact class as long as the attacker sustains the unfavorable price (≥24 hours qualifies as High per the target's impact class).

### Likelihood Explanation
The precondition is that the pool accrues WOM rewards (harvested from `MasterWombat`) and that fee routing to mWOM is active with `smartWomConverter` set — a normal, expected production configuration for this protocol, not a misconfiguration. The attacker only needs capital to swap on the public `womMWomPool` AMM (no special privileges), and can repeat/sustain the manipulation (or front-run corrective arbitrage) to keep the price unfavorable for an extended window, blocking withdrawals for as long as they're willing to spend capital, which is a griefing-style DoS with real, quantifiable temporary freezing of user principal.

### Recommendation
Do not use a strict `_minRec = _amountIn` (zero-slippage) requirement for the internal buyback swap in `smartConvert`, since AMM swaps inherently have price impact/slippage. Either: (1) allow a configurable slippage tolerance for the internal conversion, (2) wrap the `smartConvert` call in `_sendRewards` with a `try/catch` so that a failed reward conversion does not block the underlying deposit/withdraw of principal (e.g., skip the mWOM conversion and send raw WOM, or skip fee distribution for that call), or (3) decouple reward harvesting/distribution from the principal deposit/withdraw path entirely so a reward-side failure cannot freeze user funds.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `WombatStaking`, `SmartWomConvert`, a mock `MasterWombat`, `womMWomPool` (real/mock Wombat pool for WOM/mWOM), and configure a pool with `isMWOM` fee active and `smartWomConverter` set to the deployed `SmartWomConvert`.
2. Have a user deposit into the pool via `WombatStaking.deposit`, accrue WOM rewards in `MasterWombat` for that pool (simulate harvest yielding `womRewards > 0`, with `feeAmount > 0` and `isPoolFeeFree` false).
3. As an unprivileged attacker, swap a sizeable amount on `womMWomPool` (WOM→mWOM or mWOM→WOM) to push `currentRatio()` below `buybackThreshold` and specifically make `amountRec` (output of the buyback swap `IWombatRouter.swapExactTokensForTokens`) fall below `amountToSwap`.
4. Call `WombatStakingPoolHelper.withdraw` (or `WombatStaking.withdraw` directly through the approved pool helper) as the original depositor.
5. Assert the transaction reverts with `MinRecNotMatch` (bubbled up from `SmartWomConvert._convertFor`), confirming the user cannot withdraw their principal while the pool price is manipulated.
6. As a differential check, verify that without the price manipulation (baseline run), the same `withdraw` call succeeds and `IERC20(poolInfo.lpAddress).balanceOf(address(this))` and receipt-token burn/mint accounting reconcile normally — establishing that the manipulated-price run diverges by fully blocking withdrawal instead.

    function smartConvert(uint256 _amountIn, uint256 _mode) external returns (uint256 obtainedmWomAmount) {
        if (_amountIn == 0) revert MustNoBeZero();

        uint256 convertRatio = DENOMINATOR;
        uint256 mWomToWom = currentRatio();

        if (mWomToWom < buybackThreshold) {
            uint256 maxSwap = maxSwapAmount();
            uint256 amountToSwap = _amountIn > maxSwap ? maxSwap : _amountIn;
            uint256 convertAmount = _amountIn - amountToSwap;
            convertRatio = convertAmount * DENOMINATOR / _amountIn;
        }

        return _convertFor(_amountIn, convertRatio, _amountIn, msg.sender, _mode);
    }
