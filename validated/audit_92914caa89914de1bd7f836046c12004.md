### Title
`Scanner::register_offset` collisions cause distinct deposits to share one address; the second depositor's funds are received but attributed to the first registration - ([File: networks/bitcoin/src/wallet/mod.rs])

### Summary
The bug class in the Cally report is a divergence between the nominal amount recorded at deposit time and the actual balance later claimed. In Serai's Bitcoin scanner, the analogous divergence is between the nominal offset a caller asked to register and the offset actually bound to a script. `register_offset` mutates the requested offset (`offset += Scalar::ONE`) until the tweaked key is even-Y, making offsets surjective rather than bijective: two distinct requested offsets can be served by the same script, or an already-claimed script can silently reject a later registration. An unprivileged depositor only ever sees a P2TR address; they cannot tell whether their offset collided with a previously registered one.

### Finding Description
`Scanner::register_offset` loops, incrementing the caller-supplied offset until `p2tr_script_buf` yields an even-Y tweaked key, then inserts `script -> offset` into `scripts`, returning `None` if the script is already present:

- networks/bitcoin/src/wallet/mod.rs:180-196 — `register_offset` mutates `offset` and dedupes on `script`, not on the requested offset.
- networks/bitcoin/src/wallet/mod.rs:185-191 — `p2tr_script_buf(self.key + GENERATOR * offset)`; on collision `None?` is returned.
- networks/bitcoin/src/wallet/mod.rs:199-213 — `scan_transaction` resolves outputs purely by `script_pubkey`, returning a `ReceivedOutput` carrying the *stored* offset.

Because `scan_transaction` keys on `script_pubkey` alone, when two logical deposits are assigned the same script (the second `register_offset` call returns `None`, but the address derived from the caller's requested offset is identical anyway since the tweaked key is the same), an output paying that script is attributed to whichever offset was stored first. The second depositor's payment produces a `ReceivedOutput` whose `offset` belongs to the first registration. Documentation at lines 174-178 acknowledges the surjectivity but leaves collision handling to the caller.

### Impact Explanation
Two distinct deposit instructions resolve to the same scan entry. One output can only be returned once by `scan_transaction`, so one of the two depositors has funds that are on-chain and controlled by the multisig key (offset-adjusted key is identical), yet their logical deposit is never credited — the funds are received under another offset's identity and are effectively unclaimable through the credited path, mirroring the Cally finding where accrued value exists in the contract but is unreachable by its rightful owner. Conversely, a single payment can satisfy whichever deposit is checked against that offset, enabling payment-reuse across instructions.

### Likelihood Explanation
Reachable by any unprivileged depositor: offsets are caller-flow-generated per deposit, and the parity-increment rule makes near-adjacent offsets collapse onto the same script with probability ~1/2 per odd result. An attacker cannot choose which existing offset to collide with unless they can influence offset generation, but any natural collision permanently wedges the affected deposits. Requires no malicious validator — only public deposit transactions.

### Recommendation
Make `register_offset` fail (or return a distinct error) whenever the *effective* tweaked key collides, and require callers to treat `None` as "address unusable — generate a new offset", never publishing the colliding address. Alternatively key `scripts` on the requested offset and store the resolved script, so duplicate scripts across distinct logical deposits are detectable and `scan_transaction` can disambiguate or reject ambiguous outputs.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs semantics
let mut scanner = Scanner::new(key).unwrap();

// Deposit A requests offset o where key + o*G is odd-Y.
// register_offset bumps it to o+1 (even) and stores script S -> o+1.
let used_a = scanner.register_offset(o).unwrap();   // returns o+1

// Deposit B legitimately requests offset o+1.
// p2tr_script_buf(key + (o+1)*G) produces the same script S.
let used_b = scanner.register_offset(o + 1);        // None — already registered

// The depositor for B is nevertheless told an address which encodes
// the identical tweaked key; their BTC output to S is scanned and
// returns a ReceivedOutput with offset == o+1, indistinguishable from
// a payment to A's deposit. Only one of the two deposits can be
// satisfied by that output; the other depositor's funds sit
// unspendable-via-crediting despite being on-chain.
```
