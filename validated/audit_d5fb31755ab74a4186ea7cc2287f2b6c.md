### Title
Fee estimated under `needed_fee`/`calculating_fee` can be lower than the fee `SignableTransaction::new` actually requires, causing transaction construction to fail and payments to be dropped — (`File: networks/bitcoin/src/wallet/send.rs`)

### Summary
The Smilee bug class is "the quoted/estimated amount is computed on a different basis than the amount actually charged at execution, so execution reverts." Serai's Bitcoin send pipeline has the same shape: `Bitcoin::make_signable_transaction` is invoked once with `calculating_fee = true` to obtain `needed_fee`, the processor amortizes that fee across a plan's payments, and later `signable_transaction` rebuilds the transaction expecting the amortized amounts to still cover the real fee. Two divergences exist between the estimate path and the execution path.

### Finding Description
1. In `make_signable_transaction`, when `calculating_fee` is set, every payment amount is replaced with `Self::DUST` (10_000 sats) before calling `BSignableTransaction::new` (`processor/src/networks/bitcoin.rs:433-444`). The comment claims "This won't affect the fee calculation", which holds for output *size* — but the flow then relies on the *returned* `needed_fee` matching what a later call with real amounts will require.

2. The real divergence is the fee rate itself: `median_fee(&block_for_fee)` is sampled inside `make_signable_transaction` from whatever `block_number` is passed (`processor/src/networks/bitcoin.rs:430-431`). `prepare_send` calls `needed_fee` at one block, amortizes `tx_fee` (plus operating costs) across the payments by decrementing `payment.balance.amount.0` (`processor/src/networks/mod.rs:480-495`), and the documented contract is that `signable_transaction` "MUST NOT return None if the above was done properly" (`processor/src/networks/mod.rs:402-404`). On a later attempt/block, `median_fee` can be higher, so `SignableTransaction::new` computes a larger `needed_fee` (`send.rs:206-227`) and the already-amortized payments no longer cover `payment_sat + needed_fee`, hitting `NotEnoughFunds` (`send.rs:215-221`), which `make_signable_transaction` maps to `Ok(None)` (`processor/src/networks/bitcoin.rs:458`) — violating the documented invariant.

3. There is also an internal estimate/execute asymmetry inside `SignableTransaction::new`: `needed_fee` is first computed for the transaction *without* a change output (`send.rs:204-206`), and the `NotEnoughFunds` check is performed against that lower fee (`send.rs:215`). Only afterwards is the change-aware fee `fee_with_change` computed (`send.rs:225-234`). The code happens to resolve this safely (no change output is emitted and the leftover is absorbed as fee), but it demonstrates the same pattern of validating against the cheaper quantity.

### Impact Explanation
When the actual required fee exceeds the amortized estimate, `signable_transaction` returns `None` where `prepare_send`'s contract says it must not. The plan's payments — user withdrawals triggered by public sriBTC burns — were already reduced by the amortization, so the plan is unfulfillable and its branch payments are dropped (`post_fee_branches`/`drop_branches` path, `processor/src/networks/mod.rs:442-454`). This is a denial of service on withdrawals of the same character as M-3: the protocol collects/commits to one amount and discovers at execution that it is insufficient.

### Likelihood Explanation
Reachable by unprivileged users through ordinary burns (public inputs scheduling payments) combined with fee-market movement between the estimation block and the signing attempt — exactly the `swapPrice > oraclePrice` analogue where the execution price exceeds the quoted price. No malicious validator or leaked key is required. It requires the median fee to rise across the relevant blocks, which is a normal network condition rather than attacker-controlled input, hence Medium rather than High.

### Recommendation
Have `signable_transaction`/`prepare_send` re-amortize using the `needed_fee` returned for the *same* block the transaction is built for, or have `SignableTransaction::new` absorb fee growth by further reducing payments/change at construction time instead of erroring. At minimum, make the "MUST NOT return None" invariant explicit by passing the previously computed fee rate through rather than re-sampling `median_fee`.

### Proof of Concept
1. A burn schedules a `Plan` with payments summing to `P` over inputs summing to `I`.
2. `prepare_send` calls `needed_fee(block_n)` → `median_fee(block_n)` = `f1`; `SignableTransaction::new` returns `needed_fee = f1 * vbytes`. Payments are amortized down to `P - tx_fee`.
3. `signable_transaction(block_m)` is called where `median_fee(block_m)` = `f2 > f1`. `SignableTransaction::new` now computes `needed_fee' = f2 * vbytes > tx_fee`; the check `input_sat < payment_sat + needed_fee'` (`send.rs:215`) fails and returns `NotEnoughFunds`, mapped to `Ok(None)` — transaction never constructed, amortized payments dropped.

Note: I did not fully trace the retry/block-number plumbing of the multisig scheduler to confirm the two calls occur at different block numbers on every path; if they are guaranteed to share a block, the residual issue reduces to the (safe-by-luck) change-output fee asymmetry in `SignableTransaction::new`.
