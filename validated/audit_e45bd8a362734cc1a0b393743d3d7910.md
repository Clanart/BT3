### Title
PedPoP emits the ECDH key-revealing `EncryptionKeyProof` before the message's proof-of-possession is verified - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The Quarkus flaw (CVE-2023-6267) processes an untrusted JSON body before security constraints are evaluated. The direct analog exists in PedPoP: `Encryption::decrypt` computes the ECDH shared key, decrypts the ciphertext, and mints an `EncryptionKeyProof` (which reveals that shared key) while the per-message proof-of-possession Schnorr signature is only *queued* into a `BatchVerifier`. In `KeyMachine::calculate_share`, a non-canonical decrypted share triggers an early `?` return that skips `batch.verify_with_vartime_blame()` entirely, so the blame proof — containing `ecdh(victim_enc_key, attacker_supplied_key)` — is produced for a message whose PoP was never checked.

### Finding Description
`Encryption::decrypt` in `crypto/dkg/pedpop/src/encryption.rs:469-501` first queues `msg.pop.batch_verify` (line 479) and then immediately performs `ecdh::<C>(&self.enc_key, msg.key)` and `cipher(...).apply_keystream(...)` (lines 487-488), returning an `EncryptionKeyProof` embedding the ECDH result `key` plus a DLEq proof over Bob's static encryption secret.

In `KeyMachine::calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-493`):

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);   // early return BEFORE batch.verify_with_vartime_blame() at line 493
```

If the decrypted bytes are not a canonical scalar, the function returns `InvalidShare { blame: Some(...) }` without ever verifying the PoP. The in-code comment at `encryption.rs:84-90` explains the PoP exists precisely to stop Eve from reusing Alice's message key `X` so that a blame proof reveals `bX` and hence Alice's share: "While Eve's message would fail to meaningfully decrypt, Bob would then use this to create a blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob." The queued-but-never-verified PoP defeats this protection on the non-canonical-share path.

### Impact Explanation
An unprivileged DKG participant (Eve) who observes Alice's `EncryptedMessage` to victim Bob (key field `X`) sends Bob a forged `EncryptedMessage` with `key: X`, arbitrary ciphertext bytes, and an invalid PoP. Bob's `calculate_share` computes `bX`, decrypts, and — with ~15/16 probability on Ed25519 (random 32-byte plaintext is non-canonical with probability `1 - l/2^256`) — returns `InvalidShare` carrying an `EncryptionKeyProof` whose `key` field is `bX` and whose `dleq` attests it. When Bob's application publishes this blame (the documented behavior of the `blame` API), `bX` is revealed and Alice's encrypted secret share to Bob is recoverable by ChaCha20-decrypting Alice's original ciphertext — recovering Bob's threshold secret share contribution, i.e., key share recovery of an honest participant's DKG output.

### Likelihood Explanation
Reachable by any external party able to submit a DKG share message to a participant and observe/blame-trigger the resulting error. Requires the decrypted garbage to be a non-canonical `C::F` encoding (high probability on Ed25519-class fields where `l ≈ 2^252`, lower but still meaningful on secp256k1 where `l ≈ 2^256`), and requires the deployment to propagate blame proofs, which is the designed usage (`BlameMachine::blame`, `AdditionalBlameMachine`). No collusion, leaked keys, or protocol misuse is needed.

### Recommendation
Verify `msg.pop` synchronously inside `Encryption::decrypt` (or at least before any error path can surface the `EncryptionKeyProof`), so `bX` and its DLEq proof are only produced for messages with a valid proof-of-possession. Alternatively, restructure `calculate_share` to run `batch.verify` before returning blame material, or withhold the `EncryptionKeyProof` until the message's PoP has been confirmed (e.g., return the proof lazily only after successful batch verification of the decryption-PoP statement).

### Proof of Concept
1. Alice runs `KeyGenMachine`/`SecretShareMachine` for context `ctx`, producing `EncryptedMessage` `M_a` to Bob with `key = X = xG`; ciphertext = `Enc(cipher(ctx, bX), share)`.
2. Eve builds `M_e = EncryptedMessage { key: X, pop: <invalid SchnorrSignature>, msg: <arbitrary bytes> }` and submits it to Bob's `KeyMachine::calculate_share` as her share.
3. `decrypt` queues the (invalid) PoP into `batch`, computes `ecdh(b, X) = bX`, keystreams the msg, and returns `(garbage_bytes, EncryptionKeyProof { key: bX, dleq: DLEq(G,X ; bG,bX) })`.
4. `C::F::from_repr(garbage)` is `None` (with probability `1 - l/2^|repr|`; ~94% for Ed25519) → `calculate_share` returns `InvalidShare { participant: eve, blame: Some(proof) }` without calling `batch.verify_with_vartime_blame()`.
5. Bob's stack publishes the blame proof → `bX` is public → anyone computes `cipher(ctx, bX)` and decrypts `M_a.msg`, recovering Alice's secret share to Bob.
