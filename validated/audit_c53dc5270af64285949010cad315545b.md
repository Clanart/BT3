### Title
Conflict-resolution status trusted from `git diff --check` heuristic allows a crafted merge to be shown/committed as "Resolved" while conflict markers remain - ([File: app/src/lib/git/diff-check.ts])

### Summary
The DeFi report's broken invariant is: a security-relevant "is this thing safe now?" decision is derived from a coarse, gameable signal ("any non-zero collateral counts as active") instead of the actual economic state, letting an attacker keep the check permanently satisfied with a value that shouldn't count. The Desktop analog is structurally identical: whether a conflicted file is considered "resolved" is derived from the *count* of "leftover conflict marker" lines reported by `git diff --check`'s text-based heuristic, not from whether the file actually still contains unresolved `<<<<<<<`/`=======`/`>>>>>>>` markers. An attacker who controls the repository content that produces the merge/rebase conflict (a malicious fetched/cloned repo, e.g. via `.gitattributes` or file content shaped to dodge the heuristic) can make `conflictMarkerCount` read `0` for a file that git itself still considers unmerged, causing Desktop to render and treat the file as "Resolved."

### Finding Description
`getFilesWithConflictMarkers` is the sole source of truth for whether a conflicted file "still has markers": [1](#0-0) 

It runs `git diff --check` and parses stdout with a fixed regex `^(.+):\d+: leftover conflict marker` to build a `Map<path, count>`. This count becomes `conflictMarkerCount` on the file's `ConflictedFileStatus`, and every "is this file done?" decision in the app funnels through it: [2](#0-1) 

- `hasUnresolvedConflicts` returns `false` (i.e., "resolved") whenever `conflictMarkerCount === 0` for a text file with markers, regardless of what bytes are actually on disk.
- `getResolvedFiles`/`getConflictedFiles` (used to gate the merge/rebase/cherry-pick "Continue"/"Commit" buttons) rely on this same predicate.
- `isFileResolvedExternally` in the Copilot-assisted conflict flow uses the identical `conflictMarkerCount === 0` check to decide a file was "resolved in an editor" and to overwrite the on-disk file with Copilot's resolution or exclude it from the resolved-content validation path: [3](#0-2) 

The `git diff --check` command only flags marker lines that appear as *added* content in the textual diff between the index and the working tree, using git's own conflict-marker heuristic (line starts with 7 repeated marker characters). This diverges from the ground truth ("does the working tree byte content contain unresolved markers, per the index's unmerged stage entries") in several attacker-reachable ways:
- A file whose diff is suppressed for that path (e.g. via a `.gitattributes` `-diff`/`binary` attribute, or a custom `conflict-marker-size` attribute that changes the marker length git generates during merge) will not produce a "leftover conflict marker" line, even though the working tree literally contains conflict markers and git status still reports the path as unmerged (`UU`/`AA`/etc.).
- Because `.gitattributes` is repository content, an attacker who controls the branch/commit being merged, rebased, or cherry-picked onto (a cloned/fetched repository, or a PR branch a maintainer merges locally in Desktop) fully controls this attribute, and thus controls whether Desktop's `conflictMarkerCount` is truthful.

There is no independent verification of "no markers on disk" — no byte-level scan of the actual working tree file — the app trusts a git subprocess's diff-based heuristic as a proxy for ground truth, the same class of shortcut the DeFi report calls out ("active" collateral defined by cheap/gameable signal instead of true economic state).

### Impact Explanation
When `conflictMarkerCount` reads `0` for a file that is still genuinely unmerged/marker-laden:
- The Conflicts dialog shows the file as resolved and disables the warning tooltip, letting the user click "Continue"/"Commit" (`OkCancelButtonGroup` `okButtonDisabled={conflictedFilesCount > 0}` in `conflicts-dialog.tsx`) while the file content still has literal `<<<<<<<`/`=======`/`>>>>>>>` text.
- The resulting commit silently contains corrupted/unresolved content — a direct "silent corruption of what the user commits or pushes," which is in the accepted impact category for this analog scan.
- In the Copilot flow, `isFileResolvedExternally` returning `true` for such a file causes Desktop to skip writing Copilot's proposed resolution and instead stage the attacker-shaped, still-conflicted file as-is (`app-store.ts` lines ~7241-7259), reinforcing the same silent-corruption path.

### Likelihood Explanation
Exploitation requires only that the victim merge, rebase, or cherry-pick a branch/commit whose tree includes a crafted `.gitattributes` entry (or otherwise a diff-suppressing/marker-size-altering attribute) for the file the attacker wants to poison — no local access, no admin rights, and no pre-existing compromise are needed, matching the accepted attacker model ("attacker controls a cloned/fetched repository"). The precise minimal attribute value needed to make `git diff --check` skip a given file is a git-behavior detail I could not fully verify from the codebase alone (this requires confirming `git diff --check`'s interaction with `-diff`/`conflict-marker-size` attributes against the installed git version), so likelihood should be validated with a concrete PoC repository before treating this as fully confirmed rather than a strong structural analog.

### Recommendation
- Do not derive "resolved" status solely from `git diff --check`'s textual heuristic. Cross-check by scanning the actual working-tree file bytes for the standard conflict marker patterns (`^<{7}`, `^={7}`, `^>{7}`) independent of `.gitattributes`/diff-driver configuration, or by comparing against `git status --porcelain=2` unmerged stage information directly.
- Treat any file `.gitattributes` marks as binary/no-diff, or that sets a non-default `conflict-marker-size`, as always requiring manual/binary-style resolution confirmation rather than eligible for marker-count-based auto-"resolved" detection.
- Add regression tests using a merge that sets `.gitattributes` `-diff` or a custom `conflict-marker-size` on the conflicted path, asserting `getFilesWithConflictMarkers`/`hasUnresolvedConflicts` still correctly reports the file as unresolved.

### Proof of Concept
1. Attacker prepares a branch to be merged that includes, at the root, a `.gitattributes` entry such as `poison.txt -diff` (or `poison.txt conflict-marker-size=3`), alongside conflicting edits to `poison.txt` relative to the victim's branch.
2. Victim, in GitHub Desktop, merges/rebases/cherry-picks this branch onto their own; git produces a real merge conflict and marks `poison.txt` as unmerged (`UU`) with literal conflict markers written to the working tree.
3. Desktop calls `getStatus` → `getConflictDetails` → `getFilesWithConflictMarkers`, which runs `git diff --check`; because of the `.gitattributes` entry, `poison.txt` is excluded from diff-based leftover-marker detection and no "leftover conflict marker" line is produced for it, so `conflictCountsByPath` has no entry (defaults to `0` markers) for `poison.txt` in `convertToAppStatus`.
4. `hasUnresolvedConflicts` returns `false` for `poison.txt`; the Conflicts dialog (`conflicts-dialog.tsx`) shows it as resolved, `conflictedFilesCount` excludes it, and the Continue/Commit button becomes enabled.
5. The user commits, producing a commit containing literal conflict-marker text in `poison.txt` without any warning — the corrupted content is what gets pushed. [1](#0-0) [2](#0-1)

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files
}

/**
 * Determine if we have any conflict markers or if its been resolved manually
 */
export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}
