### Title
Renderer runs with `nodeIntegration: true` / `contextIsolation: false`, turning any renderer script-injection into full Node.js code execution - ([File: app/src/main-process/app-window.ts])

### Summary
The external report flags Adena Wallet's overly-permissive CSP (missing `default-src`, `unsafe-inline`/`unsafe-eval`, broad `frame-src`), which lets attacker-influenced content execute in a context broader than intended. The closest analog in GitHub Desktop is not a missing CSP header — Desktop has none, similarly — but a strictly worse variant of the same broken invariant: the main application window and the crash window are created with `nodeIntegration: true` and `contextIsolation: false`, and the renderer bundle directly `import`s Electron's `ipcRenderer` module (no `contextBridge`/preload isolation layer). Where the CSP finding merely widens the attack surface for content injection, this configuration removes the security boundary entirely: any script execution achieved inside the main renderer (not the sandboxed markdown iframe) has immediate access to Node.js primitives (`require('child_process')`, `fs`, etc.) and to the full IPC surface, i.e., renderer XSS = RCE.

### Finding Description
`AppWindow`'s `BrowserWindow` is constructed with: [1](#0-0) 
—`nodeIntegration: true` and `contextIsolation: false`. The same configuration is repeated for the crash-report window: [2](#0-1) 

With `contextIsolation` disabled, the renderer's JavaScript world is not isolated from Electron's internal/preload world, so the renderer code can `require` and use privileged Electron/Node APIs directly, as seen in the direct import of `ipcRenderer` (an Electron internal module) straight into UI code without any `contextBridge` mediation: [3](#0-2) 

Desktop does apply some CSP-equivalent mitigations elsewhere — it disables webview tags, denies new-window creation, and blocks in-window navigation: [4](#0-3) 
It also renders untrusted repository/PR/commit markdown inside a DOMPurify-sanitized, `sandbox="allow-same-origin"` (no `allow-scripts`) iframe: [5](#0-4) 

However, that sandboxing only protects markdown content rendered through `SandboxedMarkdown`. It does nothing for the rest of the main renderer surface (dialogs, PR/issue titles, branch/tag names, notifications, autocompletion suggestions, etc.), all of which run in the same unisolated, Node-integrated window. Several markdown node filters even build HTML via `innerHTML` from repository-controlled strings (owner/repo names, refs) before those nodes are inserted into a sanitized doc: [6](#0-5) [7](#0-6) 
These specific instances still land inside the sandboxed iframe (mitigated), but they illustrate the broader pattern in the codebase of directly injecting attacker/repository-controlled strings as HTML — a single such construction that reaches the *main* renderer's DOM (outside `SandboxedMarkdown`) would execute with full Node access due to the `nodeIntegration`/`contextIsolation` settings above.

### Impact Explanation
Because `contextIsolation` is `false` and `nodeIntegration` is `true` on the primary application window, any JavaScript execution primitive achieved in the main renderer — e.g., an HTML/script-injection bug reachable from an attacker-controlled GitHub API object, PR title, branch name, or repository metadata that is rendered outside the `SandboxedMarkdown` sandbox — escalates directly to arbitrary Node.js code execution on the user's machine (file read/write anywhere the OS user can access, credential/token exfiltration from Desktop's keychain-backed auth store, and IPC access to privileged main-process handlers). This is a materially higher-impact outcome than the CSP issue in the source report, which at best enabled loading of unauthorized remote resources within a still-sandboxed browser context.

### Likelihood Explanation
Exploitation requires first finding an HTML/script injection point in the *unsandboxed* portion of the renderer (i.e., not routed through `SandboxedMarkdown`) — for example a location where a GitHub API field (PR title, repo description, branch name, notification text) is inserted via `innerHTML`/`dangerouslySetInnerHTML`-equivalent patterns rather than plain text nodes, without going through DOMPurify + the iframe sandbox. Desktop's existing mitigations (`will-navigate`/`setWindowOpenHandler` denial, no `webview` tag usage, DOMPurify+iframe for markdown) substantially reduce this likelihood, but they do not compensate for `contextIsolation: false`/`nodeIntegration: true` as a defense-in-depth failure: if any injection point is ever missed (now or in a future change), there is no secondary boundary to contain it, unlike apps that keep Node integration disabled and use a narrow `contextBridge` API.

### Recommendation
- Set `contextIsolation: true` and `nodeIntegration: false` on both `AppWindow` and `CrashWindow` `webPreferences` (`app/src/main-process/app-window.ts`, `app/src/main-process/crash-window.ts`).
- Introduce a `preload` script that uses `contextBridge.exposeInMainWorld` to expose only the specific IPC channels the renderer needs, replacing the direct `ipcRenderer` import in `app/src/lib/ipc-renderer.ts`.
- Audit all locations where repository/API-controlled strings are inserted as HTML outside `SandboxedMarkdown` and ensure they go through text-node insertion or DOMPurify + iframe sandboxing consistently.
- Add an explicit restrictive CSP (`default-src 'none'`, per-directive allow-lists) to `index.html`/`session.defaultSession.webRequest.onHeadersReceived` as defense in depth, mirroring the recommendation in the source report, even though it is secondary to fixing the isolation settings.

### Proof of Concept
Conceptual chain (cannot be executed without a live injection point, which was not found during this review — this is the caveat that must be stated):
1. An attacker crafts a GitHub object (e.g., a pull request title, repository name, or branch name) containing a `<script>`/event-handler payload.
2. If that string reaches the DOM of the main application window via an `innerHTML`-style sink that is not routed through `SandboxedMarkdown`'s DOMPurify + sandboxed-iframe pipeline, the script executes in the main renderer context.
3. Because that renderer is created with `nodeIntegration: true` and `contextIsolation: false` (`app/src/main-process/app-window.ts:65-72`), the injected script has direct access to `require('child_process').exec(...)` or Node's `fs` module, achieving arbitrary code execution and file read/write outside the repository, and can call `ipcRenderer.invoke` on any privileged main-process channel to exfiltrate stored credentials.

Note: step 2's concrete injection sink was not located in the indexed portion of the codebase (all `innerHTML` usages found route through the sandboxed markdown pipeline), so this should be treated as a configuration-hardening finding (missing defense-in-depth) rather than a confirmed end-to-end exploit chain. A full audit of every renderer text-insertion sink across the codebase, which may exceed what's available in the index, would be needed to confirm or rule out a live injection path — recommend a full Devin session with repository access to complete this audit.
