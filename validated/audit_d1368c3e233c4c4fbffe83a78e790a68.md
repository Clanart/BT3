## Analysis

I found a strong analog in the `kaiax/gasless` module (KIP-247) and the `GaslessSwapRouter` contract it targets.

The gasless flow works as follows: a user signs a `GaslessSwapTx` with a fixed `SwapArgs.MinAmountOut` and `SwapArgs.AmountRepay` [1](#0-0) . The tx-pool admission check only verifies `minAmountOut >= amountRepay` and other static conditions before the transaction is even promoted/bundled with the proposer's lend transaction [2](#0-1) . The actual split between what is repaid to the proposer and what the user finally receives (`FinalUserAmount`) is computed inside the `GaslessSwapRouter` contract at execution time, and that split depends on `commissionRate()` [3](#0-2) [4](#0-3) .

Critically, `commissionRate` is mutable via `updateCommissionRate(uint256)`, an owner-gated function (see `Owner()`/`OwnershipTransferred` bindings) that emits `CommissionRateUpdated(oldRate, newRate)` [5](#0-4) [6](#0-5) , and there is **no restriction tying this update to any epoch, cooldown, or in-flight-transaction state** — the same class of flaw as the OpenQ report, where a privileged party (bounty minter / here, the router owner) can change payout parameters unilaterally at any time, including between when an unprivileged user commits to a transaction (signs `SwapArgs` with a fixed `AmountRepay`, unaware of/unable to control `commissionRate`) and when it is actually executed on-chain.

Because the user's signed `SwapArgs` only fixes `AmountIn`, `MinAmountOut`, `AmountRepay`, and `Deadline` — not the commission rate — the owner can raise `commissionRate` at any point before the swap transaction lands (e.g., right after observing the pending `GaslessApproveTx`/`GaslessSwapTx` pair in the mempool, analogous to observing contest results before rugging winners), reducing `FinalUserAmount` below what the user expected when signing, while the tx-pool/module-level checks (`checkBalanceForSwap`, `VerifyExecutable`) never re-validate the commission split against user expectations [7](#0-6) . The only user-side protection is `MinAmountOut`, which is a floor on swap output, not on `FinalUserAmount` after commission — so as long as the commission increase keeps `FinalUserAmount` at or above zero (or above whatever residual the contract requires), the owner can extract more value from the gasless user without violating any of the checked invariants.

I was not able to fully inspect the actual `GaslessSwapRouter.sol` source (only compiled Go bindings and its bytecode were indexed, and no `.sol` file for it was found via `glob_search`), so I cannot confirm from source exactly how `commissionRate` bounds the swap surplus in code, or whether there's a `MAX_COMMISSION_RATE` cap enforced on-chain. This is a limitation of what the index surfaced; a full Devin session with filesystem access would be needed to read the actual `contracts/system_contracts/kip247/GaslessSwapRouter.sol` (or wherever its source lives) to confirm bound-checks on `updateCommissionRate`.

### Title
Unrestricted `updateCommissionRate` in `GaslessSwapRouter` lets the router owner rug gasless-swap users after they sign their swap - (File: `contracts/bindings/kip247/GaslessSwapRouter.go`)

### Summary
The `GaslessSwapRouter` contract (KIP-247) that backs Kaia's gasless-transaction feature exposes an owner-only `updateCommissionRate` function with no restriction on *when* it can be called relative to pending, already-signed `GaslessSwapTx` transactions in the pool. This mirrors the OpenQ bug class: a privileged party can change payout-determining parameters after an unprivileged party (the gasless user) has already committed value/intent, before settlement occurs.

### Finding Description
A gasless user constructs a `SwapArgs` (fixing `AmountIn`, `MinAmountOut`, `AmountRepay`, `Deadline`) and signs a `GaslessSwapTx` [1](#0-0) . The tx-pool's readiness/admission logic (`VerifyExecutable`, `checkBalanceForSwap`) only checks that `MinAmountOut >= AmountRepay`, sufficient allowance/balance, and deadline — never re-derives or pins the commission rate that ultimately determines the user's `FinalUserAmount` [2](#0-1) [8](#0-7) . The commission split is resolved on-chain inside `GaslessSwapRouter.swapForGas`, driven by the contract's `commissionRate` state variable, which the owner can update at will via `updateCommissionRate` [9](#0-8) , emitting `CommissionRateUpdated` [6](#0-5) . Since the user's signature does not cover the commission rate, the owner can raise it after observing a pending gasless swap in the mempool but before it's included, capturing more of the swap surplus for the `CommissionClaimed` pool at the user's expense — the exact "change payout parameters after commitment, before settlement" pattern from the OpenQ report.

### Impact Explanation
A malicious or compromised router owner can systematically reduce `FinalUserAmount` for gasless-swap users below what they expected when signing their transaction, extracting value via commission that was not agreed to at signing time. This is a concrete instance of unauthorized value redirection/fee abuse reachable from a single unprivileged user's gasless transaction, satisfying the "fee delegation abuse / gasless settlement theft" validation criterion.

### Likelihood Explanation
Likelihood is Medium: it requires the router owner (a privileged, non-consensus role distinct from validators/proposers) to act maliciously or be compromised, and to time the `updateCommissionRate` call against pending mempool transactions — feasible since the owner can observe the public mempool and the gasless tx pool state before the swap is included. No governance or timelock gate is evident from the bindings I inspected.

### Recommendation
Bind the commission rate used for a given `GaslessSwapTx` to the rate observed at signing time (e.g., include an `expectedCommissionRate` or `minFinalUserAmount` field validated inside `swapForGas`), or enforce a timelock/epoch-delay on `updateCommissionRate` changes analogous to how governance parameter changes only take effect after an epoch boundary in `kaiax/gov` [10](#0-9) , so in-flight signed swaps are not retroactively affected by owner-initiated commission changes.

### Proof of Concept
1. User signs `GaslessApproveTx` + `GaslessSwapTx` with `SwapArgs{AmountIn, MinAmountOut, AmountRepay, Deadline}` per `makeSwapTx` [11](#0-10)  and broadcasts to the mempool.
2. Router owner observes the pending pair (e.g., via public mempool) and calls `updateCommissionRate(newHigherRate)` before the swap is included, which the ABI permits without restriction [5](#0-4) .
3. The proposer includes `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` per the module's block-building rules [12](#0-11) ; `swapForGas` executes with the new, higher commission rate.
4. `SwappedForGas` event shows a `FinalUserAmount` lower than what the user calculated when signing (based on the commission rate at signing time), while `AmountRepay` and `MinAmountOut` checks still pass since those don't constrain post-commission proceeds [3](#0-2) .

// VerifyExecutable checks if the given transactions form a valid gasless transaction
// It returns an error explaining why the transaction is not executable if it's not,
// and a boolean indicating whether the transaction is executable
func (g *GaslessModule) VerifyExecutable(approveTxOrNil, swapTx *types.Transaction) error {
	// Sx.
	swapArgs, ok := decodeSwapTx(swapTx, g.signer)
	if !ok {
		return ErrDecodeSwapTx
	}
	if !g.isSwapTx(swapArgs) {
		return ErrSwapTxInvalid
	}

	// Conditions involving ApproveTx
	if approveTxOrNil != nil {
		// Ax.
		approveArgs, ok := decodeApproveTx(approveTxOrNil, g.signer)
		if !ok {
			return ErrDecodeApproveTx
		}
		if !g.isApproveTx(approveArgs) {
			return ErrApproveTxInvalid
		}
		// AP1.
		if approveArgs.Sender != swapArgs.Sender {
			return ErrDifferentSenders
		}
		// SP1.
		if approveArgs.Token != swapArgs.Token {
			return fmt.Errorf("%w: approve token %s, swap token %s", ErrDifferentTokens, approveArgs.Token.Hex(), swapArgs.Token.Hex())
		}
		// SP2.
		if approveArgs.Amount.Cmp(swapArgs.AmountIn) < 0 {
			return fmt.Errorf("%w: approve amount %s, required amount %s", ErrInsufficientApproveAmount, approveArgs.Amount.String(), swapArgs.AmountIn.String())
		}
		// SP3.
		if approveTxOrNil.Nonce()+1 != swapTx.Nonce() {
			return fmt.Errorf("%w: approve nonce %d, swap nonce %d (expected %d)", ErrNonSequentialNonce, approveTxOrNil.Nonce(), swapTx.Nonce(), approveTxOrNil.Nonce()+1)
		}
		if nonce := g.getCurrentStateNonce(approveArgs.Sender); nonce != approveTxOrNil.Nonce() {
			return fmt.Errorf("%w: approve nonce %d, current nonce %d", ErrApproveNonceNotCurrent, approveTxOrNil.Nonce(), nonce)
		}
	} else {
		// SP3.
		if nonce := g.getCurrentStateNonce(swapArgs.Sender); nonce != swapTx.Nonce() {
			return fmt.Errorf("%w: swap nonce %d, current nonce %d", ErrSwapNonceNotCurrent, swapTx.Nonce(), nonce)
		}
	}

	// SP4.
	if swapArgs.AmountRepay.Cmp(repayAmount(approveTxOrNil, swapTx)) != 0 {
		return fmt.Errorf("%w: got %s, expected %s", ErrIncorrectRepayAmount, swapArgs.AmountRepay.String(), repayAmount(approveTxOrNil, swapTx).String())
	}

	return nil
}

- A new bundle is generated which contain either `[LendTxGenerator, GaslessApproveTx, GaslessSwapTx]` or `[LendTxGenerator, GaslessSwapTx]`
- If the bundle has conflict with any previous bundles, it is excluded from the returned bundle list.
