### Title
Malformed blame accusation crashes the DKG state machine via unguarded `HashMap` indexing — ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
Analogous to GHSA-q7rr-3cgh-j5r3 (a single malformed input causing an uncaught exception that crashes the process), the PedPoP blame flow indexes `HashMap`s with attacker-influenced `Participant` values using the panicking `[]` operator instead of validating membership first. A blame accusation referencing a `recipient` who is not a registered DKG participant reaches `self.enc_keys[&decryptor]` in `Decryption::decrypt_with_proof`, which panics (`index out of bounds`/`HashMap` index panic) and aborts the process. Similarly, an accusation naming a `sender` outside the participant set reaches `self.commitments[&sender]` in `blame_internal` and panics.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` are the public APIs for evaluating fault accusations. Both take `sender: Participant`, `recipient: Participant`, an `EncryptedMessage<C, SecretShare<C::F>>` (attacker-controlled bytes via `EncryptedMessage::read`, which itself only performs canonical `read_G`/`read_F`/`SchnorrSignature::read` decoding and returns `io::Result` — no panic there), and an optional `EncryptionKeyProof<C>` (parsed via `DLEqProof::read`, also non-panicking).

Inside `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:575-608`), the parsed message and proof are passed to `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs:366-397`). The crash path:

1. `msg.pop.verify(...)` — the PoP challenge binds `from` (`sender`) and the ciphertext, but the attacker constructing the accusation chooses the `EncryptedMessage` bytes, so they can generate `key`/`pop` over an ephemeral secret they control and pass this check trivially.
2. If `proof` is `Some`, the verifier builds the DLEq statement `&[self.enc_keys[&decryptor], *proof.key]` at `crypto/dkg/pedpop/src/encryption.rs:388`. `enc_keys` only contains entries registered via `Decryption::register` for the real participant set (`1..=n`, populated in `verify_r1` at `crypto/dkg/pedpop/src/lib.rs:315` or `AdditionalBlameMachine::new` at `crypto/dkg/pedpop/src/lib.rs:656-660`). `decryptor` is the accusation's `recipient`. `Participant::new` only rejects zero (`crypto/dkg/src/lib.rs`), so `recipient = Participant(n+1)` is a syntactically valid value that is not a key in `enc_keys`. The `HashMap` `Index` impl panics — the DLEq proof never even needs to be valid; the index is evaluated while constructing the argument slice.
3. Independently, if decryption succeeds with a canonical-scalar plaintext (fully attacker-controlled when the accuser knows their own ECDH key, which a participant-accuser does), `blame_internal` then evaluates `self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs:599` inside `share_verification_statements`, panicking for any `sender` not in `1..=n`.

The docs for `AdditionalBlameMachine::new` acknowledge this class of issue ("Usage of invalid commitments is considered undefined behavior, and may cause everything from inaccurate blame to panics", `crypto/dkg/pedpop/src/lib.rs:645-648`), but the participant-index inputs to `blame` are not covered by that warning and are not validated anywhere in the call path — `blame_internal` performs no `contains_key`/`validate_map`-style check on `sender` or `recipient` before indexing.

### Impact Explanation
Denial of service. A single crafted blame accusation — `blame(sender, Participant(n+1), forged_msg, Some(any_parseable_proof))` — triggers a panic that unwinds into and aborts whatever task/process drives the DKG machine. In a validator running this in a `catch_unwind`-less async task or thread, the whole node component handling key-gen/blame dies, stalling the DKG and any dependent signing (the same panic-per-packet shape as the Prometheus exporter crash in the reference advisory). No secret material is leaked, but availability of the threshold-key subsystem is lost.

### Likelihood Explanation
Reachability requires the integration to route blame accusations into `BlameMachine::blame`/`AdditionalBlameMachine::blame` with accuser-supplied `sender`/`recipient`/`msg`/`proof`. `AdditionalBlameMachine::new` explicitly exists so a third party ("capable of evaluating blame regardless of if the caller was a member in the DKG protocol") can evaluate accusations — meaning an accusation naming an out-of-range `recipient` or `sender` can come from parties outside the honest participant set, and nothing in the library rejects `Participant` values beyond the protocol's `n`. The only requirement on the attacker is producing an `EncryptedMessage` whose `pop` verifies under a key they choose (trivially satisfiable) — the panic fires before the proof is even checked. Likelihood hinges on whether the calling code bounds-checks `sender`/`recipient` against `n` before calling; the library itself does not.

### Recommendation
In `Decryption::decrypt_with_proof` (`crypto/dkg/pedpop/src/encryption.rs`), replace `self.enc_keys[&decryptor]` with `self.enc_keys.get(&decryptor)` and return `Err(DecryptionError::InvalidProof)` (or blame `recipient`) when absent. In `blame_internal` (`crypto/dkg/pedpop/src/lib.rs`), validate `sender` and `recipient` against `self.commitments`/`self.encryption.enc_keys` membership before indexing — e.g., `let Some(commitments) = self.commitments.get(&sender) else { return recipient; }` — treating a non-participant index as accuser fault rather than panicking.

### Proof of Concept
```rust
// Assume an AdditionalBlameMachine (or BlameMachine) constructed for n = 3,
// context = CTX, over a Ciphersuite C.

let machine: AdditionalBlameMachine<C> =
  AdditionalBlameMachine::new(CTX, 3, commitment_msgs).unwrap();

// Attacker (any accuser) crafts an EncryptedMessage with a key they know:
let k  = C::random_nonzero_F(&mut rng);
let r  = C::random_nonzero_F(&mut rng);
let msg = EncryptedMessage::<C, SecretShare<C::F>> {
  key: C::generator() * k,
  pop: SchnorrSignature::sign(&k, r, pop_challenge::<C>(CTX, C::generator()*r, C::generator()*k, Participant::new(1).unwrap(), ciphertext)),
  msg: ciphertext, // arbitrary 32 bytes
}; // fields are private; equivalent bytes are supplied via EncryptedMessage::read

// Any parseable proof suffices; the panic happens while building the
// verify() arguments, before the proof is checked.
let proof = Some(EncryptionKeyProof::read(&mut any_valid_bytes.as_slice()).unwrap());

// recipient = 4 is not among participants 1..=3
machine.blame(Participant::new(1).unwrap(), Participant::new(4).unwrap(), msg, proof);
// PANIC at crypto/dkg/pedpop/src/encryption.rs:388:
//   `self.enc_keys[&decryptor]` -> HashMap index panic, process aborts
```

Uncertainty I could not resolve without execution: whether Serai's coordinator/processor layer bounds-checks `sender`/`recipient` before calling `blame` (the coordinator crates are outside the listed in-scope set), and whether the panic is caught by an enclosing runtime. The panic itself in the in-scope library code is unconditional once the path is reached.
