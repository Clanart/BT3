### Title
`ThresholdKeys::read` performs an attacker-controlled heap allocation (`Vec::with_capacity(n)`) before validating `n`, enabling per-message memory-amplification DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` reads a `u16` participant count `n` from untrusted bytes and immediately calls `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient vector, then proceeds to read `n` scalars and `n` group elements — all before `ThresholdParams::new` validates `t <= n`, `i <= n`. Unlike the rdiffweb bug (completely unbounded length), `n` is capped at 65535 by the `u16` encoding, but a ~10-byte input still forces an up-front allocation of 65535 scalars (≥ 2 MiB) and, when the attacker supplies the bytes, 65535 point-deserialization operations. There is no sanity bound on `n` at read time at all.

### Finding Description
In `ThresholdKeys::<C>::read` (`crypto/dkg/src/lib.rs:574-632`):

- `n` is deserialized straight from the reader as a `u16` with no lower/upper plausibility check [1](#0-0) 
- If the interpolation tag byte is `0`, `Vec::with_capacity(usize::from(n))` executes unconditionally, allocating up to `65535 * size_of::<C::F>()` (~2 MiB for 32-byte fields) in a single call [2](#0-1) 
- A second loop reads `n` verification shares into a `HashMap` via `C::read_G`, each triggering full point decoding/decompression [3](#0-2) 
- Only after all this work does `ThresholdParams::new(t, n, i)` reject inconsistent parameters — the expensive work is already done [4](#0-3) 

The same class appears in `SchnorrAggregate::<C>::read`, which reads a `u32` count (up to ~4 billion) and loops `read_G` per element with no bound whatsoever (`crypto/schnorr/src/aggregate.rs:77-88`); memory growth there is proportional to supplied bytes, but the count itself is never validated against any protocol-meaningful maximum.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as an accepted untrusted-bytes sink) can force ~2 MiB of heap allocation plus up to 65535 scalar/point deserialization attempts per message, before any parameter validation runs. Repeated invocations amplify attacker input (~10 bytes → ~2 MiB allocation; a few hundred bytes of crafted input → 65535 field reads), enabling memory exhaustion / CPU-burn denial of service against the parsing party. The `SchnorrAggregate::read` variant additionally permits a 4-billion-element logical structure with no cap. Severity: Medium — the effect is bounded by `u16`/`u32` encoding limits and by actual input size for the element loops, so it is a resource-amplification DoS, not unbounded corruption.

### Likelihood Explanation
Reachability requires a caller deserializing `ThresholdKeys`/`SchnorrAggregate` from attacker-influenced bytes — plausible wherever serialized key material or aggregate signatures transit peer messages or storage. No cryptographic exploit is needed; a short crafted buffer triggers the pre-allocation immediately. Effort is trivial, but the absolute impact per message is modest, keeping this in Medium territory.

### Recommendation
- Cap `n` at read time against a protocol-meaningful maximum before allocating (e.g., reject `n` exceeding the configured participant set before `with_capacity`).
- Move `ThresholdParams::new(t, n, i)` validation ahead of the interpolation/share reads.
- Bound the `u32` count in `SchnorrAggregate::read` to a sane maximum, mirroring how `coordinator/src/p2p.rs` enforces `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating.
