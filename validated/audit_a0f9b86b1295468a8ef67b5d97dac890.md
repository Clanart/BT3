### Title
`ReceivedOutput::read` accepts attacker-controlled (offset, output, outpoint) triples without verifying the script_pubkey actually corresponds to the offset and wallet key - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the Flowise report (untrusted input forwarded into a sensitive execution pipeline without sanitization), `ReceivedOutput::read` deserializes a scalar `offset`, a `TxOut`, and an `OutPoint` from untrusted bytes and hands them directly to the wallet's signing/spending pipeline, with no check that `output.script_pubkey` is the P2TR script derived from `key + offset*G`. The only path that establishes that binding, `Scanner::scan_transaction`, is bypassed entirely when `ReceivedOutput`s are deserialized rather than scanned.

### Finding Description
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) reads:
- `offset` via `Secp256k1::read_F` — canonicality is enforced (crypto/ciphersuite/src/lib.rs:74-83), but the value is otherwise unconstrained.
- `output` and `outpoint` via raw Bitcoin consensus decoding — no relation to `offset` is checked.

Compare with `Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214), which is the intended producer: it only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` returns an offset previously registered by `register_offset` (lines 180-196), guaranteeing `output.script_pubkey == p2tr_script_buf(key + G*offset)`. `ReceivedOutput::read` performs no equivalent check — there is no key stored on `ReceivedOutput` and no validation that the script is even P2TR. Any consumer that round-trips `ReceivedOutput`s through an untrusted channel (e.g., DB recovery, processor-serde of coordinator-supplied output data) will inject attacker-chosen `(offset, output, outpoint)` values straight into the `Signer`/`send` path, where `offset` is used to re-key the threshold signature.

### Impact Explanation
An unprivileged party who can cause bytes to be fed to `ReceivedOutput::read` (or supply a crafted `ReceivedOutput` blob) can:
- Report outputs as received/spendable that are not spendable by the wallet — e.g., pairing the wallet's own outpoint/script with a wrong `offset` (offset `x` instead of the registered `y`), causing the spend attempt to sign with `key + x*G` while the output commits to `key + y*G`: the funds are counted but any spend fails.
- Pair a chosen `offset` with an output whose script_pubkey is a *real* tweaked P2TR key with a known script path (note `p2tr_script_buf` uses `TweakedPublicKey::dangerous_assume_tweaked`, so scanner-produced scripts have no script path, but nothing in `read` enforces that shape). The wallet treats the output as offset-spendable while the attacker retains a script-path spend — funds are not exclusively controlled.

This meets the "funds reported received that are not spendable" impact class.

### Likelihood Explanation
Reachable wherever serialized `ReceivedOutput`s cross a trust boundary — untrusted bytes are explicitly in scope per the `ReceivedOutput::read` API. No cryptographic break is needed; only control of the serialized blob. Severity Medium: it corrupts wallet accounting and can burn/spend-attempt against incorrect offsets, but does not directly leak key material.

### Recommendation
In `ReceivedOutput::read`, or at the point of consumption, verify consistency: recompute `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)` (rejecting `None`/odd results) and require it to equal `output.script_pubkey`. Alternatively, make deserialization private to `Scanner` so only scanned outputs can produce `ReceivedOutput`s, or store and re-verify the expected script inside `ReceivedOutput` itself.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs context
// Wallet registered offset y for script S = p2tr(key + y*G).
// Attacker supplies serialized bytes to ReceivedOutput::read:
let mut buf = vec![];
buf.extend((x).to_bytes());                    // wrong offset x != y
buf.extend(serialize(&txout_paying_to_S));     // wallet's real output
buf.extend(serialize(&outpoint));              // wallet's real outpoint
let ro = ReceivedOutput::read(&mut &buf[..]).unwrap(); // accepted, no binding check
// Wallet signs spend with key + x*G -> invalid signature for script S,
// or attacker supplies a tweaked script they co-control with offset 0.
```
Confirmed by inspection: `read` (lines 122-134) contains no call to `p2tr_script_buf` or comparison against `output.script_pubkey`; the binding exists only inside `Scanner` (lines 185-211).
