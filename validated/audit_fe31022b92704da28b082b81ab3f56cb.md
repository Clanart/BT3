### Title
Panic via `unwrap()` on `ThresholdKeys::view` when signing with Constant interpolation and a non-default signer set - (File: crypto/frost/src/sign.rs)

### Summary
`AlgorithmSignMachine::sign` calls `self.params.keys.view(included.clone()).unwrap()` on a signer set (`included`) whose membership is fully controlled by the remote participants' preprocess messages. For `ThresholdKeys` deserialized with `Interpolation::Constant` (reachable via `ThresholdKeys::read`, which accepts interpolation byte `0`), `view()` cannot produce a view for an arbitrary signer set — constant interpolation is only defined over the fixed participants `1..=t` used in `ThresholdKeys::new`. Any signing session whose `included` set differs from that fixed set causes `view()` to return `Err`, and the `unwrap()` panics, crashing the signer.

### Finding Description
In `crypto/frost/src/sign.rs`, `sign` builds `included` from `preprocesses.keys()` (attacker-influenced `Participant` values), then validates only:
- `included.len() >= t` (line 298)
- max participant `<= n` (line 302)
- no duplicates (lines 306-310)

It then does `self.params.keys.view(included.clone()).unwrap()` at line 312. Meanwhile, `ThresholdKeys::read` in `crypto/dkg/src/lib.rs` (lines 604-616) accepts `interpolation[0] == 0` → `Interpolation::Constant`, and `ThresholdKeys::new` derives `group_key` from verification shares `1..=t` (lines 620-630). A `ThresholdView` for any other participant set is not constructible under constant interpolation, so `view()` returns `Err(...)` and the `unwrap()` panics instead of surfacing a `FrostError`.

### Impact Explanation
An unprivileged counterparty in a signing session can force a panic (complete DoS of the signing process / host task) simply by participating in — or omitting themselves from — a preprocess set such that `included != {1..=t}` on a key deserialized with constant interpolation. Since `ThresholdKeys::read` is a supported untrusted-bytes ingestion path, keys produced this way are legitimate inputs, and the panic is reachable purely from public preprocess messages.

### Likelihood Explanation
Requires the key holder to use `Interpolation::Constant` (an accepted serialization variant) and a signing set other than the canonical `1..=t`. Any participant can trigger it by refusing to preprocess or by an extra/missing participant in `preprocesses`; no secret knowledge or privileged position is needed.

### Recommendation
Replace `.unwrap()` at `crypto/frost/src/sign.rs:312` with `map_err`-style propagation into `FrostError::InvalidSigningSet`, or pre-validate that the interpolation method supports the chosen `included` set before calling `view()`.

### Proof of Concept
1. Deserialize `ThresholdKeys<C>` via `ThresholdKeys::read` with interpolation byte `0` (Constant) and `n` coefficients.
2. Create an `AlgorithmMachine`, run `preprocess()`.
3. Call `sign` with a `preprocesses` map whose key set plus own `i` forms any valid (size `>= t`, `<= n`, unique) set that is not exactly `{1..=t}` — e.g. participants `{2, ..., t+1}`.
4. `view(included)` returns `Err` → `unwrap()` panics, crashing the signer.

Caveat: this conclusion rests on `ThresholdKeys::view` returning `Err` for non-`1..=t` sets under `Interpolation::Constant` (consistent with `DkgError::InapplicableInterpolation`/`IncorrectAmountOfParticipants` existing for exactly this case); I could not read `view()`'s body within the available iterations to confirm it errors rather than silently computing an incorrect view — either outcome confirms a defect at this `unwrap()`, but the crash specifically requires the `Err` path.
