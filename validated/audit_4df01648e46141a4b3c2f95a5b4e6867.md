### Title
`SignableTransaction` omits the OP_RETURN output from weight/fee calculation, producing transactions whose real fee rate and weight were never checked - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an attacker-influenceable `OP_RETURN` output to the transaction *after* the weight-and-fee estimation is performed. `calculate_weight_vbytes` only models `payments` (and optionally `change`), so the size/fee checks are evaluated against a smaller transaction than the one actually built — the same class as the OptimismPortal bug: a resource check performed before all of the resource-consuming work is accounted for, letting the real execution under-run the bound the caller specified.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` is pushed onto `tx_outs` at lines 194–202. However, the fee estimation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, and `calculate_weight_vbytes` (lines 62–99) constructs its template transaction's `output` vector solely from `payments` (plus the optional change output). The `OP_RETURN` output is never represented in the template.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` is computed from vbytes that exclude the OP_RETURN output (~83+ bytes of transaction data, and the `TxOut` overhead). The transaction the caller actually signs pays `fee_per_vbyte` on a smaller virtual size than the real one, so the *effective* fee rate is strictly below the rate the caller requested.
2. The minimum-relay-fee guard at lines 211–213 (`TooLowFee`) uses the same underestimated `vbytes`, so a transaction can pass the check while its real fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` — exactly the "check passes, execution fails" gap.
3. The `MAX_STANDARD_TX_WEIGHT` guard at lines 241–243 checks `weight`, which likewise excludes the OP_RETURN output's weight. A transaction whose real weight exceeds the standardness limit is returned as `Ok(SignableTransaction)` and can be signed to completion; no Bitcoin node will relay or mine it, and the wallet layer has no replay/repair path — the signed artifact is simply unusable.

### Impact Explanation
An unprivileged party who can cause a `SignableTransaction` to be built with `data` (the `data` parameter is a public, untrusted input to `SignableTransaction::new`) can produce a signed transaction that fails standardness/relay policy despite every internal check passing. With `MAX_INPUTS`-scale input lists, the ~330+ weight units contributed by an 80-byte OP_RETURN can push a borderline transaction over `MAX_STANDARD_TX_WEIGHT`, or drop the effective fee rate below the relay minimum, making the transaction permanently unconfirmable as constructed. Inputs are only recoverable via out-of-band reconstruction — mirroring the "no replays" property of the Portal bug.

### Likelihood Explanation
Exploitation requires the builder to supply `data` and a transaction already near a policy boundary (weight limit or minimum fee rate). The miscounting itself is unconditional — every transaction with `data` is under-charged on fee and under-checked on weight — so any deployment that attaches OP_RETURN data to large or low-fee-rate transactions hits this reliably. Severity is bounded because honest callers can re-sign with a higher fee, so this is Medium rather than High.

### Recommendation
Include the OP_RETURN output in the size model. `calculate_weight_vbytes` should accept the finalized output list (or the data length) rather than only `payments`, e.g. build the template `tx.output` from `tx_outs` after the OP_RETURN push, and reuse that single template for `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check — so the checked artifact is byte-identical in size to the artifact produced.

### Proof of Concept
Conceptual trace through `networks/bitcoin/src/wallet/send.rs`:

1. Call `SignableTransaction::new(inputs, payments, change, Some(vec![0u8; 80]), fee_per_vbyte)` with `inputs`/`payments` sized so the template's `weight` is just under `MAX_STANDARD_TX_WEIGHT` and `vbytes` yields `needed_fee` just above the minimum relay fee.
2. Lines 194–202 push `TxOut { value: 0, script_pubkey: OP_RETURN <80 bytes> }` onto `tx_outs`; this output is absent from the template built at line 204.
3. `needed_fee` (line 206), the `TooLowFee` check (line 211), and the `TooLargeTransaction` check (line 241) all evaluate the smaller template and pass.
4. The returned `SignableTransaction.tx` is ~340+ weight units heavier than checked and pays `fee_per_vbyte` on a smaller vsize than its real `tx.vsize()` — a signed transaction nodes reject or refuse to relay, despite all checks having passed.
