### Title
Depth-based "EOA-only" gate in the `solo` precompile can be bypassed by calling from within a contract constructor - ([File: precompiles/solo/solo.go])

### Summary
The `solo` precompile (`0x...100C`) implements a "must be called by an EOA directly" restriction using `evm.GetDepth() > 1` as a proxy for detecting non-EOA callers, exactly analogous to the reported `isContract`/code-size check bypass: any check that infers "is this an EOA / not a contract" from transient EVM execution state (code size, call depth) rather than from a persisted, unambiguous fact can be defeated during contract construction, because a contract executing its own constructor looks identical to a top-level EOA call from the perspective of `GetDepth()`.

### Finding Description
`PrecompileExecutor.Execute` in `precompiles/solo/solo.go` gates the `claim`/`claimSpecific` methods with: [1](#0-0) 
The comment states depth is incremented on entering the precompile call and is "expected to be 1" for a direct EOA call, so `GetDepth() > 1` is rejected as "claim must be called by an EOA directly".

This mirrors the reported `isContract` bug class: just as `extcodesize`/`isContract` returns 0 for a contract still executing its own constructor (because code is not yet persisted), the EVM call-depth counter for a `CREATE`/`CREATE2` transaction sent directly by an EOA starts the constructor's execution context at the same top-level depth as a normal EOA call. If constructor code (the "init code" of a to-be-deployed contract) invokes the `solo` precompile's `claim` method directly, `evm.GetDepth()` will still read `1` at the point the precompile executes — identical to a genuine EOA call — even though the actual caller (`caller` param, i.e., `msg.sender` inside the constructor) is a smart contract address, not an EOA.

The precompile then proceeds into `Claim`/`validate`, which only checks that `claimMsg.GetClaimer()` matches `caller`, and — if it matches and signature verification of the underlying claim message succeeds — moves funds via `bankKeeper.SendCoins`: [2](#0-1) 
Nothing in `validate`/`sigverify` checks whether `caller` is an EOA or a contract; the depth check at `Execute` was the sole mechanism meant to enforce "direct EOA call only," and it is bypassable via constructor-phase execution, exactly as in the original `ContractWhitelist.isContract` finding where a factory contract (`Impersonator`) could stake tokens undetected during its own constructor.

### Impact Explanation
The `claim`/`claimSpecific` code path performs value-moving operations (`bank.SendCoins` of native and CW20/CW721 assets to the caller's associated Sei address). The `GetDepth() > 1` check is the only control preventing this precompile from being invoked as part of arbitrary contract logic (e.g., composed atomically with other calls in the same transaction, or invoked programmatically by deployer-controlled contracts at scale). By deploying a "claimer factory" contract whose constructor calls `solo.claim`/`solo.claimSpecific`, an attacker can have arbitrary contract code — not a plain EOA — execute the fund-transfer logic while satisfying the depth check, defeating the intended access-control invariant and enabling composition of a precompile-level fund transfer with attacker-controlled contract logic in a single atomic transaction that the check was explicitly designed to prevent.

### Likelihood Explanation
This is trivially and deterministically reachable by any unprivileged account: simply send a `CREATE`/`CREATE2` transaction whose init code performs the `claim` call. No special privileges, timing, or race conditions are required — it works every time, exactly like the original `ContractWhitelist` bypass via the `Impersonator` factory PoC.

### Recommendation
Do not rely on `evm.GetDepth()` (or any other transient execution-state signal) to distinguish EOAs from contracts. Instead, explicitly reject calls where `caller` corresponds to a contract account, e.g., by checking `evm.StateDB.GetCodeSize(caller) != 0` in combination with detecting in-construction state (e.g., via `evm.StateDB.GetNonce`/creation flags used elsewhere for account existence), or by requiring `caller == tx.Origin()` at the ante/precompile level, similar to the recommendation in the original report to add defense-in-depth checks at other entry points (e.g., flag/penalize contracts discovered to have invoked EOA-gated precompile paths).

### Proof of Concept
1. Attacker deploys a contract `ClaimerFactory` whose constructor:
   - Computes/derives the future contract address (known deterministically for `CREATE`, or chosen via `CREATE2`).
   - Constructs a valid signed `MsgClaim`/`MsgClaimSpecific` tx bytes where `GetClaimer()` equals this pre-derived contract address.
   - Calls the `solo` precompile at `0x000000000000000000000000000000000000100C` with method `claim`/`claimSpecific` and the encoded tx bytes, directly from the constructor body.
2. Attacker sends a plain `CREATE` transaction (EOA-originated) to deploy `ClaimerFactory`.
3. Inside `Execute` (`precompiles/solo/solo.go:90-116`), `ctx.IsEVM()` is true, `EVMEntryViaWasmdPrecompile()`/`EVMPrecompileCalledFromDelegateCall()` are false, and `evm.GetDepth()` reads `1` because the precompile call is the first CALL made from within the constructor's execution context — identical to a genuine top-level EOA call.
4. The `claim must be called by an EOA directly` check passes despite `caller` being the newly-constructing contract address, and `Claim`/`ClaimSpecific` executes `bankKeeper.SendCoins`, transferring funds to the contract's associated Sei address — from within constructor code, not an EOA. func (p PrecompileExecutor) Claim(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, readOnly bool) (ret []byte, remainingGas uint64, err error) {
	claimMsg, sender, err := p.validate(ctx, caller, args, readOnly)
	if err != nil {
		return nil, 0, err
	}
	_, ok := claimMsg.(claimSpecificMsg)
	if ok {
		return nil, 0, errors.New("message for Claim must not be MsgClaimSpecific type")
	}
	if err := p.bankKeeper.SendCoins(ctx, sender,
		p.evmKeeper.GetSeiAddressOrDefault(ctx, caller), p.bankKeeper.GetAllBalances(ctx, sender)); err != nil {
		return nil, 0, fmt.Errorf("failed to transfer coins: %w", err)
	}
	bz, err := method.Outputs.Pack(true)
	return bz, pcommon.GetRemainingGas(ctx, p.evmKeeper), err
}
