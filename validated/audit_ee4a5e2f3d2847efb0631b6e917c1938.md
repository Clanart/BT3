### Title
`open-external` IPC handler's protocol check is a no-op that never blocks non-http(s) URIs before invoking `shell.openExternal` - ([File: app/src/main-process/main.ts])

### Summary
The bug pattern in the report is a validation check that is computed but never used to gate the guarded action, making it purely decorative. The same anti-pattern exists in `main.ts`'s `open-external` IPC handler: it inspects the URL's scheme, but the result of that inspection is only used for logging, not for allowing/denying the call to `shell.openExternal`. Every URL, regardless of scheme, is forwarded unconditionally.

### Finding Description
The `open-external` handler is registered like this: [1](#0-0) 

```js
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```

The `if` block that tests the URL prefix has no `return`/`else` — it exists solely to produce a log line. Control flow always falls through to `shell.openExternal(path)` with the raw, attacker-influencable string, exactly mirroring the `MegaThetaVault.depositForOwner` pattern where a guard condition is computed but structurally incapable of ever preventing the subsequent state change.

This handler is exposed to the renderer through the preload bridge: [2](#0-1) 
and wired into `app-shell.ts`'s `IAppShell.openExternal`, which is the sole implementation used across the renderer (release notes, PR/check links, markdown links, "view on GitHub", etc.): [3](#0-2) 

Multiple call sites pass strings built directly from GitHub API objects (PR `htmlUrl`, check-run `htmlUrl`, repository `htmlURL`) without any scheme validation upstream, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

Some individual UI components (e.g. `sandboxed-markdown.tsx`'s link interceptor) do their own `/^https?:/` filtering before invoking the callback, but that filtering is inconsistent and not centrally enforced — the actual last line of defense, the `open-external` IPC handler in the main process, does not enforce anything at all.

### Impact Explanation
Because `shell.openExternal` in Electron will hand off arbitrary URI schemes to the OS shell (not just `http(s)`), a check-run URL, PR URL, or other GitHub-API-sourced string (`htmlUrl`) that an attacker controls (e.g. via a malicious/compromised repository, a crafted GitHub Check Run, or a webhook-created PR they own) could contain a non-http(s) URI (`file://`, a custom/registered protocol handler, or on Windows a UNC path like `\\attacker-host\share`). If that string reaches `shell.openExternal` unchanged, the OS may invoke another registered application/protocol handler or attempt an SMB connection, which is a known primitive for credential leak (NTLM hash relay via UNC paths on Windows) or invoking dangerous protocol handlers registered by other installed software — all triggered by the victim simply viewing a PR/check result inside Desktop, i.e. no unusual user action beyond normal use of the app.

### Likelihood Explanation
Several UI call sites forward `htmlUrl`/`clone_url`-style fields sourced from the GitHub API or from webhook/check-run payloads with no scheme validation before calling `dispatcher.openInBrowser`/`shell.openExternal`, and the final chokepoint (`open-external` IPC handler) performs no enforcement — only a no-op logging branch. This makes exploitation dependent solely on getting an attacker-influenced URL string into a check-run or PR object surfaced to the user, which is plausible for a repository/check the attacker controls or contributes to.

### Recommendation
Make the scheme check in the `open-external` IPC handler authoritative: reject (return `false`/throw) for any URL that does not start with `http://` or `https://` (or an explicit allow-list of additional necessary schemes such as `mailto:`), instead of only logging. Additionally, centralize and enforce scheme validation for all `htmlUrl`/`clone_url` values sourced from the GitHub API before they are ever passed to `dispatcher.openInBrowser`.

### Proof of Concept
1. An attacker crafts or controls a GitHub Check Run (or PR) such that `checkRun.htmlUrl` (or an equivalent API-provided URL field) is not `http(s)://` but instead a `file://` URI or a Windows UNC path (`\\attacker\share\x`).
2. Victim opens the corresponding PR/checks view in GitHub Desktop and clicks "View on GitHub" / "View check details" (`ci-check-run-popover.tsx:onViewCheckDetails`, `pull-request-checks-failed.tsx:onViewOnGitHub`).
3. `dispatcher.openInBrowser(url)` → `app-store.ts:_openInBrowser` → `shell.openExternal(url)` (renderer) → IPC `open-external` in `main.ts`.
4. The `if` scheme check in the handler logs but does not block; `shell.openExternal(path)` is invoked with the raw attacker string, causing Electron/OS to act on the non-http(s) URI (e.g., initiate outbound SMB auth to the attacker-controlled UNC host, or invoke another registered protocol handler).
