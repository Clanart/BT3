### Title
Hookify PreToolUse hook fail-open on any exception silently disables `block` rules, allowing dangerous tool calls to proceed unchecked - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The `hookify` plugin's `PreToolUse` hook executor is designed to be the enforcement point that must query the rule engine (the local analog of the EIP-7484 "registry") before a `Bash`/`Edit`/`Write`/`MultiEdit` tool call is allowed to execute. Like the `Bootstrap` contract's `_configureRegistry()` check, this hook's entire purpose is to gate the privileged action (tool execution) on a security decision. However, the implementation wraps the whole decision-making path in a blanket `except Exception` that always resolves to "allow the operation" and always `sys.exit(0)`s, meaning that any error raised while evaluating rules — not just import errors — causes the check to be skipped and the tool call to proceed as if no rule had matched.

### Finding Description
`pretooluse.py` reads hook input, loads rules via `load_rules()`, and evaluates them with `RuleEngine.evaluate_rules()`: [1](#0-0) 

The `finally: sys.exit(0)` combined with `except Exception as e: ... print(...); ` means that regardless of what failure occurs during `evaluate_rules()` (which is where `block` rules are supposed to deny dangerous commands), the hook always terminates with exit code 0 and, critically, produces output containing only a `systemMessage` — never a `hookSpecificOutput.permissionDecision: "deny"`. Per Claude Code's documented hook contract, the absence of a `deny` decision means the tool call is allowed: [2](#0-1) 

The rule evaluation path that is supposed to produce the `deny` decision is `RuleEngine.evaluate_rules()`, which iterates conditions and only returns a deny/block decision when `blocking_rules` is non-empty: [3](#0-2) 

Field extraction (`_extract_field`) and condition matching (`_check_condition`) perform dictionary/string operations (`tool_input.get(...)`, `field_value.startswith(pattern)`, `field_value.endswith(pattern)`, string concatenation on `edits`) without validating that `tool_input` values are the expected types: [4](#0-3) [5](#0-4) 

If any tool call supplies a `tool_input` shape that isn't what these functions expect (e.g., a non-string/non-dict value that causes a `TypeError`/`AttributeError` inside `_check_condition` or `_extract_field`, or an unhandled exception during rule loading in `load_rule_file`/`Rule.from_dict`/`Condition.from_dict` in `config_loader.py`), the exception propagates up through `evaluate_rules()` to `main()` in `pretooluse.py`, is swallowed by the outer `except Exception`, and the tool call is unconditionally allowed. This is structurally identical to the reported `Bootstrap` bug: the security check ("registry"/rule engine) is supposed to gate the privileged action, but a code path exists where the privileged action (tool execution) proceeds without the check ever successfully producing a deny decision — the check is either never reached or its result is discarded in favor of a hardcoded "allow."

### Impact Explanation
An unprivileged user (or a crafted/malicious tool-call payload, e.g., from a compromised MCP tool or an attacker-controlled edit that triggers a specific `tool_input` shape) can cause the `block` rules configured in `.claude/hookify.*.local.md` (e.g., "block `rm -rf`", "block writes to `.env`") to be silently bypassed whenever the rule engine throws an unhandled exception during evaluation. Because the fallback behavior is fail-open (always allow, exit 0), this defeats the entire purpose of the hookify plugin's `PreToolUse` enforcement, allowing destructive Bash commands or sensitive file writes that the user explicitly configured to be blocked. This is a genuine hook-bypass trust-boundary issue reachable by any user relying on hookify's `block` action for safety enforcement.

### Likelihood Explanation
Moderate. Triggering requires a rule file or tool input that causes an uncaught exception somewhere in the rule-loading (`config_loader.py`) or rule-matching (`rule_engine.py`) code paths that isn't already caught by the narrower exception handlers present there (e.g., `re.error`, `IOError`/`OSError`, `ValueError`/`KeyError`/`AttributeError`/`TypeError` in `load_rules`/`load_rule_file` are already caught defensively, reducing but not eliminating the exposed surface). The `_check_condition`/`_extract_field` path in `rule_engine.py` has no such defensive catches, so any malformed `tool_input` field type reaching `startswith`/`endswith`/`in` checks would trigger the fail-open path. This is a design-level fail-open pattern rather than a one-off input validation bug, so it is reliably reproducible once a triggering condition is found.

### Recommendation
Change the fail-open default to fail-closed (or fail-safe with a warning) for `block`-capable events: if `evaluate_rules()` raises, and any loaded rule for the current event has `action: block`, the hook should return a `deny`/`ask` decision (or otherwise not silently allow), rather than defaulting to allow. At minimum, add defensive type-checking in `_check_condition`/`_extract_field` (mirroring the pattern already used in `load_rules`/`load_rule_file`) so that malformed `tool_input` cannot cause exceptions that propagate out of `evaluate_rules()` and trigger the outer fail-open handler in `pretooluse.py`.

### Proof of Concept
1. Configure a blocking rule, e.g. `.claude/hookify.block-rm.local.md` with `event: bash`, `pattern: rm\s+-rf`, `action: block`.
2. Craft a tool call whose `tool_input` for a matched tool/event supplies a field value of an unexpected type for a condition using `starts_with`/`ends_with`/`contains` operators (e.g., a list or `None` where a string is expected) such that `_check_condition` raises `TypeError`/`AttributeError` when calling `.startswith()`/`.endswith()`/`in` on a non-string.
3. This exception propagates through `RuleEngine.evaluate_rules()` up to `pretooluse.py`'s `try` block, is caught by `except Exception`, and the hook prints only a `systemMessage` and exits 0 — no `permissionDecision: deny` is emitted.
4. Because Claude Code's hook contract treats the absence of a deny decision as an allow, the tool call (including the operation the `block` rule was meant to prevent) executes.

Note: I could not execute this PoC against a live Claude Code session (no filesystem/terminal access in this mode), so the exact triggering `tool_input` shape that raises an exception is inferred from the code paths shown above rather than empirically confirmed; a Devin session with code execution would be needed to construct and verify a concrete crashing payload.

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)

    def evaluate_rules(self, rules: List[Rule], input_data: Dict[str, Any]) -> Dict[str, Any]:
        """Evaluate all rules and return combined results.

        Checks all rules and accumulates matches. Blocking rules take priority
        over warning rules. All matching rule messages are combined.

        Args:
            rules: List of Rule objects to evaluate
            input_data: Hook input JSON (tool_name, tool_input, etc.)

        Returns:
            Response dict with systemMessage, hookSpecificOutput, etc.
            Empty dict {} if no rules match.
        """
        hook_event = input_data.get('hook_event_name', '')
        blocking_rules = []
        warning_rules = []

        for rule in rules:
            if self._rule_matches(rule, input_data):
                if rule.action == 'block':
                    blocking_rules.append(rule)
                else:
                    warning_rules.append(rule)

        # If any blocking rules matched, block the operation
        if blocking_rules:
            messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
            combined_message = "\n\n".join(messages)

            # Use appropriate blocking format based on event type
            if hook_event == 'Stop':
                return {
                    "decision": "block",
                    "reason": combined_message,
                    "systemMessage": combined_message
                }
            elif hook_event in ['PreToolUse', 'PostToolUse']:
                return {
                    "hookSpecificOutput": {
                        "hookEventName": hook_event,
                        "permissionDecision": "deny"
                    },
                    "systemMessage": combined_message
                }
            else:
                # For other events, just show message
                return {
                    "systemMessage": combined_message
                }

    def _check_condition(self, condition: Condition, tool_name: str,
                        tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> bool:
        """Check if a single condition matches.

        Args:
            condition: Condition to check
            tool_name: Tool being used
            tool_input: Tool input dict
            input_data: Full hook input data (for Stop events, etc.)

        Returns:
            True if condition matches
        """
        # Extract the field value to check
        field_value = self._extract_field(condition.field, tool_name, tool_input, input_data)
        if field_value is None:
            return False

        # Apply operator
        operator = condition.operator
        pattern = condition.pattern

        if operator == 'regex_match':
            return self._regex_match(pattern, field_value)
        elif operator == 'contains':
            return pattern in field_value
        elif operator == 'equals':
            return pattern == field_value
        elif operator == 'not_contains':
            return pattern not in field_value
        elif operator == 'starts_with':
            return field_value.startswith(pattern)
        elif operator == 'ends_with':
            return field_value.endswith(pattern)
        else:
            # Unknown operator
            return False
