## Analog Found

### Title
Governing node can DOS the network by voting an unbounded `governance.unitprice` value - (File: kaiax/gov/param.go)

### Summary
The Sherlock report describes an admin who can set unbounded fee parameters (`deploymentFee`, `callFee`) that make `paidOnly`-gated functions permanently uncallable. The Kaia analog is the governance parameter `governance.unitprice`, which is Kaia's on-chain minimum gas price. Its `FormatChecker` is `noopFormatChecker`, meaning there is no upper bound enforced on the value that can be ratified through governance voting.

### Finding Description
`governance.unitprice` is registered with `Canonicalizer: uint64Canonicalizer` and `FormatChecker: noopFormatChecker`, the latter of which unconditionally returns `true` for any value: [1](#0-0) [2](#0-1) 

Compare this to other governance parameters that *do* have bespoke bounds, such as `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, which are cross-checked against each other in `checkConsistency` to prevent an inconsistent (and thus economically nonsensical) configuration: [3](#0-2) 

`governance.unitprice`, however, falls into the `default: return nil` bucket of `checkConsistency`, meaning any `uint64` value — including `math.MaxUint64` — passes validation and can be ratified via header governance (in `single` mode, only the `governance.governingnode` needs to vote it, once per epoch): [4](#0-3) 

`UnitPrice` is aggregated into the effective `ParamSet` used for mining/tx validation at each block, as documented in the module's README: [5](#0-4) 

The tx pool (`blockchain/tx_pool.go`) imports the `gov` package specifically to read this parameter and gate transaction acceptance by gas price: [6](#0-5) 

### Impact Explanation
If the governing node ratifies an extreme `governance.unitprice` value (e.g., near `uint64` max), every transaction submitted by any unprivileged sender — plain transfers, contract calls, and fee-delegated transactions alike — would need `gasPrice >= unitprice` to be accepted into the pool/block. Since no ordinary account can realistically supply such a gas price, this effectively halts all transaction processing network-wide: a chain-level DOS reachable from a governance vote, mirroring the reported Factory contract issue where an unbounded fee variable renders `paidOnly` functions permanently unusable for every caller. This is a protocol-level, not merely a single-dApp-level, denial of service.

### Likelihood Explanation
Requires the `governance.governingnode` (in `single` mode, the sole designated governance voter) to cast and have ratified a single vote — a modest privilege bar, but the report's own premise concerns exactly this class of actor ("Admin can DOS with fees") acting maliciously or via bug/misconfiguration. There is no upper bound, sanity check, or governance-consistency guard preventing the vote from taking effect, unlike the `Kip71UpperBoundBaseFee`/`Kip71LowerBoundBaseFee` pair which do have such cross-checks.

### Recommendation
Add a `FormatChecker` for `GovernanceUnitPrice` (and any other economically-unbounded governance parameters lacking one) that enforces a sane maximum, or add a `checkConsistency` rule analogous to the KIP-71 base fee bounds to reject unreasonably large votes before ratification.

### Proof of Concept
1. In `single` governance mode, the account matching `governance.governingnode` calls the `governance_vote` API with `("governance.unitprice", <uint64 max value>)`. [7](#0-6) 
2. At the next epoch boundary, the vote is ratified into `header.Governance` since `checkConsistency` performs no bound check for this parameter. [8](#0-7) 
3. Starting from the following epoch, `GetParamSet(blockNum).UnitPrice` reflects the extreme value, and the tx pool rejects essentially all incoming transactions whose `gasPrice` is below it, halting normal chain operation for every user. [9](#0-8)
