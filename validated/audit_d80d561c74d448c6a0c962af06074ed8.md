### Title
Division-by-zero panic in `consolidatedNode.Split()` can crash reward computation when a validator's CN and CL staking amounts both round to zero - (File: kaiax/staking/staking_info.go)

### Summary
`kaiax/staking/staking_info.go`'s `consolidatedNode.Split()` divides a reward amount by `totalAmount = cnAmountBig + clAmountBig` without checking whether that sum is zero. [1](#0-0) 
Because Go's `math/big.Int.Div` panics on division by zero (unlike Solidity, which reverts), a state where a consolidated node has `CLStakingInfo != nil` but both `StakingAmount == 0` and `CLStakingInfo.CLStakingAmount == 0` will crash the node process during deferred-reward computation, which is analogous to the reported `ProtectionPool.convertToSToken()` division-by-zero bug (a state-dependent variable silently becomes zero, and a later code path assumes it is always non-zero when dividing).

### Finding Description
`StakingAmounts` and `CLStakingInfo.CLStakingAmount` are both derived by rounding down raw staking-contract balances to whole KAIA units: [2](#0-1) 
Any staking/CL-staking balance under 1 KAIA rounds to `0`, so a consolidated node can legitimately have `StakingAmount == 0` while still appearing in `si.CLStakingInfos` (and thus `cn.CLStakingInfo != nil`) if its CL pool balance is also under 1 KAIA at that block.

`Split()` is invoked from `specWithProposerAndFundsFlex` / `specWithProposerAndFunds` for the block's **proposer** node, matched purely by `cn.RewardAddr == config.Rewardbase`, with no minimum-stake guard before calling `Split`: [3](#0-2) [4](#0-3) 
It is also invoked unconditionally inside `assignStakingRewardsFlex`/`assignStakingRewards` for any consolidated node whose combined CN+CL amount exceeds the threshold/minStake — but the `Split()` denominator uses only `StakingAmount + CLStakingAmount`, which is guarded there. The proposer path in `specWithProposerAndFunds*` is the unguarded one: it does not check `cn.StakingAmount >= minStake` before calling `cn.Split(proposer)`, only checking `cn.CLStakingInfo != nil`. [5](#0-4) 

If the current block's proposer's `RewardAddr` matches a consolidated node whose `StakingAmount` (rounded CN stake) is `0` and whose associated `CLStakingInfo.CLStakingAmount` (rounded CL stake) is also `0`, then in `Split()`:
```go
totalAmount := cnAmountBig(0) + clAmountBig(0) // = 0
clAmount := clAmountBig.Mul(...).Div(clAmount, totalAmount) // panics: division by zero
``` [6](#0-5) 

This is directly reachable during ordinary block reward computation (`GetDeferredReward`/`GetBlockReward`), which every full node executes to build/verify blocks and to answer `kaia_getReward`-style RPCs, executed via `getDeferredRewardFullKore`/`getDeferredRewardFullFlex`/`getDeferredRewardFullLegacy`. [7](#0-6) 

### Impact Explanation
A `big.Int` division by zero is an unrecoverable Go runtime panic, not a graceful error return. If this code path executes as part of block processing/state transition or during RPC serving of `GetDeferredReward`, it can crash the calling goroutine/process. If triggered deterministically for a specific block by every node computing that block's reward (which the reward getter must do to build/verify state), it can produce a chain-wide halt or state divergence between nodes that happen to hit vs. avoid the panic path (e.g., depending on whether the node computes rewards for verification). This matches the required "state divergence between honest nodes" / "acceptance-halting" impact class, warranting Medium severity in line with the analog.

### Likelihood Explanation
Likelihood is low-to-moderate and requires natural coincidence rather than attacker-controlled input directly: a validator's RewardAddr must be the current proposer, and both its CN staking amount and its CL staking amount must independently round down to under 1 KAIA at the exact source block used for the staking snapshot, while the CL registry entry for that node still exists (`CLStakingInfo != nil`). This can arise, for example, right after a validator withdraws (or has withdrawn) both CN and CL stake down to dust amounts but has not yet been removed from `CLRegistry`/`AddressBook`, or during transitional unstaking. No privileged transaction sender action is strictly required beyond a staker unstaking their own CN/CL positions to near-zero while remaining a block proposer for one more block; this is plausible under KIP-286's validator lifecycle since demotion happens at epoch boundaries while the panic can be hit on any intervening block.

### Recommendation
In `consolidatedNode.Split()`, guard against a zero denominator:
```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    cnAmountBig := big.NewInt(int64(c.StakingAmount))
    clAmountBig := big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)
    if totalAmount.Sign() == 0 {
        return amount, big.NewInt(0) // or return big.NewInt(0), amount, per desired default
    }
    ...
}
```
Additionally, add the same `cn.StakingAmount >= minStake`-style guard used elsewhere before calling `cn.Split` in `specWithProposerAndFundsFlex`/`specWithProposerAndFunds`, or explicitly special-case `CLStakingAmount == 0`.

### Proof of Concept
Conceptual reproduction (cannot be executed in this read-only session, but derivable from the code paths cited above):
1. Construct a `staking.StakingInfo` where a node `N` has `StakingAmounts[i] = 0` (raw CN balance < 1 KAIA) and `RewardAddrs[i] = R`.
2. Add a `CLStakingInfos` entry for the same node with `CLStakingAmount = 0` (raw CL pool balance < 1 KAIA), so `consolidateNodes()` attaches a non-nil `CLStakingInfo` to `R`'s consolidated node while leaving `StakingAmount == 0`. [8](#0-7) 
3. Set `config.Rewardbase = R` (i.e., `R` proposed the current block) and call `getDeferredRewardFullKore`/`specWithProposerAndFunds(spec, config, proposer, kif, kef, si)`.
4. Execution reaches `cn.Split(proposer)` with `cn.StakingAmount == 0` and `cn.CLStakingInfo.CLStakingAmount == 0`, causing `totalAmount = big.NewInt(0)`, and the subsequent `clAmount.Div(clAmount, totalAmount)` panics with "division by zero", crashing the reward computation. [6](#0-5) 

Note: I was not able to fully verify from the index alone whether `getDeferredReward*` executes inside the core consensus state-transition path (as opposed to only RPC/API serving) for every node on every block — this would materially affect whether the impact is a full chain halt versus a node/RPC-only crash. This should be confirmed by tracing `RewardModule.GetBlockReward`/`GetDeferredReward` callers in `blockchain/` and `work/worker.go` for a background engineering session.

	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))

	for i, n := range si.NodeIds {

			cn.StakingAmount += si.StakingAmounts[i]

				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}

	// CLStakingInfo can only exist after Prague HF.
	if len(si.CLStakingInfos) > 0 {
		for _, clsi := range si.CLStakingInfos {
			// If the nodeId of CLStakingInfo is not found in nToR, it means the validator is not in the AddressBook.
			// So we skip it.

				// One CLStakingInfo per validator is guaranteed by CLRegistry.
				cmap[r].CLStakingInfo = clsi
			}
		}
	}

	carr := make([]consolidatedNode, 0, len(cmap))
	for _, r := range rList {
		carr = append(carr, *cmap[r])
	}
	return &carr
}

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

// getDeferredRewardFullKore is for non-Simple policy and after Kore.
func getDeferredRewardFullKore(config *reward.RewardConfig, execFee, burntFee, blobFee *big.Int, si *staking.StakingInfo) (*reward.RewardSpec, error) {
	var (
		spec             = reward.NewRewardSpec()
		minted           = new(big.Int).Set(config.MintingAmount)
		distributableFee = new(big.Int).Sub(execFee, burntFee)
	)

	// Distribute using RewardRatio first. Unlike Legacy, fees are not distributed here
	// because fees are exclusively allocated to proposer. By the way, remainder goes to KIF.
	validators, kif, kef := config.RewardRatio.Split(minted)
	proposer, stakers := config.Kip82Ratio.Split(validators)
	ratioRemainder := calcRemainder(minted, proposer, stakers, kif, kef)
	kif.Add(kif, ratioRemainder)

	// Further distribute using Kip82Ratio. By the way, remainder goes to proposer.
	// After Prague, if the CLStaking is not nil, the proposer and staking rewards are proportionally distributed to both CN and CL.
	// For proposer rewards, see `specWithProposerAndFunds`.
	stakersAlloc, kip82Remainder := assignStakingRewards(config, stakers, si)
	proposer.Add(proposer, kip82Remainder)
	stakers.Sub(stakers, kip82Remainder)

	// Proposer gets the fees.
	proposer.Add(proposer, distributableFee)

	spec.Minted = minted
	spec.TotalFee = new(big.Int).Add(execFee, blobFee)
	spec.BurntFee = new(big.Int).Add(burntFee, blobFee)
	spec.Stakers = stakers
	for addr, amount := range stakersAlloc {
		spec.IncRecipient(addr, amount)
	}
	spec = specWithProposerAndFunds(spec, config, proposer, kif, kef, si)
	return spec, nil
}
