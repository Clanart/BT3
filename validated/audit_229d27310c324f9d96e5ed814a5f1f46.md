## Title
`pallet-relayer::withdraw` zeroes accrued fees before destination execution succeeds, permanently losing the payout if the destination-side manager rejects the disbursement - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
The External Report's core broken invariant: a claim function permanently forfeits the accrued reward when a downstream disbursement call can revert (there, a `spend_limit` cap on the distributor). The Hyperbridge analog is `pallet-relayer::Pallet::withdraw`, which zeroes the relayer's `Fees` balance immediately after *dispatching* the ISMP withdrawal request — not after confirming it executed — while the request itself is built with `timeout: 0` (never expires) and the destination-side executor (`HostManager`/`BandwidthManager`-style `onAccept`, or the substrate `RefundingRouter`) can revert on insufficient balance, exactly as demonstrated by the existing test `evm/tests/rust/src/tests/host_manager.rs:143` (`test_host_manager_insufficient_balance`).

### Finding Description
`Pallet::withdraw` in [1](#0-0)  reads `available_amount` from `Fees::<T>`, dispatches an ISMP `PostRequest` carrying that exact amount to the destination's `host_manager` (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate), and then unconditionally does:

```rust
Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
```

right after `dispatcher.dispatch_request(...)` succeeds — i.e., after the *request was queued*, not after it was *delivered and executed*. The comment in the module doc even states this directly: "The `Fees` entry is zeroed so the same balance cannot be withdrawn twice" and "the destination chain settles the payout when the ISMP request is delivered there" [2](#0-1) .

The dispatched request has `timeout: 0` [3](#0-2) , meaning it can never be refunded/reversed via the timeout path documented in `docs/content/developers/network/relayer.mdx:742` ("This request will not timeout"). If the destination-side executor rejects the payout — e.g. insufficient fee-token balance in the `host_manager`/manager contract, exactly the scenario already unit-tested in `evm/tests/rust/src/tests/host_manager.rs:143-173` (`WithdrawalParams` with an amount the host manager cannot cover reverts on `SafeERC20` transfer) — the on-chain `Fees` balance is already zero on Hyperbridge. The relayer has no residual accounting entry to retry the claim against; the amount is not re-issued by anything in this pallet, and the same commitment/body was already consumed with the zeroed balance baked into it.

This mirrors the reported bug precisely: a claim function (`withdraw`/`claim_rewards`) commits the accounting state before verifying the downstream `spend`/disbursement call actually succeeds, so a capacity/balance limit on the receiving side turns into permanent loss of the reward rather than a retryable failure.

### Impact Explanation
This falls squarely within the bounty's "stealing or loss of funds" and "double-settlement" categories — here the failure mode is the inverse of double-settlement: it's *loss of settlement*. A relayer's honestly-earned fee balance (`Fees<T>`) is irrecoverably wiped from the pallet's ledger the moment the ISMP dispatch call returns `Ok`, regardless of whether the funds actually reach the beneficiary on the destination chain. Because the request never times out, there is no protocol-level fallback that restores the balance or re-triggers payment.

### Likelihood Explanation
No malicious actor is required — an unprivileged relayer legitimately calling the unsigned `withdraw_fees` extrinsic [4](#0-3)  triggers this path. The only precondition is that the destination `host_manager`/manager contract temporarily lacks sufficient fee-token balance to cover the withdrawal at the moment of delivery — a realistic operational condition (fee-token liquidity drained by other concurrent withdrawals, as shown by the existing insufficient-balance test), not a contrived edge case.

### Recommendation
Do not zero `Fees::<T>` at dispatch time. Instead, either (a) only decrement/zero the balance after a confirmed delivery receipt is proven back to Hyperbridge (mirroring the `accumulate_fees` proof-based crediting flow), or (b) keep the withdrawal request's timeout non-zero and re-credit `Fees::<T>` on `OnTimeout`, so that a reverted/undelivered destination-side disbursement returns the balance to the relayer instead of silently deleting it.

### Proof of Concept
1. Relayer accrues `available_amount` fees for `dest_chain = EVM-X` via `accumulate_fees`.
2. Governance/host or normal operation temporarily leaves the EVM `host_manager` contract holding less fee-token balance than `available_amount` (demonstrated feasible in `evm/tests/rust/src/tests/host_manager.rs:143-173`, `test_host_manager_insufficient_balance`).
3. Relayer calls `withdraw_fees` → `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs:81-187`). The ISMP `dispatch_request` call itself succeeds (it only enqueues the request), so `Fees::<T>::insert(dest_chain, address, U256::zero())` executes unconditionally on line 177.
4. The request is delivered to the destination `host_manager.onAccept`, which reverts on the `SafeERC20` transfer due to insufficient balance (per the cited test).
5. Because `timeout: 0` was set, the request never expires and no refund/re-credit path exists in this pallet.
6. Result: the relayer's `Fees<T>` entry for `(dest_chain, address)` is permanently `0`, and the funds were never disbursed — the reward is lost with no retry mechanism, confirmed against `docs/content/developers/network/relayer.mdx:742` describing "will not timeout" semantics.

//! Once fees have been accumulated into [`crate::pallet::Fees`] by

//!
//! 1. The relayer signs a `(nonce, dest_chain, beneficiary?)` payload with their per-chain key (EVM
//!    secp256k1 / sr25519 / ed25519).

//!    instructing it to disburse `available_amount` of the fee token to the beneficiary.
//! 3. The `Fees` entry is zeroed so the same balance cannot be withdrawn twice.
//!

				.unwrap_or(MinWithdrawal::get())
		{
			Err(Error::<T>::NotEnoughBalance)?
		}

		let dispatcher = <T as Config>::IsmpHost::default();

		Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| {
			*value += 1;
			Ok::<(), ()>(())
		})
		.map_err(|_| Error::<T>::ErrorCompletingCall)?;

		let beneficiary_address = withdrawal_data.beneficiary.clone().unwrap_or(address.clone());
		let (to, body) = match withdrawal_data.dest_chain {
			s if s.is_substrate() => (
				HYPERBRIDGE_MODULE_ID.to_vec(),
				Message::WithdrawRelayerFees(WithdrawalRequest {
					amount: available_amount.low_u128(),
					account: AccountId32::try_from(&beneficiary_address[..])
						.map_err(|_| Error::<T>::InvalidPublicKey)?,
				})
				.encode(),
			),
			_ => {
				let HostParam::EvmHostParam(params) =
					HostParams::<T>::get(withdrawal_data.dest_chain)
						.ok_or_else(|| Error::<T>::MissingMangerAddress)?;

				let body = WithdrawalParams {
					beneficiary_address: beneficiary_address.clone(),
					amount: available_amount.into(),
					token: params.fee_token,
				}
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidPublicKey)?;

				(params.host_manager.0.to_vec(), body)
			},
		};

		let post = DispatchPost {
			dest: withdrawal_data.dest_chain,
			from: MODULE_ID.to_vec(),
			to,
			body,
			timeout: 0,
		};

		// Account is not useful in this case
		dispatcher
			.dispatch_request(
				DispatchRequest::Post(post),
				FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
			)
			.map_err(|_| Error::<T>::DispatchFailed)?;

		Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
