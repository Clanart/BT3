### Title
Unchecked ERC20 return value in Tron IntentGatewayV2's escrow `withdraw()` allows silent loss of escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` imports and enables `SafeERC20` (`using SafeERC20 for IERC20;`) and uses `safeTransferFrom` correctly on the deposit/escrow path, but its escrow **payout** path — the internal `withdraw()` function used for both fills (`RedeemEscrow`) and refunds/cancellations (`RefundEscrow`), and the `SweepDust` handler — reverts to a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks the outer `success` boolean of the call, never decoding/validating the ERC20 return data. [1](#0-0) [2](#0-1) 

This is exactly the bug class described in the external report: a token whose `transfer()` does not revert on failure but instead returns `false` will make the low-level call "succeed" (`success == true`) even though no tokens actually moved. Because the code treats `success == true` as proof of a completed transfer, it decrements the escrow accounting and marks the order filled/refunded regardless of whether the beneficiary actually received anything.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 

`success` only reflects whether the external call reverted, not whether the ERC20 semantically succeeded. Per the ERC20 spec (and exactly the class of non-standard tokens flagged in the external report), a compliant `transfer()` may return `false` on failure instead of reverting. The Tron contract never inspects the returned `bytes` for this boolean, so a `false` return is silently treated as a successful transfer.

The same pattern appears in the `SweepDust` handler inside `onAccept`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

and for the transaction-fee redemption inside `withdraw()`:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [5](#0-4) 

Critically, `beneficiary = address(uint160(uint256(body.beneficiary)))` and `_filled[body.commitment] = beneficiary;` is set unconditionally at the top of `withdraw()` before any transfer is attempted, so once the accounting has run there is no retry path — the order is permanently marked filled/refunded. [6](#0-5) 

By contrast, the deposit/escrow side of the same contract correctly uses `safeTransferFrom`, which does validate return data: [7](#0-6) [8](#0-7) 

This creates an asymmetry: token *inflow* into escrow is safely checked, but token *outflow* from escrow (the actual settlement of the intent — the core invariant "assets move exactly once and only to the rightful beneficiary and amount") is not.

### Impact Explanation
Order `input` tokens are user-supplied (chosen by whoever creates the order) and are not restricted to a governance-vetted allowlist the way `SimplexPaymaster`'s tokens are. An order creator can therefore pick an arbitrary, attacker-authored ERC20 contract as the order's input token. Such a token can:
- Behave as a fully standard ERC20 for `transferFrom` (so the initial escrow deposit via `safeTransferFrom` succeeds and looks legitimate to solvers/relayers observing on-chain state).
- Deliberately return `false` (without reverting) from `transfer()` when called by the `IntentGateway` at payout time (e.g., conditioned on the caller or the recipient being the solver rather than the original depositor).

A solver who fills such an order (delivering real value on the output side of the trade) then calls the redemption path (`RedeemEscrow` via `onAccept`, ultimately `withdraw()`), which "succeeds" per the unchecked low-level call, decrements `_orders[commitment][token]`, and permanently marks `_filled[commitment]` — but the solver's tokens never move. The escrowed balance remains stuck in the contract while the attacker who authored the token keeps whatever value the solver paid out on the other leg of the trade. This is a direct loss-of-funds / wrong-beneficiary outcome for an unprivileged counterparty (the solver), triggered entirely by an unprivileged order creator choosing a malicious token — no relayer, prover, admin, or governance compromise is required.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker must deploy and get a solver to accept an order denominated in a custom token they control, and (2) `SafeERC20`/`safeTransferFrom` is already used and enforced correctly on the deposit leg, so the attack surface is specifically the payout leg. However, since the Intent Gateway is a permissionless, open marketplace where solvers bid on arbitrary token pairs, and there is no on-chain allowlist restricting `order.inputs[].token` to known-good ERC20 contracts, a solver (or automated filler) that doesn't do off-chain token vetting is directly exposed. This is a realistic risk for an intents/solver marketplace rather than a purely theoretical one.

### Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()` for both the token loop and the `TRANSACTION_FEES` redemption, and in the `SweepDust` branch of `onAccept`) with `IERC20(token).safeTransfer(beneficiary, amount)`, consistent with how the file already handles `safeTransferFrom` on the deposit side and consistent with the main (non-Tron) `IntentGatewayV2.sol`/`EvmHost.sol` which use `safeTransfer` for their equivalent payouts. [9](#0-8) 
If Tron-chain USDT/TRC20 return-data quirks are the reason the raw call pattern was chosen (to avoid `SafeERC20`'s strict ABI-decoding reverting on some Tron tokens), then at minimum decode and check the returned boolean when data is present, mirroring `SafeERC20`'s own logic (`success && (returndata.length == 0 || abi.decode(returndata, (bool)))`), rather than relying on `success` alone.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20-like contract where:
   - `transferFrom(from, to, amount)` behaves like a standard token (real balance is debited from `from` and credited to `to`, always returns `true`).
   - `transfer(to, amount)` conditionally returns `false` (no revert) whenever `to != attacker` (or based on any attacker-chosen condition targeting the solver's address), while doing nothing to balances.
2. Attacker creates an intent `Order` with `order.inputs[0].token = EvilToken`, `order.inputs[0].amount = X`, and an attractive `output`/fee that a solver will want to fill.
3. Order placement calls `IERC20(token).safeTransferFrom(msg.sender, address(this), amount)` — succeeds normally, escrowing real `EvilToken` balance in the gateway, and `_orders[commitment][EvilToken] += amount` is recorded.
4. A solver fills the order, delivering the promised output value, and later triggers `RedeemEscrow` (same-chain: direct `withdraw()`; cross-chain: via `onAccept`).
5. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, solver, X))` invokes `EvilToken.transfer(solver, X)`, which returns `(true, abi.encode(false))` — the call does not revert, so `success == true`.
6. The code only checks `success`, so it proceeds: `_orders[commitment][EvilToken] -= X` and `_filled[commitment] = solver` are recorded as if the payment succeeded, but `EvilToken.balanceOf(solver)` is unchanged and `EvilToken.balanceOf(gateway)` still holds the escrowed `X`.
7. The solver has delivered value on the other leg of the trade but never receives their `EvilToken` payout, and the order is now permanently marked `Filled`, so there is no retry — a documented, provable loss-of-funds outcome directly attributable to the missing ERC20 return-value check.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
