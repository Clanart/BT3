### Title
Forged aggregate Schnorr signatures accepted because aggregation weights don't bind the nonces/keys - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to CVE-2022-31126's "unauthenticated remote attacker controls the outcome via a crafted request", an unauthenticated party submitting a `SchnorrAggregate` (e.g., via `SchnorrAggregate::read` of untrusted bytes, used in the Tendermint batch-signature path) can forge an aggregate signature that `SchnorrAggregate::verify` accepts for arbitrary public keys and challenges. The aggregation weights `z_i` are derived from a transcript that commits only to the per-signature *challenges* — never to the `R_i` points nor the public keys being verified — so the weights are fully predictable to the prover before it chooses `Rs` and `s`.

### Finding Description
`SchnorrAggregate::verify` reconstructs weights via a `DigestTranscript` seeded with `dst` and `domain_separate(b"signatures")`, then appends only `challenge.to_repr()` for each entry in `keys_and_challenges` (aggregate.rs:132-136). The `Rs` from the signature under verification and the public keys `A_i` are never transcripted into the weight derivation. Verification then checks `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G == 0` via `multiexp_vartime` (aggregate.rs:138-145).

Because `z_i` are a deterministic function of only the challenges (which are verifier-supplied inputs, not prover commitments), a malicious prover can compute all `z_i` first, then algebraically solve for `R_1` and `s` to satisfy the batch equation without knowing any discrete logarithm. In the correct half-aggregation construction (eprint 2021/350), the weights must be bound to the full aggregate statement (nonces and keys) so that the prover cannot choose `R_i` after learning `z_i`.

### Impact Explanation
Any verifier relying on `SchnorrAggregate::verify` accepts signatures over keys whose discrete logs the prover does not know — a universal forgery of the aggregated signature. `SchnorrAggregate`/`SchnorrAggregator` is consumed by `coordinator/tributary/src/tendermint/mod.rs` for aggregated validator signatures, so an unauthenticated party can fabricate an aggregate signature that passes verification for an arbitrary validator key set. This yields a forged signature — a Critical/High impact by the stated criteria.

### Likelihood Explanation
The forgery requires no private-key knowledge and only public inputs (the `keys_and_challenges` the verifier will check). The prover reads the deterministic `DigestTranscript` sequence to obtain `z_i`, solves one linear equation over the group, and serializes the forged `SchnorrAggregate`. Any code path feeding attacker-controlled bytes to `SchnorrAggregate::read` then `verify` (as the Tendermint message path does) is directly exploitable. Note that `SchnorrAggregator::complete` computes `s` consistently only for an aggregator holding genuinely valid component signatures; the flaw is that `verify` cannot distinguish that from a solver-chosen `(Rs, s)`.

### Recommendation
Bind the entire statement into the weight transcript before deriving each `z_i`: append each `R_i` encoding and each public key encoding (e.g., `digest.append_message(b"R", R_i.to_bytes()); digest.append_message(b"key", key.to_bytes())`) alongside the challenge, or hash a commitment to the full `(Rs, keys, challenges)` tuple into the transcript prior to weight derivation. This restores the Fiat-Shamir ordering so weights are unpredictable until the aggregate is fixed.

### Proof of Concept
Conceptual (no Rust harness needed to exhibit the algebra):

1. Verifier calls `agg.verify(dst, &[(A_1, c_1), (A_2, c_2), …])` with honest public keys/challenges.
2. Attacker replays the transcript locally: `DigestTranscript::new(dst)`, `domain_separate(b"signatures")`, `append_message(b"challenge", c_i)` for each i, then calls `weight(&mut digest)` per index — obtaining `z_1, …, z_n` exactly as `verify` computes them (they depend only on `dst` and the challenges).
3. Attacker picks `R_i` arbitrarily for i ≥ 2 (e.g., generator multiples with known dlog, or identity) and a random scalar `r`. Sets:
   - `s = z_1 · r`
   - `R_1 = r·G − c_1·A_1 − Σ_{i≥2} (z_i · z_1^{-1}) · (R_i + c_i·A_i)`
4. Serializes `SchnorrAggregate { Rs: [R_1, …, R_n], s }` and submits it.
5. `verify` evaluates `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G = z_1·(r·G − Σ_{i≥2}(z_i/z_1)(R_i + c_i·A_i)) + Σ_{i≥2} z_i(R_i + c_i A_i) − z_1·r·G = 0` → accepts.

The forged aggregate verifies against arbitrary keys `A_i` and challenges `c_i` despite the attacker knowing no secret keys — confirmed by the weight derivation at `crypto/schnorr/src/aggregate.rs` (lines 22-65 for `weight`, 127-146 for `verify`).
