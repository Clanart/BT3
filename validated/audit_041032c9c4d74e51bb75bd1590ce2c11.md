### Title
Unauthenticated broadcasting call via `AggregatorServer::internal_send_tx` (`InternalSendTx`) - (`core/src/rpc/aggregator.rs`)

### Summary
The aggregator's gRPC server does not enforce mTLS client-certificate authentication the way operator/verifier servers do — `docs/usage.md` states explicitly that "the aggregator does not enforce client certificates but does use TLS for encryption," while verifier/operator servers restrict `Internal*` methods to the caller's own certificate via `only_aggregator_and_self`. `internal_send_tx` deserializes an attacker-supplied `raw_tx` and passes it straight to `TxSenderClient::insert_try_to_send` with no signature, ownership, or provenance check on the bytes.

### Finding Description
The binding claimed to be broken: CALLER_AUTHORITY(caller reaching `/clementine.ClementineAggregator/InternalSendTx`) == HOLDER(aggregator's own client certificate). For verifier/operator servers this equality is enforced by `only_aggregator_and_self` in `core/src/rpc/interceptors.rs` [1](#0-0) , gated on `is_internal` matching the `Internal*` path prefix. That interceptor selection is driven by `config.client_verification` in `core/src/servers.rs` [2](#0-1) .

For the aggregator specifically, the documentation states this authorization is not applied at all: "The aggregator does not enforce client certificates but does use TLS for encryption," in contrast to operator/verifier which restrict `Internal` methods to self-cert holders [3](#0-2) . Under that condition (which matches the question's stated precondition `client_verification=false`/`Noop`), `internal_send_tx` on `AggregatorServer` is reachable by any party that can open a TLS (or unauthenticated) connection to the aggregator's gRPC port, and the handler performs no additional signature/ownership validation before calling `tx_sender.insert_try_to_send`, which itself only checks for duplicate txid before persisting the raw bytes [4](#0-3) . The proto/generated stub confirms the path and unauthenticated shape of the call: `rpc InternalSendTx(SendTxRequest) returns (Empty)` [5](#0-4) , and the e2e test demonstrates exactly this call pattern being used to queue a raw signed tx for broadcast [6](#0-5) .

Existing guards fail here specifically because the `only_aggregator_and_self` check that protects `Internal*` methods on verifier/operator servers is not applied to the aggregator's own server (per docs), and `insert_try_to_send`/`save_tx` never validate that `raw_tx` is a transaction the system itself produced or signed [7](#0-6) .

### Impact Explanation
This matches the High-severity category "an unauthenticated state-changing or broadcasting call": an unauthenticated caller can insert an arbitrary attacker-chosen transaction into the aggregator's own `tx_sender` broadcast/fee-bump queue. However, actually moving bridge value, causing a wrong reimbursement, or burning honest collateral would additionally require the attacker's `raw_tx` to carry a *valid* signature/witness for a bridge-controlled or fee-payer-wallet UTXO in order to be accepted by Bitcoin Core and confirm on-chain (e.g., to RBF-conflict a pending Reimburse/Challenge fee-payer input) — the attacker in this threat model holds no signing keys for those UTXOs, so a forged conflicting spend would be rejected at broadcast time by the node's mempool policy/signature checks. Absent forged signatures, the practical effect is limited to using the aggregator as an unauthenticated relay for self-signed, self-funded transactions, which by itself does not move bridge funds. The underlying authentication gap is nonetheless real and repeatable across any RPC path on the aggregator server, not just `InternalSendTx`.

### Likelihood Explanation
The scenario requires the aggregator's gRPC port to be reachable by the attacker and (per the question) `client_verification=false`. Every committed configuration in the repository (`core/src/test/data/bridge_config.toml`, `scripts/docker/configs/testnet4/bridge_config.toml`, `.env.example`) sets `client_verification = true` by default, so this depends on either (a) a deliberate operator misconfiguration, or (b) the aggregator's design genuinely never enforcing client certs regardless of the flag, as `docs/usage.md` states unconditionally. The exact code path selecting the interceptor for the aggregator server specifically (`create_aggregator_grpc_server` construction) could not be fully re-verified in this session due to tool-call limits, so it remains unconfirmed whether `client_verification=true` would still protect the aggregator or whether the aggregator server unconditionally omits the cert-restriction logic that operator/verifier servers apply.

### Recommendation
Apply the same `only_aggregator_and_self`-style (or equivalent self-cert) restriction to the aggregator's own `Internal*` RPC surface, and additionally validate that any `raw_tx` submitted to `InternalSendTx` corresponds to a transaction the aggregator/verifiers/operators actually produced (e.g., cross-check against the presigned transaction graph or require an authenticated caller identity) before calling `insert_try_to_send`.

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }

    pub async fn insert_try_to_send(
        &self,
        dbtx: &mut crate::TxSenderTransaction,
        tx_metadata: Option<TxMetadata>,
        signed_tx: &Transaction,
        fee_paying_type: FeePayingType,
        rbf_signing_info: Option<RbfSigningInfo>,
        cancel_outpoints: &[OutPoint],
        cancel_txids: &[Txid],
        activate_txids: &[ActivatedWithTxid],
        activate_outpoints: &[ActivatedWithOutpoint],
    ) -> Result<u32, BridgeError> {
        let txid = signed_tx.compute_txid();

        // do not add duplicate transactions to the txsender
        let tx_exists = self
            .db
            .check_if_tx_exists_on_txsender(Some(dbtx), txid)
            .await?;
        if let Some(try_to_send_id) = tx_exists {
            return Ok(try_to_send_id);
        }

        tracing::info!(
            "Added tx {} with txid {} to the queue",
            tx_metadata
                .as_ref()
                .map(|data| format!("{:?}", data.tx_type))
                .unwrap_or("N/A".to_string()),
            txid
        );

        let try_to_send_id = self
            .db
            .save_tx(
                dbtx,
                tx_metadata,
                signed_tx,
                fee_paying_type,
                txid,
                rbf_signing_info,
            )
            .await?;

    pub async fn save_tx(
        &self,
        tx: TxSenderDbTx<'_>,
        tx_metadata: Option<TxMetadata>,
        raw_tx: &Transaction,
        fee_paying_type: FeePayingType,
        txid: Txid,
        rbf_signing_info: Option<RbfSigningInfo>,
    ) -> Result<u32, BridgeError> {
        let query = sqlx::query_scalar(
            r#"
            INSERT INTO tx_sender_try_to_send_txs
            (raw_tx, fee_paying_type, tx_metadata, txid, rbf_signing_info)
            VALUES ($1, $2::fee_paying_type, $3, $4, $5)
            ON CONFLICT (txid)
            DO UPDATE SET txid = EXCLUDED.txid
            RETURNING id
            "#,
        )
        .bind(serialize(raw_tx))
        .bind(fee_paying_type)
        .bind(serde_json::to_string(&tx_metadata).wrap_err("Failed to encode tx_metadata to JSON")?)
        .bind(TxidDB(txid))
        .bind(
            serde_json::to_string(&rbf_signing_info)
                .wrap_err("Failed to encode rbf_signing_info to JSON")?,
        );

        let id: i32 = query.fetch_one(&mut **tx).await?;
        u32::try_from(id)
            .wrap_err("Failed to convert id to u32")
            .map_err(Into::into)
    }
