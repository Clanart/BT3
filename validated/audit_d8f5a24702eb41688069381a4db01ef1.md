## Finding: Unchecked ERC20 boolean return value in outbound escrow release paths (Tron IntentGatewayV2)

### Title
Outbound token transfers in `withdraw()` and `SweepDust` ignore the decoded ERC20 return value, allowing escrow to be marked released while tokens remain stuck - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` imports and uses `SafeERC20` correctly for *inbound* transfers (`safeTransferFrom`) when escrowing order inputs, but for *outbound* transfers — releasing escrow to solvers/beneficiaries in `withdraw()` and sweeping dust in `onAccept()`'s `SweepDust` branch — it bypasses `SafeERC20` entirely and uses raw low-level calls that only check `success` (i.e., that the call didn't revert), never decoding/validating the ERC20 boolean return value.

### Finding Description
In `withdraw()`: [1](#0-0) 
and in the `SweepDust` handler of `onAccept()`: [2](#0-1) 
the code performs `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only reverts if `success` is `false` (i.e., the call itself reverted). It never inspects the returned bytes to check the decoded boolean.

This is the mirror-image analog of the reported `BoostSideKick` bug: that report was about a token *not returning a bool at all* (causing reverts); the local analog here is a token that returns a bool that is explicitly `false` (a legacy, fully-standard-compliant transfer-failure signal used by several real ERC20s) without reverting. Because `success` (call-level) is decoupled from the ERC20-level success flag, this contract treats such a `false`-returning failed transfer as a full success.

Crucially, escrow accounting is updated *before or independent of* verifying the true transfer outcome: [3](#0-2) 
`_filled[body.commitment]` is set and `_orders[body.commitment][token] -= amount` is decremented as soon as the raw call doesn't revert — regardless of whether `amount` tokens actually moved.

Note that the sibling non-Tron implementation in `evm/src/apps/intentsv2/IntentsBase.sol` correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` for the equivalent outbound release path: [4](#0-3) 
confirming that the Tron variant's manual pattern is an inconsistent, weaker implementation of the same logic rather than an intentional design choice.

### Impact Explanation
For any escrowed token whose `transfer()` implementation returns `false` on failure instead of reverting (a valid, standards-compliant ERC20 behavior pattern), a failed release/refund/sweep will be recorded as successful:
- `_orders[commitment][token]` is decremented and `_filled[commitment]` is finalized, permanently closing the order's escrow accounting.
- `EscrowReleased`/`EscrowRefunded`/`DustSwept` events fire claiming funds were delivered.
- The beneficiary/solver receives zero tokens, and the tokens remain permanently stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them (the escrow ledger for that commitment/token is already zeroed).

This matches the bounty's "stealing or loss of funds" / "false ... acceptance" class: legitimate escrowed value is lost/locked due to the contract falsely accepting a failed on-chain transfer as a completed settlement.

### Likelihood Explanation
This triggers under normal usage without any malicious actor, relayer, or governance compromise — it only requires an intent order whose input/output token has a `transfer()` that can return `false` (e.g., insufficient balance edge cases, paused/blacklisted recipient in some legacy token implementations, or any ERC20 that follows the pre-OpenZeppelin "return false on failure" convention). Any Hyperbridge-relayed `RedeemEscrow`/`RefundEscrow`/`SweepDust` message processed by `onAccept()` for such a token hits this path automatically.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` outbound-transfer patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with `IERC20(token).safeTransfer(...)` (the contract already has `using SafeERC20 for IERC20;` and uses it correctly for inbound transfers), so the decoded boolean return value is validated consistently with the rest of the codebase, and finalize escrow/`_filled` state only after a verified successful transfer.

### Proof of Concept
1. Create a cross-chain order whose output/input token is a standards-compliant ERC20 that returns `false` (not a revert) when a `transfer()` call fails (e.g., due to a transient balance/allowance edge case reachable during settlement, or a token with a "soft-fail" transfer mode).
2. Drive the order through normal fill/cancel flow so that Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` message to `onAccept()`, invoking `withdraw()`.
3. Inside `withdraw()`, the low-level `token.call(...)` returns `success = true` (call didn't revert) but with `returndata` decoding to `false`.
4. Observe: `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, `EscrowReleased` is emitted — yet the beneficiary's token balance is unchanged, and the tokens remain trapped in the `IntentGatewayV2` contract with no remaining code path to recover them for that commitment.
