## Title
`onOpenInExternalEditor` resolves diff/PR file paths with unguarded `Path.join`, bypassing the repo-boundary check applied elsewhere - (File: `app/src/ui/app.tsx`)

## Summary
The DODO finding is about a numeric invariant (`curPoolInfo.weight` contributing to `totalWeight`) that is *never validated* at the point of use, even though the surrounding code clearly assumes it is bounded. The Desktop analog is a **path invariant** that is enforced in one code path but silently skipped in a structurally identical sibling path: the "open file in external editor" flow builds a filesystem path from an attacker-influenced string using a raw `Path.join` instead of the vetted `resolveWithin` helper that the rest of the codebase uses for exactly this purpose.

## Finding Description
Desktop has a dedicated, audited primitive for turning an untrusted relative path into a path guaranteed to stay inside a repository root:

```ts
// app/src/lib/path.ts
export function resolveWithin(rootPath: string, ...pathSegments: string[]): Promise<string | null>
``` [1](#0-0) 

This is correctly used by the "Open repository from URL" deep-link handler, which also explicitly rejects absolute paths before calling it:

```ts
if (isAbsolute(filepath)) {
  log.error(`Refusing to open absolute path: ${filepath}`)
  return
}
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else {
  log.error(`Prevented attempt to open path outside of the repository root: ${filepath}`)
}
``` [2](#0-1) 

However, the sibling "open file in external editor" handler — reachable from the Changes list, commit/diff history, stash viewer, and pull-request "Files changed" view — performs the equivalent join **without** the boundary check or absolute-path rejection:

```ts
private onOpenInExternalEditor = (path: string) => {
  const repository = this.state.selectedState?.repository
  if (repository === undefined) {
    return
  }
  const fullPath = Path.join(repository.path, path)
  this.props.dispatcher.openInExternalEditor(fullPath)
}
``` [3](#0-2) 

`Path.join` normalizes `..` segments but does **not** clamp the result to stay under `repository.path` — `Path.join('/repo', '../../etc/passwd')` legitimately resolves to `/etc/passwd`. This handler is fed `path` values that originate from:
- diff entries in commit/stash history (`app/src/ui/history/selected-commits.tsx`, `app/src/ui/stashing/stash-diff-viewer.tsx`),
- the Changes sidebar (`app/src/ui/changes/sidebar.tsx`),
- and — most importantly — the **pull request "Files changed" list**, sourced from the GitHub API (`app/src/ui/open-pull-request/pull-request-files-changed.tsx`).

All four call sites route into this same `Path.join`-only sink via `dispatcher.openInExternalEditor`, exactly the "many pools reuse one unchecked weight" pattern from the original report: one enforcement point (`resolveWithin` in the deep-link handler) exists, but the invariant it enforces is not applied at every consumer of attacker-influenced path data.

## Impact Explanation
A malicious repository owner (or a compromised/forked repo used in a PR review) can name a file with `../` traversal segments so that the path returned by the GitHub API "files changed" payload, or present in a fetched commit's tree, escapes the repository root once joined with `repository.path`. When the victim uses "Open in External Editor" on that entry, Desktop opens (and depending on the configured editor, may write to or create) a file outside the intended repository directory — the exact "file write or read outside the repo" impact class called out as valid for this scan.

## Likelihood Explanation
Exploitation requires the victim to interact with a crafted PR/commit inside Desktop and click "Open in External Editor" on the malicious entry — a normal reviewing workflow, not an unnatural user step. The attacker fully controls the string that ends up in `path` (a GitHub API object field or tracked/renamed file name), satisfying the "attacker controls a fetched repository or GitHub API object" precondition. The fact that Desktop already treats this exact scenario as attacker-controlled and defends it in the deep-link code path (`dispatcher.ts:1957-1972`) but not in `app.tsx:3429-3437` indicates the missing check is an oversight rather than an intentionally accepted risk.

## Recommendation
Route `onOpenInExternalEditor` (and any other direct `Path.join(repository.path, path)` call feeding `openInExternalEditor`) through `resolveWithin(repository.path, path)`, rejecting absolute paths and paths for which `resolveWithin` returns `null`, mirroring the guard already implemented in `dispatcher.ts`'s `openRepositoryFromUrl`.

## Proof of Concept
1. Attacker opens a pull request (or pushes a commit) whose diff contains a file entry whose reported path is `../../../../../../../.ssh/authorized_keys` (or similar), surfaced to Desktop via the GitHub API "files changed" payload or a crafted tree entry.
2. Victim reviews the PR in Desktop's "Files changed" tab (`app/src/ui/open-pull-request/pull-request-files-changed.tsx`) or views the commit in history, and clicks "Open in External Editor" for that entry.
3. `onOpenInExternalEditor` computes `Path.join(repository.path, '../../../../../../../.ssh/authorized_keys')`, which resolves outside the repository, and this path is handed to `dispatcher.openInExternalEditor` with no `resolveWithin` containment check. [3](#0-2) 
4. The configured external editor opens (and can be made to save/overwrite) the out-of-repo file, unlike the identical deep-link flow which would have blocked this with `resolveWithin`. [2](#0-1) 

Note: I was unable to fully trace, within this session, the exact sanitization (if any) applied to PR "files changed" paths as they come off the GitHub API before reaching `onOpenInExternalEditor`; confirming whether GitHub's API itself would ever return such a value, or whether an intermediate layer strips `..` segments, would require deeper tracing of `app/src/lib/stores/app-store.ts` and the PR files-changed data pipeline than was possible with the remaining tool budget.
