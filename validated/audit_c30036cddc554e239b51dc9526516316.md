### Title
Merge preview validates one commit but `git merge` resolves the branch name again, letting a remote race silently merge different attacker commits - ([File: app/src/lib/git/merge.ts])

### Summary
When a user picks a branch to merge in `MergeChooseBranchDialog`, Desktop computes a merge preview (mergeability/conflicts and commit count) against a specific, pinned commit SHA, and only guards against the *locally selected* branch changing. It does not re-validate that the branch's tip is still the same SHA at the moment the user clicks "Merge". The actual merge, dispatched via `dispatcher.mergeBranch`, is executed by `merge()` using the branch **name**, so `git merge <branch>` re-resolves the ref at execution time.

### Finding Description
`MergeChooseBranchDialog.updateStatus` computes `mergeStatus` and `commitCount` from `determineMergeability(repository, currentBranch, branch)` and `getAheadBehind`, using `branch.tip.sha` at the time of the check: [1](#0-0) 

The only staleness guard compares `this.state.selectedBranch?.tip.sha` to the `branch` argument passed into the same call, i.e. it protects against the user switching branches mid-flight, not against the same branch's remote-tracking tip advancing (e.g., a background fetch pulling in new commits an attacker pushed to a shared/forked branch) between when the preview was computed and when the user clicks the "Merge" button.

When the user clicks start, `MergeChooseBranchDialog.start` passes the previously computed `mergeStatus` object and the `Branch` object to `dispatcher.mergeBranch`: [2](#0-1) 

The underlying git operation, `merge()`, is invoked with `branch` as a **name string**, not the SHA that was actually validated by `determineMergeability`: [3](#0-2) 

Because `git merge <branch-name>` re-resolves the ref at execution time, any ref update between the preview computation and the click (which can happen automatically via `BackgroundFetcher`, which runs on a timer independent of user action and refreshes remote-tracking refs) will cause Desktop to merge a different, unreviewed set of commits than the ones represented in the "clean merge"/"N conflicted files" preview the user approved: [4](#0-3) [5](#0-4) 

The corrupted value is the merge commit's actual parent/tree content: the user believes they are merging the commits shown in `renderCleanMergeMessage`/`renderConflictedMergeMessage` (built from `mergeStatus` and `commitCount` computed against a stale SHA), but the executed `git merge` command silently incorporates whatever commits are on the branch tip at execution time — commits the attacker (owner of the forked/shared branch, or anyone who can push to it before the local merge executes) placed there after the preview ran and before the click, without re-triggering conflict/mergeability review.

### Impact Explanation
This falls under "silent corruption of what the user commits/pushes": the merge commit produced and later pushed by the user can contain content the user never reviewed or approved, because the UI's mergeability/conflict preview was computed against a now-stale commit. This can be leveraged by an attacker who controls a branch the victim is about to merge (e.g., a collaborator's branch, a fork, or any remote the victim fetches from) to smuggle unreviewed changes into the victim's merge commit that gets committed and potentially pushed upstream.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires precise timing — the attacker must push new commits to the target branch, and the victim's Desktop instance must fetch and update the local ref for that branch (which can happen via `BackgroundFetcher`'s periodic background fetch, running independent of user action) in the window between the merge preview computation and the user clicking "Merge". There's no explicit lock preventing background fetch from updating refs while the merge-choose-branch dialog is open, and no re-validation immediately before invoking `git merge`.

### Recommendation
**Short term:** Re-resolve and re-validate the target branch's tip SHA immediately before invoking `merge()`, and pin the merge to that exact SHA (e.g., `git merge <sha>`) rather than the mutable branch name, or re-run `determineMergeability` right before executing the merge and abort/re-prompt if the tip has changed since the preview was last computed.

**Long term:** Pause or suppress background ref-updating operations (background fetch, pull request updater) for a repository while a multi-commit operation dialog (merge/rebase/cherry-pick choose-branch flow) is open and awaiting user confirmation, similar to how `isPushPullFetchInProgress`/`isCommitting` guards already prevent concurrent conflicting operations elsewhere in `app-store.ts`.

### Proof of Concept
1. Victim opens the "Merge into current branch" dialog and selects `attacker-branch` (tip `A`). Desktop runs `determineMergeability` and `getAheadBehind` against SHA `A`, showing "This will merge 3 commits ... clean".
2. Before the victim clicks "Merge", the attacker (who has push access to `attacker-branch`, e.g. a shared branch or a fork the victim added as remote) pushes new commits, advancing the branch to tip `B`.
3. Desktop's `BackgroundFetcher` (running on its independent timer) fetches and updates the local remote-tracking ref for `attacker-branch` to `B` — this happens without any interaction with the open dialog, and `updateStatus` is not re-invoked because `onSelectionChanged` isn't retriggered.
4. Victim clicks "Merge", still seeing the stale "3 commits, clean" preview validated against `A`.
5. `dispatcher.mergeBranch` → `merge()` runs `git merge attacker-branch`, which resolves to `B`, silently merging the attacker's additional/different commits that were never shown in the conflict/mergeability preview. [6](#0-5) [3](#0-2)

  private updateStatus = async (branch: Branch) => {
    const { currentBranch, repository } = this.props

    const mergeStatus = await determineMergeability(
      repository,
      currentBranch,
      branch
    ).catch<MergeTreeResult>(e => {
      log.error('Failed determining mergeability', e)
      return { kind: ComputedAction.Clean }
    })

    // The user has selected a different branch since we started or the branch
    // has changed, so don't update the preview with stale data.
    //
    // We don't have to check if the state changed from underneath us if we
    // loaded the status from cache, because that means we never kicked off an
    // async operation.
    if (this.state.selectedBranch?.tip.sha !== branch.tip.sha) {
      return
    }

    // Can't go forward if the merge status is invalid, no need to check commit count
    if (mergeStatus.kind === ComputedAction.Invalid) {
      this.setState({ mergeStatus })
      return
    }

    // Commit count is used in the UI output as well as determining whether the
    // submit button is enabled
    const range = revSymmetricDifference('', branch.name)
    const aheadBehind = await getAheadBehind(repository, range)
    const commitCount = aheadBehind ? aheadBehind.behind : 0

    if (this.state.selectedBranch.tip.sha !== branch.tip.sha) {
      return
    }

    this.setState({ commitCount, mergeStatus })
  }

export async function merge(
  repository: Repository,
  branch: string,
  options?: MergeOptions
): Promise<MergeResult> {
  const onTerminalOutputAvailable = options?.onTerminalOutputAvailable
    ? createMultiOperationTerminalOutputCallback(
        options?.onTerminalOutputAvailable
      )
    : undefined

  const args = ['merge']

  if (options?.squash) {
    args.push('--squash')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  args.push(branch)

  const { exitCode, stdout } = await git(args, repository.path, 'merge', {
    expectedErrors: new Set([GitError.MergeConflicts]),
    interceptHooks: ['pre-merge-commit', 'post-merge', 'commit-msg'],
    onHookProgress: options?.onHookProgress,
    onHookFailure: options?.onHookFailure,
    onTerminalOutputAvailable,
  })

    }

      return
    }
