This confirms it: `IDatabaseOwner` is keyed by `getOwnerKey(endpoint, login)` — a case-insensitive login string, not GitHub's immutable numeric account/repo ID [1](#0-0) , and `GitHubRepository` records are keyed by `[ownerID+name]`, also derived from login/name rather than the API's numeric `id` [2](#0-1) . The `GitHubRepository` model even documents that its `dbID` "is no relation to the API ID" [3](#0-2) .

### Title
Stale local `GitHubRepository` identity is silently reused/repopulated for a renamed or deleted owner/repo, enabling repo/owner-jacking trust confusion - (File: `app/src/lib/stores/repositories-store.ts`)

### Summary
GitHub Desktop persists the "identity" of a linked GitHub repository as `(endpoint, owner login, repo name)`, never the GitHub API's immutable numeric repository/owner id. When Desktop later refreshes repository metadata from the API, it looks the record up by this mutable name-based key and overwrites the stored `cloneURL`, `htmlURL`, and `permissions` fields in place — with no numeric-id check to detect that the underlying entity has actually changed.

### Finding Description
`_upsertGitHubRepository` resolves the owner via `putOwner`, which keys owners by `getOwnerKey(endpoint, login)` (a lowercase string), and then looks up the GitHub repository row via `db.gitHubRepositories.where('[ownerID+name]').equals([owner.id, gitHubRepository.name])` [4](#0-3) . If a match is found, the existing row is updated with whatever `cloneURL`, `htmlURL`, `parentID`, and `permissions` the API currently returns for that owner/name pair [5](#0-4) , and the update is committed even though the code path explicitly reasons about "the parent getting deleted" and repo names being recreated from scratch, in the surrounding comment [6](#0-5) .

Because GitHub allows deleted repositories' (and, in some cases renamed/transferred) owner+name combinations to be reclaimed by a different, attacker-controlled account, an attacker can:
1. Wait for/acquire a repo name+owner login that a victim previously had linked in Desktop's local database (e.g. after the original repo is deleted, or the owner renames their account and an attacker claims the old login).
2. Have that reclaimed name return via the GitHub API on the victim's next `repositoryWithRefreshedGitHubRepository` refresh, called opportunistically whenever the repository lacks an `account` association [7](#0-6) .
3. `_upsertGitHubRepository` silently repoints the victim's existing local `GitHubRepository` DB row — which downstream UI/logic treats as "the same, already-trusted repository" — to the attacker's new `cloneURL`/`htmlURL`/`permissions`.

There is no guard comparing a stable numeric id before accepting this update; the "old contract" (original repository identity) is gone but Desktop keeps operating against whatever now occupies that address, exactly mirroring the residual/reusable identity problem in the `selfDestruct` report.

### Impact Explanation
Once the local `GitHubRepository` row is repointed, several trust decisions become attacker-influenced without the user explicitly re-adding or re-verifying the repository: `hasWritePermission` checks are derived from the freshly-written `permissions` field [8](#0-7) , `updateRemoteUrl` can rewrite the local git remote to the attacker's `cloneURL` [9](#0-8) , and any feature relying on `htmlURL`/`cloneURL` matching (e.g. "Open in Desktop" URL matching in `doesRepositoryMatchUrl`) would now match the attacker's repository as if it were the trusted one [10](#0-9) . This can lead the user to silently push/fetch against attacker infrastructure believing it is their original trusted repository — a "silent corruption of what the user commits or pushes" scenario as defined in the valid-impact criteria.

### Likelihood Explanation
This requires no local access, no malware, and no leaked credentials — only an attacker being able to claim a vacated `owner/name` on GitHub (a well-documented "repojacking" technique) and the victim's Desktop instance performing a routine background refresh of repository metadata, which happens automatically whenever the repository has no cached account association [11](#0-10) . The comment at repositories-store.ts:646-649 shows the developers were aware repo-recreation-with-same-name could occur but did not add an identity check to prevent silently merging into the same DB row.

### Recommendation
Store and compare against GitHub's immutable numeric repository `id` (and owner `id`) rather than relying solely on the case-insensitive login/name key. When an API refresh's numeric id no longer matches the previously stored numeric id for the same local database row, treat it as a new repository (create a new `GitHubRepository` record and prompt/warn the user) instead of overwriting the existing trusted record in place.

### Proof of Concept
1. Victim adds `github.com/legituser/legitrepo` in Desktop; Desktop stores a `GitHubRepository` row keyed by `owner.login = "legituser"`, `name = "legitrepo"`.
2. `legituser` deletes the account/repo or it becomes otherwise vacated (rename, org transfer, etc.), and `legituser/legitrepo` is later reclaimed by an attacker with a different underlying GitHub API repository id.
3. Victim's Desktop, on a routine metadata refresh (`repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` → `_upsertGitHubRepository`), fetches `legituser/legitrepo` from the API and finds the existing local row by `[ownerID+name]`, overwriting `cloneURL`, `htmlURL`, and `permissions` with the attacker's repository data — with no comparison of the underlying (never-stored) numeric repository id.
4. Any subsequent push/fetch/URL-matching operation Desktop performs based on that `GitHubRepository` record now operates against the attacker's repository while the UI still presents it as the originally trusted one.
