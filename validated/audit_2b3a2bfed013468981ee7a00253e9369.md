## Analysis Summary

I traced the bug class from the Solidity report — an unprivileged "donation" call that corrupts a shared accounting value, permanently poisoning a downstream invariant check that unauthorized deposits/withdrawals rely on — to Agave's `DepositDelegatorRewards` vote-program instruction (SIMD-0123), which lets *any* signer deposit lamports into *any* vote account's `pending_delegator_rewards` field, independent of that account's withdraw authority or stake delegation status.

### Title
Unprivileged `DepositDelegatorRewards` griefing permanently locks vote-account funds when the target has zero delegated stake - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
`deposit_delegator_rewards` (SIMD-0123) allows any signer of a funded source account to increase `pending_delegator_rewards` on an arbitrary vote account, with no relationship required to that account's authorized withdrawer or its stake delegation. `withdraw()` then refuses to fully close (zero-balance) a vote account while `pending_delegator_rewards > 0`, and caps partial withdrawals to `lamports - pending_delegator_rewards - rent_exempt_minimum`. The only mechanism that reduces `pending_delegator_rewards` is `calculate_block_reward`, which is a no-op whenever the vote account has no active delegated stake (`total_active_stake == 0`). This mirrors the reported pattern exactly: an unprivileged "donation" call corrupts a denominator/guard value (here, `pending_delegator_rewards`) that a later privileged operation (`withdraw`) depends on, and the corrupting condition (`total_active_stake == 0`) is never automatically re-validated to prevent the poison from sticking.

### Finding Description
`deposit_delegator_rewards` only requires the *source* account to sign; it performs no check that the caller has any relationship to the target vote account: [1](#0-0) 

It transfers lamports and unconditionally bumps `pending_delegator_rewards` via `add_pending_delegator_rewards`, which only checks for overflow: [2](#0-1) [3](#0-2) 

`withdraw` then treats `pending_delegator_rewards` as an untouchable reserve: full account closure is rejected while it is nonzero, and partial withdrawals are capped so the reserve can never be spent: [4](#0-3) 

The only path that decrements this value is the epoch reward distribution's `calculate_block_reward`, which is short-circuited to `0` whenever the vote account has no active delegated stake for that reward epoch — i.e., the corrupting condition analogous to the report's `totalStaked == 0` is never revisited to unwind the poison: [5](#0-4) 

Because a vote account can legitimately have zero active delegated stake (e.g., a freshly created vote account before any stake is delegated to it, or one whose stake has fully deactivated), any unprivileged actor can call `DepositDelegatorRewards` with as little as 1 lamport against such an account. This sets `pending_delegator_rewards = 1`, which then permanently blocks the account's legitimate authorized withdrawer from closing it or withdrawing its full balance, since the guard in `withdraw()` has no other route to clear the reserve while stake remains at zero.

### Impact Explanation
This is fund lock/loss of availability on a builtin program instruction path reachable by any unprivileged transaction signer — no malicious peer/validator/leaked-key assumption is required, only a funded source account controlled by the attacker (which they always have). The affected vote account's legitimate withdraw authority loses the ability to fully withdraw/close the account until the vote account acquires nonzero delegated stake and enough epochs of block-revenue distribution occur to zero out the pending balance — which may never happen for accounts that are never delegated to.

### Likelihood Explanation
Likelihood is moderate rather than "always exploitable like the original report": the corruption is easy and cheap to trigger (1 lamport, any signer), but it is only a *permanent* lock as long as `total_active_stake == 0` for that vote account across all subsequent reward epochs. For actively-staked validator vote accounts the lock is self-healing over time via inflation/commission rewards; for newly created or fully-deactivated vote accounts it can persist indefinitely, matching the "griefer front-runs before real activity begins" primitive from the original report (front-running a vote-account's first stake delegation, analogous to front-running a pool's first deposit).

### Recommendation
Restrict `DepositDelegatorRewards` so only the vote account's authorized withdrawer (or another explicitly authorized party) can increase `pending_delegator_rewards`, or require the deposit to be validated against the vote account currently having nonzero delegated/active stake before accepting it. Alternatively, provide an explicit, authorized mechanism for the withdrawer to clear/reclaim `pending_delegator_rewards` when the account has no active stake, so the reserve cannot be poisoned indefinitely by an unrelated third party.

### Proof of Concept
1. Create/observe a vote account `V` with `pending_delegator_rewards == 0` and zero currently-delegated active stake (e.g., a newly initialized V4 vote account, per `create_test_account_with_authorized` fixtures used in `programs/vote/src/vote_processor.rs`).
2. As an unrelated attacker-controlled signer `S` (funded system account), submit `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` with accounts `[V (writable, not signer), S (writable, signer), system_program]`. This succeeds per `deposit_delegator_rewards`, setting `V.pending_delegator_rewards = 1` — see the passing "Success" case at: [6](#0-5) 
3. `V`'s legitimate authorized withdrawer now attempts `Withdraw(full_balance)` to close the account. This fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0`, as demonstrated by the existing test: [7](#0-6) 
4. Because `V` has no active delegated stake, `calculate_block_reward` will return `0` every epoch (`total_active_stake == 0` branch), so `pending_delegator_rewards` never decreases, and the withdrawer permanently cannot recover the last `pending_delegator_rewards` lamports or close the account.

        .get_lamports()
        .checked_sub(lamports)
        .ok_or(InstructionError::InsufficientFunds)?;

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }
