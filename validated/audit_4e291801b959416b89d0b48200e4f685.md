### Title
Unchecked Zero `CLPoolAddr` in Reward Distribution Causes Permanent Loss of Consensus-Liquidity Staking Rewards - ([File: kaiax/reward/impl/getter.go])

### Summary
`specWithProposerAndFunds`/`specWithProposerAndFundsFlex` and `assignStakingRewards` credit the consensus-liquidity (CL) portion of block rewards directly to `cn.CLStakingInfo.CLPoolAddr` via `IncRecipient`, without validating that the address is non-zero, unlike the analogous KIF/KEF/KPF fund-address handling in the same functions, which explicitly falls back to the proposer when `common.EmptyAddress(...)` is true.

### Finding Description
In `specWithProposerAndFunds` and `specWithProposerAndFundsFlex`, when the proposer's consolidated node has a `CLStakingInfo`, the proposer's reward is split between the CN reward address and the CL pool address and both are unconditionally credited: [3](#0-2) 

Note that the KIF, KEF, and KPF addresses immediately above this block are all guarded: [4](#0-3) 

The same unguarded pattern for CL staker rewards (non-proposer validators) appears in `assignStakingRewards`, which iterates `si.ConsolidatedNodes()` and calls `cn.Split(...)` before crediting `cn.CLStakingInfo.CLPoolAddr` directly (per the code excerpt referenced in `getter.go:534-643`, `cn.Split` is invoked without any `common.EmptyAddress` check on `CLPoolAddr`).

The root cause is that `CLPoolAddr` is populated straight from the `CLRegistry`/`MultiCallDPStakingInfo` on-chain contract call result without any sanitization: [1](#0-0) [5](#0-4) 

If the CLRegistry contract (a system/governance-controlled registry, but populated per-node by node operators registering their CL pool) ever returns/records a zero address for a node's `ClPools[i]` entry — e.g., due to registry misconfiguration, a bug in registration, or a race where a validator registers a CL stake before setting its pool address — `CLPoolAddr` will be `common.Address{}` (zero). Unlike the KIF/KEF/KPF case, there is no fallback: `state.AddBalance(common.Address{}, clAmount)` in `FinalizeState` will send the CL portion of the reward to the zero address, which is permanently unreachable, matching exactly the bug class in the reference report (`ConvexRewardsAdapter._claimRewards` failing to guard against `sendTo == address(0)`).

### Impact Explanation
Any block reward portion computed for a validator's CL stake (`clAmount` from `cn.Split`) that is misdirected to the zero address is permanently and irrecoverably burned from circulation instead of reaching the intended consensus-liquidity stakers/pool. This is a supply-affecting, high-severity issue since it silently and repeatedly (every block, for every affected validator) diverts real KAIA rewards to an unrecoverable sink, unlike KIF/KEF/KPF where the code explicitly reroutes to the proposer to avoid loss.

### Likelihood Explanation
This requires the CLRegistry/AddressBookV2 on-chain data to expose a zero `CLPoolAddr` for a node that nonetheless has a positive `CLStakingAmount` — a state reachable through misconfiguration or an incomplete registration flow in the permissionless/CL registry system contracts, which are populated by transactions from CL pool operators (a reachable, non-privileged transaction path). Since `kaiax/staking/impl/getter.go` performs no defensive `common.EmptyAddress` check on `CLPoolAddr` (in contrast to the deliberate checks for KIF/KEF/KPF elsewhere in the very same file/module), the gap is a straightforward oversight rather than a deep architectural constraint.

### Recommendation
Add an explicit `common.EmptyAddress(cn.CLStakingInfo.CLPoolAddr)` guard (mirroring the KIF/KEF/KPF pattern) in `specWithProposerAndFunds`, `specWithProposerAndFundsFlex`, and `assignStakingRewards`/`assignStakingRewardsFlex`, redirecting the CL portion back to the CN's `RewardAddr` (or another safe fallback) whenever `CLPoolAddr` is the zero address, instead of unconditionally calling `IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)`.

### Proof of Concept
1. Configure (or have the CLRegistry system contract return, via a validator's own registration transaction) a `CLStakingInfo` entry for a validator's node with `CLStakingAmount > 0` but `CLPoolAddr == common.Address{}` — this can occur if the CL registry logic permits registering a staking amount before/without setting a pool address.
2. During block finalization, `getFromState`/`parseCallResult` (or `parsePermissionlessCallResult`) populates `StakingInfo.CLStakingInfos` with this zero `CLPoolAddr` entry, `kaiax/staking/impl/getter.go:211-221` and `:292-302`.
3. `getDeferredRewardFullKore`/`getDeferredRewardFullFlex` call `assignStakingRewards`/`specWithProposerAndFunds(Flex)`, which compute `cnAmount, clAmount := cn.Split(proposer)` and call `newSpec.IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)` unconditionally, `kaiax/reward/impl/getter.go:583-586`.
4. `FinalizeState` then executes `state.AddBalance(addr, amount)` for every recipient in `spec.Rewards`, including the zero address, `kaiax/reward/impl/blockstate.go:53-55`, permanently burning `clAmount` of KAIA every block this condition persists.
