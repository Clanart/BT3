Audit Report

## Title
Per-IP QUIC connection rate limiter can be bypassed during handshake window via check-then-act split between `is_allowed` and `register_connection` - (streamer/src/nonblocking/quic.rs)

## Summary
`ConnectionRateLimiter::is_allowed()` is a read-only check performed synchronously in the QUIC accept loop, while the actual token debit (`register_connection`) is deferred to inside the asynchronously spawned `setup_connection` task and only happens *after* the QUIC handshake completes. Because the accept loop does not await handshake completion before processing the next `Incoming`, multiple connection attempts from the same source IP arriving within one handshake-timeout window can all pass `is_allowed` before any of them registers a token, temporarily defeating the per-IP cap.

## Finding Description
In the accept loop, `rate_limiter.is_allowed(&incoming.remote_address().ip())` is a pure lookup (`current_tokens(ip) > 0`) that does not mutate the underlying token bucket. [1](#0-0)  The loop then hands the connection off via `incoming.accept()` followed by `tasks.spawn(setup_connection(...))`, immediately continuing to the next loop iteration without waiting for `setup_connection` to finish. [2](#0-1) 

Inside `setup_connection`, the code first awaits the QUIC handshake with a timeout (`timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await`), and only *after* the handshake succeeds does it call `rate_limiter.register_connection(&from.ip())`, which is the only method that actually consumes a token via `consume_tokens`. [3](#0-2) [4](#0-3) 

This confirms the claim's core mechanism: the check (`is_allowed`) and the mutation (`register_connection`) are separated by an entire QUIC handshake RTT and a `tokio::spawn` boundary. During that window, additional `Incoming` connections from the same IP processed by the accept loop will still see the pre-mutation token count and also pass `is_allowed`, all being spawned into their own `setup_connection` tasks.

However, this bypass is bounded, not unlimited, by other independent, synchronously-enforced guards in the same accept loop:
- A global `overall_connection_rate_limiter.current_tokens() == 0` check gates all incoming connections regardless of IP. [5](#0-4) 
- `ClientConnectionTracker::new(..., qos.max_concurrent_connections())` enforces a global concurrent-connection cap before any connection is accepted/spawned. [6](#0-5) 
- `setup_connection` also re-checks `overall_connection_rate_limiter.consume_tokens(1)` after the handshake, and requires proof of IP ownership via a completed handshake before any state mutation is attempted (as the code comment states, "we should only modify server state once source IP is verified"). [7](#0-6) [8](#0-7) 

So while the per-IP limiter can be transiently bypassed within one handshake window, an attacker still cannot exceed the server's global `max_concurrent_connections` or global rate-limit budget — they can only capture a larger *share* of that already-capped global budget than the per-IP limiter intends, and only for the duration of one handshake-timeout window before subsequent connections from that IP are properly throttled once tokens are registered.

## Impact Explanation
This is a real, reachable race condition: an unprivileged remote peer can, by opening many concurrent QUIC connections from one source IP within a single handshake-timeout window, temporarily exceed the intended `max_connections_per_ipaddr_per_min` cap and consume a disproportionate share of the server's already-capped global connection budget (`max_concurrent_connections`), degrading legitimate stake-weighted QUIC/TPU traffic. This matches the "non-RPC remote exhaustion/degradation" impact category. The exact corrupted value is the per-IP token count in `ConnectionRateLimiter`'s `KeyedRateLimiter<IpAddr>` — it is read stale by concurrently-processed `is_allowed` calls before the corresponding `register_connection` debit lands. Severity is bounded by the fact that global caps (`overall_connection_rate_limiter`, `max_concurrent_connections`) still apply, so this is a fairness/degradation issue rather than an unbounded resource-exhaustion bug.

## Likelihood Explanation
The attacker needs no stake or special privileges — the QUIC/TPU ingress accept loop is public. Exploitation requires firing many real connection attempts (and completing real handshakes, since IP spoofing is not viable against QUIC's handshake requirements) from a single source IP within the `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window, which is feasible for a motivated remote attacker with sufficient bandwidth/parallelism, though bounded by the global connection/rate caps enforced synchronously in the same accept loop before any per-IP-only decision is made.

## Recommendation
Consume the per-IP token synchronously at the same point the per-IP check is performed in the accept loop (i.e., replace `is_allowed` + later `register_connection` with an atomic check-and-consume, refunding the token if the handshake subsequently fails/times out), rather than deferring the debit to after successful handshake completion inside `setup_connection`.

## Proof of Concept
1. Configure a validator instance with `max_connections_per_ipaddr_per_min` set low (e.g., 4) and `max_concurrent_connections` set high enough to observe the effect (e.g., 100).
2. From a single test client IP, concurrently open more QUIC connections than the per-IP limit (e.g., 20) in a tight burst, each completing a real QUIC handshake against the streamer.
3. Instrument/observe `StreamerStats::connection_rate_limited_per_ipaddr` and `StreamerStats::total_new_connections`: expect more than `max_connections_per_ipaddr_per_min` connections to be counted as successfully established (`total_new_connections` incremented) before `register_connection` calls begin rejecting further attempts from that IP, demonstrating the transient per-IP cap bypass bounded only by the global caps.

        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
