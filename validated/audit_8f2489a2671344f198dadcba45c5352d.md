Let me confirm the spend path uses this offset without re-validation.### Title
`ReceivedOutput::read` doesn't verify `offset` actually derives the accompanying output's `script_pubkey` — (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner` guarantees `offset ↔ script_pubkey` consistency internally (it inserts `offset` keyed by `p2tr_script_buf(key + G*offset)` into `scripts`, and `scan_transaction` only produces matched pairs). However, `ReceivedOutput::read` deserializes an arbitrary `Scalar` offset together with an arbitrary `TxOut`/`OutPoint` without verifying that `p2tr_script_buf(key + G*offset) == output.script_pubkey`. This is the Serai analog of `BlueBerryBank.addBank` storing a `token ↔ cToken` pair without checking `token == cToken.underlying()`: two fields are persisted in association while the correspondence that makes them meaningful is never validated on the untrusted-input path.

### Finding Description
`ReceivedOutput` claims "this output is spendable by `key + offset * G`", where `key` is the scanner's long-lived key. That claim is only enforced when the struct is constructed by `scan_transaction`; the `read`/`serialize` round trip bypasses it entirely. `read` accepts any 32-byte scalar plus any decoded `TxOut`/`OutPoint` (mod.rs:120-134), so a byte stream can pair offset `x` with an output whose script commits to `key + G*y`, `y != x`, or to a script not derivable from the scanner key at all (any valid P2TR script, since `TxOut::consensus_decode` performs no ownership check).

The mismatch is only caught later in `SignableTransaction::multisig`, which returns `None` ("wrong keys") when `p2tr_script_buf(offset.group_key()) != prevouts[i].script_pubkey` (send.rs:273-282). `SignableTransaction::new` itself happily consumes the bad input — it reads `input.offset` and `input.outpoint` verbatim and computes the fee/change math as if the funds were spendable (send.rs:175-185). Nothing upstream (no `Scanner`-key-aware validation hook exists on `ReceivedOutput`) prevents a mismatched record from being stored, emitted as a `ScannerEvent::Block` output, and counted toward the wallet's spendable balance.

### Impact Explanation
Funds are reported as received yet are not spendable: a corrupted or maliciously supplied `ReceivedOutput` inflates the apparent balance and, once selected as an input, makes `SignableTransaction::multisig` return `None` — the multisig machine cannot be constructed, so the spend stalls exactly like `doBorrow` silently returning zero in the BlueBerry report. Because `SignableTransaction::new` treats the bogus input's value as available (send.rs:175), coin selection will keep preferring a permanently-unusable input, and there is no path that repairs or evicts the bad `(offset, output)` association once accepted — mirroring the report's "the wrong bank cannot be fixed".

### Likelihood Explanation
Reachability is via untrusted bytes into `ReceivedOutput::read` (DB contents, serialized output records, or any integrator-fed stream) — a permitted surface. The requirement is merely a 32-byte canonical scalar plus a syntactically valid `TxOut`/`OutPoint`, trivially constructible. Exploitation causes a deterministic stall of the affected spend rather than secret leakage or forgery, which caps this at Medium.

### Recommendation
Analogous to `require(token == cToken.underlying())`, bind the offset to the output at the trust boundary. Since `ReceivedOutput` doesn't carry the base key, either:
- store the derived spend key (or the full tweaked `ProjectivePoint`) in `ReceivedOutput` and assert `p2tr_script_buf(key + G*offset) == output.script_pubkey` inside a validating constructor used by `read`, or
- move deserialization under `Scanner` (e.g. `Scanner::read_output`) so the scanner's key is available to verify `self.scripts` contains `output.script_pubkey` and that the stored offset equals the registered one — also rejecting offsets/script pairs the scanner never registered.
