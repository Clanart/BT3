### Title
Unbounded payment sum breaks the enforced `inputs >= outputs` invariant in `SignableTransaction::new`, producing a consensus-invalid signed transaction and a panicking `fee()` - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` attempts to enforce `sum(inputs) >= sum(outputs) + fee` — the wallet analog of the reported `limit >= funded` invariant — via `if input_sat < (payment_sat + needed_fee)`. Both `payment_sat` (a wrapping `sum::<u64>()` over caller-supplied payment amounts) and the `payment_sat + needed_fee` addition are unchecked `u64` arithmetic. An unprivileged party who can specify payment amounts (e.g., via a withdrawal/burn `OutInstructionWithBalance` whose `balance.amount.0` is a `u64`) can make `payment_sat` wrap to a small value, causing the `NotEnoughFunds` guard to pass while the transaction's outputs vastly exceed its inputs. The resulting `SignableTransaction` is consensus-invalid yet is handed to `sign()`/`attempt_sign` for threshold signing, and `SignableTransaction::fee()` later computes `sum(inputs) - sum(outputs)` with a bare subtraction that panics.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`:

- `let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();` (line 187) — unchecked sum of attacker-influenced `u64` amounts. Each payment is only checked against `DUST` (a *lower* bound); there is no upper bound such as `Amount::MAX_MONEY` and no `checked_add`/`checked_sum`.
- `if input_sat < (payment_sat + needed_fee)` (line 215) — `payment_sat + needed_fee` is an unchecked `u64` addition that can wrap.
- `pub fn fee(&self)` (lines 138-141) computes `sum(prevouts) - sum(outputs)` with a bare `-`, assuming the constructor enforced `inputs >= outputs`. With a wrapped `payment_sat`, this assumption does not hold and the subtraction underflows, panicking in any build configuration (this is a `u64` underflow, always a panic).
- The change path uses `checked_sub` (line 228), showing the authors knew the ordering invariant matters but only protected that one site.

So `new()` admits a `SignableTransaction` whose `tx.output` values sum to more than `sum(inputs)`. That transaction is passed to `sign(&keys, &tx)` (as in `networks/bitcoin/tests/wallet.rs:244` and the processor's `attempt_sign`), producing a valid threshold signature over a transaction Bitcoin will reject: `sha_amounts` in the BIP-341 sighash commits to the real prevout amounts, so the signature verifies, but the transaction violates the consensus rule `sum(outputs) <= sum(inputs)`.

### Impact Explanation
Two concrete harms, both reachable from public inputs (payment amounts ultimately derived from `OutInstruction` balances):

1. A multisig-threshold signing round is consumed to sign an unspendable, consensus-invalid transaction. The FROST session completes normally and emits a signature for a TX that cannot be broadcast — a wasted/aborted signing attempt that, in the processor, leaves the `Plan` in `active_plans` and its `Eventuality` unresolved, stalling the affected payments.
2. `SignableTransaction::fee()` panics on `u64` underflow (`send.rs:139-140`). `fee()` is invoked on this object downstream (e.g., `instruction.balance.amount.0 -= tx.0.fee()` in `processor/src/multisigs/mod.rs:884`), crashing the processor node — a denial of service on the signer set.

### Likelihood Explanation
Requires a payment set whose `u64` amounts sum past `2^64` (e.g., ~520 payments each near `u64::MAX`, under `MAX_OUTPUTS`), or amounts large enough that `payment_sat + needed_fee` wraps. Whether an external user can actually register such amounts depends on the coin-supply validation of the issuing `OutInstruction`/`ExternalBalance` upstream, which is outside the in-scope crates — if balances are not capped to the real money supply before reaching `bitcoin-serai`, the trigger is trivial. Within the library itself nothing prevents it, and the panic in `fee()` is deterministic once triggered. Likelihood is therefore conditional on upstream validation; the code defect itself is unconditional.

### Recommendation
- In `SignableTransaction::new`, compute `payment_sat` with `checked_add`/`try_fold` and reject overflow (`TransactionError`), and/or reject any `payment.1 > Amount::MAX_MONEY.to_sat()`.
- Compute the guard as `input_sat.checked_sub(needed_fee).map_or(true, |r| r < payment_sat)`-style checked arithmetic rather than `payment_sat + needed_fee`.
- Make `fee()` use `checked_sub` and return `Option`/`Result` instead of panicking, and/or store the invariant-checked fee at construction time.

### Proof of Concept
```rust
// networks/bitcoin context; assumes Secp256k1 keys and a funded ReceivedOutput.
// Two payments whose u64 amounts sum past 2^64 wrap payment_sat to a small value.
let huge = u64::MAX - 1000;
let payments = vec![
  (p2tr_script_buf(key).unwrap(), huge),
  (p2tr_script_buf(key).unwrap(), huge),
];
// payment_sat wraps to ~u64::MAX*2 mod 2^64 = small; NotEnoughFunds check passes.
let tx = SignableTransaction::new(vec![output], &payments, None, None, FEE).unwrap();
// tx.tx.output values total ~2^65 sats while the single input is worth far less.
// Any call to tx.fee() panics on u64 underflow (send.rs:139-140), and sign(&keys, &tx)
// produces a signature for a transaction Bitcoin consensus rejects (outputs > inputs).
```

The same class — an assumed `A >= B` ordering that a setter/constructor fails to enforce — is the exact analog of the reported `limit >= funded` issue; here it silently yields a signed, invalid transaction and a reachable panic instead of a revert.
