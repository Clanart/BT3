### Title
Unauthenticated `old_move_txid` binding allows minting a second N-of-N presigned move-to-vault UTXO via `ReplacementDeposit` without any security-council spend of the referenced move tx - ([File: core/src/verifier.rs])

### Summary
`Verifier::is_deposit_valid` validates a `ReplacementDeposit` only by checking that the depositor's UTXO carries the expected `ReplacementDepositScript(nofn_xonly_pk, old_move_txid)` + security-council multisig script, the correct `bridge_amount`, and a minimum block height. It never checks that `old_move_txid` corresponds to a move-to-vault output that was ever actually spent via the security-council path. An unprivileged attacker can therefore self-fund a UTXO naming any genuine, already-finalized victim move-to-vault txid as `old_move_txid`, and get verifiers to presign a brand-new N-of-N move-to-vault transaction for it.

### Finding Description
The binding the protocol needs is: `deposit_data.old_move_txid` == txid of a move-to-vault transaction whose `DepositInMove` output was actually consumed by an `security_council`-signed (`Multisig::from_security_council`) input — i.e., a real "emergency stop"/replacement event, as documented at [1](#0-0) .

`Verifier::is_deposit_valid` computes the expected script pubkey purely from `deposit_data.get_deposit_scripts`, which for `ReplacementDeposit` just re-derives `ReplacementDepositScript::new(nofn_xonly_pk, replacement_deposit_data.old_move_txid)` plus the security-council multisig script [2](#0-1) , and then checks only that this matches the on-chain script pubkey of the attacker-supplied `deposit_outpoint`, that the value equals `bridge_amount`, and that the block height is above `start_height` [3](#0-2) . Nowhere in this function (or in `deposit_sign`/`deposit_finalize` callers at [4](#0-3) ) is there a lookup that `old_move_txid` is a UTXO that has been spent, let alone spent by the security council multisig script. The script itself, `ReplacementDepositScript::to_script_buf`, only embeds the `old_move_txid` bytes inside an `OP_FALSE OP_IF ... OP_ENDIF` (unexecuted, data-carrying) branch and enforces an `OP_CHECKSIG` against `nofn_xonly_pk` for the actual spending path [5](#0-4) ; it does not itself prove anything about the spend history of `old_move_txid`.

Consequently, an attacker can:
1. Observe a victim's already-finalized, unspent move-to-vault UTXO with txid `X` (a public, on-chain fact).
2. Compute `create_taproot_address([ReplacementDepositScript::new(nofn_xonly_pk, X), Multisig::from_security_council(security_council)])` exactly as `generate_replacement_deposit_address` does [6](#0-5) .
3. Fund that address themselves with exactly `bridge_amount`, creating outpoint `O`.
4. Call the aggregator's `new_deposit` with `Deposit{deposit_outpoint: O, deposit_data: ReplacementDeposit{old_move_txid: X}}`, which is parsed into `ReplacementDepositData{old_move_txid}` with no additional validation at the RPC layer [7](#0-6) .
5. Verifiers call `is_deposit_valid`, which passes all its checks since `O`'s script pubkey, value, and confirmation height are all under the attacker's control and legitimately match the formula — the equality it actually verifies (`script_pubkey(O) == expected_scriptpubkey(old_move_txid, nofn_xonly_pk, security_council)`) holds by construction, but this is not the equality that matters (whether `X` was really replaced via a security-council spend).
6. Verifiers proceed to `deposit_sign`/`deposit_finalize`, producing valid N-of-N partial signatures for a new move-to-vault transaction that Citrea's bridge contract will associate (via the replacement flow) with the victim's already-issued cBTC.

### Impact Explanation
This produces a second, illegitimate N-of-N presigned move-to-vault UTXO for a real bridge deposit that was never actually replaced, matching the "N-of-N partial signatures for an unauthorised spend" Critical category. If the resulting move tx is registered on Citrea as a valid replacement for the victim's move-to-vault txid, BTC custody diverges from the 1:1 backing of already-issued cBTC — either creating unbacked custody state or letting the attacker's self-funded coins be commingled into the bridge's N-of-N vault under the guise of a "replacement," while the original victim UTXO remains spendable/unaccounted for by the bridge's own bookkeeping. The attack is repeatable against any currently-unspent, publicly known move-to-vault UTXO and does not require compromising any verifier, operator, or the security council; the only cost is the `bridge_amount` the attacker must lock into `O` (recoverable if the flow is caught before Citrea acceptance, but the exploit is about getting valid presigned N-of-N signatures for an unauthorized replacement, which is itself the critical primitive).

### Likelihood Explanation
Preconditions are minimal and match the stated threat model exactly: attacker only needs to observe a public move-to-vault txid, fund a taproot output with `bridge_amount`, and call the aggregator's public `new_deposit`/`deposit_sign`/`deposit_finalize` gRPC endpoints, all deliberately open to unprivileged depositors. No verifier collusion, no security-council key, no majority hashrate, and no protocol-level rate limit blocks this call sequence based on the code read. The check is deterministic and stateless with respect to `old_move_txid`'s spend history, so the exploit is fully reproducible on any deployment (including the currently running testnet referenced in the question) with cost bounded by `bridge_amount` plus fees.

### Recommendation
Before accepting a `ReplacementDeposit`, `Verifier::is_deposit_valid` must independently verify that `old_move_txid` refers to a move-to-vault transaction whose `UtxoVout::DepositInMove` output has actually been spent, and that the spending transaction's witness satisfies the `Multisig::from_security_council` script path (i.e., a real security-council-authorized emergency-stop/replacement occurred). Concretely: look up `old_move_txid`'s output on-chain, confirm it is spent, fetch the spending transaction, and confirm it satisfies the security-council multisig spend path (or track this fact in the verifier DB when the security council spend is presigned/observed) — rejecting the deposit if no such spend exists or if that move-to-vault has already been consumed by a different registered replacement.

### Proof of Concept
```
cargo test --features automation test_replacement_deposit_without_security_council_spend
```
1. Run a regtest deposit and move-to-vault to finalization using existing helpers (`run_single_deposit`), producing `old_move_txid` that is genuinely unspent and belongs to "victim".
2. As "attacker", compute the replacement address via `generate_replacement_deposit_address(old_move_txid, nofn_xonly_pk, network, security_council)` and self-fund it with exactly `bridge_amount` (skip `sign_replacement_deposit_tx_with_sec_council` entirely — do not spend the victim's move UTXO at all).
3. Call `aggregator.new_deposit(Deposit{deposit_outpoint: attacker_outpoint, deposit_data: ReplacementDeposit{old_move_txid}})` then `deposit_sign`/`deposit_finalize`.
4. Assert (LHS) `deposit_data.old_move_txid == old_move_txid` (trivially true — attacker's chosen equality) while (RHS) the real invariant `is_spent_by_security_council(old_move_txid's DepositInMove output) == true` is **false** (the victim's UTXO was never touched).
5. Assert that verifiers nonetheless return valid `PartialSignature`s for the new move-to-vault tx (`is_deposit_valid` returns `Ok(())`, and `deposit_finalize` completes), demonstrating the two sides of the binding do not match yet the protocol proceeds.

    fn to_script_buf(&self) -> ScriptBuf {
        let citrea_replace: [u8; 13] = "citreaReplace".as_bytes().try_into().expect("length == 13");

        Builder::new()
            .push_x_only_key(&self.0)
            .push_opcode(OP_CHECKSIG)
            .push_opcode(OP_FALSE)
            .push_opcode(OP_IF)
            .push_slice(citrea_replace)
            .push_slice(self.1.as_byte_array())
            .push_opcode(OP_ENDIF)
            .into_script()
    }

pub fn generate_replacement_deposit_address(
    old_move_txid: bitcoin::Txid,
    nofn_xonly_pk: XOnlyPublicKey,
    network: bitcoin::Network,
    security_council: SecurityCouncil,
) -> Result<(Address, TaprootSpendInfo), BridgeError> {
    let deposit_script =
        ReplacementDepositScript::new(nofn_xonly_pk, old_move_txid).to_script_buf();

    let security_council_script = Multisig::from_security_council(security_council).to_script_buf();

    let (addr, spend) =
        create_taproot_address(&[deposit_script, security_council_script], None, network);
    Ok((addr, spend))
}
