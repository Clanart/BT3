### Title
`updateRemoteUrl` silently rewrites the local `origin` remote based on an untrusted GitHub API `clone_url` field, redirecting future pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The Biconomy bug is a case of a critical destination reference (`liquidityPool`) being mutated by an outside trigger, silently redirecting funds that users believe are still bound to the old destination. The closest Desktop analog is `updateRemoteUrl`, which automatically rewrites a repository's `origin` remote URL to whatever `clone_url` the GitHub API currently reports for the matched repository, with no user confirmation, based purely on data returned by the remote GitHub host.

### Finding Description
`updateRemoteUrl` compares the locally configured remote URL against the `clone_url` field of an `IAPIRepository` object fetched from the GitHub API, and if the protocol matches and the previous "expected" URL still matches what's stored, it calls `gitStore.setRemoteURL` to overwrite the local `origin` remote with the new URL from the API response: [1](#0-0) 

This is wired into the periodic repository-refresh path: `repositoryWithRefreshedGitHubRepository` in `app-store.ts` matches the repo via `matchGitHubRepository` (which only checks that the remote's hostname corresponds to a signed-in account's endpoint, not ownership) fetches the corresponding API repository object, and calls `updateRemoteUrl` on every refresh: [2](#0-1) 

The only checks performed before overwriting the remote are: (1) protocol equality between old and new URLs, and (2) that the remote hasn't been "manually changed" from the previously known `GitHubRepository.cloneURL`. Neither check verifies that the new `clone_url` still points at the same logical repository/owner the user originally added — it only checks protocol and that the remote wasn't already stale. The value that gets silently overwritten is the git `origin` remote URL used for all future `push`/`fetch` operations, and the source of truth for the new value is entirely the GitHub API response (`apiRepo.clone_url`), i.e., server-controlled data (`app/src/lib/stores/updates/update-remote-url.ts:19`).

Compare this to the explicit, user-confirmed path for changing a remote URL through Repository Settings, which requires the user to type and submit a new URL via `_setRemoteURL`: [3](#0-2) 
There is no equivalent confirmation step for the API-driven auto-update path.

### Impact Explanation
If the owner of a tracked upstream repository renames the repository or transfers it to a different owner (an action fully controllable by that repository's non-privileged, external owner — not an admin of Desktop or the victim's machine), the GitHub API's `clone_url` for that repo changes accordingly. Because `matchGitHubRepository` only anchors on hostname (not owner/name pinning against a stable ID), and `updateRemoteUrl`'s guard rails only check protocol and "did the user already diverge," Desktop will automatically rewrite the victim's local `origin` remote to the new `clone_url` on the next background refresh, without asking the user. This mirrors the `setLiquidityPool` scenario: a value the user implicitly trusts (their remote destination) is redirected by an external, unprivileged party's action, and subsequent operations (in this analog, `git push`/`git fetch`) silently target the new destination. In a repo-jacking scenario (old name/owner reclaimed by an attacker after a legitimate rename), this can silently redirect a victim's future pushes to an attacker-controlled repository under the same hostname, without any prompt, corrupting where the user's commits/pushes go.

### Likelihood Explanation
The trigger requires only an unprivileged, remote action by the original repository owner (rename/transfer) — no access to the victim's machine, no malware, and no unusual user interaction; the corruption happens automatically the next time Desktop performs its normal background refresh of the repository. This satisfies the "attacker controls a GitHub API object" criterion. The severity is tempered by the same mitigating factor found in the original finding: the change is recoverable (the user can inspect/reset the remote via Repository Settings), and exploiting it for credential exfiltration additionally depends on how Desktop's credential helper resolves credentials for the new host/origin.

### Recommendation
- Do not silently rewrite `origin` (or any remote) based solely on the API's `clone_url`; require explicit user confirmation before changing the remote URL, similar to the existing `UpstreamAlreadyExists` dialog pattern used for upstream remotes (`app/src/ui/upstream-already-exists/upstream-already-exists.tsx`).
- Anchor `matchGitHubRepository`/`updateRemoteUrl` to the GitHub repository's stable numeric ID rather than owner/name strings, so a rename/transfer is detected as "same underlying repo" rather than blindly trusting a new URL.
- Log/notify the user whenever an automatic remote-URL change occurs so a hijack attempt is visible rather than silent.

### Proof of Concept
1. User A adds `https://github.com/owner/repo` as `origin` in GitHub Desktop and signs in with an account that can resolve this host via `matchGitHubRepository`.
2. The external repository owner renames `owner/repo` to `owner/repo2` (or transfers ownership) — a normal, unprivileged GitHub action taken by that repo's owner, not by User A or an admin.
3. On Desktop's next periodic refresh, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)`, gets back an object whose `clone_url` reflects the new name, and `updateRemoteUrl` — seeing protocols match and the old remote unchanged from the previously cached `cloneURL` — calls `gitStore.setRemoteURL('origin', newCloneUrl)` automatically: [4](#0-3) 
4. If `owner/repo` (the old name) is later re-registered by a different, malicious party (a well-known "repo-jacking" pattern) before this refresh executes, or if the new owner's transferred namespace is itself attacker-controlled, User A's local `origin` is silently pointed at the attacker's repository, and the next `git push` sends commits there — all without any dialog or confirmation shown to User A.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
