### Title
`LinkButton` invokes `shell.openExternal()` on API-supplied URLs without any protocol validation, unlike the equivalent markdown link path - (File: `app/src/ui/lib/link-button.tsx`)

### Summary
GitHub Desktop already recognizes that URLs rendered from PR/issue/comment markdown are untrusted and enforces an `https?:` protocol allow-list before they are ever passed to `shell.openExternal()`. That check lives in `SandboxedMarkdown.setupLinkInterceptor`. However, the generic `LinkButton` component — used throughout the UI to render clickable URLs sourced directly from GitHub API response fields such as `comment.html_url`, `review.html_url`, and `secret.bypassURL` — has no equivalent check. It unconditionally calls `shell.openExternal(uri)` for whatever string it is given. This is the same class of bug as the reported "guard exists in some code paths but is missing in the function that actually needs it" pattern from the audit report: a validation/guard exists, but is not applied consistently across all reachable code paths that share the same trust boundary.

### Finding Description
`SandboxedMarkdown` deliberately treats markdown-rendered PR/issue/comment bodies as attacker-controlled content and only forwards a link click to `onMarkdownLinkClicked` (which eventually calls `dispatcher.openInBrowser` → `shell.openExternal`) if the link's protocol matches `/^https?:/`: [1](#0-0) 

That validated path is intentionally the *only* sanctioned way to open a link from rendered markdown: [2](#0-1) 

In contrast, `LinkButton` — a general-purpose component reused across the entire UI, including dialogs that render fields taken verbatim from GitHub API objects (`comment.html_url`, `review.html_url`, `user.html_url`, `secret.bypassURL`) — performs **no protocol or scheme validation at all** before calling `shell.openExternal`: [3](#0-2) 

Examples of API-sourced values being fed straight into `LinkButton`'s unguarded `uri` prop: [4](#0-3) [5](#0-4) [6](#0-5) 

And the main-process `open-external` IPC handler, which is the ultimate sink, itself performs no scheme validation — it only logs when the value happens to start with `http(s)://` and otherwise calls `shell.openExternal` unconditionally: [7](#0-6) 

**Broken invariant:** the app's own design intends that any URL originating from an untrusted GitHub API response/markdown source must pass an `https?` allow-list before reaching `shell.openExternal`. That invariant is enforced in the markdown-link code path but silently absent in the `LinkButton` code path, even though both paths render the exact same class of attacker-influenceable data (fields inside API objects for PR comments, reviews, and secret-scanning alerts).

**Attacker primitive:** an unprivileged actor who controls what these API response fields contain — e.g., an attacker operating a malicious/compromised GitHub Enterprise Server endpoint the victim has added as an account (a "GitHub API object" the attacker controls per the valid-impact scope), or a MITM/proxy able to tamper with API responses — can set `html_url`/`bypassURL` to a non-`https?` URI (e.g. a `file://` UNC path, a registered custom URI scheme, or platform-specific shell handlers) instead of a normal web link. When the victim clicks "Open in Browser"/"Bypass" in the PR comment/review/secret-scanning dialog, `shell.openExternal()` is invoked directly on that attacker-chosen string with no scheme allow-list, unlike the markdown path which would have blocked it.

### Impact Explanation
`shell.openExternal` with an unrestricted, attacker-influenced string is a well-known Electron footgun: depending on OS it can be abused to launch arbitrary local files/UNC paths, invoke installed custom URI-scheme handlers (some of which are known to lead to code execution or credential leakage, e.g. Windows `search-ms:`/UNC-path SMB credential leaks, or chained exploitation through vulnerable browser/OS URL handlers), well beyond opening a normal https page. Since this triggers from viewing an ordinary PR comment/review/notification or secret-scanning alert (all reachable purely by having an attacker-influenced GitHub/GHES account added, no local access or malware required), it satisfies the "attacker controls a GitHub API object … result is code execution / renderer-sandbox escape" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to be pointed at a GitHub Enterprise endpoint (or MITM-able API traffic) that an attacker can influence, and then requires a user click on the rendered link/button. This is a fairly natural user action (clicking "Open in Browser" on a PR comment, or "Bypass" on a secret-scanning banner) and does not require any unusual steps by the victim. The fact that Desktop's own developers already added the `https?` guard for the semantically-identical markdown-link path strongly indicates they recognize these API-sourced strings as untrusted, making the missing guard in `LinkButton` a genuine oversight rather than an intentional trust decision.

### Recommendation
Add the same protocol allow-list check used in `SandboxedMarkdown.setupLinkInterceptor` to `LinkButton.onClick` (and/or centralize it inside `shell.openExternal`/the `open-external` IPC handler in `main.ts`), rejecting any `uri` that does not start with `http://` or `https://` before calling `shell.openExternal`.

### Proof of Concept
1. Add a GitHub Enterprise account pointing to an attacker-controlled (or MITM-able) API endpoint.
2. Have that endpoint return a pull request review/comment object where `html_url` (or, for secret scanning, `bypassURL`) is set to a non-`https` URI, e.g. `file://\\attacker-host\share\payload` or a locally-registered custom scheme.
3. In Desktop, open the notification/dialog that renders this object (`PullRequestComment`, `PullRequestReview`, or the secret-scanning push-protection dialog) and click the associated `LinkButton` ("Open in Browser" / "Bypass").
4. Observe that `LinkButton.onClick` (`app/src/ui/lib/link-button.tsx:76-92`) calls `shell.openExternal(uri)` directly with the attacker-controlled string, with no scheme check — unlike the markdown-rendered link path, which would have blocked the same value via `setupLinkInterceptor`'s `/^https?:/` test.

**Note on evidence limits:** I was not able to fully confirm within the indexed code whether every `LinkButton uri=` call site in the app ultimately traces back to unauthenticated/attacker-controllable API data versus locally-generated URLs (some, like `RepositoryURL`/`WebsiteURL`, are hardcoded and not attacker-controlled). The PR comment/review and secret-scanning cases cited above are the clearest examples where the `uri` value is taken directly from a network API response object. A full audit of all `LinkButton` call sites would benefit from a broader Devin session with complete file access, since the codebase index used here may not include every consuming file.

  private setupLinkInterceptor(doc: Document): void {
    doc.addEventListener('click', ev => {
      if (doc.defaultView && ev.target instanceof doc.defaultView.Element) {
        const a = ev.target.closest('a')
        if (a !== null) {
          ev.preventDefault()

          if (/^https?:/.test(a.protocol)) {
            this.props.onMarkdownLinkClicked?.(a.href)
          }
        }
      }
    })
  }

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
