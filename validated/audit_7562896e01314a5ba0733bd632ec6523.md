### Title
Out-of-bounds panic in KAS token-transfer log decoding crashes chaindatafetcher node - ([File: datasync/chaindatafetcher/kas/repository_token_transfer.go])

### Summary
`transformLogToTokenTransfer` blindly indexes `data[1]`, `data[2]`, `data[3]` (where `data = log.Topics` concatenated with the words parsed from `log.Data`) after only checking that `log.Topics[0]` equals the ERC-20/KIP-7 `Transfer` event hash, with no check on the total number of elements. [2](#0-1)  The caller only guards `len(log.Topics) > 0`, not the combined topic+data length. [3](#0-2) 

### Finding Description
Any contract can emit an arbitrary `LOGn` opcode with topic0 set to `0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef` (the `Transfer(address,address,uint256)` signature hash) and with fewer than 3 additional topics/data words (e.g. `LOG1` with empty data, giving `data = [hash]`, length 1). `splitToWords` performs no minimum-length check (only requires length be a multiple of 32 bytes, so zero-length data passes), and `transformLogToTokenTransfer` then indexes `data[1]`, `data[2]`, `data[3]` unconditionally, causing a Go slice-index-out-of-range panic. This is exactly the same bug class as the referenced Wormhole `txverifier` fix: a log with insufficient topics triggers an out-of-bounds panic during log parsing/verification logic. [4](#0-3) 

The chaindatafetcher module processes every log of every block it fetches from the chain via `HandleChainEvent`, which dispatches to `InsertTokenTransfers` for `RequestTypeTokenTransfer`. [5](#0-4)  These block events are consumed by worker goroutines spawned in `Start()` with no panic recovery anywhere in the package. [6](#0-5) 

### Impact Explanation
When the chaindatafetcher/KAS service is enabled on a node, any unprivileged account can deploy a trivial contract that emits a malformed `Transfer`-like log (e.g. `LOG1(0,0,transferHash)`) in a normal, valid, publicly submittable transaction. Once that transaction is included in a block, every node running the chaindatafetcher module with `RequestTypeTokenTransfer` enabled panics and crashes while processing that block, since there is no `recover()` in the goroutine chain. This is a remotely triggerable crash/DoS of the affected node process, not merely resource exhaustion — the process terminates.

### Likelihood Explanation
Likelihood is high for any deployment that runs the node with chaindatafetcher/KAS mode enabled and token-transfer indexing turned on: the trigger requires only a normal contract deployment plus one transaction executing an inline-assembly `LOG1` (or any `LOGn`, n<3) with the fixed topic0 value and insufficient extra data, both fully within reach of a standard, unprivileged transaction sender.

### Recommendation
Add an explicit length check in `transformLogToTokenTransfer` (or in `transformLogsToTokenTransfers`) verifying that `len(log.Topics) + len(words) >= 4` before accessing `data[1]`, `data[2]`, `data[3]`, returning an error/skip instead of panicking when the log doesn't match the expected `Transfer` event shape. Additionally, wrap the chaindatafetcher request-handling goroutines with a `recover()` to prevent a single malformed log from taking down the whole process.

### Proof of Concept
1. Deploy a contract with a fallback/function containing raw assembly: `log1(0, 0, 0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef)` (i.e., one topic equal to the `Transfer` event hash, zero-length data).
2. Send a transaction invoking that function on a node running with `--chaindatafetcher` and KAS mode enabled with token-transfer indexing.
3. `transformLogsToTokenTransfers` sees `log.Topics[0] == tokenTransferEventHash` and calls `transformLogToTokenTransfer`; `splitToWords(nil)` returns an empty `words` slice (no error, since `0 % 32 == 0`); `data := append(log.Topics, words...)` yields a slice of length 1; `data[1]` panics with "index out of range [1] with length 1", crashing the node's chaindatafetcher goroutine and, absent any `recover()`, the process.

// splitToWords divides log data to the words.
func splitToWords(data []byte) ([]common.Hash, error) {
	if len(data)%common.HashLength != 0 {
		return nil, fmt.Errorf("data length is not valid. want: %v, actual: %v", common.HashLength, len(data))
	}
	var words []common.Hash
	for i := 0; i < len(data); i += common.HashLength {
		words = append(words, common.BytesToHash(data[i:i+common.HashLength]))
	}
	return words, nil
}

func (r *repository) HandleChainEvent(event blockchain.ChainEvent, reqType types.RequestType) error {
	switch reqType {
	case types.RequestTypeTransaction:
		return r.InsertTransactions(event)
	case types.RequestTypeTrace:
		return r.InsertTraceResults(event)
	case types.RequestTypeTokenTransfer:
		return r.InsertTokenTransfers(event)
	case types.RequestTypeContract:
		return r.InsertContracts(event)
	default:
		return fmt.Errorf("unsupported data type. [blockNumber: %v, reqType: %v]", event.Block.NumberU64(), reqType)
	}
}
