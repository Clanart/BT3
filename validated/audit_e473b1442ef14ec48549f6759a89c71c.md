### Title
Identity DKG encryption keys make secret shares publicly recoverable - ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
PedPoP accepts a participant-supplied encryption public key without requiring it to be non-identity. If a participant registers the identity point, every secret share encrypted to them uses the publicly known identity as its ECDH result, allowing anyone who observes the DKG messages to recover that participant’s secret share.

### Finding Description
`EncryptionKeyMessage::read` parses `enc_key` with `C::read_G` but applies no PedPoP-level non-identity check. [1](#0-0) 

`Decryption::register` stores the supplied key directly, also without checking it. [2](#0-1) 

When a dealer sends a share, `Encryption::encrypt` uses the registered key as the ECDH public input. [3](#0-2)  The shared point is calculated as `public * private`, so a registered identity public key always produces the identity shared secret. [4](#0-3) 

The ChaCha20 key is derived only from the transcript context and encoded ECDH result; the per-message public key is not otherwise mixed into the cipher derivation. [5](#0-4)  Consequently, for an identity registration, the keystream is computable from public data alone.

The receiving path does validate the sender’s per-message proof of possession, but that proof covers the ephemeral message key, not the registered recipient encryption key. [6](#0-5)  Round-one verification likewise verifies the polynomial-commitment proof while registering the encryption key without a corresponding proof or identity rejection. [7](#0-6) 

### Impact Explanation
A malicious participant can publish an otherwise valid commitments message whose encryption key is the identity point. Every honest dealer will encrypt that participant’s secret share under the public identity point. Any observer of the authenticated DKG channel can derive the same ChaCha20 stream and recover each scalar share sent to that participant.

This directly exposes a DKG secret share. For threshold-one configurations, the recovered share exposes the group secret. For larger thresholds, it gives an external observer a share they should not possess and reduces the protocol’s effective confidentiality margin.

### Likelihood Explanation
The attack requires only control of the registration bytes for one DKG participant. The malformed key is accepted before share encryption, no cryptographic assumption is broken, and no interaction with the victim participant’s private state is required.

The attacker must ensure the accompanying PedPoP commitments and Schnorr proof are valid, but that can be done normally by choosing a known coefficient and generating a valid proof. The encryption key itself has no proof-of-possession requirement and is not checked for identity.

### Recommendation
Reject identity encryption keys during registration and deserialization.

- In `EncryptionKeyMessage::read`, reject `enc_key.is_identity()`.
- In `Decryption::register`, defensively reject identity before inserting the key.
- If the ciphersuite API supports it, use a non-identity point-reading helper equivalent to FROST’s `Curve::read_G`, which explicitly rejects identity. [8](#0-7) 
- Add a regression test where a participant submits an identity `enc_key`; `generate_secret_shares` should fail rather than encrypt shares to it.

### Proof of Concept
Conceptually, for participant `l`:

```rust
// Construct a normal valid PedPoP Commitments payload, then append:
let malicious_enc_key = C::G::identity().to_bytes();

// Deliver the bytes to:
let msg = EncryptionKeyMessage::<C, Commitments<C>>::read(
    &mut serialized_message_and_identity_key.as_slice(),
    params,
)?;
```

`SecretShareMachine::verify_r1` registers `msg.enc_key` and verifies only the separate commitments proof. [7](#0-6)  Honest dealers then encrypt shares with `shared = identity * message_private`, which is always identity. [4](#0-3) 

An observer can reconstruct the stream cipher by:

1. Creating `RecommendedTranscript::new(b"DKG Encryption v0.2")`.
2. Appending `"context"` and the public DKG context.
3. Applying `domain_separate(b"encryption_key")`.
4. Appending `"shared_key"` as `C::G::identity().to_bytes()`.
5. Using the first 32 bytes of `challenge(b"key")` as the ChaCha20 key and `b"DKG IV v0.2\0"` as the nonce.
6. XORing the resulting keystream with each `EncryptedMessage.msg` sent to participant `l`.

fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
