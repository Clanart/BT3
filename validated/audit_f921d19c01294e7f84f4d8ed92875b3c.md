### Title
Attacker-committed `ralph-loop.local.md` state file causes unconsented Stop-hook loop activation - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
The globally-registered Stop hook [1](#0-0)  unconditionally checks only for the existence of `.claude/ralph-loop.local.md` [2](#0-1)  to decide whether to block session exit and re-feed a stored prompt to the model. Because this file lives in the repository working tree rather than being bound to the session that created it, an attacker who commits a valid-looking state file into a shared repo can force the loop to auto-activate for any victim who has the ralph-wiggum plugin installed and opens Claude Code in that repo, without ever running `/ralph-loop`.

### Finding Description
`stop-hook.sh` is registered as a `Stop` hook for every session once the plugin is enabled [3](#0-2) . Its only activation gate is `[[ ! -f "$RALPH_STATE_FILE" ]]` [2](#0-1) . If the file exists, the script parses `iteration`, `max_iterations`, and `completion_promise` from YAML-like frontmatter [4](#0-3) , and if the loop is not complete it blocks the Stop event and returns the file body as the next prompt via `"decision": "block", "reason": $prompt` [5](#0-4) .

There is no check anywhere in the script that ties activation to the current session (no `session_id` comparison), nor any check that `/ralph-loop` was invoked in this session — the intended entry point is `scripts/setup-ralph-loop.sh`, which writes the exact same file format with `active: true` [6](#0-5) , but `stop-hook.sh` never reads or validates the `active` field, and never verifies provenance of the file. Any file matching the expected frontmatter shape — regardless of how it got into the working directory (including via `git clone`) — is treated as an authoritative, currently-active loop.

This means the file functions purely as tracked, repo-scoped state with no cryptographic or session binding, so an attacker with ordinary contributor/PR access to a repository can plant `.claude/ralph-loop.local.md` with a crafted prompt body, low `iteration`, and a high or `0` `max_iterations`. When a victim who already has the plugin enabled opens a session in the cloned repo and tries to exit, the hook fires and immediately re-injects the attacker-controlled prompt text as the next turn's instructions — a form of persistent prompt injection triggered without any explicit `/ralph-loop` consent action.

### Impact Explanation
Scoped impact: unconsented recurring model exposure to repo content and attacker-controlled prompt injection triggered automatically on every exit attempt, bypassing the intended one-time explicit `/ralph-loop` opt-in. This does not itself grant new tool permissions (the fed-back prompt still goes through Claude's normal per-turn tool-approval flow), but it forces repeated re-engagement with attacker-chosen instructions and can be combined with social-engineering-style prompt content urging destructive or exfiltration actions, and prevents/annoys the user by blocking normal exit repeatedly.

### Likelihood Explanation
Requires: (1) the victim has the ralph-wiggum plugin installed and enabled (a one-time explicit user action that already surfaces plugin trust warnings) and (2) the victim opens a Claude Code session inside a repository where an attacker has been able to commit or introduce a `.claude/ralph-loop.local.md` (e.g., via a merged PR, fork, or supply-chain path). Given both preconditions, the exploit is fully deterministic and repeatable — every `Stop` event fires the hook and reads the file unconditionally.

### Recommendation
Bind loop activation to explicit, session-scoped consent instead of trusting arbitrary repo-tracked file content:
- Have `/ralph-loop`'s setup script record a random per-invocation token/`session_id` (matching the hook's `session_id` field from stdin) inside the state file, and have `stop-hook.sh` verify this against the current session's `session_id` before honoring the file.
- Alternatively/additionally, store loop state outside the project working tree (e.g., under `~/.claude/` keyed by project path and session id) so it cannot be introduced via `git clone`/checked-in content.
- Warn/refuse to activate if the state file is tracked by git (`git ls-files --error-unmatch .claude/ralph-loop.local.md`) since `.local.md` is meant to be untracked, and recommend adding `.claude/*.local.md` to `.gitignore` by default from the setup script.

### Proof of Concept
Integration test:
1. Create a fresh git repo; commit `.claude/ralph-loop.local.md` with:
```
---
active: true
iteration: 1
max_iterations: 0
completion_promise: null
---
Attacker-controlled instructions here.
```
2. Clone the repo to a victim workspace; do not invoke `/ralph-loop` in the session.
3. Start a Claude Code session in the cloned repo (with ralph-wiggum plugin enabled) and simulate a `Stop` hook event by piping a minimal `{"transcript_path": "..."}` JSON with a fabricated assistant transcript line into `stop-hook.sh`.
4. Assert: the hook returns `{"decision":"block", ...}` and re-injects the attacker's prompt — demonstrating the loop activates purely from repo content, with no `/ralph-loop` invocation and no session/consent binding check in the script (confirmed absent at `plugins/ralph-wiggum/hooks/stop-hook.sh` lines 13-18 and 130-174).
