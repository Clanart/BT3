### Title
Unbounded `app` key silently truncated to 32 bytes lets an attacker drain another app's paid bandwidth allowance - (File: `modules/pallets/bandwidth/src/lib.rs`, `modules/pallets/bandwidth/src/types.rs`)

### Summary
The external report's core defect is: a size/length control value is not bounded to what the underlying safety limit actually requires, so oversized inputs silently collapse in a way that corrupts identity/uniqueness (in the Sui case, huge slice sizes overflow the object-size limit; the fix bounds the parameter). The local analog is `AppKey::truncate_from`, which silently truncates an attacker-controlled, unbounded-length `app` identifier to 32 bytes without any uniqueness/collision check, and that truncated value is used directly as the storage key that gates and debits a prepaid resource balance.

### Finding Description
`AppKey` is defined as `BoundedVec<u8, ConstU32<32>>` [1](#0-0) . Every bandwidth-consuming code path builds this key with `AppKey::truncate_from(app.to_vec())`, which silently drops any bytes beyond the first 32 rather than rejecting oversized input — in `try_consume` [3](#0-2) , in `on_accept` [4](#0-3) , and in `allowances`/`remaining` [5](#0-4) .

Crucially, the runtime feeds `try_consume` the raw, unauthenticated `request.from` field taken directly from an inbound cross-chain ISMP `PostRequest`: `<pallet_bandwidth::Pallet<Runtime> as pallet_bandwidth::BandwidthGate>::try_consume(&request.source, &request.from, bytes)` [2](#0-1) . `request.from` is attacker-controlled sender data of arbitrary length carried in the message body, not validated against any registered identity before this call. Because two different `from` values that share the same first 32 bytes collapse to the identical `AppKey` after truncation, an attacker who controls (or can spoof, from the same `source` chain) the `from` field of an inbound message can construct a value whose first 32 bytes match a legitimate, paying app's identifier. The gate then looks up and debits the legitimate app's `Allowance` entry [6](#0-5)  for bytes attributable to the attacker's own unrelated message, not the paying app's traffic.

Unlike the BigVector case (a config value that simply needs to stay under a hard limit), here the truncation is baked into the type itself with no bound-check or rejection of oversized `app` values at the entrypoint — the "size overflow" is absorbed silently into a collision rather than erroring out, and that collision maps directly onto a shared, prepaid balance.

### Impact Explanation
This lets an unprivileged, unauthenticated sender on any source chain consume/drain another app's paid-for bandwidth allowance (a prepaid resource that gates ISMP request processing) by simply padding a `from` field to collide on the first 32 bytes. That is loss of a paid-for resource by the rightful beneficiary and unauthorized "spend" of that resource by an attacker — matching the bounty's "stealing or loss of funds" / "logic attack" categories, since bandwidth credits are purchased with real value via `BandwidthManager.sol` purchases [7](#0-6) .

### Likelihood Explanation
High: the only precondition is sending a normal inbound ISMP `PostRequest` (not a purchase message) whose `from` bytes are longer than 32 and share the target's 32-byte prefix — fully reachable by any unprivileged actor able to dispatch a cross-chain message from a source chain that has a `BandwidthManager` registered, with no relayer/prover/admin compromise required.

### Recommendation
Reject (rather than silently truncate) any `app`/`from` identifier longer than the `AppKey` bound at the point of use in `try_consume` and `on_accept`, or hash the full-length identifier into the 32-byte key instead of truncating, so collisions are cryptographically infeasible rather than trivially constructible by padding.

### Proof of Concept
1. App `A` (20-byte EVM address, right-padded to 32 bytes per convention) purchases bandwidth via `BandwidthManager.sol`; `Allowance::<T>::get(source, AppKey::truncate_from(A))` now holds a funded `SubscriptionList`.
2. Attacker dispatches an ordinary (non-purchase) `PostRequest` from the same `source` chain with `request.from` set to `A`'s 32 bytes followed by arbitrary extra bytes (`A || garbage`).
3. `ProxyModule::on_accept` calls `try_consume(&request.source, &request.from, bytes)` [8](#0-7) ; `AppKey::truncate_from(request.from)` truncates to `A`, matching the funded key.
4. `try_consume` debits `A`'s `remaining_bytes` for the attacker's message, silently draining `A`'s paid allowance without `A`'s knowledge or consent.

//! Prepaid `(chain, app)` byte balances credited by tier purchases
//! from `BandwidthManager.sol`. Each purchase carries its own

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;
