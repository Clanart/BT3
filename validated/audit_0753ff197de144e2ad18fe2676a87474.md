### Title
Unbounded CW721 enumeration/transfer loop in the `solo` precompile's `ClaimSpecific` permanently bricks legacy-account NFT migration - (File: precompiles/solo/solo.go)

### Summary
The `solo` precompile's `ClaimSpecific` handler enumerates *all* CW721 tokens owned by a legacy Sei account (via unbounded pagination) and then transfers every single token in a `for` loop, all inside one EVM transaction. If the number of tokens is large enough, the cumulative gas cost exceeds the block gas limit, permanently reverting the migration for that CW721 collection — the same "unbounded for-loop bricks the function" bug class as the referenced Visor Finance `transferERC721()` finding.

### Finding Description
`ClaimSpecific` (`precompiles/solo/solo.go:157-228`) is reachable directly from an EOA via an EVM transaction to the `solo` precompile at `0x000000000000000000000000000000000000100C` [1](#0-0) . For each `IAsset` marked as a CW721 collection with no specific token id, the code performs pagination over *all* tokens owned by the `sender` account, appending every page to `allTokens` with no limit: [2](#0-1) 

and then transfers each collected token in a second unbounded loop, one CosmWasm `Execute` call per token: [3](#0-2) 

There is no cap on `len(allTokens)`, no batching, and no way to resume/partially claim a single collection across multiple transactions — the entire `MsgClaimSpecific` asset list (and the whole CW721 collection) is processed atomically in one EVM call. Every iteration performs a full CosmWasm smart-query (during enumeration) or a full CosmWasm `Execute` (during transfer), each of which is far more gas-expensive than a plain state read/write, so gas usage scales linearly and expensively with the number of tokens owned by the legacy `sender` account for that contract.

Compare with `x/evm/client/wasm/query.go`/`precompiles/*.sol` pointer patterns which cap query pagination (`limit`, `MAX_LIMIT`) per call — `ClaimSpecific` has no such bound on the total amount of work performed in a single transaction [4](#0-3) .

Critically, the number of CW721 tokens owned by the `sender` legacy account is **not controlled by the sender/claimer** — any third party can mint or send arbitrary numbers of CW721 tokens (via `transfer_nft`) to that (still un-migrated) legacy Sei address before the owner ever calls `claimSpecific`. Because `sigverify`/`validate` (`precompiles/solo/solo.go:230-259`) only checks the tx signature and claimer identity, not the number of assets, an attacker can grief a target legacy account by inflating its NFT holdings in a given CW721 collection so that any future `ClaimSpecific` invocation for that collection always runs out of gas and reverts.

### Impact Explanation
Because `ClaimSpecific` processes the CW721 collection atomically (all tokens or none) in a single EVM call, once the token count for a collection exceeds what a block's gas limit can process, the affected NFTs become **permanently unclaimable/frozen** for the associated EVM address — there is no code path to migrate only part of a collection. This matches the "permanent freezing" impact criterion: the legacy-chain NFTs are stranded and can never be represented on the EVM side via this migration path, and the CosmWasm-side ownership can never be transferred to the caller either (since the same all-or-nothing transfer loop always fails). This is a griefing vector reachable by any unprivileged sender of a CW721 `transfer_nft` message and does not require any privileged access.

### Likelihood Explanation
Likelihood is moderate-to-high: an attacker only needs the ability to send/mint CW721 tokens (a normal, permissionless CosmWasm message) to the victim's legacy Sei address before that address performs its one-time `claimSpecific` migration. No special permissions, precompile access, or validator collusion are required. The number of tokens needed to exceed a realistic block gas limit is bounded by the cost of one CosmWasm smart query + one CosmWasm execute call per token, which is a modest and attacker-affordable multiple compared to a normal EVM opcode.

### Recommendation
- Cap the number of CW721 tokens processed per `ClaimSpecific` call (or per asset entry), and require the caller to specify explicit token IDs / pagination cursors instead of unconditionally enumerating "all tokens owned by sender."
- Allow partial/incremental claims of a CW721 collection across multiple transactions (e.g., accept a `start_after`/`limit` in `MsgClaimSpecific` for CW721 assets) rather than requiring the entire collection to be processed atomically.
- Consider decoupling the transfer step from the enumeration step, and charging/estimating gas proportional to the actual number of assets before starting the loop so the transaction fails fast (with a clear error) rather than silently degrading into an unrecoverable out-of-gas state.

### Proof of Concept
1. Identify a CW721 contract instance and a legacy (pre-EVM-association) Sei account `victim` that intends to migrate assets via `MsgClaimSpecific`.
2. As an attacker, repeatedly call the CW721 contract's `transfer_nft`/`mint` messages to send a large number (e.g., several thousand) of tokens to `victim`'s Sei address — this is a normal, permissionless CosmWasm call.
3. `victim` (or anyone holding a validly signed `MsgClaimSpecific` for `victim`) submits an EVM transaction to the `solo` precompile invoking `claimSpecific` with an `Asset` referencing that CW721 contract and empty `Denom` (i.e., "claim all my tokens in this collection"), per `precompiles/solo/solo.go:196-223`.
4. The precompile enumerates all owned tokens via repeated `QuerySmartSafe` calls and then attempts to `Execute` a `transfer_nft` for every single token in the same transaction. Once token count is high enough, the transaction runs out of gas within the block gas limit and reverts.
5. Because there is no partial-claim mechanism, every subsequent `claimSpecific` attempt for that collection also fails identically, permanently freezing `victim`'s NFTs in that collection.

pub fn query_tokens(
    deps: Deps<EvmQueryWrapper>,
    env: Env,
    owner: String,
    start_after: Option<String>,
    limit: Option<u32>,
) -> StdResult<TokensResponse> {
    let erc_addr = ERC721_ADDRESS.load(deps.storage)?;
    let querier = EvmQuerier::new(&deps.querier);
    let num_tokens = query_num_tokens(deps, env.clone())?.count;
    let start_after_id = Int256::from_str(&start_after.unwrap_or("-1".to_string()))?;
    let limit = limit.unwrap_or(DEFAULT_LIMIT).min(MAX_LIMIT) as usize;

    let mut cur = Int256::zero();
    let mut counter = 0;
    let mut tokens: Vec<String> = vec![];
    while counter < num_tokens && tokens.len() < limit {
        let cur_str = cur.to_string();
        let t_owner = match querier.erc721_owner(
            env.clone().contract.address.into_string(),
            erc_addr.clone(),
            cur_str.to_string(),
        ) {
            Ok(res) => res.owner,
            Err(_) => "".to_string(),
        };
        if t_owner != "" {
            counter += 1;
            if (owner.is_empty() || t_owner == owner) && cur > start_after_id {
                tokens.push(cur_str);
            }
        }
        cur += Int256::one();
    }
    Ok(TokensResponse { tokens })
