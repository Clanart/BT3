### Title
Malformed preprocess/share vector lengths cause out-of-bounds indexing panic in FROST transaction signing - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The external report (CVE-2022-24807) describes an out-of-bounds memory access triggered when a privileged-but-remote party supplies a malformed index/identifier in a request that is used to index an internal table without validation. The analog in Serai's in-scope code is in `TransactionSignMachine::sign` and `TransactionSignatureMachine::complete` in `networks/bitcoin/src/wallet/send.rs`, which index and `remove` from per-participant `Vec`s whose lengths are entirely controlled by the bytes an untrusted co-signer feeds to `read_preprocess` / `read_share`, with no length check against the number of inputs.

### Finding Description
`TransactionSignMachine::read_preprocess` reads one `Vec<Preprocess>` per counterparty by iterating `self.sigs` — but each element of the returned `HashMap<Participant, Vec<Preprocess>>` is itself a `Vec` whose length equals however many preprocesses that participant serialized. In `sign`, the code reshapes the map with `commitments[c]` for `c in 0 .. self.sigs.len()`:

```rust
// networks/bitcoin/src/wallet/send.rs
let commitments = (0 .. self.sigs.len())
  .map(|c| {
    commitments
      .iter()
      .map(|(l, commitments)| (*l, commitments[c].clone()))
      .collect::<HashMap<_, _>>()
  })
```

`commitments[c]` indexes position `c` (the Bitcoin input index) in each participant's preprocess vector. Nothing validated that each participant supplied exactly `self.sigs.len()` preprocesses. A co-signer who sends a serialized preprocess blob containing fewer items than the transaction has inputs causes `commitments[c]` to panic with an index-out-of-bounds access.

The identical pattern exists in `TransactionSignatureMachine::complete`, where per-participant signature-share `Vec`s (parsed by `read_share`, again length-controlled by the sender) are consumed with `shares.remove(0)` once per input. A participant who sends an empty or short share vector triggers a `remove(0)` on an empty `Vec` panic.

The CVE's shape — an attacker-supplied "index" that reaches an internal table without bounds validation, producing an out-of-bounds access — maps directly: the attacker's serialized length prefix in the preprocess/share encoding becomes an unchecked index/length used against the machine's internal `Vec`s.

### Impact Explanation
Any participant in the FROST signing session for a Bitcoin spend can, at will, panic the `sign`/`complete` path of every honest signer that accepts their preprocess/share blob. In Rust this manifests as a panic (an index-out-of-bounds / `remove` on empty `Vec`) rather than memory corruption, but the effect on the protocol is the same class of integrity/availability impact as the CVE: the malformed length field corrupts the operation. Because `TransactionMachine` preprocessing consumes `self.sigs` and the panic aborts the whole multisig attempt, a single malicious participant reliably forces the signing session to abort, stalling spending of threshold-held Bitcoin outputs.

### Likelihood Explanation
The trigger requires only that the attacker be a signer in the multisig and send a shortened `Vec<Preprocess>` (or `Vec<SignatureShare>`) — fully untrusted bytes accepted through the intended `read_preprocess`/`read_share` deserialization path. No credentials beyond normal participation, no collusion, and no protocol violation beyond a malformed payload are needed. The indexing is unconditional on the happy path once `msg` is empty.

### Recommendation
Validate lengths before indexing:

- In `TransactionSignMachine::sign`, check `commitments.len() == self.sigs.len()` for every participant's preprocess vector (returning `FrostError::InvalidCommitments`/`InvalidParticipant`-style error) before building the per-input maps.
- In `TransactionSignatureMachine::complete`, check each participant's share `Vec` has the expected number of elements before `remove(0)`, or drain with a checked iterator.
- Reject preprocess/share blobs in `read_preprocess`/`read_share` whose serialized count does not equal `self.sigs.len()`.

### Proof of Concept
```rust
// A malicious co-signer in a 2-of-2 multisig signs a 2-input
// SignableTransaction, but serializes a preprocess Vec of length 1
// instead of 2.
let mut buf = vec![];
// write only ONE Preprocess where the machine expects sigs.len() == 2
single_preprocess.write(&mut buf).unwrap();

// Honest side:
let preps = sign_machine.read_preprocess(&mut buf.as_slice()).unwrap();
let mut commitments = HashMap::new();
commitments.insert(honest_i, honest_preps);          // len 2
commitments.insert(attacker_i, preps);               // len 1

// sign() iterates c in 0 .. 2; at c == 1 it evaluates
// commitments[1] on the attacker's Vec of len 1 -> panic:
// "index out of bounds: the len is 1 but the index is 1"
sign_machine.sign(commitments, b"");
```
