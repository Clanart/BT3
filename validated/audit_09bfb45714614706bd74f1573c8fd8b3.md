### Title
Duplication of Transferred Value via Post-Hoc Error Acknowledgement in ERC20 IBC Middleware `OnRecvPacket` — ([File: x/erc20/keeper/ibc_callbacks.go])

### Summary
The `IBCMiddleware.OnRecvPacket`/`Keeper.OnRecvPacket` flow in `x/erc20` mirrors the analog bug class from the reported Stargate `lzCompose()` issue: a secondary, non-essential operation (there, `IExchange.deposit()`; here, automatic Coin→ERC20 conversion) is executed *after* the primary transfer has already been irreversibly committed, and a failure in that secondary step is not isolated from the already-completed transfer. Unlike the original report (temporary freeze), the Cosmos EVM analog produces a stronger, Critical impact: **duplication of spendable value**, because failure of the secondary step causes the whole packet to be acknowledged as failed, triggering a refund on the counterparty chain even though the underlying ICS-20 transfer already credited the receiver on this chain.

### Finding Description
`x/erc20/ibc_middleware.go` `OnRecvPacket` runs the standard ICS-20 transfer callback first, which unescrows/mints bank coins to the receiver and commits this state change directly against the real `sdk.Context` (not a discardable branch): [1](#0-0) 

If that succeeds, it passes control to `Keeper.OnRecvPacket`, which attempts an *additional*, non-essential auto-conversion of the native-ERC20-backed coin into its ERC20 representation: [2](#0-1) 

If `MintingEnabled` or `ConvertCoinNativeERC20` fails (e.g. because `BankKeeper.SetSendEnabled` is toggled false for the denom, or any other transient condition disabling minting/sending), this function returns `channeltypes.NewErrorAcknowledgement(err)` — replacing the already-successful ICS-20 acknowledgement with an error acknowledgement, **without reverting the unescrow/mint that already happened** in the preceding `im.Module.OnRecvPacket` call.

The project's own IBC middleware test explicitly documents this behavior: [3](#0-2) 

The comment states plainly: *"SendEnabled=false will cause the conversion of bank tokens to erc20 tokens to fail, but not send them back to escrow"* — i.e., the escrow is not restored, yet the acknowledgement is an error ack, which is exactly the mismatch that causes duplication.

Per ICS-20 semantics, when the sending chain receives an error acknowledgement for a `MsgTransfer` packet, its `OnAcknowledgementPacket`/`OnTimeoutPacket` logic refunds the sender (unescrows or re-mints the amount that was burned/escrowed to send the packet). Because the receiving chain (this repo) already credited the receiver's bank balance during the underlying ICS-20 receive step, and only the *optional* ERC20 conversion step failed, returning an error ack causes:
- Receiving chain: receiver retains the credited bank coins (from the successful unescrow/mint in `im.Module.OnRecvPacket`).
- Sending chain: sees an error ack and refunds the original sender the same amount.

This produces two live claims on the same underlying value — a duplication of spendable user value across the two chains' balances/escrows, which is exactly the "Critical unauthorized ... duplication ... of spendable user value across native balances ... IBC escrows" impact class.

### Impact Explanation
This is a Critical accounting-invariant violation: value that should exist exactly once (either at the receiver on the destination chain, or refunded to the sender on the source chain) can exist in both places simultaneously. Any unprivileged party can influence the trigger condition indirectly (e.g., relying on `SendEnabled` toggles, module account restrictions, or other governance/blocked-address conditions checked inside `MintingEnabled`/`ConvertCoinNativeERC20`, or any transient EVM call failure inside `ConvertCoinNativeERC20`), and the described duplication occurs deterministically once the secondary conversion step fails post-transfer.

### Likelihood Explanation
The condition is directly reachable through the ordinary IBC packet-receive flow for any token pair marked `IsNativeERC20()`. Any factor that legitimately (even temporarily) causes `MintingEnabled` to fail — `IsERC20Enabled` toggled off, `BlockedAddr`, `IsSendEnabledCoin` false, or `ConvertCoinNativeERC20`'s EVM call failing (e.g., self-destructed contract edge case not already special-cased, balance-invariance mismatch) — after the underlying ICS-20 unescrow/mint has already committed, will trigger this. The test suite's own comment confirms this is a known, reproducible code path, not a theoretical edge case.

### Recommendation
Do not let failures in the auxiliary ERC20 auto-conversion step downgrade a packet's acknowledgement from success to error once the core ICS-20 transfer state changes (unescrow/mint to receiver) have already been committed. Instead:
- Always return the original success acknowledgement from `im.Module.OnRecvPacket` once the underlying transfer has committed, regardless of the auto-conversion outcome (as is already correctly done for the `!pair.Enabled` no-op case).
- If conversion fails, leave the receiver holding the bank-denominated coin (already the documented fallback intent, e.g., in `OnAcknowledgementPacket`/`OnTimeoutPacket`'s doc comments) rather than propagating an error ack that triggers a source-chain refund.
- Alternatively, execute the auto-conversion in a cached/branched context that is discarded on failure, and only surface a Go-level panic/error (which aborts the whole transaction atomically) if consistency truly cannot be guaranteed — never a mismatched partial-commit-plus-error-ack.

### Proof of Concept
The existing test `evmd/tests/ibc/ibc_middleware_test.go` (`TestOnRecvPacketNativeErc20`, `withCallback` case) already demonstrates the mechanics:
1. Escrow tokens via `MsgTransfer` from evmChainA.
2. Disable `SendEnabled` for the native ERC20 denom on evmChainA (`evmApp.BankKeeper.SetSendEnabled(evmCtx, nativeErc20.Denom, false)`).
3. Call `transferStack.OnRecvPacket` for `packet1`; assert `errAck.Success()` is `false` — while the code comment confirms escrow was **not** restored.
4. In a real cross-chain scenario, this error ack would be relayed back to the sending chain, causing a refund there, while the receiver on evmChainA already retains the unescrowed bank balance from step 3 — the duplication. [4](#0-3)

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
