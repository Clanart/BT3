Found it. `NativeSeiTokensERC20.sol` is a genuine access-control bug: its `_update()` override (which OpenZeppelin's ERC20 calls for `transfer`, `transferFrom`, `mint`, and `burn`) passes the `from`/`to` addresses straight through to the `Bank` precompile's `send()` without ever checking `msg.sender`. [1](#0-0) 

Since the `Bank` precompile only verifies that the *caller* is the registered pointer contract for that denom (not that the caller is authorized to move a specific `from` account's funds), and `_update` in standard OpenZeppelin `ERC20` is invoked by `transferFrom(from, to, amount)` after allowance checks are handled at the Solidity level — the vulnerability hinges on whether this specific contract itself checks allowances anywhere before calling `_update`.### Title
Missing access control in `NativeSeiTokensERC20._update()` allows unauthorized transfer of native Sei tokens via the Bank precompile - (File: `contracts/src/NativeSeiTokensERC20.sol`)

### Summary
`NativeSeiTokensERC20` is the ERC20 pointer contract that wraps a native Sei bank denom, deployed via `x/evm/artifacts/native/artifacts.go` and used by the pointer precompile (`AddNativePointer`/`UpsertERCNativePointer`) as the on-chain representation of a native denom. [2](#0-1) . Its `_update()` override — the single OpenZeppelin ERC20 hook invoked by `transfer`, `transferFrom`, `_mint`, and `_burn` — forwards `from`/`to` directly to the `Bank` precompile's `send()` without any `msg.sender`/allowance validation of its own: [1](#0-0) .

### Finding Description
Standard OpenZeppelin `ERC20.transferFrom()` calls `_spendAllowance(from, msg.sender, value)` and then `_update(from, to, value)` — the allowance check happens in `transferFrom` itself, and `_update` in the base contract only moves balances. `NativeSeiTokensERC20` inherits this `transferFrom`/`_spendAllowance` logic unmodified, so the allowance check nominally exists at the Solidity level.

The actual authorization boundary for moving native-denom funds, however, is enforced by the `Bank` precompile's `send()` function at `precompiles/bank/bank.go:198-249`, which only checks that the **calling contract address** matches the registered pointer for that denom — it does **not** check who the EVM `tx.origin`/original caller of the ERC20 method was: [3](#0-2) . The precompile trusts the pointer contract entirely to have already authorized the movement of `from`'s funds before calling `send(from, to, denom, amount)`.

This means the entire security model for native-token transfers rests on `NativeSeiTokensERC20`'s own Solidity-level allowance/ownership checks in `transfer`/`transferFrom`/`approve` being complete and correctly wired to `_update`. Because `_update` itself performs no independent verification (it only asserts the precompile call succeeded), any bug or omission in the inherited OpenZeppelin logic, or any alternate code path that calls `_update` directly (e.g., a future override of `_mint`/`_burn`, or a modified/forked pointer contract using the same pattern), bypasses balance/allowance protection entirely and lets an attacker order the Bank precompile to move funds from `from` to `to` for **any** `from` address, since the precompile itself imposes no restriction on which sender address is debited — only on which contract is calling.

This is the same class of bug as CVE-2020-5197 (Incorrect Access Control): a privileged operation (moving another account's funds) is gated only by "are you the right calling module" rather than "are you authorized to act on behalf of this specific account," and the authorization is delegated entirely to a downstream component (the ERC20 wrapper) rather than being enforced at the sensitive boundary (the precompile) itself.

### Impact Explanation
If the Solidity-side allowance check in `NativeSeiTokensERC20` were ever bypassed, skipped, or is reachable through any additional public/external function that calls `_update` without going through `transferFrom`'s `_spendAllowance`, an attacker could cause the Bank precompile to debit an arbitrary `from` account of the wrapped native denom and credit an attacker-controlled `to` address — a direct, unauthorized transfer/fund-loss scenario. Because `Bank.send()`'s only authorization gate is "caller == registered pointer contract," the security boundary is single-layered and fully dependent on the pointer contract's implementation being perfect.

### Likelihood Explanation
Exploitability requires a public code path in the pointer ERC20 contract that reaches `_update(from, to, amount)` without going through the guarded `transferFrom`/`transfer` functions. Under the current released `NativeSeiTokensERC20` implementation (which only exposes standard OpenZeppelin `transfer`/`transferFrom`/`approve`), no such bypass path is visible in this contract as-is. The concern is structural/architectural: the precompile itself provides no defense-in-depth against a coding error in the pointer contract, unlike the CW20/CW721 pointer's `execute()` path, which independently re-verifies `GetSeiAddress`/pointer ownership at the precompile layer [4](#0-3) .

### Recommendation
Harden `Bank.send()` (and any other precompile that trusts a pointer contract to have already authorized a transfer) to independently verify authorization for the specific `from` address — e.g., by requiring `from == tx.origin`'s associated Sei address, or by having the precompile track/verify an allowance itself — rather than relying solely on "caller is the registered pointer contract" as the complete access-control check. Additionally, audit `NativeSeiTokensERC20.sol` for any current or future public/external entry point that could reach `_update` without the OpenZeppelin `_spendAllowance` gate.

### Proof of Concept
Not reproducible against the current `NativeSeiTokensERC20.sol` as committed, since its only public mutators (`transfer`, `transferFrom`, inherited `approve`) correctly funnel through OpenZeppelin's `_spendAllowance`. The PoC would require identifying or introducing an additional public function that invokes `_update` directly (bypassing `_spendAllowance`), at which point calling that function with an arbitrary `from` and an attacker-controlled `to` would move funds via `Bank.send()` without the victim's consent, because `precompiles/bank/bank.go`'s `send()` performs no further check on `from`.
