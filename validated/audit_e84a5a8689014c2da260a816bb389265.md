## Analysis

The C4 report's core broken invariant is: **an ERC20 transfer call site with no zero-amount guard, invoked on a public/authenticated settlement path, permanently reverts when handed an amount of 0 against a weird ERC20 that reverts on zero-value transfers — bricking an otherwise-legitimate protocol operation.**

I found this exact anti-pattern reproduced in Hyperbridge's Tron `IntentGatewayV2` escrow-redemption path, and — crucially — the sibling EVM implementation (`IntentsBase.sol`) already carries the fix that this file is missing, which confirms the gap is a real regression rather than an intentional design choice.

### Title
Missing zero-amount guard in `IntentGatewayV2.withdraw()` (Tron) permanently locks escrowed orders when redeeming a weird ERC20 - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in the Tron `IntentGatewayV2` iterates `body.tokens` and unconditionally calls `token.call(...transfer(beneficiary, amount)...)` for every entry, even when `amount == 0`. The sibling mainline implementation in `IntentsBase.sol` explicitly skips zero-amount legs (`if (amount == 0) continue;`), but this protection was not carried over to the Tron variant. [1](#0-0)

### Finding Description
A user can craft an `Order` whose `inputs` array contains **two entries for the same token address** — one with `amount = 0` placed before an entry with the real nonzero amount — via the `predispatch` escrow path, which does not enforce a nonzero-amount check per input (unlike the non-predispatch path, which explicitly reverts with `InvalidInput` on a zero-amount input): [3](#0-2) [4](#0-3) 

Since `_orders[commitment][token]` is only incremented by the *sum* across all input entries for that token, the combined escrow balance for the token remains nonzero even though one entry's `amount` is 0. When settlement later calls `withdraw()` (from `onAccept` for `RedeemEscrow`/`RefundEscrow`, from `onGetResponse` for cross-chain cancellation, or directly from `cancelOrder` for same-chain cancellation): [5](#0-4) [6](#0-5) 

the per-entry guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` at line 691 only checks the *aggregate* escrow balance for the token, not whether this specific line item's `amount` is nonzero. So when the loop reaches the entry with `amount == 0` while the aggregate balance is still positive, it proceeds straight to the external transfer call with `amount = 0`: [7](#0-6) 

If the escrowed token reverts on a zero-value transfer (the documented "weird ERC20" class referenced in the original report), this `.call` returns `success = false`, and `if (!success) revert TransferFailed();` reverts the **entire** `withdraw()` transaction — including the legitimate nonzero legs already processed in the same loop and the fee payout at the end. Because the corrupted value is the transient `success` boolean of a doomed zero-value transfer, none of the existing checks (`UnknownOrder`, `Filled`, `authenticate`) prevent reaching this call.

### Impact Explanation
This blocks `RedeemEscrow`, `RefundEscrow`, and same-chain `cancelOrder` settlement for any order using this crafted input layout with a revert-on-zero token, permanently locking the user's or solver's rightful escrowed assets — matching the "loss/lock of bridged escrow funds" bucket in the impact gate, since `withdraw()` is the sole code path that ever releases `_orders[commitment][token]` balances back to a beneficiary.

### Likelihood Explanation
The path requires no privileged role, relayer, or governance action: the order creator alone controls the `inputs` array composition through the public, unprivileged `placeOrder` entrypoint and its `predispatch` mode, which lacks the same-index zero-amount check present in the non-predispatch branch. The only external dependency is that one of the escrowed tokens reverts on a zero-amount transfer, a documented and known ERC20 behavior class.

### Recommendation
Add the same guard used in `IntentsBase.sol` to the Tron `withdraw()` loop — skip processing (`continue`) any `body.tokens[i]` entry whose `amount == 0` before performing the external transfer call, and additionally reject duplicate-token / zero-amount entries in `order.inputs` during `placeOrder`'s predispatch branch to prevent this escrow-accounting ambiguity in the first place.

### Proof of Concept
1. Attacker (order creator) places an order via `placeOrder` using the `predispatch` path with `order.inputs = [ {token: T, amount: 0}, {token: T, amount: 100} ]`, where `T` is a token that reverts on `transfer(_, 0)`.
2. `_orders[commitment][T]` accumulates to `100` (0 + 100); the commitment is computed and escrow is held.
3. On settlement (fill + cross-chain `RedeemEscrow`, or `cancelOrder`/`RefundEscrow`), `withdraw()` iterates `body.tokens` in the same order: index 0 has `amount = 0`, and `_orders[commitment][T] == 100 != 0`, so the `UnknownOrder` guard passes.
4. The call `T.call(transfer(beneficiary, 0))` reverts (weird-ERC20 zero-value-transfer semantics), causing `TransferFailed()` to revert the whole `withdraw()` transaction.
5. The order's escrow (the real 100 `T` tokens, plus any other tokens/fees in the same `body`) can never be redeemed or refunded through this path — permanently stuck.
