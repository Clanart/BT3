## Title
Unfenced `pause_for_recent_blockhash()` in the unified scheduler causes valid, non-expired transactions to be wrongly rejected as `BlockhashNotFound` (false rejection) - (File: `unified-scheduler-pool/src/lib.rs`)

## Summary
The external report's bug class is a mismatched/unsynchronized staleness check: a fixed timeout window is compared against externally-changing data without accounting for the actual timing of when the check happens relative to when the data is captured, causing legitimate data to be misclassified as stale. The Agave analog is the `BankWithSchedulerInner::register_recent_blockhash()` / `pause_for_recent_blockhash()` interaction in `unified-scheduler-pool/src/lib.rs`: if the scheduler's paused state is not properly synchronized before the blockhash queue advances, a transaction that was scheduled while still within `max_processing_age()` can be executed *after* the blockhash queue has rotated, so `check_transaction_age()` in `runtime/src/bank/check_transactions.rs` reports the transaction's blockhash as expired even though it was valid at submission time.

## Finding Description
Transaction blockhash validity in Agave is governed by a fixed window (`max_processing_age`, i.e. `MAX_PROCESSING_AGE`) checked in `Bank::check_transaction_age()`: [1](#0-0) 

This is the direct architectural analog of the DSC protocol's `staleCheckLatestRoundData()`: a hard-coded window (`TIMEOUT` there, `max_processing_age`/`MAX_PROCESSING_AGE` here) is used to decide whether externally-supplied, time-varying data (an oracle price update there, a `recent_blockhash` here) is still "fresh enough" to be trusted.

The Bank tracks this window as a fixed field on construction: [2](#0-1) 

The unified scheduler executes transactions asynchronously relative to the `Bank`'s own advancement of its `blockhash_queue`. Correctness depends on the scheduler being paused (i.e., having finished executing all in-flight, previously-scheduled transactions) before `register_recent_blockhash()` rotates the queue, so that a transaction scheduled against an "old-but-still-valid" blockhash is never executed after that blockhash has aged out from under it. This pause step is `pause_for_recent_blockhash()`.

The test harness in `unified-scheduler-pool/src/lib.rs` demonstrates precisely this failure mode by parameterizing the pause behavior: [3](#0-2) 

When `TRIGGER_RACE_CONDITION` is true, `pause_for_recent_blockhash()` returns immediately instead of waiting (`self.do_wait()`) for pending scheduled work to finish. The accompanying test explicitly documents the resulting corruption: [4](#0-3) 

The test constructs `very_old_valid_tx`, advances the bank through `max_processing_age()` slots so the blockhash is at the edge of validity, schedules the transaction (but does not yet execute it), then calls `fill_bank_with_ticks_for_tests()` which internally triggers `register_recent_blockhash()`. With the race condition triggered, the previously-valid transaction fails with `TransactionError::BlockhashNotFound`: [5](#0-4) 

The comment in the test is explicit about the corrupted invariant: `// very_old_valid_tx is wrongly handled as expired!`. This is the same broken invariant the DSC report identifies — a fixed staleness window whose evaluation timing is decoupled from the actual freshness of the underlying data, producing an incorrect stale/fresh determination. Here it's inverted relative to the DSC report's over-permissive case: instead of *accepting* data that should be considered stale, the flaw causes the opposite failure — treating fresh, still-valid data as stale — because the check against the fixed `max_processing_age` window is performed after the reference point (the blockhash queue) has been allowed to advance out from under an in-flight transaction that was captured before the advance.

## Impact Explanation
If this ordering guarantee is not correctly enforced in the production scheduler path (as opposed to only in the test harness that exists specifically to characterize/guard against it), leader nodes would non-deterministically reject valid, fee-paying user transactions with `BlockhashNotFound`, even though the transactions were well within the blockhash's valid age when submitted and scheduled. This is a false-rejection / incorrect-execution defect: it corrupts the value `max_processing_age`'s intended guarantee (any transaction accepted into scheduling while its blockhash is valid should execute successfully or fail only for reasons unrelated to blockhash age). Because leader nodes should behave deterministically for the same input transaction stream, non-deterministic false rejection undermines fee-transaction acceptance guarantees and users' ability to have valid transactions processed, and (in a broader replay/leader context) could produce divergent transaction-acceptance behavior between differently-timed leaders processing the same transaction.

## Likelihood Explanation
The unified scheduler's asynchronous execution model inherently separates the moment a transaction is scheduled from the moment it is executed, and `register_recent_blockhash()` runs on a fixed cadence (each tick/entry) independent of the scheduler's completion state. The project itself considered this scenario important enough to build a dedicated const-generic test double (`AsyncScheduler<TRIGGER_RACE_CONDITION>`) whose sole purpose is to simulate the missing pause and assert the resulting misbehavior, which indicates the underlying hazard is real and was deliberately guarded against via the `pause_for_recent_blockhash()`/`wait_for_paused_scheduler()` synchronization. Any regression that removes or weakens that synchronization (e.g., a future scheduler implementation, a refactor of `BankWithSchedulerInner::register_recent_blockhash()`, or a new scheduler backend that forgets to call `wait_for_paused_scheduler()`) would reintroduce exactly this false-rejection condition in production, without requiring any adversarial or privileged actor — it is triggered purely by normal transaction timing under load.

## Recommendation
- Ensure every scheduler backend that hooks into `BankWithSchedulerInner::register_recent_blockhash()` correctly implements the pause contract by always waiting for previously-scheduled/in-flight tasks to complete (`wait_for_paused_scheduler()`/`do_wait()`) before the blockhash queue is rotated, never skipping it as the `TRIGGER_RACE_CONDITION` test double does.
- Add a runtime (non-test) assertion or invariant check that a scheduler cannot report itself "paused" while tasks referencing the pre-rotation blockhash are still outstanding.
- Since this pattern is exactly the failure class the existing test in `unified-scheduler-pool/src/lib.rs` (`do_test_scheduler_schedule_execution_recent_blockhash_edge_case`) is designed to catch, ensure this test (and its `TRIGGER_RACE_CONDITION = true` branch) is retained and run against every new/alternate scheduler implementation added to the codebase, not just the reference implementation.

## Proof of Concept
The existing regression test is itself the proof of concept for the underlying hazard: [4](#0-3) 
1. Build a bank and advance it exactly `max_processing_age()` slots so a transaction's blockhash is at the oldest still-valid age.
2. Schedule (but do not execute) a transfer transaction using that blockhash via `bank.schedule_transaction_executions(...)`.
3. Call `bank.fill_bank_with_ticks_for_tests()`, which internally calls `register_recent_blockhash()`.
4. With a scheduler whose `pause_for_recent_blockhash()` does not wait for in-flight scheduled work (the `TRIGGER_RACE_CONDITION = true` configuration), the blockhash queue rotates before the transaction executes, and `bank.wait_for_completed_scheduler()` returns `Err(TransactionError::BlockhashNotFound)` for a transaction that was valid when scheduled — confirmed by the assertion at [5](#0-4) .

    fn check_transaction_age(
        &self,
        tx: &impl SVMMessage,
        max_age: usize,
        next_durable_nonce: &DurableNonce,
        hash_queue: &BlockhashQueue,
        error_counters: &mut TransactionErrorMetrics,
        strict_nonce_size_check: bool,
        strict_nonce_authority_check: bool,
    ) -> TransactionResult<Option<Pubkey>> {
        let recent_blockhash = tx.recent_blockhash();
        if hash_queue
            .get_hash_info_if_valid(recent_blockhash, max_age)
            .is_some()
        {
            Ok(None)
        } else if let Some((nonce_address, _)) = self.check_nonce_transaction_validity(
            tx,
            next_durable_nonce,
            strict_nonce_size_check,
            strict_nonce_authority_check,
        ) {
            Ok(Some(nonce_address))
        } else {
            error_counters.blockhash_not_found += 1;
            Err(TransactionError::BlockhashNotFound)
        }
    }
