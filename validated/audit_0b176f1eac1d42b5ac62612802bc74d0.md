`instance()` in Tron `IntentGatewayV2` defaults unregistered peers to `address(this)`, allowing forged cross-chain messages to bypass `authenticate()` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
This is the local analog of the Augur `CloneFactory` bug: a lookup that returns a zero/default value for an unregistered key is trusted downstream without validation. Instead of Augur's `lookup` defaulting to `address(0)` (causing only an uninformative revert), Hyperbridge's Tron `IntentGatewayV2.instance()` defaults an **unregistered** state-machine id to `address(this)` — the gateway's *own* address — which is then used as the expected sender in `authenticate()`. Because gateway proxy addresses are deployed deterministically (CREATE2, identical salt/init data across chains, as seen in `evm/script/DeployIntentGateway.s.sol`), this default can collide with a real, attacker-reachable value instead of safely failing closed.

### Finding Description
`evm/tron/contracts/apps/IntentGatewayV2.sol` lines 278-294:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```
Compare this to the EVM-mainline `IntentGatewayV2` (`evm/src/apps/intentsv2/IntentsBase.sol`, `_instance`), which correctly fails closed:
```solidity
function _instance(bytes calldata stateMachineId) internal view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```

In the Tron variant, `instance()` for *any* `stateMachineId` that was never registered via a `NewDeployment` governance message returns `address(this)` instead of reverting. `authenticate()` (used to gate `onAccept` for `RedeemEscrow`, `NewDeployment`, `UpdateParams`, `SweepDust`, `RefundEscrow`) then treats the incoming message as legitimate whenever `request.from == address(this)`, regardless of whether `request.source` is a real, registered peer.

Because the deployment script (`evm/script/DeployIntentGateway.s.sol`) explicitly deploys the gateway via CREATE2 with an identical salt/implementation/init data "so no peer address is embedded in the init data ... keeping the proxy address identical everywhere," an attacker can deploy an identical contract to the same address on *any* EVM-compatible chain that Hyperbridge's ISMP infrastructure can generate valid consensus/state proofs for but that was never explicitly added to `_instances` as a trusted peer. A genuine (non-forged, consensus-proof-backed) ISMP message from that unregistered chain, with `from` set to that deterministic address, will pass `authenticate()` because `instance(unregistered_source)` resolves to `address(this)`, matching `module`.

### Impact Explanation
This breaks the "module/app identity binding" invariant required by the bounty (Request/response paths must bind module identity). An attacker satisfying this collision can submit privileged `RequestKind` payloads (`RedeemEscrow`, `RefundEscrow`, `SweepDust`, `UpdateParams`, `NewDeployment`) that the gateway will treat as coming from a trusted peer instance, potentially:
- Releasing escrowed order funds (`RedeemEscrow`/`RefundEscrow`) to an attacker-chosen beneficiary without a legitimate fill/cancellation having occurred on the real peer chain.
- Registering a malicious `NewDeployment` gateway address for some state machine, which downstream authentication and cancel-order storage-proof paths would then trust.
- Sweeping protocol dust (`SweepDust`) to an attacker address.

This is unauthorized execution / potential fund loss via a false trust-boundary acceptance, matching the bounty's "false proof/state acceptance" and "unauthorized transaction or execution" categories, without requiring a malicious relayer, prover, or admin — only that the attacker can get a legitimately-proven ISMP message accepted from a chain/address they control.

### Likelihood Explanation
Exploitability depends on: (1) whether Hyperbridge's ISMP/consensus-client infrastructure accepts proofs from EVM chains outside the explicitly configured peer list for this gateway (plausible, since consensus clients are typically chain-generic, e.g. sync-committee/parachain clients configured per network rather than per-app peer), and (2) the attacker being able to deploy a contract to the exact CREATE2 address used for `IntentGatewayV2` on that chain (achievable since the salt, implementation bytecode, and constructor argument are all public in the deploy script). This does not require a malicious relayer/operator — it only requires the underlying consensus verification to be chain-scoped, not peer-scoped, which is the normal architecture for ISMP. This is a real logic bug in the file (diverging from the correctly fail-closed EVM-mainline sibling), independent of speculation about relayer/operator behavior.

### Recommendation
Change `instance()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert on an unregistered state machine id (mirroring `IntentsBase._instance` in the mainline EVM contract), e.g.:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    if (gateway == address(0)) revert UnknownInstance();
    return gateway;
}
```
Audit all callers (`authenticate`, `cancelOrder`'s storage-proof key construction) to ensure they handle the revert correctly instead of relying on a same-contract fallback for unregistered peers.

### Proof of Concept
1. Note from `evm/script/DeployIntentGateway.s.sol` that `IntentGatewayV2` is deployed via `CREATE2` with a fixed `salt`, identical `implementation` bytecode, and `initData` that does not embed any peer address — producing the *same* contract address across all EVM chains.
2. An attacker deploys the same implementation/proxy bytecode with the same `salt`/`initData` pattern to an EVM-compatible chain that is supported by Hyperbridge's consensus clients but that was never added to the target gateway's `_instances` mapping (i.e., never included in `peerChains` at `initialize`, and never registered via a `NewDeployment` message).
3. The attacker (or any actor who can drive a legitimate transaction on that unregistered chain) dispatches a POST request whose ISMP `from` field encodes that deterministic CREATE2 address and whose body is a `RequestKind.RedeemEscrow` (or `SweepDust`/`RefundEscrow`) payload targeting the victim gateway.
4. Once the real ISMP consensus/state proof for that source chain is delivered and verified by the destination `EvmHost`/handler (per `evm/src/core/EvmHost.sol` `dispatchIncoming`), the victim `IntentGatewayV2.onAccept` invokes `authenticate(request)`.
5. `authenticate()` calls `instance(request.source)`; since `request.source` was never registered, `instance()` returns `address(this)`, which equals `module` (`bytes20(request.from)`), so `Unauthorized` is never raised.
6. The forged `RedeemEscrow`/`SweepDust`/`RefundEscrow`/`NewDeployment` request executes as if it came from a trusted peer gateway, moving escrowed funds or dust to an attacker-controlled beneficiary, or registering a malicious peer instance. [1](#0-0) [2](#0-1) [3](#0-2)
