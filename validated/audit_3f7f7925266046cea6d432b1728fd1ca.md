## Title
Missing bounds checks in CLVM canonical-atom length-prefix parsing enable an unhandled-exception DoS during DEDUP-eligibility processing - (File: chia/full_node/mempool_manager.py)

## Summary
The external CVE describes an integer-underflow-driven out-of-bounds read in X.Org's length-prefix parsing logic that leads to a heap-buffer overflow. The analogous bug class in this codebase is a length-prefix parser that walks a byte buffer using an attacker-controlled length field without validating that the buffer actually contains enough bytes: `is_atom_canonical()` / `is_clvm_canonical()` in `chia/full_node/mempool_manager.py`.

## Finding Description
`is_clvm_canonical()` iterates over a raw CLVM-serialized byte buffer (`clvm_buffer`) coming from a coin spend's puzzle reveal/solution, advancing an `offset` cursor based on a variable-length size prefix read from `is_atom_canonical()`: [1](#0-0) 

`is_atom_canonical(clvm_buffer, offset)` decodes a multi-byte length prefix (up to 5 extra bytes) directly by indexing `clvm_buffer[offset]` in a loop with no check that `offset` stays within `len(clvm_buffer)`: [2](#0-1) 

and `is_clvm_canonical()`'s main loop reads `clvm_buffer[offset]` again on the next token without re-validating that `offset < len(clvm_buffer)`: [3](#0-2) 

If an attacker crafts a spend whose puzzle reveal/solution ends with a truncated/malformed length-prefix byte (e.g., a byte that declares a 5-byte length prefix but the buffer ends one byte later), `clvm_buffer[offset]` will raise an unhandled `IndexError` inside `is_atom_canonical`/`is_clvm_canonical`, rather than returning a bounds/parse error as the surrounding logic expects. This mirrors the CVE's underlying flaw class: a length-derived cursor/offset computation that is not clamped to the actual buffer size before further indexing/reads.

## Impact Explanation
If reachable from `validate_spend_bundle()`'s DEDUP-eligibility check (as the `.cursor/context/mempool.md` documentation states — "DEDUP eligibility requires canonical CLVM serialization"), a single unprivileged spend-bundle submitter could trigger an unhandled `IndexError` while the full node is validating an incoming transaction. Depending on how the caller handles exceptions from this specific function (unclear from the retrieved code — the broader `pre_validate_spendbundle` catches only `ValueError`, not generic exceptions), this could propagate as an uncaught exception during spend-bundle validation, causing a processing halt or crash of the validation worker/thread handling that spend bundle — a mempool-admission-triggered denial-of-service condition. This does not lead to memory corruption in Python (bytes indexing is bounds-checked and raises a catchable exception rather than reading out-of-bounds memory), so the impact is limited to an unhandled exception/DoS rather than data confidentiality/integrity compromise as in the original CVE.

## Likelihood Explanation
Likelihood is moderate: constructing a coin spend with a puzzle reveal/solution containing a crafted truncated atom-length prefix is straightforward for any spend-bundle submitter (no special privileges needed), but the actual severity hinges entirely on whether the calling code (`validate_spend_bundle`/`pre_validate_spendbundle`) catches generic exceptions raised from this function. I could not confirm from available context whether such a broad exception handler exists around the DEDUP-canonical check specifically, so I cannot assert with confidence that this results in an unrecoverable processing halt versus a caught, gracefully-rejected item.

## Recommendation
Add explicit bounds checks in `is_atom_canonical()` before each `clvm_buffer[offset]` access (raise a clear, expected error such as returning `canonical=False` or raising a dedicated, caught exception if `offset >= len(clvm_buffer)`), and add the same check in `is_clvm_canonical()`'s main loop before indexing `clvm_buffer[offset]`. Ensure any caller of `is_clvm_canonical` (DEDUP-eligibility check in spend-bundle admission) wraps the call so a malformed/truncated buffer is turned into a normal validation rejection instead of an unhandled exception.

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value

```
