### Title
Attacker-controlled commit identity string can permanently brick commit-history loading (DoS) - ([File: app/src/models/commit-identity.ts])

### Summary
`CommitIdentity.parseIdentity()` throws an uncaught `Error` whenever an author/committer identity string does not exactly match a strict regex. This method is called unguarded on every commit's author and committer fields inside `getCommits()`, which is the core function used by History, Squash, Rebase, and Undo-Commit features. A malicious repository (or a malicious commit fetched from an untrusted remote) can craft a commit object whose author/committer header does not conform to the expected `NAME <EMAIL> DATE TZ` shape, causing every subsequent call that tries to read that commit's history to throw — permanently breaking those features for the repository, analogous to the Angle Protocol finding where an attacker-donated value causes an arithmetic overflow that reverts (bricks) all future redemption calls.

### Finding Description
`CommitIdentity.parseIdentity` parses a raw Git ident string using a rigid regex: [1](#0-0) 

If the regex fails to match, it throws `Error("Couldn't parse identity ...")`, and if the parsed date is invalid it throws a second `Error`. There is no fallback value.

This function is invoked directly and unguarded (no try/catch) for both author and committer of *every* commit returned by `git log` in `getCommits()`: [2](#0-1) 

and again in `getAuthors()`: [3](#0-2) 

Git's raw commit object format does not enforce `fmt_ident()`'s well-formed shape when *reading* a commit — that shaping only happens when Git itself *creates* a commit via porcelain commands. An attacker can produce a commit object with plumbing (`git hash-object -t commit -w --stdin` / `git commit-tree`) whose `author`/`committer` header line is missing the date entirely, uses a non-numeric epoch, omits the `< >` bracket pair, or otherwise fails the regex `^(.*?) <(.*?)> (\d+) (\+|-)?(\d{2})(\d{2})`. Because this is a raw header on a Git object under the attacker's control, and the app parses it verbatim via `%an <%ae> %ad` / `%cn <%ce> %cd` format strings, the malformed content flows straight into `parseIdentity` with no sanitation or fallback.

Unlike other call sites in the codebase (e.g. `getAuthorIdentity` in `app/src/lib/git/var.ts:37-41`, which explicitly wraps the call in `try { ... } catch { return null }`), `getCommits()` and `getAuthors()` do not guard the call, so the thrown exception propagates out of `getCommits`.

### Impact Explanation
`getCommits()` is the backbone of commit history retrieval and is used throughout core, unprivileged workflows:
- Loading the History/Changes commit log (`git-store.ts` `loadCommitBatch`/history refresh paths)
- `squash()` (`app/src/lib/git/squash.ts:56-61`) — reads commit range before performing a squash rebase
- `getCompareCommits()` (`app/src/lib/stores/git-store.ts:1697-1730`) — branch comparison view
- `undoCommit()`/co-author restoration paths that ultimately touch commit metadata

If a single commit anywhere in the relevant revision range has a malformed identity string, the exception thrown deep inside `.map()` propagates out of `getCommits`. Any caller not wrapping the call defensively (multiple of the above paths call it directly, outside `performFailableOperation`) will surface an unhandled rejection, breaking commit history browsing, squash, and branch comparison for that repository every single time those operations are attempted against the poisoned commit — a durable, repeatable denial of service that "bricks" these features analogous to the Angle Protocol redemption bricking, since the corrupting object (a single bad commit) persists in the repository history and cannot be worked around by the victim without manual git surgery.

### Likelihood Explanation
Likelihood is moderate-to-high for any project that clones/fetches from third-party or public sources: the attacker does not need any privileged access to the victim's machine — only the ability to have the victim clone or fetch a repository containing one crafted commit (e.g., a public repo, a pull request branch, or a malicious remote). Crafting such a commit requires only Git plumbing commands, no special server compromise. The main uncertainty is which exact call sites lack a try/catch around `getCommits`/`getAuthors` at HEAD of this codebase snapshot — the search here confirmed the two direct, unguarded call sites in `app/src/lib/git/log.ts`, but a full audit of every consumer path (`git-store.ts`, `squash.ts`, `app-store.ts`) to confirm the absence of an outer catch was not fully exhaustive within the available search budget.

### Recommendation
Make `CommitIdentity.parseIdentity` resilient to malformed input instead of throwing for core read paths:
- Return a best-effort fallback identity (e.g., empty name/email, `epoch` date) when the regex doesn't match, similar to how the Angle Protocol recommendation was to clamp to `type(uint64).max` instead of reverting.
- Alternatively, wrap the `.map(CommitIdentity.parseIdentity)` calls in `getCommits()`/`getAuthors()` with per-commit try/catch so a single malformed commit degrades gracefully (e.g., shows "Unknown Author") rather than failing history loading entirely.
- Add regression tests with crafted malformed ident strings (missing date, missing brackets, non-numeric epoch) exercised through `getCommits` end-to-end, not just the unit-level `CommitIdentity.parseIdentity` tests.

### Proof of Concept
1. Create a repository and add a blob/tree as usual.
2. Manually craft a commit object with an invalid author line, bypassing `git commit`'s ident formatting, e.g.:
   ```
   printf 'tree <TREE_SHA>\nauthor Evil Author 1234567890\ncommitter Evil Author <evil@example.com> 1234567890 +0000\n\nmalicious commit\n' | git hash-object -t commit -w --stdin
   ```
   (note: `author` line intentionally omits the `<email>` and epoch/timezone shape required by `parseIdentity`)
3. Point a branch/tag at that commit SHA and publish the repository (or serve it via a local remote) for the victim to clone/fetch.
4. In GitHub Desktop, clone/fetch the repository and open the History tab (or attempt Squash/Compare involving that commit).
5. `getCommits()` calls `CommitIdentity.parseIdentity(commit.author.toString())` on the malformed `author` field, the regex fails to match, and an `Error` is thrown, uncaught, from `app/src/lib/git/log.ts:191-192`, breaking history loading (and related squash/compare operations) for that repository indefinitely.

```typescript
  public static parseIdentity(identity: string): CommitIdentity {
    // See fmt_ident in ident.c:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L346
    //
    // Format is "NAME <EMAIL> DATE"
    //  Markus Olsson <j.markus.olsson@gmail.com> 1475670580 +0200
    //
    // Note that `git var` will strip any < and > from the name and email, see:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L396
    //
    // Note also that this expects a date formatted with the RAW option in git see:
    //  https://github.com/git/git/blob/35f6318d4/date.c#L191
    //
    const m = identity.match(/^(.*?) <(.*?)> (\d+) (\+|-)?(\d{2})(\d{2})/)
    if (!m) {
      throw new Error(`Couldn't parse identity ${identity}`)
    }
```
