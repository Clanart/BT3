### Title
`PayoutCheckerTask` deduplicates payouts by withdrawal `idx`, not by `move_to_vault_txid`, allowing double reimbursement when two withdrawal rows share the same vault - ([File: core/src/task/payout_checker.rs])

### Summary
`PayoutCheckerTask::run_once` and `Operator::handle_finalized_payout` treat every unhandled `withdrawals.idx` row as an independent reimbursement request, resolving it to a `deposit_id` via `move_to_vault_txid` and allocating a fresh unused kickoff connector for that `deposit_id` on every call. Nothing checks whether another `idx` row already reimbursed the *same* `move_to_vault_txid`/`deposit_id`, so two withdrawal rows sharing a `move_to_vault_txid` and payer key let the operator run the full Kickoff→Reimburse flow twice for one vault.

### Finding Description
The binding the question claims should hold is: `count(mark_payout_handled calls that reference the same move_to_vault_txid) == 1`. Tracing the code shows this is false; the real invariant enforced is only `count(mark_payout_handled calls per distinct withdrawals.idx) == 1`.

- `get_first_unhandled_payout_by_operator_xonly_pk` selects rows by `w.idx`, filtered on `is_payout_handled = FALSE AND payout_payer_operator_xonly_pk = $1`, ordered by `idx ASC LIMIT 1` [1](#0-0) . It has no awareness of `move_to_vault_txid` uniqueness.
- The `withdrawals` table's only primary key is `idx`; `move_to_vault_txid` has no `UNIQUE` constraint [2](#0-1) , and `update_replacement_deposit_move_txid` blindly overwrites a single row's `move_to_vault_txid` with no collision check against other rows [3](#0-2) .
- `PayoutCheckerTask::run_once` resolves the row to `deposit_data` via `get_deposit_data_with_move_tx(move_to_vault_txid)` and calls `Operator::handle_finalized_payout(deposit_data.get_deposit_outpoint(), payout_tx_blockhash)` [4](#0-3) . If two idx rows share `move_to_vault_txid`, both resolve to the same `deposit_outpoint`/`deposit_id`.
- Inside `handle_finalized_payout`, the only "used" check is per `deposit_id`: `get_unused_and_signed_kickoff_connector(deposit_id, operator_xonly_pk)` picks the next connector not yet in `used_kickoff_connectors`, ordered by `round_idx ASC LIMIT 1` [5](#0-4) . It never checks whether this `deposit_id` (or its `move_to_vault_txid`) was already reimbursed by a prior call; it only checks whether a specific `(round_idx, kickoff_idx)` connector is used.
- After signing and queuing the Kickoff/Reimburse-path transactions, `handle_finalized_payout` marks only that one connector used via `mark_kickoff_connector_as_used` [6](#0-5) .
- Back in `run_once`, `mark_payout_handled(citrea_idx, kickoff_txid)` sets `is_payout_handled = TRUE` on the single `idx` row only, via `UPDATE withdrawals ... WHERE idx = $1` [7](#0-6) .

Because the "is_payout_handled" flag and the "used kickoff connector" allocation are both scoped below the deposit/vault level (per-idx and per-connector, respectively), a second withdrawal row (`idx2`) with the same `move_to_vault_txid` and the same recorded `payout_payer_operator_xonly_pk` remains eligible: the next `run_once` invocation will select `idx2`, resolve to the same `deposit_id`, obtain a *different* unused kickoff connector for that deposit, and produce a second, independent Kickoff→Reimburse chain — a second Reimburse claim against the same underlying vault/deposit, funded by the same single fronted payout.

None of the existing guards (`Verifier::is_deposit_valid`, `is_profitable`, `SECP.verify_schnorr`, `is_kickoff_malicious`, `SPV::verify`, database uniqueness constraints) intervene here, because they operate on different stages of the pipeline (payout attribution, kickoff validity, or deposit validity) and none re-checks "has this `deposit_id`/`move_to_vault_txid` already had a kickoff connector consumed for a payout."

### Impact Explanation
If two `withdrawals.idx` rows are made to share a `move_to_vault_txid` and payer `xonly_pk` (per the OP_RETURN-spoofing/front-run replacement scenario assumed by the question), the operator credited as payer will have `handle_finalized_payout` executed twice for the same deposit, consuming two separate presigned kickoff connectors and producing two Kickoff/Reimburse transaction chains for one vault. This matches the Critical impact category "an operator reimbursed for a payout it never funded" (the second reimbursement is unbacked by any second real fronting), draining an extra reimbursement amount from the operator's own round/collateral chain that was only entitled to one reimbursement per deposit. The blast radius scales with however many "unused signed" kickoff connectors exist for the deposit and how many colliding withdrawal rows can be produced, and is repeatable across any deposit/operator pairing that can be forced into this shared-`move_to_vault_txid` state.

### Likelihood Explanation
The exploit requires reaching the precondition described in the question (two `idx` rows sharing `move_to_vault_txid` and payer `xonly_pk`), which the question states is achievable via the OP_RETURN-spoofing/front-run replacement scenario acting on `update_replacement_deposit_move_txid`. Given that precondition, the rest of the exploit path requires no further attacker privilege — it is a natural consequence of `PayoutCheckerTask`'s and `handle_finalized_payout`'s per-idx/per-connector bookkeeping, which is deterministic and reproducible without any race condition (simply running `run_once` twice suffices, since each call commits and marks only the row it processed).

### Recommendation
Enforce the reimbursement-uniqueness invariant at the deposit/vault level, not the withdrawal-row level:
- Add a uniqueness/idempotency check in `handle_finalized_payout` (or in `get_first_unhandled_payout_by_operator_xonly_pk`) that a `deposit_id`/`move_to_vault_txid` has not already had a kickoff connector allocated/used for reimbursement, e.g., by querying `used_kickoff_connectors`/`deposit_signatures` joined on `deposit_id` before allowing another `idx` row referencing the same `deposit_id` to proceed.
- Alternatively/additionally, add a `UNIQUE` constraint or partial unique index on `withdrawals(move_to_vault_txid)` restricted to non-null, "active" (not-yet-reimbursed) rows, and make `update_replacement_deposit_move_txid` reject writes that would violate it.

// Setup: two withdrawal rows sharing move_to_vault_txid and payer xonly_pk.

#[tokio::test]
async fn test_double_reimbursement_via_shared_move_to_vault_txid() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    // ... insert a real deposit via insert_deposit_data_if_not_exists to get deposit_id/move_to_vault_txid ...
    let move_to_vault_txid = /* the deposit's move_to_vault_txid */;
    let operator_xonly_pk = /* operator under test */;

    // idx = 1 gets the real move_to_vault_txid
    db.upsert_move_to_vault_txid_from_citrea_deposit(None, 1, &move_to_vault_txid).await.unwrap();
    // idx = 2 is forced (via update_replacement_deposit_move_txid) onto the SAME move_to_vault_txid
    let mut dbtx = db.begin_transaction().await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), 2, &Txid::all_zeros()).await.unwrap();
    db.update_replacement_deposit_move_txid(&mut dbtx, 2, move_to_vault_txid).await.unwrap();
    dbtx.commit().await.unwrap();

    // Both rows get a payout_txid + same payer xonly_pk (simulating spoofed OP_RETURN attribution)
    db.update_payout_txs_and_payer_operator_xonly_pk(
        None,
        vec![
            (1, Txid::from_byte_array([1;32]), Some(operator_xonly_pk), BlockHash::all_zeros()),
            (2, Txid::from_byte_array([2;32]), Some(operator_xonly_pk), BlockHash::all_zeros()),
        ],
    ).await.unwrap();

    let mut task = PayoutCheckerTask::new(db.clone(), operator.clone());

    // First run: handles idx=1, allocates kickoff connector A, marks idx=1 handled.
    assert!(task.run_once().await.unwrap());
    let kickoff_txid_1 = db.get_handled_payout_kickoff_txid(None, Txid::from_byte_array([1;32])).await.unwrap().unwrap();

    // Second run: idx=2 is still is_payout_handled=FALSE (per-row flag), same move_to_vault_txid,
    // allocates a DIFFERENT kickoff connector B, marks idx=2 handled too.
    assert!(task.run_once().await.unwrap());
    let kickoff_txid_2 = db.get_handled_payout_kickoff_txid(None, Txid::from_byte_array([2;32])).await.unwrap().unwrap();

    // BUG: two distinct kickoff/Reimburse chains exist for the SAME move_to_vault_txid.
    assert_ne!(kickoff_txid_1, kickoff_txid_2);
    // Binding violated: count of mark_payout_handled/kickoff creations for this move_to_vault_txid == 2, not 1.
}

    pub async fn get_unused_and_signed_kickoff_connector(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        deposit_id: u32,
        operator_xonly_pk: XOnlyPublicKey,
    ) -> Result<Option<(RoundIndex, u32)>, BridgeError> {
        let query = sqlx::query_as::<_, (i32, i32)>(
            "WITH current_round AS (
                    SELECT round_idx
                    FROM current_round_index
                    WHERE id = 1
                )
                SELECT
                    ds.round_idx as round_idx,
                    ds.kickoff_idx as kickoff_connector_idx
                FROM deposit_signatures ds
                CROSS JOIN current_round cr
                WHERE ds.deposit_id = $1  -- Parameter for deposit_id
                    AND ds.operator_xonly_pk = $2
                    AND ds.round_idx >= cr.round_idx
                    AND NOT EXISTS (
                        SELECT 1
                        FROM used_kickoff_connectors ukc
                        WHERE ukc.round_idx = ds.round_idx
                        AND ukc.kickoff_connector_idx = ds.kickoff_idx
                    )
                ORDER BY ds.round_idx ASC
                LIMIT 1;",
        )
        .bind(i32::try_from(deposit_id).wrap_err("Failed to convert deposit id to i32")?)
        .bind(XOnlyPublicKeyDB(operator_xonly_pk));

        let result = execute_query_with_tx!(self.connection, tx, query, fetch_optional)?;

        match result {
            Some((round_idx, kickoff_connector_idx)) => Ok(Some((
                RoundIndex::from_index(
                    usize::try_from(round_idx).wrap_err("Failed to convert round idx to u32")?,
                ),
                u32::try_from(kickoff_connector_idx)
                    .wrap_err("Failed to convert kickoff connector idx to u32")?,
            ))),
            None => Ok(None),
        }
    }
