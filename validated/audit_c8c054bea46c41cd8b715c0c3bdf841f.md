### Title
PedPoG/PedPoP accepts identity encryption keys, broadcasting secret shares under a publicly-derivable cipher to any channel observer - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2024-47081 (crafted input causes credentials to be disclosed to unintended third parties), `EncryptionKeyMessage::read` accepts the group identity as a participant's `enc_key` because it uses `Ciphersuite::read_G`, which only enforces canonical encoding and does not reject identity (`crypto/ciphersuite/src/lib.rs:91-101`; the identity rejection exists only in `frost::Curve::read_G`, `crypto/frost/src/curve/mod.rs:125-131`). Once an identity key is registered, every honest participant ECDH-encrypts their secret share for that participant against the identity point, producing a keystream any observer can recompute — the "encrypted" share is plaintext to the world.

### Finding Description
- `EncryptionKeyMessage::read` (encryption.rs:57-58) reads `enc_key` via `C::read_G`, which checks only canonicality, not `is_identity`.
- `Decryption::register` (encryption.rs:351-362) stores the supplied `enc_key` with no validation.
- `Encryption::encrypt` → `encrypt` (encryption.rs:135-168) computes the shared key as `ecdh(key, to) = to * key` (encryption.rs:95-97). If `to` is the identity point, the shared point is identity regardless of the ephemeral `key`.
- `cipher` (encryption.rs:101-133) derives the ChaCha20 key solely from `RecommendedTranscript::new(b"DKG Encryption v0.2")`, the public `context`, and `ecdh.to_bytes()` — here the identity encoding, a constant. The IV is static (`b"DKG IV v0.2\0"`). The keystream is therefore publicly computable by anyone who knows `context` (not a secret; "unique among multisigs", lib.rs:147).
- Nothing else validates `enc_key`: `verify_r1` (lib.rs:300-337) only checks the commitments' PoK and length before `register` is called.

### Impact Explanation
A malicious DKG participant broadcasts an `EncryptionKeyMessage` with `enc_key = identity`. Every honest participant then computes their Pedersen share `f_j(attacker_index)`, encrypts it to identity, and emits a ciphertext that decrypts with a publicly known keystream. Any passive observer of the (authenticated, not confidential) channel — and any node later evaluating blame via `AdditionalBlameMachine`/`blame` — recovers each honest participant's secret-share value at the attacker's index. These values are the confidential DKG secret shares whose protection is the stated purpose of the encryption layer (`spec/cryptography/Distributed Key Generation.md`: "In order to protect the secret shares during communication..."). For each honest polynomial, k malicious participants registering identity keys collectively expose k distinct evaluations, directly eroding the threshold: with t-1 non-threshold participants' indexes compromised this way, a single additional share disclosure reconstructs an honest dealer's polynomial and their contributed secret. This is a secret-disclosure-to-unintended-party flaw reachable entirely with attacker-supplied public bytes.

### Likelihood Explanation
Any participant in a DKG session can set the identity encoding in their commitment message; it parses, registers, and produces no error. The attack requires no collusion and leaves the protocol completing normally (shares still verify via `share_verification_statements`, since the plaintext share is a valid share). Detection requires an out-of-band check of `enc_key` that the library never performs. Likelihood is bounded by the need to be a DKG participant and by the fact that a lone attacker exposes only evaluations at their own index (medium impact per the class).

### Recommendation
Reject the identity point wherever a public key is deserialized for encryption or ECDH: add an `is_identity` check in `EncryptionKeyMessage::read`/`Decryption::register`, and likewise for `EncryptedMessage::read`'s per-message `key` (an identity `msg.key` yields `ecdh = identity` and a publicly-decryptable ciphertext; its Schnorr PoP still verifies since `s·G = R + c·identity`). Reuse the pattern in `frost::Curve::read_G`, and consider also rejecting identity `Commitments[0]` despite the PoK (a valid Schnorr signature under the identity key is trivially produced with secret 0).

### Proof of Concept
1. Attacker, as participant `k` in a `t`-of-`n` PedPoP session with known `context`, broadcasts `EncryptionKeyMessage { msg: valid Commitments, enc_key: C::G::identity() }`. `C::read_G` accepts it (canonical encoding of identity).
2. Each honest participant `j` calls `SecretShareMachine::generate_secret_shares` → `encrypt(rng, k, share_bytes)`, which computes `ecdh = identity * key_j = identity` and ChaCha20-encrypts `f_j(k)` under key `H("DKG Encryption v0.2" || context || "encryption_key" || identity_bytes || "key")` with IV `"DKG IV v0.2\0"`.
3. Observer computes the same keystream, XORs it against `msg` in the wire `EncryptedMessage`, and recovers `f_j(k)` in cleartext for every honest `j` — all checks (`pop` batch verify, share verification) pass since the underlying share is valid.
4. Optionally, the attacker (or an observer given a blame `EncryptionKeyProof`, which here just reveals the public identity point) confirms decryption via `Decryption::decrypt_with_proof`.
