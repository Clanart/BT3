### Title
Attacker-controlled participant count in `ThresholdKeys::read` triggers O(t²) interpolation and n point decompressions, enabling CPU exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a `n` (participant count) value of up to 65535 directly from untrusted input bytes. It then decompresses `n` group elements via `C::read_G` and calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for each of `t` participants — each factor itself an O(t) loop ending in a field inversion. The result is O(t²) scalar multiplications plus `t` field inversions and `n` elliptic-curve point decompressions from a single ~4 MB input, a resource-exhaustion primitive analogous to CVE-2021-3669 (work that does not scale gracefully with an attacker-controlled count).

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16`s, reads `n` verification shares through `<C as Ciphersuite>::read_G`, then calls `ThresholdKeys::new` (lines 591-632). `ThresholdParams::new` only checks `t <= n` and `i <= n` (lines 166-179); there is no cap on `n`. `ThresholdKeys::new` then computes the group key as a sum over participants `1..=t` of `verification_shares[i] * interpolation_factor(i, t)` (lines 376-378). `interpolation_factor` for `Interpolation::Lagrange` runs a loop over all `t` included participants and finishes with a scalar inversion (lines 229-247), making key construction O(t²) field multiplications plus `t` inversions, in addition to `n` point decompressions performed during deserialization.

With `t = n = 65535`, a single serialized `ThresholdKeys` blob of roughly `n * point_len` bytes (~2-4 MB for Ristretto/ed25519) forces ~4.3 billion field multiplications and 65535 field inversions plus 65535 point decompressions — orders of magnitude more CPU work than the input size suggests.

### Impact Explanation
Anywhere untrusted bytes reach `ThresholdKeys::read` (one of the sanctioned untrusted-input entry points), an unprivileged remote party can supply a crafted key blob that stalls the deserializing thread for a very long time on a single message. Because the amplification factor grows quadratically in `t`, a small number of such messages can exhaust CPU on a validator/processor node — a denial of service against threshold-signing availability, matching the Medium-severity resource-exhaustion class of CVE-2021-3669.

### Likelihood Explanation
The input format fully controls `n` (u16) and the `n` point encodings; no authentication or prior validation bounds `n` below the u16 maximum. `ThresholdKeys::new` performs the expensive `group_key` computation unconditionally before returning, so the cost is paid even for inputs that would later be rejected for other reasons. The only constraint on the attacker is producing `n` syntactically valid point encodings (they need not be on-curve-valid for interpolation cost; `read_G` canonicality checks reject invalid points early, but valid encodings are trivially generatable, e.g. multiples of the generator).

### Recommendation
Bound `t`/`n` in `ThresholdParams::new` or in `ThresholdKeys::read` to a protocol-appropriate maximum (e.g. the tributary set size), before any O(n) deserialization or O(t²) interpolation work. Alternatively, derive `group_key` lazily or from a cached/constant term so deserialization cost is linear in input size.
