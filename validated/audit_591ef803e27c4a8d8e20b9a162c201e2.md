## Analog Vulnerability Found

### Title
CR-CAT (credential-restricted CAT) coins locked in "pending approval" state become permanently unclaimable if the recipient's Verified Credential is revoked/expired by its authorized provider - ([File: chia/wallet/vc_wallet/cr_cat_wallet.py])

### Summary
The reported issue describes an ERC20-analog where a payout loop reverts entirely if a recipient becomes "blacklisted" by a token, permanently stalling liquidation. The closest reachable analog in this Chia repo is the CR-CAT ("credential restricted CAT") mechanism, where receiving CR-CAT coins that are deferred to a "pending approval" puzzle hash can *only* ever be released to spendable balance by presenting a valid Verified Credential (VC) issued by one of a fixed `authorized_providers` list. If that provider revokes or fails to refresh the recipient's proofs (the Chia equivalent of an issuer "blacklisting" an address), the coins are permanently stuck with no alternate recovery path in the codebase.

### Finding Description
CR-CATs restrict every transfer/claim to require a VC-backed proof from one of the coin's `authorized_providers`:

- When constructing offers/payments that a wallet cannot immediately verify, `TradeManager.check_for_requested_payment_modifications` redirects CR-CAT payments to a "pending approval" puzzle hash instead of the real recipient inner puzzle hash. [1](#0-0) 

- `VCWallet.add_vc_authorization` explicitly allows CR-CAT outputs to go to this "pending approval" state so that authorization can be deferred to "another user's VC" later. [2](#0-1) 

- The only way to move these coins out of the pending state into spendable balance is `CRCATWallet.claim_pending_approval_balance`, which requires locating a VC with a provider in the coin's `authorized_providers` list and a valid `proof_hash` satisfying the `proofs_checker` flags; if none exists, it raises `RuntimeError`. [3](#0-2) 

- The underlying lookup, `VCWallet.get_vc_with_provider_in_and_proofs`, raises if there is no VC record for the required providers or if none of the recipient's proofs match the needed flags. [4](#0-3) 

- The same VC-availability requirement gates *any* future spend of the recipient's CR-CAT holdings (not just claiming pending coins): `_generate_unsigned_spendbundle` raises `RuntimeError("CR-CATs cannot be spent without an appropriate VC")` when no VC wallet/VC is present. [5](#0-4) 

Because the VC's proof set is entirely controlled by the external `proof_provider` (the CR-CAT's `authorized_providers`), a provider can simply stop signing/refreshing the recipient's proofs (i.e., effectively "de-authorize"/"blacklist" that user), exactly mirroring the reported ERC20-blacklist scenario. Once that happens:
1. Any CR-CAT payment already sitting in "pending approval" state addressed to that user can never be claimed (`claim_pending_approval_balance` will always raise `RuntimeError`).
2. Any CR-CAT coins already confirmed to that user's spendable balance can no longer be moved at all (`_generate_unsigned_spendbundle` requires a currently valid VC on every spend, not just at receipt time).

Unlike the audited protocol's suggestion of an escrow fallback, there is no alternate reclaim/clawback path coded for CR-CAT "pending approval" coins in this repository — the only exit is via a VC that the provider fully controls.

### Impact Explanation
This produces a concrete, spend-triggered halt of legitimate coin movement: value that should be under the recipient's economic control is provably locked as soon as the sole gatekeeping provider withdraws proof access, with no unprivileged recovery path (analogous to the "bad debt"/stuck-liquidation impact in the source report). This is a protocol design/implementation gap reachable by an ordinary wallet user or offer counterparty (no privileged or malicious-peer access required) simply by using CR-CAT trading/offer flows as intended.

### Likelihood Explanation
Any CR-CAT deployment that relies on `authorized_providers`/VC proofs for compliance (the stated purpose of CR-CATs, e.g. regulated stablecoin-like assets) is affected as soon as a provider revokes or lets a user's credential lapse — a routine compliance action, not an attack. Every pending-approval or already-held CR-CAT balance for that user becomes stuck at that point, with certainty rather than merely probability.

### Recommendation
Add a fallback/escrow mechanism for CR-CAT "pending approval" coins and, ideally, a way for coin holders to reclaim funds (e.g., return to sender, or a time-locked clawback) when no authorized-provider VC is currently available, so that a single provider's revocation cannot permanently freeze funds already in transit or already owned by a wallet.

### Proof of Concept
1. Alice (VC holder authorized by Provider P) receives a CR-CAT payment via an offer; because Bob (the offer counterparty) cannot verify it in time, `TradeManager.check_for_requested_payment_modifications` sends it to the "pending approval" puzzle hash [6](#0-5) .
2. Before Alice calls `crcat_approve_pending`/`claim_pending_approval_balance`, Provider P revokes/lets expire Alice's proof set (`vc.proof_hash` becomes stale/unusable for `self.info.proofs_checker.flags`).
3. Alice calls `claim_pending_approval_balance`; `get_vc_with_provider_in_and_proofs` cannot find a VC satisfying the required proofs and raises, and the call fails with `RuntimeError` [7](#0-6) .
4. Even Alice's previously-confirmed CR-CAT balance (received directly, not via pending-approval) cannot be spent, since `_generate_unsigned_spendbundle` requires a valid VC on every spend [5](#0-4) .
5. There is no code path in this repository allowing Alice (or anyone else) to reclaim these funds absent a valid VC from Provider P — the coins are permanently stuck.

```python
    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover
```
