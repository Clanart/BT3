### Title
Division by zero in `google::protobuf::operator/(const Duration&, const Duration&)` and `operator%=` when a client-controlled `Duration` message has zero value - ([File: src/google/protobuf/util/time_util.cc])

### Summary
`google::protobuf::operator/(const Duration& d1, const Duration& d2)` and `Duration& operator%=(Duration& d1, const Duration& d2)` in `time_util.cc` compute a divisor (`value2`) directly from an attacker-supplied `Duration` protobuf message's `seconds`/`nanos` fields without checking that it is non-zero. If a client parses a `Duration` message whose `seconds == 0` and `nanos == 0` (a perfectly valid, well-formed message on the wire — both fields default to 0) and the application uses it as the divisor, the library performs an unchecked 128-bit integer division by zero.

### Finding Description
`Duration` is a standard well-known-type message that is trivially produced by an ordinary client through the public binary/ProtoJSON parse APIs (e.g. `Duration::ParseFromString`, `google::protobuf::util::JsonStringToMessage`). An empty/default `Duration` (`seconds=0, nanos=0`) is indistinguishable on the wire from any other valid `Duration` — it requires no explicit fields at all, since proto3 scalar defaults are zero.

`TimeUtil`/operator overloads convert both operands into `absl::uint128` via `ToUint128`: [1](#0-0) 

and then divide/mod directly: [2](#0-1) 

Neither `operator/` nor `operator%=` validates `value2 != 0` (i.e., that `d2` is a non-zero Duration) before performing `value1 / value2` / `value1 % value2`. This mirrors the Sherlock finding's pattern exactly: `userDebt * 1e18 / collateralBalanceOf[msg.sender]` divides by an attacker-controllable value that can legitimately be zero, with no `require(... > 0)` guard beforehand. Here, `d2` plays the role of `collateralBalanceOf[msg.sender]` — a value that originates from parsed, untrusted input and is never checked for zero before being used as a divisor.

These operators are declared `PROTOBUF_EXPORT` and are part of the public C++ API surface intended for consuming applications: [3](#0-2) 

### Impact Explanation
Unlike the Solidity original — where division by zero simply causes an EVM revert that can be caught/handled by the caller — in C++, integer division/modulo by zero is undefined behavior and in practice triggers a hardware trap (`SIGFPE`), crashing the entire process. Any consuming application that: (1) accepts two `Duration` messages from a network client (binary or JSON), and (2) computes `d1 / d2` or `d1 % d2` for rate/ratio/ETA calculations, is exposed to an unrecoverable, uncatchable denial-of-service triggered by a single, otherwise perfectly valid empty `Duration` message. This is worse than the referenced Solidity issue because it cannot be guarded against by a `try/catch` at the call site.

### Likelihood Explanation
`Duration` division/modulo (rate limiting, throughput calculation, timeout math) is a common application pattern in services built on protobuf's well-known types. An attacker only needs to supply a message field of type `Duration` with default/zero value (trivial, requires no wire bytes for the length-delimited submessage or an empty submessage), then trigger any code path that divides another `Duration` by it. No malformed wire data, oversized buffers, or schema tampering is required — the only precondition is that application code combines an untrusted `Duration` with these operators, which is exactly the kind of "consuming-application exposure" pattern the original Solidity bug also relied on (an unchecked attacker-influenced denominator).

### Recommendation
Add an explicit zero-check for the divisor before performing the division/modulo in `operator/(const Duration&, const Duration&)` and `operator%=(Duration&, const Duration&)`, e.g.:
```cpp
int64_t operator/(const Duration& d1, const Duration& d2) {
  ABSL_CHECK(!(d2.seconds() == 0 && d2.nanos() == 0)) << "Division by zero Duration";
  ...
}
```
or better, return an `absl::StatusOr<int64_t>` / document loudly in `time_util.h` that callers must validate `d2 != Duration()` (the zero duration) before calling these operators, since library-level `ABSL_CHECK`/`DCHECK` alone would still crash the process (albeit with a clearer diagnostic) rather than allow graceful error handling.

### Proof of Concept
1. Attacker sends (or the application otherwise obtains) a `Duration` protobuf message parsed from client-controlled bytes/JSON with default fields — an empty message payload (`""`) parses successfully to `seconds=0, nanos=0`.
2. Application code, after parsing another (non-zero) `Duration d1` and the attacker's `Duration d2`, executes `int64_t ratio = d1 / d2;` (using `google::protobuf::operator/(const Duration&, const Duration&)`).
3. Inside `time_util.cc`, `ToUint128(d2, &value2, &negative2)` yields `value2 == 0`.
4. `absl::Uint128Low64(value1 / value2)` performs an unsigned 128-bit division by zero, which is undefined behavior and crashes the process (SIGFPE/abort) on affected platforms — confirmed by the arithmetic in `src/google/protobuf/util/time_util.cc` lines 544-554, with no precondition check present anywhere in that call path.

void ToUint128(const Duration& value, absl::uint128* result, bool* negative) {
  if (value.seconds() < 0 || value.nanos() < 0) {
    *negative = true;
    *result = static_cast<uint64_t>(-value.seconds());
    *result = *result * kNanosPerSecond + static_cast<uint32_t>(-value.nanos());
  } else {
    *negative = false;
    *result = static_cast<uint64_t>(value.seconds());
    *result = *result * kNanosPerSecond + static_cast<uint32_t>(value.nanos());
  }
}
