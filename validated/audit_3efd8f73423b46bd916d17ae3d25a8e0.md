# Finding: Unsanitized `target_url` from Commit Status API flows into `shell.openExternal` without scheme validation

### Title
Unvalidated commit-status `target_url` reaches `shell.openExternal`, allowing arbitrary protocol handler invocation - (File: `app/src/lib/ci-checks/ci-checks.ts`)

### Summary
`apiStatusToRefCheck` copies the attacker-influenced `target_url` field from the legacy Commit Status API directly into `IRefCheck.htmlUrl` with no scheme validation. This value is later passed unchanged through `dispatcher.openInBrowser` to Electron's `shell.openExternal`, which itself performs no protocol allow-listing.

### Finding Description
`apiStatusToRefCheck` builds an `IRefCheck` straight from the API response: [1](#0-0) 

Note line 78: `htmlUrl: apiStatus.target_url` — no `new URL()` parsing, no `https:`/`github.com` scheme/host check, unlike, for example, sanitized paths elsewhere in the codebase.

This is populated for every subscribed ref via `CommitStatusStore.refreshSubscription`, which fetches `api.fetchCombinedRefStatus` and maps each status object straight through `apiStatusToRefCheck`: [2](#0-1) 

The same unsanitized mapping is used in the notifications path as well: [3](#0-2) 

The resulting `htmlUrl` is later consumed directly by UI code (e.g. `pull-request-checks-failed.tsx`) and handed to `dispatcher.openInBrowser` with no re-validation: [4](#0-3) 

Following the chain to the shell layer, `openExternal` is exposed on `IAppShell` and wired straight to the main-process `openExternal` proxy with no scheme checking visible in `app-shell.ts`: [5](#0-4) 

No allow-listing of URL schemes (e.g., restricting to `https:`) was found anywhere along this path — not in `apiStatusToRefCheck`, not in the UI consumers, and not in the `openExternal` shell wrapper. The commit status object (including `target_url`) is set via the GitHub Commit Status API by any principal with a token that carries the `repo:status` scope for that repository (commonly used by CI integrations, and in some repo configurations obtainable by lower-privileged automation/bots), making it a plausible untrusted/attacker-influenced value from Desktop's perspective — the client has no way to verify the origin or intent of `target_url`.

### Impact Explanation
Because `target_url` is rendered as `IRefCheck.htmlUrl` and ultimately opened with `shell.openExternal` unchanged, a status object with `target_url` set to `file:///...`, a `javascript:`-like value, or an OS-registered custom protocol handler URI (e.g., Windows `search-ms:`, `ms-officecmd:`, or third-party app URI schemes) would be passed to the OS shell for handling. Depending on installed protocol handlers this can range from opening arbitrary local files/folders to invoking third-party application handlers with attacker-controlled arguments — a known escalation vector for uncontrolled `shell.openExternal` calls in Electron apps.

### Likelihood Explanation
Requires a user to click "View on GitHub" on a check/status entry populated from a commit status object whose `target_url` was set to a malicious URI. Setting `target_url` on a commit status only requires the `repo:status` API scope, which is broadly used by CI bots/integrations and can, in some workflows, be under the control of code/automation an attacker influences (e.g., a malicious CI script running with a status-scoped token). This still requires user interaction (a click) which lowers automatic exploitability but the corruption of the trust assumption ("htmlUrl is always an https://github.com URL") is real and unguarded in code.

### Recommendation
Validate `target_url` (and any other externally-sourced URL destined for `shell.openExternal`) against an allow-list of schemes (`https:` only, ideally restricted to the expected GitHub host) before assigning it to `IRefCheck.htmlUrl`, or perform the validation immediately before invoking `shell.openExternal`/`dispatcher.openInBrowser` so all callers are protected centrally.

### Proof of Concept
1. Mock `api.fetchCombinedRefStatus` (or the underlying `IAPIRefStatusItem`) to return a status object with `target_url: 'file:///etc/passwd'` (or `search-ms:query=...` on Windows).
2. Trigger `CommitStatusStore.refreshSubscription` for that ref; observe the cached `ICombinedRefCheck.checks[].htmlUrl` equals the malicious value unchanged (via `apiStatusToRefCheck`, `app/src/lib/ci-checks/ci-checks.ts:78`).
3. In the Checks/PR-checks-failed UI, click "View on GitHub" for that check, invoking `onViewOnGitHub` → `dispatcher.openInBrowser(url)` (`app/src/ui/notifications/pull-request-checks-failed.tsx:389`) with the unsanitized URL, which flows to `shell.openExternal`.

export function apiStatusToRefCheck(apiStatus: IAPIRefStatusItem): IRefCheck {
  let state: APICheckStatus
  let conclusion: APICheckConclusion | null = null

  if (apiStatus.state === 'success') {
    state = APICheckStatus.Completed
    conclusion = APICheckConclusion.Success
  } else if (apiStatus.state === 'pending') {
    state = APICheckStatus.InProgress
  } else {
    state = APICheckStatus.Completed
    conclusion = APICheckConclusion.Failure
  }

  return {
    id: apiStatus.id,
    name: apiStatus.context,
    description: getCheckRunShortDescription(state, conclusion),
    status: state,
    conclusion,
    appName: '',
    checkSuiteId: null,
    htmlUrl: apiStatus.target_url,
  }
}

    const { repository, pullRequest, dispatcher } = this.props

    // Some checks do not provide htmlURLS like ones for the legacy status
