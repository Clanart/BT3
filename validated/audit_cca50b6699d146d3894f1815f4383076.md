## Analog Found: Unchecked ERC20 return value in the ERC20→CW20 pointer contract

### Title
Unchecked boolean return value from wrapped ERC20 `transfer`/`transferFrom` in CW20 pointer contract can report success on failed asset movement - (File: `example/cosmwasm/cw20/src/contract.rs`)

### Summary
The CW20 pointer contract that wraps a native EVM ERC20 token for use inside CosmWasm builds an `EvmMsg::DelegateCallEvm` targeting the underlying ERC20 contract's `transfer`/`transferFrom` selector, but never inspects the ABI-encoded `bool` return value of that call before reporting success back to the caller. This mirrors the ForceDAO `notifyPools` bug class: a call that can return `false` instead of reverting is treated as a guaranteed success.

### Finding Description
The pointer's `transfer` and `transfer_from` handlers build the ERC20 payload via `EvmQuerier::erc20_transfer_payload` / `erc20_transfer_from_payload`, wrap it in `EvmMsg::DelegateCallEvm { to: erc_addr, data: payload.encoded_payload }`, and simply `add_message` it to the response — there is no `Reply` handling or decoding of the ERC20 call's return data to confirm the `bool` result of `transfer`/`transferFrom` was `true`. [1](#0-0) [2](#0-1) 

`DelegateCallEvm` is only decoded and turned into an internal EVM message by the encoder; the wasm module only fails the Cosmos message if the underlying EVM call itself reverts — it has no visibility into (and does not decode) the callee's returned `bool` payload. [3](#0-2) 

Contrast this with the Solidity-side pointer contracts and the native-token ERC20 wrapper in the same codebase, which explicitly check the boolean/success result before proceeding: [4](#0-3) [5](#0-4) 

Both of those examples check `success`/require a boolean result. The cw20-pointer's `transfer`/`transfer_from`, by contrast, only produces attributes (`from`, `to`, `amount`) and an EVM sub-message, with no confirmation step — if the delegatecall does not revert but the ERC20 logic returns `false` (e.g., because of insufficient balance/allowance implemented in a "return false" rather than "revert" style, which is exactly the non-standard-ERC20 pattern the original report warns about), the wasm message and its attributes will still indicate success.

### Impact Explanation
Any CosmWasm caller or contract composing with the ERC20→CW20 pointer (e.g., DEXes, marketplaces, or other contracts that call `transfer`/`transfer_from` on the pointer and trust its success/attributes to release a counter-asset) can be misled into believing tokens moved when they did not, if the wrapped token exhibits the "return false" failure pattern. This is a reachable, unprivileged, single-transaction path (any wasm executor calling the pointer) that can lead to unauthorized/asset-mismatched transfers and fund loss for any protocol relying on this pointer's reported success — matching the "unauthorized transfer via precompile or pointer" impact category.

### Likelihood Explanation
Likelihood depends on whether the wrapped ERC20 token implements failure via `return false` instead of `revert`. Not all ERC20 tokens do this, but it is a well-known non-standard pattern (the same pattern the original ForceDAO report calls out with BAT-style tokens), and the pointer mechanism is explicitly designed to wrap *arbitrary* externally-deployed ERC20 tokens, so the pointer contract cannot assume well-behaved revert semantics from the wrapped token. Exploitation requires no special privilege — only calling the pointer contract's wasm `transfer`/`transfer_from` message against a token that uses this pattern.

### Recommendation
- Decode the ABI-encoded `bool` return value from the `DelegateCallEvm` reply (using a `Reply` submessage with `ReplyOn::Always`/`Success`, or an equivalent synchronous check) and fail the CosmWasm execution if the returned value is `false`.
- Alternatively, adopt a "safe transfer" pattern analogous to `TransferHelper.safeTransfer`/`safeTransferFrom` already present elsewhere in the repo, which requires `success && (data.length == 0 || abi.decode(data, (bool)))`.
- Integrate static-analysis/Slither-style checks against Rust/CosmWasm and Solidity pointer contracts to catch unchecked return values from token transfer calls in CI.

### Proof of Concept
1. Deploy (or use) an ERC20 token that returns `false` from `transferFrom` when the caller lacks approval/balance instead of reverting.
2. Create an ERC20→CW20 pointer for that token (as exercised by the existing pointer test suite pattern, e.g. `contracts/test/ERC20toCW20PointerTest.js`). [6](#0-5) 
3. As an unapproved/underfunded account, invoke the pointer's wasm `transfer_from` message.
4. Because the underlying token returns `false` rather than reverting, the `DelegateCallEvm` sub-message does not revert; the wasm contract has no code path to detect the `false` return, so the transaction succeeds and emits success attributes despite no balance change actually occurring on the ERC20 side.

**Note on confidence:** I could not fully trace how `MsgInternalEVMDelegateCall` is executed on the EVM keeper side (`x/evm/keeper/evm.go`) to definitively confirm that no downstream code re-validates the ERC20 return value before considering the CosmWasm message a success; this final link should be verified by a background agent with full repository access before remediation.

    _env: Env,
    info: MessageInfo,
    recipient: String,

}

        .add_attribute("to", recipient)

func EncodeDelegateCallEVM(rawMsg json.RawMessage, sender sdk.AccAddress, info wasmvmtypes.MessageInfo, codeInfo wasmtypes.CodeInfo) ([]sdk.Msg, error) {
	encodedCallEVM := bindings.DelegateCallEVM{}
	if err := json.Unmarshal(rawMsg, &encodedCallEVM); err != nil {
		return []sdk.Msg{}, err
	}
	decodedData, err := base64.StdEncoding.DecodeString(encodedCallEVM.Data)
	if err != nil {
		return []sdk.Msg{}, err
	}
	s := sender
	if origSender, err := sdk.AccAddressFromBech32(info.Sender); err == nil {
		s = origSender
	}
	internalCallEVMMsg := types.MsgInternalEVMDelegateCall{
		Sender:       s.String(),
		To:           encodedCallEVM.To,
		CodeHash:     codeInfo.CodeHash,
		Data:         decodedData,
		FromContract: sender.String(),
	}
	return []sdk.Msg{&internalCallEVMMsg}, nil
}
