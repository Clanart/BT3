### Title
Non-atomic ERC20 auto-conversion in IBC `OnRecvPacket` allows fund duplication via error-acknowledgement after already-committed state changes - ([File: x/erc20/keeper/ibc_callbacks.go], [File: x/erc20/keeper/msg_server.go])

### Summary
The `x/erc20` IBC middleware auto-converts an incoming ICS-20 coin into its native ERC20 representation only *after* the underlying `ibc-go` transfer application has already committed the coin transfer to the receiver (or unescrowed a returning native-ERC20-backed coin). If the subsequent ERC20 conversion step fails, the code returns an `ErrorAcknowledgement`, but since this failure is expressed only as an `Acknowledgement` value (not a Go `error`), the whole `MsgRecvPacket` transaction still succeeds and **all prior state mutations are committed**. The counterparty chain, upon seeing the error acknowledgement, refunds the original sender — producing a duplicate/orphaned balance on the destination chain.

### Finding Description
`IBCMiddleware.OnRecvPacket` first executes the standard ICS-20 `OnRecvPacket` directly against `ctx` (no cache/rollback boundary): [3](#0-2) 

If that succeeds (`ack.Success()==true`, meaning bank state has already been mutated — coins minted or unescrowed to the receiver), it proceeds to `Keeper.OnRecvPacket`, which for a returning native-ERC20-backed coin (`pair.IsNativeERC20()`) calls `ConvertCoinNativeERC20`: [4](#0-3) 

`ConvertCoinNativeERC20` first escrows the just-received bank coins away from the receiver into the erc20 module account (`SendCoinsFromAccountToModule`), and only afterward attempts the ERC20-side `transfer` call: [5](#0-4) 

If that EVM `transfer` call fails (contract paused, blacklist, revert, `ErrBalanceInvariance`, etc.), the function returns an error *without reversing* the just-executed `SendCoinsFromAccountToModule` step — because there is no `CacheContext` wrapping this sequence. The caller then converts this error into an `ErrorAcknowledgement` return value rather than propagating a Go `error`: [6](#0-5) 

Because `OnRecvPacket`'s signature returns `exported.Acknowledgement` and not `error`, returning an `ErrorAcknowledgement` here does **not** cause the enclosing `MsgRecvPacket` message handler to fail/revert — the transaction commits successfully with all intermediate state changes intact (the escrow step already ran). The error acknowledgement is then written and relayed to the source chain, which — per standard ICS-20 semantics — treats this as a failed transfer and refunds/unescrows the original sender there.

Net result: the source chain restores the sender's balance (refund) while the destination chain's `x/erc20` module account is left holding the equivalent bank coins that were escrowed in step 2 but never burned (burning only happens on the success path, after the ERC20 transfer succeeds). Documented intended behavior contradicts this ("If conversion fails, then the user will receive the bank token instead" [7](#0-6) ), confirming this is an implementation bug, not intended design.

An unprivileged attacker can reliably trigger the malicious-ERC20 branch of this bug because ERC20 registration is permissionless by default (`PermissionlessRegistration: true`) [1](#0-0) , and `MsgServer.RegisterERC20` allows any signer to self-register a contract when the parameter is enabled [8](#0-7) .

### Impact Explanation
This causes irreversible duplication of spendable value across chains, matching "Critical unauthorized minting, burning, duplication, resurrection, or irreversible accounting corruption of spendable user value across... IBC escrows... or precompile-mediated assets" and "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds... escrowed assets... or token-pair-backed balances." The sender's balance is restored on the source chain via the normal error-ack refund path, while an equal amount of bank coin becomes permanently stranded (with no burn or reconciliation) inside the `x/erc20` module account on the destination chain — value that should have either gone to the receiver or never existed at all.

### Likelihood Explanation
High. An attacker who controls (or self-deploys and permissionlessly registers) an ERC20 contract can:
1. Convert native coins to that ERC20, IBC-transfer the resulting escrowed coin out to another chain.
2. Send it back via IBC to trigger the `pair.IsNativeERC20()` return path in `OnRecvPacket`.
3. At the moment of receipt, make the ERC20 contract's `transfer` revert (pause/blacklist toggle they control), causing `ConvertCoinNativeERC20` to fail after already escrowing the bank coin.

No governance action or privileged role is required; only the attacker's own permissionlessly-registered contract and ordinary IBC message flows are used.

### Recommendation
Wrap the erc20 conversion step of `OnRecvPacket` (and the escrow+transfer sequence inside `ConvertCoinNativeERC20`) in a `ctx.CacheContext()` boundary that is only committed if the entire conversion succeeds; otherwise discard all intermediate writes so the receiver keeps the plain bank coin (matching the documented fallback behavior) and no error acknowledgement is returned when the underlying ICS-20 transfer already succeeded.

### Proof of Concept
1. With `PermissionlessRegistration=true`, attacker deploys a pausable/blacklistable ERC20 contract and calls `MsgRegisterERC20` to register it as a native-ERC20 token pair.
2. Attacker calls `MsgConvertCoin` to mint the corresponding bank coin, then sends it via `MsgTransfer` (ICS-20) to a counterparty chain B, escrowing the coin on chain A.
3. Attacker sends the coin back from chain B to chain A via IBC. On `OnRecvPacket`, the base transfer app unescrows the coin to the receiver (committed to `ctx`) and returns success.
4. `erc20.Keeper.OnRecvPacket` detects `pair.IsNativeERC20()`, calls `ConvertCoinNativeERC20`, which escrows the bank coin from receiver into the erc20 module account, then calls the ERC20 contract's `transfer`.
5. Attacker has paused/blacklisted the receiver on their own ERC20 contract, so the `transfer` call reverts; `ConvertCoinNativeERC20` returns an error.
6. `OnRecvPacket` returns `channeltypes.NewErrorAcknowledgement(err)`; the `MsgRecvPacket` transaction on chain A nevertheless commits successfully (escrow to module account persists).
7. Chain B, upon seeing the error acknowledgement, refunds the attacker's original escrowed coin.
8. Attacker now holds a refund on chain B equal to the original amount, while chain A's `x/erc20` module account permanently holds the duplicate escrowed bank coin — net duplication of spendable value.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	channelVersion string,
	packet channeltypes.Packet,
	relayer sdk.AccAddress,
) exported.Acknowledgement {
	ack := im.Module.OnRecvPacket(ctx, channelVersion, packet, relayer)

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}
