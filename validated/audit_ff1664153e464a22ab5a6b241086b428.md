### Title
`ReceivedOutput::read` accepts unverified output/offset pairs, bypassing the script-to-offset binding enforced by `Scanner::scan_transaction` — ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner` maintains a `scripts: HashMap<ScriptBuf, Scalar>` map so that every `ReceivedOutput` it produces has a cryptographically bound pair: the output's `script_pubkey` is exactly `p2tr(key + offset*G)`, meaning the stored `offset` is the scalar needed to spend it. That binding is the safety check — analogous to the `VAULT_ACCOUNT_MIN_TIME` guard. However, `ReceivedOutput::read` deserializes `offset`, `output`, and `outpoint` as three independent fields from untrusted bytes and never re-checks that `output.script_pubkey` corresponds to `key + offset*G`. This alternate entry path reaches the same privileged object while skipping the invariant, exactly the "check on `exitVault` missing on `rollVaultPosition`" pattern.

### Finding Description
In `scan_transaction`, an output is only returned if `self.scripts.get(&output.script_pubkey)` succeeds, so the `offset` recorded is guaranteed to be the spending offset for that script (networks/bitcoin/src/wallet/mod.rs:199-214). `register_offset` similarly only inserts scripts derived as `p2tr(self.key + offset*G)` (mod.rs:180-196).

`ReceivedOutput::read` (mod.rs:122-134) reads:
- `offset` via `Secp256k1::read_F` — any scalar,
- `output` via `TxOut::consensus_decode` — any script_pubkey and value,
- `outpoint` via `OutPoint::consensus_decode` — any txid/vout,

and constructs `ReceivedOutput { offset, output, outpoint }` with no consistency check. There is no way within the type to detect that `output.script_pubkey != p2tr(key + offset*G)` or that the outpoint refers to a real UTXO. Downstream spend code (`wallet/send.rs`, `sign` paths using `output.offset()` to re-key per input) will produce signatures for a key that does not control the output, so the "received" funds are unspendable — or worse, an offset can be supplied that points at a *different* registered script than the decoded output's, causing the wallet to attribute/spend the wrong UTXO.

### Impact Explanation
An attacker who can feed bytes to `ReceivedOutput::read` (it is explicitly listed as an untrusted-bytes entry point) can fabricate outputs the wallet reports as received but which are not spendable by the threshold key: the offset does not derive the output's script, and the outpoint may not exist. This yields "funds reported received that are not spendable," an accepted impact class, and can also poison fee/change/dust math in `send.rs` which trusts `output.value` and `offset`.

### Likelihood Explanation
`ReceivedOutput` is serialized (`write`/`serialize`) precisely so it can be transported and later re-read; any hop where those bytes are attacker-influenced (message queue, peer processor, stored data) reaches this path. No key material or validator collusion is required — only control of serialized bytes.

### Recommendation
Either verify in `ReceivedOutput::read` (requires the scanner key, so make it a method `Scanner::read_output` that re-derives `p2tr(key + offset*G)` and compares to `output.script_pubkey`, returning an error on mismatch), or store the script binding implicitly by re-deriving the offset lookup from `output.script_pubkey` at deserialization time rather than trusting the encoded offset.

### Proof of Concept
```rust
// Given a Scanner with key K, craft malicious bytes:
let mut buf = vec![];
// offset = arbitrary scalar, e.g. 1
buf.extend(Scalar::ONE.to_bytes());
// output = TxOut paying to an unrelated P2TR script with high value
buf.extend(serialize(&TxOut { value: Amount::from_sat(1_000_000), script_pubkey: victim_script }));
// outpoint = fabricated
buf.extend(serialize(&OutPoint::new(Txid::all_zeros(), 0)));

let ro = ReceivedOutput::read(&mut &buf[..]).unwrap();
// ro.value() == 1_000_000 reported as received
// ro.offset() == 1, but p2tr(K + 1*G) != victim_script → output is unspendable
// Scanner::scan_transaction would never have produced this pair.
```
