### Title
Quadratic CPU exhaustion in `ThresholdKeys::read` via large `t`/`n` triggers O(t²) Lagrange interpolation in `ThresholdKeys::new` - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` accepts attacker-controlled `t` and `n` (u16, up to 65535) and reads `n` verification shares before calling `ThresholdKeys::new`. `ThresholdKeys::new` computes `group_key` by evaluating `interpolation_factor` for every participant `1..=t` against the `1..=t` signing set, where each `interpolation_factor` call for `Interpolation::Lagrange` iterates over all `t` included participants — producing O(t²) field multiplications and inversions inside a single deserialization call. A ~2 MB input with `t = n = 65535` forces ~4.3 billion field operations, hanging the calling thread. This is the analog of CVE-2002-0935: remote, unauthenticated resource exhaustion via a crafted request/message.

### Finding Description
The deserialization path:

- `ThresholdKeys::read` reads `t`, `n`, `i` from the input, then reads `n` group elements via `C::read_G` (decompression — itself expensive), then calls `ThresholdKeys::new` [1](#0-0) 
- `ThresholdKeys::new` computes `group_key = Σ_{i=1..=t} verification_shares[i] * interpolation_factor(i, t_set)` [2](#0-1) 
- `Interpolation::Lagrange::interpolation_factor` iterates over all `included` participants per call (O(t)), including a field inversion [3](#0-2) 

So `ThresholdKeys::new` alone performs O(t²) field work. Additionally, `ThresholdKeys::view` calls `interpolation_factor` for each included participant (again O(|included|²)) [4](#0-3) , and PedPoP's `calculate_share` performs an O(n·t) `multiexp` per participant over `stripes`, compounding the cost when commitments are attacker-influenced [5](#0-4) .

### Impact Explanation
Any component that calls `ThresholdKeys::read` (or `ThresholdKeys::new` / `view`) on bytes influenced by an untrusted party can be forced into a single-threaded computation of ~4.3 × 10⁹ field multiplications/inversions per message. Repeated messages exhaust the worker pool — the same "working threads hang" pattern as the reference advisory. No secret leakage is required; the impact is a full denial of service of the signing/key-management process.

### Likelihood Explanation
Reachable by an unprivileged party: `ThresholdKeys::read` is a listed untrusted-input sink and `n`/`t` are read directly from the byte stream with only the `t <= n <= 65535` semantic check applied afterwards [1](#0-0) . The attacker must supply `n` valid point encodings (~2 MB for n=65535), which is cheap relative to the induced O(t²) work — a strong amplification asymmetry. The checks in `ThresholdParams::new` (t ≤ n, i ≤ n) do not bound the cost [6](#0-5) .

### Recommendation
Enforce a protocol-level maximum on `n`/`t` (e.g., the `MAX_KEY_SHARES_PER_SET` bound already used elsewhere in Serai) inside `ThresholdKeys::new` and at the top of `ThresholdKeys::read`, before any allocation or interpolation work. Optionally pre-compute Lagrange denominators/numerators incrementally to make group-key derivation O(t) inversions instead of O(t²) operations (prefix/suffix products), removing the quadratic blowup even for legitimately large sets.

### Proof of Concept
```rust
// Pseudocode against crypto/dkg ThresholdKeys::<C>::read
let n: u16 = u16::MAX;
let mut bytes = vec![];
bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
bytes.extend(C::ID);
bytes.extend(n.to_le_bytes());            // t
bytes.extend(n.to_le_bytes());            // n
bytes.extend(1u16.to_le_bytes());         // i = Participant(1)
bytes.push(1);                            // Interpolation::Lagrange
bytes.extend(C::F::ONE.to_repr().as_ref()); // secret_share
for _ in 0 .. n {
  bytes.extend(C::generator().to_bytes().as_ref()); // valid verification shares
}
// Hangs: ThresholdKeys::new runs ~n^2 (~4.3e9) scalar muls + n inversions
let _ = ThresholdKeys::<C>::read::<&[u8]>(&mut bytes.as_ref());
```
The same cost profile is reachable with fewer bytes but identical asymptotics for any `t = n` well above a few thousand.
