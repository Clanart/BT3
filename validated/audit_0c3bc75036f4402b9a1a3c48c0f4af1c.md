## Analysis

The LayerZero bug's core broken invariant is: **a privileged endpoint only checks "which chain did this come from" and never checks "which module/UA on that chain sent it,"** so any unprivileged sender co-located on a trusted source chain can reach a function meant to be callable only by one specific trusted counterpart module.

The exact same broken invariant exists in Hyperbridge's built-in relayer-fee withdrawal module.

### Title
Coprocessor withdrawal channel authenticates only by chain id, not by module identity, allowing any module on the Coprocessor chain to drain relayer fees - (File: `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
`HyperbridgeWithdrawalModule::on_accept` is the `IsmpModule` callback wired to the well-known module id `HYPERBRIDGE_MODULE_ID` (`b"HYPR-FEE"`) via `IsmpHostRouter::module_for_id`. It is meant to be callable only by the trusted governance/treasury logic on the Hyperbridge coprocessor chain (Nexus). Its only authentication check is on `request.source` (the *chain*), never on `request.from` (the *module* on that chain that dispatched the request). [1](#0-0) 

### Finding Description
`on_accept` performs exactly one check before executing a privileged fund transfer:

```rust
let source = request.source;
if Some(source) != T::Coprocessor::get() {
    Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
}
``` [2](#0-1) 

`request.source` is the `StateMachine` (chain id) of the sender, not the sending module/pallet/contract on that chain. There is no check on `request.from`, which is the field the protocol otherwise uses everywhere else to authenticate the specific sending application (e.g. `hyper-fungible-token`'s `on_accept` looks up `ContractToAsset::get(source, &from)`, keying authorization on the `(chain, module)` pair, not chain alone). [3](#0-2) 

The router dispatches into `HyperbridgeWithdrawalModule` purely based on the `to` field of the incoming `PostRequest` matching `HYPERBRIDGE_MODULE_ID`:

```rust
fn module_for_id(&self, id: Vec<u8>) -> Result<Box<dyn IsmpModule>, anyhow::Error> {
    if id.as_slice() == HYPERBRIDGE_MODULE_ID {
        return Ok(Box::new(HyperbridgeWithdrawalModule::<T>::default()));
    }
    self.inner.module_for_id(id)
}
``` [4](#0-3) 

This mirrors the LayerZero report precisely: the relayer/ISMP core enforces `dest_chain`/`source_chain`/proof validity generically (`modules/ismp/core/src/handlers/request.rs`), but does **not** isolate message channels per `(chain_id, from-module)` pair — that isolation is left entirely to the individual `IsmpModule::on_accept` implementation. `HyperbridgeWithdrawalModule` fails to do this, unlike `hyper-fungible-token`, which does. As a result, **any account/pallet/contract capable of dispatching an ISMP `PostRequest` from the Coprocessor state machine** — not just the intended treasury/governance origin — can set:
- `to = HYPERBRIDGE_MODULE_ID`
- `body = Message::WithdrawRelayerFees(WithdrawalRequest { account: <attacker>, amount: <arbitrary> })`

and the module will execute the transfer unconditionally:

```rust
Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
    T::Currency::transfer(
        &RELAYER_FEE_ACCOUNT.into_account_truncating(),
        &account,
        amount,
        Preservation::Expendable,
    )?;
    ...
}
``` [5](#0-4) 

### Impact Explanation
Successful exploitation drains `RELAYER_FEE_ACCOUNT` — the pooled protocol treasury account funding relayer-fee withdrawals — to an attacker-chosen account for an attacker-chosen amount, on every destination chain that configures the Coprocessor chain as trusted (`T::Coprocessor::get()`). This is a direct, unauthorized fund transfer / theft of funds from the protocol's relayer-fee escrow, matching the bounty's "stealing or loss of funds" and "unauthorized transaction or execution" categories. Because the check only binds `source` (chain-level), the vulnerability is exploitable by any module on the Coprocessor chain without needing a malicious relayer, prover, or admin — it only requires the ability to originate an ISMP dispatch from that chain, which the protocol's own architecture (multiple pallets/contracts share a single chain identity) makes plausible.

### Likelihood Explanation
The likelihood hinges entirely on whether an unprivileged or lower-trust module/account on the Coprocessor (Nexus) chain can trigger `IsmpDispatcher::dispatch_request` with attacker-controlled `to`/`body`/`from` fields. I was not able to fully confirm within the available exploration whether Nexus exposes such a general-purpose, permissionless dispatch surface (e.g., a generic "send arbitrary ISMP message" extrinsic reachable by ordinary signed accounts, similar to the `dispatch_to_evm` example shown in the docs for other runtimes). This is the one remaining uncertainty. Regardless of that specific reachability question, the code-level fact stands on its own: the authorization check in `HyperbridgeWithdrawalModule::on_accept` is chain-scoped only, is inconsistent with the module-identity check used by sibling modules like `hyper-fungible-token`, and is a genuine, provable violation of the pivot requirement that "Cross-chain admin or host-management effects must not be reachable through ... unauthenticated message flow."

### Recommendation
Add a `from`-field allowlist check to `HyperbridgeWithdrawalModule::on_accept`, mirroring the pattern already used by `hyper-fungible-token` (`ContractToAsset::get(source, &from)`), e.g. requiring `request.from == TrustedTreasuryModuleId` in addition to `request.source == T::Coprocessor::get()`. Treat the missing `from` check as equivalent to LayerZero's UA-capability gap: scope every privileged incoming-message channel on both chain id and module id, not chain id alone.

### Proof of Concept
1. Attacker controls (or is) any pallet/contract on the chain configured as `T::Coprocessor` for a given destination host (e.g. Gargantua/EVM host chains trusting Nexus).
2. Attacker dispatches an ISMP `PostRequest` (via `IsmpDispatcher::dispatch_request`, `DispatchRequest::Post`) with:
   - `dest` = the target host chain
   - `to` = `b"HYPR-FEE"` (`HYPERBRIDGE_MODULE_ID`)
   - `from` = attacker's own (untrusted) module id — never checked
   - `body` = SCALE-encoded `Message::WithdrawRelayerFees(WithdrawalRequest { account: <attacker_account>, amount: <large_amount> })`
3. A relayer delivers this request normally through `modules/ismp/core/src/handlers/request.rs::handle`, which validates the consensus/state proof and `source_chain`/`dest_chain` per the generic ISMP rules, then routes to `module_for_id(b"HYPR-FEE")` → `HyperbridgeWithdrawalModule::on_accept`.
4. `on_accept` checks only `request.source == T::Coprocessor::get()` (true, since it genuinely came from the Coprocessor chain) and never inspects `request.from`, so it proceeds to execute `T::Currency::transfer(&RELAYER_FEE_ACCOUNT, &attacker_account, amount, ...)`, draining the relayer fee pool to the attacker.

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}
