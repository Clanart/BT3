### Title
Webhook HMAC verification does not bind the signature to the claimed shop domain, allowing cross-shop forged/replayed webhook requests - (File: `lib/shopify_app/controller_concerns/payload_verification.rb`)

### Summary
The external report describes a privileged-role rug-pull enabled by a shallow trust check: `swapYieldSource` only verifies that a contract *implements* an expected interface, not that it comes from a trusted registry, letting a privileged actor redirect funds to an attacker-controlled contract. The shopify_app analog is `ShopifyApp::PayloadVerification#hmac_valid?`, which only verifies that an incoming webhook's raw body was signed with the app's (shop-agnostic) shared secret — it never binds that signature to the shop identity asserted by the `X-Shopify-Shop-Domain` header. Because the secret is shared across every shop that installs the app, any merchant who legitimately installs the app can obtain a validly-signed `(body, HMAC)` pair and replay it to the app's public webhook endpoint while claiming a different shop's domain, causing the app to execute shop-scoped, destructive logic against a victim shop it does not control. This can be triggered anonymously over HTTP.

### Finding Description
`PayloadVerification#hmac_valid?` computes `OpenSSL::HMAC.digest` over `request.raw_post` using `ShopifyApp.configuration.secret`/`old_secret` and only checks that value against the `X-Shopify-Hmac-Sha256` header: [1](#0-0) 

`WebhookVerification#verify_request` gates the whole endpoint solely on this body-signature check: [2](#0-1) 

The shop identity used everywhere downstream (`shop_domain` in the concern, or `shop:`/`shop_domain:` in generated jobs) is taken from the `X-Shopify-Shop-Domain` header / the `shop` value from `ShopifyAPI::Webhooks::WebhookHandler.handle`, which is **not part of the HMAC-signed payload** and is never cross-checked against it: [3](#0-2) 

Generated job templates then trust this unverified `shop_domain` value to look up a `Shop` record and perform privileged, shop-scoped actions: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the HMAC secret is the app's single shared client secret (identical for all installations, all shops), the signature only proves "this body was signed by someone possessing the app secret's signing capability via a genuine Shopify delivery," not "this body/domain pair originated from shop X." Any actor who installs the app on their own (attacker-controlled) shop legitimately receives correctly-signed webhook deliveries. They can then send/replay that same signed body to the webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (or the `shop` field the webhook framework surfaces) with a victim shop's domain. `verify_request` passes because it only checks the body signature, and the generated job code (`Shop.find_by(shopify_domain: shop_domain)`) then acts against the *victim's* `Shop` record — e.g., `AppUninstalledJob#perform` calls `shop.destroy`, deleting the victim's stored access token/session record entirely from an anonymous, unauthenticated HTTP request.

### Impact Explanation
This allows an unauthenticated/unrelated-merchant actor to forge shop attribution on an otherwise validly-signed webhook and trigger shop-scoped side effects for a shop they don't own:
- Deletion of a victim `Shop` record and its offline access token (`AppUninstalledJob`), effectively uninstalling/breaking the app for that merchant.
- Execution of arbitrary generated webhook job logic (`shop.with_shopify_session { ... }`) under the victim's session/context, since `shop_domain` is trusted to resolve the acting `Shop`.
- Cross-shop data confusion for any custom webhook processing that keys off the header-derived `shop_domain`.

This maps to the report's core lesson: a check that only validates "this came from a holder of the shared secret" (interface conformance) is insufficient when the actual security requirement is "this specific claim (shop identity / yield source) is trustworthy," and the consequence is destructive cross-tenant action, not merely informational disclosure.

### Likelihood Explanation
Likelihood is moderate-to-high in any app using this gem's standard generated webhook jobs (`add_webhook`, `add_app_uninstalled_job`, `add_privacy_jobs`, `add_declarative_webhook`) as-is, since:
- Any user can become a legitimate merchant of a public Shopify app (install for free on a development/trial store) and thus obtain genuine, validly-signed webhook deliveries with a body they may partly control (webhook body content for many topics reflects data the merchant themselves control, e.g. product/order fields).
- No IP allowlisting or mTLS to Shopify's webhook senders is enforced in this code path — the endpoint accepts any POST with a valid HMAC over the body.
- The vulnerable pattern (`Shop.find_by(shopify_domain: shop_domain)` sourced from the unverified header/field) is the officially generated, documented pattern in `docs/shopify_app/webhooks.md`, so it is broadly deployed as-is by consumers of this gem.

### Recommendation
- Bind the shop identity into the trust decision: reject webhooks where the header-derived `shop_domain` does not correspond to a `Shop` record whose stored offline token/session was actually established via OAuth/token-exchange for that domain, and additionally verify (where the webhook body includes shop-identifying fields) that body and header agree.
- Consider validating that the `X-Shopify-Shop-Domain` header is itself included in the HMAC-signed material (or otherwise cryptographically bound) rather than trusted independently.
- At minimum, document/require consuming apps to treat `shop_domain` as merely a lookup key gated by additional shop-specific integrity checks (e.g., idempotency/webhook id tracking, replay protection with a nonce/timestamp window) rather than sufficient authorization for destructive per-shop operations like `shop.destroy`.

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` and installs the target app, receiving a genuinely Shopify-signed webhook delivery: `POST /webhooks/app_uninstalled` with header `X-Shopify-Hmac-Sha256: <valid-for-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures/replays this exact request to the app's public webhook endpoint but rewrites `X-Shopify-Shop-Domain` (or the equivalent `shop` field consumed by `ShopifyAPI::Webhooks::WebhookHandler.handle`) to `victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which succeeds because the body and secret are unchanged — [2](#0-1) .
4. `AppUninstalledJob#perform(topic:, shop_domain: "victim-shop.myshopify.com", webhook:)` looks up and destroys the victim's `Shop` record — [7](#0-6) , causing loss of the victim merchant's stored access token/session with no interaction from the victim and no privileged role required by the attacker.

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```text
class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
end
```
