### Title
Panic (indexing unregistered participant) in `Encryption::encrypt` / `Decryption::decrypt_with_proof` reachable via crafted PedPoP message flow — (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PHP CVE is a NULL-pointer dereference triggered by attacker-crafted serialized data — i.e., a remotely triggerable crash (DoS) via a lookup that assumes a structure exists. The Serai analog is an indexing/assert panic in the PedPoP encryption layer: `HashMap` lookups on `enc_keys` assume every referenced `Participant` has previously registered an encryption key, and panic otherwise. `Participant` itself is validated only as a nonzero `u16` (`Participant::new`), not against `enc_keys`.

### Finding Description
- `Decryption::decrypt_with_proof` computes the ECDH recipients list as `&[self.enc_keys[&decryptor], *proof.key]` (crypto/dkg/pedpop/src/encryption.rs:388). If `decryptor` is a participant index that never registered an `EncryptionKeyMessage`, the `HashMap` index operator panics.
- `Encryption::encrypt` computes `self.decryption.enc_keys[&participant]` (encryption.rs:466), panicking on any `participant` lacking a registered key.
- `Decryption::register` asserts `!self.enc_keys.contains_key(&participant)` (encryption.rs:356-359), so a duplicated registration also panics — though the code comments explicitly shift deduplication responsibility to the caller, so that path is weaker.
- Untrusted bytes reach these functions through `EncryptionKeyMessage::read` / `EncryptedMessage::read` / `EncryptionKeyProof::read` (encryption.rs:57-59, 171-177, 267-269), none of which can fail-fast for this condition — the panic happens at use time, driven by which `Participant` index the peer's message causes to be looked up.

### Impact Explanation
An unprivileged protocol peer can crash a node's DKG/share-processing task by causing a lookup of a `Participant` absent from `enc_keys` — e.g., triggering `encrypt`/`decrypt_with_proof` for an index that registered no key (indices up to `u16::MAX` are accepted by `Participant::new`). A panic aborts the current signing/DKG attempt and, depending on the runtime's panic handling, the process — a remote denial of service matching the CVE's availability impact.

### Likelihood Explanation
Reachable by any DKG participant with public inputs: they control the messages they send and the participant indices embedded in them. It requires no collusion, leaked keys, or malformed curve encodings — only a message sequence that references a participant index with no registered encryption key. Likelihood is bounded by the caller needing to route such a message into `encrypt`/`decrypt_with_proof`, but the library itself performs no guard.

### Recommendation
Replace indexing/assertions with fallible lookups: use `enc_keys.get(&participant).ok_or(...)`/`get(&decryptor)` returning a `DecryptionError`/`FrostError`, and check `Participant` against the protocol's `n`/`params` before use rather than only `Participant::new`'s nonzero check.

### Proof of Concept
Conceptual: complete a PedPoP round where participant `i` registers keys for indices `1..=n`. Have a faulty peer cause `Encryption::encrypt` or `decrypt_with_proof` to be invoked with `participant`/`decryptor = Participant(n+1)` (or any unregistered index). `self.decryption.enc_keys[&Participant(n+1)]` at encryption.rs:466 / `self.enc_keys[&decryptor]` at encryption.rs:388 panics on the empty slot, crashing the host instead of returning an error.

Caveat: I could not fully trace the call sites that feed `decryptor`/`participant` from wire messages in the remaining iterations, so the exact triggering transaction path is inferred from the read APIs and the indexing sites themselves.
