### Title
In-instructions credit the executor's entire coin balance as swap output instead of the actual amount returned, letting a balance donation inflate `sri_amount`/`coin_balance` and cause out-transfer of funds never acquired - (File: substrate/in-instructions/pallet/src/lib.rs)

### Summary
The Loop report's core flaw is crediting `address(this).balance` (ambient balance, including attacker-donated ETH) as the swap's output, letting an attacker bundle a donation with a claim to mint excess lpETH and break the 1:1 conversion invariant. Serai's `in-instructions` pallet repeats this pattern: after calling `Dex::swap_exact_tokens_for_tokens` (which returns the exact `amount_out`), the return value is discarded and the code instead reads the *entire* balance of the shared `IN_INSTRUCTION_EXECUTOR` / `POL_ACCOUNT` accounts via `Coins::<T>::balance(...)`. Any residual or deliberately transferred balance on those shared accounts is then credited to the next instruction's output.

### Finding Description
Three sites read the full account balance as "how much we got":

- `DexCall::Swap` handling in `Pallet::<T>::execute`: after the swap, `coin_balance = Coins::<T>::balance(IN_INSTRUCTION_EXECUTOR.into(), out_balance.coin)` is used as the amount burned into an `OutInstructionWithBalance` sent back on the external chain (`substrate/in-instructions/pallet/src/lib.rs`, lines 200-215). The actual `amount_out` returned by `Dex::<T>::swap_exact_tokens_for_tokens` (line 190-196) is ignored.
- `DexCall::SwapAndAddLiquidity`: `sri_amount = Coins::<T>::balance(IN_INSTRUCTION_EXECUTOR.into(), Coin::Serai).0` (line 128) is passed as the SRI side of `add_liquidity`, and all residual executor balances are swept to the user `address` (lines 144-159).
- `Emissions::<T>::swap_to_staked_sri`: `sri_amount = Coins::<T>::balance(POL_ACCOUNT.into(), Coin::Serai).0` (`substrate/emissions/pallet/src/lib.rs`, line 397) — the whole POL account balance, not the swap delta — is added as liquidity, and the minted/staked SRI amount derives from spot-price math on the full incoming `balance`.

Because `IN_INSTRUCTION_EXECUTOR` and `POL_ACCOUNT` are fixed shared accounts, any SRI/coin balance left on them — e.g., leftover from a prior `SwapAndAddLiquidity` that swept only non-zero balances, a rounding remainder from `add_liquidity` (minimums hardcoded to `1`), or a direct `Coins::transfer` to the executor account by any holder — is attributed to the *next* instruction processed. In the `DexCall::Swap` path this directly mints an external-chain out-transfer for coins the swap never produced; in `swap_to_staked_sri` it inflates PoL liquidity and the caller's staked allocation.

This mirrors the Loop bug exactly: `claimedAmount = address(this).balance` ≙ `coin_balance = Coins::balance(executor)`; donation-then-claim ≙ transfer-to-executor-then-batch-execution.

### Impact Explanation
An unprivileged user holding sriBTC/sriETH/SRI can transfer tokens to `IN_INSTRUCTION_EXECUTOR` or `POL_ACCOUNT`, then trigger (or wait for) an inbound batch instruction. For `DexCall::Swap` to an external address, the pallet burns the executor's whole `out_balance.coin` balance into an `OutInstruction`, causing the external network to pay out more than the deposit warranted — funds reported received/spendable that were never acquired by the swap. For `SwapAndAddLiquidity`/`swap_to_staked_sri`, LP tokens and staked SRI are minted against donated balance, diluting real LPs and validators' economic-security accounting.

### Likelihood Explanation
`IN_INSTRUCTION_EXECUTOR` is a constant public account ID; `Coins::transfer` is a normal signed call, so seeding it is trivially reachable with public inputs. Residual balances also arise organically: `add_liquidity` is invoked with `min` bounds of `1`, so dust remainders persist on the executor between instructions, and any `InstructionFailure` path leaves minted coins behind (the mint at line 114/171 is not rolled back per-instruction semantics depend on pallet error handling). The scenario-2 variant (inflating a ratio measured off live balances) also applies: `get_reserves`/`get_balance` read raw pool-account balances (`substrate/dex/pallet/src/lib.rs` lines 928-959), so direct transfers to `get_pool_account(pool_id)` shift reserves outside the accounting of minted LP shares.

### Recommendation
Use the `amount_out` returned by `Dex::swap_exact_tokens_for_tokens` / `do_swap` as the credited amount instead of `Coins::balance(...)`: capture `let sri_amount = Dex::<T>::swap_exact_tokens_for_tokens(...)?` at `in-instructions` lines 119-128, 190-203 and `emissions` lines 388-397. Snapshot-and-diff is a weaker alternative (balance_before vs after) but still vulnerable to concurrent credits; the return value is exact. For pools, track reserves in storage rather than deriving them from `Coins::balance(pool_account)`, or reconcile donated excess before pricing.

### Proof of Concept
1. Attacker sends a Bitcoin InInstruction `DexCall::Swap(out_balance = {coin: sriETH, amount: 1}, out_address = External(attacker_eth_addr))` with a modest BTC deposit, and in the same or prior batch window transfers `X` sriETH directly to `IN_INSTRUCTION_EXECUTOR` via `Coins::transfer`.
2. `execute` mints the BTC, swaps it for SRI→sriETH; the swap's actual output `Y` is returned but discarded.
3. Line 202-213 reads `coin_balance = Y + X` and burns it into an `OutInstructionWithBalance` for `X + Y` sriETH to the attacker's external address — an out-transfer `X` larger than the swap produced, draining pool/executor value.
4. Variant: attacker seeds `POL_ACCOUNT` with `X` SRI before a `SwapToStakedSRI` instruction; `sri_amount` at emissions line 397 becomes `swap_out + X`, so `add_liquidity` deposits mismatched amounts and the validator's minted/staked SRI (lines 416-426) is computed on inflated figures.
