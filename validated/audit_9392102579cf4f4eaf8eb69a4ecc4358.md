### Title
Manual conflict resolutions are carried over across unrelated merges/rebases, causing silent staging of unreviewed content - ([File: app/src/lib/stores/updates/changes-state.ts])

### Summary
`updateConflictState()` decides whether to preserve the user's per-file `manualResolutions` map purely based on whether the *kind* of conflict (`'merge'` vs `'rebase'`) stayed the same between the previous and new status snapshot — it never checks that the underlying operation is actually the *same* one (same `currentTip`/`currentBranch`/`targetBranch`). This mirrors the reported `VotingEscrow` bug pattern: two distinct "positions" (here, two distinct merge/rebase operations) get combined/merged without validating that their identifying state (lock end time / commit tip) actually matches, so stale per-key derived state (`slope_changes` / `manualResolutions`) is reused where it no longer applies.

### Finding Description
`updateConflictState` in `app/src/lib/stores/updates/changes-state.ts` computes the new conflict state and decides resolution-carry-over like this: [1](#0-0) 

The `manualResolutions` map is keyed only by file **path**, and it is preserved as long as `prevConflictState` and `newConflictState` are both of kind `'merge'` (or both `'rebase'`) — there is no comparison of `currentTip`, `currentBranch`, `targetBranch`, `baseBranchTip`, or `originalBranchTip` before deciding to reuse the map. `getConflictState()` builds the new state by threading through the *same* `manualResolutions` object it was given: [2](#0-1) 

This is functionally the same broken invariant as the report: two distinct "positions" (lock intervals in the Solidity report; here, two distinct merge/rebase operations, potentially against different branches/remotes) are combined without validating an identity/end-condition (`lockEnd` there, `currentTip`/branch here), so a value computed for one context (`slope_changes` / a user's manual pick of "theirs" or "ours" for a specific file) silently carries over into a different context where it no longer reflects the user's intent.

The project's own test suite acknowledges resolutions are "preserved between updates in the same merge" by relying only on the conflict `kind`, matching this reading: [3](#0-2) 

Existing guards elsewhere (e.g. the "abort counter" tests) only detect *some* rebase-tip mismatches for logging/telemetry purposes; they do not clear or invalidate `manualResolutions`, and no equivalent check exists at all for the `'merge'` branch of `updateConflictState`.

### Impact Explanation
`manualResolutions` values are later consumed directly to stage file content without further user confirmation, e.g. in `createMergeCommit`: [4](#0-3) 
and `continueCherryPick`/rebase continuation apply the same pattern by path.

If a user resolves a conflicting file path (say `README.md`) by choosing "theirs" while merging a trusted branch, then — without ever making an explicit resolution decision — a subsequent, distinct merge operation (e.g. against an attacker-controlled remote/branch that happens to also conflict on `README.md`, perhaps because Desktop retriggers `_triggerConflictsFlow`/`updateConflictState` while the working copy still reports `mergeHeadFound: true` for a new merge attempt) can silently reuse the stale "theirs" resolution and stage the attacker's version of the file into the commit, without the user reviewing or approving that specific content. This is exactly the "silent corruption of what the user commits or pushes" impact category: the committed tree ends up containing content the user never actually reviewed for that particular merge.

### Likelihood Explanation
The precondition is narrower than a fully generic exploit — it requires the app to transition between two conflict states of the *same kind* (`merge`→`merge` or `rebase`→`rebase`) with overlapping conflicted file paths but different underlying tips/branches, e.g. through a fetch/merge retry flow, a stale in-memory app-store state after switching remotes, or repeated status polling during an in-progress operation targeting a different branch. This requires specific sequencing of Desktop's async status-polling and conflict-detection code path rather than a single attacker-controlled input, so likelihood is moderate rather than trivially always-exploitable; a concrete, minimal repro sequence could not be fully validated within the available tool calls (I was unable to inspect `performEffectsForMergeStateChange`/`performEffectsForRebaseStateChange` bodies before running out of iterations, so I cannot confirm whether they add any extra invalidation not visible in the snippet reviewed).

### Recommendation
In `updateConflictState`, invalidate (reset to an empty map) `manualResolutions` whenever the identifying fields of the conflict state change between polls — for merges, compare `currentBranch`/`currentTip`; for rebases, compare `targetBranch`/`originalBranchTip`/`baseBranchTip`. Only preserve `manualResolutions` when these identifiers are unchanged between `prevConflictState` and `newConflictState`, analogous to properly updating `slope_changes` (or rejecting the merge) when lock end times differ in the original report.

### Proof of Concept
Conceptual reproduction (not fully verified against `performEffectsForMergeStateChange` internals due to tool-call limits):
1. Start merging branch `trusted` into `main`; conflict occurs on `shared.txt`; user picks "ours" (rejecting content from `trusted`).
2. Before finishing/committing, the merge is aborted or superseded and Desktop begins a new merge (`git merge attacker-branch`) that also conflicts on `shared.txt`, while `getConflictState` still reports `kind: 'merge'`.
3. `updateConflictState` sees `prevConflictState.kind === 'merge'` and `newConflictState.kind === 'merge'`, so it reuses the previous `manualResolutions` Map containing `shared.txt -> ours` without checking that `currentBranch`/`currentTip` changed.
4. When the user clicks commit, `createMergeCommit` stages `shared.txt` using the stale resolution without the user ever having reviewed the diff against `attacker-branch`, silently committing/staging content the user did not knowingly approve for this merge. [1](#0-0) [4](#0-3)

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

export async function createMergeCommit(
  repository: Repository,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  manualResolutions: ReadonlyMap<string, ManualConflictResolution> = new Map()
): Promise<string> {
  // apply manual conflict resolutions
  for (const [path, resolution] of manualResolutions) {
    const file = files.find(f => f.path === path)
    if (file !== undefined) {
      await stageManualConflictResolution(repository, file, resolution)
    } else {
      log.error(
        `couldn't find file ${path} even though there's a manual resolution for it`
      )
    }
  }
