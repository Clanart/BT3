### Title
Webhook `shop_domain` helper trusts unverified `X-Shopify-Shop-Domain` header, enabling cross-shop webhook data confusion - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
`ShopifyApp::WebhookVerification#shop_domain` returns the raw, unauthenticated `HTTP_X_SHOPIFY_SHOP_DOMAIN` header value with no binding to the HMAC-verified request body. Because the app's HMAC secret is shared across all shops installing the app (it is not per-shop), a merchant controlling shop A can capture a legitimately-signed webhook body+HMAC for their own shop and replay it against the app's webhook endpoint with the header rewritten to shop B, causing custom webhook controllers (built per the library's documented pattern) to attribute attacker-controlled webhook data to a victim shop.

### Finding Description
`verify_request` only validates that the raw POST body matches the HMAC computed with the app's client secret(s): [1](#0-0) 

It never checks that the HMAC-signed body is associated with the shop asserted in `HTTP_X_SHOPIFY_SHOP_DOMAIN`. `shop_domain` simply reads that header directly: [2](#0-1) 

The library explicitly documents building custom controllers around this concern, using `shop_domain` as the trusted shop identity to queue background work: [3](#0-2) 

Because the HMAC secret (`ShopifyApp.configuration.secret` / `old_secret`) is a single value shared by the whole app across every installed shop — not a per-shop secret — any body that is validly signed for shop A's real webhook delivery is also a *validly signed body* under the same secret irrespective of which shop header accompanies it. An attacker who is a merchant on shop A can:
1. Trigger (or use Shopify's Partner Dashboard "send test webhook" feature for) a real webhook delivery to their own app installation, capturing the raw body and its `X-Shopify-Hmac-Sha256` value.
2. Replay that exact body+HMAC to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `hmac_valid?` still returns true (it never inspects the shop header), so `verify_request` passes.
4. A custom controller built per the documented pattern calls `shop_domain` (returns `victim-shop.myshopify.com`) and enqueues a job with `shop_domain: shop_domain, webhook: webhook_params` — associating attacker-supplied webhook content with the victim's shop/session.

No downstream check (sanitize_shop_domain, session lookup validation, scope comparison) reconciles the header-derived `shop_domain` against the signed payload, so this bypass is not otherwise mitigated.

### Impact Explanation
This is a cross-shop data confusion vulnerability: an attacker can cause the host application to process/store attacker-chosen webhook payload data under a victim shop's identity/session, matching Shopify's "cross-shop information disclosure/confusion" impact class. The severity depends on what the custom controller/job does with `shop_domain` and `webhook` (e.g., writing to victim shop's DB records, triggering shop-scoped side effects), but the trust boundary violation itself (accepting a validly-HMAC'd body under an arbitrary shop identity) is concrete and reproducible.

### Likelihood Explanation
Exploitability requires only an unprivileged attacker who is any merchant able to install the target app on their own store and trigger/capture one webhook delivery — no access to the app's secret, no victim session, and no host misconfiguration. This is a realistic and repeatable precondition (test webhooks are a standard, self-service Shopify Partner Dashboard feature), and the replay itself is a trivial raw HTTP POST with a rewritten header.

### Recommendation
Do not treat `HTTP_X_SHOPIFY_SHOP_DOMAIN` as a trusted shop identity by itself. Bind the shop to the signed payload, e.g., derive/validate the shop from the webhook body (`webhook["shop_domain"]`/similar Shopify-provided fields already covered by the HMAC), or track/require unique per-delivery `X-Shopify-Webhook-Id` values with idempotency storage to prevent replay, and document that custom controllers must independently validate that the header-derived shop matches the expected recipient before using it for session/data lookups.

### Proof of Concept
```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end

# Integration test
test "hmac valid for shop A's payload is accepted with forged shop_domain header for shop B" do
  body = '{"id":1,"note":"attacker payload"}'
  secret = ShopifyApp.configuration.secret
  hmac = Base64.strict_encode64(OpenSSL::HMAC.digest("sha256", secret, body))

  post "/webhooks/carts_update",
    params: body,
    headers: {
      "HTTP_X_SHOPIFY_HMAC_SHA256" => hmac,
      "HTTP_X_SHOPIFY_SHOP_DOMAIN" => "victim-shop.myshopify.com", # forged, not shop A's real domain
      "CONTENT_TYPE" => "application/json",
    }

  assert_response :no_content
  # Assert SomeJob was enqueued with shop_domain: "victim-shop.myshopify.com"
  # even though the HMAC was generated for a body originating from the attacker's own shop.
end
```

      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)
