### Title
Zero-amount predispatch input permanently locks an order's escrow on Tron `IntentGatewayV2.withdraw` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` (Tron) validates `order.inputs[i].amount == 0` only on the non-predispatch escrow path, not on the predispatch path. A zero-amount input token can therefore enter escrow with `_orders[commitment][token] == 0`. Later, any `withdraw()` call (fill, same-chain cancel, cross-chain refund) iterates `body.tokens` — which is always `order.inputs` verbatim, since this contract has no partial-fill/proportional-amount tracking — and reverts with `UnknownOrder` the moment it hits that zero-amount token, because the check is `if (_orders[commitment][token] == 0) revert UnknownOrder()` with no zero-amount skip. This aborts the whole transaction, permanently locking every other (non-zero) token already escrowed for that same commitment.

### Finding Description
In `placeOrder` (evm/tron/contracts/apps/IntentGatewayV2.sol): [1](#0-0) 
guards `order.inputs[i].amount == 0` with `revert InvalidInput()`, but the predispatch branch above it: [2](#0-1) 
has no equivalent check — it happily escrows `reducedInputs[i].amount` (which is `order.inputs[i].amount` minus protocol fee, so also 0 when the input amount is 0) for any input token, including one whose declared amount is 0.

Every settlement path (fill via `RedeemEscrow`, same-chain cancel, cross-chain `RefundEscrow`) funnels into `withdraw()`: [3](#0-2) 
which loops `body.tokens` (always the *original* `order.inputs` array — this contract has no `_partialFills`/proportional-release logic like the newer `IntentsBase.sol`) and reverts on `_orders[commitment][token] == 0` with **no `if (amount == 0) continue;` guard**, unlike the newer EVM base contract: [4](#0-3) 
which explicitly skips zero-amount tokens before checking escrow. The Tron contract retains the unpatched pattern.

Because escrow for the zero-amount token is exactly 0 (matching the amount being withdrawn), the check is a false rejection — the "revert if attempting to re-process a legitimately zero amount" bug class from the report, applied here to `withdraw()` instead of an ICHI vault `deposit()`.

### Impact Explanation
Any order that contains a zero-amount input token in the predispatch flow becomes permanently unfillable and uncancellable: `fillOrder`/`RedeemEscrow`, same-chain `cancelOrder`, and cross-chain `RefundEscrow` all call `withdraw()`, which reverts as soon as it reaches the zero-amount token entry, aborting release of every other token escrowed under that commitment. The escrowed non-zero-amount tokens for that order (real user/solver funds) become permanently stuck in the contract — no user, solver, or governance action can retrieve them since the code path always reverts identically for that fixed commitment. This is a direct fund-lock/loss condition inherent to the contract logic, not a network-level DoS, and it's reachable by any unprivileged order creator without needing a malicious relayer, prover, or admin.

### Likelihood Explanation
Likelihood is Medium: it requires an order with `predispatch.call.length > 0` and `predispatch.assets.length > 0` where at least one `order.inputs[i].amount == 0` (either intentionally set by the order creator, or unintentionally produced when a predispatch swap/route legitimately yields a zero required amount for one asset leg). Since `placeOrder` never rejects this configuration on the predispatch path, it is trivially constructible by any caller of `placeOrder`, with no special privileges needed.

### Recommendation
Add the same zero-amount validation used in the non-predispatch branch to the predispatch escrow loop in `placeOrder` (reject `order.inputs[i].amount == 0` unconditionally), and/or add the `if (amount == 0) continue;` guard to `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match the already-patched behavior in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`.

### Proof of Concept
1. Attacker/user calls `placeOrder` with `predispatch.call.length > 0`, `predispatch.assets.length > 0`, and `order.inputs = [ {token: A, amount: 100}, {token: B, amount: 0} ]`.
2. `placeOrder`'s predispatch branch (lines 407-440) escrows `_orders[commitment][A] = 100` and `_orders[commitment][B] = 0` — no revert, since the zero check at line 446 only applies to the `else` (non-predispatch) branch.
3. A solver fills the order (or the user cancels it same-chain, or a `RefundEscrow` is dispatched cross-chain); `withdraw()` is invoked with `body.tokens = order.inputs` (both A:100 and B:0).
4. On iterating token B, `_orders[commitment][B] == 0` is true, so `withdraw()` reverts with `UnknownOrder()` before token A's 100 units are ever released.
5. Every subsequent call to fill/cancel/refund for this exact commitment repeats the same revert, permanently locking the 100 units of token A in the contract.
