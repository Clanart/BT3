I found a confirmed local analog. The Tron `IntentGatewayV2.placeOrder` credits escrow using the *requested* input amount instead of the actual token balance received, unlike the mainline EVM contract, which explicitly measures actual received balances to defend against fee-on-transfer tokens.

### Title
Escrow over-credited beyond actual tokens received for fee-on-transfer inputs, causing insolvent withdrawals - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` on Tron (`evm/tron/contracts/apps/IntentGatewayV2.sol`) credits `_orders[commitment][token]` with `reducedInputs[i].amount` — a value derived from the user-specified `order.inputs[i].amount` minus the protocol fee — without ever verifying that the gateway actually received that many tokens. The mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`) explicitly fixed this exact class of bug by snapshotting balances before/after `safeTransferFrom` and using the *actual* received delta (`order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;`) before computing protocol fees and escrow. The Tron variant regressed this fix.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`:
- The non-predispatch escrow path (lines 444-463) does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
```
`reducedInputs[i].amount` is computed from the nominal `order.inputs[i].amount` (protocol fee deducted), not from a post-transfer balance check. [1](#0-0) 

Compare this with the corrected mainline logic that measures the real balance delta: [2](#0-1) 

If any input token deducts a transfer fee (a standard ERC-20 pattern, exercised in this repo's own test suite via `FeeOnTransferToken`), the gateway physically holds less than `_orders[commitment][token]` records. Later, `withdraw()`/`_withdraw()` blindly decrements the recorded escrow and transfers the full recorded `amount` to the solver or user: [3](#0-2) 
Because the accounting ledger (`_orders[commitment][token]`) is inflated relative to the real token balance, the first-filled order's payout can drain tokens that belong to *other* orders' escrow in the same contract, or the transfer can simply revert once the shared token balance is exhausted — leaving the corrupted, higher-than-actual `_orders` entry in place and preventing that (and possibly other) orders from ever fully settling. This mirrors the BigBang bug class exactly: a fee is subtracted from the accounting ledger's "amount owed/available" side without any corresponding real-asset backing, so the recorded value structurally exceeds what's actually in custody.

### Impact Explanation
This directly threatens escrowed user/solver funds under the "stealing or loss of funds" and "transaction manipulation" impact categories: a single order placed with a fee-on-transfer token inflates the on-chain escrow ledger beyond the contract's real token balance. Subsequent fills/refunds/cancellations pay out against the inflated figure, which can (a) pull real balance belonging to unrelated orders (cross-order fund loss), or (b) permanently strand escrow that can never be paid out in full (fund lock), since `_orders[commitment][token] -= amount` never reconciles against the real balance.

### Likelihood Explanation
Reachable by any unprivileged user calling the public `placeOrder` entrypoint with an arbitrary ERC-20 `token` address that happens to charge a transfer fee — no relayer, prover, or admin involvement required. The repo's own Foundry suite already demonstrates this scenario is realistic (`FeeOnTransferToken`, tested against the *fixed* mainline contract), confirming fee-on-transfer tokens are an anticipated, non-exotic input in this codebase; the Tron deployment target simply omits the corresponding balance-delta guard.

### Recommendation
Mirror the mainline EVM fix in the Tron contract: snapshot `balanceOf(address(this))` before and after each `safeTransferFrom`, use the actual received delta as `order.inputs[i].amount` before computing `reducedInputs` and protocol fees, and only credit `_orders[commitment][token]` with the amount actually held by the contract, exactly as done in `evm/src/apps/IntentGatewayV2.sol` lines 281-298.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with a `FeeOnTransferToken` (e.g., 1% transfer fee) registered as `order.inputs[0].token`, `order.inputs[0].amount = 1000e18`.
2. User calls `placeOrder` with no predispatch call → hits the `else` branch at lines 444-463.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` actually delivers only `990e18` to the gateway (1% fee burned/retained by token).
4. Contract nonetheless sets `_orders[commitment][token] += reducedInputs[0].amount` computed from the full `1000e18` (minus protocol fee bps), e.g. `~995e18` — exceeding the `990e18` actually held.
5. On fill/settlement, `_withdraw`/`withdraw()` transfers the full recorded `995e18` out of the contract's shared token balance, which either reverts once the shared pool of that token is drained by other orders, or pays out `5e18` more than this order ever deposited, sourced from other users' escrow of the same token.
