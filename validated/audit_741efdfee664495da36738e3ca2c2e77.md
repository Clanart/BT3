### Title
`ThresholdKeys::read` permanently fixes a participant/verification-share set whose members past index `t` are never validated — malicious shares are locked in and produce persistent mis-attributed signing failures - (File: crypto/dkg/src/lib.rs)

### Summary
The external report's bug class is an initialized, immutable set (`_pooledTokens`) that cannot be updated once committed, allowing bad members to permanently poison the construct. The Serai analog is `ThresholdKeys::read` / `ThresholdKeys::new`: the `verification_shares` map (the "participant set") is frozen into an `Arc<ThresholdCore>` at construction, is never updatable, and is only partially validated — the group key is computed solely from shares `1..=t`, so verification shares for participants `t+1..=n` are entirely unconstrained, and the secret share is never checked against `verification_shares[i]`.

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) deserializes `t`, `n`, `i`, the interpolation method, the secret share, and `n` verification shares, then calls `ThresholdKeys::new`. `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) checks only the count and index range of `verification_shares`, then computes `group_key` by interpolating only participants `1..=t`:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

Nothing binds `secret_share` to `verification_shares[i]` (`C::generator() * secret_share == verification_shares[i]` is never asserted), and shares `t+1..=n` do not affect `group_key` at all. Once constructed, `core` is immutable behind `Arc` — there is no API to replace a verification share or remove a participant. The corrupted entry is then used by `ThresholdKeys::view` (lines 500-507) to build per-signing-set verification shares, and FROST share verification in `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:475-489) attributes failure to the participant index via `FrostError::InvalidShare(l)`.

### Impact Explanation
An attacker who can feed bytes to `ThresholdKeys::read` (e.g., imported/restored key material — an in-scope read path per the threat model) can embed a malicious verification share for any index `> t` without changing `group_key`. The corruption is silent at load time — the derived group key still matches the expected address key — but every signing session that includes that participant index permanently fails share verification, and `InvalidShare` blames the honest participant whose index was poisoned, not the attacker. Because the set cannot be updated, the only recovery is abandoning the key set and re-running key generation — exactly the "pause, update, re-initialize" remediation in the external report — while any funds at `group_key` risk becoming unspendable if enough indexes are corrupted. Mis-blame additionally corrupts the protocol's fault attribution (a malicious share frames an honest signer as faulty on every attempt).

### Likelihood Explanation
Exploitation requires the attacker to control serialized `ThresholdKeys` consumed by a victim, which is more constrained than an on-chain path — hence Medium rather than High. When it is reachable, the failure is deterministic and permanent: every signing set including a poisoned index fails, indefinitely, with wrong blame attribution. The gap is structural — `new` deliberately derives `group_key` from only `1..=t` — so any `n > t` key set loaded via `read` carries unvalidated, immutable members.

### Recommendation
In `ThresholdKeys::new` (or at minimum `ThresholdKeys::read`), verify internal consistency of the full fixed set: assert `C::generator() * secret_share == verification_shares[&params.i()]` after scalar/offset normalization, and commit the group key to all `n` verification shares (e.g., verify the full `1..=n` interpolation is consistent, not just `1..=t`), so malformed members are rejected at initialization instead of being permanently baked in and later surfacing as `InvalidShare` against honest participants. Document the provenance requirement on serialized `ThresholdKeys`.

### Proof of Concept
For any `t < n` ciphersuite `C`, serialize a `ThresholdKeys` blob with a valid `(t, n, i)`, honest `secret_share`, correct verification shares for indexes `1..=t`, and a replaced/garbage point for index `t+1`. `ThresholdKeys::read` succeeds and `group_key()` is unchanged (it is computed only over `1..=t`). Any subsequent `view(included)` where `included` contains `Participant::new(t+1)` produces a `verification_shares` map whose entry for `t+1` is garbage; when that participant submits a valid FROST share, `algorithm.verify_share` in `complete` fails and returns `FrostError::InvalidShare(t+1)` — blaming the honest participant — on every attempt, with no API to repair the baked-in share.
