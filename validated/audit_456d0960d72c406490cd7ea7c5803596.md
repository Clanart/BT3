### Title
Token-pair contract identity is pinned by mutable address, not by code hash, allowing selfdestruct+CREATE2 redeploy to hijack `ConvertCoin`/`ConvertERC20` escrow accounting - (File: x/erc20/keeper/msg_server.go)

### Summary
The GitHub Actions report's underlying bug class is "trusting a mutable reference (tag/branch) as if it were an immutable, content-addressed pin," which lets an untrusted party silently swap what that reference resolves to. The Cosmos EVM analog is in `x/erc20`: a `TokenPair` binds a Cosmos coin denom to an ERC-20 contract by its **address** only [1](#0-0) , never by code hash. The conversion logic (`ConvertERC20`, `ConvertCoin`/`ConvertCoinNativeERC20`) re-resolves this address at call time and trusts whatever bytecode currently lives there, only special-casing the fully-destroyed case. If the registered contract is self-destructed and a new contract is deployed at the exact same address (e.g., via `CREATE2`), the pinned "reference" silently now points to attacker-controlled logic, exactly analogous to a modified `v2` tag pointing to malicious code.

### Finding Description
`ConvertERC20` and `ConvertCoin` both guard against the destroyed-and-never-redeployed case by checking `acc.HasCodeHash()` and deleting the token pair if the contract is gone: [2](#0-1) [3](#0-2) 

This check only asks "does an account with a code hash exist at this address" — it does not verify that the code hash matches the originally registered ERC-20 bytecode. `DeleteAccount` (self-destruct) clears the code hash entirely [4](#0-3) , but nothing prevents a subsequent `CREATE2` deployment (from an attacker-controlled deployer/factory whose deployment address was precomputed before registration) from placing brand-new bytecode at that same address before the next `ConvertCoin`/`ConvertERC20` call executes.

Once redeployed, `acc.HasCodeHash()` is true again, so the pair is treated as still valid, and `ConvertCoinNativeERC20` proceeds to:
1. Escrow native coins from the sender into the module account.
2. Call `transfer(...)` on the contract at the pinned address using the original ERC20 ABI.
3. Check the resulting balance via `BalanceOf` on that same (now malicious) contract.
4. Burn the escrowed coins if the balance check "passes". [5](#0-4) 

Because the malicious contract fully controls its own `transfer` and `balanceOf` implementations, it can unconditionally report success and fabricate whatever balance value the invariant check expects — without moving or possessing any real tokens. The invariant check (`balanceTokenAfter == balanceToken + amount`) is meaningless once the code backing the "pinned" address is attacker-controlled, since both sides of the comparison are computed by the same malicious contract.

### Impact Explanation
This breaks the 1:1 backing invariant between native coin supply and ERC-20 token representation that `x/erc20` is built to preserve. An attacker who controls the deployer of the original ERC-20 contract (i.e., registered as `OWNER_EXTERNAL`/native-ERC20 pair) can:
- Self-destruct the registered contract.
- Redeploy fake logic at the same address via `CREATE2`.
- Call `ConvertCoin` repeatedly to escrow-then-unlock (or fabricate) unlimited amounts of the paired native coin while providing no real ERC-20 collateral, or conversely drain the module's escrowed coin/token balances.

This is unauthorized minting/duplication of spendable user value and a critical accounting-invariant break, matching the "Critical unauthorized minting/duplication/irreversible accounting corruption" impact category.

### Likelihood Explanation
Any user can permissionlessly deploy and register an ERC-20 contract for native pairing (`RegisterERC20` is permissionless when `PermissionlessRegistration` is enabled, per `x/erc20/keeper/msg_server.go` `RegisterERC20`), and `CREATE2` address precomputation plus self-destruct-then-redeploy is a well-known, unprivileged EVM technique requiring no validator or governance collusion. The only guard in place (`HasCodeHash()`) does not defend against this because it only detects "no contract" vs "some contract," not "the same contract."

### Recommendation
- Short term: Pin the token pair to the ERC-20 contract's code hash at registration time (already computed and stored for dynamic precompiles via `RegisterERC20CodeHash`), and verify `acc.CodeHash` matches the originally registered hash before performing any conversion in `ConvertERC20`/`ConvertCoinNativeERC20`, deleting/disabling the pair on mismatch instead of just on "no code."
- Long term: Audit all places that treat an EVM contract address as a stable identity (token pairs, dynamic precompiles, IBC/ICS-20 hooks) and ensure code-hash pinning or an equivalent immutability guarantee (e.g., rejecting registration of upgradeable/CREATE2-friendly proxies, or re-validating code hash on every privileged call) is enforced end-to-end.

### Proof of Concept
1. Attacker deploys a minimal proxy/factory that can `CREATE2` a contract to a precomputed address `X`.
2. Attacker deploys the legitimate-looking `ERC20MinterBurnerDecimals` contract at `X` via that factory and registers it as a native ERC-20 token pair through `RegisterERC20` (permissionless registration or via a passed proposal).
3. Attacker calls `selfdestruct` on the contract at `X` (via `x/vm` `DeleteAccount`), clearing its code hash.
4. Attacker uses the same factory to `CREATE2` a malicious contract at the same address `X` whose `transfer`/`balanceOf` always report success/expected values without moving real value.
5. Attacker calls `MsgConvertCoin` to convert native coins into "ERC-20 tokens" at `X`; `ConvertCoinNativeERC20` escrows the native coins, calls the fake `transfer`, and the fabricated `balanceOf` response satisfies the invariant check, so the coins are burned from escrow while the attacker's malicious contract never possessed real backing — net effect: real native coins are extracted from the module/user without giving up any real token value, or replayed to mint/duplicate value depending on direction of conversion abused.

// DeleteAccount handles contract's suicide call:
// - clear balance
// - remove code
// - remove states
// - remove the code hash
// - remove auth account
func (k *Keeper) DeleteAccount(ctx sdk.Context, addr common.Address) error {
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	acct := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	if acct == nil {
		return nil
	}

	// NOTE: only Ethereum contracts can be self-destructed
	if !k.IsContract(ctx, addr) {
		return errors.New("only smart contracts can be self-destructed")
	}

	// set account to a base account to set the whole balance as spendable
	baseAccount := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	k.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(cosmosAddr, baseAccount.GetPubKey(), baseAccount.GetAccountNumber(), baseAccount.GetSequence()))

	// clear balance
	if err := k.SetBalance(ctx, addr, new(uint256.Int)); err != nil {
		return err
	}

	var keys []common.Hash

	// clear storage
	k.ForEachStorage(ctx, addr, func(key, _ common.Hash) bool {
		keys = append(keys, key)
		return true
	})

	for _, key := range keys {
		k.DeleteState(ctx, addr, key)
	}

	// clear code hash
	k.DeleteCodeHash(ctx, addr)

	// remove auth account
	k.accountKeeper.RemoveAccount(ctx, acct)

	k.Logger(ctx).Debug(
		"account suicided",
		"ethereum-address", addr.Hex(),
		"cosmos-address", cosmosAddr.String(),
	)

	return nil
}
