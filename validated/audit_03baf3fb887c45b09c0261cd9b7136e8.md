## Analog Found: ProtoJSON duplicate-field detection differs between the pure-Python parser and the C++/upb parser, allowing "last-spelling-wins" field smuggling

### Title
ProtoJSON parser differential: pure-Python `json_format.Parse` fails to detect duplicate fields expressed under alternate JSON spellings (`json_name` vs. proto `name`), unlike the C++/upb JSON parser - (File: `python/google/protobuf/json_format.py`)

### Summary
The ruby-saml bug stems from two XML parsers (ReXML, Nokogiri) producing different document structures for identical bytes, letting an attacker craft input whose *security-relevant* structure differs depending on which parser evaluates it, enabling signature-wrapping bypass. Protobuf's ProtoJSON ecosystem has an analogous parser differential: the same JSON bytes containing a field expressed twice under two different valid spellings (`camelCase` json_name and `snake_case` proto field name) are accepted by the pure-Python `json_format` implementation with "last one wins" silently overwriting the field, while the C++/upb-based JSON parser correctly treats both spellings as referring to the same `FieldDescriptor` and rejects the input as a duplicate. Depending on which backend an application (or two cooperating applications/services) uses, identical attacker-controlled bytes are interpreted with different effective field values.

### Finding Description
In the pure-Python implementation, `_Parser._ConvertFieldValuePair` resolves each JSON key to a field via `fields_by_json_name` first, then via `message_descriptor.fields_by_name`, and only tracks duplication using a raw string list `names`: [1](#0-0) [2](#0-1) 

Because the duplicate check (`if name in names`) compares literal JSON key strings, not resolved field identity, a payload containing both `"int32Value"` and `"int32_value"` — two different string spellings that resolve to the *same* `FieldDescriptor` — passes the duplicate check and simply overwrites the field per "last one wins." This is explicitly acknowledged as a known bug in the project's own tests: [3](#0-2) 

By contrast, the C++/upb JSON parser (`src/google/protobuf/json/internal/parser.cc`) resolves the name to a `field` handle first, then calls `Traits::RecordAsSeen(*field, msg)`, which tracks "already seen" state keyed by the resolved field object, not the literal spelling used in the JSON text: [4](#0-3) 

This means the C++/upb backend correctly rejects the duplicate-field-via-alternate-spelling payload (per the ProtoJSON conformance requirement), while the pure-Python backend accepts it and silently applies "last spelling wins" semantics. The invariant that "a given field can only be set once via JSON, regardless of which of its valid name spellings is used" is violated only in one of the two officially-shipped, protobuf-maintained parsing backends for the same language ecosystem (Python).

### Impact Explanation
Any system that mixes protobuf JSON-parsing backends — e.g., a validating/allowlisting layer built against the C++-accelerated `upb` implementation (which enforces the invariant and would reject or canonicalize the duplicate) versus an enforcement/business-logic layer running with the pure-Python fallback implementation (which silently applies "last spelling wins") — can be given identical attacker-controlled ProtoJSON bytes that are interpreted with different effective field values by each component. This is the same class of impact as the ruby-saml issue: a verifier and an enforcement path disagree on the "true" value of a field within the same message due to a missing canonicalization/duplicate-detection invariant in one of the two parsers, enabling smuggling of an attacker-chosen effective value past a check performed on the other parser's (different) interpretation. It does not by itself grant RCE or memory corruption, but it is a genuine integrity/authorization-bypass-class primitive when application logic relies on ProtoJSON field uniqueness across name variants.

### Likelihood Explanation
The pure-Python `json_format` module is a public, documented, supported API (`google.protobuf.json_format.Parse`/`ParseDict`) and remains the fallback implementation used whenever the C++ accelerated extension is unavailable (e.g., certain sandboxed, embedded, or `pip`-installed pure-Python environments). Any ordinary client can submit bounded, well-formed JSON with two spellings of the same field — no privileged access, hostile schema, or huge payload is required — making this trivially triggerable end-to-end. The main constraint on real-world impact is that it requires an application architecture where two different parsing backends (or two different protobuf language runtimes) are used to interpret the same bytes for different purposes (e.g., validation vs. enforcement), which is a plausible but not universal deployment pattern.

### Recommendation
Fix `_ConvertFieldValuePair` in `python/google/protobuf/json_format.py` to track "seen" state by resolved `FieldDescriptor` identity (as the C++/upb implementation already does via `RecordAsSeen`) rather than by the raw JSON key string, so that duplicate detection is spelling-invariant and matches ProtoJSON conformance semantics across all officially maintained backends.

### Proof of Concept
Using the existing (currently passing, documented-as-bug) test as the concrete reproduction: [5](#0-4) 
```python
from google.protobuf import json_format
msg = json_format_proto3_pb2.TestMessage()
json_format.Parse('{"int32Value": 1,"int32_value":2}', msg)
assert msg.int32_value == 2  # pure-Python: succeeds silently, "last wins"
```
The equivalent bytes parsed via the C++/upb backend's `ParseField` path reach the `RecordAsSeen`/`SeenState::kFieldAlreadySeen` branch and raise `'int32Value' has already been set`, per `src/google/protobuf/json/internal/parser.cc:1261-1267`, demonstrating the cross-backend structural disagreement on identical input bytes.
