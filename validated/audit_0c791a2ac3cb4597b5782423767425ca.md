### Title
Conflict-marker text embedded in legitimate file content confuses Copilot conflict-resolution reassembly, silently deleting/misplacing committed lines - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's AI-assisted merge-conflict resolution (`_applyCopilotConflictResolutions` → `reassembleResolutions` → `reassembleResolvedFile`) reconstructs a resolved file by scanning the on-disk conflicted file line-by-line for `<<<<<<<`, `=======`, and `>>>>>>>` marker lines and splicing in the model's per-hunk output. The scan uses bare regular expressions that match *any* line with the right shape, with no escaping/quoting distinction between real git conflict markers and identical-looking text that is simply part of a file's legitimate content (e.g. documentation, test fixtures, or example transcripts that themselves contain conflict-marker-shaped lines). When such content sits inside or near a real conflict block, the reassembly logic misidentifies the conflict boundaries and silently drops or displaces genuine, non-conflicted lines when writing and staging the resolved file — mirroring the seed report's pattern of a transformation/parsing step being applied incompletely/incorrectly to nested content, corrupting the final artifact the user commits.

### Finding Description
`reassembleResolvedFile` treats any line matching `^<{7}(?:\s|$)` as the start of a conflict block, looks ahead for the *first* line matching `^={7}$` as separator and the *first* subsequent line matching `^>{7}(?:\s|$)` as the closing marker: [1](#0-0) [2](#0-1) 

This is a purely textual, positional scan — it has no way to distinguish a real unresolved git conflict from a line inside the file's actual content that happens to match the same shape (e.g. `=======` as a markdown horizontal rule/heading underline, or `>>>>>>> feature` appearing in a tutorial, changelog, chat-log fixture, or a test file that documents/tests conflict-marker parsing, such as this very repo's `app/test/unit/copilot-conflict-resolution-test.ts` and `status-parser-test.ts`, which embed literal marker lines as string content). If a real conflict block is immediately followed (later in the file) by such a look-alike line, the "look ahead for `=======`" / "first `>>>>>>>`" scan will treat that unrelated line as the closing marker of the real conflict. The code then does:

```
i = closingIndex + 1
```

skipping — and thus discarding — every legitimate line between the real conflict and the false marker, and splices in the LLM's `resolvedContent` for that hunk in their place.

Because `validateResolutionPaths` only checks that the *count* of hunks matches the *count* of `<<<<<<<` occurrences reported by the file-conflict-context builder, it cannot detect this kind of marker-shape collision — the count is unaffected, only the content between the real and the confused "closing" marker is wrong: [3](#0-2) 

The corrupted content is then written directly to disk and staged by `_applyCopilotConflictResolutions`: [4](#0-3) 

The only guard in front of committing this is the diff preview rendered in the Copilot-conflicts "Changes" tab, which computes a diff between the reassembled content and the original file via `getResolutionDiff`: [5](#0-4) 

That diff would show the dropped lines as a deletion, but nothing calls it out as anomalous or ties it to marker-scan confusion — it appears as ordinary diff noise mixed in with the legitimate AI-authored resolution, in a dialog whose whole premise is "trust the summary/reasoning, click Continue Merge." A user relying on the "reasoning" text and summary (which describe only the intended merge resolution, not accidental deletions) can easily miss an unrelated deletion buried in the diff, especially in larger files or side-by-side view.

### Impact Explanation
This causes silent corruption of what the user commits: legitimate, unrelated file content is deleted from the merge result without warning or explanation, and the AI's `reasoning` text will not mention it because it was never asked to resolve that region. Because the corrupted commit becomes part of the merge/rebase result, this can quietly remove code, tests, or documentation from the repository history, matching the "silent corruption of what the user commits or pushes" impact category. Severity depends on the file and lines lost, but the mechanism is deterministic given attacker-controlled repository/file content.

### Likelihood Explanation
The attacker only needs to get such marker-shaped content into a repository the user will merge/rebase (a cloned/fetched repo, or a branch/PR the user pulls in) — no local access, credentials, or social engineering beyond a normal merge is required. Files that legitimately contain conflict-marker-like text (documentation about git, chat/log fixtures, ASCII-art separators, or code implementing/testing conflict-marker parsers) are plausible and even present in this very codebase's own test fixtures, so the triggering condition is not exotic. The main mitigating factor is that a careful reviewer scrutinizing every line of the diff before clicking "Continue Merge" could catch it, which is why likelihood is medium rather than high.

### Recommendation
Make `reassembleResolvedFile` conflict-aware rather than purely textual:
- Track whether a `<<<<<<<` was actually opened via a stateful scan that only recognizes `=======`/`>>>>>>>` while inside an active block (already partially done), but additionally validate that the discovered block's marker suffix (e.g. branch/label after `<<<<<<<` and `>>>>>>>`) is consistent/matching, since git always pairs them with matching labels.
- Cross-check the number and position of markers found against `git status`/`git diff` conflict metadata (e.g., via `git diff --check` or actual index stage data) rather than re-deriving purely from a raw-content regex scan.
- Surface a visible warning in the Copilot conflict-resolution dialog when a scanned "conflict block" doesn't structurally match the expected git conflict grammar, or when reassembly removes lines outside of any reported hunk boundary.

### Proof of Concept
1. Create a repository containing a file, e.g. `NOTES.md`, with content that legitimately includes a line of exactly seven `>` characters followed by text, e.g. as a blockquote/prompt-log example:
   ```
   Some real documentation
   >>>>>>> forwarded message
   more real documentation that should never be touched
   ```
2. Create a genuine merge conflict earlier in the same file (two branches editing an unrelated section above), so the file on disk looks like:
   ```
   <<<<<<< HEAD
   our version
   =======
   their version
   >>>>>>> feature
   Some real documentation
   >>>>>>> forwarded message
   more real documentation that should never be touched
   ```
   (Note: in this contrived layout the real conflict already has its own correct closing marker, so to reproduce the bug precisely construct a case where the model/algorithm's `=======` lookahead spans past the real closer into the look-alike text — e.g. a conflict whose "theirs" side is empty/malformed such that the correct `=======`/`>>>>>>>` pairing is ambiguous, or a diff3-style conflict where `|||||||` base content itself contains a `=======`-shaped line before the true separator.) Given the code's look-ahead only records "did we ever see `=======`" and "first `>>>>>>>`" without validating single occurrence, embedding either marker shape anywhere between the real `<<<<<<<` and its true `>>>>>>>` (e.g. inside the "ours" or "base" text of a diff3 conflict) reliably makes `hasSeparator`/`closingIndex` latch onto the wrong line.
3. Trigger merge/rebase in Desktop, invoke "Resolve with Copilot", and click "Continue Merge".
4. Observe that `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) computes an incorrect `closingIndex`, causing lines between the true conflict and the false marker to be dropped when the reassembled content is written via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staged (`app/src/lib/stores/app-store.ts:7258-7264`), producing a committed file missing content the user never intended to change.
