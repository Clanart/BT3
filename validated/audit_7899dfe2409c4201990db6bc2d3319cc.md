### Title
Externally-sent outputs misclassified as internal `OutputType::Branch`/`Change`/`Forwarded` via deterministic offset addresses - (File: networks/bitcoin/src/wallet/mod.rs, processor/src/networks/bitcoin.rs)

### Summary
The GitLab CVE-2019-15594 bug class is "resources of a restricted type returned through an endpoint meant for another type". In Serai's Bitcoin scanner, `Scanner::scan_transaction` attributes any on-chain output to an internal `OutputType` purely by matching `script_pubkey`, while the Branch/Change/Forwarded addresses are derived from the group key via public, deterministic `hash_to_F` offsets. Any unprivileged party can compute these internal-only addresses and send funds to them, causing the processor to report externally-originated funds as internal output kinds — an unauthorized party reaching a restricted classification through a public input (a Bitcoin transaction they send).

### Finding Description
`Scanner::scan_transaction` matches outputs solely on `output.script_pubkey` against `self.scripts`, returning a `ReceivedOutput` carrying the registered offset [1](#0-0) . The offset set is fixed: `Scalar::ZERO` (External) plus three deterministic offsets `Secp256k1::hash_to_F(KEY_DST, b"branch")`, `b"change"`, `b"forward"` registered in `scanner()` [2](#0-1) . Since `KEY_DST` and the labels are constants in the source, anyone can compute `key + G*offset` and the corresponding P2TR script for every multisig group key (which is public).

`get_outputs` then maps the scanned offset back to `OutputType` via `kinds[offset_repr_ref]` and yields an `Output` with `kind == Branch/Change/Forwarded` even though the sender is external [3](#0-2) . The block scanner accepts any output with `balance >= N::DUST` and emits it as a received output [4](#0-3) .

### Impact Explanation
Output kinds gate downstream semantics: `OutputType::External` carries `data`/`presumed_origin` for crediting depositor intents, while Branch/Change/Forwarded are reserved for protocol-internal flows (own-multisig sends, change). An attacker who sends ≥ dust to the derived change/branch address produces an output the processor treats as internal:

- Funds are "received" under a kind that assumes the protocol itself created them, which can confuse accounting and UTXO scheduling (change outputs are presumed protocol-owned; an attacker-injected `Change`/`Branch` output is indistinguishable from real change).
- `presumed_origin` is populated from `tx.input[0]` of the attacker's funding tx, so attacker-controlled metadata is attached to an internal-kind output [5](#0-4) .

This mirrors the CVE: data belonging to a restricted category (internal output kinds) is obtainable/creatable through an unrestricted channel (anyone broadcasting a Bitcoin transaction), because the classification check only validates a publicly derivable script, not provenance.

### Likelihood Explanation
The attack requires only knowledge of the group key (public) and the ability to send a Bitcoin transaction — no collusion, no validator access, no malformed encodings. The offsets are deterministic constants, so the internal addresses are computable offline. Cost is one transaction plus ≥ `N::DUST` sats. It is fully reachable by an unprivileged party per the scope rules.

### Recommendation
Do not assign `OutputType` purely from the matched script_pubkey offset for externally-originated transactions. Options:

- Restrict `Branch`/`Change`/`Forwarded` classification to outputs in transactions the multisig itself signed/scheduled (e.g., only classify a scanned output as internal if the tx is a known protocol transaction, otherwise treat as `External` or ignore).
- Alternatively, make internal address derivation include a secret/unpredictable component, or at minimum document that sending to internal-kind addresses is unsupported and must be filtered at a higher layer.
