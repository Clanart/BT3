### Title
Ignored error from `MsgEVMTransaction.AsTransaction()` causes nil-pointer dereference in EVM ante `BasicDecorator` - (File: `x/evm/ante/basic.go`)

### Summary
`BasicDecorator.AnteHandle` calls `msg.AsTransaction()` and discards the returned error, then immediately dereferences the returned `*ethtypes.Transaction` pointer. `AsTransaction()` returns `(nil, nil)` whenever `UnpackTxData` fails, which is the same failure-swallowing pattern as the reported kernel bug where `devm_kasprintf()`'s possible `NULL` return was not checked before use.

### Finding Description
`MsgEVMTransaction.AsTransaction()` unpacks the `Any`-wrapped tx data and, on failure, silently returns `nil` for the transaction pointer instead of propagating the error to the caller: [1](#0-0) 

`BasicDecorator.AnteHandle`, the first EVM-specific ante decorator that runs on every submitted EVM transaction, calls this exact method and discards the error with `_`: [2](#0-1) 

It then dereferences the (possibly `nil`) `etx` multiple times without any nil check — `etx.Nonce()`, `etx.To()`, `etx.Data()`, `etx.Value()`, `etx.AccessList()`, `etx.Gas()`, `etx.Type()`: [3](#0-2) 

If `UnpackTxData` ever fails at this point in the pipeline (e.g. any code path where a `MsgEVMTransaction` reaches `BasicDecorator.AnteHandle` before its `Data` `Any` has been successfully unpacked/cached — for instance simulate/recheck paths, or any decorator-ordering change that lets `BasicDecorator` run ahead of the decoding/preprocessing decorators in `x/evm/ante/preprocess.go`), `etx` is `nil` and the very next dereference panics.

### Impact Explanation
A panic inside the ante handler pipeline is executed by every full/validator node processing the transaction (CheckTx, ReCheckTx, and DeliverTx paths), so a reachable nil dereference here could crash node processes, causing block-production delay or validator halt — the same class of impact (`crash`) called out in the report, mapped onto this codebase's public transaction-submission surface (`EVM ante pipeline`).

### Likelihood Explanation
Likelihood is Medium rather than High: under normal conditions the `Any` in `msg.Data` should already be unpacked successfully earlier in the decoding/ante pipeline (`x/evm/ante/preprocess.go` also calls `UnpackTxData`), which is presumably why the error is currently ignored in `basic.go`. I could not fully confirm, given the available index, that `BasicDecorator` is *always* guaranteed to run strictly after every decoder that would already reject an unparsable `MsgEVMTransaction`, nor whether `simulate`/`ReCheckTx` code paths can invoke `AnteHandle` with a not-yet-cached `Any`. This uncertainty should be resolved with a full trace of the ante decorator ordering in `app/ante.go` and of `x/evm/ante/preprocess.go` before treating this as certainly exploitable end-to-end.

### Recommendation
Check the error returned by `msg.AsTransaction()` in `BasicDecorator.AnteHandle` (and any other ante/keeper caller that discards it) and return a proper `sdk.Context, error` instead of proceeding to dereference a possibly-`nil` transaction, mirroring the upstream kernel fix of adding an explicit `NULL`/error check before use.

### Proof of Concept
Conceptual PoC (requires confirming reachability per the Likelihood section):
1. Craft a `MsgEVMTransaction` whose `Data` field is an `Any` with a `TypeURL` that is registered in the codec but whose payload cannot be decoded into a valid `ethtx.TxData` (or otherwise causes `UnpackTxData` to return an error) at the moment `BasicDecorator.AnteHandle` executes.
2. Submit this transaction through any path that reaches `BasicDecorator.AnteHandle` without a prior successful `UnpackTxData` call caching the value on the `Any` (e.g., simulate/ReCheckTx call path).
3. `msg.AsTransaction()` returns `(nil, nil)`; the subsequent `etx.Nonce()` call panics with a nil-pointer dereference, crashing the node's tx-processing goroutine.
