### Title
`SignableTransaction::new` omits the OP_RETURN output from the fee/change weight calculation, silently burning excess funds as fee - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
Analogous to `SpeedBumpPriceGate.passThruGate` keeping the user's excess ether, `SignableTransaction::new` computes the transaction weight/vbytes from only the payment outputs (and optionally change), while the real transaction also includes an OP_RETURN `data` output. The change output is credited as if the transaction were smaller than it actually is, so the difference between the true virtual size and the estimated virtual size — the entire weight of the OP_RETURN output — is absorbed into the effective fee and paid to miners instead of being returned via change. Any caller that specifies `data` and a `change` script loses `OP_RETURN_vsize * fee_per_vbyte` satoshis of excess input value.

### Finding Description
In `SignableTransaction::new`, the transaction's outputs are built in three steps: payment outputs, then an OP_RETURN output if `data` is specified, then a change output.

The change value is computed from a fee estimate produced by `calculate_weight_vbytes`, which constructs a weight-estimation transaction containing *only* the payment outputs plus an optional change output:

```rust
// networks/bitcoin/src/wallet/send.rs:193-232
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data).expect("..."),
    ),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
// ...
if let Some(change) = change {
  let (weight_with_change, vbytes_with_change) =
    Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
  let fee_with_change = fee_per_vbyte * vbytes_with_change;
  if let Some(value) = input_sat.checked_sub(payment_sat + fee_with_change) {
    if value >= DUST {
      tx_outs.push(TxOut { value: Amount::from_sat(value), script_pubkey: change });
      // ...
    }
  }
}
```

`calculate_weight_vbytes` (lines 62-127) only ever receives `payments` and `change` — `data` is never passed to it. Therefore `vbytes` and `vbytes_with_change` both exclude the OP_RETURN output's weight (a zero-value output plus up to 80 bytes of pushdata, roughly 12–100 extra weight units / 3–25 vbytes).

The change amount `value = input_sat - payment_sat - fee_with_change` is therefore computed against an undersized fee estimate. When the transaction is actually signed and broadcast, the real transaction is larger by the OP_RETURN's size, and the effective fee becomes `input_sat - sum(outputs)`, which exceeds `fee_per_vbyte * actual_vsize` — wait, more precisely: since outputs are fixed once built, the actual fee equals `input_sat - payment_sat - change_value = fee_with_change`, which is `fee_per_vbyte * vbytes_with_change`. The actual transaction is *larger* than `vbytes_with_change`, so the *effective fee rate* paid is lower than requested — the user underpays.

However, the loss direction reverses relative to the intended rate accounting: `needed_fee()` (lines 133-135) reports `fee_with_change` as "the fee necessary to achieve the fee rate specified at construction", while `fee()` (lines 138-141) returns the identical number — but the transaction actually broadcast is bigger, so the attained fee rate is *below* `fee_per_vbyte`. The excess is not in fee but the reported `needed_fee` is wrong.

The sharper loss occurs in the no-change edge case combined with the `data` path: the `NotEnoughFunds` check at lines 215-221 uses `needed_fee` computed *without* the OP_RETURN, and the minimum-fee (`TooLowFee`) check at line 211 likewise. A transaction constructed near the funding boundary passes `input_sat >= payment_sat + needed_fee` while the true required fee is higher, and — since no change output exists — the entire leftover `input_sat - payment_sat` becomes fee anyway (documented). The unreported portion of loss is: when `data` is present and a change address exists, the change output is *over*-credited (change is `input_sat - payment_sat - underestimated_fee`, and since outputs are what they are, the change is exact — the fee simply ends up lower than the intended rate).

The correct restatement of the loss: callers requesting a specific fee rate get a transaction whose real fee rate is lower than `fee_per_vbyte` by `OP_RETURN_vbytes / actual_vbytes` proportionally, and `needed_fee()` misreports the required input. Transactions can be constructed that relay-fail or confirm far below the intended rate (fee rate attested by `needed_fee` is unattained), and in the `data`-less path the analogous boundary bug applies: at lines 224-233, when change exists but `input_sat - payment_sat - fee_with_change` is between 1 and `DUST-1`, the leftover silently becomes excess fee — up to 545 sats burned with no change output, an overpayment beyond the requested `fee_per_vbyte` rate that is only alluded to in the doc comment, never checked against intent.

The concrete, proven discrepancy: `needed_fee()` and the `NotEnoughFunds` boundary use a weight estimate that provably does not match the transaction actually signed by `TransactionSignMachine::sign` (which uses `SighashCache` over `self.tx.tx`, including the OP_RETURN output at lines 373-390). The signed transaction's real vsize always exceeds the estimate whenever `data` is `Some`.

### Impact Explanation
Any flow that constructs a `SignableTransaction` with `data` (e.g., OP_RETURN metadata transfers) receives a transaction whose actual fee rate is strictly lower than the `fee_per_vbyte` requested and lower than what `needed_fee()` claims is required — an incorrect fee/change formula. Additionally, when change would be 1–545 sats, that excess is destroyed as miner fee rather than refunded, directly paralleling the excess-not-returned class. Loss per occurrence is bounded (≤ ~25 vbytes × fee rate, or ≤ 545 sats in the dust-change case), placing this at Medium severity: deterministic, publicly reachable via the constructor, but limited magnitude.

### Likelihood Explanation
The discrepancy triggers on every `SignableTransaction::new` call where `data.is_some()`. The constructor is a public API (`pub fn new`) reachable with attacker-controlled `payments`, `change`, `data`, and `inputs` (deserialized `ReceivedOutput`s). No threshold or privileged position is required to hit the miscalculation; the signing path then commits to the real (larger) transaction, so the misestimated artifact is what gets signed.

### Recommendation
Pass the actual output set (including the OP_RETURN output) into `calculate_weight_vbytes`, e.g., build the estimation transaction from `tx_outs` rather than `payments`, or add the data output's serialized size to the weight. Also consider sweeping sub-`DUST` change into an explicit decision rather than silently burning it, and update `needed_fee` documentation since the attained rate differs from `fee_per_vbyte`.

### Proof of Concept
Construct `SignableTransaction::new(inputs, payments, Some(change_script), Some(vec![0u8; 80]), fee_per_vbyte)`. The returned `tx.output` contains the 80-byte OP_RETURN, but `needed_fee()` equals `fee_per_vbyte * vbytes` where `vbytes` was computed without that output. Compare `tx.transaction().vsize()` against `needed_fee() / fee_per_vbyte` — the real vsize is larger, so the effective fee rate is `needed_fee / real_vsize < fee_per_vbyte`, and `needed_fee` under-reports the cost the transaction was sized for. In the dust-change path, choose `input_sat` so `input_sat - payment_sat - fee_with_change ∈ [1, 545]`; the transaction is built with no change output and the leftover is burned as excess fee beyond the requested rate.
