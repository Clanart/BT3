## Title
Expanding a diff hunk silently re-includes/excludes lines the user explicitly (de)selected, corrupting partial commits - (File: `app/src/ui/diff/text-diff-expansion.ts`)

## Summary
`expandTextDiffHunk()` (used when the user clicks "Expand up/down" on a diff hunk) inserts new context lines *inside* the existing hunk's `lines` array without ever touching or remapping the `DiffSelection` that tracks per-line include/exclude state by absolute index. When expanding **up**, the new lines are spliced in before the pre-existing lines, which shifts every pre-existing line's absolute index by the number of inserted lines. The `DiffSelection`'s `divergingLines` set, however, still holds the *old* indices, so after expansion the user's explicit selection silently attaches to the wrong lines (typically snapping back to the diff's default selection state) rather than to the line the user actually toggled.

## Finding Description
`DiffSelection` tracks only the lines that diverge from a default ("all selected" or "none selected") state, keyed by absolute unified-diff line index: [1](#0-0) 

`expandTextDiffHunk()` computes `numberOfLinesToAdd` and, for an "up" expansion, builds the new hunk lines as `[newDiffHunkLine, ...newLineDiffs, ...allHunkLinesButFirst]` — i.e. the newly generated context lines are inserted *before* the file's pre-existing lines within the same hunk: [2](#0-1) [3](#0-2) 

Because `DiffSelection.isSelected()`/`isSelectable()` key off of `hunk.unifiedDiffStart + <position within hunk.lines>`, every pre-existing line inside the expanded hunk now resolves to a **different absolute index** (`oldIndex + numberOfLinesToAdd`) than it had before expansion, while `hunks[i+1..]` (`followingHunks`) are the only entries whose `unifiedDiffStart`/`unifiedDiffEnd` are explicitly bumped by `numberOfNewDiffLines`: [4](#0-3) 

Nowhere in `expandHunk()` (the UI call site) or `expandTextDiffHunk()` is the caller's `DiffSelection` re-derived or shifted to match the new indices — the component simply swaps in the new `diff` object and keeps the old selection prop untouched: [5](#0-4) 

The only place selection state is reconciled against a changed diff is `_loadStatus`-style refresh in `app-store.ts`, which recomputes `selectableLines` when a *new diff is fetched from git* — not when the diff is expanded client-side via `expandTextDiffHunk` (see the `withSelectableLines` call sites, none of which are invoked from the expand-hunk code path). This means an expand-up (and, more subtly, expand-down/merge scenarios that shift trailing hunks) leaves the `divergingLines` set stale relative to the new line layout.

Concretely: if the default selection is `All` and the user unchecks (deselects) one specific added/removed line so that its index is added to `divergingLines`, then expands the *same* hunk upward, that line's absolute index increases by `numberOfLinesToAdd`. `isSelected()` for the new index finds nothing in `divergingLines` and falls back to the default (`All` ⇒ selected). The line the user deliberately excluded from the commit is **silently re-selected**, and `applyPatchToIndex`/`formatPatch` will stage/commit it anyway: [6](#0-5) [7](#0-6) 

The reverse also happens: a line the user explicitly *selected* (diverging from a `None` default) can silently become *unselected* after expansion, dropping intended content from the commit.

## Impact Explanation
This is a silent-corruption-of-what-the-user-commits bug: the working directory diff (which can originate from a crafted/malicious file whose changes are structured to invite context expansion, e.g. long context runs adjacent to a sensitive line) causes the app to stage content the user explicitly opted out of, or to drop content they opted into, without any warning. No confirmation dialog reflects the true patch that will be applied. Since the commit is created from `file.selection.isSelected(absoluteIndex)` at apply-patch time, the corrupted selection directly determines the bytes written to the git object database and eventually pushed.

## Likelihood Explanation
This triggers on ordinary, expected user interaction (reviewing a large diff and clicking "Expand" on a hunk after individually toggling one or more lines within that hunk) — no special privileges or local access are required, and the only "attacker" precondition is a repository/file whose diff naturally has hunks that a reviewer would want to expand near a line they've deselected. This is a normal workflow (partial commit / discard-selection review) rather than a contrived path, making the likelihood of accidental triggering reasonably high, though it requires that the user perform a partial selection before expanding.

## Recommendation
When `expandTextDiffHunk` (or the merge path in the same function) shifts line positions within a hunk or shifts subsequent hunks, remap the caller's `DiffSelection` accordingly:
- Compute the index delta introduced by the expansion/merge for each affected line, and produce a new `DiffSelection` (e.g. via a `shiftLines(fromIndex, delta)`-style transform) alongside the new `ITextDiff`.
- Alternatively, recompute `selectableLines`/`divergingLines` purely from the new hunk layout mapped back to original line identity (e.g. by old/new line number rather than positional index) so a line's selection state travels with the line itself, not its transient index.
- Add regression tests mirroring `text-diff-expansion-test.ts` that assert selection state (not just hunk headers) is preserved for specific lines across `expandTextDiffHunk` calls, especially for "up" expansions and hunk merges.

## Proof of Concept
1. Working directory has a modified file producing a diff with a single hunk containing, say, 10 changed lines, with `DiffHunkExpansionType.Up` available (i.e., there's collapsed context above it).
2. In Desktop's Changes view, deselect one specific changed line inside that hunk (this adds its absolute index to `DiffSelection.divergingLines`).
3. Click "Expand" to expand the hunk **up** by the default step (`DefaultDiffExpansionStep = 20`, see `app/src/ui/diff/text-diff-expansion.ts:13`).
4. `expandTextDiffHunk` inserts `numberOfLinesToAdd` new context lines before the existing lines in that hunk; the previously-deselected line's absolute index shifts by `numberOfLinesToAdd`, but `DiffSelection.divergingLines` still contains the old index.
5. Re-open the "Commit" panel: the previously deselected line now shows as selected (or the commit is created via `createCommit`/`applyPatchToIndex` including that line), even though the user never re-checked it — confirmable by inspecting `formatPatch()` output for the file before vs. after the expand action using the same `DiffSelection` object.

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
