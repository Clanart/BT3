### Title
Silent no-op block rules via unvalidated `Condition.field` in explicit `conditions` frontmatter - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Condition.from_dict` defaults `field` to an empty string when the explicit `conditions:` frontmatter list omits or misnames the `field` key, unlike the legacy `pattern:` path, which always infers a valid field from `event`. Because `RuleEngine._extract_field` returns `None` for any unrecognized/empty field, such a condition can never match, causing a rule that looks like an enforced `action: block` rule to silently never fire.

### Finding Description
`Rule.from_dict` supports two mutually exclusive styles: explicit `conditions:` and legacy `pattern:`. [1](#0-0) 
For the legacy path, `field` is always deterministically inferred from `event` (`bash`→`command`, `file`→`new_text`, else `content`), guaranteeing a working condition.
For the explicit `conditions` path, each item is passed to `Condition.from_dict`, which silently defaults `field` to `''` if the key is missing or misspelled: [2](#0-1) 
`RuleEngine._extract_field` has no case that matches an empty or unrecognized field name and falls through to `return None`, and `_check_condition` treats `None` as a non-match: [3](#0-2) [4](#0-3) 
No warning, error, or validation is raised anywhere in `load_rule_file`/`load_rules` for an invalid/empty `field`; the rule loads successfully and appears in the rule list with `enabled: true` and `action: block`, but it can never match, so `blocking_rules` in `evaluate_rules` never includes it. A repo-shipped `hookify.*.local.md` file (attacker-controlled repository content) or a rule generated via `/hookify` (whose frontmatter could be steered by injected instructions in the analyzed conversation/repo) can therefore ship a rule whose `message` and `name` imply active enforcement (e.g. "Block writes to .env") while the `conditions` entry quietly omits/misnames `field`, making the block permanently inert.

### Impact Explanation
A user relying on such a rule believes dangerous operations (e.g., writing to `.env`, running `rm -rf`, editing secrets) are blocked, when in fact the rule never triggers. This allows unauthorized file writes/reads to proceed unblocked, i.e., unauthorized file read or write outside the intended enforcement scope — matching the stated Immunefi impact category. It is a silent weakening of enforcement, not merely a broadened match (there's no case where omitting `field` causes over-matching), so the "weaken enforcement" half of the invariant is violated while "broaden scope" is not demonstrated.

### Likelihood Explanation
This requires the attacker to influence the content of a `hookify.*.local.md` rule file — either by shipping one directly in a repository the user opens with Claude Code, or by manipulating `/hookify`-driven generation (e.g. via prompt injection in repository content processed during rule authoring). No admin/maintainer privilege, leaked keys, or social engineering beyond ordinary repo content is needed, consistent with the stated attacker model. The flaw is deterministic and trivially reproducible: any `conditions:` entry lacking a valid `field` key is silently a permanent non-match.

### Recommendation
In `Condition.from_dict`, reject or raise on missing/unknown `field` values instead of defaulting to `''`; validate `field` against the known set of recognized field names (`command`, `new_text`, `old_text`, `file_path`, `content`, `reason`, `transcript`, `user_prompt`, etc.) at load time. `load_rule_file`/`load_rules` should treat a rule with an unmatchable condition as invalid and log a loud, explicit warning (not swallow it as a normal "no match"), especially for `action: block` rules, so silently-inert block rules cannot pass as active protections.

### Proof of Concept
Unit test in `plugins/hookify/core/config_loader.py` / `rule_engine.py` test harness:
1. Construct frontmatter:
```yaml
name: block-env-write
enabled: true
event: file
action: block
conditions:
  - operator: contains
    pattern: SECRET
```
(no `field` key).
2. `Rule.from_dict(frontmatter, "Blocking secret write")` → assert `rule.conditions[0].field == ''`.
3. Build `input_data = {"tool_name": "Write", "tool_input": {"file_path": ".env", "content": "SECRET=abc"}}`.
4. Call `RuleEngine().evaluate_rules([rule], input_data)` → assert result is `{}` (no block), even though the intent of the rule (block writes containing `SECRET`) is clearly not enforced.
5. Compare against an equivalent legacy-style rule using `pattern: "SECRET"` with `event: file`, which correctly infers `field='new_text'`/`content` and blocks — demonstrating the differential between the two parsing paths and the resulting bypass.

    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields
            if field == 'reason':
                return input_data.get('reason', '')
            elif field == 'transcript':
                # Read transcript file if path provided
                transcript_path = input_data.get('transcript_path')
                if transcript_path:
                    try:
                        with open(transcript_path, 'r') as f:
                            return f.read()
                    except FileNotFoundError:
                        print(f"Warning: Transcript file not found: {transcript_path}", file=sys.stderr)
                        return ''
                    except PermissionError:
                        print(f"Warning: Permission denied reading transcript: {transcript_path}", file=sys.stderr)
                        return ''
                    except (IOError, OSError) as e:
                        print(f"Warning: Error reading transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')

        # Handle special cases by tool type
        if tool_name == 'Bash':
            if field == 'command':
                return tool_input.get('command', '')

        elif tool_name in ['Write', 'Edit']:
            if field == 'content':
                # Write uses 'content', Edit has 'new_string'
                return tool_input.get('content') or tool_input.get('new_string', '')
            elif field == 'new_text' or field == 'new_string':
                return tool_input.get('new_string', '')
            elif field == 'old_text' or field == 'old_string':
                return tool_input.get('old_string', '')
            elif field == 'file_path':
                return tool_input.get('file_path', '')

        elif tool_name == 'MultiEdit':
            if field == 'file_path':
                return tool_input.get('file_path', '')
            elif field in ['new_text', 'content']:
                # Concatenate all edits
                edits = tool_input.get('edits', [])
                return ' '.join(e.get('new_string', '') for e in edits)

        return None
