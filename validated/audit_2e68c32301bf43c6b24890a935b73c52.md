### Title
Coinbase outputs are reported as spendable before maturity - ([File: networks/bitcoin/src/wallet/mod.rs](crypto/frost/src/sign.rs))

### Summary
`Scanner::scan_block` scans every transaction in a block, including the coinbase transaction, and returns matching outputs as ordinary `ReceivedOutput` values without tracking maturity. [1](#0-0) 

### Finding Description
`scan_block` iterates over `block.txdata` without excluding `block.txdata[0]` or checking whether a transaction is a coinbase. [2](#0-1)  Each matching transaction output is converted directly into a `ReceivedOutput` carrying its value, offset, and outpoint. [3](#0-2)  The resulting value is exposed through `ReceivedOutput::value`, with no distinction between mature and immature funds. [4](#0-3) 

Bitcoin coinbase outputs cannot be spent until they reach coinbase maturity, but `scan_block` reports them through the same type used for normally spendable UTXOs. [5](#0-4)  The source comment acknowledges that a post-processing pass is required, but the API itself still returns the immature output as received value. [6](#0-5) 

### Impact Explanation
A miner can send coinbase proceeds to a scanner-controlled address and cause Serai to account for value that cannot yet be spent. If consumers treat the returned `ReceivedOutput` list as available inputs, they may overstate immediately spendable balance, select an invalid input, or produce a transaction that cannot be relayed or confirmed. [5](#0-4) 

This is analogous to valuing an asset at principal while ignoring that part of the principal is already claimable or unavailable under the asset’s redemption rules: the scanner records nominal output value without accounting for its current spendability. [3](#0-2) 

### Likelihood Explanation
Any valid block containing a coinbase output to a watched script triggers the behavior. The coinbase position in `block.txdata[0]` is deterministic, and the implementation explicitly scans it along with all later transactions. [2](#0-1)  The impact is Medium rather than High because the funds generally become spendable after maturity unless the affected chain is reorganized before then.

### Recommendation
Do not include coinbase transactions in the normal spendable-output result. Either change `scan_block` to scan only `block.txdata[1 ..]`, or return coinbase-derived outputs separately with their maturity height so callers cannot confuse them with spendable UTXOs. If coinbase outputs are retained for accounting, their `ReceivedOutput` representation should carry maturity state and transaction construction should reject them until mature. [1](#0-0) 

### Proof of Concept
For any block `block` where `block.txdata[0].is_coinbase()` and its first output pays to `p2tr_script_buf(key)`, the following occurs:

```rust
let scanner = Scanner::new(key).unwrap();
let outputs = scanner.scan_block(&block);

// Contains the immature coinbase output even though it cannot be spent yet.
assert_eq!(outputs[0].outpoint(), &OutPoint::new(block.txdata[0].compute_txid(), 0));
assert_eq!(outputs[0].value(), block.txdata[0].output[0].value.to_sat());
```

The output is returned because `scan_transaction` matches only `output.script_pubkey` and constructs a `ReceivedOutput`; no maturity test is applied before the result is emitted. [3](#0-2)

  /// Scan a transaction.
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
