### Title
Empty aggregate signature trivially verifies in `SchnorrAggregate::verify` - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate` implements the half-aggregation scheme from eprint 2021/350. Its `read` function accepts an attacker-controlled `u32` count of nonces `Rs`, and its `verify` function only checks `self.Rs.len() == keys_and_challenges.len()` before evaluating a single multiexp. When an attacker supplies a count of `0` and the verifier is called with an empty `keys_and_challenges` slice, the check degenerates to `-s·G == 0`, which passes for `s = 0`. The bug class of the external report — a parser accepting structurally degenerate input that the consumer mishandles — maps here to a deserializer that accepts a zero-element statement and a verifier that accepts it as a valid aggregate signature.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::read` reads a `u32` length and then that many `C::G` points plus one scalar:

```rust
// crypto/schnorr/src/aggregate.rs:77-88
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;
  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }
  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

`verify` then does:

```rust
// crypto/schnorr/src/aggregate.rs:127-146
if self.Rs.len() != keys_and_challenges.len() {
  return false;
}
...
let mut pairs = Vec::with_capacity((2 * keys_and_challenges.len()) + 1);
for (i, (key, challenge)) in keys_and_challenges.iter().enumerate() {
  let z = weight(&mut digest);
  pairs.push((z, self.Rs[i]));
  pairs.push((z * challenge, *key));
}
pairs.push((-self.s, C::generator()));
multiexp_vartime(&pairs).is_identity().into()
```

There is no lower bound on the statement count. With `keys_and_challenges == &[]`, `Rs == []`, and `s == C::F::ZERO`, `pairs` contains only `(0, G)`, whose multiexp is the identity, so `verify` returns `true`. Additionally, because `z = weight(&mut digest)` is drawn per statement but the digest commits only to challenges, an empty aggregate carries no key binding at all, so the "signature" verifies regardless of the domain-separation tag.

### Impact Explanation
An unprivileged party can craft a 37-byte encoding (`0x00000000` length prefix followed by the encoding of scalar zero) which deserializes via `SchnorrAggregate::read` and passes `verify` for any `dst` when evaluated against an empty key/challenge list. This is a forged signature accepted by the verifier: the verifier formula degenerates to `0·G == 0` and no public key is ever bound. Any in-scope consumer that invokes `verify` on attacker-supplied aggregates where the number of expected signers can be attacker-influenced to zero (e.g., an empty validator/confirmation set produced by attacker-controlled input) accepts a forgery produced with zero secret knowledge. More generally, this is an incorrect verifier formula: the scheme's soundness requires at least one statement; the code never enforces it.

### Likelihood Explanation
The deserialize path is fully attacker-controlled (`SchnorrAggregate::read` reads untrusted bytes with no validation of the count), and the verify path performs no emptiness check. Exploitation requires a caller to aggregate-verify zero statements — an edge case that arises whenever the statement set is derived from external input that can be empty — rather than any cryptographic weakness, malicious validator, or leaked key. Since neither `read` nor `verify` rejects the degenerate case, the forgery is deterministic and free to produce.

### Recommendation
Reject zero-length aggregates at both layers:

- In `SchnorrAggregate::read`, error when `u32::from_le_bytes(len) == 0`.
- In `SchnorrAggregate::verify`, return `false` when `self.Rs.is_empty()` (or when `keys_and_challenges.is_empty()`), and optionally reject identity points in `Rs` and non-canonical inputs.

### Proof of Concept
```rust
// PoC: forged empty aggregate verifies
use ciphersuite::{Ciphersuite, Secp256k1, group::ff::Field};
use schnorr::aggregate::SchnorrAggregate;

fn poc() {
  // Attacker-crafted bytes: 0 nonces, s = 0
  let mut bytes = 0u32.to_le_bytes().to_vec();
  bytes.extend(<Secp256k1 as Ciphersuite>::F::ZERO.to_repr().as_ref());

  let agg = SchnorrAggregate::<Secp256k1>::read(&mut bytes.as_slice()).unwrap();
  assert!(agg.Rs().is_empty());

  // Verifier invoked with an empty statement set accepts the forgery
  assert!(agg.verify(b"any domain separator", &[]));
}
```

Uncertainty note: whether any in-scope production caller actually calls `SchnorrAggregate::verify` with an attacker-influenceable-to-empty statement list could not be fully confirmed (its observed usage is in `coordinator/tributary`, which is out of scope). The verifier-formula defect itself is concrete and fully demonstrated above; its severity depends on downstream call sites treating an empty signer set as meaningful.
