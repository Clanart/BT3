### Title
Stale cached GitHub repository permissions/association are never revoked, causing branch-protection warnings to be silently skipped after write access is removed - (File: `app/src/lib/stores/repositories-store.ts`, `app/src/models/github-repository.ts`)

### Summary
The audited bug is a "revocation gap": a delegation record set by `stake()` is never cleared by `withdraw()`, so a stale privileged reference (delegatee) keeps producing rewards/voting power after the underlying balance is gone. GitHub Desktop has the same *class* of bug in how it caches a local repository's association with a `GitHubRepository` and that repository's cached `permissions` field: once granted, this state is persisted locally and is **never actively revoked**, only conditionally overwritten, and it is explicitly documented as a known gap.

### Finding Description
`RepositoriesStore._upsertGitHubRepository` computes the permission to persist as: [1](#0-0) 
i.e. `getPermissionsString(newApiRepo) ?? existingRepo?.permissions ?? undefined` — if the freshly fetched API object does not carry a `permissions` field (which happens for parent/fork lookups via `upsertGitHubRepositoryLight`/`ignoreParent`, see the surrounding comment), the **previously cached** permission (e.g. `'write'` or `'admin'`) is kept indefinitely.

That cached value feeds `hasWritePermission()`: [2](#0-1) 
which fails "open" (`permissions === null` → treated as writable) and is used to *skip* the remote branch-protection API call entirely: [3](#0-2) 

Separately, `repositoryWithRefreshedGitHubRepository` documents that the association between a local repo and its `GitHubRepository` record is **never cleared** once `matchGitHubRepository` fails to find a match, only refreshed opportunistically: [4](#0-3) 

So exactly like the smart-contract case (delegation checkpoint persists after balance drops to zero), Desktop persists a "permission checkpoint" (`GitHubRepository.permissions`) and a repository↔GitHub-repo "delegation" that are not actively invalidated when the underlying grant is revoked (e.g., user removed as a collaborator, repo made private/renamed) — they only get corrected the next time a *full* API fetch happens to return an explicit `permissions` object.

### Impact Explanation
When `hasWritePermission()` incorrectly reports `true` for a repository the user no longer has write access to, `refreshBranchProtectionState` skips fetching real branch-protection/push-control state and clears the local "protected" warning: [5](#0-4) 
This can cause Desktop to silently omit protected-branch/commit-signing/repo-rule warnings in the commit UI, letting a user attempt to commit/push believing the branch is unprotected when it is not. This matches the "silent corruption of what the user commits or pushes" impact class — the local safety net Desktop is supposed to show is bypassed because of stale cached state, not because the user did anything unusual. It does **not** grant actual push rights (GitHub's server still enforces real permissions), so the impact is confined to Desktop's client-side warning/guard logic, not privilege escalation on GitHub itself.

### Likelihood Explanation
This is reachable through completely ordinary, non-malicious-input flows: any user who is demoted from write/admin to read (or removed) on a repository they already have open in Desktop, combined with any subsequent refresh path that upserts the repo without a full `permissions` payload (fork/parent resolution, pull-request repo upsert via `upsertGitHubRepositoryLight`, etc.), will retain the stale `'write'`/`'admin'` permission value in the local Dexie database indefinitely, as documented by the code's own comments. This requires no attacker-crafted repository content and no local/admin access — only normal use over time (permission changes are common in shared repos).

### Recommendation
- When upserting a `GitHubRepository`, do not silently fall back to the previously cached `permissions` value when the API response's `permissions` field is `undefined` for a repository the user is a primary (non-parent) member of; explicitly re-fetch full permission info before reusing stale data.
- Change `hasWritePermission()`'s "unknown → assume writable" default so it does not suppress protected-branch checks; instead, treat unknown as "verify" (make the API call) rather than "skip".
- Track and periodically force-revalidate stored repository/GitHub-repository associations rather than relying solely on the "never clear" fallback called out in the `TODO` at `app/src/lib/stores/app-store.ts:4880-4882`.

### Proof of Concept
1. Sign in to Desktop as User A with write access to `org/repo`; open the repository in Desktop so `RepositoriesStore` persists `permissions: 'write'` in its Dexie database via `_upsertGitHubRepository`.
2. Repo owner removes User A's write access (demotes to read) on GitHub.
3. In Desktop, trigger a code path that upserts `org/repo`'s `GitHubRepository` record without a full `permissions` payload — e.g. opening a PR list (which upserts head/base repos via `upsertRepo`/`upsertGitHubRepositoryLight`) or refreshing a fork's parent repo (`ignoreParent` path in `_upsertGitHubRepository`).
4. Because `getPermissionsString(...)` returns `undefined` for these payloads, `existingRepo?.permissions` ('write') is kept: `app/src/lib/stores/repositories-store.ts:627-630`.
5. Back in the repository, `refreshBranchProtectionState` calls `hasWritePermission(gitHubRepo)`, which returns `true` from the stale cached value, and Desktop clears/skips the branch-protection warning instead of calling `fetchPushControl` to get the real (now restricted) state: `app/src/lib/stores/app-store.ts:1501-1515`.
6. User A commits assuming the branch is unprotected; the actual push will be rejected by GitHub, but Desktop's local UI has silently misrepresented the protection state due to the un-revoked cached permission.

/**
 * Can the user push to this GitHub repository?
 *
 * (If their permissions are unknown, we assume they can.)
 */
export function hasWritePermission(
  gitHubRepository: GitHubRepository
): boolean {
  return (
    gitHubRepository.permissions === null ||
    gitHubRepository.permissions !== 'read'
  )
}
