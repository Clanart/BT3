### Title
Deserialized `ThresholdKeys` never verify the secret share against its verification share, letting attacker-supplied bytes define an inconsistent/incoherent threshold key - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` reconstructs a full threshold key (parameters, interpolation polynomial, secret share, and all verification shares) entirely from a byte stream. `ThresholdKeys::new`, which it calls, computes `group_key` by interpolating `verification_shares[1..=t]` but never checks that the provided `secret_share` is consistent with `verification_shares[i]` (i.e., that `G * secret_share == verification_shares[i]`), nor that the verification shares interpolate to a coherent polynomial under the supplied `Interpolation` — including `Interpolation::Constant`, whose coefficients are read verbatim from the same untrusted bytes.

### Finding Description
- `ThresholdKeys::read` parses `t`, `n`, `i`, an interpolation variant, a `secret_share`, and `n` verification shares, then forwards everything to `ThresholdKeys::new` (crypto/dkg/src/lib.rs:573-632).
- `ThresholdKeys::new` only enforces: share count equals `n`, participant indexes `<= n`, and `t == n` for `Interpolation::Constant` (crypto/dkg/src/lib.rs:355-374). It then derives `group_key` from `verification_shares` over participants `1..=t` (crypto/dkg/src/lib.rs:376-378) — it never relates `secret_share` to `verification_shares[params.i()]` or to `group_key`.
- Notably, the verification shares are read via `C::read_G` (the `Ciphersuite` method, crypto/dkg/src/lib.rs:622) which does **not** reject identity points, unlike `Curve::read_G` in FROST (crypto/frost/src/curve/mod.rs:125-131). An identity verification share can be smuggled in and is included in the `group_key` interpolation sum.
- Because `Interpolation::Constant(Vec<F>)` coefficients come straight from the byte stream (crypto/dkg/src/lib.rs:607-613), a crafted blob fully controls the interpolation factors used both for `group_key` derivation and for `view()`/`secret_share` computation at signing time (crypto/dkg/src/lib.rs:494-498).

The analog to the NetBeans PAC bug (an untrusted artifact evaluated with more privilege than intended, because the execution environment fails to constrain it) is that this deserialization trusts attacker-controlled bytes to define the *entire algebraic context* of a threshold key — polynomial coefficients, share-to-key consistency, group key — with none of the consistency invariants the DKG protocols (PedPoP `share_verification_statements`, MuSig `binding_factor`) enforce during key generation.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (the rules explicitly scope this API as untrusted input) obtains a `ThresholdKeys` object reporting a `group_key()` inconsistent with the loaded `secret_share`. Any signing (`view()` → FROST `sign`) will produce invalid shares for the reported group key, or — with `Constant` interpolation chosen by the attacker — a `group_key` whose discrete log structure is attacker-controlled (e.g., all verification shares set to `G * known_scalar` with unit coefficients), so funds received at the reported group key are either unspendable by the honest threshold or spendable solely by the attacker. This meets "funds reported received that are not spendable" / signing under an unintended key.

### Likelihood Explanation
Medium-low: exploitation requires the attacker to supply or influence the serialized key blob (e.g., a restore/import path reading `ThresholdKeys` from untrusted storage or transport). Within honest flows (PedPoP, MuSig, dealer, promotion) the shares are internally consistent, so the missing check is latent. However, the API presents `read` as a deserialization routine for a secret-bearing structure and enforces zero integrity invariants — there is no proof of possession, no self-consistency check, and no identity rejection on verification shares.

### Recommendation
In `ThresholdKeys::new` (or at the end of `ThresholdKeys::read`):
1. Verify `C::generator() * secret_share == verification_shares[params.i()]`.
2. Reject identity verification shares (use `Curve::read_G`-style checks or `is_identity` test).
3. For `Interpolation::Constant`, validate the coefficients reconstruct consistently (e.g., re-derive `group_key` from all `n` shares, not just `1..=t`, or document and enforce that coefficients must be the public MuSig binding factors — ideally serialize the key list and re-derive them rather than trusting the blob).

### Proof of Concept
```rust
// Attacker-chosen scalars s_1..=s_n; craft blob for victim participant i:
//   interpolation = Constant([1; n])  // t == n required
//   secret_share  = s_i               // attacker knows it
//   verification_shares[l] = G * s_l  // consistent — OR inconsistent variants:
// Variant A: verification_shares[i] = G * r (r != s_i)
//   -> read() succeeds; group_key() interpolates to sum_l s_l*G (or attacker
//      chosen), while this node's sign() produces share s_i — always invalid.
// Variant B: all shares consistent but polynomial known to attacker
//   -> group_key = G * sum(s_l); attacker can unilaterally sign/steal funds
//      sent to the reported group key.
```
The absence of any `secret_share ↔ verification_shares[i]` check at crypto/dkg/src/lib.rs:349-391 and the unconditional acceptance at :625-631 are the root cause.

**Caveat:** I was unable to fully trace all callers of `ThresholdKeys::read` (e.g., processor/coordinator key-loading paths) within the available iterations, so the practical reachability of attacker-controlled bytes into this API depends on deployment-specific key import/restore flows.
