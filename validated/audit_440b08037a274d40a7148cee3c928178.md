This confirms the vulnerability. `CallEVM` with `commit=false` for `balanceOf` executes without state commit, so `BalanceOf` (used as the pre-check in `ConvertCoinNativeERC20`) doesn't fail even if code was later self-destructed — but that's not the critical part. The critical part is the ordering and lack of atomicity in `ConvertCoinNativeERC20`.

### Title
Permanent Loss of User Funds via Non-Atomic Escrow-Then-Convert in `ConvertCoinNativeERC20` During IBC Timeout/Ack Refund Path - (File: `x/erc20/keeper/msg_server.go`)

### Summary
`ConvertCoinToERC20FromPacket` (invoked from `OnTimeoutPacket`/`OnAcknowledgementPacket`) calls `ConvertCoinNativeERC20`, which first escrows the sender's bank coin into the `erc20` module account via `SendCoinsFromAccountToModule`, and only afterward attempts to unescrow the corresponding ERC20 tokens via `CallEVM(... "transfer" ...)`. These two operations execute on the *same*, non-branched `sdk.Context` (only `WithKVGasConfig`/`WithTransientKVGasConfig` is applied, which does not create a cache/branch). If the ERC20 `transfer` call fails or its result doesn't produce a valid `Transfer` event (e.g., the contract was self-destructed, reverts, or misbehaves), `ConvertCoinNativeERC20` returns an error, but the escrow write from step 2 has already been committed to the real context's store. The caller, `ConvertCoinToERC20FromPacket`, catches this error, emits a failure event, and returns `nil`, so no error propagates to abort the whole packet-processing transaction. Consequently the sender's coins remain permanently trapped in the `erc20` module account with no ERC20 tokens ever delivered and no code path to reclaim them.

### Finding Description [1](#0-0) 
`ConvertCoinNativeERC20` escrows coins first:
```go
if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
    return sdkerrors.Wrap(err, "failed to escrow coins")
}
res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
if err != nil {
    return err
}
```
There is no `ctx.CacheContext()`/`writeFn()` pattern here (unlike the analogous, safer pattern used in `x/ibc/callbacks/keeper/keeper.go`'s `IBCOnTimeoutPacketCallback`/`IBCOnAcknowledgementPacketCallback`, which explicitly branch state with `ctx.CacheContext()` and only call `writeFn()` on success, and which explicitly guard against self-destructed contracts via `k.evmKeeper.IsContract(ctx, contractAddr)`). [2](#0-1) 
`ConvertCoinToERC20FromPacket` invokes `ConvertCoinNativeERC20` directly on the ambient `ctx` (only gas config is modified, not a branch):
```go
ctx = ctx.WithKVGasConfig(storetypes.GasConfig{}).WithTransientKVGasConfig(storetypes.GasConfig{})
...
if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
    ...
    ctx.EventManager().EmitEvents(...)
    return nil
}
```
Returning `nil` here means `OnTimeoutPacket`/`OnAcknowledgementPacket` (in `x/erc20/ibc_middleware.go`) also return `nil`, so the enclosing IBC `MsgTimeout`/`MsgAcknowledgement` handling completes successfully and commits all state changes made so far — including the just-escrowed bank coins that were never unescrowed. [3](#0-2) 
Even without a full contract self-destruct, any ERC20 whose `transfer` call from the module account produces no or malformed `Transfer` log (reverts, returns false, self-destructed with EIP-6780 semantics, blacklists the module or receiver, etc.) triggers this same code path via `validateTransferEventExists`/`ERC20BoolResponse` checks in `ConvertCoinNativeERC20`.

Because `RegisterERC20` is permissionless (`x/erc20/keeper/msg_server.go` `RegisterERC20`), an unprivileged actor can register a token pair backed by a contract they fully control, making a `transfer` failure or self-destruct trivially reproducible for that pair. Any honest user (including third parties, not just the pair's deployer) who sends this denom over IBC and then experiences a timeout or error-acknowledgement (naturally occurring events in IBC, not requiring a malicious relayer) will have their refunded coins permanently absorbed into the `erc20` module account, since:
- No automatic rollback exists for the escrow step.
- No manual/user-triggerable refund or "re-attempt conversion" path exists for coins already sitting in the `erc20` module account after this specific failure sequence (the doc comment's claim that "the user receives the corresponding bank token from the TokenPair instead" does not hold in this ordering — the bank token has already left the user's account and gone to the module account, not back to the user).

### Impact Explanation
This is a critical, permanent freezing/loss of user funds: the sender's refunded bank coin is irreversibly stuck in the `erc20` module account, with no minted ERC20 delivered and no available recovery mechanism in scoped code. This matches the "Critical permanent freezing, locking, theft, or unauthorized extraction of user funds ... or token-pair-backed balances" allowed impact.

### Likelihood Explanation
Likelihood is meaningful because:
- `RegisterERC20` is permissionless, so an attacker can deploy and register their own adversarial ERC20 contract.
- IBC timeouts and error acknowledgements are ordinary, expected outcomes of cross-chain transfers (no malicious relayer/validator required to trigger them; a relayer submitting a legitimate `MsgTimeout`/`MsgAcknowledgement` after a timeout window is sufficient).
- The bug fires deterministically whenever `CallEVM`'s `transfer` step fails for any of several realistic reasons (revert, self-destruct, non-standard ERC20 returning false, blacklist), not requiring rare or edge-case conditions.

### Recommendation
Wrap the escrow-then-unescrow sequence in `ConvertCoinNativeERC20` (or specifically its invocation from `ConvertCoinToERC20FromPacket`) in a `ctx.CacheContext()` branch, committing (`writeFn()`) only after the ERC20 `transfer` call and its result validation succeed; alternatively, perform an `IsContract` check before attempting the transfer (as already done in `x/ibc/callbacks/keeper/keeper.go`), and on any failure, explicitly reverse the escrow via `SendCoinsFromModuleToAccount` back to the sender before returning, so that a failed ERC20 conversion always leaves the sender holding either the ERC20 token or the original bank coin, never neither.

### Proof of Concept
1. Permissionlessly register (`MsgRegisterERC20`) a malicious ERC20 contract whose `transfer` function can be made to revert (or self-destruct) on demand, as a native ERC20 token pair.
2. Convert ERC20 to native coin via `MsgConvertERC20` for account `A`, giving `A` bank coins of the pair's denom.
3. Have `A` initiate an ICS-20 IBC transfer of these coins to a channel/receiver arranged to fail (e.g. destination without proper counterpart handling, or simply wait for timeout).
4. Before the relayer submits `MsgTimeout`/`MsgAcknowledgement` (error ack), self-destruct the ERC20 contract (or otherwise make its `transfer` revert/return false).
5. Relayer submits `MsgTimeout` — `x/erc20/ibc_middleware.go`'s `OnTimeoutPacket` → `k.OnTimeoutPacket` → `ConvertCoinToERC20FromPacket` → `ConvertCoinNativeERC20` escrows `A`'s coins to the `erc20` module account, then `CallEVM("transfer",...)` fails; error is swallowed and `nil` is returned.
6. Assert: `A`'s bank balance for the denom is now zero (or reduced by the escrowed amount), `A`'s ERC20 token balance is unchanged (still zero), and the `erc20` module account holds the escrowed coin permanently, with no further code path returning it to `A`.

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,

// ConvertCoinToERC20FromPacket converts the IBC coin to ERC20 after refunding the sender
// This function is only executed when IBC timeout or an Error ACK happens.
func (k Keeper) ConvertCoinToERC20FromPacket(ctx sdk.Context, data transfertypes.FungibleTokenPacketData) error {
	// Sender is local (source) chain address; accept local bech32 or 0x-hex
	senderBz, err := k.addrCodec.StringToBytes(data.Sender)
	if err != nil {
		return err
	}
	sender := sdk.AccAddress(senderBz)

	pairID := k.GetTokenPairID(ctx, data.Denom)
	pair, found := k.GetTokenPair(ctx, pairID)
	if !found {
		// no-op, token pair is not registered
		return nil
	}

	coin := ibc.GetSentCoin(data.Denom, data.Amount)

	switch {

	// Case 1. if pair is native coin -> no-op
	case pair.IsNativeCoin():
		// no-op, received coin is a  native coin
		return nil

	// Case 2. if pair is native ERC20 -> unescrow
	case pair.IsNativeERC20():
		// use a zero gas config to avoid extra costs for the relayers
		ctx = ctx.
			WithKVGasConfig(storetypes.GasConfig{}).
			WithTransientKVGasConfig(storetypes.GasConfig{})

		params := k.GetParams(ctx)
		if !params.EnableErc20 || !k.IsDenomRegistered(ctx, coin.Denom) {
			// no-op, ERC20s are disabled or the denom is not registered
			return nil
		}

		// assume that all module accounts on Cosmos EVM need to have their tokens in the
		// IBC representation as opposed to ERC20
		senderAcc := k.accountKeeper.GetAccount(ctx, sender)
		if types.IsModuleAccount(senderAcc) {
			return nil
		}

		// Convert from Coin to ERC20
		if err := k.ConvertCoinNativeERC20(ctx, pair, coin.Amount, common.BytesToAddress(sender), sender); err != nil {
			// We want to record only the failed attempt to reconvert the coins during IBC.
			defer func() {
				telemetry.IncrCounter(1, types.ModuleName, "ibc", "error", "total")
			}()
			ctx.EventManager().EmitEvents(
				sdk.Events{
					sdk.NewEvent(
						types.EventTypeFailedConvertERC20,
						sdk.NewAttribute(types.AttributeCoinSourceChannel, pair.Denom),
						sdk.NewAttribute(types.AttributeKeyERC20Token, pair.Erc20Address),
						sdk.NewAttribute("error", err.Error()),
					),
				},
			)
			return nil
		}

// validateTransferEventExists returns an error if the given transactions logs DO NOT include

func validateTransferEventExists(logs []*types.Log, tokenAddress common.Address) error {
	if len(logs) == 0 {
		return errors.Wrapf(
			types2.ErrExpectedEvent, "expected Transfer event",
		)
	}
	found := false
	for _, log := range logs {
		if log.Topics[0] == logTransferSigHash.Hex() {
			if log.Address != tokenAddress.Hex() {
				return errors.Wrapf(
					types2.ErrUnexpectedEvent, "Transfer event from unexpected address",
				)
			}
			if found {
				return errors.Wrapf(
					types2.ErrUnexpectedEvent, "duplicate Transfer event",
				)
			}
			found = true
		}
	}

	if !found {
		return errors.Wrapf(
			types2.ErrExpectedEvent, "expected Transfer event",
		)
	}

	return nil
