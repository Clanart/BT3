## Analysis

The C4 report's bug class — decimal-scaling math that silently breaks when the decimal delta runs in the "wrong" direction — has a direct, unguarded analog in `pallet-hyper-fungible-token`'s ERC20⇄local balance scaling helpers.### Title
`pallet-hyper-fungible-token` decimal-scale helpers use one-directional `saturating_sub`, causing silent free-minting/under-burning when a local asset has more decimals than its registered remote ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` — the two functions that translate amounts between an ERC20 token's decimal precision and the local `pallet-assets`/native-currency decimal precision — both compute the scaling exponent as `erc_decimals.saturating_sub(local_decimals)`. This is only correct when `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals` (a configuration the pallet's own README explicitly says is supported: *"Decimals between this chain and each remote chain may differ"*), `saturating_sub` clamps to `0`, so the required inverse scaling (multiply on the balance side / divide on the ERC20 side) is silently skipped. The amount is then used unscaled, mismatching the two precisions by a factor of `10^(local_decimals - erc_decimals)`. [1](#0-0) 

### Finding Description
`send()` burns/escrows `params.amount` in local decimals, then converts it to the wire amount with:

```rust
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
``` [2](#0-1) 

`on_accept()` performs the inverse conversion to credit the beneficiary:
```rust
let amount = convert_to_balance::<...>(U256::from_big_endian(...), erc_decimals, decimals)...
``` [3](#0-2) 

Both rely on:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
``` [1](#0-0) 

`erc_decimals` comes from the governance-set `Precisions` storage (`ChainConfig::decimals`, set via `register_token`/`update_token`), and `local_decimals` comes from the actual local asset's `fungibles::metadata::Inspect::decimals()` (or `T::Decimals` for the native asset). Nothing in `register_token`/`update_token` enforces `erc_decimals >= local_decimals`. Whenever governance registers a token pair where the local asset uses *more* decimals than the remote ERC20 contract (e.g. bridging a 6-decimal EVM token like USDC against a local asset created with 12 or 18 decimals — a completely ordinary configuration explicitly called out as supported), the exponent `erc_decimals.saturating_sub(local_decimals)` clamps to `0` in both directions instead of applying the required inverse scale:

- In `on_accept` (mint/release path): the raw ERC20 `amount` (denominated at the *smaller* `erc_decimals`) is credited to the beneficiary as-is at the *larger* `local_decimals` precision, over-crediting by `10^(local_decimals - erc_decimals)`.
- In `send` (burn/escrow path): the local amount is forwarded to the ERC20 side unscaled instead of being divided down, so the message amount is inflated by the same factor relative to what was actually escrowed/burned.

This breaks the 1:1 custody invariant this pallet is built to guarantee: any ordinary user calling `send()`/triggering `on_accept` on such a token pair mints or is credited far more value than what was locked/burned on the source side — no malicious relayer, prover, or governance compromise is required, only a standard token registration with mismatched decimal magnitudes.

### Impact Explanation
This is a direct violation of the "bridged assets must move exactly once and only to the rightful beneficiary and amount" pivot. On the mint/release side (`on_accept` / `on_timeout`), a normal cross-chain message causes `T::Assets::mint_into` or a native-currency `transfer` from the escrow account for an amount inflated by up to `10^(local_decimals - erc_decimals)`, which can drain the pallet's escrow account or mint unbacked supply of the wrapped asset — a direct fund-loss/unbacked-mint bug reachable by any unprivileged user who sends a routine transfer once such a token pair exists.

### Likelihood Explanation
Requires only a standard governance token registration where the local asset's decimals exceed the configured remote ERC20 decimals — a scenario the pallet documentation explicitly presents as a normal supported case ("Decimals between this chain and each remote chain may differ"). No malicious peer, relayer, or admin action is needed; the trigger is an ordinary `send()` or an ordinary inbound message once the mismatched pair is registered.

### Recommendation
Fix the scaling helpers to handle both directions symmetrically, e.g.:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
and the mirror-image fix for `convert_to_erc20`. Add a test asserting correctness when `local_decimals > erc_decimals` (the current test suite only exercises `erc_decimals(18) > local_decimals(10)`, which never triggers the clamp).

### Proof of Concept
1. Governance calls `register_token` for asset `X` where the local `pallet-assets` decimals are `18`, and configures `Precisions[(X, EvmChain)] = 6` (a legitimate pairing against a 6-decimal ERC20 like USDC).
2. A user calls `send(asset_id: X, amount: 1_000_000_000_000u128 /* 1 unit at 18 decimals is 1e18; use a small amount like 1e12 */, destination: EvmChain, ...)`. `erc_decimals(6).saturating_sub(local_decimals(18)) == 0`, so `convert_to_erc20` returns the amount unscaled instead of dividing by `10^12`; the dispatched message therefore encodes an ERC20 amount `10^12`× larger than what was actually burned/escrowed locally.
3. Symmetrically, when a genuine EVM-side message later triggers `on_accept` with an amount denominated at `erc_decimals = 6`, `convert_to_balance` again skips the required multiply-up, but any inbound message crafted with a modest ERC20 amount will be credited unscaled at 18-decimal local precision — `10^12`× the intended value — draining the escrow/minting unbacked supply, confirmed by tracing the same code path exercised in `should_receive_asset_correctly` (`modules/pallets/testsuite/src/tests/pallet_hyper_fungible_token.rs:51-96`) but with `erc_decimals < local_decimals` instead of the tested `erc_decimals(18) > local_decimals(10)` case.
