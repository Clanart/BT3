### Title
Zero-weight signing participant still counts toward the FROST threshold - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`Interpolation::Constant` accepts coefficients of zero for participant indexes. Such a participant contributes no secret-share weight, yet remains a valid `Participant`, is counted in `included.len()` toward `t`, and can provide a signature share consisting only of its bound nonce. This is analogous to the reported zero-weight voter remaining eligible: the participant occupies a threshold slot while its key-share weight is zero.

The issue is reachable through `ThresholdKeys::read`, which accepts serialized `Constant` coefficients without rejecting zero coefficients, and through attacker-supplied FROST preprocess/share bytes passed to `read_preprocess` / `read_share`.

### Finding Description
`ThresholdKeys::read` deserializes `Interpolation::Constant(Vec<F>)` and passes it to `ThresholdKeys::new` without checking that every coefficient is nonzero. [1](#0-0)  `ThresholdKeys::new` only checks that constant interpolation is used when `t == n`; it does not reject zero coefficients or verify that the local `secret_share` corresponds to `verification_shares[i]`. [2](#0-1) 

For constant interpolation, `interpolation_factor` directly returns `c[i - 1]`. [3](#0-2)  `ThresholdKeys::view` then multiplies the participant's secret and verification share by that coefficient. [4](#0-3)  A coefficient of zero therefore produces an identity verification share and zero secret contribution, while the participant remains included.

`AlgorithmSignMachine::sign` counts participants by `included.len()`, only requiring at least `t` unique in-range IDs. [5](#0-4)  During completion, all included responses are summed and the aggregate signature is verified before per-share verification. [6](#0-5)  Since a zero-weight participant's public key contribution is `0 * Y_i = identity`, a share equal to its bound nonce scalar satisfies its Schnorr share statement and also cancels its nonce contribution in the final aggregate.

### Impact Explanation
An attacker occupying a participant index with a zero constant-interpolation coefficient can satisfy one required threshold slot without knowing any secret share. For a `t = n` constant-interpolation key, this reduces the effective secret-share requirement from `t` holders to `t - 1`.

For example, with `n = t = 3` and coefficients `[1, 1, 0]`, the group key is derived only from participants 1 and 2, but participant 3 is still counted as a signer. Participant 3 can make the aggregate signature verify by contributing `R_3 = r_3 G` and `s_3 = r_3`. The result is a valid signature under the group key even though only two actual secret holders participated. This is a threshold-signature bypass and can produce signatures for messages that the required threshold of real key holders did not authorize.

### Likelihood Explanation
The cryptographic path is deterministic once malformed `ThresholdKeys` with a zero `Constant` coefficient are accepted: `ThresholdKeys::read` accepts them, `view` converts the participant's verification share to identity, and `sign` still counts the participant toward the threshold.

The environmental requirement is that constant-interpolation key material is deserialized or otherwise configured with a zero coefficient. The in-scope deserialization API allows this input and does not diagnose it. No malicious validator threshold, broken consensus assumptions, leaked key, unsafe code, or invalid curve implementation is required.

### Recommendation
Reject zero coefficients in `Interpolation::Constant`, at least during `ThresholdKeys::new` and `ThresholdKeys::read`. Constant interpolation should require `coefficients.len() == n` and every coefficient to be nonzero.

Additionally, validate the deserialized semantic consistency of `ThresholdKeys`: check `C::generator() * secret_share == verification_shares[i]` before accepting `i`'s key material. For defense in depth, FROST's signing-set construction can also reject any included participant whose interpolated verification share is identity or whose interpolation factor is zero.

### Proof of Concept
1. Create serialized `ThresholdKeys` for `n = 3, t = 3` using `Interpolation::Constant([1, 1, 0])`.
2. Set `Y_1 = x_1 G`, `Y_2 = x_2 G`, and arbitrary nonzero `Y_3`. The group key becomes `Y_1 + Y_2`; participant 3 has no group-key weight.
3. Participant 3 publishes a normal preprocess `(D_3, E_3) = (d_3 G, e_3 G)` with known `d_3, e_3`. Identity points are not needed, so `Curve::read_G` accepts them. [7](#0-6) 
4. Honest participants 1 and 2 sign `msg` in a signing set `{1,2,3}`. The set passes the quantity, range, duplicate, and map checks because participant 3 is a valid in-range `Participant`. [8](#0-7) 
5. Let participant 3's binding factor be `rho_3` and bound nonce `r_3 = d_3 + rho_3 e_3`. Participant 3 submits `SignatureShare(s_3 = r_3)` through `read_share`. [9](#0-8) 
6. The final signature has `R = R_1 + R_2 + R_3` and `s = s_1 + s_2 + s_3`. Since participant 3's key contribution is zero, the added `R_3 = r_3 G` and `s_3 = r_3` cancel in the Schnorr equation, leaving a valid signature under `Y_1 + Y_2`.
7. If aggregate verification fails for another reason and per-share blame runs, participant 3's share also verifies because its interpolated verification share is identity and `s_3 G = R_3`. [10](#0-9)
