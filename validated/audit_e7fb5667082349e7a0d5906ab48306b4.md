## Analysis

The C4 finding is about code trusting an operation to have succeeded without checking its actual return status, letting a failed transfer proceed as if it succeeded. The closest structural analog in GitHub Desktop is in `app/src/lib/git/stash.ts`, where the wrapper around `git stash` does not rely on git's own success signal (exit code) but instead uses a fragile heuristic — "exit code 1 + no `error:` line in stderr" — to *infer* that a stash operation actually succeeded, then acts on that inference by permanently deleting stash data.

### Title
Heuristic-based "success" inference in stash pop/push causes silent, irrecoverable loss of stashed changes - (File: `app/src/lib/git/stash.ts`)

### Summary
`popStashEntry` and `createDesktopStashEntry` do not check git's actual success/failure signal for `git stash pop`/`git stash push`. Instead of treating a non-zero exit code as failure (the documented git contract), they guess that the operation succeeded whenever `exitCode === 1` and stderr is empty (or contains no `error:`-prefixed line), then take destructive follow-up action based on that guess.

### Finding Description
In `popStashEntry`: [1](#0-0) 
the code sets `expectedErrors = {MergeConflicts}` and, on any other `GitError` with `exitCode === 1` and empty `stderr`, assumes the pop *did* succeed and unconditionally calls `dropDesktopStashEntry`, which runs `git stash drop` and deletes the stash forever: [2](#0-1) 

The comment in the code is explicit about the fragility of this logic: *"Not the greatest approach but stash isn't very communicative."* A near-identical heuristic exists in `createDesktopStashEntry`, where the author left a lengthy note documenting a known counter-example — `git stash push` in an unborn repository exits with code 1 and no `error:`-prefixed stderr line, yet **no stash was actually created**, and the function nonetheless treats it as success: [3](#0-2) 

This is the same class of bug as the report: the caller does not verify the operation's true return status via a reliable channel (git's exit code / documented error semantics) and instead infers success from an incidental side effect (absence of a particular string pattern in stderr). Anything in the repository or its git internals that can produce "exit 1, no `error:` line, no merge-conflict marker" without the stash actually having been applied will be silently treated as a successful pop, and the underlying stash entry will then be dropped — destroying the user's uncommitted changes with no recovery path and no user-facing error.

### Impact Explanation
If triggered, the impact is silent, irrecoverable loss of the user's own uncommitted work: Desktop believes the stash was successfully re-applied to the working directory and proceeds to delete the only copy of those changes (`dropDesktopStashEntry`). This falls under "silent corruption of what the user commits" in the sense that the working directory ends up in a state inconsistent with what the user believes was restored, and the safety net (the stash) is destroyed without ever surfacing an error, conflict UI, or confirmation to the user.

### Likelihood Explanation
Exploitability depends on being able to reliably force `git stash pop`/`push` into the exact "exit 1, empty/`error:`-less stderr, no `MergeConflicts` DugiteError, no stash actually applied/created" state from within a repository an attacker controls (e.g., via crafted `.gitattributes` filters, hooks, or repository corner cases similar to the already-documented unborn-repository case). This requires a specific, git-internals-dependent condition rather than a trivially reproducible one-line trigger, so likelihood is moderate — the code's own comments acknowledge that such edge cases exist and are not fully enumerated ("I'm not going to mess with this now but I felt the need to document my findings").

### Recommendation
Replace the stderr-pattern heuristic with an authoritative check of the operation outcome, e.g., re-querying `git stash list`/`git status` (or comparing tree state) after a `stash pop`/`push` attempt to confirm whether the stash was actually consumed/created before deciding whether to drop it or return `true`/`false`. Never drop a stash entry based solely on an exit-code/stderr-text heuristic.

### Proof of Concept
Not independently verified end-to-end against live `dugite`/git behavior (would require constructing a repository/filter setup that reproduces "exit 1, empty stderr, no conflict" for `git stash pop`), but the already-documented in-code counter-example demonstrates the same class of false-positive for `git stash push`:
```
% git stash push -m foo ; echo $?
You do not have the initial commit yet
1
```
No `error:`-prefixed line is emitted, so `createDesktopStashEntry` treats this as "stash was created successfully" per its own logic, despite no stash existing — confirming the heuristic is unsound and, by direct extension of the same code pattern, the `popStashEntry` drop-on-assumed-success path is equally unsound. /**
 * Stash the working directory changes for the current branch

export async function createDesktopStashEntry(
  repository: Repository,
  branch: Branch | string,
  untrackedFilesToStage: ReadonlyArray<WorkingDirectoryFileChange>
): Promise<boolean> {
  // We must ensure that no untracked files are present before stashing
  // See https://github.com/desktop/desktop/pull/8085
  // First ensure that all changes in file are selected
  // (in case the user has not explicitly checked the checkboxes for the untracked files)
  const fullySelectedUntrackedFiles = untrackedFilesToStage.map(x =>
    x.withIncludeAll(true)
  )
  await stageFiles(repository, fullySelectedUntrackedFiles)

  const branchName = typeof branch === 'string' ? branch : branch.name
  const message = createDesktopStashMessage(branchName)
  const args = ['stash', 'push', '-m', message]

  const result = await git(args, repository.path, 'createStashEntry').catch(
    e => {
      // Note: 2024: Here be dragons. As I converted this code to get rid of the
      // successExitCode use I got curious about the assumptions made in the
      // following logic. It assumes that as long as the exit code for `git
      // stash push` is 1 and there are no lines beginning with "error: " then
      // a stash was created. That didn't hold up to a quick read of the stash
      // code. For example, running git stash push in an unborn repository will
      // get you an exit code of 1 but no stash was created:
      //
      // % git stash push -m foo ; echo $?
      // You do not have the initial commit yet
      // 1
      //
      // I'm not going to mess with this now but I felt the need to document
      // my findings should I or any other brave soul choose to tackle this in
      // the future.
      if (e instanceof GitError && e.result.exitCode === 1) {
        // search for any line starting with `error:` -  /m here to ensure this is
        // applied to each line, without needing to split the text
        const errorPrefixRe = /^error: /m

        const matches = errorPrefixRe.exec(coerceToString(e.result.stderr))
        if (matches !== null && matches.length > 0) {
          // rethrow, because these messages should prevent the stash from being created
          return Promise.reject(e)
        }

        // if no error messages were emitted by Git, we should log but continue because
        // a valid stash was created and this should not interfere with the checkout

        log.info(
          `[createDesktopStashEntry] a stash was created successfully but exit code ${result.exitCode} reported. stderr: ${result.stderr}`
        )
        return e.result
      }
      return Promise.reject(e)
    }
  )

  // Stash doesn't consider it an error that there aren't any local changes to save.
  if (result.stdout === 'No local changes to save\n') {
    return false
  }

  return true
}

export async function dropDesktopStashEntry(
  repository: Repository,

  const entryToDelete = await getStashEntryMatchingSha(repository, stashSha)

  if (entryToDelete !== null) {
    const args = ['stash', 'drop', entryToDelete.name]
    await git(args, repository.path, 'dropStashEntry')
  }
}

export async function popStashEntry(
  repository: Repository,
  stashSha: string
): Promise<void> {
  // ignoring these git errors for now, this will change when we start
  // implementing the stash conflict flow
  const expectedErrors = new Set<DugiteError>([DugiteError.MergeConflicts])
  const stashToPop = await getStashEntryMatchingSha(repository, stashSha)

  if (stashToPop !== null) {
    const args = ['stash', 'pop', '--quiet', `${stashToPop.name}`]
    await git(args, repository.path, 'popStashEntry', {
      expectedErrors,
    }).catch(e => {
      // popping a stashes that create conflicts in the working directory
      // report an exit code of `1` and are not dropped after being applied.
      // so, we check for this case and drop them manually unless there's
      // anything in stderr as that could have prevented the stash from being
      // popped. Not the greatest approach but stash isn't very communicative
      if (
        e instanceof GitError &&
        e.result.exitCode === 1 &&
        e.result.stderr.length === 0
      ) {
        log.info(
          `[popStashEntry] a stash was popped successfully but exit code ${e.result.exitCode} reported.`
        )
        // bye bye
        return dropDesktopStashEntry(repository, stashSha)
      }
      return Promise.reject(e)
    })
  }
}
