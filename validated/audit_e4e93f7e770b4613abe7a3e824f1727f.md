### Title
Bridge Circuit Accepts Equal-Work Watchtower Challenge — Operator on Tied Fork Bypasses Disprove Gate (`circuits-lib/src/bridge_circuit/mod.rs`)

### Summary

The `bridge_circuit` function uses a strict `<` comparison to check whether the operator's total accumulated proof-of-work exceeds the maximum watchtower challenge work. The protocol specification and module documentation both require the operator's work to be **strictly greater than** any watchtower's work. The code's `<` guard allows the equal case (`total_work == max_total_work`) to pass silently, meaning an operator on a fork whose lower-128-bit work exactly ties the canonical chain's lower-128-bit work can generate a valid bridge circuit proof and escape the disprove mechanism.

### Finding Description

In `circuits-lib/src/bridge_circuit/mod.rs`, the `bridge_circuit` function extracts the operator's total work as the lower 16 bytes of the 32-byte `ChainState::total_work` field:

```rust
let total_work: TotalWork = input.hcp.chain_state.total_work[16..32]
    .try_into()
    .expect("Cannot fail");
```

It then compares this against `max_total_work` — the highest Groth16-verified watchtower work-only proof output:

```rust
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
```

The watchtower's `total_work` is produced by `work_conversion()` in `circuits-lib/src/work_only/mod.rs`, which also truncates the 256-bit accumulated work to its lower 128 bits:

```rust
fn work_conversion(work: U256) -> [u8; 16] {
    let (_, work): (U128, U128) = work.into();
    work.to_be_bytes()
}
```

Both sides of the comparison therefore represent the same quantity: the lower 128 bits of the accumulated proof-of-work. The comparison uses `<` (strict less-than), so when `total_work == max_total_work` the circuit does **not** panic and the operator's proof is accepted.

The protocol specification contradicts this behaviour in three places:

- Module doc comment (line 7–8): *"ensures that an operator's claimed Bitcoin chain state is valid and that it has **more** cumulative proof-of-work than any challenging watchtower."*
- `bridge_circuit` function doc (line 19–20): *"Work Comparison: Asserts that the operator's claimed work is **greater than** the maximum work submitted by any valid watchtower."*
- `docs/bridge-circuit.md` line 33: *"Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers."*

All three state a strict `>` requirement; the code enforces only `>=`.

### Impact Explanation

The bridge circuit is the ZK proof the operator generates off-chain to defend against a watchtower challenge. If the proof is accepted, verifiers cannot disprove the operator's claim and the operator receives reimbursement from the bridge vault. When `total_work == max_total_work`, the circuit accepts the proof even though the watchtower has demonstrated an alternative chain with equal accumulated work. Equal work means neither chain is provably canonical; the operator's payout transaction may be on a minority fork. The operator can therefore:

1. Front a withdrawal on a non-canonical fork.
2. Generate a bridge circuit proof that passes the equal-work check.
3. Collect reimbursement from the bridge vault for a payout that was never on the canonical chain.

This constitutes a loss of bridged BTC from the vault and/or operator collateral slashing avoidance, satisfying the Critical/High impact gate.

### Likelihood Explanation

The 128-bit truncation makes a collision more reachable than a full 256-bit tie. Two scenarios produce `total_work == max_total_work`:

1. **Same chain (benign):** Operator and watchtower track the same chain. The equal case is harmless but still violates the stated invariant.
2. **Fork with equal lower-128-bit work (exploitable):** A fork that diverges from the canonical chain but accumulates the same lower-128-bit work. On mainnet this requires significant mining power; on testnet4/regtest the difficulty is low enough that an attacker controlling even modest hash rate could engineer this condition. The 128-bit truncation means the upper 128 bits can differ while the comparison still shows equality, widening the attack surface compared to a full 256-bit check.

Likelihood is **Medium**: requires mining capability but the truncated comparison lowers the bar compared to a full-precision tie.

### Recommendation

Change the comparison from strict `<` to `<=` so that equal work also causes the circuit to panic, enforcing the documented strict-greater-than invariant:

```rust
// Before (incorrect — allows equal work to pass)
if total_work < max_total_work {
    panic!(...);
}

// After (correct — requires operator work to be strictly greater)
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: operator work must be strictly greater than watchtower max work. \
         Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
```

### Proof of Concept

1. A watchtower on the canonical chain at height H generates a work-only proof with `work_u128 = W` (lower 128 bits of canonical total work).
2. An operator builds a header-chain proof for a fork whose lower-128-bit total work also equals `W` (upper 128 bits may differ).
3. The operator calls `bridge_circuit`. `total_work_and_watchtower_flags` returns `TotalWork(W)` as `max_total_work`.
4. The operator's `total_work` extracted from `hcp.chain_state.total_work[16..32]` is also `W`.
5. The check `if total_work < max_total_work` evaluates `W < W` → `false` → no panic.
6. The circuit completes successfully and commits a valid journal hash.
7. The operator posts Assert transactions using this proof. Verifiers find no disprovable step because the bridge circuit proof is valid.
