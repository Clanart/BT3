### Title
`Debug` implementations on `ThresholdKeys`/`ThresholdView` print secret interpolation coefficients (and tweak scalars), enabling local disclosure of key material - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys<C>` derives `Debug`, which delegates to the manual `fmt::Debug` impl on `ThresholdCore<C>`. That impl deliberately omits `secret_share` but prints the `interpolation` field. `Interpolation<F>` itself derives `Debug`, so for the `Interpolation::Constant(Vec<F>)` variant the entire vector of per-participant secret coefficients — described in the code as "a list of constant coefficients, one for each of the secret key shares" — is rendered in plaintext whenever a `ThresholdKeys` (or `ThresholdView`, whose `Debug` also prints `interpolation` plus `scalar`/`offset`) is formatted with `{:?}`. Field elements (`Scalar` in `crypto/dalek-ff-group`, `crypto/ed448`) derive `Debug` and print their canonical values.

This is the direct analog of CVE-2019-13313 (secret material observable by a local unprivileged party through a process-inspection channel): secret values the library treats as sensitive (they are `Zeroizing`/`Zeroize`-managed) are emitted through an ambient, easily-triggered output channel (Debug formatting → logs, panic messages, `unwrap_err()`/`expect()` paths, error enums embedding these types).

### Finding Description [1](#0-0) 
`ThresholdCore::fmt::Debug` prints `interpolation` while carefully hiding `secret_share` via `finish_non_exhaustive()`. [2](#0-1) 
`Interpolation` derives `Debug`; the `Constant(Vec<F>)` payload is printed verbatim. These coefficients are secret: the enum implements `Zeroize`, `ThresholdCore::zeroize` zeroizes `interpolation`, and `interpolation_factor` multiplies them against `secret_share` (`c[i-1] * secret_share`), so a coefficient is functionally equivalent to key-share material for reconstruction contexts. [3](#0-2) 
`ThresholdKeys` derives `Debug`, so `format!("{keys:?}")`, `dbg!(keys)`, `unwrap()`/`expect` on `Result<ThresholdKeys>` (e.g., `ThresholdKeys::new`/`read` errors are propagated with `io::Error::other(format!("{e:?}"))`), or any struct embedding keys prints the leak. [4](#0-3) 
`ThresholdView::fmt::Debug` additionally prints `scalar` and `offset` — the ephemeral private scaling/tweak factors applied via `scale()`/`offset()` — and the `interpolation` coefficients. [5](#0-4) 
`Scalar` derives `Debug`, so each printed `F` renders its full 32-byte secret value, not a redacted placeholder.

Contrast with the codebase's own convention: `SecretShare::fmt::Debug` (`crypto/dkg/pedpop/src/lib.rs:242`) prints an empty `finish_non_exhaustive()` struct, and `SecretShareMachine`, `KeyMachine`, `Encryption`, and `BlameMachine` all have hand-written `Debug` impls that omit `coefficients`, `secret`, and `enc_key`. The `interpolation`/`scalar`/`offset` fields were simply missed in `ThresholdCore`/`ThresholdView`, and `derive(Debug)` on `ThresholdKeys` exposes the whole chain.

### Impact Explanation
Any code path that Debug-formats `ThresholdKeys` or `ThresholdView` — a `panic!("{e:?}")`, a `debug!`/`trace!` log line, an error variant embedding the keys, `dbg!` left in integrator or processor code — writes the constant interpolation coefficients (and view scalar/offset) to whatever sink a local unprivileged observer can read (stderr, journald, log files, crash reports). For `Interpolation::Constant` keys (the variant produced/used by `crypto/dkg/musig` and `crypto/dkg/recovery` flows where `t == n`), the coefficients let an observer who also obtains any share material (or who is a protocol participant) recover the effective secret shares directly, since `c[i-1]` is the exact multiplicative factor applied to each `secret_share`. The leaked `scalar`/`offset` additionally reveals private key tweaks applied via `scale()`/`offset()`, which the API explicitly documents as ephemeral secrets excluded from `serialize()`/`write()` — yet they are included in `Debug` output.

### Likelihood Explanation
Debug formatting is pervasive in Rust error handling: `ThresholdKeys::read`/`ThresholdKeys::new` errors are frequently wrapped via `format!("{e:?}")`, processor code uses `panic!("unknown error: {e:?}")` (`processor/src/key_gen.rs`), and `derive(Debug)` on `ThresholdKeys` invites downstream `{:?}` usage. `Interpolation::Constant` is reachable through legitimate in-scope flows (`musig` DKG, `recovery`). Exploitation requires only the ability to read local logs/stderr/panic output — precisely the "local user observes secrets" class of CVE-2019-13313 — not any cryptographic break.

### Recommendation
- Remove `field("interpolation", ...)` (and `scalar`/`offset` from `ThresholdView`) from the `Debug` impls, or replace with a non-revealing marker (e.g., print only the variant discriminant).
- Remove `Debug` from `Interpolation`'s derive list or give it a manual impl that prints only `Constant(..)`/`Lagrange`.
- Consider removing `Debug` from `Scalar`/`Point` field types used for secrets, or wrapping secret-bearing fields so `finish_non_exhaustive()` conventions cannot be bypassed.
- Remove `#[derive(Debug)]` from `ThresholdKeys` or gate it behind a non-secret impl.

### Proof of Concept
```rust
use dkg::{ThresholdKeys, ThresholdParams, Interpolation, Participant, ThresholdView};
use ciphersuite::{Ciphersuite, group::ff::Field, Ristretto};
use zeroize::Zeroizing;
use rand_core::OsRng;
use std::collections::HashMap;

fn leak() {
  // Constant interpolation requires t == n
  let params = ThresholdParams::new(2, 2, Participant::new(1).unwrap()).unwrap();

  // Secret per-participant coefficients
  let c0 = <Ristretto as Ciphersuite>::F::random(&mut OsRng);
  let c1 = <Ristretto as Ciphersuite>::F::random(&mut OsRng);
  let secret = Zeroizing::new(<Ristretto as Ciphersuite>::F::random(&mut OsRng));

  let mut shares = HashMap::new();
  shares.insert(Participant::new(1).unwrap(), Ristretto::generator() * *secret);
  // second share s.t. c0*share1 + c1*share2 == group key; value irrelevant to the leak
  let s2 = <Ristretto as Ciphersuite>::F::random(&mut OsRng);
  shares.insert(Participant::new(2).unwrap(), Ristretto::generator() * s2);

  let keys = ThresholdKeys::<Ristretto>::new(
    params,
    Interpolation::Constant(vec![c0, c1]),
    secret,
    shares,
  ).unwrap();

  let out = format!("{keys:?}");
  // `out` contains the hex/scalar encodings of c0 and c1 — secret material —
  // even though `secret_share` itself is redacted.
  assert!(out.contains(&format!("{c0:?}")));

  // ThresholdView additionally leaks `scalar` and `offset`
  let view = keys
    .offset(<Ristretto as Ciphersuite>::F::random(&mut OsRng))
    .view(vec![Participant::new(1).unwrap(), Participant::new(2).unwrap()])
    .unwrap();
  let out2 = format!("{view:?}");
  assert!(out2.contains(&format!("{:?}", view.offset())));
}
```
Any panic/log/Debug output containing these values discloses the interpolation coefficients and ephemeral tweaks to a local observer, matching the credential-disclosure bug class.

#[derive(Clone, PartialEq, Eq, Debug, Zeroize)]
pub enum Interpolation<F: Zeroize + PrimeField> {
  /// A list of constant coefficients, one for each of the secret key shares.
  /*
    There's no benefit to using a full linear combination here, as the additive term would have
    an entirely known evaluation with a fixed, public coefficient of `1`. Accordingly, the entire
    key can simply be offset with the additive term to achieve the same effect.
  */
  Constant(Vec<F>),
  /// Lagrange interpolation.
  Lagrange,
}
