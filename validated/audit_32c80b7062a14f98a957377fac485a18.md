### Title
`SignableTransaction::new` excludes the OP_RETURN `data` output from weight/fee and size-limit accounting - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The Allo report's core bug class is a batched operation whose aggregate accounting ignores a per-item contribution (each `allocate` consumed the full `msg.value`; the batch path diverged from the single-call path). The same shape exists in `bitcoin-serai`: `SignableTransaction` builds a transaction paying to multiple outputs, but its weight, vbytes, `needed_fee`, and standardness check are computed from `payments` only — the OP_RETURN `data` output that is actually included in `tx_outs` is silently excluded from every accounting pass.

### Finding Description
In `SignableTransaction::new`, the `data` OP_RETURN output is appended to `tx_outs` (lines 194-202) **before** the weight calculation, yet `calculate_weight_vbytes` is called with `payments` — not `tx_outs`:

```rust
// networks/bitcoin/src/wallet/send.rs:193-204
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) })
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

The same omission occurs in the change-output branch, where `fee_with_change` is derived from `vbytes_with_change` computed over `payments` again (lines 224-232), and in the standardness bound check `weight > MAX_STANDARD_TX_WEIGHT` (line 241), which uses the underestimated `weight`. The real transaction in `self.tx` contains `tx_outs`, including the OP_RETURN (lines 245-251), so every quantity derived from `vbytes`/`weight` diverges from what is actually signed and broadcast. `data` may be up to 80 bytes (`TooMuchData` check, line 171), so the OP_RETURN adds roughly 10 + 82 ≈ 91+ vbytes (~364 weight units) that are never paid for and never counted against the size cap.

### Impact Explanation
- **Fee underpayment / unrelayable transaction:** `needed_fee = fee_per_vbyte * vbytes` is computed on a smaller transaction than the one built, so the effective fee rate is `fee_per_vbyte * vbytes_est / vbytes_actual < fee_per_vbyte`. When `fee_per_vbyte` is near `DEFAULT_MIN_RELAY_TX_FEE`, the minimum-relay check at lines 211-213 passes using the underestimated `vbytes`, while the actual transaction's feerate falls below the minimum relay rate — the signed transaction is rejected by Bitcoin nodes, leaving inputs/change unconfirmable and effectively unspendable until reconstructed.
- **Circumvented size limit:** a transaction that actually exceeds `MAX_STANDARD_TX_WEIGHT` can pass the `TooLargeTransaction` check, producing a non-standard transaction.

### Likelihood Explanation
`data` is a public constructor parameter used to attach OP_RETURN payloads (e.g., instruction data for Serai protocol messages caused by user deposits). Any caller supplying a non-empty `data` triggers the divergence deterministically; the only preconditions are `fee_per_vbyte` near the relay minimum (or enough inputs to cross the weight cap). The defect was confirmed reachable in-tree: `test_data` in `networks/bitcoin/tests/wallet.rs` constructs a `SignableTransaction` with data yet never validates the effective feerate.

### Recommendation
Pass the final `tx_outs` (or equivalently `payments` plus the OP_RETURN script and the change script) into `calculate_weight_vbytes`, and recompute/refresh `weight`, `vbytes`, and `needed_fee` after all outputs — including `data` and `change` — are known. The minimum-relay check and `MAX_STANDARD_TX_WEIGHT` check should use the true weight of the transaction actually constructed. Alternatively, build the candidate `Transaction` once (as `calculate_weight_vbytes` already does internally) and derive all fee/size metrics from it directly.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs context — conceptual PoC
// With an output worth `v`, payments summing to `p`, and data of 80 bytes:
let data = vec![0u8; 80];
let tx = SignableTransaction::new(vec![output], &payments, None, Some(data), FEE).unwrap();

// vbytes used for needed_fee excluded the OP_RETURN output (~91+ vbytes).
// actual feerate = tx.fee() / real_vsize < FEE
// With FEE = minimum relay rate, the produced tx is below DEFAULT_MIN_RELAY_TX_FEE
// per real vbyte and is rejected on broadcast.
```

Caveat: I verified the accounting divergence directly in `send.rs` (the `data` output is added to `tx_outs` but never passed to `calculate_weight_vbytes`), but I could not exhaustively rule out a compensating adjustment elsewhere in the signing/broadcast path; `multisig()`/`sign` in the same file do not recompute the fee, so the undercount stands.
