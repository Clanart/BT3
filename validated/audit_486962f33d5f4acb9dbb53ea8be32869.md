### Title
Unbounded recursion in `PuzzleWithRestrictions.from_memo()` allows a crafted `CREATE_COIN` memo to crash a syncing wallet via Python stack overflow - (File: chia/wallet/puzzles/custody/custody_architecture.py)

### Summary
`PuzzleWithRestrictions.from_memo()` recursively reconstructs nested `MofN` custody structures from an on-chain memo blob with no depth limit. This memo is attacker-controlled: any unprivileged party can submit a spend bundle whose `CREATE_COIN` condition places a deeply/self-nested `MofN` hint in the memo field. When a wallet later observes and parses that coin (e.g. through the PlotNFT sync path), the unbounded recursive parse can exhaust the Python call stack, mirroring the "specially crafted query causes stack overflow" bug class from the Elasticsearch advisory (CWE-121/CWE-787, unbounded recursion on external input).

### Finding Description
`PuzzleWithRestrictions.from_memo()` is defined as: [1](#0-0) 

Key excerpt of the recursive branch:
```
if further_branching:
    m_of_n_hint = MofNHint.from_program(puzzle_hint_prog)
    puzzle: MIPSComponent = MofN(
        m=m_of_n_hint.m, members=[PuzzleWithRestrictions.from_memo(memo) for memo in m_of_n_hint.member_memos]

``` [2](#0-1) 

Each `MofN` member is itself parsed by a fresh call to `from_memo()`, and each member can again encode an `MofN` hint that recurses further. There is no check on nesting depth, on the number of members, or on the size of the memo program before recursing. Because `Program` objects here are Python-level CLVM wrappers (`chia.types.blockchain_format.program.Program`), this is plain Python recursion, bounded only by the interpreter's default recursion limit — not by CLVM cost metering (parsing happens after CLVM execution, when interpreting the resulting memo `Program` tree in Python).

This function is reachable from wallet code that processes untrusted, attacker-supplied coin memos without validating them first:

`PlotNFT.get_next_from_coin_spend()` calls `PuzzleWithRestrictions.from_memo(singleton_create_coin.memo_blob.rest())` directly on the memo blob taken from a `CREATE_COIN` condition of an observed coin spend: [3](#0-2) 

`singleton_create_coin` is derived from conditions produced by running an inner puzzle the wallet does not control — i.e., data that came from whoever created that coin. Any unprivileged spend-bundle submitter can craft a coin whose puzzle hash and shape look enough like the plotnft path invariants checked earlier in the function (odd-amount singleton child, launcher/mod hash matches) to reach the `memo_blob` fallback branch, while stuffing the `memo_blob` with a deeply self-referential `MofNHint` list. When a wallet later resolves this coin (during normal sync of the PlotNFT singleton chain), `from_memo()` recurses once per encoded nesting level.

### Impact Explanation
A successful trigger causes a Python `RecursionError` (uncaught, since `from_memo()` only catches `ValueError` at the call site in `plotnft_drivers.py`) or, depending on interpreter/thread stack configuration, an actual native stack overflow. This crashes or hangs the wallet's sync/processing task for any wallet that encounters the malicious coin while walking the PlotNFT singleton lineage — a spend-triggered transaction-processing halt reachable purely from a single crafted spend bundle, matching the "Impact: Accept... a spend-triggered transaction-processing halt" criterion. This is a denial-of-service against wallet users tracking PlotNFTs, not an asset-forgery or fund-theft bug, so severity is capped at Medium in line with the CVSS profile of the analog (`AV:N/AC:L/PR:L/UI:N/C:N/I:N/A:H`).

### Likelihood Explanation
Likelihood is moderate: constructing the malicious memo requires only crafting a `CREATE_COIN` condition with a nested list structure matching `MofNHint`'s expected `(m . member_memos)` shape recursively — no cryptographic material or privileged access is needed, and CLVM cost limits do not bound the depth of the resulting Python-side memo tree (cost only limits CLVM execution, not the subsequent Python parse of the output). The main constraint is getting a wallet to actually walk this coin through `get_next_from_coin_spend()`, which requires it to be recognized as a step in a PlotNFT singleton chain (odd-amount child of a singleton whose mod/launcher hashes match); this is a real but not insurmountable precondition for a wallet actively tracking plotnfts.

### Recommendation
- Add an explicit, small maximum recursion/nesting depth (and a cap on `n` members per `MofN`) to `PuzzleWithRestrictions.from_memo()` / `MofNHint.from_program()`, raising a catchable `ValueError` once exceeded instead of recursing unboundedly.
- Convert the recursive parse into an iterative, explicit-stack implementation, consistent with the project's own precedent of avoiding Python recursion on attacker-influenced CLVM trees (see `sha256_treehash` in `chia/types/blockchain_format/tree_hash.py`, which is deliberately iterative "so we don't have to worry about blowing out the python stack").
- Wrap the call site in `chia/pools/plotnft_drivers.py` (`PlotNFT.get_next_from_coin_spend`) to catch `RecursionError`/`Exception` broadly around memo parsing, and to bound the size/depth of `memo_blob` before invoking `from_memo()`.
