## Analysis

The core broken invariant in the source report is: **funds are pushed via a direct `transfer`/`safeTransfer` to a counterparty address that is dictated by data fixed earlier in the protocol flow, with no pull-based fallback — if that address becomes blacklisted by the token, the funds are permanently locked, with the message/commitment unable to be resubmitted with a different recipient.**

The direct local analog is Hyperbridge's `IntentGateway` escrow-release path. When a cross-chain order is refunded/cancelled or filled, the settlement message is delivered via ISMP and processed by `onAccept`, which calls `withdraw()`/`_withdraw()`. This function pushes each escrowed token straight to `beneficiary` using `safeTransfer` (EVM mainline) or `IERC20.transfer` (Tron variant): [1](#0-0) 

The `beneficiary` for a `RefundEscrow` message is `order.user` — chosen by the user at order-placement time and baked immutably into the cross-chain `WithdrawalRequest` body that gets hashed into the ISMP commitment on the destination chain: [2](#0-1) 

`onAccept` then decodes this immutable body and calls `_withdraw`/`withdraw` unconditionally: [3](#0-2) [4](#0-3) 

If `beneficiary`'s token (e.g., USDC) blacklists that address before the refund/redeem message is delivered, `safeTransfer`/`IERC20.transfer` will revert every time this specific commitment's withdrawal is retried. The host's incoming-message handler is built to retry indefinitely on failure rather than skip: [5](#0-4) 

so the request is neither dropped nor rerouted — it stays permanently stuck, and the escrowed input tokens for that order can never be released to anyone. There is no push/pull separation (unlike, say, the relayer-reward flow which reverts atomically before any state mutation and can be resubmitted with a different `payee`) — the beneficiary here is embedded in the already-committed cross-chain message body and cannot be altered by any party.

### Title
Escrowed order funds are permanently locked when the settlement beneficiary is blacklisted by the escrowed/fee token - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` (and its Tron-fork twin `IntentGatewayV2.withdraw`) releases escrowed order funds by pushing tokens directly to a `beneficiary` address via `IERC20.safeTransfer`/`transfer`. That beneficiary — the order's `user` for `RefundEscrow`, or the filling solver for `RedeemEscrow` — is fixed inside the ISMP `WithdrawalRequest` body at the time the settlement message is dispatched from the other chain, and cannot be changed afterward. If the beneficiary address is later blacklisted by the escrowed token (e.g. USDC) or the fee token, every future delivery attempt of that settlement message reverts inside `onAccept`, and the escrowed funds for that order (and any pending fees) become permanently unretrievable.

### Finding Description
`_withdraw` decrements the internal `_orders[commitment][token]` escrow accounting and then attempts an unconditional push transfer to `beneficiary`: [6](#0-5) 

`beneficiary` originates from data set once at order creation/cancellation time and is carried immutably through the cross-chain `WithdrawalRequest` — for cancellation refunds it is `order.user`, unconditionally taken from the order struct with no override mechanism: [7](#0-6) 

`onAccept` decodes this body and calls `_withdraw` directly with no guard against a reverting transfer: [8](#0-7) 

Because the ISMP host retries failed `onAccept` deliveries by deleting the receipt and returning (rather than treating a reverting application callback as a permanent failure that could be diverted), the same commitment/message will be resubmitted and revert again on every retry as long as `beneficiary` remains blacklisted: [5](#0-4) 

There is no pull-based claim path: unlike `pallet-relayer`'s reward claims, which fail atomically before any state mutation and can be resubmitted with a different `payee` chosen freely by the claimant, the `WithdrawalRequest.beneficiary` here is embedded in the source-chain commitment of an already-dispatched cross-chain message and cannot be resigned or redirected by the user, the solver, or governance.

### Impact Explanation
Escrowed input tokens (and any accrued transaction fees in the fee token) for the affected order become permanently locked in the `IntentGateway` contract with no recovery path — matching the "bridged assets, order escrow, refunds... must move exactly once and only to the rightful beneficiary" invariant, except here they cannot move at all. This is a direct fund-loss/fund-lock condition reachable through ordinary permissionless protocol usage (a user placing an order, then later being blacklisted by the token issuer, or a solver's fill-beneficiary being blacklisted before the `RedeemEscrow` settlement lands).

### Likelihood Explanation
Requires the escrowed or fee token to support an issuer-controlled blacklist (USDC/USDT-style tokens, which the Intent Gateway explicitly supports per its fee/token model) and the relevant beneficiary address to be blacklisted between order placement and settlement delivery. No malicious relayer, prover, or admin action is needed — it is triggered purely by external token-issuer behavior acting on an ordinary, unprivileged participant's address.

### Recommendation
Replace the direct push transfer in `_withdraw`/`withdraw` with a pull-based accounting model: on failed transfer, credit the beneficiary's balance in an internal claims ledger instead of reverting the whole settlement, and expose a separate `claim()` function (or allow the beneficiary to redirect to an alternate address they control) so a blacklisting event on one token/address cannot permanently strand escrowed funds or block the ISMP commitment from being finalized.

### Proof of Concept
1. User places a cross-chain order on chain A escrowing USDC, with `order.user` set to address `U`.
2. Before the order is filled, USDC blacklists `U` (e.g., due to unrelated OFAC/compliance action).
3. Order expires or is cancelled from the destination chain; `RefundEscrow` message is dispatched back to chain A with `WithdrawalRequest.beneficiary = U`.
4. `onAccept` on chain A calls `_withdraw`, which calls `IERC20(usdc).safeTransfer(U, amount)` — reverts because `U` is blacklisted (per `evm/src/apps/intentsv2/IntentsBase.sol:404-409`).
5. The relayer/host retries delivery of the same commitment; `dispatchIncoming` deletes the receipt and returns on failure (`evm/src/core/EvmHost.sol:811-818`), so the message is resubmittable, but `_withdraw` reverts identically every time since `beneficiary` never changes.
6. The escrowed USDC for this commitment is now permanently locked in the `IntentGateway` contract with no available function to redirect or claim it.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
