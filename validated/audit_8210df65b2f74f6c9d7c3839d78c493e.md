### Title
Arbitrary File Write via Unsanitized `foldername` Parameter in DataLayer `add_missing_files` RPC - (File: chia/data_layer/data_layer_rpc_api.py)

### Summary
The `add_missing_files` RPC endpoint of the DataLayer service accepts a caller-supplied `foldername` string and converts it directly to a `Path` object with no validation, normalization, or containment check against the service's intended `server_files_location` directory. This path is then used as the destination directory for writing DataLayer tree files (`.dat` full-tree/delta files), allowing an unprivileged RPC caller to redirect file writes to an arbitrary filesystem location, including outside the DataLayer's designated storage folder — the same class of bug (unsanitized path parameter accepted by a service endpoint, enabling writes outside the intended directory, CWE-22/CWE-440) as the referenced LoLLMS `sanitize_path`/`discussion_db_name` advisory.

### Finding Description
In `DataLayerRpcApi.add_missing_files`, the `foldername` field from the RPC request is taken verbatim and wrapped in `Path()`: [1](#0-0) 

This `foldername` is passed straight through to `DataLayer.add_missing_files`, where it overrides the service's default `server_files_location` with no sanitization, no `resolve()`-then-containment check, and no restriction to relative paths: [2](#0-1) 

That `server_files_location` (attacker-controlled) is then handed to `write_files_for_root`, which computes concrete file paths under it via `get_full_tree_filename_path`/`get_delta_filename_path`, creates any missing parent directories (`filename_full_tree.parent.mkdir(parents=True, exist_ok=True)`), and opens the file for writing: [3](#0-2) 

Critically, the write mode depends on the caller-supplied `overwrite` flag:
```
mode: Literal["wb", "xb"] = "wb" if overwrite else "xb"
```
When `overwrite=True` is also passed in the RPC request (`chia/data_layer/data_layer_rpc_api.py:411`), the file is opened in truncate/write (`"wb"`) mode rather than exclusive-create (`"xb"`) mode, meaning an existing file at the attacker-chosen path will be silently truncated and overwritten with DataLayer tree-node serialization data.

Unlike the DataLayer HTTP static file server (`chia/data_layer/data_layer_server.py`), which validates filenames via `is_filename_valid` before constructing paths under a fixed `server_files_location`, no equivalent containment/validation logic exists for the `foldername` parameter accepted by the RPC layer.

### Impact Explanation
A caller of the DataLayer RPC (an unprivileged local/authorized DataLayer RPC client) can supply an absolute or `../`-relative `foldername` to redirect file writes anywhere the DataLayer process has filesystem permissions — for example, into other chia service directories under the same `CHIA_ROOT`, config directories, or arbitrary writable paths. Combined with `overwrite=True`, this allows truncation/overwrite of existing files at attacker-chosen locations, which can corrupt configuration or state files and cause denial of service for the DataLayer or co-located services sharing the filesystem. This matches the "invalid spend or block acceptance ... spend-triggered transaction-processing halt" and expected-behavior-violation impact class analogous to the LoLLMS advisory (arbitrary write to important system folders).

### Likelihood Explanation
The endpoint is reachable directly through the standard DataLayer RPC surface (`add_missing_files`) with no additional privilege beyond normal DataLayer RPC access, matching the in-scope "local RPC caller" persona. No cryptographic material, consensus interaction, or privileged network position is required — a single RPC call with a crafted `foldername` (and optional `overwrite: true`) is sufficient to trigger the write.

### Recommendation
Sanitize and constrain `foldername` in `DataLayerRpcApi.add_missing_files` (and any other RPC/service entry point accepting a folder/file path) by:
- Rejecting absolute paths and any path components containing `..`.
- Resolving the final path and verifying it remains within the service's configured `server_files_location` (or an explicitly allow-listed base directory) before use.
- Considering removal of caller-controlled `foldername` overrides entirely for the RPC path, restricting it to trusted internal callers (e.g., CLI/dev tooling) only, since the primary production use case does not require write-location control from arbitrary RPC input.

### Proof of Concept
1. Start the DataLayer service and note its `CHIA_ROOT`/`server_files_location`.
2. Call the RPC endpoint:
```
POST /add_missing_files
{
  "ids": ["<32-byte-store-id-hex>"],
  "overwrite": true,
  "foldername": "/absolute/attacker/chosen/path"
}
```
3. Observe that `DataLayer.add_missing_files` (`chia/data_layer/data_layer.py:843`) uses the supplied `foldername` as `server_files_location`, and `write_files_for_root` (`chia/data_layer/download_data.py:69`) creates parent directories and writes/truncates `.dat` files at `/absolute/attacker/chosen/path/<store_id>-<node_hash>-full-<generation>-v1.0.dat`, confirming writes occur outside the intended `server_files_location` sandbox.
