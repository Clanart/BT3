### Title
`ReceivedOutput::read` deserializes unverified outputs, reporting non-spendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` bundles a scalar `offset`, a `TxOut`, and an `OutPoint`, and the correctness of an output as "ours" depends entirely on the invariant `output.script_pubkey == p2tr_script_buf(key + offset*G)`. That invariant is established only inside `Scanner::scan_transaction`, which builds the struct by looking up `output.script_pubkey` in the registered `scripts` map. However, `ReceivedOutput::read` (the `#[cfg(feature = "std")]` deserialization path) accepts arbitrary bytes and reconstructs the three fields with no consistency check. Any consumer that treats a deserialized `ReceivedOutput` as a received, spendable output will therefore accept attacker-crafted bytes claiming ownership of outputs whose script does not correspond to the supplied offset — the analog of a variant-uniform "is claimable" check returning the wrong answer for a class of objects.

### Finding Description
In `networks/bitcoin/src/wallet/mod.rs`, `Scanner::scan_transaction` only constructs a `ReceivedOutput` after confirming `self.scripts.get(&output.script_pubkey)` yields the registered offset, so scanner-produced outputs satisfy `p2tr(key + offset*G) == script_pubkey`. `ReceivedOutput::read` (lines 122-134) instead reads `Secp256k1::read_F` for the offset, then `TxOut::consensus_decode` and `OutPoint::consensus_decode`, and returns `Ok(ReceivedOutput { offset, output, outpoint })` unconditionally. There is no way for `read` to bind the fields to each other or to any key, and `ReceivedOutput` exposes the result via `value()`/`output()`/`outpoint()` accessors as if it were a genuine received output. The only place the offset/script linkage is ever re-verified is inside `SignableTransaction::multisig` (`networks/bitcoin/src/wallet/send.rs` lines 273-284), which returns `None` on mismatch — so the funds are reported "received" by `read` but are provably unspendable.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (the whitelisted untrusted surface) can cause a host to record a received output for any arbitrary `TxOut`/`OutPoint` — e.g., a UTXO paying to an unrelated address, or a nonexistent outpoint. The output will be reported as received with its nominal `value()` while `multisig()` can never produce a valid signature for it (or it may not even exist on chain). This is the accepted "funds reported received that are not spendable" impact, matching the report's class where a predicate reports a wrong claimability result for certain object variants.

### Likelihood Explanation
Reachability requires an integrator to deserialize `ReceivedOutput`s from an untrusted transport (e.g., outputs relayed between components or persisted/reloaded) rather than only constructing them via `Scanner`. `read` is a public API under `std`, and nothing in its signature warns that the result is unverified; the struct provides no `verify`/`is_spendable` method at all. The severity hinges on downstream trust of `read`'s output for balance/credit accounting, which is plausible but integrator-dependent — Medium at best.

### Recommendation
Either remove the standalone deserializer or bind it to a key: make `ReceivedOutput::read` take the `ProjectivePoint` (or `Scanner`) it claims to belong to and reject bytes where `p2tr_script_buf(key + offset*G) != output.script_pubkey`. Alternatively, introduce an unverified wrapper type and only expose `ReceivedOutput` after a verification step.

### Proof of Concept
```rust
// Given the wallet's base key P (even-Y tweaked group key) and any UTXO that does
// NOT pay to a registered offset of P — e.g., someone's address A:
let attacker_bytes = {
    let mut b = Vec::new();
    // arbitrary offset, e.g. 7
    b.extend(Scalar::from(7u64).to_bytes());
    // TxOut paying to the attacker's own address, not to p2tr(P + 7G)
    b.extend(serialize(&TxOut {
        value: Amount::from_sat(100_000),
        script_pubkey: ScriptBuf::new_p2tr_tweaked(
            TweakedPublicKey::dangerous_assume_tweaked(x_only(&attacker_key)),
        ),
    }));
    // any OutPoint, real or fabricated
    b.extend(serialize(&OutPoint::new(victim_txid, 0)));
    b
};

// ReceivedOutput::read accepts this and reports a 100k-sat "received" output,
// which SignableTransaction::multisig (send.rs:273-284) can never sign for.
let fake = ReceivedOutput::read(&mut attacker_bytes.as_slice()).unwrap();
assert_eq!(fake.value(), 100_000); // credited, yet unspendable
```

Note: `Scanner::scan_block` also surfaces a related variant-uniformity issue by including coinbase outputs (which are immature for 100 blocks), but this is documented in the doc comment at `wallet/mod.rs` lines 216-220, so it falls under the documented-misuse exclusion and is not part of this finding.
