### Title
Vault `deposit` trusts the stated transfer amount instead of the tokens actually received, permanently mispricing vault shares if the underlying is a fee-charging or short-transferring SIP-010 token - (File: `mainnet/contracts/vault/v0-vault-usdh.clar`, and identically in `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Every Zest vault's `deposit` function mints shares from, and books internal `assets` accounting with, the caller-supplied `amount` parameter rather than the amount the vault actually received from `receive-underlying`. If the underlying SIP-010 token ever delivers less than the requested `amount` (fee-on-transfer, rebasing, or any other short-transfer behavior), the vault's `assets` variable becomes permanently inflated relative to its real token balance. This corrupts the share exchange rate (`convert-to-assets-preview`/`convert-to-shares-preview`) used for redemptions and corrupts `utilization`/`interest-rate`/liquidity-index computations that ultimately drive the zToken price used as collateral in `market.clar`.

### Finding Description
In every vault contract, `deposit` computes `inkind` (shares to mint) from the raw `amount` argument, calls `receive-underlying` with that same `amount`, and then unconditionally books the same `amount` into the `assets` state variable, with no verification that the vault's actual token balance increased by `amount`: [1](#0-0) 

`receive-underlying` simply calls the underlying SIP-010 `transfer` and returns `ok true` regardless of how much was actually credited to the vault: [2](#0-1) 

The same unguarded pattern (`try! receive-underlying`, then `var-set assets (+ current-assets amount)`, using the stated `amount` and not an actual pre/post balance delta) is repeated identically in `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, and `v0-vault-ststxbtc.clar` (and their `local-testing` counterparts): [3](#0-2) [4](#0-3) 

The book-value `assets` is then the sole input to `total-assets`/`total-assets-preview`, which drive both the redemption exchange rate and `utilization()`: [5](#0-4) 

`utilization()` feeds `interest-rate()`, which drives `next-index`/`next-liquidity-index`, and per `docs/oracle.md`, the zToken price used as collateral in `market.clar` is `base_price * liquidity_index`: [6](#0-5) 

Thus a single deposit where the vault receives less than the stated `amount` permanently inflates `assets` relative to the vault's real token holdings, without ever being corrected, because the same "trust the parameter" pattern is used for every subsequent deposit and interest accrual.

### Impact Explanation
- Direction of the error and who is affected: the depositor whose transfer under-delivers is unaffected on their own mint (`inkind` is computed from the *pre-deposit* exchange rate, before the shortfall occurs), but the vault's recorded `assets` ends up permanently larger than its real underlying balance by the shortfall amount. This overstates the backing for every other zToken holder's shares.
- On redemption, `convert-to-assets-preview` (`ta * amount / ts`) uses this inflated `ta`, so later redeemers are paid out more underlying per share than the vault actually holds, depleting real reserves faster than intended and risking that the last redeemers cannot withdraw (temporary/permanent freezing of funds) or that the vault becomes insolvent.
- Because the same inflated `assets` also lowers computed `utilization` and feeds the liquidity index that prices zTokens as collateral in `market.clar` (`resolve-ztoken`), the corrupted state can also propagate into an overstated collateral valuation used for LTV/health checks, i.e., a wrong health verdict for positions collateralized with the affected zToken.
- This lands in the Critical impact class: theft of yield/permanent freezing of unclaimed funds and potential protocol insolvency, since the discrepancy between book assets and real assets never self-corrects and compounds with every affected deposit.

### Likelihood Explanation
The bug is triggered any time the underlying SIP-010 `transfer` called by `receive-underlying` credits the vault with less than the requested `amount` — a fee-on-transfer token, a token with a maximum-transfer/rounding quirk, or any future underlying added via the generic `<ft-trait>` deposit path (`supply-collateral-add` in `market.clar`) that doesn't guarantee a 1:1 transferred amount. Given Zest already supports multiple third-party SIP-010 underlyings (`sbtc-token`, `ststx-token`, `usdh-token-v1`, `usdcx`) and explicitly allows generic `<ft-trait>` tokens through `supply-collateral-add`, the precondition (a non-standard-behaving transfer) is realistic for future or as-yet-unaudited listed assets, and the resulting accounting drift is silent and irreversible once it occurs.

### Recommendation
In every vault's `deposit` (and any other function crediting `assets` from a token transfer), measure the actual balance delta instead of trusting the caller-supplied `amount`: read `ubalance()` (or the equivalent balance-fetch) before and after calling `receive-underlying`, and use `(- balance-after balance-before)` both for `inkind` (share) calculation and for the `assets` increment. Apply the same balance-delta pattern symmetrically to `send-underlying`/withdrawal paths if the underlying token could similarly short-deliver on outgoing transfers.

### Proof of Concept
1. Assume vault `v0-vault-usdh` has `assets = 1,000,000` and `total-supply = 1,000,000` shares (1:1 price), and its underlying `usdh-token-v1` token contract implements (now or via a future upgrade/migration to another underlying) a 1% fee-on-transfer.
2. Alice calls `deposit(amount=100,000, min-out=0, recipient=alice)`.
3. `inkind` is computed as `convert-to-shares-preview(100000)` using pre-deposit `ta=1,000,000, ts=1,000,000` → `inkind = 100,000` shares minted to Alice: [7](#0-6) 
4. `receive-underlying(100000, alice)` calls `usdh-token-v1 transfer 100000 alice current-contract none`; due to the 1% fee, the vault's real token balance only increases by 99,000: [2](#0-1) 
5. `(var-set assets (+ current-assets amount))` books `assets = 1,000,000 + 100,000 = 1,100,000`, even though the vault's real token balance is only `1,000,000 + 99,000 = 1,099,000` — a permanent 1,000-unit accounting overstatement.
6. Total shares are now `1,100,000` (Alice's 100,000 + existing 1,000,000), and `ta/ts` still reads `1,100,000/1,100,000 = 1.0`, but real backing is `1,099,000/1,100,000 < 1.0`. Every existing/future shareholder's `convert-to-assets-preview` redemption will now pay out slightly more than the vault actually holds, and the drift compounds with every such deposit until reserves are insufficient to honor the last redeemers.

(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((price (if (is-eq aid u2)
                   (try! (resolve-ststx p))  // zststx: apply ratio first
                   p))
        (li (get index (unwrap-panic (get-cached-indexes aid)))))
