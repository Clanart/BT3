### Title
Reentrancy in `IntentGatewayV2.withdraw()` sends tokens before decrementing escrow accounting — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in the Tron `IntentGatewayV2` contract performs the external token/native transfer to the beneficiary *before* updating the `_orders[commitment][token]` escrow accounting, violating checks-effects-interactions. This is the same class of bug as the reported `handle_redeem` issue: a state-mutating bookkeeping step (there: `update_stake_and_total_stake_by_debtor`, here: `_orders[...] -= amount`) is deferred to *after* the value-moving action instead of before/atomically with it, leaving a window where the on-chain accounting does not yet reflect the just-issued payout.

### Finding Description
`withdraw()` is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse()` for cancellation-confirmation flows. [1](#0-0) [2](#0-1) 

Inside `withdraw()`, for each token in the withdrawal request the contract sends value to `beneficiary` via a low-level `.call` (native ETH) or an ERC-20 `transfer` call, and only *afterwards* decrements `_orders[body.commitment][token]`: [3](#0-2) 

Compare this to the sibling implementation in `IntentsBase.sol` (used by the main EVM `IntrinsicIntents`/`ExtrinsicIntents` contracts), which correctly updates `_orders[body.commitment][token]` **before** making the external call — i.e., effects before interactions: [4](#0-3) 

The corrupted value is `_orders[body.commitment][token]`: at the moment the beneficiary's `.call{value: amount}("")` (native-token branch) executes, this storage slot still holds the pre-withdrawal (undeducted) escrow balance. If `beneficiary` is a contract (attacker-controlled, since `body.beneficiary` derives from the order's `output.beneficiary`/`user` fields that route through cross-chain messages authenticated only by gateway-instance identity, not by trustworthiness of the beneficiary itself), the `.call` hands over control flow before the deduction happens.

`_filled[body.commitment]` is set at the very top of `withdraw()` before the loop, so a naive re-entry into `withdraw()` itself for the *same* commitment would still see stale escrow amounts on other, not-yet-processed tokens in a multi-token order — the `if (_orders[...] == 0) revert UnknownOrder()` check only guards against a token already fully zeroed, not against re-entering mid-loop with other still-nonzero token balances that legitimately belong to the same order but haven't yet been paid in this pass. More critically, any other function in this same contract (or a future/inherited one) that reads `_orders[commitment][token]` to gate an action — e.g. a hypothetical additional payout path, dust sweep, or an ERC-20 with a transfer hook (some tokens implement `ERC777`-like callbacks) — would observe the stale, not-yet-decremented balance during the reentrant call.

### Impact Explanation
This matches the bounty's "stealing or loss of funds" and "transaction manipulation" categories: an external call is made while the escrow ledger for that order still shows the full, undeducted balance. Any reentrant path that consults `_orders[commitment][token]` during that window (including the loop's own later iterations processing multiple tokens, or any external composition that trusts this contract's read of `_orders`) can act on stale state and cause double-payout or fund loss relative to the intended one-time settlement of escrowed funds.

### Likelihood Explanation
The `withdraw()` function is reachable via `onAccept()` for cross-chain `RedeemEscrow`/`RefundEscrow` messages that any relayer can deliver once authenticated as originating from a registered gateway instance — no privileged actor, malicious relayer, or governance compromise is required to trigger the call; the attacker only needs to control the `beneficiary` address encoded in the (legitimately authenticated) `WithdrawalRequest`, which is attacker-influenced by construction (it is the solver/user address from the order). The multi-token loop structure (`body.tokens.length > 1`) is a normal, unprivileged order shape, making the vulnerable code path directly reachable by an unprivileged solver/user placing/filling a multi-asset order with a beneficiary contract of their choosing.

### Recommendation
Reorder `withdraw()` to update `_orders[body.commitment][token] -= amount;` (effects) before performing the native/ERC-20 transfer (interactions), mirroring the safe pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw()`. Additionally consider adding a reentrancy guard to `withdraw()`/`onAccept()`/`onGetResponse()` as defense in depth, and use `SafeERC20.safeTransfer` instead of raw low-level `.call` with manual success checks for ERC-20 transfers, consistent with the main EVM implementation.

### Proof of Concept
1. Place a cross-chain order whose `output.beneficiary` (which becomes `WithdrawalRequest.beneficiary` on redemption) is an attacker-deployed contract, and whose `inputs`/escrow spans at least two tokens, one of which is native ETH (`token == address(0)`).
2. Have a relayer deliver the authenticated `RedeemEscrow` (or `RefundEscrow`) message so `onAccept()` calls `withdraw(body, ...)`. [1](#0-0) 
3. Inside the loop, when `token == address(0)`, the attacker beneficiary's `receive()`/`fallback()` fires during `beneficiary.call{value: amount}("")` — at this point `_orders[body.commitment][address(0)]` has **not yet** been decremented. [5](#0-4) 
4. From the attacker's `receive()` callback, reenter any function that reads `_orders[body.commitment][token]` (present or future contract logic, or an ERC-20 with transfer hooks in place of plain ETH) to extract value based on the stale, undeducted balance before the original call's `_orders[...] -= amount` executes.

Note: I was not able to fully trace every external caller of `_orders` across the whole Tron contract in this pass (line ranges beyond what was fetched may contain additional reads of `_orders` that would sharpen the concrete double-spend path); a Devin session with full file access should confirm all call sites that consult `_orders[commitment][token]` to nail down the most direct exploit sequence.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
