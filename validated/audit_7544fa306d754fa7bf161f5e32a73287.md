### Title
`calculate_share` emits a blame proof (revealing the ECDH decryption key) for attacker-malleated ciphertexts before verifying the message's proof-of-possession - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each incoming `EncryptedMessage` via `Encryption::decrypt`, which unconditionally computes the ECDH shared key and returns it inside an `EncryptionKeyProof`. The proof-of-possession (`pop`) Schnorr signature is only queued into a `BatchVerifier` whose results are checked later. If the decrypted share fails scalar deserialization (`C::F::from_repr`), the function returns early with `PedPoPError::InvalidShare { blame: Some(proof) }` — publishing a decryption key for a ciphertext whose PoP may be completely invalid — before `batch.verify_with_vartime_blame()` ever runs.

### Finding Description
The PedPoP design intentionally lets a recipient publish an `EncryptionKeyProof` revealing the ECDH key for a specific message so third parties can adjudicate blame (`crypto/dkg/pedpop/src/encryption.rs:259-298`, spec: "Distributed Key Generation.md" §Blame). To prevent this leak channel being abused for messages the sender didn't actually create, each `EncryptedMessage` carries a Schnorr proof-of-possession over its ephemeral key, bound to the sender index and ciphertext via `pop_challenge` (`encryption.rs:83-91`).

The enforcement gap is ordering. In `calculate_share` (`crypto/dkg/pedpop/src/lib.rs:476-499`):

```rust
let (mut share_bytes, blame) =
  self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
let share =
  Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
    PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
  })?);
```

`decrypt` only *queues* the PoP check (`msg.pop.batch_verify(...)`) and immediately returns the plaintext plus the revealing `EncryptionKeyProof` (`encryption.rs:479-500`). The `from_repr` failure path returns `Some(blame)` before `batch.verify_with_vartime_blame()` is reached. Because ChaCha20 is a malleable keystream cipher (`encryption.rs:101-133`), an attacker who observes any honest participant's encrypted share on the wire can bit-flip the scalar bytes: the PoP will be invalid (challenge binds sender index and ciphertext), yet decryption still "succeeds", yields a non-canonical scalar with high probability (for Ristretto, a random 32-byte string is canonical only ~1/16 of the time), and the early error path hands out the ECDH key for the honest participant's message anyway.

### Impact Explanation
Publishing the `EncryptionKeyProof` discloses `shared_key = enc_key_recipient * msg.key` (`encryption.rs:487-498`), which is exactly what's needed to derive the ChaCha20 keystream and recover the original secret share plaintext `f_sender(recipient)`. This is precisely the side-effect the PoP was added to prevent (comments at `encryption.rs:83-91`, spec §Blame: a co-opted/blamed message "also reveals the message"). Repeating the attack against `t` distinct recipients' copies of the same sender's messages recovers `t` evaluations of that sender's secret polynomial, enabling interpolation of its secret — i.e., key share recovery from publicly reachable inputs (relayable ciphertexts), with the blame proofs broadcast for public adjudication (as in `CoordinatorMessage::VerifyBlame`).

### Likelihood Explanation
An unprivileged observer/relayer of DKG traffic needs only a observed `EncryptedMessage` and XOR malleability of the ChaCha20 ciphertext — no secret knowledge, no valid PoP, no collusion. Each attempt succeeds with ~15/16 probability and can be retried freely across participants/messages. The only mitigation is that the adversary is later blamed as sender once the blame is adjudicated — but the secret material is already public by then.

### Recommendation
Verify the PoP *before* constructing or releasing the `EncryptionKeyProof`. Practically: in `calculate_share`, do not attach `blame` on the `from_repr` early-return path until `batch.verify_with_vartime_blame()` has been run (restructure so the batch is verified first and `BatchId::Decryption`/`BatchId::Share` distinguishes PoP failures from share failures), or perform the PoP check eagerly inside `decrypt` and refuse to produce an `EncryptionKeyProof` for a message whose PoP is invalid. The invariant should be: an `EncryptionKeyProof` revealing an ECDH key is only ever emitted for a ciphertext that was authenticated as originating from the claimed sender.
