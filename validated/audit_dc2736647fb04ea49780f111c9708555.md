### Title
Use-After-Free of cached Python message wrapper via oneof switch inside a map value during `MergeFrom`/`MergeFromString` - (File: `python/google/protobuf/pyext/message.cc`)

### Summary
The CVE describes pyOpenSSL retaining a stale reference to a freed `X509` object because an internal C operation freed/replaced memory that a Python-level wrapper still pointed to (CWE-416, no revalidation of the wrapper after the underlying object's lifetime changed). Protobuf's C++-extension Python bindings already recognize and defend against exactly this bug class for one specific path — oneof field switching during `Message.MergeFrom()`/`ParseFromString()` — but the defense (`MaybeReleaseOneofBeforeMerge`) only walks singular (non-repeated) message fields, not repeated/map fields, leaving a code-reachable gap for message-valued map fields whose values contain a oneof.

### Finding Description
`CMessage` wrappers in the C++ Python extension hold raw `Message*` pointers into a real C++ object tree that is owned elsewhere (a parent message or, for a top-level message, the CMessage itself) [1](#0-0) . When a oneof field is switched, the previous submessage instance is deleted, so any previously-created Python `CMessage` wrapper that still points at the old submessage becomes dangling. This is exactly the class of bug in the report: an attacker/caller-controlled operation (`MergeFrom`/`ParseFromString`) frees an object referenced by a live handle without notifying the handle.

Protobuf has explicit awareness of this and mitigates it for one case. In `MergeFromStringImpl`, the comment states directly:
"We parse into a temporary message first to detect oneof switches before modifying the target message. This allows us to release the wrappers for switching oneof fields in the target message before they are deleted by C++ during the merge, preventing use-after-free bugs." [2](#0-1) 

The actual detection/release logic is `MaybeReleaseOneofBeforeMerge`: [3](#0-2) 

Critically, the recursion filter is:
```cpp
if (descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE &&
    // For normal repeated message, MergeFrom will append the messages.
    // For message map with same keys, it is overwrite
    !descriptor->is_repeated() &&
    reflection->HasField(*message, descriptor)) {
``` [4](#0-3) 

This explicitly excludes any field for which `is_repeated()` is true — which includes **map fields** (map fields are represented internally as repeated message fields at the `FieldDescriptor` level). The inline comment even acknowledges that message-map entries with matching keys are merged in place ("overwrite"/recursive-merge), yet the code takes no action for that case — it neither recurses into the map's values to detect/release nested oneof switches, nor releases the map's own composite wrapper.

If a cached Python `CMessage` wrapper exists for a value inside a message-typed map field (created earlier by the caller accessing `msg.map_field[key].some_field`), and that map-value submessage itself has a `oneof`, then a subsequent `MergeFrom`/`ParseFromString` call that recursively merges a map entry with the same key and switches the value message's active oneof case will cause the C++ layer to delete the previously active oneof submessage — while the earlier-obtained Python wrapper for it is never located or invalidated by `MaybeReleaseOneofBeforeMerge`, because the top-level map field is skipped by the `!descriptor->is_repeated()` filter before any recursion into its values ever happens.

### Impact Explanation
This produces the same primitive as the CVE: a live, attacker-influenceable Python object continues to reference C++-heap memory that has been freed. Any subsequent read/access through the stale Python message wrapper (e.g., reading a field, calling a method) dereferences freed memory, which is Use-After-Free (CWE-416). Depending on allocator reuse this can cause information disclosure or memory corruption, consistent in kind (though not necessarily in exploitability) with the pyOpenSSL analog. It is scoped to consuming applications that (a) build a `Message` with a message-valued map field whose value type contains a `oneof`, (b) cache a reference to a nested oneof submessage obtained through that map, and (c) subsequently call `MergeFrom`/`ParseFromString` again with attacker-supplied bytes that hit the same map key and switch the oneof. This matches the required exposure model: an ordinary client supplying bounded, valid Protobuf binary through a public parse API (`MergeFromString`/`ParseFromString`), consumed by trusted application code that happens to hold onto sub-object references — a legitimate, sanctioned usage pattern of the Python API (accessing message fields returns cached wrapper objects by design, as documented in `message.h`).

### Likelihood Explanation
Medium. It requires: (1) a schema with a message-typed map field whose value message contains a `oneof`, (2) application code retaining a reference to a submessage obtained via that map (a normal, encouraged usage pattern of the pure-Python-compatible C++ extension API), and (3) a second parse/merge call with attacker-controlled bytes reusing the same map key while switching the oneof value. This is a real, not contrived, application pattern (e.g., repeatedly merging incremental updates keyed by ID into a map, where each value has a `oneof` payload). It's specific to the C++ (`pyext`) Python implementation; the pure-Python and upb backends have different object-lifetime models and were not confirmed to be vulnerable in this checkout (not fully verified here — upb Python bindings use a different arena/GC-based ownership model documented in `docs/upb/wrapping-upb.md`, which may or may not exhibit the same gap; this needs further code confirmation in `python/message.c`/`map_container.c` upb sources, which I was unable to fully inspect before running out of iterations).

### Recommendation
Extend `MaybeReleaseOneofBeforeMerge` (and its `ForEach` filter in `python/google/protobuf/pyext/message.cc`) to also traverse message-valued map fields (and, defensively, repeated message fields whose semantics might change in the future) recursively, releasing/detaching any cached Python wrappers for nested submessages whose oneof case will be overwritten by the incoming merge, exactly as is already done for singular message fields. Alternatively, treat any map key present in both `self` and `other` for message-valued maps as requiring the same wrapper-release recursion currently applied only to `!descriptor->is_repeated()` fields, before calling `message->MergeFrom(*temp_message)`.

### Proof of Concept
Conceptual repro outline (requires a `.proto` schema like):
```proto
message Value { oneof kind { int32 a = 1; string b = 2; } }
message Container { map<string, Value> items = 1; }
```
```python
c = Container()
c.items["k"].a = 1
cached = c.items["k"]          # Python wrapper caches C++ Value* for key "k"
print(cached.a)                # valid access

other = Container()
other.items["k"].b = "x"        # same key, different oneof branch
c.MergeFrom(other)              # C++ recursively merges map entry "k": ClearOneof
                                 # deletes the int32 arm's storage / switches case;
                                 # MaybeReleaseOneofBeforeMerge never visited "items"
                                 # because FieldDescriptor for "items" is_repeated()==true.

print(cached.a)                 # use-after-free / stale wrapper access
```

int MaybeReleaseOneofBeforeMerge(CMessage* self, const Message& other) {
  CMessage::CompositeFieldsMap* composite_fields =
      self->composite_fields.TryGet();
  if (!composite_fields) {
    return 0;
  }

  Message* message = AssureWritable(self);
  if (message == nullptr) return -1;
  const Reflection* reflection = message->GetReflection();
  PyMessageFactory* factory = GetFactoryForMessage(self);
  std::vector<const FieldDescriptor*> fields_to_release;
  std::vector<std::pair<const FieldDescriptor*, ScopedPyObjectPtr>>
      nested_message_fields;
  composite_fields->ForEach([&](const void* key, PyObject* value) {
    const FieldDescriptor* descriptor =
        reinterpret_cast<const FieldDescriptor*>(key);
    if (descriptor->cpp_type() == FieldDescriptor::CPPTYPE_MESSAGE &&
        // For normal repeated message, MergeFrom will append the messages.
        // For message map with same keys, it is overwrite
        !descriptor->is_repeated() &&
        reflection->HasField(*message, descriptor)) {
      if (reflection->HasField(other, descriptor)) {
        Py_INCREF(value);
        nested_message_fields.emplace_back(descriptor, value);
      } else {
        // Release oneof message if the other message has set a different oneof
        const OneofDescriptor* oneof = descriptor->containing_oneof();
        if (oneof && reflection->HasOneof(other, oneof)) {
          fields_to_release.push_back(descriptor);
        }
      }
    }
  });

  for (const auto& [field, value] : nested_message_fields) {
    if (MaybeReleaseOneofBeforeMerge(
            reinterpret_cast<CMessage*>(value.get()),
            reflection->GetMessage(other, field, factory->message_factory)) <
        0) {
      return -1;
    }
  }

  for (const FieldDescriptor* field : fields_to_release) {
    if (InternalReleaseFieldByDescriptor(self, field) < 0) {
      return -1;
    }
  }
  return 0;
}
