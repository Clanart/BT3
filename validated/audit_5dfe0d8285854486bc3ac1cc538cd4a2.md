### Title
Forfeited MGP rewards routed through `_queueNewRewardsWithoutTransfer` in `vlMGPBaseRewarder` (and the analogous `_queueNewRewardsWithoutTransfer` in `mWOMSVBaseRewarder`) are never registered as a claimable reward token, permanently freezing forfeited user MGP - (File: rewards/vlMGPBaseRewarder.sol)

### Summary
When a vlMGP holder's locked MGP is force-unlocked or claimed early, a portion is forfeited via `_calExpireForfeit` and re-queued into the reward pool as a "reward" using `_queueNewRewardsWithoutTransfer`. Unlike `queueNewRewards`, this internal function never adds the reward token to the `rewardTokens` array or sets `isRewardToken[token] = true`. Since all reward accrual/claim logic (`_updateFor`, `getReward`, `_sendReward`) only iterates over the `rewardTokens` array, forfeited MGP that is not already a tracked reward token is credited into `rewards[MGP].rewardPerTokenStored` / `queuedRewards` but is unreachable by any user claim path, mirroring the Autonomint pattern of a yield value being "recorded" internally with no mechanism to withdraw or distribute it.

### Finding Description
`vlMGPBaseRewarder.queueMGP` computes a forfeit amount from expired/early-exiting positions and, when `forfeitAmount > 0`, calls `_queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()))`: [1](#0-0) 

`_queueNewRewardsWithoutTransfer` updates `historicalRewards` and either `queuedRewards` or `rewardPerTokenStored` for the given token, but — critically — it does **not** push the token into the `rewardTokens` array nor set `isRewardToken[_rewardToken] = true`, unlike the sibling `queueNewRewards` function which explicitly does register new tokens: [2](#0-1) 

Reward accrual and payout are driven entirely by iteration over `rewardTokens`: [3](#0-2) 

and `_sendReward`/`getReward`-style flows only ever process tokens present in that array. The identical pattern exists in `mWOMSVBaseRewarder`, where `_sendReward` re-queues forfeited amounts via the same unregistering helper: [4](#0-3) 

If the MGP token used for forfeiture (`address(vlMGP.MGP())`) is not already part of `rewardTokens` for that rewarder instance (e.g. because the rewarder's registered/default reward token is `WOM`, not `MGP`), the forfeited MGP balance sits in the contract's token balance and in `rewards[MGP].rewardPerTokenStored`/`queuedRewards`, but no user's `userRewards[MGP][account]` is ever incremented, because `_updateFor` never visits an unregistered token. There is no owner/manager function that sweeps or re-registers this specific forfeited-MGP balance either, so the funds become permanently unreachable — functionally identical to the Autonomint bug where `updateYieldsFromLiquidatedLrts` recorded a yield value with no corresponding withdrawal path.

This is reachable from an ordinary wallet: any vlMGP holder calling `startUnlock`/`unlock`/`forceUnLock` triggers `IMasterMagpie(masterMagpie).multiclaimFor(...)`, which flows into the rewarder's claim/queue logic and can trigger forfeiture accounting through `queueMGP`/`_sendReward`, without any privileged action required. [5](#0-4) [6](#0-5) 

### Impact Explanation
Forfeited MGP tokens (penalty/expiry-driven, a portion of user-owned locked value) are transferred into the rewarder contract but become permanently unclaimable by anyone — this is a permanent freezing of user funds/yield with no recovery mechanism, matching the accepted impact class of "theft or permanent freezing of unclaimed yield."

### Likelihood Explanation
The path is triggered purely by normal, unprivileged user actions (`startUnlock`, `unlock`, `forceUnLock` on `VLMGP`/`mWomSV`, or normal claim flows that invoke `queueMGP`), with no attacker-controlled precondition and no admin/governance involvement required. Any time a forfeiture occurs on a token not already registered in `rewardTokens` for that specific rewarder, the funds are stuck.

### Recommendation
In `_queueNewRewardsWithoutTransfer` (both `vlMGPBaseRewarder.sol` and `mWOMSVBaseRewarder.sol`), register the reward token the same way `queueNewRewards` does — check `isRewardToken[_rewardToken]`, and if false, push it into `rewardTokens` and set `isRewardToken[_rewardToken] = true` before crediting `rewardPerTokenStored`/`queuedRewards`. Alternatively, ensure the constructor/initializer always registers the MGP/mWOM token as a reward token before any forfeiture logic can run, and add an owner-callable rescue/backfill function to redistribute any already-stranded forfeited balances to current stakers.

### Proof of Concept
1. Deploy `vlMGPBaseRewarder` with only `WOM` (or another token) as the initially registered reward token (constructor content not fully verifiable from available index, but `rewardTokens` starts empty/with a different token per the pattern seen in `BaseRewardPool`'s constructor).
2. A user locks MGP in `VLMGP`, then calls `startUnlock` followed by `forceUnLock` before the cooldown ends, or otherwise reaches a path where `queueMGP` is invoked with `_account` having `rewardablePercentWAD < 1e18` per `_calExpireForfeit`. [7](#0-6) 
3. `queueMGP` computes `forfeitAmount > 0` and calls `_queueNewRewardsWithoutTransfer(forfeitAmount, address(vlMGP.MGP()))`.
4. Because `MGP` was never pushed into `rewardTokens`/`isRewardToken`, no subsequent call to `getReward`/`_updateFor` for any staker will ever include or pay out this MGP balance — the tokens remain in the contract indefinitely with no owner sweep function targeting this specific balance.

Note: I was unable to confirm from the indexed files whether `MGP` is pre-registered as a reward token in the `vlMGPBaseRewarder` constructor/initializer (the file's earlier lines were not retrievable in this session due to iteration limits), which affects whether this scenario triggers on every deployment or only under specific configurations. A Devin session with full repo access should verify the constructor/initializer of `vlMGPBaseRewarder.sol` and `mWOMSVBaseRewarder.sol` to confirm which reward tokens are registered at deployment and confirm the stuck-funds scenario end-to-end.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
        uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
