### Title
Stale Copilot conflict-resolution content can be applied without re-validating it against the current conflict state - ([File: app/src/lib/stores/app-store.ts])

### Summary
`Pool.sol`'s bug class is: validation is enforced when a change is *proposed*, but not re-enforced when the change is *executed*, so state can drift between the two phases and the execute step applies a now-invalid change. GitHub Desktop's Copilot-assisted merge-conflict resolution flow has the same shape: conflict content is analyzed and resolutions are computed once (the "propose" phase), then applied to disk later (the "execute" phase) after the user reviews a summary dialog — but the execute step never re-checks that the resolved content still corresponds to the conflict that currently exists on disk.

### Finding Description
`_startCopilotConflictResolution` computes AI-generated resolutions from the conflict content present at the time it runs and stores them on `multiCommitOperationState.copilotResolutions` [1](#0-0) . The actual disk write and `git add` only happen later, in `_applyCopilotConflictResolutions`, when the user clicks "Continue Merge" [2](#0-1) .

At execution time the only checks performed are: (1) the resolved path stays inside the repository (`resolveWithin`), and (2) the file is still reported as conflicted with unresolved markers [3](#0-2) . Notably absent is any check that the *content* of the conflict currently on disk is the same content the AI resolution was computed from (no hash/oid binding of `resolution.resolvedContent` to the conflict hunks or merge-base/target commit that produced it). This mirrors the `Pool.sol` pattern: `removeFromCommittee`/`changeCommitteeThreshold` validate `committeeThreshold` at proposal time but `_executeRemoveFromCommittee`/`_executeChangeCommitteeThreshold` never re-check it, so intervening state changes silently produce an invalid outcome.

Here, an intervening state change is entirely plausible because the window between "propose" (AI resolution computed) and "execute" (write to disk) is unbounded — it is however long the user takes to review the result dialog. During that window the repository state can change (e.g., the user aborts and restarts the conflict resolution, fetches new data from the remote, or another workflow updates the same file), the conflict markers can still be present, and `_applyCopilotConflictResolutions` will happily overwrite that new, unreviewed conflict content with the stale AI-computed content and stage it.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": the write path (`writeFile`) and staging (`git add`) execute unconditionally once the loose "still conflicted" check passes, with no verification that the applied content matches the conflict the user is actually looking at. Since a git remote/branch (attacker-controlled per the valid-impact scope) is precisely what supplies the conflicting content, a remote that changes between the propose and execute steps (e.g. via a race on fetch/rebase against a malicious or compromised remote) can cause Desktop to write and stage content that was resolved against a different, no-longer-current conflict, without the user ever seeing that mismatch.

### Likelihood Explanation
This requires no local access, admin rights, or social engineering beyond normal use of the Copilot-conflict-resolution feature against a repository whose remote content an attacker influences — squarely within the stated valid-impact scope (attacker controls a fetched repository / remote). The time-of-check-to-time-of-use window is a natural consequence of a human-reviewed dialog step sitting between resolution computation and file write, so the precondition (state changing in that window) is realistic, not contrived.

### Recommendation
Bind each `resolution` to the exact conflict content/blob it was computed from (e.g., store and re-check the conflicted file's blob SHA or hash of the pre-resolution content) and re-validate that binding in `_applyCopilotConflictResolutions` immediately before `writeFile`. If the on-disk conflict no longer matches, skip that file (same as the existing "resolved externally" skip logic) instead of silently overwriting it.

### Proof of Concept
1. Start a merge/rebase that produces a conflict; invoke `_startCopilotConflictResolution` so `copilotResolutions` is computed from conflict content C1 [1](#0-0) .
2. While the review dialog is open, cause the on-disk conflict for the same path to change to C2 while the file still reports `isConflictedFileStatus` with unresolved markers (e.g., abort/redo the operation against updated remote data, or another concurrent workflow touches the file) — this only requires the file to remain "conflicted", not that its content match C1.
3. Click "Continue Merge", triggering `_applyCopilotConflictResolutions`. The checks at lines 7233–7256 pass (path is inside repo, file is still conflicted), so `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` overwrites C2 with the AI resolution computed from C1, and the file is staged via `git add` [4](#0-3) , silently discarding/corrupting the newer conflict state the user actually intended to resolve.
