### Title
`SchnorrAggregate::verify` accepts a trivially forged aggregate signature over the empty signer set - ([File: crypto/schnorr/src/aggregate.rs])

### Summary
Analogous to CVE-2016-3085 (an authentication plugin whose verification path can be bypassed by crafted, attacker-controlled input), Serai's aggregate Schnorr verifier `SchnorrAggregate::verify` in `crypto/schnorr/src/aggregate.rs` returns `true` for a signature any unprivileged party can construct without any key: an `Rs` list of length 0 followed by a scalar `s = 0`. The verifier only checks that `Rs.len() == keys_and_challenges.len()` (0 == 0) and then evaluates a multiexponentiation containing the single pair `(-s, G)` = `(0, G)`, which is always the identity. No random weight is ever bound to a signature because the weight loop never executes, so the "per-signature weighting" defense the scheme relies on never engages. The deserializer `SchnorrAggregate::read` (lines 77-88) happily produces this object from 36 attacker-supplied bytes (`0x00000000` length prefix plus a zero scalar encoding).

### Finding Description
`SchnorrAggregate::verify` (crypto/schnorr/src/aggregate.rs:127-146) builds `pairs` as follows:

- `Rs.len() != keys_and_challenges.len()` → false. For an empty aggregate this passes when the caller's signer slice is empty.
- The transcript loop `for (_, challenge) in keys_and_challenges` appends nothing, and `weight()` is never invoked, so no entropy is mixed into the statement.
- The only pair pushed is `(-self.s, C::generator())` (line 144). With `s = 0`, `multiexp_vartime(&[(0, G)])` is the identity, so `verify` returns `true` (line 145).

Contrast with the single-signature path: `SchnorrSignature::verify` checks `R + cA - sG == 0` where `c` binds key, nonce, and message, so a zero forgery only works if the challenge is zero or the key is the identity — neither attacker-controllable (crypto/schnorr/src/lib.rs:88-110). The aggregate path removes exactly those bindings when the signer set is empty, and additionally diverges from the aggregator side: `SchnorrAggregator::complete` refuses to emit an empty aggregate (returns `None`, lines 175-178), but `verify` imposes no symmetric non-empty requirement, so read/verify and aggregate/complete are inconsistent.

### Impact Explanation
Any consumer that calls `SchnorrAggregate::verify` (or a wrapper such as a `SignatureScheme::verify_aggregate` implementation patterned on `Validators::verify_aggregate`, which forwards attacker bytes via `SchnorrAggregate::read` and only checks `signers.len() == aggregate.Rs().len()`) will accept a forged "signature" over any message whenever the declared signer set is empty. This is an authentication bypass of the exact CVE-2016-3085 shape: a plugin-style verification routine that validates attacker-supplied bytes without enforcing a minimum of one real signer. The forged signature is 36 bytes: `len = 0u32 LE` followed by the canonical encoding of scalar zero — no discrete log, no key material, no honest signer needed. Additionally, because `read` + `verify` are inconsistent with `aggregate`/`complete` (which reject empties), a verifier can be made to accept a serialization that no honest aggregator could ever produce — an undocumented acceptance difference.

### Likelihood Explanation
The forgery is deterministic and requires zero computation — any network peer who can cause a serialized aggregate signature to reach `SchnorrAggregate::read`/`verify` succeeds whenever the verifier is invoked over an empty signer list (e.g., a block/commit artifact claiming no signers, or an edge case where the caller's signer enumeration collapses to empty). It does not help when signers are non-empty, since each (R, c·key) pair is then bound by unpredictable `weight()` scalars drawn from a challenge transcript — limiting the impact to medium severity rather than a universal forgery.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::verify` (return `false` when `keys_and_challenges.is_empty()`, or when `self.Rs.is_empty()`), matching the existing non-empty guarantee in `SchnorrAggregator::complete`. Optionally also mirror the defense used elsewhere (e.g., `Signed::read`'s identity-`R` rejection) by rejecting an aggregate whose `s` is zero when `Rs` is empty, and document that a valid aggregate must contain at least one signature.

### Proof of Concept
```rust
// crypto/schnorr crate, any PrimeGroup ciphersuite C (e.g. dalek_ff_group::Ed25519)
use ciphersuite::Ciphersuite;
use schnorr::aggregate::SchnorrAggregate;

// Attacker-crafted bytes: 4-byte little-endian length 0, then scalar 0
let mut forged = 0u32.to_le_bytes().to_vec();
forged.extend(<C as Ciphersuite>::F::ZERO.to_repr().as_ref());

let agg = SchnorrAggregate::<C>::read::<&[u8]>(&mut forged.as_ref()).unwrap();
// Any DST; empty signer/challenge list
assert!(agg.verify(b"Any DST", &[])); // returns true — forged aggregate accepted
```
Root cause: `verify` at crypto/schnorr/src/aggregate.rs:127-146 never requires `Rs`/signer count ≥ 1, so the multiexp reduces to `(0)·G == identity` and unconditionally passes, while `read` (lines 77-88) imposes no minimum length either.
