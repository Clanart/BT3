Based on the investigation, I found `installAuthenticatedImageFilter` in `app/src/main-process/authenticated-image-filter.ts`, whose path-matching regex is the closest analog to a "missing minimum bound" validation flaw — a security-relevant check that enforces an upper-bound-like allowlist pattern but is too permissive at the boundary, similar in spirit to the fee-rate check that only validates one side of a range.

### Title
Overly-permissive asset-path regex causes Authorization header (repo access token) to be attached to attacker-influenced GitHub-origin paths - ([File: app/src/main-process/authenticated-image-filter.ts])

### Summary
`installAuthenticatedImageFilter` decides whether to attach a bearer `Authorization` token to outgoing `onBeforeSendHeaders` requests based solely on the request's `origin` (github.com / a GHE host) and whether the `pathname` matches a hand-rolled regex intended to only match known "safe" first-party asset endpoints (avatars, repo assets, user-attachments). [1](#0-0) 

### Finding Description
The filter's only gate for attaching the user's OAuth/PAT token to a request is a same-origin check plus a regex match on the URL path: [2](#0-1) 
There is no independent minimum/maximum bound or allow-list on the *content* of the path segments captured by `[^/]+` — the regex only enforces a loose *shape* ("some segment / some segment / assets / id / id"), not a validated, minimal, exact set of trusted path prefixes. Just as the audited contract validated an upper `feeRate` bound but omitted a floor, this filter validates that a URL is same-origin but omits a strict floor/allow-list on which paths are considered "safe" to receive the token — any path an attacker can get the renderer to request (e.g., via markdown image tags, PR body content, or GitHub API `avatar_url`/attachment fields rendered in the app, see `sandboxed-markdown.tsx` rendering of attacker-supplied markdown) that happens to satisfy the loose regex on a `github.com`/GHE-origin subpath will silently receive the `Authorization: token …` header: [3](#0-2) 
Because the check only looks at `pathname` shape and not a strict, curated minimal set of known endpoints, an attacker who controls content rendered in the app (a markdown body from a cloned/fetched repo, PR comment, or GitHub API object) could craft a same-origin path that matches the loose pattern to have Desktop attach the user's token to a request whose destination content is attacker-influenced (e.g., an "asset" upload endpoint under an attacker-controlled repo/org they created on github.com, since the regex captures arbitrary `owner`/`repo` segments: `/^\/[^/]+\/[^/]+\/assets\/[^/]+\/[^/]+\/?$/`). [4](#0-3) 

### Impact Explanation
If exploitable, this results in unintended disclosure of the signed-in user's GitHub API token to a resource path controlled by an attacker-owned repository/organization, since the regex accepts any `owner`/`repo` value as long as the path shape matches `/{owner}/{repo}/assets/{id}/{id}`. This matches the "credential/token exfiltration" impact category, since the token is attached based on a same-origin + loose-pattern check rather than a minimal, precise allow-list of first-party endpoints.

### Likelihood Explanation
This requires no local access: the trigger is markdown/content rendering in the renderer (e.g., a PR description, issue, or a cloned repository's README/markdown viewed in Desktop) that references a URL under the target's own origin (github.com) but with attacker-chosen `owner`/`repo`/id segments matching the loose regex — i.e., a naturally-occurring rendering path already exercised by `SandboxedMarkdown`. This is plausible but I could not fully confirm within this investigation whether the `assets` path segment truly allows attacker-registered content on github.com under arbitrary owner/repo combinations to receive a valid response that discloses the token value back to an attacker-controlled endpoint (the filter attaches the header to the *request*, but exfiltration requires the *response* or side effects to be attacker-observable, e.g., via an attacker-controlled redirect target or logging). This causal chain from "header attached" to "attacker observes/receives the token" is not fully demonstrated by local code alone.

### Recommendation
Tighten `isGitHubRepoAssetPath` (and `isEnterpriseAvatarPath`) to use a minimal, explicit allow-list of exact, known-safe path prefixes rather than a broad shape-matching regex that accepts arbitrary owner/repo/id values, mirroring the report's recommendation to enforce a floor (`minFeeRate`)-style strict validation instead of only checking the "shape" of acceptable input:
```ts
// Instead of accepting any owner/repo shape, validate against the specific,
// known asset-hosting prefixes GitHub actually uses.
```
Additionally, confirm that these paths cannot be influenced by attacker-controlled redirects (`onBeforeRedirect`) which could redirect a legitimate first-party request to an attacker-controlled destination that still satisfies the loose pathname regex.

### Proof of Concept
I was not able to construct a complete, verified end-to-end PoC from local code alone — doing so would require confirming (a) that github.com's `assets` endpoint accepts arbitrary attacker-chosen owner/repo segments and reflects/serves attacker-controlled content or a redirect, and (b) that `installSameOriginFilter`'s cross-origin header stripping does not also apply here (it only fires on redirect-driven origin changes, not on the initial same-origin request, so it would not prevent this specific case): [5](#0-4)

function isGitHubRepoAssetPath(pathname: string) {
  // Matches paths like: /repo/owner/assets/userID/guid
  return (

    // or: /user-attachments/assets/guid
    /^\/user-attachments\/assets\/[^/]+\/?$/.test(pathname)
  )
}
