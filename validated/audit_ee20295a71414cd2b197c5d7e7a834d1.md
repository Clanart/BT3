### Title
`Scanner::register_offset` silently re-attributes colliding Taproot scripts to the first-registered offset, so later registrations fail and received outputs are credited to the wrong offset - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`Scanner::register_offset` is an absolute "set" operation on the `scripts` map, not a collision-safe increment. Because parity-forcing increments (`offset += 1` when the tweaked point is odd) can land an offset on a script already registered for a different logical offset, an offset registered earlier front-runs a later registration: the later call gets `None`, and any Bitcoin output sent to that script is attributed by `scan_transaction` to the *first* offset only. The reported `ReceivedOutput` is then spendable only under the earlier offset's scalar, not the offset the later registrant believed it owned — incorrect accounting of received funds, directly analogous to `setDebt` letting an interleaved `incurDebt`/`repayDebt` produce unaccounted debt.

### Finding Description
In `register_offset`, the loop bumps `offset` until `p2tr_script_buf(key + G*offset)` yields an even-Y point, then does `self.scripts.insert(script, offset)` keyed by **script**, returning `None` if that script is already present (`mod.rs:180-196`). Two distinct logical offsets `o1` and `o2` can therefore map to the same script: if `o1`'s tweaked point is odd, it increments to `o1+1`; if `o1+1`'s tweaked point equals the point produced by `o2` (e.g. `o2 = o1+1`, or convergent increment chains), whichever registers first wins the script and the other returns `None`.

`scan_transaction` then does `self.scripts.get(&output.script_pubkey)` and emits a `ReceivedOutput` carrying only the stored (`offset`) scalar (`mod.rs:199-214`). There is no reverse accounting: the scanner cannot distinguish which logical offset an output "belonged" to. The doc comment acknowledges "offsets are surjective, not bijective, and the order offsets are registered in may determine the validity of future offsets" (`mod.rs:174-175`), but nothing prevents the consequence: a securely generated, honest offset can be silently rejected purely because an earlier registration's parity increment collided with it.

### Impact Explanation
An output sent to the colliding script is reported received under the first-registered offset. If the second registrant's application already derived/expected an address from its offset (e.g. a deposit address handed to a user), funds arrive at a script the scanner attributes to a *different* scalar — the same "unaccounted balance" outcome as the `setDebt` front-run, but for receive-side accounting. Funds are spendable only via the offset recorded in `scripts`; the displaced registrant has no way to detect the shadowing from `scan_transaction` output. Alternatively, the `None` return may itself be mishandled downstream (a `None` is ambiguous between "already registered" and "collision"), causing the caller to still use the offset-derived address.

### Likelihood Explanation
Each registration has ~50% odds its tweaked point is odd and increments; with many registered offsets, increment chains make collisions plausible, and an unprivileged party who can cause registrations (e.g., by requesting deposit addresses in a system registering an offset per deposit) can observe and order registrations to collide with a target's offset — a front-run of the "set" operation. Reachable purely via public inputs (offset registrations and Bitcoin transactions sent to the scripts).

### Recommendation
Make `register_offset` distinguish "same offset re-registered" (idempotent success) from "script collision" (skip the colliding script and continue incrementing, returning the first *unused* offset), and/or key `scripts` such that collision resolution is deterministic and documented. At minimum, return an error variant distinguishing the two `None` cases so callers don't derive an address for an offset that was never actually bound to its script.

### Proof of Concept
```rust
// Conceptual: two honest, distinct offsets converge on one script.
let mut scanner = Scanner::new(group_key).unwrap();

// Suppose offset_a's tweaked point is odd: it increments to offset_a + 1,
// whose tweaked point equals key + G*(offset_a + 1).
let used_a = scanner.register_offset(offset_a).unwrap(); // returns offset_a + 1

// A second registrant legitimately uses offset_b = offset_a + 1.
// p2tr_script_buf(key + G*offset_b) yields the same script already in `scripts`,
// so register_offset returns None — the offset is silently stolen.
assert_eq!(scanner.register_offset(offset_b), None);

// A deposit sent to offset_b's intended address scans as ReceivedOutput
// carrying `offset = used_a`, not offset_b.
let outputs = scanner.scan_transaction(&deposit_tx);
assert_eq!(outputs[0].offset(), used_a); // attributed to the earlier registration
```
Collision can also be forced adaptively: an actor who observes `register_offset` results (public, via derived addresses) requests a registration whose incremented value lands on a victim's pending offset script before the victim's registration executes — a direct analog of front-running `setDebt` with `incurDebt`.
