### Title
Stale Pre-Check Balance/Repayment Validation for Gasless Bundles Without Re-Verification at Execution Time - (File: kaiax/gasless/impl/tx_pool.go, kaiax/gasless/impl/getter.go, kaiax/gasless/impl/builder.go)

### Summary
The Rubicon `H-08` bug is a class of "check-before-action, no enforcement after/at-action" defect: a resource invariant (ReserveRatio) is validated once before a state-changing action is allowed, but nothing re-validates the invariant when the action actually executes, letting stale conditions be exploited. The Kaia `kaiax/gasless` module (KIP-247) has the same structural pattern: the balance/allowance/repayment checks that gate whether a `GaslessSwapTx` is admitted/bundled are computed once against a snapshot of state (`checkBalanceForSwap`, `VerifyExecutable`) and are not re-verified at the point the bundle is actually assembled and the block proposer's real KAIA is transferred to the user via the generated `LendTx`.

### Finding Description
`GaslessModule.GetCheckBalance()` returns `checkBalanceForSwap`, which validates `minAmountOut >= amountRepay`, `amountIn >= router.GetAmountIn(minAmountOut)`, allowance, and token balance [1](#0-0) . This check is invoked when the tx enters the pool (`validateTx`) and again during pool `Filter` re-validation [2](#0-1) [3](#0-2) , both of which use whatever state snapshot the pool currently holds.

Separately, `VerifyExecutable` (used by `IsExecutable`/`ExtractTxBundles`) only checks static relationships between the `ApproveTx` and `SwapTx` (sender match, token match, nonce sequencing, and that `AmountRepay` equals the statically-computed `repayAmount()`) [4](#0-3) . It does **not** re-check the DEX-dependent condition (`amountIn >= router.GetAmountIn(minAmountOut)`, i.e., whether the swap can still actually produce enough output at current on-chain price) at block-assembly time — that dynamic check exists only in `checkBalanceForSwap`, run once at pool-admission.

Critically, `ExtractTxBundles` — which runs at block-building time — prepends a `LendTxGenerator` transaction that transfers real KAIA value from the block proposer's own account directly to the swap sender, *before* the `ApproveTx`/`SwapTx` are executed [5](#0-4) . The lent amount is computed purely from the static formula `lendAmount()` (sum of tx fees) [6](#0-5) , not from any freshly-verified guarantee that the swap will actually repay that amount when it executes. The only enforcement that the swap output covers repayment is the one-time, stale `checkBalanceForSwap` performed when the swap transaction was originally added to (or re-filtered in) the pool — potentially many blocks earlier, against a different DEX price/allowance/balance state. This mirrors Rubicon's `enforceReserveRatio`: a pre-condition gate exists, but there is no invariant check performed at (or immediately before) the actual value-moving action.

### Impact Explanation
If DEX price, token balance, or allowance changes between the time `checkBalanceForSwap` passed and the time the bundle is actually built and the `LendTx` executes (which can span multiple blocks since `GaslessSwapTx` can sit in the pool), the proposer can still generate and include a `LendTx` that pays out real KAIA to the user under the assumption that the subsequent swap will repay it. If the swap subsequently reverts or under-repays (e.g., due to slippage from stale `minAmountOut`/`amountIn` checks, or an allowance/balance decrease from an intervening transaction) while the `LendTx` itself still lands (its validity depends only on the proposer's own balance and nonce, not on the swap succeeding), the block proposer's fee-repayment invariant is broken — funds move without the enforced repayment condition holding at execution time, directly analogous to LP funds moving past the ReserveRatio limit without an execution-time check.

### Likelihood Explanation
This requires an unprivileged token holder to submit an `ApproveTx`+`GaslessSwapTx` pair that passes the initial pool check, then have on-chain conditions (DEX price/liquidity, token allowance/balance) shift before the sequencing block proposer builds the bundle — plausible in busy pools/tokens with actively-traded liquidity, and requires no special privilege beyond being a normal gasless-swap user reachable via public RPC (`auction_submitBid`-style path is not needed; standard tx submission suffices).

### Recommendation
Re-validate `checkBalanceForSwap` (balance, allowance, and the DEX `GetAmountIn` slippage/price check) as part of `VerifyExecutable`/`ExtractTxBundles` immediately before generating the `LendTx` for the bundle at block-assembly time, using the state that will actually be used for execution, not only the state at pool-admission. Alternatively, ensure the `LendTx` is only ever executed atomically together with a guaranteed-successful `SwapTx` (i.e., the bundle mechanism must guarantee all-or-nothing inclusion contingent on the swap's actual on-chain repayment, not on a stale pre-check).

### Proof of Concept
Not independently reproduced; based on static analysis, could not fully verify (due to reaching tool-call budget) whether `work/builder`'s bundle execution provides all-or-nothing atomicity across `[LendTxGenerator, ApproveTx, SwapTx]` such that a failed/under-repaying `SwapTx` would also void the `LendTx`. This atomicity guarantee is the crux of whether the gap is actually exploitable for value extraction versus merely a benign revert; this should be confirmed by inspecting `work/builder/bundle.go` and `work/builder/builder.go` bundle execution/inclusion logic before treating this as a confirmed high-severity issue.

// VerifyExecutable checks if the given transactions form a valid gasless transaction
// It returns an error explaining why the transaction is not executable if it's not,
// and a boolean indicating whether the transaction is executable
func (g *GaslessModule) VerifyExecutable(approveTxOrNil, swapTx *types.Transaction) error {
	// Sx.
	swapArgs, ok := decodeSwapTx(swapTx, g.signer)
	if !ok {
		return ErrDecodeSwapTx
	}
	if !g.isSwapTx(swapArgs) {
		return ErrSwapTxInvalid
	}

	// Conditions involving ApproveTx
	if approveTxOrNil != nil {
		// Ax.
		approveArgs, ok := decodeApproveTx(approveTxOrNil, g.signer)
		if !ok {
			return ErrDecodeApproveTx
		}
		if !g.isApproveTx(approveArgs) {
			return ErrApproveTxInvalid
		}
		// AP1.
		if approveArgs.Sender != swapArgs.Sender {
			return ErrDifferentSenders
		}
		// SP1.
		if approveArgs.Token != swapArgs.Token {
			return fmt.Errorf("%w: approve token %s, swap token %s", ErrDifferentTokens, approveArgs.Token.Hex(), swapArgs.Token.Hex())
		}
		// SP2.
		if approveArgs.Amount.Cmp(swapArgs.AmountIn) < 0 {
			return fmt.Errorf("%w: approve amount %s, required amount %s", ErrInsufficientApproveAmount, approveArgs.Amount.String(), swapArgs.AmountIn.String())
		}
		// SP3.
		if approveTxOrNil.Nonce()+1 != swapTx.Nonce() {
			return fmt.Errorf("%w: approve nonce %d, swap nonce %d (expected %d)", ErrNonSequentialNonce, approveTxOrNil.Nonce(), swapTx.Nonce(), approveTxOrNil.Nonce()+1)
		}
		if nonce := g.getCurrentStateNonce(approveArgs.Sender); nonce != approveTxOrNil.Nonce() {
			return fmt.Errorf("%w: approve nonce %d, current nonce %d", ErrApproveNonceNotCurrent, approveTxOrNil.Nonce(), nonce)
		}
	} else {
		// SP3.
		if nonce := g.getCurrentStateNonce(swapArgs.Sender); nonce != swapTx.Nonce() {
			return fmt.Errorf("%w: swap nonce %d, current nonce %d", ErrSwapNonceNotCurrent, swapTx.Nonce(), nonce)
		}
	}

	// SP4.
	if swapArgs.AmountRepay.Cmp(repayAmount(approveTxOrNil, swapTx)) != 0 {
		return fmt.Errorf("%w: got %s, expected %s", ErrIncorrectRepayAmount, swapArgs.AmountRepay.String(), repayAmount(approveTxOrNil, swapTx).String())
	}

	return nil
}

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}
