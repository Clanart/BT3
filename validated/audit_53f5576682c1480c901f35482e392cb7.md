## Title
NUL-delimited `git log`/`for-each-ref` parsers can be desynchronized by attacker-controlled commit data, causing silent field misattribution - (File: `app/src/lib/git/git-delimiter-parser.ts`)

### Summary
The reported Move bug is a classic "stateful index not reset/resynchronized between iterations, causing positional data to be matched against the wrong counterpart." The closest analog in GitHub Desktop is the record-splitting logic in `createLogParser` and `createForEachRefParser` in `app/src/lib/git/git-delimiter-parser.ts`, which parse `git log`/`git for-each-ref` output by blindly slicing a NUL-joined byte/character stream into fixed-width groups using arithmetic on a running index (`i`, `consumed`), with no verification that a given slice boundary actually corresponds to a real field boundary rather than an attacker-supplied delimiter byte inside commit data (author name, email, or message body).

### Finding Description
`createLogParser` (lines 18-39) builds a git format string joining fields with the literal `%x00` (NUL) separator and invokes `git log -z --format=...`. The output is then split solely on `\0`:

The parser assumes each commit record occupies exactly `keys.length` consecutive slots in `records`, advancing `i` by `keys.length` every iteration — there is no per-record resynchronization check (no sentinel/anchor validation), analogous to `member_idx` never being reset/verified in the Move report. If any parsed field (most importantly commit author name, email, or the commit message body — all of which are fully attacker-controlled when a hostile remote or crafted commit is fetched) contains a raw NUL byte, `value.split('\0')` produces one extra element in `records`. From that point on every subsequent `records[i + ix]` slot is shifted by one, so keys (e.g., `sha`, `authorEmail`, `summary`, `parentSHAs`) get bound to the wrong underlying string for that commit and all commits parsed afterward in the same batch.

`createForEachRefParser` (lines 56-95) has a similar structural weakness: it tracks position with a manually incremented `consumed` counter and a modulo check against a literal `'\n'` sentinel that git is expected to emit between records. If the sentinel assumption is violated by unexpected data, the function throws rather than realigning, but earlier consumed fields are already mis-populated when only a plain byte-slip (not a `\n` mismatch) occurs.

The upstream flag `-z` in `createLogParser` uses NUL as a delimiter, but git commit messages, author names, and other blobs are binary-safe and can (via crafted commit objects, e.g. `git commit-tree` with a hand-built or corrupted commit object, or a raw `git hash-object`/`update-ref` from a malicious remote) contain arbitrary bytes including `\0`. Desktop does not validate or reject such records before display/history rendering, so this is a real, reachable, attacker-controlled path once such a commit is fetched.

### Impact Explanation
Because `sha`, parent SHAs, and author identity fields (`app/src/lib/git/log.ts` uses `createLogParser` to build `Commit`/`CommitIdentity` objects for the whole history, diff generation, and stash listing per the shared `git-delimiter-parser.ts` module, also used by `diff.ts` and `stash.ts`) are populated with these misaligned records, a single crafted/malicious commit in a cloned or fetched repository can silently corrupt the SHA-to-metadata mapping the user sees and interacts with in the Desktop UI (history list, commit details, stash list). Actions the user takes based on this corrupted mapping — reverting, cherry-picking, resetting, or generating diffs "for commit X" — could silently operate on or display the wrong commit, satisfying the "silent corruption of what the user commits or pushes" impact class, without any local/physical access or credential leak required — only a hostile fetched repository/remote.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control repository content (a commit with an embedded raw NUL byte in author metadata or message) that the victim fetches/clones, which fits the described attacker model exactly ("attacker controls a cloned/fetched repository ... git remote/proxy response"). Crafting such a commit is straightforward using low-level Git plumbing (e.g., `hash-object`, `mktree`/`commit-tree` with raw bytes), so no exotic tooling is needed; however whether current Git server-side/refs validation or Desktop's own `dugite`/git version rejects NUL bytes in these fields at fetch time is not verified here and would need to be confirmed with a proof-of-concept run against `createLogParser`/`createForEachRefParser` directly, since the index code itself is exactly analogous to the reported bug class but exploitability depends on git's own leniency toward NUL bytes in commit metadata, which I was not able to confirm from the codebase alone.

### Recommendation
Add explicit per-record boundary validation to both parsers (e.g., verify the sentinel character between records rather than assuming positional arithmetic always holds, similar to the recommended fix of resetting/verifying state at each outer-loop step in the original report), and reject/escape any field value that itself contains the delimiter byte before trusting it as a record boundary.

### Proof of Concept
Not able to fully verify end-to-end exploitability from static code alone (requires confirming that Git allows a NUL byte to survive in `%an`/`%ae`/`%B` output through `dugite`/`git log -z`, and confirming Desktop successfully fetches such an object). The conceptual PoC:
1. Craft a raw commit object where the author name or commit message contains a literal `\0` byte (via `git hash-object -w --stdin -t commit`).
2. Push/serve this object from an attacker-controlled remote; have the victim fetch/clone it.
3. Trigger `git log -z --format=...` parsing via `createLogParser` (`app/src/lib/git/log.ts`) by opening the repository history in Desktop.
4. Observe that `records.split('\0')` produces a shifted array, causing `entry[key] = records[i + ix]` to bind `sha`/`author`/`summary` fields from adjacent commits — verify by comparing rendered commit SHA/author against `git log` run directly in a terminal for the same repository. [2](#0-1)

import { splitBuffer } from '../split-buffer'

/**
 * Create a new parser suitable for parsing --format output from commands such
 * as `git log`, `git stash`, and other commands that are not derived from
 * `ref-filter`.
 *
 * Returns an object with the arguments that need to be appended to the git
 * call and the parse function itself
 *
 * @param fields An object keyed on the friendly name of the value being
 *               parsed with the value being the format string of said value.
 *
 *               Example:
 *
 *               `const { args, parse } = createLogParser({ sha: '%H' })`
 */
export function createLogParser<T extends Record<string, string>>(fields: T) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%x00')
  const formatArgs = ['-z', `--format=${format}`]

  const parse = <V extends string | Buffer>(value: V) => {
    const records = (
      Buffer.isBuffer(value) ? splitBuffer(value, '\0') : value.split('\0')
    ) as V[]
    const entries = []

    for (let i = 0; i < records.length - keys.length; i += keys.length) {
      const entry = {} as { [K in keyof T]: V }
      keys.forEach((key, ix) => (entry[key] = records[i + ix]))
      entries.push(entry)
    }

    return entries
  }

  return { formatArgs, parse }
}

/**
 * Create a new parser suitable for parsing --format output from commands such
 * as `git for-each-ref`, `git branch`, and other commands that are not derived
 * from `git log`.
 *
 * Returns an object with the arguments that need to be appended to the git
 * call and the parse function itself
 *
 * @param fields An object keyed on the friendly name of the value being
 *               parsed with the value being the format string of said value.
 *
 *               Example:
 *
 *               `const { args, parse } = createForEachRefParser({ sha: '%(objectname)' })`
 */
export function createForEachRefParser<T extends Record<string, string>>(
  fields: T
) {
  const keys: Array<keyof T> = Object.keys(fields)
  const format = Object.values(fields).join('%00')
  const formatArgs = [`--format=%00${format}%00`]

  const parse = (value: string) => {
    const records = value.split('\0')
    const entries = new Array<{ [K in keyof T]: string }>()

    let entry
    let consumed = 0

    // start at 1 to avoid 0 modulo X problem. The first record is guaranteed
    // to be empty anyway (due to %00 at the start of --format)
    for (let i = 1; i < records.length - 1; i++) {
      if (i % (keys.length + 1) === 0) {
        if (records[i] !== '\n') {
          throw new Error('Expected newline')
        }
        continue
      }

      entry = entry ?? ({} as { [K in keyof T]: string })
      const key = keys[consumed % keys.length]
      entry[key] = records[i]
      consumed++

      if (consumed % keys.length === 0) {
        entries.push(entry)
        entry = undefined
      }
    }

    return entries
  }

  return { formatArgs, parse }
}
