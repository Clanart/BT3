### Title
Unhandled UTF-8 decode exception on attacker-controlled CR-CAT/VC puzzle data causes wallet sync crash (DoS) - ([File: chia/wallet/vc_wallet/cr_cat_drivers.py])

### Summary
`ProofsChecker.from_program` decodes attacker-controlled, on-chain puzzle-curried bytes with `.decode("utf8")` without any exception handling. Any coin creator can curry arbitrary non-UTF-8 byte strings into the `PROOF_FLAGS_CHECKER` puzzle position that this function reads, and when a wallet syncs a CR-CAT/VC coin using that puzzle, the decode raises an uncaught `UnicodeDecodeError`, aborting wallet-side transaction/coin processing. This mirrors the underlying bug class in CVE-2020-25463: a decoder that assumes well-formed UTF-8 input and has no defensive error handling for malformed byte sequences, reachable by any third party who crafts the input.

### Finding Description
`ProofsChecker.from_program` is defined as: [1](#0-0) 

```
@classmethod
def from_program(cls, unknown_puzzle: UnknownPuzzle) -> ProofsChecker:
    if unknown_puzzle.mod != PROOF_FLAGS_CHECKER or unknown_puzzle.curried_args is None:
        raise ValueError("Puzzle was not a proof checker")  # pragma: no cover

    return cls([flag.at("f").as_atom().decode("utf8") for flag in unknown_puzzle.curried_args[0].as_iter()])
```

The `flag.at("f").as_atom()` bytes come directly from the curried arguments of a puzzle that is uncurried from an on-chain coin's puzzle reveal — data that is fully controlled by whoever created the coin/CR-CAT/VC structure, not by the wallet owner. The `.decode("utf8")` call has no `try/except`, so any byte sequence that is not valid UTF-8 (e.g. a lone continuation byte or truncated multi-byte sequence, analogous to the malformed input that triggered `fxUTF8Decode`'s invalid memory access) raises an unhandled `UnicodeDecodeError`.

A structurally similar unguarded pattern exists in `VCProofs.from_program` in the VC store, which decodes proof key/value atoms straight from a `Program` parsed off-chain data with no error handling: [2](#0-1) 

By contrast, the codebase's own generator-parsing code for CAT memos explicitly guards this exact operation, showing the maintainers are aware decode failures on untrusted data must be caught: [3](#0-2) 

```
try:
    memo = condition[3][1].decode("utf-8", errors="strict")
except UnicodeError:
    pass  # ignore this error which should leave memo as empty string
```

`ProofsChecker.from_program` and `VCProofs.from_program` lack this same protection despite consuming equally untrusted, attacker-supplied on-chain byte data.

### Impact Explanation
Any user or offer counterparty holding, syncing, or trading CR-CATs/VCs is put at risk: a malicious party can create a CR-CAT/VC coin whose `proofs_checker` (or VC proof key/value) currying contains a non-UTF-8 byte string. When the victim wallet later parses that coin's puzzle/spend during normal sync, trade acceptance, or offer processing (call sites include `chia/wallet/cat_wallet/cat_wallet.py`, `chia/wallet/vc_wallet/cr_cat_wallet.py`, `chia/wallet/trade_manager.py`, `chia/wallet/wallet_rpc_api.py`), the uncaught exception propagates and halts wallet-side processing of that coin/transaction — a spend-triggered processing halt (DoS) matching the "invalid spend or block acceptance / spend-triggered transaction-processing halt" impact category in scope.

### Likelihood Explanation
Likelihood is high for an attacker with no special privileges: they only need to construct a coin/puzzle with an intentionally malformed (non-UTF-8) byte string in the flags/proofs position and get it in front of a victim wallet (e.g. via an offer, a CR-CAT transfer, or simply being visible on-chain to a wallet that tracks/syncs CR-CAT or VC coins). No signature forgery, no consensus-level bypass, and no cooperation from the victim beyond normal wallet sync/offer processing is required.

### Recommendation
Wrap the `.decode("utf8")` calls in `ProofsChecker.from_program` (`chia/wallet/vc_wallet/cr_cat_drivers.py`) and in `VCProofs.from_program`/`prove_keys` (`chia/wallet/vc_wallet/vc_store.py`) in explicit `try/except UnicodeDecodeError` handling, mirroring the pattern already used in `chia/_tests/util/run_block.py`, and fail gracefully (skip the malformed flag/proof, or reject the coin as unrecognized) instead of letting the exception propagate and abort wallet processing.

### Proof of Concept
1. Attacker constructs a CR-CAT (or VC) coin whose puzzle reveal curries `PROOF_FLAGS_CHECKER` with a flag atom containing an invalid UTF-8 byte sequence, e.g. `b"\xff\xfe"`, instead of a normal ASCII flag string.
2. Attacker sends/transfers this coin (or includes it in an offer) to a victim wallet that tracks CR-CATs/VCs.
3. During normal sync or offer/trade processing, the victim wallet calls `CRCAT.get_current_from_coin_spend` / related driver code, which eventually calls `ProofsChecker.from_program(unknown_puzzle)`.
4. `flag.at("f").as_atom().decode("utf8")` raises `UnicodeDecodeError` with no surrounding exception handler, aborting the wallet's processing of that coin/spend (verified by direct code inspection of `chia/wallet/vc_wallet/cr_cat_drivers.py:654-659`; full runtime confirmation would require executing the wallet sync path, which was not available in this analysis — this should be validated with a Devin session against the actual wallet test harness).     @staticmethod
```python
    def from_program(prog: Program) -> VCProofs:
        first: Program = prog.at("f")
        rest: Program = prog.at("r")
        if first.atom is None and rest.atom is None:
            final_dict: dict[str, str] = {}
            final_dict.update(VCProofs.from_program(first).key_value_pairs)
            final_dict.update(VCProofs.from_program(rest).key_value_pairs)
            return VCProofs(final_dict)
        elif first.atom is not None and rest.atom is not None:
            return VCProofs({first.atom.decode("utf-8"): rest.atom.decode("utf-8")})
        else:
            raise ValueError("Malformatted VCProofs program")  # pragma: no cover
```
