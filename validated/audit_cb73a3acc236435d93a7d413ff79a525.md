This confirms the analog: `EvmHost.dispatchIncoming` for POST requests uses a low-level `.call` and, on failure, deletes the receipt to allow a retry [1](#0-0) . So a revert inside `onAccept` doesn't brick the host — but it does mean `withdraw()` itself, and thus the *entire order's* escrow release/refund, never completes as long as one token in `body.tokens` reverts on transfer.

### Title
Single malicious/blacklisting token in an order's output set can permanently lock the entire escrow in `IntentGatewayV2.withdraw` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` loops over `body.tokens` and does a raw `token.call(transfer(...))` for each escrowed token, reverting the whole call (and hence the whole `RedeemEscrow`/`RefundEscrow`/GET-response settlement) if any single transfer fails [2](#0-1) . This mirrors the Moonwell M-04 pattern: one poisoned/censorable token in a multi-token structure blocks payout for all the good tokens bundled with it.

### Finding Description
`onAccept` dispatches `RedeemEscrow`/`RefundEscrow` requests straight into `withdraw(body, isRefund)` [3](#0-2) , and `onGetResponse` does the same for cancellation-driven refunds [4](#0-3) . Inside `withdraw`, every entry of `body.tokens` (the set of tokens escrowed for that order commitment) is transferred in a single loop with no per-token isolation: `token.call(...)` and `if (!success) revert TransferFailed();` [5](#0-4) .

Orders are user-created (order creators choose the input/output tokens escrowed), so an order can legitimately bundle a normal token (e.g. USDC/USDT) with any other token address. If that token later blacklists the beneficiary (USDC/USDT-style censorship) or is upgraded to a malicious/reverting implementation, the whole `withdraw` reverts. While `EvmHost.dispatchIncoming` deletes the request receipt on failure to permit a retry at the host level [6](#0-5) , retrying `withdraw` with the *same* `body.tokens` set will hit the exact same reverting transfer every time — there is no mechanism in `withdraw` to skip the bad token and still pay out the good ones, and no admin/user path to remove one token from `body.tokens` and re-attempt with the rest. The escrow for every token in that commitment (`_orders[body.commitment][token]`) stays locked indefinitely.

### Impact Explanation
This is a fund-lock: legitimate escrowed tokens that have nothing to do with the malicious/censorable token become permanently unclaimable because they are bundled in the same atomic `withdraw` call as the poisoned one. This matches the accepted bounty impact category "stealing or loss of funds" via permanent locking, since neither the solver/filler nor the original depositor can ever redeem the good tokens for that commitment.

### Likelihood Explanation
Unlike the disputed original finding (which required a trusted admin to add a malicious reward token), this path is reachable purely through order creation, which is an unprivileged user action. It does not require a malicious relayer, prover, or admin — only that one of the tokens bundled into an order's escrow set (chosen at order-creation time) becomes non-transferable to the beneficiary at settlement time (e.g. USDC/USDT blacklist, pausable/upgradeable token). Given `IntentGatewayV2` is designed to support arbitrary ERC-20s as intent inputs/outputs, this is a realistic, low-effort condition to trigger, either accidentally (blacklisted beneficiary) or deliberately (attacker crafts an order combining a good token with a token they control the transfer behavior of).

### Recommendation
Isolate per-token transfer failures in `withdraw` (e.g., wrap each `token.call` in a way that records failure and continues the loop, deferring the failed token's balance for later re-claim) instead of reverting the entire loop; alternatively, process each token's payout as an independently retryable step keyed by `(commitment, token)` rather than looping over the whole `body.tokens` array atomically.

### Proof of Concept
1. Order creator posts an order whose escrowed output set includes both `DAI` (well-behaved) and `USDC` (censorable) for the same commitment.
2. Before settlement, the beneficiary address gets blacklisted by USDC (or the token is upgraded to revert on transfer).
3. A relayer submits the fill proof; ISMP routes to `onAccept` → `withdraw(body, false)` [3](#0-2) .
4. The loop reaches the `USDC` transfer, `token.call(...)` fails, and `revert TransferFailed()` unwinds the entire `withdraw`, including the already-computed `DAI` transfer [5](#0-4) .
5. `EvmHost.dispatchIncoming` catches the low-level call failure and deletes the receipt for retry [7](#0-6) , but every retry hits the same blacklisted-USDC revert, so the `DAI` escrow for this commitment is now permanently unreachable alongside the `USDC`.
