### Title
Unsafe/unsanitized parsing of `git commit` output allows attacker-controlled branch names to corrupt the returned commit SHA - (File: `app/src/lib/git/core.ts`)

### Summary
The Reality.eth report describes a broken invariant: an untyped, attacker-influenced external value (`bytes32`) is naively reinterpreted as a different, narrower type (`uint256`) without validating that the reinterpretation is safe, so the resulting decision (release funds) can be silently wrong. The same *class* of bug — naive positional string parsing of untrusted/externally-influenced text into a value that is implicitly trusted to have a specific format — exists in `parseCommitSHA` in [1](#0-0)  which is the function GitHub Desktop uses to extract the SHA of a commit it just created.

### Finding Description
`parseCommitSHA` extracts the commit SHA from `git commit`'s human-readable stdout by naive delimiter splitting: [2](#0-1) 

```
export function parseCommitSHA(result: IGitStringResult): string {
  return result.stdout.split(']')[0].split(' ')[1]
}
```

This assumes Git's output always has the exact shape `[<branch> <sha>] <title>` and that the *first* `]` character in the whole output is the one closing the `[branch sha]` prefix. Git's `check-ref-format` rules forbid `[` in ref names but do **not** forbid `]`. That means a branch name coming from a cloned/fetched repository (fully attacker-controlled, e.g. `release]evil`) is a syntactically valid Git ref. If the user is on such a branch when Desktop calls `createCommit()` / `createMergeCommit()` in [3](#0-2)  and [4](#0-3) , Git's stdout becomes `[release]evil 1a2b3c4] <title>`. `split(']')[0]` then returns `[release`, and `.split(' ')[1]` returns `undefined` — an incorrect/empty value is silently returned as "the commit SHA" instead of throwing or validating the shape (e.g., verifying it's a 40/7+-char hex string).

This mirrors the report's core problem: an external, attacker-influenced value is coerced into a specific expected format (`uint256` in the Solidity case, "a valid SHA string" here) without any format/bounds check, so malformed input silently produces a wrong typed value rather than a controlled error.

### Impact Explanation
`createCommit`/`createMergeCommit` return this SHA to callers throughout the app that treat it as authoritative identification of the commit that was just made (e.g., updating in-memory history/tip state, undo/redo of the last commit, post-commit UI, hooks correlation). If the value is `undefined` or truncated, any logic that compares this value against the actual repository `HEAD`/tip SHA, or uses it to look up the commit for follow-up operations (e.g., amend, undo, cherry-pick, or automated push-verification flows), can silently diverge from the real state of what was actually committed — i.e., "silent corruption of what the user commits" as covered by the accepted impact categories. Because this is driven purely by checking out a branch from a malicious/fetched remote and does not require any privileged access, local access, or social engineering beyond ordinary cloning/fetching, it fits the valid impact model (attacker controls a fetched/cloned repository object — here, its ref name).

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker must get the victim to check out a branch with a crafted name containing `]` (achievable simply by having such a branch present in a cloned/fetched repository, or a fork/PR branch, since Desktop does not sanitize or reject such ref names before use); and (2) the victim must make a commit while on that branch through Desktop's UI. Both conditions are attacker-influenced but require no exploitation beyond ordinary repository interaction, so likelihood is moderate — this is a narrow, format-string style edge case rather than a broadly reachable path, but it does not require any unnatural/social-engineering steps beyond normal clone/fetch/checkout/commit usage.

### Recommendation
Do not parse `git commit`'s human-readable, non-machine-readable stdout by naive character splitting. Use `git commit --porcelain=v2` or a subsequent `git rev-parse HEAD` (or `git log -1 --format=%H`) to retrieve the SHA in a well-defined, delimiter-safe machine format, and validate the result matches `^[0-9a-f]{7,40}$` before trusting it, throwing an explicit error rather than silently returning `undefined` or a truncated value if parsing fails.

### Proof of Concept
1. Have (or fetch/clone) a malicious repository containing a branch literally named `release]evil` (valid per `git check-ref-format`, since `]` is not in the forbidden character set — only `[` is).
2. In Desktop, check out `release]evil`.
3. Make any change and commit through Desktop's commit UI (`createCommit()` in [5](#0-4) ).
4. Git's stdout is `[release]evil <sha7>] <summary>`. `parseCommitSHA` in [1](#0-0)  computes `result.stdout.split(']')[0]` → `"[release"`, then `.split(' ')[1]` → `undefined`, so `createCommit` resolves with `undefined` instead of the real commit SHA even though the commit was actually created successfully.

Note: I was not able to trace, within the indexed code, every downstream consumer of `createCommit`'s/`createMergeCommit`'s returned SHA to fully quantify the blast radius (e.g., which UI/undo/push-verification paths directly dereference this value versus re-querying `HEAD` independently). A Devin session with full repository/terminal access would be needed to enumerate all call sites and confirm the exact downstream consequence in each case.

export async function createCommit(
  repository: Repository,
  message: string,
  files: ReadonlyArray<WorkingDirectoryFileChange>,
  options?: {
    amend?: boolean
    noVerify?: boolean
    signOff?: boolean
    allowEmpty?: boolean
  } & HookCallbackOptions
): Promise<string> {
  // Clear the staging area, our diffs reflect the difference between the
  // working directory and the last commit (if any) so our commits should
  // do the same thing.
  await unstageAll(repository)

  await stageFiles(repository, files)

  const args = ['-F', '-']

  if (options?.amend) {
    args.push('--amend')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  if (options?.signOff) {
    args.push('--signoff')
  }

  if (options?.allowEmpty) {
    args.push('--allow-empty')
  }

  const result = await git(
    ['commit', ...args],
    repository.path,
    'createCommit',
    {
      stdin: message,
      // https://git-scm.com/docs/githooks/2.46.1
      interceptHooks: [
        'pre-commit',
        'prepare-commit-msg',
        'commit-msg',
        'post-commit',
        ...(options?.amend ? ['post-rewrite'] : []),
        'pre-auto-gc',
      ],
      onHookProgress: options?.onHookProgress,
      onHookFailure: options?.onHookFailure,
      onTerminalOutputAvailable: options?.onTerminalOutputAvailable,
    }
  )
  return parseCommitSHA(result)
}
