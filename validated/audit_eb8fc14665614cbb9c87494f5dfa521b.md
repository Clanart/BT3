### Title
SignableTransaction omits the OP_RETURN output from its weight/fee calculation, underpaying fees and under-checking TX weight — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` builds the fee and weight estimates via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which reconstructs the transaction's output list from `payments` (and optionally `change`) only. However, when `data` is supplied, an `OP_RETURN` output is pushed onto `tx_outs` separately and is never included in the weight used to derive `needed_fee` or to check `MAX_STANDARD_TX_WEIGHT`. The result mirrors the reported bug class — the amount committed to cover a cost (the approved/estimated amount) is computed from a smaller object than the one actually charged (the serialized transaction) — leaving a mismatch between the accounted and actual cost. In Serai the residual cannot be drained by an attacker (Bitcoin has no allowance mechanism; surplus becomes miner fee), but the divergence causes the signed transaction to pay a feerate below `fee_per_vbyte` — potentially below the relay minimum — and can exceed the standard weight limit despite passing the in-code check.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is appended to `tx_outs` before the weight is calculated, yet the weight calculation is fed `payments`, not `tx_outs`. The `data` output (up to ~85 bytes for an 80-byte payload ≈ 340 weight units ≈ 85 vbytes) is therefore excluded from `vbytes`, `needed_fee`, the `TooLowFee` floor check, and the `MAX_STANDARD_TX_WEIGHT` check.

So `needed_fee` under-covers the real transaction, and a transaction that is actually over `MAX_STANDARD_TX_WEIGHT` passes the check at line 241.

### Impact Explanation
Two concrete harms, both matching the "charged less than committed / DOS for honest users" portion of the reference class:

1. **Underpaid fee / stuck transaction (DOS).** The actual feerate paid is `needed_fee / real_vbytes < fee_per_vbyte`. With a max-size `data` payload (~85 vbytes unaccounted) against the common small-transaction case (~150–250 vbytes), the effective feerate can fall to roughly half the requested rate, and can drop under the default minimum relay feerate — even though the `TooLowFee` check passed. A transaction created this way is signed and broadcast but may never relay or confirm, locking the consumed inputs and stalling the payouts/refunds the plan was meant to deliver — directly analogous to the reference report's denial-of-service-on-refunds impact.

2. **Bypass of the weight limit.** `weight` used at line 241 excludes the data output, so a transaction near the limit can pass the check while being non-standard and unrelayable.

### Likelihood Explanation
Any caller passing `data` (the API explicitly supports OP_RETURN payloads up to 80 bytes) triggers the discrepancy deterministically; the miscalculation is proportional to the data length, not edge-case dependent. The theft-of-surplus half of the reference class does **not** carry over (there is no reusable allowance; the surplus is burned as miner fee), which limits this to a Medium-severity reliability/DOS analog rather than a fund-theft one.

### Recommendation
Compute weight/vbytes from the actual final `tx_outs` (including the `OP_RETURN` output) rather than from `payments`. Change `calculate_weight_vbytes` to accept the constructed `Vec<TxOut>` (or add the data output into the reconstructed transaction inside it), so `vbytes`, `needed_fee`, the minimum-fee check, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the transaction that will actually be signed and broadcast.

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
