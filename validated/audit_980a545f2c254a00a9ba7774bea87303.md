### Title
`ReceivedOutput::read` trusts attacker-supplied `TxOut.value`/`OutPoint`, letting an unprivileged party inflate credited input value and cause the multisig to sign an unspendable/over-funded transaction — (`networks/bitcoin/src/wallet/mod.rs`)

### Summary
The Zest incident class — an attacker inflating the apparent value of supplied collateral to extract more than it's worth — maps directly onto Serai's Bitcoin wallet: `ReceivedOutput` is the "collateral receipt" type, and its `read` implementation accepts arbitrary, unauthenticated `TxOut` (including `value`) and `OutPoint` bytes with no validation that the referenced on-chain output exists or carries that value. `SignableTransaction::new` then trusts `input.output.value` as the spendable balance for funding, fee, and change math, and `SignableTransaction::multisig` verifies only the `script_pubkey`/offset relationship — never the value or outpoint against chain state.

### Finding Description
`ReceivedOutput::read` deserializes a scalar offset, a consensus-decoded `TxOut`, and a consensus-decoded `OutPoint` from untrusted bytes with no consistency checks whatsoever: [1](#0-0) 

`SignableTransaction::new` sums `input.output.value.to_sat()` into `input_sat` and uses it to decide affordability of payments, fees, and change: [2](#0-1) [3](#0-2) 

When the signing machine is created, the only integrity check is that the tweaked/offset group key produces the claimed `script_pubkey` — the claimed `value` and the claimed `outpoint` are never verified: [4](#0-3) 

The fabricated `TxOut` is then committed into the BIP-341 sighash via `Prevouts::All(&self.tx.prevouts)` and signed by every `AlgorithmMachine`: [5](#0-4) 

So a forged `ReceivedOutput` (inflated `value`, or an outpoint that references a dust output, an output the key doesn't control, or a nonexistent outpoint) passes the "collateral check" in `multisig` as long as `script_pubkey` matches a valid offset of the group key — exactly the Zest pattern: the protocol values collateral based on attacker-claimed data rather than verified chain state.

### Impact Explanation
Two concrete consequences, both reachable from untrusted bytes:

1. **Funds reported received that are not spendable / wasted signing of invalid transactions.** An attacker supplies a `ReceivedOutput` whose `TxOut.value` is inflated relative to the real UTXO (or whose outpoint doesn't exist). `SignableTransaction` computes payments/change/fee against the phantom value and the threshold group signs a transaction whose sighash commits to the fake prevout values. The resulting transaction is consensus-invalid, yet it was produced by the real signing quorum — a griefing/loss-of-liveness primitive against the coordinator, and it can be used to make the protocol book phantom deposits.
2. **Change/payment miscrediting.** Because `input_sat` is attacker-controlled, an inflated input causes the change computation at `send.rs:228-230` to emit change/payments sized as if real funds existed; downstream accounting that credits `Output::balance()` (`processor/src/networks/bitcoin.rs:128-130`, which reports `self.output.value()`) would credit value that was never deposited.

### Likelihood Explanation
Any party able to feed bytes to `ReceivedOutput::read` (e.g., the processor's `Output::read` path at `processor/src/networks/bitcoin.rs:145-166`, which is used to restore scanned outputs) or to submit outputs for signing can fabricate inputs. The only constraint is that `script_pubkey` be a P2TR key of the form `key + G*offset`, which the attacker can legitimately arrange by sending a dust output to a registered offset and then lying about its value. No threshold collusion, no leaked keys, and no malicious validator are required — just public inputs.

### Recommendation
- Bind `ReceivedOutput` to verified chain data: reject any `ReceivedOutput` whose `(outpoint → TxOut)` is not confirmed against the Bitcoin chain before it reaches `SignableTransaction::new`, or make `read` produce a "claim" type that must be resolved via RPC to the real UTXO set.
- In `SignableTransaction::multisig`, additionally verify each `prevouts[i]` against the actual on-chain output at `tx.input[i].previous_output` (value and script) before creating signing machines.
- Downstream, never derive credited balances (`Output::balance`) from deserialized `TxOut.value` without a chain lookup keyed on `outpoint`.

### Proof of Concept
```rust
// Attacker sends 546 sats to a legitimately registered offset, obtaining a real
// script_pubkey P for offset o. They then serialize a forged ReceivedOutput:
let mut buf = vec![];
buf.extend(o.to_bytes());                       // valid scalar offset
// TxOut claiming MAX_MONEY with the attacker's real script_pubkey
TxOut { value: Amount::from_sat(21_000_000_0000_0000), script_pubkey: P.clone() }
    .consensus_encode(&mut buf).unwrap();
// OutPoint naming the attacker's real 546-sat UTXO (or any outpoint)
fake_outpoint.consensus_encode(&mut buf).unwrap();

let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// forged.value() == huge; input_sat inflated
let tx = SignableTransaction::new(vec![forged], &payments, Some(change), None, FEE).unwrap();
// multisig() passes: p2tr_script_buf(keys.offset(o).group_key()) == P
let machine = tx.multisig(&keys).unwrap();
// Quorum signs a sighash committing to 21M BTC prevouts -> consensus-invalid TX,
// or downstream accounting credits value never deposited.
```
Root cause: `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122`) performs zero validation linking the claimed `TxOut`/`OutPoint` to chain state, and `SignableTransaction::multisig` (`send.rs:277`) only checks `script_pubkey`, not value or outpoint authenticity.
