### Title
Stale cached diff can be committed without user reviewing the actual on-disk change - (File: `app/src/lib/stores/updates/changes-state.ts`)

### Summary
`updateChangedFiles()` reuses the previously fetched diff for the currently selected working-directory file whenever the file's `id` is unchanged across a status refresh, instead of re-deriving the diff every time status is reloaded. The file `id` is computed purely from `AppFileStatusKind + path` (and `oldPath` for renames), not from file content, so it cannot detect that the file's content changed again on disk. This mirrors the C4 finding: one code path (`_commitIncludedChanges` → `createCommit`/`applyPatchToIndex`, which re-reads the file from disk at commit time) computes the "real" result, while the "view" path (`updateChangedFiles`) can present outdated information for the same operation, exactly the kind of read-path/write-path inconsistency described in the Backd report.

### Finding Description
`WorkingDirectoryFileChange`/`FileChange.id` is derived only from status kind and path: [1](#0-0) 

`updateChangedFiles()` is invoked on every status refresh (`_loadStatus`) and decides whether to keep the existing `diff` for the current selection or clear it, based solely on comparing these path/kind-based `id`s, not on any content hash or mtime: [2](#0-1) 

This function is called from `_loadStatus`, which runs on every status refresh, including automatic/background refreshes that are not initiated by the user reviewing the diff: [3](#0-2) 

Meanwhile, the actual commit path recomputes the diff to build the patch fresh from the working tree at commit time, independent of whatever diff was last rendered in the UI: [4](#0-3) [5](#0-4) 

Because the reused/cached `diff` object is keyed only by file `id` (kind+path), if the same file is modified twice in quick succession — e.g., the working tree content changes again after Desktop already fetched a diff for that file but before the user commits — a subsequent status refresh will not necessarily trigger a new diff fetch as long as the file's status kind and path remain "Modified" and it stays the sole selection. The user can then review a diff that no longer represents what's on disk, click "Commit", and have `createCommit`/`applyPatchToIndex` stage and commit the newer, unreviewed content, since that path independently re-reads the file from disk rather than using the cached diff object.

### Impact Explanation
This breaks the invariant that "the diff panel a user reviews before committing reflects exactly the content that will be committed." A user could unknowingly commit and push content they never actually saw reviewed, satisfying "silent corruption of what the user commits or pushes" in the valid-impact list. Depending on how the extra file modification is introduced (e.g., an editor autosave race, a build/watch script bundled in the repository that rewrites a tracked file shortly after it's first modified, or a slow background job triggered by opening the repo), unreviewed content can end up in a commit/push without any warning from the UI.

### Likelihood Explanation
This is a caching/staleness bug rather than a memory-safety or injection bug, so the likelihood of triggering it depends on timing: the file must be modified a second time in the narrow window between Desktop fetching/rendering its diff and the user clicking commit, without the selection changing. This is plausible in repositories with build tools, formatters, or watch scripts that rewrite tracked files shortly after they're touched, which is a scenario an attacker distributing a malicious repository (with such a script committed and documented as "run this while working") could set up, but it still requires some cooperating local process to actually run and rewrite the file — the report itself doesn't demonstrate a way to trigger the second write purely from a hostile git object/remote without any local script execution. This is the main uncertainty in this analog: I could not find, within the indexed code, a git-hook or fetch/clone-driven mechanism (independent of local tooling) that forces this race deterministically, so likelihood should be considered speculative/low-to-moderate rather than confirmed exploitable purely via a hostile remote.

### Recommendation
Make the diff-reuse decision content-aware instead of `id`-only: include a content fingerprint (e.g., mtime+size, or a hash of the diff/patch that was actually rendered) in the comparison in `updateChangedFiles()`, and invalidate/refetch the diff whenever that fingerprint changes, even if the file `id` (kind+path) is unchanged. Alternatively, force a diff refresh immediately before commit and compare it against the diff shown to the user, warning if they differ.

### Proof of Concept
1. Open a repository in Desktop and modify `file.txt`; select it in the Changes list so Desktop fetches and renders its diff (cached at `state.selection.diff`).
2. Before committing, have another process (e.g., a watch/build script within the working tree) rewrite `file.txt` again with different content, without changing its git status kind (still `Modified`) or path.
3. Trigger any background status refresh (`_loadStatus`) that happens to occur in this window — `updateChangedFiles()` sees the same `selectedFileIDs[0]` as before and reuses `state.selection.diff` from step 1 rather than fetching a fresh diff, per [6](#0-5) .
4. The user, seeing the old diff, clicks "Commit". `_commitIncludedChanges` → `createCommit` → `applyPatchToIndex` calls `getWorkingDirectoryDiff` fresh from disk [7](#0-6) , staging and committing the step-2 content that the user never actually reviewed in the UI.

    if (status === null) {
      return null
    }

    this.repositoryStateCache.updateChangesState(repository, state =>
      updateChangedFiles(state, status, clearPartialState)
    )

    this.repositoryStateCache.updateChangesState(repository, state => ({
      conflictState: updateConflictState(state, status, this.statsStore),
    }))

    this.updateMultiCommitOperationConflictsIfFound(repository)
    await this.initializeMultiCommitOperationIfConflictsFound(
      repository,
      status
    )

    if (this.selectedRepository === repository) {
      this._triggerConflictsFlow(repository, status)
    }

    this.emitUpdate()

    this.updateChangesWorkingDirectoryDiff(repository)

    return status
  }

export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)
}
