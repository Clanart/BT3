Attacker-controlled `n`/`t` in `ThresholdKeys::read` causes quadratic Lagrange interpolation and a hang in `ThresholdKeys::new` - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2020-2925 is a hang/crash (availability) bug class. The analog in Serai is a reachable CPU-exhaustion hang: `ThresholdKeys::read` accepts attacker-supplied `t` and `n` parameters and then calls `ThresholdKeys::new`, which computes the group key by evaluating a Lagrange `interpolation_factor` for each of the `t` lowest participants over the `t`-element participant set — an O(t²) computation with a `t` ceiling of `u16::MAX` (65535). Feeding `ThresholdKeys::read` a crafted payload with `t = n = 65535` (Lagrange interpolation) forces ~4.3×10⁹ scalar field multiplications in a single call, hanging the caller.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, `i` directly from the byte stream, reads `n` verification shares into a `HashMap`, and forwards everything to `ThresholdKeys::new` [1](#0-0) . `ThresholdParams::new` / `ThresholdKeys::new` only enforce `t ≤ n` and that every share index is `≤ n` [2](#0-1)  — there is no upper bound below `u16::MAX`.

`ThresholdKeys::new` then derives the group key as `Σ verification_shares[i] * interpolation_factor(i, t)` for `i` in `1..=t` [3](#0-2) . For `Interpolation::Lagrange`, each `interpolation_factor` call computes a product over all `t` participants (the standard Lagrange coefficient `∏_{j≠i} j/(j−i)`), so total work is O(t²) in field multiplications/inversions. The same O(len²) shape recurs in `view()`, which calls `interpolation_factor` once per included signer [4](#0-3) .

The crafted input is small (~2 MB: `n` 32-byte verification shares plus overhead), so there is a large asymmetry between input size and CPU consumed.

### Impact Explanation
Any code path that deserializes attacker-controlled `ThresholdKeys` bytes (key-share recovery/backup ingestion, restore flows, or any peer-supplied key material passed to `ThresholdKeys::read`) blocks for an effectively unbounded amount of time — a single ~2 MB input drives ~4.3×10⁹ scalar multiplications, and the computation is single-threaded inside `new` with no early abort. This is a complete availability loss of the calling thread/process per request, matching the "hang or frequently repeatable crash" class of CVE-2020-2925. Repeat submissions amplify it across threads.

### Likelihood Explanation
- Reachability: `ThresholdKeys::read` is a public deserialization entry point that is explicitly in the trusted boundary for untrusted bytes; `t`, `n`, the interpolation tag, and the `n` group elements are all fully attacker-controlled [5](#0-4) .
- Cost: the payload must be canonical — `n` valid `read_G` encodings and a valid `read_F` secret share — which is trivially generatable by encoding `n` copies of any valid point.
- No mitigating cap exists between `t ≤ n` and `u16::MAX`; Serai's real deployments use n of at most a few hundred, so the legitimate-input budget is tiny compared to what the parser permits.

Uncertainty: if the deployment never exposes `ThresholdKeys::read` to untrusted bytes, the practical exposure drops; the bug still stands as a library-level reachable hang under the stated input model.

### Recommendation
Enforce a sane bound on `t`/`n` during deserialization (e.g., reject `n` above a protocol maximum before allocating and before `ThresholdKeys::new`), or compute the group key with a single O(t) batch-inversion Lagrange evaluation instead of `t` independent O(t) `interpolation_factor` calls. The same bound should apply at `view()`'s `included` length, which is already limited to `n` but inherits whatever `n` was set to.

### Proof of Concept
Conceptual, against `ThresholdKeys::<C>::read`:

1. Build a byte stream:
   - `u32` length of `C::ID` followed by `C::ID` (passes the curve check).
   - `t = 65535`, `n = 65535`, `i = 1` as little-endian `u16`s (valid per `ThresholdParams`).
   - interpolation tag `1` (`Interpolation::Lagrange`).
   - `read_F`-valid secret share (e.g., `1`).
   - `n` copies of any canonical point encoding for the verification shares (e.g., the generator encoding).
2. Call `ThresholdKeys::<C>::read(&mut bytes.as_ref())`.
3. `ThresholdKeys::new` enters `t.iter().map(|i| verification_shares[i] * interpolation_factor(*i, &t))` with `|t| = 65535`; each `interpolation_factor` performs ~65535 scalar multiplications, yielding ~4.3×10⁹ field multiplications and a hang in a single `read` call — the input itself is only ~2 MB.
