## Finding

### Title
Cross-chain/cross-deployment signature replay in `HftError`/`on_accept` calldata authorization — (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `hyper-fungible-token` pallet's `on_accept` handler lets a cross-chain token transfer carry an optional SCALE-encoded `runtime_call` that is dispatched as the beneficiary's own origin, authorized by a `MultiSignature` over `(nonce, runtime_call)`. That signed payload contains no chain-binding data — no genesis hash, no `StateMachine`/chain id, no source-contract or local-asset identity — so the exact same signature is valid on every deployment of this pallet (every parachain, testnet, or fork) that shares the runtime's call-index layout, as long as the beneficiary account's nonce happens to match on that chain. This is the direct analog of the reported `_checkSig` bug: an off-chain authorization is not bound to "this contract instance" and can be replayed elsewhere.

### Finding Description
In `on_accept`: [1](#0-0) 

the code decodes `substrate_data.signature` and verifies it against `msg = keccak256((nonce, runtime_call).encode())` (with an Ethereum-prefix variant for ECDSA). `nonce` is the beneficiary's `frame_system` account nonce on *this* chain: [2](#0-1) 

There is no inclusion of:
- a genesis hash / chain identifier (so the message isn't chain-scoped),
- the `source`/`local_asset_id`/token-contract identity that this message arrived through (`ContractToAsset::<T>::get(source, &from)` at line 55), and
- any `dest`/destination chain marker.

On successful verification, the decoded `runtime_call` is dispatched with `RawOrigin::Signed(beneficiary)`, subject only to the runtime's `BaseCallFilter`: [3](#0-2) 

Because the signed digest is chain-agnostic, a signature a user produced to authorize a call on one deployment of this pallet (e.g. a specific parachain, or a forked/duplicate deployment of the same runtime — this pallet is instantiated in both `gargantua` and `nexus` runtimes per `parachain/runtimes/*/src/lib.rs`) remains valid on any other deployment sharing the runtime's call encoding, provided the beneficiary account's nonce there has not yet diverged (e.g. a fresh/low-activity account, which is the common case for a bridge-recipient account). An attacker who can trigger `on_accept` on the second deployment (by relaying/forging the corresponding cross-chain `PostRequest` with the same `message.data`/signature bytes) causes the same authorized `runtime_call` to be dispatched a second time as the victim's origin on a chain the victim never intended it for — duplicating or misusing the victim's authorization (double-dispatch of the signed call), exactly mirroring the "association ... reused in multiple instances" primitive of the seed report.

### Impact Explanation
This allows unauthorized/duplicate execution of a victim-signed `runtime_call` as the victim's own account origin on a chain/deployment the signature was never meant for. Depending on what dispatchable calls are unfiltered by `BaseCallFilter`, this can range from duplicated asset moves (e.g. `Assets::transfer`, `Balances::transfer*`) to other stateful calls executed twice under the victim's identity — a logic/replay attack matching the bounty's "replay/double-claim/double-settlement" and "unauthorized transaction or execution" categories. It does not require a malicious relayer/prover/admin — only an unprivileged actor able to submit the equivalent cross-chain message on a second deployment/fork sharing the pallet and runtime call layout.

### Likelihood Explanation
Likelihood is tied to real-world reuse of this pallet across multiple runtimes/networks (`gargantua`, `nexus`, and any future/forked deployment), and to beneficiary accounts having low/zero nonce on the second chain (the normal case for a first-time bridge recipient). No special privileges, leaked keys, or malicious infrastructure are needed — only that the same `SubstrateCalldata` bytes (signature + runtime_call) get delivered to a second on_accept execution context with a matching nonce.

### Recommendation
Bind the signed digest to the specific execution context: include the chain's genesis hash (or a stable chain/`StateMachine` identifier), the pallet instance's own identity (e.g. `local_asset_id`/`source` contract), and ideally a monotonic message-specific nonce/commitment (e.g. the ISMP request's own nonce or commitment hash) in the signed payload, rather than relying solely on `frame_system::account_nonce`, which is shared with ordinary transaction nonces and not scoped to this cross-chain authorization channel at all.

### Proof of Concept
1. Deploy/attach the `hyper-fungible-token` pallet to two runtimes that share the same `RuntimeCall` encoding (as is already the case for `gargantua` and `nexus`, or any two chains built from the same runtime).
2. Victim signs a `SubstrateCalldata { signature: Some(sig), runtime_call: call_bytes }` where `sig` is over `keccak256((0u32 /* nonce */, call_bytes).encode())`, intending it for chain A's bridged transfer.
3. Attacker relays an equivalent `PostRequest` (with the identical `message.data`) into chain B's `on_accept`, where the same beneficiary account also currently has nonce `0`.
4. `MultiSignature` verification at [4](#0-3)  succeeds on chain B despite the victim never authorizing execution there, and `runtime_call` dispatches as the victim's origin at [5](#0-4) .
