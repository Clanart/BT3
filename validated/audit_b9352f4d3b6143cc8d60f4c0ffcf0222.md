### Title
`SignCompleted` is an unsigned transaction whose embedded signature authenticates only the self-declared claimant, letting anyone forge a plan-completion claim - (File: coordinator/src/tributary/transaction.rs)

### Summary
The bug class in the report is "API/action lacks authentication or authorization checks." The Serai analog is `Transaction::SignCompleted`: it is declared `TransactionKind::Unsigned`, so `verify_transaction` performs no participant/nonce/signature check on it, and its inner `signature` field is verified only against the attacker-chosen `first_signer` key — i.e., the claimant authenticates themselves to themselves. The handler then trusts the claim and forwards a `Completed` message to the processors for that network.

### Finding Description
`Transaction::SignCompleted` carries `plan`, `tx_hash`, `first_signer`, and `signature`, and is deliberately made an unsigned transaction so multiple reporters deduplicate: [1](#0-0)  and [2](#0-1) .

For `TransactionKind::Unsigned`, `verify_transaction` performs no signer authentication at all — no participant check, no nonce, no signature over the transaction's `sig_hash`: [3](#0-2) .

The only cryptographic check is in `Transaction::verify`, which verifies `signature` under `first_signer` — a key supplied by the transaction author in the same message: [4](#0-3) . The challenge also only binds `plan`, `tx_hash`, the self-claimed `first_signer`, and `signature.R`: [5](#0-4) . An attacker picks `first_signer` as a key they control and signs — the check trivially passes and proves nothing about whether the plan actually completed or who completed it.

The block handler ignores the signature entirely (`signature: _`), only checks the plan has a known attempt, and unconditionally emits `sign::CoordinatorMessage::Completed { session, id: plan, tx: tx_hash }` to the network's processors: [6](#0-5) . Additionally, the fatally-slashed sender filter at the top of `handle_application_tx` only applies to `Signed` transactions, so `SignCompleted` bypasses it: [7](#0-6) .

### Impact Explanation
A forged `SignCompleted` causes every coordinator that processes the block to tell its processors "plan `plan` completed as external transaction `tx_hash`" for an arbitrary, attacker-chosen `tx_hash`. Processors treat `CoordinatorMessage::Completed` as authoritative completion of a signing plan — reattempts cease and the plan is finalized under a hash that may correspond to no real broadcast transaction, or a different transaction than the one actually signed. This produces a protocol state where a batch/sign plan is recorded as completed when the funds were never moved (or moved under a different hash) — directly analogous to "funds reported received that are not spendable" / an action performed without authorization. No signature, stake, or participation is required to forge the claim.

### Likelihood Explanation
Any party able to submit transactions to the tributary mempool can craft `SignCompleted` (kind byte 10, read at [8](#0-7) ) with a signature under their own freshly generated key. It passes `verify_transaction` (Unsigned branch) and `Transaction::verify` (self-referential signature), and is deduplicated only in that the first included claim wins. The only partial mitigation is that `first_signer` is slashed if the plan has no attempt — which does not prevent forgery for real, in-flight plans, where the impact lands.

### Recommendation
Bind the claim to a real authorized signer: either (a) make `SignCompleted` a `Signed` transaction (the deduplication rationale can be preserved by keying deduplication on `(plan, tx_hash)` rather than skipping authentication), or (b) at minimum verify `signature` against a key drawn from the validator set — e.g., require `first_signer` to be an active non-removed participant and verify the signature over the full transaction digest — and in the handler reject claims whose `first_signer` is not in `self.spec.validators()`. Also apply the fatally-slashed filter to `first_signer` for this transaction kind.

### Proof of Concept
1. A sign plan `P` exists: `AttemptDb::attempt(txn, genesis, Topic::Sign(P))` returns `Some`.
2. Attacker generates a Ristretto keypair `(k, K = k·G)`, chooses an arbitrary 32-byte `tx_hash`, and computes a Schnorr signature `σ = SchnorrSignature::sign(k, nonce, challenge)` where `challenge = sign_completed_challenge()` over `(P, tx_hash, K, σ.R)` per [5](#0-4) .
3. Attacker serializes `Transaction::SignCompleted { plan: P, tx_hash, first_signer: K, signature: σ }` (kind byte 10) and gossips/submits it.
4. `verify_transaction` accepts it (Unsigned, no signer check; `signature.verify(K, challenge)` passes because the attacker knows `k`).
5. `handle_application_tx` sends `CoordinatorMessage::Completed { session, id: P, tx: tx_hash }` to all processors of that network ( [9](#0-8) ), which record plan `P` as completed under a transaction that was never signed or broadcast — halting reattempts and finalizing a false completion.
