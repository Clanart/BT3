## Finding [1](#0-0) 

### Title
Silent ERC20 transfer failure falsely finalizes escrow withdrawal (unsafe raw `.call` + boolean-only check) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.sol` releases escrowed tokens using a raw low-level `.call` with the `IERC20.transfer.selector`, checking only that the call did not revert (`success`), and never decoding/validating the ERC20's returned boolean. Non-standard ERC20 tokens that return `false` instead of reverting on a failed transfer (the exact "LDO-style" bug class from the external report) will pass this check while no tokens actually move, yet the contract still deducts the escrow balance, marks the order as filled, and emits `EscrowReleased`/`EscrowRefunded` as if settlement succeeded.

### Finding Description
In `withdraw()`, escrowed token release is implemented as:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` here only reflects whether the external call reverted, not whether the ERC20 `transfer()` returned `true`. Per the referenced report, tokens like LDO return `false` on insufficient balance rather than reverting, so `success` stays `true` while the beneficiary receives nothing. Despite that, the code unconditionally proceeds to decrement `_orders[body.commitment][token] -= amount`, sets `_filled[body.commitment] = beneficiary`, and emits `EscrowReleased`/`EscrowRefunded` [1](#0-0) . The same unsafe pattern is repeated for the transaction-fee redemption and in `SweepDust` handling in the same file [3](#0-2) .

This is a real internal inconsistency: the mainline EVM implementation of the same withdrawal logic in `IntentsBase._withdraw` correctly uses `IERC20(token).safeTransfer(beneficiary, amount)`, which decodes and reverts on a `false` return [4](#0-3) . The Tron fork diverges from this safe pattern for its outbound release path.

### Impact Explanation
Because `_filled` and `_orders` accounting are updated based only on call-success rather than actual token movement, a solver/user beneficiary interacting with an atypical ERC20 (or one that becomes atypical, e.g. via a pausable/blacklist-style implementation that returns `false` rather than reverting) will have their order marked as finalized/refunded on-chain while receiving zero tokens. Because `_filled[body.commitment]` is now permanently set, the legitimate GET-request cancellation/timeout path (`onGetResponse`) that checks `Filled()` will reject any retry, and the escrow balance has already been decremented — the funds are effectively lost/locked with no path to recovery. This is a direct fund-loss condition triggered without any relayer, prover, or admin compromise, purely due to the destination token's transfer semantics.

### Likelihood Explanation
The path is reachable by any ordinary participant simply by using or being paid out in a token that returns `false` on failed transfer instead of reverting — a documented behavior class (the report's own LDO example) rather than a contrived edge case. No privileged role, malicious relayer, or forged proof is required; it is triggered purely by normal escrow settlement (`withdraw`) once a state-proof-verified `onGetResponse`/fill flow reaches the token transfer step.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and `onAccept`'s `SweepDust` branch with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in `IntentsBase._withdraw` and elsewhere in the codebase (`safeTransferFrom`/`safeTransfer` calls seen in `IntentGatewayV2.sol`, `IntentsBase.sol`, `WrappedHyperFungibleToken.sol`). This ensures a `false` return value reverts the transaction instead of allowing escrow state to be finalized without an actual transfer.

### Proof of Concept
1. Deploy an ERC20 mock that mimics LDO: `transfer()`/`transferFrom()` return `false` on insufficient balance instead of reverting.
2. Create and fill an intent order on the Tron `IntentGatewayV2` where escrow is denominated in this mock token, with the contract's token balance artificially reduced below the escrowed `amount` (e.g., by external drain, or by a fee-on-transfer-style discrepancy that the code doesn't fully guard).
3. Trigger `withdraw()` via the redeem-escrow / GET-response path.
4. Observe: `token.call(...)` returns `success = true` (mock doesn't revert) with `false` ABI-encoded in the return data, which is never checked; `_orders[...] -= amount` proceeds, `_filled[commitment] = beneficiary` is set, and `EscrowReleased` fires — while `beneficiary`'s token balance is unchanged, confirming silent loss/lock of the escrowed funds.
