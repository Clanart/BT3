## Analysis

This is exactly the analog of the M-23 report. In `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, the **commitment and escrow ledger are computed from `order.inputs[i].amount` (the amount the user *requested* to escrow), not from the amount actually captured by the gateway** — unlike the sibling `evm/src/apps/IntentGatewayV2.sol`, which explicitly re-measures the dispatcher's balance delta and overwrites `order.inputs[i].amount = received` *before* computing `reducedInputs`/the commitment (see the "Phase 1 … Phase 2" split at `evm/src/apps/IntentGatewayV2.sol:260-330`).

In the Tron variant's predispatch branch (`evm/tron/contracts/apps/IntentGatewayV2.sol:353-379` then `410-440`):

1. `reducedInputs[i].amount` is derived from `order.inputs[i].amount` (the caller-supplied, *requested* amount) at line 356-364, and the commitment is hashed over that at line 373 — **before** any tokens actually move through the predispatch call.
2. Only afterward does the code measure `balance = IERC20(token).balanceOf(dispatcher)` (line 422) and compare it to `requiredAmount = order.inputs[i].amount` (line 414), reverting if `balance < requiredAmount` (line 423) but **treating everything above `requiredAmount` as "dust"** and crediting the *original* `reducedInputs[i].amount` to escrow (line 435), regardless of what the gateway actually holds.

This mirrors the `TapToken` bug exactly: an accounting variable (`_orders[commitment][token]`, analogous to `dso_supply`/`emissionForWeek`) is credited based on a *pre-declared* value rather than the *actual* balance change, while a side "extra funds" bucket (`DustCollected`, analogous to `boostedTAP`) is computed independently off the real balance. Because `dust = balance - requiredAmount` is computed against `requiredAmount` (`order.inputs[i].amount`) rather than against the amount that was already credited via `reducedInputs[i].amount`, and because a fee-on-transfer or otherwise-lossy `predispatch.call` can make the dispatcher's real balance *less* than `order.inputs[i].amount` for a given token while still passing the `balance < requiredAmount` check for another token in the same loop (since the check is per-token, not global), the ledger `_orders[commitment][token]` can end up crediting more than the gateway actually received for that token. Later, `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-410`) pays out of `_orders[commitment][token]` unconditionally via `safeTransfer`, without ever checking the gateway's real `balanceOf(token)`.

## Comparison with the "safe" sibling implementation

The mainline EVM contract fixed this exact pattern by moving the balance measurement *before* fee/commitment computation (`evm/src/apps/IntentGatewayV2.sol:260-298`), and dedicated fuzzing/unit tests exist for fee-on-transfer tokens confirming the escrow must equal `IERC20(token).balanceOf` deltas, not the requested amount (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2257-2308`). The Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol` does not have the equivalent re-ordering/re-measurement for the predispatch path — it still books `reducedInputs[i].amount` (derived from `order.inputs[i].amount`) into escrow rather than the balance actually captured for that specific token.

## Caveats / what I could not fully verify

- I was not able to fully trace whether `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` can realistically cause a *per-token* balance shortfall for one token while other tokens in the same order pass their own `balance < requiredAmount` checks (e.g., a predispatch swap that consumes token A to produce token B, where A's post-dispatch balance ends up below `requiredAmount` for A while B's happens to be sufficient). This requires a concrete `predispatch.call` payload (e.g., a DEX swap or fee-on-transfer token) to demonstrate end-to-end; I did not have room to construct/verify a full PoC transaction trace against `ICallDispatcher`.
- I could not confirm whether this Tron contract is actually deployed/reachable in production (the directory is `evm/tron/contracts/...`), which affects whether this qualifies as "production" per the bounty gate — this should be verified before submission.
- Given the remaining uncertainty about exploitability specifically for the Tron variant, I present this as the strongest local analog I found, but recommend a Devin/security engineer construct and run a concrete Foundry/Tron test reproducing a per-token shortfall via `predispatch.call` to confirm the escrow-over-crediting is exploitable in practice, before treating it as confirmed.

### Title
Escrow ledger crediting from requested amount instead of actual received balance in predispatch flow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron `IntentGatewayV2.placeOrder`'s predispatch branch, the escrowed amount stored in `_orders[commitment][token]` is derived from the order's requested `amount`, computed and hashed into the commitment *before* the predispatch call actually moves tokens, while the post-call balance check only guards against falling below `requiredAmount` per-token rather than reconciling escrow to the actual balance received.

### Finding Description
`reducedInputs` (used both for the commitment hash and the escrow credit) is computed from `order.inputs[i].amount` at [1](#0-0) , before the `predispatch.call` is dispatched via `ICallDispatcher`. After the call executes, the code only checks that the dispatcher's balance is `>= requiredAmount` per token and treats any excess as "dust" swept to the gateway, then unconditionally credits `reducedInputs[i].amount` to `_orders[commitment][token]` [2](#0-1) . This is structurally identical to the `TapToken.emitForWeek` bug: an accounting ledger (`_orders` / `dso_supply`) is updated using a value decoupled from the contract's real token balance, with any balance/ledger divergence папered over by a side "extra" bucket (`DustCollected` / `boostedTAP`) computed independently. The sibling mainline EVM contract avoids this by re-measuring balances and overwriting `order.inputs[i].amount` with the actual delta *before* computing fees/commitment/escrow [3](#0-2) .

### Impact Explanation
If a `predispatch.call` (attacker-controlled calldata routed through `ICallDispatcher`, e.g., a DEX interaction or an ERC-20 with transfer fees) causes the dispatcher to end up holding less of a given input token than `order.inputs[i].amount` claims, the escrow ledger can still be credited with the full pre-fee `reducedInputs[i].amount` for that token as long as the naive `balance < requiredAmount` check is satisfied by whatever balance happens to be present when checked. Downstream, `_withdraw` in `IntentsBase.sol` pays out of `_orders[commitment][token]` via `safeTransfer` without ever checking the gateway's actual token balance [4](#0-3) , so an inflated escrow entry can eventually pay out more than the gateway holds for that token, at the expense of other users' escrowed funds (fund loss/insolvency across orders).

### Likelihood Explanation
This requires an attacker to construct an order with a crafted `predispatch.call`/`predispatch.assets` combination that manipulates per-token balances during the call — this is a normal, permissionless user-facing entrypoint (`placeOrder`), not requiring any privileged relayer/prover/admin role, but does require identifying a token/predispatch combination where the divergence actually manifests (e.g., fee-on-transfer intermediate token consumed by the predispatch call). I was not able to fully verify a concrete exploitable combination within available tool budget.

### Recommendation
Mirror the mainline `evm/src/apps/IntentGatewayV2.sol` fix: measure the dispatcher's actual balance delta for each input token immediately after the predispatch call executes, overwrite `order.inputs[i].amount` (or `reducedInputs[i].amount`) with that measured value, and only then compute the protocol fee, commitment hash, and escrow credit — ensuring `_orders[commitment][token]` never exceeds what the gateway actually received for that token.

### Proof of Concept
Not independently constructed/verified — see caveats above. A PoC would need a `predispatch.call` targeting `ICallDispatcher` that causes one input token's dispatcher balance to diverge from `order.inputs[i].amount` (e.g., via a fee-on-transfer token or an intermediate swap) while satisfying the per-token `balance >= requiredAmount` guard for all other tokens, then demonstrate that `_orders[commitment][token]` for the manipulated token exceeds the gateway's actual holdings, followed by a `redeemEscrow`/refund call draining more than deposited.
