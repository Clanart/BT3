### Title
Divergent conflict-marker parsers between hunk extraction and reassembly allow silent corruption of Copilot-resolved merge conflicts - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
This is the closest Desktop analog to the Symmio "inconsistent liquidation fee" root cause: two code paths compute a value from the *same underlying state* using *inconsistent logic*, and the more privileged/downstream path silently uses stale/mismatched data. In Symmio, `forceClosePosition` and `LiquidationFacet.liquidatePartyB` disagreed on `availableBalance` because one had access to reserve-vault funds the other didn't. In GitHub Desktop, `extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) and `reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) both parse the same raw, attacker-influenceable file content for `<<<<<<<`/`=======`/`>>>>>>>` conflict markers, but use different, non-equivalent parsing rules. A crafted branch merged by an unsuspecting user can make the two parsers disagree on the number/position of conflict hunks, causing the AI-generated resolution content to be spliced into the wrong location when the file is reassembled and written back to disk — silently corrupting what the user reviews and commits.

### Finding Description
`extractConflictHunks` [1](#0-0)  walks the file greedily: once it sees a line matching `oursMarker` (`^<{7}(?:\s|$)`), it collects "ours" content until the *first* line matching `baseMarker` or `separatorMarker`, then collects "theirs" content until the *first* line matching `theirsMarker`. It performs no verification that the block is well-formed before consuming lines, and it does not treat nested/stray marker-shaped lines specially — a stray `<<<<<<<`-looking line inside "ours"/"theirs" content is simply swallowed as ordinary text. If no closing `>>>>>>>` is ever found, the malformed hunk is dropped via `continue` [2](#0-1) , but because the inner scanning loops already advanced `i` to end-of-file while searching for the missing marker, any subsequent real conflict hunks later in the file are also never discovered by this function.

`reassembleResolvedFile`, which independently re-walks the *same* raw file content to splice the model's resolutions back in, uses a stricter and different rule: for each `<<<<<<<` line it performs a lookahead requiring *both* a `=======` separator *and* a `>>>>>>>` closing marker before treating the block as a real conflict; otherwise the line is pushed through as literal content and scanning continues line-by-line (it does not jump to EOF) [3](#0-2) .

Because these are two independent regexp-based scans over the same attacker-influenceable bytes with different well-formedness rules, they can disagree on:
- how many conflict blocks exist in the file (`hunks.length` from extraction vs. the number of splice points found during reassembly), and
- which lines belong to which "hunk" when marker-like text (e.g. a doc/tutorial file about git conflicts, a stored diff/patch fixture, or generated content containing literal `<<<<<<<`/`=======`/`>>>>>>>` sequences) is present in the merged file on either side.

`extractConflictHunks`'s hunk count feeds directly into:
- the prompt sent to Copilot ("Conflict 1 of N" sections built from `context.files[].hunks`) [4](#0-3) , and
- `validateResolutionPaths`, which gates acceptance of the model's response purely on whether the returned hunk count matches `expectedHunkCounts` derived from `extractConflictHunks` [5](#0-4) .

`reassembleResolvedFile` then splices the (validated, N-length) resolutions into the file by re-parsing the raw content with its own, different boundary logic and matching resolutions "by order, not by line number" [6](#0-5) . Existing guards (`validateResolutionPaths`'s hunk-count check, and the conflict-marker-leftover check in `parseCopilotConflictResolution` at lines 444-448) only validate the *model's output shape* against the *extraction* parser's view of the file — they never cross-check against what `reassembleResolvedFile`'s independent (and stricter) parser will actually find. A discrepancy between the two parsers is therefore never detected before the file is rewritten.

### Impact Explanation
When the two parsers disagree, the model's resolved content for hunk *k* gets spliced into whatever conflict block *reassembleResolvedFile* enumerates as its *k*-th block — which may not correspond to the semantic hunk the model actually resolved (as described to it via `extractConflictHunks`'s "Conflict k of N" prompt section). This can result in:
- A genuinely unresolved conflict region (still containing part of the original diff) being silently overwritten with resolution text meant for a different section, or
- Resolution text being inserted at the wrong location while a real conflict block is left with mismatched/garbled content,

all without any error being surfaced — the "reasoning" shown to the user in the resolution dialog describes a decision that no longer matches the bytes actually written to disk before the user stages and commits. This satisfies the required impact class: "silent corruption of what the user commits or pushes," reachable purely through a crafted, unprivileged branch/PR that the user merges/rebases and then accepts an AI-generated resolution for.

### Likelihood Explanation
Exploitation only requires the victim to merge or rebase against a branch/PR (fully attacker-controlled, no local access or elevated privileges needed) that contains, in the *conflicting region* of a text file, lines that begin with 7+ `<`, `=`, or `>` characters that are not intended as real git conflict markers (e.g., documentation about resolving git conflicts, a checked-in diff/patch fixture, or minified/generated separator-style content). This is a plausible, naturally-occurring shape for legitimate-looking files (READMEs, test fixtures, CI templates) and does not require any unnatural interaction — the user's normal action of clicking "Resolve with Copilot" or "Accept" in the conflict-resolution dialog triggers the vulnerable code path. The feature is gated behind Copilot conflict resolution being enabled/available, which somewhat limits blast radius, but no additional trust boundary needs to be crossed.

### Recommendation
Unify the two marker-parsing implementations into a single well-formedness-checked parser (reuse `reassembleResolvedFile`'s lookahead-validated boundary detection inside `extractConflictHunks`, or vice versa) so both hunk extraction and reassembly agree on hunk count and boundaries for the same raw content. Additionally, harden `validateResolutionPaths`/`reassembleResolutions` to fail closed (throw `CopilotValidationError`) whenever the number of splice points found during reassembly does not exactly match the number of hunks the resolution was validated against, rather than silently matching "by order."

### Proof of Concept
Not independently executed in this review (no filesystem/terminal access available); the divergence is demonstrated purely from static analysis of the two parsing implementations:
1. Extraction ends the "ours" section on the *first* separator/base marker match and the "theirs" section on the *first* closing marker match, with no lookahead validation [7](#0-6) .
2. Reassembly requires a confirmed `=======` and `>>>>>>>` pair before treating a `<<<<<<<` as a real conflict start, else it passes the line through as literal content and keeps scanning [8](#0-7) .

A concrete PoC would need a Devin session with filesystem access to construct a fixture repository containing a merge conflict where one side embeds literal `<<<<<<<`/`=======`/`>>>>>>>`-shaped lines in ordinary file content, run `extractConflictHunks` and `reassembleResolvedFile` against the resulting merged file, and diff the hunk boundaries each function reports.

export function extractConflictHunks(
  fileContent: string,
  contextLines: number = 3
): ReadonlyArray<IConflictHunk> {
  const lines = fileContent.split(/\r?\n/)
  const hunks: Array<IConflictHunk> = []

  let i = 0
  while (i < lines.length) {
    if (!oursMarker.test(lines[i])) {
      i++
      continue
    }

    const oursStart = i + 1
    const oursLines: Array<string> = []
    const baseLines: Array<string> = []
    let hasBase = false
    const theirsLines: Array<string> = []
    let hunkEnd = -1

    i = oursStart
    // Collect ours content
    while (i < lines.length) {
      if (baseMarker.test(lines[i])) {
        hasBase = true
        i++
        break
      }
      if (separatorMarker.test(lines[i])) {
        i++
        break
      }
      oursLines.push(lines[i])
      i++
    }

    // If diff3, collect base content until separator
    if (hasBase) {
      while (i < lines.length) {
        if (separatorMarker.test(lines[i])) {
          i++
          break
        }
        baseLines.push(lines[i])
        i++
      }
    }

    // Collect theirs content until closing marker
    while (i < lines.length) {
      if (theirsMarker.test(lines[i])) {
        hunkEnd = i
        i++
        break
      }
      theirsLines.push(lines[i])
      i++
    }

    // If we never found the closing marker, skip this malformed hunk
    if (hunkEnd === -1) {
      continue
    }
