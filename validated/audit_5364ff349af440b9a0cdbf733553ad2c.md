### Title
Unbounded index read in `is_atom_canonical`/`is_clvm_canonical` on attacker-supplied CLVM buffers can raise an uncaught `IndexError` during spend-bundle admission - (File: `chia/full_node/mempool_manager.py`)

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse the raw serialized CLVM bytes of a submitted coin spend's `puzzle_reveal`/`solution` to decide dedup eligibility, indexing into the buffer with an offset derived entirely from the untrusted length-prefix byte, without ever checking the offset against `len(clvm_buffer)`. This mirrors the CVE-2016-9264 bug class: a length/record field read from untrusted input is used to index into a buffer without a bounds check, causing an out-of-bounds read when the crafted input is shorter than the length field implies.

### Finding Description
`is_atom_canonical()` computes a variable-length prefix (`prefix_len` up to 5 bytes) purely from the first byte of the buffer, then does: [1](#0-0) 
```
atom_len = b & mask
for i in range(prefix_len):
    atom_len <<= 8
    offset += 1
    atom_len |= clvm_buffer[offset]
```
There is no check that `offset` stays within `len(clvm_buffer)` before indexing. `is_clvm_canonical()` drives this loop across the whole buffer and also indexes `clvm_buffer[offset]` on each iteration without a bounds check: [2](#0-1) 

Both functions are invoked directly on attacker-controlled bytes taken from a submitted `CoinSpend`'s `puzzle_reveal` and `solution` during mempool admission, in `MempoolManager.validate_spend_bundle()`: [3](#0-2) 

A crafted single- or few-byte buffer whose leading byte encodes a large length prefix (e.g. `0xf8`, which claims a 4-byte continuation length field) but whose buffer ends before those continuation bytes exist, causes `clvm_buffer[offset]` to index past the end of the `bytes` object. In Python this raises `IndexError` rather than reading adjacent heap memory (unlike the C `listmp3.c` case), so the impact class is a raised, unhandled exception rather than a silent info leak — but the reachable trigger (submitter-controlled spend bytes, no bounds validation before indexing) is the same root cause described in the CVE.

### Impact Explanation
`validate_spend_bundle()` is called for every coin spend inside a spend bundle as part of standard mempool admission (from `add_transaction()` / RPC `push_tx` paths), after CLVM/signature validation has already succeeded via the Rust `validate_clvm_and_signature()` call. Whether the raised `IndexError` is caught by an outer handler in `full_node.py`'s `add_transaction()` could not be conclusively determined within available search results — only test/documentation matches for `validate_spend_bundle` were surfaced, not the calling wrapper's exception-handling code. If uncaught at that layer, this would produce an unhandled exception per malicious spend bundle, potentially disrupting mempool processing for that submission (a localized denial-of-service on transaction admission), not a broader node crash or consensus divergence, since Python `IndexError` cannot corrupt memory the way the original C buffer overflow could.

### Likelihood Explanation
Reachable via a straightforward, single unprivileged spend-bundle submission (e.g., via RPC `push_tx`) with a hand-crafted, short `puzzle_reveal` or `solution` byte string engineered to have a first byte in the multi-byte length-prefix ranges (`0xf8`–`0xff`-adjacent classes) but insufficient trailing bytes. No special privileges, peer position, or existing coin ownership beyond referencing a spendable coin are required to trigger the code path, since `is_clvm_canonical` runs unconditionally for every coin spend during `validate_spend_bundle`.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()`/`is_clvm_canonical()` before every `clvm_buffer[offset]` access — e.g., verify `offset < len(clvm_buffer)` (and that enough trailing bytes remain for the full `prefix_len`) prior to indexing, raising a handled `ConsensusError`/returning "not canonical" instead of allowing an `IndexError` to propagate. Additionally, confirm (and add if missing) that callers of `validate_spend_bundle()` in `full_node.py` catch broad exceptions from this code path and convert them into a normal `MempoolInclusionStatus.FAILED` response rather than letting them propagate unhandled.

### Proof of Concept
1. Submit a `SpendBundle` containing one `CoinSpend` for any valid unspent coin, where `solution` (or `puzzle_reveal`) is set to a minimal, malformed serialized-CLVM buffer such as `bytes.fromhex("f8")` (single byte `0xf8`), which claims a 4-byte continuation length prefix but supplies zero continuation bytes.
2. Submit via RPC `push_tx` (or directly through `FullNode.add_transaction`), ensuring the spend otherwise passes Rust CLVM/signature validation up to the point where `validate_spend_bundle()` calls `is_clvm_canonical(bytes(coin_spend.solution))`.
3. Observe `is_atom_canonical()` attempting `clvm_buffer[offset]` for `offset >= len(clvm_buffer)`, raising `IndexError`, which is unhandled at the point examined in this investigation — full-node behavior (crash vs. clean rejection) requires further live testing beyond what the static/index search here could confirm.
