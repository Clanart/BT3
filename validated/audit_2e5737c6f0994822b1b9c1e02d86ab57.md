## Analog Found

### Title
Unverified ERC20 transferFrom delta in `BridgeTransferERC20.requestERC20Transfer` can cause cross-chain value inflation — ([File: contracts/service_chain/bridge/BridgeTransferERC20.sol])

### Summary
The Kaia service-chain bridge accepts ERC20 deposits from any unprivileged caller via `requestERC20Transfer`/`onERC20Received`, and pays out the *declared* `_value` on the counterpart chain based purely on the fact that `safeTransferFrom` did not revert — never verifying that the contract's actual token balance increased by the declared amount. This mirrors the reported Allo.sol `_fundPool` bug class: trusting a declared/expected transfer amount instead of validating the resulting balance delta.

### Finding Description
`requestERC20Transfer` is a public, unprivileged entry point: [1](#0-0) 

It calls `IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit))`, then immediately proceeds to `_requestERC20Transfer`, which emits `RequestValueTransfer` carrying the full `_value` that operators will later mint/unlock for `_to` on the counterpart chain: [2](#0-1) 

`SafeERC20.safeTransferFrom` only asserts that the low-level call succeeds and that any returned boolean is `true` — it never checks `balanceOf(address(this))` before/after the call: [3](#0-2) [4](#0-3) 

Exactly as in the reported issue, if `_tokenAddress` is a non-standard ERC20 that returns `true`/succeeds while transferring less than the requested amount (fee-on-transfer tokens, rebasing tokens, or tokens that silently cap transfers instead of reverting), the bridge will:
1. Receive less than `_value + _feeLimit` tokens.
2. In **lock-mode** (`modeMintBurn == false`), skip any burn/balance validation entirely (no `burn()` call exists in that branch) and simply emit `RequestValueTransfer(_value, ...)`.
3. Operators, observing this event, later call `handleERC20Transfer` on the counterpart chain to mint/unlock the full declared `_value` for `_to`, even though the bridge's true collateral is short.

Token registration only whitelists the token address (`onlyRegisteredToken`, `onlyUnlockedToken`) — it does not validate ERC20 transfer-semantics compliance.

### Impact Explanation
This produces genuine cross-chain supply inflation / unauthorized value movement: value credited on the counterpart chain exceeds the collateral actually locked in the bridge contract, directly matching the "Accept only concrete unauthorized value movement... or supply inflation" criterion. It is reachable by any single unprivileged transaction sender who deposits a non-standard ERC20 (there is no requirement that only vetted/standard tokens be registrable, and the vulnerability is purely in the bridging contract logic, not the token's).

### Likelihood Explanation
Likelihood depends on whether the bridge operator whitelists a non-standard-behaving ERC20 token (fee-on-transfer/deflationary/transfer-capping tokens), which is a known real-world token category. Since `_requestERC20Transfer` performs no post-transfer balance verification and no burn-based implicit check in lock mode, exploitation requires no special privileges beyond calling the public function with an already-registered non-conforming token.

### Recommendation
After `safeTransferFrom`, verify `balanceOf(address(this))` increased by exactly `_value.add(_feeLimit)` before proceeding to emit `RequestValueTransfer`/mint-equivalent operations. Alternatively, compute the actually-received amount as `balanceAfter - balanceBefore` and use that value (rather than the caller-declared `_value`) for `RequestValueTransfer` and any counterpart-chain minting/unlocking logic. Consider restricting registrable tokens to those verified to be fully ERC20-standard compliant.

### Proof of Concept
1. Bridge operator registers a "FaultyToken" that returns `true` on `transferFrom` but silently transfers only the caller's actual balance when the requested amount exceeds it (non-reverting behavior).
2. Attacker (Alice) holds 20 FaultyTokens, approves the bridge for 100.
3. Alice calls `requestERC20Transfer(tokenAddress, bob, 50, 0, "")`.
4. `safeTransferFrom(Alice, bridge, 50)` executes: FaultyToken transfers only Alice's 20 tokens but returns `true`; `SafeERC20` treats this as success.
5. `_requestERC20Transfer` emits `RequestValueTransfer(..., _value=50, ...)` despite only 20 tokens actually held by the bridge.
6. Bridge operators, trusting the event, call `handleERC20Transfer` on the counterpart chain to mint/unlock 50 tokens for Bob — inflating supply by 30 tokens relative to the bridge's real collateral.

*Note: The precise minting/lock-vs-burn behavior on the destination chain, and whether any additional operator-side sanity checks exist outside this repo's scope, could not be fully verified from the available Solidity sources alone; this assessment is based on the code paths present in `BridgeTransferERC20.sol` and `BridgeFee.sol` (`_payERC20FeeAndRefundChange`), whose full internals were not retrievable within the available search results.*

```text
    function callOptionalReturn(IERC20 token, bytes memory data) private {
        // We need to perform a low level call here, to bypass Solidity's return data size checking mechanism, since
        // we're implementing it ourselves.

        // A Solidity high level call has three parts:
        //  1. The target address is checked to verify it contains contract code
        //  2. The call itself is made, and success asserted
        //  3. The return value is decoded, which in turn checks the size of the returned data.
        // solhint-disable-next-line max-line-length
        require(address(token).isContract(), "SafeERC20: call to non-contract");

        // solhint-disable-next-line avoid-low-level-calls
        (bool success, bytes memory returndata) = address(token).call(data);
        require(success, "SafeERC20: low-level call failed");

        if (returndata.length > 0) { // Return data is optional
            // solhint-disable-next-line max-line-length
            require(abi.decode(returndata, (bool)), "SafeERC20: ERC20 operation did not succeed");
        }
    }
```
