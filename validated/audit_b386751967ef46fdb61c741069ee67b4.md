### Title
Unprivileged mWomSV holder claims 100% of bonus rewards without forfeiture by exploiting the broken `_calExpireForfeit` in mWOMSVBaseRewarder - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWOMSVBaseRewarder._calExpireForfeit` never queries `mWOMSV.getRewardablePercentWAD(_account)` and instead sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount` is always `0` regardless of how much of the user's mWomSV balance is in cooldown/unlocking. The sibling contract `vlMGPBaseRewarder._calExpireForfeit` correctly multiplies `_amount` by `vlMGP.getRewardablePercentWAD(_account) / 1e18`, proving the mWomSV version is missing this logic and is broken.

### Finding Description
In `rewards/mWOMSVBaseRewarder.sol`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();

    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
``` [1](#0-0) 

Compare to the correct pattern in `rewards/vlMGPBaseRewarder.sol`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardablePercentWAD = vlMGP.getRewardablePercentWAD(_account);
    uint256 rewardableAmount = _amount * rewardablePercentWAD / 1e18;
    ...
}
``` [2](#0-1) 

`mWOMSVBaseRewarder` never calls `mWOMSV.getRewardablePercentWAD`, so `rewardableAmount` always equals `_amount`, meaning `forfeitAmount` is always `0`. `_sendReward` uses this result directly: `uint256 forfeitAmount = _calExpireForfeit(_account, userRewards[_rewardToken][_account]); uint256 toSend = userRewards[_rewardToken][_account] - forfeitAmount;` [3](#0-2) 

`mWomSV.getRewardablePercentWAD` computes the fraction of a user's mWomSV that is still fully locked (not in cooldown/unlocking); users who have called `startUnlock` for a portion of their balance are supposed to forfeit a proportional share of unclaimed rewards, which is meant to be redistributed to remaining full lockers via `_queueNewRewardsWithoutTransfer`. [4](#0-3) [5](#0-4) 

Because the forfeiture multiplier is never applied, any unprivileged mWomSV holder can call `mWomSV.startUnlock` for up to 99%+ of their balance (this itself triggers `multiclaimFor`, but subsequent bonus reward accrual and a later `getReward`/`multiclaim` call via `MasterMagpie` will still route through `mWOMSVBaseRewarder.getReward` → `_sendReward` → `_calExpireForfeit`), and receive their full `userRewards` amount with zero forfeiture, even though `getRewardablePercentWAD` for that account is far below `1e18`.

### Impact Explanation
This is theft of unclaimed yield: rewards that should be forfeited proportionally to the unlocking share and redistributed to remaining full mWomSV lockers via `_queueNewRewardsWithoutTransfer` are instead fully claimed by the unlocking user. This directly reduces the yield backing for honest full lockers and breaks the reward conservation invariant the contract is designed to enforce (Immunefi impact class: theft of unclaimed yield).

### Likelihood Explanation
This requires no special privilege — only holding mWomSV (obtainable by locking mWOM via `mWomSV.lock`) and standard usage flow (`startUnlock`, wait for reward accrual, call `getReward`/`multiclaim` through `MasterMagpie`). It is deterministic and repeatable by any holder, with no capital requirement beyond normal staking amounts.

### Recommendation
Fix `_calExpireForfeit` in `mWOMSVBaseRewarder.sol` to match `vlMGPBaseRewarder.sol`'s pattern: query `mWOMSV.getRewardablePercentWAD(_account)` and compute `rewardableAmount = _amount * rewardablePercentWAD / 1e18` before deriving `forfeitAmount`.

### Proof of Concept

1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie`, and a mock bonus reward token; wire them together as in production.
2. User A locks mWOM via `mWomSV.lock(amount)` to receive mWomSV shares, staked into `MasterMagpie`.
3. Call `mWOMSVBaseRewarder.queueNewRewards(rewardAmount, rewardToken)` to accrue bonus rewards for User A while fully locked.
4. User A calls `mWomSV.startUnlock(0.99 * balance)`, putting 99% of shares into cooldown; assert `mWOMSV.getRewardablePercentWAD(userA) < 1e18` (close to 1%).
5. Accrue more bonus rewards via `queueNewRewards` after the unlock starts.
6. User A calls `MasterMagpie.multiclaim`/`getReward` on `mWOMSVBaseRewarder`.

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
