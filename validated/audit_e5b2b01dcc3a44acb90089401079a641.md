### Title
Uncontrolled resource consumption when computing an offer's offered coins - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer._get_offered_coins()` re-executes each parent spend's inner puzzle with `cost_left = INFINITE_COST` (no bound), independent of the CLVM-cost budget already applied in `Offer.__post_init__()`. Any wallet user or RPC caller who loads an attacker-supplied offer file (`take_offer`, `get_offer_summary`, `check_offer_validity`, CLI `take_offer`) triggers this unmetered execution path, allowing a malicious offer to consume excessive CPU time.

### Finding Description
When an `Offer` object is constructed (`Offer.from_bech32` / `Offer.from_bytes`), `__post_init__` computes additions/hints for every coin spend with a real cost budget: `max_cost = int(DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM)`, decremented across `compute_spend_hints_and_additions` calls, raising `ValidationError` if exceeded. [1](#0-0) 

However, `get_offered_coins()` / `_get_offered_coins()` is a *separate* code path that is invoked lazily (from `summary()`, `get_offered_amounts()`, `arbitrage()`, `get_pending_amounts()`, `get_primary_coins()`), all of which are reachable from unprivileged, untrusted offer files via wallet RPC endpoints (`get_offer_summary`, `check_offer_validity`, `take_offer`) before the offer's signature/mempool validity has been confirmed by a peer: [2](#0-1) 

Inside `_get_offered_coins`, the *inner puzzle* of every coin spend is re-run with an unbounded cost budget:
```
cost_left = INFINITE_COST
...
puzzle_cost, conditions = inner_puzzle.run_with_cost(cost_left, inner_solution)
assert cost_left >= puzzle_cost
cost_left -= puzzle_cost
``` [3](#0-2) 

`cost_left` is reset to `INFINITE_COST` for the whole offer (not accumulated/limited across spends, and not derived from the already-validated per-spend budget used in `__post_init__`). Because `puzzle_reveal`/`inner_puzzle` content is fully attacker-controlled in an offer file (it is only checked to structurally look like a known outer puzzle via `match_puzzle`/`get_inner_puzzle`, not cost-bounded), an attacker can construct an inner puzzle designed to consume very large CLVM execution time/cost (the codebase's own "malicious generator" test corpus in `chia/_tests/core/mempool/test_mempool.py` demonstrates this class of CLVM program — e.g., recursive string-doubling `large_string`/`SINGLE_ARG_INT_COND` style constructs) — see the malicious-generator patterns already used to test cost-DoS elsewhere in the codebase: [4](#0-3) 

This is analogous to CVE-2025-70059 (CWE-400, uncontrolled resource consumption causing DoS): an untrusted, attacker-supplied input (here, an offer file/spend bundle) is processed through an expensive operation with no resource ceiling, allowing a remote/local caller to exhaust CPU on the victim's wallet process.

### Impact Explanation
A wallet user who merely inspects an offer (via `get_offer_summary`, `check_offer_validity`, or the `take_offer` CLI/RPC flow before pushing) can be forced into a long-running/unbounded CLVM execution, stalling the wallet RPC service (single-threaded async event loop) for the duration of that computation. Because `get_offer_summary`/`check_offer_validity` are meant to safely preview *untrusted* offers received from any counterparty (this is their entire purpose), this directly matches the "spend-triggered transaction-processing halt" impact category: it can hang/DoS the local wallet node processing an untrusted spend bundle, without requiring the offer to ever be pushed to the mempool or signed.

### Likelihood Explanation
High likelihood: offer files are explicitly designed to be shared with and parsed by arbitrary untrusted counterparties before acceptance, and `get_offer_summary`/`check_offer_validity` are the documented safe way to preview them. No signature or coin ownership is required to trigger the parsing path — only that the bytes deserialize as a valid `Offer`/`WalletSpendBundle` and that `match_puzzle` recognizes an outer puzzle layer (CAT/NFT/singleton/etc.) whose inner puzzle is attacker-authored.

### Recommendation
Bound `cost_left` in `_get_offered_coins()` (and any other `INFINITE_COST` puzzle executions on unvalidated, attacker-supplied offer content) using the same `MAX_BLOCK_COST_CLVM`-derived budget enforced in `__post_init__`, and fail with a `ValidationError`/timeout rather than allowing unmetered execution. Consider computing offered coins from the already cost-limited additions computed in `__post_init__` instead of re-running inner puzzles with `INFINITE_COST`.

### Proof of Concept
Not fully verifiable without executing code (no sandbox access). Conceptual PoC: craft a `WalletSpendBundle` whose `coin_spends` include a `puzzle_reveal` that is a CAT/singleton-wrapped puzzle (so `match_puzzle` succeeds and `get_inner_puzzle`/`get_inner_solution` return a driver-recognized inner puzzle), where the *inner* puzzle is a CLVM program modeled after the malicious "large_string"/exponential-doubling generator patterns already present in this repo's test suite (`chia/_tests/core/mempool/test_mempool.py:2620-2695`), producing a very large but not-instantly-fatal execution. Serialize this as a bech32 offer and submit it to `check_offer_validity` or `get_offer_summary` on a target wallet RPC — `_get_offered_coins()` will execute the inner puzzle with `INFINITE_COST`, consuming CPU far beyond normal spend costs. This part of the analysis (actual runtime measurement) is unverified due to lack of execution environment; verification would require running this scenario against a live wallet RPC instance.
