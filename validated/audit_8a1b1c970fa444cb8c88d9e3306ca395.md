### Title
`isDiffTooLarge` / large-diff threshold silently hides oversized hunks from review before commit, letting a malicious blob content be committed unreviewed - ([File: app/src/lib/git/diff.ts])

### Summary
The perp-order bug was about a hard-coded ±12.5% "safety cap" (`px + (px >> 3)`) that was not risk-appropriate for its actual context (leverage), letting a value pass through a supposedly protective check while causing outsized, unintended damage. The closest structural analog in GitHub Desktop is the fixed, un-configurable thresholds `MaxCharactersPerLine`, `MaxReasonableDiffSize`, and `MaxDiffBufferSize` in `app/src/lib/git/diff.ts` that decide whether a diff is rendered for user review or collapsed into a `LargeText`/`Unrenderable` placeholder that requires an extra click to actually view. [1](#0-0) 

### Finding Description
`isDiffTooLarge` flags a diff as too large to render whenever *any single line* exceeds `MaxCharactersPerLine` (5000 chars), and `isBufferTooLarge`/`isValidBuffer` gate on raw buffer size (`MaxReasonableDiffSize` ≈ 4.375MB, `MaxDiffBufferSize` = 70MB). [2](#0-1) 

When any of these thresholds is exceeded, `buildDiff` returns `DiffType.LargeText` or `DiffType.Unrenderable` instead of the normal `DiffType.Text` diff, and the UI collapses the file's diff into a "too large to display" panel that the user must proactively click "Show Diff" to expand: [3](#0-2) [4](#0-3) 

This is exactly the same broken-invariant shape as the perp report: a single hard-coded numeric cap is used as a proxy for "safe to trust by default," without considering the actual risk context — here, whether the file being committed is one the user actually intends to inspect (e.g., a source file with an injected long line, or a minified/obfuscated payload). A file containing a single attacker-crafted line >5000 characters (e.g. a minified JS backdoor appended to a legitimate file, or one long line hiding a supply-chain payload) is silently collapsed by default, and Desktop's commit flow does **not** block staging/committing files whose diff is in the `LargeText`/`Unrenderable` state — the Changes list still allows the file to be checked and committed even though its content was never rendered for the user.

Unlike the bidi-character warning (`hasHiddenBidiChars`, `HiddenBidiCharsRegex`) which is a real, purpose-built guard for exactly this class of "hidden content" attack and is surfaced via `DiffContentsWarning`, the size-based collapse has no equivalent contextual signal — it's a pure performance heuristic reused as a de-facto content-review gate, and it fails silently (no warning banner, just an opt-in "Show Diff" button) rather than blocking or flagging. [5](#0-4) [6](#0-5) 

### Impact Explanation
If an attacker controls content that ends up in the user's working directory (e.g., a file modified by a build tool, a merge from an attacker-controlled branch/PR, or a dependency update script) and crafts it so at least one line exceeds 5000 characters or the diff exceeds ~4.375MB, Desktop will, by default, not render that diff for the user. A user who commits/pushes "at a glance" (trusting the Changes view) can silently commit and push content they never actually saw — this maps to the explicitly allowed impact category "silent corruption of what the user commits or pushes."

However, this requires the user to actively decide to commit the file without clicking "Show Diff" first — it degrades review, but does not force or hide the action; the file is still visibly listed in the Changes pane, and standard `git diff`/`git log` review outside Desktop still shows the content. This limits severity to a review-bypass / assurance gap rather than a definitive corruption-without-user-action.

### Likelihood Explanation
Moderately likely to be triggered unintentionally (e.g., large generated files, minified assets, long single-line JSON/lockfiles), and can be trivially engineered by an attacker who can influence a file the victim will commit (e.g. a build artifact or a file touched by a script from an untrusted source in the working directory). It does not require local/physical access, admin rights, or prior malware — only the ability to get attacker-controlled content into the working tree that the victim later stages and commits.

### Recommendation
- Do not conflate "too large/slow to render" with "safe to commit unreviewed." Consider surfacing an explicit warning (similar to `DiffContentsWarning`'s bidi-character alert) when a file has crossed the large-diff threshold and is about to be committed, rather than a silent, opt-in-only collapse.
- Consider tightening/parameterizing `MaxCharactersPerLine` based on file type (e.g., don't apply a single-line-length heuristic to files whose extension suggests non-generated source), or provide a persistent, per-file indicator in the commit dialog that content was never rendered.
- At minimum, add a "content not reviewed" indicator on the commit/Changes list entry for files in `LargeText`/`Unrenderable` state so users aren't misled into thinking the truncated view represents full review.

### Proof of Concept
1. In a tracked repository, take any file and add a single line whose length exceeds 5000 characters (e.g., `python3 -c "print('x'*6000)" >> file.js`) mixed with a small malicious payload appended within that long line.
2. Stage the file in GitHub Desktop and open the Changes diff view.
3. Observe that `isDiffTooLarge` (app/src/lib/git/diff.ts:79-89) causes `buildDiff` to return `DiffType.LargeText` (app/src/lib/git/diff.ts:868-881), and the UI renders the "The diff is too large to be displayed by default." panel (app/src/ui/diff/index.tsx:178-194) instead of the actual diff content.
4. Without clicking "Show Diff," commit the file — Desktop does not block or flag the commit, and the injected content is committed/pushed without ever being displayed to the user.

**Note:** I was unable to fully confirm from the index whether Desktop blocks/warns on committing an *unreviewed* `LargeText`/`Unrenderable` file (e.g., a confirmation dialog) — the commit-flow gating logic around `DiffSelectionType`/large file dialogs (`app/src/lib/large-files.ts`) only checks raw file *size on disk*, not whether a diff was actually rendered. If such a review-gate exists elsewhere in the commit flow, it would reduce/eliminate this finding's validity, and I could not verify its absence with certainty given index coverage limits — starting a full Devin session would allow tracing the entire commit-confirmation code path to confirm.

```typescript
function isValidBuffer(buffer: Buffer) {
  return buffer.length <= MaxDiffBufferSize
}

/** Is the buffer too large for us to reasonably represent? */
function isBufferTooLarge(buffer: Buffer) {
  return buffer.length >= MaxReasonableDiffSize
}

/** Is the diff too large for us to reasonably represent? */
function isDiffTooLarge(diff: IRawDiff) {
  for (const hunk of diff.hunks) {
    for (const line of hunk.lines) {
      if (line.text.length > MaxCharactersPerLine) {
        return true
      }
    }
  }

  return false
}
```
