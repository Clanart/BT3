### Title
Attacker-controlled transaction in the same block overwrites the instruction data and origin of scanned Serai deposits - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` accumulates scanned outputs in a single `outputs` vector across the entire block, then for every subsequent transaction — including ones that pay nothing to Serai — recomputes `presumed_origin` from that transaction's `input[0]` and applies it, plus that transaction's extracted Serai `data`, to **all** accumulated `Output`s. Any unprivileged party who lands a transaction after a victim's deposit in the same block can overwrite the deposit's attached instruction (`data`) and claimed origin, causing the deposit to be credited to the attacker's chosen Serai instruction or left with no valid instruction at all — mirroring the audited class where unsolicited, unauthenticated incoming transfers corrupt the accounting of received funds.

### Finding Description
In `get_outputs` (`processor/src/networks/bitcoin.rs:686-740`), the code loops over `block.txdata[1 ..]`, calls `scanner.scan_transaction(tx)` (`networks/bitcoin/src/wallet/mod.rs:199-214`, which matches outputs purely on `output.script_pubkey`), and pushes each match into `outputs`. The guard at line 702 is `if outputs.is_empty() { continue; }` — it checks the **accumulated** vector, not whether the current transaction produced any outputs. Consequently, once any earlier transaction in the block paid to a Serai script (External/Branch/Change/Forwarded), every later transaction in the block triggers:

- `presumed_origin` recomputation from `tx.input[0]`'s spent output (lines 714-729),
- `data = Self::extract_serai_data(tx)` for the *unrelated* transaction (line 730),
- `output.data.clone_from(&data)` for every accumulated `External` output and `output.presumed_origin.clone_from(&presumed_origin)` for all outputs (lines 731-735).

A deposit's `data` is the Serai instruction (e.g., the `Shorthand::transfer` payload that determines who is credited, per `processor/src/tests/literal/mod.rs:88-90`). The instruction embedded by the depositor via OP_RETURN or the `OP_SHA256 <hash> OP_EQUALVERIFY` witness pattern is simply replaced by whatever the attacker's later transaction carries — including empty data if the attacker provides no OP_RETURN and no matching witness.

### Impact Explanation
The scanner reports an output as received (`OutputType::External`) whose instruction data and presumed origin do not correspond to the transaction that actually created it. An attacker can craft an OP_RETURN in their own transaction — which need not pay Serai at all — containing an instruction crediting the deposit to their own Serai address, or can strip the instruction entirely (empty `data`), leaving the received funds without a valid routing instruction. The result is funds reported received under attacker-chosen metadata or effectively uncreditable bookkeeping, while the attacker expends only an ordinary Bitcoin transaction fee.

### Likelihood Explanation
Any unprivileged Bitcoin user can broadcast a transaction positioned after a victim deposit in the same block (e.g., observing the mempool and submitting with a competitive fee; miners routinely order by fee rate). No validator key, threshold collusion, or privileged access is required — the trigger is a public on-chain transaction, fully within the accepted input model. The only requirement is that a Serai-destined output exists earlier in the same block.

### Recommendation
Track per-transaction results: break/continue based on whether `scanner.scan_transaction(tx)` produced outputs for *that* transaction, and apply `presumed_origin`/`data` only to the outputs newly found in that transaction — e.g., scan into a per-tx `Vec`, `continue` if it is empty, populate metadata for those outputs only, then extend the accumulated list.
