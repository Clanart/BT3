### Title
Relayer fee ledger zeroed unconditionally at dispatch time, causing permanent loss of relayer rewards on destination-side execution failure with no timeout/retry path - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` dispatches an ISMP POST to the destination chain's host manager (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate) instructing it to pay out `available_amount` to the beneficiary, and then unconditionally zeroes `Fees::<T>` for that relayer/chain right after the dispatch call returns `Ok`. This is analogous to the external report's core flaw: an action is irreversibly locked into a "committed" state (proposal sponsorship / here, fee ledger zeroing) with no closing/retry mechanism if the follow-through never materializes, permanently trapping the actor's entitlement (a new proposal / here, their earned fees).

### Finding Description
The withdrawal flow is:
1. `Fees::<T>::get(dest_chain, address)` reads `available_amount`.
2. `dispatcher.dispatch_request(...)` sends a `DispatchPost` with `timeout: 0` to the destination's `host_manager` (EVM) via `WithdrawalParams`, or to `HYPERBRIDGE_MODULE_ID` (substrate) via `Message::WithdrawRelayerFees`.
3. Immediately after `dispatch_request` returns success (meaning only that the commitment was recorded in `RequestCommitments`, not that funds were disbursed), `Fees::<T>::insert(dest_chain, address, U256::zero())` destroys the relayer's balance entry. [3](#0-2) 

Because `timeout: 0` means the message never expires, there is no `on_timeout` recovery path available for this class of message — confirmed by the absence of any `on_timeout` handling in the relayer pallet. The destination-side `EvmHost.withdraw()` / `HostManager.onAccept()` call can genuinely revert if the host manager or `EvmHost` lacks sufficient fee-token balance, as demonstrated by `test_host_manager_insufficient_balance`, which asserts a revert with non-empty revert data when the host has no fee tokens. [2](#0-1) [4](#0-3) 

When the destination-side call reverts (insufficient host balance, a paused/frozen host, or any other execution failure at delivery time), the underlying ISMP request delivery/receipt mechanics do not roll back the source-side `Fees` mutation — that mutation already happened unconditionally at dispatch time on Hyperbridge, decoupled from the eventual destination outcome. The relayer has no mechanism analogous to "closing a stuck proposal": there is no re-accumulation, no retry of the same `available_amount`, and no `on_timeout`/`on_response` callback that restores the zeroed balance if the payout never lands. The relayer's nonce has also already been incremented, so a retried extrinsic with the same signed payload cannot be replayed either.

### Impact Explanation
This is a direct loss-of-funds condition for relayers: earned fees (`Fees::<T>` balance, populated via `accumulate_fees`/`accumulate.rs` from real relayer service work) can be permanently and unrecoverably destroyed by a single failed destination-side transfer that is entirely plausible in production (e.g., the destination `EvmHost`/`HostManager` fee-token balance is drawn down by concurrent withdrawals, is momentarily below the requested `available_amount`, or the host is frozen/paused at delivery time). No malicious actor, relayer, prover, or governance action is required — this is a straightforward ordering-of-operations bug: the ledger is mutated as if settlement is guaranteed, when settlement is actually asynchronous and can fail independently.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: relayer fee balances and host manager token balances are independently managed, and any timing where the destination-side balance dips below the requested withdrawal amount (well within normal operational variance, not requiring any adversarial behavior) triggers the failure mode. The relayer's own auto-withdraw tooling in `tesseract/messaging/relayer/src/fees.rs` treats a failed delivery as retryable and logs "they will be retried," but that off-chain expectation does not match the on-chain reality: the `Fees` ledger entry is already zero by the time delivery is attempted, so any retry after a destination-side revert has nothing left to withdraw. [5](#0-4) 

### Recommendation
Do not zero `Fees::<T>` at dispatch time. Instead, only decrement/zero the ledger once a delivery receipt (or equivalent proof-of-execution) confirms the destination-side transfer succeeded, or maintain a "pending withdrawal" intermediate state that can be reverted back into `Fees::<T>` if the destination call reverts or the request is otherwise proven never to have executed. Alternatively, give this withdrawal message class a real `timeout_timestamp` (rather than `timeout: 0`) and implement `on_timeout` to restore the zeroed balance, mirroring the safe pattern already used by the Intent Gateway's cancel/refund flow where escrow is only released after the fill/cancel outcome is proven.

### Proof of Concept
1. Relayer accrues `Fees::<T>[EVM-X, relayer] = 500 tokens` via `accumulate_fees`.
2. Destination `EvmHost` (chain `EVM-X`) has its fee-token balance drawn down (e.g., other relayers withdraw concurrently, or governance sweeps revenue) so its on-chain balance is now `< 500` tokens.
3. Relayer signs and submits `withdraw_fees` for the full `500` amount. `Pallet::withdraw` dispatches the POST and immediately sets `Fees::<T>[EVM-X, relayer] = 0` per `modules/pallets/relayer/src/withdrawal.rs:177`.
4. The message is later delivered to `EvmHost`/`HostManager` on `EVM-X`. `IHostManager.withdraw` reverts (mirrors `test_host_manager_insufficient_balance`), so no tokens ever reach the relayer's beneficiary.
5. Because `timeout: 0` was used, no timeout ever fires, `Fees::<T>` was already zeroed, and the relayer's nonce was already incremented — the relayer's 500 tokens are permanently lost with no on-chain recovery path.

#[test]
fn test_host_manager_insufficient_balance() {
	let mut env = TestEnv::new();
	let manager = host_manager_of(&mut env);

	// Host has no fee tokens; withdraw attempt should fail on SafeERC20 transfer
	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	let err = env
		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");
	assert!(!err.is_empty(), "expected non-empty revert data");
}
