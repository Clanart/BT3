### Title
Weak identity check on Copilot conflict-hunk splicing lets a crafted repository desync hunk positions and silently corrupt committed file content - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` splices the AI model's per-hunk resolutions back into the original conflicted file by re-scanning the raw file text for `<<<<<<<`/`=======`/`>>>>>>>` marker lines and matching resolutions to hunks **purely by ordinal position** (`hunkIndex`), not by content or line-range identity. The only cross-check that a returned resolution set is "correct" is `validateResolutionPaths`, which validates **hunk count equality**, not hunk correspondence.

### Finding Description
`reassembleResolvedFile` walks the raw file content line-by-line and treats every line matching `^<{7}(?:\s|$)` as the start of a candidate conflict block, doing a forward look-ahead for a `=======` separator and a `>>>>>>>` closer: [1](#0-0) 

Each well-formed marker block found is unconditionally replaced with `hunkResolutions[hunkIndex]`, and `hunkIndex` is incremented regardless of whether that block corresponds to the same conflict the model actually reasoned about. The docstring itself states the matching is "by order, not by line number" [2](#0-1) .

The only safety net before this splice is `validateResolutionPaths`, which checks that the *count* of hunks the model returned for a path matches an "expected" count derived from `IFileConflictContext.hunks` — not that they are positionally or semantically the same hunks: [3](#0-2) 

The per-resolved-content sanity check in `parseCopilotConflictResolution` is also narrow: it only rejects a hunk's `resolvedContent` if it contains **both** a `<<<<<<<`-style line **and** a `=======`-style line (`/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)`) — it does not reject content containing a lone `>>>>>>>`-style line, a lone `<<<<<<<` line, or a lone `=======` line: [4](#0-3) 

Because `IFileConflictContext.hunks`/`rawContent` originate from the attacker-controlled repository (a merge/rebase/cherry-pick conflict against a malicious branch, fork, or fetched remote), the attacker fully controls the byte content of the conflicted file, including any text that happens to look like `<<<<<<<`, `=======`, or `>>>>>>>` sequences (e.g., inside a code comment, string literal, markdown doc about Git, or a heredoc) that are *not* real conflict markers but sit between or around genuine conflict regions. If whatever component builds `IFileConflictContext.hunks` (upstream of this file, not fully verified) parses conflicts differently than `reassembleResolvedFile`'s simple forward-scanning regex state machine — e.g. by anchoring to git's actual conflict boundaries rather than re-deriving them from raw text — the two hunk counts/orderings can still coincidentally match in count while disagreeing in position. Since `validateResolutionPaths` only checks the aggregate count, such a mismatch is invisible to the app, and `reassembleResolvedFile` will happily splice hunk *N*'s AI-generated resolution into the position of a decoy/attacker-planted marker block, while a real conflict block ends up either unresolved, duplicated, or overwritten with unrelated content.

### Impact Explanation
If exploited, this results in **silent corruption of what the user commits or pushes** — the explicit in-scope impact category for this analog. A user who clones/fetches an attacker-influenced branch and merges it, then uses "Resolve with Copilot", could have code silently misplaced into the wrong file region (e.g., moving a security check, deleting a validation guard, or duplicating executable logic) without any parse error, since the reassembly logic only guards against total marker-count mismatch, not positional identity. This is worse than a normal bad AI merge because it happens **beneath** the app's own consistency checks, with no error surfaced to the user.

### Likelihood Explanation
Exploitation requires: (1) the user merges/rebases against an attacker-influenced branch/fork containing a conflicting file crafted with decoy marker-like text, and (2) the user chooses to resolve with Copilot. This is a normal, un-suspicious workflow (no unnatural steps, no local access, no leaked credentials) — the attacker only needs to get their branch/fork conflicted against the victim's work, which is a standard part of collaborative Git usage. I could not fully confirm the actual divergence in hunk-counting between the (unread) context-building module and this reassembly regex, so likelihood of the exact desync trigger is **uncertain pending further review of `app/src/lib/copilot-conflict-context.ts`**.

### Recommendation
- Anchor hunk resolutions to a stable identity (e.g., a hash or line-range of the original marker block) rather than purely ordinal position, and verify that identity at splice time.
- Reject `resolvedContent` containing *any* single conflict-marker-like line (`<{7}`, `={7}`, `>{7}`), not just the combination of two.
- Have `reassembleResolvedFile` and whatever produces `IFileConflictContext.hunks` share a single conflict-parsing implementation so they cannot disagree on hunk boundaries.
- Show the user a diff of the final reassembled file before it is written/committed, so any mis-splice is visible prior to commit/push.

### Proof of Concept
Conceptual PoC (pending confirmation of the upstream parser divergence):
1. Attacker crafts a file in their fork that contains one real conflict block plus a decoy sequence of lines that begins with a line matching `/^<{7}(?:\s|$)/` (e.g., a comment documenting git conflict-marker syntax) but is not a real git conflict.
2. Victim merges the attacker's branch, producing a real conflicted file whose raw content (`ctx.rawContent`) contains both the real marker block and the decoy sequence.
3. If the upstream context-builder counts only the real conflict as a hunk (matching the actual `.orig`/index-derived conflict count) while `reassembleResolvedFile`'s independent regex-based scan advances `hunkIndex` differently because of the decoy text, `validateResolutionPaths`'s count check passes (both still see the same total count if the decoy resolves cleanly on both sides, e.g. a well formed but non-genuine marker block), yet the resolution content gets spliced into the wrong block by `reassembleResolvedFile`'s line-order walk at lines 559–591 [1](#0-0) .
4. The user commits/pushes the corrupted file without any warning.
