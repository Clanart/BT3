### Title
PedPoP accepts the identity point as an ECDH encryption key (with a trivially valid PoP), exposing encrypted DKG secret shares to any observer - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2020-14061 is a jackson-databind deserialization bug where attacker-controlled type/typing bytes cause unintended objects to be accepted. The Serai analog: `EncryptedMessage::read` deserializes an attacker-supplied ephemeral/encryption `key` with `C::read_G`, which enforces canonical encoding but does **not** reject the identity point, and the accompanying Schnorr proof-of-possession `pop` is parsed and verified with the generic `SchnorrSignature` machinery, which also accepts `R = identity`. A signature `(R = identity, s = 0)` satisfies the verification equation `R + c·A − s·G = 0` for any challenge `c` when `A = identity`, so the identity key is accepted as a legitimately-owned encryption key. Because ECDH against the identity point always yields the identity point, the shared ChaCha20 secret encrypting that participant's secret shares becomes a publicly known constant, letting any eavesdropper recover the shares.

### Finding Description
`EncryptedMessage::read` reads the message's encryption key and PoP using the base `Ciphersuite` readers:

- `key: C::read_G(reader)?` and `pop: SchnorrSignature::<C>::read(reader)?` at crypto/dkg/pedpop/src/encryption.rs:171-176.
- `Ciphersuite::read_G` only checks that the encoding is canonical; it performs no identity rejection (crypto/ciphersuite/src/lib.rs:91-101). Identity rejection exists only in the FROST-specific `Curve::read_G` override (crypto/frost/src/curve/mod.rs:125-131), which pedpop does not use.
- `SchnorrSignature::read` similarly uses `C::read_G` for `R` (crypto/schnorr/src/lib.rs:51-53), and `verify` reduces to `multiexp_vartime` over `[(1, R), (c, A), (-s, G)]` equaling identity (crypto/schnorr/src/lib.rs:88-109). Setting `A = identity`, `R = identity`, `s = 0` satisfies this unconditionally — a forged PoP requiring no private key.
- PedPoP encrypts each participant's share with ChaCha20 keyed by an ECDH result derived from the recipient's advertised `key` (crypto/dkg/pedpop/src/encryption.rs:9-12). If `key` is the identity point, the sender-side shared secret `ephemeral_scalar * identity = identity` is fixed and known to everyone, regardless of the sender's ephemeral scalar.

An unprivileged DKG participant therefore publishes `key = identity` plus the trivial PoP `(R = identity, s = 0)`. Every other honest participant encrypts their contribution to that participant under a publicly computable key.

### Impact Explanation
All secret shares routed to the malicious participant are encrypted under a ChaCha20 key derivable by any observer of the wire messages. An eavesdropper (or any counterparty who keeps the ciphertexts) recovers those shares in plaintext. Combined with the attacker's own share, collecting `t` shares of the polynomial allows reconstruction of the threshold signing key, producing unilateral signing capability — key share recovery leading to forging arbitrary threshold signatures. This meets the "key share recovery" validation criterion.

### Likelihood Explanation
Requires only that the attacker participate in a DKG session and broadcast a crafted `EncryptedMessage`/encryption-key message — normal, unprivileged protocol input. No collusion, no validator privileges, and no race conditions are needed. Acceptance depends on pedpop's verification path not separately rejecting identity keys; `read` does not, and the PoP check passes trivially as shown. I could not fully confirm whether a later `verify` step in `pedpop` adds an explicit `is_identity` check on the key; if one exists, the attack is mitigated.

### Recommendation
In `EncryptedMessage` key handling (and any other pedpop path accepting peer-published group elements used for ECDH or as signature public keys), reject identity points — e.g., switch to `Curve::read_G` semantics or add an explicit `is_identity` check at crypto/dkg/pedpop/src/encryption.rs:173. Additionally consider rejecting `R = identity` in `SchnorrSignature::read`/verification for non-FROST uses, since `(identity, 0)` is a universal valid signature under the identity key.

### Proof of Concept
1. Attacker joins the DKG as participant `i` and serializes an encryption-key message where `key` is the canonical 32-byte encoding of the identity point (e.g., `01 00…00` for Ed25519/Ristretto).
2. Attacker sets `pop = SchnorrSignature { R: identity, s: 0 }` (encodings of identity point followed by 32 zero bytes). `pop.verify(identity, c)` returns true for any challenge `c` because `identity + c·identity − 0·G = identity`.
3. Honest participants encrypt shares `share_j(i)` via ChaCha20 keyed on `H(ephemeral_j * identity) = H(identity)` — a constant any observer computes.
4. Observer decrypts all shares addressed to `i`, collects `t` shares, interpolates the signing polynomial, and recovers the group secret key.
