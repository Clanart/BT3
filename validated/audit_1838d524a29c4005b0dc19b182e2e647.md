## Analysis: Local Analog Found

The Juicebox `changeTokenOf` bug class is: an authorized reconfiguration of a token/asset mapping silently orphans funds that were already escrowed under the *old* mapping, with no path left to redeem them. I traced the exact structural analog in the `hyper-fungible-token` pallet.

### Title
`update_token` mapping rotation permanently strands escrowed/burned funds for in-flight cross-chain transfers - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`send()` escrows or burns a user's balance and dispatches a `DispatchPost` whose `to` field is the token contract address read from `TokenContracts` **at send time**. If `update_token` later rotates or removes that chain's contract mapping (a normal, legitimate lifecycle operation — e.g. migrating to a new EVM contract), the `ContractToAsset` reverse-lookup entry for the *old* contract address is deleted. When the original request times out, `on_timeout` re-derives the asset via `ContractToAsset::<T>::get(dest, &to)` using the address embedded in the original request — which no longer resolves, so the refund path fails and the user's already-escrowed/burned funds can never be recovered.

### Finding Description
In `send()` [1](#0-0) , the pallet reads the current `TokenContracts` entry, locks/burns the user's asset, and dispatches a `DispatchPost` targeting that contract address as `to`.

`update_token` [2](#0-1)  can, at any time, overwrite `TokenContracts[chain][asset_id]` with a new contract address (deleting the old `ContractToAsset` reverse mapping) or remove the chain entirely — with no check for outstanding in-flight requests still referencing the old address.

`on_timeout` recovers the asset purely by reverse-looking-up the destination contract address embedded in the stale request: `ContractToAsset::<T>::get(dest, &to).ok_or(HftError::UnknownContractOnTimeout)?` [3](#0-2) . Once `update_token` has deleted that entry (via `add_chains` overwrite or `remove_chains`), this lookup fails, `on_timeout` errors out, and the ISMP timeout can never be successfully applied — the escrowed native balance or burned non-native asset accounting is never reversed.

This is structurally identical to `changeTokenOf`: a legitimate, authorized reconfiguration call breaks the redemption/refund path for value that was committed under the prior mapping, with **no migration or drain-check before allowing the rotation** (contrast with `EvmHost.updateHostParamsInternal`, which explicitly requires the old fee token balance to be zero before allowing a fee-token change: `if (balance != 0) revert CannotChangeFeeToken();` [4](#0-3) ). No equivalent invariant exists in `update_token`.

### Impact Explanation
Funds locked in the pallet's escrow account (native assets) or already burned (non-native assets, pending re-mint on timeout) become permanently unrecoverable once the contract mapping used by their in-flight request is rotated or removed before delivery/timeout resolves. This is a direct loss-of-funds condition for the affected sender — matching the bounty's "stealing or loss of funds" and "false state acceptance / one-time receipt handling" categories, since the pallet's own bookkeeping (`TokenContracts`/`ContractToAsset`) becomes permanently inconsistent with in-flight commitments.

### Likelihood Explanation
`update_token` is a routine, expected operational call (e.g., migrating a token's EVM contract to a new deployment) rather than a rare or adversarial action — the original C4 finding was confirmed with the same characteristic (the function is only reachable by the project's own `CreateOrigin`, yet was still accepted as a valid, fixed vulnerability because it silently breaks user redemption). Any timing overlap between an in-flight `send` and an `update_token` call on the same `(chain, asset_id)` triggers the bug; no relayer collusion, forged proof, or leaked key is required.

### Recommendation
Before allowing `update_token` to overwrite or remove a `(chain, asset_id)` mapping, either (a) retain the old `ContractToAsset` entry until all in-flight requests referencing it have resolved (timeout or response), or (b) key `on_timeout`'s asset resolution off data embedded in the original commitment/request rather than a mutable global reverse-index, so later admin changes cannot invalidate refund resolution for already-dispatched requests.

### Proof of Concept
1. Admin registers asset `A` for `StateMachine::Evm(X)` with contract `C1` via `register_token`.
2. User calls `send()`; native/non-native balance is locked/burned; a `DispatchPost` with `to = C1` is committed [5](#0-4) .
3. Before the request is delivered or times out, admin calls `update_token` to rotate the contract for `(Evm(X), A)` to `C2`, which removes `ContractToAsset::<T>::remove(chain, C1)` [6](#0-5) .
4. The original request eventually times out; `on_timeout` calls `ContractToAsset::<T>::get(dest, &to)` with `to = C1`, which now returns `None`, causing `HftError::UnknownContractOnTimeout` [3](#0-2) .
5. The timeout message can never be successfully applied; the user's locked/burned funds are stranded with no recovery path.
