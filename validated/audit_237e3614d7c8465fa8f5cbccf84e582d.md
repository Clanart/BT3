### Title
`CallbackController#deduced_phishing_attack?` validates a parsed host substring but `redirect_to_app` redirects using the full raw `decoded_host` string, and lacks the character-level sanitization applied elsewhere in the same codebase - ([File: app/controllers/shopify_app/callback_controller.rb])

### Summary
`CallbackController#redirect_to_app` builds the OAuth-callback redirect target from the raw `decoded_host` value (`"#{decoded_host}#{return_to}"`), while its phishing check `deduced_phishing_attack?` only validates `URI(decoded_host).host` through `ShopifyApp::Utils.sanitize_shop_domain`. This validate-a-substring/use-the-whole-string pattern means the actual redirect destination is never reconstructed from the sanitized/trusted host. A sibling implementation in the same gem, `ShopifyApp::EmbeddedApp#deduced_phishing_attack?`, applies an explicit `unsafe_embedded_host?` character filter (rejecting control characters, `\x7f`, backslashes, and userinfo `@`) before calling the same `sanitize_shop_domain`; `CallbackController` has no equivalent filter.

### Finding Description
`app/controllers/shopify_app/callback_controller.rb` decodes `params[:host]` via `ShopifyAPI::Auth.embedded_app_url` (external gem, not vendored in this repo) into `decoded_host` [1](#0-0) . `redirect_to_app` then constructs the redirect target as `"#{decoded_host}#{return_to}"` and only rejects it if `deduced_phishing_attack?` returns true [2](#0-1) . `deduced_phishing_attack?` validates trust by calling `ShopifyApp::Utils.sanitize_shop_domain(URI(decoded_host).host)` — i.e., it only inspects the `.host` component as extracted by Ruby's stdlib `URI()` parser, not the full string that is actually used for the redirect [3](#0-2) .

By contrast, the gem's other host-handling path, `ShopifyApp::EmbeddedApp#safe_embedded_app_url`/`#deduced_phishing_attack?`, explicitly guards against unsafe characters (control chars, `0x7f`, backslash) and userinfo (`@`) in the decoded host before calling the identical `sanitize_shop_domain` helper [4](#0-3) . `CallbackController` has no analogous `unsafe_embedded_host?`/character-filter step, so any parser-differential string that Ruby's `URI()` resolves to a trusted `.host` (e.g., via the `myshopify.com`/`shopify.com`/`spin.dev` domain lists in `ShopifyApp::Utils::TRUSTED_SHOPIFY_DOMAINS`) is accepted, and the full un-filtered `decoded_host` string — not the extracted/validated host — is what is actually sent in the `Location` header via `redirect_to(redirect_to, allow_other_host: true)`.

This is a structural TOCTOU-style flaw: the security check and the security-sensitive use operate on two different derived values (`URI(decoded_host).host` vs raw `decoded_host`), and the check itself omits the character sanitation present in the parallel code path in the same gem, indicating the hardening was not applied consistently.

### Impact Explanation
If `decoded_host` can be crafted so that Ruby's `URI()` extracts a trusted `.host` while the raw string, when actually navigated to by an embedded-app host or App Bridge (or even just echoed as the redirect `Location`), points at (or contains) an attacker-controlled origin, the callback flow would redirect the merchant's authenticated browser session to the attacker's page with query parameters (potentially including `shop`, `host`, and other callback params) appended. This maps to Shopify's "Improper Redirect / Open Redirect leading to information disclosure" impact class, since it leaks callback context to an attacker-controlled origin post-OAuth.

### Likelihood Explanation
Preconditions: the app must be embedded (`ShopifyAPI::Context.embedded?`), and the attacker only needs to control the `host` query parameter of the OAuth callback request, which is fully attacker-supplied and unauthenticated at this point in the flow. No secrets or victim cooperation are required to reach `deduced_phishing_attack?`. However, exploitability strictly depends on: (1) the exact string-construction behavior of the external `ShopifyAPI::Auth.embedded_app_url` method, which is not vendored in this repository and could not be inspected here, and (2) a concrete Ruby-`URI()`-vs-actual-destination parser differential string. Both are necessary to demonstrate a full end-to-end bypass, and neither could be conclusively verified from the code available in this repo.

### Recommendation
- In `CallbackController`, derive the redirect target from the *sanitized* host value returned by `ShopifyApp::Utils.sanitize_shop_domain`, not from the raw `decoded_host` string, mirroring the pattern that should be used consistently across the gem.
- Apply the same character-level filtering used in `ShopifyApp::EmbeddedApp#unsafe_embedded_host?` (rejecting control characters, `0x7f`, backslashes, and userinfo) to `decoded_host` in `CallbackController` before parsing/validating it.
- Reconstruct `redirect_to` from the validated host plus a known-safe path/query, rather than concatenating unvalidated user input directly into the `Location` header.

### Proof of Concept
Could not be fully constructed/verified: reproducing an end-to-end bypass requires knowledge of `ShopifyAPI::Auth.embedded_app_url`'s exact string-building logic, which lives in the external `shopify_api` gem and is not present in this repository's index, so a concrete `params[:host]` payload that (a) survives that method unchanged, (b) causes Ruby's `URI()` to extract a trusted `.host`, and (c) causes the resulting `decoded_host` string to actually navigate to a different attacker-controlled origin could not be confirmed here. The concrete, repo-verifiable defect is the code-path asymmetry itself:

```ruby
# app/controllers/shopify_app/callback_controller.rb
def deduced_phishing_attack?
  sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(URI(decoded_host).host) # validates only .host
  ...
end

def redirect_to_app
  ...
  redirect_to = "#{decoded_host}#{return_to}"   # uses the FULL raw string, not the validated host
  redirect_to(redirect_to, allow_other_host: true)
end
```
versus the hardened sibling in `lib/shopify_app/controller_concerns/embedded_app.rb`:
```ruby
def deduced_phishing_attack?(decoded_host)
  sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(decoded_host) unless unsafe_embedded_host?(decoded_host)
  ...
end
```
A unit test asserting parity would be: for a corpus of strings containing control characters, backslashes, or userinfo `@` that `unsafe_embedded_host?` in `EmbeddedApp` rejects, assert that `CallbackController#deduced_phishing_attack?` also rejects the same corpus (currently it has no equivalent filter, so this assertion would need to be added and would fail against the current implementation).

    def safe_embedded_app_url(host)
      decoded_host = Base64.decode64(host.to_s)
      return if deduced_phishing_attack?(decoded_host)

      ShopifyAPI::Auth.embedded_app_url(Base64.strict_encode64(decoded_host))
    end

    def deduced_phishing_attack?(decoded_host)
      sanitized_host = ShopifyApp::Utils.sanitize_shop_domain(decoded_host) unless unsafe_embedded_host?(decoded_host)
      if sanitized_host.nil?
        message = "Host param for redirect to embed app in admin is not from a trusted domain, " \
          "redirecting to root as this is likely a phishing attack."
        ShopifyApp::Logger.info(message)
      end
      sanitized_host.nil?
    end

    def unsafe_embedded_host?(decoded_host)
      return true if decoded_host.empty? || !decoded_host.valid_encoding?
      return true if unsafe_embedded_host_characters?(decoded_host)

      embedded_host_authority(decoded_host).include?("@")
    end

    def unsafe_embedded_host_characters?(decoded_host)
      decoded_host.each_char.any? do |character|
        character_code = character.ord
        character_code <= 0x20 || character_code == 0x7f || character == "\\"
      end
    end

    def embedded_host_authority(decoded_host)
      decoded_host.sub(%r{\Ahttps?://}i, "").split(%r{[/?#]}, 2).first.to_s
    end
