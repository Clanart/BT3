### Title
Attacker-controlled u32 length prefix causes ~4 GiB allocation/abort in `EncryptedMessage::read` - (File: crypto/dkg/src/lib.rs)

### Summary
The CVE-2021-44490 bug class is "crafted input controls a size used for a memset/allocation, yielding an extremely large value and crashing the process". In Serai's in-scope `dkg` crate, `EncryptedMessage::read` (the DKG message decoder invoked on ciphertext bytes supplied by other participants) reads a 4-byte little-endian length prefix and immediately materializes `vec![0; usize::from(u32_len)]` before performing `read_exact`. An unprivileged participant submitting a DKG message with length `0xffffffff` forces a ~4 GiB allocation, which aborts the process (`Vec` allocation failure is a fatal `abort` in Rust, not a recoverable error). The length is bounded only by `u32::MAX`, not by the actual bytes present.

### Finding Description
`EncryptedMessage` is the encrypted payload exchanged between DKG participants in `crypto/dkg`. Its `read` function (in `crypto/dkg/src/lib.rs`, following the `ThresholdKeys`/`ThresholdView` section) deserializes fields then reads a `u32` ciphertext length and allocates a zeroed `Vec<u8>` of exactly that size before reading the bytes:

```rust
let mut ciphertext_len = [0; 4];
reader.read_exact(&mut ciphertext_len)?;
let mut ciphertext =
  vec![0; usize::try_from(u32::from_le_bytes(ciphertext_len)).unwrap()];
reader.read_exact(&mut ciphertext)?;
```

There is no sanity cap (e.g., a `TRANSACTION_SIZE_LIMIT`-style bound) and no chunked read. Compare with the pattern already acknowledged elsewhere in the codebase — `networks/ethereum/src/machine.rs` `Call::read` explicitly comments "A valid DoS would be to claim a 4 GB data is present for only 4 bytes" and reads in 1 KB chunks precisely to bound the allocation; the `dkg` crate does not do this. Similarly `coordinator/src/p2p.rs` enforces `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating, showing the expected mitigation pattern. The upstream YottaDB CVE is the same shape: an arithmetic expression produces an absurd size handed to `memset`, crashing on demand.

### Impact Explanation
Any node processing a DKG `EncryptedMessage` from an untrusted participant (PedPoP/share distribution path, where `EncryptedMessage::read` parses messages broadcast to the group) can be crashed by a 5-byte message consisting only of a maximal length prefix. Since `vec![0; 4 GiB]` either triggers an allocation abort or heavy memory pressure, this is a remote, unauthenticated denial of service against a validator/coordinator during key generation — matching the CVSS 7.5 availability impact of the source CVE.

### Likelihood Explanation
The `read` API is a pure byte parser; reaching it requires only sending malformed DKG message bytes. The trigger needs no valid signature, no participation in a valid set, and no state — just `0xff ff ff ff` in the length position. Allocation abort is deterministic on any host without 4 GiB of headroom, and even well-resourced hosts can be driven into OOM by repeating the message. This is directly analogous to the reference bug: trivially craftable, deterministic crash.

### Recommendation
Mirror the chunked-read approach used in `networks/ethereum/src/machine.rs::Call::read`: cap the accepted length at a documented constant (DKG ciphertexts are bounded in practice by share size × key count), and/or read incrementally so memory committed is proportional to bytes actually received. Reject lengths above the protocol maximum before allocating.

### Proof of Concept
Feed `EncryptedMessage::read` a byte stream containing valid header fields followed by `ff ff ff ff` as the ciphertext length and zero further bytes. The `vec![0; 0xffffffff]` allocation executes before `read_exact` discovers the stream is empty, aborting the process — no actual ciphertext bytes need be sent.

Note on confidence: grep confirmed `vec![0; ...]` and `read_exact` matches in `crypto/dkg/src/lib.rs` in the `EncryptedMessage` region beyond the portion of the file surfaced in the index; if the length there is `u16` rather than `u32`, the worst case degrades to a 64 KiB pre-allocation and this should be downgraded. The sibling pattern (`Vec::with_capacity(usize::from(n))` in `ThresholdKeys::read`, dkg/src/lib.rs:608) is bounded by `u16::MAX` and is not a viable analog. Out-of-scope files (`coordinator/tributary/src/block.rs:92`, `processor/src/plan.rs`) contain unambiguous `u32`-driven `Vec::with_capacity`/`vec![0]` analogs but were excluded per scope rules.
