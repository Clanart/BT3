### Title
Unbounded future oracle timestamp poisons the monotonic freshness gate, permanently freezing price resolution for an asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`oracle-timestamp-fresh` in `v0-4-market.clar` special-cases any oracle timestamp that is greater than the current `stacks-block-time` by forcing `delta` to `u0`, treating it as maximally fresh with no upper bound check [1](#0-0) . That "future" timestamp is then written into the per-feed monotonic `last-update` map whenever it exceeds the previously stored value [2](#0-1) . Because the monotonic check requires `(>= ts prev)`, once a far-future timestamp is recorded, every subsequent legitimate price update (whose real-world publish time is necessarily less than the poisoned future value) fails the `(>= ts prev)` check and the whole call reverts with `ERR-ORACLE-INVARIANT`, exactly mirroring the reported bug class of "too-far-in-the-future timestamp mishandling" but landing on a staleness/monotonic-timestamp gate rather than block validity.

### Finding Description
The relevant code path is:

```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
``` [1](#0-0) 

There is no upper bound on how far `ts` (the oracle's `publish-time`, sourced from Pyth via `resolve-pyth` or DIA via `resolve-dia`) may exceed `stacks-block-time` [3](#0-2) . Any `ts` in the future — even far in the future — collapses `delta` to `0`, which trivially satisfies `(<= delta max-staleness)`.

`price-resolve` then persists `ts` into `last-update` whenever it is newer than the previously stored timestamp:

```clarity
(if (> timestamp last-update-time)
    (map-set last-update key timestamp)
    false)
``` [4](#0-3) 

Once an anomalously future timestamp (whether from a misbehaving relay, clock skew, or a bug on the oracle-provider's own side) is recorded as `last-update-time` for a feed, every future call to `price-resolve` for that feed will fail the monotonic check `(>= ts prev)` in `oracle-timestamp-fresh`, because a legitimate, real-time `ts` will always be less than the poisoned future value stored in `prev`. This means `ERR-ORACLE-INVARIANT` is asserted for all subsequent price resolutions of that asset until real wall-clock time (`stacks-block-time`) catches up with the poisoned future value [5](#0-4) .

This is structurally analogous to the CKB advisory: a too-far-in-the-future timestamp is not bounded/rejected by the validation logic, and the naive handling of "future" data (rather than clamping/rejecting it with a sane tolerance) corrupts subsequent state that other logic depends on (there: peer banning / chain state; here: the monotonic per-feed timestamp gate that every `price-resolve` call for that asset depends on).

### Impact Explanation
Any market operation that requires a fresh price for the affected asset — borrow, withdraw, and crucially liquidation — calls `price-resolve`/`price-multi-resolve` and will revert with `ERR-ORACLE-INVARIANT` once the feed's `last-update` is poisoned [6](#0-5) . This causes a temporary freeze of funds for that asset/market: users cannot borrow against or redeem the affected collateral, and — more importantly — liquidators cannot liquidate undercollateralized positions denominated in that asset until real time advances past the poisoned future timestamp, which is entirely at the discretion of whoever supplied the anomalous timestamp. This matches the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
Triggering the condition only requires one oracle update whose `publish-time` is set far ahead of the current `stacks-block-time` to be relayed into `price-resolve` once — there is no sanity/upper-bound check preventing it, and the effect (poisoning `last-update`) is a single write with no way to correct it except waiting out the clock. Given that the check is entirely internal to Zest's own gating logic (not a third-party price-value bug, but a missing bound on how the timestamp is validated), this is a legitimate defensive gap in the protocol's own freshness gate, independent of whether the upstream oracle acted maliciously or merely glitched.

### Recommendation
Bound the acceptable "future" window in `oracle-timestamp-fresh`: reject (rather than zero out) any `ts` that exceeds `stacks-block-time` by more than a small, explicit tolerance (e.g., a few seconds, similar to the 15-second bound used for Stacks block timestamps), instead of unconditionally treating any future timestamp as delta-zero-fresh. This prevents an anomalous timestamp from ever being written into the monotonic `last-update` map and poisoning future price resolutions.

### Proof of Concept
1. A price update for feed `F` is submitted with `publish-time = stacks-block-time + N` where `N` is very large (weeks/months), whether via a misbehaving relay or oracle-side bug.
2. `oracle-timestamp-fresh` computes `delta = u0` since `ts > stacks-block-time`, so `(<= delta max-staleness)` passes trivially; the monotonic check `(>= ts prev)` also passes since this is presumably the first/newest observed timestamp [1](#0-0) .
3. `price-resolve` stores this poisoned future timestamp into `last-update` for key `{type, ident}` [7](#0-6) .
4. All subsequent calls to `price-resolve` for feed `F` supply a real-world `ts` that is less than the poisoned `prev`, causing `(>= ts prev)` to fail and the call to revert with `ERR-ORACLE-INVARIANT` [8](#0-7) .
5. Every market action needing feed `F`'s price (borrow, withdraw, liquidate) reverts until `stacks-block-time` advances past the poisoned future value.

  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))

        (ident (get ident data))
        (key { type: type, ident: ident })

        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
