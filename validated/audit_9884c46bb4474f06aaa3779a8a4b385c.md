### Title
Path-only repository identity matching lets a swapped/attacker repository silently inherit trust and GitHub-account association from a previously-tracked repository - (File: `app/src/lib/repository-matching.ts`)

### Summary
GitHub Desktop identifies a "known" local repository purely by normalized filesystem path, never by verifying that the on-disk repository's remote/identity still matches what Desktop originally recorded. If the directory contents at a previously-trusted path are replaced (e.g., the user removes the old folder and clones a different, attacker-supplied repository into the exact same path, or opens it via CLI/deep link with that path), Desktop treats it as the *same* repository record and carries over: (a) the `safe.directory` git-ownership trust exception previously granted for that path, and (b) the persisted `gitHubRepository`/account association used to select the authenticated account, branch-protection state, and PR/API context. This mirrors the reported bug class: an identity/privilege (root role / trust+association) that should be scoped to a specific entity (an org / a specific git remote) is instead retained because the lookup key is reused (a safe address / a filesystem path) rather than the entity's real identity.

### Finding Description
`matchExistingRepository` matches tracked repositories solely by normalized path equality, with no check of the repository's actual remote URL or identity: [1](#0-0) 

This function (and equivalent inline path-only lookups) is the authority used to decide "is this directory already a repository we know" in every entry point where a user points Desktop at a path:
- Bulk/drag-and-drop add: `app-store.ts` `_addRepositories` returns the *existing* tracked `Repository` object without re-validating remote identity whenever `matchExistingRepository` finds a path match: [2](#0-1) 
- Drag-and-drop handler in the renderer: [3](#0-2) 
- CLI `open-repository` action / `x-github-client://` style local-open flows: [4](#0-3) 
- `openOrAddRepository`, used for "Open in Desktop" flows, matches by raw path equality as well: [5](#0-4) 

Separately, Git ownership trust ("safe.directory") is also keyed by path alone via `addSafeDirectory`, and once added it is never revoked or re-validated against the specific repository content that earned the trust: [6](#0-5) 

The UI trust flows (`AddExistingRepository.onTrustDirectory`, `MissingRepository.onTrustDirectory`) call `addSafeDirectory(path)` and then just re-check `getRepositoryType`, again keyed only by path, not by verifying remote identity continuity: [7](#0-6) [8](#0-7) 

Once a `Repository` record is matched/reused, downstream account selection (`getAccountForRepository`) derives the authenticated GitHub account strictly from the *stored* `gitHubRepository.endpoint`/id on that record — not from re-deriving it from the actual remote currently on disk: [9](#0-8) 

The broken invariant is identical in shape to the Palmera finding: a privileged/trusted state (`ROOT_SAFE` role / `safe.directory` exception + `gitHubRepository` association) is bound to a reusable key (a Safe address / a filesystem path) rather than to the entity that actually earned it (the org / the specific git remote+commit history). When the underlying entity changes but the key is reused, the stale privileged state is applied to the new entity without re-validation.

### Impact Explanation
If an attacker can get a user to open, clone-again, or drag-and-drop a malicious repository into a path Desktop previously trusted/tracked (a plausible, low-friction social/technical vector — e.g. instructing a user to "re-clone into the same folder" after deleting it, or crafting an "Open in Desktop"/CLI `open-repository` invocation with that path), Desktop will:
- Skip the "this directory is owned by another user / potentially unsafe" warning, because the `safe.directory` git-level exception already exists for that path — even though the content is now a completely different, attacker-controlled repository, enabling any git config-driven or hook-driven behavior Desktop relies on git trust to gate.
- Silently reuse the old `gitHubRepository`/account binding (owner, endpoint, branch-protection state, PR context) for the new attacker content, causing the UI to display and act on the wrong repository identity, and potentially select the wrong authenticated account/token context for the "current repository" operations that key off `getAccountForRepository`.

This can lead to a user unknowingly interacting with (and pushing/committing to, or trusting hooks/executables from) an attacker-substituted repository under the guise of a previously-trusted one, corrupting what the user believes they are committing/pushing to and bypassing the ownership-trust prompt that exists specifically to protect against this class of attack.

### Likelihood Explanation
Moderate. It requires the user to take an action that re-associates a path already known to Desktop with new repository content (delete+reclone into the same folder, "Clone Again" on a missing repo, or open a manipulated local path via CLI/deep-link) — no local/admin access or pre-existing malware is required, only that the attacker controls the repository/URL the user is directed to fetch into that path. The path-based matching and the path-based `safe.directory` exception are unconditional, always-on code paths (`matchExistingRepository`, `addSafeDirectory`), so once the precondition path-reuse occurs, the vulnerable behavior triggers deterministically.

### Recommendation
- Do not treat a path match alone as sufficient to reuse a tracked `Repository`'s trust/GitHub association. When re-adding/re-opening a path, re-derive and compare the current remote URL (and/or `.git` object identity) against the stored `gitHubRepository`'s clone/html URL, and clear the stale association (or re-prompt) on mismatch, similar to how `urlMatchesRemote`/`updateRemoteUrl` already exist for a related purpose. [10](#0-9) 
- Scope `safe.directory` trust decisions to more than the path: e.g., record and check a fingerprint (initial commit hash / remote URL) alongside the path, and re-prompt if content changes.
- Re-run `getRepositoryType`/ownership checks unconditionally (not just on first open) before applying account/token context for the "current" operation.

### Proof of Concept
1. User adds Repository A (owner: `victim/private-repo`) at path `/Users/alice/work/project`; Desktop stores it with `gitHubRepository` pointing to `victim/private-repo`, and (if applicable) grants a `safe.directory` exception for that path — [6](#0-5) .
2. User deletes the local folder (or it goes "missing").
3. Attacker convinces the user to run `git clone https://github.com/attacker/evil-repo /Users/alice/work/project` (e.g., via instructions, a script, or a crafted `x-github-client://openLocalRepo?...` / CLI `open-repository <path>` action) — [4](#0-3) .
4. User reopens Desktop or drags the folder in; `matchExistingRepository`/path-equality lookup finds the old tracked record and Desktop selects it directly, without re-checking that the remote now points at `attacker/evil-repo` — [2](#0-1) .
5. Desktop continues to use the old `gitHubRepository` association/account context (`getAccountForRepository`) and, if the path was previously marked `safe.directory`, skips the unsafe-ownership warning that would normally appear for a repo now owned/controlled by a different party — [9](#0-8) [8](#0-7) .

export function matchExistingRepository<T extends { readonly path: string }>(
  repos: ReadonlyArray<T>,
  path: string
): T | undefined {
  // Windows is guaranteed to be case-insensitive so we can be a bit less strict
  const normalize = __WIN32__
    ? (p: string) => Path.normalize(p).toLowerCase()
    : (p: string) => Path.normalize(p)

  const needle = normalize(path)
  return repos.find(r => normalize(r.path) === needle)
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

/**
 * Adds a path to the `safe.directories` configuration variable if it's not
 * already present. Adding a path to `safe.directory` will cause Git to ignore
 * if the path is owner by a different user than the current.
 */
export async function addSafeDirectory(path: string) {
  // UNC-paths on Windows need to be prefixed with `%(prefix)/`, see
  // https://github.com/git-for-windows/git/commit/e394a16023cbb62784e380f70ad8a833fb960d68
  if (__WIN32__ && path[0] === '/') {
    path = `%(prefix)/${path}`
  }

  await addGlobalConfigValueIfMissing('safe.directory', path)

/** Get the authenticated account for the repository. */
export function getAccountForRepository(
  accounts: ReadonlyArray<Account>,
  repository: Repository
): Account | null {
  const gitHubRepository = repository.gitHubRepository
  if (!gitHubRepository) {
    return null
  }

  return getAccountForEndpoint(accounts, gitHubRepository.endpoint)
}
