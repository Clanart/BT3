### Title
Deterministic preprocess reuse enables secret key share recovery via repeated signing under one cached seed (privilege escalation from message submitter to validator key) - (File: crypto/frost/src/sign.rs)

### Summary
The external report describes a local privilege escalation: a low-privilege user attaches input to a higher-privilege component and causes it to perform privileged actions. The Serai analog is a deterministic-nonce reuse flaw in `crypto/frost`'s preprocess caching, exercised in production by the coordinator's `SigningProtocol`. `AlgorithmSignMachine::from_cache` rebuilds the exact same nonces from a stored seed, and `DkgConfirmer` caches that seed per `(b"DkgConfirmer", attempt)` context, re-deciding it on every `share`/`complete` invocation. A party who can cause `share_internal` to execute multiple times under one context with differing inputs obtains multiple signature shares over identical `(d, e)` nonce pairs, which reduces to linear equations revealing the signer's secret key share — escalating an unprivileged message submitter into possession of a validator's root-of-trust key material.

### Finding Description
`seeded_preprocess` in crypto/frost/src/sign.rs:121-144 deterministically derives all nonces and commitments from `ChaCha20Rng::from_seed(*seed.0)`, where `seed` is the `CachedPreprocess`. The doc comments in crypto/frost/src/sign.rs:83-92 and spec/cryptography/FROST.md:51-62 explicitly warn that reusing a preprocess "will enable third-party recovery of your private key share."

In coordinator/src/tributary/signing_protocol.rs, `preprocess_internal` (lines 100-148) stores the seed in `CachedPreprocesses` keyed only by `self.context` — for `DkgConfirmer`, `(b"DkgConfirmer", self.attempt)` (line 275). Every call to `share_internal` (lines 150-181) calls `preprocess_internal` again and rebuilds the identical nonce pair via `AlgorithmSignMachine::from_cache`. `complete` (lines 312-327) invokes `share_internal` a second time on the same context. Crucially, `share_internal` signs whatever `msg` and `preprocesses` map it is handed; `DkgConfirmer::share_internal` builds `msg` from the caller-supplied `key_pair` (lines 288-301), and the preprocess map is supplied by the caller (arriving from on-chain messages submitted by any participant).

The file's own header (lines 25-48) acknowledges the hazard: re-execution is "explicitly unsafe" unless "the received nonce commitments (or the message to be signed)" are identical, and safety rests entirely on an assumed-BFT ordering plus a "TODO" check that a rebuilt service's commitments match what was published (lines 50-54). That check is unimplemented, and nothing in `preprocess_internal` or `share_internal` enforces that repeated invocations under one context are invoked on identical `(preprocesses, msg)` — there is no persisted hash of the signed inputs and no guard rejecting a second, distinct signing.

Each produced share has the form `s = d + e·ρ + λ·x·c` (sign.rs:386-398 applies `actual = base + actual·ρ`; `sign_share` adds `λ·x·c`). Across `k` reuses of the same seed with attacker-influenced `(preprocesses, msg)`, `ρ` and `c` vary while `d`, `e`, and the secret share `x` are fixed, giving `k` linear equations in 3 unknowns — `k ≥ 3` distinct invocations recovers `x` outright.

### Impact Explanation
Recovery of `x` yields the validator's MuSig secret key share for the validator-set key — the root of trust used for on-chain DKG confirmation (`set_keys_message`). An attacker able to trigger repeated `share`/`complete` executions under one attempt context (e.g., via multiple distinct `key_pair` values or differing preprocess sets being ordered for the same attempt, or after a partial process rebuild where prior input identity isn't verified — the exact gap flagged by the TODO) escalates from submitting public inputs to extracting validator key material, then unilaterally participating in validator-set signing. This is the direct analog of the reported escalation: untrusted local input driving a higher-privilege component into leaking its elevated authority.

### Likelihood Explanation
Likelihood is conditional rather than trivial: exploitation requires `share_internal`/`complete` to run more than once per context on non-identical inputs. The code contains no enforcement preventing that — the only safeguards are the assumed-BFT ordering and two explicitly acknowledged TODO checks (lines 50-54) verifying that re-derived commitments match previously published ones. Partial rebuilds, retry paths that re-execute `complete` after `share` already emitted a share, or any ordering edge that presents a different `key_pair`/`preprocesses` set under the same `attempt` all satisfy the trigger. Because the seed is deliberately persisted in the DB to survive restarts, restarts do not reset the nonce — they preserve the vulnerable condition.

### Recommendation
Persist, alongside `CachedPreprocesses`, a commitment to the exact `(sorted participant set, serialized preprocesses, msg)` the seed was first used to sign with, and have `share_internal`/`complete_internal` abort if a subsequent invocation under the same context observes different bytes. Implement the on-chain check noted in the TODO: before publishing a share, verify the commitments derived from the cached seed match this validator's previously published preprocess for that context. Alternatively, key the cached preprocess by a hash of the full signing inputs rather than only `(tag, attempt)`, so any change in inputs deterministically yields fresh nonces.
