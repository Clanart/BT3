### Title
`GeneratorPromotion::complete` panics on a missing participant index instead of returning an error, allowing a single malicious proof submission to abort key promotion - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates the untrusted `proofs: HashMap<Participant, GeneratorProof<C1>>` only by its length (`== n - 1`) and by an upper bound on each key (`<= n`). It then iterates the contiguous range `1 ..= n` and unconditionally `unwrap()`s `proofs.get(&i)`. This mirrors the Perennial bug: the code assumes that if the set has the right size and bounds, every intermediate index in the range is present. If a submitted proof is filed under the completer's own index `params.i()` (or two senders' proofs are keyed under the same `Participant`), the map still has `n - 1` entries all `<= n`, passes both checks, yet some `j != i` is absent — causing `proofs.get(&j).unwrap()` to panic.

### Finding Description
In `crypto/dkg/promote/src/lib.rs:120-156`, `complete` performs:

```rust
if proofs.len() != (usize::from(params.n()) - 1) { ... }        // line 125
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() { ... }                          // lines 132-136
}
...
for i in 1 ..= params.n() {
  let i = Participant::new(i).unwrap();
  if i == params.i() { continue; }
  let proof = proofs.get(&i).unwrap();                          // line 146 — panics
```

The checks verify cardinality and an upper bound, but never verify that the key set is exactly `{1..=n} \ {params.i()}`. Since `HashMap` deduplicates keys, a map containing `params.i()` as a key (plus n−2 distinct keys ≤ n) satisfies `len == n - 1` while omitting one expected participant. The same applies if an integrator keys proofs by a sender-claimed index and a peer submits a proof under a colliding/incorrect index.

Contrast with `crypto/dkg/pedpop/src/lib.rs:305-309`, where `validate_map` is invoked against `all_participant_indexes()` before iteration — the promotion path lacks the equivalent validation.

`GeneratorProof::read` (lines 72-77) parses attacker-controlled bytes, and `complete` is the API that consumes those proofs, so this is reachable by any party able to submit a promotion proof message — exactly the "untrusted bytes fed to a `complete` API" reachability class.

### Impact Explanation
A single participant (or mislabeled message) can panic `complete`, aborting the generator-promotion protocol for the victim. In a release build without `panic = "abort"` this unwinds through the caller; in deployments calling this on a task/thread it kills that execution context. The promotion cannot be completed in that session, denying the key-update operation for the whole group until restarted with the faulty input excluded — a deterministic, input-triggered DoS. Because the panic occurs before any error is returned, blame assignment/retries in calling code also panic rather than receiving a `PromotionError`.

### Likelihood Explanation
Triggering requires only that the `proofs` map lack one index in `1..=n` while still having `n-1` entries all `≤ n` — achievable by a peer submitting a proof keyed under the victim's own `Participant` index, or under an index already used by another participant. No valid proof needs to be forged; the panic precedes proof verification. Any deployment that keys proofs by a claimed/derived index rather than a strictly authenticated one is exposed.

### Recommendation
Replace the blind `unwrap` with an explicit membership check, e.g.:

```rust
for i in proofs.keys().copied() {
  if u16::from(i) > params.n() || i == params.i() {
    Err(PromotionError::InvalidParticipant { n: params.n(), participant: i })?;
  }
}
```

and/or fetch with error propagation:

```rust
let Some(proof) = proofs.get(&i) else {
  Err(PromotionError::IncorrectAmountOfParticipants {
    t: params.n(), n: params.n(), amount: proofs.len() + 1,
  })?
};
```

Equivalently, adopt the `validate_map`-style check used by PedPoP to assert the key set equals `all_participant_indexes()` minus `params.i()`.

// n = 3, we are participant 1. proofs must have keys {2, 3}.
