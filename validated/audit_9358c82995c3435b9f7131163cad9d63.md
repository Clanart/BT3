### Title
Unrestricted arbitrary-call dispatch and full-balance sweep in `IntentGatewayV2.placeOrder` predispatch path can drain shared `CallDispatcher` funds - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` lets any caller supply arbitrary `order.predispatch.call` bytes that get executed by the shared `CallDispatcher` contract with **no whitelist on call targets**, exactly the pattern flagged in the Magnetar report ("taking all addresses as user inputs without verifying them"). After the predispatch call executes, the gateway sweeps tokens out of the dispatcher using the dispatcher's **full current balance** (`IERC20(token).balanceOf(dispatcher)`), not a delta scoped to this specific order's deposit.

### Finding Description
In `placeOrder`, when `order.predispatch.call.length > 0`: [1](#0-0) 

the gateway transfers the caller's declared `predispatch.assets` to `dispatcher`, then executes fully attacker-controlled calldata via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`. There is no validation of the `to` addresses or selectors encoded inside that calldata — the same missing-whitelist pattern as Magnetar's `yieldbox`/`market` parameters.

Immediately after, the gateway sweeps tokens from the dispatcher using the dispatcher's live balance rather than a per-order delta: [2](#0-1) 

```solidity
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({
    to: token,
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
```

Because `dispatcher` is a single shared contract address stored once in `_params.dispatcher` and used by every caller of `placeOrder`, and because the sweep transfers the *entire* balance of `token` held by the dispatcher (not just what this order deposited), any token balance the dispatcher happens to be holding at sweep time — e.g., dust, a partially-processed deposit from another in-flight order, or leftover approval/transfer effects from the attacker's own crafted `predispatch.call` acting on tokens the dispatcher already held — gets pulled entirely into `address(this)` for the attacker's order. The attacker's `predispatch.call` is unconstrained: it can target any token contract, call `approve`/`transferFrom` on any address the dispatcher has previously interacted with, or otherwise manipulate balances before the balance-based sweep runs.

### Impact Explanation
If the `CallDispatcher` retains any token balance across calls (dust, partially swept fee-on-transfer remainders, or concurrent order state), an attacker can use the unrestricted `predispatch.call` to redirect approvals or balances belonging to other orders/users into their own order's sweep, since the sweep step reads `balanceOf(dispatcher)` rather than a per-order accounted amount. This matches the Hyperbridge impact gate criteria: "unauthorized transaction or execution," "transaction manipulation," and potential "stealing or loss of funds" from a bridge-adjacent escrow contract, achievable by an unprivileged user with no relayer/prover/admin compromise required.

### Likelihood Explanation
Moderate-to-low confidence: the exploitability depends on whether `CallDispatcher` ever holds residual balance between/during transactions (this requires reading `evm/src/utils/CallDispatcher.sol`, which I was not able to complete before the iteration limit). If `dispatch()` is strictly atomic per-call and the dispatcher never retains balance outside a single `placeOrder` invocation, the practical drain surface shrinks to same-transaction dust only (fee-on-transfer remainders, rounding). The core design flaw — fully unwhitelisted call targets combined with a balance-based (not delta-based) sweep — is confirmed directly from `IntentGatewayV2.sol`.

### Recommendation
1. Track the exact amount the dispatcher receives per order (delta before/after the deposit transfer) rather than sweeping `balanceOf(dispatcher)` in full.
2. Restrict `CallDispatcher.dispatch` call targets to a whitelist of approved contracts (tokens, routers), mirroring the `cluster.isWhitelisted` pattern the original Magnetar report recommended.
3. Ensure `CallDispatcher` never carries balance across transaction boundaries, and add reentrancy/order-isolation guards so one order's predispatch execution cannot observe or act on another order's in-flight token transfers.

### Proof of Concept
Conceptual (not fully verified against `CallDispatcher.sol` internals due to tool-call limit):
1. Attacker calls `placeOrder` with `order.predispatch.call` encoding a `Call[]` that targets an arbitrary token contract the dispatcher currently holds a balance of (from dust/rounding of a concurrent or prior order) and calls `approve(attacker, type(uint256).max)` or otherwise manipulates it.
2. The gateway then executes the balance-based sweep `IERC20(token).balanceOf(dispatcher)` at line 243 in `evm/src/apps/IntentGatewayV2.sol`, pulling the dispatcher's entire balance — including any amount not belonging to the attacker's own deposit — into the attacker's escrowed order.
3. Because the sweep is balance-based rather than delta-based, and `predispatch.call` targets are unvalidated, the attacker's order commitment ends up crediting more input than they actually deposited, at another order's/deposit's expense. [3](#0-2)
