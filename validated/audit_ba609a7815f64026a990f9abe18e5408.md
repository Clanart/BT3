### Title
SSRF via unauthenticated on-chain DataLayer mirror URLs consumed without validation - (File: chia/data_layer/data_layer_wallet.py, chia/data_layer/data_layer.py, chia/data_layer/download_data.py)

### Summary
Chia's DataLayer mirror mechanism lets any chain participant register a URL for any DataLayer store by spending a coin to the "mirror" puzzle. That URL is decoded from the coin's puzzle reveal/solution with no ownership check, propagated into the local `DataStore`'s server list, and later dereferenced by the DataLayer service's background sync loop via outbound `aiohttp` requests (HTTP GET for delta files, HTTP POST to "downloader" plugins) with no destination validation. This is the same bug class as CVE-2019-1003027 (SSRF from a missing permission/authorization check before an outbound request is made using attacker-influenced input).

### Finding Description
When a DataLayer wallet observes a coin sent to the mirror puzzle hash, it decodes the launcher_id and URL list straight from the parent coin's spend data: [1](#0-0) 

There is no check that the spender owns/controls the target `launcher_id` store, nor any validation of the URL contents (scheme, host, port) — any wallet on the network can create such a coin for any store id and any URL, as documented in the module notes: "Do not treat mirror URLs, plugins, or static file names as trusted data sources," and "Plugin and mirror URLs are external trust inputs." [2](#0-1) [3](#0-2) 

These attacker-controlled mirror URLs are pulled into the DataLayer service's per-store server list unconditionally during the periodic subscription loop: [4](#0-3) [5](#0-4) 

`fetch_and_validate()` then randomly selects one of these server URLs and issues outbound requests to it (`get_downloader()` POSTs to `<url>/handle_download`, and `insert_from_delta_file()`/`download_file()` GETs `<url>/<filename>`): [6](#0-5) [7](#0-6) [8](#0-7) 

None of these call sites restrict the URL to public/allowed hosts (no blocklist for loopback, link-local metadata addresses, or internal RPC ports), and the node making the request has no way to know the URL came from an untrusted third party rather than the store owner.

### Impact Explanation
Any wallet user who can send a small-value transaction can force every DataLayer node that later subscribes to (or already owns/tracks) a given `store_id` to make an outbound HTTP GET/POST to an attacker-chosen host and port, matching the "S:U/C:L" impact profile of the referenced CVE: the DataLayer operator learns/gets exposed to connection results (timeouts vs. connection resets vs. HTTP status codes), and the request can be aimed at internal-only services (localhost RPC ports, cloud metadata endpoints such as `169.254.169.254`, or other machines on the operator's private network) that are normally unreachable from the public internet. Because the node automatically performs this request during its background `periodically_manage_data()` loop, no interactive action is required from the victim operator beyond having previously subscribed to (or owned) the targeted store — this is an unattended, repeated SSRF primitive.

### Likelihood Explanation
Likelihood is Medium-High for exposure but capped at Medium-severity impact: creating a mirror coin only requires a normal wallet spend to a well-known puzzle (no special permission), and DataLayer mirrors are a documented, expected user-facing feature (adding mirrors for community redundancy), so operators who track/subscribe to third-party stores are directly exposed. The blast radius is limited to information leakage via error/response codes and internal network reachability probing (no direct fund theft, and downloads are size- and content-validated against the wallet-advertised Merkle root before being trusted as data), consistent with the CVSS vector `C:L/I:N/A:N` in the referenced advisory.

### Recommendation
- Before dereferencing a mirror/subscription URL, validate that it is not pointing at loopback, link-local (`169.254.0.0/16`), private RFC1918, or other operator-internal ranges unless explicitly allow-listed by configuration (mirroring common SSRF mitigations).
- Consider requiring explicit operator opt-in (e.g. only follow mirror URLs the operator has already trusted/allow-listed) rather than automatically merging every on-chain-advertised mirror URL for a store into the active fetch list.
- Apply the same validation to plugin `downloader`/`uploader` URLs consumed in `get_downloader()`/`get_uploaders()`/`check_plugins()`.

### Proof of Concept
1. Attacker spends a coin to the `create_mirror_puzzle()` puzzle hash with `launcher_id` set to any store id (including a store the attacker does not own) and `urls=["http://169.254.169.254/latest/meta-data/"]` (or `http://<victim-internal-host>:<port>/`).
2. Any DataLayer node that already tracks/owns/subscribes to that `store_id` observes the coin in `coin_added()`, decodes the URL via `get_mirror_info()`, and stores it as a `Mirror` with no ownership check. [1](#0-0) 
3. On the next `periodically_manage_data()` cycle, `update_subscription()` calls `update_subscriptions_from_wallet()` which copies the attacker's URL into the local server list, then `fetch_and_validate()`/`get_downloader()` issue an outbound HTTP request to that URL. [5](#0-4) 
4. The victim operator's DataLayer service log records success/failure/timeout of the connection to the attacker-chosen internal address, confirming SSRF (the attacker can distinguish open vs. closed/filtered ports, and can chain to more impactful internal endpoints if any are reachable and respond to the DataLayer's GET/POST shape).

Note: I could not fully trace `dl_new_mirror`'s RPC-side authorization logic (`chia/wallet/wallet_rpc_api.py`) within the available index to confirm whether the wallet RPC itself restricts which `launcher_id` a caller may target when creating a mirror; this analysis is based on the on-chain coin-observation path (`coin_added`) which processes any mirror-puzzle coin regardless of who created it, since the puzzle itself is spendable by anyone with funds to the mirror puzzle hash.

    async def get_downloader(self, store_id: bytes32, url: str) -> PluginRemote | None:
        request_json = {"store_id": store_id.hex(), "url": url}
        for d in self.downloaders:
            async with aiohttp.ClientSession() as session:
                try:
                    async with session.post(
                        d.url + "/handle_download",
                        json=request_json,
                        headers=d.headers,
                        timeout=self.client_timeout,
                    ) as response:
                        res_json = await response.json()
                        if res_json["handle_download"]:
                            return d
                except Exception as e:
                    self.log.error(f"get_downloader could not get response: {type(e).__name__}: {e}")
        return None

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
