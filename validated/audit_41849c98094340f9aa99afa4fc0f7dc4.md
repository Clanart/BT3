### Title
CPI signer-seed PDA derivation via `translate_signers` bypasses `create_program_address_units` metering, giving attackers free SHA256 work per invoke_signed call - ([File: program-runtime/src/cpi.rs])

### Summary
`translate_signers` in `program-runtime/src/cpi.rs` calls `Pubkey::create_program_address` for every signer-seeds array supplied to `invoke_signed`, up to `MAX_SIGNERS` arrays each with up to `MAX_SEEDS` seeds of `MAX_SEED_LEN` bytes, but never consumes any compute units for this work. By contrast, the equivalent direct syscall `SyscallCreateProgramAddress` explicitly charges `create_program_address_units` before doing the same `Pubkey::create_program_address` call. This is a real metering desync where the CPI signer-derivation path is entirely unpriced rather than merely flat-priced.

### Finding Description
`translate_signers` (`program-runtime/src/cpi.rs:631-674`) is the function invoked during `invoke_signed` processing to convert the caller-supplied `signer_seeds` VM slices into `Pubkey`s via `Pubkey::create_program_address(&seeds_bytes, program_id)` [1](#0-0) . It bounds `signers_seeds.len()` to `MAX_SIGNERS` and each seed list to `MAX_SEEDS` [2](#0-1) , so an attacker's sBPF program can legally supply the maximum permitted seed count/length on every CPI in a transaction. Nowhere in this function (nor is any compute-meter charge visible in `cpi.rs`'s callers of `translate_signers`) is `invoke_context.compute_meter.consume_checked(create_program_address_units)` invoked before performing the SHA256-based derivation.

Compare this to the standalone syscall path: `SyscallCreateProgramAddress::rust` explicitly consumes `create_program_address_units` before calling `Pubkey::create_program_address` [3](#0-2) , and `SyscallTryFindProgramAddress::rust` charges the same cost per bump-seed attempt [4](#0-3) . The intent of the cost model is clearly that every `create_program_address` invocation costs `create_program_address_units`, but the CPI signer-verification code path in `cpi.rs` performs this same expensive operation for free.

The invoke path's flat `invoke_units` charge is a per-CPI base cost [5](#0-4)  and is not designed to account for or scale with the number/size of signer seed arrays being hashed; it exists independent of this signer-derivation cost.

Privilege monotonicity is not affected: `Pubkey::create_program_address` is a deterministic one-way hash-based derivation, and a mismatched seed set cannot forge a signer for an address the caller does not already legitimately derive, as confirmed by existing tests (`test_native_invoke_signed_with_valid_pda_signer`, `test_native_invoke_signed_with_invalid_seeds` in `invoke_context.rs`) [6](#0-5) . So the exploitable issue is purely the compute-cost desync, not a privilege-escalation bug.

### Impact Explanation
An unprivileged attacker can deploy an sBPF program that repeatedly calls `invoke_signed` with `MAX_SIGNERS` (up to the cap enforced at `cpi.rs:646`) signer-seed arrays, each containing `MAX_SEEDS` seeds of near-`MAX_SEED_LEN` bytes, causing the runtime to perform substantial real SHA256 work in `Pubkey::create_program_address` per CPI call while charging zero compute units for that specific work (only the flat `invoke_units` CPI base cost is charged). This is a materially underpriced/unpriced compute primitive: transactions can consume disproportionately more wall-clock validator CPU (SHA256 over near-max seed material, repeated per CPI in a loop) than their compute-unit budget reflects, falling under the "materially underpriced compute" bounty category.

### Likelihood Explanation
This requires no special privileges — any user can deploy and invoke an sBPF program that calls `invoke_signed` with attacker-chosen seed arrays at or near the maximum sizes, and the loop over CPIs within a single transaction/instruction is fully attacker controlled up to `MAX_INSTRUCTION_TRACE_LENGTH` and CU-limit constraints for other charged operations (which are unaffected here since this specific work is unpriced). It is deterministic and trivially repeatable.

### Recommendation
Charge `create_program_address_units` (or an equivalent scaled cost based on seed count/length) inside `translate_signers` for each `Pubkey::create_program_address` call it performs, mirroring the charge already applied in `SyscallCreateProgramAddress`/`SyscallTryFindProgramAddress`, before or as part of computing `seeds_bytes` and invoking `create_program_address`.
