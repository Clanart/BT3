## Summary

The external report describes losing access to escrowed/locked funds when an owner swaps a token address without accounting for what's still outstanding under the old token. Hyperbridge's own `EvmHost.updateHostParamsInternal` already carries an explicit fix for exactly this class of bug — it refuses to swap `feeToken` while the old fee token still has a balance sitting in the host [1](#0-0) , with a dedicated `CannotChangeFeeToken` error [2](#0-1) , confirmed by a regression test (`testSweepFeeTokenBeforeUpdate`) [3](#0-2) .

Searching the rest of the codebase for the same "remap the token/contract identity without accounting for what's still outstanding under the old identity" pattern, the one places lacking an equivalent guard is `pallet-hyper-fungible-token`'s `update_token` extrinsic.

### Title
`update_token` remaps an EVM token-contract binding without a guard for in-flight cross-chain messages, stranding bridged funds - ([File: modules/pallets/hyper-fungible-token/src/lib.rs])

### Finding Description
`pallet-hyper-fungible-token` maintains two mappings that bind a local `AssetId` to a specific EVM contract address per chain: `TokenContracts` (asset → contract, used as `to` on outgoing dispatches) and `ContractToAsset` (contract → asset, used by `on_accept` to resolve inbound messages) [4](#0-3) .

`update_token` lets `CreateOrigin` change the contract address bound to an asset on a chain. When doing so it deletes the old `ContractToAsset` entry and inserts a new one pointing at the new contract, with no check for whether any cross-chain message is still in flight from the old contract: [5](#0-4) 

This is structurally identical to the "replacing the stake token without considering the previous token's locked balance" bug: an inbound ISMP `Send` message dispatched by the *old* EVM contract (tokens already locked/burned on the EVM side) that has not yet been delivered/processed on Hyperbridge when `update_token` runs will fail to resolve in `on_accept`, because `ContractToAsset::<T>::get(chain, old_contract)` no longer exists — the pallet's inbound routing depends entirely on this reverse map (`README.md` confirms: *"on_accept — receives Send messages... Maps the source contract back to a local asset via ContractToAsset"*) [6](#0-5) . Once the mapping is gone, the pallet's `UnregisteredAsset` error path is the only outcome for that in-flight message, even though the corresponding tokens are already locked/burned on the EVM side.

Unlike `EvmHost.updateHostParamsInternal`, which checks `IERC20(oldFeeToken).balanceOf(address(this)) != 0` before allowing the swap and reverts with `CannotChangeFeeToken` [1](#0-0) , `update_token` has no equivalent check against outstanding/in-flight state for the asset being remapped.

### Impact Explanation
Users who initiated a transfer through the old contract address before governance ran `update_token` have their tokens locked/burned on the EVM chain, but the corresponding credit on Hyperbridge cannot be processed because the reverse-lookup entry needed by `on_accept` has been deleted. This matches the accepted impact classes of "loss of funds" and "logic attacks" — funds move exactly once out of the user's control but never land at the intended beneficiary, and there is no documented recovery path (unlike `BandwidthManager`'s `Withdraw`, which explicitly names the token so stale balances from a fee-token swap remain recoverable) [7](#0-6) .

### Likelihood Explanation
This requires `CreateOrigin` (a privileged/governance action) to call `update_token` while a `send()`-originated message from the previously-registered contract is still in flight — the same operational scenario the original report flagged: a routine, non-malicious contract migration performed without awareness of in-flight state. Given multi-chain deployments and normal relayer latency, an update landing between an EVM `send` and its delivery to Hyperbridge is a realistic, non-adversarial timing window, not one requiring a malicious actor.

### Recommendation
Before removing/overwriting a `ContractToAsset` (and `TokenContracts`) entry in `update_token`, either (a) require the old contract to have zero outstanding/pending dispatch commitments for that asset/chain (mirroring `EvmHost`'s balance check before `CannotChangeFeeToken`), or (b) keep old `ContractToAsset` bindings alive (multi-map) for a grace/challenge period so in-flight messages from a since-replaced contract can still resolve to the correct asset, only removing them once no request from that contract can still be pending.

### Proof of Concept
1. Governance registers asset `X` with EVM contract `C_old` on chain `Evm(1)` via `register_token`, populating `TokenContracts[Evm(1), X] = C_old` and `ContractToAsset[Evm(1), C_old] = X` [8](#0-7) .
2. A user on chain `Evm(1)` triggers `C_old`'s `send`, which locks/burns the user's tokens on the EVM side and dispatches an ISMP `Send` POST request destined for the pallet, still in flight (not yet processed by relayer/Hyperbridge).
3. Governance calls `update_token` to migrate asset `X` to a new contract `C_new` on `Evm(1)` (e.g., a routine contract upgrade), which executes `ContractToAsset::<T>::remove(Evm(1), C_old)` and inserts the new mapping [9](#0-8) .
4. The relayer finally delivers the in-flight message originating from `C_old`; `on_accept` (per `impls.rs`/module routing, which resolves the sender via `ContractToAsset`) can no longer find asset `X` for `(Evm(1), C_old)`, so the credit fails with `UnregisteredAsset`.
5. The user's tokens remain locked/burned on the EVM chain with no corresponding credit on Hyperbridge, and no documented recovery mechanism exists in this pallet (unlike `BandwidthManager.Withdraw`, which explicitly supports draining stale balances of a prior token).

Note: I was not able to fully inspect `modules/pallets/hyper-fungible-token/src/module.rs` (the `IsmpModule` implementation containing the actual `on_accept`/`on_timeout` bodies) within the available tool budget to confirm the exact error path and whether any fallback exists; the `README.md` and `impls.rs`/`lib.rs` evidence strongly indicate `ContractToAsset` is the sole resolution mechanism, but a Devin session with full file access should verify `module.rs` directly before treating this as fully confirmed.
