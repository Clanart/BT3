### Title
Schnorr aggregate-signature verifier omits the nonces (`Rs`) from the weight transcript, allowing universal forgery - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` implements the half-aggregation scheme of eprint 2021/350. The random weights `z_i` used to combine the per-signature statements are derived from a transcript that commits only to the verifier-supplied challenges — not to the attacker-controlled nonce points `R_i`. Because the weights are predictable before `Rs` are chosen, a signer can solve for a final `R_n` that makes the multiexp sum to identity, forging an aggregate signature for arbitrary public keys and messages. All bytes are supplied via `SchnorrAggregate::read`, making this reachable purely from untrusted input.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `verify` builds the weight transcript as:

```rust
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
for (_, challenge) in keys_and_challenges {
  digest.append_message(b"challenge", challenge.to_repr());
}
let z_i = weight(&mut digest); // per index
```

The verification equation checked is `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G = 0` via `multiexp_vartime` (lines 127–145). `self.Rs` come from the signature under verification (read via `C::read_G` in `SchnorrAggregate::read`, lines 77–88), yet are never appended to `digest`. The `z_i` are therefore a deterministic public function of `dst` and the challenges alone.

Per 2021/350, the weight for each signature must be bound to that signature's nonce (and key/message); otherwise the linearity of the equation lets the signer choose one nonce to cancel the entire sum. This is a direct violation of the scheme's security requirement — an incorrect verifier formula.

### Impact Explanation
Any verifier accepting `SchnorrAggregate` proofs for aggregated Schnorr signatures can be presented a forgery: an aggregate that "proves" `n` parties each signed their respective messages, produced by an unprivileged party knowing none of the private keys. This defeats the non-repudiation/compactness purpose of half-aggregation for any downstream consumer (e.g., batched transaction or certificate verification built on this API).

### Likelihood Explanation
Trivially exploitable by anyone able to submit a `SchnorrAggregate` to a verifier. The weights are fully deterministic and computable offline; the forgery requires only solving one linear equation in the group — one inversion and a handful of multiplications. No secret knowledge, collusion, or special position is needed; the attacker just needs their forged bytes passed to `read` then `verify`.

### Recommendation
Bind every component of each aggregated signature into the weight derivation — at minimum, append each `R_i` (and ideally each public key `A_i`) to `digest` before or interleaved with the per-index `weight()` calls, matching the `z_i = H(R_i, A_i, m_i, …)` prescription of eprint 2021/350. Alternatively, derive `z_i` per-signature rather than a shared sequential stream.

### Proof of Concept
Let `keys_and_challenges = [(A_1, c_1), …, (A_n, c_n)]` and `dst` be the verifier's inputs.

1. Attacker computes the weights locally: replay the transcript — `DigestTranscript::<C::H>::new(dst)`, `domain_separate(b"signatures")`, append each `c_i.to_repr()`, then call the same `weight` derivation to obtain `z_1 … z_n`. No private inputs are involved.
2. Pick arbitrary `s` and arbitrary canonical points `R_1 … R_{n-1}`.
3. Set `R_n = z_n^{-1} · ( s·G − Σ_i z_i·c_i·A_i − Σ_{i<n} z_i·R_i )`, using the scalar inverse of the publicly-known `z_n`.
4. Serialize `SchnorrAggregate { Rs: [R_1..R_n], s }` and submit.

Verification computes `Σ z_i R_i + Σ z_i c_i A_i − sG = z_n R_n + Σ_{i<n} z_i R_i + Σ z_i c_i A_i − sG = 0` by construction, so `multiexp_vartime` returns identity and `verify` returns `true` — a valid aggregate signature over keys/messages the attacker cannot sign individually.
