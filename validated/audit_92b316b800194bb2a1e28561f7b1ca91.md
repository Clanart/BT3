### Title
SchnorrAggregate::verify weights do not bind the nonces or keys, allowing trivial forgery of aggregate signatures - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to CVE-2023-0465 (where enabling a non-default verification option causes checks to be silently skipped), `SchnorrAggregate::verify` purports to provide strong batch/half-aggregate verification, but its randomizing weights are derived solely from the verifier-supplied challenges — never binding the nonce points `Rs`, the public keys, or any per-signature values. Because the weights are publicly computable before the attacker chooses `Rs` and `s`, the "randomization" that is supposed to prevent cross-signature cancellation is fully predictable, so the verification equation degenerates to a single under-constrained linear relation the attacker can always satisfy.

### Finding Description
`SchnorrAggregate::verify` builds a `DigestTranscript` and appends only each `challenge` before deriving weights via `weight()` (`aggregate.rs:132-142`). It then checks `Σ z_i·R_i + Σ z_i·c_i·A_i − s·G == identity` via `multiexp_vartime` (`aggregate.rs:138-145`).

Since `z_i` depends only on the `dst` and the challenges — all known to the prover before they choose `Rs`/`s` — the prover can solve for any one free variable. For an aggregate over keys `A_i` with challenges `c_i`, the attacker:

1. Picks arbitrary `s` and arbitrary `R_1..R_{n-1}`.
2. Computes the public weights `z_i`.
3. Sets `R_0 = z_0^{-1}·(s·G − Σ_{i≥1} z_i·R_i − Σ_i z_i·c_i·A_i)`.

The multiexp then sums to identity and `verify` returns `true`. This works even for `n = 1`, where it reduces to an outright Schnorr forgery: `R = z^{-1}s·G − c·A` verifies for any key `A` and challenge `c`. A correct half-aggregation scheme (eprint 2021/350) derives each coefficient by hashing a transcript that binds the aggregate public key, the individual `R_i`, and the message — precisely what is missing here.

### Impact Explanation
Any caller relying on `SchnorrAggregate::verify` to authenticate that a set of parties each produced a valid Schnorr signature accepts a forgery producible by any unprivileged party who knows the (public) keys and challenges and submits attacker-chosen `Rs`/`s` bytes (reachable via `SchnorrAggregate::read` followed by `verify`). This is a forged signature accepted as valid — silent circumvention of the signature checks, mirroring the advisory's "invalid input silently ignored, checks skipped" bug class.

### Likelihood Explanation
Exploitation requires only public information (`dst`, keys, challenges) and submission of a crafted `SchnorrAggregate`. The construction is deterministic forgery, not probabilistic; wherever this aggregate verifier is used in place of individual signature verification, forgery is certain. Impact severity depends on how callers use an accepted aggregate (e.g., attesting multiple sign-offs for the cost of none).

### Recommendation
Bind each statement into its weight: for each index `i`, append `R_i`, the public key `A_i`, and the challenge `c_i` to the transcript before drawing `z_i` (e.g., `z_i = H(dst, agg_context, R_i, A_i, c_i)` per the half-aggregation paper). Alternatively, use `BatchVerifier` (which draws random per-statement weights from an `RngCore`) instead of deterministic transcript-derived weights, while still binding each `R_i`/`A_i`/`c_i` tuple into the weight computation.

### Proof of Concept
```rust
// For verifier-supplied (dst, keys_and_challenges = [(A_0, c_0)]):
let mut digest = DigestTranscript::<C::H>::new(dst);
digest.domain_separate(b"signatures");
digest.append_message(b"challenge", c_0.to_repr());
let z_0: C::F = weight(&mut digest); // publicly computable

// Attacker forges:
let s = C::F::random(rng);
let R_0 = (C::generator() * (z_0.invert().unwrap() * s)) - (A_0 * c_0);
let forged = SchnorrAggregate { Rs: vec![R_0], s };

// verify: z_0*R_0 + z_0*c_0*A_0 - s*G
//       = s*G - z_0*c_0*A_0 + z_0*c_0*A_0 - s*G = identity → true
assert!(forged.verify(dst, &[(A_0, c_0)]));
```
