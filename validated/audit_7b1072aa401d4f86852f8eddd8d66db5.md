### Title
`PlotNFT2Wallet.claim_rewards` bundles all pending pool rewards into a single atomic spend, so one unspendable reward coin blocks claiming of all others - (File: chia/wallet/plotnft_wallet/plotnft_wallet.py)

### Summary
`PlotNFT2Wallet.claim_rewards()` gathers every unclaimed pool-reward coin tracked for a plotNFT and combines them into one `WalletSpendBundle` whose validity is chained together via `CreateCoinAnnouncement`/`AssertCoinAnnouncement`. This is structurally the same bug class as the reported `VE3DRewardPool` issue: bundling logically-independent claimable items into a single all-or-nothing transaction means a single problematic item (e.g. an already-spent/stale reward coin) causes the entire claim to fail, denying the user access to every other, otherwise-claimable reward until the stale entry is somehow removed.

### Finding Description
`claim_rewards()` fetches the full list of unclaimed rewards from `plotnft2_store.get_pool_rewards()` and, without any per-coin validity check, passes the whole list to `PlotNFT.claim_pool_rewards()`: [1](#0-0) 

The resulting coin spends are wired together with a coin-announcement dependency so the whole batch must succeed as a unit: [2](#0-1) 

At the puzzle layer, `PlotNFT.claim_pool_rewards()` further ties every reward coin's spend to the singleton spend via `SendMessage`/`AssertCoinAnnouncement`-style commitments, requiring all listed reward coins to be spendable together in the same bundle: [3](#0-2) 

The list of "unclaimed" rewards is populated by wallet sync tracking p2-singleton coins paid to the plotNFT's p2-singleton puzzle hash: [4](#0-3) 

If any one of these tracked reward coins becomes unspendable in the interim (e.g., it was already consumed by a prior/parallel `forward_pool_reward` spend during a pool transition, a race between two `pw_absorb_rewards`/`claim_rewards` calls, a reorg that leaves the local `plotnft2_store` state stale relative to chain state, or any other divergence between the tracked reward list and the true unspent-coin set), the single combined coin spend for that stale coin will be rejected by the mempool as a double-spend. Because all reward spends and the singleton spend are bundled into one `WalletSpendBundle` (see `spend_bundle = WalletSpendBundle(coin_spends, G2Element())` above), the entire transaction is rejected — not just the stale reward. This blocks the user from claiming any of the other, perfectly valid, reward coins in the same call until the stale entry is manually pruned from `plotnft2_store`.

This mirrors the reported pattern precisely: multiple independent claimable assets are bundled into one all-or-nothing operation, so one bad item (there: a paused-transfer token; here: a stale/already-spent p2-singleton reward coin) DoSes the legitimate claim of everything else bundled with it.

### Impact Explanation
The impact is a spend-triggered transaction-processing halt for reward claiming: a legitimate PlotNFT owner cannot claim any of their farming rewards through `claim_rewards()`/the `pw_absorb_rewards` RPC (`chia/wallet/wallet_rpc_api.py` `pw_absorb_rewards`) as long as one previously-tracked reward coin is stale or already spent. Because the batch has no partial-success handling (unlike `ClawbackManager.spend_clawback_coins`, which tries per-coin and continues on a per-coin exception at [5](#0-4) ), users' unclaimed farming income is unable to be swept until the underlying stale-state divergence is fixed out-of-band. This is a medium-severity availability/DoS issue on reward redemption, analogous in severity to the original finding (rare but externally-triggerable condition causing loss of claim availability).

### Likelihood Explanation
The condition requires the locally tracked `pool_rewards` list to diverge from the true chain state for at least one reward coin (e.g., through a race between two claim operations, a reorg, or state drift after a pool transition). This is plausible but not attacker-trivially-reachable on demand; it depends on external timing/state conditions, similar to the original report's dependency on an external DAO pausing a token. Likelihood is therefore low-to-moderate, but the resulting halt is deterministic once triggered.

### Recommendation
Modify `claim_rewards()`/`PlotNFT.claim_pool_rewards()` to support partial claiming: allow the caller to specify a subset of reward coins to claim (analogous to the report's recommended `getReward(address[] tokens)`), and/or validate that each reward coin is still unspent immediately before building the combined spend bundle, dropping stale entries (and pruning them from `plotnft2_store`) rather than bundling them unconditionally with all other rewards. At minimum, wrap the per-coin reward-spend construction in the same fail-soft/skip pattern already used in `ClawbackManager.spend_clawback_coins`.

### Proof of Concept
1. A PlotNFT accumulates multiple unclaimed p2-singleton pool reward coins tracked in `plotnft2_store` (`add_pool_reward` in `chia/wallet/plotnft_wallet/plotnft_wallet.py:651-657`).
2. One of these reward coins becomes stale/already spent relative to the store's record (e.g., due to a race with a prior claim, or a reorg leaving the wallet's local list out of sync with chain state).
3. The user calls `claim_rewards()` (via RPC `pw_absorb_rewards`), which bundles **all** tracked reward coins, including the stale one, into a single `WalletSpendBundle` chained by coin announcements at [6](#0-5) .
4. The mempool/full node rejects the whole bundle because the stale coin's spend is a double-spend, so none of the otherwise-valid reward coins get claimed, even though most of them are perfectly spendable.

    def claim_pool_rewards(
        self,
        rewards_to_claim: list[PoolReward],
        reward_delegated_puzzles_and_solutions: list[DelegatedPuzzleAndSolution],
    ) -> list[CoinSpend]:
        if self.pooling:
            raise ValueError("Cannot claim rewards while pooling. If you're a pool, try `forward_pool_rewards`")
        if len(rewards_to_claim) != len(reward_delegated_puzzles_and_solutions):
            raise ValueError("Number of rewards and delegated puzzles and solutions must match")
        dpuz_and_solution = DelegatedPuzzleAndSolution(
            puzzle=Program.to(
                (
                    1,
                    [
                        CreateCoin(
                            puzzle_hash=self.inner_puzzle_hash(),
                            amount=self.coin.amount,
                            memos=[self.singleton_struct.struct_hash()],
                        ).to_program(),
                        *(
                            SendMessage(
                                msg=dpuz_and_sol.puzzle.get_tree_hash(),
                                sender=MessageParticipant(puzzle_hash_committed=self.puzzle_hash(nonce=0)),
                                receiver=MessageParticipant(coin_id_committed=reward.coin.name()),
                            ).to_program()
                            for reward, dpuz_and_sol in zip(rewards_to_claim, reward_delegated_puzzles_and_solutions)
                        ),
                    ],
                )
            ),
            solution=Program.to([]),
        )
        return [
            self.singleton_action_spend(
                inner_solution=self.puzzle_with_restrictions().solve(
                    member_validator_solutions=[],
                    dpuz_validator_solutions=[],
                    member_solution=self.bls_member.solve(),
                    delegated_puzzle_and_solution=dpuz_and_solution,
                )
            ),
            *(
                make_spend(
                    coin=reward.coin,
                    puzzle_reveal=reward.puzzle(),
                    solution=reward.solve(
                        self.inner_puzzle_hash(),
                        delegated_puzzle_and_solution=dpuz_and_sol,
                    ),
                )
                for reward, dpuz_and_sol in zip(rewards_to_claim, reward_delegated_puzzles_and_solutions)
            ),
        ]
