### Title
Missing timestamp/freshness validation in App Proxy HMAC verification allows unlimited replay of captured signed requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` only checks that the HMAC `signature` matches the other query parameters; it never validates that the `timestamp` parameter is recent. Any app-proxy request URL that is ever observed by an attacker (via server logs, browser history, `Referer` leakage, a proxy, or network capture) remains permanently valid and can be replayed at any point in the future.

### Finding Description
The verification logic in `app_proxy_verification.rb` computes an HMAC over all query parameters except `signature` and compares it to the client-supplied `signature`: [1](#0-0) 

Although Shopify includes a `timestamp` parameter in every app-proxy request precisely so apps can reject stale/replayed requests, this module treats `timestamp` as just another signed field — it is folded into the HMAC input but its *value* (i.e., its age relative to "now") is never checked. As a result, an HMAC that was valid the moment Shopify generated it remains valid forever, since the same signature will always verify for the same (shop, path_prefix, timestamp, ...) tuple regardless of how much time has passed.

This is the same class of bug as the external report: a value is consumed and trusted (there, a stale Chainlink price; here, an old-but-still-correctly-signed proxy request) without checking whether the source/context backing that value is still "live." In both cases, the missing liveness/freshness check lets an attacker (or an unrelated party who leaks a URL) present outdated authorization/data as if it were current.

### Impact Explanation
An attacker who obtains one legitimately-signed app-proxy URL (e.g., from a compromised CDN/log, a proxy server the storefront traffic transits, browser history on a shared device, or accidental sharing) can replay that exact request against the app's proxy endpoint indefinitely. Since `AppProxyVerification` is the only gate protecting proxy actions (`skip_before_action :verify_authenticity_token` plus `verify_proxy_request`), any state-changing or data-returning action behind it will accept the forged/stale request as authentic, even though it no longer reflects current merchant/customer intent. This can lead to accepted forged signed requests being processed well after they should have expired — a request-replay authentication bypass on the app-proxy trust boundary.

### Likelihood Explanation
App-proxy endpoints are public HTTP endpoints reachable by anonymous or unrelated actors once a URL leaks, and no additional secret is required to replay it — the leaked URL itself is fully self-authenticating under the current implementation. Any logging, caching, sharing, or interception of a proxy URL is sufficient to enable indefinite replay, making this readily reachable in real deployments that rely on `ShopifyApp::AppProxyVerification` as their sole app-proxy authentication mechanism.

### Recommendation
Add an explicit freshness check on the `timestamp` query parameter in `query_string_valid?` (e.g., reject requests where `Time.now.to_i - timestamp.to_i` exceeds a small tolerance window, such as a few minutes), in addition to the existing HMAC comparison, mirroring how OAuth callback/webhook flows should reject stale signed payloads.

### Proof of Concept
1. Configure an app with `ShopifyApp::AppProxyVerification` on a controller action.
2. Capture (via logs, `Referer` header, or network sniffing) a legitimate app-proxy request URL such as:
   `GET /apps/my-app?shop=some-store.myshopify.com&path_prefix=%2Fapps%2Fmy-app&timestamp=1466106083&signature=<valid-hmac>`
   (this is exactly the fixture already used in `test/shopify_app/controller_concerns/app_proxy_verification_test.rb`, confirming that this exact query string is accepted as valid — [2](#0-1) )
3. At any later time — days, months, or years after the original `timestamp` — replay the identical URL/query string.
4. `query_string_valid?` recomputes the same HMAC over the same parameters and returns `true`, so `verify_proxy_request` allows the request through, proving the stale request is accepted with no freshness check.

```ruby
    def verify_proxy_request
      head(:forbidden) unless query_string_valid?(request.query_string)
    end

    private

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end

    def calculated_signature(query_hash_without_signature)
      sorted_params = query_hash_without_signature.collect { |k, v| "#{k}=#{Array(v).join(",")}" }.sort.join

      OpenSSL::HMAC.hexdigest(
        OpenSSL::Digest.new("sha256"),
        ShopifyApp.configuration.secret,
        sorted_params,
      )
    end
```
