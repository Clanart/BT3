### Title
Uncaught exception on malformed commit author/committer identity from a crafted/fetched commit - (File: `app/src/lib/git/log.ts`)

### Summary
`CommitIdentity.parseIdentity()` throws whenever a Git ident string doesn't match a strict regex, but its callers in `getCommits()` and `getAuthors()` in `app/src/lib/git/log.ts` invoke it without a `try/catch`, unlike the one caller in `app/src/lib/git/var.ts` that does wrap it. This mirrors the Zebra bug pattern: a value that is technically permitted by the underlying format (a raw Git commit object's author/committer line) but violates an implicit assumption made by a strict parser (`unwrap()`-style behavior), causing an unhandled exception when Desktop processes attacker-influenced repository data (a cloned/fetched repo's commit history).

### Finding Description
`CommitIdentity.parseIdentity` matches the ident string against a fixed regex and throws if it fails: [1](#0-0) 

`getCommits()` calls `%an <%ae> %ad` formatted output through this parser directly, with no error handling around it: [2](#0-1) 

Similarly, `getAuthors()` maps raw `git log` output straight through `parseIdentity` with no try/catch: [3](#0-2) 

By contrast, the only other caller of `parseIdentity`, `getAuthorIdentity()` in `app/src/lib/git/var.ts`, explicitly wraps the call and treats a parse failure as a benign `null`: [4](#0-3) 

This shows the codebase is aware that `parseIdentity` can throw on malformed input, but that awareness was not applied consistently everywhere the function is used with untrusted data.

Git commit objects are loosely-formatted; a commit can be crafted directly with plumbing commands (`git hash-object`, `git commit-tree`, or a hand-built pack) with an author/committer line that does not conform to the "NAME <EMAIL> DATE ±TZ" shape Desktop's regex expects (e.g., missing angle brackets, missing timestamp, or unusual encoding). Git itself does not reject such objects when displaying `%an`/`%ae`/`%ad`; it will emit whatever partial/fallback text its own lenient ident-splitting logic produces. When Desktop clones or fetches such a repository and later renders history (`getCommits`) or resolves commit authors (`getAuthors`), the resulting string may fail Desktop's regex, and `parseIdentity` throws — with no surrounding guard in these call sites.

### Impact Explanation
This is a Denial-of-Service class issue: an attacker who can get a victim to clone or fetch a repository containing one crafted commit can throw an uncaught exception during a normal, expected workflow (viewing history, computing commit authors for co-author restoration, etc.). Depending on where in the call chain this propagates (it is unclear from static analysis alone whether an upper-layer `try/catch` in `git-store.ts` ultimately intercepts it, since that could not be fully confirmed in this pass), this could manifest as anything from a broken history view to a crash of the renderer process — a real availability impact triggered purely by cloning/fetching attacker content, which matches the "attacker controls a cloned/fetched repository" + "code execution/crash" criteria in scope.

### Likelihood Explanation
Crafting a Git commit object with an unusual author/committer line requires only plumbing commands available to any Git user (no admin/local access to the victim needed) and is a well-known technique used by adversarial-repository research. The victim simply needs to clone/fetch/open the repository in Desktop and view its history — a normal, expected action, not a contrived user step. This makes the likelihood at least moderate.

### Recommendation
Wrap all `CommitIdentity.parseIdentity()` call sites that process untrusted repository data (`getCommits`, `getAuthors` in `app/src/lib/git/log.ts`) in `try/catch`, falling back to a safe placeholder identity (e.g., empty name/email with a sentinel date) instead of throwing, consistent with the defensive handling already used in `getAuthorIdentity`. Additionally, audit other unguarded `forceUnwrap`/regex-based parsers over Git plumbing output (e.g., `parseRawLogWithNumstat` in the same file) for the same class of issue, since they follow the identical "assume `unwrap()`-safe format" pattern as the Zebra `rk` bug.

### Proof of Concept
1. Create a bare/local repository and craft a commit object with a non-conforming author line using plumbing commands, e.g.:
   ```
   git init poc && cd poc
   echo hi > f && git add f
   tree=$(git write-tree)
   commit=$(printf 'tree %s\nauthor malformed-no-brackets-or-date\ncommitter malformed-no-brackets-or-date\n\nmsg\n' "$tree" | git hash-object -w -t commit --stdin)
   git update-ref refs/heads/main "$commit"
   ```
2. Have a victim clone or fetch this repository into GitHub Desktop.
3. Open the repository's History view (which calls `getCommits`) or trigger commit-author resolution (`getAuthors`, e.g. via "Restore commit message" co-author flow).
4. `CommitIdentity.parseIdentity` throws because the crafted ident string doesn't match the expected regex, and the exception is unhandled at that call site — verify whether/where it surfaces (unhandled rejection, error dialog, or crash) since the full downstream exception-handling chain through `git-store.ts` could not be conclusively traced in this investigation.

**Note on completeness:** I was not able to fully confirm, within the tool budget available, whether an outer `try/catch`/`performFailableOperation` wrapper in `app/src/lib/stores/git-store.ts` ultimately converts this exception into a graceful error message rather than a hard crash. This should be verified with a live Desktop session/full codebase access (e.g., a Devin session) before treating this as confirmed-critical, since that would affect the actual severity of the impact.

  public static parseIdentity(identity: string): CommitIdentity {
    // See fmt_ident in ident.c:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L346
    //
    // Format is "NAME <EMAIL> DATE"
    //  Markus Olsson <j.markus.olsson@gmail.com> 1475670580 +0200
    //
    // Note that `git var` will strip any < and > from the name and email, see:
    //  https://github.com/git/git/blob/3ef7618e6/ident.c#L396
    //
    // Note also that this expects a date formatted with the RAW option in git see:
    //  https://github.com/git/git/blob/35f6318d4/date.c#L191
    //
    const m = identity.match(/^(.*?) <(.*?)> (\d+) (\+|-)?(\d{2})(\d{2})/)
    if (!m) {
      throw new Error(`Couldn't parse identity ${identity}`)
    }

export async function getAuthorIdentity(
  repository: Repository
): Promise<CommitIdentity | null> {
  const result = await git(
    ['var', 'GIT_AUTHOR_IDENT'],
    repository.path,
    'getAuthorIdentity',
    {
      successExitCodes: new Set([0, 128]),
    }
  )

  // If user.user.useconfigonly is set and no user.name or user.email
  if (result.exitCode === 128) {
    return null
  }

  try {
    return CommitIdentity.parseIdentity(result.stdout)
  } catch (err) {
    return null
  }
}
