### Title
Balance-based (non-delta) accounting in `compound` lets any caller sweep stranded reward-token dust belonging to previous callers - (File: rewards/ManualCompound.sol)

### Summary
`ManualCompound.compound()` determines how much of each registered reward token to convert/lock/forward by reading `IERC20(_tokenAddress).balanceOf(address(this))` rather than the amount actually attributable to `msg.sender`'s claim in that transaction. Any residue left on the contract from a prior call - e.g. from an under-consuming `ILocker`/`ISimpleHelper` call, or simply because `multiclaimOnBehalf` delivered tokens that were not fully swept in a previous transaction - is indistinguishable from the caller's own freshly claimed tokens and is forwarded entirely to the current caller.

### Finding Description
In `compound`, for every registered `Reward` the contract reads the **entire contract balance** of `_tokenAddress`, not a per-call delta: [1](#0-0) 
```
for (uint256 i; i< rewardTokensLength; i++) {
    ...
    uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));
    if (receivedBalance > 0) {
        if (_convertor != address(0)) {
            IERC20(_tokenAddress).safeApprove(_convertor, receivedBalance);
            IConverter(_convertor).convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2);
        } else if (_locker != address(0) && _lockMgp) { ... lockFor(receivedBalance, msg.sender) ... }
        else if (_helperAddress != address(0)) { ... depositFor(receivedBalance, msg.sender) ... }
        else { IERC20(_tokenAddress).safeTransfer(msg.sender, receivedBalance); }
    }
}
```
There is no bookkeeping of the balance-before-claim vs balance-after-claim for the caller's own `_lps`/`_rewards`. Consequently, whatever balance sits on the contract at the moment `compound` runs - regardless of who actually generated it - is attributed to `msg.sender`.

With the configured convertor set to `SmartWomConvert` and the caller supplying `_minRec = 0`, `_convertFor` in `SmartWomConvert.sol` will never revert on the `MinRecNotMatch` check: [2](#0-1) 
```
if (convertAmount > 0) {
    IERC20(wom).safeApprove(mWom, convertAmount);
    IMWom(mWom).deposit(convertAmount);
}
if (convertAmount + amountRec < _minRec)
    revert MinRecNotMatch();
obtainedmWomAmount = convertAmount + amountRec;
```
Since `_minRec` is attacker-controlled and set to `0`, this guard is fully neutralized, so `receivedBalance` (the entire WOM balance sitting on `ManualCompound`, including any residue from a prior partial/rounding event) is unconditionally pulled and converted for the attacker via `convertFor(receivedBalance, _convertRatio, _minRec, msg.sender, 2)`.

The attacker does not even need to supply real `_lps`/`_rewards` entries that generate meaningful claims - `multiclaimOnBehalf` can be called with empty or unrelated arrays; the sweep of `rewards[i].tokenAddress` balances in the second loop runs unconditionally for every registered reward token index, independent of what was actually claimed in the current call. Any leftover token amount left on the contract belongs, in substance, to whichever prior user's claim under-consumed it or rounded down, but the function has no per-user ledger, so the next caller simply takes it.

None of the existing guards stop this: `compound` has no `onlyOwner`/role restriction (`external` with no modifier besides none), no reentrancy guard is needed here because the exploit doesn't require reentrancy - it only requires the attacker to be the next caller after dust accrues, and no invariant check exists in `ManualCompound` reconciling `_minRec` against `obtainedmWomAmount`, and `SmartWomConvert`'s own check is bypassed by the attacker choosing `_minRec = 0`.

### Impact Explanation
Any wei of a reward token (e.g., WOM/mWOM) stranded on `ManualCompound` - due to rounding, a partial convert, or a helper/locker that consumes less than the full approved amount - becomes claimable in full by the next unrelated caller, rather than being credited back to the user whose claim produced it. This is a direct theft-of-funds primitive: value that belongs to a prior legitimate compounder is diverted to an attacker who merely calls `compound` next, satisfying "Direct theft of user funds" to the extent that stranded balances accumulate (the magnitude depends on how much dust accrues per compound cycle across all users, which can be non-trivial in aggregate over time since `compound` is presumably called frequently by the community/keepers).

### Likelihood Explanation
Preconditions are modest: (1) the reward's `convertor` is `SmartWomConvert` (a supported, non-privileged configuration already exercised by `ManualCompound`'s `Reward` struct), and (2) any residual balance exists on the contract from an earlier call. `_minRec = 0` is entirely attacker-chosen and requires no special capital. The attacker needs no privileged role - `compound` is `external` with no access control - and can call it with trivial or empty `_lps`/`_rewards` inputs, so essentially zero capital is required to sweep whatever dust is present. This is repeatable every time dust reappears (e.g., after each legitimate user's compound call that leaves any remainder), making it a persistent, low-cost drip-theft vector rather than a one-off exploit.

### Recommendation
Track a per-call delta instead of relying on `balanceOf(address(this))`:
- Record `balanceBefore = IERC20(_tokenAddress).balanceOf(address(this))` immediately before `multiclaimOnBehalf`, and only forward `balanceAfter - balanceBefore` for each reward token to the caller.
- Alternatively, have `multiclaimOnBehalf` route rewards directly to `msg.sender` bypassing intermediate custody, or maintain an explicit internal accounting map of "claimed-but-not-yet-converted" amounts per user rather than using ambient contract balance.
- Ensure any pre-existing balance on the contract (dust) is swept to a protocol-controlled sink or redistributed pro-rata rather than being available to whichever address calls `compound` next.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy `ManualCompound` with a mock `masterMagpie`, register a reward token `WOM` with `convertor = SmartWomConvert` and no `tokenHelper`/`locker`.
2. Simulate a "victim" compound call where the underlying `_locker`/helper path (or `SmartWomConvert`'s internal swap) leaves a small dust balance of `WOM`/`mWOM` on `ManualCompound` after the call completes (e.g., mock `multiclaimOnBehalf` to over-deliver relative to what gets consumed, or directly `deal`/transfer a small residual amount of the reward token straight to `ManualCompound` to simulate stranded dust from rounding).
3. As the attacker (unprivileged EOA with no relationship to the victim), call `compound(emptyOrDummy_lps, emptyOrDummy_rewards, _convertRatio=10000, _minRec=0, false)`.
4. Assert: `IConverter(SmartWomConvert).convertFor` is invoked with `receivedBalance` equal to the full stranded dust balance, that the resulting `mWOM`/locked value is credited to the attacker (`msg.sender`), and that the victim has no path to reclaim that value.
5. Confirm the invariant fails: the dust that should have remained attributable to the victim (or been unclaimable) is instead transferred to the attacker with zero cost and `_minRec = 0` never blocking the sweep, proving `_minRec` and `obtainedmWomAmount` are not reconciled against the source of the funds.
