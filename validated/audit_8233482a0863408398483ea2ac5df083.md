### Title
Unvalidated URL scheme reaches `shell.openExternal` for GitHub-API-derived links, bypassing the app's own markdown link allow-list - (File: `app/src/lib/stores/app-store.ts`, `app/src/main-process/main.ts`)

### Summary
The C4 report's broken invariant is "a broadly-scoped privileged operation (`withdraw`) accepts attacker/administrator-influenced input with no allow-list, so any target can be acted upon." The closest reachable Desktop analog is the same missing-allow-list pattern applied to `shell.openExternal`: Desktop has a dedicated safeguard that restricts markdown-rendered links (from repo/PR/issue content) to `http:`/`https:` before they are ever opened, but the same restriction is **not** enforced at the two lower-level chokepoints that actually invoke `shell.openExternal` — the `open-external` IPC handler in the main process and `AppStore._openInBrowser` in the renderer/store layer. Any code path that calls these with a URL sourced from a GitHub API object (PR/comment/check-run `html_url`, notification links, etc.) inherits no scheme validation.

### Finding Description
Desktop's markdown link interceptor explicitly whitelists `http(s):` before forwarding a clicked link: [1](#0-0) 

But the two actual sinks that perform the external launch have no such check:
- The IPC handler only *logs* when the value looks like http/https, and unconditionally calls `shell.openExternal(path)` for any string: [2](#0-1) 
- The store-level equivalent used by `Dispatcher.openInBrowser` passes the URL straight to `shell.openExternal` with no validation at all: [3](#0-2) 

Numerous UI surfaces call `dispatcher.openInBrowser(url)` (which funnels into the unguarded `_openInBrowser`) with URLs taken directly from GitHub API response objects rather than from the sandboxed-markdown-filtered path — e.g. pull request comment/review notifications and CI check-run popovers: [4](#0-3) [5](#0-4) 

Compare this to `LinkButton`, the generic building block used for these API-sourced values, which likewise performs no scheme check before calling `shell.openExternal`: [6](#0-5) 

Because these `html_url`/comment/check-run URLs originate from a GitHub/GHE API response — which the task's threat model treats as attacker-controllable (malicious/compromised GHE server, proxy, or MITM'd API response) — a crafted response can substitute a non-`http(s)` value (e.g. `file://`, a Windows `search-ms:`/`ms-officecmd:`-style handler, or another locally-registered custom protocol) for what the UI presents as an ordinary "View on GitHub" or notification link.

### Impact Explanation
`shell.openExternal` with an uncontrolled scheme is Electron's well-known indirect code-execution/file-disclosure primitive: depending on OS-registered protocol handlers, it can open local files (`file://…` disclosing files outside the repo), invoke installed applications with attacker-chosen arguments, or on Windows abuse legacy protocol handlers that have historically enabled command execution. This matches the report's impact category of "unrestricted target chosen by a privileged/trusted actor with no validation," translated to Desktop's threat model as: no allow-list exists at the actual OS-launch chokepoint, only at one specific caller (markdown rendering).

### Likelihood Explanation
Exploitation requires the user to click a link that Desktop renders as if it were a normal GitHub URL (comment author link, check-run "Details" link, PR/notification link) whose value was supplied by a malicious or compromised GitHub Enterprise server / proxied API response — squarely within the task's allowed attacker model ("a GitHub API object"). It does not require local access, admin rights, or social engineering beyond the normal act of clicking a link the app itself renders as legitimate. The main uncertainty is whether every one of the enumerated call sites (`pull-request-comment-like.tsx`, `ci-check-run-popover.tsx`, `pull-request-checks-failed.tsx`, etc.) truly passes an untouched API string all the way to `openInBrowser`, or whether some intermediate layer re-derives/validates the URL — I was not able to fully trace each of these call sites end-to-end within the available searches, so this should be verified against the live source before treating it as confirmed.

### Recommendation
Enforce the same `/^https?:/` allow-list used in `sandboxed-markdown.tsx` at the actual `shell.openExternal` chokepoints — both `ipcMain.handle('open-external', …)` in `app/src/main-process/main.ts` and `AppStore._openInBrowser` in `app/src/lib/stores/app-store.ts` — so no caller can bypass it by going through a non-markdown path. Reject or explicitly confirm-with-the-user any non-`http(s)` scheme before invoking `shell.openExternal`.

### Proof of Concept
1. Point Desktop at a malicious/compromised GitHub Enterprise endpoint (or intercept the API response via a proxy) so that a pull-request comment or check-run object's `html_url` field is replaced with a non-`http(s)` URI (e.g. a `file://` path to a sensitive local file, or a locally-registered custom-protocol URI known to chain into code execution).
2. Desktop surfaces this as a normal "View on GitHub" / notification / check-run link via `LinkButton`/`openInBrowser`, none of which validate the scheme.
3. When the user clicks it, `AppStore._openInBrowser` → `shell.openExternal(url)` is invoked directly with the attacker-chosen scheme, with no `http(s)` gate as exists in `sandboxed-markdown.tsx`'s `setupLinkInterceptor`.

  private setupLinkInterceptor(doc: Document): void {
    doc.addEventListener('click', ev => {
      if (doc.defaultView && ev.target instanceof doc.defaultView.Element) {
        const a = ev.target.closest('a')
        if (a !== null) {
          ev.preventDefault()

          if (/^https?:/.test(a.protocol)) {

          }
        }
      }
    })

  ipcMain.handle('open-external', async (_, path: string) => {
    const pathLowerCase = path.toLowerCase()
    if (
      pathLowerCase.startsWith('http://') ||
      pathLowerCase.startsWith('https://')
    ) {
      log.info(`opening in browser: ${path}`)
    }

    try {
      await shell.openExternal(path)
      return true
    } catch (e) {
      log.error(`Call to openExternal failed: '${e}'`)
      return false
    }
  })
