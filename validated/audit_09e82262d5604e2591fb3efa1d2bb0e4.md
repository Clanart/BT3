## Analog Found

### Title
Path-prefix boundary check in `resolveWithin` allows sibling-directory escape via a malicious deep-link `filepath` parameter - (File: `app/src/lib/path.ts`)

### Summary
The external report's broken invariant is: a validation function exists and is applied in the "normal" call path (`checkFork` in `executeMsg`) but is missing/insufficient in a sibling call path (`completeInboundQueuedTransfer`), letting a stale/attacker-influenced action execute in a context it was never intended for. The closest structural analog in GitHub Desktop is the boundary check used to confine a deep-link-supplied file path to the repository root: `resolveWithin` in `app/src/lib/path.ts` uses `String.prototype.startsWith` to decide containment, which is not a path-boundary-safe comparison.

### Finding Description
`app/src/ui/dispatcher/dispatcher.ts`'s `openRepositoryFromUrl` handles the `open-repository-from-url` deep-link action (reachable via the registered `x-github-client://`, `github-mac://`, `github-windows://` protocol handlers, see `app/src/main-process/main.ts:105-116` and `app/src/lib/parse-app-url.ts:98-124`). The only defenses are (1) rejecting absolute paths and (2) `resolveWithin(repository.path, filepath)`. `resolveWithin` delegates to `_resolveWithin`, whose containment check is: [2](#0-1) 

`realResolved.startsWith(realRoot)` is a **string-prefix** test, not a path-segment-boundary test. If the user's repository lives at, e.g., `/Users/alice/project`, and a sibling directory `/Users/alice/project-secrets` (or `/Users/alice/projectBackup`) exists on disk, then any resolved path under that sibling directory will also satisfy `startsWith('/Users/alice/project')`, because there is no check for a following path separator (`/`) or exact equality. This is the same category of defect as the report's missing `checkFork`: a guard that is present and *looks* sufficient in the common case, but omits a scope/boundary check that the equivalent, better-protected code path enforces elsewhere (the `isAbsolute` / `..`-traversal protections work correctly, but the final containment test itself is flawed).

### Impact Explanation
An attacker crafts a link such as:
`x-github-client://openrepo/https://github.com/victim/project?filepath=../project-secrets/id_rsa`
If the victim clicks it and already has both `project` and a similarly-prefixed sibling directory checked out (a very common pattern — `repo`, `repo-old`, `repo2`, `repo.bak`, `repo-v2`, etc.), the traversal segment is stripped by `normalize`/`resolve`, but the final `startsWith` check does not detect that the resolved path has escaped the intended root into a differently-named sibling folder. The escaped path is then passed to `shell.showItemInFolder(resolved)`, revealing the existence/location of a file outside the intended repository and opening a Finder/Explorer window on it — an unprompted disclosure of file-system layout and potentially sensitive file locations outside the repo, triggered purely by clicking a link, matching the "link the user clicks -> read outside the repo" impact category.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires the victim to have a second directory on disk whose real path is a string-prefix extension of the target repository's real path (not merely a sibling with an unrelated name), and it requires the victim to click a maliciously crafted `x-github-client://openrepo/...` link. There's no requirement for local/physical access, prior malware, or leaked credentials — the trigger is exactly the attacker-controlled deep link and directory-naming happenstance that is common in practice (backup/versioned folder names).

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to use an exact path-boundary comparison instead of raw string prefix matching, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the report's recommendation of adding the missing boundary/scope check to the code path that currently lacks it while a sibling path already has adequate protection.

### Proof of Concept
1. On disk, have `/Users/alice/project` (a repo tracked in Desktop) and `/Users/alice/project-secrets/id_rsa`.
2. Send/click: `x-github-client://openrepo/https://github.com/alice/project?filepath=../project-secrets/id_rsa`
3. `parseAppURL` parses this into an `open-repository-from-url` action with `filepath = "../project-secrets/id_rsa"` [3](#0-2) .
4. `openRepositoryFromUrl` passes the filepath to `resolveWithin(repository.path, filepath)`; because `/Users/alice/project-secrets` string-starts-with `/Users/alice/project`, containment check passes and `shell.showItemInFolder` opens/reveals the out-of-repo file [1](#0-0) [2](#0-1) .

*Note:* I could not find any additional call site that treats the `resolveWithin` result as safe for reading file *contents* (only `showItemInFolder` is used here), so the demonstrated impact is limited to path/existence disclosure rather than confirmed content exfiltration or code execution — this should be verified further in a live Desktop session if a stronger impact is required.
