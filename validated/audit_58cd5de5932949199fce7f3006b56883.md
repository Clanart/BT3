### Title
Recursive precompile calls share one `BalanceHandler`, causing `prevEventsLen` to be overwritten and balance-changing events to be dropped — desyncing StateDB balances from the bank keeper - (File: `precompiles/common/balance_handler.go`)

### Summary
The reported "interest overwritten each loop iteration" bug class maps directly onto `BalanceHandler.prevEventsLen` in this repo: instead of a per-call temporary/stacked marker, a single mutable field is overwritten on every nested/recursive precompile invocation within the same EVM transaction, causing intermediate balance-changing bank events to be skipped when reconciling native balances into the EVM `StateDB`.

### Finding Description
`BalanceHandler` records the current length of the event manager's event log in `BeforeBalanceChange`, then in `AfterBalanceChange` replays every event appended after that recorded index into `StateDB.AddBalance`/`SubBalance` calls: [1](#0-0) [2](#0-1) 

Each precompile execution constructs a fresh `BalanceHandler` via `BalanceHandlerFactory.NewBalanceHandler()` in `runNativeAction` for the "stateful precompile" (`precompiles/common`) path: [3](#0-2) [4](#0-3) 

However, precompiles that embed a single, long-lived `Precompile`/`BalanceHandler` instance (e.g. `distribution.go`, `erc20.go`, `staking.go`, `gov.go`, `slashing.go`, `ics20.go`, and the debug precompile) call `p.GetBalanceHandler()` to obtain the *same* handler object for every invocation of that precompile within a transaction, as demonstrated by the repo's own regression test: [5](#0-4) 

The debug precompile's `Run` shows the pattern: it calls `p.GetBalanceHandler().BeforeBalanceChange(ctx)` then later `p.GetBalanceHandler().AfterBalanceChange(ctx, stateDB)` [6](#0-5) [7](#0-6) 

When a contract makes recursive/nested calls into the same precompile (or into a precompile that itself triggers another call to the same precompile) within one EVM transaction, the inner call's `BeforeBalanceChange` overwrites `prevEventsLen` set by the outer call — exactly the "temporary variable overwritten every loop iteration" defect described in the external report, except here the loop is the call stack instead of a for-loop. When the inner call returns and the outer call's `AfterBalanceChange` eventually runs (or vice versa depending on ordering), the window `[prevEventsLen:]` no longer corresponds to the events generated by that specific call — some bank `coin_spent`/`coin_received`/precisebank fractional-change events end up either double-processed or, more critically, skipped entirely (if the outer scope's start index moves past events it should have captured). Because `AddBalance`/`SubBalance` are the only path used to sync bank-keeper coin movements into the EVM `StateDB` for precompile calls, dropped events mean the StateDB balance permanently diverges from the actual bank-keeper balance for the remainder of the transaction (and is what gets persisted on `Commit()`).

### Impact Explanation
This falls under "irreversible accounting corruption of spendable user value across native balances ... or precompile-mediated assets" and can lead to unauthorized extraction/duplication of value: if `StateDB` balance is desynced upward from the real bank balance, a contract can spend/transfer more EVM-visible balance than it actually owns; if desynced downward, legitimate funds become inaccessible/frozen via the EVM interface. Because balance handling is the sole bridge between native `x/bank` (and `x/precisebank`) state and the EVM `StateDB` for every stateful precompile (staking, distribution, gov, slashing, erc20, ics20), any recursive/nested-call pattern that triggers this bug can affect a broad set of asset flows.

### Likelihood Explanation
The repository's own test suite (`evmd/tests/integration/balance_handler/balance_handler_test.go`) is explicitly named/commented to reproduce "the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB." This indicates the maintainers are aware of a real, reachable bug triggerable by an ordinary unprivileged contract making nested precompile calls (no special privileges required — any user deploying/calling a contract that recurses into a precompile can trigger it). I could not fully verify from the index whether this specific case has already been patched (e.g. by giving each nested call its own handler or by stacking prevEventsLen) versus still being an open/reproduced regression, since I was unable to inspect the full test assertions/fix status or newer statedb reconciliation logic beyond what was returned. The test file's docstring calling it "the balance handler bug" strongly suggests it is a known, actively-tracked issue in this codebase's history — the finding should be validated against the latest state of `precompiles/common/balance_handler.go` and the referenced test's pass/fail assertions before relying on it as an unpatched exploit.

### Recommendation
- Do not store `prevEventsLen` as a single mutable field on a shared/long-lived `BalanceHandler`. Instead, have `BeforeBalanceChange` return a local marker value (analogous to using a temporary variable per call, as in the original audit's fix) and pass that marker explicitly into the matching `AfterBalanceChange` call, or push/pop a stack of markers so nested calls don't clobber the enclosing call's marker.
- Ensure every precompile invocation (including recursive ones into the same precompile instance) uses an isolated, call-scoped handler/state rather than one instance-level field, matching the pattern already used correctly in `precompiles/common/precompile.go`'s `runNativeAction` (which allocates a new `BalanceHandler` per call) — audit and align `p.GetBalanceHandler()` usages in `distribution.go`, `erc20.go`, `staking.go`, `gov.go`, `slashing.go`, `ics20.go` to the same per-call-scoped construction.
- Add/extend integration tests (building on `balance_handler_test.go`) covering deeper recursion depths and interleaved precompile calls (e.g., staking→distribution→staking) to confirm balances always reconcile exactly between `x/bank`/`x/precisebank` and `StateDB` after commit.

### Proof of Concept
1. Deploy a caller contract that invokes a stateful precompile (e.g., the debug precompile or staking precompile) recursively — call precompile A, which within its execution triggers another call back into the same precompile A (or a chain: A → contract → A) before the outer call's `AfterBalanceChange` runs.
2. During the outer call, `BeforeBalanceChange` records `prevEventsLen = N`.
3. The inner/nested call re-enters and calls `BeforeBalanceChange` again on the same handler, overwriting `prevEventsLen` to `M > N`.
4. When the outer call's `AfterBalanceChange` executes, it only processes events from index `M` onward instead of `N` onward, silently skipping the bank events emitted between `N` and `M` — meaning those native balance changes are never mirrored to `StateDB.AddBalance`/`SubBalance`.
5. After `Commit()`, compare `x/bank` `GetBalance` for the involved accounts against `StateDB.GetBalance` (as exercised by `evmd/tests/integration/balance_handler/balance_handler_test.go`'s `TestRecursivePrecompileCallsWithDebugPrecompile`) to observe the desync. [8](#0-7)

// TestRecursivePrecompileCallsWithDebugPrecompile demonstrates the balance handler bug
// by triggering recursive calls that share the same BalanceHandler instance.
func (s *BalanceHandlerTestSuite) TestRecursivePrecompileCallsWithDebugPrecompile() {
	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	// Create and register debug precompile
	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())
	// Set the precompile directly in the EVM keeper's precompile map
	evmApp.GetEVMKeeper().RegisterStaticPrecompile(debugPrec.Address(), debugPrec)
	err := evmApp.GetEVMKeeper().EnableStaticPrecompiles(ctx, debugPrec.Address())
	s.Require().NoError(err)

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Deployed caller contract at %s", callerAddr.Hex())
	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))
	s.Require().NoError(err)

	// Fund Contract
	err = evmApp.GetBankKeeper().SendCoins(ctx, s.chain.SenderAccounts[0].SenderAccount.GetAddress(), callerAddr.Bytes(), types.NewCoins(types.NewCoin("aatom", sdkmath.NewInt(10000000))))
	s.Require().NoError(err)

	res, _, _, err := s.chain.SendEvmTx(
		s.chain.SenderAccounts[0],
		0,             // sender index
		callerAddr,    // to address
		big.NewInt(0), // value
		input,         // data
		0,             // gas price multiplier
	)
	s.Require().NoError(err, "callback transaction should succeed")
	s.Require().False(res.IsErr(), "callback should not fail: %s", res.Events)

	s.Require().Equal(len(res.Events), 15, "callback should have 15 events")
	debug_count := 0
	for _, event := range res.Events {
		if event.Type == "debug_precompile" {
			debug_count++
		}
	}
	s.Require().Equal(10, debug_count, "callback should have 1 debug precompile")

	// Advance to next block to finalize state
	s.chain.NextBlock()
}
