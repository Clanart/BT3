### Title
Attacker-controlled `.gitmodules` file protocol bypass via `allowFileProtocol` in `updateSubmodulesAfterOperation()` - (File: `app/src/lib/git/submodule.ts`)

### Summary
The Vader `replacePool()` bug is a missing-validation bypass: a caller-supplied value (`oldToken`) is trusted without checking it actually exists/is curated, letting an attacker skip a security limit enforced elsewhere (`curatedPoolLimit`). The structural analog in Desktop is `updateSubmodulesAfterOperation()`, which conditionally injects `-c protocol.file.allow=always` into `git submodule update --init --recursive` based solely on a caller-supplied boolean `allowFileProtocol`, with no validation of the actual submodule URLs recorded in the (attacker-controlled) repository's `.gitmodules` file before this flag is applied.

### Finding Description
`updateSubmodulesAfterOperation()` builds its git arguments as: [1](#0-0) 

When `allowFileProtocol` is `true`, git's own hardening against local-path/`file://` submodule URLs (the mitigation added upstream for the CVE-2017-1000117-class submodule attacks, where git defaults `protocol.file.allow` to `user`/restricted in recursive/non-interactive submodule operations) is explicitly overridden to `always`. This flag is threaded in from `checkoutBranch()` and `checkoutCommit()`: [2](#0-1) 

The function never inspects the `.gitmodules` entries (submodule `path`/`url` fields) of the checked-out tree — content that is fully attacker-controlled in any cloned/fetched repository — before deciding to allow `file://`/local-path submodule fetches. As with `replacePool()`, the security-relevant check (git's protocol allowlist) is bypassed purely by a caller-supplied flag rather than being derived from validated properties of the untrusted input (the submodule URLs actually present in the repo).

### Impact Explanation
If `allowFileProtocol=true` is reachable for a repository whose `.gitmodules` was supplied by a third party (e.g., a forked PR checkout, a fetched branch, or an "Open in Desktop" flow), `git submodule update --init --recursive` with `protocol.file.allow=always` will follow `file://` or local relative/absolute paths defined by the attacker. This can point the submodule "clone" at arbitrary local paths reachable from the process (e.g., other repositories on disk, sensitive directories that happen to look like git repos, or via `../../` traversal in the URL) causing the tool to copy/checkout content from outside the intended repository into the working tree, or to execute repository hooks (`post-checkout`, etc.) from that external location. This matches the required impact class: file write/read outside the repo, or corruption of local state, driven by a cloned/fetched repository the attacker controls.

### Likelihood Explanation
This is only exploitable if a code path sets `allowFileProtocol=true` for a checkout/branch switch performed on an untrusted, attacker-supplied repository (e.g., PR checkout across forks). I could not confirm from the index which call sites in `app-store.ts`/`dispatcher.ts` set this flag to `true` and under what conditions (8 and 6 references respectively were found via `grep_search`, but their contents were not retrieved in the remaining budget). Because of this gap, the likelihood cannot be rated with full confidence — it depends on whether any reachable flow enables `allowFileProtocol` for repositories whose `.gitmodules` originates from an untrusted source.

### Recommendation
Before honoring `allowFileProtocol=true`, parse and validate the repository's `.gitmodules` entries (submodule `url` fields) and only allow `file://`/local paths when the target path is verified to be safe (e.g., resolves within an expected, already-trusted location), mirroring the `resolveWithin()`/`sanitizeCloneName()` pattern already used elsewhere in the codebase for path-traversal protection: [3](#0-2) [4](#0-3) 
Additionally, audit and document every call site that passes `allowFileProtocol=true` to confirm none of them apply to repositories with attacker-influenced `.gitmodules` content.

### Proof of Concept
1. Attacker publishes/forks a repository containing a `.gitmodules` file with a submodule entry: `url = file:///Users/victim/.ssh` (or a relative path such as `../../../some-sensitive-repo`).
2. Victim opens/fetches/checks out this repository or branch in GitHub Desktop through a flow that calls `checkoutBranch()`/`checkoutCommit()` with `allowFileProtocol=true`.
3. `updateSubmodulesAfterOperation()` runs `git -c protocol.file.allow=always submodule update --init --recursive`, which — because git's own protocol restriction is disabled — follows the attacker-specified local path/`file://` URL and clones/checks out its content into the victim's working tree.

*Caveat: step 2's premise (that `allowFileProtocol=true` is reachable for an untrusted repository) is not directly confirmed in the reviewed slice of the codebase; verifying the exact call sites in `app-store.ts` is required to fully confirm reachability.*

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}

/**
 * Extracts a safe single-component directory name from a URL-derived repo name.
 *
 * Mirrors the approach of git's `git_url_basename()` in `dir.c`: treat `/`,
 * `\`, and `:` as path separators, take the last non-empty component, strip a
 * trailing `.git` suffix, and reject traversal segments. This ensures the
 * result is always a single path component that cannot escape the parent
 * directory when passed to `Path.join()`.
 *
 * Examples:
 *  - `"Hello-World"` → `"Hello-World"` (unchanged)
 *  - `"desktop.git/../../otherdir"` → `"otherdir"` (last component, traversal segments skipped)
 *  - `".."` → `null` (traversal-only name rejected)
 *
 * See: https://github.com/git/git/blob/master/dir.c (`git_url_basename`)
 */
export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
