### Title
`SignableTransaction::new` omits the OP_RETURN data output from the fee/weight calculation, undercharging the fee — ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output (up to ~83 serialized bytes) to `tx_outs`, but computes transaction weight and virtual size via `calculate_weight_vbytes`, which is only passed `payments` and `change` — never `data`. The resulting `needed_fee` (and the change amount derived from it) is therefore calculated against a transaction smaller than the one actually produced and signed. This is the same bug class as the LMPVault fee report: a quantity is priced against a denominator (transaction size / total assets) that fails to account for a component (the OP_RETURN output / the newly minted shares) added in the same operation.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the data output is pushed into `tx_outs` at lines 193-202:

```rust
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data).expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}
```

but the weight/vbyte estimation at lines 204 and 225-226 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, ...)` — `payments` only, not `tx_outs` and not `data`:

```rust
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
...
let (weight_with_change, vbytes_with_change) =
  Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
```

`calculate_weight_vbytes` (lines 62-99) reconstructs the transaction from `payments` and `change` alone, so the OP_RETURN output's bytes (1-byte OP_RETURN + pushdata prefix + up to 80 bytes of data + 8-byte value + script length ≈ up to ~92 serialized bytes) are excluded from both `weight` and `vbytes`. Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is underestimated by up to `~92 * fee_per_vbyte` sats.
- The `TooLowFee` check at line 211 compares against the understated `vbytes`, so a transaction can pass the minimum-relay-fee check while its *actual* fee rate is below `DEFAULT_MIN_RELAY_TX_FEE`.
- The change amount (`input_sat - payment_sat - fee_with_change`) is still arithmetically correct for the created outputs (the data output carries zero value), so the transaction is internally consistent — it simply pays a lower effective fee rate than the caller specified.
- The final weight sanity check at line 241 also uses the underestimated `weight`, so a transaction including a data output could exceed `MAX_STANDARD_TX_WEIGHT` undetected (marginal, but real).

The `msg`-free `sign` path then has every FROST participant sign `taproot_key_spend_signature_hash` over this underpriced transaction (lines 383-390), committing real funds.

### Impact Explanation
Any caller supplying `data` produces a transaction paying materially less fee per vbyte than requested — up to ~92 vbytes unaccounted. Depending on `fee_per_vbyte`, the transaction may fall under the mempool minimum relay fee and never confirm despite `SignableTransaction` claiming `needed_fee` was met. For a threshold multisig spending real inputs, this means funds locked in a non-propagating/non-confirming transaction until reconstructed and re-signed at a corrected fee — a liveness/funds-availability failure driven entirely by public input bytes (`data`) fed to the signing path. This mirrors the audit issue's economic impact (fee recipient underpaid because the formula ignored the minted units): here the network/miner is underpaid because the formula ignored the added output.

### Likelihood Explanation
`data` is a public, caller-controlled parameter of `SignableTransaction::new`. The bug triggers deterministically whenever `data.is_some()` — no race, no adversary cooperation needed. It is a systematic miscalculation, not an edge case: every byte of the OP_RETURN output is missing from both vbyte computations. Serai's own processor currently passes `None` for `data` (`processor/src/networks/bitcoin.rs` line 450), but the wallet crate is a standalone API for constructing multisig spends, and the feature exists precisely to be used. Severity: Medium — funds are not stolen, but transactions silently underpay fees and can become unconfirmable, requiring re-construction.

### Recommendation
Include the data output in the size estimate. Either:

- Build `calculate_weight_vbytes` over the final `tx_outs` vector (payments + OP_RETURN + change) rather than the raw `payments` slice, or
- Construct the OP_RETURN `TxOut` before calling `calculate_weight_vbytes` and pass it in as an additional output.

The same fix should cover both the non-change and with-change estimations (lines 204 and 225-226), and the `TooLowFee` check should use the corrected vbytes.

### Proof of Concept
```rust
// Two SignableTransactions identical except `data`
let data = vec![0xaa; 80];
let tx_no_data = SignableTransaction::new(
  inputs.clone(), &payments, change.clone(), None, fee_per_vbyte,
).unwrap();
let tx_with_data = SignableTransaction::new(
  inputs.clone(), &payments, change, Some(data), fee_per_vbyte,
).unwrap();

// Both report the same needed_fee/vbytes basis
assert_eq!(tx_no_data.needed_fee(), tx_with_data.needed_fee()); // BUG: data tx is ~92 vbytes bigger

// After signing, the real vsize exceeds the estimate
// tx_with_data.transaction()'s serialized size > vbytes used for needed_fee,
// so effective feerate = needed_fee / actual_vsize < fee_per_vbyte.
// With fee_per_vbyte near DEFAULT_MIN_RELAY_TX_FEE (1000 sat/kvb), the signed
// transaction can be rejected by relay despite passing the TooLowFee check.
```

Root cause is `calculate_weight_vbytes` at `networks/bitcoin/src/wallet/send.rs:62-127` being invoked (lines 204, 225-226) with `payments` instead of an output list that includes the OP_RETURN output created at lines 193-202.
