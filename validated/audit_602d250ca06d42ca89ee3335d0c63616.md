## Title
Stale line-selection indices reused against a freshly re-computed diff cause the wrong lines to be staged and committed - (File: `app/src/lib/git/apply.ts`)

## Summary
GitHub Desktop lets a user select specific lines from a rendered diff for a "partial commit". The line selection is stored as a set of *absolute line indices* (`DiffSelection`) that are only meaningful relative to the exact `ITextDiff` object that was on screen when the user made the selection. When the commit is actually executed, `applyPatchToIndex` re-runs `git diff` against the *current* on-disk file and blindly re-applies the old, index-based selection to this brand-new diff, without ever checking that the diff hasn't changed shape since the user last looked at it. If the working-tree file is modified in the window between "user finishes selecting lines" and "user presses Commit", the indices no longer point at the lines the user actually reviewed, and Desktop silently stages/commits different content than what was shown and approved. This is the same class of bug as the Lybra report: a value ("the diff the selection refers to") is trusted as still-current at execution time instead of being re-validated, letting a state change in the interim silently corrupt the final on-chain/on-disk result.

## Finding Description
- The UI computes selection state (`DiffSelection`) against a specific diff snapshot using absolute line indices (`hunk.unifiedDiffStart + lineIndex`), e.g. in `patch-formatter.ts`: [1](#0-0) 
- That selection object is stored on the `WorkingDirectoryFileChange` in application state and survives independently of the diff that produced it.
- When the user commits, `_commitIncludedChanges` takes whatever `WorkingDirectoryFileChange`s are currently in `repositoryStateCache` (which may be based on a diff loaded some time earlier) and hands them to `createCommit`: [2](#0-1) 
- `createCommit` calls `stageFiles`, which for any file with a partial selection calls `applyPatchToIndex`: [3](#0-2) 
- `applyPatchToIndex` does **not** reuse the diff the user actually reviewed. It re-invokes `getWorkingDirectoryDiff` against the file on disk *at commit time*, then feeds that brand-new diff plus the old `file.selection` straight into `formatPatch`: [4](#0-3) 
- `formatPatch` trusts the selection indices unconditionally: `file.selection.isSelected(absoluteIndex)` is evaluated against whatever hunk/line layout the fresh diff happens to have, with no check that the hunk boundaries, line counts, or line content match what the selection was originally computed from: [5](#0-4) 

The only place that reconciles selection state with a changed diff is `updateChangesWorkingDirectoryDiff`, and even there the reconciliation is limited to removing selections on lines that are "no longer includeable" — it does not detect that the same numeric line index may now correspond to entirely different diff content: [6](#0-5) 

Because `applyPatchToIndex` performs its own independent `git diff` rather than consuming the diff object the selection was derived from, there is no invariant enforced between "the diff the user saw and selected lines in" and "the diff actually converted into a patch and applied to the index" at commit time.

## Impact Explanation
If the working-tree content of a file changes between when the user finishes selecting specific lines to commit and when the commit action actually runs `git diff`/`git apply` (e.g. due to a background formatter, file watcher, build tool, editor autosave, or any other process writing into the repository while Desktop's Changes view is open), the absolute line indices stored in `DiffSelection` will be replayed against a hunk layout that no longer matches. This can cause Desktop to:
- Stage and commit lines/hunks the user never selected or reviewed, or
- Silently drop lines/hunks the user explicitly wanted included,

with no error, warning, or diff re-confirmation shown to the user. This is a direct instance of "silent corruption of what the user commits" — the user believes they approved one set of changes, but git history captures a different one, which can leak unreviewed/unintended content into a commit that later gets pushed.

## Likelihood Explanation
The race window exists whenever the app takes any non-trivial time between the user's partial-selection action and the commit click (typing a commit message, thinking, or simply because the working tree is touched by another running process such as a bundler in watch mode, linter/formatter-on-save, or a script triggered by opening the cloned repository). No local/admin access or credential compromise is required — the only precondition is that something else writes to the file being partially committed during that window, which is a common developer workflow (auto-format-on-save, live builds), and the current code path performs zero staleness checks before converting the stale selection into a git-apply patch.

## Recommendation
Before calling `applyPatchToIndex`/`formatPatch`, re-validate that the diff being used to build the patch is structurally identical (or content-hash identical) to the diff the current `DiffSelection` was generated from; if it has changed, abort the partial-stage operation for that file and force the UI to refresh the diff and require the user to reselect/confirm, rather than silently re-applying possibly-mismatched line indices to a newer hunk layout.

## Proof of Concept
1. Open a repository in Desktop and modify `file.txt` so the working diff has two hunks.
2. In the Changes view, deselect all lines, then select only the lines that will end up as hunk 1 (this creates a `DiffSelection` whose diverging line set is anchored on the current hunk's `unifiedDiffStart`/absolute indices), as exercised in the existing partial-commit tests: [7](#0-6) 
3. While the commit message box is open (before clicking "Commit"), have another process append/insert lines earlier in the same file so the hunk boundaries and `unifiedDiffStart` offsets shift.
4. Click Commit. `createCommit` → `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-runs `getWorkingDirectoryDiff` against the now-modified file and calls `formatPatch(file, diff)` using the *stale* `file.selection`.
5. Inspect the resulting commit with `git show`: the staged hunk corresponds to different source lines than what was visually checked in step 2, demonstrating that the committed content diverges from what the user reviewed and approved.
