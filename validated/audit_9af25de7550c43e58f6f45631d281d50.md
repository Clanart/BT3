### Title
Unauthenticated `payout_tx` OP_RETURN operator attribution allows front-running a withdrawal payout, permanently corrupting `withdrawals.payout_payer_operator_xonly_pk` and blocking the honest funder from reimbursement - (File: core/src/verifier.rs)

### Summary
`Verifier::update_finalized_payouts` trusts the OP_RETURN output of whichever transaction is actually found on-chain spending the withdrawal UTXO as proof of who funded the payout, without checking that the embedded xonly pubkey belongs to a registered operator of that deposit or actually supplied the payout funds. Because the withdrawal input is signed with `SinglePlusAnyoneCanPay` (which only commits to input 0 and output 0), any third party who observes the broadcast payout transaction can construct a competing, fee-bumped transaction that reuses that signature, keeps output 0 unchanged, but swaps the unsigned OP_RETURN output for an arbitrary xonly pubkey.

### Finding Description
The binding this code is supposed to preserve is:

`withdrawals[i].payout_payer_operator_xonly_pk == xonly_pk of the party whose funds actually paid payout_tx.output[0] for withdrawal i`

`Verifier::update_finalized_payouts` (core/src/verifier.rs:2283-2353) fetches, per confirmed block, the txid that spent each registered withdrawal UTXO via `Database::get_payout_txs_for_withdrawal_utxos` (core/src/database/verifier.rs:170-196, joining on `bitcoin_syncer_spent_utxos.txid/vout == withdrawals.withdrawal_utxo_txid/vout`). It then does:

```
let operator_xonly_pk = op_return_output
    .and_then(|output| parse_op_return_data(&output.script_pubkey))
    .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());
```
(core/src/verifier.rs:2319-2321)

and unconditionally persists whatever 32-byte value parses as a valid xonly pubkey via `update_payout_txs_and_payer_operator_xonly_pk` (core/src/database/verifier.rs:198-251). There is no check against `deposit_data.get_operators()`, and no check that this pubkey corresponds to whoever actually supplied the Bitcoin funding the payout output.

The withdrawal input's signature is required to use `TapSighashType::SinglePlusAnyoneCanPay`, enforced in `parse_withdrawal_sig_params` (core/src/rpc/parser/operator.rs:174-187) and verified against that exact sighash type in `Operator::withdraw` (core/src/operator.rs:630-637). Per BIP341, `SIGHASH_SINGLE|ANYONECANPAY` commits only to input 0 and the correspondingly-indexed output (output 0, the user payout) — it does not commit to any other input or output. `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) places the operator-attribution OP_RETURN at output index 2, entirely outside the signed commitment.

Exploit flow: an unprivileged attacker who sees a real operator A's broadcast, unconfirmed `payout_tx` in the mempool copies A's `SinglePlusAnyoneCanPay` signature over the withdrawal UTXO. They build a rival transaction with the same input 0/signature, keep output 0 byte-for-byte identical (required because the signature commits to it), and add their own funding input(s) to cover output 0's value plus a competitive fee, and finally swap output 2's OP_RETURN for an arbitrary or third-party xonly pubkey C that never participated in this deposit and holds no collateral for it. If this rival transaction is mined instead of A's, `get_payout_txs_for_withdrawal_utxos` returns this txid (the one actually recorded in `bitcoin_syncer_spent_utxos`), and `update_finalized_payouts` stores C as `payout_payer_operator_xonly_pk` for withdrawal `i`.

None of the existing guards catch this: `Verifier::is_kickoff_malicious` (core/src/verifier.rs:1859-1915) only compares the DB-recorded pubkey against the kickoff's claimed operator — it has no way to know that C never funded anything. `SECP.verify_schnorr` only validates that the withdrawal-input signature is valid for input 0/output 0, which it still is. `Database::get_payout_txs_for_withdrawal_utxos`'s join is on the outpoint, which correctly reflects whichever transaction actually confirmed — there's no double-recording bug, but the confirmed winner's attribution is unauthenticated.

### Impact Explanation
The withdrawal row for index `i` is permanently corrupted: `payout_payer_operator_xonly_pk = C`, a party with no collateral and no presigned round/kickoff transaction graph for this deposit. Operator A, who actually funded output 0 from their own wallet, is never recorded as payer. `PayoutCheckerTask` looks up unhandled payouts by `operator.signer.xonly_public_key` (core/src/task/payout_checker.rs:41-47 calling `get_first_unhandled_payout_by_operator_xonly_pk`), so A never even attempts `handle_finalized_payout` for this withdrawal, and any later kickoff attempt by A is deemed malicious by `is_kickoff_malicious` since the recorded payer (C) mismatches A's `kickoff_data.operator_xonly_pk`. This is a permanent, irrecoverable loss of the funds A spent fronting the payout — matching "an honest operator permanently unable to be reimbursed." If instead C is chosen to be a real, unrelated registered operator's pubkey, that operator could later be credited/reimbursed for a payout it never funded, matching "an operator reimbursed for a payout it never funded" (Critical). The attack is repeatable against any withdrawal whose payout transaction is still unconfirmed/in the mempool when the attacker observes it.

### Likelihood Explanation
The attacker needs no privileges beyond broadcasting Bitcoin transactions and paying fees — no verifier/operator role, no collateral, no keys tied to the deposit. The primary cost is capital: to keep output 0 valid under the `SinglePlusAnyoneCanPay` signature, the attacker's replacement transaction must supply funding equal to the withdrawal payout amount (since the user-controlled input 0 alone is typically dust). This makes the attack costly for pure profit-seeking but fully within reach as a griefing/sabotage attack against a targeted operator, and is deterministic given: (1) visibility into the operator's payout transaction before it confirms (mempool monitoring), and (2) a higher-fee/RBF-eligible replacement. No mainnet or live Citrea is required to demonstrate the on-chain/DB mechanics.

### Recommendation
Do not trust the OP_RETURN pubkey as sole proof of payer. At minimum, in `Verifier::update_finalized_payouts`, cross-check the parsed `operator_xonly_pk` against `deposit_data.get_operators()` for the corresponding deposit before persisting it, and reject/null out attributions that don't belong to a registered operator of that deposit. Additionally consider binding the attribution output into the signed sighash (e.g., by having the user's `SinglePlusAnyoneCanPay` signature also cover output 2, or by deriving payer identity from a signature over the whole transaction from the funding operator rather than an unsigned OP_RETURN).

Test plan:
1. Set up a deposit with a known operator set `{A, B}` (via `create_test_config_with_thread_name`/`generate_random_xonly_pk` helpers as in `core/src/database/verifier.rs` tests).
2. Register a withdrawal UTXO for index `i` via `update_withdrawal_utxo_from_citrea_withdrawal`.
3. Construct payout_tx_A: input 0 = withdrawal UTXO signed with `SinglePlusAnyoneCanPay`, output 0 = user payout, output 2 = OP_RETURN(A.xonly_pk), funded by A.
4. Construct payout_tx_C: same input 0/signature, identical output 0, but output 2 = OP_RETURN(C) where `C` is a random 32-byte xonly pk not in `{A, B}`, funded by attacker-controlled inputs.
5. Simulate only `payout_tx_C` being confirmed (insert into `bitcoin_syncer_spent_utxos`/block cache instead of `payout_tx_A`).
6. Run `update_finalized_payouts` and assert via `Database::get_payout_info_from_move_txid` that `payout_payer_operator_xonly_pk == Some(C)`.
7. Assert that `Operator::handle_finalized_payout`/`PayoutCheckerTask::run_once` for A never fires for index `i` (i.e., `get_first_unhandled_payout_by_operator_xonly_pk(A)` never returns this withdrawal), proving A can never be reimbursed for the funds it fronted.
