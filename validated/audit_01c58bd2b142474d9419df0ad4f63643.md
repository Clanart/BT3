### Title
Copilot conflict resolutions write attacker-influenced content to disk without re-validating that the target file is still the expected conflicted file - ([File: app/src/lib/stores/app-store.ts])

### Summary
The reported smart-contract bug is a class of "guard only fires in one specific branch of a state transition, so the fallback path silently accepts unverified/stale data." The closest verified analog in this codebase is `AppStore._applyCopilotConflictResolutions`, which writes AI-generated conflict resolutions to disk and immediately stages them for commit. The only anti-clobber guard is conditioned on the target file being *found* in a stale in-memory snapshot of working-directory status; if it isn't found, the code falls straight through to writing and staging the file, mirroring the "unconditional update" flaw from the report where the safety check only applied along one code path.

### Finding Description
`_applyCopilotConflictResolutions` snapshots repository state once at the top of the function: [1](#0-0) 

For each AI-produced resolution it resolves the path (guarding traversal) and then applies a single conditional skip meant to avoid clobbering a file the user already resolved manually while the (potentially long-running) Copilot turn was in flight: [2](#0-1) 

The skip only triggers when `onDiskFile !== undefined && isConflictedFileStatus(onDiskFile.status) && !hasUnresolvedConflicts(onDiskFile.status)`. This covers exactly one scenario — the user resolved the conflict externally in an editor. It does **not** cover the `onDiskFile === undefined` branch (e.g., the file was reported by `git status` under a different path due to a rename/case change, or the working-directory listing captured in `state` is stale relative to disk because the Copilot turn ran for an extended period while other repository refresh operations mutated the working tree). In that branch the function proceeds to `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and stages the path with `git add`, exactly like `ExternalBribe::earned()` unconditionally advancing `prevRewards.timestamp` outside the one guarded branch.

The resolution content itself originates from a model prompt built from repository-controlled data — conflicting hunks, commit messages, and PR titles/descriptions pulled from `IConflictContextCommit`/`IConflictContextPullRequest` via `gatherCommitContext`, which in turn is built from `getMergeBase`/`getCommits` over branches that can come from a remote or a PR the user merges: [3](#0-2) 

Because the model's job is explicitly to synthesize new file content from these attacker-influenceable inputs, and `parseCopilotConflictResolution`/`validateResolutionPaths` only validate JSON shape, path membership, and hunk counts — not semantic correctness — a crafted branch/PR (prompt-injection payload embedded in commit messages, PR body, or conflicting code comments) can bias the model to produce a resolution that silently drops the user's own changes or reintroduces malicious code. That content is written straight to the working tree and staged, without ever refreshing `onDiskFile` from a fresh git status check, so the one existing anti-clobber guard cannot catch the case where the file is missing from the stale snapshot.

### Impact Explanation
If exploited, this results in the exact "silent corruption of what the user commits" scenario called out in the impact rubric: the user believes they clicked "Continue Merge" over their own reviewed content, but the file on disk (and staged for the next commit) is instead attacker-influenced text that bypassed the one existing safety check. Because `git add` is invoked immediately after writing, the corrupted content flows directly into the next commit/push with no further confirmation step.

### Likelihood Explanation
Likelihood is constrained: the attacker needs the victim to (a) hit a merge/rebase/cherry-pick conflict against attacker-controlled content and (b) use the Copilot conflict-resolution feature, and needs the `onDiskFile === undefined` condition to occur (stale/mismatched working-directory snapshot) or successfully bias the model via prompt injection despite the format constraints enforced by `validateResolutionPaths`. This is a narrower, feature-gated path rather than a universal git operation, so likelihood is Medium at best and depends heavily on how effectively the model resists injected instructions — something not verifiable from static code alone.

### Recommendation
Re-fetch working-directory/file status immediately before each `writeFile` call in `_applyCopilotConflictResolutions` (or re-run `git status` right before applying resolutions) rather than relying on the snapshot captured at function entry, and treat `onDiskFile === undefined` the same as "already resolved externally" (skip rather than proceed) unless the file is freshly confirmed as still conflicted. Additionally, consider hashing/diffing the on-disk conflicted content against what was sent to the model at generation time and refusing to apply the resolution if it no longer matches, closing the same class of "guard only checked on one path" gap identified in the original report.

### Proof of Concept
Not independently reproducible from static analysis alone (requires driving the Copilot conflict-resolution UI end-to-end with a crafted remote branch/PR and timing the state snapshot race). Conceptually:
1. Attacker publishes a branch/PR whose conflicting file content and commit messages contain an instruction attempting to manipulate the resolution model, and/or is structured so that after a rename the resolved path won't match any entry in the working-directory snapshot taken when the Copilot turn started.
2. Victim starts a merge/rebase against this branch and invokes "Resolve with Copilot."
3. While the (potentially slow) model turn is in flight, a routine background repository refresh (fetch, status poll) changes/removes the corresponding `workingDirectory.files` entry relative to the snapshot held by `state` at call time.
4. On completion, `_applyCopilotConflictResolutions` finds `onDiskFile === undefined` for the affected path, skips the "already resolved" guard, and writes/stages the model's output unmodified — silently corrupting what will be committed next.

/**
 * Gather commit messages from both sides of the merge to provide intent
 * context for conflict resolution.
 *
 * Uses getMergeBase() to find the common ancestor, then getCommits() to
 * retrieve recent commits on each side since the divergence point.
 *
 * Best-effort: returns null if the merge base cannot be determined.
 */
export async function gatherCommitContext(
  repository: Repository,
  ourBranch: string,
  theirBranch: string,
  limit: number = 10
): Promise<IConflictCommitContext | null> {
  try {
    const mergeBase = await getMergeBase(repository, ourBranch, theirBranch)
    if (mergeBase === null) {
      return null
    }

    const [ourCommits, theirCommits] = await Promise.all([
      getCommits(repository, `${mergeBase}..${ourBranch}`, limit, undefined, [
        '--first-parent',
      ]),
      getCommits(repository, `${mergeBase}..${theirBranch}`, limit, undefined, [
        '--first-parent',
      ]),
    ])

    return { ourCommits, theirCommits }
  } catch {
    return null
  }
}
