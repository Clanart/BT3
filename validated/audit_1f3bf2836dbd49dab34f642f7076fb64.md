### Title
Cross-chain escrow settlement (`withdraw`) permanently reverts on a single zero-escrow token, locking solver/user funds forever - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Wild Credit bug allowed an attacker to escape a *mandatory* liquidation step by making a sub-operation (`decreaseLiquidity` on a 0-liquidity Uni v3 position) revert deterministically, so the enclosing mandatory function could never succeed. The Tron variant of Hyperbridge's IntentGateway contains the same class of bug in its `withdraw()` function, which is the mandatory settlement path invoked from `onAccept()` (RedeemEscrow/RefundEscrow) and `onGetResponse()` (source-chain cancellation). Unlike the sibling implementation in `IntentsBase.sol`, this `withdraw()` does not skip zero-value token entries before checking escrow state, so a single token slot with zero escrow anywhere in the `WithdrawalRequest.tokens` array causes the whole settlement call to revert with `UnknownOrder()` — deterministically and permanently, since retrying does not change the underlying state.

### Finding Description
In `evm/src/apps/intentsv2/IntentsBase.sol`, the canonical `_withdraw()` explicitly guards against zero-amount entries before touching escrow state: [1](#0-0) 

By contrast, the Tron port's `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` has no such guard — it iterates every token in the request and unconditionally reverts if that token's stored escrow balance is zero: [2](#0-1) 

This `withdraw()` is the terminal, mandatory step for both settlement flows:
- `onAccept()` calls it for `RedeemEscrow` (solver claiming escrow after filling) and `RefundEscrow` (destination-chain cancellation): [3](#0-2) 
- `onGetResponse()` calls it for source-chain cancellation once the empty-fill proof is verified: [4](#0-3) 

The `WithdrawalRequest.tokens` array in both paths is built directly from `order.inputs` — the attacker/order-creator-controlled multi-token list supplied at `placeOrder` time (this is documented behavior: settlement "transfers each escrowed input token to the solver" using the order's input list, and cancellation refunds "the escrowed tokens" the same way): [5](#0-4) 

If an order is constructed with one `TokenInfo` entry in `inputs` whose `amount` is `0` (a legitimate, unchecked value in the `TokenInfo{token, amount}` struct), `_orders[commitment][token]` for that token slot will never be non-zero (nothing was escrowed for it). When the settlement message later reaches `withdraw()` — whether it is the solver's `RedeemEscrow` after delivering real output value, or the source-chain refund on cancellation — the loop hits `_orders[body.commitment][token] == 0` for that zero-amount slot and reverts `UnknownOrder()` for the *entire* call, before any of the other, legitimately escrowed tokens are transferred. Because the escrow state for that token slot never changes, the ISMP message can be resubmitted indefinitely and will always hit the same revert — this is not a transient/relayer failure but a deterministic dead end, exactly analogous to `decreaseLiquidity()` reverting forever on a 0-liquidity position.

### Impact Explanation
This breaks the "bridged assets ... must move exactly once and only to the rightful beneficiary" invariant by making them move *never*:
- A malicious order creator can place a cross-chain order whose `inputs` array includes one zero-amount token slot. A solver fills the order on the destination chain and delivers real output tokens to the beneficiary in good faith. The corresponding `RedeemEscrow` message that should release the escrowed input tokens to the solver on the source chain will permanently revert in `withdraw()`, so the solver never receives compensation while the malicious user already received their swap output — a direct, permanent loss of funds for the solver.
- The same defect blocks legitimate cancellation/refund: if a user's own order happens to include a zero-escrow token slot (e.g., padding or a partially-filled/degenerate entry), their `RefundEscrow`/GET-response cancellation flow can never complete, permanently locking their other escrowed assets in the contract.

This matches the bounty's "stealing or loss of funds" and "logic attack" categories, and requires no malicious relayer, prover, or admin — only an unprivileged order creator crafting the `inputs` array.

### Likelihood Explanation
The path requires only a normal, permissionless `placeOrder()` call with a crafted `inputs` array (one zero-amount `TokenInfo` entry) — a plausible action that is not the primary EVM verification target but is straightforward for anyone using the Tron contract, and the message-authentication logic (`authenticate()`) does not validate individual token amounts within the withdrawal body. Whether `placeOrder()` in this file affirmatively rejects zero-amount input entries could not be fully confirmed within this investigation (the function body was not retrieved before the iteration budget ended), so this should be verified before treating the finding as fully confirmed; however, the divergence between `IntentsBase._withdraw()` (which defensively skips `amount == 0`) and the Tron `withdraw()` (which does not) is a concrete, directly-observed code defect regardless.

### Recommendation
Add the same `if (amount == 0) continue;` guard used in `IntentsBase._withdraw()` to the Tron `withdraw()` function in `evm/tron/contracts/apps/IntentGatewayV2.sol` before checking `_orders[body.commitment][token] == 0`, so a single zero-value token slot cannot block release of the other escrowed tokens or brick the settlement/refund message permanently. Additionally, confirm and, if missing, add validation in `placeOrder()` to reject `TokenInfo` entries with `amount == 0` in `order.inputs`.

### Proof of Concept
1. Attacker calls `placeOrder()` on the Tron `IntentGatewayV2` with `order.inputs = [ {token: USDC, amount: 1000}, {token: DAI, amount: 0} ]` for a cross-chain order (source ≠ destination). Only USDC is actually escrowed; `_orders[commitment][DAI]` remains `0`.
2. A solver observes the order, calls `fillOrder()` on the destination chain, delivers the required output tokens to the beneficiary, and the contract dispatches a `RedeemEscrow` message with `body.tokens = order.inputs` (including the zero-amount DAI entry) back to the source chain.
3. On the source chain, the ISMP host delivers the message to `onAccept()`, which calls `withdraw(body, false)`. [6](#0-5) 
4. The loop reaches the DAI entry; `_orders[body.commitment][DAI] == 0` is true, so it reverts `UnknownOrder()` — the whole call, including the USDC transfer, is rolled back.
5. The message can be resubmitted arbitrarily many times; the escrow state for DAI never changes, so `withdraw()` reverts every time. The solver's 1000 USDC stays locked in the contract forever, while the solver already paid out the order's output assets on the destination chain.

### Settlement

When the settlement message arrives on the source chain, the ISMP host calls `onAccept()`. The handler authenticates the message (verifying it came from a known IntentGateway instance), decodes the `WithdrawalRequest`, and calls `withdraw()` which:

1. Marks the order as filled (`_filled[commitment] = solver`)
2. Transfers each escrowed input token to the solver
3. Releases stored transaction fees (in fee token) to the solver
4. Emits `EscrowReleased(commitment)`

### Cancellation

There are two modes for cross-chain cancellation:

**Cancel from source chain**: The user calls `cancelOrder()` on the source chain, which dispatches a `DispatchGet` storage read request to query the destination chain's fill status. The `CancelOptions.height` must be greater than `order.deadline` — this ensures the proof is taken from a block after the order has expired. A relayer processes this request on Hyperbridge by providing storage proofs from the destination chain. If the storage slot for `_filled[commitment]` is empty (order unfilled), Hyperbridge dispatches a response back to the source chain. The `onGetResponse` handler verifies the empty proof and calls `withdraw()` to refund the escrowed tokens to the user. If the order was filled, the response contains a non-empty value and the handler reverts with `Filled()`.

![Cancel from Source Chain](/intent-gateway-cancel-source.svg)

**Cancel from destination chain**: Before the deadline, only the order owner can call `cancelOrder()` on the destination chain. After the deadline, anyone can cancel. The function marks the order as cancelled locally (`_filled[commitment] = user`) to prevent future fills, then dispatches a cross-chain `RefundEscrow` message back to the source chain. When the source chain receives this message via `onAccept()`, it calls `withdraw()` to refund the escrowed tokens to the user and emits `EscrowRefunded(commitment)`.
