### Title
Coinbase outputs paying the multisig are permanently ignored, stranding received funds - (File: processor/src/networks/bitcoin.rs)

### Summary
`Bitcoin::get_outputs` skips `block.txdata[0]` (the coinbase) entirely, under the rationale that coinbase outputs are maturity-burdened. Unlike `Scanner::scan_block`, which documents that a post-processing pass can remove immature outputs, `get_outputs` performs no re-scan: a coinbase transaction paying the Serai multisig's P2TR script is never revisited once it matures. The funds are received on-chain but never reported to the processor, so they can never be spent — the exact analog of "ETH sent to WERC20 with no functionality to send it onward."

### Finding Description
`get_outputs` iterates `block.txdata[1 ..]` and scans each non-coinbase transaction:

```rust

for tx in &block.txdata[1 ..] {
``` [1](#0-0) 

The underlying scanner does support coinbase outputs — `Scanner::scan_block` scans `block.txdata` including index 0 — but warns that "if received outputs must be immediately spendable, a post-processing pass is needed to remove those outputs." [2](#0-1)  `get_outputs` resolves this by dropping the coinbase permanently rather than deferring it. Each block is scanned exactly once by the processor's `Scanner::run` loop, which records the block as scanned in `ScannerDb::save_block` before emitting outputs [3](#0-2) , so the coinbase output is never reconsidered after its 100-block maturity window.

A `ReceivedOutput` produced by `scan_transaction` for a matching `script_pubkey` [4](#0-3)  is the only path by which funds become spendable `SignableTransaction` inputs via `multisig` [5](#0-4) . If the output is never emitted, the UTXO remains spendable in principle but is invisible to the wallet: functionally burned.

### Impact Explanation
Any coins paid to a Serai multisig address via a coinbase transaction are permanently uncredited and unspendable through the normal pipeline. Unlike the Blueberry report (a missing transfer path), here the receive path exists but silently discards a whole class of legitimate payments, producing an identical outcome: funds locked in the protocol's key with no code path to move them.

### Likelihood Explanation
Reachable by any unprivileged party capable of producing a Bitcoin block (solo miner or pool operator) who sets a coinbase output to the Serai multisig's P2TR script — matching `scan_transaction`'s `script_pubkey` lookup. This is a griefing vector: the attacker loses the block reward portion sent, but permanently burns an equivalent amount of "received" funds from Serai's perspective, and can do so at a controlled cost. It can also occur accidentally via non-standard payout configurations. Low-to-moderate likelihood, medium impact — consistent with Medium severity.

### Recommendation
Instead of skipping `txdata[0]` unconditionally, scan the coinbase and defer maturity-bound outputs: record the output plus the block height, and emit it to `outputs` only once `block_being_scanned >= coinbase_height + 100`. Alternatively, schedule a re-scan of the coinbase transaction at maturity height.

### Proof of Concept
1. Miner mines block B whose coinbase `txdata[0]` includes an output with `script_pubkey = p2tr_script_buf(group_key)` (the multisig's external/offset address registered in `Scanner::scripts`).
2. `Scanner::run` scans block B; `get_outputs` skips `txdata[0]`, emits nothing for it, and `ScannerDb::save_block` marks B scanned.
3. After 100 confirmations the coinbase output is mature, but no code path ever scans B again; the output never becomes a `ReceivedOutput`, never enters `SignableTransaction::new`, and the multisig never signs a spend. Funds are stranded despite sitting under Serai's threshold key.

    let mut res = Vec::new();

      // If the vout index exceeds 2**32, stop scanning outputs
