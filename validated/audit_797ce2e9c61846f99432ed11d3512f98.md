Based on the investigation, I found a real local analog to the oracle-freeze pattern in the Intent Gateway's mandatory price-oracle call inside `fillOrder`.

### Title
Unconditional, un-guarded `recordSpread` oracle call in `fillOrder` freezes order settlement when the price oracle reverts - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`fillOrder` unconditionally calls out to `_params.priceOracle.recordSpread(...)` after all escrow/transfer logic has executed, with no `try/catch`. [1](#0-0)  Because Solidity reverts propagate and roll back the whole transaction, any revert inside `recordSpread` (or any call it makes) reverts the entire `fillOrder`, undoing the fill — this mirrors the reported pattern where a mandatory oracle read anywhere in the call graph freezes a critical operation (liquidation there, order settlement here).

### Finding Description
`VWAPOracle.recordSpread` is restricted to the intent gateway caller and, for every input/output token pair, fetches `IERC20Metadata(outputToken).decimals()` for the destination token supplied by whoever created the order, with no try/catch around it. [2](#0-1)  If the configured output token is a non-standard or malicious ERC-20 whose `decimals()` reverts (or is simply not implemented), every subsequent call to `recordSpread` for that token pair reverts, and because `fillOrder` calls this unconditionally whenever `_params.priceOracle != address(0)`, every solver's fill attempt for that order also reverts [3](#0-2) . The same applies if the spread math overflows for very large legitimate order volumes: `weightedSpread = spreadBps * int256(inputAmountNormalized)` is checked arithmetic in Solidity 0.8 and reverts on overflow. [4](#0-3) 

Unlike a liquidation freeze that can be "manually fixed with fake oracles," here the price oracle is entirely optional infrastructure bolted onto a critical settlement path (`fillOrder`) with no bypass, no try/catch, and no ability for `fillOrder` to proceed if the price-tracking call fails — the settlement itself is held hostage by non-essential accounting logic.

### Impact Explanation
Any order that specifies, as its output token, a contract that reverts on `decimals()` becomes permanently unfillable by any solver as long as `_params.priceOracle` is set to a contract enforcing this call — solvers can never complete the fill, `_filled[commitment]` never gets set on the fill path, and escrowed input funds sit locked until the order's `deadline` passes and `cancelOrder` (which does not touch the price oracle) can be invoked. [5](#0-4)  This is a fund-lock (not theft) that can be triggered by an unprivileged order creator picking an adversarial output token, or can occur passively for any legitimate large-notional order that overflows the spread math — freezing fills for exactly the orders the protocol most needs to settle (large volume), similar in spirit to the report's "liquidations frozen when needed most."

### Likelihood Explanation
Any user placing an order controls the `output.assets` token addresses (see `Order.output`) [6](#0-5) , so triggering the `decimals()`-revert path requires no privileged actor, relayer, or governance action — only a normal `placeOrder` call using a non-standard ERC-20 as the output token. The overflow path requires only a sufficiently large legitimate order amount. Both are reachable through the public `fillOrder`/`placeOrder` entrypoints without any malicious peer, prover, or relayer assumption.

### Recommendation
Wrap the `recordSpread` call in `fillOrder` in a `try/catch` (or a low-level `call` with bounded gas that swallows failures) so that a misbehaving price oracle or a malformed/adversarial token can never block the core escrow-release/fill logic. Settlement correctness and fund movement should never depend on the success of best-effort analytics/accounting calls. [7](#0-6) 

### Proof of Concept
1. Governance/deployer configures `_params.priceOracle` to the `VWAPOracle` contract (a supported configuration, per `Params.priceOracle`). [8](#0-7) 
2. Attacker deploys `EvilToken`, an ERC-20 whose `decimals()` function always reverts.
3. Attacker calls `placeOrder` with `output.assets` containing `EvilToken` as the output token (a normal, permissionless action).
4. Any solver calls `fillOrder` for this order: `_fillSameChain`/`_fillCrossChain` execute the transfers, but the trailing `IIntentPriceOracle(_params.priceOracle).recordSpread(...)` call internally invokes `IERC20Metadata(EvilToken).decimals()`, which reverts, unwinding the entire `fillOrder` transaction. [9](#0-8) 
5. No solver can ever fill this order; the user's escrowed input tokens remain locked until `order.deadline` passes, at which point `cancelOrder` (which bypasses the price oracle) must be used to recover funds. [5](#0-4)

        if (order.deadline < _blockNumber()) revert Expired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }

        if (_params.priceOracle != address(0)) {
            IIntentPriceOracle(_params.priceOracle)
                .recordSpread(commitment, order.source, order.inputs, options.outputs);
        }
    }

    function recordSpread(
        bytes32 commitment,
        bytes memory sourceChain,
        TokenInfo[] calldata inputs,
        TokenInfo[] calldata outputs
    ) external restrict(_intentGateway) {
        // Validate inputs and outputs have the same length
        if (inputs.length != outputs.length || inputs.length == 0) {
            return;
        }

        bytes32 sourceChainHash = keccak256(sourceChain);
        uint256 tokensLen = inputs.length;
        for (uint256 i = 0; i < tokensLen; i++) {
            address inputToken = address(uint160(uint256(inputs[i].token)));
            address outputToken = address(uint160(uint256(outputs[i].token)));

            // Get decimals for input token from storage (remote chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 inputDecimals = inputToken == address(0) ? 18 : _tokenDecimals[sourceChainHash][inputToken];
            if (inputDecimals == 0) continue; // Skip if decimals not configured

            // Get decimals for output token directly from contract (local chain)
            // Native tokens (address(0)) use 18 decimals
            uint8 outputDecimals = outputToken == address(0) ? 18 : IERC20Metadata(outputToken).decimals();

            // Normalize both amounts to 18 decimals for comparison
            uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
            uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

            // Calculate spread for this token: (output - input) / input * 10000
            // Positive spread = filler provided more tokens (good for user)
            // Negative spread = filler provided fewer tokens (filler captured spread)
            int256 spreadBps = 0;
            if (inputAmountNormalized > 0) {
                int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
                spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
            }

            // Update cumulative spread data for this token (weighted by volume)
            int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
            _updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);

            // Emit event for each token
            emit SpreadRecorded(commitment, outputToken, spreadBps);
        }
    }
