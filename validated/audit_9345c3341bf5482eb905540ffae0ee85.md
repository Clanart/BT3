### Title
Missing vote-lock check in `mWomSV.startUnlock` allows unlocking mWOM already counted as WombatBribeManager voting weight - (File: wombat/mWomSV.sol)

### Summary
`VLMGP.startUnlock` (VLMGP.sol:275-282) enforces that a user cannot start-unlock more than `getUserTotalLocked(msg.sender) - IWombatBribeManager(wombatBribeManager).userTotalVotedInVlmgp(msg.sender)`, preventing users from withdrawing locked tokens that are simultaneously counted as active voting weight. `mWomSV.startUnlock` (wombat/mWomSV.sol:247-277) has no such check against `WombatBribeManager`, even though `WombatBribeManager.sol` extensively references `mWomSV` (locking/voting logic tied to mWomSV balances). This asymmetry lets a user reserve mWOM as voting weight in the bribe manager and then freely start/complete unlock without any decrease in their still-recorded vote weight.

### Finding Description
`mWomSV.startUnlock` only checks `_amountToCoolDown <= getUserTotalLocked(msg.sender)` [1](#0-0) , and proceeds to move the requested amount into cooldown and eventually let the user call `unlock()` to withdraw the underlying mWOM back out [2](#0-1) . Nowhere in this path is `WombatBribeManager`'s recorded vote weight consulted or decremented, unlike the parallel `VLMGP.startUnlock`, which explicitly reverts if unlocking would drop a user's remaining locked balance below their `userTotalVotedInVlmgp` amount [3](#0-2) . Since `WombatBribeManager.sol` contains extensive logic referencing `mWomSV` (locking/voting weight derived from mWomSV balances), a user who has voted using mWomSV-derived weight can start and complete an unlock of their full locked mWOM balance while the bribe manager's vote-weight bookkeeping for that user remains stale/unadjusted, because there is no equivalent guard or callback to reduce recorded votes at unlock time.

### Impact Explanation
This causes a Vote Integrity violation: the sum of votes recorded in `WombatBribeManager` can exceed the actually-locked mWOM weight backing them after a user withdraws their principal, since votes are not force-reduced on unlock. This can manipulate governance/bribe-allocation outcomes (over-counted voting weight diverting bribe rewards or gauge weight to pools that no longer have real backing), matching the "governance voting result manipulation" impact class.

### Likelihood Explanation
Any unprivileged user who locks mWOM in `mWomSV`, votes via `WombatBribeManager`, and then calls `startUnlock` followed by `unlock` after the cooldown period can trigger this — no special privileges, capital beyond normal locking, or governance access are required, and the sequence is fully repeatable per epoch/voting cycle.

### Recommendation
Add the same guard used in `VLMGP.startUnlock` to `mWomSV.startUnlock`: query the bribe manager (if set) for the user's currently-voted amount tied to mWomSV and revert if `totalLockAfterStartUnlock` would fall below that voted amount, mirroring VLMGP.sol:280-282.

### Proof of Concept
Hardhat test plan:
1. Deploy `mWomSV`, `MasterMagpie`, `WombatBribeManager` and wire mWomSV into MasterMagpie/BribeManager as in production config.
2. User locks `X` mWOM via `mWomSV.lock(X)`.
3. User casts votes in `WombatBribeManager` using the full `X` weight from mWomSV.
4. User calls `mWomSV.startUnlock(X)` — assert this call succeeds (demonstrating the missing check, whereas an equivalent VLMGP call under the same voted-weight condition would revert with `NotEnoughLockedMPG`).
5. Advance time past `coolDownInSecs`, call `mWomSV.unlock(slotIndex)` to withdraw mWOM.
6. Assert `WombatBribeManager`'s recorded vote weight for the user is still `X` (unchanged) while `getUserTotalLocked(user)` is now `0`, proving `sum(active votes) > getUserTotalLocked(user)` — the Vote Integrity invariant is broken.
