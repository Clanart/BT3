### Title
Attacker-controlled `n`/`t` in `ThresholdKeys::read` triggers quadratic Lagrange-interpolation work (and `t` field inversions) during group-key derivation — (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` accepts a fully attacker-controlled `t`/`n` pair (each up to `u16::MAX = 65535`) and unconditionally calls `ThresholdKeys::new`, which derives the group key by evaluating `interpolation_factor` once per participant in `1..=t`. Each `interpolation_factor` call is O(t) field multiplications plus a field inversion, so `new` performs O(t²) field multiplications and `t` inversions. A roughly 2 MB crafted blob thus forces ~4.3 billion field multiplications plus 65535 field inversions — the same algorithmic-complexity DoS class as CVE-2019-20446 (small input, disproportionate work), here quadratic rather than exponential.

### Finding Description
The CVE-2019-20446 bug class is "crafted input causes the number of rendered/computed objects to grow super-linearly relative to input size." In Serai, the analog lives in the threshold-key deserialization path:

1. `ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16`s. `n` controls the read loop of `n` points and `ThresholdParams::new` only enforces `t <= n` — both may be 65535. [1](#0-0) [2](#0-1) 

2. `ThresholdKeys::new` computes `group_key` by summing `interpolation_factor(*i, &t)` for every `i` in `1..=t` — `t` invocations. [3](#0-2) 

3. `Interpolation::Lagrange::interpolation_factor` iterates over all `t` included participants and finishes with `denom.invert().unwrap()` — a full field inversion per call. [4](#0-3) 

Total: t² ≈ 4.29 × 10⁹ field multiplications and 65535 field inversions, triggered by `n·(point_size)` input bytes (~2.1 MB for a 32-byte group). Even `Interpolation::Constant` (which requires `t == n`) goes through the same O(t²) factor evaluations in `new` (the `Constant` arm is O(1) per call, but the group-key sum is still `t` scalar·point multiplications — the Lagrange arm is the severe one).

### Impact Explanation
Any caller that feeds untrusted bytes to `ThresholdKeys::<C>::read` — key-share material relayed between validators, recovery blobs, or deserialized multisig state — hands the sender a single-message CPU-exhaustion primitive. Parsing a ~2 MB message monopolizes a CPU core on billions of field operations before any cryptographic validity check on the shares occurs (the points are canonical-decoded but never proof-verified prior to `group_key` derivation). This stalls consensus-critical signing/key-handling code paths and matches the Medium-severity availability impact of the reference advisory.

### Likelihood Explanation
Reachable whenever `ThresholdKeys::read` (or a wrapper that embeds it) consumes peer-supplied serialization; the reachable-inputs model for this audit explicitly includes untrusted bytes passed to `ThresholdKeys::read`. No malformed encodings are needed — all `n` points can be canonical generator encodings, so the cost is incurred purely by the quantity fields, not by invalid data that might be rejected early. The only mitigation is the implicit `u16` cap; the attack is deterministic and repeatable.

### Recommendation
- Defer or amortize `group_key` derivation: compute it lazily, or derive it via a single O(t) aggregated multiexp instead of `t` independent O(t) factor evaluations (Lagrange factors for a fixed `1..=t` set can be batch-computed in O(t) total via prefix/suffix products, and the 65535 inversions collapse to 1 with Montgomery batch inversion).
- Enforce a protocol-level maximum `n` (e.g., `MAX_KEY_SHARES_PER_SET`) inside `ThresholdKeys::read`/`ThresholdParams::new`, not just `t <= n`.
- Alternatively, accept `group_key` as a supplied value verified against shares only when needed, so deserialization cost stays linear.

### Proof of Concept
```rust
// Construct a serialized ThresholdKeys blob with t = n = 65535, Lagrange
// interpolation, an arbitrary scalar share, and n copies of the canonical
// generator encoding. ThresholdKeys::read will then perform ~t^2 field
// multiplications and t inversions inside ThresholdKeys::new.
let n: u16 = u16::MAX;
let mut blob = vec![];
blob.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
blob.extend(C::ID);
blob.extend(n.to_le_bytes());          // t = 65535
blob.extend(n.to_le_bytes());          // n = 65535
blob.extend(1u16.to_le_bytes());       // i = 1
blob.push(1);                          // Interpolation::Lagrange
blob.extend(C::F::ONE.to_repr().as_ref()); // secret share
let gen = C::generator().to_bytes();
for _ in 0 .. n { blob.extend(gen.as_ref()); }
// ~2.1 MB for a 32-byte group -> ~4.3e9 field muls + 65535 inversions
let _keys = ThresholdKeys::<C>::read(&mut blob.as_slice());
```

The amplification is structural (`t` O(t) evaluations plus `t` inversions in `crypto/dkg/src/lib.rs` `interpolation_factor`/`new`), so no malformed encodings or invalid curve points are required — every byte of input is well-formed.
