### Title
`ThresholdKeys::read` deserializes an inconsistent key set (secret share not bound to verification shares / group key) — attacker-chosen bytes yield a wallet whose group key the holder cannot actually sign for - (File: crypto/dkg/src/lib.rs)

### Summary
Analogous to the Phar deserialization issue (attacker-controlled bytes deserialized into an object whose later use produces an unintended effect), `ThresholdKeys::read` accepts fully attacker-controlled `t`, `n`, `i`, interpolation coefficients, `secret_share`, and `verification_shares`, then constructs a `ThresholdKeys` via `ThresholdKeys::new` without ever checking that `C::generator() * secret_share == verification_shares[i]` or that the secret share is even consistent with the polynomial the verification shares imply. The resulting object is a syntactically valid but semantically inconsistent threshold key.

### Finding Description
`ThresholdKeys::read` parses `t`, `n`, participant index `i`, an interpolation method, one scalar `secret_share`, and `n` verification-share points, then calls `ThresholdKeys::new`. `ThresholdKeys::new` only checks the count and index range of the verification shares, `t <= n`, and the `Constant`-vs-`t==n` interpolation rule. It then derives `group_key` solely from `verification_shares[1..=t]`:

```rust
// crypto/dkg/src/lib.rs:376-378
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

At no point is the deserialized `secret_share` related to `verification_shares[params.i()]` or to the derived `group_key`. A payload with `t = 1`, `n = 1`, `i = 1`, `Interpolation::Lagrange`, `verification_shares = {1: <attacker public key>}` and an arbitrary `secret_share` deserializes successfully and reports `group_key()` equal to a key whose discrete log the attacker knows.

### Impact Explanation
Any consumer that loads `ThresholdKeys` from attacker-influenced bytes (key import/sync/backup-restore paths that pass untrusted input to `ThresholdKeys::read`) will derive a group key entirely from attacker-chosen verification shares. Deposits scanned for that `group_key` (e.g., via `Scanner::new(group_key)` in `networks/bitcoin/src/wallet/mod.rs:162`) are reported as received, while the node's `secret_share` does not correspond — the funds are spendable only by the attacker who chose the verification shares (with `t = 1`, a single-key spend). This is the concrete "funds reported received that are not spendable by the threshold" outcome, plus silent key substitution. All FROST signing with the deserialized keys will additionally produce shares that fail verification, masking the substitution as liveness failures.

### Likelihood Explanation
Reachability requires a deployment feeding untrusted bytes to `ThresholdKeys::read` — the prompt's reachability list explicitly includes `ThresholdKeys::read` as an unprivileged-input API. The attacker needs no secret material and no colluding threshold; the exploit is a pure encoding of attacker-chosen points. Severity is bounded by how often serialized keys are transported rather than generated via `KeyGenMachine`/`calculate_share` (where share consistency is enforced cryptographically by `share_verification_statements`), so Medium.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` after interpolation semantics are fixed, and reject on mismatch. This binds the deserialized secret share to the group key actually derived, converting the silent substitution into a deserialization error.

### Proof of Concept
```rust
use rand_core::OsRng;
use ciphersuite::{Ciphersuite, group::GroupEncoding};
use dalek_ff_group::{Ristretto, EdwardsPoint, Scalar};
use dkg::ThresholdKeys;
use zeroize::Zeroizing;
use std::io::Write;

// Attacker knows this scalar's discrete log
let attacker_secret = Scalar::random(&mut OsRng);
let attacker_key: EdwardsPoint = Ristretto::generator() * attacker_secret;

let mut buf = vec![];
// C::ID
let id = Ristretto::ID;
buf.write_all(&(id.len() as u32).to_le_bytes()).unwrap();
buf.write_all(id).unwrap();
// t = 1, n = 1, i = 1
buf.write_all(&1u16.to_le_bytes()).unwrap();
buf.write_all(&1u16.to_le_bytes()).unwrap();
buf.write_all(&1u16.to_le_bytes()).unwrap();
// Interpolation::Lagrange
buf.write_all(&[1u8]).unwrap();
// arbitrary secret_share, NOT attacker_secret
buf.write_all(Scalar::random(&mut OsRng).to_repr().as_ref()).unwrap();
// verification_shares[1] = attacker's public key
buf.write_all(attacker_key.to_bytes().as_ref()).unwrap();

let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap();
// keys.group_key() == attacker_key: funds sent here are spendable solely
// by the attacker, while the node's stored secret share cannot sign for them.
assert_eq!(keys.group_key(), attacker_key);
```
