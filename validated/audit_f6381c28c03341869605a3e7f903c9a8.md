Based on my investigation, the strongest analog is a **submodule `file://` protocol re-enablement** issue in the checkout/submodule update path, which mirrors the bug-report's core theme (an untrusted-repository-controlled value bypassing a safety check that is supposed to gate a dangerous, unvalidated operation).

### Title
Submodule `file://` Protocol Re-enabled on Normal Checkout Allows Local Path Exfiltration via Malicious `.gitmodules` - (File: `app/src/lib/git/submodule.ts`, `app/src/lib/git/checkout.ts`)

### Summary
`git` disables the `file://` transport for submodules by default (`protocol.file.allow=user`) specifically to stop a cloned repository from using a crafted `.gitmodules` entry to pull in arbitrary local paths on the victim's machine. Desktop's `updateSubmodulesAfterOperation` re-enables this transport with `-c protocol.file.allow=always` whenever it is called with `allowFileProtocol=true` [1](#0-0) , and multiple ordinary, non-privileged UI checkout flows (`app-store.ts`, `dispatcher.ts`, `branches-container.tsx`, `confirm-checkout-commit.tsx`, `compare.tsx`, stash dialogs) invoke `checkoutBranch`/`checkoutCommit` with `allowFileProtocol: true` even though the underlying git-level default is `false` [2](#0-1) .

### Finding Description
`checkoutBranch` and `checkoutCommit` default their `allowFileProtocol` parameter to `false`, and after running `git checkout` they call `updateSubmodulesAfterOperation`, forwarding that flag [3](#0-2) . Inside `updateSubmodulesAfterOperation`, when `allowFileProtocol` is `true`, the args array is built with `-c protocol.file.allow=always` before running `submodule update --init --recursive` [1](#0-0) .

The purpose of git's `protocol.file.allow=user` default (which Desktop is overriding) is exactly the invariant the bug report is analogous to: a fraud/invalidity check ("dummy string" placeholder in the Mantle report) that looks like a real guard but is bypassed/disabled, letting attacker-controlled data flow through unchecked. Here, the "guard" is git's own file-protocol restriction, and the "attacker-controlled data" is the `.gitmodules` file inside a cloned/fetched repository — fully attacker-controlled content, no privilege required to author it. An attacker can set a submodule URL to `file:///some/predictable/local/path` (e.g., a common Desktop clone directory as derived from `clone.ts`'s default base path logic, or a path guessed from OS conventions) so that when the victim performs an ordinary branch/commit checkout, `git submodule update` will attempt to "clone" that local path's git history straight into the submodule directory of the malicious repository's working tree.

### Impact Explanation
If the guessed/targeted local path is itself a git repository the victim has on disk, its full history (including any secrets or old commits) gets copied into the malicious repo's submodule folder. Since this happens as part of a normal checkout, the victim may unknowingly stage and push this data in a subsequent commit — a direct case of "silent corruption of what the user commits or pushes," and a path for exfiltrating local repository content to a remote controlled by the attacker once the resulting commit is pushed.

### Likelihood Explanation
Medium. The attacker fully controls the trigger content (`.gitmodules` in a cloned/fetched repo), and no unusual user action beyond opening/checking out the repository in Desktop is required. The main constraint is the attacker's ability to predict a useful local path to target, since blind `file://` fetches of non-repository paths simply fail. This limits impact primarily to scenarios where predictable clone locations (Desktop's default `~/Documents/GitHub/<repo>` style layout, as enforced/tested in `clone.ts` and `clone-path-safety-test.ts`) are targeted, or where the attacker can otherwise infer the victim's directory layout.

### Recommendation
Do not pass `allowFileProtocol: true` for ordinary/default checkout flows initiated on repositories the user does not already explicitly trust for local-path submodules. Restrict `protocol.file.allow=always` to a narrow, explicitly user-consented recovery flow (if one is truly needed), and default all checkout call sites in `app-store.ts`/`dispatcher.ts`/UI containers to `allowFileProtocol=false`, matching git's own upstream default.

### Proof of Concept
1. Attacker creates a repository with a `.gitmodules` file containing:
   ```
   [submodule "victim-data"]
       path = victim-data
       url = file:///Users/victim/Documents/GitHub/some-other-repo
   ```
2. Victim clones/fetches this repository into GitHub Desktop and performs an ordinary branch checkout or commit checkout.
3. `checkoutBranch`/`checkoutCommit` calls `updateSubmodulesAfterOperation` with `allowFileProtocol: true` [4](#0-3) , which runs `git -c protocol.file.allow=always submodule update --init --recursive` [5](#0-4) .
4. If `/Users/victim/Documents/GitHub/some-other-repo` exists as a git repository, its contents/history are copied into `victim-data/` inside the attacker's repo working tree, where the victim may later commit and push it.

**Caveat / what remains unverified:** I was unable to inspect the exact surrounding logic at the `app-store.ts`/`dispatcher.ts` call sites within the remaining tool budget to confirm whether any additional user-confirmation dialog gates the `allowFileProtocol: true` argument before it reaches `checkoutBranch`/`checkoutCommit`. If such a confirmation exists and is shown for arbitrary/first-time repositories, likelihood would be lower than stated above.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
}
