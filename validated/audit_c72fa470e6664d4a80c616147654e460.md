Audit Report

## Title
Vote-account `Withdraw` between VAT filtering and VAT burn can panic the bank, halting the cluster - (File: `runtime/src/bank.rs`)

## Summary
`Bank::maybe_burn_vat_from_staked_accounts` subtracts `vat_to_burn_per_epoch()` from every vote account listed in the epoch-stakes snapshot using `checked_sub(..).expect(...)`, relying on the invariant that `clone_and_filter_for_vat` guaranteed sufficient balance at snapshot time. That guarantee is not re-validated at burn time, and the live account fetched via `self.get_account(vote_pubkey)` can have a lower balance if the authorized withdrawer legitimately withdrew lamports in between, causing the `.expect()` to panic.

## Finding Description
`maybe_burn_vat_from_staked_accounts` iterates `epoch_stakes.stakes().vote_accounts().delegated_stakes()` and for each vote account fetches the *current* live account state via `self.get_account(vote_pubkey)`, then does `account.lamports().checked_sub(vat_to_burn_per_epoch).expect("Vote accounts should have already been filtered to contain enough balance for the VAT")` — confirmed verbatim at [2](#0-1) . The precondition doc comment explicitly states this function must only be called after `clone_and_filter_for_vat` filtering [3](#0-2) .

The filter, `VoteAccounts::clone_and_filter_for_vat`, checks `vote_account.lamports() >= minimum_vote_account_balance` only at the moment the epoch-stakes snapshot is built [4](#0-3) . The threshold `minimum_vote_account_balance_for_vat()` includes rent-exempt minimum *plus* `vat_to_burn_per_epoch()` when Alpenglow is active [5](#0-4) .

Crucially, the vote program's `withdraw` instruction — a normal, unprivileged instruction gated only by `verify_authorized_signer` and a balance check — only enforces the account remain at or above the plain rent-exempt minimum (plus `pending_delegator_rewards`), not the VAT-inclusive minimum: [1](#0-0) . This check has no knowledge of `vat_to_burn_per_epoch()` at all.

Since the epoch-stakes snapshot (and the filtering decision baked into it) is computed once — as seen in the epoch-boundary code that builds `new_epoch_stakes` and then calls `self.maybe_burn_vat_from_staked_accounts(&new_epoch_stakes)` immediately afterward within the same function [6](#0-5)  — the window for exploitation is between the block containing the VAT-eligible snapshot balance and the block that actually processes this epoch-boundary logic. Because the burn reads the *live* account via `get_account` rather than the snapshotted balance, any legitimate withdraw executed by the vote account's authorized withdrawer in a transaction landing before the epoch-boundary-processing block — reducing the balance from `minimum_vote_account_balance_for_vat()` down to the plain rent-exempt minimum — causes `checked_sub` to return `None` and the `.expect()` to panic.

## Impact Explanation
This is a bank-processing code path executed deterministically by every validator that replays the block at the epoch boundary — it is not gated behind RPC, plugins, or any privileged actor. A panic here crashes the validator process on every node processing the same block, constituting a cluster-wide consensus halt. The invariant violated is exactly the one the code's own comment assumes but never re-enforces, and the fix (re-checking balance at burn time, or saturating subtraction) is not present anywhere in the current code.

## Likelihood Explanation
Triggering this requires only: Alpenglow's feature active, a vote account sitting at/near `minimum_vote_account_balance_for_vat()` when the snapshot for `new_epoch_stakes` is taken, and its withdraw authority submitting an ordinary `VoteInstruction::Withdraw` for lamports up to `vat_to_burn_per_epoch()` before the epoch-boundary block executes `maybe_burn_vat_from_staked_accounts`. None of this requires a compromised validator, leaked keys, or privileged control — any vote-account withdraw authority can do this with a normal, permitted instruction, intentionally or accidentally.

## Recommendation
- Re-validate each vote account's live balance against `vat_to_burn_per_epoch()` inside `maybe_burn_vat_from_staked_accounts` at burn time rather than trusting the stale `clone_and_filter_for_vat` snapshot; skip or partially burn accounts that no longer qualify instead of panicking.
- Alternatively, enforce the VAT reserve directly inside `withdraw` (`programs/vote/src/vote_state/mod.rs`), similar to how `pending_delegator_rewards` is already reserved, so a withdrawer cannot bring the balance below the VAT-inclusive minimum while Alpenglow is active.
- Replace the `.expect()` in `runtime/src/bank.rs` with a saturating subtraction or explicit error handling so a stale invariant cannot escalate into a validator crash.

## Proof of Concept
1. Enable the `alpenglow` feature; fund a vote account exactly at `minimum_vote_account_balance_for_vat()` (rent-exempt minimum + `vat_to_burn_per_epoch()`).
2. Allow the epoch-stakes snapshot (`new_epoch_stakes`) to be computed while the account still holds this balance, so `clone_and_filter_for_vat` includes it as VAT-eligible.
3. Before the bank executes the epoch-boundary block that will call `maybe_burn_vat_from_staked_accounts` for this epoch's stakes, submit a `VoteInstruction::Withdraw` for `vat_to_burn_per_epoch()` lamports via the account's withdraw authority — this succeeds because `vote_state::withdraw` only checks the rent-exempt minimum.
4. When `maybe_burn_vat_from_staked_accounts` runs, `account.lamports().checked_sub(vat_to_burn_per_epoch)` on the now rent-exempt-only balance returns `None`, and `.expect("Vote accounts should have already been filtered...")` panics, crashing the bank/validator process. This can be reproduced as a Rust unit test in `runtime/src/bank/tests.rs` by constructing a `VersionedEpochStakes` containing a VAT-eligible vote account, then mutating the live account's stored lamports downward before calling `maybe_burn_vat_from_staked_accounts`.
