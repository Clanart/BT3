### Title
Precompile instructions (secp256k1/ed25519/secp256r1) bypass the metered compute unit budget entirely, letting a single unprivileged transaction get real CPU verification work performed for free — ([File: precompiles/src/lib.rs], [File: program-runtime/src/invoke_context.rs])

### Summary
Agave routes `secp256k1_program`, `ed25519_program`, and `secp256r1_program` instructions through a special "precompile" execution path in `InvokeContext::process_precompile` [1](#0-0) , which calls out to `agave_precompiles::verify_if_precompile` / the individual `Precompile::verify_fn` (`secp256k1::verify`, `ed25519::verify`, `secp256r1::verify`) [2](#0-1) . Unlike ordinary instructions processed through `process_executable_chain`, this path performs real cryptographic work (ECDSA/Ed25519/P-256 signature recovery and hashing over attacker-controlled message slices, see `precompiles/src/secp256k1.rs:23-104`) but **never calls `compute_meter.consume_checked`**. This is explicitly confirmed by the test comment in `core/tests/scheduler_cost_adjustment.rs`: "VM Execution: consume 0 from CU-meter" for a precompiled instruction, with the full `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` allocation left unspent [3](#0-2) .

### Finding Description
The only pricing applied to this real verification work is a coarse, fixed per-declared-signature-count estimate baked into the cost model at transaction admission/scheduling time — `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST` — multiplied by the signature count parsed once from `data[0]` of the precompile instruction [4](#0-3) [5](#0-4) . This cost, however, is completely decoupled from the *actual metered execution* of the transaction: the instruction/CU meter used inside `InvokeContext` (which governs `compute_unit_limit` and is what `ComputeMeter::consume_checked` enforces) is never touched for precompile instructions [6](#0-5) , [1](#0-0) .

This mirrors the ZetaChain bug class exactly: a specific message/instruction type ("privileged" in the sense that it opts out of the normal per-unit metering) is exempted from the standard compute-accounting path, and that exemption is granted per-instruction-type rather than being proportional to the actual work requested/performed. In ZetaChain, bundling arbitrary messages alongside a `MsgGasPriceVoter` benefited from an infinite gas meter; in Agave, a precompile instruction's verification work (hashing + elliptic-curve recovery/verification over attacker-supplied offsets into instruction data, see `secp256k1::verify` reading `message_slice`/`eth_address_slice` at attacker-chosen offsets [7](#0-6) ) is performed completely outside of the CU-metered execution accounting, priced only by a static, size-independent block-cost estimate computed from the declared signature count rather than the CPU work actually performed (which scales with message length and signature count, both attacker-controlled within one instruction).

### Impact Explanation
Because CU consumption for these instructions is fixed at zero regardless of how much actual verification work (hash + recovery) is performed, an unprivileged transaction sender can construct precompile instructions that make full use of the transaction size budget to maximize `count` (number of embedded signature offsets) and to reference maximum-length message slices from other instructions in the same transaction, forcing validators to spend real CPU on repeated hashing/EC recovery, while the CU-limit / compute-budget machinery — the mechanism designed to bound per-transaction work — records zero cost for that work. Block-level admission is only bounded by the static `SIGNATURE_COST`-family estimate in the cost model, not by the CU meter that governs the rest of instruction execution, so the actual-work/priced-work coupling that protects the rest of the VM (interpreted execution, syscalls, CPI) does not apply here. This is a materially underpriced/unmetered compute path reachable by any unprivileged transaction sender, matching the "materially underpriced compute" acceptance criterion.

### Likelihood Explanation
High reachability: any account can submit a transaction containing `secp256k1_program`/`ed25519_program`/`secp256r1_program` instructions with arbitrary offsets pointing at other instructions' data, without any special privilege, and this code path is exercised on every cluster for every such transaction (confirmed by `test_call_precomiled_program` / `test_builtin_ix_precompiled`). The specific "zero CU consumption" behavior is directly documented/tested in-repo, not speculative.

### Recommendation
Meter precompile verification cost against the transaction's actual compute-unit budget (via `compute_meter.consume_checked`) proportional to both the declared signature count and the size of the referenced message slices, rather than relying solely on a fixed per-signature estimate computed at cost-model time that is decoupled from the CU meter used elsewhere in `InvokeContext`. At minimum, `process_precompile` should charge CUs commensurate with the bytes hashed/verified so the compute-budget enforcement (`ComputationalBudgetExceeded`) can bound the actual CPU work, consistent with how every other instruction type is metered.

### Proof of Concept
1. Construct a transaction that includes one `secp256k1_program` instruction with `data[0] = count` set to the maximum value permitted by the remaining transaction-size budget (each signature offset entry costs `SIGNATURE_OFFSETS_SERIALIZED_SIZE` bytes, see `precompiles/src/secp256k1.rs:38-48`).
2. Have each offset entry's `message_data_offset`/`message_data_size` point into another large instruction's data blob already present in the same transaction, maximizing the bytes hashed per signature entry (`precompiles/src/secp256k1.rs:82-89`).
3. Submit the transaction with a minimal `compute_unit_limit` (e.g., via `ComputeBudgetInstruction::set_compute_unit_limit`), since the precompile path bypasses `compute_meter.consume_checked` entirely — as demonstrated by `test_builtin_ix_precompiled`, which shows "VM Execution: consume 0 from CU-meter" and the transaction still succeeding [3](#0-2) .
4. The transaction performs `count` EC-recovery + keccak-hash operations over attacker-chosen message sizes, none of which are charged against the CU limit, only against the fixed, size-independent `SECP256K1_VERIFY_COST` used purely for block-cost bookkeeping [4](#0-3) .

pub struct ComputeMeter(Cell<u64>);

impl ComputeMeter {
    /// Consume compute units
    pub fn consume_checked(&self, amount: u64) -> Result<(), Box<dyn std::error::Error>> {
        let compute_meter = self.0.get();
        let exceeded = compute_meter < amount;
        self.0.set(compute_meter.saturating_sub(amount));
        if exceeded {
            return Err(Box::new(InstructionError::ComputationalBudgetExceeded));
        }
        Ok(())
    }

    /// Set compute units
    ///
    /// Only use for tests and benchmarks
    #[cfg(feature = "dev-context-only-utils")]
    pub fn mock_set_remaining(&self, remaining: u64) {
        self.0.set(remaining);
    }
}

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
