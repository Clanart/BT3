## Title
Renamed-file diff shown to the user silently diverges from what is actually committed - ([File: app/src/lib/git/diff.ts])

### Summary
`getWorkingDirectoryDiff` in `app/src/lib/git/diff.ts` is the function that computes the diff a user sees in the Changes view and uses (via `formatPatch`) to build the partial-commit patch that is `git apply --cached`'d into the index. For renamed files, the function diffs the working tree file against the *index*, not against the blob the file had in `HEAD` before the rename. This is explicitly acknowledged in the code as "technically incorrect" because any content that is already staged for the renamed file (i.e., already present in the index) is invisible in the diff the user reviews, even though that staged content will be part of the resulting commit. [1](#0-0) 

### Finding Description
The broken invariant is: *"what the user reviews in the diff pane must equal what gets committed."* This invariant is the same class of bug as the Aave `updateInterestRates`-before-burn issue — a security-relevant computation (here, the diff rendered for user review and used to build the commit patch) is derived from a state snapshot that is stale/incorrect relative to the state that will actually be persisted.

For a renamed file, `getWorkingDirectoryDiff` runs `git diff -- <path>` (working tree vs. index) instead of comparing against the pre-rename blob in `HEAD`: [1](#0-0) 

Any bytes that are already staged in the index for that path (for example, content staged by a pre-commit/post-checkout hook triggered during checkout of an attacker-controlled repository, by a partial-stage from a previous operation, or by another tool operating on the same working directory) are excluded from the rendered diff. When the user then commits — including via the partial-commit path that literally rebuilds a patch from the rendered hunks (`formatPatch`) and re-applies it to the index with `git apply --cached` — the invisible staged bytes remain part of the final commit content because `applyPatchToIndex` only ever asks the index to apply the patch on top of what's already staged; it never resets the index to a known-clean baseline before diffing: [2](#0-1) 

So the code path that decides "what the user is shown" and the code path that decides "what gets committed" consume two different underlying states (index vs. HEAD-old-blob) at two different points in time, exactly analogous to the Aave bug reading stale `totalDebt` before the burn updates it.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes": a user can visually confirm/approve a diff that does not represent the actual bytes that end up in the object database and get pushed to the remote. In a supply-chain scenario, a maintainer reviewing a rename+edit from a contributor (or reviewing their own working directory after operations run by an attacker-controlled repository hook) could unknowingly commit and push content they never saw. This is a real, unprivileged Desktop bug class (diff pane fails to represent the true diff) rather than a purely cosmetic issue, since the commit is the artifact that other collaborators and CI will trust.

### Likelihood Explanation
The trigger condition — the index containing staged content for a path different from what's rendered — is plausible in normal Desktop usage: renames combined with partial staging, mixed CLI/Desktop usage on the same repo, or hooks that touch the index (e.g., a repository-provided `post-checkout`/`pre-commit` hook, which Desktop will execute) can leave the index in this state without any unusual/local-admin action from the user. The comment in the source acknowledges the author was aware of the discrepancy and chose the shortcut ("technically incorrect... but excessive to fix"), indicating this is a known, reachable, and still-unresolved code path rather than a theoretical corner case.

### Recommendation
For renamed files, `getWorkingDirectoryDiff` should diff the working tree file against the blob as it existed at `HEAD` for the file's old path (e.g., via `git hash-object`/`git diff <blob> <worktree file>` as the code comment itself suggests), rather than against the index, so the rendered diff always matches the final commit content regardless of any pre-existing index state. Alternatively, `applyPatchToIndex` should reset/normalize the index for the specific path before generating and applying the patch, ensuring no invisible staged content survives into the commit.

### Proof of Concept
Conceptual reproduction (exact reachability of the index pre-staging step — e.g., via a repository-supplied hook — was not verified against a live Desktop build in this session and should be validated by a background agent with terminal access):
1. Set up a repo with a tracked file `a.txt` containing `SAFE` at `HEAD`.
2. Externally (e.g., via a hook fired by opening/fetching the repository, or a second git-aware tool operating on the same working copy) stage a rename of `a.txt` to `b.txt` in the index with content `SAFE\nMALICIOUS_PAYLOAD`, while the working tree file `b.txt` only shows `SAFE\nMALICIOUS_PAYLOAD` too but the user only edits/reviews a small visible diff hunk unrelated to the malicious payload (or the payload is already fully staged so `git diff -- b.txt` shows an empty/small diff for that region).
3. In Desktop's Changes view, the diff computed by `getWorkingDirectoryDiff` (`git diff -- b.txt`, working tree vs. index) does not show the `MALICIOUS_PAYLOAD` line because it's already identical between working tree and index.
4. The user reviews what appears to be a clean rename and commits. `applyPatchToIndex`/`createCommit` commits the index as-is, including `MALICIOUS_PAYLOAD`, which the user never saw or approved.
5. The resulting commit, when pushed, silently contains content the user did not review.

Note: I was not able to fully trace, within the indexed portion of the codebase, every caller/hook path that could pre-stage index content for a renamed file before Desktop computes its diff (e.g., whether Desktop invokes any hook or external command between file-selection and diff computation that could write to the index). This should be verified by a background agent with full repository and terminal access before treating this as a confirmed exploitable path end-to-end; the core code defect (diff computed against index rather than HEAD-old-blob for renames) is confirmed directly from the source and comment at `app/src/lib/git/diff.ts` lines 379-390.

export async function applyPatchToIndex(
  repository: Repository,
  file: WorkingDirectoryFileChange
): Promise<void> {
  // If the file was a rename we have to recreate that rename since we've
  // just blown away the index. Think of this block of weird looking commands
  // as running `git mv`.
  if (file.status.kind === AppFileStatusKind.Renamed) {
    // Make sure the index knows of the removed file. We could use
    // update-index --force-remove here but we're not since it's
    // possible that someone staged a rename and then recreated the
    // original file and we don't have any guarantees for in which order
    // partial stages vs full-file stages happen. By using git add the
    // worst that could happen is that we re-stage a file already staged
    // by updateIndex.
    await git(
      ['add', '--update', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    // Figure out the blob oid of the removed file
    // <mode> SP <type> SP <object> TAB <file>
    const oldFile = await git(
      ['ls-tree', 'HEAD', '--', file.status.oldPath],
      repository.path,
      'applyPatchToIndex'
    )

    const [info] = oldFile.stdout.split('\t', 1)
    const [mode, , oid] = info.split(' ', 3)

    // Add the old file blob to the index under the new name
    await git(
      ['update-index', '--add', '--cacheinfo', mode, oid, file.path],
      repository.path,
      'applyPatchToIndex'
    )
  }

  const applyArgs: string[] = [
    'apply',
    '--cached',
    '--unidiff-zero',
    '--whitespace=nowarn',
    '-',
  ]

  const diff = await getWorkingDirectoryDiff(repository, file)
