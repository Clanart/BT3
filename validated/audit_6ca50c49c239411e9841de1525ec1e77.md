# Title
Argument injection via unsanitized tag names passed to `git push` argv — ([File: app/src/lib/git/push.ts])

## Summary
Tag names originating from an untrusted, attacker-controlled repository (via clone/fetch) can be crafted to begin with `-`/`--`, and are spliced directly into the `git push` argument vector without a `--` separator or validation, allowing them to be interpreted by git as command-line options (e.g. `--receive-pack=<program>`) instead of literal ref names.

## Finding Description
`getTagsToPush` simply returns whatever string array was persisted in `localStorage` for the repository, with no validation: [1](#0-0) 

That array is loaded into `GitStore._tagsToPush` on construction and exposed via the `tagsToPush` getter, but the array itself is populated by `fetchTagsToPush`, which parses tag names straight out of `git push --dry-run --porcelain` output with no character filtering: [2](#0-1) [3](#0-2) 

These raw strings are ultimately consumed by `push()`, which spreads them directly into the `git push` argv without a `--` end-of-options marker or any check that they don't start with `-`: [4](#0-3) [5](#0-4) 

`git()` forwards `args` as an argv array (not a shell string) to dugite's `exec`, so this is not OS shell injection, but git's own CLI parser will treat any array element starting with `-`/`--` as an option regardless of its position in the argument list: [6](#0-5) 

Crucially, the client-side sanitization that strips leading `-`/`+` characters (`sanitizedRefName`) is only applied in the **Create Tag UI dialog** (`RefNameTextBox`/`create-tag-dialog.tsx`) for tags a user types in Desktop itself: [7](#0-6) [8](#0-7) 

It is **not** applied to tags read from git plumbing (`getAllTags`/`show-ref`) or from `fetchTagsToPush`'s parsing of push dry-run output — i.e., tags that arrive via cloning/fetching an attacker-controlled repository. Git's own `check-ref-format` rules disallow control characters and spaces in ref names, so a tag literally containing a space (as in the PoC's `--upload-pack=touch /tmp/pwned`) cannot exist. However, a tag name such as `--receive-pack=/tmp/x.sh` (no spaces, only `-`, `/`, `.`) is a syntactically valid git ref and passes `check-ref-format`, so it survives creation on the attacker side and subsequent clone/fetch by the victim.

## Impact Explanation
`git push` supports `--receive-pack=<program>`, which for `ssh://` and local/filesystem transports causes the specified program to be invoked instead of `git-receive-pack` on the transport target. If a victim clones/forks an attacker's repository (inheriting the malicious tag), then later pushes to a *different* destination where that tag is still "new" (e.g., their own fork/remote), the tag name is included in `tagsToPush` and injected as a flag into that push invocation. Depending on the transport (SSH or local path) this can result in unauthorized program execution on the remote/transport side. For plain HTTPS github.com pushes, `--receive-pack` is ignored by the smart-HTTP protocol, limiting impact there to push failures/confusion rather than execution — so the severity is transport-dependent.

## Likelihood Explanation
Requires: (1) an attacker publishes a tag with a `-`/`--`-prefixed valid ref name in a repository, (2) a victim clones/forks that repository, and (3) the victim later pushes to a remote where that tag is still unpushed and where the transport is SSH or local (not plain HTTPS). This is a plausible but non-trivial chain of user actions matching the "attacker-controlled cloned repo" threat model in scope, though not guaranteed to trigger on typical GitHub HTTPS-only workflows.

## Recommendation
Insert a `--` end-of-options separator before ref names in `push()`'s argv construction (and any other Desktop code that splices tag/branch/ref names into git argv), e.g. `args.push('--', ...tagsToPush)` (adjusted for correct git-push syntax) or explicitly reject/quote ref names beginning with `-` before including them in any git argv, mirroring the existing `sanitizedRefName`/`testForInvalidChars` logic but applied to tags discovered via clone/fetch, not just user-typed input.

## Proof of Concept
1. In an attacker-controlled repository, create a tag whose name is a valid git ref but begins with `--`, e.g.:
   `git tag -- --receive-pack=/tmp/pwn.sh HEAD` (valid per `git check-ref-format`, since it contains no spaces/control chars).
2. Victim clones/forks this repository in GitHub Desktop, inheriting the tag locally.
3. Victim adds/points to a different remote (e.g. their own fork) that does not yet have this tag, and performs a push in Desktop.
4. `fetchTagsToPush` detects the tag as `[new tag]` and stores it via `storeTagsToPush`/`GitStore.tagsToPush`.
5. `push()` builds `['push', remote.name, refspec, '--receive-pack=/tmp/pwn.sh', ...]` and passes it unescaped to `git()` → dugite `exec`, where git will parse the tag string as a CLI option rather than a ref name. [4](#0-3)
