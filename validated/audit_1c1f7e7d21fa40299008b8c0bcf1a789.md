## Analog Found

### Title
Coins sent to a Pool Wallet's `p2_singleton_puzzle_hash` that aren't recognized coinbase rewards are permanently stranded by the wallet ([File: chia/pools/pool_wallet.py])

### Summary
The Ajna report describes value (rebased collateral/donations) that lands inside the pool contract but is never tracked by pool accounting, so it is permanently unrecoverable. The same class of bug exists in Chia's pooling singleton: any XCH sent to a Plot NFT's `p2_singleton_puzzle_hash` ("pool contract address") that the wallet does not recognize as a genuine coinbase pool reward is silently skipped by the only user-facing reclaim path, `PoolWallet.claim_pool_rewards()`, leaving the funds stuck.

### Finding Description
`PoolWallet.claim_pool_rewards()` is the sole wallet-exposed mechanism (via `pw_absorb_rewards` RPC) for spending coins sitting at the pool singleton's `p2_singleton_puzzle_hash`. It builds a `coin_to_height_farmed` map strictly from `WalletStateManager`'s recorded farming-reward transactions (`get_farming_rewards()`), then iterates the wallet's unspent coin records and explicitly skips anything not in that map: [1](#0-0) 

Any coin paid to the same puzzle hash by a user, a third party, or an operator mistake (the CLI itself warns "do not send money to this address" precisely because this happens) is added to the wallet's coin store as an ordinary coin, but is never included in `coin_to_height_farmed` because it has no corresponding farming-reward transaction record. It is therefore permanently excluded from every `claim_pool_rewards()` call, `raise ValueError("Nothing to claim, no unspent coinbase rewards")` notwithstanding — the coin sits at the pool address forever from the perspective of the wallet software.

Historically the project was aware coins land at `p2_singleton_puzzle_hash` and just get "ignored" (see the two CHANGELOG entries below), but the fix only stopped an exception/enabled unrelated self-pool claims — it never added a path to actually recover non-reward value sent to the address: [2](#0-1) [3](#0-2) 

The newer `PlotNFT2Wallet.coin_added()` path is stricter still: it explicitly detects a non-reward coin sent to `p2_singleton_puzzle_hash` (parent coin id prefix doesn't match `GENESIS_CHALLENGE`) and raises instead of tracking it at all: [4](#0-3) 

Note that the underlying CLVM puzzle (`P2_SINGLETON_MOD`/`claim_p2_singleton`) does not itself restrict spends to reward-shaped coins — any coin at that puzzle hash can be claimed by the singleton owner with a manually built solution: [5](#0-4) 
This confirms the loss is a wallet-software/UX gap, not a cryptographic one — exactly analogous to the Ajna report's own aside that generic "donations" to the pool are unaccounted for and lost from the protocol's normal operation, even though in principle a bespoke recovery mechanism (an auction/claim path) could exist.

### Impact Explanation
Any XCH accidentally or intentionally sent to a Plot NFT's known `p2_singleton_puzzle_hash` — which is a public, unauthenticated address anyone can pay to — becomes unreachable through the standard wallet RPC/CLI (`pw_absorb_rewards`/`chia plotnft` claim commands). This is a concrete, unauthorized-loss-of-funds condition reachable by any wallet user or third party who sends value to that address, matching the report's "Medium" severity bug class (value trapped/untracked in a pool-like contract).

### Likelihood Explanation
High reachability: the `p2_singleton_puzzle_hash` is deliberately displayed to users (as the "pool contract address"), is derivable by anyone from the public launcher id, and receiving XCH there requires no special privilege — a normal wallet send suffices. The only barrier is user/operator mistake, which the code's own warning messages acknowledge is expected to happen.

### Recommendation
Extend `PoolWallet.claim_pool_rewards()` (and the `PlotNFT2Wallet` equivalent) to build a claim spend for any unspent coin at the pool's `p2_singleton_puzzle_hash`, not only ones matching a recorded farming-reward transaction. This mirrors `singleton_top_layer.claim_p2_singleton()`, which already supports claiming arbitrary-amount coins at that puzzle hash; the constraint should be relaxed at the wallet layer so legitimately-owned but "non-reward-shaped" coins can be swept back by the pool wallet owner instead of being permanently stranded.

### Proof of Concept
1. Create a Plot NFT / pool wallet and note its `p2_singleton_puzzle_hash` (`pw_status`/`chia plotnft show`).
2. From any other wallet, send an arbitrary XCH amount directly to that puzzle hash (a plain `send_transaction`).
3. Wait for wallet sync; the coin is added to the pool wallet's coin store as `coinbase=False`/non-reward incoming coin.
4. Call `pw_absorb_rewards` (`PoolWallet.claim_pool_rewards`): the coin is skipped in the loop at `chia/pools/pool_wallet.py:753-756` because it is absent from `coin_to_height_farmed`, and no transaction ever spends it — the funds remain locked at `p2_singleton_puzzle_hash` indefinitely via the wallet's normal tooling.
