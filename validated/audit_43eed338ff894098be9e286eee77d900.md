### Title
Unvalidated `Participant` indexes in PedPoP blame path cause panic on attacker-controlled accusation — ([File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs])

### Summary
The kernel bug mishandles a connection whose early MPA processing failed: the endpoint was already unlinked, and the later close path dereferences a NULL listener. The analog in Serai is the PedPoP blame-handling path, which dereferences per-participant state (`enc_keys`, `commitments`) for `Participant` values supplied by an accuser without first checking that those participants were ever registered — the equivalent of dereferencing a listener that isn't there.

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept `sender` and `recipient` as free `Participant` parameters and forward them to `blame_internal`:

- `blame_internal` calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`, which indexes `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388) — a `HashMap` indexing panic if `decryptor` was never registered.
- If the signature/proof checks pass, `blame_internal` then evaluates `share_verification_statements(recipient, &self.commitments[&sender], ...)` (crypto/dkg/pedpop/src/lib.rs:597-604) — again a `HashMap` indexing panic if `sender` is not a registered participant.

`enc_keys` and `commitments` are only populated via `Decryption::register` for participants `1..=n` (lib.rs:656-660, encryption.rs:351-362), and `register` itself asserts non-re-registration. There is no `validate_map` or bounds check on `sender`/`recipient` anywhere in `blame`, `blame_internal`, or `decrypt_with_proof`. `Participant` is a plain `u16` wrapper, so `Participant::new(n + 1)` (or any unused index) is trivially constructible by the party initiating a blame evaluation.

Like the siw bug, the failure is on a path reachable after early/irregular processing: an accuser names a `sender`/`recipient` index for which no registered endpoint exists, and the code unconditionally dereferences the missing state.

### Impact Explanation
Any party able to submit a blame accusation (an accuser `Participant` index, an accused index, a serialized `EncryptedMessage`, and an optional `EncryptionKeyProof`) can force an out-of-bounds `HashMap` index, which panics. In Rust this unwinds/aborts the calling thread — a remote, unauthenticated-by-crypto crash of whichever component evaluates blame (in production, `CoordinatorMessage::VerifyBlame` in processor/src/key_gen.rs:504-563 feeds accuser/accused straight into `AdditionalBlameMachine::blame`). Repeated submissions deny service to the key-generation/blame-evaluation pipeline. This mirrors the CVE's pure-availability NULL-deref impact.

### Likelihood Explanation
Reachable from public inputs: the accuser controls the `sender`/`recipient` `Participant` values and the message bytes fed to `EncryptedMessage::read`/`decrypt_with_proof`. No valid shares, threshold collusion, or secret knowledge is required — only an out-of-range or unregistered participant index. It is blocked only if the surrounding deployment rejects invalid participant IDs before calling `blame`, which the library itself does not enforce.

### Recommendation
In `blame_internal` (or at the `blame` entry points), validate `sender` and `recipient` against the registered set before use — e.g. `validate_map`-style checks or `.get()` returning a defined fault result — and make `Decryption::decrypt_with_proof` use `self.enc_keys.get(&decryptor)` returning `DecryptionError` instead of indexing. Treat a blame statement referencing an unknown participant as blaming the accuser or as an invalid input, never a panic.

### Proof of Concept
```rust
// Setup: n = 4 participants; build commitments normally
let mut machines = HashMap::new();
let mut commitment_msgs = HashMap::new();
for i in 1 ..= 4u16 {
  let i = Participant::new(i).unwrap();
  let (machine, msg) = /* ... CommitmentsMachine round ... */;
  commitment_msgs.insert(i, msg);
  machines.insert(i, machine);
}

// Arbitrary third party (or a participant) evaluates blame
let blame_machine = AdditionalBlameMachine::<Ristretto>::new(
  context, 4, commitment_msgs.clone(),
).unwrap();

// Attacker names a recipient that was never registered (e.g. Participant(5))
let bogus = Participant::new(5).unwrap();
let msg: EncryptedMessage<Ristretto, SecretShare<_>> =
  EncryptedMessage::read(&mut real_share_bytes.as_slice(), params).unwrap();

// panics inside decrypt_with_proof at `self.enc_keys[&decryptor]`
blame_machine.blame(Participant::new(1).unwrap(), bogus, msg, Some(proof));

// Equivalently, an unregistered `sender` reaches `self.commitments[&sender]` in
// blame_internal after a validly-PoP-signed message is supplied.
```
Both paths panic on absent `HashMap` entries rather than returning a `PedPoPError`, crashing the blame evaluator.
