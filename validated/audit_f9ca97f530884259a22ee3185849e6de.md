## Finding

### Title
Daemon logs unredacted sensitive request data for unknown commands - ([File: chia/daemon/server.py])

### Summary
The chia daemon's WebSocket message handler redacts sensitive fields (`password`, `key`, `secret`, `mnemonic`, etc.) before logging received message contents at DEBUG level via `redact_sensitive_data()` [1](#0-0) , and this is exercised/verified by `test_message_logging_redaction` [2](#0-1) . However, in `WebSocketServer.handle_message()`, when a client sends a command that is not recognized (`command not in command_mapping`), the daemon logs the **entire raw, unredacted message** — including its `data` payload — at ERROR level, bypassing the redaction path entirely: [3](#0-2) .

### Finding Description
This is analogous to CVE-2018-16876's class of bug: verbose/log-level output that was intended to be safe (no_log/redaction) fails to redact secrets on a specific code path, leaking sensitive parameters into logs. Here, the daemon intentionally redacts sensitive keys before logging inbound messages elsewhere, but the `self.log.error(f"UK>> {message}")` statement logs the full `message` dict — which includes `data` containing whatever fields the client sent — without ever passing through `redact_sensitive_data()`. Since `handle_message` unconditionally routes to this branch for any `command` string not present in `get_command_mapping()` and not in `keychain_commands` [4](#0-3) , any local WebSocket client authenticated via mTLS (a legitimate but unprivileged local RPC caller, e.g. wallet UI or a script using the daemon proxy) can trigger this by sending a bogus/unknown command name along with a `data` payload containing `password`, `private_key`, `mnemonic`, `passphrase`, etc. That payload is written verbatim to the daemon's log file at ERROR level (not gated behind DEBUG logging like the redacted path).

### Impact Explanation
This is an information-disclosure flaw: keyring passphrases, private keys, or mnemonic-derived data sent by a legitimate local caller (or crafted by an unprivileged client that can reach the daemon socket) end up unredacted in persistent log files, which may be read by other local users/processes, backed up, or shipped in support bundles. This does not directly cause coin theft, but matches the "daemon/keychain/RPC authorization" reachable-secrets class explicitly in scope, and mirrors the CVE's exact bug class (redaction/no_log failing on an alternate code path).

### Likelihood Explanation
Any process capable of establishing a daemon WebSocket connection (mTLS-authenticated local client, as used by wallet UI, CLI, or third-party integrations built on `DaemonProxy`) can trivially trigger this by sending any command name that isn't in `get_command_mapping()`/`keychain_commands` along with a `data` dict containing sensitive-looking keys. No special daemon privilege beyond normal local RPC connectivity is required.

### Recommendation
Route the `self.log.error(f"UK>> {message}")` statement through `redact_sensitive_data()` (the same helper already used for the "Received message" debug log), consistent with the rest of the message-logging pipeline, so unknown-command payloads cannot leak secrets.

### Proof of Concept
1. Connect to the daemon WebSocket (mutual-TLS authenticated as any local daemon client).
2. Send a payload via `create_payload()` with an unrecognized `command` (e.g. `"not_a_real_command"`) and `data` containing `{"password": "supersecret", "mnemonic": "word1 word2 ..."}`, destined to `"daemon"`.
3. Since the command doesn't match `get_command_mapping()` or `keychain_commands`, `handle_message()` executes `self.log.error(f"UK>> {message}")`, writing the full unredacted `message` (including `data`) to the daemon log at ERROR level. [3](#0-2) 
4. Inspect the daemon log file — the sensitive fields appear in cleartext, unlike the redacted output produced for the "Received message:" debug log path.

**Note on confidence**: I could not exhaustively trace every logging call-site in the daemon/keychain proxy modules (e.g., `chia/daemon/keychain_proxy.py` line-level detail beyond what was retrieved) due to index/tool limits in this session; a full Devin session with repo access would be needed to confirm there are no other equivalent redaction gaps in that module.

```python
def redact_sensitive_data(obj: Any, redaction_triggers: Collection[str] = ("pass", "key", "secret", "mnemonic")) -> Any:
    """Recursively redact sensitive data from nested dictionaries."""
    if isinstance(obj, dict):
        return {
            key: "***<redacted>***"
            if any(trigger.casefold() in key.casefold() for trigger in redaction_triggers)
            else redact_sensitive_data(value, redaction_triggers)
            for key, value in obj.items()
        }
    else:
        return obj
```
