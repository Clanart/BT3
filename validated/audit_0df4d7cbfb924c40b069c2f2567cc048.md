### Title
Unhandled `bytes32()` length-validation crash when computing memos for an untrusted spend / offer bundle - ([File: chia/wallet/util/compute_memos.py])

### Summary
`compute_memos_for_spend()` builds a `Coin` from the CLVM output of executing a `CoinSpend`'s puzzle, converting the `CREATE_COIN` puzzle-hash argument directly with `bytes32(condition[1])` with no length check. If that argument is not exactly 32 bytes, the `bytes32` constructor raises an uncaught `ValueError`, propagating out of `compute_memos()`/`compute_memos_for_spend()` and crashing whatever wallet flow invoked it. This is the same bug class as CVE-2020-35909 (`multihash::from_slice` panicking on malformed but structurally-valid input instead of returning a `Result` error), applied to Chia's Python-side "trusted shape, untrusted content" hash constructor.

### Finding Description
`compute_memos_for_spend()` in `chia/wallet/util/compute_memos.py` runs a coin spend's puzzle+solution and interprets its output conditions: [1](#0-0) 

Line 20 does:
```python
coin_added = Coin(coin_spend.coin.name(), bytes32(condition[1]), uint64(int_from_bytes(condition[2])))
```
`condition[1]` is the second argument of a `CREATE_COIN` condition returned by executing an attacker-supplied `puzzle_reveal`/`solution` pair. CLVM/ChiaLisp places no consensus-level constraint that this atom be exactly 32 bytes — only full-node condition validation (elsewhere, in Rust) enforces that shape for coins that are actually created on-chain. `compute_memos_for_spend()` is a pure wallet-side helper that executes the puzzle and blindly assumes the second `CREATE_COIN` argument is a well-formed 32-byte puzzle hash. If a coin spend embedded in a wallet-received `SpendBundle`/`Offer` produces a `CREATE_COIN` with a puzzle-hash argument of any other length (e.g., 5 or 40 bytes), `bytes32()` raises `ValueError: 3 not equal to 32` (or similar), and nothing in the call chain catches it.

Since a `CoinSpend`'s `coin.puzzle_hash` only has to match `sha256(bytes(puzzle_reveal))` — a constraint the coin's own owner (the attacker) controls entirely — an attacker can freely author a puzzle that outputs `(CREATE_COIN <arbitrary-length-atom> <amount> ...)` for a coin they own, and place that spend inside a spend bundle or an `Offer` they send to a victim wallet/offer counterparty.

`compute_memos()`/`compute_memos_for_spend()` is called, uncaught, from multiple wallet-side production paths that process externally supplied bundles, including:
- `WalletStateManager.new_outgoing_transaction()` (used when constructing `TransactionRecord`s for spends, including offer-derived spend bundles): [2](#0-1) 
- `ClawbackManager.spend_clawback_coins()` / `ClawbackManager.identify()`: [3](#0-2)  and [4](#0-3) 
- `CRCATWallet.claim_pending_approval_balance()`: [5](#0-4) 
- `chia/wallet/notification_manager.py` (processing incoming notification coin spends)
- `chia/wallet/wallet_rpc_api.py` (RPC caller-facing memo computation)

`Offer` objects are parsed straight from attacker-controlled bytes via `Offer.from_bytes()`/`Offer.from_bech32()` (used by `take_offer`/`respond_to_offer`), which wrap arbitrary `CoinSpend`s from an offer counterparty: [6](#0-5)  and [7](#0-6) .

### Impact Explanation
A malicious offer-counterparty (or spend-bundle sender presented to a victim's wallet for processing, e.g., via a notification coin, a clawback coin, or an offer file) can craft a `CoinSpend` whose puzzle outputs a `CREATE_COIN` condition with a puzzle-hash argument that is not 32 bytes. When the victim's wallet later calls any of the `compute_memos()`-consuming code paths on this bundle (building the outgoing/incoming `TransactionRecord`, claiming a clawback, processing a notification, or finalizing an offer), the wallet process raises an unhandled `ValueError` and the wallet-service coroutine/RPC handler crashes or the affected wallet operation aborts unrecoverably — a spend-triggered halt of wallet transaction processing. This matches the "Reject... no-impact" exclusion boundary only if it were purely local/self-inflicted, but here the malformed data originates from an untrusted counterparty (offer/notification/clawback sender), making it a remotely triggerable DoS against another user's wallet — analogous in class and severity to the multihash `from_slice` panic causing DoS in networking code that "trusted" a `Result`-returning API.

### Likelihood Explanation
Likelihood is high: constructing a puzzle whose solution yields `CREATE_COIN` with a non-32-byte second argument requires no signature forgery, no special privilege, and no violation of consensus rules — CLVM allows arbitrary atom sizes in condition arguments, and only the coin's own puzzle_hash needs to match, which the attacker controls for their own coin. An attacker only needs to get such a spend into a bundle the victim wallet will call `compute_memos()` on — e.g. by sending a crafted offer file, a notification coin, or a spend that becomes part of a wallet-observed transaction.

### Recommendation
Harden `compute_memos_for_spend()` (chia/wallet/util/compute_memos.py) to validate the length of `condition[1]` before constructing `bytes32`, and to skip/ignore malformed `CREATE_COIN` conditions instead of raising, mirroring how full-node condition parsing tolerates malformed atoms. Wrap the `bytes32(...)` conversion (and the `int_from_bytes` call, which can also throw on oversized amount atoms) in a `try/except (ValueError, TypeError)` that simply `continue`s to the next condition, and add regression tests exercising `CREATE_COIN` conditions with puzzle-hash atoms of length 0, 31, and 33+ bytes fed through every call site (`WalletStateManager.new_outgoing_transaction`, `ClawbackManager`, `CRCATWallet`, `notification_manager`, and offer processing).

### Proof of Concept
1. Craft a coin whose puzzle is: `(mod (amount) (list (list CREATE_COIN <arbitrary-length-atom> amount)))`, curried/solved so it is a valid, self-consistent `CoinSpend` (puzzle_reveal hash matches coin.puzzle_hash) for a coin the attacker owns.
2. Package this `CoinSpend` inside a `SpendBundle`/`Offer` and send it to a victim (e.g., as an offer file via `take_offer`, or as a notification coin spend).
3. When the victim wallet processes the bundle and calls `compute_memos(bundle)` (e.g. inside `WalletStateManager.new_outgoing_transaction`, `ClawbackManager.identify`/`spend_clawback_coins`, `CRCATWallet.claim_pending_approval_balance`, or `notification_manager`), `compute_memos_for_spend()` executes:
   ```python
   coin_added = Coin(coin_spend.coin.name(), bytes32(condition[1]), uint64(int_from_bytes(condition[2])))
   ```
   Since `condition[1]` is not 32 bytes, this raises `ValueError`, uncaught anywhere in the call chain, aborting the wallet operation/RPC call that was processing the untrusted spend.

Note: I was not able to fully trace every downstream caller (e.g., whether `trade_manager.py`'s offer-finalization path calls `compute_memos` indirectly through `new_outgoing_transaction`/`WalletActionScope` side effects) within the available search budget; the exact reachable call path from `respond_to_offer`/`take_offer` to `compute_memos` should be confirmed against the live source before finalizing severity, but the vulnerable function itself and several concrete, untrusted-input-reachable callers (clawback, CR-CAT claim, notifications) are confirmed directly.

```python
def compute_memos_for_spend(coin_spend: CoinSpend) -> dict[bytes32, list[bytes]]:
    _, result = run_with_cost(coin_spend.puzzle_reveal, INFINITE_COST, coin_spend.solution)
    memos: dict[bytes32, list[bytes]] = {}
    for condition in result.as_python():
        if condition[0] == ConditionOpcode.CREATE_COIN and len(condition) >= 4:
            # If only 3 elements (opcode + 2 args), there is no memo, this is ph, amount
            coin_added = Coin(coin_spend.coin.name(), bytes32(condition[1]), uint64(int_from_bytes(condition[2])))
            if type(condition[3]) is not list:
                # If it's not a list, it's not the correct format
                continue
            memos[coin_added.name()] = [mem for mem in condition[3] if isinstance(mem, bytes)]
    return memos
```
