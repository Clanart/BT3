### Title
SSRF via unvalidated on-chain mirror URLs fetched by Data Layer clients - ([File: chia/data_layer/data_layer.py])

### Summary
Chia DataLayer mirrors let any user attach an arbitrary URL to a store's on-chain mirror record. Any node that subscribes/tracks that store later has its DataLayer service fetch that URL with plain HTTP requests, with no scheme, host, or destination validation — the same bug class as CVE-2026-55976 (Hive `avro.schema.url` SSRF): an authenticated but otherwise unprivileged actor sets a URL that is later resolved server-side, causing the victim's process to make outbound requests to attacker-chosen destinations (cloud metadata, internal services, or local endpoints reachable via HTTP).

### Finding Description
DataLayer's sync loop reads mirror URLs discovered through the wallet (on-chain mirror coins) and stores them as `ServerInfo` records for a given `store_id` [1](#0-0) . `fetch_and_validate()` then iterates these `servers_info` entries and, for each, calls `insert_from_delta_file()` → `download_file()` → `http_download()`, issuing an `aiohttp` GET to `server_info.url + "/" + filename` with no restriction on the URL's host, port, or destination [2](#0-1) .

`http_download()` performs the raw request: [3](#0-2) 

There is no allow-list of hosts/schemes, no rejection of loopback/link-local/private ranges, and no restriction that the URL must match a previously-trusted mirror registered by the store owner locally. `subscribe()` itself also accepts an arbitrary list of URLs directly from the RPC caller without validation [4](#0-3) , and mirror URLs are explicitly documented as untrusted external inputs that must not be trusted as data sources — but that guidance only covers *data* trust (verified later against wallet roots), not the *SSRF surface* of the fetch itself [5](#0-4) .

Because any store can register mirror coins with attacker-chosen URLs, and any other node that later starts tracking/subscribing to that store (a routine Data Layer client action such as `dl_track_new`/`subscribe`) will have its DataLayer service reach out to that URL during the periodic `fetch_and_validate()` cycle, this is directly analogous to Hive resolving `avro.schema.url` when a table is queried: the URL is attacker-supplied at "table/mirror creation" time and fetched later by the victim's server process at "query/sync" time.

### Impact Explanation
An attacker can cause a victim's DataLayer node to issue outbound HTTP requests to arbitrary internal or cloud-metadata endpoints (e.g. `http://169.254.169.254/...`, internal admin services, or other local network services reachable via HTTP), potentially exfiltrating instance credentials/metadata or probing/attacking internal infrastructure from the victim's server identity. This matches the CVE's Confidentiality-only impact profile (network reconnaissance / metadata exposure) rather than direct fund loss, but it is a legitimate remote-triggerable server-side request forgery inside a component (`chia/data_layer/`) reachable by ordinary Data Layer client actions (subscribe/track a store).

### Likelihood Explanation
Any user can create a mirror for a store id (their own or one they track) with an arbitrary URL, and any peer who subscribes to or tracks that store id will periodically execute `fetch_and_validate()`, unconditionally issuing HTTP requests to that URL. No special privileges beyond normal DataLayer usage (creating a store/mirror, or another node choosing to track/subscribe to a store) are required, making this readily reachable in normal DataLayer operation.

### Recommendation
- Validate and restrict mirror/subscription URLs before they are ever passed to `aiohttp` in `http_download()`/`download_file()`/`get_downloader()`/`get_uploaders()`: enforce `http`/`https` scheme only, reject loopback/link-local/private/multicast/metadata-service address ranges (with DNS-rebind protection, i.e. resolve and check the IP, not just the hostname), and consider an explicit user-configured allow-list or opt-in flag for connecting to non-public endpoints.
- Apply the same validation both to URLs learned from on-chain mirror records (`update_subscription`'s wallet-mirror sync step) and to URLs supplied directly through the `subscribe`/`DLNewMirror` RPC endpoints.

### Proof of Concept
1. Attacker creates a DataLayer store and adds a mirror URL of `http://169.254.169.254/latest/meta-data/iam/security-credentials/` (or any internal victim-reachable host) via the standard mirror-creation flow.
2. A victim node begins tracking/subscribing to the attacker's store id (a normal DataLayer client action, e.g. via `dl_track_new`/`subscribe`).
3. During the victim's periodic `periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()` cycle, the victim's DataLayer service performs an HTTP GET to the attacker-controlled URL via `http_download()` [3](#0-2) , with no destination validation, forcing an SSRF request from the victim's server identity.

    async def subscribe(self, store_id: bytes32, urls: list[str]) -> Subscription:
        parsed_urls = [url.rstrip("/") for url in urls]
        subscription = Subscription(store_id, [ServerInfo(url, 0, 0) for url in parsed_urls])
        await self.wallet_rpc.dl_track_new(DLTrackNew(launcher_id=subscription.store_id))
        async with self.subscription_lock:
            await self.data_store.subscribe(subscription)
        self.log.info(f"Done adding subscription: {subscription.store_id}")
        return subscription

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
