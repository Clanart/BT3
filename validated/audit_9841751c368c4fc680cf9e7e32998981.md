Based on my investigation, the most concrete Desktop analog to the "hardcoded/enforced value that skips proper validation across a trust boundary" bug class is in the deep-link (`x-github-client://openRepo/...`) branch-name validation, where the sanitization regex used to gate an attacker-controlled string does not actually block the one character class (`-`) that git's argument parser treats specially.

### Title
Deep-link `branch` parameter validation omits leading-dash rejection, allowing git argument injection via `parseAppURL` - (File: `app/src/lib/parse-app-url.ts`, `app/src/lib/sanitize-ref-name.ts`)

### Summary
`parseAppURL` (`app/src/lib/parse-app-url.ts:98-125`) accepts an `openRepo` protocol action from any `x-github-client://` deep link (clickable from any web page, README, or issue) and extracts a caller-supplied `branch` query parameter. Before accepting it, it only calls `testForInvalidChars(branch)` [1](#0-0) , which is backed by `invalidCharacterRegex` in `app/src/lib/sanitize-ref-name.ts` [2](#0-1) . That regex blocks control characters, spaces, `~^:?*[\|"<>`, `@{`, consecutive dots, leading/trailing dots, `.lock` suffix, and trailing `/` — but it does **not** reject a leading `-`. A value like `--upload-pack=...` or any other dash-prefixed string therefore passes validation unchanged and is forwarded as `IOpenRepositoryFromURLAction.branch` to the dispatcher, which later calls `checkoutLocalBranch(repository, branchName)` (`app/src/ui/dispatcher/dispatcher.ts:1975-1996`) [3](#0-2) .

### Finding Description
The broken invariant mirrors the `UnstakeMessenger` bug's shape: a value that crosses a trust boundary (attacker-supplied deep-link query string) is treated as if it were already a "safe branch name" because a validation function exists — but that validation function's allow-list/deny-list does not actually cover the property the downstream consumer relies on. In `UnstakeMessenger`, the assumption was "sender address == recipient address," which fails for AA/multisig wallets. Here, the assumption is "`testForInvalidChars` returning false means safe ref name," which fails for any string beginning with `-`, since git's argument parser (used transitively by whatever git subprocess call ultimately consumes this string) treats a leading `-` as the start of a flag rather than a positional ref argument. This class of "ref/branch name interpreted as a CLI flag" is the same primitive behind several historical Git/GitHub-Desktop advisories (e.g. malicious branch/tag/submodule names smuggling `--upload-pack=`, `-o`, or similar flags into a git invocation).

I was not able to fully trace, within the remaining tool budget, the exact `git` binary invocation inside `checkoutLocalBranch` / `checkoutBranch` in `dispatcher.ts` to confirm whether Desktop's git wrapper inserts a `--` separator before the ref argument in every code path reachable from this action. That is the remaining unverified link in the chain — if the wrapper does insert `--` (or invokes git with an array where the ref is passed after a separator), the injection is neutralized at that layer instead. What is verified is that the input-sanitization layer at the deep-link boundary (`parseAppURL`/`testForInvalidChars`) does not reject leading-dash strings, so any protection is fully dependent on a downstream layer the report could not confirm.

### Impact Explanation
If any downstream git invocation triggered by `checkoutLocalBranch`/`_findPullRequestBranch`/`checkoutBranch` passes the attacker-controlled branch string as a bare positional argument without a `--` separator, an attacker who gets a victim to click a crafted `x-github-client://openRepo/<repo-url>?branch=--upload-pack%3D<payload>` link could inject a git CLI flag, potentially achieving command execution or corrupting the local checkout state — squarely in the "attacker controls a link the user clicks" → "code execution / silent corruption of what the user commits" impact category named in scope.

### Likelihood Explanation
Likelihood depends entirely on the unverified downstream git call. Given that: (1) the deep-link protocol is registered app-wide and triggerable from any external link with no user warning about destination, (2) the validation regex is provably incomplete (dash omission is a one-line, easily demonstrable gap), and (3) this exact bug class (ref names as flag smuggling) has recurring precedent in git tooling, likelihood is plausible but not proven without confirming the exact git subprocess call signature used by `checkoutLocalBranch`.

### Recommendation
Add an explicit check in `testForInvalidChars` (or a new guard applied specifically at the `parseAppURL` boundary) that rejects any `branch` value beginning with `-`, mirroring the leading-dash stripping already done defensively in `sanitizedRefName` (`app/src/lib/sanitize-ref-name.ts:10`) but which is not applied to the validation predicate used to accept/reject deep-link input. Additionally, audit every git subprocess invocation that ultimately consumes `IOpenRepositoryFromURLAction.branch` to confirm a `--` separator (or equivalent safe-argument boundary) always precedes the ref argument, regardless of validation at the parsing layer, so the two layers are not each other's only defense (defense-in-depth), analogous to how the original report recommends never letting a single implicit assumption (address symmetry) be the sole safeguard.

### Proof of Concept
Not independently executed against a running Desktop build within this session (no filesystem/terminal access). Conceptual PoC: `parseAppURL('x-github-client://openrepo/https://github.com/some/repo?branch=--upload-pack%3D%2Ftmp%2Fpayload')` returns `{ name: 'open-repository-from-url', branch: '--upload-pack=/tmp/payload', ... }` because `testForInvalidChars('--upload-pack=/tmp/payload')` evaluates to `false` against `invalidCharacterRegex` [4](#0-3) , confirming the value is accepted unmodified and passed to `openBranchNameFromUrl`/`checkoutLocalBranch` [3](#0-2) . Full exploitation (confirming RCE) requires tracing the exact `git` argv construction in the checkout code path, which was not completed.

// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}
