### Title
Untrusted `ReceivedOutput` bytes bypass scanner authorization and manufacture unspendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput` represents a spendable Bitcoin output, but `ReceivedOutput::read` deserializes its `offset`, `TxOut`, and `OutPoint` independently without proving that the output belongs to the wallet key or that the outpoint actually references the supplied output. The protected construction path, `Scanner::scan_transaction`, only creates a `ReceivedOutput` when the transaction output's `script_pubkey` matches a registered key offset. The public deserialization path lacks that authorization and consistency check.

### Finding Description
`Scanner` maintains a private mapping from authorized Taproot scripts to scalar offsets. `Scanner::scan_transaction` only creates a `ReceivedOutput` when `self.scripts` contains the output's `script_pubkey`, thereby binding the stored offset to the wallet's public key and to an actual transaction output. [1](#0-0) [2](#0-1) 

`ReceivedOutput::read` provides a sibling construction path for the same security-sensitive object. It accepts an arbitrary scalar from `Secp256k1::read_F`, then independently consensus-decodes an arbitrary `TxOut` and `OutPoint`, returning all three as a `ReceivedOutput`. [3](#0-2) 

No wallet public key is supplied to `read`, and it never checks:

```text
p2tr_script_buf(wallet_key + GENERATOR * offset) == output.script_pubkey
```

It also never checks that `outpoint` resolves on-chain to the supplied `TxOut`. Consequently, malformed serialized bytes can produce an object whose API contract says it is “a spendable output,” even though no such spendable output exists. [4](#0-3) 

Downstream, `SignableTransaction::new` trusts the deserialized output's value, script, outpoint, and offset to construct inputs and calculate available funds. [5](#0-4)  `SignableTransaction::multisig` only verifies that the supplied offset derives the supplied `script_pubkey`; it does not verify that the supplied `TxOut` is the actual output at the supplied `OutPoint`. [6](#0-5) 

### Impact Explanation
An unprivileged party who can provide serialized `ReceivedOutput` bytes can cause Serai to report or treat funds as received when they are not spendable. They can:

- Reference a nonexistent or already-spent `OutPoint`.
- Pair an existing outpoint with a fabricated `TxOut`.
- Pair a victim's output with an unrelated offset.
- Fabricate a Taproot script for `wallet_key + offset * G`, making the output internally consistent while the referenced outpoint is absent or belongs to a different output.

Any balance accounting based on `ReceivedOutput::value` can be inflated arbitrarily because it returns the attacker-controlled `TxOut` value. [7](#0-6)  If passed to transaction construction, the forged input is used in funding and fee calculations and can result in an invalid consensus transaction being signed, or the forged object can remain recorded as spendable inventory. [5](#0-4) 

This maps to the reported bug class: the ordinary protected route enforces membership/authorization, while the alternate construction route exposes the same privileged result without enforcing the invariant.

### Likelihood Explanation
The vulnerable input is entirely public and unauthenticated: an attacker only needs to control serialized `ReceivedOutput` bytes consumed by an integrator or service. They do not need validator access, private keys, threshold collusion, malicious peers, leaked shares, or an invalid curve implementation.

Constructing an internally accepted forged output is practical when the target Taproot group key is known. The attacker selects a scalar offset and derives the matching P2TR script for `key + offset * G`, then serializes that script with a chosen amount and arbitrary outpoint. The later `multisig` check accepts that relationship because it compares the offset-derived script to the attacker-supplied `TxOut`, not to a confirmed blockchain output. [8](#0-7) 

### Recommendation
Remove unauthenticated standalone construction of `ReceivedOutput`, or make deserialization invariant-preserving.

Prefer an API such as:

```rust
ReceivedOutput::read(reader, scanner_or_wallet_key)
```

which validates that:

1. `offset` is registered or securely derived for the wallet key.
2. `p2tr_script_buf(wallet_key + GENERATOR * offset)` equals `output.script_pubkey`.
3. `outpoint` resolves to a confirmed transaction output equal to the supplied `TxOut`.
4. Coinbase immaturity and required confirmation depth are checked before reporting the output as spendable.

Alternatively, serialize an authenticated scanner proof or transaction context with the output and verify it during deserialization. At minimum, `read` must not create a `ReceivedOutput` for arbitrary `offset`, `TxOut`, and `OutPoint` triples.

### Proof of Concept
Conceptually, for a known wallet key `K`:

```rust
let offset = Scalar::ONE;
let forged_script =
  p2tr_script_buf(K + (ProjectivePoint::GENERATOR * offset)).unwrap();

let forged_txout = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: forged_script,
};

// Any nonexistent, spent, or unrelated UTXO.
let forged_outpoint = OutPoint {
  txid: chosen_txid,
  vout: 0,
};
```

Serialize these fields in the format expected by `ReceivedOutput::read`:

```text
offset || consensus_serialize(forged_txout) || consensus_serialize(forged_outpoint)
```

Feeding those bytes to `ReceivedOutput::read` succeeds, despite the claimed outpoint not necessarily containing the supplied output. [3](#0-2)  Calling `value()` reports `100_000` satoshis, and passing the object into `SignableTransaction::new` treats it as available input value. [5](#0-4)  `multisig` accepts the internally crafted key/script relationship and proceeds to create per-input signing machines, even though the referenced UTXO may not exist. [9](#0-8)

    let offset = Secp256k1::read_F(r)?;
    let output;
