## Finding

### Title
Stale hardcoded `STATE_COMMITMENT_SLOT` constant no longer matches `EvmHost`'s actual storage layout - ([File: modules/ismp/state-machines/evm/src/utils.rs], [File: tesseract/messaging/evm/src/lib.rs])

### Summary
The reported Blast.sol bug is a hardcoded constant (a token address) that no longer matches the real on-chain value it is supposed to mirror. The same bug class exists in Hyperbridge: the Rust-side constant `STATE_COMMITMENT_SLOT = 5`, hardcoded independently in two places to mirror `EvmHost`'s Solidity storage layout, no longer matches the actual slot index of `_stateCommitments` in the current `EvmHost.sol`.

### Finding Description
`evm/src/core/EvmHost.sol` declares its storage in this order: [1](#0-0) 

Counting slots as currently declared: `_requestCommitments` = slot 0, `_requestReceipts` = slot 1, `_responseReceipts` = slot 2, `_stateCommitments` = slot 3, `_stateCommitmentsUpdateTime` = slot 4, `_latestStateMachineHeight` = slot 5, `_vetoes` = slot 6, then `_hostParams`.

However, the off-chain/pallet code that derives the storage key for `_stateCommitments` hardcodes slot `5`, not `3`: [2](#0-1) [3](#0-2) 

Slot 5 in the current layout is `_latestStateMachineHeight` (a plain `mapping(uint256 => uint256)`), not the `mapping(uint256 => mapping(uint256 => StateCommitment))` that `_stateCommitments` actually is. This is the same class of defect as the reported Blast.sol issue: a hardcoded value meant to mirror a fixed on-chain layout/address has drifted out of sync with the real contract. The sibling constant `REQUEST_RECEIPTS_SLOT` was explicitly re-verified and documented after `_responseCommitments` was removed in PR #840: [4](#0-3) 
but `STATE_COMMITMENT_SLOT` carries no equivalent verification note and was not updated to reflect the same slot shift, indicating it is stale relative to the post-PR-#840 layout.

### Impact Explanation
Any consumer of `state_comitment_key` (which derives the trie key used to fetch/prove `overlayRoot`/`stateRoot`/`timestamp` for a given `(stateMachineId, height)` pair from a destination `EvmHost`) is querying the wrong storage slot. Instead of reading the genuine `StateCommitment` struct, the derived key resolves to `_latestStateMachineHeight`'s storage, whose raw bytes get reinterpreted as `timestamp`/`overlayRoot`/`stateRoot` offsets. This breaks the invariant that state-commitment proofs reflect real, protocol-verified commitments, since the "commitment" fields being checked no longer correspond to the actual `_stateCommitments` mapping populated by consensus updates.

### Likelihood Explanation
This is a deterministic, always-triggered mismatch (not conditional on attacker behavior) — every call site using `STATE_COMMITMENT_SLOT` is affected identically since the constant is wrong for the whole contract, not a value that can vary between chains. The severity depends on exactly how far downstream this constant flows into fund-moving or acceptance logic, which limits full certainty of impact without deeper tracing of every call site, but the constant itself is demonstrably desynchronized from the current, in-repo `EvmHost.sol` layout, mirroring precisely the "misconfigured hardcoded constant" bug class reported for Blast.sol.

### Recommendation
Re-derive `STATE_COMMITMENT_SLOT` (and any other hardcoded EVM storage-slot constants used for cross-chain proof key derivation) directly from `forge inspect EvmHost storage` after every change to `EvmHost.sol`'s storage layout, exactly as already documented for `REQUEST_RECEIPTS_SLOT`/`REQUEST_COMMITMENTS_SLOT` in `presets.rs`. Consider centralizing all such slot constants in one location with a CI check that fails the build if `forge inspect` output diverges from the hardcoded values, preventing this exact drift from recurring.

### Proof of Concept
Not applicable as an executable PoC — the issue is a static layout-constant mismatch, demonstrated by comparing the declared storage order in `evm/src/core/EvmHost.sol` lines 117–145 (yielding slot 3 for `_stateCommitments`) against the hardcoded `STATE_COMMITMENT_SLOT = 5` in `modules/ismp/state-machines/evm/src/utils.rs` line 218 and `tesseract/messaging/evm/src/lib.rs` line 594.
