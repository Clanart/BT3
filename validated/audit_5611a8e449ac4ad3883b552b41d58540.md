### Title
Missing-participant panic in `GeneratorPromotion::complete` via attacker-controlled proof map - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the *length* and *upper bound* of the `proofs` map it receives, then unconditionally calls `proofs.get(&i).unwrap()` for every participant index `1..=n` other than itself. A malicious peer can supply a `HashMap<Participant, GeneratorProof>` that has the required `n - 1` entries, all with keys `<= n`, but that includes the local participant's own index (or otherwise omits a required index). The lookup then returns `None` and the `unwrap()` panics — a crafted-input null-dereference-class denial of service, directly analogous to CVE-2017-14926.

### Finding Description
In `complete`, the only validation of the received proofs is:

- `proofs.len() == params.n() - 1` (line 125)
- every key `i` satisfies `u16::from(i) <= params.n()` (lines 132–136) [1](#0-0) 

There is no check that the map does *not* contain the local participant `params.i()`, and no check that the key set equals `{1..=n} \ {params.i()}`. The subsequent loop iterates all `i in 1..= params.n()`, skips only `params.i()`, and does `proofs.get(&i).unwrap()` (line 146). [2](#0-1) 

A `Participant` key equal to `params.i()` is admissible under both checks, so an attacker can build a map whose keys are `{params.i(), ...}` while omitting some other participant `j`. When the loop reaches `j`, `proofs.get(&j)` is `None` and the node panics inside library code — unrecoverable via the `Result<_, PromotionError>` API.

The attacker-controlled input is reachable through normal deserialization: each `GeneratorProof` is parsed with `GeneratorProof::read`, which is just `C::read_G(reader)` plus `DLEqProof::read(reader)` [3](#0-2) , both listed untrusted-byte entry points, and `complete` is a listed reachable API. No valid proof is needed — the panic occurs before `proof.verify` is even reached for the missing index.

### Impact Explanation
Any participant in a generator-promotion round can crash the local process handling `complete` by sending a malformed proof set. Because the panic occurs inside `crypto/dkg/promote` (not behind a `catch_unwind` or error variant), the calling processor/thread aborts its promotion flow, denying availability of the key-promotion/rotation procedure. Repeated submissions re-trigger the crash on each retry. This is a liveness/availability failure caused purely by untrusted wire input, matching the CVE's NULL-deref-via-crafted-document class (crafted input → unconditional dereference of an absent value → crash).

### Likelihood Explanation
Triggering requires only that the attacker be a participant (or able to submit a `GeneratorProof` keyed under an arbitrary `Participant` index) in a promotion session — an unprivileged, public-input reach. The crafted map is trivial to build: take any `n - 1` validly-encoded `GeneratorProof` blobs (even garbage that would fail verification) and key one of them as the victim's own index instead of the missing participant's. No valid DLEq proof, signature, or secret knowledge is required, since deserialization (`read_G`, `DLEqProof::read`) accepts any canonically-encoded points and the panic precedes proof verification for the omitted index.

### Recommendation
Replace the unconditional `proofs.get(&i).unwrap()` with a checked lookup returning `PromotionError`, e.g.:

```rust
let proof = proofs
  .get(&i)
  .ok_or(PromotionError::IncorrectAmountOfParticipants {
    t: params.n(), n: params.n(), amount: proofs.len(),
  })?;
```

Additionally, reject maps containing `params.i()` as a key during the initial key-validation loop, so the key set is verified to be exactly `{1..=n} \ {params.i()}` before any lookups. This converts the panic into a normal error path consistent with the rest of the function's `Result`-based API.

### Proof of Concept
Conceptual, for `n = 3`, local participant `i = 1`:

```rust
// Attacker is participant 2. Instead of keying their proof under
// Participant(2) and letting participant 3 send theirs, the attacker
// builds the map the victim will pass to `complete` as:
//
//   proofs = { Participant(1): proof_a, Participant(2): proof_b }
//
// proofs.len() == 2 == n - 1              -> passes line 125 check
// all keys <= n (1 and 2 <= 3)            -> passes lines 132-136
//
// In complete():
//   i = 1 == params.i() -> skipped
//   i = 2 -> proofs.get(&Participant(2)) -> Some, verify runs
//   i = 3 -> proofs.get(&Participant(3)) -> None -> unwrap() PANICS
//
// proof_a / proof_b can be arbitrary bytes accepted by
// GeneratorProof::read (any canonical points + any DLEqProof encoding);
// no valid proof is needed to reach the panic.
```

The panic occurs at `proofs.get(&i).unwrap()` (crypto/dkg/promote/src/lib.rs:146), aborting the promotion instead of returning a `PromotionError`.
