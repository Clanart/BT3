## Analysis

The StakeWise bug is a classic **"security classification enforced through a strict check on one path, but derived from an untrusted/attacker-influenced heuristic on another path"** — the whitelist gate (`deposit`) uses a strict per-address mapping, but the `transfer` path never re-checks it, letting an attacker end up in a privileged state (holding shares) without ever passing the real gate.

A structurally identical pattern exists in GitHub Desktop's Git credential-helper trampoline, where the classification of a remote host as a "GitHub" endpoint is done two different ways: a strict one (hostname/suffix match against `github.com`/`api.github.com`/`*.ghe.com`) and a **weak heuristic one, driven entirely by a header value the remote server itself supplies** — with no cryptographic or configuration-based trust anchor. [1](#0-0) 

### Broken invariant

`getEndpointKind()` is supposed to determine whether a remote endpoint is a legitimate GitHub product (dotcom/GHE) so that Desktop knows whether to auto-fill an internally stored account token, or treat it as a generic/unknown host. For known hosts it correctly does a hostname/suffix comparison, but as a fallback it trusts the `WWW-Authenticate` header forwarded by Git from the remote HTTP server: [2](#0-1) 

If a Git server (any HTTPS remote the user is fetching/cloning/pushing to) answers a request with `WWW-Authenticate: realm="GitHub"`, this function classifies that arbitrary attacker-controlled host as `'enterprise'` — i.e. "a real GitHub Enterprise instance" — purely from the response text, without any actual verification (no cert pinning, no ownership check, no user-configured trust the way `.ghe.com` suffix or a previously signed-in Account's origin would provide).

### Downstream consequence

That misclassification feeds directly into `getCredential()`, which — because the fabricated "enterprise" endpoint has no matching signed-in `Account` — triggers a full GitHub Enterprise sign-in flow against the attacker's own host: [3](#0-2) 

That sign-in flow opens the OAuth authorize page at the attacker's endpoint in the user's browser: [4](#0-3) 

and, once a `code`/`state` pair is returned via the `x-github-client://oauth` deep link (the attacker's own page can trivially read `state` from the very authorize URL Desktop opened and echo it back), Desktop validates only that the state matches and then POSTs the app's OAuth `client_id`/`client_secret` to the **attacker-controlled host** to exchange the code for a token: [5](#0-4) [6](#0-5) 

### Why existing guards don't stop this

- The strict hostname checks (`isDotCom`, `isGHE`) only protect the *known-good* hosts; they provide no negative check preventing an *arbitrary* host from being promoted to `'enterprise'` via the `wwwauth[]` fallback.
- `findGitHubTrampolineAccount` matching by origin is safe when an account already exists, but it is never consulted to *reject* the wwwauth-based classification when no account exists — the same asymmetry as the Solidity bug (whitelist enforced on `deposit`, not on `transfer`).
- `validateURL()` used later in `setEndpoint()` only enforces HTTPS, which the attacker already satisfies since Git only forwards WWW-Authenticate headers for HTTPS remotes.

### Title
Attacker-controlled `WWW-Authenticate` header on a Git remote spoofs "GitHub Enterprise" classification, triggering OAuth flow and exfiltrating Desktop's OAuth client secret to the attacker's host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
GitHub Desktop's Git credential-helper trampoline classifies a Git remote as a legitimate "GitHub"/"enterprise" endpoint if the remote HTTPS server merely responds with a `WWW-Authenticate: realm="GitHub"` header, with no other verification. This misclassification can be triggered by any HTTPS remote the user interacts with (clone/fetch/push), leading Desktop to launch its Enterprise OAuth sign-in flow against that attacker-controlled host, ultimately sending the app's OAuth `client_id`/`client_secret` to the attacker when exchanging the authorization code.

### Finding Description
`getEndpointKind()` uses a fallback heuristic that trusts the `wwwauth[...]` credential fields Git forwards from the HTTP response of the remote it's talking to: [7](#0-6) 
Unlike the hostname-based checks (`isDotCom`, `isGHE`), this branch has no relationship to any trusted, user-controlled value — it is 100% attacker-supplied content from the server response for a repository the user is interacting with. Once classified as `'enterprise'`, and since no `Account` exists yet for that host, `getCredential()` invokes `ui.promptForGitHubSignIn(endpoint)`, entering the normal Enterprise sign-in path with `endpoint` equal to the attacker's URL. That path opens the OAuth "authorize" URL on the attacker's server in the system browser and, upon receiving a `code`/`state` pair back through the app's registered `x-github-client://oauth` handler, POSTs the hard-coded Desktop `client_id`/`client_secret` to the attacker's `/login/oauth/access_token` endpoint to complete the exchange.

### Impact Explanation
This satisfies the "unauthorized OAuth" and "credential/token exfiltration" impact categories: the app's OAuth client secret is sent to a host the attacker fully controls (via a git remote/proxy response), and the attacker can also feed back an arbitrary "access_token" that Desktop will store as the user's Enterprise credential and subsequently use in Git operations, and could couple this with a convincing phishing page at the "authorize" URL to harvest actual GitHub credentials from the user, believing they're signing into a legitimate GitHub Enterprise prompt initiated by Desktop.

### Likelihood Explanation
No local access, malware, or leaked credentials are required — only an attacker-controlled or MITM'd HTTPS Git server that the victim clones/fetches/pushes to, and a crafted `WWW-Authenticate` response header, both fully within a remote server operator's control.

### Recommendation
Remove or drastically restrict the `wwwauth[]` realm-sniffing heuristic in `getEndpointKind()` — it should never be sufficient, on its own, to classify an arbitrary host as `'enterprise'` for the purposes of initiating a privileged sign-in/credential-fill flow. At minimum, require corroborating evidence (e.g., a successful `x-github-request-id`/version header check via `isGitHubHost()`, which already exists further down) rather than trusting a single spoofable header value.

### Proof of Concept
1. Attacker stands up an HTTPS git server (or a MITM proxy in front of one) that responds to unauthenticated Git HTTP requests with `WWW-Authenticate: realm="GitHub"`.
2. Victim adds this URL as a remote (or clones it) in GitHub Desktop and performs a fetch/push.
3. Git forwards the header to Desktop's credential helper as `wwwauth[0]=...realm="GitHub"...`; `getEndpointKind()` returns `'enterprise'` for the attacker's host.
4. Because no `Account` matches this host, Desktop calls `promptForGitHubSignIn(endpoint)`, opening `<attacker-host>/login/oauth/authorize?client_id=<DESKTOP_CLIENT_ID>&...` in the browser.
5. Attacker's page immediately redirects to `x-github-client://oauth?code=<anything>&state=<csrfToken-read-from-query>`.
6. Desktop's `resolveOAuthRequest` accepts the matching state and calls `requestOAuthToken(endpoint, code)`, POSTing `client_id`/`client_secret` to `<attacker-host>/login/oauth/access_token` — exfiltrating Desktop's OAuth secret and allowing the attacker to return an arbitrary token that Desktop treats as a valid signed-in account for that host.

async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)

    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}

      return
    }

      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
