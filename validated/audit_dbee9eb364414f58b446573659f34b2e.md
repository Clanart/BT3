### Title
Gasless swap admission relies on manipulable AMM spot-price (`getAmountIn`), enabling reserve-donation price manipulation analogous to the Uwerx skim/sync attack - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
The `kaiax/gasless` module (KIP-247) lets an unprivileged, gas-less user submit a `SwapForGas` transaction that is priced using the live reserves of the underlying DEX pool for the token being swapped, exactly the class of on-chain "spot price from mutable reserves" oracle that the Uwerx/WERX attacker exploited via `skim()`/`sync()` reserve manipulation before extracting value.

### Finding Description
`checkBalanceForSwap` in `kaiax/gasless/impl/tx_pool.go` validates a `GaslessSwapTx` before admitting it to the pool by calling the on-chain `GaslessSwapRouter.GetAmountIn(token, minAmountOut)`: [1](#0-0) . This routes into the underlying Uniswap-V2-style router's pure `getAmountIn(amountOut, reserveIn, reserveOut)` pricing function, whose inputs are the pool's *live, mutable* `reserve0`/`reserve1` state [2](#0-1) . In the Uniswap V2 design (and in the Uwerx incident), these reserves can be desynchronized from actual token balances via `skim()` (extracting any balance surplus not reflected in reserves) and `sync()` (forcing reserves to match the current, possibly-manipulated, balance) — this is precisely the mechanism SlowMist attributed the WERX loss to.

Because the admission check (`ShouldCheckSwapAmount` / `BalanceCheckLevelSwapAmount`, default `BalanceCheckLevelAll`) and the eventual on-chain settlement both derive from the same reserve-based price source [3](#0-2) , an attacker who can influence a target token's pool reserves (e.g., a fee-on-transfer/deflationary token where `to == pair` burns extra supply, as in Uwerx) can distort the reported `amountIn` requirement relative to the actual settlement outcome of `swapForGas`.

### Impact Explanation
If the manipulated price passes the mempool's `insufficient amountIn` check [1](#0-0)  while the actual settlement (proposer-lent gas repayment via `LendTxGenerator`/`repayAmount`) [4](#0-3)  is computed against a distorted reserve state, the attacker can under-repay the proposer's lent gas fee or extract more output token/WKAIA than the true market rate — a concrete fee-delegation/gasless-settlement theft matching the required impact class.

### Likelihood Explanation
Medium. This requires (1) the target token being present in the allowed gasless token set, and (2) the token/pool exhibiting a skim/sync-exploitable reserve-balance mismatch (e.g., a deflationary transfer-tax token as in the original Uwerx case). I could not verify from the indexed Go bindings alone whether `GaslessSwapRouter`'s Solidity source enforces additional slippage/reserve-freshness protections at settlement time, or whether token admission (`addToken`) is owner-gated — the `.sol` source was not present in the index, only compiled bindings.

### Recommendation
- Do not rely on instantaneous AMM reserves (`getAmountIn`/`getAmountsOut`) as the sole price source for both admission and settlement of gasless swaps; use TWAP or a reserve-freshness/sanity check (e.g., compare against `sync()` timestamp or bound acceptable reserve deltas).
- Add slippage protection in `swapForGas` settlement independent from the mempool-time `GetAmountIn` check.
- Restrict `AllowedTokens` to non-fee-on-transfer, audited tokens, or explicitly detect fee-on-transfer behavior before allowlisting.

### Proof of Concept
1. Attacker deploys/uses an allowed gasless token whose `transfer()` burns extra tokens when `to == pair` (Uwerx-style deflationary logic).
2. Attacker calls the pool's `skim(attacker)` to extract the balance surplus not reflected in `reserve0/reserve1`, then `sync()` to force reserves to match the now-depleted actual balance — inflating/deflating the spot price.
3. Attacker submits a `GaslessApproveTx` + `GaslessSwapTx` pair with `amountIn`/`minAmountOut` computed against the manipulated price; `checkBalanceForSwap` [5](#0-4)  passes because it queries the same manipulated reserves.
4. On settlement, the proposer's `LendTxGenerator` fronts gas based on `lendAmount`/`repayAmount` [4](#0-3) , while the actual swap output diverges from the manipulated expectation, resulting in under-repayment or value extraction at the proposer's/pool's expense.

Note: I was unable to inspect the `GaslessSwapRouter.sol` source (not present in the indexed repo, only Go bindings) to confirm whether on-chain slippage checks or token-allowlist access control mitigate this at settlement time. Starting a full Devin session with repository file access would be needed to confirm the exact settlement-time guarantees and close this gap definitively.

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
