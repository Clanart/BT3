### Title
`ReceivedOutput::read` trusts an unverified `offset` grant, allowing mismatched (offset, output) pairs to be reported as spendable funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a missing authorization filter: attacker-supplied access grants are persisted verbatim instead of being filtered against a policy. The analog in Serai is `ReceivedOutput`, whose `offset` field is a grant-like claim — it asserts "this output is spendable by `key + offset·G`". `Scanner::scan_transaction` establishes this invariant by only constructing `ReceivedOutput`s whose `script_pubkey` matches a registered offset, but `ReceivedOutput::read` deserializes attacker-controlled bytes and stores the `offset` verbatim with no check that it actually corresponds to the output's `script_pubkey`. A forged `ReceivedOutput` encoding therefore reports funds as received and spendable when they are not.

### Finding Description
`Scanner::scan_transaction` (crypto-adjacent invariant source) only produces a `ReceivedOutput` after looking up `output.script_pubkey` in `self.scripts`, so a legitimately scanned output satisfies `output.script_pubkey == p2tr_script_buf(key + GENERATOR * offset)` [1](#0-0) . `register_offset` similarly guarantees the stored offset is the exact scalar that produces the script [2](#0-1) .

`ReceivedOutput::read`, however, reads a `Secp256k1` scalar via `Secp256k1::read_F`, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and returns them as a coherent `ReceivedOutput` with no binding between the three fields [3](#0-2) . The struct itself stores no reference key, so downstream code has no way to detect the mismatch: `offset()`, `output()`, and `outpoint()` are trusted accessors [4](#0-3) . Consumers such as `Output::key` assume the invariant holds, computing the spend key as `tweaked_key - GENERATOR * output.offset()` and asserting the script is P2TR [5](#0-4) .

This mirrors the Open WebUI flaw exactly: the creator of the record (Scanner) enforces a policy, but the deserialization/persistence path accepts the grant (`offset`) verbatim without re-validating it against the resource (`output.script_pubkey`).

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (e.g., via a relayed/stored output record, in-scope per `ReceivedOutput::read` handling untrusted bytes) can cause the processor to treat a non-spendable or wrongly-attributed output as spendable funds:

- Craft `ReceivedOutput { offset: o', output: TxOut { script_pubkey: p2tr(key + o·G) , .. }, .. }` with `o' != o`. The output is credited to the multisig and later scheduled for spend, but the derived spend key `key + o'·G` does not match the `script_pubkey`, so the FROST signature produced is invalid for the input — the funds are reported received yet are unspendable, and the signing attempt wastes a session/attempt slot.
- Conversely, craft an output whose `script_pubkey` pays to a foreign key but with `offset` set to an attacker-chosen scalar; it is indistinguishable from a deposit to Serai at the type level, corrupting balance accounting until spend time.

This satisfies the "funds reported received that are not spendable" acceptance criterion. Severity is Medium: it requires the attacker to reach a deserialization path for `ReceivedOutput` records rather than the chain-scanning path (which is safe), and impact is integrity of output accounting / liveness of spends rather than direct theft.

### Likelihood Explanation
The `Scanner`-created objects are safe; the vulnerable surface is any channel where `ReceivedOutput`/`Output` bytes cross a trust boundary (DB entries written or influenced by untrusted components, `Output::read` in `processor/src/networks/bitcoin.rs`, inter-process messages). Because `read()` performs canonical checks on the scalar and consensus decode on the TxOut but zero semantic validation, any such channel suffices — no cryptographic break is required, only the ability to supply bytes. Exploitation does not require forging a signature or knowing a discrete log; the mismatch is accepted silently.

### Recommendation
Bind the offset to the output at construction/deserialization time. `ReceivedOutput` should either (a) store the base `key` and have `read()` (or a `verify`/`new`) recompute `p2tr_script_buf(key + GENERATOR * offset)` and reject mismatches, or (b) make the fields `pub(crate)`-only and forbid deserialization entirely, forcing all `ReceivedOutput`s to originate from `Scanner`/`register_offset`-backed paths. At minimum, `Output::read` in `processor/src/networks/bitcoin.rs` should re-verify `output.key()` consistency against the expected multisig key before the output is queued for scheduling.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/mod.rs::ReceivedOutput::read path
// Base key K (even) the scanner would watch:
let key: ProjectivePoint = /* multisig group key */;
let real_offset = Scalar::from(5u64); // script_pubkey = p2tr(K + 5G)
let real_script = p2tr_script_buf(key + (ProjectivePoint::GENERATOR * real_offset)).unwrap();

// Attacker crafts serialized bytes:
//   offset = 7 (WRONG), output.script_pubkey = real_script, outpoint = real
let mut buf = vec![];
buf.extend(Scalar::from(7u64).to_bytes());            // mismatched offset grant
buf.extend(serialize(&TxOut { value: Amount::from_sat(100_000), script_pubkey: real_script }));
buf.extend(serialize(&OutPoint::new(txid, 0)));

// Accepted verbatim — no check that offset 7 produces real_script:
let forged = ReceivedOutput::read::<&[u8]>(&mut buf.as_ref()).unwrap();
assert_eq!(forged.offset(), Scalar::from(7u64));      // claims wrong spending offset

// Downstream: Output::key computes tweaked_key - 7G, i.e., a key that does NOT
// match script_pubkey. Any SignableTransaction spending `forged` produces a
// signature for key+7G against a script requiring key+5G -> invalid input,
// funds reported received but not spendable.
```

Validation caveat: whether an unprivileged party can actually inject such bytes depends on the integrator's trust boundaries around the channels feeding `ReceivedOutput::read`/`Output::read`; within the listed scope (untrusted bytes to `ReceivedOutput::read`), the missing offset↔script binding is the concrete, verifiable defect.

  pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output =
        TxOut::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid TxOut"))?;
      outpoint =
        OutPoint::consensus_decode(&mut buf_r).map_err(|_| io::Error::other("invalid OutPoint"))?;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
  }

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
