Audit Report

## Title
Unprivileged `DepositDelegatorRewards` griefing permanently blocks vote-account closure via stuck `pending_delegator_rewards` - ([File: programs/vote/src/vote_state/mod.rs])

## Summary
`deposit_delegator_rewards` (SIMD-0123) only verifies that the depositing/source account signs the lamport transfer, with no requirement that the caller be related to the target vote account's authorized withdrawer or voter, yet it unconditionally increments the vote account's `pending_delegator_rewards` field. Because `withdraw` refuses to fully zero/close a vote account while `pending_delegator_rewards > 0`, and epoch reward distribution never reduces this field for vote accounts with zero active stake, any unprivileged attacker can permanently prevent a vote account's authorized withdrawer from closing it.

## Finding Description
`deposit_delegator_rewards` checks only `verify_authorized_signer(&source_address, signers)` on the depositor, not on the vote account's authority [1](#0-0) . It then CPIs a lamport transfer into the vote account and calls `vote_state.add_pending_delegator_rewards(deposit)` unconditionally [5](#0-4) . `add_pending_delegator_rewards` performs a bare `checked_add` with no bound or authorization gate [3](#0-2) .

Separately, `withdraw` requires the authorized withdrawer to sign, but once that check passes, it hard-fails full closure (`remaining_balance == 0`) whenever `pending_delegator_rewards > 0` [4](#0-3) . `pending_delegator_rewards` is decremented only during epoch reward distribution proportional to `total_active_stake`, and `calculate_block_reward` returns `0` outright when `total_active_stake == 0` for that vote account — meaning an unstaked/undelegated vote account's `pending_delegator_rewards` is never repaid down to zero. Thus the "guard" in `withdraw` (blocking closure when rewards are outstanding) is insufficient against this griefing path because the outstanding balance can be forced above zero by anyone and can become permanently unresolvable when the account has no active stake.

## Impact Explanation
This is a functional denial-of-service against a specific, legitimate state transition (full withdraw/close/deinitialize) on a built-in program (the vote program) triggerable by an unprivileged actor at negligible cost (1 lamport plus a signature). It does not cause fund theft, but it permanently blocks the authorized withdrawer from fully closing/deinitializing the targeted vote account, corrupting the account's `pending_delegator_rewards` value into an unrecoverable non-zero state that gates the `withdraw` codepath indefinitely.

## Likelihood Explanation
`DepositDelegatorRewards` is fully permissionless for any signer regardless of relationship to the target vote account, and the deposit amount can be as small as 1 lamport, making the attack trivially cheap and repeatable against any vote account with zero or negligible active stake (e.g., freshly initialized accounts prior to delegation, or accounts whose stake has fully deactivated).

## Recommendation
- Restrict `DepositDelegatorRewards` so it is only reachable through the stake program's actual reward-crediting path rather than as an arbitrary, permissionless instruction callable directly by any signer on any vote account.
- Allow the authorized withdrawer to forcibly sweep/forfeit `pending_delegator_rewards` on full closure instead of unconditionally blocking it.
- Add handling so that when `total_active_stake == 0`, any outstanding `pending_delegator_rewards` can still be resolved (paid out to some destination or written off) rather than remaining permanently stuck.

## Proof of Concept
1. Target a vote account `V` with `total_active_stake == 0` (e.g., freshly initialized, pre-delegation).
2. As any unprivileged signer, submit `VoteInstruction::DepositDelegatorRewards { deposit: 1 }` with self as source and `V` as vote account; `deposit_delegator_rewards` passes its only check (`verify_authorized_signer` on the source) and sets `V.pending_delegator_rewards = 1` via `add_pending_delegator_rewards`.
3. Because `V.total_active_stake == 0`, epoch reward distribution's `calculate_block_reward` returns `0` and never reduces `pending_delegator_rewards`.
4. `V`'s authorized withdrawer calls `Withdraw` for the full balance; `withdraw` hits the `pending_delegator_rewards > 0` branch and returns `InstructionError::InsufficientFunds`, permanently blocking closure.
