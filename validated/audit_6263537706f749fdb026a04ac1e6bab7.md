### Title
Deterministic prefix-truncation in `cap_diff_for_prompt` lets attacker-controlled diff content hide dangerous hunks from the security review model - (File: plugins/security-guidance/hooks/review_api.py)

### Summary
`cap_diff_for_prompt` truncates each file's diff content by keeping only the **first** `DIFF_PER_FILE_BYTES` bytes (default 80000) and the running total to `DIFF_TOTAL_BYTES` (default 400000), dropping everything after the cap and replacing it with a truncation marker. Because the drop point is a fixed, predictable byte offset rather than any content-aware or risk-aware selection, an attacker who controls the diff content (e.g., the author of a large PR/commit being auto-reviewed) can pad the file with benign filler up to the cap boundary so that the actual vulnerable/malicious hunk lands entirely past the cutoff and is silently omitted from the prompt sent to the review model.

### Finding Description
`cap_diff_for_prompt` (plugins/security-guidance/hooks/review_api.py:31-64) iterates `files: list[tuple[str, str]]` and, for each file, truncates `content` to `content[:DIFF_PER_FILE_BYTES]` if it exceeds the per-file cap, and further truncates based on a running `total` against `DIFF_TOTAL_BYTES`. In both cases the code keeps the **prefix** of the content and drops the **suffix**, appending a fixed string like `"... [truncated by security-guidance: file exceeds per-file byte cap]"`.

This capped output is fed directly into `build_investigate_prompt` (review_api.py:156-176), which embeds it verbatim as `"Unified diff (only + lines are new):\n\n" + diff_text` in the prompt handed to the investigate-stage security review model (`AGENTIC_INVESTIGATE_SYSTEM`). The model only ever sees the retained prefix; anything past the cap is invisible to it except for a generic truncation notice that carries no information about what was cut.

Since the cap thresholds are fixed, environment-overridable defaults (`DIFF_PER_FILE_BYTES=80000`, `DIFF_TOTAL_BYTES=400000`), and diff/hunk ordering in a unified diff is fully attacker-controlled (an attacker authoring the changed file/commit controls both file content and hunk order), the attacker can:
1. Prepend large benign filler content (e.g., a big generated data block, verbose comments, or dead code) to a changed file so that its byte length exceeds 80000 bytes before the actually dangerous `+` lines appear, or
2. Order/pad multiple touched files so the cumulative `total` crosses 400000 bytes exactly before the file containing the dangerous hunk.

In either case, the dangerous lines are deterministically excised from `diff_text` before it ever reaches the review model, so the model cannot flag them — not because of a genuine self-refute/adjudication decision, but because the caller never observed them. This defeats the entire purpose of the automated security review pipeline for large or padded changes, which is a real compromise of the review/export logic rather than a best-practice nit.

### Impact Explanation
This breaks the stated invariant that "truncation must not consistently drop the high-risk lines the user expects to be reviewed." Concretely, an attacker submitting a large diff/PR/commit that is fed through this review pipeline can guarantee that the actual dangerous code change is excluded from the LLM's view, causing the automated security guardrail to silently pass dangerous code that it was designed to catch. This matches the "Sensitive code/diff disclosure or exploitable code passing review undetected" bounty impact class: the security-review hook is a trust boundary control, and its bypass allows dangerous or malicious diffs to reach further automation (auto-apply, auto-merge, or reduced human scrutiny) unflagged.

### Likelihood Explanation
The preconditions are minimal: the attacker only needs to control the diff content that is reviewed (e.g., be the author of the changed file/commit/PR being processed by this pipeline) and know or empirically discover the fixed byte caps (defaults are hardcoded and visible in the open-source plugin, or trivially discoverable by observing when the "truncated by security-guidance" marker appears). No privilege escalation, no bypass of authentication, and no reliance on model behavior is required — the drop is a deterministic, reproducible function of input size and ordering. This makes the bypass fully repeatable.

### Recommendation
Replace prefix-only truncation with a risk-aware or evenly-sampled strategy: e.g., always retain full `+`/`-` hunks up to the cap by truncating from the least security-relevant regions (large unchanged context, minified/generated content) rather than blindly cutting at a fixed byte offset; or emit a structural summary (file list + byte counts + hash) for omitted regions so the model/operator is aware large tail content was excluded and can escalate to human review; or size-cap based on hunk count/diversity rather than raw bytes so an attacker cannot control which specific hunk is dropped by padding size.

### Proof of Concept
Unit test in `plugins/security-guidance/hooks/review_api.py`'s test suite:
```python
def test_cap_diff_hides_attacker_positioned_hunk():
    padding = "x" * 79950  # benign filler, just under per-file cap
    dangerous_line = "\n+os.system(user_input)  # command injection\n"
    content = padding + dangerous_line
    files = [("app.py", content)]

    capped, dropped = cap_diff_for_prompt(files)
    fp, capped_content = capped[0]

    # Assert the dangerous line was dropped by truncation, breaking the
    # "must retain high-risk lines" invariant.
    assert "os.system(user_input)" not in capped_content
    assert dropped > 0
    assert "[truncated by security-guidance" in capped_content
```
Expected result: the assertion passes, proving the dangerous `+` line is absent from what `build_investigate_prompt` ultimately sends to the review model, confirming the bypass.
