This confirms the vulnerability pattern I identified. The `DiffSelection` class stores selected/deselected state purely as **line-index numbers** (`divergingLines: Set<number>`), with no binding to file content, hash, or the diff that produced those indices. When `_commitIncludedChanges` runs, `applyPatchToIndex` re-fetches the diff fresh from disk (`getWorkingDirectoryDiff`) and blindly re-applies the old `file.selection.isSelected(absoluteIndex)` against this new diff's line numbering.

### Title
Partial-commit line selection is applied against a stale/refetched diff, causing silent commit of unintended content - (File: app/src/lib/git/apply.ts)

### Summary
GitHub Desktop lets users stage a *subset* of lines from a modified file for commit. The user's line-level selection is stored as a `DiffSelection` object containing only line-index numbers, disconnected from the diff content that produced them [1](#0-0) . When the user finally clicks "Commit", `applyPatchToIndex` **re-fetches a brand-new diff from disk** (`getWorkingDirectoryDiff`) rather than reusing the diff the selection was made against, and then reformats a patch by walking the new diff's lines and checking `file.selection.isSelected(absoluteIndex)` [2](#0-1) .

### Finding Description
This is structurally the same defect class as the reported Oracle bug: a stale/incorrect reference value (`totalSupply` instead of live balance) is used in a "before vs after" comparison that is trusted without re-validation. Here, the trusted-but-stale value is the set of **line indices** the user selected while looking at diff snapshot A, but at commit time those indices are mechanically applied to diff snapshot B (freshly read from the working directory) inside `formatPatch` [3](#0-2) .

If the on-disk file content changes between the moment the user visually reviews/selects lines in the Changes view and the moment `_commitIncludedChanges` executes — e.g. a build tool, linter/formatter on save, an IDE auto-save, a background `git` hook, or any other process writing to a tracked file in the cloned repository — the hunk layout and line offsets shift. `DiffSelection` has no way to detect this: `isSelected` is a pure integer-index lookup with no content validation [4](#0-3) .

There *is* a partial mitigation elsewhere in the code: `_selectWorkingDirectoryFiles`-style diff reloads call `withSelectableLines` to prune indices that no longer correspond to includeable lines when the Changes tab reloads a diff [5](#0-4) . However, this reconciliation only happens when the app's UI-driven diff-reload path runs and updates `state.changesState`; the commit path (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`) uses the file selection **captured synchronously from `repositoryStateCache`** at click time [6](#0-5)  and never re-validates it against the diff that `applyPatchToIndex` independently re-fetches moments later. There is a race window between that state capture, the `unstageAll`/`stageFiles` git calls, and the disk read inside `getWorkingDirectoryDiff` — during which an external write to the file is not detected or blocked.

### Impact Explanation
The consequence is silent corruption of what the user commits and pushes: lines the user explicitly deselected (believing they'd stay uncommitted, e.g. secrets, debug code, or in-progress work) can be committed anyway, or lines the user intended to include can be dropped/misapplied, because `formatPatch` maps stale indices onto new hunk content with different line semantics (context vs. add vs. delete) [7](#0-6) . Because `git apply --cached` either succeeds with a plausible-looking (but wrong) patch or fails outright, there's no user-facing signal that the wrong content was staged. This matches the "silent corruption of what the user commits or pushes" impact class explicitly called out as valid.

### Likelihood Explanation
The window is realistic in normal Desktop usage: users frequently have file-watchers, formatters (prettier/eslint --fix), pre-commit tooling, or IDEs configured to modify files on save while the Desktop Changes pane is open and a partial selection has already been made. No admin rights, malware, or unnatural steps are required — just an ordinary background process (or a malicious npm script/dependency in a cloned repo, e.g. a `postinstall`/watch task) touching a tracked file between selection and commit.

### Recommendation
Before applying `file.selection` to a freshly fetched diff in `applyPatchToIndex`, validate that the diff used to build the selection is still consistent with the file on disk (e.g., compare a content hash/mtime, or re-derive `selectableLines` and abort/re-prompt the user if the line layout has changed) rather than blindly trusting index-based `divergingLines`. Alternatively, capture and reuse the exact diff object the user selected against at commit time instead of re-fetching a new one, and fail the commit with a clear user-facing warning if the working copy has changed since selection.

### Proof of Concept
1. Open a repository in Desktop; modify a tracked file with several hunks.
2. In the Changes view, partially select lines in hunk #2 for commit, leaving hunk #1's changes unselected (e.g. a line containing a temporary secret/debug string).
3. Before clicking "Commit," have an external process (a save-hook, formatter, or a concurrently running script) rewrite the file so hunk boundaries/line offsets shift (e.g. add lines above hunk #1).
4. Click "Commit." `_commitIncludedChanges` captures the old `DiffSelection` from `repositoryStateCache`, then `applyPatchToIndex` calls `getWorkingDirectoryDiff` and reformats the patch using the stale line indices against the new diff.
5. Inspect the resulting commit: it contains different lines than what was visually selected in step 2 (potentially including the deselected secret/debug line), with no error or warning shown to the user.

export function formatPatch(
  file: WorkingDirectoryFileChange,
  diff: ITextDiff | ILargeTextDiff
): string {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (file.selection.isSelected(absoluteIndex)) {
        // A line selected for inclusion.

        // Use the line as-is
        hunkBuf += `${line.text}\n`

        if (line.type === DiffLineType.Add) {
          newCount++
        }
        if (line.type === DiffLineType.Delete) {
          oldCount++
        }

        anyAdditionsOrDeletions = true
      } else {
        // Unselected lines in new files needs to be ignored. A new file by
        // definition only consists of additions and therefore so will the
        // partial patch. If the user has elected not to commit a particular
        // addition we need to generate a patch that pretends that the line
        // never existed.
        if (
          file.status.kind === AppFileStatusKind.New ||
          file.status.kind === AppFileStatusKind.Untracked
        ) {
          return
        }

        // An unselected added line has no impact on this patch, pretend
        // it was never added to the old file by dropping it.
        if (line.type === DiffLineType.Add) {
          return
        }

        // An unselected deleted line has never happened as far as this patch
        // is concerned which means that we should treat it as if it's still
        // in the old file so we'll convert it to a context line.
        if (line.type === DiffLineType.Delete) {
          hunkBuf += ` ${line.text.substring(1)}\n`
          oldCount++
          newCount++
        } else {
          // Guarantee that we've covered all the line types
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }
