### Title
`ReceivedOutput::read`/`Output::read` accept an attacker-supplied `offset`/`kind` without verifying they match the output's actual `script_pubkey`, allowing deposits to be misattributed or rendered unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The DODO bug is a missing binding between the asset actually deposited (`zrc20`) and an attacker-controlled parameter (`params.fromToken`) selecting which asset the contract acts on. The same class exists in Serai's Bitcoin stack: `ReceivedOutput` pairs a scalar `offset` (which defines the spendable key as `group_key + offset·G`) with a `TxOut`, and `ReceivedOutput::read` deserializes both from untrusted bytes with no check that `output.script_pubkey == p2tr(group_key + offset·G)`. `processor/src/networks/bitcoin.rs`'s `Output::read` additionally reads `kind` and `presumed_origin` unchecked from the same byte stream. The only place this binding is enforced is `Scanner::scan_transaction`, which derives the offset from its `scripts` map — the `read` path bypasses it entirely.

### Finding Description
`ReceivedOutput::read` reads `offset` via `Secp256k1::read_F` and the `TxOut`/`OutPoint` via consensus decode, then returns them as a coherent unit without any consistency check:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output = TxOut::consensus_decode(&mut buf_r)...;
    let outpoint = OutPoint::consensus_decode(&mut buf_r)...;
    Ok(ReceivedOutput { offset, output, outpoint })
}
```

The honest construction path, `Scanner::scan_transaction` (wallet/mod.rs:199-214), only produces a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` hits, guaranteeing `offset` is the registered scalar for that script. The deserialize path has no equivalent guard — an attacker controls the claimed offset independently of the script embedded in the output.

Downstream, `Output::key()` (processor/src/networks/bitcoin.rs:112-122) reconstructs the group key as `script_key - offset·G`. With an attacker-chosen offset, this returns an arbitrary point: the deposit is attributed to a "group key" that does not correspond to any validator set that committed to it — the direct analog of depositing token A while acting on token B's balance. `Output::read` (bitcoin.rs:145-166) compounds this by also trusting an attacker-supplied `kind` (`External`/`Branch`/`Change`/`Forwarded`) and `presumed_origin`, while on the honest path `kind` is derived from the offset via the `kinds` map in `get_outputs` (bitcoin.rs:686-700) and `presumed_origin`/`data` are recovered from the spending transaction.

### Impact Explanation
An output whose real script belongs to, e.g., the change offset can be declared `kind: External` with a crafted `offset`, causing it to be credited/processed as a user deposit under a fabricated group key. When Serai later signs to spend it, it uses `key() + offset` which does not equal the script key, so either the produced signature is invalid (funds reported received that are not spendable) or the deposit is attributed to the wrong key/session. This matches the whitelisted impact "funds reported received that are not spendable" and the DODO class of unvalidated claimed-parameter vs actual-asset mismatch.

### Likelihood Explanation
`ReceivedOutput::read` is explicitly in the set of sinks reachable with untrusted bytes, so an unprivileged party who can feed serialized `Output`/`ReceivedOutput` data into the processor (or corrupt it in transit/storage before signature verification) can mount this. It requires no threshold collusion, no key leakage, and no validator misbehavior — only control over the byte representation of the claimed output.

### Recommendation
In `ReceivedOutput::read`, after decoding, re-derive the expected script from `key + offset·G` and reject if `output.script_pubkey` does not match (requires carrying/accepting the group key, or deferring the check to a `verify(key)`-style method that callers must invoke before use). In `Output::read`, do not trust the serialized `kind`/`presumed_origin`; re-derive `kind` from the offset via the `kinds` map exactly as `get_outputs` does (bitcoin.rs:693-695).

### Proof of Concept
1. Take any `ReceivedOutput` produced by `Scanner::scan_transaction` for offset `o` and script `s = p2tr(key + o·G)`.
2. Serialize it, then patch the leading 32 bytes (the `offset` field) to `o' ≠ o` (e.g., `o + 1` reduced mod the group order).
3. Feed to `ReceivedOutput::read` — it succeeds, producing `{offset: o', output: <script s>}`.
4. `Output::key()` on this returns `script_key - o'·G = key + (o - o')·G`, an arbitrary wrong group key; signing for the outpoint uses `key() + o'·G = key + o·G`'s mismatch, yielding an unspendable or misattributed deposit — identical structure to depositing DAI while the contract swaps its ETH balance.
