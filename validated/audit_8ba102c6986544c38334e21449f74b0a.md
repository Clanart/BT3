### Title
Unsanitized whitespace in CAT/DID wallet display names enables asset-identity spoofing in wallet UI - ([File: chia/wallet/cat_wallet/cat_wallet.py])

### Summary
Chia's keychain label-setting path (`FileKeyring.set_label`) explicitly rejects labels with leading/trailing whitespace, embedded newlines/tabs, or empty/whitespace-only content [1](#0-0) . However, the equivalent "identity/display name" fields for wallet-level asset identity — CAT wallet names (`CATWallet.set_name`) and DID wallet names (`DIDWallet.set_name`) — perform **no such validation** at all before being persisted and displayed as the canonical human-readable label for an asset/wallet.

### Finding Description
`CATWallet.set_name` simply replaces the wallet's `name` field and persists it, with zero validation of whitespace, control characters, or emptiness: [2](#0-1) 

The same pattern exists for `DIDWallet.set_name`: [3](#0-2) 

Both are called directly from the wallet RPC layer without any sanitization:
- `cat_set_name` → `CATWallet.set_name(request.name)` [4](#0-3) 
- `did_set_wallet_name` → `DIDWallet.set_name(request.name)` [5](#0-4) 

The persistence layer (`WalletUserStore.update_wallet`) also does not sanitize or normalize the `name` field before writing it to the `users_wallets` table: [6](#0-5) .

This is reachable by any local wallet-RPC caller through the `add_token`/`AddTokenCMD` flow, which lets a caller assign or rename the display name for **any** CAT asset (including ones for which they hold no legitimate authority) via `cat_set_name`: [7](#0-6) . Because a wallet's CAT name is per-wallet (not globally consensus-enforced) and unrelated to the on-chain TAIL/asset ID, an attacker-controlled wallet, a malicious dApp/RPC integration, or a crafted `add_token`/offer-import workflow can set a name like `"USDS "` (trailing space) or `" USDS"` (leading space) that is visually indistinguishable from a legitimately labeled `"USDS"` CAT wallet in UI listings, `cat_asset_id_to_name` lookups, and offer summaries — exactly the bug class described in CVE-2025-55127 (whitespace not neutralized in a user-facing identity string, causing UI-level confusion between a legitimate and illegitimate entity), but applied to on-chain asset identity rather than a username.

### Impact Explanation
Because CAT wallet names are the primary human-readable identity distinguishing one token from another in wallet UIs, GUI asset pickers, and offer-review dialogs, a whitespace-padded name creates a forged/confusable asset identity. A user reviewing an incoming offer or asset list could mistake a malicious/unrelated CAT (with a whitespace-padded copy of a trusted token's name) for the legitimate token, and accept an offer or send funds intending to interact with the trusted asset but actually interacting with a different one — a "forged asset identity" leading to potential financial loss during offer settlement. This aligns with the accepted impact categories (forged asset identity / offer settlement confusion-driven loss).

### Likelihood Explanation
Likelihood is limited by several factors that keep this at most a Medium: setting the name is entirely a **local, per-wallet, non-consensus** cosmetic label (it does not affect on-chain TAIL/asset_id matching, coin puzzle hashes, or spend validity), so it cannot itself move coins or forge cryptographic identity — it only affects what string is *displayed*. The attack requires a victim to be tricked via UI similarity during manual offer review, so it is a social/visual-spoofing vector, not a directly-exploitable coin-movement bug. Still, since any local RPC caller (in scope) can trivially set a whitespace-padded name with no server-side rejection, the precondition for the deception is trivial to create.

### Recommendation
Apply the same normalization/validation used by `FileKeyring.set_label` (reject leading/trailing whitespace, tabs/newlines, and empty/whitespace-only strings) to `CATWallet.set_name`, `DIDWallet.set_name`, and any other user/RPC-settable wallet "name" field (e.g., `create_new_cat_wallet`'s `name` argument, `CreateNewWallet.wallet_name`) before persisting via `WalletUserStore`.

### Proof of Concept
1. Create or obtain a CAT wallet for any asset ID (e.g., via `create_new_wallet` / `add_token` with `mode=EXISTING`).
2. Call the `cat_set_name` RPC (or `chia wallet add_token -n "USDS "`) with a name containing a trailing space that matches a well-known token's display name plus a space.
3. Observe via `cat_get_name` / `cat_asset_id_to_name` / GUI wallet listing that the name renders identically to the legitimate token name in most UI contexts (trailing/leading whitespace is not visually rendered), while being a distinct string tied to a different `wallet_id`/`asset_id`.
4. A victim reviewing an offer or asset list sees the spoofed name and cannot visually distinguish it from the authentic asset, risking mistaken acceptance of an offer/transfer.

**Note on completeness:** I was unable to locate a definition for `CATSetName`/`CATSetNameResponse` in `chia/wallet/wallet_request_types.py` via search (the class may be defined elsewhere or the search index did not surface it), so I cannot confirm with certainty whether any length/type validation exists at the request-streamable level for the `name` field beyond what was found in `CATWallet.set_name` and `WalletUserStore.update_wallet`. This does not change the core finding, since the actual mutation methods (`CATWallet.set_name`, `DIDWallet.set_name`) demonstrably perform no whitespace sanitization.

    def set_label(self, fingerprint: int, label: str) -> None:
        """
        Set a label for the given fingerprint. This will force a write to keyring.yaml on success.
        """
        # First validate the label
        stripped_label = label.strip()
        if len(stripped_label) == 0:
            raise KeychainLabelInvalid(label, "label can't be empty or whitespace only")
        if len(stripped_label) != len(label):
            raise KeychainLabelInvalid(label, "label can't contain leading or trailing whitespaces")
        if len(label) != len(label.replace("\n", "").replace("\t", "")):
            raise KeychainLabelInvalid(label, "label can't contain newline or tab")
        if len(label) > MAX_LABEL_LENGTH:
            raise KeychainLabelInvalid(label, f"label exceeds max length: {len(label)}/{MAX_LABEL_LENGTH}")

        async with self.db_wrapper.writer_maybe_transaction() as conn:
            cursor = await conn.execute(
                "INSERT or REPLACE INTO users_wallets VALUES(?, ?, ?, ?)",
                (

                    wallet_info.type,
                    wallet_info.data,

async def add_token(wallet_info: WalletClientInfo, asset_id: bytes32, token_name: str) -> None:
    wallet_client = wallet_info.client
    fingerprint = wallet_info.fingerprint
    existing_info = await wallet_client.cat_asset_id_to_name(CATAssetIDToName(asset_id=asset_id))

    if existing_info.wallet_id is None:
        response = await wallet_client.create_new_wallet(
            CreateNewWallet(
                wallet_type=CreateNewWalletType.CAT_WALLET,
                mode=WalletCreationMode.EXISTING,
                asset_id=asset_id,
                push=True,
            ),
            tx_config=DEFAULT_TX_CONFIG,
        )
        wallet_id = response.wallet_id
        await wallet_client.set_cat_name(CATSetName(wallet_id=wallet_id, name=token_name))
        print(f"Successfully added {token_name} with wallet id {wallet_id} on key {fingerprint}")
    else:
        await wallet_client.set_cat_name(CATSetName(wallet_id=existing_info.wallet_id, name=token_name))
        print(
            f"Successfully renamed {existing_info.name} with wallet_id {existing_info.wallet_id}"
            f" on key {fingerprint} to {token_name}"
        )
