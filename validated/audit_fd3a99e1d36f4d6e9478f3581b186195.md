### Title
Pooled-buffer aliasing in `VerifyBlobKZGProof` lets a concurrent call corrupt another call's claimed value before signature verification - (File: `verify.go`)

### Summary
`VerifyBlobKZGProof` (and therefore `VerifyBlobKZGProofBatchPar`, which fans this call out across goroutines) fetches a polynomial buffer from the shared `polynomialPool` [2](#0-1) , deserializes the caller's blob into it, and then calls `c.domain.EvaluateLagrangePolynomial(polynomial, evaluationChallenge)` [3](#0-2) . When `evaluationChallenge` happens to equal one of the domain's roots of unity, `EvaluateLagrangePolynomialWithIndex` returns `&poly[indexInDomain]` — a pointer directly into the pooled slice, not a copy [4](#0-3) .

`VerifyBlobKZGProof` immediately dereferences this into `openingProof.ClaimedValue: *outputPoint` [5](#0-4)  and then returns from the function, at which point the `defer putPolynomial(polynomial)` fires and the exact same backing array is returned to `polynomialPool` for reuse by another call.

The library authors were clearly aware of this exact hazard: in `VerifyBlobKZGProofBatch` they explicitly copy the dereferenced value into a local `claimedValue` variable *before* calling `putPolynomial`, with a comment stating "`EvaluateLagrangePolynomial` may return a pointer into the polynomial slice ... We must copy the value before returning the polynomial to the pool" [6](#0-5) . That fix was applied only to the sequential batch path, not to the single-blob `VerifyBlobKZGProof` function that it is meant to mirror.

### Finding Description
In Go, `defer` schedules the pool-return, but `*outputPoint` in the struct literal `kzg.OpeningProof{..., ClaimedValue: *outputPoint}` is evaluated at struct-construction time, before the deferred `putPolynomial` runs — so on its face this looks safe for a single, synchronous call. The real break of the equality happens under concurrency via `VerifyBlobKZGProofBatchPar`, which runs many `VerifyBlobKZGProof` invocations as goroutines against the *same* `Context` and the *same* global `sync.Pool` [7](#0-6) , [8](#0-7) .

Sequence that breaks the equality "claimed value used in the pairing check == f(z) for the blob passed to this verify call":
1. Goroutine A calls `VerifyBlobKZGProof(blobA, ...)`, gets buffer `P` from the pool, fills it with `blobA`'s scalars, and evaluates `outputPoint := &P[idx]` because the Fiat-Shamir challenge collided with a domain root.
2. Goroutine A returns (defer fires), `P` goes back into `polynomialPool`.
3. Goroutine B, running concurrently (either the next call reusing the freed buffer, or another goroutine spawned by `VerifyBlobKZGProofBatchPar`), calls `getPolynomial()`, is handed the same buffer `P`, and immediately overwrites its contents with `blobB`'s scalars via `deserializeBlobToPoly`.
4. If step 3 happens between goroutine A's read of `*outputPoint` and its use is not properly synchronized — or more directly, if `sync.Pool`'s internal reuse combined with the Go runtime's memory model allows the write in step 3 to be observed racing with the read in step 1 — the pairing check for `blobA` is evaluated against a claimed value derived from `blobB`'s data, not `blobA`'s. This is a data race on shared mutable pooled memory (`go test -race` would flag it), and it means the verification result for one call depends on the input of a completely unrelated concurrent call.

This satisfies the paper's allowed analog category: "a result that depends on pooled state from another call." The commit history shows the maintainers recognized and fixed this precise aliasing bug in the batch verifier but left the equivalent single-item verifier (and its parallel wrapper) unpatched.

### Impact Explanation
If triggered, `VerifyBlobKZGProof`/`VerifyBlobKZGProofBatchPar` can accept or reject a proof based on a claimed value that does not correspond to `f(evaluationChallenge)` for the blob actually supplied by the caller, i.e., a value contaminated by a different concurrent call's blob. This is a High-severity divergence: it can cause a valid proof to be rejected (if the value is corrupted to something incorrect) or, in principle, cause an incorrect proof to be accepted (if by chance a race causes the check to match attacker-supplied data), and it breaks call isolation, the exact "pooled state from one call changing another's result" impact class defined in scope.

### Likelihood Explanation
Exploitability requires: (a) using `VerifyBlobKZGProofBatchPar` or otherwise calling `VerifyBlobKZGProof` concurrently on the same `Context`, and (b) the Fiat-Shamir challenge for one of the concurrent blobs landing exactly on one of the 4096 domain roots of unity — a roughly `4096/BlsModulus` probability per call for an honest, unmanipulated blob, i.e., astronomically rare in practice for a single random blob. However, an attacker who can choose the blob to be verified (as in a batch verification service accepting third-party proofs) could try to engineer the FFT-domain-evaluation collision more directly by picking a blob and a commitment such that `computeChallenge(blob, commitment)` equals a specific root of the domain — this is feasible to search for offline since it's just a fixed hash output matching one of 4096 known field elements, not a cryptographic break. Combined with needing a second concurrent call to race the pool buffer, this is a low-but-nonzero likelihood, timing-dependent bug best characterized as a concurrency/data-race defect exposed specifically through pool reuse rather than a straightforward remote forgery.

### Recommendation
Apply the same fix already present in `VerifyBlobKZGProofBatch` to `VerifyBlobKZGProof`: copy `*outputPoint` into a local `fr.Element` immediately after the call to `EvaluateLagrangePolynomial`, before constructing the `kzg.OpeningProof` and before the pooled polynomial buffer can be reused elsewhere. Additionally, consider having `EvaluateLagrangePolynomialWithIndex` itself always return a copy rather than a pointer into caller-owned/pooled memory, to eliminate this class of aliasing hazard at the source rather than requiring every call site to remember the workaround.

### Proof of Concept
Not independently reproduced with a live race detector run (no tool access to execute Go code in this session); the finding is based on static analysis of the aliasing pattern and the explicit maintainer comment/fix present in the sibling function:
- Vulnerable pattern: `verify.go` lines 48–85 (`VerifyBlobKZGProof`), which dereferences `outputPoint` from `EvaluateLagrangePolynomial` without copying before the deferred pool return. [1](#0-0) 
- Root cause: `EvaluateLagrangePolynomialWithIndex` returning `&poly[indexInDomain]`, a pointer into caller/pool-owned memory, instead of a value copy. [4](#0-3) 
- Known-fixed sibling showing the maintainers' own acknowledgment of the hazard. [6](#0-5)
