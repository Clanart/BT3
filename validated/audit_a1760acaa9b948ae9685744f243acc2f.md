### Title
Underpriced Compute for Account-Data Growth Propagated Back to Caller During CPI - (File: program-runtime/src/cpi.rs)

### Summary
When a called (callee) program grows an account's data during a cross-program invocation (CPI), the runtime copies the grown data back into the caller's memory region in `update_caller_account`. This copy — which can be up to `MAX_PERMITTED_DATA_INCREASE` (10 KiB) per account, for every account passed in an `account_infos` array — is performed without any corresponding `compute_meter.consume_checked(...)` call, unlike the entry-side accounting for account data length in `translate_accounts_common`/`cpi_common`. This mirrors the external report's root cause: a mandatory, size-dependent bookkeeping/copy operation performed after the "productive" work of a call is not gas/compute-priced according to its true cost, allowing an attacker to force disproportionately expensive runtime work for near-zero declared compute cost.

### Finding Description
`cpi_common` charges compute for accounts entering a CPI based on their length *at CPI entry*: [1](#0-0) 

After the callee executes and (potentially) grows the account's data via `set_data_length`/`set_data_from_slice` inside `callee_account`, the CPI-exit path invokes `update_caller_account` for every writable account to propagate the change back to the caller: [2](#0-1) 

`update_caller_account` performs the actual growth-handling work — recomputing `post_len`, re-deriving `caller_account.serialized_data` via `CallerAccount::get_serialized_data` (which can span the account's full reserved space, i.e. `original_data_len + MAX_PERMITTED_DATA_INCREASE`), zero-filling shrink regions, and finally `copy_from_slice`-ing up to `post_len` bytes from the callee's data into the caller's serialized buffer: [3](#0-2) 

Nowhere in this function is `invoke_context.compute_meter.consume_checked(...)` invoked to charge for the size of this copy/zero-fill operation. The only compute charge tied to account size happens once, at CPI entry, based on the account's length *before* the callee had a chance to grow it (`translate_accounts_common`, line 1054-1057, and the analogous branch in `from_sol_account_info`, lines 470-478). The growth itself — up to `MAX_PERMITTED_DATA_INCREASE` bytes per account — and its associated copy-back cost are not charged at all.

Since a single CPI can carry many account infos (`check_account_infos` enforces an upper bound but still permits a substantial account list), and CPI can be issued repeatedly and nested up to the max instruction stack depth / instruction trace length, an attacker-controlled program can:
1. Pass a maximal set of writable accounts into a CPI.
2. Have the (attacker-controlled) callee grow each account's data by the maximum permitted increase (`MAX_PERMITTED_DATA_INCREASE`).
3. Force the runtime to perform large, uncharged `copy_from_slice`/zero-fill operations across all of these accounts on every single CPI return, and repeat this pattern across many CPIs within the same transaction (bounded only by `max_instruction_trace_length`, not by the compute budget, since this specific operation isn't billed).

This is structurally analogous to the audited bug: a piece of mandatory, size-driven "settle the state after a costly call" logic (there: persisting the failed payload; here: propagating grown account data back to the caller) is not priced proportionally to its true cost, letting an attacker trade a small amount of declared/priced compute for a much larger amount of actual host-side work.

### Impact Explanation
This allows execution of real host CPU/memory work (large memory copies and zero-fills across many accounts and many CPI round-trips) that is not reflected in the transaction's charged compute units. Because Solana's whole resource-accounting model (block-level throughput limiting, leader scheduling assumptions, and fee/compute markets) assumes a roughly 1:1 relationship between compute units and validator processing cost, a systematic gap here is a case of "materially underpriced compute": a malicious transaction can consume disproportionate validator processing time/CPU relative to the compute units it is billed for and relative to the fee it pays, potentially degrading validator performance/block processing under adversarial transaction construction. It does not achieve arbitrary out-of-bounds memory access (the growth is bounds-checked against `MAX_PERMITTED_DATA_INCREASE`), but it is a genuine compute-pricing gap in the CPI account-data-propagation path.

### Likelihood Explanation
Reaching this path requires only an ordinary CPI from an unprivileged BPF program to another unprivileged program that resizes a writable account it owns — a completely standard, permissionless operation available to any deployed program, requiring no special privileges. The growth amount and account count are both attacker-controlled up to protocol maximums, and the operation can be repeated within the instruction trace budget of a single transaction, making the underpricing straightforward to trigger deterministically.

### Recommendation
Add an explicit `compute_meter.consume_checked(...)` charge in `update_caller_account` (and its `virtual_address_space_adjustments`/`account_data_direct_mapping` counterparts, and `update_callee_account`) proportional to the number of bytes copied/zeroed when account data length changes across a CPI boundary — using the same `cpi_bytes_per_unit` cost model already applied at CPI entry — rather than charging solely for the account's length observed before the callee runs.

### Proof of Concept
Conceptual reproduction (cannot execute in this environment, but derivable directly from the code paths cited above):
1. Deploy attacker program `A` and callee program `B`.
2. From `A`, build a CPI to `B` passing the maximum permitted number of writable `AccountInfo`s that `A` owns, each with an initial small data length.
3. In `B`, for each of these accounts, call the SDK's account-resize API to grow the account's data by `MAX_PERMITTED_DATA_INCREASE` bytes (the protocol-enforced ceiling for in-CPI growth).
4. Return control to `A`. Measure compute units consumed by `sol_remaining_compute_units()` immediately before and after the `invoke`/`invoke_signed` call, as already done in the repo's own CU-usage tests, e.g.: [4](#0-3) 
5. Compare the measured CU delta against the actual host-side bytes copied (`accounts_count * MAX_PERMITTED_DATA_INCREASE`) to show the copy/zero-fill cost for the *grown* portion is not reflected in the CU charge, only the pre-CPI account length is billed (per lines 1052-1058 of `cpi.rs`).
6. Repeat the CPI within the same transaction up to `max_instruction_trace_length` to amplify the uncharged work while compute-unit consumption grows only linearly with the entry-side (pre-growth) account sizes, not the post-growth copy volume.

fn update_caller_account(
    invoke_context: &InvokeContext,
    check_aligned: bool,
    caller_account: &mut CallerAccount<'_>,
    callee_account: &mut BorrowedInstructionAccount<'_, '_>,
    syscall_parameter_address_restrictions: bool,
    virtual_address_space_adjustments: bool,
    account_data_direct_mapping: bool,
) -> Result<(), Error> {
    *caller_account.lamports = callee_account.get_lamports();
    *caller_account.owner = *callee_account.get_owner();

    let prev_len = *caller_account.ref_to_len_in_vm as usize;
    let post_len = callee_account.get_data().len();
    let is_caller_loader_deprecated = !check_aligned;
    let address_space_reserved_for_account =
        if syscall_parameter_address_restrictions && is_caller_loader_deprecated {
            caller_account.original_data_len
        } else {
            caller_account
                .original_data_len
                .saturating_add(MAX_PERMITTED_DATA_INCREASE)
        };

    if post_len > address_space_reserved_for_account
        && (syscall_parameter_address_restrictions || prev_len != post_len)
    {
        let max_increase =
            address_space_reserved_for_account.saturating_sub(caller_account.original_data_len);
        ic_msg!(
            invoke_context,
            "Account data size realloc limited to {max_increase} in inner instructions",
        );
        return Err(Box::new(InstructionError::InvalidRealloc));
    }

    let memory_mapping = invoke_context.memory_contexts.memory_mapping()?;
    if prev_len != post_len {
        // when virtual_address_space_adjustments is enabled we don't cache the serialized data in
        // caller_account.serialized_data. See CallerAccount::from_account_info.
        if !(virtual_address_space_adjustments && account_data_direct_mapping) {
            // If the account has been shrunk, we're going to zero the unused memory
            // *that was previously used*.
            if post_len < prev_len {
                caller_account
                    .serialized_data
                    .get_mut(post_len..)
                    .ok_or_else(|| Box::new(InstructionError::AccountDataTooSmall) as Error)?
                    .fill(0);
            }
            // Set the length of caller_account.serialized_data to post_len.
            unsafe {
                caller_account.serialized_data = CallerAccount::get_serialized_data(
                    memory_mapping,
                    check_aligned,
                    caller_account.vm_data_addr,
                    caller_account.original_data_len,
                    post_len,
                    syscall_parameter_address_restrictions,
                    virtual_address_space_adjustments,
                    account_data_direct_mapping,
                )?;
            }
        }
        // this is the len field in the AccountInfo::data slice
        *caller_account.ref_to_len_in_vm = post_len as u64;

        // this is the len field in the serialized parameters
        let serialized_len_ptr = translate_type_mut_for_cpi::<u64>(
            memory_mapping,
            caller_account
                .vm_data_addr
                .saturating_sub(std::mem::size_of::<u64>() as u64),
            check_aligned,
        )?;
        *serialized_len_ptr = post_len as u64;
    }

    if !(virtual_address_space_adjustments && account_data_direct_mapping) {
        // Propagate changes in the callee up to the caller.
        let to_slice = &mut caller_account.serialized_data;
        let from_slice = callee_account
            .get_data()
            .get(0..post_len)
            .ok_or(CpiError::InvalidLength)?;
        if to_slice.len() != from_slice.len() {
            return Err(Box::new(InstructionError::AccountDataTooSmall));
        }
        to_slice.copy_from_slice(from_slice);
    }

    Ok(())
}
