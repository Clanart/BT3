## Title
Automatic remote-URL rewrite trusts unverified GitHub API repository data, enabling silent push/pull hijack - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` automatically overwrites a repository's `origin` remote URL whenever the GitHub API's `clone_url` for the associated `GitHubRepository` no longer matches the locally-configured remote, provided the protocol hasn't changed and the remote "hasn't been manually altered" (as judged by comparing to the *previously cached* API URL). This function is invoked with no user confirmation from `repositoryWithRefreshedGitHubRepository`, which itself runs on ordinary, frequent, non-interactive code paths (selecting a repository, fetching, pushing, publishing).

### Finding Description
`updateRemoteUrl` is called with the live `apiRepo` object fetched from GitHub (or a GHES endpoint) for the repository currently open in Desktop: [1](#0-0) 

The decision to rewrite the remote is based purely on comparing three attacker/network-influenced values — the previously-cached clone URL, the newly-fetched `apiRepo.clone_url`, and the current git remote — with no verification that the "new" clone URL still points to the *same* underlying repository the user originally intended to work with: [2](#0-1) 

If the conditions are met (`protocolsMatch && remoteUrlUnchanged && !urlsMatch`), Desktop calls `gitStore.setRemoteURL(...)` which directly executes `git remote set-url origin <new-url>`: [3](#0-2) 

The trigger point, `repositoryWithRefreshedGitHubRepository`, resolves the repository to refresh via `matchGitHubRepository` and then calls `api.fetchRepository(owner, name)` — i.e., it re-fetches by owner/name path, not by an immutable, cryptographically-verified repository identity: [4](#0-3) 

This function is exercised automatically and silently on very common paths, without any explicit user action to "trust" a new remote: [5](#0-4) [6](#0-5) 

**Broken invariant:** Desktop treats the GitHub API's `clone_url` field as ground truth for "where the user's remote should point," and mutates local git state (`origin`) to match it whenever the previously observed URL is stale — without validating that the API response still corresponds to the same repository network the user is working in (e.g., verifying a stable repository ID rather than owner/name, or requiring confirmation before rewriting a remote). This mirrors the report's root cause: an externally-controlled data source (ReaperVault's share price / GitHub's API response) is consumed as authoritative accounting/config state without a sanity check against the invariant it's supposed to preserve, corrupting downstream state (`yieldingAmount` / the git `origin` remote).

**Why existing guards don't stop this:** The repo's hardened clone/path code (`isClonePathSensitive`, `sanitizeCloneName`, `resolveWithin`) and the OAuth CSRF `state` check in `sign-in-store.ts` only protect against path traversal and OAuth callback replay — they do nothing to validate the *authenticity/continuity* of the GitHub API repository object consumed by `updateRemoteUrl`. There is no check that the fetched repository ID matches a previously stored, immutable ID before rewriting the remote; only URL equality of the previous cache vs. current git config.

### Impact Explanation
If an attacker can cause the owner/name lookup used by `matchGitHubRepository` + `api.fetchRepository(owner, name)` to resolve to an attacker-controlled repository (e.g., a compromised/malicious GitHub Enterprise Server, a MITM'd/rogue API response, or "repo-jacking" a renamed repository's old owner/name slot), Desktop will silently retarget the user's `origin` remote to the attacker's repository. All subsequent `git push`/`git pull`/`git fetch` operations from that point on go to/from the attacker's remote instead of the user's real one — this is exactly the "silent corruption of what the user commits or pushes" impact category. Because the rewrite happens as a side effect of routine background refresh, the user has no indication their push destination changed.

### Likelihood Explanation
This requires the attacker to control the GitHub API object returned for the specific owner/name Desktop queries (a hostile/compromised endpoint, or successfully squatting a renamed repository's former owner/name), which is a real and previously-documented supply-chain technique ("repo-jacking"). It does not require local/physical access, admin rights, prior malware, or leaked credentials — it only requires the attacker to control what a git remote/API endpoint serves for a given repository path, matching the accepted threat model. The exact production reachability of `matchGitHubRepository`'s owner/name resolution (versus an immutable ID) could not be fully confirmed within the available tool budget — this is the main remaining uncertainty.

### Recommendation
- Before silently rewriting `origin`, verify the fetched `apiRepo` corresponds to the same immutable repository identity (its numeric `id`) previously recorded for the local `GitHubRepository`, not just owner/name path continuity.
- Require explicit user confirmation (a dialog) before automatically changing a configured remote URL, rather than performing the `git remote set-url` unattended in a background refresh path.
- Log/audit remote URL changes so users can detect unexpected redirections.

### Proof of Concept
Conceptual PoC (exact reachability of the owner/name matching step is unverified without deeper access to `matchGitHubRepository`):
1. User has Desktop open with a repository whose GitHub remote is associated via `GitHubRepository` (owner `victim-org`, name `repo`).
2. `victim-org/repo` is renamed/transferred, and the attacker later reclaims/registers a new repository at the old `owner/name` slot (or attacker compromises the GHES endpoint Desktop talks to).
3. On the next background refresh (`_selectRepositoryRefreshTasks`, `_fetch`, or `_publishRepository` flow), Desktop calls `api.fetchRepository(owner, name)` and receives the attacker's repository object with a different `clone_url`.
4. `updateRemoteUrl` sees `protocolsMatch = true`, `remoteUrlUnchanged = true` (matches previously cached URL), `urlsMatch = false` → calls `gitStore.setRemoteURL('origin', <attacker_clone_url>)`.
5. All subsequent pushes/pulls silently go to the attacker's repository. [7](#0-6)

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
