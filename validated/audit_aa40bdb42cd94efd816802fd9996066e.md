### Title
BIP-340 Schnorr signatures emitted for odd‑Y group keys are invalid on‑chain (missing key negation) - (File: networks/bitcoin/src/crypto.rs)

### Summary
The Bitcoin `Schnorr` algorithm corrects the emitted signature scalar `s` for the parity of the nonce point `R` (`needs_negation(&sig.R)`), but it never accounts for the parity of the group key `A`. Under BIP-340, verification uses the x-only key lifted to an even‑Y point (`X = ±A`), and the nonce is likewise interpreted as the even‑Y `R`. The correct negation condition is `parity(R) XOR parity(A)`; the code implements only `parity(R)`. For the ~50% of aggregate group keys with odd Y, the produced 64‑byte signature is a valid Schnorr signature under `A` but fails `lift_x`‑based BIP-340 verification, so any transaction spending a taproot output for that key is consensus‑invalid.

### Finding Description
In `networks/bitcoin/src/crypto.rs`, `Algorithm::verify` for `Schnorr` does:

```rust
self.0.verify(group_key, nonces, sum).map(|mut sig| {
  sig.s = <_>::conditional_select(&sum, &-sum, needs_negation(&sig.R));
  sig.serialize()[1 ..].try_into().unwrap()
})
```

Internally, `FrostSchnorr::sign_share`/`verify` operate on the full `ProjectivePoint` group key `A` (not `x(A)` lifted to even Y) and the share `s = k + c·a` satisfies `sG = R + cA` where `A` may have odd Y. The emitted signature is `x(R) || s`, interpreted by Bitcoin as `(R', X)` with both lifted to even Y. Since `X = -A` when `A` is odd, the share must effectively be `k + c·(-a)`, i.e., the scalar must be negated when `A` is odd (combined with the `R` parity correction: negate iff `needs_negation(R) != needs_negation(A)`). The code only applies `needs_negation(&sig.R)`, so whenever the group key has odd Y the inner `self.0.verify` succeeds (it checks `sG = R + cA` with `A` itself), `complete()` returns a signature, and the bytes are consensus‑invalid.

Root cause: the parity correction in `Algorithm::verify` at `networks/bitcoin/src/crypto.rs:145-149` accounts only for `R`, and `sign_share` at `crypto.rs:128-136` delegates to `FrostSchnorr` without negating the secret share/`sum` for the group key's parity.

### Impact Explanation
Roughly half of all FROST-derived aggregate keys have odd Y. For any such key used as a Bitcoin taproot internal/output key, every threshold signature produced by this algorithm will be rejected by Bitcoin consensus. Bitcoin sent to outputs controlled by that key is reported received by the scanner but is not spendable — the threshold can never produce a valid signature and no error is surfaced (the internal verify succeeds and `complete` returns `Ok`). This is permanent loss of spendability for those keys.

### Likelihood Explanation
Deterministic for any group key whose Y coordinate is odd (~1/2 of keys produced by an honest DKG). No attacker action is needed; equally, an unprivileged counterparty cannot be blamed since the failure is in the library's output transformation. The bug is reachable purely through the normal `preprocess`/`sign`/`complete` path.

### Recommendation
In `networks/bitcoin/src/crypto.rs`, apply the parity correction `negate s iff needs_negation(R) XOR needs_negation(group_key)`. This can be implemented either by negating `sum` inside `verify` when the group key is odd (in addition to the existing `R` correction), or by having signers use `keys.scale(-F::ONE)`/share negation when `group_key` is odd — but the former must be done consistently inside this `Algorithm` so callers cannot forget it. The HRAM challenge should also be confirmed to be computed over `x(R)` and `x(A)` (32‑byte encodings) so the internally checked statement equals the BIP-340 statement.

### Proof of Concept
1. Complete a FROST DKG over `Secp256k1` producing `ThresholdKeys` whose `group_key()` has odd Y (repeat keygen until odd; ~50% of runs).
2. Run `AlgorithmMachine::new(Schnorr::new(), keys).preprocess(rng)` → `sign(preprocesses, msg)` → `complete(shares)` for a taproot sighash `msg`.
3. `complete` returns `Ok(sig)` — a 64‑byte signature — even though `sG = R + cA` was verified against the odd‑Y `A`.
4. Verify `sig` with any BIP-340 verifier (`bitcoin::secp256k1` `verify_schnorr` or Bitcoin Core's `CheckSchnorrSignature`) against `x(A)`: it fails, because the verifier uses `X = lift_x(x(A)) = -A` while the signature's `s` was computed against `+A`.

Caveat: I reviewed the full `Algorithm<Secp256k1> for Schnorr` impl (`crypto.rs:94-160`) and confirmed `sign_share`/`verify` contain no key‑parity handling; however, I could not confirm whether callers elsewhere unconditionally pre‑negate odd keys via `ThresholdKeys::scale(-1)` before constructing the machine — if that is a documented hard requirement enforced upstream, the residual risk is reduced but the internal `verify`/`complete` still silently emits an invalid signature when it is not done.
