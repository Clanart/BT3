### Title
Conflict-resolution gate relies on a narrow `git diff --check` marker heuristic, letting attacker-crafted merge content be silently committed as "resolved" - ([File: app/src/lib/git/diff-check.ts])

### Summary
The RPL report's core pattern is: a user obtains the benefit of a required multi-step process (withdrawal) while skipping the step that should update system bookkeeping (`finalise()`), because the code that grants the benefit trusts an incomplete/partial signal instead of verifying full completion. The closest analog in GitHub Desktop is the "conflicts resolved" gate used throughout the merge/rebase/cherry-pick conflict UI: Desktop treats a conflicted file as fully resolved purely based on a marker-count heuristic derived from `git diff --check`, and uses that boolean to unlock committing/continuing the operation, rather than any semantic verification that the merge was actually completed correctly.

### Finding Description
`getFilesWithConflictMarkers` runs `git diff --check` and extracts a leftover-marker count per file using the regex `/^(.+):\d+: leftover conflict marker/gm`: [1](#0-0) 

This count is attached directly as `conflictMarkerCount` on the file's `ConflictedFileStatus` when building working-directory status: [2](#0-1) 

That single integer is the sole gate used everywhere in the UI/state layer to decide "is this file resolved":
`hasUnresolvedConflicts` treats `conflictMarkerCount === 0` as fully resolved: [3](#0-2) 

The same signal drives `getResolvedFiles`/`getConflictedFiles`, which feed both the classic merge-conflicts dialog and the newer Copilot conflict-resolution dialog's "is this file resolved externally" logic: [4](#0-3) [5](#0-4) 

Once a file is deemed "resolved" this way, `_finishConflictedMerge` stages only files still flagged `Conflicted` by git and trusts that "all other files... have already been staged by git automatically," then commits: [6](#0-5) 

The broken invariant: the "finalization" step in the RPL bug (`_finalise()`, which reconciles real state) is analogous here to *verifying the merge is actually semantically resolved*. Desktop instead infers completion from a narrow textual pattern match (`git diff --check`'s specific 7-character marker regex, anchored at line start) rather than from a robust check that the file no longer contains any conflict artifacts. Because the working tree content in a merge/rebase originates from a cloned/fetched repository (attacker-controlled branch content), an attacker who controls the branch being merged can shape file content so that `git diff --check` does not report "leftover conflict marker" for a given hunk (e.g., because the file type is excluded from `diff --check`'s marker scan, or the surrounding context defeats the checker), while the file is not actually resolved as the user or the Copilot flow believes. The UI then reports "No conflicts remaining" (`getResolvedFileStatusSummary`) and unlocks Commit/Continue, and Desktop commits/pushes that content without further scrutiny.

### Impact Explanation
If exploitable, this results in silent corruption of what the user commits: content that still logically conflicts (or contains attacker-planted payloads dressed as one side of a "resolved" conflict) gets committed and potentially pushed under the user's identity, without the user or Desktop's conflict UI ever flagging it as unresolved. This matches the allowed "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
Likelihood is **uncertain/low-to-moderate** and I want to be explicit about the limits of this analysis: I verified that the "resolved" determination is architecturally a single heuristic count derived from `git diff --check`, and that this heuristic — not a semantic check — gates commit/continue actions across multiple dialogs (classic conflicts dialog and the newer Copilot conflicts dialog). However, I did not construct or confirm a concrete file-content example that defeats `git diff --check`'s marker detection while leaving a real unresolved/malicious conflict in place; `git diff --check`'s marker regex is a well-established Git heuristic, and whether it can reliably be bypassed with attacker-controlled branch content (vs. simply matching normal git behavior) needs further testing to be certain this is a Desktop-introduced flaw rather than inherited, expected Git behavior.

### Recommendation
- Do not rely solely on `conflictMarkerCount` (derived from `git diff --check`) as the single source of truth for "resolved." Cross-check with `git status`/index unmerged-entry state (which is already partially done) and, where feasible, re-parse file content directly for marker patterns rather than depending exclusively on git's own heuristic.
- For binary or otherwise marker-scan-excluded files, ensure the "resolved" determination doesn't default to "no markers found ⇒ resolved" without an explicit manual resolution record.
- Add defense-in-depth: before committing/staging in `_finishConflictedMerge` and the Copilot flow, re-verify there are zero unmerged index entries for the repository (`git ls-files -u`) rather than trusting per-file cached counts computed earlier in the flow.

### Proof of Concept
Not constructed — I was unable to verify with certainty that `git diff --check`'s marker regex (`app/src/lib/git/diff-check.ts` line 20) can be defeated by attacker-controlled fetched/cloned branch content while a genuine unresolved conflict remains. A concrete PoC would require crafting a merge conflict whose file content triggers `UnmergedEntrySummary.BothModified`/`BothAdded` in git's index while `git diff --check` reports zero "leftover conflict marker" lines for it, then confirming Desktop's dialogs treat it as resolved and commit it via `_finishConflictedMerge`. This should be validated experimentally before treating it as a confirmed vulnerability.

export async function getFilesWithConflictMarkers(
  repositoryPath: string
): Promise<Map<string, number>> {
  const { stdout } = await git(
    ['diff', '--check'],
    repositoryPath,
    'getFilesWithConflictMarkers',
    { successExitCodes: new Set([0, 2]) }
  )

  const files = new Map<string, number>()
  const matches = stdout.matchAll(/^(.+):\d+: leftover conflict marker/gm)

  for (const [, path] of matches) {
    files.set(path, (files.get(path) ?? 0) + 1)
  }

  return files

export function hasUnresolvedConflicts(
  status: ConflictedFileStatus,
  manualResolution?: ManualConflictResolution
) {
  // if there's a manual resolution, the file does not have unresolved conflicts
  if (manualResolution !== undefined) {
    return false
  }

  if (isConflictWithMarkers(status)) {
    // text file may have conflict markers present
    return status.conflictMarkerCount > 0
  }

  // binary file doesn't contain markers
  return true
}

  public async _finishConflictedMerge(
    repository: Repository,
    workingDirectory: WorkingDirectoryStatus,
    manualResolutions: Map<string, ManualConflictResolution>
  ): Promise<string | undefined> {
    /**
     *  The assumption made here is that all other files that were part of this merge
     *  have already been staged by git automatically (or manually by the user via CLI).
     *  When the user executes a merge and there are conflicts,
     *  git stages all files that are part of the merge that _don't_ have conflicts
     *  This means that we only need to stage the conflicted files
     *  (whether they are manual or markered) to get all changes related to
     *  this merge staged. This also means that any uncommitted changes in the index
     *  that were in place before the merge was started will _not_ be included, unless
     *  the user stages them manually via CLI.
     *
     *  Its also worth noting this method only used in the Merge Conflicts dialog flow, not committing a conflicted merge via the "Changes" pane.
     *
     *  *TLDR we only stage conflicts here because git will have already staged the rest of the changes related to this merge.*
     */
    const conflictedFiles = workingDirectory.files.filter(f => {
      return f.status.kind === AppFileStatusKind.Conflicted
    })
    const gitStore = this.gitStoreCache.get(repository)
    return await gitStore.performFailableOperation(() =>
      createMergeCommit(repository, conflictedFiles, manualResolutions)
    )
  }
