### Title
Instant, retroactive `challengePeriod` reduction lets stale/pending state commitments bypass their promised fraud-challenge window - ([File: evm/src/core/HandlerV2.sol], [File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParams` can change `_hostParams.challengePeriod` with immediate effect and no floor value, while every message handler (`handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, `handleGetRequestTimeouts`) checks the *current* `host.challengePeriod()` against the delay since the state commitment's `stateMachineCommitmentUpdateTime`, rather than the challenge period that was in force when that commitment was first stored.

### Finding Description
`HandlerV2.sol` computes `delay = timestamp - host.stateMachineCommitmentUpdateTime(height)` and then does `if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();` using `host.challengePeriod()`, which is a single mutable global read from storage at call-time. [1](#0-0) [2](#0-1) 

Rust-side ISMP core does the same thing: `verify_delay_passed` fetches `host.challenge_period(proof_height.id)` fresh at verification time and compares it to `current_timestamp - update_time`. [3](#0-2) 

`challengePeriod` is stored as a single scalar per host, not per-height or snapshotted at the time a state commitment is recorded: [4](#0-3) 

`updateHostParams` writes the new `challengePeriod` immediately into `_hostParams` and takes effect for the very next call — there is no timelock on this update path itself, and unlike `unStakingPeriod` (which has a `1 days` floor), `challengePeriod` has no minimum-value validation at all: [5](#0-4) 

This means: if a state commitment for height H was recorded at time T under a challenge period of, say, 7 days (relied upon by users/relayers/fishermen to detect and veto a fraudulent commitment — see `waitForChallengePeriod` in the SDK), and the challenge period is later reduced (even to 0) via `updateHostParams`, then any request/response/timeout anchored at height H that had not yet cleared the *original* 7-day window instantly becomes processable, because the live `challengePeriod > delay` check now uses the new, smaller value. This is exactly the Nibbl-style invariant break: the wait/lock period that a party is relying on (challenge window, analogous to `BUYOUT_DURATION`) can be silently invalidated by a separate parameter-update path (`updateHostParams`, analogous to `updateVaultImplementation`) that has **no** timelock protecting in-flight commitments, whereas the original report's version at least had a competing timelock.

### Impact Explanation
This falls under "false proof/state acceptance" — pending or already-vetoable state commitments can be consumed (dispatched to destination apps, triggering fund releases, order settlement, or asset transfers) before the fraud-detection/veto window that fishermen and relayers were guaranteed at commitment time has actually elapsed in wall-clock terms. A fisherman that planned to veto a bad commitment within the original challenge window can be preempted the moment the parameter is lowered, since the check is retroactive over all existing heights simultaneously, not scoped to commitments recorded after the update.

### Likelihood Explanation
The path is straightforward: any call to `updateHostParams` that changes `challengePeriod` (via the host manager cross-chain governance route, or via `TestnetHost`'s admin override) applies globally and instantly to already-stored heights, since the check re-reads the live value with no per-height snapshot or grace/timelock on the update itself.

### Recommendation
Snapshot the applicable `challengePeriod` at the time each state machine height commitment is stored (alongside `stateMachineCommitmentUpdateTime`), and have `HandlerV2` compare against that stored value rather than the live `host.challengePeriod()`. Alternatively, enforce a minimum-value floor plus a timelock/grace-period on `challengePeriod` reductions (as is already done for `unStakingPeriod`), ensuring reductions only apply to commitments recorded after the new value takes effect.

### Proof of Concept
1. Governance/hostManager calls `updateHostParams` with `challengePeriod = 7 days` (or the chain's configured value). A relayer submits `storeStateMachineCommitment` for height H at time T0; fishermen plan to veto within 7 days if needed (`EvmHost.sol:544-562`, `_vetoes`).
2. Before the 7 days elapse (e.g., at T0 + 1 hour), governance calls `updateHostParams` again, this time setting `challengePeriod = 0` (no floor prevents this: `EvmHost.sol:573-636`).
3. Immediately after, anyone calls `HandlerV2.handlePostRequests` (or `handleGetResponses`/timeout handlers) with a proof anchored at height H: `delay = timestamp - stateMachineCommitmentUpdateTime(H)` is small, but `challengePeriod == 0` short-circuits the `challengePeriod != 0 && challengePeriod > delay` check (`HandlerV2.sol:183-185`), so `ChallengePeriodNotElapsed` never reverts.
4. The request/response is dispatched to the destination module and processed (funds moved, order settled) even though the height's fraud-challenge window that fishermen were promised at T0 never actually elapsed in real time.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

    /**
     * @dev Updates the HostParams. Will reset all fishermen accounts and initialize any new state machines.
     * @param params, the new host params.
     */
    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params
        emit HostParamsUpdated({oldParams: _hostParams, newParams: params});

        _hostParams.feeToken = params.feeToken;
        _hostParams.admin = params.admin;
        _hostParams.handler = params.handler;
        _hostParams.hostManager = params.hostManager;
        _hostParams.uniswapV2 = params.uniswapV2;
        _hostParams.unStakingPeriod = params.unStakingPeriod;
        _hostParams.challengePeriod = params.challengePeriod;
        _hostParams.consensusClient = params.consensusClient;
        _hostParams.stateMachines = params.stateMachines;
        _hostParams.hyperbridge = params.hyperbridge;
