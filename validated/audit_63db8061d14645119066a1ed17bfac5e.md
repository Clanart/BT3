### Title
`ThresholdKeys::read`/`ThresholdKeys::new` never constrain `secret_share` to `verification_shares[i]`, letting fully attacker-controlled bytes define the group key - ([File: crypto/dkg/src/lib.rs](serai--005/crypto/dkg/src/lib.rs))

### Summary
The Kakarot bug was a copy routine that validated internal consistency of a dict but never asserted the one constraint tying it to the expected default value (`prev_value == default_value`). The Serai analog is `ThresholdKeys` deserialization: `ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation data, `secret_share`, and all `verification_shares` purely from the input byte stream, and `ThresholdKeys::new` checks only structural properties (share count, participant range, `t <= n`). It never enforces the fundamental invariant of a FROST key share — that `C::generator() * secret_share == verification_shares[i]` and that the shares interpolate to a well-formed group key the local party actually participated in. The code itself acknowledges this gap: `crypto/frost/src/sign.rs` notes the failure mode is possible only by "deserializing a semantically invalid FrostKeys".

### Finding Description
`ThresholdKeys::read` reads every field from the reader — params at `crypto/dkg/src/lib.rs:591-602`, interpolation at `604-616`, `secret_share` at `618`, and `verification_shares` at `620-623` — then hands them to `ThresholdKeys::new`. That constructor only verifies `verification_shares.len() == n` and `participant <= n` (`crypto/dkg/src/lib.rs:355-365`), and computes `group_key` by interpolating shares `1..=t` (`376-378`). There is no equivalent of `default_dict_finalize`'s `assert dict_accesses_start.prev_value = default_value`: no statement binds the supplied `secret_share` to `verification_shares[i]`, nor binds the reconstruction of shares `1..=t` to any externally known commitment.

Consequences downstream:
- `ThresholdView`/`view()` builds `group_key`, interpolated `secret_share`, and per-participant verification shares entirely from these unverified fields (`crypto/dkg/src/lib.rs:463-533`).
- `AlgorithmSignatureMachine::complete` sums shares and calls `algorithm.verify(self.view.group_key(), ...)` (`crypto/frost/src/sign.rs:465`). Success is judged against the attacker-influenced `group_key`, not any ground truth, so `Ok(sig)` can be returned for a signature valid only under a group key the byte-supplier chose.
- When the share is inconsistent, signature verification fails and the blame loop (`sign.rs:475-489`) attributes `InvalidShare` to whichever participant's share fails the batch — a crafted key lets the byte-supplier steer blame/abort behavior.

### Impact Explanation
An attacker who can feed bytes to `ThresholdKeys::read` (an allowed untrusted sink) obtains a `ThresholdKeys` that passes every check yet represents a key set of their choosing. If they make `secret_share` consistent with `verification_shares[i]` and craft the `1..=t` shares so `group_key` is a key whose discrete log they know, the victim's signing machines will emit Schnorr signatures over real protocol messages that verify under the attacker's group key — a signature the protocol believes belongs to the DKG-established group but which actually belongs to the attacker. If they instead make the share inconsistent, every signing attempt either aborts or mis-blames honest participants (`FrostError::InvalidShare`/`InternalError`), corrupting signing sessions. This mirrors the report: internal consistency (canonical encodings, counts, ranges) is enforced, but the constraint tying the object to its intended "default" — the share-to-verification-share binding — is absent.

### Likelihood Explanation
Requires an attacker to control the serialized key bytes consumed by a victim. That is a narrower reachability than a network message (which is why this is at most Medium rather than High in practice), but the format is self-describing with no MAC, no hash commitment, and no consistency proof — any path that loads keys from backup,迁移 storage, or a peer-supplied blob is exploitable. Within the cryptographic layer itself, no mitigation exists.

### Recommendation
In `ThresholdKeys::new` (or at the end of `read`), assert `C::generator() * secret_share.deref() == verification_shares[&params.i()]`, the exact analog of `assert dict_accesses_start.prev_value = default_value`. Optionally also commit to the expected `group_key` (e.g., store and verify a hash of the DKG transcript/context) so the group key cannot be silently redefined by the serialized blob.

### Proof of Concept
```rust
use ciphersuite::Ciphersuite;
use dkg::{Participant, ThresholdParams, ThresholdKeys, Interpolation};
use zeroize::Zeroizing;
use group::{Group, ff::Field};

// C: any in-scope ciphersuite, e.g. dalek_ff_group::Ed25519
fn forged_keys<C: Ciphersuite>() -> Vec<u8> {
    // Attacker-chosen secret and group key material
    let s = C::F::random(&mut rand_core::OsRng);
    let t: u16 = 1;
    let n: u16 = 1;
    let i = Participant::new(1).unwrap();

    let mut buf = vec![];
    buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
    buf.extend(C::ID);
    buf.extend(t.to_le_bytes());
    buf.extend(n.to_le_bytes());
    buf.extend(i.to_bytes());
    buf.push(1); // Interpolation::Lagrange
    buf.extend(s.to_repr().as_ref()); // secret_share (unconstrained)
    // verification_shares[1] — attacker freely sets group_key = interpolation of these
    buf.extend((C::generator() * s).to_bytes().as_ref());
    buf
}

// Victim side:
// let keys = ThresholdKeys::<C>::read(&mut forged_keys::<C>().as_ref()).unwrap();
// keys.params().i() == 1, keys.group_key() is entirely attacker-defined.
// AlgorithmMachine::new(..., keys).sign(...) produces signatures valid under the
// attacker's chosen group key; inconsistent shares instead yield InvalidShare blame
// on honest participants.
```
