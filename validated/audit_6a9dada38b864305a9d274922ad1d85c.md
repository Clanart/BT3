## Title
Unsafe ERC721 transfer via `CW721ERC721Pointer.transferFrom` can permanently freeze NFTs (`File: contracts/src/CW721ERC721Pointer.sol`)

### Summary
`CW721ERC721Pointer`, the EVM-side pointer contract that lets EVM users interact with a Cosmos `CW721` NFT collection, overrides `transferFrom` to route the transfer straight to the underlying CosmWasm contract without any receiver-safety check, and does not properly support `safeTransferFrom` for this pointer's actual (remote) ownership model. As a result, any unprivileged EVM caller can move an NFT to a contract address that cannot handle ERC721 tokens, permanently freezing it.

### Finding Description
`CW721ERC721Pointer.transferFrom` is the only functional transfer path exposed by the pointer contract. It validates ownership and then directly executes `transfer_nft` on the CosmWasm contract via the wasmd precompile, with no check on whether `to` is a contract capable of receiving/handling the NFT: [1](#0-0) 

The contract inherits OpenZeppelin's `ERC721`, whose `safeTransferFrom` would normally perform the `onERC721Received` receiver check, but `CW721ERC721Pointer` never updates OZ's internal ownership bookkeeping (`_ownerOf`/`_balances`) — all read functions (`ownerOf`, `balanceOf`, `getApproved`, `isApprovedForAll`) are overridden to instead query the real CW721 contract state through the wasmd/json precompiles: [2](#0-1) 

Because the pointer's `transferFrom` override bypasses OZ's internal `_transfer`/state entirely and only talks to the CosmWasm contract, the inherited `safeTransferFrom` (which operates on the stale/never-populated internal OZ storage) cannot be used as a reliable, safe transfer path for this pointer's true token state. Practically, `transferFrom` — the unsafe variant lacking any `onERC721Received`-style check — is the only viable way to move these tokens through the EVM-side pointer.

This mirrors the reported bug class in the external report: using `transferFrom` instead of `safeTransferFrom` provides no guarantee that the destination address (an EVM contract, or a Sei address mapped to a contract) can accept/handle the NFT.

### Impact Explanation
Any EVM caller who owns (or is approved for) a CW721-backed NFT through the pointer contract can call `pointer.transferFrom(from, to, tokenId)` and send the NFT to a smart-contract address that is not designed to custody or forward NFTs. Since there is no `onERC721Received`-equivalent check and no safe alternative that actually operates on the correct (remote) state, the NFT's ownership is durably reassigned via `transfer_nft` on the CW721 contract to a Sei address tied to a contract with no mechanism to move it further — resulting in a permanently frozen/unrecoverable asset. This is a fund/asset-freezing issue reachable directly by any unprivileged transaction sender interacting with a public ERC721↔CW721 pointer.

### Likelihood Explanation
Any user with pointer approval or ownership of a token can trigger this by simply calling `transferFrom` with a contract recipient address, exactly as with any normal ERC721 transfer flow, and many wallets/dApp integrations default to `transferFrom` when a "safe" variant isn't clearly effective or documented for pointer contracts. Because the pointer is a standard user-facing EVM contract with no privileged access control on transfers, likelihood of a routine misuse (e.g., sending to an exchange/vault/contract that assumes safe-transfer semantics) is realistic.

### Recommendation
Implement a proper `safeTransferFrom` path for `CW721ERC721Pointer` that operates on the pointer's real (CW721-backed) state: after successfully executing `transfer_nft` in `transferFrom`, perform the standard `to.code.length == 0 || IERC721Receiver(to).onERC721Received(...) == selector` check (as done in the standalone `ERC721.sol` reference implementation) before finalizing, or expose `safeTransferFrom` as the primary/only transfer entry point that calls into this checked logic. Alternatively, explicitly document/gate `transferFrom` behind the same receiver check used in `safeTransferFrom` so unsafe transfers to non-compliant contracts are rejected by default.

### Proof of Concept
1. Deploy a `CW721ERC721Pointer` for an existing CW721 collection and acquire ownership of `tokenId` via the pointer as in `contracts/test/CW721ERC721PointerTest.t.sol` (`testTransferFrom`) [3](#0-2) .
2. Deploy an arbitrary contract `C` with no `onERC721Received` implementation and no logic to interact with CW721/pointer transfers.
3. Call `pointer.transferFrom(ownerEvmAddr, address(C), tokenId)`.
4. Observe the call succeeds (executes `transfer_nft` against the CW721 contract) exactly as shown in the transfer logic [4](#0-3) , permanently moving the NFT to the Sei address associated with `C`, which has no way to move or use the token further.

        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));

    function getApproved(uint256 tokenId) public view override returns (address) {
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("approvals", _curlyBrace(tId)));
        bytes memory response = WasmdPrecompile.query(Cw721Address, bytes(req));
        bytes[] memory approvals = JsonPrecompile.extractAsBytesList(response, "approvals");
        if (approvals.length > 0) {
            bytes memory res = JsonPrecompile.extractAsBytes(approvals[0], "spender");
            return AddrPrecompile.getEvmAddr(string(res));
        }
        return address(0);
    }

    // Transactions
    function transferFrom(address from, address to, uint256 tokenId) public override {
        if (to == address(0)) {
            revert ERC721InvalidReceiver(address(0));
        }
        require(from == ownerOf(tokenId), "`from` must be the owner");
        string memory recipient = _formatPayload("recipient", _doubleQuotes(AddrPrecompile.getSeiAddr(to)));
        string memory tId = _formatPayload("token_id", _doubleQuotes(Strings.toString(tokenId)));
        string memory req = _curlyBrace(_formatPayload("transfer_nft", _curlyBrace(_join(recipient, tId, ","))));
        _execute(bytes(req));
    }
