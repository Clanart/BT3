### Title
Infinite loop in `Offer.get_root_removal` via crafted parent-coin cycle in an untrusted offer file - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_root_removal()` walks a chain of `parent_coin_info` pointers among the coins listed in a `SpendBundle`'s removals, looking for a "non-ephemeral" ancestor coin. Because the `Coin` objects (`parent_coin_info`, `puzzle_hash`, `amount`) inside an offer file are fully attacker-controlled and are not validated against any real blockchain state before this method runs, an attacker can craft a `SpendBundle` where two or more removal coins reference each other as parents, forming a cycle. The `while` loop that walks parent pointers has no cycle detection and no bound, so it never terminates.

### Finding Description
`get_root_removal` computes the set of "non-ephemeral" removals (coins whose parent is not itself a coin being spent in the same bundle) and then walks parent links until it lands on one of them: [1](#0-0) 

```
def get_root_removal(self, coin: Coin) -> Coin:
    all_removals: set[Coin] = set(self.removals())
    all_removal_ids: set[bytes32] = {c.name() for c in all_removals}
    non_ephemeral_removals: set[Coin] = {
        c for c in all_removals if c.parent_coin_info not in {r.name() for r in all_removals}
    }
    if coin.name() not in all_removal_ids and coin.parent_coin_info not in all_removal_ids:
        raise ValueError("The specified coin is not a coin in this bundle")

    while coin not in non_ephemeral_removals:
        coin = next(c for c in all_removals if c.name() == coin.parent_coin_info)

    return coin
```

If an offer's `SpendBundle` contains two removal coins `A` and `B` such that `A.parent_coin_info == B.name()` and `B.parent_coin_info == A.name()`, then both `A` and `B` have their `parent_coin_info` present in `all_removal_ids`, so neither qualifies for `non_ephemeral_removals`. The `while` loop keeps calling `next(...)` and bounces forever between `A` and `B` (or among a longer attacker-chosen cycle), never reaching the loop's exit condition. There is no puzzle/solution execution, cost accounting, or hash-preimage requirement enforced here — `Coin.parent_coin_info` is an arbitrary `bytes32` supplied directly by the attacker in the offer bytes, and `SpendBundle`/`CoinSpend` deserialization does not verify that a coin's `parent_coin_info` corresponds to an actual coin created elsewhere in the bundle.

This is called via `get_primary_coins()`, which is invoked for every coin returned by `get_offered_coins()`: [2](#0-1) 

and `get_primary_coins`/`get_root_removal` are used from wallet-facing code paths (`chia/wallet/trade_manager.py`, `chia/wallet/trade_record.py`, `chia/cmds/wallet_funcs.py`) that process an incoming/untrusted `Offer` object, e.g. when a wallet inspects or accepts an offer file provided by an offer counterparty.

### Impact Explanation
Because `get_root_removal` is invoked while merely inspecting an offer (not requiring the offer to be signed correctly or valid on-chain), a malicious offer counterparty can hand a victim wallet an offer file that hangs the calling coroutine/thread indefinitely in a tight, CPU-bound Python loop. This matches the "spend-triggered transaction-processing halt" class from the Exiv2 infinite-loop analog: a single crafted, attacker-supplied blob (here, an offer bytes payload analogous to a crafted image file) causes an unbounded loop when parsed/processed by the victim application, denying that wallet flow (offer inspection/acceptance) until the process is killed.

### Likelihood Explanation
Constructing the malicious input requires only assembling a `WalletSpendBundle` with two or more `CoinSpend`s whose `Coin.parent_coin_info` values reference each other cyclically — no valid signatures, puzzle execution, or real on-chain coins are needed to reach the vulnerable comparison, since `get_root_removal` operates purely on the `Coin` metadata inside removals before any consensus-level validation. The attacker just needs to get the victim to load/inspect the offer (a normal step of the offer workflow), making this straightforward to trigger.

### Recommendation
Add cycle detection to `get_root_removal` (e.g., track visited coin names and raise a `ValueError`/return early if a coin is revisited, or bound iterations by `len(all_removals)`), and validate that `parent_coin_info` chains among removals are acyclic before trusting them in offer-summary/cancellation logic.

### Proof of Concept
Construct an `Offer`/`WalletSpendBundle` whose `coin_spends` include two coins:
- `A = Coin(parent_coin_info=B.name(), puzzle_hash=<offer puzzle hash>, amount=X)`
- `B = Coin(parent_coin_info=A.name(), puzzle_hash=<any>, amount=Y)`

with puzzle reveals/solutions crafted so that `get_offered_coins()` returns a coin whose ancestor chain routes through `A`/`B`. When the victim calls `offer.get_primary_coins()` (or any code path that calls `get_root_removal` for such a coin, e.g. inspecting a received offer), the `while coin not in non_ephemeral_removals` loop in [3](#0-2)  alternates between `A` and `B` forever, hanging the process.
