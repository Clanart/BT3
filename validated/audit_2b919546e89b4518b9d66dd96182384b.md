### Title
Time-lock on `AnkrBNBPoolHelper` positions can be bypassed by withdrawing/re-depositing directly through `MasterMagpie` — (File: `wombat/AnkrBNBPoolHelper.sol`, `rewards/MasterMagpie.sol`)

### Summary
`AnkrBNBPoolHelper.withdraw()` enforces the `unlockTime`/`lockedAmount` restriction only inside itself, by checking the caller's remaining stake in the `rewarder` after unstaking [1](#0-0) . The underlying position, however, is an ordinary `MasterMagpie` stake of `stakingToken`, and `MasterMagpie.withdraw`/`deposit` are plain, unprivileged, unrestricted entrypoints with no knowledge of the lock [2](#0-1) . A locked user can therefore unstake their receipt token directly via `MasterMagpie.withdraw`, move it to a fresh address with no `lockedAmount` recorded, re-stake it via `MasterMagpie.deposit`, and then call `AnkrBNBPoolHelper.withdraw()` from that fresh address to redeem the underlying Wombat LP value with the lock check trivially satisfied.

### Finding Description
The lock state lives only in `AnkrBNBPoolHelper.lockedAmount` and `unlockTime`, and is checked using `this.balance(msg.sender)`, i.e., the caller's balance in the pool's `rewarder` (their `MasterMagpie` stake) [3](#0-2) [4](#0-3) . Nothing in `MasterMagpie` itself is aware of this lock: `withdraw(address _stakingToken, uint256 _amount)` is a plain external function guarded only by `whenNotPaused`/`nonReentrant` and a simple `user.available < _amount` check, with no reference to any helper-level lock [5](#0-4) [6](#0-5) . Likewise `deposit(address _stakingToken, uint256 _amount)` is a plain external function anyone can call to stake `stakingToken` on behalf of themselves [7](#0-6) .

Exploit flow (all steps unprivileged):
1. A locked beneficiary (with `lockedAmount[user] > 0` set via `batchDepositLPFor` [8](#0-7) ) calls `MasterMagpie.withdraw(stakingToken, amount)` directly, bypassing `AnkrBNBPoolHelper` entirely. This unstakes the full amount of `stakingToken` (the receipt/LP-share token) to the caller's wallet as an ordinary transferable ERC20, with zero check on `unlockTime`/`lockedAmount`.
2. The user transfers this `stakingToken` to a second, "clean" address that has `lockedAmount == 0`.
3. The clean address calls `MasterMagpie.deposit(stakingToken, amount)` to re-stake under its own name — again a plain, unprivileged call.
4. The clean address calls `AnkrBNBPoolHelper.withdraw(_liquidity, _minAmount)`. Since `lockedAmount[cleanAddress] == 0`, the check `lockedAmount[msg.sender] > rest` is always false regardless of `unlockTime`, so the helper proceeds to call `WombatStaking.withdraw(...)` [9](#0-8) , which redeems the underlying Wombat LP and transfers the deposit token directly to the clean address — the value that was originally supposed to remain locked for a year.

This confirms the audit's core claim: the time restriction is enforced only in one "front-end" contract (`AnkrBNBPoolHelper`) and not where the position actually lives (`MasterMagpie`'s stake accounting), so it is trivially bypassable by routing through `MasterMagpie`'s own public `withdraw`/`deposit` functions.

Note: the specific mechanism theorized in the prompt (exploiting the ordering of `_liquidity`/`_minAmount` checks against the post-unstake `rest` balance to extract funds before the `revert NotAllowed()` fires) does **not** hold up — the `revert` inside `withdraw()` atomically reverts the entire transaction, including the prior `WombatStaking.withdraw` transfer, since there is no reentrant external hook on the standard ERC20 deposit token. The real, exploitable bypass is the cross-contract lock-enforcement gap described above.

### Impact Explanation
This allows a beneficiary of the Ankr 1-year lock compensation program to exit their position before `unlockTime`, defeating the entire purpose of the lock (e.g., anti-dump / vesting conditions attached to the ankr exploit compensation). Because the transferred/restaked amount exactly matches the user's own originally-allocated share, this is not a theft of *other users'* funds or a dilution of the shared Wombat LP pool — it only lets a locked holder access their own already-owned economic value early. It is a genuine time-lock/vesting-restriction bypass, but does not by itself cause loss of principal or backing for other users or the protocol.

### Likelihood Explanation
Trivial and fully repeatable: requires only two ordinary EOAs and standard ERC20 transfer/staking calls, no privileged role, no flash loan, no reentrancy — any locked beneficiary can execute it unassisted at any time before `unlockTime`.

### Recommendation
Enforce the lock at the position layer rather than only in the optional helper: e.g., add a lock-aware hook/check in `MasterMagpie.withdraw`/`deposit` for pools flagged as "locked", or make `stakingToken` non-transferable/soulbound for locked balances, or gate `MasterMagpie.withdraw` for this specific `stakingToken` so only the registered helper (`_onlyPoolHelper`) can invoke it, consistent with how `depositFor`/`withdrawFor` are already restricted.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `MasterMagpie`, `WombatStaking`, `AnkrBNBPoolHelper` with `unlockTime = now + 365 days`.
2. Via `ankrOperator`, call `batchDepositLPFor` to set `lockedAmount[userA] = X` and stake `X` `stakingToken` for `userA` in `MasterMagpie`.
3. Assert `AnkrBNBPoolHelper.withdraw(X, 0)` called by `userA` reverts with `NotAllowed()` (lock still active).
4. As `userA`, call `MasterMagpie.withdraw(stakingToken, X)` directly — assert it succeeds and `userA` now holds `X` raw `stakingToken` in wallet.
5. Transfer `X` `stakingToken` from `userA` to `userB` (fresh address, `lockedAmount[userB] == 0`).
6. As `userB`, call `MasterMagpie.deposit(stakingToken, X)` — assert success.
7. As `userB`, call `AnkrBNBPoolHelper.withdraw(X, 0)` — assert it **succeeds** (no revert) and `userB` receives the underlying `depositToken` (e.g., wBNB), despite `block.timestamp < unlockTime`.
8. Assert final invariant violation: locked value that should have been inaccessible until `unlockTime` was fully withdrawn before that time.
