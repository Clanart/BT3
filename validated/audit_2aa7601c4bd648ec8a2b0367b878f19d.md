### Title
ThresholdKeys deserialization validates participant indexes and curve ID but never binds `secret_share` to `verification_shares[i]`, letting a corrupted/malicious key blob cause the honest holder to be blamed as faulty - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) parses untrusted bytes into a `ThresholdKeys` via `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391). Analogous to CVE-2025-62420 — where `getJdbc` validates `jdbcUrl` but connects with a different `jdbc` field — `ThresholdKeys::new` validates `verification_shares` (count, index range) and derives `group_key` from `verification_shares[1..=t]` (line 376-378), but the `secret_share` field that is actually used to produce signature shares is never checked against `verification_shares[i]` (`G * secret_share == verification_shares[i]`). One field is validated; a different, unvalidated field is used.

### Finding Description
`ThresholdKeys::new` performs three checks:
- `verification_shares.len() == n` (line 355)
- every verification-share index `<= n` (line 361-365)
- interpolation applicability (line 367-374)

It then computes `group_key` solely from the verification shares and stores the caller-supplied `secret_share` verbatim into `ThresholdCore` (lines 380-388). No consistency check `C::generator() * secret_share == verification_shares[&i]` exists anywhere in `read`/`new`.

During signing, `ThresholdKeys::view` (crypto/dkg/src/lib.rs:463-533) interpolates this untrusted `secret_share` into `secret_share` (lines 493-498) while building `verification_shares` from the deserialized map (lines 500-506). In `AlgorithmSignatureMachine::complete` (crypto/frost/src/sign.rs:447-495), each participant's share — including our own, `responses[params.i()]` (line 455) — is verified with `algorithm.verify_share(view.verification_share(l), B.bound(l), share)` (lines 475-485). If the deserialized `secret_share` doesn't match `verification_shares[i]`, our share fails verification, and `complete` returns `FrostError::InvalidShare(i)` naming ourselves as the faulty party. Upstream (e.g., processor/src/signer.rs, batch_signer.rs, slash_report_signer.rs), `InvalidShare(l)` is turned into a `ProcessorMessage::InvalidParticipant`/`InvalidShare` blame report — i.e., an on-chain attribution of fault to the honest holder of the corrupt key material.

### Impact Explanation
An inconsistent `secret_share`/`verification_shares[i]` pair produces deterministically-invalid signature shares that cryptographically "prove" the holder is faulty. In Serai, blame feeds slashing, so a victim deserializing attacker-influenced `ThresholdKeys` bytes (key backup, DB restore, or any channel feeding `ThresholdKeys::read`) is framed as malicious during signing and is liable to be slashed. Medium severity: requires write influence over key material consumed by `read`, and the outcome is wrongful blame/DoS rather than key extraction.

### Likelihood Explanation
The `read` path enforces curve ID, participant-index validity, interpolation-tag validity, and canonical encodings, giving the appearance of full validation while silently accepting a share that contradicts the public verification share. All other production constructors (`dealer::key_gen`, `musig`, `pedpop::calculate_share`) internally guarantee consistency, so the bug is reachable only through deserialization of inconsistent bytes — which is exactly the documented purpose of `ThresholdKeys::read`/`serialize` for persistence. Any compromised or corrupt key store triggers it deterministically at the next signing session.

### Recommendation
In `ThresholdKeys::new` (or at minimum in `ThresholdKeys::read`), verify `C::generator() * secret_share == verification_shares[&params.i()]` and reject otherwise. This eliminates the validated-field/used-field split.

### Proof of Concept
1. Serialize a valid `ThresholdKeys` for participant `i` via `write`, then modify only the `secret_share` scalar bytes (e.g., add 1) while leaving `verification_shares` untouched.
2. `ThresholdKeys::<C>::read(&mut bytes)` succeeds — every check in `read`/`new` passes.
3. Build an `AlgorithmMachine::new(alg, tampered_keys)` and run a normal t-of-n signing session with honest peers.
4. `complete` fails signature verification, enters the per-share blame path, and `verify_share(view.verification_share(i), ...)` rejects the victim's own share: `FrostError::InvalidShare(i)` blames the honest holder of the inconsistent blob.

Note: exploitation depends on an attacker influencing the bytes consumed by `ThresholdKeys::read` (documented persistence API); if that input is strictly trusted in every deployment, the finding reduces to a hardening gap.
