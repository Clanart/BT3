### Title
Front-running/flash deposit into `MasterMagpie` can be used to steal a disproportionate share of newly injected `BaseRewardPool`/`BaseRewardPoolV2` rewards - (File: `rewards/BaseRewardPool.sol`, `rewards/BaseRewardPoolV2.sol`, `rewards/MasterMagpie.sol`)

### Summary
`BaseRewardPool`/`BaseRewardPoolV2` compute the global `rewardPerTokenStored` increment for a newly injected reward as `_amountReward * 1e_decimals / totalStaked()`, where `totalStaked()` is simply the live `stakingToken` balance held by `MasterMagpie` at the moment the reward is provisioned. An attacker can deposit a large amount of the staking token into `MasterMagpie` immediately before a reward injection (via the permissionless `donateRewards`, or by front-running a manager's `queueNewRewards` call in the same block), causing the numerator/denominator math to award them nearly the entire newly-queued reward, then withdraw their principal right after. This is directly analogous to the Compound `refreshCompSpeeds` flash-borrow reward manipulation described in the external report: an economically-neutral, single-block capital deployment used to seize a disproportionate share of reward emissions that were meant to be earned by long-term stakers.

### Finding Description
`_provisionReward` in `BaseRewardPool.sol` updates the cumulative reward index using the pool's current total staked balance: [1](#0-0) 

`totalStaked()` is defined as the live token balance of the `MasterMagpie` operator contract, which changes instantly with every `deposit`/`withdraw` call: [2](#0-1) 

Crucially, an individual user's earned reward for the increment is `balanceOf(account) * increment`, where `increment = R * 1e_decimals / totalStaked()`. If an attacker deposits amount `X` immediately before a reward `R` is injected (raising `totalStaked` from `S` to `S+X`), their share of that specific increment becomes `X * R / (S + X)`, which tends to `R` as `X` grows — i.e., the attacker can capture nearly the whole reward regardless of how briefly they hold the stake, while diluting the increment applied to every other staker's existing balance.

`MasterMagpie.deposit`/`withdraw` have no lock-up, cooldown, or minimum holding period, and reward accounting (`_harvestBaseRewarder` → `rewarder.updateFor`) is applied instantaneously on withdraw, locking in the attacker's inflated `userRewards` before they exit: [3](#0-2) [4](#0-3) 

The reward-injection entry point `donateRewards` is fully permissionless (anyone may call it for an already-registered reward token), and the privileged `queueNewRewards` path (invoked e.g. by `WombatBribeManager.castVotes`/`WombatStaking` reward forwarding) can be trivially front-run/sandwiched by watching the mempool, since there is no time-weighting or vesting on the staked balance used as the denominator: [5](#0-4) 

This mirrors the exact bug class in the external report: a value that determines reward distribution (`totalBorrows` there, `totalStaked()`/live balance here) can be manipulated within a single block or by ordinary transaction ordering, letting an attacker capture rewards that rightfully belong to other participants, at only the cost of gas (or flash-loan fees for the staking token if not self-funded).

### Impact Explanation
This is a direct theft of unclaimed yield from legitimate long-term stakers of `MasterMagpie` pools. Each time a reward is injected while an attacker's inflated deposit is present, the increment applied to honest stakers' balances is diluted, and the attacker walks away with the lion's share of that reward tranche, repeatable for every reward injection event (bribe casting, manager-queued rewards, or attacker-triggered `donateRewards`).

### Likelihood Explanation
Deposit/withdraw functions are unrestricted, permissionless, and instantaneous with no cooldown, and `donateRewards` requires no privilege at all. Any holder of the staking token (or anyone who can flash-borrow it) can execute this attack whenever a reward injection is imminent or self-triggered, making this a highly reachable, unprivileged-wallet exploit.

### Recommendation
Base the reward-distribution denominator on a time-weighted or snapshot staked balance rather than the instantaneous live balance, and/or introduce a minimum staking duration before a deposit is eligible to receive a share of newly injected rewards (e.g., only count balances that existed at the start of the reward period). Alternatively, restrict `donateRewards`/reward-injection timing to reduce predictability, though this only partially mitigates the flash-deposit sandwich vector for manager-triggered `queueNewRewards` calls.

### Proof of Concept
1. Attacker observes (or self-triggers via `donateRewards`) an imminent reward injection into a `BaseRewardPool`/`BaseRewardPoolV2` for staking token `T`.
2. In the same block, attacker calls `MasterMagpie.deposit(T, X)` with a very large `X` (own capital or flash-borrowed `T`), inflating `totalStaked()` from `S` to `S+X`. [6](#0-5) 
3. The reward-injection transaction executes, calling `_provisionReward`, which computes `increment = R * 1e_decimals / (S+X)` and updates `rewardPerTokenStored`. [7](#0-6) 
4. Attacker immediately calls `MasterMagpie.withdraw(T, X)`, which internally calls `rewarder.updateFor` to lock in `userRewards[attacker] ≈ X * increment ≈ R` (nearly the entire injected reward) before removing their stake. [8](#0-7) 
5. Attacker later calls `multiclaim`/`getReward` to withdraw the stolen reward tokens, having paid only gas (plus flash-loan fee, if applicable) and held zero net exposure to `T`.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
