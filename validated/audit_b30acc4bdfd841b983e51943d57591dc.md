### Title
Unbounded recursive `AccountKey` RLP decoding causes stack-overflow DoS via crafted `AccountUpdate` transaction - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each of its inner keys through `AccountKeySerializer.DecodeRLP`, and `NewAccountKey`/the serializer place no restriction on an inner key itself being another `AccountKeyRoleBased`. An attacker can therefore construct an `AccountUpdate`/`FeeDelegatedAccountUpdate` (and related) transaction whose account-key field is an arbitrarily deep chain of nested `RoleBased` keys. Decoding such a transaction (which happens on every node that receives it, e.g. via `eth_sendRawTransaction`, `txpool`, or block/tx broadcast) recurses once per nesting level with no depth limit, which can exhaust the goroutine stack and crash the node — the same class of bug as CVE-2020-36367 (unbounded recursive parser causing a stack-overflow DoS), just triggered through Kaia's account-key RLP decoder instead of mjs's `parse_block`.

### Finding Description
`AccountKeyRoleBased` is decoded like this: [1](#0-0) 

Each element `enc[i]` is itself RLP-decoded via `AccountKeySerializer.DecodeRLP`: [2](#0-1) 

`serializer.key` is constructed with `NewAccountKey(serializer.keyType)`, which happily returns a new `AccountKeyRoleBased` for `AccountKeyTypeRoleBased` with no check that this would create a nested/composite key: [3](#0-2) 

This means `AccountKeyRoleBased.DecodeRLP` → `AccountKeySerializer.DecodeRLP` → `s.Decode(serializer.key)` → (if `serializer.key` is again `AccountKeyRoleBased`) → `AccountKeyRoleBased.DecodeRLP` … forms an unbounded recursive call chain whose depth is entirely controlled by the RLP payload the attacker sends. There is no depth limit anywhere in this decode path (unlike the RLP package's `Stream` which limits list *sizes* but not decoder recursion depth for nested Decoder-implementing types).

The only place that rejects a `RoleBased` key nested inside a `RoleBased` key is `checkAccountKeyZeroValues`, which is exclusively used by the `kaia_encodeAccountKey` JSON-RPC API path (client-side helper), not by the transaction decoding/validation path used when a transaction is received and processed: [4](#0-3) 

Transactions carrying an `AccountUpdate`-family payload go through `TxInternalDataAccountUpdate.DecodeRLP` (and the fee-delegated variants), which directly RLP-decode the serializable struct containing the raw account-key bytes and then decode the `AccountKey` via the vulnerable path: [5](#0-4) 

The outer transaction envelope decoding (`Transaction.DecodeRLP` → `TxInternalDataSerializer.DecodeRLP`) is exactly the code path invoked for every transaction received by the node before any pool-admission or signature validation occurs, i.e. before the "nested role-based key" business-rule error would ever be surfaced: [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged transaction sender/public-RPC caller can craft a raw transaction (e.g. `TxTypeAccountUpdate` or `TxTypeFeeDelegatedAccountUpdate*`) whose account-key bytes encode thousands of nested `AccountKeyRoleBased` levels. Submitting this transaction via `eth_sendRawTransaction`/`kaia_sendRawTransaction` (or via p2p tx propagation once accepted by one node) forces every node that decodes it — including during mempool admission, block validation, and block import/re-execution by all honest nodes — to recurse until the goroutine stack limit is exceeded, crashing the node process. Because this affects every node that decodes the transaction (mempool nodes, block proposers, and all nodes replaying the block), this is a network-wide Denial-of-Service, matching the Medium severity of the original CVE (stack overflow DoS) but with a broader consensus-wide reach in a blockchain node context.

### Likelihood Explanation
High likelihood of reachability: any account holding funds to pay gas, or even a transaction with `Value: 0`/minimal gas targeting `AccountUpdate`, can be crafted entirely offline (no special key material required for the malformed nested key bytes; only a valid signature over the tx hash is needed, which the attacker fully controls since they sign their own transaction). No preconditions such as validator status, peer trust, or special privileges are needed — a straightforward `sendRawTransaction` call from any externally-owned account suffices.

### Recommendation
Enforce a maximum recursion/nesting depth for `AccountKeyRoleBased` decoding at the RLP-decode level (not only in the JSON API helper), e.g., pass a depth counter through `AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP` and return an error (`kerrors.ErrUnserializableKey` or a new "nested RoleBased key not allowed" error) if `AccountKeyTypeRoleBased` is encountered while already decoding inside a `RoleBased` context, mirroring the existing `isNested` check in `checkAccountKeyZeroValues`. This should be enforced unconditionally during `DecodeRLP`, independent of the JSON-RPC helper.

### Proof of Concept
Conceptually (illustrating the recursive structure an attacker RLP-encodes as the `Key` field of an `AccountUpdate` transaction):
```
AccountKeySerializer{
  keyType: AccountKeyTypeRoleBased,
  key: AccountKeyRoleBased{
    AccountKeySerializer{ keyType: AccountKeyTypeRoleBased, key: AccountKeyRoleBased{ ... nested N times ... } },
    ... (RoleAccountUpdate, RoleFeePayer slots, similarly nested)
  }
}
```
Encoding this nested structure to raw bytes (using `rlp.EncodeToBytes` on the `AccountKeySerializer`, recursively wrapping N times) and placing it as the `Key`/account-key field of a properly-signed `TxTypeAccountUpdate` transaction, then submitting it via `eth_sendRawTransaction`, will cause `AccountKeyRoleBased.DecodeRLP` to recurse N times when any node decodes the transaction (`blockchain/types/tx_internal_data_account_update.go:163-175` → `blockchain/types/accountkey/account_key_serializer.go:61-73` → `blockchain/types/accountkey/account_key_role_based.go:120-138`), consuming stack space proportional to N until a sufficiently large N triggers a fatal stack overflow / node crash. Verifying the exact N required to crash a Go binary depends on runtime stack-growth limits and was not measured in this analysis; further exploitation confirmation (actual crash reproduction) would require running the decode path in a test harness with a maliciously constructed payload, which was not part of this static review.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

// checkAccountKeyZeroValues returns errors if the input account key contains zero values of threshold or weight.
func checkAccountKeyZeroValues(key accountkey.AccountKey, isNested bool) error {
	switch key.Type() {
	case accountkey.AccountKeyTypeWeightedMultiSig:
		multiSigKey, _ := key.(*accountkey.AccountKeyWeightedMultiSig)
		if multiSigKey.Threshold == 0 {
			return errors.New("invalid threshold of the multiSigKey")
		}
		for _, weightedKey := range multiSigKey.Keys {
			if weightedKey.Weight == 0 {
				return errors.New("invalid weight of the multiSigKey")
			}
		}
	case accountkey.AccountKeyTypeRoleBased:
		if isNested {
			return errors.New("roleBasedKey cannot contains a roleBasedKey as a role key")
		}
		roleBasedKey, _ := key.(*accountkey.AccountKeyRoleBased)
		for _, roleKey := range *roleBasedKey {
			if err := checkAccountKeyZeroValues(roleKey, true); err != nil {
				return err
			}
		}
	}

func (serializer *TxInternalDataSerializer) DecodeRLP(s *rlp.Stream) error {
	if err := s.Decode(&serializer.txType); err != nil {
		// fallback to the original transaction decoding.
		txd := newEmptyTxInternalDataLegacy()
		if err := s.Decode(txd); err != nil {
			return err
		}
		serializer.txType = TxTypeLegacyTransaction
		serializer.tx = txd
		return nil
	}

	if serializer.txType == EthereumTxTypeEnvelope {
		var ethType TxType
		if err := s.Decode(&ethType); err != nil {
			return err
		}
		serializer.txType = serializer.txType<<8 | ethType
	}

	var err error
	serializer.tx, err = NewTxInternalData(serializer.txType)
	if err != nil {
		return err
	}

	return s.Decode(serializer.tx)
}
