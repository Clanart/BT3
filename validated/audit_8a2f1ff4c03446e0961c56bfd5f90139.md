## Analysis

The Poseidon report's core issue is an **ambiguous/non-injective encoding**: several distinct logical inputs get serialized to the same underlying value because the encoding function does not unambiguously delimit or length-prefix its inputs, so two different objects collide into one value.

Desktop has a direct structural analog in the way it derives cache-identity hashes for `Repository` and `GitHubRepository` objects. [1](#0-0) 

`createEqualityHash` builds the "hash" solely by `Array.join('+')` on the raw field values, with no escaping of `+` inside the values and no length-prefixing — i.e. the same non-injective, unvalidated-concatenation pattern that caused the Poseidon collision.

This hash is used as the sole identity key for:
- `GitHubRepository.hash`, built from `name`, `owner.login`, `dbID`, `isPrivate`, `htmlURL`, `cloneURL`, `issuesEnabled`, `isArchived`, `permissions`, `parent?.hash` [2](#0-1) 
- `Repository.hash`, built from `path`, `id`, `gitHubRepository?.hash`, `missing`, `alias`, `workflowPreferences.forkContributionTarget`, `isTutorialRepository` [3](#0-2) 

That string is then used as a bare `Map<string, …>` key in security/state-relevant caches — critically `RepositoryStateCache`, which stores per-repository working-directory status, staged files, commit message, and pull-request state, keyed purely by string equality of `repository.hash` with no secondary object-identity check: [4](#0-3) [5](#0-4) 

`GitStoreCache` uses the same `repository.hash` key to reuse `GitStore` instances across repositories: [6](#0-5) 

### Title
Non-injective `+`-delimited repository identity hash allows cross-repository state-cache collision - (File: app/src/models/equality-hash.ts)

### Summary
`createEqualityHash` concatenates heterogeneous fields with a bare `+` separator without escaping `+` characters that may appear inside the field values themselves (`htmlURL`, `cloneURL`, `path`, `alias`, etc.). Because two different tuples of fields can serialize to the identical joined string when a `+` inside one field's value shifts to look like a field boundary, two structurally different `Repository`/`GitHubRepository` objects can produce the same `.hash`. This hash is the sole key used by `RepositoryStateCache` and `GitStoreCache` to isolate per-repository UI and Git state, so a collision causes Desktop to serve/merge state (working directory selection, staged files, commit message, pull-request state, or a live `GitStore`) belonging to one repository into another.

### Finding Description
The comment on both `Repository.hash` and `GitHubRepository.hash` explicitly documents the invariant relied upon elsewhere in the app: "Objects with the same hash are guaranteed to be structurally equal" [7](#0-6) . This invariant is false whenever any concatenated field can itself contain the `+` delimiter, because `Array.join('+')` provides no length-prefixing or escaping — exactly the missing-injectivity defect described in the Poseidon report (zero-padding implicitly making distinct inputs equivalent). `htmlURL` and `cloneURL` on `GitHubRepository` are populated directly from API/remote metadata (`html_url`, `clone_url`) with no character-set validation before being fed into `createEqualityHash`, so a GitHub Enterprise endpoint or a proxy sitting in front of API traffic — both attacker-controlled surfaces per the accepted threat model — can return URL strings engineered to redistribute `+` characters across the joined tuple, producing a `GitHubRepository.hash`/`Repository.hash` collision with an unrelated, legitimately-cloned repository the user already has open.

### Impact Explanation
`RepositoryStateCache.get/update` key exclusively on `repository.hash` [4](#0-3) . If a malicious/compromised GitHub Enterprise server crafts repository metadata whose `Repository.hash` collides with a different, real repository already tracked in Desktop, the two repositories' `IRepositoryState` entries share the same cache slot: working-directory file selection, staged changes, in-progress commit message, and multi-commit-operation state can leak or be overwritten across repositories. This is a silent-corruption-of-what-the-user-commits primitive — a user could end up committing or pushing content associated with the wrong repository's state without any error being surfaced, since the collision is invisible (both entries look like a normal cache hit). `GitStoreCache` reusing a `GitStore` instance across repositories under the same failure mode would additionally use the wrong repository's live Git operations. No error handling exists for this case; the code assumes hash equality implies object equality everywhere it is used.

### Likelihood Explanation
Exploitation requires the user to be connected to a hostile or compromised GitHub Enterprise Server / API proxy (accepted attacker model: "a git remote/proxy response") that controls `html_url`/`clone_url` values returned for a repository, and requires the user to also have another, colliding repository open in the same Desktop session — GitHub.com itself constrains `owner.login`/`name` character sets, so genuine on-`github.com` account fields cannot alone produce the delimiter collision, making GHE/custom-endpoint scenarios the primary reachable path. This narrows likelihood versus a fully generic collision, but it remains a concrete, code-verifiable weak-construction defect with no compensating validation anywhere in the pipeline from API response to cache key.

### Recommendation
Replace `createEqualityHash`'s bare `join('+')` with an injective encoding — e.g. JSON.stringify of the ordered tuple, or length-prefixing each field (`${len}:${value}` concatenation) before joining — so that no two distinct field tuples can serialize to the same string, matching the fix applied to the Poseidon sponge (enforce a canonical, unambiguous encoding of variable-content inputs).

### Proof of Concept
1. Point Desktop at (or otherwise cause an API response to be served by) a controlled/compromised GitHub Enterprise endpoint.
2. Craft two distinct `IAPIFullRepository` responses, RepoA and RepoB, whose `owner.login`, `name`, `private`, `has_issues`, `archived`, `permissions`, and `parent` fields match an already-tracked legitimate repository, but whose `html_url`/`clone_url` differ only in where an embedded `+` character sits, such that:
   `name+owner.login+dbID+isPrivate+htmlURL_A+cloneURL_A+... === name+owner.login+dbID+isPrivate+htmlURL_B+cloneURL_B+...`
   (achievable because `join('+')` does not escape `+` occurring inside `htmlURL`/`cloneURL`).
3. Add/clone both repositories in Desktop. `GitHubRepository.hash` (and consequently `Repository.hash`) collide despite the two repositories being distinct.
4. Observe that `RepositoryStateCache.get()` for the second repository returns the `IRepositoryState` object created for the first (`app/src/lib/stores/repository-state-cache.ts:36-45`), i.e. working-directory/commit-message/PR state from RepoA appears when RepoB is selected, verifying the cross-repository state bleed.

    if (this.gitStores.has(repository.hash)) {

    }
  }

  public get(repository: Repository): GitStore {
    let gitStore = this.gitStores.get(repository.hash)
    if (gitStore === undefined) {
      gitStore = new GitStore(repository, this.shell, this.statsStore)
      gitStore.onDidUpdate(() => this.onGitStoreUpdated(repository, gitStore!))
      gitStore.onDidError(error => this.onDidError(error))

      this.gitStores.set(repository.hash, gitStore)
    }

    return gitStore
  }
