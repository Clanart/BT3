### Title
PedPoP accepts the identity encryption key, making secret shares publicly decryptable - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptionKeyMessage::read` accepts any canonical group element as a participant’s ECDH encryption key, including the identity element. If a participant advertises the identity key, every sender derives the publicly known identity ECDH result, so anyone observing the encrypted secret-share messages can derive the ChaCha20 stream and recover that participant’s shares.

### Finding Description
The vulnerable deserialization path stores `enc_key` directly after `C::read_G`, with no identity rejection or proof binding the key to its owner’s secret. [1](#0-0)  The generic `Ciphersuite::read_G` validates only that a point is valid and canonical; unlike FROST’s curve-specific `read_G`, it does not reject identity. [2](#0-1) [3](#0-2) 

`Decryption::register` inserts the supplied key without validation, and `Encryption::encrypt` later uses it as the ECDH recipient public key. [4](#0-3) [5](#0-4)  ECDH computes `public * private`, which is always identity when `public` is identity. [6](#0-5)  The cipher key is derived solely from public context and this shared point, with a fixed IV, so the identity result produces a publicly derivable keystream. [7](#0-6) 

### Impact Explanation
A malicious participant can publish the identity element as its encryption key. Honest participants then encrypt their PedPoP secret shares to that participant under the publicly known identity shared secret. Anyone who observes those encrypted messages can derive the same keystream, decrypt all shares addressed to that participant, and combine them to recover the participant’s final threshold key share. This is an unauthenticated remote key-share disclosure caused by accepting a forbidden semantic value in a syntactically valid encoding, matching the parser-validation bypass class.

### Likelihood Explanation
The attack requires the adversary to control or corrupt one DKG participant announcement, but no discrete-log knowledge, private-key access, collision, or protocol race is required. The serialized identity key is canonical and therefore survives all existing validation. The disclosed value is the threshold share belonging to the malicious participant’s identifier; while that participant would normally receive the corresponding plaintext, the flaw exposes it to all observers and reduces the threshold security of the resulting key whenever that share is otherwise treated as secret.

### Recommendation
Reject the identity element for `enc_key` in `EncryptionKeyMessage::read` or immediately after `C::read_G`. Prefer a dedicated key-reading helper that applies canonical decoding, identity rejection, and any other protocol-required subgroup checks at the trust boundary. The same check should be applied to `EncryptedMessage::key` and `EncryptionKeyProof::key` before ECDH or decryption-key verification uses them.

### Proof of Concept
1. Participant `i` creates an otherwise valid `EncryptionKeyMessage` whose `msg` contains valid `Commitments`, but whose trailing `enc_key` is the canonical identity encoding.
2. Each honest participant deserializes it with `EncryptionKeyMessage::<C, Commitments<C>>::read`, then `Decryption::register` stores identity under participant `i`.
3. During `generate_secret_shares`, each honest participant calls `encrypt(..., identity, share)`. For every ephemeral scalar `k`, ECDH computes `k * identity = identity`.
4. An observer reconstructs the transcript using the known session `context` and the encoding of identity, obtains the ChaCha20 key, applies the fixed `b"DKG IV v0.2\0"` IV, and decrypts every ciphertext addressed to `i`.
5. The observer adds the decrypted PedPoP shares to recover participant `i`’s final threshold secret share.

  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
    reader.read_exact(encoding.as_mut())?;

    let point = Option::<Self::G>::from(Self::G::from_bytes(&encoding))
      .ok_or_else(|| io::Error::other("invalid point"))?;
    if point.to_bytes().as_ref() != encoding.as_ref() {
      Err(io::Error::other("non-canonical point"))?;
    }
    Ok(point)
