Based on my investigation, I found a genuine analog: `BidPool.AddBid` in the auction module inserts a bid into shared, concurrently-read pool state (`bidMap`/`bidTargetMap`/`bidWinnerMap`) *before* an error path can fail, and on that error path it does not roll back the insertion — leaving a partially-initialized, already-exposed bid reachable by the block-building path.

### Title
Auction BidPool leaves half-initialized bid exposed to block-building path after gas-limit computation fails - ([File: kaiax/auction/impl/bid_pool.go])

### Summary
`BidPool.AddBid` calls `insertBid()` — which publishes the bid into `bp.bidMap`, `bp.bidTargetMap`, and `bp.bidWinnerMap` under `bidMu` — and only afterward calls `bp.getBidTxGasLimit(bid)`. If that later step returns an error, `AddBid` returns the error to the RPC caller, but never removes the bid it just inserted. The bid remains live in the pool with `GasLimit` unset (zero value), reachable via `GetTargetTxMap`/`getTargetTxHashMap` by the concurrently running block-builder (`AuctionModule.ExtractTxBundles`, `FilterTxs`) and other RPC/API readers, even though the API caller believes the bid submission failed.

### Finding Description
`AddBid` (`kaiax/auction/impl/bid_pool.go:252-274`) performs, in order: `validateBid` → `insertBid` (exposes bid to `bidMap`/`bidTargetMap`/`bidWinnerMap`) → `getBidTxGasLimit` → `bid.SetGasLimit(gasLimit)` → publish to `newBidCh`. [1](#0-0) 

Unlike the netfilter flowtable bug (where a hook is registered, exposing the object to the packet path, and the error-path teardown fails to synchronize with in-flight users before freeing), here the analogous pattern is: the bid map insertion is the "hook registration" that exposes the object to concurrent consumers (block builder, `GetTargetTxMap`), and the subsequent fallible step (`getBidTxGasLimit`) has no compensating removal on error. `insertBid` itself has no failure-cleanup path either — it commits the bid to all three maps unconditionally once past its own checks. [2](#0-1) 

Because `ExtractTxBundles` reads `bidTargetMap` via `GetTargetTxMap` independently and asynchronously from `AddBid`, a bid that failed gas-limit computation but is still resident in the map can be picked as the winning bid for its target transaction during block assembly. `GetBidTxGenerator` (called from `ExtractTxBundles`) checks `if bid.GetGasLimit() == 0` and re-attempts `getBidTxGasLimit`, but if that computation is deterministically failing (e.g. it depends on state that consistently errors, or a race with `validateBidSigs`/`getBidTxGasLimit` implementation details), the winning bid's bundle transaction generation fails at block-building time — after the bid has already displaced/blocked other legitimate bids for the same target/sender via `bidWinnerMap`/`bidTargetMap`. [3](#0-2) [4](#0-3) 

This directly matches the reachable-analog criteria: a single unprivileged `SubmitBid` RPC call from an auction bidder can create pool state that is exposed to block assembly before validation/initialization is fully complete and never cleaned up on the observed error, unlike the CVE's hooks which at least get unregistered (just not RCU-synced). Here the state isn't even unregistered.

### Impact Explanation
A malicious searcher/bidder can call `auction_submitBid` (`SubmitBid` in `kaiax/auction/impl/api.go:118-142`) with a bid engineered so that `insertBid` succeeds (occupying the sender's winner slot and the target's bid slot, evicting or blocking any better bid for that target/sender) but `getBidTxGasLimit` subsequently errors. [5](#0-4)  Because `senderHasDifferentWinner` and the FCFS/highest-bid replacement logic in `insertBid` treat this stuck bid as the current winner for the block/target/sender, legitimate subsequent bids from the same sender are rejected (`ErrBidSenderExists`) or lower bids for the same target are rejected (`ErrLowBid`) even though the "winning" bid can never be turned into a valid transaction. This can be used to grief/block the auction for the target transaction and starve auction fee revenue for that block, and — if `GetBidTxGenerator`'s recomputation of `getBidTxGasLimit` at build time can succeed intermittently with degenerate values — could also affect gas accounting on the resulting bid settlement.

### Likelihood Explanation
The path is trivially reachable with a single public RPC call (`SubmitBid`). Whether `getBidTxGasLimit` can actually be made to fail post-`insertBid` from attacker-controlled bid fields could not be confirmed since the function body was not located during this review (only its call sites in `bid_pool.go`, `builder.go`, `getter.go` were found). This is the main uncertainty: without seeing `getBidTxGasLimit`'s implementation, I cannot fully confirm the exact triggering condition, only that the missing rollback-on-error in `AddBid`/`insertBid` is structurally present and reachable by any bidder.

### Recommendation
In `BidPool.AddBid`, if any step after `insertBid` (e.g., `getBidTxGasLimit`) fails, explicitly remove the just-inserted bid from `bidMap`, `bidTargetMap`, and `bidWinnerMap` (mirroring the cleanup already implemented in `removeOldBids`) before returning the error, so a failed bid submission never remains reachable by the block-building path or blocks slots for legitimate bids.

### Proof of Concept
1. Submit a bid via `auction_submitBid` RPC with a valid target transaction and valid signatures, but with `CallGasLimit`/`Data` crafted so `bp.getBidTxGasLimit(bid)` (invoked after `insertBid`) returns an error.
2. Observe `SubmitBid` returns an error to the caller, but the bid is now present in `bp.bidMap`, `bp.bidWinnerMap[blockNumber][sender]`, and `bp.bidTargetMap[blockNumber][targetTxHash]` (verifiable via `BidPool` internal state or by submitting a second, valid bid from the same sender for a different target and observing `ErrBidSenderExists`, or a higher bid for the same target and observing it is only "replaced" if `Bid.Cmp` succeeds against the broken bid).
3. Confirm that at block-building time, `ExtractTxBundles`/`GetBidTxGenerator` either fails to produce a bid transaction for that target (auction slot wasted) or that the target's auction is effectively griefed for that block.

**Note:** I was unable to view the full implementation of `getBidTxGasLimit` within the tool call budget, so the exact conditions under which it fails post-insertion (and whether an attacker can reliably trigger it) remain unverified. A Devin session with full repository access would be needed to confirm the precise trigger and validate the fix.

// AddBid adds a bid to the bid pool.
// Required mutex is locked in each function.
func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
}

func (bp *BidPool) insertBid(bid *auction.Bid) error {
	bp.bidMu.Lock()
	defer bp.bidMu.Unlock()

	var (
		blockNumber  = bid.BlockNumber
		targetTxHash = bid.TargetTxHash
		sender       = bid.Sender
	)

	// Re-check bidWinnerMap here — two concurrent bids can pass validateBid together.
	if _, ok := bp.bidMap[bid.Hash()]; ok {
		return auction.ErrBidAlreadyExists
	}
	if bp.senderHasDifferentWinner(bid) {
		return auction.ErrBidSenderExists
	}

	// If same block number, same target tx hash exists, replace it if it's better
	if existingBid, ok := bp.bidTargetMap[blockNumber][targetTxHash]; ok {
		// FCFS if the bid is the same.
		if existingBid.Bid.Cmp(bid.Bid) >= 0 {
			return auction.ErrLowBid
		}

		logger.Trace("Replace bid", "old", existingBid.Hash(), "new", bid.Hash())
		delete(bp.bidMap, existingBid.Hash())
		delete(bp.bidWinnerMap[blockNumber], existingBid.Sender)
	} else {
		if int64(len(bp.bidMap)) >= bp.maxBidPoolSize {
			logger.Info("Bid pool is full", "maxBidPoolSize", bp.maxBidPoolSize, "bid", bid.Hash())
			return auction.ErrBidPoolFull
		}
	}

	hash := bid.Hash()

	bp.initializeBidMap(blockNumber)

	bp.bidMap[hash] = bid
	bp.bidTargetMap[blockNumber][targetTxHash] = bid
	bp.bidWinnerMap[blockNumber][sender] = hash

	numBidsGauge.Update(int64(len(bp.bidMap)))

	logger.Trace("Add bid", "bid", hash)

	return nil
}

func (a *AuctionModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	bundles := []*builder.Bundle{}
	curBlock := a.Chain.CurrentBlock()
	if curBlock == nil || atomic.LoadUint32(&a.bidPool.running) == 0 {
		return bundles
	}

	miningBlock := curBlock.NumberU64() + 1
	bidTargetMap := a.bidPool.GetTargetTxMap(miningBlock)
	if len(bidTargetMap) == 0 {
		return bundles
	}

	for _, tx := range txs {
		txHash := tx.Hash()
		bid, ok := bidTargetMap[txHash]
		if !ok {
			continue
		}
		b := builder.NewBundle(
			builder.NewTxOrGenList(a.GetBidTxGenerator(tx, bid)),
			txHash,
			true,
		)

		isConflict := false
		for _, prev := range append(prevBundles, bundles...) {
			if prev.IsConflict(b) {
				isConflict = true
				break
			}
		}
		if isConflict {
			continue
		}
		bundles = append(bundles, b)
	}

	return bundles
}
