### Title
Distribution precompile's `rewards()` view method omits the non-payable guard, permanently stranding EVM value sent to it - (File: precompiles/distribution/distribution.go)

### Summary
The `rewards()` method of the distribution precompile (`0x0000000000000000000000000000000000001007`) is dispatched without a `ValidateNonPayable` check and without any `HandlePaymentUsei`/fund-forwarding logic. Any caller can invoke `rewards()` with non-zero `msg.value`; the EVM's native call semantics move that value into the precompile address's balance before `Run`/`Execute` is even entered, but the precompile never consumes, refunds, or redistributes it. Because the precompile address is not a real contract and not on the "payable precompile" list that has fund-handling wiring, the sent funds become permanently unrecoverable — the same "residual/undistributed funds get stuck with no way out" bug class described in the external report for `AgentPolice.distributeLiquidatedFunds()`.

### Finding Description
In `precompiles/distribution/distribution.go`, the dispatcher explicitly does **not** validate non-payability for the `RewardsMethod` case, unlike every other transaction-like method in the same switch: [1](#0-0) 

Compare this to sibling query methods such as `ParamsMethod`, `ValidatorOutstandingRewardsMethod`, etc., and to write methods like `WithdrawValidatorCommissionMethod`, which explicitly call `pcommon.ValidateNonPayable(value)` before proceeding: [2](#0-1) 

The integration test suite explicitly documents this as a known quirk: [3](#0-2) 

The root cause is architectural: in go-ethereum's EVM, a `CALL` with non-zero `value` performs the native balance transfer from caller to callee *before* the callee's code (or precompile `Run`) executes. This happens regardless of whether the target is a real contract or a precompiled contract. The `payablePrecompiles` allow-list in `x/evm/keeper/precompile.go` only suppresses ERC20-style Transfer *events* for a few precompiles that are known to intentionally move funds (bank, staking, gov, wasmd) — it does not create or gate any actual fund-custody/refund mechanism: [4](#0-3) 

Distribution (`0x1007`) is not in that list, and more importantly, `rewards()` has no `HandlePaymentUsei` call to route the value anywhere (unlike e.g. `staking.delegate()`, which explicitly calls `pcommon.HandlePaymentUsei` to convert and forward the sent value into a proper Cosmos-side operation): [5](#0-4) 

Since the precompile address is a synthetic address with no private key and no withdrawal method, any usei/wei that lands on its balance via `rewards()`'s missing guard has no code path that can move it back out — it is permanently locked, mirroring the reported `AgentPolice` bug where excess funds accumulate in a contract that has no mechanism to release them to their rightful owner.

### Impact Explanation
Any unprivileged EVM caller (contract or EOA) can call `rewards(address)` on `0x1007` with `value > 0`. That value is deducted from the caller's usei/wei balance and credited to the precompile address's balance in the StateDB/bank-keeper ledger, with no corresponding logic to refund it or forward it into any pool, module account, or user-controlled balance. This constitutes a permanent, protocol-level loss of the sender's funds — a direct "fund loss/freezing" impact reachable from a single submitted transaction, satisfying the required impact bar (concrete fund loss or permanent freezing).

### Likelihood Explanation
Trivial to trigger: it requires only a single ordinary EVM transaction (or Solidity `call{value: x}(...)` to the precompile) invoking `rewards(address)` with non-zero value — no special privileges, no complex preconditions, and no reliance on any other actor's behavior. The bug is also self-inflicted by an attacker who intentionally probes payable-looking precompile calls, or accidentally triggered by integrators who assume all precompile methods reject value like most others in the same file do.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` to the `RewardsMethod` (and any other view/query method dispatch) exactly as is already done for `ParamsMethod`, `ValidatorOutstandingRewardsMethod`, etc., so that a value-bearing call reverts before the native EVM value transfer can strand funds at the precompile address. As defense in depth, consider a chain-level invariant/guard that rejects or auto-refunds non-zero `value` sent to any precompile address that has no explicit fund-handling logic, rather than relying on each individual precompile method to remember to add the check.

### Proof of Concept
1. From any associated EVM account, call the distribution precompile at `0x0000000000000000000000000000000000001007`:
   ```solidity
   IDistribution(0x0000000000000000000000000000000000001007).rewards{value: 1 ether}(myAddress);
   ```
2. The call succeeds (per the documented test-suite quirk, `rewards()` has no "view rejects value" test because it would otherwise revert like every other view).
3. `msg.sender`'s usei/wei balance decreases by the sent value; the value is credited to the precompile address `0x1007`'s balance.
4. No subsequent Cosmos-side operation, refund path, or admin function exists to move that balance out — the funds are permanently inaccessible, confirmed by the codebase comment: "a value-bearing call would succeed and strand the funds." [3](#0-2) [6](#0-5)

	if addr == nil {
		return false
	}
