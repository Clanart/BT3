Confirmed: `Kip71BaseFeeDenominator` has an explicit `FormatChecker` rejecting `0` [1](#0-0) , but `Kip71GasTarget` uses `noopFormatChecker`, allowing governance to set it to `0` [2](#0-1) . This flows directly into a division in `NextMagmaBlockBaseFee` with no zero-check on `gasTarget`.

### Title
Governance-settable `kip71.gastarget = 0` causes a division-by-zero panic in Magma base-fee calculation, halting block production and validation - (File: `params/kip71_config.go`)

### Summary
The `KIP71Config.NextMagmaBlockBaseFee` function, which computes every block's EIP-1559-style dynamic base fee under the Magma hardfork, divides by the governance-controlled `GasTarget` parameter without checking whether it is zero. Unlike its sibling parameter `BaseFeeDenominator`, which has an explicit `FormatChecker` rejecting `0` [1](#0-0) , `Kip71GasTarget` is registered with `noopFormatChecker`, which accepts any value including `0` [2](#0-1) .

### Finding Description
`NextMagmaBlockBaseFee` reads `gasTarget := kc.GasTarget` directly from governance config with no fallback/guard (contrast with `BaseFeeDenominator`, which explicitly falls back to `64` if zero "to avoid panic") [3](#0-2) . When `parentGasUsed != gasTarget` (true for essentially any nonzero gas usage once `gasTarget == 0`), execution enters the branch that computes:
```
gasUsedDelta := parentGasUsed - gasTarget
x := parentBaseFee * gasUsedDelta
y := x.Div(x, gasTarget)   // gasTarget == 0
``` [4](#0-3) 
`math/big.Int.Div` panics with `division by zero` when the divisor is zero. The same divide-by-`gasTarget` pattern also exists in the "gas used below target" branch [5](#0-4) .

This function is on the critical consensus/block-assembly path:
- Block producers call it every block to set the header's `BaseFee` in `commitNewWork` [6](#0-5) .
- Header verification calls the same function via `VerifyMagmaHeader` in `blockchain/block_validator.go`, so every honest node validating any block after the malicious parameter takes effect will also hit the same panic.
- `chain_makers.go`'s `makeHeader` and the fee-history RPC oracle (`node/cn/gasprice/feehistory.go`) also invoke it.

Since `GasTarget` is a governance parameter set via the standard governance-parameter update path (`kaiax/gov`), any transaction/vote that successfully sets `kip71.gastarget` to `0` and gets activated will cause **every node** (both block proposers and validators) to panic identically the moment they need to compute the next Magma base fee — a hard chain halt rather than a mere temporary withdrawal lock as in the original finding.

### Impact Explanation
This is a network-wide denial of service: as soon as the parameter takes effect, block production stops entirely because `commitNewWork` panics before a block header can be built, and any node attempting header verification panics identically, producing deterministic crashes across the whole network rather than a divergence between honest nodes. This blocks all transaction processing and value transfers chain-wide until the parameter is reverted (which itself requires the chain to be live to process a governance transaction) — a far more severe outcome than the "at least 64 hours of withdrawal lock" described in the original report, since here the chain cannot make progress to even process the fix.

### Likelihood Explanation
This requires a governance parameter change to be voted through, so it depends on the same class of "governance sets a parameter to an extreme value" trust assumption as the original finding. Kaia's governance module explicitly acknowledges this exact risk pattern by adding a zero-check for the sibling parameter `BaseFeeDenominator` [7](#0-6) , but the same protection was not applied to `GasTarget`, indicating an inconsistent/incomplete mitigation rather than an intentional design choice — raising likelihood of this being an overlooked gap versus deliberate behavior.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (mirroring the one for `Kip71BaseFeeDenominator`) that rejects `0`, and/or add a defensive zero-check with a safe fallback directly inside `NextMagmaBlockBaseFee` before dividing by `gasTarget`, consistent with the existing `baseFeeDenominator == 0` fallback.

### Proof of Concept
1. Governance proposes and passes a parameter update setting `kip71.gastarget = 0` via the standard governance parameter-vote mechanism defined in `kaiax/gov`.
2. Once the parameter set takes effect at block N (post-Magma fork), the next block proposer calls `commitNewWork` → `pset.ToKip71Config().NextMagmaBlockBaseFee(...)` [6](#0-5) .
3. Inside `NextMagmaBlockBaseFee`, since any nonzero `parentGasUsed` (virtually guaranteed) is `> gasTarget (0)`, the code computes `x.Div(x, baseFeeDenominator)`-adjacent line `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget = 0` [8](#0-7) , causing a runtime panic (`division by zero`) in the block-producing node.
4. Any other node subsequently validating the same header (or attempting to produce the next block) calls the identical function and panics the same way, halting the chain.
