### Title
Deserialized Bitcoin outputs are trusted without proving the outpoint exists or belongs to the wallet - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` converts attacker-controlled bytes directly into an offset, `TxOut`, and `OutPoint`, but performs no check that the referenced transaction output exists or that the claimed amount was actually received. [1](#0-0) 

This is analogous to unchecked external input being interpreted as authoritative data: forged serialized output bytes can make downstream wallet code treat an arbitrary Bitcoin outpoint as spendable wallet funds. [2](#0-1) 

### Finding Description
`ReceivedOutput` consists of a scalar offset, a Bitcoin `TxOut`, and an `OutPoint`. [3](#0-2) 

Its deserializer accepts each field independently: it reads a canonical scalar, then consensus-decodes an arbitrary `TxOut` and `OutPoint`, and immediately returns the composed object. [1](#0-0) 

It does not check that the outpoint exists on-chain, that the decoded `TxOut` is the output at that outpoint, or that the supplied offset was produced by a `Scanner` for the wallet. [1](#0-0) 

`SignableTransaction::new` subsequently trusts `input.output.value`, `input.offset`, and `input.outpoint` to calculate funds, derive signing offsets, and construct transaction inputs. [4](#0-3) 

`SignableTransaction::multisig` verifies only that `prevouts[i].script_pubkey` equals the script for `keys.offset(offsets[i])`; it still does not authenticate the referenced outpoint or its claimed amount against the chain. [5](#0-4) 

A legitimately scanned output is authenticated indirectly because `Scanner::scan_transaction` produces it only after observing a transaction output whose `script_pubkey` is registered, and records that transaction’s actual `TxOut` and computed outpoint. [6](#0-5) 

The raw `ReceivedOutput::read` path bypasses that scanner provenance entirely. [1](#0-0) 

### Impact Explanation
An unprivileged party can submit serialized `ReceivedOutput` bytes claiming that an arbitrary outpoint pays an arbitrary amount to a known Serai wallet address by using offset `0` and the wallet’s known P2TR script. [1](#0-0) 

The forged object reports the attacker-selected amount through `ReceivedOutput::value`, and `SignableTransaction::new` includes that amount in the available input total. [7](#0-6) [8](#0-7) 

If an integrator uses this object to credit balances or initiates spending based on it, funds can be reported as received even though no corresponding spendable Bitcoin output exists. [1](#0-0) [4](#0-3) 

The forged input can also cause the threshold participants to produce signatures for a transaction that consensus will reject, because the wallet-specific check validates only the script-to-offset relationship rather than the existence and value of the claimed UTXO. [5](#0-4) [9](#0-8) 

### Likelihood Explanation
The attacker needs only the wallet’s public P2TR script and the ability to provide serialized `ReceivedOutput` bytes to an endpoint or component that accepts untrusted `ReceivedOutput::read` data. [10](#0-9) [1](#0-0) 

The base wallet output requires offset `0`, so the attacker does not need to discover an internal offset when claiming a fake deposit to the primary wallet address. [11](#0-10) 

The attack does not require control of a validator, a leaked key, malformed curve encodings, or an invalid blockchain object; both `Secp256k1::read_F` and Bitcoin consensus decoding accept the individually well-formed forged fields. [1](#0-0) 

Exploitation depends on an integrator treating deserialized `ReceivedOutput` values as authenticated scanner results rather than as untrusted claims requiring blockchain verification. [6](#0-5) 

### Recommendation
Do not expose `ReceivedOutput::read` as an authentication boundary for untrusted data. [1](#0-0) 

Require every deserialized `ReceivedOutput` to be revalidated against a confirmed transaction: fetch `outpoint`, compare its `TxOut` to the decoded `output`, and verify `output.script_pubkey` is currently registered in the wallet `Scanner` under the supplied offset. [6](#0-5) 

Prefer a verifier API on `Scanner`, such as `verify_received_output(key, output)`, that recomputes the expected script from the claimed offset and compares all output fields to the confirmed chain data. [12](#0-11) [13](#0-12) 

If `ReceivedOutput` serialization is intended only for trusted storage, document that explicitly and avoid accepting it from peers, RPC clients, or user-controlled messages without subsequent scanner-and-chain validation. [14](#0-13) 

### Proof of Concept
The following conceptual construction creates a validly encoded but fraudulent `ReceivedOutput` for the wallet’s base P2TR address. [10](#0-9) [15](#0-14) 

```rust
use bitcoin::{
  transaction::Version,
  Amount, OutPoint, TxOut, Transaction, TxIn,
  consensus::serialize,
};
use k256::Scalar;
use bitcoin_serai::wallet::{
  ReceivedOutput, Scanner, SignableTransaction,
};

fn forged_received_output(
  scanner_base_script: bitcoin::ScriptBuf,
) -> ReceivedOutput {
  let fake_tx = Transaction {
    version: Version(2),
    lock_time: bitcoin::absolute::LockTime::ZERO,
    input: vec![TxIn::default()],
    output: vec![TxOut {
      value: Amount::from_sat(1_000_000),
      script_pubkey: scanner_base_script,
    }],
  };

  let forged = ReceivedOutput {
    offset: Scalar::ZERO,
    output: fake_tx.output[0].clone(),
    // Attacker-selected; no output necessarily exists here.
    outpoint: OutPoint::new(fake_tx.compute_txid(), 0),
  };

  // Round-trip through the untrusted input path.
  ReceivedOutput::read(&mut forged.serialize().as_slice()).unwrap()
}
```

`fake_tx.compute_txid()` identifies a transaction that only exists locally as bytes, while the decoded `TxOut` claims a payment to the wallet script. [15](#0-14) 

Because `ReceivedOutput::read` does not query the chain or prove scanner provenance, `forged_received_output(...).value()` reports the attacker-chosen amount. [16](#0-15) 

Passing that object to `SignableTransaction::new` causes the fake amount to be counted as input value and the fake `OutPoint` to become a transaction input. [4](#0-3) 

Calling `multisig` with the wallet keys still accepts the forged output when its script is the wallet’s base-key P2TR script, because the implementation checks only that `p2tr_script_buf(keys.offset(offset).group_key())` equals the claimed `script_pubkey`. [5](#0-4)
