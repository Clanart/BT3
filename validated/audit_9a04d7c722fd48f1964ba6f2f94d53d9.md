## Title
Single failing module callback in a batched `handle_unsigned` call reverts and discards all other successfully processed ISMP messages in the same batch - (File: `modules/pallets/ismp/src/impls.rs`)

### Summary
`pallet-ismp`'s `execute()` function is called from the permissionless, unsigned extrinsic `handle_unsigned`, which is wrapped in `#[frame_support::transactional]`. `execute()` flattens the per-message `events: Vec<Result<Event, anyhow::Error>>` produced by each message's handler and collects them into a single `Result<Vec<Event>, Error>`. Because `Iterator::collect::<Result<_,_>>()` short-circuits on the first `Err`, a single failing application-level callback (`on_accept`/`on_response`/`on_timeout`) for *any one* message in the batch turns the entire `execute()` call into an `Err`, which — combined with `#[transactional]` — rolls back **all** storage effects of the whole extrinsic, including consensus updates, request/response receipts, and events for completely unrelated, successfully-processed messages in the same batch.

### Finding Description
Individual message handlers (`modules/ismp/core/src/handlers/request.rs`, `response.rs`, `timeout.rs`) are explicitly designed to tolerate per-item application failures without aborting the rest of the batch: when a module's `on_accept`/`on_response`/`on_timeout` returns `Err`, the receipt/commitment is deleted so the message can be retried, but the handler itself returns `Ok(res)` where `res` is the (possibly `Err`) per-item `DispatchResult`: [1](#0-0) 

This per-item tolerance is stated as an explicit design invariant in the protocol docs ("if `on_accept` does not return `Ok`, the receipt... will not be persisted, allowing the request to be replayed").

However, at the pallet layer, `Pallet::<T>::execute` flattens all these per-item results across the *entire batch* and collects them into one fallible result: [2](#0-1) 

`.flatten().collect::<Result<Vec<_>, _>>()` returns `Err` as soon as *any single* event in the flattened stream is `Err` — discarding all previously-successful events, and propagating `Error::<T>::InvalidMessage` up through `execute()`.

`execute()` is invoked from the unsigned, permissionless extrinsic `handle_unsigned`, which is explicitly marked `#[frame_support::transactional]`: [3](#0-2) 

Under `#[frame_support::transactional]`, when the dispatchable returns `Err`, **all** storage mutations performed during that call are rolled back — not just the ones related to the failing message. This means that if a batch `Vec<Message>` contains, say, one consensus update, several valid POST requests destined for different modules, and one POST request whose destination module's `on_accept` predictably rejects it (e.g. a business-logic check unrelated to proof validity), the single rejection nullifies the entire extrinsic: the consensus state update is discarded, and the receipts/events for the otherwise fully-valid requests are rolled back too, even though they individually satisfied every ISMP invariant (valid proof, not timed out, not duplicate).

Because `handle_unsigned` is permissionless (`ensure_none(origin)`), any unprivileged party can submit such a batch — no relayer, prover, or admin collusion is required. `execute()` is also invoked identically from `validate_unsigned` for mempool validation, so a poison message can also be used to make otherwise-valid batches fail transaction-pool validation entirely (`InvalidTransaction::BadProof`).

### Impact Explanation
This is a direct analog of the `KeeperOracle.commit` issue: a shared "batch settlement" primitive causes one item's application-level failure to brick delivery of unrelated, legitimate items bundled in the same atomic execution. Concretely:
- Legitimate consensus state updates and request/response deliveries bundled with a "poison" message are silently discarded (rolled back), even though they should have succeeded independently per the protocol's own per-item failure-tolerance design.
- This causes denial of message delivery / transaction manipulation: relayers submitting multi-message batches can have their entire batch's effects nullified by inclusion of one message whose destination module rejects it, even if that message's proof is entirely valid.
- Repeated/adversarial poisoning can be used to grief relayers and delay time-sensitive consensus/request processing, undermining the "requests, responses and timeouts must be delivered exactly once and settle deterministically" guarantee the protocol relies on.

### Likelihood Explanation
High feasibility: `handle_unsigned` is unsigned and permissionless, so any actor can submit a `Vec<Message>` batch. An attacker only needs to identify one destination module whose `on_accept`/`on_response`/`on_timeout` will predictably return `Err` for a validly-proven message (e.g., a module enforcing a business rule that a particular payload violates) and include it in — or front-run with a competing batch containing — the target batch. No control over consensus, no compromised relayer/prover, and no governance access is required.

### Recommendation
Do not let a single message's application-level (module callback) failure abort or roll back the storage effects of other, independently-valid messages in the same batch. Specifically:
- Change the `events` aggregation in `Pallet::<T>::execute` (`modules/pallets/ismp/src/impls.rs`) so that a per-item `Err` is recorded as an `Event::Errors` entry (as already done for handler-level errors) rather than being propagated via `collect::<Result<Vec<_>,_>>()?` and failing the whole call.
- Ensure `#[frame_support::transactional]` on `handle_unsigned` only causes full rollback for message-format/proof-verification failures (which legitimately must remain atomic to avoid partial invalid state), not for isolated application-level (`on_accept`/`on_response`/`on_timeout`) failures, which the lower-level handlers already treat as recoverable/replayable per message.

### Proof of Concept
1. Deploy/target a module `M` whose `on_accept` rejects requests carrying a specific payload/condition (a normal, legitimate business-logic rejection, not a protocol violation).
2. Craft `messages: Vec<Message>` containing:
   - A valid `ConsensusMessage` advancing the state machine height, and/or
   - Several valid `RequestMessage`/`ResponseMessage` entries destined for unrelated, healthy modules, and
   - One additional valid-proof `PostRequest` destined for module `M` that is guaranteed to fail `on_accept`.
3. Submit this batch via the permissionless `handle_unsigned` extrinsic (`modules/pallets/ismp/src/lib.rs:373`).
4. Observe: `Pallet::execute` (`modules/pallets/ismp/src/impls.rs:59-76`) returns `Err(Error::<T>::InvalidMessage)` because the flattened `collect::<Result<Vec<_>,_>>()` hits the `Err` from module `M`'s rejection.
5. Because `handle_unsigned` is `#[frame_support::transactional]`, the entire extrinsic's storage writes are reverted — including the consensus state update and the receipts for the unrelated, valid requests/responses that would otherwise have succeeded — even though none of those depended on module `M`'s outcome.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

	impl<T: Config> Pallet<T> {
		/// Execute the provided batch of ISMP messages, this will short-circuit and revert if any
		/// of the provided messages are invalid. This is an unsigned extrinsic that permits anyone
		/// execute ISMP messages for free, provided they have valid proofs and the messages have
		/// not been previously processed.
		///
		/// The dispatch origin for this call must be an unsigned one.
		///
		/// - `messages`: the messages to handle or process.
		///
		/// Emits different message events based on the Message received if successful.
		#[pallet::weight(weight())]
		#[pallet::call_index(0)]
		#[frame_support::transactional]
		pub fn handle_unsigned(
			origin: OriginFor<T>,
			messages: Vec<Message>,
		) -> DispatchResultWithPostInfo {
			ensure_none(origin)?;

			Self::execute(messages.clone())?;

			Ok(().into())
		}
