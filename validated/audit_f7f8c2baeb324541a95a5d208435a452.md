## Title
Unvalidated base/target branch names allow git-option injection in `git rebase` invocation - (File: app/src/lib/git/rebase.ts)

### Summary
`rebase()` builds the `git rebase` argv using raw branch names as bare positional arguments, with no `--` separator to stop option parsing. Branch names originating from a fetched remote are not run through the app's own ref-sanitization logic, so a remote branch (or local branch created by checking out a remote branch) whose name begins with `-` can be interpreted by git as a flag rather than a ref.

### Finding Description
The rebase invocation is: [1](#0-0) 
```
const result = await git(
  [...gitRebaseArguments(), 'rebase', baseBranch.name, targetBranch.name],
  repository.path,
  'rebase',
  options
)
```
`baseBranch.name` and `targetBranch.name` are inserted directly after the `rebase` subcommand with no `--` end-of-options marker. Contrast this with numerous other git wrappers in the same codebase that explicitly add `--` before ref/pathspec arguments precisely to prevent this class of bug: [2](#0-1) [3](#0-2) [4](#0-3) .

Branch objects are built from `git for-each-ref`, taking `%(refname:short)` verbatim as `Branch.name`: [5](#0-4) . This includes `refs/remotes/<remote>/<name>` entries created locally as a result of fetching from an attacker-controlled remote. No sanitization is applied to these fetched ref names before they become `Branch.name`.

Notably, the codebase already has a dedicated ref-sanitizer, `sanitizedRefName`, which explicitly strips a leading `-`/`+` in addition to filtering git's officially-illegal characters: [6](#0-5)  and its test explicitly documents this: `does not allow name to start with minus`: [7](#0-6) . The fact that git's own ref-name rules (the regex in the same file) do *not* forbid a leading hyphen — it's stripped by a second, separate step — confirms that a leading-`-` ref name is syntactically valid for git itself (e.g., achievable by a remote server via the wire protocol) and is a git-created hazard the app author was already aware of. Critically, `sanitizedRefName` is only invoked in user-typed branch-name flows (e.g., new branch creation), not on branch names parsed from `for-each-ref`/fetched remotes, so it does not protect `rebase()`'s `baseBranch.name`/`targetBranch.name`.

Given this, a malicious remote could advertise a branch such as `--onto=HEAD~1` (or e.g. `-c` style option smuggling) and, once fetched, that name becomes a selectable `Branch` in Desktop's rebase UI. If the user picks it (or if it is auto-selected, e.g., as the just-fetched upstream tracking branch) as the base or target, `git rebase <name> <name>` is executed with the malicious string as a bare argv token instead of `--`-guarded, letting git parse it as an option (e.g. `--onto=<rev>`), silently altering which commit range is rewritten.

### Impact Explanation
If exploitable, this causes silent corruption of the rebase result: commits could be rewritten onto an attacker-chosen base rather than the branch the user intended, without any error surfaced (git would just perform the rebase it was told to via the injected option). This matches the "silent corruption of what the user commits/pushes" impact class in scope.

### Likelihood Explanation
This requires: (1) the victim to add/fetch a remote controlled by (or compromised by) the attacker containing a specially-named branch, and (2) the victim to select that branch as the base or target branch in the Rebase dialog (or Desktop auto-populating it, e.g. as a tracking/default branch suggestion). I was not able to fully trace, within available tool iterations, the exact UI code path (`RebaseFlow`/branch-selection dialog and `menu-event.ts` `rebase-branch` handler) to confirm whether such a maliciously-named branch would be selectable/visible in the branch picker without being filtered or whether a human would realistically choose an obviously suspicious name like `--onto=HEAD~1`. This uncertainty affects the likelihood assessment; a background agent with full repo access should verify (a) whether `menu-event.ts`'s `rebase-branch` path pre-selects a branch automatically, and (b) whether the branch-list UI displays/allows selection of such names verbatim.

### Recommendation
Add a `--` separator before ref positional arguments in `rebase()` (and any other rebase-adjacent commands, e.g. the interactive rebase's `ref` argument) so git treats subsequent tokens strictly as revisions, not options:
```ts
const result = await git(
  [...gitRebaseArguments(), 'rebase', '--', baseBranch.name, targetBranch.name],
  ...
)
```
Note `git rebase <upstream> <branch> -- ` ordering needs verification against git's actual CLI grammar (rebase's `--` handling differs from plain revision commands), so this should be validated with a PoC before shipping. As defense in depth, also consider rejecting/flagging branch names beginning with `-` when populating the rebase branch-selection UI.

### Proof of Concept
Not independently executed (no filesystem/terminal access in this analysis). Suggested PoC for the background engineer:
1. Create a bare git repo, add branch `refs/heads/--onto=HEAD~1` server-side (bypassing local `git branch` ref-name option-parsing restrictions by writing the ref directly, e.g. `git update-ref refs/heads/--onto=HEAD~1 <sha>`).
2. In GitHub Desktop, add this repo as a remote and fetch.
3. Confirm the fetched branch appears as a `Branch` with `name` starting with `-`.
4. Trigger `rebase-branch` selecting this branch as the base, and capture the actual `git` argv executed by `rebase()` (e.g. via a spy/log on `git()` in `app/src/lib/git/rebase.ts` line 395) to confirm git receives `rebase --onto=HEAD~1 <target>` rather than treating the string as a ref.
5. Inspect the resulting commit graph to confirm it was rewritten onto `HEAD~1` rather than the intended base branch's tip.

**File:** app/src/lib/sanitize-ref-name.ts (L1-11)
```typescript
// See https://www.kernel.org/pub/software/scm/git/docs/git-check-ref-format.html
// ASCII Control chars and space, DEL, ~ ^ : ? * [ \
// | " < and > is technically a valid refname but not on Windows
// the magic sequence @{, consecutive dots, leading and trailing dot, ref ending in .lock
const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}
```
