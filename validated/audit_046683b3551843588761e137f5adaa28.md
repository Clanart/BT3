### Title
Zero group key accepted by `ThresholdKeys::new`/`read` enables universally forgeable Schnorr signatures - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
Analogous to the reported "total minted == 0 returns 0" bug, Serai's DKG layer never validates that the aggregate group key is non-identity when constructing or deserializing `ThresholdKeys`. `ThresholdKeys::new` computes `group_key` purely as the interpolated sum of caller/deserialization-supplied `verification_shares` over participants `1..=t`, with no check that the result (or any individual share) is non-identity. Untrusted bytes fed to `ThresholdKeys::read` — where `read_G` accepts canonical encodings of the identity point — therefore yield `ThresholdKeys` whose `group_key()` is the identity. A Schnorr signature `(R, s)` verifies under public key `A` iff `R + c·A − s·G == 0`; when `A` is the identity, any `s` with `R = s·G` verifies, so signatures for that group key are forgeable by anyone who knows nothing.

### Finding Description
`ThresholdKeys::new` sums `verification_shares[i] * interpolation_factor(i, 1..=t)` for `i in 1..=t` and stores the result as `group_key`, performing no identity or consistency check (`crypto/dkg/src/lib.rs:376-390`). `ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation variant, an arbitrary `secret_share` scalar, and `n` arbitrary group elements via `C::read_G`, then calls `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:574-632`). An attacker supplies `t=1, n=1, i=1`, `Interpolation::Lagrange`, `secret_share = 0`, and `verification_shares[1] = identity`. `interpolation_factor` for a singleton set returns `F::ONE` (`crypto/dkg/src/lib.rs:229-247`), so `group_key = identity * 1 = identity`. `SchnorrSignature::verify` checks `multiexp(R·1 + A·c + G·(−s)).is_identity()` (`crypto/schnorr/src/lib.rs:88-110`); with `A = identity` this reduces to `R == s·G`, satisfiable by anyone for arbitrary `s`. The FROST `sign`/`complete` path (`crypto/frost/src/sign.rs:312`, `crypto/frost/src/sign.rs:447-495`) will also produce signatures under this view, since `verify` is called against `view.group_key()` which is the identity.

### Impact Explanation
Any party able to feed crafted bytes to `ThresholdKeys::read` (listed as an untrusted-bytes sink) obtains a `ThresholdKeys` whose `group_key()` is the identity point. Signatures "for" that group key are trivially forgeable — pick any `s`, set `R = s·G`, and `sig.verify(identity, c)` returns true — so any funds, batches, or protocol decisions gated on a signature under that key can be forged by an unprivileged attacker possessing no secret material at all. This mirrors the report's "unlimited transfer when the total is zero": a zero-valued aggregate silently authorizes arbitrary operations instead of being rejected.

### Likelihood Explanation
Requires an integrator to deserialize `ThresholdKeys` from bytes an attacker controls or influences. The constructor and reader perform extensive structural validation (`ThresholdParams::new` rejects zero params, invalid participants, wrong share counts; interpolation validity is checked) yet omit the single most consequential semantic check — that the resulting group key is non-identity — making the acceptance path deterministic once reached. No check exists anywhere in `new`, `read`, `view`, or `sign` that `group_key` or the `verification_shares` are non-identity, so exploitation needs no race, no collusion, and no probabilistic event.

### Recommendation
In `ThresholdKeys::new` (and therefore transitively in `ThresholdKeys::read`), reject any `verification_shares` entry equal to `C::G::identity()` and reject a computed `group_key` equal to the identity. For belt-and-suspenders, `SchnorrSignature::verify`/`batch_statements` callers could assert `public_key` is non-identity, but the authoritative fix belongs in key construction. The same check should apply to `GeneratorPromotion::complete` (`crypto/dkg/promote/src/lib.rs:138-166`) and `musig` (`crypto/dkg/musig/src/lib.rs:143-160`), which also accept attacker-influenced verification shares.

### Proof of Concept
1. Craft bytes for `ThresholdKeys::<C>::read`: `C::ID` header, `t=1, n=1, i=1`, interpolation byte `1` (Lagrange), `secret_share = 0` encoded via `to_repr`, then one `verification_shares` entry encoding `C::G::identity()` in canonical `to_bytes` form.
2. `ThresholdKeys::read` succeeds: `ThresholdParams::new(1,1,i)` is valid, share count matches `n`, no identity check exists.
3. `keys.group_key()` returns `identity` (`crypto/dkg/src/lib.rs:445-447` reduces to `identity * ONE + G * ZERO`).
4. Forge a signature: choose any scalar `s`, set `R = C::generator() * s`. `SchnorrSignature { R, s }.verify(keys.group_key(), c)` evaluates `R + c·identity − s·G = R − s·G = identity` → returns `true` for every challenge `c`.
5. Alternatively, run FROST with the crafted keys: `view(vec![Participant(1)])` yields `secret_share = 0·1 = 0`; `sign_share` produces `s = r + c·0 = r`, and `complete` returns a signature under the identity group key — again universally forgeable by third parties.
