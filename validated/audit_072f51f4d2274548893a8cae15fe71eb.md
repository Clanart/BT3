## Title
Copilot conflict resolution silently rewrites non-conflicting file content via forged conflict-marker text, enabling prompt-injection-driven code tampering - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The PoolTogether bug's core pattern is that a function derives a security-relevant delta from raw, re-derivable state without validating that the state actually reflects only "new" activity, letting an attacker manipulate what's captured on each pass. The closest Desktop analog is not financial but structural: the Copilot "Resolve with Copilot" conflict-resolution feature derives what counts as a "conflict" purely from a naive regex scan of file bytes on disk (`<{7}`, `={7}`, `>{7}` marker lines), then blindly splices model output back into those exact byte ranges — with no verification that a detected marker block corresponds to a git-generated conflict. An attacker who contributes a branch/PR that gets merged, rebased, or cherry-picked can plant plain-text lines matching these regexes as committed content. GitHub Desktop will treat that attacker-authored text as a real conflict, send it (fully attacker-controlled) into the LLM prompt, and silently overwrite it — and can use it to inject instructions that steer the model's resolution of *other, real* conflicts in the same session.

### Finding Description
`extractConflictHunks` in `app/src/lib/copilot-conflict-context.ts` identifies conflict hunk boundaries purely via regex line matching: [1](#0-0) 
It has no way to distinguish a genuine git-inserted conflict marker from attacker-authored plain text that merely matches the pattern (e.g., a code comment, documentation, or ASCII art demonstrating conflict-marker syntax, deliberately checked into the attacker's branch). If both branches happen to have an unrelated real conflict anywhere in the same file, `buildConflictContext` will read the whole file and hand every matching "hunk" — real or forged — to the model: [2](#0-1) 

The forged hunk's `oursContent`/`theirsContent`/`contextBefore`/`contextAfter` — fully attacker-controlled — are embedded verbatim into the LLM prompt via `formatConflictContextForPrompt`/`makeFencedBlock`: [3](#0-2) 

The model is instructed to "resolve" every detected hunk and return `resolvedContent` per hunk, matched **by order, not by line number**: [4](#0-3) 

`reassembleResolvedFile` then walks the file again with the same naive marker regex and splices the model's `resolvedContent` into whatever byte range matched — including the forged block: [5](#0-4) 

Finally, `_applyCopilotConflictResolutions` in `app-store.ts` writes the reassembled content straight to disk and stages it, with only a path-traversal check and a check for whether the file *still has unresolved conflict markers* — nothing that verifies the touched region was an actual git conflict: [6](#0-5) 

The corrupted value: **the on-disk content of a region that git never marked as conflicted**, which is silently rewritten and staged as if it were a legitimate three-way merge resolution.

### Impact Explanation
This satisfies "silent corruption of what the user commits or pushes" driven purely by attacker-controlled repository content (a hostile branch/PR merged, rebased onto, or cherry-picked by the victim) — no local access, malware, or leaked credentials required. Two escalating impacts:
1. **Direct corruption**: benign, non-conflicting code/comments/docs that merely resemble marker syntax get silently replaced by fabricated LLM output and committed, with the user seeing only a markdown "summary" card, not a real diff of the change.
2. **Prompt injection amplification**: because the forged hunk's content is attacker-controlled and inserted into the same LLM context/session used to resolve real conflicts (files are batched together per `SinglePromptFileLimit`/`MaxConcurrentChunks`), the attacker can embed instructions in the forged block to influence how the model resolves the genuinely conflicting file(s) in that same run, potentially causing the victim to commit attacker-favored (e.g., backdoored) resolutions for real conflicts without review.

### Likelihood Explanation
Requires: (a) the victim uses the "Resolve with Copilot" feature, (b) the attacker's branch is merged/rebased/cherry-picked and produces at least one genuine, unrelated conflict somewhere in the repo (common in normal collaboration), and (c) the attacker plants marker-like text in a file included in that operation. None of this needs special privileges beyond being a normal contributor whose branch gets merged — a routine, expected workflow. The existing guards (`resolveWithin` path-traversal check, `hasUnresolvedConflicts` check for externally-resolved files, size/line-length caps) do not address marker authenticity at all, so the path is unmitigated.

### Recommendation
- Only treat a marker block as a real conflict if it lies within a region git's index actually reports as `AppFileStatusKind.Conflicted`/`UU` for that file (cross-check hunk byte offsets against `git diff --check` / actual conflict entries from `getStatus`), not merely regex-matched text.
- Alternatively/additionally, derive hunk boundaries from `git merge-file`/`git diff3` markers freshly regenerated by Desktop rather than trusting arbitrary on-disk text.
- Sanitize/escape or clearly delimit untrusted branch content before including it in the LLM prompt, and treat any embedded meta-instructions in hunk content as inert data, not instructions (standard prompt-injection mitigation).
- Show the user an actual before/after diff (not just a model-written markdown summary) for every file touched by `_applyCopilotConflictResolutions` before staging, so unexpected changes to non-conflicting regions are visible.

### Proof of Concept
1. Attacker creates `feature` branch that: (a) modifies `README.md` line 1 (to guarantee a real, unrelated conflict with `main`), and (b) adds, elsewhere in some other tracked file (or the same file, further down), literal lines:
   ```
   <<<<<<< legacy-format-example
   old documented syntax
   =======
   new documented syntax
   >>>>>>> legacy-format-example
   ```
   as ordinary committed "documentation about conflict markers" — not an actual git conflict.
2. Victim merges/rebases `feature` into `main` in GitHub Desktop; a real conflict occurs in `README.md`.
3. Victim clicks "Resolve with Copilot." `buildConflictContext`/`extractConflictHunks` scans all conflicted-status files, but also finds the forged marker block in the other file only if that file is also flagged by git as conflicted — however, since `extractConflictHunks` runs unconditionally on any file passed to `buildConflictContext` (driven by the caller's conflicted-file list from `getStatus`), the forged block is exploitable when it sits inside the *same* file that legitimately conflicts (e.g., attacker embeds the forged block adjacent to the real conflicting section in `README.md`).
4. Copilot returns per-hunk `resolvedContent` for both the real and forged hunks.
5. `reassembleResolvedFile` splices both into `README.md`; `_applyCopilotConflictResolutions` writes and stages the file.
6. The victim clicks "Continue Merge," committing a `README.md` in which the "documentation about conflict markers" section was silently rewritten by the model — content the victim never intended to change and never saw as a diff, satisfying "silent corruption of what the user commits."

Note: full confirmation that `buildConflictContext` is invoked per-file only for files git reports as truly conflicted (versus scanning all changed files) would require tracing the caller in `app-store.ts`'s `_startCopilotConflictResolution`/`_resolveConflictsWithCopilot`, which was not fully retrieved in this session; if it is scoped strictly to git's conflicted-file list, the forged block must reside within a file that also has a genuine conflict elsewhere, as described above.

 * the original file content (which still has conflict markers on disk).
 *
 * Walks the original file line-by-line. Non-conflicted lines are copied
 * through verbatim. Each conflict marker block (`<<<<<<<` through
 * `>>>>>>>`, with a `=======` separator in between) is replaced with the
 * corresponding entry from `hunkResolutions` (matched by order, not by
 * line number). This guarantees that all non-conflicted code is preserved
 * exactly, and the model's output is only responsible for the small
 * resolved sections.
 *
 * A `<<<<<<<` line that is not followed by both a `=======` separator and
 * a closing `>>>>>>>` before EOF is treated as regular file content (not a
 * conflict block) and copied through unchanged to avoid data loss from
 * malformed or stray markers.
 *
 * @param rawContent - The full file content on disk, including conflict markers
 * @param hunkResolutions - Per-hunk resolved content, in the order they appear in the file
 * @returns The reassembled file with all conflicts resolved
