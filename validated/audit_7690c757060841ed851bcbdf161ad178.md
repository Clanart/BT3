## Analysis

The ZetaChain report's broken invariant is: **an untrusted, attacker-influenced value is treated as a trusted "identity" field and is later used to silently determine who receives value/attribution, without independent verification.** The zEVM `evmhooks` code trusts `tx.origin`/`emittingContract` as the cctx `Sender` and later uses that unverified value as the refund recipient.

The closest verifiable analog I could find in this GitHub Desktop codebase is in the **co-author restoration logic** used when amending a commit. It extracts `Co-Authored-By` identity data straight out of an untrusted commit body (which can come from a cloned/fetched repository) and unconditionally marks that identity as `kind: 'known'`, bypassing the "unknown co-author" confirmation dialog that exists specifically to prevent unverified identities from being silently baked into a commit.

### Title
Unverified `Co-Authored-By` trailers extracted from untrusted commits are marked "known" and silently re-committed on Amend, bypassing the unknown-co-author warning - (File: `app/src/lib/stores/git-store.ts`)

### Summary
When a user selects "Amend commit" on any commit — including one obtained from a cloned or fetched repository controlled by an attacker — Desktop calls `restoreCoAuthorsFromCommit` → `loadCommitAndCoAuthors`, which parses `Co-Authored-By` trailers out of that commit's message using `git interpret-trailers` and `GitAuthor.parse`. Each successfully-parsed trailer is converted into an `Author` object with `kind: 'known'` unconditionally, regardless of whether that name/email corresponds to any actual verified GitHub account.

### Finding Description
`loadCommitAndCoAuthors` extracts co-author trailers from the (attacker-influenced) commit body: [1](#0-0) 

It then reconstructs `Author` objects from the raw trailer values and always tags them as `kind: 'known'`: [2](#0-1) 

This is fundamentally different from the normal co-author flow, where co-authors are selected from GitHub API-verified collaborators via the UI, and any author not matching a verified account is classified as `UnknownAuthor` so the commit UI can warn the user: [3](#0-2) 

Because `restoreCoAuthorsFromCommit`/`loadCommitAndCoAuthors` hard-codes `kind: 'known'` for anything extracted from a commit's trailers — with no check against the actual GitHub collaborators list or any account verification — the `unknownAuthors` filter in `createCommit` never fires for these restored authors, so the "confirm commit with unknown co-authors" dialog is skipped entirely for them, even though their provenance (an arbitrary commit body) is exactly as unverified as a manually-typed unknown author would be.

The resulting `Author[]` is fed straight into `getCoAuthorTrailers`, which is what actually gets written into the new commit's trailers on Amend: [4](#0-3) 

### Impact Explanation
An attacker who controls a repository (or a branch/commit within it) that the victim clones or fetches can craft a commit whose message contains a `Co-Authored-By: <arbitrary name> <arbitrary email>` trailer. If the victim later amends that commit in Desktop (a completely ordinary workflow action, not requiring any unnatural steps), Desktop will silently re-attach that attacker-chosen name/email as a "known" co-author on the amended commit — bypassing the warning dialog designed to stop exactly this class of silent, unverified attribution. This is a silent corruption of what the user commits: the pushed commit history now falsely attributes co-authorship to an identity the user never typed, reviewed as "unverified", or consciously approved, and which could be used for reputation abuse, misattribution in blame/history, or social-engineering downstream reviewers who trust the `Co-Authored-By` trailer as ground truth.

### Likelihood Explanation
Amending commits from a freshly-cloned or fetched repository is a normal, expected Desktop workflow (e.g., fixing up the last commit of a branch pulled from a fork or collaborator). No privileged access, local exploit, or unnatural user action is required beyond the attacker getting one commit with a crafted trailer into a repo the victim will amend — which matches the in-scope threat model of "attacker controls a cloned/fetched repository."

### Recommendation
When restoring co-authors from an existing commit's trailers, classify the resulting `Author` as `UnknownAuthor` unless the name/email can be matched against a verified account (e.g., the repository's GitHub collaborators/contributors list), so the existing "confirm commit with unknown co-authors" dialog is triggered instead of unconditionally trusting the extracted identity as `kind: 'known'`.

### Proof of Concept
1. Attacker pushes a commit to a repository with message:
   ```
   Fix bug

   Co-Authored-By: Trusted Maintainer <maintainer@company.com>
   ```
2. Victim clones/fetches this repository in GitHub Desktop.
3. Victim selects that commit and chooses "Amend commit" to tweak the message or add a file.
4. `restoreCoAuthorsFromCommit` → `loadCommitAndCoAuthors` (`app/src/lib/stores/git-store.ts:786-799,887-912`) extracts the trailer and creates `{ kind: 'known', name: 'Trusted Maintainer', email: 'maintainer@company.com', username: null }`.
5. Because it is `kind: 'known'`, the `unknownAuthors` check in `createCommit` (`app/src/ui/changes/commit-message.tsx:601-615`) does not flag it, and no warning dialog appears.
6. The victim commits/pushes, and the new commit is now co-attributed to `maintainer@company.com` without any verification that this is legitimate or that the victim consciously approved it.

  private getCoAuthorTrailers() {
    const { coAuthors } = this.props
    const token = 'Co-Authored-By'
    return this.isCoAuthorInputEnabled
      ? coAuthors
          .filter(isKnownAuthor)
          .map(a => ({ token, value: `${a.name} <${a.email}>` }))

  }
