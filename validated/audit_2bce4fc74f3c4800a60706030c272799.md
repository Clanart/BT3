Based on the investigation, the strongest local analog to the "missing verification before privileged action" pattern in the report is a validation gap in the deep-link `openRepo` branch-checkout flow, not the `filepath` traversal case (which is already guarded by `isAbsolute()` + `resolveWithin()` in `dispatcher.ts`), nor the OAuth callback (which already validates `state` against the CSRF token in `sign-in-store.ts`).

### Title
Deep-link `branch` parameter is validated for illegal ref characters but not for a leading `-`/`+`, allowing git argument injection via a clicked `x-github-client`/`github-mac` URL - (File: `app/src/lib/parse-app-url.ts`)

### Summary
GitHub Desktop registers custom protocol handlers (`x-github-client`, `github-mac`, `github-windows`) that are dispatched to `parseAppURL()` and, for `openrepo` actions, ultimately drive a `git checkout` of an attacker-supplied branch name against a cloned/opened repository. [1](#0-0)  The branch value from the URL is checked only with `testForInvalidChars()`, which rejects control/special characters but does **not** reject a leading `-`/`+`, unlike the sibling function `sanitizedRefName()` in the same file, which explicitly strips leading `-`/`+` before use. [2](#0-1) [3](#0-2) 

### Finding Description
The broken invariant: any branch string reaching `checkoutLocalBranch()` should be guaranteed to be a safe git ref (not a git command-line flag), the same way `sanitizedRefName()` guarantees it elsewhere in the app. The `openrepo` deep-link path uses only `testForInvalidChars(branch)` as its gate: [4](#0-3)  This regex targets control characters, `~^:?*[\|""<>`, `@{`, consecutive dots, leading/trailing dot, `.lock` suffix, and trailing `/` — but a value like `--upload-pack=...` or `-c` passes cleanly since `-` is not in the excluded set. [5](#0-4)  The accepted `branch` value flows unmodified into `{ name: 'open-repository-from-url', ..., branch, ... }` [6](#0-5) , which `dispatchURLAction` routes to `openRepositoryFromUrl` → `openBranchNameFromUrl(url, branch)` → `checkoutLocalBranch(repository, branchName)` after cloning/fetching the (also attacker-controlled) remote. [7](#0-6)  Test fixtures confirm the URL handler accepts arbitrary branch strings so long as they don't hit the character blocklist, and only rejects things like `<>`. [8](#0-7) 

### Impact Explanation
If the resulting `branch` string is passed as a positional/flag argument into a `git` invocation (e.g., `git checkout <branch>`, `git fetch`, etc.) without an explicit `--` separator to stop option parsing, an attacker-controlled deep link (`github-mac://openRepo/<attacker-url>?branch=-<flag>...`) could inject git command-line options instead of a ref name. This class of bug (git argument/flag injection via ref-like input) is a known vector for arbitrary file write/read or code execution depending on which flag is accepted by the specific git subcommand invoked downstream (e.g., options controlling output paths, hooks, or exec helpers). This satisfies the "attacker controls a link/deep link the user clicks" and "git remote response" categories in the valid-impact list, and the ultimate effect (unexpected git behavior via injected flags) maps to "silent corruption of what the user commits/checks out" or worse.

### Likelihood Explanation
Likelihood requires: (1) the user clicks an attacker-supplied `x-github-client://openRepo/...`, `github-mac://openRepo/...`, or `github-windows://openRepo/...` link (plausible via phishing/README links, matching the "link the user clicks" trigger), and (2) the downstream git invocation for `checkoutLocalBranch` passes the branch string as a raw argv element without an `end-of-options --` guard. I was able to confirm the missing character-based guard at the parsing layer and the call chain into `checkoutLocalBranch`, but I was not able to fully inspect the exact git-invocation code inside `checkoutLocalBranch` (in `app/src/ui/dispatcher/dispatcher.ts`, only its declaration/call sites were located via grep, not its body) or the low-level `git(['checkout', branchName], ...)` call to confirm whether a `--` separator is already used there. This is a real gap in my verification — if the low-level git wrapper already inserts `--` before ref arguments, the injection primitive would be neutralized despite the missing regex check.

### Recommendation
Apply the same leading `-`/`+` stripping used in `sanitizedRefName()` to the `branch` (and `pr`) values before they leave `parseAppURL()`, or reject values that fail `sanitizedRefName(branch) !== branch`, rather than solely relying on `testForInvalidChars()`. Additionally, ensure every git invocation that accepts a ref name derived from external input inserts an explicit `--` separator before the ref argument.

### Proof of Concept
1. Attacker crafts a link: `x-github-client://openRepo/https://github.com/attacker/repo?branch=--upload-pack%3D%2Ftmp%2Fevil.sh`
2. Victim clicks the link; `handleAppURL` → `parseAppURL` accepts it because `--upload-pack=/tmp/evil.sh` contains no characters excluded by `invalidCharacterRegex`. [9](#0-8) 
3. Desktop clones/opens `attacker/repo` and calls `openBranchNameFromUrl(url, branch)` → `checkoutLocalBranch(repository, branchName)` with the unsanitized flag-like string. [10](#0-9) 
4. Whether this results in actual flag injection depends on code inside `checkoutLocalBranch`/the underlying `git()` wrapper, which I could not fully verify in this session — this should be confirmed directly against `app/src/lib/git/checkout.ts` (or equivalent) before treating this as a confirmed exploit rather than a validation-gap finding.

**Confidence caveat:** Unlike a confirmed end-to-end exploit, this report identifies a concrete, verifiable validation gap (missing leading-dash rejection in the deep-link branch parser) with a plausible attacker-triggered path, but the final sink (whether the git wrapper is immune due to an `--` separator) was not confirmed due to tool-call exhaustion. If the underlying git call already guards with `--`, this finding reduces to a defense-in-depth/hardening gap rather than an exploitable vulnerability.

const invalidCharacterRegex =
  /[\x00-\x20\x7F~^:?*\[\\|""<>]+|@{|\.\.+|^\.|\.$|\.lock$|\/$/g

/** Sanitize a proposed reference name by replacing illegal characters. */
export function sanitizedRefName(name: string): string {
  return name.replace(invalidCharacterRegex, '-').replace(/^[-\+]*/g, '')
}

/** Validate that a reference does not contain any invalid characters */
export function testForInvalidChars(name: string): boolean {
  return invalidCharacterRegex.test(name)
}

  private async openRepositoryFromUrl(action: IOpenRepositoryFromURLAction) {
    const { url, pr, branch, filepath } = action

    let repository: Repository | null

    if (pr !== null) {
      repository = await this.openPullRequestFromUrl(url, pr)
    } else if (branch !== null) {
      repository = await this.openBranchNameFromUrl(url, branch)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      return
    }

    if (filepath !== null) {
      if (isAbsolute(filepath)) {
        log.error(`Refusing to open absolute path: ${filepath}`)
        return
      }

      const resolved = await resolveWithin(repository.path, filepath)

      if (resolved !== null) {
        shell.showItemInFolder(resolved)
      } else {
        log.error(
          `Prevented attempt to open path outside of the repository root: ${filepath}`
        )
      }
    }
  }

  private async openBranchNameFromUrl(
    url: string,
    branchName: string
  ): Promise<Repository | null> {
    const repository = await this.openOrCloneRepository(url)

    if (repository === null) {
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    // if the repo has a remote, fetch before switching branches to ensure
    // the checkout will be successful. This operation could be a no-op.
    await this.appStore._fetch(repository, FetchType.UserInitiatedTask)

    await this.checkoutLocalBranch(repository, branchName)

    return repository
  }
