### Title
Silent exception swallowing in `Offer.__post_init__` corrupts additions cache and crashes offer processing on malformed spend data - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.__post_init__` builds a per-coin additions/hints cache (`self._additions`, `self._hints`) by calling `compute_spend_hints_and_additions()` on every coin spend in an untrusted, externally-supplied `Offer` (received as a bech32 blob from any offer counterparty via `Offer.from_bech32()` / `take_offer` / `check_offer_validity`). Any exception raised while parsing a spend's conditions other than the specific `ValueError("cost exceeded or below zero")` message is silently swallowed with a bare `except Exception: continue`, leaving that coin's entry entirely absent from `self._additions`.

### Finding Description
In `chia/wallet/trading/offer.py`, `__post_init__()` iterates `self._bundle.coin_spends` and does: [1](#0-0) 
```
for cs in self._bundle.coin_spends:
    assert cs.coin not in adds
    try:
        hinted_coins, cost = compute_spend_hints_and_additions(cs, max_cost=max_cost)
        max_cost -= cost
        adds[cs.coin] = [hc.coin for hc in hinted_coins.values()]
        hints = {**hints, **{id: hc.hint for id, hc in hinted_coins.items() if hc.hint is not None}}
    except ValidationError:
        raise
    except ValueError as e:
        if e.args and e.args[0] == "cost exceeded or below zero":
            raise ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, "compute_additions for CoinSpend") from e
        continue
    except Exception:
        continue
```
`compute_spend_hints_and_additions()` in `chia/wallet/util/compute_hints.py` runs the puzzle reveal via `run_with_cost()`, then for each `CREATE_COIN` condition does `bytes32(rf)` on the puzzle-hash argument and `condition.at("rrf").as_int()` on the amount argument without prior shape validation. A puzzle that emits a malformed `CREATE_COIN` (e.g., wrong-length puzzle-hash atom, or unexpected list shape) causes an unhandled `ValueError`/`EvalError` that is not the "cost exceeded" message, and is caught by the bare `except Exception: continue` — the coin's key is *never inserted* into `adds`.

Any later code path that indexes `self._additions[coin]` unconditionally will then raise `KeyError`, e.g. `_get_offered_coins()`: [2](#0-1) 
```
for parent_spend in self._bundle.coin_spends:
    coins_for_this_spend: list[Coin] = []
    parent_puzzle: UnknownPuzzle = UnknownPuzzle(known_program=parent_spend.puzzle_reveal)
    parent_solution = Program.from_serialized(parent_spend.solution)
    additions: list[Coin] = self._additions[parent_spend.coin]
```
`_get_offered_coins()` is reached from `get_offered_coins()` → `get_offered_amounts()` → `summary()`/`arbitrage()`, which are invoked by wallet RPC endpoints that process attacker-supplied offer blobs before any signature/spend validation occurs, such as `check_offer_validity` and `take_offer`: [3](#0-2) 

### Impact Explanation
Any wallet user or local RPC caller who opens/examines/accepts an attacker-crafted offer file triggers this code path before the offer is otherwise validated as safe. An unhandled `KeyError` deep inside offer-summary/`arbitrage`/`get_offered_coins` logic crashes the RPC call handling that request. Because these methods are also used internally during `respond_to_offer`/`calculate_tx_records_for_offer` while constructing/validating a real transaction, a crafted offer can halt normal transaction-processing flow for any wallet that merely inspects it — a spend-triggered processing halt reachable purely from untrusted, attacker-controlled offer content, matching the "processing malicious uploaded content" bug class in the reference CVE.

### Likelihood Explanation
High reachability: any counterparty can hand a wallet user an offer file; opening it (even to view the summary, without accepting) is enough to trigger `Offer.__post_init__` and, depending on downstream call, the `KeyError`. Constructing a CLVM puzzle that emits a `CREATE_COIN` condition with a malformed puzzle-hash atom (or other condition shape triggering an exception other than the specific cost message) is straightforward with standard puzzle authoring tools, requiring no special privileges.

### Recommendation
- Do not use a bare `except Exception: continue` in `Offer.__post_init__`; instead ensure `adds[cs.coin]` is always populated (e.g., with an empty list or an explicit sentinel) whenever an exception occurs so downstream `self._additions[coin]` lookups cannot `KeyError`.
- Alternatively, make all consumers (`_get_offered_coins`, etc.) use `.get(coin, [])` instead of direct indexing.
- Consider re-raising a `ValidationError` for any parsing failure other than the intentionally special-cased cost-exceeded case, so malformed offers are rejected explicitly rather than silently accepted with partial/incorrect internal state.

### Proof of Concept
Not independently executed; based on static code review of `chia/wallet/trading/offer.py` (`__post_init__`, `_get_offered_coins`) and `chia/wallet/util/compute_hints.py` (`compute_spend_hints_and_additions`). Conceptually:
1. Build a `CoinSpend` whose puzzle reveal, when run, outputs a `CREATE_COIN` condition with a puzzle-hash atom that is not exactly 32 bytes (e.g., `(51 0xdead 100)`), plus a legitimate `OFFER_MOD`-hash `CREATE_COIN` for the actual offered payment.
2. Wrap this spend plus a standard settlement spend into a `WalletSpendBundle` and construct an `Offer(...)` from it (as `Offer.from_bech32` would when parsing an externally received offer file).
3. Call `offer.summary()` or `offer.get_offered_coins()` (as `check_offer_validity`/`take_offer` RPCs do) — `_get_offered_coins()` indexes `self._additions[parent_spend.coin]` for the malformed spend's coin, which was never inserted, raising an unhandled `KeyError` and aborting the RPC call.

This proof-of-concept sketch was not run against a live node; verification of the exact exception type raised for a malformed `CREATE_COIN` atom and confirmation that it is not classified as `ValidationError`/the specific cost message would require executing it in a test harness such as `chia/_tests/wallet/test_util.py`'s existing `Offer` cost tests.
