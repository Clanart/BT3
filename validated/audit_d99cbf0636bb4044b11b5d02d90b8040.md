### Title
Duplicate `ReceivedOutput`s are counted multiple times, producing an invalid signed Bitcoin transaction - (File: `networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` does not reject duplicate `ReceivedOutput`s, so the same UTXO can be included multiple times and its value counted repeatedly when determining whether payments are fundable. [1](#0-0) 

### Finding Description
`ReceivedOutput::read` deserializes caller-controlled `offset`, `output`, and `outpoint` fields without checking that the resulting UTXO is unique or otherwise reserved. [2](#0-1) 

`SignableTransaction::new` sums every supplied `input.output.value` into `input_sat` and emits every supplied `input.outpoint` as a distinct `TxIn`. [1](#0-0) 

The solvency check then compares that inflated `input_sat` against `payment_sat + needed_fee`, without first ensuring that all `previous_output` values are unique. [3](#0-2) 

If change is requested, the same inflated `input_sat` is also used to calculate and add the change output. [4](#0-3) 

`multisig` validates that each offset produces the corresponding previous output's script, but this check applies independently per array position and does not prevent the same valid script/outpoint pair from appearing twice. [5](#0-4) 

Signing uses `Prevouts::All` and generates one Schnorr signature per input position, so duplicate inputs receive valid signatures even though both reference the same UTXO. [6](#0-5) 

`complete` then writes a signature witness for each transaction input and returns the transaction as successfully completed. [7](#0-6) 

This is analogous to accounting for already-allocated balances as newly available value: one spendable output is represented twice, and the duplicated representation is counted as additional funds. [1](#0-0) 

### Impact Explanation
An input list containing `[utxo, utxo]` reports twice the actual available value and can pass `NotEnoughFunds` for a payment exceeding the real UTXO's value. [1](#0-0) [3](#0-2) 

The resulting transaction contains two inputs spending the same `OutPoint`, making it invalid because a UTXO cannot be consumed twice in one transaction. [8](#0-7) 

The threshold signing flow can nevertheless complete and return this transaction, causing signers to commit signatures to a withdrawal or consolidation that can never be confirmed. [9](#0-8) [10](#0-9) 

The practical result is an unspendable signed transaction and a payment plan that appears funded even though the required inputs do not exist. [11](#0-10) 

### Likelihood Explanation
The vulnerable input format is reachable through `ReceivedOutput::read`, which accepts serialized untrusted output records, or through direct calls to the public `SignableTransaction::new` API. [2](#0-1) [12](#0-11) 

The processor forwards each scheduled input's `output` into `BSignableTransaction::new`, so any duplicate output accepted into the scheduler's input set reaches this path. [13](#0-12) 

Exploitation requires control over or corruption of the input list supplied for signing; correctly scanned Bitcoin outputs normally have unique transaction IDs and vout indexes, which limits the likelihood when inputs originate exclusively from the deduplicated scanner path. [14](#0-13) [15](#0-14) 

### Recommendation
Reject duplicate `ReceivedOutput::outpoint()` values at the beginning of `SignableTransaction::new` before calculating `input_sat`, building `tx_ins`, or constructing `prevouts`. [12](#0-11) [1](#0-0) 

A `HashSet<OutPoint>` should be populated while iterating over `inputs`, returning a new `TransactionError::DuplicateInput` when insertion fails. [16](#0-15) 

The same uniqueness invariant should be enforced or asserted before scheduler plans are converted into signable transactions. [17](#0-16) [13](#0-12) 

### Proof of Concept
The following unit-test-shaped PoC assumes `output` is a valid scanned `ReceivedOutput` and `payment` exceeds its actual value while remaining below twice its value:

```rust
// networks/bitcoin/src/wallet/send.rs test context
let output: ReceivedOutput = scanner.scan_transaction(&funding_tx).remove(0);
let actual_value = output.value();

let duplicate_inputs = vec![output.clone(), output];
let payments = vec![(payment_script, actual_value + 1)];

let signable = SignableTransaction::new(
  duplicate_inputs,
  &payments,
  Some(change_script),
  None,
  fee_per_vbyte,
).unwrap();

assert_eq!(signable.transaction().input.len(), 2);
assert_eq!(
  signable.transaction().input[0].previous_output,
  signable.transaction().input[1].previous_output
);
```

Without the duplicate check, the constructor counts `actual_value` twice, accepts the otherwise unaffordable payment, and emits two inputs spending the same outpoint. [1](#0-0) [3](#0-2) 

The signing flow will then produce signatures for both duplicate input positions and return a completed transaction that Bitcoin consensus rejects. [6](#0-5) [10](#0-9)
