### Title
Stale line-selection indices applied against a freshly re-fetched diff silently corrupt partial commits - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
Just like the Morpho `_undeploy` bug, where `assetsMax` was computed from a stale snapshot (`totalSupplyAssets`/`totalSupplyShares`) while `amount` was derived from a fresher, interest-accrued value, Desktop's partial-commit path combines two diff "snapshots" that are not guaranteed to be the same: the `DiffSelection` the user built while looking at one diff, and a **second, independently re-fetched diff** used at staging time to actually build the patch. The two are merged purely by absolute line index, with no re-validation that the index still points at the same content.

### Finding Description
When a user checks/unchecks specific lines in the Changes view, the selection (a `DiffSelection`, keyed by absolute line indices into hunks) is attached to the `WorkingDirectoryFileChange` and stored against the diff that was rendered in the UI at that time [1](#0-0) .

When the commit is actually created, `stageFiles` calls `applyPatchToIndex` for every file with a partial selection [2](#0-1) . Critically, `applyPatchToIndex` does **not** reuse the diff the selection was made against — it calls `getWorkingDirectoryDiff` again, right before building the patch: [3](#0-2) 

The freshly fetched `diff` is then passed into `formatPatch(file, diff)`, which walks the **new** diff's hunks and, for every non-context line, asks the **old** selection object whether the line at `hunk.unifiedDiffStart + lineIndex` was selected: [4](#0-3) 

`DiffSelection.isSelected` has no notion of *what* content a given absolute index represents — it is a pure index-to-boolean map. If the working-directory content changes between the moment the user made their selection (against diff #1) and the moment `applyPatchToIndex` re-diffs the file (diff #2) — e.g. because of a `.gitattributes` clean/smudge filter shipped in the cloned repository, a build tool, formatter, or any other process that touches the file — the hunk boundaries and absolute line indices shift. The stale selection indices are then blindly reapplied to the new hunk structure, so the wrong lines are folded into "selected" or "unselected" buckets. `formatPatch` also explicitly documents that a malformed diff/selection pairing is only caught if it happens to produce an *empty* patch (line 224-227) — any non-empty but semantically wrong patch is applied silently.

This mirrors the report's TOCTOU pattern precisely: a "max"/permission-like value (`assetsMax`) computed from a stale storage read is combined with a fresher, differently-derived value (`amount`) without reconciling the two, causing the code to take the wrong branch. Here, a set of "included" line positions computed against diff #1 is combined with the differently-shaped diff #2 without reconciling positions, causing the wrong lines to be included/excluded from the commit.

The code even acknowledges the general staleness problem elsewhere, but only handles the case where selectable lines *disappear* (turn into context) — not the case where positions shift while remaining selectable: [5](#0-4) 

### Impact Explanation
This falls squarely into "silent corruption of what the user commits or pushes": a user who deliberately excludes certain lines (e.g. a secret, a debug statement, or unrelated code) from a partial commit can end up committing them anyway, or conversely omit lines they intended to include — with no error, warning, or diff-mismatch indication, because `git apply --cached` (invoked with `--whitespace=nowarn`) is tolerant of imperfect patches [6](#0-5) . Because the corrupted patch is applied straight to the index and then committed via `createCommit`/`_commitIncludedChanges`, the resulting commit's content diverges from what the UI showed the user was staged [7](#0-6) .

### Likelihood Explanation
The trigger requires the working-directory content of the selected file to change between the diff render used for line-selection and the second diff fetch inside `applyPatchToIndex`. A malicious/crafted cloned repository can arrange for this deterministically via Git's clean/smudge filter mechanism (`.gitattributes` + `filter.<name>.clean`/`smudge`, both attacker-supplied content that ships with a cloned or fetched repository) so that repeated invocations of `git diff`/`git status` against the same working tree produce differing content or line counts for a tracked file. Desktop already re-invokes status/diff independently in multiple places (status refresh, `updateChangesWorkingDirectoryDiff`, and the second call inside `applyPatchToIndex`), so the two diffs used for selection vs. staging are not guaranteed to be identical even without any additional user action beyond a normal partial-commit workflow.

### Recommendation
`applyPatchToIndex`/`formatPatch` should not trust the absolute-index-based `DiffSelection` against a diff object different from the one it was created from. Options:
- Pass the exact diff object the selection was validated against (or re-verify hash/etag/mtime of the file) into `applyPatchToIndex`, refusing to stage if it doesn't match the diff fetched fresh.
- Recompute the selection against the newly fetched diff by content (line text/type), not raw index, before formatting the patch, and abort (surfacing an error to the user) if the reconciliation cannot be done safely.

### Proof of Concept
Not directly reproducible from static analysis alone; the mechanism is demonstrated by tracing the code path:
1. User opens Changes view for `file.md`; Desktop computes diff D1 and displays it; user unchecks specific lines, producing `DiffSelection` S bound to D1's hunk layout.
2. Before pressing "Commit", a background process/filter (e.g. an attacker-supplied clean/smudge filter defined in the cloned repo's `.gitattributes`) alters how `file.md`'s diff renders, so a subsequent `git diff` yields D2 with shifted hunk offsets for the same working tree state.
3. `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex(repository, file)` re-fetches the diff (D2) via `getWorkingDirectoryDiff` [8](#0-7)  and calls `formatPatch(file, D2)`, which evaluates `file.selection.isSelected(absoluteIndex)` (S, built against D1) over D2's hunks [9](#0-8) .
4. Because S's indices no longer align with D2's line layout, lines the user intended to exclude get included in the generated patch (or vice versa), and `git apply --cached` applies it without error.

I was unable to fully verify from the index whether Desktop deduplicates/caches the diff between selection-time and commit-time in all code paths (e.g., whether `state.selection.diff` is ever threaded through to `createCommit`); confirming this end-to-end would require running Desktop's git test suite (`app/test/unit/git/apply-test.ts`, `commit-test.ts`) with a crafted smudge filter to observe the actual patch generated. This can be validated with a full Devin session that has terminal access to reproduce the scenario.
