### Title
DkgConfirmer reuses a cached FROST nonce across distinct messages/participant sets, enabling validator key recovery - ([File: coordinator/src/tributary/signing_protocol.rs](coordinator/src/tributary/signing_protocol.rs))

### Summary
The ECO bug is a stale-value desync: a value decided at one point in time (L1 `inflationMultiplier`) is applied under conditions that have since changed (L2 still using the old multiplier), so the same deposit amount resolves to different values on each side. The Serai analog lives in `SigningProtocol::preprocess_internal` / `share_internal`: the FROST nonce seed is decided once and cached under a context of only `(b"DkgConfirmer", attempt)`, but the *message being signed* (`set_keys_message(set, removed, key_pair)`) and the MuSig participant re-mapping are both computed later, at share time, from state that can change between the nonce decision and each `share()`/`complete()` invocation. If `share_internal` is ever executed twice for the same `attempt` with a different `key_pair`, a different `removed` set, or a different accumulated preprocess map, the coordinator emits a second Schnorr share under the identical nonce `(d, e)` with a different binding factor and/or challenge — the classic nonce-reuse equation pair that recovers the validator's private key share.

### Finding Description
`preprocess_internal` derives the deterministic nonce seed from `CachedPreprocesses` keyed only by `self.context`, which `DkgConfirmer::signing_protocol` sets to `(b"DkgConfirmer", self.attempt)` ([signing_protocol.rs:274-277](coordinator/src/tributary/signing_protocol.rs#L274), [signing_protocol.rs:123-145](coordinator/src/tributary/signing_protocol.rs#L123)). Neither the `key_pair`, the `removed` validator list, nor the received preprocesses are folded into that context.

The message is only formed inside `DkgConfirmer::share_internal` via `set_keys_message(&self.spec.set(), &removed..., key_pair)` ([signing_protocol.rs:296-301](coordinator/src/tributary/signing_protocol.rs#L296)), where `removed` is fetched fresh from `removed_as_of_dkg_attempt` in every `DkgConfirmer::new` ([signing_protocol.rs:271](coordinator/src/tributary/signing_protocol.rs#L271)), and the preprocess map is re-indexed by `threshold_i_map_to_keys_and_musig_i_map`, which is itself a function of `removed` ([signing_protocol.rs:208-250](coordinator/src/tributary/signing_protocol.rs#L208)). Meanwhile the nonce commitments stay fixed to the cached seed via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` ([crypto/frost/src/sign.rs:121-144](crypto/frost/src/sign.rs#L121)).

There are two desync windows:

1. **`removed` changes between calls.** `RemoveParticipantDueToDkg` votes are ongoing transactions handled in `handle_application_tx` ([handle.rs:258-284](coordinator/src/tributary/handle.rs#L258)). `share()` is invoked from `generated_key_pair` ([handle.rs:57-59](coordinator/src/tributary/handle.rs#L57)) and again inside `complete()` during `DkgConfirmed` accumulation ([handle.rs:533-535](coordinator/src/tributary/handle.rs#L533), [signing_protocol.rs:321-326](coordinator/src/tributary/signing_protocol.rs#L321)). If a removal finalizes between these, the second `share_internal` signs a different `set_keys_message` (different `removed` list) and computes different binding factors over the same raw nonces.

2. **`generated_key_pair` has no idempotence guard.** It unconditionally overwrites `DkgKeyPair`/`KeyToDkgAttempt` and emits a share ([handle.rs:54-59](coordinator/src/tributary/handle.rs#L54)). A second call for the same attempt with a different `key_pair` produces a share over a different message under the same nonce.

The file's own header concedes the safety model: nonce reuse occurs if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again," and explicitly lists the missing check as a TODO ("check the commitments generated from the decided nonces are in fact its commitments on-chain") ([signing_protocol.rs:34-54](coordinator/src/tributary/signing_protocol.rs#L34)). In FROST terms, two shares `s₁ = d + ρ₁e + c₁λ·x` and `s₂ = d + ρ₂e + c₂λ·x` with the same `(d, e)` yield `x` by linear elimination — recovery of the validator's MuSig secret key.

### Impact Explanation
Recovery of a coordinator validator's private signing key (the root-of-trust key used for DKG confirmation and removal votes), plus the ability to forge that validator's confirmation shares. This is the "desynced parameter applied to a stale counterpart" class: the nonce parameter is locked to `attempt`, while the counterparty data (`removed`, `key_pair`, preprocesses) is read fresh each call.

### Likelihood Explanation
Lower than a pure unauthenticated path: triggering requires either a removal vote to finalize in the narrow window between `share()` and `complete()` for the same attempt, or a duplicate `generated_key_pair` invocation with a differing `key_pair` (e.g., after eventuality re-execution or processor resend). Both are reachable through normal validator transaction flow without breaking BFT, but require specific ordering. Rated Medium on likelihood, High on impact.

### Recommendation
Bind the full signing context into the cache key: derive `context` from `(b"DkgConfirmer", attempt, key_pair, removed)` — or at minimum store the message alongside the cached seed and refuse to `sign()` under a cached seed when the computed `msg` or `removed` differs from the first signed attempt. Additionally, implement the file's own TODO: before publishing a share, verify the on-chain recorded preprocesses/key pair match the values presumed at nonce-decision time, and add an `AttemptDb`-style "share already emitted" marker to make `generated_key_pair` idempotent.
