### Title
Quadratic Lagrange interpolation in `ThresholdKeys::new` enables CPU denial of service via crafted serialized keys - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::read` deserializes attacker-controlled `t`/`n` parameters (each up to `u16::MAX = 65535`) and then calls `ThresholdKeys::new`, which computes the group key by evaluating `interpolation_factor` for every participant `1..=t`. With `Interpolation::Lagrange`, each `interpolation_factor` call iterates over all `t` included participants, yielding O(t²) field operations — up to ~4.3 billion scalar multiplications/inversions triggered by only ~4 MB of untrusted input. This is the same bug class as JLSEC-2026-533 / CVE-2018-6616: a loop bound derived from an input-controlled field causing excessive iteration disproportionate to the input.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, and `i` directly from the byte stream (`crypto/dkg/src/lib.rs:591-602`), reads `n` verification shares (`crypto/dkg/src/lib.rs:620-623`), and passes everything to `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:625-631`). Inside `ThresholdKeys::new`, the group key is computed as:

```rust
let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
let group_key =
  t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();
```

(`crypto/dkg/src/lib.rs:376-378`)

For `Interpolation::Lagrange` (tag byte `1`, attacker-selected at `crypto/dkg/src/lib.rs:604-616`), `interpolation_factor` runs a loop over the full `included` slice for each participant (`crypto/dkg/src/lib.rs:229-246`). The result is t outer iterations × t inner iterations of field multiplications, plus `t` field inversions and `t` point multiplications.

The same quadratic pattern also exists in `ThresholdKeys::view` (`crypto/dkg/src/lib.rs:500-507`), which computes `interpolation_factor` per included participant — reachable when an attacker supplies a large `included` signing set of preprocesses to `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:290-312`), though there `included` is bounded by the local `n`.

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (listed as an untrusted-bytes sink) can set `t = n = 65535` with `Interpolation::Lagrange`. After supplying `n` encoded points (~2 MB), deserialization triggers ~4.3 billion field multiplications plus 65535 inversions and point multiplications — effectively unbounded CPU consumption per single small message, exhausting a validator's/processor's signing thread. This is an availability-only denial of service with no secret leakage, matching the Medium/A:H profile of the original advisory.

### Likelihood Explanation
Reachability depends on the integrator passing untrusted bytes to `ThresholdKeys::read` or invoking `view`/`sign` with attacker-influenced participant sets. Within the Serai deployment, `ThresholdKeys` are persisted/loaded, but any path where serialized keys or large preprocess sets cross a trust boundary exposes this. The cost asymmetry is severe: megabytes of input yield billions of operations. Likelihood is moderate since it requires a deserialization entry point reachable by an untrusted party, but no valid key material, proof, or signature is needed — the work happens before any secret is used.

### Recommendation
- Bound `t`/`n` to a sane maximum (e.g., the actual validator-set limit, well under `u16::MAX`) inside `ThresholdParams::new` or `ThresholdKeys::read` before any allocation or interpolation occurs.
- In `ThresholdKeys::new` and `ThresholdKeys::view`, batch-compute Lagrange denominators (prefix-product trick) or compute the group key via a single multiexp to reduce O(t²) to O(t log t) / O(t).
- Avoid `Vec::with_capacity(usize::from(n))` in `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:608`) before validating `n`, since it also permits a 65535-element preallocation from a 2-byte field.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;
use frost::curve::Ristretto; // any in-scope Curve

fn main() {
    let t: u16 = u16::MAX;
    let n: u16 = u16::MAX;
    let i: u16 = 1;

    let mut buf = vec![];
    // C::ID header
    buf.extend(u32::try_from(<Ristretto as Ciphersuite>::ID.len()).unwrap().to_le_bytes());
    buf.extend(<Ristretto as Ciphersuite>::ID);
    buf.extend(t.to_le_bytes());
    buf.extend(n.to_le_bytes());
    buf.extend(i.to_le_bytes());
    buf.push(1); // Interpolation::Lagrange
    // secret_share: canonical encoding of 1 (32 bytes for Ristretto)
    let mut one = <Ristretto as Ciphersuite>::F::ONE.to_repr();
    buf.extend(one.as_ref());
    // n verification shares: n copies of the generator encoding
    let g = <Ristretto as Ciphersuite>::generator().to_bytes();
    for _ in 0 .. n {
        buf.extend(g.as_ref());
    }

    // ~2 MB of input -> t^2 ≈ 4.3e9 field multiplications + 65535 inversions
    // inside ThresholdKeys::new's group_key computation.
    let _keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
}
```

The crafted input is only ~2 MB yet forces O(65535²) work in `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:376-378`) via the nested `interpolation_factor` loop (`crypto/dkg/src/lib.rs:229-246`), hanging the calling thread — analogous to the excessive-iteration DoS in `opj_t1_encode_cblks`.

Note: I verified the quadratic path exists in `ThresholdKeys::new`/`view`; I could not fully confirm every caller plumbing untrusted bytes into `ThresholdKeys::read` within the available iterations, but the sink is explicitly in scope for untrusted input per the rules.
