## Analysis

I found a real analog of the fee-on-transfer bug class in GitHub Desktop: **an unvalidated assumption that a previously-computed line-selection index still matches a freshly-fetched diff**, exactly mirroring how the original bug assumed a transferred `amount` still equaled the amount actually received.

The core invariant that breaks: `WorkingDirectoryFileChange.selection` stores *absolute line indices* into a specific diff snapshot. Git status/diff refresh logic in `app/src/lib/stores/updates/changes-state.ts` explicitly preserves this stale, index-based selection across refreshes via `file.withSelection(existingFile.selection)` [1](#0-0)  and only prunes indices that fall outside the recomputed `selectableLines` set [2](#0-1) . The comment even admits this is a known gap: *"The diff might have changed dramatically since last we loaded it... for now we'll settle on just updating the selectable lines."* [3](#0-2) 

When the file is actually staged, `applyPatchToIndex` re-fetches a brand-new diff with `getWorkingDirectoryDiff` [4](#0-3)  and hands it to `formatPatch`, which walks the new diff's hunks and tests `file.selection.isSelected(absoluteIndex)` [5](#0-4) . If the new diff's line-index layout differs even slightly from the layout the selection was computed against (e.g., a hunk gained/lost lines, or hunk boundaries shifted), the same numeric `absoluteIndex` now points to a semantically different line. `formatPatch` then silently includes/excludes the wrong content, and `git apply --cached --unidiff-zero` writes it straight into the index with no content-equality check.

This is not merely theoretical: the file content on disk between "diff shown to user / selection made" and "diff re-fetched for staging" can change because Desktop refreshes status/diff on a timer and after many git operations (fetch, pull, checkout, branch switch, stash pop, merge, LFS smudge filters configured via `.gitattributes`, editor auto-format-on-save, etc.). Any of these can be triggered by content in a cloned/fetched repository (e.g., `.gitattributes` filter config, submodule updates, merge results) without the user redoing their line selection, since `updateChangedFiles` deliberately keeps the old selection object alive.

### Title
Stale line-index selection is applied against a freshly re-fetched diff, silently corrupting partial commits - (`app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`)

### Summary
`WorkingDirectoryFileChange.selection` records which lines a user wants staged as *numeric absolute indices* into a diff snapshot. Desktop deliberately carries this selection forward across working-directory refreshes without invalidating it when the underlying diff structure changes, then re-derives a *brand-new* diff at commit time and reapplies the old indices to it, exactly like the fee-on-transfer contract that assumed a previously computed `amount` still matched funds actually available after an intervening state change.

### Finding Description
`updateChangedFiles` (`app/src/lib/stores/updates/changes-state.ts:44-59`) merges new git-status results with the existing `WorkingDirectoryFileChange`, and unconditionally re-applies `existingFile.selection` to the newly-observed file unless `clearPartialState` forces a full reset. `updateChangesWorkingDirectoryDiff` (`app/src/lib/stores/app-store.ts:3478-3497`) similarly keeps the selection object, only trimming indices that fall outside the new `selectableLines` set — indices that still fall within range but now point at a different line are left untouched, as the code comment itself concedes.

When the user commits, `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:52-61`) fetches yet another fresh diff via `getWorkingDirectoryDiff` and passes it into `formatPatch` (`app/src/lib/patch-formatter.ts:129-232`). `formatPatch` decides whether to keep a line purely by `file.selection.isSelected(absoluteIndex)` — a numeric lookup with no correlation to the actual text content of that line in the diff being formatted. If hunk boundaries or line counts shifted between the time the selection indices were established and the time this final diff was fetched, the wrong lines are selected/deselected, and `git apply --cached --unidiff-zero` (which relies purely on explicit line numbers, not context, due to `--unidiff-zero`) commits that mismatched patch into the index with no verification that the resulting staged content matches user intent.

### Impact Explanation
This causes **silent corruption of what the user actually commits/pushes** — the defining "Valid Impact" category for this task. A user who selects specific lines for a partial commit can end up staging different lines than they saw and picked, without any error or warning, because none of the involved code paths compare the *content* of the line being written against the *content* the user saw when selecting it. This is functionally identical to the origination-fee/transfer-fee mismatch in the seed report: a numeric value (`amount` / `absoluteIndex`) is trusted to still be valid after an operation shifted the actual state it was measured against.

### Likelihood Explanation
The working directory diff/status is refreshed frequently and automatically (background polling, after fetch/pull/checkout/merge, LFS smudge filters defined in a cloned repo's `.gitattributes`, submodule updates) — all without necessarily invalidating an in-progress partial-selection. Any repository content that causes the tracked file to be rewritten between the moment a user makes a partial line selection and the moment they click "Commit" is sufficient to trigger a layout shift in the diff; the more hunks/lines a file has, the higher the chance of an index collision producing a different but still "valid" line. This requires no privileged access, malware, or social engineering — only a cloned/fetched repository whose configuration (filters, submodules, merge state) can cause file content to shift during normal Desktop usage.

### Recommendation
Do not trust bare numeric line indices across diff refetches. Either (a) invalidate/reset any `Partial` selection whenever the diff's structural hash/line count changes materially, forcing the user to re-select, or (b) have `formatPatch` validate that the line *content* at each selected index in the newly-fetched diff matches the content recorded at selection time, aborting (rather than silently mis-applying) the patch if it doesn't. Additionally, consider comparing the sha/mtime of the file used to render the diff shown to the user against the file used to build the commit-time diff, and refuse to stage if they differ without an explicit re-confirmation.

### Proof of Concept
1. Open a modified text file with multiple hunks in Desktop's Changes view and select only specific lines for a partial commit (creating a `DiffSelectionType.Partial` selection keyed on absolute indices from the currently displayed diff).
2. Before committing, cause the working tree copy of that same file to be rewritten with different line boundaries but a similar overall size — e.g., trigger a background fetch+auto-merge, a submodule/LFS smudge re-checkout, or simply externally edit the file to add/remove a line inside an earlier hunk (this can be driven by repository-provided tooling such as a `.gitattributes` filter or a build script the cloned repo instructs the user to run).
3. Desktop's status/diff refresh (`updateChangedFiles`/`updateChangesWorkingDirectoryDiff`) re-renders the file with the shifted diff but preserves the old selection indices unchanged (per `app/src/lib/stores/updates/changes-state.ts:41-59` and `app/src/lib/stores/app-store.ts:3478-3497`).
4. Click "Commit". `applyPatchToIndex` fetches a new diff and `formatPatch` applies the stale indices against it (`app/src/lib/patch-formatter.ts:143-171`), producing a patch that stages different lines than originally selected; `git apply --cached --unidiff-zero` commits it without complaint.
5. Inspect the resulting commit: it contains lines the user never intended to include (or omits ones they did), with no error shown — demonstrating silent corruption of the committed content.
