### Title
Desynchronized `ReceivedOutput` offset/script_pubkey permanently locks funds and corrupts fee math - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes `offset`, `output` (a `TxOut` containing `script_pubkey` and `value`), and `outpoint` as three independent, unauthenticated fields [1](#0-0) . The only place consistency between `offset` and `script_pubkey` is enforced is inside `SignableTransaction::multisig`, which returns `None` (indistinguishable from "wrong keys") if `p2tr_script_buf(key + G*offset) != prevout.script_pubkey` [2](#0-1) . Analogous to the C-04 report — where the vault authorizes against `record.receiver` instead of `record.owner` and reverts, locking funds — Serai authorizes the spend against an attacker-influenced `offset` field rather than the identity that actually received the funds, and fails closed by silently refusing to sign.

### Finding Description
`scan_transaction` produces `ReceivedOutput`s where `offset` is looked up by `script_pubkey` in `self.scripts`, so scanned outputs are internally consistent [3](#0-2) . However, `ReceivedOutput::read` accepts arbitrary bytes: the `offset` scalar, the `TxOut`, and the `OutPoint` need not correspond to any real chain output nor to each other. There is no binding that `p2tr_script_buf(key + G*offset) == output.script_pubkey`, no check that `outpoint` exists, and no check that `value` matches the chain output.

When such an output is passed to `SignableTransaction::new`, two independent failure modes occur:

1. **Locked funds**: `multisig()` loops over inputs and returns `None` if any single input's `offset` doesn't regenerate its `script_pubkey` [4](#0-3) . One bad input poisons the entire transaction — all co-spent inputs become unspendable through this path, and the `None` return gives no indication of which input failed or why (identical to genuine wrong-key usage), mirroring C-04's silent revert.

2. **Incorrect verifier/fee formula**: `prevouts` are taken verbatim from the untrusted `TxOut` values and are committed into every input's sighash via `Prevouts::All` [5](#0-4) . A forged `value` makes `fee()`, `needed_fee`, the change computation [6](#0-5) , and the BIP-341 sighash all operate on a phantom amount — producing either an invalid (unbroadcastable) signed transaction or, if the script check passes, an arbitrarily inflated fee paid to miners.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (one of the designated untrusted-input sinks) can cause outputs to be tracked/spent that are not spendable: either the wallet permanently refuses to sign (`multisig` → `None`), locking the referenced UTXO and every input batched with it, or it signs a transaction committing to fabricated prevout amounts that the network rejects. This is the Serai equivalent of "funds get locked in the vault": assets reported as received cannot be redeemed, with no error path distinguishing corruption from wrong keys.

### Likelihood Explanation
`ReceivedOutput::read` performs zero cross-field validation — reachability is exactly the documented untrusted-bytes sink. The failure is deterministic once a desynchronized record reaches `SignableTransaction::new`/`multisig`, and because `multisig` collapses all failure causes into `None`, retrying cannot recover; the input set must be manually rebuilt. Severity is Medium: it requires influencing persisted/transported output records rather than pure on-chain data, but needs no key material, no collusion, and no protocol deviation beyond supplying crafted bytes.

### Recommendation
Bind the fields at deserialization and at spend time:

- In `SignableTransaction::new` (or a `ReceivedOutput::verify(&self, key)` helper), assert `p2tr_script_buf(key + GENERATOR*offset) == Some(output.script_pubkey)` and return a distinct `TransactionError` (e.g. `InconsistentInput`) instead of failing inside `multisig` with `None`.
- Make `multisig`'s per-input failure distinguishable (return `Result` with the failing input index) rather than `None`, so a single corrupt record doesn't silently brick an entire transaction.
- Where possible, validate `outpoint`/`value` against the confirmed chain output before queuing a spend, rather than trusting the serialized `TxOut` committed via `Prevouts::All`.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read:
// a real outpoint + a script_pubkey registered to offset O,
// but the stored offset is O' != O.
let mut buf = Vec::new();
buf.extend(O_prime.to_bytes());            // wrong offset
buf.extend(serialize(&TxOut { value: Amount::from_sat(100_000),
                              script_pubkey: script_for_O })); // script of offset O
buf.extend(serialize(&real_outpoint));
let forged = ReceivedOutput::read(&mut &buf[..]).unwrap();

// Bundled with a legitimate input:
let tx = SignableTransaction::new(vec![legit, forged], &payments, change, None, fee).unwrap();
// For EVERY participant, multisig() hits `p2tr_script_buf(offset_key) != prevout.script_pubkey`
// and returns None -> the entire batch (including `legit`) can never be signed.
assert!(tx.multisig(&keys).is_none());
```
Alternatively, keeping `offset` consistent but inflating `output.value` causes `Prevouts::All` to commit a fabricated amount into the BIP-341 sighash, yielding a signed transaction that fails consensus validation — funds received but provably unspendable via this wallet path.

    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
