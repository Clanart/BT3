## Analysis

The Solidity report's bug class is: **an attacker-controlled recursive/nested call structure causes a "diff" accounting mechanism to be miscomputed, so a value that was only added once gets counted (and paid out/credited) multiple times.**

The Cosmos EVM analog exists in the stateful-precompile balance-reconciliation mechanism, `BalanceHandler`.

### Root cause

`precompiles/common/precompile.go`'s `runNativeAction` wraps every stateful precompile call: it snapshots the event count before execution (`BeforeBalanceChange`) and, after the native action runs, replays every bank/precisebank event emitted since that point into the EVM `StateDB` (`AfterBalanceChange`): [1](#0-0) 

`BeforeBalanceChange`/`AfterBalanceChange` operate on a simple index into `ctx.EventManager().Events()`: [2](#0-1) [3](#0-2) 

This event log is **not truncated or partitioned per call** — it's the shared `ctx.EventManager()` for the whole EVM execution. When a precompile call is itself re-entered (a Solidity contract calling back into a precompile, or a precompile internally calling back into EVM which calls the precompile again — exactly the pattern exercised by `DebugPrecompileCaller.callback()` and the ICS20 "recursive precompile calls" test suite), each nested call gets its own `BalanceHandler` (one per `runNativeAction` invocation) with its own `prevEventsLen` snapshot, and each nested call's `AfterBalanceChange` already applies `stateDB.AddBalance`/`SubBalance` for the events emitted during *its own* scope. But the **outer** call's `BalanceHandler` captured `prevEventsLen` *before* the nested call happened, so when the outer call finally reaches its own `AfterBalanceChange`, it re-scans `events[outerPrevEventsLen:]` — a range that **still includes the events already consumed and applied by the inner call's handler**. Those events get parsed and applied to the `StateDB` a second time.

This is precisely the `PodUnwrapLocker` bug class: a balance-delta computation that assumes a token/event list belongs to a single, non-overlapping operation, but an attacker-controlled recursive/nested call causes the same underlying value (bank `coin_spent`/`coin_received` events) to be counted and credited to the `StateDB` more than once.

This exact scenario is already flagged as a known bug and reproduced by the test suites in this repo:
- `evmd/tests/integration/balance_handler/balance_handler_test.go` — explicitly documents: *"tests the balance handler bug where recursive precompile calls share the same BalanceHandler instance, causing prevEventsLen to be overwritten. This leads to balance desync between native bank keeper and EVM stateDB."* [4](#0-3) 
- `evmd/tests/ibc/ics20_recursive_precompile_calls_test.go` — *"Tests the native balance handler bug where reverted distribution calls leave persistent bank events that are incorrectly aggregated"* [5](#0-4) 

### Title
Double/incorrect crediting of `StateDB` balances via overlapping event windows in nested/recursive stateful-precompile calls — (`precompiles/common/balance_handler.go`, `precompiles/common/precompile.go`)

### Summary
`BalanceHandler.AfterBalanceChange` reconciles EVM `StateDB` balances with native `x/bank`/`x/precisebank` state by replaying every bank event emitted since a recorded index (`prevEventsLen`) into `stateDB.AddBalance`/`SubBalance`. Because `prevEventsLen` is captured on a per-call basis against a globally shared `ctx.EventManager()`, and each nested/recursive precompile invocation gets its own `BalanceHandler` instance (via `BalanceHandlerFactory.NewBalanceHandler()` in `runNativeAction`), an outer call's post-processing window overlaps with, and re-processes, events already consumed and applied by an inner (nested/reentrant) call's own `BalanceHandler`. A contract that recursively invokes a stateful precompile (staking, distribution, gov, ICS20, ERC20, bank, slashing — all of which wire in `BalanceHandlerFactory`) can trigger this double-application, crediting/debiting the same coin movement twice against the EVM `StateDB`.

### Finding Description
Every stateful precompile (`staking`, `distribution`, `gov`, `slashing`, `ics20`, `erc20`) is constructed with a `cmn.Precompile.BalanceHandlerFactory` [6](#0-5) . On each call, `runNativeAction` creates a fresh `BalanceHandler`, records `prevEventsLen = len(ctx.EventManager().Events())`, executes the precompile logic (which may itself trigger nested EVM calls back into the same or another precompile via `evmKeeper.CallEVMWithData`, as demonstrated by `DebugPrecompileCaller.Call0`), and finally replays `events[prevEventsLen:]` into `StateDB.AddBalance`/`SubBalance` [1](#0-0) .

If the native action recurses into another (or the same) stateful precompile call before returning, that inner call performs its own full `BeforeBalanceChange`/action/`AfterBalanceChange` cycle and applies the bank events emitted in its own window to `StateDB`. Execution then returns to the outer call, which resumes and eventually reaches its own `AfterBalanceChange` using the *original* (earlier) `prevEventsLen`. Since the event manager is a single running log for the whole transaction, the outer handler's slice `events[outerPrevEventsLen:]` still contains the inner call's events — which were already applied to `StateDB` by the inner `BalanceHandler`. The outer handler re-parses and re-applies the same `coin_spent`/`coin_received`/fractional-balance events, calling `StateDB.AddBalance`/`SubBalance` a second time for value that moved only once at the ledger (`x/bank`) level.

### Impact Explanation
This breaks the core Cosmos-EVM duality invariant that `StateDB` balances must mirror `x/bank`/`x/precisebank` native balances 1:1. Because `StateDB.AddBalance` is what the EVM actually uses for subsequent `balanceOf`/transfer logic within the same transaction (and what ultimately gets committed back), double-application inflates the EVM-visible balance of accounts involved in nested precompile calls without a corresponding real increase in the native ledger. An attacker who controls a contract that recursively re-enters a stateful precompile (as shown feasible in-repo by `DebugPrecompileCaller` and the ICS20 recursive-call test) can manufacture EVM-spendable balance not backed by real coins — an unauthorized duplication/creation of spendable value, matching the Critical "unauthorized minting/duplication of spendable user value across EVM balances" impact class.

### Likelihood Explanation
The trigger is fully unprivileged: any account can deploy a contract that calls a stateful precompile (e.g., `staking`, `distribution`, `ics20`, `erc20`) in a way that re-enters a precompile before the outer call returns (via callback/hooks such as ERC20 `_beforeTokenTransfer` overrides, exactly as exercised by `ERC20RecursiveNonReverting`/`ERC20RecursiveReverting` test contracts referenced in `ics20_recursive_precompile_calls_test.go`). No privileged role, validator cooperation, or governance action is required.

### Recommendation
Make the event-window bookkeeping reentrancy-safe: either (a) truncate/mark the global event log as consumed up to the point where an inner `AfterBalanceChange` has processed it (so an outer handler's later slice starts after the last index already consumed by any nested handler), or (b) maintain a single shared/global cursor (not per-call-local `prevEventsLen`) that is monotonically advanced by every `AfterBalanceChange` call regardless of nesting depth, so no event range is ever processed twice.

### Proof of Concept
The repository's own tests already reproduce the reentrant condition and describe the resulting desync: [7](#0-6) [8](#0-7) 
A concrete PoC would deploy a contract (analogous to `DebugPrecompileCaller`/`ERC20RecursiveNonReverting`) that, from within a stateful precompile call touching a real coin balance (e.g., `distribution.Deposit`/`ics20.Transfer`), triggers a nested call back into a stateful precompile before returning, then compares the resulting `StateDB` balance for the involved account against the `x/bank` `GetBalance` value — demonstrating a `StateDB` credit exceeding the actual bank-ledger movement.

	evmApp := s.chain.App.(evm.EvmApp)
	ctx := s.chain.GetContext()

	debugPrec := debugprecompile.NewPrecompile(evmApp.GetBankKeeper(), evmApp.GetEVMKeeper())

	a, b, c := evmApp.GetEVMKeeper().GetPrecompileInstance(ctx, debugPrec.Address())
	fmt.Println(a, b, c)

	// Deploy caller contract
	callerContract, err := contracts.LoadDebugPrecompileCaller()
	s.Require().NoError(err)

	deploymentData := testutiltypes.ContractDeploymentData{
		Contract:        callerContract,
		ConstructorArgs: []interface{}{},
	}

	// Use local helper function
	callerAddr, err := DeployContract(s.T(), s.chain, deploymentData)
	s.Require().NoError(err)
	s.chain.NextBlock()

	s.T().Logf("Debug precompile at %s", debugPrec.Address().Hex())

	// Pack the input for callback(0)
	input, err := callerContract.ABI.Pack("callback", big.NewInt(0))

	debug_count := 0
	for _, event := range res.Events {
