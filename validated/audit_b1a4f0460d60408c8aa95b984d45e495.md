### Title
Duplicate-key detection is silently skipped for `null`-valued JSON members, letting a later occurrence of the same field overwrite an already-set value without being flagged as a conflict — (`File: src/google/protobuf/json/internal/parser.cc`)

### Summary
Waitress's flaw was that its `Transfer-Encoding` handling only checked a single expected token; anything else silently fell back to a different framing mechanism (`Content-Length`), letting attacker input be parsed two different ways by two different consumers and causing request smuggling. The Protobuf ProtoJSON parser has a structurally identical "partial check, silent fallback" defect: `ParseField` special-cases `null` values and returns *before* calling `Traits::RecordAsSeen`, so a `null` occurrence of a field/oneof member is never recorded as "seen." A subsequent occurrence of the *same* key is then treated as first-seen rather than duplicate, bypassing the duplicate/oneof-conflict check that would otherwise reject the payload. The code comment explicitly acknowledges the gap: "spec behavior is that we should do duplicate key checking in the case of a null value, but this implementation currently does not (b/519557203)."

### Finding Description
`ParseField` resolves the field, then handles the `null` case up front: [1](#0-0) 

If the incoming value token is `null` and the field's message type is not `google.protobuf.Value`/`NullValue`, the function calls `lex.Expect("null")` and returns immediately — **without ever calling `Traits::RecordAsSeen`**. Only in the non-null path does the code proceed to: [2](#0-1) 

`RecordAsSeen` is what tracks which fields/oneofs have already been set during this parse pass, using per-parse tracking sets: [3](#0-2) 

Because the `null` branch skips this bookkeeping entirely, the invariant "a field/oneof member may be set at most once per JSON object (or, in duplicate-key mode, last-one-wins)" is broken specifically for the case where an earlier occurrence was `null`. Concretely:
- `{"oneofA": null, "oneofB": "x"}` — the `null` occurrence of `oneofA` is a no-op that never marks the oneof as seen, so `oneofB` is treated as the *first* write to the oneof rather than a conflicting second write. (This particular ordering happens to be benign since `oneofA` never actually got a value, matching test `testNullFirstInDuplicateOneof` in the Java runtime — but the C++/upb-based ProtoJSON path implements the tracking differently and independently, per the explicit comment marking this as an unresolved discrepancy.)
- More importantly, for legacy/duplicate-key-tolerant parsing (`allow_legacy_nonconformant_behavior`), the same-field-twice case `{"foo": "real_value", "foo": null}` results in the `null` being a silent no-op that leaves `foo`'s previously-set value **intact**, rather than applying the documented "last one wins" duplicate-key resolution rule used everywhere else in the wire/JSON format (see the project's own documented invariant): [4](#0-3) 

This is the direct analog of the Waitress bug: the "last write wins for duplicate keys" invariant is only enforced along one code path (non-null values), and the exceptional case (`null`) silently takes a different, unchecked path — exactly like Waitress checking `Transfer-Encoding` for a single exact token and falling back to `Content-Length` framing for anything else. Two different consumers of the same JSON payload (e.g., a validating proxy/gateway using a strict spec-conformant JSON parser vs. this Protobuf ProtoJSON parser as the backend) can disagree about which of two duplicate keys "wins," enabling a field-value smuggling condition: a gateway/validator may see and approve the `null` (or the final) value while the actual backend message ends up carrying the other value.

### Impact Explanation
This is a parser-differential/integrity issue (CWE-444 analog), not a memory-safety bug. Its impact depends on the consuming application: if any system treats ProtoJSON as a canonical, single-valued format (assuming duplicate keys are impossible or resolved identically everywhere, per JSON's "must have a unique name" assumption noted in the project's own docs), an attacker can craft a payload with a duplicated key where one occurrence is `null`, causing this parser to retain/ignore a value in a way that diverges from another JSON/ProtoJSON parser (or from the documented "last one wins" semantics). This is a Medium-severity integrity/confidentiality-adjacent issue — it does not grant memory corruption or RCE, but it can be leveraged in exactly the "confused deputy across two parsers" way that made the Waitress issue reportable: request/message smuggling of a field value across two disagreeing consumers.

### Likelihood Explanation
Reachable via the fully public, supported `JsonStringToMessage` / `MessageToJsonString` ProtoJSON parsing API with a bounded, attacker-controlled JSON payload and only a trusted schema — no privileged access or hostile schema required. The triggering condition (a duplicate key, one occurrence `null`) is trivial to construct. The bug is self-documented in the source via the `b/519557203` comment, confirming it is a known, currently-unfixed behavior gap in the maintained code rather than a already-patched issue.

### Recommendation
Call `Traits::RecordAsSeen` for the `null` case exactly as for the non-null case, before deciding to short-circuit, so that a `null` occurrence of a field participates in the same duplicate-key/oneof-conflict bookkeeping as any other value. If `null` is meant to explicitly clear/no-op a field, that decision should be made *after* the duplicate check, consistently applying "last one wins" (or duplicate rejection, per `allow_legacy_nonconformant_behavior`) regardless of whether the winning occurrence's value happens to be `null`.

### Proof of Concept
Using the generic `Desc<Traits>`/`Msg<Traits>` parse path in `src/google/protobuf/json/internal/parser.cc` (reachable from the public `JsonStringToMessage` API) with a message containing a `oneof` or a plain field `foo`, feed:
```json
{"foo": "real_value", "foo": null}
```
Trace: first `"foo": "real_value"` → `RecordAsSeen` returns `kFirstSeen`, field set to `"real_value"`. Second `"foo": null` → hits the `lex.Peek(JsonLexer::kNull)` branch at [5](#0-4)  (type is not `Value`/`NullValue`), calls `lex.Expect("null")`, and returns `absl::OkStatus()` **without calling `RecordAsSeen`**. No "already been set" error is raised, and the final message still has `foo == "real_value"`, i.e., the second occurrence of the duplicated key silently vanished instead of being rejected (strict mode) or applied as "last one wins" (legacy mode) — diverging from both documented behaviors and from any other JSON parser that treats `null` as a genuine value overriding the prior one. This matches the exact bug class described in the source comment at lines 1246-1248, which is not disputed but explicitly flagged as unresolved.

```text
  /// Functions for writing fields. ///

  // Marks a field as having been "seen". This will return a SeenState
  // indicating whether it is first seen, duplicate field seen, or oneof
  // conflict seen.
  static SeenState RecordAsSeen(Field f, Msg& msg) {
    if (f->real_containing_oneof() != nullptr) {
      int oneof_index = f->real_containing_oneof()->index();
      bool oneof_inserted =
          msg.parsed_oneofs_indices_.insert(oneof_index).second;
      if (!oneof_inserted) {
        // Oneof takes precedent over Field in the case of "this is in a oneof
        // and the field is set"
        return SeenState::kOneofAlreadySeen;
      }
    }

    bool field_inserted = msg.parsed_fields_.insert(f->number()).second;
    if (!field_inserted) {
      return SeenState::kFieldAlreadySeen;
    }

    return SeenState::kFirstSeen;
  }
```
