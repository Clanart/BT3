### Title
`CallDispatcher.dispatch()` is a fully permissionless arbitrary-call function that can drain any value the dispatcher is holding — ([File: evm/src/utils/CallDispatcher.sol])

### Summary
The external report's core primitive is a public function that makes an arbitrary, caller-controlled external call (`to.call(data)`) from a contract that temporarily custodies user-approved/user-owned assets, with no whitelist or origin check on `to`/`data`. Hyperbridge's `CallDispatcher` reproduces this exact primitive: `dispatch()` is `external`, takes an attacker-suppliable `Call[]` (`to`, `value`, `data`), and executes each call with no caller restriction whatsoever.

### Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` array and executes `to.call{value: call.value}(call.data)` for each entry, with the only check being that `to` has code (`extcodesize`): [1](#0-0) 

There is no `onlyGateway`, no `msg.sender` check, and no binding to any order commitment, message id, or caller identity. The contract also has an unrestricted `payable receive()`: [2](#0-1) 

`CallDispatcher` is used as a **shared singleton** referenced by `_params.dispatcher` across `IntentGatewayV2` (predispatch/postdispatch order calldata) and is documented as intentionally holding native ETH/tokens *between* the unlock/transfer step and the actual `Call` execution step, so that subsequent calls in the batch can spend it: [3](#0-2) 

The developer docs explicitly describe this hold-and-forward design for HyperFungibleToken calldata execution — tokens are unlocked/unwrapped **to the `CallDispatcher` address** first, and the dispatcher is expected to hold that balance until its own calls spend it: [4](#0-3) 

Because `dispatch()` has no access control, **anyone** — not just the gateway/HFT contract that is supposed to drive the sequence — can call it directly. If the dispatcher is holding any balance at the moment an attacker's transaction lands (e.g., leftover native ETH forwarded to it by a prior unlock step, dust that a sweep failed to fully collect, or ETH sent to its unrestricted `receive()`), the attacker can call `dispatch()` with `Call({to: attacker, value: <balance>, data: ""})` and sweep it before the legitimate flow's own `dispatch`/sweep call executes.

This is structurally identical to `Swap.sol.fillZrxQuote()` in the referenced report: a public function that performs an unrestricted external call from a contract that transiently custodies value, with the "confirm intent then forward" step separated from the "hold value" step such that any caller — not the intended party — can trigger the forwarding to a target of their choosing.

### Impact Explanation
Any native ETH (or ERC20, since `Call.data` is arbitrary and can call `transfer`/`transferFrom` if the dispatcher itself has been approved as a token holder) held by the `CallDispatcher` at any point can be redirected to an attacker-chosen address by a completely unprivileged caller. Given the documented design pattern of "unlock to `CallDispatcher`, then have it forward via `Call.value`" for cross-chain calldata execution (HFT/WrappedHFT bridging + Uniswap swap examples), the dispatcher is expected to hold real user value mid-flow. Since `dispatch()` itself does not authenticate the caller or bind the call to a specific order/commitment/message, this breaks the "funds move exactly once to the rightful beneficiary" invariant required by the bounty scope.

### Likelihood Explanation
Exploitability depends entirely on whether `CallDispatcher` ever holds a nonzero balance outside of a single atomic transaction executed by the legitimate flow (gateway/HFT). Within `IntentsBase._execute`, the transfer-in, `dispatch()` call, and sweep-out all occur in one atomic function call inside the same transaction, which would prevent an external actor from interleaving a call — this needs confirmation for the HFT/WrappedHFT `data`-execution path, where the docs' phrasing ("Tokens are unlocked... to `to` first, then the `CallDispatcher` executes each call") could imply unlock and execution are separate steps potentially in separate transactions/messages. I was not able to fully verify the HFT/WrappedHFT executor code path within the tool budget to confirm whether unlock-to-dispatcher and dispatch-execution are guaranteed atomic in every code path, or whether stray `receive()` ETH can realistically accumulate. This uncertainty limits confidence that the exploit window is real in production rather than purely theoretical.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by an authorized/registered gateway address (e.g., `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`) via an `onlyAuthorizedCaller` modifier, or
- Make `CallDispatcher` per-call/ephemeral (deploy a fresh minimal-proxy instance per order/message, matching the "hold value transiently" design without ever sharing state across unrelated flows), and
- Ensure the token/ETH unlock step and the `dispatch()` execution step are always performed atomically within a single transaction so no window exists where the dispatcher holds spendable value while awaiting an untrusted external call.

### Proof of Concept
1. Assume the `CallDispatcher` singleton momentarily holds `N` wei of native ETH between the "unlock to dispatcher" step of a cross-chain HFT calldata-execution flow and its own `dispatch()`-driven forwarding call (per the documented pattern where tokens/ETH are unlocked "to `to` first, then the `CallDispatcher` executes each call").
2. An attacker observes this state (e.g., via mempool monitoring of the unlock transaction, or via any protocol path that leaves the dispatcher non-empty even momentarily).
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: attackerContract, value: N, data: ""})]))` directly — this succeeds because `dispatch()` has no `msg.sender`/commitment check: [5](#0-4) 
4. The legitimate flow's subsequent `dispatch()`/sweep call now operates on a drained dispatcher, causing loss of the bridged funds to the attacker instead of the intended beneficiary/DeFi route.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
