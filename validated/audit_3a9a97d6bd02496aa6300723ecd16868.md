### Title
Gasless swap admission relies on a stale/manipulable AMM spot price, allowing bundle proposer/lender value drain via reserve manipulation - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessModule.checkBalanceForSwap` (the tx-pool admission gate for KIP-247 gasless swaps) sizes the required `amountIn` for a user's swap by making a single, un-pinned view call to `GaslessSwapRouter.GetAmountIn(token, minAmountOut)` against the *current* chain state at admission time [1](#0-0) . This is directly analogous to LlamaLend's reliance on a live, donation-inflatable price to gate a settlement (hard liquidation): here the settlement is "how much token must the user pay in for the block proposer to be repaid the KAIA it lent." Because the AMM reserves that back `GetAmountIn` can be shifted by the same attacker (the gasless-tx sender) via their own preceding trade against the underlying Uniswap-V2-style pool referenced by `dexAddress(token)` [2](#0-1) , the admission check and the router's on-chain repay accounting can be satisfied at a manipulated, momentarily favorable exchange rate, letting the attacker extract proposer-lent KAIA (or under-collateralize the repay) at the expense of the block proposer / gasless liquidity providers.

### Finding Description
Gasless swap transactions are lent gas by the block proposer via `GetLendTxGenerator`, and the user is expected to repay that lent amount out of the swap proceeds, per KIP-247 [3](#0-2) . The only pre-flight economic control that gate-keeps a gasless swap into the pool is `checkBalanceForSwap`, which:
1. Confirms `minAmountOut >= amountRepay` (a value declared by the *sender itself* in the transaction, not independently derived from any oracle) [4](#0-3) .
2. Optionally verifies `amountIn >= GetAmountIn(token, minAmountOut)`, where `GetAmountIn` is a live call into the `GaslessSwapRouter` contract, which in turn reads the associated DEX pair's reserves (`dexAddress(token)` / Uniswap V2-style `getReserves()`) [1](#0-0) .
3. Confirms token allowance/balance sufficiency, again against the *current* state [5](#0-4) .

Crucially, both `minAmountOut` and `amountRepay` are attacker-supplied fields decoded straight out of calldata (`decodeSwapTx`) [6](#0-5) , and the only sanity check tying them to a fair market price is the single spot-price snapshot taken via `GetAmountIn`. There is no TWAP, no minimum liquidity/slippage bound, and no protection against the sender manipulating the referenced pool's reserves in a preceding transaction within the same block before their own approve+swap bundle executes. The KIP-247 bundling logic (`ExtractTxBundles`) only orders `[LendTxGenerator, ApproveTx, SwapTx]` atomically for a given sender [7](#0-6) ; it does not prevent an attacker's own unrelated prior transaction (e.g., a large swap that skews the DEX reserves) from being included by the proposer immediately before the bundle, mirroring the "push price, then settle" structure of the Curve LlamaLend donation attack (flash-loan-driven reserve shift immediately followed by a hard-liquidation-equivalent settlement at the skewed price).

Because `amountRepay` is fixed by the sender and only loosely bounded by `minAmountOut` (also sender-supplied) and a single spot check, an attacker who first depresses the token's price against KAIA in the DEX pool (self-trade or flash-loan-funded trade) can submit a gasless swap whose `GetAmountIn`-derived `requiredAmountIn` is calculated against the manipulated (low) price, satisfying admission with a token amount that is cheap relative to fair value, while the KAIA lent by the proposer (`LendAmount`/`RepayAmount`, computed purely from gas price × gas, independent of the DEX price) is repaid using this artificially cheap token flow. The end result is a mismatch between the real economic value transferred to the proposer/protocol (in tokens, at a manipulated rate) and the KAIA value the proposer lent out, functionally draining value from the fee-delegation lender exactly as LlamaLend's donation attack drained value from lenders/borrowers through a manipulated settlement price.

### Impact Explanation
This is Medium-High severity: an unprivileged transaction sender (any account able to submit a legacy transaction and register/target an allowed gasless token/DEX pair) can exploit AMM price manipulation to make the gasless swap subsidy economically unsound, extracting value funded by the block proposer's lent gas (a form of fee-delegation abuse) without requiring any node compromise, consensus fault, or privileged role. This maps to "gasless or auction settlement theft" and "fee or fee-delegation abuse" in the reachable analog classes.

### Likelihood Explanation
Likelihood is Medium: it requires (a) an allowed gasless token whose backing DEX pool has thin liquidity relative to the attacker's capital, and (b) the ability to place a manipulating trade immediately before the attacker's own gasless bundle within the same block — both are realistic for a determined MEV-capable attacker or a proposer colluding with a searcher, similar to the flash-loan preconditions of the original LlamaLend incident. `ShouldCheckSwapAmount`/`ShouldCheckToken` gating suggests these checks are configurable and could be disabled by node config, further increasing exposure in some deployments [8](#0-7) .

### Recommendation
- Do not rely on a single un-pinned spot-price view call (`GetAmountIn`) at tx-pool admission time as an economic safety bound; require the on-chain `GaslessSwapRouter.swapForGas` to independently enforce a minimum acceptable `amountRepay`/`minAmountOut` ratio derived from a manipulation-resistant price source (e.g., TWAP, or bound the allowed slippage relative to a recent block's price).
- Reject or heavily discount gasless-token pools with insufficient liquidity depth, and/or cap the maximum `amountIn`/`minAmountOut` per gasless tx relative to pool reserves to bound the price impact an attacker can induce in-block.
- Re-validate the `GetAmountIn`-derived bound immediately before block inclusion (post-ordering), not only once at initial pool admission, to reduce the manipulation window between admission-time state and actual execution-time state.

### Proof of Concept
1. Attacker identifies a gasless-allowed token whose `dexAddress(token)` pool (Uniswap V2-style) has low reserves relative to attacker capital.
2. In the target block, attacker sends Tx1: a large swap that sells `token` into the pool (or uses a flash loan) to depress the `token`/KAIA price recorded in the pool's reserves.
3. Immediately after (same block, sequenced ahead of other pending gasless bundles), attacker submits their own gasless `ApproveTx` + `SwapTx` bundle with `amountIn`, `minAmountOut`, and `amountRepay` computed to just satisfy `checkBalanceForSwap`'s `amountIn >= GetAmountIn(token, minAmountOut)` check against the now-manipulated reserves [1](#0-0) .
4. The bundle is admitted and included by `ExtractTxBundles` as `[LendTxGenerator, ApproveTx, SwapTx]` [9](#0-8) ; the proposer lends KAIA gas per `lendAmount`/`repayAmount` (calculated solely from gas price × gas, unrelated to the DEX price) [10](#0-9) .
5. `swapForGas` executes against the manipulated reserves, satisfying the attacker's cheaply-derived `minAmountOut`/`amountRepay`, repaying the proposer's lent KAIA using tokens acquired/valued at the manipulated rate.
6. Attacker reverses Tx1's price impact (sell back or let arbitrageurs restore price), realizing a net profit funded by the value gap between the manipulated settlement and fair market price — the value effectively extracted from the fee-delegation lender (block proposer), paralleling the Curve LlamaLend donation-attack profit mechanism.

Note: I could not directly inspect the Solidity source of `GaslessSwapRouter.swapForGas` (only Go bindings were indexed), so the exact on-chain slippage/repay enforcement inside the contract itself could not be fully confirmed; a Devin session with full repository access would be needed to verify whether additional in-contract protections (e.g., TWAP checks) exist beyond what is visible in the bindings and `kaiax/gasless` Go module.

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}

func (g *GaslessModule) ExtractTxBundles(txs []*types.Transaction, prevBundles []*builder.Bundle) []*builder.Bundle {
	// there are only at most two gasless transactions in pending for a sender
	bundles := []*builder.Bundle{}
	approveTxs := map[common.Address]*types.Transaction{}
	targetTxHash := common.Hash{}
	for _, tx := range txs {
		addr, err := types.Sender(g.signer, tx)
		if err != nil {
			continue
		}
		if g.IsApproveTx(tx) {
			approveTxs[addr] = tx
		} else if g.IsSwapTx(tx) && g.IsExecutable(approveTxs[addr], tx) {
			bundleTxs := builder.NewTxOrGenList(g.GetLendTxGenerator(approveTxs[addr], tx))
			if approveTxs[addr] != nil {
				bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(approveTxs[addr]))
			}
			bundleTxs = append(bundleTxs, builder.NewTxOrGenFromTx(tx))

			b := builder.NewBundle(
				bundleTxs,
				targetTxHash,
				false,
			)

			targetTxHash = tx.Hash()

			isConflict := false
			for _, prev := range append(prevBundles, bundles...) {
				if prev.IsConflict(b) {
					isConflict = true
					break
				}
			}
			if isConflict {
				// Gasless transactions will just fail even if they aren't bundled.
				continue
			}
			bundles = append(bundles, b)
		} else {
			targetTxHash = tx.Hash()
		}
	}
	return bundles
}
