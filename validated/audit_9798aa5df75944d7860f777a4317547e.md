### Title
No Two-Step Ownership Transfer for Tokenfactory Denom Admin, Allowing Accidental Permanent Loss of Admin Control - ([File: x/tokenfactory/keeper/msg_server.go])

### Summary
The tokenfactory module's `MsgChangeAdmin` handler transfers admin rights over a denom to a new address in a single, unconfirmed step, mirroring the "No Transfer of Ownership Pattern" described in the reference report for `CrossDomainOwnable3.transferOwnership`.

### Finding Description
`ChangeAdmin` in `x/tokenfactory/keeper/msg_server.go` checks only that the sender is the current admin and that `NewAdmin` differs from the current admin, then immediately overwrites `AuthorityMetadata.Admin` with the caller-supplied address, with no acknowledgement/acceptance step by the new admin: [1](#0-0) 

`ValidateBasic` for `MsgChangeAdmin` only checks that `NewAdmin` parses as a valid bech32 address via `sdk.AccAddressFromBech32`; it does not check that the address corresponds to a key/account with a known/valid public key or that it is otherwise reachable (any syntactically valid bech32 string, including one derived from a typo or an address nobody controls the private key for, passes): [2](#0-1) 

The keeper-level `setAdmin`/`setAuthorityMetadata` helpers likewise perform no additional validation before persisting the new admin: [3](#0-2) 

This is architecturally identical to the reported bug class: a single `onlyOwner`-style function transfers control to an attacker- or user-supplied address in one transaction, with no `acceptOwnership()`/pending-owner step to confirm the new admin is a live, controlled account. The module's own README even documents that admin can be changed to `""` (no admin) or any bech32 string, permanently relinquishing all further admin capability for that denom: [4](#0-3) 

### Impact Explanation
If a denom admin submits `MsgChangeAdmin` with a mistyped/unintended (but bech32-valid) `NewAdmin`, or if a compromised/malicious front-end/dApp tricks the admin into signing such a transaction, all subsequent `Mint`, `Burn`, `ChangeAdmin`, and `SetDenomMetadata`/`UpdateDenom` operations on that denom become permanently inaccessible — matching the "onlyOwner functions... inaccessible" impact in the source report. This is a permanent freezing of privileged token-management functionality for the affected tokenfactory denom, with no recovery path since there is no pending/accept mechanism and no governance override in this module.

### Likelihood Explanation
Likelihood is bounded by user error rather than attacker action — same as the original report, which is why it was rated Medium rather than higher. Any tokenfactory denom creator/admin can trigger this in a single transaction; no special privilege beyond already holding admin authority over their own denom is required.

### Recommendation
Implement a two-step admin transfer for tokenfactory denoms: add a `PendingAdmin` field to `DenomAuthorityMetadata`, have `ChangeAdmin` set the pending admin rather than immediately overwriting `Admin`, and require a new `AcceptAdmin` message signed by the nominated address to finalize the transfer (or, at minimum, require that `NewAdmin` correspond to an account with a registered public key/existing on-chain account before permitting the change).

### Proof of Concept
1. Create a tokenfactory denom as `admin` via `MsgCreateDenom` (admin is auto-set to creator).
2. Submit `MsgChangeAdmin{Sender: admin, Denom: denom, NewAdmin: "<mistyped-but-bech32-valid-address>"}`.
3. `ChangeAdmin` in `x/tokenfactory/keeper/msg_server.go` succeeds because `NewAdmin` passes `ValidateBasic`'s bech32 check and differs from current admin.
4. `AuthorityMetadata.Admin` is now set to an address nobody controls.
5. Any subsequent `MsgMint`, `MsgBurn`, `MsgChangeAdmin`, or `MsgSetDenomMetadata`/`MsgUpdateDenom` for that denom fails with `ErrUnauthorized`, permanently, as demonstrated by the existing test asserting the old admin can no longer act after `ChangeAdmin` succeeds: [5](#0-4)

func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}
	ctx.EventManager().EmitEvents(sdk.Events{
		sdk.NewEvent(
			types.TypeMsgChangeAdmin,
			sdk.NewAttribute(types.AttributeDenom, msg.GetDenom()),
			sdk.NewAttribute(types.AttributeNewAdmin, msg.NewAdmin),
		),
	})

	return &types.MsgChangeAdminResponse{}, nil
}

func (m MsgChangeAdmin) ValidateBasic() error {
	_, err := sdk.AccAddressFromBech32(m.Sender)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid sender address (%s)", err)
	}

	_, err = sdk.AccAddressFromBech32(m.NewAdmin)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid address (%s)", err)
	}

	_, _, err = DeconstructDenom(m.Denom)
	if err != nil {
		return err
	}

	return nil
}
