### Title
OP_RETURN outputs are omitted from fee and weight accounting - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends a caller-controlled zero-value `OP_RETURN` output before calculating transaction weight and fees, but `calculate_weight_vbytes` is called with only `payments`, not the complete `tx_outs`. [1](#0-0)  Consequently, `needed_fee`, the minimum-relay-fee check, the change calculation, and the maximum-weight check all exclude the serialized data output. [2](#0-1) 

### Finding Description
The vulnerable path is externally controlled through `SignableTransaction::new(inputs, payments, change, data, fee_per_vbyte)`. [3](#0-2)  Up to 80 bytes are accepted as `data`, converted into an `OP_RETURN` output, and pushed onto `tx_outs`. [4](#0-3)  The subsequent fee calculation nevertheless reconstructs a transaction containing only `payments` and optional change, leaving the `OP_RETURN` output out of the serialized transaction used for weight and virtual-size accounting. [5](#0-4) 

When change is present, `fee_with_change` is computed from the same incomplete output set and the leftover value is reduced only by that understated fee. [6](#0-5)  The final transaction then contains the additional data output, while `needed_fee` and the weight used for the standardness check still reflect the smaller transaction. [7](#0-6) 

### Impact Explanation
This produces a transaction whose actual virtual size and weight are larger than the values used to calculate its fee. For an 80-byte payload, the omitted output contributes approximately 91 serialized bytes, so the transaction can pay dozens of satoshis less than required for the requested sat/vbyte rate and can fall below the minimum relay rate despite passing `TooLowFee`. [8](#0-7)  The transaction remains valid to sign and broadcast attempts can leave the selected UTXOs committed to a transaction that is not relayed or confirmed, while the signed transaction also carries more change than correct fee accounting would permit. [9](#0-8) 

### Likelihood Explanation
Any caller able to supply non-empty `data` reaches the bug; the payload limit permits enough data to materially affect the transaction's virtual size. [4](#0-3)  The discrepancy occurs deterministically whenever `data.is_some()`, including for an empty payload whose `OP_RETURN` output still occupies serialized bytes. [10](#0-9) 

### Recommendation
Calculate weight, virtual size, minimum fee, change, and maximum standard transaction weight from the complete `tx_outs` vector after appending the data output. Alternatively, extend `calculate_weight_vbytes` to accept the data output explicitly and use the same output set for both fee estimation and construction of the signed transaction. [11](#0-10) 

### Proof of Concept
```text
inputs   = one spendable ReceivedOutput
payments = []
change   = Some(p2tr_script_buf(change_key))
data     = Some([0u8; 80])
fee_rate = 1 sat/vbyte
```

`SignableTransaction::new` creates the `OP_RETURN` output first, but calls:

```rust
Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))
```

without passing the data output. [12](#0-11)  An 80-byte payload adds a serialized output of roughly `8 + 1 + 1 + 1 + 80 = 91` bytes, while `needed_fee` remains based on the transaction without those bytes. [10](#0-9)  The resulting signed transaction therefore has a materially lower effective fee rate than requested, even though `needed_fee()` reports only the understated value. [13](#0-12)

  fn calculate_weight_vbytes(
    inputs: usize,
    payments: &[(ScriptBuf, u64)],
    change: Option<&ScriptBuf>,
  ) -> (u64, u64) {
    // Expand this a full transaction in order to use the bitcoin library's weight function
    let mut tx = Transaction {
      version: Version(2),
      lock_time: LockTime::ZERO,
      input: vec![
        TxIn {
          // This is a fixed size
          // See https://developer.bitcoin.org/reference/transactions.html#raw-transaction-format
          previous_output: OutPoint::default(),
          // This is empty for a Taproot spend
          script_sig: ScriptBuf::new(),
          // This is fixed size, yet we do use Sequence::MAX
          sequence: Sequence::MAX,
          // Our witnesses contains a single 64-byte signature
          witness: Witness::from_slice(&[vec![0; 64]])
        };
        inputs
      ],
      output: payments
        .iter()
        // The payment is a fixed size so we don't have to use it here
        // The script pub key is not of a fixed size and does have to be used here
        .map(|payment| TxOut {
          value: Amount::from_sat(payment.1),
          script_pubkey: payment.0.clone(),
        })
        .collect(),
    };
    if let Some(change) = change {
      // Use a 0 value since we're currently unsure what the change amount will be, and since
      // the value is fixed size (so any value could be used here)
      tx.output.push(TxOut { value: Amount::ZERO, script_pubkey: change.clone() });
    }
