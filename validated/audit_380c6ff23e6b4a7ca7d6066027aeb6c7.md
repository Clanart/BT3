## Finding: Path‑containment check in `resolveWithin` uses an unanchored `startsWith`, allowing sibling‑directory escape

### Title
Sibling-directory path traversal in `resolveWithin()` bypasses repo-root containment check used for deep-link file access - (File: `app/src/lib/path.ts`)

### Summary
`resolveWithin()` is the shared guard GitHub Desktop uses to make sure an attacker-influenced, repo-relative path cannot escape the repository root before the resolved path is handed to filesystem/shell APIs. The final containment check compares the canonicalized target path to the canonicalized root using a plain string `startsWith()`, with no trailing path-separator boundary check [1](#0-0) . This is the classic "prefix without separator" traversal bug: a resolved path such as `/Users/victim/Documents/repo-evil/secret.txt` passes the check against root `/Users/victim/Documents/repo`, because the string `repo-evil` starts with `repo`, even though it is a completely different, sibling directory outside the intended repository.

### Finding Description
`_resolveWithin` computes `resolved` from `resolve(normalizedRoot, normalizedRelative)`, then canonicalizes both the root and the resolved path with `realpath`, and finally does:

```
return realResolved.startsWith(realRoot) ? resolved : null
``` [1](#0-0) 

There is no check that `realResolved` equals `realRoot` or that it starts with `realRoot + path.sep`. Consequently, any path segment sequence (e.g. `../repo-siblingname/...`) that resolves to a directory whose absolute path merely has `realRoot` as a string prefix will be treated as "inside" the repository and returned as a validated path.

This helper is the security boundary used for exactly the kind of attacker-controlled input the task calls out — a link/deep link the user clicks:

- `app/src/ui/dispatcher/dispatcher.ts`'s `openRepositoryFromUrl` handles the `open-repository-from-url` action produced by parsing an `x-github-client://openRepo/...?filepath=...` deep link (`app/src/lib/parse-app-url.ts`), and passes the attacker-supplied `filepath` query parameter straight into `resolveWithin(repository.path, filepath)`, then calls `shell.showItemInFolder(resolved)` on the result [2](#0-1) .
- The same primitive is reused in `app/src/lib/copilot-conflict-context.ts`'s `buildConflictContext`, where merge-conflict file paths (derived from repository/PR content, i.e. attacker-influenced via a crafted branch/PR) are validated with `resolveWithin` before being `stat`'d and `readFile`'d and then sent as prompt content to an external Copilot API [3](#0-2) [4](#0-3) .
- `app-store.ts` also calls `resolveWithin` (not fully inspected here due to tool-call limits).

The existing unit tests only cover `..`/`../..` traversal, null bytes, and symlink escapes [5](#0-4)  — none test the sibling-directory-with-shared-prefix case, so this gap is untested and unguarded.

### Impact Explanation
An attacker who controls a deep link (`x-github-client://openRepo/<repo>?filepath=...`) that a user clicks, or a malicious branch/PR merged in Desktop, can supply a `filepath`/conflict path that traverses to a directory adjacent to the repository whose name happens to share the repository directory name as a prefix (a common real-world occurrence for developers who keep related project variants, e.g. `project` and `project-secrets`, or `app` and `app-internal`, side by side). Depending on the consumer:
- Via `openRepositoryFromUrl`, this reveals/opens an out-of-repo file/folder in the OS file manager (`shell.showItemInFolder`) — file read/disclosure outside the repo boundary.
- Via `buildConflictContext`, out-of-repo file contents could be read and transmitted off-device inside a prompt sent to the Copilot backend — potential credential/content exfiltration if such a sibling directory contains sensitive material.

This matches the requested impact classes (file read outside the repo / exfiltration triggered by a link the user clicks or a crafted repo object), without requiring local/physical access, admin rights, or pre-existing host compromise — only that a similarly-prefixed sibling directory exists on disk, which is a realistic but not guaranteed precondition.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: exploitation depends on the existence of a sibling directory whose absolute path is a string-prefix superset of the target repository path. This is plausible in common developer directory layouts but not universal, so it is an environment-dependent bug rather than a universally reliable exploit. The underlying flaw (missing separator check) is nonetheless a genuine, reproducible defect in the containment logic itself, independent of any race condition or timing assumption — it is deterministic given the right directory naming.

### Recommendation
Fix `_resolveWithin` in `app/src/lib/path.ts` to require an exact match or a boundary-respecting prefix check, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add regression tests for sibling directories that share a name prefix with the root (e.g. root `.../repo`, target `.../repo-evil/file`) for all three variants (`resolveWithin`, `resolveWithinPosix`, `resolveWithinWin32`).

### Proof of Concept
1. Locally, two directories exist side by side: `/Users/victim/Documents/GitHub/my-project` (the Desktop-tracked repo) and `/Users/victim/Documents/GitHub/my-project-secrets` (an unrelated directory containing sensitive files).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/org/my-project?filepath=..%2Fmy-project-secrets%2Fsecret.txt`.
3. Victim clicks the link; Desktop parses it via `parseAppURL` into an `open-repository-from-url` action with `filepath = ../my-project-secrets/secret.txt` [6](#0-5) .
4. `openRepositoryFromUrl` opens `my-project`, then calls `resolveWithin(repository.path, '../my-project-secrets/secret.txt')` [2](#0-1) .
5. Inside `_resolveWithin`, `resolved` becomes `/Users/victim/Documents/GitHub/my-project-secrets/secret.txt`; `realResolved.startsWith(realRoot)` evaluates true because the string `".../my-project-secrets/secret.txt"` starts with `".../my-project"` [1](#0-0) .
6. The check passes, and `shell.showItemInFolder(resolved)` reveals `secret.txt`, a file entirely outside `my-project`, confirming the containment bypass.
