Based on my investigation, the strongest local analog to the `mergeTranches()`/`refinancePartial()` missing-`nonReentrant` bug class is a **reentrancy-guard gap between the mainline EVM `IntentGatewayV2` and its Tron fork**.

### Title
Tron fork of `IntentGatewayV2` lacks `nonReentrant` protection that was added to the mainline contract after a confirmed reentrancy finding - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2.fillOrder()`/`cancelOrder()` were hardened against a documented reentrancy class (self-fill re-entering during the beneficiary ETH transfer to steal escrow/fees) via a `nonReentrant` modifier plus a checks-effects-interactions (CEI) fix that sets `_filled[commitment] = msg.sender` before any external call. [1](#0-0) [2](#0-1) 

The regression test suite explicitly documents the pre-fix vulnerability: a malicious `beneficiary` contract re-enters `fillOrder` from its `receive()` callback during the solver's ETH transfer, self-filling with a zero-cost output to drain escrowed fees/tokens — exactly the same primitive as the external report's `mergeTranches()` reentrancy (an external callback reachable mid-state-mutation, before the "loan"/"order" is marked processed). [3](#0-2) [4](#0-3) 

### Finding Description
A repository-wide search for `nonReentrant` shows it is only present in `evm/src/apps/IntentGatewayV2.sol` (6 occurrences) and nowhere in the Tron variant `evm/tron/contracts/apps/IntentGatewayV2.sol` (0 occurrences). [5](#0-4) 

The Tron `IntentGatewayV2` is a near-identical fork (same struct/function names — `placeOrder`, `fillOrder`, `withdraw`, `onAccept`, `_instances`, `_orders`, `_filled`) of the mainline contract, sharing the exact code shape that previously enabled the fee/escrow-theft reentrancy on the mainline chain before it was patched. Its internal `withdraw()` helper (used for cross-chain redeem/refund) does perform `_filled[commitment] = beneficiary` before the ERC20/native transfer loop, matching mainline's fixed CEI ordering for that one code path: [6](#0-5) 

However, the same fork does not carry the `nonReentrant` modifier on the public entrypoints (`fillOrder`, `cancelOrder`) that mainline added as defense-in-depth, and I was unable to confirm from the retrieved code whether the fork's same-chain fill path (`_fillSameChain`-equivalent) sets `_filled[commitment]` before its native-token transfer to the beneficiary — the exact ordering that was the root cause of the original, now-fixed bug on mainline. Given the file lacks the guard modifier entirely, any ordering mistake in the fill/cancel path (even a partial CEI application, as mainline itself had prior to its fix) is not backstopped by `nonReentrant`.

### Impact Explanation
If the Tron fork's fill/cancel/withdraw sequencing has the same pre-fix ordering issue mainline had, a malicious `beneficiary` (attacker-controlled contract set as `order.output.beneficiary`) can re-enter `fillOrder` during the native-token transfer to:
- Self-fill a second output at zero net cost while the original order's escrow (input tokens, transaction fees) is still unreleased, then complete the original outer call and drain both funds paths — an unauthorized fund loss matching "stealing or loss of funds" / "logic attacks" in the bounty scope.

### Likelihood Explanation
Medium-high. The attack requires only an unprivileged solver acting as their own "malicious beneficiary" contract, exactly as demonstrated by the mainline `ReentrantBeneficiary` PoC — no relayer, prover, or admin compromise needed. The only gating factor is whether the Tron file's fill path independently reproduces the CEI fix without the `nonReentrant` modifier as a backstop, which I could not fully verify from the fetched code (fillOrder/`_fillSameChain` body in the Tron file was not fully retrieved before the tool budget was exhausted).

### Recommendation
Port the `nonReentrant` modifier (and confirm the CEI ordering — `_filled[commitment]` set before any external native/ERC20 transfer) from `evm/src/apps/IntentGatewayV2.sol` / `IntrinsicIntents.sol` / `ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `fillOrder`, `cancelOrder`, and any internal fill/withdraw helpers, and add an equivalent reentrancy regression test (mirroring `IntrinsicIntentsReentrancyTest.sol`) for the Tron build target.

### Proof of Concept
Not independently reproducible from the available index — the Tron file's `fillOrder`/`_fillSameChain`-equivalent body could not be fully retrieved to confirm the exact vulnerable ordering before the tool-call budget ran out. The mainline PoC (`ReentrantBeneficiary` re-entering via `receive()` during the ETH payout, self-filling a second output at zero cost) is a directly transferable template once that ordering is confirmed in the Tron contract. [7](#0-6) 

**Caveat:** This finding is based on the confirmed absence of the `nonReentrant` guard in the Tron fork (verified via `grep_search`) and the structural similarity to the pre-fix mainline vulnerability, but I could not fully view the Tron fork's `fillOrder`/`_fillSameChain` function bodies within the available tool budget to conclusively prove the same unordered state-mutation exists there. A Devin session with full file access should verify this before treating it as confirmed-exploitable.
