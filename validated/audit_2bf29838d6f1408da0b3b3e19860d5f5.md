## Title
Divergent conflict-marker parsers cause Copilot to silently splice merge-conflict resolutions into the wrong location, corrupting committed file content - (File: `app/src/lib/copilot-conflict-context.ts` / `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot merge-conflict-resolution feature reads a conflicted file **twice**, with two independently written parsers that are assumed to agree on where each `<<<<<<< / ======= / >>>>>>>` block starts and ends:

1. `extractConflictHunks()` in `app/src/lib/copilot-conflict-context.ts` (lines 179–279) parses the raw file to build the hunks sent to the model and the "expected hunk count" used for validation.
2. `reassembleResolvedFile()` in `app/src/lib/copilot-conflict-resolution.ts` (lines 549–599) independently re-parses the *same raw file* to decide where to splice the model's per-hunk resolutions back in.

Just like the reported `wrap`/`unwrap` bug assumes two independently-sourced values (`originToken` decimals and `WrappedToken` decimals) are equal without checking, this code assumes the two conflict-block parsers produce equal, corresponding boundaries without ever validating that they actually do. `validateResolutionPaths()` (lines 473–521) only checks the *hunk count* against `extractConflictHunks`'s count — never against `reassembleResolvedFile`'s independent parse — so a mismatch between the two parsers is invisible.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts:179-279`) collects "ours" content with a loop that only breaks on a base marker (`|||||||`) or separator (`=======`): [1](#0-0) 
It never checks for the theirs marker (`>>>>>>>`) while collecting "ours" lines, so a malformed or attacker-crafted marker sequence causes it to consume unrelated downstream content — including subsequent real conflict blocks — into a single hunk's `oursContent`/`theirsContent`.

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts:549-599`) instead performs its own independent lookahead, and specifically requires seeing a separator *before* the first closing marker or it treats the block as malformed and leaves it untouched: [2](#0-1) 

Because these two parsers use different rules for what counts as a valid/boundary conflict block, a file containing conflict-marker-like text that is not a "clean" git-generated conflict (e.g. a source file, tutorial, fixture, or test file in the *attacker's branch* that legitimately contains literal `<<<<<<<`/`=======`/`>>>>>>>`-shaped lines as content, or a merge that produces an edge-case marker layout) can cause the two parsers to disagree on:
- how many real hunks exist, and/or
- where each hunk's boundaries are.

`validateResolutionPaths` only asserts that the *count* returned by the model matches `extractConflictHunks`'s count: [3](#0-2) 
It never re-validates against `reassembleResolvedFile`'s independent boundary computation. `reassembleResolvedFile` then blindly splices the model's `hunkResolutions[hunkIndex]` into whatever block *it* thinks is hunk `hunkIndex`, matched purely "by order, not by line number" as the function's own doc comment states: [4](#0-3) 

The result: the model's resolution for logical conflict N (as it understood the prompt built from `extractConflictHunks`) gets written into a different block than intended by `reassembleResolvedFile`'s parse, or a "fake" marker-like block is left untouched while a real block absorbs content meant for another — with no error, no validation failure, and no user-visible warning.

### Impact Explanation
The attacker only needs to control the content of a branch/PR the victim merges, rebases, or cherry-picks with (a normal, unprivileged repository interaction). If that content contains lines that look like conflict markers (plausible in tutorials, test fixtures, generated diffs stored as text, or minified/templated files), Copilot's conflict resolution can silently misapply the model's resolved content to the wrong region of the file. This is a "silent corruption of what the user commits or pushes": the user reviews a file they believe was correctly resolved by Copilot (with conflict markers gone, as validated by `CopilotValidationError` checks that only look for `<{7}` /`={7}` patterns in the *resolved content itself*), then commits and pushes code that actually contains swapped, duplicated, or dropped logic from the wrong hunk.

### Likelihood Explanation
Requires no special privileges — only that the victim uses the Copilot conflict-resolution feature (an opt-in but standard workflow) on a merge/rebase/cherry-pick against attacker-influenced content. Conflict-marker-like text in real files (documentation about git, `.patch`/`.diff` fixtures, generated diff snapshots in tests) is a realistic, non-contrived scenario, making this more likely than a purely synthetic edge case, though it does require a specific marker-layout condition to trigger the divergence between the two parsers.

### Recommendation
1. Use a single, shared parsing routine for identifying conflict-block boundaries, consumed by both `extractConflictHunks` (for prompting/validation) and `reassembleResolvedFile` (for splicing), so the two paths cannot disagree.
2. Have `reassembleResolvedFile` verify that the number of well-formed blocks it identifies in `rawContent` exactly matches `hunkResolutions.length`, and throw a `CopilotValidationError` (surfacing the file as skipped/manual) rather than silently proceeding when they diverge.
3. Consider validating a content-hash/fingerprint of each block's `oursContent`/`theirsContent` sent to the model against what `reassembleResolvedFile` finds at splice time, to guarantee 1:1 correspondence rather than assuming positional alignment.

### Proof of Concept
1. Attacker prepares a branch whose file (e.g. `README.md` or a test fixture) contains, as ordinary tracked content, a malformed marker-like sequence without a proper `=======` separator immediately followed by a `>>>>>>>`-shaped line, e.g.:
   ```
   <<<<<<< example-block
   some example text
   >>>>>>> example-end
   ```
2. Victim merges this branch with another branch that creates a **real** conflict later in the same file.
3. `extractConflictHunks` (context.ts) begins collecting "ours" content at the fake `<<<<<<<` and — because it never checks for a theirs-marker while doing so — keeps consuming lines (including the fake `>>>>>>>` and all subsequent unrelated file content) until it reaches the real `=======` from the actual conflict further down, producing a single hunk whose `oursContent` bundles the fake block plus genuine surrounding content, and `theirsContent` taken from the real conflict's theirs side.
4. Copilot receives and resolves this bogus "Conflict 1 of 1" based on the merged/garbled content.
5. `reassembleResolvedFile` independently re-parses the same raw file: at the fake `<<<<<<<`, its lookahead hits the fake `>>>>>>>` before any `=======`, so `hasSeparator` is `false` and the block is treated as malformed content and copied through unchanged; it only recognizes the later, real `<<<<<<<...=======...>>>>>>>` as hunk `0` and splices the model's resolution there.
6. The model's resolution — generated against the wrong (merged/garbled) conflict boundaries — is written into the real conflict location, producing an incorrect final file that the user commits and pushes without any warning, since `reassembleResolvedFile`'s only conflict-marker-content check runs against the resolved string itself, not against a cross-parser boundary check.
