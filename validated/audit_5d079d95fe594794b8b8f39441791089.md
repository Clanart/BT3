## Analysis

I identified a valid analog to the "shelter mechanism" bug class in `MasterMagpie.sol`'s `emergencyWithdraw` function.

### Title
Users Permanently Lose Accrued MGP and Bonus Rewards When Calling `emergencyWithdraw` Due to Skipped Checkpointing - (File: `rewards/MasterMagpie.sol`)

### Summary
`MasterMagpie.emergencyWithdraw()` lets any user withdraw their `available` staking balance while the contract is paused, but unlike the normal `_withdraw()` path, it skips the reward-checkpointing calls (`_harvestMGP` and `_harvestBaseRewarder`). This causes the user's accrued-but-unclaimed MGP emissions and bonus rewards (from the pool's `BaseRewardPool`) to be permanently lost.

### Finding Description
In the standard withdrawal path, `_harvestAndUnstake` first checkpoints both MGP rewards and the pool's bonus rewarder before mutating `user.amount`/`user.available`: [1](#0-0) 

`emergencyWithdraw`, however, directly zeroes `user.available`, reduces `user.amount`, and recomputes `user.rewardDebt` from the new, smaller balance — without calling `_harvestMGP` or `_harvestBaseRewarder` first: [2](#0-1) 

Because `user.rewardDebt` is overwritten using the post-withdrawal `user.amount`, the pending MGP that had accrued against the pre-withdrawal balance (`user.amount(old) * accMGPPerShare / 1e12 - user.rewardDebt(old)`) is never moved into `unClaimedMgp` and is simply erased — it is not recoverable via `multiclaim` afterward: [3](#0-2) 

The same happens for any bonus reward tokens tracked in the pool's `BaseRewardPool`. `BaseRewardPool.balanceOf` reads the user's live balance directly from `MasterMagpie.stakingInfo`, and `earned()` multiplies that balance by the delta since the user's last checkpoint (`userRewardPerTokenPaid`): [4](#0-3) 

Since `_harvestBaseRewarder` (which calls `updateFor`/`_updateFor` to snapshot `userRewards` and `userRewardPerTokenPaid`) is skipped, and the user's on-chain balance instantly drops via `emergencyWithdraw`, any subsequent `earned()` calculation for the period between the last checkpoint and the emergency withdrawal uses the new, reduced balance instead of the actual (larger) balance that was staked during that period: [5](#0-4) 

This under-computes the reward permanently — the difference is not recoverable by any other function, exactly mirroring the original report's root cause: assets/balances are removed from the accounting system while the reward index update ("checkpoint") that should accompany that removal is skipped, permanently losing unclaimed yield.

### Impact Explanation
Any user who calls `emergencyWithdraw` (available to any wallet once the contract is paused) permanently loses:
1. Pending MGP emissions accrued since their last deposit/withdraw/claim.
2. Pending bonus reward tokens tracked by the pool's `BaseRewardPool`, proportional to the amount withdrawn.

This is a permanent, unrecoverable loss of unclaimed yield for ordinary users, matching the "theft or permanent freezing of unclaimed yield" acceptance criterion.

### Likelihood Explanation
`emergencyWithdraw` is an unprivileged, user-callable function (`external whenPaused`, no `onlyOwner`/role check) — any user with a staked, available balance can trigger it once the protocol is paused (a normal circuit-breaker state, not a malicious-admin action). Any user who has accrued rewards and calls this function during a pause will lose them; this is deterministic, not just theoretical.

### Recommendation
In `emergencyWithdraw`, call `_harvestMGP(_stakingToken, msg.sender)` and `_harvestBaseRewarder(_stakingToken, msg.sender)` (and `updatePool(_stakingToken)`) before mutating `user.available`/`user.amount`/`user.rewardDebt`, exactly as done in `_harvestAndUnstake`, so any pending MGP is moved to `unClaimedMgp` and the rewarder's `userRewards`/`userRewardPerTokenPaid` are checkpointed prior to reducing the user's on-chain balance.

### Proof of Concept
1. User deposits LP tokens into a pool via `deposit()`, and time passes while `accMGPPerShare` and the pool's `BaseRewardPool.rewardPerTokenStored` increase. [6](#0-5) 
2. Admin pauses `MasterMagpie` (`pause()`), an ordinary emergency circuit breaker. [7](#0-6) 
3. User calls `emergencyWithdraw(_stakingToken)`. `user.rewardDebt` is recomputed from the new (zeroed) `user.available`/reduced `user.amount` without first harvesting MGP or updating the `BaseRewardPool` checkpoint. [2](#0-1) 
4. Any subsequent call to `multiclaim`/`getReward` for that user returns less than the rewards actually accrued prior to step 3 — the difference is permanently lost, since `unClaimedMgp` was never credited and `userRewardPerTokenPaid` was never advanced against the pre-withdrawal balance.

    function _harvestAndUnstake(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
        updatePool(_stakingToken);

        UserInfo storage user = userInfo[_stakingToken][_account];

        if (!_isVlMgp && user.available < _amount)
            revert WithdrawAmountExceedsStaked();
        else if(user.amount < _amount && _isVlMgp)
            revert UnlockAmountExceedsLocked();
        
        _harvestMGP(_stakingToken, _account);
        _harvestBaseRewarder(_stakingToken, _account);

        user.amount = user.amount - _amount;
        
        if(!_isVlMgp)
            user.available = user.available - _amount;
        user.rewardDebt = (user.amount * tokenToPoolInfo[_stakingToken].accMGPPerShare) / 1e12;
    }
