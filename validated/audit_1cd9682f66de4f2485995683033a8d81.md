### Title
`SignableTransaction::new` omits the OP_RETURN data output from weight/fee accounting, making `needed_fee` and the change calculation stale — (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to the Blueberry report — where `bank.totalLend` is incremented in `lend()`, decremented in `withdrawLend()`, but left stale in `liquidate()` — `SignableTransaction::new` in bitcoin-serai maintains a derived accounting value (`needed_fee` / transaction weight) that is computed from a subset of the transaction's outputs. When the caller supplies `data`, an `OP_RETURN` output is pushed onto `tx_outs` at `send.rs:194-202`, but the weight/vbyte/fee computation at `send.rs:204` (`calculate_weight_vbytes(tx_ins.len(), payments, None)`) and the change-aware recomputation at `send.rs:225-226` (`calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`) only ever model `payments` plus optional change. The data output is never reflected in `vbytes`, `needed_fee`, the `NotEnoughFunds` check at `send.rs:215`, or the change `value` at `send.rs:228-230`, so every accounting figure is stale by up to ~80+ bytes (~20+ weight units ≈ up to `fee_per_vbyte * ~95` satoshis) once a data output exists.

### Finding Description
`Transaction` construction pushes the `OP_RETURN` output before the fee math runs (`send.rs:194-204`), so the actual signed transaction is strictly larger than the transaction the fee was priced for. Two consequences:

1. **Effective fee rate is lower than requested.** `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) prices `vbytes` of a transaction *without* the data output. Since the change output is set to `input_sat - payment_sat - fee_with_change` (`send.rs:228-230`), the *actual* fee paid equals exactly `fee_with_change`, which is correct for the tx without data but underpriced for the tx with data. The real fee rate is `needed_fee / actual_vsize < fee_per_vbyte`.
2. **The minimum-relay check is evaluated against the wrong vsize.** `send.rs:211` checks `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the data-less `vbytes`. A `fee_per_vbyte` that just barely satisfies the minimum for the smaller transaction will fail it for the real (larger) transaction, producing a signed transaction that standard nodes will not relay.
3. **`NotEnoughFunds` is too permissive.** `send.rs:215` admits inputs sufficient only for the data-less fee; the change branch can still emit change whose implied fee is below the true required amount.

This is a pure stale-accounting bug: one mutation path (`data` push) does not update the aggregate (`weight`/`vbytes`/`needed_fee`) that the other paths (`payments`, `change`) correctly maintain — exactly the `liquidate()`/`totalLend` pattern.

### Impact Explanation
An unprivileged party reaching this code is the external depositor: in `processor/src/networks/bitcoin.rs`, forwarded payments carry origin/return metadata, and `SignableTransaction::new` accepts up to 80 bytes of caller-influenced `data` (`send.rs:171-173`). A deposit triggering a forwarding plan with a data payload causes the coordinator/multisig to produce and sign a transaction whose actual fee rate is below both the intended rate and potentially below `DEFAULT_MIN_RELAY_TX_FEE`. The signed transaction then fails to propagate/confirm: the output is reported as forwarded but the funds are effectively stuck (an unconfirmable plan), and the input must be re-planned at a higher fee — the deposit is "reported received" while the resulting spend is non-viable as signed. This is a reachable, attacker-influenced underpayment of fees degrading to a liveness/funds-availability fault (Medium).

### Likelihood Explanation
Triggering requires only that a signed transaction include a `data` payload — a normal code path whenever an `InInstruction` with arbitrary data is forwarded. The miscalculation is deterministic (not a race); the fee shortfall scales with the data length, up to ~95 vbytes of unpriced weight for the 80-byte maximum.

### Recommendation
Include the data `TxOut` in the transaction template used by `calculate_weight_vbytes` — i.e., change its signature to take the already-built `tx_outs` (payments + OP_RETURN + optional change) rather than reconstructing outputs from `payments` alone, and recompute `needed_fee` whenever outputs change. Alternatively, pass `data` length into the weight estimator so both the `NotEnoughFunds` check, the minimum-fee check, and the change subtraction account for the OP_RETURN output.
