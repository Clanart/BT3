### Title
Merge operation resolves branch by mutable ref name instead of the SHA the user reviewed, allowing a stale/attacker-updated merge preview to silently pull in different content - (File: `app/src/lib/git/merge.ts`)

### Summary
The report's core flaw is a TOCTOU/front-running pattern: a value is validated at time T1 (a percentage/rate tied to a specific state snapshot), but the state-changing action executes later against whatever the *current* mutable state is at T2, which an adversary who controls that mutable state can change in between. Desktop's merge flow has the same structural flaw: the "is this merge clean, how many commits, any conflicts" preview is computed against a pinned commit SHA, but the actual `git merge` invocation is executed against the branch's mutable ref name, which can point to a different commit by the time the user confirms.

### Finding Description
`determineMergeability` computes the merge-tree result by pinning both sides to explicit SHAs captured at preview time: [1](#0-0) 

The `MergeChooseBranchDialog` calls this preview asynchronously and stores the result in component state, gated only by a staleness check comparing `selectedBranch.tip.sha` to the branch passed into `updateStatus` — i.e. it only protects against the *user* picking a different branch in the dialog, not against the underlying ref being updated externally while the dialog stays open: [2](#0-1) 

When the user clicks "Merge", the dialog passes the `selectedBranch` object (captured at preview time) straight through to `dispatcher.mergeBranch`: [3](#0-2) 

This flows into `AppStore._mergeBranch`, which calls `gitStore.merge(sourceBranch, ...)`: [4](#0-3) 

`GitStore.merge` forwards `branch.name` (a ref name, e.g. `github-desktop-fork-owner/feature`) to the low-level `merge()` function: [5](#0-4) 

The low-level `merge()` builds `git merge <branch-name>`, which Git resolves to whatever commit the ref currently points to at execution time — not the SHA that was used for the preview: [6](#0-5) 

Between the preview and the click, the local tracking ref for that branch can silently move forward without any explicit user action, because Desktop automatically fast-forwards local branch refs to match their upstream after **every** fetch, pull, and push, via `fastForwardBranches`: [7](#0-6) 
This is invoked from `performFetch`, `performPull`, and `performPush`: [8](#0-7) 
Desktop also runs background fetches automatically on a timer via `app/src/lib/stores/helpers/background-fetcher.ts`, so no explicit user interaction is required for the ref to move while the merge dialog is open.

The remote branch being merged is commonly a collaborator's or a fork owner's branch (this is the same "compare"/merge UI used for merging PR/fork branches into the current branch, per `merge-call-to-action-with-conflicts.tsx` and `open-pull-request` UI), so its tip is attacker-controlled content, analogous to Bob controlling his stake in the original report.

Contrast this with the existing, correct guard for push: pushes use `--force-with-lease`, which explicitly fails if the remote-tracking ref has moved since it was last observed, preventing exactly this class of staleness: [9](#0-8) 
No equivalent SHA-pinning or "ref changed under you" guard exists for the merge path.

### Impact Explanation
A user reviews "Merge — Clean, 3 commits, no conflicts" for a specific reviewed SHA. If the collaborator/fork owner (who fully controls their own branch, exactly like Bob controls his own stake) pushes new/different commits to that branch before the user clicks "Merge", and Desktop performs any background/foreground fetch/pull/push in between (which auto-fast-forwards the tracking ref), the eventual `git merge <branch-name>` merges the **new**, unreviewed tip — not the one whose diff and conflict-status the user inspected and approved. This is a silent corruption of what gets merged into (and subsequently committed/pushed from) the user's branch, matching the "silent corruption of what the user commits or pushes" impact category. It requires no local access, no credentials, and no unnatural user steps beyond normal review-then-click usage of the Merge dialog.

### Likelihood Explanation
Moderate. It requires: (1) the user to open the merge dialog and review a specific branch's mergeability/diff, (2) some time gap between review and confirming, during which (3) a background fetch/pull/push occurs (which is common — Desktop fetches automatically on an interval and after most operations) and (4) the attacker (a collaborator or PR/fork author with push rights to the source branch) pushes new content to that branch in that window. All of these are realistic, ordinary usage conditions rather than contrived attacker positioning — no mempool-style timing precision is even needed, since Desktop's periodic background fetch widens the window considerably compared to the single-transaction race in the original report.

### Recommendation
Pin the merge operation to the exact SHA that was used to compute the mergeability preview, and re-validate at merge time that the branch's current tip still matches the reviewed SHA (analogous to `--force-with-lease` for push):
- Pass `sourceBranch.tip.sha` (not `sourceBranch.name`) into `merge()`, or add an option to `git merge` /`git merge-tree` that operates against the specific SHA.
- Before executing the merge, re-check the branch's current tip against the SHA used to produce the mergeability preview shown to the user; if it has changed, force the user to re-review before proceeding (mirroring `MergeChooseBranchDialog`'s own staleness check, but applied at confirm time, not just at selection time).

### Proof of Concept
1. User A and User B collaborate; User B has push access to `feature-branch`.
2. User A opens "Merge into current branch" and selects `feature-branch`. Desktop calls `determineMergeability(repository, currentBranch, featureBranch)` pinned to `featureBranch.tip.sha = SHA1`, showing "Clean, 2 commits, no conflicts." [1](#0-0) 
3. Before User A clicks "Merge", User B pushes a new commit (`SHA2`) to `feature-branch`, e.g. containing different/malicious content.
4. Desktop's periodic background fetch or any manual fetch/pull/push runs `fastForwardBranches`, moving the local tracking ref for `feature-branch` from `SHA1` to `SHA2`. [7](#0-6) 
5. User A clicks "Merge." `MergeChooseBranchDialog.start()` still holds the stale `selectedBranch` object from step 2 and calls `dispatcher.mergeBranch(repository, selectedBranch, mergeStatus, ...)`. [3](#0-2) 
6. `gitStore.merge()` executes `git merge feature-branch`, which Git resolves against the ref's *current* tip (`SHA2`), silently merging content User A never reviewed. [10](#0-9)

```typescript
  repository: Repository,

      ours.tip.sha,

    'determineMergeability',
```

```typescript
  private updateStatus = async (branch: Branch) => {
    const { currentBranch, repository } = this.props

    const mergeStatus = await determineMergeability(
      repository,
      currentBranch,
      branch
    ).catch<MergeTreeResult>(e => {
      log.error('Failed determining mergeability', e)
      return { kind: ComputedAction.Clean }
    })

    // The user has selected a different branch since we started or the branch
    // has changed, so don't update the preview with stale data.
    //
    // We don't have to check if the state changed from underneath us if we
    // loaded the status from cache, because that means we never kicked off an
    // async operation.
    if (this.state.selectedBranch?.tip.sha !== branch.tip.sha) {
      return
    }

    // Can't go forward if the merge status is invalid, no need to check commit count
    if (mergeStatus.kind === ComputedAction.Invalid) {
      this.setState({ mergeStatus })
      return
    }

    // Commit count is used in the UI output as well as determining whether the
    // submit button is enabled
    const range = revSymmetricDifference('', branch.name)
    const aheadBehind = await getAheadBehind(repository, range)
    const commitCount = aheadBehind ? aheadBehind.behind : 0

    if (this.state.selectedBranch.tip.sha !== branch.tip.sha) {
      return
    }

    this.setState({ commitCount, mergeStatus })
  }
```

```typescript
/** Merge the named branch into the current branch. */
export async function merge(
  repository: Repository,
  branch: string,
  options?: MergeOptions
): Promise<MergeResult> {
  const onTerminalOutputAvailable = options?.onTerminalOutputAvailable
    ? createMultiOperationTerminalOutputCallback(
        options?.onTerminalOutputAvailable
      )
    : undefined

  const args = ['merge']

  if (options?.squash) {
    args.push('--squash')
  }

  if (options?.noVerify) {
    args.push('--no-verify')
  }

  args.push(branch)

  const { exitCode, stdout } = await git(args, repository.path, 'merge', {
    expectedErrors: new Set([GitError.MergeConflicts]),
    interceptHooks: ['pre-merge-commit', 'post-merge', 'commit-msg'],
    onHookProgress: options?.onHookProgress,
    onHookFailure: options?.onHookFailure,
    onTerminalOutputAvailable,
  })
```
