### Title
mWOMSVBaseRewarder never applies mWomSV's forfeiture discount, letting unlocking users claim full bonus rewards with zero forfeit - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`mWomSV.sol` implements `getRewardablePercentWAD` to compute a time/lock-weighted percentage that should discount rewards for users who have unlocked or are in cooldown, mirroring the pattern used by `vlMGP`/`vlMGPBaseRewarder`. However `mWOMSVBaseRewarder._calExpireForfeit` never calls this function; it sets `rewardableAmount = _amount` unconditionally, so `forfeitAmount` is always `0` regardless of the user's lock/cooldown status.

### Finding Description
In `rewards/vlMGPBaseRewarder.sol`, `_calExpireForfeit` correctly queries `vlMGP.getRewardablePercentWAD(_account)` and scales the reward by that percent before paying out, forfeiting the remainder into the reward pool via `_queueNewRewardsWithoutTransfer` [2](#0-1) . The equivalent function in `rewards/mWOMSVBaseRewarder.sol` — `_calExpireForfeit` — has an identical signature and even keeps the same "ignore <0.1%" gas-saving logic, but its `rewardableAmount` is set directly to `_amount` without ever calling `mWOMSV.getRewardablePercentWAD(_account)` [1](#0-0) . As a result `forfeitAmount` is mathematically always `0 = _amount - _amount`.

The reachable path is: `mWomSV.startUnlock`/`unlock` (marks part or all of a user's mWomSV as cooling down or withdrawn, which is exactly the state `getRewardablePercentWAD` is designed to penalize) [4](#0-3)  → `MasterMagpie.multiclaim`/`getReward` → `mWOMSVBaseRewarder.getReward` → `_sendReward` → `_calExpireForfeit` [5](#0-4) . Because `_calExpireForfeit` always returns `0`, `_sendReward` always sends the user's full `userRewards` balance and the `if(forfeitAmount > 0) _queueNewRewardsWithoutTransfer(...)` branch is dead code, meaning discounted yield is never redistributed back to remaining lockers. `mWOMSVBaseRewarder.balanceOf` continues to read the user's full staked amount from `MasterMagpie.stakingInfo` (which still includes cooldown amounts, per `mWomSV.balanceOf` = locked + in-cooldown) [6](#0-5) , so a user in cooldown keeps accruing and can withdraw 100% of bonus rewards with no discount, unlike the intended design mirrored in the `vlMGP` rewarder.

### Impact Explanation
This is a permanent loss/misallocation of unclaimed yield: rewards that the protocol's own design (as evidenced by the parallel, correctly-wired `vlMGPBaseRewarder`/`VLMGP` implementation) intends to forfeit from unlocking/cooling-down users and redistribute to remaining lockers instead flow entirely to the unlocking user. Since `_queueNewRewardsWithoutTransfer` is never invoked (forfeitAmount is always 0), the redistribution mechanism is permanently broken and the "should-be-forfeited" yield is transferred out of the pool to the claiming user rather than returning to remaining stakers — matching the "theft or permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
No special privileges are required — any mWomSV holder can call `startUnlock`/`unlock` and then claim rewards through `MasterMagpie`. This is fully deterministic and repeatable by any holder for any bonus reward token registered on the rewarder, with no capital requirement beyond normal locking/unlocking of mWOM.

### Recommendation
Modify `mWOMSVBaseRewarder._calExpireForfeit` to compute `rewardableAmount = _amount * mWOMSV.getRewardablePercentWAD(_account) / 1e18`, consistent with `vlMGPBaseRewarder._calExpireForfeit`, so that forfeited yield is actually computed and re-queued via `_queueNewRewardsWithoutTransfer`.

### Proof of Concept
Foundry test outline:
1. Deploy `mWomSV`, `mWOMSVBaseRewarder`, and `MasterMagpie` with two users, A and B, each locking equal mWOM amounts.
2. Queue bonus rewards via `queueNewRewards` so `rewardPerTokenStored` increases.
3. User A calls `mWomSV.startUnlock(fullAmount)` (entering cooldown, which per `getRewardablePercentWAD` should reduce A's rewardable percent below 100%).
4. Both A and B call `MasterMagpie.multiclaim`/`getReward` on the mWomSV rewarder.
5. Assert `earned`/received bonus reward for A equals B's (i.e., no discount applied despite A being in cooldown), by comparing `_calExpireForfeit(A, amount)` returning `0` via `calExpireForfeit` view function.
6. Assert `rewards[token].queuedRewards` remains `0` after A's claim, confirming `_queueNewRewardsWithoutTransfer` was never invoked, contrasting with the expected discount computed by `mWomSV.getRewardablePercentWAD(A)` (which would be `< 1e18`).

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
