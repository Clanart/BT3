### Title
`tx_sender_try_to_send_txs.txid` Unique Constraint Absent from `schema.sql`, Only Added by Migration `0003` — `save_tx` `ON CONFLICT (txid)` Fails Without It, Causing Complete Tx-Sender Liveness Failure — (File: `core/src/database/schema.sql`, `crates/clementine-tx-sender/src/db/tx_sender.rs`)

---

### Summary

`schema.sql` creates `tx_sender_try_to_send_txs` without a `UNIQUE (txid)` constraint. That constraint is only added by migration `0003_tx_sender_and_lcp_update.up.sql`. The `save_tx` function issues `ON CONFLICT (txid) DO UPDATE …`, which PostgreSQL requires a unique constraint or index to resolve. If the migration has not been applied, every call to `save_tx` raises a hard PostgreSQL error ("there is no unique or exclusion constraint matching the ON CONFLICT specification"), making it impossible to enqueue any bridge transaction — kickoffs, challenges, reimburse, payout, assert, etc.

---

### Finding Description

**Schema definition (no unique constraint on `txid`):** [1](#0-0) 

The `txid` column is declared as plain `bytea` with no uniqueness guarantee.

**Constraint added only in migration 0003:** [2](#0-1) 

**`save_tx` unconditionally uses `ON CONFLICT (txid)`:** [3](#0-2) 

PostgreSQL resolves `ON CONFLICT (column)` by looking for a unique constraint or unique index on that column at query-parse time. If neither exists, the statement is rejected with a hard error before any row is touched.

**Every bridge transaction flows through `insert_try_to_send` → `save_tx`:** [4](#0-3) 

`insert_try_to_send` is the single entry point used by the operator for kickoff, reimburse, challenge, assert, payout, and all other bridge-critical transactions. [5](#0-4) 

**Startup applies schema then migrations — but the two are divergent:** [6](#0-5) 

`schema.sql` is applied first; migrations follow. If migration 0003 is skipped, rolled back, or the database is bootstrapped from `schema.sql` alone (e.g., in a staging or disaster-recovery scenario), the constraint is absent and `save_tx` fails on every call.

**Secondary issue — non-atomic check-then-insert without the constraint:** [7](#0-6) 

`check_if_tx_exists_on_txsender` and `save_tx` run in the same `dbtx`, but two concurrent callers each hold their own transaction. Without the unique constraint, both can pass the existence check and both inserts succeed, creating duplicate rows for the same txid. The tx-sender loop then processes both rows, creating duplicate fee-payer UTXOs and potentially double-bumping fees for the same transaction.

---

### Impact Explanation

If migration 0003 has not been applied:

- `save_tx` raises a PostgreSQL error on every invocation.
- `insert_try_to_send` propagates the error to every caller.
- No bridge transaction — kickoff, challenge, reimburse, assert, payout — can be enqueued.
- Operators cannot send the `Reimburse` transaction after a successful kickoff, forfeiting their collateral.
- Operators cannot send `ChallengeTimeout` or `OperatorChallengeAck`, leaving them unable to defend against watchtower challenges.
- Watchtowers cannot send `WatchtowerChallenge`, removing the fraud-detection layer.

This constitutes slashable exposure of operator collateral and permanent liveness failure of the bridge's Bitcoin-side transaction pipeline.

---

### Likelihood Explanation

The migration is applied automatically at startup via `run_schema_script`. However, the constraint is absent from `schema.sql`, so:

1. Any deployment that bootstraps the database from `schema.sql` alone (disaster recovery, staging, manual setup) starts without the constraint.
2. Rolling back migration 0003 (its down-migration explicitly drops the constraint) removes the constraint from a live deployment.
3. If migration 0003 fails mid-apply (e.g., due to a pre-existing duplicate `txid` row from a race), the startup error may be swallowed or retried without the constraint being present.

The down-migration explicitly drops the constraint: [2](#0-1) [8](#0-7) 

---

### Recommendation

1. **Mirror the constraint in `schema.sql`:** Add `UNIQUE (txid)` directly to the `tx_sender_try_to_send_txs` table definition in `core/src/database/schema.sql` so the constraint is present regardless of migration state, matching the standalone tx-sender schema in `crates/clementine-tx-sender/migrations/0001_init.up.sql` which already declares `UNIQUE (txid)`. [9](#0-8) 

2. **Add a startup assertion:** Before starting any tx-sender worker, assert that the `uq_tx_sender_txid` constraint exists in `pg_constraint`. Fail fast with a clear error if it is absent.

3. **Make the migration idempotent:** Change `ADD CONSTRAINT uq_tx_sender_txid UNIQUE (txid)` to `ADD CONSTRAINT IF NOT EXISTS uq_tx_sender_txid UNIQUE (txid)` so repeated migration runs do not fail.

---

### Proof of Concept

1. Create a fresh PostgreSQL database and apply only `core/src/database/schema.sql` (skip migrations).
2. Start the bridge node. Startup succeeds because `run_schema_script` applies schema.sql, but migration 0003 is not present in this scenario.
3. Trigger any bridge action that calls `insert_try_to_send` — e.g., call `optimistic_payout` or initiate a deposit.
4. `save_tx` executes:
   ```sql
   INSERT INTO tx_sender_try_to_send_txs … ON CONFLICT (txid) DO UPDATE …
   ```
5. PostgreSQL returns: `ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification`.
6. `insert_try_to_send` propagates the error; no transaction is enqueued.
7. The operator cannot send the `Reimburse` transaction after a kickoff, losing their collateral. The bridge's Bitcoin-side transaction pipeline is completely non-functional.

    pub async fn insert_try_to_send(
        &self,
        dbtx: &mut crate::TxSenderTransaction,
        tx_metadata: Option<TxMetadata>,
        signed_tx: &Transaction,
        fee_paying_type: FeePayingType,
        rbf_signing_info: Option<RbfSigningInfo>,
        cancel_outpoints: &[OutPoint],
        cancel_txids: &[Txid],
        activate_txids: &[ActivatedWithTxid],
        activate_outpoints: &[ActivatedWithOutpoint],
    ) -> Result<u32, BridgeError> {
        let txid = signed_tx.compute_txid();

        // do not add duplicate transactions to the txsender
        let tx_exists = self
            .db
            .check_if_tx_exists_on_txsender(Some(dbtx), txid)
            .await?;
        if let Some(try_to_send_id) = tx_exists {
            return Ok(try_to_send_id);
        }

        tracing::info!(
            "Added tx {} with txid {} to the queue",
            tx_metadata
                .as_ref()
                .map(|data| format!("{:?}", data.tx_type))
                .unwrap_or("N/A".to_string()),
            txid
        );

        let try_to_send_id = self
            .db
            .save_tx(
                dbtx,
                tx_metadata,
                signed_tx,
                fee_paying_type,
                txid,
                rbf_signing_info,
            )
            .await?;

    pub async fn run_schema_script(
        config: &BridgeConfig,
        is_verifier: bool,
    ) -> Result<(), BridgeError> {
        let database = Database::new(config).await?;

        sqlx::raw_sql(include_str!("schema.sql"))
            .execute(&database.connection)
            .await?;
        if is_verifier {
            // Check if PGMQ schema already exists
            let is_pgmq_installed = database.is_pgmq_installed(None).await?;

            // Only execute PGMQ setup if it doesn't exist
            if !is_pgmq_installed {
                sqlx::raw_sql(include_str!("pgmq.sql"))
                    .execute(&database.connection)
                    .await?;
            }
        }

        // Apply embedded SQLx migrations from the migrations folder
        // This looks for SQL files under core/src/database/migrations at compile time
        // SQL files in migration folder will be applied in lexicographical order of their filenames
        static MIGRATOR: Migrator = sqlx::migrate!("src/database/migrations");

        MIGRATOR
            .run(&database.connection)
            .await
            .wrap_err("Failed to run migrations")?;

        database.close().await;
        Ok(())
    }
