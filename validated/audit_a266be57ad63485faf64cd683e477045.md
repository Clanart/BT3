### Title
Cached FROST preprocess is never invalidated, enabling nonce reuse across distinct signing calls and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The nginx advisory describes a conditionally-enabled code path (slice module + background cache update) where a stale/uninitialized state is consumed by attacker-driven requests. The Serai analog lives in the coordinator's DKG-confirmation signing protocol: a FROST preprocess seed is deterministically cached in the DB under `CachedPreprocesses`, keyed only by `("DkgConfirmer", attempt)`, and is *never deleted or rotated*. Every call to `share()` and `complete()` re-derives identical FROST nonces from that seed via `AlgorithmSignMachine::from_cache` → `seeded_preprocess` → `ChaCha20Rng::from_seed`. If `sign` is exercised twice under the same attempt with distinct inputs — different received `preprocesses` maps (changing the binding factors and signing set) or a different `key_pair` (changing the signed message) — the same nonce signs two different shares, which is the classic FROST nonce-reuse secret-share recovery.

### Finding Description
- `preprocess_internal` loads a 32-byte seed from `CachedPreprocesses` under `self.context`; if absent it creates one, XOR-encrypts it, and stores it. It is never removed after use (`coordinator/src/tributary/signing_protocol.rs:123-145`). [1](#0-0) 
- `share_internal` re-invokes `preprocess_internal` and calls `machine.sign(preprocesses, msg)`, where `preprocesses` and `msg` are derived from caller-supplied arguments (`coordinator/src/tributary/signing_protocol.rs:150-180`). [2](#0-1) 
- `DkgConfirmer::share` and `DkgConfirmer::complete` are separate public entry points that each call `share_internal`; `complete` even re-runs it a second time with its own `preprocesses`/`key_pair` arguments (`coordinator/src/tributary/signing_protocol.rs:304-327`). [3](#0-2) 
- `from_cache` deterministically regenerates the same `nonces` from the same seed (`crypto/frost/src/sign.rs:121-145`, `268-274`). [4](#0-3) 
- The file's own header admits the hazard: nonce reuse occurs if "the received nonce commitments (or the message to be signed) would have to be distinct and sign would have to be called again" (`coordinator/src/tributary/signing_protocol.rs:29-35`), and FROST docs state reuse "enables a third-party to recover your private key share" (`spec/cryptography/FROST.md:51-55`). [5](#0-4) 

### Impact Explanation
A validator's FROST share is `s = d + b·e·ρ + λ·c·share`. If two shares are emitted under the same `(d, e)` nonces but different `ρ`/challenge (different preprocess set or different `set_keys_message`/`key_pair`), anyone observing both published shares solves a linear system for the secret share — i.e., full recovery of the validator's MuSig root-of-trust key share, meeting the "key share recovery" bar.

### Likelihood Explanation
The arguments to `share`/`complete` (the `preprocesses` map of other validators and the `key_pair` to confirm) are attacker-influenced public inputs delivered through the tributary protocol. Safety hinges entirely on BFT-finalized identical inputs and a "complete rebuild re-decides nonces" assumption; the persisted DB seed, the lack of any consumed-flag or on-chain commitment check (explicitly noted as TODO at lines 50-54), and two independently-parameterized share-emitting paths make a second `sign` with distinct inputs reachable without validator collusion. Uncertain: I could not fully trace `handle.rs` to confirm whether distinct `key_pair`/preprocess sets can reach the same `attempt` context, so likelihood rests on the protocol-level argument in the file header.

### Recommendation
Delete (or version) `CachedPreprocesses` after the first successful `sign`, and before publishing any share verify on-chain that the regenerated commitments match the previously published preprocess for that context (the TODO at lines 50-54). Include the full intended message/`key_pair` and preprocess-set hash in the cache key so a mismatch aborts rather than reuses nonces.

### Proof of Concept
1. In attempt `k`, `DkgConfirmer::share(preprocesses_A, key_pair_1)` stores seed `S` under `("DkgConfirmer", k)` and publishes share `s1` for message `m1`.
2. `DkgConfirmer::complete(preprocesses_B, key_pair_2, shares)` (or a second `share` after a partial rebuild retaining the DB) regenerates identical nonces from `S` and publishes `s2` over different binding factors/message.
3. From `s1`, `s2`, the public preprocesses, and challenges, solve for the validator's secret share.

    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
  }
