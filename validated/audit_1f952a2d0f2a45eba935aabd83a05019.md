### Title
No slippage protection in `PublicDelegation` staking vault's `stake`/`stakeFor`/`withdraw`/`redeem` results in stakers receiving fewer shares or assets than expected - ([File: contracts/bindings/publicdelegation/PublicDelegation.go])

### Summary
The `PublicDelegation` contract is an ERC-4626-style staking vault where users deposit KAIA via `stake()`/`stakeFor()` to mint shares, and withdraw KAIA via `withdraw()`/`redeem()` by burning shares. None of these state-changing entry points accept a caller-supplied minimum/maximum bound on the exchange rate (no `minSharesOut`, `minAssetsOut`, `maxSharesBurned`, or deadline parameter), so a staker has no on-chain guarantee about how many shares they will receive for their assets, or how many assets they will receive for their shares, at execution time.

### Finding Description
`PublicDelegation` exposes an ERC-4626-like interface: `ConvertToShares`/`ConvertToAssets`/`PreviewDeposit`/`PreviewRedeem`/`PreviewWithdraw` for quoting, and mutating functions `Stake()` (payable), `StakeFor(_recipient)` (payable), `Withdraw(_recipient, _assets)`, and `Redeem(_recipient, _shares)` for actually moving value. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

None of `Stake`, `StakeFor`, `Withdraw`, or `Redeem` take any additional parameter beyond the recipient/amount — there is no `minShares`, `minAssets`, or `deadline` argument, exactly the bug class described in the report ("no way to know how many funds will be transferred to mint or burn N shares"). The `Staked`/`Redeemed` events confirm the actual assets/shares are only known post-execution: [5](#0-4) [6](#0-5) 

This is in stark contrast to the `GaslessSwapRouter` contract in the same codebase, which explicitly implements `minAmountOut`/`amountRepay`/`deadline` parameters on its `swapForGas` function and enforces them both on-chain and at mempool admission time (`checkBalanceForSwap`), showing the project is otherwise aware of and applies slippage-protection patterns elsewhere: [7](#0-6) 

### Impact Explanation
Because the exchange rate (`convertToShares`/`convertToAssets`) can move between transaction submission and execution — due to reward accrual, commission changes, other users' `stake`/`redeem`/`withdraw` calls, or `redelegateByAssets` operations changing underlying CN staking balances — an unprivileged staker calling `stake()` or `stakeFor()` has no way to bound the minimum shares minted for their KAIA, and a staker calling `withdraw()` has no way to bound the maximum shares burned to receive a requested asset amount (or minimum assets for `redeem`). A transaction can be front-run/sandwiched in the same block (e.g., by an operator or other stakers submitting large stake/redeem transactions ahead of the victim's tx) to shift the exchange rate unfavorably, causing the victim to receive materially fewer shares or fewer assets than expected at submission time. This is a direct unauthorized value-loss vector for a public, unprivileged caller — matching the required "concrete unauthorized value movement" criterion.

### Likelihood Explanation
Medium-High. Any user can call `stake`/`stakeFor`/`withdraw`/`redeem` — no privileged role required. The exchange rate is influenced by staking rewards accrual and by any other party's stake/withdraw actions, which are also public and unprivileged, making sandwiching/front-running practically feasible for anyone monitoring the mempool, especially since PublicDelegation vaults are meant to be used by ordinary, often non-technical stakers.

### Recommendation
Add slippage-protection parameters to all state-changing exchange functions:
- `stake(uint256 minShares)` / `stakeFor(address recipient, uint256 minShares)`: revert if minted shares < `minShares`.
- `withdraw(address recipient, uint256 assets, uint256 maxShares)`: revert if shares burned > `maxShares`.
- `redeem(address recipient, uint256 shares, uint256 minAssets)`: revert if assets returned < `minAssets`.
Optionally add a `deadline` parameter to prevent stale transactions from executing at a much later, worse exchange rate.

### Proof of Concept
1. Staker A submits `stake()` with `msg.value = X`, expecting `previewDeposit(X)` shares based on the current exchange rate.
2. Before A's transaction is included, another party submits a large `redeem()`/`withdraw()` or reward-affecting transaction that shifts the vault's underlying assets/total-shares ratio unfavorably for depositors.
3. A's `stake()` executes at the new, worse exchange rate and mints fewer shares than A expected — A has no `minShares` parameter to protect against this and cannot revert the transaction on unfavorable execution.
4. Symmetric attack applies to `withdraw()`/`redeem()`: a staker burns more shares than expected to withdraw a fixed asset amount, or receives fewer assets than expected for a fixed share amount, with no way to bound the outcome.

Note: I was unable to locate the actual Solidity source file for `PublicDelegation` in the indexed codebase (only compiled bindings/bytecode were found via `contracts/bindings/publicdelegation/PublicDelegation.go`); the analysis above is based on the ABI/function signatures and events exposed in the generated bindings, which conclusively show the absence of slippage parameters, but the exact internal accounting/rounding logic could not be fully verified. If deeper verification of exchange-rate computation is needed, a Devin session with full repository access could be used to locate and review the original `.sol` source (likely outside the indexed size limits).
