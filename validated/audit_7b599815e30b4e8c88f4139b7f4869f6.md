### Title
DataLayer mirror URLs let any wallet holder force SSRF requests from other DataLayer nodes - (File: chia/data_layer/download_data.py)

### Summary
Any wallet user can put an arbitrary attacker-controlled URL on-chain as a "mirror" for a DataLayer store, and any node that subscribes to that store will later have its DataLayer service issue outbound HTTP GET requests to that exact URL, with no scheme, host, or address-space validation. This is the same bug class as CVE-2024-41812 (txtdot SSRF in `/get`): an untrusted, remote-supplied URL is fed directly into an outbound HTTP client used by the service itself.

### Finding Description
DataLayer mirrors are created via `dl_new_mirror`, which calls `DataLayerWallet.create_new_mirror()`. The URLs supplied by the caller are put straight into the mirror coin's memos with no validation of scheme or destination: [1](#0-0) 

On the `DataLayer` service side, `add_mirror()` only checks that the URL list is non-empty — it performs no URL sanity check before publishing: [2](#0-1) 

`update_subscriptions_from_wallet()` pulls these mirror URLs directly from wallet RPC state (which reflects on-chain mirror coins created by *any* wallet, not just the local operator) and feeds them into the local subscription table with only a trailing-slash strip — no scheme or host filtering: [3](#0-2) 

During the periodic sync loop, `fetch_and_validate()` picks one of these `server_info.url` values and passes it into `insert_from_delta_file()` → `download_file()`: [4](#0-3) 

When no downloader plugin is configured, `download_file()` calls `http_download()`, which performs `aiohttp` `session.get(server_info.url + "/" + filename, ...)` directly against the attacker-supplied URL: [5](#0-4) [6](#0-5) 

There is no validation anywhere in this path restricting the mirror URL to a particular scheme (e.g., rejecting `file://`, `ftp://`, or requiring `http(s)://`) or blocking loopback/link-local/private-network/cloud-metadata addresses (e.g., `127.0.0.1`, `169.254.169.254`, RFC1918 ranges, internal service DNS names). Test code even demonstrates mirrors being created with URLs like `"foo"`, `"bar"`, or bare `http://127.0.0.1/...` strings, confirming the absence of format/target checks: [7](#0-6) [8](#0-7) 

The corresponding S3 plugin download path (`chia/data_layer/s3_plugin_service.py`) does constrain requests to `s3://` scheme and requires the URL to be present in a locally-configured `store.urls` allowlist, so that specific path is not exploitable. However, the default (no-downloader) HTTP path has no equivalent allowlist or scheme restriction.

### Impact Explanation
Any wallet participant (no special privileges beyond normal spend-bundle/wallet-transaction submission) can add a mirror to any store id via `dl_new_mirror`, publishing a coin with attacker-chosen URLs. Once confirmed on-chain, every other node running the DataLayer service that syncs/subscribes to that store (which happens automatically as part of normal store synchronization, not merely by opt-in mirroring) will read that URL from wallet state and have its own DataLayer process issue an HTTP GET to it during `fetch_and_validate()`. This lets a remote unprivileged party turn victim DataLayer nodes into a request proxy against arbitrary targets, including internal-network-only services or cloud metadata endpoints reachable from the victim's host, exactly mirroring the SSRF pattern described in the txtdot advisory (unauthenticated caller providing the URL, server making the request on the caller's behalf). Since v1.7.0 of txtdot mitigated by not returning the response body, note that even without response content ever surfacing to an attacker in chia's case, the request itself is still sent — matching the residual risk explicitly called out in the report ("the requests can still be sent... a firewall...should be set").

### Likelihood Explanation
Likelihood is High for reachability: creating a mirror only requires a standard transaction (`dl_new_mirror`) that any wallet with funds can submit and get confirmed, and no server-side authorization beyond normal chain consensus is needed. Any full DataLayer node tracking that store will process the mirror URL during its regular background sync loop (`periodically_manage_data()` → `update_subscription()` → `fetch_and_validate()`), which runs automatically, not on-demand by an operator decision.

### Recommendation
Validate mirror URLs before publication and before use for outbound fetches:
- Enforce an explicit allowed scheme list (e.g., `http`/`https` only) both when creating mirrors (`DataLayerWallet.create_new_mirror` / `DataLayer.add_mirror`) and when consuming them (`update_subscriptions_from_wallet`, `http_download`).
- Resolve and reject loopback, link-local, private, and other non-routable/internal address ranges before issuing the `aiohttp` GET in `http_download()`, or require an explicit user-configured mirror allowlist analogous to the S3 plugin's `store.urls` check.
- Document/require that operators run DataLayer sync behind an egress firewall restricting outbound requests to intended mirror hosts, consistent with the upstream advisory's stated residual-risk mitigation.

### Proof of Concept
1. Attacker wallet creates a DataLayer store or targets an existing store id known to be tracked by victim nodes.
2. Attacker calls `dl_new_mirror` (`DLNewMirror(launcher_id=store_id, amount=..., urls=["http://169.254.169.254/latest/meta-data/"], fee=..., push=True)`) via wallet RPC, as shown in the test flow: [7](#0-6) 
3. The transaction confirms on-chain, creating a mirror coin with the malicious URL in its memo.
4. Any victim node running the DataLayer service and subscribed/tracking that store id runs `update_subscriptions_from_wallet()`, ingesting the malicious URL into its local subscription table with no validation: [3](#0-2) 
5. On the next sync cycle, `fetch_and_validate()` selects this server and `http_download()` performs `session.get("http://169.254.169.254/latest/meta-data/" + "/" + filename, ...)` from the victim's own network context: [9](#0-8) 
6. This confirms the SSRF: the victim's DataLayer process issues an outbound request to an attacker-chosen destination that the attacker could not reach directly.

async def download_file(
    data_store: DataStore,
    target_filename_path: Path,
    store_id: bytes32,
    root_hash: bytes32,
    generation: int,
    server_info: ServerInfo,
    proxy_url: str | None,
    downloader: PluginRemote | None,
    timeout: aiohttp.ClientTimeout,
    client_foldername: Path,
    timestamp: int,
    log: logging.Logger,
    grouped_by_store: bool,
    group_downloaded_files_by_store: bool,
    max_delta_file_size: int,
) -> bool:
    if target_filename_path.exists():
        return True
    filename = get_delta_filename(store_id, root_hash, generation, grouped_by_store)

    if downloader is None:
        # use http downloader - this raises on any error
        try:
            await http_download(
                target_filename_path, filename, proxy_url, server_info, timeout, log, max_delta_file_size
            )
        except (asyncio.TimeoutError, aiohttp.ClientError, MaxDeltaFileSizeExceededError):
            new_server_info = await data_store.server_misses_file(store_id, server_info, timestamp)
            log.info(
                f"Failed to download {filename} from {new_server_info.url}."
                f"Miss {new_server_info.num_consecutive_failures}."
            )
            log.info(f"Next attempt from {new_server_info.url} in {new_server_info.ignore_till - timestamp}s.")
            return False
        return True
```

async def http_download(
    target_filename_path: Path,
    filename: str,
    proxy_url: str | None,
    server_info: ServerInfo,
    timeout: aiohttp.ClientTimeout,
    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
```
