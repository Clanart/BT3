### Title
Reward forfeiture calculation always returns zero, letting users bypass the expire-forfeit penalty on mWomSV/vlMGP rewards - (File: rewards/mWOMSVBaseRewarder.sol)

### Summary
`_calExpireForfeit` in `mWOMSVBaseRewarder.sol` is meant to compute the portion of a user's accrued reward that should be forfeited (and redistributed to remaining stakers) when the reward is not fully "rewardable" (e.g., tokens sitting in a cooldown/unlock slot rather than fully locked, per `getRewardablePercentWAD` in `wombat/mWomSV.sol`). Instead, it initializes `rewardableAmount` to the *same* value as `_amount` and then subtracts them, producing a diff of 0 every time — structurally identical to the Allora `coeffDiff` bug where a value is diffed against itself. [1](#0-0) 

### Finding Description
`_sendReward` computes the forfeit amount for a user's claim via `_calExpireForfeit(_account, userRewards[_rewardToken][_account])`: [2](#0-1) 

`_calExpireForfeit` sets `rewardableAmount = _amount` and then computes `forfeitAmount = _amount - rewardableAmount`, which is always `0` because both operands are identical: [1](#0-0) 

This mirrors the Allora `GetAllReputersOutput` bug exactly: the code appears intended to diff a "rewardable" (post-penalty) amount against the raw earned `_amount`, but the two values are set equal before subtraction, so the forfeiture math is dead code. `rewardableAmount` is never derived from the user's actual lock/cooldown state (e.g., via `getRewardablePercentWAD`, which does exist in the paired `mWomSV.sol` lock contract and computes a genuinely different, sub-100% percentage for users with cooled-down/unlocking balances) — that percentage is never consulted here. [3](#0-2) 

As a consequence, `forfeitAmount` is always `0`, `toSend` always equals the user's full `userRewards[...]`, and `_queueNewRewardsWithoutTransfer` (which redistributes forfeited amounts back into `rewardPerTokenStored` for remaining stakers) is never invoked with a nonzero amount. [4](#0-3) 

### Impact Explanation
The mWomSV forfeiture mechanism exists to penalize users who have partially unlocked/cooled-down positions (should not earn full reward), redistributing the forfeited share to full-lock stakers who remain in the system. Because the diff always computes to zero, every user always receives 100% of their computed reward regardless of lock/cooldown state, and the forfeited yield that should have flowed back to other stakers via `_queueNewRewardsWithoutTransfer`/`ForfeitRewardAdded` never materializes. This is a permanent, protocol-wide loss of yield that should have accrued to compliant lockers — it is not recoverable after the fact since the forfeit amount that should have been retained is instead unconditionally paid out and gone. This falls under permanent freezing/loss of unclaimed yield for legitimate stakers, reachable by any ordinary wallet holder of mWomSV positions calling `getReward`/`getRewards`.

### Likelihood Explanation
High likelihood: this triggers on every single reward claim (`getReward`/`getRewards`) by any unprivileged wallet holding mWomSV with a partially-unlocked/cooling-down position — no special conditions, permissions, or attacker setup required. The bug is deterministic and always active, not a rare edge case.

### Recommendation
Compute `rewardableAmount` from the actual rewardable percentage of the user's position (e.g., via `getRewardablePercentWAD` from the paired locker contract) rather than initializing it to `_amount`, then derive `forfeitAmount = _amount - rewardableAmount` from two genuinely distinct values.

### Proof of Concept
1. A user locks mWom into `mWomSV`, then calls `startUnlock` to move part of their balance into cooldown (per `wombat/mWomSV.sol` `startUnlock`, lines 247-277), which per `getRewardablePercentWAD` should reduce their effective "rewardable" percentage below 100% while in cooldown.
2. Reward accrues on their full `mWOMSVBaseRewarder` balance via `_earned`.
3. User calls `getReward`/`getRewards`, which invokes `_sendReward` → `_calExpireForfeit(_account, userRewards[...])`.
4. Inside `_calExpireForfeit`, `rewardableAmount` is set equal to `_amount`, so `forfeitAmount = _amount - rewardableAmount == 0` unconditionally, regardless of the user's actual cooldown state.
5. `toSend = userRewards - 0 = full reward`, and the user receives 100% of the reward despite holding a partially-cooling-down (non-fully-locked) position; `_queueNewRewardsWithoutTransfer` is never called to return the intended forfeited share to `rewardPerTokenStored` for other stakers, permanently diverting that yield away from compliant long-term lockers.

Note: `rewards/vlMGPBaseRewarder.sol` contains a structurally similar `_calExpireForfeit`-style flow (confirmed via grep matches for the same identifiers) but I was not able to fully read its contents in the time available; it should be checked for the identical pattern as a companion instance of the same bug class.

```text
    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;
        
        if (forfeitAmount < (_amount / 1000)) {  // if forfeitAmount is smaller than 0.1% ignore to save gas fee
            forfeitAmount = 0;
            rewardableAmount = _amount;
        }

        return forfeitAmount;
    }
```

```text
    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
```
