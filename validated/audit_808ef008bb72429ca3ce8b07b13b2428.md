### Title
`ReceivedOutput::read` deserializes an offset/output pair without validating the offset actually derives the output's `script_pubkey`, allowing forged "received" outputs that are unspendable - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes functions that accept inputs (addresses, numeric parameters) without validating them, leading to unexpected state. The Serai analog is `ReceivedOutput::read` in `networks/bitcoin/src/wallet/mod.rs`, which reconstructs a spendable-output record from raw bytes — an offset scalar, a `TxOut`, and an `OutPoint` — with no consistency check that the offset maps the scanner's key to the output's `script_pubkey`. This invariant is enforced on the production path (`Scanner::scan_transaction` only emits a `ReceivedOutput` when `self.scripts.get(&output.script_pubkey)` yields the matching offset at lines 205-210), but is completely absent on the deserialization path (lines 122-134), which is explicitly a sink for untrusted bytes.

### Finding Description
`ReceivedOutput` couples three attacker-controlled fields:

```rust
pub struct ReceivedOutput {
  offset: Scalar,
  output: TxOut,
  outpoint: OutPoint,
}
```

`ReceivedOutput::read` calls `Secp256k1::read_F` for the offset (which only enforces scalar canonicity) and `consensus_decode` for the `TxOut`/`OutPoint` (which only enforces syntactic validity), then returns the struct unconditionally. There is no check equivalent to `p2tr_script_buf(key + GENERATOR * offset) == output.script_pubkey`, no check that the output value is non-dust/nonzero, and no binding between the offset and the point the scanner actually watches. Contrast with `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`), which re-runs `ThresholdParams::new` and `ThresholdKeys::new` to re-validate deserialized state — `ReceivedOutput::read` performs no such semantic re-validation.

### Impact Explanation
A forged `ReceivedOutput` causes the wallet to treat arbitrary prevouts as owned by the multisig key:

- **Funds reported received that are not spendable.** An attacker supplies a `TxOut` paying to an unrelated `script_pubkey` (or dust) paired with any offset. The output is recorded as a wallet UTXO; when a spend is attempted, `offset` is applied to the threshold keys to derive the signing key, which does not correspond to the output's key, so the Schnorr signature is invalid on-chain. The coordinator reports/marks funds it cannot ever spend.
- **Signing of an unintended message.** Conversely, an attacker can supply the multisig's real `script_pubkey` with a *wrong* offset. The signer computes `key + offset` as its tweak and produces a signature committing to prevouts/amounts the attacker chose — a valid-looking protocol signature over attacker-constructed sighash data that fails consensus or burns fees.
- The `register_offset` documentation (lines 168-179) explicitly warns that arbitrary offsets "may introduce a script path into the output, allowing the output to be spent by satisfaction of an arbitrary script" — `read` is the one entry point where that warning is not enforced.

This is reachable by an unprivileged party wherever serialized `ReceivedOutput`s are transported or persisted from data the attacker influences (the prompt's trust model explicitly admits untrusted bytes into `ReceivedOutput::read`).

### Likelihood Explanation
Medium. The bug requires an attacker-controlled byte stream to reach `ReceivedOutput::read`, which is plausible in a system that relays or persists scan results between components, but is not achievable purely by sending a Bitcoin transaction to the chain (that path goes through `scan_transaction`, which is consistent). The payoff when reached is direct: phantom/unspendable UTXOs and signing attempts over attacker-shaped data.

### Recommendation
In `ReceivedOutput::read`, after decoding, re-derive the expected script and compare: compute `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)` against `output.script_pubkey`, rejecting mismatches. Since `read` lacks the scanner's key, either store/check a key commitment inside `ReceivedOutput` or make `read` a method on `Scanner` so the consistency check is structurally enforced. Additionally reject zero/dust `output.value` per standard dust rules, matching the "validate values before operating on them" recommendation of the report.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ReceivedOutput::read
let attacker_offset = Scalar::ONE; // any scalar
let attacker_script = ScriptBuf::new_p2tr_tweaked(/* attacker's key, not the multisig's */);
let forged = ReceivedOutput {
  offset: attacker_offset,
  output: TxOut { value: Amount::from_sat(100_000), script_pubkey: attacker_script },
  outpoint: OutPoint::new(Txid::all_zeros(), 0),
};

let mut bytes = forged.serialize().as_slice();
let decoded = ReceivedOutput::read(&mut bytes).unwrap(); // succeeds: no consistency check

// decoded.output.script_pubkey was never matched against scanner.scripts,
// yet downstream code treats `decoded` as an owned, spendable output.
// Spending derives the tweak from decoded.offset, producing an invalid signature
// for the attacker's script_pubkey -> funds counted as received, never spendable.
```

Root cause support:
- `ReceivedOutput::read` performs only canonical/syntactic decoding with no semantic check: `networks/bitcoin/src/wallet/mod.rs:122-134` [1](#0-0) 
- The offset↔script invariant is only created inside `scan_transaction`: `networks/bitcoin/src/wallet/mod.rs:199-214` [2](#0-1) 
- The codebase itself flags unconstrained offsets as dangerous (script-path injection): `networks/bitcoin/src/wallet/mod.rs:168-179` [3](#0-2) 
- By contrast, sibling deserializers do re-validate semantics (`ThresholdKeys::read` re-runs `ThresholdParams::new`/`ThresholdKeys::new`): `crypto/dkg/src/lib.rs:625-632` [4](#0-3) 

Caveat: I verified the missing check in `read` vs. `scan_transaction`, but could not trace the `send.rs` spending path within the tool-call budget to confirm exactly where `offset` is consumed during signing; the unspendable-funds conclusion assumes the standard `keys.offset(offset)` flow implied by the field's docstring.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
