### Title
Panic on point-at-infinity in BIP-340 HRAm reachable via untrusted FROST inputs — denial of service - (File: networks/bitcoin/src/crypto.rs)

### Summary

The referenced CVE is a missing-validation/null-pointer-dereference: attacker-influenced data reaches a code path that assumes a value is non-null/valid and crashes. Serai is Rust, so the direct analog is a reachable `expect`/panic on attacker-controlled cryptographic input rather than a raw pointer dereference. `bitcoin-serai`'s BIP-340 glue code assumes group elements are never the point at infinity and panics with `expect("point at infinity")` / `expect("x_only was passed a point which was infinity or odd")` when that assumption is violated. These functions are invoked on values derived from remote party bytes during FROST signing and verification.

### Finding Description

`x()` and `x_only()` in `networks/bitcoin/src/crypto.rs` unconditionally convert a `ProjectivePoint` to its affine x-coordinate and panic on the point at infinity:

- `x`: `(*encoded.x().expect("point at infinity")).into()` [1](#0-0) 
- `x_only`: `XOnlyPublicKey::from_slice(&x(key)).expect("x_only was passed a point which was infinity or odd")` [2](#0-1) 

`Hram::hram` calls `x(R)` and `x(A)`, where `R` is the aggregate nonce commitment and `A` is the group key [3](#0-2) . The code comments acknowledge the panic: "If either `R` or `A` is the point at infinity, this will panic" [4](#0-3)  and "`verify`, `verify_share` MUST be called after `sign_share` is called. Otherwise, this library MAY panic" [5](#0-4) .

The assumption that infinity is unreachable is not enforced where the inputs originate:

- Individual commitment points are read with `Curve::read_G`, which rejects the identity point *per element* [6](#0-5) . However, `R` used in `hram` is a **sum** of nonce commitments and binding-factor-weighted commitments across all signers. A sum of non-identity points can still be the identity; there is no post-aggregation identity check before `hram` runs.
- `A` is `ThresholdKeys::group_key()` = `core.group_key * scalar + generator * offset` [7](#0-6) . `ThresholdKeys::read` deserializes `t`, `n`, `i`, an interpolation blob, a secret share, and `n` verification shares entirely from the byte stream [8](#0-7) , and `group_key` is computed from verification shares with no visible rejection of an identity result before it is used in signing. (I could not fully confirm whether `ThresholdKeys::new` rejects identity group keys — the visible portion of `crypto/dkg/src/lib.rs:380-390` shows no such check.)
- `view()` also documents panic-on-bad-state behavior: `original_verification_share` panics on an invalid participant index via unchecked `HashMap` indexing [9](#0-8) , and `included`/`verification_shares` assumptions are enforced by indexing `self.core.verification_shares[i]` [10](#0-9) .

### Impact Explanation

A panic in `sign_share`/`verify` aborts the signing process (and, in a `no_std`/FFI or embedded wallet context, is an abort rather than a recoverable error). An attacker who can supply bytes that reach `Hram::hram` — via preprocess/`read_preprocess` commitments they control, or via a serialized `ThresholdKeys`/`ThresholdView` whose verification shares interpolate to an identity group key — causes the signer/verifier to crash. This is an availability loss (the Medium-severity, `VA:H`-style impact in the original report), not secret-key leakage. Since this is a panic rather than a wrong-value path, it is DoS-only.

### Likelihood Explanation

Exploitation requires producing an identity aggregate where the code assumes a non-identity point:

- For `A` (group key): bytes fed to `ThresholdKeys::read` control the `n` verification shares and the interpolation method. If `ThresholdKeys::new` does not reject an identity interpolated group key (not confirmed in the visible code), crafting shares that interpolate to identity is trivial — e.g., constant interpolation whose constant term is identity. This is a deterministic, cheap attack requiring only that the target deserialize attacker-influenced key material, which the in-scope API list explicitly permits (`ThresholdKeys::read`).
- For `R`: requires a signing participant to craft preprocess commitments such that `Σ(D_i + ρ_i·E_i)` is identity. Because each `ρ_i` binds over the full commitment set (`hash_binding_factor` over all preprocesses), this requires grinding/collusion and is harder, but preprocessing rounds that reveal commitments before fixing ρ, or a coordinator-controlled commitment set, make it feasible.

Overall: moderate. The group-key path is deterministic if the identity check is indeed absent; the nonce-sum path requires favorable protocol scheduling.

### Recommendation

- In `networks/bitcoin/src/crypto.rs`, change `x`/`x_only`/`Hram::hram` to return `Option`/error instead of `expect`ing non-infinity, and propagate the failure through `Algorithm::verify`/`sign_share` as an error/`None` rather than a panic.
- In `crypto/frost`, after aggregating nonce commitments (and after applying binding factors / per-participant transcript weights), explicitly check `R.is_identity()` before invoking the HRAm, and reject the signing session with a `FrostError`.
- In `crypto/dkg/src/lib.rs`, `ThresholdKeys::new`/`ThresholdKeys::read` should reject an identity interpolated `group_key` and identity verification shares, and `view()`/`original_verification_share` should return errors instead of panicking on missing map entries or invalid participant indexes.

### Proof of Concept

Conceptual PoC (Rust, against `blackvul/serai--014`):

```rust
// Path 1: identity group key via ThresholdKeys::read (if identity is not rejected)
// Serialize a ThresholdKeys blob whose interpolation yields an identity group key:
//   - interpolation tag 0 (Constant) with all coefficients = zero scalar,
//   - arbitrary non-zero secret share,
//   - n verification shares encoding the identity point
//     (bypass Curve::read_G's per-point identity rejection by using a non-identity
//      pair that sums to identity at the interpolation constant term).
// Feed to <Secp256k1>::read via ThresholdKeys::read, then:
let view = keys.view(included)?;               // group_key() == identity
let mut machine = AlgorithmMachine::new(Schnorr::new(), keys);
// ... preprocess exchange completes; on verify():
// Hram::hram calls x(&identity_group_key) ->
//   to_encoded_point(true).x() == None ->
//   expect("point at infinity") -> panic / abort

// Path 2: identity aggregate R
// A signer submits preprocess commitments (D, E) read via Curve::read_G
// (each individually non-identity) such that after the rho binding factors
// are computed, sum_i(D_i + rho_i * E_i) == identity.
// sign_share/verify then calls Hram::hram(&identity, &A, msg) -> panic.
```
