### Title
Seller-controlled DID recovery list persists after DID transfer, allowing former owner to recover/seize the DID from the new owner - (File: chia/wallet/did_wallet/did_wallet.py)

### Summary
Chia DIDs (Decentralized Identifiers) are singleton coins whose inner puzzle is curried with a `recovery_list` (`backup_ids`) and `num_of_backup_ids_needed`, allowing designated backup DIDs to "recover" the DID (i.e., reassign control to a new p2 puzzle/pubkey) without the current owner's private key. When a DID is transferred via `transfer_did`, this recovery list is carried over unchanged into the new inner puzzle unless the seller explicitly clears it, exactly mirroring the Footium bug pattern: an "owner" grants itself (or a colluding party) a standing approval mechanism that is not tied to the current holder and silently persists across an ownership change.

### Finding Description
In `DIDWallet.transfer_did` [1](#0-0) , the new DID inner puzzle hash is computed via `did_wallet_puzzles.get_inner_puzhash_by_p2` using `backup_ids = self.did_info.backup_ids` and `backup_required = self.did_info.num_of_backup_ids_needed` — i.e., the seller's existing recovery configuration — with no automatic reset. The same pattern appears in `get_did_innerpuz` and `get_innerpuz_for_new_innerhash`, where a code comment explicitly flags the risk: [2](#0-1) 

"Note: the recovery list will be kept. In a selling case, the seller should clean the recovery list then transfer to the new owner." This confirms that clearing the list is a manual, opt-in seller responsibility rather than an enforced or automatic step of the transfer flow.

The DID recovery capability is defined by `recovery_list`/`num_of_backup_ids_needed` curried into `DID_INNERPUZ_MOD`, and `create_recovery_message_puzzle` shows the recovery mechanism only requires attestations (`AGG_SIG_UNSAFE`) from the backup IDs rather than the current p2 key: [3](#0-2) . If the seller (malicious former owner) included itself, or DIDs it controls, in the `recovery_list` before selling the DID, and the buyer's client does not proactively detect and clear this configuration, the seller retains sufficient standing authorization to later execute a recovery spend that reassigns the DID's `p2_puzzle`/inner key to itself — effectively seizing back control of the DID coin, and by extension any dependent state (NFT ownership-layer bindings, VC issuance capability, metadata) tied to that DID's identity — without any signature or consent from the current, legitimate owner.

This is structurally analogous to the Footium report: `setApprovalForERC20` lets an owner grant itself standing approval over the escrow's assets that is never revoked on sale; here, the DID's `recovery_list` lets a "owner" grant itself (via backup IDs) standing recovery authority over the DID that is never revoked on transfer.

### Impact Explanation
A buyer who acquires a DID (and any NFTs/assets bound to that DID's ownership) from a malicious or careless seller can have the identity clawed back by the seller through a legitimate-looking recovery spend, without the buyer's key ever being compromised. Because DIDs are frequently used as the "owner" reference for NFT ownership layers (`current_owner` in `construct_ownership_layer`) and for VC issuance, recovering the DID can cascade into loss of practical control over associated provenance/authority, constituting unauthorized coin/state movement analogous in severity to the original ERC20 approval issue.

### Likelihood Explanation
Exploitation requires only that the malicious seller (a) sets up a recovery list naming itself/colluding parties as backup IDs before selling, and (b) the buyer's wallet/tooling does not detect and reset this pre-existing configuration during `transfer_did`, which the code's own comment confirms is not done automatically. Given `transfer_did` performs no default reset and `reset_recovery_list` is only invoked opportunistically [4](#0-3) , this is a realistic, low-effort attack path for a bad-faith seller.

### Recommendation
Make clearing the recovery list (`backup_ids`/`num_of_backup_ids_needed`) the default behavior of `transfer_did` unless the new owner explicitly opts to keep it (mirroring the CLI's `reset_recovery` flag default in `DidTransferDidCMD`, but enforcing it at the wallet/protocol level rather than leaving it to seller discretion). Additionally, wallets receiving a transferred DID should surface the recovery configuration to the user before treating a transfer as "safe," similar to the original report's recommendation to warn about lingering ERC20 approvals.

### Proof of Concept
1. Malicious owner Alice creates a DID with `backup_ids=[Alice_backup_did]` and `num_of_backup_ids_needed=1`.
2. Alice calls `transfer_did(new_puzhash=Bob_ph, ...)` without setting `reset_recovery`/`with_recovery_info=False`; per `transfer_did`, the new inner puzzle keeps `backup_ids=[Alice_backup_did]`.
3. Bob receives the DID, believing he has sole control, and binds NFTs/VCs to it.
4. Alice later initiates a DID recovery spend using `Alice_backup_did`'s attestation (per `create_recovery_message_puzzle`), reassigning the DID's inner p2 puzzle to a key she controls — without Bob's signature — regaining control of the DID and everything referencing it.

    def reset_recovery_list(self) -> Program | None:
        if self.did_info.current_inner is None:
            return None

        uncurried_args = uncurry_innerpuz(self.did_info.current_inner)
        if uncurried_args is None:
            return None

        _, og_recovery_list_hash, _, _, _ = uncurried_args
        if self.did_info.num_of_backup_ids_needed == 0 and not did_recovery_is_nil(og_recovery_list_hash):
            return None

        if len(self.did_info.backup_ids) > 0:
            return None

        return og_recovery_list_hash

def create_recovery_message_puzzle(recovering_coin_id: bytes32, newpuz: bytes32, pubkey: G1Element) -> Program:
    """
    Create attestment message puzzle
    :param recovering_coin_id: ID of the DID coin needs to recover
    :param newpuz: New wallet puzzle hash
    :param pubkey: New wallet pubkey
    :return: Message puzzle
    """
    puzzle = Program.to(
        (
            1,
            [
                [ConditionOpcode.CREATE_COIN_ANNOUNCEMENT, recovering_coin_id],
                [ConditionOpcode.AGG_SIG_UNSAFE, bytes(pubkey), newpuz],
            ],
        )
    )
    return puzzle
