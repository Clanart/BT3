### Title
Unbounded recursive RLP decoding of nested `AccountKeyRoleBased` account keys allows remote stack-overflow DoS via a single `sendRawTransaction` call - (File: blockchain/types/accountkey/account_key_role_based.go)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively invokes `rlp.DecodeBytes` on each sub-key through `AccountKeySerializer.DecodeRLP`, with no depth limit or check that a role key is not itself a `RoleBased` key at decode time. The only defense against nested composite keys (`CheckInstallable` / `ErrNestedCompositeType`) runs *after* the full recursive decode has already completed, so an attacker-controlled AccountUpdate transaction can force the decoder into deep, uncontrolled recursion before validation ever rejects it. This mirrors CWE-674 in the cbor2 advisory: recursive decoding of nested containers without depth tracking, reachable here from a single unauthenticated `sendRawTransaction`/`sendRawTransactions` RPC call.

### Finding Description
`AccountKeySerializer.DecodeRLP` reads a key-type tag and then dispatches to the corresponding `AccountKey.DecodeRLP` implementation: [1](#0-0) 

`AccountKeyRoleBased.DecodeRLP` decodes a `[][]byte` list, and for **each element** calls `rlp.DecodeBytes(b, &serializer)`, which itself may again dispatch into `AccountKeyRoleBased.DecodeRLP` if the encoded key type byte is `AccountKeyTypeRoleBased`: [2](#0-1) 

There is no depth counter or type check preventing a `RoleBased` key from containing another `RoleBased` key at decode time. The intended guard against nested composite keys — `CheckInstallable` returning `kerrors.ErrNestedCompositeType` — is only invoked later, during transaction/account validation (e.g. from `blockchain/state_transition.go` and `tx_pool.go`), which is *after* the entire nested structure has already been recursively decoded in memory/on the call stack: [3](#0-2) 

Because the RLP `Stream` created via `rlp.DecodeBytes` only enforces a byte-length input limit (not a call-depth limit), and each nesting level only costs a few bytes of RLP overhead (a key-type tag byte plus list/string headers), an attacker can encode many thousands of nested `AccountKeyRoleBased` layers within a modestly sized transaction payload submitted over RPC.

This is reachable from an unprivileged, unauthenticated caller through `SendRawTransaction`/`SendRawTransactions`, which call `rlp.DecodeBytes(input, tx)` directly on attacker-supplied bytes before any size or structural validation occurs: [4](#0-3) [5](#0-4) 

Decoding an `AccountUpdate`-type transaction routes through `TxInternalDataAccountCreation`/`TxInternalDataAccountUpdate` style `DecodeRLP`, which decode the `AccountKey` field using `AccountKeySerializer`, e.g.: [6](#0-5) 

There is also a public `klay_decodeAccountKey` RPC that directly decodes an attacker-supplied `AccountKeySerializer` without any size cap at all: [7](#0-6) 

### Impact Explanation
Unlike Python's `RecursionError`, uncontrolled deep recursion in Go typically results in the runtime detecting a stack-growth limit and calling `fatalthrow`, which is **not recoverable** by `defer`/`recover` and crashes the entire process (the whole Kaia node, not just the RPC handler goroutine). A remote, unauthenticated caller sending a single crafted `sendRawTransaction` (or calling `klay_decodeAccountKey`) with a deeply nested `AccountKeyRoleBased` payload could crash a full node or all validators/RPC endpoints that process the same transaction (since the same decode path runs during p2p tx propagation, mempool admission, and block execution). This satisfies the "state divergence between honest nodes" / DoS impact bar because it can take down public RPC nodes and potentially propagate to peers via the tx-pool broadcast path, since nodes gossip raw transactions before/along with validating them.

### Likelihood Explanation
High. The attack requires no special privileges — any transaction sender or public RPC caller can submit a single RLP-encoded blob. Building the payload requires no cryptographic material beyond a syntactically valid outer transaction envelope (the recursive corruption is confined to the `AccountKey` field, decoded independently of signature validation, which happens later). No existing input-size check occurs before the recursive decode in `SendRawTransaction`, and `klay_decodeAccountKey` provides an even simpler standalone reachable path with no transaction wrapping needed at all.

### Recommendation
- Add an explicit recursion-depth counter (e.g., passed via context or a package-level Stream field) to `rlp.Stream`/`AccountKeySerializer.DecodeRLP`/`AccountKeyRoleBased.DecodeRLP`, rejecting decode once a small fixed depth (e.g., 1, since nested RoleBased keys are never legitimate) is exceeded.
- Move the `IsCompositeType()`/nested-RoleBased check from `CheckInstallable` (post-decode validation) into `AccountKeyRoleBased.DecodeRLP` itself, so nested composite keys are rejected as soon as the inner key type tag is read — before recursing further.
- Add an explicit size/element-count bound when decoding `AccountKeySerializer` and `[]AccountKey` structures directly from RPC input (`klay_decodeAccountKey`, `sendRawTransaction`), independent of `MaxTxDataSize` checks that only occur after decoding.
- Consider wrapping the RLP decode of externally supplied account keys/transactions in a bounded-depth guard (`Py_EnterRecursiveCall`-equivalent) that returns a normal decode error rather than allowing native stack growth to be attacker controlled.

### Proof of Concept
Conceptually (cannot be executed here, but following the code path above):
1. Construct nested `AccountKeySerializer` bytes recursively:
   - Level 0: `AccountKeyTypeNil` (smallest valid terminal key).
   - Level i: `rlp.Encode([keyTypeByte(RoleBased), rlp.Encode([][]byte{ levelEncoded(i-1) })])`
2. Repeat until N (e.g., tens of thousands) levels are nested, keeping total payload within RPC body limits (a few hundred KB to a few MB).
3. Wrap the innermost/outermost encoding as the `AccountKey` field of an `AccountUpdate` transaction (`TxTypeAccountUpdate`), RLP-encode the full transaction, and submit via `klay_sendRawTransaction`/`eth_sendRawTransaction`, or submit the raw nested `AccountKeySerializer` bytes directly to `klay_decodeAccountKey`.
4. `rlp.DecodeBytes` → `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` → `rlp.DecodeBytes` (recursive) is invoked N times without a depth check, driving Go stack growth until the runtime's max-stack limit is hit, producing an unrecoverable fatal crash of the node process.

Note: I was not able to execute this PoC in this environment (no runtime access); the depth/byte-overhead ratio needed to reliably trigger a Go stack-overflow fatal crash (vs. merely being slow) should be empirically verified by a background engineer with Go tooling before relying on exact payload sizes.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

// SendRawTransactions will add multiple signed transactions to the transaction pool.
func (s *KaiaTransactionAPI) SendRawTransactions(ctx context.Context, inputs []hexutil.Bytes) ([]common.Hash, error) {
	hash := []common.Hash{}
	errs := []error{}

	if len(inputs) == 0 {
		hash = append(hash, common.Hash{})
		return hash, errors.New("Empty input")
	}

	for i, input := range inputs {
		if len(input) == 0 {
			hash = append(hash, common.Hash{})
			errs = append(errs, fmt.Errorf("Index %d: empty input", i))
			break
		}
		// Allow naked Ethereum tx types
		if 0 < input[0] && input[0] < 0x7f {
			input = append([]byte{byte(types.EthereumTxTypeEnvelope)}, input...)
		}
		tx := new(types.Transaction)
		if err := rlp.DecodeBytes(input, tx); err != nil {
			hash = append(hash, common.Hash{})
			errs = append(errs, fmt.Errorf("Index %d: %w", i, err))
			break
		}
		if err := s.b.SendTx(ctx, tx); err != nil {
			hash = append(hash, common.Hash{})
			errs = append(errs, fmt.Errorf("Index %d: %w", i, err))
			break
		}
		hash = append(hash, tx.Hash())
	}

	return hash, errors.Join(errs...)
}
