### Title
Unbounded length-prefixed allocation in Schnorr aggregate signature deserialization enables memory exhaustion DoS - (File: crypto/schnorr/src/aggregate.rs)

### Summary
Analogous to CVE-2023-25153 (no limit on bytes read for attacker-controlled data → denial of service), `SchnorrAggregate::read` in `crypto/schnorr/src/aggregate.rs` trusts a 32-bit length prefix read directly from the input byte stream and uses it to pre-size and grow a `Vec` of group elements. An attacker who supplies bytes that are later deserialized — e.g., an aggregate signature carried in a message to be verified — can claim a list of up to ~4.3 billion points, forcing a multi-gigabyte allocation / indefinite `read_G` loop from a tiny input.

### Finding Description
The deserialized form of the Schnorr aggregate signature begins with a `u32` little-endian count of `R` values. `read` reads those 4 bytes, converts them with `u32::from_le_bytes`, and then allocates `Vec::with_capacity(usize::try_from(count)?)` (and/or pushes `C::read_G(reader)?` once per claimed element) before any signature semantics are checked. Nothing bounds `count` against the actual number of bytes remaining in the stream, nor is there a protocol-level cap enforced in this function.

This is exactly the advisory's bug class: a size field taken from untrusted input is used to determine allocation/read volume, so a handful of attacker-controlled bytes translate into up to `u32::MAX × size_of::<C::G>()` (on the order of hundreds of GB of address space/committed memory via `with_capacity`, plus per-element decode work) of resource consumption. The analogous fixed-size readers are safe — `C::read_F`/`C::read_G` read fixed `Repr` buffers in `crypto/ciphersuite/src/lib.rs:74-101`, and `ThresholdKeys::read`/`Commitments::read` bound their loops by `n: u16` / the algorithm's nonce count (`crypto/dkg/src/lib.rs:608-623`, `crypto/frost/src/sign.rs:276-281`). Only the aggregate signature's `u32` count escapes those bounds.

### Impact Explanation
An unprivileged party that can get its bytes parsed as an aggregate signature — e.g., by submitting a signed message/transaction whose signature bytes are run through `SchnorrAggregate::read` on the verification path — can cause the parsing node to attempt an allocation proportional to an attacker-chosen 32-bit value. Per the allocator, this is an immediate abort/OOM (Rust `with_capacity` aborts on failure) or a long blocking decode loop, denying service to the verifying party. Per the scoring rules this is availability-only, hence Medium, matching the advisory's CVSS A:H-only impact.

### Likelihood Explanation
Reachability requires an integration path where attacker-supplied bytes reach `SchnorrAggregate::read` — the signature itself is a public artifact routinely transported and re-deserialized for verification, so this is a plausible untrusted-input path. The attacker needs no keys, no threshold participation, and no valid proof: four bytes set to `0xFFFFFFFF` suffice to trigger the oversized allocation before any cryptographic check runs.

### Recommendation
Cap the element count during deserialization: either enforce a fixed maximum (e.g., the maximum plausible number of nonces/sub-signature components for the protocol), or do not call `Vec::with_capacity` on the untrusted count and instead bound the loop by the reader's remaining length (`count × size_of::<<C::G as GroupEncoding>::Repr>()` must not exceed available bytes). Prefer a `u16`-bounded count consistent with the rest of the DKG/FROST serialization code.

### Proof of Concept
Serialize a valid `SchnorrAggregate`, then replace the first 4 bytes (the `R`-count prefix) with `0xFFFFFFFF`. Feed the result to `SchnorrAggregate::<C>::read(&mut bytes.as_slice())`. `read` will attempt `Vec::with_capacity(~4.29e9 × size_of::<C::G>())` — an abort-level allocation — from a payload that is only tens of bytes long. No signature content needs to be valid; the failure occurs during length-prefixed parsing, before verification.
