### Title
Persisted `CachedPreprocess` is never deleted — an interrupted/retried DKG confirmation re-signs with the same FROST nonce under a new challenge, leaking the validator's MuSig secret share — (`File: coordinator/src/tributary/signing_protocol.rs`)

### Summary
The kernel bug is a cleanup omission: an entity stays in the connected table when `connect()` is interrupted, so a retry inserts it a second time and corrupts the list. The Serai analog is in the coordinator's `SigningProtocol::preprocess_internal`: a deterministic FROST nonce seed (`CachedPreprocess`) is written to `CachedPreprocesses` keyed by `(b"DkgConfirmer", attempt)` and is **never deleted or invalidated** after `sign()` runs. `share()` and `complete()` each rebuild the `AlgorithmSignMachine` from the same cached seed via `from_cache` → `seeded_preprocess`, which regenerates identical nonces with `ChaCha20Rng::from_seed`. If the signing operation is interrupted and retried under the same context while the message being signed (the `set_keys_message` bound to a `KeyPair`) or the participant set differs, the identical nonce is "inserted" into a second signature-equation — the double-add — yielding two shares `s = d + ρ·e + λ·x` that cancel to reveal the private share `x`.

### Finding Description
`preprocess_internal` caches the seed:

```rust
if CachedPreprocesses::get(self.txn, &self.context).is_none() {
  ...
  CachedPreprocesses::set(self.txn, &self.context, &cache.0);
}
let cached = CachedPreprocesses::get(self.txn, &self.context).unwrap();
let (machine, preprocess) =
  AlgorithmSignMachine::from_cache(algorithm, keys, CachedPreprocess(cached));
``` [1](#0-0) 

There is no `CachedPreprocesses::del` anywhere; the entry persists for the life of the DB. This directly violates the contract the FROST library places on `from_cache`: "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share." [2](#0-1)  The seed deterministically regenerates the same `d, e` nonces via `ChaCha20Rng::from_seed`. [3](#0-2) 

The `DkgConfirmer` API then re-executes `sign` on that same seed at two independent call sites: `share(preprocesses, key_pair)` produces a published share, and `complete(preprocesses, key_pair, shares)` internally calls `share_internal` **again** with a `key_pair` argument that is supplied separately and never checked for equality with the one used by `share()`. [4](#0-3)  The file header concedes the danger ("it is explicitly unsafe to reuse nonces across signing sessions") and defers safety to BFT ordering of *received* messages — but the message `set_keys_message(&self.spec.set(), &removed, key_pair)` is built from a locally-supplied `key_pair`, not from BFT-finalized bytes, and the code acknowledges the check "that the commitments generated from the decided nonces are in fact its commitments on-chain" is a TODO. [5](#0-4) 

### Impact Explanation
Two shares produced under the same `(d, e)` nonce but different challenges — e.g., `share()` executed with `key_pair` K₁, the attempt interrupted (crash/reboot, which the code paths explicitly anticipate: "Rebooted, RPC error, or some invariant"), then `complete()`/`share()` executed with K₂ under the still-cached seed — give `s₁ = d + ρ₁e + λx` and `s₂ = d + ρ₂e + λx`. With `λ` known (public participant indexes), `x = ((s₁−s₂) − e(ρ₁−ρ₂)) / λ`... concretely the nonce `d + ρe` is recovered from the pair since ρ is a public binding factor, and subtracting it from either share yields `λx` → `x`. Recovery of a validator's MuSig key share breaks the root-of-trust signature for `set_keys`, i.e., forgery of DKG-confirmation signatures once combined with enough shares, or outright share theft enabling a threshold adversary to reduce the threshold. This matches the admitted impact in `sign.rs`: "Reuse will enable third-party recovery of your private key share." [6](#0-5) 

### Likelihood Explanation
The unsafe state is real and unconditional — the seed is never cleared — but the leak requires a second `sign` under the same `(b"DkgConfirmer", attempt)` context producing a different challenge (different `key_pair` in `set_keys_message`, or a different `removed`/participant set feeding `threshold_i_map_to_keys_and_musig_i_map`). In the honest flow `key_pair` is derived deterministically from the same-attempt DKG output, so `share()` and `complete()` produce identical shares and the reuse is benign. The hazard materializes on a partial rebuild / retry path — the code itself accepts a bound "preventing partial rebuilds" without enforcing it — or any future call site that supplies `key_pair` independently per call. Because the exploit needs an honest-validator interruption plus divergent inputs (rather than attacker-supplied bytes alone), likelihood is moderate, and severity of the outcome (secret share recovery) is high. Medium–High.

### Recommendation
- Delete or single-shot the cached seed: after `share_internal` runs `sign`, overwrite/remove `CachedPreprocesses[context]` so `complete()` cannot silently re-sign; persist the produced `AlgorithmSignatureMachine` (or the share) instead of re-deriving it.
- Bind the cached entry to the message: store `hash(set_keys_message)` alongside the seed and abort if a later call under the same context presents a different `key_pair`.
- Implement the noted TODO: verify our published preprocess commitments on-chain match the commitments regenerated from the cached seed before publishing any share.

### Proof of Concept
Sketch (requires coordinator-level harness):

1. Set up a `DkgConfirmer` with `attempt = 0`; call `share(preprocesses, key_pair_a)` — publishes share `s_a` computed with nonces `(d, e)` derived from the cached `ChaCha20Rng` seed.
2. Simulate interruption (drop the `SigningProtocol`; the DB `CachedPreprocesses` entry persists — observe `CachedPreprocesses::get` returning the same seed).
3. Call `complete(preprocesses, key_pair_b, shares)` with `key_pair_b != key_pair_a` (no equality check exists at line 306–323). `share_internal` regenerates identical `(d, e)`; the new `set_keys_message` yields challenge `c_b ≠ c_a`; a share `s_b` is produced/published.
4. From `s_a, s_b`, the public binding factor `ρ` and Lagrange coefficient `λ`: solve for the nonce contribution and recover `x = (s_a − s_b − ρ·e·(c_a−c_b)…) / λ` per the standard Schnorr nonce-reuse equation, obtaining the validator's Ristretto secret share. Verify `G·x` equals the validator's public key from `spec.validators()`.

Caveat: I confirmed the seed is never deleted and that `complete` re-executes `sign`, but could not fully trace every call site that supplies `key_pair`, so the divergent-message precondition is argued from the API shape (independently supplied argument, unchecked) rather than demonstrated at a concrete production call site.
