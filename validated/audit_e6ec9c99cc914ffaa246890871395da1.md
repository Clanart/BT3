### Title
`ReceivedOutput::read` accepts an attacker-chosen spend offset without binding it to the output's script, reporting unspendable funds as received - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the CrateDB `COPY FROM` flaw — where an attacker-chosen *path* selects which bytes are read and returned as if authentic — `ReceivedOutput::read` lets an attacker-chosen *offset* select which spend key is claimed for an output. The deserializer reconstructs a `ReceivedOutput` (the type the scanner uses to report spendable funds) from untrusted bytes with no check that the embedded `offset` actually derives the `script_pubkey` of the embedded `TxOut`. The offset↔script invariant is only established inside `Scanner::scan_transaction`, never in the type itself or its deserializer, so deserializing untrusted bytes bypasses the only consistency enforcement.

### Finding Description
`ReceivedOutput` has three fields: `offset` (the scalar added to the group key to obtain the spendable key), `output` (the `TxOut`), and `outpoint` (`networks/bitcoin/src/wallet/mod.rs:90-97`). It is only produced legitimately by `Scanner::scan_transaction`, which looks up `output.script_pubkey` in `self.scripts` — a map built by `register_offset`/`Scanner::new` so that the returned `offset` is guaranteed to satisfy `key + G*offset` → the output's P2TR script (`mod.rs:199-213`).

`ReceivedOutput::read` (`mod.rs:122-134`) deserializes `offset` via `Secp256k1::read_F` and then consensus-decodes an arbitrary `TxOut` and `OutPoint`:

```rust
// networks/bitcoin/src/wallet/mod.rs:122-134
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
    let offset = Secp256k1::read_F(r)?;
    let output;
    let outpoint;
    {
      let mut buf_r = BufReader::with_capacity(0, r);
      output = TxOut::consensus_decode(&mut buf_r)...;
      outpoint = OutPoint::consensus_decode(&mut buf_r)...;
    }
    Ok(ReceivedOutput { offset, output, outpoint })
}
```

There is no `key` field in `ReceivedOutput`, and no verification that `p2tr_script_buf(key + G*offset) == output.script_pubkey`. Any byte string of the form `scalar || TxOut || OutPoint` yields a structurally valid `ReceivedOutput` claiming to be spendable under `key + offset`, even when the chosen `offset` does not correspond to the script — or when the `outpoint` references no real on-chain output at all.

### Impact Explanation
An unprivileged party supplying untrusted bytes to `ReceivedOutput::read` can cause a downstream consumer (e.g., `SignableTransaction`/wallet code that spends via `output.offset()`) to treat a fabricated `ReceivedOutput` as spendable balance:

- Funds reported received that are not spendable: an output is recorded with an `offset` that does not derive its `script_pubkey`, so the threshold signature produced for `key + offset` cannot satisfy the output's key-path spend.
- Alternatively, the `offset` can be chosen so `key + G*offset` equals an attacker-benefiting address association, or the `outpoint` can point at a non-existent/double-counted UTXO, inflating perceived balance.

This mirrors the advisory: a low-privilege attacker controls a selector (file path there; scalar offset + raw TxOut here) that determines what data is trusted and disclosed/acted upon, with the system never validating the selector against the resource it claims to reference.

### Likelihood Explanation
`ReceivedOutput::read` is a public deserialization entry point listed as reachable for untrusted bytes, and `ReceivedOutput::serialize`/`read` round-tripping is exercised in tests (`networks/bitcoin/tests/wallet.rs:73,252`), indicating values of this type cross trust boundaries (storage, transport between components). Any such boundary where the bytes are not fully trusted converts into the misreporting above. Severity is Medium: it corrupts the wallet's view of received/spendable funds but does not directly leak key material.

### Recommendation
Either bind the spend key into the type or verify on deserialization:

1. Include the base `key` (or re-derive it from context) and, in `ReceivedOutput::read`, recompute `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)` and reject bytes where it does not equal `output.script_pubkey`; or
2. Store/serialize the script-derived index and recompute `offset` at read time rather than trusting a serialized scalar; and
3. Document that a `ReceivedOutput` obtained from `read` is unauthenticated unless the key↔offset↔script relation is checked.

### Proof of Concept
```rust
// Conceptual: craft bytes claiming an output is spendable under a chosen offset
use bitcoin::{TxOut, OutPoint, Amount, ScriptBuf, consensus::serialize};
use bitcoin_serai::wallet::ReceivedOutput;
use k256::{ProjectivePoint, Scalar};

// Attacker picks an offset that does NOT map to any registered script
let forged_offset = Scalar::from(0xdeadbeefu64);
let mut bytes = forged_offset.to_bytes().to_vec();
// Arbitrary TxOut / OutPoint never sent to the multisig's script
bytes.extend(serialize(&TxOut { value: Amount::from_sat(1_000_000),
                                script_pubkey: ScriptBuf::new() }));
bytes.extend(serialize(&OutPoint::null()));

let claimed = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
// claimed.offset() == forged_offset; claimed is accepted as a spendable output,
// but key + G*forged_offset does not control the script_pubkey —
// the reported funds are not spendable by the multisig.
```
