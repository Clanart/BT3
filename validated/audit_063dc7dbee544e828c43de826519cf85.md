### Title
Partial-commit line selection is re-applied against a freshly re-read diff, allowing external file changes between review and commit to silently stage unreviewed content - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets a user review a diff, select a subset of lines/hunks (a `DiffSelection`), and commit only that subset. The selection is stored as a set of *line indices* into the diff object the user was shown. However, when the commit is actually staged, `applyPatchToIndex` does not reuse that reviewed diff object — it re-reads the working directory diff from disk at staging time and replays the previously captured line indices against it.

### Finding Description
`stageFiles` → `applyPatchToIndex` is the code path that turns a `WorkingDirectoryFileChange` (which carries a `DiffSelection` computed against whatever diff the UI last rendered) into a real `git apply --cached` patch: [1](#0-0) 

```
const applyArgs: string[] = [...'apply', '--cached', ...]
const diff = await getWorkingDirectoryDiff(repository, file)
```

The diff used to build the patch is fetched **fresh, at commit time**, not the diff instance the user actually looked at when making line selections in the UI. The patch builder then walks this newly-fetched diff and asks `file.selection.isSelected(absoluteIndex)` for each line: [2](#0-1) 

`DiffSelection.isSelected` only knows about numeric line indices — it has no way to verify that the diff it is being applied to is the same diff the indices were computed from. If the file's content or hunk boundaries changed between the moment the user made their selection and the moment `createCommit` → `stageFiles` → `applyPatchToIndex` runs, the same numeric index now refers to a **different line**. This is a classic snapshot/reuse (TOCTOU) mismatch — conceptually identical to the Hyperdrive bug's root cause: a value (`dz`/line index) computed against state at time T0 (`c0`/original diff) is blindly reused against state at time T1 (`c'`/re-fetched diff), producing a result the two computations never actually agreed on.

`createCommit` itself does nothing to detect this: it unconditionally calls `unstageAll` then `stageFiles` with whatever `WorkingDirectoryFileChange[]` (and stale selections) were handed to it: [3](#0-2) 

There is no re-validation that the file's on-disk diff still matches the diff the selection was derived from, and no diff/hash comparison guard anywhere in the commit path (confirmed by the absence of any staleness check in `app-store.ts`'s commit flow or in `apply.ts`/`update-index.ts`).

### Impact Explanation
This can cause **silent corruption of what the user actually commits and pushes** — one of the explicitly valid impact classes for this analysis. A user who intentionally deselects certain lines (e.g., to exclude a hardcoded secret, a debug statement, or unrelated unrelated changes) can end up committing exactly the lines they thought they excluded, or omitting lines they thought they included, without any warning, if the working tree file is modified between diff review and clicking "Commit." Because the mismatch is silent (no error, no diff mismatch warning), the resulting bad commit can be pushed before the user notices, and if the excluded content was sensitive, it results in unintended disclosure; if intended content was dropped, it silently breaks the commit.

### Likelihood Explanation
Desktop is a long-lived, event-driven Electron app where multiple asynchronous triggers can rewrite working directory content while a commit dialog with a partial selection is open: background auto-fetch followed by `fastForwardBranches`, external tools/build watchers, IDE format-on-save, or another process (a script from a freshly cloned/untrusted repository, e.g. a package.json script, editor task, or filter/build tool the user runs against the repo) modifying tracked files. None of this requires local/physical access or admin rights — only that the working directory content changes during the window between diff render and commit, which is entirely plausible in normal usage of a hostile or "actively-modifying" repository setup. The severity is bounded by the fact that it requires a real-world race window and is more reliably reproduced with a deliberately-crafted repo/tooling than with a pure network attacker, so likelihood is moderate rather than trivial.

### Recommendation
Before calling `applyPatchToIndex`, re-diff the file and compare it (e.g., by hash of the diff/hunk text or `unifiedDiffStart`/`unifiedDiffEnd` boundaries) against the diff the `DiffSelection` was computed from; if they differ, abort staging that file and prompt the user to re-review the diff rather than silently re-applying stale line indices to new content. Alternatively, capture and pass through the exact diff object the user selected against (rather than re-fetching from disk at staging time), and only fall back to a fresh diff fetch if the working tree is confirmed unchanged (e.g., via `mtime`/blob hash comparison).

### Proof of Concept
Conceptual reproduction (cannot be executed here, but demonstrates the exact code path):
1. Modify `modified-file.md`, open Desktop, view the diff, and deselect a specific line/hunk in the Changes view — this creates a `WorkingDirectoryFileChange` with a `DiffSelection` bound to line indices of the *current* diff (see test at [4](#0-3) , which manually constructs a selection from `diff.hunks[0].unifiedDiffStart`).
2. Before clicking "Commit," modify the same file externally (e.g. a background script appends/removes a line above the hunk the user deselected), shifting all subsequent line offsets.
3. Click "Commit." `createCommit` calls `stageFiles` → `applyPatchToIndex`, which calls `getWorkingDirectoryDiff` again (`app/src/lib/git/apply.ts:60`) and reapplies the *original* selection's indices to the *new* diff via `formatPatch` (`app/src/lib/patch-formatter.ts:143-171`).
4. Because the hunk boundaries shifted, the line the user meant to exclude/include no longer aligns with the same index, so the actual committed patch differs from what the user intended and reviewed, with no warning surfaced.
