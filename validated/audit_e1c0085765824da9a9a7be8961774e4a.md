### Title
Stale line-selection state reapplied to a freshly re-fetched diff in `applyPatchToIndex` silently corrupts partially-staged commits - (File: `app/src/lib/git/apply.ts`)

### Summary
This mirrors the `InvariantLib` bug class: one code path (the UI) computes a security/integrity-relevant decision (`file.selection`, which lines the user picked to include in a partial commit) against one snapshot of the diff, while a second, independent code path (`applyPatchToIndex`) re-fetches a *different* snapshot of the same file's diff and blindly reapplies the old selection indices to it. Exactly like using `currentPosition` in one check and `latestPosition` in another, the two "snapshots" (the diff the user reviewed vs. the diff actually used to build the patch) can disagree, and there is no re-validation that the selection is still meaningful for the new diff.

### Finding Description
`applyPatchToIndex` re-fetches the working directory diff for the file being staged, independently of whatever diff was used to build the `WorkingDirectoryFileChange.selection` the user interacted with in the UI: [1](#0-0) 

That freshly fetched `diff` is then handed to `formatPatch(file, diff)`, which walks the **new** diff's hunks/lines and, for every non-context line, asks the **old** selection object whether the line at that absolute index is selected: [2](#0-1) 

`DiffSelection.isSelected(absoluteIndex)` has no knowledge of *which* diff produced that index — it is just a bitset keyed by line offset. If the file changes on disk between the moment the user made their line selections (against diff snapshot A) and the moment `applyPatchToIndex` is invoked at commit time (which independently fetches diff snapshot B), the hunk boundaries/line offsets in B can differ from A. The stale `file.selection` bitmap is then matched against the wrong absolute indices in B, so `isSelected()` returns selection decisions for lines that are not the ones the user actually toggled.

The app is aware that diffs can go stale relative to selection state — `updateChangesWorkingDirectoryDiff` explicitly reconciles `selectableLines` when the *displayed* diff is refreshed: [3](#0-2) 

But that reconciliation only happens for the diff shown while browsing changes; it is not re-run immediately before `stageFiles` → `applyPatchToIndex` performs its own independent `getWorkingDirectoryDiff` call at staging time: [4](#0-3) 

There is no code path that guarantees the diff consumed by `formatPatch` inside `applyPatchToIndex` is the same diff the reconciliation logic last validated the selection against. The only safety net (`formatPatch`'s "no changes" check) only catches the degenerate empty-patch case, not misaligned-but-non-empty patches: [5](#0-4) 

### Impact Explanation
If the working tree file is modified between when the user reviews/selects lines and when `applyPatchToIndex` runs (e.g. content rewritten by a build step, a git `smudge`/`clean` filter, a `post-checkout`/`pre-commit` hook shipped in a cloned repository, or any tool the repository configures to run on file save/checkout), the partial-commit patch built by `formatPatch` can silently stage lines the user never selected, or omit lines they did select — with no error surfaced to the user, since the only failure mode checked for is an empty patch. This is a "silent corruption of what the user commits" scenario: a cloned/fetched repository that ships filters or hooks that rewrite tracked files shortly after checkout can cause a user's careful partial-commit line selection to no longer correspond to what actually gets committed and pushed.

### Likelihood Explanation
Requires only content shipped in a cloned/fetched repository (e.g. a `.gitattributes` filter driver or a git hook) that rewrites a file's content around the time the user is staging a partial commit — no local/physical access, no elevated privileges, and no unnatural user steps beyond the ordinary "select some lines, then commit" workflow that Desktop explicitly supports. The window is realistic because staging happens as a separate, later step from diff review, and `applyPatchToIndex`'s diff fetch is decoupled in time from the UI's own diff-refresh/selection-reconciliation pass.

### Recommendation
`applyPatchToIndex` should not trust a `file.selection` computed against an unknown, possibly-earlier diff snapshot. Before formatting the patch, re-validate (or re-derive) the selection against the exact diff object it is about to use — e.g. by comparing a content/hash fingerprint of the diff used to build the selection with the freshly fetched diff, and aborting/re-prompting the user if they differ, rather than reusing raw line-offset indices across two independently-fetched diffs.

### Proof of Concept
Conceptual reproduction (exact repro would require a Devin session with terminal access, which is outside the scope of this ask-only analysis):
1. Open a repository in Desktop and modify a tracked file so it has multiple hunks.
2. In the Changes view, partially select a subset of lines from one hunk (leaving `file.selection` bound to the current diff's line offsets).
3. Before clicking "Commit", have an external process (simulating a repository-shipped git filter/hook) append/remove lines earlier in the file so hunk boundaries shift.
4. Click "Commit". `stageFiles` → `applyPatchToIndex` re-fetches the diff (now with shifted hunks) but reuses the old `file.selection` bitmap; `formatPatch` will include/exclude lines at the old absolute indices, which now correspond to different lines than what the user selected.
5. Inspect the resulting commit: it will contain lines the user did not intend to stage, or omit lines they did select, with no warning from Desktop.
