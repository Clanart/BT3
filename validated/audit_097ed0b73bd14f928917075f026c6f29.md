### Title
Line-Index (not content) based Diff Selection is silently reapplied to a regenerated diff, causing unintended lines to be committed - ([File: app/src/lib/git/apply.ts])

### Summary
This is a Desktop analog of the Compound `maxClose` bug: the audit finding is that a security-relevant check is computed against a **stale snapshot** (`borrowBalance.amount`) instead of the value that is actually acted upon (`borrowedAmount`), so the two get silently out of sync. In GitHub Desktop, the analogous stale/fresh mismatch happens in the partial-commit path: the user's line selection (`DiffSelection`) is captured against one diff snapshot, but at staging time a **brand-new diff is fetched** and the *old* selection indices are blindly reapplied to it, with no verification that line *content* — only line *position* — still matches.

### Finding Description
`DiffSelection` tracks selected lines purely as a `Set<number>` of `absoluteIndex` positions (`hunk.unifiedDiffStart + lineIndex`), with no binding to the actual line text, a diff hash, or a version token: [1](#0-0) [2](#0-1) 

When a partial commit is staged, `applyPatchToIndex` re-fetches a *fresh* diff of the file right before building the patch: [3](#0-2) 

and then `formatPatch` decides what to include purely by checking `file.selection.isSelected(absoluteIndex)` against that fresh diff — line index in, boolean out, no content comparison: [4](#0-3) 

The application is aware that diffs can drift out from under a selection — the comment in `app-store.ts` explicitly says so — but the "fix" only prunes/keeps indices based on whether the *position* is still an includeable diff line (`line.isIncludeableLine()`), not whether it's the *same* logical change: [5](#0-4) 

This reconciliation only runs inside `updateChangesWorkingDirectoryDiff`, which is itself debounced/async and only fires while a single file is selected in the Changes view: [6](#0-5) 

`_commitIncludedChanges` then takes whatever `file.selection` currently sits in the in-memory `workingDirectory` state and hands it straight to `createCommit`/`stageFiles`/`applyPatchToIndex`, without re-diffing to confirm the selection still maps onto the same content it did when the user made it: [7](#0-6) [8](#0-7) 

**Broken invariant:** the guard that is supposed to keep "what the user selected" aligned with "what actually gets committed" is index-based, not content-based, and the only reconciliation pass (`withSelectableLines`) only prunes lines that became context/non-includeable — it does **not** detect the case where a line at the *same index* is still includeable but is now a *different* line because content shifted above it (e.g., a hook, filter, watcher, or concurrent process inserted/removed lines earlier in the file between the time the user selected lines in the diff viewer and the time they clicked Commit). In that case `isSelected(absoluteIndex)` happily returns `true`/`false` for the wrong physical line, and `applyPatchToIndex`'s freshly-fetched diff (line.ts:60 in apply.ts) will faithfully stage whatever line now sits at that index.

### Impact Explanation
This causes **silent corruption of what the user commits** — an explicitly listed valid impact category. A user could:
- Believe they excluded a sensitive/unfinished line, but because content shifted, an unrelated (or attacker-inserted) line at the same index gets staged and committed instead.
- Believe they included a specific fix, but a different line ends up in the commit, while Desktop reports success with no warning.

Because the repository content itself can drive this (e.g., through a git filter/hook/build script that runs on checkout of an attacker-authored, cloned/fetched repository — an allowed attacker primitive per the report's valid-impact criteria), this is not merely a cosmetic UI bug: it can result in unintended code being committed and later pushed, silently, without any diff review actually matching the pushed content.

### Likelihood Explanation
Moderate-to-low but realistic. It requires:
1. The user to open a file's diff, make a partial line selection, and leave the Changes view open/committing while the underlying working-tree file is mutated by an external process (build watcher, git smudge filter, hook script bundled in a cloned/fetched repository) between selection and commit.
2. The mutation to shift line positions (insert/remove lines) rather than only change content at the same line — this is a very common effect of code formatters, template engines, filters, or generated file regeneration, all of which are common in real developer workflows and easily bundled into a malicious repository (e.g., committed `.gitattributes` filter driver, `husky`/`lint-staged` pre-commit hooks, or an npm `postinstall`/`watch` script that a normal `git clone && npm install && npm run dev` workflow would run naturally, no unusual user action required).
3. Desktop's async, debounced diff refresh to not have caught up before the user clicks Commit — plausible on larger repos or slower machines, and the existing mitigation in `app-store.ts` (lines 3478-3497) does not close the gap because it only removes lines that stopped being includeable, not lines whose identity shifted.

### Recommendation
- Bind `DiffSelection` (or the diff snapshot used to build it) to a content-derived identity, e.g. store the selected line's own text/hash alongside its index, or store a diff/version token (e.g., blob SHA of old/new content) and invalidate/re-map the whole selection whenever that token changes, rather than only pruning by position/includeability.
- In `_commitIncludedChanges` / `stageFiles` / `applyPatchToIndex`, re-diff and re-validate that the selection still corresponds to the exact same hunks/lines (e.g., compare against a hash of the diff that was current when the selection was captured) immediately before staging, and abort/re-prompt the user if the underlying diff changed since selection.
- Surface a hard warning ("The file changed since you reviewed this diff — please re-review before committing") instead of silently proceeding with a positionally-reapplied selection.

### Proof of Concept
1. Clone a malicious/attacker-authored repository containing a modified file and a hook/filter/build script (e.g., a `pre-commit`/`post-checkout` hook or an npm `watch` script) that inserts N new lines near the top of a tracked file when triggered.
2. In GitHub Desktop, open the Changes view for that file and select only specific lines near the bottom of the diff for partial commit (`DiffSelection.withRangeSelection`), leaving the commit dialog open.
3. Trigger the external script (simulating a natural developer action like running `npm run dev`, or a hook firing on an unrelated `git` operation from another terminal) so that it inserts lines earlier in the file, shifting all subsequent line indices down by N, before Desktop's async diff refresh (`updateChangesWorkingDirectoryDiff`) completes and reconciles the selection.
4. Click "Commit". `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches the new diff; `formatPatch` (`app/src/lib/patch-formatter.ts:157`) reapplies the old `absoluteIndex`-based selection to it.
5. Inspect the resulting commit: it contains different line content than what was visually highlighted/selected by the user at selection time, while Desktop reports a normal successful commit — demonstrating silent corruption of the committed content.

      return !lineIsDivergent
    } else if (this.defaultSelectionType === DiffSelectionType.None) {
      return lineIsDivergent
