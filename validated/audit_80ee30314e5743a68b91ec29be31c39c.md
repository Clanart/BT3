### Title
Unsafe `uint128` truncation in `UniV4UniswapV2Wrapper.swapETHForExactTokens` desyncs actual fee-token custody from `IntentGatewayV2` escrow accounting, enabling fee-pool drain - (File: `evm/src/utils/uniswapv2/UniV4UniswapV2Wrapper.sol`)

### Summary
`IntentGatewayV2.placeOrder` swaps user-supplied `order.fees` (a `uint256`, fully attacker-controlled) into fee tokens via `UniV4UniswapV2Wrapper.swapETHForExactTokens`. Internally the wrapper silently truncates the requested output amount to `uint128` before it is actually used to size the router swap, but it returns the **original, untruncated** `uint256` value as `amounts[1]`. `IntentGatewayV2` ignores this discrepancy and stores the full, untruncated `order.fees` value into the shared `_orders[commitment][TRANSACTION_FEES]` escrow slot, even though the real number of fee tokens pulled into the contract equals only `uint128(order.fees)`. This is the same class of bug as the referenced H-05 report: an unchecked downcast to `uint128` on a value used to compute how much value is actually transferred, while a separate, uncast value is trusted for accounting — creating a liability that is not backed by real assets.

### Finding Description
In `evm/src/utils/uniswapv2/UniV4UniswapV2Wrapper.sol`: [1](#0-0) 


`amountOut` is truncated to `uint128` **only** for the actual V4 swap call, so the router will only ever attempt to buy `uint128(amountOut)` tokens (wrapping around if `amountOut > type(uint128).max`). Yet the function tells its caller that the full `amountOut` (untruncated `uint256`) was obtained.

`IntentGatewayV2.placeOrder` consumes this return value naively: [2](#0-1) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        ...
        uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
        msgValue -= amounts[0];
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);

    _orders[commitment][TRANSACTION_FEES] = order.fees;   // <-- stores the full, untruncated order.fees
}
```

If an attacker sets `order.fees = (1 << 128) + K` for a small `K`, the wrapper's underlying swap only actually acquires `K` fee tokens for the gateway (because the real router call used `uint128(amountOut) = K`), but `_orders[commitment][TRANSACTION_FEES]` is credited with the full `(1 << 128) + K`. `TRANSACTION_FEES` funds are drawn from the gateway's shared `feeToken` balance — the same pool that legitimately backs every other order's escrowed transaction fee.

When this attacker's order is later filled/redeemed, `withdraw()` transfers the recorded fee amount out of the shared pool: [3](#0-2) 

```solidity
if (finalize) {
    uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
    if (fees > 0) {
        delete _orders[body.commitment][TRANSACTION_FEES];
        IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
    }
```

`fees` here is the attacker's inflated, untruncated `order.fees`, far larger than the `K` tokens actually deposited for that order. `safeTransfer` will succeed as long as the gateway's aggregate `feeToken` balance (funded by all other users' real fee escrows) is large enough — draining funds that belong to unrelated orders.

### Impact Explanation
This directly matches the "stealing or loss of funds" / "wrong beneficiary or amount" bounty class. The attacker deposits real value for only `K` fee tokens but is credited an escrow entitlement of `(1<<128)+K`, redeemable against the gateway's pooled `feeToken` balance that other users' orders rely on. On fill/redemption, the discrepancy is paid out of the shared pool, draining legitimately escrowed transaction fees belonging to other orders and potentially reverting or starving their later redemptions.

### Likelihood Explanation
The path is reachable by any unprivileged user through the public `placeOrder` entrypoint by simply choosing an `order.fees` value greater than `type(uint128).max` (achievable since `order.fees` is a plain `uint256` field with no upper-bound validation) and paying with native ETH (`msgValue > 0` branch, which routes through the vulnerable wrapper). No relayer, prover, or admin cooperation is required — it is a pure application-layer accounting bug exploitable by a single malicious order placement plus a subsequent fill/redeem.

### Recommendation
- In `UniV4UniswapV2Wrapper.swapETHForExactTokens`/`swapExactTokensForETH`/`getAmountsIn`/`getAmountsOut`, revert (e.g. via OpenZeppelin `SafeCast.toUint128`) instead of silently truncating `amountOut`/`amountIn`/`amountOutMin` when they exceed `type(uint128).max`.
- In `IntentGatewayV2.placeOrder`, never trust the caller-supplied `order.fees` for escrow bookkeeping directly; instead record the *actual* fee-token balance delta received by the contract (as is already correctly done for `order.inputs` via before/after balance checks), mirroring the pattern used at `evm/src/apps/IntentGatewayV2.sol:260-297`.
- Add an explicit upper bound check on `order.fees` (and any other externally supplied amount routed through `uint128`-based interfaces) at order placement.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.fees = (1 << 128) + 1000` and sends `msg.value` sized to cover a swap for `1000` fee tokens (the truncated `uint128` amount), targeting a destination requiring a native-ETH fee-token swap path (`msgValue > 0` branch).
2. `UniV4UniswapV2Wrapper.swapETHForExactTokens(order.fees, ...)` truncates internally to `uint128(order.fees) = 1000`, executes a real swap for `1000` fee tokens, and returns `amounts[1] = order.fees` (the full `(1<<128)+1000` value) — `amounts[0]` reflects only the ETH actually spent for `1000` tokens.
3. `IntentGatewayV2` sets `_orders[commitment][TRANSACTION_FEES] = order.fees = (1<<128)+1000`, while only `1000` real fee tokens were pulled into the contract.
4. The attacker (or a colluding solver) fills/cancels the order to trigger `withdraw()`, which calls `feeToken.safeTransfer(beneficiary, (1<<128)+1000)`. If the gateway's aggregate `feeToken` balance (funded by other users' legitimate fee escrows) is at least this large, the transfer succeeds, draining fee tokens belonging to other orders to the attacker's beneficiary.

```text
    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory amounts)
    {
        PoolKey memory poolKey = _createPoolKey(path[1]);

        bytes[] memory params = new bytes[](3);
        params[0] = abi.encode(poolKey, true, uint128(amountOut), uint128(msg.value), bytes(""));
        params[1] = abi.encode(poolKey.currency0, uint256(0), false);
        params[2] = abi.encode(poolKey.currency1, recipient, amountOut);

        bytes[] memory inputs = new bytes[](1);
        inputs[0] = abi.encode(
            abi.encodePacked(uint8(Actions.SWAP_EXACT_OUT_SINGLE), uint8(Actions.SETTLE), uint8(Actions.TAKE)), params
        );

        // Snapshot standing balance (excluding inbound msg.value) so the refund is the swap-call delta only,
        // immune to any ETH that lands on the wrapper from outside the router (e.g., selfdestruct, coinbase).
        uint256 balanceBefore = address(this).balance - msg.value;

        IUniversalRouter(_params.universalRouter).execute{value: msg.value}(
            abi.encodePacked(bytes1(uint8(Commands.V4_SWAP))), inputs, deadline
        );

        uint256 refundETH = address(this).balance - balanceBefore;

        if (refundETH > 0) {
            (bool success,) = msg.sender.call{value: refundETH}("");
            require(success, "ETH refund failed");
        }

        amounts = new uint256[](2);
        amounts[0] = msg.value - refundETH;
        amounts[1] = amountOut;
    }
```
