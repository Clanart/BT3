The BIP-340 Hram panic on identity points is a promising lead. Let me check the signing path and whether identity commitments are filtered.### Title
Identity group key / nonce sum crashes Bitcoin FROST signing via panic in `x()` ("point at infinity") - (networks/bitcoin/src/crypto.rs)

### Summary
`bitcoin_serai`'s BIP-340 `Hram` and the `x()`/`x_only()`/`needs_negation()` helpers panic unconditionally when given the point at infinity. Neither `ThresholdKeys::read`/`ThresholdKeys::new` nor `Commitments::read`/`read_G` reject the identity element, so attacker-controlled bytes that deserialize to an identity group key (or preprocesses that produce an identity nonce sum) turn the next `sign_share`/`verify` call into an unrecoverable panic — a complete, repeatable crash of the signer, analogous to CVE-2022-21515's remotely-triggerable hang/crash class.

### Finding Description
`x()` extracts the x-coordinate of a `ProjectivePoint` and `expect`s it to be non-infinity, and `Hram::hram` calls `x(R)` and `x(A)` where `A` is the group key and `R` is the aggregated nonce sum [1](#0-0) [2](#0-1) . The `Schnorr` algorithm wrapper itself documents that it "may panic if called with nonces/a group key which are the point at infinity" [3](#0-2) .

On the input side, `Ciphersuite::read_G` only enforces canonicality — it accepts the identity encoding (e.g., the 32 zero bytes canonical encoding of identity for dalek-ff-group points) [4](#0-3) . `ThresholdKeys::read` reads `n` verification shares straight from the byte stream and passes them to `ThresholdKeys::new` [5](#0-4) , and `ThresholdKeys::new` sums `verification_shares[i] * interpolation_factor` into `group_key` without any identity check on the shares or the result [6](#0-5) . Likewise, nonce commitments arriving through `read_preprocess`/`Commitments::read`/`GeneratorCommitments::read` are accepted unchecked and summed into the session nonce by `BindingFactor::nonces` [7](#0-6) [8](#0-7) . During signing, `sign` computes `Rs = B.nonces(...)` and passes them to `A::sign_share`, which invokes `Hram::hram(Rs[0][0], group_key, msg)` [9](#0-8) , hitting the `expect("point at infinity")` panic.

### Impact Explanation
A panic inside `Hram::hram` is an unhandled abort of the signing operation. In the processor deployment, panicking tasks take down the signing flow (the codebase even installs panic hooks that kill the whole process on task panics elsewhere). An unprivileged party that can feed untrusted bytes to `ThresholdKeys::read` (a listed untrusted-read surface) producing an identity `group_key` — e.g., all-identity verification shares under Lagrange interpolation, which always interpolates to identity — permanently DoSes every signing attempt using those keys. No secret leakage is required for the impact; availability of the threshold signer is lost, matching the Medium-severity complete-DoS class of the reference CVE.

### Likelihood Explanation
Two trigger paths exist:

1. **Deserialized keys (reliable):** bytes encoding `t = n`, Lagrange interpolation, and `n` identity verification shares pass all checks in `ThresholdKeys::read`/`new` — `ThresholdParams::new` only validates `0 < t <= n` and `i <= n`, and `ThresholdKeys::new` never checks for identity [10](#0-9) [11](#0-10) . Any subsequent `sign_share`/`verify` call panics deterministically.
2. **Malicious preprocess (probabilistic/harder):** forcing the aggregated `R = Σ(D_l + ρ_l·E_l)` to identity is a fixed-point problem since the attacker's own binding factor ρ depends on their commitments, making it generally infeasible — but the same panic exists for per-party bound nonces consumed by `verify_share`, and the deserialized-key path above needs no grinding.

The likelihood hinges on whether untrusted parties can supply `ThresholdKeys` encodings or malformed preprocesses in the deployment; per the engagement scope these reads are treated as untrusted-input surfaces.

### Recommendation
- Reject the identity element in `read_G` (or at minimum in `GeneratorCommitments::read`, `ThresholdKeys::new`, and `Commitments::read`), since an identity verification share, nonce commitment, or group key is never valid in this protocol.
- Make `x()`, `x_only()`, and `Hram::hram` return `Option`/`Result` instead of panicking, and propagate a `FrostError`/`InvalidShare` through `sign_share` and `verify`.
- As defense in depth, have `AlgorithmSignatureMachine::complete` treat an identity aggregate `R` as `FrostError::InvalidShare` of the responsible participant rather than allowing the panic.

// Build a ThresholdKeys blob with n identity verification shares.
let n: u16 = 3; let t: u16 = 3;
let mut bytes = vec![];
bytes.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
bytes.extend(C::ID);
bytes.extend(t.to_le_bytes());              // t
bytes.extend(n.to_le_bytes());              // n
bytes.extend(1u16.to_le_bytes());           // i = 1
bytes.push(1);                              // Interpolation::Lagrange
bytes.extend(C::F::ZERO.to_repr().as_ref()); // secret_share
for _ in 0 .. n {
  bytes.extend(C::G::identity().to_bytes().as_ref()); // identity shares accepted by read_G
}
let keys = ThresholdKeys::<C>::read::<&[u8]>(&mut bytes.as_ref()).unwrap();
assert_eq!(keys.group_key(), C::G::identity()); // no rejection

//   .0.sign(preprocesses, b"msg")  -> panic

  fn read_G<R: Read>(reader: &mut R) -> io::Result<Self::G> {
    let mut encoding = <Self::G as GroupEncoding>::Repr::default();
