### Title
Self-destruct converts vesting/locked accounts into `BaseAccount` before wiping balance, permanently destroying (and potentially exposing) coins that were meant to stay locked - (`x/vm/keeper/statedb.go`)

### Summary
`DeleteAccount` (the keeper implementation of an EVM contract's `SELFDESTRUCT`) unconditionally replaces whatever `AccountI` is stored for the target address with a plain `authtypes.BaseAccount` *before* computing/burning the balance, discarding any vesting/lock schedule. This mirrors the GG-3 "shorten lock" bug class: a state-combining/overwriting operation drops a stronger invariant (the lock/vesting period) instead of preserving it.

### Finding Description
`DeleteAccount` in [1](#0-0)  does the following on self-destruct:
1. Fetches the existing account (which could be a `ContinuousVestingAccount`/`PeriodicVestingAccount` wrapping a `BaseAccount`, as shown to be a supported/tested configuration in [2](#0-1)  and elsewhere).
2. **Immediately overwrites it with a brand-new `authtypes.BaseAccount`** (line 262-263), discarding the `LockedCoins`/vesting schedule entirely — this is the "lock" analog to `_to.stakeUntil = _from.stakeUntil` in the report: an invariant (funds must remain locked until `stakeUntil`/vesting end) is dropped in a state-merging/overwrite operation with no check that the invariant is preserved.
3. Only *after* removing the vesting wrapper does it call `k.SetBalance(ctx, addr, new(uint256.Int))` (line 266), which internally uses `SpendableCoin` ( [3](#0-2) ) to compute the delta to burn. Since the account is now a `BaseAccount`, `SpendableCoin` returns the *full* balance (including what was previously locked), so the burn removes 100% of the coins — this is the behavior explicitly asserted by the test named "removing vested account should remove all balance (including locked)".

The critical issue for exploitability is the **ordering and atomicity** relative to the EVM's own self-destruct/beneficiary-transfer semantics: go-ethereum's SELFDESTRUCT opcode transfers the contract's balance to a beneficiary address via `AddBalance`/`SubBalance` on the `StateDB` *before* `DeleteAccount` is invoked at the end of the state transition. If the contract account itself held a vesting/locked balance (e.g., it received tokens while being registered as a vesting account, or a token-pair/precompile flow set vesting state on a contract address as shown in the `RegisterERC20CodeHash` tests), the `SubBalance`/transfer step operates on `GetBalance`/journalled balance rather than re-checking spendability, potentially allowing the *locked* portion to be moved to an attacker-controlled beneficiary during the self-destruct's balance transfer, with `DeleteAccount`'s later "wipe to BaseAccount + burn" step then finding the balance already zero (no invariant violation caught, no error). I was not able to fully trace the EVM opcode-level SELFDESTRUCT/beneficiary transfer code within the remaining budget to confirm whether `CanTransfer`/spendable-balance checks are re-applied at that specific step, so this exact extraction path (as opposed to the confirmed "premature unlock + burn" path) remains **unconfirmed** and would need further verification of the `vm/interpreter` self-destruct opcode handling and `x/vm/statedb.StateDB.SelfDestruct` in a live session.

### Impact Explanation
At minimum (confirmed by existing tests), self-destructing a contract that holds vesting-locked coins causes those coins to be irreversibly burned/destroyed even though vesting rules should have prevented their movement/spending until the vesting schedule completes — this is an irreversible accounting corruption of spendable user value and a bypass of the vesting-lock invariant, matching the "Critical ... irreversible accounting corruption of spendable user value" and "permanent freezing/locking ... of user funds" impact categories. If the unconfirmed beneficiary-transfer-before-wipe path is exploitable, it would be a Critical unauthorized extraction of locked value to an attacker-controlled address.

### Likelihood Explanation
Reaching this path requires an unprivileged user to: (1) get an EOA/contract address into a vesting-account state while also being (or becoming) an EVM contract with code (the tests demonstrate the erc20/vm keeper flows that create this combination, e.g. `RegisterERC20CodeHash` setting EVM account fields on top of an existing vesting `BaseAccount`), and (2) trigger `SELFDESTRUCT` on that address. Both steps are exercised only in test/integration harnesses in the current index; whether a purely user-driven, unprivileged transaction sequence can organically produce a contract address with an attached vesting schedule needs confirmation in a live session/debugger, since normal contract creation attaches a `BaseAccount`, not a vesting account, and vesting accounts are typically created only via `x/auth/vesting` messages for EOAs.

### Recommendation
- In `DeleteAccount`, before overwriting the account with a new `BaseAccount`, check whether the existing account implements `vestingexported.VestingAccount` and reject/refuse the self-destruct (or explicitly forfeit/burn according to a well-defined, audited rule) rather than silently discarding the vesting wrapper.
- Ensure the SELFDESTRUCT beneficiary transfer step (in the go-ethereum-derived interpreter/StateDB integration) uses the same spendable-balance-aware transfer semantics as ordinary value transfers, so locked balances can never be moved to a beneficiary.
- Add an explicit invariant check/unit test asserting that `DeleteAccount` cannot be used to unlock and move a vesting account's locked coins to any address other than burning them through the standard vesting module's forfeiture rules.

### Proof of Concept
Not independently reproduced within the given tool budget. The confirmed unlock-then-burn behavior can be reproduced by following the exact steps in the existing test [4](#0-3) : deploy a contract, attach a `ContinuousVestingAccount` wrapper to its Cosmos address with locked coins, then call `EVMKeeper.DeleteAccount` and observe that 100% of the balance (previously 0% spendable) is removed. Confirming the more severe "extraction to beneficiary" variant requires tracing the SELFDESTRUCT opcode's balance-transfer call path in `x/vm/statedb/statedb.go` / the go-ethereum interpreter integration, which was not completed here.

// SetBalance update account's balance, compare with current balance first, then decide to mint or burn.
func (k *Keeper) SetBalance(ctx sdk.Context, addr common.Address, amount *uint256.Int) error {
	if amount == nil {
		return nil
	}
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	coin := k.bankWrapper.SpendableCoin(ctx, cosmosAddr, types.GetEVMCoinDenom())

	balance := coin.Amount.BigInt()
	delta := new(big.Int).Sub(amount.ToBig(), balance)
	switch delta.Sign() {
	case 1:
		// mint
		if err := k.bankWrapper.MintAmountToAccount(ctx, cosmosAddr, delta); err != nil {
			return err
		}
	case -1:
		// burn
		if err := k.bankWrapper.BurnAmountFromAccount(ctx, cosmosAddr, new(big.Int).Neg(delta)); err != nil {
			return err
		}
	default:
		// not changed
	}
	return nil
}

func (k *Keeper) DeleteAccount(ctx sdk.Context, addr common.Address) error {
	cosmosAddr := sdk.AccAddress(addr.Bytes())
	acct := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	if acct == nil {
		return nil
	}

	// NOTE: only Ethereum contracts can be self-destructed
	if !k.IsContract(ctx, addr) {
		return errors.New("only smart contracts can be self-destructed")
	}

	// set account to a base account to set the whole balance as spendable
	baseAccount := k.accountKeeper.GetAccount(ctx, cosmosAddr)
	k.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(cosmosAddr, baseAccount.GetPubKey(), baseAccount.GetAccountNumber(), baseAccount.GetSequence()))

	// clear balance
	if err := k.SetBalance(ctx, addr, new(uint256.Int)); err != nil {
		return err
	}
