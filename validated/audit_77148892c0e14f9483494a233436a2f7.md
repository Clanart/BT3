### Title
Zero `header_chain_proof_batch_size` Accepted Without Validation Causes Panic in `prove_if_ready`, Permanently Halting Header Chain Proof Generation and Exposing Operator Collateral to Undefended Watchtower Challenges — (File: `core/src/header_chain_prover.rs`)

---

### Summary

`BridgeConfig` accepts `header_chain_proof_batch_size = 0` without any lower-bound validation. When the `HeaderChainProver` automation task runs with this value, `is_batch_ready()` always returns `true`, `get_next_n_non_proven_block(0)` returns an empty block list, and `prove_if_ready()` panics unconditionally on `.expect("Exists")` against an empty iterator. The header chain prover task dies permanently, the operator can no longer generate the proofs required to disprove watchtower challenges, and the operator's collateral becomes undefended.

---

### Finding Description

`header_chain_proof_batch_size` is declared as a plain `u32` in `BridgeConfig`: [1](#0-0) 

It is parsed from the environment variable `HEADER_CHAIN_PROOF_BATCH_SIZE` with no zero-check: [2](#0-1) 

The value is stored verbatim into `HeaderChainProver.batch_size: u64`: [3](#0-2) 

**Step 1 — `is_batch_ready()` always returns `true` when `batch_size == 0`.**

The readiness check is:

```rust
if tip_height - non_proven_block.2 + 1 >= self.batch_size {
    return Ok(true);
}
``` [4](#0-3) 

With `self.batch_size == 0u64`, the right-hand side is `0`, and any `u64` value satisfies `>= 0`. The function unconditionally returns `Ok(true)`.

**Step 2 — `get_next_n_non_proven_block(0)` returns an empty `Some` instead of `None`.**

`prove_if_ready()` calls: [5](#0-4) 

Inside `get_next_n_non_proven_block`, the SQL query runs with `LIMIT 0`, returning zero rows. The guard `blocks.len() != count as usize` evaluates to `0 != 0` → `false`, so the function returns `Ok(Some((vec![], receipt)))` — an empty block list wrapped in `Some`: [6](#0-5) 

**Step 3 — Unconditional panic on empty iterator.**

Back in `prove_if_ready()`, the `Some` branch is taken (not the `None` early-return), and the code immediately calls:

```rust
let current_block_hash = unproven_blocks.iter().next_back().expect("Exists").0;
``` [7](#0-6) 

`unproven_blocks` is empty; `.next_back()` returns `None`; `.expect("Exists")` **panics**. The automation task terminates. Because `is_batch_ready()` always returns `true` with `batch_size == 0`, every subsequent invocation of the automation loop re-enters `prove_if_ready()` and panics again, making the failure permanent for the lifetime of the process.

---

### Impact Explanation

The header chain proof (HCP) is the operator's primary cryptographic instrument for defending against watchtower challenges in the bridge circuit. Without a live HCP automation task, the operator cannot produce the proof required to disprove a watchtower challenge. An undefended challenge results in the operator's collateral being slashed. The collateral amounts configured in production deployments are material (e.g., `COLLATERAL_FUNDING_AMOUNT=90000000` sats, `OPERATOR_CHALLENGE_AMOUNT=130000000` sats in the regtest Docker config). [8](#0-7) 

---

### Likelihood Explanation

The trigger requires `HEADER_CHAIN_PROOF_BATCH_SIZE=0` to be set in the operator's environment or TOML config. This is a misconfiguration, but the code bug is the absence of a validation guard that would reject it at startup. The default value is `100`, so accidental zero-setting is unlikely in normal operation; however, the missing guard means any operator who sets this value (e.g., during debugging, scripted deployment, or a typo) will silently deploy a broken prover with no startup-time error.

---

### Recommendation

Add a zero-check in `BridgeConfig::from_env()` immediately after parsing `HEADER_CHAIN_PROOF_BATCH_SIZE`:

```rust
let header_chain_proof_batch_size = read_string_from_env_then_parse::<u32>(
    "HEADER_CHAIN_PROOF_BATCH_SIZE",
)?;
if header_chain_proof_batch_size == 0 {
    return Err(BridgeError::ConfigError(
        "HEADER_CHAIN_PROOF_BATCH_SIZE must be greater than zero".to_string(),
    ));
}
```

Apply the same guard in `BridgeConfig::try_parse_from()` / TOML deserialization path. Additionally, add a defensive assertion in `HeaderChainProver::new()`:

```rust
assert!(config.header_chain_proof_batch_size > 0,
    "header_chain_proof_batch_size must be > 0");
```

---

### Proof of Concept

1. Set `HEADER_CHAIN_PROOF_BATCH_SIZE=0` in the operator's environment.
2. Start the operator node. `BridgeConfig::from_env()` parses `0` without error; `HeaderChainProver` is constructed with `batch_size = 0`.
3. The automation loop calls `prove_if_ready()`.
4. `is_batch_ready()` returns `true` (condition `N >= 0` is always satisfied for `u64`).
5. `get_next_n_non_proven_block(0)` issues `LIMIT 0` to the DB, receives zero rows, passes the `blocks.len() != 0` guard, and returns `Some((vec![], receipt))`.
6. `prove_if_ready()` enters the `Some` branch and executes `unproven_blocks.iter().next_back().expect("Exists")` on an empty `Vec` → **thread panics with message "Exists"**.
7. The automation task terminates. Every subsequent invocation repeats steps 3–6 and panics again.
8. No header chain proofs are ever generated. Any watchtower challenge against this operator goes undefended, and the operator's collateral is slashable.
