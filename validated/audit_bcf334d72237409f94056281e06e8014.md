## Finding: Silent ERC-20 transfer failure accepted as success in Tron `IntentGatewayV2` escrow release/sweep, causing fund loss

### Title
Escrow withdrawal and dust-sweep on Tron `IntentGatewayV2` accept a false-returning `transfer()` as success, permanently locking user/solver funds while marking orders settled - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The external GMToken report is a case of code assuming an ERC-20-like call behaves as expected, but the token doesn't actually perform the expected action, causing state to diverge from reality. The exact local analog exists in the Tron variant of the Intent Gateway: `withdraw()` and the `SweepDust` handler in `onAccept()` use raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the **call did not revert** (`success`), never decoding/validating the returned boolean. Tokens that return `false` on a failed transfer instead of reverting (a well-known ERC-20 non-conformance, e.g. old ERC-20s, some proxy/rebasing tokens) will make `success == true` even though no tokens moved.

### Finding Description
In `withdraw()`: [1](#0-0) 
the code decrements `_orders[body.commitment][token]` and marks `_filled[body.commitment] = beneficiary` regardless of whether the underlying `transfer()` actually moved tokens - it only reverts if the call itself throws: [2](#0-1) 

The same unchecked pattern appears in the `SweepDust` request handler inside `onAccept()`: [3](#0-2) 

This is inconsistent with the EVM-mainline implementation of the same protocol (`IntentsBase.sol`/`ExtrinsicIntents.sol`), which uses OpenZeppelin's `SafeERC20.safeTransfer`, a wrapper that explicitly decodes and requires the boolean return value to be `true` in addition to the call not reverting: [4](#0-3) 

The Tron contract even imports `SafeERC20` and uses `using SafeERC20 for IERC20;` at the top of the file, but the `withdraw()` and `SweepDust` code paths bypass it in favor of the raw, unchecked `.call()` pattern: [5](#0-4) 

### Impact Explanation
`withdraw()` is the function invoked from `onAccept()` for both `RedeemEscrow` (solver payout after a cross-chain fill) and `RefundEscrow` (user refund after cancellation), and from `onGetResponse()` for the cross-chain-cancellation path: [6](#0-5) [7](#0-6) 

If the escrowed input token happens to be one that returns `false` on a failed transfer (rather than reverting) - which is entirely plausible on Tron/EVM-compatible chains where various legacy or non-standard ERC-20 tokens are used as intent inputs - the contract will:
1. Decrement the internal escrow accounting (`_orders[commitment][token] -= amount`) as if funds moved.
2. Mark the order `_filled`/settled and emit `EscrowReleased`/`EscrowRefunded`.
3. Never actually deliver the tokens to the solver or user.

The result is a permanent, unrecoverable loss of the escrowed funds: they remain stuck in the `IntentGatewayV2` contract while the protocol's on-chain bookkeeping records the order as already settled, so no retry or cancellation path exists (the order is already marked filled/refunded). This is a direct "loss of funds" impact matching the bounty's fund-safety criteria, achievable without any relayer, prover, or admin misbehavior - the settlement message itself is legitimate; only the underlying token's transfer semantics need to return `false` on failure.

### Likelihood Explanation
This requires no malicious actor: any input/fee token configured for the Tron intent market that returns `false` rather than reverting on a failed `transfer` (e.g., due to insufficient balance from prior partial fills/rounding, blacklist checks, or paused-token states common in some token implementations) triggers the bug deterministically on the very first such failed transfer. Given intent gateways are explicitly designed to be configurable with arbitrary ERC-20 tokens as escrow inputs, and Tron's ecosystem includes many non-strictly-conforming token contracts, this is a realistic, not merely theoretical, trigger.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)` (the `SafeERC20` library is already imported and aliased with `using SafeERC20 for IERC20;` in this file), mirroring the mainline EVM `IntentsBase.sol` implementation. This ensures both call-reversion and false-boolean-return failures cause the whole transaction to revert, keeping escrow accounting and settlement state consistent with actual token movement.

### Proof of Concept
1. Register/escrow an order whose input token is an ERC-20 that returns `false` (does not revert) when a `transfer` call would fail (e.g., a mock token where `transfer` checks a blacklist and returns `false` for a blacklisted beneficiary, or simply a token with a bug returning `false` on insufficient balance instead of reverting).
2. Drive the settlement flow so `onAccept()` receives a `RedeemEscrow`/`RefundEscrow` message (or `onGetResponse` for cancellation) targeting `withdraw()`.
3. Have the mock token's `transfer()` return `false` for this specific call (still returning normally, not reverting).
4. Observe: `success` is `true` (the call itself didn't revert), so `TransferFailed()` is never raised; `_orders[commitment][token] -= amount` executes, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted - yet the beneficiary's token balance never increased. The escrowed tokens remain permanently stuck in the `IntentGatewayV2` contract with no way to re-trigger withdrawal since the order is already marked filled.
