### Title
Copilot AI conflict-resolution content is spliced into files with only a weak, bypassable conflict-marker check, allowing attacker-influenced PR/commit text to silently corrupt what the user commits - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's AI-assisted merge-conflict resolution feature builds a prompt that embeds attacker-influenceable text (PR titles/bodies, commit summaries from both sides of the merge) verbatim into the model input, then takes whatever `resolvedContent` the model returns and splices it directly into the user's working file with only a weak sanity check for leftover conflict markers. Just as the Opus report's mitigation trusted a value that could be inflated (`balance_of`) instead of an authoritative recorded amount, Desktop trusts model output validated only by path/hunk-count bookkeeping rather than any check that the spliced content faithfully reflects the actual "ours"/"theirs" hunks it was supposed to merge.

### Finding Description
`formatConflictContextForPrompt` in `app/src/lib/copilot-conflict-context.ts` (lines 482-610) inlines the PR body and commit summaries from a to-be-merged branch directly into the text sent to the model: [1](#0-0) 

These PR bodies/commit messages can originate from an untrusted branch/fork the user is merging, rebasing onto, or cherry-picking from — i.e., attacker-controlled GitHub API objects (`IConflictContextPullRequest.body`, commit summaries) — reaching an LLM prompt with only truncation, no semantic/instruction-injection defenses.

The model's response is parsed by `parseCopilotConflictResolution` (`app/src/lib/copilot-conflict-resolution.ts`, lines 281-466). The only guard against the model returning still-broken or malicious content is: [2](#0-1) 

This check only rejects a hunk if the string matches *both* an ours-marker regex and a separator regex somewhere in it — it doesn't validate that returned content is otherwise safe, correct, or free of injected code; a payload that omits one of the two exact regex shapes (e.g. no bare `=======` line) sails through untouched.

`validateResolutionPaths` (lines 473-521) only checks path membership, duplicate paths, and hunk *counts* against `expectedFiles` — never the actual content of a hunk: [3](#0-2) 

Finally, `reassembleResolvedFile` (lines 549-599) walks the original file and splices each hunk's `resolvedContent` in verbatim, matched purely by **order**, not by verified correspondence to the original ours/theirs text: [4](#0-3) 

The chain (context → prompt → model → parse → splice) never re-derives or cross-checks the resolved content against the ground truth of what was actually in the conflict — the entire correctness of what ends up in the file depends on trusting the LLM output, mirroring the ERC4626 pattern of trusting a mutable/attacker-influenceable quantity (`balance_of`) instead of an authoritative recorded value.

### Impact Explanation
If the model can be steered (via prompt injection embedded in a malicious PR description or commit message on the branch being merged) into fabricating `resolvedContent` for a hunk — e.g. silently dropping a security check that exists on "ours", inserting additional statements, or exfiltrating data via injected code — that content is spliced straight into the working file with no independent verification. The corrupted file is what the user will subsequently review (relying on the AI's `reasoning` summary, not necessarily the raw diff) and commit/push. This is "silent corruption of what the user commits or pushes," directly in the class of harm called out for this task.

### Likelihood Explanation
Exploitation requires only that the user run Desktop's Copilot-assisted conflict resolution while merging/rebasing a branch, PR, or fork that contains attacker-crafted commit messages or a PR body (the normal, expected workflow — no local access, no admin rights, no pre-existing malware). The size caps (`MAX_PR_BODY_LENGTH`, `MAX_CONFLICT_CONTENT_SIZE`) limit content size but do not defend against instruction injection or the described bypass of the conflict-marker check.

### Recommendation
- Treat all PR/commit text embedded in the prompt as untrusted; add explicit prompt-injection framing/delimiters and instruct (and enforce via post-processing) that such text is data, not instructions.
- Strengthen `parseCopilotConflictResolution`'s marker check to reject any line matching an ours/base/theirs/separator marker pattern individually, not just the combined heuristic.
- Add a content-integrity check in `reassembleResolvedFile`/`validateResolutionPaths` that verifies the resolved hunk is plausibly derived from the original ours/theirs/base text (e.g., diff-similarity bound) rather than trusting arbitrary model output paired only by ordinal position.
- Surface the actual diff (not just the AI `reasoning` text) prominently before the user commits AI-resolved files.

### Proof of Concept
Note: I was not able to fully trace the downstream UI review/commit flow (`app/src/lib/stores/copilot-store.ts`, `app-store.ts`) within the available iterations to confirm exactly how much of the raw diff is shown to the user before commit, so the following PoC path is based on the confirmed data flow above and should be validated against that missing piece:
1. Attacker opens a PR (or pushes a branch) with a body/commit message crafted as a prompt-injection payload instructing the model to alter unrelated code in a specific conflicted hunk while producing a plausible `reasoning` string.
2. Victim merges/rebases this branch in Desktop and uses the "Resolve with Copilot" flow; `formatConflictContextForPrompt` includes the malicious PR body verbatim in the request.
3. The model returns a `resolvedContent` for the targeted hunk that does not contain both marker regexes together, passing the check at `app/src/lib/copilot-conflict-resolution.ts:444-448`.
4. `reassembleResolutions`/`reassembleResolvedFile` splice this content into the file; `validateResolutionPaths` only confirms path/hunk-count match, not correctness.
5. The victim, trusting the AI reasoning, commits and pushes the corrupted file.
