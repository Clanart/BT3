### Title
Copilot conflict-resolution hunks are spliced by positional order with no content-based validation, allowing attacker-controlled repository content to silently corrupt merged/committed files - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
The external report's root cause is a **contract mismatch between producer and consumer**: `fee_manager` emits a payload whose field layout diverges from what `factory` expects, and `factory` has no way to detect the mismatch — it just consumes whatever is in the expected byte offsets, silently corrupting its state. The same "the consumer trusts positional/count data with no identity check" pattern exists in the GitHub Desktop Copilot merge-conflict-resolution feature: `reassembleResolvedFile` splices per-hunk model output into the working file purely by **positional index**, and the only cross-check performed before that (`validateResolutionPaths`) verifies hunk **count**, never hunk **identity/order correctness**.

### Finding Description
`reassembleResolvedFile` walks the on-disk conflicted file, and for every `<<<<<<< / ======= / >>>>>>>` block it encounters it pulls `hunkResolutions[hunkIndex]` and splices that content in, incrementing `hunkIndex` — matching is explicitly "by order, not by line number": [1](#0-0) [2](#0-1) 

The only validation performed on the model's raw JSON output (`parseCopilotConflictResolution`) checks shape/types of `resolutions[i].hunks[j].resolvedContent`, and separately `validateResolutionPaths` checks that the **count** of hunks per file matches the app's own count of real conflict blocks: [3](#0-2) 

Nothing validates that hunk *N* in the model's array actually corresponds to conflict block *N* in the file, i.e. there is no positional/identity guarantee comparable to a `query_id`/tag that would let the consumer detect a misaligned or reordered response. This mirrors the report's flaw: `fee_manager` reordered/added fields in `op::get_fees_notification` and `factory` had no discriminator to detect the mismatch, so it silently consumed the wrong data.

The model's context — and therefore its output ordering — is built from attacker-influenceable content: conflict markers, surrounding lines, and commit/PR metadata pulled from the repository being merged (`IFileConflictContext`, `IConflictContextCommit`, `IConflictContextPullRequest` in `app/src/lib/copilot-conflict-context.ts`) are fed verbatim into the prompt. A crafted branch/PR (e.g., a file with conflict-marker content engineered via prompt injection, unusual conflict block structure, or many closely-spaced conflicts) can cause the LLM to return hunks whose count matches but whose *order* doesn't align with the true block order — this is not something the model provider or the app enforces beyond a count check.

Once accepted, this passes straight to the write path: [4](#0-3) 

Note that `resolveWithin(repository.path, resolution.path)` does correctly prevent path traversal for the *file path* — that specific guard is solid — but there is no equivalent guard for hunk *content* correctness, which is the analog of the missing `query_id`/format discriminator in the original report.

### Impact Explanation
If hunk resolutions are misaligned, the wrong merged content is silently written into the wrong conflict location and then `git add`-ed and eventually committed/pushed by the user, who only sees a diff-review UI (`copilot-conflicts-dialog.tsx`) summarizing per-file resolutions, not necessarily a byte-exact re-verification against the true block boundaries. This falls squarely under "silent corruption of what the user commits or pushes," matching the accepted-impact class, and could be leveraged by an attacker who controls the branch/PR being merged (a cloned/fetched, untrusted, adversarial repository) to inject unintended code into the user's commit.

### Likelihood Explanation
Requires: (1) the user opts in to Copilot-based conflict resolution, (2) the repository/PR being merged contains attacker-crafted content designed to desynchronize the model's per-hunk response ordering from the true conflict-block order (a prompt-injection-adjacent technique), and (3) the model complies with a plausible-but-misordered/miscounted-but-matching-count response. This is not trivially reliable to trigger deterministically since it depends on LLM behavior, so likelihood is moderate/speculative rather than confirmed exploitable — I could not verify from static code alone whether the LLM can reliably be steered to produce a count-matching-but-misordered response; this would need dynamic testing against the actual Copilot backend, which is outside what's visible in the indexed code.

### Recommendation
Add a content-anchored validation step instead of trusting order alone: require the model to echo back (or the app to independently verify) an identifier per hunk — e.g., a hash or a snippet of the original conflicted block content — and reject/re-request resolution if the anchor doesn't match the corresponding block at splice time, analogous to including a `query_id`/tag rather than relying purely on positional/count agreement, as recommended in the original report.

### Proof of Concept
Not independently reproducible from static analysis alone (depends on LLM behavior). Conceptual PoC: craft a repository/branch whose conflicted file has two closely adjacent conflict blocks with content engineered (via prompt injection or ambiguous phrasing in commit messages referenced in context) to increase the chance the model returns exactly 2 hunks but with contents that make more semantic sense in the opposite order; upon `_applyCopilotConflictResolutions`, `reassembleResolvedFile` will splice hunk[0]'s content into the first marker block and hunk[1] into the second regardless of whether that's the content the model intended for that specific block, and `validateResolutionPaths` will not catch it because the count still matches: [5](#0-4)

export function validateResolutionPaths(
  resolutions: ReadonlyArray<IRawFileResolution>,
  expectedFiles: ReadonlyArray<IFileConflictContext>
): void {
  const expectedPaths = new Set(expectedFiles.map(f => f.path))
  const expectedHunkCounts = new Map(
    expectedFiles.map(f => [f.path, f.hunks.length])
  )
  const returnedPaths = new Set(resolutions.map(r => r.path))

  for (const path of returnedPaths) {
    if (!expectedPaths.has(path)) {
      throw new CopilotValidationError(
        `Copilot returned resolution for unexpected file: ${path}`
      )
    }
  }

  if (returnedPaths.size !== resolutions.length) {
    throw new CopilotValidationError(
      'Copilot returned duplicate file paths in resolutions'
    )
  }

  const missingPaths: Array<string> = []
  for (const path of expectedPaths) {
    if (!returnedPaths.has(path)) {
      missingPaths.push(path)
    }
  }
  if (missingPaths.length > 0) {
    throw new CopilotValidationError(
      `Copilot did not return resolutions for: ${missingPaths.join(', ')}`
    )
  }

  for (const resolution of resolutions) {
    // Delete-vs-modify resolutions use action instead of hunks — skip count check
    if (resolution.action !== undefined) {
      continue
    }
    const expectedCount = expectedHunkCounts.get(resolution.path) ?? 0
    if (resolution.hunks.length !== expectedCount) {
      throw new CopilotValidationError(
        `Copilot returned ${resolution.hunks.length} hunk(s) for "${resolution.path}" but expected ${expectedCount}`
      )
    }
  }
