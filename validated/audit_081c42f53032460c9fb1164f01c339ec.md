### Title
Unvalidated encryption key enables identity-point ECDH collapse, collapsing the ChaCha20 keystream to a public constant - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the reported "hardcoded static encryption key protecting the real key" pattern, Serai's PedPoP DKG encrypts secret shares with ChaCha20 using a **hardcoded static IV** (`b"DKG IV v0.2\0"`), which is only safe under the invariant that every ECDH shared point is distinct and secret. That invariant is not enforced: `Decryption::register` accepts any canonical `enc_key` — including the identity point — without validation. A participant registering an identity (or otherwise attacker-controlled/shared) `enc_key` causes `ecdh()` to return the identity for every message encrypted to them, making the ChaCha20 key a publicly computable constant of `context` alone. Every ciphertext sent to that participant is then decryptable by any observer, and all such ciphertexts share one keystream (static key + static IV reuse).

### Finding Description
`cipher()` derives the ChaCha20 key from `transcript("DKG Encryption v0.2" || context || shared_key)` and hardcodes the IV: [1](#0-0) 

The comment justifies the static IV solely by "the key is single-use". But the per-message freshness of `key` in `encrypt()` does not guarantee a distinct *shared key*: `ecdh` is `to * key` where `to = self.decryption.enc_keys[&participant]`, the recipient's registered public key. `C::read_G` only enforces canonical encoding — the identity's encoding is canonical, so it is accepted: [5](#0-4) 

The code itself documents that ECDH reuse leaks messages: [6](#0-5) 

### Impact Explanation
If a DKG participant broadcasts `EncryptionKeyMessage` with `enc_key = identity`, then for every share encrypted to them `ecdh = identity * key = identity`. The ChaCha20 key becomes `H(context || identity_bytes)` — a constant computable by anyone who knows the public `context`, with the fixed IV. Consequences:

1. **Public decryption**: any party observing the (authenticated but not necessarily confidential) channel can recompute the keystream and decrypt that participant's `EncryptedMessage<SecretShare>` ciphertexts — the static key is effectively hardcoded/public, mirroring the reported `r3v4` issue.
2. **Keystream reuse**: all messages to that participant (e.g., substrate share and network share in `key_gen.rs`) use the identical key+IV; XORing ciphertexts yields XOR of plaintext shares.

This is a confidentiality failure of DKG secret shares reachable purely via a malformed public `EncryptionKeyMessage` that passes `EncryptedMessage::read`/`EncryptionKeyMessage::read` and all PoK checks.

### Likelihood Explanation
Requires a DKG participant (or an unprivileged party able to submit a commitments message in a session) to register an identity `enc_key`. No collusion needed; the malformed input is a single canonical point encoding. The code explicitly relies on ECDH distinctness yet performs zero validation at `register`. Impact is bounded to shares addressed to the malicious participant (which they legitimately learn), but the *public* leak and plaintext-XOR exposure exceed the protocol's threat model — a third party gains the share without participating. Rated Medium: secret-key material leakage via a reachable, unvalidated public input.

### Recommendation
Reject identity (and any non-prime-order/torsion) points in `Decryption::register`/`Encryption::register` before storing `enc_key` (e.g., `if bool::from(msg.enc_key.is_identity()) { error }`), or bind a PoP for `enc_key` in `EncryptionKeyMessage` proving knowledge of its discrete log, which excludes identity. Additionally, consider deriving the IV from the transcript alongside the key rather than hardcoding it, so accidental shared-key repetition degrades less catastrophically.
