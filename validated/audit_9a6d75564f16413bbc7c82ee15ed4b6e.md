### Title
Non-canonical `version` byte lets `StacksTransaction::consensus_deserialize` accept bytes that don't round-trip - ([File: stacks-codec/src/transaction.rs])

### Summary
`StacksTransaction::consensus_deserialize_with_len` derives `self.version` from only the high bit of the wire byte (`version_u8 & 0x80`), while `consensus_serialize` always re-emits the canonical discriminant of the resulting `TransactionVersion` enum. Any wire byte that shares the correct high bit but differs in the low 7 bits is accepted, yet `serialize(deserialize(bytes)) != bytes`, so multiple distinct attacker-submitted byte strings collapse to one canonical, re-serialized transaction and one txid computed over different bytes than the ones actually transmitted.

### Finding Description
The claimed invariant is:
```
serialize(deserialize(b)) == b   for every b accepted by consensus_deserialize
```

Trace of the code path, `stacks-codec/src/transaction.rs`:
- Deserialization reads the raw version byte and normalizes it: [1](#0-0) 
```rust
let version_u8: u8 = read_next(fd)?;
...
let version = if (version_u8 & 0x80) == 0 {
    TransactionVersion::Mainnet
} else {
    TransactionVersion::Testnet
};
```
Any byte value with bit `0x80` unset (e.g. `0x00`, `0x01`, ..., `0x7F`) is accepted and mapped to `TransactionVersion::Mainnet`; any byte with bit `0x80` set (e.g. `0x80`, `0x81`, ..., `0xFF`) is mapped to `TransactionVersion::Testnet`. No check rejects the 127 non-canonical values in each case.

- Serialization always emits the canonical discriminant of the enum, not the originally-read byte: [2](#0-1) 
```rust
fn consensus_serialize<W: Write>(&self, fd: &mut W) -> Result<(), codec_error> {
    write_next(fd, &(self.version as u8))?;
    ...
}
```

Because the parsed `StacksTransaction` struct only stores the two-valued `TransactionVersion` enum (the original raw byte is discarded), any downstream re-serialization — for txid computation (`self.txid()` calls `consensus_serialize`), mempool relay, or block-storage round-trips — writes the canonical byte (e.g. `0x00`/`0x80`), which differs from a non-canonical byte the attacker actually transmitted (e.g. `0x01` or `0xFF`).

Exploit flow: the attacker builds and signs a normal transaction using the canonical version byte (so the signature/sighash is valid over canonical bytes, since sighash computation itself is always performed by serializing the in-memory struct, never the raw wire bytes). They then flip unused low bits of the version byte in the already-signed raw transaction bytes (e.g. change `0x80` → `0x81`..`0xFF` for testnet, or `0x00` → `0x01`..`0x7F` for mainnet) and POST the mutated bytes to `/v2/transactions`. `consensus_deserialize` still accepts it, normalizes it to the same `TransactionVersion`, and signature verification (`verify_origin`/`verify`) still succeeds because it is computed by re-serializing the canonicalized struct, not the wire bytes. The result: many distinct byte strings are all valid, sign-verified transactions that produce the *same* canonical struct and hence the *same* txid, while none of them equal `serialize(deserialize(bytes))` for their own original bytes (except the one canonical encoding).

None of the standard guards catch this: `verify_origin`/`verify` recompute the sighash from the parsed struct fields, so they don't notice the raw byte was non-canonical. `process_transaction_precheck` and `check_transaction_nonces` operate on the already-canonicalized struct. `check_transaction_postconditions` is downstream of all of this and only ever sees the canonical struct, so it cannot detect or prevent the mismatch — it is unaffected by which raw bytes produced its inputs, but it is cited in the question as the illustrative downstream consumer of a transaction whose txid may not correspond to the bytes actually broadcast.

### Impact Explanation
This is a txid/sighash-over-different-bytes issue: nodes, explorers, or relay logic that compute or index a transaction's identity by hashing the raw bytes received off the wire (rather than the canonicalized re-serialization) can disagree with the node's own internally computed txid for the same logical transaction. This enables relay confusion (the same conceptual transaction appearing under multiple wire encodings/txids in different contexts) and mempool bookkeeping inconsistencies. It does not enable asset movement outside post-conditions or forging signatures over new fields — the signature still only covers the canonical fields — so the severity is bounded to the "High - txid/sighash over different bytes than transmitted" category, not Critical. It is repeatable by any unprivileged sender for every transaction they sign, at zero additional cost (just flip unused bits in one byte before broadcasting).

### Likelihood Explanation
No special epoch or account state is required; the bug is purely in the codec layer and is reachable from any signed transaction submitted via the normal RPC ingestion path. The attacker only needs to control the raw bytes of their own already-signed transaction, which they always do. This is trivial to trigger and highly repeatable, though its blast radius is limited to bookkeeping/identity confusion rather than fund movement.

### Recommendation
Reject non-canonical version bytes during deserialization: require `version_u8 == TransactionVersion::Mainnet as u8` or `version_u8 == TransactionVersion::Testnet as u8` exactly (i.e., compare the whole byte, not just the high bit), returning a `DeserializeError` for any other value. This restores the round-trip invariant `serialize(deserialize(b)) == b` for the version field.

### Proof of Concept
```rust
// Build and sign a normal transaction (canonical testnet byte 0x80).
let privk = StacksPrivateKey::random();
let auth = TransactionAuth::from_p2pkh(&privk).unwrap();
let mut tx = StacksTransaction::new(
    TransactionVersion::Testnet,
    auth,
    TransactionPayload::TokenTransfer(
        StacksAddress::new(1, Hash160([0xaa; 20])).unwrap().into(),
        1,
        TokenTransferMemo([0u8; 34]),
    ),
);
// ... sign tx via TransactionSigner to populate the auth signature ...

let mut canonical_bytes = vec![];
tx.consensus_serialize(&mut canonical_bytes).unwrap();
assert_eq!(canonical_bytes[0], TransactionVersion::Testnet as u8); // 0x80

// Attacker mutates only the version byte's low bits post-signing.
let mut mutated_bytes = canonical_bytes.clone();
mutated_bytes[0] = 0xFF; // still has bit 0x80 set -> still "Testnet"

// Node accepts it:
let decoded = StacksTransaction::consensus_deserialize(&mut &mutated_bytes[..]).unwrap();
assert_eq!(decoded.version, TransactionVersion::Testnet); // accepted

// Round-trip is broken:
let mut re_serialized = vec![];
decoded.consensus_serialize(&mut re_serialized).unwrap();
assert_ne!(re_serialized, mutated_bytes); // FAILS the invariant
assert_eq!(re_serialized, canonical_bytes); // collapses to the canonical encoding

// And the txid computed by the node differs from a hash over the wire bytes:
assert_eq!(decoded.txid(), tx.txid()); // same txid for two different wire payloads
```
This demonstrates that `consensus_deserialize` accepts `mutated_bytes` (a non-canonical encoding), that `decoded` re-serializes to different bytes than were transmitted, and that the resulting txid is computed over bytes distinct from what the attacker actually sent to the node's RPC.
