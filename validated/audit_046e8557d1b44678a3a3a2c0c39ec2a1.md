### Title
Recursive `git clone` explicitly disables Git's clone-time hook protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), allowing a malicious repository to execute arbitrary code the moment it is cloned - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` in `app/src/lib/git/clone.ts` runs `git clone --recursive` with the environment variable `GIT_CLONE_PROTECTION_ACTIVE` hard-coded to `'false'`. `GIT_CLONE_PROTECTION_ACTIVE` is the safety switch Git added upstream to stop a cloned repository (and, critically, its recursively-cloned submodules) from getting its hook scripts installed and executed automatically as part of the clone (the class of bug covered by the CVE-2024/2025 credential-helper/hook clone advisories referenced in Desktop's own `changelog.json`). By forcing this protection off, Desktop reintroduces exactly the "attacker-authored content is acted on immediately, with no review step" pattern described in the external report: here the "operator" is any third party whose repository URL a user opens via "Clone repository" or the `x-github-client://openRepo/...` deep link, and the "malicious withdrawal" is arbitrary hook execution on the user's machine the instant the clone completes. [1](#0-0) 

### Finding Description
The broken invariant in the source report is: *attacker-supplied data is trusted and acted on immediately, without any independent verification step.* In Desktop, `clone()` builds the git invocation like this:

```
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
...
await git(args, __dirname, 'clone', opts)
``` [2](#0-1) 

Unlike every other Git-mutating operation in this codebase (`commit`, `pull`, `push`, `merge`), `clone()` never passes `interceptHooks` to `git()`, so the temporary `core.hooksPath` sandbox implemented in `app/src/lib/hooks/with-hooks-env.ts` is never engaged for cloning: [3](#0-2) 

That sandbox is the only mechanism in this codebase that would otherwise prevent a repository's own (or a submodule's) hook scripts from running with the user's real shell environment. Because `clone()` both (a) skips `interceptHooks` and (b) explicitly disables Git's own built-in `GIT_CLONE_PROTECTION_ACTIVE` guard, a repository (or any of its `--recursive`ly fetched submodules) that ships a hook — installed via clone-time mechanisms such as a crafted `core.hooksPath`/`.gitmodules` entry that Git's protection exists specifically to block — can have that hook executed with no user interaction, no diff review, and no confirmation dialog, the moment the URL is opened for cloning.

This is directly reachable from attacker-controlled input: a remote URL supplied through the "Clone repository" dialog, or the `open-repository-from-url` deep-link action parsed in `app/src/lib/parse-app-url.ts` and dispatched via `openOrCloneRepository` in `app/src/ui/dispatcher/dispatcher.ts`. [4](#0-3) [5](#0-4) 

### Impact Explanation
A malicious or compromised repository owner can craft a repository (potentially with a booby-trapped submodule) such that simply cloning it — an action GitHub Desktop performs with zero warning, exactly analogous to "anyone can immediately invoke finalize_block" in the source report — results in arbitrary code execution on the victim's machine under their own user account. This can lead to credential theft (SSH keys, Git credential helpers, tokens cached by Desktop), file system writes/reads outside the intended repo directory, and full compromise of the developer workstation. This is a direct, unprivileged, no-user-interaction path matching the report's valid-impact criteria (attacker controls a cloned repository, result is code execution / credential exfiltration).

### Likelihood Explanation
High for any user who clones an untrusted or attacker-supplied repository — which is one of Desktop's core, expected use cases (cloning open-source forks, PR branches, "Open in Desktop" links). No local access, admin rights, or social engineering beyond "clone this repo" is required; the deep-link path (`x-github-client://openRepo/...`) means the click can come from any web page or README link, matching the report's "link the user clicks" trigger. The only thing standing between an attacker and code execution is Git's own `GIT_CLONE_PROTECTION_ACTIVE` check — which this code deliberately turns off — and Desktop's `interceptHooks` sandbox, which is simply never applied to `clone()`.

### Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts` so Git's native clone-time hook protection remains active, and/or wrap the clone invocation with the same `interceptHooks` / `withHooksEnv` sandboxing used by `commit`, `pull`, `push`, and `merge` so any hooks that could fire during a recursive clone run inside the temporary, restricted `core.hooksPath` proxy rather than with full access to the user's real shell environment. If the override was added to work around a specific Git/dugite compatibility issue, that justification should be documented and scoped as narrowly as possible (e.g., only for URLs already verified as trusted), not applied unconditionally to every clone.

### Proof of Concept
1. Attacker hosts a Git repository containing a submodule (or `.gitmodules`/hook-installing configuration) engineered to trigger execution of a script as part of `git clone --recursive` — the specific technique Git's `GIT_CLONE_PROTECTION_ACTIVE` safeguard was built to block.
2. Attacker sends the victim either a normal `git clone <url>` link to paste into Desktop's "Clone repository" dialog, or a deep link such as `x-github-client://openRepo/<attacker-url>`.
3. Victim clones the repository through Desktop. `clone()` runs `git clone --recursive` with `GIT_CLONE_PROTECTION_ACTIVE=false` and without `interceptHooks`, so the protection is disabled and no hook sandbox is applied. [6](#0-5) 
4. The attacker's hook payload executes with the victim's real environment/credentials, with no confirmation prompt shown by Desktop at any point in the flow.

Note: I could not access Git's upstream source or advisory text from this index to confirm the exact mechanics `GIT_CLONE_PROTECTION_ACTIVE` guards against beyond what's inferable from Desktop's own `changelog.json` entries referencing related credential-helper/hook CVEs; a Devin session with full repo/network access would be needed to pull the upstream Git changelog for `GIT_CLONE_PROTECTION_ACTIVE` and confirm the precise attack primitive it blocks.
