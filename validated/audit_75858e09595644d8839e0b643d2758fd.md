## Analysis

I found a concrete analog: `GitHub Desktop`'s `clone` function in [1](#0-0)  explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` when performing a recursive clone. This environment variable exists in Git specifically to control the protections against a class of vulnerabilities (tracked upstream as CVE-2024-32004) where a malicious repository's tracked configuration/hooks content can be leveraged during clone/checkout to achieve arbitrary code execution. By forcing this protection off, Desktop is deliberately re-enabling exactly the class of unsafe behavior Git's own maintainers added a kill switch to guard against, for every clone (including `--recursive`, which processes submodules) that a user performs of a repository they do not control the contents of.

### Title
Recursive clone explicitly disables Git's clone-hook protection (`GIT_CLONE_PROTECTION_ACTIVE=false`), re-enabling attacker-controlled repo content execution during clone - (File: app/src/lib/git/clone.ts)

### Summary
`clone()` builds the environment for every `git clone --recursive` invocation and unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` [1](#0-0) . This is the same pattern as the Sherlock report's root cause: a security guard (the `try`/`catch` around an externally-influenced call in Teller) is bypassed by attacker-supplied external content (a self-destructing contract). Here, the "guard" is Git's own clone-time protection mechanism, and the "attacker-supplied external content" is the cloned repository itself, which is fully attacker controlled when the user clones a third-party/public repo or its submodules.

### Finding Description
The `clone` function passes `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the `env` object used for the `git clone --recursive -- url path` command [2](#0-1) . This same `env` (and thus the disabled protection) also flows into `getDefaultBranch`/`executionOptionsWithProgress` wiring but critically applies to the `--recursive` flag, which causes Git to also initialize and check out any submodules referenced by the (attacker-controlled) repository being cloned [3](#0-2) .

The invariant that should hold is: "cloning a repository whose contents are not yet trusted must not execute code from that repository's contents." Git's clone-protection mechanism enforces this by refusing certain unsafe repository layouts (e.g., symlinked `.git` directories, or hook/config injection via submodules) unless explicitly overridden. By setting this variable to `'false'` for every clone, Desktop removes that check across the board, meaning any malicious repository (or a malicious submodule nested inside an otherwise benign parent repository) is processed with the protection turned off, precisely the situation the check exists to prevent. There is no complementary safety check elsewhere in `clone.ts` — the only other guard, `isClonePathSensitive`, only validates the destination path is not a sensitive host location [4](#0-3)  and does nothing to validate the content of the repository being cloned.

### Impact Explanation
If Git's protection is what stands between "cloning an untrusted repo" and "executing attacker-controlled code/hooks during the clone process," disabling it for all clones (especially recursive submodule clones) reintroduces a code-execution surface for any user who clones a malicious or compromised public repository through Desktop — a common, low-friction action (paste URL → Clone). This matches the required impact category: attacker controls a cloned/fetched repository and the result can be code execution or file writes outside the intended repo, triggered by an ordinary/expected user action (cloning) rather than local access, admin rights, or social engineering beyond "clone this repo."

### Likelihood Explanation
Likelihood is high for exposure (every clone goes through this code path unconditionally) but the actual exploitability depends on which specific unsafe scenarios `GIT_CLONE_PROTECTION_ACTIVE` guards against in the bundled Git/dugite version Desktop uses — this could not be fully confirmed from the indexed code alone (no comment in the codebase explains *why* the flag is set to `'false'`, and I could not locate the corresponding dugite/Git version pinning or any compensating control in this repository's index). This is analogous to the Sherlock report where the guard removal is unconditional and applies regardless of whether the counterparty is trustworthy.

### Recommendation
Do not unconditionally disable `GIT_CLONE_PROTECTION_ACTIVE`. If there's a legitimate compatibility reason for turning it off (e.g., a known false-positive with certain safe repo layouts), it should be scoped narrowly and documented, and ideally re-enabled by default with the safe-directory/trust prompts Desktop already uses elsewhere (e.g., `addSafeDirectory`/`isRepositoryUnsafe` flow shown in [5](#0-4) ) gating any override.

### Proof of Concept
Not independently reproducible from the indexed code alone — verifying requires knowing the exact behavior gated by `GIT_CLONE_PROTECTION_ACTIVE` in the dugite-bundled Git version and constructing a repository (or submodule) that triggers the unsafe path Git's protection was designed to block, then confirming Desktop's clone succeeds where a protection-enabled `git clone --recursive` would refuse/warn. Because of indexing limits, I could not locate the dugite/Git version metadata or any related test coverage for this flag in this codebase; a Devin session with full repo/terminal access would be needed to pin down the exact Git behavior being disabled and build a concrete PoC repository.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
