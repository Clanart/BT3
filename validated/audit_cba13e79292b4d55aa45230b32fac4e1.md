## Analysis: ProtoJSON FieldMask Path Serialization — Ambiguous Delimiter-Based Packing

The Solidity report's core defect is: **joining multiple attacker-influenceable, variable-length values with `abi.encodePacked` (no length-prefixing) creates encodings that cannot be unambiguously split back apart**, so two logically distinct inputs can produce an identical packed byte string (or one packed string can be mis-split into extra/fewer logical values). The strongest transferable analog in this Protobuf checkout is the `google.protobuf.FieldMask` well-known-type's `ToJsonString`/`FromJsonString` (and equivalent per-language `FieldMaskUtil`) round-trip, which joins/splits multiple dynamically-sized path strings using a bare `,` separator with no escaping and no rejection of embedded separator characters.

### Title
FieldMask JSON Path Serialization Uses Unescaped Comma-Joining of Multiple Dynamic-Length Strings, Enabling Ambiguous Round-Trip Reinterpretation — (File: src/google/protobuf/util/field_mask_util.cc)

### Summary
`google.protobuf.FieldMask.paths` is an ordinary `repeated string` field with no character restrictions at the wire-format level, so an ordinary client can produce a valid, bounded binary Protobuf message containing a path that itself contains a literal comma (e.g. `paths: ["foo,bar"]`) via the public `ParseFromString` API. When this message is subsequently converted to its ProtoJSON representation via `FieldMaskUtil::ToJsonString` (C++), `FieldMaskUtil.toJsonString` (Java), or `FieldMask.ToJsonString` (Python) — all public, documented APIs — the implementation joins all paths with a single unescaped `,` and does not check for or reject a `,` already present inside an individual path. The resulting JSON string is therefore indistinguishable from a FieldMask that legitimately contained two (or more) separate paths. Any downstream consumer that parses this ProtoJSON string back into a `FieldMask` (via `FieldMaskUtil::FromJsonString`, the ProtoJSON `ParseFieldMask` parser, or any independent client implementing the documented comma-separated format) will silently reconstruct a *different, larger* set of paths than the ones originally encoded.

### Finding Description
- `FieldMaskUtil::ToJsonString` builds the JSON string by calling `SnakeCaseToCamelCase` on each path and joining with `,`: [1](#0-0) 
- `SnakeCaseToCamelCase` only rejects uppercase letters and malformed underscore sequences — it never checks for or rejects a `,` character, so a path already containing a comma passes through untouched: [2](#0-1) 
- The reverse function, `FieldMaskUtil::FromJsonString`, unconditionally splits the incoming string on every `,`: [3](#0-2) 
- `FieldMaskUtil::ToString`/`FromString` (the non-JSON string form) exhibit the identical unescaped join/split pattern: [4](#0-3) 
- The same pattern is replicated in Python (`','.join(...)` / `value.split(',')`): [5](#0-4) 
- and in Java (`String.join(FIELD_PATH_SEPARATOR, paths)` / split-on-comma): [6](#0-5) 
- The dedicated ProtoJSON codec (`json/internal/parser.cc`/`unparser.cc`) is stricter in its default (RFC-conformant) mode — it rejects any character other than lowercase, digit, or `.` — but explicitly falls back to accepting **any** raw character, including an embedded `,`, when `allow_legacy_nonconformant_behavior` is set, reproducing the exact same ambiguity in that mode: [7](#0-6) [8](#0-7) 

The attacker-controlled value here is any `FieldMask.paths` entry containing a `,`, which is fully reachable via ordinary bounded binary `ParseFromString`/`MergeFrom` since the wire format places no constraint on the string's contents. The missing check is character-escaping/rejection of the separator character at encode time (or explicit rejection at decode time in every "legacy"/utility code path). The result is that a single canonical `FieldMask{paths: ["foo,bar"]}` message and a two-path `FieldMask{paths: ["foo", "bar"]}` message serialize (via `ToJsonString`) to output that either collides or, upon `FromJsonString`, deserializes into extra unintended paths — a direct structural analog of `abi.encodePacked`'s dynamic-type ambiguity.

### Impact Explanation
`FieldMask` is commonly used by RPC/REST-gateway-style applications to scope permitted field reads/updates (e.g., an `update_mask` parameter). If a service accepts a `FieldMask` in binary form from one boundary (e.g., an internal RPC) and re-serializes it to ProtoJSON via `FieldMaskUtil::ToJsonString`/`toJsonString` to forward it to a second component that re-parses it (a realistic multi-hop pattern, since this is the exact purpose the utility documents: "Converts a field mask to a ProtoJSON string ... for use with JSON APIs"), an attacker who controls one hop's binary payload can smuggle extra field paths into the mask observed by the second hop, or cause a single intended path to be split into multiple ones. Depending on how the consuming application enforces access control or update scoping via `FieldMask`, this can widen the effective set of fields an operation is authorized to touch — an integrity/authorization-adjacent impact, consistent with the "Medium" severity of the original finding, since it requires a specific application-level round-trip pattern to be exploitable rather than being exploitable purely within Protobuf's own trust boundary.

### Likelihood Explanation
The attacker-controlled input (a `FieldMask.paths` string containing a literal comma) is trivially producible via a normal, bounded binary Protobuf message and requires no privileged access, malicious schema, or unbounded input. The vulnerable code paths (`FieldMaskUtil::ToJsonString`/`FromJsonString` in C++, Java, and Python) are public, documented, commonly-used utility APIs, not internal/test-only code. However, exploitation is contingent on an application actually round-tripping an untrusted `FieldMask` through these APIs across a trust or authorization boundary, which is an application-level integration decision rather than something Protobuf enforces by default — moderating overall likelihood.

### Recommendation
Reject (or percent-/backslash-escape) the field path separator character (`,`) — and ideally any character outside the documented `[a-z0-9_.]` path grammar — at the point paths are added to a `FieldMask` or, at minimum, in `ToJsonString`/`ToString`/`toJsonString` before joining, mirroring the stricter validation already present in `json/internal/parser.cc`'s non-legacy path. This validation should be applied uniformly across all language implementations (C++ `FieldMaskUtil`, Java `FieldMaskUtil`, Python `field_mask.py`, C# `FieldMaskPartial.cs`, PHP `GPBUtil::formatFieldMask`) rather than being enforced only by the separate low-level ProtoJSON codec, and the `allow_legacy_nonconformant_behavior` escape hatch should not silently permit unescaped separator characters through either.

### Proof of Concept
1. Construct (via ordinary binary Protobuf construction, e.g., using the public API) a `FieldMask` message with a single path containing an embedded comma: `FieldMask{ paths: ["foo,bar"] }`, and serialize it with `SerializeToString()` — a fully valid, bounded binary payload.
2. Parse it back with `FieldMask::ParseFromString(bytes)` (public parse API) — succeeds, `mask.paths(0) == "foo,bar"`.
3. Call `FieldMaskUtil::ToJsonString(mask, &json)` — per [1](#0-0) , this produces the string `"foo,bar"`, indistinguishable from the JSON representation of `FieldMask{ paths: ["foo", "bar"] }`.
4. Call `FieldMaskUtil::FromJsonString("foo,bar", &mask2)` — per [3](#0-2) , this yields `mask2.paths() == ["foo", "bar"]` — two paths, differing from the original single-path mask — demonstrating the ambiguous, lossy round-trip directly analogous to the `abi.encodePacked` unpacking ambiguity described in the source report.

bool FieldMaskUtil::SnakeCaseToCamelCase(absl::string_view input,
                                         std::string* output) {
  output->clear();
  bool after_underscore = false;
  for (char input_char : input) {
    if (input_char >= 'A' && input_char <= 'Z') {
      // The field name must not contain uppercase letters.
      return false;
    }
    if (after_underscore) {
      if (input_char >= 'a' && input_char <= 'z') {
        output->push_back(input_char + 'A' - 'a');
        after_underscore = false;
      } else {
        // The character after a "_" must be a lowercase letter.
        return false;
      }
    } else if (input_char == '_') {
      after_underscore = true;
    } else {
      output->push_back(input_char);
    }
  }
  if (after_underscore) {
    // Trailing "_".
    return false;
  }
  return true;
}

bool FieldMaskUtil::ToJsonString(const FieldMask& mask, std::string* out) {
  out->clear();
  for (int i = 0; i < mask.paths_size(); ++i) {
    absl::string_view path = mask.paths(i);

    if (!SnakeCaseToCamelCase(path, &camelcase_path)) {
      return false;
    }
    if (i > 0) {
      out->push_back(',');
    }
    out->append(camelcase_path);
  }
  return true;

  def ToJsonString(self):
    """Converts FieldMask to string according to ProtoJSON spec."""
    camelcase_paths = []
    for path in self.paths:
      camelcase_paths.append(_SnakeCaseToCamelCase(path))
    return ','.join(camelcase_paths)

  def FromJsonString(self, value):
    """Converts string to FieldMask according to ProtoJSON spec."""
    if not isinstance(value, str):
      raise ValueError('FieldMask JSON value not a string: {!r}'.format(value))
    self.Clear()
    if value:
      for path in value.split(','):
        self.paths.append(_CamelCaseToSnakeCase(path))
