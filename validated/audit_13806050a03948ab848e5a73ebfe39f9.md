### Title
Consensus-incentive reward for an entire message batch is paid to the signer of the batch's first message only - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives` pays relayers for delivering ISMP `ConsensusMessage`s. The `FeeHandler::on_executed` hook receives the *whole batch* of messages processed by `pallet-ismp::handle` in one call, but only recovers a relayer identity from `messages.get(0)` [1](#0-0) . It then iterates over **every** `StateMachineUpdated` event produced anywhere in that batch — including for state machines whose advance came from a different `ConsensusMessage` further in the vector, possibly with a different embedded signer — and pays the reward for all of them to the single relayer recovered from message index 0 [2](#0-1) .

### Finding Description
`pallet_ismp::handle` accepts an unsigned, batched `Vec<Message>` extrinsic (`ensure_none` origin) — the caller assembling the batch is not required to be the same party who produced/signed each embedded `ConsensusMessage`, because each `ConsensusMessage` already carries its own `signer`/`consensus_proof` signature that is verified independently inside ISMP's own proof-verification path. The batch submitter is therefore free to combine messages that legitimately originated from different relayers.

When the batch finishes executing, `FeeHandler::on_executed` is invoked once with `messages: Vec<MessageWithWeight>` and `events: Vec<IsmpEvent>` for the whole batch [1](#0-0) . The pallet:

1. Looks only at `messages.get(0)`, decodes its `signer`, and recovers a single `relayer_account` for the entire batch.
2. Collapses all `StateMachineUpdated` events in the batch — for potentially many distinct `state_machine_id`s — to their highest heights and pays a `process_message` reward for each one, all attributed to the one relayer recovered from `messages[0]`.

This means the reward for consensus progress genuinely proven by the signature on `messages[1]`, `messages[2]`, etc. (which could belong to different relayers than `messages[0]`'s signer) is paid entirely to whoever's `ConsensusMessage` happens to sit at index 0 of the batch. Since batch composition is controlled by the unsigned-extrinsic submitter and not tied to per-message signer identity by the reward pipeline, an attacker can construct a batch where their own trivially-produced/self-signed `ConsensusMessage` occupies slot 0, while additional, otherwise-valid `ConsensusMessage`s for unrelated state machines occupy later slots. All resulting `RelayerRewarded` payouts for that block go to the attacker's account rather than to whoever actually satisfied the proof requirement for the other state machines' updates.

The existing `LastRewardedHeight` watermark only prevents re-paying the *same* state-machine height twice [3](#0-2) ; it does nothing to bind a specific reward to the message that actually produced it, so it does not stop the misattribution described here.

### Impact Explanation
This is a direct, unauthorized redirection of treasury-funded relayer rewards (`RewardTransferFailed`/`Currency::transfer` from `TreasuryAccount`) and minted reputation assets to the wrong beneficiary — matching the bounty's "wrong beneficiary or amount" / "manipulation of ... transaction" impact class. Unlike the Voter.sol seed report (stale voting weight skewing distribution ratios over time), here the corrupted value is the *relayer identity* attributed to a batch (`maybe_relayer_account` derived solely from `messages[0]`), and the guard (`LastRewardedHeight`) that exists only protects against double payment for the same height, not against wrong-recipient payment.

### Likelihood Explanation
Exploitation requires only the ability to submit the unsigned `pallet-ismp` `handle` extrinsic with a hand-assembled `Vec<Message>` — something any network participant can already do, since `handle` is permissionless (`ensure_none` origin) and any valid `ConsensusMessage` (with its embedded signature) is public once broadcast/finalized. No relayer, prover, or admin collusion is required beyond the attacker's own actions; the attacker only needs to be able to place their own consensus message first and bundle other independently-valid consensus messages afterward in the same call.

### Recommendation
Attribute and pay out per `ConsensusMessage`, not once per batch: iterate `messages`, recover the relayer for each `Message::Consensus` variant individually, and only credit `StateMachineUpdated` events that resulted from that specific message (e.g., by correlating the height range or explicitly threading a message index through to the emitted event) to that message's own recovered signer, rather than pooling all batch events under `messages.get(0)`'s signer.

### Proof of Concept
Conceptual sequence (concrete storage/state wiring would need a Devin session against the pallet's test harness in `modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs` to execute):
1. Attacker crafts `ConsensusMessage_A` for `state_machine_id = X`, signed with their own key (cheap/self-authored, e.g. minimal real height advance).
2. Attacker copies a second, independently valid `ConsensusMessage_B` for `state_machine_id = Y`, signed by relayer B (observed once broadcast/finalized, e.g. from a previous block or public mempool data), which represents a large real height advance for `Y`.
3. Attacker submits `pallet_ismp::handle([ConsensusMessage_A, ConsensusMessage_B])` in a single unsigned extrinsic.
4. `pallet-ismp` verifies both proofs independently and successfully executes both, emitting `StateMachineUpdated` for both `X` and `Y`.
5. `Pallet::on_executed` recovers `relayer_account` only from `messages[0]` (attacker's key), then loops over both `StateMachineUpdated` events and calls `process_message` for both `X` and `Y`, transferring both rewards from `TreasuryAccount` to the attacker — even though relayer B's signature is what satisfied the proof requirement for `Y`.

Given the "no more tool calls" constraint, I was not able to trace through `pallet_ismp::handle`'s exact message-execution loop (`modules/pallets/ismp/src/impls.rs`) to confirm there is no batch-level constraint I missed that ties all messages in one `handle` call to a single signer/origin; this should be verified in a live session before treating the finding as fully confirmed. Everything else — the `messages.get(0)`-only signer recovery, the per-batch multi-state-machine event loop, and the watermark's scope being limited to double-payment prevention — is directly supported by the cited pallet code.

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,

		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);

			}
		});
