## Finding

### Title
Unvalidated PR-file paths joined with repository root without `resolveWithin` guard — path traversal in the "Files changed" PR view - (File: `app/src/ui/open-pull-request/pull-request-files-changed.tsx`)

### Summary
GitHub Desktop already hardened the most obvious analog of the `localhost-now` bug class — the `x-github-client://openrepo` deep-link handler — by routing any attacker-influenced `filepath` through `resolveWithin()`, which resolves symlinks and verifies the final path is still inside the repository root before it is ever handed to `shell.showItemInFolder` [1](#0-0) . The same discipline is applied in `copilot-conflict-context.ts` when reading conflict file contents [2](#0-1) .

However, the "Open Pull Request" file browser (`PullRequestFilesChanged`) does not apply this guard at all. It joins a `CommittedFileChange.path` value — which originates from the changeset of a pull request commit, i.e. content that can be authored by any external contributor via a fork — directly onto `repository.path` with plain `Path.join`, and then uses the result to reveal, open, or launch an external editor/program on that path: [3](#0-2) [4](#0-3) 

The same unguarded pattern (`Path.join(repository.path, path)` with a path handed straight to `dispatcher.openInExternalEditor`) also exists in the generic history view and in `app.tsx`'s `onOpenInExternalEditor`: [5](#0-4) [6](#0-5) 

### Finding Description
`file.path` for a committed change is normally produced by `getChangedFiles`/`getCommitRangeChangedFiles`, which parse `git log --raw --numstat` output [7](#0-6) . This is generally constrained by git's own path handling. But the "Open Pull Request" dialog explicitly supports viewing a **pull request whose latest commit is not local yet** — `nonLocalCommitSHA` — and offers the same file list, context menu, "Open in default program", "Reveal in File Manager", and "Open in external editor" actions on it [8](#0-7) [9](#0-8) .

None of the file-path-consuming handlers in this component — `onOpenFile`, `onFileContextMenu`, `onViewOnGitHub`, `onRowDoubleClick` — validate that the resulting path stays inside `repository.path`. This is the exact broken invariant from the H1 report: a filter/validation step that exists elsewhere in the codebase (`resolveWithin`, `isAbsolute` rejection) is simply absent on this particular ingestion path, even though the data source (a PR's changed files, which can include renamed/copied entries with an `oldPath`) is attacker-influenced in the same way a crafted URL is in the original report.

### Impact Explanation
If a `CommittedFileChange.path` (or `.oldPath` for renames/copies) can be made to contain path-escaping segments — whether through a crafted diff/rename entry associated with a fork's pull request, or through any future change to how the "non-local commit" file list is populated (e.g., directly from a GitHub API diff payload instead of local `git log`) — `Path.join(repository.path, file.path)` will happily resolve outside the repository. That path is then:
- passed to `revealInFileManager` / `shell.showItemInFolder` (file-existence/location disclosure),
- passed to `dispatcher.openInExternalEditor(fullPath)` (opens arbitrary file in the user's editor),
- passed to `openFile(fullPath, dispatcher)` (opens arbitrary file with the OS default handler for its extension).

This matches the report's core primitive (server/attacker-controlled path bypassing a path filter to reach files outside the intended root) and maps onto the program's valid-impact category of "attacker controls a GitHub API object … result is … file read outside the repo."

### Likelihood Explanation
Reaching this code requires the user to open the "Open Pull Request" dialog for a PR authored by an untrusted party, which is a normal, low-friction workflow in Desktop (no unnatural steps). The remaining uncertainty — and the reason this should be treated as **moderate rather than confirmed** likelihood — is that I could not, within the available tool budget, trace the exact producer of `changesetData.files` for the `nonLocalCommitSHA` case to confirm whether it is populated from raw git tree data (which git constrains) or from a GitHub API diff response (which is an arbitrary string with no traversal protection). This is the one open question a follow-up session should resolve before treating this as a fully confirmed exploit.

### Recommendation
Apply the same `resolveWithin(repository.path, file.path)` guard used in `dispatcher.ts` and `copilot-conflict-context.ts` to every handler in `pull-request-files-changed.tsx` (and the equivalent ones in `app.tsx`/`selected-commits.tsx`) before using the resolved path with `shell.showItemInFolder`, `openInExternalEditor`, or `openFile`. Reject (log and no-op) when `resolveWithin` returns `null`, mirroring `dispatcher.ts:1963-1971`.

### Proof of Concept
Not independently reproducible from static analysis alone, because the exact data path for `nonLocalCommitSHA`-backed PR file lists was not confirmed. Conceptually:
1. Attacker opens a PR against a repository the victim has cloned in Desktop, with a renamed/copied file whose `oldPath`/`path` metadata is crafted to contain `../../../../.ssh/authorized_keys`-style segments (or, if the non-local-commit file list is sourced from the GitHub API diff, simply submits such a path directly).
2. Victim opens "Open Pull Request" in Desktop and right-clicks/double-clicks the malicious entry in the file list.
3. `Path.join(repository.path, file.path)` resolves outside the repository, and Desktop reveals/opens/launches an editor on that external file — with no `resolveWithin` check to stop it, unlike the deep-link `filepath` handler which is explicitly protected against this exact pattern.


Repository: Annirich/desktop--021

Context: `app/src/lib/path.ts` exposes `resolveWithin(rootPath, ...pathSegments)`, which safely joins a path onto a root, resolves symlinks via `realpath`, and returns `null` if the result escapes the root. This guard is already used in `app/src/ui/dispatcher/dispatcher.ts` (`openRepositoryFromUrl`, around lines 1957-1972) to protect the `x-github-client://openrepo?filepath=` deep link, and in `app/src/lib/copilot-conflict-context.ts` (`buildConflictContext`, lines ~390-407) to protect conflict file reads. However, several UI code paths that join a `CommittedFileChange.path` (or `.oldPath`) onto `repository.path` do NOT use this guard, and instead use a plain `Path.join`:

1. `app/src/ui/open-pull-request/pull-request-files-changed.tsx`:
   - `onOpenFile` (line ~86-89): `Path.join(this.props.repository.path, path)` then calls `openFile(fullPath, dispatcher)`.
   - `onFileContextMenu` (line ~154-225): `Path.join(repository.path, file.path)` used for "Reveal in File Manager" (`revealInFileManager`), "Open in external editor" (`dispatcher.openInExternalEditor(fullPath)`), and "Open with default program" (`this.onOpenFile(file.path)`).
   - `onViewOnGitHub` builds a GitHub URL from `file.path` — lower risk but should also be sanity-checked.
   - Note this component explicitly supports pull requests whose latest commit is not yet fetched locally (`nonLocalCommitSHA` prop), meaning the underlying file list may come from a source other than a locally-verified git tree walk.

2. `app/src/ui/app.tsx`, `onOpenInExternalEditor` (line ~3429-3437): `Path.join(repository.path, path)` passed straight to `dispatcher.openInExternalEditor(fullPath)`. This is invoked with `file.path` values coming from `selected-commits.tsx` and `pull-request-files-changed.tsx`.

3. `app/src/ui/history/selected-commits.tsx`, `onRowDoubleClick` (line ~119-124): passes `file.path` up to `onOpenInExternalEditor` without any traversal check.

Task: Introduce a `resolveWithin(repository.path, file.path)` (and for rename/copy cases, also validate `file.status.oldPath` if it is used) check at each of the above call sites before the resulting path is used with `shell.showItemInFolder`/`revealInFileManager`, `dispatcher.openInExternalEditor`, or `openFile`. When `resolveWithin` returns `null`, do not perform the action — instead log an error (following the existing pattern in `dispatcher.ts`: `log.error(\`Prevented attempt to open path outside of the repository root: ${filepath}\`)`) and, where applicable in the context menu, disable/hide the corresponding menu item.

Specifically:
- In `pull-request-files-changed.tsx`, refactor `onOpenFile` and the `onFileContextMenu` handler to `await resolveWithin(repository.path, file.path)` up front, use the resolved absolute path for all three actions (reveal / open-in-editor / open-with-default-program), and only enable those menu items / proceed if resolution succeeds (in addition to the existing `fileExistsOnDisk` check, which currently runs on the unguarded `fullPath`).
- In `app.tsx`'s `onOpenInExternalEditor`, make the function `async`, call `resolveWithin(repository.path, path)`, and only call `dispatcher.openInExternalEditor` with the resolved path (bail out and log otherwise).
- Ensure `revealInFileManager` (in `app/src/lib/app-shell.ts`) receives an already-validated path, or add the same `resolveWithin` check inside `revealInFileManager` itself if it is also called from other unguarded sites.
- Add unit tests analogous to `app/test/unit/path-test.ts`'s `resolveWithin` tests and `app/test/unit/parse-app-url-test.ts`, covering a `CommittedFileChange` with a traversal-crafted `path`/`oldPath` (e.g. `../../../../.ssh/authorized_keys`) to confirm the UI handlers now refuse to act on it.
- Separately, trace and document (in code comments or a follow-up ticket) how `changesetData.files` is populated for the `nonLocalCommitSHA` case in the "Open Pull Request" flow, to confirm whether that data originates from a GitHub API diff response (unsanitized string) versus local git tree data, since this determines the real-world severity of the gap being fixed here.

/** Get the files that were changed in the given commit. */
export async function getChangedFiles(
  repository: Repository,
  sha: string
): Promise<IChangesetData> {
  // opt-in for rename detection (-M) and copies detection (-C)
  // this is equivalent to the user configuring 'diff.renames' to 'copies'
  // NOTE: order here matters - doing -M before -C means copies aren't detected
  const args = [
    'log',
    sha,
    '-C',
    '-M',
    '-m',
    '-1',
    '--no-show-signature',
    '--first-parent',
    '--raw',
    '--format=format:',
    '--numstat',
    '-z',
    '--',
  ]

  const { stdout } = await git(args, repository.path, 'getChangesFiles')
  return parseRawLogWithNumstat(stdout, sha, `${sha}^`)
}
