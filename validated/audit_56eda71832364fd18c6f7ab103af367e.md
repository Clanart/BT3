### Title
Discard Changes writes/deletes filesystem paths derived from untrusted git-status output without the `resolveWithin` containment check used elsewhere - (File: `app/src/lib/stores/git-store.ts`)

### Summary
GitHub Desktop has a dedicated path-containment primitive, `resolveWithin` (`app/src/lib/path.ts:95-100`), that resolves a path against a root and rejects it (returns `null`) if it escapes the root — including via symlinks, since it calls `realpath` on both root and resolved path before comparing prefixes. This guard is explicitly used in security-sensitive code paths such as `dispatcher.ts`'s `openRepositoryFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1957-1972`) and `app-store.ts`'s `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7233-7239`), both of which reject externally-influenced relative paths that resolve outside the repository root. However, `GitStore.discardChanges` (`app/src/lib/stores/git-store.ts:1545-1649`) performs filesystem deletion/trash operations using raw `Path.resolve`/`Path.join` on `file.path` and `file.status.oldPath` — values that originate directly from parsed `git status --porcelain -z` output (`app/src/lib/status-parser.ts`) — with no equivalent containment check.

### Finding Description
`discardChanges` builds two lists (`pathsToCheckout`, `pathsToReset`) and, for files not identified as submodules, immediately acts on the filesystem: [1](#0-0) 

Both the trash path (`this.shell.moveItemToTrash(Path.resolve(this.repository.path, file.path))`) and the permanent-delete fallback path (`rm(Path.join(this.repository.path, file.path))`) trust `file.path` (and, for renamed/copied entries, `file.status.oldPath`) to be a safe, repo-relative path. These values are populated straight from git's own status output by `buildStatusMap`/`convertToAppStatus` (`app/src/lib/git/status.ts:297-334`), which in turn comes from `parsePorcelainStatus` (`app/src/lib/status-parser.ts:105-182`) — a raw regex/string extraction with no path-traversal or containment validation.

This is the same broken invariant as the reported smart-contract issue: a value that can grow/deviate beyond what the caller expects (there: payment amount past a price threshold; here: a filesystem path past the repository boundary) is consumed directly by a state-changing operation without ever being checked against an expected bound (there: `maxAmount`; here: `resolveWithin`/repo root containment).

### Impact Explanation
If a crafted working tree entry (e.g., a path/oldPath value that traverses through an intermediate symlinked directory checked out from a malicious repository) is ever reported by `git status` as untracked/modified/renamed and the user invokes "Discard Changes" on it, `discardChanges` would call `moveItemToTrash` or `rm` on a path built without any repo-containment check — unlike the equivalent, already-guarded code paths in `dispatcher.ts` and `app-store.ts`. That could result in deletion of a file outside the repository, i.e. attacker-influenced destructive file operations triggered by a normal "discard" action on a cloned repository.

### Likelihood Explanation
I could not fully confirm exploitability. `git status` paths normally can't syntactically contain `..` traversal since they name real filesystem entries under the repo root, and I was unable to verify (within available tool calls) whether `app-shell.ts`'s `moveItemToTrash`/`rm` calls follow symlinked *intermediate* directory components the way `resolveWithin`'s `realpath`-based check is designed to catch, nor whether Desktop's checkout process would ever place a symlinked directory in a position that lets a subsequent status entry's `path`/`oldPath` traverse outside the repo. Given the existence of dedicated tests for exactly this symlink-traversal scenario against `resolveWithin` (`app/test/unit/path-test.ts:65-101`), the maintainers clearly consider "symlinked directory used to escape repo root via a git-status-derived path" a realistic threat model elsewhere in the codebase; `discardChanges` is the one destructive, user-triggerable data flow that does not receive that same protection. This should be treated as a defense-in-depth gap needing verification rather than a confirmed, actively exploitable path.

### Recommendation
Route `file.path` and `file.status.oldPath` through `resolveWithin(repository.path, file.path)` (mirroring `dispatcher.ts` and `app-store.ts`) before calling `this.shell.moveItemToTrash(...)` or `rm(...)` in `GitStore.discardChanges`, and skip/log-and-abort the operation if the resolution returns `null`, exactly as `_applyCopilotConflictResolutions` already does for its Copilot-written paths.

### Proof of Concept
I do not have a verified, concrete reproduction (e.g., a crafted repository fixture proving `git status` can surface a traversal-capable `path`/`oldPath` that `discardChanges` would act on outside the repo root). This would need to be constructed and tested against `app-shell.ts`'s actual trash/rm implementation to confirm whether the missing `resolveWithin` check is reachable in practice, which I was unable to complete within this investigation.
