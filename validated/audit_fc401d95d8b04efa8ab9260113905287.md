### Title
Blame proof generated before PoP verification lets a malicious participant replay another sender's encryption key and recover the victim's ECDH cipher key, leaking all secret shares addressed to the victim - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
Analogous to CVE-2016-0777 (a remote peer coerces the client into transmitting secret buffer contents), an unprivileged DKG participant can coerce an honest `KeyMachine` into emitting an `EncryptionKeyProof` that reveals `enc_key * msg.key` for an attacker-chosen `msg.key` — before the message's proof-of-possession is ever verified. Because `msg.key` is a public field of the broadcast `EncryptedMessage`, the attacker replays an honest sender's per-message key `K_j`, and the victim's blame output reveals the exact cipher key decrypting that honest sender's secret share to the victim.

### Finding Description
In `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:463-499), each incoming `EncryptedMessage` is processed by `self.encryption.decrypt(...)`. Inside `decrypt` (crypto/dkg/pedpop/src/encryption.rs:469-501):

- The per-message PoP (`msg.pop`) is only *queued* into the batch verifier (line 479-485), not checked.
- The ECDH shared key `key = ecdh(&self.enc_key, msg.key)` is computed and the ciphertext decrypted (line 487-488).
- An `EncryptionKeyProof { key, dleq }` — which publicly reveals the shared ECDH point — is constructed unconditionally (lines 491-499).

Back in `calculate_share`, `C::F::from_repr(share_bytes.0)` is checked at line 480 with `?` — an early return that fires *before* `batch.verify_with_vartime_blame()` at line 493. The error carries `blame: Some(blame.clone())`, i.e., the already-constructed `EncryptionKeyProof`. For a 32-byte scalar repr over the ed25519/Ristretto field (~2^252), random garbage decrypts to a non-canonical scalar with overwhelming probability, so the early return is reliably triggered.

An attacker therefore:

1. Observes honest participant j's `EncryptedMessage` to the victim — all shares are relayed through/broadcast via the coordinator (`CoordinatorMessage::Shares`, processor/src/key_gen.rs:370-474), so `msg.key` (`K_j`) is public.
2. Sends their own `EncryptedMessage` to the victim with `key = K_j`, arbitrary ciphertext, and a *forged* `pop` (which is never verified because the early return preempts the batch check).
3. Receives (or observes the broadcast of) `InvalidShare { blame: Some(EncryptionKeyProof) }`, revealing `enc_key_victim * K_j` — the ChaCha20 cipher key for honest sender j's share.
4. Decrypts j's real share offline. Repeating for every sender yields all shares addressed to the victim; `calculate_share` sums them (line 484), so the attacker recovers the victim's full secret share.

### Impact Explanation
Recovery of a validator's threshold secret share. The victim broadcasts the blame proof (`ProcessorMessage::InvalidShare { blame }`, processor/src/key_gen.rs:419-425), so the attacker learns `enc_key * K_j` for every honest sender j, decrypts every share intended for the victim, and reconstructs the victim's private FROST share — degrading the threshold security by one full party and enabling targeted follow-on compromise of the group key.

### Likelihood Explanation
Requires only participation in a DKG session and the ability to submit a crafted share message — no collusion, no malicious coordinator. The trigger is deterministic on the attacker's side (a random-decoding ciphertext fails `from_repr` with ~90% probability per attempt for Ristretto, and can be retried; even the canonical-decode path reaches a failing batch statement for `Share(l)` whose error also returns `Some(blame)`).

### Recommendation
Verify `msg.pop` (the PoP) *before* constructing or returning the `EncryptionKeyProof`. In `Encryption::decrypt`, perform `msg.pop.verify(...)` synchronously (as `decrypt_with_proof` does at encryption.rs:374-379) and refuse to produce a blame proof for a message whose PoP is invalid. Additionally, do not build the `EncryptionKeyProof` until the decrypted share has passed `from_repr` and share verification, so the ECDH key is revealed only for a properly authenticated, binding message.

### Proof of Concept
1. Attacker E and honest parties run PedPoP; victim V registers `enc_pub_key_V`.
2. Honest sender j broadcasts `EncryptedMessage { key: K_j, pop, msg: C_j }` to V (visible to E via the coordinator `Shares` message).
3. E sends V `EncryptedMessage { key: K_j, pop: garbage, msg: random_bytes }`.
4. `V.calculate_share` → `decrypt` queues the bogus PoP, computes `key = enc_key_V * K_j`, builds `EncryptionKeyProof { key, dleq }`, decrypts to garbage; `from_repr` fails → returns `InvalidShare { participant: E, blame: Some(proof) }` before batch verification.
5. E reads `proof.key = enc_key_V * K_j`, derives `cipher(context, proof.key)`, decrypts `C_j` → j's share to V.
6. Repeat for all senders; sum recovered shares = V's secret share.
