### Title
`send()` in the Bank precompile is missing the `EVMPrecompileCalledFromDelegateCall` guard that its sibling `sendNative()` has, letting a malicious contract impersonate the registered ERC20-native pointer and move arbitrary users' native-denom balances - (File: `precompiles/bank/bank.go`)

### Summary
The Sei Bank precompile exposes two transfer entry points, `send` (denom-based, ERC20-pointer-gated) and `sendNative` (usei/wei-gated). `sendNative` explicitly rejects delegatecall invocation with `ctx.EVMPrecompileCalledFromDelegateCall()`, but `send` has no such check, even though `send`'s only authorization gate is `pointer.Cmp(caller) != 0` — an address-equality check that can be satisfied via delegatecall context. This is the same bug class as the reported `VirtualAccount.payableCall` issue: a sibling function correctly enforces an access-control check that is silently omitted from another function performing an equivalent privileged action.

### Finding Description
`precompiles/bank/bank.go` defines `send()` at line 198 and `sendNative()` at line 251: [1](#0-0) 

`send()`'s only access control is:
```go
pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
if !exists || pointer.Cmp(caller) != 0 {
    return nil, 0, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
}
```
This is meant to ensure only the officially registered `ERC20NativePointer` contract for a given denom can invoke `bank.send` to move that denom on a user's behalf (the pointer contract enforces its own ERC20 `transfer`/`transferFrom` semantics before delegating to the precompile).

By contrast, `sendNative()` explicitly refuses delegatecall entry: [2](#0-1) 
```go
if ctx.EVMPrecompileCalledFromDelegateCall() {
    return nil, 0, errors.New("cannot delegatecall sendNative")
}
```

`send()` lacks this check entirely. The `caller` parameter passed into `Execute`/`send` is the same regardless of whether the precompile is invoked via `CALL` or `DELEGATECALL` from the perspective of the pointer/authorization equality check (`pointer.Cmp(caller)`), while `callingContract` differs to indicate the actual code-context address. Since `send()` never inspects `callingContract` or `ctx.EVMPrecompileCalledFromDelegateCall()`, any attacker contract that structures its call so that `caller` resolves to the registered pointer address for a target denom (i.e., via a delegatecall relationship analogous to the pattern blocked in `sendNative`, `wasmd.execute`'s pointer-callingContract check, and the `pointer`/`staking`/`gov` precompiles' `caller.Cmp(callingContract) != 0` guards) bypasses the intended "only the pointer contract itself may invoke `send`" restriction.

Every other privileged precompile entry point in the codebase (`pointer.go` Execute, `staking.go` Execute, `gov.go` Execute, `wasmd.go` execute/instantiate) implements one of these two guards — `caller.Cmp(callingContract) != 0` or `ctx.EVMPrecompileCalledFromDelegateCall()` — specifically to prevent a delegatecall from smuggling an unauthorized `caller` context into privileged logic: [3](#0-2) [4](#0-3) [5](#0-4) 

`send()`'s omission of an equivalent guard is the missing-access-modifier analog to the `VirtualAccount.payableCall` finding: the intended check ("only the registered pointer contract can move this denom") can be circumvented via a delegatecall vector that the developers clearly anticipated and blocked in the adjacent `sendNative` function, but forgot to replicate in `send`.

### Impact Explanation
If exploitable, this allows an attacker-controlled contract to invoke `banktypes.MsgSend` moving any user's balance of a pointer-registered denom between arbitrary Sei addresses without the legitimate pointer contract's ERC20 authorization logic (balance/allowance checks) being enforced, resulting in direct theft of user funds — a concrete fund-loss impact.

### Likelihood Explanation
Likelihood is **uncertain without deeper verification** of exactly how `caller`/`callingContract` are populated for `DELEGATECALL` at the EVM-precompile dispatch layer for this newer `PrecompileExecutor` interface (as opposed to the legacy `Precompile.Run` interface). The pattern is strongly suggestive — the exact same guard exists in the sibling `sendNative` function and in every other stateful precompile (`pointer`, `staking`, `gov`, `wasmd`) — which indicates the Sei developers know this delegatecall vector is real and dangerous for precompiles enforcing `caller`-based authorization, and its absence in `send()` is very likely an oversight rather than an intentional design choice.

### Recommendation
Add the same guard used in `sendNative()` to `send()`:
```go
func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, uint64, error) {
    if readOnly {
        return nil, 0, errors.New("cannot call send from staticcall")
    }
    if ctx.EVMPrecompileCalledFromDelegateCall() {
        return nil, 0, errors.New("cannot delegatecall send")
    }
    ...
```
Alternatively/additionally, pass `callingContract` into `send()` and enforce `caller.Cmp(callingContract) != 0` rejection, consistent with the `pointer`/`staking`/`gov` precompiles, to close the gap defense-in-depth style.

### Proof of Concept
A concrete PoC requires confirming, at the EVM dispatch layer (`x/evm` `Run`/`RunAndCalculateGas` call sites for `PrecompileExecutor.Execute`), the exact semantics of `caller` under `DELEGATECALL` versus `CALL` for this precompile interface — this was not fully verified within the available tool calls and the index does not expose the full dispatch code path with certainty. Conceptually, the exploit pattern mirrors the original report:
1. Attacker deploys `Evil` contract.
2. Attacker gets `Evil` to be invoked in a context where `msg.sender`/`caller` as seen by the Bank precompile equals the registered `ERC20NativePointer` address for a target denom (e.g., by delegatecalling into the precompile from a location where the calling context's `caller` resolves to the pointer's address, exactly as `sendNative`'s explicit rejection of `ctx.EVMPrecompileCalledFromDelegateCall()` is designed to prevent).
3. `Evil` calls `bank.send(victimSeiAddr, attackerSeiAddr, denom, amount)`.
4. `send()`'s only check `pointer.Cmp(caller) != 0` passes because `caller` matches the pointer address, and `banktypes.MsgSend` moves `victim`'s funds to `attacker` without going through the pointer contract's own transfer/allowance logic.

Given the reduced reasoning budget for this pass, I was not able to fully trace the EVM precompile dispatch code (`x/evm/...`) that assigns `caller`/`callingContract` for `PrecompileExecutor.Execute` calls to conclusively prove the delegatecall vector triggers in `send()` exactly as it does for the blocked case in `sendNative()`. I recommend starting a full Devin session with repository access to trace `x/evm`'s precompile call/delegatecall dispatch code to confirm exploitability before treating this as validated.
