## Analysis

The bug-class seed is: a single one-directional state transition (`forbid`) can be applied by a keeper, but there is no counterpart function to reverse it — leaving the target permanently locked out with no governance recourse. I checked several "forbidden/frozen" mechanisms in Hyperbridge — `EvmHost.setFrozenState` (reversible, admin/handler-gated), `HyperFungibleToken.pause/unpause` (reversible), `SimplexPaymaster._deactivateToken` (reversible via re-registration), `BandwidthManager` tier revocation (reversible via `Some(TierConfig)`). All of these have a working reverse path.

The one exception is `pallet-fishermen`'s blacklist calls, which are explicitly documented as permanent with **no unblacklist extrinsic**, and unlike every other privileged action in the pallet (which requires collator-set membership but is otherwise checked), a single collator finalizes the block without quorum.

### Title
Single-collator, quorum-less, irreversible blacklist of dispute-game/arbitrum-claim proofs can permanently block legitimate consensus verification with no recovery path - ([File: modules/pallets/fishermen/src/lib.rs])

### Summary
`blacklist_dispute_game` and `blacklist_arbitrum_claim` in `pallet-fishermen` let **any single** account in the active collator set permanently block a specific `(state_machine_id, proxy)` or `(state_machine_id, claim)` pair from ever being accepted as valid by the OP-stack / Arbitrum consensus verifiers. There is no quorum requirement and — critically — no `unblacklist` extrinsic exists anywhere in the pallet to undo an erroneous or premature blacklist entry.

### Finding Description [1](#0-0) 

The doc comment on `blacklist_dispute_game` explicitly states: *"The entry is permanent (there is no `unblacklist` extrinsic) — the consensus verifier will refuse any future `OpFaultProofGames` consensus proof that references this proxy."* The same is true for `blacklist_arbitrum_claim`. [2](#0-1) 

Both calls are guarded only by `T::IsCollator::contains(&account)` — membership in the active collator set — with **no quorum** (contrast with `veto_state_commitment`, which is also single-signer but only deletes an as-yet-unfinalized commitment still inside its challenge window, not a permanent global block). Once inserted, `BlacklistedDisputeGames`/`BlacklistedArbitrumClaims` are read by the OP-stack and Arbitrum `verify_consensus` implementations to permanently reject any future proof referencing that key: [3](#0-2) 

This is the direct analog of the seed report's pattern: a keeper can flip a "forbidden" flag that gates access to a shared resource (here, consensus proof acceptance for a specific dispute-game/claim identity), and the system provides no function — governance, root, or otherwise — to reverse it, contrasted directly with `EvmHost.setFrozenState`, which is fully reversible by admin/handler: [4](#0-3) 

### Impact Explanation
If a collator blacklists a dispute-game proxy or arbitrum claim in error (bug, misconfigured watcher, race with a subsequent legitimate resolution, or a since-corrected fraud determination), that specific proof identity is rejected by the consensus verifier forever. Because dispute games/claims are typically tied to a specific assertion/withdrawal, any state commitment whose validity depends on that finalized game or claim can never again be accepted through the affected consensus client, permanently blocking finalization of legitimate cross-chain requests/responses (and any withdrawals or settlements gated behind that state proof) — a fund-lock condition with no recovery mechanism, since even root/governance has no extrinsic to clear the entry.

### Likelihood Explanation
Likelihood is driven purely by the missing safety valve, not by attacker sophistication: any one of the (potentially many) active collators can trigger this with a single, unquorate, `Pays::No` extrinsic — no proof of fraud is required for the call to succeed on-chain (fraud proof gathering happens off-chain in the fisherman watcher, but the pallet call itself accepts the assertion at face value). A single mistaken or premature call is irreversible and requires no privileged access beyond ordinary collator status.

### Recommendation
Add a governance-gated (e.g. `EnsureRoot` or the technical-collective origin already used elsewhere in these runtimes) `unblacklist_dispute_game` / `unblacklist_arbitrum_claim` extrinsic that removes an entry from `BlacklistedDisputeGames` / `BlacklistedArbitrumClaims`, mirroring the recovery path that already exists for `HostFrozen` (`setFrozenState`) and pausable apps (`pause`/`unpause`). Consider also requiring a quorum (or a challenge/veto window) before a blacklist entry becomes binding, consistent with the challenge-period model used for state commitments elsewhere in the protocol.

### Proof of Concept
1. Collator `C` (a legitimate member of `T::IsCollator`) calls `blacklist_dispute_game(state_machine_id, proxy)` for a dispute-game proxy that is actually valid (e.g. due to a bug in the off-chain fisherman watcher, or because the dispute was later correctly resolved in the proxy's favor).
2. `BlacklistedDisputeGames::<T>::insert(state_machine_id, proxy, C)` is written; `DisputeGameBlacklisted` is emitted.
3. Any subsequent, otherwise-valid `OpFaultProofGames` consensus proof referencing `proxy` is permanently rejected by `pallet-ismp-optimism::verify_consensus` via `FishermanBlacklist::is_dispute_game_blacklisted`.
4. No extrinsic exists in `pallet-fishermen` (checked entire `#[pallet::call]` block, call indices 0–2 only) to remove the entry — not even under `EnsureRoot` — permanently blocking any withdrawal/settlement that depends on proving state finalized by that dispute game.
