## Finding: Unvalidated PR `head.repo.clone_url` reaches `git remote add`, enabling attacker-controlled remote URL injection

### Title
Unvalidated `clone_url` from PR API object flows into `git remote add` with no scheme/transport restriction - (File: `app/src/lib/git/remote.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
`addRemote` shells out to `git remote add <name> <url>` with the raw `url` argument and applies no validation of the URL's scheme or form. `_findPullRequestBranch` in `app-store.ts` passes `headCloneUrl`, which originates from a GitHub API pull-request object's `head.repo.clone_url` field, straight into `addRemote` whenever no existing remote already matches that URL.

### Finding Description
The sink: [1](#0-0) 

The taint path: [2](#0-1) 

Callers feed `pullRequest.head.repo.clone_url` (a GitHub API object field) directly as `headCloneUrl`, both from the "Open in Desktop" URL/deep-link handler and from the normal PR-checkout/cherry-pick UI flows: [3](#0-2) [4](#0-3) 

No code path between the API response and `git(['remote', 'add', name, url], ...)` inspects the URL's scheme (e.g. to reject `ext::`, `fd::`, or arbitrary local paths). `envForRemoteOperation`/`envForProxy`, the only URL-aware helper in the remote-operation pipeline, only pattern-matches `^https?://` to decide whether to set a proxy — it does not gate or reject any other scheme, and it isn't even invoked by `addRemote` at all: [5](#0-4) [6](#0-5) 

No `GIT_ALLOW_PROTOCOL`/`GIT_PROTOCOL_FROM_USER` environment restriction is set anywhere in the codebase (confirmed by search), so Git's own transport-helper mechanism (`ext::<shell command>`) is free to execute whatever the URL specifies once `git fetch`/`git remote add` (which itself triggers a `ls-remote`-style handshake in some Git versions) or a subsequent `_fetchRemote` call runs against that remote: [7](#0-6) 

The URL-matching guard `urlMatchesRemote` only prevents *re-adding* a remote that already exists with a matching URL; it performs no allow-listing of schemes for the value that eventually gets written by `addRemote`: [8](#0-7) 

### Impact Explanation
If a malicious/compromised API endpoint (or a GitHub Enterprise Server instance the user has added, or an MITM position on a non-pinned connection) returns a pull-request JSON object whose `head.repo.clone_url` is `ext::sh -c "..."` (or a `file://`/local-path style value), that string is written verbatim as a `git remote add` argument. Git's `ext::` transport helper runs an arbitrary shell command as soon as the remote is actually contacted (which happens automatically in the same code path via `_fetchRemote`). This yields command execution under the user's own privileges — a critical impact per the program's stated "code execution ... git remote/proxy response" impact criterion.

### Likelihood Explanation
The likelihood is constrained by the realistic threat model: on real github.com, `clone_url` is server-generated and always a well-formed `https://github.com/...` URL, so an attacker cannot directly control this field for public GitHub repos/PRs. Exploitation requires the victim to be pointed at an API endpoint the attacker controls or can tamper with (a malicious/compromised GitHub Enterprise Server the user has added as an account, or a MITM/DNS-spoofing position against an unpinned HTTPS connection to an Enterprise instance). This is a narrower likelihood than "any public PR," but it is squarely inside the program's stated valid-impact category of an attacker-controlled "GitHub API object," and none of the existing checks in the traced code (`urlMatchesRemote`, `envForProxy`'s `^https?://` regex, or any Git protocol allow-list) actually block a malicious scheme from reaching `git remote add`.

### Recommendation
Validate `headCloneUrl` (and any other API-supplied clone/remote URL, e.g. `parent.cloneURL`, `apiRepository.clone_url`, `gitHubRepository.cloneURL`) before it is passed to `addRemote`/`setRemoteURL`: reject any URL whose scheme is not one of `https`, `http`, `ssh`, or `git`, and reject bare paths. Additionally, set `GIT_ALLOW_PROTOCOL` (or the modern `protocol.*.allow` config) in `envForRemoteOperation`/`git` invocation defaults to explicitly deny `ext`, `fd`, `file`, and other local/command transports for all remote operations initiated on behalf of the user from untrusted API data.

### Proof of Concept
Not independently executed (index/tooling limitations prevent running the test suite), but based on the traced code:
1. Add a GitHub Enterprise account pointing at an attacker-controlled or MITM'd API server.
2. Have that server return a pull-request JSON object where `head.repo.clone_url = "ext::sh -c \"touch /tmp/pwned\""`.
3. Trigger PR checkout (`_checkoutPullRequest`/`_findPullRequestBranch`, reachable via UI "Checkout PR" or via the `x-github-client://openPR` deep link handled by `openPullRequestFromUrl` in `app/src/ui/dispatcher/dispatcher.ts`).
4. Because no existing remote matches this URL, `addRemote(repository, forkRemoteName, headCloneUrl)` executes `git remote add <name> "ext::sh -c \"touch /tmp/pwned\""`.
5. The subsequent `this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)` call triggers Git to invoke the `ext::` helper, executing the attacker's shell command. [9](#0-8)

    if (remote === undefined) {
      try {

        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
