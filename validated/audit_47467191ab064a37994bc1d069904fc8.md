### Title
`ThresholdKeys::read` accepts identity/untrusted verification shares and an inconsistent secret share, fabricating a group key funds can be sent to but never spent from — (File: crypto/dkg/src/lib.rs)

### Summary
The external report describes minting tokens to `address(0)` because the recipient was never validated — value becomes permanently unspendable. The Serai analog is `ThresholdKeys::<C>::read`, which deserializes untrusted bytes into the key set that determines the multisig's `group_key()` — i.e., the destination all scanned/received funds are credited to. It performs no validation that the verification shares or the implied group key are non-identity, nor that `secret_share` is consistent with `verification_shares[i]`, allowing a fabricated group key (including the identity/"zero" key, or a key whose discrete log the attacker knows) to be reported as the wallet's receiving key.

### Finding Description
`ThresholdKeys::read` reconstructs `t`, `n`, `i`, the interpolation coefficients, `secret_share`, and `n` verification shares, then calls `ThresholdKeys::new` [1](#0-0) . Two problems exist:

1. Verification shares are decoded via `<C as Ciphersuite>::read_G`, which does not reject the identity point — unlike `Curve::read_G` in the FROST crate, which explicitly errors on `"identity point"` [2](#0-1) . `ThresholdKeys::read` therefore silently accepts the group-theoretic "zero address" as a participant's key [3](#0-2) .

2. `ThresholdKeys::new` only checks the count of verification shares and that indexes are `<= n`; it never checks that `C::generator() * secret_share == verification_shares[i]` [4](#0-3) . The group key is then derived purely from the attacker-controlled shares, `group_key = Σ verification_shares[i] * interpolation_factor(i)` over `i in 1..=t` [5](#0-4) .

### Impact Explanation
The group key produced by `ThresholdKeys::new`/`view` is what downstream code (e.g., `tweak_keys` → `Scanner::new` → `scan_transaction`) treats as the wallet's receiving identity [6](#0-5) [7](#0-6) . An attacker who supplies crafted `ThresholdKeys` bytes can set every verification share to identity (yielding `group_key = identity`, the exact analog of minting to `address(0)` — outputs are reported received but are unspendable) or set the shares so the derived group key has a discrete log known to the attacker (funds received are stealable). Since the `secret_share` is never checked against `verification_shares[i]`, the node will also produce FROST signature shares under a group key the legitimate set never agreed to — signing on behalf of an attacker-defined key.

### Likelihood Explanation
Exploitation requires an attacker to feed crafted bytes to `ThresholdKeys::read`, which the scope rules explicitly classify as an untrusted-byte input surface. It does not require malicious validators, collusion, or leaked keys — only delivery of malicious serialized key material to a code path that deserializes it. Once accepted, every subsequent `view`/`sign_share`/`scan` operates on the fabricated key, so the impact is persistent, not one-shot.

### Recommendation
- In `ThresholdKeys::read` (or `ThresholdKeys::new`), reject identity verification shares (use the identity-rejecting `read_G` behavior or check `is_identity` on each share and on the computed `group_key`).
- Verify `C::generator() * secret_share == verification_shares[i]` before returning, so the deserialized secret share is provably bound to the declared participant's verification share.

### Proof of Concept
1. Construct serialized `ThresholdKeys` bytes for `t = n = 1`: valid `C::ID`, `t=1`, `n=1`, `i=1`, `Interpolation::Lagrange`, arbitrary `secret_share`, and one verification share encoded as the identity point.
2. Call `ThresholdKeys::<C>::read(&mut bytes)`. Because `read_G` does not reject identity and `ThresholdKeys::new` only validates share count/index range, deserialization succeeds.
3. `keys.group_key()` returns the identity point. `Scanner::new`/P2TR derivation downstream treats this as the receiving key; outputs paid to it are reported as received yet are unspendable — the same loss-of-funds outcome as minting to `address(0)`. Substituting shares whose sum is `a·G` for an attacker-known `a` instead yields a receiving key the attacker alone can spend from.

Caveat: I verified that `Ciphersuite::read_G` paths in-scope (e.g., dalek-ff-group's `from_bytes`) accept identity encodings and that `ThresholdKeys::new` performs no share-consistency check; I could not fully trace every upstream caller of `ThresholdKeys::read` to confirm exactly where hostile serialized key material crosses a trust boundary within the in-scope crates.
