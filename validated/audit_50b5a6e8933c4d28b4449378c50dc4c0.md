### Title
FROST preprocess seed left in memory via un-zeroized `ChaCha20Rng` state enables key share recovery from memory dumps - (File: crypto/frost/src/sign.rs)

### Summary
`AlgorithmMachine::seeded_preprocess` copies the `CachedPreprocess` seed into a `ChaCha20Rng`, which retains the raw 32-byte seed as its stream key in its internal state. That RNG is dropped without zeroization, leaving the seed — a value Serai documents as requiring "the same security as your private key share" — recoverable from a memory dump, heap snapshot, or core dump.

### Finding Description
The external report describes secrets persisted in memory without explicit clearing (CWE-316). Serai is generally disciplined (`Zeroizing` wrappers, manual `zeroize()` calls), but in `crypto/frost/src/sign.rs` the preprocess seed escapes that discipline:

```rust
// crypto/frost/src/sign.rs:127
let mut rng = ChaCha20Rng::from_seed(*seed.0);
let (nonces, commitments) = Commitments::new::<_>(
  &mut rng,
  params.keys.original_secret_share(),
  &params.algorithm.nonces(),
);
let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);
```

`ChaCha20Rng::from_seed` stores the seed as the ChaCha key inside the RNG state. When `seeded_preprocess` returns, `rng` is dropped normally; neither `ChaCha20Rng` nor `rand_chacha`'s state implements `ZeroizeOnDrop`, so the seed bytes remain in freed heap/stack memory. The same pattern occurs in `AlgorithmSignatureMachine::complete` (sign.rs:473) with `blame_entropy`, though that value is less sensitive.

The library itself states the severity of this value: `CachedPreprocess` "MUST be handled with the same security as your private key share, as knowledge of it also enables recovery" (sign.rs:86-87). From the seed, anyone can re-derive the exact `(d, e)` nonces via `ChaCha20Rng` replay, and each published signature share `s_i = nonce + c·λ_i·secret_i` then trivially yields `secret_i`.

### Impact Explanation
An unprivileged co-signer (or any party who obtains a signature share, which is broadcast) who captures a memory dump of the signing process — via a debugger, core dump, swap, hibernation image, or heap inspection — recovers the victim's FROST secret share. Combined with threshold-many compromised/dumped shares, or combined with the attacker's own shares in a `t`-of-`n` where the attacker already holds `t-1` shares, this yields full group key recovery and arbitrary signature forgery. This matches the advisory's threat model (memory access techniques → session/key compromise) mapped onto Serai's highest-value secret material.

### Likelihood Explanation
Medium. Exploitation requires memory-read capability on a host running FROST signing, which is a stronger prerequisite than a pure network attack — hence not High. However, the window is large: the RNG state persists in memory for the entire lifetime of the process's allocator reuse (indefinitely), across every preprocess generated, and the `coordinator` path (`preprocess_internal` in `coordinator/src/tributary/signing_protocol.rs:107-145`) decrypts and seeds from the same `CachedPreprocess` on every signing operation, multiplying exposure.

### Recommendation
Zeroize the RNG state before drop. Options:
- Wrap the RNG usage so the seed is re-zeroized: generate nonces from the seed, then explicitly `rng = ChaCha20Rng::from_seed([0; 32])` or write zeros into the state before the end of `seeded_preprocess`.
- Prefer streaming nonce generation directly from `Zeroizing` buffers (e.g., use `seed` to key a `ChaCha20` cipher over a `Zeroizing` keystream buffer) rather than a resident RNG object.
- Apply the same treatment to the `ChaCha20Rng::from_seed(self.blame_entropy)` in `complete` for consistency, and consider deriving `blame_entropy` from a public transcript instead.

### Proof of Concept
Conceptual: on a host running `AlgorithmSignMachine::sign` (or `from_cache`), trigger a core dump (e.g., `gcore`) after `seeded_preprocess` has executed but while freed heap pages are un-reclaimed. Search the dump for the 32-byte `CachedPreprocess` value (known-attacker scenario: encrypt the known cached value via the coordinator's `Cached Preprocess Encryption Key` derivation, or test candidate seeds by feeding each into `ChaCha20Rng::from_seed`, regenerating `Commitments::new`, and checking whether the resulting `GeneratorCommitments` match the victim's published `Preprocess.commitments`). A matching seed confirms recovery; the victim's share from `SignatureShare` then yields `secret_i = (s_i - nonce) / (c·λ_i)`.
