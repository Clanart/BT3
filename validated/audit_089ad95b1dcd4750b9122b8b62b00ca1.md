## Finding [1](#0-0) 

### Title
Escrow release (`withdraw`) on the Tron IntentGatewayV2 trusts the raw call-success flag instead of the ERC-20 return value, letting a non-reverting "returns false" token silently finalize withdrawals with zero funds delivered - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` and the `SweepDust` handler in the Tron variant of `IntentGatewayV2.sol` move escrowed ERC-20 tokens with a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the *call itself* didn't revert, not that the token's `transfer` actually returned `true`. [2](#0-1)  This is exactly the "malicious ERC20 token" pattern from the external report: a token that returns `false` on a failed transfer (instead of reverting) will make `success == true` while no tokens move, yet the contract proceeds to decrement escrow and mark the order finalized.

### Finding Description
`withdraw(WithdrawalRequest memory body, bool isRefund)` is invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` request kinds — a normal, unprivileged cross-chain settlement path reachable whenever a solver fills or a user cancels an order. [3](#0-2) 

Inside `withdraw`, before any transfer is attempted the beneficiary is finalized (`_filled[body.commitment] = beneficiary;`), and for each token the escrow accounting is decremented unconditionally after the raw call, based only on `success`: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    } else {
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
    }
    _orders[body.commitment][token] -= amount;
```

A low-level `.call` only reverts (`success == false`) if the callee reverts or the address has no code. A non-standard/malicious ERC-20 that implements `transfer` to simply `return false;` on failure (rather than reverting) is fully compliant with the low-level ABI call semantics: `success` is `true`, `TransferFailed()` never fires, and the code proceeds to decrement the escrow ledger and mark the order filled/refunded — even though the beneficiary received nothing.

This contrasts with the same logic on the standard EVM build, `IntentsBase._withdraw`, which uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and enforces the boolean return value and reverts on `false`: [4](#0-3)  The Tron contract deliberately re-implements the transfer with a raw `.call` instead of `SafeERC20`, dropping this guarantee. The same unguarded pattern also affects the `SweepDust` handler used for protocol dust withdrawals. [5](#0-4) 

### Impact Explanation
Once escrow is decremented and `_filled[commitment]` is set to the beneficiary without the tokens ever actually leaving the contract, the accounting and the on-chain custody diverge permanently: the escrowed balance is "spent" in the ledger, the order can never be re-redeemed or refunded again (finalized state), and the tokens remain trapped in the gateway with no code path to recover them for the rightful beneficiary. This is a direct loss of bridged/escrowed funds tied to custody-release logic that Hyperbridge's own pivot describes as needing to "move exactly once and only to the rightful beneficiary and amount." Any order whose input token is a non-standard ERC-20 (self-selected by the unprivileged order creator, per the intent-gateway's open token design) is affected — no malicious relayer, prover, or governance actor is required.

### Likelihood Explanation
The order creator (an ordinary, unprivileged user placing an order via `placeOrder`) unilaterally selects the input token for their own order, and the settlement/withdrawal path (`onAccept` → `withdraw`) fires automatically as part of the normal cross-chain fill/cancel flow — no special relayer collusion or admin action is needed. The only prerequisite is that the input token's `transfer` function returns `false` on failure instead of reverting, which is a known, real-world ERC-20 non-compliance pattern (and is exactly the "malicious ERC20" class flagged in the source report).

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (as already used elsewhere in the codebase, e.g. `IntentsBase.sol`), which decodes and enforces the ERC-20 boolean return value and reverts on failure. Additionally, consider verifying actual balance deltas around these transfers to defend against tokens with fee-on-transfer/rebasing behavior, consistent with the balance-diff pattern already used in `IntentGatewayV2.placeOrder`. [6](#0-5) 

### Proof of Concept
1. User deploys/uses a token `T` whose `transfer(address,uint256)` returns `false` on failure instead of reverting (compliant with the raw ABI call, non-compliant with the honest-ERC20 assumption).
2. User calls `placeOrder` on the source chain escrowing `T` as an input token; escrow entry `_orders[commitment][T] = amount` is recorded.
3. A solver fills the order on the destination chain; `RedeemEscrow` is dispatched back to source and delivered via `onAccept` → `withdraw`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` is executed against `T`; `T` internally decides to return `false` (e.g., simulating an internal restriction/rug condition) without reverting.
5. `success == true` (the low-level call did not revert), so `TransferFailed()` is never triggered; `_orders[body.commitment][T] -= amount;` executes and `_filled[commitment]` is already set to the beneficiary.
6. Result: the beneficiary's `T` balance is unchanged (funds never delivered), the order is permanently marked filled/refunded, and the escrowed `T` remains locked in the gateway with no remaining code path to reclaim it — a silent, unrecoverable loss of the escrowed funds.
