### Title
Fail-open PreToolUse rule evaluation in the `hookify` plugin lets a single malformed rule silently disable all block/deny rules for a tool call - ([File: plugins/hookify/hooks/pretooluse.py])

### Summary
The Canto report describes a class of bug where a batch-processing function encounters an error partway through, silently stops processing the remaining items without surfacing the error, and the caller proceeds as if nothing happened — permanently breaking an authorization/registration invariant. The `hookify` plugin bundled in this repo (`plugins/hookify`) reproduces the same failure pattern in Claude Code's `PreToolUse` tool-authorization trust boundary: rule evaluation happens in an unguarded loop, and any single rule that throws an exception aborts evaluation of *every* rule (including `action: block` deny rules) with the top-level handler defaulting to "allow."

### Finding Description
`pretooluse.py::main()` reads hook input, loads `.claude/hookify.*.local.md` rule files with `load_rules()`, and evaluates them with `RuleEngine.evaluate_rules()` [1](#0-0) . `evaluate_rules()` iterates over the full rule list and calls `_rule_matches()` for each rule with **no per-rule try/except** [2](#0-1) . `_rule_matches()` in turn calls `_check_condition()`/`_extract_field()` for each condition, and these methods can raise uncaught exceptions — e.g. `_check_condition` calls `pattern in field_value`, `field_value.startswith(pattern)`, or `field_value.endswith(pattern)` without a type guard: if a `.claude/hookify.*.local.md` file (attacker- or accidentally-authored) supplies a condition whose `field_value` resolves to `None`/non-string in a code path that bypasses the `None` check, or whose `pattern` is a non-string type, a `TypeError`/`AttributeError` propagates all the way up through `_rule_matches` and `evaluate_rules` [3](#0-2) .

Exactly like the Canto `processEvents` bug — where one failing event handler aborted the loop and left `PostTxProcessing` to continue as if nothing failed — this exception is caught only by the *outer* generic handler in `pretooluse.py`, which treats **any** failure as "allow the operation":
```
except Exception as e:
    error_output = {"systemMessage": f"Hookify error: {str(e)}"}
    print(json.dumps(error_output), file=sys.stdout)
finally:
    sys.exit(0)  # ALWAYS exit 0 - never block operations due to hook errors
``` [4](#0-3) 

Because rules are evaluated in a single list without isolation, one bad/unlucky rule (out of potentially many independent security rules a team maintains) is enough to make the entire batch fail and short-circuit to allow — deny (`action: block`) rules that would have matched the very tool call under evaluation are simply never reached. This mirrors the Canto report's core defect: "if [handling] the first event returns an error, then all of the events will not be handled... and the caller continues to execute normally without any error."

### Impact Explanation
This breaks the `PreToolUse` tool-authorization trust boundary: a project's `.claude/hookify.*.local.md` deny/block rules (e.g. blocking `rm -rf`, credential-file writes, path traversal) can be silently bypassed for the specific tool call whose input happens to trigger a condition-evaluation exception in *any* rule file loaded for that event, not just the rule targeting that tool call. This is a genuine "hook bypass / tool authorization" trust-boundary defect within the allowed analog categories, since the plugin ships in this repo (`plugins/hookify`) and is designed specifically to provide blocking security guardrails via `PreToolUse`.

### Likelihood Explanation
Reaching this requires: (1) the `hookify` plugin enabled with at least one `action: block` rule, and (2) any rule file (from the same project, or any other plugin/rule sharing the same event evaluation batch) supplying a condition that raises at runtime — plausible via a `contains`/`starts_with`/`ends_with` condition whose `pattern` or extracted field takes on a non-string type through `frontmatter` values that the hand-rolled YAML-subset parser in `config_loader.py::extract_frontmatter` coerces to booleans/ints in edge cases, or a `MultiEdit` field concatenation edge case. This is not attacker-controlled from a remote/network actor, but it is reachable by an ordinary project maintainer/unprivileged contributor who can add or edit a `.claude/hookify.*.local.md` rule file — no elevated Claude Code privilege is needed to trigger the fail-open condition, only to have any one rule misbehave.

### Recommendation
Wrap each rule's evaluation in `RuleEngine.evaluate_rules()`'s loop (specifically the `_rule_matches` call) in its own try/except that logs the failure and treats that individual rule as "not matched," rather than letting the exception escape and be caught by the outer fail-open handler in `pretooluse.py`/`posttooluse.py`/`stop.py`. Additionally, the outer per-hook handlers should distinguish between "no rules configured" (safe to allow) and "an internal error occurred while evaluating rules" (should not silently discard `block` semantics) — e.g. surface the error via `systemMessage` while still returning `permissionDecision: "ask"` rather than an implicit allow, so a rule-evaluation crash degrades to a prompt instead of an outright bypass.

### Proof of Concept
1. Enable the `hookify` plugin and add one blocking rule, e.g. `.claude/hookify.block-rm.local.md` with `action: block`, `event: bash`, and a condition matching `rm -rf`.
2. Add a second, unrelated `.claude/hookify.broken.local.md` rule with a condition using `operator: starts_with` (or `contains`) whose `field` resolves to a non-string value for some tool input (e.g. a field extracted from `MultiEdit`'s `edits` list edge case, or a condition value that the frontmatter parser leaves as a non-string/boolean due to its bespoke YAML subset parsing in `extract_frontmatter`).
3. Trigger a `Bash` tool call with `rm -rf /important` while the broken rule's condition also gets evaluated (since `evaluate_rules` iterates *all* loaded rules for the event, not just rules matching the current tool).
4. `_check_condition` raises an exception on the broken rule before ever evaluating the `rm -rf` blocking rule; the exception propagates out of `evaluate_rules` to the top-level `except Exception` in `pretooluse.py`, which prints a `systemMessage` and calls `sys.exit(0)` — i.e., no `permissionDecision: "deny"` is emitted, and Claude Code allows the `rm -rf` command to execute despite the intended blocking rule.

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```
