### Title
Receipt tokens minted to caller (pool helper) instead of depositor/`_for` in `WombatStaking.deposit` - (File: wombat/WombatStaking.sol)

### Summary
`WombatStaking.deposit()` mints the wombat receipt token to `msg.sender` (the calling pool helper contract) rather than to the `_for` address that is supposed to receive credit for the deposit [3](#0-2) . This is only safe as long as every pool helper immediately forwards the freshly minted receipt token balance into `MasterMagpie` on behalf of the same address; the accounting for "how much was just received" is done everywhere via `IERC20(stakingToken).balanceOf(address(this))` deltas rather than tracking exact per-call amounts [4](#0-3) .

### Finding Description
Every deposit path (`WombatPoolHelper._deposit`, `WombatPoolHelperV2._deposit`, `AnkrBNBPoolHelper._deposit`, `depositLP`) computes the amount to stake into `MasterMagpie` by taking `balanceOf(address(this))` before and after calling `WombatStaking.deposit`/`depositLP`, then staking the delta for the intended recipient [5](#0-4) . Because `WombatStaking.mint`s the receipt token to `msg.sender` (the helper) instead of to `_for`, and staking amounts are derived purely from a balance snapshot rather than an explicit amount returned/passed from `WombatStaking`, any unrelated receipt-token balance already sitting in the helper contract (e.g., from a prior transaction that reverted after mint, from a stuck partial withdrawal, or from a direct token donation) gets silently included in the "delta" and credited to whichever address happens to call the helper next. This breaks the intended 1:1 mapping between the tokens a specific depositor transferred in and the credit they receive, and it means the pool helper contracts are non-reentrancy-guarded balance-based accounting proxies rather than exact accounting systems.

### Impact Explanation
If a receipt-token balance is ever left resident in a pool helper contract between transactions (unclaimed dust from a reverted downstream call, or in the `batchDepositLPFor` flow in `AnkrBNBPoolHelper` where ratios don't evenly divide `lpAmount`, leaving rounding remainder in the helper) [6](#0-5) , the next unrelated caller who invokes `deposit`/`depositLP` on that same helper will have that leftover balance folded into their own "amount staked" delta and credited to their own `MasterMagpie` position — effectively pulling value that belonged to prior depositors (or was destined for the batch-for addresses) into an unrelated user's stake. Because `MasterMagpie.depositFor` immediately converts this into vote-weighted stake and reward-earning position, this can constitute a theft of value credited to another party.

### Likelihood Explanation
This requires a pre-existing leftover token balance in a pool helper contract, which arises from rounding remainders in `batchDepositLPFor`'s ratio-based split (`lpAmount * _ratios[i] / DENOMINATOR` truncation) [7](#0-6) , or from any other flow where minted receipt tokens are not immediately and fully forwarded to `MasterMagpie`. This is a routine, ordinary-wallet-reachable condition (any user calling `deposit`/`depositLP` on a helper) rather than an admin/governance action, but the exact size of the exploitable dust depends on prior transaction history and may often be small.

### Recommendation
Have `WombatStaking.deposit`/`depositLP` mint receipt tokens directly to `_for` instead of `msg.sender`, and have pool helpers stake only the amount explicitly returned by `WombatStaking` (rather than relying on `balanceOf` deltas), removing the dependency on the helper's transient token balance for crediting deposits.

### Proof of Concept
1. Deploy/observe `AnkrBNBPoolHelper.batchDepositLPFor` called with `_ratios` that don't evenly divide `lpAmount` (e.g., `lpAmount = 100`, three recipients at ratios summing to `DENOMINATOR` but each `lpAmount * ratio / DENOMINATOR` truncates down), leaving `remainder = lpAmount - sum(amount_i)` receipt tokens resident in the helper contract instead of being staked to any `_for` address [8](#0-7) .
2. An ordinary user then calls `depositLP(_lpAmount)` on the same helper contract [9](#0-8) .
3. The helper computes `afterDeposit - beforeDeposit`, which includes both the user's genuinely deposited LP and the leftover remainder from step 1, and stakes the inflated total to the calling user's `MasterMagpie` position via `_stake` → `IMasterMagpie(masterMagpie).depositFor(stakingToken, _amount, msg.sender)` [9](#0-8) , giving the caller credit for tokens they never deposited.

    function batchDepositLPFor(uint256 _lpAmount, address[] calldata _for, uint256[] calldata _ratios) external {
        if (msg.sender != ankrOperator) revert NotAllowed();
        if (_for.length != _ratios.length) revert LengthMisMatch();
        
        uint256 totalRatio=0;
        for(uint256 i=0; i<_ratios.length; ++i){
            totalRatio+=_ratios[i];
        }
        if(totalRatio != DENOMINATOR) revert NotAllowed();

        uint256 beforeDeposit = IERC20(stakingToken).balanceOf(address(this));
        IWombatStaking(wombatStaking).depositLP(lpToken, _lpAmount, msg.sender);
        uint256 lpAmount = IERC20(stakingToken).balanceOf(address(this)) - beforeDeposit;

        IERC20(stakingToken).safeApprove(masterMagpie, lpAmount);

        for (uint256 i = 0; i < _for.length; i++) {
            uint256 amount = lpAmount * _ratios[i] / DENOMINATOR;
            lockedAmount[_for[i]] += amount;
            IMasterMagpie(masterMagpie).depositFor(stakingToken, amount, _for[i]);
            emit NewBatchDeposit(_for[i], amount);
        }
    }
