### Title
Unhandled `AssertionError` in NFT metadata/condition parsing crashes wallet sync (analogous NULL/missing-value dereference DoS) - ([File: chia/wallet/nft_wallet/nft_puzzle_utils.py])

### Summary
The Bento4 CVE is a NULL-pointer dereference reached when parsing untrusted, attacker-crafted metadata that omits an expected sub-structure, causing an unhandled crash of the consuming process. The closest reachable analog in this codebase is in `get_metadata_and_phs()` in `chia/wallet/nft_wallet/nft_puzzle_utils.py`, which parses the *inner solution* of an NFT coin spend (data that originates from whatever spend was broadcast/accepted on-chain — i.e., attacker-controlled at the CLVM level) and blindly assumes a `CREATE_COIN` condition with a specific memo structure will be present.

### Finding Description
`get_metadata_and_phs` iterates over the conditions produced by running the p2 puzzle/solution of an NFT coin spend and looks for a `CREATE_COIN` condition (opcode 51) whose `atom == 1` marker indicates "this is the destination puzzle hash for derivation", pulling the puzzle hash out of the memo list at path `"rrrff"`: [1](#0-0) 

If a spend is crafted (or simply malformed/unexpected relative to what the wallet's NFT driver expects) such that no `CREATE_COIN` condition carries the `atom == 1` memo marker, `puzhash_for_derivation` stays `None`, and the function falls through to:
```
assert puzhash_for_derivation
return metadata, puzhash_for_derivation
```
This is a bare `assert`, which raises an unhandled `AssertionError` rather than returning a `None`/graceful failure — structurally the same defect class as the Bento4 bug: code assumes a sub-object/value is always present after parsing untrusted structured input, and dereferences/asserts on it without a null-check, crashing the caller.

This function is called from two wallet code paths that process on-chain NFT coin spend data coming from a full-node peer (i.e., from whatever spend bundle was actually accepted into a block, which anyone can construct against their own coins/singleton lineage and which the local wallet must parse when it sees the coin state):
- `WalletStateManager.determine_coin_type` uncurries a coin and dispatches to `NFTWallet.identify`, which internally calls `get_metadata_and_phs` on the untrusted `nft_data.parent_coin_spend.solution` [2](#0-1) 
- `NFTWallet.puzzle_solution_received`, invoked when the wallet processes a puzzle/solution for a coin it has determined is an NFT, calls `get_metadata_and_phs(uncurried_nft, data.parent_coin_spend.solution)` directly [3](#0-2) 
- `WalletStateManager.manual_nft_search` (an RPC-triggered path) also calls it directly on a full puzzle/solution pulled from an arbitrary coin id supplied by the local RPC caller [4](#0-3) 

None of these call sites wrap the call in a `try/except` for `AssertionError`, so a spend with a solution lacking the expected memo-tagged `CREATE_COIN` condition (something an attacker fully controls when constructing/broadcasting a spend against a singleton, or simply an edge case that differs from the wallet's hard-coded expectations) will raise unhandled and abort processing of that coin state / NFT sync callback.

### Impact Explanation
This is a spend-triggered halt of NFT-related wallet transaction processing (crash / unhandled exception in a code path reachable purely from data derived from an on-chain spend), matching the "spend-triggered transaction-processing halt" acceptance criterion. It does not on its own allow theft or supply inflation, but it can stop legitimate wallets from syncing/processing NFT state when they encounter a crafted spend of a singleton/coin that looks like an NFT to the uncurrying logic but doesn't carry the expected condition shape.

### Likelihood Explanation
Medium: an attacker only needs to get a spend accepted on-chain (or presented via RPC to `manual_nft_search`) whose puzzle reveal uncurries to the NFT singleton/state-layer pattern but whose solution's conditions omit the `atom==1` memo-tagged `CREATE_COIN`. Since `UncurriedNFT.uncurry` only checks puzzle structure (mod hashes), not solution content, crafting such a mismatch is straightforward for anyone who understands the puzzle layout, and it is triggered automatically the moment the victim wallet observes/syncs the coin.

### Recommendation
Replace the bare `assert puzhash_for_derivation` in `get_metadata_and_phs` (and any similar bare asserts on parsed condition data in this file, e.g., in `update_metadata`/`recurry_nft_puzzle`) with explicit checks that raise a caught/handled exception type, and wrap calls at the `NFTWallet.identify`, `NFTWallet.puzzle_solution_received`, and `WalletStateManager.manual_nft_search` call sites so a malformed/unexpected NFT-like spend is logged and skipped rather than propagating an unhandled `AssertionError` that halts sync.

### Proof of Concept
1. Construct a coin whose puzzle reveal uncurries as `SINGLETON_TOP_LAYER_MOD` → `NFT_MOD` (satisfying `UncurriedNFT.uncurry`'s mod checks) exactly like a normal NFT.
2. Craft the solution/inner-puzzle so that when run, the resulting condition list contains no `CREATE_COIN` (opcode 51) condition whose `atom` field (`condition.rest().rest().first().as_int()`) equals `1` (i.e., omit or alter the memo marker used by the wallet convention) — while still being a fully valid, signature-satisfying spend of the attacker's own coin.
3. Get this spend accepted into a block (or, for the RPC path, simply call `manual_nft_search` with the crafted coin id) so that a victim wallet syncing this coin state calls `determine_coin_type` → `NFTWallet.identify`/`puzzle_solution_received`, which internally call `get_metadata_and_phs`.
4. Observe `AssertionError` raised from `assert puzhash_for_derivation` at `chia/wallet/nft_wallet/nft_puzzle_utils.py:259`, propagating unhandled out of the wallet sync callback and halting processing of that coin/state update.

```python
def get_metadata_and_phs(unft: UncurriedNFT, solution: SerializedProgram) -> tuple[Program, bytes32]:
    conditions = unft.p2_puzzle.run(unft.get_innermost_solution(Program.from_serialized(solution)))
    metadata = unft.metadata
    puzhash_for_derivation: bytes32 | None = None
    for condition in conditions.as_iter():
        if condition.list_len() < 2:
            # invalid condition
            continue
        condition_code = condition.first().as_int()
        log.debug("Checking condition code: %r", condition_code)
        if condition_code == -24:
            # metadata update
            metadata = update_metadata(metadata, condition)
            metadata = Program.to(metadata)
        elif condition_code == 51:
            atom = condition.rest().rest().first().as_int()

            if atom == 1:
                # destination puzhash
                if puzhash_for_derivation is not None:
                    # ignore duplicated create coin conditions
                    continue
                memo = bytes32(condition.at("rrrff").as_atom())
                puzhash_for_derivation = memo
                log.debug("Got back puzhash from solution: %s", puzhash_for_derivation)
    assert puzhash_for_derivation
    return metadata, puzhash_for_derivation
```
