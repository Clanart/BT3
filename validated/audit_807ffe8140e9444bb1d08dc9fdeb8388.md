## Title
Unchecked ERC-20 return value in Tron `IntentGatewayV2.withdraw()` silently zeroes escrow while leaving funds stuck — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

## Summary
The Tron port of `IntentGatewayV2` decrements escrow accounting and treats a token transfer as successful based solely on whether the low-level `.call()` did not revert, without checking the ERC-20 `transfer()` boolean return value. This mirrors the external report's root cause — code assumes an external interface behaves in a specific way (revert-on-failure semantics) that isn't guaranteed to hold for every deployed token/chain, and the mismatch silently breaks the settlement path instead of reverting.

## Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the `withdraw()` function — invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` message kinds, as well as from `onGetResponse()` — releases escrowed input tokens like this: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```

`success` here reflects only whether the external call reverted — it does **not** decode/verify the ABI-encoded boolean that a compliant ERC-20 `transfer()` returns. A token that returns `false` on failure (e.g., paused, blacklisted recipient, insufficient contract balance due to a prior accounting drift, or any standards-compliant token that signals failure via return value rather than `revert`) will make this call return `success = true` even though **no tokens moved**. The function then proceeds to:
1. Mark `_filled[body.commitment] = beneficiary` (irreversibly finalizing settlement),
2. Decrement `_orders[body.commitment][token] -= amount` (zeroing the escrow accounting),
3. Emit `EscrowReleased`/`EscrowRefunded` as if the beneficiary was paid.

The contract itself imports and aliases `SafeERC20` (`using SafeERC20 for IERC20;`) at the top of the file, and the equivalent EVM implementation in `evm/src/apps/intentsv2/IntentsBase.sol` (`_withdraw`) uses `IERC20(token).safeTransfer(beneficiary, amount)`, which reverts on a `false` return. The Tron variant, however, uses the raw low-level `.call` pattern for `withdraw()`, `onAccept`'s `SweepDust` path, and `dispatchWithFeeToken`-adjacent fee transfer — none of which validate the returned boolean: [2](#0-1) [3](#0-2) 

This is exactly the class of bug in the external report: the code assumes a downstream external contract's call semantics (here, "ERC-20 transfer either succeeds and moves funds, or reverts") match what SafeERC20 guarantees, but on a different execution environment/token implementation that assumption silently breaks, corrupting protocol state (`_orders[commitment][token]` and `_filled[commitment]`) instead of causing a clean, retryable revert.

## Impact Explanation
This qualifies as fund loss/lock under the bounty's impact gate: once `withdraw()` runs with a token that returns `false` instead of reverting, the escrowed tokens remain trapped in the `IntentGatewayV2` contract (never delivered to the solver/user), while `_orders[commitment][token]` is zeroed and `_filled[commitment]` is permanently set. Any legitimate retry becomes impossible because `_filled` already blocks the order and `_orders[commitment][token] == 0` triggers `UnknownOrder()` on any subsequent attempt. The result is a silent, unrecoverable loss for the intended beneficiary (user or solver) with no attacker action required beyond the natural flow of a settlement/refund message for a token that exhibits this common non-reverting-failure behavior.

## Likelihood Explanation
No privileged actor, malicious relayer, or compromised prover is required — this triggers purely from normal protocol operation (`RedeemEscrow`/`RefundEscrow` settlement or GET-response refund) whenever the escrowed input token is one that signals transfer failure via a `false` return rather than reverting. This is a well-documented behavior class among real ERC-20 tokens (some pausable/blacklist tokens, and some non-standard implementations) and is precisely the kind of assumption mismatch the analog report highlights — the developer used `SafeERC20` in the "normal" EVM contract but reverted to raw low-level calls in the Tron-specific port, likely due to Tron VM/TRC20 ABI quirks, without re-adding the return-data check.

## Recommendation
Replace every raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()`, the `SweepDust` handler, and the fee-transfer path) with `IERC20(token).safeTransfer(...)` (the contract already has `using SafeERC20 for IERC20;` in scope), or explicitly decode and check the boolean return data (`success && (data.length == 0 || abi.decode(data, (bool)))`) before mutating `_orders`/`_filled`. Ensure state mutations only occur after a verified successful transfer.

## Proof of Concept
1. Register/escrow an input token in `IntentGatewayV2` (Tron) whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., simulate contract balance temporarily insufficient, or a blacklist-style token blocking the beneficiary).
2. Trigger the normal cross-chain settlement flow so Hyperbridge dispatches a `RedeemEscrow` (or `RefundEscrow`) message that reaches `onAccept()` → `withdraw()`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, abi.encode(false))` because the call executes without reverting but the token signals failure.
4. `success` is `true`, so no revert occurs; `_orders[commitment][token] -= amount` zeroes the escrow and `_filled[commitment] = beneficiary` is set, while `beneficiary`'s token balance is unchanged — the tokens remain stuck in the contract with no accounting path to recover them.
