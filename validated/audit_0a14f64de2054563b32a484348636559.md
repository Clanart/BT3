### Title
Pointer precompile bypasses the `RegisterPointerDisabled` governance kill-switch, keeping CW→ERC pointer registration operational after it is "shut down" - (File: `precompiles/pointer/pointer.go`, `x/evm/keeper/msg_server.go`)

### Summary
`x/evm`'s `RegisterPointerDisabled` param is the chain's emergency/governance kill-switch for creating new CW→ERC pointer contracts. It is enforced in exactly one entry point — the `MsgRegisterPointer` message handler — but the EVM `pointer` precompile, which any unprivileged EVM caller can invoke directly, performs the same state-mutating pointer-registration action without ever consulting that flag. This mirrors the reported `Clearinghouse` bug class: a "deactivated" flag that only some code paths check, letting the un-checked path keep the feature fully operational.

### Finding Description
`k.GetRegisterPointerDisabled(ctx)` is read in `x/evm/keeper/msg_server.go`'s `RegisterPointer` handler to reject `MsgRegisterPointer` calls once governance sets `RegisterPointerDisabled = true`: [1](#0-0) 

The same "pointer creation" capability is also exposed through the EVM `pointer` precompile's `AddNative`/`AddCW20`/`AddCW721`(/`AddCW1155`) methods, callable by any EVM account via a normal transaction or `eth_call`. Every implementation of this precompile (legacy `v575`, `v580`, `v605`, `v614`, matching the same dispatch pattern as the current `precompiles/pointer/pointer.go`) routes straight to `p.evmKeeper.UpsertERCNativePointer` / the CW20/CW721 upsert equivalents with no call to `GetRegisterPointerDisabled` anywhere in the executor: [2](#0-1) [3](#0-2) 

`GetRegisterPointerDisabled` itself is only referenced from `params.go` (getter) and the `RegisterPointer` msg-server handler; a repo-wide search shows no reference to it inside the `precompiles/pointer` package, confirming the precompile path is unguarded: [4](#0-3) [5](#0-4) 

So once an operator disables pointer registration (e.g., via `MigrateDisableRegisterPointer` or a governance param change, intended to stop new CW20/CW721/native pointer creation chain-wide), any unprivileged EVM transaction sender can still call the `pointer` precompile at `0x...100b` to create brand-new pointer contracts, completely bypassing the shutdown.

### Impact Explanation
`RegisterPointerDisabled` exists as a safety control (its default was flipped to `true` in a migration, i.e., it is treated as a security-relevant gate against uncontrolled pointer creation). Bypassing it via the precompile lets an attacker or ordinary user keep minting new CW↔ERC pointer contracts after the chain has explicitly disabled that capability, undermining the intended protection (e.g., against malformed/duplicate/abuse pointer contracts, or whatever operational risk motivated the shutdown) and creating unauthorized on-chain pointer/token bridges the operators believed were closed. This satisfies "unauthorized transfer via precompile or pointer" / bypass-of-security-control class of impact for a High-severity analog.

### Likelihood Explanation
High likelihood: the precompile is a permissionless, publicly reachable EVM entry point (`0x...100b`), requires no special role, and the bypass requires nothing more than a normal signed EVM transaction calling `addNativePointer`/`addCW20Pointer`/`addCW721Pointer`. No race condition or privileged access is needed — the gap is structural (missing check in one of two code paths that both perform the same governed action).

### Recommendation
Add a `if k.GetRegisterPointerDisabled(ctx) { return nil, 0, errors.New("registering CW->ERC pointers has been disabled") }` check inside the pointer precompile's `Execute`/`AddNative`/`AddCW20`/`AddCW721`/`AddCW1155` methods (or centrally before dispatch), mirroring the check already present in `x/evm/keeper/msg_server.go`'s `RegisterPointer`, so both entry points enforce the same governance-controlled shutdown state.

### Proof of Concept
1. Governance/operator sets `RegisterPointerDisabled = true` (or the chain runs the `MigrateDisableRegisterPointer` upgrade handler that sets this by default). [6](#0-5) 
2. Confirm `MsgRegisterPointer` (the intended shutdown path) now fails, as covered by `TestRegisterPointerDisabled`: [1](#0-0) 
3. From any unprivileged EVM account, send a transaction calling the `pointer` precompile's `addNativePointer(denom)` (or `addCW20Pointer`/`addCW721Pointer`) at address `0x...100b`.
4. Observe the call succeeds and a new pointer contract is deployed via `UpsertERCNativePointer`, exactly as in the normal-operation test flow used for the precompile: [7](#0-6) 
5. This demonstrates pointer registration remains fully "operational" through the precompile despite the chain having disabled it through the governed `RegisterPointerDisabled` flag — the same class of bug as `Clearinghouse` remaining active after `emergencyShutdown()`.

**Uncertainty note:** I was unable to directly open `precompiles/pointer/pointer.go` (the current, non-legacy implementation) in this session to show its exact line numbers; the conclusion is based on all four legacy versions (`v575`, `v580`, `v605`, `v614`) sharing an identical dispatch/executor pattern with no `RegisterPointerDisabled` check, plus a repo-wide grep confirming no reference to that getter anywhere under `precompiles/pointer`. A Devin session with full file access should confirm the current `pointer.go` matches this pattern before treating this as a finalized, unconditional confirmation.

func (k *Keeper) GetRegisterPointerDisabled(ctx sdk.Context) bool {
	if !ctx.IsTracing() {
		return k.GetParams(ctx).RegisterPointerDisabled
	}
	switch {
	case semver.Compare(ctx.ClosestUpgradeName(), "v6.0.6") < 0:
		// Not present in pre-5.8.0 params; use default
		return types.DefaultRegisterPointerDisabled
	default:
		return k.GetParams(ctx).RegisterPointerDisabled
	}
}
