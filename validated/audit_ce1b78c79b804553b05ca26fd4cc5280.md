### Title
`ReceivedOutput::read` deserializes an unverified `(offset, output, outpoint)` triple whose claimed prevout is never bound to the on-chain UTXO — the threshold then signs a spend of a nonexistent/mismatched deposit - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report's bug class — an account/prevout object consumed without verifying it corresponds to the real on-chain asset (checking the wrong account, missing mint verification against an authoritative feed) — maps directly onto Serai's Bitcoin wallet scanner. `ReceivedOutput::read` reconstructs a "spendable output" from fully attacker-controlled bytes (`offset`, `TxOut`, `OutPoint`), and downstream `SignableTransaction::new` / `SignableTransaction::multisig` verify only the `offset ↔ script_pubkey` half of the binding, never the `outpoint ↔ output` half. The result is a `ReceivedOutput` that reports funds received which are not spendable, and a threshold signature over a transaction that can never confirm — while any bookkeeping that credited the claimed `output.value` is drained.

### Finding Description
`ReceivedOutput::read` accepts three independent attacker-controlled fields with no consistency check:

- `offset` (a `Secp256k1` scalar),
- `output` (a `TxOut` carrying the claimed `value` and `script_pubkey`),
- `outpoint` (the claimed location of that `TxOut` on-chain). [1](#0-0) 

When the `ReceivedOutput` is legitimately produced by `Scanner::scan_transaction`, the `outpoint ↔ output` binding is guaranteed because the `TxOut` is copied verbatim out of the scanned transaction at the matching `vout`. [2](#0-1)  Deserialization drops that guarantee entirely: an unprivileged party can feed bytes to `ReceivedOutput::read` where `outpoint` references any real (or fake) UTXO while `output` is a fabricated `TxOut` cloned from a genuine Serai deposit — the exact analog of the report's `payment_mint_account_info` never being verified against the `PaymentFeed`.

Downstream, `SignableTransaction::new` uses the *claimed* `input.output.value` to compute `input_sat`, enforce `input_sat >= payment_sat + needed_fee`, and size the change output. [3](#0-2) [4](#0-3)  The only check `multisig` performs is `p2tr_script_buf(offset.group_key()) == prevouts[i].script_pubkey` — i.e., it binds the offset to the *claimed* `script_pubkey`, never the claimed `TxOut` to the real UTXO identified by `outpoint` (and it cannot, off-chain). [5](#0-4)  Signing then commits `Prevouts::All(&self.tx.prevouts)` — the fabricated prevout data — into every input's BIP-341 sighash. [6](#0-5) 

This mirrors both halves of the report: the code validates the wrong object (the claimed `TxOut`/`script_pubkey` rather than the actual UTXO behind `outpoint`), and the authoritative source (the chain, analog of `PaymentFeed`) is never consulted before value is credited and the threshold key signs.

### Impact Explanation
Two concrete impacts are reachable by an unprivileged party whose only capability is supplying serialized `ReceivedOutput` bytes (e.g., a depositor/coordinator peer relaying "their" outputs):

1. **Funds reported received that are not spendable.** Any consumer crediting deposits based on `ReceivedOutput::value()` can be shown a `ReceivedOutput` claiming an arbitrary amount against a dust or nonexistent outpoint. The fabricated `output.script_pubkey` trivially passes the `multisig` check since the attacker registers the real script. [7](#0-6) 
2. **Threshold signs an unconfirmable transaction.** `TransactionSignMachine::sign` obtains a valid threshold Schnorr signature over `Prevouts::All`, which commits to the *claimed* prevout amount/script. Bitcoin consensus recomputes the sighash from the *actual* UTXO, so a forged `ReceivedOutput` causes every input in the transaction to sign a message that can never validate — burning the honest inputs' preprocesses (which are single-use) and stalling the spend. [8](#0-7) 

### Likelihood Explanation
`ReceivedOutput` exposes `read`/`write`/`serialize` specifically so outputs can be transported between parties (e.g., depositors proving outputs to a spending coordinator). [9](#0-8)  Nothing in the type or its consumers documents that deserialized instances must originate from `Scanner::scan_transaction`/`scan_block` on a locally verified chain — there is no documentation-level MUST here, only an implicit assumption. An attacker needs no validator status, no collusion, and no malformed curve/hash input: only public bytes plus a real Serai `script_pubkey` (which is public knowledge from the address) satisfy both the `multisig` script check and signature production.

### Recommendation
Bind the claimed prevout to reality before crediting or signing, mirroring the report's remediation:

- Document `ReceivedOutput::read` as requiring the caller to re-verify `outpoint` resolves to `output` against the chain (e.g., via `gettxout`/SPV proof) — or provide a `verify_against_utxo`/`Scanner`-produced-only constructor and mark `read` as unsafe-to-trust for untrusted input.
- In `SignableTransaction::new`/`multisig`, reject `ReceivedOutput`s that did not come from `scan_transaction`/`scan_block` on a confirmed block (track provenance, e.g. a private field not round-tripped through `read`), so a forged `outpoint ↔ output` pair cannot reach the signing machines.
- When scanning, skip immature coinbase outputs inline rather than relying on a doc-comment post-processing pass. [10](#0-9) 

### Proof of Concept
```rust
// Attacker observes a real Serai p2tr deposit script for offset O.
let real_script: ScriptBuf = /* script_pubkey at known offset */;

// Build a forged ReceivedOutput:
//  - outpoint: attacker's own dust UTXO (or any outpoint; need not resolve)
//  - output:   TxOut { value: 10_BTC, script_pubkey: real_script }
//  - offset:   O (publicly derivable; scripts map offset -> script)
let forged = ReceivedOutput { offset: O, output: fake_txout_10btc, outpoint: dust_outpoint };
let bytes = forged.serialize();

// Victim/coordinator side:
let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap(); // accepted — no checks
// ro.value() == 10_BTC reported "received"
let stx = SignableTransaction::new(vec![ro], &attacker_payment, change, None, fee).unwrap();
let machine = stx.multisig(&keys).unwrap(); // passes: script matches offset key
// threshold signs; signature commits Prevouts::All(claimed 10 BTC)
// -> broadcast fails (prevout data != actual UTXO): deposit credited,
//    preprocesses burned, transaction unconfirmable.
```

Caveat: the theft-vs-DoS split depends on how an integrator credits `ReceivedOutput`s; the code path itself (unverified `read` → `multisig` check passes → signature produced over fabricated prevouts) is fully confirmed from the in-scope files.
