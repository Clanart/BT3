### Title
Scanner accepts any output paying to the key's script_pubkey regardless of value or maturity, reporting unspendable/dust outputs as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` in `networks/bitcoin/src/wallet/mod.rs` registers every transaction output whose `script_pubkey` matches a registered script as a `ReceivedOutput`, with no check on the output's value (dust) or the transaction's type (immature coinbase). This is the analog of the Gitcoin bug where `vote()` accepted any token: here, "any output" — including ones that cannot ever be economically spent or are consensus-immature — is counted as funds received by the multisig.

### Finding Description
The scanner maintains a map of `ScriptBuf -> Scalar` offsets and, for every output in a scanned transaction, does a bare lookup:

```rust
// networks/bitcoin/src/wallet/mod.rs:199-213
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout) });
}
```

No validation is performed on `output.value`. `scan_block` additionally iterates `block.txdata` including `txdata[0]`, the coinbase transaction, whose outputs are unspendable for 100 blocks (the code comments acknowledge this, but `scan_block` is the exported API and nothing enforces the required post-processing).

Downstream, `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs:150-256` validates that *payments* are at least `DUST` (line 165-169) but never validates that *inputs* meet any minimum value or that prevouts are mature. A 1-satoshi input is happily included, contributing essentially nothing while still costing ~57.5 vbytes of signature/witness weight each.

### Impact Explanation
An unprivileged party can send arbitrary Bitcoin transactions to the Serai multisig's Taproot script_pubkey with dust values (or, a miner, with immature coinbase outputs). These are reported by `scan_transaction`/`scan_block` as `ReceivedOutput`s — funds that the accounting layer treats as received balance but which are either consensus-unspendable (immature coinbase) or economically unspendable (value below the fee required to spend them, and below `DUST` the wallet itself enforces on payments). The vault's reported balance is inflated with "priceless tokens" the multisig can never actually mobilize; including them in a spend also wastes weight and can push transactions over `MAX_STANDARD_TX_WEIGHT`.

### Likelihood Explanation
Any Bitcoin user can send a dust-valued P2TR output to the multisig address at minimal cost (the outputs themselves are near-worthless by construction). No special privileges are needed — the scanner keys off the script alone, which is public.

### Recommendation
Filter in `Scanner::scan_transaction`: skip outputs with `value < DUST` (or a configurable minimum economically-spendable threshold). In `scan_block`, skip `block.txdata[0]` or mark coinbase-derived `ReceivedOutput`s with a maturity flag and have `SignableTransaction::new` reject immature/dust inputs, matching the existing `DustPayment` check applied to payments.

### Proof of Concept
1. Compute the multisig's P2TR `script_pubkey` (public group key).
2. Broadcast a transaction with an output `{ value: 1 sat, script_pubkey: <multisig script> }`.
3. `Scanner::scan_transaction(tx)` returns a `ReceivedOutput` for it; Serai's processor accounts 1 sat of "received" balance.
4. That output can never be spent profitably — the input weight cost exceeds its value — yet it remains registered as spendable funds, analogous to voting with a worthless token.
