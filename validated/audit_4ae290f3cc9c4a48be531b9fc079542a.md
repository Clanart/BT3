### Title
Non-atomic reward claim loop inside `unlock()`/`forceUnLock()` permanently freezes all locked MGP if a single reward token reverts - (File: `VLMGP.sol`, `rewards/vlMGPBaseRewarder.sol`)

### Summary
`VLMGP.unlock()` and `VLMGP.forceUnLock()` unconditionally force a "claim-all-rewards" call into `vlMGPBaseRewarder` before releasing a user's locked MGP. That claim loop iterates every registered reward token and calls `safeTransfer` with no try/catch or per-token isolation. A single reverting reward token (paused/blacklisting token, or a balance shortfall from reward accounting) makes the entire loop revert, which reverts the whole `unlock`/`forceUnLock` transaction. Since every vlMGP holder shares this same forced, non-skippable code path, one bad reward token permanently blocks all users from ever unlocking their MGP — this is the exact "single bad item halts whole batch, no atomic fallback" defect described in the external report, but with materially worse impact (permanent freeze rather than a delayed tick).

### Finding Description
`unlock()` and `forceUnLock()` both hardcode an empty reward-token filter, which forces `MasterMagpie._multiClaim` to invoke the "claim everything" branch: [1](#0-0) 

```solidity
function unlock(uint256 _slotIndex) external override whenNotPaused nonReentrant {
    ...
    address[] memory lps = new address[](1);
    address[][] memory vlMGPrewards = new address[][](1); // always length-0 inner array
    lps[0] = address(this);
    IMasterMagpie(masterMagpie).multiclaimFor(lps, vlMGPrewards, msg.sender);
    ...
    IERC20(MGP).safeTransfer(msg.sender, unlockedAmount);
}
```

Because `vlMGPrewards[0]` is always an empty array (default value, not user-settable), `_claimBaseRewarder` always takes the "claim all" path: [2](#0-1) 

That routes into `vlMGPBaseRewarder.getReward()`, which iterates over every registered reward token and unconditionally transfers whatever is owed, with no try/catch or skip-on-failure logic: [3](#0-2) 

```solidity
function getReward(address _account, address _receiver) public onlyMasterMagpie updateReward(_account) returns (bool) {
    uint256 length = rewardTokens.length;
    for (uint256 index = 0; index < length; ++index) {
        address rewardToken = rewardTokens[index];
        _sendReward(rewardToken, _account, _receiver);
    }
    return true;
}
```

`_sendReward` performs an unguarded `safeTransfer` for any nonzero owed amount: [4](#0-3) 

If any single reward token in `rewardTokens[]` reverts on transfer (e.g., the token pauses, blacklists a specific recipient, or the pool's tracked balance for that token drifts below what accounting says is owed due to rounding across many `_sendReward`/forfeit-recycle calls), the `for` loop reverts, which reverts `getReward`, which reverts `_multiClaim`, which reverts `multiclaimFor`, which reverts `unlock`/`forceUnLock` for every caller — because the reward-token set and the forced "claim all" behavior are global, not per-user-configurable. There is no way for a user to specify a partial reward-token list to `unlock`/`forceUnLock` to route around the bad token, unlike `MasterMagpie.multiclaimSpec`, which does allow selecting specific tokens.

This is structurally identical to the reported bug class: a per-item operation inside a loop (`_validateReportTimestamp` per Chainlink report / `_sendReward` per reward token) has no atomic fallback, and an upstream caller (`_processReport` / `unlock`) has no try/catch, so one failing item halts the entire batch — except here the "batch" is shared infrastructure used by every vlMGP holder, and the "tick" that gets blocked is the only unlock mechanism for locked funds.

### Impact Explanation
Once any reward token registered on `vlMGPBaseRewarder` becomes non-transferable for even a single owed recipient (or a shortfall causes `safeTransfer` to fail), `unlock()` and `forceUnLock()` become permanently uncallable for all vlMGP holders, since both hardcode the same forced full-claim path with no bypass. This permanently freezes every user's locked MGP principal (not just the tokens claimed) — meeting the "permanent freezing of funds" bar, well beyond the 24-hour threshold, and with a blast radius covering the entire vlMGP locker population rather than a single feed/user.

### Likelihood Explanation
Reward tokens for `vlMGPBaseRewarder` come from normal protocol operation (MGP emissions plus any bribe/forfeit-recycled tokens routed there), so the set of `rewardTokens[]` can grow over the contract's life. A single external ERC20 in that list adopting blacklist/pause semantics against one address, or an accounting-driven balance shortfall for one token, is a realistic, externally-triggerable condition (not requiring any privileged action), analogous to the report's "normal Data Streams API latency" trigger. Because the failure path has zero isolation and zero recovery mechanism, likelihood of eventual triggering is high given a long enough operating horizon, and impact is total and irreversible without a contract upgrade.

### Recommendation
Mirror the report's recommended fix pattern: make the per-reward-token claim loop resilient instead of atomic.
- In `vlMGPBaseRewarder.getReward`/`_sendReward`, wrap each token's `safeTransfer` in a try/catch (or use a low-level call with success check) and skip-and-log on failure, continuing to the next reward token instead of reverting the whole loop.
- Allow `unlock()`/`forceUnLock()` in `VLMGP.sol` to pass a caller-selectable reward-token subset (like `multiclaimSpec`) so a user can opt out of a known-bad token and still redeem principal.
- Ensure MGP principal release (`_unlock` + `safeTransfer(MGP)`) does not depend transactionally on the success of unrelated bribe/reward-token transfers.

### Proof of Concept
1. Protocol operation over time causes `vlMGPBaseRewarder.rewardTokens` to include token `X` (a normal registered reward/bribe token).
2. Token `X`'s issuer blacklists a specific address `A` (external event, e.g., USDC-style compliance action) — or, independently, rounding across repeated `_queueNewRewardsWithoutTransfer`/forfeit-recycle calls causes the contract's tracked balance of `X` to fall short of what accounting says address `A` is owed.
3. Address `A` (or any other vlMGP holder — since the same shared reward-token array is iterated for every `unlock`/`forceUnLock` call) calls `VLMGP.unlock(_slotIndex)`.
4. `unlock()` calls `multiclaimFor` → `_multiClaim` → `vlMGPBaseRewarder.getReward()`, which loops through all reward tokens and reaches `_sendReward` for token `X`; `IERC20(X).safeTransfer(...)` reverts.
5. The revert propagates all the way up through `unlock()`; the transaction reverts, `slot.amountInCoolDown` is never zeroed, and `IERC20(MGP).safeTransfer(msg.sender, unlockedAmount)` never executes.
6. Every vlMGP holder attempting `unlock()`/`forceUnLock()` hits the same reverting loop, since the reward-token list and the "claim all" behavior are shared and hardcoded — permanently freezing all locked MGP with no on-chain recovery path available to ordinary users.
