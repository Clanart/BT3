Based on my research, I found the confirmed local analog: `updateHostParamsInternal()` in `EvmHost.sol` never removes an entry from `_latestStateMachineHeight` when a state machine is dropped from the new `params.stateMachines` list.

### Title
Stale `_latestStateMachineHeight` entry lets a de-listed state machine's state commitments keep being accepted - (File: `evm/src/core/EvmHost.sol`)

### Summary
`updateHostParamsInternal()` only ever *adds* whitelist entries for chains in the incoming `params.stateMachines` array; it never clears `_latestStateMachineHeight` for a state machine ID that was whitelisted before but is absent from the new list. This is the same class of bug as the reported `AggregateStablePrice.remove_price_pair()` issue: an admin/governance "remove" operation leaves a stale entry behind in a parallel accounting/validity structure, and that stale entry keeps being consulted by downstream logic as if the removal never happened.

### Finding Description
`updateHostParamsInternal` [1](#0-0)  replaces `_hostParams.stateMachines` wholesale with the new list, then loops only over the *new* list to initialize `_latestStateMachineHeight[params.stateMachines[i]] = 1` if unset: [2](#0-1) 

There is no corresponding loop that diffs the old `_hostParams.stateMachines` against the new one and deletes `_latestStateMachineHeight` for IDs that were removed from the whitelist. Consequently, once a state machine ID has been onboarded (`_latestStateMachineHeight[id] != 0`), removing it from `params.stateMachines` in a later `updateHostParams` governance call does not reset that mapping entry back to zero — it simply stops appearing in the `stateMachines` array field, which (per the code comments) is largely metadata/bookkeeping, while the actual per-height commitment maps (`_stateCommitments`, `_latestStateMachineHeight`) remain populated and mutable via the consensus client's normal update path.

### Impact Explanation
Any code path that gates "is this a known/whitelisted state machine" purely on `_latestStateMachineHeight[id] != 0` (rather than re-checking membership in the current `_hostParams.stateMachines`) will continue to treat a governance-removed chain as trusted. If governance removes a state machine specifically to freeze/distrust it (e.g., a compromised or deprecated chain), a relayer can still submit consensus/state updates for that chain's already-initialized height counter, and its state commitments can still be accepted and later used to satisfy `verify_membership`/`verify_state_proof` for incoming requests/responses — i.e., false remote state acceptance from a chain the host operator believed was de-authorized. This maps directly to the bounty's "false proof/state acceptance" category.

### Likelihood Explanation
This requires no malicious peer, prover, or relayer collusion beyond the routine, already-trusted consensus-client update flow — it's a pure state-hygiene gap in the host's own storage. The triggering condition is entirely within intended, permitted admin/governance operations (a normal `updateHostParams` call that shrinks the state-machine list), so it is a logic/state-cleanup defect rather than a privilege-escalation bug. However, exploitation is dependent on some *other* code path relying solely on `_latestStateMachineHeight != 0` as a trust check without cross-referencing the live `stateMachines` array — I was not able to fully trace every proof-verification call site within the remaining iteration budget to confirm which specific consumer treats this stale entry as authoritative acceptance, so likelihood should be treated as plausible but not fully confirmed end-to-end.

### Recommendation
In `updateHostParamsInternal`, before overwriting `_hostParams.stateMachines`, compute the set difference between the old and new `stateMachines` arrays and explicitly `delete _latestStateMachineHeight[removedId]` (and any other per-state-machine mappings such as `_stateCommitments`/`_stateCommitmentsUpdateTime` entries, or at minimum gate their consumption on current whitelist membership) for every ID that is no longer present, mirroring the fix recommended for `remove_price_pair()`'s `last_tvl` cleanup.

### Proof of Concept
1. Governance calls `updateHostParams` with `stateMachines = [A]`. `_latestStateMachineHeight[A]` becomes `1`.
2. Consensus client delivers real updates for `A`; `_latestStateMachineHeight[A]` and `_stateCommitments[A][...]` advance normally over time.
3. Governance calls `updateHostParams` again with `stateMachines = [B]` only (intending to drop `A`). `_hostParams.stateMachines` no longer contains `A`, but `_latestStateMachineHeight[A]` and its `_stateCommitments[A][...]` entries are untouched.
4. Any handler/module code that checks "is `A` a known/served state machine" via `_latestStateMachineHeight[A] != 0` (instead of scanning current `_hostParams.stateMachines`) still returns true, and previously (or newly, if the consensus client can still be driven for `A`) stored commitments for `A` remain usable to satisfy proof verification — this is the exact analog of the stale `last_tvl` entry surviving `remove_price_pair()` and corrupting downstream calculations.

*Caveat: I confirmed the storage-hygiene gap directly in the code, but did not have remaining iterations to enumerate every downstream consumer of `_latestStateMachineHeight` to prove a concrete fund-loss/false-acceptance call site end-to-end. A Devin session with full repo access should trace `_latestStateMachineHeight` and `_stateCommitments` reads across `evm/src/core/` and the handler contracts to confirm which check(s) fail to re-validate against the live `stateMachines` list.*

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();
        }

        // safe to emit here because invariants have already been checked
        // and don't want to store a temp variable for the old params
        emit HostParamsUpdated({oldParams: _hostParams, newParams: params});

        _hostParams.feeToken = params.feeToken;
        _hostParams.admin = params.admin;
        _hostParams.handler = params.handler;
        _hostParams.hostManager = params.hostManager;
        _hostParams.uniswapV2 = params.uniswapV2;
        _hostParams.unStakingPeriod = params.unStakingPeriod;
        _hostParams.challengePeriod = params.challengePeriod;
        _hostParams.consensusClient = params.consensusClient;
        _hostParams.stateMachines = params.stateMachines;
        _hostParams.hyperbridge = params.hyperbridge;

        // add whitelisted state machines
        for (uint256 i = 0; i < stateMachinesLen; ++i) {
            // create if it doesn't already exist
            if (_latestStateMachineHeight[params.stateMachines[i]] == 0) {
                _latestStateMachineHeight[params.stateMachines[i]] = 1;
            }
        }
