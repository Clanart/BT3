### Title
Attacker-controlled `WWW-Authenticate` header spoofs "GitHub" classification and triggers OAuth flow (with client_secret) to a malicious host - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
When Git talks HTTPS to a remote and gets a `401`, it forwards any `WWW-Authenticate` header values to Desktop's credential helper as `wwwauth[]=...` fields. Desktop's `getEndpointKind` in `trampoline-credential-helper.ts` uses the literal string `realm="GitHub"` in that header as a trust signal to classify the remote host as a GitHub/Enterprise endpoint — completely bypassing the actual verification path (`isGitHubHost(endpoint)`, an authenticated API probe) that is used in every other code path.

### Finding Description
`getEndpointKind` decides whether a credential request is "generic" (handled by the normal/external credential helper flow) or "github.com/enterprise" (handled by Desktop's own account store / sign-in flow): [1](#0-0) 

This block is explicitly documented as a "happy-path" shortcut to *avoid* querying the real API: [2](#0-1) 

The header value comes straight from the remote server's HTTP response and is attacker-controlled whenever the user interacts with a malicious/compromised remote (a cloned/added git remote, an LFS endpoint, a submodule URL, or a MITM proxy sitting in front of a normal HTTP remote). `getCredentialUrl(cred)` — which becomes `endpoint` — is built directly from the credential fields Git supplies (`url`/`protocol`/`host`/`path`), i.e. the actual remote host being talked to: [3](#0-2) 

Once `getEndpointKind` returns `'enterprise'` for this attacker-controlled host, `getCredential` (because no matching account exists yet) calls `ui.promptForGitHubSignIn(endpoint)`: [4](#0-3) 

which starts Desktop's own Enterprise sign-in flow pointed at that attacker-controlled endpoint: [5](#0-4) 

If the user chooses "Sign in using your browser" (the normal call to action in that dialog), `authenticateWithBrowser` opens `getOAuthAuthorizationURL(endpoint, csrfToken)` in the external browser, and on callback `resolveOAuthRequest` posts Desktop's **client_id and client_secret** plus the OAuth `code` to `${endpoint}/login/oauth/access_token`: [6](#0-5) [7](#0-6) [8](#0-7) 

`setEndpoint`/`validateURL` only checks syntactic/HTTPS validity and reachability — it never confirms the host is actually GitHub software: [9](#0-8) 

The broken invariant is exactly analogous to the Solidity report: a privileged operation (approval/allowance — here, "this host is GitHub, use Desktop's trusted sign-in/OAuth machinery") is granted based on an untrusted, attacker-suppliable input instead of the properly-gated verification (`Safe.approve` after validating the token / here, `isGitHubHost` after an actual API round-trip) that exists elsewhere in the same file for the exact same decision.

### Impact Explanation
- Desktop's OAuth `client_secret` (embedded app secret used for the confidential-client token exchange) is sent to a server the attacker fully controls, purely because that server printed a spoofed `WWW-Authenticate` header.
- The attacker's endpoint is presented in Desktop's own trusted "Sign in to your GitHub Enterprise" UI, which can be used to phish the user's real Enterprise credentials/token if the user completes the flow via basic auth instead of the browser.
- No local access, admin rights, or pre-existing malware is required — only that the user perform a normal Git operation (clone/fetch/push/LFS) against an attacker-supplied remote URL.

### Likelihood Explanation
Moderate-to-high: any attacker who can host a git server or sit as a proxy for an HTTP git remote can trivially set `WWW-Authenticate: Basic realm="GitHub"` on a 401 response. The only precondition is that the user adds/uses that remote in Desktop (a completely normal workflow, e.g. cloning a malicious/compromised repo or adding a colleague-shared remote). The subsequent step (clicking "Sign in") is the expected/obvious UI action Desktop itself surfaces, not an unnatural user action.

### Recommendation
Do not trust the `wwwauth[]` realm string as sufficient evidence of a GitHub endpoint. Either remove this shortcut entirely and always fall back to the authenticated `isGitHubHost(endpoint)` check, or require that check to additionally succeed before the `wwwauth` heuristic is honored. At minimum, before initiating the sign-in/OAuth flow, re-verify the target host via the real API probe, and never disclose `client_secret` to a host that hasn't been positively verified as a genuine GitHub/GHE instance.

### Proof of Concept
1. Host a Git-over-HTTP server (e.g. a small script serving `git-upload-pack`) that responds to unauthenticated requests with `401` and header `WWW-Authenticate: Basic realm="GitHub"`.
2. In GitHub Desktop, clone/add this server as a remote and trigger a fetch (`git fetch`), so the credential helper trampoline is invoked with `cred` containing `wwwauth[0]=Basic realm="GitHub"` and `host=attacker.example`.
3. Observe `getEndpointKind` (app/src/lib/trampoline/trampoline-credential-helper.ts:157-165) returns `'enterprise'` without ever calling `isGitHubHost`.
4. Desktop shows "Sign in to your GitHub Enterprise" for `attacker.example` (via `ui.promptForGitHubSignIn`).
5. Click "Sign in using your browser"; observe (via a local proxy/log on `attacker.example`) that Desktop later performs `POST /login/oauth/access_token` including the app's real `client_id`/`client_secret` (app/src/lib/api.ts requestOAuthToken), fully controlled and captured by the attacker's server.

Note: I could not execute this end-to-end in a live environment (no runtime access); the chain above is derived entirely from static code reading across `trampoline-credential-helper.ts`, `trampoline-ui-helper.ts`, `sign-in-store.ts`, and `api.ts`, and the "happy-path" comment in the code confirms the shortcut is intentional but not gated by any verification.

export const getCredentialUrl = (cred: Map<string, string>) => {
  const u = cred.get('url')
  if (u) {
    return new URL(u)
  }

  const protocol = cred.get('protocol') ?? ''
  const username = cred.get('username')
  const user = username ? `${encodeURIComponent(username)}@` : ''
  const host = cred.get('host') ?? ''
  const path = cred.get('path') ?? ''

  return new URL(`${protocol}://${user}${host}/${path}`)
}

export async function requestOAuthToken(
  endpoint: string,
  code: string
): Promise<string | null> {
  try {
    const urlBase = getHTMLURL(endpoint)
    const response = await request(
      urlBase,
      null,
      'POST',
      'login/oauth/access_token',
      {
        client_id: ClientID,
        client_secret: ClientSecret,
        code: code,
      }
    )
    tryUpdateEndpointVersionFromResponse(endpoint, response)

    const result = await parsedResponse<IAPIAccessToken>(response)
    return result.access_token
  } catch (e) {
    log.warn(`requestOAuthToken: failed with endpoint ${endpoint}`, e)
    return null
  }
}
