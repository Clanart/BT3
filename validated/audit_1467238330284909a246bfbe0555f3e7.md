## Analog Found: Unhandled Exception (Crash) When Processing a Malformed Offer's `CREATE_COIN` Puzzle Output

### Title
Unhandled `KeyError` Crash When Processing an Untrusted Offer with a Malformed `CREATE_COIN` Condition - (File: `chia/wallet/trading/offer.py`)

### Summary
CVE-2014-0236 is a NULL-pointer dereference caused by an unvalidated zero/absent field (`root_storage`) inside an untrusted structured file (CDF), crashing the parser. The analogous pattern in this codebase is in `Offer.__post_init__()` and `Offer._get_offered_coins()`: when a coin spend inside an untrusted `Offer` produces a malformed `CREATE_COIN` condition, an internal `assert`/exception is silently swallowed for *that* coin during cache construction, but the same coin is unconditionally re-accessed later without a presence check, producing an unhandled `KeyError` that crashes whatever caller is processing the offer.

### Finding Description
`Offer.__post_init__()` builds a per-coin additions cache (`self._additions`) by calling `compute_spend_hints_and_additions()` for every coin spend in the untrusted bundle: [1](#0-0) 

Inside `compute_spend_hints_and_additions()`, a `CREATE_COIN` condition's puzzle-hash argument is asserted to be a plain atom: [2](#0-1) 

If a crafted puzzle reveal (fully attacker-controlled, since it lives inside the untrusted `Offer`/`WalletSpendBundle`) produces a `CREATE_COIN` condition whose second argument is a cons pair rather than an atom, `condition.at("rf").atom` is `None` and the `assert rf is not None` raises `AssertionError`. This is caught by the broad `except Exception: continue` in `__post_init__`, so that coin's spend is **silently skipped** — it never gets an entry in `self._additions`.

Later, `Offer._get_offered_coins()` iterates over **every** coin spend in the bundle and unconditionally indexes into that same cache: [3](#0-2) 

Because the malformed spend was skipped earlier, `self._additions[parent_spend.coin]` raises an uncaught `KeyError`. This method is reached from `get_offered_coins()`, which is called (without any try/except) by `arbitrage()`, `is_valid()`, `to_valid_spend()`, and directly by wallet-facing code such as `TradeManager.calculate_tx_records_for_offer()`: [4](#0-3) 

and `DataLayerWallet.get_offer_summary()`: [5](#0-4) 

These are exactly the code paths a wallet user's RPC calls (e.g. summarizing/inspecting an offer received from a counterparty, or accepting a trade) invoke on an untrusted, attacker-supplied offer file before any signature or coin-state validation occurs.

### Impact Explanation
A malicious offer counterparty can craft an `.offer` file (or raw `SpendBundle`) with one coin spend whose puzzle produces a structurally-invalid `CREATE_COIN` condition. When the victim's wallet parses/inspects/attempts to accept this offer — a normal, expected user action — the wallet process raises an unhandled `KeyError` instead of a graceful `ValidationError`, crashing or aborting the RPC request/task handling that offer. This is a spend/offer-triggered transaction-processing halt reachable by any offer counterparty, matching the CVE's class of "attacker-supplied structured data causes an unchecked null/absent value to crash processing."

### Likelihood Explanation
Constructing such an offer requires only assembling a `CoinSpend` with a CLVM puzzle that outputs a `CREATE_COIN` condition whose puzzle-hash argument is a pair instead of an atom — trivial to construct with any custom puzzle, no signature or on-chain state is needed to make the wallet attempt processing. The exception path is reached via ordinary offer-viewing/summary/accept flows without prior validation of the crafted spend.

### Recommendation
- In `Offer._get_offered_coins()`, use `self._additions.get(parent_spend.coin)` and skip/raise a `ValidationError` for spends missing from the cache, rather than assuming presence.
- Alternatively, in `__post_init__`, when a spend fails to compute hints/additions for any reason, raise a `ValidationError` (bad offer) instead of silently `continue`-ing, so the object is never constructed in an internally-inconsistent state.
- Replace the bare `assert rf is not None` in `compute_spend_hints_and_additions()` with an explicit, documented raise (e.g. `ValidationError`) to make the failure mode intentional rather than relying on `assert` (which is also strippable under `-O`).

### Proof of Concept
1. Construct a `CoinSpend` whose `puzzle_reveal`, when run, outputs `(51 (a . b) 100)` — i.e., a `CREATE_COIN` condition whose puzzle-hash argument is a cons pair `(a . b)` rather than an atom.
2. Wrap this spend plus a normal settlement-payment spend into a `WalletSpendBundle` and build an `Offer(...)` from it — `__post_init__` silently drops the malformed coin from `self._additions` via the broad `except Exception: continue`.
3. Serialize/bech32-encode this `Offer` and send it to a victim wallet (e.g. via `chia wallet get_offer_summary` / `take_offer` RPC, or `DataLayerWallet.get_offer_summary`).
4. When the victim wallet calls `offer.get_offered_coins()` (directly or via `arbitrage()`/`is_valid()`/`to_valid_spend()`), `_get_offered_coins()` indexes `self._additions[parent_spend.coin]` for the malformed spend's coin, which is absent, raising an unhandled `KeyError` and aborting the request/task instead of returning a controlled validation error.
