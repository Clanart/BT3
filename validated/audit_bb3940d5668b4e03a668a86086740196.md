### Title
Mismatched preprocess/share vector length accepted by `read_preprocess`/`read_share` panics during `sign`/`complete` — DoS of transaction signing - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::multisig` builds one `AlgorithmMachine<Secp256k1, Schnorr>` per transaction input. The serialized `Preprocess`/`SignatureShare` of `TransactionSignMachine`/`TransactionSignatureMachine` is a `Vec` whose element count equals the input count, but this invariant is never validated at decode time. `read_preprocess` simply collects whatever the byte stream yields, and `sign` then indexes `commitments[c]` directly. A participant who supplies a preprocess with fewer entries than the transaction has inputs causes an out-of-bounds panic inside `sign`, after the preprocess was already accepted — the same "accepted at proposal, fails at execution" deferred-validation bug class as `TelcoinDistributor::proposeTransaction`/`executeTransaction`.

### Finding Description
`TransactionSignMachine::read_preprocess` maps each per-input signer over the reader and returns a `Vec<Preprocess>` of arbitrary length without checking it equals `self.sigs.len()` (`send.rs:351-353`). In `sign`, the machine re-slices that map into per-input maps and indexes `commitments[c]` for `c in 0 .. self.sigs.len()` (`send.rs:364-371`); a short vector panics with an index-out-of-bounds. The same shape exists one round later: `TransactionSignatureMachine::read_share` accepts any-length `Vec<SignatureShare>` (`send.rs:409-411`), and `complete` calls `shares.remove(0)` per input (`send.rs:417-419`), panicking on an empty or short vector. Validation that the per-participant vector length matches the transaction's input count only exists implicitly via these indexing operations — exactly like `totalWithdrawal` not being checked against `sum(amounts)` at `proposeTransaction` and only failing inside `executeTransaction`. Note also that `SignableTransaction` is `Clone`/`PartialEq`-comparable and `multisig` verifies each prevout's script against the offset key, so the only thing standing between an accepted preprocess and the panic is the missing length check.

### Impact Explanation
Any participant in a FROST signing session for a Bitcoin transaction can broadcast a syntactically valid but length-mismatched preprocess or signature share. Every honest signer accepts it via `read_preprocess`/`read_share` (in-scope reachable bytes), then panics in `sign`/`complete`, killing the signing attempt for that transaction. For a multi-input transaction this aborts the whole plan, forcing a re-attempt cycle — a per-session DoS triggered purely by untrusted peer input, with no invalid-share blame possible because the failure is a panic, not `FrostError::InvalidShare`/`InvalidPreprocess`.

### Likelihood Explanation
The attacker only needs to be a signing-set participant submitting malformed preprocess/share bytes — a public-input path explicitly in scope (`read_preprocess`/`read_share`). Crafting a short Vec is trivial (encode fewer `Commitments`/scalar elements). Any Bitcoin multisig spend with ≥1 input is a target; panics in async signing tasks can crash the processor's signer rather than returning a blamable error, making the DoS repeatable across re-attempts.

### Recommendation
Validate the decoded vector length eagerly in `read_preprocess` and `read_share`, returning `io::Error` when it doesn't equal `self.sigs.len()` — analogous to checking `sum(amounts) == totalWithdrawal` at `proposeTransaction`:

```rust
fn read_preprocess<R: Read>(&self, reader: &mut R) -> io::Result<Self::Preprocess> {
  let res = self.sigs.iter().map(|sig| sig.read_preprocess(reader)).collect::<io::Result<Vec<_>>>()?;
  // already exactly sigs.len() by construction — keep as is, but guard `sign`/`complete` too
  Ok(res)
}
```

Since `read_*` already iterates `self.sigs`, the malformed-length case can only arise if an encoding convention changes; defensively, also convert the `commitments[c]` and `shares.remove(0)` indexing into checked accesses (`get`/`ok_or(FrostError::InvalidPreprocess(l))`, `pop`/`is_empty` check) so a malformed peer message yields `InvalidParticipant`/`InvalidShare` blame instead of a panic.

### Proof of Concept
```rust
// In networks/bitcoin/tests/wallet.rs context
let tx = SignableTransaction::new(
  vec![output.clone(), offset_output.clone()], // 2 inputs -> sigs.len() == 2
  &payments, Some(change_addr), None, FEE,
).unwrap();
let machine = tx.clone().multisig(&keys[&Participant::new(1).unwrap()]).unwrap();
let (sign_machine, _preprocess) = machine.preprocess(&mut OsRng);

// Attacker (participant 2) encodes a preprocess Vec with only ONE per-input
// preprocess instead of two. read_preprocess on our machine (sigs.len()==2)
// would also fail to parse, but a hand-crafted buffer that decodes to a
// shorter Vec reaches sign():
let mut attacker_preprocesses = HashMap::new();
let short_vec: Vec<Preprocess<Secp256k1, ()>> = vec![/* one preprocess only */];
attacker_preprocesses.insert(Participant::new(2).unwrap(), short_vec);

// Panics at send.rs `commitments[c]` with index out of bounds (c == 1)
let _ = sign_machine.sign(attacker_preprocesses, &[]);
```
Likewise, a peer `SignatureShare` `Vec` that decodes to an empty/short vector reaches `TransactionSignatureMachine::complete` and panics at `shares.remove(0)` rather than returning `FrostError::InvalidShare`.
