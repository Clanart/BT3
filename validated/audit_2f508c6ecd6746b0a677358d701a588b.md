### Title
Schnorr aggregate verifier accepts an empty aggregate (zero signers) as a valid signature - ([File: crypto/schnorr/src/aggregate.rs])

### Summary
The external report concerns a minimum-participant check that allows a draw to execute with zero participants. The direct analog in Serai is `SchnorrAggregate::verify`: it only enforces that the number of nonces equals the number of supplied `(key, challenge)` pairs, with no requirement that this quantity be non-zero. An attacker can deserialize an aggregate with `Rs = []` and `s = 0` via `SchnorrAggregate::read` and have it verify as valid whenever the caller's challenge list is empty — a "signature" produced by no signer at all is accepted.

### Finding Description
`SchnorrAggregate::read` reads an attacker-controlled `u32` count of `R` points plus a scalar `s`, permitting `Rs` to be empty and `s` to be zero (`crypto/schnorr/src/aggregate.rs:77-88`). In `verify`, the only cardinality check is `self.Rs.len() != keys_and_challenges.len()` (`crypto/schnorr/src/aggregate.rs:127-130`), which passes when both are empty. With an empty list, no `pairs` are pushed except `(-self.s, C::generator())` (`crypto/schnorr/src/aggregate.rs:138-144`), so for `s = 0` the `multiexp_vartime` result is the identity and `verify` returns `true`. By contrast, the producer side correctly refuses the empty case — `SchnorrAggregator::complete` returns `None` when nothing was aggregated (`crypto/schnorr/src/aggregate.rs:175-178`) — so `verify` is strictly weaker than the producer, the same shape as the YOLO `< 2` vs `< 1` discrepancy.

This is the mirror of the valid minimum checks elsewhere: `AlgorithmSignMachine::sign` rejects `included.len() < t` (`crypto/frost/src/sign.rs:298-300`), `ThresholdParams::new` rejects `t == 0 || n == 0` (`crypto/dkg/src/lib.rs:167-169`), and `check_keys` rejects an empty MuSig key list (`crypto/dkg/musig/src/lib.rs:47-49`). The aggregate verifier alone lacks the minimum-of-one bound.

### Impact Explanation
Wherever a caller constructs `keys_and_challenges` from an accumulated message set that can be empty (the aggregator is consumed in `coordinator/tributary/src/tendermint/mod.rs` for vote/commit aggregation), an unprivileged party can supply serialized bytes representing the empty aggregate with `s = 0` and produce an "accepted" signature over nothing — i.e., a forged aggregate signature with zero actual signers, reachable purely through untrusted bytes fed to `SchnorrAggregate::read` plus `verify`. This satisfies the forged-signature/bar acceptance criterion; the documented DST requirements do not cover the empty-statement case.

### Likelihood Explanation
Reachability depends on a caller invoking `verify` when its accumulated statement set is empty (e.g., a batch or vote set that ended up with zero valid entries) — precisely the edge case the report describes (proceeding with zero participants). If any such caller treats a successful `verify` as authorization, the forged empty aggregate is trivially constructible by any unprivileged party; no key material or collusion is required. I did not fully confirm the empty-set path in `tendermint/mod.rs`, so end-to-end exploitability there is uncertain; the cryptographic flaw in `verify` itself is unconditional.

### Recommendation
Reject empty statement lists in `SchnorrAggregate::verify` (and/or require `self.s != 0` / non-identity `R`s): add `if keys_and_challenges.is_empty() { return false; }` before the length equality check, matching the producer-side `complete()` refusal of empty aggregates. Optionally also reject identity/non-canonical `R` points.

### Proof of Concept
```rust
// crypto/schnorr/src/aggregate.rs semantics:
// Attacker-serialized aggregate: len = 0u32, no R points, s = 0
let mut bytes = 0u32.to_le_bytes().to_vec();
bytes.extend(<C as Ciphersuite>::F::ZERO.to_repr().as_ref());
let agg = SchnorrAggregate::<C>::read(&mut bytes.as_slice()).unwrap();

// Caller with an empty accumulated statement set:
assert!(agg.verify(b"dst", &[])); // returns true: multiexp == identity
// Forgery accepted with zero signers — analog of drawWinner running with 0 participants.
```
