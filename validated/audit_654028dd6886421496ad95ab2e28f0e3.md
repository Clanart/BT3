### Title
Bank precompile `sendNative` bypasses `BlockedAddr`/`IsInDenomAllowList` checks enforced by `MsgSend` - (File: precompiles/bank/bank.go)

### Summary
The Node.js report shows `fs.openAsBlob()` bypassing the permission system because it calls a low-level file-open primitive directly instead of routing through the permission-checked `fs.readFile`-style path. The Sei EVM bank precompile has the same architectural flaw: its `send` method correctly routes through `bankMsgServer.Send`, which enforces recipient/sender restrictions, but its `sendNative` method calls the raw keeper primitive `bankKeeper.SendCoinsAndWei` directly, skipping those same restrictions.

### Finding Description
`precompiles/bank/bank.go` exposes two EVM-callable transfer methods:
- `send` (ERC20-pointer transfers of a bank denom) builds a `banktypes.MsgSend` and executes it via `p.bankMsgServer.Send(...)` [1](#0-0) .
- `sendNative` (native usei/wei value transfer attached to a precompile call) instead calls the bank keeper method directly: `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)` [2](#0-1) .

The permission-relevant checks — `BlockedAddr` (rejecting transfers to protected/module addresses) and `IsInDenomAllowList` (denom-specific transfer allow-lists) — are implemented in the Cosmos SDK bank `MsgServer.Send` handler, not inside the `SendCoins`/`SendCoinsAndWei` keeper primitives themselves: [3](#0-2) 

The `BaseSendKeeper.SendCoins` primitive (and by the same pattern, `SendCoinsAndWei`) performs no `BlockedAddr` or allow-list validation; it only moves balances and lazily creates the recipient account: [4](#0-3) 

`BlockedAddr` itself is defined purely as a lookup used by the message-layer guard, and is not consulted anywhere inside the `sendNative` precompile code path: [5](#0-4) 

Because `sendNative` calls the keeper primitive directly instead of going through `bankMsgServer.Send`, an EVM transaction/contract can transfer native usei/wei to any address — including module accounts and other addresses that `BlockedAddr` is meant to protect from direct incoming transfers — something that is impossible via a normal `MsgSend` transaction or via the precompile's own `send` method.

### Impact Explanation
Module accounts (fee collector, mint, distribution, bonded/not-bonded pools, gov, etc.) are excluded from `BlockedAddr` specifically because unsolicited balance changes to these accounts can violate internal accounting invariants that other modules assume hold (e.g., that only module-internal minting/collection logic changes their balance). Allowing an EVM caller to force native token transfers into these accounts via `sendNative` can corrupt module bookkeeping invariants, potentially causing fund-accounting inconsistencies, permanent freezing of funds sent to addresses with no msg-based withdrawal path, or unexpected inflation of a module balance used in downstream distribution/settlement logic. This falls under "unauthorized transfer via precompile" / fund freezing categories.

### Likelihood Explanation
Any EVM transaction sender can call the bank precompile's `sendNative` payable method with `value` set and a target address — no special privilege is required beyond having an EVM/Sei associated address and Sei balance. This makes the bug trivially and cheaply reachable by any unprivileged transaction sender.

### Recommendation
Route `sendNative` through the same `BlockedAddr`/`IsInDenomAllowList`-enforcing path used by `send`/`MsgSend` (e.g., call `bankMsgServer.Send` or explicitly invoke `k.BlockedAddr` and `k.IsInDenomAllowList` checks before calling `SendCoinsAndWei`), so that native-value transfers initiated through the precompile are subject to the same access-control guarantees as bank module message transfers.

### Proof of Concept
1. Deploy/call a contract that invokes the bank precompile (`0x0000000000000000000000000000000000001001`) `sendNative(string receiverSeiAddr)` with `msg.value` set to a non-zero amount, where `receiverSeiAddr` is the bech32 address of a module account normally excluded via `BlockedAddr` (e.g., the fee collector or a staking pool address).
2. Observe that the transfer succeeds through `precompiles/bank/bank.go`'s `sendNative` → `bankKeeper.SendCoinsAndWei`, crediting the module account.
3. Compare with attempting the equivalent transfer via a standard `MsgSend` transaction to the same address, which is rejected by `k.BlockedAddr(to)` in `msg_server.go`'s `Send` handler — confirming the precompile path bypasses the check that the canonical transaction path enforces.

```go
func (k msgServer) Send(goCtx context.Context, msg *types.MsgSend) (*types.MsgSendResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	if err := k.IsSendEnabledCoins(ctx, msg.Amount...); err != nil {
		return nil, err
	}

	from, err := sdk.AccAddressFromBech32(msg.FromAddress)
	if err != nil {
		return nil, err
	}
	to, err := sdk.AccAddressFromBech32(msg.ToAddress)
	if err != nil {
		return nil, err
	}

	allowListCache := make(map[string]AllowedAddresses)
	if !k.IsInDenomAllowList(ctx, from, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)
	}

	if k.BlockedAddr(to) || !k.IsInDenomAllowList(ctx, to, msg.Amount, allowListCache) {
		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to receive funds", msg.ToAddress)
	}
```

```go
// BlockedAddr checks if a given address is restricted from
// receiving funds.
func (k BaseSendKeeper) BlockedAddr(addr sdk.AccAddress) bool {
	if len(addr) == len(CoinbaseAddressPrefix)+8 {
		if bytes.Equal(CoinbaseAddressPrefix, addr[:len(CoinbaseAddressPrefix)]) {
			return true
		}
	}
	return k.blockedAddrs[addr.String()]
}
```
