### Title
Attacker-controlled `ThresholdKeys` length causes large pre-validation memory allocation - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
`ThresholdKeys::read` trusts the serialized participant count `n` before validating the threshold parameters and immediately reserves `n` field elements for constant interpolation. Because `n` is a serialized `u16`, a short untrusted input can force an allocation proportional to `65,535 * size_of::<C::F>()` before the parser attempts to read the corresponding data. [1](#0-0) 

### Finding Description
The deserializer reads `t`, `n`, and `i` directly from the input stream. If the interpolation byte is `0`, it executes `Vec::with_capacity(usize::from(n))` before calling `ThresholdParams::new` or determining whether the declared coefficients are actually present. [1](#0-0) 

Validation of `t <= n` and `i <= n` does not occur until after the interpolation vector, secret share, and `n` verification shares have been parsed. [2](#0-1)  `ThresholdParams::new` itself permits any nonzero `u16` participant count satisfying those relations, so there is no deserialization-time protocol bound that prevents `n = 65535`. [3](#0-2) 

This matches the ZIP-bomb class as an input-size-to-resource amplification bug: the attacker only needs to supply the curve identifier, six parameter bytes, and one interpolation tag to trigger the reservation; they do not need to provide the `n` scalars for the allocation to occur. [4](#0-3) 

### Impact Explanation
For a 32-byte field representation, `n = 65535` requests approximately 2 MiB of vector capacity from only the small serialized header; wider fields increase the amplification proportionally. The vector is dropped if scalar parsing reaches EOF, but each active or concurrent deserialization can transiently consume this memory. [5](#0-4) 

An unprivileged party able to submit bytes to `ThresholdKeys::read` can therefore force disproportionate allocator pressure with very small inputs. Repeated concurrent requests can exhaust available memory or abort the process on allocation failure, degrading availability for unrelated signing operations. [6](#0-5) 

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API that accepts arbitrary `io::Read` input, and the malicious input does not need to represent a valid key to reach the allocation. [7](#0-6)  The exploit requires no private state, valid signature, malformed curve encoding, or cooperation from another participant; it only requires an attacker-controlled byte stream. [8](#0-7) 

The effect is bounded by the `u16` encoding and is transient for a single call, so the issue is a medium-severity availability concern rather than an unbounded persistent disk or memory write. [9](#0-8) 

### Recommendation
Parse `t`, `n`, and `i`, then call `ThresholdParams::new` and enforce the protocol’s maximum supported participant count before allocating interpolation storage. After validation, populate the vector incrementally without `Vec::with_capacity(n)`, or reserve only a small fixed capacity independent of attacker-controlled `n`. [10](#0-9) 

### Proof of Concept
The following generic test demonstrates that a tiny input triggers the allocation path and then fails at EOF:

```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;

fn allocation_trigger<C: Ciphersuite>() -> io::Result<()> {
  let mut serialized = Vec::new();

  // Curve ID.
  serialized.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  serialized.extend(C::ID);

  // t = 65535, n = 65535, i = 65535.
  serialized.extend(u16::MAX.to_le_bytes());
  serialized.extend(u16::MAX.to_le_bytes());
  serialized.extend(u16::MAX.to_le_bytes());

  // Interpolation::Constant. This executes Vec::with_capacity(65535).
  serialized.push(0);

  // No scalar bytes are supplied. The oversized reservation has already occurred.
  let result = ThresholdKeys::<C>::read(&mut serialized.as_slice());
  assert!(result.is_err());
  Ok(())
}
```

The allocation occurs at `Vec::with_capacity(usize::from(n))`; the subsequent `C::read_F` fails on EOF, after the attacker-controlled reservation has already been made. [5](#0-4)

impl ThresholdParams {
  /// Create a new set of parameters.
  pub const fn new(t: u16, n: u16, i: Participant) -> Result<ThresholdParams, DkgError> {
    if (t == 0) || (n == 0) {
      return Err(DkgError::ZeroParameter { t, n });
    }

    if t > n {
      return Err(DkgError::InvalidThreshold { t, n });
    }
    if i.0 > n {
      return Err(DkgError::InvalidParticipant { n, participant: i });
    }

    Ok(ThresholdParams { t, n, i })
