### Title
Silent remote-URL rewrite from unvalidated GitHub API `clone_url` allows repo hijack of pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl` overwrites a repository's local `origin` remote URL using the `clone_url` field of a `IAPIRepository` object returned by the GitHub API, with no validation that the new URL's hostname/owner match the original repository. This happens automatically, without any user prompt or confirmation, every time a tracked repository is selected/refreshed.

### Finding Description
When Desktop selects a repository that has an associated `GitHubRepository`, it calls `repositoryWithRefreshedGitHubRepository`, which fetches the repository object from the API (`api.fetchRepository(owner, name)`) and passes it into `updateRemoteUrl`: [3](#0-2) .

`updateRemoteUrl` checks only three conditions before rewriting the local git remote:
1. `protocolsMatch` — the scheme of the current remote and the new `clone_url` are identical (e.g., both `https:`).
2. `remoteUrlUnchanged` — the current remote still matches the *previously recorded* `gitHubRepository.cloneURL`.
3. `!urlsMatch` — the new URL differs from the current remote.

None of these checks constrain the new URL's hostname or owner/name to match the original repository: [4](#0-3) . If all three hold, `gitStore.setRemoteURL(...)` is called unconditionally with the attacker-influenced value, silently repointing `origin` to any arbitrary `https://` (or `http://`) host.

This is confirmed by the existing unit test, which shows the remote is rewritten from `https://github.com/my-user/my-repo` to a completely different repo path with no owner/host pinning enforced: [1](#0-0) .

The broken invariant, by analogy to the PAID Network report (a privileged state-mutating operation — minting tokens — trusted an attacker-influenced caller/value without verifying it against the expected authority), is: **a state-mutating operation (rewriting the git remote that all future pushes/fetches/credential-lookups depend on) trusts an externally-supplied value (the API's `clone_url`) without validating it against the expected identity (hostname+owner+name) of the repository being refreshed.**

An attacker capable of influencing the `IAPIRepository` object returned for `repos/{owner}/{name}` — e.g., a compromised/malicious GitHub Enterprise Server the victim is signed into, a network path attacker able to tamper with API responses for a non-pinned/self-signed GHE cert the user has chosen to trust, or a repository the victim was invited to that later changes ownership/clone URL server-side — can cause Desktop to silently rewrite the victim's local `origin` remote to an attacker-controlled `https://` endpoint under the same protocol, entirely automatically, the next time the user opens/selects that repository (`_selectRepositoryRefreshTasks` runs on every repository selection: [5](#0-4) ).

### Impact Explanation
Once `origin` is silently repointed:
- The next **push** performed through Desktop's UI (which the user believes goes to the original repository) is sent to the attacker's server instead — silently corrupting where the user's commits end up, potentially leaking proprietary source code.
- Because credential lookup for HTTPS remotes matches accounts by URL origin (`findGitHubTrampolineAccount`) [6](#0-5) , a changed origin can fall through to the **generic credential path**, which prompts the user via `promptForCredential`/`promptForGenericGitAuthentication` for a login/token for the new (attacker) host [7](#0-6)  — a realistic vector for token/credential exfiltration since the prompt looks like a normal Desktop auth dialog.
- **Fetches** would also pull from the attacker's repository, allowing injection of malicious commits/hooks into the user's local checkout on subsequent `git pull`/checkout operations.

This satisfies the "silent corruption of what the user commits or pushes" and potential "credential exfiltration" impact categories from an unprivileged attacker-controlled GitHub API object, without requiring local access, admin rights, or social engineering beyond normal repository usage.

### Likelihood Explanation
The refresh path runs unconditionally and silently on every repository selection for any repo with a linked `GitHubRepository` — no special user action beyond opening the repo is needed [2](#0-1) . The guard conditions (`protocolsMatch`, `remoteUrlUnchanged`) are trivially satisfiable in the common case (user hasn't customized the remote and both old/new URLs are `https:`), and are not hostname/owner-pinning checks at all, so they provide no real protection against a malicious/compromised API response. The main constraint is the attacker's ability to control the API response for that specific `owner/name`, which requires a compromised endpoint (typically GHE) or an untrusted enterprise/API MITM position — a plausible "git remote/proxy response" attacker per the task's valid-impact scope.

### Recommendation
In `updateRemoteUrl`, before calling `gitStore.setRemoteURL`, validate that the new `clone_url`'s hostname (and ideally owner) matches the existing remote's/API endpoint's expected host, and require that owner/name only change in ways consistent with a known repository rename event reported through a trusted, verified path (e.g., cross-checked via repository `id`, not just `clone_url` string). At minimum, surface a confirmation prompt to the user before silently rewriting `origin`, since this changes where the user's future commits are pushed.

### Proof of Concept
1. Sign in to a GitHub Enterprise Server (or any endpoint under attacker influence) and clone a repository tracked by Desktop, e.g. `https://ghe.example.com/org/repo.git`.
2. Attacker (controlling the GHE server or an on-path MITM able to tamper with the `repos/org/repo` API response) changes the `clone_url` field returned for that repository to `https://ghe.example.com/attacker/decoy.git` (same protocol/host, different owner/name — or even a different host if it still resolves to `https:`).
3. Victim reopens/selects the repository in Desktop. `_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` runs automatically [2](#0-1) .
4. Because `protocolsMatch` is true and `remoteUrlUnchanged` is true, `gitStore.setRemoteURL('origin', 'https://ghe.example.com/attacker/decoy.git')` executes with no prompt (mirrors the exact behavior demonstrated in the existing unit test) [1](#0-0) .
5. The victim's next push/fetch silently targets the attacker's repository.

    this.stopPullRequestUpdater()
    this.stopBackgroundPruner()

    this.startPullRequestUpdater(repository)

    this.startBackgroundPruner(repository)

  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
