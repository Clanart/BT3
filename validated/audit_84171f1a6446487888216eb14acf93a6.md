### Title
SSH `askpass` password-prompt matching allows password auto-fill/exfiltration to an untrusted SSH remote via unvalidated `username` key - ([File: app/src/lib/trampoline/trampoline-askpass-handler.ts])

### Summary
`handleSSHUserPassword` extracts a `username` string from the raw SSH `askpass` prompt text using `/^(.+@.+)'s password: $/` and immediately uses it as the lookup/storage key for a previously saved SSH password, without ever verifying that this string actually corresponds to the SSH host/user Desktop's own git operation is connecting to.

### Finding Description
GitHub Desktop configures `SSH_ASKPASS`/`DISPLAY` unconditionally for every git subprocess so OpenSSH never falls back to a TTY prompt. [2](#0-1)  Any time the OpenSSH client needs to display a prompt with no controlling terminal — including server-driven `keyboard-interactive` authentication, where the *prompt text is chosen entirely by the remote SSH server* — it invokes the trampoline binary with that literal string as an argument. The trampoline forwards it to `createAskpassTrampolineHandler`, which routes any parameter ending in `"'s password: "` to `handleSSHUserPassword`: [3](#0-2) 

```
async function handleSSHUserPassword(operationGUID: string, prompt: string) {
  const promptRegex = /^(.+@.+)'s password: $/
  const matches = promptRegex.exec(prompt)
  ...
  const username = matches[1]
  const storedPassword = await getSSHUserPassword(username)
  if (storedPassword !== null) {
    setMostRecentSSHUserPassword(operationGUID, username)
    return storedPassword
  }
  ...
}
``` [4](#0-3) 

`getSSHUserPassword` looks the string up directly in the OS keychain-backed `TokenStore` without any binding to the actual remote host of the current git operation: [5](#0-4) . Nothing in the trampoline pipeline (`ITrampolineCommand`, `withTrampolineEnv`, `trampoline-environment.ts`) records or checks the expected remote hostname for a given `operationGUID`/token — the only per-token state is the working directory path and a background-task flag. [1](#0-0) 

Because OpenSSH's `keyboard-interactive` authentication method lets the *server* supply arbitrary free-form prompt strings (this is standard SSH protocol behavior, not a Desktop bug in itself), an attacker-controlled SSH server can send a prompt whose text is exactly `"<any-string>@github.com's password: "` regardless of what host/user the connection is actually to. If the user previously chose "Remember password" for a legitimate `user@github.com` SSH password prompt (stored under that exact key), the attacker's crafted prompt string will collide with that stored key and Desktop's `handleSSHUserPassword` will silently return the stored GitHub password as the answer to the attacker's `keyboard-interactive` challenge — with no dialog, no user confirmation, and no check that this SSH session actually goes to `github.com`.

### Impact Explanation
If exploited, a stored SSH password associated with one host (e.g., a real `user@github.com` credential the user chose to remember) can be silently exfiltrated to a completely different, attacker-controlled SSH server, simply because that server chose to phrase its `keyboard-interactive` prompt text to match the stored key string. This is a credential-exfiltration vulnerability that requires no user interaction beyond adding/cloning from a malicious remote that the user's Desktop instance attempts to authenticate against via SSH.

### Likelihood Explanation
Exploitability depends on a precondition largely outside the attacker's control: the victim must have previously chosen "Remember password" for an SSH-password-authenticated remote (most GitHub SSH usage relies on key-based auth, not passwords, so stored SSH *passwords* are relatively uncommon in practice). This narrows real-world likelihood, but the underlying protocol-level trust gap (regex-derived key with no host binding) is exploitable against **any** stored SSH-user-password entry, not specifically GitHub — an attacker only needs to guess or learn that the victim has a stored password for `someuser@somehost` and phrase their `keyboard-interactive` prompt to match it exactly.

### Recommendation
Bind the SSH password store/lookup key to verified connection context rather than trusting free-form prompt text:
- Track the expected remote hostname (and ideally the SSH `TrampolineCommandIdentifier`/token) alongside `trampolineEnvironmentPath`, derived from the actual git remote URL being operated on for that `operationGUID`.
- In `handleSSHUserPassword`, only auto-fill a stored password when the parsed prompt's host component matches the verified remote host for the current operation; otherwise, always show the interactive `SSHUserPassword` dialog (never silently auto-supply a previously stored secret) so the user can visually confirm which host is asking.
- Consider not honoring `keyboard-interactive` free-text prompts for auto-fill at all, since the OpenSSH protocol allows the server to fully control that text.

### Proof of Concept
Unit-test style demonstration of the key collision (not requiring a real SSH server):
```ts
const promptRegex = /^(.+@.+)'s password: $/

// Legitimate prompt for a stored, trusted key:
promptRegex.exec("user@github.com's password: ")![1] // -> "user@github.com"

// Attacker-controlled keyboard-interactive prompt string sent by a malicious
// SSH server during a completely different connection (e.g. to evil.example.com):
promptRegex.exec("user@github.com's password: ")![1] // -> "user@github.com" (identical key)
```
Both prompts yield the identical `username` key `"user@github.com"`, and `getSSHUserPassword("user@github.com")` [6](#0-5)  cannot distinguish which server is actually asking, since the regex/store never captures or validates the real destination host of the ongoing operation.

async function handleSSHUserPassword(operationGUID: string, prompt: string) {
  const promptRegex = /^(.+@.+)'s password: $/

  const matches = promptRegex.exec(prompt)
  if (matches === null || matches.length < 2) {
    return undefined
  }

  const username = matches[1]

  const storedPassword = await getSSHUserPassword(username)
  if (storedPassword !== null) {
    // Keep this stored password around in case it's not valid and we need to
    // delete it if the git operation fails to authenticate.
    setMostRecentSSHUserPassword(operationGUID, username)
    return storedPassword
  }
