## Analysis

The report's underlying bug class is: **two identifiers that are assumed to always be distinct are never actually checked for equality, and when they collide, the "second" write silently clobbers/corrupts the state tied to the "first."**

I traced this pattern into Desktop's Copilot-driven merge-conflict auto-resolution feature, which writes AI-generated content straight to working-directory paths taken from `git status` for a repository whose content (including branch names, file layout, and casing of tracked paths) is fully attacker-controlled by whoever authored the conflicting branch/remote.

### Title
Copilot conflict-resolution write path assumes case-distinct git paths map to distinct files on disk - (File: `app/src/lib/stores/app-store.ts`)

### Summary
Desktop's Copilot auto-resolve-conflicts flow reads the list of conflicted files from `git status` (exact, case-sensitive path strings, since git itself is case-sensitive), builds per-file contexts, and later writes each file's AI-resolved content back to disk using `resolveWithin(repository.path, resolution.path)` followed by `writeFile(absolutePath, ...)`. Neither step verifies that the file paths involved are actually distinct *on the host filesystem*. On the default configurations Desktop ships on (macOS APFS, case-insensitive/case-preserving; Windows NTFS, case-insensitive), a crafted merge/rebase source containing two tracked paths that differ only in case (e.g. `Foo.txt` and `foo.txt`) resolves to a single on-disk file via `realpath` inside `resolveWithin` (`app/src/lib/path.ts:36-72`). The write loop in `app-store.ts` then treats them as two independent conflicts, `writeFile`s twice to the same physical path, and stages both logical git paths for the same commit — silently discarding one AI resolution and committing content the user never reviewed under the path they believe it belongs to.

### Finding Description
- `getStatus`/`buildStatusMap` in `app/src/lib/git/status.ts:297-349` keys working-directory files by the exact `entry.path` string returned by `git status --porcelain=2`, which git treats case-sensitively — so `Foo.txt` and `foo.txt` are legitimately two separate tracked entries. [1](#0-0) 
- Copilot's context builder resolves each conflicted file independently through `resolveWithin(workingDirectory, file.path)`, which internally calls `fs/promises.realpath` on both the root and the joined path and only checks that the *resolved* real path starts with the real root — it never compares whether two different `file.path` inputs collapse to the same `realResolved` value. [2](#0-1) 
- `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:473-521`) only rejects *string-identical* duplicate paths returned by the model — it has no concept of filesystem case-folding, so two distinct-but-colliding git paths pass validation as "two files." [3](#0-2) 
- The actual write/staging loop resolves each resolution's path independently and calls `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` for each, then `git add -- <path>` for every logical path, with no check that two `absolutePath`s coincide. [4](#0-3) 

Because the two writes target the same inode on a case-insensitive filesystem, the second `writeFile` silently overwrites the first. Both logical paths are still `git add`-ed, so the resulting commit stages the *second* resolution's content under *both* git paths (one correctly, one as a duplicate/misattributed blob) — i.e., silent corruption of what the user commits, without any error or warning surfaced by the app.

### Impact Explanation
This is attacker-reachable purely by controlling a git object graph (a branch/commit that introduces two case-colliding paths) that the victim merges/rebases against and then runs Copilot's "auto-resolve conflicts" feature on. The result is silent corruption of the resulting commit's contents relative to what the user (and the AI) believed was being resolved and reviewed — one of the explicitly valid impact categories (`silent corruption of what the user commits or pushes`). No existing guard catches it: `resolveWithin` only guards against *escaping* the repository root, not against *collapsing* two distinct repo-relative paths onto the same disk location, and `validateResolutionPaths` only guards against literal string duplicates.

### Likelihood Explanation
Requires: (1) a malicious/compromised remote or PR branch containing two tracked paths differing only by case, (2) the user merges/rebases it locally, hits conflicts on both paths, and (3) uses the Copilot "auto-resolve conflicts" feature (which writes files without further per-hunk diff confirmation being mandatory to accept). All three are ordinary, unprivileged Desktop usage on the platform's default filesystem case-insensitivity — no admin rights, local access, or social engineering beyond a normal merge/PR workflow.

### Recommendation
Before writing each Copilot resolution to disk, resolve every conflicted file's `absolutePath` up front and detect collisions (e.g., by comparing `realpath` results, or by using a case/normalization-aware set) across the whole batch; if two logical paths collapse to the same physical path, skip both and surface them as unresolved/manual-only conflicts rather than silently overwriting. The same collision check should be added to `validateResolutionPaths` so a colliding pair is rejected before any file I/O occurs.

### Proof of Concept
1. On a case-insensitive/case-preserving filesystem (macOS default, Windows), create a repo with two branches: `main` adds `src/Config.ts`, `feature` adds `src/config.ts`, both modifying an overlapping symbol so a conflict is forced on merge for both entries in `git status --porcelain=2`.
2. Victim clones/fetches, checks out `main`, runs `git merge feature` (or Desktop's UI equivalent) — two entries appear in the conflict list: `src/Config.ts` and `src/config.ts`.
3. Victim invokes Copilot's "Resolve with Copilot" action; both files are resolved independently, producing two different `resolvedContent` blobs for what the OS considers the same physical file.
4. During the write phase (`app-store.ts:7233-7259`), `resolveWithin` returns the same `absolutePath` for both logical git paths; the second `writeFile` silently overwrites the first, yet `git add -- src/Config.ts src/config.ts` stages both, producing a commit where one path's recorded blob does not match the content the user reviewed for it in the Copilot dialog.
