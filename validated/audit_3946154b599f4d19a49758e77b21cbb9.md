### Title
Permissionless ERC20 registration enables free minting of native bank-backed coins via `ConvertERC20` - (File: x/erc20/keeper/proposals.go, x/erc20/keeper/msg_server.go)

### Summary
The FantomToken report describes an owner/wallet-controlled loop that mints tokens for free by cycling ether through a settable wallet address, bypassing the token cap. The Cosmos EVM analog is not owner-privileged: when `PermissionlessRegistration` is enabled, any unprivileged account can deploy an arbitrary ERC20 contract with an unrestricted `mint` function, register it via `MsgRegisterERC20`, and then repeatedly self-mint the ERC20 token and convert it into native Cosmos coins through `ConvertERC20`, which mints real bank-denominated coins 1:1 with no economic backing.

### Finding Description
`registerERC20()` only rejects contracts that are already registered or whose denom metadata already exists; it never verifies that the ERC20 contract has a fixed total supply or that only the module/owner can mint [1](#0-0) . `CreateCoinMetadata` merely reads `name`/`symbol`/`decimals` from the contract via `QueryERC20`, with no supply invariant check [3](#0-2) . `RegisterERC20` in `msg_server.go` allows any signer to call this when `params.PermissionlessRegistration` is true, gated only by `IsERC20Enabled` [4](#0-3) .

Once registered as a "native ERC20" token pair, `ConvertERC20` → `convertERC20IntoCoinsForNativeToken` escrows the caller's ERC20 tokens into the module account (via `transfer`) and then calls `k.bankKeeper.MintCoins` to mint an equal amount of native Cosmos coins, sending them to the receiver [2](#0-1) . Since the attacker fully controls the ERC20 contract, they can mint unlimited ERC20 supply to themselves (their own contract, no `MINTER_ROLE` restriction needed since it's their own deployed code) and then convert unlimited amounts into genuine, transferable, spendable native bank coins — coins that are indistinguishable from other IBC/staking-denominated coins in the bank module and can be used chain-wide (transfers, staking, fee payment, IBC-out).

This mirrors the FantomToken bug precisely: a user-controlled, self-referential minting loop (there: owner-controlled wallet; here: attacker-controlled ERC20 contract) that lets the actor mint value "for free" that the accounting model assumes is backed 1:1.

### Impact Explanation
This breaks the core `x/erc20` invariant that native-coin supply backing a token pair is bounded by real escrowed value. An unprivileged attacker can mint unlimited native Cosmos coins with zero cost beyond gas, diluting real token holders and enabling theft/extraction of value from any pool, DEX, staking module, or IBC channel that accepts the affected denom, and corrupting total-supply accounting chain-wide — a Critical unauthorized-minting / accounting-corruption impact per the allowed impact gate.

### Likelihood Explanation
Requires `params.PermissionlessRegistration = true`, which is a genesis/governance-configurable parameter, not a hard-coded default I was able to confirm from the available files (the default value in `x/erc20/types/params.go` was not fully inspected). If permissionless registration is enabled on a live chain, exploitation requires no special privilege — any address can deploy a contract, register it, and mint — making likelihood high whenever this parameter is on. If the default is `false` and only governance can enable it, likelihood is lower but the underlying registration/conversion logic still lacks any minting-restriction check.

### Recommendation
When registering a native ERC20 token pair (whether via governance or permissionless registration), enforce that the contract's mint authority is either non-existent, restricted to the module/precompile address, or that total supply is fixed at registration time and independently verified against escrowed/minted amounts on every `ConvertERC20`/`ConvertCoin` cycle (not just balance-delta checks on the same call). Consider requiring an allow-list or an on-chain proof that the ERC20 contract cannot arbitrarily inflate supply before allowing it to back native coin minting.

### Proof of Concept
1. Ensure `x/erc20` params have `PermissionlessRegistration = true` and `EnableErc20 = true`.
2. Attacker deploys `EvilERC20` with a public, unrestricted `mint(address,uint256)` function (no role check).
3. Attacker submits `MsgRegisterERC20{Erc20Addresses: [EvilERC20]}` — succeeds via `registerERC20()` with no supply-safety checks [1](#0-0) .
4. Attacker calls `EvilERC20.mint(attacker, 10_000_000e18)` on their own contract — unrestricted, succeeds.
5. Attacker submits `MsgConvertERC20{ContractAddress: EvilERC20, Amount: 10_000_000e18, Receiver: attacker}`.
6. `convertERC20IntoCoinsForNativeToken` escrows the (freely minted) ERC20 tokens to the module account and calls `bankKeeper.MintCoins` + `SendCoinsFromModuleToAccount`, crediting the attacker with 10,000,000 native Cosmos coins of the corresponding IBC/native denom [2](#0-1) .
7. Attacker repeats steps 4–6 indefinitely, or transfers/stakes/IBC-transfers the minted native coins before detection.

Note: I was unable to confirm the default value of `PermissionlessRegistration` from the indexed files (only partial `params.go` matches were found), so likelihood assumes this governance parameter is enabled; if it is disabled by default on the target deployment, exploitation would require a governance vote first, which shifts this toward a governance-gated rather than fully unprivileged issue.

// CreateCoinMetadata generates the metadata to represent the ERC20 token on

func (k Keeper) CreateCoinMetadata(
	ctx sdk.Context,
	contract common.Address,
) (*banktypes.Metadata, error) {
	strContract := contract.String()

	erc20Data, err := k.QueryERC20(ctx, contract)
	if err != nil {
		return nil, err
	}

	// Check if metadata already exists
	_, found := k.bankKeeper.GetDenomMetaData(ctx, types.CreateDenom(strContract))
	if found {
		return nil, errorsmod.Wrap(
			types.ErrInternalTokenPair, "denom metadata already registered",
		)
	}

	if k.IsDenomRegistered(ctx, types.CreateDenom(strContract)) {
		return nil, errorsmod.Wrapf(
			types.ErrInternalTokenPair, "coin denomination already registered: %s", erc20Data.Name,
		)
	}

	// base denomination
	base := types.CreateDenom(strContract)

	// create a bank denom metadata based on the ERC20 token ABI details
	// metadata name is should always be the contract since it's the key
	// to the bank store
	metadata := banktypes.Metadata{
		Description: types.CreateDenomDescription(strContract),
		Base:        base,
		// NOTE: Denom units MUST be increasing
		DenomUnits: []*banktypes.DenomUnit{
			{
				Denom:    base,
				Exponent: 0,
			},
		},
		Name:    types.CreateDenom(strContract),
		Symbol:  erc20Data.Symbol,
		Display: base,
	}

	// only append metadata if decimals > 0, otherwise validation fails
	if erc20Data.Decimals > 0 {
		nameSanitized := types.SanitizeERC20Name(erc20Data.Name)
		metadata.DenomUnits = append(
			metadata.DenomUnits,
			&banktypes.DenomUnit{
				Denom:    nameSanitized,
				Exponent: uint32(erc20Data.Decimals), //#nosec G115 -- int overflow is not a concern here
			},
		)
		metadata.Display = nameSanitized
	}

	if err := metadata.Validate(); err != nil {
		return nil, errorsmod.Wrapf(
			err, "ERC20 token data is invalid for contract %s", strContract,
		)
	}

	k.bankKeeper.SetDenomMetaData(ctx, metadata)

	return &metadata, nil
}

func (k *Keeper) RegisterERC20(goCtx context.Context, req *types.MsgRegisterERC20) (*types.MsgRegisterERC20Response, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	params := k.GetParams(ctx)

	if !params.PermissionlessRegistration {
		if err := k.validateAuthority(req.Signer); err != nil {

			return nil, errortypes.ErrInvalidAddress.Wrapf("invalid ERC20 contract address: %s", addr)
		}
