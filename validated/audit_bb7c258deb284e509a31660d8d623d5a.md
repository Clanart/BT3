### Title
Zero-of-zero multisig spending condition allows signature-less spend from a deterministically-derivable address - (File: `stacks-common/src/address/mod.rs`, `stacks-codec/src/transaction.rs`)

### Summary
`StacksAddress::from_public_keys()` and the `Multisig`/`OrderIndependentMultisig` spending-condition `verify()` routines never reject `signatures_required == 0`. This is the direct structural analog of the Aave `LTV = 0` bug: a degenerate threshold value that the code assumes will never occur, but which is never actually validated, is used unmodified in the security-critical equality check. When `signatures_required = 0`, the "number of signatures supplied equals/at-least the required number" check is trivially satisfied by supplying **zero** signature fields, and the address (`signer` hash) that this configuration hashes to is fully deterministic and independent of any secret key.

### Finding Description
`StacksAddress::from_public_keys()` only checks `pubkeys.len() < num_sigs` and a hash-mode-specific consistency rule for `P2PKH`/`P2WPKH` (which forces `num_sigs == 1`). For `P2SH`/`P2WSH` there is **no lower bound** on `num_sigs`: [1](#0-0) 

With `num_sigs = 0` and an empty (or arbitrary) `pubkeys` vector, `public_keys_to_address_hash()` still produces a well-defined `Hash160` via `to_bits_p2sh`/`to_bits_p2sh_p2wsh`, which push `OP_0` for the required-count, push zero public keys, push `OP_0` for pubkeys.len(), and `OP_CHECKMULTISIG`: [2](#0-1) 

This hash is **entirely public and computable by anyone** — it depends on no secret material at all when `pubkeys` is empty.

On the verification side, `MultisigSpendingCondition::verify()` accepts any `fields` list whose derived `num_sigs` **equals** `signatures_required`: [3](#0-2) 
and `OrderIndependentMultisigSpendingCondition::verify()` accepts any `num_sigs` that is **not less than** `signatures_required`: [4](#0-3) 

Both then just recompute `StacksAddress::from_public_keys(0, hash_mode, signatures_required, &pubkeys)` and compare its hash to the claimed `signer`: [5](#0-4) [6](#0-5) 

With `signatures_required = 0` and `fields = []` (no `TransactionAuthField` entries at all), `num_sigs = 0`, satisfying both the `==` and `>=` checks with **zero authentication work performed**, and the recomputed address hash matches the "0-of-0" signer hash unconditionally — because it was derived from no keys in the first place. Deserialization does not reject this either: `consensus_deserialize` for both spending-condition types only checks `num_sigs_given == signatures_required` (exact match) or `num_sigs_given >= signatures_required` (order-independent variant), both trivially true at 0: [7](#0-6) [8](#0-7) 

This exactly mirrors the reported bug class: an unguarded zero-value threshold parameter (`maxLtvRaw == 0` ↔ `signatures_required == 0`) causes a security check (`netBorrowLimit.sub(borrowValue)` underflow ↔ `num_sigs == / >= signatures_required`) to silently degrade to "always passes," breaking the equality the whole authentication model relies on (`n`-of-`m` signature threshold enforcement).

### Impact Explanation
Any STX/asset balance held under the address `addr = hash(P2SH/P2WSH script with num_sigs=0, empty pubkey list)` can be spent by **anyone**, with **no valid signature whatsoever**, because the "spending condition" for that address requires and verifies zero signatures. Since the address is fully public and derivable by anyone from the two published constants (chain id, hash-mode byte, `num_sigs=0`), and the auth condition needed to spend it is trivial to construct (`fields: vec![]`, `signatures_required: 0`), this is a forged transaction that moves an asset (whatever balance lands in that address) without any authorization from a private key — matching the Critical impact category ("forging or replaying a transaction so an asset moves without authorization").

### Likelihood Explanation
Exploitation does not require compromising any private key or governance action — it only requires that STX/fungible/non-fungible assets end up assigned to the deterministic "0-of-0" principal (e.g., sent there by mistake, used as a burn/placeholder address, or targeted deliberately by an attacker who advertises it as a deposit/vanity address). This is comparable in likelihood to the Aave report's own conclusion that the analogous condition (`LTV = 0`) requires an unusual/edge-case setup (there, governance setting LTV to 0; here, funds being sent to a 0-of-0 address) rather than being triggerable purely by transaction crafting against a normal account. It was rated valid/confirmed-but-limited in the source report for the same reason.

### Recommendation
Reject `signatures_required == 0` (and, more generally, any inconsistency such as `signatures_required` mismatched with hash-mode expectations) in:
- `StacksAddress::from_public_keys()` in `stacks-common/src/address/mod.rs` / `stacks-common/src/types/mod.rs`
- The `Multisig`/`OrderIndependentMultisig` `consensus_deserialize` and `verify` paths in `stacks-codec/src/transaction.rs`

At minimum, add an explicit `num_sigs >= 1` guard so that the code can never construct or validate a "trustless" address that requires zero signatures to authorize spends.

### Proof of Concept
1. Compute `signer = public_keys_to_address_hash(&AddressHashMode::SerializeP2SH, 0, &vec![])` (no keys needed) — this is a fixed, publicly computable `Hash160`.
2. Construct a `StacksTransaction` whose origin auth is `TransactionSpendingCondition::Multisig(MultisigSpendingCondition { hash_mode: MultisigHashMode::P2SH, signer, nonce: <correct>, tx_fee: <correct>, fields: vec![], signatures_required: 0 })`.
3. Submit the transaction. `MultisigSpendingCondition::verify()` computes `num_sigs = 0` from the empty `fields`, which equals `signatures_required = 0`, passes; it recomputes the address from `(hash_mode, 0, [])`, which equals `signer` by construction, so `verify()` returns `Ok`, and the transaction is accepted as fully authorized — despite containing zero cryptographic signatures.
4. Any STX/token balance credited to that "0-of-0" principal can now be drained by constructing further such zero-signature transactions with increasing nonces.

/// Internally, the Stacks blockchain encodes address the same as Bitcoin
/// multisig address over p2sh (p2sh-p2wsh)
fn to_bits_p2sh_p2wsh<K: PublicKey>(num_sigs: usize, pubkeys: &Vec<K>) -> Hash160 {
    let mut bldr = Builder::new();
    bldr = bldr.push_int(num_sigs as i64);
    for pubk in pubkeys {
        bldr = bldr.push_slice(&pubk.to_bytes());
    }
    bldr = bldr.push_int(pubkeys.len() as i64);
    bldr = bldr.push_opcode(btc_opcodes::OP_CHECKMULTISIG);

    let mut digest = Sha256::new();
    let mut d = [0u8; 32];

    digest.update(bldr.into_script().as_bytes());
    d.copy_from_slice(&digest.finalize());

    let ws = Builder::new().push_int(0).push_slice(&d).into_script();
    Hash160::from_data(ws.as_bytes())
}

/// Convert a number of required signatures and a list of public keys into a byte-vec to hash to an
/// address.  Validity of the hash_flag vis a vis the num_sigs and pubkeys will _NOT_ be checked.
/// This is a low-level method.  Consider using StacksAdress::from_public_keys() if you can.
pub fn public_keys_to_address_hash<K: PublicKey>(
    hash_flag: &AddressHashMode,
    num_sigs: usize,
    pubkeys: &Vec<K>,
) -> Hash160 {
    match *hash_flag {
        AddressHashMode::SerializeP2PKH => to_bits_p2pkh(&pubkeys[0]),
        AddressHashMode::SerializeP2SH => to_bits_p2sh(num_sigs, pubkeys),
        AddressHashMode::SerializeP2WPKH => to_bits_p2sh_p2wpkh(&pubkeys[0]),
        AddressHashMode::SerializeP2WSH => to_bits_p2sh_p2wsh(num_sigs, pubkeys),
    }
}
