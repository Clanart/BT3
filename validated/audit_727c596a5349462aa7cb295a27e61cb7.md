### Title
Missing nil check on `state.GetDBImpl(evm.StateDB)` in legacy precompile error handler causes RPC node crash - (File: precompiles/common/legacy/v605/precompiles.go)

### Summary
The reported CVE class is a classic "unchecked allocation/lookup result dereferenced as if non-nil." An analogous, unfixed instance of this exact bug class exists in the Sei precompile framework's legacy version `v605`: `HandlePrecompileError` calls `state.GetDBImpl(evm.StateDB).SetPrecompileError(err)` without checking whether `GetDBImpl` returned `nil`, whereas every later legacy revision (`v610`, `v614`, `v620`, `v630`, `v65`, `v66`, `v67`) and the current `precompiles/common/precompiles.go` guard the same call with `if sdb := state.GetDBImpl(evm.StateDB); sdb != nil { sdb.SetPrecompileError(err) }`.

### Finding Description
`state.GetDBImpl` is documented and treated elsewhere in the same file as capable of returning `nil` — `Prepare()` in the very same file explicitly checks for it: [1](#0-0) 

But the error-handling helper in the *same, older* legacy revision skips that check entirely: [2](#0-1) 

This function is invoked from a `defer` in the precompile's `Run`/`RunAndCalculateGas` entrypoint to record any error onto the state DB (used for surfacing VM errors on `MsgEVMTransactionResponse` and metrics). If `Prepare()` itself fails because `GetDBImpl(evm.StateDB)` returned `nil` (i.e. `evm.StateDB` is not backed by Sei's custom `state.DBImpl` — a real, already-anticipated condition per the existing check), `Run` returns a non-nil `err`, and the deferred `HandlePrecompileError(err, evm, operation)` calls `GetDBImpl(evm.StateDB)` again — again getting `nil` — and immediately dereferences it via `.SetPrecompileError(err)`, causing a nil-pointer dereference panic.

Compare with the fixed later versions, which apply the same nil-guard used in `Prepare()`: [3](#0-2) [4](#0-3) 

This is the exact bug class in the CVE report: a keeper/helper allocates or looks up a pointer (`mtk_alloc_clk_data()` in the kernel case, `state.GetDBImpl()` here), a later revision recognized the call can fail/return nil (evidenced by the check already present in `Prepare()` and added to all newer legacy versions), but one code path in an older, still-shipped file was never updated to match, leaving an unguarded dereference.

### Impact Explanation
Any EVM call (from a submitted transaction, an `eth_call`, or `debug_traceCall`/historical replay) that is routed to the `v605` legacy precompile set and results in `evm.StateDB` not being a `*state.DBImpl` — the same condition `Prepare()` was written to handle gracefully — instead panics with a nil-pointer dereference inside `HandlePrecompileError`. Because this runs inside precompile execution invoked from the EVM interpreter, an unrecovered panic here can crash the calling goroutine/process, i.e. a crash of default-configuration EVM/RPC nodes servicing `eth_call`, `eth_estimateGas`, or trace RPCs against blocks/precompile addresses that resolve to the `v605` version. This matches the "crash of default-configuration RPC nodes" impact bar.

### Likelihood Explanation
Likelihood depends on how easily a caller can drive `Prepare()`/`Run()` into the `GetDBImpl(...) == nil` branch for the `v605`-versioned precompile set (e.g., via historical-block queries, tracing with a non-Sei `StateDB` wrapper, or gas-estimation paths that substitute a different `vm.StateDB`). The surrounding code treats this as a normal, reachable condition (it is explicitly checked in `Prepare()`), so the precondition for triggering the nil dereference in `HandlePrecompileError` is not purely theoretical — it is the same condition the rest of the file defends against, just missed in one function. I could not fully verify from the indexed code which call sites route requests to the `v605`-tagged precompile set (i.e., the height/version-selection logic that picks `legacy/v605` over newer versions), so exact reachability/frequency in current mainnet operation is uncertain.

### Recommendation
Apply the same nil-guard used in `Prepare()` and in every later legacy/current precompile revision to `precompiles/common/legacy/v605/precompiles.go`'s `HandlePrecompileError`:
```go
func HandlePrecompileError(err error, evm *vm.EVM, operation string) {
	if err != nil {
		if sdb := state.GetDBImpl(evm.StateDB); sdb != nil {
			sdb.SetPrecompileError(err)
		}
		metrics.IncrementErrorMetrics(operation, err)
	}
}
```
Audit all other `legacy/*` precompile directories for the same historical omission (this report only confirms `v605` as missing the guard among the versions sampled).

### Proof of Concept
1. Identify the version-selection logic (not fully located in this investigation) that routes an EVM call to `precompiles/common/legacy/v605` (e.g., based on block height/EVM version for historical replay or a specific precompile address active at that version).
2. Issue an `eth_call`/`debug_traceCall`/replay request at a height where the `v605` precompile set is selected, using a code path where `evm.StateDB` is not a `*state.DBImpl` (mirroring the condition `Prepare()` already guards against, e.g. via a tracing/simulation `StateDB` wrapper).
3. `Prepare()` returns `errors.New("cannot get context from EVM")`; the deferred `HandlePrecompileError` re-calls `state.GetDBImpl(evm.StateDB)`, gets `nil`, and calls `.SetPrecompileError(err)` on it, panicking with a nil-pointer dereference and crashing the servicing node process.

Note: I was unable to fully trace the exact production trigger conditions for `evm.StateDB` being a non-`DBImpl` type within the `v605` code path (version-routing/height-gating logic for legacy precompiles was not found in the indexed code), so the precise reachability from a single external RPC/transaction should be validated against the live version-selection logic before treating this as fully weaponizable.
