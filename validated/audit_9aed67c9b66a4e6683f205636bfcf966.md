### Title
Scanner offset registrations are immutable, making offset collisions and prior registrations a permanent DoS - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The SteadeFi report describes a write-once mapping (`feeds[token]`) with a `TokenPriceFeedAlreadySet` revert that prevents updating or removing stale entries, causing a permanent DoS of the affected asset. The same bug class exists in `Scanner::register_offset`: once a script is registered into `self.scripts`, the entry can never be updated or removed, and any later offset that resolves to an already-registered script is permanently rejected with `None`.

### Finding Description
`Scanner` maintains `scripts: HashMap<ScriptBuf, Scalar>` mapping a P2TR script to the scalar offset needed to spend it (`networks/bitcoin/src/wallet/mod.rs:155`). `register_offset` derives `p2tr_script_buf(key + G * offset)`, incrementing `offset` until the resulting point is even-Y, then inserts it:

```rust
// networks/bitcoin/src/wallet/mod.rs:184-195
loop {
  match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
    Some(script) => {
      if self.scripts.contains_key(&script) {
        None?;
      }
      self.scripts.insert(script, offset);
      return Some(offset);
    }
    None => offset += Scalar::ONE,
  }
}
```

There is no API to remove or replace a registered script. Because the increment-until-even loop makes offsets surjective rather than bijective (documented in the doc comment at lines 168-179), two distinct requested offsets can resolve to the same script — e.g., an odd-point offset `o` that increments to `o'`, followed later by a request for `o'` itself, or a request for `o' - k` which also increments to `o'`. The second registration is rejected with `None` purely because the first consumed the script, and there is no path to correct it. Registration order therefore determines which offsets are usable, exactly like the immutable `feeds` mapping in the report.

This is not theoretical for callers: `processor/src/networks/bitcoin.rs:324-331` wraps registration in `scanner.register_offset(offset).expect("offset collision")`, so a rejected registration panics rather than degrading gracefully.

### Impact Explanation
A requested offset that collides with a previously-registered script can never be registered — there is no update or removal path. Any funds sent to the address for that offset (`key + G * offset`) will be reported by `scan_transaction` with the *wrong* offset attached (the offset of whichever registration won the script), so the wallet derives the wrong spending key and the output is effectively unspendable: `scan_transaction` at `wallet/mod.rs:205-210` returns `ReceivedOutput { offset: *offset, ... }` looked up solely by `script_pubkey`. For callers that `expect` success, registration order or a collision is a hard panic/DoS.

### Likelihood Explanation
The condition is deterministic and depends only on the parity of `key + G * offset`, which is attacker/ordering-independent for any given (key, offset) pair. Any offset sequence containing two requests that normalize to the same even key — which occurs whenever an earlier request incremented onto the point a later request targets — triggers permanent rejection. The fix gap mirrors the reported bug: like Chainlink feeds that cannot be updated when circumstances change, a scanner that registered an offset for a key set that is later rotated, retweaked, or needs re-derivation (e.g., after a `tweak_keys` change) must be rebuilt from scratch with the exact same registration order to remain consistent; any divergence silently reassigns or drops offsets.

### Recommendation
Allow re-registration/removal, or better, make registration deterministic and collision-free by construction: reject increment-collisions explicitly with a distinct error (rather than silently succeeding with a bumped `offset` that steals a future offset's script), and document that callers must treat a `None` result as a fatal configuration error. If mutability is kept intentionally write-once, provide a `deregister_offset`/`clear` API so a stale or wrongly-registered script does not permanently poison the scanner.

### Proof of Concept
```rust
// With even-Y `key`:
let mut scanner = Scanner::new(key).unwrap();

// Pick an offset `o` such that key + G*o is ODD; register_offset bumps it to o+1
// and consumes the script belonging to offset o+1.
let mut o = Scalar::random(&mut OsRng);
while is_even(key + ProjectivePoint::GENERATOR * o) { o += Scalar::ONE; }
let bumped = scanner.register_offset(o).unwrap();
assert_eq!(bumped, o + Scalar::ONE); // scanner stole o+1's script for request o

// A later, legitimate request to register offset o+1 permanently fails —
// no update or removal exists, matching the immutable-feeds bug class.
assert!(scanner.register_offset(o + Scalar::ONE).is_none());
// Any funds sent to address(key + G*(o+1)) now scan with `offset = o`,
// yielding the wrong spending key -> unspendable output.
```
