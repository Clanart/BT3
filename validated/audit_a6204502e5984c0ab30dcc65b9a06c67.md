### Title
Instant reward-per-token snapshot in `BaseRewardPoolV2` lets a flash deposit dilute honest stakers' harvested WOM rewards - (File: `rewards/BaseRewardPoolV2.sol`)

### Summary
`BaseRewardPoolV2._provisionReward` folds newly queued rewards into `rewardPerTokenStored` instantly, based on the pool's `totalStaked()` value at the exact moment `queueNewRewards` is called, rather than streaming the reward over time like a Synthetix-style `rewardRate`/`periodFinish` design. Since `harvest()` on the pool helpers is permissionless and immediately triggers `queueNewRewards`, an unprivileged user can deposit a large amount of LP right before calling `harvest()`, then withdraw immediately after, capturing a disproportionate share of the freshly harvested WOM/bonus rewards that they did not economically earn, diluting the rewards long-term LP stakers were entitled to.

### Finding Description
In `rewards/BaseRewardPoolV2.sol`, reward accounting uses a global `rewardPerTokenStored` value that is updated all at once whenever new rewards are queued: [1](#0-0) 
This differs from a time-weighted emission model — the moment `queueNewRewards`/`_provisionReward` runs, the entire `_amountReward` is divided by whatever `totalStaked()` (i.e. `IERC20(stakingToken).balanceOf(operator)`, the live MasterMagpie balance) is at that instant: [2](#0-1) 

A staker's earned amount is `balanceOf(_account) * (rewardPerToken - userRewardPerTokenPaid) + userRewards`, and `userRewardPerTokenPaid` is only synced when the user's balance changes (deposit/withdraw) via `stakeFor`/`withdrawFor`/`updateRewards`: [3](#0-2) 

The harvest path that queues new WOM/bonus rewards is triggered by any unprivileged wallet calling `WombatPoolHelper.harvest()`, which has no access control and calls straight into `WombatStaking.harvest`, which ultimately calls `_sendRewards` → `IBaseRewardPool(_rewarder).queueNewRewards(...)`: [4](#0-3) [5](#0-4) 

Because `rewardPerTokenStored` jumps instantly and is not time-weighted, a wallet can:
1. Call `WombatPoolHelper.deposit()` to stake a large amount of LP into MasterMagpie right before the pool's pending WOM harvest is realized (increasing `totalStaked()` right before the reward injection dilutes the per-token rate for everyone, but also entitles the depositor to a share of the very reward about to be queued).
2. Call `WombatPoolHelper.harvest()` (permissionless) to trigger `queueNewRewards`, which immediately bakes the entire harvested reward into `rewardPerTokenStored` using the now-inflated `totalStaked()`.
3. Immediately call `withdraw()`/`getReward()` to claim a proportional share of the reward and exit — with no minimum holding period, since `balanceOf` snapshots update strictly at stake/unstake time and the reward accrues to whoever holds the balance at the instant `queueNewRewards` executes.

This is analogous to the reported bug class: the reward formula does not account for the LP's actual holding duration, so a user who deposits and withdraws in a very short window (potentially the same transaction sequence) can still capture a full pro-rata share of rewards that took a long time to accrue, at the expense of honest long-term stakers whose share of `rewardPerTokenStored` gets diluted by the transient large deposit.

### Impact Explanation
Honest, long-term LP stakers in any Wombat pool routed through `BaseRewardPoolV2` (all Wombat pool helpers using `createRewarder` via `MasterMagpie`) have their harvested WOM/bonus-token rewards diluted every time an opportunistic depositor times a large stake around a `harvest()` call. This is a direct theft of unclaimed yield from existing stakers, since the total reward pie is fixed at harvest time and get redistributed pro-rata based on `totalStaked()`, but the attacker only needed to hold their LP position for the duration of a single harvest transaction/flow rather than the period over which the reward actually accrued.

### Likelihood Explanation
`harvest()` is unprivileged and can be called by anyone at any time, and `deposit()`/`withdraw()` on `WombatPoolHelper` are also unprivileged with no lock-up or cooldown enforced in `BaseRewardPoolV2`'s stake/unstake accounting. No special conditions (oracle, governance, or privileged role) are required — any wallet holding the deposit token and gas can execute deposit → harvest → withdraw sequentially whenever a sizeable pending WOM reward exists in the underlying MasterWombat pool.

### Recommendation
Move reward distribution in `BaseRewardPoolV2` to a time-weighted streaming model (e.g., Synthetix `StakingRewards`-style `rewardRate` and `lastUpdateTime`/`periodFinish`) instead of instantly folding `_amountReward` into `rewardPerTokenStored` based on an instantaneous `totalStaked()` snapshot, so that rewards accrue proportional to the actual duration a staker's balance was present in the pool. Alternatively, enforce a minimum staking duration before a user's balance is eligible to receive a share of a given `queueNewRewards` call.

### Proof of Concept
A concrete PoC transaction script was not run against this codebase (no test harness was inspected in this session), but the exploit is directly derivable from the code:
1. Attacker observes/estimates a large pending WOM reward on `MasterWombat` for a given pool (via `WombatPoolHelper.pendingWom()`, which is a public view): [6](#0-5) .
2. Attacker calls `WombatPoolHelper.deposit(largeAmount, minLiquidity)`, staking into `MasterMagpie` via `_stake` → `IMasterMagpie(masterMagpie).depositFor(...)`: [7](#0-6) .
3. Attacker (or anyone) calls `WombatPoolHelper.harvest()`, which flows into `_sendRewards` → `queueNewRewards` → `_provisionReward`, instantly increasing `rewardPerTokenStored` using the now-larger `totalStaked()` that includes the attacker's stake: [1](#0-0) .
4. Attacker calls `WombatPoolHelper.withdraw()` and claims via `getReward`/`getRewards`, receiving a pro-rata share of the just-harvested reward proportional to their large but short-lived stake: [8](#0-7) .

Because I do not have terminal/test-execution access in this session, I could not run a Foundry/Hardhat test to produce exact numeric before/after reward figures as the original report did. If precise numeric confirmation is needed, a Devin session with repo and test-runner access should add a test analogous to the reported `testPocReward` (stake large amount → trigger harvest → withdraw quickly → compare rewards received by a long-term staker with and without the attacker's flash stake).

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;

        if (totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingTokenDecimals) /
                totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);

    /// @param _rewardToken the address of the reward token to send
    /// @param _rewarder the rewarder that will get the rewards
    /// @param _amount the initial amount of rewards after harvest

    function _sendRewards(
        address _lpToken,
        address _rewardToken,
        address _rewarder,
        uint256 _amount
    ) internal {
        if (_amount == 0) return;
        uint256 originalRewardAmount = _amount;

        if (!isPoolFeeFree[_lpToken]) {
            for (uint256 i = 0; i < feeInfos.length; i++) {
                Fees storage feeInfo = feeInfos[i];

                if (feeInfo.isActive) {
                    address rewardToken = _rewardToken;
                    uint256 feeAmount = (originalRewardAmount * feeInfo.value) / DENOMINATOR;
                    _amount -= feeAmount;
                    uint256 feeTosend = feeAmount;

                    if (feeInfo.isMWOM && rewardToken == wom) {
                        if (smartWomConverter != address(0)) {
                            IERC20(wom).safeApprove(smartWomConverter, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IConverter(smartWomConverter).smartConvert(feeAmount, 0);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        } else {
                            IERC20(wom).safeApprove(mWom, feeAmount);
                            uint256 beforeBalnce = IMWom(mWom).balanceOf(address(this));
                            IMWom(mWom).deposit(feeAmount);
                            rewardToken = mWom;
                            feeTosend = IMWom(mWom).balanceOf(address(this)) - beforeBalnce;
                        }
                    }

                    if (!feeInfo.isAddress) {
                        IERC20(rewardToken).safeApprove(feeInfo.to, 0);
                        IERC20(rewardToken).safeApprove(feeInfo.to, feeTosend);
                        IBaseRewardPool(feeInfo.to).queueNewRewards(feeTosend, rewardToken);
                    } else {
                        IERC20(rewardToken).safeTransfer(feeInfo.to, feeTosend);
                        emit RewardPaidTo(feeInfo.to, rewardToken, feeTosend);
                    }
                }
            }
        }

        IERC20(_rewardToken).safeApprove(_rewarder, 0);
        IERC20(_rewardToken).safeApprove(_rewarder, _amount);
        IBaseRewardPool(_rewarder).queueNewRewards(_amount, _rewardToken);
