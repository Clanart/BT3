### Title
`resolveWithin()` boundary check uses unanchored `startsWith`, allowing sibling-directory escape via crafted `filepath` in the `x-github-client://openRepo` deep link - ([File: app/src/lib/path.ts])

### Summary
The Lyra report's broken invariant is: a check verifies that a value moved in the "correct direction" (sign match) without verifying it actually stayed within the safe bound (magnitude), so trades that nominally "reduce risk" can in fact increase it past the safe zone. The exact same class of flaw exists in `resolveWithin()`: it verifies that the resolved path "starts with" the root path (directional/prefix containment) without verifying an exact directory boundary (a trailing separator), so a resolved path can nominally look contained while actually escaping into a sibling directory.

### Finding Description
`_resolveWithin()` computes `resolved = resolve(normalizedRoot, normalizedRelative)`, then does a final safety check that only compares the *prefix* of the resolved absolute path to the root path: `realResolved.startsWith(realRoot) ? resolved : null` [3](#0-2) .

This is the same class of bug as the Lyra report: the check confirms the resolved value moved in the "safe direction" (toward/at the root) but never confirms it stopped at the correct boundary. If `pathSegments` contains a traversal like `..` followed by a path component that shares a prefix with the root's basename (e.g. root `/Users/dev/my-repo`, segment `../my-repo-evil/secret.txt`), the result is `/Users/dev/my-repo-evil/secret.txt`, and `'/Users/dev/my-repo-evil/secret.txt'.startsWith('/Users/dev/my-repo')` evaluates to `true` even though the resolved path is a sibling directory entirely outside the root. There is no trailing path-separator check (e.g. `realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)`), which is the missing "magnitude" check analogous to the Lyra bug.

This function is reached from an unprivileged, fully remote-controlled input: the `openrepo` deep-link handler parses a `filepath` query parameter with only an "is it absolute" guard [1](#0-0) , then `dispatcher.openRepositoryFromUrl` passes it straight to `resolveWithin(repository.path, filepath)` and, if not null, calls `shell.showItemInFolder(resolved)` [2](#0-1) . An attacker who controls a link the user clicks (a classic `x-github-client://openRepo?url=...&filepath=...` "Open in Desktop" deep link) can therefore attempt to make Desktop reveal/open a file outside the cloned repository, defeating the very purpose of the `resolveWithin` guard that the code comment says exists "to open a path outside of the repository root" (see the log message at line 1969 confirming intended containment).

### Impact Explanation
If exploitable, this allows a crafted deep link/URL clicked by a user to make Desktop navigate the OS file explorer to a file outside the intended repository directory, i.e., "file read outside the repo" territory per the impact scope, via `shell.showItemInFolder`. The practical severity depends on precondition of a same-prefix sibling directory existing alongside the target clone directory (see Likelihood).

### Likelihood Explanation
The attacker fully controls the `filepath` and `url` query parameters of the deep link the victim clicks, and only needs to guess/target a directory name likely to exist next to a repo clone (e.g. many users keep multiple repos in the same parent folder, and the attacker can also control the target repository's own name via the `url` parameter, allowing the attacker to choose the repo name that will collide with a real sibling folder name they know or guess, such as a common company/project naming convention). This still requires a specific sibling directory layout on disk, so it is not universally exploitable, but it is a real logic gap in an explicit security boundary function (`resolveWithin`) that is otherwise documented and unit-tested for exactly this kind of escape (symlink test cases exist) yet the basic unanchored-prefix case is not covered by any test [4](#0-3) .

### Recommendation
Change the final containment check in `_resolveWithin()` to require an exact match or a properly separator-anchored prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This closes the sibling-directory escape while preserving the intended "at or under root" semantics documented in the function's own JSDoc [5](#0-4) .

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openRepo?url=https://github.com/attacker/my-repo&filepath=..%2Fmy-repo-secrets%2Fcredentials.txt`.
2. If the victim has (or the attacker can otherwise arrange, e.g. via a previous phishing step or a commonly-named folder) a sibling directory `my-repo-secrets` next to where `my-repo` gets cloned/opened, `dispatcher.openRepositoryFromUrl` computes `resolveWithin(repository.path /* .../my-repo */, '../my-repo-secrets/credentials.txt')`.
3. `resolve('.../my-repo', '../my-repo-secrets/credentials.txt')` → `.../my-repo-secrets/credentials.txt'`, which `startsWith('.../my-repo')` is `true` due to the missing separator check.
4. `resolveWithin` incorrectly returns the path instead of `null`, and `shell.showItemInFolder` reveals the out-of-repo file, bypassing the intended containment guard at [6](#0-5) .
