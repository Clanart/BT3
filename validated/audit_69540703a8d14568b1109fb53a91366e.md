### Title
Reentrant escrow withdrawal via checks-effects-interactions violation in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of the Intent Gateway settles escrow by sending native ETH or calling `token.call(transfer(...))` to the beneficiary **before** decrementing the corresponding `_orders[commitment][token]` balance, and unlike the mainline EVM contract, neither `cancelOrder()` nor `withdraw()` is protected by a reentrancy guard.

### Finding Description
In `withdraw()` [1](#0-0) , for each token the contract checks only `_orders[commitment][token] == 0`, performs the external transfer, and only afterward executes `_orders[body.commitment][token] -= amount`. This is the opposite of the safe accounting order used in the mainline contract's `_withdraw()`, where `_orders[body.commitment][token] = escrowed - amount;` happens **before** the external call [2](#0-1) .

Compounding this, the mainline `IntentGatewayV2.cancelOrder()` is guarded with `nonReentrant` [3](#0-2) , but the Tron `cancelOrder()` has no such guard — it is declared simply `public payable` [4](#0-3) , and a repo-wide search shows `nonReentrant` appears only in the mainline `IntentGatewayV2.sol`, never in the Tron contract.

For a same-chain cancel, the order creator controls `order.inputs`, i.e., the escrowed token list, so they can register a token contract of their choosing as an input. `_cancelSameChain`-equivalent logic calls `withdraw(body, true)` with `beneficiary = order.user` (the attacker). If that token's `transfer` implementation calls back into the attacker's own contract (fee-on-transfer/hook-style tokens, or native ETH sent to a contract beneficiary — the native path uses a raw `.call{value: amount}("")`, which always hands over control before state is updated), the callback executes while `_orders[commitment][token]` still holds its pre-decrement (non-zero) value.

### Impact Explanation
Because `_filled[commitment]` is set once at the top of `withdraw()`, the most obvious re-entry paths (`fillOrder`/`cancelOrder` on the *same* commitment) are blocked by the `Filled()` check, which limits the practically demonstrable blast radius. However, this still leaves an exploitable CEI violation surface: any additional public/external function that reads or mutates `_orders[commitment][...]` for a not-yet-decremented token index in the same withdrawal loop, or any future code path/entry point added to this contract (it is missing the reentrancy guard entirely, unlike its sibling), can be re-entered mid-transfer. Given that this pattern diverges from the already-hardened mainline implementation specifically on the fund-movement hot path, it represents a structural regression that could allow double-release of escrowed funds to the wrong beneficiary or in excess of the escrowed amount if any additional state-touching function is reachable during the callback window — i.e., unauthorized transfer/duplicate settlement of bridge-custodied funds.

### Likelihood Explanation
Medium. Exploitation requires the order creator to use a token with a transfer-time callback (or to be a contract when receiving native token) as an escrowed input — fully within the calling user's control, no privileged relayer/prover/admin needed. The `_filled` guard closes the two obvious re-entry vectors, so a full, unconditional double-spend PoC purely within existing functions could not be constructed with high confidence from the available code; the primary confirmed defect is the CEI-order violation plus complete absence of `nonReentrant`, which is a real deviation from the security posture of the mainline gateway and a latent risk for any code path (including this file's remaining functions such as `fillOrder`, `select`, and future upgrades) that touches `_orders` for the same commitment during the callback window.

### Recommendation
- Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to decrement `_orders[body.commitment][token]` (and the transaction-fee balance) before performing any external `.call`/token transfer, mirroring `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`.
- Add `ReentrancyGuard` to the Tron `IntentGatewayV2` contract and apply `nonReentrant` to `cancelOrder`, `fillOrder`, and any other externally reachable function that can trigger `withdraw()`, matching the mainline `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
Not fully constructible from local code alone: a conclusive double-withdrawal PoC would require identifying a second public entry point (beyond `cancelOrder`/`fillOrder`, both blocked by the `_filled` check) that mutates `_orders[commitment][token]` and is reachable from a token/ETH transfer callback within the same `withdraw()` call — such a path was not confirmed in the portion of `evm/tron/contracts/apps/IntentGatewayV2.sol` reviewed (lines 1–100, 400–735). This is a real, confirmed code-pattern regression (external interaction before effects, no reentrancy guard) relative to the mainline contract, but I could not verify a concrete unblocked fund-drain path within my available tool budget; further review of the full Tron contract (particularly `fillOrder`, `select`, and any dust-sweep/postdispatch calldata functions) would be needed to confirm or rule out full exploitability.
