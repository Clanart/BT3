### Title
Forced reward claim inside `startUnlock`/`unlock` can permanently lock user's principal MGP/mWOM tokens if a reward token transfer reverts - ([File: VLMGP.sol / mWomSV.sol])

### Summary
`VLMGP.startUnlock()` and `VLMGP.unlock()` (and the analogous functions in `mWomSV.sol`) unconditionally call `IMasterMagpie(masterMagpie).multiclaimFor(...)` before performing the user's actual principal-unlocking logic. This mirrors the root cause of the Connext H-04 finding: an ancillary payment/side-effect (there, paying a relayer in a possibly-nonexistent asset; here, force-transferring reward tokens) is bundled into the critical user-recovery path, and if that side-effect reverts, the whole transaction reverts, permanently blocking access to the user's own principal funds.

### Finding Description
`startUnlock()` and `unlock()` both call: [1](#0-0) [2](#0-1) 

`multiclaimFor` routes to `_multiClaim` → `_claimBaseRewarder` → `IBaseRewardPool.getReward`/`getRewards`, which perform `IERC20(rewardToken).safeTransfer(_receiver, reward)` for every registered reward token in the pool's `BaseRewardPool`: [3](#0-2) [4](#0-3) 

Reward tokens are appended to the rewarder's `rewardTokens` array whenever `queueNewRewards`/`donateRewards` is called with a new token: [5](#0-4) 

If any one of these accumulated reward tokens has a transfer that can revert for a specific account (e.g., a token with a blacklist/pause feature such as USDC/USDT, where the *user's own address* — not an admin's — becomes blacklisted or sanctioned, or a token that later becomes paused, or one whose owner-side listing causes `safeTransfer` to always fail for that receiver), then `getReward`/`getRewards` will revert. Because `startUnlock`/`unlock` call `multiclaimFor` unconditionally and do not wrap it in a try/catch or allow skipping it, the revert propagates and the entire `startUnlock`/`unlock` transaction fails — every time, for that user, regardless of gas or retries.

Since there is no code path that lets the user initiate/complete an unlock of their own locked MGP/mWOM principal without first successfully claiming all pending rewards, and no admin or user function exists to forcibly remove a poisoned reward token from the rewarder's array in this contract, the user's locked principal becomes permanently stuck once any registered reward token in the associated `BaseRewardPool` refuses to transfer to that user.

### Impact Explanation
This is a direct analog to the Connext finding: bundling an unrelated/ancillary asset transfer into the critical path needed to recover a user's own principal funds, causing a permanent lock when that ancillary transfer reverts. Here the impact is that a user's locked MGP (via `VLMGP`) or mWOM (via `mWomSV`) can never be unlocked/withdrawn if any reward token queued into their pool's `BaseRewardPool` becomes non-transferable to that specific user's address (blacklisting, token pause, or similar token-level restriction is a realistic, externally-triggerable condition, not requiring a malicious admin of this protocol). This constitutes permanent freezing of user funds, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood depends on an external reward token (added legitimately via `queueNewRewards`, e.g., WOM, USDC-like bribe tokens, etc.) later restricting transfers to a particular user address — a scenario outside the Magpie protocol's control but realistic given common reward/bribe tokens include stablecoins/tokens with blacklist functionality. Any single such event permanently blocks that user's unlock forever with no self-service recovery path in the reviewed code.

### Recommendation
Decouple the mandatory reward claim from the principal-unlocking logic:
- Wrap the `multiclaimFor` call inside `startUnlock`/`unlock` in a try/catch (or move it to a separate, optional, best-effort call), so that a failure to transfer one reward token does not block the user from unlocking/withdrawing their principal.
- Alternatively, allow `BaseRewardPool.getReward`/`getRewards` to skip failing token transfers per-token (e.g., using a low-level call and continuing on failure) rather than reverting the whole claim, and/or provide an admin/user path to deregister a problematic reward token from `rewardTokens`.

### Proof of Concept
1. Admin/manager calls `queueNewRewards` on the `BaseRewardPool` tied to a VLMGP/mWomSV pool with a token `T` that has centralized blacklist functionality (e.g., a USDC-style stablecoin) — a normal, expected reward-token registration flow: [6](#0-5) .
2. User accrues some balance of `T` as a pending reward while having locked MGP in `VLMGP`.
3. User's address gets blacklisted on token `T` (independent third-party action, e.g., sanctions/compliance action on the stablecoin issuer's side), making `T.transfer(user, amount)` always revert.
4. User calls `VLMGP.startUnlock()` or `VLMGP.unlock()`; internally `multiclaimFor` → `getReward` attempts `IERC20(T).safeTransfer(user, reward)`, which reverts: [7](#0-6) .
5. The entire `startUnlock`/`unlock` transaction reverts. There is no way for the user to unlock their MGP principal because every retry hits the same reverting reward transfer — funds are permanently locked.

    function _claimBaseRewarder(address _stakingToken, address _account, address _receiver, address[] memory _rewardTokens) internal {
        IBaseRewardPool rewarder = IBaseRewardPool(tokenToPoolInfo[_stakingToken].rewarder);
        if (address(rewarder) != address(0)) {
            if (_rewardTokens.length > 0)
                rewarder.getRewards(_account, _receiver, _rewardTokens);
            else
                // if not specifiying any reward token, just claim them all
                rewarder.getReward(_account, _receiver);
        }
    }
