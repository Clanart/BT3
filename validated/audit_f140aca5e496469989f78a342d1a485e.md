## Analysis

The Solidity report's core pattern is: **a comment/label implies one behavior, but the actual guard/parameter enforces something weaker or different, and the discrepancy was never fixed** — i.e., a validation that looks like it exists but doesn't actually constrain the dangerous value. The closest real analog in this codebase is the `open-external` IPC handler in the main process.

### Title
Missing protocol allowlist on `open-external` IPC handler allows arbitrary-scheme `shell.openExternal` calls despite implied http/https check - (File: `app/src/main-process/main.ts`)

### Summary
The main-process IPC handler `open-external` contains a conditional block that *looks like* protocol validation (checking whether the path starts with `http://` or `https://`), but that check is only used for a **log message** — it does not gate, restrict, or reject the call to `shell.openExternal(path)`. Any string reaching this handler, regardless of scheme, is passed straight to `shell.openExternal`.

### Finding Description [1](#0-0) 

```ts
ipcMain.handle('open-external', async (_, path: string) => {
  const pathLowerCase = path.toLowerCase()
  if (
    pathLowerCase.startsWith('http://') ||
    pathLowerCase.startsWith('https://')
  ) {
    log.info(`opening in browser: ${path}`)
  }

  try {
    await shell.openExternal(path)
    return true
  } catch (e) {
    log.error(`Call to openExternal failed: '${e}'`)
    return false
  }
})
```

The `if` block reads like an intended safety/allowlist check (the classic "verify then act" pattern the audit report flags as broken when the check doesn't match the enforced value), but it has no `return`/`else`/throw — it's purely informational. Whatever `path` is, whether `http:`, `file:`, a bare UNC path (`\\host\share`), or an OS-specific handler URI, it is forwarded unfiltered to Electron's `shell.openExternal`.

This handler is invoked from the renderer via `openExternal` in `app/src/ui/main-process-proxy.ts`, which is re-exported as `shell.openExternal` in `app/src/lib/app-shell.ts` [2](#0-1) . That `shell.openExternal` is called throughout the renderer, including from the generic `LinkButton` component, which opens whatever `uri` prop it is given without protocol filtering: [3](#0-2) . `LinkButton`'s `uri` values are frequently populated from GitHub API data (URLs embedded in repository/PR/user objects), which an attacker-controlled repository, organization, or pull request can influence.

By contrast, the codebase does demonstrate the correct pattern elsewhere: `validateURL()` for GitHub Enterprise addresses explicitly throws on any non-`https:` protocol [4](#0-3) , and the markdown link interceptor only forwards clicks whose `a.protocol` matches `/^https?:/` before calling into `onMarkdownLinkClicked` [5](#0-4) . The `open-external` IPC handler is the one chokepoint that lacks this enforcement even though it contains code that superficially resembles it.

### Impact Explanation
If an attacker-controlled value (from a GitHub API object such as a repository homepage, PR body-derived link, or similar) reaches a `LinkButton`/`shell.openExternal` call path that does not pre-filter by protocol the way `sandboxed-markdown.tsx` does, the unrestricted `open-external` handler will pass a non-`http(s)` URI straight to Electron's `shell.openExternal`. Depending on OS, this can be abused for local file execution (`file://` pointing at a previously-downloaded/dropped executable), UNC-path/NTLM-hash leakage via SMB (Windows credential exfiltration), or invocation of other locally registered custom URI handlers — all without any local/physical access, admin rights, or prior malware, satisfying the "attacker controls a GitHub API object / a link the user clicks" impact class.

### Likelihood Explanation
Exploitability is high for any UI surface where a link/button's target URL is rendered from remote/attacker-influenced data and forwarded to `shell.openExternal` without a client-side protocol check equivalent to the one used in `sandboxed-markdown.tsx`. The main-process handler provides zero backstop regardless of which renderer surface is used, so a single missed/inconsistent filter in the renderer becomes fully exploitable. I was not able to exhaustively trace every call site that feeds a `LinkButton.uri` or `shell.openExternal` argument from raw GitHub API/repository data before running out of tool budget, so the exact reachable renderer entry point (beyond the confirmed unguarded IPC handler itself) is not fully enumerated here.

### Recommendation
Make the `open-external` handler enforce an explicit protocol allowlist (e.g., `http:`/`https:`/`mailto:` only) and reject/return `false` for anything else, rather than only logging on the http/https branch. Additionally, audit all renderer call sites that pass externally-sourced strings into `shell.openExternal`/`LinkButton` to ensure they use the same allowlist as `sandboxed-markdown.tsx`'s link interceptor.

### Proof of Concept
1. Identify a UI surface that renders a `LinkButton`/link whose `uri` is sourced from a GitHub API field controllable by a repository owner or PR author (not fully enumerated — requires further code tracing).
2. Set that field to a non-`http(s)` value, e.g. `\\attacker.example.com\share\x` or `file:///C:/Users/victim/Downloads/malicious.exe`.
3. Victim clicks the rendered link inside GitHub Desktop.
4. The renderer calls `shell.openExternal(uri)` → IPC `open-external` → `shell.openExternal(path)` in `app/src/main-process/main.ts` line 591, with no protocol restriction, resulting in the OS handling the UNC path (potential NTLM leak) or opening the local executable.
