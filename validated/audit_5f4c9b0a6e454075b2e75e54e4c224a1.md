### Title
Native-token fee swaps in `EvmHost.dispatch()`/`fundRequest()` use `block.timestamp` as the Uniswap deadline, nullifying slippage protection against delayed inclusion - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` each swap native ETH for the protocol `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` whenever a user supplies `msg.value` instead of pre-approved fee tokens. In all three call sites the deadline argument passed to Uniswap is `block.timestamp` — i.e., the timestamp of whichever block eventually executes the transaction, not the timestamp at the time the user signed/submitted it.

### Finding Description
Uniswap's router `deadline` parameter exists to bound how long a signed/submitted swap can sit before execution, protecting the sender from being executed at a stale, unfavorable exchange rate if a block producer delays inclusion. Passing `block.timestamp` as that deadline is a well-known anti-pattern (and is literally the "never set deadline to `block.timestamp`" mitigation called out in the referenced report) because it evaluates to "whenever this transaction actually lands," making the deadline check `deadline >= block.timestamp` always trivially true regardless of how long the transaction has been pending in the mempool. There is no user-supplied, fixed deadline parameter on `DispatchPost`, `DispatchGet`, or `fundRequest()` that could otherwise bound execution to a window the caller actually intended. A block producer (or anyone able to delay relaying/mining the transaction) can hold the transaction until the WETH/feeToken pool price has moved unfavorably, then include it — the user still pays the exact `msg.value` sent but the swap executes against a stale reserve state with no protection against price movement over the delay window, since the "deadline" never actually expires.

### Impact Explanation
This directly causes fund loss for users paying Hyperbridge relayer/protocol fees in native token: they can receive a worse execution price on the ETH→feeToken swap (or overpay ETH relative to what the fee should have cost) with no recourse, since the swap is embedded inside `dispatch()`/`fundRequest()` and irreversible once executed. Because `dispatch()` is the primary entrypoint applications and end users use to pay for cross-chain POST/GET requests and to top up relayer fees (`fundRequest()`), this affects live, permissionless, unprivileged callers on every EVM deployment of `EvmHost`, matching the bounty's "stealing or loss of funds" impact category.

### Likelihood Explanation
Likelihood is moderate: exploitation requires a validator/block-builder (or a mempool actor with the ability to delay inclusion, e.g. via low gas price or private-order-flow control) willing to hold the transaction until the WETH/feeToken pool price moves against the user, which is exactly the "known block proposer schedule" scenario described in the source report. No malicious relayer, prover, or governance actor is required — the exposed surface is the public `dispatch()`/`fundRequest()` functions callable by any user paying with `msg.value`.

### Recommendation
Add an explicit `deadline` field (as an absolute timestamp chosen by the caller) to `DispatchPost`, `DispatchGet`, and to `fundRequest()`'s parameters, and pass that caller-supplied value to `swapETHForExactTokens` instead of `block.timestamp`. Never default the deadline to `block.timestamp` inside the function itself, since by definition that value is fixed only at execution time, not submission time.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` with `msg.value` set to cover `post.fee`, expecting the WETH→feeToken swap to execute promptly at the current pool price. [1](#0-0) 
2. The transaction is broadcast but a block producer chooses to delay inclusion (e.g., holding it in a private queue or simply mining several blocks before including it) while the WETH/feeToken pool price moves unfavorably for the user.
3. When finally included, `swapETHForExactTokens(post.fee, path, address(this), block.timestamp)` evaluates `deadline = block.timestamp` at execution time, so Uniswap's internal `require(deadline >= block.timestamp)` check trivially passes no matter how long the delay was.
4. The swap executes at the now-unfavorable rate, consuming the user's full `msg.value` to acquire only `post.fee` worth of `feeToken()` under stale market assumptions, with no mechanism for the user to have bounded how long they were willing to wait.
