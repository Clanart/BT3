### Title
Liquidation Uses Enabled-Asset-Filtered Debt Instead of Full Debt, Producing a Wrong Health Verdict That Blocks Liquidation of Positions with Disabled-Asset Debt - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`get-liquidation-position` is documented to return "enabled collateral + all debt" but its implementation is byte-for-byte identical to `get-position`, which filters both collateral **and** debt down to assets present in the currently-enabled bitmap. Because `liquidate()` uses this filtered position (not the full position) to compute `total-debt-usd` and the resulting `current-ltv` used in the fail-fast health check, any debt owed on an asset that has since been disabled is silently dropped from the health computation — exactly analogous to the penguin report's bug where the wrong collection (`playerOwnedPenguins` instead of `alivePenguins`) was used for a limit check.

### Finding Description
`get-liquidation-position` is defined as: [1](#0-0) 

```
(define-private (get-position (account principal)) ;; enabled only
  (let ((mask (get-enabled-bitmap)))
    (contract-call? .v0-market-vault get-position account mask)))

(define-private (get-full-position (account principal)) ;; all collaterals
  (contract-call? .v0-market-vault get-position account MAX-U64))

(define-private (get-liquidation-position (account principal)) ;; liquidation specific (enabled collateral + all debt)
  (let ((mask (get-enabled-bitmap)))
    (contract-call? .v0-market-vault get-position account mask)))
```

Despite the comment claiming "enabled collateral + all debt," `get-liquidation-position` calls `.v0-market-vault get-position account mask` with `mask = get-enabled-bitmap`, the exact same call used by `get-position` (enabled-only). In `v0-market-vault.clar`, `get-position` filters **both** the collateral list and the debt list against the single mask argument via `relevant`/`iter-lookup-collateral`/`iter-lookup-debt` (the `false` flag passed to `relevant` for debt still checks membership in the same enabled bitmap, just shifted by the debt offset). There is no separate "all debt" mask ever combined in — the intended behavior (collateral limited to enabled assets, but debt always included regardless of asset enablement) is never implemented.

`liquidate()` consumes this filtered `position` to build `total-debt-usd`: [2](#0-1) 

```
(position (try! (get-liquidation-position borrower)))
(pos-full (try! (get-full-position borrower)))
...
(assets (get-assets mask))
(notional-valued-assets (get-notional-evaluation { position: position, assets: assets }))
(total-collateral-usd (get collateral notional-valued-assets))
(total-debt-usd (get debt notional-valued-assets))
...
(current-ltv (if (is-eq total-collateral-usd u0)
                 (if (is-eq total-debt-usd u0) u0 BPS)
                 (mul-div-down total-debt-usd BPS total-collateral-usd)))
...
(health-check (asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY))
```

Note `pos-full` (the true, unfiltered debt+collateral list) is fetched separately and used only for collateral bookkeeping (`user-coll-balance`, bad-debt socialization checks), never to recompute `total-debt-usd`/`current-ltv`. If a borrower has debt in an asset that the DAO later disables (removed from the enabled bitmap — a normal, intended lifecycle action, not a misconfiguration), that debt's bit is absent from `get-enabled-bitmap`, so `iter-lookup-debt`'s `relevant` check drops the entry from `position.debt`. The notional evaluation and `current-ltv` are computed as if that debt did not exist.

### Impact Explanation
The direction of the error is a systematic **underestimation of `total-debt-usd`**, which underestimates `current-ltv`. The fail-fast `health-check` (`current-ltv >= ltv-liq-partial`) then incorrectly reports the position as healthy even when it is actually underwater once the disabled-asset debt is included. This:
- Blocks legitimate liquidators (`ERR-HEALTHY` reverts) from liquidating a genuinely unhealthy position, so the borrower keeps their collateral while carrying under-collateralized, unrepaid debt.
- Allows bad debt to accumulate unbounded on the disabled asset, since the only path to socialize/write it off (via `liquidate`) is gated by a health check that never fires for that debt.

The borrower benefits (retains over-leveraged position, avoids liquidation penalty); the protocol/lenders of the disabled asset bear the risk of unrecoverable debt. This lands on **temporary/permanent freezing of funds and protocol insolvency risk** — the debt-asset vault's lenders cannot recover their principal because the position can never be flagged liquidatable through the standard path, matching the in-scope "Critical/High" impact classes for wrong health verdicts leading to frozen or lost funds.

### Likelihood Explanation
This requires only that the DAO disable an asset that has active borrowers — a normal, expected operational action (e.g., deprecating an asset), not a bug in DAO configuration itself. Any account holding debt in that asset at disable-time becomes effectively unliquidatable for that debt going forward, making this readily triggerable in production without any attacker-controlled misconfiguration.

### Recommendation
Fix `get-liquidation-position` to actually implement its documented semantics: collateral should still be filtered to the enabled bitmap, but debt must be sourced from the full/unfiltered debt list (e.g., call `market-vault get-position` with a combined mask of `enabled-collateral-bits | ALL-DEBT-BITS`, or separately merge `pos-full`'s debt list into the position used for `get-notional-evaluation`), so `total-debt-usd`/`current-ltv` in `liquidate()` always reflect the borrower's complete debt regardless of whether the underlying asset is currently enabled.

### Proof of Concept
1. Borrower supplies collateral and borrows against asset `X` (asset `X` enabled at the time).
2. DAO later disables asset `X` (removed from `get-enabled-bitmap`), a normal operational action; borrower's debt in `X` remains recorded in `market-vault`'s `debt` map.
3. Asset `X`'s price drops (or other collateral price drops) such that, including the debt on `X`, the position's true LTV exceeds `ltv-liq-partial`.
4. A liquidator calls `liquidate(borrower, ...)`. `get-liquidation-position` filters `position.debt` to the enabled bitmap, excluding asset `X`'s debt entirely.
5. `get-notional-evaluation` computes `total-debt-usd` without `X`'s debt, producing an artificially low `current-ltv`.
6. `(asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY)` reverts with `ERR-HEALTHY` even though the true position (per `pos-full`) is liquidatable, permanently blocking liquidation of the disabled-asset debt through this function.

Note: I was unable to fully step through `v0-market-vault.clar`'s `get-position` public function body within available tool calls (only the private helper functions `relevant`/`iter-lookup-debt`/`iter-lookup-collateral` were retrieved, from the equivalent `local-testing` copy), so the exact wiring of the public `get-position` entrypoint in `mainnet/contracts/market/v0-market-vault.clar` was not directly viewed — this should be verified by a follow-up read of that file before remediation.
