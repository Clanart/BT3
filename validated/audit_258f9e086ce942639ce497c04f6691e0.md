### Title
`associate`/`associatePublicKey` in the Sei `addr` precompile recover addresses from unbound signatures reusable across chains and purposes - (File: precompiles/addr/addr.go)

### Summary
The `addr` precompile's `associate` method recovers an EVM/Sei address pair purely from a raw ECDSA signature (`v, r, s`) over an arbitrary caller-supplied `customMessage` string, with no chain ID, contract address, or protocol-specific domain separator baked into the signed hash. Any caller who obtains a valid `(v, r, s, customMessage)` tuple — signed by a victim for any purpose whatsoever, on any chain — can submit it to the precompile to force an address association and balance migration on Sei.

### Finding Description
`PrecompileExecutor.associate` at [1](#0-0)  hashes the caller-supplied `customMessage` with plain `crypto.Keccak256Hash([]byte(customMessage))` — no EIP-155/chain-id mixing, no EIP-712 domain separator, and no nonce — then recovers the signer's EVM/Sei address pair via `helpers.GetAddresses` and immediately calls `associateAddresses`, which is a state-changing operation reachable by any EVM caller through the precompile at `0x0000000000000000000000000000000000001004` [2](#0-1) .

Because the signed digest contains no chain-specific or purpose-specific binding, a signature the victim produced for one context (e.g. a personal_sign login message, or a signature made on a different Sei-based deployment/testnet, or even a stale association attempt) can be replayed verbatim by anyone to invoke `associate` on any chain where this precompile is deployed. This mirrors the reported bug class exactly: signatures lacking chain-id binding remain valid and reusable across different chain deployments/forks.

`associateAddresses` then performs a real state mutation: it calls `AssociationHelper.AssociateAddresses`, which sets the EVM↔Sei address mapping, assigns the account pubkey, and unconditionally migrates the cast address's spendable/locked/wei balances into the derived Sei address via `MigrateBalance` [3](#0-2) . The only guard is that the target Sei address must not already be associated [4](#0-3) .

### Impact Explanation
An attacker who obtains any signature a victim produced under their EVM key (posted publicly for an unrelated purpose, or leaked/observed from another chain) can front-run the victim's intended association, forcibly binding the victim's EVM address to its derived Sei address and triggering `MigrateBalance` without the victim's consent or awareness. Because the "already associated" check is one-shot, this also permanently forecloses the victim's own later, intentional association call for that Sei address. This is a real state-changing action executed by an unprivileged third party using signature material never intended to authorize a Sei-specific "associate" action, directly matching the reported bug class of chain-unbound trusted signatures being replayable outside their intended context.

### Likelihood Explanation
`v600`/`v603`/`v606`/`v610`/`v614`/`v65` legacy variants of this precompile share the identical pattern [5](#0-4) , meaning the same unbound-signature-reuse issue has persisted across multiple upgrade versions of the precompile. Any EVM signature with recoverable `(v,r,s)` and its plaintext message is sufficient — no special conditions are required beyond calling the public precompile method, making exploitation straightforward for anyone monitoring public signatures.

### Recommendation
Bind the `customMessage` signed for `associate`/`associatePublicKey` to a domain that includes the chain ID, the precompile/contract address, and ideally a purpose-specific prefix and nonce (e.g. an EIP-712 typed structure `Associate(uint256 chainId, address precompile, uint256 nonce)`), so a signature produced for association on one chain/deployment — or for an unrelated purpose — cannot be replayed to force an association elsewhere.

### Proof of Concept
1. Victim signs any message `M` with their EVM key for an unrelated purpose (e.g., a dApp login message), producing `(v, r, s)`; this signature and `M` become publicly visible (e.g., posted to a dApp backend, or is the victim's own earlier out-of-band association signature for a different Sei-based chain).
2. Attacker calls `addr.associate(v, r, s, M)` on the target Sei chain from any account.
3. `PrecompileExecutor.associate` recovers `evmAddr`/`seiAddr` from the signature over `keccak256(M)` [6](#0-5)  and calls `associateAddresses`, which succeeds because the victim's Sei address was not yet associated, causing `MigrateBalance` to move the victim's cast-address funds and pubkey binding without the victim ever calling `associate` themselves [7](#0-6) .
4. The victim's own subsequent, intentional `associate` call now fails with "address is already associated" [8](#0-7) .

func (p PrecompileExecutor) associate(ctx sdk.Context, method *abi.Method, args []interface{}, value *big.Int) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, 0, err
	}

	// v, r and s are components of a signature over the customMessage sent.
	// We use the signature to construct the user's pubkey to obtain their addresses.
	v := args[0].(string)
	r := args[1].(string)
	s := args[2].(string)
	customMessage := args[3].(string)

	rBytes, err := decodeHexString(r)
	if err != nil {
		return nil, 0, err
	}
	sBytes, err := decodeHexString(s)
	if err != nil {
		return nil, 0, err
	}
	vBytes, err := decodeHexString(v)
	if err != nil {
		return nil, 0, err
	}

	vBig := new(big.Int).SetBytes(vBytes)
	rBig := new(big.Int).SetBytes(rBytes)
	sBig := new(big.Int).SetBytes(sBytes)

	// Derive addresses
	vBig = new(big.Int).Add(vBig, utils.Big27)

	customMessageHash := crypto.Keccak256Hash([]byte(customMessage))
	evmAddr, seiAddr, pubkey, err := helpers.GetAddresses(vBig, rBig, sBig, customMessageHash)
	if err != nil {
		return nil, 0, err
	}

	return p.associateAddresses(ctx, method, evmAddr, seiAddr, pubkey)
}

func (p AssociationHelper) AssociateAddresses(ctx sdk.Context, seiAddr sdk.AccAddress, evmAddr common.Address, pubkey cryptotypes.PubKey, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if !castAddr.Equals(seiAddr) && p.accountKeeper.GetAccount(ctx, seiAddr) == nil {
		castAcc := p.accountKeeper.GetAccount(ctx, castAddr)
		castBaseAcc, ok := castAcc.(*authtypes.BaseAccount)
		if ok && castBaseAcc.GetPubKey() == nil && p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
			p.accountKeeper.SetAccount(ctx, authtypes.NewBaseAccount(seiAddr, pubkey, castBaseAcc.GetAccountNumber(), castBaseAcc.GetSequence()))
		}
	}
	p.evmKeeper.SetAddressMapping(ctx, seiAddr, evmAddr)
	acc := p.accountKeeper.GetAccount(ctx, seiAddr)
	if acc == nil {
		acc = p.accountKeeper.NewAccountWithAddress(ctx, seiAddr)
	}
	if acc.GetPubKey() == nil {
		if err := acc.SetPubKey(pubkey); err != nil {
			return err
		}
		p.accountKeeper.SetAccount(ctx, acc)
	}
	return p.MigrateBalance(ctx, evmAddr, seiAddr, migrateUseiOnly)
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
