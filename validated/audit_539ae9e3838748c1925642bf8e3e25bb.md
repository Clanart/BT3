### Title
Webhook shop attribution (`X-Shopify-Shop-Domain`) is not covered by HMAC verification, allowing cross-shop webhook/job forgery - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The reported smart-contract bug is a class of "instruction/context confusion" flaw: one context's identifier (`position_account` in `borrow_collateral`) is never bound to the identifier used by a related, security-critical action (`repay_sol`), so an attacker can satisfy the check for one identity while acting on another. In `shopify_app`, the analogous pattern exists in the webhook verification pipeline: the cryptographic proof of authenticity (HMAC) covers only the request body, while the tenant-identifying field (`shop_domain`) used to route/attribute the resulting background job is taken from an unauthenticated, unsigned HTTP header.

### Finding Description
`ShopifyApp::PayloadVerification#hmac_valid?` computes/verifies the HMAC over `request.raw_post` only: [1](#0-0) 

`ShopifyApp::WebhookVerification` uses this to gate the request, but the shop identity used by the app is derived from `shop_domain`, an untouched request header that is never part of the digest input: [2](#0-1) 

Because Shopify's webhook HMAC secret (`ShopifyApp.configuration.secret`) is the app's client secret, shared across every shop that installs the app (not shop-specific), any merchant who installs the app receives genuine, validly-signed webhook payloads for their own shop. Since the HMAC only signs the raw body and never the `X-Shopify-Shop-Domain` header, that same merchant can replay the identical signed body to the app's webhook endpoint while substituting a different, unrelated shop's domain in the header. `verify_request` will still pass (`hmac_valid?` only checks the body/secret), and the downstream job dispatch (`ShopifyAPI::Webhooks::Registry.process`, or the generated `Job.perform_later(shop_domain: webhook_request.shop, ...)`) will process the request as if it originated from the victim shop, because the shop attribution is taken straight from the forged header: [3](#0-2) [4](#0-3) 

This mirrors the root cause of the reported issue exactly: the security check (HMAC/`repay_sol` authorization) validates one piece of context (body/`random_account_as_id`), while a different, unchecked piece of context (`shop_domain` header/`position_account`) is what actually determines which tenant's resources the resulting action affects.

### Impact Explanation
Any merchant that has legitimately installed the app (an "unrelated merchant" relative to any victim shop) can forge the `shop_domain` attribution on a webhook request while keeping a body+HMAC pair valid for their own installation. This enables cross-shop confusion in whichever job consumes `shop_domain`, including the mandatory privacy jobs generated by the gem (`customers_data_request_job.rb.tt`, `customers_redact_job.rb.tt`, `shop_redact_job.rb.tt`) and any custom `CartsUpdateJob`/`OrdersCreateJob`-style handlers that key data lookups/writes off the `shop_domain` param rather than a verified per-shop signature. Depending on how the host app's job implementation trusts this value, this can lead to processing data-redaction or data-mutation actions attributed to a shop the attacker does not control - a cross-shop access/action issue matching the "accepted forged signed request" / "cross-shop access" impact classes named in the validation rules.

### Likelihood Explanation
Requires the attacker to be an app merchant (not privileged, not the host operator) who has installed the app on at least one shop and can send arbitrary HTTP requests to the app's public webhook endpoint with a spoofed header - both trivially available to any unrelated merchant. No secret material needs to be recovered; only a legitimately-received signed payload needs to be replayed with a modified header, which is a request-body/header manipulation entirely within attacker control.

### Recommendation
Bind the trusted identity used for job dispatch to something actually covered by the HMAC/signed payload rather than the raw `X-Shopify-Shop-Domain` header:
- Include the shop domain in the HMAC digest input (or use Shopify's `shop_id`/domain that is present in the JSON payload body itself, which is HMAC-protected) instead of trusting the header value for job attribution.
- Alternatively, validate that the `shop_domain` header matches a shop-scoped signature (e.g., using a per-shop signature such as Shopify webhook's `X-Shopify-Webhook-Id` correlated with API lookups, or use `ShopifyAPI::Webhooks::Registry`'s built-in body-derived shop attribution instead of the header) before allowing job dispatch to proceed.
- Document clearly that `shop_domain` in `WebhookVerification`/generated job templates is not authenticated and must not be trusted as an isolation boundary unless it is cross-checked against signed payload content.

### Proof of Concept
1. Install the target app on Shop A (attacker-controlled) and capture a legitimate webhook POST, e.g. `orders/create`, including its exact raw body and the valid `X-Shopify-Hmac-Sha256` header Shopify computed.
2. Replay this exact HTTP request to the app's `/webhooks/:type` endpoint, but replace the `X-Shopify-Shop-Domain` header value with `victim-shop.myshopify.com`.
3. `WebhookVerification#verify_request` calls `hmac_valid?(request.raw_post)`, which only checks the body against the shared app secret — it succeeds because the body is unchanged and the secret is app-wide, not shop-specific: [5](#0-4) 
4. `WebhooksController#receive` forwards the request to `ShopifyAPI::Webhooks::Registry.process`, or a generated controller calls `job_class_name.perform_later(shop_domain: webhook_request.shop, ...)` using the attacker-controlled header value as the shop attribution: [6](#0-5) 
5. The resulting job executes business logic (or a privacy/redaction job) believing the event pertains to `victim-shop.myshopify.com`, despite the request never having originated from or been signed by Shopify on behalf of that shop.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
