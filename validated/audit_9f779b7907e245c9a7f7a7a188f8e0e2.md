### Title
`SignableTransaction::new` excludes the `OP_RETURN` data output from the weight, fee, and `MAX_STANDARD_TX_WEIGHT` calculations - (networks/bitcoin/src/wallet/send.rs)

### Summary
The bug class from the external report — a committed amount that covers the base obligation but not the full promised amount (principal without interest) — maps onto `SignableTransaction::new` in `networks/bitcoin/src/wallet/send.rs`. When a caller supplies `data`, an `OP_RETURN` output is appended to the transaction's outputs, but the weight/vbytes/fee computation and the transaction-size limit check are performed on a transaction built **without** that output. The resulting transaction commits a fee that does not cover its actual serialized size.

### Finding Description
In `SignableTransaction::new`:

1. The `OP_RETURN` output is pushed into `tx_outs` before the weight is calculated [1](#0-0) .
2. `calculate_weight_vbytes` is then called with only `tx_ins.len()`, `payments`, and the change script — the `data` output is never included in the synthetic transaction whose `tx.weight()` is measured [2](#0-1) .
3. `needed_fee = fee_per_vbyte * vbytes` therefore excludes the vbytes consumed by the OP_RETURN output (a `value` field, script length, `OP_RETURN` opcode, and up to 80 bytes of pushed data — roughly 90+ bytes of real transaction size) [3](#0-2) .
4. The `NotEnoughFunds` check (`input_sat < payment_sat + needed_fee`) and the change-output derivation (`input_sat.checked_sub(payment_sat + fee_with_change)`) both use this under-measured fee, so leftover funds are misallocated between change and fee [4](#0-3) .
5. The `MAX_STANDARD_TX_WEIGHT` check uses `weight`, which similarly excludes the OP_RETURN output, so a transaction that is actually non-standard can pass the check [5](#0-4) .

Because `fee_per_vbyte` is caller-specified and the true fee is `sum(inputs) - sum(outputs)`, the signed transaction pays a *lower effective feerate* than the caller requested whenever `data` is present — the committed fee does not cover the full "amount owed" (the actual transaction size), exactly the shape of the Cooler collateral/interest bug.

### Impact Explanation
- The produced transaction's real feerate is `fee / actual_vbytes < fee_per_vbyte`. If `fee_per_vbyte` was chosen at or near the relay minimum (the code only enforces `needed_fee >= DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the underestimated `vbytes`), the transaction can fall below the minimum relay feerate once broadcast and be rejected or stuck.
- The `NotEnoughFunds` gate can admit parameter sets that only "balance" because the fee was undercharged, then dump the shortfall into the change/fees unpredictably.
- The weight-limit check can pass a transaction whose true weight exceeds `MAX_STANDARD_TX_WEIGHT`.
- In the processor path (`make_signable_transaction` calls `BSignableTransaction::new` with `data: None`), the bug is latent, but `SignableTransaction::new` is a public API explicitly documented as supporting `data`, so any consumer supplying data gets a transaction that does not pay the promised feerate.

### Likelihood Explanation
Any caller passing a non-`None` `data` argument triggers it deterministically; no adversarial timing or collusion is needed. The magnitude is bounded by the 80-byte data cap, which keeps it out of Critical/High territory, but it is a concrete accounting error in transaction construction — Medium at most.

### Recommendation
Include the OP_RETURN output (and the change output, when applicable) in the transaction passed to `calculate_weight_vbytes` before deriving `vbytes`, `needed_fee`, and performing the `MAX_STANDARD_TX_WEIGHT` check — i.e., compute the fee over the final output set, or add the data output's serialized size to `weight`/`vbytes` explicitly.

### Proof of Concept
```rust
// Conceptual: construct two transactions differing only in `data`
let inputs = vec![received_output];        // any ReceivedOutput
let payments = vec![(script_pubkey, 10_000)];

let no_data = SignableTransaction::new(inputs.clone(), &payments, None, None, 5).unwrap();
let with_data =
  SignableTransaction::new(inputs, &payments, None, Some(vec![0xaa; 80]), 5).unwrap();

// Both report the same needed_fee and weight-based accounting,
// yet with_data's serialized tx is ~90 bytes larger:
assert_eq!(no_data.needed_fee(), with_data.needed_fee());
// => with_data's effective feerate = fee / real_vbytes < 5 sat/vbyte
//    and it could slip under the relay minimum or the standard weight cap.
```
The root cause is that `data` is pushed to `tx_outs` (line 195) before weight calculation (line 204) but `calculate_weight_vbytes` rebuilds the measurement transaction from `payments`/`change` only, never seeing the OP_RETURN output [6](#0-5) .
