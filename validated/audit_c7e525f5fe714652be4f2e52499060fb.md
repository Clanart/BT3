### Title
Webhook payloads are authenticated only by body HMAC while shop identity is taken from an unsigned header, allowing cross-shop webhook forgery - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification` validates an inbound webhook solely by checking an HMAC over the raw POST body, using the app's single, shared `ShopifyApp.configuration.secret`. It never binds that signature to the shop the webhook claims to be from. The shop identity used by every downstream consumer (`WebhooksController`, and the documented custom-controller pattern) is read from the unsigned `X-Shopify-Shop-Domain` header. Any body+HMAC pair that is valid for one installation is therefore valid, unmodified, for a forged request that claims to be from a different shop, because the header carrying the shop is outside the signed data.

### Finding Description
`hmac_valid?` in `lib/shopify_app/controller_concerns/payload_verification.rb` computes: [1](#0-0) 
only over `data` (the raw body), using `ShopifyApp.configuration.secret` — a single secret shared by the app across **all** shops that install it, not a per-shop secret.

`ShopifyApp::WebhookVerification` uses this same body-only check, and separately exposes `shop_domain` by simply reading the `X-Shopify-Shop-Domain` request header, which is never included in the HMAC input: [2](#0-1) 

The built-in `WebhooksController` builds `ShopifyAPI::Webhooks::Request` from `raw_body` and `headers`, and dispatches processing/jobs keyed off the shop domain taken from those headers: [3](#0-2) 

The gem's own documentation recommends the identical unsafe pattern for custom webhook controllers — pass the header-derived `shop_domain` straight into a job alongside the (HMAC-verified-but-shop-unbound) body: [4](#0-3) 

This is structurally the same bug as the Across Protocol report: a single verification artifact (the `slowRelayRoot` / here, the body HMAC computed with one shared secret) is valid across every tenant (spoke chain / shop), and the consuming component does not check that the artifact is scoped to the specific tenant it is being applied to (destination chain ID / shop domain). In Across, the Spoke Pool trusted `destinationChainId` implicitly instead of checking it against the executing chain; here, the app trusts the `X-Shopify-Shop-Domain` header implicitly instead of it being part of what's cryptographically verified.

By contrast, other verification paths in this same codebase correctly bind context into the signature or into an authenticated value:
- `AppProxyVerification` includes `shop` as part of the signed query string itself: [5](#0-4) 
- `TokenExchange` explicitly cross-checks the authenticated shop (from the verified ID token) against the requested shop and rejects mismatches: [6](#0-5) 

Webhook verification has no equivalent binding/consistency check between the signed body and the claimed shop.

### Impact Explanation
Because the API/webhook secret is app-wide (shared across every shop that installs the app) rather than per-shop, and only the body is signed, an attacker who controls a legitimate installation of the app (i.e., installs it on their own store) can obtain a genuinely Shopify-signed `(body, HMAC)` pair for a webhook topic whose body content they influence (e.g., `products/update`, `orders/create` fields the merchant controls). They can then replay that exact body+HMAC to the app's webhook endpoint while spoofing the `X-Shopify-Shop-Domain` header to name an unrelated victim shop that also has the app installed. Because verification never checks that the signed body "belongs" to the claimed shop, the request passes `verify_request` and is processed as if it originated from the victim shop — leading to cross-shop data injection/corruption in the app's local models (jobs are dispatched with `shop_domain: <attacker-chosen victim>` per the documented pattern and `WebhooksController`/`WebhooksManager` design).

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the app on at least one shop (a normal, permitted, unprivileged action for any merchant) and be able to send a raw HTTP POST to the app's public webhook endpoint with a modified header — no secret knowledge, no privileged access, and no interaction with the victim is required. The webhook endpoint is unauthenticated by design (that's the point of HMAC verification), and the flaw is baked into the shared verification helper (`PayloadVerification`/`WebhookVerification`) used by every generated and documented webhook controller in the gem, so it affects any app built with the default gem guidance.

### Recommendation
Do not treat the `X-Shopify-Shop-Domain` header as trusted merely because the body HMAC is valid. At minimum:
- Cross-check the header-derived shop domain against an independently trusted source (e.g., confirm a session/shop record exists and that the webhook's resource actually belongs to that shop before writing/mutating data), rather than trusting the header value directly for tenant routing.
- Where the underlying Shopify webhook delivery mechanism supports it, prefer verification flows that cryptographically bind the shop domain into what is verified (e.g., via `ShopifyAPI::Webhooks::Registry` validation utilities that tie topic/shop/id together) instead of the bespoke `PayloadVerification#hmac_valid?` that only covers the raw body.
- Document this constraint prominently for consumers of `ShopifyApp::WebhookVerification#shop_domain`, warning that it is not authenticated and must not be used for tenant-scoped writes without additional verification — analogous to the existing `EnsureInstalled`/`requested_shopify_domain` warnings already present elsewhere in the docs.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Attacker triggers a webhook whose body they can influence (e.g., updates a product to embed attacker-chosen values), and captures the real Shopify-delivered POST, including `X-Shopify-Hmac-Sha256` and raw body.
3. Attacker resends the identical body and HMAC header to the app's `/webhooks/:type` endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `WebhookVerification#verify_request` computes `hmac_valid?(request.raw_post)` — unchanged body ⇒ HMAC still valid ⇒ request passes.
5. `WebhooksController`/custom controller reads `shop_domain` from the (attacker-controlled) header and queues/executes the job as if the payload came from `victim.myshopify.com`, writing attacker-influenced data under the victim shop's identity.

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

```ruby
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
```
