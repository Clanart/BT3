### Title
Submodule `file://` protocol allowance in checkout can be used to read files outside the repository - (File: `app/src/lib/git/submodule.ts`)

### Summary
GitHub Desktop's submodule update path contains an `allowFileProtocol` flag that, when enabled, passes `-c protocol.file.allow=always` to `git submodule update --init --recursive`. This disables Git's own protection (`protocol.file.allow=user`) against submodules whose URL uses the `file://` scheme — the exact protection class that CVE-2022-39253 introduced upstream to stop malicious repositories from using submodule entries to read arbitrary local files during clone/checkout. The broken invariant is analogous to the HackerOne report: a value the attacker fully controls (here, the `.gitmodules` submodule URL committed inside a repository the user clones/checks out) is trusted and fed into an operation (`git submodule update`) that can read/copy content from wherever that URL points, without Desktop verifying the target is safe.

### Finding Description [1](#0-0)  `updateSubmodulesAfterOperation` accepts an `allowFileProtocol` boolean and, when true, prepends `-c protocol.file.allow=always` to the `submodule update --init --recursive` invocation, which is otherwise governed by Git's own default of restricting `file://` submodule URLs. [2](#0-1)  and [3](#0-2)  `checkoutBranch`/`checkoutCommit` both accept an `allowFileProtocol` parameter (default `false`) that is forwarded straight into `updateSubmodulesAfterOperation`.

If a caller ever sets `allowFileProtocol: true` for a checkout/pull operation on an attacker-supplied repository (e.g., checking out a branch/PR from an untrusted fork, or checking out a submodule reference the attacker pushed), an attacker-crafted `.gitmodules` entry with a `file://` URL pointing at a sensitive absolute path on the victim's machine (e.g. `file:///C:/Users/victim/.ssh` or `file:///home/victim/.aws`) would be cloned into the submodule's checkout directory inside the repository working tree, effectively copying files from outside the repo into a location the user can then view, commit, or exfiltrate via the UI.

### Impact Explanation
This matches the "file read outside the repo" and "silent corruption of what the user commits" impact categories: content from an attacker-chosen local path could be materialized inside the repository. Combined with GitHub Desktop's UI (which shows working directory changes and lets users commit/push), this could exfiltrate local secrets if the resulting files are committed and pushed to a remote the attacker also has access to (e.g., a fork PR flow).

### Likelihood Explanation
Uncertain/low-to-unproven. `grep` across the codebase found `allowFileProtocol` referenced only in `app/src/lib/git/checkout.ts` and `app/src/lib/git/submodule.ts` — every call to `checkoutBranch`/`checkoutCommit` that I could find in this pass appears to rely on the default value (`false`), meaning `protocol.file.allow=always` may never actually be enabled at any real call site I was able to locate. I could not, within this session, enumerate every caller of `checkoutBranch`/`checkoutCommit` (e.g., inside `app-store.ts` or dispatcher code) to confirm whether any UI-driven flow explicitly opts into `allowFileProtocol: true`. This is the key open question that determines whether this is actually reachable by an attacker-controlled repository today, or whether it is dead/defensive code that is never triggered.

### Recommendation
- Confirm via full grep/read of `app/src/lib/stores/app-store.ts` and related dispatcher code whether any code path passes `allowFileProtocol: true` for a checkout/pull triggered on a repository whose submodule configuration is attacker-influenced (forked/cloned/PR-sourced repos).
- If such a path exists, remove or gate `protocol.file.allow=always` so it can never be enabled for untrusted repositories, and rely on Git's default `protocol.file.allow=user` (or `deny`) semantics instead.
- If no such path exists, this should be treated as unreachable/defensive code rather than an exploitable vulnerability.

### Proof of Concept
Not independently verified end-to-end due to inability to confirm a reachable caller passing `allowFileProtocol: true`. Conceptual PoC, pending confirmation of a reachable call site:
1. Attacker creates/forks a repository with a `.gitmodules` entry: `url = file:///home/victim/.ssh`.
2. Victim opens/clones this repository in GitHub Desktop and checks out the branch/commit containing this submodule entry via a code path that sets `allowFileProtocol: true`.
3. `git -c protocol.file.allow=always submodule update --init --recursive` is executed, copying the contents of `/home/victim/.ssh` into the submodule's working-tree path inside the cloned repository.
4. The victim's SSH keys now appear as trackable files inside the repository, which the user could inadvertently commit/push.

Given the reachability of step 2 could not be confirmed with the tools available in this session, this should be verified by a follow-up code review of all `checkoutBranch`/`checkoutCommit` callers before treating this as a confirmed, exploitable finding rather than a latent risk.

```typescript
export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  // we return `true` here so `GitStore.performFailableGitOperation`
  // will return _something_ differentiable from `undefined` if this succeeds
  return true
```
