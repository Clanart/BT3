### Title
Tampered `ReceivedOutput` fields create unspendable credited funds - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
Medium-severity parameter-tampering analog: `ReceivedOutput::read` accepts the key offset, transaction output, and outpoint as three unrelated attacker-controlled fields without proving that the outpoint exists or that the output was produced by `Scanner`. [1](#0-0) 

### Finding Description
`ReceivedOutput::read` deserializes `offset`, `TxOut`, and `OutPoint` directly, while the trusted construction path in `Scanner::scan_transaction` normally derives the outpoint from a real scanned transaction and associates it with a registered script/offset. [1](#0-0) [2](#0-1) 

`SignableTransaction::new` then trusts the serialized `TxOut` value and outpoint when calculating spendable input value and constructing the transaction inputs. [3](#0-2) 

The later signing check only verifies that `group_key + offset·G` produces the supplied output's script; it does not verify that the supplied outpoint references that output on the blockchain. [4](#0-3) 

### Impact Explanation
An attacker who can tamper with bytes passed to `ReceivedOutput::read` can report an arbitrary Bitcoin amount as received by pairing the wallet's valid script with a nonexistent or unrelated outpoint. [5](#0-4) 

The forged object can pass `SignableTransaction` construction and `multisig` key matching, but the resulting transaction is unspendable because its claimed prevout does not exist or does not contain the committed `TxOut`. [3](#0-2) [6](#0-5) 

### Likelihood Explanation
The attack requires write access to a serialized `ReceivedOutput` consumed by the wallet, which is a narrower precondition than compromising signing keys but still lets public or lower-privileged input manipulate a security-critical composite object. [1](#0-0) 

No discrete-log knowledge is needed for the base-key case because the attacker can use `offset = 0` with the wallet's ordinary Taproot script. [7](#0-6) 

### Recommendation
Authenticate serialized `ReceivedOutput`s or reconstruct them only through `Scanner` results and a blockchain-backed UTXO lookup. [2](#0-1) 

Before accounting or signing, verify that `outpoint` resolves on-chain to exactly the serialized `TxOut`, including amount and script, and that `offset` was a registered offset for the expected wallet key. [4](#0-3) 

### Proof of Concept
```rust
use bitcoin::{
  hashes::Hash,
  consensus::Encodable,
  Amount, OutPoint, TxOut, Txid,
};
use k256::Scalar;
use bitcoin_serai::wallet::{p2tr_script_buf, ReceivedOutput, SignableTransaction};

// wallet_key is an even Taproot group key already handled by this wallet.
let wallet_script = p2tr_script_buf(wallet_key).unwrap();

let mut forged_bytes = Vec::new();
forged_bytes.extend(Scalar::ZERO.to_bytes());

// Claim the selected outpoint paid 1 BTC to this wallet.
TxOut {
  value: Amount::from_sat(100_000_000),
  script_pubkey: wallet_script,
}
.consensus_encode(&mut forged_bytes)
.unwrap();

// Point to an outpoint that does not contain that output.
OutPoint {
  txid: Txid::from_byte_array([0; 32]),
  vout: 0,
}
.consensus_encode(&mut forged_bytes)
.unwrap();

let forged = ReceivedOutput::read(&mut forged_bytes.as_slice()).unwrap();
assert_eq!(forged.value(), 100_000_000);

// The fake input is accepted as funds.
let tx = SignableTransaction::new(
  vec![forged],
  &[(destination_script, 546)],
  None,
  None,
  1,
).unwrap();

// Offset zero still satisfies the wallet-key/script relationship.
assert!(tx.multisig(&threshold_keys).is_some());
```
