### Title
Single Stuck Payout Permanently Halts `PayoutCheckerTask`, Locking Operator Collateral and Blocking All Subsequent Reimbursements - (`core/src/task/payout_checker.rs`)

---

### Summary

`PayoutCheckerTask` always dequeues the **lowest-index** unhandled payout (`ORDER BY w.idx ASC LIMIT 1`). If processing that payout returns any error, the error propagates through the `WithDelay → CancelableTask → CancelableLoop` chain and terminates the background task permanently. Because `PayoutCheckerTask` does not implement `RecoverableTask` and is not wrapped with `into_buffered_errors`, a single failure stops the task with no automatic restart. On manual restart the same lowest-index payout is fetched again, causing the same failure. All higher-index payouts are never processed, the operator's kickoff transactions are never queued, and the operator's collateral UTXO chain is permanently frozen.

---

### Finding Description

**Root cause — FIFO queue with no skip-on-error:**

`get_first_unhandled_payout_by_operator_xonly_pk` always returns the single lowest-index unhandled payout:

```sql
SELECT w.idx, w.move_to_vault_txid, w.payout_tx_blockhash
FROM withdrawals w
WHERE w.payout_txid IS NOT NULL
   AND w.is_payout_handled = FALSE
   AND w.payout_payer_operator_xonly_pk = $1
   ORDER BY w.idx ASC
LIMIT 1
``` [1](#0-0) 

`PayoutCheckerTask::run_once` fetches this record and immediately returns `Err` if the deposit data is absent:

```rust
if deposit_data.is_none() {
    return Err(eyre::eyre!("Fronted withdrawal for move tx {move_to_vault_txid} found, but the signatures for the deposit are not found in the db.").into());
}
``` [2](#0-1) 

Additional failure points inside the same `run_once` call that produce the same outcome:
- `handle_finalized_payout` fails (e.g., no available kickoff connector, round-index mismatch without automation, DB error). [3](#0-2) 
- `get_block_info_from_hash` returns `None` (payout block not yet in the syncer DB). [4](#0-3) 
- `fetch_validate_and_store_lcp` fails (Citrea RPC unavailable). [5](#0-4) 

**Error propagation — task terminates on first error:**

The task is launched as `PayoutCheckerTask::new(...).with_delay(PAYOUT_CHECKER_POLL_DELAY)` and then wrapped by `ensure_task_looping` into a `CancelableLoop`: [6](#0-5) 

`WithDelay::run_once` propagates errors via `?`:
```rust
let did_work = self.inner.run_once().await?.into();
``` [7](#0-6) 

`CancelableLoop::run_once` propagates errors and exits the loop:
```rust
Err(e) => return Err(e),
``` [8](#0-7) 

`BackgroundTaskManager::monitor_spawned_task` catches the terminated task and marks it `NotRunning` — it does **not** restart it: [9](#0-8) 

Unlike `TxSenderTask`, which uses `into_buffered_errors(10, 1, ...)` and implements `RecoverableTask`, `PayoutCheckerTask` has no error-buffering or recovery wrapper. A single `Err` from `run_once` is fatal to the task. [10](#0-9) 

**Downstream blockage — manual path also blocked:**

`get_reimbursement_txs` (the manual fallback) calls `validate_payer_is_operator`, which requires `kickoff_txid` to be non-NULL in the `withdrawals` table: [11](#0-10) 

`kickoff_txid` is only written by `mark_payout_handled`, which is called at the end of a successful `PayoutCheckerTask` run: [12](#0-11) 

Because the stuck payout is never marked handled, all higher-index deposits have `kickoff_txid = NULL`, and `get_reimbursement_txs` returns an error for every one of them. Both the automated and manual reimbursement paths are blocked.

---

### Impact Explanation

The operator has already paid BTC to users on Bitcoin (fronted withdrawals). The `PayoutCheckerTask` is the sole mechanism that:
1. Assigns a kickoff connector to each deposit.
2. Queues the kickoff transaction (and all downstream reimbursement transactions) into `TxSender`.
3. Advances the round when needed.

With the task permanently stopped on payout index N, every deposit at index N+1, N+2, … never receives a kickoff connector, no kickoff transaction is ever broadcast, and the operator's collateral UTXO chain (locked across all rounds) cannot be unwound. The operator loses both the BTC already paid to users and the collateral locked in the round/ready-to-reimburse UTXO chain. [13](#0-12) 

---

### Likelihood Explanation

Several realistic conditions trigger the stuck payout:

1. **Missing deposit data** — if the operator's DB is partially restored from backup, or if a deposit was finalized during a DB migration window, `get_deposit_data_with_move_tx` returns `None` for that `move_to_vault_txid`.
2. **No available kickoff connector** — if all connectors in the current round are already consumed and the round has not been advanced (e.g., automation disabled or `end_round` failed), `get_unused_and_signed_kickoff_connector` returns `None` and `handle_finalized_payout` errors.
3. **Citrea RPC outage** — `fetch_validate_and_store_lcp` fails persistently; the task stops and the same payout is retried on every manual restart.

None of these require adversarial action; they are operational conditions that can arise in production.

---

### Recommendation

1. **Skip-and-log on per-payout errors.** Catch errors inside `run_once` at the individual payout level, log them, and advance to the next payout index rather than returning `Err`. A counter of consecutive failures per payout index can be stored in the DB; after a threshold the operator is alerted.

2. **Wrap `PayoutCheckerTask` with `into_buffered_errors`.** Implement `RecoverableTask` for `PayoutCheckerTask` (analogous to `TxSenderTask`) so transient errors are buffered and the task is not terminated on the first failure.

3. **Separate the LCP fetch from the critical path.** `fetch_validate_and_store_lcp` is needed only if a challenge occurs later. Move it to a separate, non-blocking task so a Citrea RPC failure does not block kickoff queuing.

---

### Proof of Concept

1. Operator fronts two withdrawals: payout index 0 (deposit A) and payout index 1 (deposit B).
2. Deposit A's data is absent from the operator's DB (e.g., after a partial DB restore). The `withdrawals` table has `payout_txid` set for index 0 but `get_deposit_data_with_move_tx` returns `None`.
3. `PayoutCheckerTask::run_once` fetches index 0 (lowest), calls `get_deposit_data_with_move_tx`, gets `None`, returns `Err("Fronted withdrawal for move tx … found, but the signatures for the deposit are not found in the db.")`.
4. Error propagates: `WithDelay` → `CancelableTask` → `CancelableLoop` exits with `Err`. The spawned task terminates. `BackgroundTaskManager` marks `PayoutChecker` as `NotRunning`.
5. Deposit B (index 1) is never processed. Its `kickoff_txid` remains `NULL`.
6. Operator calls `GetReimbursementTxs` for deposit B → `validate_payer_is_operator` finds `kickoff_txid = NULL` → returns error.
7. Operator calls `RestartBackgroundTasks` → task restarts → fetches index 0 again → same error → task stops again.
8. Operator's collateral locked in the round UTXO chain is permanently frozen; the BTC fronted for deposit B is unrecoverable through the bridge protocol.
