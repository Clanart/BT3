### Title
`SignableTransaction` fee/vsize estimation omits the `OP_RETURN` data output, underpaying the declared fee rate for every transaction carrying data — (`networks/bitcoin/src/wallet/send.rs`)

### Summary
`SignableTransaction::new` computes the transaction weight/vbytes — and therefore `needed_fee` — via `calculate_weight_vbytes`, which builds its template transaction only from `inputs` and `payments`. The `OP_RETURN` output appended for `data` (up to 80 bytes) is pushed into the real `tx_outs` but is never included in the weight template, so the signed transaction is larger than estimated and realizes a lower effective fee rate than `fee_per_vbyte`. This is reachable by an unprivileged user whenever they cause Serai to construct a Bitcoin transaction that carries data (e.g., a burn/withdrawal with an `OutInstruction` payload).

### Finding Description
In `SignableTransaction::new`, the data payload is appended to `tx_outs` before the size/fee calculation:

```rust
// networks/bitcoin/src/wallet/send.rs:194-202
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` constructs its template `Transaction` with `output` built **only** from `payments` (plus an optional change output):

```rust
// networks/bitcoin/src/wallet/send.rs:85-99
output: payments
  .iter()
  .map(|payment| TxOut {
    value: Amount::from_sat(payment.1),
    script_pubkey: payment.0.clone(),
  })
  .collect(),
```

The `OP_RETURN` output (`8`-byte value + compact-size length + `OP_RETURN` opcode + push opcode + up to `80` bytes of data ≈ up to ~92 bytes/~92 vbytes) is absent from the template. The same omission applies to the second call with `Some(&change)` used when change is present (`send.rs:225-227`). Consequently:

- `needed_fee = fee_per_vbyte * vbytes` is computed on a vsize that is up to ~90 vbytes too small.
- The actual signed transaction's fee (`fee()` = `sum(inputs) - sum(outputs)`) equals `needed_fee`, so its *real* fee rate is `needed_fee / actual_vsize < fee_per_vbyte`.
- The minimum-relay-fee guard compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same undersized `vbytes`, so it does not catch the shortfall — a transaction constructed at exactly the minimum relay fee rate will actually fall **below** it once the data output is included.

The change amount (`input_sat - payment_sat - fee_with_change`) remains internally consistent, so this is purely a fee-rate underestimation, not an accounting error.

### Impact Explanation
Any Serai-constructed Bitcoin transaction that carries `data` pays a lower fee rate than the operator/protocol requested. When `fee_per_vbyte` is at or near the mempool minimum, the signed transaction can be rejected by Bitcoin nodes' relay policy (`min relay fee not met`) or languish unconfirmed. Because the produced transaction is a fully-signed, threshold-authorized spend that pins its inputs, the affected outputs are effectively unspendable through this path until a replacement transaction is constructed and re-signed — a denial-of-service on fund movement for data-carrying withdrawals/burns. The magnitude scales with `fee_per_vbyte` and the data length (up to 80 bytes ≈ ~90 vbytes of uncompensated size).

### Likelihood Explanation
Reachable by an unprivileged party: the `data` field is populated for protocol-driven transactions (e.g., instructions attached to burns), which users trigger through normal Serai operations — no validator, node, or collusion assumptions are needed. Every such transaction deterministically underpays relative to its declared rate; whether it is rejected by the mempool depends on how close `fee_per_vbyte` is to the prevailing minimum, so the impact is intermittent rather than guaranteed — consistent with Medium severity. The bug is a straightforward template omission, not dependent on edge-case inputs.

### Recommendation
Include the `OP_RETURN` data output in the template used by `calculate_weight_vbytes`. Concretely, pass the constructed `tx_outs` (or the `data` length) into `calculate_weight_vbytes` so the estimated weight/vbytes match the final transaction, both for the no-change and change paths. Equivalently, build the full output list first (payments + `OP_RETURN` + optional change) and compute weight from it, then derive `needed_fee` and the change value from that accurate vsize.

### Proof of Concept
1. Construct inputs/payments such that `SignableTransaction::new` is called with `data = Some(vec![0u8; 80])` and `fee_per_vbyte` equal to the minimum relay rate (`DEFAULT_MIN_RELAY_TX_FEE / 1000` sat/vbyte).
2. `calculate_weight_vbytes` builds a template containing only the payment outputs; `vbytes` excludes the ~92-byte `OP_RETURN` output that `new` pushes into `tx_outs` at `send.rs:194-202`.
3. The min-fee check at `send.rs:211` passes because it uses the undersized `vbytes`.
4. After signing via `TransactionMachine`/`TransactionSignMachine` (`send.rs:355-398`), the broadcast transaction contains the extra `OP_RETURN` output; its actual vsize is ~90 bytes larger than `vbytes`, so `fee() / actual_vsize` falls below the minimum relay fee rate and Bitcoin Core rejects it from the mempool despite `needed_fee` nominally satisfying the check.
