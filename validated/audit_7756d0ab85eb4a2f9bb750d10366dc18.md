### Title
Attacker can capture queued rewards meant for departed stakers by timing withdraw/redeposit around `totalStaked()==0` in `_provisionReward` - (File: rewards/BaseRewardPool.sol)

### Summary
`BaseRewardPool._provisionReward` routes any incoming reward into `rewardInfo.queuedRewards` whenever `totalStaked()==0`, with no snapshot of which accounts were owed that reward. Because `totalStaked()` is a live external read of `IERC20(stakingToken).balanceOf(operator)` (via `IMasterMagpie.stakingInfo`) that any staker fully controls by withdrawing, and because reward distribution of `queuedRewards` is triggered lazily by whoever calls `_provisionReward` next when stake is nonzero, an unprivileged attacker who is the last/sole staker can withdraw to force `totalStaked()==0`, let a manager's routine `queueNewRewards` land, then redeposit a trivial amount and self-trigger distribution via the public `donateRewards` function to sweep the entire queued reward.

### Finding Description
`_provisionReward` (rewards/BaseRewardPool.sol:297-320):
```solidity
if (this.totalStaked() == 0) {
    rewardInfo.queuedRewards += _amountReward;
} else {
    if (rewardInfo.queuedRewards > 0) {
        _amountReward += rewardInfo.queuedRewards;
        rewardInfo.queuedRewards = 0;
    }
    rewardInfo.rewardPerTokenStored += (_amountReward * 10**stakingDecimals()) / this.totalStaked();
}
``` [1](#0-0) 

`totalStaked()` and `balanceOf()` read live state from the operator (MasterMagpie), fully controllable by a staker's own withdraw/deposit calls: [2](#0-1) 

`donateRewards` is a public, unprivileged entry point into `_provisionReward` requiring no special role, only that the token is already registered as a reward token: [3](#0-2) 

Exploit flow (attacker is the sole/last staker in the pool, or times around the last other staker leaving):
1. Attacker sees (or times) a manager's routine `queueNewRewards` transaction in the mempool, or simply is the sole staker.
2. Attacker withdraws all of their stake from MasterMagpie, driving `totalStaked()` to exactly 0.
3. Manager's `queueNewRewards(_amountReward, _rewardToken)` lands; since `totalStaked()==0`, the entire `_amountReward` — which was meant to reward whichever accounts were staked at that moment (the departed stakers) — is added to `rewardInfo.queuedRewards` instead of being credited via `rewardPerTokenStored` to anyone.
4. Attacker redeposits a trivial amount (e.g., 1 wei) of `stakingToken`, becoming the pool's sole staker again.
5. Attacker calls the public `donateRewards(0, _rewardToken)` (or waits for the next legitimate `queueNewRewards`). Since `totalStaked() > 0` now, `_provisionReward` folds the entirety of `rewardInfo.queuedRewards` into `_amountReward` and distributes it via `rewardPerTokenStored` based on the current tiny `totalStaked()`, crediting it almost entirely to the attacker's 1-wei stake.
6. Attacker calls `getReward` (via MasterMagpie) to claim the full queued reward, then withdraws their 1 wei.

No existing check prevents this: there is no time-locking, no snapshot of eligible recipients for `queuedRewards`, and `donateRewards` has no `onlyManager` gate that would prevent the attacker from self-triggering the flush at their chosen moment while holding a negligible/sole stake. `updateReward`/`_updateFor` only update the caller's own accounted earnings using the already-corrupted `rewardPerTokenStored`; they do not protect against this timing attack.

### Impact Explanation
This is a direct theft of unclaimed yield: reward tokens intended for stakers present at reward-queue time are instead diverted entirely to an attacker who re-enters the pool with a dust stake after the reward was queued. This matches Immunefi's "theft of unclaimed yield" / "direct theft of user funds" impact class. The magnitude equals the full `_amountReward` queued in the affected `queueNewRewards`/`donateRewards` call while `totalStaked()==0`, i.e., potentially the entire reward distribution for that period, taken from legitimate departed stakers.

### Likelihood Explanation
Feasibility depends on the attacker being able to drive `totalStaked()` to exactly 0 for the pool (trivial if they are the sole staker, or achievable by watching the mempool for a manager's `queueNewRewards`/`donateRewards` transaction and front-running it with a full withdraw, then back-running with a small redeposit plus a self-call to `donateRewards(0, token)`). This requires only ordinary EOA capabilities (withdraw, deposit, call a public function) — no privileged role — and is repeatable every time this timing window can be created, especially attractive on smaller/less-used reward pools where a single account holds all (or nearly all) of the stake at any given time.

### Recommendation
Avoid lazily flushing `queuedRewards` to whoever happens to be staked at the next `_provisionReward` call. Options: (1) disallow `queueNewRewards`/`donateRewards` from succeeding (or require reverting/holding in escrow) when `totalStaked()==0`, refunding or rejecting the deposit instead of silently queuing it against future arbitrary stakers; (2) require a minimum bonding/cooldown period after (re)staking before a user's balance is eligible to receive previously queued rewards, so a dust redeposit right after a reward-queue event cannot immediately capture it; (3) make `donateRewards` restricted or rate-limited so an attacker cannot self-trigger the flush at an advantageous moment right after redepositing.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, `BaseRewardPool`, and a reward ERC20; register attacker as sole staker with stake `S`.
2. Attacker calls `withdraw(S)` on MasterMagpie, driving `BaseRewardPool.totalStaked()` to 0.
3. As a manager (simulating normal operation, not malicious intent), call `queueNewRewards(amountReward, rewardToken)`; assert `rewards[rewardToken].queuedRewards == amountReward` and `rewardPerTokenStored` unchanged.
4. Attacker calls `deposit(1)` (1 wei stake) via MasterMagpie, then calls `donateRewards(0, rewardToken)`.
5. Assert `rewards[rewardToken].queuedRewards == 0` and `rewardPerTokenStored` increased proportionally to `amountReward / 1`.
6. Attacker calls `getReward(attacker, attacker)` via MasterMagpie; assert attacker's received `rewardToken` balance == `amountReward` (minus negligible rounding), i.e., 100% of the donation intended for the previously staked balance `S`.
7. Attacker withdraws the 1 wei stake, completing the extraction with negligible capital at risk.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
