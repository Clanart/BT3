### Title
Missing identity/zero validation of verification shares lets `ThresholdKeys::read` derive a public-valued group key - (File: crypto/dkg/src/lib.rs)

### Summary
The analog of "no zero-address validation" is the absence of identity/zero validation on group elements and scalars accepted as key material. FROST's `Curve::read_G` explicitly rejects the identity point (crypto/frost/src/curve/mod.rs:123-131), and `Participant::new`/`ThresholdParams::new` reject zero indexes (crypto/dkg/src/lib.rs:29-35, 166-176). However, `ThresholdKeys::read` deserializes each verification share with the base `Ciphersuite::read_G`, which only enforces canonical encoding and permits the identity point, and `ThresholdKeys::new` performs no identity check on `verification_shares`, no non-zero check on `secret_share`, and no consistency check that `generator() * secret_share == verification_shares[i]` (crypto/dkg/src/lib.rs:618-631, 349-391). The group key is then blindly computed as `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` (crypto/dkg/src/lib.rs:376-378).

### Finding Description
`ThresholdKeys::read` (crypto/dkg/src/lib.rs:574-632) accepts untrusted bytes encoding `t`, `n`, `i`, the interpolation variant, the secret share, and `n` verification shares. `Ciphersuite::read_G` (crypto/ciphersuite/src/lib.rs:91-101) rejects only non-canonical encodings, not identity. `ThresholdKeys::new` validates only participant indexes, counts, and interpolation applicability — it never checks that a verification share is non-identity, that the secret share is non-zero, or that the secret share matches its claimed verification share. An attacker can therefore craft a serialized `ThresholdKeys` blob where every verification share is the identity point. The derived `group_key` is then `sum(identity * factor) = identity`, i.e. the point whose discrete logarithm is 0 — a secret known to everyone. More generally, arbitrary mismatched verification shares let an attacker pin the reported `group_key()` to any point they choose while the stored `secret_share` does not correspond to it.

The same gap exists in `musig()` (crypto/dkg/musig/src/lib.rs:46-63): `check_keys` rejects duplicates and empty lists but accepts identity public keys, letting a party register a key with the publicly known discrete log 0.

### Impact Explanation
If a node consumes `ThresholdKeys::read` output for attacker-influenced bytes (e.g., restoring keys from a store another party can write, or receiving serialized keys), the resulting `group_key` can be the identity point or another key whose discrete log the attacker knows. Funds addressed to that group key (e.g., a Bitcoin output via bitcoin-serai) are spendable by the attacker while the node believes they are threshold-controlled — "funds reported received that are not actually secured by the multisig." Additionally, an inconsistent `secret_share` vs. `verification_shares[i]` produces shares that fail verification, hitting the `InternalError("everyone had a valid share yet the signature was still invalid")` path the code itself attributes to "a semantically invalid FrostKeys" (crypto/frost/src/sign.rs:491-494), confirming this state is reachable but unhandled.

### Likelihood Explanation
Requires the attacker to influence the bytes passed to `ThresholdKeys::read` (or the `keys` list passed to `musig`). That is a real but constrained channel — the deserialization API is explicitly part of the trusted-untrusted boundary — so likelihood is moderate; severity Medium is consistent with the source report's classification.

### Recommendation
- In `ThresholdKeys::new` (crypto/dkg/src/lib.rs:349), reject identity verification shares and verify `C::generator() * secret_share == verification_shares[&params.i()]` after the scalar/offset transform.
- In `musig()`/`check_keys` (crypto/dkg/musig/src/lib.rs:46), reject identity points in `keys`.
- Optionally have `Ciphersuite::read_G` take a `nonzero` flag, mirroring how `Curve::read_G` already rejects identity.

### Proof of Concept
```rust
// Crypto/dkg: deserialize a ThresholdKeys whose group_key is the identity.
// For C = some Curve impl, n = t = 1, i = 1, Lagrange interpolation:
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes()); // t
buf.extend(1u16.to_le_bytes()); // n
buf.extend(1u16.to_le_bytes()); // i
buf.push(1);                    // Interpolation::Lagrange
buf.extend(C::F::ZERO.to_repr().as_ref());       // secret_share = 0
buf.extend(C::G::identity().to_bytes().as_ref()); // verification_shares[1] = identity

let keys = ThresholdKeys::<C>::read(&mut &buf[..]).unwrap(); // succeeds today
assert!(bool::from(keys.group_key().is_identity()));         // group secret = 0, publicly known
```
Verification shares of `identity` and a `secret_share` of `ZERO` pass every check in `ThresholdKeys::new`; the derived group key is the identity, corresponding to the publicly known discrete logarithm 0.
