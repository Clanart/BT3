### Title
Unbounded slice indexing in `ioutils.IsGzip`/`IsWasm` allows out-of-bounds-read panic on attacker-supplied WASM bytecode - (File: `sei-wasmd/x/wasm/ioutils/utils.go`)

### Summary
`ioutils.IsGzip` and `ioutils.IsWasm` slice their `input` argument (`input[:3]` and `input[:4]`) without first checking `len(input)`. Any caller that invokes these helpers on attacker-controlled byte slices shorter than the magic-byte length will trigger a Go runtime panic (`slice bounds out of range`), the same missing-bounds-check root cause as the Ollama `gguf.go` out-of-bounds read that caused a DoS crash.

### Finding Description

Neither function validates `len(input)` before slicing, so a 0–3 byte (`IsGzip`) or 0–4 byte (`IsWasm`) input will panic. These helpers are consumed in multiple places in the codebase — I confirmed direct references from `x/evm/keeper/msg_server.go` (the EVM message-server handling wasm deployment via EVM transactions) and `precompiles/wasmd/wasmd.go` (the CosmWasm precompile reachable from any EVM contract call) — both of which accept attacker-supplied byte arrays as part of a submitted transaction or contract call. Legitimate on-chain code-storage (`Keeper.create` via `ioutils.Uncompress`) appears to be guarded separately, but I was not able to fully verify, within the available tool budget, whether the `msg_server.go`/precompile call sites route through the same guarded `Uncompress` wrapper or call `IsGzip`/`IsWasm` directly on unguarded, potentially very-short attacker input.

### Impact Explanation
If `IsGzip`/`IsWasm` are reached with a byte slice shorter than 3/4 bytes from a code path that is not wrapped in a `recover()` (e.g., ante-handler-adjacent logic, an EVM precompile that lacks the `defer recover()` pattern present in some other precompiles such as `p256`), the panic can escape normal Cosmos SDK / EVM panic-recovery boundaries and crash the node process, matching the "crash of default-configuration RPC nodes" impact bar. If instead the panic is caught by an existing `recover()` (as `baseapp.runTx` and some EVM precompiles do), the practical impact is downgraded to a single failed transaction rather than a full node crash.

### Likelihood Explanation
Reaching this code only requires submitting a `MsgStoreCode`-equivalent payload or precompile call with a WASM byte-code argument shorter than 4 bytes — trivially constructible by any unprivileged transaction sender or EVM contract caller. No special privileges are required.

### Recommendation
Add explicit length checks to `IsGzip` and `IsWasm` before slicing (e.g., `return len(input) >= 3 && bytes.Equal(input[:3], gzipIdent)` and the analogous 4-byte check for `IsWasm`), and audit every call site (`x/evm/keeper/msg_server.go`, `precompiles/wasmd/wasmd.go` and its legacy versions, CLI/REST tooling) to confirm none rely on unguarded direct calls to these helpers outside of `Uncompress`'s protective wrapper.

### Proof of Concept
Cannot be fully constructed without confirming the exact unguarded call path (whether `x/evm/keeper/msg_server.go` / `precompiles/wasmd/wasmd.go` call `IsWasm`/`IsGzip` directly on raw, un-length-checked user input outside of `Uncompress`, and whether that call site lacks a `recover()`). Conceptually: submit an EVM transaction invoking the wasmd precompile's store/deploy method with a `bytecode` argument of length 0–3 bytes; if the receiving code path calls `ioutils.IsWasm`/`IsGzip` on it directly, this triggers `index out of range` panic.
