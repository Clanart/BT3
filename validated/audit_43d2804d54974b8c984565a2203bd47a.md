## Analog identification

The Notional bug's core pattern is: **a security control that normally blocks a dangerous operation is deliberately disabled for a legitimate workflow, and an attacker-controlled input can exploit that disabled window to cause harm the user cannot avoid.** The closest verified GitHub-Desktop analog is Desktop's re-enabling of `protocol.file.allow=always` when updating submodules after a checkout, which unconditionally overrides Git's built-in `protocol.file.allow=user` hardening (the fix for CVE-2022-39253) and lets an attacker-controlled `.gitmodules` file in a fetched/checked-out repository make Git read arbitrary local files during `submodule update --init --recursive`.

### Title
Checkout re-enables `protocol.file.allow=always` for submodules, allowing a malicious repo's `.gitmodules` to read arbitrary local files during checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` conditionally prepends `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation that runs automatically after every branch/commit checkout. [1](#0-0) 
This flag is threaded down from `checkoutBranch`/`checkoutCommit` via an `allowFileProtocol` boolean parameter. [2](#0-1) [3](#0-2) 

### Finding Description
Git added `protocol.file.allow=user` as the default (disallowing `file://` submodule URLs during recursive operations) specifically to close CVE-2022-39253, where a malicious repository's `.gitmodules` could point a submodule at an arbitrary local path (e.g. `file:///home/user/.ssh` or a relative path escaping the repo via `../../..`) and have Git "clone" that local directory's contents into the checkout, disclosing file contents the victim never intended to share.

Desktop deliberately re-enables the disallowed behavior (`protocol.file.allow=always`) whenever `allowFileProtocol` is `true` in the submodule-update step that runs after checkout. [4](#0-3) 
Because `.gitmodules` is ordinary tracked content in the repository, an attacker who controls a repo (or a branch/PR head that Desktop fetches and checks out — e.g. via the `openRepositoryFromUrl`/`openBranchNameFromUrl` or PR-checkout flows in the dispatcher) fully controls the submodule `url=` values that Git will honor once this flag is set. [5](#0-4) 
The same `allowFileProtocol` flag is also used unconditionally in submodule fixtures/tests to add local submodules, confirming it is understood internally as "allow local/file submodule sources" rather than something scoped to a specific trusted context. [6](#0-5) 

Existing guards elsewhere in the app (e.g. `resolveWithin`/`isAbsolute` checks for the `filepath` deep-link parameter, or `isClonePathSensitive` for clone destinations) do not apply here — those protect a different data flow (the `filepath` query param and the top-level clone destination), not the `.gitmodules` `url=` field consumed by `git submodule update`. [7](#0-6) [8](#0-7) 
There is no equivalent allow-list or path-containment check around the submodule URLs themselves before `protocol.file.allow=always` is applied.

### Impact Explanation
If Desktop passes `allowFileProtocol=true` when checking out a branch/commit/PR originating from an untrusted, attacker-controlled repository (fork PR checkout, "Open in Desktop" deep link, or any fetched branch), the attacker's `.gitmodules` can direct Git to read arbitrary files from the victim's local filesystem into the resulting working tree as "submodule content." This is a direct file-read-outside-the-repo primitive with attacker control over both the source path and how the exfiltrated content is materialized in the checkout — which the victim may then unknowingly commit and push to a remote the attacker can also read, achieving credential/secret exfiltration. This matches the "file write/read outside the repo" and "silent corruption of what the user commits or pushes" categories.

### Likelihood Explanation
Likelihood depends on which call sites pass `true` for `allowFileProtocol`; I was not able to fully enumerate every caller within the available tool budget — `allowFileProtocol` usage appears in `app-store.ts` (8 references) and several UI components (branches container, stash dialogs, compare view, confirm-checkout-commit), but I could not confirm from the retrieved snippets which specific user-triggered flows (e.g., checking out a fork PR branch, or "Open in Desktop" branch checkout) set it to `true` versus leaving the safe default (`false`). This is the key uncertainty: if `allowFileProtocol` is only ever set `true` for locally-created/trusted repositories (e.g., a repo the user just created themselves), the exploitability is much lower; if it is set `true` for repositories/branches originating from untrusted third-party sources (forks, PRs, cloned URLs), the issue is directly exploitable with no unusual user action beyond a normal checkout.

### Recommendation
- Audit every call site that passes `allowFileProtocol={true}` to `checkoutBranch`/`checkoutCommit` and confirm none of them apply to branches/commits/PRs sourced from repositories or remotes not fully controlled by the local user.
- Prefer never re-enabling `protocol.file.allow=always` for content that originated from a remote/fork; if local submodules must be supported for a specific first-party workflow (e.g., internal repo creation with local test submodules), scope the override narrowly (e.g., only for repositories with no configured remote, or an explicit user opt-in) rather than through a boolean threaded generically through the checkout path.
- Alternatively, validate/sanitize `.gitmodules` submodule URLs (rejecting `file://`, absolute local paths, or paths that resolve outside the expected trust boundary) before invoking `submodule update --init --recursive` with the elevated allowance.

### Proof of Concept
Because the exact untrusted call sites for `allowFileProtocol=true` could not be confirmed from the retrieved code, a full end-to-end PoC cannot be certified without further investigation into `app/src/lib/stores/app-store.ts` and the specific dispatcher flows (fork PR checkout, "Open in Desktop" branch checkout) that call `checkoutBranch`/`checkoutCommit`. Conceptually, the PoC would be:
1. Attacker creates a public repository/fork with a `.gitmodules` entry such as `url = file:///Users/victim/.ssh` (or a relative path with `..` segments) for a submodule.
2. Victim opens the PR/branch/deep link in Desktop, triggering a checkout flow that calls `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true`. [9](#0-8) 
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, and Git materializes the contents of the local path into the submodule directory in the victim's working tree. [10](#0-9) 
4. Victim inspects/commits/pushes, potentially exfiltrating the local files to the attacker-controlled remote.

**This finding should be treated as tentative pending verification of the exact call sites that set `allowFileProtocol=true`**, since that determines whether the untrusted-input precondition required by the Valid Impact scope is actually met.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
