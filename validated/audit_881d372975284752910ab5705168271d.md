### Title
Unbounded attacker-controlled `u32` loop in `SchnorrAggregate::read` enables CPU/memory denial of service - (File: crypto/schnorr/src/aggregate.rs)

### Summary
CVE-2018-7327 class: a length/prefix field in attacker-controlled input is trusted to drive a deserialization loop without validation. In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::read` reads a little-endian `u32` and then loops that many times calling `C::read_G(reader)`, pushing each decoded point into a `Vec`. A 5-byte input declaring `0xffffffff` iterations forces up to ~4.3 billion `read_G` calls — each performing an elliptic-curve decompression and a canonicality re-encoding check — before an `UnexpectedEof` error is returned. This is the Serai analog of the Wireshark infinite-loop-via-unvalidated-length bug.

### Finding Description
In `crypto/schnorr/src/aggregate.rs` (lines 77–88):

```rust
pub fn read<R: Read>(reader: &mut R) -> io::Result<Self> {
  let mut len = [0; 4];
  reader.read_exact(&mut len)?;
  let mut Rs = vec![];
  for _ in 0 .. u32::from_le_bytes(len) {
    Rs.push(C::read_G(reader)?);
  }
  Ok(SchnorrAggregate { Rs, s: C::read_F(reader)? })
}
```

There is no bound check on `len`, and no "bytes remaining" sanity check. `C::read_G` in `crypto/ciphersuite/src/lib.rs` (lines 91–101) performs `read_exact` of a full point encoding plus `G::from_bytes` decompression and a canonicality comparison (`point.to_bytes() != encoding`) — non-trivial per-iteration work. If the reader is a file/socket that produces data slowly, or produces a trickle of bytes, the loop runs per-iteration curve operations for as many points as bytes are supplied; on an infinite/padded stream (e.g. a network peer streaming bytes, or `io::Read` over a socket) it spins without bounded total work. The same pattern — trusting an attacker-supplied count — is what the CVE fixed by validating property lengths.

In-scope reachability: `SchnorrSignature::read`/`SchnorrAggregate` deserialization is explicitly on the allowed untrusted-bytes surface. Any protocol path that accepts a serialized aggregate signature from an untrusted party (e.g. a submitted signature/cosign message parsed from bytes) exposes this.

A secondary instance of the same class exists in `processor/src/plan.rs` `Plan::read` (lines 183–194: two `u32` counts driving `N::Output::read`/`Payment::read` loops, each of which itself reads a `u32`-length `Vec` at lines 56 and 65), but `Plan` deserialization is processor-side coordinator input and lies outside the strict in-scope crate list; `SchnorrAggregate::read` in `crypto/schnorr` is the in-scope instance.

### Impact Explanation
Denial of service: an unprivileged party supplies a handful of bytes with a large `u32` count, forcing the victim to burn CPU on curve decompression (each `read_G` does field inversion/sqrt for point recovery on secp256k1/Ristretto) and/or allocate and push up to gigabytes of `C::G` elements if the stream continues to supply bytes. On a streaming reader this is unbounded in wall-clock time — the direct analog of the CVE's infinite loop. There is no secret leakage, but availability of the verifying/signing node is impacted while parsing a single message.

### Likelihood Explanation
Any code path that calls `SchnorrAggregate::read` (or a wrapper `read` that embeds it) on bytes obtained from an unauthenticated peer triggers this. The trigger requires only controlling the 4-byte prefix and optionally continuing to stream bytes; no valid cryptography is needed. Likelihood depends on whether aggregate signatures are read from unauthenticated channels in deployment; within the crypto library itself, the function is a public `pub fn` exposed for exactly that purpose.

### Recommendation
Bound the count before looping, consistent with how `coordinator/src/tributary/transaction.rs` validates `commitments_len * each_commitments_len` against `TRANSACTION_SIZE_LIMIT` (lines 283–290) and `p2p.rs` rejects `len > MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocation (lines 263–266). Concretely: enforce a protocol-level maximum aggregate size (e.g. `MAX_PARTICIPANTS`), and/or reject `len` larger than the remaining input size divided by the fixed point-encoding width (`len * <C::G as GroupEncoding>::Repr::default().as_ref().len()` bytes minimum).

### Proof of Concept
```rust
use ciphersuite::Ciphersuite;
use frost::curve::Secp256k1 as C;
use schnorr::aggregate::SchnorrAggregate;
use std::io::Read;

// A reader that never ends: simulates a malicious peer streaming bytes.
struct InfiniteZeros;
impl Read for InfiniteZeros {
  fn read(&mut self, buf: &mut [u8]) -> std::io::Result<usize> {
    buf.fill(0);
    Ok(buf.len())
  }
}

fn main() {
  // 4-byte length = u32::MAX, then an endless stream of bytes.
  let header = u32::MAX.to_le_bytes();
  let stream = InfiniteZeros;
  let mut reader = header.chain(stream); // std::io::Read::chain
  // This call will run ~4.3 billion iterations of read_G, each attempting
  // decompression, and will OOM growing Rs on valid encodings.
  let _ = SchnorrAggregate::<C>::read(&mut reader);
}
```

Against a `&[u8]` slice it still forces up to `len` decompression attempts bounded only by input exhaustion, and against a socket-backed `Read` it is a true unbounded loop — matching the CVE's failure mode of trusting an unvalidated length field.
