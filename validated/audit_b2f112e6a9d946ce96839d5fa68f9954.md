Webhook shop-domain binding excluded from HMAC verification enables cross-shop webhook confusion / forced shop deletion - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb])

### Summary
`ShopifyApp::WebhookVerification#verify_request` authenticates a webhook solely by HMAC-ing `request.raw_post` against the app secret. The `X-Shopify-Shop-Domain` header, which downstream job code trusts as the tenant identifier, is never included in the HMAC-verified data. This mirrors the `MerkleDistributor` bug class: a critical field used later to determine which "account"/tenant is affected is not bound into the cryptographically verified payload, so an attacker can swap that field while keeping a valid signature.

### Finding Description
`verify_request` computes/validates the signature only over the raw body: [1](#0-0) 

The `shop_domain` helper used by generated webhook jobs simply reads the header directly, with no cryptographic link to the verified body: [2](#0-1) 

`hmac_valid?` confirms this — the digest input `data` is only the raw body, and the shared secret is common to all shops installed on the app (not shop-specific): [3](#0-2) 

The `WebhooksController#receive` action forwards both the raw body and the full (unverified-for-domain) header set to the handler dispatch, and the generated `AppUninstalledJob` template resolves and destroys a `Shop` record purely by `shop_domain`, with no validation that the domain is consistent with the signed payload: [4](#0-3) [5](#0-4) 

Because the shared secret is the same across every shop that has installed the app, any merchant who installs the app on their own store can obtain a genuinely-signed webhook (body + valid `X-Shopify-Hmac-Sha256`) for their own shop, then replay that exact request directly to the app's public `/webhooks/:type` endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `verify_request` still passes because it never checks that the domain header is bound to the signed body, exactly analogous to `verifyClaim()` not binding `Claim.token` to the signed leaf data.

### Impact Explanation
This allows cross-tenant confusion: an attacker-controlled webhook body (with an attacker-chosen `X-Shopify-Shop-Domain`) is processed as if it originated from a shop the attacker does not control. Depending on which webhook job the app implements, consequences include:
- Using the generated `AppUninstalledJob`, an attacker can cause deletion (`shop.destroy`) of an arbitrary victim shop's record/session — a denial-of-service against another merchant's installation, achievable from an unrelated, unprivileged merchant account.
- For other jobs (e.g., orders/customers/data-request), the victim shop's tenant data could be corrupted or fabricated with attacker-controlled webhook content.

### Likelihood Explanation
Moderate-to-high: the only prerequisite is that the attacker has (or creates) their own install of the target app to legitimately harvest one correctly-signed webhook payload, then resend it directly to the app's internet-facing webhook endpoint with a modified domain header. No secret leak, no privileged access, and no cooperation from the victim shop is required — this is reachable from an unrelated-merchant HTTP request as required by the validation rules.

### Recommendation
Bind the shop domain (and any other externally-supplied routing headers such as topic/api-version if used for dispatch) into the verified signature material, or otherwise cryptographically tie the `X-Shopify-Shop-Domain` header to the signed body before trusting it for tenant resolution — e.g., include the header value in the HMAC input, or independently verify the shop domain against a known/expected value (such as looking up the domain from an installed-shop registry keyed by an already-authenticated identifier) rather than trusting the raw header value unconditionally in `shop_domain`/generated job templates.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggers a real webhook (e.g. `app/uninstalled`), and captures the legitimate request: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC_SHA256(secret, B)`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker crafts a new POST to `https://victim-app.example.com/webhooks/app_uninstalled` with the same body `B` and same `H` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `verify_request` in `webhook_verification.rb` validates `H` against `B` successfully (domain is irrelevant to the check).
4. The generated `AppUninstalledJob#perform` receives `shop_domain: "victim-shop.myshopify.com"`, looks it up, and calls `shop.destroy`, deleting the victim's installation/session despite the victim never uninstalling the app.

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
