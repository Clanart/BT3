### Title
Cached FROST preprocess seed is never invalidated after use, enabling nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary

`SigningProtocol::preprocess_internal` caches a deterministic FROST preprocess seed in `CachedPreprocesses`, keyed only by `(b"DkgConfirmer", attempt)`. Each call to `share_internal` rebuilds an `AlgorithmSignMachine` from that same seed — producing identical nonces — and then signs whatever preprocess set and message are provided in that call. Because the cached seed is never deleted, marked spent, or bound to the specific commitments/message that were signed, any second invocation under the same context with different inputs reuses the same nonces. This is the direct analog of CVE-2020-13294: an access artifact that should be revoked after use remains valid indefinitely.

### Finding Description

In `coordinator/src/tributary/signing_protocol.rs`:

- `preprocess_internal` generates a `CachedPreprocess` (a 32-byte ChaCha20 seed) once per context, XOR-encrypts it, stores it via `CachedPreprocesses::set`, and on every subsequent call decrypts the *same* seed and calls `AlgorithmSignMachine::from_cache` (`signing_protocol.rs:123-145`). `from_cache` deterministically re-derives the nonces via `seeded_preprocess` → `Commitments::new` in `crypto/frost/src/sign.rs:121-144`.
- `share_internal` calls `preprocess_internal` and then `machine.sign(preprocesses, msg)` with caller-supplied data (`signing_protocol.rs:150-180`).
- `DkgConfirmer::share` signs `set_keys_message(set, removed, key_pair)` where `preprocesses` and `key_pair` are parameters (`signing_protocol.rs:288-310`), and `DkgConfirmer::complete` independently accepts its *own* `preprocesses` map and `key_pair` and calls `share_internal` again (`signing_protocol.rs:312-327`).
- Nothing ever calls `txn.del` on `CachedPreprocesses`; the seed survives reboots and is re-consumed on every invocation.

Two `share`/`complete` executions under the same `attempt` that differ in either (a) the participant set/preprocess bytes (changing the binding factors `rho` and the aggregate nonce `R`) or (b) `key_pair`/`removed` (changing the challenge `c` via `hash_msg`) produce two shares `s₁ = d + b·ρ₁ + λ·x·c₁` and `s₂ = d + b·ρ₂ + λ·x·c₂`. With identical `d, b`, an observer solves for `x`, the validator's MuSig secret share, from publicly broadcast shares — the exact outcome `crypto/frost/src/sign.rs:85-87` and `spec/cryptography/FROST.md:51-55` warn against. The module's own header comment (`signing_protocol.rs:25-54`) acknowledges this hazard and defers safety entirely to BFT message finality plus a *TODO* check that on-chain commitments match the presumed preprocess — a check that is not implemented, and which does not prevent divergence caused by retry/re-execution paths (`share` succeeding while `complete` fails and is retried with different inputs, or `share` being invoked multiple times for the same attempt with distinct `key_pair`/preprocess sets).

### Impact Explanation

Recovery of a validator's MuSig secret share undermines the t-of-n DKG-confirmation signature that authorizes `set_keys` on Substrate — the operation that installs the network's root-of-trust validator set keys. Reused nonces across two distinct challenges yield the secret linearly, and since `set_keys_message` binds the resulting `KeyPair`, compromise of these shares at DKG-confirmation time can enable forging confirmation signatures or recovering the key whose confirmation is in flight. Classified Medium: requires a divergence in finalized inputs or a repeated signing attempt under the same context, but the missing invalidation is unconditional.

### Likelihood Explanation

The nonce-reuse path is reachable whenever `share`/`complete` is driven more than once under one `attempt` with differing inputs — e.g., a failed `complete` retried with a different preprocess map (the two functions take independent `preprocesses` arguments with no equality check against what was originally signed), or re-execution after partial state recovery, which the header comment concedes is a real flow (`signing_protocol.rs:44-48`). The only mitigations are (a) unimplemented TODO checks and (b) the assumption that BFT ordering prevents divergent inputs — yet the cryptographic artifact itself is never revoked, so any logical or operational edge that produces a second `sign` under the same context yields share reuse. That is precisely the "grants not revoked on revocation" class: the seed grant persists past its single intended use.

### Recommendation

- After successfully producing a share in `share_internal`, delete or tombstone `CachedPreprocesses` for that context (`txn.del`), so a second signing attempt under the same context cannot reproduce the nonces — either by erroring or by requiring a fresh, explicitly authorized context.
- Alternatively, persist the exact `(preprocess_set_hash, msg)` alongside the seed on first `sign` and refuse to `sign` if subsequent calls disagree, turning accidental divergence into a deterministic failure instead of key leakage.
- Implement the documented TODO: before publishing a share, verify that the commitments derived from the cached seed match the on-chain preprocess actually being signed for, binding the cached nonce to a single finalized message.

let mut confirmer = DkgConfirmer::new(&key, &spec, &mut txn, attempt).unwrap();
