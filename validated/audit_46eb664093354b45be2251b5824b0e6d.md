## Title
`createMergeCommit` skips Desktop's hook-interception guard, letting repository-supplied Git hooks execute unmediated when finishing a merge/rebase/cherry-pick - (File: `app/src/lib/git/commit.ts`)

### Summary
Desktop maintains a dedicated hook-interception subsystem (`withHooksEnv`, `getRepoHooks`, `hooks-proxy`) whose entire purpose is to intercept repository-local Git hooks (`pre-commit`, `commit-msg`, `post-commit`, etc.) discovered via the repo's own `core.hooksPath`/`.git/hooks`, proxy them through Desktop, and surface their execution to the user via `onHookProgress`/`onHookFailure` rather than letting the real Git binary invoke them silently. `createCommit` opts into this guard via the `interceptHooks` option, but the sibling function `createMergeCommit` — used to finish merges, rebases, and cherry-picks after conflict resolution — invokes `git commit` with no `interceptHooks` option at all, so `withHooksEnv` short-circuits and runs the command with the hooks completely unmediated.

### Finding Description
`withHooksEnv` only engages the interception proxy when the caller supplies `opts.interceptHooks`: [1](#0-0) 

`createCommit` (used for normal commits and amends) explicitly lists the hook names it wants intercepted: [2](#0-1) 

`createMergeCommit`, however, calls `git(['commit', '--no-edit', '--cleanup=strip'], repository.path, 'createMergeCommit')` with **no fourth options argument**, so `interceptHooks` is `undefined`: [3](#0-2) 

Because `interceptHooks` is falsy, `withHooksEnv`'s guard clause (`if (!opts?.interceptHooks || !getHooksEnvEnabled()) return fn(opts?.env)`) is taken, and the underlying `git commit` runs against whatever `core.hooksPath`/`.git/hooks` is actually configured for the repository, invoking any executable `pre-commit`, `commit-msg`, or `post-commit` hook directly with no proxying, no progress reporting, and — critically — no path through Desktop's `onHookFailure`/approval flow that the same hook names get when a *normal* commit is made via `createCommit`.

This is the same class of bug as the reentrancy report: a security-relevant invariant ("repository-controlled Git hooks are always mediated through Desktop's proxy before they run") is enforced in one commit-producing code path (`createCommit`) but not in a sibling code path (`createMergeCommit`) that reaches the identical underlying primitive (`git commit`, which triggers the same hook names).

### Impact Explanation
Hook scripts execute with the full privileges of the Desktop process/user (arbitrary local code execution), can read/exfiltrate files (including credentials), and can rewrite the commit message or amend content before the commit is finalized (silent corruption of what the user commits). Because `createMergeCommit` runs unmediated, this path bypasses Desktop's own mitigation for the well-documented class of "malicious repo plants an executable Git hook" attacks, and does so specifically at the moment a user finishes resolving merge/rebase/cherry-pick conflicts — a very common, everyday Desktop action.

### Likelihood Explanation
`core.hooksPath` pointing at an in-repo, versioned directory with hook scripts is a mainstream, widely-adopted pattern (e.g., Husky, lint-staged, pre-commit framework) that gets installed by an ordinary `npm install`/setup step immediately after cloning — not an "unnatural" manual step. A victim who clones an attacker's repository, runs the project's normal install step (which sets `core.hooksPath` and drops the hook files as part of standard, expected onboarding), and then resolves a merge conflict in Desktop will trigger `createMergeCommit`, executing the attacker's hook with no interception and no user-visible warning, unlike a plain commit which would have gone through the proxy.

### Recommendation
Pass the same `interceptHooks` (and `onHookProgress`/`onHookFailure`/`onTerminalOutputAvailable`) options from `createMergeCommit` (and its caller) into the underlying `git(...)` call, mirroring `createCommit`, so that `commit-msg`, `pre-commit`, and `post-commit` hooks are always proxied through Desktop's hook-review mechanism regardless of which commit-producing code path is used.

### Proof of Concept
1. Attacker publishes a repository containing a Husky-style setup: a `prepare` script in `package.json` that runs `git config core.hooksPath .husky` at install time, and a `.husky/post-commit` (or `commit-msg`) executable script containing an arbitrary payload (e.g., exfiltrate `~/.ssh`, `~/.git-credentials`, or `.netrc`, or silently rewrite the commit content).
2. Victim clones the repository with GitHub Desktop and runs the project's normal setup command (e.g., `npm install`) in a terminal, which sets `core.hooksPath=.husky` in `.git/config` and installs the hook files, per standard tooling conventions.
3. Victim creates a merge conflict scenario (e.g., merges/rebases a branch that conflicts) and resolves conflicts through Desktop's UI, then clicks "Continue Merge"/"Continue Rebase".
4. Desktop calls `createMergeCommit`, which invokes `git commit --no-edit --cleanup=strip` without `interceptHooks`; the attacker's `.husky` hook executes immediately and directly via the system Git binary, with no Desktop-mediated approval/progress dialog that would appear for a normal commit made via `createCommit`. export async function withHooksEnv<T>(
```typescript
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
```

```typescript
      // This clashes with our use of `--no-edit` above as Git will now change
      // it's behavior to invoke `--cleanup=whitespace` as it did not ask
      // the user to edit the COMMIT_MSG as part of creating a commit.
      //
      // From the docs on git-commit (https://git-scm.com/docs/git-commit) I'll
      // quote the relevant section:
      // --cleanup=<mode>
      //     strip
      //        Strip leading and trailing empty lines, trailing whitespace,
      //        commentary and collapse consecutive empty lines.
      //     whitespace
      //        Same as `strip` except #commentary is not removed.
      //     default
      //        Same as `strip` if the message is to be edited. Otherwise `whitespace`.
      //
      // We should emulate the behavior in this situation because we don't
      // let the user view or change the commit message before making the
```
