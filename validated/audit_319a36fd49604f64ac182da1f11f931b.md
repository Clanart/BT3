### Title

Untrusted participant indexes in PedPoP blame evaluation cause a panic (denial of service) via unchecked map lookups - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

CVE-2020-36330 is an out-of-bounds read in a parsing/validation routine reachable with attacker-controlled input. Serai's analog is not a memory-unsafe read (the crate is safe Rust), but the same bug class: missing bounds validation of attacker-supplied index data in a verification path, yielding an abort. In PedPoP's blame evaluation, the `sender`/`recipient` `Participant` arguments come from a fault accusation — public, attacker-influenced data — and are used to index `HashMap`s with the `[]` operator and to decrypt with `self.enc_keys[&decryptor]`, neither of which is checked against the registered participant set `1..=n`. A `Participant` value that is validly formed (`Participant::new` only rejects zero) but outside the registered set, or a `recipient` who never registered an encryption key, causes a panic inside library code reached from public inputs.

### Finding Description

`AdditionalBlameMachine::new` populates `commitments` and `encryption.enc_keys` only for `Participant`s `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs:656-659`). `blame` / `blame_internal` then index `self.commitments[&sender]` (`lib.rs:599`) and `self.enc_keys[&decryptor]` (`crypto/dkg/pedpop/src/encryption.rs:388`) with the `Index` operator on `HashMap`, which panics on a missing key. Nothing constrains `sender` or `recipient` to the registered set: `Participant::new` accepts any nonzero `u16`, so `sender = Participant(n + 1)` or any `recipient` absent from `enc_keys` is a reachable panic. The same shape exists in `Decryption::decrypt_with_proof` called from `BlameMachine::blame`, which any deployment surfaces when it adjudicates a peer's accusation.

This is reachable with exactly the inputs the threat model allows: a party submits a blame/accusation message naming a `sender`/`recipient` of its choice, and the honest node's machine processes it. The code even documents that out-of-range inputs "may cause ... panics" (`lib.rs:648`), but that warning covers *invalid commitments*, not attacker-chosen index arguments — and documented-MUST-misuse exclusions apply to the caller providing wrong commitments, not to unvalidated message-derived fields.

The analogous OOB-read shape in the FROST path was checked and does not hold: `Commitments::read` (`crypto/frost/src/nonce.rs:133-139`) reads exactly `generators.len()` elements, so `BindingFactor::nonces`/`bound` indexing (`nonce.rs:183-206`) cannot overrun; `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:591-623`) bounds every count it reads via `read_exact` and `ThresholdParams::new` validation. The blame path is the reachable gap.

### Impact Explanation

Availability: an unprivileged participant (or any party able to trigger blame adjudication, e.g., by reporting a fault with a crafted participant index `> n` or a non-registered `recipient`) crashes the honest node's DKG/blame handler with a panic. In a validator/processor context this aborts key generation or slashes adjudication for the session. Mirrors the CVE's availability impact (A:H) mapped onto safe-Rust's equivalent (index panic instead of OOB read).

### Likelihood Explanation

Low-to-moderate exploitation complexity: the attacker only needs their accusation processed — a normal protocol action — with an index outside the registered set. It requires the deployment to route accusations into `blame`, which is the documented purpose of `BlameMachine`/`AdditionalBlameMachine`. No key material, collusion, or malformed encodings are needed.

### Recommendation

Validate `sender` and `recipient` in `blame_internal` against the registered sets before indexing: return a defined error or a deterministic blame result when `!self.commitments.contains_key(&sender)` or `!self.encryption.enc_keys.contains_key(&decryptor)`. Replace `map[&key]` with `map.get(&key)` plus explicit handling in `Decryption::decrypt_with_proof` (`encryption.rs:388`) and `blame_internal` (`lib.rs:599`).

### Proof of Concept

```rust
// PedPoP DKG for n = 3 completes, yielding AdditionalBlameMachine via
// AdditionalBlameMachine::new(context, 3, commitment_msgs).
// commitments/enc_keys are populated only for Participant(1..=3).

// An accusation names a sender outside the registered set:
let attacker_sender = Participant::new(4).unwrap(); // valid Participant, unregistered

// AdditionalBlameMachine::blame -> blame_internal ->
//   share_verification_statements(recipient, &self.commitments[&attacker_sender], ...)
//                                              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
// HashMap Index on missing key -> panic!("key not found")

// Equivalently, inside blame_internal:
//   decrypt_with_proof -> self.enc_keys[&decryptor]  (encryption.rs:388)
// panics for any `recipient` that never registered an EncryptionKeyMessage.
```

Both panics are triggered solely by attacker-chosen `Participant` arguments to the public `blame` API; no malformed serialization is required.
