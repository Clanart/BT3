### Title
Referrer can self-reset owner-assigned tier back to default tier 1 via `registerCode` re-registration - (File: rewards/ReferralStorage.sol)

### Summary
`registerCode()` unconditionally sets `userInfos[msg.sender].tier = 1` and has no check preventing an address that already owns a code from registering another one. An attacker whose tier was demoted by the owner via `setReferrerTier` can call `registerCode()` again with a fresh, unused code to silently reset their tier back to 1, bypassing the owner's tier assignment used in `trigger()`.

### Finding Description
`registerCode()` only validates that the code itself is unoccupied (`codeOwners[_code] != address(0)`), but never checks whether `msg.sender` already has `userInfos[msg.sender].myCode != bytes32(0)`: [1](#0-0) 

This means any address can call `registerCode()` multiple times with different unused codes, and each call hardcodes `userInfo.tier = 1` regardless of any prior owner intervention. `setReferrerTier` is the only owner-controlled mechanism to adjust a referrer's tier: [2](#0-1) 

`trigger()` reads `userInfos[_referer].tier` to look up `tiers[tierId].rewardPercentage`, which directly determines the referrer's and referee's split of `_amount` (MGP reward) on every referee claim: [3](#0-2) 

So if the owner calls `setReferrerTier(attacker, 0)` to demote the attacker (e.g., tier 0 has `rewardPercentage = 0` or lower than tier 1), the attacker can simply call `registerCode(newCode)` with any never-before-used bytes32 code, which resets `userInfo.tier` to 1 and restores/upgrades their reward percentage for all future `trigger()` calls — completely bypassing the owner's demotion decision.

### Impact Explanation
This allows an unprivileged referrer to unilaterally override an owner-assigned (typically punitive, lower) tier and restore a more favorable tier, resulting in theft of unclaimed MGP referral yield beyond what the owner intended to allow — an economic loss of protocol funds each time a referee's reward is triggered afterward. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
Preconditions: the owner must have previously called `setReferrerTier` to demote the attacker below tier 1's reward percentage (a plausible moderation/anti-abuse action), and the attacker must have at least one referee still generating rewards via `trigger()`. No capital is needed — `registerCode()` is a free, unprivileged, repeatable call with an arbitrary new `bytes32` code value chosen by the attacker. This is fully reproducible and repeatable at will.

### Recommendation
In `registerCode()`, do not reset `tier` if the caller already has an existing `myCode`/tier assignment; only set the default tier 1 on first-time registration (e.g., guard with `if (userInfos[msg.sender].myCode == bytes32(0)) { userInfo.tier = 1; }`), or disallow re-registration entirely by reverting if `userInfos[msg.sender].myCode != bytes32(0)`.

### Proof of Concept
Foundry test outline:
1. Deploy `ReferralStorage`, initialize, call `setTier(0, 0)` and `setTier(1, 5000)` (tier1 = 50% reward).
2. Attacker calls `registerCode("code1")` → `userInfos[attacker].tier == 1`.
3. Owner calls `setReferrerTier(attacker, 0)` → `userInfos[attacker].tier == 0`.
4. Attacker calls `registerCode("code2")` (a fresh unused code).
5. Assert `userInfos[attacker].tier == 1` (bug reproduced — owner's demotion silently reversed).
6. Optionally call `trigger()` from a mocked `masterMagpie` for a referee of the attacker and assert `refererAmount` reflects tier 1's higher `rewardPercentage` instead of the owner-assigned tier 0.

```text
    function registerCode(bytes32 _code) external {
        if (_code == bytes32(0)) revert InvalidCode();
        if (codeOwners[_code] != address(0)) revert CodeOccupied();

        codeOwners[_code] = msg.sender;
        userInfos[msg.sender].myCode = _code;
        userInfos[msg.sender].tier = 1; // tier 1 as default

        emit RegisterCode(msg.sender, _code);
    }
```
