### Title
`unvote` Reverts on Deactivated Pools, Permanently Freezing Voted vlMGP - ([File: wombat/WombatBribeManager.sol])

### Summary
In `WombatBribeManager.sol`, the `unvote` function is documented to let users remove their votes from a pool that has been deactivated by the admin ("This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing"), but its guard condition does the opposite: it reverts with `PoolNotActive()` when the pool is *not* active [1](#0-0) . This mirrors the reported bug class where an admin-controlled "deprecation" flag on one code path (pool `isActive`) is not correspondingly relaxed on a dependent path (the user's ability to withdraw/unvote), trapping an ordinary wallet's funds.

### Finding Description
`vote()` requires `pool.isActive` to be true before allowing a user to add or remove votes on that pool [2](#0-1) . Once the admin deactivates a pool (setting `isActive = false`), users can no longer call `vote()` to zero out their position in that pool, since the very first check `if (!pool.isActive) revert PoolNotActive();` blocks the call.

`unvote()` exists specifically as an escape hatch for this scenario — its docstring states it lets a user unvote from an inactive pool so that "deleting a pool ... doesn't block users from withdrawing" [3](#0-2) . However, the implementation carries the exact same `if(!pool.isActive) revert PoolNotActive();` guard as `vote()` [4](#0-3) , meaning `unvote()` only succeeds while the pool is still active — the opposite of its stated purpose. Once a pool is deactivated, the user's vote for that pool (tracked in `userVotedForPoolInVlmgp[msg.sender][pool.poolAddress]` and rolled into `userTotalVotedInVlmgp[msg.sender]`) can never be cleared through either `vote()` or `unvote()`.

`VLMGP.startUnlock()` uses `userTotalVotedInVlmgp` to cap how much of a user's locked MGP can enter the unlock cooldown: `totalLockAfterStartUnlock` must remain `>= IWombatBribeManager(wombatBribeManager).userTotalVotedInVlmgp(msg.sender)` [5](#0-4) . Because the stuck vote amount can never be reduced once its pool is deactivated, the portion of the user's vlMGP corresponding to that vote becomes permanently ineligible for unlock — an ordinary wallet's own locked tokens become frozen with no path to recovery, purely as a side effect of a routine admin pool-deactivation action (not any malicious admin behavior).

### Impact Explanation
This causes a permanent freeze of user funds (locked MGP) with no available user-initiated remediation: neither `vote()` nor `unvote()` can clear the stale vote once the target pool is deactivated, and `VLMGP.startUnlock()` will indefinitely reject unlocking the corresponding amount. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Pool deactivation is an expected, normal lifecycle event for Wombat pools (rewarder migrations, pool sunsetting), not a rare or adversarial admin action. Any user who voted for a pool at the time it is later deactivated is affected — this can happen to any voter without any special conditions, making the likelihood high whenever a pool is retired while users still hold votes on it.

### Recommendation
Fix the guard in `unvote()` so that it does not require the pool to be active — the whole point of the function, per its own docstring, is to allow unvoting from inactive/deleted pools. Either remove the `isActive` check entirely from `unvote()`, or invert dependent logic so unvoting is always permitted regardless of pool status, ensuring `userTotalVotedInVlmgp` can always be reduced back to zero for any pool a user has voted on.

### Proof of Concept
1. User calls `vote()` with a positive delta for pool `P` while `P.isActive == true`, incrementing `userVotedForPoolInVlmgp[user][P]` and `userTotalVotedInVlmgp[user]` [6](#0-5) .
2. Admin deactivates pool `P` (sets `poolInfos[P].isActive = false`) as part of normal pool management.
3. User attempts `vote(P, 0)` or `unvote(P)` to clear their vote — both revert with `PoolNotActive()` because both check `if (!pool.isActive) revert PoolNotActive();` [7](#0-6) [8](#0-7) .
4. `userTotalVotedInVlmgp[user]` remains stuck at its prior value forever.
5. User calls `VLMGP.startUnlock()` attempting to unlock an amount that would bring `totalLockAfterStartUnlock` below `userTotalVotedInVlmgp[user]`; the call reverts with `NotEnoughLockedMPG()` [9](#0-8) , permanently freezing that portion of the user's locked MGP.

    /// @notice Unvote from an inactive pool. This makes it so that deleting a pool, or changing a rewarder doesn't block users from withdrawing
    function unvote(address _lp) public {
        Pool storage pool = poolInfos[_lp];
        uint256 currentVote = userVotedForPoolInVlmgp[msg.sender][pool.poolAddress];
        if(!pool.isActive)
            revert PoolNotActive();
        
        pool.totalVoteInVlmgp -= uint256(currentVote);
        userTotalVotedInVlmgp[msg.sender] -= uint256(currentVote);
        userVotedForPoolInVlmgp[msg.sender][pool.poolAddress] = 0;
        if (msg.sender != delegatedPool) {
            totalVlMgpInVote -= currentVote;
        }
        
        IBribeRewardPool(pool.rewarder).withdrawFor(msg.sender, uint256(currentVote), true);
    }
