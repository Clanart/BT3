## Finding

The path-containment guard `resolveWithin` in GitHub Desktop has a classic prefix-matching flaw: it compares resolved paths with `String.prototype.startsWith()` without checking for a path-separator boundary, allowing any sibling directory whose name has the repository path as a string prefix to be treated as "inside" the repository. [1](#0-0) 

### Title
Path-containment check in `resolveWithin` allows directory-name-prefix bypass, enabling file read/write outside the repository during merge-conflict resolution - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` is meant to guarantee that a resolved path stays "at, or underneath" a given root directory, and is used as the security boundary before reading or writing files whose relative paths are derived from attacker-influenced git state (merge/rebase/cherry-pick conflict paths). Its final check is:

```
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`startsWith` performs a raw string comparison with no separator boundary check, so a resolved path like `/Users/dev/myrepo-secrets/config.json` is treated as "within" root `/Users/dev/myrepo` because the string `"…/myrepo-secrets/…"` starts with `"…/myrepo"`. No symlink or `..`-escape detection failure is required — a sibling directory that merely shares the repo directory name as a prefix is enough.

### Finding Description
`resolveWithin` (and its POSIX/Win32 variants) is the sole guard used to keep file operations confined to the repository when the target path comes from data that can be influenced by a remote/attacker-controlled repository state:

- `copilot-conflict-context.ts` calls `resolveWithin(workingDirectory, file.path)` before reading conflict file contents that are then sent to Copilot's resolution service. [3](#0-2) 
- `app-store.ts` calls `resolveWithin(repository.path, resolution.path)` before writing AI-resolved content back to disk. [4](#0-3) 
- `dispatcher.ts` calls `resolveWithin(repository.path, filepath)` before revealing a deep-link-supplied file path in the file manager. [5](#0-4) 

`file.path` / `resolution.path` in the first two call sites are populated from the conflicted-file list reported by `git status`, i.e. from filenames that a malicious remote branch can freely choose when a user merges/rebases/cherry-picks it (a normal, "unprivileged" cloned/fetched repository interaction). By choosing a conflicting file whose relative path is a `..`-traversal into a sibling directory that shares the repository's directory name as a string prefix (e.g. repo at `/Users/dev/myrepo`, crafted relative path `../myrepo-secrets/id_rsa`), the resolved absolute path `/Users/dev/myrepo-secrets/id_rsa` passes the `startsWith` check even though it is a completely different directory. No symlink is needed; the existing unit tests for `resolveWithin` only cover `..`-escape and symlink-escape cases, never the same-prefix-sibling case, so this bypass is unguarded and untested. [6](#0-5) 

### Impact Explanation
- Via `copilot-conflict-context.ts`, an attacker-crafted conflict path can cause Desktop to read a file from a sibling directory (e.g. `.env`, SSH keys, other private repo contents) and transmit its contents to Copilot's external conflict-resolution API — cross-repository file read and potential credential/secret exfiltration to a third party.
- Via `app-store.ts`'s `writeFile(absolutePath, resolution.resolvedContent, 'utf8')`, the same bypass allows writing attacker/AI-controlled content to a file outside the repository, which is file write outside the repo bounds and can silently corrupt unrelated project state on disk.

### Likelihood Explanation
Requires: (1) the victim to have another directory on disk whose name is prefixed by the current repository's directory name (a common naming pattern for backups/forks, e.g. `repo`, `repo-old`, `repo.bak`, `repo2`), and (2) the victim to merge/rebase/cherry-pick a branch from an untrusted remote that introduces a conflicting file at a `..`-relative path landing in that sibling directory, and then to accept an automated (Copilot) conflict resolution. This is plausible but conditional on directory-naming coincidence, so likelihood is moderate rather than trivial.

### Recommendation
Fix the boundary check in `_resolveWithin` (`app/src/lib/path.ts`) to require an exact match or a match followed by the platform path separator:
```
return realResolved === realRoot || realResolved.startsWith(realRoot + sep)
  ? resolved
  : null
```
Add regression tests covering sibling directories whose names share the root directory name as a prefix.

### Proof of Concept
1. Locally have two directories: `/Users/dev/myrepo` (the cloned repo) and `/Users/dev/myrepo-secrets` (containing sensitive files, e.g. `id_rsa`).
2. As the attacker, prepare a branch that, when merged into `myrepo`, produces a conflicting file whose git-reported relative path is `../myrepo-secrets/id_rsa`.
3. Victim merges/rebases that branch in Desktop, triggering the Copilot conflict-resolution flow which calls `buildConflictContext` → `resolveWithin('/Users/dev/myrepo', '../myrepo-secrets/id_rsa')`.
4. `resolve()` yields `/Users/dev/myrepo-secrets/id_rsa`; `realResolved.startsWith(realRoot)` evaluates true because `"/Users/dev/myrepo-secrets/id_rsa".startsWith("/Users/dev/myrepo")` is true, so the guard incorrectly returns the path as valid.
5. The file's contents are read and sent to the external Copilot conflict-resolution API (or, on the write path, arbitrary content is written into that sibling directory), demonstrating the read/write escape from the intended repository root.
