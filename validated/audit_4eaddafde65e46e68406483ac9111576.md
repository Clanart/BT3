### Title
Copilot conflict-resolution marker check uses an overly narrow AND condition, letting leftover conflict markers slip into committed files - ([File: app/src/lib/copilot-conflict-resolution.ts])

### Summary
`parseCopilotConflictResolution` is supposed to guarantee that no hunk resolution returned by the AI conflict-resolution feature still contains raw Git conflict markers before it is spliced into the user's file and staged for commit. The guard is implemented as a single regex conjunction that requires *both* an opening `<<<<<<<` marker line *and* a `=======` separator line to be present in the same `resolvedContent` string before it rejects the output. Just like the `AdapterVault` finding where `ADAPTER_BREAKS_LOSS_POINT` used an overly tight/narrow condition that failed to represent the real invariant it was meant to protect, this check's narrow "both markers together" requirement does not represent the actual invariant ("no marker of any kind may remain"), so content with only one marker line survives validation untouched.

### Finding Description
The validation lives in `parseCopilotConflictResolution`: [1](#0-0) 

```
const rc = hunkObj.resolvedContent
if (/^<{7}\s/m.test(rc) && /^={7}$/m.test(rc)) {
  throw new CopilotValidationError(
    `Copilot returned an invalid conflict resolution payload: hunk ${j} of file "${path}" still contains conflict markers`
  )
}
```

This is the *only* place in the pipeline that checks whether a hunk resolution still contains leftover conflict-marker syntax. It never checks for a lone `<<<<<<<` line, a lone `=======` line, or a lone `>>>>>>>` closing marker (`reassemblyTheirsMarker` in the same file, defined at `app/src/lib/copilot-conflict-resolution.ts:526`, is never referenced by this validation at all). Once `resolvedContent` passes this check (or trivially bypasses it because it contains only one of the two marker types), it flows unmodified into `reassembleResolvedFile`: [2](#0-1) 

```
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  if (resolved.length > 0) {
    resultLines.push(...resolved.split(/\r?\n/))
  }
}
```

and is then written straight to disk and `git add`-ed without any further sanity check: [3](#0-2) 

```
await writeFile(absolutePath, resolution.resolvedContent, 'utf8')
pathsToStage.push(resolution.path)
```

Because the app trusts this one AND-based check to guarantee "no markers remain," any hunk resolution containing exactly one marker type — e.g. a lone `<<<<<<< HEAD` line with no matching `=======`/`>>>>>>>`, or a lone `>>>>>>> theirs` closing line, or a `=======` separator by itself — is treated as fully clean content. The conflict-resolution feature is driven by content in a cloned/fetched repository: file content, commit messages, and PR descriptions from an attacker-controlled branch are placed directly into the model prompt (see the system prompt at `app/src/lib/copilot-conflict-resolution.ts:190-254`, which explicitly forwards "Conflict markers from each file" and "recent commit messages and/or PR title/description"). A crafted upstream commit/file (e.g., one that legitimately contains literal `<<<<<<<`/`=======`/`>>>>>>>`-looking text as data, or that is engineered via prompt-injection to bias the model's truncated/partial output) can cause the model's `resolvedContent` for a hunk to retain a single marker line while omitting its counterpart, which sails through validation.

### Impact Explanation
If a hunk resolution keeps a stray/incomplete conflict marker, `reassembleResolvedFile` will splice it verbatim into the final file, and `_applyCopilotConflictResolutions` writes that content to disk and stages it with `git add` before the user commits/pushes. This is a silent corruption of what the user commits: the working tree file ends up containing invalid/broken syntax or a dangling marker line that isn't flagged by Desktop's own guard (whose entire purpose is to catch exactly this), even though the UI tells the user the conflict was "resolved" by Copilot. Depending on the file type, this can silently break builds, reintroduce a real Git conflict marker into shipped source, or (in the worst case for structured files like lockfiles/manifests, which the system prompt explicitly calls out as a resolution target) produce structurally corrupted content that gets pushed upstream.

### Likelihood Explanation
The attacker precondition is unprivileged: they only need to control content that ends up in the diff/commit history/PR description of a branch the victim merges, rebases, or cherry-picks with "Resolve with Copilot" enabled — no local access, no credentials, no admin rights. LLM output is inherently variable (truncation, partial copy of source text, token limits, or prompt-shaped bias), so producing output with exactly one marker type instead of a matched pair is a realistic, not contrived, failure mode. The existing guard is the sole defense and, as shown, its AND-based logic does not cover this case, so it provides no protection against it.

### Recommendation
Replace the conjunction with a check that rejects the presence of *any* conflict-marker line individually — `<<<<<<<`, `=======`, or `>>>>>>>` — using the same three regexes already defined for reassembly (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`), e.g. `if (reassemblyOursMarker.test(rc) || reassemblySeparatorMarker.test(rc) || reassemblyTheirsMarker.test(rc)) { throw ... }`. Additionally, perform a final marker scan on the fully reassembled file content before it is written to disk in `_applyCopilotConflictResolutions`, as a defense-in-depth backstop independent of per-hunk validation.

### Proof of Concept
1. Construct a repository with a merge/rebase conflict where the "theirs" side of a hunk is crafted so the model's returned resolution for that hunk is a string such as:
   `"const a = 1\n<<<<<<< orphan\nconst b = 2\n"` (opening marker with no `=======`/`>>>>>>>` counterpart).
2. Feed this through `parseCopilotConflictResolution`: `/^<{7}\s/m.test(rc)` is `true`, but `/^={7}$/m.test(rc)` is `false`, so the `&&` short-circuits to `false` and no `CopilotValidationError` is thrown — the hunk resolution is accepted as `validatedHunks`.
3. `reassembleResolutions` → `reassembleResolvedFile` splices this content verbatim into the file.
4. `_applyCopilotConflictResolutions` (`app/src/lib/stores/app-store.ts:7258-7259`) writes the file to disk and stages it with `git add`, so the corrupted content (with a dangling `<<<<<<<` marker) is what the user ultimately commits/pushes, with Desktop's UI reporting the conflict as cleanly resolved.
