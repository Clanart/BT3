### Title
Cached FROST preprocess seed is never deleted, enabling nonce reuse and secret share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` stores a FROST preprocess seed in the `CachedPreprocesses` DB table keyed by `context` and re-derives the identical nonces on every call, but never deletes the entry after use. The FROST API contract explicitly requires the cached preprocess "be deleted so it's never reused" (`crypto/frost/src/sign.rs`), since reuse leaks the private key share. `DkgConfirmer` invokes `preprocess_internal` once per `share()` call and again inside `complete()`, all under the same `context = (b"DkgConfirmer", self.attempt)`, so the same nonce seed is consumed for distinct `sign()` invocations.

### Finding Description
In `preprocess_internal`, when `CachedPreprocesses::get(self.txn, &self.context)` is `None`, a fresh `machine.cache()` seed is XOR-encrypted and persisted via `CachedPreprocesses::set` (signing_protocol.rs:123-134). On every subsequent call with the same context, the stored seed is decrypted and passed to `AlgorithmSignMachine::from_cache` (signing_protocol.rs:137-145), which feeds it to `ChaCha20Rng::from_seed` — deterministically regenerating the same nonces (`crypto/frost/src/sign.rs` `seeded_preprocess`, lines 121-143). There is no `CachedPreprocesses::del`/removal anywhere in the codebase; a grep confirms the only uses are `get`/`set` in this file.

`DkgConfirmer::share` and `DkgConfirmer::complete` each call `share_internal` → `preprocess_internal` (signing_protocol.rs:301, 321-324). `complete` is documented as callable after `share` and re-runs `machine.sign` under the same attempt context. The signed message is `set_keys_message(&self.spec.set(), &removed, key_pair)` (signing_protocol.rs:296-300), which varies with `key_pair`, and the FROST binding factor/challenge varies with the chosen `preprocesses` set. Two `sign()` executions therefore reuse identical nonces while producing shares bound to different challenges or different messages.

### Impact Explanation
A Schnorr/FROST signature share has the form `z = d + e·(ρ·share)` over nonce `d`. Two shares generated from the same nonce seed but different challenges/messages yield two linear equations in the same unknowns, allowing recovery of the signer's secret share — exactly the failure the `cache()`/`from_cache` documentation warns about ("Reusing preprocesses would enable a third-party to recover your private key share", `spec/cryptography/FROST.md`:51-55). Recovery of a tributary validator's MuSig/FROST secret share compromises the threshold key for that set. This mirrors the kernel bug class: a refcounted resource acquired via a lookup must be released (`of_node_put`) when done; here the cached seed acquired via `CachedPreprocesses::get` must be deleted when done, and isn't.

### Likelihood Explanation
The reuse path is exercised by normal protocol flow: `share()` is invoked when preprocesses arrive, and `complete()` re-invokes `share_internal` for the same `(b"DkgConfirmer", attempt)` context whenever the coordinator wants to locally finalize, including when the `key_pair` being confirmed differs or when the preprocess/shares subset differs (any subset of participants yields a different binding factor over the same nonce). An unprivileged participant who can influence which preprocesses are included in the confirmation set — by submitting or withholding their own preprocess (public input to `read_preprocess`/`sign`) — can force a second `sign()` execution whose challenge differs from the first while the nonce is byte-identical. No reboot or timing assumption is needed; the seed persists in the DB and survives restarts, so any repeat of the same attempt context reuses it.

### Recommendation
Delete the `CachedPreprocesses` entry after loading it in `preprocess_internal` (e.g., `CachedPreprocesses::del(self.txn, &self.context)` immediately after `get`), and/or key the cache by a value that cannot repeat across `sign()` calls (distinct context for share vs. complete, or a monotonic counter). Ensure that if a `sign()` attempt must be re-run, a genuinely fresh seed is generated rather than the persisted one.

### Proof of Concept
Conceptual trace, all in `coordinator/src/tributary/signing_protocol.rs` and `crypto/frost/src/sign.rs`:

1. Attempt `k`: `DkgConfirmer::share(preprocesses_A, key_pair_X)` → `preprocess_internal` stores seed `s` under `("DkgConfirmer", k)`, derives nonces `d, e` via `ChaCha20Rng::from_seed(s)` (`sign.rs`:127-133), signs `set_keys_message(.., key_pair_X)`, producing share `z1 = d + ρ1·e + c1·λ·x`.
2. `DkgConfirmer::complete(preprocesses_B, key_pair_Y, shares)` → `share_internal` → `preprocess_internal` finds `CachedPreprocesses::get` returns `Some(s)` (never deleted), regenerates identical `d, e` (`sign.rs`:273 → `seeded_preprocess`). With a different participant subset (`B ≠ A`) or different `key_pair`, the binding factor `ρ` and/or challenge `c` differ (`sign.rs` `sign`, lines 283+), yielding `z2 = d + ρ2·e + c2·λ·x`.
3. Given `z1, z2` and public commitments, the attacker solves a 2×2 linear system over `d, e` (or directly for `x` when `ρ1 = ρ2`) to recover the validator's secret share — confirmed by the documented invariant that reuse "will enable third-party recovery of your private key share" (`sign.rs`:211-213, `FROST.md`:51-53).
