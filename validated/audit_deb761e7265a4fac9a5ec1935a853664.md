### Title
App Proxy request signature never validates the signed `timestamp`, permitting indefinite replay of a previously valid HMAC-signed request - ([File: lib/shopify_app/controller_concerns/app_proxy_verification.rb])

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` recomputes the HMAC over all query parameters (including `timestamp`) and compares it to the `signature` param, but it never checks that the `timestamp` value is recent. Any request that was ever validly signed by Shopify for a given App Proxy call remains "valid" forever, because the timestamp is only used as signed input, not as a freshness bound.

### Finding Description
`query_string_valid?` extracts the `signature` param, recomputes `calculated_signature` over the remaining query params (which includes `timestamp`), and does a secure comparison. There is no check anywhere that `timestamp` is within a reasonable window of `Time.now`. [1](#0-0) 

This mirrors the M-1 pattern precisely: a signed value (`updatedAt`/`timestamp`) is present in the payload but the verifying code never enforces that it is current, so a stale-but-validly-signed artifact continues to be accepted indefinitely. Here, once an attacker or unrelated/anonymous party obtains a previously issued, validly signed App Proxy URL (these are ordinary GET request URLs sent to a storefront proxy path, easily captured via browser history, HTTP `Referer` headers, shared links, proxy/CDN logs, or analytics tools since App Proxy requests are not authenticated by session and are visited by any storefront customer), that URL/signature can be replayed against the app's App Proxy endpoint at any time in the future and will still pass verification. [2](#0-1) 

The included controller generator wires this concern directly into the app's App Proxy controller with no additional freshness check added on top: [3](#0-2) 

### Impact Explanation
An accepted forged/replayed signed request lets an anonymous or unrelated party re-trigger the app's App Proxy endpoint using an old, previously-seen valid signature indefinitely — bypassing the intended one-time/short-lived nature of the signed proxy request. Depending on what the app's `AppProxyController`/downstream logic does with `shop` and other params (e.g. issuing shop-scoped side effects, exposing shop-specific data via the Liquid response, or being combined with a stale `shop` context), this enables cross-shop or stale-context request forgery through the App Proxy channel without needing to compromise the shared secret.

### Likelihood Explanation
App Proxy URLs are ordinary unauthenticated GET requests rendered/loaded by any storefront visitor, so their full query string (including `timestamp` and `signature`) is trivially observable by any anonymous/unrelated visitor via browser history, `Referer` leakage, shared links, or intermediary logs. Because there is no expiry enforcement, capturing one such URL is sufficient for permanent replay — this significantly increases the realistic likelihood of exploitation relative to a scenario where a short-lived freshness window is enforced.

### Recommendation
Enforce a reasonable freshness window on the `timestamp` query parameter in `query_string_valid?` (e.g. reject if `Time.now.to_i - timestamp.to_i` exceeds a defined threshold, such as a few minutes), similar to the fix applied in the referenced analog (rejecting stale signed data), before accepting the HMAC as valid:
```ruby
def query_string_valid?(query_string)
  query_hash = Rack::Utils.parse_query(query_string)

  signature = query_hash.delete("signature")
  return false if signature.nil?

  timestamp = query_hash["timestamp"]
  return false if timestamp.nil? || (Time.now.to_i - timestamp.to_i).abs > MAX_APP_PROXY_REQUEST_AGE

  ActiveSupport::SecurityUtils.secure_compare(
    calculated_signature(query_hash),
    signature,
  )
end
```

### Proof of Concept
1. As an anonymous storefront visitor, load a page that triggers an App Proxy request (e.g. via a theme app extension or app-proxy embedded link); capture the full request URL, including `shop`, `path_prefix`, `timestamp`, and `signature` query params (via browser dev tools, browser history, or a `Referer` header on an outbound link).
2. Wait an arbitrary amount of time (hours, days, or longer).
3. Replay the exact same captured URL directly against the app's App Proxy endpoint.
4. Because `query_string_valid?` only re-validates the HMAC (which is unchanged since the params, including `timestamp`, are identical) and never checks how old `timestamp` is, the request is still accepted as valid, as demonstrated by the existing test suite which validates old, fixed timestamps (e.g. `1466106083`, corresponding to the year 2016) as currently-valid signatures: [4](#0-3)
