## Title
Unrecoverable pool-wallet lockout: `PoolWallet.target_state` is set before travel-transaction generation and is never cleared on failure, permanently blocking `join_pool`/`self_pool` — (File: `chia/pools/pool_wallet.py`)

### Summary
`PoolWallet.join_pool()` and `PoolWallet.self_pool()` assign `self.target_state` *before* calling `generate_travel_transactions()`, with no `try`/`except` to roll the flag back if transaction generation fails. `target_state` is only cleared in two places: when the chain state observed in `apply_state_transition()` matches it, or in the internal error branch of `new_peak()`. If the travel transaction is never generated (and therefore never spent on-chain), neither of those paths ever fires, so the flag is stuck `not None` forever for that wallet instance. This is the same bug class as the reported `s_hasVotedByEpochAndTokenId` issue: a "reset"/failure path leaves a guard flag set, permanently blocking the user's subsequent legitimate call (`join_pool`/`self_pool` are both gated by `if self.target_state is not None: raise ValueError(...)`).

### Finding Description
`join_pool()` and `self_pool()` share this pattern: [1](#0-0) [2](#0-1) 

Both methods set `self.target_state = ...` and then unconditionally call `await self.generate_travel_transactions(fee, action_scope)`. That method itself can raise before ever constructing/queuing a spend bundle, for example inside the fee-transaction path: [3](#0-2) [4](#0-3) 

`generate_fee_transaction` calls `standard_wallet.generate_signed_transaction(..., fee=fee, ...)`, which raises `ValueError` (e.g. "Insufficient funds") if the wallet cannot select enough coins for the requested fee, or `action_scope` processing can fail for other reasons (coin selection races, action-scope errors, etc.). Any exception raised anywhere inside `generate_travel_transactions` after `self.target_state` was already assigned leaves that field permanently non-`None`.

The only two places that ever reset `target_state` back to `None` require an actual on-chain spend matching that target: [5](#0-4) [6](#0-5) 

Since no travel spend bundle was ever produced or broadcast, `apply_state_transition` never sees a matching spend, so `target_state` is never cleared through the normal path. From then on, every subsequent call to `join_pool` or `self_pool` immediately fails with: [7](#0-6) [8](#0-7) 

This mirrors the reported pattern exactly: a guard flag (`s_hasVotedByEpochAndTokenId` / `target_state`) is set prior to a side-effecting action, the side-effecting action can abort, and no failure-path reset exists, so the user is locked out of the very function meant to change their state.

### Impact Explanation
A pool-NFT owner who is currently `FARMING_TO_POOL` and wants to leave the pool (or switch pools) via `pw_self_pool`/`pw_join_pool` can be permanently unable to do so in-process if the fee/coin-selection for the travel transaction fails once. Until the wallet service is restarted (which resets the in-memory `PoolWallet.target_state` dataclass field to its default `None`), the user cannot issue a corrective `self_pool`/`join_pool` call at all — every attempt is rejected client-side before any transaction is even built. Practically, this forces continued reward redirection to a pool the user no longer wants to be in, and blocks legitimate exit from pooling, which is exactly the class of "reward redirection / user locked out of exit" impact called out as in-scope for pool-NFT/plotnft transitions.

### Likelihood Explanation
This requires no special privilege — any wallet owner controlling a `PoolWallet` singleton can trigger it simply by calling `pw_self_pool` or `pw_join_pool` with a fee that momentarily exceeds their spendable balance (e.g., most funds are locked in pending transactions, in the singleton itself, or in unconfirmed coin selections), or by hitting any other exception path inside `generate_travel_transactions` before a spend bundle is queued. Given wallets commonly have multiple pending/unconfirmed transactions and fee estimation is user-supplied, this is an easily reachable, non-adversarial failure mode.

### Recommendation
Wrap the `self.target_state = ...` / `generate_travel_transactions(...)` sequence in `try/except`, resetting `self.target_state`, `self.next_transaction_fee`, and `self.next_tx_config` to their prior values on any exception, mirroring the cleanup already done in `apply_state_transition()`. Alternatively, only set `self.target_state` after `generate_travel_transactions` has successfully produced and queued the spend bundle.

### Proof of Concept
1. Create a `PoolWallet` in `FARMING_TO_POOL` state (via plot-NFT create + join).
2. Ensure the standard wallet has less spendable balance than the `fee` you are about to pass, or otherwise arrange `generate_signed_transaction` inside `generate_fee_transaction` to raise (e.g. concurrently lock coins in another pending spend).
3. Call `client.pw_self_pool(PWSelfPool(wallet_id=..., fee=<unaffordable_fee>, push=True))`.
4. Observe the RPC call fails with an "Insufficient funds" (or similar) error, but `PoolWallet.target_state` on the running wallet service is now set (assigned at `chia/pools/pool_wallet.py:705-707` before the failing call).
5. Retry `pw_self_pool` or `pw_join_pool` with a valid fee — observe it immediately fails with `"Cannot self pool when already having target state: ..."` / `"Cannot join a pool while waiting for target state: ..."` (`chia/pools/pool_wallet.py:633-634`, `684-685`), even though no transaction was ever broadcast, and this persists until the wallet service process is restarted.
