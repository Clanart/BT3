### Title
`TcParser::MpVerifyUtf8(const absl::Cord&, ...)` assumes UTF-8 transform is never requested for Cord-backed string fields, causing a reachable assertion failure (and validation bypass) - (File: `src/google/protobuf/generated_message_tctable_lite.cc`)

### Summary
The tail-call ("fast table") string parser for `ctype=CORD` fields passes the field's `xform_val` (transform/validation tag, e.g. `kTvUtf8`) into a Cord-specific UTF-8 verification helper whose `switch` statement has **only a `default` case** that unconditionally asserts `xform_val == 0`. When an ordinary client sends bounded, well-formed binary protobuf for a proto3 string field declared with `ctype = CORD`, the tag-dispatch fast path computes `xform_val = field_layout::kTvUtf8` (value `2`) and calls this helper, which trips `ABSL_DCHECK_EQ(xform_val, 0)`. This mirrors the CVE-2021-39157 pattern of "no case matches the produced value" being mishandled instead of properly branched on.

### Finding Description
`TcParser::MpString<is_split>` dispatches string fields by in-memory representation (`ArenaStringPtr`, `MicroString`, `Cord`) and, for each, calls an overload of `MpVerifyUtf8` to validate UTF-8 when required: [1](#0-0) 

For the `absl::string_view`/`ArenaStringPtr` and `MicroString` cases, verification correctly checks `xform_val == field_layout::kTvUtf8` and calls `utf8_range::IsStructurallyValid`: [2](#0-1) 

But the Cord overload never checks for `kTvUtf8` at all — its `switch` only contains a `default` label that asserts the value is always `0`: [3](#0-2) 

`kTvUtf8` is defined as `2 << kTvShift`, i.e. non-zero, and is exactly the value assigned to proto3 string fields requiring UTF-8 validation: [4](#0-3) 

Because `xform_val` is derived directly from the field's `type_card` in the (trusted, schema-generated) `TcParseTableBase`, and the *wire bytes* that route parsing into the `kRepCord` branch are fully attacker-controlled (an ordinary length-delimited string field on the wire), a proto3 message containing a `string` field with `ctype = CORD` will unconditionally route through `MpVerifyUtf8(const absl::Cord&, ...)` with `xform_val == kTvUtf8 (2)` whenever that field is present on the wire — the exact "value the invariant assumed could never occur" scenario. This is directly analogous to `detect-character-encoding`, where data that "matches no charset" (a case the code did not handle) crashed the process instead of being reported as an error.

### Impact Explanation
- In debug/assertion-enabled builds (`ABSL_DCHECK` active, e.g. under `-DNDEBUG` unset, ASAN/fuzzing builds, or CI/staging debug builds), an ordinary client sending a single length-delimited value for a `ctype=CORD`, proto3, UTF-8-validated string field via any public parse entry point (`ParseFromString`, `ParseFromArray`, `MergeFrom`, streaming `ParseFrom`) triggers `ABSL_DCHECK_EQ` failure, aborting the process — a remotely triggerable denial of service consistent with CWE-755 / the reported CVE's crash pattern.
- In release builds where `ABSL_DCHECK` compiles to a no-op, the function silently `return true`s without ever invoking `utf8_range::IsStructurallyValid` on the Cord contents — meaning UTF-8 validation is silently bypassed for `ctype=CORD` string fields, violating the proto3 "string fields must be valid UTF-8" invariant that the same code enforces for all other string representations. This is an integrity/soundness gap even where it does not crash.

### Likelihood Explanation
Any consuming application that (a) uses `ctype = CORD` on a proto3 `string` field (a valid, documented option) and (b) is built/tested with assertions enabled (common for OSS-Fuzz, sanitizer builds, and many CI/debug configurations) will hit this path on ordinary, valid-looking wire input from any untrusted client — no malformed encoding, huge payload, or schema tampering is required, only a normal length-delimited tag for that field number. This makes the assertion-failure path highly reachable in fuzzing/CI environments and the release-mode validation bypass unconditionally reachable in production whenever such a field is populated.

### Recommendation
Fix `TcParser::MpVerifyUtf8(const absl::Cord&, const TcParseTableBase*, const FieldEntry&, uint16_t xform_val)` to mirror the `absl::string_view` overload: branch on `xform_val == field_layout::kTvUtf8` and call `utf8_range::IsStructurallyValid` against a flattened/iterated view of the Cord's bytes, returning `false` (and logging via `PrintUTF8ErrorLog`) on invalid UTF-8, only falling into the assert-on-zero `default` path when `xform_val` is genuinely `0`. Add a regression test that parses a `ctype=CORD` proto3 string field with both valid and invalid UTF-8 payloads through the tail-call parser to confirm validation is enforced and no assertion is triggered.

### Proof of Concept
1. Define a proto3 message with a field using the Cord representation, e.g.:
```protobuf
syntax = "proto3";
message M {
  string s = 1 [ctype = CORD];
}
```
2. Build the generated code with assertions enabled (debug build / `ABSL_DCHECK` active).
3. Send a minimal valid wire payload for field 1, e.g. bytes `0x0A 0x01 0xFF` (tag=1, length-delimited, length 1, content `0xFF`) to `M::ParseFromArray`.
4. Parsing routes through `TcParser::MpString` → `kRepCord` branch → `MpVerifyUtf8(const absl::Cord&, ...)` with `xform_val == field_layout::kTvUtf8 (2)`, which falls to `default: ABSL_DCHECK_EQ(xform_val, 0);` and aborts the process in assertion-enabled builds.
5. In an NDEBUG/release build, the same call instead silently returns `true`, and the invalid UTF-8 byte `0xFF` is accepted into the Cord string field without validation, despite the field being declared with UTF-8 enforcement semantics — verifiable by inspecting `field.Get()`'s bytes post-parse against `utf8_range::IsStructurallyValid`.

I was not able to execute this build/test in this environment (index/search access only); the finding is based on direct code inspection of the cited lines and the `field_layout::kTvUtf8` constant definition confirming the value collision described above.
