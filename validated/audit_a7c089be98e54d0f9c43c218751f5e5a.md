### Title
Unchecked nil-account dereference in `EVMAddressDecorator.AnteHandle` can panic the ante pipeline - (File: `x/evm/ante/preprocess.go`)

### Summary
`EVMAddressDecorator.AnteHandle` looks up each Cosmos tx signer's account via `p.accountKeeper.GetAccount(ctx, signer)` and immediately calls `acc.GetPubKey()` without checking whether `acc` is `nil`. `AccountKeeper.GetAccount` is documented and implemented to return `nil` when the address has no stored account record, exactly the "call-assignment ... which could be null, and this value was later dereferenced without checking" pattern described in the CVE-2024-56666 analog.

### Finding Description
`EVMAddressDecorator.AnteHandle` iterates over every signer of an ordinary (non-EVM) Cosmos transaction: [1](#0-0) 
```go
for _, signer := range signers {
    if evmAddr, associated := p.evmKeeper.GetEVMAddress(ctx, signer); associated {
        ...
        continue
    }
    acc := p.accountKeeper.GetAccount(ctx, signer)
    if acc.GetPubKey() == nil {
        ...
```
`AccountKeeper.GetAccount` explicitly returns `nil` (a typed nil `types.AccountI`) when no account bytes are stored for the address: [2](#0-1) 

If a signer that has never been associated with an EVM address AND has no stored account record reaches this decorator, `acc` is `nil` and `acc.GetPubKey()` dereferences a nil interface value, causing a runtime panic. This decorator is wired into the standard Cosmos ante chain used for every non-EVM (Cosmos-native) transaction: [3](#0-2) 

### Impact Explanation
A panic thrown inside the ante handler during `DeliverTx`/`FinalizeBlock` for a block being processed is a consensus-critical crash: unhandled panics in ABCI message processing bring down the node process (or, if it occurs non-deterministically across validators depending on which accounts they've already indexed, can even contribute to consensus divergence). Because ante handlers run for every block-included transaction, a reliably triggerable nil dereference here would let an unprivileged transaction submitter halt or crash validator/full nodes — this fits the "validator halt" / "crash of default-configuration node" impact bucket allowed by the rules.

### Likelihood Explanation
The likelihood hinges on whether it is actually possible for a signer address in `sigTx.GetSigners()` to reach `EVMAddressDecorator` with no backing account record. In the same decorator chain, several earlier decorators (`ante.NewSetPubKeyDecorator`, `ante.NewValidateSigCountDecorator`, `ante.NewSigGasConsumeDecorator`, the sequential signature verification decorator, and `ante.NewIncrementSequenceDecorator`) also operate over `GetSigners()` and, in the standard Cosmos SDK pattern, typically require the account to already exist (erroring out via `GetSignerAcc` for unknown accounts) before signature/sequence processing succeeds. I was not able to fully inspect the body of `GetSignerAcc` in `sei-cosmos/x/auth/ante/sigverify.go` before running out of investigation budget, so I cannot conclusively confirm whether it always errors on a missing account (which would prevent this code path from ever seeing a nil `acc`) or whether some edge case (e.g., additional signers beyond the fee payer in a multi-signer/multisig transaction, or an account visible via `GetPubKeys()` returning a placeholder) can slip through with no account record. This is the key open question that determines whether this is practically exploitable versus a defensive-but-dead code path.

### Recommendation
Add an explicit nil check immediately after `p.accountKeeper.GetAccount(ctx, signer)` in `EVMAddressDecorator.AnteHandle` (`x/evm/ante/preprocess.go`), mirroring the safe pattern already used elsewhere in the codebase (e.g., `precompiles/auth/auth.go`'s `account` handler checks `if acc == nil`). If the account is nil, either create it (consistent with `SetAddressMapping`'s `NewAccountWithAddress` pattern) or skip pubkey-based EVM-address derivation for that signer gracefully instead of dereferencing.

### Proof of Concept
Could not be fully constructed without confirming the exact behavior of `GetSignerAcc` (`sei-cosmos/x/auth/ante/sigverify.go`) and other preceding decorators for a signer address with zero prior on-chain footprint (no balance, no account record, not EVM-associated) included as a secondary signer in a multi-signer Cosmos transaction. A background Devin session with test-execution access would be needed to construct and run such a transaction against `app.Setup`/ante-handler test harness (as used in `x/evm/ante/preprocess_test.go`) to confirm whether `acc` can in fact be `nil` at that call site.

// GetAccount implements AccountKeeperI.
func (ak AccountKeeper) GetAccount(ctx sdk.Context, addr sdk.AccAddress) types.AccountI {
	store := ctx.KVStore(ak.key)
	bz := store.Get(types.AddressStoreKey(addr))
	if bz == nil {
		return nil
	}

	return ak.decodeAccount(bz)
}
