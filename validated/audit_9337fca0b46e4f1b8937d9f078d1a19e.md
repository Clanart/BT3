### Title
Reward Sniping via Single-Block Staking Snapshot Lag - ([File: kaiax/staking/impl/getter.go])

### Summary
Kaia's reward-distribution module determines each validator's staking-reward share using a "StakingInfo" snapshot taken from a specific historical block. Before the Kaia hardfork this snapshot lags by a full `StakingInterval` (tens of thousands of blocks), but after the Kaia hardfork it lags by only **one block** (`sourceNum = num - 1`). Because deposits into a CN's staking contract are immediately reflected in that contract's native-token balance (which is what `StakingInfo.StakingAmounts` reads), a staker can inflate its staking balance right before the block that will be used as the reward source, capture a disproportionate share of that block's KIP-82 staking reward, and only afterward begin the (delayed) withdrawal process. This mirrors the "Rewards" front-running pattern in the external report, where a participant temporarily acquires eligibility (equip/stake) immediately before a reward-triggering event and drops it immediately after, at the expense of participants who held the position honestly the whole time.

### Finding Description
`kaiax/staking` documents and implements the snapshot-selection rule explicitly: [1](#0-0) 

For any block `num` after the Kaia hardfork, `sourceBlockNum` resolves to `num - 1`: [2](#0-1) 

`GetStakingInfo` then reads the AddressBook-registered staking contracts' balances directly from that historic block's state via the MultiCall contract, with no minimum holding period or vesting check: [3](#0-2) 

The staking amounts obtained from this single-block-old snapshot feed directly into the KIP-82/KIP-226 staker reward split performed during `FinalizeState()`: [4](#0-3) [5](#0-4) 

Reward shares are strictly proportional to the excess stake recorded at the snapshot block (`assignStakingRewards`), with no requirement that the funds have been staked for any minimum duration. Deposits into a `CnStakingV4` contract increase its balance immediately (a plain native-token transfer to the contract), while only *withdrawals* are subject to a lockup/approval delay (`STAKE_LOCKUP`, `approveStakingWithdrawal`, `withdrawApprovedStaking`): [6](#0-5) [7](#0-6) 

This asymmetry — instant deposit eligibility vs. delayed withdrawal — combined with the one-block reward-snapshot lag means a staker only needs its stake balance to be large at exactly the block preceding a reward-bearing block to claim an outsized share of that block's staker reward, exactly analogous to the equip-right-before/unequip-right-after pattern described in the external report for `Rewards.sol`.

### Impact Explanation
A staking-address operator (already an "unprivileged" staker persona reachable via the standard staking/reward-distribution path) can redirect a disproportionate share of the per-block staker reward pool (`Stakers` portion of `RewardSpec`, see `assignStakingRewards`/`assignStakingRewardsFlex`) to itself for a single block by depositing extra KAIA into its CN staking contract immediately before that block, diluting the rewards legitimately due to other long-term stakers. This is a reward-redirection issue within the scope of "staking and reward distribution" system components explicitly listed as in-scope.

### Likelihood Explanation
The likelihood is constrained by two factors that reduce (but do not eliminate) exploitability, mirroring the original report's "Acknowledged/low-severity" outcome:
1. Only entities that already control a CN staking address registered in the AddressBook (an existing staker) can execute this — not an arbitrary anonymous account.
2. Deposited capital used to inflate the snapshot cannot be withdrawn instantly (subject to `STAKE_LOCKUP` and the two-step `approveStakingWithdrawal`/`withdrawApprovedStaking` flow), so capital is temporarily locked, reducing profitability for small reward pools. However, no minimum staking duration is enforced before the funds count toward the reward-eligible balance, so profitability increases with block-reward size (large `MintingAmount` epochs) or coordinated timing around known high-fee blocks.

### Recommendation
- Require staking balances used for reward eligibility to be based on a time-weighted or multi-block average rather than an instantaneous one-block-old snapshot, restoring an economically meaningful minimum holding period (similar to the pre-Kaia `StakingInterval` behavior).
- Alternatively, require that the deposit itself be time-locked for at least one full staking interval before being counted towards `StakingAmounts`, symmetric with the existing withdrawal lockup.

### Proof of Concept
1. Actor controls a CN staking address `S` already registered in AddressBook with a modest existing stake.
2. At block `N-1`, actor sends a large KAIA transfer into `S`'s `CnStakingV4` contract, instantly increasing its on-chain balance.
3. `GetStakingInfo(N)` (called during `FinalizeState` for block `N`) resolves `sourceNum = N-1` and reads `S`'s inflated balance via `getFromStateByNumber` / `getFromState` (`kaiax/staking/impl/getter.go:48-179`).
4. `assignStakingRewards` (`kaiax/reward/impl/getter.go:486-534`) computes `S`'s excess-stake share using this inflated balance, granting `S` a proportionally larger cut of block `N`'s staker reward pool than its long-term stake would justify.
5. Actor later initiates `approveStakingWithdrawal` / `withdrawApprovedStaking` to retrieve the deposited KAIA once the `STAKE_LOCKUP` period elapses, having already captured the one-block reward.

func (s *StakingModule) GetStakingInfo(num uint64) (*staking.StakingInfo, error) {
	isKaia := s.ChainConfig.IsKaiaForkEnabled(new(big.Int).SetUint64(num))
	sourceNum := sourceBlockNum(num, isKaia, s.stakingInterval)

	// Try cache first
	if si, ok := s.stakingInfoCache.Get(sourceNum); ok {
		return si.(*staking.StakingInfo), nil
	}

	// Only before Kaia, try the database
	if !isKaia {
		if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
			s.stakingInfoCache.Add(sourceNum, si)
			return si, nil
		}
	}

	// Read from the state
	si, err := s.getFromStateByNumber(sourceNum)
	if err != nil {
		return nil, err
	}

	// Only before Kaia, write to database
	if !isKaia {
		WriteStakingInfo(s.ChainKv, sourceNum, si)
	}

	// Cache it
	s.stakingInfoCache.Add(sourceNum, si)
	return si, nil
}

func (r *RewardModule) FinalizeState(header *types.Header, state *state.StateDB, txs []*types.Transaction, receipts []*types.Receipt) error {
	if r.GovModule.GetParamSet(header.Number.Uint64()).ProposerPolicy == uint64(istanbul.WeightedRandom) && common.EmptyHash(header.Root) {
		qualified, err := r.ValsetModule.GetQualifiedValidators(header.Number.Uint64())
		if err != nil {
			return err
		}
		useRewardAddress := valset.NewAddressSet(qualified).Contains(r.NodeAddress)

		if rewardAddr := r.GetRewardAddress(header.Number.Uint64(), r.NodeAddress); useRewardAddress && rewardAddr != (common.Address{}) {
			header.Rewardbase = rewardAddr
			logger.Trace("Use reward address for nodeValidator", "header.Number", header.Number.Uint64(), "nodeAddress", r.NodeAddress, "rewardbase", header.Rewardbase)
		} else {
			logger.Trace("No reward address for nodeValidator. Use node's rewardbase.", "header.Number", header.Number.Uint64(), "nodeAddress", r.NodeAddress, "rewardbase", header.Rewardbase)
		}
	}

	spec, err := r.GetDeferredReward(header, txs, receipts)
	if err != nil {
		return err
	}
	if err := spec.Validate(); err != nil {
		return err
	}
	for addr, amount := range spec.Rewards {
		state.AddBalance(addr, amount)
	}
	return nil
}

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
}
