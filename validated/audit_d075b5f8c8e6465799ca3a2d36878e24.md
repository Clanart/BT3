### Title
Single-solver phantom price snapshot lets one bidder set the cross-chain FX rate used to size real settlements - (File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts)

### Summary
The Phantom snapshot mechanism computes a "liquidity-weighted median" price from all EIP-7702-delegated solver bids on a phantom order, and persists it as `PhantomOrderPriceSnapshot.medianPrice` [3](#0-2) . This snapshot is later read as the FX rate for pricing unrelated, real cross-chain orders (`quoteSnapshot` computes `amountOut = netAmountIn * medianPrice / standardAmount`) that become the actual `inputs`/`output.assets` of on-chain orders settled by `IntentGatewayV2`/V3 escrow [4](#0-3) . Nothing in the aggregation or the downstream consumer enforces a minimum number of independent solvers or bounds how far a single dominant bidder can move the price — the sole gate is `bidCount > 0` [5](#0-4) .

### Finding Description
`aggregatePhantomBids` collects every bid, verifies each is signed by an address delegated to the chain's `SolverAccount` [6](#0-5) , and reduces the surviving bids to `weightedMedian(quotes)`, where weight is the solver's own token balance [7](#0-6) . Becoming a "verified solver" is not gated by any protocol-level whitelist beyond delegating an EOA to the public `SolverAccount` contract and holding some balance of the output token — this is a permissionless role, not a privileged relayer/prover/admin. If only one solver (or one solver holding materially more of the output-token balance than genuine competitors) bids on a given phantom order's bid window, that single solver's `solverAmount` becomes the entire `medianPrice`, exactly as in the oracle report where compromising one price source lets an attacker "gain control of the median... setting it to a value between the lowest and highest values submitted." Downstream, `PhantomSnapshotIntentQuoteStrategy.validateSnapshot` only rejects a zero/negative price or `bidCount <= 0` — it never checks `bidCount` against a minimum diversity threshold, nor bounds `medianPrice` against any independent reference price [2](#0-1) . `getFxPriceFromSnapshots` in the indexer likewise consumes the most recent snapshot without a bid-count or agreement check [8](#0-7) . The resulting `amountIn`/`amountOut` are used verbatim to construct the real order that a user submits to `IntentGatewayV2`/V3, whose assets are escrowed and released on fill — i.e., the corrupted value (`medianPrice`) directly drives real fund movement, not just an off-chain display quote.

### Impact Explanation
An attacker who registers as a single Phantom solver (a normal, permissionless action — delegate an EOA to `SolverAccount` and fund it) can be the only or dominant bidder during a bid window and set `medianPrice` to any self-serving value. Because this snapshot then prices real USDC↔cNGN (and other configured Phantom pair) swaps for other users via the SDK's exact-input/exact-output quote math, the attacker can cause victims' orders to be priced far off the true market rate, transferring value to the attacker's own solver position at fill time. This satisfies "logic attacks" / "transaction manipulation" / wrong-amount settlement in the bounty scope, and does not require compromising any relayer, prover, or admin — only being an ordinary market participant with minimal liquidity during a window with no competing bids.

### Likelihood Explanation
Likelihood is meaningfully high for thin/new pairs or low-traffic windows: any bid window with a single active solver, or one solver with disproportionately larger `weight` (destination-chain balance) than the rest, degenerates the "weighted median" to that solver's own quote. The code's own comment acknowledges bids are permissionless and price-moving [1](#0-0) , and no minimum-solver-count or price-deviation guard exists anywhere in the pipeline (aggregation, indexer persistence, or SDK quote validation).

### Recommendation
Require a minimum number of *distinct, sufficiently weighted* solvers (e.g., ≥3, with no single solver's weight exceeding some fraction of total weight) before a `PhantomOrderPriceSnapshot` is considered valid for downstream pricing; reject or flag snapshots with `bidCount` below that floor instead of accepting `bidCount > 0`. Additionally, bound `medianPrice` against a slower-moving reference (e.g., a TWAP of prior accepted snapshots or an on-chain DEX price) and reject snapshots that deviate beyond a configured tolerance, mirroring the long-term recommendation in the original oracle report to make the aggregate value robust to partial/single-source compromise.

### Proof of Concept
1. Attacker generates an EOA, funds it minimally with the destination token (e.g., cNGN on Base), and EIP-7702-delegates it to the chain's public `SolverAccount` contract (same steps any legitimate solver takes, per `SolverAccountTest.sol` / `DeploySolverAccount.s.sol`).
2. Attacker watches for a Phantom order's bid window where no other solver has yet bid (or bids with a smaller balance than the attacker's), then submits a single bid quoting a heavily skewed `solverAmount` (e.g., far below fair value) via the standard `intents_getBidsForOrder`/UserOp submission flow used by `aggregatePhantomBids`.
3. When the bid window closes, `aggregatePhantomBids` counts this as the only/dominant verified bid; `weightedMedian` returns the attacker's own price as `medianPrice`, which `handlePhantomOrderPrices.handler.ts` persists into `PhantomOrderPriceSnapshot` [9](#0-8) .
4. A victim later calls `gateway.quoteIntent()` for an unrelated USDC→cNGN order; `PhantomSnapshotIntentQuoteStrategy.quote()` fetches this latest (single-bid) snapshot, passes `validateSnapshot` (only checks `bidCount > 0`), and computes `amountOut` using the attacker-set `medianPrice` [4](#0-3) .
5. The victim places a real order on-chain using this skewed `amountIn`/`amountOut`; when the same attacker (or a colluding solver) fills it, real escrowed funds settle at the manipulated rate, realizing a profit exactly analogous to Eve's median-skewing exploit in the oracle report.

// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing; if every weight is zero it falls back to the unweighted
// median so a price is still reported.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

async function isVerifiedSolverBid(params: {
	userOp: PackedUserOperation
	commitment: string
	sessionKey: HexString
	chainId: bigint
	solverAccount: string
	evmRpcUrl: string
	recoverSigner: RecoverBidSigner
	bidNonceKey: BidNonceKeyFn
	logger?: AggregationLogger
}): Promise<boolean> {
	const { userOp, commitment, sessionKey, chainId, solverAccount, evmRpcUrl, recoverSigner, bidNonceKey, logger } =
		params
	const solver = userOp.sender

	const parsed = splitBidSignature(userOp.signature)
	if (!parsed) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: malformed userOp signature")
		return false
	}

	// Cheap early-out ONLY. The prefix sits inside userOp.signature, which userOpHash excludes, so it
	// is attacker-mutable and must never be what binds a bid to an order — the nonce key below is.
	if (parsed.commitment.toLowerCase() !== commitment.toLowerCase()) {
		logger?.warn(
			{ solver, commitment, signedFor: parsed.commitment },
			"Rejecting phantom bid: signed for another order",
		)
		return false
	}

	// The authoritative binding, mirroring SolverAccount.validateUserOp on-chain. The nonce IS
	// covered by userOpHash, so a solver signature stays valid only for the (order, sessionKey) pair
	// its nonce key was derived from. `sessionKey` is read from the bid's own calldata, which is also
	// covered by userOpHash — so every operand here is signed, leaving nothing for a replay to swap.
	if (BigInt(userOp.nonce) >> 64n !== bidNonceKey(commitment as HexString, sessionKey)) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: nonce does not bind order and session key")
		return false
	}

	// SolverAccount._rawSignatureValidation recovers over the bare userOpHash and requires the signer
	// to be the account itself, which under EIP-7702 is the sender EOA.
	const signer = await recoverSigner(userOp, ENTRY_POINT_V08_ADDRESS, chainId, parsed.solverSignature)
	if (!signer || signer.toLowerCase() !== solver.toLowerCase()) {
		logger?.warn({ solver, commitment, signer }, "Rejecting phantom bid: signature does not recover to the sender")
		return false
	}

	if (!(await isDelegatedToSolverAccount(evmRpcUrl, solver, solverAccount))) {
		logger?.warn({ solver, commitment, solverAccount }, "Rejecting phantom bid: sender is not a delegated solver")
		return false
	}

	return true
}

		protocolFeeBps: bigint,
