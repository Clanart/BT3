### Title
Unbounded synchronous file read in DataLayer HTTP server enables symlink/large-file induced memory-exhaustion DoS - (File: chia/data_layer/data_layer_server.py)

### Summary
The CVE describes containers/storage reading a container-controlled file (`/etc/passwd`) without checking whether it is a symlink and without bounding read size, letting a malicious image redirect the read to an arbitrary host file and exhaust memory (OOM kill / hang). The same bug class — "open a filename that resolves through the filesystem and slurp its full contents into memory with no size bound, no symlink check" — is reachable in Chia's DataLayer static file server, `DataLayerServer.file_handler` / `folder_handler`.

### Finding Description
`DataLayerServer.file_handler` and `folder_handler` validate only the *shape* of the requested filename via `is_filename_valid()`, then build a path with `self.server_dir.joinpath(filename)` and do a fully synchronous, unbounded read: [1](#0-0) [2](#0-1) 

There is no `os.path.realpath`/symlink check on `file_path` before `open()`, and no size cap on `reader.read()`. Compare this to the peer-download path, `http_download()` and `S3Plugin.download()`, which both explicitly enforce `max_delta_file_size` before/while reading remote content: [3](#0-2) [4](#0-3) 

That size enforcement exists only on the *download/ingest* side. The *local write* side (`write_files_for_root` / `DataStore.write_tree_to_file`, invoked by `batch_update`) has no equivalent cap: [5](#0-4) 

A DataLayer store owner (an unprivileged local Data Layer client acting on their own singleton) can therefore locally insert an arbitrarily large batch of key/value pairs through the normal wallet-authorized `batch_update`/`insert_batch` flow, producing an oversized `.dat` full/delta file under `server_files_location` with no size ceiling. Any HTTP client that later requests that file via `GET /{filename}` or `GET /{tree_id}/{filename}` (the DataLayer HTTP server has no authentication) causes `file_handler`/`folder_handler` to read the entire file into a single in-memory `bytes` object before responding — mirroring the CVE's core defect of unbounded, unchecked file reads reachable via attacker-influenced file identity, resulting in memory exhaustion/OOM kill of the `data_layer_http` process (and potentially the host, per the cgroup/OOM behavior described in the CVE).

Additionally, unlike containers/storage's `/etc/passwd` case there is no explicit symlink dereference check anywhere in this read path (`open()` will transparently follow symlinks); if `server_files_location`'s directory tree could ever contain a symlink (e.g. from a misconfigured mirror-sync/plugin write path such as `S3Plugin.download`'s `target_filename` construction, which also lacks a symlink/realpath check before `mkdir`/download), a served "delta/full file" name could resolve outside the intended directory to an arbitrarily large host file, amplifying the same DoS.

### Impact Explanation
This is a Medium-severity, spend-triggered-adjacent DoS: it requires no compromised peer, no malicious node, and no elevated privilege — just (a) a Data Layer store owner performing a normal, authorized local batch update with large keys/values, and (b) any unauthenticated HTTP GET to the DataLayer file server. The result is unbounded memory allocation in the `data_layer_http` service process, causing it to hang or be OOM-killed, denying availability of the DataLayer mirroring/sync service to all subscribers of that store — directly analogous to the CVE's "hang and result in a denial of service via OOM kill" outcome.

### Likelihood Explanation
Likelihood is Medium: the write side is not artificially bounded (no `max_delta_file_size` enforcement on `write_files_for_root`), the HTTP server endpoints are open by design (they exist to serve files to arbitrary DataLayer subscribers), and no authentication or read-size guard exists in `file_handler`/`folder_handler`. The only requirement is that a legitimate store owner insert enough data in one batch (well within existing `insert_batch` limits, since no test enforces an upper bound at write time) and that any client request the resulting file.

### Recommendation
- Enforce the same `max_delta_file_size` limit used on ingest (`download_data.py`) when writing full/delta files (`write_files_for_root`/`DataStore.write_tree_to_file`), so files can never grow unbounded regardless of insert size.
- In `DataLayerServer.file_handler`/`folder_handler`, stream the response (e.g., `web.FileResponse` or chunked `StreamResponse`) instead of `reader.read()` into a single buffer, and enforce a hard maximum response size.
- Resolve `file_path`/`os.path.realpath()` and verify it stays within `self.server_dir` before opening, rejecting symlinks or paths that escape the configured directory, mirroring the fix pattern used for the containers/storage CVE (validate the target is a regular file inside the expected root before reading).

### Proof of Concept
1. As the owner of a DataLayer store, call `batch_update` via `DataLayerRpcApi` with a changelist containing keys/values sized to accumulate a very large total payload (e.g., many megabytes/gigabytes) in a single generation — `insert_batch`/`write_files_for_root` will happily write the resulting full/delta `.dat` file to `server_files_location` with no size check.
2. Confirm the corresponding root and file are published (`get_root`, file existence under `server_files_location`), as shown in the test harness pattern in `test_maximum_full_file_count`/`test_data_server_files`. [6](#0-5) 
3. From an unauthenticated client, issue `GET http://<host>:<dl_http_port>/{grouped_or_ungrouped_filename}` (or the `/{tree_id}/{filename}` route) matching the generated file name.
4. Observe `DataLayerServer.file_handler`/`folder_handler` load the entire oversized file into memory via `reader.read()` before responding, exhausting process memory and causing the `data_layer_http` service to hang or be OOM-killed. [1](#0-0)

    log: logging.Logger,
    max_delta_file_size: int,
) -> None:
    """
    Download a file from a server using aiohttp.
    Raises exceptions on errors
    """
    async with aiohttp.ClientSession() as session:
        headers = {"accept-encoding": "gzip"}
        async with session.get(
            server_info.url + "/" + filename,
            headers=headers,
            timeout=timeout,
            proxy=proxy_url,
        ) as resp:
            resp.raise_for_status()
            size = int(resp.headers.get("content-length", 0))
            max_delta_file_size_bytes = max_delta_file_size * 1024 * 1024
            if size > max_delta_file_size_bytes:
                raise MaxDeltaFileSizeExceededError(f"Maximum delta file size exceeded: {max_delta_file_size} MiB.")
            log.debug(f"Downloading delta file {filename}. Size {size} bytes.")
            progress_byte = 0
            progress_percentage = f"{0:.0%}"
            success = False
            try:
                with target_filename_path.open(mode="wb") as f:
                    async for chunk, _ in resp.content.iter_chunks():
                        f.write(chunk)
                        progress_byte += len(chunk)
                        if progress_byte > max_delta_file_size_bytes:
                            raise MaxDeltaFileSizeExceededError(
