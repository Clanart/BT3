### Title
Liquidation reverts when any position asset's Pyth confidence exceeds `max-confidence-ratio`, allowing under-margined positions to persist with no override path - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()` resolves USD prices for **every** enabled collateral/debt asset in the borrower's position before it even reaches the health check. Each resolution is gated by a global confidence-interval check (`check-confidence`) that hard-reverts if the Pyth confidence for *any* one asset exceeds a fixed BPS ratio of its price. Unlike a normal price-refresh flow, there is no way to bypass or override this gate for a liquidation call — if confidence stays wide (which is exactly what happens in volatile markets, the same conditions that make positions unhealthy), `liquidate()` reverts entirely and the under-margined position cannot be liquidated by anyone, mirroring the GTE-Perps finding where a price-quality gate blocks the risk-reduction path with no fallback.

### Finding Description
`resolve-pyth` unconditionally calls `check-confidence`, which reverts with `ERR-PRICE-CONFIDENCE-LOW` if the raw Pyth confidence interval is larger than `max-confidence-ratio` (default 10%) of the price: [1](#0-0) 

This check is invoked for every asset price via `price-resolve` → `resolve-price-feed` → `resolve-pyth`, and `price-resolve`'s failure propagates with `try!`: [2](#0-1) 

`liquidate()` calls `get-assets mask`, which resolves prices for **all** of the enabled collateral/debt assets tied to the borrower's egroup mask (not just the specific collateral/debt pair the liquidator is targeting) via `price-multi-resolve`/`iter-price-multi`, before any health check runs: [3](#0-2) [4](#0-3) 

If any single asset held by the borrower has a Pyth confidence interval currently above the configured ratio — which is precisely the condition that accompanies real market stress/volatility — `iter-price-multi` marks the fold `valid: false` and `price-multi-resolve` returns `ERR-ORACLE-MULTI`, which via `try!` aborts the entire `liquidate` transaction. The optional `price-feeds` parameter lets the liquidator push a fresher Pyth update in the same transaction, but it cannot fix the underlying confidence value the feed itself reports; if Pyth's own confidence remains wide, no caller-supplied update can satisfy the check. There is no code path in `liquidate` that bypasses `check-confidence` for the liquidation flow, and no alternate "backstop" liquidation mechanism exists in the contract at all.

### Impact Explanation
This blocks the sole liquidation path in the protocol precisely in the market conditions liquidation exists to handle (fast-moving/volatile prices, wide Pyth confidence intervals). An unhealthy position becomes un-liquidatable for as long as confidence stays wide, letting the borrower's LTV deteriorate further with zero recourse for liquidators or the DAO within `liquidate`. Continued deterioration risks the position going underwater (bad debt), which the protocol's own bad-debt-socialization path (`ERR-BAD-DEBT-SOCIALIZATION-FAILED`) exists to handle — i.e., losses eventually get pushed onto the lending pool/other suppliers, matching the "temporary freezing of funds" / insolvency-risk impact class, since collateral that should have backed the liquidator's repay-and-seize instead sits frozen behind a revert while debt accrues.

### Likelihood Explanation
Confidence widening on Pyth feeds correlates strongly with the exact volatile conditions that push LTVs above the liquidation threshold, so this is not a contrived edge case — it is the expected co-occurrence of "market moving fast" and "position needs liquidating." Because the gate applies globally to *every* asset in the borrower's mask (not just the pair being liquidated), even a single volatile collateral or debt asset in an otherwise liquidatable position is enough to block the whole call, making the blocking condition easy to hit incidentally without any attacker action.

### Recommendation
- For the liquidation path specifically, do not hard-revert the whole call on `ERR-PRICE-CONFIDENCE-LOW`; either allow liquidation to proceed using the last valid price with an explicit penalty/haircut, or apply a wider (documented) confidence tolerance for `liquidate` than for borrow/collateral-add.
- Alternatively, scope the confidence check to only the two assets actually involved in the liquidation call (`coll-aid`/`debt-aid`) rather than every asset in the position mask, so an unrelated asset's transient confidence spike cannot block liquidation of a genuinely unhealthy position.
- Add an explicit DAO/emergency override or a secondary liquidation path that can execute at a confidence-bounded/clamped price when the standard gate blocks execution, analogous to providing a backstop venue in the referenced report.

### Proof of Concept
1. Borrower holds collateral asset A and debt asset B; position LTV crosses `ltv-liq-partial`.
2. Market conditions turn volatile; Pyth's reported confidence interval for asset A (or B, or any other asset counted in the borrower's mask) exceeds `max-confidence-ratio` (10% of price).
3. A liquidator calls `liquidate(borrower, collateral-ft, debt-ft, debt-amount, ...)`.
4. Inside `liquidate`, `get-assets mask` → `price-multi-resolve` → `iter-price-multi` calls `price-resolve` for asset A, which calls `resolve-pyth` → `check-confidence`, which reverts with `ERR-PRICE-CONFIDENCE-LOW`.
5. `iter-price-multi` sets `valid: false`; `price-multi-resolve` returns `ERR-ORACLE-MULTI`; this propagates via `try!` and the entire `liquidate` transaction reverts before the health check or any collateral seizure occurs.
6. The position remains unliquidated and continues to accrue further downside for as long as confidence stays wide, with no override available within `liquidate`.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))

    ;; update timestamp if newer

        false)
