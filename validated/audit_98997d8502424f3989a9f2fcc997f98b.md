### Title
Unbounded loop in `object::root_owner()` allows permanent bricking of lazy module self-initialization via ordinary permissionless object-ownership cycles - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`object::root_owner()` walks an object's ownership chain with **no cycle/depth bound**, unlike its sibling `object::owns()` which explicitly caps traversal at `MAXIMUM_OBJECT_NESTING`. Ordinary, fully-permissionless `object::transfer` calls can create an ownership cycle (a self-loop in one call, or a 2/n-object cycle in two ordinary calls by the legitimate owner). `code::publish_package` and `init::assert_may_self_initialize` both call `root_owner()` as the authoritative check gating lazy module self-initialization for object-hosted modules. Once a cycle exists at a code object's address, every call to `root_owner()` for that address loops forever (aborts on gas exhaustion), permanently disabling the module-init safety gate for any module deployed there.

### Finding Description
`object::owns()` was deliberately hardened against ownership cycles: [1](#0-0) 

But `root_owner()`, added to support the newer lazy-module-initialization feature, has no such bound: [2](#0-1) 

Cycles are not merely theoretical — the framework's own test suite proves a self-loop can be created with a single ordinary, permissionless `transfer()` call (only the *second* attempt is rejected, because `verify_ungated_and_descendant` only rejects re-entering an *already-cyclic* graph, it does not prevent the first cycle-creating transfer): [3](#0-2) 

The same reasoning generalizes: two ordinary `transfer()` calls by the same legitimate owner (transfer A→B, then B→A) create a 2-object cycle, because `verify_ungated_and_descendant` only checks that the *signer* address appears somewhere in the destination's current owner chain — it never rejects the resulting graph itself for future traversals: [4](#0-3) 

`root_owner()` is used directly in the publish path to gate lazy module self-initialization — a security boundary specifically designed to stop a module from self-initializing after its hosting object changed owner: [5](#0-4) [6](#0-5) 

If the code-object address (or any ancestor in its ownership chain) is made part of a cycle, `assert_may_self_initialize`'s call to `root_owner()` never returns — the transaction runs out of gas instead of returning `true`/`false`. Every future call to `internal_maybe_initialize` (which is what the compiler injects for lazy `init_module` calls) for that module permanently fails, because the guard is evaluated unconditionally before allowing self-init: [7](#0-6) 

This is the direct structural analog of the external report's root cause: a privileged authorization check (`is_owner`/ownership-chain check) assumes a well-formed, acyclic ownership graph, and an actor with ordinary rights can construct a degenerate/cyclic graph that the check does not anticipate, breaking a security invariant (there: fund custody; here: the module-init/owner-change gate that is part of the object-code-deployment/publish trust model).

### Impact Explanation
This does not enable theft of funds or unauthorized code replacement, but it does permanently disable a **protected state-mutation gate** (module self-init authorization) tied directly to the publish/object-code-deployment flow. Any code object whose ownership chain becomes cyclic can never again pass `assert_may_self_initialize`, meaning `init_module`-style lazy initialization logic for that address is permanently and irreversibly bricked (denial of service on a specific, attacker-chosen on-chain object, achievable without any special privilege beyond ordinary object ownership). Given that `object_code_deployment`-based packages rely on this exact mechanism to authorize per-object self-init after upgrades/ownership changes, this breaks the "module-init ... failure that reaches protected state mutation" invariant called out as in-scope. Severity is bounded by the fact that it requires the address's own owner (or someone who controls a chain that includes it) to trigger the cycle — it is not exploitable by a fully unrelated third party against an unwilling code object owner.

### Likelihood Explanation
Creating the cycle requires only two ordinary, already-permitted `object::transfer` calls (or one self-transfer) — no bypass of any assertion is needed, and the object test suite itself demonstrates the first cycle-creating transfer succeeds. A malicious or curious integrator (or a dApp that manipulates a user's own object transfers, e.g. through a delegated/approved transfer flow) could easily trigger this against any object address that later needs lazy self-init, including addresses created via `aptos_framework::object_code_deployment::publish`.

### Recommendation
Bound `root_owner()`'s traversal the same way `owns()` is bounded, using `MAXIMUM_OBJECT_NESTING`, and either abort with a clear "cyclic ownership" error or return a defined value (e.g., the traversal depth cap) rather than looping unboundedly. Alternatively, prevent cycle formation at `transfer`/`transfer_raw_inner` time by checking the destination graph does not already lead back to the object being moved (not just checking `owner`'s presence in the *current* destination chain).

### Proof of Concept
1. `owner` creates object `A` via `object::create_object`; publishes a package at `A` via `object_code_deployment::publish` (or a plain object hosting a `code`-deployed module) with lazy module init enabled, so `code::publish_package` records `deploy_owner` via `root_owner(A)` (initially = `owner`).
2. `owner` creates a second object `B` (owned by `owner`).
3. `owner` calls `object::transfer(owner, A, B_addr)` — succeeds, `A.owner = B`.
4. `owner` calls `object::transfer(owner, B, A_addr)` — succeeds, because `verify_ungated_and_descendant` only needs to find `owner`'s address somewhere in `B`'s current chain (`B.owner == owner` still, pre-transfer), so the chain check passes and `B.owner = A` is set. Now `A.owner == B` and `B.owner == A`: a 2-cycle exists.
5. Any subsequent call that needs `root_owner(A)` (e.g., `internal_maybe_initialize` for a module hosted at `A`, or `assert_may_self_initialize` in `init.move`) loops forever between `A`↔`B` and aborts on gas exhaustion — self-initialization for the module at `A` is now permanently unreachable, confirmed structurally by the existing unit tests `test_cyclic_ownership_transfer_should_fail` / `test_cyclic_ownership_owns_should_fail` (which prove a one-step self-loop is achievable and that only `owns()`, not `root_owner()`, is protected against it): [3](#0-2)

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }

    /// Aborts unless the module at `addr` may self-initialize now. Only object-hosted modules are
    /// gated: an object must still have the transitive root owner recorded for this module at
    /// publish, so a transfer of the object or an ancestor, or its deletion, blocks self-init; an
    /// object with no record is fail-closed. Account addresses authorize their own code by publishing.
    fun assert_may_self_initialize(addr: address, module_id: ModuleId) {
        let recorded = recorded_deploy_owner(addr, module_id);
        let ok = if (recorded.is_some()) {
            object::is_object(addr)
                && recorded.destroy_some() == object::address_to_object<ObjectCore>(addr).root_owner()
        } else {
            !object::is_object(addr)
        };
        assert!(ok, error::permission_denied(EOWNER_CHANGED_SINCE_DEPLOY));
    }
