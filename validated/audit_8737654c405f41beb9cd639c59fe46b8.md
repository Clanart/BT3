### Title
`SignableTransaction::new` excludes the OP_RETURN data output from weight/fee calculation, so the signed transaction can pay less than the required fee rate and fail to relay - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The analog of "no slippage control" in Serai's in-scope code is `SignableTransaction::new` committing the caller to a transaction whose real fee rate is not bounded against the requested one. The function builds an OP_RETURN output from the caller-supplied `data` argument, but computes the transaction's weight/vbytes (and therefore `needed_fee`, the `TooLowFee` check, and the change output's value) solely from `payments`, omitting the OP_RETURN output entirely. The resulting signed transaction is larger than accounted for, so the actual fee rate is strictly below `fee_per_vbyte` — and can fall below `DEFAULT_MIN_RELAY_TX_FEE`, producing a transaction that pays less than intended and will not relay.

### Finding Description
In `SignableTransaction::new`, the caller-controlled `data` (up to 80 bytes, checked at line 171) is pushed as an OP_RETURN `TxOut` into `tx_outs` at lines 194-202. However, the fee and weight math at lines 204-235 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, ...)` — passing `payments`, not the full output set including the OP_RETURN. `calculate_weight_vbytes` (lines 62-127) reconstructs a transaction containing only `payments` plus optional `change`, so the OP_RETURN output (8-byte value + script length + up to ~83-byte scriptPubKey) is absent from the measured weight.

Consequences:

- `needed_fee = fee_per_vbyte * vbytes` (line 206) is computed on a vsize that excludes the OP_RETURN output, so the transaction's real fee rate is `(fee_paid) / (vbytes + ~93)` < `fee_per_vbyte`. There is no check that the achieved fee rate equals the requested one — the equivalent of missing slippage/bounds protection.
- The `TooLowFee` guard at lines 211-213 validates `needed_fee` against the *underestimated* `vbytes`, so a transaction that is actually below `DEFAULT_MIN_RELAY_TX_FEE` (i.e., non-standard, not relayed by default-policy nodes) passes validation when `fee_per_vbyte` is at the minimum.
- The change output value (lines 224-235) is `input_sat - payment_sat - fee_with_change`, where `fee_with_change` also excludes the OP_RETURN size — change absorbs only the under-charged fee, so the transaction silently pays less than the intended rate rather than failing.
- The `TooLargeTransaction` check (line 241) uses `weight` computed without the OP_RETURN output, so a transaction nominally under `MAX_STANDARD_TX_WEIGHT` can exceed it once the OP_RETURN is included.

This is reachable via public inputs: `data` is an arbitrary caller-supplied `Vec<u8>` fed to `SignableTransaction::new`, the exact API used to construct the transaction that `TransactionMachine` then FROST-signs (`processor` passes `None`, but the wallet API itself is in-scope and exposed to integrator/user-controlled data such as `Shorthand` payloads).

### Impact Explanation
A signed transaction whose effective fee rate is below the relay minimum will not propagate on the Bitcoin network; the inputs remain unspendable until a replacement plan is constructed and re-signed by the threshold group. For a threshold wallet, every sign attempt consumes a FROST signing session, and the produced transaction is unconditionally committed to via `Prevouts::All` (line 375) — the multisig signs whatever `SignableTransaction::new` built, with no post-hoc validation that the achieved fee matches `needed_fee`/`fee_per_vbyte`. The discrepancy is ~93 vbytes per OP_RETURN, which at boundary fee rates deterministically crosses the relay threshold; it also reduces change accuracy and can push weight past the standardness limit.

### Likelihood Explanation
The bug triggers deterministically whenever `data` is non-empty: the OP_RETURN output always exists in the final transaction but is never counted. Whether it causes non-relay depends on how close `fee_per_vbyte` is to the minimum; at 1 sat/vbyte (the typical default/minimum), ~93 uncounted vbytes means the transaction pays roughly 0 sat/vbyte effective over that portion, making `fee < DEFAULT_MIN_RELAY_TX_FEE * actual_vbytes / 1000` whenever `fee_per_vbyte` is within ~93/actual_vbytes of the minimum — easily satisfied for small transactions. Medium likelihood of a stuck/non-relayed transaction when `data` is used with low fee rates; the accounting error itself is certain.

### Recommendation
Include the OP_RETURN output in the fee/weight calculation. Either pass the fully-built `tx_outs` (or `payments` plus the OP_RETURN `ScriptBuf`) to `calculate_weight_vbytes`, or add the serialized size of the OP_RETURN output to the measured weight/vbytes before computing `needed_fee`, `fee_with_change`, and the `TooLowFee`/`TooLargeTransaction` checks. Additionally, after constructing the transaction, assert `self.fee() >= fee_per_vbyte * actual_vsize` as a slippage-style bound so the signed transaction provably achieves the requested fee rate.

### Proof of Concept
```rust
// networks/bitcoin: one input, no payments, 80 bytes of OP_RETURN data,
// fee_per_vbyte at the minimum relay rate.
let inputs = vec![output]; // a scanned ReceivedOutput
let data = vec![0u8; 80];

let tx = SignableTransaction::new(
    inputs,
    &[],                       // no payments
    None,                      // no change
    Some(data),
    1,                         // ~1 sat/vbyte, just above the TooLowFee check
).unwrap();

// tx is constructed and passes all checks, but the OP_RETURN TxOut
// (~93 vbytes) was excluded from `vbytes` at line 204, so:
//   actual_fee = needed_fee = 1 * vbytes_without_opreturn
//   actual_vsize = vbytes_without_opreturn + ~93
//   effective_rate = actual_fee / actual_vsize < DEFAULT_MIN_RELAY_TX_FEE / 1000
// The signed transaction is therefore non-standard and will not relay,
// even though SignableTransaction::new returned Ok.
```
