## Title
`SupportedStateMachines` boolean flag is ignored by `state_machine()` via `contains_key`, making `set_supported_state_machine(id, false)` a no-op that still admits proofs from a disabled chain - (`modules/ismp/clients/tendermint/src/pallet.rs`)

### Summary
The Tendermint consensus client pallet stores support status as `StorageMap<StateMachine, bool>` and exposes `set_supported_state_machine(origin, state_machine, supported)` which lets the admin flip an entry to `false` to disable a state machine [1](#0-0) . However, the only place this storage is consulted for enforcement — `TendermintClient::state_machine()` — checks `contains_key(id)` instead of reading the stored boolean value [2](#0-1) . Since `contains_key` is true regardless of whether the mapped value is `true` or `false`, calling `set_supported_state_machine(id, false)` does not disable anything; the machine remains fully "supported" for proof/state verification purposes. The only way to actually revoke support is `remove_supported_state_machine`, which deletes the key.

### Finding Description
`validate_state_machine` in ISMP core calls `consensus_client.state_machine(proof_height.id.state_id)` to obtain a `StateMachineClient` used to verify membership/non-membership and state proofs for requests, responses, and timeouts [3](#0-2) . For Tendermint-based chains, this dispatches to `TendermintClient::state_machine`, whose gate is:
```rust
if crate::pallet::SupportedStateMachines::<T>::contains_key(id) { ... } else { Err(...) }
``` [2](#0-1) 

The same pattern (`contains_key` ignoring the stored bool) also exists in the Arbitrum, Optimism, GRANDPA, sync-committee, and BEEFY clients' `state_machine()` implementations [4](#0-3) [5](#0-4) [6](#0-5) , but in those pallets the admin never inserts an explicit `false` value into `SupportedStateMachines` (their extrinsics only ever `insert(id, true)`), so the boolean-ignored behavior is dormant there. The Tendermint pallet is unique in exposing `set_supported_state_machine(id, supported: bool)` as the documented disable mechanism for admins, which makes the bug directly reachable: an admin who calls this with `supported: false` (e.g., in response to detecting a compromised or misbehaving Tendermint chain feeding state into `pallet_ismp_host_executive`-scoped governance parameters) believes the chain is disabled, but `contains_key` still returns `true`, so `state_machine()` keeps returning `Ok(...)`.

### Impact Explanation
After an admin "disables" a Tendermint-tracked EVM chain via `set_supported_state_machine(id, false)`, unprivileged relayers can still submit requests/responses/timeouts referencing that chain's state commitments; `validate_state_machine` will still succeed and membership/state proofs will still be accepted, because the enforcement check never actually looks at the `false` value. This is a false-state-acceptance condition: a chain the admin intended to cut off from the trust boundary continues to have its proofs honored, potentially settling governance-relevant state updates (host-executive parameters, module callbacks) from a source the admin explicitly tried to exclude. The unprivileged entry point is the proof/message submission itself; the admin's `false` call is only the (ineffective) mitigation attempt, not a precondition granting the attacker privilege.

### Likelihood Explanation
High, in the sense that it will always manifest whenever an admin uses `set_supported_state_machine(id, false)` as intended — the bug is deterministic, not probabilistic. It requires no attacker sophistication once the admin has (unknowingly) failed to disable the chain: any relayer can submit ordinary requests/responses/timeouts for that chain and they will be processed normally.

### Recommendation
Change all `state_machine()` implementations that read `SupportedStateMachines` to be value-aware, e.g. `SupportedStateMachines::<T>::get(id) == Some(true)` (or `.unwrap_or(false)`), instead of `contains_key`. For the Tendermint pallet specifically, this ensures `set_supported_state_machine(id, false)` actually disables the state machine, restoring parity between admin intent and enforced behavior. Add a regression test that inserts `false`, then asserts `state_machine()` returns `Err(...)`.

### Proof of Concept
1. Admin calls `TendermintClient` pallet's `set_supported_state_machine(origin, StateMachine::Evm(chain_x), false)`. Storage now has `SupportedStateMachines::<T>::get(Evm(chain_x)) == Some(false)`, and `contains_key(Evm(chain_x)) == true`.
2. Unprivileged relayer submits a `Request`/`Response`/`Timeout` message whose `proof_height.id.state_id == StateMachine::Evm(chain_x)`, with a valid membership/non-membership proof against a state commitment previously verified for `chain_x`.
3. `handlers::validate_state_machine` calls `consensus_client.state_machine(Evm(chain_x))` [3](#0-2) , which returns `Ok(Box::new(TendermintEvmStateMachine))` because `contains_key` is still `true` [2](#0-1) .
4. The proof is verified and the message is processed exactly as if the chain were still enabled, despite the admin's explicit `false` toggle — demonstrating the boolean is dead weight and `remove_supported_state_machine` is the only functioning disable path.

Note: I could not find any additional runtime-level wiring (e.g., in `parachain/runtimes/*`) that overrides or double-checks this flag before dispatch reaches `state_machine()`; if such a check exists elsewhere in code not covered by the index, it should be verified directly against the full repository.

	fn state_machine(&self, id: StateMachine) -> Result<Box<dyn StateMachineClient>, Error> {
		if crate::pallet::SupportedStateMachines::<T>::contains_key(id) {
			match id {
				StateMachine::Evm(_) => Ok(Box::new(TendermintEvmStateMachine::<H, T>::default())),
				_ => Err(Error::Custom("Unsupported state machine or chain ID".to_string())),
			}
		} else {
			Err(Error::Custom(alloc::format!("State machine not supported: {id:?}")))
		}
	}

pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
