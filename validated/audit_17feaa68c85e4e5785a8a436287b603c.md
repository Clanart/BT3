### Title
Discard-changes patch applied against working tree without re-validating current file state, allowing silent corruption of unrelated content - (`File: app/src/lib/git/apply.ts`)

### Summary
The Sherlock report's broken invariant is: *an action is executed based on an "expected" state (adaptor scale) computed at simulation time, but the actual on-chain state can drift before execution, and there is no check that the actual result matches what the user approved — so the user's committed value silently differs from what they intended.*

The closest unprivileged Desktop analog is `discardChangesFromSelection` in `app/src/lib/git/apply.ts`, which builds a `git apply` patch from an `ITextDiff` object that was computed at some earlier point (when the Changes list/diff viewer last refreshed), and applies that patch directly to the working directory with no re-verification that the file on disk still matches the diff that was used to build the patch. [1](#0-0) 

### Finding Description
`discardChangesFromSelection(repository, filePath, diff, selection)` takes a previously-computed `ITextDiff` (`diff`) and a user `DiffSelection`, converts them into a textual patch via `formatPatchToDiscardChanges`, and pipes that patch straight into `git apply --unidiff-zero --whitespace=nowarn -` against the live working tree (not `--cached`): [1](#0-0) 

`formatPatchToDiscardChanges` builds the hunk headers and content purely from the in-memory `diff.hunks` data and the `selection`, with no re-read of the file's current contents at apply time: [2](#0-1) 

The `diff` argument is fetched asynchronously via `getWorkingDirectoryDiff` at some point before the user acts (e.g., when a diff pane renders, or when a discard-selection dialog opens) and is then used later when the user confirms the discard action. If the working-directory file changes between diff computation and patch application — e.g., because a build tool, formatter, external editor, git hook, or a concurrent Desktop-triggered operation (checkout, pull, stash pop) touches the same file — the line numbers/content the patch expects to match no longer correspond to the file's real state. This mirrors the Tranche `issue()` bug exactly: the "expected" quantity (patch derived from an old diff) is used without verifying it still matches the current "scale" (actual file content) at execution time.

Unlike `git apply` used with full context normally, this call uses `--unidiff-zero`, which is intended for zero-context patches and disables Git's usual "fuzz" tolerance/context-matching leniency; this makes the command more likely to either fail outright on any mismatch or, in ambiguous cases, apply the change at the wrong location, since the patch is authoritative about exact line numbers rather than being re-derived from current content.

There is no lock, staged snapshot comparison, hash check, or "expected base content" assertion before applying — no analog to `--force-with-lease`'s remote-ref comparison exists here for the working-directory write path.

### Impact Explanation
If the patch is applied against a file whose content has drifted from the diff it was built against, `git apply` can either:
- Fail (denial of the discard action — recoverable), or
- Apply hunks at incorrect offsets/lines when there happens to be superficially matching context, corrupting file content that the user did not intend to change, and this corrupted state can subsequently be staged and committed/pushed by the user without them realizing the discard partially destroyed unrelated edits.

This satisfies "silent corruption of what the user commits or pushes" from the valid-impact criteria, since the user only asked to discard a specific selection of lines, not arbitrary nearby content.

### Likelihood Explanation
This requires the working directory file to change between the diff snapshot used to build the UI selection and the moment the user confirms the discard action — a real but narrower race window than typical git operations, since Desktop does not re-diff immediately before invoking `discardChangesFromSelection`. It does not require local/admin access, leaked credentials, or social engineering — only ordinary developer activity (autosave, formatter-on-save, build scripts, background git hooks) touching the file during the (however short) time the discard dialog/diff view is open. This is a lower-likelihood but plausible TOCTOU condition, consistent with a "Medium" severity classification similar to the original finding.

### Recommendation
Before applying the discard patch, re-fetch the current working-directory diff for the file (or at minimum re-read file content/hash) and verify it is unchanged from the diff snapshot used to build the patch; if it has changed, abort the discard and prompt the user to re-select, analogous to how `push` uses `--force-with-lease` to detect and reject stale expectations about remote state: [3](#0-2) 

### Proof of Concept
1. Open Desktop on a repo with a modified file, open the "Discard changes" partial-selection view for that file; this computes and caches an `ITextDiff` in the UI state.
2. Outside of the confirmation click (e.g., via an editor autosave, formatter-on-save hook, or a background process/git hook triggered by another Desktop action) modify the same file's lines that fall within the previously computed hunks, without Desktop's diff view refreshing.
3. Confirm the discard selection in the dialog; Desktop calls `discardChangesFromSelection` with the stale `diff` object: [1](#0-0) 
4. `git apply --unidiff-zero -` is executed against the now-different file content; depending on the divergence this either errors out or applies the reverse-hunk at incorrect positions, corrupting content the user never intended to discard, which can then be committed/pushed as-is.

Note: I was not able to fully verify, within the tool budget, the exact UI dispatch path (`app/src/ui/discard-changes/discard-selection-dialog.tsx`, `app-store.ts`, `dispatcher.ts`) to confirm precisely how long the diff snapshot is held before `discardChangesFromSelection` executes, or whether any intermediate re-diff/guard exists there. This should be checked in a full Devin session with complete file access before treating this as conclusively exploitable.

```typescript
export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
```

```typescript
export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true
      } else {
        if (line.type === DiffLineType.Add) {
          // An unselected added line will stay in the file after discarding the changes,
          // so we just print it untouched on the diff.
          oldCount++
          newCount++
          hunkBuf += ` ${line.text.substring(1)}\n`
        } else if (line.type === DiffLineType.Delete) {
          // An unselected removed line has no impact on this patch since it's not
          // found on the current working copy of the file, so we can ignore it.
          return
        } else {
          // Guarantee that we've covered all the line types.
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }
      }

      if (line.noTrailingNewLine) {
        hunkBuf += '\\ No newline at end of file\n'
      }
    })

    // Skip writing this hunk if all there is is context lines.
    if (!anyAdditionsOrDeletions) {
      return
    }

    patch += formatHunkHeader(
      hunk.header.newStartLine,
      newCount,
      hunk.header.oldStartLine,
      oldCount
    )
    patch += hunkBuf
  })

  if (patch.length === 0) {
    // The selection resulted in an empty patch.
    return null
  }

  return formatPatchHeader(filePath, filePath) + patch
}
```
