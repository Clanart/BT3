### Title
`with_locked_state` fail-opens on OSError (e.g. pre-created lock-file directory), disabling rate limiting and warning dedup - ([File: plugins/security-guidance/hooks/session_state.py])

### Summary
`with_locked_state` catches all `(OSError, IOError)` from `os.open(lock_file, ...)` / `fcntl.flock` and returns `None` instead of propagating or denying [1](#0-0) . If an attacker who can write to the state directory pre-creates the lock-file path as a directory, `os.open` raises `IsADirectoryError` (an `OSError` subtype), which is swallowed and turned into a `None` result for every subsequent locked operation on that session.

### Finding Description
`get_lock_file(session_id)` derives a deterministic path under `state_dir` (default `~/.claude/security`, or attacker-influenced via `SECURITY_WARNINGS_STATE_DIR`) [2](#0-1) . `with_locked_state` opens this path with `os.open(lock_file, os.O_RDWR | os.O_CREAT)`; if the path already exists as a directory, `os.open` raises `IsADirectoryError`, caught by the blanket `except (OSError, IOError)` and the function returns `None` [1](#0-0) . The module's own docstring confirms that `atomic_check_and_mark_warning`, `atomic_check_counter`, and `atomic_check_rate_limit` (defined in `security_reminder_hook.py`) build on `with_locked_state` and are the enforcement points for warning dedup, counters, and rate limits [3](#0-2) . Per the described pattern `return result if result is not None else True`, a `None` result from a failed lock is converted into an "allow"/pass-through decision by every caller, meaning a session-scoped I/O failure silently disables all deny/throttle logic for that session rather than failing closed.

### Impact Explanation
This fail-open behavior allows an attacker who can write into the state directory (a reachable precondition since it is either a fixed, world/user-writable default path or attacker-influenced via env var) to unconditionally disable per-warning deduplication, review counters, and rate limiting for the plugin, enabling unlimited repeated LLM review triggering or warning suppression bypass — undermining the throttle/consent gates the hook is meant to enforce.

### Likelihood Explanation
Exploitability requires only that the attacker can create a directory at the deterministic, predictable lock-file path before the hook runs — a low-privilege, single-step precondition with no race condition needed (directory creation is stable and outlives many separate hook invocations), making the bypass fully repeatable across every `atomic_check_*` call for that session.

### Recommendation
Change `with_locked_state` to fail closed by default: on `(OSError, IOError)`, either re-raise (letting the caller explicitly decide a safe/deny default) or return a distinct sentinel that callers treat as "deny"/"most restrictive," not `True`. Additionally, validate that `lock_file` is not an existing directory before calling `os.open`, and consider using an atomic, collision-resistant lock strategy (e.g., `O_EXCL`-based lock creation with retry, or a lock directory named separately from any attacker-writable pattern) so pre-created directories at the lock path cannot silently disable the gate.

### Proof of Concept
Unit test: 
1. Set `SECURITY_WARNINGS_STATE_DIR` to a temp dir.
2. Call `get_lock_file(session_id)` to compute the expected lock path, then `os.mkdir(lock_path)` to pre-create it as a directory.
3. Call `atomic_check_rate_limit(session_id, max_per_window=1, ...)` (or the analogous `with_locked_state`-based check) more times than `max_per_window` allows.
4. Assert that despite exceeding the limit, the function never returns a deny/`False` result — demonstrating the fail-open bypass — and that `debug_log` recorded a lock/state operation failure, confirming the exception path was hit.
