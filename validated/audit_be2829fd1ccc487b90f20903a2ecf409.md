### Title
Native CW20/CW721/CW1155 tokens sent to an EVM address's un-associated "cast" Sei address become permanently unclaimable once that EVM address later associates - ([File: x/evm/keeper/address.go], [File: utils/helpers/associate.go], [File: precompiles/wasmd/wasmd.go])

### Summary
Sei's dual-address model lets any EVM address be represented, before explicit association, by a "cast" Sei (bech32) address that is simply the raw 20 EVM-address bytes reinterpreted as an `sdk.AccAddress`. Any CosmWasm user can send CW20/CW721/CW1155 tokens directly to this cast address using ordinary wasm `execute` messages (`transfer`, `transfer_nft`, `send`, mint with `owner=castAddr`, etc.). This is exactly analogous to the reported bug class: value/ownership is tied to a specific *account*, and if that account later becomes an address nobody can actually sign for or reach, the tokens are permanently frozen — just as the Footium prize was tied to whichever account held the NFT at snapshot time.

### Finding Description
The EVM module resolves an unassociated Sei/EVM pair through a deterministic byte-cast fallback: [1](#0-0) [2](#0-1) 

This "cast address" is a syntactically valid bech32 Sei address, indistinguishable to any CW20/CW721/CW1155 contract from a normal account, and it can freely receive native Cosmos assets sent by any CosmWasm user (e.g. an NFT marketplace, airdrop, or direct transfer to that bech32 string).

There is no Cosmos secp256k1 keypair that maps to these bytes under the standard Cosmos address derivation (RIPEMD160(SHA256(pubkey))) — the bytes are only reachable because they equal the *Ethereum*-style keccak-derived EVM address. As a result, a plain Cosmos-signed `MsgExecuteContract` from the cast address is infeasible.

The only path back is through EVM: an EVM tx from the owning private key. However, the wasmd EVM precompile's `execute()` refuses to run unless the caller's EVM address is *already* formally associated with a Sei address, and it always resolves the sender to that associated ("true") address, never to the cast address: [3](#0-2) 

So:
1. Before association, any wasm `execute` call from the EVM side is rejected outright (`AssociationMissingErr`).
2. After association, `GetSeiAddress(caller)` returns the true Sei address, not the cast address — so the precompile can never act *as* the cast address.

Meanwhile, the association flow only migrates native bank (`usei`/wei) balances from the cast address to the true address — it explicitly does not touch CW20/CW721/CW1155 holdings, which live entirely inside the token contract's own storage keyed by the owner's bech32 string: [4](#0-3) 

The keeper code itself documents the cast address's receiving limitations (for bank coins) but does not address CosmWasm-native token ownership at all: [5](#0-4) 

Net effect: whatever CW20/CW721/CW1155 balance sits on the cast address is bound to an account nobody can ever act as, once (or even without) association occurs — a structurally identical failure mode to the Footium report, where value was tied to an *account* (here, the un-signable cast address) rather than to any mechanism that survives changes to who effectively controls that account.

### Impact Explanation
Any CW20 token amount, CW721 NFT, or CW1155 balance sent to the bech32-encoded cast form of an EVM address is permanently and unconditionally locked: it cannot be moved by a native Cosmos signature (no matching keypair) and cannot be moved via the EVM/wasmd precompile bridge (which requires prior association and then only ever authorizes the *associated* Sei address, never the cast one). This is a permanent freezing of user funds/assets, matching the "permanent freezing" impact bar.

### Likelihood Explanation
Reachable by an ordinary CosmWasm user: nothing prevents building or receiving a `MsgExecuteContract` `transfer`/`transfer_nft`/`send`/mint message whose recipient/owner argument is the bech32 form of any EVM address (this is a completely normal-looking Sei address string, and marketplaces, faucets, airdrops, and manual transfers routinely accept arbitrary bech32 recipients). No malicious validator, governance, or privileged action is required — an EVM user's own counterparties (or even the EVM user pre-association) can trigger the lock simply by using the cast address as a CW20/CW721/CW1155 destination.

### Recommendation
Extend the association migration logic (`AssociateAddresses`/`MigrateBalance` in `utils/helpers/associate.go`) to also sweep any CW20/CW721/CW1155 holdings recorded under the cast address to the newly associated true Sei address at association time (e.g. by iterating known pointer/registered token contracts, or by exposing a permissionless "migrate CW-native balance" entrypoint that any user can invoke for their own cast address). Alternatively, relax the wasmd precompile's association check so unassociated EVM callers can still act as their own cast address for wasm `execute` (mirroring `GetSeiAddressOrDefault` rather than the strict `GetSeiAddress`), and make sure this exemption survives association so previously-received tokens remain reachable.

### Proof of Concept
1. Attacker/observer learns `evmAddr` (any valid, unassociated EVM address, including one belonging to a normal user who has not yet interacted with Sei).
2. Compute `castAddr = bech32(sdk.AccAddress(evmAddr[:]))` — a syntactically valid Sei address.
3. As any CosmWasm user, execute a CW721 `mint`/`transfer_nft` (or CW20 `transfer`, or CW1155 `send`) with `owner`/`recipient` = `castAddr`.
4. The owner of `evmAddr` later associates their EVM address with their true Sei address, either explicitly via the `Associate` precompile (`precompiles/addr/.../associateAddresses`) or implicitly by signing any Cosmos/EVM tx.
5. `MigrateBalance` (in `utils/helpers/associate.go`) moves only `usei`/wei balances from `castAddr` to the true address; the CW721/CW20/CW1155 token remains owned by `castAddr` in the token contract's own state.
6. The owner now attempts to move the token: a native Cosmos tx signed as `castAddr` is impossible (no matching keypair), and calling the wasmd precompile's `execute()` from their EVM address resolves `senderAddr` to the true Sei address (per `precompiles/wasmd/wasmd.go` line 240), never `castAddr`. The token is permanently stuck.

// from an EVM address AND the originating EVM address has already been associated with

func (k *Keeper) CanAddressReceive(ctx sdk.Context, addr sdk.AccAddress) bool {
	directCast := common.BytesToAddress(addr) // casting goes both directions since both address formats have 20 bytes
	associatedAddr, isAssociated := k.GetSeiAddress(ctx, directCast)
	// if the associated address is the cast address itself, allow the address to receive (e.g. EVM contract addresses)
	return associatedAddr.Equals(addr) || !isAssociated // this means it's either a cast address that's not associated yet, or not a cast address at all.
}

func (p AssociationHelper) MigrateBalance(ctx sdk.Context, evmAddr common.Address, seiAddr sdk.AccAddress, migrateUseiOnly bool) error {
	castAddr := sdk.AccAddress(evmAddr[:])
	if castAddr.Equals(seiAddr) {
		return nil
	}
	var castAddrBalances sdk.Coins
	if migrateUseiOnly {
		castAddrBalances = sdk.Coins{p.bankKeeper.GetBalance(ctx, castAddr, "usei")}
	} else {
		castAddrBalances = p.bankKeeper.SpendableCoins(ctx, castAddr)
	}
	if !castAddrBalances.IsZero() {
		if err := p.bankKeeper.SendCoins(ctx, castAddr, seiAddr, castAddrBalances); err != nil {
			return err
		}
	}
	castAddrWei := p.bankKeeper.GetWeiBalance(ctx, castAddr)
	if !castAddrWei.IsZero() {
		if err := p.bankKeeper.SendCoinsAndWei(ctx, castAddr, seiAddr, sdk.ZeroInt(), castAddrWei); err != nil {
			return err
		}
	}
	if p.bankKeeper.LockedCoins(ctx, castAddr).IsZero() {
		p.accountKeeper.RemoveAccount(ctx, authtypes.NewBaseAccountWithAddress(castAddr))
	}
	return nil
}
