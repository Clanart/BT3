### Title
Missing `chain_id` and `verifying_contract` in EIP-712 Domain Enables Cross-Network and Cross-Deployment Replay of Aggregator Verification Signatures - (File: `core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

The `CLEMENTINE_EIP712_DOMAIN` used to authenticate aggregator-signed withdrawal approvals (`OptimisticPayoutMessage` and `OperatorWithdrawalMessage`) is constructed without a `chain_id` or `verifying_contract` field. A valid `verification_signature` produced for a withdrawal on one Citrea network or bridge deployment is cryptographically indistinguishable from one produced for another network or deployment that shares the same aggregator key, because the domain separator does not bind the signature to any specific chain or contract instance.

---

### Finding Description

`CLEMENTINE_EIP712_DOMAIN` is defined as:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

The EIP-712 standard explicitly provides `chainId` and `verifyingContract` fields in the domain separator to prevent cross-chain and cross-contract replay. Both are absent here. The two signed structs also carry no nonce:

```rust
struct OptimisticPayoutMessage {
    uint32 withdrawal_id;
    bytes input_signature;
    bytes32 input_outpoint_txid;
    uint32 input_outpoint_vout;
    bytes output_script_pubkey;
    uint64 output_amount;
}

struct OperatorWithdrawalMessage { /* identical fields */ }
``` [2](#0-1) 

The domain separator therefore reduces to `keccak256("ClementineVerification" || "1")` — a constant that is identical across every Citrea network and every bridge deployment.

The signature is verified in two places:

**Operator `withdraw` RPC** — checks `aggregator_verification_address` from config, recovers the signer from the EIP-712 hash, and rejects if it does not match: [3](#0-2) 

**Verifier `sign_optimistic_payout`** — same check before issuing a MuSig2 partial signature for the optimistic payout transaction: [4](#0-3) 

Both checks are gated on `aggregator_verification_address` being `Some(...)` in `BridgeConfig`: [5](#0-4) 

When the address is set (it is set by default), the signature is the **sole application-layer gate** that prevents an unauthorized party from triggering a withdrawal or causing verifiers to co-sign an optimistic payout transaction.

---

### Impact Explanation

**Cross-network replay**: If the same aggregator ECDSA key is used on Citrea testnet and mainnet (a common operational pattern), a `verification_signature` produced for a testnet withdrawal with parameters `(withdrawal_id=N, input_outpoint=X, output_script_pubkey=S, output_amount=A)` is valid on mainnet for any withdrawal that presents the same tuple. Because `withdrawal_id` is a simple `u32` counter and Bitcoin UTXOs can theoretically collide across networks (e.g., regtest/signet reuse), the domain-separator gap is a real cross-network replay surface.

**Cross-deployment replay**: If the bridge contract is redeployed (upgrade, migration) while the aggregator key is retained, every previously issued `verification_signature` remains valid against the new deployment. An attacker who captured a legitimate signature for a past withdrawal can replay it against the new deployment for any withdrawal that matches the same parameters, bypassing the manual-verification step the signature is meant to enforce.

**Downstream consequence**: A successfully replayed signature causes the operator to broadcast a payout transaction spending the operator's own Bitcoin UTXO (the withdrawal output) to an attacker-controlled address, and causes verifiers to issue partial MuSig2 signatures for an optimistic payout transaction that moves BTC out of the bridge vault — both without the aggregator having actually reviewed and approved the specific request.

---

### Likelihood Explanation

- The same aggregator key being reused across Citrea testnet/mainnet or across bridge redeployments is a realistic operational scenario.
- The attacker only needs to have observed one legitimate `verification_signature` (e.g., from a public testnet transaction or a prior deployment) and to find a matching `(withdrawal_id, input_outpoint, output_script_pubkey, output_amount)` tuple on the target deployment.
- The `withdrawal_id` is a monotonically increasing `u32`; low-numbered IDs will recur in any fresh deployment.
- No on-chain or DB-level "used signature" registry exists to detect replays.

---

### Recommendation

1. Add `chain_id` and `verifying_contract` to `CLEMENTINE_EIP712_DOMAIN`:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
    chain_id: CITREA_CHAIN_ID,           // bind to specific network
    verifying_contract: BRIDGE_CONTRACT, // bind to specific deployment
};
```

2. Add a per-request `nonce` (or timestamp) field to both `OptimisticPayoutMessage` and `OperatorWithdrawalMessage`, and track consumed nonces in the database to prevent replay of the same signature even within the same deployment.

3. Consider making `aggregator_verification_address` a required (non-`Option`) field in production configurations so the guard cannot be silently disabled.

---

### Proof of Concept

1. Deploy Clementine on Citrea testnet with aggregator key `K`. Process withdrawal `(id=1, utxo=X, script=S, amount=A)`. The aggregator signs and the operator broadcasts. The `verification_signature` `σ` is now public (e.g., visible in gRPC logs or captured by a network observer).

2. Deploy a fresh Clementine instance on Citrea mainnet (or a redeployed testnet contract) using the same aggregator key `K`. A new deposit creates withdrawal `(id=1, utxo=X', script=S', amount=A')`.

3. Craft a withdrawal RPC call to the mainnet operator with `(id=1, utxo=X, script=S, amount=A)` — the exact parameters from step 1 — and attach `σ`.

4. The operator calls `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>(...)` which computes `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)`. Because the domain contains only `name` and `version` (both identical across deployments), the hash matches and the recovered address equals `aggregator_verification_address`. The signature check passes.

5. The operator proceeds to `self.operator.withdraw(...)`, spending its own Bitcoin UTXO to the attacker-specified `output_script_pubkey` — a direct loss of operator collateral/reimbursement funds. [6](#0-5) [7](#0-6)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
