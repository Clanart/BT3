### Title
Reachable assertion in `Offer.__post_init__` on attacker-supplied offer bundle causes wallet-side crash - (File: chia/wallet/trading/offer.py)

### Summary
The libtiff CVE is a reachable-assertion bug: a crafted file drives execution to an `assert` that a benign input would never hit, aborting the process. Chia's `Offer` dataclass, constructed from a `WalletSpendBundle` embedded in an attacker-controlled offer file/string, contains the same anti-pattern: an unvalidated `assert` on attacker-controlled `CoinSpend` data inside `__post_init__`.

### Finding Description
`Offer.__post_init__` iterates the coin spends of the underlying `_bundle: WalletSpendBundle` and enforces uniqueness with a bare Python `assert`: [1](#0-0) 

```
for cs in self._bundle.coin_spends:
    # you can't spend the same coin twice in the same SpendBundle
    assert cs.coin not in adds
```

`_bundle` is a `WalletSpendBundle` supplied by the offer counterparty (parsed from the bech32m-encoded offer string / offer file that a wallet user receives and loads to inspect or accept a trade). Because `_bundle.coin_spends` is only "shape validated" at deserialization time — the trust boundary documented for this codebase states coin/puzzle/solution structures from peers are untrusted until real validation authority (mempool/consensus) checks them — nothing prevents an attacker from crafting an offer whose `SpendBundle.coin_spends` list contains the exact same `Coin` twice (same parent, puzzle_hash, and amount, just duplicated puzzle_reveal/solution entries) before the offer is ever run through mempool/consensus validation.

Constructing an `Offer` object (done by `TradeManager`/wallet RPC code when a user inspects or accepts an incoming offer, well before the resulting spend bundle is ever pushed to the mempool) calls `__post_init__`, which walks `_bundle.coin_spends` and hits `assert cs.coin not in adds` the moment a duplicate coin is present. This is a plain Python `assert`, not a `ValueError`/`ValidationError` raised through the normal error-handling path used elsewhere in the same function (e.g. `ValidationError` is explicitly caught/re-raised a few lines below for `compute_spend_hints_and_additions` failures), so the exception is an unhandled `AssertionError` propagating out of offer parsing.

### Impact Explanation
An `AssertionError` raised from `__post_init__` while merely parsing/inspecting an untrusted offer is not the same category of caught, application-level error as `ValidationError`; it can escape ordinary `try/except ValidationError` handling in RPC/CLI code paths that only expect validation-style exceptions, crashing the request handler or, depending on how the wallet daemon processes it, the RPC worker/task. Any single crafted offer file is enough — the attacker does not need funds, valid signatures, or mempool acceptance, only the ability to hand a malformed offer to a victim wallet (a classic offer-counterparty threat model explicitly in scope). This matches the CVE's "reachable assertion ... denial-of-service via a crafted file" pattern, mapped onto Chia's offer/trade flow instead of tiffcp.

### Likelihood Explanation
Likelihood is moderate-to-high: offers are routinely exchanged out-of-band (chat, marketplaces, files) and loaded by wallet users without prior validation; building a `SpendBundle` with a duplicated `Coin` entry among `coin_spends` requires no signature or on-chain state and no mempool admission, since the assertion fires during local object construction, prior to any consensus check.

### Recommendation
Replace the bare `assert cs.coin not in adds` in `Offer.__post_init__` with an explicit check that raises `ValidationError` (or another handled exception type), consistent with the rest of the method's error handling for malformed offers, so malformed/duplicate-coin offers are rejected gracefully instead of raising an unhandled `AssertionError`. More broadly, audit other `assert` statements that operate directly on attacker-supplied `SpendBundle`/`CoinSpend` data reachable before consensus validation (e.g., similar patterns in `chia/full_node/mempool_manager.py`) and convert them to typed validation errors.

### Proof of Concept
1. Construct a `WalletSpendBundle` whose `coin_spends` list contains two `CoinSpend` entries that reference the identical `Coin` (same `parent_coin_info`, `puzzle_hash`, `amount`) — e.g. by duplicating one entry from a legitimately generated offer bundle.
2. Encode this bundle as the `_bundle` of an `Offer` together with arbitrary `requested_payments`/`driver_dict`, and produce the corresponding offer string/file the way `Offer.to_bech32m`-style serialization does.
3. Have a wallet user load the offer (e.g., via `chia wallet check_offer_validity`/`take_offer`/`get_offer_summary`-style RPC handlers in `TradeManager`, all of which build an `Offer(...)` object from the parsed bundle).
4. Observe that `Offer.__post_init__` raises an unhandled `AssertionError` at `assert cs.coin not in adds` [2](#0-1)  instead of a handled `ValidationError`, terminating/erroring the wallet's offer-processing call.
