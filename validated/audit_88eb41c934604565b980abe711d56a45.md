The link interceptor at `sandboxed-markdown.tsx` correctly gates markdown link clicks to `https?:` before invoking `onMarkdownLinkClicked`, but the actual enforcement point — the main-process IPC handler — does not re-validate the scheme; it only inspects it for logging.

### Title
Improper Validation of `open-external` Scheme Allows Attacker-Controlled Content to Reach `shell.openExternal` Unrestricted - (File: `app/src/main-process/main.ts`)

### Summary
The main-process `open-external` IPC handler checks whether a URL starts with `http://`/`https://` only to decide what to log, then unconditionally forwards the raw string to Electron's `shell.openExternal()`. [1](#0-0)  This mirrors the `create2`/`iszero(result)` bug class: a check exists and looks like a gate, but it never actually blocks the unsafe path — it is observational, not enforcing.

### Finding Description
Renderer-side callers assume the scheme has been validated before an external open happens. `SandboxedMarkdown.setupLinkInterceptor` — the component used to render attacker-influenced content such as PR bodies, commit messages, and comments fetched from the GitHub API — only forwards a link to `onMarkdownLinkClicked` when `/^https?:/.test(a.protocol)` holds. [2](#0-1)  That callback ultimately calls `shell.openExternal(url)` via `_openInBrowser`/`app-shell.ts`. [3](#0-2) [4](#0-3) 

However, this renderer-side gate is not the only path to `shell.openExternal`. Any code with access to the exposed `openExternal` IPC bridge (`main-process-proxy.ts` → `ipcRenderer.invoke('open-external', path)`) can call the main-process handler directly, and other call sites (`LinkButton`, `openFile`, release notes, install-git dialogs, editor-error dialogs, etc.) invoke `shell.openExternal` with strings that are not necessarily scheme-restricted the same way the markdown interceptor is. Because the actual boundary — the main-process handler — performs no scheme allow-listing (`iszero(result)`-style superficial check), any of these other paths, or a future/careless caller, can pass a `file://`, `javascript:`, custom-protocol, or Windows UNC-style path straight through to `shell.openExternal`. Electron's `shell.openExternal` has a documented history of scheme-smuggling issues (e.g., crafted `file://` UNC paths executing remote scripts on Windows, or invoking arbitrary registered protocol handlers) precisely because callers are expected to validate the scheme before invoking it — which is exactly the guard that is missing here.

The core corrupted invariant: the value trusted to be "already validated as http/https" (the `path` argument reaching `shell.openExternal` in the main process) is never actually re-checked at the point of use; the existing `startsWith` check only gates a `log.info` call, not the `shell.openExternal` call itself.

### Impact Explanation
If any attacker-influenced string (a PR/commit/comment body rendered as markdown, a GitHub API field surfaced in the UI, or a crafted deep link) reaches `shell.openExternal` with a non-http(s) scheme, the impact ranges from opening arbitrary local files/applications to invoking OS-level protocol handlers, which in the worst case leads to code execution outside the sandbox (the classic Electron `openExternal` RCE class) — squarely within the accepted impact categories (renderer-sandbox escape / code execution via a link the user clicks on attacker-controlled content).

### Likelihood Explanation
Likelihood is moderate: the primary renderer-side markdown interceptor does correctly filter to `https?:` today, so the main practical exposure is (a) any other/future caller of the shared `open-external` IPC channel that does not replicate that filtering, and (b) the fact that the enforcement boundary (main process) trusts the renderer completely instead of independently validating. Because Electron's security model explicitly recommends validating untrusted input at the process boundary (main process), relying solely on renderer-side checks is fragile — a single missed call site anywhere in the large UI surface (dialogs, notifications, quick-view, copilot conflict dialogs, etc., all of which use `shell.openExternal`) reintroduces the vulnerability, exactly like the `create2` case where relying on the wrong signal (`result != 0`) instead of the correct one (`extcodesize(result) != 0`) fails silently.

### Recommendation
Move the scheme validation into the main-process `open-external` handler itself, mirroring the `extcodesize` fix pattern of validating at the actual enforcement point rather than trusting an upstream check:
```ts
ipcMain.handle('open-external', async (_, path: string) => {
  const protocol = safeParseProtocol(path) // e.g. new URL(path).protocol
  if (protocol !== 'http:' && protocol !== 'https:' && protocol !== 'mailto:') {
    log.warn(`Refusing to open external path with disallowed protocol: ${path}`)
    return false
  }
  ...
})
```
This ensures every caller of `openExternal` — present and future — is protected by a single, authoritative allow-list at the trust boundary, instead of depending on each renderer call site independently reimplementing the same `/^https?:/` check.

### Proof of Concept
1. Locate any UI surface that passes a string to `shell.openExternal`/`dispatcher._openInBrowser` without first checking its scheme (e.g., a future notification/dialog, or a modified/compromised renderer script, or a bypass of the `a.protocol` check in `sandboxed-markdown.tsx` via markdown/HTML that DOMPurify + `marked` fail to neutralize into an `<a>` tag with a non-`http(s)` `href`, such as a data: or malformed scheme that the browser's `URL`/anchor parsing normalizes differently than expected).
2. Trigger that code path with an attacker-controlled value coming from repository/PR/API content (e.g., a link in a PR description).
3. Observe that `ipcMain.handle('open-external', ...)` at [1](#0-0)  forwards the value directly to `shell.openExternal` with no protocol allow-list — the `pathLowerCase.startsWith(...)` check only affects logging, so a `file://`, custom-protocol, or UNC-path string is passed through unfiltered.
