### Title
Lack of Slippage Protection in `WombatPoolHelperV2.depositFor()` - ([File: wombat/WombatPoolHelperV2.sol])

### Summary
`WombatPoolHelperV2.depositFor()` hardcodes the `_minimumLiquidity` parameter to `0` when forwarding a user's deposit to `WombatStaking.deposit()`, completely disabling slippage protection for any unprivileged wallet using this entry point, unlike the sibling `deposit()` function which lets the caller supply a real minimum.

### Finding Description
`deposit(uint256 _amount, uint256 _minimumLiquidity)` correctly forwards a caller-supplied minimum liquidity value into `_deposit`, which is passed through to `WombatStaking.deposit()` and ultimately to the underlying Wombat AMM pool's `deposit()` call that enforces `minimumLiquidity` against the actual LP/liability computed at execution time. [1](#0-0) 

However, `depositFor(uint256 _amount, address _for)` — a fully public, unprivileged function that pulls `depositToken` from `msg.sender` and stakes on behalf of `_for` — calls `_deposit(_amount, 0, _for, address(this))`, hardcoding the minimum liquidity to zero: [2](#0-1) 

The `_deposit` internal helper then relays this zero minimum straight into `IWombatStaking(wombatStaking).deposit(...)`: [3](#0-2) 

`WombatStaking.deposit()` in turn forwards the caller-supplied `_minimumLiquidity` unmodified to the Wombat pool's `deposit()` call, which mints `receiptToken` 1:1 with the actual `lpReceived` computed from the pool's live cash/liability ratio at execution time: [4](#0-3) 

Because Wombat pool LP minting depends on the pool's amplification-factor-based liability/cash curve (visible in the mock's `exactDepositLiquidityInEquilImpl`), the LP output for a given deposit amount can vary with pool state changes between transaction submission and inclusion — the same class of AMM-style value dependency the ERC4626 report warns about for `previewDeposit`/`previewMint`. With `_minimumLiquidity` forced to `0`, `depositFor()` provides no revert condition regardless of how unfavorable the executed rate is. [5](#0-4) 

### Impact Explanation
Any unprivileged wallet calling `depositFor()` (e.g., integrators, contracts routing deposits on behalf of users, or users depositing for another address) receives whatever `receiptToken`/staked amount results from the live pool state with zero floor protection. A sandwich attacker can manipulate the Wombat pool's cash/liability ratio immediately before the deposit transaction executes and restore it after, extracting value at the depositor's expense — a direct, quantifiable loss of user funds with no way for the transaction to revert even under maximal adverse execution.

### Likelihood Explanation
`depositFor()` is a public, unauthenticated entry point requiring only a normal ERC20 approval — no privileged role is needed to trigger it, and it is reachable in the same call path used for legitimate normal deposits (e.g., by any contract or wallet depositing on behalf of another address). Any transaction hitting the public mempool is sandwichable, making exploitation practical whenever meaningful deposit sizes pass through this function.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor(uint256 _amount, address _for, uint256 _minimumLiquidity)` and forward the caller-supplied value instead of hardcoding `0`, mirroring the protection already present in `deposit()`.

### Proof of Concept
1. Attacker observes a pending `depositFor(amount, for)` transaction in the mempool.
2. Attacker front-runs it with a transaction that skews the target Wombat pool's cash/liability ratio unfavorably for deposits (e.g., large withdrawal or swap increasing pool imbalance).
3. The victim's `depositFor` executes with `_minimumLiquidity = 0`, so `IWombatPool.deposit()` succeeds regardless of the resulting `lpReceived`/`liabilityToMint`, minting fewer `receiptToken`/staking shares than the user would have received under normal pool conditions. [6](#0-5) 
4. Attacker back-runs to restore the pool state and pocket the value difference extracted from the victim's deposit, while `deposit()` callers supplying a real `_minimumLiquidity` would have reverted instead.
