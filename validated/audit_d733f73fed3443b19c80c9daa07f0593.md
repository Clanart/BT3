I found the vulnerable analog. The `evm/tron/contracts/apps/IntentGatewayV2.sol` `withdraw()` function contains the identical structural flaw as the reported bug: it decrements internal escrow accounting by a fixed `amount` while trusting a raw `token.call` transfer to actually deliver that exact amount, with no balance-based verification of what was actually sent versus what was recorded.

### Title
Escrow Accounting Desync on Fee-on-Transfer / Non-Standard Tokens in Tron `IntentGatewayV2.withdraw()` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` implements `withdraw()` using raw low-level `token.call(transfer(...))` and unconditionally decrements `_orders[commitment][token] -= amount` by the full nominal `amount`, without ever measuring the token's actual balance delta the way the mainline EVM `IntentGatewayV2.placeOrder` (and the `IntentsBase._withdraw`) careful pattern does elsewhere in the same codebase. This mirrors the `VestedStaking` USDT bug class: accounting state is derived from an assumed transfer amount instead of the observed balance effect of the transfer.

### Finding Description
Contrast the two escrow-release implementations in this repo:

- The canonical `IntentsBase._withdraw` (evm/src/apps/intentsv2/IntentsBase.sol) uses `SafeERC20.safeTransfer`, which reverts on failure, and treats `amount` as ground truth for accounting. [1](#0-0) 

- The Tron fork's `withdraw()` instead performs a raw `.call` and only checks the boolean success flag, then blindly does `_orders[body.commitment][token] -= amount`: [2](#0-1) 

For a fee-on-transfer or deflationary/rebasing token registered as an intent input, `token.call(transfer(beneficiary, amount))` can return `true` while the beneficiary actually receives less than `amount` (the fee is burned or redirected). The contract still deducts the full `amount` from `_orders[commitment][token]`, silently under-crediting the true remaining escrow relative to the token's real balance held by the contract. This is exactly the report's root cause: measuring/assuming a transfer effect instead of computing it from actual balance deltas (`balanceOf` before/after). The same file's `placeOrder` path (inherited from the shared `IntentGatewayV2.sol`) *does* protect against this on the deposit/inflow side by measuring `balanceOf(address(this))` before and after `safeTransferFrom`, e.g.: [3](#0-2) 
but the Tron `withdraw()` outflow path has no equivalent balance-verification, breaking the invariant that escrow bookkeeping must match actual token custody.

### Impact Explanation
Because escrow amounts are computed on the source chain from the deposit's *actual received* balance (fee-on-transfer-aware), but released on withdrawal using a raw call without any balance check, a fee-on-transfer or non-standard ERC20/TRC20 registered as an intent token creates a mismatch between the contract's real token balance and its internal `_orders` ledger. Over repeated fills/refunds this can leave residual real balance stuck (permanently locked funds, since `_orders[commitment][token]` reaches zero before the physical balance does), or — depending on rounding/timing across concurrent partial withdrawals of the same commitment — allow the internal accounting to diverge from custody in a way that a subsequent claim against the same commitment sees a nonzero `_orders` entry that no longer corresponds to real backing, risking fund loss for whichever party is paid last. This directly hits the bounty's "loss of funds" / "logic attack" / "transaction manipulation" categories in bridge custody of escrowed order inputs.

### Likelihood Explanation
This requires the intent order to use a token exhibiting fee-on-transfer, deflationary burn, or otherwise non-1:1 transfer semantics as an input/output asset. No malicious relayer, prover, or admin is needed — any ordinary intent-gateway user or solver interacting with such a token via `placeOrder`/`fillOrder`/`onAccept` triggers the discrepancy. Given the codebase explicitly documents and tests fee-on-transfer handling for the deposit side (`testPlaceOrder_FeeOnTransferToken_*` in `IntentGatewayV2SameChainTest.sol`) but the Tron withdraw path lacks the analogous protection, this is a concrete, provable gap rather than a hypothetical.

### Recommendation
Apply the same before/after balance-delta pattern used in `placeOrder` to the Tron `withdraw()` function: read `token.balanceOf(beneficiary)` (or `address(this)`) before the transfer, perform the transfer, and derive the actually-moved amount from the balance delta before decrementing `_orders[commitment][token]`. Alternatively, standardize on `SafeERC20.safeTransfer` plus an explicit pre/post balance check, consistent with `evm/src/apps/intentsv2/IntentsBase.sol` and `evm/src/apps/IntentGatewayV2.sol`, so that both the deposit and withdrawal legs of escrow accounting are anchored to observed token balances rather than assumed transfer amounts.

### Proof of Concept
1. Register a fee-on-transfer TRC20 token (e.g., 1% burn on transfer, mirroring the `FeeOnTransferToken` test helper already in the repo's Foundry tests) as an intent input on the Tron gateway.
2. Call `placeOrder` with `inputAmount = 1000`; the deposit side correctly measures actual received (e.g., 990) and escrows `990` — matches `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`.
3. Have a solver fill the order, triggering `withdraw(body, false)` with `amount = 990` (the full escrowed value).
4. `token.call(transfer(beneficiary, 990))` executes the token's `_transfer`, which burns 1% (≈9), so beneficiary receives only ≈981, but `_orders[commitment][token] -= 990` sets escrow to `0` regardless.
5. Compare contract's real token balance vs. zeroed-out internal accounting: the gateway now shows zero escrow for this commitment, but if a partial-fill or duplicate withdrawal path is reachable before the ledger is fully zeroed (e.g., a second `withdraw` call racing on the same partially-settled commitment, or a follow-on `SweepDust`/fee-release that assumes accounting matches balance), funds accounting is desynchronized from actual custody — the discrepancy (≈9 units per such transfer) accumulates and is unrecoverable through normal escrow flows, matching the "logic attack leading to fund loss" impact class.
