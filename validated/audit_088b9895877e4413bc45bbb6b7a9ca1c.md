## Title
Fee-accumulation batch can be front-run and split, diverting relayer fees away from the signed beneficiary - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`Pallet::accumulate` (invoked via the unsigned extrinsic `Relayer::accumulate_fees`) processes a `WithdrawalProof` batch of request commitments and an optional `beneficiary_details = (beneficiary_address, signature)` that redirects the accrued fee to a third-party address. The signature only commits to `(nonce, state_machine, beneficiary_address)` — it does **not** bind to the specific `commitments` in the batch. Because `accumulate_fees` is a permissionless, unsigned extrinsic built entirely from publicly verifiable state proofs, anyone observing a pending redirect transaction in the mempool can independently construct and submit a *subset* of the same commitments (without any `beneficiary_details`) and land it first, exactly like the `executePayroll()` split-transaction pattern.

### Finding Description
`accumulate()` [1](#0-0)  filters out already-claimed commitments before doing anything else, and requires the remaining set to be non-empty. The beneficiary redirection signature only covers `(nonce, dest_chain, beneficiary_address)`: [2](#0-1) 

Because the signed message never references `withdrawal_proof.commitments`, the redirect authorization is not scoped to the exact batch the relayer intended to sweep. Since `source_proof`/`dest_proof` are Merkle/state proofs over public chain data, any third party can independently build a valid `WithdrawalProof` for **any subset** of the same commitments and submit it as `accumulate_fees` with `beneficiary_details = None`.

If that front-run transaction lands first:
- The subset of commitments get marked `claimed = true` and their fees are credited to `delivery_address` (the relayer's own on-chain identity derived from the destination receipt) instead of the intended `beneficiary_address` [3](#0-2) .
- When the original (legitimate, beneficiary-redirecting) transaction subsequently executes, its `commitments` list has those entries filtered out as already claimed [4](#0-3) . If *all* commitments in the batch get front-run this way, the whole call reverts with `MissingCommitments`, forcing the relayer to reconstruct and resubmit a new proof — mirroring the "original tx fails and must be rescheduled" failure mode in the payroll report. If only some commitments are front-run, the relayer's intended beneficiary silently receives less than expected while the split-off fee lands on `delivery_address`.

This is structurally the same broken invariant as the `executePayroll()` report: a batch of value-moving operations is executed via multiple independently-provable sub-transactions rather than atomically, and the authorization (nonce/signature) does not bind to the exact set being executed, so a third party can partially execute the batch ahead of the original submitter, corrupting the outcome (wrong beneficiary gets funds) or forcing costly resubmission.

### Impact Explanation
This falls under "transaction manipulation" and "wrong beneficiary or amount": the relayer's explicit choice to redirect fees to a chosen beneficiary can be defeated (partially or wholly) by anyone who can see the pending unsigned extrinsic and re-derive proofs for a subset of its commitments, without needing any privileged role, key, or relayer/prover collusion — only public chain data. Funds end up credited to the wrong recipient (`delivery_address` instead of `beneficiary_address`), and the legitimate beneficiary-redirect transaction can be repeatedly griefed into `MissingCommitments` failures.

### Likelihood Explanation
`accumulate_fees` is intentionally permissionless and unsigned (`ensure_none` origin, `validate_unsigned`) [5](#0-4) , so no relayer/prover/admin compromise is required — an ordinary chain observer with access to public source/destination state can build the competing partial proof. The only timing requirement is landing a transaction before the original one is included, which is a normal mempool race, not a "malicious peer" or "front-run-only" assumption excluded by the impact gate (the manipulation itself, not the front-run timing, is the core bug: no commitment-binding in the beneficiary signature).

### Recommendation
Bind the beneficiary redirection signature to the exact commitment set being claimed (e.g., include a hash of `withdrawal_proof.commitments` in the signed message), or require the beneficiary-redirect signature nonce to be consumed atomically with the full batch such that any partial pre-claiming of the referenced commitments invalidates the whole redirect request rather than silently degrading it.

### Proof of Concept
1. Relayer R has delivered messages for commitments `[c1, c2, c3]` and wants fees paid to a treasury address `B` instead of its own delivery key, so it signs `msg = keccak256(nonce, dest_chain, B)` and submits `accumulate_fees(WithdrawalProof{ commitments: [c1,c2,c3], source_proof, dest_proof, beneficiary_details: Some((B, sig)) })`.
2. An observer sees this unsigned extrinsic in the pool. Using the same public source/destination chain state, they build `WithdrawalProof{ commitments: [c1], source_proof', dest_proof', beneficiary_details: None }` and submit it with higher priority/faster inclusion.
3. This front-run transaction lands first: `c1` is marked claimed, and its fee is credited into `Fees[dest_chain][delivery_address]` (R's own on-chain relayer key) rather than `B`.
4. R's original transaction executes afterward; `accumulate()`'s filter step drops `c1` from `withdrawal_proof.commitments` since it is now claimed [4](#0-3) , so only `c2` and `c3`'s fees get redirected to `B` — `c1`'s fee is permanently split away from the intended beneficiary. Repeating this for `c2` and `c3` before R's transaction lands causes the whole call to revert with `MissingCommitments`, forcing R to resubmit.

	pub fn accumulate(mut withdrawal_proof: WithdrawalProof) -> DispatchResult {
		// Reject duplicate commitments within the batch. The wire format is a
		// `Vec` and this extrinsic is unsigned, so this is the line of defence
		// against an attacker padding the batch with identical commitments to
		// double-claim fees.
		let mut seen = alloc::collections::BTreeSet::new();
		for key in withdrawal_proof.commitments.iter() {
			ensure!(seen.insert(key.encode()), Error::<T>::DuplicateCommitment);
		}

		// Filter out already-claimed / missing commitments
		withdrawal_proof.commitments = withdrawal_proof
			.commitments
			.into_iter()
			.filter(|req| match RequestCommitments::<T>::get(*req) {
				Some(leaf_meta) => !leaf_meta.claimed,
				// If request commitment does not exist in storage which should not be
				// possible, we skip it
				None => false,
			})
			.collect();
		ensure!(!withdrawal_proof.commitments.is_empty(), Error::<T>::MissingCommitments);
