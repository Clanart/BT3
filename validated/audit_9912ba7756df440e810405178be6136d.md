### Title
Mempool block-builder skip-counter bypass via coin-conflict "continue" paths allows spend-bundle flooding to stall block-template generation - ([File: chia/full_node/mempool.py])

### Summary
`Mempool.create_bundle_from_mempool_items()` and `Mempool.create_block_generator2()` bound the cost of scanning the mempool during block-template creation with a `skipped_items` counter: once `skipped_items` reaches `PRIORITY_TX_THRESHOLD`/`MAX_SKIPPED_ITEMS`, the scan takes cheaper shortcuts or stops early. However, the "item conflicts with a coin already committed to this block" skip path does a bare `continue` without ever incrementing `skipped_items`, unlike every other skip reason in the same loop. This mirrors the curl bug class: a category of discarded work-units is excluded from the per-call processing budget, letting an attacker who can make many mempool items fall into that specific uncounted category defeat the intended early-exit bound.

### Finding Description
Inside `Mempool.create_bundle_from_mempool_items()` in `chia/full_node/mempool.py`, every other skip reason increments the `skipped_items` budget before continuing/breaking, e.g. the cost/atom/pair-overflow path: [1](#0-0) 

But the coin-conflict skip path does not: [2](#0-1) 

The same asymmetry exists in `create_block_generator2()`. The spend-count and atom/pair skip paths increment `skipped_items`: [3](#0-2) 

while the coin-conflict skip path again does a bare `continue` with no counter update: [4](#0-3) 

`skipped_items` is the mechanism documented in `.cursor/context/mempool.md` as the bound on "max items skipped during block building" (`MAX_SKIPPED_ITEMS = 10`) and the threshold after which fast-forward/dedup processing is short-circuited (`PRIORITY_TX_THRESHOLD = 3`): [5](#0-4) 

Because items that conflict with a coin already committed to the block being assembled are never counted toward this budget, they never trigger the early-exit shortcuts. Each of these items still pays the cost of `singleton_ff.process_fast_forward_spends()` and `IdenticalSpendDedup.get_deduplication_info()` before being discarded via the uncounted `continue`. An attacker who submits many mempool items that resolve to the same underlying coin at block-build time (most straightforwardly via multiple fast-forward-eligible spends of the same singleton lineage, which are each individually valid to admit into the mempool but only one of which can ultimately be included per block) can force the block-builder to repeatedly perform full-cost FF/dedup processing on every such item, on every call, without ever reaching the `MAX_SKIPPED_ITEMS`/`PRIORITY_TX_THRESHOLD` cutoffs meant to bound this work.

### Impact Explanation
The only remaining bound on this loop is the wall-clock `timeout` check at the top of the loop: [6](#0-5) 
so the function does not hang indefinitely — but it burns its entire per-call time budget on wasted FF/dedup work for uncounted "conflict" items instead of assembling a block, directly degrading `create_block_generator`/`create_block_generator2`, which are on the block-farming path. A single unprivileged mempool submitter can flood the pool (mempool capacity is `MEMPOOL_BLOCK_BUFFER` × max block cost, i.e. up to 10× a full block) with such items, causing repeated, expensive, and ultimately fruitless scans on every block-template build attempt — a spend-triggered transaction-processing stall/degradation of block generation.

### Likelihood Explanation
Reachable purely by submitting spend bundles to the mempool through the ordinary transaction-submission path (no elevated privileges); the attacker only needs enough distinct fast-forward-eligible spends against a singleton lineage they control to occupy the "conflicts with a coin already committed to this block" branch on every scan. It requires crafting several mempool-admissible items whose resolved coin overlaps at block-build time, which is plausible but non-trivial to engineer at scale, and effects are bounded by the per-call timeout rather than unbounded — placing this at Medium likelihood/severity.

### Recommendation
Increment `skipped_items` (and/or the batch-equivalent counter) in the coin-conflict `continue` branches of both `create_bundle_from_mempool_items()` and `create_block_generator2()`, consistent with every other skip reason in the same loops, so that items which fall into this category are correctly counted against `MAX_SKIPPED_ITEMS`/`PRIORITY_TX_THRESHOLD` and the early-exit protections are not bypassed.

### Proof of Concept
1. Create/control a fast-forward-eligible singleton coin lineage.
2. Submit multiple distinct, individually mempool-admissible spend bundles referencing different points/branches of that singleton lineage such that, at block-build time, `singleton_ff.process_fast_forward_spends()` resolves several of them to the same already-committed coin id (`item_removal_ids` collision against `spent_coin_ids`/`batch_spent_coin_ids`).
3. Repeatedly call (or trigger via normal farming) `create_block_generator2()`/`create_bundle_from_mempool_items()`.
4. Observe that each conflicting item is fully processed through FF/dedup logic but its `continue` never increments `skipped_items`, so `MAX_SKIPPED_ITEMS`/`PRIORITY_TX_THRESHOLD` are never reached from these items — the loop keeps re-doing expensive work on every such item until only the wall-clock `timeout` cuts it off, yielding degraded/near-empty block templates despite mempool capacity being available.
