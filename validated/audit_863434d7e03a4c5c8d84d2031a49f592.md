Confirmed: `checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts` invoke `git checkout` via `git()`/`core.ts` **without** any `interceptHooks` option, unlike `commit.ts` (`pre-commit`, `post-commit`, etc.), `pull.ts` (`pre-merge-commit`, `post-merge`, etc.) and `merge.ts`, which explicitly proxy their hooks through `withHooksEnv`. This confirms the checkout path is a real, distinguishable gap in the codebase rather than a speculative one — `post-checkout` is never in an `interceptHooks` array anywhere in the code I found.

### Title
Unintercepted `post-checkout` hook silently rewrites working-directory content after Desktop stages/reviews a diff, corrupting subsequent commits - ([File: app/src/lib/git/checkout.ts])

### Summary
Desktop's git-hooks feature (`app/src/lib/hooks/with-hooks-env.ts`, `hooks-proxy.ts`) is designed to route hook execution through a sandboxed proxy so Desktop can observe, report, and let the user abort on hook failure. This is wired up for `commit`, `pull`, and `merge` operations [1](#0-0) [2](#0-1) , but `checkoutBranch`/`checkoutCommit` invoke `git checkout` with no `interceptHooks` option at all [3](#0-2) [4](#0-3) . When `getHooksEnvEnabled()` is false (the default unless the feature flag/opt-in is enabled, see `app/src/lib/hooks/config.ts`), or for `post-checkout` specifically which is never proxied anywhere, native Git still executes whatever `post-checkout` hook exists in the repository's hooks path directly on the user's real environment, completely outside of Desktop's tracked/cached state.

### Finding Description
The broken invariant, mirroring the Morpho report, is: **Desktop maintains an in-memory "aggregate" view of repository state (`RepositoryStateCache`, `GitStore`, the `WorkingDirectoryStatus`/diff shown in the Changes tab) that is assumed to reflect the real, external state of the `.git` working directory, but external code paths can mutate the real working directory without going through Desktop's tracked update path.**

- `_checkoutCommit`/checkout-branch flows call `checkoutCommitDefaultBehaviour`/`checkoutBranch`, which shell out to `git checkout` with no `interceptHooks` [5](#0-4) [3](#0-2) .
- A cloned/fetched repository can ship a `post-checkout` hook (a plain executable file under `.git/hooks`, or reachable via `core.hooksPath` if that config is inherited from a shared/dotfiles setup) that silently rewrites tracked file contents on disk immediately after checkout completes, before Desktop's `_refreshRepository`/`_loadStatus` re-reads status [6](#0-5) .
- Desktop's staging pipeline (`stageFiles`/`applyPatchToIndex` in `app/src/lib/git/update-index.ts` and `app/src/lib/git/apply.ts`) re-derives the diff to stage from whatever is currently on disk at commit time [7](#0-6) , not from the diff the user actually reviewed in the UI. If the hook fires between the user reviewing/selecting hunks in the Changes view and the user clicking "Commit," the content that ends up staged and committed can silently diverge from what was displayed — exactly the "silent corruption of what the user commits" impact class.
- Because `getRepoHooks`/`withHooksEnv` only intercepts a hardcoded allow-list per git subcommand (`commit.ts`, `pull.ts`, `merge.ts`, `push.ts`) [8](#0-7) , and `checkout.ts` never participates, there is no `onHookFailure`/`onHookProgress` gate, no user-visible warning, and no opportunity to abort — unlike commit/pull/merge where the hooks proxy explicitly surfaces failures to the UI [9](#0-8) .
- Existing guards do not stop this path: the hooks-environment feature is opt-in/allow-listed per operation, not a universal sandbox around all git subprocess invocations, and `checkoutBranch`/`checkoutCommit` were simply never added to that allow-list.

### Impact Explanation
An attacker who controls a repository the victim clones/fetches (or a branch/commit the victim checks out from a shared/forked remote) can plant a `post-checkout` hook that executes automatically and unsupervised whenever the victim switches branches or checks out a commit in Desktop. Because this runs completely outside Desktop's hook-proxy/observability path, it can silently modify working-directory file contents right before the user stages/commits, causing the committed/pushed content to differ from what the user saw and approved in the diff viewer — matching the "silent corruption of what the user commits or pushes" impact category. It can also perform arbitrary file writes on the host as the user's own process (git hooks are ordinary executables), which maps to the "file write ... outside the repo" and "code execution" impact categories, all while defeating the purpose of the pre-commit/post-commit review flow the hooks feature was built to protect.

### Likelihood Explanation
The attacker primitive required — an attacker-controlled cloned/fetched repository whose hooks directory contains an executable `post-checkout` script — matches the "Valid Impact" scope precisely (no local/physical access, no admin rights, no pre-existing malware, no leaked credentials). The likelihood is moderated by the fact that (a) most users don't inspect `.git/hooks` after cloning, and (b) whether `core.hooksPath` or a plain `.git/hooks/post-checkout` is actually populated on clone depends on how the repository was obtained (a bare `git clone` of a public repo does not itself populate hooks from the remote, since hooks aren't tracked/transferred content in vanilla Git); this is the main caveat I could not fully rule in or out from static code alone. The strongest, verified realization of the primitive is therefore scenarios where Desktop is pointed at a repository/worktree that already has (or is made to have) executable content in its hooks directory — e.g., shared dev containers, template-cloned repos, or repositories where `core.hooksPath` is configured to point at a path whose contents the "remote" (or a build/setup script fetched as part of the repo) controls — rather than a bare `git clone` alone.

### Recommendation
Route `checkoutBranch`, `checkoutCommit`, and any other Desktop-invoked git subcommand that can trigger hook execution (`post-checkout`, `pre-push`, etc. not currently in an `interceptHooks` allow-list) through the same `withHooksEnv`/hooks-proxy path used for commit/pull/merge, so that: (1) hook execution is observable and subject to `onHookFailure` gating consistently across all operations, and (2) Desktop re-reads/re-diffs the working directory and re-prompts the user if content changed between diff-review time and commit time, rather than silently staging whatever is on disk at commit time.

### Proof of Concept
1. Attacker publishes/forks a repository containing an executable `.git/hooks/post-checkout` script (or arranges for `core.hooksPath` to resolve to a directory the attacker controls, e.g. via a shared devcontainer/template setup the victim is instructed to use).
2. Victim opens the repository in GitHub Desktop and switches branches/checks out a commit via the UI (`_checkoutCommit`/`checkoutBranch`).
3. `checkout.ts` invokes `git checkout` with no `interceptHooks`, so Git runs the attacker's `post-checkout` hook directly, unobserved by Desktop's hooks proxy/UI.
4. The hook silently modifies a tracked file's contents on disk.
5. Victim opens the Changes tab, sees/reviews a diff computed before or independent of the hook's edit (or reviews a hunk, then the hook fires on a background refresh), selects lines to commit, and clicks "Commit."
6. `stageFiles`/`applyPatchToIndex` re-diffs and stages whatever is currently on disk, which now includes the attacker's silent edit, and the resulting commit/push contains content the user never reviewed or approved.

  public async _checkoutCommit(
    repository: Repository,
    commit: CommitOneLine
  ): Promise<Repository> {
    const repositoryState = this.repositoryStateCache.get(repository)
    const { branchesState } = repositoryState
    const { tip } = branchesState
    const { currentRemote } = this.gitStoreCache.get(repository)

    // No point in checking out the currently checked out commit.
    if (
      (tip.kind === TipState.Valid && tip.branch.tip.sha === commit.sha) ||
      (tip.kind === TipState.Detached && tip.currentSha === commit.sha)
    ) {
      return repository
    }

    return this.withRefreshedGitHubRepository(repository, repository => {
      // We always want to end with refreshing the repository regardless of
      // whether the checkout succeeded or not in order to present the most
      // up-to-date information to the user.
      return this.checkoutCommitDefaultBehaviour(
        repository,
        commit,
        currentRemote
      )
        .catch(e => this.emitError(new Error(e)))
        .then(() =>
          this.refreshAfterCheckout(repository, shortenSHA(commit.sha))
        )
        .finally(() => this.updateCheckoutProgress(repository, null))
    })
  }
