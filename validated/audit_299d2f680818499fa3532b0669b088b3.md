Based on my review, the closest structural analog to the Venus "wrong decimal/unit used in a downstream calculation, no validation catches it" bug is in GitHub Desktop's partial-diff/partial-commit machinery: a raw integer "unit" (an absolute unified-diff line index) is used as the sole handle for user line-selections, but that unit's meaning is redefined whenever the diff is expanded, merged, or regenerated — with no check that the `DiffSelection` was computed against the same diff shape it is later applied to.

### Title
Stale/rebased diff-selection indices can cause `formatPatch` to stage different lines than the user selected - (File: app/src/models/diff/diff-selection.ts)

### Summary
`DiffSelection` tracks which lines a user has (de)selected purely as a `Set<number>` of absolute, content-agnostic line indices [1](#0-0) . `formatPatch` and `formatPatchToDiscardChanges` re-derive an `absoluteIndex` from `hunk.unifiedDiffStart + lineIndex` and ask that same selection object "is this index selected?" to decide what to write into the patch that is then applied straight to the index/working tree via `git apply` [2](#0-1) [3](#0-2) . This is exactly analogous to the Venus bug: a numeric quantity (there: `capital` scaled by the wrong decimals; here: a "line index") is passed between two computations that silently assume it means the same thing in both places, with no independent validation that the assumption still holds.

### Finding Description
`hunk.unifiedDiffStart`/`unifiedDiffEnd` are not fixed identifiers of a line — they are recomputed every time a diff is reparsed, expanded, or hunks are merged. `expandTextDiffHunk` and `mergeDiffHunks` explicitly shift `unifiedDiffStart`/`unifiedDiffEnd` for hunks after the one being expanded (`hunk.unifiedDiffStart + numberOfNewDiffLines`) and splice/merge hunk line arrays together [4](#0-3) [5](#0-4) . The diff parser also computes `unifiedDiffStart` from `linesConsumed`, a running counter over the raw diff text, which shifts whenever the number of context lines, "no newline" markers, or hunk boundaries in the underlying diff text changes [6](#0-5) .

`DiffSelection`, however, has no notion of the diff it was built against — `isSelected(lineIndex)` and `withRangeSelection(from, length, selected)` operate purely on raw integers [7](#0-6) [8](#0-7) . There is no content hash, diff identity, or line-text check tying a `divergingLines` entry to a specific line of specific content — only its positional offset. Once the diff underlying a `WorkingDirectoryFileChange` is regenerated with a different hunk layout (via hunk expansion, hunk merging on expansion, or simply because the working-tree file changed between the time the user made a selection and the time `createCommit`/`applyPatchToIndex` runs), the same offset now refers to a different line, but `formatPatch` will still honor the old selection state for that offset when building the patch that is fed to `git apply --cached` [9](#0-8) .

This mirrors the reported bug's core defect precisely: a unit (decimals there, absolute line index here) is silently reinterpreted between the place it's produced and the place it's consumed, and nothing downstream re-validates the assumption — `Scores.calculateScore` trusted `capital` was 18-decimals; `formatPatch` trusts `absoluteIndex` still identifies the same diff line it did when the user clicked it.

### Impact Explanation
If exploitable, the result is that GitHub Desktop silently stages/commits (or discards) different lines than what the user visually selected in the diff viewer — i.e., "silent corruption of what the user commits or pushes," one of the explicitly valid impact categories. A user could believe they are excluding a sensitive line (e.g., a credential accidentally pasted, or a security-relevant change) from a commit, while the stale-index bug causes that line to be included anyway (or vice versa — an intended change silently dropped), because the underlying diff hunks shifted (via hunk expansion or an on-disk change) between selection and patch generation.

### Likelihood Explanation
This requires no local/admin access and no leaked credentials — only ordinary use of Desktop's partial-commit UI (line/hunk selection, "Expand hunk", or a file that changes on disk between selection and commit, e.g. due to another process/tool or a build step the repo triggers, which is squarely within "attacker controls a cloned/fetched repository" content and behavior). The expansion/merge code paths in `text-diff-expansion.ts` are user-triggerable, everyday features (`onExpandHunk` in `side-by-side-diff.tsx`) that demonstrably renumber `unifiedDiffStart`/`unifiedDiffEnd` for hunks other than the one directly touched [10](#0-9) , which is a normal, low-friction path to trigger the described index-reinterpretation, not an edge case requiring unnatural steps.

I was not able to fully verify, within the available tool budget, whether callers (e.g., in `app-store.ts`) always fully discard and rebuild a fresh `DiffSelection` on every diff/hunk-expansion event rather than reusing/remapping the old one — this is the key remaining uncertainty that determines actual exploitability versus a purely theoretical API-level fragility. I could not locate a reindexing/invalidation routine tying `DiffSelection` instances to diff identity in the portions of `app-store.ts` I examined.

### Recommendation
Bind `DiffSelection` (or the selection state persisted across diff refreshes) to diff content/identity rather than raw positional offsets — e.g., key selections by stable line content hashes, by the underlying old/new line numbers (`oldLineNumber`/`newLineNumber`, which are anchored to actual file line numbers) instead of the ephemeral `unifiedDiffStart`-relative index, or explicitly invalidate/remap the selection any time the diff is reparsed, expanded, or merged, with an assertion that catches any residual out-of-range or misaligned indices before `formatPatch` builds a patch.

### Proof of Concept
Not independently reproduced end-to-end due to tool-call limits; the PoC path would be:
1. Open a modified file with multiple hunks separated by a short gap in Desktop's changes view.
2. Partially select a subset of lines in the second hunk (unselect some Add/Delete lines), leaving other hunks fully selected.
3. Trigger "Expand hunk" on the first hunk such that it merges with the second hunk (`mergeDiffHunks`) or otherwise shifts `unifiedDiffStart` for the second hunk (`expandTextDiffHunk`, confirmed to renumber trailing hunks) [11](#0-10) .
4. Commit the partial selection and inspect the resulting commit via `git show` to check whether the actually-included/excluded lines match the lines the user visually selected before the expansion, or whether the shifted indices caused different lines to be staged.

function mergeDiffHunks(hunk1: DiffHunk, hunk2: DiffHunk): DiffHunk {
  // Remove the first line in both hunks, because those are hunk header lines
  // that will be replaced by a new one for the resulting hunk.
  const allHunk1LinesButFirst = hunk1.lines.slice(1)
  const allHunk2LinesButFirst = hunk2.lines.slice(1)

  const newHunkHeader = new DiffHunkHeader(
    hunk1.header.oldStartLine,
    hunk1.header.oldLineCount + hunk2.header.oldLineCount,
    hunk1.header.newStartLine,
    hunk1.header.newLineCount + hunk2.header.newLineCount
  )

  // Create a new hunk header line for the resulting hunk
  const newFirstHunkLine = new DiffLine(
    newHunkHeader.toDiffLineRepresentation(),
    DiffLineType.Hunk,
    null,
    null,
    null,
    false
  )

  const newHunkLines = [
    newFirstHunkLine,
    ...allHunk1LinesButFirst,
    ...allHunk2LinesButFirst,
  ]

  return new DiffHunk(
    newHunkHeader,
    newHunkLines,
    hunk1.unifiedDiffStart,
    hunk1.unifiedDiffStart + newHunkLines.length - 1,
    // The expansion type of the resulting hunk will match the expansion type
    // of the first hunk:
    // - If the first hunk can be expanded up, it means it's the very first
    //   hunk, so the resulting hunk will be the first too.
    // - If the first hunk can be expanded but short, that doesn't change after
    //   merging it with the second one.
    // - If it can be expanded up and down (meaning it's a long gap), that
    //   doesn't change after merging it with the second one.
    // - It can never be expanded down exclusively, because only the last dummy
    //   hunk can do that, and that will never be the first hunk in a merge.
    hunk1.expansionType
  )
}
