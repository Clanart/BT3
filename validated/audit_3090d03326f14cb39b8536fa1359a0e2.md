### Title
Tokenfactory denom admin can unilaterally set/change the `AllowList` via `MsgCreateDenom`/`MsgUpdateDenom` to freeze arbitrary holders' funds - ([File: x/tokenfactory/keeper/msg_server.go])

### Summary
The tokenfactory module lets any unprivileged account become the "admin" of a denom it creates, and grants that admin sole, unchecked, unilateral power to set or change the denom's `AllowList` at any time via `MsgUpdateDenom`, which is enforced by `bank`'s `IsInDenomAllowList` on every subsequent `MsgSend`/`MsgMultiSend`. This mirrors the reported bug class of an "admin" role with excessive unilateral power capable of denying/freezing user funds without any timelock, delay, or holder consent, reachable directly by an ordinary transaction sender who is the denom's self-appointed admin.

### Finding Description
Any account can become a tokenfactory "admin" simply by creating a denom with `MsgCreateDenom`; the creator is automatically set as `AuthorityMetadata.Admin` [1](#0-0) . That admin can call `MsgUpdateDenom` at any time to set the denom's `AllowList`, gated only by `msg.Sender != authorityMetadata.GetAdmin()` — no other check on existing holders, no timelock, no cooldown: [2](#0-1) 

Once an `AllowList` is set for a denom, the bank module enforces it on every `MsgSend`/`MsgMultiSend`, rejecting sends/receives for any address not on the list: [3](#0-2) [4](#0-3) 

Because the admin can update the `AllowList` unilaterally and at will (no notice, no holder opt-in, no restriction tied to already-outstanding balances), it can:
- Front-run a specific victim's pending transfer by removing that victim from the allow list before their transaction is included, causing their `MsgSend`/`MsgMultiSend` to revert with "is not allowed to send/receive funds" [5](#0-4) .
- Retroactively freeze any existing holder's already-issued balance of that denom by excluding them from a newly set allow list, permanently denying them the ability to move or dispose of funds they already legitimately hold, with the balance itself untouched but functionally frozen forever unless the admin chooses to re-include them.

This is directly analogous to the reported centralization pattern: a self-appointed, unprivileged-reachable "admin" role holds unchecked configuration power (`AllowList`) that directly controls other users' ability to move their own funds, and that power can be exercised adversarially/at will to front-run or permanently deny value to token holders — exactly the "admin has too much power... to deny/steal users' rewards" bug class from the source report, mapped onto sei-chain's tokenfactory + bank allow-list mechanism.

### Impact Explanation
Impact is High: a tokenfactory denom admin — reachable by any unprivileged transaction sender who creates a denom and distributes it to other holders — can permanently freeze other users' already-held balances of that denom by excluding them from the `AllowList`, or front-run/grief pending transfers by toggling the list. This constitutes permanent freezing of user funds for that denom, one of the explicitly accepted impact categories.

### Likelihood Explanation
Likelihood is Medium-High: it requires only that a malicious or compromised tokenfactory denom creator/admin acts adversarially against holders of a token they distributed (e.g., after an airdrop, ICO, or DEX listing of a tokenfactory asset). No governance, validator, or node-operator involvement is required — a single ordinary account triggers this purely through standard `MsgCreateDenom`/`MsgUpdateDenom` transactions.

### Recommendation
- Disallow retroactive changes to `AllowList` that would remove addresses already holding a nonzero balance of the denom, or require an explicit timelocked/delayed activation for `AllowList` updates so holders have advance notice.
- Consider making `AllowList` immutable after first mint/distribution, or gating removals behind a stricter admin-authz/multi-sig/timelock model, consistent with the report's recommendation to replace unchecked single-key admin control with a Timelock-style mechanism.

### Proof of Concept
1. Attacker calls `MsgCreateDenom` to create `factory/{attacker}/token`, becoming its admin [6](#0-5) .
2. Attacker mints the denom and distributes it to victims via `bank.MsgSend`/`MsgMultiSend` (no `AllowList` set yet, so all sends succeed) [3](#0-2) .
3. After victims hold balances (e.g., post-airdrop or after listing on a DEX), attacker submits `MsgUpdateDenom` setting `AllowList = {attacker-controlled addresses only}` [2](#0-1) .
4. Any subsequent `MsgSend`/`MsgMultiSend` by a victim (not on the new list) reverts with `"{addr} is not allowed to send funds"` / `"is not allowed to receive funds"`, as shown in `TestSendReceiverNotInAllowList` [5](#0-4)  — the victim's balance remains permanently locked/untransferable while the attacker's addresses continue to trade freely.

func (server msgServer) CreateDenom(goCtx context.Context, msg *types.MsgCreateDenom) (*types.MsgCreateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.Keeper.CreateDenom(ctx, msg.Sender, msg.Subdenom)
	if err != nil {
		return nil, err
	}

	createDenomEvent := sdk.NewEvent(
		types.TypeMsgCreateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeNewTokenDenom, denom),
	)

	if msg.AllowList != nil {
		err = server.validateAllowList(ctx, msg.AllowList)
		if err != nil {
			return nil, err
		}
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		createDenomEvent = createDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		createDenomEvent,
	})

	return &types.MsgCreateDenomResponse{
		NewTokenDenom: denom,
	}, nil
}

func (server msgServer) UpdateDenom(goCtx context.Context, msg *types.MsgUpdateDenom) (*types.MsgUpdateDenomResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	denom, err := server.validateUpdateDenom(ctx, msg)
	if err != nil {
		return nil, err
	}

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	updateDenomEvent := sdk.NewEvent(
		types.TypeMsgUpdateDenom,
		sdk.NewAttribute(types.AttributeCreator, msg.Sender),
		sdk.NewAttribute(types.AttributeUpdatedTokenDenom, denom),
	)

	if msg.AllowList != nil {
		server.bankKeeper.SetDenomAllowList(ctx, denom, *msg.AllowList)
		updateDenomEvent = updateDenomEvent.AppendAttributes(
			sdk.NewAttribute(types.AttributeAllowList, strings.Join(msg.AllowList.Addresses, ",")),
		)
	}

	ctx.EventManager().EmitEvents(sdk.Events{
		updateDenomEvent,
	})

	return &types.MsgUpdateDenomResponse{}, nil
}

		return nil, sdkerrors.Wrapf(sdkerrors.ErrUnauthorized, "%s is not allowed to send funds", msg.FromAddress)

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}
