## Title
Unanchored Prefix Check Lets Files Outside `~/.claude/plans` Bypass Security-Pattern Scanning - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The ENS `BytesUtils.equals` bug (`self.length >= offset + other.length` instead of `==`) is a length/boundary-check-that-should-be-an-exact-match bug that lets superset data satisfy a comparison meant to require equality. The closest reachable analog in this repo's unprivileged-trust-boundary surface is the plan-file exclusion check in the `security-guidance` plugin's `PostToolUse` handler, which uses an unanchored `str.startswith()` prefix check instead of a proper path-boundary comparison.

### Finding Description
In `plugins/security-guidance/hooks/security_reminder_hook.py`, the `PostToolUse` handler for `Edit`/`Write`/`MultiEdit`/`NotebookEdit` skips all security-pattern scanning for files under the plans directory: [1](#0-0) 
```
plans_dir = os.path.expanduser("~/.claude/plans")
if file_path.startswith(plans_dir):
    sys.exit(0)
```
`str.startswith()` performs a raw character-prefix comparison with no trailing path separator and no boundary check — the same class of bug as the ENS finding, where a length/prefix relationship that should be exact (`==` / a真正 directory-boundary match) is instead checked with a looser relational comparison (`>=` in ENS, unanchored prefix here). Any file path that merely shares the literal prefix `~/.claude/plans` — e.g. `~/.claude/plans-evil/secrets.env` or `~/.claude/plansXYZ/config.py` — satisfies `startswith(plans_dir)` even though it is not inside the actual `~/.claude/plans/` directory.

### Impact Explanation
This mirrors the "Substring/Unanchored Allowlist Bypass" class the plugin's own LLM-review prompt explicitly warns about elsewhere in the codebase (`value.startswith(...)` without a trailing separator being bypassable) — [2](#0-1)  — yet the plugin's own gate at line 2119 has the identical flaw. Because the check runs on every Edit/Write/MultiEdit, an unprivileged user (or an agent operating on their behalf) that creates or edits a file whose absolute path starts with the literal string `~/.claude/plans` (but is not actually the plans directory, e.g. a differently-named sibling directory) will have the file silently excluded from the pattern-based security reminder (`check_patterns`), which is Claude Code's built-in warning mechanism for hardcoded secrets, dangerous commands, and similar issues written by the agent. This is a local security-control bypass: it suppresses `additionalContext` warnings that are meant to nudge the agent/user away from writing insecure code, and it also skips `record_pending_warnings`, so the Stop-hook sweep that tallies fixed-vs-unresolved issues never even records the omission — the bypass is invisible.

### Likelihood Explanation
Triggering the bypass only requires performing a normal Edit/Write/MultiEdit call against a path that lexically starts with `~/.claude/plans` — no special privilege, sandbox escape, or attacker infrastructure is needed. Any workflow, skill, or plugin content that causes Claude to create a directory named e.g. `~/.claude/plans-workspace/` or `~/.claude/plansomething/` would silently disable this defense-in-depth control for every file written there. This is lower severity than a full permission/sandbox bypass (it only disables an advisory warning system, not tool execution), but it is a genuine trust-boundary flaw reachable by an ordinary session.

### Recommendation
Anchor the comparison to a real path boundary instead of a raw string prefix, matching the guidance the plugin already gives for path-traversal checks elsewhere in its own prompt (`os.path.realpath` + boundary check):
```python
plans_dir = os.path.realpath(os.path.expanduser("~/.claude/plans"))
real_file_path = os.path.realpath(file_path)
if real_file_path == plans_dir or real_file_path.startswith(plans_dir + os.sep):
    sys.exit(0)
```

### Proof of Concept
1. Have Claude Code (in a normal, unprivileged session) create a file at `~/.claude/plans-scratch/notes.py` (any directory name sharing the `~/.claude/plans` prefix but not the real plans directory) via the `Write` tool.
2. Write content containing a pattern the plugin normally flags, e.g. a hardcoded secret (`API_KEY = "sk-..."`) or `eval(user_input)`.
3. Observe that `check_patterns` is never invoked because `file_path.startswith(plans_dir)` evaluates `True` for `~/.claude/plans-scratch/notes.py` — the `PostToolUse` handler exits at line 2120 before any pattern scan or warning is emitted, unlike the identical write performed at, say, `~/.claude/plansX/notes.py` vs. a legitimately unrelated path such as `~/.claude/other/notes.py`, which would correctly go through `check_patterns`.

**Note on uncertainty:** I was not able to fully verify (before running out of iterations) whether `file_path` at this point is always an absolute, `expanduser`-normalized path with no symlink components, or whether some other layer already normalizes it before this check runs — the surrounding code that reads `tool_input.get("file_path")` was visible but I did not trace the full input-normalization pipeline for the `PostToolUse` payload. This does not change the core finding (the comparison itself is unanchored), but it is a caveat on the exact minimal repro path.
