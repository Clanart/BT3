### Title
Fee/vsize accounting excludes the OP_RETURN data output, producing transactions whose actual fee rate is below the intended rate and potentially below the minimum relay fee — ([File: networks/bitcoin/src/wallet/send.rs])

### Summary

`SignableTransaction::new` pushes an `OP_RETURN` output into `tx_outs` when `data` is provided, but computes `weight`/`vbytes` via `calculate_weight_vbytes(tx_ins.len(), payments, ...)`, which is fed `payments` — a list that does not contain the data output. Both `needed_fee` and the change output's value are derived from this underestimated vsize, so the final transaction's real fee (`sum(inputs) - sum(outputs)`) can fall below both the requested `fee_per_vbyte` and Bitcoin's minimum relay fee.

### Finding Description

In `SignableTransaction::new`, the `OP_RETURN` output is appended to `tx_outs` at lines 194-202, before the weight is estimated: [1](#0-0) 

`calculate_weight_vbytes` reconstructs a model `Transaction` solely from `payments` (plus an optional change output). The `OP_RETURN` output, which can carry up to 80 bytes of pushdata (enforced at ~81 bytes via `TooMuchData`), is never included: [2](#0-1) 

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` is computed on the smaller vsize (line 206). The actual transaction includes the extra ~11-90+ vbyte output, so `self.fee()` (line 138-141, `sum(inputs) - sum(outputs)`) corresponds to a lower effective sat/vbyte than requested.
2. The minimum-relay-fee gate at line 211 also uses the underestimated `vbytes`, so it can pass while the real transaction fails the relay rule `fee >= 1000 * real_vbytes / 1000`: [3](#0-2) 
3. The change path repeats the same mistake: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (lines 225-226) still omits the data output, so `value = input_sat - (payment_sat + fee_with_change)` overfunds change and further underfunds the fee.
4. Because the same underestimated `weight` is checked against `MAX_STANDARD_TX_WEIGHT` (line 241), a transaction marginally under the limit could also exceed it once the data output is included — though the dominant impact is fee underpayment.

This is the same defect class as the reference finding: an internally computed expectation (withdrawable assets / required vsize) is compared or charged against an actual on-chain quantity that can legitimately differ, and the discrepancy produces a transaction the network will reject (DoS) rather than a tolerable ~1-unit rounding difference. Here the discrepancy is structural (an entire missing output), not just 1 wei.

### Impact Explanation

Any `SignableTransaction` constructed with `data` produces a transaction paying less than the requested fee rate. When `fee_per_vbyte` is near the minimum (e.g., `fee.max(1)` from `median_fee`, see `processor/src/networks/bitcoin.rs:406-414`), the signed transaction can be below the 1000 sat/kilo-vbyte relay minimum and be rejected by Bitcoin nodes. The inputs are then committed to a transaction that cannot confirm — funds are neither delivered nor trivially recoverable without reconstructing the transaction — matching the "funds reported/handled as spendable but actually stuck" acceptance criterion. Even when relay succeeds, the caller silently pays a lower fee rate than requested, causing unpredictable confirmation delays for threshold-signed transactions that cannot be trivially rebuilt once FROST shares are consumed.

### Likelihood Explanation

Medium. The bug is deterministic whenever `data` is `Some(_)` — no attacker action required. Reachability is limited to flows that attach an OP_RETURN payload; the in-tree Bitcoin processor path (`make_signable_transaction`, `processor/src/networks/bitcoin.rs:446-452`) passes `None`, so exploitation depends on any caller (or future network integration, e.g., data-bearing sends) using the `data` parameter of this public API. The transaction construction is performed locally with public inputs (payments, change, data, fee rate), so any unprivileged party invoking this library path hits it.

### Recommendation

Include the OP_RETURN output in the weight/vsize model: pass `&tx_outs` (or an equivalent output list containing the data output) into `calculate_weight_vbytes` at both call sites (lines 204 and 225-226) instead of `payments`. Alternatively, add a safety margin to the estimated vsize, mirroring the report's suggestion of adding tolerance rather than assuming the estimate matches the actual serialized size exactly.

### Proof of Concept

```rust
// FEE chosen so the transaction *just* meets the relay minimum
let data = vec![0u8; 80]; // max permitted OP_RETURN payload

let tx = SignableTransaction::new(
  vec![funding_output],        // a ReceivedOutput with ample value
  &[(p2tr_script_buf(key).unwrap(), 1000)],
  None,
  Some(data.clone()),
  1,                            // 1 sat/vbyte
).unwrap();

// Estimated vsize excludes the ~91-byte OP_RETURN output
let (weight_no_data, vbytes_no_data) =
  SignableTransaction::calculate_weight_vbytes(1, &payments, None);
assert_eq!(tx.needed_fee(), vbytes_no_data); // = fee for the smaller TX

// The real transaction includes the OP_RETURN, so its true vsize is larger
let signed = sign(&keys, &tx);
let real_vbytes = signed.vsize() as u64;
assert!(real_vbytes > vbytes_no_data);

// Actual paid fee vs. relay minimum for the *real* size
let actual_fee = tx.fee();
let min_relay = u64::from(bitcoin::policy::DEFAULT_MIN_RELAY_TX_FEE) * real_vbytes / 1000;
assert!(actual_fee < min_relay); // not relayable despite passing the TooLowFee check
```

Root cause is purely local arithmetic: `tx_outs` gains an element at `networks/bitcoin/src/wallet/send.rs:194-202` that `calculate_weight_vbytes` (`send.rs:61-127`) never sees, so every downstream figure (`needed_fee`, the min-relay check, the change amount, the weight-limit check) is computed against a smaller transaction than the one ultimately signed and broadcast.
