### Title
OP_RETURN Data Output Omitted from Fee/Weight Calculation Causes Underpriced Transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` to the transaction's output list, but both calls to `calculate_weight_vbytes` only pass `payments` — the data output is never included in the transaction template used to compute weight and virtual size. Analogous to the reported bug (a partial interval existing in the real timeline but excluded from the pricing calculation), a real component of the final transaction exists that is unaccounted for in the fee calculation, so `needed_fee` is computed for a smaller transaction than the one actually produced and signed.

### Finding Description
In `SignableTransaction::new`, the `OP_RETURN` output is pushed onto `tx_outs` before the fee is computed:

```rust
// networks/bitcoin/src/wallet/send.rs
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(...),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
let mut needed_fee = fee_per_vbyte * vbytes;
```

`calculate_weight_vbytes` builds its template transaction solely from `payments` plus an optional `change` script — it has no `data` parameter at all (lines 62–99). The second call, used when a change output is considered, repeats the omission (`Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))`, line ~226).

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` prices a transaction that is missing the `OP_RETURN` output (an 80-byte payload adds ~80+ bytes of real size; the output also adds base txout overhead of ~11 bytes + push opcodes). The transaction actually signed and broadcast is larger than what was priced, so its effective fee rate is lower than the `fee_per_vbyte` requested.
2. The `TooLowFee` minimum-relay check (`needed_fee < (DEFAULT_MIN_RELAY_TX_FEE * vbytes) / 1000`, line ~211) validates against the same understated `vbytes`, so it can pass while the real transaction's fee falls below the relay minimum for its true vsize.
3. When `change` is `Some`, the change amount is computed as `input_sat - payment_sat - fee_with_change` (line ~228) using the understated fee, so change is inflated and the shortfall is silently absorbed by the fee.

The max-standard-weight check at line ~241 also uses `weight` from the incomplete template, so a transaction with `data` can exceed `MAX_STANDARD_TX_WEIGHT` without triggering `TooLargeTransaction`.

### Impact Explanation
A caller producing a `SignableTransaction` with `data` gets a transaction paying a fee rate strictly below the requested `fee_per_vbyte`. In the worst case the resulting transaction is under the network minimum relay fee (or over standard weight) and will not propagate/confirm, leaving the spent inputs' funds in limbo and the protocol's payment unexecuted until re-signed at a corrected fee. This is a deterministic mispricing of a real transaction component — the same failure shape as charging a stale/incorrect price because a portion of the interval was omitted from the calculation — though here the direction is underpayment of the fee rather than overpayment of a price.

### Likelihood Explanation
Any code path invoking `SignableTransaction::new` with `Some(data)` triggers it unconditionally (the library accepts up to 80 bytes and documents the `OP_RETURN` output as a supported feature). The in-repo processor currently passes `None` for `data`, so exploitation depends on integrators using the public API with data, but the miscalculation itself is unconditional for that input.

### Recommendation
Pass the data output (or its serialized size) into `calculate_weight_vbytes` — e.g., accept the already-constructed `tx_outs` list instead of `payments` — so both the no-change and with-change weight estimates include the `OP_RETURN` output. Equivalently, build the fee-estimation template from `tx_outs` after all outputs (payments, data, change) are assembled.

### Proof of Concept
```rust
// Conceptual: one P2TR input worth `input_sat`, one payment, 80-byte data, change address.
let data = vec![0xaa; 80];
let tx = SignableTransaction::new(
  vec![received_output], &payments, Some(change_script), Some(data.clone()), fee_per_vbyte,
).unwrap();

// The produced transaction contains the OP_RETURN output:
assert!(tx.transaction().output.iter().any(|o| o.script_pubkey.is_op_return()));

// But needed_fee was priced for a transaction WITHOUT that output.
// Real vsize > estimated vsize by ~90+ vbytes, so:
//   tx.fee() / real_vsize < fee_per_vbyte
// If fee_per_vbyte == 1 (min relay), the real fee rate is < 1 sat/vbyte
// and the TooLowFee check already passed on the understated vbytes,
// yielding a signed transaction the network will not relay.
```
