### Title
Attribution binding between a confirmed payout transaction and the operator who fronted it can be permanently severed via SIGHASH_SINGLE|ANYONECANPAY malleability of the payout transaction - ([File: core/src/verifier.rs], [File: core/src/database/verifier.rs], [File: core/src/operator.rs])

### Summary
The withdrawal-UTXO signature (`input_signature` in `WithdrawParams`) is a taproot key-spend signature whose sighash type is fully attacker-chosen; the codebase's own signing helper uses `TapSighashType::SinglePlusAnyoneCanPay`, which commits only to the withdrawal input and the single payout output, leaving all other outputs (including the OP_RETURN operator-attribution output) and all other inputs unsigned. Any party holding this signature — which is the withdrawing user themselves, i.e. an unprivileged attacker per the threat model — can reuse it to build an alternative transaction spending the identical `withdrawal_utxo`, dropping/corrupting the OP_RETURN and adding their own fee-bumping input(s), and get it confirmed instead of the operator's broadcast `payout_tx`. Because `get_payout_txs_for_withdrawal_utxos`/`update_finalized_payouts` attribute payouts purely from on-chain spend data plus OP_RETURN parsing, the honest operator's `payout_payer_operator_xonly_pk` becomes `NULL` and it can never surface via `get_first_unhandled_payout_by_operator_xonly_pk`, permanently blocking that operator's reimbursement.

### Finding Description
Binding claimed: `withdrawals.payout_payer_operator_xonly_pk == the operator whose payout_tx actually satisfies withdrawals.idx`.

- `Operator::withdraw` (core/src/operator.rs:560-692) accepts a caller-supplied `taproot::Signature` (`in_signature`) and directly threads it into `create_payout_txhandler` (core/src/builder/transaction/operator_reimburse.rs:407-436) via `set_p2tr_key_spend_witness(&user_sig, 0)`, with no restriction on the embedded sighash type.
- The protocol's own signing routine, `sign_withdrawal_output` (core/src/test/common/setup_utils.rs:499-543), computes the sighash with `sighash::TapSighashType::SinglePlusAnyoneCanPay` [1](#0-0) . `SIGHASH_SINGLE | ANYONECANPAY` commits only to the spent input and the output at the same index (the user payout output); it does **not** cover the anchor output, the OP_RETURN operator-attribution output, or any other inputs.
- This means the withdrawing party — who legitimately created and possesses this signature since it authorizes their own withdrawal — can construct `payout_tx'` spending the same `withdrawal_utxo` as input 0, preserving the required output 0 (so the same signature validates), but freely omitting/corrupting the OP_RETURN and adding their own additional fee input(s) via ANYONECANPAY, producing a higher-fee, standard, valid competing transaction that replaces the operator's `payout_tx` in the mempool before confirmation.
- On confirmation, `get_payout_txs_for_withdrawal_utxos` (core/src/database/verifier.rs:170-196) joins `withdrawals` to `bitcoin_syncer_spent_utxos` purely by `(withdrawal_utxo_txid, withdrawal_utxo_vout)`, so it naturally returns the attacker's replacement `txid`, not the operator's original.
- `update_finalized_payouts` (core/src/verifier.rs:2283-2353) parses the OP_RETURN of whichever transaction actually spent the UTXO; when it is missing/invalid it explicitly sets `operator_xonly_pk = None` [2](#0-1) , and `update_payout_txs_and_payer_operator_xonly_pk` (core/src/database/verifier.rs:199-251) unconditionally overwrites `payout_txid`, `payout_payer_operator_xonly_pk`, `payout_tx_blockhash` for that `idx` with no uniqueness/ownership check protecting a previously-intended payer.
- `get_first_unhandled_payout_by_operator_xonly_pk` (core/src/database/verifier.rs:282-313) filters `WHERE payout_payer_operator_xonly_pk = $1`; with the column set to `NULL`, this predicate is never true for any operator xonly pk, so `PayoutCheckerTask::run_once` (core/src/task/payout_checker.rs:39-111) never picks up this withdrawal for the honest operator, and `mark_payout_handled`/`handle_finalized_payout`/kickoff/reimburse are never triggered for it. `send_asserts` (core/src/operator.rs:1275-1295) independently confirms this dead end by erroring when `payout_op_xonly_pk_opt` is `None`.
- No existing guard (`Verifier::is_deposit_valid`, `Operator::is_profitable`, `SECP.verify_schnorr`, the presigned tx graph, or a DB uniqueness constraint) prevents this: `is_profitable` only screens the operator's own decision to front the payout, and Bitcoin/Taproot signature verification is satisfied by construction since the sighash flag permits the malleation.

### Impact Explanation
The withdrawal row (`withdrawals.idx`) becomes permanently unattributed to any operator (`payout_payer_operator_xonly_pk = NULL`), even though the honest operator broadcast (and potentially CPFP-funded) the original `payout_tx` for that withdrawal. This operator can never be scheduled for `handle_finalized_payout`/kickoff/reimbursement for this withdrawal — an honest operator permanently unable to be reimbursed, which the rules classify as Critical. The attack is repeatable per withdrawal and does not require compromising any verifier, operator, or aggregator; it only requires the withdrawing user (who already legitimately possesses the SIGHASH_SINGLE|ANYONECANPAY signature for their own withdrawal) to win a single mempool replacement race. It can be repeated across every withdrawal serviced by any operator, since the vulnerable code path (`create_payout_txhandler`, `update_finalized_payouts`, `get_first_unhandled_payout_by_operator_xonly_pk`) is common to all deposits/withdrawals/operators.

### Likelihood Explanation
Preconditions: an operator has broadcast `payout_tx` for a withdrawal but it has not yet confirmed; the withdrawing party (who legitimately owns the `input_signature` with `SinglePlusAnyoneCanPay`) constructs and broadcasts a higher-fee `payout_tx'` spending the identical `withdrawal_utxo`, satisfying the same signed output but stripping/corrupting the OP_RETURN and adding their own fee input. Cost to the attacker is only the added transaction fee needed to outbid the operator's fee in the mempool (a small amount of BTC), and no special privileges, key shares, or infrastructure access are needed — this is fully within the defined unprivileged attacker capabilities ("choose... a Schnorr signature and its sighash flag"). This is feasible on any regtest/mainnet deployment and is repeatable for every withdrawal.

### Recommendation
Do not accept withdrawal signatures with sighash flags that fail to bind the OP_RETURN attribution output; require `SIGHASH_ALL` (or `ALL|ANYONECANPAY` if additional operator fee inputs must remain flexible while still covering all outputs) so the operator-identity OP_RETURN output cannot be stripped or altered without invalidating the signature. Additionally, once a withdrawal's `payout_txid`/`payout_payer_operator_xonly_pk` has been set for a given `idx`, reject/alert on a "payer" set to `NULL` overwriting a previous non-null value (or vice versa) rather than silently accepting whichever transaction happened to confirm, and consider rejecting `WithdrawParams` whose sighash type does not cover all payout-tx outputs at the RPC-parsing layer (`core/src/rpc/parser/operator.rs`).
