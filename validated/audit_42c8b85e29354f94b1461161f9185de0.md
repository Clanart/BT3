## Analysis: Locked ether in `IntentGatewayV2.placeOrder` (Tron contracts)

**Core broken invariant from the report**: a `payable` function accepts `msg.value` greater than what is actually needed, and the contract has no logic to return the surplus — permanently locking it.

I checked every native-token entry point in the main EVM contracts (`evm/src/apps/IntentGatewayV2.sol`, `IntrinsicIntents.sol`, `ExtrinsicIntents.sol`, `EvmHost.sol`, `WrappedHyperFungibleToken*.sol`) and all of them consistently track a local `msgValue` and refund any leftover native token to `msg.sender` at the end of execution, e.g.: [1](#0-0) 

The **Tron** fork of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) reimplements the same `placeOrder` flow but drops this final refund step.

### Title
Unrefunded native-token overpayment permanently locks ether in `IntentGatewayV2.placeOrder` (Tron contracts) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` is `payable` and, like its mainline EVM counterpart, tracks a local `msgValue` variable that is decremented as native-token order inputs and the native-paid fee-swap consume it. In the mainline contract this leftover `msgValue` is explicitly refunded to `msg.sender` after the fee-escrow block. The Tron variant contains the identical fee-escrow block but the function ends (emits `OrderPlaced` and returns) without ever returning the unused `msgValue`.

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol`: [2](#0-1) 

decrements `msgValue` for native inputs: [3](#0-2) 

and for the fee swap: [4](#0-3) 

After the fee-escrow branch the function immediately emits `OrderPlaced` and returns — there is no `if (msgValue > 0) { msg.sender.call{value: msgValue}(""); }` block, unlike the mainline contract's equivalent function which explicitly performs this refund: [1](#0-0) 

Any `msg.value` sent above `sum(native order.inputs) + native fee-swap cost` is silently absorbed by the contract with no accounting, no event, and no withdrawal path back to the sender. The predispatch branch of the Tron contract has the same gap — `msgValue` is only consumed for predispatch assets, never refunded.

### Impact Explanation
This is a direct fund-loss/lock bug matching the bounty's "stealing or loss of funds" category. Any user who overestimates the required native amount when calling `placeOrder{value: X}(...)` — a very easy mistake since `order.fees`-to-native-token conversion via `swapETHForExactTokens` is imprecise and users must estimate slippage — loses the difference permanently. There is no governance sweep, no owner withdrawal, and no other function in the Tron contract that can recover ether stuck this way (the only privileged function found is `setParams`, which does not touch balances). This exactly mirrors the reported `Listing.buyFixedSale` bug: no validation rejecting overpayment and no recovery mechanism.

### Likelihood Explanation
High. `placeOrder` is a fully public, unprivileged entry point that is the primary way users interact with the Intent Gateway. No malicious peer, relayer, or governance actor is required — an ordinary user calling the same function that works correctly on the mainline EVM deployment (which always refunds) will lose funds if they replicate the same call pattern (or use tooling/SDK built for the mainline contract) against the Tron deployment.

### Recommendation
Add the same unspent-native-token refund used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract's `placeOrder` (and to the predispatch-with-native-input branch), reverting on failed refund with `InsufficientNativeToken()` to match the mainline behavior. Additionally, add a governance-gated sweep function for pre-existing stuck balances if the Tron contract is already deployed.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with a native-token order input, e.g. `order.inputs[0] = {token: address(0), amount: 1 ether}` and `order.fees = 0`.
2. Call `placeOrder{value: 2 ether}(order, graffiti)`.
3. Trace execution: `msgValue` starts at `2 ether`, is decremented by `1 ether` in the native-input loop (line ~450-451), leaving `msgValue == 1 ether`. Since `order.fees == 0`, the fee-escrow block is skipped entirely.
4. Function reaches `emit OrderPlaced(...)` and returns; the extra `1 ether` remains in the contract's balance with no accounting entry (`_orders[commitment][address(0)]` only records `1 ether`), and no code path exists to return it to the sender.

**Caveat**: I could not fully enumerate every function in the Tron contract (the `grep_search` for withdraw/sweep functions returned 9 matches I was unable to inspect before running out of iterations) — it's possible there is a separate admin sweep function elsewhere in that file that could recover the funds, though even then a permissioned sweep does not eliminate the user-fund-loss/lock impact since it would go to the admin rather than back to the original overpaying user. I recommend a Devin session or further inspection of the full file to confirm the absence of a compensating recovery path before treating this as fully final.

    function placeOrder(Order memory order, bytes32 graffiti) public payable {
        // Validate that order has inputs
        if (order.inputs.length == 0) revert InvalidInput();

        address hostAddr = host();
        // fill out the order preludes
        order.user = bytes32(uint256(uint160(msg.sender)));
        order.source = IDispatcher(hostAddr).host();
        order.nonce = _nonce++;

        // Calculate reduced inputs (after protocol fees) for commitment and escrow
        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                uint256 originalAmount = order.inputs[i].amount;
                uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
                uint256 reducedAmount = originalAmount - protocolFee;
                address token = address(uint160(uint256(order.inputs[i].token)));

                // Emit DustCollected for protocol fee if non-zero
                if (protocolFee > 0) emit DustCollected(token, protocolFee);

                reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
                unchecked {
                    ++i;
                }
            }

            // Temporarily swap inputs to calculate commitment with reduced amounts
            TokenInfo[] memory originalInputs = order.inputs;
            order.inputs = reducedInputs;
            commitment = keccak256(abi.encode(order));
            order.inputs = originalInputs;
        } else {
            // No protocol fees, use order.inputs directly
            reducedInputs = order.inputs;
            commitment = keccak256(abi.encode(order));
        }

        // escrow tokens
        uint256 msgValue = msg.value;
