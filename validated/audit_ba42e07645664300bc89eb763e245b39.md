### Title
Expired consensus clients keep authorizing request/response/timeout message flow via stale `StateCommitment`s - ([File: modules/ismp/core/src/host.rs](), [File: modules/ismp/core/src/handlers/request.rs](), [File: modules/ismp/core/src/handlers/response.rs](), [File: modules/ismp/core/src/handlers/timeout.rs]())

### Summary
`IsmpHost::is_expired` is the only mechanism that enforces the unbonding-period invariant on a consensus client, but it is invoked exclusively from the consensus-update handler. The message-processing handlers for requests, responses, and timeouts never call it, so they keep accepting proofs verified against `StateCommitment`s that were produced by a consensus client that is now past its `unbonding_period`.

### Finding Description
`IsmpHost::is_expired` compares `host.timestamp()` against `consensus_update_time` plus `unbonding_period`, returning `Error::UnbondingPeriodElapsed` once that period has passed without a fresh consensus update: [1](#0-0) 

This check is only ever invoked in `handlers/consensus.rs::update_client`, before a *new* consensus proof is verified and applied: [2](#0-1) 

It is notably absent from `freeze_client`, and — critically — from all three message-consuming handlers:

- `handlers/request.rs::handle` only checks `validate_state_machine`, receipt/timeout/proxy conditions, and `state_machine_commitment` existence + `verify_membership`, with no `is_expired` call anywhere in the function: [3](#0-2) 

- `handlers/response.rs::handle` similarly only checks timeout/proxy/commitment/receipt conditions and `verify_state_proof` against the stored `state`, without checking client expiry: [4](#0-3) 

- `handlers/timeout.rs::handle` (both `Post` and `Get` branches) checks `request_commitment` existence and elapsed timeout against the stored `state.timestamp()` / `host.timestamp()`, again without any `is_expired` call: [5](#0-4) 

Once a `StateMachineHeight -> StateCommitment` mapping has been stored via a prior successful consensus update, it remains in storage indefinitely (`store_state_machine_commitment` / `delete_state_commitment` are the only mutators, and nothing purges commitments when the parent consensus client expires). Because the per-message handlers only require: (1) the state commitment to exist in storage, and (2) the membership/non-membership/state proof to verify against it — with the challenge period gated in `validate_state_machine` — they will happily keep processing new requests, responses, and timeouts referencing state committed while the consensus client was still bonded, even long after the client's `unbonding_period` has elapsed with no update. The unbonding-period invariant exists specifically because, once validators/provers are past their unbonding period, equivocation/forking that state is no longer economically punishable, so continuing to trust commitments derived from that consensus client is unsound.

### Impact Explanation
An unprivileged relayer (submitting otherwise-legitimate proofs, not requiring any privileged operator) can continue to submit request/response/timeout messages that get accepted against a `StateCommitment` produced by a now-unbonded/expired consensus client. This directly matches the bounty's "false proof/state acceptance" and "unauthorized transaction or execution" impact categories, since the client's security guarantee (backed by slashable stake within the unbonding window) no longer holds, yet the protocol keeps treating its historical commitments as canonical for new cross-chain message flow — potentially authorizing execution based on state that could since have been proven fraudulent/forked without consequence to the original validator set.

### Likelihood Explanation
High. This requires no privileged action and no cooperation from a malicious relayer beyond simply continuing normal operation: if the consensus client for a given `consensus_state_id`/`StateMachineId` is not updated for longer than its `unbonding_period` (e.g., due to relayer inactivity, chain congestion, or an attacker deliberately withholding updates while pre-positioning a stale/forkable commitment), all subsequent request/response/timeout submissions referencing prior heights under that client continue to be processed normally, since none of the three handlers gate on `is_expired`.

### Recommendation
Call `host.is_expired(consensus_state_id)` (derived from the `StateMachineId` tied to `msg.proof.height.id` / `timeout_proof.height.id`) at the top of `handlers/request.rs::handle`, `handlers/response.rs::handle`, and `handlers/timeout.rs::handle`, before accepting any proof verified against a stored `StateCommitment`. Reject with `Error::UnbondingPeriodElapsed` if the backing consensus client has expired, mirroring the check already performed in `handlers/consensus.rs::update_client`. Consider also purging/marking stale `StateCommitment`s once a consensus client is discovered to be expired, so relayers cannot rely on old, unpurged mappings.

### Proof of Concept
1. Register a consensus client and let it commit a `StateMachineHeight -> StateCommitment` via `update_client` (populating `state_machine_commitment`, `consensus_update_time`, etc.).
2. Advance `host.timestamp()` (e.g., via block production over time) past `consensus_update_time + unbonding_period` for that `consensus_state_id`, without ever calling `update_client` again — so `host.is_expired(consensus_state_id)` now returns `Err(Error::UnbondingPeriodElapsed)`.
3. Submit a `RequestMessage` / `ResponseMessage` / `TimeoutMessage` whose `proof.height` references the previously stored (now-stale) `StateMachineHeight`, with a valid membership/non-membership proof against that old `StateCommitment`.
4. Observe that `handlers/request.rs::handle` (or `response.rs`/`timeout.rs`) succeeds: `validate_state_machine`, `state_machine_commitment`, and `verify_membership`/`verify_non_membership`/`verify_state_proof` all pass because none of them call `is_expired`, and the message is dispatched to the destination module — demonstrating that expired consensus clients keep authorizing new message flow, contrary to the intended invariant enforced only in the consensus-update path.

	/// Check if the client has expired since the last update
	fn is_expired(&self, consensus_state_id: ConsensusStateId) -> Result<(), Error> {
		let host_timestamp = self.timestamp();
		let unbonding_period = self
			.unbonding_period(consensus_state_id)
			.ok_or(Error::UnnbondingPeriodNotConfigured { consensus_state_id })?;
		let last_update = self.consensus_update_time(consensus_state_id)?;
		if host_timestamp.saturating_sub(last_update) >= unbonding_period {
			Err(Error::UnbondingPeriodElapsed { consensus_state_id })?
		}

		Ok(())
	}
