### Title
Quadratic CPU exhaustion via attacker-controlled `n`/`t` in `ThresholdKeys::read` Lagrange interpolation — (File: crypto/dkg/src/lib.rs)

### Summary
The XStream advisory (CVE-2021-21348) is a resource-exhaustion bug class: untrusted input drives computation whose cost is disproportionate to input size, pinning a CPU thread. Serai's analog is `ThresholdKeys::<C>::read`, which accepts an attacker-supplied `n` (participants) and `t` (threshold) as `u16` fields and then performs `O(t^2)` field arithmetic during `ThresholdKeys::new` group-key derivation via Lagrange interpolation. A small serialized blob (~4 MB) can force billions of field multiplications and thousands of field inversions, occupying a thread far longer than the input size justifies.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, `i` directly from the reader with `n` up to `u16::MAX` (65535), then reads `n` verification shares and calls `ThresholdKeys::new` [1](#0-0) .

`ThresholdKeys::new` computes the group key by summing `verification_shares[i] * interpolation_factor(*i, &t)` for `i` in `1..=t` [2](#0-1) .

For `Interpolation::Lagrange`, `interpolation_factor` iterates over the entire `included` set (size `t`) performing a field multiplication per element, plus one field inversion per call [3](#0-2) . Total cost is therefore `t * (t` multiplications `+ 1` inversion`)` — quadratic in the attacker-chosen `t`. With `t = n = 65535`, that is ~4.3×10⁹ field multiplications and 65535 inversions triggered by only `(2 + 2 + 2 + 1 + 32 + 65535*point_len)` bytes of input (≈2–4 MB depending on the ciphersuite).

`ThresholdParams::new` bounds `i` and `t` by `n` but places no practical cap on `n` [4](#0-3) , and `Interpolation::Constant` is only usable when `t == n` — which does not reduce the quadratic path since Lagrange is always selectable [5](#0-4) .

### Impact Explanation
An unprivileged party who can feed bytes to `ThresholdKeys::read` (e.g., any context where serialized threshold keys/key-material messages from peers are deserialized) can pin a CPU thread for orders of magnitude longer than the input size — the direct analog of the XStream ReDoS where a crafted input occupies a thread consuming maximum CPU. On a validator/processor handling consensus-adjacent messages, repeated submissions degrade or halt signing/DKG processing. The same quadratic behavior is re-triggered on every `view()` call over an attacker-sized `included` set (each `interpolation_factor` call is `O(included)`, and it is invoked once per included signer) [6](#0-5) .

### Likelihood Explanation
Reachability requires an integrator path that deserializes `ThresholdKeys` from untrusted bytes — per scope, `ThresholdKeys::read` is an accepted untrusted-bytes entry point. The attacker only controls public fields (`t`, `n`, verification-share encodings); no key material or malicious-validator assumptions are needed, and the deserialization itself is well-formed (all points canonical). The cost is `O(n^2)` field work plus point decompression of `n` points; note the `n` `read_G` calls are linear and input-proportional, so the quadratic group-key computation is the amplifying term. Severity: Medium — availability loss only, no key/share leakage.

### Recommendation
- Enforce a protocol-level maximum on `n`/`t` inside `ThresholdKeys::read`/`ThresholdParams::new` (e.g., `MAX_KEY_SHARES_PER_SET` already exists in the codebase) before allocating or interpolating.
- Alternatively compute the group key incrementally/`O(n)` (e.g., via summed Lagrange precomputation or caching denominators), or gate `read` behind a caller-supplied size limit.
- Apply the same cap to `view()`'s `included` set size.

### Proof of Concept
```rust
// crypto/dkg — attacker-crafted ThresholdKeys bytes for C = Ristretto/k256
// Build a serialized ThresholdKeys with t = n = u16::MAX, Lagrange interpolation.
let n: u16 = u16::MAX;
let mut bytes = vec![];
bytes.extend((C::ID.len() as u32).to_le_bytes());
bytes.extend(C::ID);
bytes.extend(n.to_le_bytes());            // t = 65535
bytes.extend(n.to_le_bytes());            // n = 65535
bytes.extend(1u16.to_le_bytes());         // i = 1
bytes.push(1);                            // Interpolation::Lagrange
bytes.extend(C::F::ONE.to_repr().as_ref()); // secret_share
let g = C::generator().to_bytes();
for _ in 0 .. n {
    bytes.extend(g.as_ref());             // n verification shares (~2–4 MB total)
}
// Triggers t * t field multiplications + t inversions in ThresholdKeys::new
// (~4.3e9 muls for n = 65535) — CPU pinned on ~megabytes of input.
let _ = ThresholdKeys::<C>::read(&mut bytes.as_slice());
```

  fn interpolation_factor(&self, i: Participant, included: &[Participant]) -> F {
    match self {
      Interpolation::Constant(c) => c[usize::from(u16::from(i) - 1)],
      Interpolation::Lagrange => {
        let i_f = F::from(u64::from(u16::from(i)));

        let mut num = F::ONE;
        let mut denom = F::ONE;
        for l in included {
          if i == *l {
            continue;
          }

          let share = F::from(u64::from(u16::from(*l)));
          num *= share;
          denom *= share - i_f;
        }

        // Safe as this will only be 0 if we're part of the above loop
        // (which we have an if case to avoid)
        num * denom.invert().unwrap()
      }
    }
  }
