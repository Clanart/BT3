### Title
FROST preprocess seed cached per DKG-confirmation attempt is never deleted, allowing nonce reuse across distinct `set_keys` messages - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The Nextcloud Deck advisory concerns resources of deleted entities remaining accessible. The closest reachable analog in Serai is the coordinator's `CachedPreprocesses` table: the FROST preprocess RNG seed for the DKG-confirmation signing protocol is keyed only by `(b"DkgConfirmer", attempt)` and is **never deleted** (`CachedPreprocesses` is only ever `set`/`get`). Because `DkgConfirmer::share` and `DkgConfirmer::complete` both invoke `share_internal` → `preprocess_internal`, which deterministically rebuilds the same nonces from the cached seed, a signer can produce two Schnorrkel signature shares over *different* messages with the *same* nonces if the `key_pair`/`removed` set differs between the two calls — the classic nonce-reuse secret-share recovery.

### Finding Description
`preprocess_internal` stores a ChaCha20-seeded preprocess under `CachedPreprocesses: (context) -> [u8; 32]` (coordinator/src/tributary/signing_protocol.rs:86-148). For `DkgConfirmer`, `context = (b"DkgConfirmer", self.attempt)` (line 275). On any subsequent call with the same attempt, the existing entry is returned and `AlgorithmSignMachine::from_cache` re-derives identical `nonces` and `commitments` via `seeded_preprocess` (crypto/frost/src/sign.rs:121-144). A grep confirms there is no `CachedPreprocesses::del`/`remove` anywhere — the entry persists for the lifetime of the DB, violating the `MUST only be used once` contract documented on `CachedPreprocess` (crypto/frost/src/sign.rs:84-92, 216-224).

`share(preprocesses, key_pair)` signs `set_keys_message(set, removed, key_pair)` (lines 288-310). `complete(preprocesses, key_pair, shares)` calls `share_internal` *again* (lines 312-327), producing a second signature share. If the `key_pair` argument — which is attacker-influenced public input carried in the tributary DKG-confirmation data — differs between the share that was already published and the call made at completion time (or if a participant is slashed/removed mid-protocol, changing `self.removed`, which is resolved per-call from `removed_as_of_dkg_attempt` but the message encodes `self.removed`), the same nonce `d + be` is committed to two distinct messages `m1 ≠ m2`. Two Schnorr shares `s1 = k + c1·x`, `s2 = k + c2·x` yield `x = (s1 − s2)/(c1 − c2)` — recovery of the signer's MuSig/FROST secret share.

### Impact Explanation
Recovery of a validator's private key share for the set's MuSig key compromises the threshold signing key for that tributary set: an attacker who collects a victim's two shares can combine with other compromised/threshold shares, and at minimum can reconstruct the victim's contribution, undermining the confidentiality assumption underlying every signature the set produces (key confirmation, slash reports). This is secret-key-material leakage reachable through publicly submitted preprocess/confirmation data — squarely High by the analog rules.

### Likelihood Explanation
Likelihood is moderate, not certain: the exploit requires the same `attempt` to drive `share`/`complete` paths with differing `(removed, key_pair)` message inputs. `DkgConfirmer::new` snapshots `removed` per construction, and `share`/`complete` are invoked by the coordinator as confirmation data accumulates (handle.rs `DkgConfirmation` handling); a malicious validator can publish `DkgConfirmation` preprocesses/shares for an attempt while votes to remove a participant are in flight, or conflicting `key_pair` values can arise if the DKG produced divergent results. Because the seed is keyed only by attempt and never cleared, *any* second signing under that attempt — including after a reboot, where `CachedPreprocesses` persists while in-memory machine state is lost — deterministically reuses the nonces. The persistence-across-restart property makes a reuse event realistic rather than purely adversarial.

### Recommendation
- Delete the cached preprocess the first time it is consumed: call `CachedPreprocesses::del` (add a `del` to `create_db!` usage) in `share_internal`/`sign` before producing the share, so a context can mint at most one nonce set.
- Bind the signed message into the cache key (e.g., context = `(label, attempt, hash(msg))`) so differing `key_pair`/`removed` inputs cannot collide with an existing seed.
- At minimum, record the message hash alongside the seed and refuse to sign a different message under a reused preprocess.

### Proof of Concept
1. Attempt `a` of the DKG reaches confirmation. `DkgConfirmer::share(preprocesses, key_pair_A)` is invoked; `preprocess_internal` finds no `CachedPreprocesses[(b"DkgConfirmer", a)]`, stores seed `S`, derives nonces `k`, signs `m_A = set_keys_message(set, removed_A, key_pair_A)`, publishes share `s_A = k + H(R‖P‖m_A)·x`.
2. A `RemoveParticipantDueToDkg` vote reaches `t` (or a second confirmation round supplies `key_pair_B ≠ key_pair_A`), so `complete`/`share` is later invoked with `key_pair_B` and/or `removed_B ≠ removed_A`.
3. `share_internal` → `preprocess_internal` returns the still-present seed `S` → identical `k`. It signs `m_B ≠ m_A`, producing `s_B = k + H(R‖P‖m_B)·x`.
4. `x = (s_A − s_B) / (H(R‖P‖m_A) − H(R‖P‖m_B)) mod l` — the signer's secret share is recovered from two public shares. The same trigger occurs on coordinator restart: the DB seed survives while the ephemeral `AlgorithmSignMachine` does not, so any re-driven confirmation for attempt `a` reuses `k`.
