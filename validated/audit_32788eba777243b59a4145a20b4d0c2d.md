### Title
Precompiled contract execution bypasses the OpcodeComputationCostLimit check that bounds opcode execution time - (File: blockchain/vm/evm.go)

### Summary
The reported Unbound bug is that a specific code path (DS-record negative-cache consultation) forgot to apply a pre-existing computation limit (the NSEC3 hash-iteration cap) that other code paths respect, letting an attacker force unbounded hashing while holding a global lock. Kaia has an analogous split-enforcement pattern in its `ComputationCostLimit` mechanism: the limit is only checked inside the EVM opcode loop, not on the precompiled-contract call path.

### Finding Description
Kaia bounds per-transaction EVM wall-clock cost with `ComputationCostLimit`, checked once per opcode in `EVMInterpreter.Run`: [1](#0-0) 

However, when a call target is a precompiled contract, execution goes through `run()` in `evm.go`, which invokes `RunPrecompiledContract`, adds the reported `computationCost` to `evm.opcodeComputationCostSum`, and returns — with **no check** against `ComputationCostLimit` on this path: [2](#0-1) 

Contrast this with the opcode loop, which checks the running sum immediately after every increment (interpreter.go:262-265 above). The precompile path never performs that comparison at all; it merely accumulates the cost and lets a possible transaction-level "resource" abort happen only later if/when control returns to an interpreter loop for another opcode (e.g. via a nested `CALL`). If a transaction's top-level entry point (`tx.to`) is itself a precompiled contract address (e.g. `MODEXP`, `BLAKE2F`, `BLS12_G2MULTIEXP`, `KZG` point evaluation), `EVM.Call` invokes `run()` directly and the interpreter loop is never entered for that call frame at all: [3](#0-2) 

In that scenario the `ComputationCostLimit` accounting is updated but never consulted for the entire transaction — the enforcement mechanism that is present for bytecode execution is simply absent for the "trivial" precompile-only call path.

### Impact Explanation
`ComputationCostLimit` exists specifically to bound wall-clock CPU time independent of gas pricing, because gas costs for cryptographic precompiles (BLS12-381 pairing/multiexp, MODEXP, BLAKE2F rounds) are not perfectly calibrated to real CPU cost. If gas pricing under-prices actual CPU time for some precompile/input combination, a transaction that calls that precompile directly as `tx.to` (rather than through a contract's bytecode) never has its computation-cost sum checked against the limit, defeating the purpose of the `ComputationCostLimit` safety net for that specific call pattern. This could let a single transaction consume more wall-clock CPU than the network's per-tx time budget allows, which is a resource/availability concern for block producers and could contribute to slower block processing across the network (state divergence is not the primary concern here — this is closer to the DoS class in the reference report).

### Likelihood Explanation
Likelihood is speculative and lower than the report's underlying CVE, for two reasons I could not fully rule out in the time available:
1. Gas costs for the affected precompiles (in `blockchain/vm/contracts.go`) may already be well-calibrated to real CPU time, meaning the "missing check" has no practical excess-CPU headroom to exploit — I was not able to benchmark actual precompile CPU cost vs. gas within this session.
2. Even in the normal (non-top-level) case, the check in the interpreter loop only fires *after* a costly single operation/precompile call completes — so "delayed" enforcement is arguably the intended design (same as most gas/cost accounting systems), not a bug. The genuinely different case is only the top-level-call-to-precompile path, which is a narrow reachable surface (any unprivileged sender can construct such a transaction, satisfying the "unprivileged transaction sender" reachability requirement).

### Recommendation
Add an explicit `opcodeComputationCostSum > ComputationCostLimit` check immediately after `evm.opcodeComputationCostSum += computationCost` in `run()` (blockchain/vm/evm.go:96), returning `ErrOpcodeComputationCostLimitReached` (or an equivalent early-return) so that the precompile call path enforces the same invariant as the opcode-loop path, including for top-level transactions whose `to` address is a precompiled contract.

### Proof of Concept
Conceptual PoC only (not executed/verified against a live node in this session):
1. Craft a transaction with `to` = a computation-heavy precompile address (e.g. `BLS12_G2MULTIEXP` or `MODEXP` with EIP-7883/oversized parameters) and `data` = an expensive-but-gas-legal input.
2. Send it as a top-level transaction (not via a wrapper contract call).
3. Because `EVM.Call` → `run()` executes the precompile directly without ever entering `EVMInterpreter.Run`'s opcode loop, `ComputationCostLimit` is never checked for this transaction, regardless of how high `computationCost` is relative to the configured limit.

I was unable to confirm with certainty (within tool budget) whether the gas cost tables for these precompiles leave meaningful "excess CPU time" headroom beyond what `ComputationCostLimit` is meant to catch — this would need a Devin session with the ability to run/benchmark the code to fully validate exploitability.
