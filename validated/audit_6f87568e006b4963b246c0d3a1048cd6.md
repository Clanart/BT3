### Title
Unbounded `reward.mintingamount` governance parameter allows the governing node to mint unlimited KAIA supply per block - (File: kaiax/gov/param.go)

### Summary
The `RewardMintingAmount` governance parameter, which directly determines how many native KAIA tokens are minted at every block (the block reward's `M` component), has no upper-bound validation in its `FormatChecker`, unlike other parameters such as `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` (which are checked against each other) or `RewardRatio`/`RewardKip82Ratio` (which must sum to exactly 100).

### Finding Description
`Params[RewardMintingAmount]` uses `noopFormatChecker`, meaning any non-negative or even unchecked `*big.Int` value canonicalized via `bigIntCanonicalizer` is accepted as a valid vote value: [1](#0-0) 
Contrast this with `RewardMinimumStake` and `RewardStakingRewardThreshold`, which at least enforce `v.Sign() >= 0`: [2](#0-1) 

This vote is processed through `checkConsistency` in the header-governance vote-verification path, which contains explicit cross-parameter consistency checks for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee` but treats `gov.RewardMintingAmount` (along with several other parameters) as unconditionally valid with "no more checks here": [3](#0-2) 

The vote is submitted via the permissionless `governance_vote` RPC API, gated only by governing-node/council checks, not by any sanity bound on the minted amount: [4](#0-3) 

Once ratified at an epoch boundary, `RewardConfig.MintingAmount` is read directly from the param set and used, unclamped, as the minting source `M` for every block's reward distribution (`getDeferredRewardFullKore`, `getDeferredRewardFullFlex`, etc.), which is then credited to `state.AddBalance` for stakers, proposer, and funds: [5](#0-4) [6](#0-5) 

This is directly analogous to the reported bug class ("owner can mint all of the NFTs" / unrestricted, uncapped minting), except here the mint-amount-per-block is a chain-wide inflation parameter with no protocol-enforced ceiling, reachable by whichever address currently holds the `governance.governingnode` role (in `single` mode) — the sole gatekeeper of GC's parameter-setting privilege in Kaia's governance model — or, in `none` mode, by any council member's last vote in an epoch.

### Impact Explanation
If the governing node key is compromised, or a malicious/errant governing entity submits an oversized `reward.mintingamount` vote, once ratified at the next epoch boundary this directly inflates the native KAIA supply at every subsequent block indefinitely (until another vote corrects it), diluting all holders and potentially breaking arithmetic invariants downstream (e.g., overflow risk in `big.Int` multiplication paths across the reward-splitting logic, though `big.Int` arithmetic mitigates hard overflow). This is a critical, unbounded native-token supply-inflation vector.

### Likelihood Explanation
Likelihood is Medium: it requires control of the `governance.governingnode` address (or, in `none` mode, being any council member casting the last vote of an epoch) to submit the vote, which is a documented, permissioned but not fully permissionless privilege distinct from a simple owner-only smart-contract call — this is the closest analog reachable through the constrained/governance parameter surface. There is no additional sanity check preventing an extreme value once that vote is cast and ratified.

### Recommendation
Add an explicit upper bound (and/or rate-of-change limit) to the `RewardMintingAmount` `FormatChecker` in `kaiax/gov/param.go`, analogous to the bound checks already present for `Kip71LowerBoundBaseFee`/`Kip71UpperBoundBaseFee`, so that a single vote cannot set an arbitrarily large inflation amount per block.

### Proof of Concept
1. Governing node (in `single` governance mode) calls `governance_vote` with `name="reward.mintingamount"`, `value` set to an extremely large `*big.Int` (e.g., `"100000000000000000000000000"` — arbitrarily large, since `noopFormatChecker` accepts anything the canonicalizer parses). [4](#0-3) 
2. The vote passes `checkConsistency` unconditionally for `gov.RewardMintingAmount`. [7](#0-6) 
3. At the next epoch boundary the vote is ratified into `header.Governance` and becomes the effective `reward.mintingamount` starting the following epoch.
4. From that block onward, `NewRewardConfig` sets `rc.MintingAmount` to this value every block, and `FinalizeState`/`getDeferredRewardFull*` mint and distribute this amount as new KAIA to stakers/proposer/funds every block indefinitely. [8](#0-7) [6](#0-5)

func (api *headerGovAPI) Vote(name string, value any) (string, error) {
	var (
		voter     = api.h.nodeAddress
		nextBlock = api.h.Chain.CurrentBlock().NumberU64() + 1
		gp        = api.h.GetParamSet(nextBlock)
		gMode     = gp.GovernanceMode
	)

	if gMode == "single" && voter != gp.GoverningNode {
		return "", ErrVotePermissionDenied
	}

	vote := headergov.NewVoteData(voter, name, value)
	if vote == nil {
		return "", ErrInvalidKeyValue
	}

	if gov.DeprecatedAt(vote.Name(), api.h.ChainConfig.Rules(new(big.Int).SetUint64(nextBlock))) {
		return "", ErrDeprecatedVote
	}

	err := api.h.checkConsistency(nextBlock, vote)
	if err != nil {
		return "", err
	}

	// TODO-kaiax: add removevalidator vote check

	api.h.PushMyVotes(vote)
	return "(kaiax) Your vote is prepared. It will be put into the block header or applied when your node generates a block as a proposer. Note that your vote may be duplicate.", nil
}
