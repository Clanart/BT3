### Title
OP_RETURN data output excluded from weight/fee accounting allows exceeding size budget and underpaying fee - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts a caller-supplied `data` payload of up to 80 bytes and appends an OP_RETURN output to `tx_outs`, but computes the transaction weight, virtual size, required fee, and the `MAX_STANDARD_TX_WEIGHT` check using only `payments` — the OP_RETURN output is never included in `calculate_weight_vbytes`. The transaction therefore exceeds its accounted size budget (analogous to the sandbox-accounts-for-events flaw where self-defined parameters bypassed the intended budget), paying less fee than its real size requires and potentially producing a non-standard transaction.

### Finding Description
`calculate_weight_vbytes` builds its weight-estimation transaction's `output` list solely from `payments` (plus the optional change output):

- Outputs are constructed by mapping `payments` at `send.rs:85-93`, with change appended at `send.rs:95-99`.
- The OP_RETURN output is pushed onto `tx_outs` at `send.rs:194-202`, before the weight calculation at `send.rs:204`, yet that calculation never sees it.

Consequences:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) underprices the real transaction by the full serialized size of the OP_RETURN output (~11 bytes overhead + up to 80 bytes of data ≈ up to ~91 bytes, i.e. ~91 vbytes since OP_RETURN outputs are entirely non-witness).
2. The `TooLowFee` check at `send.rs:211` uses the underestimated vbytes, so a `fee_per_vbyte` at the boundary can produce a transaction whose actual fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` and will not relay.
3. The `TooLargeTransaction` check at `send.rs:241` uses the underestimated `weight`, so a transaction genuinely over `MAX_STANDARD_TX_WEIGHT` (400,000 WU) can pass validation — meaning the constructed, signed transaction is non-standard and unspendable on the network despite the API reporting success.

### Impact Explanation
`SignableTransaction` is the object the FROST `TransactionMachine`/`TransactionSignMachine` signs (`send.rs:273-285`, `send.rs:373-390`). An unprivileged requester who can cause the processor to construct a transaction with a `data` payload (the OP_RETURN is a documented feature, `send.rs:149`) causes the threshold group to sign a transaction that either underpays its real fee rate or exceeds standardness limits — funds are consumed as inputs/change but the transaction will not propagate or be mined, burning the fee budget claim the API accounted for. This mirrors the reported class: attacker-controlled parameters produce resource consumption beyond what the system validated and budgeted.

### Likelihood Explanation
Reachable whenever `data: Some(...)` is passed to `SignableTransaction::new` — a fully public input path requiring no malicious validator, no collusion, and no invalid curve/hash inputs. The miscount is unconditional: every byte of the OP_RETURN output is missing from every weight/vbyte computation. Exploiting the boundary cases (fee-rate edge or weight edge) only requires choosing `payments`/`inputs` sizes so the true size crosses a threshold the estimated size does not.

### Recommendation
Include the OP_RETURN output in the transaction used by `calculate_weight_vbytes` — i.e., compute weight over the actual `tx_outs` (payments + optional OP_RETURN + optional change) rather than only `payments`. Concretely, pass the fully assembled output list (or the `data`) into `calculate_weight_vbytes` at `send.rs:204` and `send.rs:225-226` so `needed_fee`, the `TooLowFee` check, and the `MAX_STANDARD_TX_WEIGHT` check reflect the transaction that will actually be signed and broadcast.

### Proof of Concept
```rust
// Conceptual: construct a SignableTransaction whose real weight exceeds
// MAX_STANDARD_TX_WEIGHT but whose estimated weight does not.

let data = vec![0u8; 80]; // maximal allowed OP_RETURN payload

// Choose many inputs/payments such that estimated weight is just below
// MAX_STANDARD_TX_WEIGHT (= 400_000 WU).
let stx = SignableTransaction::new(
    inputs,            // sized so payments-only weight < limit
    &payments,
    None,
    Some(data),        // +~91 vbytes of real, unaccounted output
    fee_per_vbyte,
).unwrap();            // succeeds: TooLargeTransaction never fires

// stx.tx's true weight > MAX_STANDARD_TX_WEIGHT -> non-standard, won't relay,
// yet TransactionMachine will produce a valid FROST signature over it.

// Fee-rate variant: with fee_per_vbyte = 1 and vbytes at the relay boundary,
// needed_fee passes the TooLowFee check at send.rs:211 while the actual
// fee rate of the broadcast TX is below DEFAULT_MIN_RELAY_TX_FEE.
```

The gap is the `payments`-only output list at `send.rs:85-93` versus the extra output pushed at `send.rs:194-202`, with all subsequent size/fee checks (`send.rs:204-243`) operating on the incomplete output set.
