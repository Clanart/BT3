### Title
Manual conflict resolutions are keyed only by file path and silently carried across rebase/cherry-pick commit boundaries, causing wrong content to be committed - (File: app/src/lib/stores/updates/changes-state.ts, app/src/lib/git/rebase.ts, app/src/lib/git/cherry-pick.ts)

### Summary
`updateConflictState` carries the `manualResolutions` map forward from the previous conflict state to the new one whenever the operation "kind" (rebase/merge) is unchanged, without checking whether the underlying commit being processed has changed. [1](#0-0)  When `continueRebase`/`continueCherryPick` are subsequently invoked, they apply any entry in `manualResolutions` to whichever working-directory file currently has that path, with no check that the resolution was captured for the current commit/conflict round. [2](#0-1) [3](#0-2) 

### Finding Description
`getConflictState` builds the app's conflict state purely from coarse Git markers (`rebaseInternalState`, `isCherryPickingHeadFound`, `mergeHeadFound`) plus whatever `manualResolutions` map is passed in. [4](#0-3)  `updateConflictState` decides which `manualResolutions` to use: if a previous conflict state existed, it reuses that map verbatim; only if no previous conflict state existed does it start with an empty map. [5](#0-4)  This is confirmed by the unit test "preserves manual resolutions when a rebase is detected", which explicitly asserts the same `manualResolutions` map survives a new `getStatus` snapshot as long as `status.rebaseInternalState` is still non-null. [6](#0-5) 

Crucially, the code that decides whether to reuse the map checks only whether the *operation kind* (rebase vs merge vs cherry-pick) is unchanged (`isRebaseConflictState(prevConflictState)` etc.), not whether it's still the *same commit* being rebased/cherry-picked. [7](#0-6)  During a multi-commit rebase or cherry-pick, `rebaseInternalState`/`isCherryPickingHeadFound` remain true across every commit in the sequence — only the current commit SHA (`rebaseCurrentCommit`/`CHERRY_PICK_HEAD`) changes between rounds. So after the user resolves a conflict on `path/to/file.js` for commit N (e.g. choosing "theirs") and clicks continue, if the app then hits a *new* conflict on that same path for commit N+1 (a very common pattern for commits that repeatedly touch the same file), the stale `theirs`/`ours` choice from commit N is silently re-applied to commit N+1's unrelated conflict.

The apply-side code in both `continueRebase` and `continueCherryPick` has no defense against this: it looks resolutions up by `path` alone (`manualResolutions.has(f.path)` / `files.find(f => f.path === path)`) and calls `stageManualConflictResolution` unconditionally for a match, with no verification of commit identity, content hash, or "when" the resolution was recorded. [8](#0-7) [9](#0-8)  This is the same broken-invariant class as the Sherlock report: a stale "resolved" flag/value is trusted based on a coarse state check (agent `status == Wounded` / repo `rebaseInternalState != null`) instead of verifying it corresponds to the current instance (the specific wound round / the specific commit conflict).

The UI layer (`updateMultiCommitOperationConflictsIfFound` in `app-store.ts`) reinforces this by pushing `conflictState.manualResolutions` straight into the active `ShowConflicts`/`ShowCopilotConflicts` step on every status refresh, so the dialog the user sees for the new commit's conflict is pre-populated with the old resolution without any re-confirmation prompt. [10](#0-9) 

### Impact Explanation
The result is silent corruption of what the user commits/pushes: a repository-controlled sequence of commits that repeatedly conflict on the same file path (e.g. a malicious upstream branch crafted so that commits 1 and 2 both touch `config.json` in conflicting ways) can cause Desktop to auto-resolve commit 2's conflict using the user's choice for commit 1's conflict, without the user ever seeing or approving that specific resolution. Depending on which side ("ours"/"theirs") was chosen, this can silently drop or reintroduce attacker-controlled or victim-authored content into the resulting commit history that the user then pushes, believing they reviewed and resolved every conflict. This matches the report's core impact category: the user takes the correct remedial action (resolving conflicts) but the tool still produces a wrong/unintended outcome (a wrongly resolved commit) that the user is not warned about.

### Likelihood Explanation
This requires no local/admin access, no leaked credentials, and no unnatural user steps — only that the user rebases or cherry-picks a range of commits (a normal Desktop feature) where the attacker (a malicious/compromised remote or PR branch author) has crafted at least two commits in the range that conflict on the same file path against the base branch. This is a realistic scenario for any multi-commit rebase workflow and does not require any local corruption of the sequencer files — it flows entirely from normal `git rebase`/`git cherry-pick` conflict progression combined with Desktop's own state-management bug.

### Recommendation
Scope `manualResolutions` to the specific commit/conflict round instead of only the operation kind. Concretely:
- In `updateConflictState` (app/src/lib/stores/updates/changes-state.ts), compare the commit being processed (e.g. `rebaseInternalState`'s current commit SHA for rebase, `CHERRY_PICK_HEAD` for cherry-pick) between `prevConflictState` and the new status, and reset `manualResolutions` to an empty map whenever that commit identity changes, even though the coarse "still rebasing"/"still cherry-picking" flag remains true.
- In `continueRebase`/`continueCherryPick` (app/src/lib/git/rebase.ts, app/src/lib/git/cherry-pick.ts), additionally validate that the current in-progress commit (from `readRebaseHead`/`CHERRY_PICK_HEAD`) matches the commit the `manualResolutions` map was captured against before applying any entry, discarding stale entries rather than silently staging them.

### Proof of Concept
Not independently executed here (this analysis is based on static code review of the local `Kirstentat/desktop--020` repository, not a running Desktop instance). The following steps describe the reproducible flow supported directly by the cited code:
1. Attacker prepares a feature branch with two commits, both modifying the same file path (`shared.txt`) in ways that both conflict with the base branch when rebased/cherry-picked.
2. Victim opens the branch in Desktop and starts a rebase/cherry-pick spanning both commits (`launchRebaseOperation` in `app/src/ui/dispatcher/dispatcher.ts:588-654`, or the cherry-pick flow in `app/src/ui/multi-commit-operation/cherry-pick.tsx:12-49`).
3. Commit 1 conflicts on `shared.txt`; victim manually resolves via "Use theirs" in the conflicts dialog, which populates `manualResolutions.set('shared.txt', theirs)`.
4. Victim clicks Continue; `continueRebase`/`continueCherryPick` applies and stages the resolution, then git proceeds and hits a conflict on `shared.txt` again for commit 2.
5. Because `updateConflictState` only checks that `rebaseInternalState`/`isCherryPickingHeadFound` is still non-null (app/src/lib/stores/updates/changes-state.ts:268-305), it reuses the same `manualResolutions` map from step 3, and `updateMultiCommitOperationConflictsIfFound` pushes it into the new `ShowConflicts` step (app/src/lib/stores/app-store.ts:3138-3156) — the dialog may appear to already have `shared.txt` "resolved" with the stale "theirs" choice from commit 1's unrelated conflict.
6. If the victim continues without noticing/re-inspecting, `continueRebase`/`continueCherryPick` re-applies the stale resolution to commit 2's conflict (app/src/lib/git/rebase.ts:448-458 / app/src/lib/git/cherry-pick.ts:389-399), producing a commit with content the user never actually reviewed for that specific conflict.

function getConflictState(
  status: IStatusResult,
  manualResolutions: Map<string, ManualConflictResolution>
): ConflictState | null {
  if (status.rebaseInternalState !== null) {
    const { currentTip } = status
    if (currentTip == null) {
      return null
    }

    const { targetBranch, originalBranchTip, baseBranchTip } =
      status.rebaseInternalState

    return {
      kind: 'rebase',
      currentTip,
      manualResolutions,
      targetBranch,
      originalBranchTip,
      baseBranchTip,
    }
  }

  if (status.isCherryPickingHeadFound) {
    const { currentBranch: targetBranchName } = status
    if (targetBranchName == null) {
      return null
    }
    return {
      kind: 'cherryPick',
      manualResolutions,
      targetBranchName,
    }
  }

  const { currentBranch, currentTip, mergeHeadFound, squashMsgFound } = status
  if (
    currentBranch == null ||
    currentTip == null ||
    (!mergeHeadFound && !squashMsgFound) ||
    // If there are no conflicts, we want to ignore the squash msg found.
    // However, we do want to prompt the conflicts showing all resolved
    // if a regular merge conflicts are all resolves so user can
    // commit the merge commit.
    (!mergeHeadFound && !status.doConflictedFilesExist)
  ) {
    return null
  }

  return {
    kind: 'merge',
    currentBranch,
    currentTip,
    manualResolutions,
  }
}

export function updateConflictState(
  state: IChangesState,
  status: IStatusResult,
  statsStore: IStatsStore
): ConflictState | null {
  const prevConflictState = state.conflictState

  const manualResolutions =
    prevConflictState !== null
      ? prevConflictState.manualResolutions
      : new Map<string, ManualConflictResolution>()

  const newConflictState = getConflictState(status, manualResolutions)

  if (prevConflictState == null && newConflictState == null) {
    return null
  }

  if (
    (prevConflictState == null || isMergeConflictState(prevConflictState)) &&
    (newConflictState == null || isMergeConflictState(newConflictState))
  ) {
    performEffectsForMergeStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  if (
    (prevConflictState == null || isRebaseConflictState(prevConflictState)) &&
    (newConflictState == null || isRebaseConflictState(newConflictState))
  ) {
    performEffectsForRebaseStateChange(
      prevConflictState,
      newConflictState,
      status,
      statsStore
    )
    return newConflictState
  }

  private updateMultiCommitOperationConflictsIfFound(repository: Repository) {
    const state = this.repositoryStateCache.get(repository)
    const { changesState, multiCommitOperationState } =
      this.repositoryStateCache.get(repository)
    const { conflictState } = changesState

    if (conflictState === null || multiCommitOperationState === null) {
      this.clearConflictsFlowVisuals(state)
      return
    }

    const { step, operationDetail } = multiCommitOperationState
    if (
      step.kind !== MultiCommitOperationStepKind.ShowConflicts &&
      step.kind !== MultiCommitOperationStepKind.ShowCopilotConflicts
    ) {
      return
    }

    const { manualResolutions } = conflictState

    this.repositoryStateCache.updateMultiCommitOperationState(
      repository,
      () => ({
        step: {
          ...step,
          conflictState: { ...step.conflictState, manualResolutions },
        },
      })
    )
