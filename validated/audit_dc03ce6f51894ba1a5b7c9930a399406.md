### Title
Payout tx OP_RETURN malleability via `SIGHASH_SINGLE|ANYONECANPAY` lets an attacker rewrite the attributed operator pubkey, permanently blocking honest reimbursement - (File: core/src/builder/transaction/operator_reimburse.rs)

### Summary
`create_payout_txhandler` signs the payout transaction's input with a signature covering only input 0 and output 0 (`SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`), leaving output 2 (the OP_RETURN carrying `operator_xonly_pk`) unsigned. An attacker who observes an honest operator's unconfirmed payout tx can rebroadcast a variant with the same input/output0 but an attacker-chosen OP_RETURN payload, and if it confirms first, `Verifier::update_finalized_payouts` records a bogus `payout_payer_operator_xonly_pk` that will never match the real operator's `kickoff_data.operator_xonly_pk`, causing `is_kickoff_malicious` to always return `true` for that operator's legitimate kickoff.

### Finding Description
The broken binding: `payout_payer_operator_xonly_pk` stored in the DB for a given withdrawal MUST equal the `operator_xonly_pk` of whichever operator actually funded the payout output (i.e. the operator whose signature/funds paid the user).

Root cause:
- `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds three outputs: user payout (0), anchor (1), OP_RETURN with `operator_xonly_pk.serialize()` (2). It calls `txhandler.set_p2tr_key_spend_witness(&user_sig, 0)` with a signature whose `sighash_type` is `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY` (enforced in `Operator::withdraw`, `core/src/operator.rs:630-637`, "Ensure the signature uses SinglePlusAnyoneCanPay sighash type").
- Under BIP-341/BIP-143 semantics, `SIGHASH_SINGLE` only commits to the input and the output with the *same index* (index 0), and `ANYONECANPAY` only commits to that single input. Outputs 1 (anchor) and 2 (OP_RETURN) are **not covered by the signature**.
- Because the input, sequence, and output 0 are all attacker-observable from the honest operator's broadcast (unconfirmed) payout tx, an unprivileged attacker can copy input 0 + output 0 + the valid witness signature, and attach a different OP_RETURN payload (output 2) containing 32 bytes that parse as *some* valid but unrelated `XOnlyPublicKey` (any 32-byte string has ~50% chance of being a valid x-coordinate on secp256k1, so trivial to find one distinct from any real operator's pubkey). The signature remains valid against the new sighash because none of the changed bytes are covered.
- `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) determines the attributed operator purely from whichever transaction is found spending the tracked withdrawal UTXO in the finalized block (matched by prevout via `insert_spent_utxo`/`save_transaction_spent_utxos` in `core/src/bitcoin_syncer.rs:143-164`, not by a pre-committed txid), then parses the OP_RETURN with `parse_op_return_data` + `XOnlyPublicKey::from_slice` (`core/src/verifier.rs:2319-2321`). It has no check that the recovered key belongs to any known operator.
- Since both the honest and attacker variants spend the same UTXO, only one can confirm (a natural double-spend); if the attacker's variant confirms first (e.g. via fee bump/RBF or race), the DB permanently records the corrupted, unrelated pubkey for that withdrawal.
- Later, `Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1859-1915`) compares the stored `operator_xonly_pk` against `kickoff_data.operator_xonly_pk` submitted by the real operator who funded the payout; since these never match, it returns `true`, permanently flagging the honest operator's kickoff as malicious and blocking their reimbursement path.

No existing guard prevents this: `SECP.verify_schnorr` in `Operator::withdraw` only validates the signature against the sighash actually computed for whatever tx is broadcast, and does not pin down the OP_RETURN content; `update_finalized_payouts` performs no cross-check against the known operator set before persisting the key.

### Impact Explanation
The honest operator who genuinely funded the user's withdrawal loses the ability to ever be reimbursed for that payout, because `is_kickoff_malicious` will permanently evaluate to `true` for their real kickoff (the stored attribution can never equal their real `operator_xonly_pk`). This matches the Critical category "an honest operator permanently unable to be reimbursed" — real BTC that the operator fronted for the user is not recoverable from the bridge. The attack is repeatable per-payout and does not require any privileged role; the attacker only pays negligible fees to relay a competing transaction. Blast radius is scoped to whichever payout the attacker races, but is repeatable across any operator's payout as long as the attacker can win the confirmation race.

### Likelihood Explanation
Preconditions: the honest operator's payout tx must still be unconfirmed (visible in mempool) when the attacker acts, and the attacker must get their malleated variant confirmed instead (e.g., by broadcasting with a higher fee, since the input/output0/anchor/witness are unchanged and reusable, this is essentially free to construct — attacker cost is only the fee premium needed to win the race). This is fully attacker-feasible under the given threat model (anyone who can broadcast Bitcoin transactions) and does not require mainnet-specific conditions; it is a signature/design issue reproducible on regtest.

### Recommendation
Change the payout signature's sighash to cover all outputs (e.g. `SIGHASH_ALL` or `SIGHASH_ALL|ANYONECANPAY`) so the OP_RETURN operator-attribution output cannot be swapped without invalidating the user's signature. Alternatively, bind the OP_RETURN payload commitment separately (e.g. via a tagged hash covering it in the signed sighash) or validate in `update_finalized_payouts` that the recovered `operator_xonly_pk` belongs to a currently registered operator before persisting it, rejecting/flagging unknown keys.

### Proof of Concept
```
cargo test -p clementine-core --test <payout_malleability> -- --nocapture
```
Test plan:
1. Set up a test bridge (regtest) with a deposit and a registered honest operator (`operator.signer.xonly_public_key`).
2. Call `Operator::withdraw` for the honest operator to build and broadcast the payout tx (`payout_txhandler`), but capture it *without* mining (hold in mempool).
3. Deserialize the honest payout tx; construct a second `Transaction` with identical input 0 (same outpoint, sequence, witness) and identical output 0, but a modified output 2 OP_RETURN payload set to a distinct 32-byte value chosen so `XOnlyPublicKey::from_slice` succeeds and the value ≠ any operator's `signer.xonly_public_key` in the test's actor set.
4. Assert the crafted tx's sighash (with `SIGHASH_SINGLE|ANYONECANPAY`) equals the honest tx's sighash for input 0, and that `SECP.verify_schnorr` succeeds against the original user signature for the crafted tx (proving malleability).
5. Mine the crafted variant first (bury the honest one via `invalidate`/conflicting spend), let the verifier's Citrea/bitcoin sync run `update_finalized_payouts`.
6. Assert `db.get_payout_info_from_move_txid` returns `payout_payer_operator_xonly_pk` equal to the crafted key and `assert_ne!` against every operator's `signer.xonly_public_key` in the actor set.
7. Have the honest operator submit their real kickoff with `kickoff_data.operator_xonly_pk == operator.signer.xonly_public_key`; call `Verifier::is_kickoff_malicious` and assert it returns `true`, proving the honest operator can never be reimbursed for this payout.
