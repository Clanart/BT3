## Title
Missing lower-bound validation on `Kip71GasTarget` governance parameter causes division-by-zero panic in base fee calculation - (File: params/kip71_config.go, kaiax/gov/param.go)

### Summary
The KIP-71 (Magma) dynamic base fee mechanism computes the next block's base fee using `GasTarget` as a divisor. Unlike the sibling parameter `BaseFeeDenominator`, which has an explicit `FormatChecker` rejecting zero, the `Kip71GasTarget` governance parameter uses `noopFormatChecker` and has no lower-bound enforcement anywhere in the governance vote pipeline. A governance vote setting `GasTarget` to `0` will pass all validation checks and, once ratified, cause every node computing `NextMagmaBlockBaseFee` to panic on integer division by zero, halting block production/validation network-wide.

### Finding Description
`KIP71Config.NextMagmaBlockBaseFee` divides by `gasTarget` in both the "gas used above target" and "gas used below target" branches: [1](#0-0) 

Notice `baseFeeDenominator` is defensively guarded against a zero value (`if kc.BaseFeeDenominator == 0 { ...set to 64 }`), but `gasTarget` has no equivalent guard: [2](#0-1) 

When `parentGasUsed != gasTarget` (which is virtually guaranteed once `gasTarget == 0`, since any nonzero gas usage triggers the "used more than target" branch), the code performs `x.Div(x, new(big.Int).SetUint64(gasTarget))`. Go's `math/big.Int.Div` panics on division by zero, so this crashes the calling goroutine.

The root cause is that the governance parameter registration for `Kip71GasTarget` has no format check preventing zero, in contrast to `Kip71BaseFeeDenominator` which explicitly checks `v != 0`: [3](#0-2) 

The vote-time consistency checker (`checkConsistency`) also does not add any bound check for `Kip71GasTarget`; it is grouped with parameters considered valid "as long as it passes the format checks in `NewVoteData()`": [4](#0-3) 

Since the format checker is a no-op, a vote value of `uint64(0)` for `Kip71GasTarget` is accepted by `NewVoteData`, survives `VerifyVote`, and — once ratified at the epoch boundary via the governing node's vote — becomes the active `GasTarget` for all subsequent blocks through `ParamSet.ToKip71Config()`.

`NextMagmaBlockBaseFee` is invoked broadly across critical consensus paths: header verification (`VerifyMagmaHeader`), block generation (`chain_makers.go`, `worker.go`), the tx pool, and gas price oracle (`gasprice.go`, `feehistory.go`) — meaning every node in the network (not just the proposer) would panic when processing the first block after the change takes effect.

### Impact Explanation
A single governance vote (cast by the governing node/council member — a normal path explicitly in the "governance parameters" analog scope) that sets `Kip71GasTarget` to `0` triggers a `division by zero` panic in `math/big` on **every node** that computes or verifies the base fee for the next block. This crashes block validation/production across the network, producing a full chain halt / denial of service — a critical availability failure and a divergence risk if node crash-recovery behavior differs across implementations or client versions.

### Likelihood Explanation
Likelihood is high in terms of exploitability of the code path (trivial to trigger — a single valid vote transaction with value `0`), though it requires the ability to cast a ratified governance vote (governing node in single mode, or a council majority in ballot mode). This mirrors the reported bug class exactly: the system fails to "provide and enforce safe defaults/bounds" for a security-critical numeric parameter, even though the adjacent parameter (`BaseFeeDenominator`) correctly enforces this exact class of check, demonstrating the omission is inconsistent and unintentional rather than a deliberate design choice.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`) mirroring the one used for `Kip71BaseFeeDenominator`, rejecting `0` (and any other unsafe values, e.g., enforcing `GasTarget <= MaxBlockGasUsedForBaseFee`). Additionally, add a defensive guard in `NextMagmaBlockBaseFee` itself (similar to the existing `baseFeeDenominator == 0` fallback) so that a zero `gasTarget` cannot cause a panic even if an invalid value somehow reaches this function (e.g., from genesis/legacy chain configs not going through the governance vote pipeline).

### Proof of Concept
1. Governing node (single mode) or council majority (ballot mode) submits a `governance_vote` for `kip71.gastarget` with value `0`.
2. `NewVoteData` canonicalizes it to `uint64(0)` and `noopFormatChecker` accepts it: [5](#0-4) 
3. `VerifyVote`/`checkConsistency` pass without additional bound checks: [4](#0-3) 
4. At the next epoch, the vote is ratified and `ParamSet.GasTarget = 0` is used to build `KIP71Config` via `ToKip71Config()`: [6](#0-5) 
5. On the next block after activation, any node calling `NextMagmaBlockBaseFee` with nonzero `parentGasUsed` executes `x.Div(x, new(big.Int).SetUint64(0))`, which panics: [7](#0-6) 
6. All nodes computing/verifying the base fee for that block crash, halting the chain.
