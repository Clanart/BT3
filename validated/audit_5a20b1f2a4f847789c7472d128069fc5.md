## Title
Native-token push in cross-chain escrow withdrawal permanently locks funds when the fill beneficiary rejects value transfer - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` (used by both `ExtrinsicIntents.onAccept` for `RedeemEscrow`/`RefundEscrow` and `IntrinsicIntents._cancelSameChain`) pushes native tokens to a `beneficiary` address via a low-level `.call{value: amount}("")` and reverts the entire withdrawal if the call fails [1](#0-0) . The same pattern exists in the Tron `IntentGatewayV2.withdraw` [2](#0-1) . This is the same push-payment invariant break as GoGoPool's M-07: an unpayable beneficiary can make the fund-release call unconditionally revert.

### Finding Description
In `ExtrinsicIntents._fillCrossChain`, the `RedeemEscrow` cross-chain message hardcodes `beneficiary = msg.sender` (the filling solver) [3](#0-2) . That message is dispatched with `timeout: 0` [4](#0-3) , meaning it has no expiry to fall back to an `onPostRequestTimeout` refund path.

When the message reaches the source chain, `EvmHost.dispatchIncoming` calls `onAccept` and, on failure, explicitly deletes the request receipt "so that it can be retried," returning without reverting the batch [5](#0-4) . This design intentionally allows indefinite replay of a failing request, per the documented ISMP invariant that `on_accept` failures leave the request in a replayable state [6](#0-5) .

`onAccept` routes `RedeemEscrow`/`RefundEscrow` requests straight into `_withdraw`, which always pushes value to the same fixed `beneficiary` recorded in the message body [7](#0-6) . If a malicious (or simply non-payable) solver contract fills an order and is set as `beneficiary`, every retry of that message hits the same `beneficiary.call{value: amount}("")` and reverts identically — the message can never succeed, and because `timeout: 0` means it never times out, there is no alternate refund path either. The escrow's underlying `_orders[commitment][token]` balance is never decremented (the whole `_withdraw` call reverts, rolling back state), so the user's original escrowed principal for that order is permanently stuck with no recovery mechanism.

The same push-then-revert construct also appears in `_cancelSameChain` / `_withdraw` used for same-chain cancellations [8](#0-7)  and in the destination-chain `_cancelFromDest` refund path [9](#0-8) .

### Impact Explanation
This qualifies as a "loss of funds" impact under the Hyperbridge bounty scope: the escrowed input tokens tied to an order become permanently unretrievable, since (a) the fund-release call is a push to a fixed, message-embedded beneficiary, (b) failed `onAccept` calls are retried forever rather than escalated to any alternate handler, and (c) the dispatch uses `timeout: 0`, removing the only other exit (`onPostRequestTimeout`-based refund). Both the user's escrowed input and the solver's own earned reward become unrecoverable, but the more severe consequence is that the order originator's funds are locked with no privileged or unprivileged recovery path in the contract.

### Likelihood Explanation
Any solver can trigger this unilaterally and permissionlessly by filling an order (`ExtrinsicIntents.fillOrder`) from a contract address with no `receive`/payable `fallback`. No relayer, prover, admin, or governance collusion is required — it is a self-triggerable, single-transaction condition reachable by any unprivileged actor acting as a filler. This mirrors exactly the GoGoPool primitive (an actor who controls the destination address of a mandatory push payment can make it permanently revert), but here it additionally benefits from the "retry forever, never timeout" ISMP semantics, making the lock permanent rather than merely a temporary DoS on a single call.

### Recommendation
Adopt a pull-over-push pattern for native-token release in `IntentsBase._withdraw` / `IntentGatewayV2.withdraw`: on failed native transfer, credit an internal claimable balance for the beneficiary instead of reverting the whole withdrawal, and expose a separate `claim()` function the beneficiary (or anyone, sending to that address) can call later. Alternatively, wrap native token into WETH-equivalent and deliver it as an ERC-20 credit on transfer failure, as already done in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout` [10](#0-9) , so a failed push never blocks settlement of the underlying cross-chain message.

### Proof of Concept
1. Attacker deploys `NoReceive` contract with no `receive()`/payable `fallback()`.
2. Attacker (as `NoReceive`) calls `IntentGatewayV2.fillOrder` on the destination chain for a cross-chain order whose `output.assets` include a native-token output; `_fillCrossChain` sets `beneficiary = address(NoReceive)` for the `RedeemEscrow` message and dispatches it with `timeout: 0` [11](#0-10) .
3. A relayer delivers the `RedeemEscrow` request to the source chain; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw`, which attempts `beneficiary.call{value: amount}("")` to `NoReceive` and reverts with `InsufficientNativeToken` [12](#0-11) .
4. `EvmHost.dispatchIncoming` catches the failure, deletes the receipt, and returns normally so the request can be resubmitted [13](#0-12) .
5. Every future relayer resubmission of the identical request hits the same reverting call; because `timeout: 0` never elapses, there is no timeout-triggered refund. The user's escrowed input tokens for this order are permanently locked in the source-chain gateway with no recovery function available.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        if (orderSource != currentChain) revert WrongChain();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
