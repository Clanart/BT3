### Title
Panic in `GeneratorPromotion::complete` when a proof is keyed by our own participant index, allowing remote crash/DoS - (File: crypto/dkg/promote/src/lib.rs)

### Summary
`GeneratorPromotion::complete` validates only the count and upper bound of the supplied `proofs` map. It never checks that the map's keys exclude `params.i()` (our own index). An attacker who submits a `GeneratorProof` keyed with our participant index — i.e., a "duplicate" identifier colliding with the local signer — causes `proofs.get(&i).unwrap()` to index a missing key and panic. This is the direct analog of CVE-2024-4227's duplicate-ID-triggered DoS: duplicate/colliding identifiers reach an unchecked lookup in production code.

### Finding Description
In `crypto/dkg/promote/src/lib.rs`, `complete` performs two validations: `proofs.len() == n - 1` (lines 125–131) and every key `i <= params.n()` (lines 132–136). It then iterates `i in 1..=n`, skipping `params.i()`, and does `proofs.get(&i).unwrap()` at line 146. Because `HashMap<Participant, GeneratorProof>` cannot contain literal duplicate keys, the only way for the count to be `n-1` while a needed key is absent is for one entry to be keyed by `params.i()` itself — a colliding/duplicate identifier from the attacker's perspective. When that happens, `proofs.get(&j)` for the genuinely missing participant `j` returns `None` and `unwrap()` panics, crashing the calling thread. [1](#0-0) 

### Impact Explanation
An unauthenticated/unprivileged party supplying `GeneratorProof` messages (which are publicly read via `GeneratorProof::read`, lines 72–77, and consumed via `complete`) can trigger a panic (unwinding or abort depending on build) in any process performing generator promotion, halting the DKG/promotion session and potentially taking down the node. This is availability-only, matching the CVE's C:N/I:N/A:H profile.

### Likelihood Explanation
Triggering requires only submitting a `GeneratorProof` map where one entry uses the victim's `Participant` index instead of the prover's own — fully attacker-controlled data with no cryptographic validity needed before the panic. Any protocol path that feeds received proofs into `complete` is exposed. Likelihood is high wherever the function is reachable from network input; it is a deterministic panic, not a probabilistic one.

### Recommendation
Before iterating, verify the key set exactly: for every `i` in `1..=params.n()` with `i != params.i()`, require `proofs.contains_key(&i)`, and reject `proofs.contains_key(&params.i())`. Alternatively, replace `proofs.get(&i).unwrap()` with `.get(&i).ok_or(PromotionError::MissingParticipant(i))?` (adding a `MissingParticipant` error variant), which both fixes the panic and yields a blameable error consistent with `DkgError::DuplicatedParticipant`/`NotParticipating` handling in `ThresholdKeys::view`.
