### Title
User cannot set slippage protection on the internal WOM→mWOM swap performed during `ArbWomUp3.incentiveDeposit` (mode 2), enabling MEV sandwich losses - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.incentiveDeposit()` lets any wallet deposit WOM to receive `mWomSV` lock rewards. For `_mode == 2`, half of the deposited WOM is routed through `SmartWomConvert.convert()` with the `_minRec` parameter hardcoded to `0`, so the resulting swap inside `SmartWomConvert._convertFor()` (which trades WOM for mWOM through the Wombat router) has no effective slippage protection, and the caller has no way to supply one.

### Finding Description
`incentiveDeposit()` takes only `_amount`, `_convertRatio`, `_bullMode`, and `_mode` — there is no `minRec`/slippage parameter exposed to the user for the mode-2 path. [1](#0-0) 

For `_mode == 2`, `_deposit()` swaps half of the WOM via `SmartWomConvert.convert(toSwap, _convertRatio, 0, 0)`, hardcoding the minimum-received amount to `0`: [2](#0-1) 

`SmartWomConvert.convert()` forwards this `_minRec = 0` straight into `_convertFor()`, which executes `IWombatRouter.swapExactTokensForTokens(tokenPath, poolPath, buybackAmount, 0, ...)` — i.e., the swap itself allows infinite slippage — and the only downstream check (`convertAmount + amountRec < _minRec`) is a no-op because `_minRec` is `0`: [3](#0-2) 

This mirrors the referenced GMX bug class (H-9): a swap step in the flow allows arbitrary slippage, and no calling layer enforces the user's actual minimum-acceptable-output, so MEV/sandwich bots can extract value from the swap at the depositor's expense.

### Impact Explanation
Any unprivileged user calling `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` has the WOM-to-mWOM leg of their deposit executed with zero slippage protection. A searcher can sandwich the Wombat router swap inside the same block, causing the user to receive materially less mWOM than fair value, which is then locked into `mWomSV` on their behalf. This is a direct loss of user funds through an on-chain, permissionless MEV/sandwich attack on a routine user transaction, not a hypothetical or admin-triggered scenario.

### Likelihood Explanation
Likelihood is high: the vulnerable path is reachable by any wallet with no special permissions, requires no misconfiguration, and MEV sandwiching of AMM swaps with zero minOut is a well-established, automatable attack pattern. Every mode-2 deposit through `ArbWomUp3.incentiveDeposit` is exposed.

### Recommendation
Add a user-supplied `_minRec` (or equivalent minimum-output) parameter to `incentiveDeposit()` for the mode-2 path and thread it through to `SmartWomConvert.convert()` instead of hardcoding `0`, so the existing `convertAmount + amountRec < _minRec` check in `SmartWomConvert._convertFor()` can meaningfully enforce the user's slippage tolerance.

### Proof of Concept
1. User calls `ArbWomUp3.incentiveDeposit(amount, convertRatio, false, 2)`.
2. Internally, `_deposit()` calls `IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0)` — `_minRec` fixed at `0`.
3. A searcher observes the pending transaction, front-runs it by swapping WOM→mWOM to move the pool price, lets the victim's swap execute at the worse price inside `SmartWomConvert._convertFor` (`swapExactTokensForTokens(..., 0, ...)`), then back-runs to restore price and capture the difference.
4. The user's locked `mWomSV` balance ends up lower than it would have been absent the sandwich, with no revert possible since `_minRec == 0` at every check point.
