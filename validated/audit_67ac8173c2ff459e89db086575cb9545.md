### Title
Deterministic FROST nonce reuse across validator sets: `CachedPreprocesses` context omits the set/genesis, leaking the coordinator's secret key - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` deterministically regenerates FROST nonces from a seed cached in `CachedPreprocesses`, keyed solely by `context`. For `DkgConfirmer` the context is only `(b"DkgConfirmer", attempt)`, which binds the attempt number but not the validator set, genesis, participant list, or the message being signed. Because a coordinator's MuSig/FROST secret share is its long-lived validator key (reused across sets), and DKG confirmation attempts restart at low numbers (0, 1, …) for every new set, the same seed — hence the same nonces and the same published commitments — is reused to sign *different* `set_keys_message` messages. Two Schnorr shares over the same nonce with different challenges allow any observer to solve for the secret key.

### Finding Description
- `CachedPreprocesses` is keyed by `context` only: `create_db! { SigningProtocolDb { CachedPreprocesses: (context: &impl Encode) -> [u8; 32] } }` [1](#0-0) 
- In `preprocess_internal`, the same cached seed is XOR-decrypted and fed to `AlgorithmSignMachine::from_cache`, which calls `seeded_preprocess`, deriving nonces via `ChaCha20Rng::from_seed(*seed.0)` — fully deterministic in the seed and keys [2](#0-1) [3](#0-2) 
- The context is just `(b"DkgConfirmer", self.attempt)`; it does not include `self.spec.set()`, the genesis, the `removed` list, or the `key_pair`/message [4](#0-3) 
- The signing key is the validator's persistent Ristretto key (`self.key`), used in `musig(musig_context(...), self.key.clone(), participants)`, so it is constant across validator sets [5](#0-4) 
- The signed message differs per set: `set_keys_message(&self.spec.set(), &removed…, key_pair)` [6](#0-5) 

The file's own safety argument acknowledges nonce reuse happens if "the received nonce commitments (or the message to be signed) would have to be distinct and sign … called again," and assumes context-binding makes this impossible — but the context binds only the attempt, not the session/set [7](#0-6) . This is exactly the "incomplete fix for internal-state isolation" class: the cache key fails to isolate signing state per logical session.

### Impact Explanation
When an honest validator participates in a second validator set (e.g., after set rotation to a new Tributary/genesis) and a DKG confirmation reuses an attempt number — which always happens since attempts start at 0 per DKG — `preprocess_internal` regenerates the identical nonce commitments, and `share_internal`/`complete_internal` produce Schnorr signature shares with the same nonce under different binding factors/challenges (different participants → different MuSig coefficients; different `set`/`key_pair` → different message). Standard Schnorr nonce-reuse algebra recovers `self.key` — the validator's root-of-trust secret key — from publicly broadcast preprocesses and shares. Compromise of this key lets an attacker forge the validator's DKG confirmations and any future signatures under it. Impact: full key recovery → High.

### Likelihood Explanation
Requires no malicious action: the trigger is an honest validator simply serving in two DKG confirmations at the same attempt index across distinct sets — a routine event whenever sets rotate. All required data (nonce commitments and signature shares) is published publicly via the Tributary/Substrate. The only mitigating assumption is the BFT-ordering argument in the comments, which does not cover cross-set reuse because `context` fails to include any set identifier. Likelihood is therefore meaningful whenever more than one DKG confirmation occurs for a validator.

### Recommendation
Bind the cache context to the full signing session: e.g., `context = (b"DkgConfirmer", self.spec.set(), self.spec.genesis(), self.attempt)` (or include the `key_pair`/`removed` hash). Additionally, before producing a share, verify on-chain that the previously published commitments for this context match the regenerated ones — the TODO at line 50–54 already flags this check — so that any context collision aborts rather than reusing a nonce. Consider hashing the message/preprocess set into the seed derivation so determinism cannot span distinct sessions.

  As for safety, it is explicitly unsafe to reuse nonces across signing sessions. This raises
  concerns regarding our re-execution which is dependent on fixed nonces. Safety is derived from
  the nonces being context-bound under a BFT protocol. The flow is as follows:

  1) Decide the nonce.
  2) Publish the nonces' commitments, receiving everyone elses *and potentially the message to be
     signed*.
  3) Sign and publish the signature share.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  fn seeded_preprocess(
    self,
    seed: CachedPreprocess,
  ) -> (AlgorithmSignMachine<C, A>, Preprocess<C, A::Addendum>) {
    let mut params = self.params;

    let mut rng = ChaCha20Rng::from_seed(*seed.0);
    let (nonces, commitments) = Commitments::new::<_>(
      &mut rng,
      params.keys.original_secret_share(),
      &params.algorithm.nonces(),
    );
    let addendum = params.algorithm.preprocess_addendum(&mut rng, &params.keys);

    let preprocess = Preprocess { commitments, addendum };

    // Also obtain entropy to randomly sort the included participants if we need to identify blame
    let mut blame_entropy = [0; 32];
    rng.fill_bytes(&mut blame_entropy);
    (
      AlgorithmSignMachine { params, seed, nonces, preprocess: preprocess.clone(), blame_entropy },
      preprocess,
    )
