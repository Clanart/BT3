## Analysis

Tracing the two IBC middleware stacks in this repo:

**V1 stack** (`x/erc20/ibc_middleware.go`) correctly propagates conversion failures: [1](#0-0) 

Here, `im.keeper.OnRecvPacket(ctx, packet, ack)`'s return value **is** returned to the caller, so if `ConvertCoinNativeERC20` fails, the resulting error acknowledgement propagates all the way to ibc-go's core `RecvPacket` handling, which wraps the whole `OnRecvPacket` call chain in a `CacheContext`/`writeFn()` pattern and only commits state if the final ack is a success. That gives atomicity between the base ICS20 mint/unescrow and the ERC20 conversion for the V1 (classic channel) path — the scenario in the question does not apply there.

**V2 stack** (`x/erc20/v2/ibc_middleware.go`), which is exactly the file named in the question, has a different and broken pattern: [2](#0-1) 

Note line 89: `im.keeper.OnRecvPacket(ctx, packet, ack)` is called but **its return value is discarded**. Regardless of whether the ERC20 conversion (`k.OnRecvPacket` → `ConvertCoinNativeERC20`) succeeds or fails, `recvResult` — which already reflects the base ICS20 transfer's `Success` status from `im.app.OnRecvPacket` — is returned unchanged.

`ConvertCoinNativeERC20` itself is not atomic on failure: it first escrows the just-received coin from the recipient into the `x/erc20` module account, then calls the ERC20 contract's `transfer`; if that EVM call/contract logic reverts (e.g., a receiver-based blocklist the malicious token owner put in the bytecode), the function returns an error *after* the escrow step has already been committed, with no compensating refund: [3](#0-2) [4](#0-3) 

Because the V2 middleware swallows this error and still reports `PacketStatus_Success`, the destination chain never signals failure back to the source chain (no refund is triggered), and the recipient's coins are left stuck in the `x/erc20` module account — never burned, never converted to ERC20, never returned. This is a genuine, unprivileged-triggerable, critical fund-freezing bug, though the mechanism differs from the question's framing (it is not the source-chain escrow that gets stuck; it's the destination-chain recipient's funds trapped in the erc20 module account, and the acknowledgement is mis-reported as success rather than causing a refund-driven unwind).

### Title
Silent swallowing of ERC20 conversion errors in IBC v2 middleware causes recipient funds to be permanently trapped in the erc20 module account with no refund - (File: x/erc20/v2/ibc_middleware.go)

### Summary
`IBCMiddleware.OnRecvPacket` in the IBC v2 (Eureka) stack discards the return value of `k.keeper.OnRecvPacket`, so a failure in native-ERC20 conversion after the ICS20 credit has already occurred is never reflected in the reported `RecvPacketResult`.

### Finding Description
`x/erc20/v2/ibc_middleware.go`'s `OnRecvPacket` calls the base transfer app first, then unconditionally calls the erc20 keeper's `OnRecvPacket` but ignores its acknowledgement result [5](#0-4) . The erc20 keeper's `OnRecvPacket`, for a native-ERC20 token pair, calls `ConvertCoinNativeERC20`, which first moves the just-credited coin from the recipient to the `x/erc20` module account via `SendCoinsFromAccountToModule`, then attempts an EVM `transfer` call to unescrow the underlying ERC20 to the recipient and finally burns the escrowed coin [6](#0-5) . If the ERC20 contract's `transfer` reverts for a specific receiver (e.g., a blocklist controlled by the token pair's owner), the function returns an error after the escrow step has already run, with no unwind of that escrow. Because the v2 middleware discards this error and returns the original `Success` status from the base transfer, the packet is acknowledged as fully successful to the counterparty, so no refund is ever issued on the source chain, and the recipient never receives either the native coin (pulled into the module account) or the ERC20 tokens.

### Impact Explanation
This breaks 1:1 accounting between native coins and their ERC20 representation and results in a Critical, permanent freezing of user funds: coins are moved into the `x/erc20` module account and are never burned or forwarded, the recipient gets nothing, and the sending chain is never informed to refund because the acknowledgement falsely reports success.

### Likelihood Explanation
Any account controlling the ERC20 contract behind a registered native-ERC20 token pair (or any ERC20 with pausable/blocklist/compliance logic that can revert `transfer` for a specific address) can trigger this deterministically for a chosen recipient via ordinary IBC v2 transfers — no validator, relayer, or governance privilege is required beyond owning/controlling the token contract logic.

### Recommendation
Propagate the acknowledgement/result from `im.keeper.OnRecvPacket` in `x/erc20/v2/ibc_middleware.go` back into the returned `RecvPacketResult` (mirroring the V1 middleware's `return im.keeper.OnRecvPacket(...)` pattern), and/or make `ConvertCoinNativeERC20` atomic (e.g. run the escrow+EVM+burn sequence in a `CacheContext` that is only committed on full success) so a failed conversion neither leaves coins stranded in the module account nor is reported as a successful receive.

### Proof of Concept
1. Register (or otherwise establish) a native-ERC20 token pair whose ERC20 contract implements a `transfer` that reverts when `to == blockedReceiver`.
2. Send an IBC v2 transfer of that token's native coin denom to `blockedReceiver` on the chain hosting the token pair.
3. Observe: `im.app.OnRecvPacket` succeeds (native coin credited to `blockedReceiver`), `ConvertCoinNativeERC20` escrows that coin into the `x/erc20` module account, then the `transfer` EVM call reverts and the function returns an error — but `x/erc20/v2/ibc_middleware.go`'s `OnRecvPacket` discards that error and returns `PacketStatus_Success`.
4. Assert: `blockedReceiver`'s bank balance for the denom is zero, `blockedReceiver`'s ERC20 balance is unchanged, the `x/erc20` module account now holds the coin, and no refund acknowledgement is generated on the source chain — demonstrating permanently stranded funds despite a reported success.

func (im IBCMiddleware) OnRecvPacket(

	// return if the acknowledgement is an error ACK
	if !ack.Success() {
		return ack
	}

	return im.keeper.OnRecvPacket(ctx, packet, ack)
}

func (im IBCMiddleware) OnRecvPacket(
	ctx sdk.Context,
	sourceClient string,
	destinationClient string,
	sequence uint64,
	payload channeltypesv2.Payload,
	relayer sdk.AccAddress,
) channeltypesv2.RecvPacketResult {
	recvResult := im.app.OnRecvPacket(ctx, sourceClient, destinationClient, sequence, payload, relayer)
	if recvResult.Status == channeltypesv2.PacketStatus_Failure {
		return recvResult
	}
	packet, err := v2ToV1Packet(payload, sourceClient, destinationClient, sequence)
	if err != nil {
		return channeltypesv2.RecvPacketResult{
			Status: channeltypesv2.PacketStatus_Failure,
		}
	}
	var ack channeltypes.Acknowledgement
	if err := transfertypes.ModuleCdc.UnmarshalJSON(recvResult.Acknowledgement, &ack); err != nil {
		return channeltypesv2.RecvPacketResult{
			Status: channeltypesv2.PacketStatus_Failure,
		}
	}
	im.keeper.OnRecvPacket(ctx, packet, ack)
	return recvResult
}

func (k Keeper) ConvertCoinNativeERC20(
	ctx sdk.Context,
	pair types.TokenPair,
	amount math.Int,
	receiver common.Address,
	sender sdk.AccAddress,
) error {
	if !amount.IsPositive() {
		return sdkerrors.Wrap(types.ErrNegativeToken, "converted coin amount must be positive")
	}

	erc20 := contracts.ERC20MinterBurnerDecimalsContract.ABI
	contract := pair.GetERC20Contract()

	balanceToken := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceToken == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	// Escrow Coins on module account
	coins := sdk.Coins{{Denom: pair.Denom, Amount: amount}}
	if err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, sender, types.ModuleName, coins); err != nil {
		return sdkerrors.Wrap(err, "failed to escrow coins")
	}

	// Unescrow Tokens and send to receiver
	res, err := k.evmKeeper.CallEVM(ctx, erc20, types.ModuleAddress, contract, true, nil, "transfer", receiver, amount.BigInt())
	if err != nil {
		return err
	}

	// Check unpackedRet execution
	var unpackedRet types.ERC20BoolResponse
	if len(res.Ret) == 0 {
		// if the token does not return a value, check for the transfer event in logs
		if err := validateTransferEventExists(res.Logs, contract); err != nil {
			return err
		}
	} else {
		if err := erc20.UnpackIntoInterface(&unpackedRet, "transfer", res.Ret); err != nil {
			return err
		}
		if !unpackedRet.Value {
			return sdkerrors.Wrap(errortypes.ErrLogic, "failed to execute unescrow tokens from user")
		}
	}

	// Check expected Receiver balance after transfer execution
	balanceTokenAfter := k.BalanceOf(ctx, erc20, contract, receiver)
	if balanceTokenAfter == nil {
		return sdkerrors.Wrap(types.ErrEVMCall, "failed to retrieve balance")
	}

	exp := big.NewInt(0).Add(balanceToken, amount.BigInt())

	if r := balanceTokenAfter.Cmp(exp); r != 0 {
		return sdkerrors.Wrapf(
			types.ErrBalanceInvariance,
			"invalid token balance - expected: %v, actual: %v", exp, balanceTokenAfter,
		)
	}

	// Burn escrowed Coins
	err = k.bankKeeper.BurnCoins(ctx, types.ModuleName, coins)
	if err != nil {
		return sdkerrors.Wrap(err, "failed to burn coins")
	}

	return nil
}
