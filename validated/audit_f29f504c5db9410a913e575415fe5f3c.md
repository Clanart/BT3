### Title
PedPoP accepts encryption-key registrations for arbitrary participant indexes without sender authentication - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to the giscus flaw (unauthorized creation of a resource attributed to a foreign identity), PedPoP's round-1 `EncryptionKeyMessage` lets any unprivileged network party register an encryption key and commitments under any victim participant index. The Schnorr PoK on `Commitments` proves only *knowledge* of the first coefficient, bound to an index the attacker chooses — it does not authenticate that the sender is entitled to that index, and the `enc_key` field is not covered by the signature at all. `Decryption::register` stores whatever key arrives for each `Participant` with no proof of possession.

### Finding Description
`verify_r1` in `crypto/dkg/pedpop/src/lib.rs:305-332` calls `self.encryption.register(l, msg)` for each supplied `EncryptionKeyMessage`. `Decryption::register` (`encryption.rs:351-362`) inserts `msg.enc_key` for `participant` unconditionally — there is no PoP on `enc_key` (unlike `EncryptedMessage`, which carries a per-message `pop` `SchnorrSignature` bound to the sender via `pop_challenge` at `encryption.rs:302-324`). The only verification is `msg.sig.batch_verify(...)` against `challenge(context, l, R, Am)` (`lib.rs:86-94`, `323-329`), which commits to `l`, the nonce, and the commitment bytes — but **not** to `enc_key`, and it is satisfied by anyone who picks their own coefficient `a_0`, since the signature is verified against the attacker-supplied `commitments[0]` itself.

The code explicitly states the DKG does not provide an authenticated channel (`encryption.rs:299-301`), yet round-1 registration authenticates nothing about sender identity: an attacker who fabricates a complete `EncryptionKeyMessage<Commitments>` for index `l` — fresh coefficients, fresh PoK, attacker-controlled `enc_key` — passes all checks as "participant `l`".

### Impact Explanation
If the attacker's message occupies a participant slot (e.g., delivered before/instead of the legitimate participant's message on the unauthenticated channel, or for an index the target deployment expects to be filled externally):

- Every honest party encrypts their secret share *for participant `l`* to the attacker's `enc_key` (`lib.rs:369`, `encryption.rs:466` → `ecdh(key, enc_keys[l])`). The attacker decrypts all of them and recovers the group secret contributions / a valid `ThresholdKeys` share for index `l`.
- The attacker can also feed shares back under index `l` that pass `share_verification_statements` (`lib.rs:430-449`) since they know the coefficients, letting the DKG "complete" with the attacker as an unauthorized signer.

This is unauthorized creation of a participant's registered state — the same bug class as giscus letting an unauthenticated caller create discussions attributed to a repository.

### Likelihood Explanation
Reachable by any party able to deliver bytes to a node's round-1 endpoint: `EncryptionKeyMessage::read` requires only well-formed points (`encryption.rs:57-59`), and nothing upstream binds the message to a long-term identity. Exploitation requires winning delivery of the victim's slot, which is realistic on unauthenticated transports the library itself acknowledges may be in use; otherwise the attack surfaces as slot pre-emption for indexes the honest set never populates.

### Recommendation
Cover `enc_key` in the `Commitments` PoK: include `enc_key.to_bytes()` in `cached_msg`/`challenge` so the signature binds the encryption key to the registered index, and add a PoP on `enc_key` bound to sender `l` (mirroring `EncryptedMessage.pop`), so registrations cannot be created for an index without producing both proofs.

### Proof of Concept
1. Attacker picks victim index `l`, samples `t` coefficients `a_j`, computes `A_j = G·a_j`, `cached_msg`, `nonce r`, `R = G·r`, and signs `s = r + challenge(context, l, R, cached_msg)·a_0`.
2. Attacker picks `enc_key = G·e` for known `e`, serializes `EncryptionKeyMessage { Commitments{…, sig:(R,s)}, enc_key }`, delivers to a victim running `SecretShareMachine::generate_secret_shares`.
3. `verify_r1` accepts it: PoK verifies (`lib.rs:323-329`), `register` stores `enc_key` for `l` (`encryption.rs:360`).
4. Each honest `i` computes `encrypt(rng, l, share_i(l))` → ECDH key `e·share-ephemeral` — decryptable by the attacker; attacker recovers share `p_i(l)` from every sender and reconstructs the secret at index `l`, yielding a valid signing share the victim group believes belongs to an authorized participant.

  pub(crate) fn register<M: Message>(
    &mut self,
    participant: Participant,
    msg: EncryptionKeyMessage<C, M>,
  ) -> M {
    assert!(
      !self.enc_keys.contains_key(&participant),
      "Re-registering encryption key for a participant"
    );
    self.enc_keys.insert(participant, msg.enc_key);
    msg.msg
  }
