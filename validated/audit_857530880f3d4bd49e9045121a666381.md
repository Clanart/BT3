### Title
Copilot conflict-resolution UI presents "ours"/"theirs" labels using merge semantics even during rebase, causing users to silently commit the wrong side of a conflict - (File: `app/src/ui/multi-commit-operation/dialog/copilot-resolution-helpers.ts`)

### Summary
Desktop's own code documents a real, non-obvious ordering assumption that maps directly onto the Morpho `token0`/`token1` bug class: git's `ours` (stage `:2`) / `theirs` (stage `:3`) roles are **not fixed** — they swap during a rebase (upstream branch becomes "ours", the commit being replayed becomes "theirs"). The diff engine explicitly flags this as a caller responsibility, but the Copilot conflict-resolution label helper that drives the user-facing "Keep Current" / "Keep Incoming" choices takes `ourBranch`/`theirBranch` unconditionally, with no operation-kind awareness, while the resolution value it produces (`ManualConflictResolution.ours`/`.theirs`) is passed straight through to `git checkout --ours/--theirs`, i.e. git's raw (and, during rebase, swapped) stage semantics.

### Finding Description
`getResolutionDiff` explicitly documents the invariant and the danger of getting it wrong: [1](#0-0) 

`ManualConflictResolution.ours`/`.theirs` are semantically tied to git's raw stage values and passed directly to `git checkout --ours`/`--theirs`: [2](#0-1) [3](#0-2) 

The Copilot conflict dialog builds its "Use current file from `<branch>`" / "Use incoming file from `<branch>`" labels via `getOursTheirsLabels`, which simply echoes `ourBranch`/`theirBranch` with no parameter indicating whether the active multi-commit operation is a merge, rebase, or cherry-pick: [4](#0-3) 

This helper is invoked from the dialog for both the primary resolution dropdown and the "skipped file" dropdown, and the choice the user makes (`'ours'` or `'theirs'`) is stored directly as a `ManualConflictResolution` value: [5](#0-4) [6](#0-5) 

That stored value later drives the actual file write/stage step through `stageManualConflictResolution` → `checkoutConflictedFile`, which runs `git checkout --ours`/`--theirs` using git's raw (rebase-swapped) definition: [7](#0-6) 

Because the label text is not adjusted per operation kind, the same "ours = my branch, current" wording is shown for merges and rebases, while the underlying git operation flips which content that word actually refers to during a rebase. This is exactly the "assumes token0 is always Morpho" defect: a two-sided relationship (`ours`/`theirs`) is assumed fixed relative to a human-meaningful role ("current"/"my branch"), when in fact it depends on context (merge vs. rebase) that the code must — but does not visibly — account for at this call site.

### Impact Explanation
If the label/resolution mapping is not correctly re-derived for rebase (which the code's own comment says is the caller's job, and which the label helper visibly does nothing to handle), a user resolving a conflict during a `git rebase` who clicks "Use current file from `<my-branch>`" intending to keep their own change would instead have `git checkout --ours` applied, which during a rebase checks out the *upstream* target's content — i.e., the opposite of what the label promised. The user's own change is silently discarded, and content selected by an untrusted upstream/rebased branch (which the "attacker" controls if the user rebases onto a malicious/pushed-to remote branch or PR branch) is committed and staged instead — a silent corruption of what the user commits and eventually pushes, matching the "Valid Impact" criteria (attacker-controlled fetched/rebased branch resulting in silent corruption of committed content) without requiring local access, admin rights, or social engineering beyond a normal rebase.

### Likelihood Explanation
Rebasing onto a branch/PR the user does not fully control (a common workflow when rebasing a feature branch onto `main`/`upstream`, or rebasing onto someone else's PR branch) is routine in Desktop. Any conflict during that rebase that reaches the Copilot conflict-resolution dialog exercises exactly this label/resolution path. The bug is a labeling/semantics mismatch rather than a crash, so it produces no error and is easy to miss, increasing the chance a user trusts the "Use current file" label and unknowingly accepts the other side's content.

### Recommendation
Thread the active `MultiCommitOperationKind` (merge/rebase/cherry-pick) into `getOursTheirsLabels`/`getDeleteConflictLabels` and into the dropdown handlers in `copilot-conflicts-dialog.tsx`, and swap which branch name/label is associated with `ManualConflictResolution.ours` vs `.theirs` when the operation is a rebase, so the label always matches the actual git stage (`:2`/`:3`) that `git checkout --ours/--theirs` will apply — consistent with the mapping already required (per its own doc comment) in `getResolutionDiff`.

### Proof of Concept
1. Start a rebase in Desktop (`git rebase upstream-or-pr-branch`) that produces a text conflict.
2. Let Copilot conflict resolution run, then open the Copilot conflicts result dialog and, for a conflicted file, open the per-file resolution dropdown.
3. Observe the label `Use current file from <my-branch>` mapped to `ManualConflictResolution.ours` (see `copilot-conflicts-dialog.tsx:155-187` and `copilot-resolution-helpers.ts:119-139`).
4. Select that option and continue the rebase; `stageManualConflictResolution` → `checkoutConflictedFile` runs `git checkout --ours -- <path>` (`checkout.ts:221-235`).
5. Because git's rebase semantics make `--ours` refer to the upstream/target branch (not `<my-branch>`), the file staged/committed is the *upstream* version, not the user's own change — despite the UI telling them they kept "current"/"their own" file. Inspect the resulting commit content to confirm it matches the upstream side rather than the pre-rebase local change.

```typescript
/**
 * Returns the ours/theirs dropdown labels for a conflicted file, handling
 * both delete-vs-modify and regular text conflicts.
 */
export function getOursTheirsLabels(
  status: ConflictedFileStatus | undefined,
  ourBranch?: string,
  theirBranch?: string
): { readonly oursLabel: string; readonly theirsLabel: string } {
  if (status !== undefined && isDeleteConflictFile(status)) {
    return getDeleteConflictLabels(status, ourBranch, theirBranch)
  }

  const oursLabel = ourBranch
    ? `Use current file from ${ourBranch}`
    : 'Use current file'
  const theirsLabel = theirBranch
    ? `Use incoming file from ${theirBranch}`
    : 'Use incoming file'
  return { oursLabel, theirsLabel }
}
```

```typescript
export async function stageManualConflictResolution(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  manualResolution: ManualConflictResolution
): Promise<void> {
  const { status } = file
  // if somehow the file isn't in a conflicted state
  if (!isConflictedFileStatus(status)) {
    log.error(`tried to manually resolve unconflicted file (${file.path})`)
    return
  }

  if (isConflictWithMarkers(status) && status.conflictMarkerCount === 0) {
    // If somehow the user used the Desktop UI to solve the conflict via ours/theirs
    // but afterwards resolved manually the conflicts via an editor, used the manually
    // resolved file.
    return
  }

  const chosen =
    manualResolution === ManualConflictResolution.theirs
      ? status.entry.them
      : status.entry.us

  const addedInBoth =
    status.entry.us === GitStatusEntry.Added &&
    status.entry.them === GitStatusEntry.Added

  if (chosen === GitStatusEntry.UpdatedButUnmerged || addedInBoth) {
    await checkoutConflictedFile(repository, file, manualResolution)
  }

  switch (chosen) {
    case GitStatusEntry.Deleted:
      return removeConflictedFile(repository, file)
    case GitStatusEntry.Added:
    case GitStatusEntry.UpdatedButUnmerged:
      return addConflictedFile(repository, file)
    default:
      assertNever(chosen, 'unaccounted for git status entry possibility')
  }
```
