### Title
Sending value with `distribution.rewards()` on the distribution precompile permanently strands ETH/usei sent by the caller - ([File: precompiles/distribution/distribution.go])

### Summary
The Y2K report describes emissions tokens being transferred into a contract on the expectation that a later user action (withdraw/rollover) will return them, but when that later action never happens (null epoch), the tokens are permanently stuck because no code path exists to reclaim them. The structurally equivalent bug class in sei-chain is a precompile method that accepts native value (`usei`/`wei`) into the precompile's Cosmos account but never forwards, spends, or refunds it — leaving funds permanently locked. This exists in the `rewards()` view method of the Cosmos distribution precompile (address `0x...1007`).

### Finding Description
The distribution precompile's dispatcher explicitly enforces `pcommon.ValidateNonPayable(value)` for every state-mutating (and even some other view) method, e.g. `setWithdrawAddress` [1](#0-0) , `withdrawValidatorCommission` [2](#0-1) . However, `RewardsMethod` is dispatched straight to `p.rewards(ctx, method, args)` with no `ValidateNonPayable` check anywhere in the call chain, across the current implementation and every legacy version examined (v65, v66, v580, v605, v606, v610, v614, v620, v630, v640, v67) [3](#0-2) [4](#0-3) [5](#0-4) .

The `rewards` implementation itself only reads delegation rewards and packs the ABI output — it never touches `value`, never transfers the `usei`/`wei` sent with the call to any recipient, and never refunds the caller: [6](#0-5) .

This is confirmed directly by the codebase's own integration-test author, who documented the quirk in a spec comment: "rewards() is the one phase-2 view WITHOUT a non-payable check (a value-bearing call would succeed and strand the funds), so this spec deliberately has no 'view rejects value' test." [7](#0-6) .

Mechanically, when an EVM caller invokes `rewards(address)` on the precompile with a non-zero `msg.value`, the EVM's value-transfer semantics credit the precompile's mapped Sei account with that `usei`/`wei` before/as part of dispatch (as with any other precompile call carrying value), matching the pattern used elsewhere in the precompile family where `HandlePaymentUsei` is invoked specifically to debit-and-refund the payer for methods that don't consume payment [8](#0-7) . Because `rewards()` has no equivalent refund or non-payable guard, the credited value sits on the precompile's account with no subsequent code path to move it back to the caller — root-causing a fund freeze exactly analogous to the "null epoch" emissions being stranded in the external report (funds sent in, no return path if a specific method never handles them).

### Impact Explanation
Any EVM contract or EOA that mistakenly (or via a poorly-audited integrating contract) attaches `msg.value` to a `rewards()` call on the distribution precompile has that native value permanently locked in the precompile's account with no recovery mechanism — a direct, unauthorized, permanent loss of user funds reachable from an ordinary unprivileged EVM transaction. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
The `rewards()` view accepts a `value` parameter in its ABI signature (`payable`-shaped), so an integrator or wallet building the call is not inherently prevented from attaching value; nothing in the dispatcher rejects it as it does for every other listed distribution precompile method. This requires only a single ordinary EVM transaction/call with non-zero `value` targeting the precompile address, with no privileged access, validator behavior, or network condition needed.

### Recommendation
Add a `pcommon.ValidateNonPayable(value)` check (or a `HandlePaymentUsei`-based automatic refund, consistent with the other precompile view methods) at the top of `rewards()` in `precompiles/distribution/distribution.go` (and correspondingly in all legacy versioned copies still reachable via the module's version-gating), rejecting or refunding any non-zero value before executing the query.

### Proof of Concept
1. From any EVM account, call the distribution precompile at `0x0000000000000000000000000000000000001007` method `rewards(address)` with `msg.value > 0` (e.g., 1 ether via `ethers.Contract.rewards(delegatorAddr, { value: ethers.parseEther("1") })`).
2. Observe the call succeeds (status 1) unlike every other distribution precompile method invoked with value, which reverts with "sending funds to a non-payable function" via `pcommon.ValidateNonPayable` [9](#0-8) .
3. Confirm the precompile's underlying Sei account balance increased by the sent amount, and confirm no subsequent transaction path exists in `precompiles/distribution/distribution.go` to reclaim it — the funds are permanently stranded.

func (p PrecompileExecutor) rewards(ctx sdk.Context, method *abi.Method, args []interface{}) (ret []byte, remainingGas uint64, rerr error) {
	defer func() {
		if err := recover(); err != nil {
			ret = nil
			remainingGas = 0
			rerr = fmt.Errorf("%s", err)
			return
		}
	}()

	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		rerr = err
		return
	}

	seiDelegatorAddress, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		rerr = err
		return
	}

	req := &distrtypes.QueryDelegationTotalRewardsRequest{
		DelegatorAddress: seiDelegatorAddress.String(),
	}

	wrappedC := sdk.WrapSDKContext(ctx)
	response, err := p.distrKeeper.DelegationTotalRewards(wrappedC, req)
	if err != nil {
		rerr = err
		return
	}

	rewardsOutput := getResponseOutput(response)
	ret, rerr = method.Outputs.Pack(rewardsOutput)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
