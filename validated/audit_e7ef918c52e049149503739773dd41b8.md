### Title
Repository identity/remote URL trust based on mutable owner/name path instead of GitHub's immutable repository ID - (File: `app/src/lib/stores/updates/update-remote-url.ts`, `app/src/lib/stores/app-store.ts`, `app/src/lib/stores/repositories-store.ts`)

### Summary
The Oracle report describes a system that trusts an external data feed (`Oracle.getUnderlyingPrice`) at face value, without freshness/sanity checks, and uses it to drive a destructive state change (liquidation). The Desktop analog is `updateRemoteUrl`, which trusts the GitHub API's `IAPIRepository.clone_url` at face value and uses it to silently rewrite the local `origin` remote URL, which subsequently drives push/fetch/pull operations — without verifying that the API object it received actually describes the same repository the user originally associated with the project.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` (around lines 4874-4913) re-associates a local `Repository` with a GitHub-side repository on every repository selection, fetch, push and pull (it's invoked through `withRefreshedGitHubRepository`, which wraps `_fetch`, `_fetchRemote`, `_fetchRefspec`, and is on the `_selectRepositoryRefreshTasks` path).

The matching step, `matchGitHubRepository` (`app/src/lib/stores/app-store.ts` ~4964-4977 calling into `app/src/lib/repository-matching.ts` lines 29-46), derives `owner`/`name` purely by regex-parsing the *current git remote URL string* (`parseRemote`) — it never uses GitHub's immutable numeric repository `id`.

That `owner`/`name` pair is then used to call `api.fetchRepository(owner, name)`, i.e. a lookup by path, not by ID. The `IAPIRepository` returned is trusted directly:

- `updateRemoteUrl` (`app/src/lib/stores/updates/update-remote-url.ts` lines 7-45) compares the local remote URL against `apiRepo.clone_url` using only `urlMatchesRemote`, which itself only compares hostname/owner/name text (`app/src/lib/repository-matching.ts` lines 90-118) — never a stable repo ID.
- If the protocol matches and the stored `cloneURL` in the local DB still text-matches the remote (`remoteUrlUnchanged`), but the freshly fetched `clone_url` differs, Desktop calls `gitStore.setRemoteURL(...)` to silently rewrite the local `origin` remote — with no user confirmation dialog.
- Separately, `RepositoriesStore._upsertGitHubRepository` (`app/src/lib/stores/repositories-store.ts` lines 596-679) persists/looks up the cached `GitHubRepository` record keyed by `[ownerID+name]` (line ~613-616), again never by GitHub's immutable repo id, and overwrites `permissions`, `htmlURL`, `cloneURL`, `isArchived`, `isPrivate` fields from whatever API object currently resolves at that owner/name path.

This mirrors the Oracle bug's broken invariant: an externally-supplied value (`getUnderlyingPrice()` / `apiRepo.clone_url`) is consumed and acted upon (liquidation / remote URL rewrite + push) purely because it was successfully returned, without verifying that it is *the same, legitimate* underlying entity (a stale/manipulated price vs. the correct trading pair; an unrelated repository vs. the original one the user cloned). There is no analog to a "TWAP" or ID-pinning check anywhere in this path.

### Impact Explanation
If the owner/name path that a local repository's remote points to comes to resolve to a different, attacker-controlled repository on GitHub's side (e.g., following an org/user rename where the old login becomes squattable, or a repository being deleted/recreated at the same path by another party who reclaims the name), the next background fetch/push cycle will:
1. Silently repoint the user's `origin` remote to the attacker's `clone_url` via `gitStore.setRemoteURL`, with no prompt.
2. Immediately reuse that repointed remote for subsequent fetch/pull/push operations (see the `safeRemote`/`pushRepo` flow in `app-store.ts` ~5266-5347), sending the user's commits, branches, and credentials/tokens (via the trampoline/askpass or credential helper) to the attacker's endpoint.
3. Overwrite the cached `permissions`/`isPrivate`/`isArchived` metadata for the repository based on the attacker's repo, potentially masking loss of push protections or branch protection state (`refreshBranchProtectionState`).

This can result in the user unknowingly pushing to (leaking code/history to) an attacker-controlled remote, and/or Desktop trusting attacker-controlled branch-protection/permission metadata for security-relevant push decisions.

### Likelihood Explanation
This requires no local access, no malware, and no leaked credentials — the trigger is purely a change in what a given `owner/name` path on GitHub resolves to (name/ownership churn, a class of issue GitHub itself has previously had to mitigate for its own redirect/rename semantics), combined with the fact that Desktop periodically (via background fetch/pull/push) revalidates using path lookup instead of ID pinning. This is a realistic "renamed/reclaimed remote object" scenario analogous to a stale/manipulated oracle price being acted upon automatically. It requires no unusual user interaction beyond normal use of Desktop (background fetch is automatic).

### Recommendation
Anchor repository identity to GitHub's immutable numeric repository `id` rather than the mutable `owner`/`name` path:
- Store and compare `apiRepo.id` in `GitHubRepository`/`IDatabaseGitHubRepository`, and key `_upsertGitHubRepository` lookups by that id instead of `[ownerID+name]`.
- In `updateRemoteUrl`, refuse to auto-rewrite the local remote URL when the newly-fetched `apiRepo.id` does not match the previously cached repository id; instead, surface a user-facing confirmation dialog (similar to the existing "untrusted certificate" pattern in `app/src/ui/untrusted-certificate/untrusted-certificate.tsx`) before silently changing where a push/fetch will go.
- Treat an API-returned repository object as untrusted until its identity is confirmed against locally-known state, mirroring the report's recommendation of validating oracle data before acting on it.

### Proof of Concept
1. User clones `https://github.com/alice/project.git`; Desktop stores `GitHubRepository` keyed by `[ownerID(alice)+name(project)]` (`repositories-store.ts` ~613-616), with `cloneURL` matching the local `origin` remote.
2. `alice` renames her GitHub account (or deletes/abandons the `project` repo), and an attacker registers the `alice` login (or recreates `project` under an org that previously used that path) and creates a repository at the same `alice/project` path, setting up their own `clone_url`.
3. On the user's next automatic background fetch/push (`_fetch`/`_fetchRemote`/`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`), Desktop calls `matchGitHubRepository` (text-based owner/name parse of the existing remote URL) then `api.fetchRepository('alice','project')`, which now resolves to the attacker's repository object.
4. `updateRemoteUrl` compares text URLs only; since `remoteUrlUnchanged` (matches cached, stale `cloneURL`) and protocols match, and `!urlsMatch` is false only if the clone_url is identical string-wise — but any variation (e.g., different clone_url casing/format changes are irrelevant since it's owner/name equal) — the primary risk is that `_upsertGitHubRepository`/`setGitHubRepository` silently binds the local repository record to the attacker's actual GitHub repo object (permissions, private flag, etc.) without any ID check, and any subsequent "Push" from Desktop's UI targets the remote URL, which is the attacker's resolved path.

Note: I could not fully trace every downstream permission-consumption site (e.g., exactly how `permissions.push` cached from the attacker's repo affects the "Publish"/force-push confirmation UI) within the available tool budget; a Devin session with full repository access would be needed to confirm the complete exploit chain end-to-end. import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }

  return null
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

  private async _upsertGitHubRepository(
    endpoint: string,
    gitHubRepository: IAPIRepository | IAPIFullRepository,
    ignoreParent = false
  ): Promise<GitHubRepository> {
    const parent =
      'parent' in gitHubRepository && gitHubRepository.parent !== undefined
        ? await this._upsertGitHubRepository(
            endpoint,
            gitHubRepository.parent,
            true
          )
        : await Promise.resolve(null) // Dexie gets confused if we return null

    const { login, type } = gitHubRepository.owner
    const owner = await this.putOwner(endpoint, login, type)

    const existingRepo = await this.db.gitHubRepositories
      .where('[ownerID+name]')
      .equals([owner.id, gitHubRepository.name])
      .first()

    // If we can't resolve permissions for the current repository chances are
    // that it's because it's the parent repository of another repository and we
    // ended up here because the "actual" repository is trying to upsert its
    // parent. Since parent repository hashes don't include a permissions hash
    // and since it's possible that the user has both the fork and the parent
    // repositories in the app we don't want to overwrite the permissions hash
    // in the parent repository if we can help it or else we'll end up in a
    // perpetual race condition where updating the fork will clear the
    // permissions on the parent and updating the parent will reinstate them.
    const permissions =
      getPermissionsString(gitHubRepository) ??
      existingRepo?.permissions ??
      undefined

    // If we're told to ignore the parent then we'll attempt to use the existing
    // parent and if that fails set it to null. This happens when we want to
    // ensure we have a GitHubRepository record but we acquired the API data for
    // said repository from an API endpoint that doesn't include the parent
    // property like when loading pull requests. Similarly even when retrieving
    // a full API repository its parent won't be a full repo so we'll never know
    // if the parent of a repository has a parent (confusing, right?)
    //
    // We do all this to ensure that we only set the parent to null when we know
    // that it needs to be cleared. Otherwise we could have a scenario where
    // we've got a repository network where C is a fork of B and B is a fork of
    // A which is the root. If we attempt to upsert C without these checks in
    // place we'd wipe our knowledge of B being a fork of A.
    //
    // Since going from having a parent to not having a parent is incredibly
    // rare (deleting a forked repository and creating it from scratch again
    // with the same name or the parent getting deleted, etc) we assume that the
    // value we've got is valid until we're certain its not.
    const parentID = ignoreParent
      ? existingRepo?.parentID ?? null
      : parent?.dbID ?? null

    const updatedGitHubRepo: IDatabaseGitHubRepository = {
      ...(existingRepo?.id !== undefined && { id: existingRepo.id }),
      ownerID: owner.id,
      name: gitHubRepository.name,
      private: gitHubRepository.private,
      htmlURL: gitHubRepository.html_url,
      cloneURL: gitHubRepository.clone_url,
      parentID,
      lastPruneDate: existingRepo?.lastPruneDate ?? null,
      issuesEnabled: gitHubRepository.has_issues,
      isArchived: gitHubRepository.archived,
      permissions,
    }

    if (existingRepo !== undefined) {
      // If nothing has changed since the last time we persisted the API info
      // we can skip writing to the database and (more importantly) avoid
      // telling store consumers that the repo store has changed.
      if (shallowEquals(existingRepo, updatedGitHubRepo)) {
        return this.toGitHubRepository(existingRepo, owner, parent)
      }
    }

    const id = await this.db.gitHubRepositories.put(updatedGitHubRepo)
    this.emitUpdatedRepositories()
    return this.toGitHubRepository({ ...updatedGitHubRepo, id }, owner, parent)
