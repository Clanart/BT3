## Finding

`diffFromRawDiffOutput` in `app/src/lib/git/diff.ts` splits the entire `git diff --patch-with-raw -z` output on NUL bytes and blindly takes the **last** segment to feed to `DiffParser.parse`: [1](#0-0) 

This is safe only if NUL (`\0`) never appears inside the human-readable "patch" portion of the output — it's only supposed to appear as a separator in the machine-readable `--raw` portion that precedes the patch. That assumption breaks for files that git treats as "text" despite containing NUL bytes.

### Root cause

Git's binary-content heuristic (a NUL byte in the first ~8000 bytes) can be **overridden per-path via `.gitattributes`** by declaring `text` on that path (e.g. `payload.bin text`). This is a first-class, documented git attribute — no external diff/textconv program, no `diff.external` config, and no local trust settings are involved, so `--no-ext-diff` (already used in `getWorkingDirectoryDiff`/`getResolutionDiff`) does **not** protect against it: [2](#0-1) 

When `text` is forced on a path whose blob contains an embedded NUL, git performs a normal line-based diff and writes the literal file bytes — including the NUL — straight into the unified-diff hunk body. That means the raw `-z` output buffer now contains an *extra*, unexpected NUL inside the patch text, not just at the raw/patch boundary.

`diffFromRawDiffOutput`'s `result.split('\0')` then produces more than the expected two segments, and `pieces.at(-1)` grabs only whatever trails the *last* NUL — discarding the `diff --git` header and all preceding hunk headers/lines. Fed into `DiffParser.parse`, `parseDiffHeader` scans for a `+++` line and, not finding one, returns `null`, so the parser reports **zero hunks and empty contents**: [3](#0-2) [4](#0-3) 

`convertDiff` then renders this as an apparently unchanged/empty text diff even though the underlying git object (blob) actually contains the full attacker-controlled content: [5](#0-4) 

This same `diffFromRawDiffOutput` path is reused by `getCommitDiff`, `getBranchMergeBaseDiff`, `getCommitRangeDiff`, `getWorkingDirectoryDiff`, and `getResolutionDiff`, so it affects both history-review and working-tree/staging review flows: [6](#0-5) [7](#0-6) 

### Impact

A malicious/compromised repository (or a malicious fork/PR that a victim clones or fetches) can commit a file containing an embedded NUL together with a `.gitattributes` entry forcing `text` on that path. When the victim opens that commit's diff (History view) or diffs their own working copy against it, GitHub Desktop shows the change as empty/no-hunks, while the actual git blob contains the full malicious payload. A user relying on the (blank-looking) diff for review may then stage/commit/push or simply trust the file's contents, unaware of the hidden content — this is a "silent corruption of what the user commits or pushes"-class review-bypass, since the discrepancy is between what Desktop displays and what the git object actually contains.

### Likelihood

Moderate-to-high: crafting a text file with an embedded NUL plus a one-line `.gitattributes` override is trivial and entirely within "repository content" that an unprivileged attacker fully controls (no local config, no external tool execution, no admin rights needed).

### Recommendation (conceptual)

`diffFromRawDiffOutput` should not assume the patch body is NUL-free. It should locate the boundary between the `--raw -z` section and the patch section deterministically (e.g., by counting the expected number of raw NUL-terminated fields per file, or by using `--raw`/`--patch` in separate invocations) rather than doing a naive `split('\0')` + `at(-1)`. [1](#0-0) 

### Proof of Concept (conceptual)

```
git init repo && cd repo
printf 'payload.bin text\n' > .gitattributes
printf 'line1\nline2\n' > payload.bin
git add -A && git commit -m init

# introduce embedded NUL as part of a modified/added line, forced to be diffed as text
printf 'line1\nline2\nSECRET_PAYLOAD\x00_after_nul_line\n' > payload.bin
git diff --patch-with-raw -z --no-color -- payload.bin | xxd
```
Inspecting the raw bytes shows a NUL inside the patch hunk itself (after `SECRET_PAYLOAD`). Feeding this buffer through the same logic as `diffFromRawDiffOutput` (`split('\0')`, take last piece) yields a fragment lacking the `diff --git`/`+++` header, causing `DiffParser.parse` to return `hunks: []`, so Desktop's diff view would show no changes for `payload.bin` even though `SECRET_PAYLOAD` was actually added to the tracked file.

function diffFromRawDiffOutput(output: Buffer): IRawDiff {
  // for now we just assume the diff is UTF-8, but given we have the raw buffer
  // we can try and convert this into other encodings in the future
  const result = output.toString('utf-8')

  const pieces = result.split('\0')
  const parser = new DiffParser()
  return parser.parse(forceUnwrap(`Invalid diff output`, pieces.at(-1)))
}
