### Title
Cached preprocess seed is never cleared, causing deterministic FROST nonce reuse across `share`/`complete` calls and secret-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The DKG-confirmer MuSig/FROST signing protocol persists a `CachedPreprocess` seed in `SigningProtocolDb::CachedPreprocesses` keyed only by `(b"DkgConfirmer", attempt)`. Every call to `share_internal` re-derives the same `AlgorithmSignMachine` — and therefore the same FROST nonces `(d, e)` — from that seed via `AlgorithmSignMachine::from_cache`, without ever deleting the entry. The frost `SignMachine::from_cache` contract explicitly requires that "the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share." [1](#0-0) 

### Finding Description
`preprocess_internal` generates a preprocess once, XORs the 32-byte seed with a key-derived encryption key, and stores it. On every subsequent call it decrypts and rebuilds the machine with the identical `ChaCha20Rng` seed, so `Commitments::new` produces identical nonces. [2](#0-1)  The nonces are bound at signing time as `actual = d + rho*e` where `rho` is the per-participant binding factor over the received preprocess commitments. [3](#0-2) 

`DkgConfirmer::share` and `DkgConfirmer::complete` both funnel through `share_internal`, which consumes attacker-supplied serialized preprocesses via `machine.read_preprocess` and then calls `machine.sign(preprocesses, msg)`. [4](#0-3)  Because the seed entry is never removed, each invocation signs with the same underlying `(d, e)`. If two invocations ever see different preprocess sets (different peers' commitments → different binding factors `rho_i` and different aggregate nonce `R` → different Schnorr challenge `c`), the signer emits two shares `s1 = d + rho1*e + c1*share_i` and `s2 = d + rho2*e + c2*share_i` over the same nonce — a classic ROS-style nonce-reuse equation system that yields the secret share. The in-file comment acknowledges the danger but defers safety entirely to BFT message ordering, with a TODO noting the matching check "its commitments on-chain" is not implemented. [5](#0-4) 

### Impact Explanation
Two signature shares produced under the same `(d, e)` nonces with distinct binding factors/challenges form linear equations solvable for the signer's secret share, and for MuSig2-style aggregation even the raw private key can be extracted via the standard two-nonce/key-cancel technique. Recovery of a validator's signing key lets the attacker forge signatures attributable to that validator, break the DKG-confirmation quorum assumptions, and escalate to control of key confirmation — the same consequence class as the referenced fault-injection advisory (secret disclosure / privilege escalation), reached here through untrusted preprocess bytes fed to `read_preprocess`/`sign` rather than hardware faults.

### Likelihood Explanation
Reachability requires `share`/`complete` to be invoked more than once per `(context, attempt)` with divergent preprocess maps. The code makes no defense-in-depth attempt to prevent this: the cached seed persists, `share` is callable independently of `complete`, and `complete` itself re-runs `share_internal` (a second signing with the same nonces). [6](#0-5)  Divergence requires either a logical flaw letting new preprocess messages overwrite prior ones, a rebuild following a distinct chain, or a peer equivocating on published commitments — the file's own TODOs admit the on-chain-commitment consistency check is not implemented. Because safety hinges entirely on an external BFT assumption rather than the cryptographic invariant enforced by `frost`, the exposure is real but contingent, consistent with Medium severity.

### Recommendation
Delete (or mark consumed) the `CachedPreprocesses` entry the first time `share_internal` successfully produces a share for a context, refusing subsequent `sign` calls for that context; additionally, implement the noted TODO by verifying that the preprocess commitments being signed against match the ones already published/finalized for this attempt before emitting any share, and never allow `complete` to re-derive a signing machine after `share` has already run — reuse the machine or stored share instead of re-signing.

### Proof of Concept
1. For attempt `A`, the coordinator calls `DkgConfirmer::share(preprocesses_P, key_pair)` where `preprocesses_P` contains commitment set P. `share_internal` loads the cached seed, regenerates nonces `(d, e)`, and emits share `s1 = d + rho_1·e + c_1·share_i`.
2. The coordinator later calls `share` (or `complete`, which internally calls `share_internal`) with a different commitment map `preprocesses_Q` (e.g., an equivocating peer's alternative preprocess, or a rebuild against a different finalized message set). `CachedPreprocesses::get` returns the same seed — it was never cleared — so `from_cache` regenerates the identical `(d, e)`. [7](#0-6) 
3. The new binding factors produce `rho_2 ≠ rho_1` and a different aggregate nonce/challenge `c_2`, yielding `s2 = d + rho_2·e + c_2·share_i`.
4. With `s1, s2, rho_1, rho_2, c_1, c_2` all known/derivable from the public preprocesses and shares, solve the 2×2 linear system for `d, e` and then `share_i` (and via MuSig aggregation, the validator's key), achieving key recovery from public inputs alone.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  1) A logical flaw exists, letting new messages over write prior messages
  2) A reorganization occurred from chain A to chain B, and with it, different messages

  Reorganizations are not supported, as BFT is assumed by the presence of a BFT algorithm. While
  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,
  would be by rebuilding the local process (this time following chain B). Upon any complete
  rebuild, we'd re-decide nonces, achieving safety. This does set a bound preventing partial
  rebuilds which is accepted.

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
  }
