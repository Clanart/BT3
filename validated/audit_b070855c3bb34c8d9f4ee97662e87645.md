### Title
Missing timestamp freshness (replay) validation in App Proxy and Webhook HMAC verification - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`, `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The Sherlock finding is about the Aave leverage extension trusting a Chainlink price feed without checking whether the data source (the L2 sequencer) is actually live/fresh, letting stale data drive a security-relevant decision (forced rebalance). The generalizable bug class is: **a signed/trusted input is accepted purely because its cryptographic signature validates, with no check on the freshness/age of that input**, so previously-valid data can be replayed as if it were current.

`shopify_app`'s App Proxy and Webhook HMAC verifiers share this same root cause: they validate the HMAC signature over the request body/query string but never validate the `timestamp` parameter (or any nonce) against the current time, so a captured, validly-signed request can be replayed indefinitely.

### Finding Description
`ShopifyApp::AppProxyVerification#query_string_valid?` recomputes the HMAC over the full query string (including the `timestamp` parameter as just another signed field) and compares it to the supplied `signature`. It never checks that `timestamp` is recent: [1](#0-0) 

Similarly, `ShopifyApp::WebhookVerification#verify_request` (via `PayloadVerification#hmac_valid?`) only checks the HMAC digest of the raw POST body against the shared secret — there's no check of a delivery timestamp or webhook id to reject re-delivery of an old, previously-processed payload: [2](#0-1) [3](#0-2) 

Because the signature is computed over static/replayable fields with no server-side expiry check, once an app-proxy URL or webhook payload is observed (e.g., via browser history, logs, a shared network, or a leaked link), it remains a permanently valid, "trusted" request as far as this verification logic is concerned — exactly analogous to Chainlink data being treated as fresh with no liveness check on the sequencer.

### Impact Explanation
An attacker who obtains a previously legitimate, signed app-proxy request or webhook payload (this can happen through logs, browser history/referrer leakage, or network capture on a non-TLS-terminated hop) can resubmit it at any later time and have it accepted as authentic, because `query_string_valid?` and `hmac_valid?` perform no freshness check. Depending on what the host application does with app-proxy/webhook data (e.g., trigger state changes, re-process an "order paid" or "app/uninstalled" event), this could cause duplicate processing or logically stale/incorrect state changes to be accepted as current — the same class of impact as the original report (protocol acting on stale data as if fresh).

### Likelihood Explanation
Exploitation requires the attacker to first obtain a validly-signed request (this is not a full authentication bypass from nothing), so likelihood is lower than a direct signature bypass. However, because there is no expiry window at all in these two verifiers, the window of exploitability is unbounded (unlike Shopify's admin session tokens, which do enforce `exp`/`jwt_expire_at`, see `WithShopifyIdToken#jwt_expire_at`): [4](#0-3) 

### Recommendation
For `AppProxyVerification`, after validating the signature, additionally reject requests whose `timestamp` query parameter is older than a small tolerance window (e.g., a few minutes) before calling the wrapped action. For `WebhookVerification`, consider validating recency using the `X-Shopify-Webhook-Id` combined with an idempotency/dedup store, or rejecting deliveries whose age (if a timestamp header is available) exceeds a bounded window, so that a captured, validly-signed payload cannot be replayed indefinitely.

### Proof of Concept
1. Capture a legitimate app-proxy request URL (including `signature` and `timestamp` query params) sent by Shopify to `AppProxyVerificationController`, e.g. via a shared link, browser history, or a logging proxy.
2. At any later time, replay the exact same URL/query string to the app.
3. `query_string_valid?` recomputes the HMAC over the same (unchanged) query hash and it matches the captured `signature`, so the request passes verification and reaches the controller action as if it were a fresh, currently-authorized request: [5](#0-4)

```ruby
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
```

```ruby
    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```
