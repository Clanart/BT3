Audit Report

## Title
Unbounded concurrent WebSocket connections in RPC PubSub service enable remote memory-exhaustion DoS - (File: `rpc/src/rpc_pubsub_service.rs`)

## Summary
The `listen()` accept loop in `rpc/src/rpc_pubsub_service.rs` accepts every incoming TCP connection unconditionally and spawns a dedicated tokio task for each one, with no cap on concurrent connections. The only related instrumentation, `TokenCounter`/`CounterToken` in `metrics/src/lib.rs`, is purely informational (emits a `datapoint_info!` metric via `Arc::strong_count`) and performs no admission control, allowing an unprivileged remote attacker to exhaust validator memory/file descriptors by opening large numbers of sockets against the public PubSub port.

## Finding Description
`listen()` runs an infinite `select!` loop that calls `listener.accept()` and unconditionally spawns a `handle_connection` task for every accepted socket [1](#0-0) . The `counter_token` obtained from `TokenCounter::new("rpc_pubsub_connections")` is only used to report the live connection count as a metric; its `create_token`/`Clone`/`Drop` implementations only call `datapoint_info!` and never reject or throttle a connection [2](#0-1) . There is no `Semaphore`, `max_connections` field, or any other admission-control primitive anywhere in the accept path. Each accepted connection immediately consumes a `TcpStream`, an OS file descriptor, and a spawned task on the pubsub tokio runtime before any WebSocket handshake data is required, and `handle_connection` further allocates a `DashMap` for `current_subscriptions` and a full `jsonrpc_core::IoHandler` with `RpcSolPubSubImpl` registered once the handshake proceeds [3](#0-2) . The only existing quota, `max_active_subscriptions` (`DEFAULT_MAX_ACTIVE_SUBSCRIPTIONS = 1_000_000`), bounds *subscriptions* per established connection, not the number of TCP connections/tasks themselves [4](#0-3) . The companion JSON-RPC HTTP server configured via `ServerBuilder` in `rpc/src/rpc_service.rs` similarly sets `.max_request_body_size(...)` and `.threads(1)` but exposes no `.max_connections()` or per-IP concurrency cap.

## Impact Explanation
An unprivileged remote attacker who can reach a validator's public RPC PubSub port can open a large number of concurrent TCP connections without completing any WebSocket handshake or sending valid data, driving unbounded growth in accepted sockets and spawned tokio tasks on a runtime that by default has very few worker threads (`DEFAULT_WORKER_THREADS = 1`). This degrades or crashes the RPC/PubSub service, denying legitimate clients (e.g., wallets/dApps using `signatureSubscribe`/`accountSubscribe`) access to the node — matching the "RPC/pubsub... non-RPC remote exhaustion/crash" and "single-client low-rate RPC crash/degradation" impact categories.

## Likelihood Explanation
Likelihood is high: exploitation requires only knowledge of a public RPC PubSub endpoint's address/port and the ability to open many concurrent sockets from one or a few hosts (no authentication, staking, or special network position needed), and is trivially scriptable and repeatable.

## Recommendation
Add a bounded concurrency gate (e.g., a `tokio::sync::Semaphore` or hard connection cap) to the accept loop in `listen()` in `rpc/src/rpc_pubsub_service.rs`, rejecting or immediately closing new connections once a configurable `max_connections` threshold is reached, mirroring the existing `max_active_subscriptions` pattern but applied at the connection level. Consider an analogous `max_connections` knob for the JSON-RPC HTTP server built in `rpc/src/rpc_service.rs`.

## Proof of Concept
1. Start a validator/test-validator exposing the RPC PubSub port.
2. From an attacker host, open a large number of raw TCP connections to the pubsub port without completing the WebSocket handshake:
```python
import socket
socks = []
for _ in range(50000):
    s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s.connect(("target-rpc-host", PUBSUB_PORT))
    socks.append(s)
```
3. Observe growth in the `rpc_pubsub_connections` metric and validator process memory/fd usage with no rejection occurring, since `listen()` in `rpc/src/rpc_pubsub_service.rs` (lines 429-474) contains no cap on accepted connections.

```rust
async fn listen(
    listen_address: SocketAddr,
    config: PubSubConfig,
    subscription_control: SubscriptionControl,
    mut tripwire: Tripwire,
) -> io::Result<()> {
    let listener = match tokio::net::TcpListener::bind(&listen_address).await {
        Ok(listener) => {
            info!("rpc_pubsub listening on {listen_address:?}");
            listener
        }
        Err(e) => {
            error!(
                "failed to bind rpc_pubsub listener on {listen_address:?}: {e}. Hint: is the port \
                 already in use?"
            );
            return Err(e);
        }
    };
    let counter = TokenCounter::new("rpc_pubsub_connections");
    loop {
        select! {
            result = listener.accept() => match result {
                Ok((socket, addr)) => {
                    debug!("new client ({addr:?})");
                    let subscription_control = subscription_control.clone();
                    let config = config.clone();
                    let tripwire = tripwire.clone();
                    let counter_token = counter.create_token();
                    tokio::spawn(async move {
                        let handle = handle_connection(
                            socket, subscription_control, config, tripwire
                        );
                        match handle.await {
                            Ok(()) => debug!("connection closed ({addr:?})"),
                            Err(err) => warn!("connection handler error ({addr:?}): {err}"),
                        }
                        drop(counter_token); // Force moving token into the task.
                    });
                }
                Err(e) => error!("couldn't accept connection: {e:?}"),
            },
            _ = &mut tripwire => return Ok(()),
        }
    }
}
```

```rust
/// A helper that sends the count of created tokens as a datapoint.
#[allow(clippy::redundant_allocation)]
pub struct TokenCounter(Arc<&'static str>);

impl TokenCounter {
    /// Creates a new counter with the specified metrics `name`.
    pub fn new(name: &'static str) -> Self {
        Self(Arc::new(name))
    }

    /// Creates a new token for this counter. The metric's value will be equal
    /// to the number of `CounterToken`s.
    pub fn create_token(&self) -> CounterToken {
        // new_count = strong_count
        //    - 1 (in TokenCounter)
        //    + 1 (token that's being created)
        datapoint_info!(*self.0, ("count", Arc::strong_count(&self.0), i64));
        CounterToken(self.0.clone())
    }
}

/// A token for `TokenCounter`.
#[allow(clippy::redundant_allocation)]
pub struct CounterToken(Arc<&'static str>);

impl Clone for CounterToken {
    fn clone(&self) -> Self {
        // new_count = strong_count
        //    - 1 (in TokenCounter)
        //    + 1 (token that's being created)
        datapoint_info!(*self.0, ("count", Arc::strong_count(&self.0), i64));
        CounterToken(self.0.clone())
    }
}

impl Drop for CounterToken {
    fn drop(&mut self) {
        // new_count = strong_count
        //    - 1 (in TokenCounter, if it still exists)
        //    - 1 (token that's being dropped)
        datapoint_info!(
            *self.0,
            ("count", Arc::strong_count(&self.0).saturating_sub(2), i64)
        );
    }
}
```
