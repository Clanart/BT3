### Title
Missing Zero-Address Validation in Bank Precompile `sendNative`/`send` Allows Permanent Loss of Funds - (File: `precompiles/bank/bank.go`)

### Summary
The Sei bank precompile's `sendNative` and `send` functions accept an arbitrary bech32-encoded recipient address without checking that it does not resolve to the "zero" `AccAddress` (20 zero bytes). Unlike the project's own ERC20/ERC721/ERC1155 pointer contracts, which explicitly `require(to != address(0), ...)` before every transfer, the bank precompile performs no equivalent check, so a caller-specified transfer can permanently lock native funds at an unspendable address.

### Finding Description
`PrecompileExecutor.sendNative` in `precompiles/bank/bank.go` resolves the receiver purely from a caller-supplied string and only checks it's non-empty and successfully bech32-decodes: [1](#0-0) 

```
receiverAddr, ok := (args[0]).(string)
if !ok || receiverAddr == "" {
    return nil, 0, errors.New("invalid addr")
}
receiverSeiAddr, err := sdk.AccAddressFromBech32(receiverAddr)
...
if err := p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei); err != nil {
```

`sdk.AccAddressFromBech32` only validates that the string decodes into a byte slice of acceptable length (20 or 32 bytes per `VerifyAddressFormat`) — it does **not** reject the all-zero address: [2](#0-1) [3](#0-2) 

The same missing check exists in `send()` and across every legacy version of the bank precompile (`precompiles/bank/legacy/v552` through `v67`), so the gap has been present through the module's entire history: [4](#0-3) 

By contrast, the token pointer contracts shipped in the same repository (which the bank precompile's `usei`/native transfer path is meant to be consistent with) explicitly guard against sending to `address(0)`: [5](#0-4) [6](#0-5) 

This asymmetry confirms the zero-address check is a recognized safeguard in this codebase that was simply omitted from the native `usei`/`wei` transfer path in the bank precompile.

### Impact Explanation
The all-zero `sdk.AccAddress` is not derivable from any known public key/private key pair, so any `usei`/`wei` sent to it via `sendNative` (or `send` for `ERC20NativePointer`-routed denoms) becomes permanently unspendable — a direct, irreversible loss of funds for the party whose value is routed there. Because `sendNative` is `payable` and reachable directly by any unprivileged EVM caller with a single transaction, the class of loss (concrete fund loss / permanent freezing) matches the acceptance criteria.

### Likelihood Explanation
Likelihood is limited to accidental or automated-tooling misuse (e.g., a bridging or batching contract that forwards a zero/uninitialized address parameter), since the sender chooses the recipient themselves. Nonetheless, this exactly mirrors the reported bug class: a payment-forwarding function that omits a standard zero-address guard that is present everywhere else the same pattern occurs in-repo, making the omission an inconsistency rather than a deliberate design choice.

### Recommendation
Add an explicit check in `PrecompileExecutor.send` and `PrecompileExecutor.sendNative` (and, if still relevant, in any active legacy handlers) that rejects the zero `sdk.AccAddress` before invoking `bankKeeper.SendCoins`/`SendCoinsAndWei`, mirroring the `require(to != address(0))` pattern already used in `contracts/src/CW20ERC20Pointer.sol` and `contracts/src/CW1155ERC1155Pointer.sol`:

```go
if receiverSeiAddr.Empty() || receiverSeiAddr.Equals(sdk.AccAddress(make([]byte, 20))) {
    return nil, 0, errors.New("invalid addr: zero address")
}
```

### Proof of Concept
1. An EVM account associates its Sei address (any 0-value self transaction) and holds native `usei`.
2. The account calls `bank.sendNative(recipient)` on the bank precompile (`precompiles/bank/bank.go`, `sendNative`) with `value` set to a non-zero amount and `recipient` set to the bech32 encoding of 20 zero bytes (a syntactically valid Sei address per `AccAddressFromBech32`/`VerifyAddressFormat`).
3. `sendNative` passes validation (`receiverAddr != ""`, successful bech32 decode) and calls `p.bankKeeper.SendCoinsAndWei(ctx, senderSeiAddr, receiverSeiAddr, usei, wei)`, transferring the funds to the zero address.
4. No private key can ever be derived to control the zero address, so the transferred `usei`/`wei` is permanently unrecoverable.

```go
// AccAddressFromBech32 creates an AccAddress from a Bech32 string.
func AccAddressFromBech32(address string) (addr AccAddress, err error) {
	if len(strings.TrimSpace(address)) == 0 {
		return AccAddress{}, errors.New("empty address string is not allowed")
	}

	bech32PrefixAccAddr := GetConfig().GetBech32AccountAddrPrefix()

	bz, err := GetFromBech32(address, bech32PrefixAccAddr)
	if err != nil {
		return nil, err
	}

	err = VerifyAddressFormat(bz)
	if err != nil {
		return nil, err
	}

	return AccAddress(bz), nil
}
```
