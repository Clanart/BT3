### Title
Batch relayer-reward misattribution in `pallet-consensus-incentives` `on_executed` — one relayer collects rewards for state-machine updates delivered by other relayers' consensus messages - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`FeeHandler::on_executed` is invoked once per `pallet-ismp` extrinsic with the *full* `Vec<MessageWithWeight>` submitted in that call and the *full* list of `IsmpEvent`s produced by executing all of them. [1](#0-0)  `pallet-consensus-incentives`'s implementation derives the rewarded relayer identity **only from `messages.get(0)`** (the first `Message::Consensus` in the batch), then pays that single relayer for **every** distinct `StateMachineId` whose `StateMachineUpdated` event appears anywhere in the batch. [2](#0-1) 

### Finding Description
ISMP messages are permissionless/unsigned at the extrinsic layer (`ensure_none`-style dispatch); the actual "relayer" identity is not `frame_system`'s origin but an embedded `signer` field inside each individual `Message::Consensus` payload, recovered via `Signature::verify_and_get_sr25519_pubkey`. [3](#0-2)  Because the reward payout only ever looks at `messages[0]`, any account submitting the `execute(messages)` extrinsic can bundle N distinct `Message::Consensus` datagrams — one for each of N different `state_machine_id`s — but only the signer embedded in the **first** message is credited, while the reward loop iterates over `highest_per_state_machine`, a map built from **all** `StateMachineUpdated` events across the whole batch, regardless of which message in the batch produced which event:

```rust
let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
for event in events {
    if let IsmpEvent::StateMachineUpdated(update) = event {
        highest_per_state_machine.entry(update.state_machine_id) ...
    }
}
for (state_machine_id, latest_height) in highest_per_state_machine {
    let _ = Self::process_message(state_machine_height, state_machine_id, relayer_account.clone().into());
}
``` [4](#0-3) 

There is no per-event/per-message correlation check that the `state_machine_id` being rewarded actually corresponds to a consensus message whose embedded `signer` equals `relayer_account`. The code comment even documents the earlier, adjacent bug class (per-state-machine double counting within a batch) and shows it was patched by collapsing to a max height per chain — but the fix only deduplicated *within* one state machine; it never validated that the single globally-extracted `relayer_account` from `messages[0]` is the party actually responsible for updating *each* state machine being paid.

This is directly analogous to the Alchemix `pokeTokens` bug: a single external call fans out over multiple sub-operations (there, `reset()` + `poke()` on one token; here, N `StateMachineUpdated` events from N distinct consensus messages), and the reward-accrual logic incorrectly applies to state transitions it was never designed to cover for that beneficiary, resulting in payment inflation/misattribution beyond what the protocol intends per unit of relaying work actually performed by the credited party.

### Impact Explanation
Every block-cost reward for every `StateMachineId` touched in a batch is transferred from the treasury to a single `relayer_account`, even when the on-chain state advance for some of those chains was authored/proven via a different message with a different embedded signer. [5](#0-4)  This is a wrong-beneficiary / fund-diversion condition against the treasury: an unprivileged account can be paid for state-machine advances it did not economically produce simply by packaging additional valid (but not-yet-applied) consensus datagrams into the same `execute()` call ahead of, or alongside, its own message. This matches the bounty's "logic attacks / wrong beneficiary or amount" impact class and drains `T::TreasuryAccount` funds to the wrong party across multiple chains in a single batched claim.

### Likelihood Explanation
No privileged role, malicious relayer collusion, or front-running of a specific pending transaction is structurally required to trigger the flaw: the vulnerable code path exists any time `execute()` is called with more than one `Message::Consensus` entry targeting different `state_machine_id`s, which is a normal, permissible batching pattern (the pallet-ismp `execute` function accepts an arbitrary `Vec<Message>` in one call). [6](#0-5)  The root cause is a missing per-event-to-message attribution check, which is a deterministic logic defect rather than a timing-dependent race, so it is reliably reproducible by constructing/submitting a batch containing at least two valid, not-yet-committed consensus proofs for two different chains.

### Recommendation
Attribute the relayer reward per `StateMachineUpdated` event to the specific `Message::Consensus` entry that produced it (e.g., by tracking which message index/consensus client corresponds to each `state_machine_id` during `handle_incoming_message`, and recovering `signer` from that specific message) instead of using a single globally-extracted `messages[0]` signer for the entire batch. Alternatively, restrict `on_executed`/`process_message` to only reward when the batch contains exactly one `Message::Consensus` per distinct `state_machine_id`, and reject or split batches that would otherwise require multi-signer attribution within a single `execute()` call.

### Proof of Concept
Conceptual repro (based on `modules/pallets/testsuite/src/tests/pallet_consensus_incentives.rs` patterns):
1. Configure `StateMachinesCostPerBlock` for chain A and chain B, fund the treasury.
2. Have relayer R2 construct/observe a valid `Message::Consensus` for chain B (any account can self-sign the `keccak256(consensus_proof)` with its own key as attacker's `signer`, since the signature only proves "who claims delivery," not exclusive knowledge of the proof).
3. Attacker constructs `Message::Consensus` for chain A signed with their own key, then calls `Pallet::execute(vec![attacker_msg_for_A, r2_msg_for_B])` in one extrinsic.
4. `handle_incoming_message` processes both, emitting `StateMachineUpdated` for both chain A and chain B.
5. `on_executed` derives `relayer_account` only from `messages[0]` (attacker), then loops `highest_per_state_machine` = {A, B} and pays the attacker the treasury reward for **both** A's and B's block-cost advance, even though R2's message is what advanced chain B.
6. Assert: attacker's balance increases by `reward_A + reward_B`, while R2 (whose proof produced B's advance) receives nothing — confirming misattributed payout.

		let host = Pallet::<T>::default();

		let message_results = messages

			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
