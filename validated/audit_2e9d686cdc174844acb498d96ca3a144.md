## Finding: Silent Remote-URL Rewrite from Untrusted GitHub API Data

### Title
Desktop silently rewrites a repository's `origin` remote URL based on an unvalidated GitHub API `clone_url`, allowing silent redirection of pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes a repository's associated GitHub metadata, it compares the locally configured git remote URL against the `clone_url` field of the API response and, if they differ (but share the same URL scheme), it automatically calls `git remote set-url` to overwrite the local remote — with no user prompt, no diff shown, and no check that the new host belongs to the same GitHub/GitHub Enterprise endpoint the repository is associated with.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository`, which fetches fresh repo data straight from the API (`api.fetchRepository`) and unconditionally feeds it into the remote-rewrite logic: [1](#0-0) 

`updateRemoteUrl` itself only performs two checks before rewriting the remote: (1) that the URL *scheme* ("https:" vs "https:") of the old and new URL matches, and (2) that the currently configured remote still equals the previously cached `cloneURL`. It never verifies that the new URL's *hostname* corresponds to the repository's known API `endpoint` (github.com or the specific GHES host the user connected to): [2](#0-1) 

The actual write is an unconditional `git remote set-url`: [3](#0-2) 

This refresh path runs automatically and silently every time a repository is selected/switched to (`_selectRepositoryRefreshTasks` → `repositoryWithRefreshedGitHubRepository`), and again whenever the active account changes: [4](#0-3) [5](#0-4) 

The broken invariant mirrors the Perennial report exactly: a routine, seemingly-safe automated maintenance action (rebalancing collateral / refreshing repo metadata) is allowed to push a tracked state variable (leverage / `origin` remote URL) into an unsafe value derived from an external, less-trusted input (market weight = 0 / API `clone_url`), with no guard checking that the resulting state is actually safe (leverage below margin threshold / new host matches the trusted endpoint).

### Impact Explanation
The corrupted value is the git `origin` remote URL. Because the rewrite happens transparently on repository selection/background refresh, all subsequent user actions — `git push`, `git fetch`, `git pull` — silently target whatever host the (attacker-influenced) API response specified, satisfying the "silent corruption of what the user commits or pushes" impact bucket:
- A push silently ships the user's local commits to a third-party server instead of GitHub, with no on-screen indication the origin changed.
- A fetch/pull silently merges attacker-supplied refs into the user's working tree as if they came from the legitimate origin.
- If the attacker-chosen host happens to match an entry already known to the OS credential manager (or if the user's Git credential helper matches by scheme/hostname pattern loosely), the credential/token normally scoped to the real GitHub endpoint can be sent to the new host, producing credential exfiltration.

### Likelihood Explanation
The only way to reach the attacker-controlled `clone_url` is via the response of `api.fetchRepository(owner, name)`, i.e. the GitHub/GHES API response object itself: [6](#0-5) 

This matches the accepted attacker model ("attacker controls...a GitHub API object"): a malicious or compromised GitHub Enterprise Server the user has legitimately added an account for, or a network position capable of tampering with API responses, can return an arbitrary `clone_url` and have it silently applied on the very next repository selection or account refresh — no unusual user interaction required beyond normal app usage.

### Recommendation
Before calling `gitStore.setRemoteURL`, validate that the parsed hostname of `apiRepo.clone_url` matches the hostname of the repository's known/trusted `endpoint` (or an explicit allow-list derived from the account the repository is associated with), and/or surface a confirmation prompt to the user instead of performing the rewrite silently, mirroring the "recommendation" pattern of validating state before allowing an automated transition (as in the Perennial fix of tying collateral to leverage even when weight is 0 — here, tying the remote rewrite to a validated trusted host even when the API-reported repo identity differs).

### Proof of Concept
1. Add an account for a GitHub Enterprise Server (or a MITM-capable network position for `api.github.com`).
2. Have that server return, for `GET repos/{owner}/{name}`, a JSON payload with `clone_url` pointing to an attacker-controlled `https://` host (any host, since only the scheme is checked).
3. Existing unit test demonstrates the exact unconditional-rewrite mechanics — the test asserts the local remote is silently updated to whatever `clone_url` is provided, without hostname allow-listing: [7](#0-6) 
4. In the live app, open/select the affected repository (or trigger the periodic background fetch/refresh) — `repositoryWithRefreshedGitHubRepository` runs automatically and rewrites `origin` to the attacker's URL with no dialog.
5. The user's next `git push`/`git fetch` silently targets the attacker's server.

```typescript
import { IAPIRepository } from '../../api'
import { GitStore } from '../git-store'
import { urlMatchesRemote } from '../../repository-matching'
import * as URL from 'url'
import { GitHubRepository } from '../../../models/github-repository'

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
