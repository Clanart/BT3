### Title
Anyone can force-claim and force-lock a user's MGP rewards via `multiclaimFor()` without consent - (File: rewards/MasterMagpie.sol)

### Summary
`MasterMagpie.multiclaimFor()` lets any unprivileged caller trigger a full reward claim for an arbitrary `_account`, exactly the access-control gap described in the reference finding (Sublime's `withdrawInterest()`), where anyone could force a state-changing withdrawal for another user regardless of whether it is in that user's interest.

### Finding Description
`multiclaimFor()` takes an arbitrary `_account` supplied by the caller with no `msg.sender == _account` check, and internally routes both the claimed user and the receiver to that same `_account`: [1](#0-0) 

This calls `_multiClaim(_stakingTokens, _account, _account, _rewardTokens)`, which for the default staking pools does not simply transfer liquid MGP — it forces the claimed MGP to be locked on the user's behalf via `_sendVlMGPFor`: [2](#0-1) [3](#0-2) 

`_sendVlMGPFor` calls `vlmgp.lockFor(_amount, _account)`, which locks the MGP into vlMGP (a vote-locked token) for the account without that account's consent. Unlike `multiclaimSpec`/`multiclaim`/`multiclaimOnBehalf` (the last of which is restricted with `_onlyCompounder`), `multiclaimFor` has no restriction on who may invoke it or when, so any address can force an arbitrary user's claimable MGP to be swept into a time-locked position at a moment the user did not choose.

### Impact Explanation
Forcing a user's rewards to be claimed and immediately locked into vlMGP converts otherwise flexible/claimable MGP into a vote-locked, non-transferable position with a lock duration, which is functionally a freeze of the user's yield for that lock period (typically well beyond 24 hours in vlToken designs) that the user did not request. This mirrors the original report's concern that forced withdrawal/claim actions can leak value or work against the specific holder's optimal strategy (e.g., they may have preferred to let rewards accrue, batch-claim for gas efficiency, or claim at a specific time), except here the forced state change also locks the resulting tokens rather than simply transferring already-owed value.

### Likelihood Explanation
The function is `external`, unauthenticated beyond `whenNotPaused`, and callable by any wallet at any time against any staked user, exactly as with the original `withdrawInterest()` bug — no special conditions or privileged role are required to trigger it, so likelihood is high whenever a user holds an outstanding claim.

### Recommendation
Restrict `multiclaimFor` (and any similar "for" methods without an explicit privileged modifier) to `msg.sender == _account`, or gate it behind the same `_onlyCompounder`/authorized-caller pattern already used for `multiclaimOnBehalf`, consistent with the referenced fix that added `require(msg.sender == _lender)`.

### Proof of Concept
1. User A stakes into MasterMagpie and accrues claimable MGP rewards in a default pool.
2. Attacker (unrelated address) calls `multiclaimFor([stakingToken], [[]], userA)`.
3. `_multiClaim` computes `defaultPoolAmount` for User A and invokes `_sendVlMGPFor(userA, userA, defaultPoolAmount)`, which calls `vlmgp.lockFor(defaultPoolAmount, userA)`.
4. User A's previously claimable MGP is now locked in vlMGP without their consent, at a time and under lock terms they did not choose. [1](#0-0) [3](#0-2)
