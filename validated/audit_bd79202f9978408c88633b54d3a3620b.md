### Title
`determineMergeability` swallows unexpected `git merge-tree` errors and reports a false "Clean" merge status - ([File: app/src/lib/git/merge-tree.ts])

### Summary
`determineMergeability` in [1](#0-0)  runs `git merge-tree --write-tree` against the tip commits of two branches to compute whether a merge would be clean, conflicted, or invalid. Its result feeds directly into a UI decision (`ComputedAction`) that controls whether Desktop lets the user perform the merge without warning. When the underlying `git` call rejects with any error other than `CannotMergeUnrelatedHistories`, the function re-throws — but at least one call site coerces *any* thrown error into a fabricated "Clean" result instead of surfacing the failure, exactly mirroring the PreimageOracle pattern of writing a plausible-looking value into shared state on failure instead of reverting/propagating the error.

### Finding Description
`determineMergeability` is the sole source of truth for whether a merge between `ours` and `theirs` will be clean. Its caller in `MergeChooseBranchDialog.updateStatus` is: [2](#0-1) 

Any error from the `git merge-tree` invocation — for example a corrupt/oversized tree from a fetched or cloned remote, a git process crash, an out-of-memory condition, or any other unexpected `GitError` not equal to `CannotMergeUnrelatedHistories` — is caught and mapped unconditionally to `{ kind: ComputedAction.Clean }`. This is the exact analog of the `PreimageOracle` bug: a failed/aborted computation (`outOfGas` in the original; a failed `merge-tree` invocation here) still results in the "answer" slot being populated with a valid-looking value instead of causing the caller to treat the operation as failed.

That fabricated `Clean` status then flows into `renderStatusPreviewMessage`, which shows the reassuring message "This will merge N commits from X into Y" [3](#0-2) , and into `canStart()`/`canStartOperation`, which uses `mergeStatus?.kind` to decide whether the "Merge" button is enabled [4](#0-3) . Clicking "Merge" then invokes `dispatcher.mergeBranch(repository, selectedBranch, mergeStatus, ...)` [5](#0-4) , which performs the real `git merge` regardless of whether the preview computation actually verified a clean merge.

### Impact Explanation
The corrupted value here is the `mergeStatus`/`ComputedAction` that Desktop treats as ground truth for "this merge is safe and has no conflicts." An attacker who controls the contents of a branch/ref the user is asked to merge (e.g., a malicious PR branch fetched into the repository, or a crafted object graph that makes `git merge-tree` fail rather than cleanly report conflicts) can cause the mergeability probe to error out. Instead of Desktop halting or warning the user, the UI silently reports "Clean," the confirmation UI is suppressed, and the user is guided straight into running the real merge with no indication that conflicts or anomalies exist. This falls squarely under "silent corruption of what the user commits or pushes": the user can end up committing/merging content whose conflict state was never actually verified, based on attacker-influenced repository content delivered via fetch/clone — no local access, no admin rights, and no prior compromise required.

### Likelihood Explanation
This path is reachable purely by the user choosing to merge a branch that came from a remote/fork the attacker controls (a completely normal, expected workflow in Desktop). Triggering an error from `git merge-tree` (rather than a graceful conflict report) requires the object/tree data to cause git itself to fail — this is plausible but not trivially reproducible without crafting a specific malformed/oversized git object, so likelihood is assessed as medium rather than high. No special user action beyond a normal merge attempt is needed once such a repository state exists.

### Recommendation
`updateStatus` (and any other caller of `determineMergeability`) should not collapse an unexpected error into `ComputedAction.Clean`. Instead:
- Propagate/log the failure and set a distinct UI state such as `ComputedAction.Invalid` (already used for unrelated-histories) or a new "Unknown/Error" status.
- Disable `canStartOperation` (or otherwise require explicit user acknowledgment) whenever the mergeability check could not be completed, rather than allowing the merge button to be enabled on a fabricated "no conflicts" result.
- Apply the same fix pattern anywhere else `ComputedAction.Clean` is used as a catch-all fallback for git command failures (e.g., check `rebase-choose-branch-dialog.tsx` and any similar mergeability/rebase-preview flows for the same pattern).

### Proof of Concept
1. Prepare a repository with a branch `theirs` whose tree/commit graph is crafted (or otherwise arranged) so that `git merge-tree --write-tree --name-only --no-messages -z <ours> <theirs>` exits with an unexpected non-`CannotMergeUnrelatedHistories` git error (e.g., due to a corrupted/oversized object introduced via a malicious fetch).
2. In Desktop, open the "Merge into current branch" dialog and select `theirs`.
3. `updateStatus` calls `determineMergeability`, which throws; the `.catch` handler in [6](#0-5)  converts this into `{ kind: ComputedAction.Clean }`.
4. The dialog displays "This will merge N commits..." with no conflict warning, and the "Merge" button is enabled.
5. The user clicks Merge; Desktop runs the real `git merge`, which may produce actual conflicts or unexpected tree content that was never surfaced to the user during the preview step, resulting in an uninformed commit/push.

Note: I was not able to execute `git merge-tree` against a crafted malicious object to empirically confirm which specific error codes it can emit beyond `CannotMergeUnrelatedHistories` in this environment; the analysis is based on static code review of the catch-all error handling shown above.

```typescript
export async function determineMergeability(
  repository: Repository,
  ours: Branch,
  theirs: Branch
) {
  return git(
    [
      'merge-tree',
      '--write-tree',
      '--name-only',
      '--no-messages',
      '-z',
      ours.tip.sha,
      theirs.tip.sha,
    ],
    repository.path,
    'determineMergeability',
    { successExitCodes: new Set([0, 1]) }
  )
    .then<MergeTreeResult>(({ stdout }) => {
      // The output will be "<tree-id>\0[<filename>\0]*" so we can get the
      // number of conflicted files by counting the number of null bytes and
      // subtracting one for the tree id.
      const conflictedFiles = (stdout.match(/\0/g)?.length ?? 0) - 1
      return conflictedFiles > 0
        ? { kind: ComputedAction.Conflicts, conflictedFiles }
        : { kind: ComputedAction.Clean }
    })
    .catch<MergeTreeResult>(e =>
      isGitError(e, GitError.CannotMergeUnrelatedHistories)
        ? Promise.resolve({ kind: ComputedAction.Invalid })
        : Promise.reject(e)
    )
}
```
