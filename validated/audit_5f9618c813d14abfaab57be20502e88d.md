## Analysis

The bug-class in the external report is: a value earmarked for a specific facilitator role (the "commission"/affiliate payout) is only ever paid out along **one** completion path of a multi-path settlement flow, and the alternate, equally-legitimate completion path silently skips that payout — misallocating value that was accounted for at deposit time.

The Hyperbridge analog for this class exists in the same-chain partial-fill path of `IntrinsicIntents._fillSameChain` combined with the fee-release logic in `IntentsBase._withdraw`.

**Mechanism:**

`placeOrder` escrows `order.fees` into a sentinel slot `_orders[commitment][TRANSACTION_FEES]` at order creation, meant to compensate whoever fills the order [1](#0-0) .

For same-chain orders, `_fillSameChain` allows any number of unrelated solvers to progressively fill different portions of the order over time via `_partialFills`. On every call, `_withdraw` is invoked with `finalize = isFullyFilled` and `beneficiary = msg.sender` (the *current* caller), and `TRANSACTION_FEES` is only released when `finalize` is `true`: [2](#0-1) 

The fee-release itself: [3](#0-2) 

The consequence: the *entire* accumulated `order.fees` is transferred in full to whichever solver happens to submit the fill call that pushes `isFullyFilled` to `true`, regardless of how small that solver's actual contribution was. Any earlier solver(s) who filled the vast majority of the order's output receive none of the fee, because their fills set `finalize = false` and `_filled[commitment]` is explicitly deleted after a partial fill (line 140), leaving the order open and un-attributed for anyone to swoop in and complete.

### Title
Same-chain partial-fill order fee (`TRANSACTION_FEES`) is paid entirely to whichever solver completes the final sliver of an order, not the solver(s) who did the real work - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents._fillSameChain` lets unrelated, permissionless solvers each fill a fraction of a same-chain intent order's outputs. The escrowed transaction fee (`order.fees`, stored under `TRANSACTION_FEES`) is only released on the fill call that finally satisfies `isFullyFilled`, and it is paid 100% to `msg.sender` of that one call. A solver who fills 99.9% of the order's required output receives none of the fee if a different address submits the final, arbitrarily small remaining fill.

### Finding Description
`placeOrder` escrows `order.fees` for the lifetime of the order [1](#0-0) . During same-chain fills, each partial fill computes `amountFilled` per output asset and only marks `isFullyFilled = true` once every output asset reaches its `totalRequired` amount [4](#0-3) . The withdrawal beneficiary for the *fee* release is always `msg.sender` of the call that completes the order, and `_withdraw`'s fee branch only executes when `finalize == true`, transferring the whole `TRANSACTION_FEES` balance in one shot [5](#0-4) . Because `_filled[commitment]` is deleted after every non-final partial fill (line 140 of `IntrinsicIntents.sol`), the order remains open to *any* solver, not just those who previously filled it, and there is no accounting that splits `order.fees` proportionally across contributors. This exactly mirrors the reported class: money escrowed for one purpose (compensating the filler) is only released along a single completion event and is not apportioned to the party the design intends to reward, wrongly benefiting whichever address happens to trigger that specific completion.

### Impact Explanation
An unprivileged solver can monitor a partially-filled, still-open same-chain order and submit a trivial final fill (e.g., 1 wei of the remaining output) purely to trigger `isFullyFilled = true` and collect the **entire** `order.fees` escrow, which was funded to compensate meaningful fill effort. This is a wrong-beneficiary/wrong-amount fund diversion inside the intent settlement/reward path, directly matching the bounty's "stealing or loss of funds" and "logic attacks" categories — no malicious relayer, prover, or admin is needed, and no proof forgery is involved; it is a pure public-entrypoint sequencing flaw in `fillOrder`.

### Likelihood Explanation
Same-chain partial fills are a documented, intended feature (any solver may fill any portion), and `order.fees` amounts can be economically significant for large orders. An attacker only needs to watch on-chain state of `_partialFills`/`_orders` for a commitment and submit a minimal fill once the order is nearly complete — a straightforward, cheap, and repeatable strategy requiring no special privileges.

### Recommendation
Track fee entitlement per contributor (e.g., accumulate a per-solver credit proportional to the escrow released to each partial filler) and distribute `TRANSACTION_FEES` pro-rata across all solvers who filled the order, rather than paying it wholly to the address that happens to complete the final fraction. Alternatively, disallow fee-bearing orders from same-chain partial fills (similar to the existing `PartialFillNotAllowed` restriction already applied to orders carrying `output.call`), forcing an all-or-nothing fill so the entire fee always goes to the single solver who did the entire job.

### Proof of Concept
1. User places a same-chain order with `order.fees = 100` (fee token) and `output.assets[0].amount = 1000` DAI, no `output.call`.
2. Solver A calls `fillOrder` providing `999` DAI. `_fillSameChain` computes `amountFilled = 999 < totalRequired = 1000` → `isFullyFilled = false`; `_withdraw(body, false, false)` releases only the proportional input escrow to Solver A; `TRANSACTION_FEES` stays untouched; `_filled[commitment]` is deleted, re-opening the order to anyone [6](#0-5) .
3. Attacker (Solver B), who contributed nothing previously, calls `fillOrder` providing the remaining `1` DAI. `amountFilled` reaches `totalRequired`, so `isFullyFilled = true`; `_withdraw(body, false, true)` runs with `beneficiary = attacker`, and the fee branch pays the full `100` fee tokens to the attacker [3](#0-2) .
4. Result: Solver A supplied 99.9% of the required output and receives 0 fee tokens; the attacker supplied 0.1% and receives the entire 100-fee-token payout.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }
