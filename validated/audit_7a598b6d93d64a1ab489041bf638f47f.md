## Title
Ambiguous, unanchored conflict-marker parsing lets attacker-crafted file content cause the Copilot AI merge-conflict resolver to silently discard legitimate code the user is about to commit - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
The Copilot-assisted "Resolve conflicts" feature extracts conflict hunks from a file twice, using two independently-written marker parsers that rely on bare, unanchored regexes (`/^={7}$/`, `/^<{7}(?:\s|$)/`, `/^>{7}(?:\s|$)/`) with no verification that a matched line was actually produced by Git as part of the current conflict. `extractConflictHunks` uses these regexes to split a hunk into `oursContent`/`theirsContent` and builds the "expected hunk count" used for validation; `reassembleResolvedFile` independently re-scans the raw file with the same ambiguous patterns to decide where to splice the model's resolution back in. Because the two scans can silently disagree about *where inside a hunk* the "ours"/"theirs" boundary falls (while still agreeing on the *number* of hunks), a repository file that is fully attacker/branch controlled can make the model see corrupted "ours"/"theirs" content and produce a resolution that quietly drops user code — with none of the existing validation (`validateResolutionPaths`) able to detect it, because it only checks hunk *counts*, never content alignment.

### Finding Description
`extractConflictHunks` in [1](#0-0)  defines the marker regexes as bare, content-agnostic patterns — a "separator" is any line consisting of exactly seven `=` characters and nothing else, with no requirement that it was genuinely emitted by Git for this conflict.

When collecting the "ours" side of a hunk, the parser breaks out of the loop the moment it sees a line matching the base or separator marker: [2](#0-1) 

If the *real* "ours" content of the conflict itself happens to contain a line that is exactly `=======` (a very ordinary thing to find in real files — Markdown/RST setext-style heading underlines, ASCII banners, changelog dividers, license text, etc.), the loop stops early there instead of at Git's real separator. The subsequent "theirs" collection loop only checks for the closing `>>>>>>>` marker and does **not** re-check for the separator: [3](#0-2) 

So everything from the coincidental fake separator through Git's *real* separator and the real "theirs" text gets merged into `theirsContent`, while `oursContent` is silently truncated. The hunk is still counted as exactly one hunk (`hunks.push(...)` at line 269), so `getHunkSkipReason` and the hunk-count contract used later remain unaffected.

Separately, `reassembleResolvedFile` in [4](#0-3)  re-scans the same raw file from scratch, using the same kind of bare marker regexes (`reassemblyOursMarker`, `reassemblySeparatorMarker`, `reassemblyTheirsMarker`, declared at [5](#0-4) ) to find the span from `<<<<<<<` to `>>>>>>>` and splice in the model's `resolvedContent` for that ordinal hunk index. It correctly identifies the whole `<<<<<<<...>>>>>>>` span as one block (so hunk *counts* agree with the extraction step), but it has no way to know that the model was shown a corrupted "ours"/"theirs" split for that block. It unconditionally replaces the entire block with whatever the model returned: [6](#0-5) 

`validateResolutionPaths` — the only integrity check performed on the model's output — verifies only file paths and per-file **hunk counts**, never that the model's understanding of hunk boundaries/content matches ground truth: [7](#0-6) 

This is structurally the same class of bug as the `ChainlinkUtil::getPrice` issue: a downstream consumer trusts a value (here, "the conflict is correctly split into ours/theirs and the reassembly boundary matches what the model reasoned about") that can silently drift out of its valid invariant (the true ours/theirs split) without any check, and the system keeps operating on the now-incorrect value instead of detecting the anomaly and failing safe.

### Impact Explanation
The corruption happens in the write path that produces the file content the user is about to `git add`/commit — i.e., silent corruption of what the user commits, one of the explicitly valid impact categories. A user resolving a real merge/rebase/cherry-pick conflict with Copilot could have a chunk of their own intended "ours" code re-classified as "theirs" input to the model and then have the model drop or rewrite it without any warning, error, or diff review flagging the discrepancy, because both the hunk-extraction and hunk-count validation still line up numerically. The victim sees only the final "resolved" file and a plausible-looking reasoning string; nothing in the pipeline signals that the boundary used was wrong.

### Likelihood Explanation
The trigger content — a bare line of exactly `=======` (or `<<<<<<<`/`>>>>>>>`) — is unremarkable and can appear in ordinary source, docs, or config files. It requires no special privileges: the attacker only needs to get such a line into the "ours" or "theirs" side of a real conflict, e.g. by authoring a branch/PR that a victim later merges/rebases against and then resolves with the Copilot conflict-resolution feature. No local access, no leaked credentials, and no unnatural user steps are needed beyond using the app's own "Resolve with Copilot" feature on an attacker-influenced branch.

### Recommendation
Do not treat the two independent marker scans as trustworthy on their own. Specifically:
- Have `reassembleResolvedFile` reuse the exact hunk boundaries (start/end line indices) computed once by `extractConflictHunks`, instead of re-deriving them from a second regex scan of the raw file.
- In `extractConflictHunks`, require the base/separator/theirs markers encountered while collecting "ours"/"base" content to be the *first* structurally valid occurrence relative to the already-open `<<<<<<<`, and reject/skip (mark `skippedReason`) any hunk where marker nesting looks ambiguous (e.g., a `=======`-looking line appears before any `>>>>>>>` has been found and the resulting split doesn't round-trip back to the original raw slice).
- Add a round-trip invariant check: after splitting a hunk into ours/base/theirs, reconstruct the original raw slice from the parsed pieces and the recognized markers, and fail closed (skip the file, fall back to manual resolution) if it does not match byte-for-byte — mirroring "revert unless the value is within the valid, verifiable range" from the Chainlink fix.

### Proof of Concept
1. Create a repository where a merge produces a conflict in `notes.md` such that the "ours" side contains legitimate content ending with a standalone divider line consisting of exactly `=======` (e.g., a Markdown setext H1 underline the user wrote intentionally), followed further down by Git's real `=======` separator and the "theirs" content, e.g.:
```
<<<<<<< HEAD
Section Title
=======
(regular markdown content that a human wrote as a divider, matches the separator regex)
This part of "ours" is real user code/content that should be preserved.
=======
incoming branch's replacement text
>>>>>>> feature-branch
```
2. Invoke the "Resolve with Copilot" flow. `extractConflictHunks` truncates `oursContent` at the first `=======`-looking line ("Section Title" divider) and folds everything after it — including the user's real trailing "ours" content, Git's true separator, and the real "theirs" text — into `theirsContent`.
3. The model, shown this corrupted split, produces a single-hunk resolution based on the wrong understanding of what "ours" vs "theirs" actually contain.
4. `validateResolutionPaths` passes because the file still reports exactly 1 expected hunk vs. 1 returned hunk.
5. `reassembleResolvedFile` splices the model's resolution over the entire real `<<<<<<<...>>>>>>>` span, silently discarding "This part of 'ours' is real user code/content that should be preserved." from the final committed file, with no warning to the user.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
