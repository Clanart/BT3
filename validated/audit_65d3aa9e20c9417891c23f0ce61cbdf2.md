### Title
Bitcoin fee rate derived from attacker-malleable on-chain median with no upper bound, enabling fee inflation and loss of funds - ([File: processor/src/networks/bitcoin.rs](processor/src/networks/bitcoin.rs))

### Summary
Analogous to `SwapPair::getSwapFee` computing a fee from mutable on-chain state (the DEX reserves' spot ratio) without an explicit bound, Serai's Bitcoin network adapter computes the fee rate it will pay as the **median fee rate of all transactions in the latest block** (`Bitcoin::median_fee`). An unprivileged party can broadcast Bitcoin transactions paying arbitrarily high fees, shifting that median upward between when a `Plan`/`SignableTransaction` is prepared and when the signed transaction is broadcast. The resulting overpaid fee is burned to miners (which the attacker may be), and is amortized across user payments, directly reducing what users receive — with no `max_fee`/slippage-style bound anywhere in the path.

### Finding Description
In `Bitcoin::median_fee`, the fee rate is computed by iterating `block.txdata[1 ..]` and pushing `(in_value - out) / tx.vsize()` for each transaction, then taking `fees[fees.len() / 2]`. Every fee sample comes from transactions any unprivileged party can include in a block — there is no filtering, no cross-block averaging (the code even has a `TODO` noting it should use "a fee representative of several blocks"), and no cap. [1](#0-0) 

`make_signable_transaction` then passes this `fee.0` into `SignableTransaction::new` as `fee_per_vbyte`, where the only check is a *lower* bound (`TooLowFee` when below relay minimum). There is no upper bound on `needed_fee = fee_per_vbyte * vbytes`, and the actual paid fee is `sum(inputs) - sum(outputs)`, absorbed by shrinking the change output and payments. [2](#0-1) [3](#0-2) 

Upstream, `prepare_send` calls `needed_fee` (which goes through `make_signable_transaction` → `median_fee`) and amortizes the computed `tx_fee` across the plan's payments, subtracting it from each `payment.balance.amount.0` — so the manipulated fee is taken directly out of user-facing amounts, not absorbed by the protocol. [4](#0-3) 

This mirrors the external report exactly: the cost charged to users is a function of chain state that an unprivileged actor can alter before the transaction is produced/included, and neither the signer nor the protocol commits to or bounds the acceptable fee range — identical to the missing "explicit check that fees are within an acceptable range" mitigation for `SwapPair`.

### Impact Explanation
- If the sampled block contains few transactions (common on low-activity periods, or a block the attacker can dominate — e.g., an attacker who is also a miner, or simply a moment when the mempool is thin), a single attack transaction paying, e.g., 50,000 sat/vbyte makes the median 50,000 sat/vbyte. Serai's transaction of ~n vbytes then pays `n * 50_000` sats of fee, far exceeding intent.
- The overage is silently deducted from user payments via fee amortization and/or the change output, so users receive less than intended — a concrete loss of funds, matching the "fee charged differs from what the user expected at signing time" impact class.
- A miner (or anyone able to place high-fee transactions in recent blocks) recoups most of the fee as mining reward, giving direct economic incentive, analogous to LP holders donating to reserves to force higher fees on benign swappers.

### Likelihood Explanation
- Reachability is purely public: the attacker only needs to send ordinary Bitcoin transactions (public inputs on the external chain), which is within the allowed threat model of untrusted inputs the system consumes.
- The median over a single block is trivially shifted when `txdata` is small; `fees.get(fees.len() / 2)` picks the attacker's sample directly if they supply the majority (or only) non-coinbase transaction.
- The only mitigating factor is cost: the attacker must actually pay the high fees on their own transaction unless they are a miner (who recovers them), so exploitation is most profitable for miner-attackers or brief low-fee windows. This makes it Medium rather than High — the same profile as the original swap-fee report.

### Recommendation
Add an explicit upper bound on the accepted fee, mirroring the report's mitigation of "a check that fees are within an acceptable range":
- Clamp or reject `median_fee` results above a configured maximum `max_fee_per_vbyte` in `Bitcoin::median_fee` / `make_signable_transaction`, and have `prepare_send` treat an out-of-range fee as an unfulfillable plan (retry on a later block) rather than amortizing it onto payments.
- Sample the median over multiple blocks (per the existing `TODO` at `make_signable_transaction`) instead of a single latest block, so a single attacker-dominated block cannot skew the estimate.
- Optionally have `SignableTransaction`/`prepare_send` accept an expected-fee tolerance and abort signing when `needed_fee` exceeds it.

### Proof of Concept
1. Serai's Bitcoin processor is about to construct a `SignableTransaction` for a pending `Plan`; it calls `self.get_block(block_number)` then `self.median_fee(&block)` (`processor/src/networks/bitcoin.rs` lines 430–431).
2. The attacker broadcasts a transaction paying 1,000,000 sats fee over ~200 vbytes (5,000 sat/vbyte) — or several such transactions — so it is included in that block's `txdata`.
3. `median_fee` pushes `5_000` into `fees`; with the attacker's transaction(s) at or past the median position, `Fee(5000)` is returned.
4. `BSignableTransaction::new` computes `needed_fee = 5000 * vbytes` (e.g., ~500 vbytes → 2,500,000 sats). The only guard, `TooLowFee`, passes; `NotEnoughFunds` passes since the multisig is well-funded.
5. `prepare_send` amortizes `tx_fee` across `payments`, subtracting it from `payment.balance.amount.0` — users receive ~2.5M sats less than intended; the excess goes to miners.
6. If the attacker mines the block containing Serai's transaction (or their own fee-inflation transactions), they recover the fee directly.

The asymmetry is the vulnerability: the signer computes the fee from `block.txdata` — data an unprivileged party fully controls — and the signed result is committed by `Prevouts::All`-style sighash semantics with no re-check of the fee magnitude before broadcast.

  async fn median_fee(&self, block: &Block) -> Result<Fee, NetworkError> {
    let mut fees = vec![];
    if block.txdata.len() > 1 {
      for tx in &block.txdata[1 ..] {
        let mut in_value = 0;
        for input in &tx.input {
          let mut input_tx = input.previous_output.txid.to_raw_hash().to_byte_array();
          input_tx.reverse();
          in_value += self
            .rpc
            .get_transaction(&input_tx)
            .await
            .map_err(|_| NetworkError::ConnectionError)?
            .output[usize::try_from(input.previous_output.vout).unwrap()]
          .value
          .to_sat();
        }
        let out = tx.output.iter().map(|output| output.value.to_sat()).sum::<u64>();
        fees.push((in_value - out) / u64::try_from(tx.vsize()).unwrap());
      }
    }
    fees.sort();
    let fee = fees.get(fees.len() / 2).copied().unwrap_or(0);

    // The DUST constant documentation notes a relay rule practically enforcing a
    // 1000 sat/kilo-vbyte minimum fee.
    Ok(Fee(fee.max(1)))
  }
