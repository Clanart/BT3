### Title
BIP-340 parity handling covers `R` but not the group key `A`, producing invalid signatures for odd-Y threshold keys — ([File: networks/bitcoin/src/crypto.rs])

### Summary
The MISP CVE-2020-8892 bug class is "a guard enumerated over variants but missed one" (brute-force protection checked some HTTP methods but not PUT). The same shape exists in bitcoin-serai's BIP-340 wrapper over modular-FROST Schnorr: the code handles the parity case for the nonce commitment `R` (negating the challenge and the final `s`), but never handles the parity case for the signing key `A`. Under BIP-340, verification uses the *even-Y* lift of the x-only public key. When `ThresholdView::group_key()` has an odd Y coordinate, every signature produced is valid only against the odd point `-P_even`, so it fails on-chain verification.

### Finding Description
In `Hram::hram` (crypto.rs:59–73), the challenge `c` is conditionally negated via `needs_negation(R)` so the nonce side conforms to BIP-340's implicit even-Y `R`. In `Schnorr::verify` (crypto.rs:145–149), `s` is conditionally negated via `needs_negation(&sig.R)`. Both adjustments only inspect `R`. `sign_share` (crypto.rs:128–136) delegates unmodified to `FrostSchnorr`, which computes `s_share = nonce + c·(share + offset)·λ` where `share` corresponds to the group key `A` as committed. `verify` then calls `self.0.verify(self.view.group_key(), &self.Rs, sum)` — the verification internally succeeds against `A`, but no code ever negates the secret share / effective key when `A` is odd. There is no `needs_negation(&group_key)` call anywhere; `needs_negation` is only applied to `R` (crypto.rs:72, 146).

For a BIP-340 verifier, the public key is `P = lift_x_even(x(A))`. If `A` is odd, `P = -A`, and a valid signature requires `s·G = R + c·(-A)`, i.e. the signer must use `-d`. Since the FROST shares sum to `d` with `d·G = A`, the emitted `s` satisfies `s·G = R_even + c·A` — a signature for the wrong public key.

### Impact Explanation
Approximately half of all generated threshold keys have odd Y. For any such key, every Bitcoin transaction signature the multisig produces will be rejected by Bitcoin consensus/BIP-340 verification. Outputs sent to the corresponding x-only address are unspendable — funds reported received are effectively burned. This matches the accepted impact class of funds that cannot be spent.

### Likelihood Explanation
Certain whenever `group_key()` is odd (~50% per key generation), unless an unexamined keygen step retries for even-Y keys (no such normalization is visible in `crypto.rs` or the FROST `sign`/`complete` path, where `view.group_key()` is used as-is at sign.rs:363, 465). An attacker is not required to trigger it; it is a correctness defect in the protocol mapping.

### Recommendation
Normalize the group key to even Y before signing: when `needs_negation(group_key)` is true, use `-(share + offset)` in `sign_share` (equivalently negate `s` at aggregation), consistent with how `R` parity is already handled. Alternatively, enforce an even-Y group key at DKG/key-aggregation time.

### Proof of Concept
1. Complete FROST DKG until `ThresholdKeys::group_key()` has odd Y (`needs_negation(&group_key) == 1`).
2. Run `AlgorithmSignMachine::sign` over any `msg`; `Hram::hram` negates `c` only for odd `R`, and `sign_share` uses the share for `A` unchanged.
3. `Schnorr::verify` returns a 64-byte signature after negating `s` for `R` parity only.
4. Verify against BIP-340 with `P = lift_x_even(x(A)) = -A`: `s·G = R + c·A ≠ R + c·P`, so verification fails on Bitcoin.

Caveat: I could not inspect the DKG/promotion path (crypto/dkg) in this session; if key aggregation already enforces or compensates for even-Y group keys, the defect is unreachable. The gap within `networks/bitcoin/src/crypto.rs` itself is unambiguous. [1](#0-0) [2](#0-1) [3](#0-2)
