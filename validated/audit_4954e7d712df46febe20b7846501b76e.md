## #Vulnerability found — Path Traversal via Malicious Commit Tree Paths in "Reveal/Open" File Sinks

### Title
Path Traversal writing/reading outside the repository via unsanitized committed file paths in `revealInFileManager` / external-editor / open-file sinks — (`File: app/src/lib/app-shell.ts`, `app/src/ui/app.tsx`, `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/ui/diff/binary-file.tsx`, `app/src/ui/lib/conflicts/unmerged-file.tsx`, `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`, `app/src/ui/changes/filter-changes-list.tsx`)

### Summary
GitHub Desktop already has a hardened, symlink-aware path-containment primitive, `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` in [1](#0-0) , which is correctly used to guard several newer sinks (e.g. the deep-link file opener in [2](#0-1)  and the Copilot conflict-resolution writer in [3](#0-2) / [4](#0-3) ). However, a large set of older sinks that turn a `file.path` (taken directly from git's raw diff/log/status output) into a filesystem path still do a bare `Path.join(repository.path, path)` with **no** traversal or symlink check — the exact `resolve-path`-style bug class from the report.

The attacker-controlled value is `CommittedFileChange.path`, produced in `parseRawLogWithNumstat` by taking the raw path token from `git log --raw` verbatim, with no rejection of `..` path components: [5](#0-4) . Since tree entries are single path components (no `/`), a component literally named `".."` is syntactically legal in a git tree object; git's *transfer-time* fsck checks (`fetch.fsckObjects`/`transfer.fsckObjects`) are off by default, so a malicious remote (a URL the user is asked to clone, or an "Open in Desktop" / PR flow pointing at a non-GitHub host) can deliver a commit whose tree contains such an entry into the local object database. Git's `checkout`-time `verify_path` protections don't apply here because Desktop never needs to check the branch out — it only needs to run `git log --raw`/`git diff --raw` to list `CommittedFileChange` for the History or "Files changed" (PR) views.

### Finding Description
1. **Attacker primitive**: attacker controls a git remote/repo the victim clones or fetches (explicitly in-scope per the report's Valid Impact list). They craft a commit whose tree contains an entry named `..` (or a chain of `..` entries), so a resulting diff/log path token looks like `../../../../Library/LaunchAgents/evil.plist` or `../../.ssh/authorized_keys`.
2. **Broken invariant**: `parseRawLogWithNumstat` trusts this string unconditionally and stores it in `CommittedFileChange.path`: [6](#0-5) .
3. **Unguarded sinks** — none of these call `resolveWithin`, they call `Path.join`/`join` directly, which does **not** clamp `..` segments back inside the root:
   - `revealInFileManager`: [7](#0-6) 
   - History "Reveal in Finder / Copy Path / Open in External Editor / Open with default program" context menu: [8](#0-7) 
   - "Files changed" tab of an open PR (same context menu pattern, attacker-controlled `head` branch of a PR the user hasn't checked out): [9](#0-8) 
   - Binary-file "Open in external program" for a committed file diff: [10](#0-9) 
   - Global "open in external editor" bridge from the changes list: [11](#0-10) 
   - Merge-conflict dialog editor launch and Copilot-conflicts overflow menu: [12](#0-11) , [13](#0-12) 
   - "Copy Path" clipboard action, which also leaks the resolved absolute out-of-repo path: [14](#0-13) 
   - `buildSubmoduleDiff`'s `fullPath` (submodule path is likewise attacker-controlled tree/`.gitmodules` data): [15](#0-14) 

Why existing guards don't help: `resolveWithin` exists in the same codebase and is proven effective against exactly this pattern (including symlink escapes, per its own tests: [16](#0-15) ), but it was only retrofitted onto the newer deep-link and Copilot-conflict code paths, not onto the much older history/PR/context-menu file-open code paths that predate it.

### Impact Explanation
Once `Path.join(repository.path, '../../.ssh/authorized_keys')` resolves outside the repo, `shell.showItemInFolder`/`electronShell.openPath`/spawning the user's external editor operate on a target outside the intended repo boundary. Depending on which context menu item the user clicks, this can:
- Reveal/open arbitrary files on the victim's disk in Finder/Explorer or the OS default handler (`OpenWithDefaultProgramLabel`), which for certain file types can lead to code execution (e.g., double-clicking a revealed `.desktop`/`.lnk`/executable, or the default handler auto-executing a scriptable file type).
- Launch the user's configured external editor pointed at a sensitive out-of-repo file, and via "Copy Path" leak the absolute out-of-repo path.
- In the Copilot-conflict resolution write path this is already fixed with `resolveWithin`, showing the project itself treats this as a real, high-severity class of bug — the remaining unguarded call sites are simply unpatched instances of the same defect.

This matches the CVE-2018-3732 primitive precisely: a join-based path resolver that fails to reject `..` traversal for attacker-supplied relative paths.

### Likelihood Explanation
Requires only that the victim clone/fetch/open (via "Open in Desktop"/PR flow) an attacker-controlled repository and then interact with the History view or an open PR's "Files changed" tab and right-click "Reveal in Finder" / "Open in External Editor" / "Copy Path" — no checkout of the malicious branch is required, and `git log --raw`/`git diff --raw` will happily print the crafted path since Desktop's own transfer step doesn't call `fetch.fsckObjects`/`transfer.fsckObjects` validation. This is a normal, expected user action for reviewing a fetched branch or PR, not an "unnatural" step.

### Recommendation
Route every `Path.join(repository.path, file.path)` / `join(repository.path, path)` call listed above through the existing `resolveWithin` helper (already used by `openRepositoryFromUrl` and `buildConflictContext`) and refuse to reveal/open/copy when it returns `null`. Additionally, consider rejecting `..` path components (and absolute paths) when parsing `CommittedFileChange`/`WorkingDirectoryFileChange` paths in `parseRawLogWithNumstat` and the status parser, so a malformed path never enters the app model at all.

### Proof of Concept
1. Attacker hosts a git repo (plain `git://`/`http://` remote, no GitHub-side push protections) containing a commit whose tree has, at the root, an entry literally named `..`, containing a further crafted entry, e.g. equivalent to creating a blob that `git log --raw` reports as path `../../../../tmp/pwned`.
2. Victim clones this repo in GitHub Desktop (`fetch.fsckObjects` is off by default, so the object is accepted) or opens a PR from it via the "Open in Desktop" deep link / PR review flow, without checking out the malicious branch.
3. Victim opens the commit in History (or the PR's "Files changed" tab) and right-clicks the file entry, choosing "Reveal in Finder" or "Open in External Editor".
4. `Path.join(repository.path, '../../../../tmp/pwned')` resolves to `/tmp/pwned`, outside the cloned repo, and Desktop calls `shell.showItemInFolder`/launches the editor on that out-of-repo path — reproducing the `resolve-path` "`C:../../`"-style escape from the original report inside GitHub Desktop.

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
