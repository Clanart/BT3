### Title
Reward double-counting via mutable `mWomSV.getUserTotalLocked` balance in `calDoubledCounted` - (File: wombat/ArbWomUp3.sol)

### Summary
`ArbWomUp3.getRewardAmount` (mode `_lock == true`, i.e., `_mode == 2`) computes the MGP reward for crossing tier brackets by subtracting `calDoubledCounted(_account)`, which is derived live from `mWomSV.getUserTotalLocked(_account)` instead of from a persisted, monotonically increasing record of rewards already paid. Because a user can reduce their `mWomSV` locked balance at any time (via the locker's unlock/withdraw flow) between separate `incentiveDeposit` calls, they can re-claim MGP rewards for tier brackets they were already paid for.

### Finding Description
`incentiveDeposit` with `_mode == 2` computes `rewardToSend` via `getRewardAmount(_amount, msg.sender, true)`: [1](#0-0) 

The "already rewarded" baseline is computed entirely from the current live value of `mWomSV.getUserTotalLocked(_account)`: [2](#0-1) 

The contract has a `bracketRewarded` mapping intended for exactly this purpose, but it is explicitly unused: [3](#0-2) 

Exploit flow:
1. Attacker calls `incentiveDeposit(amount1, _convertRatio, false, 2)`. This locks `amount1/2` worth of `mWom` into `mWomSV` via `_deposit` (`ILocker(mWomSV).lockFor(...)`) and pays out MGP reward for crossing tier(s) up to `mWomSV.getUserTotalLocked(attacker)`. [4](#0-3) 
2. In a separate transaction, the attacker calls `mWomSV`'s unlock/withdraw mechanism to reduce their locked balance back down (this is a normal, permissionless user action on the locker contract, outside `ArbWomUp3`'s control).
3. Attacker calls `incentiveDeposit` again with a new `amount2`. `getRewardAmount` recomputes `accumulated = amount2 + mWomSV.getUserTotalLocked(attacker)` using the now-reduced locked balance, and `calDoubledCounted` also uses that reduced balance, so it subtracts a smaller "already paid" amount than what was truly already paid in step 1. The tier bracket spanning the withdrawn portion gets rewarded again.

This is possible because there is no monotonic, contract-owned bookkeeping of cumulative rewards issued per user — the entire "double count correction" is re-derived from a balance the user fully controls and can lower at will by interacting with `mWomSV` directly (a call outside `ArbWomUp3`'s `nonReentrant` guard, so the guard does not prevent this cross-transaction manipulation).

### Impact Explanation
This allows an attacker to repeatedly re-claim MGP tier-bracket rewards by cycling lock/unlock on `mWomSV`, draining the MGP reward pool held by `ArbWomUp3` (funded via `vlMGP.lockFor`) beyond what should be paid for genuinely new locked WOM. This is a direct theft of protocol/reward funds (MGP intended for legitimate incentive recipients), matching a Critical/High direct-theft-of-funds impact, bounded by `mgpleft = IERC20(mgp).balanceOf(address(this))` at line 127-128, i.e., the attacker can drain up to the entire MGP balance held for incentives.

### Likelihood Explanation
The attack requires no privileged role, only: (1) enough WOM capital to make an initial deposit and cross a tier boundary, (2) calling `mWomSV`'s public unlock function (a normal user action, not restricted), and (3) repeating `incentiveDeposit`. This is fully repeatable per user and does not require flash loans or front-running, only capital reuse (lock → unlock → lock again). The `_convertRatio` framing in the question is a secondary detail (it affects how much of `_amount` goes through `SmartWomConvert.convert` vs. `mWomSV` deposit) but the core double-count exploit works independent of the exact `_convertRatio` value, as long as `_mode == 2` is used so `getRewardAmount`'s `_lock` branch and `calDoubledCounted` are invoked.

### Recommendation
Replace the live-balance-derived `calDoubledCounted` with a persisted, monotonically-increasing per-user accounting of rewards already paid (e.g., actually use the existing but dead `bracketRewarded` mapping, or track cumulative `mgpReward` paid per account), updated at the end of each successful `incentiveDeposit` call and never decreased. Reward calculations should be based on cumulative WOM ever committed through this contract, not on the user's currently-locked `mWomSV` balance, which the user can freely reduce.

### Proof of Concept
Hardhat test plan:
1. Deploy `ArbWomUp3`, `mWomSV` (or mock `ILocker` with `lockFor`/`getUserTotalLocked`/unlock functions), `mWOM`, `SmartWomConvert` mock, and MGP token; fund `ArbWomUp3` with MGP and set `rewardTier`/`rewardMultiplier` via `setMultiplier`.
2. Attacker calls `incentiveDeposit(amount1, 0, false, 2)` where `amount1` crosses tier index 1 threshold. Assert MGP reward paid (`vlMGP.lockFor` amount) equals expected tier-crossing reward and record `mWomSV.getUserTotalLocked(attacker)` = `L1`.
3. Attacker calls `mWomSV.startUnlock` (or equivalent) to reduce locked balance to `L2 < L1` (below the tier-1 threshold), then finalize unlock/withdraw.
4. Attacker calls `incentiveDeposit(amount2, 0, false, 2)` with `amount2` small enough that `amount2 + L2` again crosses the tier-1 threshold.
5. Assert: total MGP rewarded to attacker across steps 2 and 4 exceeds the reward that should be paid for `amount1 + amount2` total net new locked WOM as if step 3 never happened — i.e., the same tier bracket reward is paid twice, proving the double-count correction failed to persist state monotonically.
