### Title
BIP-340 `verify` accepts signatures against odd-Y group keys that Bitcoin will reject - (File: networks/bitcoin/src/crypto.rs)

### Summary
The Bitcoin FROST `Algorithm::verify` implementation verifies the completed Schnorr signature against the group key `A` as a full secp256k1 point, while `Hram::hram` commits only to the x-coordinates of `R` and `A`. If the group key has odd Y parity, the emitted 64-byte signature `(x(R), s)` is mathematically valid under Serai's internal verification (`sG == R + cA` with the odd-Y `A`) but is not a valid BIP-340 signature for the x-only (implicitly even-Y) key Bitcoin verifies against. No parity check or key negation is performed at verification or emission time.

### Finding Description
The external report's bug class — a documented security requirement that is never enforced at runtime — maps directly here. `crypto.rs` documents the `Schnorr` algorithm as "BIP-340 Schnorr signature algorithm" (line 76), yet nothing enforces BIP-340's key-parity requirement:

- `Hram::hram` (lines 59–73) hashes `x(R)` and `x(A)`, discarding the Y parity of both points. The challenge is therefore identical for `A` and `-A`.
- `Schnorr::verify` (lines 139–149) delegates to `FrostSchnorr::verify`, which computes `c = hram(R_sum, group_key, msg)` and checks `sG == R + c·group_key` with `group_key` used verbatim, then conditionally negates `s` only based on `needs_negation(&sig.R)` (line 146) — the nonce parity — and drops R's sign bit for serialization.

BIP-340 verification uses the even-Y lift of `x(A)`. Let `A_odd` be an odd-Y group key and `A_even = -A_odd`. Serai verifies `sG = R + c·A_odd = R - c·A_even`, while Bitcoin requires `sG = R' + c·A_even` with even-Y `R'`. Unless `c == 0`, the signature that Serai's `verify` returns `Some` for fails on-chain. There is no `needs_negation` check on the group key anywhere in this file, and no error path exists in `verify` to reject an odd-parity key.

The same asymmetry applies per-participant: `verify_share` (lines 152–159) checks shares against verification shares as-is, consistent internally but blind to the parity mismatch.

### Impact Explanation
When a DKG produces an odd-Y aggregate group key (≈50% probability absent upstream normalization), every FROST signing session `complete`s successfully, `verify` returns `Some([u8; 64])`, and the coordinator/processor treats the Bitcoin transaction as signed — yet the transaction is unbroadcastable because the taproot/BIP-340 signature check fails. Funds controlled by that key become unspendable until the issue is diagnosed; since shares were already consumed and shares are verified per-share as valid, blame attribution finds no malicious signer. This is "funds reported spendable/signed that are not spendable" — a concrete impact, not merely a sanity-check gap.

### Likelihood Explanation
Likelihood hinges on whether the group key passed to this algorithm is guaranteed even-Y by construction. Within the audited scope, `ThresholdKeys`/`ThresholdView` support a scalar offset (added to `included[0]`) which could be used to normalize parity, and `networks/bitcoin/src/wallet/mod.rs` references `needs_negation`/`x_only`, suggesting normalization may occur in wallet/tweak handling. I could not fully confirm whether the key fed to `Algorithm::verify` is always the normalized even-Y key. If normalization is only applied at output-address construction and not to the signing group key (e.g., odd internal key with the tweak applied on top, where the tweaked key parity is again random), the bug triggers with ~50% probability per key generation. Given the deterministic failure once triggered and no in-code guard, severity is at least Medium.

### Recommendation
In `Hram::hram` or `Schnorr::verify`/`sign_share`, normalize the effective key: compute `needs_negation(group_key)` and, when odd, either (a) require callers to supply the even-Y representative and use `ThresholdKeys` offset so shares correspond to `-A`, or (b) negate the challenge consistently with BIP-340 semantics (`c` computed against the even-Y lift, `s` adjusted for `R` parity as already done). Concretely: assert `group_key` has even Y in `verify`, or fold key parity into the secret-share/offset handling so that the verified statement `sG == R + c·A_even` matches what Bitcoin checks.
