### Title
Untrusted `ReceivedOutput` value is treated as the real UTXO amount - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` accepts an attacker-supplied `TxOut` containing an arbitrary `value`. `SignableTransaction::new` later uses that encoded value as the input’s actual spendable balance, without checking the referenced outpoint or its on-chain amount. A participant can therefore be induced to sign a Taproot transaction whose sighash commits to a fabricated prevout amount, producing a transaction Bitcoin consensus rejects.

### Finding Description
`ReceivedOutput::read` deserializes the scalar offset, complete `TxOut`, and `OutPoint` directly from untrusted bytes. It performs no verification that `outpoint` exists, that its script matches the offset-derived key, or that the encoded `value` equals the real UTXO value. [1](#0-0) 

`SignableTransaction::new` sums `input.output.value` to determine available funds and stores those attacker-controlled `TxOut`s as the prevouts. [2](#0-1) [3](#0-2) 

Before signing, `multisig` checks only that the supplied prevout’s `script_pubkey` equals the script for the offset group key; it does not validate the amount or existence of the referenced outpoint. [4](#0-3) 

Finally, signing uses `Prevouts::All`, meaning each BIP-341 signature commits to the attacker-supplied prevout amounts. If an amount differs from the actual UTXO, Bitcoin validators calculate a different sighash and reject the transaction. [5](#0-4) 

### Impact Explanation
An unprivileged party supplying a serialized `ReceivedOutput` can report an arbitrary Bitcoin amount for a real or nonexistent outpoint. This can bypass `NotEnoughFunds`, create a transaction with incorrect change or fees, and cause threshold participants to sign a transaction that cannot be broadcast successfully.

This is the Serai equivalent of accounting for the requested amount rather than the amount actually received: the deserialized `TxOut.value` is treated as authoritative even though it is merely attacker-controlled metadata until checked against the UTXO set.

### Likelihood Explanation
The issue is reachable wherever untrusted serialized `ReceivedOutput` data is accepted through `ReceivedOutput::read` and then passed to `SignableTransaction::new`. Exploitation only requires preserving or choosing a prevout script matching the expected key while changing its encoded amount, or referencing a nonexistent outpoint.

The practical result is an invalid spending transaction and disrupted signing, rather than direct theft, because the produced signatures cannot be reused against the actual prevout amount.

### Recommendation
Do not let deserialized `ReceivedOutput` values substitute for chain-verified UTXO data. Before constructing `SignableTransaction`, resolve every `outpoint` against a trusted Bitcoin view and require:

- the UTXO exists and is unspent;
- its `script_pubkey` matches the supplied `TxOut`;
- its actual amount exactly equals `TxOut.value`;
- the encoded offset derives the same output script.

Alternatively, deserialize only the `OutPoint` and scalar offset, then obtain the complete `TxOut` from a trusted chain source.

### Proof of Concept
Conceptually, an attacker creates a serialized `ReceivedOutput` for a controlled outpoint but encodes an inflated `TxOut.value`:

```rust
use bitcoin::{
  consensus::encode::serialize,
  Amount, OutPoint, TxOut,
};
use frost::curve::{Ciphersuite, Secp256k1};
use serai_bitcoin::wallet::{ReceivedOutput, SignableTransaction};

let claimed = ReceivedOutput {
  offset,
  output: TxOut {
    value: Amount::from_sat(real_amount * 100),
    script_pubkey: expected_script,
  },
  outpoint: real_outpoint,
};

let mut bytes = offset.to_bytes().to_vec();
bytes.extend(serialize(&claimed.output));
bytes.extend(serialize(&real_outpoint));

let forged = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
let signable = SignableTransaction::new(
  vec![forged],
  &payments,
  change,
  None,
  fee_per_vbyte,
).unwrap();
```

`SignableTransaction::new` accounts for `real_amount * 100` as available input. The generated signatures commit to that fabricated amount under `Prevouts::All`, so Bitcoin nodes reject the completed transaction when the actual UTXO contains only `real_amount`.
