### Title
Missing `\r` (carriage-return) escaping in `TextFormat.Printer` when `escapeNonAscii=false` breaks the string-escaping invariant, enabling desynchronization of line/record-oriented TextFormat consumers - (File: `java/core/src/main/java/com/google/protobuf/TextFormat.java`)

### Summary
The Apache CVE fails because backend response-header values containing unescaped `CR`/`LF` are forwarded verbatim, letting an attacker inject content that a downstream consumer interprets as additional protocol structure (HTTP desync/response splitting). The Protobuf analog is in Java `TextFormat.Printer.printFieldValue()`: when a `Printer` is configured with `escapingNonAscii(false)`, the `STRING` field case escapes only `\`, `"`, and `\n`, but **not** `\r` or other C0 control bytes, contradicting the API's own documented invariant that "the new Printer still escapes newlines and quotes in strings." Any consuming application that lets an attacker control a string field and serializes it with this non-default (but public) `Printer` configuration will embed a raw, unescaped `\r` byte into the generated TextFormat text.

### Finding Description
`TextFormat.Printer.printFieldValue()` has two escaping code paths for `STRING` fields: [1](#0-0) 

- When `escapeNonAscii == true` (the default), it calls `TextFormatEscaper.escapeText()`, whose `REPLACEMENT_CHARS` table escapes every byte in `0x00–0x1f` (including `\r` → `\\r`), plus `"`, `\`, etc.: [2](#0-1) 

- When `escapeNonAscii == false`, it instead calls `escapeDoubleQuotesAndBackslashes(value).replace("\n", "\\n")`. `escapeDoubleQuotesAndBackslashes` only replaces `\` and `"`: [3](#0-2) 

The manual `.replace("\n", "\\n")` patch covers line feed, but **no equivalent handling exists for `\r`, `\t`, `\0`, or any other control byte**. This is a documented invariant violation: the `escapingNonAscii(boolean)` javadoc explicitly claims "In either case, the new Printer still escapes newlines and quotes in strings," yet the code demonstrably fails to escape carriage return in the `false` branch: [4](#0-3) 

The failed invariant maps directly to the Apache bug class: an attacker-controlled value (string field content) is embedded into a structured text output without escaping a control character (`CR`) that downstream tooling commonly treats as a record/line delimiter — the same "missing check on injected control bytes into a structured stream" pattern as HTTP response splitting, just in the TextFormat serialization surface instead of HTTP headers.

### Impact Explanation
If an application accepts attacker-controlled string field values (a normal, trusted-schema scenario per the threat model) and serializes messages via `TextFormat.printer().escapingNonAscii(false)` — a supported public API — for logging, config generation, or transmission to another line/record-oriented system (e.g., syslog forwarders, `\r`-delimited log shippers, or naive line-based TextFormat parsers), the attacker can inject raw `\r` bytes that the consumer may interpret as a record boundary. This can desynchronize the record structure the consumer expects, similar in effect to how unescaped `CR`/`LF` in HTTP header values causes response splitting/desync in Apache. Because the escaped/unescaped forms are not semantically equivalent representations here (unlike the intentional XSS-safety escaping seen in JSON writers across the codebase, which is optional-but-harmless), this is a genuine correctness/security gap, though its severity is capped at Medium because exploitation depends on how a downstream consumer parses the TextFormat output — Protobuf itself has no public network endpoint.

### Likelihood Explanation
Likelihood is moderate: `escapingNonAscii(false)` is an explicitly supported, documented public configuration of `TextFormat.Printer` (not a hidden/internal API), and any application that stores/logs/transfers attacker-influenced string fields via TextFormat with this setting is directly exposed. It is not the default (`escapeNonAscii=true` is default), which reduces the likelihood, and TextFormat's own re-parser behavior for raw `\r` inside a quoted string literal (i.e., whether `TextFormat.Parser` correctly round-trips it) was not verified in this pass — this remains an open question that affects whether the impact is limited to "presentation-layer" desync in third-party consumers versus also affecting protobuf's own parser.

### Recommendation
In `TextFormat.java`, replace the ad hoc `escapeDoubleQuotesAndBackslashes(value).replace("\n", "\\n")` call in the `escapeNonAscii == false` branch with a helper that escapes all C0 control bytes (`\r`, `\t`, `\0`, etc.) in addition to `\`, `"`, and `\n`, matching the invariant already documented in the `escapingNonAscii()` javadoc and already implemented for the `escapeNonAscii == true` path via `TextFormatEscaper.escapeText`/`REPLACEMENT_CHARS`.

### Proof of Concept
```java
TestAllTypes msg = TestAllTypes.newBuilder()
    .setOptionalString("line1\rline2")
    .build();

String out = TextFormat.printer()
    .escapingNonAscii(false)
    .printToString(msg);
// out contains the literal, unescaped '\r' byte inside the quoted string,
// e.g.: optional_string: "line1\rline2"
//                              ^ raw CR byte, not "\\r"
```
Compare with the default printer, which correctly escapes it:
```java
String safe = TextFormat.printer().printToString(msg);
// optional_string: "line1\rline2"  -- here "\r" is the two-char escape sequence "\\r"
```
This confirms the escaping asymmetry between the two documented-equivalent code paths in [1](#0-0)  and [3](#0-2) .
