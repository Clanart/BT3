### Title
Unchecked payment/amount bounds allow u64 overflow in `SignableTransaction::new`, producing transactions that drain or burn multisig funds - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` validates payments only against a *lower* bound (`DUST`) and sums attacker-influenceable `u64` amounts with plain `sum::<u64>()` and `payment_sat + needed_fee` arithmetic. There is no upper bound equivalent to the report's `uint176`/`_MAX_REWARD_AMOUNT` cap — nothing constrains a payment or the sum of inputs/outputs to Bitcoin's real maximum (~2.1e15 satoshis). Values above the economically meaningful range pass validation and silently wrap the solvency check, so a transaction is constructed and signed that pays out more than the inputs contain, or whose true balance relation is miscalculated — the same "the checked bound is insufficient for the downstream computation" bug class as `FarmAccounting.startFarming`.

### Finding Description
The only per-payment bound is the dust floor:

```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
``` [1](#0-0) 

The solvency check then relies on unchecked wrapping arithmetic over those amounts:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
...
let payment_sat = payments.iter().map(|payment| payment.1).sum::<u64>();
...
if input_sat < (payment_sat + needed_fee) {
  Err(TransactionError::NotEnoughFunds { .. })?;
}
``` [2](#0-1) 

`sum::<u64>()` and `payment_sat + needed_fee` wrap on overflow in release builds. A payment of `u64::MAX` (or several large payments whose sum wraps) makes `payment_sat + needed_fee` wrap to a tiny value, so `input_sat < wrapped_total` is false and `NotEnoughFunds` is bypassed. The resulting `TxOut { value: Amount::from_sat(u64::MAX), .. }` is created unconditionally at line 190 — no check that the value is a valid Bitcoin amount or ≤ the inputs. The same wrap applies to `input_sat` if multiple `ReceivedOutput`s with large (crafted or misread) `TxOut.value`s are supplied via `ReceivedOutput::read` / consensus decode, which performs no sanity bound on `value` either. [3](#0-2) [4](#0-3) 

Downstream, `fee()` computes `sum(prevouts) - sum(outputs)`, which underflows/panics for such a transaction, and `create_output`-side amortization (`to_amortize = actual - expected`, `payment.balance.amount.0 -= subtractable`) assumes `expected ≤ actual`, again with raw u64 subtraction. [5](#0-4) [6](#0-5) 

Payments reaching `SignableTransaction::new` carry amounts decoded from untrusted chain data (`payment.balance.amount.0`, a `u64` `SubstrateAmount`), so the oversized value is reachable via public inputs; the processor only substitutes `DUST` when `calculating_fee` is set and otherwise passes the raw amount through. [7](#0-6) 

### Impact Explanation
A payment whose amount wraps the solvency check produces a signed transaction spending more than the multisig inputs hold — either an invalid transaction that permanently locks the input set (funds received/tracked but unspendable, since `fee()`/`actual - expected` arithmetic diverges from reality) or, where the wrap produces a small positive `payment_sat`, a transaction paying an incorrect amount and reporting a wrong fee/change split. Either way, accounting of participant funds is incorrect: the multisig can burn inputs as fees or strand outputs, directly mirroring the "participants receive less than they are owed" outcome of the FarmAccounting bug.

### Likelihood Explanation
Requires a large payment amount to reach the scheduler — amounts are `u64` fields supplied from external instructions — plus enough combined inputs or a wrapping sum such that the check passes. Not every deployment accepts arbitrary withdrawal magnitudes, and several paths panic (DoS) rather than mis-account, so likelihood is moderate but the bound-check gap is unconditional in the code.

### Recommendation
Impose an explicit upper bound analogous to `_MAX_REWARD_AMOUNT`: reject any payment `> MAX_MONEY`-style limit (e.g., `21_000_000 * 1e8` sats) and use `checked_add`/`checked_sum` for `input_sat`, `payment_sat`, `payment_sat + needed_fee`, and `fee()`, erroring on overflow instead of wrapping.
