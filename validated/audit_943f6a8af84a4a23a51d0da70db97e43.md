### Title
Forfeiture mechanism in `mWOMSVBaseRewarder._calExpireForfeit` never queries `mWomSV.getRewardablePercentWAD`, allowing 100% yield capture with near-zero lock time via `ArbitrumMWomAirdrop.claim(isLock=true)` - ([File: rewards/mWOMSVBaseRewarder.sol])

### Summary
`ArbitrumMWomAirdrop.claim(isLock=true)` routes vested mWOM directly into `mWomSV` via `ILocker.lockFor` [1](#0-0) . The reward contract that pays out `mWomSV` stakers, `mWOMSVBaseRewarder`, is supposed to forfeit reward proportional to a user's unlocked/short-held share via `getRewardablePercentWAD`, but its `_calExpireForfeit` function is a no-op that always returns zero forfeiture regardless of holding time [2](#0-1) . Combined with the airdrop's `lockFor` entry point, an attacker can lock, immediately `startUnlock`/`unlock` after the cooldown, and still receive their full pro-rata share of any reward accrued during that period with zero effective holding-time penalty.

### Finding Description
`ArbitrumMWomAirdrop.claim` with `isLock=true` approves and calls `locker.lockFor(claimable, msg.sender)` [1](#0-0) , which for the mWOM airdrop is `mWomSV.lockFor`, crediting the attacker's locked balance without any special restriction [3](#0-2) .

`mWomSV` implements `getRewardablePercentWAD(_user)`, which is explicitly designed to reduce the rewardable percentage for amounts that are in cooldown or recently unlocked, weighted by elapsed cooldown time [4](#0-3) . This function exists specifically to support proportional forfeiture of yield for users who don't hold their lock for very long.

However, `mWOMSVBaseRewarder` — the contract that actually pays reward tokens to `mWomSV` holders via `_sendReward` — computes forfeiture using `_calExpireForfeit`:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = _amount;
    if (rewardableAmount > _amount)
        revert InvalidRewardableAmount();
    uint256 forfeitAmount = _amount - rewardableAmount;
    ...
    return forfeitAmount;
}
``` [2](#0-1) 

This function assigns `rewardableAmount = _amount` directly instead of scaling it by `mWOMSV.getRewardablePercentWAD(_account)`. As a result, `forfeitAmount` is always `_amount - _amount = 0`, no matter how briefly the user held their `mWomSV` position or how quickly they cycle through lock → cooldown → unlock. The contract holds a reference to the locker (`ILocker public mWOMSV`) [5](#0-4)  but the getter is never invoked anywhere in the reward-payout path — grep across the contract confirms `getRewardablePercentWAD` is not called in `mWOMSVBaseRewarder.sol` at all.

Given this, an attacker can:
1. Call `ArbitrumMWomAirdrop.claim(totalAmount, proof, false, true)` to lock vested mWOM into `mWomSV` via `lockFor` [6](#0-5) .
2. Call `mWomSV.startUnlock(fullAmount)` to begin the cooldown [7](#0-6) .
3. Wait `coolDownInSecs`, then call `mWomSV.unlock(slotIndex)` [8](#0-7) , which internally triggers `multiclaimFor` and thus `mWOMSVBaseRewarder.getReward`/`getRewards` → `_sendReward`.
4. Because `_calExpireForfeit` never applies the intended `getRewardablePercentWAD`-based discount, `_sendReward` pays out the attacker's full accrued `userRewards` with zero forfeiture [9](#0-8) .

Existing guards (`whenNotPaused`, `nonReentrant`, merkle proof verification, `onlyMasterMagpie` on `getReward`) do not address this because the vulnerability is a logic bug in the forfeiture calculation itself, not an access-control or reentrancy gap.

### Impact Explanation
This is a theft of unclaimed/forfeitable yield: value intended to be redistributed to long-term stakers (via `_queueNewRewardsWithoutTransfer` when forfeiture > 0) is instead captured entirely by short-term lockers, including attackers who lock airdropped mWOM for only the minimum cooldown period. This matches the "theft of unclaimed yield that should be forfeited" Immunefi impact class. Note this bug is not unique to the airdrop path — any account that calls `mWomSV.lock`/`lockFor` directly and cycles through unlock is equally affected — the airdrop's `isLock=true` option is simply one (unprivileged, attacker-reachable) entry point into the same broken reward contract.

### Likelihood Explanation
High feasibility and full repeatability: the attacker needs only a valid merkle-proof allocation in `totalRewardMerkleRoot` (or, independent of the airdrop, any mWOM to lock directly) and to wait out `coolDownInSecs`. No privileged role, flash loan, or governance action is required, and the sequence can be repeated indefinitely by any allocated address (or any mWOM holder), each time capturing proportional reward-pool payouts that other long-term stakers would have otherwise received via forfeiture redistribution.

### Recommendation
Fix `_calExpireForfeit` in `rewards/mWOMSVBaseRewarder.sol` to actually scale by the locker's rewardable percentage, e.g.:
```solidity
function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
    uint256 rewardableAmount = (_amount * mWOMSV.getRewardablePercentWAD(_account)) / 1e18;
    uint256 forfeitAmount = _amount - rewardableAmount;
    if (forfeitAmount < (_amount / 1000)) {
        forfeitAmount = 0;
    }
    return forfeitAmount;
}
```
This mirrors the pattern that should exist analogous to `VLMGP`/`vlMGPBaseRewarder`, and would correctly apply forfeiture proportional to a user's short holding time before the `mWomSV` reward is paid out.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbitrumMWomAirdrop`, `mWomSV`, `mWOMSVBaseRewarder`, `MasterMagpie` with test configuration; set `startVestingTime` in the past.
2. Register attacker in `totalRewardMerkleRoot` with a `totalAmount`; fund the airdrop contract with `reward` (mWOM) tokens.
3. Have a "long-term" control staker lock mWOM directly into `mWomSV` and hold; queue a reward into `mWOMSVBaseRewarder` via `queueNewRewards`/`donateRewards` so `rewardPerTokenStored` increases while both attacker and control staker are staked.
4. Attacker calls `ArbitrumMWomAirdrop.claim(totalAmount, proof, false, true)` to lock the airdropped mWOM into `mWomSV`.
5. Attacker calls `mWomSV.startUnlock(fullAmount)`, warps `coolDownInSecs` forward, and calls `mWomSV.unlock(slotIndex)`.
6. Assert: reward token balance received by attacker (via the internal `multiclaimFor` call inside `unlock`) equals the full `earned()` amount computed from `rewardPerTokenStored * balance`, with **zero** deduction, despite `mWomSV.getRewardablePercentWAD(attacker)` returning a value less than `1e18` (i.e., predicting a nonzero forfeiture) at the time of `unlock`.
7. Compare against expected behavior: `toSend` in `_sendReward` should equal `userRewards - (userRewards * (1e18 - getRewardablePercentWAD)/1e18)`, but observed `toSend == userRewards` in all cases, confirming the forfeiture bypass.

    function _calExpireForfeit(address _account, uint256 _amount) internal view returns (uint256) {
        uint256 rewardableAmount = _amount;
        if (rewardableAmount > _amount)
            revert InvalidRewardableAmount();

        uint256 forfeitAmount = _amount - rewardableAmount;

            forfeitAmount = 0;
            rewardableAmount = _amount;

    function getRewardablePercentWAD(address _user) override public view returns(uint256 percent) {
        uint256 fullyInLock = getUserTotalLocked(_user);
        uint256 inCoolDown = getUserAmountInCoolDown(_user);
        uint256 userTotalmWomSV = fullyInLock + inCoolDown;
        if (userTotalmWomSV == 0)
            return 0;
        percent = fullyInLock * 1e18 / userTotalmWomSV;

        uint256 timeNow = block.timestamp;
        UserUnlocking[] storage userUnlocking = userUnlockings[_user];

        for (uint256 i; i < userUnlocking.length; i++) {
            if (userUnlocking[i].amountInCoolDown > 0) {
                if (block.timestamp > userUnlocking[i].endTime) {// fully unlocked 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 * (userUnlocking[i].endTime - userUnlocking[i].startTime)
                        / userTotalmWomSV / (timeNow - userUnlocking[i].startTime);
                }
                else {// still in cool down 
                    percent += userUnlocking[i].amountInCoolDown * 1e18 / userTotalmWomSV;
                }

            }
        }

        return percent;
    }
