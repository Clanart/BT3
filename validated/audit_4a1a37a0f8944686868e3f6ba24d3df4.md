### Title
CR-CAT `authorized_providers` Whitelist Trusts a Persistent DID Identity Whose Control Can Be Transferred, Enabling a Formerly-Trusted Provider to Turn Malicious - ([File: chia/wallet/vc_wallet/cr_cat_drivers.py])

### Summary
CR-CATs (credential-restricted CATs) gate spends on a static `authorized_providers` list of DID `launcher_id`s baked into the CAT coin at mint time [1](#0-0) . Authorization is proven at spend time solely by a puzzle announcement from whichever entity currently controls the inner puzzle of that DID (`provider_innerpuzhash`), not by any property that is fixed once the provider was vetted and whitelisted [2](#0-1) . Because DID singletons are ordinary transferable singletons, control of a whitelisted `launcher_id` can pass to a new owner (sale, compromise, or planned handoff) without the `authorized_providers` list ever being updated on any already-minted CR-CAT coin. This is the direct analog of "whitelisting a proxy": the identity checked (`launcher_id`) is stable, but the actual authority behind it (the DID's current inner puzzle / controller) can change arbitrarily, exactly like an upgradable proxy changing implementation while its address stays whitelisted.

### Finding Description
`construct_cr_layer` curries `authorized_providers` (a list of DID `launcher_id`s) and a `proofs_checker` into every CR-CAT coin, and this list is immutable for the life of that coin lineage [1](#0-0) . When a wallet wants to spend/approve a CR-CAT, it looks for a `VerifiedCredential` (VC) whose `proof_provider` is in that `authorized_providers` list [3](#0-2) , and the CRCATWallet performs the same provider-membership check when claiming pending balances [4](#0-3) .

The actual on-chain authorization, however, is not "the DID with this `launcher_id` is immutable/benign" — it is "whoever currently controls the DID's inner puzzle at the time of spend can sign off." The `magic_condition_for_new_proofs` / `activate_backdoor` mechanisms require only a `provider_innerpuzhash` and a matching announcement from that DID coin [2](#0-1) [5](#0-4) . A DID's inner puzzle (i.e. who controls it) can be transferred like any other singleton/DID ownership transfer, entirely independent of the `authorized_providers` list embedded in already-minted CR-CAT coins.

This means: at whitelist time the operator does due diligence on the entity holding `launcher_id`; but nothing in the protocol prevents that DID from being sold, handed off, or compromised afterward. The `launcher_id` — the thing actually checked by `CREDENTIAL_RESTRICTION` / `authorized_providers` — persists unchanged, while the "implementation" (who controls the DID and therefore who can mint proofs / authorize CR-CAT movement) can change freely, mirroring the report's proxy-upgrade class of bug: a whitelist entry that was safe when added can silently become malicious because the checked identity is stable but its controlling logic is not.

### Impact Explanation
Any CR-CAT asset that lists a given DID as an `authorized_provider` is permanently exposed to whoever eventually controls that DID's `launcher_id`, even if that party is unrelated to (or hostile to) the entity that was originally vetted. Once such a transfer happens, the new controller can:
- Issue proofs (`magic_condition_for_new_proofs`) that satisfy the `proofs_checker` for existing CR-CAT holders, effectively becoming the credential authority for that CAT.
- Approve/authorize CR-CAT spends via `check_for_final_modifications`/`add_vc_authorization` trade flows without holders' consent being re-validated against the new real-world identity [6](#0-5) .
- Potentially execute the backdoor/revocation path (`activate_backdoor`) to invalidate legitimate VCs, disrupting all wallets relying on that provider.

Since CR-CATs are specifically designed for regulated/permissioned assets (e.g., securities-like tokens), an unnoticed provider-DID handoff can silently convert what holders believe is a compliant, gatekept asset into one controlled by an unauthorized party — a supply/authorization-integrity issue for every CR-CAT that trusted that provider.

### Likelihood Explanation
Moderate. This requires a legitimate transfer or compromise of the provider DID's control (a normal DID-transfer operation, not a protocol bug), so it does not happen automatically, but nothing in the CR-CAT/VC code detects or prevents it, and no on-chain mechanism exists to update or revoke `authorized_providers` on already-minted CR-CATs once a provider DID changes hands. Given CR-CATs are explicitly built for long-lived regulated assets, provider organizations changing custodianship of their DID keys over time is a realistic operational event.

### Recommendation
- Document clearly (as the original report recommends for proxies) that `authorized_providers` entries must be DID singletons whose control is either non-transferable or is only ever transferred through a governed/notarized process, and that whitelisting a DID implicitly trusts all future controllers of that `launcher_id`.
- Consider adding a mechanism for CR-CAT issuers to rotate/deprecate `authorized_providers` on existing coins (e.g., via a TAIL-level circulating-supply reissuance path or a separate revocation registry) rather than baking the list permanently into the CAT's inner puzzle hash.
- For high-assurance deployments, recommend binding authorization to a covenant on the provider DID's transfer program (similar to the covenant/EML pattern already used for VC's own singleton lineage in `vc_drivers.py`) so that a provider DID cannot be transferred to an uncommitted transfer program without breaking the whitelist relationship.

### Proof of Concept
1. Operator O mints CR-CAT `X` with `authorized_providers = [D.launcher_id]`, where `D` is DID controlled by trusted org A (`construct_cr_layer`/`CRCAT.launch`) [7](#0-6) .
2. Wallets holding `X` accept VCs issued under provider `D.launcher_id` because it's in `authorized_providers`, verified via `get_vc_with_provider_in_and_proofs` [3](#0-2) .
3. Org A performs a standard DID ownership transfer of `D` to org B (a normal singleton spend changing D's inner puzzle) — `D.launcher_id` is unchanged.
4. Org B, now controlling `D`, issues a puzzle announcement using `magic_condition_for_new_proofs`/`activate_backdoor` with `provider_innerpuzhash` matching their new control of `D`, satisfying the exact same on-chain check CR-CAT `X` requires [2](#0-1) .
5. All existing CR-CAT `X` coins still list `D.launcher_id` as authorized, so org B's proofs/authorizations are accepted by every wallet and by `TradeManager.check_for_final_modifications` for offers involving `X` [6](#0-5)  — with no protocol-level signal that the provider's real-world controller has changed.

def construct_cr_layer(
    authorized_providers: list[bytes32],
    proofs_checker: Program,
    inner_puzzle: Program,
) -> Program:
    first_curry: Program = CREDENTIAL_RESTRICTION.curry(
        CREDENTIAL_STRUCT,
        authorized_providers,
        proofs_checker,
    )
    return first_curry.curry(first_curry.get_tree_hash(), inner_puzzle)

    def magic_condition_for_new_proofs(
        self,
        new_proof_hash: bytes32 | None,
        provider_innerpuzhash: bytes32,
        new_proof_provider: bytes32 | None = None,
    ) -> Program:
        """
        Returns the 'magic' condition that can update the metadata with a new proof hash. Returning this condition from
        the inner puzzle will require a corresponding announcement from the provider DID authorizing that proof hash
        change.
        """
        magic_condition: Program = Program.to(
            [
                -10,
                self.eml_lineage_proof.to_program(),
                [
                    Program.to(self.eml_lineage_proof.parent_proof_hash),
                    self.launcher_id,
                ],
                [
                    provider_innerpuzhash,
                    self.coin.name(),
                    Program.to(new_proof_hash),
                    None,  # TP update is not allowed because then the singleton will leave the VC protocol
                ],
            ]
        )
        return magic_condition

    async def get_vc_with_provider_in_and_proofs(
        self, authorized_providers: list[bytes32], proofs: list[str]
    ) -> VerifiedCredential:
        vc_records: list[VCRecord] = await self.store.get_vc_records_by_providers(authorized_providers)
        if len(vc_records) == 0:  # pragma: no cover
            raise ValueError(f"VCWallet has no VCs with providers in the following list: {authorized_providers}")
        else:
            for rec in vc_records:
                if rec.vc.proof_hash is None:
                    continue  # pragma: no cover
                vc_proofs: VCProofs | None = await self.store.get_proofs_for_root(rec.vc.proof_hash)
                if vc_proofs is None:
                    continue  # pragma: no cover
                if all(proof in vc_proofs.key_value_pairs for proof in proofs):
                    return rec.vc
        raise ValueError(f"No authorized VC has the correct proofs: {proofs}")  # pragma: no cover
