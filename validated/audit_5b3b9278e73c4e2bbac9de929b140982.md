## Analysis

The Forte finding's core defect is: **a size/precision decision is made using an incomplete signal (only the exponent, not the digit count), so a downstream computation returns a value larger/smaller than the mathematically correct one, and that wrong value is then used as ground truth for further arithmetic (multiplication).**

Searching Hyperbridge for the closest local analog to "wrong-sized intermediate value silently accepted and propagated to fund movement," the `IntrinsicIntents._fillSameChain` escrow-release fast path exhibits the same class of defect: it substitutes an aggregate/pooled value (`_orders[commitment][token]`) for a per-leg value it should have computed proportionally, whenever a "fully filled" shortcut condition is hit — mirroring how Float128's `toPackedFimport` substitutes the wrong-sized mantissa whenever a "boundary" condition is hit.

### Title
Escrow release keyed only by token address lets a solver drain the full pooled escrow by completing the cheapest leg of a multi-token order - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
In `_fillSameChain`, when a specific output leg `i` reaches `amountFilled == totalRequired`, the code takes the "full release" fast path and sets `escrowedAmount = _orders[commitment][order.inputs[i].token]` — the **entire remaining escrow balance stored for that token** — instead of the proportional share that belongs to leg `i`. `_orders` is keyed only by `(commitment, token)`, not by leg index, so if two entries in `order.inputs` share the same token address (backing two different output legs), completing the cheaper leg drains the whole pooled balance, including the portion that was meant to back the other, still-unfilled leg.

### Finding Description
`_fillSameChain` iterates per output asset index `i` and, for the completing fill of leg `i`, does: [1](#0-0) 

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
```

The `else` branch correctly computes a *proportional* release scoped to `order.inputs[i].amount`. But the `if` branch (meant to avoid leaving rounding dust for the last fill of a leg) instead reads the **current total balance stored under that token key** in `_orders`, via `_withdraw`: [2](#0-1) 

`_orders[commitment][token]` is a single running balance per `(commitment, token)` — it does not distinguish which input "slot"/leg it is backing. If `order.inputs` contains two entries with the same `token` (e.g., two input legs both denominated in USDC, backing two separate output legs such as a tiny DAI amount and a large WETH amount), then finishing the cheap leg first triggers the `if` branch and pulls **all** currently-escrowed USDC for that commitment — including the amount that should remain locked to pay out once the second (expensive) leg is filled.

The order is not marked fully filled in this scenario (`isFullyFilled` stays false because the other leg's `totalRequired > amountFilled`), so `_filled[commitment]` is deleted and the order remains open for a second solver — but the second output leg's backing escrow has already been paid out to the first solver.

### Impact Explanation
This is a direct loss-of-funds / wrong-beneficiary-and-amount bug against the user's escrow, reachable by any permissionless solver (no relayer, prover, or admin involvement): a solver can construct/target an order (or the user who wrote it, if crafted adversarially, or simply a coincidental token overlap in a multi-asset order) to claim the entire pooled escrow for a token by satisfying only the smallest leg denominated in that token, leaving the rest of the order's true intended payout obligation (to the destination beneficiary) unbacked by escrow. This is exactly the class of impact the bounty gate calls out: "stealing or loss of funds," "unauthorized transaction," "logic attacks."

### Likelihood Explanation
The path requires no privileged actor — only `placeOrder`/`fillOrder`, both public entrypoints. It requires an order whose `order.inputs` array contains two entries with the same token address (an EVM-side check on `placeOrder`/order construction for duplicate input tokens was not found in the retrieved code, though this could not be fully confirmed within available context — a background agent should verify whether `IntentsBase` or `IntentGatewayV2.placeOrder` rejects duplicate `inputs[].token` entries). If duplicates are not rejected, the exploit is straightforward and solver-only.

### Recommendation
Do not use the pooled `_orders[commitment][token]` balance as a proxy for "this leg's full remaining share." Track escrow per `(commitment, leg index)` (or equivalently, cap the "full release" fast path at `order.inputs[i].amount - alreadyReleased[i]` computed from a per-leg-tracked cumulative release, mirroring `_partialFills[commitment][outputToken]`), so that finishing one leg can never draw down escrow reserved for another leg sharing the same token.

### Proof of Concept
1. User places an order with `order.inputs = [ {USDC, 999}, {USDC, 1} ]` and `order.output.assets = [ {WETH, 500e18}, {DAI, 1} ]` (two legs, same input token USDC, second leg trivially cheap).
2. Solver calls `fillOrder` providing only `DAI: 1` for leg index 1. `alreadyFilled(DAI)==0`, `totalRequired==1`, `fillAmount==1`, so `amountFilled == totalRequired` → fast path triggers: `escrowedAmount = _orders[commitment][USDC]`, which equals the full `1000` USDC still escrowed (since leg 0/WETH hasn't been touched).
3. `_withdraw` sends the full 1000 USDC to the solver for providing 1 wei of DAI. `isFullyFilled` is false (WETH leg unfilled), so `_filled[commitment]` is cleared, order remains "open," but its USDC backing is now gone — the WETH leg can never be honestly paid out of escrow again.

This should be validated end-to-end in a Foundry test analogous to `testPartialFill_RoundingDustReleasedToFinalSolver` but with two input legs sharing a token address, confirming that `usdc.balanceOf(solver)` after step 2 equals the *entire* escrowed 1000 USDC rather than a leg-scoped 999 (or 0).

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
