## Finding

The DODO bug class — proportional split via floor division `total * weight / totalWeight` leaving a remainder that is either lost or breaks a strict downstream amount check — has a direct analog in Chia's NFT royalty-splitting logic used when building multi-NFT offers.

### Title
Floor-division rounding in multi-NFT royalty split can leave mojos unaccounted or mismatch on-chain royalty enforcement, risking offer settlement failure - (File: `chia/wallet/nft_wallet/nft_wallet.py`)

### Summary
When an offer or request includes more than one royalty-enabled NFT, `NFTWallet.make_nft1_offer` splits a single fungible payment amount across the multiple royalty-bearing NFTs using integer (floor) division, exactly mirroring the DODO `curTotalAmount * weight / totalWeight` pattern that drops remainder tokens.

### Finding Description
Two places divide a fungible amount by a "split count" without carrying forward the remainder:

1. When computing `trade_prices` for royalty-enabled NFTs being requested, the fungible amount is divided by `offer_side_royalty_split` (the number of royalty NFTs offered): [1](#0-0) 

2. When computing the actual royalty payment owed to each NFT's royalty address, `compute_royalty_amount` is invoked once per NFT with `request_side_royalty_split` as the divisor, again floor-dividing the total offered amount: [2](#0-1) 

3. The related static helper `royalty_calculation` performs the same pattern explicitly (`abs(amount) // len(royalty_assets_dict) * percentage // MAX_ROYALTY_BASIS_POINTS`), compounding two floor divisions: [3](#0-2) 

4. The core division primitive: [4](#0-3) 

Just as in the DODO report, when `amount` is not evenly divisible by the split count (`offer_side_royalty_split` / `request_side_royalty_split` / `len(royalty_assets_dict)`), the sum of the individually-rounded shares is strictly less than the true total. The royalty-transfer CLVM puzzle curried into each NFT's ownership layer (`NFT_TRANSFER_PROGRAM_DEFAULT`, referenced via `puzzle_for_transfer_program` in [5](#0-4) ) independently derives/enforces an expected royalty amount from the curried `percentage` and the trade price passed at spend time. Because the wallet-side split computation and the on-chain enforcement are performed independently — one via a single combined percentage/amount calculation, the other via a pre-split, floor-divided per-NFT amount — a mismatch of even 1 mojo between "what the wallet computed for this specific NFT" and "what the puzzle expects for this specific NFT" can occur whenever the total isn't evenly divisible by the NFT count.

### Impact Explanation
This affects any unprivileged offer counterparty/taker or maker who constructs or accepts an offer bundling multiple royalty-enabled NFTs against a single fungible asset (a supported, reachable flow via `NFTWallet.make_nft1_offer`, called from the wallet offer-creation RPC path). The consequences mirror the DODO report:
- Rounding-lost mojos: the sum of per-NFT royalty payments can be less than the "true" proportional total, silently underpaying royalty recipients by a small, dust-level amount per offer.
- Assertion mismatch risk: if the CLVM royalty-transfer puzzle's exact-amount check (driven by curried percentage and trade price) does not tolerate the wallet's independently-rounded per-NFT split, the spend can fail its on-chain condition check, causing the composed offer spend bundle to be rejected by mempool/consensus (a spend-triggered transaction-processing halt for that offer).

This is a Medium-severity issue: it is a genuine rounding-consistency defect in a reachable, unprivileged code path (offer maker/taker with multi-NFT offers), but its blast radius is limited to dust-level fund loss or reverted transactions for the specific offer, not systemic fund theft or consensus divergence.

### Likelihood Explanation
Likelihood is moderate: it requires an offer with multiple (`>1`) royalty-enabled NFTs bundled against fungible tokens where the total royalty-bearing amount is not evenly divisible by the NFT count — a realistic but not universal scenario for NFT bundle offers/collections trades.

### Recommendation
Replace the naive `amount // split_count` per-item computation with an accumulator-based approach: track the running total already allocated, and for the last item in the split, assign `remaining_amount = total_amount - already_allocated` instead of recomputing via division. This ensures the sum of all per-NFT royalty payments and trade prices exactly equals the intended total, eliminating both silent rounding losses and mismatches with the on-chain royalty transfer puzzle's exact-amount checks.

### Proof of Concept
1. Construct an offer requesting 3 royalty-enabled NFTs (`request_side_royalty_split = 3`) against an offered fungible amount of `100` mojos with a royalty percentage that does not evenly divide by 3 (e.g., percentage yielding `10` per split intended, but `100 // 3 = 33` per NFT, `33*3=99`, losing 1 mojo — see the floor division at [6](#0-5)  and per-NFT royalty compute loop at [7](#0-6) ).
2. Observe that `sum(extra_royalty_amount for each NFT)` is less than the mathematically exact proportional total, and that if the corresponding on-chain royalty-transfer puzzle solution strictly requires the "exact" computed amount, the offer settlement spend can fail its condition check.

def compute_royalty_amount(offered_amount: int, royalty_split: int, percentage: int) -> uint64:

                        "address": address,

                    }
                )

        return summary_dict
