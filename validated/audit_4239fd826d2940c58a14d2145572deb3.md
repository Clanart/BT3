### Title
Hard 8000-character truncation of `diff_text` in `build_refute_prompt` lets an attacker-sized diff hide the vulnerable `+` lines from the self-refute pass, causing real findings to be REFUTEd as "pre-existing" - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` slices the already-capped diff text to only the first 8000 characters (`diff_text[:8000]`) before handing it to the adversarial self-refute model, while the earlier investigate stage and the per-file/global diff caps (`DIFF_PER_FILE_BYTES`=80000, `DIFF_TOTAL_BYTES`=400000) allow far larger diffs to be reviewed. Any diff whose vulnerable `+` lines land after byte 8000 of the assembled `diff_text` becomes invisible to the refute model, which is explicitly instructed to REFUTE a candidate when its `vulnerableCode` "does NOT appear on any + line in the DIFF block above."

### Finding Description
`build_refute_prompt(candidates, diff_text)` in [1](#0-0)  builds the stage-2 prompt as:
```
"...\n\nDIFF:\n" + diff_text[:8000]
```
This truncation is independent of, and far smaller than, the caps applied when the diff was first assembled for the investigate stage — `cap_diff_for_prompt` permits up to `DIFF_PER_FILE_BYTES` (80000) per file and `DIFF_TOTAL_BYTES` (400000) total [2](#0-1) . The identical pattern (`diff_text[:8000]`) is duplicated in the in-process agentic pipeline in `llm.py`'s `agentic_review` self-refute branch [3](#0-2) .

The refute prompt then instructs the model to REFUTE a candidate under the rule:
```
"- PRE-EXISTING: the cited vulnerableCode does NOT appear on any + line in the DIFF block above — it is unchanged context in a touched file. The diff did not introduce it."
``` [4](#0-3) 

Because the "DIFF block above" is silently cut off at 8000 characters, an attacker who authors a diff whose total assembled text (across all touched files, in file order) exceeds 8000 characters before the actual dangerous `+` line can push that line outside the visible window. The stage-1 investigate pass (which sees the full, much larger diff) still correctly flags the vulnerability as a candidate, but stage-2 self-refute — looking at the truncated `diff_text[:8000]` — cannot find the cited `vulnerableCode` on any visible `+` line, satisfies its own PRE-EXISTING rule, and REFUTEs the finding. The candidate is then dropped from `survived` [5](#0-4) , i.e., the real vulnerability never surfaces to the developer/reviewer.

No unprivileged-attacker assumption is violated: any contributor whose diff is fed through the agentic review pipeline (Stop hook / commit reviewer) fully controls the diff's file ordering and total size, and 8000 characters is trivially exceeded by an ordinary multi-file diff or even a single file with modest boilerplate preceding the injected vulnerability. There is no allowlist, position-aware anchoring, or "vulnerable file first" prioritization protecting the refute-stage window from this truncation.

### Impact Explanation
This breaks the stated invariant that "prompt assembly must not let untrusted repo content suppress review of dangerous changes." The self-refute stage is the last gate before a finding is surfaced; silently dropping a correctly-identified critical/high finding because of an unrelated truncation bug in prompt construction is a logic-level bypass of a required security guard, matching the "Logic-level service disruption caused by bypassing a required guard" impact category — a genuinely dangerous change can pass the automated security review undetected simply because of diff size/ordering, not because of any legitimate risk assessment.

### Likelihood Explanation
Highly feasible and repeatable: no special privilege is needed beyond authoring a normal commit/diff reviewed by the plugin. The only precondition is that the assembled `diff_text` exceeds 8000 characters before the vulnerable `+` line — a condition met by many real-world PRs/diffs (multiple touched files, or one file with sufficient preceding content), independent of the much larger `DIFF_PER_FILE_BYTES`/`DIFF_TOTAL_BYTES` caps that were presumably intended to bound what the reviewer can see. This is fully deterministic and reproducible via a unit test on `build_refute_prompt`.

### Recommendation
Do not apply a flat `[:8000]` slice to the full assembled diff in the refute prompt. Instead:
- Truncate per-candidate: include only the diff hunks/files relevant to the current batch of candidates (their `filePath`s), guaranteeing each candidate's cited `vulnerableCode` region is preserved.
- If a global cap is still desired, apply it consistently with `cap_diff_for_prompt`'s caps (or make it configurable/large enough), and if truncation is unavoidable, insert an explicit truncation marker and re-order so that files referenced by `candidates` appear first / are never dropped.
- Add a fast invariant test asserting that for every candidate's `filePath`, the corresponding diff hunk remains present in the string returned by `build_refute_prompt` regardless of overall diff size.

### Proof of Concept
Unit test against `build_refute_prompt` in `plugins/security-guidance/hooks/review_api.py`:
```python
def test_refute_prompt_preserves_vulnerable_diff_after_truncation():
    # Simulate several harmless "decoy" files pushing the real
    # vulnerable line past the 8000-char cutoff.
    decoy = "\n".join(f"+ line {i} of harmless padding" for i in range(400))  # ~10k chars
    vulnerable_line = "+ os.system(user_input)  # command injection"
    diff_text = (
        "=== DIFF: decoy1.py ===\n" + decoy + "\n\n"
        "=== DIFF: real_target.py ===\n" + vulnerable_line
    )
    candidates = [{
        "filePath": "real_target.py",
        "category": "Command Injection",
        "vulnerableCode": "os.system(user_input)",
        "explanation": "...", "fix": "...", "severity": "critical",
    }]

    prompt = build_refute_prompt(candidates, diff_text)

    # Expected (fails today): the vulnerable + line must still be visible
    # in the DIFF block sent to the refute model.
    assert "os.system(user_input)" in prompt.split("DIFF:\n", 1)[1]
```
Expected result today: the assertion fails because `diff_text[:8000]` cuts off before `real_target.py`'s section, demonstrating that the refute model would never see the injected vulnerability and would REFUTE it as PRE-EXISTING/absent, confirming the bypass.

DIFF_TOTAL_BYTES = int(os.environ.get("DIFF_TOTAL_BYTES", "400000"))


def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```
