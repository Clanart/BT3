## Title
Unauthenticated `Withdraw`/`OptimisticPayout` calls on the Aggregator gRPC service can trigger operator payouts and N-of-N signing without any caller authentication - (File: `core/src/servers.rs`, `core/src/rpc/aggregator.rs`)

### Summary
The aggregator's gRPC server explicitly does not enforce client TLS certificates, unlike the operator/verifier servers which restrict callers to the aggregator's certificate or the entity's own certificate. This means any network-reachable, unauthenticated party can invoke the aggregator's state-changing/broadcasting RPCs (`Withdraw`, `OptimisticPayout`, `SendMoveToVaultTx`, `NewDeposit`, etc.) directly, playing the role normally reserved for the trusted `clementine-backend` service.

### Finding Description
Per `docs/usage.md:192-203`: "Clementine uses mutual TLS (mTLS) to secure gRPC communications... Verifier/Operator methods can only be called by the aggregator... The aggregator does not enforce client certificates but does use TLS for encryption." [1](#0-0) 

This is corroborated in code by the interceptor logic in `core/src/rpc/interceptors.rs:22-77`, which is only wired up for operator/verifier servers via `Interceptors::OnlyAggregatorAndSelf` (checking that the caller's leaf certificate matches either the aggregator's or the entity's own cert) [2](#0-1) . The aggregator server (`create_aggregator_grpc_server`, not shown in the excerpt but part of `core/src/servers.rs`) is not shown applying an equivalent restriction — the config comment for `client_verification`/`aggregator_cert_path` and the TLS server setup in `core/src/servers.rs:79-178` describes cert-based restriction only from the operator/verifier side, and the docs explicitly state the aggregator "does not enforce client certificates."

This matches the bug-class hint from the external report: a state-changing/signing entry point (`DualVmToken.approve`) is reachable by a party other than the one it is meant for, because no check restricts the caller. Here, the analog is the aggregator's `Withdraw`/`OptimisticPayout`/`SendMoveToVaultTx` RPCs (`core/src/rpc/aggregator.rs:1010-1250`, `1973-2096`), which are meant to be called only by the trusted `clementine-backend` orchestration service (per proto comments: "Used by the clementine-backend service to initiate a withdrawal" at `core/src/rpc/clementine.proto:767-773`), but any TCP/TLS client can reach them because the aggregator's gRPC layer has no client-certificate gate.

### Impact Explanation
Reaching these endpoints as an unprivileged, non-mTLS-authenticated party does trigger real state-changing behavior on the aggregator (nonce aggregation rounds with verifiers, dispatch of withdrawal requests to operators, insertion of transactions into `tx_sender` for broadcasting, e.g. `core/src/rpc/aggregator.rs:2075-2096`). While the deeper protocol checks (user Schnorr signature over the withdrawal UTXO, matching against Citrea-registered withdrawal data, and the optional `aggregator_verification_address` ECDSA check) still gate the ultimate fund movement, the RPC surface itself is unauthenticated — matching the "High" impact bucket definition given in the rules ("an unauthenticated state-changing or broadcasting call"). This lets an unprivileged caller directly drive verifier nonce-generation/signing rounds and operator dispatch cycles that are meant to be gated by the backend orchestrator, without needing any credential.

### Likelihood Explanation
High: this requires no key, certificate, or privileged role — only network reachability to the aggregator's gRPC port, which is explicitly documented and coded to skip client-certificate verification. No misconfiguration is needed; this is the aggregator's intended/documented behavior ("The aggregator does not enforce client certificates").

### Recommendation
Apply an authentication gate (e.g., an API key, request signing, or IP allowlisting) in front of the aggregator's public gRPC surface so that only the trusted `clementine-backend` service (or otherwise authorized callers) can invoke state-changing/broadcasting RPCs such as `Withdraw`, `OptimisticPayout`, `NewDeposit`, and `SendMoveToVaultTx`.

### Proof of Concept
Any TLS client (no client certificate required, since the aggregator config doesn't enforce `client_verification`-style checks the way operator/verifier servers do) can connect to the aggregator's exposed port and call `ClementineAggregator/OptimisticPayout` or `ClementineAggregator/Withdraw` with attacker-supplied `WithdrawParams`, driving the aggregator to fan out nonce-generation/signing requests to verifiers and dispatch requests to operators — reachable purely as an unauthenticated caller, unlike the operator/verifier RPCs which reject non-aggregator/non-self certificates per `core/src/rpc/interceptors.rs:62-76` and `core/src/test/rpc_auth.rs:97-101` (test showing the aggregator's own client cert is rejected by the operator on `internal_end_round`, illustrating how strict operator/verifier auth is — in contrast to the aggregator, which enforces none of this). use tonic::{service::Interceptor, transport::CertificateDer, Request, Status};

#[derive(Debug, Clone)]
pub enum Interceptors {
    OnlyAggregatorAndSelf {
        aggregator_cert: CertificateDer<'static>,
        our_cert: CertificateDer<'static>,
    },
    Noop,
}

fn is_internal(req: &Request<()>) -> bool {
    // This normally doesn't exist but we add it in the AddMethodMiddleware
    let Some(path) = req.metadata().get("grpc-method") else {
        // No grpc method? this should not happen
        tracing::error!("Missing grpc-method header in request");
        return false;
    };
    path.as_bytes().starts_with(b"Internal")
}

impl Interceptor for Interceptors {
    #[allow(clippy::result_large_err)]
    fn call(&mut self, req: Request<()>) -> Result<Request<()>, Status> {
        match self {
            Interceptors::OnlyAggregatorAndSelf {
                our_cert,
                aggregator_cert,
            } => only_aggregator_and_self(req, our_cert, aggregator_cert),
            Interceptors::Noop => Ok(req),
        }
    }
}

#[allow(clippy::result_large_err)]
fn only_aggregator_and_self(
    req: Request<()>,
    our_cert: &CertificateDer<'static>,
    aggregator_cert: &CertificateDer<'static>,
) -> Result<Request<()>, Status> {
    let Some(peer_certs) = req.peer_certs() else {
        if cfg!(test) {
            // Test mode, we don't need to verify peer certificates
            return Ok(req);
        } else {
            // If we're not in test mode, we need to check peer certificates
            return Err(Status::unauthenticated(
                "Failed to verify peer certificate, is TLS enabled?",
            ));
        }
    };

    // IMPORTANT: Only check the leaf (end-entity) certificate, which is always the first
    // certificate in the chain. The leaf is the only certificate whose private key the peer
    // proved possession of during the TLS handshake. Checking anywhere else in the chain
    // would allow identity spoofing: an attacker could include a pinned cert as an
    // intermediate in their chain without possessing its private key.
    let Some(leaf_cert) = peer_certs.first() else {
        return Err(Status::unauthenticated("Peer certificate chain is empty"));
    };

    if is_internal(&req) {
        if leaf_cert == our_cert {
            Ok(req)
        } else {
            Err(Status::unauthenticated(
                "Unauthorized call to internal method (not self)",
            ))
        }
    } else if leaf_cert == aggregator_cert || leaf_cert == our_cert {
        Ok(req)
    } else {
        Err(Status::unauthenticated(
            "Unauthorized call to method (not aggregator or self)",
        ))
    }
}
