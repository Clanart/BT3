## Title
`WombatStaking.depositLP` mints receipt tokens and stakes based on the input amount instead of the actual LP amount received, causing accounting insolvency for fee-on-transfer/deflationary LP tokens - (File: `wombat/WombatStaking.sol`)

### Summary
`WombatStaking.depositLP()` transfers LP tokens from the user with `safeTransferFrom(_for, address(this), _lpAmount)` and then immediately stakes `_lpAmount` to Master Wombat and mints `_lpAmount` of the pool's receipt token to the caller, without ever measuring what amount was actually received. This is inconsistent with the sibling `deposit()` function in the same contract, which correctly measures the actual LP received via a before/after balance diff (`lpReceived`) before staking and minting.

### Finding Description
In `wombat/WombatStaking.sol`, `deposit()` correctly guards against amount mismatches: [1](#0-0) 
```
IERC20(depositToken).safeApprove(poolInfo.depositTarget, _amount);
uint256 beforeBalance = IERC20(poolInfo.lpAddress).balanceOf(address(this));
IWombatPool(poolInfo.depositTarget).deposit(...);
uint256 lpReceived = IERC20(poolInfo.lpAddress).balanceOf(address(this)) - beforeBalance;
_toMasterWomAndSendReward(_lpAddress, lpReceived, true);
IMintableERC20(poolInfo.receiptToken).mint(msg.sender, lpReceived);
```
However, `depositLP()` does not follow the same pattern and instead trusts the caller-specified `_lpAmount` directly: [2](#0-1) 

The `_lpAmount` is used both to stake into Master Wombat (via `_toMasterWomAndSendReward` → `_stakeToWombatMaster`, which calls `IERC20(_lpToken).safeApprove(masterWombat, _lpAmount)` and `IMasterWombat(masterWombat).deposit(poolInfo.pid, _lpAmount)`) and to mint the receipt token 1:1 to the user: [3](#0-2) 

If the underlying `poolInfo.lpAddress` token has a transfer fee, is deflationary, or is otherwise non-standard (actual received amount < `_lpAmount`), `WombatStaking` will not actually hold enough LP tokens to satisfy the subsequent stake call, and will still mint the full `_lpAmount` of receipt tokens to the depositor. This mirrors the root cause of the referenced report: an amount used for downstream custody/redemption accounting is assumed equal to the requested/transferred amount instead of the amount actually received, without a check that would catch a shortfall.

### Impact Explanation
If the actual LP tokens received are less than `_lpAmount`:
- The Master Wombat deposit call may revert due to insufficient balance in the contract, permanently blocking `depositLP` (and by extension, the associated pool helper's `depositLP` path) for that LP token.
- If it doesn't revert (e.g., is not fully validated upstream), the receipt token supply outstanding for that pool becomes permanently larger than the actual LP custodied and staked in Master Wombat. Since receipt tokens represent a 1:1 claim redeemable via `WombatPoolHelper.withdraw` → `WombatStaking.withdraw` → `burnReceiptToken`, this creates a shortfall where not all receipt-token holders can be made whole — a direct protocol insolvency for that pool's depositors.

### Likelihood Explanation
Reachable by any ordinary wallet calling `WombatPoolHelper.depositLP()` / `WombatPoolHelperV2.depositLP()`, which directly forwards to `WombatStaking.depositLP()`: [4](#0-3) 
No privileged role is required to trigger the vulnerable code path — likelihood depends only on whether a registered pool's LP token exhibits fee-on-transfer/deflationary behavior, which is plausible for LP tokens wrapping fee-on-transfer underlying assets in the Wombat ecosystem.

### Recommendation
Mirror the pattern already used in `deposit()`: measure the actual LP balance received via a before/after diff in `depositLP()`, and use that measured amount (not the caller-supplied `_lpAmount`) for both `_toMasterWomAndSendReward`/staking and for the receipt-token `mint` call.

### Proof of Concept
1. A pool is registered in `WombatStaking` whose `lpAddress` token charges a transfer fee (e.g., 1%) on `transferFrom`.
2. A user calls `WombatPoolHelper.depositLP(1000)`, which calls `WombatStaking.depositLP(lpToken, 1000, user)`.
3. `safeTransferFrom(_for, address(this), 1000)` results in `WombatStaking` actually receiving only 990 tokens due to the fee.
4. `_toMasterWomAndSendReward(_lpAddress, 1000, true)` → `_stakeToWombatMaster` attempts to approve and deposit 1000 tokens to Master Wombat while only 990 are held, either reverting (DoS) or, depending on Master Wombat's transfer semantics, resulting in a shortfall.
5. `IMintableERC20(poolInfo.receiptToken).mint(msg.sender, 1000)` mints receipt tokens for the full 1000 regardless, over-representing the LP actually custodied/staked, so the sum of receipt tokens exceeds the LP recoverable on withdrawal. [2](#0-1)
