### Title
Payout tx malleability via SIGHASH_SINGLE|ANYONECANPAY lets an attacker inject a forged first OP_RETURN, breaking `deposit_constant`'s operator binding - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
`create_payout_txhandler` signs the withdrawal input of `payout_tx` with `SinglePlusAnyoneCanPay`, which only commits to input 0 and output 0 [1](#0-0) [2](#0-1) . Because of this, anyone who observes the operator's broadcast (or unsigned/pre-broadcast) payout transaction can rebroadcast a malleated variant that adds extra inputs/outputs — including an extra OP_RETURN placed before the operator's real OP_RETURN — while the SinglePlusAnyoneCanPay signature remains valid. `bridge_circuit` and `update_finalized_payouts` both derive the operator identity by taking only the *first* OP_RETURN found via `get_first_op_return_output` [3](#0-2) , so if the malleated (attacker-modified) version of the transaction is the one that actually confirms, `deposit_constant`/the DB-recorded "payer" pubkey will bind to the attacker's forged key instead of the real funding operator's key.

### Finding Description
The binding claimed by the protocol is:
`deposit_constant.operator_xonlypk == xonly_pk of the operator whose wallet funded payout_tx's input`.

`bridge_circuit` computes this via:
```
let first_op_return_output = get_first_op_return_output(&input.payout_spv.transaction)...
let operator_xonlypk = parse_op_return_data(&first_op_return_output.script_pubkey)...
let deposit_constant = deposit_constant(operator_xonlypk, ...);
``` [4](#0-3) 

`get_first_op_return_output` only returns the first OP_RETURN match: [3](#0-2) 

Crucially, `bridge_circuit` never verifies the payout_tx's own witness/signature for the withdrawal input — it only checks that the SPV-included transaction's input `previous_output` matches the txid/vout coming from the storage proof [5](#0-4) . So whatever transaction actually gets confirmed spending that specific outpoint is accepted as "the" payout tx, and its first OP_RETURN is trusted blindly.

The operator-side construction of `payout_tx` always emits exactly one OP_RETURN with the real operator's key, and signs the withdrawal input with `SIGHASH_SINGLE|SIGHASH_ANYONECANPAY`: [6](#0-5) 

That sighash type only commits to input index 0 and output index 0 of the final transaction; it does **not** fix the set/order of other inputs or outputs. This is exactly why the withdrawal-signing helper in the test suite uses `SinglePlusAnyoneCanPay` [7](#0-6) . Because the attacker (per the threat model) can choose/observe the withdrawal UTXO and the signature/sighash flag, and can broadcast Bitcoin transactions, they can take the operator's broadcast-but-unconfirmed payout tx (visible in the mempool, or, since they hold or can reconstruct a valid SIGHASH_SINGLE|ANYONECANPAY witness for output 0) and rebroadcast a modified version that:
- keeps input 0 → output 0 unchanged (satisfying the committed sighash),
- adds an extra OP_RETURN output *before* the operator's real OP_RETURN output (e.g. containing a forged/victim operator's xonly_pk), and
- optionally adds extra fee-paying inputs (permitted by ANYONECANPAY) to win the race to confirmation.

If this variant is the one that gets mined, both `get_first_op_return_output` call sites — inside `bridge_circuit`'s `deposit_constant` computation and inside `update_finalized_payouts`, which persists the "payer" operator pubkey to the DB — pick the attacker's forged OP_RETURN instead of the real one [8](#0-7) . The real funding operator, when later submitting a kickoff to claim reimbursement, will fail `is_kickoff_malicious`'s cross-check, because it compares the DB-recorded operator_xonly_pk (now the forged one) against `kickoff_data.operator_xonly_pk` (their real key) and treats the mismatch as proof of malice [9](#0-8) .

Existing guards do **not** close this gap: `is_kickoff_malicious` assumes the DB-recorded operator key (itself derived via the same vulnerable "first OP_RETURN" logic) is trustworthy; there is no check anywhere that a payout_tx contains *exactly one* OP_RETURN output, and no signature check inside `bridge_circuit`/`update_finalized_payouts` on the payout_tx's own witness to establish which OP_RETURN was truly authored by the broadcasting operator.

### Impact Explanation
- The real, honest operator who fronted the withdrawal can be flagged malicious by `is_kickoff_malicious` and denied reimbursement — "an honest operator permanently unable to be reimbursed" / "an honest operator disprovable" (Critical), because once mined, the malleated payout_tx is immutable and the wrong operator key is permanently bound into `deposit_constant`/DB state.
- Alternately, if the forged first OP_RETURN happens to match some other (targeted) operator's real registered key, that operator's later legitimate reimbursement claims for unrelated kickoffs could be muddled by DB records showing them as "payer" for a payout they never fronted, corrupting the payer-tracking data used across the withdrawal/kickoff reconciliation flow.
- This is repeatable for every withdrawal cycle where the attacker can win the mempool race against the operator's broadcast of `payout_tx`, since the underlying weakness (SIGHASH_SINGLE|ANYONECANPAY + first-OP_RETURN parsing) is structural, not a one-off bug.

### Likelihood Explanation
Exploitation requires only mempool visibility and the ability to broadcast a competing (higher-fee or RBF) transaction — capabilities explicitly within the unprivileged attacker's scope (broadcast Bitcoin transactions, pay fees, choose bytes of withdrawal UTXO/signature/sighash flag). No key compromise, no operator/verifier privilege, no majority hashrate is needed; standard SIGHASH_SINGLE|ANYONECANPAY malleability plus normal fee-bumping/RBF race dynamics suffice. The payout_tx uses a non-ephemeral anchor for CPFP, meaning it is plausible for such a transaction to have minimal explicit fee, making a fee-boosted attacker replacement more likely to be preferred by miners.

### Recommendation
- Require and enforce a canonical, unambiguous encoding for the operator identity in `payout_tx` that is covered by the withdrawal input's signature (e.g., sign with `SIGHASH_ALL` for that input, or explicitly include the OP_RETURN output index in the signed message/commitment) so it cannot be malleated after signing.
- Have `bridge_circuit` and `update_finalized_payouts` reject (panic/None) any payout_tx that contains more than one OP_RETURN output, instead of silently taking the first match via `get_first_op_return_output`.
- Additionally verify that the OP_RETURN's committed operator key was authored by the same signer that funded/produced the transaction (e.g. bind the OP_RETURN content into the signed sighash rather than leaving it outside the signature's commitment).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}
