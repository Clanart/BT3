Based on the M‑5 pattern (a safety invariant is enforced only inside one narrow code path while an alternative path reaching the same state change skips it, letting an attacker profit at the protocol's expense), I found a directly analogous gap in `IntentGatewayV2`'s order‑fill vs. order‑cancel logic.

### Title
`fillOrder` never checks `order.deadline`, letting solvers fill expired orders that the cancellation paths assume are unfillable - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/apps/intentsv2/IntrinsicIntents.sol`, `evm/src/apps/IntentGatewayV2.sol`)

### Summary
The IntentGateway documentation explicitly states that `fillOrder` "verifies the order hasn't expired (`order.deadline >= block.number`)" [1](#0-0)  before executing a fill. However, the concrete `fillOrder` entry point and its internal `_fillSameChain`/`_fillCrossChain` helpers contain no such check anywhere in the code I inspected.

### Finding Description
`IntentGatewayV2.fillOrder` validates chain routing, the `_filled` guard, solver-selection authorization, and output-array lengths, then dispatches to `_fillSameChain` or `_fillCrossChain` — but never compares `order.deadline` to the current block: [2](#0-1) 

`_fillCrossChain` (destination-chain fill) similarly performs no deadline check before transferring output tokens and dispatching the `RedeemEscrow` settlement message: [3](#0-2) 

`_fillSameChain` also has no deadline check: [4](#0-3) 

By contrast, every cancellation path meticulously enforces the deadline as the load-bearing safety invariant:
- Source-side cancel requires the proof height to be strictly after the deadline: `if (options.height <= order.deadline) revert NotExpired();` [5](#0-4) 
- Destination-side cancel treats the deadline as the point where authorization opens up to the public: `if (order.deadline >= _blockNumber()) { ... require order.user ... }` [6](#0-5) 

This is the same broken invariant shape as M‑5: a critical guard ("this state must go through the safe/expired path") exists in the code path designed for it (cancellation) but is entirely absent from the alternative path (fill) that reaches an equivalent, competing state mutation (`_filled[commitment]` + fund movement). Just as the Numa comptroller only checked `isDeprecated` inside `liquidateBorrowAllowed` and not in the alternate liquidation entry points, here the deadline check only lives inside the cancel functions and not inside `fillOrder`.

### Impact Explanation
The source-side cancellation flow (`_cancelFromSource` → `onGetResponse`) is built on the assumption that once `options.height > order.deadline`, the order can no longer be filled on the destination, so an empty `_filled` slot at that height is proof the user is entitled to their refund: [7](#0-6) . Because `fillOrder`/`_fillCrossChain` place no such restriction on the solver, a solver can still fill the order on the destination chain after the queried height/deadline, deliver output tokens to the beneficiary, and dispatch `RedeemEscrow` back to the source chain — racing the user's in-flight refund. Depending on delivery order on the source chain (refund lands first vs. `RedeemEscrow` lands first), this can result in escrow being paid out twice from the source contract's perspective (once via refund, once via redeem) for the same commitment, or in the solver paying the beneficiary in real value while receiving nothing back once the escrow has already been drained by the refund — either way violating the exactly-once settlement guarantee that the whole cancel/fill state machine is designed to provide. This maps directly to the bounty's "replay/double-claim/double-settlement" and "funds must move exactly once" impact categories.

### Likelihood Explanation
Any solver (unprivileged, public entry point) can trigger this simply by calling `fillOrder` after `order.deadline` — no relayer, prover, or admin collusion is required, and no malformed proof is needed. The race window is bounded by ordinary cross-chain message latency (the time between a user's deadline passing and their `RefundEscrow`/`onGetResponse` settlement finalizing on the source chain), which is realistically achievable for an opportunistic solver.

### Recommendation
Add an explicit `if (order.deadline < block.number) revert OrderExpired();` (or the destination-chain-appropriate equivalent) check at the top of `fillOrder`, `_fillSameChain`, and `_fillCrossChain`, mirroring the checks already present in `_cancelFromSource`/`_cancelFromDest`, so that once an order's deadline has passed it can never be filled, matching the invariant the cancellation paths already depend on.

### Proof of Concept
1. User places a cross-chain order with `deadline = D`.
2. At block `> D`, user calls `cancelOrder` from source; this dispatches a `DispatchGet` to read the destination's `_filled[commitment]` slot at a height `> D`.
3. Before/while that GET request is being finalized on Hyperbridge, a solver calls `fillOrder` on the destination chain — this succeeds because `_fillCrossChain` never checks `order.deadline`.
4. The solver's fill dispatches `RedeemEscrow` to the source chain; concurrently, the user's GET response (captured at a height before the fill, or racing it) can still validate an empty slot and trigger a refund via `onGetResponse`.
5. Both the `RefundEscrow`/`onGetResponse` withdrawal and the solver's `RedeemEscrow` withdrawal target the same commitment's escrowed inputs on the source chain, producing conflicting/duplicate settlement for a single order.

Note: I was not able to fully trace `_withdraw`'s internal accounting guards in `IntentsBase.sol` (not fully read) to confirm whether a second withdrawal attempt reverts cleanly or pays out zero — this affects whether the end result is direct fund duplication versus a solver-side loss with incorrect settlement state. The core, directly verified defect is the missing deadline check in the fill path, which is the exact analog of the M‑5 bypass; the precise blast radius of the resulting race should be confirmed with a full trace of `IntentsBase._withdraw` and `_orders` bookkeeping.
