### Title
Permanent order-freeze via blacklisted beneficiary in `_withdraw` blocks permissionless RefundEscrow/RedeemEscrow settlement - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` (invoked from `ExtrinsicIntents.onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse` after a cross-chain cancellation proof) unconditionally pushes escrowed ERC20 tokens to `beneficiary` via `IERC20(token).safeTransfer(beneficiary, amount)` with no fallback. This mirrors the Notional M-5 pattern exactly: the "settlement" step (releasing/refunding escrow) is meant to be a one-shot, non-blocking finalization of a cross-chain intent, but it embeds an unconditional push-transfer to a user-controlled address that can be a USDC/USDT-style blacklisted account.

### Finding Description
`_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol:390-425` decrements the per-commitment escrow accounting (`_orders[body.commitment][token] = escrowed - amount;`) *before* attempting the transfer, and then calls `IERC20(token).safeTransfer(beneficiary, amount)` [1](#0-0) . There is no try/catch, no ETH-style fallback, and no way to redirect funds to an alternate address if the beneficiary's token contract rejects the transfer (e.g., a blacklisted address on a centrally-administered stablecoin).

This function is reached from two permissionless paths:
- `onAccept` for `RequestKind.RedeemEscrow` / `RequestKind.RefundEscrow`, called directly by the Hyperbridge host when delivering a POST request [2](#0-1) .
- `onGetResponse`, called by the host after a GET-based cancellation proof, which also calls `_withdraw` unconditionally [3](#0-2) .

Both `onAccept` and `onGetResponse` are marked `onlyHost` and are the terminal handler the ISMP host invokes when delivering a message — there is no host-side try/catch around this call comparable to the timeout-retry pattern used elsewhere in the codebase (`EvmHost.dispatchTimeOut`, which explicitly catches a failed `onPostRequestTimeout` call and re-stores the commitment for retry instead of reverting the whole delivery — see `evm/src/core/EvmHost.sol:885-899`). For POST/GET message delivery, if the module callback reverts, delivery for that message reverts, and the commitment/order state is never advanced — the request can be resubmitted, but every resubmission will hit the exact same unconditional transfer and revert identically, forever, as long as the token blacklists that beneficiary.

Because `beneficiary` for `RefundEscrow` is `order.user` (the original order creator) set unilaterally in `_cancelFromDest` [4](#0-3) , and for `RedeemEscrow` is `msg.sender` (the solver) set in `_fillCrossChain` [5](#0-4) , any counterparty who becomes blacklisted on the escrowed ERC20 (intentionally or not) permanently blocks that specific commitment's settlement.

### Impact Explanation
Order escrow is meant to move exactly once to the rightful beneficiary. Here, if the beneficiary's address is blacklisted by the escrowed ERC20 token issuer, the tokens become **permanently locked** in the `IntentGatewayV2`/`ExtrinsicIntents` contract:
- The order can never be finalized (`_filled[commitment]` is only set inside `_withdraw`, which never completes), so the commitment is stuck in limbo — not filled, not refunded.
- `RedeemEscrow` (paying the solver who filled an order) blocks a legitimate solver payout, disincentivizing solvers and stalling the intent settlement pipeline for that commitment.
- `RefundEscrow`/`onGetResponse` cancellation blocks a legitimate user refund after order expiry, permanently locking user funds in escrow with no admin bypass, no partial-token skip, and no alternate destination for the stuck asset.
- Because `_orders[...] -= amount` happens before the transfer, there's no accounting corruption on retry, but repeated retries are guaranteed to fail identically — this is a permanent fund lock rather than a delay.

This matches the bounty's "stealing or loss of funds" / fund-lock impact category, and is a direct structural analog of the Notional M-5 report (permissionless settlement path with an unconditional ERC20 push-transfer to a user-controlled, blacklistable address).

### Likelihood Explanation
Likelihood is moderate: it requires the beneficiary address to be blacklisted on the specific escrowed ERC20 (e.g., USDC/USDT). This is a realistic, externally-triggerable condition (OFAC/compliance blacklisting, exchange freezes) not requiring any malicious relayer, prover, or governance actor — a normal user or solver becoming blacklisted on the token issuer's side is enough to trigger the permanent lock, satisfying the "unprivileged attacker/externally caused" requirement (the "attacker" here is effectively the token issuer's blacklist action, but the vulnerable code path is squarely in-scope Hyperbridge contract logic with no mitigation).

### Recommendation
- Wrap the ERC20 push-transfer in `_withdraw` with a try/catch (or low-level `call`), and on failure, credit the amount to an internal "claimable" balance mapping for the beneficiary instead of reverting the whole settlement.
- Always finalize order state (`_filled[commitment]`, escrow accounting) independent of whether the transfer succeeds, so a blacklisted beneficiary cannot block the entire commitment/other tokens in the same withdrawal from settling.
- Provide a separate permissionless `claim()`/`pull`-style withdrawal function so any address (including a newly-designated one, if allowed by governance) can retrieve stuck balances, decoupling settlement finality from token-transfer success — analogous to the Notional recommendation to let the protocol bypass the transfer and force-settle first.

### Proof of Concept
1. User creates a cross-chain intent order with `inputs` denominated in a blacklist-capable ERC20 (e.g., USDC) via the standard order-creation flow, escrowing the tokens in `IntentGatewayV2`/`ExtrinsicIntents` (`_orders[commitment][token] += amount`).
2. Before the order is filled/expired, the user's address (`order.user`) gets blacklisted by the USDC issuer.
3. Order deadline passes; anyone calls `_cancelFromDest` (permissionless after deadline) to dispatch a `RefundEscrow` request back to the source chain [4](#0-3) .
4. Hyperbridge relayer delivers the POST request; host calls `onAccept` → `_withdraw(body, true, true)` [2](#0-1) .
5. Inside `_withdraw`, `IERC20(token).safeTransfer(beneficiary, amount)` reverts because `beneficiary` (the blacklisted user) is rejected by USDC's `transfer` [1](#0-0) .
6. The entire `onAccept` call reverts; the message delivery fails on the host side. Any resubmission of the same POST request hits the identical revert. The escrowed USDC remains permanently locked in the contract, and the commitment is never marked `_filled`, blocking both refund and any future accounting cleanup for that order.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        bytes memory body = bytes.concat(
            bytes1(uint8(RequestKind.RefundEscrow)),
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}))
        );

        DispatchPost memory request = DispatchPost({
            dest: order.source,
            to: abi.encodePacked(_instance(order.source)),
            body: body,
            timeout: 0,
            fee: options.relayerFee,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
