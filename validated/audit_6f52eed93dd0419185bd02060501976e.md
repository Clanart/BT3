### Title
Unauthenticated `sender`/`recipient` indexes cause a panic in PedPoP blame evaluation, aborting the process (crash DoS) - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

`BlameMachine::blame_internal` and `AdditionalBlameMachine::blame` index `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with participant indexes taken verbatim from the caller — i.e., from a blame-accusation message — without ever checking that the indexes belong to the DKG set. Passing any `Participant` value that was not registered causes a `HashMap` index panic, crashing the caller's process. This is a remotely triggerable denial of service analogous to CVE-2024-20966 (a network-reachable party causing a repeatable crash of the server).

### Finding Description

`blame_internal` is reached through two public APIs:

- `BlameMachine::blame(self, sender, recipient, msg, proof)` at crypto/dkg/pedpop/src/lib.rs:623-632.
- `AdditionalBlameMachine::blame(&self, sender, recipient, msg, proof)` at crypto/dkg/pedpop/src/lib.rs:674-682, whose doc explicitly states it can be used "regardless of if the caller was a member in the DKG protocol".

Inside `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575-609), two unguarded index operations use the attacker-controlled indexes:

```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],   // line 388: panics if `decryptor` unregistered
)
```

```rust
multiexp_vartime(&share_verification_statements::<C>(
  recipient,
  &self.commitments[&sender],               // line 599: panics if `sender` unregistered
  Zeroizing::new(share),
))
```

Neither `blame` nor `blame_internal` validates `sender` or `recipient` against the participant set. `Participant::new` accepts any non-zero `u16` (crypto/dkg/src/lib.rs:29-35), so an accuser can name e.g. `Participant(0xFFFF)` or any index `> n`. Because `self.commitments` and `self.decryption.enc_keys` are only populated for `1..=n` (via `verify_r1`/`AdditionalBlameMachine::new`), indexing with such a value panics instead of returning `PedPoPError`.

The bug class mirrors the advisory: easily exploitable, network-reachable, requiring only the ability to submit a blame-accusation message naming an out-of-range party, and resulting in a repeatable crash of the node handling blame resolution.

### Impact Explanation

A panic inside `blame_internal` unwinds into whatever async task/thread is adjudicating DKG blame. In a validator/processor deployment this kills the key-confirmation/blame-resolution path: the DKG attempt cannot be conclusively resolved, the accused party is never marked faulty, and the operator's process crashes. Repeated accusations with invalid indexes produce a "frequently repeatable crash" of the key-generation pipeline — exactly the availability impact of the reference CVE. There is no error return; `HashMap` indexing is a hard panic.

### Likelihood Explanation

Reachability requires only that a party can cause a `blame` call with a `sender`/`recipient` it controls. The library takes `sender`, `recipient`, `msg`, and `proof` as parameters specifically because the message "must have been authenticated as actually having come from the sender in question" — i.e., the caller feeds in accusation contents, and nothing constrains the `Participant` values to the set. `AdditionalBlameMachine::new` exists precisely for arbitrary third-party blame evaluation and likewise performs no index bounds check (`1 ..= n` is only used to *populate* the map, not to validate the queried keys). A single malformed accusation deterministically panics, making this trivially and repeatedly exploitable whenever accusations carry attacker-influenced participant indexes.

### Recommendation

In `blame_internal` (crypto/dkg/pedpop/src/lib.rs:575), validate `sender` and `recipient` before indexing:

```rust
if !self.commitments.contains_key(&sender) ||
   (proof.is_some() && !self.enc_keys.contains_key(&decryptor))
{
  // treat the accuser as faulty / return a defined error
}
```

and have `blame`/`AdditionalBlameMachine::blame` return `Result<Participant, PedPoPError>` (e.g. `DkgError::InvalidParticipant`) instead of panicking. Alternatively, replace `self.commitments[&sender]` with `self.commitments.get(&sender)` and return the accuser as faulty on `None`, matching the function's contract that it must always identify *some* faulty party rather than abort.

### Proof of Concept

```rust
// Participant n=3, t=2 DKG; an accuser submits a blame statement naming
// a non-existent sender. Any of the following panic inside blame_internal:

// 1. sender out of range -> self.commitments[&sender] panics (line 599)
machine.blame(Participant::new(7).unwrap(), params.i(), msg, Some(proof));

// 2. decryptor/recipient unregistered while a proof is supplied ->
//    self.enc_keys[&decryptor] panics (line 388)
machine.blame(sender, Participant::new(9).unwrap(), msg, Some(proof));

// 3. Via the non-member path explicitly supported by the API:
let arbiter = AdditionalBlameMachine::<C>::new(context, 3, commitment_msgs).unwrap();
arbiter.blame(Participant::new(u16::MAX).unwrap(), Participant::new(1).unwrap(), msg, None);
// -> panic: HashMap index into `commitments` for Participant(65535)
```

Each case requires only a `Participant` value outside `1..=n` in an accusation; no valid shares, signatures, or collusion are needed, and the crash is deterministic and repeatable. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
