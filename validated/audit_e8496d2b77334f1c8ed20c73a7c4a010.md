Based on my research, I found a structural analog to the reported Solana bug in the `IntentGatewayV2` cross-chain gateway's peer-registration logic.

### Title
Unconditional overwrite of registered peer gateway address via `_addDeployment` - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
### Finding Description
The original report's core broken invariant is: **a shared trust-anchor account (`ForeignContract`, keyed only by chain id) can be silently overwritten because the write path performs no "does a legitimate entry already exist" check**, letting an attacker redirect where the protocol accepts messages from for that chain.

The same pattern exists in `IntentsBase._addDeployment`: [1](#0-0) 

```solidity
function _addDeployment(Deployment memory body) internal {
    _instances[keccak256(body.chain)] = body.gateway;
    emit DeploymentAdded({chain: string(body.chain), gateway: body.gateway});
}
```

`_instances` is the trust anchor used everywhere in the gateway to authenticate and route cross-chain settlement traffic — `_instance()` is used to resolve the peer gateway address for `RedeemEscrow`/`RefundEscrow` dispatches, and (per the intent-gateway docs) inbound settlement messages are authenticated by checking that they "came from a known IntentGateway instance" — i.e., against this exact mapping: [2](#0-1) 

Unlike the LayerZero endpoint's equivalent mapping setter, which explicitly clears the stale reverse mapping before writing a new one to prevent a revoked/attacker-supplied value from lingering or colliding: [3](#0-2) 

`_addDeployment` performs **no existence check, no previous-value comparison, and no event differentiating "first registration" from "silent replacement."** Any code path that can drive a `NewDeployment` request into `onAccept()` for a given chain id (`body.chain`) unconditionally clobbers whatever gateway address was previously trusted for that chain — exactly the same "no guard against re-registration" defect that broke `ForeignContract` in the Solana report.

### Impact Explanation
If the authentication of inbound `NewDeployment` messages is anchored only to "message originated from the Hyperbridge coprocessor chain" rather than to a specific, hardcoded, immutable module id for `pallet-intents-coprocessor` (which is unavoidable for the very first registration, since `_instances` itself cannot yet be trusted to validate the coprocessor's own identity), overwriting `_instances[keccak256(chain)]` lets an attacker redirect that chain's trusted peer to an address they control. Because `_instances` is also the source of authorization for `RedeemEscrow`/`RefundEscrow` inbound messages, corrupting this single mapping enables an attacker-controlled "gateway" to be treated as the legitimate settlement counterpart for that state machine — a direct path to unauthorized escrow release/fund theft or to a permanently broken (bricked) cross-chain route for that chain, mirroring the "verification will fail / bridge broken" outcome in the original report.

### Likelihood Explanation
The concrete authentication check performed inside `onAccept()` for the `NewDeployment` request kind (i.e., exactly which field — `request.source`, `request.from`, or a hardcoded coprocessor module id — is validated before calling `_addDeployment`) was not directly inspectable within the available context/tool budget. The intents-coprocessor pallet's own `add_deployment` call is governance-gated (`T::GovernanceOrigin`), so the legitimate path is privileged. The risk here is specifically whether the **destination-side** `onAccept` validates the identity of the sender for `NewDeployment` messages as tightly as it must for `RedeemEscrow`/`RefundEscrow` — since `_addDeployment` itself contains zero defense-in-depth (no idempotency/overwrite guard), it relies entirely on that external authentication being airtight, which is a weaker invariant than a value-level check would provide.

### Recommendation
Add a defense-in-depth guard to `_addDeployment` so it cannot silently replace an already-trusted peer:
```solidity
function _addDeployment(Deployment memory body) internal {
    bytes32 key = keccak256(body.chain);
    address existing = _instances[key];
    if (existing != address(0) && existing != body.gateway) revert InstanceAlreadyRegistered();
    _instances[key] = body.gateway;
    emit DeploymentAdded({chain: string(body.chain), gateway: body.gateway});
}
```
and separately confirm that `onAccept()` authenticates `NewDeployment` requests against a hardcoded, immutable coprocessor module id (not merely `request.source == hyperbridge chain`), analogous to the recommended `init` (not `init_if_needed`) fix in the original report.

### Proof of Concept
Not independently verifiable end-to-end without access to the exact `onAccept()` authentication branch for `RequestKind.NewDeployment` in `IntentGatewayV2.sol`, which I could not fully retrieve in this session. The concrete, locally-verified defect is that `_addDeployment` (evm/src/apps/intentsv2/IntentsBase.sol:521-524) performs an unconditional overwrite of the `_instances` trust mapping with no existence/uniqueness guard — structurally identical to the unguarded `ForeignContract` overwrite in the original report. I recommend a Devin session inspect `IntentGatewayV2.onAccept()` (both `evm/src/apps/IntentGatewayV2.sol` and the Tron variant) to confirm exactly which request fields authenticate the `NewDeployment` case, and to build a full PoC exploit transaction if the authentication turns out to be insufficiently scoped.
