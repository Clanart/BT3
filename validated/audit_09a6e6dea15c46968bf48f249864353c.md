### Title
Uncontrolled CPU Consumption via Unbounded Decimal String Parsing in Governance Parameter Canonicalization - (File: kaiax/gov/param.go)

### Summary
The `bigIntCanonicalizer` used to canonicalize `*big.Int`-typed governance parameters (`reward.mintingamount`, `reward.minimumstake`, `reward.stakingrewardthreshold`) calls Go's `big.Int.SetString(v, 10)` directly on attacker-influenced strings with no length cap, unlike every other big-integer decoding path in this codebase (`hexutil.DecodeBig`, `hexutil.Big.UnmarshalText`) which explicitly reject inputs over 64 hex nibbles (256 bits) before doing any digit processing. `math/big`'s base-10 `SetString` has known superlinear (near-quadratic) time complexity in the number of decimal digits, which is exactly the CWE-400 "Algorithmic Complexity" bug class described in the spray-json advisory (CVE-2018-18853): an attacker who controls the input string can force disproportionate CPU consumption during parsing.

### Finding Description
`bigIntCanonicalizer` in [1](#0-0)  converts `string`/`[]byte` values to `*big.Int` via `new(big.Int).SetString(v, 10)` with **no bound on the length of `v`**. This is used for the `RewardMintingAmount`, `RewardMinimumStake`, and `RewardStakingRewardThreshold` parameters [2](#0-1) [3](#0-2) .

Contrast this with every other numeric decoding path in the codebase, which enforces an explicit size cap before parsing digits:
- `hexutil.DecodeBig` rejects any hex payload longer than 64 nibbles (256 bits) before decoding [4](#0-3) .
- `hexutil.Big.UnmarshalText` performs the identical `len(raw) > 64` check [5](#0-4) .
- `math.ParseBig256` bounds the *result* bit length to 256 bits, but only *after* calling `big.Int.SetString(s, 10)` for decimal strings [6](#0-5)  — post-hoc bounding does not prevent the quadratic-time cost already incurred during parsing of a very long digit string.

`bigIntCanonicalizer` has neither a pre-check on string length nor a post-hoc bit-length check, making it strictly weaker than both of the above.

These parameters are populated from governance data that is exposed and consumable through public RPC surfaces documented in the module, e.g. `governance_getParams` and `governance_getContractParams`, where `reward.mintingamount` / `reward.minimumstake` are returned/read as decimal strings [7](#0-6) . The `governance_getContractParams` RPC additionally lets the caller specify an arbitrary `govparam` contract address to read parameters from [8](#0-7) , meaning an unprivileged caller can point the RPC at a contract they control and return an arbitrarily long numeric string for a big-int parameter, which then flows into `bigIntCanonicalizer`.

### Impact Explanation
If an attacker can get a very long decimal digit string into one of these parameter values (via a header vote's `[]byte` value, or via a contract they control that is queried through `governance_getContractParams`), the node performing canonicalization would spend disproportionate CPU time in `big.Int.SetString(v, 10)`, since the go stdlib decimal parser's complexity for `SetString` grows faster than linearly with the number of digits. This can be triggered per RPC call by any public-RPC caller who can point the call at a contract address they deploy/control, producing a CPU-consumption denial-of-service reachable without special privileges.

### Likelihood Explanation
Likelihood is bounded by two open questions this exercise could not fully verify (index/tool-call limits prevented reading `kaiax/gov/contractgov/impl/getter.go` in full): (1) whether the contractgov getter enforces any ABI-level or byte-length limit on the returned parameter bytes/string before calling the canonicalizer, and (2) whether header-vote paths that feed `bigIntCanonicalizer` with `[]byte` are gated to validator/proposer-only submission versus reachable by an ordinary transaction. Given the demonstrated absence of a length check inside `bigIntCanonicalizer` itself — in clear contrast to the deliberate 64-nibble caps applied everywhere else numeric strings are decoded in this codebase — the core parsing weakness is confirmed at the file/function level even though full RPC-argument-to-sink reachability could not be exhaustively traced in this session.

### Recommendation
Add an explicit length/byte-size cap on the input to `bigIntCanonicalizer` before calling `big.Int.SetString`, mirroring the `len(raw) > 64` guard used in `hexutil.DecodeBig`/`hexutil.Big.UnmarshalText`, and apply this bound consistently to `[]byte` and `string` cases in the `RewardMintingAmount`, `RewardMinimumStake`, and `RewardStakingRewardThreshold` parameter paths, in both `headergov` (vote/governance byte payloads) and `contractgov` (contract-supplied byte/string payloads).

### Proof of Concept
Recommend that the background agent write a unit test targeting `bigIntCanonicalizer` in `kaiax/gov/param.go` (following the pattern of `TestBigIntCanonicalizer` in `kaiax/gov/param_test.go`) that passes a string of several million decimal digits and measures wall-clock time, comparing it against the guarded `hexutil.DecodeBig`/`math.ParseBig256` equivalents, to empirically confirm the disproportionate CPU cost, and additionally trace/verify whether `contractgov/impl/getter.go` and the `governance_getContractParams` RPC handler in `contractgov/impl/api.go` allow an externally supplied contract address to inject such an oversized string into `RewardMintingAmount`/`RewardMinimumStake`/`RewardStakingRewardThreshold`.

// Numbers larger than 256 bits are not accepted.
func DecodeBig(input string) (*big.Int, error) {
	raw, err := checkNumber(input)
	if err != nil {
		return nil, err
	}
	if len(raw) > 64 {
		return nil, ErrBig256Range
	}
	words := make([]big.Word, len(raw)/bigWordNibbles+1)
	end := len(raw)
	for i := range words {
		start := max(end-bigWordNibbles, 0)
		for ri := start; ri < end; ri++ {
			nib := decodeNibble(raw[ri])
			if nib == badNibble {
				return nil, ErrSyntax
			}
			words[i] *= 16
			words[i] += big.Word(nib)
		}
		end = start
	}
	dec := new(big.Int).SetBits(words)
	return dec, nil
}

// ParseBig256 parses s as a 256 bit integer in decimal or hexadecimal syntax.
// Leading zeros are accepted. The empty string parses as zero.
func ParseBig256(s string) (*big.Int, bool) {
	if s == "" {
		return new(big.Int), true
	}
	var bigint *big.Int
	var ok bool
	if len(s) >= 2 && (s[:2] == "0x" || s[:2] == "0X") {
		bigint, ok = new(big.Int).SetString(s[2:], 16)
	} else {
		bigint, ok = new(big.Int).SetString(s, 10)
	}
	if ok && bigint.BitLen() > 256 {
		bigint, ok = nil, false
	}
	return bigint, ok
}
