### Title
Missing `request.from` (module-identity) binding in `BandwidthManager.onAccept` allows unauthorized `Withdraw` action to drain the manager's held funds - (File: evm/src/apps/BandwidthManager.sol)

### Summary
The external report's core broken invariant is: an authorization credential is trusted without being bound/verified against the channel it arrives on (Bearer token accepted over an unencrypted channel; `session_id` duplicated outside its proper authorization slot). The local analog is `BandwidthManager.onAccept()`, which authorizes privileged, fund-moving governance actions (`SetTiers`, `Withdraw`) solely on `request.source == hyperbridge`, without ever checking `request.from` (the module identity of the sender on Hyperbridge). This breaks the "module/app identity binding" invariant that the ISMP request path is supposed to enforce.

### Finding Description
`BandwidthManager.sol`'s `onAccept` is the single inbound governance entrypoint for the contract, gated by `onlyHost` and an explicit source check: [1](#0-0) 

It checks `request.source.equals(IDispatcher(_host).hyperbridge())` but never checks `request.from`. Compare this with the pallet-side symmetric check, `pallet_bandwidth::on_accept`, which does bind the counterpart identity — it rejects any message whose `request.from` does not match the registered `BandwidthManager` address: [2](#0-1) 

On the EVM side, the contract's own comments assert that the pallet enforces the module id round-trip ("Must equal `pallet-bandwidth`'s `PalletId` ... changing it on either side breaks the round-trip"), but this is only a naming convention — nothing in `onAccept` actually verifies that the inbound `request.from` equals `PALLET_BANDWIDTH.0` (`b"BWMARKET"`): [3](#0-2) 

Because `request.source` is automatically set to the Hyperbridge state-machine id for *any* request dispatched locally on Hyperbridge (it is not attacker-controllable per se), the only remaining authorization boundary that should stop a non-`pallet-bandwidth` sender from reaching `Withdraw` is `request.from`. Since that check is absent, any Hyperbridge-side caller capable of dispatching an ISMP `PostRequest` with `to = <BandwidthManager address>` and an attacker-chosen `body` can impersonate `pallet-bandwidth` and drive the `Withdraw` branch: [4](#0-3) 

The `Withdrawal` struct fields (`token`, `beneficiary`, `amount`) are fully attacker-controlled via the forged `body`, letting an attacker set `beneficiary` to their own address and `amount` up to the contract's full ERC-20/native balance.

### Impact Explanation
`BandwidthManager` custodies buyer funds — every `purchase()` call transfers the scaled fee-token price into the contract and holds it until governance withdraws it: [5](#0-4) 

A forged `Withdraw` message (crafted by any entity able to dispatch a Hyperbridge-originated `PostRequest` to the manager's address with an unbound `from` field) directly transfers the entire accumulated buyer-fee balance (ERC-20 or native) to an attacker-chosen `beneficiary`, with no signature, no admin origin, and no relayer/validator collusion required beyond normal message delivery. This is unauthorized execution and outright theft of custodied funds — squarely inside the bounty's "unauthorized transaction or execution" / "stealing or loss of funds" categories, and it matches the stated pivot: "Cross-chain admin or host-management effects must not be reachable through malformed proofs, wrong module bindings, or unauthenticated message flow."

### Likelihood Explanation
Likelihood hinges on whether any unprivileged, non-admin path exists on Hyperbridge for dispatching a `PostRequest` with an attacker-chosen `to` and `body` while `source` is automatically the Hyperbridge state machine. Governance-triggered dispatch (`dispatch_withdraw`/`dispatch_set_tiers` in `pallet_bandwidth`) is `AdminOrigin`-gated, so it is not itself the attack vector: [6](#0-5) 

However, the documentation elsewhere in the repo confirms Hyperbridge exposes generic user-callable dispatch entrypoints (e.g. a "ping"/demo module callable "from any signed account" that dispatches an arbitrary-destination `PostRequest`), which is the kind of path that would satisfy `request.source == hyperbridge` while letting the caller pick `to`/`from`/`body`: [7](#0-6) 

I was not able to fully confirm, within the remaining tool budget, whether that specific demo pallet (`modules/pallets/demo/src/lib.rs`) or another public extrinsic gives full attacker control over an arbitrary raw `body` byte string (as opposed to only a fixed ping payload). Regardless of that specific reachability question, the vulnerability itself — `onAccept` failing to bind `request.from` even though the pallet side does bind it — is a proven, concrete defect in the mutual-authentication contract between `pallet-bandwidth` and `BandwidthManager.sol`, and it is the exact bug class the fix should close.

### Recommendation
In `BandwidthManager.onAccept`, in addition to the existing `request.source` check, verify `request.from` equals the registered `pallet-bandwidth` module id (`PALLET_BANDWIDTH_MODULE_ID`, i.e. `b"BWMARKET"`) before processing `SetTiers`/`Withdraw`:
```solidity
if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();
if (!request.from.equals(PALLET_BANDWIDTH_MODULE_ID)) revert UnauthorizedAction();
```
This mirrors the binding already enforced symmetrically on the pallet side (`request.from != manager.0.to_vec()` check in `on_accept`) and closes the identity-binding gap.

### Proof of Concept
1. Identify (or use) any mechanism on Hyperbridge that lets a caller dispatch a locally-originated ISMP `PostRequest` targeting an arbitrary EVM `to` address and arbitrary `body` bytes (`request.source` is set automatically to the Hyperbridge state machine for such dispatches).
2. Set `to = <BandwidthManager contract address>` and craft `body = abi.encodePacked(uint8(1) /* ACTION_WITHDRAW */, abi.encode(Withdrawal{ token: <feeToken>, beneficiary: <attacker>, amount: <manager's full balance> }))`.
3. Deliver the message through the normal relayer pipeline to the destination EVM chain; `EvmHost` calls `BandwidthManager.onAccept`.
4. `onAccept` checks only `request.source == hyperbridge` (true) and never checks `request.from`, so it decodes the forged body as a valid `Withdraw` action and executes `IERC20(token).safeTransfer(attacker, amount)` (or a native transfer), draining the contract to the attacker.

    /// @notice Inbound governance from `pallet-bandwidth`. The first
    /// body byte selects `OnAcceptActions`; the remainder is the
    /// action's ABI-encoded payload.
    /// @dev Only the configured host may invoke (`onlyHost`); the
    /// request's `source` must additionally equal hyperbridge.
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }

		#[pallet::call_index(5)]
		#[pallet::weight(T::DbWeight::get().writes(1))]
		pub fn dispatch_withdraw(
			origin: OriginFor<T>,
			target: StateMachine,
			token: H160,
			beneficiary: H160,
			amount: U256,
		) -> DispatchResult {
			<T as pallet_ismp::Config>::AdminOrigin::ensure_origin(origin)?;
			let manager = BandwidthManager::<T>::get(&target).ok_or(Error::<T>::UnknownManager)?;

			let payload = Withdrawal {
				token: alloy_primitives::Address::from(token.0),
				beneficiary: alloy_primitives::Address::from(beneficiary.0),
				amount: to_alloy_u256(amount),
			};
			let mut body = vec![ACTION_WITHDRAW];
			body.extend(payload.abi_encode_params());

			let commitment = Self::dispatch_governance(target, manager, body)?;
			Self::deposit_event(Event::WithdrawalDispatched {
				target,
				token,
				beneficiary,
				amount,
				commitment,
			});
			Ok(())
		}
