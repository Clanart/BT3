### Title
Unbounded O(t²) work with modular inversions during attacker-controlled `ThresholdKeys` deserialization causes CPU denial of service - (File: crypto/dkg/src/lib.rs)

### Summary

Analogous to CVE-2026-10819 (missing size/frame limits enabling DoS via crafted input), `ThresholdKeys::read` accepts an attacker-controlled participant count `n` and threshold `t` of up to 65,535 each, then `ThresholdKeys::new` performs Lagrange interpolation that costs O(t²) field multiplications plus one field inversion per participant. A ~2 MB input forces billions of field operations and 65,535 inversions — a large amplification of input size to CPU work, with no bound or early cap.

### Finding Description

`ThresholdKeys::read` reads `t`, `n`, `i` as raw `u16` values from the reader, then unconditionally reads `n` scalars (for `Interpolation::Constant`) and `n` group elements, and calls `ThresholdKeys::new`:

- `crypto/dkg/src/lib.rs` lines 591–632: `t`, `n` come straight from the bytes (`read_u16`), `n` controls the `1 ..= n` read loop and `Vec::with_capacity(n)`.
- `crypto/dkg/src/lib.rs` lines 376–378: `ThresholdKeys::new` computes `group_key` as the sum over `1 ..= t` of `verification_shares[i] * interpolation.interpolation_factor(*i, &t)`.
- `crypto/dkg/src/lib.rs` lines 229–246: `interpolation_factor` for `Interpolation::Lagrange` iterates over all `included` (length `t`), performing O(t) field multiplications and — critically — a `denom.invert().unwrap()` per call.

So `group_key` computation is O(t²) field multiplications plus O(t) field inversions. With `t = n = 65,535` (both just `u16` values in the byte stream, validated only by `ThresholdParams::new` which checks `t <= n` and non-zero, lines 166–179), deserialization of a ~2.1 MB blob (65,535 × 32-byte points + scalars) triggers ~4.3 × 10⁹ field multiplications and 65,535 inversions in a single synchronous call — work that completes long after the input is consumed and cannot be aborted.

The same O(t²)-with-inversion cost is re-incurred on every `ThresholdKeys::view` call (`interpolation_factor` per included signer, lines 500–506), so even honestly-loaded large key sets pay it per signing session, but the attacker-reachable amplification point is `read` → `new`.

Note the parallel with the upstream fix pattern: Serai itself caps this class elsewhere — `Transaction::read` for `DkgCommitments` enforces `commitments_len * each_commitments_len <= TRANSACTION_SIZE_LIMIT` (coordinator/src/tributary/transaction.rs:286) — but no equivalent bound exists in the in-scope DKG crate.

### Impact Explanation

An unprivileged party that can cause a node/participant to deserialize a `ThresholdKeys` blob (the threat model explicitly allows untrusted bytes into `ThresholdKeys::read`) can burn orders of magnitude more CPU than the input size would suggest: ~2 MB in, billions of field ops and tens of thousands of inversions out, all on the synchronous read path. Repeated submissions can stall the participant's DKG/signing pipeline. This matches the advisory's class: authenticated/unprivileged input triggering disproportionate computation due to a missing cap. Rated Medium analog (DoS only, no secret leakage).

### Likelihood Explanation

Reachability depends on an integrator feeding network-received bytes to `ThresholdKeys::read` (e.g., key-share exchange/recovery flows, where `crypto/dkg/recovery` also deserializes key material). `n`/`t` are `u16` so the maximum is fixed at 65,535, capping the worst case — but the cost ratio (input ≈32 B per O(t) outer iteration each causing O(t) inner work) still gives ~2000×+ amplification with inversions, and the code applies no `TRANSACTION_SIZE_LIMIT`-style guard. Requires only crafting the two `u16` header fields; all subsequent reads succeed with trivially valid encodings (e.g., generator points, `1` interpolation tag for Lagrange).

### Recommendation

Cap `t`/`n` at a protocol-realistic maximum (e.g., the `MAX_KEY_SHARES_PER_SET` bound already enforced in coordinator `SlashReport` handling) inside `ThresholdKeys::read` before allocating or interpolating — reject inputs where `n` exceeds the deployment maximum. Alternatively/al additionally, replace the per-participant `denom.invert()` with a batch inversion (Montgomery trick) to reduce the O(t) inversion cost, and consider computing `group_key` via a single multiexp rather than O(t²) naive Lagrange evaluation.

### Proof of Concept

```rust
// Attacker-controlled bytes fed to ThresholdKeys::<Ristretto>::read
let mut buf = vec![];
// curve ID header (as expected by read)
buf.extend((Ristretto::ID.len() as u32).to_le_bytes());
buf.extend(Ristretto::ID);
// t = 65535, n = 65535, i = 1
buf.extend(65535u16.to_le_bytes());
buf.extend(65535u16.to_le_bytes());
buf.extend(1u16.to_le_bytes());
// interpolation = Lagrange (tag 1) — skips the n-scalar Constant read
buf.push(1u8);
// secret_share
buf.extend(Ristretto::F::ONE.to_repr().as_ref());
// n verification shares, all the generator (valid, non-identity)
for _ in 1 ..= 65535u16 {
  buf.extend(Ristretto::generator().to_bytes().as_ref());
}
// ~2.1 MB total; read() -> ThresholdKeys::new performs ~t^2 ≈ 4.3e9 field
// multiplications plus 65,535 field inversions synchronously.
let _ = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice());
```

`ThresholdParams::new` accepts `t = n = 65535` (non-zero, `t <= n`, `i <= n`), `verification_shares.len() == n` passes the count check, and `interpolation_factor` then loops all 65,535 included participants per group_key term with an `invert().unwrap()` each — confirming the unbounded quadratic cost is driven entirely by two attacker-controlled bytes.
