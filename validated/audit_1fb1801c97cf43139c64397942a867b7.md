## Finding: `resolveWithin()` path-containment check uses an unanchored string prefix comparison, allowing escape into sibling directories

### Title
Directory-traversal escape via unanchored `startsWith` boundary check in `resolveWithin()` - (File: `app/src/lib/path.ts`)

### Summary
`_resolveWithin()` is Desktop's central guard against path traversal/symlink escape, used to validate paths that ultimately come from untrusted sources: deep-link URLs a user clicks, and file paths recorded in a cloned/fetched repository's git status (merge conflicts). The final containment check compares the resolved real path to the real root using a plain string `startsWith()`, without verifying a path-separator boundary. A resolved path whose name merely shares the root directory's name as a *string prefix* (e.g. root `…/acme` vs. escaped target `…/acme-secrets`) passes the check even though it lives in a completely different, sibling directory.

### Finding Description
`_resolveWithin()` performs the following at the end of its logic: [1](#0-0) 

```
const resolved = resolve(normalizedRoot, normalizedRelative)
const realRoot = await realpath(normalizedRoot)
const realResolved = await realpath(resolved)
return realResolved.startsWith(realRoot) ? resolved : null
```

`String.prototype.startsWith` has no notion of path separators. If `realRoot` is `/Users/victim/Projects/acme` and `realResolved` resolves (via enough `..` segments in the attacker-supplied relative path) to a sibling path such as `/Users/victim/Projects/acme-secrets/passwords.txt`, the check `realResolved.startsWith(realRoot)` evaluates to `true`, because the string `"acme-secrets"` begins with the string `"acme"`. The function returns the escaped path as if it were safely inside the root, defeating the entire purpose of the guard.

This is the same class of defect as the reported bug: an implicit assumption (“the underlying primitive enforces the invariant we expect”) holds in the common case but silently breaks for a realistic edge case (sibling names sharing a prefix), just as `transferFrom` was assumed to universally special-case `src == msg.sender` but didn't on Arbitrum's WETH.

`resolveWithin()` is exercised with attacker-influenced input in at least three places:

1. Deep-link file-open handling — `filepath` comes directly from an `x-github-client://` URL a user clicks: [2](#0-1) 

2. Reading conflict-file contents from a cloned/fetched repository's working tree during a merge — `file.path` originates from `git status`/conflict data, which an attacker fully controls via a crafted repository/branch that the victim merges: [3](#0-2) 

3. Writing AI-resolved conflict content back to disk at the resolved path: [4](#0-3) 

The existing tests only validate `..` traversal out of the root and back in, symlink escapes (POSIX only), and null bytes — they never exercise the sibling-prefix case, so the bug is not caught: [5](#0-4) 

### Impact Explanation
- **Data exfiltration**: In `copilot-conflict-context.ts`, a maliciously crafted repository (the attacker controls a branch merged by the victim) can declare a conflicted file path such as `../<sibling-dir-with-prefix>/<sensitive-file>`. If the victim's repository directory name is a string prefix of any sibling directory in the same parent folder (a very common occurrence — e.g. `app` next to `app-legacy`, `web` next to `web2`, or a repo the user renamed with a suffix), the guard passes and the sensitive file's contents are read and forwarded into the Copilot conflict-resolution context (sent off-repo to the AI backend).
- **Arbitrary file write outside the repo**: In `app-store.ts`, the same class of escape lets a resolved path outside the repository be treated as valid, so `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` can silently write/overwrite a file in a sibling directory — corrupting data the user never intended to touch, entirely outside the guard's intended scope.
- **Deep-link based disclosure**: In `dispatcher.ts`, a link the user clicks can supply a `filepath` that escapes to a sibling folder and calls `shell.showItemInFolder` on it, revealing the existence/location of files outside the repo.

This matches the report's required impact class: attacker-controlled repository/merge content or a clicked link resulting in reads/writes outside the intended directory boundary.

### Likelihood Explanation
The precondition (a sibling directory whose name has the repository's directory name as a string prefix) is not exotic — Desktop routinely disambiguates clone directory names by appending suffixes (`-1`, `-2`, etc.), and users commonly keep short/common project names (`app`, `api`, `web`, `src`) alongside other similarly-prefixed folders. The attacker does not need local or admin access; they only need to get the victim to merge a branch/PR containing a crafted conflicting file path, or click a crafted `x-github-client://` link — both are unprivileged, remotely triggerable actions already anticipated by the existing (but incomplete) traversal defenses in this exact function.

### Recommendation
Anchor the containment check on a path boundary instead of a raw string prefix, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
(using the platform-appropriate separator from the `options` object, i.e. `join`'s own separator, not the hard-coded native `Path.sep`, to keep the win32/posix variants correct). Add a unit test asserting that a root of `.../acme` cannot escape into `.../acme-evil` or `.../acme.bak`.

### Proof of Concept
```ts
import { resolveWithin } from '../../src/lib/path'
import { mkdtemp, mkdir, writeFile } from 'fs/promises'
import { join } from 'path'
import { tmpdir } from 'os'

const parent = await mkdtemp(join(tmpdir(), 'poc-'))
const root = join(parent, 'acme')            // victim's repo root
const sibling = join(parent, 'acme-secrets') // unrelated sibling folder
await mkdir(root)
await mkdir(sibling)
await writeFile(join(sibling, 'passwords.txt'), 'super-secret')

// Attacker-controlled conflict/link "path" crafted to escape `root`
const escaped = await resolveWithin(root, '../acme-secrets/passwords.txt')

console.log(escaped)
// => `${parent}/acme-secrets/passwords.txt`  (NOT null, even though it is
//     outside `root` — the prefix check incorrectly treats it as contained)
```
