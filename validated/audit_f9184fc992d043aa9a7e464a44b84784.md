### Title
Secret-dependent table indexing in "constant-time" `multiexp` leaks FROST nonce scalars via cache timing - (File: crypto/multiexp/src/straus.rs)

### Summary
`multiexp` is documented and used as the constant-time path for secret scalars (FROST nonce derivation/combination calls it), but both of its secret-scalar backends — `straus()` and `pippenger()` — index lookup tables with a secret-derived index instead of using `conditional_select`. `prep_bits()` carefully uses `black_box` to prevent compiler-induced secret-dependent branches (the exact Botan CVE-2024-50382 failure mode), yet `straus.rs:43` (`tables[s][usize::from(groupings[s][b])]`) and `pippenger.rs:26` (`buckets[usize::from(bits[p][n])]`) perform data-dependent memory access that reveals each window of the secret scalar through cache-line timing. ### Finding Description
The bug class in CVE-2024-50382 is secret-dependent data flow where a constant-time operation was required — the compiler materialized a branch on a secret carry bit instead of an XOR. Serai's codebase contains the structurally identical defect, but at the source level: the scalar-index lookups in `multiexp`'s non-vartime algorithms are secret-dependent memory accesses. Every other sensitive path in the codebase (`Scalar::pow` in `crypto/dalek-ff-group/src/lib.rs:225-231`, `Point::mul` in `crypto/ed448/src/point.rs:258-266`) correctly uses `bits.ct_eq(&i)` + `conditional_select` over all 16 table entries. Only `straus()` and `pippenger()` index directly. `groupings[s][b]` is literally a `window`-bit chunk of the secret scalar; the touched cache line discloses it. [4](#0-3) [1](#0-0) 

Note that `Algorithm::Single` (`pairs[0].1 * pairs[0].0`) dispatches to `Group::mul`, which uses the constant-time `conditional_select` ladder — so single-scalar secret multiplication is safe; the leak begins at 2+ pairs where `straus`/`pippenger` run. [5](#0-4) 

### Impact Explanation
`multiexp` is invoked on secret scalars during FROST signing — `crypto/frost/src/sign.rs` and `crypto/frost/src/nonce.rs` call it for the nonce combination `base + rho * actual` — and in `crypto/dkg/musig/src/lib.rs`. An unprivileged party who can request signatures on chosen messages (a normal FROST co-signer or anyone able to trigger signing of attacker-influenced message bytes) induces the signer to run `straus`/`pippenger` over secret nonce scalars. A co-located observer (shared-tenant cache probe, or a malicious participant running code on the same host in realistic validator deployments) recovers the scalar window indices — i.e., the nonce bits themselves — from cache-line access patterns. Repeated nonce leakage across signatures yields FROST signing-key share recovery, equivalent to the "key material disclosure" impact of the original GHASH finding. Severity matches Medium (C:H, AC:H side channel, no integrity/availability impact). [6](#0-5) 

### Likelihood Explanation
Medium. Exploitation requires a cache-timing observation channel against the signing host (cross-VM side channel or co-resident process), which is the same AC:H bar as CVE-2024-50382, but there is no mitigation: the secret-indexed lookup is unconditional on every multi-scalar `multiexp` call with ≥2 pairs, and every FROST signature satisfies that condition. No PoC below requires modifying Serai — only observing it.

### Recommendation
In `straus()`, replace `tables[s][usize::from(groupings[s][b])]` with a `conditional_select` sweep over all `2^window` entries (as `Point::mul` does), or accumulate into each table entry's cache line unconditionally. In `pippenger()`, bucket assignment `buckets[idx] += pairs[p].1` is inherently index-dependent; either perform the bucket accumulation via per-bucket conditional masks (`buckets[i] = conditional_select(buckets[i], buckets[i] + pairs[p].1, idx.ct_eq(i))`) or document/route secret-scalar callers to a scalar multiplication path that never data-indexes. Keep the `u8_from_bool`/`black_box` hardening in `prep_bits`. Alternatively, restrict `multiexp` to public scalars and use `Group::mul` chains for secrets — but an explicit constant-time path is the correct fix.

### Proof of Concept
```rust
// Conceptual: for a signer computing multiexp(&[(d0, P0), (d1, P1)])
// via straus(window=3), groupings[s][b] holds 3-bit chunks of d_s.
// straus.rs:43 indexes tables[s][chunk] — each of the 8 entries is a
// distinct cache line (G is ~64-128 bytes). A Prime+Probe observer on
// the same cache set recovers chunk = 3 bits of the secret scalar per
// observation point; iterating b over ~86 windows yields the full
// 256-bit nonce contribution. Same for pippenger.rs:26 bucket index.
// With leaked nonces across N FROST sign() calls on attacker-chosen
// messages, standard techniques recover the key share.
```
I could not fully enumerate every `multiexp` call site in `frost/src/sign.rs`/`nonce.rs`/`musig` due to iteration limits, but the presence of `multiexp` calls in those files combined with the unconditional secret-indexed lookups in `straus`/`pippenger` establishes the reachable defect.
