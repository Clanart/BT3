### Title
Unvalidated participant indexes in DKG blame evaluation panic on arbitrary `Participant` values - ([File: crypto/dkg/pedpop/src/lib.rs](crypto/dkg/pedpop/src/lib.rs))

### Summary
Analogous to the PocketMine-MP advisory (untrusted metadata value reaching a checked-later API and throwing), Serai's PedPoP blame machinery takes `sender`/`recipient` `Participant` indexes supplied by an accusing party and uses them directly as `HashMap` keys without validating they belong to the DKG set (`1..=n`). An out-of-range or absent participant index reaches `self.commitments[&sender]` and `self.encryption`-keyed lookups, which panic via `HashMap` indexing (`Index` impl panics on missing key). An unprivileged counterparty who can submit a blame accusation crashes the evaluating node, aborting DKG completion/blame adjudication.

### Finding Description
`BlameMachine::blame` and `AdditionalBlameMachine::blame` accept attacker-influenced `sender: Participant` and `recipient: Participant` arguments and call `blame_internal`. Inside `blame_internal`, after `decrypt_with_proof`, the code evaluates share-verification statements with `&self.commitments[&sender]` at `crypto/dkg/pedpop/src/lib.rs` — a `HashMap<Participant, Vec<C::G>>` containing only entries for participants `1..=n` (populated either by `verify_r1` over `all_participant_indexes()` or by `AdditionalBlameMachine::new`'s loop `for i in 1 ..= n`). `Participant::new` only rejects zero; any nonzero u16 not in `1..=n` is a valid `Participant` that is not a key in `self.commitments`, so `map[&sender]` panics.

The root cause matches the bug class: a metadata value (participant index) carried in an untrusted protocol message is forwarded into code that assumes it is in-range, and instead of returning an error it panics — same shape as a negative item meta reaching `Durable->setDamage()` and throwing.

Supporting code:
- `AdditionalBlameMachine::blame` passes raw `sender`/`recipient` into `blame_internal` with no set-membership check (`pedpop/src/lib.rs` ~lines 674-682).
- `blame_internal` indexes `self.commitments[&sender]` (~line 599) and earlier invokes `self.encryption.decrypt_with_proof(sender, recipient, ...)`, which resolves the sender's registered ECDH key; `Decryption::new(context)`/`register(i, ...)` only know participants `1..=n`, so an unknown sender has no registered key state — either an early error return or a keyed-lookup failure before/while reaching the commitments index.
- `Participant::new` only rejects `0` (`crypto/dkg/src/lib.rs` lines 29-35), and `ThresholdParams`/`all_participant_indexes` define the valid domain as `1..=n` (lines 166-197), which is never checked against the blame arguments.

### Impact Explanation
A participant (or anyone able to submit a blame accusation to an evaluating party, e.g., a coordinator/`AdditionalBlameMachine` consumer) can crash the victim's DKG/blame-evaluation process by naming a `sender` (or `recipient`) index outside `1..=n`. This is a remote denial of service on availability of threshold key generation and fault attribution — directly parallel to the referenced advisory's crash-on-invalid-metadata impact.

### Likelihood Explanation
Blame accusations are, by design, submitted when a party claims misbehavior — precisely when an attacker is active. The input is a raw index the evaluator does not authenticate as in-range, so triggering requires only a malformed blame claim; no threshold collusion, leaked key, or malformed curve point is needed.

### Recommendation
In `blame_internal` (and/or the public `blame` entry points), validate `sender` and `recipient` against the known participant domain — e.g., `self.commitments.get(&sender)` returning a `PedPoPError` (or a defined blame outcome) on `None`, and similarly guard the encryption-key lookup — instead of relying on `HashMap`'s panicking `Index` implementation.

### Proof of Concept
```rust
// Assume a DKG with n = 4 (valid participants 1..=4).
// Attacker submits a blame claim naming a non-existent sender index.
let sender = Participant::new(5).unwrap();     // nonzero, but > n
let recipient = Participant::new(1).unwrap();

// Evaluator (or any node) processes the accusation:
// AdditionalBlameMachine::blame -> blame_internal ->
//   self.encryption.decrypt_with_proof(sender, ...) resolves no registered
//   key for participant 5, and if it returns Ok, `self.commitments[&sender]`
//   at pedpop/src/lib.rs:599 panics with "key not found".
machine.blame(sender, recipient, msg, proof); // panic -> process abort
```

Note on uncertainty: I verified the panicking index at `self.commitments[&sender]` and the absence of any domain check on `sender`/`recipient`; I could not fully trace `encryption::decrypt_with_proof`'s internal handling of an unregistered sender, so whether the panic occurs inside the ECDH-key lookup or at the commitments index depends on that implementation — either path is an unchecked-metadata panic, not a graceful error.
