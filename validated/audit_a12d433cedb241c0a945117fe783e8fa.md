### Title
Cross-shop session hijack via unauthenticated `shop` query parameter in `EnsureInstalled` - ([File: app/controllers/concerns/shopify_app/ensure_installed.rb])

### Summary
In the legacy (non `use_new_embedded_auth_strategy`) flow, `EnsureInstalled#current_shopify_domain` derives the active shop purely from `params[:shop]` after only a format check, and `installed_shop_session` loads that shop's stored offline session/access token from `SessionRepository` with no cryptographic verification that the request actually originated from that shop's Shopify Admin session. Any anonymous client can therefore cause the app to activate and use a victim shop's offline access token by simply setting `shop=victim.myshopify.com` on any `EnsureInstalled`-protected route.

### Finding Description
The before_action chain for the legacy path is: `check_shop_domain` → `current_shopify_domain` → `check_shop_known` → `installed_shop_session`. [1](#0-0) 

`current_shopify_domain` only calls `ShopifyApp::Utils.sanitize_shop_domain(params[:shop])`, which normalizes/validates the *format* of the domain string but performs no signature, HMAC, or token check tying it to the actual requester: [2](#0-1) 

`installed_shop_session` then loads the shop's offline session straight from that unverified domain: [3](#0-2) 

`check_shop_known` assigns this session to `@shop` and only redirects if no session exists for that domain — it does not redirect if a session for an *arbitrary but different* domain than the true caller exists: [4](#0-3) 

The only other gate, `validate_non_embedded_session`, does not authenticate the caller either: it simply makes an Admin API call using the already-loaded (potentially victim's) session/token, and only redirects to login if that token itself has become invalid (HTTP 401). It does not verify that the request originated from that shop's authenticated Admin context — `loaded_directly_from_admin?` merely checks `params[:embedded] == "1"`, which is also attacker-controllable: [5](#0-4) [6](#0-5) 

Unlike `ShopifyApp::LoginProtection` (used by the modern/token-exchange flow), which derives the session from a verified ID token or encrypted session cookie via `current_shopify_session` / `load_current_session` (`ShopifyAPI::Utils::SessionUtils.current_session_id`), `EnsureInstalled`'s legacy branch has no equivalent verification step — no HMAC check on the query string, no `shopify_id_token` validation, no comparison against a signed session id. [7](#0-6) 

Because the controller trusts `params[:shop]` directly to key into `SessionRepository.retrieve_shop_session_by_shopify_domain`, any request bearing a valid-looking shop domain for which the app happens to have a stored offline session will have that shop's session activated and available to the rest of the controller action (e.g., for making authenticated Admin API calls on the victim's behalf), regardless of who is actually making the HTTP request.

### Impact Explanation
An unauthenticated/unrelated attacker can force the app to load and act using another merchant's offline access token by controlling only the `shop` query parameter, resulting in cross-shop session confusion / unauthorized use of a victim's Shopify access token — matching Shopify's "Broken Authentication" / "Cross-shop data access via session confusion" impact class.

### Likelihood Explanation
Preconditions: the host app must use `EnsureInstalled` without `use_new_embedded_auth_strategy` (the legacy flow branch), and the victim shop must already have an installed offline session in `SessionRepository` — a very common real-world configuration for older Shopify apps. No secret, token, or victim interaction is required beyond knowing/guessing the victim's `myshopify.com` domain, which is often discoverable/public. This makes the issue highly feasible and repeatable for any protected route using this concern.

### Recommendation
Do not derive the active shop/session purely from the unauthenticated `params[:shop]`. Bind the session to a verified source of truth: require and validate a Shopify-signed session token (`shopify_id_token`/JWT) or verify the request's HMAC/signature (as done for OAuth callbacks and webhooks) before calling `retrieve_shop_session_by_shopify_domain`, and reject the request if the verified shop does not match `params[:shop]` — mirroring the `LoginProtection#current_shopify_session` / `session_shop_conflicts_with_params` pattern already implemented for the non-legacy flow.

### Proof of Concept
```ruby
# test/controllers/concerns/ensure_installed_test.rb (illustrative)
test "attacker can load victim's session via unauthenticated shop param" do
  victim_domain = "victim-shop.myshopify.com"
  ShopifyApp::SessionRepository.store_shop_session(
    ShopifyAPI::Auth::Session.new(shop: victim_domain, access_token: "victim-token")
  )

  # Attacker sends request with no id_token, no HMAC, no prior auth for victim_domain
  get "/protected_route", params: { shop: victim_domain, embedded: "1" }

  # EXPECTED (secure): request should be rejected/redirected because attacker
  # never proved control of victim_domain via signed token/HMAC.
  # ACTUAL: @installed_shop_session / @shop is populated with victim's stored
  # offline session and access_token "victim-token", and the controller action
  # executes using it.
  assert_equal "victim-token", controller.installed_shop_session.access_token
end
```
This demonstrates that `installed_shop_session` returns the victim's offline session solely because `params[:shop]` names the victim's domain, with no verification that the request actually came from that shop's authenticated Admin/App Bridge context.
