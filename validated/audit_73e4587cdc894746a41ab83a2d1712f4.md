### Title
Division-by-zero panic in reward distribution when a proposer's staking and consensus-liquidity stake are both zero - (File: kaiax/reward/impl/getter.go, kaiax/staking/staking_info.go)

### Summary
The staking/reward accounting for the Prague consensus-liquidity (CL) feature can panic with a division-by-zero when a validator's own CN staking amount and its associated CL staking amount are both zero at the same time. This mirrors the referenced report's root cause (an unguarded division whose denominator can become zero through normal, non-malicious use), except here the trigger is a legitimate staker/validator withdrawing/unstaking rather than a direct token transfer.

### Finding Description
`consolidatedNode.Split` computes `totalAmount = StakingAmount + CLStakingAmount` and unconditionally divides by it: [1](#0-0) 

This function is invoked from `specWithProposerAndFundsFlex` and `specWithProposerAndFunds` for the block **proposer**, gated only on `cn.CLStakingInfo != nil` — there is no check that `cn.StakingAmount + cn.CLStakingInfo.CLStakingAmount > 0`: [2](#0-1) [3](#0-2) 

By contrast, the sibling functions `assignStakingRewards` / `assignStakingRewardsFlex` only call `Split` inside a branch that is only reached when the summed stake exceeds `minStake`/`threshold`, so the divisor there is provably non-zero: [4](#0-3) 

The proposer path has no equivalent `minStake` guard before calling `Split`. `CLStakingAmount` and `StakingAmount` are both derived from on-chain state (AddressBook / CLRegistry contracts) and are rounded down to whole KAIA units: [5](#0-4) [6](#0-5) 

If a node is listed in the AddressBook with a rounded-down staking amount of 0 (e.g., staked balance below 1 KAIA) while also being registered in the CL registry with a rounded-down CL amount of 0 (e.g., the CL pool currently holds no delegated stake, which any staker can cause by withdrawing/unstaking), then `StakingAmount == 0 && CLStakingAmount == 0` for that node's `consolidatedNode`. If this node becomes the block proposer, `cn.Split(proposer)` executes `new(big.Int).Div(clAmount, totalAmount)` with `totalAmount == 0`, which panics in Go's `math/big`.

### Impact Explanation
A panic inside `FinalizeState`/deferred-reward computation, which runs on every full node processing that block, would crash or halt block processing on all honest nodes simultaneously (or diverge behavior if only some nodes hit the code path), which is a severe availability/consensus risk — analogous to the referenced report's "unusable contract" outcome but at the chain-liveness level rather than a single contract. This qualifies as a state-divergence / chain-halting condition, warranting Medium-to-High severity depending on how easily the zero-stake/zero-CL-stake condition can be produced and how often the affected node is selected as proposer.

### Likelihood Explanation
Reaching this exact state requires: (1) a validator's CN stake to round down to 0 KAIA, and (2) its CL staking pool balance to also round down to 0 KAIA, and (3) that validator being selected as the block proposer. Whether a listed AddressBook validator can have effectively-zero CN stake, and whether the permissionless/eligibility filters (e.g., `IsRewardEligible`) would exclude such nodes before they can be selected as proposer, was not verifiable within the available index/tool access. This uncertainty means the practical likelihood could not be fully confirmed — it should be validated against `valset` proposer-eligibility rules and `AddressBookV2`/CLRegistry minimum-stake enforcement before treating this as fully proven.

### Recommendation
Add an explicit zero-denominator guard in `consolidatedNode.Split` (return `(amount, big.NewInt(0))` or `(big.NewInt(0), big.NewInt(0))` when `totalAmount.Sign() == 0`), independent of the `minStake`/eligibility filtering performed by callers, so that the proposer-reward code paths (`specWithProposerAndFunds`, `specWithProposerAndFundsFlex`) cannot panic regardless of how staking/CL amounts round down.

### Proof of Concept
Conceptual reproduction (not independently executed against a live chain):
1. A validator node is registered in the AddressBook with staking amount that rounds down to 0 KAIA (`StakingAmounts[i]/1e18 == 0`), per `parseCallResult`/`parsePermissionlessCallResult` rounding. [7](#0-6) 
2. The same node's reward address also has a CL pool registered whose staking amount currently rounds down to 0 KAIA (e.g., after all CL delegators have withdrawn), producing a `CLStakingInfo` entry with `CLStakingAmount == 0`. [5](#0-4) 
3. This node is selected as block proposer (`config.Rewardbase` matches `cn.RewardAddr`).
4. During deferred reward calculation, `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` calls `cn.Split(proposer)`. [8](#0-7) 
5. Inside `Split`, `totalAmount = 0 + 0 = 0`, and `clAmount.Div(clAmount, totalAmount)` panics with "division by zero". [9](#0-8)

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```

```go
// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
```
