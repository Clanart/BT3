### Title
Tokenfactory denom allow-list restriction is enforced only in the bank `MsgSend`/`MultiSend` message servers, not in the underlying `SendCoins`/`InputOutputCoins` keeper methods, letting other callers (precompiles, IBC, modules) bypass the sender/receiver allow-list - (File: sei-cosmos/x/bank/keeper/send.go)

### Summary
The GitLab CVE (BIT-gitlab-2025-1540 / CVE-2025-1540) is a case where an authorization/visibility restriction was correctly enforced in one code path but silently skipped in another due to attribute/flow misconfiguration, letting a restricted user reach data they should not. The closest reachable analog in sei-chain is the tokenfactory denom `AllowList` restriction: it is checked explicitly inside the `x/bank` `MsgServer.Send`/`MultiSend` handlers via `IsInDenomAllowList`, but the enforcement is not embedded in the `BaseSendKeeper.SendCoins` / `InputOutputCoins` primitives themselves [1](#0-0) . Any other caller that invokes `SendCoins` directly instead of going through the `Msg` handler bypasses the allow-list entirely.

### Finding Description
`x/bank`'s `BaseSendKeeper` defines `IsInDenomAllowList` as a standalone helper that must be explicitly invoked by callers; it is not woven into `SendCoins` [2](#0-1) . The only place in `sei-cosmos/x/bank` that calls `IsInDenomAllowList` is the `MsgServer.Send` handler, which checks both sender and receiver against the allow list before calling `k.SendCoins` [1](#0-0) .

The bank EVM precompile's `send` method, however, calls `p.bankKeeper.SendCoins` directly — bypassing the `MsgServer.Send` entry point and therefore the allow-list check entirely: [3](#0-2) . The precompile only validates that the caller is the registered ERC20 pointer for the denom, not that the sender/receiver are permitted by the denom's tokenfactory `AllowList`.

This mirrors the GitLab bug class exactly: the "authorization" (allow-list) attribute is properly enforced on one entry point (the CLI/REST `Msg` path) but is misconfigured/omitted on another reachable entry point (the EVM precompile path), letting an actor who should be blocked from moving a restricted tokenfactory denom do so anyway.

### Impact Explanation
Tokenfactory `AllowList` is a security control used to restrict transfers of certain denoms to a specific set of addresses (e.g., KYC'd addresses or a permissioned pool for a regulated asset) [4](#0-3) . If the EVM ERC20 pointer for such a denom exists, any EVM caller holding the pointer-wrapped balance can call `send` on the bank precompile to move the underlying native coin to or from addresses that are explicitly excluded from the allow list, defeating the restriction. This is an unauthorized transfer via a precompile — funds move to/from addresses the denom admin intentionally blocked, which is a direct authorization bypass with fund-movement consequences for permissioned denoms.

### Likelihood Explanation
Reachable by any account holding tokens of an allow-listed tokenfactory denom that also has an ERC20 native pointer registered (a normal, permissionless action any user can request via the pointer precompile). No special privilege beyond being the registered pointer contract (itself just an on-chain construct anyone can create by calling `AddNative`) is required to trigger `send`, making this reachable from an ordinary EVM transaction.

### Recommendation
Move the `IsInDenomAllowList` (and `BlockedAddr`) enforcement into `BaseSendKeeper.SendCoins`/`InputOutputCoins` themselves (or at minimum add explicit allow-list checks inside the bank precompile's `send` before calling `SendCoins`), so that every code path that moves tokenfactory-restricted denoms — not just the `Msg` server — is subject to the same authorization checks.

### Proof of Concept
1. Denom admin creates a tokenfactory denom and calls `SetDenomAllowList` restricting transfers to a fixed address set, excluding address `X` [5](#0-4) .
2. Anyone registers an ERC20 native pointer for that denom via the pointer precompile's `AddNative` [6](#0-5) .
3. Address `X` (excluded from the allow list) holds/receives the wrapped ERC20 balance and calls the bank precompile's `send(from, to, denom, amount)` directly from EVM. The precompile validates only that `caller` equals the registered pointer, then calls `bankKeeper.SendCoins` unconditionally [3](#0-2) , moving funds to/from `X` even though the standard `MsgSend` path would have rejected this with "not allowed to send/receive funds" [7](#0-6) .

// IsInDenomAllowList checks if the given address is allowed to send the given coins.
// The check is performed only fot token factory denoms. For each token factory denom,
// it checks if there is allow list for the given denom. If there is no allow list,
// the address is allowed to send the coins. If there is an allow list, the address is
// allowed to send the coins only if it is in the allow list.
func (k BaseSendKeeper) IsInDenomAllowList(ctx sdk.Context, addr sdk.AccAddress, coins sdk.Coins, cache map[string]AllowedAddresses) bool {
	for _, coin := range coins {
		// Skip if denom does not contain the token factory prefix
		if !strings.HasPrefix(coin.Denom, TokenFactoryPrefix) {
			continue
		}

		allowedAddresses := k.getAllowedAddresses(ctx, cache, coin.Denom)
		// skip if there is no allow list for the denom
		if len(allowedAddresses.set) == 0 {
			continue
		}

		if !allowedAddresses.contains(addr) {
			return false
		}
	}
	return true
}

func (p PrecompileExecutor) send(ctx sdk.Context, caller common.Address, method *abi.Method, args []interface{}, value *big.Int, readOnly bool) ([]byte, error) {
	if readOnly {
		return nil, errors.New("cannot call send from staticcall")
	}
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, err
	}

	if err := pcommon.ValidateArgsLength(args, 4); err != nil {
		return nil, err
	}
	denom := args[2].(string)
	if denom == "" {
		return nil, errors.New("invalid denom")
	}
	pointer, _, exists := p.evmKeeper.GetERC20NativePointer(ctx, denom)
	if !exists || pointer.Cmp(caller) != 0 {
		return nil, fmt.Errorf("only pointer %s can send %s but got %s", pointer.Hex(), denom, caller.Hex())
	}
	amount := args[3].(*big.Int)
	if amount.Cmp(utils.Big0) == 0 {
		// short circuit
		return method.Outputs.Pack(true)
	}
	senderSeiAddr, err := p.accAddressFromArg(ctx, args[0])
	if err != nil {
		return nil, err
	}
	receiverSeiAddr, err := p.accAddressFromArg(ctx, args[1])
	if err != nil {
		return nil, err
	}

	if err := p.bankKeeper.SendCoins(ctx, senderSeiAddr, receiverSeiAddr, sdk.NewCoins(sdk.NewCoin(denom, sdk.NewIntFromBigInt(amount)))); err != nil {
		return nil, err
	}

	return method.Outputs.Pack(true)
}

func (p PrecompileExecutor) AddNative(ctx sdk.Context, method *ethabi.Method, caller common.Address, args []interface{}, value *big.Int, evm *vm.EVM, hooks *tracing.Hooks) (ret []byte, remainingGas uint64, err error) {
	if err := pcommon.ValidateNonPayable(value); err != nil {
		return nil, 0, err
	}
	if err := pcommon.ValidateArgsLength(args, 1); err != nil {
		return nil, 0, err
	}
	token := args[0].(string)
	metadata, metadataExists := p.bankKeeper.GetDenomMetaData(ctx, token)
	if !metadataExists {
		return nil, 0, fmt.Errorf("denom %s does not have metadata stored and thus can only have its pointer set through gov proposal", token)
	}
	name := metadata.Name
	symbol := metadata.Symbol
	var decimals uint8
	for _, denomUnit := range metadata.DenomUnits {
		if denomUnit.Exponent > uint32(decimals) && denomUnit.Exponent <= math.MaxUint8 {
			decimals = uint8(denomUnit.Exponent)
			name = denomUnit.Denom
			symbol = denomUnit.Denom
			if len(denomUnit.Aliases) > 0 {
				name = denomUnit.Aliases[0]
			}
		}
	}
	contractAddr, err := p.evmKeeper.UpsertERCNativePointer(ctx, evm, token, utils.ERCMetadata{Name: name, Symbol: symbol, Decimals: decimals})
	if err != nil {
		return nil, 0, err
	}

	ret, err = method.Outputs.Pack(contractAddr)
	remainingGas = pcommon.GetRemainingGas(ctx, p.evmKeeper)
	return
}
