### Title
Symlinked working-directory files bypass repo boundary via `readPartialFile`, letting diff expansion disclose off-repo file content - (File: `app/src/ui/diff/syntax-highlighting/index.ts`)

### Summary
`getNewFileContent` reads a working-directory file's on-disk content with `readPartialFile`, which uses `fs.createReadStream(path, {start, end})`. Node's stream/file APIs follow symlinks by default (no `O_NOFOLLOW`). If the repo-tracked/untracked entry at that path is actually a symlink (git tracks symlinks as mode `120000` blobs whose content is the target path string), the on-disk checkout is a real OS-level symlink, and `readPartialFile` transparently follows it and reads whatever it points to - even if that target is completely outside the repository. [2](#0-1) [3](#0-2) 

### Finding Description
`getFileContents` computes `canBeExpanded` purely from the truncated byte count it reads (`newContents.length <= MaxDiffExpansionNewContentLength`, capped at `MaxHighlightContentLength` = 1MB): [4](#0-3) 

Because `readPartialFile` only ever reads the first ~1MB of whatever `createReadStream` resolves to, an attacker doesn't need the off-repo target to be small — only its first ~1MB (split into lines) needs to fit under the threshold for `canBeExpanded` to be `true`. This matches the "large off-repo file, size check still passes" scenario in the question, since the check never validates true file size or that the path stays within the repository — it only inspects the truncated buffer already read.

The unrestricted `newContents` is then fed straight into the diff-expansion logic when the user clicks "Show more"/"Expand whole file": [5](#0-4) [6](#0-5) 

Notably, git's own diff machinery treats symlinks safely: a normal (non-expanded) diff of a symlink shows the blob content (i.e. the target path string), not the resolved file. It is specifically Desktop's fs-level read in `readPartialFile`/`getNewFileContent` (used for syntax highlighting and diff expansion) that bypasses that safety and dereferences the symlink. I found no `lstat`/symlink-type check anywhere in `status.ts`, `diff.ts`, or the app-store conflict-gathering code that would prevent this — `grep` for `isSymbolicLink`/`lstat` in the production `app/src` tree returned no hits outside of `custom-integration.ts`, which is unrelated.

### Impact Explanation
An attacker who controls repository content (a branch/commit introducing a symlink such as `secret -> /Users/victim/.ssh/id_rsa`) can, once that symlink exists as a `WorkingDirectoryFileChange` (e.g. as an uncommitted/untracked entry, or as a conflicted file surfaced during a merge/rebase), get Desktop to read and display up to ~1MB of arbitrary off-repo file content in the diff pane when the user expands the diff or when syntax highlighting kicks in. This is a "read outside the repo" issue per the stated valid-impact list. The most concerning escalation path would be if this same working-directory content-reading code is reused to build the Copilot conflict-resolution prompt (`app/src/lib/copilot-conflict-context.ts`, which separately reads files via `fs/promises.readFile` combined with `resolveWithin`), since that would transmit off-repo content to an external Copilot API call — but I was not able to fully confirm within the available context whether `resolveWithin` guards against symlink dereferencing (as opposed to just string-based `..`-escape checks), so that specific exfiltration path remains unverified. [7](#0-6) 

### Likelihood Explanation
Requires the symlink to actually exist as a real OS symlink on the checkout, which needs macOS/Linux (or Windows with Developer Mode/`SeCreateSymbolicLinkPrivilege`), and requires the symlinked path to appear as a `WorkingDirectoryFileChange` (untracked/modified/conflicted) rather than only a `CommittedFileChange` (which instead safely uses `git show`/`getPartialBlobContents`). This narrows realistic triggers to merge/rebase/cherry-pick conflicts or freshly-added-but-uncommitted symlinks, making it a plausible but not trivially universal path.

### Recommendation
Before calling `readPartialFile` on a `WorkingDirectoryFileChange` path in `getNewFileContent`, `lstat` the path and refuse to read (or explicitly reject) if it is a symlink whose resolved real path (via `fs.realpath`) falls outside `repository.path`. Apply the equivalent check anywhere else on-disk reads are done for diff/expansion/Copilot-context purposes.

### Proof of Concept
1. Create a repo containing (as an untracked working-directory entry) a symlink `leak -> /etc/passwd` (or a large sensitive file whose first 1MB is targeted).
2. Open the repo in Desktop; view "Changes" for `leak`, which is small enough that `canBeExpanded` becomes `true` because only the first ~1MB of the target is read.
3. Click "Expand whole file" / "Show more" in the diff view — the panel renders the resolved contents of `/etc/passwd` rather than repo-scoped data, confirming `readPartialFile`'s symlink-following read crosses the repository boundary. [3](#0-2)

async function getNewFileContent(
  repository: Repository,
  file: ChangedFile
): Promise<Buffer | null> {
  if (file.status.kind === AppFileStatusKind.Deleted) {
    return null
  }

  if (file instanceof WorkingDirectoryFileChange) {
    return readPartialFile(
      Path.join(repository.path, file.path),
      0,
      MaxHighlightContentLength - 1
    )
  } else if (file instanceof CommittedFileChange) {
    return getPartialBlobContents(
      repository,
      file.commitish,
      file.path,
      MaxHighlightContentLength
    )
  }

  return assertNever(file, 'Unknown file change type')
}

export async function getFileContents(
  repo: Repository,
  file: ChangedFile
): Promise<IFileContents> {
  const [oldContents, newContents] = await Promise.all([
    getOldFileContent(repo, file).catch(e => {
      log.error('Could not load old contents for syntax highlighting', e)
      return null
    }),
    getNewFileContent(repo, file).catch(e => {
      log.error('Could not load new contents for syntax highlighting', e)
      return null
    }),
  ])

  return {
    file,
    oldContents: oldContents?.toString('utf8').split(/\r?\n/) ?? [],
    newContents: newContents?.toString('utf8').split(/\r?\n/) ?? [],
    canBeExpanded:
      newContents !== null &&
      newContents.length <= MaxDiffExpansionNewContentLength,
  }

export async function readPartialFile(
  path: string,
  start: number,
  end: number
): Promise<Buffer> {
  return await new Promise<Buffer>((resolve, reject) => {
    const chunks = new Array<Buffer>()
    let total = 0

    createReadStream(path, { start, end })
      .on('data', (chunk: Buffer) => {
        chunks.push(chunk)
        total += chunk.length
      })
      .on('error', reject)
      .on('end', () => resolve(Buffer.concat(chunks, total)))
  })
}

export function expandWholeTextDiff(
  diff: ITextDiff,
  newContentLines: ReadonlyArray<string>
): ITextDiff | undefined {
  let result = diff

  // The logic is to keep expanding the first hunk until it's the only one.
  // First expand the first hunk up, and then down as many times as possible.
  // If there is only one hunk, just expand it once up.
  while (
    result.hunks.length > 1 ||
    (result.hunks.length === 1 &&
      result.hunks[0].expansionType === DiffHunkExpansionType.Up)
  ) {
    const firstHunk = result.hunks[0]

    const partialResult = expandTextDiffHunk(
      result,
      firstHunk,
      firstHunk.expansionType === DiffHunkExpansionType.Up ? 'up' : 'down',
      newContentLines,
      newContentLines.length
    )

    if (partialResult === undefined) {
      return
    }

    result = partialResult
  }

  return result
}
