Based on my investigation, the strongest local analog is in the Tron variant of the Intent Gateway.

### Title
Withdraw path lacks zero-amount guard, allowing a revert-on-zero-transfer token to permanently lock escrowed funds and finalized order state - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron `IntentGatewayV2.sol`'s `withdraw()` function transfers every token listed in a `WithdrawalRequest` without checking whether the amount is non-zero, unlike the parallel implementation in `IntentsBase.sol::_withdraw()`, which explicitly `continue`s past zero-amount legs.

### Finding Description
`cancelOrder`, `onAccept` (for `RedeemEscrow`/`RefundEscrow`), and `onGetResponse` all route through `withdraw(WithdrawalRequest memory body, bool isRefund)` [1](#0-0) . That loop calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for every entry in `body.tokens` with no `if (amount == 0) continue;` guard [2](#0-1) .

Compare this to the newer `IntentsBase.sol::_withdraw()`, which explicitly skips zero-amount legs before touching escrow or issuing a transfer: `if (amount == 0) continue;` [3](#0-2) . The Tron contract's `withdraw()` is missing this guard entirely, and unconditionally marks the order finalized (`_filled[body.commitment] = beneficiary`) at the top of the function before any transfer happens [4](#0-3) .

If any token in a multi-input order's escrow entry can legitimately be zero at withdrawal time (e.g., a token whose full amount has already been consumed/adjusted, or a caller-influenced `RedeemEscrow`/`RefundEscrow` message body carrying a zero-amount `TokenInfo` entry for one of several input tokens), and that token is a standard revert-on-zero-transfer ERC-20 (a known class explicitly called out and fixed for in the referenced Sherlock report), the `token.call(...)` will still succeed at the low-level call layer only if the token reverts; a reverting `transfer(x, 0)` bubbles up as `success == false`, and the code path then reverts with `TransferFailed()` [5](#0-4) . This aborts the entire `withdraw()` call — including the escrow decrement for all other (non-zero) tokens in the same request and the finalization marker — since Solidity state changes revert atomically. The user/beneficiary can never successfully cancel or have their proceeds released for that commitment, because every retry will hit the same zero-amount leg and revert again.

### Impact Explanation
This matches the exact bug class from the external report: a revert-on-zero-transfer token combined with a code path that can legitimately compute a zero transfer amount causes permanent fund lock — the same "seller's funds remain locked in the system" impact. Here, escrowed user/solver funds tied to a multi-token order become permanently unrecoverable because `withdraw()` can never complete for that commitment.

### Likelihood Explanation
Likelihood is constrained by whether a legitimate flow can actually produce a zero-amount entry in `body.tokens` for the Tron contract (I could not fully confirm a same-chain/cross-chain path that constructs a `WithdrawalRequest` with a zero amount for one of several inputs within the available context — `order.inputs[i].amount == 0` is rejected at `placeOrder` time via `if (order.inputs[i].amount == 0) revert InvalidInput();`, and same-chain/cross-chain cancel build `tokens: order.inputs` directly from the original order). The missing-guard code is a real and verifiable inconsistency with the audited/fixed sibling implementation in `IntentsBase.sol`, but I was not able to conclusively demonstrate, from the code retrievable in this session, an unprivileged, single-transaction path that populates a zero-amount `TokenInfo` in an otherwise non-empty `body.tokens` array for the Tron gateway. This is a defense-in-depth gap that mirrors a previously fixed real-world vulnerability class, but full exploitability confirmation would require reviewing any additional call sites that construct `WithdrawalRequest.tokens` (e.g., partial-fill or dust-adjustment logic) that may not be present in the excerpts retrieved.

### Recommendation
Add the same zero-amount skip used in `IntentsBase.sol::_withdraw()` to the Tron `withdraw()` function:
```solidity
uint256 amount = body.tokens[i].amount;
if (amount == 0) { unchecked { ++i; } continue; }
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
```
This prevents a revert-on-zero-transfer token from blocking finalization and escrow release for the other legs of the same withdrawal request, aligning the Tron contract with the guard already present in the main `IntentsBase.sol` implementation.

### Proof of Concept
Not independently constructible from the code retrieved in this session — I could not confirm a call path that produces a zero-amount `TokenInfo` entry inside `body.tokens` for the Tron `IntentGatewayV2.withdraw()` function. If such a path exists (e.g., via a multi-token order where one token's escrow is reduced to exactly zero by an intermediate operation before `withdraw()` is invoked), the PoC would be: place an order with two input tokens, one of which is a strict revert-on-zero-transfer ERC-20; drive that token's remaining escrowed amount to zero through the legitimate flow; call `cancelOrder`/trigger `RedeemEscrow`/`RefundEscrow`; observe `withdraw()` reverts with `TransferFailed()` on every subsequent attempt, permanently locking the other token's escrow and the fee refund for that commitment.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
