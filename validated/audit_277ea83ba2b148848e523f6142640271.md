### Title
Panic (node crash / DoS) in `consoleLog.decode` via crafted `string`/`bytes` offset causing negative slice index - (File: blockchain/vm/contracts.go)

### Summary
The `consoleLog` precompiled contract, used to emulate Hardhat's `console.log`, decodes ABI-like parameters from fully attacker-controlled EVM calldata. The offset ("start") value for dynamic `string`/`bytes` arguments is derived from a `big.Int` via `.Int64()` without validating that the value fits safely in a non-negative `int`, and the subsequent bounds check can be bypassed when this value becomes negative, leading to a Go runtime panic ("slice bounds out of range") when the transaction sender/contract deployer/caller sends this crafted precompile input, analogous to the unchecked type/size parsing in CVE-2021-46549 (Cesanta MJS `parse_cval_type`) that caused a SEGV from insufficiently validated attacker input.

### Finding Description
`consoleLog.decode` in [1](#0-0)  parses the `string`/`bytes` dynamic-type offset directly from calldata:

```go
start := int(big.NewInt(0).SetBytes(params[pos : pos+registerSize]).Int64())
if len(params) < start+registerSize {
    return nil, errors.New("input too short")
}
size := int(big.NewInt(0).SetBytes(params[start : start+registerSize]).Int64())
```

`params` is fully attacker-controlled call input (the tail of `consoleLog.Run`'s `input`, see [2](#0-1) ). `big.Int.Int64()` reinterprets the low 64 bits of an arbitrarily large unsigned value as a signed `int64` "undefined" result per Go documentation when the value doesn't fit — in practice it simply returns the truncated bit pattern, which the caller can force to be negative by choosing the appropriate 32-byte word. Once `start` is negative:
- The guard `len(params) < start+registerSize` can be satisfied (a negative number added to 32 is still small, and `len(params)` is non-negative), so the check silently passes.
- The subsequent slice expression `params[start : start+registerSize]` (and later `params[start+registerSize : start+size+registerSize]`) uses a negative index, which Go slicing does not silently clamp — it panics with "slice bounds out of range" at runtime.

This mirrors the CVE-2021-46549 bug class: a type/size field parsed from untrusted input is used to index into a buffer without adequate bounds validation, causing a crash (SEGV in C / panic in Go) instead of clean input rejection.

### Impact Explanation
A panic inside `consoleLog.Run`, invoked as part of standard EVM execution for any transaction that calls the `CONSOLE_LOG` precompile address (registered in [3](#0-2) , wired into EVM interpretation in [4](#0-3) ), is not itself contained by a `recover()` inside the precompiled-contract dispatch path in the reviewed code — a panic here would propagate up through block/transaction processing. If unrecovered at a higher layer, this crashes the node process executing the transaction, i.e., a Denial-of-Service triggerable by any account able to submit a transaction (or an internal call from a malicious contract) targeting the console-log precompile with crafted calldata. This satisfies the Medium-severity DoS bar analogous to the source CVE (5.5, `AV:L/AC:L/PR:N/UI:R/S:U/C:N/I:N/A:H`), here reachable remotely without local access since any transaction sender can trigger it.

### Likelihood Explanation
Likelihood depends on whether the `consoleLog` precompile is active on the target network. The code comment states it implements "solidity console.log for local networks", and a related flag exists in [5](#0-4) , suggesting it may be gated to development/private networks rather than unconditionally enabled on public mainnet. I was unable to fully confirm, within the available search budget, whether this precompile is compiled into and reachable in the standard production precompile set used by public Kaia mainnet nodes, or only enabled via an opt-in flag for local/dev chains. If it is reachable on any node that a transaction/caller can target (including private chains run in production, or if the flag is enabled by node operators), the vulnerability is trivially and deterministically triggerable with a single crafted transaction — no race condition or special privilege required — making likelihood high in that scope.

### Recommendation
- In `consoleLog.decode` (and the equivalent `common.Bytes*Ty` size-parsing branch), validate that `start` and `size` are derived safely and are non-negative before use, e.g., check `big.Int.IsInt64()` and additionally verify the resulting value is within `[0, len(params)]` before any negative-capable arithmetic; reject with an error rather than proceeding when out-of-range.
- Replace raw `int(...).Int64()` conversions on attacker-controlled `big.Int` values with a bounded helper that clamps/rejects values that cannot be represented as valid slice indices.
- Wrap precompiled-contract execution (or at minimum this precompile) with a `recover()` guard so that any residual unexpected panic in decode logic is converted into a normal EVM execution error instead of crashing the process, consistent with defense-in-depth already used elsewhere (e.g., RPC callback `recover()` in `networks/rpc/service.go`).
- Confirm and document whether `CONSOLE_LOG` is compiled/enabled for public production networks; if it is intended to be dev-only, ensure it cannot be invoked on mainnet/production precompile address space at all.

### Proof of Concept
1. Construct calldata for the `consoleLog` precompile: 4-byte selector matching a `string` or `bytes` signature entry present in `common.ConsoleLogSignatures` (see [6](#0-5) ), followed by parameter words.
2. In the `pos`-th 32-byte word (the offset word for the dynamic argument), place a value whose low 64 bits, when reinterpreted as `int64`, are negative (e.g., top bit of byte 24 of that word set, i.e., word = `0x00...0080000000_00000000`-style pattern making `Int64()` negative).
3. Submit a transaction/call (or an internal `CALL` from a contract) to the `CONSOLE_LOG` precompile address with this calldata.
4. During execution, `c.decode` computes `start` as negative; the check `len(params) < start+registerSize` passes because the right side is small, then `params[start:start+registerSize]` executes a negative-index slice operation, causing a Go runtime panic ("slice bounds out of range") within transaction execution.

// decode decodes the input into a list of string according to the provided types
func (c *consoleLog) decode(params []byte, types []common.ConsoleLogType) ([]string, error) {
	var res []string
	for i, t := range types {
		pos := i * registerSize
		switch t {
		case common.Uint256Ty:
			if len(params) < pos+registerSize {
				return nil, errors.New("input too short")
			}
			res = append(res, strconv.FormatUint(big.NewInt(0).SetBytes(params[pos:pos+registerSize]).Uint64(), 10))
		case common.Int256Ty:
			if len(params) < pos+registerSize {
				return nil, errors.New("input too short")
			}
			res = append(res, strconv.FormatInt(big.NewInt(0).SetBytes(params[pos:pos+registerSize]).Int64(), 10))
		case common.BoolTy:
			if len(params) < pos+registerSize {
				return nil, errors.New("input too short")
			}
			if params[pos+registerSize-1] != 0 {
				res = append(res, "true")
			} else {
				res = append(res, "false")
			}
		case common.StringTy:
			if len(params) < pos+registerSize {
				return nil, errors.New("input too short")
			}
			start := int(big.NewInt(0).SetBytes(params[pos : pos+registerSize]).Int64())
			if len(params) < start+registerSize {
				return nil, errors.New("input too short")
			}
			size := int(big.NewInt(0).SetBytes(params[start : start+registerSize]).Int64())
			if len(params) < start+size+registerSize {
				return nil, errors.New("input too short")
			}
			res = append(res, string(params[start+registerSize:start+size+registerSize]))
