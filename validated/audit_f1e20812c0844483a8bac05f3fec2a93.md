Audit Report

## Title
Precompile signature-verification loops (`secp256k1`/`ed25519`/`secp256r1`) run to completion with no per-iteration compute metering, letting a fixed per-signature cost estimate diverge from real CPU work - ([File: precompiles/src/secp256k1.rs, precompiles/src/ed25519.rs, precompiles/src/secp256r1.rs])

## Summary
`secp256k1::verify`, `ed25519::verify`, and `secp256r1::verify` each loop over an attacker-controlled signature count (up to 255 for secp256k1/ed25519, up to 8 for secp256r1) doing real cryptographic work (ECDSA recovery, ed25519 strict verification, OpenSSL ECDSA verification) per iteration, with zero `compute_meter`-style metering or early-abort checkpoints, unlike every other compute path in the SVM. This runs during `Bank::verify_transaction` before compute-budget accounting/SVM execution begins, so the only "cost" charged is a flat per-signature estimate used for block-cost/scheduling limits, not a real-time cap enforced during verification.

## Finding Description
`verify_if_precompile` in `precompiles/src/lib.rs` (L98-119) dispatches to the relevant `verify_fn` based on program id, called from `Bank::verify_transaction`/conformance harness in `TransactionVerificationMode::HashAndVerifyPrecompiles` mode, prior to SVM execution. Each verify function (`precompiles/src/secp256k1.rs` L44-101, `precompiles/src/ed25519.rs` L30-77, `precompiles/src/secp256r1.rs` L59-139) loops over the signature count doing full cryptographic verification per iteration with no `compute_meter.consume_checked` calls — confirmed by an empty grep for `consume_checked` across the `precompiles` crate. This contrasts with genuine SVM syscalls (e.g. `syscalls/src/lib.rs` L1016-1019, L2745-2778) that gate expensive work behind `consume_checked`. The cost model (`cost-model/src/block_cost_limits.rs` L9-20, `cost-model/src/cost_model.rs` L129-151) only applies a flat per-signature estimate for scheduling/fee purposes, which is never enforced as an actual execution-time cutoff inside the verification loops themselves.

## Impact Explanation
Because verification is unmetered and unconditional, an attacker can submit transactions maximizing real cryptographic work relative to the flat cost assumption (particularly `secp256r1`, which uses heavier OpenSSL BigNum/EC/ECDSA machinery than the flat `SECP256R1_VERIFY_COST` implies). A validator/leader processing many such transactions spends CPU proportional to real crypto cost rather than the assumed budget used for block-cost limits, degrading transaction-processing throughput for validators that must replay the block. This is a non-RPC, remote, unprivileged resource-exhaustion/degradation vector triggered by ordinary fee-paying transactions.

## Likelihood Explanation
Likelihood is bounded by transaction size limits (max 255 signatures for secp256k1/ed25519, max 8 for secp256r1 per `precompiles/src/secp256r1.rs` L30-32) and by the cost-tracker/fee mechanism, which still caps how many such transactions fit per block based on the (possibly underestimated) flat cost. This is a genuine metering gap rather than an unbounded primitive; the real magnitude of cost divergence (especially for the OpenSSL-based `secp256r1` path) would require empirical benchmarking to quantify severity precisely.

## Recommendation
Add per-iteration compute-metering (or equivalent early-abort gating) inside `secp256k1::verify`, `ed25519::verify`, and `secp256r1::verify` so real cryptographic cost cannot exceed the estimate charged by the cost model. Re-benchmark `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, and `SECP256R1_VERIFY_COST` against measured real cost (especially the OpenSSL-based `secp256r1` path) to ensure flat per-signature costs are conservative upper bounds.

## Proof of Concept
1. Construct a transaction with a `secp256r1_program` instruction using the maximum allowed `num_signatures` (8) and large message data referencing maximal instruction data.
2. For `secp256k1_program`/`ed25519_program`, construct transactions with `num_signatures` up to 255 within transaction size limits.
3. Submit many such transactions concurrently to a leader and profile wall-clock time spent inside `Precompile::verify` versus the CU-equivalent time assumed by the flat cost constants (`SECP256R1_VERIFY_COST * num_signatures`, etc.), demonstrating that no `consume_checked` or equivalent cap exists inside the verification loops (`precompiles/src/secp256k1.rs`, `precompiles/src/ed25519.rs`, `precompiles/src/secp256r1.rs`).

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
