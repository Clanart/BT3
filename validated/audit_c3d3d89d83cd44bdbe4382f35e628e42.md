## Analysis

The report's core bug class is: *"path is checked against a restricted root, but the checked/allowed string and the actually-opened path differ, so a crafted relative segment (or, more generally, a filesystem indirection) escapes the intended root."* The codebase already has a hardened primitive for exactly this — `resolveWithin()` in `app/src/lib/path.ts` — which normalizes, resolves, and then calls `realpath()` on both the root and the resolved target before checking `startsWith`, explicitly to catch **symlink-based escapes**, not just `..` segments: [1](#0-0) 

This helper is used correctly in a few places that treat data as untrusted — the `x-github-client://` deep-link handler and the Copilot conflict-resolution writer: [2](#0-1) [3](#0-2) 

However, several other UI code paths that turn a **git-status/diff file path into a filesystem path and then open/reveal it** still use a naive `Path.join(repository.path, path)` with no `resolveWithin`/`realpath` check at all: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) 

The `file.path`/`path` value in these call sites is exactly the kind of "untrusted, attacker-influenced repository content" the safe helper was built to guard against, because Git tracks symlinks as regular blobs (mode `120000`) whose content is the link target. A malicious/compromised remote can commit a symlink entry, e.g. `notes.txt -> ../../../../.ssh/id_rsa` (or any absolute path). Once the victim clones/fetches/checks out that commit, Desktop's `git status`/`git log` reporting surfaces `notes.txt` as an ordinary changed/committed file. The user right-clicks it and picks "Reveal in Finder/Explorer," "Open with Default Program," or "Open in External Editor" — all totally ordinary, expected interactions with their own Changes/History list — and Desktop does `Path.join(repository.path, 'notes.txt')`, which returns a path that *looks* contained but is, at the OS level, a symlink pointing anywhere on disk. `shell.showItemInFolder`, `shell.openExternal('file://...')`, and the external-editor launcher all happily follow that symlink outside the repository root.

### Title
Symlink-based path traversal in file-open/reveal actions bypasses repository-root containment - (File: `app/src/lib/app-shell.ts`)

### Summary
`revealInFileManager`, the Changes/History/PR-files "Open with Default Program," and "Open in External Editor" context-menu actions build the on-disk path for a file with `Path.join(repository.path, file.path)` and pass it directly to Electron's `shell.showItemInFolder` / `shell.openExternal` / the external-editor launcher, without ever calling the project's own `resolveWithin()` symlink-aware containment check.

### Finding Description
`file.path` originates from `git status`/`git diff`/`git log` output describing the *committed* content of a repository that a user cloned or fetched — content the remote/attacker fully controls. Git allows committing a symlink (mode `120000`) whose target string is arbitrary (e.g. `../../../../.ssh/id_rsa`, `/etc/passwd`, or a Windows junction if the repo is later checked out on Windows-with-symlinks-enabled). After checkout, that symlink is a completely ordinary-looking entry in the working directory, reported through the app's status pipeline like any other file.

When the user interacts with that entry through completely benign actions — right-click ➜ "Reveal in Finder", "Open with Default Program", or "Open in [Editor]" (available from the Changes list, commit history file list, and PR files-changed view) — the code does:
```ts
const fullyQualifiedFilePath = Path.join(repository.path, path)
```
`Path.join` is a pure string operation; it does not resolve symlinks. The resulting path is still nominally "under" `repository.path` as a string, so it passes any naive prefix check, but the OS will transparently follow the symlink component when the shell/editor actually opens it, landing anywhere on the filesystem the attacker chose.

This is the same broken invariant as the Node.js report: a directory-containment guard (or, here, the *absence* of the one guard the codebase already knows it needs) is defeated by an indirection the guard doesn't account for. The project already has the fix pattern in hand — `resolveWithin()` explicitly `realpath()`s both the root and the candidate and rejects anything whose real path escapes, with a dedicated test for exactly the symlink-escape scenario: [10](#0-9) 

but that guard is applied only to the deep-link `filepath` parameter and the Copilot conflict writer, not to the much more commonly used "open/reveal a changed or committed file" actions.

### Impact Explanation
Successful exploitation lets a malicious repository read (via "Open with Default Program"/"Open in External Editor", which will display the target file's contents) or expose the location of (via "Reveal in Finder/Explorer") arbitrary files outside the repository that the victim's OS user account can access — e.g. SSH private keys, cloud credential files, browser profile data, or other repos' secrets — simply by having the victim right-click a file that appears in their own Changes tab or commit history after cloning/checking out the attacker's repository. Depending on the target file and the OS's file-type association, "Open with Default Program" could also result in unintended execution of a script/binary outside the repo tree. This satisfies the stated valid-impact criteria: attacker controls a cloned/fetched repository, no local/physical access or prior compromise is required, and the outcome is file read outside the repo (and potentially code execution depending on default-app associations).

### Likelihood Explanation
Moderate-to-high. No unusual user behavior is required beyond opening a file the attacker placed in their own repository — this is standard Desktop usage (browsing Changes/History and using the context menu), not a contrived multi-step social-engineering flow. The main constraint is platform symlink support (macOS/Linux by default; Windows requires either Developer Mode/symlink privilege or an admin-elevated `git clone`, which somewhat lowers likelihood there but not on macOS/Linux).

### Recommendation
Route every place that turns a repository-relative `file.path` into a filesystem path for `shell.showItemInFolder`, `shell.openExternal`, or external-editor launching through the existing `resolveWithin()` helper (or a thin wrapper around it), rejecting and logging when the resolved real path escapes the repository root — exactly as already done in `dispatcher.ts`'s `openRepositoryFromUrl` and `app-store.ts`'s Copilot conflict-resolution writer. At minimum this should cover `app/src/lib/app-shell.ts` (`revealInFileManager`), `app/src/ui/changes/sidebar.tsx` and `app/src/ui/changes/filter-changes-list.tsx` (`onOpenItem`, "Copy Paths"), `app/src/ui/history/selected-commits.tsx`, `app/src/ui/open-pull-request/pull-request-files-changed.tsx`, `app/src/ui/app.tsx` (`onOpenInExternalEditor`), and `app/src/ui/multi-commit-operation/dialog/copilot-conflicts-dialog.tsx`.

### Proof of Concept
1. Attacker creates a repository containing a symlink committed with `ln -s ../../../../.ssh/id_rsa leak.txt && git add leak.txt && git commit`.
2. Victim clones or fetches/checks out this repository in GitHub Desktop on macOS or Linux.
3. In the Changes tab (if `leak.txt` shows as untracked/new) or in History (after the commit lands), victim right-clicks `leak.txt` and selects "Open with Default Program" or "Reveal in Finder".
4. `Path.join(repository.path, 'leak.txt')` yields a path whose final component is a symlink to `~/.ssh/id_rsa`; the OS resolves the symlink when the default program opens it or Finder reveals it, displaying/locating the victim's private key content outside the repository, with no `resolveWithin`/`realpath` check ever performed to prevent it.
