### Title
Unauthenticated `SendMoveToVaultTx` RPC lets a caller bind an arbitrary transaction to any deposit outpoint without verifying it is the presigned move-to-vault tx - (File: core/src/rpc/aggregator.rs)

### Summary
The aggregator's `send_move_to_vault_tx` handler validates only the *shape* of the supplied raw transaction (output count, output amounts, and output script pubkeys) before registering it in the tx-sender queue for broadcast under a caller-supplied `deposit_outpoint`. It never checks that `movetx.input[0].previous_output` actually equals `deposit_outpoint`, nor that `deposit_outpoint` corresponds to a deposit that has already gone through the `NewDeposit`/N-of-N signing flow. This is analogous to the reported bug class: a caller can invoke a state-changing/broadcasting operation and bind it to a value/identity ("deposit presigned") it was never authorized to act on ("deposit minted once"), because the only checks performed are structural, not attributional.

### Finding Description
`send_move_to_vault_tx` in `core/src/rpc/aggregator.rs` (around lines 1973-2102) is exposed on `ClementineAggregator`, a public, non-`Internal`-prefixed RPC per `core/src/rpc/clementine.proto` (`rpc SendMoveToVaultTx(SendMoveTxRequest) returns (Txid) {}`, lines 781). Unlike inter-entity calls guarded by `only_aggregator_and_self` in `core/src/rpc/interceptors.rs` (lines 22-76), which restrict `Internal*`-named methods to the aggregator or the entity itself, `SendMoveToVaultTx` carries no such prefix and is documented as reachable from the client-facing side of the system.

The handler: [1](#0-0) 
only checks input/output counts and output amounts, and [2](#0-1) 
only checks that the output script pubkeys match the expected vault/anchor addresses. At no point does it verify that `movetx.input[0].previous_output` matches the caller-supplied `deposit_outpoint`, nor that `deposit_outpoint` is a deposit that previously completed the `NewDeposit` N-of-N signing ceremony. It then unconditionally persists the association and enqueues the transaction for broadcast: [3](#0-2) 

Because the binding between `deposit_outpoint` and the transaction that is registered/broadcast under it is asserted purely from caller-supplied data rather than derived from the deposit's actual presigned move transaction, the equality the protocol should enforce — *deposit presigned by N-of-N == deposit registered/broadcast as moved* — is not checked at this entry point. The only remaining backstop is the Bitcoin network itself rejecting an unsigned/invalid witness at broadcast time, but the aggregator has already committed the deposit_outpoint → txid association to its own database before that backstop can apply.

### Impact Explanation
This matches the report's High-impact category of "an unauthenticated state-changing or broadcasting call": any caller reaching this RPC can force the aggregator to register and attempt to broadcast a transaction tied to a `deposit_outpoint` it does not own or control the presigned witness for, without the aggregator first confirming that the transaction is the legitimate, N-of-N-signed move-to-vault transaction for that specific deposit. If the deposit-to-move_txid slot is later relied upon (e.g., by `get_move_to_vault_txid_from_citrea_deposit`, used elsewhere for withdrawal/payout matching) before an actual valid confirmation occurs, this creates a window where the recorded deposit state does not reflect an authentic, verifier-signed movement of funds — the same "operator credited versus the party that paid" / "deposit presigned versus deposit minted once" mismatch the reference bug class targets.

### Likelihood Explanation
The RPC is reachable without any privileged role, key, or certificate check distinguishing it from other `Internal`-prefixed, self/aggregator-only methods, so likelihood of an unprivileged caller reaching it is high. The main open question — whether a production deployment fronts this specific RPC with additional authentication outside the repository (e.g., only the "clementine-backend service" has network access) — could not be fully confirmed from the available code and would need to be verified in a live/full-source review.

### Recommendation
In `send_move_to_vault_tx`, before enqueuing the transaction:
1. Verify `movetx.input[0].previous_output == deposit_outpoint`.
2. Verify `deposit_outpoint` corresponds to a deposit that has already completed the `NewDeposit` signing flow (i.e., a `DepositData`/presigned move transaction exists for it), rejecting the request otherwise.
3. Consider requiring that the transaction ID matches the one previously computed/signed during `NewDeposit` (via `create_move_to_vault_txhandler`), rather than accepting an arbitrary raw transaction from the caller.

### Proof of Concept
1. An unprivileged client calls `ClementineAggregator.SendMoveToVaultTx` with:
   - `deposit_outpoint` = an arbitrary or victim deposit outpoint.
   - `raw_tx` = a transaction crafted by the caller with exactly one input, two outputs matching `bridge_amount`/`0`, and script pubkeys matching the expected vault/anchor addresses (all publicly derivable/known values — `bridge_amount`, verifier musig2 aggregate key, security council multisig, network anchor script).
2. `send_move_to_vault_tx` passes all structural checks (`core/src/rpc/aggregator.rs:2019-2073`) since none of them tie the input to `deposit_outpoint` or to an existing presigned deposit record.
3. The handler commits the `deposit_outpoint → movetx` association to the DB and enqueues the raw transaction for broadcast (`core/src/rpc/aggregator.rs:2075-2100`), without ever confirming the caller was authorized to bind this specific deposit's identity to this transaction. [4](#0-3)
