Duplicate signer entries in `SchnorrAggregate::verify` let one signature count as many signers - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::verify` validates the aggregate equation `Σ z_i·(R_i + c_i·K_i) − s·G == 0` over the caller-supplied `(key, challenge)` slice, but never checks that the listed keys are distinct. Because each position gets an independent weight `z_i` derived from a running transcript, repeating the same `(key, challenge, R)` triple `k` times produces a perfectly valid verification: `(z_1 + … + z_k)·s·G − s_agg·G == 0`. A verifier that attributes one unit of signing weight per list entry therefore counts a single real signer as `k` signers — the direct analog of voting-power inflation via a missing "already voted" check.

### Finding Description
The external report's class is "repeatable action inflates counted weight because the repeat path lacks an already-acted check". In Serai this maps onto aggregate Schnorr verification:

- `SchnorrAggregate::verify(dst, keys_and_challenges)` only checks `self.Rs.len() == keys_and_challenges.len()` (aggregate.rs:128), then iterates the slice, pushing `(z_i, Rs[i])` and `(z_i·challenge_i, key_i)` pairs and verifying the sum equals `s·G` (aggregate.rs:138-145).
- There is no deduplication of `key` (nor of `(key, challenge)` pairs). The aggregation weights `z_i` are position-dependent outputs of `weight(&mut digest)` (aggregate.rs:22-65), so duplicates do not cancel; they sum. Any entry that individually satisfies `s_i·G == R_i + c_i·K_i` can be replicated arbitrarily, and the aggregate remains valid as long as `s = Σ z_i·s_i`, which `SchnorrAggregator::complete` computes exactly that way (aggregate.rs:180-184).
- The attacker's `s` need not even come from `SchnorrAggregator`: they can directly compute `s = (z_1+…+z_k)·s_A` for a single genuine signature `s_A` under key `K_A` and nonce `R_A`, then submit `Rs = [R_A; k]` and `keys_and_challenges = [(K_A, c_A); k]`. `verify` returns `true`.
- This is reachable from untrusted bytes: `SchnorrAggregate::read` parses `Rs` and `s` from a reader (aggregate.rs:77-88), and `verify` takes the key/challenge list as an argument. The in-tree Tendermint consumer `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs:201-229` builds `signers` and challenges externally and calls this `verify`, attributing one validator signature per entry — precisely the "voting power" interpretation.

The analogous guard that exists elsewhere in the codebase — `DkgError::DuplicatedParticipant` in `ThresholdKeys::view` (crypto/dkg/src/lib.rs:476-479) and `FrostError::DuplicatedParticipant` in `AlgorithmSignMachine::sign` (crypto/frost/src/sign.rs:306-310) — is absent here.

### Impact Explanation
A single valid Schnorr signature can be presented as an aggregate signature "by" `k` signers. Any caller that weights outcomes by signer count (e.g., consensus voting power, threshold-of-signers checks) accepts `k` votes from one key. This is a forged aggregate signature: it claims participation of signers who never signed, which meets the "forged proof or signature" acceptance bar.

### Likelihood Explanation
Fully attacker-controlled and deterministic. The attacker needs one valid `(R, s)` under challenge `c` for key `K` — obtainable by signing once themselves or replaying an observed signature if the challenge is reconstructible — then locally derives the positional weights `z_i` (public DST, public transcript) and sets `s_agg = s·Σz_i`. No collusion, no key material beyond one real signature.

### Recommendation
In `SchnorrAggregate::verify`, reject `keys_and_challenges` slices containing duplicate keys (sort by `key.to_bytes()` or insert into a `HashSet` of the encoded points, erroring/`false` on collision), mirroring the `DuplicatedParticipant` checks in `dkg`/`frost`. Documenting and enforcing distinctness is required by the aggregate Schnorr construction (eprint 2021/350 assumes distinct signer keys).

### Proof of Concept
```rust
// C: some Ciphersuite; DST: &'static [u8]
let key = Zeroizing::new(C::random_nonzero_F(&mut OsRng));
let pubkey = C::generator() * key.deref();
let challenge = C::random_nonzero_F(&mut OsRng); // attacker-crafted/bound challenge
let sig = SchnorrSignature::<C>::sign(&key, Zeroizing::new(C::random_nonzero_F(&mut OsRng)), challenge);

// Recompute the positional weights verify() will derive
let mut digest = DigestTranscript::<C::H>::new(DST);
digest.domain_separate(b"signatures");
let k = 8;
for _ in 0..k { digest.append_message(b"challenge", challenge.to_repr()); }
let mut d2 = digest.clone();
let weights: Vec<C::F> = (0..k).map(|_| weight::<_, C::F>(&mut d2)).collect();

// Forge: s_agg = s * Σ z_i ; Rs = [sig.R; k]
let s_agg = sig.s * weights.iter().sum::<C::F>();
let agg = SchnorrAggregate { Rs: vec![sig.R; k], s: s_agg };

// Passes, claiming k signers though only one key signed
assert!(agg.verify(DST, &vec![(pubkey, challenge); k]));
```
The `weight` function is private; a PoC re-implements it inline or serializes via `SchnorrAggregator` fed the same signature `k` times (`aggregator.aggregate(challenge, sig)` in a loop), which produces the identical forgery — `aggregate` likewise performs no dedup.
