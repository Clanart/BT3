### Title
`SignableTransaction::new` omits the OP_RETURN data output from weight/vbytes and fee calculation - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` appends an OP_RETURN output carrying caller-supplied `data` to `tx_outs`, but computes `weight`, `vbytes`, `needed_fee`, and the `TooLargeTransaction` bound using only `payments` (and optionally `change`). The data output's bytes are never counted, so the transaction's true size exceeds the estimate the fee and standardness checks were made against — value committed as an OP_RETURN output silently escapes the size accounting, analogous to value escaping `msg.value` accounting.

### Finding Description
At `networks/bitcoin/src/wallet/send.rs:194-202`, the OP_RETURN output is pushed into `tx_outs` before any sizing is done. However, the sizing call at `send.rs:204` passes `payments` — the pre-data output list — into `calculate_weight_vbytes`:

```rust
// send.rs:194-204
if let Some(data) = data {
  tx_outs.push(TxOut {
    value: Amount::ZERO,
    script_pubkey: ScriptBuf::new_op_return(
      PushBytesBuf::try_from(data)
        .expect("data didn't fit into PushBytes depsite being checked"),
    ),
  })
}

let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (`send.rs:62-99`) builds a template transaction whose outputs are exactly `payments` plus an optional change output — the data output is absent. Consequently:

1. `needed_fee = fee_per_vbyte * vbytes` (`send.rs:206`) is priced for a smaller transaction than the one actually produced (`tx_outs` includes the ~9–91 extra non-witness bytes of the OP_RETURN output, ≈25–91 vbytes).
2. The minimum-relay-fee check (`send.rs:211`) can pass for a transaction whose real feerate falls below `DEFAULT_MIN_RELAY_TX_FEE`, causing mempool rejection.
3. The `MAX_STANDARD_TX_WEIGHT` check (`send.rs:241`) uses the under-counted `weight`, so a transaction that is actually non-standard (and can never confirm) is accepted and signed.

The FROST-signed transaction (`TransactionSignMachine::sign`, `send.rs:373-397`) then commits to this oversized `tx` via `Prevouts::All`, so the produced signatures are valid only for the under-fee/non-standard transaction.

### Impact Explanation
Any caller supplying `data` gets a transaction whose effective feerate is strictly lower than requested — up to ~91 vbytes unaccounted. When `fee_per_vbyte` is at or near the minimum relay rate, or when the payment set is already near `MAX_STANDARD_TX_WEIGHT`, the resulting signed transaction is unrelayable/non-standard. The threshold-signing ceremony produces signatures usable only for that dead transaction, and the spent fee budget / round is wasted; the funds remain locked in the inputs until a fresh, correctly-priced transaction is constructed and re-signed through another full multisig round. This is a reachable accounting error from a public input (`data` up to 80 bytes is explicitly permitted by the `TooMuchData` check at `send.rs:171`).

### Likelihood Explanation
The bug triggers deterministically whenever `data` is `Some` — every transaction carrying Serai's embedded `InInstruction`/refund metadata. Whether it causes relay failure depends on the chosen feerate and payment size, but the fee is *always* underpaid relative to the requested rate, and the standardness bound is always checked against a weight lower than reality.

### Recommendation
Include the data output in the size estimate: either pass the fully-built `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or add `data.map_or(0, |d| d.len() + overhead)` to the computed weight/vbytes before deriving `needed_fee` and checking `MAX_STANDARD_TX_WEIGHT`. The same fix must be applied to the `weight_with_change`/`vbytes_with_change` call at `send.rs:225-226`.

### Proof of Concept
```rust
// networks/bitcoin/src/wallet/send.rs semantics:
// payments: one P2TR payment; data: 80 bytes (allowed, passes TooMuchData at :171)
let payments = vec![(p2tr_script_buf(key).unwrap(), 1000)];
let data = Some(vec![0u8; 80]);

// calculate_weight_vbytes is invoked with `payments` only (:204),
// so `vbytes` excludes the OP_RETURN output (~91 vbytes missed).
let tx = SignableTransaction::new(inputs, &payments, None, data, fee_per_vbyte).unwrap();

// Actual tx contains the OP_RETURN output (:194-202), so
// tx.transaction().vsize() > vbytes used for needed_fee (:206).
// Therefore tx.fee() / tx.transaction().vsize() < fee_per_vbyte.
// With fee_per_vbyte chosen at the min-relay boundary, the signed tx is rejected
// by mempool despite passing the TooLowFee check (:211).
// With payments sized to the limit, weight (:241) is checked against a value
// lower than the real tx weight, yielding a non-standard transaction.
```
