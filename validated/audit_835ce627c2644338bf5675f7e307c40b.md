## Finding

### Title
Supermajority participation check counts raw signature-array length, not distinct authorities, letting a single replayed BEEFY signature satisfy the 2/3+1 threshold - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
`verify_mmr_update_proof` (and its Solidity twin `EcdsaBeefy.verifyMmrUpdateProof`) derives the BEEFY supermajority check from `signatures.len()` — the raw count of `(index, signature)` entries supplied in the untrusted proof — instead of the count of *distinct* recovered authorities. This is the same broken invariant as the reported `ValidateVoteExtensions` bug: an aggregate total is computed straight from attacker-controlled input data without validating that each contributing entry is unique, so the total can be inflated by repetition rather than by genuine additional participation.

### Finding Description
`verify_mmr_update_proof` computes: [1](#0-0) 

`signatures_length` is simply `mmr.signed_commitment.signatures.len()`, and this raw count — not a deduplicated count of authority indices — is what `check_participation_threshold` gates on: [2](#0-1) 

The subsequent loop recovers a public key per signature entry and pushes `(authority_leaves, authority_indices)` pairs without any uniqueness check: [3](#0-2) 

Nothing rejects two entries in `mmr.signed_commitment.signatures` sharing the same `index`/signature. BEEFY commitment signatures are broadcast publicly in relay-chain GRANDPA/BEEFY justifications, so an attacker does not need to forge anything — they can take one (or a few) legitimately-observed authority signatures and repeat the same `(index, signature)` tuple multiple times in the array to multiply `signatures_length` far past the honest number of distinct signers, while the merkle-multiproof step is fed the same repeated `(index, leaf)` pairs and is never asked to prove that the set of indices is distinct.

The identical pattern (raw `votes.length` gating a supermajority check, no `authorityIndex` uniqueness check) exists in the Solidity ECDSA verifier: [4](#0-3) 

Notably, sibling consensus verifiers in this same codebase *do* guard against exactly this class of bug — the Pharos verifier explicitly rejects duplicate participant keys, and the BSC/sync-committee verifiers use a bitset that structurally cannot double-count a validator: [5](#0-4) [6](#0-5) 

This confirms the maintainers are aware of and have patched duplicate-participant inflation elsewhere, but the naive BEEFY ECDSA path (both Rust and Solidity) was left without the same guard.

`submit_proof` on `pallet-beefy-consensus-proofs` is a plain signed extrinsic — any account can call it, it is not relayer/prover-gated beyond the SP1-nonce binding, which only applies to the SP1 path, not the naive proof type: [7](#0-6) [8](#0-7) 

### Impact Explanation
If the merkle multi-proof step does not itself reject duplicate `(index, leaf)` entries in the proof it is asked to verify, an unprivileged submitter can pass `check_participation_threshold`/`SuperMajorityRequired` using far fewer than 2/3+1 distinct BEEFY authorities, causing the light client to accept and commit a new MMR root / parachain state commitment as finalized. Since BEEFY consensus underlies Hyperbridge's cross-chain state commitments feeding into ISMP request/response/timeout handling, false state acceptance here directly enables acceptance of forged parachain state, corrupting downstream proof verification for bridged messages, asset transfers, and settlement — matching the "false proof/state acceptance" impact category.

### Likelihood Explanation
The precondition (repeatable, previously-observed authority signatures being freely available since BEEFY justifications are public relay-chain data) is trivially met, and `submit_proof` is callable by any signed account with no relayer/prover trust assumption. The only unresolved variable is whether the underlying `rs_merkle`/`MerkleMultiProof.sol` multiproof verification implementation happens to reject repeated indices as a side effect of its internal structure; the *threshold check itself* is unconditionally vulnerable to the inflated count regardless, since it runs on `signatures.len()` before any merkle verification occurs.

### Recommendation
In `verify_mmr_update_proof` (and `EcdsaBeefy.verifyMmrUpdateProof`), deduplicate `sig.index` (and/or the recovered authority address) before computing the participation count, mirroring the `DuplicateParticipant` check already implemented in `modules/consensus/pharos/verifier/src/lib.rs`. Reject the proof if `authority_indices` contains any duplicate index, and base `check_participation_threshold` on the deduplicated count rather than raw array length.

### Proof of Concept
1. Observe a legitimate BEEFY `SignedCommitment` for the current authority set on the relay chain, capturing one authority's `(index, signature)` pair over the commitment.
2. Construct a `ConsensusMessage`/naive `BeefyConsensusProof` whose `signed_commitment.signatures` (or Solidity `votes`) array repeats that single `(index, signature)` tuple enough times to make `signatures_length`/`sigLen` exceed `((2 * authority_set.len) / 3) + 1`, while real distinct signers remain far below the supermajority.
3. Submit via `pallet-beefy-consensus-proofs::submit_proof` (signed, permissionless) or the EVM `EcdsaBeefy.verify` entry point.
4. `check_participation_threshold`/`checkParticipationThreshold` passes on the inflated count; the merkle multiproof step is presented with the same repeated `(index, leaf)` pairs, exercising whether duplicate entries can still validate. [9](#0-8)

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

    function verifyMmrUpdateProof(BeefyConsensusState memory trustedState, RelayChainProof memory relayProof)
        internal
        pure
        returns (BeefyConsensusState memory, bytes32)
    {
        uint256 sigLen = relayProof.signedCommitment.votes.length;
        uint256 latestHeight = relayProof.signedCommitment.commitment.blockNumber;
        Commitment memory commitment = relayProof.signedCommitment.commitment;
        if (
            commitment.validatorSetId != trustedState.currentAuthoritySet.id
                && commitment.validatorSetId != trustedState.nextAuthoritySet.id
        ) {
            revert UnknownAuthoritySet();
        }

        bool isCurrentAuthorities = commitment.validatorSetId == trustedState.currentAuthoritySet.id;
        AuthoritySetCommitment memory authoritySet =
            isCurrentAuthorities ? trustedState.currentAuthoritySet : trustedState.nextAuthoritySet;
        if (!checkParticipationThreshold(sigLen, authoritySet.len)) revert SuperMajorityRequired();

        uint256 payloadLength = commitment.payload.length;
        bytes32 mmrRoot;
        for (uint256 i = 0; i < payloadLength; i++) {
            if (commitment.payload[i].id == MMR_ROOT_PAYLOAD_ID && commitment.payload[i].data.length == 32) {
                mmrRoot = Bytes.toBytes32(commitment.payload[i].data);
            }
        }
        if (mmrRoot == bytes32(0)) revert MmrRootHashMissing();

        // verify the commitment
        bytes32 commitmentHash = keccak256(Codec.Encode(commitment));
        MerkleMultiProof.Leaf[] memory authorities = new MerkleMultiProof.Leaf[](sigLen);
        for (uint256 i = 0; i < sigLen; i++) {
            Vote memory vote = relayProof.signedCommitment.votes[i];
            address authority = ECDSA.recover(commitmentHash, vote.signature);
            authorities[i] =
                MerkleMultiProof.Leaf({index: vote.authorityIndex, hash: keccak256(abi.encodePacked(authority))});
        }

        bool valid = MerkleMultiProof.VerifyProof(authoritySet.root, relayProof.proof, authorities, authoritySet.len);
        if (!valid) revert InvalidAuthoritiesProof();

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
