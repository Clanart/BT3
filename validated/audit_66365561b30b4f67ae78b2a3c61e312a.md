### Title
`depositFor` In `WombatPoolHelperV2` Hardcodes `minimumLiquidity` To 0, Enabling Sandwich-Attack Theft From Depositors - (File: `wombat/WombatPoolHelperV2.sol`)

### Summary
`WombatPoolHelperV2.depositFor` ignores any caller-supplied slippage protection and always forwards `_minimumLiquidity = 0` to `WombatStaking.deposit`, which in turn passes it unmodified to the underlying Wombat AMM pool's `deposit`. This removes all slippage protection for any user depositing via this pool-helper entrypoint, mirroring the exact bug class described in the external report (hardcoded `minMarketTokens`/`minimumLiquidity` = 0).

### Finding Description
`depositFor` is a public entrypoint on the pool helper that any unprivileged wallet can call to deposit stable/LP tokens into a Wombat pool on behalf of an address: [1](#0-0) 

Unlike the sibling `deposit(uint256 _amount, uint256 _minimumLiquidity)` function which forwards a caller-chosen `_minimumLiquidity`, `depositFor` hardcodes the value to `0`: [2](#0-1) 

This `0` value flows unchanged through `WombatStaking.deposit` into `IWombatPool(poolInfo.depositTarget).deposit(...)`, the actual Wombat AMM pool contract, which uses the pool's bonding-curve invariant (cash/liability ratio) to determine how much LP liquidity to mint for the deposited amount: [3](#0-2) [4](#0-3) 

Because `minimumLiquidity` is always `0`, the transaction will never revert regardless of how unfavorable the pool's cash/liability ratio is at execution time. An unprivileged actor (a searcher/MEV bot) observing a pending `depositFor` call in the mempool can:
1. Front-run the deposit with a swap that skews the pool's cash/liability ratio unfavorably for depositors (e.g., adding liability/cash imbalance for the deposited token).
2. Let the victim's `depositFor` execute, receiving materially less LP liquidity than a fair, unmanipulated ratio would have produced (with no floor to protect them, since `minimumLiquidity = 0`).
3. Back-run to reverse the initial swap and capture the value siphoned out of the victim's deposit.

This is a classic sandwich-attack pattern that extracts value directly from an ordinary depositor's transaction, entirely achievable by any unprivileged wallet with mempool visibility — no admin/governance/oracle control needed.

### Impact Explanation
Any user calling `depositFor` (e.g., to deposit for themselves or on behalf of another address) can have their deposit sandwiched, causing them to mint fewer LP/receipt tokens than the fair value of their deposited principal. The difference is captured by the attacker, constituting direct theft of user funds during an ordinary, unprivileged deposit flow.

### Likelihood Explanation
Likelihood is high: `depositFor` is a permissionless, frequently-used entrypoint for pool helpers, sandwich-attack infrastructure against AMM deposits/swaps is commodity tooling, and the complete absence of a minimum-liquidity floor (rather than merely a loose one) means there is zero cost or risk for an attacker to extract the maximum possible slippage on every observed deposit.

### Recommendation
Add a `_minimumLiquidity` parameter to `depositFor` so callers can supply a caller-computed, appropriately tight minimum-liquidity floor (as already done in `deposit`), and enforce it end-to-end through `WombatStaking.deposit` into the Wombat pool's `deposit` call, rather than hardcoding `0`.

### Proof of Concept
1. Alice calls `WombatPoolHelperV2.depositFor(amount, alice)` intending to deposit `amount` of `depositToken`.
2. An MEV bot observes this pending transaction and front-runs it with a trade that skews the target Wombat pool's cash/liability ratio for `depositToken` unfavorably.
3. Alice's transaction executes: because `_minimumLiquidity` is hardcoded to `0` in [5](#0-4) , the deposit proceeds and mints Alice a reduced amount of LP liquidity/receipt tokens versus the fair-market amount, with no on-chain check to abort the transaction.
4. The bot back-runs to restore the pool ratio and realizes a profit equal to the value it extracted from Alice's deposit.
