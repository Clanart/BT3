## Title
Incomplete UTI allow-list in `isApplicationBundle` lets non-`.app` executable bundle types (Automator workflows, preference panes, installer packages, etc.) be misclassified as safe and passed to `UNSAFE_openDirectory` - (File: `app/src/lib/is-application-bundle.ts`)

## Summary
`isApplicationBundle` is the *only* gate that decides whether a directory is safe to hand to `shell.openPath` via `UNSAFE_openDirectory`, whose own doc-comment says it must never be called on unverified paths because macOS can treat a directory as executable. [1](#0-0) [2](#0-1) 

## Finding Description
The check queries `mdls` for `kMDItemContentType`/`kMDItemContentTypeTree` and then tests membership against a hard-coded three-item list: [3](#0-2) 

That list — `com.apple.application-bundle`, `com.apple.application`, `public.executable` — only covers the classic `.app` bundle UTI chain shown in the function's own comment. It does not include the many other Apple UTIs for bundle types that macOS LaunchServices will still open/execute/launch a helper process for when double-clicked or opened via `shell.openPath`/Finder, e.g.:

- `com.apple.automator-workflow` (`.workflow`) — opens in Automator and can run embedded shell/AppleScript actions
- `com.apple.systempreference.prefpane` (`.prefPane`) — loaded as a plugin bundle by System Preferences, can contain executable code
- `com.apple.installer-package-archive` (`.pkg`) — launches Installer.app
- other bundle-style content types (`.plugin`, `.saver`, `.qlgenerator`, `.action`, etc.)

Since `isApplicationBundle` returns `false` for any of these, whichever caller depends on it to gate `UNSAFE_openDirectory` would treat such a directory as an ordinary, safe-to-open folder and forward it to `shell.openPath`.

## Impact Explanation
If an attacker ships a repository containing a directory that macOS/LaunchServices recognizes as one of the non-covered bundle UTIs (e.g., a folder named `evil.workflow` with the correct Info.plist so `mdls` reports `com.apple.automator-workflow`), and GitHub Desktop's code path that relies on `isApplicationBundle` ends up calling `UNSAFE_openDirectory`/`shell.openPath` on that specific directory (rather than a parent, or via the safe `showItemInFolder`/`showFolderContents` selection-only APIs), the OS could launch the associated bundle handler (Automator, System Preferences, Installer, etc.) instead of merely opening a Finder window. Depending on the bundle's contents, that can result in execution of attacker-supplied logic outside GitHub Desktop's control.

## Likelihood Explanation
Exploitability is conditional on two things this review could not fully confirm from the available index:
1. That some caller invokes `UNSAFE_openDirectory` directly on a repository-content-controlled path (not merely `showItemInFolder`, which only *selects* an item in Finder and is safe) — the callers identified are `app/src/main-process/menu/build-default-menu.ts` and `app/src/main-process/main.ts`, but the exact call chain from a repo-controlled directory to `UNSAFE_openDirectory` was not verified within tool budget.
2. That the target directory name/path is attacker-controllable via ordinary repository content (e.g., an untracked/ignored folder shipped in the clone) rather than a fixed application-owned path.

The `isApplicationBundle` gap itself is real and verifiable from the code, but without confirming the exact reachable call site, likelihood should be treated as unverified/uncertain rather than confirmed end-to-end.

## Recommendation
- Replace the finite allow-list with a deny-list/positive-safety check based on the full UTI conformance tree (e.g., reject if `kMDItemContentTypeTree` contains any of `com.apple.bundle`, `com.apple.package`, `public.executable`, `com.apple.application`, or any UTI conforming to `com.apple.generic-bundle`), or better, check `public.directory` plus absence of any "launchable" conformance rather than presence of a specific hard-coded set.
- Alternatively, avoid `mdls`/UTI heuristics entirely and use `LSCopyApplicationForItem`-style checks or simply never call `shell.openPath` on arbitrary repository-relative directories — prefer `shell.showItemInFolder` (selection only, doesn't execute) wherever the target may be repository-controlled.

## Proof of Concept
1. Create a directory `poc.workflow` inside a test repository with a minimal `Info.plist`/`document.wflow` so Spotlight indexes it with `kMDItemContentType = "com.apple.automator-workflow"` (or `poc.prefPane`, `poc.pkg`).
2. Run `mdls -name kMDItemContentType -name kMDItemContentTypeTree poc.workflow` and confirm none of `com.apple.application-bundle`, `com.apple.application`, `public.executable` appear in the output.
3. Call `isApplicationBundle('poc.workflow')` from `app/src/lib/is-application-bundle.ts` and assert it returns `false`.
4. Pass the same path to `shell.openPath` (as `UNSAFE_openDirectory` in `app/src/main-process/shell.ts` would) and observe that macOS launches Automator/System Preferences/Installer rather than opening a plain Finder window — demonstrating the isApplicationBundle result (`false`) diverges from actual LaunchServices executable behavior (`true`). import { execFile } from './exec-file'

```typescript
/**
 * Attempts to determine if the provided path is an application bundle or not.
 *
 * macOS differs from the other platforms we support in that a directory can
 * also be an application and therefore executable making it unsafe to open
 * directories on macOS as we could conceivably end up launching an application.
 *
 * This application uses file metadata (the `mdls` tool to be exact) to
 * determine whether a path is actually an application bundle or otherwise
 * executable.
 *
 * NOTE: This method will always return false when not running on macOS.
 */
export async function isApplicationBundle(path: string): Promise<boolean> {
  if (process.platform !== 'darwin') {
    return false
  }

  // Expected output for an application bundle:
  // $ mdls -name kMDItemContentType -name kMDItemContentTypeTree /Applications/GitHub\ Desktop.app
  // kMDItemContentType     = "com.apple.application-bundle"
  // kMDItemContentTypeTree = (
  //     "com.apple.application-bundle",
  //     "com.apple.application",
  //     "public.executable",
  //     "com.apple.localizable-name-bundle",
  //     "com.apple.bundle",
  //     "public.directory",
  //     "public.item",
  //     "com.apple.package"
  // )
  const { stdout } = await execFile('mdls', [
    ...['-name', 'kMDItemContentType'],
    ...['-name', 'kMDItemContentTypeTree'],
    path,
  ])

  const probableBundleIdentifiers = [
    'com.apple.application-bundle',
    'com.apple.application',
    'public.executable',
  ]

  return probableBundleIdentifiers.some(id => stdout.includes(`"${id}"`))
}
```

```typescript
import { shell } from 'electron'

/**
 * Wraps the inbuilt shell.openItem path to address a focus issue that affects macOS.
 *
 * When opening a folder in Finder, the window will appear behind the application
 * window, which may confuse users. As a workaround, we will fallback to using
 * shell.openExternal for macOS until it can be fixed upstream.
 *
 * CAUTION: This method should never be used to open user-provided or derived
 * paths. It's sole use is to open _directories_ that we know to be safe, no
 * verification is performed to ensure that the provided path isn't actually
 * an executable.
 *
 * @param path directory to open
 */
export function UNSAFE_openDirectory(path: string) {
  // Add a trailing slash to the directory path.
  //
  // On Windows, if there's a file and a directory with the
  // same name (e.g `C:\MyFolder\foo` and `C:\MyFolder\foo.exe`),
  // when executing shell.openItem(`C:\MyFolder\foo`) then the EXE file
  // will get opened.
  // We can avoid this by adding a final backslash at the end of the path.
  const pathname = __WIN32__ && !path.endsWith('\\') ? `${path}\\` : path

  shell.openPath(pathname).then(err => {
    if (err !== '') {
      log.error(`Failed to open directory (${path}): ${err}`)
    }
  })
}
```
