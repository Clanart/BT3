### Title
Webhook HMAC verification authenticates only the request body while `shop_domain` is trusted from an unsigned header, allowing shop-identity spoofing on custom webhook controllers - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
The `StrategySupplyMorpho` bug class is: a value that is validated/approved (`_asset`) is different from the value actually relied upon for the critical operation (`loanToken`), so trust established for one field is silently applied to a different, unverified field. The same class of bug exists in `ShopifyApp::WebhookVerification`: `hmac_valid?` only authenticates `request.raw_post` (the body), while the gem's own `shop_domain` helper — defined in the very same module and documented as the trusted tenant identifier for custom webhook controllers — is read straight from the unsigned `X-Shopify-Shop-Domain` header, which is never covered by the HMAC computation.

### Finding Description
`ShopifyApp::WebhookVerification#verify_request` computes `hmac_valid?(request.raw_post)` and only rejects the request if the HMAC over the raw body does not match the app's shared secret: [1](#0-0) 

The digest itself is computed purely over `data` (the body) and the app-wide `ShopifyApp.configuration.secret`/`old_secret` — no header, including the shop domain header, is part of the signed material: [2](#0-1) 

Yet the same module exposes `shop_domain`, sourced directly from the client-controlled `HTTP_X_SHOPIFY_SHOP_DOMAIN` header, with no cross-check against the HMAC-verified payload: [3](#0-2) 

The gem's documentation explicitly instructs developers to build custom webhook controllers on top of `WebhookVerification` and use `shop_domain` as the tenant identifier once the request "verifies" as legitimate: [4](#0-3) 

Because the app secret is shared across all shops that installed the app (it is not per-shop), any actor who controls one legitimately-installed shop can obtain a body + valid HMAC pair for real events from Shopify. Nothing in `verify_request` binds that HMAC to the `X-Shopify-Shop-Domain` header value, so the header can be altered to name an arbitrary victim shop domain while keeping the original (still-valid) body and HMAC. `verify_request` will pass, and the downstream job/controller code will process the payload as if it belongs to the spoofed `shop_domain`.

### Impact Explanation
This lets an attacker who has legitimate access to any shop that has installed the app forge webhook deliveries attributed to a different, unrelated shop's domain, as long as the body content stays HMAC-valid. Depending on the app's job logic (as shown in the generator templates and docs, jobs are queued with `shop_domain: shop_domain`), this can corrupt or leak data under the wrong tenant record, trigger shop-scoped side effects (e.g. mandatory privacy webhooks such as `shop/redact`, `customers/redact`) against a shop the attacker does not control, or otherwise achieve cross-shop data confusion — all without ever compromising the app's secret. This is a cross-shop access/data-integrity issue reachable by any anonymous or unrelated party that can install the app once.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on any shop (trivial for a public/embedded Shopify app) to obtain genuine webhook bodies/HMACs, and (2) sending an HTTP POST to the app's custom webhook endpoint with the captured body/HMAC and a modified `X-Shopify-Shop-Domain` header. No secret leakage, no cryptographic break, and no privileged access to the victim shop is required, making this a highly likely-to-be-reachable analog wherever the documented custom-controller pattern (`shop_domain` reliance) is used.

### Recommendation
Do not treat `shop_domain` (or any other header) as authenticated data derived from `verify_request`. Either:
1. Include the shop domain (and other identifying headers) as part of the HMAC-signed material checked in `hmac_valid?`, or
2. Cross-validate `shop_domain` against a shop identifier embedded in the verified body payload before using it for any tenant-scoped action, or
3. Document explicitly (and enforce in code) that `shop_domain` from `WebhookVerification` must never be trusted for tenant-scoped writes without an additional authenticated correlation to the verified payload.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. `carts/update`, including its raw body `B` and the Shopify-computed header `X-Shopify-Hmac-Sha256: H` (valid against the app's shared secret, per `hmac_valid?`).
2. Replay the exact same request to the app's custom webhook endpoint (built per the documented pattern using `ShopifyApp::WebhookVerification`), but set `X-Shopify-Shop-Domain: victim.myshopify.com` instead of the attacker's domain, keeping body `B` and header `H` unchanged.
3. `verify_request` calls `hmac_valid?(request.raw_post)`, which only recomputes the HMAC over `B` with the shared secret — this succeeds since `B`/`H` are unmodified and valid. [1](#0-0) 
4. The controller/job code, following the documented pattern, calls `shop_domain` and queues `SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)` — this now runs with `shop_domain == "victim.myshopify.com"` even though the payload originated from the attacker's shop. [5](#0-4)

```ruby
    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
```
