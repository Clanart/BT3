## Title
Path-containment check in `resolveWithin()` uses unanchored `String.startsWith`, allowing deep-link `filepath` to escape the intended repository directory - (File: `app/src/lib/path.ts`)

### Summary
The invariant this code is supposed to enforce is "the resolved path must be at or underneath the root directory." The bug in `_resolveWithin()` mirrors the reported smart-contract flaw: a boundary comparison that is *almost* right but omits the boundary itself. `getProfitSharingE18()` failed to properly gate on `MAX_ANNUALIZED_YEILD`; here `_resolveWithin()` fails to properly gate on the path-separator boundary between the root directory and any sibling that happens to share the same string prefix. [1](#0-0) 

### Finding Description
`_resolveWithin()` computes `realResolved` and checks containment with:

```ts
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`String.prototype.startsWith` is a raw character-prefix test, not a path-segment test. If `realRoot` is `/Users/victim/Documents/GitHub/repo`, then `/Users/victim/Documents/GitHub/repo-secret/config` also "starts with" `realRoot`, even though `repo-secret` is a completely distinct sibling directory, not a subdirectory of `repo`. The check does not verify that the character immediately following `realRoot` in `realResolved` is a path separator (or that the strings are equal), so the guard is bypassed whenever the caller can make the resolved path land in any directory whose name is prefixed by the root directory's name.

This function is the security backstop used by the "Open Repository from URL" deep-link flow. `parseAppURL()` extracts an attacker-controlled `filepath` query parameter directly from the `x-github-client://openRepo?...&filepath=...` URL with no path-restriction beyond regex checks on unrelated fields (`pr`, `branch`). [3](#0-2) 

`Dispatcher.openRepositoryFromUrl()` then only rejects absolute paths and otherwise trusts `resolveWithin(repository.path, filepath)` as the sole containment guard before revealing the resolved path in the OS file browser:

```ts
if (isAbsolute(filepath)) { ... return }
const resolved = await resolveWithin(repository.path, filepath)
if (resolved !== null) {
  shell.showItemInFolder(resolved)
} else {
  log.error(...)
}
``` [4](#0-3) 

Because `filepath` is relative (not absolute) but can still contain leading `..` segments, `Path.normalize()` does not strip them (there's nothing earlier in the same string to cancel a leading `..`), so `resolve(normalizedRoot, normalizedRelative)` can legitimately walk out of `repository.path` into a sibling directory such as `<GitHub folder>/<repoName>-something`. As long as that sibling's absolute path begins with the exact characters of `repository.path`, the flawed `startsWith` check incorrectly reports it as "within root."

### Impact Explanation
An attacker who controls a link the victim clicks (an `x-github-client://openRepo?url=...&filepath=..%2F<reponame>-evil%2Fsome-file` deep link, or a crafted "Open in Desktop" button on a malicious/compromised web page) can cause GitHub Desktop to resolve and reveal a file located outside the cloned repository directory — e.g., a sibling repository named to collide with a prefix of the target's directory name (`repo` vs `repo-secret`, `repo` vs `repository`, etc.). This directly matches the accepted impact class: "a link or deep link the user clicks" resulting in "file... read outside the repo." While the immediate primitive here reveals the file via `shell.showItemInFolder` (opening the OS file manager at that path) rather than exfiltrating content directly, it demonstrates the guard function used as the general path-containment primitive in the codebase is unsound, and the same flawed check is reused for reading files in other flows (e.g. Copilot conflict-file resolution at `buildConflictContext()` in `app/src/lib/copilot-conflict-context.ts`), where content is read into memory and sent onward. [5](#0-4) 

### Likelihood Explanation
The precondition is narrow: the victim's local directory layout must contain a sibling folder whose name shares a prefix with the target repository's directory name (e.g., cloning both `foo` and `foo-bar` under the same parent, a common occurrence for forks/variants), and the attacker needs the victim to click a crafted deep link — no local access, no malware, no leaked credentials required, consistent with the accepted threat model. The test suite already asserts correct behavior for `..`-only escapes and symlink escapes but does not test the "sibling directory sharing a string prefix" case, so this specific bypass is unguarded and untested. [6](#0-5) 

### Recommendation
Anchor the containment check on a path-segment boundary instead of a raw string prefix, e.g.:
```ts
return realResolved === realRoot ||
  realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the exact fix pattern from the source report — replace the incomplete boundary condition with the correct inclusive/exclusive boundary — so that only true subdirectories of `realRoot` (or `realRoot` itself) pass, and prefix-colliding siblings are correctly rejected.

### Proof of Concept
1. Victim has cloned two repositories side by side: `~/Documents/GitHub/repo` and `~/Documents/GitHub/repo-secret` (the latter containing sensitive files, e.g. a private fork).
2. Attacker sends the victim a link: `x-github-client://openRepo?url=https://github.com/victim/repo&filepath=..%2Frepo-secret%2Fsecret.txt`.
3. `parseAppURL()` extracts `filepath = "../repo-secret/secret.txt"` with no rejection (only absolute paths and invalid branch/pr chars are rejected).
4. `openRepositoryFromUrl()` calls `resolveWithin('~/Documents/GitHub/repo', '../repo-secret/secret.txt')`.
5. Inside `_resolveWithin`, `resolved` becomes `~/Documents/GitHub/repo-secret/secret.txt`; `realResolved.startsWith(realRoot)` evaluates true because `"...repo-secret/secret.txt".startsWith("...repo")` is true in plain string comparison.
6. The function returns the out-of-root path as valid, and `shell.showItemInFolder(resolved)` reveals `secret.txt` from the sibling repository to the attacker's chosen deep link target, despite the intended containment guard.
