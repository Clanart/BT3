### Title
Empty aggregate Schnorr signature trivially verifies — missing non-empty check in `SchnorrAggregate::verify`/`read` - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The reported bug class is "an empty/default credential is treated as valid, bypassing an authentication check." In Serai's half-aggregation implementation (`crypto/schnorr/src/aggregate.rs`), `SchnorrAggregate::read` accepts an aggregate containing zero `R` points with `s = 0`, and `SchnorrAggregate::verify` then returns `true` because the multiexp over zero statements plus `-s*G` (with `s = 0`) sums to the identity. Like hoppscotch's empty `ONBOARDING_RECOVERY_TOKEN`, the empty case is never rejected, so a 36-byte blob of zeros is accepted as a valid "signature" by any verifier that calls `verify` with an empty `keys_and_challenges` list.

### Finding Description
`SchnorrAggregate::read` reads a `u32` count and accepts `0`, then reads `s` via `C::read_F` which accepts the canonical zero scalar (`crypto/ciphersuite/src/lib.rs:74-83`). `verify` only checks `self.Rs.len() == keys_and_challenges.len()` and then computes `multiexp_vartime(&pairs).is_identity()`. With `Rs` empty and `s = 0`, `pairs` contains only `(-0, generator)` and the multiexp trivially sums to identity, so `verify` returns `true` (`crypto/schnorr/src/aggregate.rs:127-146`). Neither `read` nor `verify` enforces a non-empty aggregate — the producer side has such a check (`SchnorrAggregator::complete` returns `None` for empty input, line 176), but the verifier/decoder does not, so an attacker never needs an honest aggregator.

### Impact Explanation
Any protocol built on `SchnorrAggregate` that derives its `keys_and_challenges` set from attacker-influenced data — e.g., the subset of validators matching some attacker-chosen filter, or a batch where the attacker's entries were all filtered out — will accept the byte string `0x00000000 || 0x00…00` (4-byte zero length + 32-byte zero scalar) as a valid aggregate signature. This is a forged signature acceptance: the "empty credential" (no signers at all) passes verification, exactly mirroring the empty recovery token authenticating disclosure in the reference report.

### Likelihood Explanation
Exploitation requires a verifier to call `verify` with an empty `keys_and_challenges`, so impact depends on the integrator. However, nothing in the API documents that `verify` returns `true` for the empty set, and `read` actively enables the attack by deserializing the trivial forgery. An unprivileged party supplies only public bytes on the wire — no key material, collusion, or trusted position is required.

### Recommendation
Reject empty aggregates in `SchnorrAggregate::read` (error if `len == 0`) and defensively in `verify` (return `false` when `keys_and_challenges.is_empty()`), matching the producer-side invariant already enforced in `SchnorrAggregator::complete`. Also consider rejecting `s == 0` or identity `R` values per the strictness documented on `SchnorrSignature`.

### Proof of Concept
```rust
// crypto/schnorr/src/tests or any consumer
use schnorr::SchnorrAggregate;
use dalek_ff_group::Ristretto;

// Forged aggregate: u32 len = 0, then s = 0 (canonical zero scalar)
let mut forged = vec![0u8; 4];
forged.extend([0u8; 32]);

let agg = SchnorrAggregate::<Ristretto>::read(&mut forged.as_slice()).unwrap();
// Passes against an empty signer set — a "signature" by nobody verifies
assert!(agg.verify(b"dst", &[]));
```
Caveat: I verified the read/verify logic directly in `crypto/schnorr/src/aggregate.rs` and the canonical-zero acceptance in `crypto/ciphersuite/src/lib.rs`; the exploit's real-world severity depends on whether any Serai consumer calls `verify` with an attacker-influenceable empty key set, which I could not confirm within the in-scope crates.
