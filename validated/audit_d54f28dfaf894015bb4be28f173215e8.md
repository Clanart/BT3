### Title
Unvalidated participant indexes in PedPoP blame handling cause a reachable panic (DoS) on attacker-supplied blame accusations - (File: crypto/dkg/pedpop/src/lib.rs, crypto/dkg/pedpop/src/encryption.rs)

### Summary
CVE-2017-17432 is an OpenAFS denial of service where unvalidated fields in an Rx ack packet reach an integer underflow / assertion failure, crashing the system. The analog in Serai is `BlameMachine::blame` / `AdditionalBlameMachine::blame` in PedPoP: the `sender` and `recipient` `Participant` values (attacker-controlled `u16` indexes carried in, or implied by, a blame accusation message) are used to index `HashMap`s via the `[]` operator without membership checks. Any out-of-range participant index causes a panic, crashing the validator/processor evaluating blame.

### Finding Description
`BlameMachine::blame` delegates to `blame_internal`, which:

1. Calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`. If a `proof` is supplied, `decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` at `crypto/dkg/pedpop/src/encryption.rs:388`. `enc_keys` only contains entries for participants `1..=n` (populated by `Decryption::register` / `AdditionalBlameMachine::new`). A `recipient` index outside that set panics on `HashMap` indexing.
2. If decryption succeeds and the decrypted bytes are a canonical scalar, `blame_internal` calls `share_verification_statements(recipient, &self.commitments[&sender], ...)` at `crypto/dkg/pedpop/src/lib.rs:597-600`. `self.commitments[&sender]` panics for any `sender` not among the `1..=n` registered participants.

Unlike the DKG verification path (`verify_r1` uses `validate_map` to bound every index to `all_participant_indexes()`), the blame path performs no bounds check on `sender` or `recipient` before indexing. `Participant` is merely a non-zero `u16`, so any value in `1..=65535` is accepted by the type system while `commitments`/`enc_keys` only hold `n` entries. The code itself acknowledges this hazard: `AdditionalBlameMachine::new` documents that invalid commitments "may cause everything from inaccurate blame to panics" (`lib.rs:647-648`), but the panic on participant index is reachable with fully valid commitments.

### Impact Explanation
An unprivileged party who can submit a blame accusation (a peer in the DKG, or anyone able to feed messages into a node's blame evaluation) can crash the process evaluating blame by naming a `sender` or `recipient` index greater than `n` — for example `Participant::new(n + 1)`. Crafting the required inputs is feasible: the accusing party controls the `EncryptedMessage` and can produce a valid per-message PoP Schnorr signature (they know the ephemeral key they chose) and a valid `EncryptionKeyProof` DLEq for a registered `recipient`, causing execution to reach the panicking index. This aborts processing of the blame epoch — and if the panic is not caught, the node itself — matching the CVE's "assertion failure → application crash" class (availability-only impact).

### Likelihood Explanation
The panic requires only that a node evaluate a blame claim where the named sender/recipient is not a registered participant. Blame messages are, by design, exchanged between mutually distrustful parties during abnormal DKG termination — precisely the scenario where malformed accusations are expected. No threshold of colluders, no secret knowledge, and no protocol violation beyond sending a syntactically valid message with an out-of-range participant index is needed. Any `unwrap()`-free `HashMap` `[]` access on untrusted indexes is a textbook reachable panic.

### Recommendation
Replace panicking index operations with lookups that return `PedPoPError`/`DecryptionError`:
- In `Decryption::decrypt_with_proof`, use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` instead of `self.enc_keys[&decryptor]`.
- In `blame_internal`, resolve `sender`/`recipient` via `.get()` and treat a missing sender entry as `sender`-faulty (or an explicit error) rather than indexing.
- Add a `Participant`-in-range check (`u16::from(p) <= n`) at the top of `BlameMachine::blame` and `AdditionalBlameMachine::blame`.

### Proof of Concept
Conceptual (library-level):

```rust
// n = 10 participant DKG completed; we hold an AdditionalBlameMachine built from
// the 10 authenticated commitment messages.
let mut machine = AdditionalBlameMachine::<Ristretto>::new(context, 10, commitment_msgs).unwrap();

// Attacker (or a buggy relay) submits a blame accusation naming a non-existent
// sender. `msg` is any EncryptedMessage with a valid PoP (the accuser knows the
// ephemeral key), and `proof` is a valid DLEq for a real decryptor's key.
let sender = Participant::new(11).unwrap();     // out of range: commitments has 1..=10
let recipient = Participant::new(1).unwrap();

// Path A — panics at `self.commitments[&sender]` in blame_internal
// (crypto/dkg/pedpop/src/lib.rs:599)
machine.blame(sender, recipient, msg, Some(proof));

// Path B — equally: recipient = Participant::new(11) panics at
// `self.enc_keys[&decryptor]` (crypto/dkg/pedpop/src/encryption.rs:388)
// whenever `proof` is Some and the message PoP verifies.
```

Both paths terminate the calling thread via `HashMap` index panic rather than returning a `PedPoPError`, giving a remote crash reachable solely from attacker-supplied participant indexes and message bytes.
