## Title
Loose substring match on attacker-controlled `WWW-Authenticate` header lets a malicious git remote spoof a "GitHub Enterprise" endpoint and trigger unauthorized account sign-in/binding - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
This is the closest analog to the reported bug class: a parsing routine that classifies attacker-supplied data using an overly permissive match (the Noir bug used a non-greedy/last-match regex that let extra `<...>` content hijack the parsed value; here a plain `String.includes()` check on an untrusted header lets attacker-controlled text hijack the classification of a remote endpoint). The corrupted value is the return of `getEndpointKind()`, which decides whether an arbitrary git host should be treated as a first-party "GitHub" endpoint.

### Finding Description
`getEndpointKind()` is invoked by the git-credential trampoline every time Git needs credentials for an HTTP(S) remote (clone/fetch/push). When the endpoint isn't already recognized as `github.com`/GHE, Desktop falls back to inspecting the `WWW-Authenticate` header that the *remote server itself* returned to Git: [1](#0-0) 

The check is a bare substring test:
```
if (v.includes('realm="GitHub"')) {
  return 'enterprise'
}
```
Any HTTP server the user adds as a remote (or any MITM/malicious proxy sitting on the network path of a legitimate remote) fully controls this header and can trivially include the literal substring `realm="GitHub"` in its `WWW-Authenticate` response to a Git HTTP auth challenge. There is no validation that the value is a well-formed, single-token realm, that it originates from a real GitHub product, or that it matches the challenged host in any other way — this is the same class of defect as the report's flaw: a "detect substring/last-match" heuristic standing in for a real, bounded parse.

Once `getEndpointKind` returns `'enterprise'` for the attacker's host, `getCredential()` treats the endpoint as first‑party: [2](#0-1) 

Because the attacker's host is not a previously-registered account, `accounts.some(a => a.endpoint === apiEndpoint)` is false, so Desktop calls `ui.promptForGitHubSignIn(endpoint)` and, on success, `credWithAccount` stores the resulting `Account` bound to `endpoint` — the attacker-controlled host — as if it were a legitimate "sign in to GitHub Enterprise" account.

### Impact Explanation
- The victim only performs an ordinary `clone`/`fetch`/`push` against a remote that returns a crafted `WWW-Authenticate` header (attacker controls a git remote/proxy response — an explicitly in-scope primitive).
- Desktop's UI presents its native "Sign in to GitHub"/"GitHub Enterprise" flow for a host that is not actually GitHub-branded, and on completion binds an `Account` object to that attacker endpoint as though it were a genuine GitHub Enterprise Server, i.e. unauthorized account binding driven entirely by server-controlled response data rather than user intent or verified endpoint metadata.
- This also suppresses the normal "generic" credential path (`storeCredential`/`eraseCredential` early-return when `endpointKind !== 'generic'`), silently changing how credentials for that host are subsequently managed by Desktop.

### Likelihood Explanation
High for the classification bypass itself: any HTTP(S) git server (including one the user is simply trying/exploring, or one reached via a compromised network path/proxy) can add this header without any special privileges, and the check requires nothing more than an exact literal substring — no signature, TLS pinning, or endpoint allow-listing. The subsequent sign-in prompt does require the user to proceed through the sign-in dialog, but the trigger condition (misclassification) is fully attacker-controlled and silent.

### Recommendation
Do not use substring matching on `WWW-Authenticate` to make trust decisions. At minimum:
- Parse the header properly (token/parameter grammar) and require the realm parameter to equal `GitHub` exactly, not merely contain it.
- Never let a raw header value from an unauthenticated/untrusted host promote that host to a privileged classification (`'enterprise'`) that changes credential-handling and sign-in UI. Corroborate with an actual API probe (`isGitHubHost`, already used later in the function) before offering the "Sign in to GitHub" flow, instead of trusting a header from the very same untrusted server as a shortcut.

### Proof of Concept
1. Attacker stands up an HTTPS git server at `https://attacker.example/victim/repo.git` (or MITMs an HTTP git remote) and configures it to answer an unauthenticated Git smart-HTTP request with:
   ```
   HTTP/1.1 401 Unauthorized
   WWW-Authenticate: Basic realm="GitHub"
   ```
2. Victim adds this URL as a remote in GitHub Desktop and performs `fetch`/`clone`/`push`.
3. Git invokes Desktop's credential trampoline; `getEndpointKind` (`app/src/lib/trampoline/trampoline-credential-helper.ts:137-179`) sees the `wwwauth[...]` entry containing `realm="GitHub"`, matches the substring check, and returns `'enterprise'`.
4. `getCredential` finds no existing account for `attacker.example`, so it calls `ui.promptForGitHubSignIn('https://attacker.example')`, presenting Desktop's trusted "Sign in to GitHub Enterprise" UI for the attacker's host.
5. If the victim completes sign-in, `credWithAccount` persists an `Account` bound to `attacker.example`, believing it to be a legitimate first-party GitHub Enterprise account added to Desktop. [3](#0-2) [2](#0-1)

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

const getEndpointKind = async (cred: Credential, store: Store) => {
  const credentialUrl = getCredentialUrl(cred)
  const endpoint = `${credentialUrl}`

  if (isGist(endpoint)) {
    return 'generic'
  }

  if (isDotCom(endpoint)) {
    return 'github.com'
  }

  if (isGHE(endpoint)) {
    return 'ghe.com'
  }

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  const existingAccount = await findGitHubTrampolineAccount(store, endpoint)
  if (existingAccount) {
    return isDotCom(existingAccount.endpoint) ? 'github.com' : 'enterprise'
  }

  // All GitHub hosts use HTTPS, so if the protocol is not HTTPS we can
  // assume that this is not a GitHub host.
  if (credentialUrl.protocol !== 'https:') {
    return 'generic'
  }

  return (await isGitHubHost(endpoint)) ? 'enterprise' : 'generic'
}
