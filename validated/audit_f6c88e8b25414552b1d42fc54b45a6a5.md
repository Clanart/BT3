### Title
Partial-commit staging re-diffs the working tree at commit time and reapplies stale line-index selections, silently committing attacker-modified content - ([File: app/src/lib/git/apply.ts])

### Summary
GitHub Desktop lets a user select individual lines/hunks of a modified file for a partial commit. The selection the user makes in the UI is stored as *line indices* against the diff that was rendered at review time. When the commit is actually created, Desktop does not reuse that reviewed diff — it re-runs `git diff` against the current working-tree file and reapplies the old line-index selection to the new diff. If the file content on disk changes between "user reviews/selects lines" and "commit is executed," the index-based selection silently applies to different content than what the user approved, exactly mirroring the reported bug class: a decision (vote/selection) made at time T is not frozen, and a later "finalize" step (`finalize`/`createCommit`) re-reads live, attacker-influenceable state instead of the snapshot the user actually approved.

### Finding Description
The partial-commit path is:
- `applyPatchToIndex(repository, file)` re-fetches the diff fresh from disk via `getWorkingDirectoryDiff(repository, file)` at commit time, rather than using the diff object the user reviewed in the UI: [1](#0-0) 
- It then hands that freshly-fetched diff, together with `file.selection` (a `DiffSelection` populated earlier from the reviewed diff's line indices), to `formatPatch`: [2](#0-1) 
- `formatPatch` builds the patch purely by walking the *new* diff's hunks and asking `file.selection.isSelected(absoluteIndex)` for each line, where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` is computed against the *current* diff structure, not the one the user actually looked at: [3](#0-2) 
- This patch is then applied directly to the git index with `git apply --cached`, and `createCommit` proceeds to unconditionally stage and commit whatever `stageFiles`/`applyPatchToIndex` produced: [4](#0-3) [5](#0-4) 

There is no check anywhere in `_commitIncludedChanges` (the top-level commit entry point) that the working-directory content or diff shape is unchanged since the user last reviewed and selected lines — it simply takes whatever `selection` is currently attached to the in-memory `WorkingDirectoryFileChange` objects and calls `createCommit`: [6](#0-5) 

Because Desktop polls/refreshes working-directory status independently of user review (background status refresh, file watchers, or a build/format-on-save tool touching the file), and because the selection is line-index based rather than content-hash or blob-based, an on-disk mutation between "user selects lines N–M to include" and "user clicks Commit" is silently reapplied to whatever lines N–M now happen to correspond to in the new diff. Nothing re-validates that the diff the selection was built from still matches the diff being staged.

This is the structural analog of the reported Voter.sol bug: `_tallyAutoVotes` reads live `autoOption`/balance at finalize time instead of freezing it at epoch end; here, `applyPatchToIndex`/`formatPatch` read the live on-disk diff at commit time instead of freezing/validating against the diff the user actually reviewed and selected lines from.

### Impact Explanation
The corrupted value is the git index / resulting commit content: a user can be made to commit lines they never reviewed or approved, or fail to commit lines they did approve, without any warning. Since Desktop shows the commit summary/diff as the basis of trust for "what will be committed," this breaks the core invariant that "what the user selected is what gets committed and pushed." An attacker who can transiently modify a tracked file on disk during the review→commit window (e.g., via a build tool, editor plugin, linter/formatter run as part of a workflow, a symlinked/shared file, or a race with another process touching the working tree) can cause silent corruption of the commit that is subsequently pushed to a shared/remote repository — potentially injecting unreviewed code into history under the victim's authorship.

### Likelihood Explanation
This requires some ability to modify the working-tree file content in the window between the user's line selection and the commit action. This is plausible in ordinary developer workflows without any "attacker with local/physical access" assumption in the traditional sense — e.g., an npm/build script, git hook, IDE auto-formatter, or file-watcher process running as part of the repository's own tooling (which the user does not control and may be triggered automatically) can rewrite files during that window; the user is simply doing normal work (reviewing a diff, selecting some lines, then clicking Commit some time later). No elevated privileges are needed and no unnatural steps are required from the victim.

### Recommendation
Freeze the diff snapshot used for line selection and reuse the exact same diff object when building the patch in `applyPatchToIndex`, instead of re-fetching `getWorkingDirectoryDiff` at commit time. If the working-tree file has changed (e.g., detect via mtime/hash or by comparing the newly-fetched diff to the one the selection was derived from) between selection and staging, abort the partial commit and force the user to re-review the diff before proceeding, analogous to freezing auto-vote choices after the epoch/decision point.

### Proof of Concept
Conceptual reproduction (cannot be executed here, but follows directly from the code above):
1. User modifies `foo.txt`, opens the Changes view; Desktop computes a diff with hunks and shows it.
2. User selects only lines 1–5 (via `DiffSelection`) for a partial commit and leaves the Commit dialog open/types a message (introducing a delay).
3. Before the user clicks "Commit," a background process (linter, formatter-on-save, build script, or any tool run against the repo) rewrites `foo.txt` such that the diff hunks shift or content at "line 1–5" now corresponds to entirely different, attacker/tool-controlled text.
4. User clicks "Commit." `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` re-runs `getWorkingDirectoryDiff` (new content) and reapplies the stale `file.selection` indices via `formatPatch`, producing a patch from the *new* file content at those same line positions.
5. The resulting commit contains content the user never reviewed, silently pushed to the remote if the user then pushes — with no diff mismatch warning shown anywhere in the flow.
