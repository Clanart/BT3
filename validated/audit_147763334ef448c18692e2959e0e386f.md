### Title
Unbounded attacker-controlled allocation in `ThresholdKeys::read` enables amplified memory exhaustion - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::<C>::read` deserializes the threshold parameters `t`, `n`, `i` directly from the input stream, then uses the attacker-controlled `n` to size a `Vec::with_capacity` allocation and to drive two unbounded read loops — all before `ThresholdParams::new` validates that `n` is sensible. This is a direct analog of CVE-2017-11528 (`ReadDIBImage` memory exhaustion via a crafted file): an untrusted serialized key blob of only a few dozen bytes can force a disproportionate allocation and CPU work.

### Finding Description
In `crypto/dkg/src/lib.rs`, `ThresholdKeys::read` performs the following:

- Reads `t`, `n`, `i` as raw `u16`s from the stream (lines 591-602).
- If the interpolation tag is `0` (`Interpolation::Constant`), it allocates `Vec::with_capacity(usize::from(n))` — up to 65,535 `C::F` elements (~2 MiB on a 32-byte field) — from an input that at that point may be only ~15 bytes long (lines 606-613).
- It then iterates `for _ in 0 .. n` calling `C::read_F`, and iterates `for l in 1 ..= n` calling `C::read_G` into a `HashMap` (lines 608-623).
- Only *after* all of this is `ThresholdParams::new(t, n, i)` invoked to check `t <= n` and participant validity (lines 625-630).

So the size of the allocations and the iteration counts are fully attacker-controlled and are checked only after the work is done. A prefix of a handful of bytes (valid `C::ID`, `t`, `n = 0xFFFF`, `i`, interpolation tag `0`) triggers the ~2 MiB `with_capacity` allocation before any further bytes need to be present. Supplying garbage bytes additionally forces 65,535 failed-then-retried field/point deserialization attempts and HashMap insertions per message.

`ThresholdKeys::read` is explicitly in the set of deserialization APIs reachable with untrusted bytes (it is the persistence format for threshold keys and is loaded from disk/state the attacker can influence, e.g., supplied key material or stored blobs).

### Impact Explanation
Each crafted input of tens of bytes causes a multi-megabyte heap allocation plus up to ~131k deserialization attempts. Repeated submissions produce sustained heap churn and CPU burn, degrading or aborting the signer/DKG service — a denial of service of the same class (memory exhaustion via crafted input bytes) as CVE-2017-11528. On 64-bit systems `Vec::with_capacity` of this size won't panic immediately, but concurrent or repeated requests multiply the footprint linearly with zero cost to the attacker beyond sending a few bytes.

### Likelihood Explanation
Any code path that feeds untrusted or third-party-originated bytes to `ThresholdKeys::read` (restoring keys, importing shares, gossiped state) is exploitable. The attacker needs no key material, no participation in the protocol, and no valid data — only control over the serialized bytes. The `n` field is read before any length-vs-content cross-check, so truncated inputs still trigger the allocation.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` **before** performing any allocation or loops sized by `n`. Additionally, avoid `Vec::with_capacity(usize::from(n))` / pre-sized `HashMap`s on unvalidated counts — either use `Vec::new` and let it grow with actually-read elements, or cap `n` at a protocol maximum (e.g., the 255-participant bound implied by `Participant`) and reject early.

### Proof of Concept
```rust
use std::io;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;

// C: any in-scope Ciphersuite, e.g. Ristretto or Secp256k1
fn poc<C: Ciphersuite>() {
  let mut buf = vec![];
  // Valid curve ID so the early rejection path isn't hit
  buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
  buf.extend(C::ID);
  buf.extend(1u16.to_le_bytes());      // t = 1
  buf.extend(u16::MAX.to_le_bytes());  // n = 65535  <- attacker controlled
  buf.extend(1u16.to_le_bytes());      // i = 1
  buf.push(0);                         // Interpolation::Constant -> Vec::with_capacity(65535)

  // Only ~ID.len() + 9 bytes supplied; ThresholdKeys::read allocates
  // 65535 * size_of::<C::F>() and attempts 65535 read_F calls.
  let _ = ThresholdKeys::<C>::read(&mut buf.as_slice());
}
```
