### Title
Missing validation of `Kip71GasTarget` (and related KIP‑71 parameters) allows a governance‑set zero `GasTarget` to cause a division‑by‑zero panic in `NextMagmaBlockBaseFee`, halting block production on every node - ([File: params/kip71_config.go])

### Summary
The KIP‑71 (Magma) dynamic base‑fee parameters (`GasTarget`, `LowerBoundBaseFee`, `UpperBoundBaseFee`, `MaxBlockGasUsedForBaseFee`) are registered as governance parameters with a `noopFormatChecker`, meaning no range/non‑zero validation is performed before they are accepted and written into `ChainConfig.Governance.KIP71`. Only `BaseFeeDenominator` has both a non‑zero check and a runtime fallback. `NextMagmaBlockBaseFee` in `params/kip71_config.go` divides by `gasTarget` without checking for zero and without any fallback (unlike the `baseFeeDenominator` case, which explicitly falls back to `64` when zero). If `GasTarget` is set to `0` through governance, every node that computes the next base fee — which happens on every single block after any gas is used — will hit an integer divide‑by‑zero and panic, crashing every honest node's process. This is directly analogous to the ZeroExExchangeWrapper bug pattern: a price/parameter library accepts values that a downstream price-computation function has not defended against, leading to guaranteed reverts (here, fatal panics) whenever the read path is exercised.

### Finding Description
`NextMagmaBlockBaseFee` computes the delta of the base fee using `gasTarget` as a divisor in three code paths (`parentGasUsed == gasTarget`, `>`, `<`): [1](#0-0) [2](#0-1) 

Notice the explicit defensive fallback that exists **only** for `BaseFeeDenominator`: [1](#0-0) 

No equivalent guard exists for `gasTarget` (`kc.GasTarget`), which is used directly as a divisor at `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` in both the "usage above target" and "usage below target" branches: [3](#0-2) [4](#0-3) 

The governance parameter registry that controls how `GasTarget`/`LowerBoundBaseFee`/`UpperBoundBaseFee`/`MaxBlockGasUsedForBaseFee` are validated before being accepted uses a no‑op checker, unlike `Kip71BaseFeeDenominator` which explicitly rejects zero: [5](#0-4) 

Because `x.Div(x, y)` on `*big.Int` with `y == 0` triggers a Go runtime panic ("division by zero"), any node that reaches this code path with `GasTarget == 0` will crash. `NextMagmaBlockBaseFee` is called from the block/worker header-assembly and validation paths (`work/worker.go`, and block validation uses `KIP71Config.VerifyMagmaHeader` -> `NextMagmaBlockBaseFee`), so this affects both block proposers building new blocks and all full nodes validating headers.

### Impact Explanation
If `GasTarget` (or, by extension, other unchecked KIP‑71 fields whose values could coincide with edge conditions) is set to `0` via a governance vote, every node computing the next block's base fee panics as soon as a block consumes any gas above the (zero) target, which is essentially every block after the parameter change. This is a chain‑halting, consensus‑wide denial of service — not a localized revert for a single caller, but a crash of the node process itself across the network, since every CN, PN, and EN independently executes `NextMagmaBlockBaseFee`. This maps to the "state divergence between honest nodes" / "acceptance of invalid transaction or block" class of impact (nodes crash and cannot progress, and any node running a hardened/patched validator might behave differently, creating a chain split risk), which satisfies the medium/high/critical bar required.

### Likelihood Explanation
The parameter is only settable via the governance mechanism (an allowed reachable path per scope), and would require a validator/governance vote to set `GasTarget = 0`. This could occur due to a governance misconfiguration/typo, or a malicious governing node/council member intentionally submitting the parameter — no cryptographic or consensus-breaking capability is needed, only a successful governance parameter update, which is a normal, expected transaction/vote flow. Given the complete absence of a format check (contrasted with the explicit `!= 0` check on the analogous `BaseFeeDenominator` field), this is a straightforward oversight rather than a deep edge case, making it plausible.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` (and ideally `Kip71MaxBlockGasUsedForBaseFee`, `Kip71LowerBoundBaseFee`, `Kip71UpperBoundBaseFee`) in `kaiax/gov/param.go` that rejects `0`, mirroring the existing check on `Kip71BaseFeeDenominator`. Additionally, add a defensive runtime fallback in `NextMagmaBlockBaseFee` (`params/kip71_config.go`) analogous to the existing `baseFeeDenominator == 0` fallback, so that a zero `gasTarget` cannot cause a division-by-zero panic even if it somehow reaches this function (e.g., via a legacy genesis config or a future code path that bypasses `FormatChecker`).

### Proof of Concept
1. Via the governance module, submit a parameter vote/update setting `Kip71GasTarget = 0` (accepted because `FormatChecker` for this parameter is `noopFormatChecker`, per `kaiax/gov/param.go:324-334`).
2. Once the vote is applied to `ChainConfig.Governance.KIP71.GasTarget`, the next block that uses any gas (`parentGasUsed > 0 = gasTarget`) causes every node calling `NextMagmaBlockBaseFee` (proposers assembling headers in `work/worker.go`, and validators verifying headers via `KIP71Config.VerifyMagmaHeader`) to execute:
   ```go
   gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget) // = parentGasUsed
   x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
   y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 -> panic: division by zero
   ``` [3](#0-2) 
3. Every node in the network panics simultaneously while attempting to compute the base fee for the next block, halting block production/validation network‑wide.
