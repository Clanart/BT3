## Title
Divergent conflict-marker boundary parsing between `extractConflictHunks` and `reassembleResolvedFile` allows silent corruption of the file Copilot conflict resolution commits - (File: `app/src/lib/copilot-conflict-context.ts`, `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
GitHub Desktop's Copilot-assisted conflict resolution feature parses a conflicted file's conflict-marker regions twice, using two independently written scanners that make different assumptions about where a conflict block begins and ends. `extractConflictHunks` is used to build the prompt sent to the model, while `reassembleResolvedFile` is used later to splice the model's per-hunk output back into the original file. When the on-disk file contains marker-like text that is ambiguous (e.g. a stray `>>>>>>>`-looking line before the first real `=======` separator), the two scanners disagree about which lines constitute "the hunk," even though they may agree on the total hunk *count*. Because `validateResolutionPaths` only checks the hunk **count**, not boundaries, this mismatch passes validation and the model's resolution content is spliced into the wrong location on disk, while unrelated lines containing literal marker-like text are copied through verbatim into the final committed file.

### Finding Description
`extractConflictHunks` (`app/src/lib/copilot-conflict-context.ts`) collects the "ours" section of a hunk by scanning forward and breaking only on a base marker (`|||||||`) or separator (`=======`) — it never checks for a `>>>>>>>` theirs-marker while collecting ours content: [1](#0-0) 

`reassembleResolvedFile` (`app/src/lib/copilot-conflict-resolution.ts`) instead looks ahead from the `<<<<<<<` line and treats the block as valid only if a separator is seen *before* the first `>>>>>>>` it encounters; if a `>>>>>>>`-looking line appears first, it immediately (and independently of `hasSeparator`) fixes `closingIndex` there: [2](#0-1) 

Given a file where a `>>>>>>>`-looking line of ordinary content appears between a `<<<<<<<` marker and the real `=======`/`>>>>>>>` pair of a *second*, well-formed conflict below it, `extractConflictHunks` folds everything into a single hunk whose `oursContent` includes the stray marker-like text and the second block's own `<<<<<<<`/`ours` lines as literal text. `reassembleResolvedFile`, however, treats the first `<<<<<<<` as malformed (no separator before the first `>>>>>>>`-looking line), copies it and the following lines through **verbatim**, and only recognizes the *second*, well-formed block as "the hunk" to replace. Both scanners end up reporting exactly one hunk, so `validateResolutionPaths` — which only compares hunk counts — sees no discrepancy: [3](#0-2) 

The model's resolution (computed for the *entire* region as understood by `extractConflictHunks`, including the literal `<<<<<<<`/`>>>>>>>`-looking lines it was shown as "ours" content) is then spliced by `reassembleResolvedFile` only over the second block, while the first block's literal marker-like lines are left untouched in the output: [4](#0-3) 

Nothing downstream re-validates the *reassembled* file for leftover conflict markers or structural correctness — the per-hunk marker check only inspects the model's own `resolvedContent` string, not the final spliced file: [5](#0-4) 

The corrupted content is written straight to disk and staged without further inspection: [6](#0-5) 

### Impact Explanation
This causes silent corruption of what the user commits: the file written to disk and staged via `git add` can contain leftover literal conflict-marker-like lines (potentially reintroducing an actual unresolved-looking conflict block into version-controlled source, which may break builds or reintroduce logic from the wrong side) plus the model's merged content spliced at the wrong offset relative to what it was actually asked to resolve. Since the "Result" dialog and diff view are driven by the same `resolvedContent`, the user has no strong signal that the write diverged from the well-formed hunks they reviewed conceptually — matching the report's "corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
This requires the attacker to control content of a file participating in a merge/rebase/cherry-pick brought in via a crafted commit/branch (a normal, unprivileged Desktop workflow: cloning/fetching a repo and merging/rebasing against attacker-supplied branches). The triggering condition — an ordinary line of file content that happens to match the marker regex `^>{7}(?:\s|$)` (7+ `>` characters followed by whitespace/EOL) positioned between a `<<<<<<<` and its intended `=======` — is a narrow but realistic content pattern (e.g. ASCII art, changelog formatting, generated diff/patch fixtures, or a file documenting Git conflict markers) that an attacker fully controls in their commit.

### Recommendation
Make `reassembleResolvedFile` reuse the exact same boundary logic as `extractConflictHunks` (ideally by having reassembly consume the actual `IConflictHunk` objects/offsets already computed during extraction rather than re-scanning the raw text with different rules), and add a post-reassembly check that rejects (falls back to skipping the file / surfacing an error) any reassembled file that still contains conflict-marker patterns, rather than trusting hunk-count parity as proof the two parses agree.

### Proof of Concept
Given a conflicted file on disk:
```
<<<<<<< HEAD
line A
>>>>>>> not-a-real-marker-but-matches-regex
line B
<<<<<<< HEAD
line C
=======
line D
>>>>>>> branch2
trailing content
```
1. `extractConflictHunks` produces exactly one hunk with `oursContent = "line A\n>>>>>>> not-a-real-marker-but-matches-regex\nline B\n<<<<<<< HEAD\nline C"` and `theirsContent = "line D"` — this is what gets sent to Copilot in the prompt (`app/src/lib/copilot-conflict-context.ts:200-237`).
2. Copilot returns one `resolvedContent` for this single hunk, based on merging that entire region.
3. `validateResolutionPaths` sees `hunks.length === 1 === expectedCount` and passes (`app/src/lib/copilot-conflict-resolution.ts:509-520`).
4. `reassembleResolvedFile` treats the first `<<<<<<<` as malformed (no separator before the first `>>>>>>>`-looking line) and copies lines 0-3 through **verbatim**, including the literal `<<<<<<< HEAD` and the fake `>>>>>>>` line; it only replaces the *second* block (lines 4-8) with the model's `resolvedContent` (`app/src/lib/copilot-conflict-resolution.ts:559-591`).
5. The final file written via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staged via `git add` contains a stray, uncommented `<<<<<<< HEAD` marker line plus content misapplied relative to what the model actually analyzed — silently committed if the user accepts the Copilot resolution (`app/src/lib/stores/app-store.ts:7258-7267`).
