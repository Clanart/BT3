### Title
Fee-Token Migration Can Be Permanently Griefed via Direct ERC20 Transfer to `EvmHost` — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal()` blocks a fee-token change with a strict, externally-manipulable balance check: `if (balance != 0) revert CannotChangeFeeToken();`. Since anyone can transfer even 1 wei of the current fee token directly to the host contract at any time, an attacker can keep this check permanently true, blocking Hyperbridge governance from ever migrating the protocol fee token via cross-chain `updateHostParams` — the exact same "strict-equality/inequality DoS via unsolicited direct transfer" primitive as the reported `HarTokenSale.finalizeSettlement()` bug.

### Finding Description
`updateHostParamsInternal` is the internal function that applies a `HostParams` update dispatched by cross-chain governance through `HostManager.onAccept` → `IHostManager(_params.host).updateHostParams(hostParams)`: [1](#0-0) 

Before committing new params, it guards against changing the fee token while the host still holds a balance of the old one: [2](#0-1) 

`balance` is read live via `IERC20(oldFeeToken).balanceOf(address(this))` — a value any external account can influence merely by calling `oldFeeToken.transfer(hostAddress, 1)`. There is no allowlist or authentication on ERC20 `transfer`; anyone holding even a dust amount of the current fee token can send it directly to the `EvmHost` contract address at any time, including immediately before (or independent of) the governance message being processed, and keep `balance != 0` forever.

Unlike the original `HarTokenSale` report where the attacker had to front-run a specific pending transaction, here the attacker does not even need to front-run: they can pre-emptively donate 1 wei of the fee token to the host contract at any point, and the check will keep failing on every future attempt to migrate the fee token, since:
- The host has no function to sweep/rescue an old fee token's dust balance before a migration.
- `withdraw()` (the only outbound-transfer path, also `restrict(_hostParams.hostManager)`) requires another cross-chain governance round-trip and itself is silent about clearing this specific residual-balance guard for the specific token being migrated away from.
- Nothing prevents the same griefer from re-donating another 1 wei immediately after any withdrawal clears the balance, re-arming the block before the next `updateHostParams` message lands.

### Impact Explanation
This permanently blocks a critical, privileged, cross-chain-governed state transition (fee-token migration) on the ISMP host contract — the same class of impact as the seed report (`finalizeSettlement()` DoS blocking refunds forever). It falls under "logic attacks" / DoS of core bridge/host-management execution reachable by an unauthorized, unprivileged actor, without needing a malicious relayer, prover, or governance actor — matching the required Hyperbridge impact gate (cross-chain admin/host-management effects reachable through unauthenticated message flow, in this case an unauthenticated direct token transfer that permanently corrupts a state precondition the privileged path relies on). While it does not directly steal funds, it can permanently strand governance's ability to react to a compromised/deprecated fee token (e.g., a token that needs to be migrated away from due to a vulnerability or depeg), which can cascade into broader protocol dysfunction since `feeToken()` is used pervasively across dispatch/handler fee accounting.

### Likelihood Explanation
High. The cost to the attacker is 1 wei of the fee token (or any nonzero dust amount) and a single unauthenticated ERC20 `transfer` call — no special timing, no front-running of a specific mempool transaction, and no privileged role required. Once governance's queued `updateHostParams` message with a new `feeToken` attempts to land on this EVM host, it will revert with `CannotChangeFeeToken()` as long as the attacker keeps re-donating dust after each withdrawal attempt.

### Recommendation
Do not gate the fee-token change on the *contract's* raw balance, which is attacker-controllable. Options:
- Track internally-accounted "protocol-owned" balance of the old fee token (distinct from the raw `balanceOf`) and require that internal accounting to be zero, or
- Allow `updateHostParams` to proceed regardless of stray token balance, and instead require/allow an explicit sweep of the old fee token's balance to the new fee-token-designated treasury/beneficiary as part of the same governance-authorized transaction (e.g., extend `updateHostParamsInternal` to auto-forward any residual `oldFeeToken` balance to `params.admin`/treasury rather than reverting), or
- Replace the strict `balance != 0` revert with a bounded tolerance/sweep-then-proceed pattern so unsolicited dust transfers cannot indefinitely block governance.

### Proof of Concept
1. Assume `EvmHost.feeToken() == USDT` and governance wants to migrate to `USDC` via a cross-chain `updateHostParams` message with `params.feeToken = USDC`.
2. Attacker (any address holding USDT) calls `USDT.transfer(address(evmHost), 1)` at any time — no permission required.
3. When the governance-dispatched `updateHostParams` message is delivered through `HostManager.onAccept` → `EvmHost.updateHostParams` → `updateHostParamsInternal`, the check
   ```solidity
   uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
   if (balance != 0) revert CannotChangeFeeToken();
   ```
   sees `balance == 1` (wei) and reverts with `CannotChangeFeeToken()`, aborting the entire governance update (including all the other legitimate param changes bundled in the same call).
4. Attacker repeats step 2 after any subsequent `withdraw()` clears the balance, indefinitely re-arming the block. [2](#0-1)
