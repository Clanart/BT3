### Title
Gasless module classifies ApproveTx/SwapTx by calldata alone, ignoring `tx.Value()`, allowing native KAIA sent with an approve/swap call to be silently absorbed instead of refunded/accounted - (File: kaiax/gasless/impl/getter.go)

### Summary
The `receiveFunds` bug class describes a function that determines the "kind" of deposit purely from a subset of parameters (token address / volume) while ignoring `msg.value`, so native protocol tokens sent alongside an ERC20 deposit are silently un-tracked and become unrecoverable by the sender. The Kaia gasless module has an analogous classification flaw: `decodeFunctionCall`, used by both `decodeApproveTx` and `decodeSwapTx`, classifies a transaction as a gasless `ApproveTx`/`SwapTx` purely from `tx.Type()`, `tx.To()`, and the 4-byte selector plus ABI-decoded calldata — it never inspects or requires `tx.Value() == 0`.

### Finding Description
`decodeFunctionCall` in `kaiax/gasless/impl/getter.go` only checks the tx type, destination, and function selector: [1](#0-0) 

`IsApproveTx`/`IsSwapTx` (and thus `IsModuleTx`, used by the tx pool to decide gasless bundling) rely solely on this decoding, with no validation that `tx.Value()` is zero: [2](#0-1) [3](#0-2) 

The repay/lend accounting (`repayAmount`, `lendAmount`) used to compute how much the proposer lends and expects to be repaid is derived only from `tx.Fee()` (gas price × gas), completely independent of any `tx.Value()` the sender attached to the ApproveTx/SwapTx: [4](#0-3) 

Because the gasless-pattern recognition, balance checks (`checkBalanceForApprove`/`checkBalanceForSwap`), and repay-amount verification never reference or constrain `msg.value`, a user (or gasless "sender" as described in scope: "gasless user") could attach a nonzero native KAIA value to the ApproveTx or SwapTx while still satisfying every other match condition (A1–A4, S1–S3). The module would still recognize and process the transaction as a valid gasless bundle member, sign a `LendTx` to the sender, and expect exactly `repayAmount` in return, with the sender's attached `msg.value` neither refunded, tracked, nor incorporated into the accounting.

### Impact Explanation
This falls into the same bug class as the report: a value-classification function omits `msg.value` from its logic, so tokens sent along with a call are not properly registered for the sender who may lose them, while the accounting used elsewhere (the router's `swapForGas` implementation, or an attacker-controlled ERC20/router combination) could still process and potentially consume that stray value or cause a state divergence between the fee-lending accounting and the actual token/KLAY movement. Since the value is not part of the decoded `ApproveArgs`/`SwapArgs`, the pool's execution decision (`IsExecutable`/`VerifyExecutable`) and the proposer's lend/repay bookkeeping are computed independently of it, meaning the accounting can be manipulated or become inconsistent with actual value transferred, a state-divergence/fee-delegation-abuse condition under the given rules.

### Likelihood Explanation
Reachable directly by any unprivileged "gasless user" constructing an ApproveTx or SwapTx with a nonzero `Value` field — no special privileges are required, only that the transaction is a legacy type addressed to the whitelisted token/router with the expected selector. The classification and repay-amount logic never rejects or examines this field, so the condition is trivially reachable from a single submitted transaction.

### Recommendation
In `decodeFunctionCall` (or in `decodeApproveTx`/`decodeSwapTx`), require `tx.Value().Sign() == 0` as an explicit condition before recognizing the transaction as a valid ApproveTx/SwapTx, mirroring the recommended fix in the referenced report (reject the transaction/deposit when the "wrong" value channel is nonzero rather than silently ignoring it).

### Proof of Concept
1. A gasless user builds a legacy transaction `to = router`, `data = swapForGas(token, amountIn, minAmountOut, amountRepay, deadline)` selector-matching, but sets `tx.Value() = X > 0` (nonzero KAIA attached).
2. `decodeFunctionCall` (kaiax/gasless/impl/getter.go:182-193) only checks `tx.Type()`, `tx.To()`, calldata length, and selector — it accepts the tx regardless of `tx.Value()`.
3. `IsSwapTx`/`isSwapTx` (getter.go:92-103) and `IsModuleTx` (tx_pool.go:55-60) classify it as a valid gasless swap tx purely from the decoded calldata fields, ignoring the attached value.
4. `checkBalanceForSwap` and `VerifyExecutable`/`repayAmount` (getter.go:107-182, 361-367) compute required balances and repay amounts strictly from `tx.Fee()` and calldata fields, never referencing or refunding `tx.Value()`.
5. The transaction proceeds through the gasless bundling flow with the attached native value unaccounted for in the module's bookkeeping, exhibiting the same "value silently unregistered while other logic proceeds" pattern as the reported `receiveFunds` issue.

func (g *GaslessModule) IsApproveTx(tx *types.Transaction) bool {
	args, ok := decodeApproveTx(tx, g.signer)
	return ok && g.isApproveTx(args)
}

func (g *GaslessModule) isApproveTx(args *ApproveArgs) bool {
	g.gaslessInfoMu.RLock()
	defer g.gaslessInfoMu.RUnlock()

	return g.allowedTokens[args.Token] && // A1
		g.swapRouter == args.Spender && // A3
		args.Amount.Cmp(abi.MaxUint256) == 0 // A4
}

func decodeFunctionCall(tx *types.Transaction, method abi.Method) (common.Address, map[string]interface{}, bool) {
	if tx.Type() != types.TxTypeLegacyTransaction || // not legacy tx: unable to statically determine the max gas fee.
		tx.To() == nil || // not a contract call.
		len(tx.Data()) < 4 || // too short to be a contract call.
		!bytes.Equal(tx.Data()[:4], method.ID) { // not the target function.
		return common.Address{}, nil, false
	}

	inputs := make(map[string]interface{})
	err := method.Inputs.UnpackIntoMap(inputs, tx.Data()[4:])
	return *tx.To(), inputs, err == nil
}

func lendAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	r := new(big.Int)

	// R2 = ApproveTx.Fee() if exists
	if approveTxOrNil != nil {
		r.Add(r, approveTxOrNil.Fee())
	}

	// R3 = SwapTx.Fee()
	r.Add(r, swapTx.Fee())

	// LendAmount = R2 + R3
	return r
}

func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
