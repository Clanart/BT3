### Title
Symlink-following file read discloses arbitrary host file contents in diff view - (File: `app/src/ui/diff/syntax-highlighting/index.ts`)

### Summary
`getNewFileContent` builds the on-disk path for a `WorkingDirectoryFileChange` by joining `repository.path` with the git-relative `file.path` and passes it directly to `readPartialFile`, which uses `fs.createReadStream` — a symlink-following API.

### Finding Description
In `getNewFileContent`, for working-directory files the code calls:
```
readPartialFile(Path.join(repository.path, file.path), 0, MaxHighlightContentLength - 1)
``` [1](#0-0) 

`readPartialFile` opens the path with `createReadStream(path, { start, end })`, which resolves symlinks via the OS (Node's `fs` open calls follow symlinks by default; there is no `lstat`/`O_NOFOLLOW` guard anywhere in this path): [2](#0-1) 

Unlike `getWorkingDirectoryDiff`, which invokes `git diff` and lets git handle symlinks specially (git reports a symlink entry's target string rather than dereferencing it on disk), this code bypasses git entirely and touches the filesystem directly, inheriting the OS symlink-follow semantics. [3](#0-2) 

Critically, the resulting `newContents` is not merely used for tokenization — it is fed into `expandWholeTextDiff`/`expandTextDiffHunk`, which splice these raw lines directly into the rendered diff hunks as literal `DiffLine` text: [4](#0-3) 
and these expansion functions are invoked from the diff UI using `contents.newContents` sourced straight from `getFileContents`/`getNewFileContent`: [5](#0-4) [6](#0-5) 

So if an attacker-controlled clone/checkout contains a symlink at `file.path` pointing to an arbitrary absolute path outside `repository.path` (e.g. `~/.ssh/id_rsa`, `~/.aws/credentials`, a browser cookie DB, etc.), and the user selects that changed/new file in the Changes view and expands the diff (or the highlighter otherwise reads it for tokenization), Desktop reads the target file content from the host filesystem and displays it verbatim in the diff pane.

### Impact Explanation
This breaks the implicit invariant that file reads for diff rendering stay within `repository.path`, allowing an attacker-controlled repository to cause the app to read and display arbitrary files readable by the user's OS account. This matches the "read outside the repo" / file-disclosure criteria in scope: the attacker only controls repository content (a symlink checked into or created within the clone), no local access or malware is required, and the disclosure happens through normal user interaction with the Changes/diff view.

### Likelihood Explanation
Git checkouts can create symlinks from tracked/untracked entries (subject to `core.symlinks`), and untracked files can be symlinks created by any script or tool that runs against a freshly cloned repo. A malicious repository author can commit a symlink (`ln -s /home/user/.ssh/id_rsa payload`) or ship it as part of a build/setup script executed post-clone; the moment the file shows up as a changed/new/untracked file and the user opens the diff (especially expands it, since "Expand Whole File" is readily available in the diff context menu), the target's content is displayed. This requires only ordinary user interaction with the app on a malicious clone, matching the in-scope "attacker controls a cloned/fetched repository" threat model.

### Recommendation
Before reading `file.path` for syntax highlighting/expansion in `getNewFileContent`, verify the resolved real path stays within `repository.path`:
- Use `fs.lstat`/`fs.realpath` on the joined path and reject (return `null`) if `fs.lstatSync(path).isSymbolicLink()` is true, or if `fs.realpathSync(path)` does not start with `repository.path` (after resolving `repository.path` itself with `realpath`, and confirming a proper path-boundary check, not just a string prefix).
- Alternatively, route working-directory content reads through `git show :<path>`/`git cat-file` semantics like committed files, so symlink handling matches git's own (non-dereferencing) treatment.
- Apply the same containment check in any other direct `fs`-based readers of `file.path` joined with `repository.path` (e.g. `formatPatch`/other working-directory file access sites) to avoid parallel bypasses.

### Proof of Concept
1. Create a sensitive file outside the repo, e.g. `/tmp/secret.txt` with confidential content.
2. Initialize/clone a test repository at `/tmp/repo`.
3. Inside `/tmp/repo`, create a symlink: `ln -s /tmp/secret.txt payload.txt`.
4. Open the repo in GitHub Desktop; `payload.txt` appears as an untracked/new file in Changes.
5. Select `payload.txt` in the Changes list — `getFileContents` → `getNewFileContent` → `readPartialFile(Path.join(repository.path, 'payload.txt'), ...)` follows the symlink via `createReadStream` and reads `/tmp/secret.txt`.
6. The contents of `/tmp/secret.txt` are shown in the diff/syntax-highlighted view (most reliably confirmed via "Expand Whole File", which splices `newContents` directly into visible diff lines), confirming out-of-repository file disclosure.

export async function readPartialFile(
  path: string,
  start: number,
  end: number
): Promise<Buffer> {
  return await new Promise<Buffer>((resolve, reject) => {
    const chunks = new Array<Buffer>()
    let total = 0

    createReadStream(path, { start, end })
      .on('data', (chunk: Buffer) => {
        chunks.push(chunk)
        total += chunk.length
      })
      .on('error', reject)
      .on('end', () => resolve(Buffer.concat(chunks, total)))
  })
```

export async function getWorkingDirectoryDiff(
  repository: Repository,
  file: WorkingDirectoryFileChange,
  hideWhitespaceInDiff: boolean = false
): Promise<IDiff> {
  // `--no-ext-diff` should be provided wherever we invoke `git diff` so that any
  // diff.external program configured by the user is ignored
  const args = [
    'diff',
    ...(hideWhitespaceInDiff ? ['-w'] : []),
    '--no-ext-diff',
    '--patch-with-raw',
    '-z',
    '--no-color',
  ]
  const successExitCodes = new Set([0])
  const isSubmodule = file.status.submoduleStatus !== undefined

  // For added submodules, we'll use the "default" parameters, which are able
  // to output the submodule commit.
  if (
    !isSubmodule &&
    (file.status.kind === AppFileStatusKind.New ||
      file.status.kind === AppFileStatusKind.Untracked)
  ) {
    // `git diff --no-index` seems to emulate the exit codes from `diff` irrespective of
    // whether you set --exit-code
    //
    // this is the behavior:
    // - 0 if no changes found
    // - 1 if changes found
    // -   and error otherwise
    //
    // citation in source:
    // https://github.com/git/git/blob/1f66975deb8402131fbf7c14330d0c7cdebaeaa2/diff-no-index.c#L300
    successExitCodes.add(1)
    args.push('--no-index', '--', '/dev/null', file.path)
  } else if (file.status.kind === AppFileStatusKind.Renamed) {
    // NB: Technically this is incorrect, the best kind of incorrect.
    // In order to show exactly what will end up in the commit we should
    // perform a diff between the new file and the old file as it appears
    // in HEAD. By diffing against the index we won't show any changes
    // already staged to the renamed file which differs from our other diffs.
    // The closest I got to that was running hash-object and then using
    // git diff <blob> <blob> but that seems a bit excessive.
    args.push('--', ensureRelativePath(file.path))
  } else {
    args.push('HEAD', '--', ensureRelativePath(file.path))
  }

  const { stdout, stderr } = await git(
    args,
    repository.path,
    'getWorkingDirectoryDiff',
    { successExitCodes, encoding: 'buffer' }
  )
  const lineEndingsChange = parseLineEndingsWarning(stderr)

  return buildDiff(stdout, repository, file, 'HEAD', 'HEAD', lineEndingsChange)
}
