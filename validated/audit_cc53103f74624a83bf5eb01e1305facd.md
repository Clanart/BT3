## Title
Incorrect bracket-stripping in `ActionsLogParser.parse` corrupts extracted URL text via `String.replace` first-match semantics - (File: `app/src/lib/actions-log-parser/action-log-parser.ts`)

### Summary
`ActionsLogParser.parse` splits Actions log text on `UrlRegex` and then attempts to strip enclosing bracket characters (`{`, `(`, `<`, `[` / `}`, `)`, `>`, `]`) from a matched URL entry before exposing it as `entryUrl` for rendering as a link.

### Finding Description
`UrlRegex` is defined as: [1](#0-0) 
The URL body character class `[^\s<>|'"]{2,}` does **not** exclude `)`, `]`, or `}`, so these characters can be swallowed into the matched URL token itself (e.g. a log line like `(https://evil.com/path))` produces the single regex match `(https://evil.com/path))`).

In `parse()`, bracket stripping is done like this: [2](#0-1) 

The bug: `entrySuffix` is *located* using a regex anchored to the end of the string (`(?=$)`), but it is then *removed* using `String.prototype.replace(entrySuffix, '')`, which removes the **first** occurrence of that literal substring in `entry`, not the occurrence at the end that was actually matched. When the URL body legitimately (or maliciously) contains an earlier occurrence of the same bracket character(s) that also appear as the trailing closer, `.replace()` strips the wrong character from the middle/front of the URL rather than the trailing one, and leaves the genuine trailing bracket character(s) still attached to `entryUrl`.

For example, with input `(https://evil.com/a)b)` — `entryPrefix` = `"("` (length 1), `entrySuffix` computed by the anchored regex = `")"` (the last character). `entry.replace("(", '')` removes the leading `(` correctly, but `.replace(")", '')` removes the **first** `)` in `"https://evil.com/a)b)"`, i.e. the one after `/a`, producing `entryUrl = "https://evil.com/ab)"` — a URL that literally never appeared in the raw log, with a stray trailing `)` incorrectly retained as part of the link target and a legitimate path character silently deleted.

This demonstrates the invariant violation asked about in the question: "only genuine enclosing brackets are stripped from a URL" is broken, since the code does not verify the substring index of the match, only whether that character exists somewhere earlier in the string.

### Impact Explanation
The corrupted `entryUrl` is used to build the clickable link for the rendered log line (`IParsedOutput.entryUrl` populates the anchor href in the Actions log view). An attacker who controls CI log output (e.g. via a workflow that echoes attacker-influenced text, or a malicious dependency/action that writes to stdout) can craft a bracketed URL string so that the character stripped by mistake shifts the resulting href to a different, attacker-chosen destination than what a naive reading of the surrounding bracket-delimited text would suggest, or leaves extraneous trailing punctuation attached to a domain suffix in a way that changes the effective path/host boundary perceived versus rendered. However, this only affects **path/query content after the host**, since the regex requires `https?://[a-z0-9][a-z0-9-]*[a-z0-9]\.` immediately after the optional bracket prefix — the host portion of the URL is not manipulable by this bracket bug. The practical effect is a rendering inconsistency in the CI log viewer (wrong path/query segment in the clickable link, or a stray bracket character appended to/left in the href) rather than a host-spoofing primitive that could disguise an entirely different origin as trustworthy.

### Likelihood Explanation
Reaching this code path only requires attacker-influenced text to appear in Actions log/log line content and be rendered through `ActionsLogParser.parse`, which is plausible for any repository whose CI output includes untrusted strings (build tool output, dependency banners, etc.). Constructing an input that triggers this specific `.replace()` first-match mismatch is straightforward once the character classes above are understood.

### Recommendation
Replace the string-based `.replace(entryPrefix, '')` / `.replace(entrySuffix, '')` calls with explicit `substring()` slicing based on the actual matched indices (i.e., `entry.slice(entryPrefix.length, entry.length - entrySuffix.length)`), so stripping is positional rather than based on first-occurrence string matching. Additionally, consider excluding `)`, `]`, `}` from the trailing/general URL body character class in `UrlRegex`, or validate bracket-type pairing (e.g., `(` must pair with `)`, not with `]`), to avoid unbalanced/mismatched bracket types being accepted as valid "enclosing" markers at all.

### Proof of Concept
Add a unit test asserting the extracted `entryUrl` differs from what a correct positional strip would produce:
```ts
// app/src/lib/actions-log-parser/action-log-parser.ts (behavior under test)
const parser = new ActionsLogParser('(https://evil.com/a)b)', 'prefix')
const lines = parser.getParsedLogLinesTemplateData()
const output = lines[0].lineContent[0].output[0]
// Expected (correct) entryUrl if stripping is positional: "https://evil.com/a)b"
// Actual entryUrl produced by current code (first-occurrence replace): "https://evil.com/ab)"
assert.notEqual(output.entryUrl, 'https://evil.com/a)b')
```
This confirms `entryUrl` is computed incorrectly relative to the raw log text, though the exploitable severity is limited to path/query corruption rather than host spoofing due to the regex's strict host-matching prefix. [3](#0-2) [1](#0-0)
