### Title
Stale line-selection indices are silently reapplied to a freshly re-diffed file, allowing a partial commit to include unreviewed content - ([File: app/src/lib/git/apply.ts])

### Summary
`applyPatchToIndex` builds the patch that is staged and ultimately committed by re-fetching the diff at commit time and mechanically re-applying the `DiffSelection` that was captured earlier from the UI, without re-validating that the selection's line indices still correspond to the same lines in the freshly fetched diff. This mirrors the LineaRollup bug pattern: one artifact (the `y` value / `_submissionData.compressedData`) is produced independently of, and never checked against, the data it is supposed to represent (`snarkHash`), so a mismatch is silently accepted instead of causing a hard failure. Here, the "compressed data" analog is `_submissionData` and the "data used elsewhere" analog is the fresh diff computed by `getWorkingDirectoryDiff`; the missing check is a validation that the previously-captured `DiffSelection` (line indices) is still consistent with the newly loaded diff before it is used to build the patch that lands in the commit.

### Finding Description
`applyPatchToIndex` in [1](#0-0)  fetches a brand-new diff for the file (`getWorkingDirectoryDiff`) immediately before formatting the patch, but then calls `formatPatch(file, diff)` where `file.selection` is the `DiffSelection` object that was computed earlier against a *previous* version of the diff (i.e., whatever the user last interacted with in the UI). `formatPatch` blindly walks the new diff's hunks and asks `file.selection.isSelected(absoluteIndex)` for each line using positional indices from the new diff, as shown in [2](#0-1) . `DiffSelection.isSelected` only tracks a `Set<number>` of line indices that have diverged from a default (all-selected/none-selected) state — it has no concept of line *content*, only position, per [3](#0-2) .

The only place that reconciles a selection with a newer diff is `updateChangesWorkingDirectoryDiff` in the app store, which recomputes `selectableLines` and drops selections for lines that no longer exist, per [4](#0-3) . That reconciliation only clears lines that fall outside the new set of selectable positions; it does not, and cannot, detect the case where the working directory changed such that the *same line index* now maps to *different content* (e.g., another process/tool inserted or reordered lines elsewhere in the file, shifting what a given index number represents, or a hunk of identical size was replaced by different content). Nothing compares old-diff-line-text vs. new-diff-line-text at the same index before staging.

This is the structural analog of the LineaRollup issue: `submitData` computed `y` (via `_calculateY`) from `_submissionData.compressedData` but never checked it against the corresponding value the prover actually used for `snarkHash`, per [5](#0-4)  — likewise here, the line-index selection produced from one diff snapshot is combined with a structurally different diff snapshot with no equivalence check that the two are talking about the same underlying content.

### Impact Explanation
This falls in the "silent corruption of what the user commits or pushes" impact category. If the working directory file is modified between when the user made their line-level partial-stage selection and when Desktop calls `applyPatchToIndex` to build the commit (e.g., a build tool, linter/formatter, editor auto-save, or a malicious background process controlled by an attacker with only unprivileged local write access to the working tree — or more relevantly, content programmatically regenerated by a git hook/tool triggered by the app itself), the resulting committed patch can include or exclude lines the user never reviewed, without any error or warning. The user believes they are committing exactly what they saw and selected in the diff viewer, but `git apply --cached` will succeed on the new hunk structure and stage different content than what was displayed, silently corrupting the commit contents.

### Likelihood Explanation
The precondition (working directory mutates between diff-render/selection and commit execution) is realistic in normal Desktop usage — this is an interactive app where noticeable time passes between viewing a diff, selecting lines, writing a commit message, and clicking "Commit". Any concurrent process touching the file (editors with format-on-save, file watchers, background code generators) can trigger it without any "unnatural" user steps, local/admin access, or leaked credentials — it only requires the ordinary condition of the working tree changing during an interactive, multi-step commit flow.

### Recommendation
Before using a cached `DiffSelection` to build the patch in `applyPatchToIndex`, re-validate it against the diff actually used to produce the patch: compare a content fingerprint (e.g., hash of the file's on-disk content, or the diff's hunk text) captured when the selection was created against the content used in `getWorkingDirectoryDiff` immediately prior to `formatPatch`. If they differ, abort `applyPatchToIndex` and force the UI to refresh the diff/selection rather than silently proceeding with `git apply --cached`.

### Proof of Concept
Conceptual reproduction (cannot be executed in ask-only mode, but derivable from the cited code):
1. Modify a tracked file with a multi-line change; open it in Desktop's Changes view. Desktop calls `updateChangesWorkingDirectoryDiff` and computes a diff, e.g. hunk with 10 lines starting at `unifiedDiffStart = 5`.
2. User partially selects lines 5–7 for staging (`DiffSelection.withRangeSelection(5, 3, true)`), leaving the commit message box open (not yet clicking "Commit").
3. Before the user commits, an external process (editor autosave, formatter, or another tool with only ordinary write access to the working copy) rewrites the same region of the file so that lines at indices 5–7 now correspond to entirely different content (same hunk size/position, different text).
4. User clicks "Commit". `stageFiles` → `applyPatchToIndex` ( [6](#0-5) ) re-fetches the diff (now reflecting the new content) but reuses `file.selection`, still holding indices 5–7 from the stale selection.
5. `formatPatch` ( [7](#0-6) ) includes the new content at indices 5–7 in the patch because `isSelected(5..7)` returns true — content the user never saw or approved is staged and committed, with no error surfaced.
