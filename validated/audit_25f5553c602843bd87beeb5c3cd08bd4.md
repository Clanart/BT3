### Title
Partial-commit patch selection can silently apply to a re-fetched (stale-relative) diff, corrupting what is actually committed - (File: `app/src/lib/git/apply.ts`)

### Summary
The Alchemix report's root cause is a broken invariant: a value (`epochRevenues`) is computed by re-reading a live, mutable quantity (`thisBalance`) at "checkpoint" time and blindly accumulating it, instead of tracking the actual delta tied to the state that was originally observed. Whenever the live quantity moves between the time state is captured and the time it's consumed, the stored value silently diverges from reality.

The same class of bug exists in GitHub Desktop's partial-commit ("stage part of a file") pipeline. The user's line/hunk selection (`DiffSelection`) is captured against one rendering of a file's diff, but `applyPatchToIndex` re-reads the diff from disk at commit time and reapplies the old selection indices to whatever the new diff happens to contain, without any check that the diff is still the one the selection was made against.

### Finding Description
When a user partially stages a file, Desktop stores a `DiffSelection` bit-per-line object keyed by an *index into the diff currently shown*, on the `WorkingDirectoryFileChange` model. When the user commits, `_commitIncludedChanges` in `app/src/lib/stores/app-store.ts` passes the selected `WorkingDirectoryFileChange` objects (carrying their `.selection`) straight to `createCommit`, which calls `applyPatchToIndex`: [1](#0-0) 

Crucially, `applyPatchToIndex` does **not** reuse the diff that was rendered when the user made the selection. It fetches a **brand-new** diff from disk/working tree at commit time: [2](#0-1) 

That freshly-fetched diff is then handed to `formatPatch`, which walks `diff.hunks` and, for every non-context line, asks `file.selection.isSelected(absoluteIndex)` — where `absoluteIndex` is computed purely from the **new** diff's `hunk.unifiedDiffStart`/`lineIndex`: [3](#0-2) 

There is no verification anywhere in this path that the diff being formatted is the same diff (same hash/content) the selection indices were derived from. `DiffSelection` is a pure bitset over integer indices — it has no notion of "this index refers to line X of content Y." If the file's on-disk content changes between the moment the user reviews/selects lines in the Changes view and the moment `_commitIncludedChanges` actually runs `applyPatchToIndex`, the new diff will have a different hunk structure/line count, and the old bitset indices get silently reinterpreted against different lines. `formatPatch` will happily build a patch from whatever lines line up with the stale indices — it only throws if the resulting patch is completely empty: [4](#0-3) 

Nothing else guards this: `_commitIncludedChanges` does not re-diff and re-validate selection right before calling `createCommit`, and `getWorkingDirectoryDiff` is a plain `git diff` invocation with no idempotency/consistency check against the previously displayed diff: [5](#0-4) [6](#0-5) 

This mirrors the Alchemix bug precisely: a stateful value (`epochRevenues`/`DiffSelection`) is combined with a freshly re-sampled live quantity (`thisBalance`/on-disk diff) instead of the originally-observed one, and no code path detects the divergence — the operation just proceeds and produces an incorrect but silently-accepted result.

### Impact Explanation
This falls under "silent corruption of what the user commits or pushes." A file in a cloned/fetched repository whose content is mutated by something other than the user between selection and commit — e.g., a `post-checkout`/`pre-commit` hook, a build tool, linter/formatter-on-save, or any file watcher triggered merely by having the repository open in Desktop — can cause Desktop to build a patch from mismatched line indices. The result: the commit includes different content than what the user visually reviewed and selected in the diff viewer, with no warning, error, or diff re-confirmation. Because git commits are typically pushed and trusted by collaborators/CI, this can propagate unintended or attacker-influenced content into the repository history under the victim's authorship, entirely silently.

### Likelihood Explanation
Requires only a benign trigger unrelated to attacker's device access: any file mutation racing with a commit action (auto-formatters, git hooks the repo defines, background build scripts, or a malicious `post-checkout`/`post-merge` hook shipped in a cloned repository that rewrites tracked files shortly after checkout). Desktop performs the diff refetch and patch application asynchronously (`await getWorkingDirectoryDiff` in `applyPatchToIndex`, `await gitStore.performFailableOperation` in `_commitIncludedChanges`), widening the window for such a race. No elevated privileges or local malware are needed — the "malicious" component can arrive purely via the repository's own configured hooks/tooling, which is within the described threat model (attacker controls a cloned/fetched repository).

### Recommendation
Bind `DiffSelection` to the identity/content of the diff it was computed against (e.g., store the diff's text hash or hunk fingerprint alongside the selection). Before calling `formatPatch`/`applyPatchToIndex`, re-fetch the diff and compare it against the one the selection was derived from; if they differ, abort the partial commit and force the UI to re-render the new diff for the user to re-select, rather than silently reapplying stale indices to new content.

### Proof of Concept
Conceptual reproduction (cannot be executed in this read-only environment, but derivable from the cited code paths):
1. Open a repo in Desktop, modify `file.txt` to add lines A and B, and in the Changes diff view, select only line A for the commit (unselect line B). This sets `file.selection` bitset relative to the diff hunk indices at that moment.
2. Before pressing "Commit," have a `post-checkout`/build script (or a manual edit racing the click) change `file.txt` so the diff now has a different hunk layout — e.g., insert a new line before A, or reorder A and B.
3. Click "Commit." `_commitIncludedChanges` → `createCommit` → `applyPatchToIndex` re-fetches the diff via `getWorkingDirectoryDiff` (new hunk indices) and calls `formatPatch(file, newDiff)`, which reuses the old `file.selection.isSelected(absoluteIndex)` bitset unchanged.
4. Because indices no longer point at the lines the user intended, `formatPatch` builds and applies (`git apply --cached`) a patch that stages a different set of lines than what the user selected — with no error, since `formatPatch` only fails on a fully empty patch.
