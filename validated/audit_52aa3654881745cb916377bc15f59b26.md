### Title
Unbounded attacker-controlled length in `SchnorrAggregate::read` enables memory/computation denial of service - (File: crypto/schnorr/src/aggregate.rs)

### Summary
The CVE-2018-1000168 class — improper validation of a length/count field in a network-supplied frame, causing resource exhaustion and denial of service — maps onto `SchnorrAggregate::<C>::read` in `crypto/schnorr`. The deserializer reads a little-endian `u32` element count directly from the untrusted byte stream and then loops that many times, pushing a fully parsed group element into a `Vec` on every iteration, with no upper bound, no remaining-length check, and no sanity limit on the claimed count.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::read` performs: [1](#0-0) 

```rust
let mut len = [0; 4];
reader.read_exact(&mut len)?;
let mut Rs = vec![];
for _ in 0 .. u32::from_le_bytes(len) {
  Rs.push(C::read_G(reader)?);
}
```

The `len` field is entirely attacker-controlled and may claim up to 4,294,967,295 nonces. Two denial-of-service surfaces result:

1. **CPU exhaustion without bandwidth cost.** A reader over a non-failing or replaying source (e.g., a buffered stream whose peer feeds bytes slowly, or any `Read` implementation over a large concatenated buffer) forces up to ~4.3 billion `C::read_G` calls. Each `read_G` performs full point decompression and validation. Even at EOF the error path is only hit after the first failed read, but any attacker who supplies *some* valid points followed by a huge claimed count still pays nothing for the declared length itself — the loop count is trusted before any data is.
2. **Memory exhaustion.** If the attacker actually supplies a large blob of valid point encodings, `Rs` grows proportionally with no cap; a serialized aggregate claiming hundreds of millions of `R` values allocates gigabytes before `verify` is ever reached. `verify` only compares `Rs.len()` against `keys_and_challenges.len()` *after* the entire allocation and parsing has occurred (`aggregate.rs:128`), so the oversized allocation is never prevented.

The write side explicitly acknowledges aggregates can approach this scale (`expect("more than 4 billion signatures in aggregate")` at `aggregate.rs:96`), confirming no internal bound exists. For contrast, `Commitments::read` in `crypto/dkg/pedpop/src/lib.rs:110-128` bounds its loop by the locally-configured `params.t()`, and `ThresholdKeys::read` in `crypto/dkg/src/lib.rs:604-623` bounds reads by a `u16` `n` — `SchnorrAggregate::read` is the outlier that trusts a 32-bit wire field.

### Impact Explanation
Analogous to the nghttp2 ALTSVC frame handling crash: an unprivileged party who can cause a node/verifier to deserialize an aggregate signature from untrusted bytes (any context where a serialized `SchnorrAggregate` is received over the wire) can force the host to attempt up to ~4.3 billion point deserializations and unbounded `Vec` growth, exhausting CPU and memory and denying service. This is a reachable crash/DoS from public input bytes alone, requiring no keys, no collusion, and no protocol violation beyond a malformed length prefix.

### Likelihood Explanation
Exploitation requires only that the application deserializes a `SchnorrAggregate` from bytes influenced by an untrusted party — the documented purpose of the `read`/`serialize` pair (`aggregate.rs:77`, `aggregate.rs:107`). The malicious input is trivially constructed (four bytes `0xFFFFFFFF` followed by optional padding). Severity is Medium: high availability impact on the deserializing process, but no confidentiality/integrity loss, mirroring the original CVE's availability-only CVSS profile.

### Recommendation
Bound the loop before parsing: either cap `len` at the maximum plausible aggregation size (e.g., the threshold `n`), or pre-check that the remaining stream contains at least `len * size_of::<C::G::Repr>() + size_of::<C::F::Repr>()` bytes before attempting any `read_G` calls. Reject declared counts exceeding the protocol's maximum signer set.

### Proof of Concept

```rust
use ciphersuite::Ciphersuite;
use schnorr::SchnorrAggregate;

// Attacker-controlled bytes: a u32 count of ~4.29 billion nonces.
let mut malicious = 0xFFFF_FFFFu32.to_le_bytes().to_vec();
// Optionally append many valid 33-byte encodings to drive memory growth;
// the loop count itself is already trusted before data is checked.
let mut cursor = Cursor::new(malicious);

// Attempts up to ~4.3 billion Secp256k1::read_G calls / Vec pushes —
// CPU- and memory-exhausting the host.
let _ = SchnorrAggregate::<Secp256k1>::read(&mut cursor);
```
Root cause is at `crypto/schnorr/src/aggregate.rs:78-85`: the wire-supplied count is used as the loop bound with no validation, the same improper-input-validation shape as CVE-2018-1000168.
