### Title
Operator falsely credited with a payout it never funded via unvalidated OP_RETURN pubkey in payout tx - ([File: core/src/verifier.rs])

### Summary
`is_kickoff_malicious` (and the upstream `update_finalized_payouts`) treats the OP_RETURN operator xonly pubkey inside a payout tx as authoritative proof that the named operator fronted the withdrawal, with no check that the named operator actually signed or funded the transaction's non-withdrawal inputs. Because the payout tx uses `SinglePlusAnyoneCanPay` (only input 0 and output 0 are committed by the withdrawer's signature), the withdrawer themself can self-fund the transaction and stamp an arbitrary operator's xonly pubkey into the unsigned OP_RETURN output, causing the bridge's bookkeeping (and any operator's automated `PayoutCheckerTask`) to treat that operator as having fronted a payout it never touched.

### Finding Description
The claimed binding is: `operator_xonly_pk_opt` (from DB, populated by `update_finalized_payouts` at `core/src/verifier.rs:2319-2321` purely by parsing the payout tx's OP_RETURN) `==` "the operator that actually funded/signed the extra inputs of the payout tx." This binding does not hold, because nothing in the code path enforces it.

Trace:
1. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a `Payout` tx with input 0 = the withdrawal UTXO (spent via `SpendPath::KeySpend` using the withdrawer's `user_sig`), output 0 = user payout, output 2 = OP_RETURN containing `operator_xonly_pk.serialize()`. The witness is set only for input 0 (`set_p2tr_key_spend_witness`).
2. The withdrawer's signature is required to have `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:174-187`, `core/src/operator.rs:630-637`). This sighash type commits only to input 0 and output 0 — **not** to the OP_RETURN output, not to additional funding inputs, and not to who broadcasts the tx.
3. Anyone holding this signature (the withdrawer/attacker themself, since it is their own withdrawal) can therefore construct a completely different payout transaction: self-funding extra inputs (their own wallet, own fees) while writing an arbitrary xonly pubkey (e.g. a target operator's) into the OP_RETURN, and broadcast it themselves — bypassing any operator's `withdraw()` RPC entirely.
4. `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`) matches "the payout tx" purely by which transaction spends the tracked `withdrawal_utxo_txid/vout` — it does not care who broadcast it or what other inputs it has.
5. `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) then parses the OP_RETURN of that tx and stores whatever xonly pubkey is found (`operator_xonly_pk = parse_op_return_data(...)`) as `payout_payer_operator_xonly_pk`, with no verification that the named operator's wallet/signature funded any of the additional inputs.
6. `is_kickoff_malicious` (`core/src/verifier.rs:1859-1914`) later only checks `operator_xonly_pk != kickoff_data.operator_xonly_pk` (line 1887) to decide maliciousness — it never checks that the operator named in the OP_RETURN actually signed/funded the payout.
7. Separately, `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`) has each operator poll `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, if a match is found, automatically calls `handle_finalized_payout` and proceeds toward `Reimburse`, with no cross-check against the operator's own broadcast/funding history of that specific payout tx.

Because steps 3–7 rely solely on unauthenticated OP_RETURN content, an attacker who is the withdrawer of their own funds can front their own payout with their own money and falsely attribute it to any operator's xonly pubkey, making that operator's (or a future/legitimate) kickoff for that deposit pass `is_kickoff_malicious`'s check and become eligible for `Reimburse`, even though the named operator never fronted anything.

### Impact Explanation
This lets bridge value move out of the operator collateral/reimbursement machinery to an operator that did not fund the corresponding withdrawal — matching the Critical category "an operator reimbursed for a payout it never funded." The blast radius is broad: it is repeatable for every withdrawal the attacker (as withdrawer) initiates, and can target any registered operator xonly pubkey observed via `fetch_operator_keys`/`GetOperatorKeys`. Because `PayoutCheckerTask` automatically drives `handle_finalized_payout` → kickoff → `Reimburse` per operator based solely on the DB record, this can trigger automated reimbursement flows for payouts an operator never made, corrupting the SLASHING_TRUTH invariant that reimbursement eligibility should equal actual fronting.

### Likelihood Explanation
Preconditions: attacker must be the legitimate withdrawer of a bridge withdrawal (fully within their unprivileged capability set — they call Citrea's `withdraw`, choose the withdrawal UTXO and hold the `SinglePlusAnyoneCanPay` signature for their own payout). No verifier/operator/aggregator privilege, no key compromise, and no majority hashrate is needed. Cost is only their own BTC withdrawal amount plus fees for the transaction they self-fund (they get their own withdrawal executed as a side effect). The attack is deterministic given knowledge of the (unauthenticated) OP_RETURN scheme and is repeatable per withdrawal.

### Recommendation
Do not trust the OP_RETURN pubkey as proof of funding. Require that the payout tx's additional (non-withdrawal) inputs be spendable only by/attributable to the specific operator (e.g., cross-check that at least one additional input's scriptPubkey/signature corresponds to the claimed operator's registered wallet, or have the operator counter-sign the full payout tx including the OP_RETURN commitment under `SIGHASH_ALL`/`SIGHASH_DEFAULT` for their contribution) before `update_finalized_payouts`/`is_kickoff_malicious` accept the OP_RETURN-claimed operator as the payer.
