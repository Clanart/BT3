### Title
Attacker-Controlled OP_RETURN in a Replaced Payout Tx Lets Any Operator Be Falsely Credited (and Reimbursed) for a Withdrawal It Never Funded - (`core/src/verifier.rs::update_finalized_payouts`)

### Summary
`update_finalized_payouts` attributes a withdrawal's payout to whichever xonly-pubkey happens to be encoded in the first `OP_RETURN` output of the transaction that spends the withdrawal UTXO, with no check that this pubkey's owner actually signed or funded any input of that transaction. Because the withdrawal UTXO is spent with a user-controlled `SinglePlusAnyoneCanPay` signature that commits only to the matching-index output (not to other inputs/outputs), the withdrawing user (an unprivileged attacker) can replace an honest operator's payout tx via RBF with one that pays the same committed output but appends an arbitrary `OP_RETURN` naming any operator, causing that operator to be credited and later reimbursed for funds it never advanced.

### Finding Description
Binding claimed: `withdrawals.payout_payer_operator_xonly_pk` (the operator credited/reimbursed for withdrawal `idx`) == the xonly-pubkey of the party that actually funded the inputs of the transaction paying the withdrawing user. The code never establishes this equality.

In `update_finalized_payouts` (`core/src/verifier.rs:2283-2353`), for every `(idx, payout_txid)` returned by `get_payout_txs_for_withdrawal_utxos` (`core/src/database/verifier.rs:170-196`, which simply finds whatever tx spent the registered `withdrawal_utxo_txid:vout`), the code looks up the on-chain tx and does: [1](#0-0) 
i.e. it takes the first `OP_RETURN` output, parses out 32 bytes, and treats them as `operator_xonly_pk` — purely a byte-pattern match, with no signature check, no check that this pubkey's key signed any input, and no check on which input funded the paid output. This value is written straight into the DB via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`).

The honest `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) only cryptographically signs input 0 (the withdrawal UTXO) with the user's own key-spend signature using `TapSighashType::SinglePlusAnyoneCanPay`; this sighash flag is enforced in `parse_withdrawal_sig_params` (`core/src/rpc/parser/operator.rs:161-203`). `SinglePlusAnyoneCanPay` commits only to the output at the *same index* as the signed input and to no other inputs (`ANYONECANPAY`) — it does **not** commit to the operator's funding inputs, the anchor output, or the `OP_RETURN` output added later by whoever assembles the final transaction (in the honest flow, `Operator::withdraw`, `core/src/operator.rs:560-691`, adds funding inputs via `fund_raw_transaction`/`sign_raw_transaction_with_wallet` and its own `OP_RETURN`).

Because the same user (who is the withdrawal-UTXO owner and thus the attacker per the threat model) already possesses this valid, replayable `SinglePlusAnyoneCanPay` signature, they can construct a competing transaction that:
- spends the identical withdrawal UTXO with the same signature,
- pays the exact committed output (same amount/script, satisfying `SIGHASH_SINGLE`),
- supplies its own fee-paying input(s) instead of the honest operator's,
- appends an `OP_RETURN` naming an arbitrary operator `O2` who never signed or funded anything,
- and broadcasts it with a higher fee to RBF-replace the honest operator `O1`'s in-flight payout tx (both txs use `NON_STANDARD_V3`/replaceable sequencing).

Once this replacement confirms, `update_finalized_payouts` records `O2` as `payout_payer_operator_xonly_pk` for that withdrawal index. Downstream, `Operator::validate_payer_is_operator` (`core/src/operator.rs:1687-1740`) and `PayoutCheckerTask`/`handle_finalized_payout` (`core/src/task/payout_checker.rs:31-113`, `core/src/operator.rs:839-916`) trust this DB column verbatim — they only compare it against `self.signer.xonly_public_key`, never checking whether `O2` actually signed or funded the on-chain payout — so `O2`'s node will automatically build a kickoff and claim the bridge's reimbursement for a payout it never made.

No existing guard closes this gap: `SECP.verify_schnorr` is only used to validate the *user's* signature over the committed output, never to tie the `OP_RETURN` pubkey to any input; `Verifier::is_deposit_valid`, `is_kickoff_malicious`, and the bridge circuit's `parse_op_return_data` (`circuits-lib/src/bridge_circuit/mod.rs:206-236,608-617`) all likewise treat the `OP_RETURN` bytes as ground truth for "who paid," not as something requiring proof of funding.

### Impact Explanation
The named operator `O2` is credited in the `withdrawals` table and, via the automated `PayoutCheckerTask`, will kick off the reimbursement flow and eventually pull `bridge_amount` from the round/reimbursement connector for a withdrawal it never funded — a direct case of "an operator reimbursed for a payout it never funded" (Critical). This is repeatable per withdrawal and can target any operator's xonly-pubkey (which are public), so the blast radius spans every future withdrawal handled by any operator running with automation enabled.

### Likelihood Explanation
The attacker only needs to be an ordinary withdrawing user: they legitimately call Citrea `withdraw`, choose their own withdrawal UTXO and `SinglePlusAnyoneCanPay` signature (as required/normal), and then race the honest operator's broadcast payout tx with a higher-fee replacement carrying a forged `OP_RETURN`. This requires no verifier/operator privilege, no key compromise, and only ordinary BTC fees to win the RBF race — well within the described unprivileged attacker capabilities.

### Recommendation
Do not trust the `OP_RETURN` payload alone to determine the payer. Require the operator's identity to be cryptographically bound to the transaction that actually funds the payout — e.g., require the operator to place a signature (or a musig/aggregate signature over the full transaction, or a keyed input from a well-known operator-controlled UTXO/round output) whose validity requires the named operator's key to have authorized that specific transaction, and have `update_finalized_payouts` verify that signature/input ownership before writing `payout_payer_operator_xonly_pk`, instead of merely `parse_op_return_data` + `XOnlyPublicKey::from_slice`.
