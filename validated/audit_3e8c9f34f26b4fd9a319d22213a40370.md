### Title
Unguarded `total.Sub(locked)` in EVM balance/coinbase-sweep logic can underflow, mirroring the ECG `totalBorrowedCredit` bug - ([File: x/evm/keeper/balance.go], [File: x/evm/keeper/abci.go])

### Summary
Two places in the EVM module compute a derived "unlocked" quantity by subtracting a `LockedCoins`-derived value from a raw balance using plain `sdk.Int.Sub`, exactly the same "assume A ≥ B always" pattern that broke `totalBorrowedCredit` in the ECG report. `sdk.Int.Sub` does not panic or clamp on a negative result (unlike `sdk.Coin.SubAmount`/`Coins.Sub`), so if `LockedCoins` for the address ever exceeds its raw `usei` balance, the result silently becomes negative and is fed into consensus-critical code (`GetBalance` returned to the EVM interpreter, and `SendCoinsAndWei` at `EndBlock`).

### Finding Description
`x/evm/keeper/balance.go`:
```go
func (k *Keeper) GetBalance(ctx sdk.Context, addr sdk.AccAddress) *big.Int {
	denom := k.GetBaseDenom(ctx)
	allUsei := k.BankKeeper().GetBalance(ctx, addr, denom).Amount
	lockedUsei := k.BankKeeper().LockedCoins(ctx, addr).AmountOf(denom)
	usei := allUsei.Sub(lockedUsei)
	wei := k.BankKeeper().GetWeiBalance(ctx, addr)
	return usei.Mul(state.SdkUseiToSweiMultiplier).Add(wei).BigInt()
}

`LockedCoins` for a vesting account is computed independently of the account's *current* balance — it is `OriginalVesting - DelegatedVesting`, a value that only depends on the account's vesting schedule/fields, not on how much `usei` the address currently holds: [3](#0-2) [4](#0-3) 

Meanwhile, the wei-denominated sub-usei debit/credit path (`SubWei`/`AddWei`, invoked from the EVM StateDB's `SubBalance`/`AddBalance`) mutates the `usei` balance directly via `setBalance`, with no reference to `LockedCoins` or vesting locks: [5](#0-4) 

Because the raw `usei` balance can move independently of the vesting schedule fields that drive `LockedCoins`, `allUsei`/`useiBalance` is not guaranteed to stay ≥ `lockedUsei`/`lockedUseiBalance`. When it dips below, `sdk.Int.Sub` (unlike `Coin.SubAmount`, which explicitly panics on negative results — see `sei-cosmos/types/coin.go:129-136`) silently returns a negative `sdk.Int`, exactly analogous to how `redeemableCredit()` could exceed `targetTotalSupply()` in the ECG report.

### Impact Explanation
- In `GetBalance` (`x/evm/keeper/balance.go`), a negative `usei` value is multiplied and converted to a `*big.Int` that is handed to go-ethereum's EVM as an account's balance. Downstream conversions to `uint256.Int` for value/gas checks are not designed to handle negative `big.Int` inputs; this is the exact class of "assume subtraction result is non-negative" bug the ECG report flags, and here it directly touches EVM balance accounting rather than an off-chain estimator.
- In `EndBlock`'s coinbase sweep (`x/evm/keeper/abci.go`), a negative `balance` is passed into `SendCoinsAndWei`, which internally must construct an `sdk.Coin`/perform bank debits; `sdk.Coin` construction/validation paths panic on negative amounts elsewhere in the codebase (`sei-cosmos/types/coin.go:129-136`, `:395-399`). A panic inside `EndBlock` halts block production for every validator running this code path deterministically — a chain-halt scenario.

### Likelihood Explanation
This mirrors the ECG finding's root cause precisely (unguarded `Sub` of two independently-varying derived quantities), but I was not able to fully trace, within the available tool budget, a concrete transaction sequence that:
1. gets a `LockedCoins`-bearing (vesting) account associated with an EVM address or landed as the deterministic coinbase address (`state.GetCoinbaseAddress`), and
2. drives its raw `usei` balance below that locked amount purely via the wei-denominated debit path.
I could not confirm within the remaining budget whether `MsgCreateVestingAccount` can target the synthetic per-tx coinbase addresses, nor whether the downstream `SendCoinsAndWei`/`NewCoin` calls actually panic on a negative input versus silently no-op. These are the two missing links needed to fully prove exploitability end-to-end.

### Recommendation
Apply the same fix recommended in the ECG report: clamp the subtraction to zero (`if allUsei.LT(lockedUsei) { usei = sdk.ZeroInt() } else { usei = allUsei.Sub(lockedUsei) }`) in both `x/evm/keeper/balance.go`'s `GetBalance` and `x/evm/keeper/abci.go`'s coinbase-sweep, instead of relying on the invariant that raw balance always exceeds locked balance.

### Proof of Concept
Not fully constructed — this report is based on static code analysis identifying the same "unguarded derived subtraction" pattern as the source report. A concrete PoC would need to verify: (a) whether a vesting/locked account can be established at one of the deterministic `GetCoinbaseAddress` addresses or at an address later associated with an EVM account, and (b) whether the wei-debit path (`SubWei`) can reduce that address's `usei` balance below its `LockedCoins` value without triggering the standard `SendCoins` lock check. This would need to be validated with a running testnet/Devin session with full repo access.

	if amt.Equal(sdk.ZeroInt()) {
		return nil
	}
	defer func() {
		if err == nil {
			ctx.EventManager().EmitEvent(
				types.NewWeiSpentEvent(addr, amt),
			)
		}
	}()
	currentWeiBalance := k.GetWeiBalance(ctx, addr)
	if amt.LTE(currentWeiBalance) {
		// no need to change usei balance
		return k.setWeiBalance(ctx, addr, currentWeiBalance.Sub(amt))
	}
	currentUseiBalance := k.GetBalance(ctx, addr, sdk.MustGetBaseDenom()).Amount
	currentAggregatedBalance := currentUseiBalance.Mul(OneUseiInWei).Add(currentWeiBalance)
	postAggregatedbalance := currentAggregatedBalance.Sub(amt)
	if postAggregatedbalance.IsNegative() {
		return sdkerrors.Wrapf(sdkerrors.ErrInsufficientFunds, "%swei is smaller than %swei", currentAggregatedBalance, amt)
	}
	useiBalance, weiBalance := SplitUseiWeiAmount(postAggregatedbalance)
	if err := k.setBalance(ctx, addr, sdk.NewCoin(sdk.MustGetBaseDenom(), useiBalance), true); err != nil {
		return err
	}
	return k.setWeiBalance(ctx, addr, weiBalance)
}
