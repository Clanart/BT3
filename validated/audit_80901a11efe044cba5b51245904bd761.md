### Title
Direct ERC20 donation to MasterMagpie inflates `BaseRewardPool.totalStaked()`, permanently diluting `rewardPerTokenStored` for legitimate stakers - ([File: rewards/BaseRewardPool.sol])

### Summary
`totalStaked()` in `BaseRewardPool` / `BaseRewardPoolV2` / `mWOMSVBaseRewarder` / `vlMGPBaseRewarder` returns `IERC20(stakingToken).balanceOf(operator)` (MasterMagpie's raw token balance) rather than an internally-tracked sum of user deposits [1](#0-0) , while `balanceOf(_account)` is derived purely from MasterMagpie's internal `userInfo[stakingToken][account].amount` accounting [2](#0-1) [3](#0-2) . An unprivileged attacker can call `IERC20(stakingToken).transfer(operator, D)` directly (bypassing `deposit`/`depositFor`), inflating the denominator used in `_provisionReward`'s `rewardPerTokenStored += amount*10**decimals/totalStaked()` [4](#0-3)  without increasing any user's tracked `balanceOf`, permanently diluting the reward-per-token growth for that `queueNewRewards` call.

### Finding Description
`_provisionReward` (called from `queueNewRewards`, restricted to `onlyManager`, and from permissionless `donateRewards`) computes:
```
rewardInfo.rewardPerTokenStored += (_amountReward * 10**decimals) / totalStaked();
```
`totalStaked()` reads `IERC20(stakingToken).balanceOf(operator)` — the raw ERC20 balance held by the MasterMagpie contract — not a sum of `userInfo[...].amount` [5](#0-4) . `balanceOf(_account)`, used both for `earned()` and for `updateRewards`'s `userShare`, instead reads `IMasterMagpie(operator).stakingInfo(stakingToken, _account)`, i.e. `userInfo[stakingToken][_account].amount`, which is only mutated through `_deposit`/`_withdraw` in `MasterMagpie.sol` [6](#0-5) [7](#0-6) .

Because a plain `transfer(operator, D)` bypasses `_deposit` entirely, it increases the value returned by `totalStaked()` by `D` while leaving every user's tracked `balanceOf` (and the sum of all `user.amount`) unchanged. When a manager subsequently calls `queueNewRewards(R, token)`, the per-token increment becomes `R*10**decimals/(realTotalStaked + D)` instead of `R*10**decimals/realTotalStaked`, permanently under-crediting `rewardPerTokenStored` relative to the fair value for that reward event. Since `rewardPerTokenStored` only increases going forward and is never retroactively corrected, this dilution baked into `earned()` computations for all current and future holders of that reward tranche is permanent — an amount of `R * D/(realTotalStaked + D)` of the reward token becomes unclaimable by any account's tracked `balanceOf` and stays stranded in the contract, since no accounting hook ever assigns it to anyone.

No existing check prevents this: `queueNewRewards` and `_provisionReward` trust `totalStaked()` unconditionally, there is no reentrancy or balance-consistency check between MasterMagpie's internal accounting and the raw ERC20 balance, and `donateRewards` is even fully permissionless, meaning an attacker doesn't need any special timing beyond front-running/timing a `queueNewRewards`/`donateRewards` call.

### Impact Explanation
This is a **permanent freezing of unclaimed yield / dilution of legitimate stakers' rewards** — matching the Immunefi impact class "theft or permanent freezing of unclaimed yield." The attacker's own donated stakingToken becomes unrecoverable by them (MasterMagpie has no sweep function reachable by the attacker, and they cannot `withdraw()` tokens they never deposited through `_deposit`), so this is a pure griefing/self-funded attack, but it still causes a real, quantifiable, permanent reduction in `earned()` for every other staker in that pool for the reward tranche(s) queued while the donation is outstanding.

### Likelihood Explanation
Feasibility is high in mechanical terms — this only requires an unprivileged EOA holding the pool's `stakingToken` and a single `IERC20.transfer` call, with no special permissions needed. However, the attack is economically irrational for a profit-seeking attacker under this scope: the attacker permanently loses their own donated capital `D` and gains nothing measurable in return (their own `balanceOf` in the pool is unaffected by the donation, so they do not capture a larger share of subsequent rewards). The attack is purely a costly griefing vector rather than a profitable exploit, which reduces real-world likelihood, though it remains technically reproducible by any unprivileged actor at any time before a `queueNewRewards`/`donateRewards` call.

### Recommendation
Track `totalStaked()` via an internal counter incremented/decremented in `_deposit`/`_withdraw` (or by summing `userInfo[...].amount` at the MasterMagpie level) instead of reading `IERC20(stakingToken).balanceOf(operator)`. This removes the ability for direct token transfers to influence reward-per-token math independent of tracked stake.

### Proof of Concept
1. Deploy `MasterMagpie` + `BaseRewardPool` for a mock `stakingToken`/`rewardToken`.
2. Have User A `deposit(stakingToken, 100e18)` through MasterMagpie (tracked stake).
3. Record `rewardPerTokenStored` baseline = 0.
4. **Control run:** manager calls `queueNewRewards(10e18, rewardToken)`; record `rewardPerTokenStored_control` and User A's `earned()`.
5. **Reset state**, repeat steps 1-3, then before `queueNewRewards`, have attacker (unprivileged EOA) call `IERC20(stakingToken).transfer(address(masterMagpie), 900e18)` directly (no `deposit` call).
6. Manager calls `queueNewRewards(10e18, rewardToken)`; record `rewardPerTokenStored_attack` and User A's `earned()`.
7. Assert `rewardPerTokenStored_attack < rewardPerTokenStored_control` (specifically ≈ `rewardPerTokenStored_control * 100/1000`), and that User A's `earned()` in the attack run is permanently lower than in the control run for the same deposit and reward amount, with the difference (~90% of the queued reward) unclaimable by any account, remaining stranded as `rewardToken` balance in the `BaseRewardPool` contract.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
