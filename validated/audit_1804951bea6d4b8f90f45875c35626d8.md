Based on my analysis, this is a real design pattern issue but likely does not rise to a Critical scoped finding for the slashing precompile specifically, and I need to be clear about the uncertainty.

## Analysis

`GetSigningInfos` at [1](#0-0)  is a pure query handler that never touches `contract.Value()` and never invokes any bank/coin transfer logic — it only calls `p.slashingKeeper.SigningInfos(ctx, req)` and packs the response.

The slashing `Execute` dispatcher at [2](#0-1)  does **not** check `contract.Value()` before dispatching to query handlers, unlike the ERC20 precompile, which explicitly guards against this: [3](#0-2) 

The ERC20 code comment makes clear this check exists specifically because "ERC20 precompiles cannot receive funds ... and will not be possible to recover funds sent to an instance of them" — confirming the underlying EVM `CALL` mechanism transfers `msg.value` into the target address's `StateDB` balance **before** the precompile's `Run`/`Execute` is even invoked, regardless of whether the target is a precompile and regardless of the ABI's `stateMutability`. Solidity's own non-payable compile-time revert only exists in generated caller bytecode — it doesn't apply if the call is crafted directly (raw calldata + value) against a precompile.

However, I could not confirm within the available code whether the slashing precompile's `Precompile` struct has a `BalanceHandlerFactory` set (i.e., whether `AfterBalanceChange`/bank-level reconciliation runs for it) — I found `NewPrecompile` construction is not indexed here, and I was unable to verify whether the value transfer for a precompile invocation is only an in-memory `StateDB` balance mutation (reverted like any other EVM state on tx revert, and reconciled at commit time via the bank keeper) or whether it constitutes a real, permanent bank-level fund movement outside of any reachable recovery path. This distinction is central to whether the impact is "permanently frozen" (Critical) versus a transient, functionally-irrelevant balance bump that a subsequent transaction from that "address" could never realize because no private key exists for `0x...0806` — which is the same characteristic that make this bucket of issue Critical in the ERC20 case (hence the explicit guard there).

## Assessment

The pattern found here — missing `contract.Value()` rejection on `slashing.Execute`, mirroring exactly the guard ERC20 added specifically to prevent unrecoverable fund loss — indicates a genuine gap in the slashing precompile relative to the codebase's own established safety pattern. If `msg.value` sent to `getSigningInfos`/`getSigningInfo`/`getParams`/`unjail` is transferred into the EVM balance of address `0x0000000000000000000000000000000000000806` (a fixed system address with no private key and no precompile method that can move value out on the caller's behalf), that value is unrecoverable — an unprivileged attacker can trigger it via an ordinary transaction with no special privileges, matching the Critical "permanent freezing of user funds" bar in the allowed impact list.

I could not fully verify the end-to-end commit path (state_transition.go / vm.EVM value-transfer semantics for precompile targets, and whether any block-level sweep or reconciliation reclaims such stray balances) within the indexed context, so I cannot state with certainty that funds are irreversibly lost versus merely inaccessible through documented precompile interfaces. This uncertainty is due to index coverage limits on the exact `EVM.Call`/`state_transition.go` value-transfer code path for precompile addresses.

### Title
Missing `msg.value` rejection in slashing precompile query/tx dispatch allows fund loss to non-recoverable precompile address - (File: `precompiles/slashing/slashing.go`)

### Summary
`Precompile.Execute` in `precompiles/slashing/slashing.go` dispatches to `GetSigningInfo`, `GetSigningInfos`, `GetParams`, and `Unjail` without ever checking `contract.Value()`, unlike the ERC20 precompile which explicitly rejects any nonzero value with `ErrCannotReceiveFunds` specifically because value sent to a precompile via `CALL` is otherwise unrecoverable.

### Finding Description [2](#0-1)  shows the dispatcher does not perform any value check before invoking `GetSigningInfo`/`GetSigningInfos`/`GetParams`/`Unjail`. None of these handlers ( [4](#0-3) ) consume `contract.Value()`. Compare this to the ERC20 precompile's explicit safeguard: [3](#0-2) , added as "a safety measure" against unrecoverable fund loss.

### Impact Explanation
If confirmed that value sent in a `CALL` to the slashing precompile address is durably credited to that address's balance (as the ERC20 comment implies is the general precompile behavior), funds sent this way would be permanently locked, since the fixed precompile address `0x...0806` has no private key and no exposed withdrawal path.

### Likelihood Explanation
Trivial to trigger — any unprivileged EOA or contract can send a `CALL` with `value > 0` and valid `getSigningInfos` calldata directly to `0x0000000000000000000000000000000000000806`, bypassing Solidity's compiler-generated non-payable check (which only exists in caller-side generated bytecode, not enforced by the precompile itself).

### Recommendation
Add the same `contract.Value().Sign() == 1` rejection check used in `precompiles/erc20/erc20.go` to `precompiles/slashing/slashing.go`'s `Execute` (and audit other precompiles — staking/distribution/gov/bank/ics20 — that lack this guard on their non-payable query paths) to reject any nonzero value before dispatch.

### Proof of Concept
Send a raw Ethereum transaction with `to = 0x0000000000000000000000000000000000000806`, `value = 1 ether`, and `data` = ABI-encoded `getSigningInfos(pageRequest)` call. If the transaction succeeds and returns the signing infos while debiting the caller's balance and crediting the precompile address's balance in `StateDB`/bank keeper with no subsequent recovery path, the invariant is violated.

**Caveat:** I was unable to fully verify the exact commit-time value-transfer semantics for `CALL`s targeting precompile addresses in this repository's `x/vm` state-transition code, so confirm this concretely with a live integration test (as suggested in the PoC) before treating this as a confirmed Critical before remediation.

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte

	switch method.Name {
	// slashing transactions
	case UnjailMethod:
		bz, err = p.Unjail(ctx, method, stateDB, contract, args)
	// slashing queries
	case GetSigningInfoMethod:
		bz, err = p.GetSigningInfo(ctx, method, contract, args)
	case GetSigningInfosMethod:
		bz, err = p.GetSigningInfos(ctx, method, contract, args)
	case GetParamsMethod:
		bz, err = p.GetParams(ctx, method, contract, args)
	default:
		return nil, fmt.Errorf(cmn.ErrUnknownMethod, method.Name)
	}

	return bz, err
}
