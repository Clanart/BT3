### Title
Silent Corruption of Committed File Content via Ambiguous Conflict-Marker Re-Scanning in Copilot Conflict Resolution - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` in `app/src/lib/copilot-conflict-resolution.ts` splices Copilot's per-hunk resolutions back into the on-disk conflicted file by re-scanning it line-by-line and matching `<<<<<<<`/`=======`/`>>>>>>>` marker patterns *by order of appearance*, not by any positional or content identity tied to the original hunk extraction. Because this re-scan is a separate, independent parser from whatever built the original hunk list shown to the model, any attacker-controlled file content that merely resembles conflict markers (without being real markers) can desynchronize the two parses, causing resolved content to be spliced into the wrong location — silently corrupting what the user commits and potentially pushes upstream.

### Finding Description
When the user hits a merge/rebase/cherry-pick conflict and uses the "Resolve with Copilot" flow, the app:
1. Extracts per-hunk conflict context per file (used to build the model prompt), stored as `IFileConflictContext.hunks`.
2. Sends the raw hunk content to the model, which returns `IHunkResolution[]` (one entry per hunk, matched only by order — see comment at [1](#0-0) ).
3. Validates only that the *count* of returned hunks matches the *count* of expected hunks per file via `validateResolutionPaths` [2](#0-1) .
4. Reassembles the final file by walking the **raw on-disk file content again** with a fresh, independent regex-based scan (`reassemblyOursMarker` / `reassemblySeparatorMarker` / `reassemblyTheirsMarker`), splicing `hunkResolutions[hunkIndex]` into each detected conflict block in order [3](#0-2) .

The broken invariant: the code assumes the ordinal sequence of conflict-marker blocks found by this second, independent scan is identical to the ordinal sequence of hunks that were extracted earlier and shown to the model. Nothing enforces that these two parses agree in the presence of adversarial file content. If the repository being merged/rebased contains a tracked file whose *non-conflicted* content contains sequences that match `^<{7}(?:\s|$)`, `^={7}$`, or `^>{7}(?:\s|$)` at line starts (e.g. ASCII banners, patch/diff fixtures, previously-and-incompletely-resolved nested conflict markers committed as literal text, or content deliberately crafted by a malicious contributor to a shared branch/fork), the re-scan can:
- detect a phantom or malformed block and skip it as "not a conflict" while the original hunk extractor counted it as a real conflict (or vice versa), or
- misalign the closing marker lookahead (`closingIndex`) if a `=======`/`>>>>>>>`-like line appears inside what the extractor considered a single hunk's content,

producing a shift in `hunkIndex` versus the true intended target block. Because `validateResolutionPaths` only checks that the *total* hunk count per file matches (not that block boundaries are the same), this desynchronization is not caught. The result is that a resolution intended for conflict N gets written into conflict M, and the file is written to disk and staged automatically via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and `git add` in `_applyCopilotConflictResolutions` [4](#0-3)  with no further diff-based sanity check before the user commits.

I was not able to fully verify, within the available tool budget, the exact hunk-extraction implementation in `app/src/lib/copilot-conflict-context.ts` (only partial grep matches were found, not the full parsing logic), so I cannot confirm with certainty whether its marker-detection algorithm is byte-for-byte identical to `reassembleResolvedFile`'s. Given they are two independently-written functions serving different purposes (one for prompt construction, one for output splicing), and the comment explicitly says matching is "by order, not by line number," this is a structurally fragile invariant even if today's implementations happen to agree on the common case.

### Impact Explanation
If exploitable, this allows content from one conflict resolution to be silently written into a different location in the file than the model intended, and the corrupted result is what the user reviews (in the result dialog, if they trust it) and commits/pushes. Because the write path auto-stages and there is no re-diff-against-original verification step for the AI-assisted flow (unlike the manual conflict UI which is driven directly off `git checkout --ours/--theirs`), this is a silent-corruption-of-what-the-user-commits scenario: security-relevant code changes could be dropped, reordered, or overwritten without any error being raised, and the corrupted commit can be pushed to a shared repository.

### Likelihood Explanation
Exploitability depends on:
- The user having the Copilot conflict resolution feature enabled and reaching a real merge/rebase/cherry-pick conflict against attacker-influenced content (e.g., a branch/fork the attacker contributed to, which is a realistic no-privilege attacker path since Desktop routinely merges branches from collaborators/PRs).
- The conflicted file (or its surrounding unconflicted context lines within the same hunk region) containing lines that coincidentally or deliberately match the marker regexes without being genuine conflict markers.

This is a narrow but structurally real edge case (crafted files, patch/diff fixtures, or previously mis-resolved conflicts containing literal marker-like text are plausible in real repos), and the validation logic (`validateResolutionPaths`) explicitly does not defend against it since it only checks aggregate hunk counts, not block-boundary alignment. I could not fully confirm the hunk-extraction parser's exact marker-detection rules to give a precise reproduction input, which is the main source of uncertainty here.

### Recommendation
Do not re-derive conflict block boundaries in `reassembleResolvedFile` via an independent regex scan of the raw file. Instead, reuse the exact same hunk boundaries (e.g., line offsets or the same parser) that were used to build `IFileConflictContext.hunks`, or thread positional metadata (start/end line indices) through `IHunkResolution` so reassembly cannot desynchronize from extraction. Additionally, add a verification step comparing the reassembled file against the original conflict markers actually removed (e.g., assert no leftover marker lines, and that the count/order of spliced blocks matches the originally extracted hunk offsets, not just their count) before writing to disk and staging.

### Proof of Concept
Not fully reproducible without confirming the exact algorithm in `copilot-conflict-context.ts`'s hunk extractor (which I could not fully retrieve). Conceptually:
1. Attacker contributes a branch/fork containing a file with two real conflicting hunks and, between them, unconflicted lines that happen to start with 7 `<`/`=`/`>` characters (e.g. a code comment banner, ASCII divider, or leftover literal conflict-marker text from history).
2. Victim merges/rebases this branch, hits conflicts, and uses "Resolve with Copilot."
3. The prompt-side extractor counts hunks based on its own parsing; `reassembleResolvedFile`'s independent scan (`app/src/lib/copilot-conflict-resolution.ts:549-599`) may treat the marker-like decoy lines differently, shifting `hunkIndex` relative to the true block being replaced.
4. `validateResolutionPaths` (`app/src/lib/copilot-conflict-resolution.ts:509-520`) passes because the total hunk count still matches.
5. `_applyCopilotConflictResolutions` writes the misaligned reassembled content to disk and stages it (`app/src/lib/stores/app-store.ts:7258-7268`), and the user commits/pushes silently corrupted content.

export function reassembleResolvedFile(
  rawContent: string,
  hunkResolutions: ReadonlyArray<IHunkResolution>
): string {
  const eol = rawContent.includes('\r\n') ? '\r\n' : '\n'
  const lines = rawContent.split(/\r?\n/)
  const resultLines: Array<string> = []
  let hunkIndex = 0
  let i = 0

  while (i < lines.length) {
    if (reassemblyOursMarker.test(lines[i])) {
      // Look ahead to verify this is a well-formed conflict block:
      // must have a ======= separator and a >>>>>>> closing marker.
      let hasSeparator = false
      let closingIndex = -1
      for (let j = i + 1; j < lines.length; j++) {
        if (reassemblySeparatorMarker.test(lines[j])) {
          hasSeparator = true
        } else if (reassemblyTheirsMarker.test(lines[j])) {
          closingIndex = j
          break
        }
      }

      if (!hasSeparator || closingIndex === -1) {
        // Malformed marker — copy through as regular content
        resultLines.push(lines[i])
        i++
        continue
      }

      // Skip through the entire conflict marker block
      i = closingIndex + 1

      // Splice in the resolved content for this hunk
      if (hunkIndex < hunkResolutions.length) {
        const resolved = hunkResolutions[hunkIndex].resolvedContent
        if (resolved.length > 0) {
          resultLines.push(...resolved.split(/\r?\n/))
        }
      }
      hunkIndex++
    } else {
      resultLines.push(lines[i])
      i++
    }
  }

  return resultLines.join(eol)
}
