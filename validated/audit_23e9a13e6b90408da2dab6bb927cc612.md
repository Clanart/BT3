### Title
Unchecked unsigned subtraction in `GPBCodedInputStreamBytesUntilLimit` can underflow if `bufferPos` exceeds `currentLimit` - ([File: objectivec/GPBCodedInputStream.m])

### Summary
`GPBCodedInputStreamBytesUntilLimit` computes `state->currentLimit - state->bufferPos` using unsigned `size_t` arithmetic with no check that `currentLimit >= bufferPos`. This is structurally the same failure pattern as the UniV3Oracle report: two values believed to satisfy an ordering invariant (`bufferPos <= currentLimit`, analogous to `obs0`'s timestamp preceding `obs1`'s) are subtracted directly. In the Solidity report the violated invariant caused a revert (DoS on price computation); in this C code the same violated invariant causes silent unsigned wraparound to a huge value, which is worse because it is not caught by any exception path.

### Finding Description
`objectivec/GPBCodedInputStream.m` maintains a single-limit stack via `PushLimit`/`PopLimit`: [1](#0-0) 

```
size_t GPBCodedInputStreamPushLimit(GPBCodedInputStreamState *state, size_t byteLimit) {
  byteLimit += state->bufferPos;
  size_t oldLimit = state->currentLimit;
  if (byteLimit > oldLimit) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidSubsectionLimit, nil);
  }
  state->currentLimit = byteLimit;
  return oldLimit;
}

void GPBCodedInputStreamPopLimit(GPBCodedInputStreamState *state, size_t oldLimit) {
  state->currentLimit = oldLimit;
}

size_t GPBCodedInputStreamBytesUntilLimit(GPBCodedInputStreamState *state) {
  return state->currentLimit - state->bufferPos;
}
```

`GPBCodedInputStreamBytesUntilLimit` never validates that `currentLimit >= bufferPos` before subtracting; it simply relies on the invariant being upheld by correct push/pop discipline elsewhere in the parser (`readMessage:`, `readMapEntry:`, `readGroup:`, all of which call `PushLimit`/pop in a strict LIFO nesting: [2](#0-1) ). `CheckSize` is the only other guard against reading past `currentLimit`, and it stops `bufferPos` exactly at `currentLimit` when the limit is hit: [3](#0-2) .

This mirrors the UniV3Oracle pattern exactly: the correctness of the subtraction depends entirely on an implicit invariant (`currentLimit >= bufferPos` / `timestamp1 >= timestamp0`) that is not verified at the point of use — it is only *usually* true because of how the surrounding code is structured. If any caller manages to invoke `PopLimit` with a stale/mismatched `oldLimit` (e.g., a limit captured before further reads advanced `bufferPos` past that captured value in a nested/loop scenario, or a caller bug in extension/unknown-field handling that pops an outer limit out of order relative to `bufferPos`), `currentLimit` can end up smaller than `bufferPos`. Because both fields are `size_t` (unsigned), `currentLimit - bufferPos` wraps around to a value near `SIZE_MAX` instead of producing a small or negative "past-limit" indicator.

### Impact Explanation
Unlike the Solidity case (which reverts, i.e., a safe failure), the ObjC arithmetic silently produces a bogus, enormous "bytes until limit" value with no exception raised. Any logic that trusts `bytesUntilLimit` as a bound (e.g., to decide whether more length-delimited data can be safely consumed within the current sub-message) could be misled into believing far more data remains than actually does, potentially reading beyond the intended message boundary into data belonging to an outer message/field. This is a parsing-correctness/integrity issue (crossing a length-delimited framing boundary), not a memory-safety issue, since actual byte reads are still bounded by `CheckSize` against `state->bufferSize`.

### Likelihood Explanation
I could not identify, within the code retrieved, an actual call site that violates the push/pop LIFO discipline — `readMessage:`, `readMapEntry:`, and `readGroup:` all follow strict "push, recurse, pop" ordering, and `CheckSize` clamps `bufferPos` to `currentLimit` on limit violations rather than letting it run past. This markedly limits the reachability of the underflow through the public generated-code parsing paths visible in this checkout. I was not able to fully audit `GPBDictionaryReadEntry`, extension-registry parsing, or `mergeFromCodedInputStream:` internals (not retrieved in the available context) to rule out an order-of-operations bug there that could pop a limit while `bufferPos` has already advanced past it. This is flagged as unverified rather than confirmed.

### Recommendation
Harden `GPBCodedInputStreamBytesUntilLimit` (and any other subtraction relying on `currentLimit`/`bufferPos` ordering) with an explicit invariant check, mirroring the corrected UniV3Oracle pattern of rejecting/short-circuiting instead of trusting implicit ordering:
```c
size_t GPBCodedInputStreamBytesUntilLimit(GPBCodedInputStreamState *state) {
  if (state->bufferPos > state->currentLimit) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidSubsectionLimit, nil);
  }
  return state->currentLimit - state->bufferPos;
}
```
Additionally, audit all callers of `PushLimit`/`PopLimit` (including `GPBDictionaryReadEntry` and extension-registry paths not covered here) to confirm strict LIFO nesting is enforced structurally, not just by convention.

### Proof of Concept
I was unable to construct or run a concrete bounded-input reproduction within this session — no call site was found in the retrieved code that violates the push/pop ordering, so I cannot currently demonstrate `currentLimit < bufferPos` being reached through a public parse API. This finding should be treated as a defense-in-depth gap (missing invariant check analogous to the reported bug class) rather than a proven exploitable underflow; a background engineer should specifically fuzz `mergeFromCodedInputStream:` with malformed nested length-delimited/group framing (mismatched limits across recursive extension/unknown-field parsing) to attempt to trigger `currentLimit < bufferPos` before deciding on remediation priority.
