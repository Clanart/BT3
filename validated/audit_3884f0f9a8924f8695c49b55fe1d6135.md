### Title
Recursive submodule operations do not restrict Git transport protocols, allowing `ext::` command execution from an attacker-controlled `.gitmodules` - ([File: app/src/lib/git/submodule.ts])

### Summary
Desktop clones, fetches, pulls, and checks out with `--recursive`/`--recurse-submodules` enabled by default, and never sets `GIT_ALLOW_PROTOCOL` (or an equivalent `protocol.*.allow` denylist for anything except `file`) around these invocations.

### Finding Description
`clone()` always passes `--recursive` to `git clone`, `fetch()` always passes `--recurse-submodules=on-demand`, `pull()` always passes `--recurse-submodules`, and `checkoutCommit()`/`checkoutBranch()` call `updateSubmodulesAfterOperation()` which runs `git submodule update --init --recursive`. The only protocol-related environment configuration in `updateSubmodulesAfterOperation` is a narrow `protocol.file.allow=always` toggle gated by `allowFileProtocol` — no other protocol is restricted. [5](#0-4)  Because `.gitmodules` is repository content controlled by whoever authored the commits (e.g., a malicious fork, a PR branch, or any cloned/fetched repository), an attacker can add a submodule entry whose URL uses Git's `ext::` transport (e.g. `url = ext::sh -c touch\ /tmp/pwned`). When Desktop clones such a repo, or fetches/pulls/checks out a branch containing this `.gitmodules`, the invoked `git submodule update --init --recursive` (or the recursive clone) will invoke the `ext::` helper command with no protocol allowlist in place to block it. This mirrors the historical `CVE-2017-1000117`/git-submodule "ext::"-transport RCE class of bug, where the fix upstream was for callers to set `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow=user` explicitly. `envForRemoteOperation`/`envForProxy` only handle proxy resolution for http(s) and do not add any protocol allowlist. [6](#0-5) 

### Impact Explanation
If exploitable, this results in arbitrary command execution on the user's machine merely by cloning, fetching, pulling, or checking out a branch from an attacker-controlled repository — a "clone/fetch a hostile repo → RCE" primitive squarely within scope (attacker controls a cloned/fetched repository object).

### Likelihood Explanation
This depends entirely on whether the embedded Git binary Desktop ships defaults to restricting `ext::`/other risky protocols on its own (modern Git versions disable `ext`, `file`, and other protocols by default for submodule recursion since Git 2.19+ / CVE-2018-11235 hardening, unless explicitly allowed). I could not verify the embedded `dugite`/Git version's default protocol allowlist behavior from the indexed code, since that lives in the vendored Git binary, not the app's TypeScript source. If the bundled Git version defaults to blocking `ext::` and other non-standard protocols during recursive submodule handling (as current Git releases do), then this finding is **not exploitable** and the missing explicit allowlist in `submodule.ts` is defense-in-depth only, not a real vulnerability — Desktop is relying on upstream Git's built-in protocol restrictions rather than duplicating them.

### Recommendation
Explicitly set `GIT_ALLOW_PROTOCOL=file:git:http:https:ssh` (or the git config equivalent, `protocol.allow=never` plus per-protocol `protocol.<name>.allow=always` for the ones actually needed) around all `envForRemoteOperation`-based invocations, rather than relying implicitly on whatever the bundled Git version's compiled-in defaults happen to be. Verify the exact Git version bundled via `dugite` and confirm its default `protocol.allow` behavior for `ext`, `ssh`, and any legacy `foreign_vcs` helpers before ruling this in or out with certainty.

### Proof of Concept
Could not be fully constructed/verified within this exercise because it requires confirming the exact behavior of the bundled Git binary (version and its compiled default `protocol.allow` list) — which is outside the indexed TypeScript source.
