### Title
Direct transfers to Serai's internal (branch/change/forward) Bitcoin addresses bypass the deposit path and are misclassified as protocol-owned outputs - (networks/bitcoin/src/wallet/mod.rs)

### Summary

In the Fractional `Buyout` finding, `end` counted tokens via `balanceOf(address(this))` without distinguishing tokens deposited through the constrained `sellFractions` path from tokens pushed in by a direct `safeTransferFrom`, letting an attacker bypass the intended accounting flow. The same bug class exists in Serai's Bitcoin integration: `get_outputs` classifies every scanned output purely by which registered offset script it pays to, with no provenance check. All of Serai's internal offsets (`Branch`, `Change`, `Forwarded`) are deterministic public values (`Secp256k1::hash_to_F(KEY_DST, b"branch")`, `b"change"`, `b"forward"`), so any unprivileged user can compute these addresses and send a Bitcoin transaction directly to them, bypassing the `External` deposit path (which is the only path that attaches InInstruction `data` and `presumed_origin`).

### Finding Description

`scanner()` registers fixed, publicly derivable offsets for each `OutputType` and `scan_transaction` matches outputs solely on `output.script_pubkey` membership in `self.scripts`. `get_outputs` then sets `kind` from the matched offset and only populates `data`/`presumed_origin` for `OutputType::External`. Therefore a deposit sent directly to the change or branch address produces an `Output` of `kind == Change`/`Branch` with no `data` and no origin — it is indistinguishable from Serai's own internal change and will be consumed by the scheduler as a protocol input rather than credited to the depositor. ### Impact Explanation

An unprivileged user sending funds to the derived `change`, `branch`, or `forward` address has their output reported as a protocol-internal output: it carries no InInstruction `data` and no `presumed_origin`, so no balance is credited to any Serai account, yet the funds are spendable by the multisig and will be swept as ordinary inputs. The depositor permanently loses the funds (funds received by the protocol but not attributable to — or recoverable by — the sender), the exact "tokens transferred directly to the contract bypass the intended deposit path" consequence of the reference bug.

### Likelihood Explanation

The offset scalars are deterministic `hash_to_F` values over the constant `KEY_DST` (`b"Serai Bitcoin Output Offset"`), and `branch_address`/`change_address`/`forward_address` are public functions, so the addresses are computable by anyone who knows the group key. A confused or malicious user needs only one ordinary Bitcoin transaction to trigger the misclassification; the scanner applies no filter on who created the output or whether the tx carries a Serai data commitment.

### Recommendation

Distinguish provenance like the recommended fix in the reference report ("record deposits made via the intended path"). Concretely, in `get_outputs` (`processor/src/networks/bitcoin.rs`), when an output matches the `Branch`, `Change`, or `Forwarded` offset but the containing transaction is not a Serai-constructed spend (e.g., does not spend a known Serai input / lacks the expected structure), either drop the output or reclassify it as `External` so it is still credited. Alternatively, require `Change`/`Branch` outputs to only be accepted when the tx spends a known Serai outpoint.

### Proof of Concept

1. Obtain the multisig group key `K` (public).
2. Compute `change_offset = Secp256k1::hash_to_F(b"Serai Bitcoin Output Offset", b"change")` (and increment until `K + G*offset` is even, mirroring `register_offset`).
3. Send a Bitcoin tx paying `p2tr_script_buf(K + G*change_offset)` from an unrelated wallet, with no InInstruction.
4. `get_outputs` returns an `Output { kind: OutputType::Change, presumed_origin: derived, data: [] }`; the scanner emits it and downstream code treats it as Serai-owned change. The sender's deposit is never credited while the multisig can (and eventually will) spend it.

  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }

    let mut res = Vec::new();

      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });

    }
