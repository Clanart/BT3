## Finding

### Title
Webhook `shop_domain` is not cryptographically bound to the HMAC-verified payload, enabling cross-shop webhook replay/spoofing - (File: `lib/shopify_app/controller_concerns/webhook_verification.rb`)

### Summary
The reported bug class is that a commitment/ciphertext is verified for integrity but is never cryptographically bound to the identity of the submitter (voter address), so a captured valid commitment can be replayed and attributed to a different identity. The `ShopifyApp::WebhookVerification` concern has the analogous property: it validates only the HMAC over the raw request body, while the shop identity used by downstream consumers (`shop_domain`) is read from an unauthenticated header that is completely outside the HMAC digest.

### Finding Description
`WebhookVerification#verify_request` computes/validates the HMAC solely over `request.raw_post`: [1](#0-0) 

The shop identity exposed to consumers of the module is taken directly from a request header that plays no part in that HMAC computation: [2](#0-1) 

`hmac_valid?` (shared by both webhook and app-extension verification) only ever hashes the raw payload bytes with the shared app secret — it never mixes in a shop identifier: [3](#0-2) 

The gem's own documentation instructs integrators to build custom webhook controllers that trust this unauthenticated `shop_domain` helper directly to route/attribute the (HMAC-verified) body to a shop: [4](#0-3) 

Because the digest never incorporates the shop identifier (the "voter address" analog), a valid `(raw_post, HMAC)` pair produced for one shop can be resubmitted with a different `X-Shopify-Shop-Domain` header value and will still pass `verify_request`, exactly as in the reported bug class where a valid commitment/ciphertext could be resubmitted under a different, unrelated voter's identity without needing to know the shared secret.

### Impact Explanation
Any consumer that follows the documented pattern and uses the `shop_domain` helper to key stored data, queue background jobs, or scope side effects can have data intended for shop A processed under an attacker-chosen `shop_domain` value, while still passing the app's HMAC check. This is a cross-shop attribution/confusion vulnerability of the same root cause as the reported "duplicable votes" issue: the authenticated payload and the identity used to process it are not bound together.

### Likelihood Explanation
The webhook endpoint is unauthenticated/anonymous-reachable and explicitly skips CSRF protection (`skip_before_action :verify_authenticity_token`), matching the required "unprivileged HTTP request" surface. Exploitation requires the attacker to already possess one valid `(body, HMAC)` pair (e.g., from their own shop's legitimate webhook traffic that they can observe/log), after which the shop-attribution header can be freely modified for replay — no knowledge of the shared secret is required, mirroring the original bug's "reuse without knowing contents" pattern.

### Recommendation
Bind the shop identity into the verified payload rather than trusting an out-of-band header: include/derive the shop domain from data that is itself covered by the HMAC (e.g., verify that the `shop_domain`/`X-Shopify-Shop-Domain` header matches a shop identifier embedded in the verified JSON body, or otherwise mix the header value into the HMAC computation before comparison) in `lib/shopify_app/controller_concerns/webhook_verification.rb` and `lib/shopify_app/controller_concerns/payload_verification.rb`, and update `docs/shopify_app/webhooks.md` guidance accordingly.

### Proof of Concept
1. Capture one legitimate webhook delivery for `shop-a.myshopify.com`: `raw_post = B`, header `X-Shopify-Hmac-Sha256 = H` (H is valid for B under the shared app secret).
2. Replay a POST to the app's webhook route with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `hmac_valid?(B)` succeeds (per `lib/shopify_app/controller_concerns/payload_verification.rb:13-23`) because it never checks the shop header.
4. `shop_domain` (per `lib/shopify_app/controller_concerns/webhook_verification.rb:23-25`) returns the attacker-supplied `shop-b.myshopify.com`, and any consumer job following the documented pattern (`docs/shopify_app/webhooks.md:86-104`) processes shop A's webhook payload as if it belonged to shop B.

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

If you'd rather implement your own controller then you'll want to use the [`ShopifyApp::WebhookVerification`](/lib/shopify_app/controller_concerns/webhook_verification.rb) module to verify your webhooks, example:

```ruby
class CustomWebhooksController < ApplicationController
  include ShopifyApp::WebhookVerification

  def carts_update
    params.permit!
    SomeJob.perform_later(shop_domain: shop_domain, webhook: webhook_params.to_h)
    head :no_content
  end

  private

  def webhook_params
    params.except(:controller, :action, :type)
  end
end
