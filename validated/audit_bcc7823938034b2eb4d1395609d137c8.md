Based on my investigation, I found a concrete analog in the credential trampoline logic. The original report's bug class is: **a security-relevant decision is derived from iterating over untrusted/attacker-influenced key-value data, and the first matching case "wins" without further verification.** The closest structural analog in GitHub Desktop is the `WWW-Authenticate` "happy path" check in `getEndpointKind`.

### Title
Attacker-controlled `WWW-Authenticate` header spoofs GitHub host classification, triggering unauthenticated GHE sign-in/OAuth flow against an arbitrary server - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind` classifies a git remote's endpoint as `'github.com'`, `'ghe.com'`, `'enterprise'`, or `'generic'` in order to decide whether GitHub Desktop should attempt to fill GitHub credentials or prompt an Enterprise sign-in. When the endpoint doesn't match a known dotcom/GHE hostname pattern, the code iterates the credential map's `wwwauth[N]` entries — values that come directly and unauthenticated from the remote server's HTTP response — and short-circuits to `'enterprise'` the moment it sees `realm="GitHub"`, with no cryptographic or DNS-based verification: [1](#0-0) 

### Finding Description
Git captures `WWW-Authenticate` response headers from whatever server it's talking to and forwards them verbatim to the credential helper as `wwwauth[]=` entries; this data is entirely attacker-controlled by anyone who runs (or MITMs) a git remote/proxy. The comment even states the intent is to avoid "having to resort to making a request ourselves" — i.e., to skip the actual verification that the fallback path performs via `isGitHubHost(endpoint)`: [2](#0-1) 

This is functionally the same class of flaw as the Axelar report: a lookup/classification loop over externally-influenced data is trusted to select "the" branch of security logic, without confirming there is only one legitimate case or verifying the source of the signal. Here, instead of non-determinism across nodes, the risk is that any attacker-controlled endpoint can force itself to be treated as an "enterprise" (GitHub) endpoint just by returning a crafted header — no valid TLS identity or GitHub-specific response is required.

Once `endpointKind !== 'generic'`, `getCredential` checks whether an account already exists for that endpoint; if not, it invokes the interactive Enterprise sign-in flow for the attacker's own endpoint URL: [3](#0-2) 

### Impact Explanation
An attacker who controls (or intercepts/proxies) a git remote that the victim fetches/clones/pushes to can force GitHub Desktop to present the user with a native "Sign in to GitHub Enterprise" prompt bound to the attacker's chosen endpoint URL, purely from a spoofed `WWW-Authenticate: realm="GitHub"` header on a 401 response — something entirely under the attacker's control, requiring no valid GitHub-Enterprise deployment. This routes the user into Desktop's Enterprise OAuth/token flow (`getOAuthAuthorizationURL`/`requestOAuthToken` in `app/src/lib/api.ts`) against an untrusted host chosen by the attacker, which is a phishing/OAuth-hijack primitive matching the "unauthorized OAuth" impact category. It also causes the app's credential-fill logic to skip the generic/external credential helper path for that host (`if (endpointKind !== 'generic') return undefined`), silently changing how the app authenticates to a remote the user did not choose. [4](#0-3) 

### Likelihood Explanation
The trigger requires only that the user perform a normal git operation (fetch/clone/push) against a remote or proxy the attacker controls — exactly the "attacker controls a git remote/proxy response" scenario. No local access, malware, or leaked credentials are needed; the header is sent as part of a standard HTTP 401 challenge during a routine Desktop-initiated git network operation.

### Recommendation
Do not treat the `wwwauth[]` `realm` value as sufficient proof of a GitHub host. Either remove the header-based short-circuit entirely and always fall back to the authenticated `isGitHubHost(endpoint)` network check, or require that the check additionally confirm a legitimate GitHub-specific response signal (e.g., `x-github-request-id`) before classifying an unknown host as `'enterprise'`, matching the same verification level used in the non-header fallback path.

### Proof of Concept
1. Attacker stands up an HTTPS server (any hostname, e.g. `https://evil.example`) and configures it to respond `401 Unauthorized` with header `WWW-Authenticate: Basic realm="GitHub"` for any git-smart-http request.
2. Victim adds `https://evil.example/foo/bar.git` as a remote and runs `fetch`/`push` in GitHub Desktop.
3. Git captures the header and forwards `wwwauth[0]=Basic realm="GitHub"` to Desktop's credential trampoline via `getCredential`.
4. `getEndpointKind` (`trampoline-credential-helper.ts:157-165`) matches `realm="GitHub"` and returns `'enterprise'` without any network verification.
5. Since no existing account matches `evil.example`, Desktop shows an "Sign in to GitHub Enterprise" prompt bound to `https://evil.example`, and if the user proceeds, Desktop's OAuth exchange (`requestOAuthToken` in `app/src/lib/api.ts`) is performed against the attacker-controlled host.
