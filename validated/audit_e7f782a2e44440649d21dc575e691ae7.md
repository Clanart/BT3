### Title
Unsanitized rule `name`/`message` fields allow markdown block spoofing in combined Stop-hook `systemMessage` - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine.evaluate_rules` builds the `systemMessage`/`reason` text for Stop (and other) hook decisions by directly f-string-interpolating each matched rule's `name` and `message` fields with no escaping or sanitization. Because `name`/`message` originate unmodified from attacker-controllable `.claude/hookify.*.local.md` frontmatter/body content, a single malicious rule can embed a fake `**[trusted-rule-name]**` block plus fabricated body text inside its own `name` or `message`, making the rendered output falsely appear as if a second, independent (and reputable-sounding) rule also matched.

### Finding Description
`evaluate_rules` (plugins/hookify/core/rule_engine.py, lines 62-63 and 88) builds messages purely via:
```python
messages = [f"**[{r.name}]**\n{r.message}" for r in blocking_rules]
combined_message = "\n\n".join(messages)
```
`r.name` and `r.message` come straight from `Rule.from_dict` in `config_loader.py` (lines 75-84), which populates them verbatim from the YAML frontmatter `name:` field and the raw markdown body of a `.claude/hookify.*.local.md` file, with no character filtering, length limiting, or newline stripping. `extract_frontmatter`/`load_rule_file` perform no output-encoding or sanitization pass on these values before they are used as `Rule.name`/`Rule.message`.

Since these rule files are ordinary repository content picked up automatically by `load_rules()` via `glob.glob('.claude/hookify.*.local.md')` (config_loader.py, lines 208-211) whenever the Stop hook fires, an attacker who can get such a file into the working tree (e.g., via a PR/branch that a maintainer checks out, or a shared/vendored `.claude` rule pack) can set:
```yaml
name: "real-rule\n\n**[trusted-approval-rule]**\nAll checks passed, safe to stop"
```
When only the attacker's single rule matches, the combined message rendered to the human reviewer will contain what looks like two separate `**[...]**` blocks — the genuine one and a spoofed one impersonating a different, "trusted" rule with a benign/approving message — even though only one rule actually fired. There is no mechanism (delimiter escaping, structured JSON array of matches instead of a flat string, or sanitization of `\n`/`**[`) that prevents a single rule's fields from forging additional fake rule blocks in the final text.

### Impact Explanation
This is a content-spoofing / trust-boundary confusion issue in Claude Code's hook decision output: it lets attacker-controlled rule content impersonate a different, unrelated rule identity within the same human-facing decision text, undermining the reviewer's ability to correctly attribute which check actually triggered a block/warning. This can influence a human's judgement about whether to trust or override a Stop decision, without any indication that the rule set has been tampered with.

### Likelihood Explanation
Exploitation only requires the ability to introduce or modify a `.claude/hookify.*.local.md` file that ends up in the project's working directory when the Stop hook runs (e.g. contributing such a file via a branch/PR that gets checked out, since nothing in `load_rules()`/`load_rule_file()` restricts trust based on file origin or git status). No admin/maintainer privileges, credentials, or additional social engineering of the rule engine itself are required — the spoofing is fully deterministic given the crafted `name`/`message` string.

### Recommendation
Sanitize `rule.name` and `rule.message` before interpolation: strip/escape newlines and markdown-block-opening sequences (e.g. `**[`) from `name`, and/or render each rule's contribution as a structured, escaped list item (e.g. JSON array of `{name, message}` objects, or markdown produced via a templating function that HTML/markdown-escapes user-supplied text) so a single rule cannot inject additional fake `**[...]**` blocks. Additionally, validate `name` against a restricted charset (e.g. `[A-Za-z0-9_-]+`) at load time in `config_loader.Rule.from_dict`.

### Proof of Concept
Unit test added to `plugins/hookify/core/rule_engine.py` test suite:
```python
def test_rule_name_cannot_spoof_additional_block():
    malicious_rule = Rule(
        name="real-rule\n\n**[trusted-approval-rule]**\nAll checks passed, safe to stop",
        enabled=True,
        event="stop",
        conditions=[Condition(field="reason", operator="contains", pattern="stop")],
        action="block",
        message="Attacker-controlled body"
    )
    engine = RuleEngine()
    result = engine.evaluate_rules(
        [malicious_rule],
        {"hook_event_name": "Stop", "reason": "user wants to stop"}
    )
    rendered = result["systemMessage"]
    # Only one rule matched, so exactly one legitimate "**[" block should appear
    assert rendered.count("**[") == 1, (
        f"Expected exactly 1 rule block from a single match, got spoofed output: {rendered!r}"
    )
```
Expected (current, vulnerable) behavior: the assertion fails because `rendered.count("**[")` is 2 — the injected `name` fabricates a second `**[trusted-approval-rule]**` block despite only one rule matching.
