### Title
Scanner credits zero/dust-valued outputs as received funds that cannot be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a deposit path where a user transfers real value in, but the credited/minted amount rounds down to zero, so the protocol keeps the funds and the user receives nothing usable. The analog in Serai is in `networks/bitcoin/src/wallet`: `Scanner::scan_transaction` reports any output paying to a registered `script_pubkey` as a `ReceivedOutput`, with no minimum-value check, while `SignableTransaction::new` treats every `ReceivedOutput` as fully spendable input value. Outputs below the dust threshold (or zero-valued) are credited as received yet are economically or practically unspendable — an unprivileged party can send such outputs to a monitored address using only public transaction data.

### Finding Description
`Scanner::scan_transaction` matches outputs purely on `output.script_pubkey` membership in `self.scripts` and unconditionally pushes a `ReceivedOutput` carrying the output's value (networks/bitcoin/src/wallet/mod.rs:199-214). There is no check that `output.value` meets the dust threshold or even exceeds zero.

The spend side, `SignableTransaction::new` (networks/bitcoin/src/wallet/send.rs:150-256), sums all `inputs` values as `input_sat` (line 175) and enforces `DUST` only on *payment* outputs (lines 165-169). A `ReceivedOutput` with value < 546 sats:

- is counted toward the balance the wallet "received",
- cannot fund a payment by itself, since any payment output must be ≥ `DUST` and the fee alone typically exceeds the dust input's value,
- when combined with other inputs contributes less value than the marginal fee cost of adding it as an input (~`fee_per_vbyte * input_vbytes`), so spending it destroys value rather than adding it.

The only guard that ever fires is `NotEnoughFunds` when `input_sat < payment_sat + needed_fee`, which treats the dust input's face value as real usable balance — it is never discounted by its input-cost. A zero-value output is even starker: it is reported as a received output yet can never be spent without losing money on fees.

This mirrors the report's shape exactly: value flows to a Serai-controlled script, the system credits the deposit (`scan_transaction` returns it as `ReceivedOutput`), but the credited amount is effectively zero/unspendable. Reachability requires only that an external party send a Bitcoin transaction — a listed allowed input ("Bitcoin transactions they send").

### Impact Explanation
Funds are reported received that are not spendable (an explicitly accepted impact class). An attacker can grief accounting by flooding registered/offset addresses with dust outputs, or more concretely, a depositor whose real payment lands below `DUST` (e.g., due to a malformed or split transaction) is credited with an output the multisig can never economically spend — the bitcoin is locked exactly like the zero-mint LRT deposit in the original report. `needed_fee`/`fee` accounting (send.rs:133-141, 215-221) also becomes incorrect because dust inputs inflate `input_sat` while costing more in fee than they contribute.

### Likelihood Explanation
Any unprivileged party can send dust or zero-value Taproot outputs to a scanned `script_pubkey`; no validator cooperation, key access, or internal state is needed. Bitcoin's consensus rules permit zero-value and sub-dust outputs in non-standard or miner-included transactions, and dust outputs are trivially relayed in many configurations. The only mitigating factor is that outputs with value < dust are non-standard to relay under default policy, but they are consensus-valid and occur in practice (e.g., inscription-era dust spam). Medium likelihood, bounded impact (DoS/accounting grief + locked funds rather than theft).

### Recommendation
In `Scanner::scan_transaction` (networks/bitcoin/src/wallet/mod.rs:199-214), skip outputs whose `value.to_sat() < DUST` (reuse the `DUST` constant from `send.rs`) or value == 0, so non-spendable outputs are never reported as received. Additionally or alternatively, in `SignableTransaction::new` (send.rs:150-256), filter `inputs` to drop `ReceivedOutput`s whose value is below `DUST`, and/or require each input's value to exceed the marginal fee cost of including it (`fee_per_vbyte * input_vbytes`) before counting it toward `input_sat` — analogous to the report's recommended `amountOut == 0` revert.

### Proof of Concept
```rust
// networks/bitcoin — conceptual PoC
let scanner = Scanner::new(tweaked_group_key).unwrap();
// Attacker sends a tx with an output paying to the scanned script_pubkey
// with value = 1 sat (or 0).
let dust_tx: Transaction = /* tx with TxOut { value: Amount::from_sat(1), script_pubkey: scanned_script } */;

let outputs = scanner.scan_transaction(&dust_tx);
// BUG: outputs.len() == 1 — a 1-sat output is reported as received
assert_eq!(outputs[0].value(), 1);

// It can never fund anything: DUST check on payments requires >= 546 sats,
// and the fee to spend the input exceeds its 1-sat value.
// SignableTransaction::new(vec![outputs[0].clone()], &payments, ... ) -> NotEnoughFunds,
// yet the wallet's accounting credited 1 sat as received.
```

Root cause: `scan_transaction` unconditionally accepts matched outputs at mod.rs:205-211 with no `value >= DUST` check, and `SignableTransaction::new` counts every input's face value at send.rs:175 without checking it exceeds its marginal spend cost.

*Caveat: I verified the scanner and spend paths fully; I did not check whether a higher layer (e.g., the processor feeding `ReceivedOutput`s) performs its own dust filtering — if such filtering exists upstream, severity drops.*
