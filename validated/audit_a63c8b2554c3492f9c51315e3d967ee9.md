This confirms `PayoutCheckerTask::run_once` runs automatically per-operator, polling `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` and, if found, automatically calls `handle_finalized_payout` and proceeds to kick off / claim reimbursement — with no independent check that the operator itself actually broadcast that specific payout transaction. It fully trusts the DB-recorded `payout_payer_operator_xonly_pk`, which is populated solely from `get_first_op_return_output` in `update_finalized_payouts`.

### Title
Attacker-chosen sighash flag + first-OP_RETURN attribution lets payout credit be reassigned to an arbitrary operator via RBF - (File: `core/src/verifier.rs`, `crates/clementine-tx-sender/src/rbf.rs`, `core/src/builder/transaction/operator_reimburse.rs`)

### Summary
`create_payout_txhandler` signs the withdrawal input with the user-chosen `sighash_type` (rules explicitly allow the attacker/withdrawer to pick this), and if the withdrawer picks `SIGHASH_SINGLE|ANYONECANPAY` the signature only commits to input 0 and output 0 (the user payout), leaving the anchor and OP_RETURN outputs unconstrained. An unprivileged party can therefore RBF-replace the operator's broadcast-but-unconfirmed payout transaction, keep the same witness and output 0, and substitute a different OP_RETURN (containing any operator's valid xonly pubkey) while dropping the real funding operator's OP_RETURN. `get_first_op_return_output` (`circuits-lib/src/bridge_circuit/mod.rs` L688-692), consumed by `Verifier::update_finalized_payouts` (`core/src/verifier.rs` L2312-2321), blindly records whichever OP_RETURN comes first as the payer, with no relationship to who actually funded the payout.

### Finding Description
Binding claimed: `payout_payer_operator_xonly_pk (DB)` == `operator_xonly_pk of the operator who actually funded/broadcast the payout tx`. This binding is enforced only by "first OP_RETURN found in the mined payout transaction," which is not authenticated in any way.

`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs` L407-436) signs input 0 with `txhandler.set_p2tr_key_spend_witness(&user_sig, 0)`, where `user_sig` (and its `sighash_type`) is supplied by the withdrawer. `Operator::withdraw` (`core/src/operator.rs` L630-637) verifies this signature with `SECP.verify_schnorr` against `user_xonly_pk`, but accepts whatever `sighash_type` the withdrawer chose — the rules explicitly grant the attacker the ability to "choose ... a Schnorr signature and its sighash flag." If the withdrawer (who may be the attacker, withdrawing their own funds) chooses `SIGHASH_SINGLE | SIGHASH_ANYONECANPAY`, the resulting signature commits only to input 0 and to output 0 (the user payout output) — not to output 1 (anchor) or output 2 (OP_RETURN with the operator's pubkey).

The operator then funds/broadcasts this transaction via `fund_raw_transaction(..., add_inputs: Some(true), replaceable: ...)`. Because outputs 1 and 2 are not covered by the signature, an attacker who observes the transaction in the mempool can build a replacement transaction that: reuses the exact same input 0 (same outpoint + same witness/signature, still valid because it isn't bound to the other outputs), keeps output 0 unchanged (required for the SIGHASH_SINGLE digest to remain valid), and replaces outputs 1/2 with the attacker's own funding input and a spurious OP_RETURN containing any syntactically-valid 32-byte xonly pubkey (e.g., an existing operator Q's real pubkey), omitting the real operator R's OP_RETURN entirely. The attacker pays the RBF fee bump with their own funds — no operator/verifier/aggregator privileges are required.

Once mined, `Verifier::update_finalized_payouts` (`core/src/verifier.rs` L2311-2321) calls `get_first_op_return_output`, which just does `tx.output.iter().find(|out| out.script_pubkey.is_op_return())` (`circuits-lib/src/bridge_circuit/mod.rs` L688-692) with no cross-check against which input/signature actually authorized which output. It parses whatever pubkey is there and stores it as `payout_payer_operator_xonly_pk` via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs` L198-251).

Downstream consumers trust this DB field unconditionally:
- `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs` L39-47) polls `get_first_unhandled_payout_by_operator_xonly_pk(self.operator.signer.xonly_public_key)` for *each* operator's own automation, and if it matches, automatically calls `handle_finalized_payout` and proceeds toward a kickoff/reimbursement — with no verification that the operator itself broadcast the payout.
- `Operator::validate_payer_is_operator` (`core/src/operator.rs` L1686-1740) rejects the real funding operator R's reimbursement attempt because the DB says the payer is Q, not R ("Payer is not own operator for deposit").
- `Verifier::is_kickoff_malicious` (`core/src/verifier.rs` L1857-1915) compares `operator_xonly_pk` (from the DB, now Q) against `kickoff_data.operator_xonly_pk`; if Q's kickoff matches Q's own DB-recorded value, the kickoff is *not* flagged malicious, since both sides of the check were derived from the same forged attribution.

None of `Verifier::is_deposit_valid`, `Operator::is_profitable`, `SECP.verify_schnorr`, `only_aggregator_and_self`, `verify_storage_proofs`, `SPV::verify`, or the presigned transaction graph validate that the OP_RETURN pubkey corresponds to the entity that actually broadcast/funded the transaction — none of them inspect signature coverage of non-output-0 outputs.

### Impact Explanation
- The honest operator R, who genuinely funded the withdrawer's payout from its own wallet, is permanently blocked from reimbursement for that deposit (`validate_payer_is_operator` fails forever, since the DB field is fixed post-finalization) — matches Critical: "an honest operator permanently unable to be reimbursed."
- If operator Q's own automation (`PayoutCheckerTask`) picks up the forged attribution (it polls purely by its own xonly pubkey with no additional check), Q's software will automatically proceed to kick off and eventually claim the Reimburse transaction for a deposit whose withdrawal Q never funded — matches Critical: "an operator reimbursed for a payout it never funded." This is a real BTC/asset-diversion primitive since the deposit's move-to-vault UTXO gets spent to "reimburse" a party that expended nothing.
- The attack is repeatable across any withdrawal for which the attacker/withdrawer controls their own signature's sighash flag (i.e., every future withdrawal, since sighash flag choice is attacker-controlled per the stated rules), and can target any operator's known xonly pubkey.

### Likelihood Explanation
The attacker needs only: (1) to be a normal withdrawer able to choose `SIGHASH_SINGLE|ANYONECANPAY` for their own withdrawal signature (explicitly within attacker capability per the rules), (2) enough BTC to fund an RBF fee-bump input, and (3) the ability to observe/replace the operator's not-yet-confirmed payout transaction in the mempool before it confirms — all standard, unprivileged Bitcoin operations. No verifier, operator, or aggregator compromise is needed. Operator xonly pubkeys are generally public (needed for deposit/kickoff protocol), so choosing a target "Q" is trivial.

### Recommendation
Enforce a fixed, non-malleable sighash type for the payout input (`SIGHASH_ALL`, or if `ANYONECANPAY` is required for RBF-style funding, at minimum enforce `SIGHASH_SINGLE` is rejected in favor of an explicit commitment covering the OP_RETURN output — e.g., require the sighash to cover a fixed-position OP_RETURN, or better, remove attacker sighash-flag choice altogether and have the operator/aggregator dictate the sighash type). Additionally, `get_first_op_return_output`/`update_finalized_payouts` should validate that the OP_RETURN commitment is structurally bound to the same transaction that pays the withdrawer (e.g., verify a fixed output index/order rather than "first found"), and cross-check that the operator claiming payer credit is the one whose wallet/keys funded the extra inputs (not derivable purely from an unauthenticated OP_RETURN).
