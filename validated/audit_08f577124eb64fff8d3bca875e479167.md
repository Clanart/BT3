## Analysis

The LayerZero ONFT bug is about an unchecked, unbounded decimal-scaling factor derived from `local_decimals - shared_decimals` that is computed once at config time and then applied unchecked on every transfer, causing overflow/DoS. The Hyperbridge codebase has a structurally identical pattern in the `hyper-fungible-token` pallet's ERC20 ⇄ substrate-balance conversion.

### Title
Live (mutable) asset metadata decimals combined with frozen `Precisions` config allow unbounded/incorrect cross-chain amount scaling and `u128::pow` overflow in `hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`register_token`/`update_token` validate the decimal relationship between a local asset and its EVM counterpart exactly once, at registration time, and persist only the EVM side (`Precisions` storage). The local side of the ratio is *not* persisted — every subsequent `send`, `on_accept`, and `on_timeout` call re-reads the local decimals live via `<T::Assets as fungibles::metadata::Inspect<_>>::decimals(asset_id)` and recomputes the scaling exponent with `erc_decimals.saturating_sub(local_decimals)`.

### Finding Description
At registration: [1](#0-0) 
`config.decimals >= local_decimals` is checked only once, using whatever `local_decimals` happens to be *at registration time*, and the result (`config.decimals`) is stored permanently in `Precisions`. The `local_decimals` value itself is never stored — it is recomputed dynamically on every subsequent call: [2](#0-1) 

and identically in `on_timeout`: [3](#0-2) 

and in `send`: [4](#0-3) 

Both conversion helpers use `saturating_sub` and an unbounded exponent on the *native* `u128` type before widening: [5](#0-4) 

Because `local_decimals` for non-native assets is read live from `pallet-assets` metadata rather than from a value frozen at registration, the invariant `erc_decimals >= local_decimals` enforced by `register_token`/`update_token` can silently break after registration if the asset's metadata decimals are later changed (via `pallet-assets::set_metadata`, callable by the asset's `Owner` — unless `freeze_metadata` was invoked, which the pallet does not enforce or require). If `local_decimals` grows to meet or exceed `erc_decimals`:
- `erc_decimals.saturating_sub(local_decimals)` silently clamps to `0` instead of going negative, so `convert_to_erc20`/`convert_to_balance` apply a scaling factor of `10^0 = 1` instead of the correct (now-negative, i.e. inverse) scaling — corrupting every subsequent cross-chain amount computed by the pallet (`send`, `on_accept` mint/release, and `on_timeout` refund) without any error being raised.
- Conversely, if `register_token`/`update_token` is ever invoked (by `CreateOrigin`) with a very large decimal gap (e.g. `local_decimals = 0`, `config.decimals = 200`, which still satisfies `config.decimals >= local_decimals`), `10u128.pow(200)` in `convert_to_erc20`/`convert_to_balance` overflows the native `u128` computation before it's widened to `U256`. Depending on whether the runtime enables overflow-checks, this either traps (permanently failing `send`/`on_accept`/`on_timeout` for that asset — funds already escrowed can never be released/refunded, since the timeout path uses the exact same computation) or wraps silently, producing an attacker-uncontrolled but corrupted amount.

This is the exact analog of the reported bug: an unbounded, unchecked decimal-scaling exponent computed from two independently-set decimal values, applied via unchecked native-width arithmetic, on both the send and receive/timeout paths.

### Impact Explanation
- Once the local/EVM decimal invariant desyncs (via ordinary, permitted metadata mutation on the asset, or via extreme registration values), amounts minted/released to beneficiaries in `on_accept` and amounts refunded in `on_timeout` are computed with a wrong scale factor — this is a "wrong beneficiary or amount" / fund-loss or fund-inflation bug, not a cosmetic issue.
- Because `on_timeout` uses the identical (now-corrupted or panicking) conversion, escrowed/burned tokens from `send` can become **permanently unrecoverable**: if the pow overflows and traps, both the success path (`on_accept` on destination) and the failure path (`on_timeout` refund on source) will keep failing, freezing the corresponding message and its underlying escrowed funds.
- If the scale instead silently clamps to `1x` due to `saturating_sub`, users on one side systematically receive far more or far less than the correct amount, with no revert to signal it.

### Likelihood Explanation
`register_token`/`update_token` are `CreateOrigin`-gated, so triggering the extreme-decimal-gap case requires the trusted registrar to make an unusual choice, similar to how the original LayerZero bug required only the ordinary/trusted `init` call to accept an unvalidated decimal value — no malicious relayer, prover, or governance compromise is needed, just the absence of a bound check that the code otherwise clearly intends to have (the existing `config.decimals >= local_decimals` check shows the authors are aware of the invariant but only enforce the lower bound, never an upper bound on the *difference*). The metadata-drift variant additionally does not require `CreateOrigin` at all — it only requires that the registered asset's `pallet-assets` metadata is not frozen, which is a runtime/asset-creation choice, not something the `hyper-fungible-token` pallet itself enforces or checks.

### Recommendation
- Persist `local_decimals` (or the resolved scaling factor) at registration time inside `Precisions`/a new storage item, instead of re-reading live, mutable `pallet-assets` metadata on every transfer.
- Require `freeze_metadata` (or an equivalent immutability guarantee) for any asset registered with `native: true`/`false` before `register_token` succeeds, or re-validate the invariant against the live value on every call and reject/abort rather than `saturating_sub`-ing to zero.
- Cap the maximum allowed decimal difference (e.g. `<= 18` or whatever fits safely in `u128::pow`) in `register_token`/`update_token`, mirroring the fix accepted for the original LayerZero report.
- Use `checked_pow`/`checked_mul` in `convert_to_erc20`/`convert_to_balance` and propagate an error instead of allowing a panic or silent wraparound.

### Proof of Concept
1. Governance calls `register_token` for asset `X` with `native: false`, current `pallet-assets` decimals `= 6`, and EVM `config.decimals = 18` for chain `C`. Check `18 >= 6` passes; `Precisions[X, C] = 18` is stored permanently.
2. The asset's `Owner` (not the bridge's `CreateOrigin`) later calls `pallet_assets::set_metadata` to change `X`'s decimals to `18` (permitted since metadata wasn't frozen).
3. A user calls `send` for asset `X` to chain `C` with `amount = 1_000_000` (interpreted now at the pallet's *live* 18-decimal metadata).
   - `decimals = Inspect::decimals(X) = 18` (live), `erc_decimals = Precisions[X, C] = 18` (frozen at registration).
   - `convert_to_erc20(1_000_000, 18, 18) = 1_000_000 * 10^(18-18) = 1_000_000` — no scaling applied even though the original registration intended a `10^12` scale-up (`config.decimals(18) >= local_decimals(6)` at registration time).
   - The EVM-side `HyperFungibleToken`/`WrappedHyperFungibleToken` contract receives an amount `10^12` times smaller than intended, permanently under-crediting the beneficiary relative to what was escrowed/burned on the substrate side — see the conversion call sites: [6](#0-5)  and helper [7](#0-6) .

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
