### Title
Missing identity check on registered DKG encryption keys lets any observer decrypt secret shares - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The PedPoP DKG's `Encryption`/`Decryption` layer performs an "incomplete blacklist" style validation — the exact analog of CVE-2015-8560, where `util.c` filtered dangerous characters but forgot `;`. Here, every other scalar/point that feeds a sensitive computation is forced non-zero/non-identity (`C::random_nonzero_F`, canonical `read_G`), yet a participant-supplied ECDH public key (`enc_key` in `EncryptionKeyMessage`) is registered and used without any check that it is not the identity point. A participant who registers `enc_key = identity` causes every `EncryptedMessage` addressed to them to be encrypted under an ECDH shared secret that equals the identity point — a publicly known value — so the ChaCha20 keystream key is computable by anyone.

### Finding Description
`EncryptionKeyMessage::read` parses `enc_key` with `C::read_G`, which only enforces canonical encoding (identity is a canonical encoding), and `Decryption::register` stores it unconditionally — there is no identity/torsion rejection anywhere [1](#0-0) [2](#0-1) . Later, `encrypt` computes the shared key as `ecdh(&key, to)` = `to * key`; with `to == identity` this product is always the identity point regardless of the random per-message `key` [3](#0-2) [4](#0-3) . The ChaCha20 key is derived from `transcript.append_message(b"shared_key", ecdh.to_bytes())` with a static IV — correct only under the assumption the ECDH output is secret [5](#0-4) . Since `Enc(identity || context)` is publicly computable, the ciphertext is XORed with a keystream any observer can regenerate. The honest senders hit this path automatically: `SecretShareMachine::generate_secret_shares` encrypts each share to `self.decryption.enc_keys[&participant]` without inspecting it [6](#0-5) [7](#0-6) .

Contrast with the rest of the codebase, which does enforce the missing check: nonces, encryption scalars, and coefficients all come from `C::random_nonzero_F`, and `read_F` enforces canonical scalars — the dangerous-value list simply omits "identity ECDH public key" [8](#0-7) .

### Impact Explanation
Any party that can observe the encrypted secret-share messages addressed to the malicious participant (in Serai's deployment these messages are relayed through the coordinator/Tributary layer, where all validators see them) can decrypt the plaintext secret shares sent to that participant. The sum of those shares is that participant's final `ThresholdKeys` `secret_share`, so the DKG's confidentiality guarantee — each share known only to its holder — is silently broken. An observer effectively becomes an additional holder of that share, undermining the threshold assumption (a `(t-1)`-member coalition plus an observer reaches `t` shares; a lone observer also gains material usable against share-reuse/ROS-style attacks on that participant's signing). This is key-share recovery reachable purely from public/relayed DKG transcript data, not a documented-MUST misuse: nothing in `KeyGenMachine`/`Commitments` documentation tells callers to reject identity encryption keys.

### Likelihood Explanation
A single malicious DKG participant triggers it deterministically by serializing `enc_key` as the identity encoding in their `EncryptionKeyMessage` — one mutated point in an otherwise validly-signed commitment message. All `n-1` honest participants will then encrypt shares to the identity key in the very next round. No honest participant can detect it, since nothing validates the key and decryption "succeeds" normally for the attacker. The only precondition is the standard one for this class: the attacker participates in (or registers into) a DKG session.

### Recommendation
Reject identity (and, for curves with a cofactor, low-order/torsion points) in `Decryption::register` — e.g., `if bool::from(msg.enc_key.is_identity()) { Err/PedPoPError::InvalidCommitments }` — and apply the same check in `EncryptedMessage`/`EncryptionKeyMessage` validation paths. Preferably, have `C::read_G` callers that consume peer ECDH keys use a `read_nonidentity_G` helper. Also consider binding `enc_key` into the PedPoP PoK `challenge` so the encryption key is proven together with the commitments [9](#0-8) .

### Proof of Concept

```rust
// Malicious participant i_mal in a PedPoP DKG (context Ctx, params t-of-n).
// Instead of broadcasting EncryptionKeyMessage { msg: Commitments, enc_key: g^k },
// broadcast it with:
let malicious_msg = EncryptionKeyMessage::<C, Commitments<C>> {
    msg: valid_commitments,      // PoK over coefficients verifies normally
    enc_key: C::G::identity(),   // canonical encoding; passes read_G and register
};

// Honest participant j executes:
//   generate_secret_shares -> encrypt(rng, i_mal, share_j_to_mal)
//   -> ecdh(&key_j, identity) == identity
//   -> cipher(context, &identity)  // keystream key = H(context, identity_bytes), public
// The EncryptedMessage ciphertext C_j = share_j XOR keystream.

// Observer recovery (no private keys needed):
let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
transcript.append_message(b"context", Ctx);
transcript.domain_separate(b"encryption_key");
transcript.append_message(b"shared_key", C::G::identity().to_bytes());
let mut key = Cc20Key::default();
key.copy_from_slice(&transcript.challenge(b"key")[..32]);
let mut iv = Cc20Iv::default();
iv.copy_from_slice(b"DKG IV v0.2\0");
ChaCha20::new(&key, &iv).apply_keystream(&mut ciphertext); // => SecretShare repr
let share_mal_from_j = C::F::from_repr(repr).unwrap();
// Repeating over every sender's EncryptedMessage to i_mal and summing
// recovers i_mal's full ThresholdKeys secret_share.
```

```rust
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}
```
