### Title
SignableTransaction::new fails to reject duplicated inputs, inflating the input balance and producing a signature over an unspendable transaction - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` accepts a `Vec<ReceivedOutput>` without checking for duplicate outpoints. A duplicated `ReceivedOutput` is counted twice in `input_sat`, twice in `tx.input`, and twice in `prevouts`, inflating the apparent balance the transaction has available — the same class of bug as `OlympusTreasury.addAsset` failing to deduplicate `locations` and thereby inflating the reported asset balance.

### Finding Description
`SignableTransaction::new` sums the value of every entry in `inputs` into `input_sat` (`send.rs:175`), then builds one `TxIn` per entry (`send.rs:177-185`) and stores one `prevout` per entry (`send.rs:253`). There is no check that two entries share the same `outpoint`. The balance check `input_sat < (payment_sat + needed_fee)` (`send.rs:215`) and the change computation `input_sat - payment_sat - fee_with_change` (`send.rs:228`) therefore treat a duplicated input as fresh funds.

The inputs are untrusted: `ReceivedOutput::read` (`networks/bitcoin/src/wallet/mod.rs:122`) deserializes `offset`, `TxOut`, and `OutPoint` from arbitrary bytes, and nothing prevents the same outpoint being supplied twice.

Because every entry becomes a real `TxIn`, the resulting transaction contains the same outpoint twice — which is invalid under Bitcoin consensus (a transaction may not spend the same outpoint twice) — while the FROST signing machines still sign a Taproot sighash committing to the duplicated prevouts (`Prevouts::All`). The change output is likewise inflated by the duplicated value, so even ignoring the duplicate-input consensus rule, the tx claims more funds than it actually controls.

### Impact Explanation
A `SignableTransaction` built over duplicated inputs passes the `NotEnoughFunds` check and emits an inflated change output. The threshold multisig then signs a transaction that cannot be relayed or confirmed — meaning a plan/batch can be executed (and its nonce consumed) while the payments never occur, and the declared change amount is fabricated relative to actual inputs. This mirrors the original finding: duplicated list entries produce an inflated balance that downstream logic treats as real.

### Likelihood Explanation
Exploitation requires feeding a duplicated `ReceivedOutput` list into `SignableTransaction::new`. Since `ReceivedOutput` is deserializable from untrusted bytes and the function performs no outpoint dedup, this is reachable wherever input lists are assembled from data not fully controlled by the local party. It requires no key material or collusion.

### Recommendation
In `SignableTransaction::new`, reject duplicated outpoints (e.g., insert each `input.outpoint` into a `HashSet` and error on collision) before computing `input_sat` and building `tx_ins`/`prevouts`. Note the Scanner layer already assumes output IDs are unique (`processor/src/multisigs/scanner.rs` panics on re-scan), but that invariant is not enforced at the point where inputs are committed into a transaction.

### Proof of Concept
Conceptual:

```rust
// networks/bitcoin/src/wallet/send.rs
let output: ReceivedOutput = ...; // one real output worth V sats
// Duplicate it
let inputs = vec![output.clone(), output.clone()];
let payments = [(some_scriptbuf, V + DUST)]; // exceeds real funds V
// Succeeds because input_sat = 2V, though only V exists
let tx = SignableTransaction::new(inputs, &payments, Some(change), None, fee).unwrap();
// tx.fee() = 2V - outputs; tx.input contains the same outpoint twice -> consensus-invalid
```

`input_sat` is inflated at `send.rs:175`, the check at `send.rs:215` passes incorrectly, and `tx_ins`/`prevouts` (`send.rs:177-185`, `send.rs:253`) embed the duplicate.
