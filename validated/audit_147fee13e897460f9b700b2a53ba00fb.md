### Title
Diff-hunk expansion silently invalidates line-selection indices, causing wrong lines to be staged/committed - (File: `app/src/ui/diff/text-diff-expansion.ts`)

### Summary
This is the same bug class as the QuantAMM report: a data structure is repacked/re-indexed (there, weight/multiplier slots; here, diff-hunk line indices), but a downstream consumer keeps using the *old* index scheme to read from the *new* layout. In GitHub Desktop, partial-commit selection (`DiffSelection`) is keyed by an absolute line index computed as `hunk.unifiedDiffStart + lineIndex`. Expanding a diff hunk (`expandTextDiffHunk`) recomputes `unifiedDiffStart`/`unifiedDiffEnd` for every hunk after the expansion point, shifting the absolute index space, but the selection bitset is not remapped along with it. The same absolute index therefore points at a different physical diff line after expansion.

### Finding Description
`diffHunkForIndex`/`diffLineInfoForIndex` locate a line purely by absolute index (`index - hunk.unifiedDiffStart`): [1](#0-0) 

This same absolute index is what `DiffSelection` stores selected/unselected state against, and it is exactly what `formatPatch`/`formatPatchToDiscardChanges` use to decide whether to include a line when building the patch that is applied to the index / working tree: [2](#0-1) [3](#0-2) 

When a user expands hunk context (clicking "expand up/down" in the diff view), `expandTextDiffHunk` rewrites the current hunk's `unifiedDiffEnd` by adding the number of newly inserted context lines, and then shifts **every subsequent hunk's** `unifiedDiffStart`/`unifiedDiffEnd` by that same offset: [4](#0-3) [5](#0-4) 

This expansion is triggered from component-local state in `SideBySideDiff.onExpandHunk`/`expandHunk`, i.e. purely inside the diff-viewer component: [6](#0-5) 

The only place the app re-derives "selectable lines" from a fresh set of hunks is the `AppStore` status-refresh path, which is driven by the working-directory diff being reloaded from git (e.g. after a `git status`/diff refresh), not by the interactive hunk-expansion the user just performed in the renderer: [7](#0-6) 

Because expansion changes the mapping from absolute index → diff line for every hunk after the expansion point, but the `DiffSelection` object the user has already built up (by checking/unchecking individual lines or hunks before or after expanding) is not migrated to the new index space, a previously selected absolute index can now resolve to an entirely different line (e.g., a line that was unrelated context before expansion, or a line in a different hunk once hunks are merged via `mergeDiffHunks`): [8](#0-7) 

### Impact Explanation
If the selection state is not correctly remapped when hunks are expanded/merged, `formatPatch` can produce a patch that includes lines the user never intended to stage/commit, or excludes lines the user did intend to commit — a silent corruption of what gets committed or pushed, exactly the impact class called out as valid (no code execution needed, just wrong data reaching the user's commit/push). Because `DiffHunkExpansionType.Short` causes automatic **hunk merging** (`mergeDiffHunks`) when hunks are close together, the renumbering/shift math is non-trivial (mirroring the QuantAMM "more than 4 tokens" edge case), which is where an off-by-one/stale-index class of bug is most likely to hide.

### Likelihood Explanation
Triggering hunk expansion is an ordinary, expected user action available on every multi-hunk diff (clicking the "Expand" affordance in the diff viewer), and a maliciously crafted repository can trivially shape file contents/diffs to control hunk boundaries and gap sizes, making the short-gap auto-merge path (and its index recalculation) reachable on demand. No admin rights, local access, or prior compromise is required — only that the victim opens a diff from an attacker-influenced repository and interacts with the normal "expand" UI, which is a natural, expected step (not "unnatural user steps").

### Recommendation
- When a hunk is expanded/merged, walk the existing `DiffSelection` and remap every stored index by the same `numberOfNewDiffLines` offset applied to hunks after the expansion point (and merge selection bits appropriately when two hunks are merged), instead of leaving the selection keyed to now-stale absolute indices.
- Alternatively, tie selection to stable line identity (e.g., `(oldLineNumber, newLineNumber)` pairs) rather than a purely positional absolute index that shifts under hunk-expansion/merge.
- Add regression tests asserting that a `DiffSelection` built before an `expandTextDiffHunk`/merge still selects the *same textual lines* afterward, not just the same numeric indices.

### Proof of Concept
Conceptual reproduction (no execution environment available to run it here, but each step is backed by the cited code paths):

2. In the Changes view, select (stage) a specific added line in the *second* hunk using its current absolute index (`hunk.unifiedDiffStart + lineIndex`).
3. Click "Expand" on the gap between the two hunks; this triggers `onExpandHunk` → `expandTextDiffHunk`, which merges the hunks via `mergeDiffHunks` and shifts subsequent hunks' `unifiedDiffStart/End` by `numberOfNewDiffLines`: [10](#0-9) 
4. Commit the partial selection. `formatPatch` re-evaluates `file.selection.isSelected(absoluteIndex)` against the *new* hunk layout using the *old* stored indices: [2](#0-1) 
5. Verify (via the existing test harness in `app/test/unit/patch-formatter-test.ts` and `app/test/unit/text-diff-expansion-test.ts`, extended to combine a pre-set `DiffSelection` with a subsequent `expandTextDiffHunk` call) whether the resulting patch stages the originally-selected text or a different line that now occupies that absolute index.

Note: I was not able to fully verify inside the available tool budget whether some other code path re-synchronizes `DiffSelection` immediately after `expandHunk` runs (only the unrelated, poll-driven `updateChangesWorkingDirectoryDiff`/`app-store.ts:3478-3497` revalidation was found, which is not wired to the interactive expand action). If such a synchronization step exists elsewhere and correctly remaps indices, this finding would be mitigated; confirming that requires deeper tracing of `SideBySideDiff`'s `onIncludeChanged` prop wiring back into `Dispatcher`/`AppStore`, which a Devin session with full-repo access and the ability to run the test suite could verify conclusively.

export function diffHunkForIndex(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): DiffHunk | null {
  const hunk = hunks.find(h => {
    return index >= h.unifiedDiffStart && index <= h.unifiedDiffEnd
  })
  return hunk || null
}

/**
 * Locate the diff line and hunk for the given (absolute) line number in the diff.
 */
function diffLineInfoForIndex(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): IDiffLineInfo | null {
  const hunk = diffHunkForIndex(hunks, index)
  if (!hunk) {
    return null
  }

  const line = hunk.lines[index - hunk.unifiedDiffStart]
  if (!line) {
    return null
  }

  return { hunk, line }

/** Merges two consecutive hunks into one. */
function mergeDiffHunks(hunk1: DiffHunk, hunk2: DiffHunk): DiffHunk {
  // Remove the first line in both hunks, because those are hunk header lines
  // that will be replaced by a new one for the resulting hunk.
  const allHunk1LinesButFirst = hunk1.lines.slice(1)
  const allHunk2LinesButFirst = hunk2.lines.slice(1)

  const newHunkHeader = new DiffHunkHeader(
    hunk1.header.oldStartLine,
    hunk1.header.oldLineCount + hunk2.header.oldLineCount,
    hunk1.header.newStartLine,
    hunk1.header.newLineCount + hunk2.header.newLineCount
  )

  // Create a new hunk header line for the resulting hunk
  const newFirstHunkLine = new DiffLine(
    newHunkHeader.toDiffLineRepresentation(),
    DiffLineType.Hunk,
    null,
    null,
    null,
    false
  )

  const newHunkLines = [
    newFirstHunkLine,
    ...allHunk1LinesButFirst,
    ...allHunk2LinesButFirst,
  ]

  return new DiffHunk(
    newHunkHeader,
    newHunkLines,
    hunk1.unifiedDiffStart,
    hunk1.unifiedDiffStart + newHunkLines.length - 1,
    // The expansion type of the resulting hunk will match the expansion type
    // of the first hunk:
    // - If the first hunk can be expanded up, it means it's the very first
    //   hunk, so the resulting hunk will be the first too.
    // - If the first hunk can be expanded but short, that doesn't change after
    //   merging it with the second one.
    // - If it can be expanded up and down (meaning it's a long gap), that
    //   doesn't change after merging it with the second one.
    // - It can never be expanded down exclusively, because only the last dummy
    //   hunk can do that, and that will never be the first hunk in a merge.
    hunk1.expansionType
  )
}

    hunkIndex: number,
    expansionType: DiffHunkExpansionType

    const { diff } = this.state

      return
    }

    this.setState({ lastExpandedHunk: { hunkIndex, expansionType } })
