### Title
Unvalidated PR `head.repo.clone_url` from GitHub API is used to add a git remote and fetch, allowing an attacker-controlled fork to redirect Desktop's "Open PR from Desktop" flow to an arbitrary git host - (File: `app/src/lib/stores/app-store.ts`)

### Summary
This is the closest structural analog to the Solana `deposit_for_burn` bug: in that report, `authorize()` validates one field (`mint_recipient`) but omits validating a second, security-relevant field (`destination_domain`), letting an attacker redirect funds to an unintended destination. In GitHub Desktop, `_findPullRequestBranch`/`_checkoutPullRequest` validate the *owner* used to name the fork remote (`headRepoOwner` → `forkPullRequestRemoteName`) but never validate that the *host/domain* embedded in `headCloneUrl` matches the trusted GitHub endpoint (dotcom or the specific GHES instance) associated with the base repository. The clone URL is taken directly from GitHub API data (`pull.head.repo.clone_url`) or from a deep-link-triggered PR lookup, and is passed straight into `addRemote` and then fetched.

### Finding Description
The relevant code path: [1](#0-0) 

`openPullRequestFromUrl` receives a `url` (attacker-influenced through the `x-github-client://openrepo/...&pr=N` deep link, validated only for path/branch/pr shape in `parseAppURL`) and calls `this.appStore.fetchPullRequest(url, pr)`: [2](#0-1) 

This resolves an `endpoint`/`account` from the URL's hostname and fetches the PR data. It then flows into `_checkoutPullRequest` → `_findPullRequestBranch`: [3](#0-2) 

Here, `headCloneUrl` (`pull.head.repo.clone_url`, sourced from the GitHub API's PR object) is used to search existing remotes via `urlMatchesRemote`, and if no match is found, a **new remote is created and populated with this URL unchanged** — `addRemote(repository, forkRemoteName, headCloneUrl)`. The remote name is derived only from `headRepoOwner` (analogous to the "mint_recipient" check in the report), but there is **no check that the hostname of `headCloneUrl` matches the hostname/endpoint of the base repository's account** (analogous to the missing "destination_domain" check).

Immediately after, the code fetches from that remote: [4](#0-3) 

`_fetchRemote` will run `git fetch` against whatever host is embedded in `headCloneUrl`, and the resulting branch is checked out into the user's working repository.

### Impact Explanation
If an attacker can influence the `head.repo.clone_url` field returned for a PR (e.g., by controlling a malicious GHES-style API response, or by getting Desktop to resolve a PR whose `head.repo` metadata points to a different host than expected — this is plausible since GitHub's API generally trusts `clone_url` as stored data and it isn't recomputed/cross-checked against the account's own endpoint), Desktop will silently add a new git remote pointing at an attacker-controlled host and fetch from it. This can result in:
- Fetching and checking out attacker-controlled commit content into the user's working directory, with no visual indication that the fetch source is not GitHub (i.e. checked-out code could differ from what the user believes they are reviewing — a "silent corruption of what the user commits/pushes/reviews" style outcome).
- Any subsequent trust decisions (e.g., diffing PR content, cherry-pick, "Open in Desktop") acting on data fetched from an unverified host.

### Likelihood Explanation
The `headCloneUrl` is largely governed by GitHub's actual API responses in the common case, which limits attacker control under normal GitHub.com usage. However, the check is entirely absent in code — there is no domain allow-list comparison anywhere in `_findPullRequestBranch`, `_checkoutPullRequest`, `startCherryPickWithPullRequest`, or `checkoutPullRequest` in `dispatcher.ts`. This makes the likelihood **dependent on scenarios where API responses can be spoofed or where GHES/proxy responses are attacker-influenced** (e.g., a compromised or malicious GHES-compatible endpoint, or a MITM'd non-TLS-pinned connection) — I could not verify from the indexed code whether there is a separate network-layer safeguard (e.g., certificate pinning or response signing) that would fully mitigate this, so likelihood should be treated as **moderate, contingent on an untrusted/spoofable API response**, similar in spirit but not identical in exploitability to the original finding.

### Recommendation
In `_findPullRequestBranch` (and any other place that consumes `head.repo.clone_url`/`base.repo.clone_url` from the GitHub API), validate that the hostname of the URL matches the expected GitHub endpoint (dotcom or the specific enterprise account endpoint) for the associated `Account`/`GitHubRepository` before calling `addRemote` or fetching, using the existing `parseRemote`/`urlMatchesRemote`-style hostname comparison already used elsewhere (e.g., as in `findAccountForRemoteURL`). Reject or surface an error for PR head/base repo URLs whose host doesn't match the expected endpoint domain, rather than silently trusting API-supplied clone URLs.

### Proof of Concept
Not independently reproducible from static code alone: it requires controlling (or spoofing) a GitHub/GHES-compatible API response for a pull request such that `head.repo.clone_url` points to a different host than the account's configured endpoint, then triggering the "Open Pull Request in Desktop" flow (via `x-github-client://openrepo/...&pr=N` or the in-app "Checkout this PR" action) against that PR — at which point `_findPullRequestBranch` will `addRemote`/fetch from the attacker-controlled host without a hostname check. I was unable to execute this end-to-end in the indexed codebase, so this should be validated dynamically with a Devin session or local test harness before being treated as confirmed-exploitable.

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }

    const endpoint = getEndpointForRepository(repoUrl)
    const account = getAccountForEndpoint(this.accounts, endpoint)

    if (account) {
      const api = API.fromAccount(account)
      const remoteUrl = parseRemote(repoUrl)
      if (remoteUrl && remoteUrl.owner && remoteUrl.name) {
        return await api.fetchPullRequest(remoteUrl.owner, remoteUrl.name, pr)
      }
    }
    return null
  }
