### Title
Missing zero-value validation for KIP-71 `GasTarget` governance parameter causes division-by-zero panic in base fee calculation - (File: `params/kip71_config.go`, `kaiax/gov/param.go`)

### Summary
`KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without any zero-check, while the sibling parameter `BaseFeeDenominator` is explicitly protected against a zero value. Because the governance parameter definition for `Kip71GasTarget` uses `noopFormatChecker` instead of a `v != 0` check (unlike `Kip71BaseFeeDenominator`), a governance/GovParam update that sets `GasTarget` to `0` will be accepted, and the very next base-fee computation will panic with a division-by-zero error.

### Finding Description
`NextMagmaBlockBaseFee` computes the next block's base fee using the current governance parameters: [1](#0-0) 

Here `BaseFeeDenominator` is explicitly guarded: if it is `0`, the code falls back to a safe default (`64`) "to avoid panic". No equivalent guard exists for `GasTarget`: [2](#0-1) 

When gas used differs from `gasTarget` (which is guaranteed whenever `gasTarget == 0` and any gas is used), the code performs: [3](#0-2) 

and, symmetrically, in the "used less than target" branch: [4](#0-3) 

Both branches execute `x.Div(x, new(big.Int).SetUint64(gasTarget))`. In Go, `big.Int.Div` panics with `"division by zero"` when the divisor is zero.

The root cause is that the governance parameter definition for `Kip71GasTarget` does not enforce a non-zero value, unlike `Kip71BaseFeeDenominator` which explicitly requires `v != 0`: [5](#0-4) [6](#0-5) 

`Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, which accepts any value, including `0`. This missing validation exactly mirrors the reported bug class: a config/update path lacks the safeguard needed to prevent a parameter that is later used as a divisor from becoming zero, leading to a division-by-zero panic in a downstream calculation (`premiumDiscountFactor` in the original report vs. `NextMagmaBlockBaseFee`'s baseFeeDelta calculation here).

`GasTarget=0` can be set through either governance path:
- On-chain **contract governance** via `GovParam.setParam`/`setParamIn`, which is `Ownable`-restricted to the contract owner (a privileged but on-chain, transaction-driven path) — [7](#0-6) , exercised end-to-end in [8](#0-7) .
- **Header governance** vote pushed by the governing node, consumed by `kaiax/gov` and turned into a `ParamSet` via `Set`, which performs no bounds checking beyond type assertion for `GasTarget`: [9](#0-8) .

Once the parameter becomes effective, `NextMagmaBlockBaseFee` is invoked by consensus header validation (`BlockValidator`, which holds a reference to the governance module `mGov`) as well as by the miner/worker and gas price oracle when building/estimating the base fee for the next block: [10](#0-9) 

Any node computing the base fee for the block following the activation of `GasTarget=0` will panic in `math/big`.

### Impact Explanation
A panic inside `NextMagmaBlockBaseFee`, which is on the block header validation and block-building path, will crash any node process (validator or full node) that reaches this code when processing/mining the block where the malicious `GasTarget=0` value takes effect. Because all correctly-configured nodes evaluate this same deterministic function against the same governance state, the panic occurs network-wide simultaneously, halting block production and header validation across the network — a chain-halting denial of service, not merely resource exhaustion on a single peer. This satisfies the "state divergence / acceptance of invalid transaction or block" bar since it directly breaks consensus-critical base-fee computation for every node, rather than being a peer-local or p2p-message-triggered issue.

### Likelihood Explanation
Reaching this requires a party with governance-update capability (the `GovParam` contract owner, or a governing node casting a header vote) to set `Kip71GasTarget` to `0`. This is a plausible misconfiguration or malicious-insider action since, unlike `BaseFeeDenominator`, no protocol-level `FormatChecker` currently rejects the value `0` for `GasTarget`, so nothing in the validation pipeline (`kaiax/gov/param.go`) stops it from becoming an active, effective parameter before the vulnerable arithmetic executes.

### Recommendation
Add a `v != 0` format check (matching `Kip71BaseFeeDenominator`'s checker) to the `Kip71GasTarget` parameter definition in `kaiax/gov/param.go`, rejecting zero at the governance parameter validation stage. As defense in depth, also add an explicit zero-guard for `gasTarget` inside `NextMagmaBlockBaseFee` in `params/kip71_config.go`, mirroring the existing `BaseFeeDenominator` fallback, so that even a value that slips past parameter validation cannot cause a runtime panic in consensus-critical code.

### Proof of Concept
1. Deploy/enable the `GovParam` contract and set it as the active governance contract (as in `tests/gov_contract_test.go`'s `TestGovernance_GovModule` setup).
2. As the contract owner, call `setParam("kip71.gastarget", true, <bytes for 0>, activationBlock)` (per `contracts/bindings/gov/GovParam.go`'s `SetParam`), or cast an equivalent header-governance vote (`gov.Kip71GasTarget: uint64(0)`).
3. Once the parameter activates, produce a block where `parentHeaderGasUsed != 0`.
4. `NextMagmaBlockBaseFee` (`params/kip71_config.go`) executes `x.Div(x, new(big.Int).SetUint64(0))` in the ">" or "<" branch, causing a `runtime panic: division by zero` in every node's `BlockValidator`/miner code path that evaluates the base fee for that block, matching the same root-cause pattern (unchecked divisor sourced from an unvalidated governance-updatable parameter) as the original `UsdTokenSwapConfig` report.
