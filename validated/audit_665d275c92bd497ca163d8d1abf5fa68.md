## Analysis

The external report's bug class — a party front-running a reward/fee event to capture yield that should accrue to existing stakers — has a valid **unprivileged-wallet** analog in `WombatStaking.sol`'s reward-harvesting mechanism, independent of any admin/clerk action.

### Root Cause

`WombatStaking._toMasterWomAndSendReward` is triggered on every `deposit`, `depositLP`, `withdraw`, and the fully permissionless `harvest` function <cite repo="bsaldua/contracts--015" path="wombat/WombatStaking.sol" start="329="335" end="335" />. This pulls all WOM (and bonus token) rewards accrued in the external MasterWombat contract since the last interaction and immediately pushes them into the `BaseRewardPool` via `queueNewRewards` -> `_provisionReward` [1](#0-0) .

Critically, `_provisionReward` distributes the entire harvested amount **instantly** against the current `totalStaked()` snapshot — there is no linear vesting/rewardRate-over-duration mechanism like Synthetix-style pools:

```
rewardInfo.rewardPerTokenStored =
    rewardInfo.rewardPerTokenStored +
    (_amountReward * 10**stakingDecimals()) /
    this.totalStaked();
``` [2](#0-1) 

`harvest()` itself is callable by **any address**, gated only by `_onlyActivePool`, not by any manager/pool-helper restriction [3](#0-2) .

### The unprivileged analog to "frontrunning with fee increase"

Instead of a clerk raising fees before `slurp`, an ordinary (even flash-loan-funded) wallet can:
1. Observe (via mempool or on-chain state) that a large amount of WOM has accrued in MasterWombat since the last harvest for a given pool (no one has deposited/withdrawn/harvested in a while).
2. Front-run the next harvest-triggering transaction (or simply call it themselves) by first calling `WombatPoolHelper.deposit()`, which stakes a large LP position into `MasterMagpie` [4](#0-3) .
3. Immediately call the permissionless `harvest()`, which distributes the backlog of WOM rewards pro-rata over `totalStaked()` **including the attacker's freshly deposited stake**, even though the attacker contributed none of the time/liquidity that generated those rewards.
4. Immediately `withdraw()` to realize the stolen share of `rewardPerTokenStored`, diluting genuine long-term LPs.

This is the same root cause as the report — reward/fee accounting that can be manipulated by timing a transaction around a distribution event — but achieved entirely by an ordinary wallet exploiting `BaseRewardPool`'s instant, un-vested reward math and `WombatStaking`'s permissionless `harvest`, not by a privileged clerk/governance actor.

### Title
Just-in-time deposit before permissionless `harvest()` allows unprivileged wallets to steal accrued yield from existing stakers - (File: `wombat/WombatStaking.sol`, `rewards/BaseRewardPool.sol`)

### Summary
`WombatStaking.harvest` is callable by any address and forces an instant, un-vested distribution of all WOM/bonus rewards accrued since the last interaction, proportional to `BaseRewardPool.totalStaked()` at the moment of distribution. An attacker can deposit a large stake immediately before triggering (or observing) a harvest, capture a share of rewards that accrued before their deposit, and withdraw immediately after, diluting legitimate stakers' yield.

### Finding Description
`_provisionReward` in `BaseRewardPool.sol` updates `rewardPerTokenStored` using the reward amount divided by the current `totalStaked()`, with no time-weighted release [2](#0-1) . Because `harvest()` is public/permissionless [3](#0-2) , and deposits into `MasterMagpie` occur before the next reward snapshot is taken, an attacker's newly added stake participates fully in any reward batch distributed after their deposit, regardless of how briefly they were staked.

### Impact Explanation
This is a direct theft of unclaimed yield from genuine long-term stakers: it redistributes rewards that should have accrued to holders who supplied liquidity for the full accrual period to a short-term, just-in-time depositor.

### Likelihood Explanation
Any wallet (potentially flash-loan funded, since the underlying deposit tokens are typically liquid stablecoins in Wombat pools) can execute this without any special privilege, only requiring visibility into accrued-but-unharvested reward backlogs, which are readable on-chain.

### Recommendation
Introduce a time-weighted reward release (e.g., stream newly harvested rewards over a fixed duration rather than crediting them instantly to `rewardPerTokenStored`), and/or require a minimum staking duration/cooldown before a deposit is eligible to share in a reward distribution.

### Proof of Concept
1. Pool `P` has not been interacted with for a long period; large pending WOM accrues in MasterWombat for `P`.
2. Attacker calls `WombatPoolHelper.deposit()` for pool `P` with a large amount (optionally flash-loaned), staking receipt tokens into `MasterMagpie` [4](#0-3) .
3. Attacker (or anyone) calls `WombatStaking.harvest(P)`, which distributes the accrued WOM backlog pro-rata to `totalStaked()`, now inflated by the attacker's deposit [3](#0-2) .
4. Attacker calls `WombatPoolHelper.withdraw()` to unstake and realize the earned share of rewards, then repays the flash loan.

    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
        emit RewardAdded(_amountReward, _rewardToken);
    }
