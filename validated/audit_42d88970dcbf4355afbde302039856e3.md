### Title
`ThresholdKeys::new` / `ThresholdKeys::read` never checks the secret share matches its verification share, producing keys that permanently fail every signing attempt — ([File: crypto/dkg/src/lib.rs])

### Summary
The reported bug class is a value that is validated on every use (`computeMultiplier` reverting when `feeScaled > SCALAR`) but is never validated at construction, so a bad initial value permanently bricks the protocol. The Serai analog is the consistency invariant between `secret_share` and `verification_shares[i]` in `ThresholdKeys`. Every signing attempt implicitly depends on `G * secret_share == verification_shares[i]` (the interpolated share must verify, and the aggregate must verify against `group_key`), yet `ThresholdKeys::new` — which is also the sole validation gate for `ThresholdKeys::read`, an explicitly in-scope sink for untrusted bytes — never checks it. A deserialized `ThresholdKeys` with a mismatched share is accepted, then fails on every single signing attempt.

### Finding Description
`ThresholdKeys::new` validates only:

- `verification_shares.len() == params.n()` [1](#0-0) 
- each participant index `<= n` [2](#0-1) 
- `t == n` when `Interpolation::Constant` is used [3](#0-2) 

It then computes `group_key` from `verification_shares[1..=t]` and stores the supplied `secret_share` unconditionally [4](#0-3) . There is no check that `C::generator() * *secret_share == verification_shares[&params.i()]`.

`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation variant, `secret_share`, and `n` verification shares entirely from attacker-controlled bytes, then delegates all validation to `ThresholdKeys::new` [5](#0-4) . So a malformed byte stream yields a fully "valid" `ThresholdKeys` whose share is inconsistent with the verification map.

On use, `view()` interpolates `secret_share` into a signing-set secret share [6](#0-5)  and `AlgorithmSignMachine::sign` returns a `SignatureShare` built from it [7](#0-6) . In `complete()`, the aggregate fails `algorithm.verify`, and the per-share blame pass flags this participant via `verify_share` [8](#0-7) . Every attempt fails identically — the check the constructor omitted is instead enforced, in effect, at every use, permanently.

### Impact Explanation
Untrusted bytes passed to `ThresholdKeys::read` (explicitly in scope) produce keys that can never sign: `complete()` either returns `FrostError::InvalidShare(own_i)` or `FrostError::InternalError` on every attempt [9](#0-8) . Worse, `group_key` is computed solely from `verification_shares`, so a crafted serialization can present a `group_key` interpolating to a secret the attacker knows, while the holder's `secret_share` is inconsistent — funds sent to that key are spendable by the attacker alone, and the holder only discovers the bricking when signing is attempted. This mirrors the reported bug exactly: missing validation at the one-time initialization point converts into a failure on every subsequent operation.

### Likelihood Explanation
Reachable by any unprivileged party able to supply `ThresholdKeys` bytes to `read` (e.g., a processor/coordinator loading key material received over a channel, or an attacker-influenced serialization). No collusion or malicious validator required; the deserializer itself is the attack surface. Medium likelihood and Medium severity — permanent unspendability of the key set rather than direct secret leakage.

### Recommendation
In `ThresholdKeys::new` (`crypto/dkg/src/lib.rs:354`), after the existing checks, verify share consistency:

```rust
if C::generator() * secret_share.deref() != verification_shares[&params.i()] {
  Err(DkgError::InvalidShare)?  // new variant
}
```

Since `read` funnels through `new`, this simultaneously fixes the deserialization path, matching the report's recommendation of moving the check into the constructor.
