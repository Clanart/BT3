### Title
`VerifyBlame` passes `accuser`/`accused` in the wrong argument order to `BlameMachine::blame`, inverting fault attribution and blaming honest participants - (File: processor/src/key_gen.rs)

### Summary
The PedPoP blame API `blame_internal(sender, recipient, msg, proof)` attributes fault based on who `sender` and `recipient` are. In `CoordinatorMessage::VerifyBlame`, the handler invokes `.blame(accuser, accused, ...)` — passing the *accuser* as `sender` and the *accused* as `recipient`, even though the supplied `share` is defined as "the encrypted secret share from the accused sender to the accusing recipient." The roles are swapped, so blame resolution produces inverted or attacker-controlled results.

### Finding Description
`BlameMachine::blame` / `AdditionalBlameMachine::blame` delegate to `blame_internal`, which decides fault strictly from the `sender`/`recipient` roles: an invalid PoP returns `sender`, an invalid/absent decryption proof returns `recipient`, a valid share returns `recipient` [1](#0-0) .

The `VerifyBlame` handler reads the share as the message *from* `accused` *to* `accuser`, then calls `.blame(accuser, accused, substrate_share, substrate_blame)` and `.blame(accuser, accused, network_share, network_blame)` [2](#0-1) . Inside `blame_internal` the PoP is verified against `from = accuser` [3](#0-2) , but a legitimately generated `EncryptedMessage` binds its PoP to the actual sender (`from` = the encrypting participant, `self.i`) [4](#0-3) .

Two consequences:

1. **Honest accuser slashed**: if the `accused` genuinely sent a share with an invalid PoP, verification in `blame_internal` either (a) fails because `from` is checked as `accuser` instead of `accused`, returning `sender` = `accuser`, or (b) — for a message that was legitimately *encrypted* but carries an invalid share — the DLEq proof is checked against `enc_keys[&decryptor]` = `enc_keys[accused]` [5](#0-4) , which is the wrong party's encryption key, misrouting the blame decision.
2. **Malicious accuser frames an honest party**: if the accuser fabricates an accusation against a valid share, the "share was canonical and valid" branch returns `recipient` = `accused`, so the honest accused is blamed [6](#0-5) , and the handler emits `ProcessorMessage::Blame { participant: accused }` [7](#0-6) .

This is the direct analog of the ImageMagick error-manager mishandling: the error/blame-management path operates on misidentified objects, so the wrong party's state is treated as the faulty one.

### Impact Explanation
Blame resolution is the slashing/fault-attribution mechanism for the DKG. Inverting it means (a) a participant who sends malformed shares can cause the *victim* who reports them to be marked faulty, and (b) a malicious accuser can get an honest peer blamed by submitting an accusation against a valid share. Either path lets an unprivileged DKG participant cause an honest party to be fatally faulted/slashed while the actual misbehaving party escapes attribution — an incorrect-verifier/incorrect-attribution outcome reachable purely with messages the attacker causes to be processed.

### Likelihood Explanation
Any participant in a key-generation session can trigger `CoordinatorMessage::Shares` with a malformed share (forcing a victim into `PedPoPError::InvalidShare` and an `InvalidShare` accusation), or submit `VerifyBlame` accusations directly. No special privileges, collusion, or malformed cryptographic primitives are required — only the ability to send protocol messages.

### Recommendation
Swap the arguments so the call is `.blame(accused, accuser, share, blame)` — i.e., `sender` = `accused`, `recipient` = `accuser` — matching the documented semantics that `msg` is "the encrypted secret share from the accused sender to the accusing recipient" [8](#0-7) . Add a regression test where an honest accuser reports a genuinely invalid PoP and where a malicious accuser reports a valid share, asserting the `accused`/`accuser` outcomes respectively.

### Proof of Concept
1. Run a PedPoP DKG session (as in `crypto/dkg/pedpop/src/tests.rs`). Have participant 2 send participant 1 an encrypted share whose PoP is invalidated via `invalidate_pop` (analogous to `invalidate_msg`).
2. Participant 1 calls `calculate_share`, obtains `PedPoPError::InvalidShare { participant: 2, blame: Some(..) }`, and submits a `CoordinatorMessage::VerifyBlame { accuser: 1, accused: 2, share, blame }`.
3. The handler calls `AdditionalBlameMachine::blame(accuser=1, accused=2, share, proof)`. `blame_internal` verifies the PoP with `from = 1` (line 374–379 of `encryption.rs`), which fails for a message legitimately sent by 2 → returns `sender` = `accuser` = 1.
4. Since `substrate_blame != accused`, the handler returns `ProcessorMessage::Blame { participant: accuser }` — the honest reporter is marked faulty.
5. Symmetrically, an accuser blaming a fully valid share reaches the `recipient` return → `accused` is blamed, letting a malicious accuser frame an honest peer.
