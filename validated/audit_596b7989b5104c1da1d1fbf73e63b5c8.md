### Title
`DLEqProof::verify` / `MultiDLEqProof::verify` accept proofs over empty or vacuous generator sets, enabling a forged proof (crypto/dleq/src/lib.rs)

### Summary
Like the Ghostfolio bug, where bypassing a symbol-validation step let attacker input reach a privileged SQL sink, `DLEqProof::verify` performs only a length-equality check on `generators`/`points` and never requires the statement to be non-empty or bound to any prover-supplied data. When called with empty (or attacker-shaped) statement lists, the transcript binds nothing and the only remaining check — `self.c == challenge(transcript)` — is satisfiable by anyone who can compute the transcript hash, since `c` is attacker-controlled via `DLEqProof::read`.

### Finding Description
In `crypto/dleq/src/lib.rs`, `DLEqProof::verify` iterates `generators.iter().zip(points)` and computes the Fiat-Shamir challenge from whatever was transcripted [1](#0-0) . With `generators = []` and `points = []`, the loop body never runs, so the only transcripted material is the `b"dleq"` domain separator and whatever the caller put in the transcript before. The attacker then crafts `DLEqProof { c: challenge_of_that_empty_transcript, s: arbitrary }` via `DLEqProof::read`, which accepts any canonical scalars without semantic validation [2](#0-1) . Verification returns `Ok(())` for a proof that binds no generators and no points.

`MultiDLEqProof::verify` has the same shape: `points.len() != generators.len()` and `self.s.len() != generators.len()` are checked, but a zero-length `generators` with `s = []` passes, and the challenge is computed over only `discrete_logarithm` labels that were never emitted [3](#0-2) . Additionally, inner `points[i].len() != generators[i].len()` is checked inside the loop but `s[i]` indexing relies on the outer length check only — a proof can mix empty per-key statements with real ones, and each empty sub-statement contributes nothing to the challenge while still being reported as verified.

### Impact Explanation
A `DLEqProof`/`MultiDLEqProof` is used to establish that a set of points shares one discrete logarithm (e.g., `EncryptionKeyProof` in PedPoP proves `key = enc_key * msg.key` where `enc_key * G = enc_keys[decryptor]` [4](#0-3) ). In any protocol where the statement being proven is itself attacker-influenced (e.g., a prover sends proof plus the list of points to be verified, and the verifier treats `Ok(())` as "these N keys are bound"), an attacker can supply an empty or truncated statement that "verifies" while binding nothing — a forged proof accepted by an unprivileged remote party. This is exactly the injected-command shape of the reference bug: a missing validation gate lets attacker bytes pass through to a security-relevant accept path.

### Likelihood Explanation
Exploitation requires a caller that derives `generators`/`points` (or their count) from prover-supplied data. In-tree callers pass fixed generators, so the issue is latent in the public API rather than active in PedPoP today. However, the API is exported specifically for untrusted input (`DLEqProof::read` is listed as an untrusted-bytes entry point), the failure is silent (`Ok(())` on a vacuous statement), and the test suite explicitly entertains `i = 0` as valid [5](#0-4) . Medium: real forged-proof acceptance, but impact depends on integrator usage of attacker-controlled statement lists.

### Recommendation
Reject `generators.is_empty()` (and `generators.is_empty()` / empty inner lists for `MultiDLEqProof`) in `verify` — and symmetrically in `prove` — so the Fiat-Shamir transcript is guaranteed to bind at least one `(generator, nonce, point)` triple. Treat zero-statement proofs as `InvalidProof` rather than vacuously true.

    if generators.len() != points.len() {

      Err(DLEqError::InvalidProof)?;
    }

    Ok(())

  pub fn verify<T: Transcript>(
    &self,
    transcript: &mut T,
    generators: &[Vec<G>],
    points: &[Vec<G>],
  ) -> Result<(), DLEqError> {
    if points.len() != generators.len() {
      Err(DLEqError::InvalidProof)?;
    }
    if self.s.len() != generators.len() {
      Err(DLEqError::InvalidProof)?;
    }

    transcript.domain_separate(b"multi_dleq");
    for (i, (generators, points)) in generators.iter().zip(points).enumerate() {
      if points.len() != generators.len() {
        Err(DLEqError::InvalidProof)?;
      }

      transcript.append_message(b"discrete_logarithm", i.to_le_bytes());
      for (generator, point) in generators.iter().zip(points) {
        DLEqProof::verify_statement(transcript, *generator, *point, self.c, self.s[i]);
      }
    }

    if self.c != challenge(transcript) {
      Err(DLEqError::InvalidProof)?;
    }

    Ok(())
  }
