### Title
Attacker-controlled participant index causes panic (DoS) in DKG blame handling - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

CVE-2019-19722 is a NULL pointer dereference: a crafted input crashes a driver. The Rust analog is an unguarded `HashMap` index (implicit panic on missing key) reachable from attacker-supplied data. In `Decryption::decrypt_with_proof`, the `decryptor`/`sender` arguments are attacker-influenceable `Participant` values; the code indexes `self.enc_keys[&decryptor]` and `self.commitments[&sender]` without checking membership, panicking when the named participant was never registered — exactly the "crafted input → crash" bug class, aborting the DKG host process.

### Finding Description

`BlameMachine::blame` / `AdditionalBlameMachine::blame` accept `sender: Participant` and `recipient: Participant` naming the parties of an accusation, plus an `EncryptedMessage` and optional `EncryptionKeyProof` — all derived from an accusation raised by an arbitrary participant. `Participant::new` only rejects zero, so any nonzero `u16` is a valid `Participant`, including indexes that were never part of the DKG.

Two unguarded indexes are reachable:

1. `crypto/dkg/pedpop/src/encryption.rs` — in `decrypt_with_proof`, after the PoP signature verifies, a provided proof triggers `self.enc_keys[&decryptor]`:
```rust
proof.dleq.verify(
  &mut encryption_key_transcript(self.context),
  &[C::generator(), msg.key],
  &[self.enc_keys[&decryptor], *proof.key],
)
```
`enc_keys` only contains indexes `1..=n` registered via `Decryption::register` (encryption.rs:351-362). Passing a `recipient` like `Participant(0xffff)` makes this `HashMap` index panic.

2. `crypto/dkg/pedpop/src/lib.rs` — `blame_internal` unconditionally indexes `self.commitments[&sender]` when evaluating share-verification statements; a `sender` outside the DKG set panics.

Note the sibling function `Decryption::register` does guard re-registration with an `assert!`, but nothing validates that a *blame* accusation references registered participants — `validate_map` is only applied to the commitments/share maps in `verify_r1`/`calculate_share`, not to the `sender`/`recipient` blame arguments.

### Impact Explanation

Any party able to submit a blame request (or relay a crafted `EncryptedMessage`/accusation pair into `blame`) can panic the process evaluating blame — an unprivileged remote crash/DoS killing the validator's DKG/blame evaluation. Since `blame` is the mechanism used to adjudicate faults during key generation, crashing it blocks completion and prevents honest resolution of the dispute. Severity tracks the CVE analog: availability-only impact, Medium.

### Likelihood Explanation

Reachable whenever the integrating protocol exposes blame adjudication to untrusted accusations: the attacker (or a relayed accusation naming a forged sender/recipient index outside `1..=n`) supplies a syntactically valid `Participant` that was never registered. The PoP check in path (1) is satisfiable because the attacker controls `msg.key` and can produce a valid Schnorr signature for their own crafted message; the panic then fires on the missing `enc_keys` entry before any semantic validation of the participant's membership.

### Recommendation

Replace the implicit `HashMap` indexes with checked lookups returning `DecryptionError`/`PedPoPError` (e.g., `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` and `self.commitments.get(&sender)` returning `sender`/an error), or validate `sender`/`recipient ∈ all_participant_indexes()` at the top of `blame_internal`.

### Proof of Concept

```rust
// For a DKG with n participants, evaluate blame naming a non-member recipient.
let bm: AdditionalBlameMachine<Ristretto> =
  AdditionalBlameMachine::new(context, n, commitment_msgs)?; // registers enc_keys for 1..=n

let bogus = Participant::new(0xffff).unwrap();
// Attacker crafts msg with their own key so the PoP verifies, plus Some(proof).
bm.blame(sender, bogus, crafted_msg, Some(crafted_proof));
// -> panics inside Decryption::decrypt_with_proof at `self.enc_keys[&decryptor]`
//    (crypto/dkg/pedpop/src/encryption.rs:388): "no entry found for key"
```

The analogous crash via `self.commitments[&sender]` in `blame_internal` (crypto/dkg/pedpop/src/lib.rs:599) fires for a `sender` index outside the DKG once decryption succeeds.
