## Title
Operator payout detection accepts any output amount for a payout tx spending the withdrawal UTXO, allowing an under-funded self-broadcast payout to trigger a full `bridge_amount` reimbursement - (File: core/src/verifier.rs, core/src/builder/transaction/operator_reimburse.rs)

### Summary
The payout transaction that fronts a withdrawal is entirely defined by the withdrawer's own `SinglePlusAnyoneCanPay` Schnorr signature over their own dust UTXO, so anyone who controls the withdrawal UTXO can construct and broadcast a valid payout tx paying themselves an arbitrary (near-zero) amount while embedding any operator's x-only pubkey in the OP_RETURN. Neither the chain-observation logic that attributes a payout to an operator (`update_finalized_payouts`), the kickoff-validity check (`is_kickoff_malicious`), nor the bridge circuit itself ever verifies that the payout output amount matches the required withdrawal amount, so the reimbursement flow proceeds to pay out the full `bridge_amount` via `create_reimburse_txhandler` for a withdrawal that was never actually funded for that amount.

### Finding Description
The claimed binding is:
`create_reimburse_txhandler` output value (`== move_txhandler.DepositInMove` value `== bridge_amount`) `==` amount actually delivered to the withdrawal's `script_pubkey` in the payout tx that is credited to the reimbursed operator.

`create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a tx with a single input (the withdrawal dust UTXO, key-spend) and sets the witness from `user_sig` — the *withdrawer's own* signature, verified in `Operator::withdraw` against `user_xonly_pk` derived from the input UTXO's own script (`core/src/operator.rs:614-637`). Because this is `SinglePlusAnyoneCanPay`, the withdrawer alone decides and signs the output amount/script for output index 0, and `ANYONECANPAY` lets anyone attach extra funding inputs. No N-of-N or operator signature is required to make this transaction valid and broadcastable — the operator's participation in the normal flow (`Operator::withdraw`) is purely a courtesy/business decision, not a cryptographic requirement.

Once broadcast, the chain-scanning logic in `Verifier::update_finalized_payouts` (`core/src/verifier.rs:2283-2353`) attributes the payout to whichever operator's x-only pubkey appears in the tx's first OP_RETURN output, purely via `parse_op_return_data`, with **no check of the output amount**. This is stored via `update_payout_txs_and_payer_operator_xonly_pk` (`core/src/database/verifier.rs:198-251`). The victim operator's own automation then discovers this via `get_first_unhandled_payout_by_operator_xonly_pk` (`core/src/database/verifier.rs:282-313`) and `PayoutCheckerTask::run_once` (`core/src/task/payout_checker.rs:39-111`), which calls `Operator::handle_finalized_payout` and proceeds to kickoff — again with no amount check.

`Verifier::is_kickoff_malicious` (`core/src/verifier.rs:1857-1915`), which gates whether verifiers treat a kickoff as fraudulent, only checks that the OP_RETURN operator pubkey matches the kickoff's operator and that the committed payout blockhash (via Winternitz) matches — it never checks the payout output amount.

The bridge circuit itself (`circuits-lib/src/bridge_circuit/mod.rs`, `circuits-lib/src/bridge_circuit/storage_proof.rs:44-133`) verifies only that the payout tx's referenced input matches the withdrawal outpoint (`txid`/`vout`) recorded via Citrea storage proofs — it never checks the *value* of the payout tx's output against a required minimum. So even under Challenge/Assert/Disprove, an underpaid-but-otherwise-consistent payout cannot be disproven.

As a result, the reimbursement path (`Kickoff` → no successful Challenge/Disprove → `ChallengeTimeout` → `create_reimburse_txhandler`, `core/src/builder/transaction/operator_reimburse.rs:341-385`) unconditionally pays the operator the full `DepositInMove` value (`== bridge_amount`), regardless of how little was actually paid to the withdrawer.

### Impact Explanation
An unprivileged withdrawer (attacker) can register a Citrea withdrawal for the full `bridge_amount`, then single-handedly construct and broadcast a payout transaction that pays their own withdrawal script only dust (e.g. 1000 sats) while embedding a target operator's x-only pubkey in the OP_RETURN. That operator's automation will treat this as its own fronted payout, kick off, and — absent a successful challenge (none is possible since the tx is internally consistent per the checks the protocol performs) — receive the full `bridge_amount` reimbursement from the move-to-vault UTXO. This matches the explicitly listed Critical category "an operator reimbursed for a payout it never funded" and results in `bridge_amount` BTC (~10 BTC per current paramset) leaving custody for a withdrawal that was almost entirely unfunded. This is repeatable per withdrawal/operator and does not require any operator, verifier, or aggregator compromise — only a Citrea `withdraw()` call and a single Bitcoin broadcast.

### Likelihood Explanation
The attacker needs only: (1) a normal Citrea withdrawal registration for `bridge_amount`, (2) knowledge of a target operator's x-only pubkey (public information), and (3) the ability to sign and broadcast one Bitcoin transaction using their own withdrawal-UTXO key plus a small funding input for fees/dust. No privileged role, key compromise, or majority hashrate is required, and the attack works purely on regtest/testnet/mainnet against the automation's passive detection logic. The main cost to the attacker is the dust amount paid to their own withdrawal output and transaction fees; they do not need the operator's cooperation at all.

### Recommendation
Add an explicit minimum-amount check whenever a payout tx is attributed to an operator: `update_finalized_payouts`/`is_kickoff_malicious` (and ideally the bridge circuit/storage proof verification) should validate that the payout tx's output value credited to the withdrawal script_pubkey is at least `bridge_amount - operator_withdrawal_fee_sats` (mirroring `Operator::is_profitable`) before allowing a kickoff/reimbursement to be treated as valid for that operator. Reimbursement paid via `create_reimburse_txhandler` should be bounded by, or otherwise tied cryptographically to, the actually verified payout amount rather than unconditionally paying the full `bridge_amount`.

### Proof of Concept
```
cargo test underpaid_payout_reimbursement_regtest -- --nocapture
```
Plan for the test (regtest, no mainnet, no live Citrea — using existing e2e test harness in `core/src/test/deposit_and_withdraw_e2e.rs`):
1. Deposit `bridge_amount` and register a withdrawal on the mock Citrea client for the full `bridge_amount`.
2. As the "attacker" (test controls the withdrawer's key), sign a payout transaction via `create_payout_txhandler`/`sign_withdrawal_output`-style helper for only `Amount::from_sat(1000)` to an attacker-controlled address, embedding the honest operator's x-only pubkey (not going through `Operator::withdraw`/`is_profitable`).
3. Broadcast the tx directly via RPC (bypassing the operator's gRPC `withdraw`/`internal_withdraw` entirely) and mine to finality.
4. Let the victim operator's automation (`PayoutCheckerTask`) pick it up, kickoff, and (absent challenge) send `ChallengeTimeout` and `Reimburse`.
5. Assert: `reimburse_tx.output[0].value == bridge_amount` (from `UtxoVout::DepositInMove`) while the actual amount paid to the withdrawal `script_pubkey` was `1000` sats — i.e. assert these two values are unequal, proving the broken binding.
