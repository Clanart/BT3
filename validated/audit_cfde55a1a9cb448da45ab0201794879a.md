### Title
Unencoded `file://` URL construction in `openFile` can truncate/redirect the opened resource - (File: `app/src/ui/lib/open-file.ts`)

### Summary
`openFile` builds the URL passed to `shell.openExternal` by naive string interpolation, `` `file://${fullPath}` ``, without percent-encoding reserved URL characters (`#`, `?`, `%`, etc.) that may legitimately appear in a file name committed to a repository. [1](#0-0) 

### Finding Description
`fullPath` reaching `openFile` is derived from paths of files tracked in the working copy (e.g. changed/committed files surfaced in the Changes sidebar or PR file list), which are attacker-controlled the moment a user clones or fetches a hostile repository and interacts with one of its files in the UI. [1](#0-0) 

The function does not call `encodeURI`/`encodeURIComponent`, nor Node's `url.pathToFileURL`, before concatenating the path into a `file://` string:
```
const result = await shell.openExternal(`file://${fullPath}`)
```
Because `#` and `?` are reserved delimiters in the URL/URI grammar (`#` starts a fragment, `?` starts a query string), a file whose name contains one of these characters (e.g. `notes#draft.txt` or `report?v2.txt`) will have the URL truncated at that point once it is parsed by the underlying OS shell invocation performed by Electron's `shell.openExternal`. Likewise, a literal `%` followed by two hex digits in a filename (e.g. `50%discount.txt` containing `%64`) can be percent-decoded by the URL/shell layer into a different character sequence than what is on disk, causing the resolved path to diverge from `fullPath`. This is invoked through the IPC-proxied `shell.openExternal`, which is provided by `app/src/lib/app-shell.ts` and forwarded to the main process. [2](#0-1) 

### Impact Explanation
In the best case this only misleads the user about which resource was opened (truncated path/fragment ignored). In a worse case, if the decoded/truncated string happens to resolve to a different, pre-existing path on disk (e.g. via a crafted `%XX` sequence that decodes into a path separator or `..` sequence recognized by the OS's URL-to-path resolution), the application could open a file other than the one the user intended and believes they inspected — a form of "silent corruption of what the user believes they are viewing," within scope for repository-content-driven issues. It does not, by itself, achieve code execution because `shell.openExternal` merely invokes the OS's default handler for the resolved resource, and I could not confirm within this codebase that arbitrary path traversal outside the filesystem is reliably achievable versus mere truncation — this depends on Electron/OS-level URL parsing behavior that is outside this repository's code and that I was not able to verify further with the tools available.

### Likelihood Explanation
Reaching `openFile` requires the victim to open a specific file from a maliciously-named entry inside a cloned/fetched repository (via the Changes sidebar, history file list, PR file list, or conflict resolution UI) — a normal, expected user action, not an "unnatural" step. An attacker fully controls the triggering filename simply by committing a file with `#`, `?`, or `%` in its name.

### Recommendation
Construct the file URL safely, e.g. using Node's `url.pathToFileURL(fullPath).toString()` (which performs correct percent-encoding of reserved characters) instead of manual template-literal concatenation in `app/src/ui/lib/open-file.ts`.

### Proof of Concept
1. In a repository, commit a file named `a#b.txt`.
2. In the Desktop UI, trigger "Open file" for that path (e.g. from the Changes sidebar), which calls `openFile(fullPath, dispatcher)` with `fullPath` ending in `.../a#b.txt`.
3. Inspect the argument passed to the mocked `shell.openExternal` (as in `app/test/helpers/test-app-shell.ts`) — it will be `file://.../a#b.txt`; when parsed as a URL, everything from `#` onward is treated as a fragment rather than part of the path, so the resource ultimately resolved differs from the literal `fullPath` string that was intended. [3](#0-2)

```typescript
import { shell } from '../../lib/app-shell'
import { Dispatcher } from '../dispatcher'

export async function openFile(
  fullPath: string,
  dispatcher: Dispatcher
): Promise<void> {
  const result = await shell.openExternal(`file://${fullPath}`)

  if (!result) {
    const error = {
      name: 'no-external-program',
      message: `Unable to open file ${fullPath} in an external program. Please check you have a program associated with this file extension`,
    }
    await dispatcher.postError(error)
  }
}
```
