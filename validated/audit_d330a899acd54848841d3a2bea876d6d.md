Based on the code I found, there's a concrete analog in how GitHub Desktop silently rewrites a repository's trusted `origin` remote URL using data pulled from the GitHub API, without pinning the new URL to the previously-trusted host.

### Title
Unvalidated GitHub API `clone_url` silently rewrites the local git remote, redirecting future push/fetch traffic - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The original report's broken invariant is: a critical destination/config value (the staking target) can be silently mutated by a privileged migration path with no way to null it out safely, so the owner loses control over where funds/liquidity end up. The Desktop analog is `updateRemoteUrl`, which silently rewrites the repository's `origin` remote URL to whatever `clone_url` is returned by a `GitHubRepository`/API object, guarding only on protocol equality and "did the URL structurally change" — never re-validating that the *new* host is the one the user originally trusted.

### Finding Description
`updateRemoteUrl` compares the stored remote to the API-provided `clone_url` and rewrites the remote when the stored value hasn't been manually edited: [1](#0-0) 

The only checks performed are:
- `protocolsMatch`: the URL scheme (https/ssh) of old vs new must match.
- `remoteUrlUnchanged`: the stored remote must still equal `gitHubRepository.cloneURL` (i.e., the user hasn't hand-edited it).
- `!urlsMatch`: the new `clone_url` differs from the current remote.

Crucially, there is **no check that the new `clone_url`'s hostname equals the old remote's hostname**. `urlMatchesRemote` compares hostname/owner/name of two URLs to decide "are these the same repo," but it is only used to detect *whether* something changed — not to constrain *what* the new value is allowed to be: [2](#0-1) 

Once `!urlsMatch` is true (i.e., owner/name/host differ from the current remote at all), the code unconditionally calls `gitStore.setRemoteURL(...)` with the API-supplied value, which shells out to `git remote set-url`: [3](#0-2) 

If the `IAPIRepository`/`GitHubRepository` object feeding this function is attacker-influenced — e.g., a compromised/malicious GitHub Enterprise Server instance, a proxy sitting between Desktop and the API, or an API response for a repository that was renamed/transferred to attacker-controlled infrastructure — the `clone_url` field can point to an arbitrary host of the attacker's choosing, as long as the protocol matches. Desktop will then silently overwrite `origin` with that host with no user confirmation and no re-validation against the account's real endpoint.

### Impact Explanation
Once `origin` is silently repointed to an attacker-controlled host:
- Subsequent `git push` operations will send the user's commits (and, depending on credential-helper configuration, their auth token/credentials via HTTPS Basic auth headers) to the attacker's server instead of the real repository — this is silent corruption of what the user pushes plus potential credential/token exfiltration.
- Subsequent `git fetch`/`pull` will pull attacker-supplied refs/objects into the local repo, which can be leveraged for further supply-chain-style attacks (the classic "malicious repository content" vector already flagged as in-scope for this bug class).
- The user has no visible signal that `origin` changed, since this happens automatically as part of a background repository refresh, not through the Repository Settings dialog the user would normally review.

### Likelihood Explanation
This requires the attacker to control (or MITM) a GitHub API response consumed by Desktop — explicitly listed as an in-scope attacker capability ("a GitHub API object ... or a git remote/proxy response"). It does not require local access, admin rights, or prior malware. The most realistic trigger is a malicious/compromised GitHub Enterprise Server the victim has already added an account for, or a network position that can tamper with API responses for that endpoint (no request/response signing is evident in this flow). I was not able to fully trace, within the available iterations, the exact call site in `app-store.ts` that supplies the `IAPIRepository` to `updateRemoteUrl` (only found via `grep_search` matches, not fully read), so I cannot confirm with certainty how frequently/automatically this refresh happens or whether any additional caller-side validation exists; a Devin session with full file access should verify the app-store.ts call site before treating this as fully confirmed.

### Recommendation
Require the new `clone_url` returned by the API to share the same hostname as the currently trusted remote (or at minimum the same hostname as the account's configured endpoint) before calling `setRemoteURL`. If the hostname differs, treat it as a suspicious/foreign redirect and surface an explicit user confirmation dialog rather than silently rewriting `origin`.

### Proof of Concept
1. User adds a GitHub Enterprise Server account in Desktop and clones a repo from it; `origin` is set to `https://ghes.company.com/org/repo.git`.
2. The GHES instance (compromised, or an attacker-in-the-middle proxy in front of it) returns an API repository object where `clone_url` is `https://attacker.evil/org/repo.git` (same protocol, different host/owner/name).
3. Desktop's background repository refresh calls `updateRemoteUrl`; since `remoteUrlUnchanged` is true (user hasn't hand-edited the remote) and `urlsMatch` is false (owner/name differ), `protocolsMatch` is true (both https), the code calls `gitStore.setRemoteURL('origin', 'https://attacker.evil/org/repo.git')` with no host-pinning check [4](#0-3) .
4. The user's next `git push` sends commits (and HTTPS credentials, if cached) to `attacker.evil` instead of the real GHES server.

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

export async function setRemoteURL(
  repository: Repository,
  name: string,
  url: string
): Promise<true> {
  await git(['remote', 'set-url', name, url], repository.path, 'setRemoteURL')
  return true
}
