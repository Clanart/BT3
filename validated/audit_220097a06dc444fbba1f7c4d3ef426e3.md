### Title
Unvalidated `foldername` RPC parameter allows DataLayer RPC caller to write/overwrite arbitrary files outside `server_files_location` - (File: chia/data_layer/data_layer_rpc_api.py)

### Summary
The DataLayer RPC endpoint `add_missing_files` accepts a client-supplied `foldername` string and passes it, unvalidated, all the way down to raw file-write calls (`open(...)`) that create/overwrite `.dat` files at that location. This mirrors the CVE-2023-33466 bug class (authenticated API user overwrites arbitrary files on disk, which in specific deployments can be leveraged toward configuration overwrite/RCE), but here the actor is any local caller with access to the DataLayer RPC.

### Finding Description
`DataLayerRpcApi.add_missing_files()` takes `foldername` directly from the JSON request body with no restriction to a safe base directory: [1](#0-0) 

That value is passed straight into `DataLayer.add_missing_files()`, which uses it (or the default `server_files_location`) as the destination folder for every generated full/delta tree file, with no path canonicalization or containment check: [2](#0-1) 

The actual disk write happens in `write_files_for_root()`, which joins the caller-controlled `foldername` with a deterministic filename and opens it directly for writing, honoring an attacker-suppliable `overwrite=True` flag that switches the file mode from exclusive-create (`"xb"`) to truncate-write (`"wb"`), allowing existing files at that path to be overwritten: [3](#0-2) 

By contrast, the same module's S3 plugin service constrains all writes to a fixed `server_files_path` and validates filenames with `is_filename_valid()` before ever touching disk: [4](#0-3) [5](#0-4) 

No equivalent containment exists for the `add_missing_files` RPC path — the directory itself is fully caller-chosen, and (per the module's own documentation) file-system writes for these `.dat` files are explicitly called out as having outstanding TODOs around locking/hardening: [6](#0-5) 

### Impact Explanation
A caller with access to the DataLayer RPC (a "local RPC caller" per the in-scope actor list) can direct the DataLayer service to write files into an arbitrary directory on the filesystem rather than the intended `server_files_location`, and with `overwrite=True` can truncate/overwrite an existing file at a path they control if they can predict or match the deterministic `<store_id>-<node_hash>-{full,delta}-<generation>-v1.0.dat` filename for a store they own. This is the same class of primitive as the Orthanc CVE (authenticated-user file overwrite via an API parameter that escapes the intended storage directory), and depending on process file permissions and deployment layout it degrades disk hygiene/availability guarantees and widens the blast radius of an otherwise "local-admin-only" RPC surface.

### Likelihood Explanation
Reaching this code path requires only calling the `add_missing_files` RPC endpoint (exposed via `chia data add_missing_files --directory ...` per [7](#0-6) ) with a store id the caller already owns/knows and an arbitrary `foldername`/`overwrite=True`. No chain state, consensus validation, or privileged wallet key is required beyond RPC connectivity, making this straightforward to trigger for anyone who can reach the DataLayer RPC port.

### Recommendation
Validate and canonicalize `foldername` against an allow-listed base directory (e.g., resolve and require it to be `server_files_location` or a documented sub-path) before it reaches `write_files_for_root()`/`add_missing_files()`; reject any request supplying a folder outside that boundary, and treat `overwrite=True` as sensitive (e.g., require it to only apply within the managed directory).

### Proof of Concept
1. Create/own a DataLayer store and confirm at least one generation (`get_root_history` shows generation ≥ 1).
2. Call the DataLayer RPC `add_missing_files` with `{"ids": ["<store_id>"], "overwrite": true, "foldername": "/path/outside/server_files_location"}`.
3. Observe that `DataLayer.add_missing_files()` → `write_files_for_root()` creates/overwrites `<store_id>-<node_hash>-full-<n>-v1.0.dat` and `-delta-` files at the attacker-chosen directory, bypassing the intended `server_files_location` containment, as shown in [8](#0-7) .

    async def add_missing_files(self, store_id: bytes32, overwrite: bool, foldername: Path | None) -> None:
        root = await self.data_store.get_tree_root(store_id=store_id)
        latest_generation = root.generation
        full_tree_first_publish_generation = max(0, latest_generation - self.maximum_full_file_count + 1)
        singleton_record = (
            await self.wallet_rpc.dl_latest_singleton(DLLatestSingleton(launcher_id=store_id, only_confirmed=True))
        ).singleton
        if singleton_record is None:
            self.log.error(f"No singleton record found for: {store_id}")
            return
        max_generation = min(singleton_record.generation, root.generation)
        server_files_location = foldername if foldername is not None else self.server_files_location
        files = []
        for generation in range(1, max_generation + 1):
            root = await self.data_store.get_tree_root(store_id=store_id, generation=generation)
            res = await write_files_for_root(
                self.data_store,
                store_id,
                root,
                server_files_location,
                full_tree_first_publish_generation,
                overwrite,
                self.group_files_by_store,
            )
            files.append(res.diff_tree.name)
            if res.full_tree is not None:
                files.append(res.full_tree.name)
