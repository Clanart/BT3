### Title
CW20ERC20Pointer's `approve()` reads stale on-chain allowance and issues relative `increase_allowance`/`decrease_allowance`, enabling classic ERC20 approve front-running / allowance-doubling theft - (File: contracts/src/CW20ERC20Pointer.sol)

### Summary
The `CW20ERC20Pointer` contract exposes a standard `IERC20.approve(spender, amount)` interface but does not "set" the allowance atomically. Instead it reads the current CW20 allowance and then issues a relative `increase_allowance` or `decrease_allowance` CosmWasm execute message for the delta between the on-chain value and the caller's desired final value:

```solidity
function approve(address spender, uint256 amount) public override returns (bool) {
    if (amount > type(uint128).max) {
        amount = type(uint128).max;
    }
    uint256 currentAllowance = allowance(msg.sender, spender);
    if (currentAllowance > amount) {
        ... decrease_allowance by (currentAllowance - amount)
    } else if (currentAllowance < amount) {
        ... increase_allowance by (amount - currentAllowance)
    }
    return true;
}
``` [3](#0-2) 

This is the textbook ERC20 "approve front-running" pattern: because `currentAllowance` is queried live from CW20 state at execution time rather than compared against the value the user believed was outstanding when they signed the transaction, a spender who already holds an allowance can race the owner's allowance-changing transaction.

### Finding Description
Any EVM caller (a normal, unprivileged transaction sender) can interact with `CW20ERC20Pointer` — the canonical ERC20-compatible wrapper automatically deployed for CW20 tokens via the `pointer` precompile's `addCW20Pointer` (`AddCW20` → `UpsertERCCW20Pointer`) — exactly like any ERC20 token. A token owner who previously granted `spender` an allowance of `X` and later wants to change it to `Y` calls `approve(spender, Y)`. Because Sei EVM transactions sit in the public mempool before execution, `spender` can front-run this call with a `transferFrom` that consumes the full outstanding allowance `X`. When the owner's `approve(spender, Y)` transaction subsequently executes, `allowance(msg.sender, spender)` now returns `0` (or whatever `spender` left behind), so the pointer computes `increase_allowance` by `Y - 0 = Y` instead of recognizing that the owner intended to *replace* `X` with `Y`. The net effect is that `spender` receives both the original `X` tokens (from the front-run `transferFrom`) and a fresh allowance of `Y`, doubling the tokens they can extract relative to what the owner intended for that transaction.

### Impact Explanation
This directly matches the "unauthorized transfer via precompile or pointer" and "concrete fund loss" impact categories: a spender that has been granted a CW20 allowance through the ERC20 pointer interface can steal funds beyond what the owner intends whenever the owner attempts to change (especially lower) that allowance, using ordinary transaction ordering/front-running available to any public mempool participant — no validator, network, or governance compromise is required.

### Likelihood Explanation
Likelihood is realistic: any application or user that follows the standard (and widely recommended) practice of changing an ERC20 allowance by calling `approve()` again — including to reduce or revoke it — is exposed. The attack requires only that the spender is already approved and is watching the mempool, which is a routine capability for any contract-integrated spender (e.g., a DEX router, marketplace, or other pointer-composed contract) built on top of `CW20ERC20Pointer`.

### Recommendation
Do not derive relative CW20 `increase_allowance`/`decrease_allowance` calls from a live-queried "current" allowance inside `approve()`. Instead, either: (1) require callers to use `increaseAllowance`/`decreaseAllowance` with an expected-current-value parameter (as in OpenZeppelin's safe-approve pattern) and revert on mismatch, or (2) require the allowance to be set to zero before it can be changed to a new non-zero value (the standard ERC20 approve-race mitigation), or (3) if CW20 semantics allow it, use a native "set_allowance" style CW20 message instead of computing deltas from potentially stale reads.

### Proof of Concept
1. Deploy/associate a `CW20ERC20Pointer` for a CW20 token; owner has balance `100` in the CW20 contract.
2. Owner calls `pointer.approve(spender, 80)` → CW20 allowance(owner, spender) = 80.
3. Owner decides to reduce trust in spender and submits `pointer.approve(spender, 20)` to the mempool.
4. `spender`, monitoring the mempool, front-runs with `token.transferFrom(owner, spender, 80)` on the underlying CW20 contract (or via the pointer's `transferFrom`), draining the full existing allowance before the owner's transaction lands. CW20 allowance is now 0.
5. Owner's `approve(spender, 20)` executes: `currentAllowance` (0) < `amount` (20), so the pointer issues `increase_allowance(spender, 20)`. CW20 allowance(owner, spender) becomes 20.
6. `spender` calls `transferFrom(owner, spender, 20)` again, extracting the remaining 20.
7. Total extracted by `spender`: 100 tokens, i.e., the owner's entire balance, despite intending to cap the spender's access at 20 after step 3 — identical outcome to the referenced FootiumEscrow PoC, reproduced against `contracts/src/CW20ERC20Pointer.sol`'s `approve()`.
