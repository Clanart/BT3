### Title
Missing scheme/host validation on GitHub API-supplied `clone_url` before `git remote add` — attacker-controlled remote created from a pull request fork - (`app/src/lib/git/remote.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
The Sherlock report's core defect is a missing sanity check on an externally influenced parameter (`stopTime`) before it is used in a critical operation, allowing an attacker-shaped value to silently drive unintended, expensive/irreversible behavior. The closest analog in GitHub Desktop is the lack of any allow‑listing or validation of the remote URL (`clone_url`) that comes from a pull request's `head.repo` object — a GitHub API object that is effectively attacker-controlled, since the PR head repo is the *fork owner's* repository — before that URL is handed to `git remote add` and later `git fetch`.

### Finding Description
When a user checks out a pull request from a fork, `_findPullRequestBranch` in `app/src/lib/stores/app-store.ts` takes `headCloneUrl` (sourced from `pullRequest.head.repo.clone_url`, populated straight from the GitHub API response) and, if no existing remote matches it, calls: [1](#0-0) 
into `addRemote`, defined here with zero validation of the URL's scheme, host, or shape: [2](#0-1) 
The same unchecked pattern occurs for the "Open in Desktop" deep-link flow, where a `clone_url` value is passed all the way from `dispatcher.ts`'s `openPullRequestFromUrl` into `_checkoutPullRequest`: [3](#0-2) 
Compare this to the Enterprise-server URL entry path, which explicitly enforces `https:` only and rejects everything else: [4](#0-3) 
No equivalent allow-list exists for `addRemote`, nor is there any `GIT_ALLOW_PROTOCOL` environment restriction configured anywhere in the codebase (confirmed absent via search), and `envForRemoteOperation`/`envForProxy` only special-case `http(s)` for proxy resolution, doing nothing to constrain or reject other schemes: [5](#0-4) 
`urlMatchesRemote`/`urlMatchesCloneURL` (used to *find* an existing remote) simply return `false` for any URL that doesn't match the app's known GitHub URL regex shapes, meaning any URL that fails to parse (e.g., a non-standard scheme) is treated as "no match" and falls straight through to the `addRemote(...)` branch with the raw, unvalidated string: [6](#0-5) 

This is structurally identical to the Sherlock bug: a value that originates from an external/untrusted source (there, a user-supplied `stopTime`; here, a GitHub API field controlled by whoever owns the PR's head fork) is consumed by a critical operation (`createStream`/`git remote add` + `git fetch`) without a guard that would reject "obviously wrong" values (a `stopTime` in the past / a non-`http(s)`/`ssh` remote URL).

### Impact Explanation
Any repository maintainer using GitHub Desktop who opens (or reviews via "Open in Desktop") a pull request from a malicious fork will have Desktop automatically run `git remote add github-desktop-<owner> <attacker-supplied-url>` followed by `git fetch` on that remote, with no scheme allow-listing performed by Desktop itself. This satisfies the "attacker controls a GitHub API object" and "git remote/response" criteria in the Valid Impact section: the attacker doesn't need any local/physical access — they only need to open a PR (or have a user click an "Open in Desktop" deep link with a crafted `clone_url` if that value isn't independently re-validated server-side). Depending on what git version/transport helpers are enabled in the bundled dugite/git binary, this could range from SSRF-like probing of internal file paths, to a vector for the well-known "smart HTTP/ext transport" class of remote URL abuse if any legacy or misconfigured git build without hardened `protocol.*.allow` defaults is present. Even absent full code execution, this is a silent-corruption/unauthorized-remote-configuration primitive: Desktop is unconditionally writing an attacker-chosen value into the repository's `.git/config` and initiating a network fetch against it, entirely outside the user's awareness of what value was used.

### Likelihood Explanation
High for the "unauthorized remote written to repo config" primitive: it happens automatically whenever a user reviews/checks out a fork PR, which is a completely ordinary, unprompted workflow (no unnatural steps). The escalation to code-execution-level impact depends on the specific git binary's protocol allow-list defaults, which I could not fully verify from this codebase alone (git's own upstream hardening for `ext::`/`fd::` since 2.12.1 mitigates the most severe outcome by default) — this is the aspect I'm least certain about.

### Recommendation
Add an explicit scheme/host allow-list check (mirroring `validateURL` in `enterprise-validate-url.ts`) inside `addRemote` (`app/src/lib/git/remote.ts`) or immediately before it is called in `_findPullRequestBranch`/`openRepositoryFromUrl`, rejecting any `clone_url` that isn't `https:`, `git:`, or a well-formed `ssh://`/`git@host:` form matching the parseable shapes already defined in `remote-parsing.ts`. Additionally, set `GIT_ALLOW_PROTOCOL` explicitly in `envForRemoteOperation` to a known-safe allow-list (`http:https:ssh:git`) for all remote operations, so that even if an unexpected scheme slips through application-level checks, the underlying git process refuses to honor it — the same defense-in-depth pattern already applied via `isClonePathSensitive` for clone destinations and `sanitizeCloneName` for path traversal.

### Proof of Concept
1. Attacker forks a target repository on GitHub and, via a manipulated/self-hosted GitHub-Enterprise-like API endpoint (or any flow where Desktop trusts a raw `clone_url` string from a PR's `head.repo`), causes the PR object returned to Desktop to contain `head.repo.clone_url = "<non-standard-scheme-url>"` instead of a normal `https://.../owner/repo.git` value.
2. Victim, using GitHub Desktop, opens that pull request and Desktop calls `_checkoutPullRequest` → `_findPullRequestBranch`, which fails to match any existing remote via `urlMatchesRemote` (since the crafted URL doesn't fit the app's known regexes) and falls into:
```ts
remote = await addRemote(repository, forkRemoteName, headCloneUrl)
```
`app/src/lib/stores/app-store.ts:8648-8651`
3. `addRemote` executes `git(['remote', 'add', name, url], ...)` verbatim with no validation:
`app/src/lib/git/remote.ts:29-36`
4. Desktop then calls `_fetchRemote`, invoking `git fetch <forkRemoteName>` against the attacker-controlled URL/value with no `GIT_ALLOW_PROTOCOL` restriction set in the process environment (`app/src/lib/git/environment.ts:76-81`), relying entirely on whatever protections the bundled git binary provides by default.

```typescript
export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
```
