### Title
Cached deterministic FROST nonce reused across distinct messages within one DKG-confirmation attempt enables validator key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
The bug class in the external report is a use-after-free: state that must be consumed exactly once is used again after being logically invalidated. The analog in Serai is a one-time FROST preprocess (a cryptographic single-use object) being re-materialized from a persisted seed and reused. `DkgConfirmer` derives its signing nonce deterministically from `CachedPreprocesses`, keyed only by `(b"DkgConfirmer", attempt)`, and re-derives the identical nonce on every call within that attempt — including the re-execution inside `complete` — regardless of which message is actually being signed.

### Finding Description
`SigningProtocol::preprocess_internal` stores a 32-byte seed in the DB under `context = (b"DkgConfirmer", attempt)` and rebuilds the `AlgorithmSignMachine` from that same seed via `AlgorithmSignMachine::from_cache` on every invocation [1](#0-0) . The FROST documentation is explicit that a cached preprocess "MUST only be used once. Reuse of it enables recovery of your private key share" [2](#0-1) .

`share_internal` calls `preprocess_internal` and then `machine.sign(preprocesses, msg)`, where `msg = set_keys_message(&self.spec.set(), &removed, key_pair)` — i.e., the message embeds the externally supplied `key_pair` [3](#0-2) . `complete` then re-executes `share_internal` with whatever `key_pair` was passed to it, signing again with the same cached nonce [4](#0-3) .

The signature share is `s = nonce_scalar + c · λ_i · x_i` (`sign_share` producing `challenge * secret + nonce`, per `SchnorrSignature::sign` semantics) [5](#0-4) . If two executions under the same `attempt` sign messages differing only in `key_pair`, both shares use the identical `nonce_scalar`. The Schnorrkel challenges `c_1 ≠ c_2` are publicly computable, so `x_i = (s_1 - s_2) / (λ_i (c_1 - c_2))` — direct recovery of the validator's MuSig secret share. Even when only the counterparties' preprocess sets differ, each additional signing adds a linear equation in the same reused `(d, b, x)` unknowns, and three executions suffice to solve.

The file's own safety argument concedes the scheme is only safe if no "logical flaw [lets] new messages overwrite prior messages" and that checking that published commitments match the presumed preprocess is an unimplemented `TODO` [6](#0-5) . Nothing in `share_internal` binds the cached nonce to `msg` or to the preprocess set; the cache is keyed solely on `attempt`, so any code path that reaches `share`/`complete` twice in one attempt with different `key_pair` or preprocess inputs produces the reuse.

### Impact Explanation
Recovery of a validator's MuSig secret share. With enough shares recovered (or combined with the share's role in confirming `set_keys`), an attacker can forge validator signatures on `set_keys_message` confirmations — the root-of-trust operation installing new threshold keys — achieving signature forgery against the coordinator's validator key. This matches the accepted impact of key-share recovery and signing of unintended messages.

### Likelihood Explanation
Reachability requires the coordinator to execute `share`/`complete` twice under the same `attempt` with differing `key_pair` or differing preprocess sets. The `key_pair` and the preprocess bytes (`HashMap<Participant, Vec<u8>>` parsed via `read_preprocess` in `share_internal`) are attacker-influenced, unauthenticated-input data [7](#0-6) . The safety rests entirely on BFT finality plus an acknowledged-missing commitment-consistency check (`TODO` at lines 50–54), and `DkgConfirmer::complete` unconditionally re-signs via `share_internal` even after `share` already published a share for the same attempt [8](#0-7) . I could not fully trace `handle.rs` to confirm which transaction handlers invoke `share` and `complete` with independently supplied `key_pair` values within one attempt; if they can differ, the exploit is deterministic. Given the reliance on a documented-but-unimplemented guard, likelihood is moderate — rated High severity / Medium likelihood overall.

### Recommendation
Bind the cached preprocess to the exact message and signing set: store `H(msg || sorted preprocess bytes)` alongside the seed in `CachedPreprocesses`, and in `share_internal` refuse to sign (or re-derive a fresh nonce, deleting the old cache entry) if the hash differs from the first recorded one for that `attempt`. Implement the noted `TODO` of verifying the published on-chain preprocess equals the presumed preprocess before publishing any share. Alternatively, mix `msg` and the preprocess digest into the nonce derivation (e.g., `hash_to_F(b"nonce", seed || msg || commitments_digest)`) so reuse of the seed across differing messages still yields distinct nonces.

### Proof of Concept
1. In attempt `a`, cause `DkgConfirmer::share(preprocesses, key_pair_A)` to execute, publishing share `s_1` over `msg_A = set_keys_message(set, removed, key_pair_A)` using nonce `r` derived from `CachedPreprocesses[("DkgConfirmer", a)]`.
2. In the same attempt, cause `DkgConfirmer::complete(preprocesses', key_pair_B, shares)` to execute; it internally calls `share_internal` again, producing `s_2` over `msg_B` with the identical `r`.
3. Compute the Schnorrkel challenges `c_1 = H(R ‖ A ‖ msg_A)`, `c_2 = H(R ‖ A ‖ msg_B)` (same `R` since the nonce and MuSig context are identical), and the signer's Lagrange coefficient `λ_i` from the published participant set.
4. Recover the validator share: `x_i = (s_1 - s_2) · (λ_i · (c_1 - c_2))⁻¹`.

I was unable to fully verify, within the available iterations, the exact call sites in `handle.rs` that feed `key_pair` into `share`/`complete`, so the trigger path in step 2 is inferred from the unconditionally re-executing `complete` implementation rather than confirmed end-to-end.

  In order for nonce re-use to occur, the received nonce commitments (or the message to be signed)
  would have to be distinct and sign would have to be called again.

  Before we act on any received messages, they're ordered and finalized by a BFT algorithm. The
  only way to operate on distinct received messages would be if:

  2) A reorganization occurred from chain A to chain B, and with it, different messages

  a significant amount of processes may be byzantine, leading to BFT being broken, that still will
  not trigger a reorganization. The only way to move to a distinct chain, with distinct messages,

  fn share_internal(
    &mut self,
    participants: &[<Ristretto as Ciphersuite>::G],
    mut serialized_preprocesses: HashMap<Participant, Vec<u8>>,
    msg: &[u8],
  ) -> Result<(AlgorithmSignatureMachine<Ristretto, Schnorrkel>, [u8; 32]), Participant> {
    let machine = self.preprocess_internal(participants).0;

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();
    for participant in participants {
      preprocesses.insert(
        participant,
        machine
          .read_preprocess(&mut serialized_preprocesses.remove(&participant).unwrap().as_slice())
          .map_err(|_| participant)?,
      );
    }

    let (machine, share) = machine.sign(preprocesses, msg).map_err(|e| match e {
      FrostError::InternalError(e) => unreachable!("FrostError::InternalError {e}"),
      FrostError::InvalidParticipant(_, _) |
      FrostError::InvalidSigningSet(_) |
      FrostError::InvalidParticipantQuantity(_, _) |
      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),
      FrostError::InvalidPreprocess(p) | FrostError::InvalidShare(p) => p,
    })?;

    Ok((machine, share.serialize().try_into().unwrap()))
