### Title
Attacker-controlled participant count in `ThresholdKeys::read` triggers oversized allocation before input validation - (File: crypto/dkg/src/lib.rs)

### Summary
CVE-2017-7652 is a resource-exhaustion bug: a small trigger (a SIGHUP reload) forces the process to attempt a resource acquisition (opening a file / allocating a descriptor) that fails under exhaustion conditions, taking down the service. The Serai analog lives in `ThresholdKeys::read` in `crypto/dkg/src/lib.rs`, which trusts a `u16` `n` field from untrusted bytes and performs `Vec::with_capacity(usize::from(n))` plus an `n`-iteration `read_G`/`HashMap` fill before the value is ever validated against `ThresholdParams`. A short crafted buffer forces an allocation of up to 65,535 scalar slots (~2 MiB) and, more importantly, up to 65,535 canonical point-deserialization attempts or an early abort — orders of magnitude more work/memory than the few input bytes supplied, with no bound tied to the actual bytes present.

### Finding Description
In `ThresholdKeys::read` (`crypto/dkg/src/lib.rs:574-632`):

1. `t`, `n`, and `i` are read directly from the stream as little-endian `u16`s (`lib.rs:591-602`). `n` is fully attacker-controlled, up to 65,535.
2. For `Interpolation::Constant`, the code immediately does `Vec::with_capacity(usize::from(n))` (`lib.rs:608`) and then loops `n` times calling `C::read_F` (`lib.rs:609-611`). The capacity reservation happens before a single scalar byte is proven present.
3. Independently of the interpolation arm, the code loops `for l in (1 ..= n)` inserting a `read_G` result into a `HashMap` (`lib.rs:620-623`). Each `read_G` performs a full point decompression (`crypto/ciphersuite/src/lib.rs:91-100`).
4. Only *after* all of this is `ThresholdParams::new(t, n, i)` invoked (`lib.rs:626`), which would have rejected absurd `n`/`t` combinations.

This mirrors the Mosquitto flaw's shape exactly: a resource-acquisition step (here, memory reservation + expensive per-element decompression) is executed on demand based on unbounded, unvalidated attacker input, before the cheap validation that would have rejected it. The Ethereum network code in this same codebase explicitly acknowledges this DoS class and chunked its reads to avoid it (`networks/ethereum/src/machine.rs:51-60`); `ThresholdKeys::read` has no such mitigation.

### Impact Explanation
`ThresholdKeys::read` is explicitly a sink for untrusted bytes (serialized key material crossing trust boundaries — e.g., supplied by a counterparty or restored from attacker-influenced storage). Each invocation with `n = 0xFFFF` reserves ~2 MiB of `Vec` capacity and attempts up to 65,535 point decompressions from a buffer that need only be a handful of bytes long; the read fails fast on `read_exact` but the capacity allocation already occurred, and in a loop the attacker forces repeated large reservations and allocation churn. On memory-constrained validator/coordinator processes this translates to allocator pressure, OOM aborts (`Vec::with_capacity` aborts on failure rather than returning an error), and denial of signing/DKG service — the same availability impact class as the Mosquitto advisory (CVSS 7.5, availability-affecting resource exhaustion reachable by a low-privilege party).

### Likelihood Explanation
Exploitation requires only that an attacker reach a code path feeding their bytes to `ThresholdKeys::read` — one of the enumerated untrusted-input sinks. No valid keys, signatures, or protocol state are required; the malicious `n` is consumed before any cryptographic check. Cost to the attacker is a few bytes per attempt. Mitigating factors: the amplification per call is bounded by `u16::MAX` (~2 MiB reservation, ~65K decompression attempts), so sustained requests are needed for full exhaustion — consistent with a Medium-severity availability finding rather than a single-packet kill.

### Recommendation
Validate `t`/`n`/`i` via `ThresholdParams::new` *before* performing any `n`-proportional allocation or reads, and cap `n` at a protocol-meaningful bound (e.g., `MAX_KEY_SHARES_PER_SET`, as already done in `coordinator/src/tributary/transaction.rs:431`). Replace `Vec::with_capacity(usize::from(n))` with a plain `Vec::new()`/`push` loop so memory grows only as real input bytes are consumed, matching the chunked-read pattern used in `networks/ethereum/src/machine.rs:51-60`.

### Proof of Concept
```rust
// crypto/dkg/src/lib.rs - ThresholdKeys::read reachability PoC sketch
// Construct a malicious serialization for Ciphersuite C (e.g., Ristretto):
let mut buf = vec![];
buf.extend((C::ID.len() as u32).to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());        // t = 1 (plausible)
buf.extend(u16::MAX.to_le_bytes());    // n = 65535 (attacker-controlled)
buf.extend(1u16.to_le_bytes());        // i = 1
buf.push(0u8);                         // Interpolation::Constant
// No scalar bytes follow.
// ThresholdKeys::read::<&[u8]>(&mut buf.as_ref()) will:
//   1. Vec::with_capacity(65535)  -> ~2 MiB reserved before any byte check
//   2. fail on first read_F -> error, but allocation already performed
// Repeating this in a service loop forces repeated multi-MiB reservations
// and allocator churn from ~40-byte inputs.
assert!(ThresholdKeys::<C>::read(&mut buf.as_ref()).is_err()); // errors late, after allocating
```

Root cause confirmed: `n` is read and used for `with_capacity` and the `read_G` loop at `crypto/dkg/src/lib.rs:598-623`, while `ThresholdParams::new` validation only happens at `lib.rs:626`, after the resource expenditure.
