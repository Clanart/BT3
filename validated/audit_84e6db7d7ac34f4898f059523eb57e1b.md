### Title
Malicious `.gitmodules` `file://` URL can trigger local git-repository disclosure via re-enabled `protocol.file.allow` during submodule checkout - (File: `app/src/lib/git/submodule.ts`)

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  accepts an `allowFileProtocol` flag that, when `true`, passes `-c protocol.file.allow=always` to `git submodule update --init --recursive`. This directly re-enables the `file://` transport for submodule fetches, which is the exact protection upstream Git disabled by default (in response to the class of issue covered by GIT's CVE-2022-39253 fix) to stop repositories from cloning arbitrary local paths as "submodules." The function is invoked from `checkout.ts` [2](#0-1)  (7 references found), meaning some Desktop-driven checkout/branch-switch flows opt back into the vulnerable behavior.

### Finding Description
Git's submodule fetch machinery will honor whatever `url =` value is present in a cloned/fetched repository's `.gitmodules` file. Upstream Git hardened this in 2022 by refusing `file://`, `ext::`, and similarly local/command-execution-capable transports for submodules unless `protocol.file.allow` (or `protocol.ext.allow`) is explicitly set to `always`. Desktop's `updateSubmodulesAfterOperation` has a code path, gated only by a boolean `allowFileProtocol` argument, that unconditionally re-adds `-c protocol.file.allow=always` to the submodule-update invocation [3](#0-2) . If this flag is set to `true` for a checkout/branch-switch triggered on an untrusted, attacker-authored repository (e.g., after cloning or pulling a repo the user does not control), a `.gitmodules` entry such as `url = file:///Users/victim/some-other-private-repo` would cause Git to locally "clone" that path into the submodule directory of the checked-out repository — disclosing the contents of another local git repository (which could be a different private project, or contain credentials/config committed in that repo's history) into the attacker-authored repository's working tree. Because these disclosed files then live inside the user's working directory, a subsequent `git add`/commit/push by the user could silently exfiltrate that data to the attacker's remote.

### Impact Explanation
If reachable on a checkout of an untrusted repository, this breaks the invariant that opening/checking out a repository should not read files or repository contents from outside that repository's own remote. It matches the "valid impact" criteria: file read outside the repo, and potential silent corruption/exfiltration of what the user later commits and pushes, triggered purely by cloning/checking out an attacker-controlled repository — no local access, admin rights, or social engineering beyond normal repo browsing.

### Likelihood Explanation
Uncertain / not fully confirmed. I found the vulnerable primitive (`updateSubmodulesAfterOperation` re-enabling `protocol.file.allow=always`) but was unable, within the remaining tool budget, to read the full contents of `app/src/lib/git/checkout.ts` to confirm exactly when `allowFileProtocol=true` is passed — specifically, whether it is scoped to a safe context (e.g., only for repositories the user already trusts, or only for local test fixtures) or whether it applies broadly to checkouts of any cloned repository including freshly cloned/untrusted ones. This distinction determines whether the bug is exploitable by an unprivileged attacker-controlled repo or is an intentional, safely-scoped escape hatch. I could not verify this before running out of iterations.

### Recommendation
Confirm every call site of `updateSubmodulesAfterOperation` and `allowFileProtocol=true` in `app/src/lib/git/checkout.ts`; the flag should never be `true` for checkouts of repositories that were freshly cloned/fetched from an untrusted or attacker-influenceable source. If it is currently used for such flows, remove the `protocol.file.allow=always` override (or restrict `file://` submodule targets to paths inside the repository root) and rely on Git's default protocol restrictions for submodules originating from remote content.

### Proof of Concept
Not fully constructible without confirming the exact `checkout.ts` call sites; conceptually:
1. Attacker publishes a public repository containing a `.gitmodules` file with `url = file:///path/that/might/exist/on/victim`.
2. Victim clones/opens the repository in Desktop and performs a branch checkout that internally calls `updateSubmodulesAfterOperation(..., allowFileProtocol: true)`.
3. Git executes `submodule update --init --recursive` with `protocol.file.allow=always`, cloning the local path into the submodule directory, disclosing its contents inside the attacker's repository working tree.

Given the unresolved question about the exact trigger conditions in `checkout.ts`, this should be treated as a lead requiring code-level confirmation rather than a fully verified finding.
