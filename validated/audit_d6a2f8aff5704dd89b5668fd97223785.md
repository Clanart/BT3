### Title
Derived `Debug` on `EncryptionKeyProof` prints the ECDH shared decryption key, leaking secret-share plaintexts to logs - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
`EncryptionKeyProof<C>` derives `Debug` even though its `key` field is the secret ECDH shared point used to derive the ChaCha20 cipher that decrypts a DKG `SecretShare` message. Any `{:?}`/`Debug`-based logging of the proof (e.g., while preparing or handling a blame argument) emits the shared decryption key, the direct analog of Impala logging session secrets (CVE-2021-28131): a secret that must stay out of logs is formatted into them.

### Finding Description
`EncryptedMessage` ciphertexts are decrypted by computing `ecdh = msg.key * enc_key` and feeding it through `cipher()`, which builds a ChaCha20 keystream [1](#0-0) . `Encryption::decrypt` returns an `EncryptionKeyProof` whose `key` field is exactly that shared ECDH point, alongside a DLEq proof binding it [2](#0-1) .

`decrypt_with_proof` demonstrates the authority of this value: possession of `proof.key` alone is sufficient to run `cipher(context, &proof.key).apply_keystream(msg)` and recover the plaintext [3](#0-2) .

Despite holding this secret, the struct derives `Debug`, so `format!("{:?}", proof)` serializes `key` (a `Zeroizing<C::G>` whose `Debug` renders the encoded point) [4](#0-3) . Contrast with neighboring code, which carefully suppresses secrets: `SecretShare`'s `Debug` prints nothing, and `Encryption`'s manual `Debug` uses `finish_non_exhaustive()` to omit `enc_key` [5](#0-4) , [6](#0-5) . The `EncryptionKeyProof` derive is inconsistent with this secrecy discipline.

### Impact Explanation
Any party that obtains the `Debug` output of an `EncryptionKeyProof` — via application logs, error reports, or telemetry — can re-derive the ChaCha20 keystream and decrypt the corresponding `EncryptedMessage` carrying a threshold `SecretShare`, recovering that dealer's share of the group private key. Combined with other participants' shares (or used to decrypt *all* messages from that sender, since the blame mechanism reveals the per-sender ECDH key as noted in the comment at lines 84–90), this enables reconstruction of key material and unauthorized signing. It also undermines the blame protocol: the proof is meant to be revealed selectively to arbiters, not broadcast in routine logs.

### Likelihood Explanation
`EncryptionKeyProof` is produced on every `decrypt` call during PedPoP round 2 and is returned to the caller for potential blame use [7](#0-6) . Rust integrations routinely `Debug`-log return values and error contexts; because the type advertises `Debug`, nothing warns the integrator that it contains a secret. No attacker protocol action is required beyond triggering normal DKG traffic and reading exposed logs — matching the Impala threat model (an authenticated user with log access).

### Recommendation
Implement `fmt::Debug` manually for `EncryptionKeyProof` using `finish_non_exhaustive()` (printing only `dleq`, which is a public proof), or wrap `key` so its `Debug` is suppressed. Audit other derived-`Debug` types carrying secrets (`Decryption` prints only public keys and is fine; `EncryptedMessage` correctly lacks `Debug`).

### Proof of Concept
```rust
// After a normal PedPoP round-2 decrypt:
let (share, proof) = encryption.decrypt(&mut rng, &mut batch, id, from, msg.clone());
// Integrator logs the proof for observability / blame bookkeeping:
let leaked = format!("{:?}", proof); // contains hex/bytes of proof.key (ECDH shared point)

// An attacker with log access parses `key` out of `leaked` and re-runs:
let mut stolen = msg.msg.clone();
cipher::<C>(context, &Zeroizing::new(recovered_key_point))
  .apply_keystream(stolen.as_mut().as_mut());
// `stolen` is now the dealer's plaintext SecretShare — threshold share recovered.
```
This is enabled solely by the `#[derive(Debug)]` on `EncryptionKeyProof` [4](#0-3)  and the fact that `key` alone decrypts the message [8](#0-7) .

fn ecdh<C: Ciphersuite>(private: &Zeroizing<C::F>, public: C::G) -> Zeroizing<C::G> {
  Zeroizing::new(public * private.deref())
}

// Each ecdh must be distinct. Reuse of an ecdh for multiple ciphers will cause the messages to be
// leaked.
fn cipher<C: Ciphersuite>(context: [u8; 32], ecdh: &Zeroizing<C::G>) -> ChaCha20 {
  // Ideally, we'd box this transcript with ZAlloc, yet that's only possible on nightly
  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce
  // Use a static IV in acknowledgement of this
  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
  zeroize(key.as_mut());
  res
}
