### Title
Unbounded-depth JSON decoding in the `json` precompile (`extractAsBytes`/`extractAsBytesList`) can crash validator nodes via Go runtime stack-overflow - (File: precompiles/json/json.go)

### Summary
The `json` precompile's decode path calls `encoding/json.Unmarshal` directly on attacker-supplied calldata with no nesting-depth limit, mirroring the bug class in CVE-2021-46532 (a recursive-descent parser crashing the process via unbounded recursion), but reachable here from any Sei EVM transaction/call.

### Finding Description
`extractAsBytes` unmarshals `args[0]` (the raw calldata bytes passed to `extractAsBytes(bytes,string)`) directly into `map[string]gjson.RawMessage{}` via `gjson.Unmarshal`, where `gjson` is simply `encoding/json` [1](#0-0) [2](#0-1) . Go's standard `encoding/json` decoder is a recursive-descent parser with no configurable or built-in nesting-depth limit for arrays/objects: decoding a value like `[[[[[...]]]]]` nested tens of thousands of levels deep drives the decoder into a correspondingly deep call stack. Unlike an ordinary panic, a Go goroutine stack overflow is a fatal, unrecoverable runtime error (`runtime: goroutine stack exceeds ... - fatal error: stack overflow`) that `recover()` cannot catch, so it terminates the entire process.

By contrast, the codebase already recognizes and defends against exactly this bug class elsewhere:
- Protobuf `Any` unpacking enforces `MaxUnpackAnyRecursionDepth` [4](#0-3)  and `statefulUnpacker.UnpackAny` checks `r.maxDepth <= 0` before recursing [5](#0-4) .
- `unknownproto.rejectUnknownFieldsWithDepth` explicitly caps `MaxProtobufNestingDepth = 100` "to prevent stack overflow attacks" [6](#0-5) .
- `evmrpc/tracers.go`'s `validateMuxTraceConfig` enforces `maxMuxTracerNestingDepth` on caller-supplied nested JSON tracer configs [7](#0-6) .
- The ABI decode-gas walker in `precompiles/common/decode_cost.go` caps `maxDecodeWalkOps` specifically to bound a "hypothetical deeply-nested type" [8](#0-7) .

None of these depth guards apply to the `json` precompile's own `gjson.Unmarshal` calls, which decode fully unstructured attacker JSON with the stock `encoding/json` package and no depth cap.

### Impact Explanation
Any address can call `extractAsBytes`, `extractAsBytesList`, or `extractAsBytesFromArray` on the `json` precompile (`0x1003`) via a normal EVM transaction or `eth_call`, supplying a deeply nested JSON payload as the `bytes` argument. Because `chargeDecodeGas`/`GasCostPerByte` only charges gas linear in payload length before decode (not proportional to nesting depth) [9](#0-8) , a modestly sized but deeply nested payload (e.g., tens of thousands of `[` characters) is cheap under gas metering yet drives the Go json decoder to a stack depth that trips Go's stack-overflow guard. Since this is unrecoverable, it crashes the validator's `seid` process handling the transaction/query — every validator that executes the same transaction (deliver-tx path) or every full/RPC node that services the same `eth_call` would crash identically, which is a validator-halt / consensus-relevant DoS, not merely a single RPC node issue.

### Likelihood Explanation
Likelihood is high in principle: the payload is fully attacker-controlled EVM calldata, requires no special privileges, and the precompile is a well-known/public one at a fixed address that's part of Sei's documented precompile set [10](#0-9) . However, I could not directly execute or reproduce the exact stack depth needed to trigger Go's stack-overflow guard within this environment, so likelihood of *reliable* exploitation depends on unverified factors: the effective per-call gas limit vs. the bytes-per-nesting-level needed, whether `abi.Unpack`'s own length/size limits on the `bytes` argument cap total payload size below what's needed to reach fatal stack depth, and whether Go's default goroutine stack growth (up to ~1GB by default) is reachable before an out-of-gas/OOM condition intervenes first in this specific deployment. These are areas a background agent with test-execution capability should verify empirically.

### Recommendation
Wrap all JSON decode calls in the `json` precompile with an explicit nesting-depth guard before calling `encoding/json.Unmarshal` (e.g., a pre-scan that rejects payloads whose bracket/brace nesting exceeds a fixed maximum, similar to `MaxProtobufNestingDepth` in `sei-cosmos/codec/unknownproto/unknown_fields.go` or `maxMuxTracerNestingDepth` in `evmrpc/tracers.go`), and apply the same guard uniformly across the current and all legacy versions of the precompile (`precompiles/json/json.go` and each `precompiles/json/legacy/vXXX/json.go`). Charge gas proportional to nesting depth (not just byte length) so decode cost cannot be made artificially cheap relative to decoder work.

### Proof of Concept
Conceptual PoC (not executed/verified in this environment):
1. Construct calldata for `extractAsBytes(bytes,string)` where the `bytes` argument is a JSON value consisting of `N` nested arrays, e.g. `strings.Repeat("[", N) + strings.Repeat("]", N)` for a sufficiently large `N` (tens of thousands, depending on default goroutine stack size).
2. Submit this as calldata to the `json` precompile address `0x0000000000000000000000000000000000001003` via `eth_call` or a mined transaction.
3. `PrecompileExecutor.extractAsBytes` calls `gjson.Unmarshal(bz, &decoded)` on the payload [2](#0-1) , which is `encoding/json.Unmarshal`; the resulting recursive descent should exhaust the goroutine stack and crash the node with `fatal error: stack overflow` rather than a recoverable Go panic.

A background Devin agent with a running dev node should confirm the exact `N` required and whether gas/ABI size limits prevent reaching it before finalizing severity.
