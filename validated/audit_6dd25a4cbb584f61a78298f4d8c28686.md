### Title
`compound()` distributes the contract's full token balance instead of the caller's claimed delta - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound()` computes `receivedBalance` as `IERC20(_tokenAddress).balanceOf(address(this))` for every configured reward token after calling `multiclaimOnBehalf`, rather than measuring the delta produced by the caller's own claim. Any tokens already sitting on the contract — from dust left by prior partial distributions, rounding, or any other source — are paid out in full to whichever address calls `compound()` next, even if that caller supplies `_lps`/`_rewards` for pools where they hold no stake.

```solidity
function compound(...) external {
    uint256 rewardTokensLength = rewards.length;        
    IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender);
    ...
    for (uint256 i; i< rewardTokensLength; i++) {
        address _tokenAddress = rewards[i].tokenAddress;
        ...
        uint256 receivedBalance = IERC20(_tokenAddress).balanceOf(address(this));

        if (receivedBalance > 0) {
            ... // convert / lock / deposit / transfer receivedBalance to msg.sender
        }
    }
    emit Compounded(msg.sender, rewardTokensLength, _lockMgp);
}
```

`receivedBalance` is taken from the contract's total balance for every reward token in the `rewards` array (`rewardTokensLength` loop), not from any pre/post-call delta tied to `msg.sender`'s own `multiclaimOnBehalf` output. There is no snapshotting of balances before the claim and no restriction requiring `_lps`/`_rewards` to correspond to positions the caller actually holds. An attacker can call `compound()` with `_lps`/`_rewards` for pools they have zero stake in (or even empty arrays), and if any compoundable reward token balance is present on the contract at call time, the entire balance is routed to the attacker via `convertFor`, `lockFor`, `depositFor`, or `safeTransfer` — all keyed to `msg.sender`. No modifier, ownership check, or reward-index accounting reconciles `compoundableRewards[token]` against the actual amount attributable to the caller.

### Impact Explanation
This is a direct theft-of-funds vector: any leftover balance on the `ManualCompound` contract (e.g., dust from previous compounds, rewards sent by other users' claims that complete in the same transaction context, or tokens accidentally/incidentally transferred in) is fully claimable by an unprivileged caller who has no legitimate right to it. This matches Immunefi's "Direct theft of user funds" (Critical) impact class, since compounding is meant to be a self-service operation where a caller only receives value produced by their own claim.

### Likelihood Explanation
Exploitation requires no special privileges: any EOA can call `compound()` with arbitrary `_lps`/`_rewards` arrays for pools where it holds no stake. The only precondition is that a nonzero balance of a compoundable reward token exists on the contract when `compound()` is invoked — a state that can arise naturally (dust, rounding remainders from prior compounds, or race conditions where multiple compounds are pending) or be induced by front-running another user's compound transaction. This makes the bug fully unprivileged, repeatable, and low-capital to exploit.

### Recommendation
Snapshot each reward token's balance before calling `multiclaimOnBehalf`, and after the call compute `receivedBalance` as the post-call balance minus the pre-call snapshot (the delta attributable to this call), rather than using the raw `balanceOf(address(this))`. Additionally, validate that `_lps`/`_rewards` correspond to pools where `msg.sender` actually holds a stake (e.g., via `IMasterMagpie` accounting) before processing claims on their behalf.

### Proof of Concept
Hardhat/Foundry test plan:
1. Deploy `ManualCompound` with a mock `masterMagpie` whose `multiclaimOnBehalf` is a no-op (or claims 0 for arbitrary `_lps`).
2. Add a compoundable reward token via `addReward`.
3. Pre-seed the `ManualCompound` contract with a nonzero balance of that reward token directly (simulating dust/leftover funds), e.g. via `token.transfer(manualCompound, 100e18)`.
4. From an attacker account with no stake in `masterMagpie`, call `compound(_lps, _rewards, 0, 0, false)` where `_lps`/`_rewards` reference pools the attacker never staked in.
5. Assert that the attacker's balance of the reward token increases by the full pre-seeded amount (100e18), despite `multiclaimOnBehalf` returning/claiming zero for the attacker.
6. Assert this violates the invariant that `compoundableRewards[token]` accounting should reconcile only with value the caller's own claim produced — i.e., the caller received funds not tied to `rewards[i].tokenAddress` claims from their own stake.
