### Title
No minimum-value check on spent inputs lets dust outputs be reported as funds and burned on fees - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` enforces a minimum value (`DUST = 546`) on *payments* but performs no equivalent check on the *inputs* it consumes. `Scanner::scan_transaction` reports any output paying a registered script as a `ReceivedOutput` regardless of amount. An unprivileged party can therefore send dust (or otherwise uneconomical) outputs to a known Serai address; those outputs are reported as received funds, and when the multisig later spends them the fee cost of the extra input exceeds the value recovered, causing a net loss of escrowed funds. This is the Serai analog of the reported bug class: a value-bearing entry point accepts user-supplied amounts with no minimum/fee-viability validation, so economically stuck/loss-making funds are processed.

### Finding Description
In `SignableTransaction::new`, each payment is validated against the dust threshold:

```rust
for (_, amount) in payments {
  if *amount < DUST {
    Err(TransactionError::DustPayment)?;
  }
}
``` [1](#0-0) 

However, the inputs are summed and accepted unconditionally:

```rust
let input_sat = inputs.iter().map(|input| input.output.value.to_sat()).sum::<u64>();
``` [2](#0-1) 

There is no check that an input's value exceeds `DUST` or exceeds the marginal fee cost of adding a ~58-vbyte Taproot key-spend input (per the weight model in `calculate_weight_vbytes`, which counts each input as a fixed-size TXIN plus a 64-byte witness signature). [3](#0-2) 

On the receive side, `Scanner::scan_transaction` pushes a `ReceivedOutput` for every output whose `script_pubkey` matches a registered script, with no amount filtering:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { ... });
}
``` [4](#0-3) 

Any external party who learns a Serai deposit/branch script (publicly visible on-chain once used) can send arbitrarily small outputs to it. The scanner reports them as received value, and `SignableTransaction::new` will happily spend them, paying more in incremental fee than they contribute.

### Impact Explanation
- Funds are reported received that are not economically spendable: each dust input added increases `needed_fee` by `fee_per_vbyte * ~58` vbytes while contributing less than `DUST` (546 sat) or, for very small outputs, less than the marginal fee itself. The difference is burned from other escrowed inputs/change, a direct net loss attributable to threshold-signed transactions.
- In the extreme, an attacker can fill the input set with dust up to `MAX_STANDARD_TX_WEIGHT`, inflating `needed_fee` while contributing almost nothing, degrading every subsequent spend until outputs are curated off-line.
- This mirrors the reported bug: a missing lower-bound/`msg.value`-style validation on a value-bearing interface lets a peer cause funds to be committed in a way that loses or locks value. Here the lock/loss is realized as fee burn rather than stuck L1→L2 messages.

### Likelihood Explanation
Likelihood is moderate-to-low but real. It requires only that an observer send dust to an already-known Serai script — no key material, no validator collusion, no RPC access. Whether the loss is automatic depends on the coordinator including scanned outputs without value curation; the in-scope wallet itself provides no defense or warning (`ReceivedOutput` does not even expose a viability check; `value()` is informational only). Medium severity: bounded per-transaction loss, but repeatable and attacker-initiated.

### Recommendation
- Reject or quarantine inputs below a viability threshold in `SignableTransaction::new` (e.g., require `input.value >= DUST` and `input.value >= fee_per_vbyte * marginal_input_vbytes`), returning a new `TransactionError` variant rather than silently spending them.
- Optionally have `Scanner` expose the dust threshold or annotate `ReceivedOutput`s flagged as uneconomical so callers can exclude them.
- Document that consolidating sub-dust inputs always costs more than it recovers.

### Proof of Concept
Conceptual, using the public API in `networks/bitcoin/src/wallet/`:

```rust
// Attacker sends a 1-sat output to the Serai P2TR script (publicly known on-chain).
// Scanner reports it as received:
let outputs = scanner.scan_transaction(&attacker_dust_tx);
assert_eq!(outputs[0].value(), 1); // no minimum check performed

// Coordinator builds a spend including that dust input:
let mut inputs = vec![legit_output];          // e.g. 100_000 sat
inputs.push(outputs[0].clone());              // 1-sat dust input

// SignableTransaction::new accepts it — only payments are dust-checked, not inputs.
let tx = SignableTransaction::new(inputs, &payments, Some(change), None, fee_rate).unwrap();

// needed_fee now includes ~58 vbytes * fee_rate for the dust input,
// which exceeds the 1 sat it contributes. The delta is taken from
// the escrowed funds via reduced change — a net loss signed by the multisig.
assert!(tx.needed_fee() > fee_rate * vbytes_without_dust_input);
```

Root cause: `SignableTransaction::new` validates `payments` against `DUST` at lines 165-169 while `inputs` are summed unconditionally at line 175, and `Scanner::scan_transaction` (wallet/mod.rs lines 199-214) admits outputs of any value.
