## Title
Partial commit/discard staging trusts a stale line-selection bitmap against a freshly re-fetched diff, allowing silent inclusion/exclusion of unreviewed content - (File: `app/src/lib/git/apply.ts`)

### Summary
The Kubernetes report's underlying flaw is that a security decision (an admission check) was made by comparing a "new" value against a supposed "old" value, but the "old" value handed to the validator was not actually the prior state — it was silently aliased to the new state, so any code trusting that old/new diff made the wrong decision without any error being raised. `GitHub Desktop`'s partial-commit staging path has the structurally identical flaw: it builds a line-selection bitmap against one diff (the one rendered to the user), then re-fetches a brand-new diff at apply time and blindly re-uses that bitmap's line indices against the new hunk layout, with no revalidation that the indices still refer to the same content.

### Finding Description
When a user selects individual lines/hunks to commit or discard, the UI computes a `DiffSelection` bitmap (`file.selection`) whose entries are keyed by absolute line index into a specific `ITextDiff` (`hunk.unifiedDiffStart + lineIndex`), as seen throughout `app/src/lib/patch-formatter.ts` (`formatPatch`, lines 132-232) and `app/src/ui/diff/side-by-side-diff.tsx` (`onLineNumberCheckedChanged`, lines 935-961).

The staging code path (`stageFiles` → `applyPatchToIndex`) does **not** reuse the diff the user reviewed. Instead, `applyPatchToIndex` fetches a completely new diff from disk right before formatting the patch: [1](#0-0) 

The retrieved `diff` here can differ from the diff that produced `file.selection` if the working-tree file changed in between (e.g. a background operation, an auto-formatter, an `fsmonitor`/hook-driven mutation, or any process writing to the tracked file while the commit dialog is open). `formatPatch` then walks the **new** diff's hunks and asks `file.selection.isSelected(absoluteIndex)` (`app/src/lib/patch-formatter.ts:143-157`) — but those `absoluteIndex` values were only meaningful relative to the **old** hunk layout. If hunks shift (lines added/removed elsewhere in the file), the same index now points at different diff content.

Critically, the codebase already contains a guard for exactly this staleness scenario — but only in the UI presentation layer, not in the actual git-apply path used for staging/committing: [2](#0-1) 

That reconciliation (`withSelectableLines`) only runs when the UI reloads a diff for display. It is never invoked again immediately before `stageFiles`/`applyPatchToIndex` builds the actual patch that is applied with `git apply --cached`, so the "old vs new" diff mismatch that the UI code explicitly anticipates and defends against is left completely unguarded on the actual staging path — the same pattern as the H1 report, where a defense that looked like it covered "old vs new" comparisons didn't actually cover the code path that mattered.

### Impact Explanation
This can silently corrupt what the user commits: a line the user explicitly deselected (e.g., a secret, a debug statement, or a partial fix they didn't want to include) can be staged and committed anyway, or conversely a change the user intended to include can be silently dropped — with `git apply --cached` succeeding without any warning to the user, because `--unidiff-zero` lets git apply hunks based on line offsets rather than content matching. This is committing/pushing content the user never actually approved, matching "silent corruption of what the user commits or pushes."

### Likelihood Explanation
Reaching the mismatch requires the working-tree file to change between the moment the user's line selection was computed (based on a displayed diff) and the moment `applyPatchToIndex` re-fetches the diff at commit/discard time. Desktop performs numerous background operations on repositories (fetch, status refresh, file-system watching) and users routinely have editors/build tools/linters actively writing to files while the commit dialog remains open with a stale selection, making this a realistically triggerable race rather than a purely theoretical one. The `app-store.ts` staleness-remediation code demonstrates that the Desktop team is aware this race exists for the UI selection state, but the fix was not threaded through to the actual staging code.

### Recommendation
Before calling `formatPatch`/`formatPatchToDiscardChanges` in `applyPatchToIndex` and its discard-changes equivalent, re-validate (or recompute) the selection bitmap against the freshly-fetched diff — reusing the same `withSelectableLines`-style reconciliation that `app-store.ts` already performs for the UI — and abort/re-prompt the user if the diff has materially changed (e.g., compare a content hash or hunk signature captured at selection time) rather than blindly applying stale line indices to a new hunk layout.

### Proof of Concept
1. Open a file with multiple hunks in Desktop's Changes view and deselect one specific added line (e.g. an added debug `console.log`) while keeping the rest selected, producing a `DiffSelection` bitmap tied to the currently displayed diff.
2. Before clicking "Commit", have an external process (editor auto-save, linter/formatter with `--fix`, or any script touching the tracked file) insert or remove lines earlier in the file, shifting hunk boundaries — without Desktop re-rendering the diff view in time.
3. Click "Commit". `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) fetches the new diff via `getWorkingDirectoryDiff`, then `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) applies the old `file.selection` bitmap against the new hunk indices.
4. Inspect the resulting commit: the previously deselected line (or an unrelated line that now occupies that index) is included/excluded contrary to what the user last saw and intended, with no error or warning surfaced by `git apply --cached`.
