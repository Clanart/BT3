### Title
Payout OP_RETURN (and hence bridge-circuit `deposit_constant`/`journal_hash`) is malleable under `SinglePlusAnyoneCanPay`, letting an attacker frame/disprove the honest fronting operator - ([File: circuits-lib/src/bridge_circuit/mod.rs])

### Summary
The user's withdrawal signature for the `payout_tx` is required to use `TapSighashType::SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:182`), which commits only to input 0 and the matching output 0 (the user payment), leaving every other input and output - including the operator-identifying `OP_RETURN` at output index 2 - unsigned and freely replaceable. An attacker can therefore take the honest operator's broadcast, unconfirmed `payout_tx`, reuse the signed input/witness and the user-payment output, and mine a variant with a different `OP_RETURN` operator key. This corrupts `deposit_constant`/`journal_hash` computed by `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:206-244`) and by the host (`bridge-circuit-host/src/structs.rs:482-516`), causing the honest operator's own kickoff assertions to mismatch the verifier's independently-computed `deposit_constant` (which is keyed on `kickoff_data.operator_xonly_pk`, `core/src/verifier.rs:2478-2486`), leading to a successful `Disprove` and collateral burn against the honest operator.

### Finding Description
Binding claimed and broken: `deposit_constant(operator_xonlypk_from_mined_payout_OP_RETURN, ...) == deposit_constant(kickoff_data.operator_xonly_pk, ...)` for the operator that actually fronted the payout.

Trace:
1. `create_payout_txhandler` (`core/src/builder/transaction/operator_reimburse.rs:407-436`) builds a tx with input 0 = user's withdrawal UTXO (key-spend), output 0 = user payment, output 1 = anchor, output 2 = `OP_RETURN(move_txid || operator_xonly_pk)`.
2. The user's signature over input 0 is enforced to be `SinglePlusAnyoneCanPay` (`core/src/rpc/parser/operator.rs:174-187`, and verified the same way in `Operator::withdraw`, `core/src/operator.rs:630-637`). This sighash type commits only to input 0 and output 0; ANYONECANPAY leaves other inputs unauthenticated and SINGLE leaves outputs 1..n unauthenticated.
3. Once the honest operator broadcasts this tx (funded via `fund_raw_transaction`, unconfirmed), the input-0 witness is public in the mempool. An attacker can construct a conflicting/double-spend transaction: same input 0 at the same index with the same witness, same output 0, but attacker's own funding inputs and an attacker-chosen `OP_RETURN` (e.g. naming a different operator or garbage), and get this variant mined instead (ordinary fee/RBF competition, well within attacker capabilities).
4. `bridge_circuit` (`circuits-lib/src/bridge_circuit/mod.rs:206-229`) and the host (`bridge-circuit-host/src/structs.rs:485-515`) read `operator_xonlypk` straight from `get_first_op_return_output`/`parse_op_return_data` on whatever payout tx is canonical, and fold it into `deposit_constant` and then `journal_hash` (`mod.rs:634-684`).
5. Independently, verifiers precompute the "expected" `deposit_constant` from `kickoff_data.operator_xonly_pk` (`core/src/verifier.rs:2478-2486`), which is fixed to the honest operator's real identity from the kickoff transaction, and use it inside the additional-disprove script.
6. Because the mined payout tx's `OP_RETURN` was attacker-rewritten, the honest operator's own assertions (built from the corrupted on-chain OP_RETURN data) can no longer match the verifiers' independently-derived `deposit_constant`, and `verify_additional_disprove_conditions`/`send_disprove_tx_additional` (`core/src/verifier.rs:2420-2757`) succeeds in disproving the honest operator even though they truly funded the payout.

Existing guards do not prevent this: `assert_eq!` on `payout_input_index`/vout only checks the withdrawal outpoint/index match, not who signed the OP_RETURN; SPV verification only proves the (already-attacker-shaped) transaction is in the canonical chain; nothing binds the `OP_RETURN` content to the input-0 signature because of the chosen sighash flag.

### Impact Explanation
An honest operator that legitimately fronts a withdrawal payout can have their kickoff `Disprove`d and their collateral burned, purely because an unprivileged attacker rewrote the unsigned `OP_RETURN` byte range of the mined payout transaction before confirmation. This is repeatable per withdrawal/operator and requires no privileged role, key compromise, or majority hashrate - only the ability to broadcast a competing Bitcoin transaction with sufficient fee. This matches the Critical category "an honest operator's collateral burned" / "a true claim made unprovable."

### Likelihood Explanation
Preconditions: an operator's `payout_tx` must be visible unconfirmed in the mempool (normal operation, since it's funded/broadcast by the operator's own node) and the attacker must win the fee race for the conflicting/double-spend transaction reusing the same signed input. Attacker cost is limited to the funding inputs/fees needed to get their variant mined (bounded, feasible, and explicitly within the stated attacker capabilities: choosing a Schnorr signature/sighash flag and an `OP_RETURN`). No mainnet hashrate majority or protocol collusion is required.

### Recommendation
Require the withdrawal/payout signature to use a sighash type that commits to the entire transaction (e.g. `SIGHASH_ALL`, or at minimum extend commitment to cover the `OP_RETURN` output and all inputs), or otherwise bind the operator identity to data that is authenticated by the withdrawal signature rather than reading it from an unsigned `OP_RETURN` output.
