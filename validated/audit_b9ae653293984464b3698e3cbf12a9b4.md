### Title
Hardcoded zero slippage in `SmartWomConvert._convertFor()` swap enables sandwich attack against `ArbWomUp3.incentiveDeposit()` users - ([File: wombat/SmartWomConvert.sol], [File: wombat/ArbWomUp3.sol])

### Summary
`ArbWomUp3.incentiveDeposit()` (mode 2) lets any unprivileged wallet convert WOM into locked mWOM via `SmartWomConvert.convert()`, but it hardcodes the swap's minimum-received parameter to `0`, removing all slippage protection for the AMM leg of the conversion. An attacker can sandwich the underlying Wombat pool swap to force the user's buyback leg to return close to zero mWom, permanently reducing the amount locked on the user's behalf while the attacker extracts the difference.

### Finding Description
`ArbWomUp3._deposit()` mode 2 branch calls: [1](#0-0) 
```
IERC20(wom).safeApprove(smartWomConvert, toSwap);
IConverter(smartWomConvert).convert(toSwap, _convertRatio, 0, 0);
```
The third argument, `_minRec`, is hardcoded to `0`. This is reachable from the unprivileged, external entry point `incentiveDeposit()`: [2](#0-1) 

Inside `SmartWomConvert._convertFor()`, the `_minRec` parameter is only checked *after* the swap has already executed, and the swap itself is always called with a hardcoded `0` minimum-out: [3](#0-2) 
```
amountRec = IWombatRouter(router).swapExactTokensForTokens(
    tokenPath, poolPath, buybackAmount, 0, address(this), block.timestamp
);
...
if (convertAmount + amountRec < _minRec)
    revert MinRecNotMatch();
```
When `_minRec` is genuinely supplied by an end user calling `SmartWomConvert.convert()` directly, a post-swap revert at least reverts the whole transaction (including the swap) if the result is too low, providing atomic protection. However, when `ArbWomUp3` calls `convert(toSwap, _convertRatio, 0, 0)` with `_minRec` hardcoded to `0`, the post-swap check `convertAmount + amountRec < 0` can never fail, so **there is no protection at all** for the WOM→mWOM buyback swap executed via the `womMWomPool`.

An attacker observing a pending `incentiveDeposit(_amount, _convertRatio, _bullMode, 2)` transaction in the mempool can:
1. Front-run with a large swap that skews the `womMWomPool` price against the pending buyback swap.
2. Let the victim's transaction execute — `IWombatRouter.swapExactTokensForTokens` will accept virtually any output because `amountOutMin = 0`.
3. Back-run to restore the pool price, capturing the value the victim swap gave up.

The result: the victim's WOM is transferred out, but the mWOM lock amount (`ILocker(mWomSV).lockFor(mWomBal, _account)`) reflects a sandwiched, near-zero buyback output, causing a permanent, direct loss of user funds.

### Impact Explanation
This is a direct theft of user funds during an unprivileged, standard deposit flow (`incentiveDeposit`), with the loss realized as reduced mWOM locked for the victim and extracted value captured by the attacker via the sandwich. This matches the "concrete direct theft of user funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires mempool visibility and a two-sided swap around the `womMWomPool`/Wombat DEX pool (public, permissionless), and depends on pool depth/liquidity to determine profitability, similar to the referenced report's low-likelihood/high-impact classification of price-based sandwich attacks.

### Recommendation
Do not hardcode `_minRec` to `0` in `ArbWomUp3._deposit()`. Either compute an on-chain slippage-safe minimum before calling `convert()`, or propagate a user-supplied `_minMWomRec` parameter through `incentiveDeposit()` into the `convert()` call. Additionally, in `SmartWomConvert._convertFor()`, pass a real minimum-out value (derived from `_minRec` and the split ratio) into `swapExactTokensForTokens` rather than hardcoding `0`, so that if the swap itself would return too little, it fails atomically rather than relying solely on a post-hoc balance check.

### Proof of Concept
1. Attacker monitors mempool for `ArbWomUp3.incentiveDeposit(amount, convertRatio, bullMode, 2)` transactions.
2. Attacker front-runs by swapping a large amount of WOM for mWOM (or vice versa) on the `womMWomPool` used by `SmartWomConvert`, moving the price unfavorably for the pending buyback swap.
3. Victim's transaction executes: `_deposit` mode 2 calls `smartWomConvert.convert(toSwap, _convertRatio, 0, 0)`. Inside, `swapExactTokensForTokens(... buybackAmount, 0, ...)` executes with `amountOutMin = 0`, accepting a heavily reduced `amountRec`.
4. Check `convertAmount + amountRec < 0` never reverts (since `_minRec` is `0`), so the reduced `mWomBal` is locked for the victim via `mWomSV.lockFor(mWomBal, _account)`.
5. Attacker back-runs to reverse their initial swap, capturing the value taken from the victim's buyback. [4](#0-3) [5](#0-4)
