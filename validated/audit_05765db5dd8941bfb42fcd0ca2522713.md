Confirmed: `werc20.Precompile` embeds `*erc20.Precompile` [1](#0-0)  and its `Execute` dispatches non-deposit/withdraw calls straight to the inherited `HandleMethod`/`transfer` logic [2](#0-1) , unlike the plain ERC20 precompile, which explicitly rejects any call carrying `contract.Value() > 0` before dispatch [3](#0-2) . The `Transfer`/`TransferFrom`/`Approve` handlers never look at `contract.Value()` — they only move the ERC20-represented coin via `banktypes.NewMsgSend` [4](#0-3) .

### Title
WERC20 precompile permanently locks native value sent alongside non-deposit ERC20 calls (`transfer`/`transferFrom`/`approve`) - (File: precompiles/werc20/werc20.go)

### Summary
The WERC20 precompile's `Execute` only special-cases native `msg.value` for the `deposit`/fallback/receive path, where `Deposit()` immediately forwards the received value back to the caller via `BankKeeper.SendCoins` [5](#0-4) . For every other selector (`transfer`, `transferFrom`, `approve`, view methods), execution falls through to `p.HandleMethod`, inherited unmodified from the base ERC20 precompile [6](#0-5) , none of which check or refund `contract.Value()`. This mirrors the reported `bridgeRingToAbstract()` bug class exactly: a value-accepting entrypoint has an execution branch that completes successfully while silently discarding attached value with no refund and no recovery mechanism.

### Finding Description
When an EVM `CALL` targets a precompile address with non-zero `value`, the geth EVM core (via `evm.Call`) unconditionally transfers that value from caller to the precompile's account in the `StateDB` *before* invoking `Run`. For the plain ERC20 precompile this is explicitly guarded against: `Execute` reverts any call carrying value with `ErrCannotReceiveFunds`, and the comment states this is "a safety measure because currently funds cannot be received due to the lack of a fallback handler" [7](#0-6) .

The WERC20 precompile removes/bypasses that safety check for its `Execute` implementation. Only `deposit`/`fallback`/`receive` route through `Deposit()`, which relies on `contract.Value()` to know how much native coin to `SendCoins` back to the caller [8](#0-7) . Any other selector — e.g. `transfer(address,uint256)` called with `msg.value > 0` — routes to `p.HandleMethod` → `Transfer`/`transfer`, which only performs the bank `MsgSend` for the ERC20-denominated coin and never touches `contract.Value()` [9](#0-8) .

Because the EVM has already credited that native value to the precompile's `StateDB` balance as part of the `CALL` opcode, and the `BalanceHandler` only reconciles bank-emitted `CoinSpent`/`CoinReceived` events for actions the Go code actually performs [10](#0-9) , no bank-side compensating transfer ever occurs for the "silently accepted" value. The end state is: the precompile's on-chain account (module-owned, not an EOA, with — per the ERC20 comment — "no fallback handler" and no withdrawal path) permanently retains the native coin balance corresponding to the attached `msg.value`, with no mechanism in the WERC20/ERC20/bank code to recover it for the user.

This is the direct structural analog of the reported issue: a payable-like surface accepts value, has a legitimate non-revert execution path unrelated to consuming that value, and the value becomes permanently unrecoverable.

### Impact Explanation
This is a Critical, unprivileged-user-triggerable **permanent freezing/locking of user funds**. Any unprivileged EOA or contract that calls `transfer`, `transferFrom`, or `approve` on a WERC20 token-pair precompile address while attaching native `msg.value` (a mistake analogous to the exact scenario in the report — e.g., wallet/dApp tooling that defaults to attaching value, or a user copying a `deposit{value: x}()` pattern onto a different selector) will have that value irrecoverably stuck in the precompile's account, since precompile accounts have no owner key, no code, and no withdrawal entrypoint that references received-but-unaccounted value. This directly matches the required impact: "permanent freezing, locking ... of user funds ... via ordinary transaction ... flow."

### Likelihood Explanation
Likelihood is moderate-to-high: WERC20 precompiles are meant to be interacted with by ordinary wallets/dApps expecting WETH-like semantics, where sending value to *any* function of the wrapped-token contract is a common (if mistaken) pattern from users used to plain `IWERC20`/`WETH` ABIs. The vulnerability requires no special conditions, only an ordinary EVM transaction with an ERC20-transfer selector and non-zero value, both fully attacker/user controlled.

### Recommendation
Reinstate the same guard used in the base ERC20 precompile at the top of `werc20.Execute`, but scoped to only allow value for `deposit`/fallback/receive selectors: reject (revert) any call to `transfer`, `transferFrom`, `approve`, or any query method that carries `contract.Value() > 0`, e.g.:
```go
if method.Type != abi.Fallback && method.Type != abi.Receive && method.Name != DepositMethod {
    if contract.Value().Sign() == 1 {
        return nil, fmt.Errorf(cmn.ErrCannotReceiveFunds, contract.Value().String())
    }
}
```
placed before the `switch` in `precompiles/werc20/werc20.go`'s `Execute`.

### Proof of Concept
1. Deploy/identify a WERC20 precompile instance backing a registered token pair (address per `x/erc20` `TokenPair` registry).
2. From an unprivileged EOA, craft an EVM transaction: `to = <WERC20 precompile address>`, `value = 1 ether`, `data = abi.encodeWithSelector(transfer.selector, someRecipient, 0)` (amount can be 0 or any amount the caller holds).
3. Submit the transaction. It succeeds: the ERC20 `transfer` logic executes the bank `MsgSend` for the (possibly zero) token amount, but the 1 ether native value transferred by the EVM `CALL` opcode into the precompile's account is never returned or accounted for.
4. Query the precompile address's native balance (`eth_getBalance`) before and after: it increases by exactly the attached value, with no code path in `werc20`/`erc20`/`bank` capable of transferring it back out — the funds are permanently locked.

*Note: This was traced via static code review of `precompiles/werc20` and `precompiles/erc20`; I was not able to execute the integration test suite to empirically confirm the exact `StateDB`/bank balance divergence at runtime, so the PoC above should be validated with a live/integration-test run before treating this as fully confirmed.*

func (p Precompile) Execute(ctx sdk.Context, stateDB vm.StateDB, contract *vm.Contract, readOnly bool) ([]byte, error) {
	method, args, err := cmn.SetupABI(p.ABI, contract, readOnly, p.IsTransaction)
	if err != nil {
		return nil, err
	}

	var bz []byte

	switch {
	case method.Type == abi.Fallback,
		method.Type == abi.Receive,
		method.Name == DepositMethod:
		bz, err = p.Deposit(ctx, contract, stateDB)
	case method.Name == WithdrawMethod:
		bz, err = p.Withdraw(ctx, contract, stateDB, args)
	default:
		// ERC20 transactions and queries
		bz, err = p.HandleMethod(ctx, contract, stateDB, method, args)
	}

	return bz, err
}

// HandleMethod handles the execution of each of the ERC-20 methods.
func (p *Precompile) HandleMethod(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
	method *abi.Method,
	args []interface{},
) (bz []byte, err error) {
	switch method.Name {
	// ERC-20 transactions
	case TransferMethod:
		bz, err = p.Transfer(ctx, contract, stateDB, method, args)
	case TransferFromMethod:
		bz, err = p.TransferFrom(ctx, contract, stateDB, method, args)
	case ApproveMethod:
		bz, err = p.Approve(ctx, contract, stateDB, method, args)
	// ERC-20 queries
	case NameMethod:
		bz, err = p.Name(ctx, contract, stateDB, method, args)
	case SymbolMethod:
		bz, err = p.Symbol(ctx, contract, stateDB, method, args)
	case DecimalsMethod:
		bz, err = p.Decimals(ctx, contract, stateDB, method, args)
	case TotalSupplyMethod:
		bz, err = p.TotalSupply(ctx, contract, stateDB, method, args)
	case BalanceOfMethod:
		bz, err = p.BalanceOf(ctx, contract, stateDB, method, args)
	case AllowanceMethod:
		bz, err = p.Allowance(ctx, contract, stateDB, method, args)
	default:
		return nil, fmt.Errorf(cmn.ErrUnknownMethod, method.Name)
	}

	return bz, err
}

func (p Precompile) Deposit(
	ctx sdk.Context,
	contract *vm.Contract,
	stateDB vm.StateDB,
) ([]byte, error) {
	caller := contract.Caller()
	depositedAmount := contract.Value()

	callerAccAddress := sdk.AccAddress(caller.Bytes())
	precompileAccAddr := sdk.AccAddress(p.Address().Bytes())

	// Send the coins back to the sender
	if err := p.BankKeeper.SendCoins(
		ctx,
		precompileAccAddr,
		callerAccAddress,
		sdk.NewCoins(sdk.Coin{
			Denom:  evmtypes.GetEVMCoinExtendedDenom(),
			Amount: math.NewIntFromBigInt(depositedAmount.ToBig()),
		}),
	); err != nil {
		return nil, err
	}

	if err := p.EmitDepositEvent(ctx, stateDB, caller, depositedAmount.ToBig()); err != nil {
		return nil, err
	}

	return nil, nil
}

	for _, event := range events[bh.prevEventsLen:] {
		switch event.Type {
		case banktypes.EventTypeCoinSpent:
			spenderAddr, err := ParseAddress(event, banktypes.AttributeKeySpender)
			if err != nil {
				return fmt.Errorf("failed to parse spender address from event %q: %w", banktypes.EventTypeCoinSpent, err)

				// Bypass blocked addresses
				continue
			}

				return fmt.Errorf("failed to parse amount from event %q: %w", banktypes.EventTypeCoinSpent, err)
			}
