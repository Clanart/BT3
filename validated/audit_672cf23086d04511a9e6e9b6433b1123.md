### Title
Silent remote URL rewrite to an attacker-controlled host via unpinned `clone_url` from GitHub API - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
`updateRemoteUrl()` automatically rewrites a repository's local `origin` remote URL whenever the GitHub API's `clone_url` for that repository differs from what's currently configured, but it never verifies that the new URL still points at the same host (or even the same repository identity) as the one the user originally trusted. It only checks that the *protocol* matches and that the *existing* remote hasn't been manually changed by the user. This mirrors the referral-code bug's root cause: a value (`referralCode` / `remote.url`) is trusted in one place, while a separate, independently-sourced value (`storageRefCode` / `apiRepo.clone_url`) silently overrides it in another function, without validating that the override is consistent with the original invariant.

### Finding Description
`updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts` performs: [1](#0-0) 

The only gating conditions before calling `gitStore.setRemoteURL(...)` are:
1. `protocolsMatch` — both URLs use the same scheme (e.g. both `https:`).
2. `remoteUrlUnchanged` — the *current* remote still matches the *previously cached* `gitHubRepository.cloneURL` (i.e., the user hasn't manually edited the remote).
3. `!urlsMatch` — the new API-provided `clone_url` differs from the current remote.

None of these conditions requires that the **hostname** of the new `clone_url` matches the hostname of the existing remote. `urlMatchesRemote` (used to compute `urlsMatch`) does compare hostnames, but that comparison is used to decide whether an update is *needed* (it's true when they *don't* match), not to reject the update. `parseRemote`/`urlMatchesRemote` in `app/src/lib/repository-matching.ts` never gets called in a way that constrains the destination host: [2](#0-1) 

So if `apiRepo.clone_url` — a value sourced from the GitHub API response (attacker-controllable via a compromised/malicious GitHub Enterprise Server endpoint, or any response the app treats as an "API object" per the task's threat model) — points to a completely different host, e.g. `https://evil.example.com/attacker/repo.git`, and the local remote hasn't been manually edited, Desktop will silently execute `git remote set-url origin https://evil.example.com/attacker/repo.git` on the user's behalf.

### Impact Explanation
This causes silent corruption of what the user pushes: subsequent `git push`/`git fetch` operations initiated from Desktop's UI (which use `remote.url` for all git operations, e.g. `push()` in `app/src/lib/git/push.ts` and `envForRemoteOperation(remote.url)`) will silently target the attacker-controlled host instead of the user's real GitHub repository, without any confirmation dialog or visible warning. This matches the task's valid-impact category of "git remote/proxy response... result is... silent corruption of what the user commits or pushes," and could also facilitate credential prompts against the attacker's host during subsequent git network operations.

### Likelihood Explanation
The trigger path requires the app to fetch repository metadata from a GitHub API endpoint (dotcom or, more plausibly, a GitHub Enterprise Server the user has configured) that returns an attacker-influenced `clone_url` field, and for the user's local remote to not have been manually customized since the last cached `cloneURL`. Given Desktop refreshes repository metadata routinely (e.g. after fetches, on repository selection) and calls this update path automatically, the precondition of "local remote unchanged" is the common case for most users who never hand-edit remotes. The barrier is control over the API response content, which is plausible for a rogue/compromised GHES instance or any endpoint whose API responses aren't fully origin-pinned.

### Recommendation
In `updateRemoteUrl`, in addition to `protocolsMatch`, require that the hostname of `updatedRemoteUrl` matches the hostname of the current `remoteUrl` (and/or the account's configured API endpoint host) before calling `gitStore.setRemoteURL`. If the hostnames differ, treat this as a repository migration event that should be surfaced to the user for explicit confirmation rather than applied silently — consistent with the referral-code fix pattern of validating the authoritative source before use rather than silently substituting it.

### Proof of Concept
1. User has GitHub Desktop configured against a GitHub Enterprise Server account, with `origin` = `https://ghe.company.com/org/repo.git`, matching the cached `gitHubRepository.cloneURL`.
2. The GHE instance (compromised, or an attacker with request/response tampering capability against that specific endpoint) returns an API repository payload where `clone_url` = `https://evil.example.com/org/repo.git`, keeping the same `https:` protocol.
3. Desktop calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)`:
   - `protocolsMatch` → true (`https:` === `https:`)
   - `remoteUrlUnchanged` → true (user never manually edited origin)
   - `urlsMatch` → false (hostnames differ: `ghe.company.com` vs `evil.example.com`)
4. The condition `protocolsMatch && remoteUrlUnchanged && !urlsMatch` is satisfied, so `gitStore.setRemoteURL('origin', 'https://evil.example.com/org/repo.git')` executes silently.
5. The next push/fetch from the Desktop UI sends the user's commits to `evil.example.com` instead of the real server, with no user-visible confirmation of the remote change. [3](#0-2)

  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}
