### Title
Attacker-controlled `offset`/`outpoint` in `ReceivedOutput::read` lets unauthenticated parties register unspendable "received" funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes three fully attacker-controlled attributes — a scalar `offset`, a `TxOut`, and an `OutPoint` — with no check that they are mutually consistent or that the referenced output exists on chain. This is the direct analog of CVE-2026-5708's "unsanitized control of user-modifiable attributes": the deserializer trusts user-supplied fields that should only ever be produced by the trusted `Scanner`, and downstream signing treats them as authoritative.

### Finding Description
`Scanner::scan_transaction` is the only code path that produces a legitimate `ReceivedOutput`: it looks up `output.script_pubkey` in `self.scripts` (built from the group key via `register_offset`) and records the *real* `OutPoint` derived from `tx.compute_txid()` and `vout` [1](#0-0) .

`ReceivedOutput::read`, however, accepts arbitrary bytes and returns a `ReceivedOutput` claiming any `offset`, any `TxOut`, and any `OutPoint`, with no binding between them [2](#0-1) :

```rust
let offset = Secp256k1::read_F(r)?;
output = TxOut::consensus_decode(&mut buf_r)...;
outpoint = OutPoint::consensus_decode(&mut buf_r)...;
Ok(ReceivedOutput { offset, output, outpoint })
```

The `offset` is security-critical: it is the scalar added to the threshold key to obtain the key that must sign for this output (`keys.offset(...)` produces a spend key `group_key + offset*G`, mirroring `tweak_keys`' use of `offset` for the TapTweak) [3](#0-2) . `ThresholdKeys::offset` applies it verbatim with no validation [4](#0-3) . Because `view()` adds the offset to `included[0]`'s secret share and to that participant's verification share [5](#0-4) , the signature produced is only valid for a `script_pubkey` derived from `group_key + offset*G` (+ TapTweak). If the supplied `offset` does not correspond to `output.script_pubkey` — a consistency the deserializer never checks — the multisig will produce a signature that fails BIP-340 verification against the real output.

### Impact Explanation
Any party able to feed serialized bytes into `ReceivedOutput::read` (e.g., a coordinator message, a submitted event, or any integrator path that round-trips outputs) can cause the system to record funds as received that are not spendable:

- Set `outpoint`/`output` to a genuine on-chain output paying the group key, but `offset` to an arbitrary scalar → the registered output cannot be signed for; funds are counted as balance yet any spend produces an invalid signature.
- Set `outpoint` to a nonexistent output → phantom funds reported received.

Because `offset` is also re-keyed per spend, an attacker controlling it controls which key the threshold group attempts to sign as, degrading availability of the wallet and corrupting the reported balance — matching the CVE pattern where a user-modifiable attribute silently changes security-relevant state.

### Likelihood Explanation
Severity Medium. Exploitation requires an integration path where `ReceivedOutput` bytes cross a trust boundary (the struct is `pub`, `read` is `pub`, and the type is explicitly designed for serialization round-trips via `serialize`/`write` [6](#0-5) ). It does not leak key material or forge signatures, but it deterministically yields unspendable recorded funds whenever the offset doesn't match the script — a concrete, reachable consequence requiring only crafted bytes.

### Recommendation
Do not deserialize `offset` from untrusted bytes. Either:
- Recompute `offset` by looking up `output.script_pubkey` in the `Scanner`'s `scripts` map at read/registration time (re-derivation, mirroring `scan_transaction`), or
- Verify the consistency invariant `p2tr_script_buf(key + G*offset) == output.script_pubkey` inside `ReceivedOutput::read`/`sign`, and reject mismatches.

### Proof of Concept
```rust
// Group key K with a registered deposit at offset o for script S.
// Attacker crafts bytes: offset' (arbitrary), TxOut{script_pubkey: S, value}, real OutPoint.
let forged = ReceivedOutput::read(&mut attacker_bytes).unwrap();
// forged.offset() == offset' != o
// Spending forged: keys.offset(offset') yields K + offset'*G, whose tweaked
// script_pubkey != S. The resulting BIP-340 signature is invalid for the real
// output => funds counted as received are unspendable.
```

Caveat: the exact call sites plumbing untrusted bytes into `ReceivedOutput::read` (processor/coordinator layers) are outside the indexed in-scope crates, so reachability rests on the type's public serialization API being the canonical transport for scanned outputs.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
