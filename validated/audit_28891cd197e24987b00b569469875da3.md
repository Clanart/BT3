### Title
Untrusted preprocess keyed with `Participant(0)` panics `SignMachine::sign` via `view().unwrap()` - (File: crypto/frost/src/sign.rs)

### Summary
The libgsf CVE-2016-9888 class is a crash on attacker-controlled input (null dereference on a crafted file). The Serai analog is an unhandled `Result` that panics during processing of an untrusted FROST preprocess. `AlgorithmSignMachine::sign` collects the participant indexes from the peer-supplied `HashMap<Participant, Preprocess>` into `included`, then calls `self.params.keys.view(included.clone()).unwrap()` before any validation that every index is within the valid signer range `1 ..= n`. [1](#0-0) 

### Finding Description
In `crypto/frost/src/sign.rs`, `sign` builds `included` from the keys of the `preprocesses` map (untrusted, per-participant preprocess messages read via `read_preprocess`/`Commitments::read`). The only bounds check performed is on the *maximum* index: `included[included.len() - 1] > n` returns `InvalidParticipant`. Because `included` is sorted ascending, an attacker who submits their preprocess keyed as `Participant(0)` makes `included[0] == 0`, which passes the upper-bound check and the duplicate check (the local participant index `i` is always `>= 1`, so `0` is never a duplicate). FROST participant indexes are defined over `1 ..= n`; index `0` has no polynomial evaluation point / verification share, so `ThresholdKeys::view`/`ThresholdView` construction for a set containing `0` cannot produce a valid view and returns `Err`. The `.unwrap()` on line 312 then panics, crashing the signing task.

A second, related panic exists in the same path: peers' `Commitments` are read with counts derived from the local algorithm's `nonces()` layout (`Commitments::read` reads exactly `generators.len()` nonce-commitment sets, `nonce.rs:133`), so length mismatches are handled — the unguarded failure point is specifically the participant-index validation gap feeding the `unwrap`. [2](#0-1) [3](#0-2) 

### Impact Explanation
Any unprivileged participant in a FROST signing session (or any party able to deliver a preprocess message into the `preprocesses` map under a chosen `Participant` key) can remotely crash the signer's `sign` call. For a coordinator/processor that runs signing in a long-lived process without panic isolation, this is a denial of service on the threshold-signing path, analogous to the crafted-TAR crash in the reference advisory. No key material is leaked and no invalid signature is produced — the impact is availability only, consistent with the Medium severity of the original bug class.

### Likelihood Explanation
The trigger requires only sending a syntactically valid preprocess message labeled with participant index `0`. No cryptographic computation, race condition, or collusion is needed; a single malicious or even malformed peer input reaching `sign` suffices. Reachability is through the explicitly in-scope path `read_preprocess` → `sign(preprocesses, msg)`. [4](#0-3) 

### Recommendation
Validate participant indexes before constructing the view. In `AlgorithmSignMachine::sign`, after the `> n` check, also reject `included[0] == Participant(0)` (i.e., check the minimum, not just the maximum, of the sorted set) with `FrostError::InvalidParticipant`. Alternatively, replace `view(included.clone()).unwrap()` with `view(included.clone()).map_err(...)`? — but that alone is insufficient since a `view` that does not error on `0` would silently corrupt Lagrange coefficients; an explicit range check `1 <= l <= n` for all `l in included` is the correct fix.

### Proof of Concept
```rust
// Attacker is a session participant (or relays a preprocess) and submits their
// Preprocess under Participant(0) instead of their real index.
let mut preprocesses = HashMap::new();
let malicious_bytes = /* serialized Commitments for the algorithm's nonce layout */;
let preprocess = sign_machine.read_preprocess(&mut &malicious_bytes[..]).unwrap();
preprocesses.insert(Participant::from(0u16), preprocess);
// Plus enough honest preprocesses so included.len() >= t.

// Honest signer calls:
let res = sign_machine.sign(preprocesses, b"message");
// included == [0, i, ...]; all checks pass; keys.view() -> Err for index 0;
// sign.rs:312 `.unwrap()` panics -> process/task crash (DoS).
```
Caveat: I could not read `ThresholdKeys::view`/`ThresholdView` internals directly (the `keys.rs` source wasn't indexed under that path), so the finding assumes `view` rejects index `0` — the standard FROST behavior since indexes are `1 ..= n`. If `view` does not error, the index-0 path instead produces a silently invalid view, which is a worse outcome and still a bug; either way the missing lower-bound validation is the defect.
