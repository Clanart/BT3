This is confirmed: GitHub Desktop supports running git hooks (`post-checkout`, `post-merge`, etc.) with `interceptHooks` during operations like `pull` [1](#0-0) , and hooks can run in the user's shell environment via `withHooksEnv`/`createHooksProxy` [2](#0-1) [3](#0-2) . A malicious repository can therefore ship a `post-merge`/`post-checkout` hook that, upon `git pull`/checkout, asynchronously rewrites tracked working-directory file content in the background while GitHub Desktop still holds a stale line-indexed `DiffSelection` for that file from a previous render.

### Title
Stale line-indexed `DiffSelection` combined with hook-driven working-directory mutation can cause commits to include attacker-influenced content silently - (File: `app/src/lib/git/apply.ts`, `app/src/lib/patch-formatter.ts`, `app/src/lib/stores/app-store.ts`)

### Summary
GitHub Desktop's partial-commit ("stage selected lines") feature works by taking a `DiffSelection` — a set of *line indices* computed against a diff that was rendered at some earlier point — and later reformatting a patch from a **freshly recomputed** diff (`getWorkingDirectoryDiff`) using those same indices [4](#0-3) [5](#0-4) . The invariant the app depends on is "index N in the diff always corresponds to the same logical line the user reviewed and selected." That invariant is not guaranteed: the code explicitly acknowledges the diff can change dramatically between renders, and only reconciles which indices remain *selectable*, not what content those indices now represent [6](#0-5) .

### Finding Description
The corrupted value is the set of line indices in `DiffSelection.divergingLines` used by `formatPatch`/`formatPatchToDiscardChanges` to decide which lines go into the generated patch [7](#0-6) . When the working tree changes between the time a user reviews/selects lines in the Changes view and the time `stageFiles`/`applyPatchToIndex` actually re-diffs and applies the patch, the index-to-content mapping can shift (lines added/removed elsewhere in the file), so the "selected" indices no longer correspond to the reviewed hunks/lines.

GitHub Desktop's hook subsystem provides exactly this kind of attacker-controlled, asynchronous working-directory mutation vector: hooks such as `post-merge` and `post-checkout` are proxied and executed with access to the repository's shell environment during normal `pull`/checkout operations [8](#0-7) [9](#0-8) . A hook shipped inside an attacker-controlled/cloned repository is not sandboxed against modifying tracked files after the pull/checkout completes (e.g., spawning a detached background process that edits a file a few seconds later while the app is still rendering the pre-mutation diff and the user is making a partial selection). Existing guards do not stop this path: `updateChangesWorkingDirectoryDiff` only filters *which* indices remain "selectable" using `isIncludeableLine()`; it does not verify that the *content* mapped to a retained index is unchanged, and `applyPatchToIndex` re-fetches the diff independently right before applying, trusting the (possibly stale) selection indices against the new diff without any hash/content-based validation [10](#0-9) [11](#0-10) .

### Impact Explanation
If exploited, this results in silent corruption of what the user commits: the resulting commit can include lines the user never intended to stage/commit, or omit lines they meant to include, based on a hunk index collision introduced by attacker-controlled hook-driven mutation. This falls squarely in the "silent corruption of what the user commits or pushes" impact class.

### Likelihood Explanation
Likelihood is low-to-moderate. It requires: (1) the user to have git hooks enabled for the repository (a feature that is opt-in per the Preferences UI shown in `git.tsx`, though changelog notes hooks were "Enabled by default" in 3.5.5-beta4) [12](#0-11) [13](#0-12) ; (2) a narrow timing window between diff render/selection and the actual patch application; and (3) the attacker needing the hook to modify the exact file under review. This is a race-condition-class bug rather than a deterministic one, and I could not find a concrete reproduction path fully independent of hooks being enabled and of precise timing, which limits confidence that this is reliably and remotely exploitable purely by an attacker-controlled repository without any additional local trust decision (the user must have already opted to trust/enable hook execution for the repo).

### Recommendation
Before applying a partial-selection patch, validate that the diff used to build the patch is unchanged relative to the diff the selection was made against (e.g., by comparing content hashes of the file/hunks, not just line indices) and abort/re-prompt the user if it has changed. Additionally, consider re-running `updateChangesWorkingDirectoryDiff`-style reconciliation immediately before `stageFiles`/`createCommit`, not only on selection load, and invalidate stale selections whose underlying hunk content no longer matches rather than only pruning indices that became non-selectable.

### Proof of Concept
Not independently verified end-to-end (would require a running Desktop instance, a repo with hooks enabled, and precise timing). Conceptual PoC:
1. Attacker publishes/shares a repository containing a `post-merge` hook that spawns a detached process which, several seconds after the hook exits, appends/removes a line in a specific tracked file.
2. Victim (with git hooks execution enabled) clones/pulls the repo in Desktop; `post-merge` runs via the hooks proxy [9](#0-8) .
3. Victim opens the Changes view, reviews the diff of the target file, and selects specific lines to stage for a partial commit — this diff/selection is computed against the pre-mutation content.
4. Before the victim commits, the detached background process (started by the hook) mutates the file's content, shifting line positions.
5. Victim commits; `applyPatchToIndex` re-fetches the diff (now shifted) and applies the patch using the stale line indices [11](#0-10) , silently including/excluding different content than what the victim visually reviewed and selected.

Given the reliance on hooks being enabled and a timing race, I flag this with moderate confidence rather than as a definitively confirmed exploit chain.

  /** Returns a value indicating the computed overall state of the selection */
  public getSelectionType(): DiffSelectionType {
    const divergingLines = this.divergingLines
    const selectableLines = this.selectableLines

    // No diverging lines, happy path. Either all lines are selected or none are.
    if (!divergingLines) {
      return this.defaultSelectionType
    }
    if (divergingLines.size === 0) {
      return this.defaultSelectionType
    }

    // If we know which lines are selectable we need to check that
    // all lines are divergent and return the inverse of default selection.
    // To avoid looping through the set that often our happy path is
    // if there's a size mismatch.
    if (selectableLines && selectableLines.size === divergingLines.size) {
      const allSelectableLinesAreDivergent = [...selectableLines].every(i =>
        divergingLines.has(i)
      )

      if (allSelectableLinesAreDivergent) {
        return this.defaultSelectionType === DiffSelectionType.All
          ? DiffSelectionType.None
          : DiffSelectionType.All
      }
    }

    // Note that without any selectable lines we'll report partial selection
    // as long as we have any diverging lines since we have no way of knowing
    // if _all_ lines are divergent or not
    return DiffSelectionType.Partial
  }
