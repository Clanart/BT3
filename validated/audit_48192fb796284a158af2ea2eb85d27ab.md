### Title
Cached FROST preprocess reused across distinct `sign()` executions without deletion, enabling nonce reuse and validator key-share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` loads a cached preprocess seed from `CachedPreprocesses` and reconstructs a deterministic `AlgorithmSignMachine` via `AlgorithmSignMachine::from_cache`, but never clears the cached seed. `share_internal` then invokes `machine.sign(preprocesses, msg)` on a machine whose nonces are fully determined by that seed. Because `DkgConfirmer::share` and `DkgConfirmer::complete` each independently call `share_internal`, `sign()` is executed more than once under the same context key `(b"DkgConfirmer", attempt)`. If the two executions differ in the message (derived from `key_pair`, an externally supplied value) or in the peer preprocess set, the same nonce `d`/`e` pair signs two distinct challenges — the exact FROST nonce-reuse condition the library documents as enabling third-party recovery of the signer's private key share. The stale-consumed-resource shape mirrors CVE-2024-26792: an identifier/seed consumed once is consumed again because nothing cleared it on the first path.

### Finding Description
In `preprocess_internal` (signing_protocol.rs:100-148), the seed stored in `CachedPreprocesses::set`/`get` is loaded at line 137 and passed to `AlgorithmSignMachine::from_cache` at line 145. `from_cache` calls `seeded_preprocess`, which seeds `ChaCha20Rng::from_seed(*seed.0)` and deterministically derives all nonces (`crypto/frost/src/sign.rs:121-144`). The FROST contract for `from_cache` states: "After this, the preprocess must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" (`crypto/frost/src/sign.rs:216-219`). No deletion of `CachedPreprocesses` occurs anywhere.

`share_internal` (line 150-181) calls `preprocess_internal` at line 156 and then `machine.sign(preprocesses, msg)` at line 170. Within `DkgConfirmer`, `share()` (line 304-310) and `complete()` (line 312-327) both route through `share_internal` with the identical context `(b"DkgConfirmer", self.attempt)` (line 275). `complete` calls `share_internal` at line 322 unconditionally to rebuild the machine. Therefore the same deterministic nonce set is fed into `sign()` at least twice per confirmation attempt.

The safety argument in the file header (lines 25-48) relies on all `sign()` inputs being identical because they are BFT-finalized tributary data. That argument covers `serialized_preprocesses`, but `msg` is built from `set_keys_message(&self.spec.set(), &removed, key_pair)` (lines 296-300) where `key_pair` is supplied by the caller (`generated_key_pair` in `handle.rs:47-60` passes the `KeyPair` observed from a Substrate event, not from tributary ordering). If a second key-pair event for the same attempt reaches `generated_key_pair` — e.g., a re-emitted or competing `set_keys` event before the attempt is finalized — or if `complete` is invoked with a `key_pair` that diverges from the one used in `share`, the validator re-signs a different `msg` with identical nonces.

With two FROST shares `s₁ = d + e·ρ₁·λ·x + c₁·(x·λ)` and `s₂ = d + e·ρ₂·λ·x + c₂·(x·λ)` over the same nonces but different binding factors/challenges, an observer solves the linear system for `x` — the Ristretto validator key, which is the root-of-trust key used for DKG confirmation. Both shares are published publicly on tributary.

### Impact Explanation
Recovery of a validator's Ristretto signing key (`self.key`). That key is the validator's identity key for the tributary BFT layer and the MuSig confirmation key — recovering it enables forging `DkgConfirmation` shares, `RemoveParticipantDueToDkg` votes, and any other validator-signed tributary transactions, i.e., full impersonation of that validator for the affected set and falsified DKG confirmations accepted on Substrate. This is the "key share recovery" acceptance criterion.

### Likelihood Explanation
Requires two executions of `share_internal` under one `(DkgConfirmer, attempt)` context with divergent `msg` or preprocess sets. The normal path signs the same message twice harmlessly (identical shares), which is why this is not automatically fatal. The divergence window is the externally supplied `key_pair` parameter, which is not bound by tributary ordering: any path that calls `generated_key_pair` or `complete` with a different `KeyPair` for the same attempt — a duplicated/updated Substrate event, a coordinator processing both a `share` and a `complete` against a re-submitted key pair, or a partial state rebuild that re-decides inputs differently than the header's "complete rebuild" assumption — triggers it. No malicious-threshold or broken-BFT assumption is needed; it only requires the event feed to present two distinct key pairs for one attempt, which the code does not deduplicate (`DkgKeyPair::set` at handle.rs:54 overwrites unconditionally). The file itself flags the missing "on-chain-preprocess-matches-presumed-preprocess check" as a TODO (lines 50-54), indicating the invariant is known-unenforced. Rated Medium: strong impact, conditional reachability.

### Recommendation
- After `AlgorithmSignMachine::from_cache` succeeds, either delete `CachedPreprocesses` for the context or store a binding commitment (hash of the `msg` and the sorted preprocess set) alongside the seed; on the next `share_internal` call, refuse to `sign` if the commitment differs.
- Bind the signed `key_pair` into the context key (e.g., `(b"DkgConfirmer", attempt, key_pair_bytes)`) only if multiple key pairs per attempt are legitimate; otherwise record the first `key_pair` signed under an attempt and reject divergent re-signing.
- Implement the acknowledged TODO: before publishing a share, verify the reconstructed machine's published preprocess equals the nonce commitments already on chain, so any divergence fails closed instead of re-signing.

### Proof of Concept
Sketch (coordinator, `DkgConfirmer` path):

1. Attempt `a` begins; `DkgConfirmer::new(key, spec, txn, a)` is built.
2. `generated_key_pair(txn, key, spec, key_pair_A, a)` executes → `share(preprocesses_P, key_pair_A)` → `share_internal` → `preprocess_internal` stores seed `S` under `CachedPreprocesses[(b"DkgConfirmer", a)]`, rebuilds nonces `(d, e)` from `S`, and publishes `share_A = sign(P, set_keys_message(..., key_pair_A))`.
3. A second key-pair event for attempt `a` with `key_pair_B ≠ key_pair_A` triggers `generated_key_pair` again (or `complete` is called with `key_pair_B`) → `preprocess_internal` re-loads the same seed `S` (never deleted) → identical `(d, e)` → publishes `share_B = sign(P, set_keys_message(..., key_pair_B))`.
4. Observer reads `share_A` and `share_B` from public tributary data. The binding factors `ρ` and challenges `c` differ (different `msg` hashed into `rho_transcript` at `crypto/frost/src/sign.rs:362-379` and the Schnorrkel challenge), the nonce scalars are identical, so the two-share linear system over `share_i = d + e·ρᵢ·λ·x + cᵢ·λ·x` yields the validator's secret `x`.

What I could not fully verify: whether coordinator/main.rs guarantees `generated_key_pair` fires at most once per attempt and whether `complete` always receives the same `key_pair` that `share` used — the deduplication point (or its absence) for the external key-pair event is the load-bearing reachability condition, and the relevant call sites were not all enumerable in this pass.
