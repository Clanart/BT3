## Analysis

The CVE describes a divide-by-zero causing denial-of-service. The closest reachable analog in this codebase is in the KIP-71 dynamic base fee calculation, which is directly triggered by a governance parameter that lacks a non-zero format check, unlike its sibling parameter.

### Title
Divide-by-zero panic in `NextMagmaBlockBaseFee` via zero `GasTarget` governance parameter - (File: `params/kip71_config.go`)

### Summary
The KIP-71 governance parameter `GasTarget` can be set to `0` because its `FormatChecker` is a no-op, unlike `BaseFeeDenominator` which explicitly rejects zero. Once a `GasTarget=0` vote is enacted, every node computing `NextMagmaBlockBaseFee` for the following block divides by `gasTarget`, causing an unrecovered `math/big` division-by-zero panic across the entire network.

### Finding Description
The `Kip71GasTarget` parameter definition uses `noopFormatChecker`, which accepts any `uint64` value including `0`: [1](#0-0) 

Compare this to the sibling parameter `Kip71BaseFeeDenominator`, which explicitly requires `v != 0`: [2](#0-1) 

The `checkConsistency` function in `headerGovModule.VerifyVote` path explicitly performs *no additional value validation* for `gov.Kip71GasTarget` votes beyond the format checker: [3](#0-2) 

`NextMagmaBlockBaseFee` in `params/kip71_config.go` guards against `BaseFeeDenominator == 0` by defaulting to `64`, but performs no equivalent guard for `gasTarget == 0`: [4](#0-3) 

When `parentGasUsed != gasTarget` (which is guaranteed whenever `gasTarget == 0` and any gas was used in the parent block), the code proceeds to divide by `gasTarget` directly: [5](#0-4) [6](#0-5) 

`x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0` triggers a `math/big` division-by-zero panic (Go's `big.Int.Div`/`Quo` panic when the divisor is zero, unlike Solidity's revert-on-zero-division).

`NextMagmaBlockBaseFee` is invoked from `VerifyMagmaHeader`, which is part of block header validation that every full node performs, as well as from the gas price oracle (`node/cn/gasprice/feehistory.go` `processBlock`) used by public RPC (`eth_feeHistory`): [7](#0-6) 

### Impact Explanation
Once `GasTarget=0` is enacted via a governance vote (reachable through the governance parameter voting mechanism, category explicitly in scope), any node that processes the next block with nonzero gas usage will panic in `NextMagmaBlockBaseFee` during header verification. Because this function is called by every node validating blocks and by RPC nodes serving `eth_feeHistory`/gas price suggestions, this results in a network-wide denial-of-service — nodes crash while attempting consensus-critical header verification, which can halt block production or cause state-processing divergence between nodes that crash versus restart at different times.

### Likelihood Explanation
`GasTarget` is a governance-tunable parameter exposed through the standard header-vote mechanism (`gov.Kip71GasTarget`). Its format checker is a no-op that accepts `0`, and `checkConsistency` performs no additional bound check for this parameter, in contrast to the explicit `!= 0` check applied to `BaseFeeDenominator`. This asymmetry means the safeguard was clearly intended but omitted for `GasTarget`, making the zero-value case reachable through a single successful governance vote/parameter change without requiring code compilation flags or unusual configuration.

### Recommendation
Add a non-zero format checker for `Kip71GasTarget` mirroring `Kip71BaseFeeDenominator`'s `FormatChecker: func(cv any) bool { v, ok := cv.(uint64); return ok && v != 0 }`, and/or add a defensive fallback inside `NextMagmaBlockBaseFee` (similar to the existing `baseFeeDenominator == 0` fallback) to avoid dividing by a zero `gasTarget`.

### Proof of Concept
1. Via governance voting (single mode governing node, or council majority), submit a vote setting `Kip71GasTarget = 0`. This passes `NewVoteData`'s format check because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`, and passes `checkConsistency` in `kaiax/gov/headergov/impl/header.go`, which does not validate the value for this parameter.
2. Once the vote is enacted at the next epoch boundary, the new `ParamSet.GasTarget` becomes `0`.
3. When any node processes the following block that used any nonzero gas (`parentHeaderGasUsed > 0`), `VerifyMagmaHeader` → `NextMagmaBlockBaseFee` computes `parentGasUsed = min(parentHeaderGasUsed, upperGasLimit) > 0 = gasTarget`, entering the `parentGasUsed > gasTarget` branch, then executes `x.Div(x, new(big.Int).SetUint64(gasTarget))` with `gasTarget == 0`, causing a `big.Int` division-by-zero panic that crashes the node process.
