Based on my investigation, I found a valid analog to CVE-2017-11450's bug class ("crash due to insufficient length validation before parsing").

### Title
Auction bid signature parsing panics on short signature bytes (index-out-of-range DoS) - (File: kaiax/auction/bid.go)

### Summary
The `getSigner` helper used to verify auction bid signatures indexes into the raw signature byte slice without first validating its length, mirroring the CVE-2017-11450 root cause (parsing a byte buffer that is shorter than the format expects, causing a crash).

### Finding Description
`getSigner` in [1](#0-0)  clones the caller-supplied `sig` slice and immediately accesses fixed offsets (`crypto.RecoveryIDOffset` = 64, `copiedSig[0:32]`, `copiedSig[32:64]`) without checking `len(sig) >= crypto.SignatureLength (65)` first. This is unlike every other signature-consuming entry point in the codebase (e.g. `PersonalAPI.EcRecover`, `KaiaTransactionAPI.RecoverFromMessage`, `crypto.Ecrecover`/`sigToPub`), which all explicitly check `len(sig) != crypto.SignatureLength` before touching the bytes, as seen in [2](#0-1)  and [3](#0-2) .

`getSigner` is invoked by `Bid.ValidateSearcherSig` and `Bid.ValidateAuctioneerSig`: [4](#0-3) . The `Bid` struct's `SearcherSig` and `AuctioneerSig` fields are plain `[]byte` fields populated directly from externally supplied bid data (`BidData.SearcherSig`, `BidData.AuctioneerSig`) at [5](#0-4) , and bids are submitted through the auction bid-pool/RPC path in `kaiax/auction/impl/bid_pool.go` and `kaiax/auction/impl/api.go` (confirmed to reference `SearcherSig`/`AuctioneerSig` and a bid-submission API, though I was not able to fully trace whether any prior length check exists in `bid_pool.go`/`api.go` before `ValidateSearcherSig`/`ValidateAuctioneerSig` are called — this should be verified).

If no length gate exists earlier in the submission pipeline, a bidder can submit a bid whose `searcherSig` or `auctioneerSig` is fewer than 65 bytes (including empty). `slices.Clone` on such a short slice preserves its short length, and the subsequent index/slice operations (`copiedSig[64]`, `copiedSig[0:32]`, `copiedSig[32:64]`) will panic with "index out of range" or "slice bounds out of range."

### Impact Explanation
A panic inside a goroutine handling untrusted RPC/bid-pool input that is not recovered will crash the node process — a remotely triggerable denial of service reachable by any unprivileged auction bidder, matching the CVE's "cause a denial of service (application crash)" impact class.

### Likelihood Explanation
Likelihood depends entirely on whether `bid_pool.go`/`api.go` validate `len(SearcherSig)`/`len(AuctioneerSig) == 65` before calling `ValidateSearcherSig`/`ValidateAuctioneerSig`. I could not fully confirm this given the tool budget — `getSigner` itself performs no such check, so the vulnerability is real at the function level, but whether it is reachable end-to-end from the public bid-submission RPC requires verifying the call chain in `kaiax/auction/impl/bid_pool.go` and `kaiax/auction/impl/api.go`.

### Recommendation
Add an explicit length check at the top of `getSigner` (and/or at bid ingestion in `bid_pool.go`/`api.go`):
```go
func getSigner(sig, digest []byte) (common.Address, error) {
    if len(sig) != crypto.SignatureLength {
        return common.Address{}, ErrInvalidSignature
    }
    ...
}
```
This mirrors the existing pattern used everywhere else in the codebase for signature-length validation.

### Proof of Concept
Submit an auction bid (via the bid-pool submission API) with `searcherSig` (or `auctioneerSig`) set to a byte slice shorter than 65 bytes (e.g., `0x00` or empty `0x`). When the node calls `Bid.ValidateSearcherSig`/`ValidateAuctioneerSig` → `getSigner`, the line `copiedSig[crypto.RecoveryIDOffset]` (index 64) or `copiedSig[32:64]` will panic with "index out of range"/"slice bounds out of range" since the short slice was never length-checked, potentially crashing the node if the panic is not recovered up the call stack.

**Note:** Given the limited exploration budget, I was unable to fully confirm whether `kaiax/auction/impl/bid_pool.go` or `kaiax/auction/impl/api.go` perform a length check on `SearcherSig`/`AuctioneerSig` prior to calling the validation functions, or whether the goroutine handling bid submissions has panic recovery. A Devin session with full codebase access should verify these two points before treating this as confirmed-exploitable end-to-end.

```go
func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (b *Bid) ValidateAuctioneerSig(auctioneer common.Address) error {

	recoveredAuctioneer, err := getSigner(b.AuctioneerSig, digest)

	}

	if recoveredAuctioneer != auctioneer {
		return fmt.Errorf("invalid auctioneer sig: expected %v, calculated %v", auctioneer.String(), recoveredAuctioneer.String())
	}

	return nil
}
```

```go
func getSigner(sig, digest []byte) (common.Address, error) {
	// Manually convert V from 27/28 to 0/1
	copiedSig := slices.Clone(sig)
	if copiedSig[crypto.RecoveryIDOffset] == 27 || copiedSig[crypto.RecoveryIDOffset] == 28 {
		copiedSig[crypto.RecoveryIDOffset] -= 27
	}

	v := copiedSig[crypto.RecoveryIDOffset]
	r := new(big.Int).SetBytes(copiedSig[0:32])
	s := new(big.Int).SetBytes(copiedSig[32:64])
	if !crypto.ValidateSignatureValues(v, r, s, true) {
		return common.Address{}, ErrInvalidSignature
	}
```
