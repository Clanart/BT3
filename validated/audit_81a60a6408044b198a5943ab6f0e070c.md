### Title
Automatic remote-URL rewrite trusts unvalidated GitHub API `clone_url` field, allowing silent remote hijack - ([File: app/src/lib/stores/updates/update-remote-url.ts])

### Summary
GitHub Desktop periodically refreshes a repository's GitHub metadata and, if the upstream repo's `clone_url` differs from what's stored locally, silently rewrites the user's `origin` remote to that new URL. The function that performs this rewrite, `updateRemoteUrl`, only checks that the git protocol (http/ssh) hasn't changed and that the *previous* clone URL still matches the current remote — it never validates that the new `clone_url` returned by the API still points to the same host/owner/name the user actually cloned from. This is structurally the same flaw as the Chainlink report: an external, attacker-influenceable data source (`oracle.latestRoundData()` there, the GitHub API response here) is consumed and used to update critical state without a freshness/consistency/sanity check.

### Finding Description
`repositoryWithRefreshedGitHubRepository` in `app-store.ts` calls `api.fetchRepository(owner, name)` to get fresh repo info, then unconditionally feeds the resulting `apiRepo` into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` then decides whether to rewrite the local remote based on the raw `apiRepo.clone_url` value: [2](#0-1) 

The only checks performed before calling `gitStore.setRemoteURL(...)` are:
1. `protocolsMatch` — the scheme (`https:`/`ssh:`) of old vs. new URL is the same.
2. `remoteUrlUnchanged` — the user hasn't manually edited their remote away from the previously cached `cloneURL`.
3. `!urlsMatch` — the new URL differs from the current one.

None of these checks validate that the **hostname** of the new `clone_url` matches the account's known endpoint (e.g., `github.com` or the configured GHES host), nor that the owner/repo identity is preserved. `parsedResponse<T>` in `http.ts` only validates that the payload is well-formed JSON — it does no schema/field validation of the trust-sensitive `clone_url` field: [3](#0-2) 

This mirrors the oracle bug exactly: the app trusts an externally-supplied value (`clone_url`) without checking it against an independent invariant (that it should belong to the same trusted host/identity) before using it to mutate a security-relevant local state (the git remote that future `push`/`fetch`/`pull` operations rely on).

### Impact Explanation
If an attacker can influence the GitHub/GHES API response for a `repos/{owner}/{name}` request — e.g. a malicious or compromised proxy in front of an HTTP-only or improperly TLS-validated GitHub Enterprise Server, or a compromised/malicious GHES instance itself — they can set `clone_url` to an arbitrary attacker-controlled git host. Desktop will then silently rewrite the user's `origin` remote to that host on the next background refresh, with no user prompt or confirmation. Subsequent `git fetch`/`pull`/`push` from the Desktop UI will silently talk to the attacker's server. This falls squarely into "silent corruption of what the user commits or pushes": pushes could be redirected to an attacker's server (exposing code/commits), and fetched content could be attacker-controlled without any visible indication the remote changed.

### Likelihood Explanation
Exploitation requires the attacker to control the API response to a `fetchRepository`/`fetchRepositoryCloneInfo` call — a realistic condition for the named threat classes in scope ("a GitHub API object" or "a git remote/proxy response"), particularly for GHES deployments behind a hostile network intermediary, a compromised enterprise instance, or an on-path proxy. It requires no local access, no admin rights, and no user action beyond Desktop's normal periodic repository refresh (`repositoryWithRefreshedGitHubRepository`), which runs automatically in the background.

### Recommendation
Add a validation step in `updateRemoteUrl` (or before it's called) analogous to the two Chainlink checks: verify the new `clone_url`'s hostname matches the expected account endpoint hostname (`getHTMLURL(account.endpoint)`), and verify owner/name identity is preserved (reusing `urlMatchesRemote`/`urlsMatch` helpers already in `repository-matching.ts`) before allowing the automatic rewrite. If the host or owner/name changes unexpectedly, the app should either refuse the automatic update or explicitly prompt the user for confirmation rather than silently changing `origin`.

### Proof of Concept
1. User has GitHub Desktop configured against a GitHub Enterprise Server account whose HTTPS traffic is intercepted by a malicious/compromised proxy (or the GHES instance itself is compromised).
2. Desktop performs its periodic repository refresh, calling `api.fetchRepository(owner, name)` → `GET repos/{owner}/{name}`.
3. The attacker's proxy/server returns a response where `clone_url` is set to `https://attacker.example.com/owner/name.git` (same protocol scheme, so `protocolsMatch` passes; different from current remote, so `!urlsMatch` passes; `remoteUrlUnchanged` passes because the user hasn't manually edited their remote).
4. `updateRemoteUrl` calls `gitStore.setRemoteURL('origin', 'https://attacker.example.com/owner/name.git')`, silently repointing `origin` — visible only if the user manually inspects `git remote -v`.
5. The next push/fetch/pull from Desktop's UI now targets the attacker's host.

```typescript
export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
```

```typescript
export async function parsedResponse<T>(response: Response): Promise<T> {
  if (response.ok) {
    return deserialize<T>(response)
  } else {
    let apiError: IAPIError | null
    // Deserializing the API error could throw. If it does, we'll throw a more
    // general API error.
    try {
      apiError = await deserialize<IAPIError>(response)
    } catch (e) {
      throw new APIError(response, null)
    }

    throw new APIError(response, apiError)
  }
}
```
