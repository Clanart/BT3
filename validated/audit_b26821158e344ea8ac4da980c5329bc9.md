### Title
Windows trailing-dot/space repository name bypasses `sanitizeCloneName` and `isClonePathSensitive`, allowing clone destination to resolve outside the intended base directory - (File: `app/src/lib/remote-parsing.ts`, `app/src/lib/git/clone.ts`)

### Summary
`sanitizeCloneName` in `app/src/lib/remote-parsing.ts` is the guard that turns an attacker-controlled repository name (parsed from a URL, deep link, or `owner/name` shortcut) into a single safe path component before it is joined onto the user's chosen base directory for cloning. It explicitly rejects the literal strings `".."` and `"."`, but does not account for the Win32 behavior of silently stripping trailing dots and spaces from the final path component when a directory is created without the `\\?\` long-path prefix.

### Finding Description
`sanitizeCloneName` [1](#0-0)  splits the attacker-supplied name on `/`, `\`, and `:`, takes the last non-empty component, strips a trailing `.git` suffix, and only rejects the component if it is exactly `".."`, `"."`, or empty:

```
if (
  lastComponent === '..' ||
  lastComponent === '.' ||
  lastComponent.length === 0
) {
  return null
}
```

This equality check does not catch a component such as `".. "` (two dots followed by one or more trailing spaces). On Windows, the Win32 `CreateDirectory`/`CreateFile` APIs (used transparently by both `git.exe` and Node's `fs` when the `\\?\` extended-length prefix is not used) strip trailing dots and spaces from the final path segment before resolving it. That means a directory literally named `".. "` on disk is created as `".."`, i.e. the parent directory, once passed through the OS.

The value flows into the clone path unsanitized:
- `app/src/ui/clone-repository/clone-repository.tsx` calls `sanitizeCloneName(parsed.name)` in `updateUrl` and `onChooseWithOpenDialog`, then does `Path.join(dirPath, safeName)` [2](#0-1)  and [3](#0-2) . `Path.join`/`Path.win32.join` do not interpret `".. "` as `".."`, so the literal string survives and is stored as the clone `path`.
- That path is then passed straight to `git clone ... -- <url> <path>` in `app/src/lib/git/clone.ts` [4](#0-3) .
- The only existing backstop, `isClonePathSensitive`, resolves the path with `Path.resolve` before comparing it to a fixed deny-list of sensitive directories [5](#0-4) . `Path.resolve` is a purely lexical/string operation — it does not know about the Win32 trailing-dot/space stripping — so a path ending in `".. "` is not normalized to its parent and will not match the deny-list (nor would it match `home` or `.ssh`, etc., unless the attacker's target happens to be one of those exact directories).

Because `Path.resolve`/`Path.join` and the sanitizer both operate on the literal string while the actual filesystem operation (via `git.exe`/Win32) applies its own trailing-character normalization, there is a mismatch between the value Desktop believes it is using and the value the OS actually resolves to — the same class of bug as the Solidity report, where the guard's model of the computation ("timePlusFee < timeRemaining") diverged from the real invariant it was supposed to enforce once a boundary case was hit.

### Impact Explanation
An attacker who controls a repository name reachable through the GitHub Desktop clone flow (a crafted GitHub API repository name/URL, a malicious `x-github-desktop://` or `github-windows://` deep link that pre-fills the clone URL, or a generic-URL clone target) can cause the resolved clone destination to land one directory level above the user's intended parent folder on Windows, evading both `sanitizeCloneName`'s traversal check and `isClonePathSensitive`'s sensitive-path deny-list. Depending on the user's chosen base directory, this can redirect `git clone --recursive` to write into a directory the user did not intend (e.g., a shared parent folder), which is a "silent corruption of what gets written to disk outside the intended repo directory" class of impact. The severity is bounded by two factors that must be independently verified in a live Windows environment before treating this as fully exploitable: (1) `git clone` refuses non-empty target directories, so a successful full clone requires the resolved parent-level directory to be empty; (2) exploitation only shifts the write target up by one directory level per crafted component, since `sanitizeCloneName` still returns a single path component.

### Likelihood Explanation
Likelihood is moderate rather than high: the attacker needs to control the repository *name* string end-to-end (e.g. via an API response, a generic clone URL, or a deep-link/`owner/name` shortcut) and needs the victim to actually go through the standard Clone dialog flow, and the target parent directory must be empty for `git clone` to actually populate it. The bug is a genuine gap in the sanitizer's own documented threat model ("reject traversal segments... ensures the result cannot escape the parent directory"), and the existing test suite (`app/test/unit/clone-path-safety-test.ts`) only exercises `..`/`.`/empty and `/`, `\`, `:`-based traversal, not the Windows trailing-dot/space normalization case, so this specific bypass is not currently covered by tests. I was not able to execute the actual Win32 `CreateDirectory` behavior in this environment to confirm the exact runtime outcome (e.g., whether `git.exe` on Windows also performs this normalization identically to raw Win32 calls), so this should be validated experimentally on a Windows host before treating it as fully confirmed.

### Recommendation
In `sanitizeCloneName`, trim trailing dots and spaces from `lastComponent` (mirroring Windows' own normalization) before performing the `".."`/`"."`/empty check, so a component that *would* normalize to `".."` or `"."` after OS-level trimming is caught. Additionally, harden `isClonePathSensitive` (and any other consumer of the resolved clone path) to apply the same trim-then-resolve normalization before comparing against the deny-list, rather than relying solely on `Path.resolve` of the literal string. Consider also validating that the final resolved clone path's parent directory (post-OS-normalization) is exactly the directory the user selected, rejecting the clone if it does not match.

### Proof of Concept
1. Construct a crafted repository identifier whose `name` component is `foo.. ` (or simply `.. ` for a maximal jump) — reachable, for example, via a generic Clone-by-URL entry such as `https://evil.example.com/owner/..%20.git` or an equivalent API-provided repository name.
2. `parseRepositoryIdentifier` / `parseRemote` extract `name = ".. "` (trailing space preserved, since the regexes and `sanitizeCloneName`'s splitting only strip `/`, `\`, `:` and a trailing `.git` suffix, not whitespace).
3. `sanitizeCloneName(".. ")` does not equal `'..'`, `'.'`, or an empty string, so it is returned unchanged as `".. "`.
4. `Path.join(dirPath, ".. ")` in `updateUrl`/`onChooseWithOpenDialog` produces a path such as `C:\Users\victim\Documents\GitHub\.. ` (literal trailing space preserved by Node's path handling).
5. `isClonePathSensitive` calls `Path.resolve("C:\\Users\\victim\\Documents\\GitHub\\.. ")`, which — because Node's `path.resolve` does not strip trailing spaces from Windows path segments — does **not** collapse to `C:\Users\victim\Documents`, so the sensitive-path check passes.
6. `git clone --recursive -- <url> "C:\Users\victim\Documents\GitHub\.. "` is executed; on Windows, the underlying `CreateDirectory` call strips the trailing space and dots from the final segment, causing git to actually operate against `C:\Users\victim\Documents` (the parent of the intended `GitHub` folder) instead of a new subdirectory inside it.

This PoC could not be executed end-to-end in this sandboxed, non-Windows analysis environment, so step 6's exact filesystem outcome (which depends on Win32/`git.exe` internals) is asserted based on documented Windows path-normalization behavior rather than direct observation, and should be confirmed on a real Windows machine.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
