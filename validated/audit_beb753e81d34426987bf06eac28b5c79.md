### Title
Scanner accepts dust outputs which cost more to spend than their value - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` registers every output paying to a tracked `script_pubkey` with no minimum-value check, and `SignableTransaction::new` enforces `DUST` only on *payments*, not on *inputs*. An unprivileged party can send a dust output (e.g. 1–546 sats, or any amount below the fee needed to spend it) to the Serai threshold address. The scanner reports it as a `ReceivedOutput`; when it is later included as an input, spending it consumes ~57 vbytes of fee (230 weight units per the code's own accounting) while contributing less value than that fee — a net loss. This is the same bug class as the reported finding: the protocol enforces a minimum unit on the outgoing operation but not on the residual/incoming balance, leaving value that is below the spendable threshold.

### Finding Description
The external finding is that `transferWearables()`/`sellPrivateWearables()` only check the *transferred* amount against `BASE_WEARABLE_UNIT`, never checking the *remaining* balance, so a user can be left with a balance below the minimum unit that can never be moved.

In `networks/bitcoin/src/wallet/mod.rs`, `scan_transaction` accepts any output whose `script_pubkey` matches a registered script, regardless of `output.value`:

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
``` [1](#0-0) 

In `networks/bitcoin/src/wallet/send.rs`, `SignableTransaction::new` rejects payments below `DUST` (line 166) and only creates change when the leftover `>= DUST` (line 229), but it sums and includes *all* supplied `inputs` unconditionally — there is no check that each input's value exceeds the fee cost of spending it: [2](#0-1) [3](#0-2) 

The code itself documents that a Taproot input costs 230 weight units ≈ 57 vbytes (`networks/bitcoin/src` comments, lines 606–638), so any input worth less than `57 * fee_per_vbyte` sats is net-negative: including it raises `needed_fee` by more than the value it contributes. An attacker can therefore send outputs of e.g. 100 sats to the vault address; the scanner reports them as received balance, yet spending them burns more fee than they return, and even leaving them unspent inflates the reported balance.

### Impact Explanation
Funds are reported received that are not economically spendable (a stated acceptance criterion: "funds reported received that are not spendable"). Worse, if downstream scheduling (`processor` uses `SignableTransaction::new` with whatever `inputs` it is given) includes such outputs, each dust input actively destroys value — the fee exceeds its worth, subsidized by the honest inputs. Just as the wearable user is stuck with an unspendable sub-unit balance, the Serai wallet accumulates sub-`DUST` residual balances that can never be profitably moved.

### Likelihood Explanation
Requires only that an unprivileged party send a Bitcoin transaction paying dust to a Serai P2TR address — public, cheap (costs the attacker only the dust value plus their own fee), and repeatable. The wallet then permanently tracks these outputs.

### Recommendation
In `Scanner::scan_transaction` (and/or at `ReceivedOutput` acceptance), ignore outputs whose `value` is below `DUST` — or at least below the marginal fee cost of an input (≈57 vbytes × current fee rate). Alternatively, have `SignableTransaction::new` filter inputs where `input.value < fee_per_vbyte * 57` so net-negative inputs are never signed over.

### Proof of Concept
1. Register a scanner on the vault key; attacker sends a TX with a 100-sat output to `p2tr_script_buf(group_key)`.
2. `scan_transaction` returns a `ReceivedOutput` with `value() == 100` — reported as balance.
3. `SignableTransaction::new(vec![honest_input, dust_input], &payments, change, None, fee_per_vbyte)` succeeds; the dust input adds 230 WU ≈ 57 vbytes of fee while contributing only 100 sats — net-negative whenever `fee_per_vbyte >= 2`, and even at 1 sat/vbyte the spendable value is 43 sats, below `DUST = 546`, mirroring the "balance below `BASE_WEARABLE_UNIT`" residue that can never be usefully moved.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
