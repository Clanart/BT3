### Title
`SignableTransaction::new` omits the OP_RETURN output from weight/vbytes and fee accounting, so the charged fee and standardness check don't cover the actual transaction - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
When a `data` payload is specified, an OP_RETURN output is appended to `tx_outs`, but `calculate_weight_vbytes` is invoked with only `payments` — never including the data output. The resulting `weight`, `vbytes`, `needed_fee`, the `NotEnoughFunds` check, and the `MAX_STANDARD_TX_WEIGHT` check all ignore the OP_RETURN output's real size. The analogue of the report's "value deducted but not delivered": the caller is charged a fee and the transaction is built as if it were smaller than it is — the intended feerate is silently not delivered, and the standardness bound can be bypassed.

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is pushed onto `tx_outs` before any size accounting: [1](#0-0) 

Yet the weight/vbyte calculation only receives `payments`: [2](#0-1) 

and inside `calculate_weight_vbytes` the transaction's outputs are built exclusively from `payments` plus optional `change` — the OP_RETURN output is never represented: [3](#0-2) 

Consequences:

1. **Fee under-delivery.** `needed_fee = fee_per_vbyte * vbytes` uses the undercounted `vbytes`, so the actual transaction pays less per vbyte than the caller-specified `fee_per_vbyte`. An 80-byte payload adds ~90+ vbytes (output + script overhead); the fee charged simply doesn't cover it. The difference between `needed_fee` and the fee miners would need for the real size is lost — deducted from inputs as excess fee implicitly, but not at the requested rate.
2. **Standardness check bypass.** `weight > MAX_STANDARD_TX_WEIGHT` is evaluated on the smaller phantom transaction, so a transaction that actually exceeds the standard weight limit (and will be rejected by relay policy) is accepted and signed.
3. **`NotEnoughFunds` under-check.** The sufficiency check uses the understated `needed_fee`, and `change` inclusion at line 228 compares `input_sat` against `payment_sat + fee_with_change` where `fee_with_change` is also computed without the OP_RETURN output. [4](#0-3) 

### Impact Explanation
The produced transaction's effective feerate is lower than the caller requested — with the maximum 80-byte payload the shortfall is roughly `90 * fee_per_vbyte` sats. In a fee-sensitive environment the transaction can fail to propagate or confirm, locking funds in an unconfirmed state. Worse, a transaction crossing `MAX_STANDARD_TX_WEIGHT` will be rejected by relay nodes entirely while the signer believes it produced a valid, properly-priced transaction — the opposite accounting error to the reported bug (here value is "collected" for a purpose it never fulfills), but the same class: ledgered value does not reach its intended destination/purpose. Reachable purely via the public `data` parameter.

### Likelihood Explanation
Any caller passing a non-empty `data` payload triggers the miscounting deterministically; no adversarial timing or collusion is required. The standardness-bypass branch additionally requires a large number of inputs/payments, which is less common but still reachable through public inputs alone.

### Recommendation
Include the OP_RETURN output in the size accounting. Either pass the already-constructed `tx_outs` (or the serialized `ScriptBuf` of the OP_RETURN) into `calculate_weight_vbytes`, or compute weight/vbytes after `tx_outs` is fully populated so that `needed_fee`, the `NotEnoughFunds` check, change-inclusion math, and the `MAX_STANDARD_TX_WEIGHT` check all reflect the real transaction.

### Proof of Concept
Construct a `SignableTransaction` with `payments` summing to near the input total, `data` of 80 bytes, and a chosen `fee_per_vbyte`:

```rust
let stx = SignableTransaction::new(
  inputs,                                  // sum = payment_sat + needed_fee (no slack)
  &payments,
  None,
  Some(vec![0u8; 80]),                     // OP_RETURN output
  fee_per_vbyte,
).unwrap();
```

- `stx.transaction().output` contains the OP_RETURN output (pushed at send.rs:195).
- `stx.vbytes` used for `needed_fee` was computed at send.rs:204 from `payments` only — roughly 90 vbytes short of the real transaction size, so `stx.fee() / actual_vbytes < fee_per_vbyte`.
- With `input_sat == payment_sat + needed_fee`, the check at line 215 passes even though the true required fee is higher.
- With enough inputs that `real_weight > MAX_STANDARD_TX_WEIGHT` but `phantom_weight <= MAX_STANDARD_TX_WEIGHT`, line 241 passes while the signed transaction is non-standard and unrelayed.
