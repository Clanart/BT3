### Title
`ReceivedOutput::read` accepts an arbitrary `offset`/`TxOut`/`outpoint` triple with no check the offset derives the output's `script_pubkey`, enabling funds reported received that are not spendable - ([File: networks/bitcoin/src/wallet/mod.rs](networks/bitcoin/src/wallet/mod.rs))

### Summary
`ReceivedOutput::read` (networks/bitcoin/src/wallet/mod.rs:122-134) deserializes three inner fields — a scalar `offset`, a `TxOut`, and an `OutPoint` — yet never validates their mutual consistency. Analogous to the referenced IPVS bug (inner headers consumed without ensuring they are actually present/consistent after parsing), the inner `offset` is never checked to satisfy the only relation that makes the output spendable: `p2tr_script_buf(key + offset*G) == output.script_pubkey`, nor is `outpoint` checked to reference `output`. Any byte string that decodes produces an accepted `ReceivedOutput`.

### Finding Description
`Scanner::scan_transaction` (mod.rs:199-214) is the only constructor that establishes the invariant: it looks up `output.script_pubkey` in `self.scripts` and stores the registered `offset` alongside it (mod.rs:205-210). `ReceivedOutput::read` bypasses this entirely:

```rust
pub fn read<R: Read>(r: &mut R) -> io::Result<ReceivedOutput> {
  let offset = Secp256k1::read_F(r)?;          // arbitrary scalar accepted
  output  = TxOut::consensus_decode(...)        // arbitrary script_pubkey accepted
  outpoint = OutPoint::consensus_decode(...)    // arbitrary prevout accepted
  Ok(ReceivedOutput { offset, output, outpoint })
}
```

The spend path relies on `offset()` (mod.rs:101-103): the signer re-keys its share by this scalar so the group signature verifies under the tweaked x-only key embedded in `script_pubkey`. If `offset` does not correspond to `script_pubkey`, the resulting key cannot sign for the output — the spend fails consensus- or signature-validation — yet the output has already been recorded as a valid receipt.

### Impact Explanation
Any component persisting/transporting scanner results and re-loading them via `ReceivedOutput::read` (e.g., `Output::read` in the processor, which wraps `ReceivedOutput::read` at processor/src/networks/bitcoin.rs:156) will treat attacker-supplied bytes as a confirmed received output. The system can therefore:

- Report/confirm a deposit or balance (`balance()`/`value()` at mod.rs:115-128) that is not spendable, leading to funds locked when a spend is later attempted with the wrong offset.
- Accept a mismatched `outpoint`, pointing the recorded "received" funds at a nonexistent or unrelated UTXO.

This matches the accepted impact "funds reported received that are not spendable": an unprivileged party supplying the serialized bytes needs no key material — `read_F`, `consensus_decode` accept any well-formed encoding.

### Likelihood Explanation
Reachability requires only that serialized `ReceivedOutput` bytes cross a trust boundary (DB restoration, inter-process handoff, or any `read` of untrusted bytes), which is the documented purpose of `read`/`serialize`. No cryptographic break is needed; the attacker just writes 32 bytes of scalar + a consensus-encoded `TxOut`/`OutPoint`. Exploitation is deterministic whenever the read path lacks a surrounding consistency check.

### Recommendation
In `ReceivedOutput::read`, after decoding, verify the spendability relation before returning:

```rust
let derived = p2tr_script_buf(scanner_key + (ProjectivePoint::GENERATOR * offset))
  .ok_or(io::Error::other("offset yields unusable script"))?;
if derived != output.script_pubkey {
  return Err(io::Error::other("offset inconsistent with output script_pubkey"));
}
```

This requires `read` to take the base key (as `Scanner::new` does), or alternatively expose a `verify(key) -> bool` on `ReceivedOutput` that all consumers must call. Additionally consider binding `outpoint` to a known txid where context permits.

### Proof of Concept
```rust
use bitcoin::{TxOut, OutPoint, ScriptBuf, Amount, Txid, hashes::Hash};
use serai_bitcoin::wallet::ReceivedOutput;
use k256::Scalar;

// Attacker-supplied bytes: a real-looking received output with a garbage offset
let mut buf = vec![];
buf.extend(Scalar::ONE.to_bytes());                       // offset = 1, unrelated to script
let txout = TxOut {
  value: Amount::from_sat(100_000),
  script_pubkey: ScriptBuf::new(),                        // any script
};
buf.extend(bitcoin::consensus::encode::serialize(&txout));
buf.extend(bitcoin::consensus::encode::serialize(
  &OutPoint::new(Txid::all_zeros(), 0),
));

let output = ReceivedOutput::read(&mut buf.as_slice()).unwrap();
// Accepted: value() reports 100k sats "received", but offset() cannot sign for script_pubkey
assert_eq!(output.value(), 100_000);
// Any spend constructed with output.offset() fails verification -> locked funds
```
