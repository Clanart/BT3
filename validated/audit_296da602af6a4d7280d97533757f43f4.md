### Title
Full-fill escrow release drains shared per-token escrow instead of the per-leg share, letting a solver steal escrow backing other unfilled output legs - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`_fillSameChain` releases escrow for a fully-completed output leg by reading the *entire* current balance of `_orders[commitment][token]`, rather than the amount proportional to that specific input/output pair. Because `_orders` is keyed only by `(commitment, token)` — not by input index — any order whose `inputs` array uses the same token to back two or more distinct output legs allows a solver to fully drain the shared escrow balance by cheaply completing just one of those legs, at the expense of the order creator and any other leg still awaiting settlement.

### Finding Description
Escrow is stored per `(commitment, token)`, aggregated across all input entries with that token address: [1](#0-0) 

When a solver fully fills one output pair in `_fillSameChain`, the code computes the escrow to release for that pair as follows: [2](#0-1) 

Note that on a full fill (`amountFilled == totalRequired`), `escrowedAmount` is set to `_orders[commitment][token]` — the *complete* remaining escrow balance stored under that token key — instead of the proportional share tied to `order.inputs[i]`. This "grab everything" behavior was explicitly introduced (per the rounding-dust test comment) to avoid leaving truncation dust locked when a single input token backs a single output leg. But nothing in `placeOrder`/the `Order` struct enforces that each input token is used to back only one output leg. If an order's `inputs` array repeats the same token across two indices (e.g., `inputs[0].token == inputs[2].token == TokenA`, backing `output[0]` and `output[2]` respectively), then filling `output[0]` alone (even a very small, cheap leg) causes `escrowedAmount = _orders[commitment][TokenA]`, which is the sum of *both* legs' escrowed TokenA — not just the leg being filled.

The withdrawal path then blindly decrements by that inflated amount: [3](#0-2) 

This zeroes out the escrow that was meant to back the still-unfilled `output[2]` leg. A later solver attempting to complete `output[2]` will find `_orders[commitment][TokenA] == 0` and be blocked by `if (escrowed == 0) revert UnknownOrder();`, permanently stranding that leg while the first solver has already walked away with tokens they did not pay for.

Existing guards do not stop this: `remaining`/`alreadyFilled` tracking in `_partialFills` is keyed per `outputToken`, correctly preventing double-fill of the *same* output leg, but it has no visibility into the fact that the *input* escrow pool is shared across multiple output legs. There is no check that each input token index maps 1:1 and exclusively to one output leg.

### Impact Explanation
This is a direct, unauthorized transfer of escrowed user funds to an opportunistic solver, and a fund-lock for the order creator's remaining leg — matching the bounty's "stealing or loss of funds," "unauthorized transaction or execution," and "logic attacks" categories. No relayer, prover, or admin compromise is needed; the same-chain fill path (`fillOrder` → `_fillSameChain`) is a fully public, unprivileged entrypoint.

### Likelihood Explanation
Any user (or solver acting as the order-placer, or a third party who crafts/relays an order with duplicate input tokens across legs) can trigger this by placing an order whose `inputs` array reuses a token across multiple output pairs, then having any solver fill the cheapest of those legs. No special privileges, timing races, or off-chain cooperation are required — a single `fillOrder` call on the smallest leg is sufficient to trigger the over-release.

### Recommendation
Track escrow per `(commitment, inputIndex)` rather than per `(commitment, token)`, or compute the full-fill release strictly as the residual `order.inputs[i].amount` for that specific leg (tracking already-released amount per index) instead of reading the shared token-keyed balance. Alternatively, enforce at `placeOrder` time that each input token backs exactly one output leg (reject orders with duplicate `inputs[*].token` values), and add an invariant check in `_withdraw`/`_fillSameChain` that the amount released never exceeds the specific leg's proportional share of `_orders[commitment][token]`.

### Proof of Concept
1. User places a same-chain order with `inputs = [ {TokenA, 500}, {TokenB, 100}, {TokenA, 500} ]` and `outputs = [ {TokenX, 100}, {TokenY, 50}, {TokenZ, 1000} ]` (indices 0 and 2 both escrow TokenA, backing separate output legs). Escrow storage now holds `_orders[commitment][TokenA] = 1000`.
2. A solver fills only `output[0]` (100 TokenX) — a cheap leg — via `fillOrder`. In `_fillSameChain`, `i = 0`, `amountFilled == totalRequired` for output[0], so `escrowedAmount = _orders[commitment][TokenA]` reads the full `1000`, not the `500` allocated to `inputs[0]`.
3. `_withdraw` transfers the full `1000` TokenA to the solver and sets `_orders[commitment][TokenA] = 0`.
4. Any solver attempting to later fill `output[2]` (targeting the 500 TokenA meant for that leg) finds `_orders[commitment][TokenA] == 0` and reverts with `UnknownOrder()` — the leg can never be filled, and the user's second TokenA allocation is gone, captured entirely by the first solver.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
