### Title
Blame proof reveals the ECDH key before the message's proof-of-possession is verified, leaking a co-opted sender's secret share plaintext - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
The PedPoP DKG encrypts each secret share with a per-message ECDH key so a single message's key can be revealed during blame without side effects. A proof-of-possession (`pop`) exists specifically to stop an attacker from copying someone else's per-message key and triggering a blame that reveals the victim's message. However, `KeyMachine::calculate_share` returns the blame `EncryptionKeyProof` — which contains the raw ECDH shared point — on a non-canonical-share early return *before* the batched PoP verification is ever run. An unprivileged participant can therefore replay-and-mangle another sender's ciphertext to force the victim's ECDH key to be published, decrypting the victim's secret-share message. This is a direct analog of CVE-2018-12374: protected plaintext leaks out through an unintended user-triggered action path.

### Finding Description
In `Encryption::decrypt` (crypto/dkg/pedpop/src/encryption.rs:479-500), the PoP is only *queued* into the `BatchVerifier`, while the ECDH key `ecdh(enc_key, msg.key)` is computed immediately and returned inside an `EncryptionKeyProof` alongside a DLEq proof of correctness. In `KeyMachine::calculate_share` (crypto/dkg/pedpop/src/lib.rs:476-499), when the decrypted bytes fail `C::F::from_repr`, the function early-returns `PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }` at line 480-482 — exiting before `batch.verify_with_vartime_blame()` at line 493. The design comment at encryption.rs:84-88 acknowledges exactly this attack shape (copying Alice's `msg.key` so a blame reveals `bX`, decrypting Alice's message) and states the PoP is the mitigation — but the mitigation is only enforced inside the batch verification, which is skipped by this error path. `Decryption::decrypt_with_proof` (encryption.rs:374-397) will correctly blame the attacker afterwards, but by then the shared key `bX` is already public.

### Impact Explanation
Any participant Eve can take Alice's authenticated `EncryptedMessage` to Bob (`key = X`, ciphertext `C`), flip bits in the ciphertext, attach any `key`/PoP fields, and submit it as her own share to Bob. Bob's `calculate_share` computes `bX` (the genuine Alice↔Bob ECDH key), decrypts to garbage, fails `from_repr`, and returns `blame = Some(EncryptionKeyProof { key: bX, dleq })`. When Bob publishes the blame per protocol, every participant obtains `bX` and can decrypt `C`, recovering Alice's secret-share polynomial evaluation `f_A(b)` for Bob. Leaked per-sender shares reduce the effective security of the generated threshold key; combined with honest shares an attacker can reconstruct or bias key material. This is secret-share plaintext recovery reachable purely with public DKG round messages.

### Likelihood Explanation
The attack requires only a DKG participant (or anyone able to feed shares to a `KeyMachine`, since messages arrive over the authenticated channel the attacker can also write to as a participant) to replay a victim's message with modified ciphertext. No collusion, no key knowledge, and no broken primitives are needed — the vulnerable ordering (decrypt-and-emit-proof before batch PoP verification) is deterministic and triggers whenever the mangled ciphertext decodes to a non-canonical scalar, which is overwhelming likely for random garbage. Medium likelihood in a real validator set, since DKG sessions run with mutually untrusted operators.

### Recommendation
Do not emit an `EncryptionKeyProof` until the message's PoP has been verified. Concretely, in `KeyMachine::calculate_share`, restructure so `from_repr`/share failures observed before `batch.verify_with_vartime_blame()` return `blame: None` (treat as a decryption-phase failure like `BatchId::Decryption`), or verify the PoP inline before producing blame. Alternatively, make `Encryption::decrypt` return the proof only after the queued batch verifies, deferring blame-proof construction to post-verification handling. Also consider binding the sender index more explicitly or rejecting reused `msg.key` values across messages so a copied key field can be detected before decryption.

### Proof of Concept
1. Run a `t`-of-`n` PedPoP session (e.g., the `commit_enc_keys_and_shares` harness in crypto/dkg/pedpop/src/tests.rs). Alice (sender `ONE`) produces `EncryptedMessage { key: X, pop, msg: C }` to Bob (`TWO`) where `C` encrypts a canonical share under keystream derived from `bX`.
2. Eve (`THREE`) copies `X` and `C'` = `C` with bits flipped, signs a PoP over `C'` with her own per-message key (or any PoP — it is never checked on this path), and submits it to Bob as her share.
3. Bob's `calculate_share` calls `self.encryption.decrypt(...)`: PoP is queued to `batch`, `key = ecdh(b, X) = bX` is computed, `C'` decrypts to non-canonical bytes, `C::F::from_repr` returns `None`, and the function early-returns `InvalidShare { participant: THREE, blame: Some(EncryptionKeyProof { key: bX, ... }) }` at lib.rs:480-482 — before `batch.verify_with_vartime_blame()` at lib.rs:493 ever checks the PoP.
4. Bob publishes the blame. Anyone applies `cipher(context, bX)` to Alice's original `C`, recovering Alice's plaintext share for Bob. Blame adjudication still fingers Eve, but the victim's share is already leaked — matching the CVE-2018-12374 pattern of decrypted plaintext escaping via an unintended path.
