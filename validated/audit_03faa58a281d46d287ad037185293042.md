The targeted file `app/src/models/github-repository.ts` only defines a permission type and a plain data class — it contains no matching, comparison, or credential-selection logic whatsoever. [1](#0-0) [2](#0-1) 

`GitHubRepositoryPermission` is simply a `'read' | 'write' | 'admin' | null` union used to record the user's permission level on a repo, consumed only by `hasWritePermission`, which has no bearing on account/endpoint selection. [3](#0-2) 

The actual account/endpoint selection logic lives elsewhere and uses strict equality on `endpoint`, not on owner/name or permission fields: `getAccountForEndpoint` does `accounts.find(a => a.endpoint === endpoint)`. [4](#0-3) 

`findAccountForRemoteURL` (used for remote-URL-to-account matching) compares parsed hostnames exactly, and falls back to an "owner/name" lookup only after filtering candidate accounts by exact hostname match before calling `canAccessRepository` against the live API — it does not blend results across different endpoints/hosts. [5](#0-4) 

Other call sites (`app-store.ts`, `commit-status-store.ts`, `background-fetcher.ts`, `get-account-for-repository.ts`) all key off `repository.gitHubRepository.endpoint` via `getAccountForEndpoint`, again strict string equality, not owner/name-based collision. [6](#0-5) 

There is no code path where an attacker-controlled remote URL or owner/name reaching `GitHubRepositoryPermission` could cause cross-account/endpoint token confusion — the permission field is purely descriptive metadata, and the actual account-selection functions rely on exact endpoint-hostname equality checks that reject mismatched hosts. /** Get the authenticated account for the repository. */
export function getAccountForRepository(
  accounts: ReadonlyArray<Account>,
  repository: Repository
): Account | null {
  const gitHubRepository = repository.gitHubRepository
  if (!gitHubRepository) {
    return null
  }

  return getAccountForEndpoint(accounts, gitHubRepository.endpoint)
}
