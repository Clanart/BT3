## Analysis

The Velodrome bug's core broken invariant is: **a reward/escrow ledger entry is decremented but never zeroed/reset after payout, and the "has funds" guard only checks non-zero instead of comparing against the exact amount being paid — allowing repeated payout calls to drain more than was ever escrowed.**

The direct local analog is in `IntentGatewayV2.sol`'s escrow settlement path.

### Title
Escrow ledger in `IntentGatewayV2.withdraw()` is decremented by caller-supplied amount instead of zeroed/exact-matched, enabling duplicate escrow payout - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()`, which is invoked from `onAccept` (RedeemEscrow/RefundEscrow) and from `onGetResponse` (destination-proven cancellation), settles the `_orders[commitment][token]` escrow map the same way `Bribe.deliverReward()` settled `tokenRewardsPerEpoch`: it only checks that the balance is non-zero, then subtracts the amount being paid, without ever validating that the subtracted amount equals the full remaining balance or explicitly deleting the entry. [1](#0-0) 

### Finding Description
In `withdraw()`, for each token in the withdrawal body:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
... transfer(beneficiary, amount) ...
_orders[body.commitment][token] -= amount;
```
The guard only rejects a fully-exhausted balance (`== 0`); it never asserts `amount == _orders[commitment][token]` nor deletes the slot. This is structurally identical to `Bribe.deliverReward()`'s failure to zero `tokenRewardsPerEpoch[token][epochStart]` after transfer — as long as any positive residual remains, a second call with the same commitment passes the guard and pays out again. [2](#0-1) 

`withdraw()` can be reached twice for the same order commitment via `cancelOrder`'s source-chain branch, which — unlike the destination-chain branch that immediately sets `_filled[commitment]` before dispatching — does **not** set any local "cancellation in flight" flag before dispatching its `DispatchGet` storage-proof query: [3](#0-2) 

Each call only checks `_orders[commitment][token] == 0` (existence, not idempotency) before dispatching: [4](#0-3) 

Because the `DispatchGet` request encodes `options.height` into the request, two calls to `cancelOrder` for the same order at different (or even queued/pending) heights produce two distinct ISMP requests/commitments — ISMP's own commitment-based replay protection does not consider them duplicates. If the destination order remains unfilled for both queries (plausible in any window before a solver fills or before the first refund lands), both resolve through `onGetResponse`: [5](#0-4) 

Each resolution calls `withdraw(body, true)` with the identical `body.commitment`. The first call pays the beneficiary and decrements the ledger by `amount`; if that decrement does not drive the entry to exactly zero (e.g. `amount` supplied in the cross-chain body does not exactly equal what remains in `_orders[commitment][token]`), the second call still passes the `!= 0` check and pays out again from the same escrow.

### Impact Explanation
This is a duplicate-settlement / fund-loss bug on a public, unprivileged entrypoint: `cancelOrder`. An order owner can trigger two independent escrow-release attempts against the same commitment without any relayer collusion, malicious prover, or admin action — only correctly-delivered, honestly-proven ISMP messages are needed. A successful double-resolution drains escrowed tokens beyond what a single refund/redemption should pay, at the expense of the pool of escrowed funds belonging to other orders/users in the contract (since `_orders` is a shared contract-wide ledger keyed by commitment, but token balances are pooled in the single contract).

### Likelihood Explanation
Likelihood is bounded by whether a partial/non-exact decrement is actually reachable in practice (I could not fully verify, within the available context, whether `body.tokens[i].amount` supplied in `WithdrawalRequest` always exactly equals the stored `_orders[commitment][token]` value credited at order-placement time — `newOrder()` credits `reducedInputs[i].amount`, i.e., an amount already adjusted for protocol fees, while `cancelOrder`'s same-chain and source-chain branches build the `WithdrawalRequest` from `order.inputs`, the pre-fee-adjustment amount). If these two values diverge, the missing exact-match/zeroing invariant becomes directly exploitable exactly as described; if they always coincide exactly, the bug degrades to a latent defense-in-depth gap (still absent an idempotency guard on the ledger itself) rather than an immediately provable fund-loss. This uncertainty could not be fully resolved with the tools available in this session — a background engineering session with full repository access should verify the exact relationship between `order.inputs[i].amount` and the value stored in `_orders[commitment][token]` at escrow-credit time, and should audit all call sites of `withdraw()` for missing idempotency/exact-amount checks.

### Recommendation
- In `withdraw()`, replace the subtract-and-check pattern with an exact read-and-delete: read `_orders[commitment][token]` once, `delete` it (or set to `0`) before transferring, and use the stored value as the authoritative transfer amount rather than trusting `body.tokens[i].amount` from the message.
- Add an explicit idempotency marker per commitment (e.g., check/set `_filled[commitment]` at the very top of `withdraw()`, consistent with how the destination-chain cancel branch already does it) so a second resolution for the same commitment reverts unconditionally, regardless of remaining ledger balance.
- Audit `cancelOrder`'s source-chain branch to prevent dispatching multiple concurrent `DispatchGet` cancellation queries for the same commitment (e.g., a "cancellation pending" flag), closing the multi-dispatch path entirely.

### Proof of Concept
1. User places a cross-chain order via `newOrder()`, escrowing tokens; `_orders[commitment][token]` is credited.
2. Order expires unfilled. User calls `cancelOrder(order, options1)` on the source chain — passes the `_orders[commitment][token] == 0` check, dispatches `DispatchGet` query #1 (height = h1).
3. Before query #1 resolves, user calls `cancelOrder(order, options2)` again (height = h2) — the same non-zero check still passes because no ledger mutation nor pending-flag has occurred yet; dispatches a second, independent ISMP `DispatchGet` request.
4. Both queries return "order unfilled" and are independently, honestly delivered by relayers/provers (no malicious behavior required).
5. `onGetResponse` fires twice, each calling `withdraw(body, true)` with the same `commitment`.
6. First call: passes `_orders[commitment][token] == 0` check, transfers `amount`, decrements ledger.
7. Second call: if the ledger entry did not reach exactly zero after step 6 (non-exact `amount` vs. stored balance), the `== 0` guard still passes, and the beneficiary is paid a second time from the same escrow — a duplicate settlement/fund-loss event exactly mirroring the Bribe `deliverReward()` M-14 pattern.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];

            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
