### Title
Unchecked Cumulative Block Gas Usage During Block Assembly — GasPool Enforcement Is Dead Code - ([File: work/worker.go], [File: blockchain/gaspool.go])

### Summary
Kaia declares a `GasPool` type with `SubGas`/`AddGas` intended to bound the total gas consumed by transactions packed into a block (mirroring go-ethereum's `core.GasPool` pattern), but this type is never instantiated or invoked anywhere in the actual block-building or transaction-application code path. As a result, the miner/proposer's transaction-selection loop only ever bounds the *byte size* of the block, never the *cumulative gas* consumed by the included transactions — the exact bug class described in the external report for `cosmos-sdk`/`block-sdk`.

### Finding Description
`blockchain/gaspool.go` defines `GasPool` with `SubGas` returning `ErrGasLimitReached` when the pool is exhausted [1](#0-0) , and `blockchain/error.go` documents this as the mechanism that should reject transactions "if the amount of gas required ... is higher than what's left in the block" [2](#0-1) . However, a repo-wide search shows `GasPool` is referenced only inside `blockchain/gaspool.go` itself and a doc comment — it is never constructed with a block gas limit nor passed into `ApplyMessage`/`ApplyTransaction`/`ApplyTransactions` anywhere in the codebase.

Concretely, `blockchain.BlockChain.ApplyTransaction` (the function invoked once per transaction during both block building and block validation) takes no gas-pool argument and performs no check that `*usedGas` (i.e., `header.GasUsed`) stays under any block gas limit before or after calling `ApplyMessage` [3](#0-2) .

On the block-proposer side, `work/worker.go`'s `Task.ApplyTransactions` / `CommitTransactionLoop` only gates inclusion of a transaction on `env.txFitsSize(tx)` / `env.txFitsSizeForBundle(...)` (byte-size checks) and blob-space checks (`env.hasBlobSpace`) before calling `commitTransaction`/`commitBundleTransaction` [4](#0-3) . Neither of these calls, nor `commitTransaction` itself [5](#0-4) , nor `commitBundleTransaction` [6](#0-5) , checks the running total of `env.header.GasUsed` against any configured block gas ceiling. `header.GasUsed` is simply accumulated by `bc.ApplyTransaction` without a corresponding cap check anywhere in this loop.

This is structurally identical to the reported `block-sdk` `DefaultPrepareLaneHandler` bug: the proposer/lane-building logic bounds `totalSize` against `maxTxBytes` but never bounds accumulated gas against the block's gas limit, allowing the built payload to exceed the intended computational budget of the block.

### Impact Explanation
Because gas accumulation is unbounded relative to any block-level cap, a block producer (or, indirectly, unprivileged senders submitting many transactions with high gas limits/large gas usage but small byte footprints) can cause a block to be assembled whose total executed gas far exceeds the chain's intended per-block computational budget. Since `header.GasLimit`/gas-limit enforcement is not exercised anywhere in the transaction inclusion loop, blocks can be produced and accepted that violate the chain's configured gas budget — this is an "acceptance of an invalid block" class issue: nodes have no code path that would reject a block for exceeding an intended gas ceiling, since the only enforcement primitive (`GasPool`) is unused. This can be leveraged to inflate block processing cost, degrade honest-node synchronization/import time uniformly (denial-of-service via processing-cost blowout), and, combined with MEV bundle execution (`commitBundleTransaction`/`ApplyTransactions`), allows adversarial actors to force disproportionately expensive blocks that a properly gas-limited network would have rejected or truncated.

### Likelihood Explanation
Any transaction sender or bundle submitter can trigger this by crafting transactions/bundles with high gas usage relative to byte size (e.g., heavy computation, large loops, or many bundled transactions), since the only admission control in `CommitTransactionLoop` is the byte-size check (`txFitsSize`/`txFitsSizeForBundle`) and blob-space check — gas is never checked cumulatively. No special privileges beyond normal transaction submission or (for bundle-based amplification) auction/bundle participation are required.

### Recommendation
Instantiate a `blockchain.GasPool` sized to the block's configured gas limit (`header.GasLimit` or the equivalent chain-configured gas ceiling) at the start of `Task.ApplyTransactions`, and call `gasPool.SubGas(msg.Gas())` (or the actual gas consumed) before/while committing each transaction and bundle in `commitTransaction`/`commitBundleTransaction`, aborting the `CommitTransactionLoop` when `ErrGasLimitReached` is returned — mirroring how `txFitsSize` currently gates on byte size. Additionally, add a corresponding cumulative-gas check in `blockchain.BlockValidator.ValidateBody`/`ValidateHeader` so that blocks received from peers are rejected if their total `GasUsed` (or sum of transaction gas) exceeds the block's declared/expected gas limit.

### Proof of Concept
1. Submit (or have a bundle submitter submit via `txBundlingModules`) a sequence of transactions/bundles whose individual byte sizes are small (so they pass `env.txFitsSize`/`env.txFitsSizeForBundle`) but whose declared `GasLimit`/actual gas consumption is very large (e.g., computation-heavy contract calls near `params.UpperGasLimit`).
2. Observe in `Task.ApplyTransactions` (`work/worker.go`) that inclusion is gated only by `txFitsSize`/blob-space checks; there is no call site anywhere that constructs a `blockchain.GasPool` or calls `SubGas` against `env.header.GasUsed`.
3. Continue submitting until the block's byte-size budget (`maxTxBytes`-equivalent) is reached — at that point `env.header.GasUsed` can already exceed the chain's intended block gas budget, since gas was never checked, only bytes.
4. Confirm via `blockchain.BlockChain.ApplyTransaction` (`blockchain/blockchain.go:2792-2846`) that no gas-pool parameter or cumulative-gas assertion exists in the transaction-application path used both for mining and for validating imported blocks — i.e., the resulting over-gas block will also pass validation on receiving nodes.

// SubGas deducts the given amount from the pool if enough gas is
// available and returns an error otherwise.
func (gp *GasPool) SubGas(amount uint64) error {
	if uint64(*gp) < amount {
		return ErrGasLimitReached
	}
	*(*uint64)(gp) -= amount
	return nil
}

func (env *Task) commitTransaction(tx *types.Transaction, bc BlockChain, nodeAddr common.Address, vmConfig *vm.Config) (error, []*types.Log) {
	snap := env.state.Snapshot()

	receipt, _, err := bc.ApplyTransaction(env.config, &nodeAddr, env.state, env.header, tx, &env.header.GasUsed, vmConfig)
	if err != nil {
		if err != vm.ErrInsufficientBalance && err != vm.ErrTotalTimeLimitReached {
			tx.MarkUnexecutable(true)
		}
		env.state.RevertToSnapshot(snap)
		return err, nil
	}

	env.tcount++
	env.txs = append(env.txs, tx)
	env.receipts = append(env.receipts, receipt)
	env.size += uint64(tx.Size())
	if tx.Type() == types.TxTypeEthereumBlob {
		env.blobs += len(tx.BlobHashes())
		*env.header.BlobGasUsed += tx.BlobGas()
	}

	return nil, receipt.Logs
}
