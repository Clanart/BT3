### Title
Alpenglow per-slot validator reward calculation divides by whole-epoch `total_stake` while only paying `reward_validators`, permanently diluting active-validator rewards - (File: `runtime/src/block_component_processor/vote_reward.rs`)

### Summary
The Concur `MasterChef` bug is a class of "denominator that can only grow/never shrinks to match active recipients" issue: `totalAllocPoint` accumulates every pool ever added, but rewards are only handed out to pools that are actually used, so idle allocation permanently dilutes payouts to active stakers. Agave's Alpenglow per-slot validator reward computation has the same structural shape: the reward denominator (`total_stake`, taken once from `EpochStakes::total_stake()`) reflects the entire epoch's staked lamports, but the numerator side (`reward_validators`, the validator set attested in a given slot's `ValidatedRewardCert`) only pays out to whoever is actually in that cert.

### Finding Description
`RewardState::try_new` fixes `total_stake` for the reward slot as the full epoch stake weight: [1](#0-0) 

`calculate_reward`/`calculate_reward` (module function) then compute each validator's slot reward as `max_possible_validator_reward * validator_stake_lamports / (slots_per_epoch * total_stake_lamports)`: [2](#0-1) 

But only validators present in `reward_validators` (the cert's validator set for that specific slot) actually receive a payout — `update_account` gates on `self.reward_validators.contains(&vote_state.vote_pubkey)`, and the top-level iteration in `update_accounts` only visits `state.reward_validators.iter().cloned()` (or the union with `final_cert` signers): [3](#0-2) [4](#0-3) 

This is exactly analogous to `totalAllocPoint` in MasterChef: the denominator (`total_stake`) includes every staked lamport in the epoch's `EpochStakes` snapshot — including stake delegated to validators that are offline, delinquent, or simply absent from this particular slot's reward certificate — while only the numerator side (`reward_validators`) shrinks per slot. There is no compensating adjustment that removes a non-participating validator's stake from `total_stake` for that slot, just as MasterChef never lets `totalAllocPoint` shrink when a pool becomes unused.

### Impact Explanation
Every lamport of stake belonging to a validator who is not in a given slot's `reward_validators` set is still counted in the fixed `total_stake` divisor, but earns nothing for that slot. The pool of `max_possible_validator_reward` lamports intended for that slot is therefore only partially distributed: active/participating validators are paid `fractional_stake_of_active_validator / total_stake`, not `fractional_stake_of_active_validator / total_active_stake`, so they receive strictly less than their proportional share of the actually-payable budget any time any stake is not represented in the per-slot cert. The undistributed remainder is not recovered or redirected — it is simply never minted/credited to anyone for that slot, a systemic under-payment of validator/staker rewards, i.e., an unrecoverable value leak on the reward-distribution path, mirroring the confirmed Medium-severity MasterChef dilution finding.

### Likelihood Explanation
This does not require a malicious peer, admin, or leaked key — it triggers under ordinary, expected conditions: any epoch/slot in which some fraction of staked validators is offline, catching up, or otherwise excluded from a specific slot's reward certificate while `total_stake` still reflects their full epoch-stake weight. Because validator downtime and partial certification are routine (not adversarial), this dilution is expected to occur continuously across nearly every slot with less-than-100% validator participation, making it a systemic, unprivileged, protocol-inherent economic bug rather than a hypothetical edge case.

### Recommendation
Compute the reward denominator from the actual per-slot active/participating stake (e.g., sum of `reward_slot_validator_stake` over `reward_validators`) rather than the static whole-epoch `total_stake`, so that non-participating stake is excluded from the divisor for that slot — analogous to the MasterChef fix of allowing `totalAllocPoint` to be adjusted or unused pools removed so it reflects only currently-eligible allocation.

### Proof of Concept
1. At epoch boundary, `EpochStakes::total_stake()` fixes `total_stake` = sum of all delegated stake for the epoch (e.g., 1000 SOL across 10 validators, 100 SOL each) — see `RewardState::try_new`, `runtime/src/block_component_processor/vote_reward.rs:198`.
2. In a given reward slot, only 8 of the 10 validators are present in the `ValidatedRewardCert`'s `validators()` set (`reward_validators`), because 2 are offline/catching up.
3. `calc_vote_rewards_update_vote_states` iterates only `reward_validators` (`runtime/src/block_component_processor/vote_reward.rs:456-479`), so only the 8 active validators' `update_account` is invoked; the 2 absent validators receive no credits for this slot.
4. Each of the 8 active validators is paid via `calculate_reward` using `total_stake_lamports` = 1000 SOL (all 10 validators' stake), not 800 SOL (`runtime/src/block_component_processor/vote_reward.rs:488-510`), so each gets `100/1000` share instead of the correct `100/800` share.
5. Sum of rewards actually paid for the slot = 80% of `max_possible_validator_reward`; the remaining 20% budgeted for that slot is permanently unallocated to any staker, repeating every slot any validator is absent from the reward cert — a continuous dilution identical in mechanism to the MasterChef `totalAllocPoint` bug.

    epoch_state: &EpochInflationState,
    total_stake_lamports: u64,
    validator_stake_lamports: u64,
) -> (u64, u64) {
    // Rewards are computed as following:
    // per_slot_inflation = epoch_validator_rewards_lamports / slots_per_epoch
    // fractional_stake = validator_stake / total_stake_lamports
    // rewards = fractional_stake * per_slot_inflation
    //
    // The code below is equivalent but changes the order of operations to maintain precision

    let numerator =
        epoch_state.max_possible_validator_reward as u128 * validator_stake_lamports as u128;
    let denominator = epoch_state.slots_per_epoch as u128 * total_stake_lamports as u128;

    // SAFETY: the result should fit in u64 because we do not expect the inflation in a single
    // epoch to exceed u64::MAX.
    let reward_lamports: u64 = (numerator / denominator).try_into().unwrap();

    let validator_reward_lamports = reward_lamports / 2;
    let leader_reward_lamports = reward_lamports - validator_reward_lamports;
