## Title
Type-contract violation in `get_template_singleton_inner_puzzle` returns `False` instead of `Program | None`, causing local exceptions during pool/plotnft singleton spend construction - (File: chia/pools/pool_puzzles.py)

### Summary
`chia/pools/pool_puzzles.py` contains helper functions that are declared to return a `Program` (or a tuple of typed values) but actually return the boolean `False` on the failure path when `Program.uncurry()` fails to match the expected shape. This is structurally the same bug class as the RefindPlus `InternalApfsTranslateBlock` issue: a helper that should signal "no result" via `None`/an error instead returns a sentinel of the wrong type, and callers that expect a well-typed object (and, in some call sites, deref it with `==`, `.get_tree_hash()`, or unpacking) can hit unexpected `AttributeError`/unpacking failures when fed a malformed/adversarial curried puzzle.

### Finding Description
`get_template_singleton_inner_puzzle` at `chia/pools/pool_puzzles.py:148-153` is annotated to return `Program`, but on the `uncurry()` failure branch it returns `False`:
```python
def get_template_singleton_inner_puzzle(inner_puzzle: Program) -> Program:
    r = inner_puzzle.uncurry()
    if r is None:
        return False
    uncurried_inner_puzzle, _args = r
    return uncurried_inner_puzzle
```
Similarly, `get_seconds_and_delayed_puzhash_from_p2_singleton_puzzle` at `chia/pools/pool_puzzles.py:156-164` is annotated `-> tuple[uint64, bytes32]` but also returns `False` on the same failure path.

`get_template_singleton_inner_puzzle` is used by `is_pool_singleton_inner_puzzle`, `is_pool_waitingroom_inner_puzzle`, and `is_pool_member_inner_puzzle` (`chia/pools/pool_puzzles.py:168-180`) to classify an untrusted, on-chain inner puzzle (derived from a coin's `puzzle_reveal`) as a pool-member or waiting-room puzzle. These classifier functions are, in turn, invoked from `create_travel_spend` and `create_absorb_spend` (`chia/pools/pool_puzzles.py:202,207,265,268`), which build a pool wallet's next spend from state reconstructed off an arbitrary/attacker-influenced parent coin spend (`pool_state_to_inner_puzzle`, `get_inner_puzzle_from_puzzle`) during normal pool-participant (plotnft) sync/travel/absorb flows.

Because the failure sentinel is `False` (a bool) instead of `None`, any code path relying on `is r is None` semantics, or that later tries to treat the returned value as a `Program` (e.g., calling `.get_tree_hash()` or comparing it against `POOL_MEMBER_MOD`/`POOL_WAITING_ROOM_MOD`), is exercising undefined/incorrect behavior for a value that violates its type contract. `False == POOL_MEMBER_MOD` will silently evaluate `False` (not raise), so `is_pool_member_inner_puzzle`/`is_pool_waitingroom_inner_puzzle` both return `False`, falling through to the `else: raise ValueError` branches in `create_travel_spend`/`create_absorb_spend` — an unhandled exception raised while a pool wallet is trying to process/spend a singleton coin whose inner puzzle cannot be uncurried into the expected pool template.

### Impact Explanation
This a local, wallet-side denial-of-service / processing halt: a plotnft/pool participant syncing against a maliciously-crafted (or merely malformed) singleton inner puzzle on chain can trigger an unhandled `ValueError` inside `create_travel_spend`/`create_absorb_spend`, aborting the pool wallet's spend-bundle construction for that singleton. This matches the "spend-triggered transaction-processing halt" acceptance criterion for local pool wallet users. It does not directly produce coin-set divergence, forged assets, or unauthorized fund movement — the impact is confined to local processing correctness/availability for pool wallet operations, consistent with the CVE's own "null/type mismatch causing crash" classification (Medium severity, local scope).

### Likelihood Explanation
Likelihood is limited: `create_travel_spend`/`create_absorb_spend` are pool-wallet-internal helpers invoked by `pool_wallet.py` during its own state-machine flow (travel/absorb spends), not directly on arbitrary attacker-supplied singleton puzzles chosen by a remote peer without any other constraint — the inner puzzle passed in originates from `pool_state_to_inner_puzzle`, which the wallet itself constructs from its tracked `PoolState`, so under normal operation the mismatch cannot occur. The vulnerable type contract (`False` instead of `None`) is nonetheless a real code defect that would manifest if `pool_state_to_inner_puzzle`'s inputs are ever influenced by untrusted on-chain data (e.g. through `get_inner_puzzle_from_puzzle` fed a `last_coin_spend.puzzle_reveal` observed on-chain, at `chia/pools/pool_puzzles.py:230,281`) that does not match the expected mod. I was unable to fully trace every call path into `pool_wallet.py` to confirm a fully attacker-controlled trigger within the available search budget, so likelihood should be treated as uncertain/lower-bound rather than confirmed.

### Recommendation
Change `get_template_singleton_inner_puzzle` and `get_seconds_and_delayed_puzhash_from_p2_singleton_puzzle` to return `None` (matching their honest optional semantics) instead of `False`, and update their type hints to `Program | None` / `tuple[uint64, bytes32] | None` respectively. Update all call sites (`is_pool_member_inner_puzzle`, `is_pool_waitingroom_inner_puzzle`, `is_pool_singleton_inner_puzzle`) to explicitly check `is None` and propagate a clear, caught error (rather than allowing an uncaught `ValueError` to bubble out of spend construction) when a coin's inner puzzle cannot be uncurried into the expected pool template.

### Proof of Concept
Not independently reproduced end-to-end due to tool/iteration limits; the defect is demonstrated statically:
```python
from chia.pools.pool_puzzles import get_template_singleton_inner_puzzle, is_pool_member_inner_puzzle
from chia.types.blockchain_format.program import Program

# Any puzzle that Program.uncurry() cannot decompose (e.g. an uncurried atom)
bogus_puzzle = Program.to(1)
result = get_template_singleton_inner_puzzle(bogus_puzzle)
assert result is False  # violates the declared `-> Program` return type
assert is_pool_member_inner_puzzle(bogus_puzzle) is False  # silently swallowed by False == POOL_MEMBER_MOD
```
Feeding such a puzzle into `create_travel_spend`/`create_absorb_spend` (both classifier checks failing) reaches the `else: raise ValueError` branch, aborting spend construction. A full chain-level trigger from an untrusted peer/coin was not confirmed within the scope of this review.
