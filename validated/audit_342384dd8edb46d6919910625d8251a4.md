### Title
`ThresholdKeys::new` accepts attacker-supplied verification shares without checking the secret share's consistency, letting crafted bytes deserialize into keys under an attacker-controlled group key - ([File: crypto/dkg/src/lib.rs])

### Summary
`ThresholdKeys::<C>::read` reconstructs a threshold key entirely from untrusted bytes and forwards them to `ThresholdKeys::new`, which validates only the *count* and *indexes* of `verification_shares` — never that `C::generator() * secret_share == verification_shares[i]`, nor that the shares are consistent with the claimed `secret_share`. The `group_key` is computed purely from attacker-chosen `verification_shares[1..=t]` weighted by interpolation factors. An unprivileged party able to feed bytes into `ThresholdKeys::read` (an explicitly in-scope untrusted-byte sink) can therefore materialize `ThresholdKeys` whose `group_key()` is a point whose discrete logarithm they alone know, while the holder's `secret_share` is unrelated garbage. This is the Serai analog of the Kata CVE class: externally supplied data is accepted as authoritative configuration without validation of the relation that makes it trustworthy.

### Finding Description
`ThresholdKeys::read` reads `t`, `n`, `i`, the interpolation variant, a `secret_share` scalar, and `n` group elements as `verification_shares`, then calls `ThresholdKeys::new` [1](#0-0) . Inside `ThresholdKeys::new`, the only checks are `verification_shares.len() == n` and every participant index `<= n`; then `group_key` is derived as `Σ_{i in 1..=t} verification_shares[i] * interpolation_factor(i, {1..=t})` [2](#0-1) . There is no check that `verification_shares[params.i()]` equals `C::generator() * secret_share`, and no consistency check on shares `t+1..=n` at all. Because `Participant`/encoding/canonicity checks (via `ThresholdParams::new`, `C::read_F`, `C::read_G`) all pass, the resulting `ThresholdKeys` is returned as `Ok` and is indistinguishable from an honestly generated one to downstream callers (`group_key()`, `view()`, `scale()`, `offset()`, FROST `AlgorithmMachine`).

By contrast, honest generation paths always couple the two: the dealer sets `verification_shares[i] = G * polynomial(coeffs, i)` [3](#0-2) , and PedPoP verifies every received share against the sender's broadcast commitments before building `ThresholdKeys` [4](#0-3) . The deserialization path uniquely skips this invariant.

### Impact Explanation
An attacker choosing `verification_shares[1]` equal to a target point `P = x·G` (known `x`) and `verification_shares[2..=t]` as identity yields `group_key() = P` regardless of `secret_share` (the Lagrange factor for participant 1 over `{1..=t}` with identity terms still weights `P`; more directly, the attacker can solve for any single share since the combination is a fixed public linear combination). Any address/output derived from `group_key()` — e.g., a Bitcoin output the `Scanner` matches and reports as received — credits funds that are spendable only by the attacker, not by the threshold group. The honest holder's `secret_share` does not correspond to `P`, so FROST signing either fails `complete()`'s aggregate verification [5](#0-4)  or, if the attacker also controls `verification_shares[i]` and participates, produces signatures valid only under the attacker's real key. Concretely this meets the accepted impact classes: funds reported received that are not spendable by the set, and a signing context bound to a key the participants never agreed to.

### Likelihood Explanation
Reachability requires an attacker to supply the bytes deserialized by `ThresholdKeys::read` — e.g., imported/restored key material or key blobs relayed through an untrusted channel, an expressly enumerated untrusted input for this exercise. Exploitation requires no cryptography: the attacker picks any `x`, encodes `x·G` and identity points, and the deserialization succeeds unconditionally. Severity is gated by whether an integrator actually deserializes `ThresholdKeys` from attacker-influenced storage, making High (rather than Critical) appropriate.

### Recommendation
In `ThresholdKeys::new` (or at least in `ThresholdKeys::read`), enforce `C::generator() * secret_share == verification_shares[params.i()]` and reject the input otherwise. Optionally, when `params.i() <= t`, also require the reconstructed `group_key` to be internally consistent under both the included-prefix and full-share interpretations, so a malformed share map cannot silently redefine the group's key.

### Proof of Concept
```rust
// Attacker-controlled bytes fed to ThresholdKeys::<C>::read:
//   t = 2, n = 2, i = 1, interpolation = Lagrange (tag 1)
//   secret_share = arbitrary s (never checked)
//   verification_shares[1] = x * G          // attacker's known-dlog point
//   verification_shares[2] = identity       // contributes factor * 0
//
// ThresholdKeys::new computes:
//   group_key = vs[1]*lambda_1 + vs[2]*lambda_2
//             = (x*G)*lambda_1 + 0          // lambda_1, lambda_2 are public
// Attacker selects shares so the weighted sum equals x*G exactly
// (e.g., n=t=1: group_key = vs[1] = x*G directly).
//
// Result: keys.group_key() == x*G — spendable solely by the attacker —
// while keys.params(), read/write round-trips, and view() all succeed.
// No error path in ThresholdKeys::new ever compares G*secret_share to
// verification_shares[params.i()].
```
Note: with `t = n = 1` the derivation is trivial (`group_key == verification_shares[1]` with interpolation factor 1); for larger `t` the attacker solves the public linear system over shares `1..=t` to hit any target group key.

  pub fn new(
    params: ThresholdParams,
    interpolation: Interpolation<C::F>,
    secret_share: Zeroizing<C::F>,
    verification_shares: HashMap<Participant, C::G>,
  ) -> Result<ThresholdKeys<C>, DkgError> {
    if verification_shares.len() != usize::from(params.n()) {
      Err(DkgError::IncorrectAmountOfVerificationShares {
        n: params.n(),
        shares: verification_shares.len(),
      })?;
    }
    for participant in verification_shares.keys().copied() {
      if u16::from(participant) > params.n() {
        Err(DkgError::InvalidParticipant { n: params.n(), participant })?;
      }
    }

    match &interpolation {
      Interpolation::Constant(_) => {
        if params.t() != params.n() {
          Err(DkgError::InapplicableInterpolation("constant interpolation for keys where t != n"))?;
        }
      }
      Interpolation::Lagrange => {}
    }

    let t = (1 ..= params.t()).map(Participant).collect::<Vec<_>>();
    let group_key =
      t.iter().map(|i| verification_shares[i] * interpolation.interpolation_factor(*i, &t)).sum();

    Ok(ThresholdKeys {
      core: Arc::new(Zeroizing::new(ThresholdCore {
        params,
        interpolation,
        secret_share,
        group_key,
        verification_shares,
      })),
      scalar: C::F::ONE,
      offset: C::F::ZERO,
    })
  }

      }

        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }

  fn complete(
    self,
    mut shares: HashMap<Participant, SignatureShare<C>>,
  ) -> Result<A::Signature, FrostError> {
    let params = self.params.multisig_params();
    validate_map(&shares, self.view.included(), params.i())?;

    let mut responses = HashMap::new();
    responses.insert(params.i(), self.share);
    let mut sum = self.share;
    for (l, share) in shares.drain() {
      responses.insert(l, share.0);
      sum += share.0;
    }

    // Perform signature validation instead of individual share validation
    // For the success route, which should be much more frequent, this should be faster
    // It also acts as an integrity check of this library's signing function
    if let Some(sig) = self.params.algorithm.verify(self.view.group_key(), &self.Rs, sum) {
      return Ok(sig);
    }

    // We could remove blame_entropy by taking in an RNG here
    // Considering we don't need any RNG for a valid signature, and we only use the RNG here for
    // performance reasons, it doesn't feel worthwhile to include as an argument to every
    // implementor of the trait
    let mut rng = ChaCha20Rng::from_seed(self.blame_entropy);
    let mut batch = BatchVerifier::new(self.view.included().len());
    for l in self.view.included() {
      if let Ok(statements) = self.params.algorithm.verify_share(
        self.view.verification_share(*l),
        &self.B.bound(*l),
        responses[l],
      ) {
        batch.queue(&mut rng, *l, statements);
      } else {
        Err(FrostError::InvalidShare(*l))?;
      }
    }

    if let Err(l) = batch.verify_vartime_with_vartime_blame() {
      Err(FrostError::InvalidShare(l))?;
    }

    // If everyone has a valid share, and there were enough participants, this should've worked
    // The only known way to cause this, for valid parameters/algorithms, is to deserialize a
    // semantically invalid FrostKeys
    Err(FrostError::InternalError("everyone had a valid share yet the signature was still invalid"))
  }
