## Title
`HostManager.onAccept` authenticates only the source chain, not the sender module, unlike every other Hyperbridge app - ([File: evm/src/core/HostManager.sol])

## Summary
`HostManager.onAccept` — the contract that executes cross-chain governance actions (`Withdraw`, `SetHostParam`) on every connected EVM chain — verifies only that the incoming ISMP `PostRequest.source` equals the Hyperbridge chain id. It never checks `request.from` against the expected governance module identifier. Every other `onAccept` implementation in this codebase (token bridges, intent gateways, the LayerZero adapter) checks both the source chain **and** the sender module address/id before trusting the payload. This is the same class of bug as the SSH `InsecureIgnoreHostKey()` report: the verification step exists but only checks a coarse-grained identity (which network/IP-equivalent = "which chain") while skipping the fine-grained identity check (which key/module = "who on that chain").

## Finding Description
`HostManager.onAccept` (evm/src/core/HostManager.sol:95-109):
```solidity
function onAccept(IncomingPostRequest calldata incoming) external override restrict(_params.host) {
    PostRequest calldata request = incoming.request;
    // Only the Hyperbridge parachain can send requests to this module.
    if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

    OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
    if (action == OnAcceptActions.Withdraw) {
        WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
        IHostManager(_params.host).withdraw(withdrawParams);
    } else if (action == OnAcceptActions.SetHostParam) {
        HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
        IHostManager(_params.host).updateHostParams(hostParams);
    }
}
``` [1](#0-0) 

The only trust check is `request.source.equals(hyperbridge())` — a chain-level identity check. There is no check equivalent to `keccak256(request.from) == keccak256(expectedModuleId)`.

Compare this to every sibling `onAccept` in the repo, which all layer a *module-level* check on top of the chain-level check:
- `ExtrinsicIntents._authenticate` requires `request.from` to equal the registered gateway instance address for `request.source`: [2](#0-1) 
- `HyperFungibleToken.onAccept` requires `keccak256(request.from) == keccak256(expectedSource)` in addition to the chain being in `_supportedChains`: [3](#0-2) 
- `HyperbridgeLzEndpoint.onAccept` requires `keccak256(request.from) == keccak256(abi.encodePacked(address(this)))`: [4](#0-3) 

On the source side, the intended sender of these governance messages is `pallet-ismp-host-executive`, which sets `from: PALLET_ID.to_bytes()` (`ModuleId::Pallet(PalletId(*b"hostexec"))`) when dispatching `Withdraw`/`updateHostParams` payloads: [5](#0-4) [6](#0-5) . But `HostManager` never verifies `request.from` equals this value — it accepts a `PostRequest` from *any* module on the Hyperbridge chain, as long as `request.source` matches the Hyperbridge chain id.

The low-level `IsmpDispatcher::dispatch_request` implementation used by all pallets copies `dispatch_post.from` verbatim into the outgoing `PostRequest` with no restriction on which pallet/account sets it: [7](#0-6) . The dispatching pattern documented for third-party pallet integrators shows this `from` field is fully caller-controlled at the call site: [8](#0-7) . This confirms `from` is not cryptographically or structurally bound to a specific pallet by the dispatcher itself — the sender-identity guarantee, if any, has to come entirely from the destination-side `onAccept` check, exactly like host-key verification has to come from the SSH client rather than the transport.

## Impact Explanation
If any code path on the Hyperbridge chain (a newly added pallet, a mis-configured integration, or a bug in an existing pallet) can dispatch a `PostRequest` to a `HostManager` address with attacker/unintended-influenced `from` bytes, `HostManager.onAccept` will execute it as legitimate governance:
- `Withdraw` → drains `EvmHost` fee-token/native revenue to an attacker-chosen `beneficiary` (`IHostManager(_params.host).withdraw(withdrawParams)` → `EvmHost.withdraw`, unauthenticated once `onAccept`'s single check passes).
- `SetHostParam` → rewrites `HostParams` (admin, handler, consensusClient, hostManager, fee token, challenge period, etc.) via `updateHostParams`, effectively taking over the host contract's trust roots on that EVM chain.

Both are direct "stealing/loss of funds" and "unauthorized transaction/execution" impacts within the bounty's required categories, because the *only* gate standing between an ISMP message and full governance execution is a single coarse chain-id equality check.

## Likelihood Explanation
This is a defensive-in-depth gap rather than a currently demonstrated, fully unprivileged exploit: in the code paths I could confirm, the pallets that are allowed to reach `HostManager` (`pallet-ismp-host-executive`, `pallet-bandwidth`'s governance dispatch) gate their calls behind `HostExecutiveOrigin`/`AdminOrigin` (root-level) before setting `from`, so under the *current* runtime wiring an external, unprivileged user cannot yet set `request.from` freely. However, `dispatch_request`'s `from` field is not protected by the ISMP dispatcher itself — it is copy-through from caller input — so the security of every `HostManager`-receiving governance action on every connected chain rests entirely on "no pallet added to the Hyperbridge runtime, now or in the future, ever lets an unprivileged caller pick `from`." That is a fragile, implicit invariant, and it is inconsistent with the rest of the codebase, where every comparable `onAccept` explicitly re-validates the module identity rather than relying on chain-wide trust. Any future pallet, permission misconfiguration (e.g., `HostExecutiveOrigin`/`AdminOrigin` set too broadly by governance), or an as-yet-unaudited pallet dispatching with attacker-influenced `from` would immediately become a full governance-takeover primitive with no additional check to stop it.

## Recommendation
Add a module-identity check to `HostManager.onAccept`, mirroring `ExtrinsicIntents._authenticate` / `HyperFungibleToken.onAccept`:
```solidity
if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();
if (keccak256(request.from) != keccak256(HOST_EXECUTIVE_MODULE_ID)) revert UnauthorizedAction();
```
where `HOST_EXECUTIVE_MODULE_ID` is the SCALE-encoded `ModuleId::Pallet(PalletId(*b"hostexec"))` bytes, matching what `pallet-ismp-host-executive` actually sets as `from`. This closes the gap regardless of what other pallets exist or are added to the Hyperbridge runtime in the future.

## Proof of Concept
Conceptual PoC (cannot be fully executed without a pallet that lets a caller set `from` freely, which is the open question noted above):
1. On the Hyperbridge chain, get any dispatch path (present or future pallet, or a governance/permission misconfiguration) to call `pallet_ismp::Pallet::dispatch_request` with:
   - `dest = StateMachine::Evm(<target_chain>)`
   - `from = <anything, e.g. b"attacker"> ` (not the host-executive `PALLET_ID`)
   - `to = <HostManager address on target_chain>`
   - `body = [OnAcceptActions.Withdraw as u8] ++ abi.encode(WithdrawParams{ token: feeToken, beneficiary: attacker, amount: full_balance })`
2. Once a relayer delivers this request and it passes standard ISMP proof verification (the state/consensus proof only proves the message came from the Hyperbridge chain, not from a specific pallet), `HostManager.onAccept` on `target_chain` checks only `request.source.equals(hyperbridge())`, which is true.
3. `HostManager` calls `IHostManager(_params.host).withdraw(withdrawParams)`, which is `restrict(_hostParams.hostManager)`-gated only against `msg.sender == HostManager` — satisfied here — transferring the requested `amount` of `token` to `beneficiary` at evm/src/core/EvmHost.sol:651-660.
