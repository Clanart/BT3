Based on the evidence gathered, I can identify a structurally analogous bug class in GitHub Desktop, though I was unable to fully trace every call site before running out of tool iterations — I flag that limitation explicitly in the Likelihood section.

### Title
Discard-changes line range can be computed against an expanded diff while the patch is formatted against the original diff, causing wrong lines to be reverted - (File: app/src/ui/diff/side-by-side-diff.tsx)

### Summary
GitHub Desktop's "Expand Whole File" / hunk-expansion feature creates a second, larger line-numbering space (the expanded diff) that sits on top of the original diff's line numbers. Discarding changes always applies the resulting patch against the **original** diff [1](#0-0) , but the line range that identifies *which* lines to discard is only guaranteed to be translated back into the original diff's numbering for the hunk-level discard path, via `findInteractiveOriginalDiffRange` [2](#0-1) . This mirrors the reported Ostium bug: one part of the calculation (the patch/collateral applied) uses the "full"/original reference frame while another part (the price impact / line range) can be computed in a different, unreduced frame — the two must be kept in lockstep or the wrong quantity gets acted on.

### Finding Description
`DiffHunk.unifiedDiffStart`/`unifiedDiffEnd` line indices are relative to whichever diff object is currently held in component state (`this.state.diff`), which can be either the original diff or an expanded one produced by `expandWholeTextDiff` after the user chooses "Expand Whole File" [3](#0-2) . `findInteractiveDiffRange` returns a range expressed in terms of whatever `hunks` array it was given [4](#0-3) , i.e. it can be an expanded-diff-relative range.

`onContextMenuHunk` explicitly converts that range back to original-diff line numbers before calling `onDiscardChanges`, using `findInteractiveOriginalDiffRange`, which calls `getLineInOriginalDiff` to map each index through `DiffLine.originalLineNumber` [5](#0-4) [6](#0-5) . `onDiscardChanges` itself carries a comment underscoring that this translation is required: "Pass the original diff (from props) instead of the (potentially) expanded one" [1](#0-0) .

The patch that is actually applied to the working directory is built by `formatPatchToDiscardChanges`, which walks `diff.hunks` (the diff passed in — always `this.props.diff`, i.e. the original, un-expanded diff) and uses `selection.isSelected(absoluteIndex)` where `absoluteIndex = hunk.unifiedDiffStart + lineIndex` computed against that original diff [7](#0-6) . This means the `DiffSelection` passed to `onDiscardChanges` must always encode line numbers in the *original* diff's index space, not the expanded one — the invariant only holds if every caller performs the same original-diff translation that `onContextMenuHunk` does.

The broken invariant, precisely: `startLine`/`endLine` fed to `onDiscardChanges` (line 1590) must be original-diff-relative, but `onDiscardChanges` performs no translation itself — it simply trusts its caller and builds `withRangeSelection(startLine, ...)` directly [8](#0-7) . Any call site that does not route through `findInteractiveOriginalDiffRange` before calling `onDiscardChanges` while the diff is in its expanded state would silently apply the discard patch to the wrong lines of the file, because the selection index and the `hunk.unifiedDiffStart` used by `formatPatchToDiscardChanges` would refer to different underlying line sequences (expanded vs. original).

### Impact Explanation
If such a mismatched call path exists (single-line/gutter discard rather than whole-hunk discard, or any future direct-click discard action added on an expanded view), the result is a `git apply` patch that reverts/removes the wrong lines from the user's working directory without any error or confirmation dialog beyond the normal "Discard changes" prompt [9](#0-8) . This is silent corruption of the user's working tree and, transitively, of what they subsequently stage and commit — since Desktop gives no diff preview of exactly which physical lines the discard patch will touch.

### Likelihood Explanation
I confirmed one call path (`onContextMenuHunk` → whole-hunk discard) that correctly performs the original-diff translation. I was not able to locate and verify, within the available tool budget, whether the single-line discard action (clicked on an individual gutter row rather than a hunk range) or any other `onDiscardChanges` caller also performs this translation, or whether it relies on the same `findInteractiveOriginalDiffRange` helper. This is the key open question that determines whether the vulnerability is live: it requires the user to have expanded a hunk/whole file (a normal, encouraged workflow for reviewing large diffs) and then use a discard action whose line numbers were computed against the expanded diff without translation.

### Recommendation
Audit every call site of `onDiscardChanges` in `app/src/ui/diff/side-by-side-diff.tsx` and require that line ranges always be passed through `findInteractiveOriginalDiffRange` (or an equivalent explicit translation) whenever `this.diffToRestore !== null` (i.e., the diff is currently expanded), rather than relying on each caller to remember to do so. Consider making `onDiscardChanges` itself diff-space-aware — accepting only original-diff-relative indices by construction (e.g., via a typed wrapper) so it is impossible to pass expanded-diff indices by mistake.

### Proof of Concept
Not independently reproduced end-to-end due to incomplete verification of all `onDiscardChanges` call sites; the concrete PoC would be: (1) open a file with a diff, (2) use "Expand Whole File" to enter the expanded-diff state, (3) trigger a discard action whose line index was derived from the expanded hunk numbering without going through `findInteractiveOriginalDiffRange`, (4) observe that `formatPatchToDiscardChanges`/`git apply` reverts different physical lines than the ones the user selected in the expanded view.

export function findInteractiveOriginalDiffRange(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): IDiffRange | null {
  const range = findInteractiveDiffRange(hunks, index)

  if (range === null) {
    return null
  }

  const from = getLineInOriginalDiff(hunks, range.from)
  const to = getLineInOriginalDiff(hunks, range.to)

  if (from === null || to === null) {
    return null
  }

  return {
    ...range,
    from,
    to,
  }
}

export function findInteractiveDiffRange(
  hunks: ReadonlyArray<DiffHunk>,
  index: number
): IDiffRange | null {
  const hunk = diffHunkForIndex(hunks, index)
  if (!hunk) {
    return null
  }

  const relativeIndex = index - hunk.unifiedDiffStart

  let rangeType: DiffRangeType | null = getNextRangeType(
    null,
    hunk.lines[relativeIndex]
  )
  let contextLineBeforeIndex: number | null = null

  for (let i = relativeIndex - 1; i >= 0; i--) {
    const line = hunk.lines[i]
    if (!line.isIncludeableLine()) {
      const startIndex = i + 1
      contextLineBeforeIndex = hunk.unifiedDiffStart + startIndex
      break
    }

    rangeType = getNextRangeType(rangeType, line)
  }

  const from =
    contextLineBeforeIndex !== null
      ? contextLineBeforeIndex
      : hunk.unifiedDiffStart + 1

  let contextLineAfterIndex: number | null = null

  for (let i = relativeIndex + 1; i < hunk.lines.length; i++) {
    const line = hunk.lines[i]
    if (!line.isIncludeableLine()) {
      const endIndex = i - 1
      contextLineAfterIndex = hunk.unifiedDiffStart + endIndex
      break
    }

    rangeType = getNextRangeType(rangeType, line)
  }

  const to =
    contextLineAfterIndex !== null ? contextLineAfterIndex : hunk.unifiedDiffEnd

  return { from, to, type: rangeType }
}

export function formatPatchToDiscardChanges(
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
): string | null {
  let patch = ''

  diff.hunks.forEach((hunk, hunkIndex) => {
    let hunkBuf = ''

    let oldCount = 0
    let newCount = 0

    let anyAdditionsOrDeletions = false

    hunk.lines.forEach((line, lineIndex) => {
      const absoluteIndex = hunk.unifiedDiffStart + lineIndex

      // We write our own hunk headers
      if (line.type === DiffLineType.Hunk) {
        return
      }

      // Context lines can always be let through, they will
      // never appear for new files.
      if (line.type === DiffLineType.Context) {
        hunkBuf += `${line.text}\n`
        oldCount++
        newCount++
      } else if (selection.isSelected(absoluteIndex)) {
        // Reverse the change (if it was an added line, treat it as removed and vice versa).
        if (line.type === DiffLineType.Add) {
          hunkBuf += `-${line.text.substring(1)}\n`
          newCount++
        } else if (line.type === DiffLineType.Delete) {
          hunkBuf += `+${line.text.substring(1)}\n`
          oldCount++
        } else {
          assertNever(line.type, `Unsupported line type ${line.type}`)
        }

        anyAdditionsOrDeletions = true

export async function discardChangesFromSelection(
  repository: Repository,
  filePath: string,
  diff: ITextDiff,
  selection: DiffSelection
) {
  const patch = formatPatchToDiscardChanges(filePath, diff, selection)

  if (patch === null) {
    // When the patch is null we don't need to apply it since it will be a noop.
    return
  }

  const args = ['apply', '--unidiff-zero', '--whitespace=nowarn', '-']

  await git(args, repository.path, 'discardChangesFromSelection', {
    stdin: patch,
  })
}
