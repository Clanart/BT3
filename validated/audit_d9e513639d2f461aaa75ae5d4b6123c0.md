### Title
Userinfo-authority bypass in `githubAssetVideoRegex` allows CDN allow-list to be spoofed - (`app/src/lib/markdown-filters/video-url-regex.ts`)

### Summary
`githubAssetVideoRegex` is a plain string-pattern regex (`^https://user-images\.githubusercontent\.com.+ext$`), not a proper URL/host parser. Because the greedy `.+` segment can contain an `@`, an attacker can craft a URL where the literal CDN string is placed in the userinfo (`user@host`) portion of the authority and the actual host is attacker-controlled, e.g. `https://user-images.githubusercontent.com@evil.example/x.mp4`. The regex still matches this string, but a WHATWG URL parser (and the DOM `.href`/`.src` accessors used by the calling code) resolve the real authority to `evil.example`.

### Finding Description
`githubAssetVideoRegex` is used as the sole authorization check in two node filters that are applied to attacker-controlled markdown (PR/issue/commit bodies, comments, etc.) rendered inside `SandboxedMarkdown`:

- `VideoTagFilter` decides whether to keep or strip a `<video>` element by testing `el.src` against the regex. [1](#0-0) 
- `VideoLinkFilter` decides whether to rewrite an auto-linked `<a>` into a `<video src="...">` element by testing `node.firstChild.href` against the regex. [2](#0-1) 

Both filters read `.src`/`.href` from live DOM elements, meaning the value being tested is already a browser-normalized, absolute URL string (per the WHATWG URL Standard's serialization), not raw untrusted text. Under that spec, `https://user-images.githubusercontent.com@evil.example/x.mp4` parses to userinfo `user-images.githubusercontent.com`, host `evil.example`, path `/x.mp4`, and re-serializes with the username preserved before `@`, so `el.src`/`a.href` returns the same string. Since `githubAssetVideoRegex` is defined purely as a literal-prefix + `.+` + extension pattern with no host/authority boundary anchoring (no check that the text right after the CDN literal is `/` and not `@`, `.`, or another authority separator), it matches this string: [3](#0-2) 

The comment describing the escaped literal even documents the intended behavior — a check against "a github user asset" host — which the regex fails to enforce correctly: [4](#0-3) 

This markdown pipeline is wired into `SandboxedMarkdown`, which is used to render repository/API-derived markdown (PR descriptions, commit messages, etc.) inside a sandboxed iframe after `DOMPurify.sanitize()` with no custom tag/attribute allow-list configuration (default DOMPurify config, which permits `<video>`/`src`): [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who controls markdown rendered by Desktop (a PR description/comment, commit message, or other GitHub API text field) can embed a link or `<video>` tag whose src passes the `githubAssetVideoRegex` check but actually resolves to an attacker-controlled host. Since this filter is the only gate deciding whether a `<video>` element's `src` is trusted, the bypass causes Desktop to render (and thus fetch, since the sandboxed iframe only restricts scripting via `sandbox="allow-same-origin"`, not networking) media content from an arbitrary attacker server whenever the victim views that markdown in the app. This can be used to fingerprint/track the user (leaking IP address, user agent, timing) or serve unexpected content, defeating the intent of restricting video embeds to the `user-images.githubusercontent.com` CDN.

### Likelihood Explanation
Exploitation only requires the attacker to author markdown text (PR body, issue/commit comment, etc.) containing a specially-crafted URL — no special privileges, no user interaction beyond viewing the content in Desktop, and no bypass of any other existing check, since this regex is the only validation performed by `VideoTagFilter`/`VideoLinkFilter`. This fits squarely in the "attacker controls a GitHub API object / repository content" threat model in scope.

### Recommendation
Replace the string-pattern check with proper URL parsing: construct a `URL` object from the candidate src/href and verify `url.protocol === 'https:'`, `url.hostname === 'user-images.githubusercontent.com'` (or the appropriate allow-listed hostname), `url.username === ''`, and `url.password === ''`, in addition to checking the pathname extension. This eliminates userinfo/authority-confusion bypasses entirely, since the check would be against the parsed `hostname` rather than a literal substring match.

### Proof of Concept
```js
const { githubAssetVideoRegex } = require('./app/src/lib/markdown-filters/video-url-regex')

const malicious = 'https://user-images.githubusercontent.com@evil.example/x.mp4'
console.log(githubAssetVideoRegex.test(malicious)) // true — bypasses intended host check

const a = document.createElement('a')
a.href = malicious
console.log(a.href)       // "https://user-images.githubusercontent.com@evil.example/x.mp4"
console.log(new URL(malicious).hostname) // "evil.example"  <-- real destination host
```
This demonstrates the regex accepts the crafted string while the actual authority/host resolved by the URL/DOM parser is `evil.example`, confirming the domain-confusion bypass described in the question.

Note: I was not able to fully verify from the indexed code whether an additional Content-Security-Policy restricts network fetches inside the `SandboxedMarkdown` iframe (no CSP `meta`/header configuration was found via search) or whether DOMPurify's default configuration is overridden elsewhere to disallow `<video>`; the analysis above assumes DOMPurify defaults (which do permit `<video>`/`src`) since no custom `ALLOWED_TAGS`/`ADD_TAGS` configuration was found in the codebase. If a CSP fully blocks all `media-src`/`connect-src` outside the CDN, the practical network-fetch impact would be mitigated, though the allow-list logic itself (`githubAssetVideoRegex`) is still incorrect regardless.
