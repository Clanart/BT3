### Title
Multi-signature Schnorr aggregates verify with different weights than aggregation - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregator::complete` derives each aggregation weight from a transcript that is updated after every appended challenge, while `SchnorrAggregate::verify` first appends every challenge and only then derives every weight. For aggregates containing more than one signature, the verifier therefore uses coefficients different from those used to calculate `s`, causing honestly generated aggregates to fail verification.

### Finding Description
The aggregator interleaves challenge appends and weight derivation. `aggregate` appends one challenge to `self.digest`, and `complete` calls `weight` once per signature. Each `weight` call invokes `DigestTranscript::challenge`, which mutates the transcript before the next challenge is appended. [1](#0-0) [2](#0-1) 

The verifier instead appends all `keys_and_challenges` to a fresh digest before calculating any weights. It then derives `z_i` and checks `sum(z_i R_i + z_i c_i A_i) - sG == 0`. [3](#0-2) 

For signatures `s_i = r_i + c_i a_i`, aggregation returns `s = Σ a_i s_i`, where `a_i` are the aggregator's interleaved weights. Verification uses independently computed `z_i`, so it effectively checks `Σ z_i S_i - Σ a_i S_i = Σ(z_i - a_i)S_i = 0`, where `S_i = R_i + c_i A_i`. This equality is not implied by signature validity and is false except for accidental scalar relations.

### Impact Explanation
Any consumer that accepts an aggregate produced by `SchnorrAggregator` and verifies it with `SchnorrAggregate::verify` will reject valid multi-signature aggregates. This is a reachable public-input failure through `SchnorrAggregate::read`, followed by `verify` with attacker-supplied or externally supplied public keys and challenges. It breaks the intended aggregation/verification contract and can make otherwise valid signed data unusable.

### Likelihood Explanation
The mismatch occurs deterministically whenever at least two signatures are aggregated through the provided API. Single-signature aggregates happen to use the same transcript state, masking the issue in the trivial case. No malicious participant, network state, malformed encoding, or integrator-provided cryptographic primitive is required.

### Recommendation
Make aggregation and verification derive weights from identical transcript operation sequences. Either append all challenges before deriving all weights in both paths, or interleave challenge appends and weight derivation in both paths. Add a regression test that aggregates and verifies at least two distinct valid Schnorr signatures.

### Proof of Concept
```rust
use rand_core::OsRng;
use zeroize::Zeroizing;

use ciphersuite::{Ciphersuite, group::ff::Field};
use schnorr::{SchnorrSignature, SchnorrAggregator};

// C is any in-scope Ciphersuite, such as Secp256k1 or Ristretto.
fn aggregate_two_signatures_fails<C: Ciphersuite>() {
  let k1 = Zeroizing::new(C::random_nonzero_F(&mut OsRng));
  let k2 = Zeroizing::new(C::random_nonzero_F(&mut OsRng));
  let a1 = C::generator() * *k1;
  let a2 = C::generator() * *k2;

  let c1 = C::random_nonzero_F(&mut OsRng);
  let c2 = C::random_nonzero_F(&mut OsRng);

  let sig1 = SchnorrSignature::<C>::sign(
    &k1,
    Zeroizing::new(C::random_nonzero_F(&mut OsRng)),
    c1,
  );
  let sig2 = SchnorrSignature::<C>::sign(
    &k2,
    Zeroizing::new(C::random_nonzero_F(&mut OsRng)),
    c2,
  );

  let mut aggregator = SchnorrAggregator::<C>::new(b"test-domain");
  aggregator.aggregate(c1, sig1);
  aggregator.aggregate(c2, sig2);
  let aggregate = aggregator.complete().unwrap();

  // Deterministically false except for an accidental relation between the two
  // different weight sequences.
  assert!(aggregate.verify(b"test-domain", &[(a1, c1), (a2, c2)]));
}
```

The final assertion fails because the first and second weights are generated from different transcript states in `complete` and `verify`.
