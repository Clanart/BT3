### Title
Missing owner/approval check in `CW721ERC721Pointer.approve()` allows unauthorized NFT approvals - (File: `contracts/src/CW721ERC721Pointer.sol`)

### Summary
`CW721ERC721Pointer.approve()` forwards an `approve` message to the wrapped CW721 contract without first verifying that `msg.sender` is the token owner or an already-approved operator, unlike `transferFrom()`, which explicitly requires `from == ownerOf(tokenId)` before executing [3](#0-2) .

### Finding Description
The standard ERC721 `approve()` semantics (and the underlying OpenZeppelin implementation, e.g. the plain `ERC721.sol` reference in this repo) require the caller to be the token owner or an approved-for-all operator before setting a new spender approval [4](#0-3) . `CW721ERC721Pointer.approve()` skips this authorization check entirely and just builds a CosmWasm `approve` payload and calls `_execute` [5](#0-4) .

`_execute` issues the request via `delegatecall` into the wasmd precompile's `execute(string,bytes,bytes)` [6](#0-5) . Inside the precompile, the delegatecall path is only checked to confirm the *contract address being called* (`contractAddrStr`) is a registered pointer of the `callingContract` [7](#0-6)  — it does not verify that the original EVM `caller` is authorized over the specific token being approved. The `Sender` on the resulting `MsgExecuteContract` is derived directly from `caller` (the original EOA/tx sender), not the pointer contract [8](#0-7) .

As a result, any EVM account can call `approve(spender, tokenId)` on the pointer for **any** `tokenId`, even one it does not own, and the CW721 contract will process an `approve` message from that account's associated Sei address. Whether this succeeds depends on the underlying CW721 contract's own authorization logic for `approve` (which, per CW721 spec, requires `info.sender == owner`), so the CW721 contract itself is expected to reject non-owner approvals. This weakens the analog to the CVE (which is about improper authorization allowing exposure/side effects via an alternate access path) but the pointer contract's own approve method lacks defense-in-depth that its sibling `transferFrom()` has.

### Impact Explanation
If the underlying CW721 contract does not itself enforce owner-only `approve` semantics defensively (e.g. a custom or misconfigured CW721 implementation), an attacker could set themselves as approved spender for tokens they don't own via the pointer, then transfer/steal the NFT. Even with a compliant CW721 contract rejecting this at the CosmWasm layer, this is inconsistent with the other write paths in the same contract (`transferFrom` has an explicit ownership check; `approve` does not), and it means the pointer contract does not defend against unauthorized approval attempts at the EVM layer, delegating all correctness to the wrapped CW721 contract's own validation.

### Likelihood Explanation
Any unprivileged EVM account can call `approve()` on any deployed `CW721ERC721Pointer` for any `tokenId` without holding or being approved for that token; the call is a direct, single-transaction path reachable by any contract deployer or EOA interacting with the pointer.

### Recommendation
Add an explicit authorization check in `CW721ERC721Pointer.approve()` mirroring `transferFrom()`'s pattern — i.e., `require(msg.sender == ownerOf(tokenId) || isApprovedForAll(ownerOf(tokenId), msg.sender), "not authorized")` — before issuing the CW721 `approve` execute message, so the pointer contract enforces the ERC721 authorization invariant independently of the wrapped CW721 contract's own validation.

### Proof of Concept
1. Deploy/obtain a `CW721ERC721Pointer` for an existing CW721 collection where account A owns `tokenId=1`.
2. As account B (not owner, not approved), call `pointer.approve(B_or_C_address, 1)`.
3. Observe that the pointer contract issues the CosmWasm `approve` message with `Sender` = B's associated Sei address without the pointer contract validating B's authorization over token `1`; the request only fails if the wrapped CW721 contract itself rejects the non-owner sender (as CW721 spec-compliant contracts do), meaning correctness is fully delegated to the CW721 contract instead of being enforced in the pointer contract's `approve()` as it is in `transferFrom()`.
