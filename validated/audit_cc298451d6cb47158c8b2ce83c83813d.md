### Title
Uncontrolled recursive decoding of nested `AccountKeyRoleBased` in RLP allows DoS via resource-exhausting transactions - (File: `blockchain/types/accountkey/account_key_role_based.go`)

### Summary
`AccountKeyRoleBased.DecodeRLP` recursively decodes each of its sub-keys as an independent `AccountKeySerializer`, and if a sub-key is itself of type `AccountKeyTypeRoleBased`, decoding recurses again with no depth limit. The only defense against nesting (`IsCompositeType()` check yielding `kerrors.ErrNestedCompositeType`) is applied in `CheckInstallable`/`CheckUpdatable`, which runs only *after* the entire (potentially deeply nested) structure has already been fully decoded. This mirrors the Jenkins Token Macro bug class (CWE-674, uncontrolled recursive expansion of attacker-controlled input) — the recursive processing happens before any guard can stop it.

### Finding Description
`AccountKeySerializer.DecodeRLP` decodes a key type and then dispatches to the concrete key's own `DecodeRLP`: [1](#0-0) 

For `AccountKeyRoleBased`, decoding treats each element as raw bytes and independently re-invokes `rlp.DecodeBytes` on a fresh `AccountKeySerializer` for every element: [2](#0-1) 

Because each nested element is decoded via a brand-new `rlp.DecodeBytes` call (not through the parent `rlp.Stream`'s natural list-nesting), any stream-level depth/size protection that would normally bound nested-list recursion is bypassed — a nested `AccountKeyRoleBased` inside a `AccountKeyRoleBased` inside another `AccountKeyRoleBased`, etc., causes this decode routine to call itself recursively with no depth check whatsoever.

The only place nested composite types are rejected is `CheckInstallable`/`CheckUpdatable`, which iterates one level of the already-decoded slice and checks `IsCompositeType()`: [3](#0-2) [4](#0-3) 

This check happens strictly after full RLP decoding of the entire nested structure has completed, exactly like Jenkins Token Macro's original flaw where recursive expansion occurred before any recursion-limiting logic was applied. `AccountKeyRoleBased.IsCompositeType()` unconditionally returns `true`: [5](#0-4) 

so nothing prevents an attacker from constructing an `AccountKey` payload for a `TxTypeAccountUpdate` (or `TxTypeFeeDelegatedAccountUpdate*`) transaction where the key field encodes a chain of nested `AccountKeyRoleBased` values many levels deep. `types.NewTransactionWithMap`/decoding of the raw transaction bytes (as happens when any node or public RPC endpoint accepts a raw transaction via `eth_sendRawTransaction`, p2p tx propagation, or block body decoding) will trigger `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP`, recursing through every nesting level before the `TxPool.AddRemote`/`applyTransaction` code path ever gets a chance to call `CheckInstallable`/`CheckUpdatable` and reject it with `kerrors.ErrNestedCompositeType` (as demonstrated by the existing single-level nesting test): [6](#0-5) 

That test only exercises one level of nesting and confirms it is eventually rejected — it does not test deep nesting, and the rejection happens only after the recursive decode has already fully executed.

### Impact Explanation
An attacker (any unprivileged transaction sender, no special privileges required) can craft a single `AccountUpdate`-type transaction whose `AccountKey` field encodes a long chain of nested `AccountKeyRoleBased` structures. Because each nesting level only costs a few bytes of RLP overhead, a transaction well within normal size limits can encode thousands of nesting levels. Submitting this transaction to a public RPC endpoint or the network causes every node that decodes it (mempool ingestion, gossip propagation, block validation) to recurse through `AccountKeyRoleBased.DecodeRLP` to that depth, resulting in excessive CPU consumption and/or Go-routine stack growth. This is a resource-exhaustion / denial-of-service risk reachable by any transaction sender before the transaction is ever accepted or included, since the eventual rejection (`ErrNestedCompositeType`) happens only after the costly recursive decode has completed. Repeated submission of such transactions can be used to degrade node performance across the network, consistent with a Medium-severity availability impact analogous to the Jenkins Token Macro DoS.

### Likelihood Explanation
Likelihood is high: the attacker only needs to construct and submit one transaction; no special account state, keys, or governance/administrative privileges are required. Any public RPC caller or peer receiving/propagating the transaction is exposed to the decode cost, matching the "unprivileged transaction sender" reachable-path requirement.

### Recommendation
Enforce a maximum recursion/nesting depth check inside `AccountKeyRoleBased.DecodeRLP` (and the corresponding `UnmarshalJSON` path) before or during decoding of nested elements, rejecting any key whose sub-key type is `AccountKeyTypeRoleBased` (or otherwise composite) immediately at decode time rather than deferring the check to `CheckInstallable`/`CheckUpdatable`. Alternatively, track and bound decode depth via a context/counter threaded through `NewAccountKey`/`DecodeRLP` so that recursive decoding aborts as soon as nesting is detected, mirroring how the Token Macro plugin fix stopped applying recursive expansion to token output.

### Proof of Concept
1. Construct an `AccountKeyRoleBased` value `K0` wrapping a legacy/public key.
2. Wrap `K0` in another `AccountKeyRoleBased` to get `K1 = RoleBased{K0}`, then `K2 = RoleBased{K1}`, and repeat this nesting N times (N in the thousands, still fitting comfortably under the transaction size limit due to compact RLP encoding).
3. Build a `TxTypeAccountUpdate` transaction with `TxValueKeyAccountKey: KN`, sign it, and RLP-encode the transaction.
4. Submit the raw transaction via `eth_sendRawTransaction` to a Kaia node's public RPC or broadcast via p2p.
5. Observe that `AccountKeySerializer.DecodeRLP` → `AccountKeyRoleBased.DecodeRLP` recurses N times per node that decodes the transaction, before `TxPool.AddRemote`/`applyTransaction` finally rejects it with `kerrors.ErrNestedCompositeType`, consuming disproportionate CPU/stack resources for a single unprivileged submission — repeatable at scale for sustained DoS.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}

func (a *AccountKeyRoleBased) CheckUpdatable(newKey AccountKey, currentBlockNumber uint64) error {
	if newKey, ok := newKey.(*AccountKeyRoleBased); ok {
		lenOldKey := len(*a)
		lenNewKey := len(*newKey)
		// If no key is to be replaced, it is regarded as a fail.
		if lenNewKey == 0 {
			return kerrors.ErrZeroLength
		}
		// Do not allow undefined roles.
		if lenNewKey > (int)(RoleLast) {
			return kerrors.ErrLengthTooLong
		}
		for i := range lenNewKey {
			switch {
			// A composite key is not allowed.
			case (*newKey)[i].IsCompositeType():
				return kerrors.ErrNestedCompositeType
			// If newKey is longer than oldKey, init the new attributes.
			case i >= lenOldKey:
				if err := (*newKey)[i].CheckInstallable(currentBlockNumber); err != nil {
					return err
				}
			// Do nothing for AccountKeyTypeNil
			case (*newKey)[i].Type() == AccountKeyTypeNil:

			// Check whether the newKey is replacable or not
			default:
				if err := CheckReplacable((*a)[i], (*newKey)[i], currentBlockNumber); err != nil {
					return err
				}
			}
		}
		return nil
	}
	// Update is not possible if the type is different.
	return kerrors.ErrDifferentAccountKeyType
}
