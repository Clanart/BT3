### Title
Direct-transfer donation to `MasterMagpie` permanently dilutes/freezes reward accrual in `BaseRewardPool` - (File: `rewards/BaseRewardPool.sol`, `rewards/MasterMagpie.sol`)

### Summary
`BaseRewardPool._provisionReward()` computes `rewardPerTokenStored` by dividing the incoming reward amount by `this.totalStaked()`, and `totalStaked()` is defined as the raw ERC20 balance of the staking token held by the `MasterMagpie` (`operator`) contract rather than an internally tracked sum of user deposits. Any unprivileged wallet can transfer the pool's staking/receipt token directly to `MasterMagpie` to inflate this denominator without increasing any user's tracked share (`balanceOf`, which reads from `MasterMagpie.stakingInfo`), permanently diluting the reward-per-token math for every future reward distribution.

### Finding Description
`BaseRewardPool.totalStaked()` returns the operator's raw token balance: [1](#0-0) 

while `balanceOf(_account)` is derived from `MasterMagpie`'s internal `stakingInfo` accounting, not from the raw token balance: [2](#0-1) 

`_provisionReward()` (called by `queueNewRewards`/`donateRewards`) uses `this.totalStaked()` as the divisor when updating `rewardPerTokenStored`: [3](#0-2) 

Because `totalStaked()` reflects the *actual balance* of the staking token sitting in the `MasterMagpie` contract (the same address used as `operator`), any wallet can call `IERC20(stakingToken).transfer(masterMagpie, X)` directly (bypassing `deposit`/`depositFor`) to inflate `totalStaked()` without ever incrementing any user's `stakingInfo` amount. This mirrors the root cause in the external report: a denominator derived from a token balance that can be inflated by a bare transfer, decoupled from the internal share/credit accounting that determines user entitlements. `BaseRewardPoolV2.totalStaked()`/`balanceOf()` have the identical pattern: [4](#0-3) 

### Impact Explanation
Once `totalStaked()` is inflated by a direct donation, every subsequent `_provisionReward()` call divides the reward amount by an artificially large denominator, permanently reducing `rewardPerTokenStored` growth relative to what legitimate stakers should receive. Unlike the original Yieldy bug (which reverts and causes DOS), here the effect is silent and irreversible: the diluted `rewardPerTokenStored` is written into storage and stakers who claim afterward receive fewer rewards than they earned for as long as the donated tokens remain in `MasterMagpie` — there is no mechanism found to sweep/exclude non-accounted balances from `totalStaked()`. This constitutes a permanent freezing/loss of unclaimed yield for all stakers of the affected pool, reachable by any ordinary wallet holding the staking token, without needing any privileged role.

### Likelihood Explanation
Any user who holds (or can acquire, e.g. via the pool helper deposit flow) the staking/receipt token for a given `BaseRewardPool` can perform this at any time with a plain ERC20 transfer to the `MasterMagpie` contract address — no special timing, governance, or privileged access required. The cost is simply the value of the tokens donated (which are not recoverable by the attacker), similar to the "low cost, no direct attacker profit but high griefing damage" pattern acknowledged as valid (Medium severity) in the original report.

### Recommendation
Decouple `totalStaked()` from the raw token balance of the operator. Track a dedicated internal counter (e.g., sum of all `stakingInfo[stakingToken][*].amount`, or a `totalSupply`-style state variable incremented/decremented exclusively in `_deposit`/`_withdraw`) and use that internal counter as the denominator in `_provisionReward()` instead of `IERC20(stakingToken).balanceOf(operator)`.

### Proof of Concept
1. Pool `P` in `MasterMagpie` has legitimate stakers with total tracked `stakingInfo` amount `S`, and `BaseRewardPool.totalStaked()` currently equals `S` (equal to `MasterMagpie`'s actual token balance).
2. Attacker calls `IERC20(stakingToken).transfer(masterMagpie, D)` directly, sending `D` staking tokens straight to the `MasterMagpie` contract without calling `deposit`/`depositFor`. No `stakingInfo` entry is created or modified for the attacker.
3. `BaseRewardPool.totalStaked()` (`rewards/BaseRewardPool.sol:126-128`) now returns `S + D`, while legitimate stakers' aggregate share is still `S`.
4. Anyone (or the reward manager) calls `queueNewRewards`/`donateRewards`, invoking `_provisionReward()` (`rewards/BaseRewardPool.sol:297-318`); `rewardPerTokenStored` is incremented by `(_amountReward * 10**decimals) / (S + D)` instead of `(_amountReward * 10**decimals) / S`.
5. Every legitimate staker's `earned()` calculation, which depends on `rewardPerToken()`, is permanently understated relative to their actual share `S`, and the difference (approximately `D/(S+D)` of every future reward) is never credited to any staker, effectively freezing/losing that portion of yield indefinitely.

```text
    function _provisionReward(uint256 _amountReward, address _rewardToken) internal {
        IERC20(_rewardToken).safeTransferFrom(
            msg.sender,
            address(this),
            _amountReward
        );
        Reward storage rewardInfo = rewards[_rewardToken];
        rewardInfo.historicalRewards =
            rewardInfo.historicalRewards +
            _amountReward;
        if (this.totalStaked() == 0) {
            rewardInfo.queuedRewards += _amountReward;
        } else {
            if (rewardInfo.queuedRewards > 0) {
                _amountReward += rewardInfo.queuedRewards;
                rewardInfo.queuedRewards = 0;
            }
            rewardInfo.rewardPerTokenStored =
                rewardInfo.rewardPerTokenStored +
                (_amountReward * 10**stakingDecimals()) /
                this.totalStaked();
        }
```
