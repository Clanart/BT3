### Title
`Scanner::scan_transaction` reports economically unspendable dust outputs as received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The external report describes a protocol which assumes an external economic constant (stablecoin 1:1 parity) when sizing an operation, so that when real conditions deviate, the operation cannot complete and user funds are locked. The analog in Serai's in-scope code is the Bitcoin `Scanner`/`ReceivedOutput` flow: `scan_transaction` reports every output paying to a registered `script_pubkey` as a spendable `ReceivedOutput` with no minimum-value check, so an attacker can permanently credit the vault with outputs whose value is below the fee required to spend them — funds the bridge reports as received but which can never be profitably (or, at elevated fee rates, at all) spent.

### Finding Description
`Scanner::scan_transaction` matches purely on `output.script_pubkey` and pushes a `ReceivedOutput` for every matching output, regardless of `output.value` [1](#0-0) .

`ReceivedOutput` exposes `value()` directly from the `TxOut` [2](#0-1) , and `SignableTransaction::new` treats the full `input_sat = sum(inputs)` as available value when checking `input_sat < payment_sat + needed_fee` [3](#0-2) [4](#0-3) .

The only minimum-value logic in the wallet is `DUST = 546`, and it is applied exclusively to *outgoing* payments and to the change output the wallet itself creates [5](#0-4) [6](#0-5) [7](#0-6) . No corresponding floor is enforced on *incoming* outputs by `Scanner`.

The fee model itself documents that each input costs ~57 vbytes to spend (230 weight units for a Taproot input plus witness signature) [8](#0-7) . Any received output whose value is below `57 vbytes * prevailing feerate` costs more to spend than it contributes.

### Impact Explanation
An unprivileged party can send a Bitcoin transaction containing one or many outputs paying to a Serai vault/deposit script (`p2tr_script_buf(key)` or any registered offset script) with an arbitrarily small value (e.g. 546 sats, the minimum relayable, or a value just under the spend cost). `Scanner::scan_transaction`/`scan_block` will emit a `ReceivedOutput` for each, so downstream accounting credits these as received funds.

These outputs are effectively unspendable:

- At any feerate above `value / 57` sat/vbyte, including them as inputs produces a net negative contribution — the "funds" cannot cover their own spend cost. Like the Derby report's failed swap, the operation built around the assumed usable balance cannot deliver its expected value: `input_sat` overstates spendable balance, so a `NotEnoughFunds` failure (or a silently negative-value input) locks the planned spend until the plan is rebuilt excluding the poisoned outputs.
- During fee-rate spikes (the analog of the report's "turbulent market"), a large band of previously borderline outputs becomes permanently unprofitable to spend, yet remains credited as received value.

This fits the accepted impact class "funds reported received that are not spendable" and requires only a public Bitcoin transaction from an unprivileged sender — no validator, node, or key-holder collusion.

### Likelihood Explanation
Sending dust to a known vault/deposit address is trivially cheap (546 sats per output per the wallet's own `DUST` constant, reusable across hundreds of outputs in one transaction since `scan_transaction` iterates all outputs). Serai addresses are public/static per registered offset, so the attack requires no interaction with Serai participants. Whether it freezes a specific spend depends on how the integrator selects inputs, but the scanner-level misreporting of value is unconditional and deterministic.

### Recommendation
Enforce a minimum received value in `Scanner::scan_transaction` (or when accepting `ReceivedOutput`s into `SignableTransaction::new`), sized against the documented ~57 vbyte input cost at a conservative maximum feerate — e.g. reject/flag outputs below a threshold such as the `DUST`-for-inputs bound used in `processor/src/networks/bitcoin.rs` (`const DUST: u64 = 10_000`, chosen so an output is spendable under a 5000 sat/kvB rate) [9](#0-8) . At minimum, `SignableTransaction::new` should not count sub-spend-cost inputs toward `input_sat`.

### Proof of Concept
1. Obtain a vault's scan script: `script = p2tr_script_buf(group_key)` (or any offset script registered via `register_offset`).
2. Broadcast a transaction with an output `{ script_pubkey: script, value: 600 }` (above the 546 relay dust limit, below any realistic 57+ vbyte spend cost at moderate feerates).
3. `scanner.scan_block(&block)` returns `ReceivedOutput { offset, output, outpoint }` with `value() == 600`, indistinguishable from a genuine deposit [1](#0-0) .
4. Passing this `ReceivedOutput` to `SignableTransaction::new` adds 600 sats to `input_sat` while adding ~57 vbytes of cost; at e.g. 20 sat/vbyte the input contributes 600 − 1140 = −540 sats, and `input_sat < payment_sat + needed_fee` fails — the spend cannot be constructed with the credited balance, mirroring the locked-vault failure of the original report.

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
