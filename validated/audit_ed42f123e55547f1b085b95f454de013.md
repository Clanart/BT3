### Title
Unbounded array index access in `claimAllBribes` reverts and permanently blocks bribe reward claims for all users - ([File: wombat/WombatBribeManager.sol])

### Summary
`WombatBribeManager.claimAllBribes` (and by extension `claimBribe`) loops through every active pool and directly indexes into `IWombatBribe(bribesContract).rewardTokens()[0]` without checking whether the returned array is empty, mirroring the reported nord bug class where an `Option` (`posted_order`) was assumed to always be populated (`unwrap()`'d) when in reality a legitimate code path could leave it empty, causing a crash.

### Finding Description
In `claimAllBribes`, for every pool with a non-zero `bribesContract`, the code does: [1](#0-0) 
```
address bribesContract = address(voter.infos(lp).bribe);
if (bribesContract != address(0)) {
    rewardTokens[i] = address(IWombatBribe(bribesContract).rewardTokens()[0]);
```
This assumes `rewardTokens()` always returns a non-empty array, exactly analogous to the nord `Receipt::Trade` code assuming `posted_order` is always `Some`. There is no `require`/length check before the `[0]` access. A Wombat `Bribe` contract can legitimately have zero registered reward tokens (e.g. right after being created by `addPool`/`voter` and before any external incentive/reward token is added to it, or if all its reward tokens are later removed on the Wombat side) — this is not an attacker-controlled or malicious-admin condition, just a normal, reachable state for that dependency, the same way the `fill_results.add == None` state in nord is reachable without any execution failure.

When any single pool in the `pools` array has such a bribe contract, `IWombatBribe(bribesContract).rewardTokens()[0]` performs an out-of-bounds array read on an empty array, which reverts the entire transaction in Solidity (the semantic analog of Rust's `Option::unwrap()` panicking on `None`).

### Impact Explanation
Because `claimAllBribes` iterates over `pools` (all active voting pools) in a single loop and the revert occurs mid-loop, any single "poisoned" pool with a bribe contract that currently has zero reward tokens registered will cause `claimAllBribes` (and `claimBribeFor`/`castVotesAndClaimBribes`, which call it) to revert for every unprivileged wallet, for every pool, not just the affected one. Since `unvote`, `vote`, and other user-facing entry points to reclaim/redirect voting power do not depend on this function, the direct, permanent consequence is loss of the ability to claim already-earned but unclaimed bribe rewards for all voters until an admin removes the offending pool via `removePool`. This is a freezing of unclaimed yield for an extended period (well over 24 hours, since it persists until manual intervention), triggerable without any privileged action, purely as a byproduct of adding a pool whose Wombat bribe has not yet had any reward token configured.

### Likelihood Explanation
This does not require a malicious admin: `addPool` is a normal admin operation to onboard a new Wombat pool for voting, and it is common/expected for a freshly-created Wombat `Bribe` to have no reward tokens registered yet (reward tokens are typically added later by whoever funds the bribe). Any unprivileged user calling `claimBribe`/`claimAllBribes`/`castVotesAndClaimBribes` while such a pool is registered will trigger the revert, blocking bribe claims for the entire pool set.

### Recommendation
Check the length of `IWombatBribe(bribesContract).rewardTokens()` before indexing, and skip pools whose bribe has no reward tokens registered (mirroring the nord fix recommendation to explicitly handle the "empty" case instead of unconditionally accessing index 0):
```solidity
IERC20[] memory tokens = IWombatBribe(bribesContract).rewardTokens();
if (tokens.length > 0) {
    rewardTokens[i] = address(tokens[0]);
    ...
}
```

### Proof of Concept
1. Admin calls `addPool(lp, rewarder, name)` for a Wombat LP whose associated `voter.infos(lp).bribe` is a valid, non-zero `Bribe` contract that has not yet had any reward token added (`IWombatBribe(bribe).rewardTokens()` returns `[]`), a normal/expected initial state. [2](#0-1) 
2. Any unprivileged user who has voted for at least one pool (or none) calls `claimAllBribes(msg.sender)` (or `claimBribe`, or `castVotesAndClaimBribes`).
3. Execution reaches `IWombatBribe(bribesContract).rewardTokens()[0]` for the poisoned pool and reverts due to out-of-bounds array access on the empty array, exactly as `Option::unwrap()` panics on `None` in the nord report.
4. All users are now unable to claim any bribe rewards from any pool through this function until an admin calls `removePool` for the poisoned entry.
