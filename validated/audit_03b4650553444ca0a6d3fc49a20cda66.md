### Title
Unchecked length-prefix parsing in `is_atom_canonical`/`is_clvm_canonical` can raise an unhandled `IndexError` on a crafted spend bundle - ([File: chia/full_node/mempool_manager.py])

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse the CLVM atom length-prefix bytes of a `SpendBundle`'s puzzle/solution buffer by indexing directly into the buffer with an offset that is derived from attacker-controlled length-prefix bits, without ever validating that the offset stays within the buffer bounds. This mirrors the rclone bug class: an untrusted, attacker-supplied length/offset value is used to index into a byte buffer without a bounds check, and the language's normal “safe” indexing behavior (Go slice panic / Python `IndexError`) is allowed to propagate instead of being converted into a handled validation error.

### Finding Description
`is_atom_canonical(clvm_buffer, offset)` reads a byte at `offset`, derives a `prefix_len` (0–5) from its high bits, and then loops `prefix_len` times doing: [1](#0-0) 
incrementing `offset` and indexing `clvm_buffer[offset]` on every iteration with no check that `offset < len(clvm_buffer)`.

`is_clvm_canonical(clvm_buffer)` drives this loop: [2](#0-1) 
At the top of every iteration it does `b = clvm_buffer[offset]` before any bounds check, and also calls `is_atom_canonical`, which itself has the same unchecked indexing. If the buffer ends with a truncated multi-byte atom length prefix (e.g. the very last byte is `0xFC`–`0xFF`, signaling a 5-byte length field, but fewer than 5 bytes remain), the function indexes past the end of `clvm_buffer` and Python raises an unhandled `IndexError` (`bytes index out of range`), analogous to the Go slice-bounds panic in the rclone report — an attacker-controlled length value drives an unchecked read past a buffer boundary.

This is directly analogous to the rclone bug class: in both cases a length/offset value taken from untrusted, attacker-supplied data is used to index/slice a buffer without validating it against the buffer's actual size, and the runtime's default "safe" behavior (panic in Go, `IndexError` in Python) is what stops the out-of-bounds access — meaning the crash is deterministic and attacker-triggerable, not memory-unsafe, but still an uncaught exception in transaction-processing code.

### Impact Explanation
Because this function lives in `chia/full_node/mempool_manager.py`, its role is to validate whether the CLVM serialization of a spend bundle's puzzle reveal/solution is in canonical form. This is data the full node parses directly out of a submitted, attacker-controlled `SpendBundle` before/while admitting it to the mempool. A malformed buffer with a truncated trailing multi-byte atom-length prefix causes an unhandled `IndexError` during this canonical-form check, which can abort spend-bundle processing for that transaction (and, depending on where in the call chain the exception propagates, potentially disrupt the caller's per-request processing loop), matching the "spend-triggered transaction-processing halt" impact category.

### Likelihood Explanation
I was not able to fully trace, within the available tool budget, the exact call sites that invoke `is_clvm_canonical`/`is_atom_canonical` on submitted spend bundle data (e.g., whether it's called from `pre_validate_spendbundle`, `add_spend_bundle`, or another admission path in `MempoolManager`), nor whether an outer `try/except` already wraps that call and safely converts the exception into a rejection. This uncertainty limits how confidently I can assert full remote unauthenticated reachability. The construct itself (buffer indexing with an offset derived from an attacker-controlled length prefix, no bounds check) is a clear defect and a strong structural analog to the rclone CVE, but confirming end-to-end reachability and blast radius (single-connection failure vs. broader denial of service) requires reading the surrounding `MempoolManager` code paths that call these functions.

### Recommendation
Add explicit bounds checks in `is_atom_canonical` and `is_clvm_canonical` before every buffer index/slice: verify `offset < len(clvm_buffer)` before reading `clvm_buffer[offset]`, and verify enough bytes remain (`offset + prefix_len < len(clvm_buffer)`) before entering the prefix-reading loop, returning a clean "not canonical"/parse-error result (or raising a well-defined, caught exception) instead of allowing a raw `IndexError` to propagate. Additionally, confirm (via code review/tests) that all callers of these functions wrap them in a try/except that safely rejects the malformed spend bundle rather than crashing a processing task.

### Proof of Concept
Construct a `clvm_buffer` whose last byte is a length-prefix marker requiring trailing continuation bytes that are not present, e.g.:
```python
from chia.full_node.mempool_manager import is_clvm_canonical

# 0xFC signals a 5-byte big atom length prefix (2 + 8*4 bits), but no
# continuation bytes follow.
buf = b"\xfc"
is_clvm_canonical(buf)  # raises IndexError: index out of range
```
More generally, any buffer ending in a byte matching `0b11111100`–`0b11111111` (the multi-byte length-prefix patterns) without the required number of trailing length bytes triggers the same unhandled `IndexError` inside `is_atom_canonical`/`is_clvm_canonical`.
