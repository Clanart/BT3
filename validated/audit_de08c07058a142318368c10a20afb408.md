### Title
`ThresholdKeys::read` pre-allocates attacker-controlled `n`-sized buffers before validation, enabling memory amplification DoS - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` deserializes a serialized threshold key set from an untrusted byte stream. The participant count `n` is read as a raw `u16` and immediately used to size `Vec::with_capacity` for the `Interpolation::Constant` coefficient vector, and to drive two loops that read `n` scalars and `n` group elements into a `HashMap`, all before `ThresholdParams::new(t, n, i)` validates the parameters at the end of the function [1](#0-0) .

### Finding Description
The bug class in the reference advisory is untrusted input driving allocation/loop work not bounded by validation. The analog in `ThresholdKeys::read`:

1. `t`, `n`, and `i` are read as raw `u16`s at lines 591–602. `n` is not yet checked against `t`, `i`, or any maximum beyond `u16::MAX`.
2. When the interpolation tag is `0` (`Interpolation::Constant`), the code executes `Vec::with_capacity(usize::from(n))` at line 608 — an allocation of `n * size_of::<C::F>()` bytes driven entirely by a 2-byte attacker field. With `n = 0xFFFF` and a 32-byte scalar (e.g., `Ristretto`, `Secp256k1`), a single ~9-byte prefix forces a ~2 MiB reservation before a single scalar byte is read.
3. The loops at lines 609–611 and 621–623 then iterate up to `n` times performing `C::read_F`/`read_G` — each `read_G` involves a point decompression and re-canonicalization (`from_bytes` + `to_bytes` comparison in `Ciphersuite::read_G` at crypto/ciphersuite/src/lib.rs:91-100), so the attacker also controls CPU work proportional to bytes they supply.
4. Only after all allocations and reads does `ThresholdParams::new(t, n, i)` run (line 626), so an inconsistent `(t, n, i)` — e.g., `t > n`, `n = 0`, `i > n` — still triggers the full allocation and deserialization work first.

### Impact Explanation
`ThresholdKeys::read` is a deserialization entry point for untrusted bytes (it is one of the enumerated attacker-reachable `read` APIs). An unprivileged party can force a ~2 MiB allocation per call with only a handful of transmitted bytes (allocation-before-read amplification factor of ~200,000× on the initial reservation). While the allocation is released when a `read_exact` fails on a truncated stream, an attacker sustaining concurrent calls — or supplying the full body (bounded only by `u16::MAX * ~64 bytes ≈ 4 MiB per call`, still many times larger than any legitimate key set for realistic `n`) — can inflate memory footprint and allocator pressure well beyond the true message size, degrading or OOM-ing the host. This is the same CWE-400 shape as the reference bug: allocation grows based on attacker-controlled parameters rather than validated need.

### Likelihood Explanation
Reachability is direct: any path that feeds peer- or wire-controlled bytes into `ThresholdKeys::read` (e.g., key material rehydrated from coordinator-supplied data or a gossiped payload) triggers the allocation. Exploitation requires no keys, no valid signatures, and no protocol role — only the ability to get the deserializer invoked repeatedly or concurrently. Impact is resource exhaustion only (no secret leakage, no forgery), and the transient nature of the reservation on truncated input makes it a Medium-severity DoS rather than something higher.

### Recommendation
Validate `t`, `n`, `i` via `ThresholdParams::new` (or explicit bounds checks) *before* any allocation sized by `n`. Replace `Vec::with_capacity(usize::from(n))` with a plain `Vec::new()` (or a capacity bounded by a protocol-realistic maximum, e.g., `min(n, MAX_PARTICIPANTS)`), and consider streaming the scalar/point reads so memory committed never exceeds bytes actually consumed. Apply a documented maximum participant count early to cap both the scalar vector and the `verification_shares` `HashMap` loop.

### Proof of Concept
```rust
use std::io;
use dalek_ff_group::Ristretto;
use ciphersuite::Ciphersuite;
use dkg::ThresholdKeys;

// Attacker bytes: valid curve ID, then n = 0xFFFF with interpolation = Constant.
fn malicious_payload() -> Vec<u8> {
    let mut buf = vec![];
    buf.extend(&(u32::try_from(<Ristretto as Ciphersuite>::ID.len()).unwrap())
        .to_le_bytes());
    buf.extend(<Ristretto as Ciphersuite>::ID);
    buf.extend(&1u16.to_le_bytes());      // t = 1 (passes trivial checks)
    buf.extend(&u16::MAX.to_le_bytes());  // n = 65535, unchecked at this point
    buf.extend(&1u16.to_le_bytes());      // i = 1
    buf.push(0);                          // Interpolation::Constant
    // No scalar bytes follow: the ~2 MiB Vec::with_capacity(n) has already
    // been reserved before the first read_F fails.
    buf
}

fn main() {
    // Each call transiently reserves ~2 MiB of heap from ~9 attacker bytes.
    // Concurrent/repeated calls multiply allocator pressure arbitrarily.
    let _ = ThresholdKeys::<Ristretto>::read(&mut malicious_payload().as_slice());
}
```

Uncertainty note: this analog captures the allocation-amplification half of the advisory's bug class. I did not find an in-scope analog of the "stuck iterator that never returns `None`" half — the reachable `read`/`verify` loops in `crypto/frost`, `crypto/dkg`, `crypto/schnorr`, and `crypto/multiexp` are all bounded by their input or caller-supplied slice lengths. Other in-scope candidates (`SchnorrAggregate::read` in crypto/schnorr/src/aggregate.rs:77-88) grow only with bytes actually present, so they do not amplify.

    {
      let different = || io::Error::other("deserializing ThresholdKeys for another curve");

      let mut id_len = [0; 4];

      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }
