### Title
`SignableTransaction` omits the OP_RETURN output from weight/vsize and fee calculation, producing under-priced or non-standard transactions - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`SignableTransaction::new` accepts an arbitrary `data` payload of up to 80 bytes and appends it as an `OP_RETURN` output to `tx_outs` (lines 194–202). However, the weight/vbyte computation at line 204 (`Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`) is performed over `payments` only — the already-pushed OP_RETURN output is never included in the weight, the virtual size, the `needed_fee`, or the `MAX_STANDARD_TX_WEIGHT` check. The resulting transaction is larger than what the fee was priced for, so the effective fee rate is lower than `fee_per_vbyte`, and a transaction at the standardness boundary can exceed `MAX_STANDARD_TX_WEIGHT` without being rejected by `TransactionError::TooLargeTransaction`.

### Finding Description
In `SignableTransaction::new`, the data output is added to `tx_outs` before weight calculation:

```rust
// send.rs:194-204
if let Some(data) = data {
  tx_outs.push(TxOut { value: Amount::ZERO, script_pubkey: ScriptBuf::new_op_return(...) });
}
let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
```

`calculate_weight_vbytes` (lines 62–127) builds its dummy transaction from `payments` and `change` only; it has no parameter for the OP_RETURN output. Consequently:

1. `vbytes` (and `vbytes_with_change` at line 226) undercounts the real vsize by the full OP_RETURN output size (~`8 + 1 + 1 + len(data)` bytes, up to ~90 vbytes with the maximum 80-byte payload).
2. `needed_fee = fee_per_vbyte * vbytes` is therefore under-priced relative to the true transaction size.
3. The `weight > MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight` computed without the OP_RETURN output (or without the change output in the no-change path interplay), so a transaction that is actually non-standard can pass validation.

The same omission applies to the change path: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` still never models the OP_RETURN output.

### Impact Explanation
An unprivileged party able to influence the `data` field of a transaction the multisig is asked to sign (e.g., any flow attaching an InInstruction/arbitrary metadata to a Bitcoin spend) can cause the produced transaction to have an effective fee rate materially below the requested `fee_per_vbyte`. Near the minimum-relay-fee boundary this yields a signed transaction that Bitcoin Core will not relay or mempool-accept (`min relay fee not met` / non-standard weight), leaving the spent inputs' funds locked in an unbroadcastable transaction while `fee()`/`needed_fee()` report consistent-looking values. Analogous to the reference incident's "slippage"/value-loss class: the protocol commits funds under miscalculated economics — the declared fee rate is not the fee rate actually paid, and correctness of the spend is silently degraded by attacker-controlled bytes.

### Likelihood Explanation
Requires only that a transaction be constructed with `data: Some(..)` — a normal, supported code path (OP_RETURN outputs are a first-class feature of `SignableTransaction::new`). The miscalculation is deterministic whenever `data` is non-empty; severity of the outcome depends on how close the requested fee rate is to relay minimums and how large the payload is, but no attacker privilege beyond supplying transaction data is needed.

### Recommendation
Include the OP_RETURN output in `calculate_weight_vbytes` — pass the fully constructed `tx_outs` (or an explicit data length) into the weight model rather than `payments` alone, for both the change and no-change invocations, so `needed_fee`, the dust-change threshold decision, and the `MAX_STANDARD_TX_WEIGHT` check all account for the data output.

### Proof of Concept
```rust
// Conceptual: construct a SignableTransaction with max-size OP_RETURN data
let data = vec![0u8; 80];
let tx = SignableTransaction::new(
    vec![input],                       // one ReceivedOutput
    &[(payment_script, 1000)],
    None,
    Some(data),
    fee_per_vbyte,                     // e.g. exactly min relay rate
).unwrap();
// tx.weight()/vsize of tx.transaction() exceeds the vbytes used for needed_fee
// by the OP_RETURN output (~90 vbytes), so the actual fee rate is
// needed_fee / actual_vsize < fee_per_vbyte, potentially below
// DEFAULT_MIN_RELAY_TX_FEE, making the signed TX non-relayable.
```

The root cause is at `networks/bitcoin/src/wallet/send.rs:194-204` and `networks/bitcoin/src/wallet/send.rs:224-235`, where `tx_outs` diverges from the `payments`-only model used by `calculate_weight_vbytes` (`networks/bitcoin/src/wallet/send.rs:62-127`).
