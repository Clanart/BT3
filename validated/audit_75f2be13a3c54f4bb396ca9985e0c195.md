### Title
Attacker-classified internal outputs: unprivileged Bitcoin sender can deposit to the multisig's reserved Change/Branch offset scripts and have them reported as protocol-internal outputs - (File: processor/src/networks/bitcoin.rs)

### Summary
The Nextcloud bug is a missing authorization check: an app without `MANAGE_DOCUMENTS` could view thumbnails it was not entitled to. The Serai analog is in the Bitcoin output scanner: `get_outputs` classifies any on-chain output solely by whether its `script_pubkey` matches a registered offset script. Three of the four registered offsets (`Branch`, `Change`, `Forwarded`) are internal classifications, yet their scalars are deterministic and publicly computable (`Secp256k1::hash_to_F(KEY_DST, b"change"|"branch"|"forward")`). Any third party can therefore send a transaction paying to an internal-only script and have the processor report it as an `OutputType::Change` or `OutputType::Branch` output — an output classification the protocol reserved for transactions it created itself — without any check that the output was actually produced by an authorized internal flow.

### Finding Description
`scanner()` registers three offsets derived from public constants and returns a `kinds` map keyed by offset serialization:

```rust
// processor/src/networks/bitcoin.rs:333-344
register(OutputType::Branch,   *BRANCH_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"branch")));
register(OutputType::Change,   *CHANGE_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"change")));
register(OutputType::Forwarded,*FORWARD_OFFSET.get_or_init(|| Secp256k1::hash_to_F(KEY_DST, b"forward")));
```

`get_outputs` then scans every non-coinbase transaction and labels each matched output purely by offset — there is no provenance check against outputs the processor itself produced:

```rust
// processor/src/networks/bitcoin.rs:691-699
for tx in &block.txdata[1 ..] {
  for output in scanner.scan_transaction(tx) {
    let kind = kinds[offset_repr_ref];
    let output = Output { kind, presumed_origin: None, output, data: vec![] };
    outputs.push(output);
  }
```

`Scanner::scan_transaction` matches only `output.script_pubkey` against the registered scripts, and `register_offset` documents that the offsets must be "securely generated" because arbitrary offsets can introduce script-path spends — but `hash_to_F` offsets are deterministic and computable by anyone holding the (public) group key, so they offer no authorization property:

```rust
// networks/bitcoin/src/wallet/mod.rs:205-210
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput { offset: *offset, output: output.clone(), ... });
}
```

These outputs are pushed to `scanner.events` / saved via `ScannerDb::save_outputs` and handed to the multisig scheduler (`processor/src/multisigs/scanner.rs:562-566, 700`), which treats non-`External` kinds as internal artifacts rather than deposits.

### Impact Explanation
An unprivileged Bitcoin user can inject outputs the processor believes are `Change` or `Branch` outputs — internal UTXO bookkeeping entries it assumes were created by its own signed transactions. Depending on downstream handling in `processor/src/multisigs/scheduler/utxo.rs`, such phantom internal outputs can corrupt UTXO accounting: an attacker-originated `Change` output can be treated as change of a plan that never existed, and `Branch` outputs may be misattributed to key-rotation flows. Since the offsets are known, the outputs remain spendable by the multisig, but they are *attributed* to flows that never authorized them — the same failure mode as the Nextcloud advisory: data is surfaced to a consumer under a classification it had no permission to carry. I could not fully trace the scheduler's handling of `OutputType::Change`/`Branch` within the iteration budget, so the concrete accounting impact (e.g., crediting a forged internal output toward a pending plan or double-spending accounting) is inferred from the classification path rather than proven end-to-end.

### Likelihood Explanation
The attack requires only sending a standard P2TR transaction to a deterministically derived address — computable offline by anyone who knows the multisig's group key (which is public). No key material, collusion, or validator access is needed. The cost is the deposited amount plus fees, and ≥ `N::DUST` to pass the dust filter at `processor/src/multisigs/scanner.rs:564`.

### Recommendation
Track provenance for internal output kinds: maintain a DB set of outpoints/scripts the protocol itself created (or is expecting as change/branch), and only classify a scanned output as `Change`/`Branch` if it matches a recorded internal output; otherwise classify as `External` or reject. At minimum, do not let `kinds` promote an externally-created script match to an internal `OutputType` without corroborating evidence.
