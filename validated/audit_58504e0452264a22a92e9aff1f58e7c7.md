### Title
Attacker-controlled `Participant` indexes in `blame`/`decrypt_with_proof` cause out-of-bounds `HashMap` indexing, crashing the process (remote DoS) - (File: crypto/dkg/pedpop/src/encryption.rs, crypto/dkg/pedpop/src/lib.rs)

### Summary
`Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` and `BlameMachine::blame_internal` indexes `self.commitments[&sender]` without checking that the supplied `Participant` index is within the protocol set (`1 ..= n`). `Participant::new` accepts any non-zero `u16` (up to 65535), so untrusted blame inputs carrying a participant index outside the registered set trigger a panic (indexing a missing `HashMap` key), aborting the calling thread/process. This is the Serai analog of CVE-2026-18916: an unprivileged remote party can crash a serving instance by supplying crafted public inputs, denying service.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `decrypt_with_proof` performs `self.enc_keys[&decryptor]` (line ~388) to fetch the decryptor's encryption key before verifying the DLEq proof. `enc_keys` only contains entries for participants registered via `register`/`AdditionalBlameMachine::new`, which populates exactly `1 ..= n` (`crypto/dkg/pedpop/src/lib.rs` lines 649–662). If `decryptor` is a `Participant` whose index exceeds `n` — or was never registered — the `HashMap` index panics.

Likewise, `BlameMachine::blame_internal` (`crypto/dkg/pedpop/src/lib.rs`, lines 575–609) evaluates `self.commitments[&sender]` (line ~599) when checking share validity, panicking for an out-of-range `sender`.

The public entry points are `BlameMachine::blame` and `AdditionalBlameMachine::blame`, which take `sender`/`recipient` as raw `Participant` values. In Serai's deployment, blame parameters originate from wire-encoded data — e.g. `Transaction::InvalidDkgShare` reads `accuser` and `faulty` as `Participant::new(u16::from_le_bytes(...))` with no upper bound (`coordinator/src/tributary/transaction.rs` lines 346–354). A `u16` value larger than `n` deserializes fine (only `0` is rejected) and reaches `blame_internal`, where the unchecked indexing panics.

### Impact Explanation
A single malformed blame/accusation message with `sender` or `recipient` set to any value in `(n, 65535]` deterministically panics the node evaluating it. Repeated messages keep crashing the service (or the task processing them), denying service — the same availability impact class as the NSD serve-child crash. Since `blame` can be invoked by `AdditionalBlameMachine` by parties "not a member in the DKG protocol," the input surface is broader than just DKG participants.

### Likelihood Explanation
Triggering only requires supplying a syntactically valid `EncryptedMessage` (or `EncryptionKeyProof`) plus an out-of-range participant index — the `pop` Schnorr signature in `decrypt_with_proof` binds `from`, and an attacker holding the ephemeral key can produce a valid PoP for any sender label, or the panic on `enc_keys[&decryptor]` fires before any verification when `recipient` is out of range. No privileged position is needed; the panic is reachable from untrusted bytes.

### Recommendation
Replace `self.enc_keys[&decryptor]` and `self.commitments[&sender]` with `.get(...)` lookups returning `DecryptionError::InvalidProof`/`PedPoPError::InvalidParticipant`-style errors, and/or validate `sender <= n` and `recipient <= n` at the top of `blame_internal`/`decrypt_with_proof`. Callers should also bound-check `Participant` values read from the wire against the active `ThresholdParams::n` before invoking `blame`.

### Proof of Concept
```rust
// Setup: a completed PedPoP DKG with params n = 3 (or AdditionalBlameMachine::new(ctx, 3, msgs))
let mut machine: BlameMachine<Ed25519> = ...; // from calculate_share(...)
let blame_machine = AdditionalBlameMachine::<Ed25519>::new(context, 3, commitment_msgs).unwrap();

// Attacker crafts an accusation with recipient = Participant(500), which was never registered.
let sender = Participant::new(1).unwrap();
let recipient = Participant::new(500).unwrap(); // valid Participant: only 0 is rejected

// Any EncryptedMessage / EncryptionKeyProof the attacker constructs; if `proof` is Some(_),
// decrypt_with_proof reaches `self.enc_keys[&decryptor]` and panics before proof verification.
let msg: EncryptedMessage<Ed25519, SecretShare<...>> = attacker_msg;
let proof: Option<EncryptionKeyProof<Ed25519>> = Some(attacker_proof);

// PANIC: `self.enc_keys[&decryptor]` -> "no entry found for key"
let _faulty = blame_machine.blame(sender, recipient, msg, proof);
```

The same panic occurs via `self.commitments[&sender]` in `blame_internal` when `sender` is out of range and `recipient` is in range with a well-formed message/proof.

Note: I could not fully trace whether the coordinator validates `accuser`/`faulty` against `n` before invoking these APIs; the panic itself is fully contained in the in-scope `crypto/dkg/pedpop` code regardless of caller validation.
