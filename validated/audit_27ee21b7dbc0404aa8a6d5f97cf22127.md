### Title
Webhook shop attribution is not covered by HMAC verification, enabling cross-shop webhook spoofing - (File: lib/shopify_app/controller_concerns/webhook_verification.rb)

### Summary
Shopify webhook requests are authenticated by `ShopifyApp::WebhookVerification#verify_request`, which validates an HMAC computed only over the raw request body [1](#0-0)  using `PayloadVerification#hmac_valid?`, which likewise hashes only `data = request.raw_post` against the app's shared secret [2](#0-1) . The shop that a webhook is attributed to, however, is read straight from the `X-Shopify-Shop-Domain` request header, which is not part of the signed payload [3](#0-2) . The same pattern is repeated in the generated webhook controller and the built-in `WebhooksController`, both of which construct `ShopifyAPI::Webhooks::Request` from `request.raw_post` and `request.headers` and hand the resulting shop attribution downstream to per-shop background jobs [4](#0-3) [5](#0-4) .

### Finding Description
This mirrors the CryptoPunks root cause: an operation is executed and its result is attributed to an identity (`shop_domain`) that is *not* covered by the cryptographic proof of authorization (the HMAC), only the payload content is. Since one shared app secret is used for HMAC across all shops installed on an app, a party that can trigger and capture one legitimately-signed webhook delivery for their own shop (or for any shop) holds a `(body, hmac)` pair that remains valid regardless of which `X-Shopify-Shop-Domain` header value accompanies it, because that header is excluded from the signed bytes [2](#0-1) . Replaying that same body with a different shop-domain header still passes `hmac_valid?`, so `verify_request` allows the request through [1](#0-0) , and the controller/job layer will process the payload under the attacker-chosen shop's identity [4](#0-3) .

### Impact Explanation
An app relying on `shop_domain`/`webhook_request.shop` (as returned by `WebhookVerification#shop_domain` or `ShopifyAPI::Webhooks::Request#shop`) to key per-tenant background jobs or datastores can have webhook-driven state (e.g. `CartsUpdateJob`, `OrdersCreateJob`) attributed to, and mutate data belonging to, a shop other than the one that actually generated the event — a cross-shop data-integrity/spoofing issue, analogous to the CryptoPunk being deposited to the wrong account despite the underlying "sale" transaction being real.

### Likelihood Explanation
Exploitation requires the attacker to have captured at least one validly HMAC-signed webhook body (e.g., from their own installation, since the HMAC secret is shared per-app rather than per-shop), then resend it directly to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header. This bypasses Shopify's own delivery infrastructure but the receiving `WebhookVerification`/`PayloadVerification` code, as written, has no mechanism to detect the substitution because the header is outside the signed scope [6](#0-5) .

### Recommendation
Bind the shop identity to the signed payload rather than trusting the unauthenticated header — e.g., include/validate the shop domain from the webhook body (most Shopify webhook payloads embed shop-identifying data) or require the `X-Shopify-Shop-Domain` value to match a domain independently verified via the session/token layer before dispatching shop-scoped jobs, instead of relying solely on `request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]` in `shop_domain` [3](#0-2) .

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook (e.g., `carts/update`), capturing the raw POST body and its valid `X-Shopify-Hmac-Sha256` header from Shopify's real delivery.
2. Attacker resends the identical body and HMAC header to the app's `/webhooks/:type` endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. `PayloadVerification#hmac_valid?` recomputes the HMAC over the same raw body with the shared app secret and it matches, so `verify_request` passes [1](#0-0) .
4. `WebhooksController#receive` (or the generated per-topic job) processes the event using `shop_domain: "victim-shop.myshopify.com"`, injecting attacker-controlled webhook content attributed to a shop the attacker does not own [4](#0-3) .

# frozen_string_literal: true

module ShopifyApp
  module WebhookVerification
    extend ActiveSupport::Concern
    include ShopifyApp::PayloadVerification

    included do
      skip_before_action :verify_authenticity_token, raise: false
      before_action :verify_request
    end

    private

    def verify_request
      data = request.raw_post
      unless hmac_valid?(data)
        ShopifyApp::Logger.debug("Webhook verification failed - HMAC invalid")
        head(:unauthorized)
      end
    end

    def shop_domain
      request.headers["HTTP_X_SHOPIFY_SHOP_DOMAIN"]
    end
  end
end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
