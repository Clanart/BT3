## Title
Unbounded CLVM cost when parsing untrusted `Offer` files enables wallet-side spend-processing halt — (File: `chia/wallet/trading/offer.py`)

### Summary
The `funtoken` bug is a "hardcoded/mismatched gas budget breaks the 63/64-style resource-metering invariant, letting an attacker force unbounded recursive execution and halt transaction processing." Chia's consensus-critical CLVM execution paths (mempool `pre_validate_spendbundle`, block validation, `compute_additions_with_cost`) all thread a single, monotonically-decreasing `max_cost` through nested puzzle execution, so this class of bug cannot occur there — CLVM's own cost accounting already enforces the equivalent invariant. The closest analog that reproduces the "unbounded/hardcoded resource budget consumed by attacker-controlled recursion in the same class of code" is in `Offer._get_offered_coins()`, which processes attacker-supplied `CoinSpend`s from an **untrusted offer file** and runs their inner puzzles with an unbounded cost budget instead of the network's `MAX_BLOCK_COST_CLVM`.

### Finding Description
`Offer.__post_init__` correctly threads a shrinking `max_cost` (starting at `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`) through `compute_spend_hints_and_additions` for every coin spend in the bundle, and raises `ValidationError` if the cumulative cost is exceeded [1](#0-0) .

However, `Offer._get_offered_coins()`, which is used to figure out what coins/assets an offer actually contains (called via `get_offered_coins()` from `TradeManager.calculate_tx_records_for_offer` and other offer-summary/accept code paths), initializes its own independent cost budget as `INFINITE_COST` rather than reusing the bounded budget, and then runs each spend's inner puzzle against that budget: [2](#0-1) 

Because `cost_left` starts at `INFINITE_COST`, an attacker who crafts an offer file containing a `CoinSpend` whose inner puzzle is expensive or deeply/recursively self-referential is not bounded by `MAX_BLOCK_COST_CLVM` at all when a wallet inspects or takes that offer — this method runs the inner puzzle unconstrained by the network's cost ceiling that every other code path (mempool admission, block validation, `compute_additions_with_cost`) enforces. This mirrors the root cause of the C4 finding: a resource-metering call site uses a budget disconnected from the actual remaining/overall budget, permitting attacker-chosen recursion depth/cost to dictate resource consumption of the code that must process it.

### Impact Explanation
An attacker can distribute a maliciously crafted `.offer` file (or serve it via any offer-sharing mechanism) where the "offered" coin's parent puzzle is designed to be extremely CPU/memory expensive (e.g., deep self-recursive CLVM, similar in spirit to the `deep_recursion` test puzzle already present in this codebase's test suite) but still valid CLVM that a normal `max_cost`-bounded validator would reject early. When a victim wallet calls `Offer.get_offered_coins()` (e.g., during offer summary display or `take_offer` flows in `TradeManager`), that inner puzzle is executed with no cost ceiling, unlike every consensus-facing execution path. This can hang/consume excessive memory in the victim's wallet process while it evaluates an untrusted offer, i.e., a spend/offer-triggered halt of transaction processing local to the wallet handling the offer.

### Likelihood Explanation
Medium. Exploitation requires only crafting a spend bundle with a recursive/expensive inner puzzle and packaging it as a standard bech32-encoded offer — something any unprivileged offer counterparty can construct and hand to another user's wallet (there is no signature-of-offer-maker requirement checked before this code path runs). It does not require access to the mempool or consensus at all, only that a victim wallet processes the file via `Offer.from_bech32`/`from_bytes` and then calls `get_offered_coins()`.

### Recommendation
Thread the same bounded, decrementing `max_cost` (e.g., `MAX_BLOCK_COST_CLVM`, or the residual budget tracked in `__post_init__`) into `_get_offered_coins()` instead of starting from `INFINITE_COST`, and raise `ValidationError` (as `__post_init__` already does) if the cumulative cost of inner-puzzle execution during offered-coin detection exceeds that budget.

### Proof of Concept
1. Construct a `CoinSpend` whose puzzle is a deeply recursive CLVM program comparable to the `deep_recursion` test puzzle already used in mempool cost tests [3](#0-2) , sized so that a solution argument (e.g. `n = 10_000_000`) would cost far more than `MAX_BLOCK_COST_CLVM` if metered.
2. Wrap this spend as the "offered" side of a `WalletSpendBundle`/`Offer`, matching the settlement puzzle heuristics in `_get_offered_coins` (parent puzzle producing a `CREATE_COIN` to `OFFER_MOD_HASH`).
3. Serialize via `Offer.__bytes__`/`to_bech32` and deliver it to a victim.
4. Victim wallet calls `Offer.from_bech32(...)` then `offer.get_offered_coins()` (reachable from `TradeManager.calculate_tx_records_for_offer`) — `_get_offered_coins` executes the inner puzzle with `cost_left = INFINITE_COST`, so the recursive puzzle runs to completion unbounded by `MAX_BLOCK_COST_CLVM`, unlike `__post_init__`'s already-bounded `compute_spend_hints_and_additions` call, causing excessive CPU/memory consumption in the wallet process while it evaluates the offer.
