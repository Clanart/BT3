### Title
Stale decimal precision check lets an asset owner cause unauthorized over-minting in `hyper-fungible-token` cross-chain transfers - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`register_token`/`update_token` validate `erc_decimals >= local_decimals` only **once, at registration time**, but `on_accept` (and `on_timeout`) re-derive `local_decimals` live from the asset's current `pallet-assets` metadata on every incoming message. Because `pallet-assets` metadata (including `decimals`) is mutable by the asset's `Owner` at any time via the standard `set_metadata`/`force_set_metadata` extrinsics, an asset owner can invalidate the invariant after registration and cause the bridge to mint far more local tokens than the amount actually locked/burned on the remote chain — the exact "config validated at instantiate but never re-checked at execution, causing miscalculated amounts" pattern from the external report, mapped onto this repo's real custody logic.

### Finding Description
`register_token`/`update_token` enforce the invariant once: [1](#0-0) 

`Precisions::<T>` stores the `erc_decimals` value fixed at registration time, but `on_accept` re-reads the *current* local asset decimals from `pallet-assets` metadata on every message: [2](#0-1) 

The conversion itself has no floor/invariant guard — it silently clamps the exponent to zero when `local_decimals > erc_decimals`: [3](#0-2) 

If the underlying asset's `decimals` metadata is later increased above the registered `erc_decimals` (e.g. via `pallet-assets::set_metadata`, callable by the asset's `Owner`, independent of the bridge's `T::CreateOrigin`), `erc_decimals.saturating_sub(local_decimals)` collapses to `0`, the divisor becomes `1`, and the raw ERC20 `U256` amount is minted verbatim into the local asset instead of being scaled down by `10^(erc_decimals-local_decimals)`. This produces a massive over-mint for any subsequent legitimate cross-chain deposit, and the same stale-decimals issue also corrupts the refund path in `on_timeout`.

### Impact Explanation
This is unauthorized minting / fund creation on the destination chain relative to what was actually escrowed/burned on the source chain — a direct "false state acceptance leading to loss/theft of funds" and "logic attack" per the bounty's impact categories. Any beneficiary of a subsequent bridged message (including the asset owner themselves, self-bridging any amount) receives orders of magnitude more tokens than backed by the locked/burned collateral, diluting or draining value backing the bridged asset.

### Likelihood Explanation
The precondition — the asset's `Owner` in `pallet-assets` calling the standard `set_metadata` extrinsic to change `decimals` after the bridge has registered the token — is a normal, permissionless capability of asset ownership in `pallet-assets`, not a compromised admin/governance/relayer/prover assumption of the bridge itself. Whether the asset owner is distinct from bridge governance in production deployments (e.g., a pre-existing community token bridged by governance while the original creator retains `Owner` rights) determines exploitability; this could not be fully confirmed from the indexed files, since the runtime-level asset ownership/admin wiring (`parachain/runtimes/*/src/ismp.rs`, asset creation origin) was not fully inspected due to tool-call limits.

### Recommendation
- Store and use a single, immutable decimals value captured at registration time for both sides of the conversion (or re-validate `erc_decimals >= current_local_decimals` inside `on_accept`/`on_timeout`/`send` before using it, rejecting the message rather than clamping to zero).
- Replace `saturating_sub` with a checked subtraction that errors (`HftError::ErcDecimalsBelowLocal`-style) when `local_decimals > erc_decimals` at message-processing time, rather than only at registration.
- Consider freezing or asserting the local asset's metadata (decimals) once registered for bridging, or requiring `CreateOrigin`-only control over metadata changes for bridged assets.

### Proof of Concept
1. Governance registers asset `X` (created/owned by user `A`) via `register_token`, with `local_decimals = 6` and `erc_decimals = 18` (passes `ensure!(18 >= 6)`).
2. A legitimate bridge deposit of `1e18` raw ERC20 units (1 token, 18-decimals) arrives; `on_accept` computes `1e18 / 10^(18-6) = 1e6` local units — correct.
3. User `A`, still the `Owner` of asset `X` in `pallet-assets`, calls `set_metadata` to change `X`'s decimals from `6` to `18` (no bridge-side check prevents this).
4. Any subsequent bridged deposit of `1e18` raw ERC20 units now computes `local_decimals = 18`, so `erc_decimals.saturating_sub(local_decimals) = 0`, divisor `= 1`, and `on_accept` mints `1e18` local units instead of `1e6` — a `1,000,000x` over-mint credited to the beneficiary, backed by no corresponding escrow.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
