## Finding: Directory containment check in `resolveWithin` uses a naive string prefix comparison, allowing sibling-directory escape

The reported dNFT bug is a **broken invariant on a boundary check**: the liquidation gate compares a value (share percentage) against a threshold using logic that can be satisfied by a crafted, attacker-timed input, letting a value that should be rejected as "outside the safe zone" pass as "inside" it. The Desktop analog is a boundary/containment check that is enforced by unsafe string comparison rather than a real path-boundary comparison.

### Title
Directory containment bypass via string-prefix comparison in `resolveWithin` — ([File: app/src/lib/path.ts])

### Summary
`resolveWithin()` is the shared primitive Desktop uses to confine an attacker/remote-influenced relative path (e.g. a `filepath` query parameter from an `x-github-client://openRepo` deep link) to a trusted root directory (the repository path) before performing a filesystem action such as revealing a file with `shell.showItemInFolder`. The containment check is implemented as a raw string prefix comparison, `realResolved.startsWith(realRoot)`, with no verification that the next character after the prefix is a path separator. [1](#0-0) 

### Finding Description
`_resolveWithin` computes `resolved` by joining/normalizing the attacker-controlled `pathSegments` and resolving them against `rootPath`, then calls `realpath()` on both the root and the resolved path and finally checks `realResolved.startsWith(realRoot)` to decide whether the resolved path is "inside" the root. [2](#0-1) 

This is the classic "prefix without separator" containment bug: if the root directory happens to be, say, `/Users/victim/Documents/GitHub/myrepo` and a sibling directory `/Users/victim/Documents/GitHub/myrepo-secrets` exists, a relative path such as `../myrepo-secrets/file` normalizes/resolves to `/Users/victim/Documents/GitHub/myrepo-secrets/file`, which passes `startsWith(realRoot)` as a raw string even though it is a completely different, sibling directory outside the intended root. The existing unit tests only cover exact-parent escapes (`..`, `../..`) and symlink escapes, not the sibling-prefix case, so this gap is not covered by `resolveWithin` tests. [3](#0-2) 

The primary reachable, attacker-controlled call site is the `open-repository-from-url` deep link handler. `parseAppURL` accepts a `filepath` query parameter straight from a URL (i.e., something an attacker can put in a link a user clicks or an `x-github-client://` protocol handler invocation), doing essentially no sanitization beyond taking it verbatim from the query string. [4](#0-3) 

`Dispatcher.openRepositoryFromUrl` then only rejects absolute `filepath` values; for a relative value it hands the path straight to `resolveWithin(repository.path, filepath)` and, if that returns non-null, calls `shell.showItemInFolder(resolved)` on the resolved path. [5](#0-4) 

Because `resolveWithin`'s containment guard can be defeated by a sibling directory whose name shares the repository directory name as a prefix, this check does not actually guarantee `resolved` is inside the repository — it only guarantees the string happens to start with the same characters.

### Impact Explanation
An attacker who can get a victim to click a crafted `x-github-client://openRepo/...?filepath=...` link (or any `open-repository-from-url` deep link) can attempt to make Desktop reveal/open a file located outside the cloned repository's working directory, provided a sibling directory exists whose name is prefixed by the repository's directory name (e.g. auto-generated clone folders such as `repo`, `repo-1`, `repo-old`, `repo-backup`, or attacker-primed folder names an app installer/user commonly creates). This breaks the "file access confined to the repo" invariant that `resolveWithin` and the `isAbsolute`/`resolveWithin` guard in the dispatcher are specifically designed to enforce. `resolveWithin` is also used more broadly (e.g. in Copilot's conflict-context file reader) so the same containment defect could be re-triggered anywhere this shared helper is trusted as an authoritative boundary check. [6](#0-5) 

### Likelihood Explanation
The exploit requires (a) the victim to click an attacker-supplied link, which is within the accepted threat model ("a link or deep link the user clicks"), and (b) a sibling directory on disk whose name is prefixed by the repository directory's name. This second condition is opportunistic rather than fully attacker-controlled, which lowers likelihood versus a universal bypass, but it is a real, non-hypothetical directory-naming pattern (Desktop itself, and most OSes/clone tools, create suffixed sibling folders like `repo-1`, `repo (2)`, `repo-copy`, `repo-old`, etc. when handling name collisions), so the precondition is plausible in real user environments.

### Recommendation
Fix the containment check in `_resolveWithin` to compare directory boundaries rather than raw string prefixes, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
Add a regression test asserting that a sibling directory sharing a name prefix with the root is correctly rejected (e.g. root `/tmp/x` and target `/tmp/x-secret` must not be considered "within").

import { resolveWithin } from '../../src/lib/path'
import { mkdir, rm } from 'fs/promises'
import { join } from 'path'
import { tmpdir } from 'os'

// setup: /tmp/.../repo and a sibling /tmp/.../repo-secret/leak.txt
const base = await mkdtemp(join(tmpdir(), 'poc-'))
const root = join(base, 'repo')
const sibling = join(base, 'repo-secret')
await mkdir(root, { recursive: true })
await mkdir(sibling, { recursive: true })
await writeFile(join(sibling, 'leak.txt'), 'secret')

// Simulates dispatcher.openRepositoryFromUrl handling
// x-github-client://openRepo/<url>?filepath=../repo-secret/leak.txt
const resolved = await resolveWithin(root, '../repo-secret/leak.txt')
console.log(resolved)

// treats "repo-secret" as within "repo".

```typescript
async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
