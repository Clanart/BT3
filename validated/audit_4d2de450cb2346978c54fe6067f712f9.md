## Analysis

The Sherlock report's core invariant is: **a multi-asset transfer loop that reverts entirely on a single asset's transfer failure permanently blocks an otherwise-valid state transition** (liquidation). The direct Hyperbridge analog is the escrow-release loop in the Intents settlement path.

### Title
Single failing token transfer in multi-asset escrow release permanently blocks fund settlement (RedeemEscrow/RefundEscrow) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw` iterates over all tokens in a `WithdrawalRequest` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one in a single loop, with no per-asset failure isolation. [1](#0-0) 
This function is invoked from `onAccept` for both `RedeemEscrow` and `RefundEscrow` request kinds, and from `onGetResponse` for cross-chain cancellation refunds. [2](#0-1) [3](#0-2) 

If a transfer to any single token in the order's input set reverts (blacklisted beneficiary address, a paused/upgraded token, or a token that reverts on zero-value transfer), the entire `_withdraw` call reverts.

### Finding Description
`EvmHost.dispatchIncoming` calls `module.onAccept(...)` and, on failure, deletes the stored request receipt "so that it can be retried" rather than reverting the whole handler batch: [4](#0-3) 

This retry design assumes failures are transient. But a failing ERC-20 transfer inside `_withdraw` is often **permanent**: a USDC-blacklisted beneficiary stays blacklisted, a token the issuer paused for that pair stays paused, or a token that reverts on 0-value transfer (weird-ERC20) will always revert for that same order. Because `_withdraw` has no per-token try/catch or skip-and-retry-later mechanism, any single non-cooperative or misbehaving asset in a multi-input order makes the *entire* escrowed order — including all the other, perfectly fine tokens in the same commitment — permanently unredeemable and unrefundable. Since retries just repeat the exact same reverting call, the request can be resubmitted forever without ever succeeding, and the escrowed funds are locked in the contract indefinitely.

This is directly analogous to `AccountManager._liquidate`/`sweepTo` in the referenced report: one asset's transfer failure blocks settlement of the whole batch, and it is a condition that can be deliberately engineered by a user/solver (e.g., placing an order whose input token set includes a token they know will be blacklisted or paused for their own beneficiary, or exploiting a zero-value-transfer-revert token) to prevent the solver from ever redeeming escrow, or to prevent themselves from ever being refunded on cancel — but crucially, it also destroys the funds of the *other* party who has no control over which tokens end up in that same order.

### Impact Explanation
Escrowed order funds (both solver redemption via `RedeemEscrow` and user refunds via `RefundEscrow`/cross-chain cancel) become permanently locked in the `IntentGateway`/`IntentsBase` contract whenever one token in a multi-input order cannot be transferred out. This is a direct loss-of-funds / fund-lock condition reachable through the normal, authenticated ISMP settlement flow — no malicious relayer, prover, or admin required, only an order whose input asset set includes a token that is (or becomes) non-transferable to the relevant beneficiary.

### Likelihood Explanation
Multi-input orders are a core supported feature (`order.inputs` is an array, and `_withdraw` explicitly loops over `body.tokens`). Any user placing an order can choose which input tokens are included, and any of the well-documented weird-ERC20 behaviors (blacklists, pausability, zero-transfer reverts, proxy upgrades) apply. A user could intentionally include a token whose transfer to a solver-controlled or self address will fail (e.g., get their own address blacklisted on USDC before cancelling) to lock a solver's fill from ever being redeemed, or a solver could grief a user's refund the same way. No special privileges are needed to trigger it — just crafting/filling an order with a problematic token in `order.inputs`.

### Recommendation
In `_withdraw` (and the equivalent `withdraw` function in the Tron variant of `IntentGatewayV2.sol`), do not let one token's transfer failure abort the whole loop. Wrap each per-token transfer in a try/catch (or low-level call check) and, on failure, skip that asset while still releasing all other tokens and finalizing the order, leaving the failed asset's balance recorded for a later retry/manual sweep — mirroring the recommendation from the original AccountManager finding.

### Proof of Concept
1. Solver/user creates an order with `order.inputs = [tokenA, tokenB]` where `tokenB` is a blacklist-capable stablecoin (e.g. USDC-like).
2. User (as `order.user`/beneficiary of a refund) or solver (as beneficiary of a redeem) gets blacklisted on `tokenB`, or `tokenB` is paused for that specific beneficiary/pair.
3. Order fill/cancel proceeds normally; Hyperbridge delivers `RedeemEscrow`/`RefundEscrow` via `onAccept`, which calls `_withdraw`. [5](#0-4) 
4. The `IERC20(tokenB).safeTransfer(beneficiary, amount)` call reverts, reverting the entire `_withdraw`, which reverts the whole `onAccept` call.
5. `EvmHost.dispatchIncoming` catches this revert and deletes the request receipt to permit retry: [6](#0-5) 
6. Any subsequent retry of the same request hits the identical revert — `tokenA`'s escrow (which would have transferred fine) and `tokenB`'s escrow are both permanently stuck, with no path to release either.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;

                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
