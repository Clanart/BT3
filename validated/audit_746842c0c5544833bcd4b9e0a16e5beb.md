### Title
`protocol.file.allow=always` override during submodule update re-enables local-file submodule cloning bypassed by attacker `.gitmodules` - (File: app/src/lib/git/submodule.ts)

### Summary
`updateSubmodulesAfterOperation` in `app/src/lib/git/submodule.ts` accepts an `allowFileProtocol` flag that, when `true`, adds `-c protocol.file.allow=always` to the `git submodule update --init --recursive` invocation. This deliberately re-enables `file://` submodule URLs, a class of URL that upstream Git disabled by default specifically because a malicious repository's `.gitmodules` can point a submodule at an arbitrary local path (including via `../` traversal or absolute paths) and have Git clone/copy it into the working tree. `checkoutBranch` and `checkoutCommit` in `app/src/lib/git/checkout.ts` forward this flag straight through to the submodule update step, with no validation of the resulting submodule paths/URLs from the repo the user just cloned or fetched.

### Finding Description
The invariant that should hold is: content coming from an untrusted, attacker-controlled repository (`.gitmodules`) must never be able to instruct Desktop to read/copy files from arbitrary local filesystem paths outside the user's chosen working tree. Git's own `protocol.file.allow=user` default enforces this by refusing `file://` submodule URLs unless the top-level clone was itself invoked with `file://`. [1](#0-0) 

`updateSubmodulesAfterOperation` takes a boolean `allowFileProtocol` and, when set, unconditionally injects `-c protocol.file.allow=always` before `submodule update --init --recursive` — this disables Git's own protection for the entire submodule update, regardless of which submodule URLs are present in the (attacker-supplied) `.gitmodules` file of the checked-out branch/commit. [2](#0-1) [3](#0-2) 

`checkoutBranch` and `checkoutCommit` both propagate `allowFileProtocol` unchanged into `updateSubmodulesAfterOperation` after running `git checkout`, meaning that whichever `.gitmodules` content is present *after* checkout (i.e., attacker-controlled, since checkout switches to a branch/commit the attacker crafted) is what governs the submodule URLs resolved with the protection disabled.

The existing repo test fixture confirms this flag is exercised for exactly the "submodule wasn't initialized yet" scenario: [4](#0-3) 

This mirrors the report's broken-invariant pattern precisely: a safety check that exists to bound a value/scope (`mintCap` bounding mintable USX; Git's `protocol.file.allow=user` bounding submodule fetch to safe protocols) is bypassed through a secondary code path (`outboundTransferShares` cross-chain mint; `allowFileProtocol` submodule-update override) that is not re-validated against the same invariant before being applied to attacker-influenced state (`totalMint` on the receiving chain; the `.gitmodules` content of a just-checked-out, attacker-controlled ref).

### Impact Explanation
If `allowFileProtocol=true` is applied when initializing submodules for a branch/commit whose content is attacker-controlled (e.g., a cloned fork, a PR branch checked out via "Open PR in Desktop", or a branch fetched from an untrusted remote), a crafted `.gitmodules` with a `file://` URL pointing outside the repository (or using `../` traversal) can cause Git to clone/copy files from arbitrary locations on the victim's filesystem into the submodule's working directory inside the repo, where they become visible/committable. This is a confidentiality violation (reading files outside the intended repo boundary) and, depending on what's copied (e.g., SSH keys, credential files, another repo's `.git/hooks`), can escalate to credential exfiltration or code execution on subsequent operations.

### Likelihood Explanation
Exploitability depends on exactly which call sites in `app-store.ts` pass `allowFileProtocol=true` for checkouts originating from untrusted/attacker-supplied refs (e.g., PR checkouts, cross-fork branches) versus purely local/user-created branches. I could not fully confirm all such call sites before this session ended, so I cannot state with certainty whether this flag is reachable from a fully attacker-controlled trust boundary in the current build, or whether it's gated to trusted first-party repos only (e.g., the "already-cloned-locally" uninitialized submodule case shown in the test). This is the key open question a Devin agent with full repo access should resolve by tracing every `checkoutBranch`/`checkoutCommit` call with `allowFileProtocol=true` back to its trigger (PR checkout, branch-from-URL, etc.) in `app-store.ts` and `dispatcher.ts`.

### Recommendation
Before setting `allowFileProtocol=true`, validate that every submodule URL parsed from `.gitmodules` for the target ref stays within trusted protocols/paths, or restrict the override to repositories/refs that are provably first-party (never remote/PR/fork-originated). Alternatively, keep Git's default `protocol.file.allow=user` and instead special-case only the specific local relative paths Desktop itself needs (e.g., resolve `file://` submodule targets through the same `resolveWithin` guard already used elsewhere, such as in `app/src/lib/stores/app-store.ts` around the Copilot conflict-resolution file writes) before allowing the protocol override. [5](#0-4) 

### Proof of Concept
1. Attacker creates a repository with a branch containing a `.gitmodules` entry such as:
   `[submodule "x"] path = x url = file:///../../../../home/victim/.ssh`
2. Victim opens this repository/branch in Desktop through a flow that ends up calling `checkoutBranch`/`checkoutCommit` with `allowFileProtocol=true` (per `app/src/lib/git/checkout.ts` lines 102-146 and 163-207).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, bypassing Git's own protection and cloning the victim's `~/.ssh` directory (or other arbitrary local path) into the working tree at `x/`.
4. The victim's own file-listing/diff view in Desktop now shows the exfiltrated files as untracked content, which the victim could inadvertently commit and push, or which the attacker's crafted post-checkout hooks/scripts could read directly from disk.
