### Title
Coinbase outputs to Bitcoin multisig addresses are permanently skipped after maturity - (File: `processor/src/networks/bitcoin.rs`)

### Summary

`Bitcoin::get_outputs` assumes all spendable multisig outputs appear in non-coinbase transactions and iterates only over `block.txdata[1 ..]`. A coinbase output paying a registered multisig script is therefore never returned, even though `Scanner::scan_transaction` can recognize it and `Scanner::scan_block` explicitly supports scanning coinbase transactions. Once the containing block is marked scanned, the output is not reconsidered when it becomes mature. [1](#0-0) [2](#0-1) 

### Finding Description

The Bitcoin scanner registers all expected `ScriptBuf` values and `scan_transaction` returns a `ReceivedOutput` whenever a transaction output's `script_pubkey` matches one of them. [3](#0-2) 

The generic wallet-level `scan_block` scans every transaction in `block.txdata`, while warning that coinbase outputs require maturity handling before they are immediately spendable. [2](#0-1) 

The processor implementation instead discards the entire coinbase transaction unconditionally with `block.txdata[1 ..]`. [1](#0-0) 

The block scanner invokes `get_outputs` once for each newly confirmed block and only retains outputs returned by that call. [4](#0-3) 

When a block is acknowledged, `save_scanned_block` loads only the saved output list, marks those outputs as seen, and advances the persistent `scanned_block` height. [5](#0-4) 

Consequently, a coinbase payment to a registered external, branch, change, or forwarded address is absent when the block is scanned and remains absent after the normal Bitcoin coinbase maturity period. [6](#0-5) [5](#0-4) 

### Impact Explanation

Funds paid to a multisig-controlled Taproot output through a coinbase transaction remain consensus-spendable by the threshold key, but normal Serai operation never places the resulting `Output` into the scheduler's UTXO set. [7](#0-6) [8](#0-7) 

Because the block height is advanced without recording the coinbase output, maturity does not trigger another scan of `txdata[0]`, making the funds unavailable to subsequent payments, refunds, aggregation, rotation, and change handling. [5](#0-4) 

This creates an effective loss of deposited or donated Bitcoin under normal protocol operation, analogous to reward tokens being sent through a valid source that the accounting path never enumerates. [1](#0-0) 

### Likelihood Explanation

Any miner or mining pool can create a valid block whose coinbase pays one of Serai's publicly derivable multisig scripts, including the external, branch, change, or forwarded output scripts. [9](#0-8) [10](#0-9) 

The attacker does not need validator access, malformed encodings, collusion, or RPC compromise; the only required public input is a Bitcoin block containing the payment. [11](#0-10) [12](#0-11) 

The issue can also occur without malicious intent when a miner pays the vault directly as part of a pool payout, donation, fee arrangement, or withdrawal flow. [13](#0-12) 

### Recommendation

Do not permanently discard `block.txdata[0]` during output discovery. [14](#0-13) 

Scan the coinbase transaction and either:

- Queue matching outputs until they have at least 100 confirmations, then emit them as ordinary spendable `Output`s.
- Record matching coinbase outpoints in persistent scanner state and re-check them when their containing block height reaches `coinbase_height + 100`.
- Reject or separately classify coinbase outputs while still retaining enough state to activate them after maturity.

The implementation should not merely call `scan_block`, because that API explicitly reports coinbase outputs before they are immediately spendable. [13](#0-12) 

### Proof of Concept

1. Derive a Bitcoin multisig key and its external P2TR script using `p2tr_script_buf`. [15](#0-14) 

2. On regtest, mine a block whose coinbase transaction has a `TxOut` above the dust threshold paying that `script_pubkey`. [16](#0-15) 

3. Call `Scanner::scan_block` with the registered `Scanner`; the coinbase output is returned as a `ReceivedOutput`, demonstrating that the lower-level scanner recognizes it. [17](#0-16) 

4. Call `Bitcoin::get_outputs` with the same block and key; it returns an empty list because the loop begins at `txdata[1]`. [1](#0-0) 

5. Allow the scanner to process the block; no `ScannerEvent::Block` is emitted for the coinbase output, and `ram_scanned` advances to the block. [18](#0-17) [19](#0-18) 

6. Mine 100 additional blocks; the original block is never re-scanned because its height is already below `ram_scanned` and later below the persisted `scanned_block`. [20](#0-19) [5](#0-4)
