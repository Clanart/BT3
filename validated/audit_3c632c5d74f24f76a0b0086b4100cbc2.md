### Title
Missing replay/expiry protection in `AppProxyVerification` signature scheme allows indefinite replay of captured app-proxy requests - (File: `lib/shopify_app/controller_concerns/app_proxy_verification.rb`)

### Summary
`ShopifyApp::AppProxyVerification#query_string_valid?` validates only the cryptographic integrity of an app-proxy request's `signature` parameter against the shop's shared secret. It never checks the `timestamp` parameter (or any nonce) for freshness, so a signed app-proxy URL/query string, once captured, remains permanently valid and can be replayed by anyone at any time, exactly the same "signature schema without a nonce/expiry" root cause described in the external PPS-oracle report.

### Finding Description
`calculated_signature` builds the HMAC over the sorted set of query params (which includes `timestamp`), and `query_string_valid?` only performs a `secure_compare` between the computed and provided signature: [1](#0-0) 

The `timestamp` value is treated as just another signed field, not as an expiry/freshness check — there is no comparison against `Time.now`, no maximum age enforcement, and no nonce tracking anywhere in the module or its `included do ... before_action :verify_proxy_request ... end` hook: [2](#0-1) 

The test suite confirms this: a hardcoded `timestamp=1466106083` (year 2016) with its matching signature is asserted valid with no time-based rejection logic exercised anywhere: [3](#0-2) 

This is analogous to the reported `ECDSAPPSOracle` issue: a signature over a fixed set of parameters, without a nonce or expiry bound to the signer/domain, lets a previously valid signed message be reused indefinitely once observed by anyone other than the original signer/requester.

### Impact Explanation
Any controller mixing in `ShopifyApp::AppProxyVerification` (per the documented and generator-scaffolded pattern in `docs/shopify_app/engine.md` and `lib/generators/shopify_app/app_proxy_controller/templates/app_proxy_controller.rb`) accepts a captured request forever: [4](#0-3) 

App-proxy URLs are inherently exposed to storefront visitors' browsers (visible in the address bar, browser history, `Referer` headers sent to third-party resources loaded on the proxied page, shared social links, proxy/CDN/server access logs, etc.). Because the signature check has no expiry, anyone who ever observes one such fully-formed signed URL/query string can replay the exact same request an unlimited number of times, indefinitely, from any anonymous unrelated party — even after the acting user's session or intent is long gone. For any app-proxy endpoint that performs a state-changing action (e.g., submitting a review, redeeming a promotion, recording a vote, or any write-oriented proxy handler apps commonly build on this pattern per the docs' `ReviewsController` example), this enables unauthorized repeated/duplicated state changes triggered by an unrelated anonymous attacker, without needing the app's shared secret.

### Likelihood Explanation
High. No secrets or privileged access are required — the attacker only needs to observe one previously-issued, legitimately-signed app-proxy request (a routine occurrence given browser history, logs, and referrer leakage), and the vulnerable check accepts it forever since neither `timestamp` freshness nor a nonce is validated.

### Recommendation
In `query_string_valid?`, after confirming the HMAC matches, additionally reject requests whose `timestamp` is outside an acceptable window (e.g., `Time.now.to_i - timestamp.to_i` within a few minutes), and/or track consumed nonces/signatures to prevent reuse, mirroring the report's suggested fix of binding freshness (nonce) into the verified payload rather than trusting HMAC validity alone.

### Proof of Concept
1. Configure an app-proxy controller with `include ShopifyApp::AppProxyVerification` as documented.
2. Capture one legitimately Shopify-signed app-proxy request URL (e.g., from a storefront visitor's browser history, a shared link, or a proxy access log) containing `shop`, `path_prefix`, `timestamp`, and `signature` params.
3. At any later time — hours, days, or years after issuance — replay the exact same query string via a direct HTTP request to the app's proxy endpoint.
4. `query_string_valid?` recomputes the HMAC over the same params and it matches, so `verify_proxy_request` allows the request through with no age check, as shown by the test asserting validity for a `timestamp=1466106083` value with no rejection logic present: [3](#0-2) .

    def query_string_valid?(query_string)
      query_hash = Rack::Utils.parse_query(query_string)

      signature = query_hash.delete("signature")
      return false if signature.nil?

      ActiveSupport::SecurityUtils.secure_compare(
        calculated_signature(query_hash),
        signature,
      )
    end
