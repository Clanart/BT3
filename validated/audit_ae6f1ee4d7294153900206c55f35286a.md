### Title
`git clone` explicitly disables Git's built-in clone-time hook-write protection - ([File: app/src/lib/git/clone.ts])

### Summary
GitHub Desktop's `clone()` helper invokes `git clone --recursive` against an attacker-suppliable URL (from "Clone repository" dialog, "Open in Desktop" deep links, or CLI `--cli-clone`) while explicitly forcing `GIT_CLONE_PROTECTION_ACTIVE=false` in the child process environment. [1](#0-0) 

### Finding Description
`GIT_CLONE_PROTECTION_ACTIVE` is the environment variable Git added specifically to gate the fix for CVE-2024-32002 — a critical clone-time RCE where a maliciously-crafted repository (using nested/recursive submodules combined with case-insensitive or symlink-aware filesystem tricks) can cause Git to write a file into `.git/hooks/` (e.g. `post-checkout`) during a recursive clone. Because `--recursive` is unconditionally passed by Desktop's `clone()` and the protection variable is unconditionally forced to `'false'`, any protection that a locally-installed Git version would otherwise apply during this specific clone invocation is disabled for every clone Desktop performs: [2](#0-1) [3](#0-2) 

This mirrors the bug-class from the external report precisely: a multi-step protocol operation (clone → submodule init/checkout → hook execution) has an intermediate, security-relevant state ("has an untrusted hook been written to `.git/hooks` yet?") whose enforcement guard is deliberately bypassed by the caller (`GIT_CLONE_PROTECTION_ACTIVE=false`), just as the Bunni rebalance flow bypassed the intermediate consistency guard between `rebalanceOrderPreHook` and `rebalanceOrderPostHook`. The attacker in both cases is the untrusted counterparty (fulfiller contract / malicious remote repository) that is invoked mid-operation while the host's own safety invariant is not being enforced.

Notably, Desktop's own hook interception mechanism (`getRepoHooks` / `withHooksEnv` / `hooks-proxy.ts`) is careful to filter environment variables passed to hook subprocesses (only `GIT_`/`GITHEAD_` prefixed, explicitly excluding sensitive vars), showing the team is aware hooks are an attack surface for untrusted repository content: [4](#0-3) 
Yet that same care is not extended to the clone-time write protection that stops such a hook from being planted into `.git/hooks` in the first place.

### Impact Explanation
If a locally installed/bundled Git binary relies on `GIT_CLONE_PROTECTION_ACTIVE` being unset/true to enforce the CVE-2024-32002 mitigation, forcing it to `'false'` here removes that mitigation specifically for the clone path Desktop controls, on every clone (including ones triggered by a user simply pasting/clicking a URL or an "Open in Desktop" deep link). A successful exploitation results in a hook script from an attacker-controlled repository being written to `.git/hooks` and later executed as native code on the victim's machine — i.e., code execution outside of any git-object sandboxing, satisfying the "attacker controls a cloned/fetched repository … resulting in code execution" impact category.

### Likelihood Explanation
Likelihood depends on the exact Git version bundled via `dugite` and whether its protections are independently enforced regardless of this env var, which I could not fully verify from the indexed files (no `dugite`/git version pin was inspected). What is certain from the code is that Desktop actively opts out of this named protection unconditionally for every clone, removing a defense-in-depth layer that upstream Git ships specifically to stop malicious-repository clone-time RCE. Because triggering a clone requires nothing more than the victim entering/clicking an attacker-supplied clone URL (no local access, no prior compromise), the precondition for reaching this code path is trivial to satisfy for an unprivileged remote attacker.

### Recommendation
Remove the explicit `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `clone()` (or set it to `'true'`/leave unset) so that Git's built-in clone-time hook/path protections remain active, especially given `--recursive` is always passed and submodule content is inherently attacker-controlled. If the override exists to work around a compatibility issue, that workaround should be scoped/justified with a comment and ideally replaced with an equivalent protection Desktop enforces itself post-clone (e.g., scanning for unexpected files written under `.git/hooks` before any hook is ever allowed to execute).

### Proof of Concept
Not independently reproduced here (no terminal/filesystem access in this environment), but the mechanical steps to validate are:
1. Build a malicious Git repository per the public CVE-2024-32002 pattern (recursive submodule whose path collides with `.git/hooks` on a case-insensitive filesystem, or leverages a symlinked submodule path) that plants an executable `post-checkout` hook.
2. Host it and have GitHub Desktop clone it via the "Clone repository" dialog or an `x-github-client://openrepo/...` deep link, which invokes `clone()` in `app/src/lib/git/clone.ts`.
3. Observe whether the hook is written into `.git/hooks` and executes automatically upon the recursive submodule checkout, confirming the disabled protection is exploitable with the specific Git/dugite version Desktop ships. [5](#0-4)

export async function clone(
  url: string,
  path: string,
  options: CloneOptions,
  progressCallback?: (progress: ICloneProgress) => void
): Promise<void> {
  if (isClonePathSensitive(path)) {
    throw new Error(
      `The clone destination "${path}" targets a sensitive system location. ` +
        'Cloning into this directory is not allowed.'
    )
  }

  const env = {
    ...(await envForRemoteOperation(url)),
    GIT_CLONE_PROTECTION_ACTIVE: 'false',
  }

  const defaultBranch = options.defaultBranch ?? (await getDefaultBranch())

  const args = [
    '-c',
    `init.defaultBranch=${defaultBranch}`,
    'clone',
    '--recursive',
  ]

  let opts: IGitStringExecutionOptions = { env }

  if (progressCallback) {
    args.push('--progress')

    const title = `Cloning into ${path}`
    const kind = 'clone'

    opts = await executionOptionsWithProgress(
      { ...opts, trackLFSProgress: true },
      new CloneProgressParser(),
      progress => {
        const description =
          progress.kind === 'progress' ? progress.details.text : progress.text
        const value = progress.percent

        progressCallback({ kind, title, description, value })
      }
    )

    // Initial progress
    progressCallback({ kind, title, value: 0 })
  }

  if (options.branch) {
    args.push('-b', options.branch)
  }

  args.push('--', url, path)

  await git(args, __dirname, 'clone', opts)
}
