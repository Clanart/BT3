## Analog Identified: `EvmHost` resets `_latestStateMachineHeight` to a hardcoded `1` on veto instead of restoring the true previous height

### Title
Vetoing the latest state commitment on `EvmHost` collapses height tracking to `1` instead of the real previous height, reopening already-superseded heights for silent commitment overwrite - ([File: evm/src/core/EvmHost.sol])

### Summary
The bug report's core invariant is: *a value that gates fund-affecting logic (exchangeRate) is not correctly restored when a component transitions from a disabled state back to an enabled one — it snaps to a stale/incorrect baseline instead of the true prior value.* The Hyperbridge analog is `_latestStateMachineHeight`, the height watermark that gates whether an incoming consensus-verified state commitment is accepted as new. When a fisherman successfully vetoes the *latest* commitment for a state machine (the legitimate, permissionless fraud-proof path that "turns off" that height), `EvmHost` resets the watermark to a hardcoded `1` rather than to the real previous verified height, unlike the Substrate implementation of the identical operation.

### Finding Description
`deleteStateMachineCommitmentInternal` in `EvmHost.sol` handles a fisherman's veto of a state commitment: [1](#0-0) 

```solidity
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    ...
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
    }
    ...
}
```

Compare this to the Substrate pallet's equivalent handler for the exact same protocol operation, which correctly restores the watermark to the tracked *previous* height rather than an arbitrary constant: [2](#0-1) 

The Substrate side maintains a dedicated `PreviousStateMachineHeight` map precisely so a veto only rolls the watermark back to the last *actually verified* height: [3](#0-2) 

`EvmHost` has no such tracking — it always resets to `1`, discarding potentially thousands of already-verified, already-relied-upon heights of progress.

This watermark is the sole gate `HandlerV2.handleConsensus` uses to decide whether an intermediate state from a new consensus proof should be stored (i.e., trusted) as an update to a given height: [4](#0-3) 

```solidity
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    ...
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
```

Once the watermark is `1`, virtually any subsequent consensus message's intermediate states — for heights that were already finalized, already past their challenge period, and already relied upon by relayers/apps — satisfy `intermediate.height > 1` and get unconditionally written via `storeStateMachineCommitment`, which overwrites the existing state commitment and its update time in place: [5](#0-4) 

This silently swaps a previously-trusted, challenge-period-matured `StateCommitment` (overlay root used to verify request/response proofs) for a new one carried by whatever consensus proof next lands, with no re-validation that the replaced height was actually still "live" or that its replacement is consistent with history. The `MerkleMountainRange` proof check in `handlePostRequests`/`handleGetResponses` trusts `host.stateMachineCommitment(request.proof.height).overlayRoot` unconditionally: [6](#0-5) 

so a poisoned commitment at an old height becomes usable to accept requests/responses the protocol should never have trusted.

### Impact Explanation
This breaks the core Hyperbridge invariant that "state commitments must never let false remote state become trusted." The height watermark exists specifically to prevent old, already-superseded heights from being reconsidered. Resetting it to `1` on EVM (vs. correctly restoring to the previous height on Substrate) reopens the entire history below the true previous height for silent overwrite by any future consensus update, enabling false state acceptance and downstream unauthorized message/proof acceptance — directly matching the bounty's "false proof/state acceptance" and "transaction manipulation" categories.

### Likelihood Explanation
The veto (`freeze_client`/`deleteStateMachineCommitment`) path is a normal, permissionless, expected part of the protocol's byzantine-fault-tolerance design — any fisherman with a valid fraud proof can trigger it against a byzantine or even a legitimately disputed height; it is not a "malicious peer/relayer/admin" precondition. The resulting corruption is a pure code defect (wrong constant vs. tracked previous height) present on every `EvmHost` deployment, verified against the parallel, correctly-implemented Substrate logic in the same repository.

### Recommendation
Mirror the Substrate design: track a `_previousStateMachineHeight` mapping updated alongside `storeStateMachineCommitment`/`storeLatestCommitmentHeight`, and have `deleteStateMachineCommitmentInternal` restore `_latestStateMachineHeight[id]` to that tracked previous height instead of the hardcoded `1`.

### Proof of Concept
1. State machine `X` is honestly advanced to height `1000`; `_latestStateMachineHeight[X] = 1000`, with `_stateCommitments[X][1000]` set and its challenge period elapsed — requests/responses are actively being processed against it.
2. A fisherman submits a valid fraud proof against height `1000` (e.g., a genuine equivocation at that height). `deleteStateMachineCommitment` fires, and per `EvmHost.sol:719-721`, `_latestStateMachineHeight[X]` is set to `1` (not `999` or any real prior height).
3. The next consensus update for `X` (an ordinary, otherwise-honest `ConsensusMessage`) includes intermediate states for heights `500..1005` in its batch, as consensus clients typically resubmit rejected recent history.
4. `HandlerV2.handleConsensus` checks `intermediate.height > latestHeight` where `latestHeight == 1` — every height in `500..1005` passes and is written via `storeStateMachineCommitment`, overwriting `_stateCommitments[X][500..999]`, which were previously finalized, past their challenge period, and already used to validate delivered requests/responses.
5. Any inconsistency introduced in this re-derivation (or a subsequent proof crafted against the freshly reset watermark) can now poison a previously-matured, already-relied-upon height, letting `handlePostRequests`/`handleGetResponses` accept proofs against state the protocol should have permanently sealed.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}
