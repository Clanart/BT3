### Title
Partial-commit patch generation ignores the "hide whitespace" diff mode, causing the wrong lines to be staged/committed - ([File: app/src/lib/git/apply.ts])

### Summary
This is the closest Desktop analog to the FrankenDAO bug: a value (there, "token voting power"; here, "line index / hunk structure of a diff") is computed once under one set of mutable settings and then independently recomputed later under a different value of that setting, and the two computations are combined as if they were consistent. In `Staking.sol`, `getTokenVotingPower()` was recomputed with the live `monsterMultiplier`/`baseVotes` instead of reusing the value captured at `stake()` time. In GitHub Desktop, `WorkingDirectoryFileChange.selection` (the set of line indices the user checked/unchecked in the diff view) is computed against a diff that may have been generated with `hideWhitespaceInDiff: true`, but when the patch is actually built for staging, the diff is regenerated with the default (`hideWhitespaceInDiff: false`), producing different hunks/line numbering. The stale selection indices are then applied against the new hunk layout.

### Finding Description
When a file is selected in the Changes view, Desktop loads its diff and honors the user's "hide whitespace" preference: [1](#0-0) 
The resulting `diff.hunks` (with different line offsets/hunk boundaries because `-w` was passed to `git diff`) is what the user visually interacts with, and `file.selection` records line-selection state keyed by `absoluteIndex = hunk.unifiedDiffStart + lineIndex` computed against *that* diff: [2](#0-1) 

When the user actually commits (a partial/hunk-level stage), `stageFiles()` routes files with partial selections to `applyPatchToIndex()`: [3](#0-2) 

But `applyPatchToIndex()` calls `getWorkingDirectoryDiff(repository, file)` **without** forwarding `hideWhitespaceInDiff`, so it silently defaults to `false`: [4](#0-3) [5](#0-4) 

The freshly-fetched diff (without `-w`) is then handed to `formatPatch(file, diff)`, which walks `diff.hunks` and tests `file.selection.isSelected(absoluteIndex)` using indices that were computed against the *whitespace-hidden* diff: [6](#0-5) 

Because hiding whitespace changes hunk boundaries, line counts, and can merge/split hunks compared to the non-`-w` diff, the same `absoluteIndex` values refer to different lines in the two diffs. This is structurally identical to the FrankenDAO bug: a derived/cached value (`selection` indices, analogous to `stakedVotingPower`) computed under one configuration (`monsterMultiplier=50` / `hideWhitespaceInDiff=true`) is reused unmodified against a recomputation performed under a different configuration (`monsterMultiplier=60` / `hideWhitespaceInDiff=false`), with no invariant enforcing that the two are consistent.

### Impact Explanation
The practical effect is silent corruption of what the user commits: lines the user believed they deselected (and expected to remain unstaged/uncommitted) can end up included in the patch applied via `git apply --cached`, and vice versa — lines the user selected can be dropped or the wrong hunk lines can be toggled between add/delete/context. Since `git apply` on a malformed/mismatched hunk can also outright fail or misapply context, this can additionally break partial commits. This falls squarely under "silent corruption of what the user commits or pushes," matching the requested impact category for this analog.

### Likelihood Explanation
The "hide whitespace" toggle is a first-class, easily discoverable UI preference exposed in the diff view (referenced throughout `app/src/ui/changes/changes.tsx`, `app/src/ui/diff/*`, and threaded as `this.hideWhitespaceInChangesDiff` in `app-store.ts`), so any user who enables it and then makes a partial (line/hunk-level) commit on a file containing both whitespace-only and substantive changes in the same region will trigger the mismatch deterministically — no special repository content is required, though a repository/file crafted with interleaved whitespace-only and real edits in the same hunk (an attacker-controlled cloned/fetched repo) maximizes the chance that the hunk boundaries diverge enough to flip a real line's inclusion state, making it a viable vector for causing a victim to unknowingly commit/push unintended content.

### Recommendation
Thread the same `hideWhitespaceInDiff` value used to build the displayed diff/selection all the way through to the diff regenerated for patch construction, i.e. have `applyPatchToIndex()` accept and pass `hideWhitespaceInDiff` to `getWorkingDirectoryDiff()`, or — better, mirroring the FrankenDAO fix's approach of caching the originally-used value — persist/reuse the exact diff object (and its hunk layout) that produced the user's selection instead of recomputing it with a different flag value at commit time.

### Proof of Concept
1. Enable "Hide whitespace changes" in the diff view for a file that has both a whitespace-only edit and a substantive edit inside the same hunk region.
2. Select only the substantive line for inclusion in the commit, leaving the whitespace-only line deselected, using the whitespace-hidden diff's line indices.
3. Commit. `stageFiles` → `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) recomputes the diff with `hideWhitespaceInDiff` defaulted to `false`, shifting hunk/line boundaries.
4. `formatPatch` (`app/src/lib/patch-formatter.ts:143-157`) applies the stale `absoluteIndex`-based selection against the new hunk layout, so the line ultimately staged/committed does not correspond to what the user selected in the UI — either committing the whitespace-only change unintentionally, dropping the intended change, or misapplying the patch.
