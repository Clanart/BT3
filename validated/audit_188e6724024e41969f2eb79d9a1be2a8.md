### Title
Flat top-tier multiplier applied to entire `_amountToConvert` in `_lock=false` path allows over-issuance of unclaimed MGP rewards - (File: wombat/ArbWomUp3.sol)

### Summary
`getRewardAmount()` computes rewards differently depending on the `_lock` flag: the `_lock==true` branch walks reward tiers incrementally so only the portion of `accumulated` balance within each tier band earns that tier's multiplier, while the `_lock==false` branch multiplies the *entire* `_amountToConvert` by a single flat multiplier corresponding to the caller's current tier. An attacker can cheaply reach the top tier with a small `mWomSV` lock and then convert a large `_amountToConvert` through the `_lock==false` path (`_mode == 1`), earning the top multiplier on the whole amount instead of the correct tiered/blended rate.

### Finding Description
In `incentiveDeposit()`, the `_lock` argument passed into `getRewardAmount` is `_mode == 2` [1](#0-0) . Calling with `_mode == 1` routes execution to the flat-rate branch:

```solidity
if (!_lock) {
    mgpReward = _amountToConvert * rewardMultiplier[getUserTier(_account)] / DENOMINATOR;
}
``` [2](#0-1) 

`getUserTier` is derived solely from the attacker's current `mWomSV.getUserTotalLocked(_account)` balance [3](#0-2) , which the attacker fully controls and can inflate cheaply by first performing a small `_mode == 2` deposit (which locks converted `mWom` into `mWomSV` via `_deposit`) [4](#0-3) , reaching the top `rewardTier` threshold. On the subsequent `_mode == 1` call with a much larger `_amountToConvert`, the entire amount is multiplied by the top-tier `rewardMultiplier`, whereas the `_lock==true` branch would only apply the top multiplier to the portion of `accumulated` above the top tier boundary, applying lower multipliers to the lower bands [5](#0-4) . No modifier, tier-band check, or double-counting protection exists for the `_lock==false` path (`calDoubledCounted` is only subtracted in the `_lock==true` branch) [6](#0-5) . The only limiting factor is the contract's own `mgp` balance cap [7](#0-6) , which does not prevent an individual attacker from draining a disproportionate share of the finite reward pool relative to their true tiered entitlement.

### Impact Explanation
This results in theft of unclaimed MGP emissions from the shared reward pool: an attacker receives significantly more `vlMGP` than the tiered incentive structure intends, at the expense of other legitimate participants and program economics, up to the full remaining `mgp` balance held by the contract. This matches the Immunefi "theft of unclaimed yield" impact class.

### Likelihood Explanation
Exploitation only requires ordinary WOM tokens (attacker's own capital) and two transactions: a small `_mode == 2` deposit to reach the top tier, then a `_mode == 1` deposit with a large `_amountToConvert`. No special privileges, oracle manipulation, or governance access are needed, and the exploit is repeatable until the contract's `mgp` balance is exhausted.

### Recommendation
Make the `_lock==false` branch use the same tiered/incremental accounting as the `_lock==true` branch (optionally without the `calDoubledCounted` adjustment, or with an equivalent adjustment based on the account's pre-existing tier-relevant balance), so that the flat multiplier is never applied to amounts spanning multiple tier bands.

### Proof of Concept
Foundry test plan:
1. Deploy `ArbWomUp3` with `setMultiplier` configuring tiers e.g. `rewardTier = [0, 1000e18, 10000e18]`, `rewardMultiplier = [100, 200, 500]` (basis points scale).
2. Fund the contract with a large `mgp` balance so the cap in `getRewardAmount` does not mask the bug.
3. Attacker calls `incentiveDeposit(smallAmount, ratio, false, 2)` sized so post-lock `mWomSV.getUserTotalLocked(attacker) >= rewardTier[2]` (top tier).
4. Attacker calls `incentiveDeposit(hugeAmount, ratio, false, 1)`.
5. Assert `vlMGP` amount locked for attacker via the `_mode==1` call equals `hugeAmount * rewardMultiplier[2] / DENOMINATOR`.
6. Compute the "correct" tiered reward for the same `hugeAmount` by simulating the `_lock==true` incremental walk starting from the attacker's pre-existing `mWomSV` balance, and assert the flat-rate reward from step 5 strictly exceeds this tiered value, demonstrating over-issuance.
