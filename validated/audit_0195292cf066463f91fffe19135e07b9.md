### Title
Improper Authentication via Signature Wrapping in the `VALIDATE_SENDER` Precompile - ([File: blockchain/vm/contracts.go])

### Summary
The `VALIDATE_SENDER` precompiled contract (`validateSender.Run` / `validateSender.validateSender`) lets any contract or transaction sender check whether a set of raw ECDSA signatures, over an attacker-supplied 32-byte "message," recover to the public keys registered under a given `from` address's `AccountKey`. Because the precompile does not bind the signed message to any Kaia-specific domain, purpose, nonce, or transaction context, a signature that is valid and was produced for a completely different purpose can be "wrapped" into a call to this precompile and accepted as proof that the address authorized *this* action — the same class of confusion exploited in the OpenSAML XML Signature wrapping bug (CVE-2011-1411), where a signature valid for one part of a message was accepted as authenticating another part/context.

### Finding Description
`validateSender.validateSender` parses the input as `from (20 bytes) || msg (32 bytes) || sigs (65*n bytes)`, `ecrecover`s each signature against the raw 32-byte `msg`, and then calls `accountkey.ValidateAccountKey` with a hard-coded `accountkey.RoleTransaction` role: [1](#0-0) 

`ValidateAccountKey` simply delegates to `AccountKey.Validate`, which — for `AccountKeyWeightedMultiSig`/`AccountKeyPublic`/role-based keys — only checks that the recovered public keys match members of the account's registered key set and meet a weight threshold; it has no concept of *what* the message represents: [2](#0-1) [3](#0-2) 

Unlike normal Kaia transaction signing, where the signed hash is derived deterministically from the full transaction contents via `SigHash`/`FeePayerSigHash` (binding type, nonce, gas price, recipient, amount, payload, chain ID, etc. — see e.g. `SenderTxHash`/`SigHash` implementations for fee-delegated tx types): [4](#0-3) 

the `VALIDATE_SENDER` precompile accepts an arbitrary caller-chosen 32-byte value as the "message." Any 32-byte value that an account owner has ever signed for *any* purpose — a signature over an unrelated protocol message, a hash that happens to coincide with some other artifact — can be replayed through this precompile by an unrelated third party to prove "ownership" of `from` inside whatever smart contract logic relies on `VALIDATE_SENDER` for authorization (e.g., gasless/meta-transaction relaying, custom account-abstraction/permission contracts, auction bid authorization schemes built on top of this precompile). There is no EIP-712-style domain separator, no expiry, no binding to `msg.sender`/contract address/calldata, and no nonce — exactly the missing "context binding" that makes XML Signature wrapping attacks possible in OpenSAML: a syntactically valid signature is accepted outside the context it was actually created for.

### Impact Explanation
Any smart contract built on Kaia that uses `VALIDATE_SENDER` as an authentication/authorization primitive (a documented, public precompile at a fixed address, intended for general dApp use per Kaia's precompile docs) is exposed to cross-context signature replay: an attacker who obtains any valid signature from a victim over a 32-byte value (from an unrelated dApp, a previous unrelated authorization, etc.) can present it to `VALIDATE_SENDER` to be treated as if the victim authorized an unrelated action. Depending on how a given contract uses the "authenticated" `from` address (e.g., gasless transaction execution, permission grants, fund transfers gated by this check), this can lead to unauthorized actions being executed on behalf of the victim's account — i.e., unauthorized value movement / privilege confusion, matching CWE-287.

### Likelihood Explanation
Reachable by any unprivileged caller through a normal EVM `CALL`/`STATICCALL` to the precompile address — no special privileges, node access, or consensus role are required. The likelihood that a *given* deployed contract using this precompile is exploitable depends on whether that contract also adds its own domain binding (many naive implementations, including simple "verify this address signed this message" patterns common in gasless/permit-style contracts, would not). The precompile itself provides no such protection, pushing the burden entirely onto downstream contract authors, which is the systemic weakness being reported.

### Recommendation
- Require the signed message passed to `VALIDATE_SENDER` to be a domain-separated hash (e.g., including the calling contract address, chain ID, a purpose tag, and a nonce) rather than an arbitrary caller-supplied 32 bytes, or
- Document and enforce that `VALIDATE_SENDER` must never be treated as a general authentication primitive without additional context binding by the caller contract, and provide a variant/helper that mandates EIP-712-style structured, domain-bound signing.
- At minimum, add a domain/purpose prefix inside the precompile itself (analogous to `personal_sign`'s `"\x19Kaia Signed Message:\n"` prefix or EIP-191) so signatures produced for this precompile cannot be confused with signatures produced for any other purpose.

### Proof of Concept
1. Victim account `V` has an `AccountKeyPublic`/`AccountKeyWeightedMultiSig` registered on-chain.
2. `V` signs an arbitrary 32-byte hash `H` for some unrelated purpose (e.g., an off-chain message, a signature required by another dApp, or a hash that happens to match a value used elsewhere).
3. Attacker deploys/uses a contract `C` that calls the `VALIDATE_SENDER` precompile with `input = V || H || sig` to "authenticate" `V` for some privileged action in `C` (e.g., authorize a gasless transfer on `V`'s behalf).
4. `validateSender.validateSender` recovers the public key from `sig` over `H`, finds it matches `V`'s registered key via `accountkey.ValidateAccountKey(..., RoleTransaction, ...)`, and returns success — even though `V` never intended `sig`/`H` to authorize anything in contract `C`. [5](#0-4) 

**Note:** I was unable to find any actual downstream contract/module within this indexed repo that consumes `VALIDATE_SENDER` for privileged fund movement (e.g., in the gasless or auction modules) — reachability to concrete "unauthorized value movement" therefore depends on external/future contracts built on top of this precompile, which is inherent to it being a general-purpose public primitive. If a Devin session with full repo/file access is available, it would be worth verifying whether any in-repo system contracts or the gasless/auction modules already call `VALIDATE_SENDER`, which would elevate this from a design-weakness finding to a directly exploitable one.

func (c *validateSender) validateSender(input []byte, picker types.AccountKeyPicker, currentBlockNumber uint64) error {
	ptr := input

	// Parse the first 20 bytes. They represent an address to be verified.
	if len(ptr) < common.AddressLength {
		return errInputTooShort
	}
	from := common.BytesToAddress(input[0:common.AddressLength])
	ptr = ptr[common.AddressLength:]

	// Parse the next 32 bytes. They represent a message which was used to generate signatures.
	if len(ptr) < common.HashLength {
		return errInputTooShort
	}
	msg := ptr[0:common.HashLength]
	ptr = ptr[common.HashLength:]

	// Parse remaining bytes. The length should be divided by common.SignatureLength.
	if len(ptr)%common.SignatureLength != 0 {
		return errWrongSignatureLength
	}

	numSigs := len(ptr) / common.SignatureLength
	if numSigs == 0 {
		return errNoSignatures
	}
	pubs := make([]*ecdsa.PublicKey, numSigs)
	for i := range numSigs {
		p, err := crypto.Ecrecover(msg, ptr[0:common.SignatureLength])
		if err != nil {
			return err
		}
		pubs[i], err = crypto.UnmarshalPubkey(p)
		if err != nil {
			return err
		}
		ptr = ptr[common.SignatureLength:]
	}

	k := picker.GetKey(from)
	if err := accountkey.ValidateAccountKey(currentBlockNumber, from, k, pubs, accountkey.RoleTransaction); err != nil {
		return err
	}

	return nil

func (a *AccountKeyWeightedMultiSig) Validate(currentBlockNumber uint64, r RoleType, recoveredKeys []*ecdsa.PublicKey, from common.Address) bool {
	if a.Threshold == 0 {
		return false
	}
	isIstanbul := fork.Rules(new(big.Int).SetUint64(currentBlockNumber)).IsIstanbul

	// Validation 1. if isIstanbul is true, check whether the signature number exceeds key number
	if isIstanbul && len(recoveredKeys) > len(a.Keys) {
		logger.Debug("AccountKeyWeightedMultiSig validation failed and number of signatures exceeds key number",
			"numSigs", len(recoveredKeys), "numKeys", len(a.Keys))
		return false
	}

	numberOfValidAndUniqueSigs := 0
	weightedSum := uint(0)

	// To prohibit making a signature with the same key, make a map.
	// TODO-Kaia: find another way for better performance
	pMap := make(map[string]*ecdsa.PublicKey)
	for _, bk := range recoveredKeys {
		b, err := rlp.EncodeToBytes((*PublicKeySerializable)(bk))
		if err != nil {
			logger.Warn("Failed to encode recovered public keys of the tx", "recoveredKeys", recoveredKeys)
			continue
		}
		pMap[string(b)] = bk
	}

	for _, k := range a.Keys {
		b, err := rlp.EncodeToBytes(k.Key)
		if err != nil {
			logger.Warn("Failed to encode public keys in the account", "AccountKey", a.String())
			continue
		}

		// if the registered key is included in one of the transaction signatures,
		// update weightedSum and validSigNum
		if _, ok := pMap[string(b)]; ok {
			weightedSum += k.Weight
			numberOfValidAndUniqueSigs++
		}
	}

	// Validation 2. if isIstanbul is true, check whether invalid signature exists
	if isIstanbul && numberOfValidAndUniqueSigs < len(pMap) {
		logger.Debug("AccountKeyWeightedMultiSig validation failed and invalid signature exists",
			"numberOfValidSigs", numberOfValidAndUniqueSigs, "numberOfUniqueSigs", len(pMap))
		return false
	}

	// Validation 3. check whether enough signatures are gathered
	if weightedSum < a.Threshold {
		logger.Debug("AccountKeyWeightedMultiSig validation failed and weightedSum is smaller than threshold",
			"recoveredKeys", recoveredKeys, "accountKeys", a.String(), "threshold", a.Threshold, "weighted sum", weightedSum)
		return false
	}

	return true
}

func (t *TxInternalDataFeeDelegatedSmartContractExecution) SenderTxHash() common.Hash {
	hw := sha3.NewKeccak256()
	rlp.Encode(hw, t.Type())
	rlp.Encode(hw, []interface{}{
		t.AccountNonce,
		t.Price,
		t.GasLimit,
		t.Recipient,
		t.Amount,
		t.From,
		t.Payload,
		t.TxSignatures,
	})

	h := common.Hash{}

	hw.Sum(h[:0])

	return h
}
