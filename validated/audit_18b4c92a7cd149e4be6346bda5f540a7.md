### Title
Unauthenticated DKG share reuse can expose another participant's encrypted share - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
`KeyMachine::calculate_share` decrypts each submitted `EncryptedMessage` and can return an `EncryptionKeyProof` before the message's Schnorr proof-of-possession has actually been verified. A malicious DKG participant can copy the per-message encryption key from another participant's encrypted share, submit malformed ciphertext with an invalid PoP, and cause the victim to publish the ECDH shared key for the copied key. [1](#0-0) 

### Finding Description
`EncryptedMessage` is explicitly designed to prevent this attack: an attacker who reuses Alice's message key would otherwise induce Bob to reveal `bX`, thereby revealing Alice's encrypted share to Bob. [2](#0-1) 

However, `Encryption::decrypt` only queues `msg.pop` for batch verification, then immediately calculates `key = enc_key * msg.key`, decrypts the ciphertext, and returns an `EncryptionKeyProof` containing that ECDH key. [3](#0-2) 

The caller then attempts `C::F::from_repr` on the decrypted bytes and immediately returns `InvalidShare { blame: Some(blame) }` if they are non-canonical, without first calling the batch verifier that would reject the invalid PoP. [4](#0-3) 

Since `PedPoPError::InvalidShare` publicly carries `Option<EncryptionKeyProof<C>>`, this early error exposes the ECDH shared key even though the submitted PoP is invalid. [5](#0-4) 

Once exposed, `EncryptionKeyProof.key` is sufficient to derive the ChaCha20 keystream and decrypt the original `EncryptedMessage` that used the copied message key. [6](#0-5) [7](#0-6) 

### Impact Explanation
An unauthorized DKG participant can recover another participant's encrypted contribution to a victim's secret share by forcing disclosure of its ECDH key. The leaked value is not merely a validity signal: it directly decrypts the previously observed `EncryptedMessage`, exposing a DKG secret share that the protocol explicitly treats as confidential and blame-safe. [8](#0-7) 

### Likelihood Explanation
The attacker only needs to observe an encrypted share's public message key and submit attacker-controlled share bytes through `EncryptedMessage::read` / `calculate_share`; no private key or valid PoP is required. [9](#0-8) [10](#0-9) 

For curves whose scalar representation is wider than the scalar modulus, uniformly malformed decrypted bytes have a high probability of failing `from_repr`; for Ristretto/Ed25519-style 32-byte scalars, this is approximately 15/16. If the bytes happen to be canonical, the invalid PoP is found first during later batch blame, so no key is published. [11](#0-10) [12](#0-11) 

### Recommendation
Do not derive or disclose an `EncryptionKeyProof` before authenticating the message key's PoP. Either synchronously call `msg.pop.verify` before `ecdh`/`cipher` inside `Encryption::decrypt`, or defer scalar parsing, share accumulation, and all blame-proof generation until the queued PoP statements have been verified. The safer fix is to reject invalid PoPs before decryption, matching the later `decrypt_with_proof` order. [13](#0-12) 

### Proof of Concept
```text
1. Alice sends Bob EncryptedMessage { key: X, pop: valid_pop, msg: ct }.
2. Mallory observes X and submits to Bob:
     key = X
     pop = arbitrary structurally valid SchnorrSignature
     msg = arbitrary ciphertext bytes
3. Bob's KeyMachine::calculate_share calls Encryption::decrypt.
4. Bob queues Mallory's invalid PoP, but still computes:
     key = bob_enc_key * X
   and decrypts Mallory's ciphertext.
5. If the decrypted scalar representation is non-canonical,
   calculate_share immediately returns:
     InvalidShare { participant: Mallory, blame: Some(EncryptionKeyProof { key, ... }) }
6. Mallory obtains the blame proof and uses `key` to derive the same
   ChaCha20 keystream protecting Alice's original `ct`.
7. Mallory decrypts Alice's share to Bob.
```

This reaches the vulnerable path solely through untrusted `EncryptedMessage` bytes supplied to `calculate_share`; the copied `key`, arbitrary `pop`, and arbitrary `msg` are all read directly from the serialized message. [14](#0-13) [15](#0-14)

  pub fn calculate_share<R: RngCore + CryptoRng>(
    mut self,
    rng: &mut R,
    mut shares: HashMap<Participant, EncryptedMessage<C, SecretShare<C::F>>>,
  ) -> Result<BlameMachine<C>, PedPoPError<C>> {
    validate_map(
      &shares,
      &self.params.all_participant_indexes().collect::<Vec<_>>(),
      self.params.i(),
    )?;

    let mut batch = BatchVerifier::new(shares.len());
    let mut blames = HashMap::new();
    for (l, share_bytes) in shares.drain() {
      let (mut share_bytes, blame) =
        self.encryption.decrypt(rng, &mut batch, BatchId::Decryption(l), l, share_bytes);
      let share =
        Zeroizing::new(Option::<C::F>::from(C::F::from_repr(share_bytes.0)).ok_or_else(|| {
          PedPoPError::InvalidShare { participant: l, blame: Some(blame.clone()) }
        })?);
      share_bytes.zeroize();
      *self.secret += share.deref();

      blames.insert(l, blame);
      batch.queue(
        rng,
        BatchId::Share(l),
        share_verification_statements::<C>(self.params.i(), &self.commitments[&l], share),
      );
    }
    batch.verify_with_vartime_blame().map_err(|id| {
      let (l, blame) = match id {
        BatchId::Decryption(l) => (l, None),
        BatchId::Share(l) => (l, Some(blames.remove(&l).unwrap())),
      };
      PedPoPError::InvalidShare { participant: l, blame }
    })?;

/// An encrypted message, with a per-message encryption key enabling revealing specific messages
/// without side effects.
#[derive(Clone, Zeroize)]
pub struct EncryptedMessage<C: Ciphersuite, E: Encryptable> {
  key: C::G,
  // Also include a proof-of-possession for the key.
  // If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X,
  // then send Bob a message also claiming to use X.
  // While Eve's message would fail to meaningfully decrypt, Bob would then use this to create a
  // blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob.
  // This is a massive side effect which could break some protocols, in the worst case.
  // While Eve can still reuse their own keys, causing Bob to leak all messages by revealing for
  // any single one, that's effectively Eve revealing themselves, and not considered relevant.

  // TODO: https://github.com/serai-dex/serai/issues/151
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"encryption_key");

  let mut ecdh = ecdh.to_bytes();
  transcript.append_message(b"shared_key", ecdh.as_ref());
  ecdh.as_mut().zeroize();

  let zeroize = |buf: &mut [u8]| buf.zeroize();

  let mut key = Cc20Key::default();
  let mut challenge = transcript.challenge(b"key");
  key.copy_from_slice(&challenge[.. 32]);
  zeroize(challenge.as_mut());

  // Since the key is single-use, it doesn't matter what we use for the IV
  // The issue is key + IV reuse. If we never reuse the key, we can't have the opportunity to
  // reuse a nonce

  let mut iv = Cc20Iv::default();
  // The \0 is to satisfy the length requirement (12), not to be null terminated
  iv.copy_from_slice(b"DKG IV v0.2\0");

  // ChaCha20 has the same commentary as the transcript regarding ZAlloc
  // TODO: https://github.com/serai-dex/serai/issues/151
  let res = ChaCha20::new(&key, &iv);
