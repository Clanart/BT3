### Title
Incorrect RLock usage in `GaslessModule.PreAddTx` allows concurrent map mutation of `knownTxs`, causing crash/state corruption reachable from ordinary transaction submission - ([File: kaiax/gasless/impl/tx_pool.go])

### Summary
`GaslessModule.PreAddTx` takes a **read lock** (`g.knownTxsMu.RLock()`) but then calls `g.knownTxs.add(tx, TxStatusQueue)`, which **mutates** the underlying `knownTxs` map (a plain Go `map[common.Hash]*knownTx`, not concurrency-safe). [1](#0-0) 

This mirrors the bug class in the reported Linux/Xen CVE: a resource is exposed/"published" for concurrent access (there, `fd_install()`; here, holding only a shared `RLock` while writing) before/without the exclusive guarantee that the mutation actually requires, opening a window where another concurrent holder of the same "read" lock can observe or further mutate the structure mid-update, corrupting it or crashing the process (Go's runtime fatally panics on concurrent map read/write, `fatal error: concurrent map writes`).

### Finding Description
`knownTxs` is a bare `map[common.Hash]*knownTx` with mutating methods `add`, `addKnownTx`, and `delete` (all non-atomic map writes) guarded only nominally by `GaslessModule.knownTxsMu sync.RWMutex`. [2](#0-1) [3](#0-2) 

Every other write path in the module correctly acquires the **exclusive** lock before mutating the map: `IsReady` (`Lock`), `PreReset` (`Lock`), `PostReset` (`Lock`). [4](#0-3) [5](#0-4) [6](#0-5) 

`PreAddTx`, invoked on every single transaction submitted to the node's mempool (both `AddLocal`/`AddRemote` and batch `AddRemotes`) via the generic `TxPool.add()` module hook, is the odd one out: it takes only `RLock()` yet performs a write (`g.knownTxs.add(...)`, plus `numQueue()` iterating the map) inside that "read" critical section. [7](#0-6) 

Because `sync.RWMutex.RLock()` permits **multiple concurrent holders**, any two transactions that are gasless bundle txs and get processed close together — or a `PreAddTx` write racing with a legitimate concurrent read section elsewhere that also happens to take `RLock` — can run `k[tx.Hash()] = &knownTx{...}` (map write) at the same time as another goroutine iterates/reads the same map, which is undefined behavior for Go maps and typically manifests as a fatal, unrecoverable process crash (`fatal error: concurrent map read and map write` or `concurrent map writes`), or silently corrupted map state (lost/duplicate entries) feeding into `IsReady`'s admission/promotion accounting.

### Impact Explanation
This is reachable by any unprivileged party submitting ordinary transactions to a public RPC endpoint — no privileged role is required. The proximate effects are:
- **Node crash / denial of availability** of the mempool-serving process on any node running the gasless module, triggered purely by transaction submission timing, not by any protocol-level malicious payload.
- **State corruption** of the `knownTxs` bookkeeping map, which governs gasless queue/pending admission limits (`GetMaxBundleTxsInQueue`, `numQueue`), potentially allowing bypass of the intended gasless-tx admission caps (`ErrBundleTxQueueFull`) or double counting, affecting gasless settlement queueing behavior described in KIP-247. [8](#0-7) 

Given this affects the gasless transaction pool's admission-control bookkeeping and node stability, and is reachable without any special privilege, the severity is assessed as Medium-High depending on how reliably the race can be triggered under real transaction load; the exact concurrency window (whether `pool.mu` around `TxPool.add()` fully serializes calls into `PreAddTx`) could not be fully confirmed from static review alone.

### Likelihood Explanation
`PreAddTx` runs on every transaction add path (`AddLocal`, `AddRemote`, `AddRemotes`) for **every** transaction, not just gasless ones (the read of `g.knownTxs.get` happens unconditionally, and the map write happens whenever `IsBundleTx` is true). Kaia is a high-throughput chain with public RPC nodes constantly receiving concurrent submissions from many senders, so any concurrency gap between `PreAddTx` and other lock users, or between two goroutines both entering `RLock()`, is exercised continuously in production, making this a **live, easily-triggered** race rather than a theoretical one.

### Recommendation
Change `PreAddTx` to take the exclusive lock (`g.knownTxsMu.Lock()` / `defer g.knownTxsMu.Unlock()`) whenever it may write to `g.knownTxs`, matching the pattern already used correctly in `IsReady`, `PreReset`, and `PostReset`. Alternatively, split the function into a read-only check phase (using `RLock`) and a separate write phase (using `Lock`), ensuring no write ever occurs while only a read lock is held. Add a `go test -race` regression test that concurrently calls `PreAddTx` alongside `IsReady`/`PreReset`/`PostReset` to catch this class of bug.

### Proof of Concept
1. Start a node with the gasless module enabled.
2. From two or more RPC clients, concurrently submit distinct valid gasless bundle transactions (`GaslessApproveTx`/`GaslessSwapTx`) such that `IsBundleTx(tx)` is true for each, ensuring their `PreAddTx` calls can overlap in time (e.g., via `AddRemotes` batch calls from multiple goroutines, or concurrent `AddLocal`/`AddRemote` RPC calls hitting the mempool at the same moment as internal reset/promotion cycles).
3. Run the node binary built/tested with `-race`, or under sustained load; observe `fatal error: concurrent map writes` (or `concurrent map read and map write`) crashing the process, or observe `knownTxs` bookkeeping (`numQueue()`/`numExecutable()`) diverge from the true pool state across nodes, causing state/admission divergence between honest nodes running the same gasless workload.

```go
func (g *GaslessModule) PreAddTx(tx *types.Transaction, local bool) error {
	g.knownTxsMu.RLock()
	defer g.knownTxsMu.RUnlock()

	if knownTx, ok := g.knownTxs.get(tx.Hash()); ok && knownTx.elapsedPromotedOrAddedTime() < KnownTxTimeout {
		return ErrUnableToAddKnownBundleTx
	}

	if g.IsBundleTx(tx) {
		if uint(g.knownTxs.numQueue()) >= g.GetMaxBundleTxsInQueue() {
			return ErrBundleTxQueueFull
		}
		g.knownTxs.add(tx, TxStatusQueue)
	}
	return nil
}
```

```go
type knownTxs map[common.Hash]*knownTx

func (k knownTxs) add(tx *types.Transaction, status int) {
	if tx == nil {
		return
	}

	if ktx, ok := k.get(tx.Hash()); ok {
		ktx.status = status
	} else {
		k[tx.Hash()] = &knownTx{
			tx:           tx,
			addedTime:    time.Time{},
			promotedTime: time.Time{},
			status:       status,
		}
	}

	if status == TxStatusQueue {
		k[tx.Hash()].startAddedTimeIfZero()
	} else if status == TxStatusPending {
		k[tx.Hash()].startPromotedTimeIfZero()
	}

	updateMetrics(&k)
}
```
