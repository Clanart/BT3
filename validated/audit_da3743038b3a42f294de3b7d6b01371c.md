## Finding

### Title
Unbounded loop over all registered bribe pools in `castVotes()` can permanently DOS emissions voting/bribe distribution - (File: `wombat/WombatBribeManager.sol`)

### Summary
`WombatBribeManager.castVotes()` is a public, unprivileged function that iterates over the entire `pools` array (every registered LP/gauge) to compute vote deltas and then forwards the full list to `WombatStaking.vote()`, which itself loops again over every pool performing external calls (`safeApprove`, `queueNewRewards`, token transfers). As the number of registered pools grows, the cumulative gas cost of this call-chain grows linearly and unboundedly, mirroring exactly the `distributeAll()` gas-DOS pattern described in the external report for `updatePeriod()`.

### Finding Description
`castVotes()` builds three arrays sized `pools.length` and loops over all of them: [1](#0-0) 

It then calls `wombatStaking.vote()`, passing the full pool set: [2](#0-1) 

`WombatStaking.vote()` in turn loops over every entry of `_lpVote`/`rewardAmounts`, calling into `voter.infos()`, `IWombatBribe.rewardTokens()`, and performing `safeApprove`/`queueNewRewards`/`safeTransfer` calls per pool with a non-zero reward: [3](#0-2) 

New pools are appended to the `pools` array via `addPool()` (owner-only, but the resulting large array size is what causes the unprivileged-facing DOS — the vulnerability is the *unbounded loop*, not the admin action) and can never shrink except one-at-a-time by index via `removePool()`: [4](#0-3) 

This is the same bug class as the reported `updatePeriod()`/`distributeAll()` issue: a function that must iterate over *all* registered gauges/pools in a single transaction, with no ability to page or batch, so gas cost scales with the number of pools and can exceed the block gas limit.

### Impact Explanation
Once the number of registered pools grows large enough that a single `castVotes()` (and the nested `WombatStaking.vote()`) call exceeds the block gas limit, the transaction always reverts. Because `castVotes()` is the sole path used to: (1) actually cast/rebalance votes on the underlying Wombat voter, (2) harvest bribes from Wombat and forward them into pool-specific `BribeRewardPool` rewarders, this would permanently freeze the distribution of all voting-based (bribe) rewards to every user who staked/voted vlMGP across all pools — not just future rewards, but the mechanism to route already-accrued-but-unqueued bribe rewards into claimable rewarders. This satisfies the "permanent freezing of unclaimed yield" / 24h+ freeze impact bar, since there is no owner-only fallback path to force a single-pool vote+distribute once the array is oversized (the only non-full-set alternative, `harvestSinglePool()`, does not reach `_forwardRewards`/reward-queueing logic tied to `castVotes`'s vote-delta computation and delegated pool distribution).

### Likelihood Explanation
Likelihood is moderate to low today (depends on the current pool count relative to block gas limit) but grows monotonically over time as new pools are added via `addPool()`, and unlike `updatePeriod()`/`distributeAll()`, there is no owner action available to reduce the impact other than manually calling `removePool()` one index at a time — itself requiring owner intervention, not something any unprivileged actor can trigger to unblock the system. The vulnerability is purely a function of protocol growth (more registered gauges), matching the exact precondition that made the original report's `distributeAll()` issue exploitable/likely over time.

### Recommendation
Refactor `castVotes()` (and the corresponding `WombatStaking.vote()` path) to support partial/paginated execution — e.g., allow the caller to pass a subset of pool indices to process per transaction (similar to the recommended mitigation for `updatePeriod()`, which now only processes a fixed subset of gauges), rather than requiring the entire `pools` array to be processed atomically in one call.

### Proof of Concept
1. Owner repeatedly calls `addPool()` to register additional LP/gauge pools over time (a normal, expected protocol operation) until `pools.length` is large enough that the gas required by `castVotes()` → `WombatStaking.vote()`'s nested loops (including external calls to `voter.infos`, `IWombatBribe.rewardTokens()`, `safeApprove`, `queueNewRewards`) exceeds the network block gas limit.
2. Any user (or the scheduled/expected caller) invokes `castVotes(bool swapForBnb)`.
3. The transaction always reverts due to out-of-gas, regardless of gas provided, because the loop bounds (`pools.length`) cannot be reduced by an unprivileged caller.
4. All bribe reward distribution and vote-casting functionality for every pool becomes permanently unusable until the owner manually prunes pools via `removePool()`, freezing unclaimed bribe yield for all voters.

        address _lp,
        address _rewarder,
        string memory _name
    ) external onlyOwner {

        if(_lp == address(0))
        revert ZeroAddressError();
        Pool memory pool = Pool({
            poolAddress: _lp,
            rewarder: _rewarder,
            totalVoteInVlmgp: 0,
            name: _name,
            isActive: true
        });
        if (_lp != delegatedPool) {
            pools.push(_lp); // we don't want the delegatedPool in this array
        }
        poolInfos[_lp] = pool;
        emit AddPool(_lp, _rewarder);
    }

    function removePool(uint256 _index) external onlyOwner {
        uint256 length = pools.length;
        if(_index >= length) revert OutOfPoolIndex();
        pools[_index] = pools[length - 1];
        pools.pop();
    }
