## Title
Missing uniqueness binding lets one Bitcoin payout satisfy two Citrea withdrawal indices, causing double reimbursement - (File: core/src/database/verifier.rs)

### Summary
`get_payout_txs_for_withdrawal_utxos` joins `withdrawals` to `bitcoin_syncer_spent_utxos` purely on `(txid, vout)` bytes, and the `withdrawals` table has no `UNIQUE` constraint on `(withdrawal_utxo_txid, withdrawal_utxo_vout)`. If Citrea ever assigns the same Bitcoin outpoint bytes to two different withdrawal indices, a single on-chain spend of that UTXO is attributed to both indices, letting an operator be reimbursed twice from a single payout.

### Finding Description
The intended binding is: **count(payout_txid for withdrawal idx i) == number of distinct Bitcoin payout transactions actually broadcast for i**, i.e., each withdrawal index's payout evidence must come from a spend unique to that index's move-to-vault deposit.

`update_withdrawal_utxo_from_citrea_withdrawal` stores whatever `(txid, vout)` bytes Citrea reports for a given index with no uniqueness check: [1](#0-0) 

The `withdrawals` table schema enforces `idx` as primary key only — there is no `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)`: [2](#0-1) 

`get_payout_txs_for_withdrawal_utxos` then joins on raw outpoint bytes: [3](#0-2) 

This is confirmed by the module's own test, which shows the join returning a row per matching `(idx, spending_txid)` pair for every withdrawal row whose UTXO bytes match a spent-UTXO row — nothing prevents two `idx`s from sharing identical UTXO bytes: [4](#0-3) 

`update_finalized_payouts` (invoked from `Verifier::handle_finalized_block` in the state-processing path) takes exactly these `(idx, payout_txid)` pairs and writes payout attribution per idx without deduplicating by `payout_txid`: [5](#0-4) [6](#0-5) 

`get_first_unhandled_payout_by_operator_xonly_pk` picks payouts by `idx` (`ORDER BY w.idx ASC`), independent of `payout_txid`, so if two indices A and B are both marked paid by the same operator with the same `payout_txid`, `PayoutCheckerTask` processes them as two separate, independent claims across two separate polling iterations: [7](#0-6) [8](#0-7) 

Each call invokes `Operator::handle_finalized_payout` with a *different* `deposit_data.get_deposit_outpoint()` (since idx A and idx B correspond to different deposits/move-to-vault UTXOs), allocating a fresh kickoff/reimbursement connector for each: [9](#0-8) 

Nothing in this code path checks whether the `payout_txid` associated with idx B has already been used to reimburse idx A. `mark_payout_handled`/`get_handled_payout_kickoff_txid` operate per-idx or per unique `payout_txid` in isolation, not cross-idx: [10](#0-9) 

**Attacker's action:** an unprivileged user calls Citrea's `withdraw`/`safeWithdraw` twice with two different withdrawal indices A and B but with byte-identical `input_outpoint` (same Bitcoin UTXO). Nothing in the reachable Clementine code inserts a Bitcoin-side uniqueness check on the withdrawal UTXO across different indices — `update_withdrawal_utxo_from_citrea_withdrawal` blindly overwrites the row for whichever `idx` Citrea reports, for both A and B, with the same bytes: [11](#0-10) 

Once *any* single payout transaction spends that shared UTXO, the join in `get_payout_txs_for_withdrawal_utxos` (line 170-196) returns two rows — one for A, one for B — both carrying the same `payout_txid`, and both get marked paid, enabling two full reimbursement claims from a single fronted payment.

### Impact Explanation
An operator (or the fronting entity, potentially even the attacker's own colluding operator, but note the attack requires only the on-chain fact of ONE spend — the "impact" is realized regardless of whether the double-claim is by an honest operator's automation or malicious operator) obtains a second kickoff/reimbursement claim funded by deposit B's move-to-vault UTXO, without ever having fronted a second BTC payment to any user. This matches the Critical category: "an operator reimbursed for a payout it never funded" / "BTC leaving a move-to-vault UTXO without a matching fronted withdrawal." The blast radius scales with the number of deposit/withdrawal pairs an attacker can align to a duplicated UTXO and is repeatable per duplicate-UTXO pair the attacker can arrange via Citrea's `withdraw` calls.

### Likelihood Explanation
The DB-side flaw (missing `UNIQUE` constraint, byte-only join, per-idx marking without cross-idx `payout_txid` dedup) is unconditionally present in this repo and requires no verifier/operator compromise. However, the actual trigger condition — Citrea's Bridge contract accepting the *same* `input_outpoint` bytes for two different withdrawal indices A and B — is a precondition entirely determined by the Citrea Bridge smart-contract logic, which is **not part of this repository** and could not be verified here (out of scope per the rules: "third-party crate, Citrea contract... defects with no path through this repository"). Whether Citrea's contract validates/deduplicates the supplied `input_outpoint` bytes across withdrawal indices is unknown from the available Clementine source; if Citrea's contract already rejects a duplicate outpoint being registered against a second index, this Clementine-side gap is unreachable and the finding is latent/defense-in-depth only, not independently exploitable.

### Recommendation
Add a defense-in-depth guard independent of Citrea's contract behavior:
1. Add `UNIQUE(withdrawal_utxo_txid, withdrawal_utxo_vout)` on the `withdrawals` table (or a partial unique index excluding NULLs) so `update_withdrawal_utxo_from_citrea_withdrawal` fails/aborts if the same Bitcoin UTXO is ever assigned to two different `idx`s.
2. In `get_payout_txs_for_withdrawal_utxos`/`update_payout_txs_and_payer_operator_xonly_pk`, deduplicate by `payout_txid` so a single spend can only satisfy one withdrawal `idx`, and log/alert on the conflict rather than silently marking both paid.

#[tokio::test]
async fn duplicate_withdrawal_utxo_across_indices_double_attributes_payout() {
    let config = create_test_config_with_thread_name().await;
    let db = Database::new(&config).await.unwrap();
    let mut dbtx = db.begin_transaction().await.unwrap();

    let shared_utxo = bitcoin::OutPoint {
        txid: bitcoin::Txid::from_byte_array([0x77; 32]),
        vout: 0,
    };
    let payout_txid = Txid::from_byte_array([0x88; 32]);
    let move_txid_a = Txid::from_byte_array([0x01; 32]);
    let move_txid_b = Txid::from_byte_array([0x02; 32]);
    let idx_a = 10u32;
    let idx_b = 20u32;

    let block_id = db.insert_block_info(Some(&mut dbtx), &BlockHash::all_zeros(), &BlockHash::all_zeros(), 0).await.unwrap();
    db.insert_txid_to_block(&mut dbtx, block_id, &payout_txid).await.unwrap();
    // Single Bitcoin spend of shared_utxo
    db.insert_spent_utxo(&mut dbtx, block_id, &payout_txid, &shared_utxo.txid, shared_utxo.vout.into()).await.unwrap();

    // Two withdrawal indices set to the SAME withdrawal_utxo bytes
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_a, &move_txid_a).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_a, shared_utxo, block_id).await.unwrap();
    db.upsert_move_to_vault_txid_from_citrea_deposit(Some(&mut dbtx), idx_b, &move_txid_b).await.unwrap();
    db.update_withdrawal_utxo_from_citrea_withdrawal(Some(&mut dbtx), idx_b, shared_utxo, block_id).await.unwrap();

    // BINDING CHECK (before): count(payout_txid rows for shared_utxo spend) should be 1
    let txs = db.get_payout_txs_for_withdrawal_utxos(Some(&mut dbtx), block_id).await.unwrap();
    assert_eq!(txs.len(), 2, "single spend attributed to two withdrawal indices - binding broken");

    let operator_pk = generate_random_xonly_pk();
    db.update_payout_txs_and_payer_operator_xonly_pk(
        Some(&mut dbtx),
        vec![(idx_a, payout_txid, Some(operator_pk), BlockHash::all_zeros()),
             (idx_b, payout_txid, Some(operator_pk), BlockHash::all_zeros())],
    ).await.unwrap();

    // BINDING CHECK (after): both idx now show as paid by the same payout_txid -> double attribution
    let info_a = db.get_payout_info_from_move_txid(Some(&mut dbtx), move_txid_a).await.unwrap().unwrap();
    let info_b = db.get_payout_info_from_move_txid(Some(&mut dbtx), move_txid_b).await.unwrap().unwrap();
    assert_eq!(info_a.2, payout_txid);
    assert_eq!(info_b.2, payout_txid);
    // Both idx_a and idx_b are now eligible for get_first_unhandled_payout_by_operator_xonly_pk / handle_finalized_payout,
    // enabling two independent kickoff/reimbursement claims from a single Bitcoin spend.
}

    pub async fn update_payout_txs_and_payer_operator_xonly_pk(
        &self,
        tx: Option<DatabaseTransaction<'_>>,
        payout_txs_and_payer_operator_xonly_pk: Vec<(
            u32,
            Txid,
            Option<XOnlyPublicKey>,
            bitcoin::BlockHash,
        )>,
    ) -> Result<(), BridgeError> {
        if payout_txs_and_payer_operator_xonly_pk.is_empty() {
            return Ok(());
        }
        // Convert all values first, propagating any errors
        let converted_values: Result<Vec<_>, BridgeError> = payout_txs_and_payer_operator_xonly_pk
            .iter()
            .map(|(idx, txid, operator_xonly_pk, block_hash)| {
                Ok((
                    i32::try_from(*idx).wrap_err("Failed to convert payout index to i32")?,
                    TxidDB(*txid),
                    operator_xonly_pk.map(XOnlyPublicKeyDB),
                    BlockHashDB(*block_hash),
                ))
            })
            .collect();
        let converted_values = converted_values?;

        let mut query_builder = QueryBuilder::new(
            "UPDATE withdrawals AS w SET
                payout_txid = c.payout_txid,
                payout_payer_operator_xonly_pk = c.payout_payer_operator_xonly_pk,
                payout_tx_blockhash = c.payout_tx_blockhash
                FROM (",
        );

        query_builder.push_values(
            converted_values.into_iter(),
            |mut b, (idx, txid, operator_xonly_pk, block_hash)| {
                b.push_bind(idx)
                    .push_bind(txid)
                    .push_bind(operator_xonly_pk)
                    .push_bind(block_hash);
            },
        );

        query_builder
            .push(") AS c(idx, payout_txid, payout_payer_operator_xonly_pk, payout_tx_blockhash) WHERE w.idx = c.idx");

        let query = query_builder.build();
        execute_query_with_tx!(self.connection, tx, query, execute)?;

        Ok(())
    }

    async fn update_finalized_payouts(
        &self,
        dbtx: DatabaseTransaction<'_>,
        block_id: u32,
        block_cache: &block_cache::BlockCache,
    ) -> Result<(), BridgeError> {
        let payout_txids = self
            .db
            .get_payout_txs_for_withdrawal_utxos(Some(dbtx), block_id)
            .await?;

        let block = &block_cache.block;

        let block_hash = block.block_hash();

        let mut payout_txs_and_payer_operator_idx = vec![];
        for (idx, payout_txid) in payout_txids {
            let payout_tx_idx = block_cache.txids.get(&payout_txid);
            if payout_tx_idx.is_none() {
                tracing::error!(
                    "Payout tx not found in block cache: {:?} and in block: {:?}",
                    payout_txid,
                    block_id
                );
                tracing::error!("Block cache: {:?}", block_cache);
                return Err(eyre::eyre!("Payout tx not found in block cache").into());
            }
            let payout_tx_idx = payout_tx_idx.expect("Payout tx not found in block cache");
            let payout_tx = &block.txdata[*payout_tx_idx];
            // Find the first output that contains OP_RETURN
            let circuit_payout_tx = CircuitTransaction::from(payout_tx.clone());
            let op_return_output = get_first_op_return_output(&circuit_payout_tx);

            // If OP_RETURN doesn't exist in any outputs, or the data in OP_RETURN is not a valid xonly_pubkey,
            // operator_xonly_pk will be set to None, and the corresponding column in DB set to NULL.
            // This can happen if optimistic payout is used, or an operator constructs the payout tx wrong.
            let operator_xonly_pk = op_return_output
                .and_then(|output| parse_op_return_data(&output.script_pubkey))
                .and_then(|bytes| XOnlyPublicKey::from_slice(bytes).ok());

            if operator_xonly_pk.is_none() {
                tracing::info!(
                    "No valid operator xonly pk found in payout tx {:?} OP_RETURN. Either it is an optimistic payout or the operator constructed the payout tx wrong",
                    payout_txid
                );
            }

            tracing::info!(
                "A new payout tx detected for withdrawal {}, payout txid: {:?}, operator xonly pk: {:?}",
                idx,
                payout_txid,
                operator_xonly_pk
            );

            payout_txs_and_payer_operator_idx.push((
                idx,
                payout_txid,
                operator_xonly_pk,
                block_hash,
            ));
        }

        self.db
            .update_payout_txs_and_payer_operator_xonly_pk(
                Some(dbtx),
                payout_txs_and_payer_operator_idx,
            )
            .await?;

        Ok(())
    }
