### Title
Optional identity binding in `verify_signature` allows signature-validity-only authentication, enabling identity spoofing for wallet/NFT/DID-based signature verification - ([File: chia/wallet/util/signing.py])

### Summary
Chia's `verify_signature()` RPC helper, exposed through the `verify_signature` wallet RPC endpoint, mirrors the exact bug class in the Parse Server OAuth2 advisory: it only proves that *some* valid BLS keypair produced the signature over the given message, and only cross-checks that the public key is bound to a specific claimed identity (`address`) when the caller explicitly supplies that optional parameter. When `address` is omitted (its default), the function returns `isValid=True` for any self-generated keypair/message/signature triple, without ever proving the signer is the specific wallet/NFT/DID identity being authenticated.

### Finding Description
`verify_signature()` in [1](#0-0)  computes `message_to_verify` from the signing mode and calls `AugSchemeMPL.verify(public_key, message_to_verify, signature)`. The identity-binding check is gated entirely behind an `if address is not None:` branch: [2](#0-1) 

Only inside that branch does the code decode the address to a puzzle hash and compare it against the puzzle hash derived from `public_key` (via `puzzle_hash_for_synthetic_public_key` or `p2_delegated_conditions.puzzle_for_pk`) — i.e., only then is the caller's *claimed identity* (`address`) actually checked against the key that produced the signature. If `address` is `None` (the default, per the request type), the function only proves "a valid signature exists for this arbitrary public key," never that the public key belongs to the account/NFT/DID the verifier believes it is authenticating.

This is defined on the request type as `address: str | None = None` in [3](#0-2) , and is passed straight through by the RPC handler: [4](#0-3) 

The counterpart signing endpoints `sign_message_by_address` / `sign_message_by_id` are explicitly designed for third parties to prove ownership of a wallet address, NFT, or DID via CHIP-0002 message signing [5](#0-4) ; `verify_signature` is the corresponding verification primitive relying parties are meant to call to confirm that proof. Exactly like the Parse Server OAuth2 adapter (which validated token liveness via introspection but skipped the `useridField`/subject binding unless explicitly configured), this Chia primitive validates cryptographic signature liveness/validity but skips the "does this key belong to the claimed identity" binding unless the caller remembers to pass `address`.

### Impact Explanation
Any relying application (offer/trade counterparty verification, "Sign in with Chia" style login flows, DID/NFT ownership attestations, custody/clawback approval flows) that calls the RPC without supplying `address` — which is the easy/default path since the parameter is optional — will accept a signature from *any* attacker-controlled keypair as proof that a specific claimed identity (wallet address / NFT / DID) authorized the message. This is a direct identity-spoofing / account-takeover primitive: an attacker who can produce any valid BLS signature over the expected message (using their own key, which they always can) can impersonate an arbitrary claimed identity to any consumer of this API that omits the `address` binding, matching CWE-287 (Improper Authentication) in the referenced advisory.

### Likelihood Explanation
The vulnerable code path is the default behavior of a documented, public wallet RPC endpoint (`verify_signature`) intended specifically for external identity verification. No special privileges are needed by the attacker — they only need to generate their own keypair and sign the expected message, which is standard capability for any wallet user. The likelihood of a relying integrator omitting the optional `address` field (since it is genuinely optional and not required for the call to succeed) is high, mirroring how Parse Server operators frequently left `useridField` unset.

### Recommendation
Require `address` (or an equivalent claimed-identity parameter) to be supplied and validated for any identity-assertion use of `verify_signature`, or, if `address` must remain optional for backward compatibility, clearly document/flag that omitting it yields "signature is valid for *some* key" semantics only and is unsafe for authentication decisions. Consider defaulting to a fail-closed API (`is_valid=False` / explicit error) when `address` is not provided but the signing mode is one used for identity-proof purposes (CHIP-0002 / CHIP-0002_P2_DELEGATED_CONDITIONS), forcing callers to explicitly opt into the weaker "raw signature validity" mode instead of opting into the stronger identity check.

### Proof of Concept
1. Attacker generates their own BLS keypair `sk_attacker`, computes `pk_attacker = sk_attacker.get_g1()`.
2. Attacker signs the expected challenge message using CHIP-0002 framing: `sig = AugSchemeMPL.sign(sk_attacker, Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash())`.
3. Attacker calls the wallet RPC `verify_signature` with `{message, pubkey: pk_attacker, signature: sig, signing_mode: "CHIP_0002"}` and **no `address` field**.
4. `verify_signature()` in `chia/wallet/util/signing.py` skips the `address is not None` branch entirely and returns `VerifySignatureResponse(isValid=True)` — exactly as if a legitimate wallet/DID/NFT owner had signed, even though `pk_attacker` has no relationship to any specific claimed account.
5. Any relying service that trusts this `isValid=True` result as proof of a specific claimed identity (because it forgot to pass `address`) is now spoofed.

def verify_signature(
    *, signing_mode: SigningMode, public_key: G1Element, message: str, signature: G2Element, address: str | None
) -> VerifySignatureResponse:
    """
    Given a public key, message and signature, verify if it is valid.
    :param request:
    :return:
    """
    if signing_mode in {SigningMode.CHIP_0002, SigningMode.CHIP_0002_P2_DELEGATED_CONDITIONS}:
        # CHIP-0002 message signatures are made over the tree hash of:
        #   ("Chia Signed Message", message)
        message_to_verify: bytes = Program.to((CHIP_0002_SIGN_MESSAGE_PREFIX, message)).get_tree_hash()
    elif signing_mode == SigningMode.BLS_MESSAGE_AUGMENTATION_HEX_INPUT:
        # Message is expected to be a hex string
        message_to_verify = hexstr_to_bytes(message)
    elif signing_mode == SigningMode.BLS_MESSAGE_AUGMENTATION_UTF8_INPUT:
        # Message is expected to be a UTF-8 string
        message_to_verify = bytes(message, "utf-8")
    else:
        raise ValueError(f"Unsupported signing mode: {signing_mode!r}")

    # Verify using the BLS message augmentation scheme
    is_valid = AugSchemeMPL.verify(
        public_key,
        message_to_verify,
        signature,
    )
