### Title
`ThresholdKeys::read` accepts a `secret_share` inconsistent with the `verification_shares`, silently producing a divergent `group_key`/share pair - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The Eco bug class is "the same logical value maintained in two places, where an alternate update path lets them diverge, so downstream consumers use a stale/inconsistent parameter." The Serai analog lives in `ThresholdKeys` deserialization: a threshold keypair consists of a `secret_share` and the per-participant `verification_shares` map, and the two are independent fields in the serialized blob. `ThresholdKeys::read` reconstructs both but never checks that `secret_share * G == verification_shares[i]`. The `group_key` is derived solely from `verification_shares` (`ThresholdKeys::new`, crypto/dkg/src/lib.rs:376-378), while signing uses the raw `secret_share`. Any reader of the serialized bytes therefore accepts a key whose private share does not correspond to its public commitments — a permanent divergence between the "registered" key and the key actually used to sign.

### Finding Description
`ThresholdKeys::write` serializes `params`, `interpolation`, `secret_share`, and all `verification_shares` as independent fields (crypto/dkg/src/lib.rs:538-560). `ThresholdKeys::read` parses each field and calls `ThresholdKeys::new` (lib.rs:618-630). `new` validates participant indices, count, and interpolation applicability, then computes `group_key` by interpolating `verification_shares[1..=t]` — but performs no check tying `secret_share` to `verification_shares[i]` (lib.rs:355-390). This is equivalent to the L2ECO issue: `linearInflationMultiplier` existed on both `L2ECO` and `L2ECOBridge` and could be updated on one without the other; here the secret share and its public commitment are two copies of one fact, and the deserialization path updates both from attacker-controlled bytes with no consistency check.

In PedPoP, the honest-generation path does verify shares against the dealer's commitments, so divergence cannot arise through the DKG itself — it arises specifically through `ThresholdKeys::read` (one of the enumerated untrusted-byte sinks), used for key imports and DB reads (`GeneratedKeysDb::read_keys` calls `ThresholdKeys::read` on stored bytes, processor/src/key_gen.rs:57-58).

### Impact Explanation
A `ThresholdKeys` deserialized with `secret_share` ≠ `verification_shares[i]·G` yields a signer whose `group_key()` advertises one key while `sign_share` uses a different secret. Concretely, in `AlgorithmSignMachine::sign` the view is built from these keys (crypto/frost/src/sign.rs:312) and in `complete` the summed shares are verified against `view.group_key()` (sign.rs:465); a tampered share produces a signature that fails under the group key, or worse, every honest share verifies individually (against `verification_shares`) while the aggregate never verifies — the code itself flags this as reachable only via "a semantically invalid FrostKeys" (sign.rs:491-494). For a validator/processor loading keys this means batches/transactions that can never produce a valid threshold signature (permanent signing DoS for that key set), and blame is mis-assigned since `verify_share` checks against the inconsistent verification shares.

### Likelihood Explanation
Reaching this requires attacker influence over bytes fed to `ThresholdKeys::read` — e.g., corrupted/tampered serialized key material presented to an import path. It does not require a malicious validator or collusion; it is a deserialization-validation gap exactly like the report's "alternate path mutates one copy." Likelihood is moderate because production paths generate keys via PedPoP where consistency holds, but the code explicitly contemplates deserialized-invalid keys (sign.rs:493), confirming the state is reachable and unhandled upstream.

### Recommendation
In `ThresholdKeys::new` (or in `read`), assert `C::generator() * secret_share == verification_shares[&params.i()]`. This is cheap (one scalar multiplication) and collapses the two stored copies into a verified single fact — mirroring the report's recommendation to derive the dependent value from one source rather than trusting both.

### Proof of Concept
```rust
// Construct honest keys, then deserialize a blob with a swapped secret_share.
let mut serialized = honest_keys.serialize().to_vec();
// Layout: id_len(4) | id | t(2) | n(2) | i(2) | interp(1[+n*32]) | share(32) | shares(n*32/33)
// Overwrite the secret_share field with a different scalar:
let share_off = 4 + C::ID.len() + 6 + 1; // for Interpolation::Lagrange
let forged = C::F::random(&mut OsRng).to_repr();
serialized[share_off .. share_off + 32].copy_from_slice(forged.as_ref());

let keys = ThresholdKeys::<C>::read(&mut serialized.as_slice()).unwrap(); // accepted
assert_ne!(C::generator() * keys.original_secret_share().deref(),
           keys.original_verification_share(keys.params().i())); // divergence, never checked
// keys.group_key() is unchanged; signing now produces shares that fail
// complete()'s aggregate verify while blaming innocent participants.
```
`ThresholdKeys::new` at crypto/dkg/src/lib.rs:349-391 performs count/index/interpolation checks only; the missing equality check is the fix site.
