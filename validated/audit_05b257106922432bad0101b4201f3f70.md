Confirmed: `msg_server.go`'s `EVMTransaction` handler explicitly `panic(pe)` re-raises any non-`ErrReadEstimate` panic after logging `"EVM PANIC"` [1](#0-0) , and `precompiles/common/precompiles.go`'s `HandlePrecompileError` only converts *gas-meter* panics to reverts while letting other panics propagate (confirmed by the regression test `TestDynamicGasPrecompileRepanicsNonGas`) [2](#0-1) . This means an unrecovered type-assertion panic inside a pointer-precompile executor is not a benign per-tx revert — it is a real Go panic that only gets caught at higher-level, chain-wide recovery points (`makeGigaDeliverTx` / `ProcessTxsSynchronousGiga`), which log it and convert it into an `ErrPanic` ABCI response [3](#0-2) . While this stops a full node crash, it still means the `AddCW20Pointer`/`AddCW721Pointer` precompile calls are not safely isolated from malformed contract responses in the way the report requires.

### Title
Unchecked type assertion on CW20/CW721 `name`/`symbol` query response causes a Go panic in the pointer precompile - ([File: precompiles/pointer/pointer.go])

### Summary
The `AddCW20`/`AddCW721` (and `AddCW1155`) pointer-precompile handlers query a caller-supplied CosmWasm contract for its `token_info`/`contract_info`, unmarshal the JSON response into a `map[string]interface{}`, and then do an unchecked type assertion `formattedRes["name"].(string)` / `formattedRes["symbol"].(string)` to build the ERC pointer's name/symbol [4](#0-3) . This pattern is repeated identically across essentially every historical pointer precompile version (`v552` through the current `pointer.go`) [5](#0-4) [6](#0-5) .

### Finding Description
Any CosmWasm contract address can be passed as `cwAddr` to `addCW20Pointer`/`addCW721Pointer`. The contract is queried with `{"token_info":{}}` or `{"contract_info":{}}`, and the JSON result is unmarshaled into a generic map. The code assumes `formattedRes["name"]` and `formattedRes["symbol"]` are present and of type `string`, and asserts this without the two-value `ok` form: `name := formattedRes["name"].(string)`. A CW20/CW721 contract fully controlled by the caller can trivially return a `token_info`/`contract_info` response where `name` or `symbol` is omitted (yielding `nil` in the map) or is a non-string JSON value (number, object, array, bool). In Go, `nil.(string)` or `float64.(string)` in the single-value assertion form panics with "interface conversion: interface {} is nil, not string" (or similar), rather than returning an error.

This is directly analogous to the MobSF root cause (CWE-1287, Improper Validation of Specified Type of Input): externally-supplied, attacker-controlled data (`CFBundleIdentifier` in MobSF; `name`/`symbol` fields from an untrusted CW20/CW721 contract in sei-chain) is trusted to have an expected format/type without validation, and a mismatch turns into an unhandled runtime error instead of a graceful rejection.

### Impact Explanation
The unhandled panic is not caught as a normal EVM revert because `HandlePrecompileError` (the `defer` wrapping every dynamic-gas precompile call) only intercepts gas-meter panics and re-panics everything else [7](#0-6) . It propagates up through `evm.Create`/`Execute` into `msgServer.EVMTransaction`, which itself re-panics after logging "EVM PANIC" for anything other than an OCC read-estimate error [1](#0-0) . It is only caught at the top-level giga/legacy `deliver_tx` recovery wrappers, which convert it into a generic `ErrPanic` ABCI response and log a full stack trace [3](#0-2) . While this specific call path does not crash the node outright (thanks to the outer recover), it defeats the precompile's own error-handling contract, produces noisy panic logs/metrics on every validator for a single crafted transaction, and represents a fragile "last line of defense" pattern rather than intended, validated error handling — any future change or code path that reaches this same helper without the outer app-level recover (e.g. in query/simulation contexts, migrations, or genesis paths that reuse `AddCW20`/`AddCW721`) would turn this into a genuine validator-crashing DoS.

### Likelihood Explanation
Likelihood is high: any account can deploy a minimal CosmWasm contract that responds to `token_info`/`contract_info` queries with a non-string or missing `name`/`symbol` field, then call `addCW20Pointer`/`addCW721Pointer` from a normal EVM transaction. No special privileges, governance action, or validator collusion is required — this is reachable by any unprivileged CW20/CW721 deployer plus pointer-precompile caller, exactly the actor classes in scope.

### Recommendation
Replace every unchecked `formattedRes["name"].(string)` / `formattedRes["symbol"].(string)` assertion in the pointer precompile executors (`precompiles/pointer/pointer.go` and all `legacy/vNNN` copies) with the two-value form, returning a normal precompile error (not a panic) when the field is missing or not a string, e.g.:
```go
name, ok := formattedRes["name"].(string)
if !ok {
    return nil, 0, fmt.Errorf("cw contract returned non-string name")
}
```
Apply the same fix to `symbol` (and any other typed field pulled from `formattedRes`), across all active and legacy versions of the pointer precompile, plus the migration helpers in `x/evm/migrations/migrate_all_pointers.go` that follow the same pattern via `QueryERCSingleOutput`.

### Proof of Concept
1. Deploy a CosmWasm contract whose `{"token_info":{}}` query handler returns valid JSON such as `{"name": 12345, "symbol": "X", "decimals": 6, "total_supply": "0"}` (i.e., `name` is a JSON number, not a string), or omits `name` entirely.
2. From an EVM account, call the pointer precompile's `addCW20Pointer(cwAddr)` (or `addCW721Pointer` with an analogous `contract_info` response) targeting this contract's Sei address.
3. Inside `AddCW20`, `p.wasmdKeeper.QuerySmart` succeeds and `json.Unmarshal` succeeds, but `formattedRes["name"].(string)` panics because the underlying value is a `float64`/`nil`, not a `string`.
4. Observe in validator logs the `"EVM PANIC"` message and stack trace from `msg_server.go`'s deferred recover, and an `ErrPanic`-coded `ResponseDeliverTx`/`ExecTxResult` for that transaction, confirming the type-safety violation reaches all the way to the top-level panic-recovery boundary instead of being handled as a normal precompile execution error.
