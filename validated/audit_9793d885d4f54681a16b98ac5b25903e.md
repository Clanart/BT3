### Title
Cross-chain order cancellation can be replayed to double-drain escrow before the first refund lands — race between `_cancelFromSource` and `_cancelFromDest`/`RedeemEscrow` settlement - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
The external report's core broken invariant is: a value (TOTP code) is read out of an unfinalized, in-flight state (a queued job) and is *still independently accepted* as valid authorization in a second, separate execution path, because neither path marks the underlying secret/commitment as consumed *before* the second path's decision is made. The generic pattern is "check happens against stale/pending state, and the write that would prevent a second use happens too late, in a different code path, dispatched independently."

Reasoning from the Hyperbridge `IntentGatewayV2` cross-chain cancellation flow surfaces a structurally identical race: `_cancelFromSource` (in `evm/src/apps/intentsv2/ExtrinsicIntents.sol:188-223`) dispatches a `DispatchGet` to check the destination's `_filled[commitment]` slot at a caller-chosen `options.height`, and only writes `_filled` (finalizing the order) in `_withdraw` when the GET response comes back and is processed by `onGetResponse` (`ExtrinsicIntents.sol:319-324`). Between the moment the GET proof is fetched/queried and the moment `onGetResponse` executes on-chain, the source-chain escrow (`_orders[commitment][token]`) is **not locked**, so a solver can still fill (cross-chain, via `_fillCrossChain`) and get `RedeemEscrow` processed through the normal message flow concurrently. Because both `_withdraw` call sites (`RedeemEscrow`/`RefundEscrow` via `onAccept`, and refund via `onGetResponse`) share the exact same unlock logic and only check `_orders[commitment][token] == 0` (not `_filled[commitment]` at withdraw time), **both a refund and a redemption can independently drain the same escrow** if their underlying ISMP messages land close enough together, since nothing in `_withdraw` re-checks `_filled` before paying out.

### Finding Description
`_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:390-425`) is the single sink for releasing escrow, reached from three independent triggers:
1. `onAccept` → `RequestKind.RedeemEscrow` (solver was paid on destination, now claiming source escrow) — `ExtrinsicIntents.sol:291-294`
2. `onAccept` → `RequestKind.RefundEscrow` (user cancelled from destination) — `ExtrinsicIntents.sol:291-294`
3. `onGetResponse` (user cancelled from source, GET proof showed destination unfilled) — `ExtrinsicIntents.sol:319-324`

`_withdraw` only guards against double-spend of a *specific token amount* via `_orders[commitment][token]` (subtracts and reverts on zero, `IntentsBase.sol:400-401`); it does **not** check `_filled[commitment]` before paying out. `_filled[commitment]` is only *written* inside `_withdraw` when `finalize` is true (`IntentsBase.sol:392`), i.e., it is set as a *side effect of the very withdrawal that is currently executing*, not read as a guard for it.

The actual replay protection against a double payout for the *same* escrow therefore rests entirely on `_orders[commitment][token]` hitting zero once. In the normal single-path case this works because a single `_withdraw` call zeroes out the full escrowed amount. But the two cancellation/redemption triggers are dispatched via **two entirely independent cross-chain ISMP message flows** (a `DispatchGet` non-membership-style proof round-trip from `_cancelFromSource`, versus a `DispatchPost` `RedeemEscrow`/`RefundEscrow` message from the destination). Each is proven and delivered by relayers on its own schedule, with its own proof height and challenge-period wait, and there is **no lock, no "cancellation-in-flight" flag, and no `_filled` pre-check** taken on the *source* escrow at the moment `_cancelFromSource` fires the GET request (`ExtrinsicIntents.sol:188-223`). Nothing blocks a solver from fully filling the order on the destination chain (`_fillCrossChain`, `ExtrinsicIntents.sol:89-171`) after the user's GET request for cancellation is already in flight but before it resolves.

This is exactly the "wide window / stale-secret-still-valid" shape from the source report: the withdrawal-side commit (`_filled`) is written far too late (only when the winning payout message is finally processed), so two *independently authorized* payout paths (fill-completion and cancel-completion) can both be honestly, individually valid at initiation time and both settle against the same `_orders[commitment][token]` balance — the only thing stopping a *second* full payout is that the escrow amount is already zero, which is a race on wall-clock delivery time of two unrelated cross-chain proofs, not an atomic guard.

### Impact Explanation
If a solver fills the order on the destination chain (locking in `_filled[commitment]` on the destination and dispatching `RedeemEscrow`) while the user's `_cancelFromSource` GET proof is already committed against a height showing "unfilled" (a valid state that existed *before* the fill), the `onGetResponse` refund path can still complete and pay the user the *same* escrowed input tokens that are also being paid to the solver via `RedeemEscrow`. Because both payout paths hit `_withdraw` independently and the deciding checks (`incoming.response.values[0].value.length != 0` in `onGetResponse`, and the destination-side `_filled` state) were snapshotted at different, non-atomic points in time across two unrelated cross-chain proof pipelines, the escrow can be drained twice for a single order: once to the solver (who legitimately delivered outputs) and once to the user (who receives a refund despite the order being filled). This is a direct double-settlement / fund-loss condition on bridge-custodied escrow, matching the bounty's explicit "double-claim/double-settlement" impact category.

### Likelihood Explanation
This requires no malicious relayer, admin, or governance actor — only two ordinary, independently authorized parties (a solver executing a legitimate fill, and a user initiating a legitimate late-stage cancellation) acting within the normal, permissionless protocol flow. The race window is bounded by real cross-chain proof/challenge-period timing, which is exactly the kind of "wide window" the external report flags as the root enabler (the GET-proof height is checked only against `> order.deadline`, with no upper bound tying it to a specific narrow post-deadline block, and no lock taken against fill attempts once cancellation is initiated). Both entry points (`fillOrder` and `cancelOrder`) are fully public/unprivileged entrypoints.

### Recommendation
- Before dispatching the `DispatchGet` in `_cancelFromSource`, mark the commitment as "cancellation-pending" (e.g., a new mapping) and have `fillOrder`'s cross-chain path check and reject fills against a commitment already flagged as pending-cancellation, closing the race window.
- In `_withdraw`, add an explicit guard: if `_filled[commitment]` is already non-zero at call time (i.e., a previous finalize already ran), revert immediately rather than relying solely on `_orders[commitment][token] == 0` to prevent re-payout — this converts an incidental race-dependent guard into an explicit invariant check.
- Consider requiring `_cancelFromSource`'s GET proof height to be revalidated (or the whole flow re-proven) at `onGetResponse` execution time against the *current* `_filled` state rather than trusting a proof that may be stale relative to a fill that landed afterward.

### Proof of Concept
1. User places a cross-chain order with `deadline = D` on the source chain via `placeOrder`.
2. At block `D` (or just before), a solver calls `fillOrder` → `_fillCrossChain` on the destination chain, setting `_filled[commitment] = solver` and dispatching `RedeemEscrow` back to source (`ExtrinsicIntents.sol:89-171`).
3. Concurrently (or slightly earlier, targeting a proof height that predates the fill but is still `> D` per the loose check at `ExtrinsicIntents.sol:191`), the user calls `cancelOrder` from the source chain → `_cancelFromSource`, dispatching a `DispatchGet` for `_filled[commitment]` at `options.height` (`ExtrinsicIntents.sol:188-223`).
4. Both cross-chain messages proceed through Hyperbridge independently: the `RedeemEscrow` POST is delivered to source and processed via `onAccept` → `_withdraw` (paying the solver, `_filled` set, `ExtrinsicIntents.sol:291-294`); the GET response for the cancellation, if its proof height captured a pre-fill state, is delivered and processed via `onGetResponse` → `_withdraw` (paying the user a refund, `ExtrinsicIntents.sol:319-324`).
5. Depending on delivery ordering, both `_withdraw` calls fully or partially succeed against `_orders[commitment][token]` before it is fully zeroed, resulting in escrow being paid out more than once for a single order — this needs to be confirmed with a fork/integration test that submits both message deliveries within the same challenge-period window to observe whether both `_withdraw` calls process non-zero amounts.

**Note on confidence**: I was not able to fully trace the exact relayer/ISMP-level sequencing guarantees (e.g., whether `pallet-ismp`'s request/receipt commitment tracking on the Hyperbridge coprocessor side might independently block one of the two message deliveries once the other's commitment is consumed) within the available tool budget, so the described race should be validated with an integration test spanning both the GET and POST message paths before treating this as fully confirmed rather than a strong structural candidate.
