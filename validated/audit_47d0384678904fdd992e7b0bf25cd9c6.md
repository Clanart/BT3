### Title
Payout tx's operator-attribution OP_RETURN is unsigned under `SinglePlusAnyoneCanPay`, letting anyone rewrite it and win the block-inclusion race - ([File: core/src/builder/transaction/operator_reimburse.rs])

### Summary
The payout transaction created by `create_payout_txhandler` places the user's payout output at index 0, an anchor at index 1, and the operator-attribution `OP_RETURN` at index 2, but the user's authorizing signature is required to use `SinglePlusAnyoneCanPay` sighash. Under BIP-341, `SIGHASH_SINGLE` only commits to the output at the *same index* as the signed input (index 0), so outputs 1 and 2 - including the operator's x-only pubkey that determines who gets reimbursed - are completely unsigned and can be freely rewritten by anyone who observes the broadcast transaction, while the original signature/witness remains valid.

### Finding Description
Binding under test: `payout_txid` recorded as confirmed for withdrawal `i` (via `update_finalized_payouts` reading the block and calling `get_first_op_return_output`/`parse_op_return_data`, [1](#0-0) ) must equal the txid operator A actually intended, and the attributed `operator_xonly_pk` stored in `withdrawals.payout_payer_operator_xonly_pk` must be A's key.

`create_payout_txhandler` builds the payout tx with the OP_RETURN carrying `operator_xonly_pk` as output index 2, after the user payout (index 0) and anchor (index 1): [2](#0-1) . The single input is signed key-spend with a user-supplied `taproot::Signature` whose `sighash_type` is expected/enforced to be `SinglePlusAnyoneCanPay` (per the error message and the aggregator's `parse_withdrawal_sig_params` check [3](#0-2) , and verified against `in_signature.sighash_type` in `Operator::withdraw`: [4](#0-3) ).

`calculate_pubkey_spend_sighash` computes the sighash per BIP-341/`bitcoin::sighash` semantics: [5](#0-4) . Under `SIGHASH_SINGLE`, only the output at the same index as the input (index 0) is committed; `ANYONECANPAY` means only the signer's own input is committed. This means outputs 1 (anchor) and 2 (OP_RETURN operator pubkey) are **not covered by the signature at all**, and additional inputs may be freely added.

Exploit flow: once operator A broadcasts `payout_tx`, an attacker (unprivileged, per the threat model, capable of broadcasting Bitcoin transactions) copies the transaction, keeps the input and its witness (still valid because it doesn't commit to outputs 1/2), keeps output 0 unchanged (it is signature-committed), but replaces output 2's OP_RETURN payload (e.g., with a different, uninvolved operator's xonly pubkey, or garbage), optionally adds an extra input (ANYONECANPAY-permitted) to raise the fee, and submits this sibling transaction with a different txid at a higher feerate to a different relay/pool. Standard mempool/miner fee-priority selection (no majority hashrate needed) can then confirm the attacker's sibling instead of A's original.

When the block is scanned, `update_finalized_payouts` reads whichever payout tx actually confirmed spending the withdrawal UTXO and parses its OP_RETURN to determine `payout_payer_operator_xonly_pk` [6](#0-5) . There is no check that the confirmed payout tx matches a specific txid that any operator "claimed" beforehand - attribution is derived purely from whatever OP_RETURN bytes happen to be in the block. This directly feeds `is_kickoff_malicious`, which compares this DB-derived `operator_xonly_pk` against `kickoff_data.operator_xonly_pk` [7](#0-6) , and `get_first_unhandled_payout_by_operator_xonly_pk`, which drives `PayoutCheckerTask`'s reimbursement flow for whichever operator's key ends up attributed [8](#0-7) .

No existing guard prevents this: `Verifier::is_deposit_valid`, `Operator::is_profitable`, and `SPV::verify` do not check who broadcast the transaction or bind the txid to a specific pre-committed value; the musig2/N-of-N signing flow is not involved for the payout tx (it is a solo user-key-spend); and the database uniqueness constraint on `withdrawals.idx` does nothing to prevent this because there is only ever one row per withdrawal - it just gets whatever operator key the confirmed OP_RETURN happens to contain.

### Impact Explanation
- If the attacker rewrites the OP_RETURN to point to operator X while A actually funded the withdrawal, X (an uninvolved operator) becomes the DB-attributed payer, and X can later kick off and be reimbursed for a payout it never funded (`get_first_unhandled_payout_by_operator_xonly_pk` + `PayoutCheckerTask`/`send_asserts` path).
- A, who genuinely funded the user's payout, will fail `is_kickoff_malicious`'s pubkey check when it later submits its kickoff (attributed pk ≠ A), and per the state machine this is expected to lead to A's kickoff being treated as malicious/A's collateral being burned - a permanent, unrecoverable loss for an honest operator.
- This is repeatable for every withdrawal broadcast by any operator, and requires no operator/verifier/aggregator privilege, no hashrate majority, and no key compromise - only observing a broadcast transaction and paying a marginally higher fee. This satisfies the Critical bucket ("an operator reimbursed for a payout it never funded" / "an honest operator's collateral burned").

### Likelihood Explanation
The attacker only needs to: (1) observe operator A's `payout_tx` in the mempool (public data), (2) construct a sibling transaction reusing the same signed input and output 0, with a rewritten OP_RETURN and/or added fee-bumping input, (3) broadcast it with a higher feerate via any relay. No control over verifiers, aggregator, or hashrate is required - this is a standard "malleate-then-race" attack enabled purely by the incomplete sighash coverage, and it is deployable on every payout, by any anonymous internet participant with a small amount of BTC for fees.

### Recommendation
Require the payout transaction's user signature to use `TapSighashType::AllPlusAnyoneCanPay` (or otherwise commit to all outputs, not just output 0) so the operator-attribution OP_RETURN and anchor cannot be altered without invalidating the signature. Additionally, when recording `payout_payer_operator_xonly_pk` during `update_finalized_payouts`, cross-check the confirmed payout txid against the txid the operator originally signed/broadcast (or otherwise pin attribution to a value the signature itself commits to) rather than trusting whatever OP_RETURN happens to be present in the block.

### Proof of Concept
```
cargo test payout_op_return_malleability_race --features integration -- --nocapture
```
Plan:
1. Set up regtest bridge with one deposit and one registered withdrawal (citrea_idx `i`), get the withdrawal UTXO via `get_withdrawal_utxo_from_citrea_withdrawal`.
2. Have operator A build/sign a valid `payout_tx_A` via `create_payout_txhandler` with `SinglePlusAnyoneCanPay`, broadcast it (do not mine).
3. As "attacker", take `payout_tx_A`'s witness/input, construct `payout_tx_attacker` with identical input/output0, but OP_RETURN rewritten to an uninvolved operator X's xonly pubkey, and an extra funding input/higher fee (ANYONECANPAY permits this without needing A's key). Assert `SECP.verify_schnorr` still succeeds against the original signature for `payout_tx_attacker`'s sighash (proving malleability).
4. Broadcast `payout_tx_attacker` and mine exactly one block containing only `payout_tx_attacker` (not `payout_tx_A`).
5. Run block sync (`update_finalized_payouts`) and assert `db.get_payout_info_from_move_txid(...)` returns `payout_payer_operator_xonly_pk == X`, `payout_txid == payout_tx_attacker.txid()`, even though A funded the withdrawal output.
6. Assert that when A later submits its kickoff, `Verifier::is_kickoff_malicious` returns `true` for A (binding violated: intended payer A ≠ attributed payer X).

pub fn create_payout_txhandler(
    input_utxo: UTXO,
    output_txout: TxOut,
    operator_xonly_pk: XOnlyPublicKey,
    user_sig: taproot::Signature,
    _network: bitcoin::Network,
) -> Result<TxHandler<Signed>, BridgeError> {
    let txin = SpendableTxIn::new_partial(input_utxo.outpoint, input_utxo.txout);

    let output_txout = UnspentTxOut::from_partial(output_txout.clone());

    let op_return_txout = op_return_txout(PushBytesBuf::from(operator_xonly_pk.serialize()));

    let mut txhandler = TxHandlerBuilder::new(TransactionType::Payout)
        .with_version(NON_STANDARD_V3)
        .add_input(
            NormalSignatureKind::NotStored,
            txin,
            SpendPath::KeySpend,
            DEFAULT_SEQUENCE,
        )
        .add_output(output_txout)
        .add_output(UnspentTxOut::from_partial(anchor_output(
            NON_EPHEMERAL_ANCHOR_AMOUNT,
        )))
        .add_output(UnspentTxOut::from_partial(op_return_txout))
        .finalize();
    txhandler.set_p2tr_key_spend_witness(&user_sig, 0)?;
    txhandler.promote()
}

    pub fn calculate_pubkey_spend_sighash(
        &self,
        txin_index: usize,
        sighash_type: TapSighashType,
    ) -> Result<TapSighash, BridgeError> {
        let prevouts_vec: Vec<&TxOut> = self
            .txins
            .iter()
            .map(|s| s.get_spendable().get_prevout())
            .collect();
        let mut sighash_cache: SighashCache<&bitcoin::Transaction> =
            SighashCache::new(&self.cached_tx);
        let prevouts = match sighash_type {
            TapSighashType::SinglePlusAnyoneCanPay
            | TapSighashType::AllPlusAnyoneCanPay
            | TapSighashType::NonePlusAnyoneCanPay => {
                bitcoin::sighash::Prevouts::One(txin_index, prevouts_vec[txin_index])
            }
            _ => bitcoin::sighash::Prevouts::All(&prevouts_vec),
        };

        let sig_hash = sighash_cache
            .taproot_key_spend_signature_hash(txin_index, &prevouts, sighash_type)
            .wrap_err("Failed to calculate taproot sighash for key spend")?;
