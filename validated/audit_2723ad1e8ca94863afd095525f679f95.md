### Title
Escrow accounting mutated *after* external token transfer in `withdraw()` (missing CEI/reentrancy-guard) — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The reported CREAM `gulp` bug is a case of an accounting variable (`totalReserves`/`internalCash`) being written *after* an external call, in a function reachable while other flows are executing, with no reentrancy guard. The Tron deployment of Hyperbridge's `IntentGatewayV2` contract reproduces exactly this pattern in its escrow-release routine: `withdraw()` sends tokens/ETH to the beneficiary via a low-level `.call` **before** decrementing the `_orders` escrow ledger, and the contract has no `ReentrancyGuard`/`nonReentrant` protection at all — unlike the canonical (non-Tron) `evm/src/apps/IntentGatewayV2.sol`, which imports and applies `nonReentrant` throughout, and unlike `IntentsBase._withdraw`, which correctly decrements escrow *before* transferring (true checks-effects-interactions).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    for (uint256 i; i < len;) {
        ...
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- state mutated AFTER the external call
        ...
    }
    ...
}
``` [1](#0-0) 

This is the exact "gulp" pattern: the corrupted value is `_orders[commitment][token]` (the escrow ledger), which is written only *after* an arbitrary external call (`beneficiary.call{value:...}` for native assets, or `token.call(...)` for a caller-supplied token address). The token address itself is fully attacker-controlled at order-placement time — `placeOrder` only requires the token to support `transferFrom` for the initial deposit, so an attacker can register a contract whose `transfer()` selector path (invoked here via low-level `.call`, not `safeTransfer`) executes arbitrary reentrant logic before `_orders[...] -= amount` commits.

By contrast, the canonical EVM contract explicitly wraps its equivalent flows with `nonReentrant`: [2](#0-1) 
and the shared library implementation `IntentsBase._withdraw` performs the decrement *before* the transfer (correct CEI):
```solidity
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
``` [3](#0-2) 

The Tron fork of `withdraw()` reverts this fix and drops the guard, so the two independently-audited protections (CEI ordering and `nonReentrant`) that exist in the sibling contract are both absent here. `withdraw()` is reachable from three places: `cancelOrder` (same-chain refund, publicly callable by the order owner), `onAccept` (host-gated `RedeemEscrow`/`RefundEscrow`), and `onGetResponse` (host-gated cross-chain cancel settlement). [4](#0-3) [5](#0-4) [6](#0-5) 

While `_filled[body.commitment]` is set as the first statement of `withdraw()`, which blocks a naive re-entrant call back into `cancelOrder` for the *same* commitment (it would hit the `Filled()` check at the top of `cancelOrder`), this only closes one specific re-entry path. It does **not** restore proper CEI ordering for `_orders`, and it does not protect the transaction-fee redemption block that follows the token loop, which also performs a raw `.call` transfer before clearing state:
```solidity
uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
if (fees > 0) {
    address feeToken = IDispatcher(host()).feeToken();
    (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
    if (!success) revert TransferFailed();
    delete _orders[body.commitment][TRANSACTION_FEES];   // <-- also after the call
}
``` [7](#0-6) 

### Impact Explanation
`_orders[commitment][token]` is the sole source of truth for how much of each token is still escrowed and redeemable for a given order commitment. Mutating it after handing control to an attacker-influenceable external call (raw `.call` to an arbitrary "token" address or to the beneficiary for native ETH) is the precise anti-pattern flagged in the report: unpredictable/duplicated payout logic can result from any code path that manages to re-enter the accounting-sensitive window before the decrement executes. Given this is escrow-custody code for cross-chain intents (fund loss/duplicate settlement is explicitly in-scope), any surviving reentrant path into this window (e.g., through future code changes, additional entry points, or host dispatch nesting not covered by the current `_filled`/`onlyHost` gates) would result in draining more tokens than were ever escrowed for the order — a direct, unauthorized loss of bridged/escrowed funds.

### Likelihood Explanation
Moderate-to-low as currently gated: the `_filled` flag blocks the most obvious re-entry vector (`cancelOrder` → `withdraw` → reenter `cancelOrder`), and `onAccept`/`onGetResponse` are `onlyHost`-restricted, limiting a directly attacker-triggered double-invocation within a single transaction. However, the contract has fully regressed the CEI ordering and dropped the `ReentrancyGuard` present in its sibling implementation, meaning the residual protection is incidental (a side effect of `_filled`'s placement) rather than a deliberate, defense-in-depth guarantee. Any additional call path into `withdraw()`, any batching/nesting behavior in the host's dispatch loop, or any future refactor that adds a second attacker-reachable caller of `withdraw()` would reopen a directly exploitable double-spend, exactly mirroring the CREAM `gulp` finding's root cause.

### Recommendation
- Reorder `withdraw()` to decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing any external call, matching `IntentsBase._withdraw`'s CEI pattern.
- Replace raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` with `SafeERC20.safeTransfer`, which is already used elsewhere in the codebase, to avoid silently accepting non-standard/malicious token behavior.
- Add `ReentrancyGuard`/`nonReentrant` to `withdraw()` (and any public entrypoints that call it) so the fix does not rely solely on the incidental positioning of the `_filled` write, consistent with the mainline `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Attacker deploys a "token" contract `EvilToken` that implements `transferFrom` normally (so escrow deposit in `placeOrder` succeeds) but whose 4-byte `transfer(address,uint256)` handler contains attacker logic.
2. Attacker calls `placeOrder` with `order.inputs` containing `EvilToken` (and/or native ETH) as one of the escrowed assets, becoming `order.user`.
3. Attacker calls `cancelOrder` (same-chain path) before the order is filled; this invokes `withdraw(body, true)`.
4. Inside the token loop, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` invokes `EvilToken`'s handler **before** `_orders[commitment][token] -= amount` executes — demonstrating the CEI violation is live and reachable from an unprivileged, public entrypoint. (Full fund-drain requires an additional re-entry path beyond `cancelOrder`, which the current `_filled` check happens to block; this PoC demonstrates the unguarded external-call-before-state-write window that is the direct structural analog of the `gulp` finding and should be closed regardless of whether a full bypass is currently composable.)

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

            // Same-chain: validate locally and refund immediately
            // only owner can cancel

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);
