### Title
`SignableTransaction::new` omits the OP_RETURN data output from the weight/vbyte fee calculation, underpaying the intended fee rate — ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
This is the analog of M-14: a rate/fee formula whose quantity omits a term that the caller's inputs contribute. In M-14, `util = borrows / (liquidity - reserves + borrows)` was implemented without subtracting `reserves`, skewing the rate downward. Here, `calculate_weight_vbytes` computes the transaction vsize over `payments` (plus optional change) only, while `SignableTransaction::new` appends an `OP_RETURN` output carrying up to 80 bytes of caller-supplied `data` to `tx_outs` *before* computing the fee. The data output's weight is never included in `needed_fee`, so the transaction pays `fee_per_vbyte` over a smaller-than-actual vsize — the realized fee rate is strictly lower than the rate the caller specified.

### Finding Description
`SignableTransaction::new` pushes the `OP_RETURN` output to `tx_outs` when `data` is supplied (send.rs:194-202), but then calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` (send.rs:204) — a helper that builds a mock transaction containing only `payments` and an optional change output (send.rs:68-99). The data output is absent from the mock. The same omission occurs in the change branch: `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:225-226) again ignores `data`. Both `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) and the minimum-relay-fee check `needed_fee < DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` (send.rs:211) therefore use a vsize that is too small.

### Impact Explanation
When a change output is created, the actual fee paid equals `fee_with_change` exactly (`change = input_sat - payment_sat - fee_with_change`, send.rs:228-233), so the signed transaction achieves a fee rate below `fee_per_vbyte` — the same class of consequence as M-14's under-computed interest rate (a formula producing a systematically lower value because a term is missing from the quantity). Concretely: with an 80-byte data output, roughly 22 extra vbytes (~89 bytes serialized) go unfunded. If `fee_per_vbyte` was chosen near the minimum relay rate, the true fee rate can fall below `DEFAULT_MIN_RELAY_TX_FEE` while the undercounted check at send.rs:211 still passes, producing a transaction the default mempool will not relay — funds locked by this multisig are not spendable via the produced transaction until it is re-signed.

### Likelihood Explanation
`data` is a public, caller-controlled input (up to 80 bytes) passed straight into `SignableTransaction::new`; any party that can cause the coordinator to attach an OP_RETURN reaches this path without privileged access. The error is deterministic and proportional to the data size, so it triggers on every transaction that includes both `data` and a change output — no adversarial timing or collusion is required.

### Recommendation
Include the data output in the fee/vsize accounting: either pass the fully-constructed `tx_outs` (including the OP_RETURN output) into `calculate_weight_vbytes`, or append a zero-valued `TxOut` with the `ScriptBuf::new_op_return` script to the mock transaction at send.rs:85-94 whenever `data.is_some()`. After computing `fee_with_change`, recompute the change value against the corrected fee so the realized rate matches `fee_per_vbyte`.
