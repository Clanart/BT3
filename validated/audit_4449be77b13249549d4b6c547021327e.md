### Title
Distribution precompile query methods accept native token value without validating or refunding it, permanently locking sent funds - (File: precompiles/distribution/distribution.go)

### Summary
The `distribution` precompile's `Execute` dispatcher forwards `value` to several read-only/query handlers (`rewards`, `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) without calling `pcommon.ValidateNonPayable(value)` and without ever consuming/refunding the value via `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei`, unlike the payable transaction methods (`sendNative`, `wasmd.execute`) which correctly process or reject `value`.

### Finding Description
`PrecompileExecutor.Execute` in the distribution precompile dispatches by method name [1](#0-0) . State-mutating methods either call `pcommon.ValidateNonPayable(value)` (e.g. `WithdrawValidatorCommissionMethod`) or pass `value` into handlers that call `pcommon.HandlePaymentUsei`/`HandlePaymentUseiWei` to properly account for/refund transferred wei (as seen in `bank.sendNative` and `wasmd.execute`) [2](#0-1) [3](#0-2) .

However, the query-style branches — `RewardsMethod`, `ParamsMethod`, `ValidatorOutstandingRewardsMethod`, `ValidatorCommissionMethod`, `ValidatorSlashesMethod`, `DelegationRewardsMethod`, `DelegatorValidatorsMethod`, `DelegatorWithdrawAddressMethod`, `CommunityPoolMethod` — simply call their handler functions with `value` passed through but perform no `ValidateNonPayable` check and no payment/refund handling [4](#0-3) . This is explicitly documented in the integration test notes: "`distribution.rewards` accepts value (no non-payable check)" [5](#0-4) .

In the EVM call flow, when a caller attaches `msg.value` to a precompile call, the EVM's core call logic transfers that value (as usei/wei balance) into the precompile's address *before* invoking the precompile's `Run`/`RunAndCalculateGas`/`Execute` function — this is standard go-ethereum/Sei value-transfer semantics, independent of what the precompile logic does. This is exactly why the `bank` and `wasmd` payable functions must explicitly call `HandlePaymentUsei`/`HandlePaymentUseiWei` to "refund payer because the following precompile logic will debit the payments from payer's account" [6](#0-5) . If a precompile handler does not perform this refund/accounting step, the wei/usei credited to the precompile's associated Sei address remains stuck there permanently, because there is no mechanism to spend or withdraw funds from a precompile's own address.

This mirrors the reported Allo `registerRecipient` bug class: a payable-reachable code path silently fails to forward/account for attached native value to the logic that would otherwise use or refund it, resulting in funds being stranded at an address the caller cannot reasonably recover.

### Impact Explanation
Any unprivileged EVM caller can send a transaction to the distribution precompile (`0x0000000000000000000000000000000000001007`) invoking `rewards`, `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, or `communityPool` with a non-zero `value`. The call succeeds (no revert), but the attached usei/wei is permanently locked in the precompile's associated account with no code path to move it out — a direct, irreversible loss of user funds. This satisfies the "permanent freezing" / "concrete fund loss" criteria.

### Likelihood Explanation
Trivially reachable: a single standard EVM transaction from any address with sufficient balance, using the standard JSON-RPC/`eth_sendRawTransaction` surface, calling a published, public precompile ABI method with `value` set. No special privileges, no delegatecall/static-call bypass required — the call succeeds because these are meant to be called normally as queries; the only unusual part is attaching value, which many wallets/contracts might do inadvertently if these methods are (or become) marked payable in tooling, or an attacker can do deliberately to grief users into locking funds, or simply as a self-inflicted loss.

### Recommendation
Add `pcommon.ValidateNonPayable(value)` checks to all query-style branches in `distribution.Execute` (`rewards`, `params`, `validatorOutstandingRewards`, `validatorCommission`, `validatorSlashes`, `delegationRewards`, `delegatorValidators`, `delegatorWithdrawAddress`, `communityPool`) so that any attached value causes an immediate revert (consistent with `WithdrawValidatorCommissionMethod`'s handling), preventing funds from ever being transferred into the precompile address in the first place. Audit other precompiles (e.g. `staking`, `gov`, `oracle`) for the same missing-`ValidateNonPayable` pattern on non-payment-handling methods.

### Proof of Concept
1. Call the distribution precompile at `0x0000000000000000000000000000000000001007` via `eth_sendRawTransaction`, invoking `rewards(...)` (or any of `validatorOutstandingRewards`, `communityPool`, etc.) with `value: <non-zero wei amount>` and a real EOA sender.
2. The EVM core call logic transfers `value` (converted to usei/wei) into the precompile's backing Sei account balance as part of standard `CALL` value-transfer semantics.
3. `PrecompileExecutor.Execute` routes to the corresponding handler (e.g. `p.rewards(ctx, method, args)`), which never calls `ValidateNonPayable` nor `HandlePaymentUsei`/`HandlePaymentUseiWei` [7](#0-6) .
4. The transaction succeeds; the query result is returned normally, but the transferred value remains credited to the precompile address's balance with no method exposed anywhere in the codebase to withdraw or reassign it — permanently locking the sender's funds.

func HandlePaymentUsei(ctx sdk.Context, precompileAddr sdk.AccAddress, payer sdk.AccAddress, value *big.Int, bankKeeper putils.BankKeeper, evmKeeper putils.EVMKeeper, hooks *tracing.Hooks, depth int) (sdk.Coin, error) {
	usei, wei := state.SplitUseiWeiAmount(value)
	if !wei.IsZero() {
		return sdk.Coin{}, fmt.Errorf("selected precompile function does not allow payment with non-zero wei remainder: received %s", value)
	}
	coin := sdk.NewCoin(sdk.MustGetBaseDenom(), usei)
	// refund payer because the following precompile logic will debit the payments from payer's account
	// this creates a new event manager to avoid surfacing these as cosmos events
	if err := bankKeeper.SendCoins(ctx.WithEventManager(sdk.NewEventManager()), precompileAddr, payer, sdk.NewCoins(coin)); err != nil {
		return sdk.Coin{}, err
	}
