## Title
`GitStore.discardChanges` permanently discards a file's content even when the Trash backup for that file fails - (File: `app/src/lib/stores/git-store.ts`)

### Summary
`GitStore.discardChanges` moves each file to be discarded into the OS Trash before checking it out of the index/HEAD, but the paths that will actually be checked out (`pathsToCheckout`/`pathsToReset`) are queued unconditionally, regardless of whether the Trash move for that file succeeded. This mirrors the `InitialETHCrowdfund.batchContributeFor` bug pattern: a piece of accounting state (`ethAvailable` there, `pathsToCheckout`/`pathsToReset` here) is mutated before/independently of confirming the corresponding sub-operation actually succeeded, so a failure in one step silently loses value the caller expected to be preserved.

### Finding Description
`discardChanges` iterates over the files to discard: [1](#0-0) 

For every file, if the move to Trash (`this.shell.moveItemToTrash`) throws:
- if `askForConfirmationOnDiscardChangesPermanently` is `true`, the function throws a `DiscardChangesError` and aborts.
- if it is `false` (the common/default path), the catch block only does something for `AppFileStatusKind.Untracked` files (deletes them with `rm`). For any other status kind (in particular `Modified`), the catch block does nothing at all.

Regardless of which branch was taken - and regardless of whether the Trash move even succeeded - execution falls straight through to: [2](#0-1) 

which unconditionally pushes the file's path into `pathsToCheckout` and `pathsToReset`. These arrays are later used to perform the actual destructive operation: [3](#0-2) 

`resetPaths` + `checkoutIndex` overwrite the working-directory file with whatever is in the index/HEAD - i.e., they discard the user's uncommitted edits. Because the queuing of `pathsToCheckout`/`pathsToReset` is not conditioned on the Trash move having succeeded for a `Modified`/tracked file, a Trash failure results in the user's changes being wiped from disk with **no backup copy ever created**, silently defeating the entire purpose of the "move to Trash first" step described in `docs/technical/discard-changes.md`: [4](#0-3) 

This is structurally identical to the crowdfund bug: `ethAvailable -= args.values[i]` was performed before confirming `contributeFor` succeeded; here, the file is queued for irreversible checkout before confirming the "backup" (trash) step succeeded.

### Impact Explanation
The corrupted value is the set of paths queued for `checkoutIndex`/`resetPaths` - it is not filtered to exclude files whose Trash backup failed. The result is silent, permanent loss of uncommitted user work: the file is neither in Trash (recoverable) nor does it retain the user's edits (it's reset to HEAD/index content). Existing guards do not stop this path because:
- The `try`/`catch` around `moveItemToTrash` only re-throws when `askForConfirmationOnDiscardChangesPermanently === true`; the default/common case swallows the error for non-Untracked files.
- There is no check after the catch block that skips adding a file's path to `pathsToCheckout`/`pathsToReset` if its trash step failed.

This falls under "silent corruption of what the user commits" in spirit (loss of uncommitted content the user would otherwise have committed), triggered by any repository/environment condition that makes the Trash operation fail for a specific tracked file (e.g., filesystem/path restrictions, permissions, or platform-specific Trash API failures for particular filenames present in a cloned/fetched repository).

### Likelihood Explanation
This requires the Trash API to fail for a specific file while the rest of `discardChanges` proceeds normally - a real but conditional trigger (e.g., certain filenames/paths that a hostile repository can supply that a given OS/Trash implementation rejects, or a full/unwritable Trash). I was not able to fully confirm from the indexed code which filenames or environmental conditions reliably fail `shell.trashItem`/`moveItemToTrash` (the implementation in `app/src/lib/app-shell.ts` was found but not fully inspected in this session), so likelihood is uncertain and depends on OS-level Trash behavior rather than a guaranteed cross-platform trigger.

### Recommendation
Only queue a file's path into `pathsToCheckout`/`pathsToReset` if the corresponding Trash step (or the manual `rm` for untracked files) actually completed successfully; otherwise skip discarding that file and surface an error/warning to the user instead of silently proceeding to checkout.

### Proof of Concept
Conceptual (not executed - would need to be validated on a real OS to find a filename/path that reliably makes `shell.trashItem` throw):
1. Attacker publishes/pushes a repository containing a tracked file whose path or name is known to make the OS Trash API fail for some users (e.g., extremely long path near `MAX_PATH` on Windows, or a filesystem/permissions edge case).
2. Victim clones/fetches this repo, opens it in Desktop, and modifies that file.
3. Victim selects "Discard Changes" for that file with `askForConfirmationOnDiscardChangesPermanently` at its default (`false`).
4. `moveItemToTrash` throws internally; the catch block does nothing (file status is `Modified`, not `Untracked`).
5. Execution still reaches the unconditional `pathsToCheckout.push(file.path)` / `pathsToReset.push(file.path)`, and `resetPaths` + `checkoutIndex` overwrite the file with the HEAD/index version.
6. The user's edits are now gone with no Trash copy - unrecoverable loss.

I could not fully verify the exact filesystem condition that triggers a `moveItemToTrash` failure from the indexed contents of `app/src/lib/app-shell.ts`; a Devin session with full repo/file access would be needed to confirm a concrete reproducible trigger on a specific OS.

### Moving Files to Trash

Electron provides the [`shell.trashItem(fullPath)`](https://www.electronjs.org/docs/api/shell#shelltrashitempath)
