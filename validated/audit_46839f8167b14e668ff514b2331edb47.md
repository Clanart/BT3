### Title
Ed448 `Point::mul` discards the scalar's least-significant bits when `NUM_BITS % 4 != 0`, producing incorrect scalar multiplication - ([File: crypto/ed448/src/point.rs](crypto/ed448/src/point.rs))

### Summary

In `crypto/ed448/src/point.rs`, `impl Mul<Scalar> for Point` uses a 4-bit windowed scalar multiplication that only commits a window when `(i + 1) % 4 == 0`. The Ed448 scalar field has `NUM_BITS = 446` (the group order is ~2^446), and `446 % 4 == 2`. The final partial window — which holds the scalar's two least-significant bits — is accumulated into `bits` but never added into `res`. The result is that every scalar multiplication silently computes `(k - (k mod 4)) * P` instead of `k * P`. This is the same bug class as the Basin finding: a shift/window boundary error where a portion of a packed value is read from the wrong position — here, the tail bits are simply dropped instead of merged.

### Finding Description

```rust
for (i, mut bit) in other.to_le_bits().iter_mut().rev().enumerate() {
  bits <<= 1;
  let mut bit = u8_from_bool(&mut bit);
  bits |= bit;
  bit.zeroize();

  if ((i + 1) % 4) == 0 {
    if i != 3 {
      for _ in 0 .. 4 {
        res = res.double();
      }
    }
    // select table[bits], res += add_by
    bits = 0;
  }
}
```

`i` counts over the bit-reversed scalar, MSB first. A window is only flushed when `i + 1` is a multiple of 4. For a 446-bit scalar the last flush happens at `i = 443`; the iterations `i = 444` and `i = 445` load the scalar's two LSBs into `bits` and the loop exits without ever adding `table[bits]` to `res`. Just as the Basin `storeBytes16()` code discarded the `shl()` and read the wrong half of the slot, this code fails to flush the final partial window, dropping bits 0–1 of every scalar.

### Impact Explanation

`Point * Scalar` is wrong for ~3/4 of all scalars (any scalar not divisible by 4). Because this is the group-law multiplication used by everything built on the Ed448 ciphersuite — nonce commitments `G * r`, public keys `G * x`, Schnorr/DLEq verification terms `s * G`, `c * A`, FROST `calculate_share`/`verify` math — the consequences are:

- Honest Schnorr/DLEq proofs over Ed448 fail verification: the verifier recomputes `f(s)·G - f(c)·A` where `f(k) = k & !3`, while the prover transcripted `r·G`; the challenge mismatches whenever truncation interacts non-linearly with `r + c·a`.
- It constitutes an incorrect verifier formula: equality checks between truncated multiplications are not equivalent to the true group equation, so any proof system relying on `s·G = R + c·A` over Ed448 is operating on a different relation than specified. Truncated multiplication is not a homomorphism (`f(a·b) ≠ f(a)·f(b)`), so verification equations are mathematically inconsistent, not merely relocated.

### Likelihood Explanation

The bug triggers deterministically on every Ed448 scalar multiplication — no attacker effort is required to reach it. Untrusted bytes fed to `read_G`/`read_F`/proof `read` functions for the Ed448 ciphersuite, or any verify API, immediately exercise the broken code path. Reachability from public inputs is total; the only caveat is that the dominant effect is correctness/availability breakage of the Ed448 suite rather than a clean forgery, consistent with the Basin finding being downgraded to Medium.

### Recommendation

Flush the residual window after the loop, or pad the iteration to a multiple of 4. For example, after the `for` loop:

```rust
let remaining = usize::try_from(Scalar::NUM_BITS).unwrap() % 4;
if remaining != 0 {
  for _ in 0 .. remaining {
    res = res.double();
  }
  // conditional-select table[bits] and add to res
}
```

Alternatively, iterate over `NUM_BITS.div_ceil(4)` windows explicitly and mask/zero-pad the final window so no bits are dropped. Add a test multiplying by small scalars (e.g., `3·G`, `5·G`) and by `Scalar::ONE + Scalar::ONE + Scalar::ONE`, plus known-answer vectors with scalars whose low bits are set.

### Proof of Concept

1. Instantiate `Point::generator()` in `crypto/ed448`.
2. Compute `G * Scalar::from(3u64)`.
3. Expected: `G + G + G`. Actual: the window containing bits `0b011` is loaded at `i = 444, 445`, never flushed, so the result is `Point::identity()` — the low bits `11` are dropped.
4. Similarly `G * Scalar::ONE` returns identity instead of `G` for a 446-bit scalar field, since the only set bit lands in the discarded tail window.
5. Any Schnorr/DLEq proof generated over Ed448 and verified through this `Mul` implementation fails or evaluates a truncated relation, corrupting the "oracle" (verification result) exactly as the corrupted pump storage corrupted oracle values in Basin.
