### Title
OP_RETURN data output excluded from fee/weight accounting, over-crediting change with funds reserved for the fee - ([File: networks/bitcoin/src/wallet/send.rs])

### Summary
When a `SignableTransaction` is built with `data` (an OP_RETURN output), the output is pushed onto `tx_outs` but `calculate_weight_vbytes` is only ever called with `payments`, so the data output's weight is never counted. The analogous accounting error to the Hyperdrive report — an amount that should have been carved out (here, fee) remains inside a spendable balance (here, the change output).

### Finding Description
In `SignableTransaction::new`, the OP_RETURN output is appended to `tx_outs` before the fee and change are computed: [1](#0-0) 

Both weight calculations, however, pass `payments` (which does not include the data output): [2](#0-1) [3](#0-2) 

`calculate_weight_vbytes` builds the dummy transaction solely from `payments` and an optional `change` script, so an OP_RETURN of up to 80 bytes (plus output overhead) is invisible to `needed_fee`: [4](#0-3) 

The change output is then credited `input_sat - payment_sat - fee_with_change`, where `fee_with_change` is missing the data output's vbytes — exactly the report's pattern of "the fee remains inside the spendable pool": [5](#0-4) 

### Impact Explanation
- `needed_fee()` under-reports the true required fee; the processor's `needed_fee`/`prepare_send` amortization path relies on this value to subtract fees from payments.
- The transaction's *effective* feerate is `fee_per_vbyte * vbytes_counted / vbytes_actual`, i.e. strictly below the requested rate. For `fee_per_vbyte` near the minimum relay bound, the produced transaction can fall below `DEFAULT_MIN_RELAY_TX_FEE` and fail to propagate, leaving inputs unspendable until reconstructed — reachable by any caller supplying `data` and low fee rate.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses the same incomplete `weight`, so the size bound can be exceeded by the omitted output's weight.
- Over-credited change is burned nowhere — it is simply mislabeled, so the inconsistency between `needed_fee` (used for planning) and `fee()` (actual) is a real accounting discrepancy.

### Likelihood Explanation
Any call to `SignableTransaction::new` with `data: Some(_)` and `change: Some(_)` triggers it; the magnitude is `fee_per_vbyte * (vbytes of OP_RETURN output)`, roughly `fee_per_vbyte * ~35` for an 80-byte payload. No malicious validator or collusion is needed — it is deterministic from public inputs.

### Recommendation
Include the OP_RETURN output in the transaction built inside `calculate_weight_vbytes` (pass the full output list, or pass `data` through), so both `vbytes`/`vbytes_with_change` and the `weight` used for `MAX_STANDARD_TX_WEIGHT` reflect the real transaction. Alternatively, assert `data.is_none()`'s weight contribution by adding a fixed worst-case overhead when `data` is present.

### Proof of Concept
Construct a `SignableTransaction` with `inputs` of sufficient value, `payments`, `change = Some(addr)`, and `data = Some(vec![0; 80])`. Observe:
1. `tx.output` contains 3+ outputs including the 89-byte OP_RETURN output, yet `needed_fee()` equals `fee_per_vbyte * vsize(tx_without_data_output)`.
2. The change output value equals `input_sat - payment_sat - needed_fee`, i.e. it absorbs the sats that should have paid for the OP_RETURN weight.
3. `tx.fee() / tx.vsize()` is strictly less than `fee_per_vbyte`, and with `fee_per_vbyte` at the minimum relay bound, `tx.fee()` is below `DEFAULT_MIN_RELAY_TX_FEE * vsize / 1000`, so the signed transaction is rejected by relay while `needed_fee()` claimed it was adequate.
