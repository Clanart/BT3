## Title
Tron `IntentGatewayV2.placeOrder` credits escrow using the pre-transfer declared amount instead of the actually-received balance, allowing fee-on-transfer tokens to inflate escrow bookkeeping beyond real token holdings — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The seed report's core defect is a **preview/actual mismatch**: a value quoted or computed before a fee is applied is later used as if it were the final, fee-adjusted amount, letting accounting drift from reality. The Tron deployment of `IntentGatewayV2.placeOrder` reproduces exactly this class of bug in its escrow bookkeeping: it computes the protocol-fee-reduced input amount from the **caller-declared, pre-transfer** `order.inputs[i].amount` and credits that value to `_orders[commitment][token]`, without ever reconciling it against the token balance the contract actually received.

### Finding Description
In the canonical EVM contract (`evm/src/apps/IntentGatewayV2.sol`), `placeOrder` is careful to record the **actual** received balance before computing the protocol fee: [1](#0-0) 
```
} else {
    for (uint256 i; i < inputsLen;) {
        ...
        uint256 balBefore = IERC20(token).balanceOf(address(this));
        IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
        ...
```
Only *after* this actual-balance correction does it compute `protocolFee`/`reducedAmount` (Phase 2) and credit escrow (Phase 3) — so fee-on-transfer tokens can never cause an over-credit.

The Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) inverts this ordering. It computes `reducedInputs[i].amount` from `order.inputs[i].amount` (the raw, caller-declared amount) **before** any token transfer happens: [2](#0-1) 

Then, in the non-predispatch path, it transfers `order.inputs[i].amount` via `safeTransferFrom` and credits escrow with the **pre-computed** `reducedInputs[i].amount` — with no balance-before/after check to verify how much was actually received: [3](#0-2) 
```
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            ...
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```
For a fee-on-transfer (or otherwise balance-lossy) ERC-20, the contract's real token balance increases by less than `order.inputs[i].amount`, but `_orders[commitment][token]` is credited with `order.inputs[i].amount - protocolFee`, a value derived from the gross declared amount, not the net received amount. This is the same class of defect the seed report flags: a fee-inclusive figure (`previewDeposit`) diverging from the fee-exclusive one actually realized on-chain (`deposit`) — here the direction is reversed but the effect is the same: the escrow ledger is decoupled from the contract's actual asset backing.

Note the predispatch branch of the same function *does* perform a dust check against the call-dispatcher's real balance (`uint256 dust = balance - requiredAmount;`), which underscores that the missing check in the simple-transfer branch is an inconsistency/oversight rather than a deliberate design choice.

### Impact Explanation
`_orders[commitment][token]` is the ledger the contract trusts for every subsequent payout path: `withdraw()` (invoked from same-chain `cancelOrder`, cross-chain `RefundEscrow`, and `RedeemEscrow` via `onAccept`) pays out based on this stored value, not on a live balance check. If the recorded escrow for a commitment exceeds what was actually contributed to the pooled token balance, the shortfall is covered by tokens belonging to other users' orders. An attacker can therefore use a fee-on-transfer token as an order input, inflate their own escrow-ledger entry, and redeem or cancel to receive more tokens than they deposited — draining the shared pool at the expense of other users. This is a direct loss-of-funds / wrong-beneficiary-amount vulnerability reachable by any unprivileged caller through the public `placeOrder` entry point, with no relayer, prover, or admin involvement required.

### Likelihood Explanation
The precondition is simply configuring or being permitted to use a fee-on-transfer ERC-20 as an order input on the Tron deployment — no privileged role, malicious relayer, or state-proof manipulation is needed. The bug is triggered purely by calling the public `placeOrder(order, graffiti)` function with such a token, making exploitation straightforward once a suitable token exists in the input set. The corresponding EVM contract's already-fixed pattern (balance-diff correction) shows the team is aware fee-on-transfer tokens are a real concern for this contract family, making the omission in the Tron fork a genuine regression rather than an accepted design tradeoff.

### Recommendation
Mirror the EVM contract's fix in the Tron contract: capture `balanceOf(address(this))` before and after each `safeTransferFrom` in the non-predispatch branch of `placeOrder`, and compute `order.inputs[i].amount` (and therefore `reducedInputs[i].amount` and the commitment) from the actual received delta rather than the caller-declared amount — exactly as `evm/src/apps/IntentGatewayV2.sol` lines 281-298 already do.

### Proof of Concept
1. Governance/deployment registers a fee-on-transfer ERC-20 (e.g., 5% transfer fee) as a valid input token on the Tron `IntentGatewayV2`.
2. Attacker calls `placeOrder` with `order.inputs[0] = {token, amount: 1000e18}` and no predispatch call.
3. Contract fee logic computes `protocolFee = 1000e18 * bps/10000` and `reducedAmount = 1000e18 - protocolFee` **before** any transfer occurs (see `evm/tron/contracts/apps/IntentGatewayV2.sol:356-359`).
4. `safeTransferFrom(msg.sender, address(this), 1000e18)` moves only `950e18` into the contract due to the token's transfer fee.
5. `_orders[commitment][token] += reducedAmount` (≈ `999.5e18` for a 5bps protocol fee) is credited — ~`49.5e18` more than the contract actually received for this order.
6. Attacker cancels the order (same-chain path) or waits for a fill/redeem; `withdraw()` pays out based on the inflated `_orders[commitment][token]` value, taking the excess from token balance contributed by other users' escrowed orders.

I was not able to view the body of `withdraw()` itself in the available index (only its call sites), so the exact arithmetic of the payout/decrement logic is not directly confirmed here — this should be verified in a live session before finalizing severity, but the escrow-credit inflation at `placeOrder` time is directly evidenced in the code shown above and is sufficient on its own to break the amount-consistency invariant between the ledger and the contract's real holdings.
