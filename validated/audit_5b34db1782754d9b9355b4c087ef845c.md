Based on my review of the intent-gateway cross-chain cancellation path, I found a direct structural analog to the reported bug.

### Title
Zero-amount order input permanently blocks source-chain cancellation (`UnknownOrder` revert) - (evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
The `AddCollateral` bug pattern — a permissionless zero-amount entry that later trips a strict "amount must be nonzero" guard and blocks the legitimate settlement action — has a structural analog in `_cancelFromSource`. The function checks every input token's escrow balance with an undiscriminated `== 0` existence test, which reverts the *entire* cancellation if even one input token has zero (or already-zero) escrow, rather than skipping that token.

### Finding Description
`_cancelFromSource` in [1](#0-0)  iterates over every `order.inputs[i]` and requires `_orders[commitment][token] != 0`, reverting with `UnknownOrder` for the whole call if any single input token's escrowed balance is zero:

```solidity
for (uint256 i; i < inputsLen;) {
    if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();
    ...
}
```

This mirrors the OtterSec pattern precisely: elsewhere in the same contract, `_withdraw` treats a zero token amount as a no-op (`if (amount == 0) continue;`) at [2](#0-1) , showing the codebase's own convention is that a zero-amount leg should be skipped, not treated as fatal. `_cancelFromSource`, however, does not skip — it uses the same `== 0` test as an "order exists" check rather than a "should this token be processed" check, so a single zero-escrow input (e.g. an order placed with a zero-amount input token, since no visible input-amount validation exists in the reviewed code) makes the whole multi-token order's source-chain cancellation permanently unreachable.

### Impact Explanation
If a user's cross-chain order contains one input token whose escrowed balance is zero — either because it was placed with `amount == 0` (no check was found preventing this in the reviewed code path) or because prior partial processing zeroed it — `_cancelFromSource` can never succeed for that order commitment. The user is forced onto `_cancelFromDest`, which does not have this defect, but that path can only be triggered after `order.deadline` has passed and depends on interacting with the destination chain first; if the user relies on the source-side cancel/refund flow, their remaining legitimately-escrowed tokens for other input assets become unreachable via that entrypoint, matching the "AddCollateral" report's core failure mode: a strict `> 0`/`== 0` guard on one item blocking recovery of otherwise-valid escrowed funds.

### Likelihood Explanation
Any user (or an order author themselves) can construct an order with a zero-amount input leg — no privileged actor, relayer, or prover involvement is required, satisfying the "unprivileged attacker/self-inflicted footgun" bar. The exact conditions under which `placeOrder` accepts a zero-amount input are not verified from the code visible in this scan; I was not able to inspect `placeOrder`'s validation logic (`evm/src/apps/intentsv2/IntentGatewayV2.sol`) within the index, so whether this path is fully reachable end-to-end depends on that unverified validation.

### Recommendation
In `_cancelFromSource`, skip tokens whose escrowed amount is zero (mirroring `_withdraw`'s `if (amount == 0) continue;`) instead of reverting the entire cancellation, and/or add an explicit `amount > 0` check on every `order.inputs[i].amount` in `placeOrder` to prevent zero-amount legs from being escrowed at all.

### Proof of Concept
1. User calls `placeOrder` with `order.inputs = [ {token: A, amount: X}, {token: B, amount: 0} ]` (assuming no `> 0` validation exists on placement — unverified in this scan).
2. Order expires unfilled.
3. User calls `_cancelFromSource`; the loop reaches `i` for token `B`, finds `_orders[commitment][B] == 0`, and reverts with `UnknownOrder`, even though token `A`'s escrow of `X` is still recoverable.
4. User cannot recover token `A` via the source-cancel path for this order; the only remaining path is `_cancelFromDest`, which has different authorization/timing requirements. [1](#0-0) [3](#0-2)

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }
