## Analysis

The report's underlying flaw is a *security check that only validates part of a combined result*, letting an internal component silently fail/malform while the overall check still reports success. The closest structural analog in GitHub Desktop is the containment check inside `_resolveWithin()`.

### Title
Prefix-based path-containment check in `_resolveWithin()` allows escaping the repository root via a deep-link `filepath` - (File: app/src/lib/path.ts)

### Summary
`resolveWithin()` (backed by `_resolveWithin`) is Desktop's sole gate against path traversal for attacker-influenced file paths. It resolves an untrusted relative path against a root, then decides containment with a raw string `startsWith()` comparison of the two `realpath()` results. [1](#0-0)  Just as the WebAuthn bug combined two nested operations and only checked the outer result for success (allowing a shifted/malformed hash to be accepted as valid), `_resolveWithin` combines two independently-resolved path strings and validates their relationship with an incomplete comparison, letting a sibling path that merely shares a name prefix be accepted as "inside" the root.

### Finding Description
`_resolveWithin` computes `realRoot` and `realResolved` via two separate `realpath()` calls and then does:
```
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

`String.prototype.startsWith` has no path-boundary awareness: `"/Users/foo/repo-evil/secret".startsWith("/Users/foo/repo")` is `true` even though `repo-evil` is a sibling directory, not a subdirectory, of `repo`. There is no check that the character following `realRoot` in `realResolved` is a path separator (or that they are exactly equal). This is the “malformed-but-accepted” result: the containment check succeeds even though the resolved path is *not* actually within the root.

This function is the app's controlling guard for attacker-influenced paths in at least two real call sites:

- `Dispatcher.openRepositoryFromUrl`, which handles the `filepath` query parameter of the `open-repository-from-url` deep link (`x-github-client://openRepo/...?filepath=...`) — fully attacker-controlled data reachable by a link the user clicks: [3](#0-2) 
The deep link parser only rejects filepaths that are literally absolute or contain "invalid chars" for branch names; it does not block `..` segments or sibling-prefix names in `filepath`: [4](#0-3) 

- `AppStore` Copilot conflict-resolution flow, which uses the same guard before writing model-resolved content to disk: [5](#0-4) [6](#0-5) 

### Impact Explanation
If a repository the victim has cloned contains (or an attacker can arrange to exist) a sibling directory whose name has the repository's directory name as a prefix (e.g., repo at `/Users/victim/repo` and a sibling `/Users/victim/repo-secrets` or `/Users/victim/repository`), a crafted deep link's `filepath` parameter can resolve into that sibling and be treated as "inside" the repo, causing Desktop to reveal (`shell.showItemInFolder`) a path outside the intended repository boundary. In the Copilot conflict-resolution path, the same prefix bypass would let file *writes* land in a sibling directory outside the repository root, which is a stronger primitive (arbitrary file write outside the repo) if `resolution.path` can be steered to a prefix-colliding value.

### Likelihood Explanation
The `filepath` deep-link vector requires only a link click and a plausible directory layout, which is common for developers who keep sibling projects with overlapping name prefixes (`repo`, `repo-fork`, `repo.wiki`, `repo-old`, etc.) or where the attacker can create such a sibling ahead of time (e.g., via a `.gitignore`d build/scratch folder or a previous clone). It is “Medium” likelihood: it depends on a directory-naming coincidence rather than being universally exploitable, mirroring the original report's own “Medium Risk” framing where exploitation is real but conditional. The existing unit tests validate correct traversal and symlink cases but do not test the sibling-prefix-collision case, so the gap is untested and unguarded. [7](#0-6) 

### Recommendation
Change the containment check in `_resolveWithin` to be boundary-aware, e.g.:
```ts
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```
This mirrors the WebAuthn fix's recommendation to make each step's result independently and completely validated, rather than relying on an imprecise combined check.

### Proof of Concept
1. Victim clones a repo to `/Users/victim/repo`, and separately has (or an attacker creates) `/Users/victim/repo-evil/secret.txt` (e.g., a leftover scratch folder, or a directory the attacker can influence to exist, such as via a previous unrelated clone/download).
2. Attacker sends the victim a link: `x-github-client://openRepo/https://github.com/victim/repo?filepath=../repo-evil/secret.txt`.
3. `parseAppURL` accepts the filepath since it isn't absolute and doesn't match the invalid-char check for branches. [8](#0-7) 
4. `openRepositoryFromUrl` calls `resolveWithin(repository.path, filepath)`; `isAbsolute(filepath)` is false so the traversal proceeds to `_resolveWithin`. [9](#0-8) 
5. `resolve(normalizedRoot, normalizedRelative)` yields `/Users/victim/repo-evil/secret.txt`; `realResolved.startsWith(realRoot)` evaluates true because `"/Users/victim/repo-evil/secret.txt".startsWith("/Users/victim/repo")` is `true`, so the function returns the out-of-repo path as valid. [1](#0-0) 
6. Desktop calls `shell.showItemInFolder(resolved)` on the out-of-repository file, disclosing/revealing content outside the cloned repository boundary that the user did not intend to expose via this link.

    } else if (branch !== null) {

        shell.showItemInFolder(resolved)
      } else {
        log.error(

    })
