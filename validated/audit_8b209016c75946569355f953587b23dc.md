Based on the investigation, the strongest local analog to the TON `WithdrawFunds` gas-field draining bug is in the legacy Tron `IntentGatewayV2.withdraw()` path, where escrow release performs the external transfer *before* validating/decrementing the tracked escrow balance — the same "unvalidated value paid out without being properly checked against what is actually owed" pattern as the original report.

### Title
Escrow release transfers funds before validating/decrementing tracked balance in `withdraw()` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.withdraw()` on Tron pays out `body.tokens[i].amount` to the beneficiary and only afterward decrements `_orders[body.commitment][token]`, and its pre-transfer guard only checks that the escrow slot is non-zero (`_orders[body.commitment][token] == 0`) rather than validating `amount <= _orders[body.commitment][token]` before the transfer executes. [1](#0-0) 

### Finding Description
`withdraw()` is invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` message kinds. For each token entry in the `WithdrawalRequest`, the function checks only that the escrow slot is non-zero, then immediately performs the external transfer (native `.call{value: amount}` or `token.call(transfer(...))`), and *afterwards* subtracts `amount` from `_orders[body.commitment][token]`. [2](#0-1) 

This is the same class of defect the TON report flagged: a value that determines an outbound transfer (`forward_milliton`/`gas_transfer` there, `amount` here) is spent/paid without first being properly bound to what was actually reserved/escrowed for that specific action. The later, patched version of this logic in `IntentsBase._withdraw()` fixes exactly this ordering — it computes `escrowed`, updates `_orders[...]` to `escrowed - amount` (reverting on underflow if `amount > escrowed`) **before** making the external call: [3](#0-2) 

The Tron contract's `withdraw()` also does not track/return the ERC-20 boolean return value beyond a raw `.call` success check (`token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`), so any token whose `transfer()` implementation does not strictly enforce sufficient sender balance before returning, or that triggers an external hook during the transfer, executes its side effects while `_orders[body.commitment][token]` is still un-decremented. [4](#0-3) 

### Impact Explanation
If the effects-before-interactions ordering is bypassed (e.g., via a token contract with transfer hooks that reenter the gateway, or a message path that races two withdrawal deliveries for the same commitment/token before the first's decrement lands), the un-decremented escrow slot can be read/paid a second time, resulting in the contract paying out more than was actually escrowed for that order — a direct, unauthorized loss of pooled TRC-20/native funds belonging to other users' orders, matching the "stealing or loss of funds" / "double-settlement" impact classes.

### Likelihood Explanation
The order creator fully controls which token address is used as `order.inputs[i].token` in `placeOrder`, so an attacker can select an ERC-20/TRC-20-like implementation with transfer-time callback behavior for their own order without needing any malicious relayer, prover, or admin — the withdrawal delivery itself is a normal, permissionless part of the settlement flow (`onAccept` triggered by the host processing a legitimately authenticated cross-chain message). The fact that the codebase's newer `IntentsBase._withdraw()` already fixes the ordering strongly suggests this was a known, real weakness in the legacy Tron contract rather than a hypothetical concern.

### Recommendation
Apply the same fix already present in `IntentsBase._withdraw()` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: read the escrowed amount into a local variable, decrement `_orders[body.commitment][token]` (which will revert on underflow if `amount` exceeds what was escrowed) **before** performing the external native/token transfer, and check the boolean return value of `transfer()` rather than only the low-level call success.

### Proof of Concept
1. Attacker deploys a token `T` whose `transfer()` implementation invokes a callback/hook on the recipient before or during balance updates (or otherwise executes side effects without atomically enforcing sender-balance sufficiency).
2. Attacker calls `placeOrder` escrowing `T` as `order.inputs[0].token` with amount `A`, recorded as `_orders[commitment][T] = A`. [5](#0-4) 
3. A solver fills the order cross-chain; the destination dispatches `RedeemEscrow` back to the source chain, which `onAccept()` routes to `withdraw()`.
4. `withdraw()` sees `_orders[commitment][T] != 0`, calls `T.transfer(beneficiary, A)`. Because the decrement to `_orders[commitment][T]` has not yet executed, `T`'s callback (or a racing second delivery) can trigger logic that reads/uses the still-nonzero escrow slot before it is zeroed, allowing more than `A` to be extracted for that commitment/token pair. [6](#0-5) 

Note: I could not find a second, independently-triggerable public entrypoint in this file that a reentrant call could hit mid-`withdraw()` to complete a concrete double-payout in one transaction — `onAccept`/`onGetResponse` are both `onlyHost`-gated, so full end-to-end exploitability depends on the specific token's callback semantics and/or a race between two legitimately authenticated withdrawal messages for the same commitment. This is flagged as the strongest **locally provable** ordering defect matching the report's bug class; a background engineering review should confirm whether any reachable path lets the un-decremented escrow slot be consumed twice before concluding full exploitability.
