### Title
Escrow withdrawal in `IntentGatewayV2.withdraw` permanently locks native-token payouts to contract beneficiaries with no receive/fallback - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw` (the internal function invoked by `onAccept` for both `RedeemEscrow` and `RefundEscrow` cross-chain messages) pays out escrowed native-token amounts to a `beneficiary` address with a raw `call{value: amount}("")` and reverts the entire withdrawal if that call fails, with no fallback path. This is the exact bug class from the external report (WETH/ETH sent to a contract without a receive path can permanently lock funds) — except here it's worse: the codebase already contains the correct mitigation pattern elsewhere (`WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`), but `IntentGatewayV2.withdraw` does not use it.

### Finding Description
`withdraw()` is reached from `onAccept` for both `RedeemEscrow` and `RefundEscrow` request kinds, which are the sole mechanisms for releasing escrowed order funds back to a beneficiary after cross-chain settlement or cancellation: [1](#0-0) 

Inside `withdraw`, when the escrowed token is the native asset (`token == address(0)`), the payout uses a bare low-level call and hard-reverts on failure: [2](#0-1) 

If `beneficiary` is a smart contract with no `receive()`/payable `fallback()` (e.g. a multisig, vault, or any non-payable contract wallet), the `call{value: amount}("")` fails, `InsufficientNativeToken()` is raised, and the whole ISMP message processing reverts. Since `_filled[body.commitment]` is only set (and `_orders[...]` only decremented) if the call succeeds, the escrowed native tokens remain locked in the contract with no alternative redemption path — the `WithdrawalRequest` body (commitment, tokens, beneficiary) is fixed by the authenticated cross-chain message and cannot be resubmitted with a different beneficiary.

This is materially different from how the codebase handles the identical class of problem in `WrappedHyperFungibleToken.onAccept`/`onPostRequestTimeout`, which explicitly try a native push first and, on failure, re-wrap and deliver the underlying WETH as an ERC-20 transfer instead of reverting: [3](#0-2) 

`IntentGatewayV2.withdraw` has no equivalent fallback for native-token beneficiaries.

### Impact Explanation
Any order whose native-token beneficiary (the depositor being refunded, or the solver being paid out) resolves to a contract without a payable receive path causes escrowed native-token funds to become permanently unrecoverable through the protocol's only settlement/refund path (`RedeemEscrow`/`RefundEscrow` via `onAccept`). This matches the bounty's "loss of funds" impact category: funds are irreversibly stuck in the contract rather than reaching the rightful beneficiary, with no retry mechanism since the beneficiary and commitment are baked into the authenticated cross-chain message.

### Likelihood Explanation
No malicious relayer, prover, or admin is required — any user or contract-based intent participant (e.g. someone using a smart-contract wallet, vault, or DAO treasury as their address) that places or fills a native-asset order can trigger this simply by being the natural beneficiary of a normal settlement or cancellation flow. This is a realistic, unprivileged, ordinary-usage path, not a contrived edge case, and the codebase already demonstrates awareness of and remediation for this exact bug class in `WrappedHyperFungibleToken`, but the fix was not applied to `IntentGatewayV2`.

### Recommendation
Mirror the `WrappedHyperFungibleToken` mitigation in `IntentGatewayV2.withdraw`: on failure of the native `call{value}`, fall back to wrapping the native asset (e.g. via WETH `deposit`) and delivering it to the beneficiary as an ERC-20 transfer instead of reverting the entire withdrawal, so escrowed funds can never become permanently stuck regardless of the beneficiary's contract type.

### Proof of Concept
1. A depositor (or solver) address that is a smart contract with no `receive()`/payable `fallback()` is set as the beneficiary of an order whose escrowed token is the native asset (`address(0)`).
2. The order is cancelled (`RefundEscrow`) or successfully filled and settled cross-chain (`RedeemEscrow`), causing the host to deliver an authenticated ISMP POST to `IntentGatewayV2.onAccept`.
3. `onAccept` calls `withdraw(body, isRefund)` per [1](#0-0) .
4. Inside `withdraw`, `beneficiary.call{value: amount}("")` fails because the contract cannot accept ETH, per [4](#0-3) , causing the transaction to revert with `InsufficientNativeToken()`.
5. Because there is no fallback path, this message can never be successfully re-processed with a different outcome — the escrowed native tokens for that commitment remain locked in `IntentGatewayV2` indefinitely.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }
