## Analysis

The OtterSec bug's core pattern: an instruction that pays out value derived from a shared/ambiguous state (pool notional) never checks a **discriminant that must match the specific instance the payout is being computed against** — so a caller can invoke the payout path under one identity/strategy while the underlying accounting belongs to a different one, extracting more value than was ever escrowed for that identity.

The direct local analog is in `IntentGatewayV2.sol`'s escrow-release path, which pays out an attacker-suppliable `amount` against an escrow balance gated only by a "non-zero" check rather than an exact-match check, combined with a source-authentication check that validates *any* known gateway instance rather than the specific chain the order actually names as its counterparty.### Title
`withdraw()` pays out an attacker-controlled amount to an attacker-controlled beneficiary without validating the request came from the order's actual destination or that the amount matches escrow — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` (lines 682-721) is the single sink for both `RedeemEscrow` (order filled) and `RefundEscrow` (order cancelled) cross-chain messages. It receives an attacker/sender-supplied `WithdrawalRequest{commitment, tokens[], beneficiary}` and pays out `tokens[i].amount` to `beneficiary` from the `_orders[commitment][token]` escrow. The only gate on the amount is `_orders[body.commitment][token] == 0` (non-zero check), not an equality/upper-bound check against the actual escrowed amount, and `authenticate()` (lines 289-294) only verifies that `request.source` is *some* known `IntentGatewayV2` instance — never that it equals the specific `order.destination` recorded in the commitment being drained. This mirrors the OtterSec Mango bug: a payout instruction that trusts caller-supplied notional/strategy data instead of binding it to the specific instance/strategy the escrow was created under.

### Finding Description
`authenticate()`:
```solidity
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
``` [1](#0-0) 

This only checks that `request.source` maps (via the `_instances` registry) to the `from` module address in the message — i.e., that the sender is *a* legitimate `IntentGatewayV2` deployment somewhere in the multi-chain fleet. It never checks `request.source == order.destination` for the specific `commitment` being redeemed.

`onAccept` routes both redeem and refund kinds through the same `withdraw()` with no additional binding to the order's true destination chain:
```solidity
if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
    authenticate(incoming.request);
    WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
    return withdraw(body, kind == RequestKind.RefundEscrow);
}
``` [2](#0-1) 

And `withdraw()` itself trusts the caller-supplied `amount` and `beneficiary` verbatim, gating only on non-zero balance rather than an exact match:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        ...
        _orders[body.commitment][token] -= amount;
        ...
    }
``` [3](#0-2) 

Because `commitment = keccak256(abi.encode(order))` is public data (any observer can read a placed `Order` from the `OrderPlaced` event) and is never re-derived or checked against the specific `request.source` chain that fired the message, a message reaching `withdraw()` from *any* registered `IntentGatewayV2` instance — not necessarily the one named in `order.destination` — is accepted at face value. The escrow-existence check (`== 0`) also does not enforce that the withdrawn `amount` equals the amount actually escrowed for that `(commitment, token)`, only that some non-zero balance is still present, so any `amount ≤` the true remaining balance is accepted and paid to an arbitrary `beneficiary` chosen by whoever triggers the cross-chain dispatch — this is exactly the pattern from the seed report (a payout instruction that computes/pays value without pinning the invocation to the specific instance/strategy that the escrowed value belongs to).

### Impact Explanation
An attacker who can get a `RedeemEscrow` or `RefundEscrow` `PostRequest` dispatched from any chain hosting a registered `IntentGatewayV2` instance — reusing the public `commitment` of a real victim order placed for a *different* destination chain — can drain that victim's escrowed input tokens to a `beneficiary` of the attacker's choosing, partially or fully, before the legitimate fill/cancel flow executes. This is unauthorized transfer of escrowed bridge funds to the wrong beneficiary/amount, i.e. direct fund loss for order makers, matching the bounty's "stealing or loss of funds" / "transaction manipulation" / "wrong beneficiary or amount" categories.

### Likelihood Explanation
Exploitability hinges on an attacker being able to trigger a genuine, host-delivered `PostRequest` of kind `RedeemEscrow`/`RefundEscrow` from a chain other than `order.destination`, carrying a forged `WithdrawalRequest.commitment` that matches a real victim order (public data) and an attacker-chosen `beneficiary`/`amount`. Whether an unprivileged attacker can drive such a dispatch (e.g. via the destination-side fill/cancel entrypoints on a chain that is a valid "known instance" but not the order's declared destination) depends on code in `evm/src/apps/IntentGatewayV2.sol` and companion files (`IntentsBase.sol`, `ExtrinsicIntents.sol`) that were not fully inspected in this pass due to iteration limits — the `withdraw`/`authenticate` weakness itself is confirmed in the Tron variant, but full confirmation that an unprivileged, non-relayer/non-admin actor can originate the cross-chain `PostRequest` requires reading the fill/cancel dispatch entrypoints on the paired chain, which I could not fully trace before this session ended.

### Recommendation
Bind every `RedeemEscrow`/`RefundEscrow` acceptance to the specific order it claims to settle: decode/require the full `Order` (or at minimum `order.destination`) alongside the `WithdrawalRequest`, and assert `request.source == order.destination` (not merely "a known instance") before calling `withdraw()`. Additionally, `withdraw()` should require `amount == _orders[commitment][token]` (or otherwise validate against a per-commitment expected total set at `placeOrder` time) rather than accepting any non-zero-gated attacker-supplied amount, and should check `_filled[commitment] == address(0)` before mutating state to close any residual double-payout window.

### Proof of Concept
Conceptual (not executed — flagged as unverified due to inability to trace the fill/cancel dispatch entrypoint in the paired mainline contract within this session):
1. Victim places `Order` on Chain S with `destination = Chain A`, escrowing tokens; `commitment = keccak256(abi.encode(order))` is emitted publicly in `OrderPlaced`.
2. Attacker, via a legitimate cross-chain dispatch path on Chain B (also a registered `IntentGatewayV2` instance, e.g. through that chain's fill/cancel entrypoint), causes a `PostRequest` of kind `RedeemEscrow` (or `RefundEscrow`) to be sent to Chain S with `body = WithdrawalRequest{commitment: <victim's commitment>, tokens: [{token, amount: <victim's escrowed amount>}], beneficiary: <attacker>}`.
3. On Chain S, `onAccept` calls `authenticate(request)`, which only checks that Chain B's module address matches `_instances[keccak256(Chain B)]` — it does not check `request.source == order.destination (Chain A)` — so authentication passes. [1](#0-0) 
4. `withdraw()` finds `_orders[commitment][token] != 0`, transfers `amount` to the attacker's `beneficiary`, and decrements escrow — draining funds meant for the real filler on Chain A. [4](#0-3)

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
