## Finding

### Title
Git's clone symlink/case-collision protection is explicitly disabled during `clone --recursive` - ([File: app/src/lib/git/clone.ts])

### Summary
Desktop's `clone()` function unconditionally sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'` in the environment used to invoke `git clone --recursive` against an attacker-supplied URL, disabling the safety checks Git itself added to guard against malicious repositories that abuse recursive submodule/`.git` layout collisions.

### Finding Description
`clone()` builds the git invocation environment by merging the network environment with a hard override: [1](#0-0) 
and then runs `clone --recursive` against the caller-supplied `url` and destination `path`: [2](#0-1) [3](#0-2) 

`GIT_CLONE_PROTECTION_ACTIVE` is a real upstream Git environment variable used to gate the additional path/name-collision safety checks that Git performs during clone (particularly with `--recursive`) to prevent a malicious repository/submodule tree from writing into or overwriting sensitive repository metadata such as `.git`, hooks, or config paths on case-insensitive or symlink-tolerant filesystems. Desktop's code explicitly forces this protection **off** for every clone it performs, rather than leaving it at its (protective) default or only disabling it after Desktop's own equivalent validation.

The only other clone-time guard present is `isClonePathSensitive()`, which checks whether the *destination directory itself* resolves to a known sensitive location (home dir, `.ssh`, `.gnupg`, etc.): [4](#0-3) 
That check only validates the top-level clone destination path chosen by the user/UI. It does nothing to prevent a malicious remote from using crafted submodule paths, symlinks, or case-folding tricks *inside* the cloned tree — which is exactly the class of attack `GIT_CLONE_PROTECTION_ACTIVE` was designed to catch, and which Desktop has disabled.

Since `clone` always runs with `--recursive`, an attacker-controlled repository (cloned via a URL the user pastes, a `github-mac://openRepo/` deep link parsed by `parseAppURL`, or a `--cli-clone` command-line argument) can include submodules engineered to collide with the superproject's `.git` directory on case-insensitive filesystems (default on macOS/Windows) or to place symlinked paths that git's built-in clone protection would normally refuse.

### Impact Explanation
If the disabled clone-time protection is what would have blocked a case-collision/symlink submodule attack, an attacker who controls a repository (or a link that Desktop clones) can potentially write or overwrite files outside the intended clone directory — e.g. into `.git/hooks` of the resulting repository — which can lead to arbitrary code execution the next time an ordinary git operation (checkout, commit, merge) triggers a hook in that repo. This satisfies the "unprivileged, attacker controls a cloned repository, results in code execution or file write outside the repo" impact bar.

### Likelihood Explanation
Every clone performed by Desktop goes through this code path with `--recursive` and the protection forced off, so no special user action beyond cloning (or opening) an attacker-supplied repository/URL is required. This significantly raises likelihood compared to relying on a user to manually configure something insecure.

### Recommendation
Do not force `GIT_CLONE_PROTECTION_ACTIVE=false`. Leave Git's clone protection at its default (enabled) value, and only relax it if Desktop can prove an equivalent, narrower guarantee (e.g. after independently validating the resulting working tree layout). If the override was added to work around a specific compatibility problem, scope it as narrowly as possible and document/justify why it's safe, rather than disabling it unconditionally for all clones.

### Proof of Concept
1. Attacker publishes a repository containing a submodule (or nested repo) whose path is engineered to collide with `.git` when case-folded (e.g. `GIT~1`/`.git` collisions used in the git clone/checkout protections), or a symlink pointing at a sensitive path inside the tree.
2. Attacker sends the victim a link such as `github-mac://openRepo/https://attacker.example/owner/repo` (parsed by `parseAppURL`) or simply shares the clone URL. [5](#0-4) 
3. Victim clones via Desktop; `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` in the environment, so Git's built-in protection against the malicious layout does not trigger. [6](#0-5) 
4. The malicious submodule content is written into the repository, including into locations (e.g. hooks) that a protected clone would have refused, setting up code execution on subsequent git operations in that repo.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
