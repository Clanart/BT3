### Title
Identity ("zero") verification shares accepted by `ThresholdKeys::read`/`ThresholdKeys::new` produce an identity group key, enabling universal signature forgery - (File: crypto/dkg/src/lib.rs)

### Summary
The YoloV2 bug class is: per-element zero values accepted because only an aggregate invariant (total > 0, count == n) is checked, producing a poisoned state that breaks later protocol logic. The Serai analog lives in `ThresholdKeys::read` / `ThresholdKeys::new`: attacker-supplied serialized bytes may encode identity (zero) points as verification shares. Only the *count* of shares and the *parameters* are validated — no share is checked for non-identity, and no check binds `group_key != identity` or `secret_share * G == verification_shares[i]`. If the shares for participants `1..=t` are the identity, the interpolated `group_key` is the identity point, for which anyone can forge a Schnorr signature.

### Finding Description
`ThresholdKeys::read` deserializes `t`, `n`, `i`, the interpolation coefficients, the `secret_share`, and `n` verification shares, each read with `<C as Ciphersuite>::read_G` at crypto/dkg/src/lib.rs:622. That reader (crypto/ciphersuite/src/lib.rs:91-101) only enforces canonicality — it accepts the identity point. Identity rejection exists only in `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131), which the DKG path does not use.

`ThresholdKeys::new` (crypto/dkg/src/lib.rs:349-391) then checks only:
- `verification_shares.len() == n` (line 355),
- participant indexes `<= n` (line 362),
- `t == n` when `Interpolation::Constant` (line 369).

It never rejects identity shares and never checks that `G * secret_share == verification_shares[i]`. The group key is computed as `sum(verification_shares[i] * interpolation_factor(i, 1..=t))` for `i in 1..=t` (lines 376-378). Setting shares `1..=t` to the identity yields `group_key == identity`, exactly analogous to filling a round with zero deposits so `currentEntryIndex` stays zero: the zero elements pass all structural checks and poison the derived aggregate.

With `group_key == identity`, `group_key()` returns `(identity * scalar) + G * offset`; for the untweaked keys stored/read (`offset == 0`, `scalar == 1`), the verification key is the identity. A Schnorr signature `s*G = R + c*A` with `A = identity` reduces to `s*G = R`, which anyone produces by picking `s` and setting `R = s*G` — a valid forgery for any message under that group key.

### Impact Explanation
An attacker who can feed crafted bytes to `ThresholdKeys::read` (an explicitly in-scope untrusted-input surface) causes the victim to adopt threshold keys whose group key is the identity. Any funds or protocol authority bound to that group key are spendable by arbitrary forgers — equivalent in severity to the YoloV2 total-logic-blockage, but escalated to signature forgery rather than mere DoS. It can also be used as a pure DoS: identity shares for indexes `> t` leave `group_key` valid but corrupt the per-participant verification shares used by `ThresholdView::view` (crypto/dkg/src/lib.rs:500-507) and `verify_share` blame logic.

### Likelihood Explanation
Requires the attacker to supply the serialized `ThresholdKeys` blob (e.g., a key file, backup, or wire payload deserialized via `ThresholdKeys::read`). Within the stated model — untrusted bytes fed to `ThresholdKeys::read` — this is directly reachable with public inputs; no validator collusion or leaked secret is needed. The zero values pass every implemented validation, mirroring the original report's "only the sum is checked" root cause.

### Recommendation
In `ThresholdKeys::new` (or `ThresholdKeys::read`), reject any identity verification share and reject a `group_key` that is the identity. Additionally verify `C::generator() * secret_share == verification_shares[i]` so the deserialized secret is bound to the declared shares, and prefer an identity-rejecting reader for all consensus/protocol encodings.

### Proof of Concept
```rust
use zeroize::Zeroizing;
use dkg::{ThresholdKeys, ThresholdParams, Interpolation, Participant};
use ciphersuite::{Ciphersuite, group::{ff::Field, GroupEncoding}};
use dalek_ff_group::Ristretto;

// Craft serialized ThresholdKeys for Ristretto with t = n = 2, i = 1,
// Lagrange interpolation, zero secret_share, and BOTH verification shares = identity.
let mut buf = vec![];
buf.extend(u32::try_from(<Ristretto as Ciphersuite>::ID.len()).unwrap().to_le_bytes());
buf.extend(<Ristretto as Ciphersuite>::ID);
buf.extend(2u16.to_le_bytes());            // t
buf.extend(2u16.to_le_bytes());            // n
buf.extend(Participant::new(1).unwrap().to_bytes()); // i
buf.push(1);                               // Interpolation::Lagrange
buf.extend(<Ristretto as Ciphersuite>::F::ZERO.to_repr().as_ref().to_vec()); // secret_share
for _ in 0 .. 2 {
  buf.extend(<Ristretto as Ciphersuite>::G::identity().to_bytes().as_ref().to_vec());
}
let keys = ThresholdKeys::<Ristretto>::read(&mut buf.as_slice()).unwrap();
assert!(bool::from(keys.group_key().is_identity()));
// Forging: Schnorr sig for group_key == identity is (R = s*G, s) for arbitrary s;
// s*G = R + c*identity holds for every message/challenge c.
```

Root cause: `ThresholdKeys::new` at crypto/dkg/src/lib.rs:355-378 enforces count/index/interpolation invariants only, while the identity check in `Curve::read_G` (crypto/frost/src/curve/mod.rs:125-131) is bypassed because `ThresholdKeys::read` uses `<C as Ciphersuite>::read_G` (crypto/dkg/src/lib.rs:622), which per crypto/ciphersuite/src/lib.rs:91-101 accepts the canonical identity encoding.

One caveat: whether the attacker can plausibly supply the `ThresholdKeys` blob depends on the integrator (it is normally a locally generated secret). The cryptographic defect — accepting zero-value group elements that corrupt the derived group key — stands on the in-scope code regardless.
