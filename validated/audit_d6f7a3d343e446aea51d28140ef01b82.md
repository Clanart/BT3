## Title
Git's clone recursion-safety check is explicitly disabled during every Desktop clone, re-enabling submodule-hook based code execution from a malicious repository - (File: `app/src/lib/git/clone.ts`)

## Summary
`clone()` in `app/src/lib/git/clone.ts` runs `git clone --recursive` for every repository the user clones, but explicitly forces the environment variable `GIT_CLONE_PROTECTION_ACTIVE` to `'false'` on every invocation.

## Finding Description
The broken invariant here mirrors the report's pattern: a safety value that must remain isolated/enforced is instead force-cleared and silently folded into the "trusted" execution path.

```
app/src/lib/git/clone.ts:81-93

``` [1](#0-0) 

`GIT_CLONE_PROTECTION_ACTIVE` is Git's own internal guard used during recursive `clone --recursive`/submodule initialization to detect an attacker-controlled repository whose submodules try to redirect Git's working files (e.g. via symlinked or case-collision `.git`/hooks paths) outside of the intended submodule directory — the exact primitive behind past "malicious repository with crafted submodules leads to code execution during recursive clone" issues in upstream Git. Desktop's `clone()` sets this variable to `'false'` unconditionally, which suppresses that internal Git-side protection for every single clone Desktop performs, while still passing `--recursive` so nested submodules are automatically fetched and checked out.

The only defense Desktop adds itself, `isClonePathSensitive()`, only validates the *destination path* is not a sensitive local directory such as `~/.ssh`; it does nothing to validate the content of a cloned repository's submodules or hooks:
```
app/src/lib/git/clone.ts:16-47
function isClonePathSensitive(unresolvedClonePath: string): boolean { ... }
``` [2](#0-1) 

That check therefore does not stop a malicious repository from abusing the recursive-submodule path once Git's own protection has been turned off. The attacker fully controls the content of the cloned/fetched repository, which is exactly the "attacker-controlled cloned/fetched repository" primitive called out as valid impact in this report.

`clone()` is reachable from ordinary, unprivileged user flows: the Clone Repository dialog (`app/src/ui/clone-repository/clone-repository.tsx`), and the `x-github-client://openRepo` deep link / "Clone Again" flow (`app/src/ui/dispatcher/dispatcher.ts` → `openOrCloneRepository` → `clone`), so a victim only needs to clone a URL an attacker supplies (including via a deep link they are lured into clicking) — no local access, no leaked credentials, no social engineering beyond "clone this repo." [3](#0-2) 

## Impact Explanation
If the disabled check is in fact the guard against Git's known submodule/hook-redirection attack, an attacker-hosted repository cloned through Desktop could cause Git to write or overwrite files outside the intended submodule working tree (e.g. into the top-level `.git/hooks` directory), resulting in arbitrary code execution the next time a hook fires (e.g., on the very next `git` operation Desktop performs in that repository). This satisfies the "code execution... from an attacker-controlled cloned/fetched repository" impact bucket, and is high severity because it requires no special privileges and executes as the logged-in user.

## Likelihood Explanation
Likelihood is high for any user who clones a URL under attacker control: the flag is unconditional (not feature-gated, not opt-in), applies to every clone (`Clone repository` dialog, PR/branch-from-URL deep links, "Clone Again"), and always runs with `--recursive`, so any malicious public/private repository with a single crafted submodule entry would exercise the disabled protection on first clone.

## Recommendation
Remove the `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override so Git's built-in clone-recursion protection remains active for all Desktop-initiated clones. If the override exists to work around a compatibility issue (e.g. slower clones or a false-positive on legitimate submodule layouts), gate it behind an explicit, narrowly-scoped exception rather than disabling it globally, and add a regression test that a crafted repository with a submodule attempting to escape its directory (e.g. via a symlinked/hook-colliding submodule path) fails the clone instead of succeeding.

## Proof of Concept
1. Host a public repository containing a submodule entry crafted to redirect Git's submodule checkout machinery outside the submodule's own working directory (the classic pattern is a submodule name/path that collides with `.git`/`hooks` on a case-insensitive filesystem, or a symlink placed via a prior commit that the submodule checkout then writes through).
2. In GitHub Desktop, use "Clone repository" (or click an `x-github-client://openRepo` deep link pointing at the malicious repo/branch) to clone it.
3. Observe that `clone()` runs `git -c init.defaultBranch=... clone --recursive -- <url> <path>` with `GIT_CLONE_PROTECTION_ACTIVE=false` set in the environment, bypassing Git's own protection that would otherwise abort/guard the clone.
4. Confirm (in a controlled test environment) whether the crafted submodule succeeds in writing a hook file outside the submodule directory; if so, the next Git operation Desktop performs against that repository executes attacker-controlled code.

Note on confidence: I was not able to browse Git's own source/changelog from this session to cite the exact upstream advisory number for `GIT_CLONE_PROTECTION_ACTIVE`; the variable name and its use pattern strongly match Git's internal recursive-clone submodule-escape protection, but that specific attribution should be verified against Git's release notes before treating the severity/CVE mapping as final.

function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
