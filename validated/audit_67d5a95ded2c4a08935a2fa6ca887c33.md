### Title
Unmitigated zero-share mint on deposit due to interest-inflated exchange rate rounding - (File: `mainnet/contracts/vault/v0-vault-*.clar`)

### Summary
Every Zest tokenized vault (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) computes shares to mint via `convert-to-shares-preview`, which performs `mul-div-down amount ts ta` [3](#0-2) . The `deposit` function checks only `(>= inkind min-out)` for slippage and never asserts `inkind > 0` before minting [4](#0-3) . If a caller submits `min-out u0` (a legitimate, commonly-used no-slippage-protection value), a deposit that rounds down to zero shares will still succeed: real underlying assets are transferred in and `var-set assets` is incremented, but `ft-mint? zft u0 recipient` mints nothing to the depositor.

### Finding Description
The vault mitigates the classic first-depositor inflation attack by minting `MINIMUM-LIQUIDITY` (`u1000`) shares to `NULL-ADDRESS` during `initialize` [5](#0-4) [6](#0-5) , similar to the "dead shares" mitigation the report recommends. This prevents `ts == u0` from ever recurring, so `convert-to-shares-preview` always takes the `mul-div-down amount ts ta` branch after initialization [3](#0-2) .

However, the exchange rate `ta/ts` (total-assets/total-supply) is not static — `total-assets-preview` grows continuously as borrower interest accrues via the index mechanism (`debt-preview`, `next-index`) independent of any new share issuance [7](#0-6) [8](#0-7) . This is functionally the same "drip" mechanism described in the referenced xETH report — assets increase without shares increasing, inflating the assets-per-share ratio over time as the vault ages and utilization/interest accumulates.

Once `ta` has grown sufficiently relative to `ts` (which is bounded to grow slowly since `MINIMUM-LIQUIDITY` is only 1000 units and legitimate deposits may be small relative to accumulated interest in a mature high-utilization vault), a deposit amount smaller than `ta/ts` computes `inkind = mul-div-down amount ts ta` that rounds down to `u0`. Unlike `redeem`, which explicitly guards this with `ERR-OUTPUT-ZERO` [9](#0-8) , `deposit` has no equivalent check [10](#0-9) . If the caller (or an integrating wallet/contract) passes `min-out u0`, `(>= inkind min-out)` is `(>= u0 u0)` which passes, so the deposit is processed: the depositor's underlying assets are pulled into the vault and added to `assets`, but they receive zero `zft` shares. The value is silently redistributed pro-rata to all existing shareholders (which profit) at the expense of the depositor who minted zero shares (who loses the entire deposited amount).

### Impact Explanation
This is a direct loss of user funds at rest: a depositor transfers real underlying tokens into the vault permanently but receives no vault shares in return, with no way to reclaim the lost value. This lands on the Critical impact class: direct theft of user funds at rest (their principal is transferred to and redistributed among other shareholders).

### Likelihood Explanation
Likelihood increases as vaults mature: total-assets grows via accrued interest while total-supply of shares grows only through new deposits, so the ratio `ta/ts` trends upward as utilization/interest accrues, especially for lower-decimal or higher-precision underlying assets and long periods between new deposits. Any depositor (or front-end/integration) that supplies `min-out u0` — a common default for users who don't calculate expected shares off-chain — is exposed. This does not require any malicious actor to donate funds or manipulate the DAO/oracle; it happens through ordinary vault operation (interest accrual) once the assets-per-share ratio is large enough relative to a user's deposit size.

### Recommendation
Add an explicit `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check in `deposit` (mirroring the check already present in `redeem`) in every vault (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) before minting, so that deposits that would round down to zero shares revert instead of silently consuming the depositor's funds.

### Proof of Concept
1. Vault is deployed and `initialize` mints `MINIMUM-LIQUIDITY` (u1000) shares to `NULL-ADDRESS`, so `ta = ts = 1000` initially.
2. Over time, borrowers accrue interest; `total-assets-preview` grows (e.g., to `ta = 2,000,000`) while `total-supply` (`ts`) stays at `1000` because no further deposits/redeems have occurred.
3. A user calls `deposit` with `amount = 1000` and `min-out = u0` (default/no slippage protection). `convert-to-shares-preview` computes `mul-div-down 1000 1000 2000000` = `0` (rounds down).
4. `(>= inkind min-out)` → `(>= u0 u0)` passes; `(> amount u0)` passes since `amount = 1000`. `receive-underlying` transfers `1000` units from the user into the vault, `var-set assets` increases by `1000`, but `ft-mint? zft u0 recipient` mints zero shares to the user.
5. The user's `1000` units are now split pro-rata among all existing shareholders (a gain for them), and the depositor has permanently lost their `1000` units with nothing to redeem.
