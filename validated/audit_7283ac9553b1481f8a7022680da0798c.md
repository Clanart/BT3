### Title
Deterministic reuse of cached FROST preprocess lets repeated signing under one context leak the secret key share - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::preprocess_internal` derives a FROST preprocess seed deterministically from `CachedPreprocesses`, keyed only by `self.context`. Every call to `share_internal` (and therefore `complete`, which re-invokes `share_internal`) rebuilds the `AlgorithmSignMachine` from the *same* seed via `AlgorithmSignMachine::from_cache`/`seeded_preprocess`, producing identical nonces `d, e`. If `share`/`complete` is ever invoked twice under the same context with a different preprocess set, participant set, or message, the signer emits two shares reusing one nonce — enabling recovery of their secret key share (FROST's documented MUST NOT; `cache()` warns reuse "enables recovery of your private key share"). This is the analog of the reported bug: a party extracting more than its fair share of value because the protocol hands out a claim (a signature share) without accounting for state already consumed.

### Finding Description
In `preprocess_internal`, the preprocess is created once per `context`, XOR-encrypted, stored via `CachedPreprocesses::set`, and decrypted identically on every subsequent call in the same context [1](#0-0) . `share_internal` calls `self.preprocess_internal(participants).0` each time it runs, so the machine — and its nonces — is regenerated deterministically [2](#0-1) . `DkgConfirmer::complete` calls `share_internal` a second time with caller-supplied `preprocesses`, meaning a single confirmation produces a share during `share()` and another during `complete()` under the identical context `(b"DkgConfirmer", attempt)` [3](#0-2) .

`seeded_preprocess` derives nonces purely from `ChaCha20Rng::from_seed(*seed.0)` [4](#0-3) . In `sign`, the binding factor `rho` is computed from `group_key`, `hash_msg`, and a hash of *all* participants' transcripts, and each nonce is combined as `base + rho * actual` [5](#0-4) . The emitted share is `s_i = d_i + e_i·rho_i + lambda_i·secret_i·c` [6](#0-5) . Two executions with identical `d_i, e_i` but different `rho_i`/`c` (different `included` set or message) yield a solvable linear system: `s1 - s2 = e_i·(rho1 - rho2) + lambda_i·secret_i·(c1 - c2)`, and with two differing equations an attacker recovers `e_i` and then `lambda_i·secret_i` — the interpolated private key share. The `SignMachine::from_cache` contract explicitly states the cache "must be deleted so it's never reused. Any reuse will presumably cause the signer to leak their secret share" [7](#0-6)  — the coordinator violates this by design.

### Impact Explanation
An unprivileged counterparty (or any path that causes `share`/`complete` to run twice under one context with differing preprocess maps — e.g., a restarted validator receiving a different participant set within the same DKG attempt) obtains two shares bound to the same nonce, recovering the victim's threshold secret share. Combined with `t-1` other compromised or recovered shares this collapses the multisig; even alone it destroys the threshold security margin for that participant. This matches the accepted impact class of key share recovery.

### Likelihood Explanation
`complete` unconditionally re-executes `share_internal`, so the second derivation is automatic; whether the resulting share differs depends on whether the preprocess map or message seen at completion time differs from share time. Retry/reboot paths and coordinator-supplied preprocess maps (`threshold_i_map_to_keys_and_musig_i_map` keys shares by threshold index derived from the current `removed` set [8](#0-7) ) make divergent inputs across calls realistic rather than hypothetical.

### Recommendation
Do not key `CachedPreprocesses` solely by a reusable `context`: include a per-invocation/session nonce (or delete the cached preprocess when first consumed and error if a second `share` is requested). At minimum, bind the seed to the exact preprocess map/message being signed so re-derivation under divergent inputs is impossible, honoring the one-use contract documented on `from_cache`.

### Proof of Concept
1. Instantiate `DkgConfirmer` for a fixed `attempt`; call `share(preprocesses_A, key_pair)` — it emits share `s1 = d + e·rho_A + lambda·secret·c_A`.
2. Cause `complete(preprocesses_B, key_pair, shares)` to run with a preprocess map `B` differing in one participant (e.g., different `removed` set or a duplicated/absent validator's preprocess), or a different `msg`. `share_internal` regenerates the machine from the same cached seed → same `d, e`; emits `s2 = d + e·rho_B + lambda·secret·c_B` inside `complete`.
3. Given `s1, s2` and the public preprocesses, solve `e = (s1 - s2 - lambda·secret·(c_A - c_B))...` — using both equations and the known group key, recover `lambda·secret` and `e`, i.e., the signer's interpolated secret share.

    let mut participants = serialized_preprocesses.keys().copied().collect::<Vec<_>>();
    participants.sort();
    let mut preprocesses = HashMap::new();

      FrostError::DuplicatedParticipant(_) |
      FrostError::MissingParticipant(_) => unreachable!("{e:?}"),

  our_key: &Zeroizing<<Ristretto as Ciphersuite>::F>,
  mut map: HashMap<Participant, Vec<u8>>,

    .i(removed, <Ristretto as Ciphersuite>::generator() * our_key.deref())
    .expect("MuSig t-of-n signing a for a protocol we were removed from")
    .start;
  assert!(map.insert(our_threshold_i, vec![]).is_none());

  let spec_validators = spec.validators();

    for (key, _) in &spec_validators {
      if threshold_i == spec.i(removed, *key).expect("MuSig t-of-n participant was removed").start {
        return *key;
      }
    }
    panic!("requested info for threshold i which doesn't exist")
  };

  let mut sorted = vec![];
  let mut threshold_is = map.keys().copied().collect::<Vec<_>>();

    participants.push(key);
