### Title
Full-balance (not delta) sweep in `ManualCompound.compound`'s non-compoundable refund loop allows theft of any token dust stuck in the contract - ([File: rewards/ManualCompound.sol])

### Summary
`ManualCompound.compound()` refunds "non-compoundable" reward tokens using `IERC20(token).balanceOf(address(this))` rather than tracking the amount actually just claimed for the caller, and the compoundable-reward sweep loop similarly sweeps the entire `rewards.length` array's balances regardless of what was claimed this call. Any token balance that ends up sitting in `ManualCompound` from an earlier transaction (e.g. from `getReward()` forwarding *all* rewarder tokens when a caller passes an empty `_rewards[i]` array, or from a reward that flips from compoundable to non-compoundable via `removeReward` between two users' transactions) can be swept by any subsequent, unrelated caller who simply names that token in their `_rewards` argument.

### Finding Description
`compound()` claims on behalf of `msg.sender` via `IMasterMagpie(masterMagpie).multiclaimOnBehalf(_lps, _rewards, msg.sender)` [1](#0-0) , which internally calls `_claimBaseRewarder`, sending claimed tokens to `address(this)` (`ManualCompound`) [2](#0-1) . Crucially, if a caller passes `rewardLength == 0` for a given pool, `_claimBaseRewarder` calls `rewarder.getReward(_account, _receiver)`, which forwards **all** reward tokens for that pool, not just ones the caller listed [3](#0-2) .

Back in `compound()`, the refund-to-caller loop only iterates over the caller-supplied `_rewards[i][j]` entries, and only refunds a token when `rewardLength > 0` for that pool [4](#0-3) . Any token that was forwarded to `ManualCompound` by `getReward()` (because the caller specified `rewardLength == 0`) but is *not* currently in the `rewards` array (i.e. `compoundableRewards[token] == false`, e.g. just removed via `removeReward`) is neither refunded in loop 1 (not named) nor swept in loop 2 (not a registered reward) [5](#0-4) . It is left stranded as a real ERC20 balance inside `ManualCompound`.

Because both sweep loops use `balanceOf(address(this))` instead of a per-call delta, any later, unrelated caller who calls `compound()` and simply names that stranded token as one of their `_rewards[i][j]` entries — while it is still marked non-compoundable — will trigger `rewardBalance = IERC20(token).balanceOf(address(this))` and receive the **entire** stranded balance via `safeTransfer(msg.sender, rewardBalance)`, regardless of whether they personally claimed any of it [6](#0-5) . No modifier, reentrancy guard, or per-user accounting in `ManualCompound` restricts this refund to the amount attributable to the current caller.

The transaction-revert precondition described in the prompt (partial completion via revert leaving balance behind) is not itself viable, since a reverted transaction unwinds all its token transfers atomically. However, the underlying root cause — full-balance sweeps combined with the `rewardLength == 0` / reward-reconfiguration path — produces the same stranded-balance condition through a realistic, non-revert path (mismatched `_rewards` array length vs. a reward being removed via `removeReward` between transactions).

### Impact Explanation
Any unprivileged attacker can steal reward-token balances belonging to other users that have become stranded in `ManualCompound`, resulting in direct theft of another user's unclaimed/pending yield. This matches the "theft of unclaimed yield" impact class.

### Likelihood Explanation
Exploitation requires a specific but realistic precondition: a reward token transitions between compoundable/non-compoundable status (via `addReward`/`removeReward`, an owner-controlled but externally observable action) while a user's `compound()` call is constructed with a `_rewards` array that does not fully match the rewarder's actual token set (e.g., `rewardLength == 0` triggering `getReward()`'s full-forward behavior). This is a timing-dependent, moderate-likelihood scenario rather than a trivial, always-available exploit, but it requires no special privileges or capital from the attacker — only awareness of the stranded balance and a follow-up `compound()` call.

### Recommendation
Track and refund/sweep amounts based on balance deltas (before/after the `multiclaimOnBehalf` call) per token instead of `balanceOf(address(this))`, or explicitly disallow `rewardLength == 0` (require callers to always fully enumerate reward tokens) so `getReward()`'s implicit "claim all" path cannot introduce untracked tokens. Additionally, consider snapshotting balances before claiming and only forwarding the incremental amount attributable to the current call.

### Proof of Concept
Foundry test plan:
1. Deploy `MasterMagpie`, a rewarder with two reward tokens (A = normally compoundable, B = target), and `ManualCompound` configured with A only (`addReward(A,...)`), while B is not registered (`compoundableRewards[B] == false`).
2. User1 calls `compound(lps=[pool], rewards=[[]], ...)` (i.e., `rewardLength == 0` for that pool) — this triggers `getReward()` which forwards both A and B into `ManualCompound`. Assert loop1 does nothing (rewardLength==0 guard) and loop2 only sweeps A back to User1 (since B isn't in `rewards`), leaving B's balance stuck in `ManualCompound`.
3. Attacker (unrelated address, possibly with zero stake) calls `compound(lps=[pool], rewards=[[B]], ...)`. Assert `compoundableRewards[B] == false`, so loop1 computes `IERC20(B).balanceOf(address(this))` (equal to User1's stranded balance) and transfers it entirely to attacker via `safeTransfer`.
4. Assert attacker's balance of B equals User1's originally claimed (and never received) amount, and `ManualCompound`'s balance of B is now zero — demonstrating direct theft of User1's yield.
