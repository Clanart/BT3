### Title
Forged `ReceivedOutput` decouples scalar offset from script key, attributing funds to a key that cannot spend them - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput` is the wallet's record of "an output paying to `key + offset*G`". Its deserializer, `ReceivedOutput::read`, reads the scalar `offset`, the `TxOut`, and the `OutPoint` as three fully independent, attacker-controlled fields and never checks that `output.script_pubkey == p2tr_script_buf(group_key + offset*G)`. The binding between the offset and the script is assumed, not verified. This mirrors M-14: an address/key field is accepted in a form that decodes cleanly but is semantically bound to the wrong domain, so funds are credited to a destination no one can sign for.

### Finding Description
`ReceivedOutput::read` performs three independent parses with no cross-validation [1](#0-0) . Legitimate construction only occurs inside `Scanner::scan_transaction`, which looks up the offset keyed by the matched `script_pubkey`, guaranteeing consistency [2](#0-1) . Deserialization bypasses that guarantee entirely.

Downstream, ownership attribution inverts the offset: the processor's `Output::key()` computes `scriptKey - offset*G`, so an attacker who supplies an arbitrary `offset` with a real on-chain `TxOut`/`OutPoint` causes the output to be attributed to an arbitrary group key [3](#0-2) . When spending is later attempted, `SignableTransaction::multisig` derives `keys.offset(offset)` and rejects the input only because `p2tr_script_buf` mismatches, returning `None` [4](#0-3)  — i.e., the funds were already reported received under a key/offset pair that cannot produce a valid BIP-340 spend. As in M-14, the asset is locked at a destination (here, a key-offset pair) that does not correspond to any controllable credential.

### Impact Explanation
An unprivileged party who can feed bytes to `ReceivedOutput::read` (a listed untrusted-input entry point) can fabricate an output record pairing a victim/foreign `script_pubkey` and outpoint with a chosen offset. The result is funds reported received under a group key that does not control them: either misattribution to the wrong multisig session (crediting a key that never received them) or a permanently unspendable input once scheduled, since no `ThresholdKeys` can satisfy both `p2tr_script_buf(offset.group_key()) == script_pubkey` and the honest group key. Impact is loss/lock of credited funds — the same "funds secured to an address nobody holds the key for" consequence as the ZetaChain abort-address bug.

### Likelihood Explanation
Reachability depends on an integration point where a `ReceivedOutput` is deserialized from bytes supplied by an untrusted party rather than produced by the local `Scanner`. The format is explicitly exposed as a network-facing read API. No cryptographic break is needed — only a length-correct serialization, making the attack trivial once such a path exists. Consistency cannot be checked by the reader alone since the group key isn't stored, so the check must be enforced at consumption; `multisig` does so (as a `None` rejection) but the scanner/attribution path does not.

### Recommendation
Either store/verify the group key inside `ReceivedOutput` and check `p2tr_script_buf(key + GENERATOR*offset) == output.script_pubkey` in `read`, or make `read` crate-private so only `Scanner`-produced (internally consistent) values can exist. At minimum, attribute outputs by script lookup (as `scan_transaction` does) rather than by subtracting an untrusted offset from the script key.

### Proof of Concept
```rust
// Attacker crafts bytes for ReceivedOutput::read:
let mut buf = vec![];
buf.extend(Scalar::ONE.to_bytes());            // arbitrary offset
buf.extend(serialize(&victim_txout));          // any real P2TR output's TxOut
buf.extend(serialize(&victim_outpoint));       // its outpoint
let forged = ReceivedOutput::read(&mut buf.as_slice()).unwrap(); // succeeds — no binding check

// Output::key() then yields scriptKey - 1*G, an arbitrary key the victim
// multisig doesn't control; SignableTransaction::multisig later rejects the
// input (returns None), so the reported funds can never be signed for.
```

The structural defect is identical to M-14's: a field decoded in the wrong domain (`Pubkey` vs `[u8; 20]` there; an unbound `offset` vs the script-implied offset here) passes parsing, and the loss only becomes apparent when the funds must be moved.
