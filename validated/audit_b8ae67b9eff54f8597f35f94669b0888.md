### Title
Missing bounds/overflow validation in `GPBCodedInputStreamPushLimit` allows attacker-controlled `byteLimit` to bypass sub-message boundary enforcement - ([File: objectivec/GPBCodedInputStream.m])

### Summary
The Float Capital `_withdraw` bug is a classic "unchecked-value-drives-a-guarded-subtraction/addition, invariant silently violated" pattern: the contract computed `userAmountStaked[token][msg.sender] -= amount` using an attacker-supplied `amount` that was never validated to be `<=` the existing staked balance, so the check that was supposed to bound the operation was bypassed and an unsigned quantity wrapped, corrupting global state used by unrelated users. The transferable invariant is: *a value taken from untrusted wire input must be validated against the current position/limit **before** it is combined arithmetically to establish a new boundary; skipping that check (or performing the check with unsafe/overflow-prone arithmetic) lets the attacker set an out-of-range boundary that downstream code trusts.*

In the Objective-C protobuf binding, `GPBCodedInputStreamPushLimit` establishes the sub-message/length-delimited boundary (`currentLimit`) that all subsequent `CheckSize` calls rely on to keep buffer reads in-bounds. Unlike every other language implementation in this same repository (C++, Java, C#, PHP), which guard `PushLimit`/`pushLimit` against overflow of the `position + byteLimit` addition, the Objective-C version performs the addition without an overflow check.

### Finding Description
`GPBCodedInputStreamPushLimit` is:

```objectivec
size_t GPBCodedInputStreamPushLimit(GPBCodedInputStreamState *state, size_t byteLimit) {
  byteLimit += state->bufferPos;
  size_t oldLimit = state->currentLimit;
  if (byteLimit > oldLimit) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidSubsectionLimit, nil);
  }
  state->currentLimit = byteLimit;
  return oldLimit;
}
``` [1](#0-0) 

`byteLimit` here is a `size_t` derived from an attacker-controlled wire varint (e.g. the length of a length-delimited field/sub-message) after only a 2 GB sanity check in `CheckFieldSize`:

```objectivec
GPB_INLINE void CheckFieldSize(uint64_t size) {
  if (size > 0x7fffffff) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidSize, nil);
  }
}
``` [2](#0-1) 

`CheckFieldSize` bounds the value to `<= 0x7fffffff` (2 GB), but `GPBCodedInputStreamPushLimit` then does `byteLimit += state->bufferPos` with **no check that this addition does not overflow `size_t`**, and no check that `byteLimit >= 0` (moot for `size_t`, but the analogous negative-size guard present in every other language binding is simply absent here). Compare this to the equivalent, hardened logic in the other bindings that all this repository's other parsers use:

- C++: `byte_limit >= 0 && byte_limit <= INT_MAX - current_position && byte_limit < current_limit_ - current_position` [3](#0-2) 
- Java (stream decoder): `byteLimit > Integer.MAX_VALUE - rawPos` overflow check before establishing `currentLimit` [4](#0-3) 
- C#: computes `absoluteLimit` in `long` specifically "to avoid int overflow when byteLimit is near int.MaxValue" [5](#0-4) 
- PHP: explicit check `$byte_limit <= PHP_INT_MAX - $current_position` [6](#0-5) 

Every other binding treats "add the untrusted size to the current position to derive the new limit" as a hazardous operation requiring an explicit overflow guard — exactly the same class of hazard as `userAmountStaked[token][msg.sender] -= amount` in the original finding, where an attacker-controlled operand is combined with a stateful counter without validating the operand against the counter's safe range first. The Objective-C implementation omits this guard entirely.

Because `state->bufferPos` and `state->bufferSize` are of type `size_t`, on 32-bit builds (`size_t` = 32-bit unsigned) a 2 GB-capped `byteLimit` (`<= 0x7fffffff`, i.e. up to ~2^31−1) added to a `bufferPos` that is bounded by the (also `size_t`) `bufferSize` of the input `NSData` can, in principle, wrap around 32-bit `size_t` if `bufferPos` is close to `SIZE_MAX` — however `bufferPos` is itself bounded by the size of the actual input buffer, so on 32-bit platforms this requires an input buffer whose size plus the declared length together approach `2^32`, which is impractical for realistic inputs and is further constrained by the fact that `NSData` backing the parse must actually contain that many bytes (or the message would fail the `CheckSize` growth check afterward). On 64-bit platforms (`size_t` = 64-bit), `byteLimit` is capped at `0x7fffffff` and `bufferPos` cannot exceed the actual buffer length (bounded by process memory, realistically far below `2^64`), so the addition cannot practically overflow.

### Impact Explanation
If the overflow guard were reachable (e.g., on constrained 32-bit targets with a maximal input buffer), an attacker could cause `byteLimit` to wrap to a small value that is `<= oldLimit`, passing the `byteLimit > oldLimit` check while representing an incorrect (wrapped) absolute limit. All subsequent `CheckSize` calls compare against this corrupted `currentLimit`, potentially allowing reads to be considered "in-limit" when they should have been rejected, or vice versa causing premature truncation — a parser-state-integrity violation analogous to the underflowed `userAmountStaked` balance corrupting subsequent contract logic. This would manifest as either (a) incorrect sub-message boundary enforcement (message A's parse could read into message B's bytes) or (b) a spurious/incorrect exception, not memory-unsafe access, since `CheckSize` still separately re-validates against `state->bufferSize`, the actual allocated buffer bound, before any byte read: `size_t newSize = state->bufferPos + size; if (newSize > state->bufferSize) { GPBRaiseStreamError(...); }` [7](#0-6) . That secondary bound against the real buffer size means an out-of-bounds memory read/corruption is not achievable purely through this gap — the practical impact is limited to logical mis-parsing / incorrect message-boundary enforcement under the narrow (largely impractical on 64-bit) overflow precondition, which is why this is at most a Medium-severity robustness gap rather than a memory-safety vulnerability.

### Likelihood Explanation
Low-to-Medium. On the mainstream 64-bit platforms where Objective-C protobuf typically runs (iOS/macOS arm64, x86_64), triggering the overflow requires an input buffer whose size is comparable to `SIZE_MAX` (2^64), which is not feasible for any bounded client-submitted payload. On legacy 32-bit targets, the precondition (`bufferPos` near `2^32`) requires an implausibly large in-memory `NSData` buffer, which itself would likely be rejected by normal memory allocation limits well before reaching this code path. Thus, while the code lacks the defense-in-depth overflow check that every sibling language implementation in the same repository includes, exploiting it to violate the boundary invariant is not practically reachable with realistic bounded inputs.

### Recommendation
Add the same overflow-aware guard used by the C++/Java/C#/PHP implementations to `GPBCodedInputStreamPushLimit`, e.g.:
```objectivec
size_t GPBCodedInputStreamPushLimit(GPBCodedInputStreamState *state, size_t byteLimit) {
  if (byteLimit > SIZE_MAX - state->bufferPos) {
    GPBRaiseStreamError(GPBCodedInputStreamErrorInvalidSize, nil);
  }
  byteLimit += state->bufferPos;
  ...
}
```
This brings the Objective-C binding in line with the overflow-conscious limit arithmetic already present in every other language implementation in the codebase, removing the one place where the "combine untrusted size with current position" operation is unguarded.

### Proof of Concept
Not independently reproducible with a realistic bounded payload: the precondition for the wrap (`state->bufferPos + byteLimit` overflowing `size_t`) requires an input buffer whose length approaches `SIZE_MAX`/`2^32`, which cannot be constructed from a bounded client-submitted Protobuf message under the stated threat model. I was unable to construct or run a concrete failing test within this exercise; this is flagged as a defense-in-depth/hardening gap identified by comparative code review against the other language bindings' equivalent, guarded `PushLimit` implementations, rather than a demonstrated exploitable bug.
