### Title
`Scanner::scan_block` reports immature coinbase outputs as spendable `ReceivedOutput`s — funds accounted as received that cannot actually be spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary

The external bug is an accounting-vs-transfer split: the contract deducts `royaltyAmount * amounts[i]` from the payer's balance but only transfers `royaltyAmount`, leaving a residue of accounted-but-undelivered value in the contract that any later caller can sweep via `_allWethToETHResidue`.

The structural analog in `bitcoin-serai` is `Scanner::scan_block`. `Scanner` is the component that decides which outputs "belong" to the threshold wallet and therefore which `ReceivedOutput`s downstream code may feed into `SignableTransaction` as inputs. `scan_block` iterates `block.txdata` including `txdata[0]`, the coinbase transaction, and returns any coinbase output paying to a scanned script as a `ReceivedOutput` with no maturity marker.

### Finding Description

`scan_transaction` matches outputs purely by `script_pubkey` and wraps every match into a `ReceivedOutput` carrying `offset`, `output`, and `outpoint` (`networks/bitcoin/src/wallet/mod.rs:199-214`). `scan_block` then applies it to every transaction in the block, including the coinbase (`mod.rs:221-227`).

A coinbase output is consensus-unspendable for 100 blocks. A `ReceivedOutput` carries no field distinguishing a mature output from an immature one — `read`/`serialize` round-trip only `offset`, `output`, `outpoint` (`mod.rs:122-141`). Any consumer that sums `ReceivedOutput::value()` or uses these outputs as `inputs` to `SignableTransaction::new` is working with an inflated notion of "received" value: the accounted amount exceeds the actually transferable amount, exactly mirroring the report's "deducted `royaltyAmount * amount`, transferred only `royaltyAmount`" split.

Mirroring the second half of the report — residue swept by an unrelated caller — `SignableTransaction` computes `fee = sum(prevouts) - sum(tx.output)` (`networks/bitcoin/src/wallet/send.rs:137-141`) and, when `change` is `None` or the remainder is below `DUST`, the entire leftover becomes fee paid to a third party (`send.rs:145-147`, `223-235`). An immature input included in the set either forces a consensus-invalid transaction (DoS on signing, since a FROST round would be spent on an unbroadcastable tx) or, if it somehow confirms (e.g., scanned at a reorg boundary), the phantom value flows to miners as fee.

### Impact Explanation

- An unprivileged miner (anyone can mine; a coinbase paying the multisig's P2TR script is a "Bitcoin transaction they send") can make the wallet record received value that is not spendable for 100 blocks.
- If the immature output is selected as an input, the resulting transaction violates consensus (`COINBASE_MATURITY`), so any FROST signing attempt over it produces a transaction that cannot be broadcast — a liveness failure triggered by a third party's transaction.
- If the accounting (sum of `ReceivedOutput::value()`) is consumed without the maturity check, received-but-not-spendable funds corrupt the balance view — the same "credited more than deliverable" property as the source bug.

### Likelihood Explanation

Reachable by any miner at any time — a coinbase output paying to a scanned script requires no cooperation and no knowledge of the internal key. Whether the concrete processor integration performs the "post-processing pass" the doc comment demands could not be fully verified within the search budget (the doc comment at `mod.rs:217-220` itself acknowledges the hazard and shifts responsibility to callers), so likelihood is conditional on the consumer using `scan_block` — which exists precisely so callers don't have to remember to exclude `txdata[0]`-equivalent filtering.

### Recommendation

Change `scan_block` to skip the coinbase's outputs, or attach maturity metadata:

```rust
pub fn scan_block(&self, block: &Block) -> Vec<ReceivedOutput> {
  let mut res = Vec::new();
  for (i, tx) in block.txdata.iter().enumerate() {
    // Skip coinbase outputs: they are consensus-unspendable for 100 blocks
    if i == 0 && tx.is_coinbase() {
      continue;
    }
    res.extend(self.scan_transaction(tx));
  }
  res
}
```

Alternatively, return `(ReceivedOutput, bool /* coinbase */)` or a `matures_at` height so callers cannot silently treat immature value as spendable.

### Proof of Concept

Conceptual, using the existing test scaffolding in `networks/bitcoin/tests/wallet.rs`:

1. Build a `Scanner` for an even `key` (`Scanner::new`).
2. Construct a `Block` whose `txdata[0]` is a coinbase `Transaction` with an output `TxOut { value: 5_000_000_000 sats, script_pubkey: p2tr_script_buf(key) }`.
3. `scanner.scan_block(&block)` returns a `ReceivedOutput` with `value() == 5_000_000_000` and `offset == Scalar::ZERO` — identical in shape to a normal payment.
4. Feed it into `SignableTransaction::new(vec![received], &payments, change, None, fee)` — the transaction is constructed and handed to `multisig(...)` for signing, but any node rejects it: coinbase inputs are immature.

This demonstrates received-and-accounted value that is not spendable, with the excess either stalling signing or, if spent after maturity under a changed state, silently absorbed into `fee()`.

Caveat: the doc comment at `mod.rs:217-220` documents that callers must filter coinbase outputs; if every production caller already does so, this reduces to a dangerous-default API rather than a live vulnerability. That caller-side filtering could not be confirmed in the available iterations.
