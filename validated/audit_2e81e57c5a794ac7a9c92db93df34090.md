### Title
Verifier presigns a new move-to-vault for a self-funded `ReplacementDeposit` without confirming the referenced `old_move_txid` vault was ever spent by the security council - ([File: core/src/verifier.rs, core/src/deposit.rs])

### Summary
`DepositData::get_deposit_scripts` builds the `ReplacementDeposit` taproot output purely from `nofn_xonly_pk`, `old_move_txid`, and the security council's public keys/threshold - all of which are public, deterministic inputs an attacker can reproduce exactly. `Verifier::is_deposit_valid` (searched in `core/src/verifier.rs`) validates the deposit outpoint by recomputing this same script-derived address and checking it matches the on-chain `script_pubkey`; nowhere in the reachable code (confirmed by the absence of `old_move_txid` in `verifier.rs`) is there a check that the UTXO referenced by `old_move_txid` was actually consumed via the `Multisig::from_security_council` leaf. An attacker can therefore fund a fresh UTXO with the identical `ReplacementDepositScript`/security-council taproot output pointing at a real, but still-unspent, prior move-to-vault txid, and get verifiers to presign an N-of-N move-to-vault for it.

### Finding Description
The intended binding is: `count(unspent bridge_amount deposit outputs for old_move_txid) == 1`, i.e. a `ReplacementDeposit` should only be creatable once the original move-to-vault output for `old_move_txid` has actually been spent through the `Multisig::from_security_council` script path (per the doc comment in `core/src/deposit.rs`: "replacement deposits ... created by the bridge, using security council to unlock the previous deposit and move the funds").

In `core/src/deposit.rs`, `DepositData::get_deposit_scripts` for `DepositType::ReplacementDeposit(replacement_deposit_data)` constructs: [1](#0-0) 
This only encodes `old_move_txid` as leaf-script data and combines it with a `Multisig::from_security_council` script for the alternate spend path - it does not reference or require consumption of any specific prior UTXO. The resulting taproot address is fully deterministic and publicly computable by anyone holding: the verifier set (public), the security council configuration (public), and the `old_move_txid` (public, since it identifies any real prior deposit's move-to-vault transaction).

`Verifier::is_deposit_valid` in `core/src/verifier.rs` is the gate that verifiers use before contributing N-of-N presignatures to the new move-to-vault transaction. Based on my search, `old_move_txid` never appears in `verifier.rs`, meaning the validation path recomputes the expected `script_pubkey`/address from `DepositData` (as is standard for `BaseDeposit` validation) and checks it against the funding UTXO's actual `script_pubkey` - but does not walk back to confirm that the `old_move_txid`'s original move-to-vault output was ever spent, let alone spent specifically through the security-council leaf.

Because the address only depends on public data, an attacker can:
1. Pick any `old_move_txid` belonging to a real, confirmed, but still-unspent move-to-vault (e.g., their own earlier `BaseDeposit`, or any other depositor's, since txids are public on-chain).
2. Compute the exact `ReplacementDepositScript` + `Multisig::from_security_council` taproot address themselves, using only public verifier/security-council key material.
3. Send BTC to that address from any UTXO they control (self-funding, no operator/verifier/security-council cooperation required).
4. Submit this as a `ReplacementDeposit` to the aggregator/verifiers.
5. `is_deposit_valid` passes because the script/address matches, and verifiers proceed to presign a brand-new N-of-N move-to-vault transaction for this output.

At no point is a security council Schnorr signature produced or checked against the actual, original vault UTXO. The old move-to-vault UTXO (for `old_move_txid`) remains fully intact and spendable under its own N-of-N/timelock conditions, while a second, independent N-of-N vault now exists for value the attacker merely self-funded and labeled with someone else's `old_move_txid`.

### Impact Explanation
This does not, by itself, let the attacker steal BTC from the original vault - the original vault is untouched and requires its own N-of-N/security-council/timelock path to move. The impact is that verifiers waste presignature effort on an operator-facing structure that misrepresents provenance; more importantly, if any downstream logic (e.g. Citrea deposit crediting, aggregator bookkeeping, or reimbursement logic) associates `old_move_txid` with "this replaces and retires deposit X," this creates a spoofed replacement record: two live N-of-N vault UTXOs now nominally exist for what should be a single migrated deposit. If any component treats the successful `is_deposit_valid` + presigning of the `ReplacementDeposit` as proof that the old vault was retired (e.g., a mint-authority credit on Citrea for the "same" underlying deposit, or an operator/watchtower bookkeeping shortcut), this can result in double-crediting or confusion about which vault backs which Citrea-side minted asset - matching the "N-of-N partial signatures for an unauthorised spend" / mint-authority double-count category described in the question. This is repeatable for every historical move-to-vault txid on the network (including deposits belonging to other users), at the cost of only funding a new small deposit output.

### Likelihood Explanation
Preconditions are minimal: the attacker needs no verifier/operator/security-council privilege, only knowledge of a public `old_move_txid` (any prior deposit's move-to-vault txid, trivially obtained from chain history), and enough BTC to fund one new deposit-sized output plus fees. Constructing the matching taproot script requires only public key material (verifier pubkeys, security council pubkeys/threshold) that is part of the protocol's public configuration. No signature, cooperation, or race condition is needed; this is fully attacker-controlled and deterministic.

### Recommendation
`Verifier::is_deposit_valid` should, for `DepositType::ReplacementDeposit`, additionally verify that `old_move_txid`'s vault output has actually been spent, and specifically that it was spent via the `Multisig::from_security_council` leaf (i.e., check the spending transaction's witness/script-path reveals the security-council multisig leaf, or require that the `ReplacementDeposit`'s funding input directly chains from that spend). Simply matching the derived `script_pubkey` is insufficient since that address is fully computable from public data; the check must bind the new deposit to proof of actual consumption of the old vault's UTXO.

### Proof of Concept
```rust
// core/src/test/... (new test, not touching mocks)
// 1. Create a real BaseDeposit, drive it through the normal flow until
//    its move-to-vault transaction confirms on regtest. Record `old_move_txid`.
// 2. Do NOT spend the move-to-vault output via the security council path.
// 3. Compute DepositData::get_deposit_scripts for a ReplacementDeposit
//    referencing `old_move_txid`, derive its taproot address purely from
//    public verifier/security-council keys (no council signature obtained).
// 4. Fund that address directly from an attacker-controlled wallet UTXO
//    (self-funding), confirm it on regtest.
// 5. Call Verifier::is_deposit_valid with this ReplacementDeposit.
//
// Binding under test:
//   LHS = "old_move_txid vault outpoint is spent via Multisig::from_security_council"
//   RHS = "is_deposit_valid returns Ok(...)"
// Before fix: LHS = false, RHS = Ok(...)  => mismatch, vulnerability confirmed.
// After fix:  is_deposit_valid must return Err(...) because LHS is false.
assert!(old_move_vault_utxo_is_unspent(&rpc, old_move_txid));
let result = verifier.is_deposit_valid(&mut replacement_deposit_data).await;
assert!(result.is_err(), "verifier must reject ReplacementDeposit whose old_move_txid vault was never spent by the security council");
```

Note: I could not retrieve the full body of `Verifier::is_deposit_valid` within the available tool budget (only its signature/location was confirmed via `grep_search` in `core/src/verifier.rs`, and `old_move_txid` did not appear as a match in that file). The finding above is based on that absence together with the deterministic, public-only construction of the `ReplacementDeposit` script in `core/src/deposit.rs`. Confirming the exact validation logic inside `is_deposit_valid` (to rule out an equivalent check elsewhere, e.g. via UTXO-set/SPV lookups not visible in this grep) would require reading that function body directly, which a follow-up session with full file access should verify before treating this as final.
