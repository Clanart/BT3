### Title
Out-of-range `Participant` index in `VerifyBlame` causes unchecked `HashMap` indexing panic, crashing PedPoP blame arbitration - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary
CVE-2024-32608 is memory corruption in HDF5's `H5A__close` triggered when cleaning up malformed attacker-supplied data, yielding denial of service. In Serai's memory-safe Rust, the analogous defect is an unhandled panic reached while processing malformed/untrusted protocol inputs in the PedPoP blame-resolution path: `BlameMachine::blame_internal` and `Decryption::decrypt_with_proof` index `HashMap`s (`self.commitments[&sender]`, `self.enc_keys[&decryptor]`) keyed only by participant indexes `1..=n`, yet the `sender`/`recipient`/`decryptor` arguments are attacker-influenced `Participant` values that are never bounds-checked against `n`. `Participant::new` only rejects zero, so indexes like `n+1` or `65535` pass construction and trigger a panic on the indexing operation.

### Finding Description
`Participant` is defined as a non-zero `u16`; validity against the actual `n` is only enforced by `ThresholdParams::new`/`ThresholdKeys` in some paths. In `crypto/dkg/pedpop/src/lib.rs`, `AdditionalBlameMachine::new` builds `commitments` and `encryption.enc_keys` exclusively for indexes `1..=n` (the `for i in 1 ..= n` loop calling `encryption.register(i, msg)`). `blame_internal` then calls `self.encryption.decrypt_with_proof(sender, recipient, msg, proof)`, which performs `self.enc_keys[&decryptor]` in `crypto/dkg/pedpop/src/encryption.rs` — a `HashMap` index that panics on a missing key. If that lookup is skipped (proof is `None`), `blame_internal` still evaluates `self.commitments[&sender]` with the same unchecked indexing.

The reachable caller is the processor's `CoordinatorMessage::VerifyBlame` handler in `processor/src/key_gen.rs`: it reads the attacker-supplied `share` via `EncryptedMessage::read`, then calls `AdditionalBlameMachine::new(context, params.n(), ...).blame(accuser, accused, substrate_share, substrate_blame)` where `accuser` and `accused` come directly from the coordinator message. Neither `key_gen.rs` nor `blame`/`blame_internal`/`AdditionalBlameMachine::new` validates that `accuser`/`accused` satisfy `1 <= i <= n`. A DKG participant can therefore submit a blame/accusation message naming an `accused` (or spoofed `accuser`) index outside the session's participant set, causing the processor to panic while arbitrating a fatal-slash path.

Note: `blame_internal`'s panic is also reachable for an in-range `accused` only if that participant's commitments were missing, but `AdditionalBlameMachine::new` already returns `MissingParticipant` for those, so the out-of-range index is the unhandled case.

### Impact Explanation
The panic crashes the processor task handling `VerifyBlame`. This is a denial of service against the DKG blame-arbitration path — the same impact class as the CVE (corruption of control flow leading to DoS during cleanup/finalization of malformed objects). Secondarily, because `VerifyBlame` is the mechanism that determines which party gets fatally slashed, aborting the arbitration prevents the protocol from resolving who is faulty: a malicious participant that triggered a legitimate accusation can force re-tries or stall the slash by poisoning the `accused`/`accuser` fields. The `AdditionalBlameMachine::new` doc comment acknowledges panics are possible for invalid inputs, but it scopes that warning to invalid *commitment messages*, not to out-of-range participant indexes passed to `blame`, so this panic is undocumented behavior.

### Likelihood Explanation
Medium. Reachability requires only that an unprivileged participant get a `VerifyBlame` coordinator message processed — blame messages are part of the normal PedPoP flow and are explicitly fed to `EncryptedMessage::read`/`EncryptionKeyProof::read` and the blame API with sender-controlled `accuser`/`accused` fields. The trigger is trivial (any u16 index not in `1..=n`, including `0` being rejected but `n+1..=65535` accepted by `Participant::new`). The impact is capped at a panic/DoS and aborted blame arbitration rather than memory corruption or secret leakage, so it does not reach High.

### Recommendation
Validate `accuser` and `accused` in the `VerifyBlame` handler (and inside `blame`/`blame_internal`/`decrypt_with_proof`) against `params.n()` before any map access, returning the accuser as faulty or a dedicated error for out-of-range indexes. Replace `self.commitments[&sender]` and `self.enc_keys[&decryptor]` with `.get()`-based lookups that map a missing key to a deterministic blame outcome (e.g., blame the accuser for a malformed accusation) instead of panicking.

### Proof of Concept
Conceptual, via `processor/src/key_gen.rs` `CoordinatorMessage::VerifyBlame` handling and `AdditionalBlameMachine::blame` in `crypto/dkg/pedpop/src/lib.rs`:

```rust
// Session params: t = 3, n = 5. All five participants registered in
// AdditionalBlameMachine::new(context, 5, commitment_msgs), so
// `commitments` and `enc_keys` only contain keys for Participants 1..=5.

// Malicious participant submits an accusation with an out-of-range index.
let accused = Participant::new(6).unwrap();   // 6 > n = 5, yet valid per Participant::new
let accuser = Participant::new(1).unwrap();   // a real participant

// VerifyBlame { id, accuser, accused, share, blame } reaches:
//   AdditionalBlameMachine::new(context, params.n(), commitment_msgs)?
//     .blame(accuser, accused, substrate_share, substrate_blame)
// -> blame_internal(sender = accused = 6, recipient = accuser = 1, ...)
// -> decrypt_with_proof: if proof is Some, `self.enc_keys[&1]` exists,
//    DLEq verify runs; on the share-check path `self.commitments[&6]`
//    indexes a HashMap with keys {1..=5} -> panic "key not found".
//    If proof is None, DecryptionError::InvalidProof returns early only
//    after `msg.pop.verify`; the subsequent `self.commitments[&sender]`
//    in the from_repr/multiexp path still panics for sender = 6.

// Symmetric crash: accuser = Participant::new(65535) panics earlier at
// `self.enc_keys[&decryptor]` inside Decryption::decrypt_with_proof.
```

Both orderings abort `VerifyBlame` processing via an unwinding panic instead of returning an attributable `Participant`, matching the malformed-input crash class of CVE-2024-32608.
