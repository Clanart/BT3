### Title
Unhandled `IndexError` in mempool CLVM canonical-encoding check causes a spend-triggered crash - ([File: chia/full_node/mempool_manager.py])

### Summary
`is_atom_canonical()` and `is_clvm_canonical()` in `chia/full_node/mempool_manager.py` parse the raw CLVM byte encoding of an attacker-supplied `puzzle_reveal`/`solution` without validating that the declared atom-length prefix is consistent with the remaining buffer size, mirroring the CVE-2018-9264 root cause ("length inconsistency" in a dissector leading to out-of-bounds access).

### Finding Description
`is_atom_canonical()` reads the length-prefix bytes and computes `atom_len` purely from the header bits, with no bound check against `len(clvm_buffer)`: [1](#0-0) 

`is_clvm_canonical()` then advances its own cursor by the *claimed* `atom_len` returned from `is_atom_canonical()`, again without checking that this offset stays within `len(clvm_buffer)`: [2](#0-1) 

Because `clvm_buffer` is a plain `bytes` object, indexing past its end (`clvm_buffer[offset]` on the next loop iteration, or `clvm_buffer[offset]` inside `is_atom_canonical` while reading multi-byte length prefixes near the end of the buffer) raises an unhandled `IndexError` rather than returning `False`/rejecting the input gracefully. This is exactly the missing "length inconsistency" check called out in the CVE: the code trusts the declared length field instead of validating it against the actual remaining buffer.

This function is invoked directly on attacker-controlled bytes from every coin spend in a submitted `SpendBundle`, inside the mempool admission path: [3](#0-2) 

`validate_spend_bundle()` is called from `add_spend_bundle()` with no `try`/`except` wrapping the `is_clvm_canonical` calls: [4](#0-3) 

An `IndexError` raised here is not one of the expected/handled `Err` return paths of `validate_spend_bundle`/`add_spend_bundle`, so it propagates up as an unhandled Python exception in the mempool-manager call stack rather than being converted into a clean `MempoolInclusionStatus.FAILED` rejection.

### Impact Explanation
A single crafted, unsigned/garbage `puzzle_reveal` or `solution` byte string (with a truncated or oversized atom length-prefix near the end of the buffer) submitted as part of any `SpendBundle` can trigger an unhandled `IndexError` deep in `MempoolManager.add_spend_bundle` / `validate_spend_bundle`. Depending on how the caller of `add_spend_bundle` (full-node RPC / peer message handler) wraps this call, this can surface as a crash of the request-handling task or, if not caught anywhere up the stack, disrupt mempool/transaction processing for that node — a spend-triggered transaction-processing halt, matching the class of impact called for in scope ("invalid spend or block acceptance" / "spend-triggered transaction-processing halt").

### Likelihood Explanation
Likelihood is high in terms of reachability: `is_clvm_canonical()` runs on every coin spend of every spend bundle submitted to the mempool, before any signature check gates the byte-level parsing, and the buffer content (puzzle_reveal/solution bytes) is fully attacker-controlled. Constructing a crafted atom whose multi-byte length prefix is truncated at the very end of the buffer, or whose length pushes the running offset past `len(clvm_buffer)`, is straightforward given the exposed encoding rules in `is_atom_canonical`.

### Recommendation
Add explicit bounds checks in `is_atom_canonical()` before reading each length-prefix byte (raise/return non-canonical if `offset >= len(clvm_buffer)`), and in `is_clvm_canonical()` validate that `offset + atom_len <= len(clvm_buffer)` before continuing the loop (returning `False` instead of relying on a subsequent out-of-bounds index to fail). Additionally, wrap the mempool admission path (`validate_spend_bundle`/`add_spend_bundle`) so that any unexpected exception from byte-level parsing of attacker-controlled puzzle/solution data is converted into a `MempoolInclusionStatus.FAILED` / `Err.INVALID_COIN_SOLUTION` result rather than propagating as an unhandled exception.

### Proof of Concept
Construct a `CoinSpend` whose `puzzle_reveal` (or `solution`) bytes end with a non-canonical, multi-byte atom length prefix that is truncated, e.g. a buffer ending in `...\xf8` (a byte indicating a 5-byte length prefix follows) with zero or one trailing bytes actually present. When `MempoolManager.add_spend_bundle()` calls `validate_spend_bundle()`, which calls `is_clvm_canonical(bytes(coin_spend.puzzle_reveal))`, the loop inside `is_atom_canonical`/`is_clvm_canonical` will index past the end of the short `bytes` object and raise `IndexError`, which is not caught by `chia/full_node/mempool_manager.py:640-668` (`add_spend_bundle`), so it propagates as an unhandled exception through the mempool admission call for that node.

*Note: I was unable to trace, within this session, the exact top-level RPC/peer-message handler that calls `add_spend_bundle()` to confirm whether an outer generic `except Exception` exists further up the call stack (e.g., in `full_node.py` or the RPC layer) that would downgrade this to a logged error rather than a full crash. This should be verified before treating the severity as confirmed process-crashing rather than a caught-but-unexpected exception.*

```python
def is_atom_canonical(clvm_buffer: bytes, offset: int) -> tuple[int, bool]:
    b = clvm_buffer[offset]
    if (b & 0b11000000) == 0b10000000:
        # 6 bits length prefix
        mask = 0b00111111
        prefix_len = 0
        min_value = 1
    elif (b & 0b11100000) == 0b11000000:
        # 5 + 8 bits length prefix
        mask = 0b00011111
        prefix_len = 1
        min_value = 1 << 6
    elif (b & 0b11110000) == 0b11100000:
        # 4 + 8 + 8 bits length prefix
        mask = 0b00001111
        prefix_len = 2
        min_value = 1 << (5 + 8)
    elif (b & 0b11111000) == 0b11110000:
        # 3 + 8 + 8 + 8 bits length prefix
        mask = 0b00000111
        prefix_len = 3
        min_value = 1 << (4 + 8 + 8)
    elif (b & 0b11111100) == 0b11111000:
        # 2 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000011
        prefix_len = 4
        min_value = 1 << (3 + 8 + 8 + 8)
    elif (b & 0b11111110) == 0b11111100:
        # 1 + 8 + 8 + 8 + 8 + 8 bits length prefix
        mask = 0b00000001
        prefix_len = 5
        min_value = 1 << (2 + 8 + 8 + 8 + 8)

    atom_len = b & mask
    for i in range(prefix_len):
        atom_len <<= 8
        offset += 1
        atom_len |= clvm_buffer[offset]

    return 1 + prefix_len + atom_len, atom_len >= min_value
```
