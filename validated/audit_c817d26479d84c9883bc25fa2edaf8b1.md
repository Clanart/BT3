Retroactive reward mis-pricing from unsegmented rate-change window in `pallet-consensus-incentives::calculate_reward` — (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives` pays relayers per block of consensus progress they help deliver. The reward for a batch of unrewarded blocks is computed as a single multiplication of the *entire* backlog span by the *current* `cost_per_block` rate, exactly like the reported `ClientCommunityState::update` bug where `dividends_value` is computed from a single stale/current `rate` applied across a period instead of being segmented at the point the rate changed.

### Finding Description
`Pallet::calculate_reward` computes the reward for a relayer's delivered message as: [1](#0-0) 

```rust
let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);
let blocks = latest_height.saturating_sub(baseline);
let blocks_as_balance = blocks.saturated_into();
let reward = blocks_as_balance.saturating_mul(block_cost);
```

`block_cost` is read live from `StateMachinesCostPerBlock` at claim time via `Self::calculate_reward(&state_machine_id, block_cost)` inside `process_message`: [2](#0-1) 

The watermark `LastRewardedHeight` only advances when a reward is actually processed: [3](#0-2) 

`cost_per_block` is a single mutable value updated in place by `update_cost_per_block`, with no history of which rate applied to which block range: [4](#0-3) 

This is the same broken invariant as the reported bug: a rate that changes over time (`community_state.base_crncy[i].rate` there, `StateMachinesCostPerBlock` here) is applied as a flat multiplier over a whole delta (`drvs_tokens` there, `blocks` here) instead of being pro-rated / segmented across the sub-intervals during which each rate was actually in effect. `process_message` — the function that actually performs the payout — is invoked from the permissionless `on_executed` `FeeHandler` path any time a relayer delivers a ConsensusMessage; there is no requirement that the relayer (or anyone) call `calculate_reward` promptly after each rate change, so blocks accumulated under an old rate get paid at whatever rate happens to be current at claim time.

### Impact Explanation
Any legitimate, honest governance rate change (`update_cost_per_block`) creates a window in which an unprivileged relayer's ordinary message delivery mis-prices the entire outstanding backlog:
- If governance raises `cost_per_block` (e.g., due to rising infra costs going forward), a relayer holding a large backlog of un-rewarded blocks accrued under the old, lower rate is paid the new, higher rate for all of them — draining the treasury (`T::TreasuryAccount`) beyond the amount actually budgeted for those blocks. This is a direct loss of protocol funds to relayers, requiring no malicious relayer behavior, no compromised prover/relayer assumption, and no admin collusion — it is a pure consequence of ordinary rate maintenance plus ordinary permissionless delivery.
- If governance lowers `cost_per_block`, relayers with backlog are systematically underpaid for blocks that should have earned the old higher rate, which can be gamed inversely by relayers timing their claims to submit *before* a scheduled rate decrease and *after* long backlog accumulation to capture an inflated payout, or conversely discouraged from delivering once they detect an imminent decrease (weakening liveness incentives).

This matches the required impact class: "stealing or loss of funds" / "logic attacks" against a bridge treasury via a state-machine-scoped incentive pool that is not properly time-segmented.

### Likelihood Explanation
The likelihood is moderate-to-high in any deployment where `cost_per_block` is adjusted more than once for a state machine with pending un-rewarded blocks (a normal, expected governance operation — cost tuning is precisely what `update_cost_per_block` exists for). No special relayer privilege is required to trigger `process_message`/`on_executed`; delivering a single ConsensusMessage after a rate bump is sufficient to realize the over/under-payment on the entire backlog since `LastRewardedHeight`. The bug is latent until the first rate change after a backlog exists, so it is not always triggerable, but it requires no adversarial coordination — only normal cost-tuning governance plus normal relayer activity.

### Recommendation
Segment the reward calculation at rate-change boundaries instead of applying a single current rate over the whole `[baseline, latest_height]` span:
- Record the block height (or timestamp) at which each `cost_per_block` change takes effect (e.g., store `(height, rate)` history per `state_machine_id`), and when computing `calculate_reward`, sum `Σ (blocks_in_segment_i × rate_i)` across all segments intersecting `[baseline, latest_height]`.
- Alternatively, force `LastRewardedHeight` to be advanced (auto-settling any pending backlog at the *old* rate) synchronously inside `update_cost_per_block` before the new rate is written, so no backlog ever straddles a rate boundary.

### Proof of Concept
1. Governance calls `update_cost_per_block(SM, 10)` for state machine `SM`. No relayer has claimed a reward yet; `LastRewardedHeight[SM]` is unset (defaults to `previous_height`).
2. 10,000 blocks of consensus progress accumulate on `SM` with no relayer delivering a `ConsensusMessage` (nothing forces a claim promptly).
3. Governance later calls `update_cost_per_block(SM, 1000)` (a 100x cost increase, reflecting say a new, more expensive execution environment for future blocks only).
4. A relayer delivers a single `ConsensusMessage` for `SM`. `process_message` fires, reading `block_cost = 1000` from `StateMachinesCostPerBlock`, and `calculate_reward` computes `reward = 10_000 blocks × 1000 = 10,000,000`, when the intended reward for those 10,000 blocks (priced at the rate in effect while they occurred) was `10,000 × 10 = 100,000`.
5. The treasury pays out 100x the intended amount for a backlog that predates the rate change, confirmed by [5](#0-4)  transferring `reward` unconditionally from the treasury account to the relayer.
