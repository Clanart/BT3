### Title
Uncontrolled Recursion in Nested AccountKeyRoleBased RLP Decoding Enables Stack-Overflow DoS via AccountUpdate Transaction - ([File: blockchain/types/accountkey/account_key_role_based.go])

### Summary
`AccountKeyRoleBased.DecodeRLP` and `AccountKeySerializer.DecodeRLP` mutually recurse to decode an `AccountKey` field with no depth limit. Because the nesting-composite check (`CheckInstallable` / `ErrNestedCompositeType`) only runs *after* the whole structure has already been fully RLP-decoded, an attacker can submit a single `AccountUpdate`/`FeeDelegatedAccountUpdate*` transaction whose `Key` field is a deeply nested `AccountKeyRoleBased{AccountKeyRoleBased{AccountKeyRoleBased{...}}}` chain. Decoding this structure recurses once per nesting level with no bound, which can exhaust the goroutine stack (uncontrolled recursion, CWE-770) before any semantic validation (nonce, signature, `CheckInstallable`) is ever reached.

### Finding Description
`AccountKeyRoleBased.DecodeRLP` decodes a list of RLP-encoded sub-keys and, for each entry, delegates to `AccountKeySerializer.DecodeRLP`, which in turn calls `NewAccountKey(keyType)` and then `s.Decode(serializer.key)` on the freshly created key object: [1](#0-0) [2](#0-1) 

If `keyType` is again `AccountKeyTypeRoleBased`, `s.Decode(serializer.key)` re-enters `AccountKeyRoleBased.DecodeRLP`, creating unbounded mutual recursion for every nesting level present in the attacker-supplied RLP bytes. There is no depth counter or recursion guard anywhere in this decode path, and the RLP package itself (`rlp/decode.go`) does not appear to enforce a nesting-depth limit for this recursive struct-decoding path.

The only depth/composite-type restriction that exists — rejecting a `RoleBased` key containing another `RoleBased` key (`ErrNestedCompositeType`) — is enforced in `CheckInstallable`/`CheckUpdatable`, which run only *after* decoding completes: [3](#0-2) 

This means a crafted transaction can force the node to fully unwind a deep recursive decode before that check ever executes. Because `TxInternalDataAccountUpdate.DecodeRLP` (and the fee-delegated variants) invoke this key-decoding path during ordinary transaction deserialization — i.e., whenever a raw transaction is received via RPC (`eth_sendRawTransaction`) or via the tx pool/block processing pipeline — this is reachable from a single, unprivileged, unsigned-check-pending transaction submission: [4](#0-3) 

Unlike `AccountKeyWeightedMultiSig`, whose key-count limit (`MaxNumKeysForMultiSig = 10`) is only checked in `AccountCreationGas`/`SigValidationGas`/`CheckInstallable` (also post-decode) but caps a flat list rather than recursive structure: [5](#0-4) 
the `RoleBased` recursion is structurally unbounded because nesting depth, not list length, drives the recursion, and RLP encoding overhead per nesting level is small enough that a modest transaction payload can encode a large number of nesting levels.

### Impact Explanation
A stack overflow triggered during RLP decoding of a transaction typically causes the Go runtime to crash the process (unrecoverable `runtime: goroutine stack exceeds maximum size` panic, which cannot be caught by `recover()`). Any node that decodes the malicious transaction — full nodes relaying transactions, mempool nodes validating incoming raw transactions, or block producers re-executing a block containing the tx — would crash. This is a genuine denial-of-service against public RPC endpoints and the transaction propagation/validation path, matching CWE-770 (Allocation of Resources Without Limits) analogous to the reported Spring Cloud Function issue (unbounded recursive resource growth from attacker-controlled input causing resource exhaustion/crash).

### Likelihood Explanation
Likelihood is high for any node that accepts and decodes raw transactions from untrusted sources (public RPC `eth_sendRawTransaction`, p2p tx broadcast, or block import), since decoding occurs unconditionally before signature or nonce checks. An attacker only needs to craft the RLP bytes of a nested `AccountKeyRoleBased` structure and does not need a valid signature to trigger the crash during decode/`ErrUnserializableKey`-path handling (decoding happens prior to signature verification).

### Recommendation
- Add an explicit recursion-depth counter/limit to `AccountKeySerializer.DecodeRLP` / `AccountKeyRoleBased.DecodeRLP` (e.g., reject decoding if depth > 1, since only one level of nesting is ever semantically valid) so malformed/malicious nested structures are rejected immediately rather than after full recursive decode.
- Alternatively, enforce a byte-size or nesting-depth check up front (before recursing) using the RLP stream's list metadata, returning an error such as `kerrors.ErrNestedCompositeType` at decode time instead of at `CheckInstallable` time.
- Add a global RLP decode-depth guard in `rlp/decode.go` for recursive `Decoder` implementations to provide defense-in-depth against similar unbounded-recursion patterns elsewhere in the codebase.

### Proof of Concept
Conceptual encoding (not executed, derived from code review):
1. Construct `keyN = AccountKeyPublic` (leaf key).
2. Construct `keyN-1 = AccountKeyRoleBased{keyN}`, `keyN-2 = AccountKeyRoleBased{keyN-1}`, … repeated thousands of times, each wrapped via `NewAccountKeySerializerWithAccountKey` and RLP-encoded per `AccountKeyRoleBased.EncodeRLP`: [6](#0-5) 
3. Embed the resulting bytes as the `Key` field of a raw `AccountUpdate` transaction (`txInternalDataAccountUpdateSerializable.Key`), sign it with any valid key (or even an invalid one, since decode precedes signature check), and submit via `eth_sendRawTransaction` or p2p broadcast.
4. When the receiving node calls `rlp.DecodeBytes` on the transaction (`TxInternalDataAccountUpdate.DecodeRLP` → `fromSerializable` → `accountkey.NewAccountKeySerializer().DecodeRLP`), the recursive chain of `AccountKeyRoleBased.DecodeRLP` calls unwinds the full nesting depth before `CheckInstallable`'s `ErrNestedCompositeType` check can run, potentially exhausting the goroutine stack and crashing the node process.

Note: I was not able to fully verify inside the `rlp` package whether any implicit depth limiting exists for interface/Decoder-based recursive decoding (only confirmed no explicit `maxListDepth`/depth-tracking identifiers exist via search); a live proof-of-concept transaction and stack-trace capture would need to be run in a background Devin session with full repository/tooling access to confirm the crash empirically.

func (a *AccountKeyRoleBased) DecodeRLP(s *rlp.Stream) error {
	enc := [][]byte{}
	if err := s.Decode(&enc); err != nil {
		return err
	}

	keys := make([]AccountKey, len(enc))
	for i, b := range enc {
		serializer := NewAccountKeySerializer()
		if err := rlp.DecodeBytes(b, &serializer); err != nil {
			return err
		}
		keys[i] = serializer.key
	}

	*a = (AccountKeyRoleBased)(keys)

	return nil
}

func (a *AccountKeyRoleBased) CheckInstallable(currentBlockNumber uint64) error {
	// A zero-role key is not allowed.
	if len(*a) == 0 {
		return kerrors.ErrZeroLength
	}
	// Do not allow undefined roles.
	if len(*a) > (int)(RoleLast) {
		return kerrors.ErrLengthTooLong
	}
	for i := 0; i < len(*a); i++ {
		// A composite key is not allowed.
		if (*a)[i].IsCompositeType() {
			return kerrors.ErrNestedCompositeType
		}
		// If any key in the role cannot be initialized, return an error.
		if err := (*a)[i].CheckInstallable(currentBlockNumber); err != nil {
			return err
		}
	}
	return nil
}
