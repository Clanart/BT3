### Title
Unvalidated `sender`/`recipient` participant indexes in PedPoP blame evaluation cause a reachable panic - ([File: crypto/dkg/pedpop/src/lib.rs])

### Summary
Analogous to CVE-2019-6476 (an assertion failure reachable via attacker-influenced protocol input), `BlameMachine::blame`, `AdditionalBlameMachine::blame`, and the shared `blame_internal` accept caller/accuser-supplied `sender` and `recipient` `Participant` values without checking them against the protocol's participant set. `blame_internal` then indexes `self.commitments[&sender]` directly, panicking when `sender` is not a known participant, aborting the host process during blame arbitration.

### Finding Description
`Participant` is an arbitrary non-zero `u16` (`crypto/dkg/src/lib.rs:26`), so any accuser can supply e.g. `Participant::new(u16::MAX)` as `sender`. Neither `BlameMachine::blame` nor `AdditionalBlameMachine::blame` validates `sender`/`recipient` against `n` before calling `blame_internal` (`crypto/dkg/pedpop/src/lib.rs:623-632`, `:674-682`). Inside `blame_internal`, after `decrypt_with_proof` and scalar decoding, the code performs `&self.commitments[&sender]` (`crypto/dkg/pedpop/src/lib.rs:596-601`), which is a `HashMap` index that panics on a missing key. `AdditionalBlameMachine::new` only populates `commitments` for `1 ..= n` (`:654-661`), and `KeyMachine`/`BlameMachine` likewise only hold commitments for real participants, so any out-of-range `sender` guarantees a missing key. `decrypt_with_proof` also internally resolves the sender's registered ECDH material, so an unregistered `sender` either panics there or reaches the `commitments` lookup; neither path returns an `Err`.

This mirrors the CVE's shape: a well-formed-looking but semantically unexpected protocol input (a participant index outside the real set, analogous to a referral where an answer was expected) triggers a crash instead of a handled error.

### Impact Explanation
A panic in `blame`/`AdditionalBlameMachine::blame` kills the process evaluating blame. `AdditionalBlameMachine` is explicitly intended for third parties ("capable of evaluating blame regardless of if the caller was a member"), i.e. arbiters/validators processing accusations from arbitrary parties. Crashing such a node denies service and, worse, prevents the DKG from ever reaching a successful-completion confirmation, permanently stalling key generation for the honest set. Severity: Medium (availability loss; no secret leakage or forgery).

### Likelihood Explanation
Reachable by any party able to submit an accusation to a node running blame evaluation — no threshold collusion, no leaked keys, only control over `sender`/`recipient` argument values, both of which are unconstrained public inputs. The attacker only needs a syntactically valid `EncryptedMessage`/`proof` pair to reach the vulnerable lookup (or trigger the panic inside `decrypt_with_proof` for an unregistered `sender`).

### Recommendation
Validate `sender` and `recipient` at the top of `blame`/`blame_internal` and in `AdditionalBlameMachine::blame`: return an error (e.g. `DkgError::InvalidParticipant`) when either index is not in `1 ..= n` or not present in `self.commitments`. Replace `self.commitments[&sender]` with a checked `get`/`ok_or` lookup.

### Proof of Concept
```rust
// Any party with an AdditionalBlameMachine (e.g. built via
// AdditionalBlameMachine::new(context, n, commitment_msgs)) submits:
machine.blame(
    Participant::new(u16::MAX).unwrap(), // sender: not in 1..=n
    Participant::new(1).unwrap(),        // recipient
    msg,                                 // attacker-controlled EncryptedMessage
    proof,
);
// blame_internal -> self.commitments[&sender] on a HashMap keyed only by
// real participants -> panic: "no entry found for key"
```
For `BlameMachine::blame` the same applies: `sender` is taken verbatim from the accusation and indexed into `self.commitments` (`crypto/dkg/pedpop/src/lib.rs:599`) with no range check.
