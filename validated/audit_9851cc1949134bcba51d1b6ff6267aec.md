### Title
`internal_withdraw` RPC Handler Bypasses Aggregator ECDSA Verification Signature Check Present in `withdraw` - (File: `core/src/rpc/operator.rs`)

---

### Summary

The Operator gRPC service exposes two withdrawal endpoints: `withdraw` and `internal_withdraw`. The `withdraw` handler enforces an ECDSA aggregator verification signature check before calling `operator.withdraw()`. The `internal_withdraw` handler calls `operator.withdraw()` directly, skipping this check entirely. This is the direct Clementine analog of the UniProxy bug: a "safe" validated path exists (`withdraw`) but an "unsafe" unvalidated path (`internal_withdraw`) is also exposed and reachable.

---

### Finding Description

In `core/src/rpc/operator.rs`, the `withdraw` handler (line 193) conditionally enforces an ECDSA signature check:

```rust
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // ... recover address from ECDSA sig, compare to config ...
    if address_from_sig != address_in_config {
        return Err(BridgeError::InvalidECDSAVerificationSignature).map_to_status();
    }
}
```

The `internal_withdraw` handler (line 169) calls the same underlying `operator.withdraw()` with zero application-level authentication:

```rust
async fn internal_withdraw(
    &self,
    request: Request<WithdrawParams>,
) -> Result<Response<RawSignedTx>, Status> {
    // ... parse params ...
    let payout_tx = self.operator.withdraw(...).await?;
    Ok(Response::new(RawSignedTx::from(&payout_tx)))
}
```

There are two compounding weaknesses:

1. **`internal_withdraw` always skips the ECDSA check.** Any caller that reaches this endpoint can trigger `operator.withdraw()` without the aggregator's manual verification signature.

2. **`aggregator_verification_address` is `Option<Address>`.** When not configured, even the `withdraw` endpoint skips the ECDSA check entirely. The "safe" path is therefore optional by design.

The ECDSA verification signature is described in the proto and module comments as the mechanism by which Citrea/aggregator manually attests that a withdrawal is legitimate before the operator fronts BTC. Bypassing it removes this attestation gate.

---

### Impact Explanation

The primary transport-level protection is mTLS (`client_verification: bool`, default `true`). However:

- If `client_verification` is set to `false` (a supported configuration value), or if the aggregator's mTLS certificate is compromised, any network-reachable party can call `internal_withdraw`.
- Even with mTLS enabled, `internal_withdraw` is reachable by any holder of a valid client certificate (not just the aggregator), depending on how `client_verification` is implemented.
- An attacker who reaches `internal_withdraw` can trigger the operator to broadcast a payout transaction for any `withdrawal_id` for which they hold the user's taproot input signature, without the aggregator's ECDSA attestation that the withdrawal was manually verified.
- The operator fronts real BTC in the payout transaction. If the withdrawal is later found invalid or the reimbursement path fails, the operator loses collateral.

---

### Likelihood Explanation

Likelihood is medium. Exploitation requires either mTLS misconfiguration (`client_verification=false`) or a compromised client certificate. Both are realistic in operational deployments. The `aggregator_verification_address` being optional further reduces the effective security bar: operators who omit this config field have no application-level authentication on either endpoint.

---

### Recommendation

1. **Remove or gate `internal_withdraw` behind the same ECDSA check as `withdraw`.** If `internal_withdraw` is intended for aggregator-internal use only, it should enforce the same `aggregator_verification_address` check, not bypass it.

2. **Make `aggregator_verification_address` mandatory**, not `Option<Address>`. The check should not be silently skipped when the field is absent.

3. **Enforce that `client_verification=true` is required** when `aggregator_verification_address` is unset, so there is always at least one authentication layer on the withdrawal path.

---

### Proof of Concept

1. Deploy an operator with `client_verification=false` (or obtain any valid client cert) and `aggregator_verification_address` unset.
2. Observe a valid `withdrawal_id` and the corresponding user taproot signature from a pending withdrawal.
3. Call `internal_withdraw` directly with those parameters and an arbitrary `out_script_pubkey`.
4. The operator broadcasts a payout transaction without any aggregator ECDSA attestation, fronting BTC to the specified output address.
