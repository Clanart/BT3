Based on my investigation, I found a real local analog to the `slot0` manipulation issue in Hyperbridge's Simplex intent-filler: the `FXFiller` prices and sizes cross-chain intent fills directly from a live Uniswap V4 pool's spot state (`sqrtPriceX96`/tick), with a manipulation guard that is **optional** and applied inconsistently.

### Title
Optional, per-chain Uniswap V4 spot-price guard lets a manipulated pool tick under/over-price intent fills and LP withdrawals - (File: sdk/packages/simplex/src/strategies/fx.ts, sdk/packages/simplex/src/funding/uniswapV4/UniswapV4LiquidityState.ts)

### Summary
`FXFiller` (the reference Simplex intent-filler) derives bid/ask prices for "pool-priced" pairs directly from a Uniswap V4 pool's `slot0` (`sqrtPriceX96`, `currentTick`) via `UniswapV4LiquidityState.refresh()` [1](#0-0) , exactly the same spot-price pattern flagged in the seed report (Perp.sol's `slot0` reallocation). The only defense is a `referencePrice`/`maxDeviationBps` guard that is explicitly **optional per chain** — "omit both to leave the chain unguarded" [2](#0-1) , and the docs themselves acknowledge "Pool-based pricing trusts the live pool, which leaves the filler exposed to a manipulated, stale, or thin pool returning a bad quote" [3](#0-2) .

### Finding Description
`checkPriceGuard` only runs on the `referenceRate` path used for confirmation-depth sizing [4](#0-3) , and is a no-op whenever no `priceGuard` entry exists for the chain: `if (!guard || guard.reference.lte(0)) return true` [5](#0-4) . Separately, `UniswapV4FundingPlanner.planWithdrawalForToken` computes the exact amount of liquidity to withdraw from the LP position using the live `sqrtPriceX96`/pool state with no guard check at all [6](#0-5) . Because the pool state is refreshed live on-demand before each withdrawal plan ("on-demand refresh runs before each withdrawal plan so calculations use current on-chain reserves" [7](#0-6) ), an attacker can momentarily skew the pool's spot price (flash-loan swap or thin-liquidity manipulation) immediately before submitting an intent order, causing the filler to (a) quote an unfavorable bid/ask for the fill and/or (b) withdraw LP liquidity at the skewed tick, both of which directly transfer value out of the filler's/LP's real balances to the attacker's beneficiary address in the actual on-chain intent settlement.

### Impact Explanation
This directly threatens "intent settlement" and "bridged assets ... must move exactly once and only to the rightful beneficiary and amount," per the Hyperbridge impact gate. If the guard is left unconfigured on a chain (the documented default, and the wizard step even asks "Add a price guard?" defaulting to `false` [8](#0-7) ), fills against that pool are priced solely from the manipulable spot tick, causing real fund loss to the filler/LP on each exploited fill — the same class of loss as the original Predy `slot0` reallocation issue, but here it is baked into a shipped reference filler that solvers are expected to run in production.

### Likelihood Explanation
No privileged actor, relayer, or prover compromise is required — any unprivileged party with capital to move the target Uniswap V4 pool's spot price (a normal DEX swap) can trigger this, then immediately submit or wait for an intent order that gets filled against the skewed quote. The guard is opt-in and per-chain, so any filler operator who omits it (or an attacker who confines manipulation within the configured `maxDeviationBps` band) is exposed on every pool-priced fill and every LP-funded withdrawal.

### Recommendation
- Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory whenever `[vault.uniswapV4]` pool-based pricing is configured, rather than optional per chain.
- Apply the same guard check inside `UniswapV4FundingPlanner.planWithdrawalForToken` before computing withdrawal amounts from `sqrtPriceX96`, not only in `FXFiller.referenceRate`/trade pricing.
- Replace or supplement the instantaneous `getSlot0` read with a TWAP-based quote (matching the seed report's own recommended mitigation) for both fill pricing and LP withdrawal sizing, since a single manipulable spot read is used for both.

### Proof of Concept
1. Filler operator configures a `[vault.uniswapV4]` position for pair USDC/CNGN with no `referencePrice`/`maxDeviationBps` (valid per `filler-toml.ts` validation, which only enforces guard fields together, not their presence) [9](#0-8) .
2. Attacker swaps a large amount through the target Uniswap V4 pool to push `sqrtPriceX96`/tick to an extreme favoring cNGN.
3. Attacker immediately places (or has pre-staged) a cross-chain intent order swapping USDC→cNGN.
4. `FXFiller.canFill`/pricing path and `UniswapV4LiquidityState.refresh()` read the just-manipulated `getSlot0` [10](#0-9) , and `UniswapV4FundingPlanner` withdraws LP liquidity and credits the attacker's order using that skewed price [11](#0-10) .
5. Attacker reverses their manipulating swap in the pool, pocketing the difference — the filler/LP settles the intent at a loss, matching the exact mechanism (attacker manipulates spot price → forces an out-of-market allocation/fill → profits) described in the seed Predy `reallocate`/`slot0` report.

	// Per-position price guard: referencePrice and maxDeviationBps are optional but
	// must be set together. A given chain may not carry conflicting guard values.
	const guardByChain: Record<string, { referencePrice: string; maxDeviationBps: number }> = {}
	for (const position of uniswapV4?.positions ?? []) {
		const hasRef = position.referencePrice !== undefined
		const hasBps = position.maxDeviationBps !== undefined
		if (hasRef !== hasBps) {
			throw new Error(
				"vault.uniswapV4: a position price guard needs both 'referencePrice' and 'maxDeviationBps', or neither",
			)
		}
		if (!hasRef) continue

		const parsedRef = Number(position.referencePrice)
		if (!Number.isFinite(parsedRef) || parsedRef <= 0) {
			throw new Error(
				`vault.uniswapV4: position 'referencePrice' for chain '${position.chain}' must be a positive number`,
			)
		}
		if (
			!Number.isFinite(position.maxDeviationBps!) ||
			position.maxDeviationBps! <= 0 ||
			position.maxDeviationBps! > 10_000
		) {
			throw new Error(
				`vault.uniswapV4: position 'maxDeviationBps' for chain '${position.chain}' must be a number between 0 (exclusive) and 10000`,
			)
		}
		const existing = guardByChain[position.chain]
		if (
			existing &&
			(existing.referencePrice !== position.referencePrice || existing.maxDeviationBps !== position.maxDeviationBps)
		) {
			throw new Error(`vault.uniswapV4: conflicting price guard values for chain '${position.chain}'`)
		}
		guardByChain[position.chain] = {
			referencePrice: position.referencePrice!,
			maxDeviationBps: position.maxDeviationBps!,
		}
	}

#### Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the filler exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the filler refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}
