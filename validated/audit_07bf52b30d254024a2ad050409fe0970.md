## Title
Copilot conflict resolution matches per-hunk resolutions to conflict markers by ordinal position, not content — a repo with reordered/extra conflict hunks causes wrong resolved content to be spliced into unrelated code - (File: `app/src/lib/copilot-conflict-resolution.ts`)

### Summary
`reassembleResolvedFile` splices the LLM's per-hunk `resolvedContent` values into the on-disk conflicted file purely by **ordinal index** (`hunkIndex`), not by any content or location anchor tying a resolution back to the specific conflict it was generated for. [1](#0-0) [2](#0-1) 

This is the same bug class as the reported `early_purchase::deposit_tokens::handler()` issue: a value that should be tied to a specific, verified item (`amount_to_deposit` for a specific deposit) is instead substituted with an unrelated/derived value (`calculate_base_purchase_cost(...)`) and written anyway, silently producing an incorrect result. Here, resolution N's content should go into conflict block N of a *specific* file, but the code trusts the model's declared ordering/count of hunks matching the file's real hunk count, with no independent verification of the mapping.

### Finding Description
The reassembly walks the raw on-disk file, and for every well-formed `<<<<<<<...=======...>>>>>>>` block it encounters, it pulls the next resolution off `hunkResolutions` in array order:
```
if (hunkIndex < hunkResolutions.length) {
  const resolved = hunkResolutions[hunkIndex].resolvedContent
  ...
}
hunkIndex++
``` [2](#0-1) 

`hunkResolutions` comes straight from the model's JSON response, validated only for basic shape (non-empty `resolvedContent` string, no leftover markers, etc.), not for count or ordering fidelity against the actual file: [3](#0-2) 

The comment on the function explicitly documents that resolutions are "matched by order, not by line number," which is trusted to guarantee correctness "as long as" the model's hunk order matches the file's real conflict order. [4](#0-3) 

The system prompt sent to the model is the *only* thing enforcing this invariant ("hunks: An ordered array with one entry per conflict in the file, matching the 'Conflict 1 of N', 'Conflict 2 of N' order..."), i.e. correctness of the splice depends entirely on the model faithfully preserving order/count, which the model derives from conflict content that originates from the merge of two (potentially attacker-influenced) branches: [5](#0-4) 

An attacker who controls one side of a merge (a fetched/cloned branch, a PR branch merged via GitHub Desktop's conflict-resolution flow) can craft conflicting hunks — e.g. by adding decoy conflict markers, deeply nested/edge-case marker text, or hunks designed to trick the model into reordering, dropping, duplicating, or hallucinating extra hunk entries relative to the real file. Because the splice is purely positional, any mismatch between `hunkResolutions.length`/order and the actual number of conflict blocks in the file causes resolution content meant for one conflict to be silently written into a different, unrelated location in the file (or dropped/duplicated), while the file will appear cleanly "resolved" (no conflict markers) to the user.

The result is then written directly to disk and staged without further diffing against the pre-resolution content or human review of the exact substitution: [6](#0-5) 

Existing guards do not stop this: `validateResolutionPaths` only checks that resolved *paths* correspond to expected files, not that hunk counts/order match; `reassembleResolvedFile`'s only defense is against literally malformed marker blocks (missing `=======` or `>>>>>>>`), not against hunk-count/order mismatches between a well-formed multi-hunk file and the model's returned `hunks` array. [7](#0-6) 

### Impact Explanation
This can cause **silent corruption of what the user commits/pushes** — code from one conflict resolution ends up applied to a different conflict site, or a hunk is skipped/duplicated — while the UI presents the file as "resolved" with no markers remaining. Since this happens during multi-commit operations (merge/rebase/cherry-pick conflict resolution) and the resolved content is written to disk and staged automatically, a user who accepts the Copilot suggestion (which the app explicitly nudges toward) can commit and push logic that silently differs from what either side intended, without any diff-count sanity check catching the mismatch.

### Likelihood Explanation
Requires: (1) the user has Copilot conflict resolution enabled and invokes it during a merge/rebase/cherry-pick with multiple conflicting hunks in a file, and (2) the attacker controls content on one side of the conflict (a malicious/compromised branch, fork, or PR the user merges). No local access, admin rights, or social engineering beyond normal repo/PR interaction is required. The severity is somewhat mitigated by depending on LLM behavior (an indeterministic component), but the code contains no independent verification, so a well-crafted set of conflict hunks reliably has a good chance of confusing the ordinal mapping.

### Recommendation
Do not rely on ordinal position alone to map model resolutions to conflict blocks. Before reassembly, hard-fail (not just warn) if `hunkResolutions.length` does not exactly equal the number of well-formed conflict blocks found in `rawContent`. Consider requiring the model to echo back an anchor (e.g., a hash or verbatim snippet of `oursContent`/`theirsContent` for each hunk) and verify that anchor against the actual block content before splicing, rather than trusting declared order.

### Proof of Concept
Conceptual PoC (not executed, based on code reading):
1. Attacker crafts a branch that, when merged, produces a file with two real conflict hunks — but structures the surrounding content/conflicts so the model is induced to return only one `hunks` entry (or 3, with an extra fabricated one) in its JSON response, or return them in swapped order.
2. `reassembleResolutions` → `reassembleResolvedFile` is called with `rawContent` (2 real conflict blocks) and `hunkResolutions` of mismatched length/order.
3. Because splicing is purely by `hunkIndex` position, the second real conflict block gets resolution content intended for a different conflict (or none at all, or a duplicate), while the resulting file has zero conflict markers and appears fully resolved.
4. The mismatched content is written via `writeFile(absolutePath, resolution.resolvedContent, 'utf8')` and staged with `git add`, with no verification step catching the mismatch. [8](#0-7)
