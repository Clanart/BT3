### Title
Scanner reports immature coinbase outputs as spendable received funds - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
Analogous to the missing precondition check in `liquidate()` (anyone can trigger a claim before the liquidation conditions are actually satisfied), `Scanner::scan_block` emits `ReceivedOutput`s for outputs created by a block's coinbase transaction without checking the coinbase maturity precondition. Coinbase outputs are unspendable for 100 blocks under Bitcoin consensus, yet the Scanner reports them as immediately usable inputs. An unprivileged miner can pay Serai's key from a coinbase transaction, causing Serai to credit/mint against funds it cannot actually spend — the "premature claim" shape, expressed as "funds reported received that are not spendable."

### Finding Description
`Scanner::scan_block` iterates over every transaction in the block, including `block.txdata[0]` (the coinbase): [1](#0-0) 

`scan_transaction` itself performs no maturity or coinbase check — it only matches `output.script_pubkey` against registered scripts: [2](#0-1) 

The docstring explicitly admits the gap, offloading responsibility to a caller that the in-scope code does not provide: [3](#0-2) 

The processor-side scanner pipeline consumes per-block outputs via `network.get_outputs(&block, key)` and pushes every output above `N::DUST` into the `ScannerEvent::Block` event, which is then treated as received, spendable funds (feeding `PlanFromScanning`, forwarding, and `SignableTransaction` input selection): [4](#0-3) [5](#0-4) 

No filtering of `txdata[0]` / coinbase occurs anywhere in this path. The wallet test even demonstrates the behavior directly: `send_and_get_output` mines to a Serai address (funding via the coinbase) and `scan_block` returns the coinbase output as a `ReceivedOutput` after maturity blocks are mined externally — the function itself has no maturity awareness: [6](#0-5) 

### Impact Explanation
Any party capable of producing a block (solo miner or pool operator — an unprivileged actor on the Bitcoin network from Serai's perspective) can pay Serai's group key or a registered offset script in the coinbase transaction. After `CONFIRMATIONS`, the Scanner reports the output as received External/Branch funds. The scheduler may then select this output as an input to a `SignableTransaction` (e.g., to fund a burn or a forwarding plan). Any such transaction is consensus-invalid for 100 blocks, so either the spend stalls/DoSes the batch pipeline, or — worse — the deposit is credited and sriBTC minted against collateral that is unspendable and trivially burned if the block is shallowly reorganized. This mirrors the source bug: a value-claiming action executes without enforcing the precondition that makes the claim valid.

### Likelihood Explanation
The reachability condition is a miner (or anyone with block production) paying Serai's publicly known address in the coinbase — Bitcoin places no restriction on coinbase outputs beyond maturity, and Serai's deposit addresses are public. No validator, peer, or RPC access is required. The only mitigating factor is that it requires producing a block, so exploitation probability depends on attacker mining share; the failure mode once triggered is deterministic.

### Recommendation
In `Bitcoin::get_outputs` (or in `scan_block`), skip `block.txdata[0]` / the coinbase transaction entirely, or mark coinbase-sourced `ReceivedOutput`s and exclude them from both crediting and input selection until `block_height + 100 <= current_height`. The docstring's suggested post-processing pass must actually be enforced rather than delegated.

### Proof of Concept
```rust
// networks/bitcoin/tests/wallet.rs — regtest
// 1. Build Scanner for an even group key `key`.
let mut scanner = Scanner::new(key).unwrap();

// 2. Miner (or regtest RPC) produces a block whose coinbase pays Serai's P2TR script.
rpc.rpc_call::<Vec<String>>(
    "generatetoaddress",
    serde_json::json!([1, Address::from_script(&p2tr_script_buf(key).unwrap(),
                       Network::Regtest).unwrap()]),
).await.unwrap();

// 3. Do NOT mine the 100 maturity blocks. Scan the block directly.
let block = rpc.get_block(&rpc.get_block_hash(height).await.unwrap()).await.unwrap();
let outputs = scanner.scan_block(&block);

// 4. BUG: outputs contains the coinbase TxOut as a ReceivedOutput even though
//    spending it is a consensus violation until height+100.
assert_eq!(outputs.len(), 1);
assert_eq!(outputs[0].outpoint(), &OutPoint::new(block.txdata[0].compute_txid(), 0));
// block.txdata[0].is_coinbase() == true, yet it is reported as spendable input.
```

Note: I was unable to verify the final iteration whether `Bitcoin::get_outputs` in `processor/src/networks/bitcoin.rs` calls `scan_block` verbatim versus `scan_transaction` on `txdata[1 ..]`; the scanner core (`scan_block`) demonstrably includes the coinbase and the documented safeguard is not implemented in the in-scope crate itself. If `get_outputs` already filters the coinbase, this reduces to a no-impact documented caveat.

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
