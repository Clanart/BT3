### Title
Denial-of-service via unbounded nested-loop coin-dependency resolution when processing an untrusted offer - ([File: chia/wallet/trading/offer.py])

### Summary
`Offer.get_cancellation_coins()` in [1](#0-0)  resolves which coins in an offer's spend bundle must be cancelled to invalidate the whole trade, by walking `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` dependency chains extracted from each coin's revealed puzzle/solution. It uses a `while True` outer loop combined with a nested `while True` loop that rescans the entire `dependencies`/`announcements` maps on every iteration to find coins whose announcements are consumed transitively by other coins in the bundle.

### Finding Description
The CVE describes wolfSSL's TLS 1.3 handshake state machine getting stuck reprocessing crafted repeated protocol messages because the loop did not make bounded, well-defined progress per message. The Chia analog is a coin-dependency resolution loop that is driven entirely by attacker-controlled data (a submitted offer's coin spends and their announcement conditions), where the amount of work done per "message" (coin) is not tightly bounded.

`get_cancellation_coins()` first extracts, for every non-addition coin spend in the offer, the `CREATE_COIN_ANNOUNCEMENT` messages it creates and the `ASSERT_COIN_ANNOUNCEMENT` messages it depends on [2](#0-1) . It then enters a loop that repeatedly calls `detect_dependent_coin()` to find a coin whose dependency can be satisfied by another coin, and on each match, walks the remaining `dependencies` dict to find every other coin transitively depending on the removed coin's announcements, re-scanning the full dict and rebuilding `remove_these_keys` on each pass of the inner loop [3](#0-2) .

Because this operates over attacker-supplied puzzle/solution content (an offer file can be freely constructed and handed to a wallet to preview/cancel — an "offer counterparty" input), the number of coins, and the fan-out/depth of announcement dependency chains between them, is fully controlled by the offer's author. The inner `for coin, deps in dependencies.items(): if set(deps) & set(removed_announcements)` scan combined with the outer re-run of `detect_dependent_coin()` over the shrinking `coin_names`/`dependencies` structures gives at least O(N²) (and potentially worse, depending on `detect_dependent_coin`'s own complexity, which was not fully inspected) behavior for N coin spends with crafted mutual announcement chains — directly analogous to a "stuck" processing loop triggered by adversarial input, matching the accepted "spend-triggered transaction-processing halt" impact class.

### Impact Explanation
A malicious offer counterparty could construct an offer file containing a large number of coin spends chained together via `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions, arranged to maximize the number of dependency-resolution passes performed by `get_cancellation_coins()`. Because CLVM execution here uses `INFINITE_COST` [4](#0-3) , the number-of-coins/announcement-fan-out constraint that normally bounds mempool CLVM cost does not apply to an offer file being merely inspected/cancelled by a wallet (it has not yet been submitted to the mempool for cost-limited validation). This could cause the wallet's single-threaded processing to stall for an extended period when a user attempts to view/cancel a hostile offer, a localized denial-of-service against the wallet's transaction-processing path.

### Likelihood Explanation
Medium. Exploitation requires convincing a wallet user to load/inspect/cancel a crafted offer file — this is within the "offers and trades" reachable surface for an offer counterparty, requiring no privileged access, matching the CVE's "unauthenticated attacker sends crafted messages" pattern, but it does require user interaction (importing/cancelling the offer) rather than a bare network packet.

### Recommendation
- Bound the number of coin spends and announcement dependency edges processed by `get_cancellation_coins()`, or replace the repeated full-dictionary rescans with a linear-time graph traversal (e.g., a proper topological/SCC pass over the dependency graph) so the algorithm's complexity does not scale worse than O(N) or O(N log N) with attacker-controlled offer size.
- Enforce a reasonable cap on the number of coin spends / announcements accepted for offer preview/cancellation before running this analysis, and add a timeout around the computation.
- Audit `detect_dependent_coin()` (not shown here) for the same rescanning behavior, since it is called every outer-loop iteration.

### Proof of Concept
Not independently verified against a running node; based on static review of the loop structure only:
1. Construct an offer `SpendBundle` with N non-addition coin spends, each puzzle/solution emitting a `CREATE_COIN_ANNOUNCEMENT` and an `ASSERT_COIN_ANNOUNCEMENT` referencing another coin in the set, chained so that removing each dependent coin repeatedly triggers a fresh full scan of `dependencies`.
2. Pass this offer to a wallet's `TradeManager` cancellation/preview path that calls `Offer.get_cancellation_coins()` (see `chia/wallet/trade_manager.py`).
3. Observe CPU time scaling superlinearly with N due to the repeated full-dictionary rescans in the nested `while True` loops.

**Note on confidence**: I was not able to inspect the body of `detect_dependent_coin()` (referenced but not located within the explored code) due to tool budget exhaustion, so the exact worst-case complexity and whether it can be pushed to true non-termination (rather than bounded polynomial blowup) is not fully confirmed. This should be verified by a full review of `chia/wallet/trading/offer.py` in its entirety, including `detect_dependent_coin()`, and the call sites in `chia/wallet/trade_manager.py`, before treating this as a confirmed high-severity finding.

    def get_cancellation_coins(self) -> list[Coin]:
        # First, we're going to gather:
        dependencies: dict[bytes32, list[bytes32]] = {}  # all of the hashes that each coin depends on
        announcements: dict[bytes32, list[bytes32]] = {}  # all of the hashes of the announcement that each coin makes
        coin_names: list[bytes32] = []  # The names of all the coins
        additions = self.additions()
        for spend in [cs for cs in self._bundle.coin_spends if cs.coin not in additions]:
            name = bytes32(spend.coin.name())
            coin_names.append(name)
            dependencies[name] = []
            announcements[name] = []
            conditions: Program = run_with_cost(spend.puzzle_reveal, INFINITE_COST, spend.solution)[1]
            for condition in conditions.as_iter():
                if condition.first() == 60:  # create coin announcement
                    announcements[name].append(
                        AssertCoinAnnouncement(asserted_id=name, asserted_msg=condition.at("rf").as_python()).msg_calc
                    )
                elif condition.first() == 61:  # assert coin announcement
                    dependencies[name].append(bytes32(condition.at("rf").as_python()))

        # We now enter a loop that is attempting to express the following logic:
        # "If I am depending on another coin in the same bundle, you may as well cancel that coin instead of me"
        # By the end of the loop, we should have filtered down the list of coin_names to include only those that will
        # cancel everything else
        while True:
            removed = detect_dependent_coin(coin_names, dependencies, announcements)
            if removed is None:
                break
            removed_coin, provider = removed
            removed_announcements: list[bytes32] = announcements[removed_coin]
            remove_these_keys: list[bytes32] = [removed_coin]
            while True:
                for coin, deps in dependencies.items():
                    if set(deps) & set(removed_announcements) and coin != provider:
                        remove_these_keys.append(coin)
                removed_announcements = []
                for coin in remove_these_keys:
                    dependencies.pop(coin)
                    removed_announcements.extend(announcements.pop(coin))
                coin_names = [n for n in coin_names if n not in remove_these_keys]
                if removed_announcements == []:
                    break
                else:
                    remove_these_keys = []

        return [cs.coin for cs in self._bundle.coin_spends if cs.coin.name() in coin_names]
