### Title
Gasless `RepayAmount` formula assumes a fixed fee for the dynamic-fee `LendTx`, causing systematic fee-accounting mismatch in the gasless module - (File: `kaiax/gasless/impl/getter.go`)

### Summary
The gasless module (KIP-247) requires a `GaslessSwapTx` to repay the proposer an amount computed by `repayAmount()`, which assumes the proposer-funded `LendTx` will cost exactly `SwapTx.GasPrice() * TxGas`. In reality the `LendTx` is built as an EIP-1559-style dynamic-fee transaction (`TxTypeEthereumDynamicFee`) whose actual charged fee is `effectiveGasPrice * gasUsed`, not the static `GasFeeCap`. This mirrors the root cause of the referenced Anycall finding: a fee amount is hard-coded/assumed instead of being derived from what will actually be charged for the underlying transaction, producing a mismatch between declared and real fee.

### Finding Description
`VerifyExecutable()` enforces that a `GaslessSwapTx.AmountRepay` exactly equals `repayAmount(approveTxOrNil, swapTx)`: [1](#0-0) 

`repayAmount` is defined as `R1 + LendAmount`, where `R1` is documented as "LendTx.Fee() = SwapTx.GasPrice() * TxGas": [2](#0-1) 

However, the actual `LendTx` generated by `GetLendTxGenerator` is a `TxTypeEthereumDynamicFee` transaction whose `GasFeeCap`/`GasTipCap` are copied from the (legacy) `SwapTx`, but whose executed cost depends on the block's base fee (KIP-71) at inclusion time, not on the static `GasPrice()` used in the `R1` formula: [3](#0-2) 

Kaia's `buyGas()` state transition confirms that the amount actually deducted for a transaction is `st.gasPrice` (the *effective* gas price after Magma/KIP-71, i.e. `min(baseFee+tip, feeCap)`), not the fee cap itself: [4](#0-3) 

Because `SwapTx` must be a legacy transaction (a precondition of `decodeFunctionCall`) with a fixed `GasPrice()` chosen by the user at signing time, but the `LendTx` is only constructed later at block-building time using the current (possibly very different) base fee, the value `R1` used for `AmountRepay` verification does not track the `LendTx`'s real cost. Whenever the network base fee is lower than the swap-tx's declared `GasPrice()` at the moment the `LendTx` executes (a normal, expected KIP-71 condition), the proposer's actual outlay for `LendTx` is strictly less than `R1`, while the gasless user is still forced (via the `AmountRepay == repayAmount()` equality check) to repay the full, inflated `R1` amount. [5](#0-4) 

### Impact Explanation
Every gasless swap sender systematically overpays the proposer relative to the proposer's real cost of funding the `LendTx`, since `R1` is a static overestimate that does not reconcile with KIP-71's dynamic base-fee-driven effective gas price. This is an unauthorized/undisclosed value transfer from gasless users to block proposers baked into a "confirmed", protocol-level accounting formula rather than any user-agreed commission — a fee-accounting/gasless-settlement issue in the sense targeted by the Analog Scan rules (fee abuse / gasless settlement irregularity), reachable by any ordinary gasless user submitting a `GaslessApproveTx`/`GaslessSwapTx` pair.

### Likelihood Explanation
This triggers on essentially every gasless swap whenever the KIP-71 base fee at the time the `LendTx` is built/executed differs from the `GasPrice()` the user signed into the `SwapTx` — which is the normal case given KIP-71's per-block base-fee adjustments and the unavoidable delay between signing a legacy-priced `SwapTx` and its inclusion in a proposer-built bundle. No privileged access or special conditions are required; a public, gasless-eligible user is fully able to trigger the discrepancy simply by using the gasless flow under normal fee volatility.

### Recommendation
Compute `R1` (the repayment owed for the `LendTx`) from the actual effective gas price that will be applied to the dynamic-fee `LendTx` (i.e., `min(baseFee + tipCap, feeCap) * TxGas`) rather than assuming it equals the legacy `SwapTx.GasPrice() * TxGas`. Alternatively, make `LendTx` a legacy-priced transaction using the same fixed `GasPrice`, so its cost is deterministic and matches the `R1` term used in `repayAmount()`.

### Proof of Concept
1. A user signs a legacy `GaslessApproveTx`/`GaslessSwapTx` pair with `GasPrice = G` (satisfying the pool's admission rule against the base fee at signing time).
2. Several blocks later, when the proposer includes the bundle, KIP-71's dynamic base fee has decreased to `B < G`.
3. `GetLendTxGenerator` builds `LendTx` with `GasFeeCap = GasTipCap = G` (copied from `SwapTx`), but `buyGas()`/state transition only deducts the effective gas price `min(B+tip, G) ≈ B`, costing the proposer `B * TxGas`, not `R1 = G * TxGas`.
4. `VerifyExecutable` still requires `SwapTx.AmountRepay == repayAmount(...)`, which was computed using `R1 = G * TxGas`.
5. The user's swap output is drained for the larger, stale `R1` amount, while the proposer's genuine cost was the smaller `B * TxGas`, resulting in a fee mismatch identical in nature to the audited Anycall finding (fee amounts computed/assumed independently of what is actually charged for the underlying transfer). func repayAmount(approveTxOrNil, swapTx *types.Transaction) *big.Int {
	// R1 = LendTx.Fee() = SwapTx.GasPrice() * TxGas
	r1 := new(big.Int).Mul(swapTx.GasPrice(), new(big.Int).SetUint64(params.TxGas))

	// RepayAmount = R1 + R2 + R3
	return new(big.Int).Add(r1, lendAmount(approveTxOrNil, swapTx))
}
