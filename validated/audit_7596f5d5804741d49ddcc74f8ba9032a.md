### Title
Same-chain partial-fill escrow release reads the full aggregated `_orders[commitment][token]` balance instead of the per-leg share, letting one filled leg drain escrow owed to another leg with the same input token - (File: `evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the escrow amount to release to a solver differently depending on whether the *current output leg* is fully completed or only partially completed. On a full-leg completion it reads `_orders[commitment][token]` directly — the **entire remaining escrow balance for that token across the whole order** — instead of the amount escrowed specifically for that leg's input index. `_orders` is keyed only by `(commitment, token)`, aggregating all `order.inputs[i]` entries that share the same token, exactly mirroring the external report's root cause: a coarse aggregation key (`delegator, token` / here `commitment, token`) is used to gate/settle a value that is actually tracked per finer-grained unit (per delegation hash / here per output leg index `i`).

### Finding Description
`_orders` is declared as: [1](#0-0) 

It is decremented generically by token in `_withdraw`, with no leg/index awareness: [2](#0-1) 

In `_fillSameChain`, progress per **output leg** is tracked precisely via `_partialFills[commitment][outputToken]`, but the escrow amount released back to the solver for a leg that just reached full completion is computed as the *entire remaining balance under that input token key*, not the proportional/owed amount for that specific leg: [3](#0-2) 

If an order's `inputs` array contains two (or more) entries that reference the **same token address** at different indices (nothing in the visible code path validates uniqueness of `order.inputs[i].token`), `_orders[commitment][token]` holds the *sum* of both inputs' escrowed amounts. When the first of the two corresponding output legs is fully filled, the code releases the **whole pooled balance** (both legs' escrow) to whichever solver completed that first leg, then zeroes `_orders[commitment][token]`. When the second, independent leg subsequently reaches full completion (by the same or a different solver, in the same or a later transaction), `escrowedAmount` is recomputed the same way — now reading `0` — so `escrowedInputs[i].amount == 0`, and `_withdraw` silently skips releasing anything for that token (the `if (amount == 0) continue;` branch), while the solver has already delivered the required output tokens to the beneficiary.

This is the same broken invariant as the `ERC20BalanceGteEnforcer` report: a resource whose true bookkeeping happens at a fine granularity (per delegation hash / per output-leg index) is settled/released using a coarser, shared aggregation key (delegator+token / commitment+token), letting one completion event consume value that belongs to another logically distinct unit.

### Impact Explanation
A solver that legitimately fills a later leg of a multi-input, same-token order can deliver the required output assets to the beneficiary and receive **zero** input tokens in return — a direct loss of funds for that solver, and a transaction that silently "succeeds" while misallocating escrowed funds entirely to whichever leg happened to complete first. This is a wrong-beneficiary/wrong-amount settlement bug in the production Intent Gateway escrow-release path (`_fillSameChain` / `_withdraw`), falling squarely under "stealing or loss of funds" and "transaction manipulation" per the bounty scope. It requires no malicious peer, relayer, or governance actor — only an order whose `inputs` array has a repeated token, filled by unprivileged solver(s) via the normal `fillOrder` flow.

### Likelihood Explanation
Exploitability hinges on whether the order-placement path (`placeOrder` in `evm/src/apps/IntentGatewayV2.sol`) permits `order.inputs` to contain duplicate token addresses across different indices without rejecting or auto-merging them — this file was not fully reviewed in this pass, so it is **not fully confirmed** whether such orders are constructible today. If duplicate-token inputs are allowed (which the escrow declaration/comments and the per-index loop structure suggest is not explicitly disallowed), the bug is trivially triggerable by any user placing such an order and any two solvers (or the same solver across two fills) racing to complete the two legs.

### Recommendation
Track escrow release per output-leg index rather than by the shared `(commitment, token)` key alone: either (a) compute `escrowedAmount` for a fully-completed leg using the same proportional formula used for partial fills (`order.inputs[i].amount * fillAmount / totalRequired`, capped by remaining escrow) instead of reading the raw aggregate `_orders[commitment][token]`, or (b) key `_orders` by `(commitment, inputIndex)` in addition to token so that legs sharing a token cannot cannibalize each other's escrow. Additionally, consider rejecting orders whose `inputs` contain duplicate token addresses at `placeOrder` time if per-leg tracking is not adopted.

### Proof of Concept
1. User places a same-chain order with `order.inputs = [{token: USDC, amount: 100}, {token: USDC, amount: 100}]` and two distinct `order.output.assets` entries (e.g., different output tokens or the same token split across two legs), escrowing 200 USDC total under `_orders[commitment][USDC] = 200`.
2. Solver A calls `fillOrder` providing only `options.outputs[0]` sufficient to fully satisfy leg 0 (`amountFilled == totalRequired` for index 0), leaving leg 1 unfilled (`solverAmount == 0` for index 1).
3. In `_fillSameChain`, index 0 hits the full-fill branch: `escrowedAmount = _orders[commitment][USDC]` reads `200` (the full pooled balance for both legs), which is transferred to Solver A via `_withdraw`, and `_orders[commitment][USDC]` is decremented to `0`.
4. Solver B later calls `fillOrder` to complete leg 1, delivering the required output assets to the beneficiary. When leg 1 reaches full completion, `escrowedAmount = _orders[commitment][USDC] = 0`; `_withdraw` skips the zero-amount token, and Solver B receives no input tokens despite having fulfilled their leg's output obligation — an outright loss of the funds they provided.
