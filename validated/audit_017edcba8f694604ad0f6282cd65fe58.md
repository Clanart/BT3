## Analog Found: Unsynchronized channel close vs. concurrent send in `BidPool` causes panic reachable by an auction bidder

### Title
Race between `BidPool.AddBid`/`HandleBid` (publish) and `BidPool.stop` (shutdown) causes `panic: send on closed channel` - (File: `kaiax/auction/impl/bid_pool.go`)

### Summary
`BidPool` in the Kaia auction module has the same bug class as the reported broker `Publish/Broadcast` vs. `shutdown` race: a publisher goroutine can send on `bidMsgCh`/`newBidCh` while a concurrent `stop()` call closes those same channels, with no mutex or synchronization protecting the two operations against each other.

### Finding Description
`BidPool.AddBid` unconditionally sends to `bp.newBidCh` after validating and inserting a bid: [1](#0-0) 

`BidPool.HandleBid` (invoked from the JSON-RPC `SubmitBid` path and from p2p bid ingestion) enqueues into `bp.bidMsgCh` using a non-blocking `select`/`default`: [2](#0-1) 

`BidPool.stop()` closes both channels, guarded only by an `atomic.CompareAndSwapUint32` on the `stopped` flag — this CAS only prevents `stop()` from double-closing the channels, it does **not** synchronize against a concurrent sender: [3](#0-2) 

The `running` flag checked in `AddBid`/`HandleBid` (`atomic.LoadUint32(&bp.running) == 0`) is a separate atomic variable from `stopped`, so there is a window where:
1. `AddBid`/`HandleBid` reads `running == 1` and proceeds past the guard.
2. Concurrently, `stop()` sets `running = 0`, calls `clearBidPool()`, and then closes `bp.bidMsgCh`/`bp.newBidCh` via the `stopped` CAS.
3. The already-in-flight `AddBid` call reaches `bp.newBidCh <- bid` (or `HandleBid` reaches `bp.bidMsgCh <- bid`) after the channel has been closed.

A `select`/`default` non-blocking send (as in `HandleBid`) does **not** protect against sending on an already-closed channel — Go panics immediately on `send on closed channel` regardless of the `select` construct. Note that `start()` also recreates these channels on restart (`bp.bidMsgCh = make(...)`, `bp.newBidCh = make(...)`), which is itself an unsynchronized write racing with any in-flight reader/sender of the old channel reference, compounding the underlying data race.

This is structurally identical to the reported `broker.go` issue: a publish path (`AddBid`/`HandleBid`) and a shutdown path (`stop`) touch shared mutable channel state without a common lock, and the only "safe" observable outcome (a returned error) is not what happens — instead a panic occurs.

### Impact Explanation
A panic on the node process crashes (or at minimum kills) the goroutine handling bid submission/propagation, and depending on how it's caught, can crash the geth/kaia node process entirely (unhandled panics in a goroutine terminate the whole program in Go). Since `AddBid` is reachable from the public `auction_submitBid` RPC / p2p bid gossip, an auction bidder or bidding-adjacent RPC caller can time bid submissions around block-boundary state transitions (auctioneer/entry-point changes, block insert events that flip `running`/call `stop()`/`start()`) to trigger this panic, causing a validator/CN node crash — a denial-of-service against block production/auction settlement availability, which is a concrete, reachable safety impact (Medium-High depending on exploitability window).

### Likelihood Explanation
`stop()`/`start()` on the bid pool are driven by block-processing/module lifecycle transitions (e.g., disabling auction, chain reorg handling, node stop), which happen routinely and are not attacker controlled directly, but bid submission via RPC/p2p is fully attacker controlled and high frequency. The race window between the `running` check and the actual channel send in `AddBid`/`HandleBid` versus the `stop()`'s clear+close sequence is real but narrow, requiring precise timing (an attacker flooding bid submissions during a module stop/restart transition, e.g., during a hard fork toggling auction module, or auctioneer/entry-point updates that call `clearBidPool` and, in stop paths, the channel close). This makes it a genuine but timing-dependent (Medium likelihood) race, matching the "unwanted side effects...observed when node operations deviate from the happy path" characterization in the original report.

### Recommendation
- Protect `bidMsgCh`/`newBidCh` send and close operations with a single mutex (or use a `sync.Once`-guarded shutdown channel pattern) so that a send can never race with a close.
- Prefer the idiomatic Go pattern: close a separate `done`/`quit` channel and have `AddBid`/`HandleBid` `select` on both the data channel and `quit`, returning an error instead of attempting the send, rather than closing the data channel directly.
- Ensure `running` and `stopped` are updated atomically together (e.g., under one mutex) so a torn read between the two flags cannot occur during `AddBid`/`HandleBid`.
- Avoid recreating channels in `start()` while old references may still be held by in-flight goroutines; instead, always allocate new channels together with new goroutines under the protecting lock.

### Proof of Concept
1. Node has the auction module enabled and `BidPool.running == 1`.
2. Attacker (any auction bidder) calls `auction_submitBid` repeatedly in a tight loop, driving many concurrent `AddBid`/`HandleBid` calls, each of which passes the `running` check in [4](#0-3)  and proceeds toward `bp.newBidCh <- bid` at line 271.
3. Concurrently, an event that calls `bp.stop()` occurs (e.g., disabling the auction module via governance/config change, chain reorg cleanup, or node shutdown sequence) which executes `clearBidPool()` then `close(bp.bidMsgCh); close(bp.newBidCh)` in [3](#0-2) .
4. If step 2's send happens after step 3's close for the same channel instance, the send at `bp.newBidCh <- bid` (or `bp.bidMsgCh <- bid` inside the `select`/`default` in `HandleBid`) panics with `send on closed channel`, since Go's channel-close semantics panic on send-after-close irrespective of the surrounding `running`/`stopped` atomic checks (which are not mutually exclusive with the channel operations).

This is directly analogous to the reported broker.go pattern: Publish (`AddBid`/`HandleBid`) racing with Shutdown (`stop`) on unsynchronized channel state, with the same class of unwanted outcome (panic) instead of the desired outcome (a clean error return).

func (bp *BidPool) stop() {
	// Stop the bid pool.
	atomic.CompareAndSwapUint32(&bp.running, 1, 0)
	bp.clearBidPool()

	// Only close channels if they haven't been closed before
	if atomic.CompareAndSwapUint32(&bp.stopped, 0, 1) {
		close(bp.bidMsgCh)
		close(bp.newBidCh)
	}
	bp.wg.Wait()
}
```

func (bp *BidPool) AddBid(bid *auction.Bid) (common.Hash, error) {
	if atomic.LoadUint32(&bp.running) == 0 {
		return common.Hash{}, auction.ErrAuctionPaused
	}

	if err := bp.validateBid(bid); err != nil {
		return common.Hash{}, err
	}

	if err := bp.insertBid(bid); err != nil {
		return common.Hash{}, err
	}

	gasLimit, err := bp.getBidTxGasLimit(bid)
	if err != nil {
		return common.Hash{}, err
	}
	bid.SetGasLimit(gasLimit)

	bp.newBidCh <- bid

	return bid.Hash(), nil
```

		return
	}

	default:
		logger.Trace("Bid queue is full, dropping bid", "peerID", peerID)
	}
}
