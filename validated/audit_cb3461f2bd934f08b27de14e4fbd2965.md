### Title
Silent precision-loss corruption of unquoted int64/uint64 ProtoJSON number literals via double round-trip check - ([File: upb/json/decode.c])

### Summary
The external report describes a defect class where a numeric value is represented through a fixed-precision intermediate (floating point) while the true value range is far larger, and no check catches the resulting silent divergence between the "intended" value and the "actually stored" value — leading to a wildly different number being accepted and used downstream. The Protobuf analog is in upb's ProtoJSON decoder: unquoted JSON numbers for `int64`/`uint64`/`sint64`/`fixed64`/`sfixed64` fields are parsed through a `double` intermediate, and the only integrity check performed is a round-trip comparison against that same (already-lossy) double, not against the original decimal digits. For any value whose magnitude exceeds 2^53 (the exact-integer limit of IEEE-754 double), the parser can silently accept and store a different 64-bit integer than the one literally present in the JSON payload, without raising any error.

### Finding Description
`jsondec_int` and `jsondec_uint` in `upb/json/decode.c` (identically duplicated in `php/ext/google/protobuf/php-upb.c` and `ruby/ext/google/protobuf_c/ruby-upb.c`, confirmed at matching line ranges) handle the `JD_NUMBER` case for signed/unsigned 64-bit integer fields by: [1](#0-0) [2](#0-1) 

1. Calling `jsondec_number(d)` to obtain a `double dbl` from the raw JSON number text.
2. Range-checking `dbl` against double-representable bounds near `INT64_MIN/MAX` or `UINT64_MAX`.
3. Casting `dbl` to the target integer type and then re-comparing the integer back to `dbl` (`val.int64_val != dbl` / `val.uint64_val != dbl`) to reject non-integral numbers.

The failed invariant: this "round-trip" check only verifies that the *double* and the *cast integer* agree with each other — it never compares against the original decimal digit string. Because a C `double` has only 53 bits of exact integer precision, any literal integer above `2^53` (`9007199254740992`) that is not exactly representable rounds to the *nearest* representable double during step 1, before any check runs. The subsequent round-trip check in step 3 trivially succeeds (the integer and the double it was cast from are self-consistent) even though that value differs from what was actually written in the JSON text — sometimes by up to a few thousand for values near `2^63`. This is the direct analog of the reported incident: a fixed-precision representation (double mantissa / gas fee unit conversion) combined with a much larger nominal value range (64-bit integer / wei amount) produces a silently wrong magnitude, and the existing "sanity" check is defeated because it validates internal consistency of the lossy pipeline rather than fidelity to the original input.

By contrast, the newer C++ `json/internal/parser.cc` implementation used by the mainline C++ runtime is not susceptible to this specific failure for plain digit-string numbers: it first attempts an exact `absl::SimpleAtoi` parse of the literal digits and only falls back to the double-based `ParseFloatStringAsInt` path for numbers containing a decimal point or exponent (where precision loss is an expected characteristic of that literal form): [3](#0-2) 

The upb-based JSON decoder (used by the C core library, and by the PHP and Ruby native extensions that wrap it) has no equivalent exact-integer fast path for unquoted numbers — every `JD_NUMBER` literal, regardless of format, goes through the lossy `double` conversion first.

### Impact Explanation
This is a data-integrity defect in the ProtoJSON parsing surface, reachable by any ordinary client sending bounded, well-formed JSON to a public parse API (`upb_JsonDecode` and its PHP/Ruby bindings). No crash, no memory corruption, and no allocation issue occurs — the parser returns success. The impact is that an attacker (or even a well-behaved but naive client) can supply a large plain-integer JSON number for an `int64`/`uint64`-typed field and have the decoded protobuf message silently contain a *different* integer than the one transmitted, with the discrepancy growing as magnitude increases (up to thousands of units near `INT64_MAX`/`UINT64_MAX`). Any consuming application that trusts the decoded value for accounting, identifiers, quantities, or financial amounts (the same class of value the Bitfinex incident concerned — a numeric amount that ends up several orders of magnitude wrong due to unnoticed precision handling) would silently operate on corrupted data. This matches the Medium severity of the analog: it is a genuine, exploitable integrity bug in a supported parsing backend, but it does not achieve memory safety compromise or RCE.

### Likelihood Explanation
High likelihood of occurrence whenever a client legitimately (or maliciously) sends unquoted large 64-bit integers in ProtoJSON, which the wire format explicitly permits as an accepted (if discouraged) representation for 64-bit integral fields. No special privileges, malicious schema, or malformed input structure is required — a single, well-formed JSON number literal near or above `2^53` triggers it deterministically. The bug is fully within the trusted-schema / bounded-payload / public-API threat model specified.

### Recommendation
- In `upb/json/decode.c` (and the duplicated `php-upb.c` / `ruby-upb.c` copies), replace the double-based path for unquoted `int64`/`uint64` JSON numbers with an exact big-integer/digit-string parser (mirroring `upb_BufToInt64`/`upb_BufToUint64`, already used for the quoted-string case) whenever the literal is a plain integer with no fractional or exponent part.
- Only fall back to the `double` (`jsondec_number`) path for literals that are inherently floating-point in form (decimal point or exponent), and clearly document/enforce that such values retain only double precision.
- Alternatively, compare the parsed integer against a re-serialization of the *original digit text*, not against the intermediate double, to detect precision loss and reject (or require quoting for) such values, consistent with the proto3 JSON canonical mapping recommendation that 64-bit fields be quoted.

### Proof of Concept
Feed the upb JSON decoder a message with an `int64` field set via an unquoted literal that is not exactly representable in `double`, e.g.:
```json
{"int64_field": 9223372036854775000}
```
`jsondec_number` parses this literal via a double conversion, rounding it to the nearest representable double (a multiple of 1024 near this magnitude, e.g. `9223372036854774784.0` or `9223372036854775808.0`). The subsequent checks in `jsondec_int`: [4](#0-3) 
only verify `dbl` is within double-representable int64 bounds and that casting back to `int64_t` reproduces the same `dbl` — both of which hold trivially for the rounded value. The decoded field therefore silently ends up holding `9223372036854774784` (or another nearby value) instead of the literal `9223372036854775000` that was sent, with no error reported. A full trace confirming the exact rounding direction for a specific 10–20 digit literal, and an equivalent test against `php-upb.c`/`ruby-upb.c`, would require running the actual `strtod`-equivalent `jsondec_number` routine, which was not fully retrievable within the available search budget; the affected code paths and the missing-check logic, however, are directly confirmed from the source excerpts above.

/* Parse INT32 or INT64 value. */
static upb_MessageValue jsondec_int(jsondec* d, const upb_FieldDef* f) {
  upb_MessageValue val;

  switch (jsondec_peek(d)) {
    case JD_NUMBER: {
      double dbl = jsondec_number(d);
      if (dbl > 9223372036854774784.0 || dbl < -9223372036854775808.0) {
        jsondec_err(d, "JSON number is out of range.");
      }
      val.int64_val = dbl; /* must be guarded, overflow here is UB */
      if (val.int64_val != dbl) {
        jsondec_errf(d, "JSON number was not integral (%f != %" PRId64 ")", dbl,
                     val.int64_val);
      }
      break;
    }
    case JD_STRING: {
      upb_StringView str = jsondec_string(d);
      jsondec_checkempty(d, str, f);
      val.int64_val = jsondec_strtoint64(d, str);
      break;
    }
    default:
      jsondec_err(d, "Expected number or string");
  }

  if (upb_FieldDef_CType(f) == kUpb_CType_Int32 ||
      upb_FieldDef_CType(f) == kUpb_CType_Enum) {
    if (val.int64_val > INT32_MAX || val.int64_val < INT32_MIN) {
      jsondec_err(d, "Integer out of range.");
    }
    val.int32_val = (int32_t)val.int64_val;
  }

  return val;
}

template <typename T>
absl::StatusOr<LocationWith<T>> ParseIntInner(JsonLexer& lex, double lo,
                                              double hi) {
  absl::StatusOr<JsonLexer::Kind> kind = lex.PeekKind();
  RETURN_IF_ERROR(kind.status());

  LocationWith<T> n;
  switch (*kind) {
    case JsonLexer::kNum: {
      absl::StatusOr<LocationWith<MaybeOwnedString>> x = lex.ParseRawNumber();
      RETURN_IF_ERROR(x.status());
      n.loc = x->loc;
      if (absl::SimpleAtoi(x->value.AsView(), &n.value)) {
        break;
      }

      RETURN_IF_ERROR(ParseFloatStringAsInt<T>(*x, &n.value, lo, hi));
      break;
    }
    case JsonLexer::kStr: {
      absl::StatusOr<LocationWith<MaybeOwnedString>> str = lex.ParseUtf8();
      RETURN_IF_ERROR(str.status());

      n.loc = str->loc;

      // SimpleAtoi will ignore leading and trailing whitespace, so we need
      // to check for it ourselves.
      for (char c : str->value.AsView()) {
        if (absl::ascii_isspace(c)) {
          return lex.Invalid("non-number characters in quoted number");
        }
      }
      if (absl::SimpleAtoi(str->value.AsView(), &n.value)) {
        break;
      }

      RETURN_IF_ERROR(ParseFloatStringAsInt<T>(*str, &n.value, lo, hi));
      break;
    }
    default:
      return lex.Invalid("expected number or string");
  }

  return n;
}

template <typename Traits>
absl::StatusOr<int64_t> ParseInt(JsonLexer& lex, Field<Traits> field) {
  absl::StatusOr<LocationWith<int64_t>> n =
      ParseIntInner<int64_t>(lex, -9007199254740992.0, 9007199254740992.0);
  RETURN_IF_ERROR(n.status());

  if (Traits::Is32Bit(field)) {
    if (std::numeric_limits<int32_t>::min() > n->value ||
        n->value > std::numeric_limits<int32_t>::max()) {
      return n->loc.Invalid("integer out of range");
    }
  }

  return n->value;
}
