### Title
Missing `chain_id` in `CLEMENTINE_EIP712_DOMAIN` Enables Cross-Network Replay of Withdrawal Authorization Signatures — (`core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is defined with only `name` and `version`, omitting `chain_id` (and `verifying_contract`). This is the direct Clementine analog of M-16: a domain separator that is incomplete per EIP-712, enabling a signature produced for one Clementine deployment (e.g., testnet, chain_id=5655) to be replayed verbatim on any other deployment that shares the same `aggregator_verification_address`.

---

### Finding Description

In `core/src/rpc/ecdsa_verification_sig.rs`, the single shared domain object used for all withdrawal authorization checks is:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

EIP-712 requires `chainId` in the domain separator to prevent cross-chain replay. The Citrea chain ID is a known runtime value (`citrea_chain_id` in `BridgeConfig`), but it is never bound into the domain. [2](#0-1) 

This domain is used in two production authorization paths:

**1. Optimistic payout** — `Verifier::sign_optimistic_payout` recovers the signer address from the EIP-712 hash and compares it to `aggregator_verification_address`:

```rust
let address_from_sig =
    recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>(
        deposit_id, input_signature, input_outpoint,
        output_script_pubkey.clone(), output_amount,
        verification_signature,
    )?;
if address_from_sig != address_in_config {
    return Err(BridgeError::InvalidECDSAVerificationSignature);
}
``` [3](#0-2) 

**2. Operator withdrawal** — `ClementineOperator::withdraw` performs the same check with `OperatorWithdrawalMessage`: [4](#0-3) 

Both paths call `recover_address_from_ecdsa_signature`, which hashes the message against `CLEMENTINE_EIP712_DOMAIN`: [5](#0-4) 

Because `chain_id` is absent from the domain, the EIP-712 digest is identical across all EVM-compatible networks. A `verification_signature` produced for one deployment is cryptographically valid on every other deployment that uses the same `aggregator_verification_address`.

The proto comment explicitly acknowledges the intent to use different struct names to prevent cross-message replay:

> "This message contains same data as the one in Optimistic Payout signature, but with a different message name, so that the same signature can't be used for both optimistic payout and normal withdrawal." [6](#0-5) 

The cross-message protection works (different struct names produce different type hashes). The cross-network protection does not work because `chain_id` is absent.

---

### Impact Explanation

When `aggregator_verification_address` is configured (the intended production hardening), an attacker who observes a valid `verification_signature` from one Clementine deployment can replay it on another deployment sharing the same key. This bypasses the aggregator's manual authorization gate for:

- **Optimistic payout**: causes verifiers to co-sign a MuSig2 partial signature releasing BTC from the vault UTXO to an attacker-controlled output.
- **Operator withdrawal**: causes the operator to process a payout transaction without aggregator re-authorization.

The remaining checks (withdrawal UTXO must match DB, deposit must exist, output amount within bounds) constrain exploitability to cases where the replayed parameters are also valid on the target network — realistic when the same operator runs testnet and mainnet deployments with the same key, or when a protocol upgrade creates a new deployment.

---

### Likelihood Explanation

`aggregator_verification_address` is optional and defaults to `None` (skipping the check entirely). When it is set — which is the documented production intent — the missing `chain_id` is always present. The attack requires the same key to be used across two deployments and a matching withdrawal state on the target network, making it medium likelihood in a multi-deployment environment.

---

### Recommendation

Include `chain_id` (and optionally `verifying_contract`) in `CLEMENTINE_EIP712_DOMAIN`. Because the chain ID is a runtime value from `BridgeConfig`, the domain cannot be a `static`; it must be constructed at startup and stored as an immutable field or passed into `recover_address_from_ecdsa_signature`:

```rust
// In BridgeConfig or a dedicated init function:
pub fn build_eip712_domain(chain_id: u64) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
    }
}
```

Pass the resulting domain into `recover_address_from_ecdsa_signature` instead of using the global `CLEMENTINE_EIP712_DOMAIN`. Update all callers in `verifier.rs`, `operator.rs`, and test helpers in `core/src/test/sign.rs`. [7](#0-6) 

---

### Proof of Concept

1. Deploy Clementine on two networks (testnet chain_id=5655, mainnet chain_id=1) with the same `aggregator_verification_address`.
2. On testnet, the aggregator signs a valid `OptimisticPayoutMessage` for `withdrawal_id=N`, producing `verification_signature S`.
3. On mainnet, submit the same `OptimisticPayoutMessage` fields with `verification_signature S` to the aggregator's `optimistic_payout` RPC.
4. `recover_address_from_ecdsa_signature::<OptimisticPayoutMessage>` computes `eip712_signing_hash` against `CLEMENTINE_EIP712_DOMAIN` — which has no `chain_id` — and recovers the same address on mainnet.
5. The address matches `aggregator_verification_address`; the check passes; verifiers co-sign the optimistic payout transaction on mainnet without the aggregator having authorized it for mainnet.
