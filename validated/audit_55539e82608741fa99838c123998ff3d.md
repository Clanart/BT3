## Finding

The Tron deployment of `IntentGatewayV2` never verifies actual token receipt before crediting escrow, unlike the hardened EVM implementation that was specifically patched to address fee-on-transfer/rebasing token accounting drift — this is a direct local analog of the Olas `StakingToken.sol` M-08 bug.

### Title
`IntentGatewayV2.placeOrder` on Tron credits escrow using the user-declared amount instead of actual tokens received, causing accounting/custody mismatch for fee-on-transfer or rebasing tokens - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The main EVM `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) explicitly measures the contract's token balance before and after each `safeTransferFrom` call and uses the *actual received amount* to compute the escrow and commitment, precisely to defend against fee-on-transfer/rebasing tokens. [1](#0-0) 
This behavior is documented and unit-tested (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`). [2](#0-1) 

The Tron fork of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not have this protection: it derives `reducedInputs[i].amount` purely from `order.inputs[i].amount` (the caller-supplied value) minus the protocol fee, then transfers `order.inputs[i].amount` via `safeTransferFrom` and separately credits `_orders[commitment][token] += reducedInputs[i].amount` — with no balance-before/after check tying the credited escrow to what the contract actually received. [3](#0-2) [4](#0-3) 

### Finding Description
`placeOrder` on Tron computes `reducedInputs` (escrowed-amount ledger entries) straight from the order struct's stated `amount`, before any transfer occurs: [5](#0-4) 

Then, in the non-predispatch path, it performs the transfer and credits escrow using the *requested* amount, not what was actually received:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
``` [6](#0-5) 

For a fee-on-transfer, rebasing, or otherwise variable-balance ERC20 token, the actual amount received by the contract will be less than `order.inputs[i].amount`. The internal `_orders[commitment][token]` ledger nevertheless records the full (fee-reduced-only) amount as escrowed. This is precisely the M-08 pattern: internal accounting (`_orders`) diverges from the contract's real custodial balance.

Later, when the order is filled and redeemed (same-chain `withdraw()` or cross-chain `RedeemEscrow` via `onAccept`), the contract pays out the *ledger* amount to the beneficiary/solver: [7](#0-6) 
There is no balance check at withdrawal time either — `token.call(transfer.selector, beneficiary, amount)` blindly transfers the internally recorded `amount`, decrementing `_orders[...] -= amount`.

Because the escrow ledger for that token is inflated relative to the contract's real token holdings, the shared token pool backing *all* outstanding orders for that token becomes under-collateralized by the sum of all fee losses. Any unprivileged user placing an order with a FOT/rebasing token creates this shortfall — no malicious relayer, prover, or admin is required.

### Impact Explanation
This falls squarely under "stealing or loss of funds" and "logic attacks" in the bounty scope: the escrow accounting no longer matches actual custody. Once enough FOT/rebasing-token orders accumulate escrow debt beyond the contract's real balance for that token, later legitimate redemptions (`withdraw`/`onAccept`) for other commitments using the same token can be starved — the contract will be short of tokens to honor the ledger, causing reverts (fund lock) for some order owners while earlier claimants effectively drain the shared pool at others' expense. This is a genuine fund-loss/fund-lock condition triggered purely by normal, permissionless use of a standard token category (fee-on-transfer/rebasing), not by any privileged or adversarial infrastructure actor.

### Likelihood Explanation
Likelihood is moderate to high wherever the Tron `IntentGatewayV2` is deployed with a governance-added FOT or rebasing token in its supported input set (or if such a token is deployed without an allowlist restricting inputs — the contract itself imposes no token-type restriction on `order.inputs`). Any user can trigger the divergence simply by placing an order denominated in such a token; no special access or timing is required. The primary EVM contract has already been fixed for this exact scenario (see the balance-diff logic and dedicated tests), confirming the project acknowledges this class of risk — but the fix was not carried over to the Tron variant.

### Recommendation
Apply the same balance-before/after measurement used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: snapshot the contract's token balance immediately before each `safeTransferFrom` in `placeOrder`, and use `balanceAfter - balanceBefore` as the actual received amount for computing `reducedInputs`, the commitment, and the `_orders` escrow credit — rather than trusting `order.inputs[i].amount`.

### Proof of Concept
1. Governance/admin registers (or the contract otherwise accepts) a fee-on-transfer ERC20 token, e.g. 1% fee, as a valid `order.inputs[i].token` on the Tron `IntentGatewayV2`.
2. User A calls `placeOrder` with `inputs[0].amount = 1000` of the FOT token. The contract's `safeTransferFrom(msg.sender, address(this), 1000)` actually delivers only `990` tokens to the contract (fee-on-transfer skims 10).
3. Despite receiving only 990 tokens, `_orders[commitment][token]` is credited with `reducedInputs[0].amount` (990 minus any protocol fee, e.g. 990 if fee is 0%) — but more importantly, this number is computed from the *stated* 1000, not the 990 actually held; if protocol fee is 0 the ledger is credited a full 990 while other outstanding orders for the same token already assume the token balance is fully backing their own escrow.
4. Repeat with multiple users/orders using the same FOT token: each placement leaks ~1% of value to the token's fee mechanism while `_orders` sums record the full pre-fee-adjusted amounts.
5. When solvers redeem via `withdraw()`/`onAccept`, the contract attempts to pay out the full ledger amounts. Once cumulative fee leakage exceeds the contract's actual token balance, a subsequent legitimate redemption's `token.call(transfer.selector, beneficiary, amount)` fails or under-pays, leaving that order's beneficiary unable to claim funds they are entitled to under the ledger — a direct loss/lock of user funds caused entirely by an unprivileged actor's normal order placement.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount");

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
