Based on my investigation, I found `matchGitHubRepository()` in `app/src/lib/repository-matching.ts`, which is the closest analog to the M-19 pattern: an identity/authorization check that validates *some* representations of "who is trusted" but omits an equally valid one, and — critically — this check is used to select which authenticated account's OAuth token gets attached to network requests for an attacker-influenced remote.

### Title
Repository-to-account matching trusts hostname alone, letting a spoofed remote name select the wrong account for API credential use - (File: app/src/lib/repository-matching.ts)

### Summary
`matchGitHubRepository()` decides which signed-in `Account` "owns" a given git remote purely by comparing the remote's parsed hostname to each account's endpoint hostname, case-insensitively. It never verifies that the `owner`/`name` pair actually corresponds to a repository the matched account can access. This mirrors the Sherlock M-19 pattern of an overly narrow/incomplete identity check, but instead of *rejecting* a legitimate actor, the incomplete check here causes Desktop to silently *accept and use* a mismatched context — attaching an authenticated account's identity/API token to arbitrary owner/name pairs sourced from a remote URL, with no ownership or access verification at the matching layer.

### Finding Description
```ts
// app/src/lib/repository-matching.ts:29-46
export function matchGitHubRepository(
  accounts: ReadonlyArray<Account>,
  remote: string
): IMatchedGitHubRepository | null {
  for (const account of accounts) {
    const htmlURL = getHTMLURL(account.endpoint)
    const { hostname } = URL.parse(htmlURL)
    const parsedRemote = parseRemote(remote)

    if (parsedRemote !== null && hostname !== null) {
      if (parsedRemote.hostname.toLowerCase() === hostname.toLowerCase()) {
        return { name: parsedRemote.name, owner: parsedRemote.owner, account }
      }
    }
  }
  return null
}
``` [1](#0-0) 

This function is fed directly from an attacker-influenced value: the `origin`/`upstream` remote URL of a cloned or fetched repository (`gitStore.defaultRemote.url`), via `app-store.ts`'s `matchGitHubRepository(repository)` helper: [2](#0-1) 

The result feeds `repositoryWithRefreshedGitHubRepository`, which calls `api.fetchRepository(owner, name)` using the *matched account's* API client, then persists the API response as the repository's associated `GitHubRepository` (including `cloneURL`, `permissions`) and can subsequently trigger `updateRemoteUrl()` to overwrite the local remote with the API's `clone_url`: [3](#0-2) [4](#0-3) 

The broken invariant: the only thing verified before using a signed-in account's credentials against an `owner/name` pair is that the *hostname string* matches — there is no check that `owner` is the authenticated user, a collaborator, or otherwise entitled to that specific repository. This is the same class of gap as M-19: the guard checks one valid form of authorization (holder/hostname) but omits verifying the actual resource-level right (operator approval/ownership of the specific repo), so any owner/name pulled from an attacker-controlled remote is treated as legitimate input to the authenticated API call and to `updateRemoteUrl`, which can silently rewrite the tracked remote URL for the repository based on unverified matching.

### Impact Explanation
An attacker who controls a remote URL a user adds/clones/fetches from (e.g., a git server responding on the same hostname pattern, or a malicious fork hosted under an attacker `owner` on the same GitHub/GHE hostname) can cause Desktop to:
- Query the GitHub API using the victim's own authenticated account for an `owner/name` chosen by the attacker (information-disclosure/probing of private repos the account can access is bounded by API permissions, but the *pairing decision* itself has no authorization check).
- Have `updateRemoteUrl()` silently rewrite the local git remote to the `clone_url` returned by the API for that mismatched pairing when `urlMatchesRemote` heuristics line up, altering what the user unknowingly pushes/fetches to next — a silent corruption of the push/fetch destination.

This is bounded (it doesn't grant write access beyond what the account already has), but it demonstrates the same broken-invariant class as M-19: authorization decisions made from an incomplete identity check (hostname-only) rather than validating the specific resource relationship.

### Likelihood Explanation
Moderate-to-low. It requires a user to add/clone a remote under a hostname that matches one of their signed-in accounts' endpoints (trivial for github.com, since almost every Desktop user has a github.com account), and for the API lookup / `updateRemoteUrl` heuristics in `update-remote-url.ts` to align (protocol match + prior clone URL match) before it rewrites the remote silently.

### Recommendation
Do not rely solely on hostname matching in `matchGitHubRepository()` to select an account for API calls that will influence stored `GitHubRepository` data or trigger `updateRemoteUrl()`. After matching by hostname, verify that the matched account actually has a relationship to the specific `owner`/`name` (e.g., require a successful, permission-checked `fetchRepository` call with an explicit ownership/collaborator check) before using its result to overwrite `remote` state via `updateRemoteUrl`.

### Proof of Concept
1. Sign in to Desktop with a GitHub.com account.
2. Clone or add a remote pointing to `https://github.com/attacker-controlled-owner/some-repo.git` (attacker-controlled owner/name, same `github.com` hostname).
3. Desktop's periodic repository refresh calls `matchGitHubRepository()`, which matches solely on hostname (`github.com` == `github.com`), returning `{ owner: 'attacker-controlled-owner', name: 'some-repo', account: <victim account> }` with no check that the victim has any real relationship to that repo.
4. `repositoryWithRefreshedGitHubRepository()` uses the victim's account/API client to fetch that repo's metadata and, via `updateRemoteUrl()`, can silently rewrite the local remote URL if the update conditions in `update-remote-url.ts` are met — changing what the user's next `push`/`fetch` targets without an explicit user action or warning.

**Uncertainty:** I was not able to fully trace every downstream consumer of `matchGitHubRepository()`'s result (e.g., `pull-request-matching.ts`, `find-upstream-remote.ts`) within the available index to confirm all code paths where this mismatch could escalate beyond metadata/remote-URL corruption; a full audit would require Devin to trace those additional call sites and the exact preconditions in `update-remote-url.ts` (`urlMatchesRemote`, `protocolsMatch`) that gate the silent remote rewrite.

  private async repositoryWithRefreshedGitHubRepository(
    repository: Repository
  ): Promise<Repository> {
    const repoStore = this.repositoriesStore
    const match = await this.matchGitHubRepository(repository)

    // TODO: We currently never clear GitHub repository associations (see
    // https://github.com/desktop/desktop/issues/1144). So we can bail early at
    // this point.
    if (!match) {
      return repository
    }

    const { account, owner, name } = match
    const { endpoint } = account
    const api = API.fromAccount(account)
    const apiRepo = await api.fetchRepository(owner, name)

    if (apiRepo === null) {
      // If the request fails, we want to preserve the existing GitHub
      // repository info. But if we didn't have a GitHub repository already or
      // the endpoint changed, the skeleton repository is better than nothing.
      if (endpoint !== repository.gitHubRepository?.endpoint) {
        const ghRepo = await repoStore.upsertGitHubRepositoryFromMatch(match)
        return repoStore.setGitHubRepository(repository, ghRepo)
      }

      return repository
    }

    if (repository.gitHubRepository) {
      const gitStore = this.gitStoreCache.get(repository)
      await updateRemoteUrl(gitStore, repository.gitHubRepository, apiRepo)
    }

    const ghRepo = await repoStore.upsertGitHubRepository(endpoint, apiRepo)
    const freshRepo = await repoStore.setGitHubRepository(repository, ghRepo)

    await this.refreshBranchProtectionState(freshRepo)
    return freshRepo

    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)

  }

export async function updateRemoteUrl(
  gitStore: GitStore,
  gitHubRepository: GitHubRepository,
  apiRepo: IAPIRepository
): Promise<void> {
  // I'm not sure when these early exit conditions would be met. But when they are
  // we don't have enough information to continue so exit early!
  if (gitStore.defaultRemote === null) {
    return
  }

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }
}
