### Title
`cap_diff_for_prompt` measures diff caps in Unicode code points, not bytes, allowing multi-byte content to exceed `DIFF_TOTAL_BYTES`/`DIFF_PER_FILE_BYTES` by up to 4x - ([File: plugins/security-guidance/hooks/review_api.py])

### Summary
`cap_diff_for_prompt` enforces `DIFF_PER_FILE_BYTES` and `DIFF_TOTAL_BYTES` using Python's `len(content)` on `str` values, which counts Unicode code points, not encoded bytes. An attacker who controls file content that is later diffed and sent to `build_investigate_prompt` can pad it with multi-byte (e.g. CJK, emoji, astral-plane) characters so the actual UTF-8 payload transmitted to the external model is several times larger than the configured byte budget.

### Finding Description
`cap_diff_for_prompt` truncates and accumulates using `len(content)` [1](#0-0) , and the constants are explicitly named as byte caps: `DIFF_PER_FILE_BYTES = int(os.environ.get("DIFF_PER_FILE_BYTES", "80000"))` / `DIFF_TOTAL_BYTES = int(os.environ.get("DIFF_TOTAL_BYTES", "400000"))` [2](#0-1) . Since Python `str.__len__` counts code points and diff content is a decoded text string (not raw bytes), any character outside the ASCII/Latin-1 range that encodes to 2–4 bytes in UTF-8 is counted as "1 byte" toward the cap. `build_investigate_prompt` calls `cap_diff_for_prompt(diff_files)` and directly embeds the (uncapped-by-actual-bytes) content into the prompt string sent to the model [3](#0-2) . There is no `.encode("utf-8")` length check anywhere in the capping logic, so an attacker-controlled file consisting largely of 3-4 byte UTF-8 characters (e.g. CJK ideographs or emoji) can pass through the length check while its actual transmitted byte size is up to ~4x the intended `DIFF_PER_FILE_BYTES`/`DIFF_TOTAL_BYTES` limits.

### Impact Explanation
This weakens (but does not fully defeat as "unbounded") the byte-budget invariant intended to bound outbound data volume to the external LLM API. The practical amplification factor is bounded (~4x, the max UTF-8 encoding width), not unbounded — a `400000`-length string of 4-byte code points would produce ~1.6MB of actual UTF-8 payload against a 400KB intended cap. This is a real accounting bug in a cost/exfiltration-scope control, but the impact is a bounded multiplier over the configured budget rather than truly unbounded exfiltration, since the cap still limits the *character count*, and per-file/total structure still applies (each file and the overall diff are still character-count-bounded).

### Likelihood Explanation
Trivially reachable: any file an attacker can influence content of (via a tracked/untracked file the victim subsequently diffs/commits) can contain arbitrary Unicode text, and no encoding-normalization or byte-length check occurs before the size check. The precondition (attacker controls file content that a victim reviews via this pipeline) matches the stated threat model, and the flaw reproduces deterministically for any input containing multi-byte characters.

### Recommendation
Compute cap accounting against `content.encode("utf-8", errors="surrogateescape")` byte length (or track/truncate by encoding to bytes and slicing bytes, then re-decoding safely with `errors="ignore"`/`"replace"` to avoid splitting multi-byte sequences) rather than `len(content)` on the `str`. Ensure `DIFF_PER_FILE_BYTES`/`DIFF_TOTAL_BYTES` are enforced against the same encoding that is ultimately transmitted over the network (UTF-8 JSON payload to the Claude API).

### Proof of Concept
Unit/invariant test in `review_api.py`'s test suite:
```python
def test_cap_diff_for_prompt_enforces_actual_utf8_bytes():
    # 100_000 CJK characters, each 3 bytes in UTF-8 => 300_000 actual bytes
    content = "字" * 100_000
    capped, dropped = cap_diff_for_prompt([("f.py", content)])
    total_utf8_bytes = sum(len(c.encode("utf-8")) for _, c in capped)
    assert total_utf8_bytes <= review_api.DIFF_TOTAL_BYTES, (
        f"transmitted UTF-8 bytes {total_utf8_bytes} exceeds "
        f"DIFF_TOTAL_BYTES={review_api.DIFF_TOTAL_BYTES}"
    )
```
Expected: this assertion currently fails (300,000 UTF-8 bytes reported as within cap since `len(content) == 100000 < 400000`), demonstrating the accounting gap. Fuzz variant: generate random strings mixing ASCII and 4-byte astral code points (e.g. `\U0001F600`) and assert `len(capped_content.encode("utf-8")) <= DIFF_PER_FILE_BYTES` per file and cumulative total `<= DIFF_TOTAL_BYTES`.

```python
def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()
        + "\n\nInvestigate per the method in your instructions, then return "
        "the findings list."
    )
```
