Based on the evidence gathered, the closest structural analog to the reported bug class — "a limit/guard that exists but can be silently bypassed by a value the attacker fully controls, letting an external actor push a trusted subsystem past a designed safety boundary" — is GitHub Desktop's opt-in override of git's `protocol.file.allow` submodule guard.

### Title
Submodule update can be forced to allow `file://` URLs from an untrusted checkout, bypassing git's built-in submodule protocol guard - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` builds the `git submodule update --init --recursive` argument list and, when its caller passes `allowFileProtocol: true`, prepends `-c protocol.file.allow=always` to the invocation. [1](#0-0)  This same boolean is threaded straight through the public `checkoutBranch` and `checkoutCommit` helpers, which default the parameter to `false` but let a caller flip it to `true` for any branch/commit checkout, including checkouts driven by remote data (e.g. PR branches from forks). [2](#0-1) [3](#0-2) 

### Finding Description
Since Git 2.38, `protocol.file.allow` defaults to `user` for `git submodule` operations specifically as a hardening measure against malicious `.gitmodules` files that declare submodule URLs using the `file://` scheme — such URLs let an attacker point a "submodule clone" at an arbitrary local path (e.g. `file:///home/victim/.ssh`) and have its contents copied into the working tree, effectively achieving an out-of-repo file read/exfiltration primitive (this is the class of bug fixed upstream as CVE-2022-39253 and related git advisories).

Desktop's `updateSubmodulesAfterOperation` explicitly reintroduces `-c protocol.file.allow=always` whenever `allowFileProtocol` is `true`, which unconditionally re-opens that guard for the entire `submodule update --init --recursive` invocation — including any nested/transitively-referenced submodules declared in the checked-out repository's `.gitmodules`. [4](#0-3)  The `.gitmodules` file and the SHAs it points at are attacker-controlled content in a cloned/fetched repository — exactly the "repository content" trust boundary called out as in-scope in the report's Valid Impact section. `listSubmodules` itself only reads `.gitmodules`/`.git/modules` to enumerate entries and applies no scheme allow-listing before update is invoked. [5](#0-4) 

The intended safety boundary here is git's own `protocol.file.allow=user` default; Desktop's `allowFileProtocol` flag is a deliberate escape hatch, and it is not the caller's responsibility to sanitize `.gitmodules` content before triggering an update with that flag set — the guard is either fully on or fully off for the whole recursive submodule tree.

### Impact Explanation
If any Desktop code path checks out attacker-influenced refs (e.g. a contributor's fork branch, a PR checkout, or any remote-provided branch/commit) with `allowFileProtocol: true`, a malicious `.gitmodules` entry with a `file://` URL can cause git to copy arbitrary local filesystem content (SSH keys, credential files, git config, etc.) into the user's working tree as part of the "submodule clone," where it then becomes readable/committable/exfiltratable by any code that consumes repository contents afterward. This matches the report's core theme: a numeric/boolean safety gate exists, but a value fully under the control of the untrusted party (the cloned repo's `.gitmodules`, analogous to the NFT receiver-count check) is what determines whether the gate is actually enforced.

### Likelihood Explanation
The vulnerability requires only that some caller of `checkoutBranch`/`checkoutCommit` sets `allowFileProtocol: true` for a ref that ultimately originates from an untrusted remote/fork (no local access, malware, or leaked credentials needed — just cloning/checking out attacker-supplied content, which is core, everyday Desktop functionality). I was not able to enumerate every call site of `checkoutBranch`/`checkoutCommit` within the available tool budget to confirm which flows pass `true`, so I cannot state with certainty that an *unprivileged, remotely-triggerable* call site currently sets this flag for untrusted refs — this is the main open question a follow-up investigation would need to resolve. Test fixtures show `protocol.file.allow=always` is used routinely to set up local submodule test fixtures, which confirms the flag is functional and does re-enable `file://` submodules, but those are test-only invocations, not proof of a live vulnerable call site. [6](#0-5) 

### Recommendation
Audit every call site of `checkoutBranch`, `checkoutCommit`, and `updateSubmodulesAfterOperation` to confirm `allowFileProtocol` is only ever `true` for repositories/refs the user has explicitly and knowingly trusted (e.g. local-only, non-remote scenarios), never for PR/fork checkouts or any ref sourced from a remote/API response. Consider parsing `.gitmodules` before invoking `submodule update` and rejecting/warning on `file://` (and other non-`https`/`ssh`) submodule URLs regardless of the `allowFileProtocol` flag, so the enforcement doesn't depend on a single boolean threaded through several layers of call sites.

### Proof of Concept
Conceptual reproduction (exact trigger path unconfirmed without further call-site tracing):
1. Attacker creates a public repository containing a `.gitmodules` file with an entry such as:
   ```
   [submodule "evil"]
     path = evil
     url = file:///Users/victim/.ssh
   ```
2. Victim uses a Desktop flow that ends up calling `checkoutBranch`/`checkoutCommit` with `allowFileProtocol: true` against this repository/branch (e.g. checking out a PR or fork branch, if such a call site exists).
3. `updateSubmodulesAfterOperation` runs `git -c protocol.file.allow=always submodule update --init --recursive`, and git happily "clones" `file:///Users/victim/.ssh` into `evil/`, copying the victim's private keys into the working tree where they are now part of the checked-out repository content. [7](#0-6)

export async function listSubmodules(
  repository: Repository
): Promise<ReadonlyArray<SubmoduleEntry>> {
  const [submodulesFile, submodulesDir] = await Promise.all([
    pathExists(join(repository.path, '.gitmodules')),
    pathExists(join(repository.path, '.git', 'modules')),
  ])

  if (!submodulesFile && !submodulesDir) {
    // repo path + .gitmodules and + .git/modules covers the vast majority of
    // "normal" repositories but if we're in a linked worktree the modules
    // directory is actually in the git common dir so we'll also check for the
    // existence of the modules directory there as well before giving up on the
    // existence of submodules in this repo. We're reading the commondir file
    // ourselves here instead of calling out to git to avoid the cost of
    // spawning a process on Windows
    const commonDirPath = join(repository.resolvedGitDir, 'commondir')
    const commonDir = await readFile(commonDirPath, 'utf8')
      .then(content => content.replace(/\r?\n$/, ''))
      .then(p => (p ? resolve(repository.resolvedGitDir, p) : null))
      .catch(() => null)

    if (!commonDir || !(await pathExists(join(commonDir, 'modules')))) {
      log.info('No submodules found. Skipping "git submodule status"')
      return []
    }
  }
