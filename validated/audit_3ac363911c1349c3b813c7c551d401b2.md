## Finding: Consensus-incentive rewards attribute an entire batch's state-machine updates to a single "first message" signer

### Title
Reward misattribution in `pallet-consensus-incentives::on_executed` pays the wrong relayer for multi-chain/multi-message consensus batches - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`FeeHandler::on_executed` extracts the reward beneficiary from `messages.get(0)` only, then pays that single signer for **every** `StateMachineUpdated` event in the whole batch, without checking which of the (possibly many) `Message::Consensus` entries in `messages` actually produced which update. A batch can legitimately contain several consensus messages (for different state machines, or different provers of the same consensus client) processed together in one `handle` extrinsic; only the signer of the first one is credited for the whole batch's reward span.

### Finding Description
`on_executed` (`modules/pallets/consensus-incentives/src/impls.rs:108-163`) does two independent things that don't stay bound to each other:

1. It picks a single `relayer_account` by decoding the signer of `messages[0]` only: [1](#0-0) 

2. It scans **all** `events` (not just events tied to `messages[0]`), collapses them per `state_machine_id` to the highest `latest_height` seen in the batch, and pays that single `relayer_account` for every one of those state machines: [2](#0-1) 

The in-code comment shows the pallet's authors already know this class of bug well — they previously had to patch a related double-payment bug where multiple `StateMachineUpdated` events for the *same* chain were each rewarded ("pays the same block-span reward N times"), and fixed it by collapsing to `highest_per_state_machine`: [3](#0-2) 

But that fix only handles the case of one state machine appearing multiple times in one relayer's own batch — it never re-derives which message caused which event. If a single extrinsic call to `pallet-ismp::handle` carries a `Vec<Message>` containing consensus proofs for **multiple distinct state machines** (a normal, supported batching pattern), or consensus proofs whose underlying signatures belong to different accounts, the reward computed from `calculate_reward` (`modules/pallets/consensus-incentives/src/impls.rs:78-100`, using `latest_commitment_height`/`previous_commitment_height`/`LastRewardedHeight` deltas) for *every* one of those chains is paid entirely to whoever happens to be `messages[0]`'s signer.

This is the direct analog of the Casimir `rewardStakeRatioSum` bug: both compute a reward from a state delta (blocks advanced / rewards accrued) that is legitimately owned by multiple distinct contributors across a batch, but the accounting collapses the batch into a single value/beneficiary instead of tracking per-contributor deltas. Casimir double-counted an unclaimed balance across reports; here the pallet single-attributes a multi-party delta to one party.

### Impact Explanation
This directly causes wrong-beneficiary fund transfers from the `TreasuryAccount` (`T::Currency::transfer(&treasury, &relayer_account, reward, ...)`, `modules/pallets/consensus-incentives/src/impls.rs:53-59`) plus a matching reputation-asset mint (`modules/pallets/consensus-incentives/src/impls.rs:67-68`). Whoever's message lands first in the `messages` vector for a batch drains treasury rewards that are meant to compensate the relayer(s) who actually advanced consensus for the *other* state machines in that batch. This is a genuine "stealing/loss of funds via wrong beneficiary" class of bug on a public, permissionless, unsigned entry point (`ensure_none`-gated ISMP message handling), not merely a relayer/prover trust assumption — the flaw is in how the pallet reconciles `events` back to `messages`, independent of who is honest.

### Likelihood Explanation
Requires a batch containing consensus messages/updates for more than one state machine (or otherwise decoupled from `messages[0]`'s signer) to be processed in a single `on_executed` call — a normal operational pattern for the relayer given multiple connected chains, not a contrived edge case. No compromised prover, governance action, or leaked key is needed; it only requires the batching pattern the pallet's own message-handling pipeline already supports.

### Recommendation
Bind each `StateMachineUpdated` event to the specific `Message::Consensus` entry (and its signer) that produced it, rather than collapsing all events in the batch to a single `messages[0]` signer. If the underlying `IsmpHost`/message-processing API doesn't expose a message-to-event correlation, add one (e.g., index events by the position/consensus-client of the message that emitted them) so `process_message` is called once per `(state_machine_id, signer)` pair actually responsible for that update.

### Proof of Concept
Conceptual reproduction (exact wiring of `pallet_ismp::handle` batching would need runtime-level confirmation):
1. Relayer A submits a valid `Message::Consensus` proof advancing `StateMachine::Evm(1)` from height 100 → 200.
2. In the same `handle` extrinsic call, a second `Message::Consensus` from relayer B advances `StateMachine::Evm(2)` from height 50 → 150, batched alongside A's message with A's message placed first (`messages[0]`).
3. `on_executed` receives both `StateMachineUpdated` events, collapses them to `{Evm(1): 200, Evm(2): 150}`, and calls `process_message` for both entries using `relayer_account` decoded solely from `messages[0]` (relayer A).
4. Relayer A is paid the full `blocks * block_cost` reward for **both** chains, including the span (50→150) that relayer B's message actually delivered; `LastRewardedHeight` for `Evm(2)` is advanced so relayer B can never claim that span.
