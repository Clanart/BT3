### Title
Fee/weight calculation omits the OP_RETURN output, producing a transaction that pays less than the required fee rate - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
The original bug class is a function reporting/using a declared parameter (`txData.GetGas()`, the gas *limit*) instead of the actual computed result (`res.GasUsed`). The direct analog in Serai lives in `SignableTransaction::new`, which derives `needed_fee` from a *reconstructed template transaction* rather than the transaction actually being built. The template passed to `calculate_weight_vbytes` only includes `payments` and the optional `change` output — it never includes the OP_RETURN `data` output that is pushed onto `tx_outs` before the weight is computed. The result is a signed transaction whose real fee rate is lower than the caller-requested `fee_per_vbyte`, potentially below the Bitcoin minimum relay fee.

### Finding Description
`SignableTransaction::new` builds the real output vector `tx_outs`, appending an OP_RETURN output carrying up to 80 bytes of caller-supplied `data` at send.rs:194-202. However, the fee is computed from `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)` at send.rs:204, whose synthetic `tx.output` is built *only* from `payments` (send.rs:85-94) — the OP_RETURN output is never represented.

A serialized OP_RETURN output costs ~9 + 1 + 80 ≈ 90+ vbytes that are entirely absent from `vbytes`, so `needed_fee = fee_per_vbyte * vbytes` (send.rs:206) underprices the true transaction. The same omission exists on the change path, where `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` (send.rs:225-226) again ignores the data output even though it remains in `tx_outs`.

The minimum-relay check at send.rs:211 uses this understated `vbytes`, so a transaction with `data` can pass the check while its actual weight makes its real feerate fall below `DEFAULT_MIN_RELAY_TX_FEE`. The honest `fee()` accessor (send.rs:138-141) confirms the discrepancy: it computes the real `sum(inputs) - sum(outputs)`, which the code itself acknowledges at send.rs:132 ("The actual fee this transaction will use is `sum(inputs) - sum(outputs)`") — mirroring the original bug where the reported value (needed/estimated) diverges from the actual value.

### Impact Explanation
An external party that causes a Serai multisig to sign a Bitcoin transaction with instruction data (the `data` parameter is populated from depositor/payment instructions) produces a transaction whose effective feerate is strictly below the requested rate, and which can fall under the mempool minimum relay fee. The signed transaction may then be unrelayable or stuck, leaving scanned multisig funds temporarily unspendable and requiring re-planning/re-signing — funds "received"/controlled that are not spendable at the intended terms, analogous to a receipt reporting wrong consumption. Since `SignableTransaction` feeds the FROST `TransactionMachine` which signs the underpriced sighash with `Prevouts::All` (send.rs:373-390), every participant's share commits to the fee-deficient transaction.

### Likelihood Explanation
Any payment flow carrying `data` of non-trivial length underprices the fee by roughly `fee_per_vbyte * (10 + data.len())` sats. With `data` near the 80-byte maximum and low fee rates (e.g., 1 sat/vbyte), the shortfall is ~90 sats, enough to drop a small transaction below relay minimums or significantly below target confirmation priority. The trigger requires only that a transaction include OP_RETURN data, which is a supported public code path.

### Recommendation
Include the OP_RETURN output (and any other output actually added to `tx_outs`) in the template passed to `calculate_weight_vbytes`, so `needed_fee` reflects the transaction that will actually be signed. Concretely, build the template output list from `tx_outs` (plus the hypothetical change output) rather than from `payments` alone, or compute the weight on the final `tx` once `tx_outs` is finalized, iterating if the change-output decision depends on the fee.

The signed transaction is constructed from `tx_outs` containing the OP_RETURN output (send.rs:246-251) while `needed_fee` was computed without it (send.rs:204-206), so `fee()` (send.rs:138-141) reports an actual fee whose rate is lower than the rate the caller specified.
