## Title
Fee-on-Transfer / Deferred-Deduction Tokens Break MasterMagpie's Staking Accounting, Enabling Over-Withdrawal at Other Stakers' Expense - (File: `rewards/MasterMagpie.sol`)

### Summary
`MasterMagpie` credits a user's staked balance with the full `_amount` parameter passed to `deposit`/`depositFor`, without verifying that the same amount actually arrived in the contract via `safeTransferFrom`. For any staking token that deducts a fee/tax on transfer (or otherwise delivers less than the nominal amount), this creates a permanent mismatch between the pool's real token balance and the sum of users' recorded `amount`/`available`, allowing depositors of such tokens to withdraw more than they contributed, at the expense of other stakers in the same pool.

### Finding Description
In `_deposit`, the user's balance is incremented by the full requested amount *before/regardless of* how much is actually transferred in: [1](#0-0) 

```
user.amount = user.amount + _amount;
if (!_isVlmgp) {
    user.available = user.available + _amount;
    IERC20(pool.stakingToken).safeTransferFrom(address(msg.sender), address(this), _amount);
}
```

There is no before/after `balanceOf` check (unlike, e.g., `WombatStaking.deposit`, which correctly measures `lpReceived` via a before/after balance diff [2](#0-1) ). If `pool.stakingToken` charges a transfer fee, the contract's real token balance increases by less than `_amount`, but `user.amount`/`user.available` are credited with the full nominal `_amount`.

On withdrawal, `_withdraw` pays out the full accounted amount regardless of what was actually deposited: [3](#0-2) 

```
function _withdraw(address _stakingToken, address _account, uint256 _amount, bool _isVlMgp) internal {
    _harvestAndUnstake(_stakingToken, _account, _amount, _isVlMgp);
    if (!_isVlMgp)
        IERC20(tokenToPoolInfo[_stakingToken].stakingToken).safeTransfer(address(msg.sender), _amount);
    ...
```

Because pool "size" for emission math (`_calLpSupply`) is based on the real `balanceOf(this)` for non-locker pools [4](#0-3) , the pool's real balance can be driven below the sum of all users' credited `amount`. The first users to withdraw after a fee-on-transfer deposit will drain real tokens belonging to other stakers, and the last stakers to withdraw will find the pool under-collateralized and unable to pay out their full recorded balance — a direct loss of funds for other, honest stakers. The same pattern exists in `emergencyWithdraw`, which pays `user.available` in full [5](#0-4) .

This is reachable entirely by an ordinary, unprivileged wallet: any depositor into a pool whose `stakingToken` is fee-on-transfer (or otherwise short-transfers) triggers the mismatch simply by calling the public `deposit`/`withdraw` functions [6](#0-5) . No admin misbehavior, oracle manipulation, or external protocol compromise is required — only that a pool for such a token exists, which is exactly the scenario the referenced external report warns about for a comparable lending protocol.

### Impact Explanation
Every deposit of a fee/tax-charging staking token permanently understates the real balance available to satisfy other stakers' recorded shares in that pool. Since withdrawals pay out the nominal (not actual) amount, an attacker (or even an ordinary user unaware their token has a fee) can extract more tokens than they contributed, directly at the expense of co-stakers in the pool, and can ultimately render the pool insolvent so that later stakers cannot withdraw their full recorded balance. This constitutes direct theft of user funds / protocol insolvency for that pool.

### Likelihood Explanation
Triggering the bug requires no privileged access — any wallet can call `deposit`/`withdraw` on a pool whose staking token happens to apply a transfer fee (a property of the token contract, not of MasterMagpie's admin). Given `add()` allows pool managers to whitelist arbitrary ERC20 contracts as staking tokens over the life of the protocol, and third-party/community LP or reward-bearing tokens sometimes introduce fees post-listing, the precondition is realistic, matching the exact concern already acknowledged (though not fixed) for the analogous pattern in the referenced report.

### Recommendation
In `_deposit`, measure the actual amount received by comparing `IERC20(pool.stakingToken).balanceOf(address(this))` before and after the `safeTransferFrom` call, and credit `user.amount`/`user.available` with that measured amount instead of the nominal `_amount`. Alternatively, explicitly document and enforce (e.g., via a transfer-fee check at pool-registration time) that only standard, non-fee-charging tokens may be registered as `stakingToken` in `add()`.

### Proof of Concept
1. Pool manager registers a fee-on-transfer ERC20 (e.g., 10% fee) as `pool.stakingToken` via `MasterMagpie.add()`.
2. User A calls `deposit(stakingToken, 100)`. `safeTransferFrom` delivers only 90 tokens to the contract, but `_deposit` sets `user.amount = 100`, `user.available = 100` [1](#0-0) .
3. User A immediately calls `withdraw(stakingToken, 100)`. `_withdraw` transfers the full 100 tokens out via `safeTransfer` [7](#0-6) , even though the pool only ever received 90.
4. The pool is now short 10 tokens relative to any other staker's recorded balance in the same pool; repeating this cycle (or having multiple depositors) drains the pool, leaving later withdrawers unable to redeem their full recorded `amount`.
