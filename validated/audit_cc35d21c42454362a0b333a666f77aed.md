Found a solid local analog. The bug pattern from the peg-oracle report — an incentive designed to protect one party silently pays out on the *other* direction because the check only verifies "is there a value" rather than "is the value correct/sufficient" — maps directly onto `fundRequest`'s refund path in `evm/src/core/EvmHost.sol`.

### Title
`fundRequest` additional fee is refunded entirely to the *original* dispatcher on timeout, silently misattributing funds contributed by a different payer - ([File: evm/src/core/EvmHost.sol])

### Summary
`fundRequest` lets **anyone** top up the relayer fee on a pending request [1](#0-0) , and the docs explicitly advertise this: *"someone else can fund your request"* / *"the additional fee goes to the payer address if the request times out"* [2](#0-1) . However `FeeMetadata` only tracks a single `sender` field, and `fundRequest` merges the new amount into the *existing* `metadata.fee` for that one stored `sender`, with no record of who actually contributed the incremental amount: [3](#0-2) 

On timeout, the entire accumulated `fee` (original dispatch fee + every top-up from every funder) is refunded as one lump sum to `meta.sender` — the original dispatcher only: [4](#0-3) 

This is structurally the same defect as the PegOracle bug: a value that should be attributed/paid in a specific direction (to the party who actually contributed the extra fee) is instead resolved using a single collapsed value (the *original* payer only), because the code never distinguishes "whose contribution is this" the same way the oracle bug never correctly resolved "which side of the peg is this."

### Finding Description
- `fundRequest` is permissionless and callable by any address, on any pending commitment, any number of times [3](#0-2) .
- The escrowed amount is pulled from `msg.sender`/`_msgSender()` via `safeTransferFrom` or a native-token swap, so the *actual payer* of each top-up is known at call time, but that information is discarded — only `metadata.fee += amount` is persisted against the pre-existing `sender`.
- `dispatchTimeOut` (POST) and the GET-timeout equivalent refund the whole `meta.fee` to `meta.sender` in a single transfer once the timeout callback succeeds [4](#0-3) .
- Any relayer-fee amount added by a *different* address than the original dispatcher (a common, explicitly documented use case — "gas prices spike, so a third party funds delivery" [5](#0-4) ) is permanently misdirected to the original `sender` if the request ever times out, rather than back to whoever actually paid it.
- Existing guards don't stop this: `fundRequest`'s only check is `metadata.sender == address(0)` (i.e., "does this commitment exist") [6](#0-5)  — exactly analogous to the PegOracle's flaw of checking *that* a value exists/compares, without checking *whose* value or in *which direction* it should be attributed.

### Impact Explanation
This falls inside the bounty scope as "unauthorized transaction/wrong beneficiary or amount" for a bridged asset: a legitimate third-party funder's fee tokens (potentially significant, since `fundRequest` supports repeated top-ups and native-token swaps) are transferred out of the protocol to an address (the original dispatcher) who did not contribute those funds, whenever a timeout occurs after multiple funders have topped up the same commitment. The original `sender` receives funds it never paid; the actual funder receives nothing. This is a real, unprivileged, protocol-level fund-misdirection bug, not merely relayer/operator behavior.

### Likelihood Explanation
Requires no malicious relayer, prover, or governance action — only two unprivileged accounts: the original dispatcher (or any attacker acting as one) and a third-party funder, plus the underlying request timing out. `fundRequest` and multi-party funding are explicitly documented and encouraged usage patterns (spiking gas prices), so the precondition (two distinct funders on one commitment, followed by a timeout) is realistic, not a contrived edge case.

### Recommendation
Track per-funder contributions (e.g., a `mapping(bytes32 => mapping(address => uint256))` of commitment → funder → amount funded) instead of collapsing all fee top-ups into the single `sender` field, and on timeout iterate/refund each funder their own contributed amount rather than paying the entire accumulated `fee` to `meta.sender`.

### Proof of Concept
1. Alice dispatches a `PostRequest` with `fee = 10` fee-tokens; `_requestCommitments[commitment] = {sender: Alice, fee: 10}`.
2. Bob observes gas prices spiking and calls `fundRequest(commitment, 50)`, paying 50 fee-tokens from his own balance. State becomes `{sender: Alice, fee: 60}` — Bob's contribution is nowhere recorded as his.
3. The request times out before delivery. `dispatchTimeOut` succeeds the app callback and executes `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` — i.e., `safeTransfer(Alice, 60)` [4](#0-3) .
4. Alice receives all 60 tokens, including the 50 Bob paid; Bob receives 0 and has no recourse — his 50 tokens are permanently lost to an unrelated party, with no admin/relayer/prover compromise required.

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }

    function fundRequest(bytes32 commitment, uint256 amount) external payable notFrozen {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                amount, path, address(this), block.timestamp
            );
        } else {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
        }

        FeeMetadata memory metadata = _requestCommitments[commitment];
        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;

        emit RequestFunded({commitment: commitment, newFee: metadata.fee});
    }
