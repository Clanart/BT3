### Title
Protocol fee is computed on the user-declared order amount before actual funds are swept, letting a `predispatch` call generate uncredited excess tokens that skip the fee — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
This is the same "declared amount vs. actual balance" divergence that broke Pumponomics in `FluidLocker::provideLiquidity`: a value-based mechanism (there, `_pump(ethAmount)`; here, `protocolFeeBps`) is applied to the caller-declared parameter, while the operation that actually moves funds sweeps **the full available balance** of an intermediary contract. In `IntentGatewayV2.placeOrder` (tron variant), the protocol fee is computed from `order.inputs[i].amount` *before* any tokens have actually moved, and the escrow/dust bookkeeping that follows sweeps the dispatcher's entire balance rather than only the fee-taxed amount.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, the protocol fee is computed first, straight from the caller-supplied `order.inputs[i].amount` (`originalAmount`), before any escrow transfer has occurred: [1](#0-0) 

Only afterward, in the `predispatch` branch, does the contract actually move tokens — and it sweeps the **entire balance** of the `dispatcher`, not just the amount the fee was calculated on: [2](#0-1) 

The excess above `requiredAmount` is only `emit`ted as `DustCollected` — it is never charged a protocol fee and is not reconciled against the fee already computed on `originalAmount`: [3](#0-2) 

Because `order.predispatch.call` is attacker-controlled calldata dispatched through `ICallDispatcher(dispatcher).dispatch(...)`, the order-placer can craft a predispatch call that causes the dispatcher to end up holding materially more of the input token/ETH than `order.inputs[i].amount` declares (e.g., an unwrap/redeem/claim call that yields more raw tokens than the nominal input, or simply pre-funding the dispatcher). Since the fee was already fixed on the smaller declared amount in Phase 2's calculation (executed before this sweep in the source ordering shown), the full excess balance flows into the gateway without any proportional protocol fee having been applied to it — exactly mirroring how `FluidLocker::_pump(ethAmount)` only pumped the explicit call amount while `provideLiquidity` consumed the contract's entire WETH balance.

Notably, the main (non-tron) `evm/src/apps/IntentGatewayV2.sol::placeOrder` was rewritten precisely to close this gap — its comment states *"we mutate order.inputs to reflect actual received so the commitment and escrow are consistent with what the gateway holds"* and it recomputes protocol fees in **Phase 2, after** actual balances are measured: [4](#0-3) [5](#0-4) 

This confirms the pattern is a known, previously-fixed bug class in the sibling implementation — but the tron contract still computes fees on the declared amount before the balance-sweep, reproducing the same "declared parameter vs. swept full-balance" divergence that enabled Pumponomics skipping in the seed report.

### Impact Explanation
Any value that lands in the dispatcher above the order's declared `requiredAmount` — whether from attacker pre-funding or from the predispatch call itself yielding more than declared — bypasses the protocol fee entirely and is only logged as "dust" rather than fee-taxed or captured into `_orders` accounting. This directly weakens the protocol's fee-collection mechanism (Hyperbridge's analog to Pumponomics buy-pressure/fee-revenue), causing the protocol to lose fees it is entitled to on real economic value moving through `IntentGatewayV2`, matching the "logic attack / loss of funds" impact class.

### Likelihood Explanation
`order.predispatch.call` and `order.predispatch.assets` are fully attacker-supplied by the order placer with no privileged actor, relayer, or prover involvement — an ordinary user calling `placeOrder` can shape the predispatch call to produce excess balance in the dispatcher relative to the declared `order.inputs[i].amount`, or simply pre-fund the dispatcher address directly (the same "transfer directly to the contract, then call with a dust official parameter" trick used in the original Superfluid PoC). No malicious peer, governance, or off-chain component is required.

### Recommendation
Port the main contract's fix into the tron variant: measure the dispatcher's actual token/ETH balance received for each input **before** computing `protocolFeeBps`/`reducedInputs`, and compute the commitment/fee from the actually-received amount (capped at `requiredAmount`, with any true excess still emitted as dust but never used to fund order fulfillment for free). Ensure `_orders[commitment][token]` is only ever credited from fee-adjusted, verified-received amounts, never from the pre-transfer declared amount.

### Proof of Concept
1. Attacker calls `IntentGatewayV2(tron).placeOrder(order, graffiti)` with `order.inputs[i].amount` set to a modest `requiredAmount` and `order.predispatch.call` pointing at a call dispatcher whose executed calldata (or attacker's separate pre-funding transfer to `dispatcher`) results in `dispatcher` holding `balance >> requiredAmount` in the input token before the sweep.
2. `protocolFee = (originalAmount * protocolFeeBps) / 10_000` is computed strictly from `requiredAmount` at lines 353-368, before any balance is inspected.
3. The sweep loop at lines 410-440 transfers the dispatcher's **full balance** to the gateway, computes `dust = balance - requiredAmount`, and only `emit`s it — no fee is charged on `dust`, and `_orders[commitment][token]` is credited only with the fee-adjusted `reducedInputs[i].amount`.
4. Net effect: the attacker's order is backed by materially more real value than the protocol fee was computed against, reproducing the "fee/pump computed on declared parameter while operation consumes full available balance" bug class from the seed report.
