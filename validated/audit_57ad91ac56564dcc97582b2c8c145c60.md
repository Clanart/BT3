### Title
Surjective `Scanner::register_offset` mapping lets an earlier offset claim a later deposit slot's script — deposits become credited to/spendable under the wrong offset - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The reference bug is a privilege-ownership mismatch: `ReachFactory` deploys `ReachDistributionV2`, so the deployer — not the intended user — is left owning the contract, and no ownership transfer ever occurs. In Serai, the analogous shape is `Scanner::register_offset` in bitcoin-serai: the function maps a requested scalar offset to a registered script surjectively, not bijectively. Because Taproot requires even-y internal keys, a requested offset `k` is silently incremented until `key + k*G` is even (`offset += Scalar::ONE`). If offset `k` was already registered, a request for `k-1` collides into `k`'s script and registration returns `None` — yet the script remains bound to `k`. Any deposit sent to the script a user derives for slot `k-1` is then attributed by `scan_transaction` to offset `k`, i.e., the output's controlling "owner" is a different slot than intended, with no transfer mechanism.

### Finding Description
`register_offset` loops, incrementing the caller-supplied scalar until `p2tr_script_buf(key + offset*G)` returns `Some` (even point) [1](#0-0) . The deduplication check is keyed on the resulting `script_pubkey`, not the requested offset (`self.scripts.contains_key(&script)` → `None`). Two adjacent requested offsets `k-1` (odd result, incremented to `k`) and `k` therefore map to the same effective scalar — but only the first-registered wins the `scripts` entry.

`scan_transaction` matches outputs purely by `script_pubkey` and stamps them with whatever offset won registration [2](#0-1) . There is no re-registration, replacement, or transfer path — the binding is fixed at first registration, exactly paralleling "ownership assigned at deployment to the wrong party with no transfer".

### Impact Explanation
If offsets are derived from publicly predictable data (e.g., sequential deposit slots, account indexes — the documented HDKD use case), an earlier slot's parity increment deterministically collides with the next slot's offset. A deposit intended for slot `k-1` is reported by the scanner as a `ReceivedOutput` carrying offset `k` — funds are credited under, and spendable only via, the wrong offset/spending policy. Where downstream code treats the registered offset as identifying the depositor/account, the earlier slot effectively "owns" the later slot's deposit. Conversely, if downstream code retries/derives a different address for the failed registration, the deposited funds may map to no registered slot and become unspendable under any expected key — "funds reported received that are not spendable".

### Likelihood Explanation
Reachable by an unprivileged party whenever offset values are influenced by external input or are simply sequential: collision requires only that some requested offset be odd-resulting (≈50% per the code's own comment) and adjacent to an already-registered offset. No key material, validator status, or collusion is needed — the attacker only needs a slot/offset allocated after a parity-bumped registration. The severity hinges on integrator usage of `register_offset` return (Some/None handling), so Medium is the appropriate ceiling.

### Recommendation
Make the mapping explicit and non-confusable:
- Return a distinct error/`None` when incrementing changes the requested offset, so a bumped scalar can never silently shadow a neighboring slot; or
- Check `self.scripts` for both the requested scalar's script *and* record the requested→effective mapping, rejecting registration if either collides; or
- Reserve even/odd staggering (e.g., only accept odd-indexed requests or pre-multiply by 2) so parity increments can never land on another slot's scalar.

```rust
  pub fn register_offset(&mut self, mut offset: Scalar) -> Option<Scalar> {
    // This loop will terminate as soon as an even point is found, with any point having a ~50%
    // chance of being even
    // That means this should terminate within a very small amount of iterations
    loop {
      match p2tr_script_buf(self.key + (ProjectivePoint::GENERATOR * offset)) {
        Some(script) => {
          if self.scripts.contains_key(&script) {
            None?;
          }
          self.scripts.insert(script, offset);
          return Some(offset);
        }
        None => offset += Scalar::ONE,
      }
    }
  }
```

```rust
  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
```
