### Title
Attacker-controlled `WWW-Authenticate` header from a git remote spoofs GitHub-host detection and auto-triggers an OAuth sign-in flow to the attacker's endpoint - (File: `app/src/lib/trampoline/trampoline-credential-helper.ts`)

### Summary
`getEndpointKind()` in the trampoline credential helper classifies an unknown git remote as a GitHub Enterprise host purely by pattern-matching the `realm="GitHub"` string inside a `WWW-Authenticate` header that Git forwards from the remote server's HTTP response. That header is fully attacker-controlled content coming from the remote the user is cloning/fetching/pushing to. A malicious git server can set this header to force Desktop to treat it as a trusted "GitHub Enterprise" endpoint, which changes the authentication UX from a passive username/password prompt into an active browser-based OAuth sign-in flow directed at the attacker's own server.

### Finding Description
When Git needs credentials for an HTTPS remote, it invokes Desktop's credential helper trampoline, which is handled by `createCredentialHelperTrampolineHandler` → `getCredential()`. [1](#0-0) 

To decide how to treat an unknown endpoint, `getEndpointKind()` first checks whitelisted GitHub/GHE hostnames, then falls back to reading `wwwauth[...]` credential fields — data captured by Git from the remote's HTTP `WWW-Authenticate` response header and forwarded verbatim to the helper: [2](#0-1) 

If the string `realm="GitHub"` appears anywhere in that attacker-supplied header, the endpoint is classified as `'enterprise'` — an authenticated, trusted GitHub host — without ever calling `isGitHubHost(endpoint)` (the actual API-based verification, which is only used as a last resort when no `wwwauth` header is present): [3](#0-2) 

Because `getCredential()` finds no stored account for this newly-"enterprise" endpoint, it invokes `ui.promptForGitHubSignIn(endpoint)`: [4](#0-3) 

`promptForGitHubSignIn` then automatically calls `dispatcher.beginEnterpriseSignIn()` and `setSignInEndpoint(origin)` — using the attacker's own remote origin as the sign-in endpoint — and pops the Sign-In dialog with only a generic message ("Git requesting credentials to access `<url>`"): [5](#0-4) [6](#0-5) 

If the user clicks "Continue with browser," Desktop opens an OAuth authorization URL built from that same attacker-controlled endpoint and, on callback, exchanges the returned code and fetches "user" data from that same endpoint: [7](#0-6) [8](#0-7) 

The broken invariant: Desktop's decision to treat a remote as an authenticated GitHub-branded identity provider (and to launch the OAuth account-linking UI) is derived from unauthenticated, attacker-supplied header text rather than a cryptographic or API-verified check of the host's identity. Unlike the manual Enterprise sign-in path (`EndpointEntry` step), which requires the user to type the address themselves, this path is triggered silently by ordinary git operations (clone/fetch/push) against a URL the attacker fully controls.

### Impact Explanation
An attacker who merely hosts a git HTTP server (no MITM, no compromised credentials, no local access — matching the "attacker controls ... a git remote/proxy response" model) can force GitHub Desktop to present what looks like a legitimate "Sign in to GitHub Enterprise" browser flow for their own domain during a normal clone/fetch. If the user proceeds, Desktop will complete an OAuth handshake and create/store an `Account` object bound to the attacker's endpoint inside Desktop's `AccountsStore`, i.e., unauthorized account binding driven entirely by remote-server response content rather than user intent to add that host as a trusted GitHub instance. It does not, on its own, allow harvesting of the user's *existing* GitHub.com/Enterprise credentials, because credential lookup for those is still keyed by exact stored-account origin matching (`findGitHubTrampolineAccount`), so this is not a full credential-exfiltration primitive, but it is a spoofable trust-classification bug that manipulates authentication UI/flow selection based on attacker input.

### Likelihood Explanation
Any user who clones, fetches, or pushes to an attacker-hosted HTTPS git remote will have their traffic pass through this code path automatically — there is no special repository content or unusual local step required, only a normal git network operation against a server the attacker controls. The only extra step required is the user clicking "Continue with browser" on the resulting Sign-In dialog, which many users will do reflexively since GitHub Desktop already trains them to expect this dialog when authenticating to enterprise git hosts.

### Recommendation
Do not use the unauthenticated `WWW-Authenticate`/`wwwauth[]` header content as a sufficient condition to classify a host as `'enterprise'`. Always corroborate it with the authenticated `isGitHubHost()` API probe (or drop the header heuristic entirely) before elevating an unknown endpoint into the OAuth sign-in flow, and surface the exact remote URL/host prominently (not just a generic message) whenever an automatic sign-in flow is triggered from a git credential request rather than direct user input.

### Proof of Concept
1. Attacker hosts `https://evil.example.com/some-repo.git`, configured so any unauthenticated HTTP request receives `401` with header `WWW-Authenticate: realm="GitHub"`.
2. Victim runs `git clone https://evil.example.com/some-repo.git` from GitHub Desktop.
3. Git invokes Desktop's trampoline credential helper; `getEndpointKind()` reads the forwarded `wwwauth[...]` value, matches `realm="GitHub"`, and returns `'enterprise'` without ever verifying via `isGitHubHost()`.
4. Since no stored account matches `evil.example.com`, `getCredential()` calls `ui.promptForGitHubSignIn('https://evil.example.com/...')`, which calls `beginEnterpriseSignIn()` + `setSignInEndpoint(origin)` with the attacker's origin, and shows the Sign-In dialog.
5. Victim clicks "Continue with browser"; Desktop opens an OAuth URL at `evil.example.com`, and on redirect calls `requestOAuthToken`/`fetchUser` against `evil.example.com`, storing whatever account identity the attacker's server returns as a new linked GitHub Enterprise account in Desktop.

**Uncertainty:** I could not fully trace `isGitHubHost()`'s implementation or `AccountsStore.addAccount` in this pass to confirm exactly how a spoofed account is persisted/used afterward; a Devin session with full repo access would be needed to verify downstream handling of the attacker-created `Account` object.

/** Implementation of the 'get' git credential helper command */
async function getCredential(cred: Credential, store: Store, token: string) {
  const ghCred = await getGitHubCredential(cred, store)

  if (ghCred) {
    return ghCred
  }

  const endpointKind = await getEndpointKind(cred, store)
  const accounts = await store.getAll()

  const endpoint = `${getCredentialUrl(cred)}`
  const apiEndpoint = getAPIEndpoint(endpoint)

  // If it appears as if the endpoint is a GitHub host and we don't have an
  // account for that endpoint then we should prompt the user to sign in.
  if (
    endpointKind !== 'generic' &&
    !accounts.some(a => a.endpoint === apiEndpoint)
  ) {
    if (getIsBackgroundTaskEnvironment(token)) {
      debug('background task environment, skipping prompt')
      return undefined
    }

    const account = await ui.promptForGitHubSignIn(endpoint)

    if (!account) {
      setHasRejectedCredentialsForEndpoint(token, endpoint)
    }

    return credWithAccount(cred, account)
  }

  // GitHub.com/GHE creds are only stored internally
  if (endpointKind !== 'generic') {
    return undefined
  }

  return useExternalCredentialHelper()
    ? getExternalCredential(cred, token)
    : getGenericCredential(cred, token)
}

  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })

  public async resolveOAuthRequest(action: IOAuthAction) {
    if (!this.state || this.state.kind !== SignInStep.Authentication) {
      return
    }

    if (!this.state.oauthState) {
      return
    }

    if (this.state.oauthState.state !== action.state) {
      log.warn(
        'requestAuthenticatedUser was not called with valid OAuth state. This is likely due to a browser reloading the callback URL. Contact GitHub Support if you believe this is an error'
      )
      return
    }

    const { endpoint } = this.state
    const token = await requestOAuthToken(endpoint, action.code)

    if (token) {
      const account = await fetchUser(endpoint, token)
      this.state.oauthState.onAuthCompleted(account)
    } else {
      this.state.oauthState.onAuthError(
        new Error('Failed retrieving authenticated user')
      )
    }
  }
