### Title
Unhandled underflow in mempool fee calculation can crash spend-bundle admission - (File: chia/full_node/mempool_manager.py)

### Summary
### Finding Description
In `MempoolManager.validate_spend_bundle`, the mempool computes the fee for an incoming, untrusted spend bundle as a plain Python integer subtraction before any check that additions do not exceed removals: [1](#0-0) 

`addition_amount` is accumulated directly from the `CREATE_COIN` conditions produced by the submitter-controlled spend bundle, and `removal_amount` is accumulated from the coin records being spent. There is no explicit check prior to line 814 (`fees = uint64(removal_amount - addition_amount)`) that `removal_amount >= addition_amount`. If a malicious or malformed spend bundle creates more value than it consumes (an attempted inflation/minting spend), `removal_amount - addition_amount` becomes negative, and casting a negative Python `int` to the strict `uint64` type used throughout the codebase raises an exception rather than yielding a controlled `Err` result — mirroring the `battleElo()` pattern where `currentRating + eloA - 1000` underflows and reverts instead of being range-checked.

This is directly analogous to the reported Solidity issue: a value derived from attacker-influenced inputs is subtracted without a bounds check, and the underflow surfaces as an uncontrolled revert/exception rather than a clean validation error, in a function that is on the hot path for processing every submitted transaction.

### Impact Explanation
If the exception is not caught by the caller of `validate_spend_bundle` (e.g. `add_spend_bundle` / RPC handlers in `mempool_manager.py`), a single crafted spend bundle submitted by any unprivileged party (wallet RPC, peer gossip, or local `push_tx`) could raise an unhandled exception during mempool admission instead of being cleanly rejected with `Err.MINTING_COIN` (which is the check that exists later, only in the consensus/block-validation path in `chia/consensus/block_body_validation.py`, not in the mempool admission path). This could disrupt mempool processing for the submitted bundle and, depending on exception propagation, affect the node's transaction-processing loop — a spend-triggered transaction-processing halt condition.

### Likelihood Explanation
Reachable by any unprivileged spend-bundle submitter: constructing a spend bundle whose `CREATE_COIN` conditions sum to more than the amount of the coins being spent is trivial (no signature validity requirement to reach this code path, only that the spend passes CLVM execution to produce `SpendBundleConditions`). This computation executes unconditionally for every spend bundle during `validate_spend_bundle`, before the consensus-level `MINTING_COIN` check that exists in block validation.

### Recommendation
Add an explicit check in `validate_spend_bundle` (mirroring `block_body_validation.py`'s `if removed < added: return Err.MINTING_COIN`) before computing `fees`, so that `removal_amount < addition_amount` is rejected with a controlled `Err` value rather than relying on the `uint64()` constructor to fail. This should be verified against the actual behavior of the `uint64` type in this codebase to confirm whether it raises on negative input (which I was unable to directly confirm from the available index — the `chia/util/ints.py` file defining `uint64` was not resolvable via search in this pass).

### Proof of Concept
Conceptual PoC: submit a spend bundle spending a single coin of amount `X` with a solution that includes a `CREATE_COIN` condition creating a coin of amount `X+1` (or several conditions summing above `X`). This is invalid (would mint value) but the mempool's fee computation at `chia/full_node/mempool_manager.py:814` executes `uint64(removal_amount - addition_amount)` with a negative operand before any minting-specific check occurs in this function, unlike the equivalent consensus check in `chia/consensus/block_body_validation.py:541-546`. I was not able to directly execute this in the current environment to confirm the exact exception raised (no terminal/code-execution access), so this should be validated by running `validate_spend_bundle` against such a bundle and observing whether it returns a clean `Err` or raises an unhandled exception.
