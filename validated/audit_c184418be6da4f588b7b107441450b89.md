### Title
TOCTOU symlink-race in AI conflict-resolution file reader lets a crafted merge conflict read files outside the repository and exfiltrate them to the Copilot service - (File: app/src/lib/copilot-conflict-context.ts)

### Summary
`buildConflictContext` in `app/src/lib/copilot-conflict-context.ts` validates that a conflicted file path stays inside the repository by calling `resolveWithin(workingDirectory, file.path)` once, and only then performs separate, later filesystem calls (`stat`, then `readFile`) against the *same string path* to load the file's contents for the Copilot conflict-resolution feature. This reproduces the exact bug class from the Ajna report: a safety-relevant value (“is this path safely inside the repo?”) is computed at one point in time and then relied upon at a *different* point in time, with no guarantee that the underlying filesystem state hasn't changed in between.

### Finding Description
`resolveWithin` (app/src/lib/path.ts:36-71) determines path safety like this: [1](#0-0) 

It calls `realpath()` on the fully joined path to detect symlink escapes, but then **returns the un-resolved, symlink-preserving path (`resolved`), not the realpath’d value**. The containment guarantee therefore only holds *at the instant the check runs*.

`buildConflictContext` uses this check-then-use pattern: [2](#0-1) 

Between the `resolveWithin` check (line ~393) and the subsequent `stat`/`readFile` calls (lines ~413/431), there are two `await` boundaries — enough time for the working directory to change. Git repositories can legitimately contain symlinks as tracked objects, and GitHub Desktop is confirmed to invoke repository-provided git hooks during git operations (`app/src/lib/hooks/get-repo-hooks.ts`, `app/src/lib/hooks/with-hooks-env.ts`), i.e. attacker-controlled code from a cloned/fetched repository *can* run during the exact operations (merge/checkout) that produce the conflict Desktop is about to inspect. A malicious repository can therefore:
1. Produce a merge conflict on a normal text file so the initial `resolveWithin` check passes and conflict markers are detected.
2. Use a hook invoked by the same git operation (or a subsequent concurrent operation triggered by Desktop, e.g. another background status/fetch) to atomically replace that path with a symlink pointing at a sensitive file outside the repository (e.g. `~/.ssh/id_rsa`, a `.netrc`, or Desktop's own credential store paths) before the `stat`/`readFile` executes.
3. `readFile(absolutePath, 'utf8')` then follows the swapped symlink and returns the *target file’s contents*, which are subsequently formatted into a prompt string and sent to the Copilot SDK/service (`formatConflictContextForPrompt`).

This is functionally identical to the Ajna issue’s root cause: a guard (`_getVotesScreening`/`resolveWithin`) is evaluated once, but the state it depends on (`block.number`/filesystem symlink target) is allowed to diverge from what is actually used at consumption time (`_screeningVote`/`readFile`), defeating the invariant the guard was meant to enforce.

### Impact Explanation
If exploited, this results in file read outside the repository root, and — because the file content is embedded into a request sent to the Copilot AI backend — exfiltration of sensitive local file contents (SSH keys, tokens, `.netrc` credentials, etc.) off the user's machine to a third-party network endpoint. This matches the "file read outside the repo" and "credential/token exfiltration" categories of valid impact for this task, and the attacker primitive required (crafting a cloned/fetched repository with conflicting content and a hook/symlink swap) is fully within the "attacker controls a cloned/fetched repository" scope, with no local/physical access, admin rights, or pre-existing host malware required.

### Likelihood Explanation
Exploitation requires: (a) the AI-assisted conflict resolution feature to be enabled and used on an attacker-supplied repository, and (b) winning a narrow TOCTOU race window between the `resolveWithin` check and the `stat`/`readFile` calls, or otherwise arranging for the hook execution to occur before the read. This makes it non-trivial but realistic: git hooks execute synchronously as part of the same git invocation that produces the conflict, and Desktop's async architecture inserts multiple `await` points between the check and the read, giving a hook (or another concurrent async filesystem operation triggered by Desktop itself, such as a background status refresh) a real opportunity to land in that window. I was not able to fully verify from static code alone the precise ordering guarantees between hook execution and `buildConflictContext`'s invocation, so the exact reliability of the race is uncertain and would need to be confirmed dynamically.

### Recommendation
- Resolve the path once and perform all subsequent filesystem operations (`stat`, `readFile`) against a file descriptor obtained via `open()`/`fs.promises.open` at that time, then use `fstat`/`read` on the descriptor rather than re-resolving the path string. This eliminates the TOCTOU window entirely.
- Alternatively, have `resolveWithin` return the `realResolved` (fully dereferenced) path instead of the symlink-preserving `resolved` path, and re-verify immediately before use with `O_NOFOLLOW` semantics where supported.
- Ensure hook execution triggered by conflict-producing git operations cannot race with the AI conflict-context construction (e.g., snapshot/copy conflicted files to a temp location immediately after the git operation completes, before any other async work runs).

### Proof of Concept
Conceptual reproduction (not run against a live instance):
1. Prepare a malicious upstream repository with two branches that conflict on `secret.txt` (a normal text file with conflict markers) and include a `post-checkout`/`post-merge` hook (or exploit another async operation racing in the same window) that, immediately after the merge command starts, replaces `secret.txt` in the working tree with a symlink to `~/.ssh/id_rsa`.
2. Have the victim clone/fetch this repository in GitHub Desktop and trigger a merge that produces the conflict.
3. Trigger the AI-assisted conflict resolution feature, which calls `buildConflictContext`. async function _resolveWithin(
```typescript
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
```
