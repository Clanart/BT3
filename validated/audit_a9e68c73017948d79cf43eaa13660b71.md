## Analysis

`_cancelFromDest` in [1](#0-0)  only gates the *caller* with an `order.user` check, and only while `order.deadline >= _blockNumber()`:

```solidity
function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
    if (order.deadline >= _blockNumber()) {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
    }

    _filled[commitment] = address(uint160(uint256(order.user)));
    ...
``` [2](#0-1) 

There is no check of `_filled[commitment] == address(0)` (the `Filled` error exists in `IntentsBase` for exactly this purpose, at [3](#0-2)  but is never referenced in `_cancelFromDest`). By contrast, `_fillCrossChain` sets `_filled[commitment] = msg.sender` unconditionally too, with the same absence of a re-entry guard [4](#0-3) .

The real double-payment protection lives on the *source* chain in `_withdraw`, which reverts with `UnknownOrder` if `_orders[commitment][token] == 0` [5](#0-4) . This does stop the same escrow slot from being drained twice — but it does **not** stop a *race*: after a solver legitimately fills an order pre-deadline (dispatching `RedeemEscrow` to the source chain) [6](#0-5) , any unprivileged address can call `_cancelFromDest` once the deadline passes on the destination chain and dispatch a competing `RefundEscrow` message for the very same commitment [7](#0-6) . Since Hyperbridge post-request delivery/processing order between the two independently-dispatched messages is not guaranteed to match dispatch order, whichever message's `onAccept` is processed first on the source chain wins the `_orders[...] == 0` race in `_withdraw` [8](#0-7) . If `RefundEscrow` lands first, the user is refunded the input escrow even though the solver already delivered the output tokens on the destination chain (per `_fillCrossChain`'s beneficiary transfer) — and the solver's legitimate `RedeemEscrow` then reverts with `UnknownOrder` when it is later processed, since the escrow is already zeroed. The user ends up with both the solver-delivered output tokens and their refunded input tokens, at the solver's expense.

This is a real double-settlement / wrong-beneficiary outcome reachable purely through unprivileged calls (permissionless post-deadline `_cancelFromDest`) and normal asynchronous message delivery — it is not blocked by the existing `_orders`-zero guard, because that guard only prevents the *same* withdrawal path from firing twice, not two competing withdrawal paths (`RedeemEscrow` vs `RefundEscrow`) racing for the same escrow.

### Title
Permissionless post-deadline `_cancelFromDest` can race an already-in-flight `RedeemEscrow` message, letting the user double-collect at the solver's expense - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_cancelFromDest` allows any unprivileged caller to trigger a `RefundEscrow` dispatch for an order after its deadline, without checking whether `_filled[commitment]` is already set (i.e., the order was already filled by a solver whose `RedeemEscrow` message is still in flight). This overwrites the `_filled` receipt and creates a race between two competing withdrawal messages targeting the same source-chain escrow.

### Impact Explanation
If the attacker's `RefundEscrow` message is processed on the source chain before the legitimate solver's `RedeemEscrow` message, the user receives their input tokens back via refund even though the solver already paid out the order's outputs on the destination chain. The solver's subsequent `RedeemEscrow` then reverts (`UnknownOrder`) because the escrow was already zeroed, so the solver never gets reimbursed. Net effect: wrongful double benefit to the user / loss of funds for the solver, and a broken "exactly-once" settlement invariant for `_filled`.

### Likelihood Explanation
Requires only a normal, unprivileged transaction (`_cancelFromDest`) after the order deadline, combined with the ordinary timing variability of cross-chain message relaying/finality between the destination and source chains — no malicious relayer, prover, or privileged role is needed.

### Recommendation
In `_cancelFromDest`, revert with `Filled()` if `_filled[commitment] != address(0)` before proceeding, mirroring the guard pattern already defined for this exact purpose in `IntentsBase`.

### Proof of Concept
1. Place a cross-chain order with `order.deadline = D`.
2. A solver calls the fill entrypoint before block `D`, executing `_fillCrossChain`, which sets `_filled[commitment] = solver` and dispatches `RedeemEscrow` to the source chain (delivery pending).
3. After block `D`, an unrelated address calls the cancel entrypoint invoking `_cancelFromDest`; since `order.deadline < _blockNumber()`, the `order.user` check is skipped, `_filled[commitment]` is overwritten to `order.user`, and `RefundEscrow` is dispatched to the source chain.
4. If `RefundEscrow` is delivered/processed on the source chain before `RedeemEscrow`, `_withdraw` refunds the user and zeroes `_orders[commitment][token]`.
5. When `RedeemEscrow` is later processed, `_withdraw` reverts with `UnknownOrder` — the solver, who already paid out the order on the destination chain, receives nothing.
