## Line-selection commit race: file's stale line-index selection is reapplied against a freshly re-diffed file, silently corrupting partial commits - (File: app/src/lib/git/apply.ts)

### Summary
`updateChangedFiles` in `app/src/lib/stores/updates/changes-state.ts` carries a file's line-based `DiffSelection` forward across status refreshes purely by matching the file's `id` (path), without ever verifying that the diff the selection indices were computed against still matches the file's current on-disk content. When the user later commits, `_commitIncludedChanges` in `app/src/lib/stores/app-store.ts` (lines 3681-3714) hands these `WorkingDirectoryFileChange` objects — with their carried-over `selection` — straight to `createCommit` → `stageFiles` → `applyPatchToIndex`. `applyPatchToIndex` (`app/src/lib/git/apply.ts:60`) re-fetches a brand-new diff (`getWorkingDirectoryDiff`) at commit time and then calls `formatPatch(file, diff)`, which indexes into that *new* diff using `file.selection.isSelected(absoluteIndex)` — i.e. the *old* line-index selection is blindly applied to a structurally different hunk layout. ### Finding Description
This is the same "two-step process with attacker-influenced state mutating between the step that decides the outcome and the step that finalizes it" class of bug as the Symmetry report: the UPNL is computed against a set of positions that can silently change underneath the user between the liquidation-start step and the liquidation-finish step, and nothing re-validates consistency before the funds-critical action (deallocate) executes. In Desktop, the analogous "critical action" is committing a partial selection of lines, and the "state that can silently change underneath" is the file's diff/hunk layout.

The flow:
1. The user opens the Changes view; Desktop computes a diff for a file and the user manually selects specific lines/hunks to include. This selection is stored as absolute line indices (`DiffSelection`, keyed by `unifiedDiffStart`-relative offsets) tied to *that specific diff*.
2. A background status refresh (`_loadStatus` → `updateChangedFiles`) runs (Desktop refreshes status very frequently: after fetches, on window focus, on file-watcher events, periodically). If the file on disk changed in the meantime — e.g. a fetch/checkout/merge touched it, an editor autosaved, a build tool regenerated it, or (as the report's threat model requires) an attacker-controlled process/hook/CI script or a malicious file the user cloned triggers a write — `updateChangedFiles` merely does `filesByID.get(file.id)` and reattaches `existingFile.selection` onto the *new* file object via `file.withSelection(existingFile.selection)`. There is no check that the new diff's hunk boundaries match the old one.
3. The user clicks "Commit". `_commitIncludedChanges` reads `state.changesState.workingDirectory.files` (the merged/stale-selection file objects) and passes them to `createCommit`.
4. `applyPatchToIndex` re-diffs the file fresh from disk (correctly, for correctness of git apply), but then calls `formatPatch(file, diff)` using the *old* selection object against the *new* diff's line indices. `formatPatch` walks the new diff's hunks and, for each line, asks `file.selection.isSelected(absoluteIndex)` — indices that were computed for a different diff.

Because hunk offsets, line counts, and content differ between the two diffs, the old selection bitmap silently includes/excludes the wrong lines. Nothing errors out — `git apply --cached` will happily apply a syntactically valid patch. The result is a commit whose content does not match what the user visually reviewed and intended to select, i.e. exactly the "silent corruption of what the user commits" impact category.

### Impact Explanation
An unprivileged actor who can trigger any file write in the working tree in the small time window between the user's diff/hunk selection and their commit click (e.g., via a malicious `post-checkout`/`post-merge` hook shipped in a cloned repo, a build script invoked by an npm/IDE integration, or content changes from a background fetch/merge/checkout Desktop itself performs) can cause the user's next partial commit to silently include or exclude different lines than the user selected. This can be used to smuggle unreviewed/malicious content into a commit the user believes is a clean, hand-reviewed partial commit, or to silently drop a security fix the user thought they were committing — undermining the integrity of what gets committed and eventually pushed.

### Likelihood Explanation
This does not require local/physical access, admin rights, or leaked credentials — only a file write anywhere in the working tree that races with the interval between the user reviewing/selecting diff hunks and pressing "Commit". Desktop's own background refresh cadence (post-fetch, file-system-watcher triggered `_loadStatus`, periodic refresh) plus common repo-side triggers (git hooks executed by Desktop itself, e.g. `post-checkout`, build watchers, editor autosave) make the underlying race condition easy to hit in normal use, especially for larger diffs where users take time to review/select hunks. The `clearPartialState` codepath in `updateChangedFiles` even acknowledges partial selections can become stale by resetting them to "include all" in some situations — but only for the commit-completion path, not for the general merge-status path that runs on every refresh while the user is still actively selecting lines.

### Recommendation
Tie a `DiffSelection` to the diff it was computed against (e.g., store a hash/identity of the diff content or the hunk structure alongside the selection) and invalidate/re-map the selection whenever `updateChangedFiles` detects the underlying diff has changed for a file with a `Partial` selection, rather than blindly reattaching indices by file `id`. At minimum, before `applyPatchToIndex`/`formatPatch` is invoked at commit time, re-verify that the diff freshly fetched matches the diff the selection was built against; if not, either reject the commit for that file and force the user to re-review, or fall back to committing "all" changes rather than silently applying mismatched line indices.

### Proof of Concept
1. Open a repository in Desktop with a file `foo.txt` containing multiple distinguishable hunks of changes.
2. In the Changes view, deselect all lines, then select only lines belonging to hunk A (e.g., lines 1-5) via the line-selection UI. This creates a `DiffSelection` with absolute indices anchored to the currently-displayed diff.
3. Without clicking Commit yet, externally modify `foo.txt` in a way that shifts hunk boundaries (e.g., add/remove lines earlier in the file, or run a git hook/background process that rewrites part of the file) so that a background `_loadStatus` refresh recomputes a structurally different diff for `foo.txt` (different `unifiedDiffStart` offsets/hunk counts). Confirm via `updateChangedFiles` that `existingFile.selection` is carried over unchanged (`file.withSelection(existingFile.selection)`).
4. Click "Commit". Observe that `applyPatchToIndex` re-fetches the diff fresh (`getWorkingDirectoryDiff`) and calls `formatPatch(file, diff)` with the stale selection.
5. Inspect the resulting commit's content (`git show HEAD -- foo.txt`) and compare it to what was visually highlighted/selected in step 2 — the committed lines no longer correspond to the originally selected hunk, demonstrating silent corruption of committed content.
