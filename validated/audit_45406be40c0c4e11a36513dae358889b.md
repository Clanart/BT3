### Title
Deserialized `ReceivedOutput` claims an offset/output pairing that is never verified, letting an untrusted party assert ownership of outputs the key cannot spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The bug class is "a caller supplies an input asset it does not own, and the system never verifies ownership before locking/spending it." In `bitcoin-serai`, the honest path (`Scanner::scan_transaction`) produces a `ReceivedOutput` whose `offset` provably corresponds to the scanned key (`output.script_pubkey == p2tr(key + G*offset)`, populated only via `self.scripts.get(&output.script_pubkey)` at `networks/bitcoin/src/wallet/mod.rs:205-211`). However, `ReceivedOutput::read` (`mod.rs:122-134`) accepts the `offset`, `output`, and `outpoint` fields as independent, unauthenticated claims: it reads a scalar and a `TxOut`/`OutPoint` but never re-derives `p2tr_script_buf(key + G * offset)` nor checks that the claimed `output.script_pubkey` equals it, nor that the `outpoint` actually exists/pays that `TxOut`.

### Finding Description
`ReceivedOutput` is the assertion "this outpoint's TxOut is spendable by our key offset by `offset`". `Scanner` guarantees this invariant by construction (script table built in `Scanner::new`/`register_offset` at `mod.rs:162-196`, lookup at `mod.rs:205`). The deserialization path drops the invariant entirely: `read_F` accepts any scalar, and the `TxOut`/`OutPoint` are consensus-decoded with no binding to the offset or to the scanner's key. Any party able to feed bytes to `ReceivedOutput::read` can therefore register an output under an offset that does not spend it — the exact analogue of starting a quest with an NFT the caller doesn't own.

### Impact Explanation
Downstream spending code (`networks/bitcoin/src/wallet/send.rs`) consumes `ReceivedOutput`s and produces a signature valid only for `key + G*offset`. For a forged `ReceivedOutput`:
- If the real outpoint pays a different script (e.g., an attacker-controlled P2TR output with a script path the attacker can satisfy, per the warning at `mod.rs:177-179`), Serai reports funds as received that are not spendable by its key — and are in fact spendable by the attacker. This matches the accepted impact "funds reported received that are not spendable" and can cause deposits to be credited to Serai that Serai can never claim.
- If the outpoint is nonexistent/spent, the built transaction is invalid, wasting fees or stalling signing.

### Likelihood Explanation
Reachability depends on whether `ReceivedOutput::read` consumes attacker-influenced bytes in deployment (e.g., outputs relayed between scanner and signer components). The `scan_transaction` path is safe; only the deserialization path is vulnerable. Impact when reached is real but is bounded to misreported/unspendable funds and invalid transactions rather than key compromise — Medium.

### Recommendation
Make `ReceivedOutput` self-validating: after deserializing, recompute `p2tr_script_buf(key + ProjectivePoint::GENERATOR * offset)` and require it equals `output.script_pubkey` (this requires passing the base key or a `Scanner` into `read`). Separately, consumers should confirm the `outpoint` resolves on-chain to the claimed `TxOut` (value + script) before treating it as received.

### Proof of Concept
```rust
// Attacker knows Serai's base key K and an offset O where
// p2tr_script_buf(K + G*O) = S_serai.
// Attacker crafts a TxOut paying to S_evil, a P2TR script they control
// (e.g., key path = attacker's key, or a script path they can satisfy),
// plus any outpoint of a real UTXO paying S_evil.

let mut bytes = vec![];
bytes.extend(O.to_bytes());              // valid scalar
bytes.extend(serialize(&txout_evil));    // script_pubkey = S_evil != S_serai
bytes.extend(serialize(&outpoint_evil));

let ro = ReceivedOutput::read(&mut &bytes[..]).unwrap(); // accepted, no check
// ro.offset() == O, so send.rs will sign as if it owned the output,
// yet the spend is invalid (or the funds belong to the attacker).
```

Confidence note: the missing-binding flaw in `ReceivedOutput::read` is confirmed directly from `mod.rs:122-134` versus the invariant enforced at `mod.rs:185-211`. The end-to-end exploitability (whether untrusted bytes actually reach `ReceivedOutput::read` and whether a consumer re-checks the outpoint on-chain) could not be fully verified within the available iterations; `send.rs` was not read.
