### Title
Clawback timelock has no upper bound validation, allowing indefinite griefing/locking of a recipient's clawback coin - ([File: chia/wallet/puzzles/clawback/drivers.py])

### Summary
`create_clawback_merkle_tree()` and the wallet's `ClawbackPuzzleDecorator` only enforce a lower bound (`timelock >= 1`) on the `timelock` (a `uint64`) used to build the clawback puzzle's `ASSERT_SECONDS_RELATIVE` claim condition. There is no upper-bound (sanity) check preventing a sender from setting an extremely large `timelock` value (up to `uint64` max) when creating a clawback coin to a recipient.

### Finding Description
`create_clawback_merkle_tree()` in [1](#0-0)  only validates:
```
if timelock < 1:
    raise ValueError("Timelock must be at least 1 second")
```
No maximum is enforced. This `timelock` value is embedded directly into the recipient's claim-path puzzle via `ASSERT_SECONDS_RELATIVE` (opcode 80), as seen in `create_merkle_solution()` [2](#0-1) , and the same unbounded value flows through the `ClawbackPuzzleDecorator` used by the standard wallet transaction path when a user creates an outgoing clawback spend (`decorate_target_puzzle_hash()` / `solve()`) [3](#0-2) . The `time_lock` value is read straight from user/CLI/RPC-supplied config (`clawback_timelock`) with no maximum check, and is stored as-is in the on-chain `REMARK` condition and in `ClawbackMetadata`.

Because the sender's own clawback path (`create_p2_puzzle_hash_puzzle(sender_ph)`) has no such `ASSERT_SECONDS_RELATIVE` restriction, the sender can always reclaim the coin immediately — but the *recipient's* only claim path is gated by `ASSERT_SECONDS_RELATIVE timelock`. This mirrors the reported bug class ("insufficient input validation of a time/period parameter, too large a value results in effectively lost/stuck funds for the counterparty, too small a value undermines the safety guarantee the clawback mechanism is meant to provide").

### Impact Explanation
If a sender (an unprivileged wallet user constructing an ordinary spend/offer with the clawback decorator) sets an unreasonably large `timelock` (e.g., near `uint64` max, representing centuries), the recipient's claim path becomes practically unusable — the funds are indefinitely inaccessible to the recipient unless the sender voluntarily claws them back. This is a griefing / "stuck yield" style issue analogous to the reported `TenetVesting` cliff/vestingPeriod bug: the counterparty who accepts what looks like a normal, short-timelock clawback payment can be misled or, in automated/offer-driven flows, receive a payment with an unexpectedly huge lock that they cannot practically verify without inspecting the raw solution.

### Likelihood Explanation
Low. It requires a sender to deliberately (or through misconfigured tooling defaults) set an excessive `clawback_timelock`. There is no on-chain enforcement or wallet-side upper-bound sanity check to prevent it, and no automatic warning is surfaced to the recipient before accepting such a coin.

### Recommendation
Add an upper-bound check in `create_clawback_merkle_tree()` (and ideally at the CLI/RPC parameter-parsing layer for `clawback_timelock` / `--clawback-time`) to reject unreasonable values (e.g., cap at some sane maximum such as a few years in seconds), mirroring the existing lower-bound check:
```python
if timelock < 1 or timelock > MAX_CLAWBACK_TIMELOCK:
    raise ValueError(...)
```
Additionally, wallet/CLI code accepting a recipient-visible clawback offer should surface the effective timelock duration prominently so a recipient can reject unreasonably long timelocks before accepting funds.

### Proof of Concept
1. Call `create_clawback_merkle_tree(timelock=uint64(2**64 - 1), sender_ph, recipient_ph)` — this succeeds without error (only `timelock < 1` is checked) [4](#0-3) .
2. Use this to build a clawback coin sent to a victim recipient via `generate_clawback_spend_bundle()` [5](#0-4) .
3. The recipient's claim solution requires `ASSERT_SECONDS_RELATIVE timelock` to pass, which for `timelock = 2**64-1` seconds will never be satisfiable within the chain's lifetime, while the sender retains an always-available reclaim path — permanently denying the recipient's claim path for that coin.

*(Note: this analog was derived by tracing the same input-validation-bug class — unbounded time/period parameters causing stuck funds — to the closest reachable code path in this repo, the clawback timelock. I was not able to fully confirm whether any additional layer, such as CLI parameter bounds in `chia/cmds/wallet_funcs.py` or `wallet_request_types.py`, imposes an upper bound; grep searches for `MAX`/bound keywords in the clawback puzzle module did not surface any additional cap, but I could not read every call site exhaustively within the available iterations.)*

def create_clawback_merkle_tree(timelock: uint64, sender_ph: bytes32, recipient_ph: bytes32) -> MerkleTree:
    """
    Returns a merkle tree object
    For clawbacks there are only 2 puzzles in the merkle tree, claim puzzle and clawback puzzle
    """
    if timelock < 1:
        raise ValueError("Timelock must be at least 1 second")
    timelock_condition = [ConditionOpcode.ASSERT_SECONDS_RELATIVE, timelock]
    augmented_cond_puz_hash = create_augmented_cond_puzzle_hash(timelock_condition, recipient_ph)
    merkle_tree = MerkleTree(
        [
            augmented_cond_puz_hash,
            curry_and_treehash(P2_CURRIED_PUZZLE_MOD_HASH_QUOTED, Program.to(sender_ph).get_tree_hash()),
        ]
    )
```

def create_merkle_solution(
    timelock: uint64,
    sender_ph: bytes32,
    recipient_ph: bytes32,
    inner_puzzle: Program,
    inner_solution: Program,
) -> Program:
    """
    Recreates the full merkle tree of a p2_1_of_n clawback coin. It uses the timelock and each party's
    puzhash to create the tree.
    The provided inner puzzle must hash to match either the sender or recipient puzhash
    If it's the sender, then create the clawback solution. If it's the recipient then create the claim
    solution.
    Returns a program which is the solution to a p2_1_of_n clawback.
    """
    merkle_tree = create_clawback_merkle_tree(timelock, sender_ph, recipient_ph)
    inner_puzzle_hash = inner_puzzle.get_tree_hash()
    if inner_puzzle_hash == sender_ph:
        cb_inner_puz = create_p2_puzzle_hash_puzzle(sender_ph)
        merkle_proof = create_merkle_proof(merkle_tree, cb_inner_puz.get_tree_hash())
        cb_inner_solution = create_p2_puzzle_hash_solution(inner_puzzle, inner_solution)
    elif inner_puzzle_hash == recipient_ph:
        condition = [80, timelock]
        cb_inner_puz = create_augmented_cond_puzzle(condition, inner_puzzle)
        merkle_proof = create_merkle_proof(merkle_tree, cb_inner_puz.get_tree_hash())
        cb_inner_solution = create_augmented_cond_solution(inner_solution)
    else:
        raise ValueError("Invalid Clawback inner puzzle.")
    solution: Program = Program.to([merkle_proof, cb_inner_puz, cb_inner_solution])
    return solution
```

def generate_clawback_spend_bundle(
    coin: Coin, metadata: ClawbackMetadata, inner_puzzle: Program, inner_solution: Program
) -> CoinSpend:
    time_lock: uint64 = metadata.time_lock
    puzzle: Program = create_merkle_puzzle(time_lock, metadata.sender_puzzle_hash, metadata.recipient_puzzle_hash)
    if puzzle.get_tree_hash() != coin.puzzle_hash:
        raise ValueError(
            f"Cannot spend merkle coin {coin.name()}, "
            f"recreate puzzle hash {puzzle.get_tree_hash().hex()}, actual puzzle hash {coin.puzzle_hash.hex()}"
        )

    solution: Program = create_merkle_solution(
        time_lock, metadata.sender_puzzle_hash, metadata.recipient_puzzle_hash, inner_puzzle, inner_solution
    )
    return make_spend(coin, puzzle, solution)

class ClawbackPuzzleDecorator:
    """
    This class is a wrapper for clawback puzzles. It allows us to add Clawback characteristics to the inner puzzle.
    """

    time_lock: uint64

    @staticmethod
    def create(config: dict[str, Any]) -> ClawbackPuzzleDecorator:
        self = ClawbackPuzzleDecorator()
        self.time_lock = uint64(config.get("clawback_timelock", 0))
        return self

    def decorate(self, inner_puzzle: Program) -> Program:
        # We don't wrap anything for the Clawback
        return inner_puzzle

    def decorate_target_puzzle_hash(
        self,
        inner_puzzle: Program,
        target_puzzle_hash: bytes32,
    ) -> tuple[Program, bytes32]:
        return (
            self.decorate(inner_puzzle),
            create_merkle_puzzle(self.time_lock, inner_puzzle.get_tree_hash(), target_puzzle_hash).get_tree_hash(),
        )

    def solve(
        self, inner_puzzle: Program, primaries: list[CreateCoin], inner_solution: Program
    ) -> tuple[Program, Program]:
        # Append REMARK condition [1, "CLAWBACK", TIME_LOCK, SENDER_PUZHSAH, RECIPIENT_PUZHSAH]
        if len(primaries) == 1:
            recipient_puzhash = primaries[0].puzzle_hash
            metadata = ClawbackMetadata(self.time_lock, inner_puzzle.get_tree_hash(), recipient_puzhash)
            remark_condition = Program.to(
                [
                    ConditionOpcode.REMARK.value,
                    RemarkDataType.CLAWBACK,
                    bytes(VersionedBlob(ClawbackVersion.V1.value, bytes(metadata))),
                ]
            )
            # Insert the REMARK condition into the condition list
            conditions = remark_condition.cons(inner_solution.rest().first().rest())
            conditions = inner_solution.rest().first().first().cons(conditions)
            inner_solution = inner_solution.replace(rf=conditions)
        return self.decorate(inner_puzzle), inner_solution
