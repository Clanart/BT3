### Title
Any participant can fatally blame/slash an honest validator by submitting a forged `EncryptedMessage` with a failing PoP in `VerifyBlame` - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary

`BlameMachine::blame` / `Decryption::decrypt_with_proof` unconditionally attributes an invalid per-message proof-of-possession (`pop` Schnorr signature) to the claimed `sender`. Since anyone can fabricate an `EncryptedMessage` whose `pop` does not verify, any accuser can cause `blame` to return an arbitrary honest participant as `faulty`. `processor/src/key_gen.rs` `VerifyBlame` then emits `ProcessorMessage::Blame { participant: accused }` for that victim, which the code comments state results in being "fatally slashed" — with no proof the share bytes ever came from the accused.

### Finding Description

`Decryption::decrypt_with_proof` verifies the message PoP and maps a failure to `DecryptionError::InvalidSignature` [1](#0-0) . `BlameMachine::blame_internal` then maps `InvalidSignature` to blaming the `sender` (i.e., the accused) [2](#0-1) .

The PoP challenge does bind the claimed sender via `transcript.append_message(b"sender", sender.to_bytes())` [3](#0-2) , but that only prevents *relabeling a valid message* — it does nothing against a *forged, intentionally-invalid* message. A Schnorr signature failing to verify proves only that bytes are malformed; it carries zero evidence that `sender` ever produced them. The API docs acknowledge the message "must have been authenticated as actually having come from the sender" [4](#0-3) , yet the processor's `VerifyBlame` handler performs no such check: it merely parses attacker-supplied `share` bytes via `EncryptedMessage::read` [5](#0-4) , builds an `AdditionalBlameMachine`, calls `blame(accuser, accused, substrate_share, substrate_blame)` [6](#0-5) , and slashes `accused` whenever either blame result equals `accused` [7](#0-6) .

### Impact Explanation

An invalid PoP is unforgeable evidence of *nothing* — it can be generated by anyone for any `msg.key`. Because `InvalidSignature` blames the accused unconditionally, a malicious participant can get any honest validator fatally slashed at zero cost (no key knowledge, no valid share needed, `blame` proof may be `None` since `InvalidSignature` returns before the proof is consulted [8](#0-7) ). Slashing is a direct financial penalty and ejects the victim from the validator set — analogous to the Ozone bug where an authenticated user could destroy/regenerate another user's secrets.

### Likelihood Explanation

Fully reachable by an unprivileged participant using only public inputs they control: the `accuser`, `accused`, `share`, and `blame` fields of `VerifyBlame`. The crafted `share` just needs `EncryptedMessage::read` to succeed (any valid-encoding point + any `R`,`s` scalars + a `SecretShare` payload) and the PoP to fail — trivially satisfiable. No collusion or special role required.

### Recommendation

`blame`/`decrypt_with_proof` must not attribute an `InvalidSignature` to `sender` unless there is authenticated evidence the message originated from that sender (e.g., requiring the accuser's channel-authenticated record of the accused's share, or making the PoP failure non-attributable/ambiguous rather than convicting the accused). At minimum, the processor should bind the submitted `share` to a message actually recorded as sent by `accused` before adjudicating.

### Proof of Concept

1. Participant `accuser` waits for (or triggers) a `VerifyBlame` opportunity and submits `accused = victim`, `share` = serialized bytes `{ key = G*x for random x, pop = (R = G*r, s = random scalar), msg = 32 zero bytes }`, `blame = None`.
2. `processor/src/key_gen.rs` parses it fine via `EncryptedMessage::read` [9](#0-8) .
3. `decrypt_with_proof` fails PoP verification → `InvalidSignature` [1](#0-0) .
4. `blame_internal` returns `sender` = victim for both substrate and network machines [8](#0-7) .
5. Processor returns `ProcessorMessage::Blame { participant: victim }` → victim is fatally slashed despite never sending any such message [7](#0-6) .
