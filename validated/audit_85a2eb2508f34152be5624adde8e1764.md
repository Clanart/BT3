### Title
Unvalidated `ReceivedOutput` deserialization can report unspendable outputs as wallet funds - (File: `networks/bitcoin/src/wallet/mod.rs`)

### Summary
`ReceivedOutput::read` accepts an arbitrary scalar offset, arbitrary `TxOut`, and arbitrary `OutPoint`, but never verifies that the offset derives the output’s `script_pubkey` or that the outpoint resolves to the encoded output. An unprivileged party supplying serialized wallet data can therefore cause an output that the `Scanner` would never recognize to be treated as a received output.

### Finding Description
`ReceivedOutput` represents a spendable output by combining `offset`, `output`, and `outpoint`. Its deserialization path validates only that `offset` is a canonical secp256k1 scalar and that the Bitcoin structures decode successfully. [1](#0-0) 

Legitimate outputs are produced by `Scanner::scan_transaction`, which looks up `output.script_pubkey` in `self.scripts`, obtains the corresponding registered offset, and binds the output to `OutPoint::new(tx.compute_txid(), vout)`. [2](#0-1) 

The deserialized path omits both sides of that binding:

1. It does not recompute `p2tr_script_buf(self.key + GENERATOR * offset)` and compare it with `output.script_pubkey`.
2. It does not verify that `outpoint` identifies a transaction output equal to `output`.

This matters because offsets are security-critical: `register_offset` warns that arbitrary offsets may introduce a script path, causing the output to be spendable by something other than the expected key-path signature. [3](#0-2) 

### Impact Explanation
A malicious serialized `ReceivedOutput` can report a Bitcoin output as wallet funds even though the wallet’s key cannot spend it through the intended Taproot key path. This matches the accepted impact class of “funds reported received that are not spendable.”

Depending on the caller, consequences include:

- Crediting an incoming payment that cannot be spent by the threshold key.
- Attempting to sign or construct a transaction using an offset unrelated to the output’s script.
- Persisting and later treating attacker-shaped wallet state as authentic scan results.

The issue is not the Bitcoin consensus decoding itself; it is the missing semantic validation tying the scalar offset, script, transaction output, and outpoint together.

### Likelihood Explanation
The vulnerability is reachable wherever serialized `ReceivedOutput` values cross a trust boundary through `ReceivedOutput::read`. The attacker does not need a validator key, threshold collusion, unsafe code, or protocol-level message forging. They only need to supply bytes encoding a canonical scalar followed by valid Bitcoin `TxOut` and `OutPoint` structures.

Exploitation is constrained by where the application stores or receives these values. If `ReceivedOutput` values are strictly locally generated by `Scanner` and never trusted after serialization, this is primarily an API-boundary weakness. If they are restored from untrusted storage or transmitted between components, it is directly exploitable.

### Recommendation
Do not expose `ReceivedOutput::read` as an unchecked trusted constructor. Either:

- Make the raw reader crate-private and only deserialize outputs generated by `Scanner`; or
- Add a validating reader such as `ReceivedOutput::read_for_key(reader, key)` which:
  1. Reads the scalar canonically.
  2. Recomputes the P2TR script for `key + GENERATOR * offset`.
  3. Requires it to equal `output.script_pubkey`.
  4. Verifies `outpoint` against the containing transaction before accepting the output.
  5. Rejects immature coinbase outputs when immediate spendability is required.

Persisting the scanner’s registered offset table separately does not remove the need to authenticate that mapping.

### Proof of Concept
Conceptually, construct a valid serialized object whose `offset` is zero but whose `TxOut` pays an unrelated P2TR key:

```rust
use bitcoin::{OutPoint, TxOut, Txid, hashes::Hash};
use bitcoin::key::XOnlyPublicKey;
use bitcoin::ScriptBuf;
use frost::curve::{Ciphersuite, Secp256k1};
use serai_bitcoin::wallet::ReceivedOutput;

let mut bytes = Vec::new();

// Canonical scalar zero.
bytes.extend(<Secp256k1 as Ciphersuite>::F::ZERO.to_repr().as_ref());

// A syntactically valid output paying some unrelated Taproot key.
let unrelated_xonly = XOnlyPublicKey::from_slice(&[2u8; 32]).unwrap();
let output = TxOut {
    value: bitcoin::Amount::from_sat(50_000),
    script_pubkey: ScriptBuf::new_p2tr_tweaked(
        bitcoin::key::TweakedPublicKey::dangerous_assume_tweaked(unrelated_xonly),
    ),
};
bytes.extend(bitcoin::consensus::encode::serialize(&output));

// Any syntactically valid outpoint.
let outpoint = OutPoint {
    txid: Txid::from_raw_hash(Hash::all_zeros()),
    vout: 0,
};
bytes.extend(bitcoin::consensus::encode::serialize(&outpoint));

let received = ReceivedOutput::read(&mut bytes.as_slice()).unwrap();
assert_eq!(received.value(), 50_000);
```

`read` accepts this object even though no scanner registration or Taproot derivation check has proven that `offset = 0` corresponds to the wallet key or the output script.
