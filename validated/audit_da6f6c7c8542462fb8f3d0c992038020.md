I found a concrete analog: `_findPullRequestBranch` in `app-store.ts` takes the `headCloneUrl` sourced from a GitHub API PR payload (`pullRequest.head.repo.clone_url`) — an attacker-controlled field for PRs opened from forks — and passes it directly to `addRemote`, and then to `_fetchRemote`, with no scheme/host validation, mirroring the report's pattern of an unchecked externally-supplied "address" being used to instantiate a trusted object (here, a git remote that is fetched).

### Title
Unvalidated PR head `clone_url` from GitHub API used to add and fetch a git remote - (File: app/src/lib/stores/app-store.ts)

### Summary
`_findPullRequestBranch` receives `headCloneUrl`, which ultimately comes from `pullRequest.head.repo.clone_url` in the GitHub API response for a pull request [1](#0-0) . Because a pull request's head repository is typically an attacker-controlled fork, this string is attacker-controlled data. It is passed unmodified to `addRemote`, which shells out to `git remote add <name> <url>` [2](#0-1) , and then to `_fetchRemote` to run `git fetch` against it [3](#0-2) . No validation of the URL's scheme/format equivalent to the report's "isContract"-style check is performed before this attacker-controlled value is used to configure a trusted git remote object.

### Finding Description
`_checkoutPullRequest`/`_findPullRequestBranch` accepts `headCloneUrl` and only checks whether it matches an existing remote via `urlMatchesRemote`; if no match is found it calls `addRemote(repository, forkRemoteName, headCloneUrl)` directly [4](#0-3) . `addRemote` simply forwards the string to `git remote add name url` [2](#0-1) , and the code then fetches the newly-added remote [3](#0-2) . Unlike `clone()` [5](#0-4)  or `parseRemote`/`remote-parsing.ts`, which constrain URLs to `https?://`, `git@`, `git:`, or `ssh://git@` patterns [6](#0-5) , there is no equivalent format/scheme gate applied to `headCloneUrl` before it reaches `addRemote`/`git fetch`. This is analogous to the `AutoTradingFund`/`MarginAccount` pattern in the report: an attacker-supplied "address" (here a git remote URL rather than a contract address) is used directly to instantiate a trusted resource (a configured git remote that is subsequently operated on) without validating that it conforms to an expected/safe shape.

### Impact Explanation
Existing guards (`urlMatchesRemote`, the regex-based `remoteRegexes` in `remote-parsing.ts`) are not enforced on this particular path — they are only used for *matching* against known remotes, not for *validating* `headCloneUrl` before `addRemote` is invoked. If `git remote add`/`git fetch` on this repository/host is reachable with a crafted value that doesn't need to match the expected GitHub host/scheme shapes (e.g., values relying on local file paths or alternate transports supported by the installed git binary), this could let a malicious fork's PR head URL cause the user's Desktop instance to fetch from or otherwise interact with a location the user did not intend, when they merely view/checkout a PR from a fork. This matches the task's valid-impact category of "attacker controls a git remote/proxy response" delivered via an attacker-controlled GitHub API object (the forked PR's `head.repo.clone_url`).

### Likelihood Explanation
Likelihood is significant because opening PRs from forks is a completely ordinary, unprivileged workflow — any GitHub user can open a pull request against a public repository and control the `head.repo.clone_url` value for their own fork (which is exactly the string returned by the GitHub API). Whenever a Desktop user clicks "checkout" on such a PR (via the branches list, a "checkout pull request" notification, or an `openrepo`/`openRepositoryFromUrl` deep link that resolves a PR), this code path is exercised without further confirmation of the URL contents.

### Recommendation
Before calling `addRemote`/fetching, validate `headCloneUrl` (and similarly `pullRequest.base.repo.clone_url` used in `getRepositoryFromPullRequest`) using the same strict parsing already implemented in `remote-parsing.ts`'s `parseRemote`, rejecting any URL that doesn't match the expected `https?://`/`git@`/`ssh://` GitHub remote shapes, mirroring how `clone.ts` and `enterprise-validate-url.ts` already gate other externally-supplied URLs before use.

### Proof of Concept
Exact reproduction steps could not be fully verified without running Desktop end-to-end (e.g., confirming precisely which crafted `clone_url` values the local git binary would treat unsafely), so this should be validated empirically:
1. Fork a public GitHub repository and open a pull request against the upstream repository.
2. Using the GitHub API (or by manipulating a locally-hosted GHE test instance if available) return a crafted `head.repo.clone_url` value that does not match the expected `https://`, `git@`, or `ssh://` shapes validated by `parseRemote`.
3. In Desktop, view the PR and choose "Checkout" (or click a deep link that triggers `openPullRequestFromUrl`), causing `_checkoutPullRequest` → `_findPullRequestBranch` → `addRemote(repository, forkRemoteName, headCloneUrl)` → `_fetchRemote` to run with the unvalidated value [7](#0-6) .
4. Confirm whether the unvalidated string reaches `git remote add`/`git fetch` verbatim and observe the resulting remote/fetch behavior, since this diverges from the stricter validation performed by `clone.ts`/`remote-parsing.ts` for other remote-URL entry points.
