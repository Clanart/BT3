Audit Report

## Title
Cross-Cluster CRDS Signature Replay via Missing Shred-Version/Cluster Binding in `CrdsValue::signable_data` - (File: `gossip/src/crds_value.rs`)

## Summary
`CrdsValue::signable_data()` serializes only `CrdsData`, omitting any shred-version or genesis-hash binding, so a signature valid on one cluster is valid on any cluster. The only cluster-separation control, `discard_different_shred_version` in `cluster_info.rs`, strictly checks shred-version solely for `CrdsData::ContactInfo`; for every other variant (`Vote`, `LowestSlot`, `EpochSlots`, `DuplicateShred`, `SnapshotHashes`, `RestartLastVotedForkSlots`, `RestartHeaviestFork`) it degrades to "does any record for this pubkey already exist," allowing cross-cluster replay of legitimately-signed values whenever the target cluster's CRDS table already holds any record for that pubkey.

## Finding Description
`CrdsValue::signable_data()` returns `wincode::serialize(&self.data)` with no cluster-identifying value included: [1](#0-0) 
Signing in `CrdsValue::new` signs exactly that same cluster-agnostic payload: [2](#0-1) 
Verification (`verify` / `verify_with_cache`) checks only the ed25519 signature over `signable_data()`, which is cluster-agnostic by construction: [3](#0-2) [4](#0-3) 

The sole cluster-separation control is `discard_different_shred_version`, applied to `PushMessage`/`PullResponse` payloads. It strictly enforces shred-version match only for `ContactInfo`; for all other variants it falls back to "does the local CRDS table already have any record for this pubkey," irrespective of that record's shred-version/cluster origin: [5](#0-4) 

This confirms the claimed exploit path: a `Vote`, `EpochSlots`, `RestartHeaviestFork`, or `RestartLastVotedForkSlots` `CrdsValue` legitimately signed by validator V on cluster A can be replayed verbatim into cluster B, provided V's pubkey already has any existing record (e.g., a `ContactInfo` entry, which itself would only be admitted if it matched cluster B's shred-version) in cluster B's CRDS table. The signature verification cannot detect the cross-cluster origin because the signed payload never encodes shred-version/cluster identity, and the transport-layer filter's fallback path (`crds.get_records(&value.pubkey()).next().is_some()`) provides no cluster binding for non-`ContactInfo` variants.

## Impact Explanation
An unprivileged network relay can inject foreign-cluster CRDS state into a target cluster under a real validator's identity without that validator's cooperation. The most consequential targets are `RestartHeaviestFork` and `RestartLastVotedForkSlots`, which feed the wen-restart cluster-recovery protocol — corrupting the aggregated restart-fork view other validators build during a live restart, i.e., degrading/corrupting halt-recovery consensus. Replayed `Vote`/`EpochSlots`/`DuplicateShred` values likewise pollute a validator's view of another validator's real-time consensus-relevant state. This aligns with the "false execution/rooting/acceptance, consensus halt" impact category via gossip, and exactly names the corrupted value: the CRDS table entries for `RestartHeaviestFork`/`RestartLastVotedForkSlots`/`Vote`/`EpochSlots` keyed under the victim's real pubkey.

## Likelihood Explanation
The attacker needs no privileged access, no key material, and no cooperation from the signer — only the ability to capture/relay ordinary gossip traffic, which matches the required unprivileged-attacker, public-input threat model. The precondition (target CRDS table already having a record for the replayed pubkey) is a plausible operational occurrence for validators whose identity is reused or observed across networks (test/dev clusters, coordinated multi-network operations), though it is a nontrivial precondition rather than universally satisfied.

## Recommendation
Bind the CRDS signature to the cluster by including a shred-version or genesis-hash-derived value inside `CrdsValue::signable_data()`, so signatures produced under one cluster fail verification under another. Additionally, make `discard_different_shred_version` require an exact shred-version match for all `CrdsData` variants rather than falling back to "any record exists for this pubkey" for non-`ContactInfo` types.

## Proof of Concept
1. Capture validator V's signed `CrdsValue` carrying `CrdsData::RestartHeaviestFork` (or `Vote`/`EpochSlots`) from cluster A's gossip traffic — signature is `Ed25519_Sign(V_priv, wincode::serialize(CrdsData))` per `CrdsValue::new`.
2. On cluster B (different shred_version), where V's pubkey already has a `ContactInfo`/other record in the local CRDS table, wrap the captured bytes in `Protocol::PushMessage(V_pubkey, [captured_value])` and send to a cluster B node.
3. In `discard_different_shred_version`, since the variant is not `ContactInfo`, the check falls through to `crds.get_records(&value.pubkey()).next().is_some()`, which is `true`, so the value passes the shred-version filter.
4. `verify_with_cache`/`verify` succeeds because the ed25519 signature is valid over `signable_data()`, which never encoded cluster A's shred version.
5. The foreign `RestartHeaviestFork`/`Vote`/`EpochSlots` entry is inserted into cluster B's CRDS table under V's real pubkey, polluting cluster B's view of V's state.

    pub(crate) fn verify_with_cache(&self, cache: &SigVerifyCache) -> bool {
        if cache.verified_values.contains(&self.hash) {
            return true;
        }
        let pubkey = self.pubkey();
        let signable_data = self.signable_data();
        let message = signable_data.borrow();
        let sig_bytes: [u8; 64] = self.signature.into();
        let signature = ed25519_dalek::Signature::from_bytes(&sig_bytes);
        let verified = match cache.verifying_keys.get(&pubkey) {
            Some(vk) => vk.verify_strict(message, &signature).is_ok(),
            None => {
                let Ok(vk) = ed25519_dalek::VerifyingKey::try_from(pubkey.as_ref()) else {
                    return false;
                };
                if vk.verify_strict(message, &signature).is_err() {
                    return false;
                }
                cache.verifying_keys.insert(pubkey, vk);
                true
            }
        };
        if verified {
            cache.verified_values.insert(self.hash);
        }
        verified
    }

// Discards CrdsValues in PushMessages and PullResponses from nodes with
// different shred-version.
fn discard_different_shred_version(
    msg: &mut Protocol,
    self_shred_version: u16,
    crds: &Crds,
    stats: &GossipStats,
) {
    let (values, skip_shred_version_counter) = match msg {
        Protocol::PullResponse(_, values) => (values, &stats.skip_pull_response_shred_version),
        Protocol::PushMessage(_, values) => (values, &stats.skip_push_message_shred_version),
        // Shred-version on pull-request callers can be checked without a lock
        // on CRDS table and is so verified separately (by
        // check_pull_request_shred_version).
        Protocol::PullRequest(..) => return,
        // No CRDS values in Prune, Ping and Pong messages.
        Protocol::PruneMessage(_, _) | Protocol::PingMessage(_) | Protocol::PongMessage(_) => {
            return;
        }
    };
    let num_values = values.len();
    values.retain(|value| match value.data() {
        CrdsData::ContactInfo(ci) => ci.shred_version() == self_shred_version,
        // for any other CRDS types we check if we store anything already
        // for this pubkey, if we do we allow more values in
        _ => crds.get_records(&value.pubkey()).next().is_some(),
    });
    let num_skipped = num_values - values.len();
    if num_skipped != 0 {
        skip_shred_version_counter.add_relaxed(num_skipped as u64);
    }
}
