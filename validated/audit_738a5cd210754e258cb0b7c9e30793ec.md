### Title
`SignableTransaction::new` computes weight/fee without the OP_RETURN data output, underpaying the fee and over-sizing change - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
Analogous to storing `_amount` instead of the post-fee amount, `SignableTransaction::new` computes the transaction weight — and therefore `needed_fee`, the `NotEnoughFunds` check, and the change output value — from only the payment outputs and optional change. The OP_RETURN `data` output is pushed onto `tx_outs` but is never fed into `calculate_weight_vbytes`, so the stored `needed_fee` and the computed change amount correspond to a smaller transaction than the one actually built and signed.

### Finding Description
In `networks/bitcoin/src/wallet/send.rs`, the data output is appended to `tx_outs` at lines 194–202, yet the weight calculation at line 204 calls `Self::calculate_weight_vbytes(tx_ins.len(), payments, None)`, whose `payments` argument is the raw `&[(ScriptBuf, u64)]` slice — not `tx_outs`. The OP_RETURN output (up to 80 bytes of data plus output overhead, ~90+ real bytes/vbytes) is therefore invisible to both the no-change fee (`needed_fee`, line 206) and the with-change fee (`fee_with_change`, line 227). Consequently:

- `needed_fee` (returned by `needed_fee()` and asserted against in `processor` tests) is smaller than the fee a correctly-sized transaction requires.
- The `input_sat < payment_sat + needed_fee` sufficiency check at line 215 can pass when the true required fee would make it fail.
- The change value at line 228 (`input_sat - payment_sat - fee_with_change`) is over-credited by the omitted output's cost, embedding the shortfall into the actual fee.
- The `TooLowFee` check at line 211 uses the undercounted `vbytes`, so a transaction whose *true* fee rate falls below `DEFAULT_MIN_RELAY_TX_FEE` can pass validation.
- The `MAX_STANDARD_TX_WEIGHT` check at line 241 likewise uses the undercounted `weight`.

The actual fee paid is still `sum(inputs) - sum(outputs)` (= the underestimated `fee_with_change`), so the signed transaction achieves a lower sat/vbyte rate than `fee_per_vbyte` requested — by roughly the vbyte size of the data output. With ~80 bytes of attacker-supplied data, that is ~90–100 vbytes of unpaid-for weight.

### Impact Explanation
`data` is caller-controlled bytes (used for embedding instructions, e.g., InInstruction/transfer shorthands, which derive from external user inputs). An unprivileged party who can cause a transaction with a large `data` payload to be constructed forces the multisig to sign a transaction paying materially less than the intended fee rate — potentially below the network's minimum relay fee, so the transaction cannot propagate and its inputs (including the over-valued change output) are unspendable until the transaction is rebuilt. This maps to the accepted class of "funds reported received/sent that are not spendable" and "incorrect value stored" (the change amount is computed against a fee that doesn't reflect the real transaction).

### Likelihood Explanation
The miscalculation occurs on every call that supplies non-empty `data`; reaching the min-relay or NotEnoughFunds boundary requires a large (~80-byte) payload or a marginal input amount. Underpaying the fee rate is deterministic; whether the TX is actually rejected depends on prevailing mempool policy, so the reliable harm is a systematically lower-than-specified fee rate and incorrect change sizing — Medium.

### Recommendation
Include the data output in the weight calculation. Change `calculate_weight_vbytes` to accept the actual output list (`tx_outs`, including the OP_RETURN and a placeholder change `TxOut`), or pass a `data_len` parameter so the OP_RETURN output is serialized into the sizing transaction before computing `weight`/`vbytes`. Then `needed_fee`, `fee_with_change`, the `NotEnoughFunds`, `TooLowFee`, and `TooLargeTransaction` checks all reflect the real transaction.

### Proof of Concept
From `networks/bitcoin/src/wallet/send.rs` (lines 188–256, shown above): construct

```rust
SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)
```

`tx_outs` gains a ~92-byte OP_RETURN output, but `vbytes`/`vbytes_with_change` are computed from a `Transaction` containing only the payment and change outputs. `tx.needed_fee()` returns `fee_per_vbyte * vbytes_underestimate`, while `tx.transaction()` serializes ~92 bytes larger. `tx.fee() / tx.transaction().vsize()` is strictly less than `fee_per_vbyte`, and for `fee_per_vbyte` near `DEFAULT_MIN_RELAY_TX_FEE` the produced transaction is below the minimum relay fee despite the line-211 check passing.
