### Title
Coinbase outputs paying a Serai multisig are either reported as immediately spendable (`Scanner::scan_block`) or permanently ignored (`Bitcoin::get_outputs`), so funds received via coinbase can never be correctly credited and spent - (File: networks/bitcoin/src/wallet/mod.rs, processor/src/networks/bitcoin.rs)

### Summary
The DODO `superWithdraw` bug is a "rescue path that cannot handle a class of legitimately-received funds": assets are permanently stuck because the withdrawal path only understands one token interface. The Serai analog lives in the Bitcoin output scanning pipeline. A coinbase transaction can pay to a Serai multisig's P2TR script just like any other transaction, but:

- `Scanner::scan_block` scans `block.txdata` including `txdata[0]` (the coinbase) and returns the coinbase outputs as ordinary `ReceivedOutput`s with no marker distinguishing them, even though they are bound by the 100-block maturity rule and are not yet spendable. `SignableTransaction::new` performs no maturity check, so a consumer that feeds such a `ReceivedOutput` in will produce a fully-signed transaction that the network rejects — funds reported received that are not spendable. [1](#0-0) 
- `Bitcoin::get_outputs` (the path the processor actually uses) fixes this by skipping the coinbase entirely via `&block.txdata[1 ..]`, but it does so unconditionally — it does not track coinbase outpoints and admit them after maturity. A coinbase output paying a Serai address is therefore never emitted as an `Output`, never enters `ram_outputs`, and is never spendable by the multisig. The funds are received on-chain yet permanently invisible to Serai. [2](#0-1) 

### Finding Description
`scan_transaction` emits a `ReceivedOutput` for every output whose `script_pubkey` is in `self.scripts`, with no notion of coinbase maturity [3](#0-2) . `scan_block` applies it to all of `block.txdata`, including `txdata[0]` [1](#0-0) . The only protection is a doc comment telling integrators to post-process [4](#0-3) , while `ReceivedOutput` carries no flag (only `offset`, `output`, `outpoint`) to let a consumer distinguish an immature coinbase output [5](#0-4) .

The processor's `get_outputs` takes the opposite approach and drops `txdata[0]` unconditionally: `for tx in &block.txdata[1 ..]` [6](#0-5) . Nothing downstream re-scans those coinbase outputs once mature — the scan cursor advances past the block, `ram_outputs`/DB only record what `get_outputs` emitted, and a re-scan of the same block would again skip `txdata[0]`. So a coinbase payment to a Serai address is a unilateral, permanent loss.

The library-half of the issue is also real: `SignableTransaction::new`/`multisig` validate only that the prevout's `script_pubkey` matches `p2tr_script_buf(offset.group_key())` [7](#0-6)  — a coinbase `ReceivedOutput` passes all checks, gets signed with `Prevouts::All`, and the resulting transaction is consensus-invalid for 100 blocks. There is no BIP-68/CB maturity check anywhere in `send.rs`.

### Impact Explanation
An unprivileged external party (any miner, or anyone who can cause a coinbase output to pay the multisig address — e.g., a pool directing payouts to a Serai deposit address) can make real BTC appear at a Serai-controlled script that the processor will never credit. Those funds are locked under a script Serai watches but an outpoint Serai refuses to index, forever. Symmetrically, any consumer using `Scanner::scan_block` as directed gets outputs reported as spendable which produce invalid transactions when spent — burning a signing round on an un-relayable transaction.

### Likelihood Explanation
Coinbase payments to arbitrary P2TR addresses are rare but fully attacker- or accident-reachable (a mining pool, a miner paying out to an exchange deposit address, or merged-mining side payments). Medium severity: permanent loss of funds limited to the coinbase-payment code path, requiring someone to pay the multisig via coinbase.

### Recommendation
- In `get_outputs` (`processor/src/networks/bitcoin.rs`), instead of unconditionally skipping `txdata[0]`, check maturity: for each scanned output in the coinbase, record the outpoint and emit it only once the block is ≥100 confirmations deep (e.g., a deferred-outputs queue keyed by block height), or document and enforce that coinbase payments are unsupported while still refunding/aggregating them later.
- In `Scanner`/`ReceivedOutput`, add an `is_coinbase`/maturity flag so consumers of `scan_block` can distinguish immature outputs, and have `SignableTransaction::new` reject inputs flagged as immature coinbase outputs.

### Proof of Concept
```rust
// Conceptual: miner pays Serai multisig via coinbase
let scanner = Scanner::new(group_key).unwrap();
// Block whose coinbase output[0] pays p2tr_script_buf(group_key)
let outputs = scanner.scan_block(&block);        // returns the immature coinbase output
// Consumer cannot tell it is immature:
assert_eq!(outputs[0].offset(), Scalar::ZERO);
let tx = SignableTransaction::new(vec![outputs[0].clone()], &payments, change, None, fee)
    .unwrap();                                     // succeeds; signed tx is consensus-invalid
// Meanwhile the processor path never emits it at any height:
let outputs = bitcoin.get_outputs(&block, group_key).await; // empty — txdata[1..] only
```

  pub fn scan_transaction(&self, tx: &Transaction) -> Vec<ReceivedOutput> {
    let mut res = Vec::new();
    for (vout, output) in tx.output.iter().enumerate() {
      // If the vout index exceeds 2**32, stop scanning outputs
      let Ok(vout) = u32::try_from(vout) else { break };

      if let Some(offset) = self.scripts.get(&output.script_pubkey) {
        res.push(ReceivedOutput {
          offset: *offset,
          output: output.clone(),
          outpoint: OutPoint::new(tx.compute_txid(), vout),
        });
      }
    }
    res
  }
