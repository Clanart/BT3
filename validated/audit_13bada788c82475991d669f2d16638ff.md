### Title
Blame verification inverts accuser/accused, fatally slashing the honest reporter and exonerating the faulty DKG participant - (File: processor/src/key_gen.rs)

### Summary
The PedPoP blame API is invoked with the `accuser`/`accused` arguments swapped. `AdditionalBlameMachine::blame(sender, recipient, msg, proof)` expects `sender` to be the accused dealer and `recipient` the accusing party. `KeyGen::handle` passes them reversed, so every `VerifyBlame` evaluation blames the honest accuser instead of the faulty dealer — an improper-attribution/access-control failure causing loss of funds (fatal slashing of honest validators) while a malicious dealer can never be proven at fault.

### Finding Description
The external report concerns improper access control leading to loss of funds; the analogous shape in Serai is a missing/inverted authorization check on *who is determined to be at fault* in the DKG blame path.

`AdditionalBlameMachine::blame` is documented: "The message should be a copy of the encrypted secret share from the accused sender to the accusing recipient", i.e., `sender` = accused, `recipient` = accuser [1](#0-0) . Internally, `blame_internal` calls `decrypt_with_proof(sender, recipient, ...)`, where `sender` is used as `from` in the PoP challenge — the Schnorr signature inside `EncryptedMessage` cryptographically binds the real sender's `Participant` index [2](#0-1) . On `InvalidSignature`, `blame_internal` returns `sender`; on a bad share, it also returns `sender` [3](#0-2) .

The call site passes the roles reversed:

```rust
// processor/src/key_gen.rs:543-556
.blame(accuser, accused, substrate_share, substrate_blame);
...
.blame(accuser, accused, network_share, network_blame);
```

and then treats `substrate_blame == accused` as proof of dealer fault, otherwise blaming the accuser [4](#0-3) .

Because the real `EncryptedMessage` PoP was produced with `from = accused` (the dealer is the encrypting party, via `encrypt(rng, context, self.i, ...)`) [5](#0-4) , verifying it with `from = accuser` always fails. `decrypt_with_proof` returns `InvalidSignature`, `blame_internal` returns `sender` — which is the **accuser** — and the handler emits `ProcessorMessage::Blame { participant: accuser }` [6](#0-5) . This holds unconditionally for every accusation, both substrate and network curves.

### Impact Explanation
- Any honest validator who reports an invalid secret share is themselves returned as the faulty party and is fatally slashed — direct loss of funds for a party that did nothing wrong.
- A participant who publishes malformed shares (invalid PoP, garbage ciphertext, wrong share value) can never be convicted through `VerifyBlame`, since conviction would require `blame()` to return `accused`, which it cannot do when given the message signed by `accused` under a `from` index of `accuser`.
- The attacker only needs to submit an invalid encrypted share (public, untrusted bytes fed to `EncryptedMessage::read` / `calculate_share` / `blame`), then wait for the victim's accusation to destroy the victim's stake — matching the "trigger loss of funds via incorrect access control" class.

### Likelihood Explanation
The inversion is unconditional: the PoP challenge mixes in `sender.to_bytes()` [7](#0-6) , so no honest message can satisfy the swapped verification, and no attacker action beyond sending one malformed share is required. The first invalid share in any DKG session deterministically converts the reporter's valid accusation into a fatal slash against the reporter.

### Recommendation
Swap the arguments at both call sites in `processor/src/key_gen.rs`:

```rust
.blame(accused, accuser, substrate_share, substrate_blame)
.blame(accused, accuser, network_share, network_blame)
```

so `sender = accused` and `recipient = accuser`, matching the `blame(sender, recipient, ...)` contract. Add a regression test asserting a properly formed accusation returns `accused` and a bogus accusation returns `accuser`.

### Proof of Concept
1. Run a PedPoP DKG where participant A (dealer) sends participant B an `EncryptedMessage` whose ciphertext is corrupted but which carries a valid PoP signed with `from = A` (as produced by `encrypt` / the test helper `invalidate_msg` [8](#0-7) ).
2. B's `calculate_share` fails share verification and returns `PedPoPError::InvalidShare { participant: A, blame: Some(proof) }` [9](#0-8) ; B submits `VerifyBlame { accuser: B, accused: A, share, blame }`.
3. The handler calls `blame(B, A, msg, proof)`; `decrypt_with_proof` verifies the PoP with `from = B` against a signature created with `from = A` → `InvalidSignature` → returns `B` [10](#0-9) .
4. `substrate_blame (= B) != accused (= A)`, so the handler emits `Blame { participant: B }` — the honest accuser B is fatally slashed while dealer A escapes [11](#0-10) .

Note: while the buggy call site is in `processor/`, the fault lies in the ordering contract of the in-scope `crypto/dkg/pedpop` blame API being violated, and the cryptographic evidence (PoP sender binding) lives entirely in `crypto/dkg/pedpop/src/encryption.rs`.

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }

fn encrypt<R: RngCore + CryptoRng, C: Ciphersuite, E: Encryptable>(
  rng: &mut R,
  context: [u8; 32],
  from: Participant,
  to: C::G,
  mut msg: Zeroizing<E>,
) -> EncryptedMessage<C, E> {
  /*
  The following code could be used to replace the requirement on an RNG here.
  It's just currently not an issue to require taking in an RNG here.
  let last = self.last_enc_key.to_bytes();
  self.last_enc_key = C::hash_to_F(b"encryption_base", last.as_ref());
  let key = C::hash_to_F(b"encryption_key", last.as_ref());
  last.as_mut().zeroize();
  */

  // Generate a new key for this message, satisfying cipher's requirement of distinct keys per
  // message, and enabling revealing this message without revealing any others
  let key = Zeroizing::new(C::random_nonzero_F(rng));
  cipher::<C>(context, &ecdh::<C>(&key, to)).apply_keystream(msg.as_mut().as_mut());

  let pub_key = C::generator() * key.deref();
  let nonce = Zeroizing::new(C::random_nonzero_F(rng));
  let pub_nonce = C::generator() * nonce.deref();
  EncryptedMessage {
    key: pub_key,
    pop: SchnorrSignature::sign(
      &key,
      nonce,
      pop_challenge::<C>(context, pub_nonce, pub_key, from, msg.deref().as_ref()),
    ),
    msg,
  }
}

fn pop_challenge<C: Ciphersuite>(
  context: [u8; 32],
  nonce: C::G,
  key: C::G,
  sender: Participant,
  msg: &[u8],
) -> C::F {
  let mut transcript = RecommendedTranscript::new(b"DKG Encryption Key Proof of Possession v0.2");
  transcript.append_message(b"context", context);

  transcript.domain_separate(b"proof_of_possession");

  transcript.append_message(b"nonce", nonce.to_bytes());
  transcript.append_message(b"key", key.to_bytes());
  // This is sufficient to prevent the attack this is meant to stop
  transcript.append_message(b"sender", sender.to_bytes());
  // This, as written above, doesn't hurt
  transcript.append_message(b"message", msg);
  // While this is a PoK and a PoP, it's called a PoP here since the important part is its owner
  // Elsewhere, where we use the term PoK, the important part is that it isn't some inverse, with
  // an unknown to anyone discrete log, breaking the system
  C::hash_to_F(b"DKG-encryption-proof_of_possession", &transcript.challenge(b"schnorr"))
}

  pub(crate) fn decrypt_with_proof<E: Encryptable>(
    &self,
    from: Participant,
    decryptor: Participant,
    mut msg: EncryptedMessage<C, E>,
    // There's no encryption key proof if the accusation is of an invalid signature
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Result<Zeroizing<E>, DecryptionError> {
    if !msg.pop.verify(
      msg.key,
      pop_challenge::<C>(self.context, msg.pop.R, msg.key, from, msg.msg.deref().as_ref()),
    ) {
      Err(DecryptionError::InvalidSignature)?;
    }

    if let Some(proof) = proof {
      // Verify this is the decryption key for this message
      proof
        .dleq
        .verify(
          &mut encryption_key_transcript(self.context),
          &[C::generator(), msg.key],
          &[self.enc_keys[&decryptor], *proof.key],
        )
        .map_err(|_| DecryptionError::InvalidProof)?;

      cipher::<C>(self.context, &proof.key).apply_keystream(msg.msg.as_mut().as_mut());
      Ok(msg.msg)
    } else {
      Err(DecryptionError::InvalidProof)
    }
  }
