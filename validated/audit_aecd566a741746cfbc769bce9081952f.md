### Title
Blame proof (ECDH decryption key) emitted before the message proof-of-possession is verified, enabling cross-message secret share recovery - (File: crypto/dkg/pedpop/src/lib.rs)

### Summary

`KeyMachine::calculate_share` returns an `EncryptionKeyProof` — which reveals the ECDH shared key `b·msg.key` — inside `PedPoPError::InvalidShare` when the decrypted share fails scalar deserialization, *before* the batch verifier ever checks the sender's `pop` Schnorr proof-of-possession. This re-opens the exact attack the PoP was added to prevent: an attacker who copies the per-message encryption key `X` from a victim's honest ciphertext can induce the recipient to publish `b·X`, letting anyone decrypt the victim's real secret share.

### Finding Description

In `crypto/dkg/pedpop/src/encryption.rs`, the code documents the threat model explicitly:

> "If this proof-of-possession wasn't here, Eve could observe Alice encrypt to Bob with key X, then send Bob a message also claiming to use X. While Eve's message would fail to meaningfully decrypt, Bob would then use this to create a blame argument against Eve. When they do, they'd reveal bX, revealing Alice's message to Bob." [1](#0-0) 

The PoP (`msg.pop`) is only checked via `batch_verify` inside `Encryption::decrypt`, which nonetheless always computes and returns `EncryptionKeyProof { key: ecdh(enc_key, msg.key), ... }`. [2](#0-1) 

In `calculate_share`, the decrypted bytes are checked with `C::F::from_repr` and, on failure, the function returns immediately with `blame: Some(blame)` — an early `?` that bypasses `batch.verify_with_vartime_blame()` at line 493. [3](#0-2) 

So the blame proof is released into the caller's hands (the processor forwards it for on-chain/fatal blame adjudication, `processor/src/key_gen.rs`) even when the PoP is forged. Only if the batch verifier runs and fails under `BatchId::Decryption(l)` is `blame` set to `None`. [4](#0-3) 

The downstream `BlameMachine::blame` / `AdditionalBlameMachine::blame` does re-verify the PoP and would blame the sender, but by then the ECDH key `b·X` has already been published as part of the blame statement. [5](#0-4) 

This mirrors CVE-2017-15042's shape exactly: a security precondition (PoP verification / STARTTLS) is enforced by code, but the sensitive material (ECDH key / password) is released on a path where that precondition was never checked, because the peer's (sender's) malformed message triggers early disclosure.

### Impact Explanation

Eve observes Alice's honest `EncryptedMessage` to Bob (key `X = x·G`). Eve crafts her own share message to Bob reusing `X` as `msg.key`, with an invalid `pop` and garbage (non-canonical scalar) ciphertext. Bob's `calculate_share` decrypts, hits the `from_repr` failure, and returns `InvalidShare { blame: Some(proof) }` where `proof.key = b·X`. When Bob publishes the blame proof per protocol, any observer recomputes the ChaCha20 cipher from `b·X` and decrypts Alice's genuine secret share to Bob. Combined with other leaked/forged shares, this can enable recovery of DKG secret material that should never have been exposed — the precise "massive side effect" the code comments warn about.

### Likelihood Explanation

Requires an attacker to be a DKG participant (or to inject messages authenticated as one, per the assumed authenticated channel) who has observed a victim's encrypted share message. The trigger is fully deterministic: any non-canonical share bytes cause the early return. Whether the leak materializes depends on the integrator publishing the blame proof even though `AdditionalBlameMachine` would attribute fault to the sender — which is the designed flow (the processor reads and submits `blame` before adjudicating it).

### Recommendation

Do not attach `EncryptionKeyProof` until the sender's PoP has been verified. Concretely: in `calculate_share`, run the queued `BatchId::Decryption` PoP statements through the batch verifier (or verify `msg.pop` inline) before returning `blame: Some(...)` for the malformed-share path, e.g. defer the `from_repr` failure until after `batch.verify_with_vartime_blame()`, or return `blame: None` whenever the batch has not yet confirmed the PoP. Alternatively, verify `msg.pop` synchronously inside `Encryption::decrypt` before computing/returning the ECDH proof.

### Proof of Concept

1. Alice runs `generate_secret_shares`, producing `Enc_A→B` with `key = X`, valid `pop`, valid share ciphertext.
2. Eve (participant l) builds `Enc_E→B`: `key = X` (copied), `pop = <arbitrary invalid SchnorrSignature>` (or even a valid PoP over a *different* malformed message — only `X` reuse matters), `msg` = 32 bytes of `0xFF` (guaranteed non-canonical per the same technique used in `invalidate_share_serialization`, encryption.rs:228-237).
3. Bob calls `calculate_share` with the share map including Eve's message. `self.encryption.decrypt` returns `(gibberish, proof)` where `proof.key = b·X`; `from_repr` fails; `Err(InvalidShare { participant: E, blame: Some(proof) })` returns before `batch.verify_with_vartime_blame()` would flag `BatchId::Decryption(E)` with `blame: None`.
4. Bob's blame proof `b·X` is published. Observer computes `cipher(context, b·X)` and decrypts `Enc_A→B.msg`, recovering Alice's secret share to Bob.

Relevant code: `crypto/dkg/pedpop/src/lib.rs:463-499` (`calculate_share`), `crypto/dkg/pedpop/src/encryption.rs:469-501` (`Encryption::decrypt` always emits the proof), `crypto/dkg/pedpop/src/encryption.rs:83-90` (documented attack the PoP is meant to prevent).

  fn blame_internal(
    &self,
    sender: Participant,
    recipient: Participant,
    msg: EncryptedMessage<C, SecretShare<C::F>>,
    proof: Option<EncryptionKeyProof<C>>,
  ) -> Participant {
    let share_bytes = match self.encryption.decrypt_with_proof(sender, recipient, msg, proof) {
      Ok(share_bytes) => share_bytes,
      // If there's an invalid signature, the sender did not send a properly formed message
      Err(DecryptionError::InvalidSignature) => return sender,
      // Decryption will fail if the provided ECDH key wasn't correct for the given message
      Err(DecryptionError::InvalidProof) => return recipient,
    };

    let Some(share) = Option::<C::F>::from(C::F::from_repr(share_bytes.0)) else {
      // If this isn't a valid scalar, the sender is faulty
      return sender;
    };

    // If this isn't a valid share, the sender is faulty
    if !bool::from(
      multiexp_vartime(&share_verification_statements::<C>(
        recipient,
        &self.commitments[&sender],
        Zeroizing::new(share),
      ))
      .is_identity(),
    ) {
      return sender;
    }

    // The share was canonical and valid
    recipient
  }
