## Title
Uncontrolled Resource Consumption via Offer Parsing with Unbounded CLVM Execution Cost - (File: `chia/wallet/trading/offer.py`)

### Summary
`Offer.__post_init__()` bounds inner-puzzle execution during additions/hints computation to `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM` [1](#0-0) , but `Offer._get_offered_coins()` — invoked by `get_offered_coins()`, `get_offered_amounts()`, `arbitrage()`, `summary()`, `get_pending_amounts()`, `get_primary_coins()`, and `save_trade()` — runs each parent coin's inner puzzle with `cost_left = INFINITE_COST` instead of a bounded budget [2](#0-1) .

### Finding Description
When a wallet receives an untrusted offer file from a counterparty and calls `Offer.from_bech32()`/`Offer.from_bytes()`, construction succeeds because `__post_init__()` correctly enforces `MAX_BLOCK_COST_CLVM` on `compute_spend_hints_and_additions()` [1](#0-0) . However, as soon as any code path calls `get_offered_coins()` (directly or transitively through `summary()`, `arbitrage()`, `get_pending_amounts()`, `get_primary_coins()`, or `TradeManager.save_trade()` for interested-coin subscription), `_get_offered_coins()` runs each matched puzzle driver's inner puzzle with `inner_puzzle.run_with_cost(cost_left, inner_solution)` where `cost_left` starts at `INFINITE_COST` (imported from `chia/types/blockchain_format/program.py`) rather than any bounded consensus cost limit [3](#0-2) .

This means a malicious offer counterparty can craft an offer whose CAT/NFT/singleton-style outer puzzle wraps an inner puzzle that is extremely expensive to execute (e.g., unbounded loops via recursive CLVM operators, or a puzzle engineered to consume large CPU/memory before returning) with no cost ceiling enforced in this specific path. Because `summary()`/`get_offer_summary` RPC and CLI `examine_only` flows are explicitly designed to let a wallet inspect an offer *before* deciding whether to accept it [4](#0-3) [5](#0-4) , this is directly reachable by any wallet user who receives an offer file from an untrusted party — the DoS triggers merely by parsing/inspecting the offer, not by accepting it.

The mempool/consensus layer's cost metering (`MAX_BLOCK_COST_CLVM`, `max_tx_clvm_cost`, atom/pair bounds) [6](#0-5)  and the offer's own `__post_init__`/`conditions()` paths do bound cost correctly [7](#0-6) , but this parallel `_get_offered_coins()` code path bypasses those protections entirely by using `INFINITE_COST`.

### Impact Explanation
This maps to CWE-400 (Uncontrolled Resource Consumption), directly analogous to the OpenMeetings report: an untrusted external input (offer file from a counterparty, analogous to an uploaded file) causes unbounded resource consumption (CPU/memory) on the receiving party's system, without requiring the victim to accept the offer — a spend-triggered/inspection-triggered processing halt or severe resource exhaustion of the wallet process. This can degrade or crash the wallet service, a denial-of-service against an individual wallet user's node.

### Likelihood Explanation
Likelihood is High for wallet users who routinely inspect offers shared via out-of-band channels (offer marketplaces, chat, files) before accepting them — this is a standard supported workflow (`examine_only`, `get_offer_summary`). No signature or on-chain action is required from the attacker; only a syntactically valid `Offer` object with a matched puzzle driver whose inner puzzle is computationally expensive.

### Recommendation
Bound `cost_left` in `Offer._get_offered_coins()` to a consensus-derived limit (e.g. `DEFAULT_CONSTANTS.MAX_BLOCK_COST_CLVM`, consistent with `__post_init__()` and `conditions()`), decrementing per-spend and raising `ValidationError(Err.BLOCK_COST_EXCEEDS_MAX, ...)` when exceeded, mirroring the pattern already used in `compute_spend_hints_and_additions()`/`compute_additions_with_cost()`.

### Proof of Concept
Not independently executable within this review — reachability and severity were established analytically by tracing `Offer.summary()` → `get_offered_amounts()` → `get_offered_coins()` → `_get_offered_coins()` → `inner_puzzle.run_with_cost(INFINITE_COST, ...)` [8](#0-7) [9](#0-8) . Confirming actual wall-clock/CPU impact requires constructing a concrete outer/inner puzzle pair recognized by `match_puzzle()` whose inner puzzle triggers pathological CLVM execution time, and measuring `Offer.summary()` latency in a live wallet — this step was not performed in this analysis and should be validated with a runnable reproduction before treating severity as fully confirmed.

## Resource limits

### Cost metering

Every CLVM operation has an associated cost. Total cost per block cannot
exceed `MAX_BLOCK_COST_CLVM = 11 000 000 000`.

### Generator byte cost

Each byte of generator program costs `COST_PER_BYTE = 12 000` CLVM cost
units, in addition to execution cost.

### Atom/pair bounds (mempool only)

After CLVM execution:

```python
if sbc.num_atoms > sbc.cost * 60_000_000 / MAX_BLOCK_COST_CLVM:
    reject  # too many atoms
if sbc.num_pairs > sbc.cost * 60_000_000 / MAX_BLOCK_COST_CLVM:
    reject  # too many pairs
```

This bounds memory usage relative to cost paid. At max cost, allows
60 million atoms or pairs.
