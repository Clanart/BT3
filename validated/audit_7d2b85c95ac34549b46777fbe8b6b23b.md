## Title
Stale line-index reuse when the working-directory diff changes silently corrupts partial commits - (File: `app/src/lib/stores/app-store.ts`, `app/src/models/diff/diff-selection.ts`, `app/src/lib/patch-formatter.ts`)

## Summary
GitHub Desktop lets a user select individual diff **lines** (not whole files) to include in a commit. The selection is stored as a set of *absolute line indices* (`DiffSelection.divergingLines`) that are meaningful only relative to the specific `IDiff` that was loaded when the selection was made. When the underlying diff changes (e.g. after a pull/fetch updates `HEAD`, or any refresh that reloads the diff for the same file), Desktop does **not** recompute which content the previously-selected indices correspond to — it only filters out indices that are no longer "selectable" at all. The remaining indices are reused verbatim against the new diff and are then fed straight into `formatPatch()`/`applyPatchToIndex()` to build the actual patch staged and committed. This is the same class of bug as the HMX report: an aggregate/derived piece of state (the line-index selection) is patched incrementally instead of being fully resynchronized with the object it is supposed to describe (the diff), so the two silently diverge.

## Finding Description
`DiffSelection` tracks selected lines purely by numeric index: [1](#0-0) 

When a new diff is loaded for the currently selected file, `updateChangesWorkingDirectoryDiff` explicitly acknowledges that the diff content may have "changed dramatically" and only patches the `selectableLines` set (used to invalidate indices that are no longer selectable, e.g. now hunk-header/context lines) instead of validating that the selected lines still refer to the same content: [2](#0-1) 

The filtering logic in `withSelectableLines` only drops indices that fell entirely outside the new selectable set — it does not detect that index `N` in the old diff and index `N` in the new diff can now refer to completely different (possibly unrelated) lines, for example after hunks shift due to upstream changes: [3](#0-2) 

These stale, index-based selections are exactly what gets turned into the real git patch at commit time. `applyPatchToIndex` re-fetches the diff independently and applies `file.selection` (computed against a possibly different diff) to it via `formatPatch`: [4](#0-3) 

`formatPatch` blindly trusts `file.selection.isSelected(absoluteIndex)` for whatever diff it is handed: [5](#0-4) 

No component re-validates that a diverging line index still points at the same textual content it did when the user clicked it — the invariant "selection state describes the currently displayed diff" is allowed to break silently, precisely as the HMX report describes for reserve accounting ("cumulative amounts stay in sync with actual position reserve amounts").

## Impact Explanation
If the base diff for a file changes between the moment the user curates a partial selection and the moment `stageFiles`/`applyPatchToIndex`/`createCommit` executes (e.g. because the local branch fast-forwarded/rebased onto new upstream commits touching the same file, delivered by an attacker-controlled or compromised git remote/proxy), the indices the user selected no longer correspond to the lines they inspected. The resulting patch can:
- silently include lines the user never reviewed or intended to commit (e.g. attacker-introduced content pulled from the remote), or
- silently drop lines the user did intend to commit,
- or produce a patch whose hunk boundaries no longer match the working tree, causing `git apply --cached` to apply changes at the wrong offsets.

This is a "silent corruption of what the user commits/pushes" primitive: the committed content diverges from what the user visually approved in the diff viewer, without any error being surfaced (the operation reports success).

## Likelihood Explanation
The trigger only requires an attacker-controlled remote to introduce new commits that touch a file the user already has a partial/line-level selection on, combined with the routine Desktop flow of fetching/pulling before finishing a commit — no local malware, no admin rights, no unnatural steps, and no reliance on a leaked credential. Desktop performs background fetches automatically and refreshes the changes/diff state (`refreshChangesSection` → `updateChangesWorkingDirectoryDiff`) whenever status is reloaded, so the race window is realistic in normal day-to-day usage (open a file, start selecting individual hunks/lines, let a background refresh or pull complete, then commit).

## Recommendation
Do not persist or reuse selection state as raw line indices across diff reloads. Either:
- Re-anchor the selection to diff content (e.g. line text/hash or hunk identity) rather than raw index, invalidating/re-mapping on every diff reload, or
- Force `DiffSelectionType.None`/clear the partial selection entirely whenever the diff for the selected file changes (safer default, mirrors the "subtract-then-readd" recommendation in the original report: fully recompute the derived state rather than incrementally patching it), and require the user to re-review and re-select lines against the fresh diff before allowing a partial commit.

## Proof of Concept
1. Open a repository in Desktop with a locally modified, uncommitted file `foo.txt` (diff against `HEAD` has multiple hunks).
2. In the Changes view, deselect the lines you don't want to commit (creating a `DiffSelectionType.Partial` selection referencing specific absolute line indices), but do not commit yet.
3. While the commit box is still open, let Desktop's automatic background fetch/pull bring in a new upstream commit (simulating a malicious/compromised remote) that also modifies `foo.txt`, shifting hunk boundaries; Desktop's `refreshChangesSection` reloads the diff via `updateChangesWorkingDirectoryDiff`, which reuses the previously diverging line indices, only dropping ones outside the new selectable set (`app/src/lib/stores/app-store.ts:3478-3497`, `app/src/models/diff/diff-selection.ts:320-330`).
4. Click "Commit". `_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex` fetches the diff again and calls `formatPatch(file, diff)` (`app/src/lib/git/apply.ts:60-81`, `app/src/lib/patch-formatter.ts:143-171`) using the stale index-based selection.
5. Inspect the resulting commit: it contains lines/hunks that do not match what was visually selected in step 2, demonstrating silent corruption of the committed content.
