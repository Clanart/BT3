### Title
Hardcoded dust threshold (`DUST = 546`) can produce outputs Bitcoin nodes reject as dust - ([File: networks/bitcoin/src/wallet/send.rs](https://github.com/Kirstentat/serai--004/blob/main/networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` validates payment amounts and change outputs against a single statically compiled constant `DUST: u64 = 546`. Like the reference finding — where a governance-hardcoded stable price silently drifts from the real market value — this constant hardcodes a *network policy value* that is not actually fixed. Bitcoin's dust threshold is computed as `3 * minRelayTxFee * (serialized output size + spend input size) / 1000`, so it varies with both the output type and the prevailing mempool minimum relay fee. When the effective dust limit exceeds 546 sats, the wallet will build and threshold-sign transactions containing outputs the peer-to-peer network treats as dust: the transaction is non-standard, will not relay, and the payment/change output is below the spendable threshold.

### Finding Description
At `send.rs:32`, the dust floor is fixed:

```rust
pub const DUST: u64 = 546;
```

It is then used as the sole ground truth in two places:

- `send.rs:165-169` — any user-specified payment amount `>= 546` is accepted, regardless of the destination `script_pubkey`'s type or the current fee environment.
- `send.rs:228-233` — leftover input value `>= DUST` after fees is emitted as a change output; the change script is `p2tr_script_buf`, whose real dust floor differs from the comment's assumption since the code explicitly declines to "delineate" per output type (`send.rs:29-31`).

The constant is compiled in; nothing queries the node for `getnetworkinfo`'s `incrementalfee`/relay fee or recomputes `GetDustThreshold` for the actual output scripts. The only dynamic check is a lower bound against `DEFAULT_MIN_RELAY_TX_FEE` (`send.rs:211`), itself a static default — a node raised to a higher `minrelaytxfee` (common during mempool congestion) raises dust proportionally while this code still uses the stale floor.

### Impact Explanation
- **Funds sent to unspendable/uneconomic outputs**: a withdrawal payment of, e.g., 546 sats accepted by `DustPayment` validation can be dust under the network's current policy, so the output can never be spent without burning its entire value to fees — funds are reported sent yet are not spendable.
- **Stuck threshold-signed transactions**: if a change output or payment is dust under peers' actual policy, the whole transaction is non-standard and fails to relay. Because Serai's FROST `TransactionMachine` already consumed preprocesses and the UTXOs are committed in the sighash (`Prevouts::All`), the signed artifact is unusable and the batch must be rebuilt.

### Likelihood Explanation
Requires the prevailing minimum relay fee to rise above the compiled default (or an unusual payment script whose dust floor exceeds 546 sats). Both are real but episodic conditions — mempool min-fee spikes occur during congestion, and relay policy is not consensus-fixed. This matches the reference report's medium severity: an assumption that holds "most of the time" but fails exactly under stress, with no on-chain mechanism to notice it failed.

### Recommendation
Do not hardcode `546`. Compute the dust threshold per output the way Bitcoin Core does (`GetDustThreshold`/`IsDust`) using the actual `script_pubkey` and the fee rate / `minrelaytxfee` obtained dynamically from the node (e.g., via `getnetworkinfo`/`estimatesmartfee`), or apply a conservative safety multiplier over a queried value. At minimum, differentiate segwit vs. non-segwit dust sizes and derive the floor from the same fee source used for `fee_per_vbyte`.

### Proof of Concept
1. Network conditions raise mempool `minrelaytxfee` such that the effective dust limit for a P2TR output exceeds 546 sats (Bitcoin Core computes dust as `3 * minRelayFee * (out_size + in_size) / 1000`; ~67 wu input + ~43 byte output ⇒ dust crosses 546 once min relay fee roughly doubles).
2. `SignableTransaction::new` is called with a payment of 546 sats (or leftover change of 546–600 sats). The check `*amount < DUST` passes (`send.rs:166`), and the change branch pushes a `TxOut` with `value >= DUST` (`send.rs:229-230`).
3. `multisig` → `TransactionMachine::sign` produces a fully valid FROST/Schnorr-signed transaction committing to all prevouts (`send.rs:375-397`).
4. Broadcasting fails: peers reject the transaction as non-standard (dust output). The payment value exists on no spendable UTXO, and the consumed inputs/preprocesses cannot be reused for a corrected transaction without reconstruction.
