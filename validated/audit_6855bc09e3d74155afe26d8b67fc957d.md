### Title
`aggregator_verification_address = None` Silently Bypasses Aggregator Authorization on `Withdraw` and `OptimisticPayoutSign` RPCs — (File: `core/src/rpc/operator.rs`, `core/src/verifier.rs`)

### Summary

The `aggregator_verification_address` field in `BridgeConfig` is `Option<alloy::primitives::Address>`. When it is `None` — which is the default when the `AGGREGATOR_VERIFICATION_ADDRESS` environment variable is absent — the ECDSA authorization check that is supposed to verify the aggregator's identity is silently and completely skipped in both the operator's `Withdraw` RPC handler and the verifier's `sign_optimistic_payout` function. This is the direct structural analog of the reported bug: just as the `ReserveSwapper` test passed because the ESD address was never registered (causing the guard to compare against the zero address), here the guard is never entered at all when the "registry" value is absent. Any actor holding a valid mTLS client certificate can invoke these privileged bridge actions without the aggregator's authorization, bypassing the manual-verification gate that is explicitly described as a launch-period security control.

    // ... ECDSA recovery and comparison ...

**How `None` is reached in production — `core/src/config/env.rs` lines 165–171:**

```rust

    .ok()
    .map(|addr| {
        addr.parse::<alloy::primitives::Address>()
            .wrap_err("Failed to parse AGGREGATOR_VERIFICATION_ADDRESS")
    })
    .transpose()?;
```

If `AGGREGATOR_VERIFICATION_ADDRESS` is absent from the environment, `aggregator_verification_address` is `None` and both guards above are silently skipped.

**Missing enforcement gate — `core/src/config/mod.rs` lines 291–333 (`check_mainnet_requirements`):**

`check_mainnet_requirements` enforces `client_verification = true` and rejects `RISC0_DEV_MODE`, but it does **not** check whether `aggregator_verification_address` is set. A mainnet operator or verifier deployed without `AGGREGATOR_VERIFICATION_ADDRESS` passes all startup checks and runs with the authorization gate permanently open.

**Exploit path:**

1. Attacker is any actor that possesses a valid mTLS client certificate (e.g., another operator, a verifier, or any party the CA has issued a cert to).
2. Operator or verifier is deployed without `AGGREGATOR_VERIFICATION_ADDRESS` set.
3. Attacker calls `Withdraw` (operator gRPC) or `OptimisticPayoutSign` (verifier gRPC) with a valid withdrawal registered in Citrea, omitting `verification_signature` entirely.
4. Neither handler returns an error; both proceed to the downstream business logic.
5. The operator broadcasts a payout transaction; the verifier produces a partial MuSig2 signature — both without the aggregator's manual approval.

### Impact Explanation

The `aggregator_verification_address` check is documented as "an extra verification of aggregator's identity and to force citrea to check withdrawal params manually during some time after launch." When it is absent, any actor with a valid mTLS certificate can:

- Force the operator to process any Citrea-registered withdrawal without the aggregator's manual review, bypassing the launch-period safety gate.
- Obtain verifier partial signatures for an optimistic payout without the aggregator's authorization, enabling the aggregator's MuSig2 ceremony to be replicated by an unauthorized party.

While the downstream checks (Citrea registration, UTXO match, profitability) prevent direct fund theft, the authorization bypass removes the human-in-the-loop control that is the stated purpose of this field, constituting an authentication/authorization bypass in the gRPC actor-role boundary that grants privileged bridge actions to the wrong party.

### Likelihood Explanation

The `AGGREGATOR_VERIFICATION_ADDRESS` environment variable is not listed as mandatory in `check_mainnet_requirements` and is absent from the `.env.example` as a required field. Any operator or verifier deployed from environment variables without explicitly setting this variable silently runs with the guard disabled. The default `BridgeConfig` struct (used in tests) happens to set a hardcoded address, masking the gap in test coverage.

### Recommendation

1. Add `aggregator_verification_address` to `check_mainnet_requirements`: if it is `None` on `Network::Bitcoin`, push a misconfiguration entry and return an error.
2. In `Withdraw` and `sign_optimistic_payout`, treat `aggregator_verification_address = None` as a hard error rather than a silent pass-through, or at minimum emit a prominent warning that the authorization gate is disabled.
3. Add `AGGREGATOR_VERIFICATION_ADDRESS` to the required-variable list in deployment documentation and the `.env.example` file.

    /// Checks various variables if they are correct for mainnet deployment.
    pub fn check_mainnet_requirements(&self, actor_type: cli::Actor) -> Result<(), BridgeError> {
        if self.protocol_paramset().network != Network::Bitcoin {
            return Ok(());
        }

        let mut misconfigs = Vec::new();

        if matches!(actor_type, cli::Actor::Verifier | cli::Actor::Operator)
            && !self.client_verification
        {
            misconfigs.push("CLIENT_VERIFICATION=false".to_string());
        }

        /// Checks if an env var is set to a non 0 value.
        fn check_env_var(env_var: &str, misconfigs: &mut Vec<String>) {
            if let Ok(var) = std::env::var(env_var) {
                if var == "0" || var.eq_ignore_ascii_case("false") {
                    return;
                }

                misconfigs.push(format!("{env_var}={var}"));
            }
        }

        check_env_var("DISABLE_NOFN_CHECK", &mut misconfigs);

        if is_dev_mode() {
            misconfigs.push("Risc0 dev mode is enabled (RISC0_DEV_MODE=1)".to_string());
        }

        if is_test_vk() {
            misconfigs.push("use-test-vk feature is enabled".to_string());
        }

        if !misconfigs.is_empty() {
            return Err(BridgeError::ConfigError(format!(
                "Following configs can't be used on Mainnet: {misconfigs:?}",
            )));
        }

        Ok(())
    }
