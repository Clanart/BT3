## Title
Native-token escrow releases in `IntentsBase._withdraw` permanently revert (and lock user funds) when the beneficiary cannot accept ETH, with no ERC20/WETH fallback unlike other Hyperbridge asset contracts - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The external report's core invariant is: *a contract that is designed to hold funds for later claim must be able to receive/release those funds, or claims/refunds get permanently stuck.* The same broken invariant exists in `IntentGatewayV2`'s intent-settlement escrow. `IntentsBase._withdraw()` — the single internal function used to release escrow on fill, refund, and cancellation — pushes native ETH to the beneficiary with a raw `.call{value: amount}("")` and **reverts the entire withdrawal** if that call fails, with no recovery path.

### Finding Description
`_withdraw()` is the common escrow-release routine invoked from every settlement/refund path (`onAccept` for `RedeemEscrow`/`RefundEscrow`, `_cancelSameChain`, `_cancelFromSource` via `onGetResponse`, `_cancelFromDest`): [1](#0-0) 

For native-token entries (`token == address(0)`), it does:
```solidity
(bool sent,) = beneficiary.call{value: amount}("");
if (!sent) revert InsufficientNativeToken();
``` [2](#0-1) 

There is no fallback to an ERC20/WETH delivery path. This is the same pattern independently reproduced in the Tron fork's monolithic `IntentGatewayV2.sol` `withdraw()`: [3](#0-2) 

Contrast this with `WrappedHyperFungibleToken.onAccept` / `onPostRequestTimeout`, which explicitly guard against exactly this class of failure: they attempt a native push first, and if the beneficiary/refundee cannot accept native value, they re-wrap to WETH and deliver as an ERC20 transfer instead — with an inline comment stating the intent is precisely to avoid "permanently lock[ing] funds": [4](#0-3) [5](#0-4) 

`IntentsBase._withdraw` has no equivalent safety valve. If the escrow contains native ETH and the resolved `beneficiary` is a contract address that reverts on receiving ETH (no `receive()`/payable `fallback()`, or one that reverts under some condition, e.g. paused/guarded wallet), the entire `_withdraw` call reverts unconditionally.

Because `beneficiary` here is either `order.user` (fixed at order placement, used for cancel/refund paths) or the cross-chain filler address embedded in the `RedeemEscrow` message (used for fill settlement), a single non-payable/reverting address anywhere in that role deterministically and permanently blocks the corresponding escrow release — there is no retry-with-different-recipient, no admin sweep, and no ERC20/WETH fallback route for the affected order's escrowed native token.

### Impact Explanation
This matches the bounty's "stealing or loss of funds" category: escrowed native ETH becomes permanently unrecoverable for the affected order once the beneficiary/refund address cannot accept a raw ETH push. Unlike `WrappedHyperFungibleToken`, which the same codebase already hardened against this exact scenario, `IntentGatewayV2`/`IntentsBase` (the intent-settlement escrow) was not, leaving an inconsistent, unguarded path in a contract explicitly holding user/solver funds pending claim — directly analogous to `DelegatedStaking` not being able to receive/settle funds for claimants.

### Likelihood Explanation
Moderate: it requires (a) an order with native-token (`address(0)`) inputs, and (b) a beneficiary/refund address that is a contract without a working `receive()`/payable fallback (or one that reverts, e.g. due to a re-entrancy guard, gas-stipend limits from `.call` interactions, or deliberate griefing by a solver embedding a hostile beneficiary in the cross-chain settlement message). No relayer, prover, or admin compromise is needed — the condition is entirely reachable through normal `placeOrder`/`fillOrder`/`cancelOrder` usage with an unprivileged, attacker- or user-chosen address.

### Recommendation
Add the same defensive pattern already used in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`: attempt the native ETH push, and on failure, wrap the ETH (e.g., via WETH) and deliver it as an ERC20 transfer to the beneficiary instead of reverting the whole withdrawal. Alternatively, decouple escrow release from push-delivery entirely by crediting an internal, pull-based balance that the beneficiary can withdraw at their own contract's convenience, so a single non-payable recipient cannot brick settlement/cancellation for an order.

### Proof of Concept
1. User places a same-chain (or cross-chain) order with a native-token (`address(0)`) input and sets `order.user`/fill-beneficiary to a deployed contract with no `receive()`/payable `fallback()` (or one that always reverts).
2. Order proceeds normally through escrow (`placeOrder`).
3. On cancellation (`_cancelSameChain`/`_cancelFromDest`→`onAccept`) or fill settlement (`onAccept`→`RedeemEscrow`), `_withdraw()` attempts `beneficiary.call{value: amount}("")`.
4. The call fails because the beneficiary contract cannot accept ETH; `_withdraw` reverts with `InsufficientNativeToken()`.
5. Because this is the only code path that releases escrowed native tokens for the order, and there is no ERC20/WETH fallback or pull-based alternative, the escrowed ETH for that order is permanently locked in the gateway with no possible on-chain resolution.

Note: I could not confirm within tool budget whether `IntentGatewayV2.onAccept` is invoked via `EvmHost`'s low-level `.call` (which retries on failure, as seen for `dispatchTimeOut` at [6](#0-5) ) or a direct external call that would propagate the revert as a hard failure of the incoming message. If it is retried like `dispatchTimeOut`, the immediate settlement message would fail-and-retry rather than fail atomically, but the escrow would still never release since the same non-payable beneficiary condition recurs on every retry — the fund-lock outcome is unchanged either way.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
