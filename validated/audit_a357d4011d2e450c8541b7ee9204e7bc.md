### Title
`aggregator_verification_address = None` Bypasses ECDSA Authorization on Operator `Withdraw` RPC, Allowing Any Caller to Force Withdrawal Execution - (File: `core/src/rpc/operator.rs`)

### Summary

The `Withdraw` RPC on the operator gRPC server contains a conditional ECDSA authorization check that is entirely skipped when `aggregator_verification_address` is `None` (not configured). Because the aggregator server does not enforce client certificates, any external party can call `aggregator.withdraw()` → `operator.withdraw()` without any application-level authorization. This allows an unauthorized actor to force the operator to execute any Citrea-registered withdrawal, draining operator liquidity and breaking bridge liveness.

### Finding Description

**Root cause — conditional ECDSA check in `operator.withdraw`:**

In `core/src/rpc/operator.rs` lines 209–239, the ECDSA verification signature check is wrapped in `if let Some(address_in_config) = self.operator.config.aggregator_verification_address`. When `aggregator_verification_address` is `None`, the entire block is skipped and `self.operator.withdraw(...)` is called unconditionally:

```rust
// if verification address is set in config, check if verification signature is valid
if let Some(address_in_config) = self.operator.config.aggregator_verification_address {
    // ... ECDSA check ...
}
// Falls through to withdraw() with no auth check when None
let payout_tx = self.operator.withdraw(...).await?;
``` [1](#0-0) 

**`aggregator_verification_address` is an optional field:**

The field is declared as `Option<alloy::primitives::Address>` and is read from the optional env var `AGGREGATOR_VERIFICATION_ADDRESS`. If the env var is absent, the value is `None`. [2](#0-1) [3](#0-2) 

**Aggregator server does not enforce client certificates:**

The aggregator gRPC server is created without the `OnlyAggregatorAndSelf` interceptor. The `create_aggregator_grpc_server` function calls `create_grpc_server` which, when `client_verification = true`, applies the interceptor only to verifier/operator servers. The aggregator path passes the raw service without certificate-based caller restriction. The documentation explicitly states: *"The aggregator does not enforce client certificates but does use TLS for encryption."* [4](#0-3) [5](#0-4) 

**Attack path:**

1. Attacker connects to the aggregator's public gRPC endpoint (no client cert required).
2. Attacker calls `aggregator.withdraw(AggregatorWithdrawalInput { withdrawal: WithdrawParamsWithSig { withdrawal: <valid_params>, verification_signature: None }, ... })`.
3. Aggregator forwards the call to `operator.withdraw(WithdrawParamsWithSig)` using the aggregator's own mTLS certificate.
4. Operator's `withdraw` handler receives the request with a valid aggregator cert, passes the mTLS interceptor check.
5. Because `aggregator_verification_address = None`, the ECDSA check block is skipped entirely.
6. `self.operator.withdraw(...)` executes: validates against Citrea state, checks profitability, creates and broadcasts the payout transaction. [6](#0-5) 

**Analog to the external bug:**

The external bug: `adapterToId[msg.sender]` returns `0` (the Solidity default) for any unregistered sender, and adapter ID `0` is a legitimately registered adapter — so the `isAdapterInitialized(0)` check passes for all callers.

The Clementine analog: `aggregator_verification_address` being `None` (the Rust default when the env var is absent) causes the entire ECDSA identity check to be skipped — so any caller who can reach the aggregator passes the authorization gate on the withdrawal path.

### Impact Explanation

An attacker with network access to the aggregator's gRPC port can force the operator to execute any withdrawal that is registered in the Citrea bridge contract. Because the user's `SinglePlusAnyoneCanPay` signature commits to the specific output, funds cannot be redirected to the attacker. However:

- The operator is forced to front BTC for every triggered withdrawal immediately, potentially exhausting operator liquidity.
- An attacker can batch-trigger all pending registered withdrawals simultaneously, locking the operator's collateral and preventing legitimate bridge operations.
- This breaks bridge liveness: the operator may be unable to service new withdrawals or maintain collateral for ongoing BitVM challenge cycles.

This falls under the allowed impact category: *"Unauthorized state transition in... payout... flow that breaks bridge safety/liveness with material fund impact."*

### Likelihood Explanation

- `AGGREGATOR_VERIFICATION_ADDRESS` is an optional environment variable with no default in the env-based config path. Any operator who does not explicitly set it will have `aggregator_verification_address = None`.
- The aggregator endpoint is network-accessible by design (users call it to initiate deposits/withdrawals).
- No privileged access, leaked keys, or internal network access is required.
- The `check_mainnet_requirements` function does **not** check whether `aggregator_verification_address` is set — it only checks `client_verification` and dev-mode flags. [7](#0-6) 

### Recommendation

1. **Require `aggregator_verification_address` to be set** when `client_verification = true` and the network is mainnet. Add a check in `check_mainnet_requirements`:
   ```rust
   if self.aggregator_verification_address.is_none() {
       misconfigs.push("AGGREGATOR_VERIFICATION_ADDRESS not set".to_string());
   }
   ```
2. **Enforce ECDSA check unconditionally** on the `Withdraw` RPC, or at minimum treat `aggregator_verification_address = None` as "reject all withdrawal requests" rather than "skip the check."
3. **Add client certificate enforcement to the aggregator** for the `withdraw` endpoint, or introduce a separate authenticated withdrawal endpoint.

### Proof of Concept

**Preconditions:**
- Operator is running with `AGGREGATOR_VERIFICATION_ADDRESS` not set (env var absent).
- A withdrawal is registered in the Citrea bridge contract with a valid user signature.
- Attacker has network access to the aggregator's gRPC port.

**Steps:**
```python
# Using grpcio or any gRPC client
import grpc
from clementine_pb2 import AggregatorWithdrawalInput, WithdrawParamsWithSig, WithdrawParams
from clementine_pb2_grpc import ClementineAggregatorStub

# Connect to aggregator (no client cert required)
channel = grpc.secure_channel('aggregator:17000', grpc.ssl_channel_credentials(ca_cert))
stub = ClementineAggregatorStub(channel)

# Craft withdrawal params for a registered Citrea withdrawal
params = AggregatorWithdrawalInput(
    withdrawal=WithdrawParamsWithSig(
        withdrawal=WithdrawParams(
            withdrawal_id=<registered_id>,
            input_signature=<user_singleplus_sig>,
            input_outpoint=<withdrawal_utxo>,
            output_script_pubkey=<user_output>,
            output_amount=<amount>,
        ),
        verification_signature=None  # No ECDSA sig needed
    )
)

# Aggregator forwards to operator.withdraw() with aggregator cert
# Operator skips ECDSA check (aggregator_verification_address = None)
# Payout tx is broadcast
response = stub.Withdraw(params)
```

The operator broadcasts the payout transaction without any authorization from the legitimate aggregator operator. Repeating this for all registered withdrawals drains the operator's BTC liquidity. [8](#0-7) [1](#0-0)

pub async fn create_aggregator_grpc_server(
    config: BridgeConfig,
) -> Result<(std::net::SocketAddr, oneshot::Sender<()>), BridgeError> {
    let addr: std::net::SocketAddr = format!("{}:{}", config.host, config.port)
        .parse()
        .wrap_err("Failed to parse address")?;
    let aggregator_server = AggregatorServer::new(config.clone()).await?;
    aggregator_server.start_background_tasks().await?;

    let svc = ClementineAggregatorServer::new(aggregator_server)
        .max_encoding_message_size(config.grpc.max_message_size)
        .max_decoding_message_size(config.grpc.max_message_size);

    if config.client_verification {
        tracing::warn!("Client verification is enabled on aggregator gRPC server",);
    }

    let (server_addr, shutdown_tx) =
        create_grpc_server(addr.into(), svc, "Aggregator", &config).await?;

    match server_addr {
        ServerAddr::Tcp(socket_addr) => Ok((socket_addr, shutdown_tx)),
        _ => Err(BridgeError::ConfigError("Expected TCP address".into())),
    }
}
