The most direct analog to this "credential/action committed before validation" pattern in Cosmos EVM's own code lives in the IBC callbacks contract keeper, where cached EVM state changes are flushed to the real context **before** the invariant check that is supposed to guard against irrecoverable fund loss.### Title
Isolated-address ERC20 allowance is committed to chain state before the "receiver has zero balance" invariant is checked, permanently freezing user IBC funds — ([File: x/ibc/callbacks/keeper/keeper.go])

### Summary
`ContractKeeper.IBCReceivePacketCallback` executes the EVM callback contract in a cached context (`cachedCtx`) and then calls `writeFn()` to commit those changes to the real `ctx` **before** it verifies that the isolated receiver address ended up with a zero token balance. Because the isolated receiver address is a module-derived address with no private key, any state that leaves tokens/allowance stuck there is unrecoverable. The invariant check exists specifically to prevent this ("This check is here to prevent funds from getting stuck in the isolated address, since they would become irretrievable"), but by the time it runs, `writeFn()` has already made the damage permanent instead of triggering a revert. [1](#0-0) 

### Finding Description
The callback flow is:
1. `approve()` is called on the ERC20 precompile from the isolated receiver address (`receiverHex`) to the attacker/user-specified `contractAddr`, for the full transferred `amountInt`. [2](#0-1) 
2. `CallEVMWithData` executes attacker/user-supplied `calldata` against `contractAddr`, all still inside `cachedCtx`. [3](#0-2) 
3. `writeFn()` is invoked, flushing every state mutation from steps 1–2 (the ERC20 `approve`, any `transferFrom`/`transfer` performed by the contract, and any other side effects of the contract call) into the actual chain state. [4](#0-3) 
4. Only *after* that commit does the code check `receiverTokenBalance == 0` — the very invariant meant to guarantee the callback contract fully swept the isolated address. If it is non-zero, the function returns an error. [5](#0-4) 

Because the isolated address is generated by `types.GenerateIsolatedAddress(destChannel, sender)` and is enforced to have no corresponding signing key, any residual balance or dangling `approve` allowance left at that address after `writeFn()` has already committed is **permanently unrecoverable** — nobody can ever sign a transaction from that address to move the funds or revoke the allowance. Returning an error at this point only affects the acknowledgement/event path; it does not, and cannot, undo the already-committed EVM state.

This is trivially reachable by an unprivileged actor: the IBC sender of the packet (untrusted per the module's own documentation: "IBC packet senders cannot be explicitly trusted, as they can be deceitful") fully controls both `contractAddress` and the `calldata` executed via the `dest_callback` memo field. Any callback contract that does not perfectly drain 100% of the received token balance in a single pass (due to a bug, rounding, or simply a contract designed to leave a remainder) — or a contract deliberately crafted to leave 1 unit behind — causes the check to fail, but the tokens/allowance are already irreversibly stuck at the isolated address by the time the error is returned. [6](#0-5) 

### Impact Explanation
This matches the "Critical permanent freezing/locking of user funds" impact category. Any ordinary (non-malicious, buggy) or malicious IBC-callback-enabled transfer whose destination contract does not perfectly zero out the isolated address's balance results in those tokens (and any unspent portion of the granted allowance) being permanently locked at an address that can never be controlled by any key. This is not a privileged-actor or relayer-only issue — it is triggerable by any ordinary IBC sender using the standard, documented `dest_callback` memo flow, using tokens they are entitled to transfer. The severity is amplified because the code path explicitly acknowledges the risk ("funds may get stuck", "receiver has unrecoverable tokens") yet the ordering of `writeFn()` vs. the check defeats the intended safeguard.

### Likelihood Explanation
High/likely to trigger unintentionally, and trivially triggerable intentionally. No special privileges are required — any account capable of initiating an ICS-20 transfer with a `dest_callback` memo pointing to a contract they control (or any imperfect third-party integration contract) can hit this path. No race condition or timing precision is required, unlike the TOTP-window race in the source report; this is a deterministic, single-transaction ordering bug.

### Recommendation
Move the `receiverTokenBalance` check to run against `cachedCtx` **before** calling `writeFn()`, so that if the isolated address retains a non-zero balance, the entire cached context (including the `approve` and the contract call side effects) is discarded rather than committed. Only call `writeFn()` after all invariants pertaining to the isolated address have been verified to hold. Additionally, consider explicitly revoking/resetting the ERC20 allowance from the isolated address to `contractAddr` after the callback completes (success or failure) so that no allowance can ever persist beyond the scope of a single packet's processing.

### Proof of Concept
1. Attacker (or any user) submits an ICS-20 transfer from a counterparty chain with `sender = "attackerSenderID"`, `receiver = GenerateIsolatedAddress(destChannel, "attackerSenderID")`, and memo:
```json
{"dest_callback": {"address": "0xMaliciousOrBuggyContract", "gas_limit": "1000000", "calldata": "..."}}
```
2. On `OnRecvPacket`, `IBCReceivePacketCallback` runs: `approve(isolatedAddr, 0xMaliciousOrBuggyContract, amount)` then calls the contract with the supplied calldata. [7](#0-6) 
3. The contract calls `transferFrom(isolatedAddr, attackerAddr, amount-1)`, intentionally leaving 1 unit of the ERC20 balance at `isolatedAddr` (and consuming allowance down to 1, or the contract simply doesn't drain fully due to a bug).
4. `writeFn()` commits this state to the chain. [4](#0-3) 
5. The subsequent check finds `receiverTokenBalance != 0` and returns `types.ErrEVMCall` ("receiver has unrecoverable tokens after callback") — but the `approve` and `transferFrom` executed in step 3 are already permanently on-chain. [8](#0-7) 
6. The remaining 1 unit (or any larger un-swept remainder in real-world buggy-contract scenarios) is now permanently stuck at `isolatedAddr`, which has no private key and can never be recovered — matching the exact "unrecoverable tokens" scenario the check's comment warns about, except the warning fires after the damage is already committed.

Note: I was unable to fully trace how the ibc-go `callbacks` middleware (external dependency, not part of this repo) treats the error returned from `IBCReceivePacketCallback` with respect to the packet acknowledgement (i.e., whether it still returns a success ack for the underlying transfer despite the callback error). That external behavior is out of this repository's scope, but it does not change the core, reachable, in-repo bug: the fund-loss-prevention check runs after the state is already irreversibly committed via `writeFn()`.
