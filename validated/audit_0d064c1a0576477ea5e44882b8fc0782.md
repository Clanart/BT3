### Title
Origin remote URL is silently rewritten to an attacker-controlled host when refreshing GitHub repository metadata - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
When Desktop refreshes the GitHub metadata for a repository it re-fetches the repository object from the API and, under certain conditions, silently rewrites the local `origin` remote's URL to whatever `clone_url` the API/server returned — without verifying that the new URL still points to the same host. Because this check only compares URL *protocol* (`ssh`/`https`), not hostname/owner/name equality, a malicious or compromised API endpoint (e.g. a GitHub Enterprise Server the user has added as an account, or a MITM/rogue proxy sitting in front of it) can redirect the user's git remote to an attacker-controlled server without any prompt.

### Finding Description
`repositoryWithRefreshedGitHubRepository` fetches the repository from the account's API and passes the raw `IAPIFullRepository` object into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` decides whether to overwrite the current remote with `apiRepo.clone_url`: [2](#0-1) 

The guard is:
```
if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
  await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
}
```
- `protocolsMatch` only compares `URL.parse(url).protocol` (`https:` vs `ssh:`-style prefixes), not hostname.
- `remoteUrlUnchanged` only verifies the *current* remote still matches what was previously stored for this `GitHubRepository` (i.e., the user hasn't hand-edited it).
- `urlsMatch` uses `urlMatchesRemote` (`app/src/lib/repository-matching.ts:90-118`), comparing hostname/owner/name — but the code only requires this to be **false**, i.e. the new URL is explicitly allowed to point to a *different* hostname, owner, or repo name.

There is no check anywhere in this path that the new `clone_url` hostname equals the old remote's hostname. `setRemoteURL` then performs a raw `git remote set-url` with that value: [3](#0-2) 

The `apiRepo` object originates from `API.fetchRepository(owner, name)`, which issues a `GET repos/{owner}/{name}` request against whatever endpoint the associated `Account` is configured for: [4](#0-3) 

For non-github.com accounts this endpoint is a user-added GitHub Enterprise Server URL (or, in a MITM/rogue-proxy scenario, any server that can intercept/answer that HTTPS request). The server has full control over the `clone_url` field returned in the JSON body — this is exactly the "attacker controls...a GitHub API object" / "git remote/proxy response" primitive. Existing tests only assert same-owner/name behavior and protocol-mismatch rejection; none of them verify hostname stays fixed: [5](#0-4) [6](#0-5) 

### Impact Explanation
Once the origin remote is rewritten, all subsequent user-initiated `git fetch`/`git push`/`git pull` operations transparently target the attacker's host instead of the real one:
- Future commits the user believes are being pushed to their real repository are silently sent to an attacker-controlled server (silent corruption of what the user pushes).
- Future fetches pull objects/refs from the attacker's server, which can inject malicious commits/branches into the user's local history on the next fetch/merge.
- Because the switch happens transparently in a background metadata-refresh routine (`repositoryWithRefreshedGitHubRepository`, invoked e.g. after account changes), the user is given no explicit UI warning that their remote target changed hosts.

This matches the "silent corruption of what the user commits or pushes" and "attacker-controlled git remote/proxy response" impact categories.

### Likelihood Explanation
This requires the victim to have an account pointed at a server the attacker controls or can intercept (e.g., a compromised/rogue GitHub Enterprise Server, or a network position able to MITM that endpoint's HTTPS traffic), and requires the local remote to not have been manually customized away from the previously-known API URL (`remoteUrlUnchanged`) and matching protocol scheme — both very common defaults (most users never hand-edit `origin`). No local access, admin rights, or pre-existing malware is required; the attacker only needs to control the API response for a single `repos/{owner}/{name}` call, which happens automatically during normal background repository-metadata refreshes.

### Recommendation
In `updateRemoteUrl`, add an explicit hostname-equality check between the existing remote URL and the incoming `apiRepo.clone_url` (reusing `parseRemote`/`urlMatchesRemote`'s hostname field) before allowing an automatic rewrite, and refuse (or prompt the user) if the hostname differs from the account's configured endpoint host. At minimum, never silently switch to a different hostname without explicit user confirmation.

### Proof of Concept
1. Add a GitHub Enterprise Server account in Desktop pointing at `https://ghe.example.com` (attacker-controlled or MITM'd).
2. Clone a repo from that server; `origin` is set to `https://ghe.example.com/org/repo.git`.
3. Attacker's server later serves a `GET repos/org/repo` response with `"clone_url": "https://evil.example.com/org/repo.git"` (still `https`, so `protocolsMatch` is true; the URL differs in hostname, so `urlsMatch` is false).
4. Desktop's periodic/background call to `repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl` sees `protocolsMatch && remoteUrlUnchanged && !urlsMatch` all satisfied and calls `gitStore.setRemoteURL('origin', 'https://evil.example.com/org/repo.git')` — rewriting the remote with no user interaction, confirmable via `app/src/lib/stores/updates/update-remote-url.ts:42-44` and `app/src/lib/git/remote.ts:56-64`.
5. Subsequent pushes/fetches by the user now target `evil.example.com`.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

  /** Fetch a repo by its owner and name. */
  public async fetchRepository(
    owner: string,
    name: string
  ): Promise<IAPIFullRepository | null> {
    try {
      const response = await this.ghRequest('GET', `repos/${owner}/${name}`)
      if (response.status === HttpStatusCode.NotFound) {
        log.warn(`fetchRepository: '${owner}/${name}' returned a 404`)
        return null
      }
      return await parsedResponse<IAPIFullRepository>(response)
    } catch (e) {
      log.warn(`fetchRepository: an error occurred for '${owner}/${name}'`, e)
      return null
    }
  }

      t,
      apiRepository
    )
    assert(gitStore.currentRemote !== null)

    const originalUrl = gitStore.currentRemote.url
    const updatedUrl = 'https://github.com/my-user/my-updated-repo'
    const updatedApiRepository = { ...apiRepository, clone_url: updatedUrl }

  })
