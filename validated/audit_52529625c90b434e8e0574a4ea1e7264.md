### Title
`ReceivedOutput::read` accepts untrusted bytes that break the offset ↔ script_pubkey binding, letting an attacker inject outputs Serai reports as received but cannot spend - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`Scanner::scan_transaction` guarantees that every `ReceivedOutput` it produces satisfies `output.script_pubkey == p2tr(key + offset)` — the offset is looked up from the registered `scripts` map keyed by the output's actual script (networks/bitcoin/src/wallet/mod.rs:199-214). `ReceivedOutput::read`, an in-scope untrusted-bytes deserialization API, deserializes `offset`, `output` (a `TxOut`), and `outpoint` independently and performs no such consistency check (lines 122-134). An attacker can therefore fabricate a `ReceivedOutput` claiming an arbitrary scalar offset for a `TxOut` paying to any script — including one not controlled by the group's key — and Serai will treat it as a spendable, received output.

### Finding Description
The spendability invariant of `ReceivedOutput` is enforced only at construction time inside `Scanner` (`self.scripts.get(&output.script_pubkey)` at line 205). The `read` constructor bypasses this entirely: it calls `Secp256k1::read_F` for the offset, then `TxOut::consensus_decode` and `OutPoint::consensus_decode` for the rest, returning the tuple as a valid `ReceivedOutput` (lines 123-133). There is no `Scanner`-keyed validation and no check that `p2tr_script_buf(key + offset)` equals `output.script_pubkey`. This is the direct analog of the CVE's UI-spoofing class: the object presents itself to downstream consumers ("reported received") as spendable funds under a known key offset, when in fact the bytes attest to no such relationship.

### Impact Explanation
A spoofed `ReceivedOutput` whose `TxOut` does not correspond to `key + offset` is unspendable by the group. If it is fed into `SignableTransaction::new` and the signing flow in `send.rs`, the threshold group will produce a Schnorr signature under `key + offset` for an input the key cannot authorize, yielding a transaction Bitcoin rejects — i.e., funds reported received that are not spendable, plus a signer round spent on an unspendable input. This matches the accepted impact class "funds reported received that are not spendable" and an undocumented deserialization/invariant gap.

### Likelihood Explanation
Reachability requires that attacker-influenced bytes reach `ReceivedOutput::read` (an API explicitly listed as in-scope for untrusted input). The impact is bounded: the forged input produces an invalid spend rather than key leakage or a forged signature, so severity is Medium at best (DoS of a signing session / corrupted output accounting). I was unable to fully verify the exact downstream consumption path of `ReceivedOutput::read` results in the in-scope crates (`send.rs` signing flow was not read), so the strength of the end-to-end impact carries some uncertainty.

### Recommendation
In `ReceivedOutput::read`, or at the point where a deserialized `ReceivedOutput` is first consumed, verify `output.script_pubkey == p2tr_script_buf(key + offset)` against the scanning key (or record the expected script during `write`/`read`). Alternatively, make `read` take the `Scanner` (or expected key) so the offset-to-script binding is re-validated on deserialization, mirroring the check in `scan_transaction` at line 205.

### Proof of Concept
```rust
// networks/bitcoin context; attacker-controlled bytes:
let mut bytes = Vec::new();
// offset = 1 (or any scalar)
bytes.extend((Scalar::ONE).to_bytes());
// TxOut paying to an attacker-chosen script_pubkey NOT equal to p2tr(key + 1)
bytes.extend(bitcoin::consensus::encode::serialize(&TxOut {
  value: Amount::from_sat(50_000),
  script_pubkey: attacker_script, // e.g. P2TR to attacker's own key
}));
// any OutPoint the attacker claims
bytes.extend(bitcoin::consensus::encode::serialize(&claimed_outpoint));

let forged = ReceivedOutput::read::<&[u8]>(&mut bytes.as_ref()).unwrap();
// forged.offset() == 1, forged.output().script_pubkey != p2tr(key + G*1)
// Consumers treat `forged` as a spendable Serai output; any spend built on it
// produces a signature under key+1 for an input that key does not control.
```
