### Title
`updateEndRemainingAllocation()` can be re-triggered to shrink the bonus denominator and let later claimants over-extract `totalBonus` - (File: rewards/Airdrop.sol)

### Summary
`updateEndRemainingAllocation()` is a public, unguarded function that can be called by anyone, any number of times, after `periodsEndTime[4]`. Because it always overwrites `totalEndRemainingAllocation` with the *current* `totalRemainingAllocation`, and `totalRemainingAllocation` only shrinks as other users claim, an attacker can re-snapshot the bonus denominator to a smaller value immediately before calling `claim()`, inflating their own `getBonusAmount()` payout at the expense of the fixed `totalBonus` pool and other claimants' principal.

### Finding Description
The intended design of the vesting/bonus mechanism is:
- Users who claim early (before `periodsEndTime[4]`) forfeit the unvested portion of their allocation; that forfeited amount is added to `totalBonus` in `claim()`: [1](#0-0) .
- After `periodsEndTime[4]`, all periods are fully vested (`percentPerPeriod` sums to `denominator`), so `claimableAmount == userAllocation` and no further forfeiture/`totalBonus` growth occurs from that point on.
- `totalEndRemainingAllocation` is meant to be a one-time snapshot of `totalRemainingAllocation` taken at the moment the vesting period ends, used as the fixed denominator so every remaining claimant's bonus share is `userAllocation * totalBonus / totalEndRemainingAllocation`: [2](#0-1) .

The bug is that the snapshot function has no "already set" guard and is public: [3](#0-2) 

`claim()` only guards against re-triggering the snapshot through its own internal call path (`if (totalEndRemainingAllocation == 0)`): [4](#0-3) , but nothing stops any address from calling `updateEndRemainingAllocation()` directly at any later time. Each direct call recomputes `totalEndRemainingAllocation = totalRemainingAllocation`, and since `totalRemainingAllocation` only decreases as other users claim and zero out their `allocations[user]` [5](#0-4) , the denominator used for the bonus calculation shrinks monotonically over time while the numerator `totalBonus` stays fixed post-vesting-end.

An attacker can wait for several legitimate users to claim (shrinking `totalRemainingAllocation`), then call `updateEndRemainingAllocation()` themselves immediately before `claim()`, re-pinning the denominator to the smaller current value and thereby inflating their own bonus far beyond their fair proportional share of `totalBonus`. Because the sum of bonuses paid to sequential claimants who each re-snapshot the denominator can exceed the actual `totalBonus` accumulated (e.g., four equal claimants re-snapshotting successively receive far more in aggregate bonus than `totalBonus` itself), the contract can pay out more airdrop tokens than were ever forfeited, draining balance intended for other users' principal and causing later legitimate claimants to hit `InsufficientBalance` (funds frozen/lost).

### Impact Explanation
This is a direct theft of user funds / protocol insolvency: an unprivileged caller can inflate their own bonus payout beyond the fixed `totalBonus` pool by manipulating the timing of a public, unguarded snapshot function, at the expense of other users' principal allocations or the accuracy of the reserved bonus pool. This matches the Immunefi "Critical - Direct theft of user funds" class, since real ERC20 (`aidropToken`) value is extracted disproportionately and can leave other, non-malicious claimants unable to claim their legitimately earned principal+bonus.

### Likelihood Explanation
- No special privileges are required; `updateEndRemainingAllocation()` and `claim()` are both `external`/`public` with no access control.
- The only precondition is `block.timestamp >= periodsEndTime[4]` (airdrop vesting fully matured) and that at least one other claim has already reduced `totalRemainingAllocation` since the first snapshot — a naturally occurring condition once the airdrop enters its final claim phase with multiple participants.
- No capital is needed beyond the attacker's own registered allocation; the attack is simply calling two public functions in the right order, and is repeatable by any claimant who wants to front-run the "first snapshot" state.

### Recommendation
Make the end-remaining-allocation snapshot idempotent/one-time, e.g., add an explicit `bool endRemainingAllocationSet` flag (or check `totalEndRemainingAllocation == 0` inside `updateEndRemainingAllocation()` itself, matching the guard already present in `claim()`), so the value can only ever be set once regardless of caller:
```solidity
function updateEndRemainingAllocation() public {
    if (block.timestamp >= periodsEndTime[4] && totalEndRemainingAllocation == 0) {
        totalEndRemainingAllocation = totalRemainingAllocation;
    }
}
```
Additionally, consider capturing the snapshot automatically at `periodsEndTime[4]` via a keeper/permissionless-but-idempotent call rather than relying on the first `claim()`/`updateEndRemainingAllocation()` invocation timing.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy `Airdrop` with `startTime = now + 1`, register 4 users with equal `allocations` (e.g., 100e18 each), fund the contract with enough `aidropToken`.
2. Warp to before `periodsEndTime[4]`; have one additional user (`earlyClaimer`, allocation 100e18) call `claim()` early so that `claimableAmount < allocation`, causing `totalBonus` to accumulate a nonzero forfeited amount (e.g., 50e18).
3. Warp to `>= periodsEndTime[4]`.
4. `user1.claim()` — this triggers the first `updateEndRemainingAllocation()` internally, snapshotting `totalEndRemainingAllocation = totalRemainingAllocation` (call this `D0`). Record `user1`'s received bonus (`bonus1 = alloc * totalBonus / D0`).
5. `user2.claim()` (no manipulation) — record `bonus2` computed against the same `D0` reduced only by `user1`'s exit — expected roughly consistent with fair share.
6. Now have `attacker` (a remaining registered claimant) explicitly call `updateEndRemainingAllocation()` directly right before calling `claim()`. Assert that `totalEndRemainingAllocation` changes to the new, smaller `totalRemainingAllocation` (post `user1`/`user2` claims), and that `attacker`'s resulting bonus (`bonusAttacker = alloc * totalBonus / newSmallerDenominator`) is strictly greater than what they would have received under the original `D0` snapshot.
7. Sum all bonuses paid (`bonus1 + bonus2 + bonusAttacker + ...`) and assert this sum can exceed the original `totalBonus` recorded at step 2, and/or that the last remaining legitimate claimant's `claim()` reverts with `InsufficientBalance` due to token balance depletion — demonstrating direct fund theft/frozen funds for honest users.
