## Title
Split-then-floor division in CPI instruction-translation cost accounting systematically undercharges compute units - (File: `program-runtime/src/cpi.rs`)

### Summary
`translate_instruction_rust` and `translate_instruction_c` compute the compute-unit cost of translating a CPI instruction's data and account-metas by performing **two separate integer (floor) divisions and then summing the results**, instead of summing the byte counts first and dividing once. This is the same "divide in the middle instead of at the end" anti-pattern flagged in the external report, and it causes the CPI-translation charge to be systematically less than the cost model intends.

### Finding Description
In `program-runtime/src/cpi.rs`, the cost of translating a CPI `Instruction` from guest memory is computed as: [1](#0-0) 

```rust
let mut total_cu_translation_cost: u64 = (data.len() as u64)
    .checked_div(invoke_context.get_execution_cost().cpi_bytes_per_unit)
    .unwrap_or(u64::MAX);

let account_meta_translation_cost =
    (account_metas.len().saturating_mul(size_of::<AccountMeta>()) as u64)
        .checked_div(invoke_context.get_execution_cost().cpi_bytes_per_unit)
        .unwrap_or(u64::MAX);

total_cu_translation_cost =
    total_cu_translation_cost.saturating_add(account_meta_translation_cost);
```

The identical pattern exists in the C variant: [2](#0-1) 

The intended cost model is "bytes charged per `cpi_bytes_per_unit`" — i.e. `floor(total_bytes / cpi_bytes_per_unit)`. Because `floor(a/n) + floor(b/n) <= floor((a+b)/n)`, computing `floor(data_len/n) + floor(meta_len/n)` instead of `floor((data_len+meta_len)/n)` always undercharges (never overcharges), and the discrepancy can be as large as `n-1` (currently `cpi_bytes_per_unit = 250`) per CPI call, purely because the division was performed on each component separately rather than on the combined total. [3](#0-2) 

This mirrors exactly the "division in the midst of a calculation instead of at the end" bug class from the report: multiplication/addition of the two byte counts should happen first, then a single division at the end.

### Impact Explanation
Every cross-program invocation (`invoke`/`invoke_signed`) goes through `translate_instruction_rust` or `translate_instruction_c`, both callable freely by any unprivileged on-chain program. Each call under-consumes compute units relative to the intended cost model by up to `cpi_bytes_per_unit - 1` (249) CUs. Because CPI depth/call count within a transaction is bounded only by `max_instruction_trace_length` (and effectively by the transaction's own CU budget), a program that performs many CPIs with data/account-meta sizes engineered to individually round down (e.g., data length and meta-bytes each just under a multiple of 250) can accumulate a non-trivial amount of "free" compute across a transaction, i.e., materially underpriced compute relative to what the fee/cost model assumes it charges.

### Likelihood Explanation
The mis-charge is deterministic and requires no privileged access — any BPF program invoking a CPI instruction with a chosen instruction-data length and account-meta count will trigger it on essentially every CPI call. It is not a corner case; it reproduces on default cost parameters (`cpi_bytes_per_unit = 250`).

### Recommendation
Sum the byte counts first, then perform a single division:
```rust
let total_bytes = (data.len() as u64)
    .saturating_add(account_metas.len().saturating_mul(size_of::<AccountMeta>()) as u64);
let total_cu_translation_cost = total_bytes
    .checked_div(invoke_context.get_execution_cost().cpi_bytes_per_unit)
    .unwrap_or(u64::MAX);
```
Apply the same fix to `translate_instruction_c`.

### Proof of Concept
1. Craft a CPI `Instruction` where `data.len()` is, e.g., `249` bytes (just under one `cpi_bytes_per_unit` unit) and where `account_metas.len() * size_of::<AccountMeta>()` is also just under a multiple of 250 (e.g., 3 accounts → 102 bytes, or more accounts to approach 249 again).
2. With current code: `floor(249/250) = 0` for data, `floor(102/250) = 0` for metas → total charge `0`.
3. With combined-sum-first calculation: `floor((249+102)/250) = floor(351/250) = 1` → charge `1`.
4. Repeating such a crafted CPI invocation many times within a transaction (bounded by `max_instruction_trace_length`) accumulates an under-charge of up to `(cpi_bytes_per_unit - 1)` CU per call versus the intended model, which can be measured by comparing consumed compute units reported via `sol_remaining_compute_units` before/after the loop against the expected combined-division cost.
