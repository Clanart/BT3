### Title
Cached FROST preprocess reused across distinct `sign()` calls enables secret share recovery via differing binding factors - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
`SigningProtocol::share_internal` regenerates a deterministic FROST signing machine from a DB-cached preprocess seed every time it runs. Because `share()` and `complete()` each invoke `share_internal` (potentially multiple times per attempt, with different preprocess sets), the same underlying nonce pair `(d, e)` is signed under different binding factors `rho`, violating the one-use requirement on preprocesses and enabling algebraic recovery of the validator's MuSig/FROST secret share — the same bug class as the Orbit Chain key-compromise bridge drain.

### Finding Description
`preprocess_internal` stores only a 32-byte seed in `CachedPreprocesses`, keyed by `context` (for `DkgConfirmer`, `(b"DkgConfirmer", attempt)`), and rebuilds the machine via `AlgorithmSignMachine::from_cache` on every call [1](#0-0) . `share_internal` calls `preprocess_internal` unconditionally and then `machine.sign(preprocesses, msg)` [2](#0-1) .

Two public paths trigger signing under the same seed:

1. `DkgConfirmer::share` → `share_internal` → `sign` [3](#0-2) 
2. `DkgConfirmer::complete` → `share_internal` → `sign` [4](#0-3) 

Inside `sign`, the effective nonce scalar is `actual = base + rho * binding_nonce`, where `rho = H_rho(group_key, hash_msg(msg), hash_commitments(transcript over participant set + preprocess bytes))` [5](#0-4) . The participant set folded into the transcript — and hence `rho` — is derived from the keys of the caller-supplied `preprocesses` map [6](#0-5) . Because the underlying nonces `(d, e)` come from the same seed, two `sign` executions with different preprocess sets (or different `msg`) produce signature shares of the form:

```
share_i = d + rho_i * e + lambda_i * s * c_i
```

with publicly known `rho_i`, `lambda_i`, `c_i`. Each share published on the tributary yields one linear equation in the three unknowns `(d, e, s)`; three shares under distinct `rho`/message recover the secret share `s` outright. The file's own header acknowledges the hazard ("it is explicitly unsafe to reuse nonces across signing sessions") but the nonce-reuse protection rests entirely on BFT message consistency — it does not prevent `share`/`complete` being invoked on *different* preprocess sets within one finalized attempt, since preprocesses arrive in separate transactions and the set passed in is whatever has been received so far [7](#0-6) . The code even flags the missing guard: "we have to check the commitments generated from the decided nonces are in fact its commitments on-chain (TODO)" [8](#0-7) .

`ThresholdKeys` reuse also does not save this: `musig(...)` is rebuilt identically each call, so `from_cache` yields bit-identical nonces regardless of which `participants` list or `preprocesses` map is supplied [9](#0-8) .

### Impact Explanation
Recovery of `s` — the validator's share of the MuSig validator-set key — is equivalent to compromise of a multisig signer key (the Orbit Chain bug class). Combined with the ability to observe all published shares, an attacker who collects `>= t` leaked shares, or who already participates, can forge `set_keys` confirmations and any other signature the validator set produces. Even short of full key theft, each additional distinct-`rho` share progressively exposes the nonce scalars, and the shares are broadcast publicly on the tributary.

### Likelihood Explanation
Triggering requires `share_internal` to run multiple times under one `(b"DkgConfirmer", attempt)` context with differing preprocess maps or messages. This occurs when a coordinator calls `share()` on an early subset of received preprocesses and `complete()` (or `share()` again) later on a different subset — sets are assembled from independently submitted validator transactions, not pinned to a canonical set. No collusion or key access is needed; an external participant only needs distinct preprocess sets to be presented, which normal asynchronous message arrival can produce. The protection argument in the header covers reorgs and rebuilds but not in-attempt set variation.

### Recommendation
- Bind the cache entry to the exact signing inputs: store alongside the seed a hash of `(sorted preprocess set, msg)` and refuse to sign if a subsequent call presents a different tuple for the same context.
- Alternatively, track "seed consumed" state so `share_internal` can execute at most once per context, deriving `complete`'s machine from stored post-`sign` state rather than re-running `sign`.
- Implement the noted TODO: verify the regenerated commitments match the ones already published on-chain before emitting any share.

### Proof of Concept
1. Attempt `a` begins; coordinator calls `preprocess()` → seed `S` stored under `("DkgConfirmer", a)`, commitments `C` published.
2. Transaction carrying preprocesses `{P2, P3}` arrives; `share()` is invoked → `share_internal` rebuilds nonces `(d, e)` from `S`, signs with set `{self, P2, P3}` → share `sig_1 = d + rho_1 e + λ_1 s c_1` published.
3. A further transaction carrying `P4`'s preprocess arrives; `complete()` is invoked with `{P2, P3, P4}` → `share_internal` rebuilds the same `(d, e)` from `S`, signs with the 4-party set → `sig_2 = d + rho_2 e + λ_2 s c_2`.
4. A third invocation with yet another distinct set/message yields `sig_3`.
5. Observer solves the 3×3 linear system over the scalar field for `(d, e, s)` — recovering the validator's secret share — since `rho_i`, `λ_i`, `c_i` are all computable from public transcript data.

*Caveat:* I could not fully trace `handle.rs` call ordering to confirm how many times `share()`/`complete()` may fire per attempt; the linear-system attack requires at least three distinct-`rho` signatures (two suffice if `msg` is identical across calls, reducing unknowns to `(d, e)`-linear forms that still expose `s` when combined with the known share structure). If the coordinator guarantees the identical preprocess map on every call, the shares are identical and no leak occurs — the vulnerability is the absence of any code-level enforcement of that invariant, which the file itself marks as TODO.
