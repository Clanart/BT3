Based on the evidence gathered, I found a genuine local analog: the BEEFY consensus verifier (both the Substrate/Rust and EVM implementations) lacks the duplicate-signer guard that sibling verifiers in the same codebase already added for the exact same bug class.

### Title
BEEFY consensus verifiers count raw ECDSA vote entries toward the supermajority threshold without deduplicating authority indices, allowing padded/duplicate votes to fake quorum - (File: `modules/consensus/beefy/verifier/src/lib.rs`, `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
The external report's core defect is: a counter of "valid signers" is incremented from a raw list of signature entries without checking for duplicates, so one real signer can be replicated to satisfy a supermajority/threshold check. Hyperbridge's own codebase shows it is aware of this exact bug class and has patched it in some consensus verifiers but not in the BEEFY (ECDSA) verifier, which is the primary consensus client securing Polkadot-relay-chain-derived state on both Substrate and EVM.

### Finding Description
In `verify_mmr_update_proof` (`modules/consensus/beefy/verifier/src/lib.rs`), the threshold check is: [1](#0-0) 
`signatures_length` is simply `mmr.signed_commitment.signatures.len()` — a raw count of entries in an attacker/relayer-supplied vector — checked against `check_participation_threshold`: [2](#0-1) 
Each signature is then independently ECDSA-recovered and pushed into `authority_leaves`/`authority_indices` with **no deduplication** on `sig.index`: [3](#0-2) 
The identical pattern exists on the EVM side in `verifyMmrUpdateProof` (`EcdsaBeefy.sol`): `sigLen` is the raw `votes.length`, checked with `checkParticipationThreshold`, then each vote is recovered and pushed into a `Leaf[]` array with no uniqueness check on `authorityIndex`: [4](#0-3) [5](#0-4) 

Contrast this with two other verifiers in the same codebase that explicitly guard against this exact bug class:
- Pharos verifier rejects duplicate participant BLS keys before counting stake: [6](#0-5) 
- Tendermint verifier rejects a validator set with a repeated address: [7](#0-6) 
- Sync-committee verifier is structurally immune because it counts bits in a bitvector rather than raw list entries: [8](#0-7) 

BEEFY has no equivalent check on `signatures`/`votes`. Because the merkle multi-proof only needs the caller-supplied `(index, leaf)` pairs to be internally consistent with the proof hashes (the leaf values for known indices are not re-derived from anything external), supplying the same valid `(authorityIndex, signature)` pair multiple times inflates `signatures_length`/`sigLen` without adding any additional real signer, while still constructing a merkle multi-proof that verifies (each duplicated leaf trivially matches its own known position in the tree).

### Impact Explanation
If a relayer/prover-submitted consensus proof can satisfy the 2/3+1 supermajority check with signatures from fewer real authorities than required (in the extreme, a single or minority-colluding signer duplicating their vote entries), the light client accepts a BEEFY commitment — and therefore an MMR root and derived parachain state commitments — that was never actually finalized by the real supermajority of the relay chain's authority set. This is exactly the "false proof/state acceptance" category called out as in-scope: it lets forged remote state become trusted on Hyperbridge (Substrate) and on any EVM chain running `EcdsaBeefy`, which underlies fund movement, request/response settlement, and every downstream ISMP action gated on consensus state.

### Likelihood Explanation
This does not require a colluding validator majority or leaked keys — it only requires whoever assembles the `MmrProof`/`RelayChainProof` (an untrusted, permissionless relayer/prover role by design) to duplicate index/signature entries they already possess. The check is purely a count of vector length; there is no code path anywhere in `verify_mmr_update_proof` or `verifyMmrUpdateProof` that deduplicates `sig.index`/`vote.authorityIndex` before the threshold comparison, unlike the parallel Pharos and Tendermint verifiers in the same repository that explicitly close this gap.

### Recommendation
Before comparing against the supermajority threshold, deduplicate on `authorityIndex` (e.g., collect into a `BTreeSet`/mapping and use its length) in both `verify_mmr_update_proof` (Rust) and `verifyMmrUpdateProof` (Solidity), mirroring the `verify_validator_membership`/`ensure_unique_addresses` pattern already used by the Pharos and Tendermint verifiers, and reject the proof if the deduplicated count is lower than the vector length.

### Proof of Concept
1. Obtain (or produce, as the untrusted relayer/prover role) one valid ECDSA signature over a BEEFY commitment from a single authority at index `i`, sufficient for at least one genuine authority membership merkle proof leaf.
2. Construct `signed_commitment.signatures` (or `signedCommitment.votes`) by repeating the `(index: i, signature: sig)` entry `N` times, where `N >= (2*total)/3 + 1`.
3. Submit this as `MmrProof`/`RelayChainProof` to `verify_mmr_update_proof` / `EcdsaBeefy.verify`.
4. `signatures_length`/`sigLen` equals `N`, passing `check_participation_threshold`/`checkParticipationThreshold` even though only one real authority actually signed.
5. Each duplicated entry recovers the same address and produces the same `(index, leaf)` pair, which trivially satisfies the merkle multi-proof against the authority set root since it's the correct leaf for that known index.
6. The verifier accepts the forged consensus update, advancing `trusted_state.latest_beefy_height` and finalizing attacker-influenced MMR/parachain state commitments.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
