## Title
Discard Changes writes/deletes files using an unverified path from a malicious repository's status entry, bypassing the repo-containment check used elsewhere - (File: `app/src/lib/stores/git-store.ts`)

### Summary
The external report's broken invariant is: a destructive operation (`transferFrom`) trusted an attacker-influenced parameter (`from`) without verifying it against the true state (actual token owner), instead relying on a weaker, unrelated authorization path (`sendNft`'s "authorized to manage" check). The equivalent invariant in GitHub Desktop is: a destructive filesystem operation (discarding/deleting a working-tree file) must verify that the path it is about to act on truly resides inside the repository root before touching the filesystem. Desktop has already recognized this class of bug and added a dedicated guard, `resolveWithin`/`resolveWithinPosix`/`resolveWithinWin32` in [1](#0-0) , which resolves symlinks via `realpath` and checks the result is contained in the repo root. That guard is consistently applied in newer code paths such as Copilot conflict-resolution file writes [2](#0-1)  and deep-link file opening [3](#0-2) . However, `GitStore.discardChanges`, the core "Discard Changes" implementation, does **not** use this guard and instead resolves the path with plain, non-symlink-aware `Path.resolve`/`Path.join`, exactly mirroring the pattern OtterAudits flagged: a critical authorization/containment check exists elsewhere in the codebase but is skipped for this particular destructive path.

### Finding Description
`GitStore.discardChanges` takes `WorkingDirectoryFileChange[]` (derived from `git status` parsing) and, for each file, computes the on-disk path to delete/trash as:

```ts
await this.shell.moveItemToTrash(
  Path.resolve(this.repository.path, file.path)
)
...
await rm(Path.join(this.repository.path, file.path))
``` [4](#0-3) 

`file.path` (and `file.status.oldPath` for renames/copies, also blindly checked out at [5](#0-4) ) comes straight from the porcelain status parser, which returns whatever string git reports for a path field with no normalization or root-containment check [6](#0-5) . `Path.resolve`/`Path.join` are purely lexical: unlike `resolveWithin`, they never call `realpath` and never verify that the final resolved location is still a descendant of `repository.path` (see the dedicated symlink-escape test proving why that call is necessary: [7](#0-6) ). The only check performed before deleting is a submodule-path string match [8](#0-7) ; there is no check that the path stays inside the working directory once any intermediate path component is a symlink.

This is the direct functional analog of the CW721 report: `transferFrom` trusted the caller-supplied `from` without checking it against the real ownership record; `discardChanges` trusts the git-status-supplied `file.path` without checking it against the real repository boundary, even though the codebase has since built (and applies elsewhere) exactly the primitive needed to perform that check.

### Impact Explanation
An attacker who controls a cloned/fetched repository (or a working tree the victim opens in Desktop, e.g. via a symlinked directory checked out/created by a build step, IDE, or another tool while the repo is open in Desktop) can arrange for a working-tree entry reported by `git status` to traverse through a symlinked directory component. Because `discardChanges` resolves that path with plain lexical resolution and hands it directly to `shell.moveItemToTrash` / `rm` (which do follow symlinked intermediate directories at the OS level), a "Discard changes" action the user believes only touches files inside the repository can move-to-trash or permanently delete a file outside the repository, causing unauthorized file deletion/corruption outside the intended repo boundary — matching the "file write or read outside the repo" and "silent corruption" impact classes.

### Likelihood Explanation
Likelihood is moderate: it requires a working tree containing a symlinked directory whose target lies outside the repo, with git reporting an untracked/modified file path that traverses that symlink (untracked symlinked directories themselves are reported as a single untracked entry, but nested build tooling, submodule mismanagement, or a maliciously crafted worktree/checkout can produce a status entry whose path component is such a symlink). This is a purely repository/working-tree-content-driven attacker primitive — no local/admin access, no leaked credentials, and no unnatural user step beyond the ordinary "Discard Changes" action the app markets as safe. The presence of the dedicated `resolveWithin` hardening elsewhere in the codebase, deliberately added to close exactly this class of bug for other file-writing code paths, strongly indicates the team is aware of and defends against this exact primitive — but `discardChanges` was missed.

### Recommendation
In `GitStore.discardChanges` (`app/src/lib/stores/git-store.ts`), replace the raw `Path.resolve(this.repository.path, file.path)` / `Path.join(this.repository.path, file.path)` calls with `resolveWithin(this.repository.path, file.path)` (as already used in `app-store.ts` and `dispatcher.ts`), and skip/report the file if the resolved path is `null` (outside the repository root), before calling `shell.moveItemToTrash` or `rm`. Apply the same containment check to `file.status.oldPath` used for checkout in the rename/copy branch.

### Proof of Concept
1. Attacker prepares/influences a working tree opened in Desktop such that a component of a reported working-directory path is a symlink pointing outside the repository (e.g., `linked-dir -> /Users/victim/Documents/important`), and git status reports an untracked or modified file such as `linked-dir/secret.txt`.
2. Victim opens the repository in Desktop, sees the file in the Changes list, and clicks "Discard Changes".
3. `GitStore.discardChanges` computes `Path.resolve(repository.path, 'linked-dir/secret.txt')`, which lexically looks like it's under the repo, but the OS resolves `linked-dir` through the symlink when the trash/delete syscall runs.
4. `shell.moveItemToTrash` (or the `rm` fallback path) operates on `/Users/victim/Documents/important/secret.txt`, deleting/trashing a file outside the repository — without any `resolveWithin`-style containment check ever being performed, unlike the hardened Copilot/deep-link code paths shown at [2](#0-1)  and [3](#0-2) .

async function _resolveWithin(
  rootPath: string,
  pathSegments: string[],
  options: {
    join: (...pathSegments: string[]) => string
    normalize: (p: string) => string
    resolve: (...pathSegments: string[]) => string
  } = Path
) {
  // An empty root path would let all relative
  // paths through.
  if (rootPath.length === 0) {
    return null
  }

  const { join, normalize, resolve } = options

  const normalizedRoot = normalize(rootPath)
  const normalizedRelative = normalize(join(...pathSegments))

  // Null bytes has no place in paths.
  if (
    normalizedRoot.indexOf('\0') !== -1 ||
    normalizedRelative.indexOf('\0') !== -1
  ) {
    return null
  }

  // Resolve to an absolute path. Note that this will not contain
  // any directory traversal segments.
  const resolved = resolve(normalizedRoot, normalizedRelative)

  const realRoot = await realpath(normalizedRoot)
  const realResolved = await realpath(resolved)

  return realResolved.startsWith(realRoot) ? resolved : null
}
```

// 2 <XY> <sub> <mH> <mI> <mW> <hH> <hI> <X><score> <path><sep><origPath>
const renamedOrCopiedEntryRe =
  /^2 ([MADRCUTX?!.]{2}) (N\.\.\.|S[C.][M.][U.]) (\d+) (\d+) (\d+) ([a-f0-9]+) ([a-f0-9]+) ([RC]\d+) ([\s\S]*?)$/

function parsedRenamedOrCopiedEntry(
  field: string,
  oldPath: string | undefined
): IStatusEntry {
  const match = renamedOrCopiedEntryRe.exec(field)

  if (!match) {
    log.debug(`parsedRenamedOrCopiedEntry parse error: ${field}`)
    throw new Error(`Failed to parse status line for renamed or copied entry`)
  }

  if (!oldPath) {
    throw new Error(
      'Failed to parse renamed or copied entry, could not parse old path'
    )
  }

  return {
    kind: 'entry',
    statusCode: match[1],
    submoduleStatusCode: match[2],
    oldPath,
    renameOrCopyScore: parseInt(match[8].substring(1), 10),
    path: match[9],
  }
}
