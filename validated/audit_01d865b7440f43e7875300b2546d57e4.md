### Title
Webhook HMAC verification does not bind the signature to the shop domain or topic, allowing a malicious merchant to replay a genuine signed webhook against a different shop - ([File: lib/shopify_app/controller_concerns/webhook_verification.rb](lib/shopify_app/controller_concerns/webhook_verification.rb))

### Summary
`ShopifyApp::WebhookVerification#verify_request` only validates that the HMAC in `X-Shopify-Hmac-Sha256` matches an HMAC computed over the raw request body (`request.raw_post`), using the app's shared client secret. [1](#0-0) 
It never checks that this proof of authenticity is bound to the `X-Shopify-Shop-Domain` header (or the `X-Shopify-Topic` header), both of which are read unauthenticated and later trusted for authorization/dispatch decisions. [2](#0-1) [3](#0-2) 

### Finding Description
The signature only covers the request body; the `shop`/`shop_domain` value used to look up and act on a specific tenant's record is derived purely from an unsigned header (or the unsigned `webhook_id`/`shop` field extracted by `ShopifyAPI::Webhooks::Request`), and the generated job templates key all destructive/data-sensitive actions off that header value without re-deriving or cross-checking it against anything covered by the HMAC: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Because Shopify's webhook client secret is per-app (not per-shop), any merchant who has installed the app already legitimately possesses one or more valid `(body, HMAC)` pairs from Shopify's own delivered webhooks for their own shop (e.g., topics whose bodies are constant/predictable such as `app/uninstalled`, which is typically delivered with an empty JSON body `{}`). Since the verification code checks only `hmac_valid?(request.raw_post)` and does not tie the accepted signature to the shop domain or topic that will be used downstream, that merchant can resend the exact same `(body, HMAC)` pair to the webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and, since `x-shopify-topic` routing in `ShopifyAPI::Webhooks::Registry.process` is likewise taken from an unsigned header, potentially an arbitrary topic) belonging to a different shop that uses the same app. This is precisely analogous to the Zetachain root cause: a value used to select/act on an entity (nonce there, shop_domain/topic here) is never checked for consistency with the cryptographically-verified payload, letting a malicious actor "point" a validated signature at unrelated state.

### Impact Explanation
This allows a malicious merchant/observer to trigger unauthorized state changes against a completely different shop that has installed the same app: e.g., replaying an `app/uninstalled` webhook to cause `shop.destroy` [8](#0-7)  against a victim shop, or replaying `shop/redact`/`customers/redact` to trigger deletion of another shop's stored data [9](#0-8) , or `customers/data_request` to trigger data-disclosure workflows for a victim's customer data [10](#0-9) . This is an accepted forged/misdirected signed request that causes cross-shop state change and potential permanent data loss for a victim tenant, without the attacker needing the app's secret.

### Likelihood Explanation
The attacker only needs to be an unprivileged, existing merchant of the app (an "unrelated-merchant" per the rules) who receives at least one genuine webhook with a predictable/reusable body (common for lifecycle/privacy topics with empty or near-empty JSON bodies), and the target must be another shop using the same multi-tenant app instance — a realistic scenario for any shopify_app-based app serving multiple merchants.

### Recommendation
Bind the accepted HMAC to the specific delivery: verify the signature together with (or in addition to) the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and ideally the `X-Shopify-Webhook-Id` values (e.g., by including them in the signed material, or by cross-checking that the shop domain in the header matches a shop domain independently known to be associated with the currently active `webhook_id`/session), rather than trusting the unsigned header for tenant selection in `shop_domain` and the downstream job templates.

### Proof of Concept
1. Malicious merchant `victim-unrelated.myshopify.com` has the app installed and captures a genuine Shopify-delivered `app/uninstalled` webhook request (body `{}`, valid `X-Shopify-Hmac-Sha256`).
2. They send a POST to the app's webhook endpoint with the same body/HMAC but `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a different shop using the same app).
3. `WebhookVerification#verify_request` only checks `hmac_valid?(request.raw_post)`, which passes since the body/HMAC pair is genuinely valid for the secret. [1](#0-0) 
4. The request is processed and `AppUninstalledJob` runs `Shop.find_by(shopify_domain: "victim-shop.myshopify.com")` and calls `shop.destroy`, destroying the victim shop's record despite the app never actually being uninstalled from that shop. [8](#0-7)

    def shopify_hmac
      request.headers["HTTP_X_SHOPIFY_HMAC_SHA256"]
    end

    def hmac_valid?(data)
      secrets = [ShopifyApp.configuration.secret, ShopifyApp.configuration.old_secret].reject(&:blank?)

      secrets.any? do |secret|
        digest = OpenSSL::Digest.new("sha256")
        ActiveSupport::SecurityUtils.secure_compare(
          shopify_hmac,
          Base64.strict_encode64(OpenSSL::HMAC.digest(digest, secret, data)),
        )
      end
    end
```

class AppUninstalledJob < ActiveJob::Base
  extend ShopifyAPI::Webhooks::WebhookHandler

  def self.handle(topic:, shop:, body:, webhook_id:, api_version:)
    perform_later(topic: topic, shop_domain: shop, webhook: body)
  end

  def perform(topic:, shop_domain:, webhook:)
    shop = Shop.find_by(shopify_domain: shop_domain)

    if shop.nil?
      logger.error("#{self.class} failed: cannot find shop with domain '#{shop_domain}'")
      
      raise ActiveRecord::RecordNotFound, "Shop Not Found"
    end

    logger.info("#{self.class} started for shop '#{shop_domain}'")
    shop.destroy
  end
```
