### Title
Unrestricted, shared `CallDispatcher` allows anyone to steal token/ETH dust or exploit residual allowances left by intent orders - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has **no access control** — it is `external` and callable by any address, not just the `IntentGateway`/`IntentsBase` contracts that are supposed to be its only legitimate callers. Because the `CallDispatcher` is a persistent, shared singleton used across every order's predispatch/postdispatch calldata execution (per its own docs: "Existing `CallDispatcher` deployments are listed on the contract addresses page"), it routinely and transiently holds real user/solver funds and can be left holding residual token balances or standing token approvals after an order's calls finish. Since `dispatch()` is unauthenticated, an attacker can call it directly with an arbitrary `Call[]` to sweep out whatever balance currently sits at the dispatcher's address, or to exploit any lingering `approve()` grants issued to third-party routers during a legitimate order's calldata.

### Finding Description
`CallDispatcher.sol` :
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [1](#0-0) 

There is no `msg.sender` check restricting `dispatch()` to be called only by an `IntentGatewayV2`/`IntentsBase` instance. Yet `IntentsBase._execute()` treats the dispatcher as a trusted, temporary funds holder:

```solidity
function _execute(Order calldata order, uint256 outputsLen) internal {
    if (order.output.call.length == 0) return;
    address dispatcher = _params.dispatcher;
    ICallDispatcher(dispatcher).dispatch(order.output.call);
    ...
    // sweep only the outputsLen listed tokens back to gateway as dust
}
``` [2](#0-1) 

The predispatch flow follows the same pattern: assets are transferred to the dispatcher, `dispatch()` executes the caller-supplied calls (e.g. swaps), and only the tokens explicitly known to the caller are swept back. The `_execute` sweep loop only iterates over `order.output.assets` (`outputsLen` entries) — any token balance left on the dispatcher that isn't one of those declared assets is never recovered by the protocol and simply sits at the dispatcher's address.

Because real calldata patterns granted to the dispatcher include **unlimited allowances** to external routers — demonstrated directly in the test suite:
```solidity
postdispatchCalls[0] = Call({
    to: address(usdc),
    value: 0,
    data: abi.encodeWithSelector(IERC20.approve.selector, uniswapRouter, type(uint256).max)
});
``` [3](#0-2) 

— the dispatcher can be left with standing, unlimited approvals to third-party contracts after an order completes, exactly mirroring the `HardenedTopupProxy` root cause of granting `type(uint256).max` allowance instead of the exact amount needed for the current transaction.

Combined with `dispatch()`'s complete lack of caller restriction, this creates a direct analog of H-1: a shared, persistent contract (`topupproxy` ↔ `CallDispatcher`) that (1) accumulates leftover balance beyond what any single transaction accounts for, (2) grants unlimited rather than exact-amount allowances to external targets, and (3) can be driven by an unprivileged, unauthenticated caller to route arbitrary calldata that drains whatever value currently sits under its control — the very traits WatchPug identified as enabling the topupproxy attack.

### Impact Explanation
Any token or native-ETH balance stranded on the `CallDispatcher` (from partial/failed sweeps, slippage remnants outside the declared `output.assets` set, or funds in-flight between the transfer-to-dispatcher step and the sweep-back step across different order executions) is stealable by any external account, since `dispatch()` performs no authorization check. This is a direct "unauthorized transaction or execution" / "stealing or loss of funds" impact against a live production contract that is shared across all `IntentGatewayV2` order flows, so the blast radius covers dust and stray funds from every order routed through the gateway, not a single user's escrow.

### Likelihood Explanation
The likelihood is high for an unprivileged attacker: no proof forgery, relayer/prover compromise, or governance access is needed. The attacker only needs to observe the `CallDispatcher`'s on-chain token/ETH balance (a public, permissionless read) and submit a single transaction calling `dispatch()` with calldata that transfers that balance to themselves. The precondition — non-zero balance briefly or persistently held by the dispatcher — is a normal, documented side effect of the predispatch/postdispatch calldata-execution feature (dust from imperfect sweeps, rounding, or output tokens not enumerated in `order.output.assets`).

### Recommendation
1. Add an access-control check to `CallDispatcher.dispatch()` restricting callers to a registered `IntentGatewayV2`/`IntentsBase` instance (e.g., an `onlyAuthorizedCaller` allowlist set at deployment or via governance), so arbitrary external accounts cannot trigger arbitrary calls from the dispatcher.
2. Ensure `_execute`'s sweep logic accounts for *all* tokens the calldata could plausibly touch (not just the `outputsLen` output assets), or require calldata authors to declare every token that may be minted/received so it can be fully swept before the transaction ends.
3. Avoid granting unlimited allowances (`type(uint256).max`) from the `CallDispatcher` to external routers within order calldata; grant only the exact amount needed for that call, and revoke/reset it after execution, consistent with the guidance already given in the HFT docs ("Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances").

### Proof of Concept
1. A legitimate order executes `_execute()`, whose `order.output.call` includes `approve(uniswapRouter, type(uint256).max)` on some ERC20 `T` from the `CallDispatcher` (as shown in `testPostdispatchTokenSweep`), followed by a swap that leaves a small residual balance of `T` on the dispatcher that is not part of `order.output.assets` and therefore is never swept.
2. Attacker observes `T.balanceOf(dispatcher) > 0`.
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: T, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, T.balanceOf(dispatcher))})]))` directly — this succeeds because `dispatch()` has no caller restriction — draining the dispatcher's `T` balance to the attacker.
4. Repeat opportunistically across every order that routes calldata through the shared dispatcher to continuously harvest stray funds and exploit any standing router allowances left behind. [1](#0-0) [2](#0-1) [3](#0-2)
