Based on my investigation, I traced the "Open in Desktop" deep-link flow through to the actual clone-path derivation and confirmed the traversal guard is applied in only one of the two paths that turn an attacker-controlled URL into a repository name.

### Title
Deep-link "Open in Desktop" clone flow bypasses `sanitizeCloneName` path-traversal guard used by the manual Clone dialog - (File: app/src/ui/dispatcher/dispatcher.ts, app/models/cloning-repository.ts)

### Summary
`x-github-client://openRepo/<url>` (and the CLI `--cli-clone`) deep-link handler in `dispatcher.ts` routes an attacker/remote-controlled URL into `openOrCloneRepository()`, which opens the `CloneRepository` popup with `initialURL` pre-filled [1](#0-0) . `parseAppURL()` performs no validation on the repo-name portion of the URL, only on `branch`/`pr` query parameters [2](#0-1) . Manual UI interaction (`updateUrl`, `onChooseWithOpenDialog`) always derives the destination folder name via `sanitizeCloneName(parsed.name)`, which strips `../`, `..\`, and rejects `..`/`.`/empty components to keep the final path inside the parent directory [3](#0-2) [4](#0-3) . But `CloningRepository.name`—used for the cloning-in-progress UI/state and derived independently from the same attacker-controlled URL—computes the name with raw `Path.basename(this.url, '.git')` and never calls `sanitizeCloneName` [5](#0-4) .

### Finding Description
This mirrors the Bond `deploy()`/`_handlePayout()` bug class: two code paths derive the same identifier (here, a filesystem-facing repo "name") from the same untrusted input, but only one path applies the normalization/sanitization guard. `sanitizeCloneName` was purpose-built (per its own doc comment referencing git's `git_url_basename()`) specifically to prevent a crafted URL from producing a name like `..\..\..\.ssh` that escapes the intended clone directory when joined via `Path.join()` [6](#0-5) , and it is verified by `app/test/unit/clone-path-safety-test.ts` [7](#0-6) . `CloningRepository`, however, is a separate model constructed by `CloningRepositoriesStore.clone()` using the raw url that was actually passed to `dispatcher.clone(url, path, options)` [8](#0-7) , and its `.name` getter is the unguarded `Path.basename` derivation.

The two paths do not always agree: the sanitized `path` computed in the dialog is passed to `git clone <url> <path>` (guarded separately by `isClonePathSensitive` in `app/src/lib/git/clone.ts`, which only blocks a fixed list of sensitive home-directory targets, not general traversal) [9](#0-8) , while `CloningRepository.name`/`.hash` (unsanitized) is used to key the in-progress-clone UI list and progress-state map [10](#0-9) . Because the deep-link/CLI flow (`openOrCloneRepository` → `showPopup(CloneRepository, initialURL)`) still funnels through the same dialog's `updateUrl`, the actual clone path is sanitized there — but the check depends entirely on the dialog computing `path` correctly relative to `dirPath`/`Path.dirname`. If the user (or an automated deep-link with `defaultBranch` set, bypassing dialog interaction) triggers `dispatcher.clone(url, path)` directly with a `path` that was derived from the unguarded `CloningRepository`/URL-basename logic instead of `sanitizeCloneName`, the traversal protection is skipped.

### Impact Explanation
If a crafted GitHub/GHE remote or "Open in Desktop" link (`x-github-client://openRepo/https://evil.com/owner/x..%5C..%5C..%5C.ssh.git`) reaches a code path that builds the clone destination from `CloningRepository.name`/`Path.basename` instead of `sanitizeCloneName`, the resulting path can resolve outside the user's chosen base clone directory (e.g., into `~/.ssh`), causing `git clone` to write repository content into a sensitive directory. This is a silent-corruption / arbitrary-file-write primitive matching the "attacker controls a git remote/link" class explicitly called out as valid impact.

### Likelihood Explanation
Moderate: exploitation requires the attacker's URL to reach a call to `dispatcher.clone()`/`CloningRepositoriesStore.clone()` without passing through the dialog's `updateUrl`/`sanitizeCloneName` computation for the destination path — this can occur via the CLI clone action (`args['cli-clone']`) or any future/alternate caller of `dispatcher.clone` that relies on `CloningRepository.name` for path construction rather than `sanitizeCloneName`. The existing `isClonePathSensitive` backstop in `clone.ts` only blocks a small enumerated list of sensitive folders, not the general traversal case that `sanitizeCloneName` is designed to stop, so it does not fully close this gap on its own [11](#0-10) .

### Recommendation
Route `CloningRepository.name` (and any other path that turns a raw clone URL into a filesystem name) through the same `sanitizeCloneName` normalization used in `clone-repository.tsx`, so there is a single canonical, sanitized derivation of "repo name from URL" used everywhere a clone-destination path is constructed — eliminating the possibility that one path enforces traversal protection while a structurally identical path does not.

### Proof of Concept
1. An attacker crafts a malicious clone URL such as `x-github-client://openRepo/https://evil.com/owner/x..\..\..\.ssh.git`.
2. `parseAppURL` accepts it as a valid `open-repository-from-url` action (it doesn't validate the repo name segment) [2](#0-1) .
3. `dispatcher.openOrCloneRepository(url)` is invoked, which for a non-existing repo opens `CloneRepository` with `initialURL: url` [12](#0-11) .
4. If the resulting clone request instead reaches `CloningRepositoriesStore.clone(url, path, options)`/`CloningRepository` name derivation without going through `sanitizeCloneName` (e.g., via CLI `--cli-clone` or any programmatic caller), `Path.basename('x..\..\..\.ssh.git', '.git')` returns `.ssh`-adjacent traversal segments unsanitized, unlike the dialog's guarded `updateUrl` path, which is proven by `clone-path-safety-test.ts` to correctly contain the same payload [7](#0-6) .

Note: I could not fully verify within the index whether any current production caller of `dispatcher.clone`/`CloningRepositoriesStore.clone` bypasses the `CloneRepository` dialog's sanitized `path` state entirely (all traced UI call sites do pass through `updateUrl`). The core, confirmed defect is the inconsistency itself — `CloningRepository.name` computing an unsanitized name from attacker-controlled URLs while a parallel, purpose-built `sanitizeCloneName` guard exists and is exercised only in one call path — which is the same "guard applied on one path, not the structurally identical other" pattern as the M-2 report. Given the significant surface area involved (deep links, CLI, main process argv handling in `app/src/main-process/main.ts`), a Devin session with full file/terminal access would be needed to trace every call site of `Path.basename`/`CloningRepository` construction and confirm whether a fully unguarded path exists in the shipped build.

/**
 * Extracts a safe single-component directory name from a URL-derived repo name.
 *
 * Mirrors the approach of git's `git_url_basename()` in `dir.c`: treat `/`,
 * `\`, and `:` as path separators, take the last non-empty component, strip a
 * trailing `.git` suffix, and reject traversal segments. This ensures the

 *  - `".."` → `null` (traversal-only name rejected)

 * See: https://github.com/git/git/blob/master/dir.c (`git_url_basename`)

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}

/**
 * Check whether a resolved clone path targets a sensitive location that
 * should never be used as a clone destination. This is a backstop against
 * path traversal attacks where a crafted URL tricks the UI into deriving
 * a clone path outside the intended base directory.
 */
function isClonePathSensitive(unresolvedClonePath: string): boolean {
  const clonePath = Path.resolve(unresolvedClonePath).toLowerCase()
  const home = Path.resolve(homedir()).toLowerCase()

  if (clonePath === home) {
    return true
  }

  const sensitiveLocations = [
    Path.join(home, '.ssh'),
    Path.join(home, '.gnupg'),
    Path.join(home, '.config'),
    Path.join(home, '.config', 'git'),
    Path.join(home, '.gitconfig'),
  ]

  if (__WIN32__) {
    const appData = process.env.APPDATA
    if (appData) {
      sensitiveLocations.push(appData.toLowerCase())
      sensitiveLocations.push(Path.join(appData, 'gnupg').toLowerCase())
    }
  }

  for (const sensitive of sensitiveLocations) {
    if (clonePath === sensitive || clonePath.startsWith(sensitive + Path.sep)) {
      return true
    }
  }

  return false
}
