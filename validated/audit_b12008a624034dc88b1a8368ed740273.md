## Finding: `allowFileProtocol` parameter in `updateSubmodulesAfterOperation` is caller-controlled, and its default call sites need verification, but no `GIT_ALLOW_PROTOCOL` allowlist exists anywhere in the codebase for the standard `submodule update --recursive` path

### Title
Attacker-controlled `.gitmodules` in a cloned repository can trigger fetches of arbitrary submodule URLs without a transport allowlist - ([File: app/src/lib/git/submodule.ts])

### Summary
`updateSubmodulesAfterOperation` in [1](#0-0)  runs `git submodule update --init --recursive` against submodule URLs that come entirely from the repository's own `.gitmodules` file — content fully controlled by whoever authored the cloned/fetched repository (an attacker). The function explicitly supports opting into `protocol.file.allow=always` via the `allowFileProtocol` flag [2](#0-1) , and nowhere in the codebase is a `GIT_ALLOW_PROTOCOL`/`protocol.*.allow` allowlist configured to restrict which transports (`ext::`, `file://`, arbitrary helper protocols) a submodule URL is permitted to use during clone/checkout/pull. This mirrors the report's core theme — a party who doesn't control Desktop's trust boundary (there: the game admin; here: the author of a git remote/repo) can steer a privileged, security-relevant operation because a downstream safety control (protocol allowlisting) was never centrally enforced.

### Finding Description
Cloning is done with `--recursive` in `clone()` [3](#0-2) , and there is a dedicated helper, `updateSubmodulesAfterOperation`, invoked after checkout/pull/fetch to run `git submodule update --init --recursive` [4](#0-3) . Submodule URLs are read by Git from `.gitmodules`, a file that is part of the tracked, attacker-authored repository content — i.e., this is exactly the "attacker controls a cloned/fetched repository" primitive called out as valid in this task.

Git's own defense against malicious submodule/transport URLs (e.g., `ext::sh -c ...`, or unexpected `file://` reads) is the `protocol.<name>.allow` configuration / `GIT_ALLOW_PROTOCOL` environment variable, which by default in modern Git already blocks `ext::` unless explicitly enabled — but Desktop's own code shows it is aware of and actively toggles `protocol.file.allow=always` for submodules under some conditions (`allowFileProtocol` parameter), meaning Desktop already reaches into this exact protocol-gating mechanism. No corresponding restrictive allowlist (e.g., `-c protocol.ext.allow=never`, or a `GIT_ALLOW_PROTOCOL=file:git:http:https:ssh` env var) is set anywhere in `environment.ts`, `core.ts`, or `submodule.ts` [5](#0-4) . Whether this represents a genuinely broken invariant depends on which Git version ships via `dugite` and its compiled-in default for `protocol.ext.allow` — I was not able to verify the bundled Git's default protocol allowlist from local code alone, so this is a **potential** gap rather than a confirmed exploitable one.

### Impact Explanation
If the bundled Git's default protocol restrictions can be bypassed or if `allowFileProtocol` is ever set to `true` for a submodule update triggered against an untrusted, attacker-supplied repository (e.g., after cloning a URL from `open-repository-from-url`/`x-github-client://openrepo/...` deep link, or from a hostile fork's PR head), a malicious `.gitmodules` entry could cause Desktop to read local files via `file://` submodules or, in older/misconfigured Git installs, execute commands via `ext::`. This would constitute a repo-controlled RCE/file-read primitive, matching the "attacker controls a cloned/fetched repository" and resulting in "code execution, file write or read outside the repo" criteria from the task's valid-impact list.

### Likelihood Explanation
Likelihood is **low-to-medium** and unconfirmed: modern Git ships with `ext::`, `file://` (in some contexts) disabled by default at the protocol layer independent of Desktop's own configuration, so this would only be exploitable if (a) the bundled `dugite`/Git version's defaults are more permissive than assumed, or (b) `allowFileProtocol=true` is passed for submodule operations against a repository the user does not already fully trust (I could not trace all call sites of `updateSubmodulesAfterOperation` to confirm this). This uncertainty means I cannot assert this is a confirmed, exploitable vulnerability from the code alone — it is a plausible analog worth a background agent tracing all call sites of `updateSubmodulesAfterOperation` and the bundled Git's compiled default `protocol.*.allow` values.

### Recommendation
Explicitly set a restrictive `GIT_ALLOW_PROTOCOL` (e.g., `http:https:ssh:git`) or `-c protocol.ext.allow=never -c protocol.file.allow=never` in `envForRemoteOperation`/`updateSubmodulesAfterOperation` for any submodule/clone/fetch operation performed against a repository whose content (i.e., `.gitmodules`) is not already fully trusted, rather than relying implicitly on the bundled Git binary's compiled-in defaults. Audit every call site of `allowFileProtocol: true` to confirm it is never reachable from an untrusted/attacker-supplied repository or URL.

### Proof of Concept
Not independently confirmed end-to-end due to inability to inspect the exact bundled Git binary's default protocol allowlist and every call site passing `allowFileProtocol`. Conceptually: (1) attacker publishes a public repo whose `.gitmodules` defines a submodule URL using `ext::sh -c 'touch /tmp/pwned'` or a `file://` path pointing outside the intended clone target; (2) victim opens the repo via a `x-github-client://openrepo/...` deep link or clones it directly in Desktop, which runs `clone --recursive` [3](#0-2) , or a later operation calls `updateSubmodulesAfterOperation` with `allowFileProtocol: true` [2](#0-1) ; (3) absent an explicit deny-list/allow-list override, submodule URL handling falls through to Git's compiled-in defaults with no Desktop-level backstop.

**Uncertainty statement:** I was unable to verify (a) the exact protocol-allow defaults compiled into the `dugite`-bundled Git binary, and (b) every call site of `updateSubmodulesAfterOperation` to determine whether `allowFileProtocol: true` is ever passed for an untrusted repository. This finding should be treated as a plausible bug-class analog for a background Devin agent to confirm or refute, not a fully proven vulnerability.
