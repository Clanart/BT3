## Finding

### Title
Silent, unconfirmed rewrite of `origin` remote URL from GitHub API data enables repo-name-squatting hijack of pushes/fetches - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
The report's broken invariant is "state used to authorize/execute an action is replaced by attacker-controlled data between the time the user validated it and the time it is used." In Beedle, the lender changes `pool.auctionLength` after the borrower's expectations. The GitHub Desktop analog is `updateRemoteUrl`, which silently rewrites the `origin` git remote's URL based on data returned by the GitHub API for the repo owner/name pair, with no user confirmation — unlike the equivalent `upstream` remote change, which explicitly prompts the user via a dialog.

### Finding Description
When Desktop periodically refreshes a repository's associated GitHub metadata, `repositoryWithRefreshedGitHubRepository` calls `api.fetchRepository(owner, name)` using the owner/name derived from the *existing* `origin` remote URL, then passes the API's response straight into `updateRemoteUrl`: [1](#0-0) 

`updateRemoteUrl` compares the previously known clone URL to the new one and, if the previous state matched (i.e., the user never manually edited the remote) and the protocol is unchanged, it silently calls `gitStore.setRemoteURL` with whatever `clone_url` the API returned — no confirmation, no diff shown to the user: [2](#0-1) 

The owner/name pair used for the API lookup is derived purely from parsing the current remote URL string: [3](#0-2) 

This is the classic GitHub "repojacking" primitive: if the original `owner/name` GitHub identity behind the remote becomes available again (e.g., an org/user is renamed or deleted, or a repo is deleted/renamed and the old slug is reclaimed), an attacker can register a new repository under that exact `owner/name`. GitHub's `/repos/{owner}/{name}` API is a path-based lookup, so `api.fetchRepository(owner, name)` — called with the *stale* owner/name Desktop still has cached — will return the attacker's new repository object, whose `clone_url` field is fully attacker-controlled.

Contrast this with the analogous "the remote may need updating" flow for the `upstream` remote, which explicitly surfaces a dialog and requires the user to click "Update": [4](#0-3) 

No equivalent confirmation exists for the `origin` remote change performed by `updateRemoteUrl` — it's applied unconditionally as soon as the guard conditions match, which is exactly the "sandwich" gap: the user validated/trusted the repository under its original identity, but the identity backing that remote is silently swapped by data the attacker now controls.

### Impact Explanation
Once `origin`'s URL is silently repointed to the attacker's repository:
- The user's next `git push` sends their (potentially private, proprietary) commits/branches to the attacker-controlled repository, exfiltrating source code — this is "silent corruption of what the user commits or pushes."
- The user's next `git fetch`/`git pull` merges attacker-controlled history/code into the user's local repository under the guise of the "same" project, since Desktop shows no warning that the remote changed.
- Because the hostname stays `github.com`, credential helpers still authenticate normally, so the attack is transparent to the user — there is no broken-lock/HTTPS-cert cue.

### Likelihood Explanation
Exploitation is fully unprivileged from the attacker's perspective: it requires only the ability to claim a `github.com/{owner}/{name}` slug that used to point to the victim's repository (e.g., after an org rename, ownership transfer, or repo deletion) — the same class of prerequisite as well-documented "repo-jacking"/dependency-confusion issues, not local access, malware, or leaked credentials. It also does not require the victim to take any unusual action: the metadata refresh path runs automatically during normal periodic background refresh (`repositoryWithRefreshedGitHubRepository`), and the guard conditions (`protocolsMatch`, `remoteUrlUnchanged`, `!urlsMatch`) are trivially satisfiable whenever the old slug is squatted with a same-protocol clone URL.

### Recommendation
- Never silently overwrite `origin`'s remote URL from asynchronous API refresh data. At minimum, surface a confirmation dialog identical in spirit to `UpstreamAlreadyExists`, showing the old and new URL and requiring explicit user approval before calling `setRemoteURL`.
- Additionally, verify repository identity continuity using a stable identifier (e.g., the numeric GitHub repository `id`) rather than only reusing the owner/name pair to re-query the API — if the `id` returned for the same `owner/name` differs from the previously stored `gitHubRepository.dbID`/API id, treat it as a different repository and refuse to auto-update the remote.

### Proof of Concept
1. Victim adds `https://github.com/alice/project` as `origin` in Desktop; Desktop stores `gitHubRepository.cloneURL = https://github.com/alice/project`.
2. `alice` renames her account or deletes/renames `project` on GitHub, causing `alice/project` to expire/free up.
3. Attacker registers `github.com/alice` (or creates `project` under a squattable name) and creates a new public/private repo at `alice/project`, e.g., with `clone_url: https://github.com/attacker-controlled-mirror/project`. (`owner`/`name` fields returned by `/repos/alice/project` now belong to attacker's repo.)
4. Desktop's periodic background refresh calls `repositoryWithRefreshedGitHubRepository` → `matchGitHubRepository` (still derives `alice/project` from the stale remote) → `api.fetchRepository('alice', 'project')`, which now returns the attacker's `apiRepo` object: [5](#0-4) 
5. `updateRemoteUrl` finds `protocolsMatch = true`, `remoteUrlUnchanged = true` (matches the old cached cloneURL), `urlsMatch = false` (attacker's `clone_url` differs) and calls `gitStore.setRemoteURL('origin', attackerCloneUrl)` with no prompt: [6](#0-5) 
6. The victim's next push/fetch silently targets the attacker's repository.

  private async matchGitHubRepository(
    repository: Repository
  ): Promise<IMatchedGitHubRepository | null> {
    const gitStore = this.gitStoreCache.get(repository)

    if (!gitStore.defaultRemote) {
      await gitStore.loadRemotes()
    }

    const remote = gitStore.defaultRemote
    return remote !== null
      ? matchGitHubRepository(this.accounts, remote.url)
      : null
  }
