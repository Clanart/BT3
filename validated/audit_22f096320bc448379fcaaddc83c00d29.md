### Title
`git submodule update` re-enables `protocol.file.allow=always`, letting a malicious submodule URL read files outside the repository during checkout - ([File: app/src/lib/git/submodule.ts])

### Summary
Similar to the Dahlia bug — where a security-relevant check (`calcMaxBorrowAssets`) was evaluated against stale state because an update (`_accrueMarketInterest`) was skipped — GitHub Desktop's checkout flow can skip a Git hardening default (`protocol.file.allow`) that exists specifically to stop untrusted, attacker-controlled `.gitmodules` content from reaching the filesystem. The corrupted invariant here is "submodule URLs from an untrusted repo must never be resolved with `file://`/`ext::` semantics unless the user explicitly opted in," and Desktop's checkout path can silently override that invariant with `protocol.file.allow=always`.

### Finding Description
`updateSubmodulesAfterOperation` builds the argument list for `git submodule update --init --recursive` and conditionally prepends `-c protocol.file.allow=always` based on the `allowFileProtocol` flag: [1](#0-0) 

`checkoutBranch` forwards its own `allowFileProtocol` parameter (default `false`) straight into this call: [2](#0-1) 

Git upstream disabled `file://`/`ext::`-based submodule URLs by default (the fix that shipped after CVE‑2022‑39253) precisely because a `.gitmodules` file — which is ordinary tracked content that an attacker fully controls in any repository they can get a victim to clone or fetch — can point a submodule at `file:///` or `ext::sh -c ...` to read arbitrary local files or execute commands during `submodule update --init`. Desktop's `allowFileProtocol` flag exists to punch a hole through that protection, and the unit test suite shows it being passed as `true` for the exact scenario of checking out a branch that introduces a submodule: [3](#0-2) 

The unresolved question — and the reason this can't be stated with full certainty as an exploitable production path — is which caller(s) in `app-store.ts`/`dispatcher.ts` invoke `checkoutBranch`/`_checkoutBranch` with `allowFileProtocol: true` for a real (non-test) checkout of a branch from a remote/attacker-controlled repository, versus only from local, same-machine test fixtures. I was not able to fully trace every call site of `checkoutBranch(...)` within the size limits of the code index to confirm whether `allowFileProtocol` is ever set to `true` in response to checking out a branch that originates from a remote fetch (e.g., `pr/<n>` fork checkouts, `open-repository-from-url` deep-link flows, or `openBranchNameFromUrl`/`openPullRequestFromUrl` in `dispatcher.ts`, which do call `checkoutLocalBranch`/`_checkoutPullRequest` after a fetch of attacker-supplied content): [4](#0-3) [5](#0-4) 

### Impact Explanation
If `allowFileProtocol: true` is (or can be) reached for a checkout of a branch/PR fetched from an attacker-influenced remote (a forked PR, a deep-linked "Open in Desktop" URL, or a cloned repo), a `.gitmodules` entry pointing at `file:///<absolute path>` or an `ext::` helper would let `git submodule update --init` read arbitrary files on the victim's machine or execute an arbitrary command, entirely outside the boundaries of the checked-out repository — matching the "file read/write outside the repo" / "code execution" impact classes called out as valid.

### Likelihood Explanation
Likelihood is contingent on the specific call sites that pass `true` for `allowFileProtocol` for non-local checkouts; this is the reintroduction of a default Git chose to disable specifically because `.gitmodules` is untrusted, attacker-controlled data in exactly the scenarios Desktop supports (opening PRs from forks, "Open in Desktop" deep links, cloning arbitrary URLs). Because I could not exhaustively confirm every production call site that sets this flag to `true` (index size limits prevented a complete trace of all `checkoutBranch`/`_checkoutBranch` callers), this should be treated as a **strong candidate requiring verification** rather than a confirmed, fully-traced vulnerability.

### Recommendation
- Audit every call site that passes `allowFileProtocol: true` into `checkoutBranch`/`updateSubmodulesAfterOperation` and ensure it is never set for branches/commits/PRs originating from a remote/fork/deep-link that the user did not explicitly and knowingly trust.
- Prefer leaving `protocol.file.allow` at Git's hardened default and only opting in per-submodule after explicit user confirmation, not globally for the whole `submodule update --init --recursive` invocation.
- Add a regression test asserting that checking out a branch fetched from an untrusted remote (PR/fork/deep link flows) never sets `protocol.file.allow=always`.

### Proof of Concept
1. Attacker creates a public repository with a branch containing a `.gitmodules` file such as:
   ```
   [submodule "evil"]
       path = evil
       url = file:///C:/Users/victim/AppData/Roaming/GitHub Desktop/... (or ext::sh -c 'calc.exe')
   ```
2. Attacker gets the victim to open this via a supported untrusted-input path (fork PR checkout, `x-github-client://openRepo/...?branch=...` deep link, or "Clone in Desktop").
3. If the branch-checkout code path that runs for this scenario invokes `checkoutBranch(..., allowFileProtocol: true)` (as exercised by the test at `app/test/unit/git/checkout-test.ts:150-167`), `updateSubmodulesAfterOperation` executes `git -c protocol.file.allow=always submodule update --init --recursive`, resolving the malicious submodule URL and reading/exfiltrating data or executing the `ext::` command outside the intended repository sandbox.

export async function checkoutBranch(
  repository: Repository,
  branch: Branch,
  currentRemote: IRemote | null,
  progressCallback?: ProgressCallback,
  allowFileProtocol: boolean = false
): Promise<true> {
  const title = `Checking out branch ${branch.name}`
  const opts = await getCheckoutOpts(
    repository,
    title,
    branch.name,
    currentRemote,
    progressCallback
      ? clampProgress(0, CheckoutStepWeight, progressCallback)
      : undefined,
    `Switching to ${__DARWIN__ ? 'Branch' : 'branch'}`
  )

  const baseArgs = getCheckoutArgs(progressCallback)
  const args = [...baseArgs, ...(await getBranchCheckoutArgs(branch))]

  await git(args, repository.path, 'checkoutBranch', opts)

  // Update submodules after checkout
  await updateSubmodulesAfterOperation(
    repository,
    currentRemote,
    progressCallback
      ? clampProgress<ICheckoutProgress>(
          CheckoutStepWeight,
          1,
          progressCallback
        )
      : undefined,
    'checkout',
    title,
    branch.name,
    allowFileProtocol
  )

  private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }
