### Title
DID recovery-list ("backup_ids") privileges cannot be cleared on transfer, letting a previous owner retain recovery control - (File: `chia/wallet/did_wallet/did_wallet.py`, `chia/wallet/wallet_request_types.py`)

### Summary
The Registry.sol report describes a pattern where a privileged actor (`onlyProfileOwner`) can grant itself a persistent, lower-tier privilege (`addMembers`) right before giving up ownership, so the escalated privilege survives the ownership transfer. The closest reachable analog in this codebase is the Chia DID (Decentralized Identifier) singleton: the DID owner controls a "recovery list" (`backup_ids` / `num_of_backup_ids_needed`), which is a set of "member" DIDs empowered to co-sign a recovery/ownership-change spend of the DID. `DIDWallet.transfer_did()` [1](#0-0)  always re-curries the new inner puzzle with the **same** `backup_ids`/`num_of_backup_ids_needed` taken from `self.did_info`, and the public RPC request object `DIDTransferDID` now hard-fails if a caller tries to opt out of carrying recovery info forward: [2](#0-1) 

### Finding Description
`DIDWallet.transfer_did()` builds the new inner puzzle hash for the new owner via `did_wallet_puzzles.get_inner_puzhash_by_p2()`, explicitly reusing `self.did_info.backup_ids` and `self.did_info.num_of_backup_ids_needed` from the outgoing owner's state [3](#0-2) . This is the DID analog of Registry's member list: whoever currently controls the DID (the "owner") can, at any time before transferring it, add DIDs to the recovery list (backup_ids) — those DIDs function like privileged "members" able to later co-sign a recovery spend that overrides the current inner puzzle owner key.

The CLI even exposes a `reset_recovery` flag intended to let a transferring owner clear this list [4](#0-3) , which is wired through `transfer_did()` in `chia/cmds/wallet_funcs.py` as `with_recovery=not self.reset_recovery` [5](#0-4) . However, the underlying RPC request type `DIDTransferDID` now unconditionally rejects `with_recovery_info=False` in `__post_init__`, raising `ValueError("Recovery related options are no longer supported. \`with_recovery\` must always be true.")` [6](#0-5) . This means the "reset recovery" escape hatch is non-functional at the RPC boundary: any attempt to transfer a DID while clearing the recovery list fails, so `WalletRpcApi.did_transfer_did()` [7](#0-6)  and `DIDWallet.transfer_did()` always carry the outgoing owner's recovery list into the new owner's DID puzzle.

The consequence mirrors the Registry.sol bug exactly: an owner who is about to transfer a DID (e.g., selling it, or handing it to someone else for a new purpose) can, right before the transfer, add their own address or a colluding DID as a `backup_id`. Because recovery-list clearing is blocked, the new owner inherits a DID whose recovery co-signers still include the previous owner's chosen DID(s), which retain the ability to participate in a future recovery spend and potentially redirect/recover the singleton's control away from the new owner, without the new owner's consent or knowledge.

### Impact Explanation
DIDs are used as an authority/identity anchor throughout the wallet stack — as NFT ownership anchors, as VC (Verified Credential) `proof_provider`s that gate CR-CAT approvals (see `authorized_providers` in `chia/wallet/vc_wallet/cr_outer_puzzle.py` and `VCWallet.revoke_vc()` [8](#0-7) ), and generally as a persistent on-chain identity. A recovery list that cannot be reset on transfer means privileges (recovery co-signer rights) an old owner planted persist indefinitely across ownership changes, letting a former owner (or their designated ally) retain unauthorized influence/control over a DID singleton after it has ostensibly been sold or handed off — a concrete unauthorized-coin-control/identity-forging risk consistent with the report's "escalated privileges after removal" pattern.

### Likelihood Explanation
Medium likelihood: any DID owner can trivially add backup ids to their own DID at will before initiating a transfer (this is a normal, permissionless wallet operation, no protocol-level restriction), and the RPC/CLI path for clearing the list before/at transfer is explicitly disabled by `DIDTransferDID.__post_init__`. A buyer/new-holder of the DID has no visibility forcing function requiring them to check/clear the recovery list themselves unless they know to do so, and the current code path structurally prevents doing it through the sanctioned "reset" flag.

### Recommendation
Restore (or fix) the ability to clear the recovery list (`backup_ids`/`num_of_backup_ids_needed`) as part of `transfer_did`, rather than unconditionally rejecting `with_recovery_info=False` in `DIDTransferDID.__post_init__`. At minimum, surface the recovery list state to the recipient/new owner prior to accepting a transferred DID (e.g., via `did_get_info`) and/or require an explicit reset spend when a DID changes p2 ownership, so previous-owner-controlled backup ids cannot silently persist across an ownership change.

### Proof of Concept
1. Owner A creates a DID wallet and, prior to transfer, calls `did_update_recovery_ids` (or equivalent) to add a backup DID (their own alt DID, or a colluding party's DID) to `backup_ids` with `num_of_backup_ids_needed = 1`.
2. Owner A calls `did_transfer_did` to transfer the DID to Owner B, attempting `reset_recovery=True` to strip the backup list.
3. `DIDTransferDID.__post_init__` raises `ValueError` because `with_recovery_info` is forced to always be `True` [6](#0-5)  — the reset path is unreachable, so the transfer (if it proceeds without reset) preserves the original `backup_ids`/`num_of_backup_ids_needed` unchanged, as coded in `transfer_did()` [3](#0-2) .
4. Owner B now controls the DID's p2 key, but Owner A's planted backup DID remains a valid recovery co-signer able to participate in a future recovery spend against Owner B's will.
