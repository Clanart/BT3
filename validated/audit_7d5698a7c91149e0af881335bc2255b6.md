### Title
Partial-fill escrow rounds to zero, causing solvers to lose their input-token compensation - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents._fillSameChain` computes the escrow released to a solver on a non-terminal partial fill with `(order.inputs[i].amount * fillAmount) / totalRequired`. When `fillAmount` is small relative to `totalRequired` (or `order.inputs[i].amount` is small relative to `totalRequired`), Solidity integer division truncates this to zero. The solver still transfers the full `fillAmount` of output tokens to the beneficiary, but receives `escrowedAmount == 0` in return — an exact analog of the PirexRewards `(rewardState * userRewards) / globalRewards` rounding-to-zero bug, except here it directly costs the solver real, already-transferred tokens instead of merely clearing an accrual.

### Finding Description
In `_fillSameChain` (evm/src/apps/intentsv2/IntrinsicIntents.sol:116-123):

```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [1](#0-0) 

For any *non-final* partial fill (`amountFilled != totalRequired`), the escrow released to the solver uses the ratio formula. Before this, the solver has already unconditionally paid `beneficiaryTotal = fillAmount + beneficiaryShare` in real output tokens to the beneficiary:

```solidity
IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
``` [2](#0-1) 

If `order.inputs[i].amount * fillAmount < totalRequired`, `escrowedAmount` truncates to `0`. This zero amount is passed to `_withdraw`, which silently skips it:

```solidity
uint256 amount = body.tokens[i].amount;
if (amount == 0) continue;
``` [3](#0-2) 

Because `amount == 0` short-circuits before `_orders[commitment][token]` is decremented, the un-released escrow silently stays in `_orders`. It is not credited to the solver that "earned" it via that fill — it is later swept in bulk by whichever solver happens to complete the order (`amountFilled == totalRequired` branch, which grabs the *entire remaining* `_orders[commitment][token]` balance rather than a proportional share). This is functionally identical to PirexRewards: a participant whose share is too small relative to the total is entitled to a nonzero amount, the ratio math rounds it to zero, and the "reward" (here, escrow) intended for that participant is siloed away and later captured by someone else.

### Impact Explanation
An unprivileged solver who performs a legitimate, non-terminal partial fill of an order with a `fillAmount` small enough to trigger the rounding truncation pays real ERC20/native output tokens to the order's beneficiary and receives zero input-token compensation for that fill — a direct, unrecoverable loss of funds for that solver. The forfeited escrow is not burned or refunded to the original order creator; it remains claimable in full by whichever address happens to complete the order later (`amountFilled == totalRequired`), since that branch releases the entire live `_orders[...]` balance rather than the caller's proportional share. This violates the "bridged assets/escrow ... must move exactly once and only to the rightful beneficiary and amount" invariant: escrow originally owed to the shortchanged solver ends up transferred to a different, later solver instead.

### Likelihood Explanation
`fillOrder` (which routes into `_fillSameChain`) is a fully public, unprivileged entrypoint — any address can act as a solver and choose an arbitrary `fillAmount` for a partial fill. Orders with output assets that have low decimals relative to the input token, or orders where a solver naturally wants to fill a small slice, easily produce `order.inputs[i].amount * fillAmount < totalRequired`, especially since inputs/outputs are independently priced token pairs (not forced 1:1). No relayer, prover, admin, or governance action is required — only two independent solver calls against the same order commitment.

### Recommendation
- Reject or explicitly refund fills whose computed `escrowedAmount` truncates to zero (revert with a dedicated error, mirroring the "fallback logic if amount == 0" mitigation from the referenced report), rather than silently discarding the entitled escrow.
- Alternatively, track escrow release with a running remainder (e.g. `escrowedAmount = (order.inputs[i].amount * amountFilled) / totalRequired - alreadyReleased`) so each fill's true proportional share is computed cumulatively and rounding error cannot be "swept" by a later, unrelated filler.
- Ensure `_orders[commitment][token]` is decremented in lockstep with `_partialFills`, so unreleased dust cannot be captured wholesale by whichever address happens to finalize the order.

### Proof of Concept
1. Order requires `totalRequired = 1_000_000` units of output token B, escrowing `order.inputs[0].amount = 999` units of input token A (a legitimate, low-value/low-decimals input relative to output).
2. Solver S1 (attacker or ordinary solver) calls `fillOrder` with `solverAmount = 1000` (a small, valid partial fill: `remaining = 1_000_000 > 1000`, so `fillAmount = 1000`).
3. `escrowedAmount = (999 * 1000) / 1_000_000 = 0` (integer truncation) — see evm/src/apps/intentsv2/IntrinsicIntents.sol:120.
4. S1 has already transferred `1000` units of token B to the beneficiary via `safeTransferFrom` (line 107), but `_withdraw` skips the zero-amount token entry (IntentsBase.sol:398), so S1 receives 0 units of token A.
5. `_orders[commitment][tokenA]` is unchanged (still holds the full 999 units) because the decrement at IntentsBase.sol:403 never runs for the zero amount.
6. Solver S2 later completes the order with `fillAmount = 999_000`, triggering `amountFilled == totalRequired`, and receives `escrowedAmount = _orders[commitment][tokenA]` = the **full** 999 units of token A — including the 0 that should have gone to S1.
7. Net result: S1 paid 1000 units of token B and received nothing; S2 received all 999 units of token A for providing only 99.9% of the output, capturing the value S1 was owed.
