### Title
Unbounded allocation on untrusted length prefix in `ReceivedOutput::read` enables memory exhaustion DoS - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
`ReceivedOutput::read` deserializes a `TxOut` via `bitcoin::consensus::encode::Decodable::consensus_decode` directly from a caller-supplied `Read` stream with no size bound. `TxOut`'s consensus encoding embeds a `ScriptBuf` whose compact-size (VarInt) length prefix controls a `vec![0; len]` allocation in rust-bitcoin's `ScriptBuf::consensus_decode`. An attacker who controls the bytes being deserialized can claim a script_pubkey length near `u64::MAX` in ~9 bytes, forcing a multi-gigabyte allocation that aborts the process — the same memory-exhaustion class as CVE-2023-6337, where a length-prefixed structure is mapped to memory before validation.

### Finding Description
`ReceivedOutput::read` reads a scalar offset, then performs two `consensus_decode` calls over a zero-capacity `BufReader` wrapping the untrusted reader:

```rust
// networks/bitcoin/src/wallet/mod.rs
let mut buf_r = BufReader::with_capacity(0, r);
output = TxOut::consensus_decode(&mut buf_r)
  .map_err(|_| io::Error::other("invalid TxOut"))?;
```

There is no length check, chunked read, or size cap anywhere in this path. Bitcoin consensus decoding trusts the VarInt length field of the embedded `script_pubkey` and allocates a buffer of the claimed size before attempting to fill it (`read_exact` fails only *after* the allocation succeeds, and on most platforms the `vec![0; len]` allocation itself aborts on failure rather than returning an error). Thus a byte stream as small as ~40 bytes (`offset` + VarInt + `value`) can trigger an allocation of up to ~18 exabytes, exhausting host memory and crashing the process.

By contrast, hardened parsers in the same codebase acknowledge this exact bug class — e.g., `coordinator/src/p2p.rs` caps messages at `MAX_LIBP2P_REQRES_MESSAGE_SIZE` before allocating, and `networks/ethereum/src/machine.rs` reads a `u32` length in 1 KB chunks specifically commenting "A valid DoS would be to claim a 4 GB data is present for only 4 bytes." `ReceivedOutput::read` (and the sibling `Transaction::read` paths) lack any equivalent mitigation.

### Impact Explanation
An unprivileged party who can cause serialized `ReceivedOutput` bytes of their choosing to be fed to `ReceivedOutput::read` — e.g., malformed scanner/DB output round-trips, signed preprocessor/share payloads, or any RPC/network path that round-trips these structures — can reliably crash the validator/processor node with a tiny payload. Repeated crashes of threshold participants stall DKG ceremonies and signing rounds (liveness denial across the network), and since the failure is an allocation abort rather than a recoverable `io::Error`, no error handling can catch it. This is a host-level memory exhaustion DoS matching the severity profile (AV:N/AC:L/PR:N → A:H) of the reference advisory.

### Likelihood Explanation
The trigger requires only that attacker-influenced bytes reach `ReceivedOutput::read` (or the equivalent `consensus_decode` paths on `Transaction`/`Block` scanned from Bitcoin data). `scan_block`/`scan_transaction` themselves take already-parsed `bitcoin` types, but any transport, persistence, or message path that serializes `ReceivedOutput` and later re-reads it from a stream an attacker can influence — including adversarial Bitcoin blocks/TXs deserialized elsewhere via `consensus_decode` — reaches the unbounded allocation. The payload cost is tens of bytes; reliability is deterministic on systems where oversized allocations abort.

### Recommendation
Do not pass untrusted streams directly to `consensus_decode` for allocation-heavy types. Options:
- Deserialize `TxOut`/`OutPoint` from a bounded buffer: read a `u32`/`u64` length prefix in `ReceivedOutput::write`/`read`, cap it at a sane maximum (e.g., the `TRANSACTION_SIZE_LIMIT`-style constant or a fixed few-KB bound for `TxOut` + `OutPoint`), reject larger claims before allocating, and only then call `consensus_decode` on a `&[u8]` slice.
- Alternatively use `consensus_decode_from_finite_reader` / a `Take`-limited reader combined with a pre-checked length, mirroring the chunked-read pattern already used in `networks/ethereum/src/machine.rs`.
- Apply the same cap to every other `consensus_decode` site reachable from untrusted bytes in `networks/bitcoin`.

### Proof of Concept
Conceptual byte stream fed to `ReceivedOutput::read` on `Secp256k1`:

```rust
// 32-byte scalar offset (any valid encoding), then TxOut:
//   value: 8 bytes
//   script_pubkey VarInt: 0xff || u64::MAX (9 bytes claiming ~18 EB)
let mut payload = vec![0u8; 32];
payload.extend(&0u64.to_le_bytes());       // TxOut.value
payload.push(0xff);                        // VarInt marker for u64
payload.extend(&u64::MAX.to_le_bytes());   // claimed script_pubkey length
// No further bytes needed — the vec![0; u64::MAX] allocation aborts
let _ = ReceivedOutput::read(&mut &payload[..]); // OOM/abort before read_exact fails
```

The process is killed by the allocator before `consensus_decode` can notice the data is absent, yielding denial of service from a ~50-byte input.
