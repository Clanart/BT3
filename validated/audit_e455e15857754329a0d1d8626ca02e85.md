### Title
`SignableTransaction` fee/weight calculation omits the OP_RETURN data output, undercharging the intended fee rate - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
The `SignableTransaction::new` constructor computes the transaction weight, virtual size, `needed_fee`, the minimum-relay-fee check, and the maximum-standard-weight check using `calculate_weight_vbytes`, which reconstructs the transaction from only the payment outputs and an optional change output. The OP_RETURN `data` output — pushed onto `tx_outs` before the weight is computed — is never included in that reconstruction. This mirrors the reported bug class: a value (the true transaction size) is computed by a dedicated mechanism but the actual operation (fee assignment and change sizing) uses a stale/1:1-substituted model of the transaction, so the created transaction pays a lower effective fee rate than requested and can violate policy limits the code believes it enforced.

### Finding Description
In `SignableTransaction::new`, the outputs are assembled as: payment outputs, then an optional OP_RETURN output carrying up to 80 bytes of caller-supplied `data`:

```rust
// networks/bitcoin/src/wallet/send.rs
194|    if let Some(data) = data {
195|      tx_outs.push(TxOut {
196|        value: Amount::ZERO,
197|        script_pubkey: ScriptBuf::new_op_return(
198|          PushBytesBuf::try_from(data) ...
```

The fee and weight are then derived from `calculate_weight_vbytes(tx_ins.len(), payments, None)` and, when change exists, `calculate_weight_vbytes(tx_ins.len(), payments, Some(&change))` — both of which build a scratch `Transaction` containing only the payment outputs and the change output:

```rust
204|    let (mut weight, vbytes) = Self::calculate_weight_vbytes(tx_ins.len(), payments, None);
205|    let mut needed_fee = fee_per_vbyte * vbytes;
...
224|    if let Some(change) = change {
225|      let (weight_with_change, vbytes_with_change) =
226|        Self::calculate_weight_vbytes(tx_ins.len(), payments, Some(&change));
227|      let fee_with_change = fee_per_vbyte * vbytes_with_change;
```

Neither call accounts for the OP_RETURN output already in `tx_outs`. Consequently:

1. `needed_fee` (what the change calculation reserves and what `needed_fee()` reports) is `fee_per_vbyte` times a vsize that excludes the ~10–90+ byte OP_RETURN output. The change output is set to `input_sat - payment_sat - fee_with_change`, so the *actual* fee paid equals `fee_with_change` while the real transaction is larger — the realized fee rate is strictly below `fee_per_vbyte`.
2. The `TooLowFee` check at line 211 compares `needed_fee` against `DEFAULT_MIN_RELAY_TX_FEE * vbytes / 1000` using the same understated `vbytes`. A caller specifying `fee_per_vbyte` at the relay minimum (e.g., 1 sat/vbyte) passes the check yet produces a transaction whose true fee rate is below the minimum, so it will not relay.
3. The `MAX_STANDARD_TX_WEIGHT` check at line 241 uses `weight`/`weight_with_change`, both computed without the data output, so a transaction slightly above the standard weight limit can pass the check and be produced as a non-relayable transaction.

The `data` argument and `payments` are untrusted, attacker-influencable inputs (anyone requesting a Serai outbound Bitcoin transaction supplies the destination, amount, and can trigger metadata payloads), making this reachable from public inputs.

### Impact Explanation
Underestimated fee accounting causes two concrete harms:

- **Transactions that fail to relay**: when `fee_per_vbyte` is at/near the minimum relay fee, the OP_RETURN omission makes the realized fee rate fall below `DEFAULT_MIN_RELAY_TX_FEE`, producing a signed transaction the network rejects — outputs committed to it are effectively unspendable until a replacement is constructed.
- **Silent fee-rate deviation**: the protocol believes it is paying `fee_per_vbyte` sat/vbyte but pays strictly less (difference scales with data length, up to ~90 vbytes of omission). Combined with the `MAX_STANDARD_TX_WEIGHT` bypass, the constructed transaction can exceed consensus-adjacent policy limits the code explicitly checks.

This is a real, deterministic miscalculation on Serai's own code, not an integrator misuse.

### Likelihood Explanation
The `data: Option<Vec<u8>>` parameter is a public input to `SignableTransaction::new`; any transaction built with non-empty data triggers the miscalculation every time — no race, no collusion, no malicious validator required. Severity is bounded because the absolute error is capped at the serialized size of one ≤80-byte OP_RETURN output (~92 vbytes worst case) and only matters when fee rates or weight are near their limits, placing this at Medium.

### Recommendation
Include the OP_RETURN output in the weight/vbytes estimation. The cleanest fix is to build the scratch transaction inside `calculate_weight_vbytes` from the final `tx_outs` vector (payments + data + change), or to pass `data`'s serialized OP_RETURN output into the function so both the no-change and with-change estimates reflect the true transaction. Alternatively, construct the scratch `Transaction` directly from `tx_ins`/`tx_outs` as finally assembled, and recompute `needed_fee` and the `TooLowFee`/`TooLargeTransaction` checks against that.

### Proof of Concept
1. Call `SignableTransaction::new(inputs, &payments, Some(change), Some(vec![0u8; 80]), fee_per_vbyte)` where `fee_per_vbyte == 1` (the relay minimum in sat/vbyte terms the check tests against).
2. The `TooLowFee` check at `send.rs:211` uses `vbytes` from `calculate_weight_vbytes`, which built a transaction containing only the payment outputs — the OP_RETURN output added at `send.rs:195` is absent.
3. The resulting `SignableTransaction.tx` contains the OP_RETURN output, so its actual vsize exceeds `vbytes` by roughly 90 vbytes; `fee() = needed_fee = 1 * vbytes`, so the realized fee rate is `vbytes / actual_vsize` sat/vbyte < 1 — below `DEFAULT_MIN_RELAY_TX_FEE`.
4. `send_raw_transaction` rejects the transaction (insufficient feerate / non-standard), demonstrating the inconsistency between the fee/weight the code computed and the transaction it actually produced — the same class of flaw as minting/burning 1:1 while a computed conversion factor is ignored.
