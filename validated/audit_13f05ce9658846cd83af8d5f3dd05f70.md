## Analysis

The 0x report's core broken invariant is: **a shared execution surface accepts arbitrary externally-supplied calls once a superficial gate passes, with no allowlist on what can be called or by whom — letting a party siphon value that happens to be sitting in that shared surface.**

The direct Hyperbridge analog is `CallDispatcher.dispatch()`, the shared singleton contract used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`/`IntentsBase` to execute swap/composability calldata during cross-chain and same-chain flows. [1](#0-0) 

### Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to drain residual token/ETH dust left by cross-chain calldata execution - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is `external` with no caller restriction (no `onlyGateway`/`onlyHFT` modifier), and it forwards arbitrary `Call{to, value, data}` entries to any contract with code. [2](#0-1)  The contract is deployed once per chain and shared across `HyperFungibleToken.onAccept`, `WrappedHyperFungibleToken.onAccept`, and `IntentsBase._execute`/`IntentGatewayV2.placeOrder` predispatch/postdispatch flows, all of which route bridged assets or swap outputs through it. [3](#0-2) [4](#0-3) 

### Finding Description
Each integration only sweeps back the specific token set it knows about after calling `dispatch()`:
- `IntentsBase._execute` sweeps only `order.output.assets[0..outputsLen)` balances left on the dispatcher after running `order.output.call`. [5](#0-4) 
- The Tron `IntentGatewayV2` predispatch path sweeps only `order.inputs[]` tokens after running `order.predispatch.call`. [6](#0-5) 

Any calldata (swap paths, multi-hop routes, intermediate tokens, leftover ETH from `swapETHForExactTokens`-style calls, failed/partial approvals, etc.) that leaves a balance in the dispatcher **outside the enumerated asset list** is never swept and persists indefinitely in the CallDispatcher's storage/balance. Because `dispatch()` has no access control and no `msg.sender` check, this leftover balance is a public bounty: any unprivileged address can call `CallDispatcher.dispatch()` directly with a `Call` that transfers out that ERC20/ETH balance to themselves, since the only check performed is `extcodesize(to) != 0`. [7](#0-6) 

This mirrors the 0x issue precisely: the "gate" (checking the target has code, or checking the transformer selector) is not a security boundary — once past it, the call executes with full trust, and because the surface is shared across many unrelated operations (many users' orders/transfers reusing one dispatcher), any dust or transient balance becomes drainable by an unrelated third party with no signature, no relayer, no proof, and no privileged role required.

### Impact Explanation
Funds temporarily or permanently resident in the shared `CallDispatcher` (dust from swaps/predispatch/postdispatch calldata across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`) can be stolen by any unprivileged actor who simply calls `dispatch()` before the legitimate sweep occurs or for token types the sweep logic doesn't enumerate. This is a direct "stealing/loss of funds" and "unauthorized execution" impact against a production contract that custodies bridged and escrowed assets.

### Likelihood Explanation
Likelihood is high for any deployment where calldata execution (Uniswap-style swaps, multi-hop routes) is used, since intermediate/leftover balances in tokens not part of the declared `assets`/`inputs` array are a normal byproduct of swap slippage, multi-token routes, or reverted partial legs — and the dispatcher's `dispatch()` requires no permission to call. No malicious relayer, prover, or admin is needed — a fully public, unprivileged actor watching the dispatcher's on-chain balance can act.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allowlist (the registered HFT/WrappedHFT/IntentGateway contracts), or make the dispatcher ephemeral per-call (e.g., deploy a fresh minimal-proxy dispatcher instance per execution via CREATE2 and self-destruct/expect zero residual balance at the end), and additionally have all sweep logic capture and return *all* non-zero balances on the dispatcher (not just the declared asset list) at the end of every `_execute`/predispatch flow so nothing is left behind between transactions.

### Proof of Concept
1. A solver fills a cross-chain order whose `order.output.call` swaps output token A for token B via a DEX router, but the route also produces a small residual amount of an intermediate token C (or leftover native ETH from a `swapETHForExactTokens` refund) that is not part of `order.output.assets`.
2. `IntentsBase._execute` only builds `sweepCalls` for the declared `outputsLen` tokens, so token C's balance remains on the `CallDispatcher` after the transaction completes. [5](#0-4) 
3. Anyone (no relationship to the order, no signature) calls `CallDispatcher.dispatch(abi.encode([Call({to: tokenC, value:0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly. [2](#0-1) 
4. The call succeeds because `dispatch()` performs no caller check and `tokenC` has code, transferring the dust to the attacker with zero authorization.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
