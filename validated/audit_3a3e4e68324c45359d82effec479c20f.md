## Title
Data Layer wallet trusts unverified hint memo for singleton root/inner-puzzle-hash instead of deriving it from the actual committed puzzle hash - (File: `chia/data_layer/data_layer_wallet.py`)

### Summary
This is the same bug class as the ZkEvmV2 report: two related pieces of state — an actual on-chain committed value and an auxiliary value that is supposed to correspond to it — are accepted without cross-validating that they are consistent. In Chia's DataLayer wallet, `singleton_removed()` extracts the new singleton's `full_puzzle_hash` directly from the `CREATE_COIN` condition (the value actually committed on-chain), but pulls `root` and `inner_puzzle_hash` from the CREATE_COIN hint/memo (`condition[3]`) without ever checking that `create_host_fullpuz(inner_puzzle_hash, root, launcher_id)` actually hashes to `full_puzzle_hash`.

### Finding Description
`singleton_removed` in `chia/data_layer/data_layer_wallet.py` parses the parent spend's output conditions: [1](#0-0) 

`full_puzzle_hash` (line 829) is the puzzle hash that was actually created by the spend and is what determines the real on-chain singleton identity/puzzle. However `root` and `inner_puzzle_hash` (lines 832-833) come from the hint field of the same CREATE_COIN condition — a value that is *not* enforced by the singleton puzzle itself to correspond to the puzzle hash actually created. The wallet then stores these unchecked values directly into the `SingletonRecord`: [2](#0-1) 

The correct puzzle hash is derived as `create_host_fullpuz(inner_puzzle_hash, root, genesis_id)` via `create_host_layer_puzzle`: [3](#0-2) 

Nowhere in `singleton_removed` is `create_host_fullpuz(inner_puzzle_hash, root, singleton_record.launcher_id).get_tree_hash_precalc(inner_puzzle_hash)` compared against `full_puzzle_hash`. This mirrors the report's root cause precisely: the "shnarf"-equivalent (`full_puzzle_hash`, the value that actually seals the state on-chain) and the "state root hash"-equivalent (`root`/`inner_puzzle_hash`, the value used for downstream DataLayer proof verification, offers, and RPC reporting) are two independently supplied values that are never checked to match.

By contrast, the correctly-guarded path is `create_update_state_spend`, where the wallet itself computes `next_full_puz_hash` from `root_hash`/`new_puz_hash` and puts that into the CREATE_COIN puzzle-hash argument, so self-generated spends are internally consistent: [4](#0-3) 

But `singleton_removed` is the generic sync path used for *any* singleton spend seen on-chain (including spends made by a different owner/tool, or a maliciously crafted DL singleton spend), and it has no equivalent consistency check.

### Impact Explanation
If a singleton owner (or anyone able to produce a DL-singleton-shaped spend recognized by `match_dl_singleton`) creates a child coin whose actual puzzle hash corresponds to root `A`, but whose hint memo advertises a different root `B`, every wallet syncing this spend via `singleton_removed` will record `SingletonRecord.root = B` while the coin's real puzzle hash encodes `A`. This directly desynchronizes the wallet-reported Data Layer root from the actual chain state: `get_root`/`get_proof`/`verify_proof` RPCs will report/verify against the wrong root, `dl_verify_proof_internal` checks are keyed off `inner_puzzle_hash`/`root` supplied by the caller rather than a value cryptographically bound to the record produced here, and downstream consumers (offer construction/verification, `create_update_state_spend`'s "current root" lookups, mirrors/publication logic) can be misled into treating a store as being at a root it is not actually at. This can allow acceptance of stale/forged inclusion proofs or malformed offers, and can desync coin-set/state interpretation between honest wallets that resync independently (since each derives `root` from the same untrusted hint).

### Likelihood Explanation
Reachable purely from an on-chain spend of a DL singleton (a wallet-initiated action, not a validator/farmer-only path) — no special privileges beyond controlling/spending an existing DL singleton (which any store owner or, once take_offer/graftroot mechanics run, an offer counterparty naturally does) are required to produce a hint/puzzle-hash mismatch. The wallet's automatic sync logic (`singleton_removed`, invoked from `wallet_state_manager.py`) processes every matching spend without additional verification, so the mismatch is exploitable whenever a wallet observes such a spend.

### Recommendation
In `singleton_removed`, after extracting `full_puzzle_hash`, `root`, and `inner_puzzle_hash` from the hint, recompute the puzzle hash via `create_host_fullpuz(inner_puzzle_hash, root, singleton_record.launcher_id).get_tree_hash_precalc(inner_puzzle_hash)` and assert equality with `full_puzzle_hash` before constructing `new_singleton`/`SingletonRecord`. If they don't match, treat the hint as invalid/untrusted (log and skip, or fall back to re-deriving state without trusting the hint) rather than persisting an unverified root.

### Proof of Concept
1. Owner of a DL singleton crafts a spend (e.g. custom inner puzzle / solution) that outputs a `CREATE_COIN` condition with `puzzle_hash = full_puzzle_hash_for_root_A` (the real, on-chain puzzle) but a hint/memo `[launcher_id, root_B, inner_puzzle_hash]` where `root_B != root_A`.
2. Broadcast the spend; any full node accepts it since consensus validates the singleton puzzle/puzzle-hash equality, not the hint contents.
3. A syncing wallet observes the spend and calls `singleton_removed`; it derives `new_singleton = Coin(parent_name, full_puzzle_hash_for_root_A, amount)` (correct, matches chain) but stores `SingletonRecord(root=root_B, inner_puzzle_hash=..., lineage_proof=LineageProof(..., create_host_layer_puzzle(inner_puzzle_hash, root_B)..., ...))` — a lineage proof/root that does not correspond to the actual singleton coin's puzzle.
4. Subsequent calls such as `get_root`, `get_proof`, offer creation (`generate_new_reporter`/`create_update_state_spend`), or proof verification against this wallet state now operate on the incorrect root `B`, diverging from the real committed state `A`.

def create_host_fullpuz(innerpuz: Program | bytes32, current_root: bytes32, genesis_id: bytes32) -> Program:
    db_layer = create_host_layer_puzzle(innerpuz, current_root)
    mod_hash = SINGLETON_TOP_LAYER_MOD.get_tree_hash()
    singleton_struct = Program.to((mod_hash, (genesis_id, SINGLETON_LAUNCHER_PUZZLE_HASH)))
    return SINGLETON_TOP_LAYER_MOD.curry(singleton_struct, db_layer)
