## Analysis Summary

The reported `SwapLibrary._swapTokenExactOutput` bug is a case where a function performs partial/irreversible state changes, then signals failure to the caller (return 0) — but the state changes made prior to detecting the failure condition are **not undone**, so the caller believes nothing happened while state was actually mutated.

The closest analog I found in this Cosmos EVM repository is in the IBC ERC20 callback handler, `IBCReceivePacketCallback`, which commits cached EVM state via `writeFn()` **before** performing its final invariant check, and returns an error only *after* the state has already been committed to the real `ctx`. [1](#0-0) 

### Finding Description

In `IBCReceivePacketCallback` (`x/ibc/callbacks/keeper/keeper.go`), the flow is:
1. `k.evmKeeper.CallEVM(...)` is executed against a `cachedCtx` (a `ctx.CacheContext()`) to call `approve(contractAddr, amountInt)` on the ERC20 token, granting the destination callback contract an allowance from the isolated receiver address. [2](#0-1) 
2. `k.evmKeeper.CallEVMWithData(...)` is executed, still on `cachedCtx`, invoking the destination contract with attacker/relayer-supplied `cbData.Calldata` from the packet memo. [3](#0-2) 
3. **`writeFn()` is called, committing all of the above EVM state changes (approval + arbitrary contract call) into the real `ctx`.** [4](#0-3) 
4. **Only after this commit** does the function check the invariant that the receiver's ERC20 balance must be zero (i.e., that the destination contract fully pulled the approved tokens via `transferFrom`). If this check fails, the function returns an error. [5](#0-4) 

This is structurally identical to the `SwapLibrary` bug class: the function returns an error (analogous to "reverting"), giving the impression to the caller that the whole operation failed and can be treated as a no-op, but the state mutations that occurred earlier in the call (the `approve` grant to the callback contract, and any side effects of the attacker-controlled `cbData.Calldata` execution) have already been **irreversibly committed** via `writeFn()`.

Concretely:
- The isolated receiver address now has an outstanding ERC20 `approve` allowance granted to `contractAddr` for `amountInt`, even though the callback is reported as failed.
- Whatever `cbData.Calldata` executed against `contractAddr` (arbitrary calldata chosen by the sender via the packet memo) is fully committed, regardless of whether the final sanity check passes.
- If the destination contract only partially pulls tokens (or does something else with the approval and calldata execution), the residual approval remains valid for the un-pulled amount, and the tokens can be extracted later via that still-valid allowance — after the operation was already reported/acknowledged as failed.

I was not able to fully verify from the indexed code how the outer IBC-go callback middleware (`ProcessCallback` in ibc-go) treats an error returned from this contract keeper method — specifically, whether ibc-go performs its own outer `CacheContext`/rollback around the whole `IBCReceivePacketCallback` invocation such that the `writeFn()`-committed EVM state is itself discarded when an error bubbles up. This is a material open question: if ibc-go's own callback wrapper caches and reverts the entire call on error, this local `writeFn()` before the final check would be non-issue for that path (though it would still be dead code / an ordering bug). Since I could not locate the actual ibc-go `ProcessCallback` call site or its cache-context handling in the indexed code, I could not confirm end-to-end whether this reaches a **Critical**, unauthorized-fund-extraction outcome, or whether it is fully mitigated by an outer rollback layer.

### Impact Explanation (if not mitigated by an outer rollback)

If the outer IBC-go callback machinery does not itself revert `ctx` state on the error returned here, this bug would let an unprivileged IBC packet sender (choosing the `dest_callback` memo and target contract/calldata) leave a stale-but-valid ERC20 `approve` allowance and any calldata side effects committed on-chain, while the operation is reported as failed — enabling later unauthorized extraction of the escrowed/minted ERC20 tokens tied to that isolated receiver address, i.e., unauthorized extraction of token-pair-backed balances.

### Likelihood / Confidence

Given the uncertainty about ibc-go's own middleware-level rollback behavior (which I could not verify in the available index), I cannot confidently assert this reaches the required Critical, reachable-without-outer-mitigation bar.

### Recommendation

- Move the final invariant check (`receiverTokenBalance == 0`) to occur **before** calling `writeFn()`, performing it against `cachedCtx` instead of `ctx`, so that a failing invariant discards all EVM side effects (the `approve` and the arbitrary calldata call) atomically with the rest of the operation.
- Confirm explicitly (via a Devin session with full repo/dependency access, since ibc-go's `callbacks` module source is not fully indexed here) whether `ProcessCallback` in ibc-go wraps this call in its own cache-and-revert boundary; if it does not, the fix above is necessary to prevent state leakage on reported failure.

Because I could not conclusively confirm an unmitigated Critical impact end-to-end within this repository's indexed code (the missing link being ibc-go's own callback processing/rollback semantics, which sits outside what I could inspect), I am not confident enough to assert this as a definitively valid Critical, in-scope finding as required by the strict output gate.
