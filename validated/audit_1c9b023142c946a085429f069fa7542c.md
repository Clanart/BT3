### Title
Out-of-bounds `HashMap` indexing in PedPoP blame handling panics on untrusted participant indexes - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
Analogous to CVE-2017-6415 (a parser crashing on a crafted file's out-of-range reference), `Decryption::decrypt_with_proof` and `BlameMachine::blame_internal` index `HashMap`s with `Participant` indexes that come from an attacker-supplied blame accusation without checking membership. A crafted accusation naming a recipient or sender outside the registered set causes a panic (`HashMap` index operator), crashing the process — a denial of service reachable entirely from attacker-controlled bytes (`EncryptedMessage::read`, `EncryptionKeyProof::read`) and indexes.

### Finding Description
`Decryption::decrypt_with_proof` evaluates `self.enc_keys[&decryptor]` while building the DLEq verification statement, before any bounds check on `decryptor` (encryption.rs:381-390). `enc_keys` only ever contains indexes populated via `Decryption::register`, which are the DKG participant indexes (pedpop/src/lib.rs:351-361).

If a valid `EncryptionKeyProof` is supplied and `decryptor` is in `enc_keys`, execution reaches `BlameMachine::blame_internal`, which computes `self.commitments[&sender]` to build `share_verification_statements` (pedpop/src/lib.rs:596-604). `commitments` contains only real participants (inserted in `verify_r1` / `AdditionalBlameMachine::new`, lib.rs:331-336 and :654-660). `sender`, `recipient`, `msg`, and `proof` are all parameters of the public `BlameMachine::blame` / `AdditionalBlameMachine::blame` APIs (lib.rs:623-632, :674-682), and `msg`/`proof` are raw deserialized structures (`EncryptedMessage::read` at encryption.rs:171-177, `EncryptionKeyProof::read` at encryption.rs:267-269).

An attacker can therefore submit a blame accusation where:

- `recipient` is their own valid participant index (so `enc_keys[&decryptor]` resolves),
- `sender` is any `Participant` not in `commitments` (e.g. `Participant::new(n+1)` or any index that never registered),
- `msg` is an `EncryptedMessage` with a PoP the attacker can legitimately sign (the PoP key is chosen by the sender — the accuser can produce `msg.key = G*k`, `pop` signed by `k`, and a valid `EncryptionKeyProof` DLEq because they know their own `enc_key` and `k`),

and `blame_internal` panics on `self.commitments[&sender]` at lib.rs:599. Alternatively, naming an unregistered `recipient` panics directly on `self.enc_keys[&decryptor]` at encryption.rs:388, before the DLEq is even checked.

Unlike the surrounding `Result`-returning paths (`PedPoPError::MissingParticipant`, `InvalidShare`), this is an unhandled `panic!` via `HashMap`'s `Index` impl — exactly the "missing check → crash on crafted input" shape of the radare2 NULL-deref.

### Impact Explanation
Every honest node that evaluates the blame accusation (`AdditionalBlameMachine::blame` is explicitly designed to let third parties/arbiters evaluate blame, per lib.rs:639-648) panics. In a deployment where the panic handler aborts or the process isn't structured to survive a task panic, a single crafted accusation kills the evaluation — denying the protocol's ability to attribute fault and, depending on the host, halting the node. CVSS-analogous impact: availability loss from a remotely-triggerable crash (Medium, matching the source advisory's DoS-only severity).

### Likelihood Explanation
No threshold cooperation, no leaked keys, no special privileges are needed: the accuser only needs a valid registered encryption key (their own) and the ability to submit a blame statement — an ordinary, public protocol action. Constructing the triggering `msg`/`proof` requires only knowledge of the accuser's own secret key. The panic is deterministic.

Caveat: this finding assumes the caller feeds `blame`/`AdditionalBlameMachine::blame` participant indexes derived from the accusation without pre-filtering them to `1..=n`. The library itself performs no such validation — `AdditionalBlameMachine::new` even documents that usage with unauthenticated data "may cause everything from inaccurate blame to panics" (lib.rs:646-648), but the panic in `blame_internal` occurs for `sender`/`recipient` values even when the *commitments* were fully valid; only the accusation's indexes are bogus.

### Recommendation
Replace the indexing with fallible lookups:

- In `Decryption::decrypt_with_proof` (encryption.rs:388): `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?`.
- In `BlameMachine::blame_internal` (lib.rs:599): `let Some(sender_commitments) = self.commitments.get(&sender) else { return sender };` — an accusation against a non-participant should blame the accuser's claim, i.e. treat it as an invalid accusation rather than crash.
- Optionally validate `sender`/`recipient` against `params.all_participant_indexes()` at the top of `blame`/`AdditionalBlameMachine::blame`.

### Proof of Concept
```rust
// n = 3, t = 2 DKG completes normally; all three participants are in
// `commitments` / `enc_keys`.
// Attacker is a participant (index 2) who builds a blame accusation:

// sender: a Participant that was never registered (e.g. index 200 while n = 3)
let fake_sender = Participant::new(200).unwrap();
// recipient: the attacker themselves (valid, present in enc_keys)

//   key = G * k, pop = SchnorrSignature::sign(k, ..)  -> passes pop.verify

//   dleq = DLEqProof::prove(.., &[G, msg.key], &enc_key_me)  -> verifies
let msg: EncryptedMessage<Ristretto, SecretShare<Fr>> = /* attacker-built */;
let proof: EncryptionKeyProof<Ristretto> = /* attacker-built, verifies */;

// Any node evaluating the accusation:
let faulty = blame_machine.blame(fake_sender, me, msg, proof);
// -> panic at crypto/dkg/pedpop/src/lib.rs:599:
//    self.commitments[&fake_sender]  (key not found)
```

A variant passing `recipient = Participant::new(200)` panics earlier at `crypto/dkg/pedpop/src/encryption.rs:388` on `self.enc_keys[&decryptor]`, requiring only that `msg.pop` verify — no valid DLEq needed.
