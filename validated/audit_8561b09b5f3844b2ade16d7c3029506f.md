### Title
`SchnorrAggregate::verify` accepts a trivially forgeable aggregate when the signer set is empty — zero signatures checked - (File: crypto/schnorr/src/aggregate.rs)

### Summary
`SchnorrAggregate::verify` reduces the half-aggregation check to a single multiexp that must equal the identity. When `keys_and_challenges` is empty and the aggregate contains zero `R` values, the only remaining term is `-s·G`, so any attacker can set `s = 0` and produce an "aggregate signature" that verifies over zero signatures. This is the direct analog of the Kinto `MINUS_ONE_SIGNER` bug: the verification routine has no minimum-signer bound and silently degenerates to checking zero signatures, which it then accepts.

### Finding Description
In `crypto/schnorr/src/aggregate.rs`, `SchnorrAggregate::verify` builds the verification pairs as follows:

- For each `(key, challenge)` it pushes `(z_i, R_i)` and `(z_i * c_i, key_i)` where `z_i = weight(digest)` (lines 138–143).
- It then pushes `(-self.s, C::generator())` and requires `multiexp_vartime(&pairs).is_identity()` (lines 144–145).

The only guard is a length equality check `self.Rs.len() != keys_and_challenges.len()` at line 128. There is no check that either list is non-empty. When both are empty, `pairs` is exactly `[(-s, G)]`, and the verification equation collapses to `-s·G == 0`, which holds for `s = 0`. `SchnorrAggregate::read` (lines 77–88) happily deserializes `len = 0` followed by a zero `s` scalar, so a 5-byte untrusted blob is a valid "signature" for an empty signer set.

This mirrors Problem 1 of the reference report exactly: just as `owners.length - 1 == 0` caused `_validateSignature` to check zero signatures and let anyone withdraw, `Rs.len() == 0` causes `SchnorrAggregate::verify` to check zero signatures and accept a forgery.

Note: Serai's own consumer `Validators::verify_aggregate` in `coordinator/tributary/src/tendermint/mod.rs` (lines 201–229) passes through this same path, and the weight check in `Network::verify_commit` (`coordinator/tributary/tendermint/src/ext.rs`, lines 273–274) happens to reject empty signer lists afterwards — but that protection lives in the caller, not the verifier. The crypto primitive itself returns `true` for a forged aggregate over an empty set, and any other caller (or a caller that filters the signer list down to zero entries, e.g., after removing participants) inherits the bug. The downstream-weight-check coincidence is analogous to Kinto relying on external code to save it — the verifier's contract is broken.

### Impact Explanation
An unprivileged party can produce a `SchnorrAggregate` encoding (zero `R`s, `s = 0`) that `verify` accepts for any message and any empty `(key, challenge)` list — i.e., a forged signature validating "zero signatures required." Any code path that reaches `verify` with a caller-computed signer set that can be empty (filtering, removal sets, dynamic participant lists) accepts attacker-controlled bytes as a valid aggregate signature, enabling forged authentication of arbitrary messages. Severity: Medium — impact is a signature forgery, but only on the degenerate empty-signer path.

### Likelihood Explanation
`SchnorrAggregate::read` and `verify` are public APIs taking untrusted bytes and a caller-supplied signer list. Whether a production caller can actually reach the empty-signer case depends on integrator logic; in Serai's tendermint usage the subsequent weight check incidentally rejects it. However, the verifier itself has no invariant preventing zero statements, and any caller that builds `keys_and_challenges` dynamically (e.g., excluding removed/offline validators) can collapse to the empty case without noticing — precisely the Kinto scenario where a policy change silently reduced required signatures to zero.

### Recommendation
In `crypto/schnorr/src/aggregate.rs`, reject empty aggregates in `SchnorrAggregate::verify` (and `read`):

```rust
if self.Rs.is_empty() || self.Rs.len() != keys_and_challenges.len() {
  return false;
}
```

Optionally also reject `s == 0`/`R == identity` defensively, and document that `verify` never accepts a zero-signer statement — mirroring the report's recommendation to bound the verification result and never check zero signatures.

### Proof of Concept
```rust
// crypto/schnorr semantics demonstration
// SchnorrAggregate { Rs: [], s: 0 } serialized as:
//   u32 le length = 0, followed by s.to_repr() (all-zero scalar encoding)
let mut encoded = 0u32.to_le_bytes().to_vec();
encoded.extend(C::F::ZERO.to_repr().as_ref());
let agg = SchnorrAggregate::<C>::read(&mut encoded.as_slice()).unwrap();
// keys_and_challenges built by the caller is empty (e.g., all signers filtered out)
assert!(agg.verify(DST, &[])); // forged: verifies over zero signatures
```

The multiexp reduces to `(-0)·G = identity`, so `is_identity()` returns true and the forged aggregate is accepted — no signer participation, nonce, or private key required.
