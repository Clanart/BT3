### Title
Malicious FROST preprocess forces the aggregate nonce to the point at infinity, panicking honest signers — (File: networks/bitcoin/src/crypto.rs)

### Summary
The upstream bug class is "panic on an exceptional condition the code assumed could never occur on attacker-influenceable state." In Serai, the equivalent is `x()`/`x_only()` in `networks/bitcoin/src/crypto.rs`, which `expect`s the input point to be non-infinity. These helpers are invoked inside `Hram::hram`, which runs during `sign_share` and `verify` on the aggregate nonce commitment `R`. `R` is a binding-factor-weighted sum of per-participant nonce commitments (`B.nonces(&nonces)` in `crypto/frost/src/sign.rs`), and those commitments come from `Preprocess` messages supplied by unauthenticated-then-authenticated counterparties via `read_preprocess`. A participant who crafts their `Commitments` so the aggregate `R` is the identity element causes every honest signer's `sign()`/`complete()` to panic inside `crypto.rs:15`/`crypto.rs:22`.

### Finding Description
- `Commitments::read` (`crypto/frost/src/nonce.rs`, invoked from `AlgorithmSignMachine::read_preprocess` at `crypto/frost/src/sign.rs:276-281`) accepts arbitrary curve points for the hiding/binding nonce commitments; no identity or cancellation checks are performed.
- In `AlgorithmSignMachine::sign` (`crypto/frost/src/sign.rs:325-383`), each included participant's commitments are bound into `B`, rho factors are computed over the transcript (`sign.rs:362-371`), and `B.nonces(&nonces)` produces the aggregate nonce vector `Rs` (`sign.rs:383`). `R` is attacker-influenceable because it is `Σ_l (D_l + rho_l·E_l)` where the attacker chooses `D_l`, `E_l` after seeing all other preprocesses.
- `self.params.algorithm.sign_share(&view, &Rs, nonces, msg)` (`sign.rs:398`) routes into `IetfSchnorr`/`Schnorr`, whose `Hram::hram` calls `x(R)` (`crypto.rs:59-66`) → `key.to_encoded_point(true).x().expect("point at infinity")` (`crypto.rs:13-16`). If `R` is identity this is an unconditional panic. The same panic fires in `Schnorr::verify` (`crypto.rs:145-149`) during `AlgorithmSignatureMachine::complete` (`sign.rs:465`) for the aggregated signature path.
- The only guards in `sign()` are participant-set checks (`sign.rs:297-310`); nothing validates that the aggregate nonce is non-identity, analogous to the kernel running without checking `ATTR_SEPT_VE_DISABLE`.

### Impact Explanation
Any single participant in a FROST/Bitcoin signing session can publish a preprocess that crashes every honest signer's process when the aggregate nonce collapses to the identity point. Because `TransactionSignMachine::sign` (`networks/bitcoin/src/wallet/send.rs:355-398`) drives one inner `AlgorithmSignMachine` per input, a single poisoned `Vec<Preprocess>` aborts the whole transaction signing attempt across all signers, halting withdrawals/spends (funds temporarily unspendable while signers are crashed before producing shares). This maps the report's "unhandleable exception on assumed-impossible state → panic" onto a reachable panic from public protocol bytes.

### Likelihood Explanation
The attacker must make `Σ_l (D_l + rho_l·E_l) = 0` where `rho_attacker` is a hash of all commitments including their own — a fixed-point problem in a random oracle. In a single session this is hard (~2^128 via rho-function iteration). However, Serai explicitly runs many parallel signing sessions (ROS-style exposure is in scope): an attacker controlling one seat across `k` concurrent sessions collects `k` candidate `rho·e` terms and uses a Wagner/generalized-birthday solve to select commitment scalars whose weighted contributions cancel the honest sum in at least one session, with work roughly `2^(256/(1+log2 k))`. With `k ≈ 2^16` parallel preprocess rounds this is practical. Triggering requires only sending well-formed preprocess bytes to `read_preprocess`; no collusion, key material, or validator privileges are needed.

### Recommendation
Reject identity (and generally any non-prime-subgroup/exceptional) points in `Commitments::read` and, additionally, validate the aggregate `Rs` produced by `B.nonces` before use, returning `FrostError` instead of panicking. Make `x()`/`x_only()` in `crypto.rs` return `Option`/`io::Result` and propagate failure through `Hram`/`Algorithm` rather than `expect`ing non-infinity on adversary-influenceable points, so a bad preprocess is a session abort, not a process abort.

### Proof of Concept
```rust
// Honest signer path (simplified):
// 1. Attacker observes all other participants' preprocesses for the session.
// 2. Across many parallel sessions (or via rho fixed-point grinding), attacker selects
//    nonce commitments (D, E) such that for the included set:
//        sum_l (D_l + rho_l * E_l) == ProjectivePoint::IDENTITY
//    and serializes them as a normal Preprocess message.
// 3. Honest signer calls:
//        machine.read_preprocess(&mut attacker_bytes)?;   // succeeds — no identity check
//        machine.sign(commitments_map, b"")               // send.rs:355
// 4. Inside sign(): B.nonces(&nonces) -> R = identity (sign.rs:383)
//    sign_share -> Hram::hram(&R, &A, msg) -> x(&R)
//    crypto.rs:15: encoded.x().expect("point at infinity") -> PANIC
//    => honest signer process crashes before emitting a SignatureShare;
//       TransactionSignatureMachine::complete can never run.
```
The panic is deterministic once `R = identity` is achieved; the only probabilistic part is constructing cancelling commitments, which the parallel-session (Wagner) route makes feasible for a single malicious participant.
