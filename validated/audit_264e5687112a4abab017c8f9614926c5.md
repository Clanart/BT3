### Title
Excess Native-Token Payment Permanently Locked in `EvmHost` on `dispatch()`/`fundRequest()` — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and forward the *entire* amount into `IUniswapV2Router02.swapETHForExactTokens`, requesting only the exact `post.fee` / `get.fee` / `amount` of fee-token output. `swapETHForExactTokens` is an exact-output swap that only consumes as much ETH as needed and refunds the leftover — but the refund goes to the caller of the router, which is `EvmHost` itself, not the original end user who sent the `msg.value`. This is the same broken invariant as the reported `Multicall.click()` bug: the contract computes/consumes a smaller amount than `msg.value` and the difference is not returned to the payer, only this time by construction (asymmetric swap-refund destination) rather than a stale price read.

### Finding Description
In `EvmHost.sol`: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
```

The identical pattern repeats in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest()` [3](#0-2) .

`swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), deadline)` will only spend the ETH amount required to obtain `post.fee` units of `feeToken`; any unused ETH is refunded by the Uniswap V2 router to `msg.sender` **of the swap call**, i.e., `address(this)` (the `EvmHost` contract), not to `_msgSender()` (the user who called `dispatch`/`fundRequest`). There is no subsequent step in any of these three functions that forwards the refunded ETH back to the caller — no `.call{value: refund}(...)` to `_msgSender()`, and no tracking of a "leftover ETH" balance owed to that specific caller.

This is precisely the class of bug described in the external report: the function does not verify/reconcile `msg.value` against the amount actually required (`post.fee`), so any excess a user sends (a very likely occurrence, since front-end fee estimates via `quote()` are explicitly documented as inexact/sandwich-prone and users are told to send a buffer) becomes stuck. Unlike `IntentGatewayV2`, which the codebase's own tests confirm explicitly refunds unspent native tokens back to `msg.sender` after an equivalent swap (see `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`, `testFillCrossChain_RefundsSolverExcessNativeToken` in `IntentGatewayV2Test.sol`), `EvmHost.dispatch()`/`fundRequest()` contain no such refund-forwarding logic. [4](#0-3) 

### Impact Explanation
Any unprivileged user calling the public, unauthenticated `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` entrypoints on `EvmHost` with `msg.value` greater than what is needed to acquire the exact fee-token amount permanently loses the difference — it accumulates as stray ETH inside the `EvmHost` contract with no user-facing withdrawal path evidenced in this file. Given that the documentation explicitly warns that `quote()` estimates are approximate and subject to sandwich risk, and recommends buffering value sent (e.g., the `HyperbridgeLzEndpoint` applies a 2x buffer), overpayment is a realistic, expected occurrence, not a contrived edge case. This is direct loss of user funds through the core `IsmpHost` contract, matching the required impact category "stealing or loss of funds."

### Likelihood Explanation
High likelihood: this triggers on the ordinary, documented usage path (`dispatch{value: msg.value}(...)`) with no admin, relayer, or malicious-peer involvement, purely from normal slippage between the amount of native token a user sends and the exact fee-token output needed. Every dispatcher call with `msg.value > 0` is exposed.

### Recommendation
After `swapETHForExactTokens` returns, check `address(this).balance` (or capture the router's returned amounts) for any leftover ETH attributable to the caller and forward it back to `_msgSender()` via a low-level call, exactly as `IntentGatewayV2` does for its native-token swap paths. Alternatively, require exact `msg.value` (revert on mismatch) and let the caller retry with a corrected fee, or expose an explicit sweep/refund function keyed to the paying address.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1 ether}(DispatchPost{..., fee: 0.1 ether feeToken worth ...})`, sending 1 ETH as a safety buffer above the estimated fee-token cost (as documented practice).
2. Inside `dispatch()`, `swapETHForExactTokens{value: 1 ether}(0.1e18, path, address(this), deadline)` is called; suppose only 0.3 ETH is needed to acquire `0.1e18` feeToken.
3. Uniswap V2 router refunds the remaining 0.7 ETH — to `EvmHost` (the caller of the swap), not to the user.
4. `dispatch()` returns; the user has been charged the full 1 ETH from their wallet but only 0.3 ETH worth of value was ever attributed to their request. The 0.7 ETH is now stuck in `EvmHost`'s balance with no mechanism in `dispatch()`, `fundRequest()`, or elsewhere in this file to return it to the user.

    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
