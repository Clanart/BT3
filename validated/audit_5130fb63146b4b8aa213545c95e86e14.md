### Title
`Scanner::scan_transaction` marks outputs as received without any minimum-value check, reporting dust outputs that cannot be economically spent - (File: networks/bitcoin/src/wallet/mod.rs)

### Summary
The referenced bug is a missing minimum-threshold check at acceptance time: `register()` marked a subnet `Status.Active` unconditionally, while `addStake()` correctly required `stake >= s.minStake`. The same bug class exists in `networks/bitcoin/src/wallet/mod.rs`: `Scanner::scan_transaction` accepts any transaction output whose `script_pubkey` matches a registered offset and reports it as a spendable `ReceivedOutput`, with no validation that `output.value` meets any minimum (dust limit or fee-spendability). No later stage re-checks the value before the output is surfaced to the caller.

### Finding Description
`ReceivedOutput` is the type the wallet layer hands to callers as a spendable output: it carries an HDKD `offset`, the `TxOut`, and the `OutPoint` (`networks/bitcoin/src/wallet/mod.rs:90-97`). `scan_transaction` populates it purely on script match (`networks/bitcoin/src/wallet/mod.rs:199-214`):

```rust
if let Some(offset) = self.scripts.get(&output.script_pubkey) {
  res.push(ReceivedOutput {
    offset: *offset,
    output: output.clone(),
    outpoint: OutPoint::new(tx.compute_txid(), vout),
  });
}
```

There is no comparison of `output.value.to_sat()` against any floor. This is directly parallel to the IPC bug: the "activation" predicate (a matching `script_pubkey`) is checked, but the "minimum collateral" predicate (a value at or above what it costs to spend the input) is not, so under-provisioned entries are reported as valid/spendable. The struct even exposes `value()` (`mod.rs:116-118`), confirming the value is meaningful downstream, yet nothing gates on it. The only documented exception handled is coinbase maturity in `scan_block` (`mod.rs:216-220`) — value sufficiency is neither checked nor documented as a caller responsibility.

### Impact Explanation
An accepted impact criterion is "funds reported received that are not spendable." An attacker who sends transactions paying tiny amounts (e.g., at or below the ~330-sat P2TR dust boundary, or any value lower than the sat/vbyte cost of a Taproot key-path input, roughly 58 vbytes) to a registered script causes `scan_transaction` to emit `ReceivedOutput`s that:

- are counted as received balance by whatever consumes the scanner results, but
- can never be spent without the input's fee cost exceeding its value, so any transaction attempting to include them is either uneconomical or produces incorrect fee/change math downstream.

This is a forced, persistent inflation of the wallet's apparent balance and input set, attackable repeatedly for the cost of the dust itself.

### Likelihood Explanation
The attack requires only that the attacker broadcast ordinary Bitcoin transactions to the multisig's known Taproot `script_pubkey` — a public input explicitly in scope ("Bitcoin transactions they send"). No validator privilege, threshold collusion, or key material is needed. Registration of additional offsets via `register_offset` (`mod.rs:180-196`) gives an attacker additional distinct scripts to target, each of which is matched identically with no value check. Likelihood is therefore moderate-to-high: dusting well-known addresses is a standard, low-cost technique.

### Recommendation
Add a minimum-value gate in `scan_transaction` analogous to the `stake >= s.minStake` fix — e.g., reject or quarantine outputs whose `value` is below a configurable `min_value` (defaulting to the greater of the P2TR dust threshold and the current estimated fee to spend one Taproot input), so only economically spendable outputs are reported as `ReceivedOutput`. Alternatively, expose the check as an explicit parameter so callers cannot forget it, and document that `scan_block` still requires the coinbase-maturity post-pass.

### Proof of Concept
```rust
// Attacker crafts a transaction with an output paying, e.g., 200 sats
// (below spendable threshold) to the multisig's registered script_pubkey.
let dust_output = TxOut {
  value: Amount::from_sat(200),
  script_pubkey: multisig_script, // the script registered in Scanner::scripts
};
let attacker_tx = Transaction { /* ... outputs: vec![dust_output] ... */ };

// Scanner reports it as a spendable ReceivedOutput despite the value
// being below the cost to ever spend it.
let received: Vec<ReceivedOutput> = scanner.scan_transaction(&attacker_tx);
assert_eq!(received.len(), 1);          // accepted as "active"
assert_eq!(received[0].value(), 200);   // under the required minimum
// No field or error path marks this output as unspendable.
```
