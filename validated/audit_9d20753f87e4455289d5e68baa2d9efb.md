Based on my investigation, the strongest verified analog is in the custom-protocol/deep-link handling path, not in IPC (the IPC layer is properly guarded by `isTrustedIPCSender`, which I confirmed via [1](#0-0)  and [2](#0-1) , so that's not a viable analog).

The report's broken invariant is: **untrusted input reaches a routing function that dispatches to a sensitive handler without validating/authorizing the caller or fully validating the payload.** In GitHub Desktop the equivalent routing function is `parseAppURL`, fed directly by the OS-level custom protocol handler (`x-github-client://`, `github-mac://`, etc.), which any website or attacker-crafted link can invoke via `app.on('open-url', ...)`.

### Title
Unvalidated `filepath` parameter in custom-protocol "Open in Desktop" deep link allows path traversal outside the cloned repository - (File: app/src/lib/parse-app-url.ts)

### Summary
`parseAppURL` builds an `IOpenRepositoryFromURLAction` from an externally-supplied, attacker-controlled URL (any web page can trigger Desktop's registered custom protocol). It validates `branch` (`testForInvalidChars`) and `pr` (`^\d+$`) but performs **no validation whatsoever on `filepath`** before passing it through to the dispatcher, which is later used to open a file after cloning.

### Finding Description
`handleAppURL` in `app/src/main-process/main.ts` is registered as the handler for OS-level `open-url` events and command-line protocol launches — this is attacker-reachable input, since any application (including a web browser navigating to a crafted `x-github-client://` link) can invoke it: [3](#0-2) 

The URL is parsed by `parseAppURL`, which extracts `filepath` from the querystring and returns it unmodified, unlike `branch` and `pr` which go through validation: [4](#0-3) 

The resulting action is routed by `dispatchURLAction` straight to `openRepositoryFromUrl(action)` with no additional authorization or provenance check on the source of the URL (no distinction between a link the user typed vs. one embedded in a malicious web page/email): [5](#0-4) 

This mirrors the reported bug-class exactly: a routing/dispatch function (`parseAppURL` → `dispatchURLAction`, analogous to the Solidity fallback dispatcher) forwards an externally-triggered request to a sensitive handler (`openRepositoryFromUrl`) without verifying the caller's legitimacy or fully sanitizing the payload that reaches it.

### Impact Explanation
If `openRepositoryFromUrl` uses the attacker-supplied `filepath` to open a file relative to the freshly cloned repository (as its name and the test suite's use of paths like `Octokit.Reactive/Octokit.Reactive.csproj` imply — see [6](#0-5) ), an attacker-controlled string containing traversal sequences (`../../`) could cause Desktop to open/read a file **outside** the cloned repository directory, matching the "file read/write outside the repo" impact category from a link the user merely clicks.

### Likelihood Explanation
Likelihood is high for triggering the code path (protocol handlers are registered at install time and clickable links are a normal attack vector — see `possibleProtocols` registration at [7](#0-6) ), but I was **not able to verify** the exact downstream consumer of `filepath` (the `openRepositoryFromUrl` implementation) within this session/tool budget, so I cannot confirm whether a sanitization step exists further down the call chain before the file is actually opened.

### Recommendation
Sanitize/canonicalize `filepath` in `parseAppURL` (or immediately in the consumer) the same way `branch` is checked with `testForInvalidChars`, rejecting any value containing `..`, absolute path prefixes, or resolving outside the target repository root before it is used for any file-system operation.

### Proof of Concept
1. Attacker hosts a link: `x-github-client://openrepo/https://github.com/attacker/repo?filepath=..%2F..%2F..%2F.ssh%2Fid_rsa`
2. Victim clicks the link (or it's embedded in a webpage that auto-navigates to the protocol URI).
3. OS invokes Desktop's registered protocol handler → `app.on('open-url')` → `handleAppURL` → `parseAppURL` returns `{ name: 'open-repository-from-url', url, filepath: '../../../.ssh/id_rsa', ... }` unfiltered [8](#0-7) .
4. `dispatchURLAction` forwards to `openRepositoryFromUrl(action)` [5](#0-4)  with no re-validation.

**Caveat:** I could not retrieve the body of `openRepositoryFromUrl` (the actual file-open sink) in this session to confirm whether it re-validates `filepath` before use, so this should be treated as a strong candidate requiring confirmation of the sink rather than a fully proven end-to-end exploit. If a Devin session with full repo access is available, verifying `openRepositoryFromUrl`'s handling of `filepath` would be the next concrete step.
