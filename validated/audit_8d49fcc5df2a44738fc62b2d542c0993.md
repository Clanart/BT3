### Title
Attacker-controlled PedPoP decryption/blame input panics on unregistered participant index, crashing the node (DoS) - (File: crypto/dkg/pedpop/src/encryption.rs)

### Summary
The nettle advisory concerns a crash/denial-of-service triggered when a cryptographic routine processes specially crafted, attacker-supplied input. The direct analog in Serai's in-scope code lives in PedPoP's encryption module: `Decryption::register` and `Decryption::decrypt_with_proof` index `self.enc_keys` by a `Participant` derived from untrusted protocol messages, panicking (`assert!` / HashMap `Index`) instead of returning an error when the referenced participant has no registered encryption key. An unprivileged DKG participant can crash the target by sending a second `EncryptionKeyMessage` for the same participant index, or by triggering a blame/decryption flow (via attacker-supplied `EncryptedMessage`/`EncryptionKeyProof` bytes) naming a `decryptor` index that was never registered.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `Decryption` tracks per-participant encryption keys in `enc_keys: HashMap<Participant, C::G>`:

- `register` (lines 351-362) executes `assert!(!self.enc_keys.contains_key(&participant), "Re-registering encryption key for a participant")`. The `participant` value is attacker-chosen (the sender index of the incoming `EncryptionKeyMessage`, read via `EncryptionKeyMessage::read`). Sending a second registration for the same participant deterministically panics.
- `decrypt_with_proof` (lines 366-397) computes `self.enc_keys[&decryptor]` at line 388 inside the DLEq verification for a blame proof. `HashMap`'s `Index` impl panics when the key is absent. The `decryptor`/`from` participants and the `msg`/`proof` objects all originate from attacker-controlled bytes (`EncryptedMessage::read` lines 171-177, `EncryptionKeyProof::read` lines 267-269), and the PoP signature check at line 374 passes for any message the attacker signs with their own ephemeral key — no honest-party secret is needed to reach line 388.

The panic propagates up through the PedPoP share-verification/blame path, aborting the calling thread/process instead of returning `DecryptionError`.

### Impact Explanation
A malicious participant (or any party able to feed these messages into a PedPoP verifier) can crash every honest node that processes the message. For a validator set running this DKG, a single crafted re-registration or a blame proof referencing an unregistered `decryptor` index halts the key-generation/share-verification routine — a remotely triggerable denial of service matching the reported bug class (crafted input → crash). Liveness of the threshold protocol is broken; repeated messages can keep nodes down.

### Likelihood Explanation
Reachability requires only that the attacker can submit DKG messages (commitments/encryption-key registrations/blame proofs) — an unprivileged capability for any protocol participant. No collusion, leaked keys, or malicious infrastructure is needed; the trigger is deterministic, not probabilistic, since `HashMap::index` panics unconditionally on a missing key and the `assert!` fires unconditionally on re-registration.

### Recommendation
Replace infallible accesses on attacker-influenced indices with checked lookups:

- In `register`, return an `io::Error`/`DkgError` (e.g., a new `DuplicateRegistration` variant) instead of `assert!` when `enc_keys.contains_key(&participant)`.
- In `decrypt_with_proof`, use `self.enc_keys.get(&decryptor).ok_or(DecryptionError::InvalidProof)?` instead of `enc_keys[&decryptor]`.
- Apply the same fix to `encrypt`'s `self.decryption.enc_keys[&participant]` (line 466), which has the same panic mode if called with an unregistered index.
