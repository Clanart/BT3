### Title
IBC Voucher Double-Mint via Front-Run of Predictable ERC20 Precompile Address - (File: `x/erc20/keeper/ibc_callbacks.go`, `x/erc20/keeper/token_pairs.go`, `utils/utils.go`)

### Summary
The `merkleRoot`-as-salt front-running pattern in the Joyn report maps directly onto Cosmos EVM's IBC-to-ERC20 auto-conversion flow. The ERC20 precompile address for any IBC voucher denom is deterministically derived from the denom hash (`utils.GetIBCDenomAddress`), which is public and computable ahead of time from the (port, channel, base-denom) tuple. An attacker can pre-deploy code to that exact address, causing the one-time registration guard in `CreateNewTokenPair` to reject the legitimate registration on first receipt of that IBC coin — but by the time that failure is detected, the underlying ICS20 transfer has already minted the voucher coin to the receiver, resulting in a double-mint of value across chains when the source chain refunds the sender in response to the resulting error acknowledgement.

### Finding Description
`GetIBCDenomAddress` computes the ERC20 contract address purely from the IBC denom hash: [1](#0-0) . This is the "salt"-equivalent of the reported bug — fully predictable before the first transfer of a given denom ever occurs, since IBC denom hashes are `sha256(port/channel/.../baseDenom)` and channels/ports are public.

`CreateNewTokenPair` enforces a one-time-use invariant on this address, exactly like the `SplitProxy` salt: if an account with code already exists at the derived address, registration is rejected: [2](#0-1) .

An attacker can front-run any future first transfer of a given IBC denom by sending an ordinary EVM transaction (e.g. `CREATE2`, or simply having a contract deployed via nonce-based `CREATE` land at that address, or directly setting code through any reachable path) to occupy that predictable address with `HasCodeHash() == true` before the first relayed packet for that denom arrives.

When the first IBC transfer of that denom subsequently arrives, `IBCMiddleware.OnRecvPacket` first executes the core ICS20 transfer logic (`im.Module.OnRecvPacket`), which mints/credits the voucher coin to the receiver's bank balance, and only afterward invokes `k.keeper.OnRecvPacket` for ERC20 conversion: [3](#0-2) . Inside that keeper callback, when the denom is unregistered and IBC-prefixed, `RegisterERC20Extension` is invoked, and any error from it is turned into an `Error Acknowledgement`: [4](#0-3) . `RegisterERC20Extension` calls the vulnerable `CreateNewTokenPair`: [5](#0-4) .

Because the receiver's voucher-coin balance was already credited by the time the middleware later decides to return an error acknowledgement, that credit is not rolled back on the destination chain (the ack value returned up the module stack does not revert the state mutations already committed by the lower-level transfer module in the same transaction). The relayer will deliver this error acknowledgement to the source chain, where standard ICS20 `OnAcknowledgementPacket` processing refunds the original sender by releasing the escrowed tokens back to them. The net effect: the destination-chain receiver retains the minted voucher balance, and the source-chain sender also gets their original funds refunded — an unauthorized duplication of the same unit of value across two chains.

### Impact Explanation
This breaks the core 1:1 IBC escrow/voucher accounting invariant required by the "Asset-representation path" guidance: escrowed value on the source chain is duplicated instead of consumed. Any unprivileged party can trigger it by simply predicting the deterministic ERC20 address for a not-yet-transferred IBC denom and squatting it with contract code, then having (or waiting for) that denom to be relayed for the first time. This is a Critical, unauthorized duplication/minting of spendable user value across native balances and IBC escrows, matching the allowed impact gate.

### Likelihood Explanation
The precompile address is deterministic and computable in advance by anyone who knows the source chain, channel-id, and base denom (all public IBC topology information). Occupying that address only requires a normal, unprivileged EVM transaction executed before the first transfer of that particular denom/channel pair is relayed — a reasonably achievable condition for new channels or new denoms, especially since relayers are permissionless and an attacker can also control/delay when they submit the triggering `RecvPacket` themselves.

### Recommendation
- Remove the implicit assumption that a failed post-transfer registration step can safely be reported as a full "Error Acknowledgement" after the underlying transfer already mutated state. Either:
  - Perform the address-collision / registration feasibility check *before* invoking the underlying ICS20 `OnRecvPacket` (i.e., pre-validate that the precompile address is free of foreign code), or
  - If registration fails after the coin has already been credited, treat it as a soft-failure (do not return an error acknowledgement) — leave the user with the plain bank-denom coin and skip ERC20 conversion, exactly as is already done for the "no-op" cases (`ERC20 disabled`) elsewhere in the same function.
- Alternatively, make the derived ERC20 address collision-safe against pre-existing foreign code by not relying purely on `HasCodeHash()` — e.g., mix in a chain-specific/module-specific salt component that cannot be pre-computed and squatted by an ordinary externally-owned account outside the erc20 module's control.

### Proof of Concept
1. Attacker identifies a channel/port and base denom that has never had a voucher transferred to this chain (e.g., a newly created IBC channel), and computes the future IBC denom `ibc/<hash>` and its corresponding EVM address via `GetIBCDenomAddress`.
2. Attacker submits an ordinary EVM transaction that results in contract code being deployed to that exact address (e.g., via `CREATE2` with attacker-controlled deployer/salt combination that collides with the target address, or simply via repeated nonce-based deployments until landing on it — computation is feasible offline since the target address is fully known in advance).
3. A legitimate user initiates (or a relayer relays) the first ICS20 transfer of that base denom over that channel to this chain.
4. `IBCMiddleware.OnRecvPacket` runs the core transfer logic first, crediting the receiver's account with the new IBC voucher coin.
5. The erc20 keeper's `OnRecvPacket` then calls `RegisterERC20Extension` → `CreateNewTokenPair`, which finds `account.HasCodeHash() == true` at the precomputed address and returns `ErrTokenPairAlreadyExists`.
6. `OnRecvPacket` returns a `channeltypes.NewErrorAcknowledgement(err)`.
7. This error acknowledgement propagates to the source chain, which refunds the sender's escrowed tokens, while the receiver on the destination chain still holds the credited voucher coin from step 4 — resulting in duplicated value across the two chains.

// GetIBCDenomAddress returns the address from the hash of the ICS20's Denom Path.
func GetIBCDenomAddress(denom string) (common.Address, error) {
	if !strings.HasPrefix(denom, "ibc/") {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrapf("coin %s does not have 'ibc/' prefix", denom)
	}

	if len(denom) < 5 || strings.TrimSpace(denom[4:]) == "" {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrapf("coin %s is not a valid IBC voucher hash", denom)
	}

	// Get the address from the hash of the ICS20's Denom Path
	bz, err := ibctransfertypes.ParseHexHash(denom[4:])
	if err != nil {
		return common.Address{}, ibctransfertypes.ErrInvalidDenomForTransfer.Wrap(err.Error())
	}

	return common.BytesToAddress(bz), nil
}

// CreateNewTokenPair creates a new token pair and stores it in the state.
func (k Keeper) CreateNewTokenPair(ctx sdk.Context, denom string) (types.TokenPair, error) {
	pair, err := types.NewTokenPairSTRv2(denom)
	if err != nil {
		return types.TokenPair{}, err
	}
	account := k.evmKeeper.GetAccount(ctx, pair.GetERC20Contract())
	if account != nil && account.HasCodeHash() {
		return types.TokenPair{}, errorsmod.Wrapf(types.ErrTokenPairAlreadyExists, "token already exists for token %s", pair.Erc20Address)
	}
	err = k.SetToken(ctx, pair)
	if err != nil {
		return types.TokenPair{}, err
	}
	return pair, nil
}

	// return if the acknowledgement is an error ACK

	}

func (k Keeper) RegisterERC20Extension(ctx sdk.Context, denom string) (*types.TokenPair, error) {
	pair, err := k.CreateNewTokenPair(ctx, denom)
	if err != nil {
		return nil, err
	}

	// Add to existing EVM extensions
	if err := k.EnableDynamicPrecompile(ctx, pair.GetERC20Contract()); err != nil {
		return nil, err
	}

	return &pair, err
}
