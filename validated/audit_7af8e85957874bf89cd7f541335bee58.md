## Analysis

The strongest analog to the GNTDeposit bug in this codebase is `updateRemoteUrl` in `app/src/lib/stores/updates/update-remote-url.ts`, which silently rewrites a repository's `origin` remote based on a GitHub API `clone_url` value, using a stale trust check that doesn't validate the actual new destination.

### Title
Silent, unprompted rewrite of the git remote URL from an untrusted GitHub API `clone_url` field - (File: `app/src/lib/stores/updates/update-remote-url.ts`)

### Summary
Similar to how GNTDeposit trusted a stale "unlocked" flag instead of re-validating each new deposit, GitHub Desktop's `updateRemoteUrl` trusts a stale "remote URL matches previously known clone URL" check instead of validating the new target host/owner/name it is about to write. This lets a value returned by the GitHub API (`apiRepo.clone_url`) silently overwrite the user's `origin` remote to point anywhere, as long as the URL scheme (http/ssh) happens to match.

### Finding Description
`updateRemoteUrl` is invoked from `repositoryWithRefreshedGitHubRepository` in `app/src/lib/stores/app-store.ts` every time Desktop refreshes GitHub repository metadata in the background (repository selection, periodic refresh, add-repository flow, fetch/push/pull): [1](#0-0) 

The function decides whether to rewrite the remote using three checks: [2](#0-1) 

- `protocolsMatch` only checks that both URLs use the same protocol string (e.g. both `https:`), not that they point to the same host.
- `remoteUrlUnchanged` only checks that the *current* local remote still matches the *previously cached* `gitHubRepository.cloneURL` — it says nothing about whether the *new* `apiRepo.clone_url` is legitimate.
- `urlsMatch` is deliberately false in the exploit case (that's the trigger condition).

Nowhere does the code verify that the new `clone_url` still refers to the same owner/repo identity that the user originally added, or that it targets a GitHub host at all. `urlMatchesRemote`/`urlsMatch` are only used to detect *whether* something changed, not to reject changes to a different host or organization: [3](#0-2) 

If all three conditions align, Desktop calls `gitStore.setRemoteURL(...)` and rewrites `origin` with **no user confirmation or notification**, exactly as GNTDeposit's `onTokenReceived` mutated `balances[_from]` without re-validating the timelock state: [4](#0-3) 

Since `apiRepo` comes directly from a GitHub/GHE API response object (`IAPIRepository`), any attacker capable of influencing that response body (a malicious/compromised GitHub Enterprise instance, a spoofed/mirrored API endpoint the user has been configured to trust, or a compromised upstream proxy in front of the API) can set `clone_url` to an attacker-controlled repository URL that merely preserves the protocol scheme. Because the existing tests only assert the "same owner/repo" case and the "protocol differs" case, they never assert that a *different host* with the *same protocol* is rejected: [5](#0-4) 

### Impact Explanation
This corrupts what the user pushes/fetches going forward. Once `origin` is silently repointed, the next `git push` sends the user's code (and, if the attacker sets an SSH/HTTPS URL of their choosing, potentially credentials via the trampoline credential helper matched by hostname) to the attacker's repository, and the next `git fetch`/`pull` retrieves attacker-controlled history into the user's working copy — a direct "silent corruption of what the user commits or pushes" scenario, driven entirely by an attacker-controlled GitHub API object.

### Likelihood Explanation
The precondition (`remoteUrlUnchanged` true) is the *common* case — most users never hand-edit their `origin` URL after cloning through Desktop, so their remote continues to match `gitHubRepository.cloneURL`. The refresh path (`repositoryWithRefreshedGitHubRepository` → `updateRemoteUrl`) runs automatically and repeatedly in the background (on repository selection, periodic status refresh, and around fetch/push/pull), so the attacker doesn't need to wait for any unusual user action — only for Desktop's routine background refresh to hit the malicious API response once.

### Recommendation
Before rewriting a remote URL, verify that the new `clone_url` still identifies the *same* GitHub host/owner/repo identity previously associated with the local `GitHubRepository` record (e.g., match by stable repository ID rather than trusting the URL string alone), and require explicit user confirmation for any change of hostname, similar to how GNTDeposit's fix required resetting/validating state on each new "deposit" rather than trusting a stale flag.

### Proof of Concept
1. User adds/clones a repository through Desktop against a GitHub Enterprise (or otherwise attacker-influenceable) endpoint; `origin` matches `gitHubRepository.cloneURL` exactly.
2. Attacker who controls (or can MITM/spoof) the API response for that endpoint's repository-fetch call returns `clone_url: "https://attacker.example.com/attacker/repo.git"` (same `https:` scheme as the legitimate remote).
3. On the next background refresh, `app-store.ts`'s `repositoryWithRefreshedGitHubRepository` calls `updateRemoteUrl(gitStore, gitHubRepository, apiRepo)`.
4. `protocolsMatch` is true (both `https:`), `remoteUrlUnchanged` is true (local remote still equals the old cached `cloneURL`), `urlsMatch` is false (new host differs) → `gitStore.setRemoteURL('origin', 'https://attacker.example.com/attacker/repo.git')` executes silently.
5. The user's subsequent push/fetch operations now target the attacker's repository without any dialog, warning, or opt-in.

  const remoteUrl = gitStore.defaultRemote.url
  const updatedRemoteUrl = apiRepo.clone_url
  const urlsMatch = urlMatchesRemote(updatedRemoteUrl, gitStore.defaultRemote)

  // Verify that protocol hasn't changed. If it has we don't want
  // to alter the protocol in case they are relying on a specific one.
  // If protocol is null that implies the url is a ssh url
  // of the format git@github.com:octocat/Hello-World.git, which
  // can't be parsed by URL.parse. In this case we assume the user
  // manually configured their remote to use this format and we don't
  // want to change what they've done just to be safe
  const parsedRemoteUrl = URL.parse(remoteUrl)
  const parsedUpdatedRemoteUrl = URL.parse(updatedRemoteUrl)
  const protocolsMatch =
    parsedRemoteUrl.protocol !== null &&
    parsedUpdatedRemoteUrl.protocol !== null &&
    parsedRemoteUrl.protocol === parsedUpdatedRemoteUrl.protocol

  // Check if the default remote url has been manually changed from the
  // clone url retrieved from the GitHub API previously
  const remoteUrlUnchanged =
    gitStore.defaultRemote &&
    urlMatchesRemote(gitHubRepository.cloneURL, gitStore.defaultRemote)

  if (protocolsMatch && remoteUrlUnchanged && !urlsMatch) {
    await gitStore.setRemoteURL(gitStore.defaultRemote.name, updatedRemoteUrl)
  }

export function urlMatchesRemote(url: string | null, remote: IRemote): boolean {
  if (url == null) {
    return false
  }

  const cloneUrl = parseRemote(url)
  const remoteUrl = parseRemote(remote.url)

  if (remoteUrl == null || cloneUrl == null) {
    return false
  }

  if (!caseInsensitiveEquals(remoteUrl.hostname, cloneUrl.hostname)) {
    return false
  }

  if (remoteUrl.owner == null || cloneUrl.owner == null) {
    return false
  }

  if (remoteUrl.name == null || cloneUrl.name == null) {
    return false
  }

  return (
    caseInsensitiveEquals(remoteUrl.owner, cloneUrl.owner) &&
    caseInsensitiveEquals(remoteUrl.name, cloneUrl.name)
  )
}

    const originalUrl = gitStore.currentRemote.url
    const updatedUrl = 'https://github.com/my-user/my-updated-repo'
    const updatedApiRepository = { ...apiRepository, clone_url: updatedUrl }
    await updateRemoteUrl(gitStore, gitHubRepository, updatedApiRepository)
    assert.notEqual(originalUrl, updatedUrl)
    assert.equal(gitStore.currentRemote.url, updatedUrl)
  })

    const { gitHubRepository, gitStore } = await createRepository(

    const originalUrl = gitStore.currentRemote.url
    assert.notEqual(originalUrl.length, 0, 'Expected originalUrl to be empty')
