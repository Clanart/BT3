### Title
EIP-712 Domain Separator Missing `chain_id` and `verifying_contract` Enables Cross-Deployment Signature Replay on Withdrawal and Optimistic Payout Authorization — (File: `core/src/rpc/ecdsa_verification_sig.rs`)

---

### Summary

`CLEMENTINE_EIP712_DOMAIN` is constructed with only `name` and `version`, omitting `chain_id` and `verifying_contract`. Any `verification_signature` accepted by `recover_address_from_ecdsa_signature` on one Clementine deployment (e.g., testnet, Citrea chain_id=5655) is cryptographically identical to a valid signature on any other deployment sharing the same aggregator key. This breaks the authentication guard protecting both the operator `withdraw` RPC and the verifier `sign_optimistic_payout` path.

---

### Finding Description

In `core/src/rpc/ecdsa_verification_sig.rs`, the static EIP-712 domain is:

```rust
pub static CLEMENTINE_EIP712_DOMAIN: Eip712Domain = alloy_sol_types::eip712_domain! {
    name: "ClementineVerification",
    version: "1",
};
``` [1](#0-0) 

No `chain_id` and no `verifying_contract` are included. The EIP-712 standard defines these fields precisely to scope a signature to a specific chain and contract instance. Without them, the domain separator hash is identical across every Clementine deployment regardless of which Citrea chain (`citrea_chain_id` in config) or bridge contract address it targets.

This domain is used in `recover_address_from_ecdsa_signature`, which is the sole cryptographic check for two privileged bridge actions:

**1. Operator `withdraw` RPC** (`core/src/rpc/operator.rs`, line 222): [2](#0-1) 

**2. Verifier `sign_optimistic_payout`** (`core/src/verifier.rs`, line 1605): [3](#0-2) 

Both call `recover_address_from_ecdsa_signature` with the same domain-less `CLEMENTINE_EIP712_DOMAIN` and compare the recovered address to `config.aggregator_verification_address`. [4](#0-3) 

The config already carries `citrea_chain_id` (e.g., `5655`) and `bridge_contract_address`, both of which are deployment-specific, but neither is fed into the domain. [5](#0-4) 

---

### Impact Explanation

An attacker who captures a legitimately issued `verification_signature` from one Clementine deployment (e.g., testnet) can submit it verbatim to a second deployment (e.g., mainnet) that shares the same `aggregator_verification_address`. Because the EIP-712 hash is domain-agnostic, `recover_address_from_ecdsa_signature` returns the same address on both deployments, and the guard passes.

- **Operator withdrawal path**: The operator then calls `self.operator.withdraw(...)`, which constructs and broadcasts a payout transaction spending the bridge-controlled UTXO. A replayed testnet signature can authorize a mainnet payout to an attacker-controlled address, draining bridged BTC.
- **Optimistic payout path**: Verifiers are induced to contribute MuSig2 partial signatures for an optimistic payout, bypassing the full BitVM challenge flow and releasing funds without on-chain proof.

The `aggregator_verification_address` field is `Option<Address>` and the check is gated on `if let Some(...)`, meaning deployments that omit it have no protection at all — but even those that configure it are vulnerable to cross-deployment replay. [6](#0-5) 

---

### Likelihood Explanation

The same aggregator key being reused across testnet and mainnet deployments is a common operational pattern, especially during staged rollouts. The `withdrawal_id` is a sequential integer, so collisions across deployments are expected. The `input_outpoint` must match the DB record from Citrea, which limits replay to cases where the same withdrawal parameters appear on both networks — a realistic condition when the same user withdraws the same amount on both a test and production deployment. The proto comment explicitly acknowledges replay concerns between message types (`OptimisticPayoutMessage` vs `OperatorWithdrawalMessage`) but the cross-deployment vector was not addressed. [7](#0-6) 

---

### Recommendation

Bind the domain to the deployment by including `chain_id` and `verifying_contract` in `CLEMENTINE_EIP712_DOMAIN`. Since the domain must be static today, convert it to a function that accepts the runtime config values:

```rust
pub fn clementine_eip712_domain(chain_id: u64, contract_address: Address) -> Eip712Domain {
    alloy_sol_types::eip712_domain! {
        name: "ClementineVerification",
        version: "1",
        chain_id: chain_id,
        verifying_contract: contract_address,
    }
}
```

Pass `config.citrea_chain_id as u64` and the parsed `config.bridge_contract_address` at every call site (`recover_address_from_ecdsa_signature` in `rpc/operator.rs` and `verifier.rs`). This ensures a signature issued for testnet (chain_id=5655, contract=0x3100…0002) is cryptographically invalid on any other deployment.

---

### Proof of Concept

1. Deploy Clementine on testnet (Citrea chain_id=5655) and mainnet (Citrea chain_id=1) with the **same** `aggregator_verification_address` key.
2. On testnet, the aggregator signs a `WithdrawParamsWithSig` for `withdrawal_id=0`, producing `verification_signature = S`.
3. On mainnet, a deposit with `withdrawal_id=0` exists (sequential IDs collide naturally). The attacker submits the same `WithdrawParamsWithSig` with `verification_signature = S` to the mainnet operator's `withdraw` RPC.
4. `recover_address_from_ecdsa_signature::<OperatorWithdrawalMessage>` computes `eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN)` — identical on both networks because the domain has no chain_id — and recovers the same aggregator address.
5. The check `address_from_sig != address_in_config` passes. The operator calls `self.operator.withdraw(...)` and broadcasts a payout transaction on mainnet, transferring real BTC to the attacker's `output_script_pubkey`. [1](#0-0) [8](#0-7) [9](#0-8)

pub fn recover_address_from_ecdsa_signature<M: WithdrawalMessage + alloy_sol_types::SolStruct>(
    deposit_id: u32,
    input_signature: taproot::Signature,
    input_outpoint: OutPoint,
    output_script_pubkey: ScriptBuf,
    output_amount: Amount,
    signature: PrimitiveSignature,
) -> Result<alloy::primitives::Address, BridgeError> {
    let params = M::new(
        deposit_id,
        input_signature,
        input_outpoint,
        output_script_pubkey,
        output_amount,
    );

    let eip712_hash = params.eip712_signing_hash(&CLEMENTINE_EIP712_DOMAIN);

    let address = signature
        .recover_address_from_prehash(&eip712_hash)
        .wrap_err("Invalid signature")?;
    Ok(address)
}
