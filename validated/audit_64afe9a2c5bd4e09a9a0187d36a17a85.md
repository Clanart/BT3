### Title
Missing presence check on `enc_keys[&decryptor]` in `Decryption::decrypt_with_proof` allows a malicious participant to panic the DKG blame path — ([File: crypto/dkg/pedpop/src/encryption.rs](crypto/dkg/pedpop/src/encryption.rs))

### Summary
The kernel bug class is "field assumed non-NULL is attacker-controllable to NULL, causing a crash." The Serai analog is a map lookup assumed to always succeed: `Decryption::decrypt_with_proof` indexes `self.enc_keys[&decryptor]` where `decryptor` is a `Participant` value supplied inside an attacker-crafted accusation message (deserialized via `EncryptionKeyMessage::read` / `EncryptedMessage::read`, which are in-scope `read` entry points). `HashMap`'s `Index` impl panics on a missing key, so any accusation naming a `decryptor` participant who never registered an encryption key crashes the node processing the blame — the same unchecked-assumption → availability-loss shape as CVE-2025-21773.

### Finding Description
In `crypto/dkg/pedpop/src/encryption.rs`, `decrypt_with_proof` verifies the accuser-supplied DLEq proof against `self.enc_keys[&decryptor]`:

```rust
// crypto/dkg/pedpop/src/encryption.rs:381-390
if let Some(proof) = proof {
  proof
    .dleq
    .verify(
      &mut encryption_key_transcript(self.context),
      &[C::generator(), msg.key],
      &[self.enc_keys[&decryptor], *proof.key],
    )
    .map_err(|_| DecryptionError::InvalidProof)?;
```

`enc_keys` is only populated through `Decryption::register` (`encryption.rs:351-362`), which itself asserts `!self.enc_keys.contains_key(&participant)` — a second panic reachable by re-sending a registration message. Neither `read` path (`EncryptedMessage::read` at `encryption.rs:171-177`, `EncryptionKeyMessage::read` at `encryption.rs:57-59`) nor `decrypt_with_proof` validates that `decryptor` has a registered key before indexing. The `from`/`decryptor` participant values originate from bytes the accuser controls (the `EncryptionKeyProof` is optional and read with `EncryptionKeyProof::read` at `encryption.rs:267-269`).

The code "assumed `enc_keys[decryptor]` could never be absent" — exactly mirroring the etas_es58x assumption that `udev->serial` could never be NULL.

### Impact Explanation
An unprivileged DKG participant who is accused (or who crafts/forwards an accusation naming an arbitrary `decryptor`) causes a panic in the blame-resolution path of every node that evaluates it. This aborts DKG/share-blame processing and can halt threshold key generation or signing recovery — a remote denial of service matching the CVE's `A:H` impact. Because blame handling runs after the accuser's message is parsed, authentication of the message does not prevent reaching the panic; the attacker only needs a valid participant index that was never registered.

### Likelihood Explanation
Requires only that an attacker submit a blame/accusation referencing a `decryptor` participant absent from `enc_keys` — trivially satisfiable by naming any valid `Participant` index that didn't complete (or didn't send) an `EncryptionKeyMessage` registration, e.g. a participant who went offline mid-DKG, which is a common real-world condition.

### Recommendation
Replace the indexing with a checked lookup, mirroring the upstream fix ("add a check before accessing it"):

```rust
let enc_key = self
  .enc_keys
  .get(&decryptor)
  .ok_or(DecryptionError::InvalidProof)?;
```

and similarly return an error (or ignore) in `Decryption::register` instead of `assert!`ing on duplicate registration, since that assert is also reachable from a retransmitted peer message.

### Proof of Concept
```rust
// Setup: a Decryption context where only participant 2 registered an enc_key.
let mut dec = Decryption::<Ristretto>::new(context);
// participant 1 never calls dec.register(...)
// Attacker (any participant) submits an accusation whose decryptor = Participant(1)
// with some EncryptionKeyProof parsed via EncryptionKeyProof::read.
dec.decrypt_with_proof(faulty, Participant::new(1).unwrap(), msg, Some(proof));
// => thread panics at `self.enc_keys[&decryptor]` inside HashMap Index impl
//    before the DLEq is even evaluated.
```

Note: I was unable to fully trace the upstream call site of `decrypt_with_proof` within `crypto/dkg/pedpop/src/lib.rs` in the available iterations, so exact external invocation wiring is unverified — however the function's contract (attacker-supplied `decryptor` + optional proof) makes the panic reachable by construction.
