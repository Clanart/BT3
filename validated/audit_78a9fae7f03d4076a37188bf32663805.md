### Title

BIP-340 signatures are generated for the odd-Y group key instead of its even-Y x-only representative - (File: `networks/bitcoin/src/crypto.rs`)

### Summary

Serai’s Bitcoin FROST Schnorr wrapper normalizes the signature nonce parity but fails to normalize the group key parity required by BIP-340. When the threshold group key has an odd Y coordinate, the protocol internally verifies against that odd point, then emits only the x coordinate and adjusted `s` value. Bitcoin verification interprets that x coordinate as the even-Y point, equivalent to `-group_key`, so every emitted signature is invalid for approximately half of generated keys.

### Finding Description

`Hram::hram` computes the BIP-340 challenge from `x(R)`, `x(A)`, and the message, then conditionally negates the challenge when `R` is odd. [1](#0-0) 

`verify` asks the generic Schnorr algorithm to verify the original aggregate `sum` against the original `group_key`, and only afterward conditionally negates `s` when `R` is odd. [2](#0-1) 

No corresponding adjustment is made for `needs_negation(group_key)`. Consequently, for an odd `A`, the internally verified equation binds `a = dlog(A)`, while the emitted x-only signature must satisfy the BIP-340 equation for `a' = dlog(-A)`. The nonce-parity correction only converts `-r + c·a` into `r' + c·a`; it does not convert the signer scalar from `a` to `-a`.

The generic Schnorr implementation preserves this mismatch because it verifies `sG = R + cA` using the exact `group_key` point passed to it. [3](#0-2) 

### Impact Explanation

Any Bitcoin output controlled by an odd-Y FROST group key cannot be spent with signatures generated by this implementation. The threshold protocol can complete successfully and return a 64-byte signature, but Bitcoin’s BIP-340 verifier will reject it because the verifier derives the even-Y public key while the signature was produced for the odd-Y group key.

This can permanently render received funds unspendable unless the key set is recreated or the signing implementation accounts for the public-key parity correction. The failure affects roughly half of uniformly distributed secp256k1 group keys.

### Likelihood Explanation

The condition occurs naturally whenever the threshold key has odd Y parity, with probability approximately `1/2`. An attacker does not need special access beyond causing funds to be assigned to an affected key; deposit acceptance and later spending expose the defect.

### Recommendation

Apply BIP-340 public-key parity normalization consistently. Either:

- Transform the threshold signing secret into the scalar for `even_Y(group_key)` before producing shares, which requires negating each participant’s effective signing contribution when the group key is odd; or
- Change the FROST algorithm interface so `sign_share`, `verify_share`, and `verify` consistently use the effective even-Y secret/public key rather than only normalizing `R` and `s`.

At minimum, `verify` must not accept the internally generated signature unless it checks the equation against the BIP-340 even-Y representative. Add deterministic tests over both odd and even group keys and both odd and even aggregate nonces.

### Proof of Concept

Let `A` be an odd-Y group key and `a = dlog(A)`. BIP-340 verification uses the even-Y point `A' = -A`, whose discrete logarithm is `a' = -a`.

For an even nonce `R = rG`, Serai computes:

```text
c = H(x(R), x(A), m)
s = r + c·a
```

The emitted signature is `(x(R), s)`. Bitcoin expects:

```text
sG = R + c·A'
  = rG + c·(-aG)
  = (r - c·a)G
```

But Serai emits:

```text
sG = (r + c·a)G
```

These are equal only when `c·a = 0`, which occurs with negligible probability. Therefore, a valid internal FROST completion for an odd group key serializes to a BIP-340 signature that necessarily fails Bitcoin verification. The erroneous normalization point is the final conditional negation in `verify`, which handles `R` parity but not `A` parity. [4](#0-3)

    fn hram(R: &ProjectivePoint, A: &ProjectivePoint, m: &[u8]) -> Scalar {
      const TAG_HASH: Sha256 = Sha256::const_hash(b"BIP0340/challenge");

      let mut data = Sha256::engine();
      data.input(TAG_HASH.as_ref());
      data.input(TAG_HASH.as_ref());
      data.input(&x(R));
      data.input(&x(A));
      data.input(m);

      let c = Scalar::reduce(U256::from_be_slice(Sha256::from_engine(data).as_ref()));
      // If the nonce was odd, sign `r - cx` instead of `r + cx`, allowing us to negate `s` at the
      // end to sign as `-r + cx`
      <_>::conditional_select(&c, &-c, needs_negation(R))
    }
