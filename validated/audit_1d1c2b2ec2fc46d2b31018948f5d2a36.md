### Title
Governance-settable `Kip71GasTarget = 0` causes division-by-zero panic in KIP-71 base fee calculation - ([File: params/kip71_config.go])

### Summary
The KIP-71 dynamic base fee formula in `KIP71Config.NextMagmaBlockBaseFee` divides by the governance-controlled `GasTarget` parameter without checking for zero, unlike the sibling `BaseFeeDenominator` parameter which is explicitly guarded against a zero value.

### Finding Description
`NextMagmaBlockBaseFee` computes the fee delta as `parentBaseFee * gasUsedDelta / gasTarget / baseFeeDenominator` in both the "gas used above target" and "gas used below target" branches: [1](#0-0) [2](#0-1) 

The `BaseFeeDenominator` is defensively checked and replaced with a safe default (64) when zero: [3](#0-2) 

But `GasTarget` (`gasTarget := kc.GasTarget`) receives no such protection, and `y := x.Div(x, new(big.Int).SetUint64(gasTarget))` will panic with a Go `big.Int` "division by zero" runtime error if `gasTarget == 0` and `parentGasUsed != 0`.

The governance parameter registry confirms `Kip71GasTarget` uses `noopFormatChecker` (no validation), while the analogous `Kip71BaseFeeDenominator` explicitly rejects zero: [4](#0-3) 

This means governance can vote `governance.kip71.gastarget = 0` (a valid, in-scope governance parameter) and it will be accepted and applied without any bound check, unlike `BaseFeeDenominator`.

`NextMagmaBlockBaseFee` is invoked during header preparation/block assembly (`work/worker.go`), block verification (`blockchain/chain_makers.go`), and gas price oracle logic (`node/cn/gasprice/*`), all of which execute on every block after the Magma hardfork.

### Impact Explanation
Once `GasTarget` is set to 0 via governance and a block with non-zero `parentGasUsed` is produced, every node calling `NextMagmaBlockBaseFee` (block proposers computing the next block's base fee, and all nodes validating headers via `VerifyMagmaHeader`) will panic. This is a chain-halting Denial of Service affecting all full nodes and validators — not merely a resource-only issue, since it crashes the node process entirely on the very next block, causing state divergence/consensus halt.

### Likelihood Explanation
Requires a successful governance vote to set `governance.kip71.gastarget` to `0`, which is within the explicitly in-scope "governance parameters" attack surface. Given the value is only sanitized by `noopFormatChecker` (no bounds check), any governance proposal or malicious/misconfigured governing node/DAO vote could trigger this; there is no code-level barrier preventing the value from being accepted and persisted.

### Recommendation
Add a `FormatChecker` for `Kip71GasTarget` in `kaiax/gov/param.go` that rejects `v == 0`, mirroring the existing check on `Kip71BaseFeeDenominator`. Additionally, add a defensive zero-check inside `NextMagmaBlockBaseFee` (similar to the existing `BaseFeeDenominator` fallback) so a zero `GasTarget` cannot cause a panic even if it slips through elsewhere (e.g., genesis config, hardcoded chain config, or future governance code paths).

### Proof of Concept
1. Submit and pass a governance vote setting `governance.kip71.gastarget = 0` (accepted because `Kip71GasTarget`'s `FormatChecker` is `noopFormatChecker`): [5](#0-4) 
2. Once the new parameter set becomes active, the next block header/block production or verification triggers `NextMagmaBlockBaseFee(parentHeaderNumber, parentHeaderBaseFee, parentHeaderGasUsed)` with `parentHeaderGasUsed > 0`.
3. Inside the function, `parentGasUsed > gasTarget` (since `gasTarget == 0`), leading to:
```go
gasUsedDelta := new(big.Int).SetUint64(parentGasUsed - gasTarget)
x := new(big.Int).Mul(parentBaseFee, gasUsedDelta)
y := x.Div(x, new(big.Int).SetUint64(gasTarget)) // gasTarget == 0 → panic: division by zero
``` [6](#0-5) 
4. The Go runtime panics with "division by zero", crashing the node process on every node that processes/verifies the block (proposers, RPC gas price oracle callers, and validators), halting the chain.
