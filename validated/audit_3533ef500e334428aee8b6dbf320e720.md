Confirmed: `parse_withdrawal_sig_params` enforces `TapSighashType::SinglePlusAnyoneCanPay` on the withdrawal input signature [1](#0-0) . `SIGHASH_SINGLE` only commits the output at the *same index* as the signed input (index 0, the user payout output). It does **not** cover output index 2, the `OP_RETURN` output that carries the operator's x-only pubkey used to attribute who "fronted" the withdrawal [2](#0-1) . `ANYONECANPAY` additionally lets any party supply the funding input for output 0.

### Title
Payout OP_RETURN operator attribution is not committed by the user's signature, allowing front-running that mis-attributes/erases the fronting operator - (File: core/src/builder/transaction/operator_reimburse.rs, core/src/verifier.rs)

### Summary
The `payout_tx`'s `OP_RETURN` output, which the protocol uses as the sole source of truth for "which operator fronted this withdrawal," is never covered by the user's `SinglePlusAnyoneCanPay` signature. Any party who observes an operator's unconfirmed payout transaction in the mempool can replace the funding input and rewrite the `OP_RETURN` payload before it confirms, breaking the binding `operator credited == operator that paid`.

### Finding Description
`operator.rs::withdraw()` builds the payout transaction via `create_payout_txhandler`, embedding the operator's own x-only pubkey in an `OP_RETURN` output at index 2 [3](#0-2) [4](#0-3) . The only cryptographic commitment on the transaction is the user's `taproot::Signature` over input 0, enforced to use `SinglePlusAnyoneCanPay` [1](#0-0) . Under `SIGHASH_SINGLE`, the signature commits only to the output at the same index as the signed input (output 0, the user's payout), while `ANYONECANPAY` means other inputs (i.e., whoever funds output 0 via `fund_raw_transaction`/CPFP) are unconstrained and unsigned by the user [5](#0-4) . Consequently, the `OP_RETURN` output and the funding input are entirely mutable by any third party who observes the not-yet-confirmed transaction, since Bitcoin taproot key-path spends do not otherwise link unrelated outputs to the signed input under `SIGHASH_SINGLE`.

Downstream, `verifier.rs::update_finalized_payouts` trusts the on-chain `OP_RETURN` bytes as authoritative proof of which operator "fronted" the withdrawal, storing `operator_xonly_pk` from parsed `OP_RETURN` data with no additional authentication [6](#0-5) . This value later gates which operator's `PayoutCheckerTask` is allowed to claim reimbursement, via `get_first_unhandled_payout_by_operator_xonly_pk` filtering strictly on `payout_payer_operator_xonly_pk` [7](#0-6) , and `validate_payer_is_operator` / `handle_finalized_payout` used by `get_reimbursement_txs` [8](#0-7) .

An unprivileged party can:
1. Observe an honest operator O's unconfirmed `payout_tx` (which funds the withdrawal output with O's own money) in the mempool.
2. Construct a conflicting/RBF transaction spending the same withdrawal dust input, keeping output 0 (the user payout, protected by `SIGHASH_SINGLE`) identical, but supplying their own funding input and rewriting the `OP_RETURN` output to point to a different or invalid operator pubkey.
3. Get this alternate transaction confirmed first (e.g., with a higher fee / RBF).

If the attacker sets the `OP_RETURN` to an invalid/garbled value, `operator_xonly_pk` parses to `None` [9](#0-8) ; the withdrawal is then permanently unattributable to any operator, since `get_first_unhandled_payout_by_operator_xonly_pk`'s query can never match a `NULL` `payout_payer_operator_xonly_pk`. The honest operator O, who genuinely fronted the funds, can never automatically or manually trigger reimbursement (`get_reimbursement_txs` relies on `validate_payer_is_operator` finding O as payer). If the attacker instead names a different real operator P (who paid nothing), operator P's own `PayoutCheckerTask` will pick up the payout as "its own" and proceed through `handle_finalized_payout` to claim reimbursement it never funded.

### Impact Explanation
This breaks the custody binding "the operator credited versus the party that paid." Two concrete outcomes map to Critical severity per the defined impact categories: an honest operator (O) can be made permanently unable to be reimbursed for a real payout it fronted, or a different operator (P) can be reimbursed for a payout it never funded, at O's expense.

### Likelihood Explanation
The attack requires only mempool visibility and the ability to submit a conflicting/higher-fee transaction — no verifier, operator, watchtower, or key-compromise role is needed. The withdrawal dust input and `SinglePlusAnyoneCanPay` scheme are both public once the honest operator's payout transaction is broadcast (visible in the mempool prior to confirmation), which is a standard, expected occurrence in the withdrawal flow.

### Recommendation
Bind the `OP_RETURN` operator-attribution output to the user's signature (e.g., by using `SIGHASH_ALL` or a Single output index scheme that also commits to the OP_RETURN output, or by moving operator identity into an input/witness that is itself signed and verifiable), so that the operator credited as payer cannot be altered by any party other than the one whose funding input actually satisfies the payout.

### Proof of Concept
1. Operator O calls `withdraw()`/`internal_withdraw()`, producing a valid, unconfirmed `payout_tx` with input 0 = user's dust UTXO (signed `SinglePlusAnyoneCanPay`), output 0 = user payout (funded by an additional O-owned input added via `fund_raw_transaction`), output 2 = `OP_RETURN(O_xonly_pk)` [10](#0-9) .
2. Attacker observes this transaction in the mempool, copies input 0 and output 0 verbatim (both are protected by the `SIGHASH_SINGLE` commitment and thus unmodifiable), replaces O's funding input with their own funding input of equal value, and replaces the `OP_RETURN` payload with arbitrary/garbled bytes (or another operator's pubkey).
3. Attacker broadcasts this transaction with a higher fee (RBF) so it confirms instead of O's.
4. `update_finalized_payouts` parses the confirmed transaction's `OP_RETURN`, finds `operator_xonly_pk = None` (or a different operator), and persists this attribution [6](#0-5) .
5. O's `PayoutCheckerTask` never finds this payout under its own key via `get_first_unhandled_payout_by_operator_xonly_pk` and can never claim reimbursement for the funds it fronted, despite having genuinely paid the user.
