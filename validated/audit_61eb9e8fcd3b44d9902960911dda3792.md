### Title
`resolveWithin()` uses a raw string-prefix check instead of a path-boundary check, allowing sandbox escape to sibling directories - ([File: app/src/lib/path.ts])

### Summary
The external report's root cause is a boundary check that compares a value against the *wrong reference point*, making the check always pass when it shouldn't (`(anchorPrice - minPrice) / minPrice` instead of `/ anchorPrice`). The equivalent broken-invariant pattern exists in GitHub Desktop's path-containment guard `resolveWithin()`: instead of verifying that a resolved path is *inside* a root directory (root + path separator, or exact equality), it only checks that the resolved path's string **starts with** the root path string. A sibling directory whose name happens to share the root directory name as a prefix (e.g. `repo` vs `repo-secrets`) will incorrectly pass the "is within root" check.

### Finding Description
`_resolveWithin()` in [1](#0-0)  resolves a path and then validates containment using:

```js
return realResolved.startsWith(realRoot) ? resolved : null
``` [2](#0-1) 

This is a plain string `startsWith` comparison with **no trailing separator check**. If `realRoot` is `/Users/victim/Documents/GitHub/repo` and an attacker-influenced relative segment resolves to `/Users/victim/Documents/GitHub/repo-secrets/token.txt`, the check `realResolved.startsWith(realRoot)` evaluates to `true` even though `repo-secrets` is a completely different, sibling directory — not a subdirectory of `repo`. The correct invariant (analogous to using `anchorPrice` instead of `minPrice` in the report) would be to check `realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)`.

This helper is treated as a security boundary and is called directly with attacker-influenced input in at least two places:
- `app/src/ui/dispatcher/dispatcher.ts` `openRepositoryFromUrl()`, which resolves the `filepath` query parameter taken directly from an `x-github-desktop://openRepo?...&filepath=...` deep link that the user clicks, and then calls `shell.showItemInFolder(resolved)` on the result: [3](#0-2) . The `filepath` value originates from `parseAppURL()` in [4](#0-3) , which performs no validation on `filepath` beyond passing it through — it is fully attacker controlled via the deep link.
- `app/src/lib/copilot-conflict-context.ts`, which uses `resolveWithin(workingDirectory, file.path)` as the sole guard "against path traversal and symlink escapes" before reading file content into an AI context: [5](#0-4) .

The existing guard against absolute paths (`isAbsolute(filepath)` check right before `resolveWithin` is called in `dispatcher.ts`) does not stop this path, because the traversal is achieved via relative segments (e.g., `../repo-secrets/file`) resolved against the root, not via a literal absolute path.

### Impact Explanation
An attacker who controls a deep link (`x-github-desktop://openRepo?...&filepath=..%2F..%2Fsome-sibling-dir%2Fsecret.file`) that the victim clicks, where the victim's local "Documents/GitHub" (or wherever the repo lives) also happens to contain — or can be made to contain via a related crafted clone — a directory whose name is a prefix-extension of the target repo's directory name, can cause Desktop to reveal/open a file outside the intended repository boundary via `shell.showItemInFolder`. The same broken check is also depended on by the Copilot conflict-resolution feature to keep file reads confined to the repository working directory before sending content to an external model; a bypass here means file content outside the intended repo directory could be read and exfiltrated to the AI backend. This matches the "read outside the repo" and "attacker controls a link the user clicks" categories in the Valid Impact list.

### Likelihood Explanation
Exploitation requires: (1) the victim clicking an attacker-supplied `x-github-desktop://` link (a normal, low-friction user action Desktop explicitly supports and no local/admin access is required), and (2) a naming coincidence/collision between the repository's directory name and a sibling directory. The naming-collision precondition lowers real-world likelihood somewhat, but it is not impossible to arrange in common cloning layouts (e.g., cloning `repo` and `repo-backup`, `repo` and `repo.bak`, or numbered/duplicate clone folders that Desktop itself can create when cloning into an existing non-empty directory), and no additional attacker capability beyond a clickable link is required.

### Recommendation
Change the boundary check in `_resolveWithin()` (`app/src/lib/path.ts`) from a raw prefix check to an exact-or-separator-bounded check:

```js
return realResolved === realRoot || realResolved.startsWith(realRoot + Path.sep)
  ? resolved
  : null
```

Use the platform-appropriate separator from the passed-in `options` (`Path.sep` equivalent for `Path.win32`/`Path.posix`) rather than the default `Path` module, to keep behavior consistent with `resolveWithinPosix`/`resolveWithinWin32`.

### Proof of Concept
1. Victim has cloned a GitHub Desktop repository at `/Users/victim/Documents/GitHub/repo` and, coincidentally or due to a prior duplicate-clone, also has `/Users/victim/Documents/GitHub/repo-secrets/token.txt` on disk.
2. Attacker sends the victim a link: `x-github-desktop://openRepo?url=https://github.com/owner/repo&filepath=..%2Frepo-secrets%2Ftoken.txt`.
3. Desktop's `parseAppURL()` extracts `filepath = "../repo-secrets/token.txt"` unmodified [4](#0-3) .
4. `openRepositoryFromUrl()` passes this to `resolveWithin(repository.path, filepath)` [6](#0-5) .
5. Inside `_resolveWithin`, `resolved = Path.resolve("/Users/victim/Documents/GitHub/repo", "../repo-secrets/token.txt")` = `/Users/victim/Documents/GitHub/repo-secrets/token.txt`. The check `realResolved.startsWith(realRoot)` evaluates `"...GitHub/repo-secrets/token.txt".startsWith("...GitHub/repo")` → `true`, so the function returns the path instead of `null`.
6. `shell.showItemInFolder(resolved)` opens/reveals `token.txt`, a file entirely outside the intended repository directory.

**Uncertainty**: I could not fully confirm from the index whether Desktop's clone flow ever creates directory names that collide as prefixes in normal usage (e.g., "clone into existing non-empty directory" behavior) — this affects the practical likelihood of the naming-collision precondition, and a full assessment would need to inspect the clone-target directory-naming logic and dialog flows more closely.
