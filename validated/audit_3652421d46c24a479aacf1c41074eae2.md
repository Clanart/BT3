### Title
Malicious `post-commit` git hook can spoof a fake `[branch sha]`/diffstat line in Bash stdout, diverting `_COMMIT_SHA_RE`-based commit review away from the real (malicious) commit - ([File: plugins/security-guidance/hooks/security_reminder_hook.py])

### Summary
`handle_commit_review_posttooluse` determines `commit_succeeded` and the SHA to review purely from text pattern-matching (`_COMMIT_SHA_RE` + `_COMMIT_DIFFSTAT_PATTERNS`) over the combined stdout/stderr of the `git commit` Bash invocation, and picks the *last* `[branch sha]`-shaped match as authoritative. Because git hooks (e.g. `post-commit`) run inside the same process and their stdout is interleaved into the exact same captured output stream after git's own commit line, an attacker who controls a repo-level hook (via a committed `.git/hooks` script or a repo-tracked `core.hooksPath`) can print a fabricated `[branch fakesha]` line plus fake diffstat text (e.g. `1 file changed`) that appears after the genuine commit line, causing the reviewer to `git show`/`git diff` a different (real, but pre-existing, benign) SHA instead of the just-created malicious commit.

### Finding Description
The relevant logic: [1](#0-0) 
`_COMMIT_SHA_RE` is a line-anchored, multiline regex (`^\[[^\]]*?\b([0-9a-f]{7,40})\]`) matched against `stdout + "\n" + stderr`, and `_COMMIT_DIFFSTAT_PATTERNS` requires git-only diffstat markers to also be present.

`commit_succeeded` is computed as: [2](#0-1) 

When choosing which SHA(s) to review, the code explicitly takes only the **last** regex match under the stated assumption that "the real commit line is always last in git's own output": [3](#0-2) 

This assumption holds for `pre-commit`/`husky`/`lint-staged` hook output (which runs *before* git prints its own `[branch sha]` line, so any decoy naturally precedes the real line). However, it does **not** hold for a `post-commit` hook, which git invokes *after* it has already written the `[branch sha]` summary line to stdout. A `post-commit` hook script fully controlled by the attacker (committed into the repo if `core.hooksPath` points to a repo-tracked directory, a common team setup, or otherwise present in `.git/hooks`) can simply `echo` a bracketed line such as `[main 0000000] decoy` together with a line matching one of `_COMMIT_DIFFSTAT_PATTERNS` (e.g. `" 1 file changed, 1 insertion(+)"`), appearing textually after the real commit line. Since `_COMMIT_SHA_RE.findall` is used and only `all_shas[-1]` is kept, this fabricated trailing entry overrides the genuine SHA.

Downstream, the code resolves the SHA with `git show -p <sha>` and only proceeds if `returncode == 0`: [4](#0-3) 
If the attacker picks a SHA of a real, already-existing benign commit (e.g., an ancestor of `HEAD`, easily known/guessable from local history), `git show` succeeds and the review pipeline analyzes that benign diff instead of the actual new/malicious commit. The genuine malicious commit is never diffed or sent to `analyze_code_security`/`agentic_review`, so no vulnerability findings are raised, while the attacker-controlled commit remains on `HEAD` and can subsequently be pushed by `/commit` without ever having been reviewed.

The reflog-fallback path (`_git_reflog_recent_commits`) does not help here because it only activates when `commit_succeeded` is `False`; the fabricated diffstat+bracket line makes `commit_succeeded` evaluate to `True`, so the authoritative reflog corroboration is never consulted, and the spoofed SHA is trusted directly.

Additionally, this spoofed (but real, pre-existing) SHA gets persisted via `_append_reviewed_shas`, which could affect the push-sweep's reviewed-commit bookkeeping for that ancestor SHA, though the primary and clearly demonstrable impact is the skipped review of the actual new commit.

### Impact Explanation
This allows an attacker who controls repository-level git hook configuration (a plausible artifact-injection vector: a malicious `post-commit` hook committed to a shared hooks directory referenced by `core.hooksPath`, or planted by a prior compromised session) to make `/commit`'s automated security review silently analyze the wrong (benign) commit while the actual malicious commit — potentially containing injected secrets, backdoors, or exfiltration code — is created, left as `HEAD`, and can be pushed without triggering the intended LLM-based commit review. This matches the "secret/vulnerability exfiltration into pushed history without triggered review" impact category: a trust-boundary bypass of the review-binding invariant (the reviewed SHA must correspond to the actual commit produced).

### Likelihood Explanation
Requires the attacker to have already placed a crafted git hook (`post-commit`, or any hook invoked between the actual commit creation and the tool call returning) that is executed as part of the victim's `git commit` invocation — e.g., via a repo-tracked `core.hooksPath` config accepted from a cloned repository, a shared hook script in a monorepo, or a supply-chain-planted hook. This is consistent with the stated precondition ("attacker controls repo-level git hooks or commit message templates that alter stdout formatting"). No admin/maintainer privilege on the victim machine is needed beyond the ability to have a hook execute during `git commit`, which is a realistic scenario in shared-hooks/monorepo setups or after a prior weaker compromise. The exploit is deterministic and repeatable given hook execution — it does not depend on timing races.

### Recommendation
Do not trust the *last* bracketed SHA match unconditionally. Instead:
1. Independently corroborate any bracket-derived SHA against `git rev-parse HEAD` (or the reflog `HEAD@{0}`) captured at the time of the tool call, and only accept the parsed SHA if it matches (or is a prefix of) the actual current `HEAD`.
2. When multiple `[bracket sha]` matches are found, prefer the one that verifiably corresponds to `HEAD`, not simply the last one positionally, since hook output ordering can be attacker-influenced for `post-commit`/`post-merge` style hooks that run after git's own output.
3. Consider stripping/ignoring hook-generated stdout on the review path where possible (e.g., by using `--no-verify` semantics only for detection purposes, or explicitly running the diffstat check against `git show`/`git log` output freshly queried from the repo, rather than trusting embedded process stdout).

1. Set up a temp git repo with two commits: `benign_sha` (older, innocuous) and `malicious_sha` (new, contains a hardcoded secret / vulnerable pattern), with `malicious_sha` at `HEAD`.
2. Simulate a `git commit` invocation whose real stdout is `"[main <malicious_sha_abbrev>] msg\n 1 file changed, 3 insertions(+)"`, then append attacker-controlled `post-commit` hook output: `"[main <benign_sha_abbrev>] decoy\n 1 file changed, 1 insertion(+)"`.
3. Feed this combined string as `tool_response.stdout` into the handler (or directly test `_COMMIT_SHA_RE.findall` + the `shas = [all_shas[-1]]` selection logic).
4. Assert that today's code selects `benign_sha_abbrev` (the decoy) instead of the true `git rev-parse HEAD` value (`malicious_sha`) — demonstrating the mismatch between the SHA used for review and the actual `HEAD` produced by the invocation.
5. Extend the test to run the full handler against the two-commit fixture repo and assert that `analyze_code_security`/`agentic_review` is invoked with `benign_sha`'s diff, not `malicious_sha`'s diff, confirming the vulnerable commit is never analyzed while `commit_succeeded` remains `True` and no `skip_reason` metric is emitted.

# git-only signals that corroborate a real commit object — NOT emitted by
# pre-commit / lint-staged / husky hook output, which can contain bracketed
# labels like `[pre-commit abc1234]` that otherwise look like a commit line.
_COMMIT_DIFFSTAT_PATTERNS = [
    re.compile(r'\b\d+ files? changed'),
    re.compile(r'^ create mode ', re.MULTILINE),
    re.compile(r'^ delete mode ', re.MULTILINE),
    re.compile(r'^ rename ', re.MULTILINE),
]

# Capture-group form of the [branch sha] pattern. Mirrors Claude Code's own
# commit-id parsing, but tolerates spaces before the
# sha (covers `[detached HEAD abc1234]`). 7–40 hex chars: git's abbrev floor
# through full sha; the abbrev resolves fine with `git show`. Anchored to
# line-start so a `[hex]` in the commit subject (`[main abc] Revert [e38]`)
# or trailing hook output isn't picked up and fed to `git show`.
_COMMIT_SHA_RE = re.compile(r'^\[[^\]]*?\b([0-9a-f]{7,40})\]', re.MULTILINE)

# Regex matching `git commit` commands. Mirrors Claude Code's own commit
# detection — it does NOT tolerate `git -c k=v commit` global options, which
# keeps this hook aligned with CC's commit attribution on what counts as a
# commit.
_GIT_COMMIT_RE = re.compile(r'\bgit\s+commit(?:\s|$)')
