### Title
Auction bid tampering via signature-scope mismatch: `MaxGasPrice` excluded from EIP-712 commitment (V2) - ([File: kaiax/auction/eip712.go])

### Summary
Kaia's auction/bid module signs a `Bid` with two independent signatures — a searcher EIP-712 signature over `BidData` and an auctioneer signature over the *searcher signature bytes*. For the `AuctionVersionV2` typehash, the EIP-712 struct definition and its `EncodeData()` implementation omit the `MaxGasPrice` field entirely, so that field is never cryptographically bound by either signature. This mirrors the "multiple root elements" class of bug in the referenced advisory: verification is performed over one representation of the data (the V2 typed struct / the raw `SearcherSig` bytes) while a different, unauthenticated field (`MaxGasPrice`) is present in and later consumed from the same object.

### Finding Description
The V2 EIP-712 type string used for searcher-signature verification excludes `maxGasPrice`: [1](#0-0) 

Correspondingly, `Bid.EncodeData()` (the V2 encoder invoked by `GetHashTypedData` when `version == AuctionVersionV2` or unknown) never serializes `b.MaxGasPrice` into the struct hash that the searcher signs: [2](#0-1) 

Only the newer `bidV3.EncodeData()` path includes `maxGasPrice`: [3](#0-2) 

The searcher signature is validated with `ValidateSearcherSig`, which just recomputes `GetHashTypedData` and recovers the signer — it inherits whichever field set the selected version encodes: [4](#0-3) 

The auctioneer signature is validated separately and independently of `BidData` — it only commits to the raw `SearcherSig` byte blob via a personal-sign digest, never touching `BidData` fields (including `MaxGasPrice`) directly: [5](#0-4) [6](#0-5) 

Both checks are invoked together in `validateBidSigs`, which is the sole signature gate before a bid is admitted to the pool: [7](#0-6) 

Because neither signature check depends on `b.MaxGasPrice` when the bid is processed under the V2 typehash, any party that can observe a validly-signed V2 bid in transit (over the bid-gossip network reachable by `HandleBid`, or via a public RPC bid-submission endpoint) can rewrite `MaxGasPrice` to an arbitrary value and re-submit it: both `ValidateSearcherSig` and `ValidateAuctioneerSig` will still pass because the signature scope simply does not cover that field, exactly analogous to the SAML "verify one element, act on another" root-cause pattern. [8](#0-7) 

### Impact Explanation
`MaxGasPrice` is part of `BidData` and is presumably consulted during bid settlement/gas accounting for the auction (fee cap enforcement for the winning bid's execution). Since it is not bound by either signature for V2 bids, an attacker who intercepts or relays a legitimately signed bid can alter the fee cap the searcher/auctioneer actually agreed to, without invalidating the cryptographic proof of authorization. This can lead to fee/fee-delegation abuse or incorrect settlement (e.g., forcing a lower or higher effective gas price than what the searcher and auctioneer actually authorized), which the pool would accept as validly signed.

### Likelihood Explanation
Any unprivileged network participant that can observe bid traffic (bid gossip is handled via `HandleBid`, reachable by peer IDs, and likely via public bid-submission RPC) can perform this mutation without any special privileges — it requires only re-broadcasting a modified copy of an already-signed bid. The V2 path is the default/fallback path in `GetHashTypedData` (`else { structHash = EncodeEIP712(b) }`), so it is not a corner case reachable only under unusual configuration; any deployment or bid still using `AuctionVersionV2` (or an unrecognized version string, which also falls back to the V2 encoder) is exposed. I was not able to fully confirm the exact downstream usage of `MaxGasPrice` in settlement code within the tool budget available, so the precise value-movement impact should be validated against the settlement/gas-accounting code path before treating this as fully proven end-to-end.

### Recommendation
Include `MaxGasPrice` in the V2 EIP-712 struct type and `EncodeData()` (or deprecate/reject V2 bids that carry a non-zero `MaxGasPrice`), and/or have the auctioneer signature commit to the full `BidData` hash (not just the `SearcherSig` bytes) so that no field of a `Bid` can be altered post-signature without invalidating both signatures.

### Proof of Concept
1. Attacker observes a validly signed V2 `Bid` (`SearcherSig`, `AuctioneerSig` both valid) propagating on the bid-gossip channel or a public RPC endpoint.
2. Attacker copies the bid, changes `BidData.MaxGasPrice` to an arbitrary value, and leaves `SearcherSig`/`AuctioneerSig` unchanged.
3. `bp.validateBidSigs(bid)` still passes because:
   - `ValidateSearcherSig` recomputes `GetHashTypedData` using V2's `EncodeData()`, which never serializes `MaxGasPrice`, so the digest — and thus the recovered signer — is unaffected by the tampering.
   - `ValidateAuctioneerSig` only checks a signature over `b.SearcherSig` bytes, which are also unaffected.
4. The tampered bid (with attacker-chosen `MaxGasPrice`) is accepted into the pool as if fully authorized by both the searcher and the auctioneer.

func (b *Bid) ValidateSearcherSig(chainId *big.Int, verifyingContract common.Address, version string) error {
	if chainId == nil {
		return ErrNilChainId
	}

	if common.EmptyAddress(verifyingContract) {
		return ErrNilVerifyingContract
	}

	digest := b.GetHashTypedData(chainId, verifyingContract, version)

	recoveredSender, err := getSigner(b.SearcherSig, digest)
	if err != nil {
		return fmt.Errorf("failed to recover searcher sig: %v", err)
	}

	if recoveredSender != b.Sender {
		return fmt.Errorf("invalid searcher sig: expected %v, calculated %v", b.Sender.String(), recoveredSender.String())
	}

	return nil
}

func (bp *BidPool) validateBidSigs(bid *auction.Bid) error {
	bp.auctionInfoMu.RLock()
	defer bp.auctionInfoMu.RUnlock()

	if bid.SearcherSig == nil || len(bid.SearcherSig) != crypto.SignatureLength {
		return auction.ErrInvalidSearcherSig
	}
	if bid.AuctioneerSig == nil || len(bid.AuctioneerSig) != crypto.SignatureLength {
		return auction.ErrInvalidAuctioneerSig
	}

	// Verify the EIP712 signature.
	if err := bid.ValidateSearcherSig(bp.ChainConfig.ChainID, bp.auctionEntryPoint, bp.auctionEntryPointVersion); err != nil {
		return err
	}

	// Verify the auctioneer signature.
	if err := bid.ValidateAuctioneerSig(bp.auctioneer); err != nil {
		return err
	}

	return nil
}
