## Analysis

The external report's core broken invariant is: **a trader can mutate shared pool/order state immediately before their real trade so that a fee/slippage mechanism that should apply to their transaction is bypassed, letting them capture value that should be shared with the protocol/other stakeholders.**

The closest local analog is in the Intent Gateway's same-chain partial-fill surplus split. Surplus (solver overpayment above what the order requires) is supposed to be split between the beneficiary and the protocol via `surplusShareBps`. But that split is gated on the fill being the **very first** fill of the output-token pair (`alreadyFilled == 0`), exactly as documented: "Surplus only applies on the first fill of each output token pair." [1](#0-0) 

Any unprivileged solver can permanently disable that gate for an order by submitting a trivial dust partial-fill first, then completing the fill afterward — the identical "pre-position state, then execute the real trade" pattern from the external report.

### Title
Same-chain partial-fill surplus split can be permanently disabled by a dust front-fill - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents._fillSameChain` only computes and splits solver-overpayment "surplus" with the beneficiary/protocol when `alreadyFilled == 0`, i.e., only on the literal first fill ever recorded for that `(commitment, outputToken)` pair. [2](#0-1) 

Because `_partialFills[commitment][outputToken]` is monotonically increasing and world-readable/callable by anyone (solver selection is optional and off by default), any solver can submit an arbitrarily small dust fill (e.g., 1 wei of the output token) before the real fill. This sets `alreadyFilled != 0`, which permanently routes every subsequent fill of that pair into the `else` branch — the one with no surplus computation at all: [3](#0-2) 

### Finding Description
The surplus-split logic exists specifically to prevent a solver from pocketing 100% of an overpayment that should be shared with the beneficiary and protocol (`surplusShareBps`), mirroring the exact concern in the external report — a fee/spread that is supposed to accrue to the pool/protocol being captured entirely by the trader who manipulates the state first. Here:

1. The `if (alreadyFilled == 0 && solverAmount > totalRequired)` condition is the *only* code path that computes `dust`, `protocolShare`, and `beneficiaryShare`.
2. `alreadyFilled` is read from `_partialFills[commitment][outputToken]`, storage that is written on every call to `fillOrder` for a same-chain order, by any caller (no access control on `fillOrder` itself beyond solver-selection, which most deployments have disabled per the tests using `solverSelection: false`).
3. Once any fill — even 1 wei — has landed for a pair, `alreadyFilled` is nonzero for the rest of that order's lifetime, and the transferred amount in every later fill is capped at `remaining` (`fillAmount = solverAmount > remaining ? remaining : solverAmount`), with `beneficiaryShare = protocolShare = 0` hard-coded for that path.
4. A solver who intends to complete the order with genuine surplus can trivially pre-empt their own large fill with a self-submitted dust fill, guaranteeing the surplus-split branch is unreachable when they later complete the order, and keep any value above `totalRequired` (since they are never obligated to transfer more than `remaining`) instead of contributing it to `beneficiaryShare`/`protocolShare` as `DustCollected`.

This is the direct structural analog of the report's "add liquidity, trade, remove liquidity" trick: mutate shared per-order state ahead of the real settlement action to disable a fee/split mechanism that is supposed to apply to that settlement.

### Impact Explanation
This lets an ordinary, unprivileged solver deterministically evade the protocol's `surplusShareBps` fee-sharing invariant on same-chain orders, redirecting value that the contract's own accounting logic (`DustCollected`, `protocolShare`) is designed to route to the protocol treasury and the order's beneficiary. It is a logic attack on fee/value distribution reachable through the public `fillOrder` entrypoint with no privileged role, malicious relayer, or governance actor required — matching the bounty's "logic attacks" / "transaction manipulation" category.

### Likelihood Explanation
High. `fillOrder` is a fully public entrypoint for same-chain orders in the default configuration (`solverSelection: false`, as used throughout the test suite), and the two calls required (dust fill, then completion fill) are ordinary sequential transactions from the same or coordinated accounts — no front-running, relayer collusion, or privileged access needed.

### Recommendation
Compute and enforce the surplus split based on cumulative overpayment across the whole fill history of the pair, not solely on whether it is the very first recorded fill. E.g., track `totalPaid` per pair and compute `dust = totalPaid + solverAmount - totalRequired` (clamped ≥ 0) on every fill, splitting the incremental dust each time, so an attacker cannot escape the split by seeding a prior nonzero `alreadyFilled` value.

### Proof of Concept
Given a same-chain order: `totalRequired = 900e18` DAI, `surplusShareBps = 5000` (50%):

1. Attacker (solver) calls `fillOrder(order, {outputs: [{token: DAI, amount: 1}]})`. `alreadyFilled == 0` but `solverAmount(1) > totalRequired` is false → goes to `else` branch, `fillAmount = 1`, `_partialFills[commitment][DAI] = 1`. No surplus logic ever ran. [4](#0-3) 
2. Attacker calls `fillOrder` again with `outputs: [{token: DAI, amount: remaining + N}]` for any `N > 0`. Now `alreadyFilled = 1 != 0`, so the surplus branch is skipped unconditionally: `fillAmount = min(solverAmount, remaining) = remaining`, `beneficiaryShare = protocolShare = 0`. [5](#0-4) 
3. The order completes as fully filled (`isFullyFilled = true`), `_execute`/`OrderFilled` fire, but no `DustCollected` event is ever emitted and neither the protocol treasury nor the beneficiary receive any surplus share for this order — contrary to the documented and tested 50/50 (or configured) split behavior for a genuine first/only fill (compare with `testSurplusSplitBetweenBeneficiaryAndProtocol`, which shows the intended split when `alreadyFilled` starts at 0 and stays 0 through completion). [6](#0-5)

    function testSurplusSplitBetweenBeneficiaryAndProtocol() public {
        // Test 50/50 split: solver provides 2100 DAI, user gets 2050, protocol gets 50
        IntentGatewayV2 customGateway = _deployGatewayProxy();
        Params memory customParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: false,
            surplusShareBps: 5000, // 50% to protocol, 50% to beneficiary
            protocolFeeBps: 0,
            priceOracle: address(0)
        });
        customGateway.initialize(customParams, new bytes[](0));

        uint256 solverOutputAmount = 2100 * 1e18;

        // Setup order
        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 2000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(uint256(uint160(user))),
            source: abi.encodePacked(host.host()),
            destination: abi.encodePacked(host.host()),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(customGateway), 1000 * 1e6);
        customGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Filler fills order with surplus
        vm.startPrank(filler);
        dai.approve(address(customGateway), 2200 * 1e18); // Approve surplus + fees

        TokenInfo[] memory outputs = new TokenInfo[](1);
        outputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: solverOutputAmount});

        uint256 userDaiBalanceBefore = dai.balanceOf(user);

        vm.recordLogs();
        customGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, outputs: outputs}));
        vm.stopPrank();

        // Verify beneficiary received 2050 DAI (2000 + 50% of 100 surplus)
        assertEq(dai.balanceOf(user) - userDaiBalanceBefore, 2050 * 1e18, "Beneficiary gets 50% surplus");

        // Verify protocol received 50 DAI (50% of 100 surplus)
        assertEq(dai.balanceOf(address(customGateway)), 50 * 1e18, "Protocol gets 50% surplus");

        // Verify DustCollected event
        Vm.Log[] memory entries = vm.getRecordedLogs();
        bool found = false;

            }
        }
