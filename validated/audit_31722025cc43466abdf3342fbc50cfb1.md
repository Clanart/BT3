## Finding: Confirmed — Integer division truncation to zero in `convert_to_balance` silently drops bridged funds with no refund

### Title
Dust-amount cross-chain transfers truncate to zero and settle successfully, permanently burning sender funds with no refund - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` performs an unchecked integer division that can round a nonzero ERC20 amount down to `0` when `erc_decimals > local_decimals`, and `on_accept` treats this as a successful, final settlement.

### Finding Description
`convert_to_balance` scales an ERC20 `U256` amount down to local balance precision by dividing by `10^(erc_decimals - local_decimals)`: [1](#0-0) 

`register_token`/`update_token` only enforce `erc_decimals >= local_decimals`, never the reverse, so this division is legal and common in production (e.g. an 18-decimal EVM token bridging to a 10/12-decimal Substrate asset): [2](#0-1) 

On the EVM source side, `send()` unconditionally burns `params.amount` from the caller before dispatching the POST request — the burn is not gated on whether the destination can represent that value at its precision: [3](#0-2) 

On the Substrate destination side, `on_accept` converts `message.amount` via `convert_to_balance`. If `message.amount < 10^(erc_decimals - local_decimals)`, the division truncates to `0`, which still parses successfully as a valid balance (`"0".parse::<Balance>()` succeeds), so no error is raised: [4](#0-3) 

`on_accept` then proceeds to transfer/mint `amount = 0` to the beneficiary, emits `TokenReceived` with `amount: 0`, and returns `Ok(...)` — meaning the ISMP request commitment is consumed as successfully processed: [5](#0-4) [6](#0-5) 

Because `on_accept` returns `Ok`, the request is fulfilled from the ISMP host's perspective, so the timeout/refund path (`on_timeout`, which re-mints `message.from` on the EVM side or refunds on the Substrate side) never fires. The tokens already burned on the source chain are gone with nothing credited on the destination.

### Impact Explanation
This breaks the invariant that settlement must credit an amount proportional to the burned/escrowed value. Any cross-chain transfer whose EVM-side raw amount is smaller than `10^(erc_decimals - local_decimals)` burns real value on the source chain while crediting exactly zero on the destination, and the request is marked as accepted/fulfilled so no refund mechanism ever triggers. This matches the "wrong amount" / "loss of funds" / "broken refund accounting" impact categories in scope.

### Likelihood Explanation
Any unprivileged caller of `send()` on the EVM `HyperFungibleToken` contract can trigger this simply by choosing a sufficiently small `amount` relative to the configured decimal gap — no privileged operator or malicious relayer is required. The precondition (`erc_decimals > local_decimals`) is an explicitly supported, common configuration (the pallet's own benchmarks use `EVM_DECIMALS = 18` vs `LOCAL_DECIMALS = 12`).

### Recommendation
`convert_to_balance` should reject (return an error) rather than silently produce `0` when the input value is nonzero but its scaled-down representation would be zero (i.e., `value != 0 && value / scale == 0`), causing `on_accept` to fail and allowing the timeout/refund path to eventually return funds to the sender. Alternatively, enforce a minimum transferable amount at the EVM `send()` call site based on the configured decimal precision so dust amounts can never be burned in the first place.

### Proof of Concept
1. Register a token with `local_decimals = 12` and `erc_decimals = 18` (diff = 6, scale = `10^6`).
2. On the EVM side, call `send()` with `params.amount = 500_000` (less than `10^6`), which burns `500_000` wei-equivalent from the caller and dispatches the POST request.
3. On the Substrate destination, `on_accept` computes `U256::from(500_000) / U256::from(10^6) = 0`, `convert_to_balance` returns `Ok(0)`, and the function mints/transfers `0`, emits `TokenReceived { amount: 0, .. }`, and returns `Ok(weight)`.
4. The ISMP request is now marked processed/committed; `on_timeout` never runs. The sender's `500_000` units burned on the EVM side are unrecoverable, while the beneficiary received `0` on the destination chain.

	let dec_str = (value /

	.to_string();
	dec_str.parse::<B>()
}
