### Title
Malformed per-input preprocess vector crashes Bitcoin transaction signing - (File: networks/bitcoin/src/wallet/send.rs)

### Summary
`TransactionSignMachine::sign` trusts every participant’s `Vec<Preprocess<Secp256k1, ()>>` to contain one entry per transaction input and indexes it without checking length. A signer can submit a syntactically valid signing-set entry whose preprocess vector is shorter than `self.sigs.len()`, causing an out-of-bounds panic before signature shares are produced. [1](#0-0) 

### Finding Description
For a Bitcoin transaction, `TransactionMachine::preprocess` creates one `AlgorithmSignMachine` per input and emits a `Vec` with the same number of preprocesses. [2](#0-1)  The corresponding `TransactionSignMachine` declares its preprocess type as `Vec<Preprocess<Secp256k1, ()>>`. [3](#0-2)  During `sign`, it rebuilds per-input commitment maps by iterating `0 .. self.sigs.len()` and indexing each participant’s vector with `commitments[c]`. [4](#0-3)  There is no check that `commitments.len() == self.sigs.len()` or that every vector has the same length, so any short vector panics on indexing. [1](#0-0) 

### Impact Explanation
A participant able to supply preprocess data for a Bitcoin multisignature can crash the signing process instead of merely having their input rejected. This is a reachable denial of service against signing availability for transactions with at least one input, matching the bug class of attacker-controlled structured input causing a panic. [5](#0-4) 

### Likelihood Explanation
The panic requires only a malformed `HashMap<Participant, Vec<Preprocess<..>>>` passed to `sign`; no secret key material, invalid curve point, or protocol violation beyond the inconsistent vector length is needed. It is limited to crashing the local signing operation rather than forging a signature or recovering shares. [5](#0-4) 

### Recommendation
Validate every participant preprocess vector before indexing: reject any whose length differs from `self.sigs.len()` with a `FrostError`, or transpose the map with `get(c).ok_or(...)` instead of direct indexing. [1](#0-0) 

### Proof of Concept
Conceptually, for a transaction with two inputs, an honest machine has `self.sigs.len() == 2`. If a cosigner supplies `commitments.insert(attacker_i, vec![])` or a one-element vector while other signers supply two preprocesses, the rebuild loop evaluates `commitments[1]` for the attacker’s empty/short vector and panics before `taproot_key_spend_signature_hash` or share generation occurs. [6](#0-5)
