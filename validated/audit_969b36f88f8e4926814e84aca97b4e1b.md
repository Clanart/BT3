## Title
Challenge-period boundary check is off-by-one between the EVM handler and the Substrate `ismp-core` reference implementation, letting EVM messages be processed one second/block before the challenge period has actually elapsed by the protocol's own definition — (File: `evm/src/core/HandlerV2.sol`)

## Summary

The external report's core defect is a `<`/`<=` boundary mismatch between two logically-coupled functions (`mint()` using inclusive bounds, `getPrice()` using exclusive bounds) that causes the wrong branch to execute at the exact boundary timestamp. Hyperbridge has a structurally identical mismatch in the "challenge period elapsed" check, which is implemented independently on EVM (`HandlerV2.sol`) and on Substrate (`modules/ismp/core/src/handlers.rs`) using **opposite-strictness comparisons** for what is supposed to be the same security invariant.

## Finding Description

The ISMP protocol defines a `challenge_period`: a mandatory window after a state commitment is stored during which fishermen can submit fraud/veto proofs, before any request, response, or timeout referencing that state commitment may be trusted and processed. This is described explicitly in the docs: *"Assert that the configured `challenge_period` for the `StateCommitment` has elapsed"* [1](#0-0) .

The canonical Rust reference implementation enforces this with a **strict** inequality — the delay must be *greater than* the configured period:

```rust
Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
``` [2](#0-1) 

`validate_state_machine` rejects with `ChallengePeriodNotElapsed` whenever this check is false [3](#0-2) , i.e. it rejects when `delay == challenge_period` exactly.

The EVM `HandlerV2` implements the *same* invariant, but with the **opposite** strictness — it only reverts when the delay is *strictly less than* the period, meaning it accepts when `delay == challengePeriod` exactly:

```solidity
uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
uint256 challengePeriod = host.challengePeriod();
if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
``` [4](#0-3) 

This exact pattern (`challengePeriod > delay` ⇒ revert, therefore pass when `delay >= challengePeriod`) is repeated identically in all four EVM message handlers:
- `handlePostRequests` [5](#0-4) 
- `handleGetResponses` [6](#0-5) 
- `handlePostRequestTimeouts` [7](#0-6) 
- `handleGetRequestTimeouts` [8](#0-7) 

Meanwhile, the testsuite used to validate host implementations (including the Substrate pallet host) explicitly asserts the strict, Rust-core semantics: setting the previous update time to exactly `challenge_period / 2` before `now` should still be rejected, confirming the pallet path uses the strict `>` rule [9](#0-8) , and the pallet's own unit test reuses this exact boundary check [10](#0-9) .

So the two production message-handling paths — EVM `HandlerV2` and Substrate `pallet-ismp`/`ismp-core` — disagree at the exact boundary `delay == challengePeriod`: one treats the challenge period as elapsed, the other does not, exactly analogous to the report's `<`/`<=` mismatch causing two functions meant to encode the same rule to diverge at the edge value.

## Impact Explanation

The challenge period exists specifically so that a fraudulent/vetoable `StateCommitment` cannot be relied upon until fishermen have had the full configured window to contest it (per the Pivots: *"Consensus proofs, state proofs, challenge periods, and state commitments must never let false remote state become trusted"*). Because `HandlerV2` accepts `delay == challengePeriod` (one unit early relative to the strict Substrate/Rust-core definition of "elapsed"), any permissionless caller of `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, or `handleGetRequestTimeouts` can dispatch/timeout a message using a state commitment at the earliest possible instant the EVM contract allows — one second/block before the protocol's own strict definition (used by the tooling that waits for the challenge period, e.g. `waitForChallengePeriod`/`wait_for_challenge_period`, and by the pallet host) considers the window fully closed. This shortens the effective dispute window relied upon to prevent false-state-based execution, request delivery, and relayer-fee refunds — a direct violation of the challenge-period invariant in the Impact Gate. Every EVM host's message path is affected identically since the pattern is duplicated four times.

## Likelihood Explanation

Exploitation requires hitting an exact one-second/one-block window (`delay == challengePeriod`), which is a narrow, low-probability condition to line up with an adversarial state commitment that would otherwise be vetoed — mirroring the "low likelihood, high impact" classification given to the original report. Any permissionless relayer/user can attempt this by simply timing their `handle*` call to land exactly at `block.timestamp == updateTime + challengePeriod`; no privileged role, malicious peer, or leaked key is required.

## Recommendation

Align `HandlerV2.sol`'s boundary check with the strict `ismp-core` semantics used elsewhere in the protocol (`elapsed > challengePeriod`, not `elapsed >= challengePeriod`):

```solidity
if (challengePeriod != 0 && challengePeriod >= delay) revert ChallengePeriodNotElapsed();
```

Apply the same fix consistently to all four occurrences in `evm/src/core/HandlerV2.sol`.

## Proof of Concept

1. A state commitment for height `H` is stored on an `EvmHost`, and `stateMachineCommitmentUpdateTime(H)` is recorded as `T0`.
2. `host.challengePeriod()` returns `P`.
3. At `block.timestamp == T0 + P` exactly, a relayer calls `handlePostRequests` (or any of the other three handlers) with a valid MMR/state proof for height `H`.
4. `delay = (T0 + P) - T0 = P`. The check `challengePeriod > delay` evaluates `P > P` → `false`, so the handler does **not** revert and proceeds to verify the proof and dispatch the request/response/timeout [11](#0-10) .
5. Had the same commitment and timing been evaluated by the Substrate/`ismp-core` reference logic (`verify_delay_passed`), `current_timestamp.saturating_sub(update_time) > delay_period` evaluates `P > P` → `false`, so `validate_state_machine` returns `Err(ChallengePeriodNotElapsed)` and processing is rejected [12](#0-11) .
6. The same commitment/timing pair is therefore accepted on the EVM host and rejected under the protocol's own strict definition — a real one-unit boundary divergence in a security-critical invariant.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

/// This function does the preliminary checks for a request or response message
/// - It ensures the consensus client is not frozen
/// - Checks for frozen state machine is deprecated and malicious state machine commitment will be
///   deleted instead
/// - Checks that the delay period configured for the state machine has elapsed.
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }
