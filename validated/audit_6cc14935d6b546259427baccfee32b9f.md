## Title
Command Injection via Unsanitized Repository Clone Path in "Open in Shell" - ([File: app/src/lib/shells/win32.ts])

### Summary
GitHub Desktop's Windows shell-launcher builds shell command strings by directly interpolating the repository's local file-system path into a template string that is executed with Node's `child_process.spawn(..., { shell: true })`. The repository path is itself derived, with insufficient sanitization, from an attacker-controlled remote URL (via the Clone dialog or the `x-github-client://openRepo/<url>` deep link). This mirrors the `logkitty` bug: untrusted, non-shell-escaped input is formatted into a command string that is then handed to a shell for execution.

### Finding Description
When a user clones a repository, Desktop suggests a local folder name derived from the remote URL through `sanitizeCloneName()`: [1](#0-0) 

This function only guards against path traversal (splitting on `/ \ :`, rejecting `..`/`.`/empty, stripping a trailing `.git`). It does **not** strip characters that are valid in NTFS file names but are control/metacharacters for `cmd.exe` (e.g. `&`, `|`, `%`, `^`, parentheses, spaces). This is used both from the manual Clone dialog and from the `x-github-client://openRepo/<url>` protocol handler flow, where the URL is attacker-supplied and pre-fills the clone target: [2](#0-1) [3](#0-2) 

Once cloned, the resulting `Repository.path` (which now contains the attacker-chosen substring) is used verbatim whenever the user invokes "Open in Shell" from the Repository menu or repository list context menu: [4](#0-3) [5](#0-4) 

The Windows launcher then builds command strings by interpolating this path into a template literal and passes them to `spawn` with `shell: true`, e.g. for Hyper, Alacritty, Git Bash, Cygwin, and Warp: [6](#0-5) [7](#0-6) 

Because `shell: true` on Windows routes the arguments through `cmd.exe /d /s /c`, and `cmd.exe` treats `&`, `|`, `<`, `>` as command separators/control characters even when the surrounding text is wrapped in double quotes, a folder name containing e.g. `& calc.exe &` breaks out of the intended single argument and is executed as a separate command — exactly the same "insecure command formatting" flaw as the reported `logkitty` `adb.ts` issue, just surfacing on the "Open in Shell" launch path instead of an ADB wrapper.

### Impact Explanation
An attacker who controls a git remote URL (via a normal clone flow, a shared repo link, or the `x-github-client://openRepo` protocol handler) can smuggle shell metacharacters into the locally created repository directory name. When the victim later uses the built-in "Open in Shell" feature (a common, expected workflow) for that repository, arbitrary commands execute on the victim's machine with the privileges of the Desktop process — remote code execution triggered purely by cloning a link and clicking a normal application menu item, matching the report's "Valid Impact" criteria (attacker-controlled clone target / clicked link leading to code execution).

### Likelihood Explanation
Requires the victim to (1) clone/open a maliciously-named remote and (2) subsequently click "Open in Shell" for that repository — both are ordinary, expected Desktop actions, not "unnatural user steps." `sanitizeCloneName` is exercised on every generic clone and on deep-link-initiated clones, so the attack surface is reachable without any special privileges.

### Recommendation
- Sanitize (or shell-escape) the working directory path before interpolating it into any string passed to `spawn(..., { shell: true })` on Windows, or switch these Windows shell launches to pass the path strictly as a separate `args[]` element without `shell: true`/string concatenation (as already done in `app/src/lib/shells/linux.ts`'s non-templated cases).
- Alternatively, extend `sanitizeCloneName()` to reject/replace shell metacharacters (`& | < > ^ % " ' \`` and control chars), not just path-traversal separators, consistent with the stricter `sanitizedRepositoryName()` used elsewhere (`app/src/ui/add-repository/sanitized-repository-name.ts`).
- Use the existing `shell-escape.ts` cmd-quoting helpers (`app/src/lib/hooks/shell-escape.ts`) consistently for all `shell: true` invocations in `win32.ts`.

### Proof of Concept
1. Attacker hosts (or points a deep link at) a remote whose URL's final path segment is: `foo & calc.exe & bar.git` (or embeds a more damaging payload such as downloading and executing a payload).
2. Victim clicks a link such as `x-github-client://openRepo/https://evil.example.com/owner/foo%20&%20calc.exe%20&%20bar` or manually pastes the URL into Desktop's Clone dialog; Desktop pre-fills/creates the clone target directory using `sanitizeCloneName()`, producing a folder literally named `foo & calc.exe & bar`.
3. Victim completes the clone; `Repository.path` now ends in `...\foo & calc.exe & bar`.
4. Victim right-clicks the repository (or uses Repository → Open in Shell) and selects "Open in Shell" for a configured shell such as Git Bash, Hyper, Alacritty, or Warp.
5. `win32.ts`'s `launch()` builds e.g. `--cd="C:\...\foo & calc.exe & bar"` and runs it via `spawn(gitBashPath, [...], { shell: true })`; `cmd.exe` parses the embedded `&` as a command separator and executes `calc.exe` (or the attacker's payload) on the victim's machine.

export function sanitizeCloneName(name: string): string | null {
  const components = name.split(/[/\\:]/)

  let lastComponent = ''
  for (let i = components.length - 1; i >= 0; i--) {
    if (components[i].length > 0) {
      lastComponent = components[i]
      break
    }
  }

  if (lastComponent.length === 0) {
    return null
  }

  if (lastComponent.endsWith('.git')) {
    lastComponent = lastComponent.slice(0, -4)
  }

  if (
    lastComponent === '..' ||
    lastComponent === '.' ||
    lastComponent.length === 0
  ) {
    return null
  }

  return lastComponent
}
