### Title
Category-Only Vulnerability Dedup Lets New Security Findings in the Same File Silently Bypass the Stop/Commit-Review Security Hook - (File: `plugins/security-guidance/hooks/llm.py`, `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
The `security-guidance` plugin's Stop/PostToolUse hooks are meant to force Claude to fix newly-introduced vulnerabilities by exiting with code 2 and blocking the turn. The dedup logic that decides whether a finding is "already known" keys only on `(filePath, category)` [1](#0-0)  instead of the specific vulnerable-code instance. This mirrors the reported bug class: a status/identity flag (`AgentStatus.Wounded` / "finding already known") is checked without verifying it still corresponds to the *same* underlying event (`woundedAt == roundId` / the exact vulnerable code). Once any finding of a given category is recorded for a file, a genuinely new, distinct vulnerability of the same category introduced later in the same file is treated as a duplicate and the block is silently skipped.

### Finding Description
`_finding_keys` reduces every finding to a `(filePath, category)` tuple, discarding the actual vulnerable code: [1](#0-0) .

`_dedup_against_state` and every `_record_fire`/`_record_findings`/`_record` callback in `security_reminder_hook.py` use exactly this coarse key to decide both "have we already told the user about this" and "should we record this as told": [2](#0-1)  and again in the push-sweep handler [3](#0-2) , and in the Stop hook's `_record_fire` [4](#0-3) .

The comments explicitly document the *reason* for this design (diff-context lines shift, so exact-code matching "under-dedupes") [5](#0-4) , but the tradeoff has the opposite failure mode from what's described: it "over-dedupes" any future distinct vulnerability of the same category in the same file for the remainder of the `PREVIOUS_FINDINGS_TTL_SEC` window (1 hour by default) [6](#0-5) .

Concretely: if the LLM reviewer once flags, say, a Command Injection in `app.py`, that `(app.py, Command Injection)` pair is persisted into `previous_findings`. If the developer later "fixes" that specific line but a *different, newly introduced* command-injection vulnerability appears elsewhere in `app.py` within the TTL window, `_dedup_against_state`/`_record_fire` will match on the same key and treat it as already-reported, so the Stop/PostToolUse/push-sweep hooks will not exit 2 and will not surface the new vulnerability to the developer or block the turn.

The prompt-level dedup instruction sent to the LLM reinforces the same weakness by explicitly telling the model to match on `(filePath, category)` and not exact code bytes: [7](#0-6) .

### Impact Explanation
This is a hook-bypass of the security-guidance plugin's core enforcement mechanism (blocking via exit code 2 on Stop/PostToolUse). An attacker with no special privileges — anyone who can get the target repo/file to hit one finding in a category (accidentally or deliberately) — effectively immunizes that `(filePath, category)` pair against detection for up to an hour, allowing subsequent, unrelated, and more severe vulnerabilities of the same category in that file to be silently introduced and committed/pushed without the safety hook ever firing. Since this plugin is the project's automated security gate, defeating it undermines the guarantee that newly introduced vulnerabilities in reviewed diffs will be caught and blocked.

### Likelihood Explanation
The condition to trigger this is low-effort and requires no special access: it only requires two edits to the same file within the TTL window that fall into the same vulnerability `category` (a very coarse label — e.g. "SQL Injection", "SSRF", "Hardcoded Secrets" — covering many distinct code locations/patterns). This is a common, realistic occurrence in ordinary development sessions, not an edge case, making the bypass easy to hit unintentionally as well as easy to exploit intentionally.

### Recommendation
Key dedup/record state on a stronger identity than `(filePath, category)` alone — e.g. include a normalized hash of the vulnerable code snippet's surrounding context (line range or AST fingerprint) so that a fix followed by a new, distinct instance in the same category/file is not conflated with the original finding. Alternatively, only suppress re-flagging when the new finding's vulnerable-code snippet substantially overlaps the previously recorded one, falling back to "report as new" whenever no meaningful overlap exists, rather than defaulting to safe-side suppression on category+path collision alone.

### Proof of Concept
1. In a session with the `security-guidance` plugin active, introduce a command-injection vulnerability at line 10 of `app.py` and let a `Stop` or `git commit` PostToolUse fire, causing the hook to flag `(app.py, "Command Injection")` and record it into `previous_findings` via `_record_fire`/`_record_findings` [4](#0-3) .
2. "Fix" that specific line (e.g., replace `subprocess.run(cmd, shell=True)` with a safe call).
3. Within `PREVIOUS_FINDINGS_TTL_SEC` (3600s) [8](#0-7) , introduce a completely different, newly-introduced command-injection vulnerability at line 200 of the same `app.py` (different code, same category).
4. Trigger `Stop` again: the LLM reviewer flags the new finding, but `_dedup_against_state` matches `(app.py, "Command Injection")` against the already-recorded key and drops it [9](#0-8) , so `vulns` becomes empty, the hook exits 0 instead of 2, and the new vulnerability is never surfaced or blocked.
