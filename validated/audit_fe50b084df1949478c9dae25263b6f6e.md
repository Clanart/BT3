## Title
Deep-link driven PR/branch checkout silently adds a remote and fetches from an attacker-influenced clone URL with no user-visible confirmation - (File: `app/src/ui/dispatcher/dispatcher.ts`)

### Summary
The Hubs report shows that a permission gate enforced on the primary UI path (the room's "Create and move objects" toggle) was never applied to a secondary, attacker-reachable entry point (chat `/add` commands), letting an unauthenticated user perform the same privileged action the toggle was meant to block. The structurally equivalent pattern in GitHub Desktop is the `x-github-client://openRepo/...` deep-link handler: the ordinary, user-visible "Clone repository" path forces the user to see and confirm a URL in the Clone dialog before any git network operation runs, but the PR/branch deep-link path performs `git remote add` + `git fetch` + `git checkout` against a URL that is never shown to the user, sourced instead from GitHub API response data and a URL parameter the link itself carries.

### Finding Description
`parseAppURL` accepts a `pr` or `branch` query parameter on `openRepo` deep links [1](#0-0) . `dispatchURLAction` routes any `open-repository-from-url` action straight to `openRepositoryFromUrl` with no additional user prompt [2](#0-1) .

For the PR case, `openPullRequestFromUrl` calls `fetchPullRequest(url, pr)` and then feeds the API's `head.repo.clone_url` and `head.ref` directly into `_checkoutPullRequest` [3](#0-2) . `_findPullRequestBranch` (invoked by `_checkoutPullRequest`) will, if no existing remote matches that clone URL, silently run `addRemote` and then `_fetchRemote` against it before checking out a new local branch [4](#0-3) . None of this surfaces the clone URL to the user or asks for confirmation — it is entirely driven by whatever `head.repo.clone_url`/`head.ref` values are returned for the `pr` number supplied in the link, and that PR number is attacker-chosen since the attacker crafts the link.

Contrast this with the manual "Clone a Repository" flow, where the user must see the resolved URL and explicitly click "Clone" before any equivalent `addRemote`/fetch operation executes [5](#0-4) . The safety/visibility gate that exists on that primary path (user sees and approves the destination URL) has no equivalent on the deep-link PR/branch path — exactly the "primary path has a gate, secondary path doesn't" pattern in the Hubs report.

The `branch` variant is similarly ungated for the actual git operations: `openBranchNameFromUrl` runs `_fetch` (a network operation reaching the repository's configured remote) and then checks out a local branch purely from a link-controlled repository URL and branch string, with only ref-syntax validation via `testForInvalidChars`, not any consent step [6](#0-5) , [7](#0-6) .

### Impact Explanation
Clicking an attacker-supplied `x-github-client://openRepo/...` link (e.g. embedded in a webpage, README, or an "Open in Desktop" style CTA) can cause Desktop to add a new git remote and fetch from it without the user ever seeing which URL is being contacted or being asked to approve the operation, unlike the ordinary Clone flow. This expands the attack surface accepted by "attacker controls a GitHub API object / a link the user clicks / a git remote response" to include automatic remote creation and network fetch, which is the precursor step to any clone/fetch-based compromise (malicious `.gitattributes` filters, hooks fetched via LFS/submodule config, etc., that other Desktop hardening assumes only happens after an explicit, URL-visible Clone confirmation).

### Likelihood Explanation
Requires only that the victim click a single crafted link — no prior authentication, no local access, and no prior compromise, matching the valid-impact bar. The PR-number and branch-name fields are directly attacker-supplied in the link `parseAppURL` accepts, and the fetch/remote-add code path executes unconditionally once `dispatchURLAction` routes the parsed action.

### Recommendation
Route `open-repository-from-url` PR/branch actions through the same user-visible confirmation used by the manual Clone dialog before performing `addRemote`/`_fetchRemote`/checkout — e.g., show the resolved clone URL and require explicit approval, or at minimum surface a non-dismissible notice showing the remote host/URL that is about to be added and fetched, so the deep-link path can't silently perform a privileged network operation the primary UI path always gates behind visible confirmation.

### Proof of Concept
1. Host a public GitHub repository and open a pull request against it from a fork whose `head.repo.clone_url` you control.
2. Send the victim (who has GitHub Desktop registered as the protocol handler) a link: `x-github-client://openRepo/https://github.com/<you>/<repo>?pr=<pr-number>`.
3. When clicked, Desktop calls `openPullRequestFromUrl` → `_checkoutPullRequest` → `_findPullRequestBranch`, which runs `git remote add github-desktop-<owner> <your-fork-clone-url>` and `git fetch` against it — with the destination URL never shown to or confirmed by the user, unlike the Clone Repository dialog flow.   private async openPullRequestFromUrl(
    url: string,
    pr: string
  ): Promise<RepositoryWithGitHubRepository | null> {
    const pullRequest = await this.appStore.fetchPullRequest(url, pr)

    if (pullRequest === null) {
      return null
    }

    // Find the repository where the PR is created in Desktop.
    let repository: Repository | null =
      this.getRepositoryFromPullRequest(pullRequest)

    if (repository !== null) {
      await this.selectRepository(repository)
    } else {
      repository = await this.openOrCloneRepository(url)
    }

    if (repository === null) {
      log.warn(
        `Open Repository from URL failed, did not find or clone repository: ${url}`
      )
      return null
    }
    if (!isRepositoryWithGitHubRepository(repository)) {
      log.warn(
        `Received a non-GitHub repository when opening repository from URL: ${url}`
      )
      return null
    }

    // ensure a fresh clone repository has it's in-memory state
    // up-to-date before performing the "Clone in Desktop" steps
    await this.appStore._refreshRepository(repository)

    if (pullRequest.head.repo === null) {
      return null
    }

    await this.appStore._checkoutPullRequest(
      repository,
      pullRequest.number,
      pullRequest.head.repo.owner.login,
      pullRequest.head.repo.clone_url,
      pullRequest.head.ref
    )

    return repository
  }

  public async _findPullRequestBranch(
    repository: RepositoryWithGitHubRepository,
    prNumber: number,
    headRepoOwner: string,
    headCloneUrl: string,
    headRefName: string
  ): Promise<Branch | undefined> {
    const gitStore = this.gitStoreCache.get(repository)
    const remotes = await getRemotes(repository)

    // Find an existing remote (regardless if set up by us or outside of
    // Desktop).
    let remote = remotes.find(r => urlMatchesRemote(headCloneUrl, r))

    // If we can't find one we'll create a Desktop fork remote.
    if (remote === undefined) {
      try {
        const forkRemoteName = forkPullRequestRemoteName(headRepoOwner)
        remote = await addRemote(repository, forkRemoteName, headCloneUrl)
      } catch (e) {
        this.emitError(
          new Error(
            `Couldn't find PR branch, adding remote failed: ${e.message}`
          )
        )
        return
      }
    }

    const remoteRef = `${remote.name}/${headRefName}`

    // Start by trying to find a local branch that is tracking the remote ref.
    let existingBranch = gitStore.allBranches.find(
      x => x.type === BranchType.Local && x.upstream === remoteRef
    )

    // If we found one, let's check it out and get out of here, quick
    if (existingBranch !== undefined) {
      return existingBranch
    }

    const findRemoteBranch = (name: string) =>
      gitStore.allBranches.find(
        x => x.type === BranchType.Remote && x.name === name
      )

    // No such luck, let's see if we can at least find the remote branch then
    existingBranch = findRemoteBranch(remoteRef)

    // It's quite possible that the PR was created after our last fetch of the
    // remote so let's fetch it and then try again.
    if (existingBranch === undefined) {
      try {
        await this._fetchRemote(repository, remote, FetchType.UserInitiatedTask)
        existingBranch = findRemoteBranch(remoteRef)
      } catch (e) {
        log.error(`Failed fetching remote ${remote?.name}`, e)
      }
    }

    if (existingBranch === undefined) {
      this.emitError(
        new Error(
          `Couldn't find branch '${headRefName}' in remote '${remote.name}'. ` +
            `A common reason for this is that the PR author has deleted their ` +
            `branch or their forked repository.`
        )
      )
      return
    }

    // For fork remotes we checkout the ref as pr/[123] instead of using the
    // head ref name since many PRs from forks are created from their default
    // branch so we'll have a very high likelihood of a conflicting local branch
    const isForkRemote =
      remote.name !== gitStore.defaultRemote?.name &&
      remote.name !== gitStore.upstreamRemote?.name

    if (isForkRemote) {
      return await this._createBranch(
        repository,
        `pr/${prNumber}`,
        remoteRef,
        false
      )
    }
