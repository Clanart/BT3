### Title
Attacker-controlled `WWW-Authenticate` header from a git remote/proxy triggers an unverified "GitHub Enterprise" sign-in flow - ([File: app/src/lib/trampoline/trampoline-credential-helper.ts])

### Summary
The underlying bug class in the report is: a security-critical decision (loan solvency) is made by trusting an externally-supplied, unauthenticated value (a manually pushed price) instead of a properly verified source, and the code has no independent check to catch the discrepancy before it is acted upon. In GitHub Desktop's credential-helper trampoline, the analogous broken invariant is that `getEndpointKind()` classifies a remote host as a legitimate "GitHub"/"enterprise" endpoint by trusting the raw `WWW-Authenticate` header text that Git forwards from the remote server's HTTP response, and this classification directly gates whether Desktop launches its trusted native "Sign in to GitHub Enterprise" OAuth UI for that host — with the actual host-verification check (`isGitHubHost`) only run as a fallback that is skipped once the header is present.

### Finding Description
When Git performs an HTTPS operation (fetch/push/pull/clone) against a remote and gets a 401 challenge, it forwards any `WWW-Authenticate` header(s) to the configured credential helper as `wwwauth[n]=...` fields. GitHub Desktop's trampoline credential helper reads these fields directly from the credential request: [1](#0-0) 

If the value contains `realm="GitHub"`, `getEndpointKind` immediately classifies the endpoint as `'enterprise'` — this classification is derived purely from attacker-controllable response content, with no host allow-list or certificate check, and it short-circuits before the actual network-based verification (`isGitHubHost(endpoint)`) that exists later in the same function for the case where no such header is present: [2](#0-1) 

That classification flows into `getCredential`. When the endpoint kind is not `'generic'` and Desktop has no existing account for it, Desktop prompts the user with its native "GitHub sign-in" flow rather than a generic auth prompt: [3](#0-2) 

`promptForGitHubSignIn` then pre-fills and launches the built-in Enterprise OAuth sign-in wizard, pointed at the attacker's origin, purely because the remote's HTTP response contained the magic string `realm="GitHub"`: [4](#0-3) 

The corrupted value is the `endpointKind` classification (`'enterprise'`) — it is derived from an untrusted, attacker-supplied HTTP response header rather than from a verified GitHub/GHE identity check, yet it is used to decide whether to present Desktop's trusted, chrome-less "Sign in" dialog (which the user is conditioned to trust because it's part of the native app, not a browser tab with a visible URL) for a host the user never explicitly told Desktop was a GitHub server.

### Impact Explanation
This lets an attacker who controls (or can respond as) a git remote/proxy that the user fetches, pushes, pulls, or clones from — e.g., a malicious or compromised Git server, or a MITM/proxy on an untrusted network — force GitHub Desktop's native "Sign in to GitHub Enterprise" flow to open against the attacker's own origin, without the user ever typing that URL or opting into an Enterprise connection. Because the flow is triggered automatically from a background git operation and rendered using Desktop's own trusted sign-in chrome, it materially increases the credibility of a phishing/credential-harvesting attempt and can result in a fraudulent OAuth/account binding: a real `Account` object tied to the attacker's endpoint can end up created in `AccountsStore`, and Desktop will subsequently reuse it to authenticate future operations against that same origin via `findGitHubTrampolineAccount` matching by origin. This satisfies the "unauthorized OAuth or account binding" and "credential exfiltration" impact classes named as valid in the task.

### Likelihood Explanation
The trigger requires no local access, no admin rights, and no prior compromise of the user's machine — only that the user perform a normal HTTPS git operation (fetch/clone/push/pull) against an attacker-influenced remote or through a malicious/rogue proxy that returns a crafted `WWW-Authenticate: ... realm="GitHub"` header on a 401 response. This is a standard, spec-compliant HTTP response the attacker fully controls, matching the report's "attacker controls a git remote/proxy response" primitive.

### Recommendation
Do not trust the `wwwauth[...]` realm string alone to decide whether to launch the trusted GitHub Enterprise sign-in UI. Always perform (or require) the independent `isGitHubHost(endpoint)` verification — or an equivalent authenticated check against a known GitHub API surface — before classifying an unrecognized endpoint as `'enterprise'`/`'github.com'`, regardless of what the remote's HTTP headers claim. At minimum, gate the automatic sign-in prompt on this endpoint being previously known/added by the user (e.g., in Preferences), rather than auto-launching OAuth sign-in for arbitrary origins first encountered via a git response header.

### Proof of Concept
1. Stand up an HTTPS git server (or a MITM proxy) at `https://evil.example.com`.
2. Configure it so that any Git HTTP request without credentials returns `401` with header `WWW-Authenticate: Basic realm="GitHub"`.
3. In GitHub Desktop, add this URL as a remote of an existing repo (or clone from it) and trigger a fetch/push (e.g., `Fetch origin`).
4. Git forwards the `wwwauth[0]=Basic realm="GitHub"` field to Desktop's credential helper via the trampoline.
5. `getEndpointKind` returns `'enterprise'` purely from that header match [5](#0-4) , skipping the `isGitHubHost` network check entirely.
6. Since no Desktop account exists for `evil.example.com`, `getCredential` calls `ui.promptForGitHubSignIn('https://evil.example.com')` [6](#0-5) , which opens Desktop's native "Sign in to GitHub Enterprise" dialog pre-targeted at the attacker's origin [7](#0-6) .
7. The user, believing this is a legitimate in-app GitHub Enterprise connection prompt, completes sign-in against the attacker's server.

  // When Git attempts to authenticate with a host it captures any
  // WWW-Authenticate headers and forwards them to the credential helper. We
  // use them as a happy-path to determine if the host is a GitHub host without
  // having to resort to making a request ourselves.
  for (const [k, v] of cred.entries()) {
    if (k.startsWith('wwwauth[')) {
      if (v.includes('realm="GitHub"')) {
        return 'enterprise'
      } else if (/realm="(GitLab|Gitea|Atlassian Bitbucket)"/.test(v)) {
        return 'generic'
      }
    }
  }

  public promptForGitHubSignIn(endpoint: string): Promise<Account | undefined> {
    return new Promise<Account | undefined>(async resolve => {
      const cb = (result: SignInResult) => {
        resolve(result.kind === 'success' ? result.account : undefined)
        this.dispatcher.closePopup(PopupType.SignIn)
      }

      const { hostname, origin } = new URL(endpoint)
      if (hostname === 'github.com') {
        this.dispatcher.beginDotComSignIn(cb)
      } else {
        this.dispatcher.beginEnterpriseSignIn(cb)
        await this.dispatcher.setSignInEndpoint(origin)
      }

      this.dispatcher.showPopup({
        type: PopupType.SignIn,
        isCredentialHelperSignIn: true,
        credentialHelperUrl: endpoint,
      })
