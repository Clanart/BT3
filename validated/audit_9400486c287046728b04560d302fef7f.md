### Title
Cached FROST preprocess is never unregistered after use, allowing nonce reuse and private key share recovery - (File: coordinator/src/tributary/signing_protocol.rs)

### Summary
Analogous to CVE-2025-61662 — where a GRUB command remains registered after its module is unloaded, leaving a stale entry that can be invoked after its valid lifetime — Serai's coordinator persists a one-time-use FROST preprocess seed in `CachedPreprocesses` and never deletes it. Any later code path that re-enters `preprocess_internal` under the same `context` resurrects the same seed, deterministically regenerating the identical FROST nonces and commitments. If that reuse signs a different message (or a different signer set, which changes the binding factors and challenge), the signer leaks its threshold secret share — the exact "reuse will enable third-party recovery of your private key share" failure the FROST docs warn about.

### Finding Description
`SigningProtocol::preprocess_internal` keys a preprocess seed on `self.context` in the `CachedPreprocesses` DB table. On first call it generates a seed, XOR-encrypts it, and stores it; on every subsequent call it reads the still-present entry back and rebuilds the machine via `AlgorithmSignMachine::from_cache` with the identical `CachedPreprocess` [1](#0-0) . There is no `remove`/`delete` on `CachedPreprocesses` anywhere — the "registration" outlives the resource's one-time-use lifetime, exactly like the orphaned gettext command.

The seed fully determines the nonces: `seeded_preprocess` feeds `*seed.0` into `ChaCha20Rng::from_seed` and derives `Commitments::new` from it [2](#0-1) . The API contract requires the preprocess be deleted after `from_cache` so it is never reused [3](#0-2) .

Reuse is structurally baked in: `share_internal` calls `preprocess_internal` again rather than consuming the preprocess created by `preprocess` [4](#0-3) , and `DkgConfirmer::complete` calls `share_internal` a second time after `share` already ran [5](#0-4) . Because the DB entry persists (including across process restarts), any re-execution of `share`/`complete` for the same `("DkgConfirmer", attempt)` context — e.g., a retry with different submitted `preprocesses` or a different `key_pair`, both of which flow from tributary data — produces a second signature share with identical nonces `(d, b)` but different binding factors/signature challenge `c`. Two shares `d + b·rho + λ·s·c` and `d + b·rho' + λ·s·c'` with known `d,b` commitments are enough to solve for the secret share `s`.

### Impact Explanation
Recovery of a validator's MuSig/FROST secret share under Ristretto/Schnorrkel. Combined with threshold-many compromised shares this compromises the validator-set key pair protecting set transitions; even below threshold it permanently degrades the scheme's security margin. This satisfies the accepted impact class "key share recovery."

### Likelihood Explanation
The stale-state root cause is unconditional: the cache is never invalidated, and `complete` demonstrably triggers a second derivation of the same nonces. Whether the second signing pass binds a different challenge depends on the caller-supplied `preprocesses` map and `key_pair` differing between invocations — e.g., a coordinator crash/restart mid-attempt followed by resubmission with a different signing set. The message and preprocess inputs are externally supplied bytes read via `read_preprocess`, so the differing-input condition is reachable through public protocol data rather than requiring a malicious key-holder.

### Recommendation
Delete the `CachedPreprocesses` entry (a `remove` on the context key) the first time the cached seed is loaded for `sign` — i.e., consume-on-read in `preprocess_internal` when invoked from `share_internal`, or add an explicit invalidation after `share`/`complete` succeeds — so the preprocess cannot be resurrected after its single use. Additionally, `complete` should reuse the `AlgorithmSignatureMachine` produced by `share` rather than re-running `share_internal` and re-signing.

### Proof of Concept
1. For context `("DkgConfirmer", attempt = N)`, call `DkgConfirmer::preprocess()` — stores seed `s` in `CachedPreprocesses`.
2. Call `DkgConfirmer::share(preprocesses_A, key_pair_A)` → emits share `σ₁ = d + b·ρ_A + λ·x·c_A` where `(d,b)` derive from `ChaCha20Rng::from_seed(s)`.
3. Re-enter `DkgConfirmer::share` (or `complete`) with `preprocesses_B` (a different participant subset or different peer preprocess bytes) — `preprocess_internal` reloads the same undeleted seed `s`, regenerating identical `(d, b, D, E)`.
4. The second call emits `σ₂ = d + b·ρ_B + λ·x·c_B`. With `D = d·G`, `E = b·G` known from the broadcast preprocess and `ρ`, `c`, `λ` computable publicly, the observer solves for `d`, `b`, and then the secret share `x` from the two equations — full private key share recovery caused solely by the stale, never-unregistered cache entry.
