### Title
OP_RETURN data is excluded from fee accounting, diverting the intended fee into change - ([File: networks/bitcoin/src/wallet/send.rs](networks/bitcoin/src/wallet/send.rs))

### Summary
`SignableTransaction::new` appends caller-controlled `data` as an `OP_RETURN` output, but calculates transaction weight, required fees, and change using only `payments`. [1](#0-0)  Consequently, a transaction carrying an OP_RETURN pays only the fee required for the smaller transaction without the data output, while any change calculation retains the omitted fee amount as spendable change. [2](#0-1) 

### Finding Description
The transaction constructor accepts up to 80 bytes of public `data` and adds it to `tx_outs` as a zero-value `OP_RETURN` output. [3](#0-2) [4](#0-3)  Both fee calculations pass `payments` to `calculate_weight_vbytes`, not `tx_outs`, so the added output is omitted from the no-change and with-change virtual-size calculations. [5](#0-4) [6](#0-5) 

When change is enabled, the change amount is computed as `input_sat - payment_sat - fee_with_change`, where `fee_with_change` omits the OP_RETURN output. [7](#0-6)  The final transaction nevertheless contains both the OP_RETURN and the inflated change output. [8](#0-7)  The miners’ actual fee is `sum(inputs) - sum(outputs)`, so the portion that should have paid for the OP_RETURN’s weight is instead paid to the change script. [9](#0-8) 

This closely matches the reported bug class: one accounting path commits value to a recipient, while a later/parallel fee calculation uses an incomplete view of the transaction and therefore fails to reserve the intended fee. The same omission also means the standard-weight check does not include the OP_RETURN output. [10](#0-9) 

### Impact Explanation
An unprivileged caller able to supply the transaction `data` can cause the multisig to sign a transaction whose actual fee rate is below the requested `fee_per_vbyte`, while the difference is credited to the change output. For an 80-byte payload, the error is approximately the payload output’s full serialized size because OP_RETURN data is entirely non-witness data. Repeated transactions can systematically underpay miners and misattribute wallet value, and borderline transactions can fail relay or remain unconfirmed.

### Likelihood Explanation
The flaw is deterministic whenever `SignableTransaction::new` receives `Some(data)` because every byte accepted by the `data` length check is appended to `tx_outs` but never represented in either weight estimate. [11](#0-10)  No malformed encoding, malicious validator, leaked key, or invalid curve input is required; ordinary public transaction data is sufficient.

### Recommendation
Represent the OP_RETURN output in the transaction used by `calculate_weight_vbytes`, preferably by passing the complete output list rather than reconstructing only `payments`. Compute both `needed_fee` and `fee_with_change` against the exact output set that will be signed, including the data output and optional change output. Add regression tests asserting `needed_fee() == fee_per_vbyte * transaction().vsize()` for empty, partial, and maximum-size OP_RETURN payloads.

### Proof of Concept
```rust
// Conceptual regression test inside bitcoin-serai's wallet test context.
let fee_per_vbyte = 10;
let data = vec![0xaa; 80];
let change = p2tr_script_buf(scanner_key).unwrap();

// `received` is a normal output returned by `Scanner::scan_transaction`.
let tx = SignableTransaction::new(
  vec![received],
  &[(payment_script, 546)],
  Some(change),
  Some(data),
  fee_per_vbyte,
)
.unwrap();

let actual_vbytes = bitcoin::policy::get_virtual_tx_size(
  i64::try_from(tx.transaction().weight().to_wu()).unwrap(),
  0,
) as u64;

assert!(tx.transaction().output.iter().any(|output| {
  output.script_pubkey.is_op_return()
}));

assert_eq!(
  tx.needed_fee(),
  fee_per_vbyte * actual_vbytes,
  "OP_RETURN output was omitted from fee accounting"
);
```

The assertion fails because `needed_fee` is derived from a transaction containing only `payments`, while `transaction().output` also contains the OP_RETURN output. [12](#0-11)  With change present, `fee()` equals the underestimated amount and the unaccounted value remains in the change output rather than being paid as the requested fee. [9](#0-8) [2](#0-1)
