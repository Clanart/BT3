Confirmed. This is a real, provable analog to the fee-on-transfer bug, and it exists specifically in `WrappedHyperFungibleToken.send()` (and its upgradeable counterpart) — the same class of bug that `IntentGatewayV2.placeOrder()` explicitly hardened against elsewhere in this same repo.

### Title
Fee-on-transfer tokens drain the shared `WrappedHyperFungibleToken` custody pool via unchecked `send()` accounting - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 with `safeTransferFrom(msg.sender, address(this), params.amount)` but never verifies the contract's actual received balance. It dispatches the cross-chain message using the user-supplied `params.amount` rather than the amount actually locked [1](#0-0) . For a fee-on-transfer (or deflationary/rebasing) underlying token, the contract receives less than `params.amount`, yet the destination chain's `HyperFungibleToken.onAccept()` mints the full, uncorrected `message.amount` to the beneficiary [2](#0-1) .

### Finding Description
This is the exact "unsupported fee-on-transfer token" bug class from the external report, but it manifests as a real, exploitable custody-drain in a shared-pool bridge contract rather than a per-user accounting nuisance.

The codebase's own `IntentGatewayV2.placeOrder()` demonstrates the developers are aware of this exact class of bug and fixed it with an explicit balance-before/after check and by mutating `order.inputs[i].amount` to the actually received amount before computing the commitment and escrow record [3](#0-2) . The dedicated Foundry test suite even has a `FeeOnTransferToken` mock and multiple tests asserting "Escrow should match actual received amount" [4](#0-3) .

`WrappedHyperFungibleToken.send()` (and the identical `WrappedHyperFungibleTokenUpgradeable.send()`) has no such protection:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
body: abi.encode(HyperFungibleToken.Message({ ..., amount: params.amount, ... }))
```
There is no balance-before/after diff, and the dispatched `amount` is always the requested amount, never the actual amount locked [5](#0-4) .

Because `WrappedHyperFungibleToken` is a **lock/unlock shared-custody pool** (not a 1:1 mint-per-user vault — the docs describe it as "custodies the underlying token without minting any new supply" and holds funds for potentially many users across many chains), an attacker can:
1. Configure/find a fee-on-transfer (or otherwise deflationary) ERC20 registered as `_underlying` (or simply exploit any underlying token that later becomes fee-on-transfer via upgrade/governance, or any token with transfer hooks that burn a portion).
2. Call `send()` with `params.amount = X`. The pool actually receives `X - fee`, but the dispatched message says `amount = X`.
3. On the destination chain, `HyperFungibleToken.onAccept()` mints the full `X` tokens to the attacker's beneficiary — more “claim” than was actually backed on the source chain.
4. The attacker (or any holder) can then bridge back (`send()` on destination, `onAccept()`/timeout-refund on source) and withdraw the full `X` in underlying tokens from the shared pool via `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` [6](#0-5) , which pulls from the pool's aggregate balance — i.e., from the tokens locked by *other* honest users — since the pool's real underlying balance is short by the accumulated fee amount.

This directly parallels the report's core claim ("user sent 100 XYZ with 10% fee, accounting sets amount to 100, but only 90 is received") but escalates it from "user shortchanges themselves" (harmless in `IntentGatewayV2`, since only the sender is affected there) to "protocol-wide shared custody deficit that lets any bridging user extract more underlying than the pool actually holds" — a genuine loss-of-funds / insolvency vector for `WrappedHyperFungibleToken`.

### Impact Explanation
Every `send()` call with a fee-on-transfer (or any deflationary-transfer) underlying token creates a permanent gap between (a) the aggregate `amount` values circulating as claims across the destination `HyperFungibleToken` mints, and (b) the actual ERC20 balance custodied by `WrappedHyperFungibleToken`. Because the pool is shared across all users of that token pair, this is a loss-of-funds bug: honest users' locked principal becomes partially unrecoverable once the deficit accumulates and the pool cannot fully honor unlock/timeout-refund requests at face value — first-come-first-served withdrawals succeed, later ones revert or drain remaining balance disproportionately.

### Likelihood Explanation
No privileged actor, relayer, or prover is needed — the flaw is triggered by any permissionless call to the public `send()` entrypoint using a deflationary underlying token, matching the intended pivot ("bridged assets ... must move exactly once and only to the rightful beneficiary and amount"). The only precondition is that the deployment's configured `_underlying` be (or become) a fee-on-transfer/deflationary token, which is plausible given `configure()` lets governance point at essentially any ERC20 and the docs explicitly market this contract as a generic "wrapper for existing ERC20 tokens."

### Recommendation
Apply the same fix already used in `IntentGatewayV2.placeOrder()`: snapshot `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom` in `send()`, and dispatch the cross-chain message using the actual delta received rather than `params.amount`. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken`, configure `_underlying` to a token with e.g. a 10% transfer fee (using the same `FeeOnTransferToken` mock already present in the test suite at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. Call `send({amount: 1000e18, ...})`. Verify `IERC20(_underlying).balanceOf(wrapper)` increased by only `900e18`, while the emitted `Sent` event and dispatched ISMP message report `amount: 1000e18`.
3. On the destination `HyperFungibleToken`, observe `onAccept()` minting `1000e18` to the beneficiary — a 100e18 surplus claim relative to the 900e18 actually locked.
4. Have another honest user lock additional underlying tokens via `send()`, then have the attacker bridge back and unlock, showing the pool pays out more than the attacker actually contributed, at the expense of the other user's locked balance.

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {

        if (_isWeth && msgValue >= params.amount) {

            commitment = dispatchWithFeeToken(request);
        }

            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
