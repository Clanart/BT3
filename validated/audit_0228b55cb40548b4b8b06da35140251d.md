### Title
Unbounded quadratic/cubic amplification in `Offer.get_cancellation_coins()` via attacker-controlled duplicate coin announcements causes wallet-side denial of service - (File: chia/wallet/trading/offer.py)

### Summary
`Offer.get_cancellation_coins()` and its helper `detect_dependent_coin()` build per-coin dependency/announcement maps by parsing every `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` condition in every coin spend of an offer, then repeatedly rescans these maps in nested loops without any bound on the number of announcements per coin. An offer counterparty who crafts an offer with many coin spends, each emitting many announcement conditions (well within CLVM cost limits), can make the wallet-side cancellation routine perform superlinear work, mirroring the "duplicate footnote definitions" amplification pattern in the reported CVE: no de-duplication of repeated announcement entries before they are cross-multiplied against every other coin's announcement list.

### Finding Description
`Offer.get_cancellation_coins()` (`chia/wallet/trading/offer.py:425-471`) iterates every coin spend in the offer bundle and, for each spend, appends **all** `CREATE_COIN_ANNOUNCEMENT` and `ASSERT_COIN_ANNOUNCEMENT` conditions found in its output conditions into per-coin lists `announcements[name]` and `dependencies[name]`, with no de-duplication: [1](#0-0) 

It then enters a loop calling `detect_dependent_coin()` repeatedly until no more dependent coins are found: [2](#0-1) 

`detect_dependent_coin()` itself is a triple-nested loop over `names × deps[name] × announcement_dict.items()`: [3](#0-2) 

Because `deps[name]` and `announcement_dict[coin]` are simple lists populated directly from the (unbounded, un-deduplicated) condition list of each coin spend, an attacker who constructs an offer where each coin spend emits a large number of `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions causes the inner-most loop (`for coin, announces in announcement_dict.items(): if dependency in announces`) to become an O(announcements_per_coin) linear scan, executed for every `(name, dependency)` pair across every coin, and this entire scan is re-run once per detected dependent coin in the outer `while True` loop in `get_cancellation_coins`. This is directly analogous to the reported bug class: repeated/duplicated announcement "definitions" are never deduplicated before being cross-multiplied against all other coins' announcement/dependency lists, producing polynomial blowup proportional to (number of coins) × (announcements per coin)² in the worst case.

This code path is reachable by any wallet user processing/cancelling an offer received from an untrusted counterparty — `TradeManager.cancel_pending_offers()` calls `Offer.from_bytes(trade.offer).get_cancellation_coins()` on offers stored from trade negotiation: [4](#0-3) 

### Impact Explanation
A malicious offer counterparty can craft an offer whose coin spends include large numbers of duplicate/cheap `CREATE_COIN_ANNOUNCEMENT` / `ASSERT_COIN_ANNOUNCEMENT` conditions (these conditions are extremely cheap in CLVM cost terms, unlike CREATE_COIN, allowing many to be packed within cost limits). When the victim wallet later attempts to cancel the trade (a normal wallet operation available to any user holding the offer), `get_cancellation_coins()` performs superlinear-to-polynomial work over these announcement lists, which can stall or hang wallet RPC processing — a local, spend-bundle/offer-triggered transaction-processing (wallet-side) denial of service. This does not directly cause fund loss, forged assets, or invalid consensus state, but it degrades wallet availability for the affected user, consistent with the CWE-407-style resource-exhaustion class in the report (Availability impact only).

### Likelihood Explanation
Likelihood is moderate: constructing an offer with attacker-controlled coin spends bearing excessive duplicate announcement conditions is straightforward for any party willing to negotiate/send an offer, and cancellation is a common wallet action a victim would eventually trigger on a stalled/abandoned trade. The blast radius is limited to the wallet processing the malicious offer, not the network or consensus layer.

### Recommendation
- De-duplicate `announcements[name]` and `dependencies[name]` entries (e.g., store as `set[bytes32]` instead of `list[bytes32]`) before use in `detect_dependent_coin()` and `get_cancellation_coins()`.
- Replace the nested-list membership scan in `detect_dependent_coin()` with a reverse index (`dict[bytes32, bytes32]` mapping announcement hash → coin name) built once, turning the lookup from O(coins × announcements) into O(1) per dependency check.
- Impose a reasonable cap on the number of `CREATE_COIN_ANNOUNCEMENT`/`ASSERT_COIN_ANNOUNCEMENT` conditions considered per coin spend when parsing offers for cancellation purposes, rejecting or truncating pathological offers early.

### Proof of Concept
1. Construct an offer (`Offer`) whose underlying `WalletSpendBundle` contains `k` coin spends.
2. For each spend, craft a puzzle/solution that emits `m` distinct `CREATE_COIN_ANNOUNCEMENT` conditions and `m` distinct `ASSERT_COIN_ANNOUNCEMENT` conditions referencing announcements from other coins in the bundle (cheap CLVM ops, so `m` can be in the thousands within block/tx cost limits).
3. Send this offer to a victim wallet (as an offer counterparty) and have them accept/store it via normal trade negotiation.
4. Have the victim wallet call `TradeManager.cancel_pending_offers()` (a standard user action to cancel a pending/stuck trade), which invokes `Offer.get_cancellation_coins()` on the stored offer.
5. Observe that processing time scales with `k * m^2` (nested nested loop in `detect_dependent_coin` re-invoked per iteration of the `while True` loop in `get_cancellation_coins`), causing the wallet to become unresponsive for a duration disproportionate to the ~small offer size, analogous to the reported footnote O(N²) amplification.

```python
def detect_dependent_coin(
    names: list[bytes32], deps: dict[bytes32, list[bytes32]], announcement_dict: dict[bytes32, list[bytes32]]
) -> tuple[bytes32, bytes32] | None:
    # First, we check for any dependencies on coins in the same bundle
    for name in names:
        for dependency in deps[name]:
            for coin, announces in announcement_dict.items():
                if dependency in announces and coin != name:
                    # We found one, now remove it and anything that depends on it (except the "provider")
                    return name, coin
    return None
```
