### Title
Empty Schnorr aggregate is accepted as valid - ([File: crypto/schnorr/src/aggregate.rs](crypto/schnorr/src/aggregate.rs))

### Summary
`SchnorrAggregate::verify` accepts an aggregate containing zero component signatures when `s == 0`. Although `SchnorrAggregator::complete` explicitly refuses to produce an empty aggregate, `SchnorrAggregate::read` can deserialize one and `verify` will accept it. This creates a forged aggregate-signature edge case analogous to missing validation when a supply/member count reaches zero.

### Finding Description
`SchnorrAggregate::read` permits a zero-length `Rs` vector without requiring at least one aggregate member. `SchnorrAggregate::verify` only checks that `self.Rs.len() == keys_and_challenges.len()`; for an empty aggregate and empty verifier input, that check succeeds. It then builds a single statement containing only `(-self.s, C::generator())`. When `s == 0`, this evaluates to the identity and verification returns `true`. [1](#0-0) [2](#0-1) 

This behavior is inconsistent with the producer-side invariant: `SchnorrAggregator::complete` explicitly returns `None` when no signatures were aggregated, showing that an empty aggregate is not intended to be a valid object. [3](#0-2) 

### Impact Explanation
An unprivileged party can submit bytes encoding an empty `SchnorrAggregate` with `s = 0`, and `verify` will accept it whenever the verifier evaluates it against an empty `keys_and_challenges` list. This is an incorrect verifier result for an object the aggregation API deliberately refuses to construct. In any protocol path that treats successful aggregate verification as authorization for a batch/set whose membership can be empty, this permits a forged aggregate acceptance without any signer participation. [2](#0-1) 

### Likelihood Explanation
The malicious encoding is deterministic and publicly constructible: a little-endian `u32` length of zero followed by the canonical encoding of scalar zero. Exploitation requires a caller to invoke `verify` with an empty `keys_and_challenges` list; it does not require malformed point encodings, secret access, validator misbehavior, or a probabilistic collision. [1](#0-0) [4](#0-3) 

### Recommendation
Reject empty aggregates in both deserialization-independent verification and construction paths. At minimum, add:

```rust
if self.Rs.is_empty() {
  return false;
}
```

at the beginning of `SchnorrAggregate::verify`. Preferably also reject `Rs.is_empty()` in `SchnorrAggregate::read`, so callers cannot transport an object that can never be produced by `SchnorrAggregator::complete`. [2](#0-1) [5](#0-4) 

### Proof of Concept

```rust
use ciphersuite::{group::ff::Field, Ciphersuite};
use dalek_ff_group::Ed25519;
use schnorr::aggregate::SchnorrAggregate;

// Encoding:
//   u32_le R_count = 0
//   scalar s = 0
let mut bytes = 0u32.to_le_bytes().to_vec();
bytes.extend(<Ed25519 as Ciphersuite>::F::ZERO.to_repr().as_ref());

let aggregate =
  SchnorrAggregate::<Ed25519>::read::<&[u8]>(&mut bytes.as_ref()).unwrap();

// There are no keys/challenges, yet verification succeeds.
assert!(aggregate.verify(b"some verifier-specific dst", &[]));
```

The acceptance occurs because verification reduces to `multiexp_vartime(&[(0, G)]).is_identity()`, which is unconditionally true for `s == 0`. [4](#0-3)
