### Title
`ThresholdKeys::read` trusts an attacker-controlled `n` to pre-allocate and drive deserialization, enabling amplified memory exhaustion - (File: crypto/dkg/src/lib.rs)

### Summary
`ThresholdKeys::<C>::read` in `crypto/dkg/src/lib.rs` deserializes `t`, `n`, and `i` as raw `u16`s and then uses `n` directly to size `Vec::with_capacity(usize::from(n))` for the `Interpolation::Constant` coefficient list and to bound the `1 ..= n` loop that reads `n` verification shares via `C::read_G`. The `n` value is only validated afterward by `ThresholdParams::new(t, n, i)` inside `ThresholdKeys::new` — after the allocation and the reads have already been driven by the untrusted value. This is the same bug class as CVE-2017-13716: a length field in untrusted bytes controls memory allocation/work before validation. [1](#0-0) 

### Finding Description
The read order is:

1. `C::ID` length and bytes checked (fixed).
2. `t`, `n`, `i` read as `u16`; only `i` is range-checked via `Participant::new` at this point.
3. If `interpolation[0] == 0`, `Vec::with_capacity(usize::from(n))` allocates `n * size_of::<C::F>()` immediately, then attempts `n` `read_F` calls.
4. `secret_share` is read.
5. A `HashMap` of `n` verification shares is populated by `n` `read_G` calls.
6. Only then does `ThresholdParams::new(t, n, i)` reject invalid `t`/`n`/`i` combinations. [2](#0-1) 

Because `n` is a `u16`, a single crafted input of ~10 bytes forces an immediate allocation of up to 65,535 field elements (≈2 MB for 32-byte scalars, ≈3.6 MB for ed448-sized scalars) before any validation, and commits the deserializer to consuming up to `n` scalar + `n` point encodings from the stream. There is no length prefix tied to the actual bytes present, no cap on `n` relative to any expected threshold set, and no chunked/lazy reading as done elsewhere in the codebase (contrast the deliberate chunked read in `networks/ethereum/src/machine.rs` `Call::read`, which exists precisely to avoid this pattern). [3](#0-2) 

### Impact Explanation
An unprivileged party who can supply bytes to `ThresholdKeys::read` (explicitly an untrusted-bytes sink for key material distributed or recovered in DKG flows) can cause repeated ~200,000× amplified allocations per call (a handful of input bytes → ~2 MB committed). Repeated or parallel calls exhaust process memory and crash the validator/processor, mirroring the CVE's "excessive memory allocation and application crash" DoS. The read loop additionally burns CPU/IO proportional to the claimed `n` rather than the input size, and the `HashMap` insert loop for `1 ..= n` performs 65,535 point-deserialization attempts. The impact is availability only — no secret material is at risk — consistent with a Medium severity DoS.

### Likelihood Explanation
`ThresholdKeys::read` is a public deserialization API over `io::Read`; anywhere serialized `ThresholdKeys` (or wrapped structures containing them) cross a trust boundary — peer-provided key material, resumption/recovery blobs, coordinator-supplied data — the attacker controls the `n` byte pair. The trigger is trivial: valid `C::ID`, arbitrary `t`, `n = 0xFFFF`, valid `i`, interpolation byte `0x00`. No valid signature or protocol position is needed since parsing fails only after the allocation is committed.

### Recommendation
- Read and validate `ThresholdParams::new(t, n, i)` before allocating or iterating over `n`, so oversized/invalid sets are rejected upfront.
- Remove the speculative `Vec::with_capacity(usize::from(n))` or cap it to a small constant (e.g., `min(n, 1024)`); grow the vector only as elements are actually read.
- For the `Interpolation::Constant` and `verification_shares` loops, fail fast once the underlying reader hits EOF (already true via `read_exact`), and consider bounding `n` to the maximum participant set the deployment supports.

### Proof of Concept
```rust
// Feeds ThresholdKeys::<C>::read a minimal crafted blob:
// - id_len + C::ID (required prefix check)
// - t = 1, n = 0xFFFF, i = 1 (Participant::new(1) succeeds)
// - interpolation = 0 (Constant) -> Vec::with_capacity(65535) runs
//   allocating ~2MB of C::F before any read_F fails on EOF.

let mut buf = vec![];
buf.extend(u32::try_from(C::ID.len()).unwrap().to_le_bytes());
buf.extend(C::ID);
buf.extend(1u16.to_le_bytes());      // t
buf.extend(0xFFFFu16.to_le_bytes()); // n: max, unvalidated
buf.extend(1u16.to_le_bytes());      // i: valid participant
buf.push(0u8);                       // Interpolation::Constant
// no further bytes needed: allocation occurs, then read_F hits EOF
let _ = ThresholdKeys::<C>::read(&mut buf.as_slice()); // Err, but ~2MB already allocated
```

Caveat: the allocation is bounded at 65,535 elements per call because `n` is a `u16`, so sustained/parallel calls are needed for meaningful exhaustion; this caps severity at Medium rather than High. Other in-scope readers I sampled (`Commitments::read` in `crypto/frost/src/nonce.rs`, `SchnorrAggregate::read` in `crypto/schnorr/src/aggregate.rs`) size their work by the actual bytes consumed or by parameters, not by a claimed-then-unvalidated length, and do not exhibit this pattern.
