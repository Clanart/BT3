### Title
Git's clone-time repository protections are explicitly disabled during untrusted `git clone`, re-enabling symlink/hook-based attacks from a malicious remote - ([File: app/src/lib/git/clone.ts])

### Summary
`clone()` in `app/src/lib/git/clone.ts` builds the environment for `git clone --recursive` and explicitly sets `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, which turns off Git's own built-in clone-time defenses (the mitigations added upstream for the class of `.git`-directory / symlink / case-insensitive-filesystem collision attacks, e.g. CVE-2024-32002/32004/32005/32006/32007-style issues) for every repository Desktop clones, including repositories whose URL the user simply pasted or clicked ("Clone repository", "Open in Desktop" deep links, forked/malicious remotes). This is the exact "invariant" analog to the Hub report: a safety guard that should gate execution of attacker-supplied content is turned off on the very code path that consumes untrusted, attacker-controlled input (a remote repository), while no compensating guard exists elsewhere in the clone pipeline (`clone --recursive` also auto-inits and updates submodules, and hook execution interception via `interceptHooks`/`withHooksEnv` is only wired into `commit`, `merge`, `pull`, `push` — not into `clone`, per [1](#0-0) ). [2](#0-1) 

### Finding Description
`clone()` is the function invoked whenever Desktop clones a URL supplied by the user or by a deep link/"Open in Desktop" action (`open-repository-from-url` in `app/src/lib/parse-app-url.ts`), i.e. a remote fully controlled by an attacker. It composes the child-process environment as:

```ts
const env = {
  ...(await envForRemoteOperation(url)),
  GIT_CLONE_PROTECTION_ACTIVE: 'false',
}
...
const args = ['-c', `init.defaultBranch=${defaultBranch}`, 'clone', '--recursive']
...
args.push('--', url, path)
await git(args, __dirname, 'clone', opts)
``` [3](#0-2) 

`GIT_CLONE_PROTECTION_ACTIVE` is a Git-internal switch used to gate the protections Git added against maliciously crafted repositories that abuse case-insensitive/case-normalizing filesystems, NTFS short names, or symlinked `.git` directories to smuggle content into the real `.git` directory of a clone (historically exploited to write hooks or config files that execute code on the victim's machine during or shortly after `clone`). By passing `GIT_CLONE_PROTECTION_ACTIVE=false`, Desktop is telling the bundled Git binary to *not* apply these protections for exactly the operation where the repository content is fully attacker-controlled (a URL from the internet, a forked repo, or a deep-link "Open in Desktop" clone).

This mirrors the structure of the smart-contract report precisely: in the Hub contract, `operateFlowMatrix()` carries `nonReentrant`, while the sibling function `groupMint()` — which also performs an external call to attacker-controlled code before finalizing state — lacks it. Here, Desktop's own `git` wrapper (`app/src/lib/git/core.ts`) supports intercepting/sandboxing hook execution (`interceptHooks`, `withHooksEnv`) and this is wired into `commit.ts`, `merge.ts`, `pull.ts`, and `push.ts` (per `grep_search` matches), but `clone.ts` does not use `interceptHooks` at all — and additionally goes out of its way to disable Git's own native protection for the operation that is by definition the first point of contact with fully untrusted, attacker-supplied repository content, combined with `--recursive` which also auto-clones/executes config from submodules.

Because `envForRemoteOperation` values are spread before `GIT_CLONE_PROTECTION_ACTIVE: 'false'`, the disabling flag cannot be overridden by anything upstream; it is unconditionally set for every clone Desktop performs, including clones initiated purely by clicking a malicious "Open in Desktop" link, with no user warning or opt-out path visible in this function.

### Impact Explanation
If the underlying Git version's clone-protection mechanism (gated by `GIT_CLONE_PROTECTION_ACTIVE`) is what stands between an attacker-hosted repository and writing/overwriting files outside the intended working tree (e.g., into the real `.git/hooks` via case-collision or symlink tricks on case-insensitive filesystems, which is common on macOS/Windows — both supported Desktop platforms), then disabling it removes Desktop's only defense at the exact point where the attacker fully controls the payload (the cloned repo tree, refs, and submodule definitions). The consequence is potential arbitrary file write outside the intended repo directory and/or execution of attacker-supplied hook code merely by having the user clone or "Open in Desktop" a malicious repository/URL — no further user action required, satisfying the report's required impact category ("attacker controls a cloned/fetched repository... result is code execution, file write... outside the repo").

### Likelihood Explanation
Likelihood depends on the exact Git version bundled with Desktop (via `dugite`) and whether that version's clone-protection logic is truly bypassed by this environment variable for the vulnerable filesystem/config combinations it addresses. I could not confirm from the indexed code alone (a) the exact bundled Git version/patch level, or (b) definitive documentation of what `GIT_CLONE_PROTECTION_ACTIVE=false` disables beyond its name and typical usage as an internal git testing/override knob — this determination requires checking Git's source for the exact behavior gated by this variable in the bundled version, which is outside what the indexed code exposes. Attacker delivery is trivial (any public repo URL, a forked malicious repo, or an "Open in Desktop"/`x-github-client://openrepo/...` deep link processed by `parseAppURL`), requiring no privileged access, no prior compromise, and only a normal "clone" action the app performs unattended.

### Recommendation
- Remove the unconditional `GIT_CLONE_PROTECTION_ACTIVE: 'false'` override in `app/src/lib/git/clone.ts`, or restrict it to a narrowly justified, documented scenario (e.g., only for local/trusted-path clones), and add an inline comment/test explaining why native Git clone protections are safe to disable in this exact code path.
- If disabling it is required for a specific compatibility reason (e.g., legitimate long-path or case handling), gate it behind an explicit check verifying the destination isn't on a case-insensitive filesystem or add Desktop-side equivalent hardening (e.g., post-clone verification that no unexpected paths were written outside `path/.git`).
- Wire `interceptHooks`/`withHooksEnv` (already used by `commit`, `merge`, `pull`, `push`) into the clone/submodule-update path as well, so hooks originating from a freshly cloned, attacker-controlled repository are not executed unsandboxed.
- Add a regression test asserting that cloning a maliciously crafted repository (symlinked `.git`, case-colliding hook paths) does not result in files being written or hooks executed outside the intended clone directory, mirroring the existing `clone-path-safety-test.ts` coverage for path traversal.

### Proof of Concept
```
1. Attacker crafts a Git repository that relies on the case-insensitive-filesystem
   / symlinked-.git-directory technique historically blocked by Git's native
   clone protections (the mechanism gated by GIT_CLONE_PROTECTION_ACTIVE) to
   place a hook (e.g. post-checkout) into the real .git/hooks of the clone
   target rather than the intended working tree location.
2. Attacker distributes the repo URL, or crafts a deep link:
   x-github-client://openrepo/https://evil.example/attacker/repo.git
3. Victim clicks the link (parsed by app/src/lib/parse-app-url.ts as
   'open-repository-from-url') or pastes the URL into Desktop's "Clone
   repository" dialog.
4. Desktop calls clone(url, path, options) in app/src/lib/git/clone.ts, which
   spawns `git -c init.defaultBranch=... clone --recursive -- <url> <path>`
   with GIT_CLONE_PROTECTION_ACTIVE=false in the environment, disabling the
   Git-side defenses that would otherwise reject/neutralize the malicious
   layout.
5. If the bundled Git version's protection is indeed bypassed by this flag for
   the crafted payload, the hook/config file is written into the real .git
   directory and executes on subsequent git operations Desktop performs
   automatically (status refresh, fetch, checkout), without further user
   interaction.
```
Note: step 4/5 depend on the specific bundled Git version's behavior for this flag, which I was unable to verify from the indexed source alone; this should be confirmed against the exact `dugite`/Git version shipped before treating this as a confirmed exploit chain, but the code-level fact — Desktop explicitly disables Git's native clone protections for every clone of a URL that can be fully attacker-controlled, with no compensating hook-sandboxing on the clone path — is verified directly in the repository.

export async function withHooksEnv<T>(
  fn: (env: Record<string, string | undefined> | undefined) => Promise<T>,
  path: string,
  opts: IGitExecutionOptions | undefined
): Promise<T> {
  if (!opts?.interceptHooks || !getHooksEnvEnabled()) {
    return fn(opts?.env)
  }

  const hooks = await Array.fromAsync(getRepoHooks(path, opts.interceptHooks))

  if (hooks.length === 0) {
    return fn(opts?.env)
  }
