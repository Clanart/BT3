## Title
Silent line-index desync between reviewed diff and staged patch on partial commits — ([File: app/src/lib/git/apply.ts])

### Summary
The Tapioca report's broken invariant is: a value captured at time T1 (the pool snapshot used to compute `eligibleTapAmount`) is used to authorize an action at T2 without re-validating that the snapshot still matches reality, causing the accounting to silently exceed its budget. The structural GitHub Desktop analog is a **line-index snapshot** (`DiffSelection`) captured against a diff rendered at T1, which is later re-applied against a **freshly regenerated diff** at T2 (commit time) without verifying line-for-line equivalence — allowing the wrong lines to be silently staged and committed.

### Finding Description
When a user selects specific lines/hunks of a file for a partial commit, the selection is stored as a `DiffSelection`, which is a set of **line indices**, not content hashes: [1](#0-0) 

`_commitIncludedChanges` captures the working-directory file list (with these index-based selections) synchronously, then performs asynchronous work (`formatCommitMessage`, hook execution, git spawning) before the commit is actually written: [2](#0-1) 

The actual staging happens in `stageFiles` → `applyPatchToIndex`, which **re-fetches the diff from disk at that later moment** rather than reusing the diff the user actually reviewed and clicked on: [3](#0-2) 

`formatPatch` then walks the (new) diff's hunks and calls `file.selection.isSelected(absoluteIndex)` purely by numeric line index: [4](#0-3) 

There is no comparison between the diff the selection was computed against and the diff being staged. The app is aware this problem exists — the "before/after" diff-reload path used for interactive selection explicitly acknowledges that "the diff might have changed dramatically since last we loaded it" and only prunes indices, it does not recompute correctness of the mapping: [5](#0-4) 

That guard exists for the *live diff view* (`updateChangesWorkingDirectoryDiff`), but it does not run in the commit path (`_commitIncludedChanges` → `createCommit` → `stageFiles` → `applyPatchToIndex`), which instead calls `getWorkingDirectoryDiff` a second, independent time with no staleness check.

### Impact Explanation
If the on-disk content of a file changes between when the user visually reviews/selects lines (T1) and when Desktop actually stages the patch (T2) — e.g. content rewritten by an LFS smudge filter fetched from an attacker-controlled/malicious remote, by a background operation, or timing-sensitive editor/tooling changes during the commit's async window — the same numeric line indices in the newly-fetched diff may correspond to entirely different content (different additions/deletions, shifted hunks). `formatPatch` will silently include/exclude lines that no longer match what the user actually reviewed and selected, and `git apply --cached` will stage that mismatched content. The result is a commit (and subsequent push) containing content the user never approved — a silent corruption of what the user commits, matching the "silent corruption of what the user commits or pushes" impact category.

### Likelihood Explanation
The likelihood is moderate-to-low and depends on winning a race during the async window between the initial state snapshot in `_commitIncludedChanges` and the second `getWorkingDirectoryDiff` call inside `applyPatchToIndex`. This window is real (message formatting, hook interception, and process spawning are all awaited), and the second diff fetch is unconditionally independent of the first — there is no revalidation as exists elsewhere in the codebase for the live-view path. However, triggering file mutation precisely inside that window from a remote-controlled vector (e.g. a slow/malicious LFS or filter response) requires favorable timing, which is why this is presented as a real, code-supported race rather than a certainty.

### Recommendation
Capture and pass through a single diff/content snapshot from selection-time all the way to `stageFiles`/`applyPatchToIndex`, rather than re-fetching a fresh diff at staging time. Alternatively, before applying the patch, re-verify that the diff used to build the patch is unchanged from the diff shown to the user (e.g., compare blob OIDs or diff content hashes) and abort/re-prompt the commit if it has changed, mirroring the safety logic already present in `updateChangesWorkingDirectoryDiff` at app-store.ts:3478-3493.

### Proof of Concept
1. Select a file with partial line selection in the Changes view (e.g., select only 2 of 10 modified lines).
2. Trigger `_commitIncludedChanges` (click Commit). The selection snapshot (line indices 3 and 7, say) is captured at `app/src/lib/stores/app-store.ts:3685-3689`.
3. During the async gap before `stageFiles` runs (formatCommitMessage / hook execution), have an external process (e.g. an LFS smudge/clean filter response from a malicious remote, or a concurrent write) change the file's content on disk such that the diff hunk boundaries shift (lines inserted/removed above the previously selected lines).
4. `applyPatchToIndex` re-runs `git diff` (`app/src/lib/git/apply.ts:60`) producing a new hunk layout; `formatPatch` applies the *old* numeric indices (3 and 7) against the *new* hunks, staging different lines than the user selected.
5. The commit is created and can be pushed with content the user never reviewed or approved, with no error or warning surfaced.

Note: I was not able to fully trace every filter/hook code path (e.g., LFS smudge invocation timing) inside this indexed codebase to prove the exact external trigger with certainty; that would require deeper runtime tracing that a Devin session with full repo/tooling access could verify.
