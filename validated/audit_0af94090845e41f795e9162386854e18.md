### Title
`ThresholdKeys::read` accepts deserialized key material without verifying the secret share matches its verification share, allowing a mismatched key to be loaded and funds addressed to it to be unspendable - ([File: crypto/dkg/src/lib.rs](crypto/dkg/src/lib.rs))

### Summary
The external report describes insufficient validation of remotely supplied content (a downloaded ZIP) leading to compromise. The Serai analog is insufficient validation of remotely/untrusted supplied serialized `ThresholdKeys`. `ThresholdKeys::read` parses `t`, `n`, `i`, the interpolation table, the secret share, and `n` verification shares from a byte stream, then reconstructs the keys via `ThresholdKeys::new` — which validates parameter ranges and share counts but never checks that `secret_share * G == verification_shares[i]` nor that the verification shares interpolate to a consistent polynomial/commitment set. Loading attacker-crafted serialized keys therefore produces a `ThresholdKeys` whose `group_key()` is derived from attacker-chosen verification shares while the local secret share does not correspond, yielding an address nobody can sign for. ### Finding Description
`ThresholdKeys::read` at crypto/dkg/src/lib.rs:574-632 reads `t`, `n`, `i` (lines 591-602), an interpolation discriminant plus optional `n` coefficient scalars (lines 604-616), a `secret_share` scalar (line 618), and `n` group elements as verification shares (lines 620-623), then calls `ThresholdKeys::new`. `ThresholdKeys::new` (lines 349-391) checks only:

- `verification_shares.len() == n` (lines 355-360)
- participant indices ≤ `n` (lines 361-365)
- `Constant` interpolation only when `t == n` (lines 367-374)

It then computes `group_key` as the interpolation over participants `1..=t` of the supplied verification shares (lines 376-378). There is no check anywhere that:

1. `secret_share * C::generator() == verification_shares[&i]` — the loaded secret share is never bound to the loaded verification shares.
2. The verification shares lie on a degree-`t-1` polynomial at all (any `n` arbitrary points are accepted), so the reconstructed `group_key` under `view()` for different signing subsets is inconsistent — different `included` sets of size `t` interpolate to *different* group keys.

Contrast with `pedpop`'s `KeyMachine::calculate_share`, which explicitly verifies each received share against the sender's commitments via `share_verification_statements` before building `ThresholdKeys` (crypto/dkg/pedpop/src/lib.rs:430-449, 487-499) — the DKG path enforces exactly the consistency invariant that the deserialization path omits.

Reachable path from public input: `ThresholdKeys::read` is the canonical loader for serialized key material (key recovery/migration flows), and the read rules explicitly place untrusted bytes fed to `ThresholdKeys::read` in scope. An attacker supplying the serialized blob controls every field except the fixed curve ID.

### Impact Explanation
A crafted serialized `ThresholdKeys` causes the node to treat `group_key()` — computed from attacker-controlled verification shares — as its own key:

- **Funds reported received that are not spendable.** The scanner/wallet layer derives deposit addresses from `group_key()`. Funds sent to those addresses can never be signed for, because the stored `secret_share` does not equal any share consistent with the verification shares — the FROST signature produced by `view().secret_share()` will fail `verification_share(i)` checks and never aggregate to a valid group signature. The deposit is effectively burned while appearing as legitimately received.
- **Inconsistent group keys across signing sets.** Since the verification shares are arbitrary points, `view()` interpolates `group_key` independently of any polynomial; two different size-`t` subsets derive different group keys, so which "wallet" the funds belong to depends on the signing set — a silent divergence between nodes that loaded different malicious blobs.

This maps to the file-upload class: unvalidated remotely supplied content is installed as authoritative state, with the damage (unspendable funds / corrupted key state) deferred to later use rather than immediate code execution.

### Likelihood Explanation
Likelihood hinges on whether serialized `ThresholdKeys` ever come from a non-local-trusted source (key-recovery import, coordinator-delivered key blobs, or peer-provided backups). Where it occurs, no cryptographic check in `read`/`new` catches the inconsistency — the blob passes canonical-encoding checks for every field, so rejection only happens implicitly at signing time, after funds may already be addressed to the bogus group key. The missing `secret_share * G == verification_shares[i]` check is a single, cheap equality test, and its absence is objectively verifiable at crypto/dkg/src/lib.rs:380-391.

### Recommendation
In `ThresholdKeys::new` (covering both construction and `read`), add:

- `debug_assert`/hard check that `secret_share * C::generator() == verification_shares[&params.i()]`, returning a new `DkgError::InvalidSecretShare` variant on mismatch.
- Optionally, consistency verification that the `n` verification shares lie on a common degree-`t-1` polynomial (e.g., verify that interpolation over an independent size-`t` subset yields the same `group_key`), matching the invariant the PedPoP path enforces via `share_verification_statements`.

### Proof of Concept

```rust
// Attacker crafts a serialized ThresholdKeys blob for curve C:
//   C::ID header (passes curve check)
//   t = 2, n = 3, i = 1
//   interpolation byte = 1 (Lagrange)
//   secret_share = attacker-chosen scalar s' (canonical encoding)
//   verification_shares[1..=3] = three random points P1, P2, P3 (canonical encodings)
let keys = ThresholdKeys::<C>::read(&mut blob.as_slice()).unwrap();

// group_key is derived solely from the attacker-chosen points:
//   group_key = P1*lambda_1 + P2*lambda_2  (for set {1,2})
// No error is raised despite:
assert_ne!(C::generator() * keys.original_secret_share().deref(),
           keys.original_verification_share(Participant::new(1).unwrap()));

// Wallet/scanner reports keys.group_key() as the deposit address.
// Any FROST signing attempt over view({1,2,3}) produces a share whose
// s_i * G != verification_share(i), so no valid group signature is possible:
// funds sent to group_key() are permanently unspendable.
// Additionally, view({1,2}) and view({2,3}) interpolate different group keys.
```

```rust
  /// Read keys from a type satisfying `std::io::Read`.
  pub fn read<R: io::Read>(reader: &mut R) -> io::Result<ThresholdKeys<C>> {
    {
      let different = || io::Error::other("deserializing ThresholdKeys for another curve");

      let mut id_len = [0; 4];
      reader.read_exact(&mut id_len)?;
      if u32::try_from(C::ID.len()).unwrap().to_le_bytes() != id_len {
        Err(different())?;
      }

      let mut id = vec![0; C::ID.len()];
      reader.read_exact(&mut id)?;
      if id != C::ID {
        Err(different())?;
      }
    }

    let (t, n, i) = {
      let mut read_u16 = || -> io::Result<u16> {
        let mut value = [0; 2];
        reader.read_exact(&mut value)?;
        Ok(u16::from_le_bytes(value))
      };
      (
        read_u16()?,
        read_u16()?,
        Participant::new(read_u16()?).ok_or(io::Error::other("invalid participant index"))?,
      )
    };

    let mut interpolation = [0];
    reader.read_exact(&mut interpolation)?;
    let interpolation = match interpolation[0] {
      0 => Interpolation::Constant({
        let mut res = Vec::with_capacity(usize::from(n));
        for _ in 0 .. n {
          res.push(C::read_F(reader)?);
        }
        res
      }),
      1 => Interpolation::Lagrange,
      _ => Err(io::Error::other("invalid interpolation method"))?,
    };

    let secret_share = Zeroizing::new(C::read_F(reader)?);

    let mut verification_shares = HashMap::new();
    for l in (1 ..= n).map(Participant) {
      verification_shares.insert(l, <C as Ciphersuite>::read_G(reader)?);
    }

    ThresholdKeys::new(
      ThresholdParams::new(t, n, i).map_err(io::Error::other)?,
      interpolation,
      secret_share,
      verification_shares,
    )
    .map_err(io::Error::other)
  }
```
