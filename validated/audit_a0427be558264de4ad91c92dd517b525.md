### Title
Single-Step `ChangeAdmin` in Tokenfactory Permanently Freezes Denom Administration on Misconfiguration - ([File: x/tokenfactory/keeper/msg_server.go])

### Summary
The tokenfactory module's `MsgChangeAdmin` handler reassigns the admin of a factory-created denom in a single, irreversible step, with no acceptance step from the new admin. Any admin-controlled denom (created permissionlessly by any account via `MsgCreateDenom`) can have its admin authority permanently and unrecoverably transferred to an unintended or invalid address in one transaction.

### Finding Description
`ChangeAdmin` in `x/tokenfactory/keeper/msg_server.go` directly overwrites the `AuthorityMetadata.Admin` field for a denom as soon as the current admin submits the message, with no two-step "propose then accept" pattern: [1](#0-0) 

The actual state mutation is performed by `setAdmin`, which simply overwrites the stored admin with whatever address was supplied: [2](#0-1) 

`MsgChangeAdmin.ValidateBasic` only checks that `new_admin` is a syntactically valid bech32 address — it does not (and cannot) verify that the address is controlled by anyone, is not a burn/black-hole address, or that the sender actually intended that exact address: [3](#0-2) 

This is the same bug class as the reported `TimeLock.changeOwner` issue: a privileged "owner"/"admin" role is transferred in one atomic step with no confirmation from the receiving party, so any client-side typo, copy-paste error, or accidental use of a non-existent/unspendable address results in an irreversible loss of control. Once the admin field is set to an address nobody controls (or is cleared to `""`), there is no path to recover admin rights — `Mint`, `Burn`, `SetDenomMetadata`, `UpdateDenom`, and any future `ChangeAdmin` for that denom become permanently inoperable, as confirmed by the module's own test asserting that the old admin can no longer act after the change: [4](#0-3) 

### Impact Explanation
Once admin is mistakenly reassigned to an unrecoverable address, the denom's mint/burn/metadata-update/admin-transfer capabilities are permanently frozen — no governance or fallback mechanism exists in the module to reclaim or reset admin authority for a factory denom. For actively-used denoms (e.g., wrapped/bridged assets or reward tokens whose supply is meant to be actively managed), this permanently freezes legitimate future mint/burn operations tied to that denom's economic design, matching the "permanent freezing" impact category.

### Likelihood Explanation
Any account can permissionlessly create a tokenfactory denom (`MsgCreateDenom`) and become its admin, then call `MsgChangeAdmin` at will. Because the change is single-step and irreversible, ordinary operational mistakes (wrong address pasted, use of a module/contract address expected to relay another accept step that doesn't exist, or targeting a not-yet-derived CosmWasm contract address before its instantiation) are sufficient to trigger the freeze — no adversarial coordination is required, only a single transaction from the current admin.

### Recommendation
Adopt a two-step admin transfer pattern for `x/tokenfactory`, analogous to `Ownable2Step`: add a `pending_admin` field to `DenomAuthorityMetadata`, have `MsgChangeAdmin` (or a new `MsgProposeChangeAdmin`) only set `pending_admin`, and require a new `MsgAcceptAdmin` message signed by the `pending_admin` to finalize the transfer, clearing `pending_admin` afterward. Optionally retain a `MsgCancelChangeAdmin` for the current admin to abort an in-flight proposal.

### Proof of Concept
1. Account A calls `MsgCreateDenom` to create `factory/A/mycoin`, becoming its admin.
2. Account A calls `MsgChangeAdmin(denom, new_admin=B)` where `B` is a mistyped/unowned address (still passes bech32 validation in `ValidateBasic`).
3. `ChangeAdmin` in `msg_server.go` succeeds and calls `setAdmin`, immediately overwriting `AuthorityMetadata.Admin` to `B`.
4. Neither A nor anyone else can now call `Mint`, `Burn`, `SetDenomMetadata`, `UpdateDenom`, or `ChangeAdmin` for `factory/A/mycoin`, since all of these require `msg.Sender == authorityMetadata.Admin`, as enforced in `ChangeAdmin`'s own authorization check: [5](#0-4)  — the denom's admin capabilities are permanently frozen.

func (server msgServer) ChangeAdmin(goCtx context.Context, msg *types.MsgChangeAdmin) (*types.MsgChangeAdminResponse, error) {
	ctx := sdk.UnwrapSDKContext(goCtx)

	authorityMetadata, err := server.GetAuthorityMetadata(ctx, msg.Denom)
	if err != nil {
		return nil, err
	}

	if msg.Sender != authorityMetadata.GetAdmin() {
		return nil, types.ErrUnauthorized
	}

	// Validate new admin we change to should be different from current admin
	if msg.NewAdmin == authorityMetadata.GetAdmin() {
		return nil, types.ErrAdminAlreadyExists
	}

	err = server.setAdmin(ctx, msg.Denom, msg.NewAdmin)
	if err != nil {
		return nil, err
	}

func (k Keeper) setAdmin(ctx sdk.Context, denom string, admin string) error {
	metadata, err := k.GetAuthorityMetadata(ctx, denom)
	if err != nil {
		return err
	}

	metadata.Admin = admin

	return k.setAuthorityMetadata(ctx, denom, metadata)
}

	if err != nil {

	}

	_, err = sdk.AccAddressFromBech32(m.NewAdmin)
	if err != nil {
		return sdkerrors.Wrapf(sdkerrors.ErrInvalidAddress, "Invalid address (%s)", err)
	}

	if err != nil {
		return err
	}

	return nil
}
