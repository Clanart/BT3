### Title
Off-by-One Comparison in Bridge Circuit Work Check Allows Operator to Pass with Equal Watchtower Work — (`circuits-lib/src/bridge_circuit/mod.rs`)

### Summary

The `bridge_circuit` function uses a strict `<` comparison to check whether the operator's total work exceeds the maximum watchtower work. When the two values are equal, the circuit does not panic and the operator's proof is accepted. The protocol invariant — stated explicitly in both the module docstring and `docs/bridge-circuit.md` — requires the operator's work to be **strictly greater than** the maximum watchtower work. The equality boundary is handled incorrectly, directly mirroring the Morpho close-factor bug class.

### Finding Description

In `circuits-lib/src/bridge_circuit/mod.rs`, the work comparison is:

```rust
// If total work is less than the max total work of watchtowers, panic
if total_work < max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

The module-level docstring states the circuit "ensures that an operator's claimed Bitcoin chain state is valid and that it has **more** cumulative proof-of-work than any challenging watchtower." [2](#0-1) 

`docs/bridge-circuit.md` reinforces this: "Asserts that the Operator's `total_work` from their HCP is **greater than** the `max_total_work` from the Watchtowers." [3](#0-2) 

The `TotalWork` type is a `[u8; 16]` big-endian array (the lower 128 bits of the 256-bit cumulative work, produced by `work_conversion`): [4](#0-3) 

The HCP's total work is sliced from the same lower 128 bits: [5](#0-4) 

`TotalWork` derives `PartialOrd` over `[u8; 16]`, which is lexicographic — correct for big-endian byte arrays. [6](#0-5) 

When `total_work == max_total_work`, the condition `total_work < max_total_work` is `false`, so the circuit does **not** panic and the operator's proof is accepted. The correct guard is `total_work <= max_total_work`.

### Impact Explanation

The bridge circuit is the sole on-chain arbiter of whether a challenged operator's payout was on the canonical Bitcoin chain. If an operator can pass the circuit with equal work to a watchtower's chain, they can claim reimbursement for a payout that was not provably on the canonical chain. A successful exploit allows the operator to:

1. Operate on a fork chain whose lower 128 bits of cumulative work equal the canonical chain's value.
2. Produce a valid HCP for that fork chain.
3. Pass the work comparison check (incorrectly).
4. Claim operator collateral reimbursement for a payout that was not on the canonical chain, resulting in loss of bridged BTC from the bridge vault.

The remaining circuit checks (SPV, LCP, storage proofs) still apply, but they are scoped to the operator's claimed chain — if the operator controls the fork, those checks can be satisfied within the fork context.

### Likelihood Explanation

On mainnet, achieving exactly equal lower-128-bit total work between two chains is computationally infeasible under normal conditions. On testnet4 or regtest (where the protocol is actively deployed and tested), it is trivially achievable. The bug is a clear invariant violation regardless of network, and the equality boundary is a reachable code path that any watchtower can trigger by submitting a challenge with work exactly matching the operator's chain tip.

### Recommendation

Change the comparison from strict `<` to `<=` to enforce the stated invariant that the operator's work must be **strictly greater than** the maximum watchtower work:

```rust
// Correct: panic if operator work is NOT strictly greater than max watchtower work
if total_work <= max_total_work {
    panic!(
        "Insufficient total work: Total Work {total_work:?} - Max Total Work: {max_total_work:?}",
    );
}
``` [1](#0-0) 

### Proof of Concept

1. Deploy Clementine on regtest with `FINALITY_DEPTH=1`.
2. Operator performs a payout on a fork chain. Compute the fork chain's lower-128-bit total work value `W`.
3. A watchtower submits a challenge with a Work-Only Proof whose `work_u128` equals exactly `W` (achievable on regtest by mining the same number of blocks at the same difficulty).
4. The operator constructs a `BridgeCircuitInput` with `hcp.chain_state.total_work[16..32] == W` and `max_total_work == W`.
5. The circuit evaluates `total_work < max_total_work` → `W < W` → `false` → no panic.
6. The circuit proceeds to commit a valid journal hash, and the operator's proof is accepted despite the watchtower having submitted equal work — violating the canonical-chain invariant.
